This confirms the exploitable binding mismatch. `Handler#stacks` resolves the target `Repository`/`Stack` using `payload.dig('repository', 'full_name')` [1](#0-0) , while `WebhooksController#verify_signature` authenticates the webhook using a completely different field: `repository_owner` = `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`, which selects the `Shipit.github(organization:)` config (and thus the `webhook_secret` used for HMAC verification) [2](#0-1) , [3](#0-2) .

### Title
Webhook signature verification is bound to `repository.owner.login`/`organization.login` while the acted-upon repository is taken from `repository.full_name` - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
When Shipit is configured with multiple GitHub Apps/organizations (documented, supported configuration — see `config/secrets.development.shopify.yml` and `test/dummy/config/secrets_double_github_app.yml`), each organization has its own `webhook_secret` [4](#0-3) . `WebhooksController#verify_signature` picks which secret to verify the request against solely from `repository_owner` (`repository.owner.login` or `organization.login`) [3](#0-2) , then calls `github_app.verify_webhook_signature` [5](#0-4) . But every event handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc.) resolves the target `Stack`/`Repository` from a *different* payload field, `repository.full_name` [1](#0-0) , [6](#0-5) . Nothing enforces that the owner segment of `repository.full_name` matches `repository.owner.login`/`organization.login`.

### Finding Description
The binding that must hold is: `organization authenticated == organization of the repository written`. In this engine that equality is:
`repository_owner (used to pick webhook_secret) == owner(repository.full_name) (used to select the Stack that gets mutated)`.

Because these are two independent, attacker-controlled JSON fields in the same webhook body, an attacker who controls (or compromises) one legitimately-registered, low-privilege GitHub organization/App installation configured in Shipit's multi-org `github:` config can craft a webhook payload where:
- `repository.owner.login` (or `organization.login`) = the attacker's own org (so the signature validates with the attacker's own legitimate `webhook_secret`), and
- `repository.full_name` = `"victim-org/victim-repo"` (any repository/stack already registered in Shipit, belonging to a different organization).

`verify_signature` succeeds because the signature is checked against the attacker-org's own valid secret. `Handler#stacks`/`#repository_name` then resolves and acts on the victim's `Repository`/`Stack` looked up by `full_name`, with no re-check that this repository belongs to the org that was actually authenticated [1](#0-0) .

### Impact Explanation
Depending on the handler triggered this allows an attacker who controls one configured (but otherwise unprivileged w.r.t. the victim stack) GitHub organization to forge state-changing webhook events against another organization's stack, e.g.:
- `push` → `GithubSyncJob`/`stack.sync_github` forcing a sync to an attacker-chosen `expected_head_sha` on the victim stack's branch [6](#0-5) , which can influence what gets deployed.
- `status`/`check_suite` → forging CI status on victim commits, bypassing `ci.require`/`ci.blocking` deploy gating.

This crosses the "unauthorized deploy/rollback" and "cross-repository writes" bar (High/Critical) because a party never granted any access to the victim repository can inject verified-looking webhook events that alter the victim stack's deploy-eligibility state.

### Likelihood Explanation
Requires the attacker to control (or have compromised) at least one GitHub organization that is itself configured as a legitimate, signed webhook source in Shipit's `github:` multi-org secrets (this is an explicitly documented, supported deployment mode — see `docs/setup.md` and `test/dummy/config/secrets_double_github_app.yml`). No Shipit session, API token, or the victim's `webhook_secret` is required — only a correctly-signed request under the attacker's own org's secret. This is a realistic scenario for shared/multi-tenant Shipit instances serving several GitHub orgs.

### Recommendation
After resolving `repository_owner` and verifying the signature, re-derive the organization from `repository.full_name` (or `organization.login`) and require it to match `repository_owner` before dispatching to handlers; alternatively, have `Handler#stacks` filter by `repositories.owner == verified_organization` in addition to `full_name`, rather than trusting `full_name` alone as the sole binding key.

### Proof of Concept
1. Configure Shipit with two GitHub orgs, `OrgA` (attacker-controlled) and `OrgB` (victim), each with its own `webhook_secret`, as shown in `test/dummy/config/secrets_double_github_app.yml`.
2. Attacker sends a `push` webhook to `/github/webhooks` with `X-Github-Event: push`, body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": { "full_name": "OrgB/victim-repo", "owner": { "login": "OrgA" } }
}
```
signed with `OrgA`'s `webhook_secret` in `X-Hub-Signature`.
3. `verify_signature` calls `Shipit.github(organization: 'OrgA')` (from `repository_owner`) and validates successfully because the attacker used `OrgA`'s real secret [5](#0-4) .
4. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("OrgB/victim-repo")` [1](#0-0)  and triggers `stack.sync_github(expected_head_sha: 'attacker-chosen-sha')` on the victim's stack, even though the request was never authorized by `OrgB`.
