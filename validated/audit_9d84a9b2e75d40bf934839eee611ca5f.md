### Title
Incorrect reset of the AA response counter on chain revert allows the `MAX_RESPONSES_PER_PRIMARY_TRIGGER` cap to be bypassed - (File: `aa_composer.js`)

### Summary
`handleTrigger()` in `aa_composer.js` enforces a hard cap on the number of AA responses that can be produced within a single primary trigger's call chain via `arrResponses.length >= constants.MAX_RESPONSES_PER_PRIMARY_TRIGGER` [1](#0-0) . This cap is the equivalent of Xen's "linear-pagetable depth" restriction: it exists to bound the amount of work (DB writes, batch writes, formula evaluation) one trigger unit can force the network to perform. When a chain of secondary triggers fails and `revert()` is invoked, the code does `arrResponses.splice(0, arrResponses.length); // start over` [2](#0-1) , wiping the shared counter back to zero, exactly analogous to how the Xen bug reset the `linear_pt_entry` count when resuming a partially-validated pagetable and thereby dropped the tracked state that was supposed to prevent exceeding the depth limit.

### Finding Description
`arrResponses` is a single array shared by reference across the *entire* recursive tree of primary + secondary AA triggers spawned from one trigger unit (see how it is threaded through `trigger_opts` and passed unchanged into every recursive `handleTrigger(trigger_opts)` call, e.g. `child_trigger_opts.arrResponses` inherited from `{ ...trigger_opts }` in `handleSecondaryTriggers` [3](#0-2) ). Its length is checked at the top of every invocation of `handleTrigger` before an AA is allowed to execute, to enforce the global response cap: [4](#0-3) 

However, in `revert()` (reached only for the primary/top-level trigger, when one of several secondary AA branches errors out), the shared counter is explicitly zeroed: [5](#0-4) 

This means that any AA responses that were already generated and counted against the cap before the failure (i.e., work that was actually performed — formula evaluation, balance updates, response records) are erased from the bookkeeping array, even though the DB-level `ROLLBACK TO SAVEPOINT initial_balances` only reverts data written *after* the initial balance savepoint, not necessarily undoing the CPU/formula-evaluation cost already spent. After the reset, `bounce(err)` is invoked, which itself calls `finish()` → `addResponse()` → pushes exactly one new bounce response back onto the now-empty `arrResponses`. Because the counter has been reset to (effectively) 1 instead of reflecting the true cumulative count of AA invocations attempted in this trigger's processing, any code path or future extension that relies on `arrResponses.length` (or `number_of_responses`/`previous_aa_responses`, which are derived from it, see `objValidationState.number_of_responses = arrResponses.length` [6](#0-5) ) to bound resource consumption sees stale/incorrect state, mirroring the Xen root cause: an anti-abuse counter is reset on a "resume" path (recovering from a failed/partial evaluation) rather than being correctly preserved or fully unwound together with the state it is meant to protect.

### Impact Explanation
This falls under "node disagreement on validity/stability" and computational-DoS risk within the reachable AA-trigger surface: an attacker who posts a single trigger unit can craft an AA chain that builds up many secondary AA invocations (each performing formula evaluation, balance/state updates and DB writes) up to just under the cap, deliberately causes the final branch to fail so `revert()` fires and the counter resets to zero, and is then free to trigger the deep chain machinery again in the same transaction context in the belief that the cap resource-bounding logic no longer reflects real cumulative work. Because `MAX_RESPONSES_PER_PRIMARY_TRIGGER` (default 10, see `constants.js`) is the sole global guard against unbounded per-trigger AA response chains [7](#0-6) , any bypass of its accounting undermines the anti-spam/anti-DoS assumption baked into AA processing performed identically by every full node validating/executing the unit, risking excess per-unit computation that every node must redo, i.e., a shared-resource exhaustion vector rather than a purely local one.

### Likelihood Explanation
Reachability is straightforward: an unprivileged user only needs to post one trigger unit paying an AA whose definition posts payments to a chain of other AAs, and arrange for one AA deep in the chain to return an error (many ways exist: insufficient balance for an asset, a bounce condition, a thrown formula error). No special privileges, hub/peer trust, or non-deterministic timing is required — the revert path is deterministically reachable through normal `oscript` logic, which is well documented and tested (`test/aa_composer.test.js` contains chained-AA and bouncer test cases exercising this exact machinery) [8](#0-7) .

### Recommendation
Do not reset `arrResponses` to empty in `revert()`. Preserve the true cumulative count of AA invocations attempted during trigger processing separately from the list of *committed* responses that get persisted/broadcast, so `MAX_RESPONSES_PER_PRIMARY_TRIGGER` and related derived values (`number_of_responses`, `previous_aa_responses`) cannot be reset by triggering a controlled revert. If the array must be cleared for correctness of the response payload, track total attempted AA calls in a separate monotonic counter that is never rolled back within the same trigger-processing transaction, and enforce the cap against that counter instead of `arrResponses.length`.

### Proof of Concept
Not independently reproducible/confirmed with a runnable exploit in this pass — the review is based on static code analysis of `aa_composer.js`. To confirm exploitability, a Devin session with full repo/test access should: (1) construct a primary AA that forwards to N secondary AAs (N close to `MAX_RESPONSES_PER_PRIMARY_TRIGGER`), (2) make the last one bounce with an error to trigger `revert()`, (3) inspect `arrResponses.length` and repeat the chain-building logic to verify whether the cap can be circumvented across repeated revert cycles within one trigger's processing, and (4) measure whether this allows exceeding the intended bound on AA responses/DB writes per trigger unit.
