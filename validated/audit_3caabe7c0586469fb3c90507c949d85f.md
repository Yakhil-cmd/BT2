### Title
`StatusHandler#process` writes GitHub statuses to any commit sharing a sha across all repositories/stacks, including `detached: true` commits - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target commit(s) with `Commit.where(sha: params.sha)`, an unscoped query that is filtered neither by the payload's repository nor by `reachable` (`detached: false`) [1](#0-0) . Since the `status` webhook's `params` schema doesn't even collect a `repository` field, `create_status_from_github!` is invoked against every `Commit` row that matches the given sha regardless of which stack/repository it belongs to, or whether it is `detached: true` (i.e., logically superseded/rewritten history) [2](#0-1) .

### Finding Description
The binding that should hold is: `commit.stack.repository == Repository.from_github_repo_name(payload.repository.full_name)` AND `commit.detached == false`, for every `Commit` that receives a new `Status` from a `status` webhook. In the actual code this binding never appears — `Commit.where(sha: params.sha)` performs a global, cross-tenant, cross-stack lookup with no repository join/filter and no `.reachable` scope [3](#0-2) .

Contrast this with the base `Handler` class, which does define a `stacks`/`repository_name` helper intended to scope work to the payload's own repository [4](#0-3) , and with the `reachable` scope defined on `Commit` (`where(detached: false)`) which other code paths (e.g. `blocked?`) do use [5](#0-4) , [6](#0-5) . `StatusHandler` uses neither.

`WebhooksController#verify_signature` only validates that the request is a legitimately signed webhook from *some* GitHub organization known to Shipit (`Shipit.github(organization: repository_owner)`); it does not confirm that the target commit sha actually belongs to that organization's repository [7](#0-6) . Consequently, an attacker who controls any repository already configured as a Shipit-tracked repository (their own fork/org, which they can legitimately register and receive a valid webhook secret for) can send a genuinely-signed `status` webhook event with an arbitrary, publicly-known commit sha belonging to a *different, victim* repository/stack. Because `sha` is a public/globally-knowable value (visible via git history, GitHub UI, or the target Shipit instance's own commit list), no sha collision is needed — the attacker simply copies a known sha from the victim stack into their own webhook's `sha` field. `Commit.where(sha:)` matches that row in the victim's stack, and `create_status_from_github!` writes an attacker-controlled `state`/`description`/`target_url`/`context` into the victim's `Status`, updating `commit.status`/`deployable?` calculations and potentially triggering `schedule_continuous_delivery`/`stack.schedule_merges` for the victim stack [8](#0-7) , [9](#0-8) .

The `detached: true` sub-case in the question is a specific instance of this same missing scoping: because there is no `.reachable` filter either, even commits that have been superseded/rewritten (`detached: true`, e.g. after a force-push/rebase via `detach_children!` [10](#0-9) ) still match `Commit.where(sha:)` and get a live `Status` row written and persisted (`has_many :statuses, ... dependent: :destroy`) [11](#0-10) .

### Impact Explanation
An attacker who has any repository registered in the same Shipit instance (no maintainer/operator privilege required, just a repo they can send real GitHub webhooks from) can, per request, write a forged CI status onto an arbitrary commit sha in a completely unrelated victim repository/stack — including logically detached/superseded commit rows that should have been quarantined. This matches the "payload for one repository mutating another's stack/commit" critical-impact category: it can flip a victim commit from failing to "success", potentially enabling `deployable?`/`schedule_continuous_delivery` to fire for the victim stack, or conversely mark a legitimate victim commit as failing/blocked, corrupting historical CI records relied upon by downstream reporting/audit. The attack is repeatable against any sha the attacker can observe and against any repository configured on the same Shipit instance.

### Likelihood Explanation
Preconditions: the attacker needs at least one repository/organization already onboarded to the target Shipit instance (common in multi-tenant/self-service Shipit deployments where any team can add their own repo) so that `verify_signature` succeeds for a webhook they can legitimately trigger (e.g., by using the GitHub API/UI on their own repo, or via GitHub Apps status API against their own repo). They also need the target sha, which is public. No Shipit session, API token, or GitHub secret theft is required. This is straightforward and repeatable.

### Recommendation
Scope the lookup in `StatusHandler#process` to the payload's own repository and to reachable commits, e.g. require `repository.full_name` in the params schema and query via `stacks.flat_map(&:commits).merge(Commit.reachable).where(sha: params.sha)`, or join through `stack: :repository` similar to other handlers (`PullRequest::EditedHandler#pull_request`) and add `.reachable` to exclude `detached: true` rows.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "does not write a status to a commit belonging to another repository" do
  victim_stack = shipit_stacks(:shipit)
  victim_commit = victim_stack.commits.create!(sha: 'deadbeef' * 5, message: 'victim commit')

  attacker_repository_payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'repository' => { 'full_name' => 'attacker-org/attacker-repo' }
  }

  assert_no_difference -> { victim_commit.statuses.count } do
    Shipit::Webhooks::Handlers::StatusHandler.call(attacker_repository_payload)
  end
end

test "does not write a status to a detached commit" do
  stack = shipit_stacks(:shipit)
  detached_commit = stack.commits.create!(sha: 'cafebabe' * 5, message: 'detached', detached: true)

  payload = { 'sha' => detached_commit.sha, 'state' => 'success' }

  assert_no_difference -> { detached_commit.statuses.count } do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end
end
```
Both assertions currently fail (the status count increments) because `Commit.where(sha: params.sha)` in `app/models/shipit/webhooks/handlers/status_handler.rb:21` neither joins on repository nor applies `.reachable`.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
