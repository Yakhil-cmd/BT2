## Analog Vulnerability Found

### Title
Webhook signature verification selects the trust boundary (GitHub App/secret) from mutable, unsigned request parameters instead of the signed payload - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The reported bug class is about a security check whose result is derived from a value that gets silently swapped out (`vd = vd.intersectValidationData(vd)` combining a value with itself, or one policy's result overwriting another's) so the final decision no longer reflects the full, intended set of authenticated data. In Shipit, the webhook signature-verification step picks *which* GitHub App/organization secret to validate the signature against using `WebhooksController#repository_owner`, which reads from `params` (`ActionController::Parameters`, merged from route/query and body), while the handler code that actually mutates state re-parses the raw HTTP body independently. These two lookups are not guaranteed to agree, breaking the binding: *the organization whose webhook secret authenticated the request* must equal *the repository the payload handlers act on*.

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App configuration used to validate the HMAC signature by calling `repository_owner`: [1](#0-0) [2](#0-1) 

`repository_owner` reads from Rails' `params`, which (per `ActionDispatch::Http::Parameters#parameters`) is built by merging query-string parameters over JSON-body-derived parameters at the top level. Because this merge is shallow, a query string like `?repository[owner][login]=attacker-org` can fully replace the `repository` key of `params` that would otherwise have come from the JSON body, decoupling `repository_owner` from what is actually inside the signed raw body.

Meanwhile, the `create` action re-parses the literal raw HTTP body independently of `params` and hands that untouched hash straight to the event handlers: [3](#0-2) 

Handlers resolve the target repository/stack purely from that re-parsed body's `repository.full_name`, with no re-check of which organization's secret was used to authenticate the request: [4](#0-3) [5](#0-4) 

Shipit explicitly supports multiple independently-configured GitHub Apps/organizations sharing the single `/webhooks` endpoint, each with its own `webhook_secret`: [6](#0-5) [7](#0-6) 

Consequently, an attacker who legitimately controls the GitHub App/webhook secret for **one** org configured in `Shipit.github` (e.g., they administer `attacker-org`, which the Shipit operator also tracks) can:
1. Craft an arbitrary raw JSON body whose `repository.full_name` claims to be a **different**, victim-owned repository/stack tracked by the same Shipit instance.
2. Compute a valid `X-Hub-Signature` HMAC over that raw body using the `attacker-org` webhook secret they legitimately know.
3. Append `?repository[owner][login]=attacker-org` (or rely on top-level `organization.login` similarly) so `verify_signature` selects and validates against `attacker-org`'s secret — which succeeds, because the signature genuinely matches that secret and that exact raw body.
4. The `create` action then dispatches the same raw body — whose `repository.full_name` names the victim's repository — to `PushHandler`, `StatusHandler`, `PullRequest::*Handler`, `CheckSuiteHandler`, etc., which act on the victim stack/repository with no cross-check that its owning org matches the org whose secret authenticated the delivery.

This exactly mirrors the report's bug class: the "check" (which org's key authenticates the delivery) and the "effect" (which repository's state handlers mutate) are drawn from two different representations of attacker-influenced input instead of being the same, intersected value.

### Impact Explanation
An attacker with legitimate GitHub App/webhook-secret access for only one org tracked by a shared Shipit instance can forge webhook deliveries impersonating any other tracked repository. Depending on which handler fires, this enables:
- Forcing `GithubSyncJob`/`stack.sync_github` on arbitrary victim stacks (`PushHandler`), potentially advancing deploy state.
- Forging `check_suite`/`status` events to manipulate a victim stack's release/deployable status (`StatusHandler`, `CheckSuiteHandler`), which can gate `continuous_deployment` automation.
- Forging `pull_request` events to open/close/archive review-stack deployments (`ReviewStackAdapter`, `ClosedHandler`, `LabelCapturingHandler`) for a victim repository.

Because these mechanisms can influence continuous-deployment triggers and deploy/rollback lifecycle state for repositories the attacker does not own, the impact falls into the "unauthorized deploy/rollback" category (Critical), contingent on how the victim stack's `shipit.yml`/CD settings react to forged events.

### Likelihood Explanation
Exploitation requires the operator to run Shipit in the documented multi-organization mode (`config/secrets.yml` keyed per-org, each with its own `webhook_secret`) and to track at least one repository belonging to an organization the attacker legitimately controls (a supported, documented configuration, not a misconfiguration). Given that, no further privilege (no Shipit session, no `ApiClient` token) is needed — only the ability to craft an HTTP request with a chosen query string and a signature computed from a secret the attacker legitimately possesses.

### Recommendation
Derive `repository_owner` (and any other value used to select the verification key) exclusively from the parsed raw body used for signature verification and processing — never from `ActionController::Parameters`, which can be polluted by query-string data. After selecting the app/org by that trusted value, re-verify that the same `repository.full_name`'s owner matches the organization whose secret validated the signature before invoking any handler.

### Proof of Concept
1. Shipit is configured with `github: { attacker-org: {..., webhook_secret: S1}, victim-org: {...} }` and tracks `attacker-org/some-repo` and `victim-org/victim-repo`.
2. Attacker crafts `body = {"ref":"refs/heads/main","after":"<arbitrary-sha>","repository":{"full_name":"victim-org/victim-repo", ...}}`.
3. Attacker computes `sig = "sha1=" + HMAC-SHA1(S1, body)` (S1 is the webhook secret they know for `attacker-org`, e.g. because they created the app on their own org).
4. Attacker sends:
   `POST /webhooks?repository[owner][login]=attacker-org` with header `X-Hub-Signature: sig`, `X-Github-Event: push`, and the above `body`.
5. `verify_signature` computes `repository_owner` from `params` → `"attacker-org"` (query string wins), fetches `attacker-org`'s app, and successfully verifies `sig` against the raw body — verification passes.
6. `create` re-parses `request.raw_post` (unaffected by the query string) and dispatches it to `PushHandler`, which resolves `repository_name` = `"victim-org/victim-repo"` from the body and triggers `sync_github`/deploy flow on the victim's stack, despite the request never having been authenticated by `victim-org`'s webhook secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
