### Title
Unscoped `Commit.where(sha:)` lookup in `StatusHandler` lets a signed webhook from one authenticated GitHub organization write CI status onto commits belonging to a different repository/stack - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates a webhook by looking up the `GitHubApp` (and its `webhook_secret`) for the organization named in the payload (`repository.owner.login` / `organization.login`), then verifies the HMAC over the raw body. Once verified, the payload is dispatched to a handler. `StatusHandler#process`, however, resolves *which* database row to mutate purely by commit SHA, with no repository/organization scoping at all, so it writes to any `Commit` in the datastore that happens to share that SHA - regardless of which repository/organization's key was actually used to authenticate the request. ### Finding Description
The signature-verification step derives the signing organization exclusively from the request body's own claimed `repository.owner.login`/`organization.login`: [4](#0-3) 

This selects `Shipit.github(organization: repository_owner)`, i.e. a specific per-organization `webhook_secret`, and checks the raw body against it. The equality this is supposed to guarantee is:

`organization whose secret signed the payload == organization on whose behalf a mutation happens`

Contrast this with every other handler, which resolves the write target via `Repository.from_github_repo_name(repository_name)` (scoped to the payload's own `repository.full_name`): [5](#0-4) 

`StatusHandler`, by contrast, ignores `repository` entirely and just matches by SHA across the whole `commits` table: [3](#0-2) 

Because Shipit is commonly configured with multiple `Stack`s/`Repository`s (multiple environments, forks, or multiple organizations each with their own onboarded GitHub App/secret in `Shipit.github_app_config`), a request that is validly signed using organization A's `webhook_secret` can carry a `sha` that also identifies a commit that belongs to a `Stack`/`Repository` under organization B. `Commit.where(sha: params.sha)` will match and update the status on **all** of them, even though the cryptographic verification only proved authorship by organization A, not by B. This breaks the "organization authenticated vs repository written" binding explicitly called out as in-scope.

### Impact Explanation
CI/commit statuses recorded here are a security-relevant gate: `DeploySpec#required_statuses`/`blocking_statuses`/`hidden_statuses` (delegated on `Stack`) determine whether a commit is considered deployable, and `Commit#create_status_from_github!` is what feeds that state. [6](#0-5) 

An attacker who controls a repository/organization already onboarded to the Shipit instance (with its own legitimately configured webhook secret) can forge a `status` payload for a commit SHA that also exists in an unrelated, more privileged stack (e.g. two environments tracking the same upstream repository, or a fork sharing history with the target repo), and cause a success/failure status to be recorded against that other stack's commit. If the forged status satisfies `required_statuses`, this can enable an unauthorized deploy of that commit in the victim stack - matching the Critical "unauthorized deploy" impact bucket.

### Likelihood Explanation
Exploitation requires: (1) the attacker's organization/repo is already configured as a legitimate GitHub App organization in Shipit (so `verify_signature` succeeds using their own secret), and (2) a commit SHA collision/overlap between the attacker-controlled repo and the victim stack's repo — realistically achievable when Shipit tracks the same repository under multiple environments/stacks, or when a fork retains identical commit history/SHAs with the upstream repo it targets. This is a narrower precondition than a fully unauthenticated attack, but it does not require any Shipit session, API token, or GitHub App private key — only ordinary push/CI access to an onboarded repository, which is exactly the "no additional privilege" bar the rules require.

### Recommendation
Scope `StatusHandler#process` (and any similar lookup) by repository, not just by SHA - e.g. resolve `stacks` (as `Handler#stacks` already does via `Repository.from_github_repo_name(repository_name)`) and restrict `Commit.where(sha: params.sha)` to `commits` belonging to those stacks, so a webhook authenticated for organization/repo A can never mutate commit state belonging to a different repository B.

### Proof of Concept
1. Organization/repo `attacker-org/app` is legitimately onboarded to Shipit with its own GitHub App config (`webhook_secret_A`).
2. Shipit also tracks `victim-org/app` (`Stack`/`Repository` B), which shares a commit SHA `deadbeef...` with `attacker-org/app` (e.g. because `attacker-org/app` is a fork of `victim-org/app` sharing history, or Shipit tracks two environments of the same upstream repo).
3. Attacker triggers/crafts a `status` webhook event for `attacker-org/app`, signed with `webhook_secret_A`, containing `sha: "deadbeef...", state: "success"`.
4. `WebhooksController#verify_signature` succeeds (correctly signed for organization A).
5. `StatusHandler#process` runs `Commit.where(sha: "deadbeef...")`, which returns the commit rows in **both** stacks (A and B), and calls `create_status_from_github!` on all of them - marking the commit in victim stack B as passing CI, even though the signature only proved authorization for organization A.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
