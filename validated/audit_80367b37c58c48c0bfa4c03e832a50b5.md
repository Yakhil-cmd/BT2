### Title
`has_only` oscript formula allows a single `^` character to bypass the entire allowed-character-set check via `[^]` regex trick - ([File: formula/evaluation.js])

### Summary
The oscript `has_only(str, sub)` built-in is meant to let an AA author validate that a string contains **only** characters from an allowed set (`sub`). The implementation builds a JavaScript character-class regex directly from `sub` with only partial escaping, so a single special character (`^`) injected into `sub` turns the intended whitelist check into a match-everything expression, silently defeating the validation the AA relies on — directly analogous to the CVE's "special characters that trigger unintended command/behavior interpretation."

### Finding Description
`has_only` is implemented in the `evaluate` switch of the oscript formula evaluator: [1](#0-0) 

The code takes the user/AA-supplied `sub` string and inserts it almost verbatim into a `RegExp` character class:
```
if (sub.match(/\\]/) || sub[sub.length - 1] === '\\')
    return setFatalError(...);
sub = sub.replace(/]/g, '\\]');
var bMatches = new RegExp("^[" + sub + "]*$").test(str);
```
The only sanitization performed is escaping `]` and rejecting a trailing/embedded `\]`. It does **not** escape or reject `^`. In JavaScript regex syntax, `[^]` (empty negated character class) is a well-known idiom that matches **any single character**, because an empty negated set excludes nothing. Consequently, if `sub === "^"`, the constructed pattern becomes `^[^]*$`, which matches literally any string (including empty string, newlines, arbitrary bytes) — not "only characters equal to `^`" as an author would expect.

This means whichever oscript computation feeds `sub` to `has_only` — whether the AA author intended it to be a fixed literal allow-list (e.g. `"0-9"`, `"a-zA-Z"`), or it is derived dynamically from state vars, `trigger.data`, or other formula expressions — a value of `"^"` (or any string ending up equal to `"^"` after concatenation/interpolation) silently disables the whole check, letting the `str` argument be *anything*.

This is directly reachable by an unprivileged unit poster / AA trigger sender: `has_only` is evaluated inside `formula/evaluation.js`'s AA-formula interpreter, which is invoked whenever an AA processes a trigger unit (`aa_composer.js` `handleTrigger`/`evaluateAA`/`replace`), and formula inputs frequently derive from trigger data, params, or state vars that trace back to attacker-controlled unit content. [2](#0-1) 

### Impact Explanation
If an AA uses `has_only()` as an input-sanitization gate before using a value (e.g., validating that an amount/address/field string contains only digits or a specific alphabet before using it in state-variable keys, building a payment output address, or gating a payout), an attacker who can influence the `sub` argument (or cause it to evaluate to `"^"`) — or more critically, any AA design that expects `has_only` to correctly reject non-whitelisted characters — gets the check to always pass. This can let malformed/attacker-crafted strings flow into places the AA author assumed were already sanitized (state var keys, oscript concatenation into further authorization checks, output addresses), potentially causing AA fund loss, corrupted state, or a bypass of an intended authorization/format check implemented in oscript. Because AA behavior must be deterministic and identical across all full nodes, this is a correctness/security bug in the oscript engine itself (in `formula/evaluation.js`), not merely an application bug, and it can be exploited by any address able to trigger the affected AA with a single crafted unit.

### Likelihood Explanation
Exploitability requires an AA to actually use `has_only` for a security-relevant character-set check where the "allowed" set is influenced (even indirectly, e.g. through concatenation of a fixed prefix with attacker data) by attacker-supplied trigger data, or where the AA author is unaware of the `[^]` regex quirk and assumes `has_only` is airtight. Given `has_only` is a documented public oscript primitive intended precisely for this kind of validation, and the flaw is silent (no error, no exception — it simply returns `true` for everything), it is a plausible trap for AA authors and a directly exploitable bug in the language runtime shared by every AA on the network. It requires no privileged position — a single crafted trigger data field containing `"^"` is sufficient once a vulnerable AA is deployed.

### Recommendation
- In `formula/evaluation.js`, reject or properly escape all regex-significant characters in `sub` before embedding it in a character class — at minimum reject a leading `^` (and `-`, `\` outside intended escapes), or better, build the match using a non-regex approach (e.g., iterate character-by-character checking `sub.indexOf(ch) !== -1` for each character of `str`) instead of dynamically constructing a `RegExp`.
- Add a fix-mci-gated correction (as is the pattern for other oscript engine bugs in this codebase, e.g. `pemCurvesFixMci`, `aa2UpgradeMci`) so behavior changes deterministically for all nodes at a defined MCI.
- Add regression tests covering `has_only(str, "^")`, `has_only(str, "^abc")`, and other regex-metacharacter edge cases to ensure the whitelist semantics hold for all inputs.

### Proof of Concept
An AA author (or a vulnerable AA already deployed) uses oscript such as:
```
$allowed = "^";  // or dynamically derived value that can become "^"
$ok = has_only(trigger.data.name, $allowed);
if ($ok) {
    // proceeds trusting that trigger.data.name only contains chars from $allowed
    ...
}
```
Sending a trigger with `data.name` set to **any** arbitrary string (including special characters, script-like payloads used elsewhere in oscript concatenation, or characters intended to be forbidden) still causes `has_only` to evaluate to `true`, because the underlying check evaluates `new RegExp("^[^]*$").test(str)`, which matches unconditionally. This can be confirmed directly against `formula/evaluation.js` lines 2037-2049 without needing network access, by evaluating the oscript formula `has_only("anything at all", "^")` through `evalFormulaWithVars`/`evaluate` in `test/formula.test.js`-style harness and observing the result is always `true` regardless of the first argument's content.
