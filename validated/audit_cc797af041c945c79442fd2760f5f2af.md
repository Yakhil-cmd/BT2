Confirmed: `CallerDeposit` tracks any `attached_deposit` sent by an external caller, refunded only when `env::promise_result(0)` is `PromiseResult::Failed` in `rlp_execute_callback` [1](#0-0) . This checks only whether the downstream cross-contract call panicked, not whether it semantically succeeded — the same class of bug as the Solidity report (checking that a call didn't revert instead of checking its actual returned success indicator).

### Title
Wallet contract treats non-panicking but logically-failed target calls as success, silently forfeiting the caller's attached deposit - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
`WalletContract::rlp_execute_callback` classifies the outcome of the inner action's promise purely by whether the receipt panicked (`PromiseResult::Failed` vs `PromiseResult::Successful`), never inspecting the semantic content of the returned value. This mirrors the reported ERC-20 pattern of trusting a call's completion without validating its actual success signal.

### Finding Description
`inner_rlp_execute` builds a promise for the user's decoded action (an arbitrary `FunctionCall`, `Transfer`, `AddKey`, or `DeleteKey` targeted at any account, including emulated NEP-141 `ft_transfer` calls) and chains it to `rlp_execute_callback` [2](#0-1) . The callback only branches on `env::promise_result(0)`:

```rust
match env::promise_result(0) {
    PromiseResult::Failed => { ... refund caller_deposit ... }
    PromiseResult::Successful(value) => {
        ExecuteResponse { success: true, success_value: Some(value), error: None }
    }
}
``` [1](#0-0) 

`CallerDeposit` is only refunded on the `Failed` branch [3](#0-2) . However, a target contract's method can return normally (no panic) while communicating logical failure only in its return payload (e.g., a JSON object indicating an error, or a boolean `false`), exactly the ERC-20 `transfer`-returns-`false` pattern the external report warns about. Because `rlp_execute_callback` never parses or validates `value` against the expected success shape for the action that was performed, it unconditionally reports `success: true` and skips the deposit refund whenever the promise did not panic, even though the intended action (e.g., a NEP-141 transfer that returned a semantic error rather than panicking) did not happen as intended.

### Impact Explanation
Any deposit attached by an external (non-self) predecessor when calling `rlp_execute` (`CallerDeposit::new`, tracked whenever `predecessor_account_id != current_account_id`) can be silently forfeited: the wallet contract reports the meta-transaction as successful and never refunds the yoctoNEAR deposit, even though the underlying action produced no effect. This is an unauthorized loss of caller funds resulting from trusting call completion instead of validating the actual outcome — the same balance-accounting flaw the referenced report describes for ERC-20 `transfer`/`transferFrom`.

### Likelihood Explanation
This is reachable directly from user-submitted RLP transactions relayed through `rlp_execute`/`rlp_execute_with_receipts`, requiring only that the target contract invoked by the decoded action return a non-panicking-but-logically-failed response (a common, standards-compliant pattern for many NEP-141/custom contracts that signal errors via return value rather than panic). No validator or privileged role is needed — any relayer/caller combination reaching this code path triggers it.

### Recommendation
In `rlp_execute_callback` (and the parallel `Some(value)` branches), do not conflate "promise did not panic" with "action succeeded." For known action kinds (especially the emulated ERC-20/NEP-141 transfer), parse `value` against the expected success schema of the target method and only report `success: true` / skip the deposit refund when the parsed value confirms the action's logical success; otherwise treat it the same as `PromiseResult::Failed` and refund `caller_deposit`.

### Proof of Concept
1. Deploy the wallet contract for an eth-implicit account and fund it with a NEP-141 token.
2. Have an external relayer call `rlp_execute` with `tx_bytes_b64` encoding an RLP transaction that targets a custom NEP-141-like contract whose `transfer`-style method returns `{"ok": false}` (or any non-panicking failure payload) instead of panicking on insufficient balance, attaching a non-zero deposit as the predecessor.
3. Observe `rlp_execute_callback` receives `PromiseResult::Successful(value)` (since the target method did not panic) and returns `ExecuteResponse{success: true, ...}`, and the `CallerDeposit` refund logic in the `Failed` branch [4](#0-3)  is never triggered, permanently retaining the caller's attached deposit despite the intended transfer not occurring.

/// A data type to keep track of the deposit given by an external caller.
/// This allows us to refund the caller's deposit if the cross-contract call fails.
#[derive(Debug, PartialEq, Eq, Clone, serde::Serialize, serde::Deserialize)]
pub struct CallerDeposit {
    pub account_id: AccountId,
    pub yocto_near: NonZeroU128,
}

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
}
