## Title
Asymmetric floor/ceil rounding in TPS-fee balance accrual causes multi-recipient AA/unit authors to systematically lose TPS-fee credit and overpay - (File: storage.js / composer.js)

### Summary
The `bytes/base-asset` "TPS fee" (rate-limiting fee) accounting in `ocore` splits a unit's fee overpayment/underpayment across multiple `earned_headers_commission_recipients` shares using `Math.floor` when crediting balances, but the code that later spends that credit computes the amount still owed using `Math.ceil` on the *inverse* operation (dividing by the same share). This is the identical rounding-direction mismatch described in the external report (`stIchi` rounded up / `enIchi` rounded down in `WIchiFarm.pendingRewards`): one side of a debit/credit pair is always rounded in the direction unfavorable to the address, and the other side of the pair is rounded in the *same* unfavorable direction again, so the address never recovers the fractional unit it is owed.

### Finding Description
`storage.js` `updateTpsFees()` computes, for every stable unit, the difference between what was pre-paid (`objUnitProps.tps_fee`) and what was actually owed (`getFinalTpsFee(...)`), then splits this delta across the unit's `earned_headers_commission_recipients` shares: [1](#0-0) 
```
const total_tps_fees_delta = (objUnitProps.tps_fee || 0) - tps_fee; // can be negative
...
const tps_fees_delta = Math.floor(total_tps_fees_delta * share / 100);
...
await conn.query("REPLACE INTO tps_fees_balances ... ", [address, mci, tps_fees_balance + tps_fees_delta]);
```
`Math.floor` is applied to each recipient's share of the delta. When `total_tps_fees_delta` is positive (unit overpaid and should be refunded via credit), flooring strictly reduces the credit each address receives; summed across all recipients, the sum of the floored per-recipient credits can be strictly less than the true `total_tps_fees_delta`, so a fraction of the overpayment is silently lost instead of being credited to any address.

Later, when a new unit is composed and the code decides how much *additional* fee an address must pay given its accrued balance, it performs the inverse operation and always rounds the required-payment **up**: [2](#0-1) 
```
for (let address in recipients) {
    const share = recipients[address] / 100;
    ...
    const tps_fees_balance = row ? row.tps_fees_balance : 0;
    const addr_tps_fee = Math.ceil(tps_fee - tps_fees_balance / share);
    if (addr_tps_fee > paid_tps_fee)
        paid_tps_fee = addr_tps_fee;
}
```
and the same asymmetric pattern is repeated in `storage.getPaidTpsFee()`: [3](#0-2) 
```
for (let address in recipients) {
    const share = recipients[address] / 100;
    ...
    const tps_fee = tps_fees_balance / share + objUnitProps.tps_fee;
    if (tps_fee < min_tps_fee)
        min_tps_fee = tps_fee;
}
```
Because `tps_fees_balance` was floored downward when it was credited (favoring the protocol against the address), and the amount required to be paid is ceiled upward when it is later debited (again favoring the protocol against the address), the two roundings compound in the *same* direction rather than cancelling out — exactly mirroring the `WIchiFarm` pattern where `stIchi` (debt) is ceiled and `enIchi` (entitlement) is floored, so the user's true entitlement is eaten by rounding on both sides of the calculation. `validateTpsFee` in `validation.js` performs the same `tps_fees_balance / share` division and is validated on-chain, meaning every node applies this same lossy accounting, so it is a protocol-level (not merely client-side) rounding defect.

### Impact Explanation
Any address that shares TPS-fee credit through `earned_headers_commission_recipients` (i.e., a multi-authored unit or a unit whose commissions/tps-fee credit is split across addresses) will accumulate a `tps_fees_balance` that is persistently smaller than its true, mathematically-owed credit. Whenever that address later composes a new unit and the code determines `addr_tps_fee = Math.ceil(tps_fee - tps_fees_balance/share)`, the deficit forces the address to pay a slightly larger `tps_fee` than actually required, unit after unit. Over many units this compounds into real, permanent loss of Bytes for the affected address (an economic loss reachable simply by any address that is a member of a shared-commission unit, i.e. an ordinary unpriviledged unit poster), and in aggregate it constitutes a small, silent inflation/leak of value out of the fee-accounting system to no one (the "lost" fractions are neither credited to any address nor burned in a way that's accounted for on-chain).

### Likelihood Explanation
This triggers automatically and deterministically any time `earned_headers_commission_recipients` splits a unit's authorship among multiple addresses (a normal, supported, unprivileged feature) and the resulting `total_tps_fees_delta * share / 100` is not an exact integer — which is the generic case, since `share` is a percentage and `total_tps_fees_delta` is an arbitrary integer fee delta. No attacker action beyond normal multi-authored/AA usage is required, so likelihood is high; the per-event loss is small, hence Medium severity, matching the classification of the analogous WIchiFarm finding.

### Recommendation
Make the crediting and debiting operations consistent in rounding direction (or track fractional remainders) so that the sum of all per-recipient floors never diverges from the true total delta, and so that `Math.ceil` on the payment side is not applied to a balance that was already floored down on the credit side. Concretely: track exact (non-integer) balances internally (or carry a remainder ledger per address/mci) instead of flooring on credit and ceiling on debit, or floor consistently in both places and let a single, explicitly designated address absorb the truncation remainder rather than letting it silently disappear.

### Proof of Concept
1. Configure a unit with `earned_headers_commission_recipients` splitting authorship shares, e.g., two addresses A (60%) and B (40%).
2. Suppose the unit overpays its `tps_fee` such that `total_tps_fees_delta = 5`.
   - Credit to A: `Math.floor(5*60/100) = Math.floor(3) = 3`
   - Credit to B: `Math.floor(5*40/100) = Math.floor(2) = 2`
   - Sum credited = 5 (in this case exact, but pick a delta that doesn't divide evenly, e.g. `total_tps_fees_delta = 7`):
   - A: `Math.floor(7*0.6) = Math.floor(4.2) = 4`
   - B: `Math.floor(7*0.4) = Math.floor(2.8) = 2`
   - Sum credited = 6, but true delta owed = 7 → 1 unit is lost and never credited to anyone [4](#0-3) .
3. When address A later composes a new unit needing `tps_fee = 10`, with `share = 0.6` and `tps_fees_balance = 4` (already short by the floor above):
   - `addr_tps_fee = Math.ceil(10 - 4/0.6) = Math.ceil(10 - 6.67) = Math.ceil(3.33) = 4` — A is forced to pay an extra unit beyond the true fractional shortfall of `3.33`, compounding the earlier floor-based loss [5](#0-4) .

This demonstrates the same "ceil on one side, floor on the other, of the same underlying quantity" defect described in the external `WIchiFarm.pendingRewards` report, here manifesting in `ocore`'s TPS-fee balance accounting.
