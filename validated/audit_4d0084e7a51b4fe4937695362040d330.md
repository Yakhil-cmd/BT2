### Title
Missing RSA modulus size validation allows trivially forgeable signatures accepted by `is_valid_sig` - (File: signature.js)

### Summary
`signature.validateAndFormatPemPubKey()` only checks `hex_pub_key_length` when `objSupportedPemTypes[typeIdentifiersHex].algo == "ECDSA"`; the RSA (`PKCS #1`) entry defines no length constraint at all, so an attacker-supplied RSA public key of any size — including cryptographically trivial sizes (e.g., 32–64 bits) — passes validation as long as it structurally parses as a valid RSA `SubjectPublicKeyInfo` and its OID matches PKCS#1.

### Finding Description
The overall bug class mirrors CVE-2019-18632: acceptance of a cryptographic credential/certificate that has not been sufficiently vetted, letting an attacker present a "signature" that verifies without possessing the corresponding legitimate private key.

In `signature.js`, `validateAndFormatPemPubKey(pem_key, algo, handle, bPostPemCurvesFix)` walks the DER-encoded `SubjectPublicKeyInfo`, extracts the AlgorithmIdentifier OID bytes (`typeIdentifiersHex`), and looks it up in `objSupportedPemTypes`. For every ECDSA curve entry it additionally checks that the embedded public key material length exactly matches `hex_pub_key_length`: [3](#0-2) 

But the RSA entry has no `hex_pub_key_length` property, so this branch is simply skipped for RSA keys, meaning `validateAndFormatPemPubKey` will accept an RSA public key with an arbitrarily small modulus (bounded only by the overall 736-byte base64/DER size cap intended for 4096-bit keys): [4](#0-3) [1](#0-0) 

This validated PEM key is then used directly by `verifyMessageWithPemPubKey()`, which falls back to Node's `crypto.createVerify('SHA256').verify()` for any non-secp256k1 algorithm, including RSA of any (even tiny) key size: [5](#0-4) 

This full path is reachable from an unprivileged AA trigger sender: the oscript/formula op `is_valid_sig` evaluates attacker-controlled `message`, `pem_key`, and `signature` expressions (typically sourced from `trigger.data.*`), calls `signature.validateAndFormatPemPubKey()` on the attacker-supplied key, and then calls `signature.verifyMessageWithPemPubKey()`: [6](#0-5) 

Because tiny RSA moduli (e.g., 32–128 bits) are trivially factorable, an attacker who controls the entire trigger payload can generate their own "attacker RSA key + matching signature" pair off-chain in seconds and have `is_valid_sig` return `true` for an attacker-chosen message — without ever needing the private key of a real, previously trusted signer. If an AA's oscript logic uses `is_valid_sig` as a trust/authentication gate (e.g., "if signed by oracle X's key embedded in trigger data, release funds"), the missing size floor undermines the intended security guarantee that only a specific real-world keyholder could produce a valid signature, since the AA's dApp author might reasonably assume `is_valid_sig` performing "signature validation" implies a cryptographically meaningful key-size floor is enforced by the platform (as is done for ECDSA curves) — but for RSA, none exists.

### Impact Explanation
Any AA that uses `is_valid_sig` with an RSA key path (all algo="any"/"RSA" call sites in `formula/evaluation.js`) to gate fund release, oracle acceptance, or condition satisfaction can be manipulated by an attacker-crafted trigger, because the attacker can mint their own valid (RSA-key, signature) pair for whatever message they want and pass `is_valid_sig` unconditionally. This can lead to unauthorized AA fund release/loss if the AA's oscript ties value transfer to a passing `is_valid_sig` check on attacker-influenced inputs. This is Medium-High impact for the reachable subset (AAs performing RSA-based signature checks against attacker-influenced keys/messages); it does not affect ECDSA-curve enforcement, which is properly length-checked.

### Likelihood Explanation
Reachable via a single posted AA trigger by any unprivileged sender able to invoke `is_valid_sig(message, pem_key, signature)` in oscript formula evaluation with attacker-controlled arguments [7](#0-6) . Exploitation requires the AA's own logic to trust an attacker-controlled `pem_key`/`message` triple (i.e., not pin the key to a hardcoded, out-of-band trusted key), which limits blast radius to AAs written with that pattern, but the platform itself provides no minimum-key-size safeguard for RSA to prevent it.

### Recommendation
Add a minimum RSA modulus-size enforcement (e.g., >=2048 bits, matching the existing 4096-bit maximum implied by the 736-byte cap) in `validateAndFormatPemPubKey` for the `algo === 'RSA'` case in `signature.js`, mirroring the existing `hex_pub_key_length` check performed for ECDSA curves.

### Proof of Concept
1. Attacker generates a 32-bit RSA keypair (`openssl genrsa -out weak.pem 32` or programmatically) and exports the public key as `-----BEGIN PUBLIC KEY-----` PEM.
2. Attacker signs an arbitrary chosen `message` with the weak private key (trivial since factoring a 32-bit modulus is instantaneous) via `signMessage`/openssl `SHA256` sign.
3. Attacker posts an AA trigger with `trigger.data = { message, pem_key: weak_pubkey_pem, signature }` targeting an AA whose oscript contains `is_valid_sig(trigger.data.message, trigger.data.pem_key, trigger.data.signature)` as a spending/authorization condition.
4. `validateAndFormatPemPubKey` accepts the weak RSA key (no length check for RSA) and `verifyMessageWithPemPubKey` returns `true`, satisfying the condition without the attacker possessing any legitimately trusted key — demonstrating the forged/weak-credential acceptance analogous to CVE-2019-18632's certificate faking.

function verifyMessageWithPemPubKey(message, signature, pem_key, bPostPemCurvesFix) {
	var contentB64 = pem_key
		.replace("-----BEGIN PUBLIC KEY-----", "")
		.replace("-----END PUBLIC KEY-----", "")
		.replace(/\s/g, "");
	var der = Buffer.from(contentB64, 'base64');
	var algIdStart = der[1] <= 0x7F ? 4 : der[1] === 0x81 ? 5 : der[1] === 0x82 ? 6 : -1;
	if (algIdStart >= 0 && der.slice(algIdStart, algIdStart + SECP256K1_ALG_ID.length).equals(SECP256K1_ALG_ID)
			&& bPostPemCurvesFix)
		return verifyMessageWithSecp256k1PemPubKey(message, signature, der);

	var verify = crypto.createVerify('SHA256');
	verify.update(message);
	verify.end();
	var encoding = ValidationUtils.isValidHexadecimal(signature) ? 'hex' : 'base64';
	try {
		return verify.verify({key: pem_key}, signature, encoding);
	} catch(e) {
		console.log("exception when verifying with pem key: " + e);
		return false;
	}
