## Verified analog: Cross-organization webhook forgery in `WebhooksController#verify_signature`

### Title
Cross-organization webhook forgery — HMAC signature is verified against the org derived from `repository.owner.login`/`organization.login`, but handlers act on the independently-controlled `repository.full_name` field — (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
In Shipit's multi-GitHub-App configuration, `WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate the HMAC signature with, based on `repository.owner.login` (or `organization.login`) taken directly from the unauthenticated JSON body. Once verification passes, the same raw payload is dispatched to webhook handlers that resolve the target `Repository`/`Stack` using a *different* field: `repository.full_name`. These two fields are never checked for consistency.

### Finding Description
`WebhooksController#verify_signature` computes:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 
and uses it to pick the app/secret:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [2](#0-1) 

`Shipit.github(organization:)` looks up per-organization config keyed by that exact string, and every org has its own independent `webhook_secret` (see the multi-org config schema) [3](#0-2) [4](#0-3) .

Once `verified` is true, the controller dispatches the *entire* raw payload — unmodified — to all handlers for the event:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [5](#0-4) 

Handlers, however, do not use `repository.owner.login` to determine which repository/stack to mutate. They use `repository.full_name` instead:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [6](#0-5) 

`PushHandler`, for example, uses exactly this `stacks` helper to find matching stacks and call `stack.sync_github(expected_head_sha: params.after)`: [7](#0-6) 

`Repository.from_github_repo_name` simply splits `full_name` on `/` and does a DB lookup — it performs no cross-check against `repository.owner.login`: [8](#0-7) 

**Binding broken:** *organization that authenticated* (`repository.owner.login`, used to pick the webhook secret that validated the HMAC) ≠ *repository that is written* (`repository.full_name`, used by the handler to find and mutate the target `Repository`/`Stack`). Nothing in `WebhooksController` or `Handler` enforces `repository.full_name.split('/').first == repository_owner`.

### Impact Explanation
An attacker who controls (or has installed) their own legitimate GitHub App/organization in a multi-org Shipit deployment — i.e., they know their own org's `webhook_secret`, an unprivileged position with respect to any *other* tenant org on the same Shipit instance — can craft an arbitrary JSON body where:
- `repository.owner.login` = their own org (`"attacker-org"`) — used only to select the secret for signing.
- `repository.full_name` = a victim org/repo they don't administer (`"victim-org/prod-app"`).

They sign this payload with `attacker-org`'s real webhook secret and POST it to `/webhooks` with `X-Github-Event: push`. `verify_signature` looks up `Shipit.github(organization: "attacker-org")`, validates successfully (it's their own secret over their own bytes), and the request proceeds. `PushHandler` then resolves the stack via `repository.full_name = "victim-org/prod-app"`, entirely bypassing the fact that the cryptographic proof only ever covered `attacker-org`. This lets the attacker forge `push`, `status`, `check_suite`, `membership`, and pull-request events against any repository/stack tracked by the shared Shipit instance, causing e.g. unauthorized `sync_github` calls, fake commit statuses, or spurious review-stack provisioning/archival — all without ever possessing the victim org's actual webhook secret or repository write access. This is a cross-organization/cross-repository write achieved purely by exploiting the authentication/action-field mismatch, matching the report's "field acted upon but not covered by the binding actually verified" bug class.

### Likelihood Explanation
This requires the Shipit instance to be configured with the multi-org GitHub App schema (`config/secrets*.yml` keyed by organization, as documented and tested) so that more than one organization's webhook secret exists on the same install — a supported, documented configuration [4](#0-3) . Any party who is a legitimate app-installer/admin of *one* tracked organization can trivially forge events for *any other* tracked organization's repositories, with no additional secrets, no session, and no repository write access needed for the victim org.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler#repository_name`), enforce that the organization used to select/verify the webhook secret matches the owner embedded in every repository-bearing field of the payload actually consumed by handlers (i.e., assert `repository.full_name.split('/').first.casecmp?(repository_owner)` before dispatching), rejecting mismatched payloads with `422`.

### Proof of Concept
1. Configure Shipit with two orgs, `attacker-org` and `victim-org`, each with its own `webhook_secret` (per the documented multi-org schema).
2. As the (legitimate) admin of `attacker-org`'s GitHub App, compute `sha1=HMAC(webhook_secret_of_attacker_org, body)` for a `push` payload where:
   - `repository.owner.login = "attacker-org"`
   - `repository.full_name = "victim-org/prod-app"`
   - `ref = "refs/heads/master"`, `after = "<attacker-chosen-sha>"`
3. POST to `/webhooks` with header `X-Github-Event: push` and `X-Hub-Signature: sha1=<computed>`.
4. `verify_signature` succeeds using `attacker-org`'s secret; `PushHandler` resolves stacks for `victim-org/prod-app` via `repository.full_name` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")`, mutating a stack the attacker has no legitimate relationship to.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
```
