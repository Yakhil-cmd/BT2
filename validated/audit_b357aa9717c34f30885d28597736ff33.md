### Title
System-vote counting uses momentary balance instead of balance held since the vote, allowing flash-funded takeover of `op_list`/system parameter votes - (File: `main_chain.js`)

### Summary
`countVotes()` in `main_chain.js` weighs every voter's ballot by whatever balance sits in their voting address **at the moment vote-counting stabilizes**, not by the balance the address held when it actually cast the `system_vote`. Because a `system_vote_count` message can be posted by any unprivileged address at will, an attacker can pre-register a vote with a throwaway balance, temporarily concentrate a large balance into the voting address right before triggering the count, and move the funds away immediately afterward — permanently swinging the `op_list` (witness list) or other system parameters (`threshold_size`, `base_tps_fee`, `tps_interval`, `tps_fee_multiplier`) with only momentary control of funds, echoing the report's "gain outsized power for an instant, low-cost commitment" pattern.

### Finding Description
`saveSystemVote()` records a voter's choice with the timestamp of the unit that cast it [1](#0-0) , but the actual vote weight is computed later, only when someone posts a `system_vote_count` message and it stabilizes [2](#0-1) . Posting `system_vote_count` is available to any ordinary address — validation only checks the subject name and that the author isn't an AA [3](#0-2) .

When the count runs, `countVotes()` computes each voter's balance from the *current* stable UTXO set with no reference to when the funds arrived relative to the vote timestamp:

```
const bal_rows = await conn.query(`
    SELECT outputs.address, SUM(outputs.amount) AS balance
    FROM outputs
    JOIN units ON outputs.unit = units.unit
    WHERE outputs.address IN(${strAddresses})
        AND outputs.asset IS NULL
        AND units.is_stable = 1 AND units.sequence = 'good'
        AND NOT EXISTS (...)
    GROUP BY outputs.address`);
``` [4](#0-3) 

This balance is inserted into the temporary `voter_balances` table and then joined with `op_votes`/`numerical_votes` filtered only by the vote's own `timestamp >= since_timestamp` window [5](#0-4) , and used directly to tally `total_balance` per candidate/value [6](#0-5) [7](#0-6) .

There is no requirement that the balance be held for any minimum duration, nor that it match the balance held at the time the `system_vote` message was posted — exactly the class of flaw in the external report, where a very short/instantaneous holding period was still given (near-)full weight because the code only checked a boolean condition (`rd > 0`) instead of a meaningful minimum duration.

### Impact Explanation
`op_list` votes determine the network's order-provider/witness set, which directly underlies main-chain stability and unit validity determination across all nodes. An attacker who can briefly consolidate a large balance into a voting address, trigger `system_vote_count`, and then move the funds away can force an illegitimate witness-list change or corrupt system parameters (`tps_fee_multiplier`, `threshold_size`, etc.) that govern fee calculation and consensus thresholds network-wide. This falls squarely into "node disagreement on validity/stability" and "network unable to confirm new units" territory, since a manipulated OP list changes what every node treats as canonical stability.

### Likelihood Explanation
No special privilege is required — any address can send a `system_vote` message and, separately, any address can send `system_vote_count` to trigger tallying [8](#0-7) . An attacker only needs enough own/borrowed liquidity to temporarily dominate the votes for a given subject during the single main-chain-index window when the count message stabilizes, then can redistribute the funds immediately after. The existing safeguard (`since_timestamp` expansion loop for insufficient participation) does not address this because it only concerns whether votes span a long-enough *time window*, not whether the balance behind each vote persisted.

### Recommendation
Weight votes by a balance measured at (or derived from an average held since) the timestamp the `system_vote` was cast, not by the balance at count time — e.g., snapshot balances at vote time into `system_votes`/`op_votes`/`numerical_votes`, or require the voting balance to have been held continuously for a minimum period before the count, analogous to the report's fix of enforcing `rd > 1 weeks` instead of `rd > 0`.

### Proof of Concept
1. Attacker address A holds a small balance and posts `system_vote` for `op_list` (or another subject) — recorded with A's address and the message timestamp [1](#0-0) .
2. Immediately before triggering a count, attacker moves a large sum of its own bytes from another address into A.
3. Attacker (or a colluding party) posts `system_vote_count` for that subject; once it stabilizes, `countVotes()` reads A's current large balance from stable, unspent outputs and adds it to the vote tally [4](#0-3) [6](#0-5) .
4. After the count concludes and the new `op_list`/parameter value is stored in `storage.systemVars`, attacker moves the large balance back out of A, having paid only ordinary transfer fees for the temporary weight, achieving disproportionate governance influence.
