Confirmed root cause: `WebhooksController#verify_signature` selects which GitHub App/webhook secret to verify against using `repository_owner`, defined as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0) [2](#0-1) . Once the HMAC check passes for that one field, `create` hands the *entire* raw payload to the event handlers unmodified [3](#0-2) . Every handler (`PushHandler`, `StatusHandler`, etc.) independently derives the target `Repository`/`Stack` from a *different* payload field, `payload.dig('repository', 'full_name')`, via the shared `Handler#repository_name`/`#stacks` helpers [4](#0-3) , and `StatusHandler` goes further and resolves the target purely by commit `sha` with no repository/owner scoping at all [5](#0-4) .

### Title
Webhook signature verification is bound to `repository.owner.login`/`organization.login` while handlers act on unrelated payload fields (`repository.full_name`, bare commit `sha`) - (File: app/controllers/shipit/webhooks_controller.rb)

### Finding Description
The equality the engine is supposed to enforce is:

`organization whose webhook_secret produced a valid HMAC == organization that owns the repository/stack being mutated`

`verify_signature` computes the signing organization from `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`), and looks up that organization's GitHub App (`Shipit.github(organization: repository_owner)`) to check `X-Hub-Signature` against the raw body [6](#0-5) . If the byte-for-byte HMAC of the *entire* raw body validates for that one org's secret, the whole `params` hash — every other field in the JSON, including `repository.full_name` and `sha` — is treated as trustworthy and handed to handlers [3](#0-2) .

This is the same class of bug as the `RewardsDistributor` finding: a value used for authorization/verification (`_rewardPerToken` snapshot, here `repository.owner.login`) is decoupled from the value the effect is actually computed against (accrued reward at claim time, here `repository.full_name`/`sha` used by `Handler#repository_name` and `StatusHandler#process`). Concretely, GitHub always signs the entire payload with the webhook secret configured for the specific repository that generated the event, so `repository.owner.login` and `repository.full_name` are consistent for genuine GitHub-originated deliveries. But Shipit is explicitly designed to run multiple independent GitHub Apps for multiple orgs, each with its own `webhook_secret` [7](#0-6) , and the controller re-derives the org purely from a field inside the same untrusted body rather than from any binding tied to which App/secret actually delivered the request (there is no per-App callback URL or App ID assertion consumed here — only the raw HMAC of the body plus a value read out of that same body).

Because the signing key lookup and the "what do I act on" lookup are two independent `dig` calls into the same JSON body, a party who can get *any* one configured organization to deliver a webhook with attacker-influenced content (e.g., by owning/administering a repository in Org A, which is enough to make GitHub emit real `push`/`status` signed events for that repository, signed with Org A's `webhook_secret`) can shape any field of that payload that GitHub does not itself fix, then rely on handlers resolving the actual mutation target from `repository.full_name` (`Handler#repository_name`) or from a bare `sha` (`StatusHandler`) rather than from `repository.owner.login`. If those two fields ever diverge — which GitHub does not prevent Shipit from receiving as long as the org's own app is used to sign it — Shipit will perform state changes (queuing `GithubSyncJob`, creating commit `Status` records via `commit.create_status_from_github!`) against a stack/commit that has nothing to do with the organization whose signature was actually checked.

### Impact Explanation
`StatusHandler#process` writes a `Status` for every `Commit` in the entire Shipit instance matching a given `sha`, with no repository scoping at all [5](#0-4) . Forged/mismatched CI-status webhooks can flip `required_statuses`/`ci.require` checks used elsewhere to gate deploys (`DeploySpec#required_statuses`, `#blocking_statuses`) [8](#0-7) , effectively allowing an attacker who controls one legitimately-configured org+repo to mark a commit shared/colliding across a different stack as passing CI, contributing to an unauthorized deploy. `PushHandler` similarly triggers `stack.sync_github` for any stack whose `branch` matches, driven off `repository.full_name` rather than the verified org [9](#0-8) .

### Likelihood Explanation
Low. It requires the operator to run Shipit with the multi-org GitHub App configuration (explicitly documented and supported) [7](#0-6) , and requires an attacker who already controls a repository/organization onboarded into that same Shipit instance to get GitHub to sign a delivery whose `repository.full_name`/`sha` fields point at a different stack's data. This is a real but narrow trust-boundary gap between the signature-verification key selection and the handlers' target-resolution fields, matching the report's "check value diverges from effect value" bug class.

### Recommendation
Bind signature verification to the same identity used for the mutation: after verifying the HMAC, re-derive (or cross-check) the organization from the *same* field(s) the handler will use (`repository.full_name`), and reject the webhook if `repository.owner.login`/`organization.login` doesn't match the owner segment of `repository.full_name`. For `StatusHandler`, scope the `Commit` lookup by the repository resolved from the verified organization instead of a bare, globally-unscoped `sha`.

### Proof of Concept
1. Configure Shipit with two GitHub orgs, `OrgA` and `OrgB`, each with its own installed App/`webhook_secret`, as in `docs/setup.md`'s multi-org example [7](#0-6) .
2. Attacker administers a repository under `OrgA` and has GitHub's App for `OrgA` deliver a `status` (or `push`) webhook for a commit in `OrgA`'s repo — a legitimately signed request, verified by `Shipit.github(organization: 'OrgA').verify_webhook_signature` [1](#0-0) .
3. Because `StatusHandler#process` matches purely on `Commit.where(sha: params.sha)` with no repository/org check [5](#0-4) , if any commit with a colliding/shared `sha` (e.g., a fork, cherry-pick, or coincidental match across `OrgB`'s stack) exists in the Shipit database, the attacker-signed webhook creates a `Status` on `OrgB`'s commit despite the signature only proving authenticity for `OrgA`.

This confirms the check-vs-effect divergence exists in code; I was not able to further verify from static analysis alone whether real-world SHA collisions/shared commits across orgs are common enough to make step 3 practical — that would need runtime/dataset inspection beyond what the indexed source provides.
