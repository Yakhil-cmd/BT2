### Title
CCMenu token issued for one stack authorizes reading `cc.xml` of any stack because it is created unscoped and `Api::CCMenuController#stack` bypasses the base `stacks` scoping - ([File: app/controllers/shipit/ccmenu_url_controller.rb], [File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`CCMenuUrlController#fetch` mints an `ApiClient` with the `read:stack` permission but never sets `stack:` on it, so `current_api_client.stack_id` is always `nil` for CCMenu tokens. `Api::CCMenuController#show` then resolves the target stack via `Stack.from_param!(params[:stack_id])` directly, without going through `Api::BaseController#stacks` (which would have scoped by `stack_id` anyway, but returns `Stack.all` when `stack_id` is nil). The result: any authenticated low-privilege user who can trigger `#fetch` for a stack they legitimately own gets a token that reads `cc.xml` for *every* stack in the installation, including ones owned by teams they are not a member of.

### Finding Description
The claimed binding is:
`stack.id` whose `cc.xml` is exposed by a CCMenu token == `current_api_client.stack_id` (the single stack the token was issued for).

Tracing the code shows this binding never holds:

- `CCMenuUrlController#fetch` builds the token's backing `ApiClient` with:
```ruby
def client
  @client ||= ApiClient.create_with(permissions: %w[read:stack])
                       .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
end
``` [1](#0-0) 
No `stack:` attribute is set, and the record is found/created by `creator` + fixed `name`, not by stack — so `stack_id` is permanently `nil` for this client, and the same client is reused across every stack the user ever requests a CCMenu URL for.

- `Api::BaseController` defines the intended scoping mechanism:
```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end
``` [2](#0-1) 
Since `stack_id` is `nil` for the CCMenu client, `stacks` would already fall back to `Stack.all` even if used.

- `Api::CCMenuController` doesn't even use that scoping helper — it overrides `stack` to query directly and globally:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [3](#0-2) 

- Authorization is only `require_permission :read, :stack`, which merely checks the string permission `"read:stack"` is present in the client's `permissions` array via `ApiClient#check_permissions!`, with no per-stack check whatsoever:
```ruby
def check_permissions!(operation, scope)
  required_permission = "#{operation}:#{scope}"
  unless permissions.include?(required_permission)
    raise InsufficientPermission, ...
  end
  true
end
``` [4](#0-3) 

Exploit flow: the attacker owns/administers Stack A (low-privilege, within their team's `Shipit.github_teams`). They hit the legitimate settings UI/route that triggers `CCMenuUrlController#fetch` for Stack A, obtaining a URL like `.../ccmenu?stack_id=A&token=T`. Because `T` authenticates an `ApiClient` with `stack_id = nil` and permission `read:stack`, the attacker simply substitutes `stack_id=B` (a Shipit-operator-only stack never in their team) in the URL and requests `Api::CCMenuController#show`. `require_permission!` passes (permission check is global, not stack-scoped) and `stack` resolves `B` unscoped, returning `B`'s `cc.xml` — build status, last build label/time, activity, web URL for stack B.

None of the existing guards catch this: `verify_signature`/webhook checks are irrelevant (this is an authenticated API path), `require_permission!` only checks the permission string not the target stack, and the one scoping mechanism that exists (`Api::BaseController#stacks`) is bypassed by `CCMenuController#stack` and would be ineffective anyway due to the token's `stack_id` being `nil`.

### Impact Explanation
Any authenticated low-privilege user with visibility into at least one stack can mint a token that reads `cc.xml` (build/activity/status metadata) for **any** stack in the Shipit installation, including stacks belonging to teams/repositories they have no GitHub permission over. This is a stack-state read authorization bypass — escalation past repository/team-based authorization (`Shipit.github_teams`) entirely, matching the "High: escalation into `Shipit.github_teams` authorization, unauthenticated read of stack state" category. It is fully repeatable: the same token works for every `stack_id` value on the instance, and the attacker needs only one legitimate `#fetch` call to obtain it. No secrets, GitHub tokens, or write access are exposed — only read of build metadata via `cc.xml` — so this does not rise to Critical (no RCE, no forged webhook/session, no cross-tenant write).

### Likelihood Explanation
Preconditions are minimal: the attacker needs an ordinary Shipit session and access to at least one stack (their own low-privilege stack) so that the legitimate `#fetch` route is reachable. No Shipit or GitHub secrets, no operator role, and no special configuration are required — the bug is present in the default engine code as mounted. The attacker only needs to guess or discover the target `stack_id` (stack slugs like `owner/repo/env` are often predictable/enumerable), and the exploit is a single unauthenticated-cost HTTP GET per stack once the token is obtained, fully repeatable against arbitrary stacks.

### Recommendation
- In `CCMenuUrlController#fetch`, create/find the `ApiClient` scoped to the specific stack, e.g. `ApiClient.create_with(permissions: %w[read:stack], stack: stack).find_or_create_by!(creator: current_user, stack: stack, name: 'CCMenu Client')`, so `stack_id` is always set.
- In `Api::CCMenuController#stack`, use the inherited `stacks` scope (`stacks.from_param!(params[:stack_id])`) instead of unscoped `Stack.from_param!`, so tokens with a non-nil `stack_id` are restricted to that stack.
- Add a model/database constraint or validation making `stack` required (not `optional: true`) for CCMenu-purpose clients, or add an explicit check in `require_permission!`/`stack` that rejects requests where `current_api_client.stack_id.present? && current_api_client.stack_id != stack.id`.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb (new test)
test "a CCMenu token issued for one stack cannot read another stack's cc.xml" do
  owned_stack = shipit_stacks(:shipit) # stack the test user is a member of
  restricted_stack = Stack.create!(
    repository: Repository.new(owner: "operators-only", name: "secret-repo"),
    branch: "main"
  ) # belongs to a team NOT in the test user's Shipit.github_teams

  # Simulate CCMenuUrlController#fetch for the owned stack
  get :fetch_url_equivalent... # invoke Shipit::CCMenuUrlController#fetch for owned_stack as @user
  token = extracted_token_from_ccmenu_url

  # Binding under test:
  # LHS expected: ApiClient.authenticate(token).stack_id == owned_stack.id
  client = ApiClient.authenticate(token)
  assert_equal owned_stack.id, client.stack_id, "token must be scoped to the issuing stack"

  # RHS actual: request cc.xml for restricted_stack using the same token
  get :show, params: { stack_id: restricted_stack.to_param, token: token }
  assert_response :forbidden, "token scoped to owned_stack must not read restricted_stack's cc.xml"
end
```
Both assertions currently fail against the actual code: `client.stack_id` is `nil` (not `owned_stack.id`), and the second request returns `200 OK` with `restricted_stack`'s `cc.xml`, proving the divergence between the claimed binding and actual behavior.
