### Title
Cross-repository Status webhook flips `Commit#deployable?` and triggers an unauthorized deploy via missing repository binding in `StatusHandler#process` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits purely `Commit.where(sha: params.sha)` with no check that the webhook's `repository` field matches the stack's actual GitHub repository [1](#0-0) . Because `verify_signature` only proves the request is a genuine GitHub webhook for *some* organization known to Shipit — not that this organization owns the stack the matched commit belongs to — a real, validly signed status event from repository R2 can write a `success` status onto a commit that also exists (same SHA) in stack S1 tracking a different repository R1, flipping `Commit#deployable?` to true and letting continuous delivery deploy it with R1's own credentials.

### Finding Description
The claimed-but-unenforced binding is: `webhook.repository.full_name == commit.stack.repository.full_name`. Tracing the code shows this is never checked.

- `WebhooksController#verify_signature` resolves the signing key via `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight from the attacker-supplied payload (`params.dig('repository','owner','login')`) [2](#0-1) . This only proves the request came from GitHub for *an* organization Shipit knows about (R2) — it says nothing about the target stack.
- `GitHubApp#verify_webhook_signature` verifies the HMAC using that organization's own webhook secret [3](#0-2) . Crucially, the attacker does not need to know any secret themselves: if they own repository R2 and install/onboard it into the same Shipit instance (or R2 is a fork of R1 sharing history with S1), GitHub itself computes and signs the real webhook when their own CI posts a status — a completely legitimate, correctly-signed delivery.
- `StatusHandler#process` then does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [1](#0-0)  — this is a *global* lookup across all stacks/repositories by SHA alone, with no `stack_id`/repository scoping tied to the payload's `repository` object.
- `Commit#deployable?` is `!locked? && (stack.ignore_ci? || (success? && !blocked?))` [4](#0-3) . A `success` status written by the forged-cross-repo event flips this from false to true for commit `c` in S1, purely because of R2's status.
- Existing tests confirm that a `success` status transition on a commit with `stack.continuous_deployment: true` directly triggers a deploy path (skipped only for orthogonal reasons — deploy already running, stack locked, or newer commit deployed), never because the status's origin repository was checked [5](#0-4) .
- `Stack#trigger_continuous_delivery` then calls `trigger_deploy(commit, Shipit.user, env: cached_deploy_spec.default_deploy_env)` [6](#0-5) , and `trigger_deploy`/`build_deploy` runs using the stack's own repository and credentials (R1's GitHub App/token), not R2's [7](#0-6) .

None of `verify_signature`, `drop_unhandled_event`, the `ExplicitParameters` schema on `StatusHandler` (which only requires `sha`/`state`, and merely `accepts :branches`) enforce any relationship between the payload's repository and the commit/stack that gets mutated. The `params` schema for `StatusHandler` does not even require or validate a `repository` field [8](#0-7) .

Exploit flow: attacker forks/creates repository R2 containing a commit with the same SHA as an existing, undeployed commit `c` in R1's stack S1 (trivial via fork-and-preserve-history, or by directly reproducing the git object), enables any CI on R2 they fully control, and has that CI report `success` for that SHA to GitHub. GitHub delivers a genuinely signed `status` webhook to Shipit. `StatusHandler#process` matches `c` by SHA regardless of repository, marks it `success`, `c.deployable?` becomes true, and (with `S1.continuous_deployment: true`) `trigger_continuous_delivery`/`trigger_deploy` runs on R1 using R1's own credentials.

### Impact Explanation
This is a cross-tenant write: a webhook authenticated for repository/organization R2 mutates commit and stack state belonging to R1, and can cause `Stack#trigger_deploy` to execute using R1's real deploy credentials against a commit that never actually passed R1's own CI. This matches the "Critical" category: a payload for one repository mutating another's stack/commit and causing an unauthorized deploy. It is repeatable against any stack with `continuous_deployment: true` and any commit SHA colliding between an attacker-controlled repository and a victim stack (most straightforwardly a fork sharing history).

### Likelihood Explanation
Preconditions: (1) attacker owns/controls a repository whose commits can share a SHA with a commit already present in a target stack (fork of the target repo is the simplest, entirely attacker-achievable path with no privileges), (2) that repository (or its org) is one Shipit already recognizes for webhook signature verification (e.g., because the Shipit GitHub App is installable broadly, or the fork inherits the same org/App installation as the upstream), (3) the target stack has `continuous_deployment: true`. None of these require any Shipit session, API token, or secret. Attacker cost is low: fork the repo, add CI reporting `success`, no interaction with Shipit credentials needed since GitHub itself signs the delivery.

### Recommendation
In `StatusHandler#process`, require and validate the payload's `repository.full_name` (or owner/name) and scope the `Commit` lookup to commits whose `stack.repository` matches that value before calling `create_status_from_github!`, e.g. `Commit.joins(:stack).where(sha: params.sha, shipit_stacks: { repository_id: ... })` after resolving the repository from the payload, rejecting/ignoring commits whose stack repository doesn't match.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test ":status from a different repository does not mark a commit deployable or trigger a deploy" do
  stack = shipit_stacks(:shipit)
  stack.update!(continuous_deployment: true)
  commit = stack.commits.last
  refute_predicate commit, :deployable?

  request.headers['X-Github-Event'] = 'status'
  # payload claims to originate from an unrelated repository owned by the attacker
  forged_payload = {
    'sha' => commit.sha,
    'state' => 'success',
    'context' => 'ci/attacker',
    'branches' => [{ 'name' => stack.branch }],
    'repository' => { 'full_name' => 'attacker/unrelated-repo', 'owner' => { 'login' => 'attacker' } }
  }.to_json

  assert_no_difference -> { Deploy.count } do
    post :create, body: forged_payload, as: :json
  end

  refute_predicate commit.reload, :deployable?
end
```
Both sides of the binding (`params['repository']['full_name']` vs `commit.stack.repository.full_name`) should be asserted unequal before the fix, and the test should show `assert_no_difference('Deploy.count')` failing (i.e., a deploy IS created) against current code, proving the vulnerability; after adding repository scoping in `StatusHandler#process`, the assertion should pass.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def trigger_deploy(*args, **kwargs)
      if changed?
        # If this is the first deploy since the spec changed it's possible the record will be dirty here, meaning we
        # cant lock. In this one case persist the changes, otherwise log a warning and let the lock raise, so we
        # can debug what's going on here. We don't expect anything other than the deploy spec to dirty the model
        # instance, because of how that field is serialised.
        if changes.keys == ['cached_deploy_spec']
          save!
        else
          Rails.logger.warning("#{changes.keys} field(s) were unexpectedly modified on stack #{id} while deploying")
        end
      end

      run_now = kwargs.delete(:run_now)
      deploy = with_lock do
        deploy = build_deploy(*args, **kwargs)
        deploy.save!
        deploy
      end
      run_now ? deploy.run_now! : deploy.enqueue
      continuous_delivery_resumed!
      deploy
    end
