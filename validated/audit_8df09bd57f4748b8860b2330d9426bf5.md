### Title
Unscoped SHA lookup in `StatusHandler#process` lets a forged status webhook from an attacker's own repository write a `success` status onto another stack's commit, triggering an unauthorized deploy via `Stack#trigger_continuous_delivery` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves the target `Commit` purely by `sha`, with no scoping to the repository/organization that GitHub signed the webhook for. Because the `commits` table's uniqueness constraint is `[sha, stack_id]` (not `sha` alone), the same sha can legitimately exist as a `Commit` row on multiple, unrelated `Stack`s (e.g. forks sharing history), so a status the attacker legitimately gets GitHub to sign for their own repository is applied to every stack that happens to have a matching sha, including a victim's stack, and can drive that victim stack straight into `trigger_continuous_delivery` → `trigger_deploy`.

### Finding Description
The broken binding is:
`commit.stack_id (the Commit row that receives the status)` == `stack tracking the repository named in the signed webhook payload`

`StatusHandler#process` violates this:
```
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [1](#0-0) 

This query is global across all stacks, keyed only by `sha`, with no filter on `params.repository`/organization. The DB schema confirms multiple `Commit` rows with the same `sha` but different `stack_id` are expected and allowed — the unique index is composite `[sha, stack_id]`, not `sha` alone: [2](#0-1) 
The test fixtures even contain such a duplicate: sha `467578b362bf2b4df5903e1c7960929361c3435a` exists both on stack `shipit` (`fourth`) and stack `shipit_undeployed` (`undeployed6`). [3](#0-2) [4](#0-3) 

`WebhooksController#verify_signature` only authenticates that the webhook genuinely came from GitHub for the organization named in the payload; it never checks that the `sha` in the payload actually belongs to that organization's repository: [5](#0-4) 
The `StatusHandler` params schema only validates field types/presence (`sha`, `state`, `branches`), it does nothing to scope the commit lookup: [6](#0-5) 

Exploit flow: the attacker owns a repository/stack in the same Shipit installation (any unprivileged GitHub user who forks a tracked repo, or who is granted their own tracked stack, satisfies this). Because forks copy git objects verbatim, ancestor commits keep identical SHAs in both the fork and the original repository. The attacker posts (or has GitHub post, e.g. via their own CI on their fork) a `status` webhook for their own repository/organization — this passes `verify_signature` legitimately since it is a real, correctly signed GitHub webhook for the attacker's own org. `StatusHandler#process` then writes the `success` status onto every `Commit` row matching that `sha`, including the victim's stack's `Commit` row for the same shared ancestor commit.

Writing the status triggers `Status#schedule_continuous_delivery` → `Commit#schedule_continuous_delivery` → `ContinuousDeliveryJob.perform_later(stack)` using the **victim's own stack** (the stack owning the `Commit` row that got the status), not the attacker's stack: [7](#0-6) [8](#0-7) 

`ContinuousDeliveryJob#perform` then calls `stack.trigger_continuous_delivery` on the victim stack: [9](#0-8) 
which selects the commit via `next_commit_to_deploy` and calls `trigger_deploy`: [10](#0-9) 

No existing guard prevents this: `verify_signature` authenticates the webhook's origin org, not the sha-to-stack relationship; `drop_unhandled_event` does not apply since `status` is a handled event; `ExplicitParameters` only validates types; there is no `repository.full_name` check anywhere in `StatusHandler#process`.

### Impact Explanation
An attacker who controls any repository tracked by the Shipit installation (their own fork/org, no special privilege) can write CI statuses onto commits belonging to a completely different tenant's stack whenever the two stacks share a commit SHA (forks of the same upstream, shared history, cherry-picks producing identical trees). If the victim stack has `continuous_deployment` enabled and the forged status makes that shared commit "deployable," this results in an unauthorized deploy of the victim's stack with no attacker-authenticated action against that stack — exactly the "payload for one repository mutating another's stack/commit... or an unauthorized deploy" Critical category. This is repeatable against any victim stack sharing SHAs with an attacker-controlled repository, and the blast radius scales with however many forks/mirrors exist across tenants of the same Shipit installation.

### Likelihood Explanation
Preconditions: attacker must have (a) a Shipit-tracked repository/stack they control (fork of a victim's public repo, or their own tracked repo whose history happens to intersect a victim's), and (b) a commit whose sha is shared with a `Commit` row already imported into the victim's stack (trivially true for common ancestor commits of forks, which is common for open-source projects tracked by CI/CD systems like Shipit). Attacker cost is a normal GitHub push/PR/CI workflow on their own repository — no secrets, no privileged role, no session. Feasibility is high wherever forking is possible and multiple stacks track related histories; repeatable per shared-sha commit.

### Recommendation
Scope `StatusHandler#process` (and analogous handlers/lookups) by repository, not by `sha` alone: filter `Commit.joins(:stack).where(sha: params.sha, stack: { repository_owner: ..., repository_name: ... })` (or via the `repository_owner`/`repository.full_name` extracted from the webhook payload), so only commits belonging to stacks tracking the exact repository named in the verified webhook are updated.

### Proof of Concept
minitest under `test/controllers/webhooks_controller_test.rb` (no live GitHub):
1. Use fixtures `shipit_commits(:fourth)` (stack `shipit`) and `shipit_commits(:undeployed6)` (stack `shipit_undeployed`), which already share `sha = "467578b362bf2b4df5903e1c7960929361c3435a"`.
2. Enable `continuous_deployment` on `shipit_undeployed` stack (the "victim") and ensure it is deployable/not locked/no active task.
3. Stub `GithubHook.any_instance.stubs(:verify_signature).returns(true)` (as existing tests do) to represent a validly-signed webhook for the attacker's own org/repo (e.g. `owner: 'shopify'`, matching whichever org the `shipit` stack, the "attacker's" stack, belongs to).
4. `POST :create` with `X-Github-Event: status`, body `{ sha: "467578b362bf2b4df5903e1c7960929361c3435a", state: "success", context: "ci/travis" }.merge(repository_params_for_attacker_repo)`.
5. Assert: `assert_difference('shipit_stacks(:shipit_undeployed).commits.find_by(sha: ...).statuses.count', 1)` — proving the cross-stack write — and `assert_enqueued_with(job: ContinuousDeliveryJob, args: [shipit_stacks(:shipit_undeployed)])`.
6. Perform the enqueued `ContinuousDeliveryJob` and assert `assert_difference('Deploy.count')` scoped to `shipit_undeployed`'s deploys, verifying `Stack#trigger_continuous_delivery` deployed the victim's commit though the attacker only authenticated a webhook for their own, unrelated repository.

    def trigger_continuous_delivery
      return if cached_deploy_spec.blank?

      commit = next_commit_to_deploy

      if should_resume_continuous_delivery?(commit)
        continuous_delivery_resumed!
        return
      end

      if should_delay_continuous_delivery?(commit)
        continuous_delivery_delayed!
        return
      end

      begin
        trigger_deploy(commit, Shipit.user, env: cached_deploy_spec.default_deploy_env)
      rescue Task::ConcurrentTaskRunning
      end
    end
