### Title
Unfiltered `machine.environment` in fork PR's `shipit.yml` injects arbitrary env vars (including `ENV`) into `PTY.spawn` for review-stack dependency/deploy steps - ([File: app/models/shipit/deploy_spec.rb], [lib/shipit/task_commands.rb], [lib/shipit/command.rb])

### Summary
`DeploySpec#machine_env` returns `config('machine', 'environment')` verbatim with no key allowlist, unlike `deploy_variables`/`rollback_variables` which are explicitly filtered through `EnvironmentVariables#permit` before use. Because `TaskCommands#env` merges `deploy_spec.machine_env` into the hash ultimately passed to `Command#unbundled_env` and then `PTY.spawn`, and because a `ReviewStack`'s `DeploySpec::FileSystem` is built directly from the fork PR branch's checked-out `shipit.yml`, an unprivileged PR author can inject arbitrary environment keys (e.g. `ENV`) that end up in the environment of the `bundle`/`ruby` dependency step subprocess.

### Finding Description
The broken invariant, stated as an equality that should hold but doesn't:
`keys(env passed to PTY.spawn) == keys(deploy_spec.machine_env) ∩ AllowedMachineEnvKeys` — but no `AllowedMachineEnvKeys` allowlist exists for `machine.environment`, so in practice `keys(env passed to PTY.spawn) ⊇ keys(config('machine','environment'))` unfiltered.

Code path:
1. `DeploySpec::FileSystem#initialize` loads config from the checked-out working directory of the review-stack branch, i.e. the attacker's fork PR branch content (`app/models/shipit/deploy_spec/file_system.rb` `config_file_path`/`load_config`, using `SafeYAML.load`). [1](#0-0) 
2. `DeploySpec#machine_env` returns that config's `machine.environment` verbatim, with zero filtering: [2](#0-1) 
Contrast this with `deploy_variables`/`rollback_variables`, which are always passed through `filter_deploy_envs`/`filter_rollback_envs` (`EnvironmentVariables#permit`) before merging into task env — `machine_env` has no equivalent gate. [3](#0-2) 
3. `TaskCommands#env` merges `deploy_spec.machine_env` (attacker-controlled) into the env hash used for both `install_dependencies` and `perform` steps: [4](#0-3) 
4. `Command#unbundled_env` merges `@env` (containing the attacker's arbitrary keys) over `BASE_ENV`/`PATH` with no allowlist, and `Command#start` passes this directly to `PTY.spawn`: [5](#0-4) 

Exploit flow: attacker opens a PR from a fork against a repository configured to auto-create `ReviewStack`s (`allow_all` or `allow_with_label` + attacker self-labels their own PR — both permitted per the threat model as the attacker owns the PR). The PR branch's `shipit.yml` includes a `machine: {environment: {ENV: "/path/to/malicious/rcfile"}}` entry pointing at a file also committed in the fork branch (e.g. under the checkout directory) that the shell reads on startup. When Shipit provisions the review stack and runs `TaskCommands#install_dependencies` (a `bundle`/`ruby` step), the resulting `Command` is started with `ENV` set in its process environment, and the shell invoked to run the dependency step command sources that attacker-controlled file at startup, achieving code execution as the Shipit deploy-host process user.

Why existing guards don't stop this: `filter_deploy_envs`/`filter_rollback_envs` only gate `deploy.variables`/`rollback.variables`, not `machine.environment`; there is no equivalent `EnvironmentVariables#permit` call anywhere in the `machine_env` path. `ReviewStack#env` only adds PR label-derived keys and doesn't restrict `machine_env`. Nothing in `Command`/`unbundled_env`/`BASE_ENV` filters key names either — it merges `@env.stringify_keys` unconditionally.

### Impact Explanation
This grants arbitrary command execution on the Shipit deploy host under the identity running task/deploy jobs, triggered purely by opening/labeling a fork PR against a repository with review-stack auto-provisioning enabled — no maintainer approval or merge required, matching the Critical "RCE on the deploy host via `Command`/`PTY.spawn`" category. The blast radius extends to any repository/stack that uses review stacks with PR-authored `shipit.yml`, and is repeatable per PR/per push.

### Likelihood Explanation
Preconditions: the target repository must have review-stack provisioning enabled for PRs (`allow_all`, or `allow_with_label` where the attacker can add the label to their own PR), and Shipit must actually run `ruby`/`bundle` dependency steps (common default via `BundlerDiscovery`). No Shipit secrets, sessions, or team membership are required — only the ability to open a PR and control its branch content, which is explicitly in the unprivileged attacker's grasp per the threat model.

### Recommendation
Apply an explicit allowlist/schema to `DeploySpec#machine_env` analogous to `filter_deploy_envs`/`filter_rollback_envs` (e.g., require operator-side `VariableDefinition`s or a fixed set of permitted keys for `machine.environment`, and reject/ignore reserved/loader-sensitive names such as `ENV`, `BASH_ENV`, `RUBYOPT`, `LD_PRELOAD`, `PATH` etc.), or disallow `machine.environment` entirely for review-stack-tier `DeploySpec::FileSystem` sourced from untrusted fork branches, restricting it to server-side/cacheable config.

### Proof of Concept
Minitest plan (`test/models/deploy_spec_test.rb` / `test/unit/task_commands_test.rb` style):
```ruby
test "#machine_env passes through attacker-controlled ENV key with no filtering" do
  spec = DeploySpec.new('machine' => { 'environment' => { 'ENV' => '/tmp/evil.sh' } })
  assert_equal({ 'ENV' => '/tmp/evil.sh' }, spec.machine_env) # binding broken: no allowlist applied
end

test "TaskCommands#env inherits unfiltered machine_env into Command env reaching PTY.spawn" do
  task_commands = TaskCommands.new(@task)
  task_commands.stubs(:deploy_spec).returns(stub(machine_env: { 'ENV' => '/tmp/evil.sh' }, directory: nil))
  command = task_commands.install_dependencies.first
  assert_equal '/tmp/evil.sh', command.env['ENV']
  assert_equal '/tmp/evil.sh', command.unbundled_env['ENV'] # value that would reach PTY.spawn
end
```
Assertion on both sides of the binding: LHS = `keys(command.unbundled_env)` includes `'ENV'`; RHS (expected, per invariant) = `keys(deploy_spec.machine_env) ∩ allowlist` should be empty for `'ENV'` — they diverge, confirming the vulnerability.

    end
