### Title
Webhook signature verification is keyed on an attacker-controlled `repository.owner.login` field that is decoupled from the `repository.full_name` the handlers actually act on, allowing cross-organization/cross-repository webhook forgery when any configured organization has no `webhook_secret` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which organization's secret to validate a webhook against using a value pulled straight out of the still-unverified JSON body, while the handlers that actually mutate state key off a different (or no) field from that same body. This is the same class of bug as the audit finding: one side of an equality (`collateral` vs `debt*feeAdjustment`) is silently drawn from an inconsistent source than the other side, so the two "match" only by convention, not by enforcement.

### Finding Description
`verify_signature` selects the GitHub App/secret to verify against using: [1](#0-0) [2](#0-1) 

`repository_owner` is read from `params`, which is populated from the raw JSON request body **before** any signature check has happened - it is fully attacker-controlled. `Shipit.github(organization: repository_owner)` then loads that organization's config and its `webhook_secret`: [3](#0-2) 

Crucially, `verify_webhook_signature` treats an unset/blank `webhook_secret` as "always valid": [4](#0-3) 

Once `verify_signature` passes, `create` re-parses the *same* raw body and dispatches it to handlers, with no re-binding to the organization that was just "authenticated": [5](#0-4) 

The handlers scope their side effects using an entirely different field from the same payload - `repository.full_name`: [6](#0-5) 

or, in the case of `StatusHandler`, using no repository scoping at all - a global `sha` lookup across every stack/repo/org in the installation: [7](#0-6) 

Because `repository_owner` (used to pick the verifying secret) and `repository.full_name`/`sha` (used to pick what gets mutated) are read from the same untrusted JSON body but never checked against each other, an attacker can put one organization's login in `repository.owner.login` (to satisfy/bypass `verify_signature`) while pointing the actual payload contents at a completely different, unrelated repository or commit.

### Impact Explanation
If any organization configured on the Shipit instance (`Shipit.github_organizations`) has no `webhook_secret` set - plausible in a multi-tenant deployment where some orgs are added without configuring a secret - `verify_webhook_signature` for that org returns `true` unconditionally, regardless of the `X-Hub-Signature` header. An attacker who knows (or discovers) that org's login can then set `repository.owner.login` to that org while setting `repository.full_name` (for `push`, `check_suite`, `pull_request`) or `sha` (for `status`, which has no repository scoping whatsoever) to target any *other* repository/commit tracked anywhere in the same Shipit instance.

This breaks the intended binding "the organization whose signature was verified == the repository/commit being written to." Concretely, via `StatusHandler`, this lets an unauthenticated attacker inject a fabricated commit `Status` (e.g. `state: "success"`) onto an arbitrary commit belonging to a fully-protected, unrelated repository, without ever knowing that repository's real `webhook_secret`. Since commit statuses feed into Shipit's deployability checks, this is a cross-repository write that can be used to make an unreviewed/failing commit appear deployable, i.e. an unauthorized-deploy primitive - matching the "Critical: cross-repository writes / unauthorized deploy" impact category.

### Likelihood Explanation
No credentials, tokens, or GitHub access are required - only that the webhook endpoint is reachable (it is unauthenticated by design) and that at least one configured organization lacks a `webhook_secret`. Given `github_app_config` supports independent per-organization configuration, and nothing in the codebase enforces that every configured organization set a secret, this is a realistic misconfiguration rather than a purely theoretical one.

### Recommendation
- Bind signature verification and payload processing to the same, single source of truth: derive the organization used for HMAC verification from the same `repository.full_name`/`organization.login` field the handlers use, and reject the webhook if `repository.owner.login` doesn't match the repository actually referenced.
- Do not allow `verify_webhook_signature` to silently succeed when `webhook_secret` is blank; either require a secret for every configured organization or fail closed.
- Scope `StatusHandler` (and any other handler lacking it) to the repository named in the payload rather than performing a global, cross-repository `Commit.where(sha:)` lookup.

### Proof of Concept
1. Configure two GitHub organizations in `secrets.github`: `org-a` (no `webhook_secret` set) and `org-b` (protected, has a real `webhook_secret`), both with stacks/commits tracked by this Shipit instance.
2. As an unauthenticated attacker, POST to `/github/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-a/dummy" },
  "sha": "<commit sha belonging to org-b's repo>",
  "state": "success",
  "context": "ci/required-check"
}
```
No `X-Hub-Signature` header (or an arbitrary one) is needed.
3. `verify_signature` calls `Shipit.github(organization: "org-a").verify_webhook_signature(...)`, which returns `true` unconditionally because `org-a` has no `webhook_secret`. [8](#0-7) 
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and creates a forged "success" status on the `org-b` commit, entirely bypassing `org-b`'s own webhook secret. [7](#0-6)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
