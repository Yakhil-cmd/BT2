### Title
Unbounded recursive expansion of `definition template` parameters can crash a validating node - (File: definition.js)

### Summary
CVE-2023-31723 describes a segfault in yasm's `expand_mmac_params`, caused by unbounded/uncontrolled recursive expansion of macro parameters while parsing nested macro-call structures. The analogous pattern in ocore is `replaceInTemplate()`, which recursively walks an arbitrary user-supplied, arbitrarily nested `definition_template` payload and substitutes `$name` placeholders with caller-supplied `params`, with no depth limit of its own.

### Finding Description
`replaceInTemplate` recurses over the full JSON structure of a stored `definition_template` message via its inner `replaceInVar` closure, descending into every array element/object field with no bound on nesting depth: [1](#0-0) 

This function is invoked from two call sites when a unit's address definition contains a `['definition template', [unit, params]]` operator:

1. In `validateDefinition`'s `evaluate()` (used when validating a brand-new address definition attached to a unit), the call is wrapped in try/catch but only `NoVarException` is swallowed — any other thrown error (e.g. `RangeError: Maximum call stack size exceeded`) is re-thrown: [2](#0-1) 

2. In `validateAuthentifiers`'s `evaluate()` (used every time a unit is signed by/authenticated against an address whose definition uses a template), the call has **no try/catch at all**: [3](#0-2) 

The `evaluate()` functions that surround these calls do enforce `MAX_COMPLEXITY`/`MAX_OPS` limits on the definition *tree structure itself*, but those counters only increment once per definition-tree node during `evaluate` — they do not bound the recursion depth of `replaceInTemplate`, which runs as a separate, prior step on the raw template JSON (an attacker-controlled `definition_template` message) before `evaluate` ever sees the filled-in result: [4](#0-3) 

An unprivileged unit poster can post a `definition_template` app message containing a deeply nested array/object structure (e.g., thousands of nested arrays), have it become stable, and then reference it via `['definition template', [that_unit, {...}]]` in any address definition (their own address, or the definition supplied inline when providing authentifiers for validation). When any node evaluates/validates that definition — which happens routinely for authentifier checks and re-validation — `replaceInTemplate`'s unbounded recursion can exhaust the JS call stack, throwing an uncaught `RangeError` at the second call site (`validateAuthentifiers`), crashing the node process the same way for every node that processes this unit.

### Impact Explanation
Because this validation path runs deterministically and identically on every full node/witness/hub that processes the crafted unit (via `validateAuthentifiers`, which lacks the try/catch present in the other call site), a single malicious unit can reliably crash any node that attempts to validate it, preventing the network from confirming that unit (and potentially subsequent units depending on it). This matches the "network unable to confirm new units" / node-crash class of impact.

### Likelihood Explanation
Reaching this code only requires: (1) posting an ordinary `definition_template` message with a deeply nested payload, waiting for it to stabilize, and (2) posting a unit whose author/authentifier definition references that template via `['definition template', ...]`. Both operations are available to any unprivileged unit poster with no special privileges, matching the "unprivileged unit poster ... address definitions and authentifiers" reachable surface named in scope. The main uncertainty is the exact JS engine stack-frame budget needed to trigger the crash (nesting depth), which depends on runtime/stack-size configuration and was not verified experimentally here.

### Recommendation
Add an explicit depth (and/or total node count) limit inside `replaceInTemplate`/`replaceInVar`, mirroring the `MAX_DEPTH`/complexity checks already used elsewhere in `definition.js` and `aa_validation.js`, and reject templates whose parameter tree exceeds that limit before recursing. Additionally, wrap the `validateAuthentifiers` call site (definition.js ~802-819) in the same try/catch used in `validateDefinition`, converting any unexpected exception (including stack-overflow `RangeError`s) into a normal validation failure (`cb(false)`/`cb2(false)`) rather than letting it propagate and crash the process.

### Proof of Concept
1. Post a unit with app `definition_template` whose payload is a very deeply nested array, e.g. `JSON.stringify` of `Array(50000).fill(0).reduceRight((acc) => [acc], '$x')` (a chain of nested single-element arrays terminating in `"$x"`), and let it become stable.
2. Post a second unit whose author or authentifier definition is `['definition template', [<first_unit>, {x: 'value'}]]`.
3. When any node validates the second unit (or later revalidates the address's authentifiers), `replaceInTemplate` recurses once per nesting level; at sufficient depth this throws `RangeError: Maximum call stack size exceeded`, which is uncaught in the `validateAuthentifiers` call path (definition.js:802-819) and crashes the node process.

function replaceInTemplate(arrTemplate, params){
	function replaceInVar(x){
		switch (typeof x){
			case 'number':
			case 'boolean':
				return x;
			case 'string':
				// searching for pattern "$name"
				if (x.charAt(0) !== '$')
					return x;
				var name = x.substring(1);
				if (!ValidationUtils.hasOwnProperty(params, name))
					throw new NoVarException("variable "+name+" not specified, template "+JSON.stringify(arrTemplate)+", params "+JSON.stringify(params));
				return params[name]; // may change type if params[name] is not a string
			case 'object':
				if (Array.isArray(x))
					for (var i=0; i<x.length; i++)
						x[i] = replaceInVar(x[i]);
				else
					for (var key in x)
						assignField(x, key, replaceInVar(x[key]));
				return x;
			default:
				throw Error("unknown type");
		}
	}
	return replaceInVar(_.cloneDeep(arrTemplate));
}
