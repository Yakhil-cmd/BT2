### Title
Webhook signature verification is keyed on `repository.owner.login`/`organization.login` while every event handler writes state keyed on `repository.full_name` or `params.sha`, with no cross-check between the two — allowing forged writes to any repository once one configured GitHub organization has no `webhook_secret` set - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb], [File: lib/shipit/github_app.rb])

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and therefore the HMAC secret) to validate a webhook against using only `repository.owner.login` (or `organization.login`) taken from the *unverified* JSON body. [1](#0-0)  `GitHubApp#verify_webhook_signature` then returns `true` unconditionally whenever that organization's `webhook_secret` is blank — a state explicitly presented as valid/optional in the docs and example secrets files. [2](#0-1)  Meanwhile every actual write performed by a handler (which stack/repository/commit gets updated) is derived from a *different* field of the same unverified body — `repository.full_name` in `Handler#repository_name` (used by `PushHandler`, pull-request handlers, etc.) or `sha` in `StatusHandler`. [3](#0-2) [4](#0-3)  Neither the controller nor the handlers verify that the organization used to select/validate the signature actually matches the owner of the repository that is subsequently written to.

### Finding Description
The security-relevant equality that should hold is:

`organization whose secret authenticated the request == owner of the repository the handler subsequently writes to`

In this engine that binding is never enforced:

1. `verify_signature` picks the GitHub App/secret via `repository_owner`, computed as `params.dig('repository','owner','login') || params.dig('organization','login')`. [5](#0-4) 
2. `Shipit.github(organization:)` looks up per-organization app config from `secrets.github`, supporting deployments with multiple GitHub Apps/organizations (`app/…`, `lib/shipit.rb`). [6](#0-5) 
3. `verify_webhook_signature` treats a blank `webhook_secret` as automatically verified: `return true unless webhook_secret`. [2](#0-1)  The shipped example configs explicitly show `webhook_secret: # nil` as an acceptable value for any configured organization, and the setup docs call the webhook secret "optional." [7](#0-6) 
4. Once `verify_signature` passes (trivially, because the attacker only needs to name an organization configured in `secrets.github` with no `webhook_secret`), the request body is handed unmodified to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` in `WebhooksController#create`. [8](#0-7) 
5. Handlers never re-validate that the repository they act on belongs to the organization that "authenticated" the request. `Handler#repository_name` reads `payload.dig('repository', 'full_name')` directly, and `Repository.from_github_repo_name` is then used to locate the target `Stack` for `PushHandler`, all pull-request handlers, etc. [3](#0-2)  `StatusHandler` similarly trusts `params.sha` unconditionally to look up any `Commit` record system-wide and creates a GitHub-style CI status for it via `commit.create_status_from_github!(params)`, with no verification that the commit belongs to a repository owned by the authenticating organization. [4](#0-3) 

This is analogous to the Surge `Pool.sol` bug: the field used to gate/authorize the state transition (`_util`, computed from a manipulable live balance) is decoupled from the field that determines the magnitude of the transition (`timeDelta`), letting an attacker use a cheap, attacker-controlled side channel to legitimize a large, otherwise-blocked update. Here the "gate" (organization signature check) is keyed on one payload field while the "write" (which stack/commit is mutated) is keyed on a completely different, unrelated payload field, and the engine never checks that they agree.

### Impact Explanation
An attacker who can reach the public `/webhooks` endpoint (no session, no `ApiClient` token, no GitHub credentials required — only knowledge that some configured Shipit organization has a blank `webhook_secret`, which is a documented, supported configuration) can:
- Forge `status` events for arbitrary commit SHAs on *any* tracked stack, injecting fabricated CI-success statuses that `ci.require`/`ci.blocking` checks rely on, directly enabling an **unauthorized deploy** of unreviewed code (High/Critical per the given impact list).
- Forge `push` events pointing at arbitrary tracked repositories to trigger `GithubSyncJob`/`stack.sync_github`, and forge `pull_request`/`membership` events to archive/unarchive review stacks or create arbitrary teams/users, regardless of which organization actually owns those resources.

This crosses the organizational trust boundary the multi-org configuration (`Shipit.github(organization:)`, `github_app_config`) is meant to enforce: a webhook that is only "authenticated" as belonging to Org A can freely mutate state belonging to Org B's repositories, because the code path that decides trust and the code path that decides target never reference the same value.

### Likelihood Explanation
Likelihood is conditional but realistic: it requires at least one configured GitHub organization/app to have no `webhook_secret` set — a state the project's own example configs (`config/secrets.development.shopify.yml`, `config/secrets.development.example.yml`) show as normal/default, and which `docs/setup.md` explicitly labels "optional." In any Shipit deployment where an operator follows the documented multi-org setup without filling in every `webhook_secret` (e.g. during initial onboarding of a new org, or because the field is marked optional), any unauthenticated internet user can exploit this immediately with a single crafted POST, with zero repository or platform credentials.

### Recommendation
- Require `webhook_secret` to be present for every configured organization (fail closed instead of `return true unless webhook_secret`), or at minimum log/alert loudly when an org is running unauthenticated.
- Bind the authenticated organization to the object being mutated: after verifying the signature for organization `O`, every handler should confirm that the repository/commit/stack it operates on actually belongs to `O` (i.e., compare `repository.owner.login` used for auth against the owner of `repository.full_name`/the commit's repository) before performing any write, rejecting the event otherwise.
- Treat the entire webhook payload as coming from a single, already-authenticated source rather than re-deriving trust-relevant identifiers (organization) and target identifiers (repository/commit) from independent, unauthenticated substructures of the same JSON body.

### Proof of Concept
Preconditions: Shipit is configured with at least two GitHub organizations, e.g. `OrgA` (has `webhook_secret` set) and `OrgB` (no `webhook_secret`, matching the shipped example configs), and `OrgA/victim-repo` has a tracked `Stack` with `ci.require` configured.

1. Attacker sends, unauthenticated, with no `X-Hub-Signature` header (or any garbage value):
```
POST /webhooks
X-Github-Event: status

{
  "sha": "<sha-of-a-real-commit-on-OrgA/victim-repo-that-lacks-passing-CI>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "OrgB" }, "full_name": "OrgA/victim-repo" }
}
```
2. `verify_signature` resolves `repository_owner` → `"OrgB"`, fetches `Shipit.github(organization: "OrgB")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the (missing/garbage) signature header. [1](#0-0) [2](#0-1) 
3. The request proceeds to `StatusHandler`, which looks up `Commit.where(sha: params.sha)` — a commit that actually belongs to `OrgA/victim-repo` — and calls `commit.create_status_from_github!(params)`, injecting a forged `success` status for the required CI context. [4](#0-3) 
4. With the forged passing status now present, an operator (or continuous deployment) can ship the previously CI-blocked commit — an unauthorized deploy enabled entirely by an unauthenticated request that never needed any credential belonging to `OrgA` or `victim-repo`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
