### Title
`Api::CCMenuController#stack` bypasses the `current_api_client.stack_id` binding enforced by `Api::BaseController#stacks`, allowing cross-stack CC.xml disclosure with any token - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Api::CCMenuController` overrides both `authenticate_api_client` and `stack`, and its `stack` method calls `Stack.from_param!(params[:stack_id])` directly instead of going through `Api::BaseController#stacks`, which is the only place that restricts stack access to `current_api_client.stack_id`. As a result, a CCMenu token minted for one stack can be replayed with an arbitrary `stack_id` in the URL to read another stack's deploy/rollback state.

### Finding Description
The binding that should hold is: `stack requested via params[:stack_id]` == `current_api_client.stack_id` (when the client is stack-scoped), exactly as enforced in `Api::BaseController#stacks`: [1](#0-0) 

`Api::CCMenuController` never calls `stacks`. It defines its own `stack`: [2](#0-1) 
which resolves any `params[:stack_id]` against the full `Stack` table with no reference to `current_api_client.stack_id`.

`require_permission :read, :stack` only checks that the client's `permissions` array contains the literal string `"read:stack"`; `ApiClient#check_permissions!` performs no stack-identity comparison at all: [3](#0-2) 

The token is minted per-stack by `CCMenuUrlController#fetch`, which creates/reuses an `ApiClient` scoped to `read:stack` (not tied at the DB level to a single stack in a way that's enforced downstream) and builds a URL containing `stack_id` and `token`: [4](#0-3) 

This URL is explicitly meant to be handed to unauthenticated third-party CI-badge tools. Attack flow:
1. Attacker (or a legitimate low-privilege user) obtains a CCMenu URL for stack A, e.g. `GET /api/1/stacks/A/cc.xml?token=T`.
2. Attacker sends `GET /api/1/stacks/B/cc.xml?token=T` (same token, different `stack_id`).
3. `authenticate_api_client` succeeds via `ApiClient.authenticate(params[:token])`, which only verifies the signed client id, not the stack in the URL.
4. `require_permission!(:read, :stack)` passes because the client still has `read:stack` permission generically.
5. `stack` resolves `Stack.from_param!(params[:stack_id])` = stack B directly, ignoring the client's `stack_id`, and renders stack B's deploy/rollback XML.

Existing guards do not catch this: `verify_signature`/webhook checks are irrelevant to this HTTP GET path; `ExplicitParameters` doesn't apply here; the only relevant guard, the `stacks` scoping in `Api::BaseController`, is simply never invoked because `CCMenuController` shadows both `authenticate_api_client` and `stack`.

### Impact Explanation
An attacker who obtains any single valid CCMenu token (which is by design distributed to unauthenticated third-party CI dashboard tools) can enumerate/guess other stacks' `stack_id` (owner/repo/branch/env slugs, which are not secret) and read their deploy status, lock state, last build result, etc. for every stack in the Shipit instance — an unauthenticated cross-tenant read of stack state, matching the "High" impact category (unauthenticated read of stack state).

### Likelihood Explanation
Preconditions are minimal: the attacker only needs one legitimate CCMenu token, which is handed out by design to unauthenticated CI-badge consumers via `CCMenuUrlController#fetch`. No secrets, GitHub credentials, or privileged roles are required, and `stack_id` values (repo owner/name/branch) are typically discoverable/guessable from public repo names. The attack is a single unauthenticated GET request and is fully repeatable against any stack in the instance.

### Recommendation
Make `Api::CCMenuController#stack` go through the scope-enforcing accessor, e.g. remove the custom `stack` override and rely on `Api::BaseController#stack`/`#stacks` (`stacks.from_param!(params[:stack_id])`), or explicitly check `current_api_client.stack_id.nil? || current_api_client.stack_id == resolved_stack.id` before rendering.

### Proof of Concept
Minitest integration test (in `test/controllers/api/ccmenu_controller_test.rb` style):
```ruby
test "a token minted for stack A cannot be used to read stack B" do
  stack_a = shipit_stacks(:shipit)
  stack_b = Stack.create!(repository: Repository.new(owner: "foo", name: "bar"), branch: "main")

  client = ApiClient.create!(creator: shipit_users(:walrus), name: "CCMenu Client",
                              permissions: %w[read:stack], stack: stack_a)

  get :show, params: { stack_id: stack_b.to_param, token: client.authentication_token }

  # Binding under test: stack requested via params[:stack_id] should equal current_api_client.stack_id
  assert_not_equal stack_b.id, client.stack_id
  assert_response :forbidden # or :not_found — currently fails: renders 200 with stack_b's XML
end
```
This demonstrates that `stack_b.id != client.stack_id` yet the controller still renders `stack_b`'s CC.xml, proving the binding is broken.
