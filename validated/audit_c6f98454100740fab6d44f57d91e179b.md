### Title
Frontmatter parser mis-splits on embedded `---` in a rule value, silently corrupting/downgrading `.claude/hookify.*.local.md` security rules - ([File: plugins/hookify/core/config_loader.py])

### Summary
`extract_frontmatter` locates the end of the YAML frontmatter block by calling `content.split('---', 2)`, which splits on the raw literal substring `---` anywhere in the file rather than on a line that is exactly `---`. A rule author's `pattern:` (or any other) value containing `---` inside it (e.g. a shell/log pattern like `foo---bar` or a regex range like `a---z`) will be treated as the closing delimiter, truncating the parsed frontmatter dict before later-declared fields such as `action: block` or `enabled: true` are parsed.

### Finding Description
`extract_frontmatter` (`plugins/hookify/core/config_loader.py:87-103`) does:
```
parts = content.split('---', 2)
frontmatter_text = parts[1]
message = parts[2].strip()
```
This is a naive substring split with no line-boundary check, unlike a real YAML parser which only treats a `---` that occupies its own line as a document delimiter. If a value inside the frontmatter block (e.g. `pattern: "id---rm"` or any regex containing a literal `---`, which is valid in patterns matching command output, log lines, or ranges) appears before the intended closing `---` line, the second occurrence counted by `split(..., 2)` is that embedded text, not the real delimiter.

Effect: `frontmatter_text` (parts[1]) is truncated at the embedded `---`, so any frontmatter keys that appear *after* that line in the file (commonly `action`, but also `enabled`, `event`, `tool_matcher`) are pushed into `parts[2]`, which becomes part of the rule's `message` body instead of the parsed dict. The real closing `---` delimiter line is now just plain text inside the message.

Consequences observed downstream:
- `Rule.from_dict` (`plugins/hookify/core/config_loader.py:75-84`) falls back to defaults for any field missing from the truncated dict: `action=frontmatter.get('action', 'warn')` at line 81. A rule authored as `action: block` that is declared after the crafted `pattern` line silently becomes `action: warn`.
- In `RuleEngine.evaluate_rules` (`plugins/hookify/core/rule_engine.py:55-58`), only rules with `rule.action == 'block'` are placed into `blocking_rules`, which is the only path that produces `permissionDecision: deny` in `pretooluse.py`. A rule downgraded to `warn` will show a message but **allow the dangerous Bash/Edit/Write/MultiEdit operation to proceed**, defeating the intended enforcement.
- The `pattern` value itself is also truncated/malformed (missing its trailing portion, quotes unbalanced), potentially producing a broken regex that fails to match the dangerous command at all, or in `load_rule_file` (line 256-258) an empty `frontmatter` dict causes the whole rule to be silently dropped with only a stderr warning that is not surfaced to the user in the hook's JSON output.

No existing check in `extract_frontmatter`, `Rule.from_dict`, or `load_rule_file` validates that the closing delimiter is on its own line, that all expected keys were actually parsed, or that `action`/`enabled` values were explicitly declared vs. defaulted. There is no allowlist, workspace guard, or approval prompt gating the *content* of `.claude/hookify.*.local.md` files themselves — they are just read via `glob.glob` and parsed (`config_loader.py:198-241`).

### Impact Explanation
This affects `PreToolUse`/`PostToolUse` hook enforcement — the mechanism repositories use to auto-block dangerous Bash commands or file edits. If an untrusted contributor can influence the content of a `hookify.*.local.md` rule file (e.g., via a PR that "adds/updates" a security rule, or via any automated flow that lets Claude Code or a script write such a file based on issue/PR text), a crafted `pattern` value containing `---` can silently convert an intended `action: block` guard into a no-op `warn`, or delete the rule outright. The impact is an approval/enforcement bypass: dangerous commands or file writes that the maintainer believed were blocked continue to execute normally, with the only signal being a benign warning message or a stderr line that is not shown to the interactive user.

### Likelihood Explanation
Feasibility is high and requires no special privilege: it only requires the ability to get an ordinary-looking hookify rule file (or an edit to one) into `.claude/` — a scenario within the "reachable from ordinary repository content, plugin files ... hook/frontmatter parsing" threat model. The trigger is a single plain-text value containing `---`, which is unremarkable in review (e.g. a pattern intended to catch commands like `curl ... | sh` variants, log separators, or numeric ranges expressed with `---`) and easy to overlook since the parser gives no error for a "successful" (but wrong) parse when other fields still resolve to something. It is fully deterministic and reproducible with a static test file.

### Recommendation
Replace the ad-hoc `split('---', 2)` approach with delimiter detection anchored to whole lines only (e.g., iterate lines and treat a line equal to exactly `---` as a boundary, not any substring match), or better, use Python's `yaml.safe_load` for the frontmatter block via a proper YAML library and only split the raw text on a regex like `^---\s*$` in `re.MULTILINE` mode. Additionally, `Rule.from_dict` should treat missing but referenced security-relevant keys (`action`, `enabled`) as a hard parse error rather than silently defaulting, or `load_rule_file` should reject rules where the number of parsed top-level keys looks inconsistent with the raw text (e.g., cross-check key count before/after).

### Proof of Concept
Unit test to add to a hookify test suite (`plugins/hookify/core/config_loader.py` test target `extract_frontmatter`):
```python
from hookify.core.config_loader import extract_frontmatter, Rule

content = """---
name: block-dangerous-curl
enabled: true
event: bash
pattern: "curl .*---pipe.* | sh"
action: block
---

Blocked: piping remote script to shell.
"""

fm, msg = extract_frontmatter(content)

# Expected (correct) behavior: action key must survive parsing
assert fm.get('action') == 'block', f"action was lost/downgraded: {fm}"

rule = Rule.from_dict(fm, msg)
assert rule.action == 'block', f"Rule action defaulted to '{rule.action}' instead of 'block' due to frontmatter truncation"
```
Running this against the current implementation demonstrates that `fm` does not contain the `action` key (it ends up embedded in `msg`), `Rule.from_dict` defaults `action` to `'warn'`, and thus `RuleEngine.evaluate_rules` would place this rule in `warning_rules` instead of `blocking_rules`, allowing the matched dangerous Bash command to execute.
