### Title
Attacker-controlled swap route can expand the caller’s signed authorization tree to drain unrelated wallet tokens - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The controller passes opaque `swap` bytes to the configured router after authorizing only an exact input-token transfer to that router, but contracts reached through the route can invoke additional caller-authorized token transfers that Soroban simulation records beneath the caller’s root authorization. [1](#0-0) [2](#0-1) 

### Finding Description
`swap_tokens` snapshots the controller’s input and output balances, authorizes exactly `token_in.transfer(controller, router, amount_in)`, and then invokes `router.execute_strategy(controller, amount_in, swap)` without decoding the venue or pool addresses inside `swap`. [3](#0-2) 

That narrow controller authorization does not prevent route-selected code from calling `caller.require_auth()`-protected token functions against the account owner who submitted the transaction. [4](#0-3) 

During transaction simulation, such a call is recorded as a child invocation below the caller’s `swap_collateral` authorization entry; signing the returned tree therefore authorizes the unrelated wallet transfer together with the visible collateral swap. [5](#0-4) 

The affected entrypoints include `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, and `multiply`, because they pass user-supplied route bytes through the same `swap_tokens` path. [6](#0-5) [7](#0-6) 

### Impact Explanation
A malicious route can steal tokens held by the account owner outside the supplied collateral and outside the swap’s declared input and output assets. [8](#0-7) 

The regression test demonstrates theft of Alice’s entire unrelated `WALLET_BALANCE` while her `swap_collateral` still receives a valid output and satisfies the normal accounting checks. [9](#0-8) 

The attacker does not need a protocol role, leaked key, upgrade, oracle manipulation, or control of the victim’s account; the prerequisite is persuading the victim or its wallet integration to sign the poisoned authorization tree produced for the malicious route. [10](#0-9) 

### Likelihood Explanation
The exploit is feasible because route bytes are supplied as an argument to an ordinary owner-authorized strategy call, while the extra token transfer only appears in the nested authorization tree generated by simulation rather than in the controller entrypoint arguments themselves. [1](#0-0) [11](#0-10) 

An honest authorization tree prevents the transfer: enforcement rejects the rogue call, rolls back the transaction, and leaves both the unrelated wallet token and supplied collateral unchanged. [12](#0-11) 

Likelihood is therefore bounded by wallet or client failure to inspect the complete simulated authorization tree; a client that only validates the root call and routed input amount can sign the child theft authorization. [13](#0-12) 

### Recommendation
Require a machine-readable route manifest or authenticated quote and validate every simulated authorization subtree before signing; a legitimate strategy should contain no extra `require_auth` transfer from the caller beyond the expected strategy-specific pulls. [1](#0-0) [12](#0-11) 

Where routing remains opaque, wallets and integrating contracts should reject any child invocation under the caller’s root entry that transfers a token other than the authorized strategy input or targets an unexpected recipient. [11](#0-10) 

### Proof of Concept
1. Deploy a route-invoked contract initialized with `(victim, unrelated_token, attacker, amount)` and have its route callback call `unrelated_token.transfer(victim, attacker, amount)`. [4](#0-3) 

2. Give the victim supplied USDC collateral and an unrelated wallet-token balance, encode the malicious contract as a hop pool, and submit `swap_collateral(victim, account_id, USDC, amount, ETH, route)`. [14](#0-13) [15](#0-14) 

3. Simulate the transaction and sign the returned root authorization containing the child `unrelated_token.transfer(victim, attacker, WALLET_BALANCE)` invocation. [2](#0-1) 

4. Execute the signed transaction: the swap succeeds, the victim receives fair ETH collateral, the unrelated token is transferred to the attacker, and the victim’s wallet balance becomes zero. [9](#0-8) [13](#0-12)

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);
