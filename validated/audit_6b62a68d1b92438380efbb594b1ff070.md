### Title
Webhook signature verification is scoped to the wrong GitHub App, letting an unauthenticated sender target any tracked stack once *any* configured organization lacks a `webhook_secret` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `GithubApp`/secret to verify a webhook against using the payload's own `repository.owner.login` (or `organization.login`) field, while the actual write target used by every event handler is a *different* payload field: `repository.full_name`. Because `GithubApp#verify_webhook_signature` unconditionally returns `true` when that app's `webhook_secret` is blank, a caller can pick any organization slot configured without a secret to sail through signature verification, and then supply an unrelated `repository.full_name` naming any stack tracked by the Shipit instance. This breaks the binding "organization that authenticated" == "repository that is written."

### Finding Description
`WebhooksController#verify_signature` computes the authorizing organization purely from attacker-supplied JSON: [1](#0-0) [2](#0-1) 

It then verifies the signature using that org's app: [1](#0-0) 

`GithubApp#verify_webhook_signature` has a bypass built in for apps configured without a secret: [3](#0-2) 

Meanwhile, every event handler resolves the *stack to mutate* from a completely independent field of the same JSON body, `repository.full_name`, with no cross-check against `repository.owner.login`/`organization.login` used above: [4](#0-3) 

For example, `PushHandler` finds stacks by that `repository_name` and calls `stack.sync_github(expected_head_sha: params.after)`, with `after` fully attacker-controlled: [5](#0-4) 

Shipit's own documented multi-org configuration explicitly allows an org entry with `webhook_secret` left blank/nil: [6](#0-5) [7](#0-6) 

Putting this together: if any org configured in `Shipit.github` config has no `webhook_secret` (a state the engine's own docs/config samples treat as valid), an unauthenticated caller can send `POST /webhooks` with `X-Github-Event: push` and a payload where `repository.owner.login` (or `organization.login`) is set to that no-secret org — causing `verify_signature` to short-circuit to `true` with no signature header needed — while `repository.full_name` names any *other* repository/stack tracked by the same Shipit install. `PushHandler` will then locate and act on that unrelated stack.

This is exactly the report's structural pattern: the entity that is authenticated (the organization used to pick a verification key) is not the entity that the mutation is scoped to (the repository/stack acted upon), so control over one payload field ("which org verifies me") lets the attacker drive an unrelated field ("which repo/stack gets written").

### Impact Explanation
An unauthenticated request can force a `GithubSyncJob` to run against an arbitrary tracked stack, with an attacker-chosen `expected_head_sha`, without ever presenting valid credentials for that stack's real organization/app. On stacks with continuous deployment/auto-deploy enabled, driving a sync against a spoofed head can trigger deployment of whatever commit satisfies that sha lookup, i.e., an unauthorized deploy trigger crossing the trust boundary of the organization that was actually authenticated. At minimum this is an unauthenticated write into another organization's stack state (queuing jobs, mutating commit history tracking) that should require that organization's own webhook credential.

### Likelihood Explanation
Requires only that one org among possibly many configured under `Shipit.github` lacks a `webhook_secret` — a state the project's own setup docs and fixtures present as a normal, supported configuration for multi-org installs. No attacker credentials, GitHub App key, or session are needed; the request is a plain unauthenticated HTTP POST to the public `/webhooks` endpoint.

### Recommendation
Do not select the verifying GitHub App from unauthenticated payload fields, and do not let any org's missing `webhook_secret` short-circuit verification for the whole shared endpoint. At minimum: require `webhook_secret` for every configured org (fail closed rather than `return true unless webhook_secret`), and after signature verification, cross-check that `repository.owner.login`/`organization.login` (the field the signature was verified against) matches the org portion of `repository.full_name` (the field handlers act on) before dispatching to any handler.

### Proof of Concept
1. Configure Shipit with two orgs, `OrgA` (has `webhook_secret`) and `OrgB` (no `webhook_secret`), both tracked in the same instance — mirroring `test/dummy/config/secrets_double_github_app.yml`.
2. Send, with no signature header:
```
POST /webhooks
X-Github-Event: push
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": { "full_name": "OrgA/victim-repo", "owner": { "login": "OrgB" } }
}
```
3. `verify_signature` resolves `repository_owner` to `OrgB`, calls `Shipit.github(organization: "OrgB").verify_webhook_signature(...)`, which returns `true` immediately because `OrgB`'s `webhook_secret` is blank (`lib/shipit/github_app.rb:76-83`).
4. `PushHandler#process` resolves the target stack via `repository.full_name = "OrgA/victim-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")`, mutating `OrgA`'s stack despite the request never authenticating as `OrgA`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
