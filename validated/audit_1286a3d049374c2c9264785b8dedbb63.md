### Title
Webhook signature verified against `repository.owner.login`/`organization.login`, but the stacks acted upon are selected via unchecked `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to verify the HMAC signature against based on `repository.owner.login` (falling back to `organization.login`), but every webhook `Handler` subclass locates the `Stack`/`Repository` to mutate using the independent, unchecked field `repository.full_name`. Nothing enforces that the owner segment encoded in `full_name` matches the `owner.login`/`organization.login` used for signature verification.

### Finding Description
`verify_signature` computes the organization used to pick the correct per-org GitHub App/secret purely from attacker-supplied JSON: [1](#0-0) [2](#0-1) 

That organization is used only to look up `Shipit.github(organization: repository_owner)` and its associated `webhook_secret`, per the multi-org configuration format that Shipit explicitly supports (distinct App/secret per organization): [3](#0-2) 

Once the signature is accepted, `Shipit::Webhooks.for_event(event)` dispatches the same raw `params` hash to handlers such as `PushHandler` and `StatusHandler`. Every handler resolves the target `Repository`/`Stack` via `Handler#repository_name`, a field that is completely separate from the field used for signature verification: [4](#0-3) [5](#0-4) [6](#0-5) 

The equality this design implicitly assumes but never enforces is:
`organization used to select webhook_secret (payload['repository']['owner']['login'] / payload['organization']['login'])` == `owner segment of payload['repository']['full_name']` (the repository actually mutated by the handler).

In a Shipit instance configured to manage multiple organizations (as documented/supported by the `github: { OrgOne: {...}, OrgTwo: {...} }` credentials layout), an attacker who legitimately controls their own onboarded organization ("OrgA", with its own GitHub App and thus knows/possesses that org's `webhook_secret`, since GitHub App webhook secrets are set by whoever configures the App — typically the customer org's own admin) can POST a crafted webhook body directly to `/webhooks` with:
- `repository.owner.login` = `"OrgA"` (so `verify_signature` looks up and validates against OrgA's own known secret — a signature the attacker can legitimately compute), and
- `repository.full_name` = `"OrgB/victim-repo"` (an unrelated repository/organization tracked by the same Shipit instance that the attacker does not administer).

Because `repository_name` is never cross-checked against `repository_owner`, the forged payload is accepted and dispatched to handlers operating on `OrgB/victim-repo`'s stacks — e.g. `PushHandler#process` calling `stack.sync_github` for a chosen branch/SHA, or, more critically, `StatusHandler#process` calling `commit.create_status_from_github!(params)` to inject an arbitrary CI `state` ("success"/"failure"/"pending") for an arbitrary `sha` on the victim's stack.

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" binding described as an explicit target class. Concretely, an attacker with control of only their own tenant's GitHub App/secret can forge commit statuses on a victim repository they do not administer. Since Shipit's deploy safety logic gates deploys on required CI statuses (`deploy_spec.required_statuses`/`blocking_statuses`), injecting a spoofed passing status for an otherwise-unreviewed or failing commit can enable an unauthorized deploy to proceed on the victim's stack — a Critical-tier impact ("unauthorized deploy") per the scope's impact criteria. It can also be used to trigger spurious `sync_github` operations against unrelated stacks.

### Likelihood Explanation
This requires a Shipit deployment configured for multiple GitHub organizations sharing one instance (a supported, documented configuration per `secrets_double_github_app.yml`), where one tenant's org admin is a lower-trust/unprivileged party relative to other tenants on the same instance. In that (not uncommon for shared internal deploy tooling) setup, no victim credentials, GitHub App private key, or Shipit session/API token is required — only knowledge of the attacker's own tenant's webhook secret, which they legitimately possess as that org's App administrator.

### Recommendation
In `WebhooksController#verify_signature` (or in `Webhooks::Handlers::Handler`), enforce that the organization used to resolve/verify the webhook secret is the same organization implied by `repository.full_name` (i.e., assert `repository.full_name.split('/').first == repository_owner`, or resolve the target repository/stack first and derive the verification organization strictly from the resolved `Repository`/`Stack` record rather than from independently-controlled payload fields) before dispatching to any handler.

### Proof of Concept
1. Shipit instance configured with two organizations, `OrgA` (attacker-administered) and `OrgB` (victim), each with its own GitHub App and `webhook_secret`, per `test/dummy/config/secrets_double_github_app.yml`.
2. Attacker crafts a `status` event JSON body:
   ```json
   {
     "sha": "<victim commit sha on OrgB/victim-repo>",
     "state": "success",
     "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=<hmac>` using OrgA's known `webhook_secret` over the raw body.
4. `POST /webhooks` with header `X-Github-Event: status`. `verify_signature` looks up `Shipit.github(organization: "OrgA")` and successfully verifies the attacker-computed signature.
5. `StatusHandler#process` runs against `Commit.where(sha: params.sha)` for the commit belonging to `OrgB/victim-repo`, creating a forged "success" status that Shipit's deploy safety checks will honor for that stack.
