### Title
Whale-market RAY value overflow permanently freezes a market before the borrow-index cap engages — (File: contracts/pool/src/cache/scale.rs)

### Summary
Like CVE-2022-21341 (unauthenticated, low-complexity partial DoS), a single unprivileged account can drive a market's RAY-scaled book value past `i128::MAX`, at which point every index accrual panics. Because every verb accrues first, the market freezes permanently — no withdraw, repay, liquidate, borrow, or `clean_bad_debt`/`recapitalize` can ever execute again on that market.

### Finding Description
Accrual and utilization recompute the market's total borrowed/supplied value by unscaling RAY shares against the live index:

- `Cache::calculate_utilization` calls `scaled_to_original(borrowed, borrow_index)` and `scaled_to_original(supplied, supply_index)` ( [1](#0-0) ).
- `mul_div_*` paths panic with `GenericError::MathOverflow` when the result does not fit `i128` ( [2](#0-1) ).
- `MAX_BORROW_INDEX_RAY` exists as an index ceiling, but the overflow happens in the *value* computation (`scaled_amount × index`) before the index cap can engage, so the cap never protects it ( [3](#0-2) ).

The harness test proves the end state: after ~few years at 98% utilization on a steep curve with a whale-scale book, `update_indexes` reverts with `MATH_OVERFLOW`, and `withdraw` and `repay` revert identically because they accrue first ( [4](#0-3) ). The docs acknowledge the boundary but impose no mitigation in code: "Finite RAY value capacity can be exhausted before the index ceiling. Synchronizing an overlarge book can then fail before an otherwise risk-reducing operation" ( [5](#0-4) ).

### Impact Explanation
Permanent freezing of funds. Once `supplied × supply_index` or `borrowed × borrow_index` exceeds `i128::MAX` in RAY terms, every supply, withdrawal, repayment, liquidation, and bad-debt cleanup on that market reverts forever — accrual runs unconditionally at the head of each verb, and there is no recovery entrypoint that skips it. All supplier balances in that market are permanently locked; bad debt can never be cleaned or recapitalized there.

### Likelihood Explanation
Reachable by any single unprivileged address via `supply` + `borrow` legs only: supply a whale-scale amount of an 18-decimal asset on a steep rate curve and borrow to high utilization, then let accrual run. No privileged role, oracle manipulation, or third party is needed; the only cost is capital (the harness uses ~1e9 whole tokens) and elapsed accrual time, which is unbounded. The ceiling shortfall grows with both decimals and book size, so the condition is easiest on high-decimal markets — precisely the ones most exposed.

### Recommendation
Make `scaled_to_original`/accrual saturate rather than panic on RAY value overflow, or enforce the index cap *before* the value computation so `MAX_BORROW_INDEX_RAY` always engages first. Additionally, enforce a supply/borrow cap expressed in RAY value terms (not just token units) at listing and supply time so a book can never reach the overflow cliff regardless of decimals.

### Proof of Concept
`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs::a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (lines 321–361): supply `BILLION * 1e18` BIG18, borrow 98% against COL collateral, advance time in yearly chunks until `try_update_indexes_for(["BIG18"])` fails with `MATH_OVERFLOW`, then observe `try_withdraw_raw` and `try_repay` failing with the same error — the market is permanently frozen while `borrow_index < MAX_BORROW_INDEX_RAY`.
