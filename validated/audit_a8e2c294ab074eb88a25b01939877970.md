### Title
Cross-stack authorization bypass in `Api::CCMenuController#stack` — scoped API tokens read any stack's deploy status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`ApiClient` records can be bound to a single `stack` so that a leaked/scoped token only authorizes operations on that one stack [1](#0-0) . Every other API controller enforces this binding through `Shipit::Api::BaseController#stacks`/`#stack`, which filters the queryable stack set down to `current_api_client.stack_id` before resolving the `stack_id` param [2](#0-1) . `Api::CCMenuController`, however, overrides `#stack` to resolve the stack directly from `Stack.from_param!(params[:stack_id])`, completely bypassing that scoping [3](#0-2) .

### Finding Description
The equality that should hold is: **stack a token authorises == stack the request handler touches**, i.e. `current_api_client.stack_id` (when present) must equal the `stack_id` resolved for the request.

- `ApiClient#check_permissions!` only checks the operation/scope string (e.g. `read:stack`) against the client's `permissions` array; it never checks `stack_id` at all [4](#0-3) .
- The stack-level binding is instead enforced by the `stacks`/`stack` helpers in `BaseController`, which every "normal" API controller (`Api::StacksController`, `Api::DeploysController`, etc.) relies on via `stack.from_param!` / `stacks.from_param!` [2](#0-1) .
- `Api::CCMenuController` redefines `#stack` to call `Stack.from_param!(params[:stack_id])` on the unscoped `Stack` model class, not on the api-client-scoped `stacks` relation [5](#0-4) . It also overrides `authenticate_api_client` to authenticate via a `?token=` query param instead of HTTP Basic auth, but still calls `require_permission :read, :stack`, which only validates the *scope string*, not the stack id [6](#0-5) [7](#0-6) .

As a result, any `ApiClient` token with `read:stack` permission — even one created and intentionally scoped to a single stack (via `stack_id`, as seeded in the `here_come_the_walrus` fixture [8](#0-7) , or via `CCMenuUrlController#client`, which mints a `read:stack`-permissioned client tied to the current stack context [9](#0-8) ) — can be replayed against `GET /api/stacks/:stack_id/ccmenu` (route defined at `config/routes.rb:28` [10](#0-9) ) with an arbitrary `stack_id` and will successfully render that *other* stack's latest deploy/rollback status, entirely bypassing the stack scope the token was meant to be restricted to.

Before the attacker's request: token T is minted with `stack_id = A`, `permissions = [read:stack]`; the intended invariant is "T authorises reads only on stack A."
After the attacker's request: T is submitted with `stack_id = B` (any other stack in the instance); `authenticate_api_client` succeeds (token is valid), `require_permission!(:read, :stack)` succeeds (T has `read:stack`), and `stack` resolves to `Stack.from_param!(B)` — stack B's data is returned even though T's `stack_id` column is `A`.

### Impact Explanation
This is an unauthenticated (from stack B's perspective) read of another stack's deploy state via a token that was explicitly scoped to a different, single stack — matching the "escalation into authorization scope" / "unauthenticated read of stack state, task streams or deploy output" impact class. The CCMenu XML response exposes the latest deploy/rollback id and running/ended status for the target stack [11](#0-10) , which is information the token issuer did not intend to expose beyond the single stack it was scoped to (e.g. tokens embedded in CI-status widgets/URLs, as created by `CCMenuUrlController`).

### Likelihood Explanation
Likelihood is Medium: exploitation requires possession of a valid `ApiClient` token that is scoped to one stack (`stack_id` set) with `read:stack` permission — such tokens are routinely created/shared for CI status badges via `CCMenuUrlController#client`, and are designed to be embedded in low-trust contexts (CI dashboards, browser extensions) precisely because they are supposed to be limited to a single stack. No additional privileges beyond holding such a token are required, and the target `stack_id` is a simple owner/repo/environment path guessable/enumerable by anyone with access to the Shipit UI.

### Recommendation
Make `Api::CCMenuController#stack` use the same scoped `stacks` relation as `BaseController`, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
removing the private override entirely so it inherits `BaseController#stack`, ensuring the `current_api_client.stack_id` restriction is enforced consistently across all API endpoints.

### Proof of Concept
1. Create/seed an `ApiClient` scoped to stack A with `permissions: ['read:stack']` (as done for `here_come_the_walrus` in fixtures, or via `CCMenuUrlController#client`) and note its `authentication_token`.
2. As shown in `test/controllers/ccmenu_controller_test.rb`, the existing test suite only exercises `CCMenuUrlController#fetch` (which mints the token) and never verifies that `Api::CCMenuController#show` rejects a `stack_id` different from the token's `stack_id` [12](#0-11) .
3. Send `GET /api/stacks/<owner>/<other-repo>/<other-env>/ccmenu?token=<token>` where `<other-repo>/<other-env>` is a stack B different from the token's bound stack A.
4. `Api::BaseController#authenticate_api_client` (overridden) validates the token successfully; `require_permission :read, :stack` passes because the token has `read:stack`; `Api::CCMenuController#stack` calls `Stack.from_param!` unscoped and returns stack B's `NoDeploy`/latest deploy data in the XML response — despite the token being created/intended only for stack A.

require 'uri'
require 'test_helper'

module Shipit
  class CCMenuUrlControllerTest < ActionController::TestCase
    setup do
      @stack = shipit_stacks(:shipit)
      @user = shipit_users(:walrus)
      session[:user_id] = @user.id
    end

    test ":fetch returns ok with json" do
      get :fetch, params: { stack_id: @stack.to_param }
      assert_response :ok
      data = JSON.parse(response.body)
      assert_includes data, 'ccmenu_url'
    end

    test ":fetch creates a read only api client" do
      assert_difference 'ApiClient.count' do
        get :fetch, params: { stack_id: @stack.to_param }
      end
    end

    test ":fetch url includes api token on query string" do
      get :fetch, params: { stack_id: @stack.to_param }
      data = JSON.parse(response.body)
      client = ApiClient.last
      query = Rack::Utils.parse_nested_query(URI(data['ccmenu_url']).query)
      assert_equal client.authentication_token, query['token']
    end
  end
