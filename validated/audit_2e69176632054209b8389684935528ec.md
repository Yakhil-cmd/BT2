## Title
Missing Sender-Authorization Check in `new_shared_address` Device Message Handler Allows Spoofed Shared-Address Injection - (File: `wallet_defined_by_addresses.js`)

### Summary
The device-message handler for `new_shared_address` (`wallet.js` `case "new_shared_address"`, invoking `wallet_defined_by_addresses.handleNewSharedAddress`) accepts and permanently stores a shared-address definition and its "signers" map from **any paired correspondent device**, without ever verifying that the sending device (`from_address`) is actually one of the parties who should be defining that address. This mirrors the Casdoor SCIM bug pattern: a resource-creation endpoint performs the privileged create action while skipping the authorization check that should bind the caller's identity to the resource being created.

### Finding Description
`handleMessageFromHub` dispatches the `new_shared_address` subject directly to `handleNewSharedAddress(body, ...)`: [1](#0-0) 

`handleNewSharedAddress` only performs *self-consistency* checks on the attacker-supplied payload — that `body.definition` hashes to `body.address`, that `body.signers` addresses are syntactically valid, and that the signer map matches the address leaves extracted from the definition: [2](#0-1) 

Nowhere in this flow (nor in `determineIfIncludesMeAndRewriteDeviceAddress`) is `from_address` (the actual device that sent the message) checked against the definition/signers being submitted: [3](#0-2) 

Contrast this with the sibling handler `arbiter_contract_shared` in `wallet.js`, which explicitly binds the claimed content to the sender by requiring that one of the addresses in the payload is provably tied to `from_address` via `wallet_signing_paths`: [4](#0-3) 

`handleNewSharedAddress` has no equivalent binding check — the only real safeguard, `determineIfIncludesMeAndRewriteDeviceAddress`, merely confirms that *some* address in the payload belongs to the receiving wallet's own `my_addresses`/`shared_addresses`, not that the sender is legitimately associated with any of the peer addresses in the definition. Once accepted, the record is written unconditionally into `shared_addresses` / `shared_address_signing_paths` via `addNewSharedAddress`, and then re-broadcast to other devices believed to be cosigners of the local member addresses: [5](#0-4) [6](#0-5) 

### Impact Explanation
Any device that has paired with the victim (a low-privilege, easily obtainable relationship — pairing codes are routinely shared for payment requests) can send a `new_shared_address` message that:
- Embeds the victim's real address as one leaf of an `["or", [...]]`/`["and", [...]]` definition alongside an attacker-controlled key, while the definition's actual logic gives the attacker unilateral spending rights (e.g., `or` of attacker sig and victim address, or a nested definition crafted so the "shared" branch is unreachable in practice).
- Passes all of `handleNewSharedAddress`'s checks because they only verify hash/structural consistency, not the requester's authority to assert this relationship.
- Gets persisted as a trusted `shared_addresses` record and is even forwarded to other correspondents of the victim's member addresses via `forwardNewSharedAddressToCosignersOfMyMemberAddresses`, propagating the deception.

The victim's wallet UI will then present the injected address as a legitimate joint/multisig address it is a party to, encouraging the victim (or their contacts) to send funds to it under the belief that spending requires their cooperation, while the attacker can in fact drain it unilaterally — a concrete fund-loss / unauthorized-spending outcome reachable purely from a paired-device message with no privileged access. This fits the reachable class of "wallet and contract message handling" defined in scope.

### Likelihood Explanation
Likelihood is high for anyone who has paired with the victim device at least once (a very low bar — pairing is a normal part of ordinary wallet/contract interactions, e.g., for exchanging a payment address or arbiter contract). No additional privilege, funds, or on-chain action is required to reach `handleNewSharedAddress`; it is invoked directly from the device-message dispatcher with attacker-fully-controlled `body`.

### Recommendation
Add an explicit authorization/ownership binding to `handleNewSharedAddress`, analogous to the check already used in `arbiter_contract_shared`: require that the `device_address` claimed for each `signerInfo` that is not the local device, and specifically the definition/signers pertaining to `from_address`, is verifiable (e.g., cross-check against previously-exchanged pairing/definition data or require a signed acknowledgment from each claimed peer device) before persisting the shared address. At minimum, surface a strong, unavoidable warning to the user distinguishing "self-verified" vs. "peer-asserted, unverified" shared-address components, and require out-of-band confirmation before funds are ever sent to such an address.

### Proof of Concept
1. Attacker device `D_a` pairs with victim device `D_v` (e.g., normal correspondent pairing for a payment request).
2. Attacker crafts `arrDefinition = ["or", [["sig", {pubkey: attacker_pubkey}], ["address", victim_address]]]`, computes `address = chash160(arrDefinition)`.
3. Attacker sends device message `{subject: "new_shared_address", body: {address, definition: arrDefinition, signers: {"r.0": {address: attacker_address}, "r.1": {address: victim_address, device_address: D_v}}}}` to `D_v`.
4. `handleNewSharedAddress` verifies hash/signer consistency (all satisfied) and calls `addNewSharedAddress`, storing the address as a "shared address" in `D_v`'s wallet — `from_address` (`D_a`) is never checked against the definition content or victim's address ownership.
5. `D_v`'s wallet UI now shows this address as a shared/multisig address involving the victim; anyone depositing funds there (including the victim) can have them unilaterally withdrawn by the attacker via the `sig` branch alone.

function determineIfIncludesMeAndRewriteDeviceAddress(assocSignersByPath, handleResult){
	var assocMemberAddresses = {};
	var bHasMyDeviceAddress = false;
	for (var signing_path in assocSignersByPath){
		var signerInfo = assocSignersByPath[signing_path];
		if (signerInfo.device_address === device.getMyDeviceAddress())
			bHasMyDeviceAddress = true;
		if (signerInfo.address)
			assocMemberAddresses[signerInfo.address] = true;
	}
	var arrMemberAddresses = Object.keys(assocMemberAddresses);
	if (arrMemberAddresses.length === 0)
		return handleResult("no member addresses?");
	db.query(
		"SELECT address, 'my' AS type FROM my_addresses WHERE address IN(?) \n\
		UNION \n\
		SELECT shared_address AS address, 'shared' AS type FROM shared_addresses WHERE shared_address IN(?)", 
		[arrMemberAddresses, arrMemberAddresses],
		function(rows){
		//	handleResult(rows.length === arrMyMemberAddresses.length ? null : "Some of my member addresses not found");
			if (rows.length === 0)
				return handleResult("I am not a member of this shared address");
			var arrMyMemberAddresses = rows.filter(function(row){ return (row.type === 'my'); }).map(function(row){ return row.address; });
			// rewrite device address for my addresses
			if (!bHasMyDeviceAddress){
				for (var signing_path in assocSignersByPath){
					var signerInfo = assocSignersByPath[signing_path];
					if (signerInfo.address && arrMyMemberAddresses.indexOf(signerInfo.address) >= 0)
						signerInfo.device_address = device.getMyDeviceAddress();
				}
			}
			handleResult();
		}
	);
}
