### Title
Webhook signature is verified against the organization named in the payload while write handlers (e.g. `StatusHandler`) act on data scoped by a different, attacker‑controlled field, enabling cross‑repository status forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp`/`webhook_secret` to use for HMAC verification based on `repository.owner.login` (or `organization.login`) taken from the untrusted JSON body itself, not from any fixed, per-endpoint configuration. Once the signature check passes, downstream handlers such as `StatusHandler` use *other* attacker-controlled fields from the same body (`sha`) to decide *what* to write, with no re-check that the authenticating organization matches the object being mutated. This breaks the binding "organization that authenticated == repository/commit that is written."

### Finding Description
`WebhooksController#verify_signature` picks the GitHub app config purely from a field inside the unverified payload: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` resolves a distinct `GitHubApp` (and thus a distinct `webhook_secret`) per organization when the engine is configured in multi-organization mode: [3](#0-2) 

The HMAC is computed over the entire raw body using whatever secret corresponds to `repository_owner`: [4](#0-3) 

So an attacker who legitimately possesses the `webhook_secret` for **one** organization (`org-A`) hosted on this Shipit instance — e.g. because they administer `org-A`'s GitHub App/webhook settings, a routine, unprivileged capability for that org's own maintainers — can craft an arbitrary JSON body, set `repository.owner.login` (or `organization.login`) to `org-A` so `verify_signature` selects `org-A`'s secret, and sign the body with that secret. Nothing ties the rest of the payload's content to `org-A`.

`StatusHandler` then processes the `status` event using only `sha` from that same body, with **no scoping to a repository at all**: [5](#0-4) 

`Commit.where(sha: params.sha)` is a global lookup across every stack/repository/organization tracked by the Shipit instance, not scoped by `repository_owner` or `full_name`. Compare this with other handlers (`PushHandler`, `PullRequest::*Handler`) which at least resolve the acting `Repository` via `payload.dig('repository','full_name')`: [6](#0-5) 

`StatusHandler` has no such requirement in its `params` block and never consults `repository` at all, so the commit whose status gets overwritten can belong to any organization in the instance — including one the attacker has no relationship with and whose webhook secret they never possessed.

The values written (`state`, `description`, `target_url`, `context`, `created_at`) are taken verbatim from the forged payload and persisted as a real commit status via `Commit#create_status_from_github!`, exactly as if GitHub itself had reported it — Shipit does not re-fetch/verify the status against the GitHub API.

This is the analog of the report's "missing validation lets a caller substitute an unintended value" bug class: here the unvalidated/unbound value is the *organization identity used for authentication* versus the *repository/commit actually mutated*, i.e. `authenticating_org != commit.stack.repository.owner`.

### Impact Explanation
This is a cross-repository write: an actor authorized only for `org-A`'s webhook secret can inject arbitrary CI/commit status records (`state: success`, arbitrary `context`/`description`/`target_url`) onto commits belonging to any other organization's stacks tracked by the same Shipit deployment. Since Shipit stacks commonly gate deploys/merges on required commit statuses being green, this can be used to forge a passing CI/status check on a commit in a repository the attacker does not control, contributing to an unauthorized deploy path. Even independent of downstream deploy-gating logic, forging status data cross-organization is itself an unauthorized cross-repository write to Shipit's persisted state.

### Likelihood Explanation
Requires the attacker to control a legitimate GitHub App/webhook configuration for at least one organization already onboarded to the shared Shipit instance (a normal, unprivileged position for that org's own administrators, not a privileged Shipit account or `ApiClient` token). No Shipit session or repository write access to the *target* organization is needed — only knowledge of the target's commit SHA (public, discoverable information) and the ability to send an HTTP POST to `/github/webhooks`.

### Recommendation
- In `WebhooksController#verify_signature`, after verifying the HMAC, cross-check that the resolved `repository_owner`/`organization` actually matches the organization owning the repository named in `params.dig('repository','full_name')` before dispatching to handlers, or bind webhook secrets 1:1 to specific `Repository` records rather than to organizations parsed from the payload.
- Add a `requires :repository { requires :full_name, String }` clause to `StatusHandler#params`, and scope the `Commit` lookup through `Repository.from_github_repo_name(params.repository.full_name)` (as `PushHandler`/pull-request handlers already do), rather than a global `Commit.where(sha:)` lookup.

### Proof of Concept
1. Attacker is a maintainer of `org-A`, which is configured in this Shipit instance with its own GitHub App and `webhook_secret_A` (multi-org `secrets.github` config, see `lib/shipit.rb#github_app_config`).
2. Attacker crafts a `status` webhook payload:
```json
{
  "repository": {"owner": {"login": "org-A"}, "full_name": "org-A/some-repo"},
  "sha": "<sha-of-a-commit-in-org-B's-stack>",
  "state": "success",
  "context": "ci/required-check",
  "description": "forged",
  "target_url": "https://example.com"
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(webhook_secret_A, body)` and POSTs to `/github/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "org-A")`, verifies successfully against `webhook_secret_A`.
5. `StatusHandler#process` executes `Commit.where(sha: params.sha)` — matching the commit in `org-B`'s stack — and calls `create_status_from_github!`, writing a forged "success" status on `org-B`'s commit, even though the attacker never had `org-B`'s webhook secret or any access to `org-B`'s repository.

```ruby
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)

    @github[organization] ||= GitHubApp.new(organization, config)
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
