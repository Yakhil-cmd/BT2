### Title
Cross-repository CI status injection via `status` webhook — the authenticated organization is never checked against the repository whose commit is written - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates an incoming webhook only against the GitHub App belonging to the organization named in the payload's `repository.owner.login`/`organization.login` field. [1](#0-0)  That authenticated organization identity is never re-checked against the actual repository whose data gets mutated once the payload is dispatched to a handler. `StatusHandler#process` looks up commits **globally by `sha` alone**, with no scoping to the repository or organization that was authenticated: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`. [2](#0-1)  Every other handler scopes writes through `stacks`, which is derived from `Repository.from_github_repo_name(repository_name)` — i.e., the same repository whose owner was verified. [3](#0-2)  `StatusHandler` breaks that binding.

### Finding Description
The equality that should hold is: **organization authenticated == repository/stack written to**. Every handler except `StatusHandler` enforces this by scoping mutations through `stacks`/`Repository.from_github_repo_name(repository_name)`, where `repository_name` comes from the same `repository.full_name` field used (indirectly, via `owner.login`) to select the GitHub App/webhook secret used in signature verification. [3](#0-2) [4](#0-3) 

`StatusHandler`, however, ignores `repository`/`stacks` entirely and resolves the target purely from the attacker-controlled `sha` field, matching against the global `Commit` table across all stacks/repositories/organizations: [5](#0-4) 

Because Shipit supports multiple GitHub Apps/organizations sharing one installation (each with its own `webhook_secret`), an attacker who legitimately controls (or compromises) a repository/organization that is *also* onboarded onto the same Shipit instance can send a validly-signed `status` event for their own repository, but set `sha` to the commit hash of a commit that actually belongs to a *different* onboarded repository/stack. GitHub commit SHAs are public information (visible via the GitHub API, git log, or the target repo's Shipit deploy history UI), so obtaining a target SHA requires no privileged access. `verify_signature` only checks the signature against the attacker's own organization's app, which succeeds because the attacker legitimately owns that org/app; nothing thereafter checks that the `sha` being written actually belongs to a commit under that same organization.

### Impact Explanation
`create_status_from_github!` creates a `Status` record on the matched commit for the context named in the forged payload. [6](#0-5)  Commit statuses directly gate `Commit#deployable?` (`!locked? && (stack.ignore_ci? || (success? && !blocked?))`), which in turn gates continuous deployment / merge-queue eligibility and the deploy dashboard's "safe to deploy" state. [7](#0-6)  An attacker who controls one org onboarded to the shared Shipit instance can therefore forge a `success` status (satisfying required CI checks) for a target commit belonging to an unrelated, victim-owned repository/stack, making that commit `deployable?` and eligible to be auto-deployed by continuous delivery or merged by the merge queue — without ever having write access, a Shipit session, or an API token for the victim repository. This crosses the "unauthorized deploy" / cross-repository-write bar (High/Critical impact bucket).

### Likelihood Explanation
Requires only: (1) the attacker's own organization/app onboarded on the same Shipit instance (a realistic multi-tenant deployment as documented in `docs/setup.md`'s "Using Multiple Github Applications" section — this is the intended supported configuration, not a misconfiguration) [8](#0-7) ; (2) knowledge of a target commit SHA, which is public; (3) the ability to trigger a real, validly-signed `status` webhook from the attacker's own GitHub org (trivially done by setting a commit status via the GitHub API on any repo they control, since GitHub forwards that event with attacker-supplied `sha`, `state`, `context`, `description`, `target_url` fields verbatim). No social engineering, session, or victim-side credential is needed.

### Recommendation
Scope `StatusHandler#process` (and any other global-table lookups) by the authenticated repository, e.g. restrict the `Commit.where(sha: params.sha)` query to `stacks` (as `Handler#stacks` already does for other handlers), so a status event can only ever mutate commits belonging to the repository that was actually authenticated via `verify_signature`.

### Proof of Concept
1. Shipit instance is configured with two organizations, `victim-org` and `attacker-org`, each with its own GitHub App/webhook secret (multi-org setup per `docs/setup.md`).
2. Attacker discovers the SHA of a pending commit in `victim-org/victim-repo` that is tracked by a Shipit stack (public info, e.g. from the Shipit UI or GitHub).
3. Attacker (owner of `attacker-org`) sets a commit status via the GitHub API on any commit in a repo they own within `attacker-org`, but crafts/forwards (e.g. via a proxy or by controlling the receiving webhook relay, or simply because GitHub apps can be configured to fire on arbitrary repos they administer) a `status` webhook payload where `sha` = victim commit's SHA, `state` = `success`, `context` matches a `required_statuses` context configured for the victim stack.
4. `WebhooksController#verify_signature` validates the signature using `Shipit.github(organization: 'attacker-org')` — succeeds, since attacker legitimately owns that org's webhook secret. [9](#0-8) 
5. `StatusHandler#process` runs `Commit.where(sha: <victim sha>)`, finds the victim's commit (no org/repo check), and creates a `success` `Status` on it. [2](#0-1) 
6. The victim commit now satisfies `required_statuses`/CI checks and becomes `deployable?`, potentially triggering continuous deployment or merge-queue merge for `victim-org/victim-repo` — a deploy/merge the attacker never had authorization to trigger.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
    end
  end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml
production:
  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
```
