### Title
Unfiltered PR label injection into review-stack deploy/task environment enables `GIT_CONFIG_COUNT`-based RCE - (File: app/models/shipit/review_stack.rb)

### Summary
`ReviewStack#env` merges every pull request label name (uppercased) as an environment variable key, with a fixed value `"true"`, with no allowlist. This merged hash flows unfiltered through `TaskCommands#env` and `Command#unbundled_env` into `PTY.spawn`, so an attacker who names a PR label `GIT_CONFIG_COUNT` (or `GIT_CONFIG_KEY_0`/`GIT_CONFIG_VALUE_0`) can attempt to inject arbitrary environment variables into every `git`/task command executed for that review stack.

### Finding Description
The broken binding: `Stack#env` (and by extension every step's process environment) should only ever contain trusted, operator-defined keys as validated by `EnvironmentVariables#permit(deploy_variables/rollback_variables/...)`. Instead, `ReviewStack#env` breaks this by directly merging attacker-controlled label names as env keys with no allowlist check:

```ruby
def env
  return super unless pull_request.present?
  super.merge(pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" })
end
``` [2](#0-1) 

`TaskCommands#env` merges `@stack.env` straight in (no `filter_*_envs`/`EnvironmentVariables.permit` call anywhere in this chain): [1](#0-0) 

`Command#unbundled_env` merges `@env` (stringified) on top of `BASE_ENV`+`PATH`, and `Command#start` passes this directly to `PTY.spawn`: [5](#0-4) 

The `filter_deploy_envs`/`filter_rollback_envs`/`EnvironmentVariables#permit` allowlist mechanism exists [6](#0-5)  but is only applied to the user-supplied `env:` argument at deploy/task-trigger time (`Stack#build_deploy`, `Stack#trigger_task`) [7](#0-6) , not to `Stack#env`/`ReviewStack#env`, which is merged unconditionally by `TaskCommands#env`. So the label-derived keys bypass the allowlist entirely.

Given `allow_with_label` provisioning behavior, an unprivileged fork contributor can open a PR against the base repo, have the review stack auto-provisioned (label-gated), and add a label literally named `GIT_CONFIG_COUNT` (and, if multiple custom labels are permitted/settable by the PR author or a low-trust collaborator, also `GIT_CONFIG_KEY_0`/`GIT_CONFIG_VALUE_0`). `git` itself recognizes `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_n`/`GIT_CONFIG_VALUE_n` and will honor arbitrary config keys such as `core.fsmonitor`, `core.hooksPath`, or `alias.*`, which git executes as external commands during subsequent git invocations run by `TaskCommands#checkout`/`#clone` or any `tasks.<name>.steps` step that shells out to git.

**Caveat on exploitability of label names/values.** Whether an attacker who is *not already a repository collaborator* can set arbitrary label names on their own PR against another org's repo depends on GitHub permissions (only users with `triage`+ access can typically apply/create labels on someone else's repo), which is a GitHub-side permission, not enforced by this engine. GitHub label *names* also cannot contain arbitrary characters freely, but `GIT_CONFIG_COUNT`, `GIT_CONFIG_KEY_0`, `GIT_CONFIG_VALUE_0` are valid label text. However, the underlying application-side flaw — `ReviewStack#env` merging fully attacker-influenced label strings into the process environment with zero allowlisting — is real and independent of that GitHub-permission question, and it directly violates the stated invariant that no fork-controllable key should reach `Command#unbundled_env`.

### Impact Explanation
If exploitable end-to-end (i.e., the PR author or a sufficiently-privileged collaborator can attach a label with one of these exact names to a PR/fork whose review stack is provisioned under `allow_with_label`), the label values are merged into the environment of every git command shelled out during clone/checkout/deploy/task steps for that review stack. Setting `GIT_CONFIG_COUNT=0` doesn't help the attacker alone, but if a matching `GIT_CONFIG_KEY_0=core.fsmonitor`/`GIT_CONFIG_VALUE_0=<command>` pair reaches the environment, `git` will execute the configured command as a subprocess of the Shipit deploy host during any subsequent git operation — Remote Code Execution on the deploy host, scoped to that repository's review stack but running with the deploy host's ambient privileges (potentially exposing `GITHUB_TOKEN`/deploy secrets available to that process).

### Likelihood Explanation
Preconditions: the target repository must be configured with `provisioning_behavior=allow_with_label` [2](#0-1) , a review stack must exist/be provisioned for the fork PR, and the attacker (or a collaborator acting on their behalf) must be able to attach the specific label name(s) `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_0`/`GIT_CONFIG_VALUE_0` to that PR — this label-setting capability is gated by GitHub's own repository permissions, not by anything in this engine, which reduces the likelihood for a genuinely unprivileged external attacker but the application-level lack of allowlisting is unconditional.

### Recommendation
Apply `EnvironmentVariables.permit` (or an explicit, fixed allowlist of safe uppercased-boolean-flag keys) to the labels hash in `ReviewStack#env` before merging it into the stack environment, and/or blocklist environment variable names beginning with `GIT_`, `BUNDLE_`, `RUBYOPT`, `LD_PRELOAD`, etc. Additionally, `Command#start`/`unbundled_env` should strip or reject any `GIT_CONFIG_*` / other git-behavior-altering variables that did not originate from Shipit's own trusted config layers.

    def start(&block)
      return if @started

      @control_block = block
      @out = @pid = nil
      FileUtils.mkdir_p(@chdir)
      begin
        @out, child_in, @pid = PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)
        child_in.close
      rescue Errno::ENOENT
        raise NotFound, "#{Shellwords.split(interpolated_arguments.first).first}: command not found"
      rescue Errno::EACCES
        raise Denied, "#{Shellwords.split(interpolated_arguments.first).first}: Permission denied"
      end
      @started = true
      self
    end

    def unbundled_env

    end
