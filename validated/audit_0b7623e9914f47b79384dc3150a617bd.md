### Title
Gas-key nonce replay via delete-then-recreate within the same block height resets nonce floor to an already-consumed value - ([File: runtime/runtime/src/access_keys.rs])

### Summary
`add_gas_key` (and `add_regular_key`) initializes every nonce slot for a (re)created access key purely from `initial_nonce_value(block_height)`, with no memory of any nonce value that was ever consumed under that `(account_id, public_key)` pair before it was deleted. Because `apply_state.block_height` is fixed for the whole chunk/receipt application, an attacker who deletes and immediately re-adds the same gas-key public key inside the same block gets the exact same nonce floor as before, allowing a previously-signed, already-executed transaction bound to a specific `(public_key, nonce_index, nonce)` to pass the nonce check again.

### Finding Description
`add_gas_key` sets every nonce index to `initial_nonce_value(block_height) = (block_height - 1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER` [1](#0-0)  and this is the only place gas-key nonces get initialized. `action_add_key` only rejects an `AddKeyAction` if a key with the same `public_key` currently exists in state [2](#0-1) ; it performs no check against the account/public-key's *historical* highest-ever-used nonce. `delete_gas_key` fully removes all `num_nonces` stored nonce entries via `remove_gas_key_nonce` [3](#0-2) , wiping any trace that a higher nonce was previously consumed for that key.

`initial_nonce_value` is keyed solely on `block_height`, which is fixed for the entire chunk application (`apply_state.block_height`) [4](#0-3) , so a `DeleteKeyAction` followed by an `AddKeyAction` for the same `public_key` inside the same block (e.g., two actions of one transaction, or receipts landing in the same chunk) produces an identical `initial_nonce_value` to the one used when the key was first created at that height. If a signed transaction `TX1` at `(public_key, index i, nonce N1)` was already accepted once (requiring `N1 > initial_nonce_value(H)` at the time), then after delete+recreate at the same height `H`, the nonce floor for index `i` is reset back to the same `initial_nonce_value(H)`, and `N1` again satisfies the "greater than stored nonce" check used by the runtime's transaction/nonce verification — resurrecting an already-consumed `(public_key, index, nonce)` tuple.

The existing `get_access_key(...).is_some()` guard in `action_add_key` only prevents adding a key while it currently exists; it does nothing once the key has been deleted, and there is no persisted "maximum nonce ever seen" record independent of the access-key/gas-key-nonce trie entries that get wiped on delete.

### Impact Explanation
This breaks the strictly-increasing-nonce invariant that NEAR's protocol nonce mechanism is supposed to guarantee, which is the sole replay-protection primitive for transactions/meta-transactions signed under a given `(account_id, public_key, nonce_index)`. Gas keys are explicitly designed for relayer/session-key patterns where a signed transaction is trusted to execute at most once (e.g., signed payment authorizations, relayed meta-transactions). An account owner able to delete and recreate their own gas key within one block can cause a previously-executed signed transaction to be re-validated and re-applied, corresponding to the "authorization bypass / replay" impact class.

### Likelihood Explanation
Preconditions: the attacker must control the account performing `DeleteKeyAction` immediately followed by `AddKeyAction` for the same `public_key`, and this delete+add must land in the same block/chunk application (same `apply_state.block_height`) as when the key/nonce range was first established, so that `initial_nonce_value` is identical. This is achievable by an ordinary account holder using only standard `DeleteKey`/`AddKey` actions, without any validator or node-operator privilege, but it requires precise sequencing (delete and re-add happening at the same block height as the original key creation/usage window), which constrains — but does not eliminate — practical exploitation. `delete_gas_key` also requires the gas key's remaining balance be at or below `GasKeyInfo::MAX_BALANCE_TO_BURN` [5](#0-4) , which is an additional constraint but not a blocker for an attacker willing to burn a small remaining balance.

### Recommendation
Do not derive the nonce floor purely from `block_height` on every add; persist a monotonically non-decreasing "last used nonce" per `(account_id, public_key)` (or per index) that survives key deletion, or refuse to reuse a `public_key` for `AddKeyAction` within some minimum number of blocks after it was deleted, or store a tombstone recording the highest nonce ever consumed for a given `public_key` on that account so a newly (re)created key inherits a floor at least as high as any prior maximum, regardless of `block_height`.

### Proof of Concept
Integration test outline (extends `test-loop-tests/src/tests/gas_keys.rs` / `runtime/runtime/src/access_keys.rs` test module):
1. At block height `H`, submit `AddKeyAction` creating gas key `pk` with `num_nonces >= 1`; nonce index `i` initializes to `initial_nonce_value(H)`.
2. Submit and successfully apply a transaction `TX1` signed with `pk`, `nonce_index = i`, `nonce = N1` where `N1 > initial_nonce_value(H)`; assert stored nonce for `(account, pk, i)` becomes `>= N1`.
3. In the same block height `H` (e.g., a second transaction in the same chunk, or a batch of actions `[DeleteKeyAction{pk}, AddKeyAction{pk, same gas_key_info}]` inside one transaction), delete then re-add `pk`.
4. Assert via `get_gas_key_nonce` that the nonce for `(account, pk, i)` is reset to `initial_nonce_value(H)` (same value as step 1).
5. Resubmit `TX1` (identical signed bytes) and assert the runtime currently *accepts* it (demonstrating the bug) instead of rejecting it with `InvalidNonce`/`AddKeyAlreadyExists`-style protection — the fix should make this assertion flip to rejection.

Uncertainty: I could not fully retrieve the exact nonce-comparison/acceptance code path in `runtime/runtime/src/verifier.rs` (grep results were truncated before inspection completed) to confirm the precise "nonce must be strictly greater than stored value" semantics and whether any additional cross-check exists there; this analysis relies on the documented NEAR nonce model and the confirmed reset behavior in `access_keys.rs`. Verifying `verifier.rs`'s nonce-check function directly is recommended before treating this as fully confirmed.

pub(crate) fn initial_nonce_value(block_height: BlockHeight) -> Nonce {
    // Set default nonce for newly created access key to avoid transaction hash collision.
    // See <https://github.com/near/nearcore/issues/3779>.
    (block_height - 1) * near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER
}
