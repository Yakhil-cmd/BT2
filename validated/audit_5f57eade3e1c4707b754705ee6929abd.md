### Title
Unfiltered pull-request label injects a `PATH` environment variable, overriding the deploy host's PATH resolution during task/deploy commands - (File: app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb)

### Summary
`LabelCapturingHandler#capture_labels` persists GitHub label names verbatim onto `Shipit::PullRequest#labels` with no allow-list. `ReviewStack#env` turns every label into an env-var key (`upcase => "true"`) and `TaskCommands#env` merges `@stack.env` directly into the final process environment without ever routing it through `EnvironmentVariables#permit`/`deploy_spec.machine_env` whitelisting. Because `Command#unbundled_env` lets `@env`'s keys override the computed `PATH`, an attacker-controlled label named `PATH` fully overwrites the `PATH` seen by `PTY.spawn`.

### Finding Description
The broken binding: the question assumes `Command#unbundled_env`'s key set must equal only whitelisted variables from `deploy_spec.machine_env`/`VariableDefinition`. In fact `TaskCommands#env` merges `@stack.env` raw: [1](#0-0) 

`@stack.env` (via `ReviewStack#env`) turns each persisted label into an env key set to the fixed value `"true"`: [2](#0-1) 

Only `@task.env` (the very last merge) is filtered through `EnvironmentVariables#permit`/`filter_envs`/`filter_deploy_envs`; `@stack.env` is never filtered. This is confirmed by existing tests asserting arbitrary label names like `WIP`/`BUG` become environment keys unfiltered: [3](#0-2) 

Labels reach `PullRequest#labels` unfiltered from the webhook payload: [4](#0-3) 

`Command#unbundled_env` builds `PATH` and then lets `@env` override it wholesale: [5](#0-4) 

`@env` is subsequently passed straight to `PTY.spawn`: [6](#0-5) 

Attacker request: an unprivileged GitHub user opens a PR against a repository with ReviewStacks enabled, adds a label literally named `PATH` (GitHub `labeled` webhook, `pull_request.labels: [{name:"PATH"}]`), and commits a relative-path executable (e.g. `true/bundle`, `true/git`) into their own branch. When the review stack next runs task/deploy commands, `unbundled_env['PATH']` becomes the literal string `"true"` — a single, cwd-relative PATH entry (not the built system PATH). Since `Command#start` runs `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` with `chdir` set to the task's checked-out working directory (the attacker's own branch content), any unqualified command name (`git`, `bundle`, `cap`, etc.) invoked by deploy/task steps will be resolved by searching the relative directory `true` under that working directory first — i.e., the attacker's own committed file — leading to arbitrary code execution on the deploy host.

None of the existing guards stop this: `LabeledHandler`/`UnlabeledHandler` only gate archive/provision status on specific labels configured by the repo owner, not general label capture; `LabelCapturingHandler` has no name restriction on labels (`requires :name, String`); `EnvironmentVariables#permit` is applied only to `@task.env`, never to `@stack.env`; `deploy_spec.machine_env` is repo-owner controlled and irrelevant here since the vulnerable value flows from `@stack.env`, merged before `machine_env`.

### Impact Explanation
This is Critical: RCE on the deploy host via `Command`/`PTY.spawn`. The blast radius is scoped to the ReviewStack for the affected repository/PR (the checked-out working directory the attacker controls), but it lets an unprivileged PR author execute arbitrary code in the context of the Shipit deploy worker process for that stack — the same process that holds `GITHUB_TOKEN` and other deploy secrets (`Shipit::Commands#base_env` injects `GITHUB_TOKEN`), so exfiltration of those secrets and lateral movement to other stacks/hosts sharing the worker are realistic follow-on impacts. It is repeatable: the attacker can relabel/unlabel/relabel to re-trigger `capture_labels` on demand and can retarget any repository they can open a labeled PR against, provided ReviewStacks are enabled for it.

### Likelihood Explanation
Preconditions: the target repository must have `review_stacks_enabled` and a provisioning behavior that creates a ReviewStack for the attacker's own PR (e.g. `allow_all`, or `allow_with_label`/`prevent_with_label` satisfied by labels the attacker also controls) — this is standard, commonly-enabled Shipit review-app functionality, not a special/insecure configuration. The attacker only needs: ability to open a PR from their own fork/branch, ability to add a label named `PATH`, and ability to commit a relative-path executable file into their own branch — all actions available to any unprivileged GitHub user with write access to their own fork. No Shipit credentials, webhook secret, or GitHub App key are required.

### Recommendation
- In `ReviewStack#env` (or before persisting), reject/skip label names that collide with reserved/security-sensitive environment variable names (`PATH`, `LD_PRELOAD`, `LD_LIBRARY_PATH`, `IFS`, `BUNDLE_GEMFILE`, `RUBYOPT`, etc.), or better, namespace label-derived variables (e.g. prefix with `LABEL_`) so they can never collide with system variables.
- Route `@stack.env` through the same `EnvironmentVariables#permit` whitelist mechanism used for `@task.env`, or explicitly filter out reserved keys before merging into `TaskCommands#env`.
- In `Command#unbundled_env`, compute `PATH` last and refuse to let `@env` fully replace it — at minimum, always prepend `Shipit.shell_paths`/`ENV['PATH']` and ignore/log any attempt from `@env` to set `PATH` directly, or explicitly strip `PATH` (and other security-sensitive keys) from `@env` before merging.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_test.rb
test "#env allows a 'PATH' label to override the process PATH" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["PATH"]
  assert_equal "true", stack.env["PATH"]
end

# test/unit/command_test.rb
test "#unbundled_env lets @env's PATH override the built PATH" do
  command = Command.new("true", env: { "PATH" => "true" }, chdir: ".")
  assert_equal "true", command.unbundled_env["PATH"]
  refute_includes command.unbundled_env["PATH"], Shipit.shell_paths.join(":")
end

# test/lib/shipit/task_commands_test.rb
test "#env propagates an unfiltered PATH label into the process env" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["PATH"]
  task = shipit_tasks(:shipit_restart)
  task.stack = stack

  env = Shipit::TaskCommands.new(task).env

  assert_equal "true", env["PATH"]
end
```
These assert both sides of the claimed binding directly: `ReviewStack#env['PATH']` is attacker-settable to `"true"`, and `Command#unbundled_env['PATH']` is overridden by `@env['PATH']` rather than remaining restricted to `Shipit.shell_paths`/`ENV['PATH']`, confirming the divergence the question describes.
