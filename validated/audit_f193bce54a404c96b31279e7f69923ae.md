### Title
Stack-scoped `ApiClient` CCMenu token permits reading build status of arbitrary stacks - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` checks only that an `ApiClient` token carries the generic `read:stack` permission, but resolves the target `Stack` directly from the request parameter instead of through the client's stack-scoping, so a token that was minted for one stack can be replayed against any other stack ID.

### Finding Description
`ApiClient` supports being scoped to a single stack via `belongs_to :stack, optional: true` and the `stack_id` column [1](#0-0) . This scoping is the mechanism the app relies on elsewhere: `Api::BaseController#stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` whenever the client is stack-scoped [2](#0-1) .

`CCMenuUrlController` is the code path that actually creates these scoped tokens for the public CCMenu XML feed: it builds an `ApiClient` with only the `read:stack` permission, generates a signed `authentication_token` from it, and embeds it, together with the specific `stack_id`, in a URL [3](#0-2) . Nothing in the `ApiClient`/token itself binds the token cryptographically to that `stack_id` — the token only encodes the `ApiClient` row id [4](#0-3) , and permission enforcement is purely string-based (`operation:scope`, e.g. `"read:stack"`) with no stack argument [5](#0-4) .

`Api::CCMenuController` overrides `stack` to bypass the scoped `stacks` helper entirely and resolve straight from the raw `params[:stack_id]`:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [6](#0-5) 
while its only authorization gate is the generic permission check `require_permission :read, :stack` [7](#0-6) , which never inspects whether `current_api_client.stack_id` equals the requested `params[:stack_id]`.

This mirrors the reported bug class: the equality that should hold is `stack the token authorizes == stack the request touches`. Before the flow completes, the app checks a coarse binding (does this token have `read:stack` permission at all) but never checks the fine-grained one (is *this* stack the one the token is scoped to) — exactly as `_isProposerPermitted` checked `msg.sender == proposer` but failed to also validate `msg.sender == proposerOne` for the specific first-block case, letting an authorized-but-differently-scoped actor slip through (or, here, letting a differently-scoped-but-still-"authorized" caller access an unintended object).

### Impact Explanation
Any holder of a CCMenu token minted for stack A (these tokens are designed to be embedded in plain URLs meant for CI dashboard tools, and thus are exposed via browser history, referrer headers, logs, or shared dashboards) can substitute an arbitrary `stack_id` in the request and read the CCMenu XML — including `lastBuildStatus`, `lastBuildLabel`, deploy activity, and lock status — for any other stack in the Shipit instance, even ones that the token was never authorized against and that the token holder may have no other access to. This is an unauthenticated (relative to that stack) read of stack state and deploy output, matching the report's "High" impact bucket.

### Likelihood Explanation
Any party who has ever legitimately received one CCMenu URL (a `read:stack`-scoped `ApiClient` token) can immediately enumerate/read the state of every other stack simply by changing the `stack_id` query parameter — no cryptographic break, no privileged account, and no additional secret is required beyond possessing one such token, which by design is distributed outside of authenticated sessions.

### Recommendation
In `Api::CCMenuController#stack` (and any other controller that overrides the scoped `stacks` helper), resolve the stack through `stacks.from_param!(params[:stack_id])` instead of `Stack.from_param!(params[:stack_id])`, so that a stack-scoped `ApiClient` can only ever resolve its own bound stack, consistent with `Api::BaseController#stacks`.

### Proof of Concept
1. Operator calls `CCMenuUrlController#fetch` for Stack A, receiving a URL such as `.../api/stacks/A/ccmenu.xml?token=<signed-id-of-scoped-client>`.
2. Attacker who obtains this URL (e.g., via referrer leakage, shared CI dashboard config, or logs) changes the path/param to target Stack B: `.../api/stacks/B/ccmenu.xml?token=<same-token>`.
3. `CCMenuController#authenticate_api_client` successfully authenticates the token (it only decodes the `ApiClient` id) [8](#0-7) .
4. `require_permission :read, :stack` passes because the client's `permissions` array contains `read:stack`, regardless of which stack is requested [7](#0-6) .
5. `stack` resolves to Stack B via `Stack.from_param!`, and the controller renders Stack B's CCMenu XML (build status, last deploy, lock state) to the attacker [9](#0-8) .
