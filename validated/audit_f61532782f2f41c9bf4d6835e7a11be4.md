### Title
Cross-stack token scope confusion in CCMenuUrlController/CCMenuController - unscoped `ApiClient` grants read access to every stack ([File: app/controllers/shipit/ccmenu_url_controller.rb], [File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::CCMenuUrlController#fetch` mints a signed `ApiClient` token intended to scope CCMenu XML access to a single stack, but the `ApiClient` record is created with `stack_id` left `nil` and the token is a bare signed client id with no embedded stack binding. `Shipit::Api::CCMenuController` compounds this by overriding the base `stack` resolution method so that it looks up `params[:stack_id]` directly instead of scoping through `current_api_client.stack_id`, meaning even a stack-bound client would not be enforced. The result: a token obtained for one stack works against any stack.

### Finding Description
The intended binding is:
`token.stack_id == stack.id` (the stack named in the `cc_menu_url` path that the token is "for").

Tracing the code:
- `app/controllers/shipit/ccmenu_url_controller.rb:15-18`: `client` is `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')` — no `stack:` attribute is set, so `ApiClient#stack_id` is `nil` (`belongs_to :stack, optional: true`, `app/models/shipit/api_client.rb:8`).
- `app/controllers/shipit/ccmenu_url_controller.rb:8-9`: the URL is built for `stack.to_param` (the specific stack the user requested), but the query token is `client.authentication_token`, which is just `message_verifier.generate(id)` (`app/models/shipit/api_client.rb:34-36`) — a signature over the client's row id only, carrying no stack scoping information.
- `app/controllers/shipit/api/ccmenu_controller.rb:33-36`: `authenticate_api_client` is overridden to accept any `ApiClient` for which `ApiClient.authenticate(params[:token])` succeeds — this only verifies the signature and permission set, not any stack relationship.
- `app/controllers/shipit/api/ccmenu_controller.rb:29-31`: `stack` is overridden to `Stack.from_param!(params[:stack_id])`, bypassing `Api::BaseController#stack`/`#stacks` (`app/controllers/shipit/api/base_controller.rb:74-80`), which is the only place that would have scoped lookups via `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`.
- `require_permission :read, :stack` only calls `current_api_client.check_permissions!('read', 'stack')` (`app/controllers/shipit/api/base_controller.rb:82-84`), which checks the client's `permissions` array (`%w[read:stack]`), never the client's `stack_id` against the requested `stack_id`.

So after tracing: `token.stack_id` is `nil` (both because the row was created without one, and because even a bound client's `stack_id` is never consulted by `CCMenuController#stack`). The equality `token.stack_id == stack.id` never holds in the code's actual behavior — the token effectively authorizes `Stack.all` for `read:stack`, not just the originating stack. No existing guard (`require_permission!`, `authenticate_api_client`, `stacks` scoping) closes this gap because `CCMenuController` locally reimplements both authentication and stack resolution in a way that drops the stack scoping present in the base controller.

Attacker flow: a logged-in user (any user Shipit's front end authenticates, e.g. via GitHub OAuth to the configured org per the README) with UI access to at least one stack visits `GET /stacks/:owner/:repo/:env/cc_menu_url` for their own stack, receives `{ ccmenu_url: ".../api/stacks/:owner/:repo/:env/cc_menu.xml?token=..." }`, and then replays that `token` against `GET /api/stacks/:other_owner/:other_repo/:other_env/cc_menu.xml` for any other stack. Since the token only proves "some `ApiClient` with `read:stack` permission", and `CCMenuController` never checks stack identity, the request succeeds and returns that other stack's latest deploy/rollback status (`app/controllers/shipit/api/ccmenu_controller.rb:22-25`).

### Impact Explanation
An attacker with legitimate but limited access to a single, possibly low-sensitivity stack can obtain a token that discloses the deploy/rollback status (`stack.deploys_and_rollbacks.last`, its `id`, `ended_at`, `running?`) for **every** stack hosted on the Shipit instance, including stacks they have no authorization to view. This is a cross-tenant confidentiality break: state that should be gated per-stack (deploy status, and indirectly release cadence/activity) becomes readable for arbitrary repositories. This matches the "High — unauthenticated (here: unauthorized) read of stack state" category: the token itself was legitimately minted, but the read it grants is no longer scoped to the resource the user is authorized for. The token is durable (a signed id, not time-limited beyond `ApiClient` deletion) and reusable indefinitely and repeatably against any/all stacks.

### Likelihood Explanation
Preconditions are minimal: the attacker only needs a valid Shipit session (`current_user`) and the ability to reach `cc_menu_url` for at least one stack they can view — a very common and often broadly granted access level (any org member per the documented GitHub OAuth flow). No secrets, GitHub App keys, or special Shipit privileges are required. The exploit is a single authenticated GET request to mint the token, followed by trivial replay against arbitrary `stack_id` path segments on the unauthenticated-by-session API surface. This is low-cost, fully repeatable, and does not depend on any race condition or GitHub-side interaction.

### Recommendation
- Set `stack: stack` when creating the `ApiClient` in `CCMenuUrlController#client`, and make `stack_id` part of the `find_or_create_by!` lookup key (so one CCMenu client per stack, not one shared across all stacks for a user).
- In `Api::CCMenuController`, stop overriding `stack`/`authenticate_api_client` in a way that discards scoping — reuse `Api::BaseController#stacks`/`#stack`, which respects `current_api_client.stack_id`, and additionally enforce `current_api_client.stack_id == stack.id` (or `stack_id.nil?` should not implicitly mean "all stacks" for CCMenu-issued tokens).

### Proof of Concept
```ruby
# test/controllers/ccmenu_url_controller_test.rb (new or extended)
test "cc_menu_url token is not scoped to the requesting stack" do
  low_priv_user = shipit_users(:walrus) # has access to `stacks(:shipit)` only
  sign_in(low_priv_user)

  get cc_menu_url_stack_url(stacks(:shipit).to_param) # /stacks/:owner/:repo/:env/cc_menu_url
  assert_response :ok
  json = JSON.parse(response.body)
  token = URI(json['ccmenu_url']).query.split('=').last

  other_stack = stacks(:cyclimse) # a different stack the user has no access to in the UI
  get api_stack_ccmenu_url(stack_id: other_stack.to_param, token: token, format: :xml)

  # Assert the binding: token minted for `stacks(:shipit)` should NOT authorize `other_stack`
  assert_response :success # demonstrates the vulnerability: should have been :unauthorized/:forbidden
end
```
This proves `client.stack_id` (nil at creation) diverges from `stack.id` (the path stack), and that `CCMenuController` grants access regardless.
