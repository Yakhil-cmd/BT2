## Confirmed: valid cross-tenant vulnerability

### Title
`StatusHandler#process` applies GitHub status webhooks to every `Commit` sharing a SHA across all organizations, bypassing the org-scoped signature check - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates a webhook only against the GitHub App belonging to the org named in the payload's `repository.owner.login` (org A), but `StatusHandler#process` then mutates **every** `Commit` row in the entire database whose `sha` matches, with zero filter on repository, stack, or organization. Any org sharing a commit SHA with org A (e.g. both tracking a fork/mirror of the same upstream repo) gets its `Commit`/`Status` records mutated by a webhook that was never signed by, or addressed to, that org.

### Finding Description
The claimed binding is:

`authenticated_org = Shipit.github(organization: repository_owner).organization` (org A, verified in `WebhooksController#verify_signature`, [1](#0-0) )

should equal

`mutated_org = organization_owning(Commit#stack#repository)` for every record touched by the handler invoked from that request.

Tracing the code shows this equality is **not enforced** for the `status` event:

- `WebhooksController#create` dispatches the raw parsed payload to every registered handler for the event, after `verify_signature` only checks the HMAC against `Shipit.github(organization: repository_owner)` — i.e., org A's secret. [2](#0-1) 
- `StatusHandler#process` does: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a global, unscoped lookup by `sha` alone. [3](#0-2) 
- By contrast, every other handler (`PushHandler`, all `PullRequest::*Handler`s) explicitly scopes to the repository named in the payload via `Repository.from_github_repo_name(repository_name)` / `params.repository.full_name` before touching any stack. [4](#0-3) [5](#0-4) [6](#0-5) 
- The `commits` table index is `(stack_id, sha)`, not a global unique constraint on `sha`, per the migration `db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb` — the schema itself acknowledges the same SHA can legitimately exist under multiple, unrelated `stack_id`s (and therefore unrelated repositories/organizations). `Commit belongs_to :stack` with no repository-level uniqueness enforced at the DB layer. [7](#0-6) 

Exploit flow: Attacker is an unprivileged contributor to a repo in org A. Org A and org B each run Shipit-tracked stacks against repositories that share a commit history (fork, mirror, vendored subtree, or reused upstream commit) — a routine, non-adversarial condition, not a SHA-1 collision. The attacker performs an ordinary, unprivileged action in org A's repo (opens a PR / pushes a branch) that causes GitHub's own infrastructure to emit a genuine, correctly-signed `status` webhook for org A to Shipit. `verify_signature` passes because it only checks the signature against org A's `webhook_secret`, which is legitimately correct. `StatusHandler#process` then queries `Commit.where(sha: params.sha)` across the whole table, finds org B's `Commit` with the same SHA, and calls `create_status_from_github!` on it — writing a `Status` row and mutating org B's `Commit`/`Stack` state (touching `updated_at`, potentially enabling CI, scheduling continuous delivery/merges via `schedule_continuous_delivery` and `stack.schedule_merges`). None of `verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema (`StatusHandler` only requires `sha`/`state`, no repository), or model validations check that the `Commit` found belongs to a stack/repository under the authenticated org.

### Impact Explanation
A webhook validly signed for org A causes write mutations (`Status` creation, `Commit`/`Stack` `updated_at` touches, CI enablement, and scheduling of `ContinuousDeliveryJob`/merge-request processing) on org B's `Commit` record, with zero org-B credential, session, or webhook secret ever presented. This is "a payload for one repository mutating another's stack/commit," matching the Critical severity bucket in the rules. The blast radius spans every organization configured in `Shipit.github_teams`/multi-tenant `github` config that happens to share any commit SHA with the attacker's org — repeatable for every subsequent status GitHub sends for that SHA (and for any other SHA shared across orgs).

### Likelihood Explanation
Preconditions: a multi-tenant Shipit instance with two orgs configured under `config/secrets.yml`'s multi-org `github` block (as documented in `docs/setup.md`), and at least one commit SHA shared between a repository under org A and a repository under org B (naturally occurs with forks/mirrors of shared upstream code, common in real deployments). Attacker cost is zero beyond normal unprivileged repo contribution (open PR/push branch) to cause GitHub to legitimately fire a status webhook. No secrets, tokens, or elevated GitHub roles are needed. This is deterministic and repeatable per status event.

### Recommendation
Scope `StatusHandler#process` to the repository named in the webhook payload, mirroring `PushHandler`/`PullRequest` handlers: require `repository.full_name` in the params schema, resolve `Repository.from_github_repo_name(...)`, and restrict the `Commit` lookup to `commit.stack.repository_id == repository.id` (or join through `stacks`) before calling `create_status_from_github!`, rather than a global `Commit.where(sha:)`.

### Proof of Concept
minitest plan (no live GitHub, `test/controllers/webhooks_controller_test.rb`-style):
1. Configure two `GitHubApp`s/`Organization`s A and B with distinct `webhook_secret`s (as in `test/dummy/config/secrets_double_github_app.yml`).
2. Create `Stack`/`Repository` under org A and org B, each with a `Commit` having the identical `sha` (`SAME_SHA`).
3. Build a `status` webhook payload: `{ sha: SAME_SHA, state: 'success', repository: { full_name: 'orgA/repo', owner: { login: 'A' } } }`.
4. Sign it only with org A's `webhook_secret` (`X-Hub-Signature`), post to `/webhooks`.
5. Assert: `assert_response :ok`.
6. Binding check both sides:
   - Before: `orgB_commit.statuses.count == 0`.
   - After: `assert_equal 1, orgB_commit.reload.statuses.count` (fails the security property — B's commit was mutated using only A's signature) while also confirming `assert_equal 1, orgA_commit.reload.statuses.count`.
7. Assert no B-scoped credential (session, `ApiClient`, org-B `webhook_secret`) was ever referenced/stubbed in the request.
