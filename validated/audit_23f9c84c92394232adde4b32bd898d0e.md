## Finding

Based on my research, I found a plausible analog to CVE-2015-5146 (NUL-byte causing an unhandled crash in a message-processing path) in ocore's AA/formula pipeline, but I could not fully confirm whether the crash path is actually unguarded end-to-end, since I ran out of iterations before reading the exact `aa_composer.js` lines where `objectHash.getUnitHash`/`getBase64Hash` are invoked.

### Title
Unhandled NUL-byte exception in unit hashing triggered by `json_parse` results reaching `getSourceString` - (File: string_utils.js, formula/evaluation.js, object_hash.js)

### Summary
`json_parse()` in oscript/AA formulas parses arbitrary JSON supplied in trigger data or AA state, including JSON escape sequences like `\u0000`, without stripping or rejecting embedded NUL (`\x00`) bytes in resulting strings. [1](#0-0) 
Those parsed values can be echoed into AA response messages (e.g. `data`, `data_feed` payloads) or stored as state variables. When ocore later computes the canonical source string / hash of the resulting object (unit, payload, etc.) via `getSourceString`, any string or object key containing a `\x00` byte causes the function to `throw`. [2](#0-1) 
This helper is invoked from `object_hash.js` to compute unit/payload hashes, [3](#0-2) 
and `object_hash.js`'s hash functions are called from `aa_composer.js` when building and finalizing AA response units.

### Finding Description
`isObjectWellFormed` — the check that rejects "lone surrogate or null byte" — is applied to incoming, already-serialized units at validation time. [4](#0-3) 
It is not re-applied to values that are synthesized at runtime by AA/oscript execution (e.g., the object produced by `json_parse`, which is only checked for size (`isTooBigObj`), non-finite numbers, and `null` replacement, not for embedded NUL bytes). [5](#0-4) 
If such a string is then included in a message an AA composes in its response (`data`, `data_feed`, etc.), or persisted as a state variable that later feeds into a response, the value is not re-validated for NUL bytes before the response unit is serialized/hashed.

Some code paths do defensively guard this: `json_stringify` wraps `getJsonSourceString` in `try/catch` and turns the NUL-byte throw into a formula-level fatal error rather than letting it escape. [6](#0-5) 
However, this protection is specific to the `json_stringify` formula op. I was not able to verify, within the available iterations, whether the equivalent hash computation performed later by `aa_composer.js` when finalizing/saving the AA response unit (via `objectHash.getUnitHash`/`getBase64Hash`) is similarly wrapped in error handling, or whether it can throw uncaught.

### Impact Explanation
If the hashing call inside `aa_composer.js`'s response-building/save flow is not wrapped in `try/catch`, an attacker-controlled AA trigger (data field with a `\u0000`-escaped string, processed by `json_parse` and echoed to a response message or state variable) would cause a synchronous, uncaught exception on every full node processing that trigger. In Node.js this crashes the process — a deterministic denial of service reachable by any unprivileged AA trigger sender, matching the CVE's bug class (authenticated/unprivileged input with an embedded NUL byte causing a service crash). If multiple/most nodes process the same trigger identically, this could stall network confirmation of the associated AA and subsequent units depending on it.

### Likelihood Explanation
Medium-confidence. The lack of NUL-byte filtering after `json_parse` is confirmed in code, and `getSourceString`'s throw-on-NUL-byte behavior is also confirmed. What remains unconfirmed is whether the specific hash call site inside `aa_composer.js` that finalizes AA response units has its own guard/try-catch around the hashing step; without reading those exact lines I cannot assert the exception definitely escapes uncaught.

### Recommendation
- Reject or strip NUL bytes from `json_parse` results before they can be merged into AA response payloads or state variables (mirroring the check already done for `payload_uri`). [7](#0-6) 
- Ensure every call to `objectHash.getUnitHash`/`getBase64Hash` triggered during AA response composition/saving is wrapped in `try/catch`, converting a NUL-byte (or any other "well-formedness") violation into a bounce/fatal formula error instead of an uncaught exception, consistent with the `json_stringify` handling pattern. [6](#0-5) 

### Proof of Concept
Not fully verified — the described PoC (an AA trigger with `data: { y: "\"\\u0000\"" }`, an AA definition doing `$b = json_parse(trigger.data.y); ... response messages include $b`) would need to be tested against the actual response-saving code path in `aa_composer.js` (not fully retrieved) to confirm whether the resulting NUL byte reaches an un-guarded `getSourceString` call and crashes the process.
