### Title
Cross-tenant webhook forgery: signature verification org (`repository.owner.login`) is never bound to the mutated repository org (`repository.full_name`) - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to check against using `params.dig('repository','owner','login')`, while every pull_request handler (`EditedHandler`, `ReopenedHandler`, `ClosedHandler`, etc.) resolves and mutates the actual target repository using the independent field `params.repository.full_name`. Because these two JSON fields are never checked for consistency, and `GithubApp#verify_webhook_signature` unconditionally returns `true` when an org has no configured `webhook_secret`, an attacker can pick any org lacking a secret for the "owner.login" field while pointing `full_name` at an arbitrary, fully-verified organization's repository, bypassing signature verification entirely for that target.

### Finding Description
The broken binding, stated as an equality that must hold but doesn't:
`org_used_for_verification (params.repository.owner.login)` **must equal** `org_that_owns_the_mutated_repo (derived from params.repository.full_name)` — but the code path never enforces this.

Trace:
- `app/controllers/shipit/webhooks_controller.rb:24-49` (`verify_signature`) computes `repository_owner` via `repository_owner` (line 59-62: `params.dig('repository','owner','login') || params.dig('organization','login')`), fetches `Shipit.github(organization: repository_owner)`, and calls `verify_webhook_signature`. [1](#0-0) [2](#0-1) 
- `lib/shipit/github_app.rb:76-83` (`verify_webhook_signature`) returns `true` unconditionally when `webhook_secret` is blank for that org's config (`return true unless webhook_secret`). [3](#0-2) 
- After `verify_signature` passes (or is bypassed), `WebhooksController#create` dispatches the *entire raw JSON body* — including `repository.full_name` — to the registered handlers. [4](#0-3) 
- The pull_request handlers (`EditedHandler`, `ReopenedHandler`, `ClosedHandler`) independently resolve the repository to mutate via `Shipit::Repository.from_github_repo_name(params.repository.full_name)`, a field entirely distinct from `repository.owner.login`. [5](#0-4) 

Because the attacker controls the raw JSON body of the webhook POST and no code checks that `owner.login` matches the org portion of `full_name`, an attacker can craft a payload where `repository.owner.login = "empty-org"` (an org configured in `Shipit.github` with no `webhook_secret`, causing `verify_webhook_signature` to short-circuit `true`) while `repository.full_name = "legit-org/production-repo"` names a real, fully-configured, actively-verified organization's repository. The signature check therefore never validates anything against the real target's secret, yet the handler proceeds to mutate `legit-org/production-repo`'s tracked `PullRequest` row.

None of the existing guards catch this: `drop_unhandled_event` only checks event type presence; `check_if_ping` only intercepts `ping` events; there is no `ExplicitParameters` schema or model validation cross-checking `owner.login` against `full_name`'s owner segment anywhere in the controller or handler chain.

### Impact Explanation
This is an authentication-bypass / cross-tenant-mutation bug: a webhook payload that is signed (or exempted from signing) under one organization's identity is used to mutate a `PullRequest` record belonging to a different, fully-configured organization's repository. This matches the Critical category "a payload for one repository mutating another's stack, commit, task or team" and "authentication bypass (forged webhook ... accepted)". The blast radius spans all repositories tracked by any org configured in `Shipit.github`, as long as at least one org in that same Shipit deployment has a blank/absent `webhook_secret` (a state the codebase's own config samples show as valid/expected during setup). This is repeatable for every pull_request event type routed through handlers keyed off `full_name` (edited, reopened, closed, labeled, etc.), not limited to a single request.

### Likelihood Explanation
Exploitation requires only that the Shipit deployment's `Shipit.github` multi-org config contains at least one organization entry with no `webhook_secret` set — a state the repo's own sample configs (`config/secrets.development.shopify.yml`) show is valid/expected, i.e., plausible in real multi-tenant deployments during onboarding of a new org. Given that precondition, the attacker needs no credentials, tokens, or GitHub App secrets — only the ability to POST an arbitrary JSON body to `/webhooks` with a crafted `X-Github-Event: pull_request` header, fully within the stated unprivileged attacker capabilities.

### Recommendation
Bind webhook signature verification to the same organization/repository that is subsequently mutated: after selecting `Shipit.github(organization: repository_owner)`, validate that the owner segment of `params.repository.full_name` matches `repository_owner` before dispatching to handlers, and reject (422) any payload where they diverge. Additionally, treat organizations with a blank `webhook_secret` as unable to authenticate any webhook for a *different* org's repository — i.e., scope the "no secret configured" bypass strictly to that org's own repositories, not to arbitrary `full_name` values.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (illustrative, not exhaustive)
test "empty-org (no webhook_secret) cannot forge edits to legit-org's tracked PR" do
  Shipit.github_config = {
    'legit-org' => { 'webhook_secret' => 'legit-secret' },
    'empty-org' => {} # no webhook_secret, per documented setup pattern
  }

  stack = shipit_stacks(:shipit) # backed by legit-org/production-repo
  pr = shipit_pull_requests(:some_pr_on_production_repo)

  request.headers['X-Github-Event'] = 'pull_request'
  body = {
    action: 'edited',
    number: pr.number,
    pull_request: { title: 'PWNED', body: 'attacker-controlled' },
    repository: {
      owner: { login: 'empty-org' },      # used for verify_signature -> bypassed
      full_name: 'legit-org/production-repo' # used by EditedHandler to resolve repo
    }
  }.to_json
  # No X-Hub-Signature header supplied at all

  post :create, body: body, as: :json

  pr.reload
  assert_equal 'PWNED', pr.title # mutated with no valid signature for legit-org ever supplied
end
```
This demonstrates the equality `repository_owner (verification) == owner(full_name) (mutation target)` is violated: `empty-org != legit-org`, yet the mutation on `legit-org`'s `PullRequest` succeeds.

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
