This confirms the vulnerability. `create_status_from_github!` calls `add_status` which creates a `Status` record and, critically, calls `stack.schedule_merges` when the new status is `pending?` or `success?`, and fires `deployable_status` hooks — meaning a forged status can push an unrelated repository's commit into a deployable/mergeable state.### Title
`StatusHandler#process` writes commit statuses via a global `Commit.where(sha:)` lookup with no repository scoping, allowing any webhook-owning attacker to mutate another repository's commit CI state - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
Every other `Handler` subclass (`PushHandler`, `PullRequest::*Handler`, `CheckSuiteHandler`) restricts its mutation target to records reachable through `stacks`, which is built from `Repository.from_github_repo_name(repository_name)` — i.e., scoped to the repository named in the verified payload. `StatusHandler#process` is the sole exception: it looks up `Commit.where(sha: params.sha)` globally, with no join to `stacks`/`repository`, so a validly-signed webhook for repository A can create/replicate a `Status` on a `Commit` that actually belongs to repository B.

### Finding Description
The binding that must hold for every handler is: **mutation target set == `stacks`-scoped records for the payload's verified repository**, i.e. `Handler#stacks == Repository.from_github_repo_name(payload.repository.full_name).stacks`.

- `Handler#stacks` (app/models/shipit/webhooks/handlers/handler.rb:32-38) enforces this by deriving stacks strictly from `Repository.from_github_repo_name(repository_name)`.
- `CheckSuiteHandler#process` (app/models/shipit/webhooks/handlers/check_suite_handler.rb:13-17) correctly uses `stacks.where(branch: ...)` then `stack.commits.where(sha: ...)`, so it only touches commits belonging to stacks of the verified repository.
- `PullRequest::*` handlers all resolve `repository` via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` before touching any `PullRequest`/`ReviewStack` record (e.g. app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb:50-54, closed_handler.rb:49-53, labeled_handler.rb:65-68).
- `StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24) instead does:
  ```ruby
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
  ```
  This performs a bare, unscoped, global `Commit` lookup by `sha` alone — it never resolves `repository_name`/`stacks`, so the repository asserted in `params.repository.full_name` (used only for `verify_signature`'s org lookup) is never checked against the `stack`/`repository` that actually owns the matched `Commit`.

Root cause: signature verification (`WebhooksController#verify_signature`, app/controllers/shipit/webhooks_controller.rb:24-49) only proves the request was signed with the secret of the organization named in `payload['repository']['owner']['login']`. It proves nothing about which `sha` values the sender is authorized to reference. Since `sha` values are public GitHub data (readable by anyone via the GitHub UI/API for any repo, private or public depending on access, but typically public repos are the common target), an attacker who owns/controls any GitHub repository with a Shipit webhook configured (thus knows that repo's `webhook_secret`) can send a `status` event whose `repository` block names their own repo (satisfying signature verification) but whose `sha` field is copied from a commit that actually belongs to a different, unrelated repository tracked by the same Shipit instance.

Exploit flow:
1. Attacker owns `attacker/evil-repo`, configures a GitHub webhook on it pointing at the Shipit host, thus knows the valid `X-Hub-Signature` secret for organization `attacker`.
2. Attacker finds a commit `sha` belonging to `victim/real-repo` (a repo tracked by the same Shipit instance) — obtainable from GitHub's public commit history/API for that repo.
3. Attacker POSTs to `/webhooks` with `X-Github-Event: status`, body `{ "repository": {"full_name": "attacker/evil-repo", "owner": {"login": "attacker"}}, "sha": "<victim sha>", "state": "success", ... }`, signed with `attacker`'s webhook secret.
4. `verify_signature` passes (valid signature for `attacker`'s org).
5. `Webhooks.for_event('status')` dispatches to `StatusHandler`, which runs `Commit.where(sha: "<victim sha>")` — this matches the `victim/real-repo` commit despite the payload's `repository` field naming `attacker/evil-repo`.
6. `commit.create_status_from_github!(params)` → `add_status` creates a `Status` on the victim's commit, can flip its aggregate CI state (`success`/`failure`/`pending`), fire `deployable_status`/`commit_status` hooks, and — critically — call `stack.schedule_merges` when the new status is `pending?` or `success?` (`app/models/shipit/commit.rb:379-384`), potentially pushing the victim commit toward automatic merge/deploy eligibility.

None of the existing guards prevent this: `verify_signature` only authenticates the sender's own org, `drop_unhandled_event`/`check_if_ping` are irrelevant, the `ExplicitParameters` schema for `StatusHandler` requires only `sha`/`state`/etc. with no repository-membership constraint, and `Handler#stacks` (the scoping mechanism used elsewhere) is simply never called by `StatusHandler`.

### Impact Explanation
An attacker who owns any GitHub repository connected to a shared Shipit instance can forge CI status data for commits belonging to any other tenant repository on that instance, without any privileged role, session, or secret beyond their own repo's webhook secret. This can corrupt another team's CI/merge-readiness signal (marking failing commits as `success`, triggering `schedule_merges`/auto-merge eligibility, or marking passing commits as `failure` to block deploys) — a cross-tenant write matching the "payload for one repository mutating another's stack/commit" Critical category. It is fully repeatable against any commit sha the attacker can discover for any other repository on the instance, giving broad cross-tenant blast radius limited only by the attacker's ability to enumerate/guess valid shas of tracked commits (trivial for public repos).

### Likelihood Explanation
Preconditions are minimal and match the stated attacker model exactly: the attacker needs only (a) a GitHub repository they own with a webhook configured to point at the shared Shipit host (something any GitHub user can do on their own repo), giving them a valid signing secret for their own org, and (b) knowledge of a target commit's `sha`, which is public information for public GitHub repos. No Shipit session, API token, or elevated GitHub permission is required. This is cheap, deterministic, and repeatable against arbitrary target commits/repos tracked by the instance.

### Recommendation
Scope `StatusHandler#process` through the same `stacks` mechanism used by other handlers, e.g. resolve `stacks` from `Repository.from_github_repo_name(repository_name)` and only update commits belonging to those stacks (mirroring `CheckSuiteHandler`):
```ruby
def process
  stacks.flat_map(&:commits).select { |c| c.sha == params.sha }.each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
or more efficiently, join through `stacks.commits.where(sha: params.sha)`, ensuring the payload's verified `repository.full_name` must match the commit's own stack/repository before any status is written.

### Proof of Concept
Minitest plan (controller-level, no live GitHub, per repo rules):
```ruby

  other_repo_owner = "attacker" # a different Repository fixture whose webhook secret is stubbed as valid

  GithubHook.any_instance.stubs(:verify_signature).returns(true) # simulate attacker's own valid signature

  forged_payload = {
    "sha" => victim_commit.sha,
    "state" => "success",
    "branches" => [],
    "repository" => { "full_name" => "attacker/evil-repo", "owner" => { "login" => other_repo_owner } }
  }.to_json

  request.headers['X-Github-Event'] = 'status'

  assert_difference -> { victim_commit.statuses.count }, 1 do
    post :create, body: forged_payload, as: :json
  end
  # Demonstrates: StatusHandler mutated victim_commit despite payload naming an unrelated repository.

test "push webhook for repository A cannot mutate stacks of repository B (control)" do

  cross_repo_payload["repository"]["owner"]["login"] = "attacker"
```
