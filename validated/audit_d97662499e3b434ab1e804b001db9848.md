### Title
Webhook signature is verified against the payload's claimed organization while the write target (commit/stack) is selected independently, allowing a forged CI status to unlock deploys for any repository - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` authenticates an inbound webhook using a GitHub App config selected from the **unverified JSON body** (`repository.owner.login` / `organization.login`), then dispatches the payload to handlers that write to state (commits, statuses, stacks) using a **different, independently-controlled field** of that same unverified body (`repository.full_name`), or — in the case of `StatusHandler` — no repository scoping at all. This breaks the equality "organization whose secret authenticated the request" == "repository/commit that is written", which is the direct engine analog of the `directionMask` bug (`tokenIn` used to compute the quote vs. `tokenIn == weth` used to decide direction, instead of checking the pool's actual `token0`/`token1`).

### Finding Description
`verify_signature` picks the verifying GitHub App/secret using `repository_owner`, derived straight from the untrusted request body: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` resolves per-organization config (multiple orgs, each with its own, possibly absent, `webhook_secret`), as shown in the multi-org secrets example: [3](#0-2) 

`verify_webhook_signature` treats a blank/unconfigured `webhook_secret` as automatically verified: [4](#0-3) 

Once "verified" against organization `A` (whose secret the attacker controls, or which is simply unset/blank), the payload is routed to handlers. Handlers determine the actual record to mutate using `repository.full_name` — a field entirely independent of the `repository.owner.login`/`organization.login` field used for authentication: [5](#0-4) 

`StatusHandler` is worse: it does not scope to a repository/stack at all, it looks up **every** `Commit` matching the given `sha` across the whole installation: [6](#0-5) 

That status directly feeds the deploy-safety gate: [7](#0-6) 

and successful/pending transitions schedule continuous delivery / merges: [8](#0-7) 

### Impact Explanation
An attacker who can produce a validly-signed webhook for **any** organization configured on the Shipit install (including one with a blank/absent `webhook_secret`, which is explicitly supported per `config/secrets.development.example.yml` and treated as auto-verified) can send a `status` (or `push`, `pull_request`) event whose `repository.owner.login`/`organization.login` matches that weakly-configured org, while the actual data written (commit `sha`, or `repository.full_name` for other handlers) targets a stack belonging to a **different, strictly-configured** organization. For `status` events this forges a `success` CI status on an arbitrary commit sha anywhere in the Shipit instance, which:
- Flips `Commit#deployable?` to `true` for that commit, bypassing the CI safety gate relied upon by `Api::DeploysController#create`'s `require_ci` check.
- Triggers `stack.schedule_merges`/continuous-delivery scheduling on stacks configured for continuous deployment, producing an **unauthorized deploy** without the attacker ever needing the real webhook secret, GitHub write access, or a Shipit session/API token for the targeted repository.

This matches the Critical impact bucket ("an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Likelihood is limited by the precondition that at least one GitHub App organization on the instance has no `webhook_secret` configured (explicitly documented/supported as `# nil` in `config/secrets.development.example.yml` and `config/secrets.development.shopify.yml`) or by the attacker otherwise possessing a valid signature for one organization. Given multi-org installs are a first-class supported configuration and per-org secrets can be individually omitted, this is a realistic and unprivileged attack surface for the engine — the attacker needs no GitHub App private key, no `ApiClient` token, and no session.

### Recommendation
Bind signature verification to the exact same repository/organization identity used to select the target stack:
- Verify the webhook using the organization/repository derived from the record actually being mutated (e.g., resolve `Repository.from_github_repo_name(payload.dig('repository','full_name'))` first, then verify the signature using that repository's own configured GitHub App/organization), rather than trusting `repository.owner.login`/`organization.login` independently.
- In `StatusHandler`, scope the `Commit` lookup to the repository identified from the verified payload (`stacks`/`repository_name`) instead of a bare `Commit.where(sha:)` across the whole installation.
- Do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is blank for any organization that is expected to host production-critical stacks; require explicit opt-in for unsigned orgs and never let an unsigned org's identity "unlock" writes to a differently-owned repository's data.

### Proof of Concept
1. Configure (as is explicitly supported) two orgs in `github:` secrets, e.g. `weak-org` with `webhook_secret: nil` and `strict-org` with a real secret; `strict-org/critical-app` is a Shipit stack set to continuous deployment.
2. POST to `/webhooks` with header `X-Github-Event: status`, no `X-Hub-Signature` (or any value, since a blank secret short-circuits `verify_webhook_signature` to `true`), and body:
```json
{
  "organization": { "login": "weak-org" },
  "sha": "<sha of an undeployed commit on strict-org/critical-app>",
  "state": "success",
  "context": "ci/required-check"
}
```
3. `verify_signature` calls `Shipit.github(organization: 'weak-org')` and passes because `weak-org`'s `webhook_secret` is blank (`lib/shipit/github_app.rb:76-83`).
4. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) looks up `Commit.where(sha: ...)` with no ownership check and creates a `success` `Status` on the `strict-org/critical-app` commit.
5. `Commit#deployable?` becomes `true` (`app/models/shipit/commit.rb:227-229`) and, if `critical-app` has continuous deployment enabled, a deploy is auto-scheduled — all without ever presenting `strict-org`'s real webhook secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
