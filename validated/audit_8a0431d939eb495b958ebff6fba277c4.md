### Title
Unbounded per-asset unspent-output scan when composing AA payment responses can DoS an AA's ability to pay out that asset - (File: `aa_composer.js`)

### Summary
When an Autonomous Agent (AA) needs to pay out coins in a message, `sendUnit()` → `completePaymentPayload()` selects unspent outputs sent to the AA's address and greedily accumulates them in `iterateUnspentOutputs()` until the target amount is reached. For the base asset (bytes), the selection query filters out outputs smaller than `FULL_TRANSFER_INPUT_SIZE` to prevent a "dust" DoS, but for any custom asset there is no such minimum-amount filter and no `LIMIT` on the number of rows fetched or iterated. [1](#0-0) 

### Finding Description
`readStableOutputs()` builds the SQL condition as:
```
asset ? "="+conn.escape(asset) : " IS NULL AND amount>=" + FULL_TRANSFER_INPUT_SIZE
```
so the dust threshold `amount>=FULL_TRANSFER_INPUT_SIZE` is applied **only** when `asset` is null (i.e. base bytes). When a specific asset is being paid, the query returns every unspent output of that asset sent to the AA, with no floor on amount and no `LIMIT`. [2](#0-1) 

`iterateUnspentOutputs()` then walks the entire returned row set synchronously in a `for` loop, pushing every output into `payload.inputs`/`arrConsumedOutputs` until `total_amount` reaches `target_amount`: [3](#0-2) 

This is exactly the class of bug described in the external report: an array/result set that is fully scanned from the beginning on every call, and whose size is controlled by ordinary, unprivileged actions (here: any unit poster can send arbitrarily many tiny-amount payment outputs of a given custom asset to the AA's address). Because there is no per-output minimum and no row limit, an attacker can inflate the number of unspent same-asset outputs held by the AA indefinitely and cheaply (asset amounts can be as small as 1 unit; the attacker only pays the normal byte fee for posting the unit, not for the asset amount itself).

Each subsequent time the AA needs to send that asset (any AA response that includes a `payment` message in that asset), `sendUnit()` must re-run this unbounded scan/loop over all such unspent outputs before it can accumulate enough value to satisfy the target amount, or before it even determines it needs to fall back to `issueAsset()`. As the attacker keeps feeding more dust outputs, the cost of this loop (and of building `payload.inputs`, which contributes to unit size/oversize-fee calculations, and to `arrUsedOutputIds` used in a follow-up "NOT IN (...)" SQL clause) keeps growing without bound.

### Impact Explanation
- The `payload.inputs` array assembled from this loop is not capped by the composer itself before the resulting unit is passed to `validateAndSaveUnit()` / `writer.saveJoint()`. If the loop consumes too many outputs, the resulting AA response unit can become invalid (e.g., exceeding message/size limits) or too expensive to build (long-running synchronous JS loop plus a very large SQL result set), causing the AA's response for that asset to bounce or fail entirely.
- Because any payment path in that asset goes through the same `completePaymentPayload()`/`iterateUnspentOutputs()` code, a single attacker can effectively freeze an AA's ability to pay out a specific asset by continuously topping up the AA address with many small-amount outputs of that asset, which is the same "grow indefinitely → later calls fail" pattern as the referenced `lockedCapitals` issue, but here it directly causes AA fund-flow disruption (bounced responses / stuck funds) rather than just gas waste.
- This is worse for custom assets than for bytes precisely because the code contains an explicit anti-dust mitigation for the base asset ("byte outputs less than 60 bytes ... are ignored to prevent dust attack: spamming the AA with very small outputs so that the AA spends all its money for fees when it tries to respond") that was never extended to non-base assets. [4](#0-3) 

### Likelihood Explanation
Likelihood is Medium-High for AAs that hold/pay out custom assets that any address can freely obtain and send to the AA in small increments (e.g., divisible assets with permissive issuance/transfer, or well-known widely-held assets). An unprivileged unit poster only needs to author many payment units, each transferring a tiny amount of the target asset to the AA's address — a routine, cheap, and repeatable action requiring no special privileges, definitions, or AA interaction beyond ordinary payment messages.

### Recommendation
- Apply a minimum-amount ("dust") filter to non-base assets as well, or make it configurable/derived from the message's own size overhead (similar to `FULL_TRANSFER_INPUT_SIZE` for bytes), in `readStableOutputs()` and `readUnstableOutputsSentByAAs()`.
- Add an explicit `LIMIT` to both queries (bounded by e.g. `MAX_MESSAGES_PER_UNIT`/`MAX_INPUTS_PER_PAYMENT_MESSAGE`) so the number of rows fetched and iterated per response is capped regardless of how many dust outputs an attacker has created.
- Consider consolidating/sweeping many small same-asset outputs into fewer, larger outputs periodically (e.g., via a maintenance transfer) so the "unspent output set" used for future payouts doesn't grow unbounded from attacker-controlled dust.

### Proof of Concept
1. Deploy (or target) an AA that, on some trigger, sends out a payment in a custom asset `X` that it holds a balance of.
2. As an unprivileged attacker, repeatedly post ordinary `payment` units transferring `1` unit of asset `X` to the AA's address (cost: normal byte fee only; no dust filter blocks this because `readStableOutputs()`'s condition only enforces `amount>=FULL_TRANSFER_INPUT_SIZE` when `asset` is null). [5](#0-4) 
3. Repeat step 2 thousands of times to accumulate a large number of tiny unspent outputs of asset `X` addressed to the AA.
4. Trigger the AA to send out asset `X`. `completePaymentPayload()` calls `readStableOutputs()` (no `LIMIT`, no dust filter for `asset`) and `iterateUnspentOutputs()` must loop over the full (attacker-inflated) result set to accumulate the needed amount. [6](#0-5) 
5. As the dust count grows without bound, the loop/query cost grows correspondingly, degrading or eventually breaking the AA's ability to compose a valid response paying out asset `X`, mirroring the unbounded `lockedCapitals` scan pattern from the referenced report.

			function readStableOutputs(handleRows) {
			//	console.log('--- readStableOutputs');
				if (asset && assetInfos[asset].auto_destroy && assetInfos[asset].definer_address === address && mci >= constants.pemCurvesFixMci)
					return handleRows([]);
				// byte outputs less than 60 bytes (which are net negative) are ignored to prevent dust attack: spamming the AA with very small outputs so that the AA spends all its money for fees when it tries to respond
				conn.query(
					"SELECT unit, message_index, output_index, amount, output_id \n\
					FROM outputs \n\
					CROSS JOIN units USING(unit) \n\
					WHERE address=? AND asset"+(asset ? "="+conn.escape(asset) : " IS NULL AND amount>=" + FULL_TRANSFER_INPUT_SIZE)+" AND is_spent=0 \n\
						AND sequence='good' AND main_chain_index<=? \n\
						AND output_id NOT IN("+(arrUsedOutputIds.length === 0 ? "-1" : arrUsedOutputIds.join(', '))+") \n\
					ORDER BY main_chain_index, unit, output_index", // sort order must be deterministic
					[address, mci], handleRows
				);
			}

			function readUnstableOutputsSentByAAs(handleRows) {
			//	console.log('--- readUnstableOutputsSentByAAs');
				if (asset && assetInfos[asset].auto_destroy && assetInfos[asset].definer_address === address && mci >= constants.pemCurvesFixMci)

				conn.query(
					"SELECT outputs.unit, message_index, output_index, amount, output_id \n\
					FROM outputs \n\
					CROSS JOIN units USING(unit) \n\
					CROSS JOIN unit_authors USING(unit) \n\
					CROSS JOIN aa_addresses ON unit_authors.address=aa_addresses.address \n\

						AND output_id NOT IN("+(arrUsedOutputIds.length === 0 ? "-1" : arrUsedOutputIds.join(', '))+") \n\
					ORDER BY latest_included_mc_index, level, outputs.unit, output_index", // sort order must be deterministic
					[address, mci], handleRows
