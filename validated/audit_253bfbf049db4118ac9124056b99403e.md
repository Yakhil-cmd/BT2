### Title
Cross-repository CI status forgery via unscoped commit lookup in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
Webhook signature verification only proves that the request was signed with the `webhook_secret` of the *organization named in the payload's own `repository.owner.login` field*. It does not constrain which `Commit`/`Stack`/repository the payload is permitted to mutate. `StatusHandler` looks up the target commit by SHA **globally**, across every stack tracked by the Shipit instance, so a validly-signed status webhook from one organization can write a CI status onto a commit that belongs to a completely different organization's repository.

### Finding Description
`WebhooksController#verify_signature` derives the signing organization purely from attacker-supplied JSON and uses it only to pick which secret to check the HMAC against: [1](#0-0) [2](#0-1) 

Once the signature is validated for that self-declared organization, the handler dispatch (`Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`) is invoked with the raw, attacker-controlled JSON body for every registered handler: [3](#0-2) 

For the `status` event, `StatusHandler#process` resolves the target purely by SHA, with no scoping to the stack, repository, or organization that produced the signature: [4](#0-3) 

Because `Commit.where(sha: params.sha)` is a global lookup, any commit SHA already synced into *any* stack in the Shipit instance can be targeted, including SHAs belonging to a repository owned by a completely different GitHub organization than the one whose secret validated the signature. This breaks the binding: **organization that authenticated (via `verify_webhook_signature`) ≠ repository/stack actually written to (via `Commit.where(sha:)`)**. The existing test suite confirms the handler writes payload fields (`state`, `description`, `target_url`, `context`) directly onto the located commit's `Status` without any origin check: [5](#0-4) 

### Impact Explanation
`ci.require` in `shipit.yml` gates deploys/merges on the presence of specific status contexts on a commit (documented in `README.md`), and the merge queue also relies on commit statuses to decide mergeability. An attacker who controls (or has installed the Shipit GitHub App on) any organization tracked by this Shipit instance can forge a "success" status for a required CI context on a commit belonging to an unrelated, higher-value stack/repository, letting that commit bypass CI gating for deploy or auto-merge — an unauthorized deploy/merge across a repository/organization boundary the attacker does not control. This matches the Critical impact category "cross-repository writes...or an unauthorized deploy, rollback or merge."

### Likelihood Explanation
The only prerequisite is possession of a `webhook_secret` for *some* organization onboarded to the Shipit instance (e.g., the attacker's own org, which they can freely configure since a GitHub App webhook secret is chosen by whoever installs the app) and knowledge of a target commit SHA already tracked by another stack (trivially obtainable for public repositories, or from prior legitimate access). No Shipit session, `ApiClient` token, or GitHub write access to the victim repository is required — only the ability to send a correctly HMAC-signed webhook body to `/webhooks`.

### Recommendation
Scope the commit lookup in `StatusHandler#process` (and analogous handlers) to the repository/organization actually authenticated by `verify_signature`, e.g. filter `Commit.where(sha: params.sha)` by `stack.repository` matching `repository_owner`/`repository.full_name` from the same verified payload, rejecting any commit whose owning repository does not match the organization used to validate the HMAC signature.

### Proof of Concept
1. Attacker creates/owns GitHub org `attacker-org`, installs a GitHub App there, and knows its `webhook_secret` (`S_attacker`).
2. Attacker identifies a commit SHA `deadbeef...` already tracked in Shipit under `victim-org/victim-repo`'s stack (e.g., from public commit history or Shipit's own commit page).
3. Attacker crafts a `status` event payload:
```json
{
  "sha": "deadbeef...",
  "state": "success",
  "context": "ci/required-check",
  "target_url": "https://attacker.example/fake",
  "repository": { "owner": { "login": "attacker-org" } }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(S_attacker, raw_body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` resolves `repository_owner` = `attacker-org`, verifies successfully against `S_attacker`.
6. `StatusHandler#process` runs `Commit.where(sha: "deadbeef...")`, finds the commit belonging to `victim-org/victim-repo`, and calls `create_status_from_github!`, writing a forged "success" status for `ci/required-check` onto the victim's commit — potentially unblocking a deploy or merge gated on that context, despite the attacker having no relationship to `victim-org`.
