### Title
Reused Bitcoin L1 lockup outputs let a staker double-count sats credited to `pox-5` bonds - (File: `stackslib/src/chainstate/stacks/boot/pox-5.clar`)

### Summary
This is the strongest reachable analog to the `xcall()` "missing sanity check" bug class in this repo's scope. `register-for-bond` in `pox-5.clar` accepts a Bitcoin L1 lockup proof (`btc-lockup`) and credits `sats-total` to the caller's bond membership via `verify-l1-lockups`/`validate-l1-lockup`, but the duplicate-output check (`seen-outpoints`) is only tracked locally within the single call's fold accumulator, not persisted anywhere on-chain. The same Bitcoin UTXO/output can therefore be replayed across separate `register-for-bond` calls to credit `sats-total` multiple times without ever locking additional BTC, breaking the equality "sats credited == sats actually locked on Bitcoin."

### Finding Description
`register-for-bond` computes the sats a staker is credited with for a bond by calling `verify-l1-lockups`: [1](#0-0) 

`verify-l1-lockups` builds a fresh accumulator (including `seen-outpoints: (list)`) for each invocation and folds over the supplied outputs via `validate-l1-lockup`: [2](#0-1) 

Inside `validate-l1-lockup`, duplicate detection is only performed against `seen-outpoints`, a value that lives purely inside the current call's accumulator and is discarded once the function returns: [3](#0-2) 

There is no map in the contract (confirmed via search — no `used-outpoints`/persisted outpoint map exists outside this local accumulator field) that records previously consumed `(txid, output-index)` pairs across separate transactions. This means:
- A staker can present the *same* Bitcoin lockup output in two different `register-for-bond` calls (e.g., registering into two different bonds, or after `unstake`/roll-over cycles) and have `sats-total` credited both times.
- Because `amount-ustx` sizing and reward eligibility are derived from `sats-total` (see `min-ustx-for-sats-amount`/`sats-total` usage in `register-for-bond`), this inflates the staker's/bond's recognized BTC collateral without any additional BTC being locked.

This mirrors the reported `xcall()` class of vulnerability: the function performs *some* checks (script/amount/merkle/duplicate-within-call) but is missing the one check that actually enforces the invariant the protocol depends on — that a given L1 lockup can only ever back one credited stake, globally, not just within a single call.

### Impact Explanation
This breaks the "sats credited by an L1 proof that were never locked on Bitcoin" invariant and results in double-counting of a bond commitment. Since `sats-total` determines the staker's `protocol-bonds-total-staked`, `total-sbtc-staked`-adjacent bond bookkeeping, and bond reward share calculations (per the `pox-5.clar` bond reward-splitting logic seen in the referenced test files), replaying an L1 outpoint lets an attacker claim reward shares and bond slots backed by BTC collateral that does not actually exist on-chain in that quantity. This is a Critical-severity finding under the given impact taxonomy ("double-counting a commitment or reward", "unbacked... reward").

### Likelihood Explanation
The only requirement is that the attacker (an ordinary, unprivileged staker) call `register-for-bond` more than once with a `btc-lockup` payload referencing the same Bitcoin transaction output(s) they already used in a prior successful call — no signer, bond-admin, or miner privileges are needed, and no cross-call state prevents the replay. This is straightforwardly reachable through the normal public entry point.

### Recommendation
Persist consumed L1 outpoints in a durable map (e.g., `used-l1-lockup-outpoints: { txid, output-index } -> bool`) and check/insert into it inside `validate-l1-lockup` (or immediately after `verify-l1-lockups` returns, before crediting `sats-total`), so that once an outpoint has backed a bond registration it can never be credited again by any subsequent call, regardless of which bond or staking transaction references it.

### Proof of Concept
1. Staker Alice locks 1 BTC output `O` on L1 to the `pox-5` timelock script and calls `register-for-bond` for `bond-index = 0`, submitting a Merkle proof for `O`. `sats-total` for `O` is credited to bond 0's membership and `protocol-bonds-total-staked`.
2. A new bond (`bond-index = 1`) is set up (or Alice becomes eligible for another bond via allowlisting/roll-over).
3. Alice calls `register-for-bond` again for `bond-index = 1`, submitting the *same* Merkle proof for output `O` (same `txid`/`output-index`, same header/leaf-hashes).
4. `verify-l1-lockups` re-validates `O` from scratch (fresh `seen-outpoints` accumulator) — all per-output checks (`script`, `amount`, `merkle-proof`, `unlock-burn-height`) pass again because none of them depend on prior calls, and no persisted outpoint-usage map rejects the replay.
5. `sats-total` for `O` is credited a second time to bond 1, so the same locked BTC now backs collateral/reward-eligibility in two separate bonds simultaneously — double-counting confirmed.

Note: I could not execute this against a running node/test harness in this session (ask-only mode, no execution tools), so this PoC is based on static code tracing of `register-for-bond` → `verify-l1-lockups` → `validate-l1-lockup` and a repo-wide search confirming the absence of any persisted outpoint-tracking map. A Devin session with the Clarinet/simnet test suite (`contrib/core-contract-tests/tests/pox-5/*`) could confirm this dynamically by adapting an existing `registerForBond`/`btcLockup` test to reuse the same lockup proof across two `register-for-bond` calls.

        (staker principal)
        (bond-index uint)

            outputs: (list 10
                {
                    height: uint,
                    tx: (buff 100000),
                    output-index: uint,
                    header: (buff 80),
                    leaf-hashes: (list 14 (buff 32)),
                    tx-count: uint,
                    tx-index: uint,
                    amount: uint,
                    unlock-burn-height: uint,
                }
            ),
            staker-unlock-bytes: (buff 683),
        })

    (let (
            (bond (unwrap! (get-protocol-bond bond-index) ERR_BOND_NOT_FOUND))
            (accumulation (try! (fold validate-l1-lockup (get outputs lockups)
                (ok {
                    sum: u0,
                    staker: staker,

                    early-unlock-bytes: (get early-unlock-bytes bond),
                    seen-outpoints: (list),
                })
            )))
        )
