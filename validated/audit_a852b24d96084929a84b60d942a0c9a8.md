### Title
`OpenedHandler#provision?` operator-precedence bug lets `review_stacks_enabled: false` repos still create and enqueue review stacks for provisioning - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`ReviewStackProvisioningQueue.queued_stacks` and `.work` do indeed select and provision any `Shipit::ReviewStack` with `provision_status: :deprovisioned` and `awaiting_provision: true`, with no join/filter on the owning repository's `review_stacks_enabled` flag. [1](#0-0)  The real defect that makes this exploitable is upstream: `OpenedHandler#provision?` (and identically `ReopenedHandler#unarchive?`) has a Ruby operator-precedence bug that causes `review_stacks_enabled` to gate only the `allow_all` branch, not the `allow_with_label`/`prevent_with_label` branches, so a repo configured with `review_stacks_enabled: false` and `provisioning_behavior: allow_with_label` (or `prevent_with_label`) will still create a stack, enqueue it via `ReviewStackProvisioningQueue.add`, and have it picked up and provisioned by the unfiltered `.work` pass.

### Finding Description
Binding claimed/expected: `stack.repository.review_stacks_enabled == true` for every stack popped by `.work` and passed to `stack.provisioner.up`. Actual binding enforced by `queued_stacks`: only `provision_status == :deprovisioned AND awaiting_provision == true`, with `repository.review_stacks_enabled` never referenced. [1](#0-0) 

The gate that is supposed to prevent a disabled-review-stacks repo from ever reaching this queue is `OpenedHandler#respond_to_pull_request_opened?` → `#provision?`:
```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
``` [2](#0-1) 
Because `&&` binds tighter than `||` in Ruby, this evaluates as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label) || (prevent_with_label? && !has_label)`.
The `review_stacks_enabled` check is scoped only to the first disjunct. If an operator sets `review_stacks_enabled: false` on a repository but leaves `provisioning_behavior` as `allow_with_label` or `prevent_with_label` (e.g. toggling the feature off without resetting behavior), `provision?` still returns `true` whenever the label condition matches, entirely independent of `review_stacks_enabled`. The exact same bug pattern exists in `ReopenedHandler#unarchive?`. [3](#0-2) 

Attacker path: any GitHub user who can open a PR against such a misconfigured repository, and who can apply/have applied the configured provisioning label (attacker owns the PR and can label their own PR/fork), sends a `pull_request` `opened` webhook. `OpenedHandler#process` calls `ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!`, which creates the `ReviewStack` and immediately calls `Shipit::ReviewStackProvisioningQueue.add(stack)`, setting `awaiting_provision: true`. [4](#0-3)  On the next cron pass, `ReviewStackProvisioningQueue.work` finds this stack via `queued_stacks` (no `review_stacks_enabled` filter) and calls `stack.provisioner.provision?` then `stack.provision`, which transitions to `:provisioning` and fires `stack.provisioner.up`. [5](#0-4) [6](#0-5) 

Contrast: `LabeledHandler#respond_to_label_change?` correctly `&&`-chains `repository.review_stacks_enabled` with the rest of the condition as a single top-level conjunct (not split across `||` branches), so it is not affected by this precedence issue. [7](#0-6)  This asymmetry confirms `OpenedHandler`/`ReopenedHandler` diverge from the intended design present elsewhere in the same module.

### Impact Explanation
Once the stack is queued, `ReviewStackProvisioningQueue.work` provisions it exactly like any properly enabled repo's stack, ultimately invoking the configured `ProvisioningHandler#up`, which (per the review-stacks provisioning design) executes host commands. This means a repository whose administrator explicitly disabled review-stack auto-provisioning (`review_stacks_enabled: false`) can still have its provisioner invoked by an unprivileged PR author's webhook, purely due to leftover `provisioning_behavior` configuration. This is a repository-scoped authorization bypass of the `review_stacks_enabled` control, matching "a command running that should not" / provisioning executed for a repository that did not authorize it under current configuration. Severity is bounded by the precondition below.

### Likelihood Explanation
This requires a specific, non-default repository configuration: `review_stacks_enabled: false` combined with `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` (rather than reset to a neutral/`allow_all`-disabled state). This is a plausible operator misconfiguration (e.g., disabling the review-stacks feature toggle without also resetting the behavior enum), not something the attacker can set directly - the attacker only controls the PR content/labels and opens/reopens the PR. Given that precondition exists, exploitation is trivial and repeatable (open a labeled PR, or unlabeled PR for `prevent_with_label`) against any repo with that specific combination.

### Recommendation
Fix the operator-precedence bug in `OpenedHandler#provision?` and `ReopenedHandler#unarchive?` by wrapping the entire behavior check with `review_stacks_enabled` as a single top-level conjunct, mirroring `LabeledHandler`:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Additionally, as defense in depth, `ReviewStackProvisioningQueue.queued_stacks` should join `Repository` and filter on `review_stacks_enabled: true` so that the queue itself enforces the invariant regardless of how a stack was enqueued.

### Proof of Concept
Minitest plan (in `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` style):
```ruby
test "does not create/enqueue stacks when review_stacks_enabled is false, even with allow_with_label behavior" do
  repository = shipit_repositories(:shipit)
  repository.review_stacks_enabled = false
  repository.provisioning_behavior = :allow_with_label
  repository.provisioning_label_name = "pull-requests-label"
  repository.save!

  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  # Binding under test: repository.review_stacks_enabled == false  =>  no stack should be queued
  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Currently this assertion fails: `Shipit::Stack.count` increases by one, `ReviewStackProvisioningQueue.add` is invoked, `stack.awaiting_provision` becomes `true`, and a subsequent `ReviewStackProvisioningQueue.work` call would find the stack via `queued_stacks` and invoke `stack.provisioner.up`, demonstrating both halves of the broken equality (`review_stacks_enabled == false` on the repository vs. the stack still being provisioned by `.work`).
