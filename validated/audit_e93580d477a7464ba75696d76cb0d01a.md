### Title
Unauthorized `DepositDelegatorRewards` lets any signer inflate a victim vote account's locked-balance requirement, freezing the withdrawer's own funds - (File: `programs/vote/src/vote_state/mod.rs`)

### Summary
The `DepositDelegatorRewards` instruction (SIMD-0123) permits **any** account that can sign a lamport transfer to permissionlessly push lamports and increase the `pending_delegator_rewards` counter on **any** vote account, without any authorization check from that vote account's withdraw authority. This counter is later used as a hard floor in the `withdraw` instruction's balance check, meaning an unprivileged attacker can inflate the minimum balance a vote account must retain, freezing lamports that legitimately belong to the withdraw authority — the same "attacker manipulates a shared accounting denominator/counter to freeze victim funds" pattern described in the WatchPug report.

### Finding Description
`deposit_delegator_rewards` only requires the **source** account to be a signer; it performs no check that the caller controls or is authorized on the **vote account** being credited: [1](#0-0) 

Specifically, `verify_authorized_signer` is applied to `source_address` (the payer), not to the vote account's staker/withdrawer: [2](#0-1) 

The deposited amount is unconditionally added to `pending_delegator_rewards` via `add_pending_delegator_rewards`, which any caller can trigger for an arbitrary target vote account: [3](#0-2) 

This `pending_delegator_rewards` value is then used as a mandatory reserve that `withdraw` will not let the authorized withdrawer dip below: [4](#0-3) 

Concretely: if `remaining_balance == 0`, a full account close is rejected outright when `pending_delegator_rewards > 0`; otherwise the withdrawer must always keep `min_rent_exempt_balance + pending_delegator_rewards` in the account. Because an attacker can invoke `DepositDelegatorRewards` on the victim's vote account pubkey at will (limited only by the attacker's own lamports and `u64` overflow protection in `add_pending_delegator_rewards`), the attacker unilaterally raises this floor, locking lamports the withdraw authority previously could freely withdraw — without the withdraw authority's consent, and without ever becoming a vote-account signer.

This mirrors the WatchPug bug class: an external, unprivileged party performs a "donation" into a protocol accounting field it does not own, which is then used unconditionally as a denominator/floor in another party's math, degrading or freezing that party's ability to operate normally.

### Impact Explanation
The attack freezes lamports that legitimately belong to the vote account's withdraw authority (the validator operator), preventing withdrawal of a self-chosen amount and potentially blocking a full account close entirely (since `pending_delegator_rewards > 0` unconditionally blocks the zero-balance path). This is a griefing/DoS on a legitimate, unprivileged withdrawal path in the vote program's instruction handler, achievable by any address holding a small amount of lamports.

### Likelihood Explanation
High — the instruction is fully permissionless with respect to the target vote account (only the lamport source needs to sign), requires no special stake or validator role, and costs the attacker only the lamports they choose to deposit (which are not lost — they remain in the vote account and would eventually flow to delegators via the block-reward distribution path). The barrier to executing this griefing is therefore low; it is a single, cheaply repeatable transaction.

### Recommendation
Require that `DepositDelegatorRewards` either (a) be restricted to a designated/authorized depositor (e.g., the block-revenue collector or program-derived escrow), or (b) not extend the mandatory reserve enforced in `withdraw` unilaterally based on third-party deposits — e.g., track "reserve contributed by the withdrawer/collector" separately from arbitrary external deposits, or cap/rate-limit how much an unrelated party can inflate `pending_delegator_rewards` for a vote account they do not control.

### Proof of Concept
1. Attacker identifies a target vote account `V` with authorized withdrawer `W` and low `pending_delegator_rewards`.
2. Attacker submits `VoteInstruction::DepositDelegatorRewards { deposit: N }` with accounts `[V (writable), attacker_source (signer, writable), system_program]`, per the instruction's account-count check in `vote_processor.rs` (`instruction_context.check_number_of_instruction_accounts(2)?`) — no signature or authorization from `W` or `V` is required.
3. This transfers `N` lamports from the attacker into `V` and sets `pending_delegator_rewards += N` via `add_pending_delegator_rewards`.
4. `W` subsequently attempts to `withdraw` lamports from `V`; per the `withdraw` logic, `remaining_balance` must now exceed `min_rent_exempt_balance + pending_delegator_rewards`, which is `N` lamports higher than before the attacker's deposit — funds that `W` could previously withdraw are now locked, and if `W` attempts to close the account entirely, the close is rejected outright while `pending_delegator_rewards > 0`.

Note: I was unable to fully confirm within the available search budget whether/how `pending_delegator_rewards` is decremented after being paid out through `calculate_block_reward` during epoch reward distribution (I found the read/consumption path in `runtime/src/bank/partitioned_epoch_rewards/calculation.rs` lines 173-232, but did not locate an explicit subtraction of `pending_delegator_rewards` on the vote account after distribution). This affects whether the freeze is temporary (resolved as rewards are distributed each epoch) or could persist/duplicate reward payouts across epochs — this aspect would need direct code confirmation in a full Devin session before being escalated further.

pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}
