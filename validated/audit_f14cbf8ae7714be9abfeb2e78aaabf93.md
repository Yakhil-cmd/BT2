### Title
Unverifiable route bytes can conceal an unrelated wallet-token transfer beneath `swap_collateral` authorization - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary
A strategy route can invoke attacker-selected code during `swap_collateral`, and a token transfer performed by that code is represented as a child of the victim’s signed controller authorization. Because the controller treats `swap` as opaque bytes and only bounds the router’s controller-held input/output, a deceptive client can present an ordinary collateral swap while the simulated authorization tree includes an unrelated `token.transfer(victim, attacker, amount)`. If the victim signs that tree, the attacker receives the wallet token while the requested collateral swap still completes normally. [1](#0-0) [2](#0-1) 

### Finding Description
`process_swap_collateral` authenticates the caller and accepts arbitrary `StrategySwap` bytes for distinct collateral assets. [3](#0-2) 

`swap_tokens` forwards those bytes to the configured router after authorizing only the controller’s exact input-token transfer; it then checks controller balance deltas and positive output, but it does not inspect venue code or constrain token transfers made below the router against the original user. [4](#0-3) 

The harness demonstrates that an attacker-controlled hop pool invoked by route bytes can call `token::Client::transfer(victim, attacker, amount)`. [5](#0-4) 

During authorization recording, that transfer is attached as a sub-invocation of the victim’s `swap_collateral` entry; submitting the recorded tree makes the transfer execute and drains the unrelated token while crediting the expected swap output. [6](#0-5) 

Enforcement rejects the route when the victim signs only the honest root invocation, but the identical route succeeds when the simulated tree containing the theft is signed. [7](#0-6) 

### Impact Explanation
A malicious route can steal any unrelated token balance for which the crafted authorization includes a transfer, rather than limiting loss to the collateral amount routed through the swap. [8](#0-7) 

The proof-of-concept transfers the victim’s entire `77_770_000_000`-unit wallet-token balance to the attacker while delivering the fair `25_000_000` ETH output expected from the collateral swap. [8](#0-7) [9](#0-8) 

This is theft of user funds and is analogous to hiding critical transaction information behind a trusted-looking action. [10](#0-9) 

### Likelihood Explanation
An unprivileged attacker can deploy the malicious venue and supply its address inside the opaque route bytes used by `swap_collateral`; success additionally requires the victim’s client or wallet to submit a poisoned simulated authorization tree without clearly disclosing the unexpected child transfer. [11](#0-10) [12](#0-11) 

The route can still satisfy its declared output and final account-risk checks, so normal quote validation or a displayed collateral-swap summary does not reveal the unrelated wallet-token transfer. [13](#0-12) [9](#0-8) 

### Recommendation
Decode and display every authorization sub-invocation before signing, and reject a strategy authorization tree containing anything other than the explicitly expected protocol token pulls. [14](#0-13) 

At the protocol boundary, use an allowlist of vetted venues or replace opaque caller-supplied route programs with constrained route descriptors that cannot introduce arbitrary contract calls. [15](#0-14) 

### Proof of Concept
1. Deploy a fake pool whose `swap` method executes `token.transfer(victim, attacker, amount)` for a token unrelated to the lending markets. [5](#0-4) 
2. Encode route bytes that name that pool while retaining the expected `USDC -> ETH` swap input and minimum output. [16](#0-15) 
3. Have the victim call `controller.swap_collateral(alice, account_id, USDC, 50_000_000_000, ETH, route)`. [17](#0-16) 
4. Simulation records the fake pool’s wallet-token transfer as a child of the victim’s `swap_collateral` authorization. [12](#0-11) 
5. Signing the poisoned tree executes the route, leaves the victim with zero wallet-token balance and the attacker with `77_770_000_000`, while the victim’s account receives the expected ETH collateral. [9](#0-8) 
6. The control run proves the same route is refused when only the honest root authorization is signed, confirming that the decisive condition is concealment of the extra child authorization. [18](#0-17)

pub(crate) fn swap_tokens(
    env: &Env,
    refund_to: &Address,
    token_in: &Address,
    amount_in: i128,
    token_out: &Address,
    swap: &StrategySwap,

    require_positive_amount(env, amount_in);
    assert_with_error!(env, !swap.is_empty(), GenericError::InvalidPayments);

    let controller = env.current_contract_address();
    let router_addr = storage::get_swap_aggregator(env);
    let router = SwapAggregatorClient::new(env, &router_addr);
    let token_in_client = token::Client::new(env, token_in);

    // Snapshot before router execution to measure its spend and output.
    let in_before = token_in_client.balance(&controller);
    let out_before = token::Client::new(env, token_out).balance(&controller);

    // Authorize only this token transfer to this router for this exact amount.
    authorize_transfer_as_current(env, token_in, &controller, &router_addr, amount_in);

    storage::with_flash_guard(env, || {
        let _ = router.execute_strategy(&controller, &amount_in, swap);
    });

    // Reject input gains or overspending; refund only this swap's unused input.
    let in_after = token_in_client.balance(&controller);
    assert_with_error!(env, in_after <= in_before, StrategyError::RouterOverspend);
    let actual_spent = in_before - in_after;
    assert_with_error!(
        env,
        actual_spent <= amount_in,
        StrategyError::RouterOverspend
    );
    let leftover = amount_in - actual_spent;
    if leftover > 0 {
        token_in_client.transfer(&controller, refund_to, &leftover);
    }

    verify_router_output(env, token_out, out_before)
}

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}
