### Title
Webhook signature is verified against the organization derived from `repository.owner.login`, while every event handler resolves the target repository/stack from the independent, unverified `repository.full_name` field, allowing cross-tenant stack takeover in multi-organization deployments - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
In multi-organization Shipit deployments (`Shipit.github_organizations`, `github_app_config`), each tenant organization has its own `webhook_secret`. `WebhooksController#verify_signature` selects which secret to validate the HMAC signature against using `repository_owner`, taken from `params.dig('repository', 'owner', 'login')` [1](#0-0) [2](#0-1) . Every downstream `Handler` however resolves the repository/stack to act on from a *different* JSON field in the same untrusted payload: `payload.dig('repository', 'full_name')` [3](#0-2) . Nothing ties these two fields together, so signature validity for organization A does not guarantee that the event content actually belongs to organization A's repository.

### Finding Description
The binding that should hold is:
`organization whose webhook_secret validated the signature == organization that owns the repository the handler mutates`

In this codebase that binding is implemented as two separate, independently attacker-controlled reads of the same JSON body:

- Signature/organization selection: `Shipit.github(organization: repository_owner)` and `repository_owner = params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0) [2](#0-1) .
- Repository/stack resolution used by every handler (`PushHandler`, `MembershipHandler`, `PullRequest::OpenedHandler`, `LabeledHandler`, `ClosedHandler`, etc.): `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))` [3](#0-2) [4](#0-3) , and `Repository.from_github_repo_name` simply splits the string on `/` with no cross-check against `repository.owner.login` [5](#0-4) .

Multi-org support is real and active: `Shipit.github(organization:)` looks up a per-organization `GitHubApp` config, each with its own `webhook_secret`, via `github_app_config(organization)` [6](#0-5) , and `GitHubApp#verify_webhook_signature` HMACs the raw body against that org-specific secret [7](#0-6) . The included multi-app fixture `secrets_double_github_app.yml` demonstrates exactly this deployment shape (`OrgOne`, `OrgTwo`, each with distinct config).

Because a tenant that legitimately controls its own GitHub App installation (and therefore legitimately knows its own `webhook_secret`) can freely construct the JSON body it sends (whether via a real GitHub delivery from a repo they administer, or by directly POSTing a self-signed request, since they know the secret used to compute `X-Hub-Signature`), they can set:
- `repository.owner.login` = their own organization login (so `verify_signature` picks their own valid secret and the signature check passes),
- `repository.full_name` = `"victim-org/victim-repo"` (an entirely different tenant's repository).

`verify_signature` passes, `Webhooks.for_event(event).each { |handler| handler.call(params) }` runs, and the handler acts on the victim's `Repository`/`Stack`, e.g.:
- `PushHandler#process` finds the victim's non-archived stacks matching `branch` and calls `stack.sync_github(expected_head_sha: params.after)`, driving deploy-relevant sync state for a repository the attacker doesn't own [8](#0-7) .
- `PullRequest::OpenedHandler`/`LabeledHandler`/`ClosedHandler` create, archive, or unarchive `ReviewStack`s scoped to the victim's `repository.review_stacks` [9](#0-8) [10](#0-9) .

### Impact Explanation
This breaks the organization-authenticated ↔ repository-written binding and results in cross-repository/cross-tenant writes on stacks the attacker does not administer: forged pushes triggering `sync_github`, forced archive/unarchive of review stacks, and creation of `PullRequest`/`ReviewStack` records for a victim organization's repository — all while only holding credentials for the attacker's own unrelated tenant. This matches the "Critical - cross-repository writes" impact bucket in scope.

### Likelihood Explanation
Requires the attacker to be a legitimate admin of some organization/GitHub App installation configured on the same shared Shipit instance (i.e., a valid multi-tenant `webhook_secret`) but with no access whatsoever to the victim organization/repository. This is a realistic configuration for any Shipit instance serving multiple GitHub orgs, as evidenced by the shipped `secrets_double_github_app.yml` example. No GitHub App private key, `api_clients_secret`, or session is needed — only the ability to legitimately trigger (or self-sign) a webhook delivery for the attacker's own tenant while spoofing the `repository.full_name` field.

### Recommendation
Bind the two checks together: derive the organization used for stack/repository resolution from the same verified source used for signature validation (e.g., require `repository.full_name.split('/').first.casecmp?(repository_owner)` before dispatching to handlers), or resolve the target `Repository` via the verified `repository_owner` value rather than trusting `full_name` independently. Reject the webhook (422) if the two do not match.

### Proof of Concept
1. Attacker administers `attacker-org`, which has a legitimate GitHub App installation on this shared Shipit instance with `webhook_secret = S`.
2. Attacker crafts a `push` payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker chosen sha>",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org" }
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(S, raw_body)` themselves (they know `S`), sets `X-Github-Event: push`, and POSTs to `/github/webhooks`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")` and successfully verifies the signature against `S` [1](#0-0) .
5. `PushHandler#process` resolves `stacks` from `full_name = "victim-org/victim-repo"` via `Handler#stacks`/`Repository.from_github_repo_name` [3](#0-2) [5](#0-4)  and calls `stack.sync_github` on the victim's stack — despite the attacker never having authenticated as or being authorized for `victim-org`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
