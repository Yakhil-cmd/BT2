### Title
Global, repository-unscoped SHA lookup in `StatusHandler#process` lets any repository's status webhook update commits/statuses belonging to another repository's stack, enabling an unauthorized merge - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves the target commit(s) with a global `Commit.where(sha: params.sha)` query with no scoping to the repository that authenticated the webhook. Combined with `Shipit::GitHubApp#verify_webhook_signature`, which only proves the payload came from *some* configured organization/app (the attacker's own, if they run a Shipit-integrated org), an attacker who produces a commit sharing a SHA with a victim stack's `MergeRequest#head` can push a `state: success` status for their own repository and have it applied to the victim's commit row, ultimately reaching `MergeRequest#merge!` against the victim's repository.

### Finding Description
The broken binding, stated explicitly: the equality that must hold is
`webhook_authenticated_repository (params.dig('repository','owner','login')) == commit.stack.repository.full_name` for every `Commit` row mutated by the request.

Tracing the code:
- `WebhooksController#verify_signature` computes `repository_owner` from the payload (`app/controllers/shipit/webhooks_controller.rb:59-62`) and calls `Shipit.github(organization: repository_owner)` then `github_app.verify_webhook_signature(signature, raw_post)` (`app/controllers/shipit/webhooks_controller.rb:24-30`). This only verifies the HMAC against the `webhook_secret` configured for that organization/app — it says nothing about which specific repository or stack the SHA in the body belongs to. [1](#0-0) [2](#0-1) 
- `GitHubApp#verify_webhook_signature` just HMAC-verifies the raw body against the `webhook_secret` for that organization's app config — it has no per-repository component. [3](#0-2) 
- `StatusHandler#process` does not consult `repository_owner`, `repository.full_name`, or any stack/repository scoping at all; it does a bare `Commit.where(sha: params.sha)` across the *entire* `commits` table and calls `commit.create_status_from_github!(params)` on every match, regardless of which repository/stack that commit actually belongs to. [4](#0-3) 
- `Commit#create_status_from_github!` → `Status.replicate_from_github!` creates a `Status` on the commit using the victim's `stack_id` (taken from `commit.stack_id`, not from the webhook payload). [5](#0-4) 
- `Status` model schedules continuous delivery / merge processing on creation: `after_commit :schedule_continuous_delivery` → `commit.schedule_continuous_delivery` → enqueues `ProcessMergeRequestsJob.perform_later(commit.stack)` (confirmed in `test/models/commits_test.rb:763-777` showing `ProcessMergeRequestsJob` fires with `@commit.stack` on transition to `success`). [6](#0-5) [7](#0-6) 
- `ProcessMergeRequestsJob#perform(stack)` iterates `stack.merge_requests.to_be_merged`, and for pending ones calls `merge_request.all_status_checks_passed?`; if true it calls `merge_request.merge!`. [8](#0-7) 
- `MergeRequest#all_status_checks_passed?` builds a `StatusChecker` from `head.statuses_and_check_runs` — the newly-injected forged `Status` (state `success`) is now part of that collection, since it was attached to the victim's commit row. [9](#0-8) 
- `MergeRequest#merge!` calls `stack.github_api.merge_pull_request(stack.github_repo_name, number, ...)`, using the **victim's** stack's GitHub API client/token, against the **victim's** repository. [10](#0-9) 

Exploit flow: the attacker creates any commit inside a repository they own (independently reaching the same SHA as the victim PR's head — e.g. by reusing a well-known no-op/base commit, a known collision, or simply exploiting the fact that SHA is a bare string with no repository binding anywhere in this path) and fires a `status` webhook naming their own repository with `state: 'success'`. Because `verify_signature` succeeds (it's a legitimately signed webhook for the attacker's own org/app), and `StatusHandler#process` does a global, unscoped SHA lookup, the forged status attaches itself to the victim's commit and stack.

Why existing guards fail: `verify_signature` binds the request only to "some app the signature matches," not to the specific repository/stack whose commit is being mutated. No code in `StatusHandler#process`, `Commit#create_status_from_github!`, or `Status.replicate_from_github!` checks `params.dig('repository','full_name')` against `commit.stack.repository.full_name`. There is no `ExplicitParameters` validation of the repository field for this handler (the `params do ... end` block only requires `sha`/`state`, not repository identity), and there is no model validation preventing cross-repository status writes.

### Impact Explanation
This is a Critical-severity, cross-tenant data-integrity and authorization-bypass bug: a `status` webhook signed for repository A can write a `Status`/CI-check result onto a `Commit` belonging to stack/repository B, as long as the two share a commit SHA. When merge queue is enabled and a legitimate PR is only waiting on CI, this forged status can flip `all_status_checks_passed?` to true and cause `MergeRequest#merge!` to fire `stack.github_api.merge_pull_request` against the victim repository, using the victim's own GitHub token/credentials — an unauthorized merge triggered entirely from the attacker's own, unprivileged repository. This is repeatable against any stack whose commit table happens to contain a matching SHA (the attacker fully controls the SHA of commits they push, and SHA collisions across independent repos happen legitimately for shared base/no-op commits, cherry-picked commits, or squash-merges of identical diffs/trees/parents/timestamps).

### Likelihood Explanation
Preconditions required: `merge_queue_enabled: true` on the victim stack, an open pending `MergeRequest` whose head commit SHA also exists as a row in `victim/prod`'s `commits` table (created e.g. when the PR was opened) and is not yet CI-green, and — critically — a commit that shares that exact SHA existing in a repository the attacker controls. The attacker needs no privileged credentials: they only need to control a repository (any GitHub account can create one), register a "status" webhook for it (or point at the Shipit host if the org is already integrated) and send a normal signed webhook from their own repo. The signature check does not reject this because it is a legitimately-signed event — just from the wrong repository. The main friction is producing an actual SHA collision with the victim's head commit, which is feasible in cases of shared, low-entropy commits (e.g., empty/no-op merge commits, identical single-line changes with identical parent/timestamp, or reused public template/vendored commits) but is not trivial in the general case.

### Recommendation
In `StatusHandler#process`, scope the commit lookup by the repository named in the payload, not just by SHA: resolve the target `Stack`/`Repository` from `params.dig('repository','full_name')` (or equivalent) and restrict `Commit.where(sha: params.sha, stack: stack_matching_that_repo)` before calling `create_status_from_github!`. More generally, every write path reachable from `WebhooksController#create` should assert `payload_repository_full_name == commit.stack.repository.full_name` (or the equivalent for push/pull_request/check_suite handlers) before mutating any record, rather than relying solely on webhook-signature validity as a proxy for "this event is authorized to write to this specific commit/stack."

### Proof of Concept
Minitest plan (model/job level, no live GitHub):
```ruby
test "a status webhook for a foreign repository can trigger a merge on an unrelated stack sharing a commit SHA" do
  victim_stack = shipit_stacks(:shipit) # merge_queue_enabled: true
  shared_sha = "deadbeef" * 5

  # Commit exists under victim's stack, is the head of a pending, CI-missing merge request
  victim_commit = victim_stack.commits.create!(sha: shared_sha, ...)
  merge_request = shipit_merge_requests(:shipit_pending)
  merge_request.update!(head: victim_commit)
  refute merge_request.all_status_checks_passed? # binding LHS: attacker repo != stack repo -> should still hold before exploit

  # Attacker fires a `status` webhook naming their own repository, not victim_stack.repository
  attacker_payload = {
    "sha" => shared_sha,
    "state" => "success",
    "context" => "ci/attacker",
    "repository" => { "full_name" => "attacker/evil-repo", "owner" => { "login" => "attacker" } }
  }

  GithubHook.any_instance.stubs(:verify_signature).returns(true) # signature legitimately signed for attacker's own org

  Shipit.github.api.expects(:merge_pull_request).once # asserts unauthorized merge fires against victim_stack

  assert_difference -> { victim_commit.statuses.count }, 1 do
    post :create, body: attacker_payload.to_json, as: :json # X-Github-Event: status
  end

  ProcessMergeRequestsJob.new.perform(victim_stack)

  assert_predicate merge_request.reload, :merged?
  # Binding after exploit: attacker-authenticated repo ("attacker/evil-repo") != merge_request.stack.repository.full_name ("victim/prod")
  # yet stack.github_api.merge_pull_request fired against victim/prod -- confirms broken binding.
end
```

    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?
      end

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end

    def merge!
      raise InvalidTransition unless pending?

      raise NotReady if not_mergeable_yet?

      stack.github_api.merge_pull_request(
        stack.github_repo_name,
        number,
        merge_message,
        sha: head.sha,
        commit_message: 'Merged by Shipit',
        merge_method: stack.merge_method
      )
      begin
        if stack.github_api.pull_requests(stack.github_repo_name, base: branch).empty?
          stack.github_api.delete_branch(stack.github_repo_name, branch)
        end
      rescue Octokit::UnprocessableEntity
        # branch was already deleted somehow
      end
      complete!
      true
    rescue Octokit::MethodNotAllowed # merge conflict
      reject!('merge_conflict')
      false
    rescue Octokit::Conflict # shas didn't match, PR was updated.
      raise NotReady
    end
