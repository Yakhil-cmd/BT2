## Analysis

This confirms a valid, exploitable analog: `Shipit.github(organization:)` supports multi-tenant configuration keyed by GitHub organization login [1](#0-0) , and `WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate the HMAC signature against based on an **attacker-controlled, unverified field** (`repository.owner.login` / `organization.login`) taken from the raw JSON body itself, before the signature has been checked [2](#0-1) . Once the signature passes, `create` re-parses the same raw body and dispatches to handlers that key off a *different* field, `repository.full_name` (or `organization.login`, `team`, `sha`, `ref`, etc.), which GitHub's real payload always keeps consistent with `repository.owner.login`, but nothing in this engine enforces that consistency [3](#0-2) .

## Title
Webhook signature is verified against the organization named in an unverified payload field, while handlers act on a different repository/organization field from the same unverified body - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks the `GitHubApp` (and thus the `webhook_secret` used for HMAC verification) using `repository_owner`, which is read directly out of the untrusted, not-yet-verified JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`). The `create` action then processes the event using other fields from that same untrusted body (e.g. `repository.full_name`, `organization.login`, `sha`) via the registered handlers. Because Shipit can be configured to serve multiple GitHub organizations (`Shipit.github(organization:)`), an attacker who is an authenticated admin of *any one* organization configured on the same Shipit instance knows that organization's `webhook_secret` and can forge a payload where the "authenticating" field points to their own org (so signature verification passes) while the "acted-upon" field points to a victim org/repository configured on the same instance.

### Finding Description
The binding that should hold is: `organization whose webhook_secret authenticated the request == organization/repository the handler writes to`. Before the fix would be needed, GitHub always sends payloads where `repository.owner.login` and `repository.full_name`'s owner segment (and `organization.login`) are consistent, so this binding holds implicitly. But the webhook endpoint is unauthenticated by design (protected only by HMAC) and accepts arbitrary POST bodies [4](#0-3) . `verify_signature` computes `repository_owner` and calls `Shipit.github(organization: repository_owner)` to fetch the app config/secret for that org, then verifies the raw body's signature against it [5](#0-4) , and `GitHubApp#verify_webhook_signature` performs a straightforward HMAC compare with no binding of the *content* of the payload's other fields to the chosen secret [6](#0-5) .

Once verification passes, `create` dispatches the full parsed body to handlers such as `PushHandler` (acts on `params.ref`/`params.after` to sync stacks) [7](#0-6) , `MembershipHandler` (creates/updates `Team`/`User` records and team membership keyed on `params.organization.login`) [8](#0-7) , and the pull-request handlers (look up repositories/stacks via `params.repository.full_name`, archiving/unarchiving review stacks) [9](#0-8) . None of these re-derive or cross-check the organization/repository against the one used for signature selection. The two values are extracted from independent JSON paths in the same body (`repository.owner.login` vs. `repository.full_name`/`organization.login`), so an attacker fully controls both and can decouple them.

### Impact Explanation
On a multi-tenant Shipit deployment (multiple orgs configured under `secrets.github`), an attacker who administers one onboarded organization (and thus knows/controls its GitHub App `webhook_secret`) can forge signed-looking webhook requests that are authenticated as "their org" but whose payload content (`repository.full_name`, `organization.login`, commit `sha`, branch `ref`, team membership) targets a different, victim organization/repository hosted on the same instance. Depending on handler, this can: add arbitrary users to a victim `Team` (impacting `Shipit.github_teams` authorization used by `Authentication#force_github_authentication` to grant application access) [10](#0-9) [11](#0-10) ; force `sync_github`/branch state changes on a victim stack via `PushHandler`; or archive/unarchive victim review stacks. This maps to the "High: escalation into `Shipit.github_teams` authorization" impact category, since forged `membership` events can grant an attacker (or an accomplice) access to a victim's protected Shipit application.

### Likelihood Explanation
Requires the Shipit instance to be configured for more than one GitHub organization and the attacker to control/administer one of those organizations' webhook secret (i.e., they are a legitimate but hostile tenant) — this is a realistic scenario for shared/hosted Shipit deployments. No repository write access, GITHUB_TOKEN, or `ApiClient` token is required; the only requirement is knowledge of one organization's own `webhook_secret`, which that organization's admin necessarily has.

### Recommendation
Cross-validate that all organization/repository identifiers used by the dispatched handlers are consistent with the organization whose secret authenticated the request. Concretely, in `WebhooksController#verify_signature`/`create`, after resolving `repository_owner`/`organization` and verifying the signature, re-derive `repository_owner` from the same trusted value and reject the request (422) if `params.dig('repository','full_name')`'s owner segment or `params.dig('organization','login')` does not match the organization used to select the `webhook_secret`.

### Proof of Concept
1. Shipit is configured with two orgs, e.g. `secrets.github: { attacker_org: {...}, victim_org: {...} }`.
2. Attacker (a legitimate GitHub org admin of `attacker_org`) knows `attacker_org`'s `webhook_secret`.
3. Attacker POSTs to `/webhooks` with header `X-Github-Event: membership` and a body:
```json
{
  "action": "added",
  "team": {"id": 1, "name": "core", "slug": "core", "url": "https://x"},
  "organization": {"login": "victim_org"},
  "member": {"login": "attacker-controlled-user"},
  "repository": {"owner": {"login": "attacker_org"}, "full_name": "attacker_org/dummy"}
}
```
4. `verify_signature` computes `repository_owner` = `"attacker_org"` (from `repository.owner.login`), fetches `attacker_org`'s `GitHubApp`, and verifies the HMAC using the secret the attacker knows — verification succeeds [12](#0-11) .
5. `create` dispatches to `MembershipHandler`, which reads `params.organization.login` = `"victim_org"` and `params.member.login`, creating/associating a `Team` scoped to `victim_org` and adding the attacker-controlled user as a member [8](#0-7) .
6. If `victim_org`'s team is one referenced by `Shipit.github_teams`, the attacker-controlled user now satisfies `User#authorized?` and gains access to the victim's Shipit application [13](#0-12) .

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
