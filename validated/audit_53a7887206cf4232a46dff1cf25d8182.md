## Finding

### Title
Unhandled exception in AA-trigger processing permanently locks the global `aa_triggers` mutex, freezing all AA execution - (File: aa_composer.js)

### Summary
`handleAATriggers()` acquires a single global mutex key `['aa_triggers']` and then iterates every pending trigger with `async.eachSeries`, calling `handlePrimaryAATrigger()` for each row and only releasing the mutex when the series' final callback fires [1](#0-0) . Inside `handlePrimaryAATrigger()`, the completion callback that finalizes a trigger's DB write is an `async` function that is invoked as a bare callback to `conn.query(...)` — its return value/rejection is neither awaited nor wrapped in a `try/catch`, and it contains an unguarded `throw` [2](#0-1) . If that `throw` fires (e.g. `throw Error("handlePrimaryAATrigger: unit ... not found in cache")` or `throw Error("AA composer: batch write failed: "+err)`), the `async.eachSeries` callback `cb` for that row is never invoked, so the series never completes, `unlock()` is never called, and the `aa_triggers` mutex key stays locked for the remaining lifetime of the process.

### Finding Description
`handleAATriggers` is the single choke point that executes every AA trigger network-wide, whether triggered by a stabilizing MCI in `main_chain.js` or `writer.js` [3](#0-2) [4](#0-3) . It is guarded by `mutex.lock(['aa_triggers'], ...)`, and this mutex implementation only releases a lock when the caller explicitly invokes the `unlock` callback passed to `proc` [5](#0-4) . There is no timeout, watchdog, or `finally`-style guarantee that `unlock()` runs.

Within `handlePrimaryAATrigger`, after the trigger's response is computed, the code deletes the row from `aa_triggers`, updates counters, and writes the AA batch — all inside a nested chain of callbacks, one of which is declared `async function(){...}` and directly performs `throw Error(...)` on two internal-invariant checks (cache miss, batch write failure) without any surrounding `try/catch` [6](#0-5) . Because this function is used purely as a fire-and-forget callback (its returned promise is never `.then()`/`.catch()`'d by `conn.query`), a `throw` inside it becomes an unhandled promise rejection rather than being routed to the `cb(err)` error-propagation pattern used everywhere else in this same file (e.g. the `sendUnit` message loop routes errors through `cb(err)` into `bounce()` [7](#0-6) ). This is inconsistent with the rest of the AA composer's defensive error handling and leaves this one path unprotected.

Once this occurs, `async.eachSeries`'s final callback in `handleAATriggers` (which calls `unlock()` and `onDone()`) never runs [8](#0-7) . Every subsequent call to `handleAATriggers()` — triggered by every future MCI stabilization anywhere on the network — queues behind the permanently-held `aa_triggers` key and never executes, because `mutex.lock` simply queues jobs whose keys are locked and only drains the queue from inside `unlock()` [9](#0-8) .

### Impact Explanation
Because `aa_triggers` is a single global mutex key shared by all AA execution paths, a single stuck trigger permanently halts AA processing for the entire node: no further AA responses are computed, no AA-issued units are created, and payments sent to any AA address are left unprocessed indefinitely (funds effectively frozen inside AAs, and dependent triggers/timers/contracts never fire). Unlike the top-level `network.js` `process.on('uncaughtException')` handler, which is designed for synchronous throws inside the main event-loop stack and intentionally crashes the process to avoid inconsistent state [10](#0-9) , a rejection from a detached `async` callback does not go through that path — it surfaces (if at all) as an unhandled rejection warning, and the process can keep running with AA execution permanently disabled, mirroring the DNS-over-QUIC bug class where a listener silently stops functioning while the rest of the server continues.

### Likelihood Explanation
The trigger condition requires a legitimate-looking payment/trigger to an AA address that causes `storage.assocStableUnits[unit]` to be missing at the exact moment the completion callback runs, or a batch-write failure to the underlying key-value store. Both are internal invariant checks rather than externally-supplied fields, so triggering them reliably from a remote, unprivileged unit poster requires further work to identify the exact state-cache race or storage condition; nonetheless, the reachability (any AA trigger sender) and the complete absence of error handling on this path make the defect concretely exploitable once such a condition is found, and it is reachable purely by posting payments to AA addresses — no special privilege required.

### Recommendation
Wrap the `async function` callback in `handlePrimaryAATrigger` (aa_composer.js lines 102-114) in `try/catch`, routing any failure through the existing `onDone`/`cb(err)` pattern so `async.eachSeries` in `handleAATriggers` always completes and `unlock()` is always reached, e.g. by calling a `cb(err)`-style continuation instead of `throw`, and by adding a global `process.on('unhandledRejection', ...)` handler consistent with the existing `uncaughtException` handler so that any such failure surfaces the same fail-fast/restart behavior instead of silently wedging the mutex.

### Proof of Concept
1. Post any unit whose payment/message targets a valid AA address so a row is inserted into `aa_triggers`.
2. Cause `storage.assocStableUnits[unit]` to be absent when the trigger's stabilization completion callback runs (or force the RocksDB `batch.write` call to error), so the `throw` at aa_composer.js line 106 or 114 fires inside the un-awaited `async` callback.
3. Observe that `handleAATriggers`'s `async.eachSeries` final callback (and thus `unlock()`) never executes; the `aa_triggers` mutex key remains locked forever.
4. Send further units triggering other/different AAs and confirm they are queued and never processed — all future AA execution on the node is permanently stalled without any explicit crash.

function handleQueue(){
	console.log("handleQueue "+arrQueuedJobs.length+" items");
	for (var i=0; i<arrQueuedJobs.length; i++){
		var job = arrQueuedJobs[i];
		if (isAnyOfKeysLocked(job.arrKeys))
			continue;
		arrQueuedJobs.splice(i, 1); // do it before exec as exec can trigger another job added, another lock unlocked, another handleQueue called
		console.log("starting job held by keys", job.arrKeys);
		exec(job.arrKeys, job.proc, job.next_proc);
		i--; // we've just removed one item
	}
	console.log("handleQueue done "+arrQueuedJobs.length+" items");
}
