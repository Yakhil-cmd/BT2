## Analysis: Analog to "Uber Owner has too much power" in ocore

The strongest analog in `ocore--002` is the **asset definer's unilateral, unchecked power over the attestor list of a `spender_attested` asset**, which functions much like the Reality Cards `UberOwner`: a single address created once at issuance can later completely rewrite spending eligibility for a live asset, with no timelock, multisig requirement, or restriction on what changes are permitted.

### Title
Asset definer can unilaterally rewrite the attestor list of a live `spender_attested` asset, permanently freezing holder funds - (File: `validation.js`)

### Summary
When an asset is defined with `spender_attested: true`, only the `definer_address` (the original issuer/poster of the `asset` message) may publish `asset_attestors` updates that completely replace the list of addresses whose attestation is required to spend the asset. This power is permanent, unbounded, and requires no consensus beyond a single signature from the definer, mirroring the `UberOwner` centralization risk: one address effectively controls who may transact in an asset for its entire lifetime.

### Finding Description
`validateAttestorListUpdate` only checks that the single author is `objAsset.definer_address` and that the new attestor list is well-formed (sorted, non-empty, under the size cap); it imposes no restriction on the *content* of the change, no cooldown, and no way for holders to object: [1](#0-0) 

`checkAttestorList` validates only formatting, not any policy constraint: [2](#0-1) 

`storage.readAsset`/`addAttestorsIfNecessary` always resolves to the *latest* attestor-list unit at the current last-ball MCI, so a fresh `asset_attestors` message from the definer instantly supersedes the old list for all future validation of that asset: [3](#0-2) 

Payment validation for a `spender_attested` asset checks the sender against the *current* attested-address set, not the set that existed when the sender received the funds: [4](#0-3) 

Consequently, the definer can, at will and without any counterbalance, drop existing attestors (thereby de-attesting every holder who relied on them) and add only self-controlled attestors — unilaterally deciding who can spend the asset going forward, exactly as `UberOwner` could unilaterally rewrite protocol rules in the referenced report.

### Impact Explanation
Any holder of a `spender_attested` asset can be permanently frozen out of spending their balance the moment the definer republishes the attestor list, since attestation status is evaluated against the live list rather than the list in effect at receipt time. This is a concrete "AA/asset fund freezing" outcome: legitimately-held asset balances become permanently unspendable at the sole discretion of one address, and the definer can simultaneously grant itself/colluding addresses continued spend rights — a supply-control/censorship capability functionally identical to the disputed `UberOwner` risk (single key compromise or malice rewrites the rules governing everyone's funds).

### Likelihood Explanation
Any unprivileged user can define such an asset (this is a standard, intended feature: `issued_by_definer_only`/`spender_attested` assets are commonly created by ordinary asset issuers, not privileged operators). No special permission beyond being the original definer is required to later "rug" holders via `asset_attestors`; the action is a normal validated message type reachable by any asset issuer at any time after issuance.

### Recommendation
- Evaluate spender attestation against the attestor list that was current when the payer's balance was received (or introduce a required delay/versioning window), rather than always using the newest list.
- Consider requiring holder-visible commitments (e.g., a minimum notice period before an attestor-list change takes effect) so that funds cannot be frozen retroactively/instantly.
- Document and/or enforce (e.g., via `r of set`/multisig authentifiers on the definer address) that `asset_attestors` updates for security-sensitive assets should require multi-party authorization rather than a single definer signature.

### Proof of Concept
1. Definer posts an `asset` message with `spender_attested: true`, `attestors: [A]` (validated per `validation.js:2725-2827`).
2. Users receive/hold the asset while attested by `A`.
3. Definer later posts an `asset_attestors` message for the same asset with `attestors: [B]` where `B` only attests the definer's own address (validated solely by `validateAttestorListUpdate`, `validation.js:2829-2848`).
4. `storage.readAsset` now resolves the latest attestor list to `[B]` (`storage.js:1917-1946`).
5. Any prior holder attempting to spend now fails `objAsset.arrAttestedAddresses.indexOf(issuer_address) === -1` (`validation.js:2115-2122`) — their funds are permanently frozen, while the definer/colluding address remains free to transact.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}

function checkAttestorList(arrAttestors){
	if (!isNonemptyArray(arrAttestors))
		return "attestors not defined";
	if (arrAttestors.length > constants.MAX_ATTESTORS_PER_ASSET)
		return "too many attestors";
	var prev="";
	for (var i=0; i<arrAttestors.length; i++){
		if (!isValidAddress(arrAttestors[i]))
			return "invalid attestor address: "+JSON.stringify(arrAttestors[i]);
		if (arrAttestors[i] <= prev)
			return "attestors not sorted";
		prev = arrAttestors[i];
	}
	return null;
}
