### Title
Commit-status webhook handler writes statuses by SHA only, without checking they belong to the organization/repository whose signature was verified - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App / webhook secret to check the HMAC signature against the *organization named in the payload's `repository.owner.login`* (or `organization.login`) field [1](#0-0) , and that organization is derived exactly the same way the handler later resolves "which repo does this event belong to" would need to [2](#0-1) . However, `StatusHandler`, which processes GitHub `status` events, never uses the repository field at all when deciding which local `Commit` rows to mutate — it queries by raw SHA across the entire `commits` table: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [3](#0-2) . The base `Handler` class does expose a `repository_name`/`stacks` helper scoped by `payload.dig('repository', 'full_name')` [4](#0-3) , but `StatusHandler` does not call it — unlike `PushHandler`, which does scope its writes through `stacks` [5](#0-4) .

### Finding Description
The trust binding the signature check is supposed to establish is: *"the organization whose webhook secret validated this payload" == "the organization/repository whose data gets mutated by this payload."* `verify_signature` enforces the left-hand side using `repository_owner` pulled straight out of the JSON body [2](#0-1) . But `StatusHandler#process` never re-checks that the `Commit` rows it's about to update actually belong to that same repository/organization — it matches purely on the git SHA string, which is a content-addressed value that is not unique per-repository (e.g. two Shipit-tracked repos that share history through a fork/mirror relationship, or repos created from the same template with an unmodified initial commit, will contain identical SHAs).

Consequently, a status event that is cryptographically valid for organization/repo A can end up calling `commit.create_status_from_github!(params)` on `Commit` records belonging to a completely different repository/stack (and potentially a different GitHub organization with its own, unrelated webhook secret), simply because that other repo happens to contain a commit with the same SHA.

### Impact Explanation
`Commit` statuses populated this way feed directly into merge-queue gating logic: `MergeRequest#all_status_checks_passed?` builds a `StatusChecker` from `head.statuses_and_check_runs` [6](#0-5) , which controls whether a pull request is eligible for automatic merge. An attacker who only has commit-status write privileges on one repository (Repo A) — a privilege far short of write access to the target repository (Repo B) — could, if Repo B shares a commit SHA with Repo A (fork/mirror/shared-template scenario), forge/replay a legitimately-signed `status` webhook for Repo A that Shipit will apply to the shared commit inside Repo B's stack, marking required CI checks as `success` and enabling `MergeRequest#merge!` to proceed on Repo B. This is a cross-repository write that can lead to an unauthorized merge, matching the "cross-repository writes / unauthorized merge" Critical impact category.

### Likelihood Explanation
This requires a real, but not rare, precondition: two Shipit-tracked repositories sharing at least one commit SHA (forks, repository splits, or repos bootstrapped from an identical template/boilerplate commit are common in real organizations), plus the attacker having legitimate commit-status write access on only one of them. Given that precondition, no additional privilege escalation is needed — the webhook signature check passes normally because it is validated against the correct (attacker-controlled) organization; the flaw is purely that `StatusHandler` never confirms the target commit's repository matches the payload's repository.

### Recommendation
Scope `StatusHandler`'s lookup by repository, not just by SHA — e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or joining through `Repository.from_github_repo_name(repository_name)` (the same helper `Handler#stacks` already provides) before calling `create_status_from_github!`, so a verified webhook can only mutate commits that actually belong to the repository named (and cryptographically bound) in that same payload.

### Proof of Concept
1. Shipit tracks two repositories: `org-a/repo` (forked from) and `org-b/repo` (the fork), both sharing the initial commit SHA `abc123...` because history hasn't diverged at that commit yet.
2. Attacker has collaborator access to `org-a/repo` sufficient to set a commit status (a normal, legitimate GitHub permission, not a Shipit credential).
3. Attacker sets a `success` status on commit `abc123...` in `org-a/repo` via the GitHub API; GitHub delivers a `status` webhook to Shipit, signed with `org-a`'s configured `webhook_secret`.
4. `WebhooksController#verify_signature` validates the signature against `org-a`'s secret and passes [1](#0-0) .
5. `StatusHandler#process` runs `Commit.where(sha: 'abc123...')`, which also matches the `Commit` row belonging to `org-b/repo`'s stack, and calls `create_status_from_github!` on it [3](#0-2) .
6. `org-b/repo`'s merge-queue `StatusChecker` now sees a forged `success` status for a required check, potentially allowing `MergeRequest#merge!` to merge a PR the attacker had no write access to.
