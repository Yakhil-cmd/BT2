## Title
Webhook signature verification authenticates the sending GitHub organization but not the repository field used to route the event, allowing cross-tenant forged webhooks - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
Shipit supports multi-tenant GitHub App configuration, where each organization has its own `webhook_secret` [1](#0-0) . The `WebhooksController` picks which organization's secret to verify the signature against by reading an **unauthenticated** field from the JSON body (`repository.owner.login` / `organization.login`), then verifies the raw body's HMAC against that one org's secret [2](#0-1) . Once the signature check passes, every downstream handler independently re-reads a *different* field of the same attacker-controlled JSON body — `repository.full_name` — to resolve which `Stack`/`Repository` the event applies to, via `Handler#repository_name` and `Repository.from_github_repo_name` [3](#0-2) [4](#0-3) . Nothing ties the field used for signature-org-selection (`repository.owner.login`) to the field used for repository resolution (`repository.full_name`) — they are simply two independent JSON keys the attacker fully controls in the raw POST body that the signature covers, but the signature itself only proves "this body was sent by someone who knows Org A's secret," not "the org fields inside this body are self-consistent."

### Finding Description
This is the same "check performed on the wrong side of the binding" class as the reported `depositRequest()` bug: the cap check was evaluated using post-deposit `liquidity` instead of the pre-deposit deposit amount, so the check and the effect it was meant to gate were bound to different values. Here, the signature verification is bound to `repository_owner` (the value used to pick the HMAC secret), but the security-relevant effect — which `Stack`/`Repository` a job processes — is bound to a separate, unauthenticated field, `repository.full_name`.

Concretely, an operator/admin of Organization A in a multi-tenant Shipit install legitimately knows Org A's `webhook_secret` (they configured GitHub's webhook secret themselves when installing the GitHub App for their own org — this is standard setup, not privileged access to Shipit or to any other org). Using that secret, they can:

1. Compute a valid `X-Hub-Signature` HMAC over an arbitrary JSON body they construct.
2. Set `repository.owner.login` (or `organization.login`) to `"org-a"` so `verify_signature` selects Org A's `GithubApp` and the signature check passes [5](#0-4) .
3. Set `repository.full_name` to `"org-b/victim-repo"` — a repository belonging to a completely different, unrelated tenant of the same Shipit instance.
4. POST this to the shared `/github/webhooks` endpoint (there is one endpoint for all orgs, not one per org).

`verify_signature` passes because the HMAC is valid for Org A's secret over the exact bytes sent [6](#0-5) . The `create` action then dispatches to handlers for the claimed event [7](#0-6) , and those handlers resolve the target purely from `repository.full_name`:

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

`Repository.from_github_repo_name` does a case-insensitive DB lookup with no further ownership check [4](#0-3) , so it will happily resolve to `org-b/victim-repo`'s `Stack`(s), which belong to a different, unrelated tenant that the attacker has no legitimate relationship with.

This breaks exactly the binding called out in the rules: *"an organization that authenticated versus the repository that is written."* The signature authenticates "Org A sent this," but the code acts on "whatever repository the body claims," and those two are never checked against each other.

### Impact Explanation
Depending on which webhook event/handler is targeted, this enables cross-tenant, cross-repository effects on a victim stack the attacker does not own or administer:
- `push` events enqueue `GithubSyncJob` for the victim stack, which fetches commits via the victim's own GitHub App credentials/config and can trigger `stack.lock_reverted_commits!`, spec cache rebuilds, etc. [8](#0-7) 
- `status` / `check_suite` events can inject fabricated commit statuses/check-run states for a victim commit [9](#0-8) , which feed directly into `Commit#deployable?` and the merge-queue's `all_status_checks_passed?` gate, potentially causing the merge queue to `merge!` a pull request that hasn't actually passed CI [10](#0-9)  — i.e., an unauthorized merge on a repository the attacker doesn't control.
- `pull_request` events routed through review-stack handlers can archive/unarchive or provision review stacks for a victim repository [11](#0-10) .

This matches the "cross-repository writes" / "unauthorized deploy, rollback or merge" High/Critical impact bucket in the rules, achieved purely from a webhook-forging attacker who is unprivileged with respect to the victim's org/repository/Shipit account.

### Likelihood Explanation
This requires the attacker to know a valid `webhook_secret` for at least one organization configured in the same multi-tenant Shipit instance. That is a realistic, low-privilege condition for a self-service/multi-tenant Shipit deployment: any org onboarded onto the platform sets its own webhook secret during GitHub App installation, and that org's own staff (unprivileged w.r.t. other tenants) know it. Given that secret, forging the cross-repository payload requires no additional access — just crafting JSON and computing HMAC-SHA1, which `verify_webhook_signature` does not defend against because it only checks byte-for-byte integrity against the org key chosen from within the same forgeable payload [12](#0-11) .

### Recommendation
Bind the field used to select/verify the webhook secret to the same field used to resolve the target repository/stack, or verify the signature against every configured org's secret and then cross-check that the resolved `repository.full_name`'s owner actually belongs to the organization whose secret validated the request. Concretely: after `verify_signature` succeeds for `repository_owner`, reject the request (before invoking handlers) if `repository.full_name`'s owner segment does not case-insensitively match `repository_owner`/`organization.login`. This restores the equality the current code assumes but never checks: `verified_org == owner(repository.full_name)`.

### Proof of Concept
1. Attacker administers "Org A", legitimately installed as a tenant on the shared Shipit instance, and knows Org A's `webhook_secret` (set during their own GitHub App setup).
2. Attacker crafts a JSON body:
```json
{
  "repository": {
    "owner": {"login": "org-a"},
    "full_name": "org-b/victim-repo",
    "name": "victim-repo"
  },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/circleci"
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(body, org_a_webhook_secret)>` and sets `X-Github-Event: status`.
4. POST to `/github/webhooks`. `verify_signature` resolves `Shipit.github(organization: "org-a")` from `repository.owner.login`, verifies successfully against Org A's secret [6](#0-5) .
5. The `status` handler resolves the target stack via `repository.full_name` = `"org-b/victim-repo"` [3](#0-2) , and creates/updates a `Status` on the victim commit belonging to an unrelated tenant, even though the attacker has no relationship to `org-b` or `victim-repo` whatsoever.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
