`GitHubApp#verify_webhook_signature` returns `true` when `webhook_secret` is unset, allowing unsigned webhook forgery - ([File: lib/shipit/github_app.rb])

### Summary
`GitHubApp#verify_webhook_signature` explicitly bypasses cryptographic verification and returns `true` whenever the organization's configured `webhook_secret` is blank. `WebhooksController#verify_signature` relies solely on this method's boolean result and performs no independent check that a secret exists, so any organization/repository configured without a `webhook_secret` accepts entirely unauthenticated, attacker-forged webhook POSTs.

### Finding Description
The broken binding: for any organization `org`, `verify_webhook_signature(sig, body)` should equal `true` **iff** `sig` is a valid HMAC-SHA1 of `body` under `org`'s `webhook_secret`. Instead, when `webhook_secret` is absent, the binding is:
`verify_webhook_signature(sig, body) == true` for **all** `sig`, `body` — i.e., authenticity is unconditionally asserted without any cryptographic check.

Code path:
- `lib/shipit/github_app.rb:76-77`:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
```
- `app/controllers/shipit/webhooks_controller.rb:24-30` (`verify_signature` before_action) resolves `github_app = Shipit.github(organization: repository_owner)` from the attacker-controlled `params.dig('repository','owner','login')` and calls `github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)`. If it returns `true` (which it does unconditionally when `webhook_secret` is nil/blank for that org), the request proceeds.
- `create` then dispatches `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`, which for `pull_request`/`opened` invokes `Shipit::Webhooks::Handlers::PullRequest::OpenedHandler`, creating a `ReviewStack`/queuing sync jobs based entirely on attacker-supplied JSON.

No other guard exists: `drop_unhandled_event` only checks the event name has a registered handler; `check_if_ping` only special-cases `ping`; there is no separate secret-presence assertion anywhere in the controller or `GitHubApp`. The existing test suite (`test/controllers/webhooks_controller_test.rb`) stubs `verify_webhook_signature` in most tests, and its one direct signature test (`"verifies webhook signature"`) only exercises the case where a secret is configured and mismatched — it never asserts behavior when `webhook_secret` is absent, so this divergence is untested and unguarded.

Attacker's exact request: an unprivileged internet user sends `POST /webhooks` with header `X-Github-Event: pull_request`, an arbitrary/omitted `X-Hub-Signature`, and a JSON body such as `{"action":"opened","repository":{"owner":{"login":"<org-with-no-secret>"},"full_name":"..."},"pull_request":{...attacker-controlled branch/labels/etc...}}`. Because that org's `webhook_secret` is blank, `verify_webhook_signature` returns `true` regardless of the (missing/garbage) signature, and the handler proceeds to create/update stack state from entirely forged data.

### Impact Explanation
This is an authentication bypass: a forged webhook is accepted as if it came from GitHub for an organization whose operator omitted `webhook_secret`. Depending on which handler is registered for the spoofed event (e.g., `push`, `pull_request opened`, `status`, `check_suite`, `membership`), the attacker can trigger `GithubSyncJob`, create `ReviewStack`s, inject commit `Status`es, or manipulate `Team`/`Membership` records for that organization — all without holding any Shipit credential. This matches the "authentication bypass (forged webhook ... accepted)" Critical category. Impact is scoped to organizations that have `webhook_secret` unset in their config; it is repeatable indefinitely against that org's `/webhooks` endpoint (no rate limiting or nonce checks apply here).

### Likelihood Explanation
The only precondition is an operator configuring an organization/GitHub App entry without a `webhook_secret` (e.g., via `secrets.github` or per-org config lacking that key) — a configuration omission, not a code exploit requiring secrets. Given `webhook_secret` is optional in the config schema (`@webhook_secret = @config[:webhook_secret].presence`, `lib/shipit/github_app.rb:50`) with no validation elsewhere forcing its presence, this is a plausible real-world misconfiguration, especially for single-org/default setups or during initial rollout before secrets provisioning. Attacker cost is a single unauthenticated HTTP POST; no GitHub account interaction or privileged token is needed.

### Recommendation
Change `verify_webhook_signature` to fail closed when no `webhook_secret` is configured (return `false`/raise, and log loudly), rather than treating an absent secret as "verification not required." At minimum, require `webhook_secret` presence at config-load/boot time for any organization exposed via `/webhooks`, and add a startup/health check (`Shipit.all_settings_present?`-style) that flags orgs missing this value.
