## Title
Webhook signature verified against `repository.owner.login`'s GitHub App while handlers act on `repository.full_name` — cross-organization signature confusion in multi-org deployments - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to validate the HMAC signature using `repository_owner`, derived from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). The event handlers, however, resolve which `Repository`/`Stack` to act on using an entirely separate payload field, `payload.dig('repository', 'full_name')` in `Handler#repository_name`. These two fields are never cross-checked against each other, so the "organization whose secret authenticated the request" and the "repository that gets written to" are two independent, attacker-controlled fields in the same unsigned-until-verified JSON body.

### Finding Description
In a multi-organization Shipit deployment (`config/secrets.yml` keyed by org, as documented in `docs/setup.md:182-209` and exercised by `test/dummy/config/secrets_double_github_app.yml`), each organization has its own `webhook_secret`.

`verify_signature` does:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
``` [1](#0-0) 

`repository_owner` is read straight out of the untrusted, not-yet-verified JSON body:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

`GitHubApp#verify_webhook_signature` computes the HMAC using the secret belonging to whatever org name was extracted:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  algorithm, signature = signature.split("=", 2)
  return false unless algorithm == 'sha1'
  SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
end
``` [3](#0-2) 

After the request passes this check, `create` dispatches the *entire raw body* to the handlers:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [4](#0-3) 

Handlers resolve the target `Repository`/`Stack` using a **different** field, `repository.full_name`, not `repository.owner.login`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [5](#0-4) 

`Repository.from_github_repo_name` splits this by owner/name and looks up the DB row directly — again with no relation back to `repository_owner`:
```ruby
def self.from_github_repo_name(github_repo_name)
  repo_owner, repo_name = github_repo_name.downcase.split('/')
  find_by(owner: repo_owner, name: repo_name)
end
``` [6](#0-5) 

The binding that should hold is:
`organization whose secret verified the signature == owner of the repository the handler writes to`

Because the controller never enforces `repository.owner.login == repository.full_name.split('/').first`, this equality can be broken by any attacker who can produce a *validly-signed* payload for **any one** of the configured organizations (e.g., because that org's `webhook_secret` is unset — `webhook_secret` is commonly left blank in example/dev configs, and `verify_webhook_signature` explicitly returns `true` in that case; or because the attacker has push/webhook-trigger rights on a low-value repo in Org A). Such an attacker can set `repository.owner.login` to Org A (used only for signature verification, or matching a null-secret org) while setting `repository.full_name` to `OrgB/victim-repo` (used only by the handler to pick the `Stack`), causing Shipit to process a forged `push`/`status`/`check_suite` event against a completely different, victim-controlled stack that lives under a different, unrelated organization/secret.

### Impact Explanation
This breaks the trust boundary between organizations in a multi-tenant/multi-org Shipit installation: a signature valid for (or exempted for) organization A is accepted as authorization to mutate state (queue `GithubSyncJob`, create commit `Status`, trigger `RefreshCheckRunsJob`, create `Membership`/`Team` records) for a repository/stack belonging to organization B. Depending on the target handler this enables forged CI-status injection (`StatusHandler`), forced sync events, or membership/team manipulation for `Shipit.github_teams`-based authorization (`membership` event, `app/controllers/shipit/webhooks_controller.rb` dispatch + membership handler) — i.e. escalation into `Shipit.github_teams` authorization, which is explicitly listed as a High-severity outcome for this engine.

### Likelihood Explanation
Exploitability requires (a) a multi-org Shipit configuration (documented and supported feature, `docs/setup.md:182-209`), and (b) the ability to produce one validly-signed (or secret-less) webhook payload for at least one configured organization while controlling the `repository.full_name` field for another. Many real-world/dev configurations ship with `webhook_secret: # nil` (seen repeatedly in `config/secrets.development.shopify.yml`, `config/secrets.development.example.yml`, `test/dummy/config/secrets.yml`), which per `verify_webhook_signature`'s `return true unless webhook_secret` makes the "verified" org trivially spoofable by naming it in `repository.owner.login`, while `repository.full_name` freely points at any other configured org's real repo.

### Recommendation
In `WebhooksController`, after determining `repository_owner` and verifying the signature, also verify that `params.dig('repository', 'full_name')&.split('/')&.first` matches `repository_owner` (case-insensitively) before dispatching to handlers; reject (422) on mismatch. Additionally, consider requiring `webhook_secret` to be present for every configured organization (fail closed) rather than allowing `verify_webhook_signature` to return `true` when unset.

### Proof of Concept
1. Configure Shipit with two orgs, `OrgOne` (no `webhook_secret` set) and `OrgTwo` (real stack, real `webhook_secret`) — matches the supported multi-org schema in `test/dummy/config/secrets_double_github_app.yml`.
2. Attacker sends a `push` webhook to `/github/webhooks` with header `X-Github-Event: push`, no valid `X-Hub-Signature` needed for `OrgOne`, and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "OrgOne" }, "full_name": "OrgTwo/victim-repo" }
}
```
3. `verify_signature` resolves `github_app = Shipit.github(organization: "OrgOne")`; since `OrgOne.webhook_secret` is blank, `verify_webhook_signature` returns `true` unconditionally — the request passes.
4. `PushHandler#process` runs `Repository.from_github_repo_name("OrgTwo/victim-repo")`, finds the real `OrgTwo` stack, and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")`, forcing a sync job against a stack that belongs to an org whose real webhook secret was never checked.
