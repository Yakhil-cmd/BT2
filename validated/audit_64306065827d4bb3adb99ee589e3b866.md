### Title
Missing trust decoration for messages from indirect (unverified) correspondent devices in wallet message handler - (File: wallet.js)

### Summary
`handleMessageFromHub()` in `wallet.js` receives a `bIndirectCorrespondent` flag that is meant to mark messages coming from a device that was never directly, out-of-band paired/verified by the user (an "indirect" correspondent, introduced transitively, e.g. through a shared/multisig address). The only place that was supposed to act on this trust flag — restricting what an indirect correspondent may send — is entirely commented out, so every subject (including signing requests, shared-address creation, contract offers, private-payment notifications, etc.) is processed identically regardless of the sender's trust level. This is the same bug class as the reported Element iOS issue: content originating from an unverified/less-trusted channel is not decorated/distinguished from content coming from a verified channel, and the receiving logic silently treats it as fully trusted.

### Finding Description
`wallet.js` registers `handleMessageFromHub` on the `handle_message_from_hub` event, which is emitted by `device.js` after successfully decrypting and signature-checking a `hub/message` payload: [1](#0-0) 

Critically, `device.js` distinguishes between correspondents that are directly known (`rows[0].is_indirect`) and passes this flag through to the handler: [2](#0-1) 

In `wallet.js`, the flag arrives as `bIndirectCorrespondent`, and the intended access-control check that limits an indirect correspondent to only bootstrapping subjects (`cancel_new_wallet`, `my_xpubkey`, `new_wallet_address`) is disabled via comments: [3](#0-2) 

Because this check never executes, `doHandle()`'s `switch (subject)` processes **every** subject — including `signature`, `new_shared_address`, `prosaic_contract_response`, `arbiter_dispute_request`, `text`, `object`, and private payment chain related subjects — from an indirect correspondent exactly as if it came from a device the user directly paired and verified. There is no warning, decoration, or reduced-trust code path exposed to the wallet/UI layer that a signing request, contract response, or shared-address setup message is coming from an unverified relay device rather than a device the user has personally confirmed (e.g., via QR-code pairing). This mirrors the CVE-2022-41904 root cause: content whose provenance/trust cannot be fully established is processed and surfaced to the user without any indication that it is less trustworthy.

### Impact Explanation
An indirect correspondent is, by design, a device the user has not personally verified — it becomes "known" only transitively (e.g., through introduction via a common multisig/shared address, `addIndirectCorrespondents`). With the trust check disabled, such a device can:
- Send `new_shared_address` messages to establish shared (multi-signature) addresses with the victim, embedding an attacker-controlled definition/cosigner without any additional verification friction, since the wallet cannot warn the user that the message came from a lower-trust path.
- Send `signature`/signing-request-flow messages, contract offers/responses (`prosaic_contract_response`, `arbiter_dispute_request`), or other messages that feed into unit composition and confirmation dialogs (`signing_request` event), potentially leading the user to approve spending from a shared address that the attacker helped set up under false pretense of legitimacy.
Combined, this can enable unauthorized/loss-of-funds outcomes for shared/multisig addresses whose cosigner relationship the user believed was established with a fully verified device, satisfying the "concrete unauthorized spending" / "AA or wallet fund loss" bar.

### Likelihood Explanation
Reaching this path requires only becoming an "indirect correspondent" of the victim (a status obtainable without direct pairing, e.g. by being introduced as a cosigner on a shared address the victim participates in) and then sending arbitrary `hub/message` subjects through the hub. The message-level integrity checks (signature over `objDeviceMessage`, hash checks) in `device.js` are unrelated to this trust bypass — they only prove the message was sent by the claimed device key, not that the device is meant to be trusted for arbitrary wallet operations. Because the mitigating check exists in the source but is commented out (not removed), it strongly suggests this is a regression/incomplete removal rather than an intentional design choice, increasing the likelihood that this gap is unintentional and exploitable.

### Recommendation
Re-enable (or replace with an updated allow-list) the trust check for `bIndirectCorrespondent` in `wallet.js`'s `handleMessageFromHub`, restricting indirect correspondents to a minimal, safe allow-list of subjects, and/or surface a clear "unverified sender" decoration to the UI layer via the emitted events (`signing_request`, `text`, `object`, contract-offer events, etc.) so the user can make an informed trust decision before approving any signature, shared-address creation, or fund-related action originating from a non-directly-verified device.

### Proof of Concept
1. Attacker device A becomes an "indirect correspondent" of victim device V — e.g., by being added as a cosigner device on a shared address that V is also a cosigner of, causing `device.js`'s `correspondent_devices.is_indirect` to be set for A on V (per the `addIndirectCorrespondents` flow), without V ever performing a direct pairing/QR verification of A.
2. A crafts and signs (with its own permanent device key) a `hub/message` with `subject: "new_shared_address"` or `subject: "signature"` (or a contract-offer subject) and sends it through V's hub.
3. V's `device.js` `handleJustsaying('hub/message', ...)` verifies only the message signature/hash (not the trust level) and emits `handle_message_from_hub` with `bIndirectCorrespondent = true`. [4](#0-3) 
4. `wallet.js`'s `handleMessageFromHub` reaches the disabled check and falls straight into the `switch(subject)` handling the message with full trust, identical to a directly verified correspondent. [5](#0-4) 
5. Depending on subject, this can create a shared address controlled in part by A, or push a signing/contract flow toward V that V's UI has no way to flag as coming from an unverified device.
