## Confirmed vulnerability

**Binding claimed:** `Commit#sha` scoping in `StatusHandler#process` (via `Commit.where(sha: params.sha)`) should equal `Commit#stack` == the repository that authenticated the webhook (`repository_owner`/`repository.full_name` in the payload). This binding does **not** hold: the query is scoped only by `sha`, with no join or filter on `stack_id`/repository at all. [1](#0-0) 

## Trace

- `WebhooksController#verify_signature` derives `repository_owner` from the payload's own `repository.owner.login` field and verifies the HMAC using `Shipit.github(organization: repository_owner)`'s configured `webhook_secret` for that org. [2](#0-1)  This only proves the payload was signed by whichever GitHub App/org is configured for that `repository_owner` — it says nothing about which `sha` values that signer is entitled to report statuses for.
- `StatusHandler#process` then does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — with **no** filter tying the matched commits to the repository that sent the webhook. [1](#0-0) 
- `Commit#create_status_from_github!` unconditionally records the incoming `context`/`state`/`branches` as a `Status` row and recomputes `status` via `Status::Group.compact`. [3](#0-2) [4](#0-3) 
- `Status::Group` applies `hidden?`/`allowed_to_fail?` per `context` (deploy_spec's `ci.hide`/`ci.allow_failures`, defined by the **victim** stack's own `shipit.yml`) purely by string match on `context`, with no notion of which repo/app produced the status. [5](#0-4) 

So any party who controls a valid webhook signature for **some** org configured in Shipit (which can be their own org/repo, since Shipit's model is that any onboarded org's app secret is valid for that org) can send a `status` event whose `sha` happens to coincide with a commit that exists in a **different** stack (e.g. a shared upstream commit present in both a fork and the canonical repo, or a rebase/cherry-pick producing an identical sha across stacks), and that status will be applied to the victim commit regardless of which repository it actually came from. There is no repository/stack identity check anywhere between the webhook boundary and `Commit#create_status_from_github!`.

## Why this is credible

- `ExplicitParameters` schema (`params do ... end`) only validates payload shape (`sha`, `state`, `context`, `branches`), not repository ownership. [6](#0-5) 
- No model validation in `Commit`, `Status`, or `Stack` cross-checks the reporting repository against `stack.repository`.
- `verify_signature` authenticates *the sender's org*, not *the sha's ownership*.

## Assessment

This is a real, exploitable design gap in this engine: `sha` is a global lookup key across all stacks/repositories in the `commits` table, and any org with a legitimately configured (even attacker-owned/onboarded) GitHub App/webhook secret can inject or suppress CI status for any commit sha that coincidentally matches a commit in another tenant's stack. This satisfies the "payload for one repository mutating another's stack/commit" Critical category, contingent on the precondition that a shared/colliding sha exists between attacker- and victim-controlled repos (most realistically via forks sharing history, or deliberately crafted identical trees/commits, which is feasible since git shas are reproducible from content+metadata).

### Title
Cross-repository status/CI-state spoofing via unscoped `sha` lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits solely by `Commit.where(sha: params.sha)` with no repository/stack scoping, so a validly-signed webhook from any onboarded GitHub org can write a `Status` (arbitrary `context`/`state`) onto a commit belonging to an unrelated victim stack whenever the shas collide (e.g., shared git history between a fork and the tracked repo). This lets an attacker manipulate `Status::Group`'s `hidden?`/`allowed_to_fail?` classification of a victim's deploy-blocking CI context.

### Finding Description
The intended binding is: *the repository that authenticated the webhook == the repository owning the commit whose status is being recorded*. In code, `repository_owner` is validated against the signer's own webhook secret in `WebhooksController#verify_signature`, but `StatusHandler#process` never re-checks that binding — it looks up commits purely by `sha` across the entire `commits` table and calls `commit.create_status_from_github!(params)` for every match. `create_status_from_github!` records the status verbatim and recomputes `Commit#status` via `Status::Group`, which applies the victim stack's own `ci.hide`/`ci.allow_failures` deploy_spec rules by `context` string match only, oblivious to which repository actually produced the status. An attacker who owns/controls a repository under any Shipit-onboarded GitHub org (their own account/org is sufficient, since the secret model is per-org, not per-privileged-org) can fire a `status` webhook naming a `context` identical to one the victim relies on and a `sha` shared with the victim's commit (via forked history, cherry-pick, or deliberately reproduced tree+metadata), forging or hiding CI results for the victim's commit.

### Impact Explanation
This causes a status/commit record to be written for a repository (the victim's stack) that the attacker never authenticated against, and it changes `Commit#state`/`deployable?` used to gate deploys — matching "a payload for one repository mutating another's stack/commit" (Critical). Repeated per matching sha, and any Shipit instance hosting multiple stacks with shared or overlapping git history is affected across tenants.

### Likelihood Explanation
Requires: (1) the attacker's org has a webhook secret configured in Shipit (i.e., is an onboarded org — plausible in multi-tenant/open-source hosting scenarios), (2) a `sha` collision exists between attacker- and victim-controlled repos, most realistically via shared upstream history in forks. This is a moderate-but-realistic precondition; cost per exploit attempt is a single crafted HTTP POST to `/webhooks`.

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` (and the analogous check-run handler) by the reporting repository, e.g., join through `Stack`/`Repository` and filter `Commit.joins(:stack).where(sha: params.sha, shipit_stacks: { repository_id: repository_from_payload.id })`, rejecting/ignoring statuses for shas that don't belong to a commit in a stack tracking that exact repository.

### Proof of Concept
Add a minitest in `test/models/commits_test.rb`-style: create two stacks backed by different `Repository` records but seed `Commit` rows with the identical `sha` in each; configure `deploy_spec` for the victim stack with `ci.allow_failures` on context `"metrics/coveralls"`; call `victim_commit.create_status_from_github!(state: 'success', ...)` first to establish genuine passing state is required, then invoke `StatusHandler.new.process` equivalent with `params` shaped as `{sha: shared_sha, context: 'metrics/coveralls', state: 'failure', branches: [{name: 'master'}]}` as if received from the attacker's repository's webhook; assert `victim_commit.reload.state` is unaffected/hidden by the allow_failures rule despite no real CI ever running for the victim, and that a `Status` row was created on `victim_commit` even though the request's `repository` field named the attacker's repo, not the victim's.
