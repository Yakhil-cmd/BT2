### Title
Deregistered Bridge Operator's Votes Persist and Can Execute Unauthorized Value Transfers — (`contracts/service_chain/bridge/BridgeOperator.sol`)

---

### Summary

`BridgeOperator.deregisterOperator()` removes an operator from the active set but does **not** clear that operator's already-cast votes from the internal `votes` storage. A single remaining active operator can then vote on the same nonce, reach the threshold using the deregistered operator's stale vote count, and cause `handleKLAYTransfer` / `handleERC20Transfer` / `handleERC721Transfer` to execute — transferring bridged assets to an attacker-controlled address.

---

### Finding Description

`BridgeOperator.sol` maintains a nested mapping `votes[voteType][nonce]` of type `VotesData`, which tracks per-operator vote keys and aggregate vote counts:

```solidity
mapping(uint8 => mapping (uint64 => VotesData)) private votes;
``` [1](#0-0) 

When `deregisterOperator()` is called, it deletes the operator from `operators` and splices them out of `operatorList`, but **leaves all entries in `votes[*][*].voted[operator]` and `votes[*][*].voteCounts[*]` intact**:

```solidity
function deregisterOperator(address _operator) external onlyOwner {
    require(operators[_operator]);
    delete operators[_operator];
    for (uint i = 0; i < operatorList.length; i++) {
       if (operatorList[i] == _operator) {
           operatorList[i] = operatorList[operatorList.length-1];
           operatorList.length--;
           break;
       }
    }
    emit OperatorDeregistered(_operator);
}
``` [2](#0-1) 

The threshold check in `_voteCommon()` compares the raw accumulated count against `operatorThresholds`:

```solidity
if (vote.voteCounts[_voteKey] >= operatorThresholds[uint8(_voteType)]) {
    return true;
}
``` [3](#0-2) 

Because the deregistered operator's vote count is never decremented, any subsequent vote by a still-active operator on the same `(nonce, voteKey)` can push the count to or past the threshold, triggering execution. The code itself documents this as a known but unmitigated scenario:

```
// Note that outstanding votes by the deregistered operator are not revoked.
// ...
// In this case the request was executed with A's vote after A is deregistered.
// The Owner shall recognize this issue and expect that operator deregistration
// takes some time to be fully effective.
``` [4](#0-3) 

The transfer functions (`handleKLAYTransfer`, `handleERC20Transfer`) call `_voteValueTransfer`, which calls `_voteCommon`, and on threshold-reach immediately execute the asset transfer:

```solidity
if (!_voteValueTransfer(_requestedNonce)) { return; }
...
(bool ok, ) = _to.call.value(_value)("");
require(ok, "handleKLAYTransfer: transfer failed");
``` [5](#0-4) 

---

### Impact Explanation

A compromised or rogue operator A votes on a malicious `handleKLAYTransfer` (or ERC20/ERC721) request targeting an attacker address. The owner deregisters A to stop the transfer. However, A's vote count for that nonce remains in storage. Any remaining active operator B who votes on the same nonce with the same parameters causes the threshold to be reached, and the bridge sends the bridged KAIA or tokens to the attacker. This is an **unauthorized transfer of KAIA or bridged assets** from the bridge contract.

---

### Likelihood Explanation

Medium. The window requires: (1) a compromised operator to have voted before deregistration, and (2) another active operator to vote on the same nonce. In a typical 2-of-3 multi-operator bridge setup, this is a realistic race condition. The owner has no atomic way to deregister and cancel the vote simultaneously.

---

### Recommendation

In `deregisterOperator()`, iterate over all open (non-closed) nonces and decrement `votes[voteType][nonce].voteCounts[votes[voteType][nonce].voted[_operator]]` for the deregistered operator, then clear `votes[voteType][nonce].voted[_operator]`. Alternatively, add a `deregisteredAt` timestamp per operator and reject vote contributions from operators deregistered before the vote was cast.

---

### Proof of Concept

```
State: operators = {Owner, A, B}, threshold(ValueTransfer) = 2

Step 1: Operator A calls handleKLAYTransfer(nonce=7, to=attacker, value=1000 KLAY)
        → _voteCommon: voteCounts[keccak(calldata)] = 1 < 2 → no execution

Step 2: Owner discovers A is compromised → calls deregisterOperator(A)
        → operators[A] = false, operatorList = {Owner, B}
        → votes[ValueTransfer][7].voteCounts[keccak(calldata)] still = 1  ← NOT cleared

Step 3: Operator B calls handleKLAYTransfer(nonce=7, to=attacker, value=1000 KLAY)
        → _voteCommon: voteCounts[keccak(calldata)] = 2 >= threshold(2) → returns true
        → closedValueTransferVotes[7] = true
        → _to.call.value(1000 KLAY)("") executes → 1000 KLAY sent to attacker
```

The root cause is at `contracts/service_chain/bridge/BridgeOperator.sol` lines 159–174: `deregisterOperator` does not clear `votes[*][*].voted[_operator]` or decrement the corresponding `voteCounts` entry. [2](#0-1)
