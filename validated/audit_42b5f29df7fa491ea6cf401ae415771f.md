### Title
CCMenu API token scoped to one stack can read build status of any stack - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides the stack-resolution method inherited from `Shipit::Api::BaseController` and, in doing so, drops the scoping check that restricts a stack-bound `ApiClient` token to the single stack it was issued for. Any valid API token — including one created for (and intended to be usable against) only one specific stack — can be replayed with a different `stack_id` to read another stack's build/deploy status.

### Finding Description
`ApiClient` supports being bound to a single stack (`belongs_to :stack, optional: true`) and `Shipit::Api::BaseController` enforces this binding whenever a controller resolves the target stack: [1](#0-0) 

```
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

This is a real, tested feature: `test/controllers/api/stacks_controller_test.rb` verifies "an api client scoped to a stack will only see that one stack" using the `here_come_the_walrus` fixture, confirming stack-scoped tokens are a supported authorization boundary in this engine.

`Shipit::Api::CCMenuController`, however, redefines `stack` to bypass this scoping entirely: [2](#0-1) 

```
private

def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end

def authenticate_api_client
  @current_api_client = ApiClient.authenticate(params[:token])
  super unless @current_api_client
end
```

`authenticate_api_client` here only verifies that the presented `token` corresponds to *some* valid `ApiClient` and that `require_permission :read, :stack` (a scope-level permission check, not an instance-level one) passes: [3](#0-2) 

`require_permission!` merely checks the `read:stack` permission string is present on the client — it never checks `current_api_client.stack_id` against the requested `params[:stack_id]`: [4](#0-3) 

The binding that's broken is: **the stack a token authorizes (`ApiClient#stack_id`, enforced in `BaseController#stacks`) versus the stack it actually touches (`Stack.from_param!(params[:stack_id])` in `CCMenuController#stack`)**. Any token issued for stack A — regardless of how narrowly scoped it is supposed to be — can be pointed at stack B's `stack_id` parameter and CCMenuController will happily resolve and render stack B's state.

### Impact Explanation
This is an unauthenticated-scope read: a token minted for one stack (e.g., via the CCMenu URL feature at `app/controllers/shipit/ccmenu_url_controller.rb`, which mints `ApiClient` tokens with `read:stack` permission for embedding in CI dashboard tools) can be reused to read `lastBuildStatus`, `lastBuildLabel`, lock status, and activity for **any** stack in the Shipit instance, not just the stack it was generated for. This matches the "unauthenticated read of stack state" impact category — a client is meant to be confined to a single stack's read access but escalates to reading the state of every stack, because the per-stack authorization check present in the base controller is simply absent from this endpoint.

### Likelihood Explanation
Exploitation requires possession of any valid CCMenu/API token with `read:stack` permission (the same low bar required to legitimately use the CCMenu feature at all — tokens are exposed unauthenticated in a query string per `CCMenuUrlController#fetch`). No privileged account, GitHub credentials, or session are needed beyond a token that is otherwise expected to be restricted. Given tokens are designed to be embedded in third-party CI dashboard tools (long-lived, low-friction), the likelihood of a leaked/shared token being reused against unrelated stacks is high.

### Recommendation
Make `Shipit::Api::CCMenuController#stack` reuse the scoped `stacks` resolution from `BaseController` instead of calling `Stack.from_param!` directly, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
This ensures the `current_api_client.stack_id` binding enforced elsewhere in the API is also enforced for the CCMenu endpoint.

### Proof of Concept
1. Obtain (or have a CI tool leak) a CCMenu token for Stack A via `GET /stacks/:stack_id/ccmenu_url` (`CCMenuUrlController#fetch`), which returns a URL like `.../api/stacks/A/ccmenu.xml?token=<TOKEN>`.
2. Replay the same `TOKEN` against a different, unrelated stack: `GET /api/stacks/B/ccmenu.xml?token=<TOKEN>`.
3. Because `Api::CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` without checking `current_api_client.stack_id`, the request succeeds and returns Stack B's build/deploy status, even though the token was only ever meant to authorize reads for Stack A.
