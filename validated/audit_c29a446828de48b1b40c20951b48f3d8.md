### Title
Vote-commission rewards silently vanish (neither credited nor burned) when the commission account is missing at distribution time - (File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs)

### Summary
Like the Rio `RioLRTRewardDistributor`, which assumed a specific delivery mechanism (`receive()`) would always fire and therefore lost Execution Layer rewards when it didn't, Agave's reward-commission distribution path assumes the legacy commission account (a vote account) "should always exist" at distribution time. When that assumption is violated, the calculated commission reward is dropped from *every* accounting bucket — it is not credited to the recipient and it is not counted as burned — unlike every other failure branch in the same function.

### Finding Description
`load_and_reward_commission_accounts` in `calculation.rs` loads each vote account's commission at distribution time (deliberately deferred from the calculation phase so intervening mutations are reflected) [1](#0-0) . For the legacy (non-`custom_commission_collector`) path, the code comments that "commission accounts were always vote accounts, which cannot be closed... so `maybe_commission_account` should always exist," and if that assumption fails, it just does `return None;` [2](#0-1) .

Critically, this early `return None` happens *before* the code reaches the burn-accounting logic that every other failure path uses. Compare the two failure branches:
- Missing account (line 1141-1147): returns `None` with **no** update to `total_non_incinerator_burned_lamports` or `total_incinerator_lamports`.
- `checked_add_lamports` overflow (line 1155-1162): returns `None` **but** explicitly adds `*commission_lamports` to `total_non_incinerator_burned_lamports` before returning.
- Failed `collector_type_checked` (line 1177-1185): also explicitly burns `*commission_lamports` before returning. [3](#0-2) 

So the missing-account case is the only branch that drops the lamports entirely instead of burning them. `distribute_reward_commissions` then aggregates `distributed_lamports`, `distributed_to_incinerator_lamports`, and `burned_lamports` from this function's output and asserts the sum is `<= point_value.rewards` (a `>=` check, so it silently tolerates the shortfall rather than catching it) [4](#0-3) . The result is fed into `create_epoch_rewards_sysvar`'s "already distributed" total [5](#0-4) , meaning `distributed_rewards` in the `EpochRewards` sysvar permanently undercounts `total_rewards` by exactly the dropped commission amount — the invariant `total_rewards == distributed_rewards` that the codebase's own tests assert (e.g. `test_invalid_inflation_rewards_collector_burns_sysvar_rewards`) is violated in this one path [6](#0-5) .

Capitalization is only increased by `distributed_lamports + distributed_to_incinerator_lamports` [7](#0-6) , so the vanished commission is never minted into circulation at all — it is neither paid to the intended vote-account owner, nor formally burned/tracked, nor added to capitalization. This is functionally identical to the Rio bug: a reward that the protocol calculated as "owed" is lost because the code relies on an assumption ("the account always exists") that a legitimate, in-scope user action (closing/emptying a vote account via the vote program's `Withdraw` instruction) can invalidate between the reward-calculation snapshot and the (multi-block) distribution phase.

### Impact Explanation
Every epoch, calculated inflation-reward commissions represent real economic value owed to validator operators. When the underlying vote account is removed from accounts-db between the calculation and distribution phases (which can span up to 10% of an epoch's slots per `get_reward_distribution_num_blocks`) [8](#0-7) , the associated commission lamports are permanently and silently lost with no error surfaced beyond a `debug!` log line. This breaks the reward-accounting invariant enforced elsewhere in the same module (`total_rewards == distributed_rewards`), understating rewards actually distributed relative to what was promised/calculated, and represents a class of "lost lamports" bug directly analogous to the cited Rio finding.

### Likelihood Explanation
This requires the `custom_commission_collector` feature to be inactive (the legacy code path, which is the default/pre-activation behavior) and a vote account that held delegated stake during the rewarded epoch to be closed/emptied via a normal `Withdraw` vote-program instruction before the distribution phase reaches its partition. Because distribution can be spread over many blocks, there is a real window where this ordinary user/operator action (withdrawing/closing their own vote account) can race with reward payout. This is a legitimate, in-scope vote-program instruction interaction, not a validator-role or theoretical-only scenario, though the size of the practical window and exact conditions under which a still-scheduled-for-reward vote account can be fully emptied mid-distribution were not fully verified against the `Withdraw` instruction's guard conditions (I could not load `vote_state::withdraw` in the final iteration to confirm exactly when a fully-closing withdrawal is permitted for a previously-staked vote account).

### Recommendation
In the `else` branch of `load_and_reward_commission_accounts` where `maybe_commission_account` is `None`, treat the dropped `commission_lamports` the same way the sibling failure branches do: add `*commission_lamports` (and `*burned_lamports`, if not already zero) to `total_non_incinerator_burned_lamports` before returning `None`, so the amount is consistently accounted for as burned rather than silently vanishing from the reward-accounting totals.

### Proof of Concept
Not independently reproduced; the mechanism is demonstrated purely from code inspection of the asymmetric error-handling branches in `load_and_reward_commission_accounts` [9](#0-8) . A full PoC would require: (1) constructing a bank with `custom_commission_collector` inactive, (2) a vote account with delegated stake earning a nonzero commission in the rewarded epoch, (3) fully withdrawing/closing that vote account between the reward-calculation block and its distribution partition block, and (4) asserting that `EpochRewards.total_rewards != EpochRewards.distributed_rewards` at the end of distribution — this last step could not be executed in this read-only investigation.

    /// Calculate the number of blocks required to distribute rewards to all stake accounts.
    pub(super) fn get_reward_distribution_num_blocks(
        &self,
        rewards: &PartitionedStakeRewards,
    ) -> u64 {
        let total_stake_accounts = rewards.num_rewards();
        if self.epoch_schedule.warmup && self.epoch < self.first_normal_epoch() {
            1
        } else {
            const MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH: u64 = 10;
            let num_chunks = total_stake_accounts
                .div_ceil(self.partitioned_rewards_stake_account_stores_per_block() as usize)
                as u64;

            // Limit the reward credit interval to 10% of the total number of slots in a epoch
            num_chunks.clamp(
                1,
                (self.epoch_schedule.slots_per_epoch / MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH).max(1),
            )
        }
