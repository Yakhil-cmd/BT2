This confirms the vulnerability: this Shipit engine supports a **multi-organization GitHub App configuration** (`Shipit.github_organizations`, `github_app_config`), where each organization has its own `webhook_secret` [1](#0-0) . The webhook controller selects *which* organization's secret to verify against based on an unauthenticated payload field, and then uses a *different* payload field to decide which repository to act on.

### Title
Webhook Signature Verification Uses Wrong Organization Key, Allowing Cross-Repository Forged Events - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
### Finding Description
`WebhooksController#verify_signature` determines which organization's `webhook_secret` to validate the incoming signature against by reading `repository_owner`, which is taken directly from the untrusted JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`), *before* the signature has been verified: [2](#0-1) [3](#0-2) 

The actual repository/stack that gets acted upon in `create` is resolved from a *different* field of the same payload, `repository.full_name`, via `Repository.from_github_repo_name` inside each handler (e.g. `PushHandler`): [4](#0-3) [5](#0-4) 

In a multi-org configuration (`Shipit.github` keyed per organization, each with its own `webhook_secret`) [6](#0-5) , this creates a binding mismatch: **the organization whose secret authenticates the request ≠ the repository whose stack is written**. An attacker who legitimately owns/administers *any one* organization onboarded to this Shipit instance (and therefore knows that organization's `webhook_secret`, e.g. because they configured the GitHub webhook themselves) can craft an arbitrary payload where `repository.owner.login` (or `organization.login`) is set to their own org (so `verify_webhook_signature` checks against a secret they know and passes), while `repository.full_name` is set to `"victim-org/victim-repo"` — a stack belonging to a completely different, unrelated organization also configured on the same Shipit instance. The signature only proves the attacker knows *some* org's secret; it never binds that org to the specific repository field consumed downstream by the handlers.

### Impact Explanation
This breaks the equality "organization that authenticated == repository that is written." Concretely, with `push` events this lets the attacker fabricate `GithubSyncJob` enqueues and, through the sync flow, cause commits/statuses to be recorded for a victim org's stack that the attacker doesn't own, or trigger `membership`, `status`, `pull_request`, `check_suite`, and `merge` event handlers scoped to the victim repository/stack, corrupting merge/deploy state or invoking privileged repository actions cross-tenant — an unauthorized write to another organization's stack from a party who has no relationship to that repository. This satisfies the "cross-repository writes" / "unauthorized deploy/ship" bar since deploy scheduling and merge-queue mutation for a stack the attacker doesn't control become reachable.

### Likelihood Explanation
Requires the attacker to be a legitimate admin of *some* GitHub organization already integrated with the shared Shipit instance (a realistic multi-tenant deployment scenario, which this engine explicitly supports via `github_app_config` per-organization secrets), with zero access to the victim organization or repository. No GitHub App private key, no Shipit session, and no victim credentials are needed — only the attacker's own legitimately-issued webhook secret and the ability to POST to the shared `/webhooks` endpoint.

### Recommendation
After signature verification succeeds, re-derive `repository_owner` used for the secret lookup and cross-check it against the owner encoded in `repository.full_name` (or any repository/organization identifier used later by handlers) before dispatching to `Shipit::Webhooks.for_event(event)`; reject the request if they diverge. Alternatively, resolve the target `Repository`/`Stack` first and verify the signature using the secret of the organization that actually owns that repository, rather than trusting an unauthenticated field to select the verification key.

### Proof of Concept
1. Shipit is configured for two organizations, `attacker-org` and `victim-org`, each with a distinct `webhook_secret` in `secrets.github`.
2. Attacker knows `attacker-org`'s `webhook_secret` (they legitimately administer that org and set up its webhook).
3. Attacker crafts a JSON body for the `push` event:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org_webhook_secret, body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: "attacker-org")` (from `repository.owner.login`), verifies successfully against the attacker's own secret [2](#0-1) .
6. `create` dispatches to `PushHandler`, which resolves `stacks` via `repository.full_name = "victim-org/victim-repo"` [4](#0-3)  and enqueues a `GithubSyncJob` for the victim's stack, entirely under attacker control, despite the attacker having no legitimate relationship to `victim-org`.
