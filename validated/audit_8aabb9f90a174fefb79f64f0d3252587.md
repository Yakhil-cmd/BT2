### Title
Signature verification keyed on `repository.owner.login`/`organization.login` while push/status/pull_request/membership handlers act on the unrelated `repository.full_name` field allows cross-repository writes when any configured GitHub org has no `webhook_secret` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret to validate a webhook against using `repository_owner`, which is read straight from the attacker-suppliable JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`), and verifies the raw body against *that* org's secret. But every event handler resolves the actual target `Repository`/`Stack` using a *different* field in the same body: `payload.dig('repository', 'full_name')`. Because signature validity is bound to the org named in one field while the mutation is bound to the repo named in another, an attacker can pick an org that has no `webhook_secret` configured to sail through `verify_signature`, then point `repository.full_name` at any other repository tracked by the instance. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

### Finding Description
The binding that should hold is: **organization authenticated by the HMAC signature == organization owning the repository that is mutated by the handler**. Instead:

1. `verify_signature` computes `repository_owner` from the body and fetches `Shipit.github(organization: repository_owner)`, then checks `X-Hub-Signature` against `request.raw_post` using that org's `webhook_secret`. [5](#0-4) 
2. `verify_webhook_signature` explicitly treats an absent secret as automatically verified: `return true unless webhook_secret`. [6](#0-5) 
3. `repository_owner` itself falls back to the "organization" sub-object of the payload, so the attacker fully controls which org's config is looked up. [2](#0-1) 
4. Once the request passes `verify_signature`, `Shipit::Webhooks.for_event(event)` dispatches the raw `params` (untouched) to handlers such as `PushHandler`, `StatusHandler`, `MembershipHandler`, etc. [7](#0-6) 
5. Every handler resolves the target repository purely from `payload.dig('repository', 'full_name')` via `Handler#repository_name`/`#stacks`, then `Repository.from_github_repo_name` — none of them re-check that this repo's owner matches the org whose secret was used to authenticate the request. [3](#0-2) [8](#0-7) 

Consequently, `repository.owner.login` (used for auth) and `repository.full_name` (used for the write target) are two independent, attacker-controlled JSON fields in the same unsigned-or-loosely-signed request. If the Shipit deployment has configured even one GitHub organization without a `webhook_secret` — a configuration explicitly supported and shown as the example/default in this engine's own setup files — that org's name becomes a "free pass" identity: any request naming it as `repository.owner.login`/`organization.login` bypasses signature checking entirely (`head(422) unless verified` is skipped because `verified` is `true`), while the payload's `repository.full_name` can name a completely different, secret-protected repository/stack belonging to another organization. [9](#0-8) [10](#0-9) 

### Impact Explanation
This breaks the "organization authenticated versus the repository that is written" binding named in the review rules. Concretely, an unprivileged attacker (no Shipit session, no `ApiClient` token, no `webhook_secret`, no repository write access) can:
- Trigger `PushHandler#process`, causing `stack.sync_github(expected_head_sha:)` to run for a victim stack/repository the attacker doesn't own, using an attacker-chosen `after` SHA/branch — this can start syncs/continuous-deployment flows for a real branch/commit combination the attacker selects, i.e. an unauthorized deploy trigger against a protected repository. [4](#0-3) 
- Similarly forge `status`, `check_suite`, `pull_request`, or `membership` events against any tracked repository/stack, since all handlers key off the same spoofable `repository.full_name`/`organization.login` fields rather than the org that was actually authenticated. [11](#0-10) 

This matches the "unauthorized deploy" / "cross-repository writes" Critical impact bar, because the crossing of trust domains (org A's identity used to unlock writes against org B's repository) is exactly the class of binding violation the audit is asking about, analogous to the Perennial report's core theme: an accounting/trust boundary (there: liquidated collateral vs. socialized funds; here: authenticated org vs. mutated repository) is not enforced consistently, letting one actor's state affect another's without their consent.

### Likelihood Explanation
Exploitability depends entirely on operator configuration: it requires at least one GitHub organization registered in `Shipit.github` config with `webhook_secret` blank/nil. The engine's own example secrets files (`config/secrets.development.shopify.yml`, `test/dummy/config/secrets_double_github_app.yml`) show `webhook_secret: # nil` as the baseline/documented configuration, meaning this is a realistic, even encouraged, default rather than an edge case. Any Shipit instance that has not deliberately set a `webhook_secret` for every org it manages is exposed; the attacker only needs to know (or guess) that org's login, which is often public knowledge (a GitHub org name), and does not need any secret, token, or session.

### Recommendation
Bind the signature-verifying organization to the object actually being mutated, not to an attacker-suppliable field:
- Derive the org used to select `Shipit.github(organization: ...)` from the `full_name`/repository that the handler will act on (or resolve the `Repository` first and use its stored `owner`), rather than trusting `params.dig('repository','owner','login')`/`organization.login` directly.
- After verification, re-derive `repository_owner` from the resolved `Repository` record (or otherwise validate that `repository.owner.login` matches `repository.full_name`'s owner segment) before dispatching to handlers.
- Do not allow `verify_webhook_signature` to short-circuit to `true` when `webhook_secret` is blank if that org's identity can be spoofed to affect other orgs' repositories — at minimum, require a configured secret for every org, or refuse to act on any repository whose owner differs from the authenticated org.

### Proof of Concept
Given a Shipit deployment with:
```yaml
github:
  NoSecretOrg:
    webhook_secret: # nil
  VictimOrg:
    webhook_secret: "s3cr3t"
```
and a tracked repository/stack `VictimOrg/victim-repo`, an attacker with no credentials sends:
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=anything-or-omitted

{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "NoSecretOrg" },
    "full_name": "VictimOrg/victim-repo"
  }
}
```
- `repository_owner` resolves to `"NoSecretOrg"` → `Shipit.github(organization: "NoSecretOrg")` has no `webhook_secret` → `verify_webhook_signature` returns `true` unconditionally, so `verify_signature` passes regardless of the (fake/omitted) `X-Hub-Signature`. [1](#0-0) [6](#0-5) 
- `Shipit::Webhooks.for_event('push')` invokes `PushHandler.call(params)`. [7](#0-6) 
- `PushHandler#stacks` resolves via `Repository.from_github_repo_name('VictimOrg/victim-repo')`, finds the real `VictimOrg` stack (which is protected by its own `"s3cr3t"` secret in normal operation), and runs `stack.sync_github(expected_head_sha: params.after)` for it. [3](#0-2) [4](#0-3) 

The attacker never presented `VictimOrg`'s secret, yet caused a state-changing action (sync/deploy trigger) on `VictimOrg`'s repository, purely by choosing an org name that happens to have no secret configured.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
