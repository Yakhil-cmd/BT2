### Title
Webhook signature verification is bound to `repository.owner.login`/`organization.login`, but event handlers act on the independently-attacker-controlled `repository.full_name` — allowing cross-organization writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` is used to validate the inbound HMAC signature based on `repository.owner.login` (falling back to `organization.login`) taken from the raw JSON body. The event handlers, however, resolve the actual `Repository`/`Stack` to mutate using a *different* field of that same attacker-supplied JSON body: `repository.full_name`. Because the whole request body is just JSON crafted by whoever sends the POST, and only its raw bytes are HMAC-verified against one org's secret, these two fields can be made inconsistent, breaking the intended binding `organization_that_authenticated == repository_that_is_written`.

### Finding Description
`verify_signature` picks the GitHub App/org whose `webhook_secret` will validate the signature purely from a field of the untrusted payload: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` supports one `GitHubApp` (and one `webhook_secret`) per organization in a multi-tenant secrets layout: [3](#0-2) 

Once the signature is accepted, the actual event handler resolves which `Repository`/`Stack` to act on from a *separate* field of the same JSON body, `repository.full_name`, with no cross-check against `repository_owner`: [4](#0-3) [5](#0-4) 

`PushHandler` then uses that lookup to sync arbitrary stacks to an attacker-chosen `expected_head_sha`: [6](#0-5) 

`StatusHandler` is worse still — it does not scope by repository at all, matching purely on `sha` across the whole install: [7](#0-6) 

Because nothing forces `repository.owner.login` (the value used to pick the verifying `webhook_secret`) to equal the owner encoded in `repository.full_name` (the value used to pick the affected `Repository`/`Stack`), a party who legitimately knows *one* organization's `webhook_secret` (their own tenant's GitHub App secret, configured in `secrets.github`) can forge a JSON body where `repository.owner.login` = their own org (to pass `verify_signature`) while `repository.full_name` = `"other-org/other-repo"`, and sign the whole raw body with their own known secret. `verify_signature` passes, and the handler subsequently drives `sync_github`/status updates against a `Stack` belonging to a different organization, using that stack's own GitHub credentials.

### Impact Explanation
This breaks the equality `organization_that_authenticated == repository_that_is_written`, one of the explicitly in-scope trust bindings. Concretely, an attacker who controls webhook credentials for one tenant can:
- Force `GithubSyncJob`/`sync_github` on another organization's `Stack` with an attacker-chosen `expected_head_sha` (`app/models/shipit/webhooks/handlers/push_handler.rb`).
- Inject arbitrary commit statuses for any `sha` present anywhere in the install (`StatusHandler`), independent of any organization scoping at all.

Combined, these primitives can manipulate another organization's commit/deploy state (e.g., marking a chosen commit "deployable", influencing `undeployed_commits_count`/continuous-delivery eligibility), which maps to the Critical bucket ("cross-repository writes, or an unauthorized deploy"). I was not able to fully trace the `ContinuousDeliveryJob` trigger conditions within the tool budget available, so the full "unauthorized deploy" chain via continuous delivery is plausible but not fully confirmed end-to-end; the cross-organization write (forced sync / forged status on another org's data) is confirmed directly from the code cited above.

### Likelihood Explanation
Exploitability requires the attacker to know a valid `webhook_secret` for *some* organization configured on the same Shipit instance — realistic in any multi-tenant deployment where each customer/organization independently provisions its own GitHub App and thus knows its own `webhook_secret`, as documented by the multi-org `secrets.github` layout (`test/dummy/config/secrets_double_github_app.yml`, `lib/shipit.rb#github_app_config`). No GitHub compromise, no Shipit session, and no privileged Shipit account are required — only knowledge of one tenant's own webhook secret, which that tenant's admins legitimately possess.

### Recommendation
Bind the two fields together before dispatching to handlers: after `verify_signature` resolves `repository_owner`, re-derive/validate that the same value is the owner segment of `repository.full_name` (and of `organization.login` when used as fallback) before invoking `Shipit::Webhooks.for_event(event)`. Additionally, scope `StatusHandler`'s `Commit.where(sha: params.sha)` lookup by the repository resolved from the verified organization, not solely by `sha`.

### Proof of Concept
1. Attacker controls tenant `OrgA` in a multi-org Shipit deployment and knows `OrgA`'s `webhook_secret` (legitimately configured for their own GitHub App integration).
2. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(OrgA_webhook_secret, raw_body)` and POSTs to `/webhooks`.
4. `verify_signature` computes `repository_owner = "OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and validates successfully (`app/controllers/shipit/webhooks_controller.rb:24-49`).
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("OrgB/victim-repo")` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on `OrgB`'s stack (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) — a write against an organization the attacker never authenticated as.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end
```
