### Title
Unvalidated externally-supplied size field defeats the `gh skill preview` output-size safety cap - ([File: pkg/cmd/skills/preview/preview.go])

### Summary
`gh skill preview` renders a third-party skill repository's files to the terminal, and enforces a `maxTotalBytes` (512 KiB) cap on how much extra-file content it will fetch and print, in addition to a `maxFiles` (20) cap. The cap relies on an accumulator (`totalBytes`) that is compared against a per-file `Size` value taken verbatim from the repository's Git Trees API response. Like the reported UTXO-accumulation bug (an unchecked `int64` sum trusted to gate a downstream financial decision), this code trusts an externally-supplied numeric field to gate a downstream safety decision without validating its sign or bounds, so a value from an attacker-controlled source can defeat the accumulator check entirely.

### Finding Description
`discovery.DiscoverSkillFiles` / `discovery.ListSkillFiles` populate `SkillFile.Size` directly from the `"size"` field of the (attacker-influenceable) Git Trees API JSON response: [1](#0-0) [2](#0-1) 

`renderAllFiles` then uses this untrusted `Size` field as the sole pre-fetch gate protecting the 512 KiB rendering budget: [3](#0-2) 

The check is `if totalBytes+f.Size > maxTotalBytes { break }`. Because `Size` is decoded from JSON into a plain Go `int` with no validation that it is non-negative (or otherwise sane), a server that supplies a negative (or otherwise crafted) `size` value for a tree entry can keep `totalBytes+f.Size` permanently below `maxTotalBytes`, so the cap check never trips. Note that the *actual* fetched content length (`len(sanitized)`) is added into `totalBytes` after the fact, but the pre-fetch decision that gates whether to keep fetching more files is made using the attacker-suppliable declared `Size`, not the previously observed real content size — mirroring the original bug pattern where an unchecked accumulated value is trusted for a critical threshold decision.

The declared `Size` value originates from `client.REST(host, "GET", ".../git/trees/...")`, and `host` is the repository's own host (`repo.RepoHost()`), which can be any GitHub Enterprise Server hostname configured by the user. Against a normal (non-malicious) `github.com`/GHES server, the "size" field is authoritative and non-negative, but `gh skill preview` is specifically designed to let a user preview *untrusted* third-party skills before installing/running them; if that skill lives on, or is fetched through, a host under attacker control (e.g., a rogue GHES-compatible endpoint the user has configured, matching this task's allowed "attacker-controlled host during a normal gh command" analog), the JSON body — including the `size` field — is fully attacker-controlled.

### Impact Explanation
Bypassing the `maxTotalBytes` cap does not achieve code execution, but it defeats an explicit safety control designed to bound resource consumption when previewing untrusted repository content. With the cap defeated (while `maxFiles = 20` still bounds file count), an attacker can cause `gh skill preview` to fetch and print up to 20 arbitrarily large blobs to the user's terminal/pager instead of the intended 512 KiB budget, resulting in excessive memory use, CPU spent sanitizing/rendering the content, and terminal flooding — the same "untrusted terminal output" risk category called out for this analysis. It is a resource-exhaustion / safety-control-bypass issue, not a memory-safety or authentication bypass; there is no arithmetic overflow of the classic `int64` wraparound kind demonstrated here (Go's `int` is 64-bit on all supported build targets), but the accumulator can be trivially driven negative by supplying a negative `size`, which is functionally equivalent to the overflow-based bypass in the original report: an attacker-controlled value defeats an accumulated-threshold safety check.

### Likelihood Explanation
Reachability requires the user to run `gh skill preview` against a repository whose Git Trees API responses are attacker-controlled — i.e., a skill hosted by (or proxied through) a hostname the attacker controls. This is squarely within the intended threat model of `gh skill preview` (previewing skills from arbitrary/untrusted sources before install), so the likelihood of reaching this code path during ordinary use is high for that specific workflow, though the requirement that the *host itself* (not just the repo owner on github.com) be attacker-controlled narrows real-world exploitability, since GitHub.com's own Trees API always returns accurate non-negative sizes.

### Recommendation
Do not trust the declared `Size` field for a security-relevant resource cap. Clamp/validate `f.Size` (reject or treat as `0`/`maxTotalBytes` any negative or implausible value) before using it in the `totalBytes+f.Size > maxTotalBytes` comparison, and additionally enforce the cap using the actual bytes read from `FetchBlob` (e.g., limit `io.ReadAll` with `io.LimitReader` so a single blob cannot exceed a hard byte ceiling regardless of what the tree API claims), so the safety net is derived only from measured, trusted quantities rather than an externally-supplied number.

### Proof of Concept
Not independently executable from static analysis (requires standing up a malicious GHES-compatible host to be queried by `gh skill preview`), but the logical PoC is:
1. Configure `gh` to talk to an attacker-controlled hostname (e.g., a fake GHES endpoint) for a repository.
2. Have that host's `git/trees/<sha>?recursive=true` response return entries such as `{"path":"big1.bin","type":"blob","sha":"...","size":-999999999}` for up to 20 blob entries, each of whose corresponding `git/blobs/<sha>` response is base64 content many megabytes in size.
3. Run `gh skill preview <owner>/<repo>` (non-interactive/non-TTY path, or the "dump all" path). Because `totalBytes+f.Size` is always very negative, the `maxTotalBytes` check in [4](#0-3) 
never triggers, and up to 20 large blobs are fetched and printed to the terminal instead of the intended 512 KiB total.
