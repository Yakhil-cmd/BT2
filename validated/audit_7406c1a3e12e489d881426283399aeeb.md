### Title
Cross-repository status forgery via unscoped commit lookup in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
Unlike every other webhook handler in this engine, `Shipit::Webhooks::Handlers::StatusHandler#process` resolves the target `Commit` purely by SHA (`Commit.where(sha: params.sha)`) with no scoping to the repository that sent the webhook. Because `Status.replicate_from_github!` trusts `commit.stack_id` and the attacker-controlled `context`/`state` fields verbatim, a webhook signed for one repository can write a `Status` row attached to a *different* stack's commit whenever the two repositories happen to share a commit SHA (e.g. via a fork), letting an attacker forge a security-critical CI check (e.g. `soc/compliance`) for a victim stack.

### Finding Description
The broken binding is: `commit.stack_id` (derived from `Commit.where(sha: params.sha)`) should equal `Repository.from_github_repo_name(payload['repository']['full_name']).stacks.pluck(:id)` — i.e. the commit resolved from the sha lookup must belong to a stack owned by the repository that authenticated the webhook. It does not.

Code path:
1. `WebhooksController#verify_signature` only checks that the raw payload is validly signed for `repository_owner` (`Shipit.github(organization: repository_owner)`), i.e. that *some* org's webhook secret matches — it never checks that the `sha`/`context` in the payload actually originates from that repository's CI. [1](#0-0) 
2. `StatusHandler#process` then does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a global, unscoped lookup across every stack/repository in the installation. [2](#0-1) 
3. Every other handler in this codebase (`PushHandler`, `CheckSuiteHandler`, all `PullRequest::*Handler`s) scopes its lookup through `Repository.from_github_repo_name(repository_name)` via the base `Handler#stacks` helper before touching any stack/commit. [3](#0-2) [4](#0-3) [5](#0-4) . `StatusHandler` alone omits this scoping.
4. `Commit#create_status_from_github!` writes the status using `stack_id` taken from whichever `Commit` row matched: `statuses.replicate_from_github!(stack_id, github_status)` → `Status.replicate_from_github!` performs `find_or_create_by!(stack_id:, state:, description:, target_url:, context:, created_at:)` with the attacker-supplied `context`/`state` written verbatim. [6](#0-5) [7](#0-6) 
5. Deploy gating then trusts that `context` string as-is: `Commit#deployable?` and `#blocked?` use `stack.blocking_statuses` (from `shipit.yml`'s `ci.blocking`) matched purely by `context`, and `MergeRequest::StatusChecker#required_statuses`/`merge_request_required_statuses` do the same for `merge.require`. [8](#0-7) [9](#0-8) 

Exploit flow: attacker forks (or otherwise obtains a repository sharing commit history/SHAs with) the victim's tracked repository, or otherwise arranges for a Commit row shared by SHA to exist in both the attacker's and victim's stacks (git commit SHAs are content-addressed and identical across forks that share history). The attacker's own repository is registered under a GitHub org/account whose Shipit GitHub App/webhook secret they can legitimately trigger (since GitHub itself signs webhooks for events on repos where the app is installed, no Shipit secret is stolen). The attacker triggers a real `status` webhook on their own repo for that shared SHA with `context: 'soc/compliance', state: 'success'`. Shipit's `verify_signature` succeeds (it's a legitimately signed webhook for the attacker's own org), and `StatusHandler#process` matches the victim's `Commit` row by bare SHA, writing a `Status` under the victim's `stack_id` with the forged context — satisfying `ci.blocking`/`merge.require` for the victim's stack without the victim's actual CI ever running.

Existing guards do not prevent this: `verify_signature` authenticates *sender identity* per organization, not *sha ownership*; `ExplicitParameters` only validates payload shape, not repository/sha binding; there is no `repository.full_name` check anywhere in `StatusHandler` or `Status`/`Commit` status-creation code.

### Impact Explanation
An unprivileged GitHub user who controls any repository (their own fork or unrelated repo) can cause a `Status` row with attacker-chosen `context`/`state` to be written against a victim stack's commit, as long as a shared-SHA commit exists between their repository and the victim's tracked repository/branch. This can spoof a required, security-critical CI gate (`ci.blocking`, `merge.require`) and make `Commit#deployable?` true or unblock a queued merge request, leading to an unauthorized deploy or merge — this is a Critical-severity "payload for one repository mutating another's stack/commit" and effectively an authentication-bypass of the CI-gating control. The attack is repeatable against any stack/commit for which a shared SHA can be arranged.

### Likelihood Explanation
Preconditions: the victim stack must have a `Commit` row (imported via `GithubSyncJob`/PR sync) whose SHA matches a commit the attacker can trigger a `status` webhook for from their own repository — realistic via forking a public repo tracked by Shipit and preserving shared ancestor commits, or via any other repo sharing history with the target. The attacker needs no Shipit credentials, session, or `api_clients_secret` — only the ability to own/control a GitHub repository that can emit real signed webhooks (any public repo with the relevant GitHub App/webhook installed, which is the normal, unprivileged path for any GitHub user interacting with a public open-source project). This makes the attack low-cost and feasible for any repository configured with `ci.blocking`/`merge.require`.

### Recommendation
Scope `StatusHandler#process` (and `Commit.create_status_from_github!`/`Status.replicate_from_github!`) so that a status/context is only ever recorded against commits belonging to stacks whose `Repository` matches `payload['repository']['full_name']`, mirroring the `Handler#stacks` pattern used by `PushHandler` and `CheckSuiteHandler`. Concretely, change `StatusHandler#process` to intersect `Commit.where(sha: params.sha)` with `stacks` (repository-scoped) before calling `create_status_from_github!`.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb (conceptual, no live GitHub)
test "status webhook from an unrelated repository cannot forge a blocking status on another stack's commit" do
  victim_stack = shipit_stacks(:shipit)
  victim_stack.update!(cached_deploy_spec: DeploySpec.new('ci' => { 'blocking' => ['soc/compliance'] }))

  shared_sha = 'deadbeefdeadbeefdeadbeefdeadbeefdeadbeef'
  victim_commit = victim_stack.commits.create!(sha: shared_sha, author: shipit_users(:shipit),
    committer: shipit_users(:shipit), authored_at: Time.now, committed_at: Time.now, message: "shared ancestor")

  # attacker's payload claims a different, attacker-owned repository
  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'soc/compliance',
    'branches' => [{ 'name' => 'master' }],
    'repository' => { 'full_name' => 'attacker/unrelated-repo', 'owner' => { 'login' => 'attacker' } }
  }

  refute victim_stack.blocking_statuses.empty?
  refute victim_commit.reload.deployable? # precondition: not satisfied before forgery

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  victim_commit.reload
  # equality that should hold but doesn't:
  # commit.stack_id (via sha match) == Repository.from_github_repo_name('attacker/unrelated-repo').stacks.pluck(:id)
  assert_equal 'soc/compliance', victim_commit.statuses.last.context
  assert_equal victim_stack.id, victim_commit.statuses.last.stack_id
  assert victim_commit.deployable? # BUG: forged status from unrelated repo satisfies ci.blocking
end
```
