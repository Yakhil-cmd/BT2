Based on my research, I found a concrete Polkadot SDK analog to the LMPVault `feeSink` DoS pattern inside the custom `pallet-psm` (Peg Stability Module) in this repository.

### Title
PSM `mint`/`redeem` permanently bricked when the fee sent to the fixed `fee_destination` account is below the internal asset's `min_balance` - (File: substrate/frame/psm/src/lib.rs)

### Summary
`pallet-psm`'s `mint` and `redeem` extrinsics are permissionless, signed dispatchables that, on every successful swap, route a protocol fee to a single admin-configured `fee_destination` account [1](#0-0) . Just like the LMPVault report where fee-share minting to `feeSink` can revert once `feeSink` crosses `perWalletLimit`, here the fee credit to `fee_destination` can revert if it is below the internal asset's `min_balance` the first time that account is credited, because `T::Fungibles::mint_into`/`transfer` ultimately go through `increase_balance`, which enforces `ensure!(amount >= details.min_balance, TokenError::BelowMinimum)` for any account that doesn't yet have an asset-account entry [2](#0-1) .

### Finding Description
In `mint`, after the swap accounting, the pallet unconditionally tries to credit the fee to `fee_destination`: [3](#0-2) 

`fee_destination` is set once at `create_psm` time and is not changeable by any dispatchable found in the pallet's call set (only `full_admin`/`emergency_admin` origins are reassignable) [4](#0-3) . `create_psm` only registers `fee_destination` as a system account via `inc_providers`, it does not create the corresponding *asset* account nor validate that the configured fee floor can satisfy the internal asset's `min_balance` [5](#0-4) .

Because the minimum fee obtainable per call is bounded below by `fee_rate * min_swap_amount` (the smallest legal swap), if that product is smaller than `T::Fungibles::minimum_balance(internal_asset)`, then the very first `mint_into(internal_asset, &fee_destination, fee)` call fails with `TokenError::BelowMinimum` and the `?` operator propagates the error, reverting the entire `mint()` extrinsic — for every user, permanently, since `fee_destination`'s asset account is never established. The same failure mode exists in `redeem`, which instead uses `T::Fungibles::transfer(internal_asset, &who, &info.fee_destination, fee, Preservation::Expendable)` for the fee leg [6](#0-5) , hitting the identical `increase_balance` check.

This mirrors the LMPVault root cause precisely:
- Both route a *mandatory* fee-collection step to a single fixed sink account before completing the core state transition.
- Both fee-sink accounts are subject to an account-level balance threshold (`perWalletLimit` vs. pallet-assets' `min_balance`).
- Neither implementation has a fallback (e.g., skip/best-effort the fee mint) if the threshold check fails, so the entire core function (`_collectFees`→`rebalance`/`updateDebtReporting` vs. PSM's `mint`/`redeem`) reverts and stays broken.
- Recovery in the LMPVault case is by raising `perWalletLimit`; here there is no discovered dispatchable to change `fee_destination` or migrate its asset account, making the PSM instance's core `mint`/`redeem` functionality permanently unusable once the failure is triggered.

### Impact Explanation
Once triggered, `Psm::mint` and `Psm::redeem` become permanently unusable for the affected `internal_asset`, freezing PSM functionality (no more minting/redeeming of the pegged stablecoin through that instance) with no in-pallet remediation path found (removal via `remove_psm` additionally requires zero outstanding debt on all externals, which is unreachable if users can't redeem). This is a deterministic denial of service on a core financial primitive triggered purely by ordinary, permissionless use (any signed account calling `mint`), matching the accepted severity class of the original Medium-rated LMPVault finding.

### Likelihood Explanation
Triggering requires that `fee_rate.mul_ceil(min_swap_amount) < T::Fungibles::minimum_balance(internal_asset)` for the configured `internal_asset`/`external_asset` pair — a config combination that is plausible (e.g., a low default fee like 0.5% combined with a small `min_swap_amount` relative to an asset with a non-trivial existential/minimum balance) but is dependent on the specific PSM instance parameters chosen at `create_psm`/`add_external_asset` time. I was not able to find any validation in `create_psm` or the external-asset/fee setters ensuring this invariant holds; nor could I fully verify the fee-rate setter code (`set_minting_fee`/`set_redemption_fee`) since I ran out of iterations before reading it in full. This is a real code-level absence of a defensive check, not merely a theoretical config error, since nothing in the pallet enforces or documents the constraint.

### Recommendation
- Validate, at `create_psm` and whenever `min_swap_amount`, `MintingFee`, `RedemptionFee`, or `fee_destination` are set, that the minimum possible fee is `>= T::Fungibles::minimum_balance(internal_asset)`, or
- Use `Precision::BestEffort`/skip the fee transfer gracefully (mirroring the "fold into burn rather than abort" pattern already used elsewhere in this repo, e.g. `settle_pgas_refund` in `pallet-revive`) [7](#0-6) , so a fee that cannot be delivered to `fee_destination` doesn't abort the whole swap.
- Pre-provision `fee_destination`'s asset account (e.g., a placeholder `touch`/top-up) at `create_psm` time to guarantee it always exists before any fee is minted.

### Proof of Concept
I could not execute a live reproduction (no filesystem/terminal access in this mode), and I was unable to fully confirm within my remaining tool budget whether `set_minting_fee`/`add_external_asset` impose any additional guard that would prevent this scenario — this should be verified by a developer with full repo access before treating this as fully confirmed. The failing guard identified is `ensure!(amount >= details.min_balance, TokenError::BelowMinimum)` in `substrate/frame/assets/src/functions.rs:511`, reachable transitively from the signed extrinsics `Psm::mint` (`substrate/frame/psm/src/lib.rs:754`) and `Psm::redeem` (`substrate/frame/psm/src/lib.rs:858-866`). A minimal integration test to confirm this would: (1) create an internal asset with a non-trivial `min_balance`, (2) `create_psm` with `min_swap_amount` and default/low `MintingFee` such that `fee_rate.mul_ceil(min_swap_amount) < min_balance`, (3) call `Psm::mint` with the minimum legal `external_amount`, and (4) assert the call fails with `TokenError::BelowMinimum` and that subsequent `mint`/`redeem` calls for any user continue to fail identically.

	/// Refund `RefundPercent` of `amount` from `from`'s PGAS hold to `to`'s free balance and
	/// burn the rest. Returns the amount actually transferred to `to` (excludes the burned
	/// portion).
	///
	/// If crediting `to` would violate its existential deposit (e.g. `to` has no asset
	/// account and the refund would create one below ED), the refund portion is folded into
	/// the burn rather than aborting the whole refund.
	///
	/// `amount` is capped at the PGAS actually held by `from`: when a recipient with no
	/// [`NativeDepositOf`] credit triggers a refund on a contract whose deposit was paid in
	/// native, the call settles whatever PGAS is actually held instead of reverting.
	fn settle_pgas_refund(
		reason: HoldReason,
		from: &T::AccountId,
		to: &T::AccountId,
		amount: BalanceOf<T>,
	) -> Result<BalanceOf<T>, DispatchError> {
		if amount.is_zero() {
			return Ok(BalanceOf::<T>::zero());
		}
		// Cap the amount we settle at what's actually held in PGAS. A refund recipient with
		// no `NativeDepositOf` credit on a contract whose deposit was paid in native would
		// otherwise route the full amount through PGAS and revert on `Precision::Exact`.
		let pgas_held = Self::pgas_on_hold(reason, from);
		let amount = amount.min(pgas_held);
		if amount.is_zero() {
			return Ok(BalanceOf::<T>::zero());
		}
		let refund = RefundPercent::get().mul_floor(amount);
		let mut burn = amount.saturating_sub(refund);
		let mut refunded = BalanceOf::<T>::zero();

		if !refund.is_zero() {
			let can_credit = matches!(
				<Mutator as fungibles::Inspect<T::AccountId>>::can_deposit(
					Id::get(),
					to,
					refund,
					Provenance::Extant,
				),
				DepositConsequence::Success
			);
			if can_credit {
				refunded = <Holder as fungibles::MutateHold<T::AccountId>>::transfer_on_hold(
					Id::get(),
					&reason.into(),
					from,
					to,
					refund,
					Precision::BestEffort,
					Restriction::Free,
					Fortitude::Polite,
				)?;
			} else {
				burn = burn.saturating_add(refund);
			}
		}
