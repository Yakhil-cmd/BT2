## Title
Rounding in `earned_headers_commission_recipients` distribution can inflate the number of bytes credited from headers commissions - (File: `headers_commission.js`)

### Summary
The reported Goldilocks bug is a rounding error in a fee/interest split (`FixedPointMathLib.mulWadUp`) that causes a tracked aggregate (`outstandingDebt`) to diverge from the true sum of individual obligations. The same rounding-divergence class exists in ocore's header-commission distribution logic: when a unit's authors declare `earned_headers_commission_recipients` with several percentage shares, each recipient's payout is computed independently with `Math.round()` (or SQL `ROUND()`), and the **sum of the rounded parts is never checked against the un-rounded total**. Because shares are attacker-controlled integers that only need to sum to 100, an attacker can pick shares that make every individual `round()` operation round *up*, producing a sum strictly greater than the actual `headers_commission` that was paid — i.e. minting extra spendable bytes.

### Finding Description
`validateHeadersCommissionRecipients()` only checks that the declared shares are positive integers summing to 100; it performs no check relating the rounding behavior to the true total amount: [1](#0-0) 

When main-chain indexes stabilize, `calcHeadersCommissions()` computes, for every "winner" unit, its share of the parent's `headers_commission` (`full_amount`) using per-recipient rounding, both in the MySQL SQL path and the SQLite/in-memory JS path: [2](#0-1) [3](#0-2) [4](#0-3) 

Each recipient's amount is `Math.round(full_amount * share / 100.0)` computed *independently* per recipient — there is no adjustment (e.g., giving the last recipient the remainder) to force the rounded parts to sum exactly to `full_amount`. Because `Math.round` rounds halves up (`Math.round(1.5) === 2`), an attacker who authors a multi-authored unit and declares two (or more) of their own addresses with shares whose fractional split of an odd `full_amount` lands exactly on `.5` boundaries (e.g. two recipients at 50%/50% against an odd headers_commission) will have *every* recipient's rounded amount rounded up, so the sum exceeds `full_amount` by 1 (or more, with more recipients/careful share selection).

These rounded, possibly-inflated amounts are inserted straight into `headers_commission_contributions` and then aggregated into `headers_commission_outputs`: [5](#0-4) 

`headers_commission_outputs` rows are later spendable as genuine `type: "headers_commission"` inputs, validated by amount using `mc_outputs.calcEarnings` which simply sums the (already-inflated) stored amounts — the validator has no way to detect the discrepancy because it trusts the previously-computed, already-rounded totals: [6](#0-5) 

This mirrors the Goldilocks pattern exactly: a per-item rounding operation (`mulWadUp`/`Math.round`) feeding into an aggregate/spendable balance (`outstandingDebt`/`headers_commission_outputs`) without reconciling the rounded parts against the true total, so the tracked aggregate diverges from reality.

### Impact Explanation
Unlike the original report (which only causes a revert/DoS), this ocore analog directly creates new spendable bytes with no corresponding input reduction anywhere in the system — the attacker's designated recipient addresses receive `headers_commission_outputs` rows whose sum exceeds the actual `headers_commission` fee that was paid by the parent unit's author. Since these outputs are fully spendable via ordinary `type: "headers_commission"` inputs, this is a genuine, repeatable supply-inflation vector: any unprivileged unit poster who is multi-authored (or who controls multiple addresses used as `earned_headers_commission_recipients`) can systematically bias share splits to always round in their favor whenever they win a headers-commission distribution, extracting free bytes from the network over time.

### Likelihood Explanation
The attacker fully controls the `earned_headers_commission_recipients` list and share percentages for any unit they author (only constrained to positive integers summing to 100 and sorted by address), and can use addresses they control as multiple "recipients." Winning headers commission from a parent unit happens as a normal, repeated part of protocol operation (any unit can become the winning child of a parent), so the attacker only needs patience/volume to repeatedly trigger the rounding-favorable split, making this a practical, low-cost, and repeatable attack rather than a one-off edge case.

### Recommendation
When distributing `full_amount` (headers commission or witnessing payout) among multiple recipients with percentage shares, avoid rounding each share independently. Instead:
- Compute the rounded amount for all but the last recipient, and assign the last recipient `full_amount - sum_of_previous_rounded_amounts` (remainder distribution), guaranteeing the total distributed exactly equals `full_amount`; or
- Track cumulative rounding error and adjust subsequent recipients' amounts to compensate, ensuring `SUM(amount) === full_amount` for every distribution event, in both the SQL (`headers_commission.js` MySQL branch) and JS (SQLite/in-memory) code paths.

### Proof of Concept
1. Attacker creates address `A` and address `B` (both controlled by attacker).
2. Attacker composes and posts a multi-authored unit `U` (authored by `A` and `B`) that becomes the winning "best child" for some parent unit `P` whose `headers_commission` (`full_amount`) is an odd number, e.g. `full_amount = 3`.
3. In `U`, attacker sets `earned_headers_commission_recipients = [{address: A, earned_headers_commission_share: 50}, {address: B, earned_headers_commission_share: 50}]` — this passes `validateHeadersCommissionRecipients` (sum = 100, both positive integers, sorted by address).
4. When `P` stabilizes, `calcHeadersCommissions()` computes for each recipient `amount = Math.round(3 * 50 / 100) = Math.round(1.5) = 2`, giving both `A` and `B` an amount of `2` bytes each — total `4` bytes credited into `headers_commission_outputs`, one more byte than the `3` bytes actually paid by `P`'s author.
5. Attacker later spends these `headers_commission_outputs` rows as ordinary `type: "headers_commission"` inputs; `validation.js`'s `calcEarnings`-based check (lines 2582-2598) accepts them because it only checks against the already-inflated stored totals.
6. Repeating this process across many headers-commission wins accumulates unbounded extra bytes with no corresponding fee payment, constituting supply inflation.

function validateHeadersCommissionRecipients(objUnit, cb){
	if (objUnit.authors.length > 1 && typeof objUnit.earned_headers_commission_recipients !== "object")
		return cb("must specify earned_headers_commission_recipients when more than 1 author");
	if ("earned_headers_commission_recipients" in objUnit){
		if (!isNonemptyArray(objUnit.earned_headers_commission_recipients))
			return cb("empty earned_headers_commission_recipients array");
		var total_earned_headers_commission_share = 0;
		var prev_address = "";
		for (var i=0; i<objUnit.earned_headers_commission_recipients.length; i++){
			var recipient = objUnit.earned_headers_commission_recipients[i];
			if (!isPositiveInteger(recipient.earned_headers_commission_share))
				return cb("earned_headers_commission_share must be positive integer");
			if (hasFieldsExcept(recipient, ["address", "earned_headers_commission_share"]))
				return cb("unknown fields in recipient");
			if (!isValidAddress(recipient.address))
				return cb("invalid recipient address checksum");
			if (recipient.address <= prev_address)
				return cb("recipient list must be sorted by address");
			total_earned_headers_commission_share += recipient.earned_headers_commission_share;
			prev_address = recipient.address;
		}
		if (total_earned_headers_commission_share !== 100)
			return cb("sum of earned_headers_commission_share is not 100");
	}
