### Title
Webhook signature scoped to `repository.owner.login` while stack resolution uses `repository.full_name` allows cross-organization stack mutation - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects the `GitHubApp` (and therefore the HMAC secret) used to validate the webhook signature based solely on `params.dig('repository','owner','login')`, an attacker-controlled field in the raw JSON body. `PushHandler` (and all other handlers) instead resolve the target `Stack`/`Repository` from a *different* field of the same untrusted body, `payload.dig('repository','full_name')`. Because these two fields are never cross-checked, an attacker who owns any org registered in `Shipit.github_apps` can sign a payload with their own `webhook_secret` while setting `full_name` to a victim's repository, causing the victim's stack to be mutated.

### Finding Description
The binding the code implicitly assumes is: `repository_owner used to pick webhook_secret == organization that owns repository.full_name used to resolve the mutated Stack`. This is never enforced.

- `verify_signature` computes `github_app = Shipit.github(organization: repository_owner)` and verifies `request.raw_post` against that org's `webhook_secret`: [1](#0-0) 
- `repository_owner` is read straight from the request body with no relation to any other field: [2](#0-1) 
- `#create` re-parses `request.raw_post` and dispatches to handlers using the *same* body: [3](#0-2) 
- `Handler#stacks`/`#repository_name` resolve the target repository from `payload.dig('repository','full_name')`, a completely independent field from `repository.owner.login`: [4](#0-3) 
- `PushHandler#process` then calls `stack.sync_github(expected_head_sha: params.after)` for every non-archived stack on the target branch of the resolved repository: [5](#0-4) 
- `Repository.from_github_repo_name` simply splits `full_name` on `/` and does a DB lookup with no ownership check against the verifying org: [6](#0-5) 

Attacker request: attacker crafts a JSON body where `repository.owner.login == "org-attacker"` and `repository.full_name == "org-victim/stack-repo"`, computes `X-Hub-Signature: sha1=HMAC(org-attacker_webhook_secret, raw_body)` (a secret the attacker legitimately possesses because Shipit is configured for their own org), and POSTs to `/webhooks` with `X-Github-Event: push`. `verify_signature` selects `Shipit.github(organization: 'org-attacker')`, computes the HMAC with the attacker's own secret over the exact bytes the attacker sent, and it matches — verification succeeds. `#create` then reparses the same bytes and `PushHandler` resolves stacks via `full_name = 'org-victim/stack-repo'`, finding the victim's real `Stack` and invoking `sync_github(expected_head_sha: params.after)` with an attacker-chosen `after` SHA.

Existing guards do not close this gap: `drop_unhandled_event` only checks the event type exists; `ExplicitParameters` schemas in handlers only enforce presence/type of `repository.full_name`, not its relationship to `repository.owner.login`; there is no code anywhere in the controller or `PushHandler`/`Handler` base class that compares `repository_owner` to the owner portion of `full_name`. The existing test suite (`test/controllers/webhooks_controller_test.rb`) never exercises a mismatched owner/full_name pair — it only tests unknown organizations and correctly-matched payloads, so this divergence is untested. `Repository.from_github_repo_name` (`app/models/shipit/repository.rb:53-56`) performs a pure lookup and has no awareness of which webhook secret validated the request.

### Impact Explanation
An unprivileged attacker who merely controls a GitHub organization/repo that has been separately onboarded to the same Shipit instance (a normal, low-privilege multi-tenant scenario supported by "Using Multiple GitHub Applications") can trigger `Stack#sync_github` — and by extension any other handler logic keyed off `repository.full_name` (pull_request handlers, review-stack archiving/unarchiving, label capture, etc.) — against a stack belonging to a completely different, victim organization, without ever possessing the victim's `webhook_secret`. This is a cross-repository/cross-tenant write triggered by a request authenticated only for the attacker's own tenant, matching the "Critical: a payload for one repository mutating another's stack" category. It is fully repeatable against any repository/stack registered on the shared Shipit instance, and applies to every webhook handler that trusts `full_name` (push, pull_request family, status, check_suite), not just push.

### Likelihood Explanation
Requires only that the Shipit instance is configured with `Shipit.github_apps` for more than one organization (documented, supported multi-tenant setup) and that the attacker's own org is one of them — a standard precondition, not a privileged one. The attacker needs no Shipit session, API token, or victim secrets; they only need to know their own `webhook_secret` (which they configured) and the victim's `full_name` (public information). The attack is a single crafted HTTP POST, trivially repeatable and scriptable.

### Recommendation
In `verify_signature`/`create`, after computing `repository_owner`, also parse `repository.full_name` and require that the owner segment of `full_name` matches `repository_owner` (and matches the organization whose secret verified the signature) before dispatching to handlers; reject the request (422) on mismatch. Equivalently, have handlers derive the repository solely from the same organization value used for signature verification rather than trusting `full_name` independently.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb
test "push payload signed by org-attacker cannot mutate org-victim's stack" do
  # Preconditions: Shipit.github_apps configured for 'org-attacker' and 'org-victim'
  # with distinct webhook_secret values; a Stack exists for org-victim/stack-repo on 'master'.
  attacker_secret = Shipit.github(organization: 'org-attacker').send(:webhook_secret)
  victim_stack = shipit_stacks(:victim) # repository full_name == 'org-victim/stack-repo', branch 'master'

  body = {
    ref: 'refs/heads/master',
    after: 'deadbeef' * 5,
    repository: { owner: { login: 'org-attacker' }, full_name: 'org-victim/stack-repo' }
  }.to_json

  signature = 'sha1=' + OpenSSL::HMAC.hexdigest('sha1', attacker_secret, body)

  @request.headers['X-Github-Event'] = 'push'
  @request.headers['X-Hub-Signature'] = signature

  Shipit::Stack.any_instance.expects(:sync_github).never # assert the equality: verifying org != repo-owning org, so no mutation should occur

  post :create, body:, as: :json

  # Current (vulnerable) behavior: sync_github IS called on victim_stack despite
  # signature having been verified only against org-attacker's secret.
  # assert_response :unprocessable_entity  # expected after fix
end
```
This test demonstrates the equality `repository_owner ('org-attacker') != full_name owner ('org-victim')` is never checked, and that `sync_github` is invoked on the victim's stack using a request authenticated only under the attacker's own webhook secret.
