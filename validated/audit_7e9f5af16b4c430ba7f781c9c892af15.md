## Title
Multisig transaction payload-mismatch check is feature-gated, allowing an executing owner to run an unapproved payload — ([File: aptos-move/framework/aptos-framework/sources/multisig_account.move])

## Summary
`validate_multisig_transaction` (the VM-invoked prologue for `MultisigTransaction`) only compares the executor-supplied `payload` against the on-chain-stored full `transaction.payload` when the feature flag `abort_if_multisig_payload_mismatch_enabled` is turned on. When the payload was stored in full on-chain via `create_transaction` (as opposed to `create_transaction_with_hash`), and this feature is disabled, there is no invariant enforcing that the payload actually executed equals the payload that other owners voted to approve.

## Finding Description
`multisig_account::validate_multisig_transaction` is the function the VM calls as part of the transaction prologue for a `MultisigTransaction` payload:
<cite repo="Jaredbentat/aptos-core--034" path="aptos-move/framework/aptos-framework/sources/multisig_account.move" start="1361="384" end="1385" />

Looking at the exact logic: [1](#0-0) 

There are two independent checks:
1. If `transaction.payload_hash.is_some()` (i.e., the owner used `create_transaction_with_hash`), the supplied `payload` is unconditionally hashed and compared to the stored hash — this path is always enforced.
2. If `transaction.payload.is_some()` (i.e., the owner used `create_transaction`, storing the *full* payload on-chain), the match between the caller-supplied `payload` argument and the stored `transaction.payload` is **only checked when `features::abort_if_multisig_payload_mismatch_enabled()` returns true**: [2](#0-1) 

Meanwhile, actual execution in the VM deserializes and executes whatever payload bytes are supplied with the `MultisigTransaction` transaction variant at submission time (not necessarily the one voted on), via `execute_multisig_payload`: [3](#0-2) 

If the feature flag is disabled (its default/rollout state matters — I could not fully confirm the current default state of `ABORT_IF_MULTISIG_PAYLOAD_MISMATCH` in this environment; that would need verification via `types/src/on_chain_config/aptos_features.rs` and `aptos-move/aptos-release-builder/src/components/feature_flags.rs`), an owner who is authorized to *execute* the queued transaction (i.e., has reached quorum in `num_approvals`) can pass an entirely different payload than the one other owners voted on, and it will execute successfully, because:
- The owner/approval-count check (`num_approvals >= num_signatures_required`) only validates quorum on the *sequence number*, not on the specific payload content, when `payload.is_some()` and the mismatch-abort feature is off.
- Only the hash-based path (`create_transaction_with_hash`) enforces content-binding unconditionally.

This breaks the "approval validation accepting the wrong approval set" invariant explicitly called out in the admission pivots — the quorum that voted "yes" is bound to sequence number, not to payload content, whenever the mismatch check is disabled.

## Impact Explanation
This allows a malicious multisig owner with execution rights to substitute a completely different `MultisigTransactionPayload` (e.g., transferring funds to their own address, or calling a different entry function/module) than what other owners approved, while still passing the "quorum" check because the vote/approval accounting is keyed on `sequence_number`, not on payload identity. This is a state-transition-under-the-wrong-approval-set bug — the transaction that executes on behalf of the multisig account is not the transaction that received the required signatures/votes.

## Likelihood Explanation
Exploitation requires:
1. The multisig owners to create transactions via `create_transaction` (full payload on-chain) rather than `create_transaction_with_hash`.
2. The `abort_if_multisig_payload_mismatch_enabled` feature to be disabled on the network at the time.
3. The attacker to be one of the k-of-n owners with the ability to submit the final `MultisigTransaction` executing call (any owner can execute once quorum is reached).

I was not able to fully confirm, within the remaining tool budget, whether this feature flag is enabled by default in the current mainnet/testnet configuration, or whether it was already enabled unconditionally in a later change (the presence of the flag and its explicit feature-gating in the source strongly suggests it was added as a fix-in-progress/rollout gate, which itself implies there was a past window, and possibly still is on some deployments, where this check does not apply). This uncertainty affects the practical likelihood assessment.

## Recommendation
Make the full-payload match check (`payload == stored_payload` when `transaction.payload.is_some()`) unconditional, independent of the `abort_if_multisig_payload_mismatch_enabled` feature flag, mirroring the unconditional hash-check path. If the flag exists purely for a staged rollout, ensure it is enabled everywhere before considering this fixed, and add an explicit invariant/test that `create_transaction`-based multisig transactions cannot execute with a payload different from the one stored at creation, regardless of feature-flag state.

## Proof of Concept
Not independently verified end-to-end due to inability to confirm the on-chain default state of the feature flag within the available tool budget. Conceptual PoC:
1. Owner A calls `create_transaction(owner_A, multisig_addr, payload_X)` (transfer 10 APT to owner_B).
2. Owners B and C approve (assume 2-of-3 threshold reached with A + B).
3. With `abort_if_multisig_payload_mismatch_enabled` disabled, Owner A submits a `MultisigTransaction` execution with a different `payload_Y` (e.g., transfer 10,000 APT to Owner A's own address).
4. `validate_multisig_transaction` passes because quorum (`num_approvals >= num_signatures_required`) is satisfied on the sequence number and the payload/hash-mismatch checks are skipped (since `payload_hash` is `None` and the feature flag is off).
5. `execute_multisig_payload` executes `payload_Y`, not `payload_X`, against the multisig account.

**Confidence caveat:** This candidate is architecturally sound based on the source code read, but I could not confirm (a) the live/default status of the `abort_if_multisig_payload_mismatch_enabled` feature flag, or (b) whether an additional safeguard elsewhere (e.g., in `aptos_vm.rs` prior to calling into the module) re-validates payload identity outside this Move function. Further verification of `types/src/on_chain_config/aptos_features.rs` feature-flag defaults and any related recent commit history would be needed to fully confirm exploitability today.

        // on chain.
        let multisig_account_resource = borrow_global<MultisigAccount>(multisig_account);
        let transaction = multisig_account_resource.transactions.borrow(sequence_number);
        if (transaction.payload_hash.is_some()) {
            let payload_hash = transaction.payload_hash.borrow();
            assert!(
                sha3_256(payload) == *payload_hash,
                error::invalid_argument(EPAYLOAD_DOES_NOT_MATCH_HASH),
            );
        };

        // If the transaction payload is stored on chain and there is a provided payload,
        // verify that the provided payload matches the stored payload.
        if (features::abort_if_multisig_payload_mismatch_enabled()
            && transaction.payload.is_some()
            && !payload.is_empty()
        ) {
            let stored_payload = transaction.payload.borrow();
            assert!(
                payload == *stored_payload,
                error::invalid_argument(EPAYLOAD_DOES_NOT_MATCH),
            );
        }
