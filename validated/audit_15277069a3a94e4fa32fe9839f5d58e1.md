### Title
`in_data_feed` formula op fails to reject the internal `\n` key-delimiter in attacker-controlled `feed_name`/`feed_value`, allowing data-feed condition forgery - (File: formula/evaluation.js)

### Summary
The AWS advisory describes a defense-in-depth gap where special characters (quotes/backslashes) supplied to a policy-building routine were not escaped before being embedded into a structured document, letting an attacker corrupt the intended field boundaries of that document. The analogous mechanism in ocore is the leveldb key format used for data feeds: `'df\n'+address+'\n'+feed_name+'\n'+type+'\n'+encoded_value+'\n'+mci` [1](#0-0) . `\n` is the field delimiter, and every code path that *writes* a feed (`validateInlinePayload`, `aa_validation.js`) explicitly rejects `feed_name`/`value` containing `\n` [2](#0-1) [3](#0-2) . However, the runtime `in_data_feed` oscript operator, which lets an AA query whether a data feed exists, evaluates `feed_name` and `feed_value` from arbitrary (trigger-controlled) formula expressions and only checks that they are non-empty/typed values — it never rejects embedded `\n` bytes or applies the `MAX_DATA_FEED_NAME_LENGTH`/`MAX_DATA_FEED_VALUE_LENGTH` limits used everywhere else.

### Finding Description
In `formula/evaluation.js`, the `in_data_feed` case evaluates `oracles`, `feed_name`, and `feed_value` from formula expressions that can depend on `trigger.data` (fully attacker-controlled by whoever posts the triggering unit): [4](#0-3) 

The only validation performed is:
- `oracles` must split into valid addresses,
- `feed_name` must be a non-empty string,
- `feed_value` must pass `isValidValue`.

None of these checks reject the `\n` byte or bound the string length to the data-feed limits. The result is passed straight to `dataFeeds.dataFeedExists` → `dataFeedByAddressExists`, which builds a leveldb range query by naive string concatenation: [5](#0-4) 

Because real oracle-posted feeds are guaranteed `\n`-free (enforced at posting time), the *stored* keys always have `feed_name` and `value` cleanly delimited by single `\n` bytes. But an attacker driving the `in_data_feed` query can set `feed_name` to a string that itself contains embedded `\n` characters that mimic the internal `type`/`value`/`mci` structure of the key. Since leveldb range lookups match on raw bytes rather than semantic fields, this lets the attacker construct a `gt`/`lt` range (see the `'>' `/`'>='`/`'<'`/`'<='` branches at lines 148-164) that matches an *unrelated* key actually written by the oracle for a *different* feed name/value, or that widens the match window to any record under the oracle's `df\n<address>\n` prefix. This defeats the intended semantics of `in_data_feed`, which is supposed to answer "did this specific oracle post this specific feed_name satisfying this specific relation to this value" — instead it can be tricked into a false positive using data the oracle posted for an entirely different purpose.

### Impact Explanation
`in_data_feed` is the exact primitive AAs use to gate fund release, e.g., oracle-based betting/prediction markets, price-triggered payments, insurance payouts, etc. If an AA lets any part of the feed_name/value expression be influenced by trigger data (a common and endorsed pattern for flexible oracle-driven AAs, mirrored by the address-definition-level `"in data feed"` templated examples in the codebase's own tests) [6](#0-5) , an unprivileged trigger sender can forge a positive "data feed exists" result without the referenced oracle ever having posted matching data. This is a concrete path to AA fund loss (unauthorized release of AA-held funds) purely by choosing a delimiter-laden `feed_name` in the triggering unit's `data` field — no compromise of the oracle, hub, or network is required.

### Likelihood Explanation
Reachable by a single unprivileged AA trigger sender against any deployed AA that forwards trigger-supplied data into the `feed_name` or `feed_value` arguments of `in_data_feed` (a documented, encouraged oscript feature for building generic oracle-driven AAs). No special privileges, node compromise, or timing races are needed — only crafting a trigger unit with an appropriately delimiter-laden data field.

### Recommendation
In the `in_data_feed` case of `formula/evaluation.js`, before calling `dataFeeds.dataFeedExists`, reject `feed_name` and any string `feed_value` that contain `\n`, and enforce `constants.MAX_DATA_FEED_NAME_LENGTH` / `constants.MAX_DATA_FEED_VALUE_LENGTH`, mirroring the checks already present in `validation.js` (lines 1933-1943) and `aa_validation.js` (lines 95-111). This restores the invariant that the key-value delimiter can never appear inside an externally-controlled field used to build the composite leveldb key.

### Proof of Concept
1. An oracle address `ORACLE` posts a legitimate, unrelated data feed, e.g. `data_feed: {heartbeat: "alive"}`, at some mci `M` — this is stored (illustratively) as key `df\nORACLE\nheartbeat\ns\nalive\n<encoded M>`.
2. A malicious user deploys or targets an AA whose oscript formula executes something like:
   `in_data_feed({oracles: trigger.data.oracle, feed_name: trigger.data.feed, feed_value: {operator: '>', value: 1000000}})`
   intended to require the oracle to have posted a price feed above 1,000,000 before releasing funds.
3. The attacker sends a trigger unit with `data.oracle = "ORACLE"` and `data.feed` set to a string embedding `\n` bytes crafted to reproduce the byte sequence `heartbeat\ns\nalive` (or another arbitrary already-posted key suffix) so that the `gt`/`lt` range built in `dataFeedByAddressExists` for relation `'>'` matches the pre-existing `heartbeat` key even though the oracle never posted any numeric feed above 1,000,000.
4. `dataFeedExists` returns `true`, the AA's condition is satisfied, and funds are released without the oracle ever posting the required condition — demonstrating unauthorized fund release via `in_data_feed` key-delimiter injection.
