### Title
CCMenu API client is created without a `stack_id`, so its token authorizes reads against every stack - ([File: app/controllers/shipit/ccmenu_url_controller.rb])

### Summary
`CCMenuUrlController#fetch` finds-or-creates a single shared `ApiClient` per user named `'CCMenu Client'` with `permissions: %w[read:stack]`, but never sets `stack:` on the created record. Because `Shipit::Api::BaseController#stacks` only restricts the queryable stacks when `current_api_client.stack_id?` is true, a token minted for one stack's ccmenu URL in fact authorizes `GET /api/stacks/:any_stack_id/tasks` for every stack in the installation.

### Finding Description
Binding claimed by the design: `client.stack_id == stack.id` (the stack passed as `params[:stack_id]` to `#fetch`) should be the only stack the returned `authentication_token` can read.

Code path:
- `app/controllers/shipit/ccmenu_url_controller.rb:15-18`: `client` is `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')`. The `find_or_create_by!` lookup/creation attributes are only `creator` and `name`; `stack` is never assigned. `stack:` is computed at line 20-22 (`Stack.from_param!(params[:stack_id])`) but only used to build the returned URL (`uri = URI(api_stack_ccmenu_url(stack_id: stack.to_param))`), never passed into the `ApiClient` attributes.
- `app/models/shipit/api_client.rb:8`: `belongs_to :stack, optional: true` — confirming `stack_id` can be `nil` and is not required.
- `app/controllers/shipit/api/base_controller.rb:74-76`:
```
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end
```
Since `current_api_client.stack_id` is `nil` for the CCMenu client, `stacks` resolves to `Stack.all`.
- `app/controllers/shipit/api/tasks_controller.rb:9-15` (`index`/`show`) and its `require_permission :read, :stack` only check `permissions.include?('read:stack')` via `ApiClient#check_permissions!` (`app/models/shipit/api_client.rb:38-45`) — this checks the permission *name*, not stack scoping. `stack` is resolved via `stacks.from_param!(params[:stack_id])` (`base_controller.rb:78-80`), which succeeds for **any** stack id because `stacks` is `Stack.all`.

Because the same `'CCMenu Client'` record is reused (`find_or_create_by!` matches on `creator`+`name` only, regardless of which stack's ccmenu URL is being requested), the very first stack a user requests a ccmenu URL for creates an unscoped `ApiClient`, and subsequent `fetch` calls for other stacks reuse and reveal the token for that same unscoped client. Either way, `stack_id` is never populated, so the resulting `authentication_token` (`app/models/shipit/api_client.rb:34-36`) is a bearer credential valid for `Stack.all`, not just the requested stack.

None of the existing guards close this gap: `require_permission :read, :stack` only checks the permission list, not the `stack_id` scope; `authenticate_api_client` only verifies the signed token identifies a valid `ApiClient` row; there is no additional check anywhere in `Api::TasksController` or `Api::BaseController` that cross-references the token's intended stack against `params[:stack_id]`.

Attacker/operator flow: An operator (any authenticated Shipit user, not necessarily privileged beyond normal use) requests `GET /stacks/:id/ccmenu.xml` (routed to `CCMenuUrlController#fetch`), extracts `token` from the returned `ccmenu_url`, then replays `Authorization: Basic <base64(token)>` (or equivalent HTTP Basic auth) against `GET /api/stacks/:another_stack_id/tasks`. Because `stacks` falls back to `Stack.all`, the request succeeds and returns task data for a stack the token was never meant to authorize.

### Impact Explanation
This is unauthenticated-scope-widening read access: a credential intended to be scoped to reading CI status of one stack (via the CCMenu XML feed, typically shared in dashboards, chat, or embedded in CI tools) becomes a valid Basic-auth bearer token for reading task/deploy history (`Shipit::Api::TasksController#index`/`#show`) of **every** stack in the Shipit instance, including stacks/repositories the token holder/sharer has no relation to. This matches the "High - unauthenticated read of stack state, task streams or deploy output" impact category, since anyone who obtains a leaked/shared ccmenu URL (which is explicitly designed to be shared externally, e.g., embedded in CI dashboards) gains broad read access across all stacks, not just the one advertised. It is fully repeatable — the token doesn't expire and is reused across all ccmenu requests by the same user.

### Likelihood Explanation
Preconditions are minimal: any Shipit user with access to trigger `GET /stacks/:id/ccmenu.xml` for at least one stack (a normal, low-privilege operator action, and the entire point of the CCMenu feature is to hand this URL to external tools). No GitHub secrets, webhook secrets, or `api_clients_secret` are needed by the attacker — only possession of a shared/leaked `ccmenu_url`. Given ccmenu URLs are designed for external consumption (CI dashboards, monitoring tools), the likelihood of them leaking beyond their intended stack context is realistic and the exploit requires just two HTTP requests.

### Recommendation
When creating the CCMenu `ApiClient`, include `stack:` (or `stack_id: stack.id`) in both the `create_with` attributes and the `find_or_create_by!` lookup key (or create a distinct client per stack, e.g. name it uniquely per stack), so `current_api_client.stack_id?` is true and `stacks` correctly narrows to `Stack.where(id: current_api_client.stack_id)`.

### Proof of Concept
```ruby
# test/controllers/ccmenu_url_controller_test.rb (conceptual addition)
test "ccmenu token is scoped to the requested stack only" do
  stack1 = shipit_stacks(:shipit)
  stack2 = shipit_stacks(:cyclimse) # any other stack fixture
  session[:user_id] = shipit_users(:walrus).id

  get :fetch, params: { stack_id: stack1.to_param }
  token = URI.decode_www_form(URI(JSON.parse(response.body)['ccmenu_url']).query).to_h['token']

  client = Shipit::ApiClient.authenticate(token)
  assert_equal stack1.id, client.stack_id, "token must be scoped to stack1"

  # Demonstrate the break: replay token against a different stack's tasks endpoint
  authorization = ActionController::HttpAuthentication::Basic.encode_credentials(token, '')
  get "/api/stacks/#{stack2.to_param}/tasks", headers: { 'Authorization' => authorization }
  assert_response :forbidden # currently fails: returns 200 with stack2's tasks because client.stack_id is nil
end
```
Both sides of the binding (`client.stack_id` vs. `stack1.id`) diverge: `client.stack_id` is `nil` while `stack1.id` is non-nil, and the second request against `stack2` succeeds instead of being rejected — confirming the vulnerability.
