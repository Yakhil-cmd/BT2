Confirmed root cause: `Handler#stacks` resolves target stacks purely from `payload.dig('repository', 'full_name')` on the raw-body-derived hash [1](#0-0) , which is completely independent of which organization's secret was used to authenticate the request.

### Title
Signature-org / repository-written binding bypass via query-string override of `repository_owner` in `WebhooksController` - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub organization's `webhook_secret` to validate the HMAC signature against using `repository_owner`, which reads from the framework's `params` (query string merged with body) [2](#0-1) [3](#0-2) . The actual event processing in `create`, however, re-parses the raw POST body independently via `JSON.parse(request.raw_post)` and dispatches that hash to handlers [4](#0-3) . In Rails, query-string parameters override body parameters on key collisions in the merged `params` hash, so an attacker can supply `?repository[owner][login]=<org>` to steer which organization's secret is checked, while the JSON body (used for actual processing) references a completely different, unrelated repository.

### Finding Description
The binding that should hold is: *organization authenticated == repository that is written*. This bug breaks it into two independent values:

1. **Organization authenticated**: `repository_owner` in `verify_signature`, sourced from `params.dig('repository','owner','login')` — the standard `ActionController::Base#params`, which merges query-string and body parameters (query wins on conflicts) [3](#0-2) .
2. **Repository written**: `repository_name` in `Handler#repository_name`, sourced from `payload.dig('repository','full_name')` where `payload` is the *local* variable from `JSON.parse(request.raw_post)` built fresh in `create`, unaffected by query parameters [5](#0-4) [6](#0-5) .

`Shipit.github(organization:)` looks up a per-organization config, including its own independent `webhook_secret` [7](#0-6) [8](#0-7) , and `GitHubApp#verify_webhook_signature` **returns `true` unconditionally if that organization has no configured `webhook_secret`** [9](#0-8) . Multi-org configs with some organizations lacking a secret are an explicitly supported and documented configuration [10](#0-9) [11](#0-10) .

An attacker who knows (or can guess) the login of *any* configured GitHub organization that either has no `webhook_secret` set, or whose secret the attacker knows, can send a POST to `/webhooks` with:
- Query string `?repository[owner][login]=<weakly-protected-org>`
- Body JSON whose `repository.full_name`/`repository.owner.login` targets a **different** victim stack that is protected by a distinct (unknown-to-the-attacker) `webhook_secret`
- `X-Github-Event: push` (or `status`, `check_suite`, etc.)

`verify_signature` resolves the organization from the query-overridden `repository_owner`, finds `webhook_secret` blank for that org, and passes verification unconditionally (or trivially, since the attacker knows that secret). `create` then re-parses the raw body and dispatches to `PushHandler`, which resolves stacks strictly by `repository.full_name` from the body — targeting the victim's stack regardless of which organization was "authenticated" [12](#0-11) .

### Impact Explanation
This allows an unauthenticated attacker to forge GitHub webhook events (push, status, check_suite, etc.) for an arbitrary victim stack whose true `webhook_secret` they never possess, as long as any other organization in the multi-org config has a weak/absent secret. Forged `push` events trigger `stack.sync_github(expected_head_sha:)` [12](#0-11) , and forged `status`/`check_suite` events can manipulate commit statuses that gate deploys/merges — an unauthorized influence over the deploy/merge pipeline of a stack the attacker does not control, matching the "unauthorized deploy" impact class.

### Likelihood Explanation
Requires: (a) knowledge of at least one configured GitHub organization login in the multi-org setup (often discoverable, e.g., from public GitHub org/app installation pages or Shipit UI), and (b) that organization having no/weak `webhook_secret` — a configuration explicitly supported and shown in the docs/examples without warning about this cross-org consequence. No authentication, GitHub App installation, or repository access is required by the attacker.

### Recommendation
Do not derive `repository_owner` from the framework's merged `params`; instead derive it from the same `JSON.parse(request.raw_post)` value used for actual processing (or explicitly ignore query parameters entirely for this controller). Additionally, verify that the organization used to select the webhook secret matches the organization owning the repository actually dispatched to handlers, and consider disabling the "no secret configured ⇒ auto-pass" behavior in `verify_webhook_signature` for multi-org installations.

### Proof of Concept
```
POST /webhooks?repository[owner][login]=weakly-protected-org HTTP/1.1
X-Github-Event: push
Content-Type: application/json
(X-Hub-Signature: omitted, or computed with weakly-protected-org's known secret)

{
  "ref": "refs/heads/master",
  "after": "deadbeef...",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "victim-org" }
  }
}
```
`verify_signature` resolves `repository_owner` from the query string (`weakly-protected-org`) and passes verification (secret blank ⇒ `verify_webhook_signature` returns `true`) [9](#0-8) . `create` then re-parses the body and dispatches the payload referencing `victim-org/victim-repo` to `PushHandler`, which finds and syncs the victim stack [12](#0-11) .

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
