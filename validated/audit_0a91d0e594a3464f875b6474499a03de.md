### Title
CCMenu API endpoint ignores `ApiClient#stack_id` scoping, allowing a stack-scoped token to read any other stack's status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::BaseController` restricts stack access for scoped API clients via the `stacks` helper (`Stack.where(id: current_api_client.stack_id)` when `stack_id` is set), and every other API controller resolves the target stack through `stacks.from_param!`. `Shipit::Api::CCMenuController` overrides `#stack` to call `Stack.from_param!(params[:stack_id])` directly, bypassing that scope entirely, so an `ApiClient` restricted to one stack can fetch the CCMenu XML (`activity`/`lastBuildStatus`/`lastBuildTime`) of any other stack in the installation.

### Finding Description
The intended invariant, enforced everywhere else in the API, is:
`stack_returned_to_client == (current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all).from_param!(params[:stack_id])`

This is implemented in `BaseController#stacks`/`#stack`: [1](#0-0) 

`CCMenuController` overrides `#stack` and drops the scoping: [2](#0-1) 

So the actual binding becomes `stack_returned_to_client == Stack.from_param!(params[:stack_id])`, independent of `current_api_client.stack_id`. `require_permission :read, :stack` only checks that the string `"read:stack"` is present in `ApiClient#permissions`; it never checks which stack the permission applies to: [3](#0-2) 

The rendered view exposes the real `activity`/`lastBuildStatus`/`lastBuildTime` of whatever stack was resolved: [4](#0-3) 

Exploit flow: an operator issues an `ApiClient` scoped to stack A only (`belongs_to :stack, optional: true` with `stack_id` set) with the `read:stack` permission, intended to only ever see stack A via `GET /api/stacks/:stack_id/cc.xml`. Because `CCMenuController#stack` never consults `current_api_client.stack_id`, that same token can request `GET /api/stacks/<stack_B>/cc.xml` and receive stack B's real build status. All other resource controllers (`StacksController#stack`, `TasksController`, `DeploysController`, `LocksController`, `HooksController#hooks`) correctly go through `stacks.from_param!`/`stack_id:` scoped queries, so this is an isolated regression specific to CCMenu.

### Impact Explanation
A tenant/client holding a token intentionally scoped to a single stack (e.g. via `ApiClient.stack_id`) can read the deploy activity and last build status of every other stack in the Shipit instance by simply changing the `stack_id` path/query parameter — a cross-tenant unauthorized read of stack state, repeatable against arbitrary stacks with a single GET request each. This matches the High-severity category "unauthorized read of stack state" across tenants sharing one Shipit deployment.

### Likelihood Explanation
Preconditions: the operator must have issued at least one stack-scoped `ApiClient` with `read:stack` permission (a normal, documented way to restrict a CI/CD integration to one project) and shared it with a less-trusted tenant/repo owner. Given that, the attack costs a single authenticated HTTP GET with a different `stack_id` — no secrets, no privileged role, and fully repeatable. This is a realistic multi-tenant Shipit deployment scenario.

### Recommendation
Remove the `#stack` override in `CCMenuController` (or make it use the inherited `stacks.from_param!(params[:stack_id])`) so CCMenu status lookups respect `current_api_client.stack_id` scoping like every other API controller.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb
test "a stack-scoped client cannot read another stack's status" do
  stack_a = shipit_stacks(:shipit)
  stack_b = Stack.create!(repository: Repository.new(owner: "other", name: "repo"), branch: "main")
  stack_b.update!(lock_reason: "locked", locked_since: Time.current) # force distinct merge_status

  @client.update!(stack: stack_a, permissions: ['read:stack'])

  get :show, params: { stack_id: stack_b.to_param, token: @client.authentication_token }

  project = get_project_from_xml(response.body)
  # Broken binding: stack resolved == Stack.from_param!(params[:stack_id]) regardless of @client.stack_id
  assert_equal stack_b.to_param, project['name']            # attacker-chosen stack B is returned
  refute_equal stack_a.merge_status, project['lastBuildStatus'].downcase # real stack B status leaked, not stack A's
end
```
This demonstrates the CCMenu response for stack B contains stack B's real `activity`/`lastBuildStatus` even though the authenticated `ApiClient` is scoped only to stack A via `stack_id`.
