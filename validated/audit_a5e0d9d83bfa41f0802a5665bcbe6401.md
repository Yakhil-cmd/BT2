### Title
Falsy-cap (`cap: 0`) treated as "uncapped" enables unbounded re-issuance of an AA-defined asset - ([File: aa_composer.js])

### Summary
The Gearbox report flags a pattern where code checks whether a value **exists** (`getLastPrice(...)` returning non-zero-ish presence) instead of checking that the value is actually meaningful (`> 0`). The same class of bug — using a truthy/falsy check on `cap` instead of validating the actual numeric semantics of "capped vs. uncapped" — exists in `aa_composer.js`'s asset-issuance logic and its counterpart in `inputs.js`.

### Finding Description
When an AA defines an asset via an `asset` message, `cap` can be a formula string (`aa_validation.js` `validatePayload` case `'asset'`, lines 230-241) that is only checked to be a syntactically valid formula at definition time — its *runtime result* is not constrained to be a positive integer before it is used to decide issuance behavior.

At issuance time, `aa_composer.js` decides whether the asset is "capped" purely by JS truthiness: [1](#0-0) 
```
var issue_amount = objAsset.cap || (target_amount - total_amount);
...
if (objAsset.cap) { // only our AA can issue, no unstable consensus-breaking issues possible
    conn.query("SELECT 1 FROM inputs WHERE type='issue' AND asset=?", [asset], function(rows){
        if (rows.length > 0) // already issued
            return cb2('already issued');
        addIssueInput(1);
    });
}
else{
    conn.query( // filtered by our AA's address, all equally visible on all nodes
        "SELECT MAX(serial_number) AS max_serial_number FROM inputs WHERE type='issue' AND asset=? AND address=?",
        [asset, address],
        function(rows){
            var max_serial_number = (rows.length === 0) ? 0 : rows[0].max_serial_number;
            addIssueInput(max_serial_number+1);
        }
    );
}
```
The identical pattern also exists in the light-wallet coin-picking path: [2](#0-1) 

Both places treat `objAsset.cap` as a boolean: if `cap` evaluates to `0` (a legitimate numeric value the AA author's formula could produce, e.g. from `trigger.data`-derived logic, or from `otherwise ''`/`0` fallbacks such as in the `create_an_asset.oscript` sample: `cap: "{trigger.data.cap otherwise ''}"`), the code silently falls into the "uncapped" branch. In that branch, issuance is no longer restricted to a single issue event guarded by "already issued" — instead the AA can issue again and again with incrementing `serial_number`, i.e. the "single issuance of a fixed total supply" guarantee that a capped asset is supposed to provide is bypassed.

This mirrors the Gearbox bug exactly: the code checks *existence/truthiness* of `cap` (`objAsset.cap`) rather than validating that the underlying condition ("is this asset actually capped, i.e. `cap` is a defined positive number") holds. `0` is a value that exists (was explicitly set) but is treated as "does not exist."

### Impact Explanation
An AA author who parameterizes `cap` via a formula (directly or indirectly influenced by external trigger data, which is explicitly one of the reachable actors per scope: "AA trigger sender") can cause an asset intended to be capped to instead behave as freely re-issuable, since the "already issued" single-shot guard is skipped. This is a supply-inflation bug for an AA-controlled asset: repeated triggers can mint the asset multiple times under the "uncapped" code path even though the AA definition nominally declares a `cap`, breaking the cap invariant that other parts of the protocol/consumers rely on (e.g., `validation.js` "issue must be equal to cap" logic at line 2345 also uses the same falsy check `objAsset.cap &&`, so a `cap` of `0` bypasses that validation entirely too, at line `2321`/`2345` in `validation.js`).

### Likelihood Explanation
Requires a specific AA design where `cap` is set from a formula that can evaluate to `0` under attacker/trigger-influenced conditions, or an AA author mistake. It is not a universal, always-exploitable path (unlike the original report's "any token pair"), so likelihood is Medium: it depends on how the AA author wires `cap`, but any AA that computes `cap` dynamically from user/trigger-supplied data is exposed, and this is a documented, encouraged pattern (`create_an_asset.oscript` sample ships with `cap` sourced from `trigger.data.cap`).

### Recommendation
Replace the truthiness checks on `cap` throughout `aa_composer.js`, `inputs.js`, and `validation.js` with an explicit numeric check, e.g. `typeof objAsset.cap === 'number' && objAsset.cap > 0` (or the Decimal-aware equivalent used elsewhere in the codebase), so that `cap === 0` is treated as "capped with zero supply" (and likely rejected outright as invalid) rather than silently interpreted as "uncapped."

### Proof of Concept
1. Deploy an AA whose `asset` message sets `cap: "{trigger.data.cap otherwise ''}"` (as in the shipped `create_an_asset.oscript` sample) and whose subsequent issuance logic relies on `objAsset.cap` to gate a single issuance.
2. Send a trigger with `data.cap = 0` (or omit `cap` so the formula evaluates to `''`/`0` depending on AA logic) when defining the asset — this passes `aa_validation.js`'s definition-time checks because `cap` is a formula string, not a literal, so `isPositiveInteger` is never enforced on the runtime value.
3. Trigger issuance: `aa_composer.js`'s `issueAsset()` evaluates `objAsset.cap` as falsy (`0`), takes the `else` branch, and issues using `serial_number` increments instead of the single-shot "already issued" check.
4. Send additional triggers to invoke issuance again — each one succeeds and increments `serial_number`, producing unbounded additional supply of an asset the AA definition labeled as `cap`-bearing.

*(Note: full confirmation of this PoC requires runtime-tracing how the `asset` message's `cap` formula result is passed into `assetInfos[asset]` inside `aa_composer.js`'s `handleTrigger`, which I could not fully inspect due to iteration limits — the exact code path that populates `objAsset` from the evaluated `asset` message payload was not retrieved. This should be verified by a follow-up code review before treating this as fully confirmed.)*
