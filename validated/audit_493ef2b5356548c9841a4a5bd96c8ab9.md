Based on my research, I found a concrete analog: the `attested` operator in address-definition validation loops over an attacker-controlled attestor-address array with **no cap on array length**, while `MAX_ATTESTORS_PER_ASSET` (64) exists and is enforced for the equivalent asset-attestor path but not here, and the op's cost is not reflected in the complexity/ops budget the way sibling ops (e.g. `in data feed`) are.

### Title
Unbounded attestor-list loop in address-definition `attested` op enables cheap complexity-budget bypass and disproportionate validation/query cost - (File: definition.js)

### Summary
`validateDefinition()`'s `attested` case in `definition.js` accepts an arbitrary-length array of attestor addresses (`args[1]`) and iterates over every element with only an `isValidAddress` check, without ever bounding the array length or charging additional complexity/op cost proportional to its size, unlike the sibling `in data feed` op (`arrAddresses`) which explicitly does `complexity += arrAddresses.length-1`.

### Finding Description
In `definition.js`, the `attested` op is validated as: [1](#0-0) 
This is analogous in kind to Wireshark's CVE-2022-0585 class of bug: a "large loop in a dissector" that is not bounded relative to the complexity/anti-spam accounting the surrounding validator otherwise relies on. Every `evaluate()` call increments `complexity`/`count_ops` by exactly 1 regardless of `arrAttestors.length`: [2](#0-1) 
Compare this to the `in data feed` op just below it in the same function, which explicitly scales complexity with the size of its address array: [3](#0-2) 
The `attested` op has no equivalent scaling, and no length cap like `MAX_ATTESTORS_PER_ASSET` used for the analogous asset-attestor-list path: [4](#0-3) 
At authentication time (`validateAuthentifiers`), the same op re-evaluates and passes the entire attacker-supplied attestor array straight into a DB query via `storage.filterAttestedAddresses`: [5](#0-4) 

### Impact Explanation
Because `attested` only costs 1 complexity unit no matter how large `arrAttestors` is, an attacker can embed it inside heavily-nested `or`/`and` combinators — which are the mechanism `MAX_COMPLEXITY`/`MAX_OPS` are meant to bound — and get many multiples of unbounded-length attestor arrays validated/evaluated for the price of one complexity unit each. Each unit posting an address definition (or any transaction authenticating against such a definition) causes the node to loop through and validate every attestor address, and later to build/run a SQL query with all of them, every time the address signs. Since the cost scales with array size but the complexity accounting used to throttle validation work does not, this creates disproportionate CPU/DB work per byte of "charged" complexity compared to the `in data feed` op that was explicitly hardened this way — a node-disagreement/DoS-adjacent inefficiency reachable by any unprivileged unit poster defining or using such an address.

### Likelihood Explanation
Reachable directly and repeatedly by any unprivileged party who posts a unit containing an `attested` address-definition clause or signs with an address defined that way; no special privilege, hub, or peer position is required — only a normally-formed unit within existing size limits (`MAX_UNIT_LENGTH`), which the codebase's own comparison (`in data feed` charging per-address) indicates was recognized as a needed safeguard for size-based address lists but omitted here.

### Recommendation
Bound `arrAttestors.length` in the `attested` case (e.g., cap it similarly to `MAX_ATTESTORS_PER_ASSET`) and/or scale `complexity`/`count_ops` by `arrAttestors.length` the same way `in data feed` does, both in `validateDefinition`'s `evaluate()` (validation time) and in `validateAuthentifiers`'s `evaluate()` (authentication time), so that validation cost is proportionally reflected in the complexity budget that gates overall unit processing cost.

### Proof of Concept
Construct an address definition such as:
```
['attested', ['this address', [<N distinct valid base32 addresses>]]]
```
wrapped inside nested `['or', [...]]`/`['and', [...]]` branches to multiply the number of `attested` evaluations, keeping total `complexity` at/below `constants.MAX_COMPLEXITY` (100) and `count_ops` below `constants.MAX_OPS`, while each `attested` clause carries an attestor array as large as the remaining unit-size budget (`constants.MAX_UNIT_LENGTH`, default 5e6 bytes) allows. Post the unit defining/using this address; validation and each subsequent authentication against it will perform O(total attestor entries across all clauses) work while the complexity/op accounting only reflects the number of `attested` clauses (≤ MAX_COMPLEXITY), not their aggregate size — unlike `in data feed`, whose complexity scales with `arrAddresses.length` per [6](#0-5) .

function checkAttestorList(arrAttestors){
	if (!isNonemptyArray(arrAttestors))
		return "attestors not defined";
	if (arrAttestors.length > constants.MAX_ATTESTORS_PER_ASSET)
		return "too many attestors";
	var prev="";
	for (var i=0; i<arrAttestors.length; i++){
		if (!isValidAddress(arrAttestors[i]))
			return "invalid attestor address: "+JSON.stringify(arrAttestors[i]);
		if (arrAttestors[i] <= prev)
			return "attestors not sorted";
		prev = arrAttestors[i];
	}
	return null;
}
