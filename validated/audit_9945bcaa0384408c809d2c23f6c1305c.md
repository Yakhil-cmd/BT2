### Title
Stack-scoped API token authorization bypass in CCMenuController - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
An `ApiClient` token that is deliberately scoped to a single `Stack` (via `ApiClient#stack_id`) can be used against the `Shipit::Api::CCMenuController#show` endpoint to read the build/deploy status of **any** stack in the Shipit instance, not just the one it was authorized for.

### Finding Description
`Shipit::Api::BaseController` establishes the invariant that a scoped `ApiClient` (one with a non-nil `stack_id`) may only resolve `stack` from the set of stacks it is authorized for: [1](#0-0) 

This binds "the stack a token authorizes" (`current_api_client.stack_id`) to "the stack an action touches" (`stack`). Every other API controller (`DeploysController`, `TasksController`, `RollbacksController`, `HooksController`, etc.) inherits this `stack` method unmodified.

`CCMenuController`, however, overrides `stack` to resolve directly from the global `Stack` model, completely ignoring `current_api_client.stack_id`: [2](#0-1) 

`require_permission :read, :stack` at the top of the controller only checks that the token has the generic `read:stack` permission string via `ApiClient#check_permissions!`; it does not check which stack the token is scoped to: [3](#0-2) 

So the equality that should hold — `current_api_client.stack_id == stack.id` whenever the client is stack-scoped — is broken specifically in this controller. Any holder of a valid, stack-A-scoped token (created via `ApiClientsController#create` and possibly shared with a limited-trust integration, e.g. a CI dashboard) can supply an arbitrary `stack_id` param to read stack B's, C's, etc. build state.

### Impact Explanation
This is an unauthenticated-scope read of stack state: a credential deliberately restricted to one stack's status is usable to enumerate build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `activity`, lock state, `webUrl`) for every stack managed by the Shipit instance. This matches the High-severity class of "escalation into `Shipit.github_teams` authorization" / "unauthenticated read of stack state" defined for this engine, since it crosses a repository/stack authorization boundary that the `ApiClient.stack_id` scoping mechanism is specifically designed to enforce.

### Likelihood Explanation
Exploitation only requires possession of any valid `ApiClient` authentication token scoped to a single stack (a low-privilege credential intentionally distributed to third-party tools like CI status dashboards, since `CCMenuController` supports simple query-string token auth) and knowledge/guessing of another stack's `stack_id` param (stack slugs are typically `owner/repo/environment`-style and often predictable/enumerable). No additional privileges are required beyond the scoped token itself.

### Recommendation
Remove the `stack` override in `CCMenuController`, or reimplement it to reuse `BaseController#stacks` (i.e., `stacks.from_param!(params[:stack_id])`) so that stack-scoped tokens remain confined to their authorized stack, consistent with every other API controller.

### Proof of Concept
1. As an admin, create an `ApiClient` scoped to `stack_id: A` with `permissions: ['read:stack']` (via `ApiClientsController#create`), and note its `authentication_token`.
2. Send `GET /api/ccmenu/:B_stack_id?token=<token_scoped_to_A>` where `B` is a different stack.
3. Observe `assert_response :ok` with `B`'s build status XML returned, even though the token's `stack_id` is `A` — confirmed by the fact that `CCMenuController#stack` (`app/controllers/shipit/api/ccmenu_controller.rb:29-31`) never consults `current_api_client.stack_id`, unlike `BaseController#stack` (`app/controllers/shipit/api/base_controller.rb:74-80`) which every other endpoint relies on.
