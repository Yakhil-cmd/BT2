### Title
Address-order-biased slot allocation in `applyViolationTransition` allows a below-MinStake `ValActive` validator to remain active and collect block rewards for up to one full epoch — (`kaiax/valset/impl/transition_context.go`)

### Summary
When multiple `ValActive` validators simultaneously fall below `MinStake` and the `MaxSlotAvailable` slot budget is exhausted by the first (lowest-address) demotion, all remaining below-MinStake validators are silently skipped and stay `ValActive`. Because `ValExiting → ValInactive` only fires at epoch boundaries, the slot stays consumed for the entire inter-epoch window, and the skipped validators receive block rewards they are not entitled to.

### Finding Description
`applyViolationTransition` iterates validators in ascending address order via `sortedAddrs := newValidators.Addresses()`. [1](#0-0) 

The `hasSlot` closure counts the live `ValExiting` entries in `newValidators` and compares against `ctx.MaxSlotAvailable`. Once the first below-MinStake `ValActive` validator is demoted, `CountByState(ValExiting)` equals `MaxSlotAvailable`, so `hasSlot` returns `false` for every subsequent candidate. [2](#0-1) 

The slot is not released until `applyEpochTransition` fires T1 (`ValExiting → ValInactive`). [3](#0-2) 

Between epochs, every block re-runs `applyViolationTransition`, finds the slot still full, and skips the remaining below-MinStake validators again.

`slotLimitsFor` with `n = 6` yields `MaxSlotAvailable = 1`, `MinActiveCount = 4` — a realistic production configuration. [4](#0-3) 

### Impact Explanation
The skipped validator remains `ValActive`, is included in the qualified validator set, proposes and signs blocks, and receives KAIA block rewards for up to one full epoch. This is an unauthorized reward distribution affecting KAIA system-managed funds.

### Likelihood Explanation
Requires two or more `ValActive` validators to drop below `MinStake` simultaneously within the same epoch, with `MaxSlotAvailable = 1` (occurs for `n ∈ {4, 5, 6, 7, 8}` active validators — small but real networks). Stake can drop due to unstaking, slashing, or consolidation changes. No privileged access or key compromise is required; the trigger is purely on-chain staking state.

### Recommendation
After each demotion within the loop, recheck whether the slot is now free before skipping. Alternatively, prioritize demotion candidates by stake amount (lowest stake first) rather than address order, so the most-violating validator is always processed first. At minimum, document that address order determines demotion priority and that below-MinStake validators may remain active for up to one epoch when the slot budget is exhausted.

func maxSlotAvailable(n uint64) uint64 {
	if n < 4 {
		return 0
	}
	return (n/3 + 1) / 2
