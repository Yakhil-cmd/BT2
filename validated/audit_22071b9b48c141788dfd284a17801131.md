### Title
Webhook signature verified against an attacker-controlled organization field while handlers act on a different, unscoped repository key - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` chooses which GitHub App / `webhook_secret` to validate the HMAC signature against using a value taken directly from the untrusted JSON payload (`repository.owner.login`, falling back to `organization.login`), while the handlers that actually mutate state key off a *different* field of the same payload (`repository.full_name`) — or, in the case of `StatusHandler`, off no repository scoping at all. Any GitHub organization legitimately onboarded onto a shared Shipit instance (an unprivileged actor with respect to other orgs' stacks) can produce a validly-signed webhook using its own known secret while pointing the payload's action-relevant fields at another organization's repository/commits.

### Finding Description
`verify_signature` derives the org used to pick the verifying secret purely from payload content: [1](#0-0) [2](#0-1) 

This chooses `Shipit.github(organization: repository_owner)` and verifies the raw body against *that org's* `webhook_secret`: [3](#0-2) 

Once verified, the same raw JSON body is dispatched to handlers, but the handler base class resolves the target `Stack`/`Repository` from a *different* JSON key — `repository.full_name` — not from `repository.owner.login` that was used for signature selection: [4](#0-3) 

Nothing re-validates that `repository.owner.login` (used to pick/verify the secret) matches `repository.full_name` (used to pick the mutated stack). Because the attacker controls the entire raw JSON body and signs it with their own org's secret, they can freely set `repository.full_name` to any other onboarded org/repo string.

The impact is worse for `StatusHandler`, which doesn't even use `repository_name`/`full_name` scoping — it looks up commits **globally by sha** across the whole install and writes a GitHub-reported status onto them: [5](#0-4) 

So an org with a valid (self-known) `webhook_secret` can forge a `status` event, signed with its own secret, containing an arbitrary `sha` belonging to a completely unrelated stack/org, and `create_status_from_github!` will attach that (attacker-chosen) status/state to it. `PushHandler` similarly resolves stacks via the attacker-supplied `full_name` and calls `sync_github`: [6](#0-5) 

This is structurally the same class of bug as the reported `OrchidDirectory.pull()` issue: a check performed against one key (`stake` itself / `repository.owner.login`) is assumed to guarantee correctness for an operation actually keyed on something else (`last` / `repository.full_name`, or nothing at all for `StatusHandler`), breaking the intended binding "organization authenticated == repository written."

### Impact Explanation
Forged commit statuses feed directly into merge-queue and continuous-deployment gating logic (`MergeRequest#all_status_checks_passed?`, `Status::Group`), which decide whether a PR is auto-merged or whether continuous delivery proceeds to deploy. An attacker who controls one onboarded, low-privilege GitHub org can inject a "success" status for a commit sha belonging to a different organization's stack, potentially unblocking an unauthorized merge or deploy for a repository they have no legitimate access to — a cross-repository write / unauthorized merge/deploy, matching the Critical-severity bucket in scope.

### Likelihood Explanation
Exploitation requires only that the attacker control any single organization already configured on the shared Shipit instance (i.e., knows their own org's `webhook_secret`, which is a normal, unprivileged tenant capability) and can send an HTTP POST to `/webhooks` with a crafted JSON body — no access to other orgs' secrets, tokens, or the target repository is needed.

### Recommendation
- After signature verification, re-derive the acting organization strictly from the same field used for verification (`repository.owner.login`/`organization.login`) and require that the repository/stack resolved by handlers belong to that same, already-authenticated organization before performing any lookups or mutations.
- Scope `StatusHandler` (and any other handler) queries by the verified repository, not by a global `sha` lookup across all stacks.
- Prefer deriving the verifying organization from a value that cannot be independently manipulated relative to the value used for the write path (e.g., always use `repository.full_name`'s owner segment for both verification and lookup, consistently).

### Proof of Concept
1. Attacker legitimately controls (or registers) organization `attacker-org` on a shared multi-tenant Shipit deployment, and knows `attacker-org`'s `webhook_secret`.
2. Attacker crafts a `status` webhook payload:
   ```json
   {
     "sha": "<victim-repo commit sha>",
     "state": "success",
     "context": "ci/anything",
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/some-repo" }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org secret, body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `verify_signature` resolves `repository_owner = "attacker-org"`, fetches `attacker-org`'s app/secret, and the HMAC matches — verification passes.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — which is not scoped to `attacker-org` at all — and calls `create_status_from_github!`, writing an attacker-controlled "success" status onto a commit belonging to a victim organization's stack, potentially unblocking that stack's merge queue or continuous deployment.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
