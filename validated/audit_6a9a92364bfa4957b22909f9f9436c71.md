### Title
Webhook signature verification is keyed on `organization.login`/`repository.owner.login` while handlers act on the unrelated `repository.full_name` field, letting an attacker who controls one GitHub org write to stacks belonging to another org - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / webhook secret to verify against using `repository_owner`, derived from `params.dig('repository','owner','login')` or `params.dig('organization','login')`. Once the signature check passes, the raw, unconstrained payload is handed to the event handlers, which look up the target `Stack`/`Repository` using an entirely different field, `payload.dig('repository','full_name')`, with no check that this value belongs to the same organization that was used to authenticate the request. ### Finding Description
This mirrors the Halborn report's root cause: `Treasury.premiumIncome` mutated `poolIncome[_poolId]` using an attacker-supplied `_poolId`/`_amount` with no check that the caller was the trusted `policyCenter`, so the value that got acted upon (the pool being credited) was never bound to the identity that was supposed to control it. Here, the binding that should hold is:

`organization/account used to verify the HMAC signature == organization owning the repository the handlers write to`

`verify_signature` computes `repository_owner` from the JSON body and fetches the `GitHubApp`/webhook secret configured for *that* organization via `Shipit.github(organization: repository_owner)`, then validates `X-Hub-Signature` against the raw body using that org's secret. This only proves "the sender knows the webhook secret configured for org X" - it says nothing about which repository the payload's `repository.full_name` claims to represent for the purposes of stack lookup.

Once `head(422)` isn't triggered, `WebhooksController#create` re-parses the same raw body and dispatches it unmodified to every registered `Handler` for that event. Every handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, `PullRequest::*Handler`, etc.) inherits `Handler#stacks`, which resolves the target `Repository`/`Stack` purely from `payload.dig('repository', 'full_name')` - a field that is never cross-checked against the `repository_owner`/`organization.login` value used for signature verification.

Because a GitHub webhook payload's top-level `organization`/`repository.owner` object and the nested `repository.full_name` string are two independent JSON fields, nothing stops an attacker who legitimately owns/administers a GitHub organization "Attacker-Org" (and therefore can configure a webhook there and knows its own `webhook_secret`) from sending a POST to Shipit's webhook endpoint with:
- `organization.login` / `repository.owner.login` = `"Attacker-Org"` (so `verify_signature` picks Attacker-Org's own configured webhook secret, which the attacker knows, and the HMAC computed with that secret validates),
- `repository.full_name` = `"victim-org/victim-repo"` (an unrelated repository that has a Shipit `Stack` configured).

The signature check only proves the request is authentically signed by *some* organization's secret that Shipit trusts - it does not prove the payload actually originates from GitHub for the `victim-org/victim-repo` repository. The handler layer then blindly trusts `repository.full_name` to select which `Stack` records receive status updates, commit records, PR merge-status changes, etc.

### Impact Explanation
This breaks the authentication/authorization boundary between "organization that signed the webhook" and "repository whose Shipit state is mutated." Depending on which handler is invoked, an attacker who controls their own GitHub org's webhook secret can:
- Inject fabricated commit statuses / check-suite results (`StatusHandler`, `CheckSuiteHandler`) into another org's stack, potentially flipping "deployable" gating checks used before deploy/merge decisions.
- Inject fabricated `push` events tied to a victim stack (`PushHandler`), affecting undeployed-commit tracking and possibly triggering continuous deployment logic for a stack the attacker does not own.
- Inject fabricated pull-request/merge events for a victim's merge queue.

This does not directly grant RCE or steal `GITHUB_TOKEN`, but it can result in an unauthorized deploy/merge decision being influenced by attacker-forged repository status data written into a stack the attacker doesn't control, which matches the "unauthorized deploy, rollback, or merge" / "escalation" impact classes called out in the rules.

### Likelihood Explanation
Requires only that the attacker control (or create) any GitHub organization and register a Shipit-recognized webhook for it (which needs only a `secrets.yml`/config entry mapping that org to a webhook secret Shipit is configured to trust - a normal, low-privilege setup step for any org onboarded to the shared Shipit instance). No repository write access to the victim repo, no `ApiClient` token, and no session/GitHub App private key on the victim's side is required, since the attacker signs with their own org's secret and only forges the unrelated `repository.full_name` field.

### Recommendation
In `Handler#repository_name` / `Handler#stacks`, validate that the resolved repository's owner matches the organization that was used to verify the webhook signature (i.e., thread `repository_owner` through to the handler and assert `repository.full_name.split('/').first == repository_owner`, or equivalently verify against `Repository#owner`). Reject the payload (422) on mismatch, analogous to fixing `premiumIncome` by requiring the caller identity to match the entity the mutation is scoped to.

### Proof of Concept
1. Attacker administers GitHub org `attacker-org` and configures a webhook pointed at the shared Shipit instance's `/webhooks` endpoint, choosing/knowing the webhook secret Shipit is configured to use for `attacker-org` (a normal setup action within the attacker's own org, requiring no access to `victim-org`).
2. Attacker crafts a `status` (or `push`/`check_suite`) event JSON body:
   ```json
   {
     "organization": { "login": "attacker-org" },
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
     "sha": "<forged-sha>",
     "state": "success",
     "context": "ci/required-check"
   }
   ```
3. Attacker computes `X-Hub-Signature` with `attacker-org`'s known webhook secret over the raw body and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: 'attacker-org')` and validates the signature successfully (matches `app/controllers/shipit/webhooks_controller.rb:24-30,59-62`).
5. `WebhooksController#create` dispatches the parsed body to `Shipit::Webhooks.for_event('status')`, and `StatusHandler` (via `Handler#stacks`/`#repository_name`, `app/models/shipit/webhooks/handlers/handler.rb:32-38`) resolves stacks for `"victim-org/victim-repo"` and writes the forged commit status into the victim's stack - despite the request never being authenticated as coming from `victim-org`.
