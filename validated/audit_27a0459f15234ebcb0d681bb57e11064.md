This confirms the vulnerability. `StatusHandler#process` performs a global lookup with no organization/repository scoping:

```ruby

    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

The controller's `verify_signature` only checks that the signature matches the webhook secret for `repository_owner` (derived from the payload's own `repository.owner.login`), which is entirely attacker-controlled since the attacker owns that org and its webhook secret. It never checks that the resolved `Commit`'s stack/repository belongs to that same organization. [2](#0-1) 

The binding claimed broken: `verified_repository_owner (from payload.repository.owner.login, checked only against Shipit.github(organization: repository_owner).verify_webhook_signature)` == `commit.stack.repository.owner (the actual owner of the stack containing the commit matched by sha)`. Tracing the code: `verify_signature` binds trust only to whichever org name appears in the payload body itself, and does not cross-check anything about the commit that gets mutated. `StatusHandler#process` then does a completely global `Commit.where(sha: params.sha)`, with no `stack_id`, no `github_repo_name`, no organization filter at all — so any commit row anywhere in the DB with that sha is mutated, regardless of which repo/org it came from. `commit.create_status_from_github!(params)` calls `add_status`, which can trigger `deployable_status` hooks and schedule merges via `ProcessMergeRequestsJob`. Both sides of the equality are checked before code execution and after: before, they're only implicitly assumed equal (typical case, attacker owns both), but after tracing, they are never actually enforced equal anywhere in the request path. The existing test suite only exercises the same-org case (`repository_params` hardcoded to `shopify` matching the stack's `github_repo_name`), so it never catches the cross-tenant divergence. ### Title
Cross-tenant commit status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits globally by `sha` with no scoping to the organization/repository that authenticated the webhook via `verify_signature`. An attacker who controls their own GitHub org (and thus its webhook secret) can forge a `status` event naming a sha belonging to a commit under a completely different victim stack, and have `create_status_from_github!` mutate that victim commit's CI status.

### Finding Description
The broken binding: `payload.repository.owner.login` (the org whose webhook secret validated the HMAC in `WebhooksController#verify_signature`) should equal `commit.stack`'s owning repository/organization for every `Commit` mutated by the handler, but `StatusHandler#process` never checks this. `verify_signature` resolves `Shipit.github(organization: repository_owner)` purely from the attacker-supplied JSON body and verifies the signature against that org's secret — which the attacker legitimately possesses for their own org.

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

Attacker request: POST `/webhooks` with header `X-Github-Event: status`, `X-Hub-Signature` computed with the attacker's own org's webhook secret, and a body whose `sha` is a known victim commit sha (e.g. leaked via a public GitHub commit page or task output URL) but `repository.owner.login` set to the attacker's own controlled org. `verify_signature` succeeds because it only checks the attacker's own org's secret against the attacker's own org name — it has no relationship to the sha in the body. `StatusHandler#process` then finds the victim's `Commit` row purely by `sha` (globally, no `stack_id`/`repository` filter) and calls `commit.create_status_from_github!(params)`, writing a forged `state`/`description`/`target_url` onto it, potentially flipping `deployable_status` and firing `ProcessMergeRequestsJob`.

### Impact Explanation
A completely unrelated org's webhook can write CI status onto any known commit sha belonging to any other tenant's stack in the same Shipit instance. This can flip `deployable_status` to `success`, unlocking `schedule_merges`/auto-merge behavior on a victim's commit, or conversely mark a legitimate victim commit as `failure`/`error` to block deploys — a cross-repository, cross-tenant unauthorized write matching "Critical: a payload for one repository mutating another's stack/commit."

### Likelihood Explanation
Attacker only needs to control one GitHub org already onboarded to the same Shipit instance (their own repo/org, legitimately) and to know a target commit sha of another tenant's stack (commit shas are not secrets — visible on public GitHub pages, PR pages, task output, etc.). No Shipit credentials, session, or victim org secrets are required. This is trivially repeatable against any known sha.

### Recommendation
Scope the lookup in `StatusHandler#process` to commits whose stack's repository matches the verified `repository_owner`/`repository.full_name` from the payload (e.g. join through `stack.repository` and filter by owner/name), mirroring the pattern used in `CheckSuiteHandler`, which at least scopes by `stacks.where(branch: ...)` although it too should verify repository ownership explicitly.
