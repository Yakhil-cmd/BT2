### Title
Webhook signature verification is keyed on `repository.owner.login`, but repository writes are keyed on the independent `repository.full_name` field, enabling cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate the HMAC signature against using `repository.owner.login` (or `organization.login`), while every webhook handler that actually mutates state resolves the target repository/stack from the independent `repository.full_name` field of the very same JSON body. Because these are two separate, attacker-controlled fields inside one payload, an actor who legitimately administers a GitHub App/organization onboarded to this Shipit instance (and therefore legitimately possesses that org's `webhook_secret`) can sign a payload whose `owner.login` matches their own org (to pass signature verification) but whose `full_name` names a repository belonging to a different organization onboarded to the same instance, causing Shipit to act on that other organization's stacks.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` does: [1](#0-0) 
selecting `github_app = Shipit.github(organization: repository_owner)`, where `repository_owner` is: [2](#0-1) 
i.e. `params.dig('repository', 'owner', 'login')`.

Once the signature check passes, `create` blindly dispatches the raw parsed body to every registered handler for the event: [3](#0-2) 

Every default handler (push, pull_request opened/closed/reopened, etc.) resolves the repository/stack to act on from a *different* field of that same body — `repository.full_name` — not `repository.owner.login`: [4](#0-3) [5](#0-4) 

`Repository.from_github_repo_name` simply splits `full_name` on `/` and looks the repo up with no cross-check against the payload's `owner.login`: [6](#0-5) 

Because HMAC-SHA1/256 verification only proves that *some* secret holder produced the whole byte string — it says nothing about which logical sub-field of the JSON should be trusted for authorization decisions — the engine effectively authenticates "this request came from organization X" (via `owner.login`) but then authorizes "act upon repository Y" (via `full_name`), where X and Y are independent, attacker-controlled strings in the same payload. In a multi-tenant Shipit deployment (multiple GitHub orgs/Apps configured via `Shipit.github(organization:)`), any org administrator who owns a legitimate, correctly-configured GitHub App integration for their *own* org holds that org's real `webhook_secret` as a normal, expected credential of running Shipit for their team. That legitimately-scoped secret is exactly what breaks the binding: it authenticates "org X" but the request body can still cause writes against org Y's `Stack`/`Repository`/`ReviewStack` records, e.g. `PushHandler#process` calling `stack.sync_github`, or `PullRequest::OpenedHandler` calling `ReviewStackAdapter#find_or_create!`, or `ClosedHandler#process` calling `review_stack.archive!` on org Y's review stack.

### Impact Explanation
This crosses the "cross-repository writes" impact bar explicitly listed as Critical: an entity authenticated as organization X can trigger repository-state-changing webhook handlers (sync, review-stack creation/archival/unarchival, label capture) against a stack that belongs to organization Y, entirely outside X's GitHub permissions and outside of any Shipit session/API-client credential for Y. This is a break of the deployment-trust binding "organization that authenticated == repository that is written," which the verification logic fails to enforce.

### Likelihood Explanation
Exploitability requires: (1) the Shipit instance is configured for more than one GitHub organization/App (`Shipit.github(organization: ...)` supports this multi-tenant configuration), and (2) the attacker administers/owns one of those onboarded orgs' GitHub Apps (a routine, unprivileged-relative-to-Shipit position — they only have rights over their own org, not others). Given that, forging the JSON body is trivial: swap `repository.full_name` (and, if needed, the PR/user sub-objects) to point at the victim org/repo while keeping `repository.owner.login` equal to the attacker's own org so their own valid secret verifies. No Shipit user session, `ApiClient` token, or stolen secret is needed — only the attacker's own legitimately-obtained per-org webhook secret, which is a normal, minimally-privileged credential in this trust model, not a bypass of any credential boundary.

### Recommendation
Bind the field used for signature-secret selection to the same field used for authorization/repository resolution: verify the signature against the app/secret owning `repository.full_name` (or `organization.login` when there is no repository), or, more robustly, after verifying the signature, re-derive the acting organization from `Repository.from_github_repo_name(full_name).owner` and reject the request unless it equals `repository_owner` used for verification. Handlers should never trust `full_name` in isolation from the field that determined which secret authenticated the request.

### Proof of Concept
1. Shipit instance configured with two orgs, `org-a` and `org-b`, each having its own GitHub App and `webhook_secret` (per `Shipit.github(organization:)`), where the attacker owns/administers `org-a`'s App.
2. Attacker crafts a `pull_request` (or `push`) webhook JSON body with:
   - `repository.owner.login = "org-a"` (so `WebhooksController#repository_owner` picks `org-a`'s app/secret)
   - `repository.full_name = "org-b/victim-repo"` (the field every handler actually uses to resolve the target `Repository`/`Stack`)
3. Attacker computes `X-Hub-Signature` over the raw body using `org-a`'s legitimately-known `webhook_secret`.
4. POST to `/webhooks` with `X-Github-Event: pull_request`. `verify_signature` calls `Shipit.github(organization: "org-a").verify_webhook_signature(...)`, which succeeds because the attacker signed with `org-a`'s real secret.
5. `Webhooks.for_event('pull_request')` handlers run; `OpenedHandler#repository` resolves `Repository.from_github_repo_name("org-b/victim-repo")`, and `ReviewStackAdapter#find_or_create!` creates/mutates a review stack under `org-b` — despite the request having authenticated only as `org-a`.
