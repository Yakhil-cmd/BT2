### Title
Unauthenticated GitHub webhook forgery escalates into `Shipit.github_teams` authorization when a multi-org deployment leaves one organization's `webhook_secret` unset - (File: lib/shipit/github_app.rb)

### Summary
In a multi-organization Shipit deployment, each GitHub App/organization has its own independent `webhook_secret`. `GitHubApp#verify_webhook_signature` treats a blank `webhook_secret` as a degenerate case that trivially passes verification (`return true unless webhook_secret`) instead of failing closed, exactly like the `py_ecc` `prime_field_inv(0, p)` bug that silently returned a "valid" value (`0`) for a degenerate input instead of raising. Because `WebhooksController#verify_signature` selects which organization's `GitHubApp` (and therefore which secret) to check against using an organization name taken straight from the *unverified* request body, an attacker can simply address their forged payload to any configured organization whose secret is blank and have the "verified" check pass unconditionally. This lets an unprivileged attacker forge a `membership` event that adds an arbitrary GitHub login to a `Team`, which is exactly the object consulted by `Shipit.github_teams`/`User#authorized?` for application authorization.

### Finding Description
`GitHubApp#verify_webhook_signature` is: [1](#0-0) 

`webhook_secret` is optional and configured per-organization; multiple shipped example/test configs demonstrate leaving it blank as a supported configuration for an organization (`webhook_secret: # nil`): [2](#0-1) [3](#0-2) 

`WebhooksController#verify_signature` selects the `GitHubApp` (and thus the secret used for verification) using `repository_owner`, which is read directly out of the still-unverified JSON body: [4](#0-3) 

So, for any multi-org install where `OrgTwo` (say) has `webhook_secret` unset, an attacker with no Shipit session, no `ApiClient` token and no GitHub credentials can POST directly to `/webhooks` with `X-Github-Event: membership`, an arbitrary `X-Hub-Signature` (or none at all — `nil.split("=",2)` on a missing header would raise, but any junk value works because the check short-circuits before it's ever used), and `{"organization": {"login": "OrgTwo"}, ...}`. `verify_webhook_signature` returns `true` immediately because `webhook_secret` is blank, and the request is fully processed as if genuinely delivered by GitHub.

`MembershipHandler#process` then executes attacker-controlled team mutations with no further checks: [5](#0-4) 

`Team#add_member` and `Team.find_or_create_by!`/`User.find_or_create_by_login!` will create the `Team` and `User` records on the fly if they don't already exist, and `add_member` unconditionally appends the attacker-chosen login to the team's membership: [6](#0-5) 

That membership is exactly what gates application access: `User#authorized?` checks whether the current user's teams intersect `Shipit.github_teams` (built from `github.oauth.teams`), and `Authentication#force_github_authentication` enforces this on every controller that includes it: [7](#0-6) [8](#0-7) 

The equality that should hold is: **`GitHubApp#verify_webhook_signature` returns true if and only if the request signature was actually produced with that organization's `webhook_secret` over `request.raw_post`.** Instead, when `webhook_secret` is blank for the organization named in the (unverified) payload, the function returns true for *any* signature, breaking the binding between "GitHub App configured for organization X authenticated this payload" and "payload is treated as originating from GitHub for organization X."

### Impact Explanation
An attacker who controls (or can create) any ordinary GitHub account can:
1. Forge a `membership` `added` event for an organization in the deployment whose `webhook_secret` is unset, adding their own GitHub login to a `Team` that backs one of `Shipit.github_teams`.
2. Complete a normal GitHub OAuth login with that same account.
3. Pass `User#authorized?` and gain full access to the Shipit UI/API endpoints protected by `force_github_authentication` (stacks, repositories, api_clients, deploys, etc.), despite never having been a legitimate member of the authorizing GitHub team.

This is an authentication/authorization bypass: escalation into `Shipit.github_teams` authorization by an attacker who otherwise holds no privileged credential, matching the in-scope High-impact category.

### Likelihood Explanation
This requires only:
- A multi-organization deployment (a documented, first-class configuration per `docs/setup.md`'s "Using Multiple Github Applications" section and shipped example config files).
- At least one configured organization with a blank `webhook_secret` (also explicitly shown as a supported value in the shipped example/config fixtures).
- Network access to the public `/webhooks` endpoint and an ordinary GitHub account.

No repository write access, no App private key, no `ApiClient` token, and no existing Shipit session are needed, so this is reachable by a fully unprivileged external attacker in any such deployment.

### Recommendation
`verify_webhook_signature` should not treat a missing `webhook_secret` as automatic success; at minimum it should fail closed (or the engine should require/validate that every configured organization has a non-blank `webhook_secret` when multiple organizations are configured, since a per-org bypass is far more dangerous than a global one). Additionally, `WebhooksController#verify_signature` should not use organization data taken from the unverified body to select the verification secret without re-checking that the same organization name matches the payload after signature verification succeeds.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgOne` (with `webhook_secret` set) and `OrgTwo` (with `webhook_secret` left blank, as in `test/dummy/config/secrets_double_github_app.yml`), and set `oauth.teams` such that a team belonging to `OrgTwo` grants access.
2. As an unauthenticated attacker, POST to `/webhooks`:
```
X-Github-Event: membership
X-Hub-Signature: sha1=anything
Body: {
  "action": "added",
  "team": {"id": 999, "name": "Access", "slug": "access", "url": "https://api.github.com/teams/999"},
  "organization": {"login": "OrgTwo"},
  "member": {"login": "attacker-github-login"},
  "repository": {"owner": {"login": "OrgTwo"}}
}
```
3. `verify_webhook_signature` returns `true` because `OrgTwo`'s `webhook_secret` is blank, regardless of the bogus signature header.
4. `MembershipHandler#process` creates/updates `Team` `access` and adds `attacker-github-login` as a member.
5. The attacker completes GitHub OAuth as `attacker-github-login`; `User#authorized?` now returns `true`, granting access to the protected Shipit application.

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)

    end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
