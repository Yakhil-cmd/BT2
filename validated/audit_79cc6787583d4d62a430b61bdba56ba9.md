### Title
Missing cosigner authorization check allows any paired device to trigger local signing requests via `"sign"` message - (File: wallet.js)

### Summary
The `"sign"` subject handler in `handleMessageFromHub` resolves the target `body.address`/`body.signing_path` via `findAddress()`, and when the address resolves to a wallet controlled by the local device (`ifLocal`), it should verify that the message's sender (`from_address`) is actually a legitimate cosigner of that specific multisig wallet before honoring the signing request. That verification query is present in the code but has been commented out, with the note "the commented check would make multilateral signing impossible." [1](#0-0) 

### Finding Description
`findAddress()` resolves `body.address`/`body.signing_path` by joining `my_addresses`, `wallets`, and `wallet_signing_paths` on the wallet, and returns `ifLocal` if the resolved `device_address` for that signing path equals the local device's own address. [2](#0-1) 
Crucially, this lookup is not scoped to `from_address` (the sender of the network message) — it only checks that the *signing_path/wallet* combination is locally owned, not that the specific *sender* is one of that wallet's registered cosigner devices. The commented-out check that would have validated `SELECT 1 FROM extended_pubkeys WHERE wallet=? AND device_address=?` against `from_address` — analogous to the NocoDB advisory's fix of re-scoping the permission check to the correct owning entity via `fk_workspace_id` — was intentionally disabled and never replaced with an equivalent per-sender check. [3](#0-2) 
As a result, any correspondent device that has previously paired with the victim (which, per the in-scope model, is an unprivileged paired device / AA-adjacent counterparty) can send a `"sign"` message referencing *any* of the victim's local multisig addresses and signing paths that it can guess or has observed (e.g. shared/multisig addresses whose device_address happens to match the local device for some signing path), and the victim node will accept it as if it came from an authorized cosigner — proceeding to fire the `"signing_request"` event and, in the `signed_message` branch, to validate and hash the attacker-supplied unit before the event is emitted to the UI layer. [4](#0-3) 

### Impact Explanation
This is a scope/ownership check analogous to the NocoDB bug class: the code fetches/validates a resource (the wallet address) without properly re-validating that the *requesting principal* (from_address) is entitled to act on it, only checking a broader, unrelated condition (that the wallet resolves locally at all). This allows an unrelated correspondent to inject spoofed signing requests for wallets/addresses they are not a cosigner of, forcing the victim's client to process attacker-controlled unsigned unit content (parse authors, compute hashes, validate, and surface a signing/confirmation dialog) tied to addresses the sender has no legitimate claim to sign for.

### Likelihood Explanation
Reaching this path requires only being an established correspondent device of the victim (any paired device, not necessarily a genuine cosigner) and knowing/guessing a valid `address` + `signing_path` combination that resolves locally for the victim — information that could be learned from previous shared-address setup traffic or contract flows. No additional privilege beyond "paired device" is required to send the `"sign"` message itself.

### Recommendation
Restore (and correctly implement) the sender/cosigner authorization check before entering the `ifLocal` branch of the `"sign"` handler: verify that `from_address` is actually present as a registered signer (e.g., via `extended_pubkeys`/`wallet_signing_paths` for BIP44 wallets, or `shared_address_signing_paths` for shared addresses) for the specific `wallet`/`signing_path`/`address` being requested, rather than only checking whether the signing path resolves to the local device in general.

### Proof of Concept
Concrete exploitation would require a background Devin agent to: (1) pair two ocore instances as normal correspondent devices, (2) have Instance A learn (or brute force via contract-sharing flows) a multisig `address`/`signing_path` combination belonging to Instance B that resolves locally on B, (3) have Instance A send a `"sign"` device message to B with that `address`/`signing_path` and an attacker-crafted `unsigned_unit`, and (4) observe that B's `findAddress` resolves to `ifLocal` and proceeds to `callbacks.ifOk()` and emits `"signing_request"` without ever validating that A is a legitimate cosigner — confirming the missing authorization check identified above. [5](#0-4)
