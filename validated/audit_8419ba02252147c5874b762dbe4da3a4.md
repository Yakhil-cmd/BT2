### Title
`StatusHandler#process` writes CI status by bare SHA with no repository check, letting one repo's status flip a different stack's required `release/gate` context - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)` and never compares the incoming payload's repository to the commit's stack repository, so any repo capable of emitting a signed `status` webhook can write a `Status` (e.g. `context: release/gate`, `state: failure`) onto a `Commit` belonging to an unrelated stack that happens to share the same SHA. Because `Status#after_create` calls `schedule_continuous_delivery`, this can trigger `ContinuousDeliveryJob` on the victim stack, turning a cross-tenant write into an unauthorized ship/block decision.

### Finding Description
The invariant that should hold is: `params.repository.full_name == commit.stack.repository.full_name` for every `Status` created from a webhook. Instead, the handler only checks SHA equality: [1](#0-0) 

The `params` schema for this handler doesn't even declare a `repository` field [2](#0-1) , unlike other handlers such as `PullRequest::OpenedHandler`, which explicitly resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)` before touching any stack state [3](#0-2) .

This is exploitable because the `commits` table's uniqueness constraint is on `[sha, stack_id]`, not on `sha` alone [4](#0-3) , meaning the same SHA can legitimately exist as separate `Commit` rows across multiple stacks/repositories (forks, mirrors, or repos with shared/cherry-picked history). `WebhooksController#verify_signature` only proves the request was really signed by the sending organization's webhook secret [5](#0-4) ; it authenticates *who sent the request*, not *which repository's commits may be mutated*. Once past that check, `Commit.where(sha:)` fans the write out to every stack sharing that SHA.

When the created `Status` lands on the victim commit, `after_create :enable_ci_on_stack` and `after_commit :schedule_continuous_delivery` fire unconditionally [6](#0-5) , calling `commit.schedule_continuous_delivery`, which (per existing tests) drives `ContinuousDeliveryJob` deploy/skip decisions when `continuous_deployment` is enabled on the stack [7](#0-6) . A `release/gate` context flipping to `failure` (or a required context flipping to `success`) changes `commit.state`/`deployable?` for the victim stack even though the webhook never authenticated against that stack's repository.

### Impact Explanation
A payload authenticated for repository A can create/alter a `Status` on a `Commit` belonging to stack B's repository, as long as both repositories share a commit SHA. This directly matches the specified Critical impact category: "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge." If the victim stack has `continuous_deployment` enabled and gates on `release/gate` (or any CI context), the attacker can force the commit's aggregate `state` to flip, potentially unblocking (ship) or blocking a deploy on a stack they have no relationship to. This is repeatable against any stack whose commits share a SHA with a repo the attacker controls or can trigger status events from.

### Likelihood Explanation
The attacker needs: (1) a repository/organization capable of legitimately emitting a signed `status` webhook to the Shipit instance (satisfied by "emit webhooks from a repository they own" per the threat model), and (2) a SHA collision with a commit tracked by the victim stack — realistic via forks, mirrored history, or cherry-picked/backported commits sharing identical content (and thus identical SHA-1). No Shipit secrets, sessions, or API tokens are required; `verify_signature` is satisfied by the attacker's own (legitimately signed) organization traffic, and `StatusHandler` performs no additional repository check afterward.

### Recommendation
Scope `StatusHandler#process` to only affect commits belonging to the repository that authenticated the webhook: require `repository.full_name` in the handler's params schema, resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)`, and constrain the commit lookup to `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { id: repository.id })` (or equivalent), mirroring the pattern already used in `PullRequest::OpenedHandler`/`EditedHandler`.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb
test "status webhook only affects commits of the authenticating repository" do
  attacker_stack = shipit_stacks(:soc)          # different repo than victim
  victim_stack   = shipit_stacks(:shipit)
  victim_stack.update!(continuous_deployment: true)

  shared_sha = "deadbeef" * 5
  victim_commit   = victim_stack.commits.create!(sha: shared_sha, message: "x",
                     author: shipit_users(:walrus), committer: shipit_users(:walrus),
                     authored_at: Time.now, committed_at: Time.now)
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, message: "x",
                     author: shipit_users(:walrus), committer: shipit_users(:walrus),
                     authored_at: Time.now, committed_at: Time.now)

  before_state = victim_commit.reload.state

  Shipit::Webhooks::Handlers::StatusHandler.new.call(
    'sha' => shared_sha, 'state' => 'failure', 'context' => 'release/gate',
    'repository' => { 'full_name' => attacker_stack.repository.github_repo_name }
  )

  after_state = victim_commit.reload.state

  # Broken binding under test:
  # params.repository.full_name ("attacker/repo") should NOT equal
  # victim_commit.stack.repository.full_name ("shopify/shipit-engine")
  # yet victim_commit.state changed as a result of the attacker's payload.
  refute_equal before_state, after_state,
    "victim stack's commit state changed from an unrelated repository's webhook"
end
```
