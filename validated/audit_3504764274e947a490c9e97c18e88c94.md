### Title
Webhook signature is verified against the payload's claimed organization, but handlers act on an unrelated `repository.full_name` field, allowing a foreign org to write into another tracked repository's stack - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to use for HMAC verification based on `repository.owner.login` (or `organization.login`), but every event `Handler` (e.g. `PushHandler`) locates the `Repository`/`Stack` to mutate using the independent, unchecked `repository.full_name` field from the same JSON body. Nothing ties these two fields together, so a party that legitimately controls one GitHub organization tracked by this Shipit instance can forge a signed webhook whose "authenticating org" is their own, while the "repository being written to" is any other org/repo Shipit tracks.

### Finding Description
`verify_signature` picks the app/secret purely off `repository_owner`: [1](#0-0) [2](#0-1) 

The actual HMAC check just compares the signature to `HMAC(webhook_secret_for(repository_owner), raw_body)`: [3](#0-2) 

Each configured organization has its own independent `webhook_secret`: [4](#0-3) 

Once the signature check passes, every `Handler` subclass resolves the target `Repository`/`Stack` from a *different* payload field, `repository.full_name`, with no cross-check against `repository_owner`: [5](#0-4) 

`PushHandler` then mutates real stack state (`sync_github`) for whatever stacks match that unchecked `full_name`: [6](#0-5) 

The equality that should hold but doesn't: `organization authenticated (repository_owner used for signature verification) == organization owning the repository actually written (repository.full_name used by Handler#stacks)`. An attacker who administers *any* org that this multi-tenant Shipit instance tracks (and therefore knows/can trigger a validly-signed delivery for their own org's `webhook_secret`) can set `repository.owner.login`/`organization.login` to their own org while setting `repository.full_name` to `victim-org/victim-repo`. The signature check passes (it's verified against the attacker's own org's secret), and the handler happily looks up and mutates the victim's `Stack` (queues `GithubSyncJob`, and analogously for `status`/`check_suite` handlers, records commit statuses/check runs) even though the attacker has no relationship to `victim-org`.

### Impact Explanation
This is a cross-repository write: an unprivileged party (relative to the victim org) can inject webhook-driven state changes (synced commits, CI/commit statuses, check-run refreshes) into a `Stack` belonging to an entirely different, unrelated GitHub organization that they do not administer. Because CI status/check-run injection feeds Shipit's continuous-deployment gating, this can be leveraged to make an already-pushed but not-yet-green commit appear CI-passing, causing an unauthorized deploy to proceed on the victim stack. This satisfies the "cross-repository writes" / "unauthorized deploy" bar for Critical/High impact.

### Likelihood Explanation
High, assuming the deployment tracks more than one GitHub organization (the documented, supported multi-org configuration shown in `config/secrets.development.shopify.yml`) — a standard setup for shared Shipit installations. Any organization admin/owner in that shared instance can trigger this without any additional privilege, since the only "credential" it depends on is a webhook secret they are legitimately entitled to (their own org's), not the victim's.

### Recommendation
In `Handler#repository_name` (and everywhere handlers resolve the acted-upon repository), require that the resolved repository's owner match the `repository_owner`/`organization.login` value that was used to select the verifying `webhook_secret` in `WebhooksController#verify_signature`. Reject (422) events where these two identities diverge, rather than trusting `repository.full_name` unconditionally once any org's signature validates.

### Proof of Concept
1. Shipit is configured with two orgs, `attacker-org` and `victim-org`, each with its own `webhook_secret` (per `config/secrets.development.shopify.yml` pattern). Attacker administers `attacker-org` and has a GitHub App/webhook installed there, so they can compute a valid `sha1=` HMAC using `attacker-org`'s `webhook_secret`.
2. Attacker crafts a `push` event body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha already existing on victim repo>",
  "repository": { "full_name": "victim-org/victim-repo", "owner": { "login": "attacker-org" } }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org_webhook_secret, body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and the signature validates successfully (per `app/controllers/shipit/webhooks_controller.rb:24-30`).
5. `PushHandler#stacks` resolves via `Repository.from_github_repo_name("victim-org/victim-repo")` (per `app/models/shipit/webhooks/handlers/handler.rb:32-38`) and calls `stack.sync_github(expected_head_sha: ...)` on the real victim stack (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`), even though the request was authenticated solely against `attacker-org`'s secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
