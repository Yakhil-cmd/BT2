### Title
System governance votes for network parameters can never be applied if no one pays the `SYSTEM_VOTE_COUNT_FEE` - ([File: main_chain.js])

### Summary
Casting a `system_vote` for a system parameter (`op_list`, `threshold_size`, `base_tps_fee`, `tps_interval`, `tps_fee_multiplier`) is free and permissionless, but the vote is never actually tallied and applied to `storage.systemVars` unless a *separate*, explicitly funded `system_vote_count` message is posted on the same MCI. That message requires paying a fixed `constants.SYSTEM_VOTE_COUNT_FEE` of `1e9` bytes [1](#0-0) . This is structurally identical to the UMA `Governor` bug: an action can be "approved" (votes cast, quorum reachable) but its actual on-chain effect requires a distinct, separately funded execution step, and if no economic actor volunteers to pay that fee, the approved governance change is stuck forever.

### Finding Description
Votes are recorded for free via the `system_vote` app [2](#0-1) , and persisted in `system_votes`/`op_votes`/`numerical_votes` by `saveSystemVote` when the unit stabilizes [3](#0-2) .

However, the actual counting/application of votes into `storage.systemVars` (`countVotes`) is only invoked for subjects that appear in `voteCountSubjects`, and that array is populated *exclusively* from `system_vote_count` messages, not from `system_vote` messages themselves: [4](#0-3) [5](#0-4) 

Posting a `system_vote_count` message requires paying `constants.SYSTEM_VOTE_COUNT_FEE` (1e9 bytes) as part of the base-asset balance check, enforced in `validatePaymentInputsAndOutputs`: [6](#0-5) 

and the composer explicitly adds this fee to the target amount only when a `system_vote_count` message is present: [7](#0-6) 

For `op_list`, there is a fallback: an "emergency" path (`applyEmergencyOpListChange`) can force a count if the network has been stuck long enough [8](#0-7) [9](#0-8) . But **no such fallback exists for the numeric subjects** (`threshold_size`, `base_tps_fee`, `tps_interval`, `tps_fee_multiplier`) — the `default` branch of `countVotes` throws for any subject it doesn't recognize, and `applyEmergencyOpListChange` handles `op_list` only.

This mirrors the UMA `Governor` bug class exactly: the "proposal" step (casting a vote) is decoupled from the "execution" step (counting/applying the vote), and the execution step has a funding requirement that is not guaranteed to ever be met — even after a supermajority of stake has voted for a change, if nobody is willing to spend 1e9 bytes (a nontrivial, fixed, non-refundable fee) to trigger `system_vote_count`, the change never takes effect.

### Impact Explanation
If enough stakeholders vote to change a system parameter (e.g., `threshold_size`, `base_tps_fee`, `tps_interval`, `tps_fee_multiplier`) but no single actor is willing to unilaterally pay the 1e9-byte fee to submit `system_vote_count` (there is no reward or reimbursement for doing so, and the fee is fully burned/spent as a normal fee), the approved parameter change can be stalled indefinitely. This can leave the network running with outdated fee/TPS parameters that the community has already voted to change, i.e., "network unable to apply an agreed-upon system-wide governance change," which affects fee economics and TPS throughput calibration network-wide. Because there is no emergency fallback for non-`op_list` subjects (only `op_list` has `applyEmergencyOpListChange`), this is a permanent governance stall for those parameters, not merely a delay.

### Likelihood Explanation
Any unprivileged unit poster with sufficient balance can cast `system_vote` for free, so votes can accumulate easily. Triggering the count, however, requires a single actor to spend 1e9 bytes with no direct individual benefit (a classic public-goods/free-rider problem), making it plausible in practice that nobody submits `system_vote_count` even after a vote clearly has a winning majority — especially for the less prominent numeric subjects, which (unlike `op_list`) lack any emergency/automatic fallback.

### Recommendation
- Add an automatic or lower-cost path to trigger vote counting for numeric subjects analogous to `applyEmergencyOpListChange`, e.g., automatically count votes once a mci threshold or age condition is met (instead of solely relying on a manually paid `system_vote_count`).
- Alternatively, reduce or refund the `SYSTEM_VOTE_COUNT_FEE` to the counting party from the accumulated stake of interested voters, so there is a rational incentive for someone to submit the count.
- At minimum, document and monitor for this liveness risk, and consider triggering `countVotes` automatically whenever a new `system_vote` for a subject is stabilized and the voting share/timeframe conditions in `countVotes` are already satisfied, removing the separate paid `system_vote_count` step as a strict prerequisite.

### Proof of Concept
1. A supermajority of GBYTE holders (by stake, per `SYSTEM_VOTE_MIN_SHARE`) each post free `system_vote` messages for `subject: "tps_fee_multiplier"` with the same new `value`, as validated in [10](#0-9) .
2. These votes stabilize and are persisted via `saveSystemVote` [3](#0-2) , but `voteCountSubjects` remains empty because no `system_vote_count` message was posted [4](#0-3) .
3. `countVotes` is never called for `tps_fee_multiplier`, so `storage.systemVars.tps_fee_multiplier` never updates [5](#0-4) .
4. Because posting `system_vote_count` costs 1e9 bytes with no compensating incentive [1](#0-0) , [7](#0-6) , and because no emergency fallback exists for this subject (unlike `op_list`), the approved network-wide vote can remain permanently unenacted.
