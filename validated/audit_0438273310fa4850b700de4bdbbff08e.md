### Title
Blacklisted or auth-failing accumulator permanently reverts `claim_revenue`, freezing unclaimed protocol yield - (File: contracts/controller/src/markets.rs)

### Summary
The Wagmi M-4 bug class is "an unprivileged flow dies because it pushes tokens to a recipient the caller does not control." In XOXNO Lending, `repay` has no third-party leg (the pool refunds overpayment only to the `payer`, `pool/src/ops/repay.rs:32`), so the class does not map onto repayment. It does map onto `claim_revenue`: any caller may invoke it, but every asset leg ends in an unconditional `transfer_amount_measured` to the single admin-configured `accumulator` address (`contracts/controller/src/markets.rs:174-196`). If that transfer reverts — e.g. the accumulator is blacklisted, deauthorized, or the Stellar asset requires authorization the accumulator lacks — the entire `claim_revenue` call reverts and the market's revenue can never be claimed.

### Finding Description
`claim_revenue(env, caller, assets)` is reachable by any authorized caller (`require_authorized_caller` only requires the caller to sign; it is listed as an open/`None`-role endpoint in `docs/reference/endpoints.md:38`). For each `HubAssetKey`:

1. `pool_claim_revenue_call` moves the claimable revenue from the pool to the controller (`markets.rs:184`).
2. The controller measures its balance delta (`markets.rs:182-186`).
3. If `received > 0`, it calls `payments::transfer_amount_measured(env, asset, &controller, &accumulator, received, ...)` (`markets.rs:189-196`).

`transfer_amount_measured` invokes `token.transfer` and panics on failure — there is no `try_transfer`/escrow fallback. Because steps 1–3 are one atomic transaction, a reverting forward-leg also unwinds the pool-side claim (`pool/src/ops/revenue.rs:25-31` burns revenue shares and transfers out before the forward leg runs). Revenue shares are never burned successfully, so the yield stays claimable-but-unclaimable forever while the accumulator cannot receive the token.

### Impact Explanation
Temporary/permanent freezing of unclaimed yield. All protocol revenue for the affected asset is locked: the pool-side claim always precedes the forward, so the revert is total and no caller can extract revenue to any other destination. Unlike Wagmi, funds are not lost — revenue shares remain intact — but they are unreachable until governance changes the accumulator via `set_accumulator`, and for a token that blacklists every plausible accumulator the yield is frozen indefinitely.

### Likelihood Explanation
Requires an external condition (accumulator blacklisted/deauthorized on a listed token), not attacker action — but it is unprivileged to trigger and can arise organically: the accumulator is a fixed admin-set address shared across all markets and hubs (`storage::try_get_accumulator`), so one incompatible or subsequently-flagged token bricks `claim_revenue` for that market for everyone. Medium severity: freezing of unclaimed yield with a governance-only recovery path.

### Recommendation
Mirror the Wagmi fix: wrap the forward leg in `try_transfer` (Soroban `token::Client::try_transfer`), and on failure retain the funds at the controller (or forward to a governance-recoverable escrow) while still emitting the claim event. Alternatively, allow `claim_revenue` to leave the measured receipt in controller custody for a later sweep when the accumulator transfer fails, so a single bad recipient cannot DoS the claim.

### Proof of Concept
1. Deploy controller + pool; governance calls `set_accumulator(A)`; a market lists USDC-like token T.
2. `supply` and `borrow` create activity; `update_indexes` accrues positive revenue (`pool/src/ops/revenue.rs` burns claimable shares on claim).
3. Token T's issuer revokes authorization / blacklists address A (or A is a contract that rejects the transfer).
4. Any unprivileged caller invokes `claim_revenue(caller, [(hub, T)])`. The pool pays out to the controller, then `transfer_amount_measured(..., &accumulator, ...)` at `markets.rs:189-196` panics; the whole transaction reverts, including the pool-side burn.
5. Repeat — every `claim_revenue` call for that asset reverts identically. Revenue accrues but can never leave the pool until governance re-points the accumulator.

Key code: `contracts/controller/src/markets.rs:129-138` (entrypoint), `markets.rs:174-196` (unconditional forward), `contracts/pool/src/ops/revenue.rs:22-35` (payout leg that gets atomically reverted).
