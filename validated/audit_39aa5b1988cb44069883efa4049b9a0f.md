### Title
Signature verification uses `repository.owner.login` while the pull-request handler mutates the stack for `repository.full_name`, allowing a secret-less organization's webhook to archive another organization's review stack - (File: app/models/shipit/webhooks/handlers/pull_request/closed_handler.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects the `GitHubApp` (and therefore the HMAC secret used to verify the payload) using `params.dig('repository', 'owner', 'login')`, but `PullRequest::ClosedHandler` resolves and mutates the target `Repository`/review stack using the independent field `params.repository.full_name`. Because these are two separately attacker-controlled fields in the same raw JSON body, and because `GitHubApp#verify_webhook_signature` returns `true` unconditionally when the resolved organization has no `webhook_secret` configured, an attacker who owns/controls an organization with no configured secret can forge a `pull_request` `closed` event whose `repository.full_name` names a victim organization's repository, causing `review_stack.archive!` to run against the victim's stack.

### Finding Description
The broken binding, stated explicitly: the equality the code implicitly relies on is
`organization_that_verified_signature == organization_owning_full_name_repository`
i.e. `params.dig('repository','owner','login') == params.repository.full_name.split('/').first`.

This equality is **not enforced anywhere** in the code:

- `Shipit::WebhooksController#verify_signature` computes `repository_owner` purely from `params.dig('repository', 'owner', 'login')` (or `params.dig('organization', 'login')`) and uses it to fetch `github_app = Shipit.github(organization: repository_owner)`, then calls `github_app.verify_webhook_signature(...)`. [1](#0-0) [2](#0-1) 

- `GitHubApp#verify_webhook_signature` short-circuits to `true` when the resolved organization's config has no `webhook_secret`: [3](#0-2) 

- `PullRequest::ClosedHandler#process` never re-checks `repository.owner.login`. It resolves the target repository solely from `params.repository.full_name` and immediately archives whatever review stack matches: [4](#0-3) 

**Exploit flow**: The attacker registers/controls a GitHub organization `attacker-org` that a Shipit operator has configured in `secrets.github` (as any onboarded org can be, e.g. via self-service setup or a legitimately owned org with no secret set — the audit assumes this org exists with no `webhook_secret`, which is the state the question stipulates: "verified against a secret-less organization"). The attacker POSTs to `/webhooks` with header `X-Github-Event: pull_request` and a JSON body where:
- `repository.owner.login` = `"attacker-org"` (so `Shipit.github(organization: "attacker-org")` resolves a config with no secret, and `verify_webhook_signature` returns `true` regardless of the actual `X-Hub-Signature` header value or absence thereof),
- `repository.full_name` = `"victim-org/victim-repo"` (the real target),
- `action` = `"closed"`, plus the other required `pull_request` fields matching an existing open review stack's PR number.

Since `verify_signature` passes (bypassed by the missing secret), the request reaches `WebhooksController#create`, which dispatches to `ClosedHandler`. The handler looks up `Shipit::Repository.from_github_repo_name("victim-org/victim-repo")`, finds the real victim `Repository`, resolves the matching `review_stack` for that PR number, and calls `review_stack.archive!` — mutating a resource never authenticated by the attacker's request.

**Why existing guards fail**: `drop_unhandled_event` and `ExplicitParameters` schema only check event type/shape, not repository/organization consistency. `verify_signature` authenticates *a* signature against *an* organization's secret, but that organization is chosen from a different payload field (`repository.owner.login`) than the one the business logic actually acts on (`repository.full_name`). No code path cross-checks that these two fields agree, and no model validation on `Repository`/`ReviewStack` prevents cross-organization archival since the archival logic trusts the payload's `full_name` unconditionally.

### Impact Explanation
A successful request causes `review_stack.archive!` to execute against a repository/stack belonging to an organization the attacker never authenticated against — this is "a payload for one repository mutating another's stack," matching the **Critical** impact category defined in the rules. Archiving a review stack disrupts or masks in-flight deploys for the victim tenant. The attack is repeatable against any repository/organization combination as long as the attacker can get any organization onboarded with a config lacking `webhook_secret`, and does not require any Shipit session, API token, or GitHub secret belonging to the victim.

### Likelihood Explanation
Preconditions: (1) Shipit is configured in multi-organization mode (`github_default_organization` non-nil, i.e., `secrets.github` keyed by org) since the single-app schema (`config = secrets.github` with no `organization` param) applies its one global secret universally rather than per-org lookup; (2) at least one onboarded organization has no `webhook_secret` set in its per-org config block — this is exactly the scenario the question stipulates. Given that precondition, the attacker's cost is minimal: a single unauthenticated HTTP POST with a crafted JSON body, no GitHub App keys, no Shipit credentials, and no interaction with the victim organization at all. The attack is fully repeatable and requires no timing windows or race conditions.

### Recommendation
Enforce that the organization used to verify the webhook signature matches the organization actually being mutated. Concretely: after fetching the target repository/stack in each handler (or centrally in the controller/`Handler` base class), assert that `Shipit::Repository.from_github_repo_name(params.repository.full_name)`'s owner equals `repository_owner` used in `verify_signature`, and reject the request (422) otherwise. Additionally, `GitHubApp#verify_webhook_signature` should not silently return `true` when `webhook_secret` is blank in a multi-org configuration — a missing secret for a configured organization should either be treated as a configuration error (fail closed) or that organization should not be permitted to authenticate webhooks for repositories outside its own namespace.

### Proof of Concept
Minitest plan (to be placed under `test/controllers/webhooks_controller_test.rb`, following existing conventions in that file):

```ruby
test "pull_request closed event from a secret-less organization cannot archive another organization's review stack" do
  # Arrange: victim stack/review stack belongs to "shopify" org (has webhook_secret configured)
  victim_stack = shipit_stacks(:shipit) # or a review-stack fixture with known PR number
  victim_repo_full_name = "shopify/#{victim_stack.repository.name}" # adjust to actual victim fixture
  refute victim_stack.archived?, "precondition: victim stack must start unarchived"

  # Ensure "attacker-org" is configured with NO webhook_secret (simulate via stub or fixture secrets)
  Shipit.stubs(:github).with(organization: "attacker-org").returns(
    Shipit::GitHubApp.new("attacker-org", { app_id: 1, installation_id: 1, private_key: nil }) # no :webhook_secret key
  )

  body = {
    action: "closed",
    number: victim_stack_pr_number, # matching PR number on the victim review stack
    pull_request: {
      id: 1, number: victim_stack_pr_number, url: "https://api.github.com/x",
      title: "x", state: "closed", additions: 1, deletions: 1,
      head: { sha: "abc", ref: "branch" },
      user: { login: "attacker" },
      assignees: [], labels: []
    },
    repository: {
      full_name: victim_repo_full_name,   # names the VICTIM repository
      owner: { login: "attacker-org" }    # used ONLY for signature org lookup
    },
    sender: { login: "attacker" }
  }.to_json

  @request.headers['X-Github-Event'] = 'pull_request'
  # No valid X-Hub-Signature needed because attacker-org has no webhook_secret,
  # so verify_webhook_signature short-circuits to true.

  post :create, body: body, as: :json

  assert_response :ok
  # Assert the binding violation: verification happened against "attacker-org",
  # yet the victim stack (owned by "shopify") was mutated.
  assert victim_stack.reload.archived?, "victim review stack was archived by a request never authenticated by its owning organization"
end
```

This demonstrates the binding violation directly: `organization_verified ("attacker-org") != organization_owning_stack ("shopify")`, yet `review_stack.archive!` executes on the victim's stack.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
