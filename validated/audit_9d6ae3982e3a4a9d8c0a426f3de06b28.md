### Title
Permanent loss of bridged funds when Sui→Ethereum unlock reverts, with no refund path in `bridge::send_token` - (File: crates/sui-framework/packages/bridge/sources/bridge.move)

### Summary
The Sui native bridge burns the user's coin on Sui immediately and unconditionally in `send_token`/`send_token_internal`, before the corresponding unlock transaction is ever executed on the Ethereum side. If the Ethereum-side unlock (`SuiBridge.transferBridgedTokensWithSignatures` → `BridgeVault.transferETH`) reverts for a legitimate, attacker-uncontrolled recipient (e.g., a smart-contract recipient address that has no payable `receive`/`fallback`), the burn on Sui can never be undone and there is no code path in `bridge.move` to reclaim or refund the burned asset. This is the same root cause as the Scroll "Lack of Refunds" report: a two-phase bridging operation where the first phase (burn/lock) is irreversible while the second phase (unlock/mint) can fail, with no compensating refund mechanism.

### Finding Description
On the Sui→Ethereum path, `send_token`/`send_token_internal` in `crates/sui-framework/packages/bridge/sources/bridge.move` unconditionally burns the user's coin via `inner.treasury.burn(token)` and stores a `BridgeRecord` before any Ethereum-side confirmation exists: [1](#0-0) 

The record only ever gets signatures attached via `approve_token_transfer` (idempotent, retryable), and the actual unlock happens off-chain when the bridge client submits `SuiBridge.transferBridgedTokensWithSignatures` on Ethereum: [2](#0-1) 

That call ultimately dispatches to `BridgeVault.transferETH`, which performs a raw low-level call to the recipient and reverts the entire transaction if the call fails:
```
function transferETH(address payable recipientAddress, uint256 amount) ... {
    wETH.withdraw(amount);
    (bool success,) = recipientAddress.call{value: amount}("");
    require(success, "ETH transfer failed");
}
``` [3](#0-2) 

If `recipientAddress` (the low 20 bytes of the user-supplied 32-byte Sui target address) resolves to a contract with no payable fallback, or one that intentionally/unintentionally reverts on ETH receipt, `transferBridgedTokensWithSignatures` will revert every time it is retried. There is no bookkeeping in `bridge.move` that lets the original sender reclaim the already-burned coin, nor any Move-side "unlock failed, refund sender" entrypoint — `BridgeRecord.claimed` only tracks the mint/claim side of Ethereum→Sui transfers, not a refund state for Sui→Ethereum burns.

This is structurally identical to the Scroll bug: value is destroyed/escrowed on the source chain before the destination-chain execution is guaranteed to succeed, and a reverting destination-chain callback (here, ETH transfer to a non-accepting recipient) leaves the user with no recovery path.

### Impact Explanation
This causes permanent, non-recoverable loss of user funds bridged from Sui to Ethereum whenever the destination address cannot accept a raw ETH transfer. Under the HackenProof Sui impact gate, this falls squarely under the High/Medium category of "permanent fund lock," triggered purely by an ordinary user's own bridging transaction (`send_token`) combined with any recipient address that reverts ETH receipt — no malicious bridge authority, validator, or governance action is required.

### Likelihood Explanation
Likelihood is realistic: any user (or a griefer targeting another user by providing/spoofing a contract recipient address, or simply a benign multisig/contract wallet without a `receive()` function) can cause this outcome. Since `send_token` performs the burn before any destination-chain execution or validation of recipient "acceptability" occurs, and Ethereum has no generic guarantee that an arbitrary address can accept a bare ETH transfer, this is a naturally occurring failure mode, not a contrived edge case.

### Recommendation
Introduce a refund path in the Move bridge module analogous to the requested Scroll fix: if the destination-chain unlock is provably unable to complete (e.g., recorded as permanently failed by the bridge committee/oracle, or after a timeout with committee attestation of failure), allow the original sender to reclaim the equivalent value from the treasury via a signed "refund" system message, mirroring the `execute_system_message` governance flow. Alternatively, change ETH delivery on the EVM side to a pull-based/WETH-wrapped delivery (transfer WETH instead of raw ETH, or use a `try/catch` push-then-fallback-to-escrow pattern) so recipient-side reverts do not block settlement and do not require unwinding an already-burned Sui asset.

### Proof of Concept
1. User calls `bridge::send_token<SUI_ETH_TYPE>` targeting Ethereum with `target_address` set to the address of a deployed contract that has no `receive`/`fallback` (or that always reverts on receiving ETH). The coin is burned immediately: [1](#0-0) 
2. The bridge client relays the message; `approve_token_transfer` attaches signatures successfully on Sui.
3. The bridge client (or anyone) calls `SuiBridge.transferBridgedTokensWithSignatures` on Ethereum, which routes to `BridgeVault.transferETH`; the raw call to the contract recipient reverts, so `require(success, "ETH transfer failed")` reverts the whole transaction: [4](#0-3) 
4. Every subsequent retry of `transferBridgedTokensWithSignatures` for this nonce reverts identically since the recipient's inability to accept ETH is a permanent property of that address.
5. The user's coin remains burned on Sui with `record.claimed` never being applicable (that flag only exists for the mint-side of Ethereum→Sui), and no Move function exists to refund the sender — funds are permanently lost.

fun send_token_internal<T>(
    inner: &mut BridgeInner,
    target_chain: u8,
    token: Coin<T>,
    message: BridgeMessage,
) {
    assert!(!inner.paused, EBridgeUnavailable);
    assert!(chain_ids::is_valid_route(inner.chain_id, target_chain), EInvalidBridgeRoute);

    // burn / escrow token, unsupported coins will fail in this step
    inner.treasury.burn(token);

    // Store pending bridge request
    inner
        .token_transfer_records
        .push_back(
            message.key(),
            BridgeRecord {
                message,
                verified_signatures: option::none(),
                claimed: false,
            },
        );
}

    function transferBridgedTokensWithSignatures(
        bytes[] memory signatures,
        BridgeUtils.Message memory message
    )
        external
        nonReentrant
        verifyMessageAndSignatures(message, signatures, BridgeUtils.TOKEN_TRANSFER)
        onlySupportedChain(message.chainID)
    {
        // verify that message has not been processed
        require(!isTransferProcessed[message.nonce], "SuiBridge: Message already processed");

        IBridgeConfig config = committee.config();

        BridgeUtils.TokenTransferPayload memory tokenTransferPayload =
            BridgeUtils.decodeTokenTransferPayload(message.payload);

        // verify target chain ID is this chain ID
        require(
            tokenTransferPayload.targetChain == config.chainID(), "SuiBridge: Invalid target chain"
        );

        // convert amount to ERC20 token decimals
        uint256 erc20AdjustedAmount = BridgeUtils.convertSuiToERC20Decimal(
            IERC20Metadata(config.tokenAddressOf(tokenTransferPayload.tokenID)).decimals(),
            config.tokenSuiDecimalOf(tokenTransferPayload.tokenID),
            tokenTransferPayload.amount
        );

        _transferTokensFromVault(
            message.chainID,
            tokenTransferPayload.tokenID,
            tokenTransferPayload.recipientAddress,
            erc20AdjustedAmount
        );
