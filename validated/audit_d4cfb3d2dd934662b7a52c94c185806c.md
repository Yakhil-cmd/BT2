### Title
Authorization bypass in `handleNewSharedAddress` lets any paired device register the local wallet under a shared (multisig) address it never agreed to join - ([File: wallet_defined_by_addresses.js])

### Summary
`wallet.js`'s `"new_shared_address"` message handler forwards an arbitrary correspondent's `new_shared_address` device message straight into `wallet_defined_by_addresses.js:handleNewSharedAddress()` with **no check that the sending device (`from_address`) is actually one of the legitimate members/co-signers of the proposed shared address**. This is the direct analog of CVE-2017-0919: a peer can make the victim's wallet "perform operations" (register a shared/multisig address, watch it, and later co-sign/fund it) under a group ("shared address") the peer was never authorized to add the victim to.

### Finding Description
The wallet protocol handler in `wallet.js` dispatches the message without any sender authorization check: [1](#0-0) 

`handleNewSharedAddress` only validates internal self-consistency of the attacker-supplied payload (definition hashes to the claimed address, every signer's address matches its path in the definition, every definition path has a signer) - it never verifies that the message actually originated from, or was consented to by, the other claimed co-signer(s): [2](#0-1) 

The only "authorization" check that exists is `determineIfIncludesMeAndRewriteDeviceAddress`, which merely checks that one of the addresses referenced in the definition happens to already be one of *my* known addresses (`my_addresses` or `shared_addresses`): [3](#0-2) 

This check does not verify that the sending device is entitled to bind the victim's address into this new definition, nor does it constrain the *other* branch(es) of the definition. Since `Definition.validateDefinition` (called via `validateAddressDefinition`) accepts arbitrary boolean combinations such as `or`, an attacker who merely knows one of the victim's real, already-used addresses (addresses are public on the DAG) can construct:
```
["or", [["address", victim_address], ["address", attacker_address]]]
```
and send it as a fabricated `new_shared_address` message. `extractAddressPathsFromDefinition`/`handleNewSharedAddress`'s consistency checks all pass, `determineIfIncludesMeAndRewriteDeviceAddress` succeeds because `victim_address` is one of the victim's own addresses, and `addNewSharedAddress` inserts the bogus address into `shared_addresses` / `shared_address_signing_paths`, causing the victim's wallet to start watching/treating this address as a jointly-controlled address: [4](#0-3) 

Because the condition is an `or`, the attacker alone can spend anything sent to that address at any time - there is no real "sharing" of control, only an illusion created in the victim's local wallet state. This mirrors GitLab's import bypass: an unauthorized party manipulates data (the shared-address membership record) to grant themselves standing "under a group" (the shared multisig address) that the victim believed was mutually controlled.

### Impact Explanation
If the victim's wallet UI/flow leads the user to fund this "shared address" (e.g., believing a counterparty will co-sign a joint transaction, or because the address is silently watched and used by automated flows such as `sendToPeerAllSharedAddressesHavingUnspentOutputs`/private-payment forwarding, which operate on any row in `shared_addresses`), funds sent to that address are unilaterally spendable by the attacker via the `or` branch alone. This is a concrete path to unauthorized loss of funds sent by the victim, satisfying the "unauthorized spending" bar for impact. Severity aligns with High given the low complexity (one crafted device message, only the victim's already-public address needed) and the direct fund-loss consequence.

### Likelihood Explanation
Likelihood is high for a paired-device attacker (which is an explicitly in-scope reach vector: "paired device can reach ... wallet and contract message handling"): pairing with a target device (or being an already-paired but dishonest correspondent) is the only prerequisite, and address values referenced in a definition are not secret - they are public addresses seen on the DAG. No additional signatures or proofs of co-signer consent are required by `handleNewSharedAddress`.

### Recommendation
- In `wallet.js`, when handling `"new_shared_address"`, require and verify that `from_address` corresponds to a device address actually present in `body.signers` and that it is legitimately mapped to the signing path(s) it claims, rather than trusting the message content unconditionally.
- In `handleNewSharedAddress`/`determineIfIncludesMeAndRewriteDeviceAddress`, reject definitions where "my" address is only reachable through a permissive `or`/`weighted and` branch that allows funds to be spent without any signature from a device the user actually controls, or require an explicit, out-of-band user confirmation (with full disclosure of the definition's boolean structure, not just presence) before persisting the address as "shared."
- Add an explicit UI confirmation step before `addNewSharedAddress` is called from network-originated (non-`bForwarded`) messages, showing the actual spending conditions (not just "shared with member X") so users can detect an `or` bypassing bypass structure.

### Proof of Concept
1. Attacker pairs with victim's device (`device.js:handlePairingMessage`) or is already a correspondent.
2. Attacker learns victim's address `V` (public on the DAG, e.g. via any past unit victim authored).
3. Attacker builds `arrDefinition = ["or", [["address", V], ["address", A]]]` where `A` is an address attacker fully controls, computes `body.address = objectHash.getChash160(arrDefinition)`, and `body.signers = {"r.0": {address: V}, "r.1": {address: A}}`.
4. Attacker sends device message `{"new_shared_address", body}` to victim.
5. `wallet.js` case `"new_shared_address"` calls `handleNewSharedAddress(body, ...)` unconditionally (`wallet.js:236-245`); all internal consistency checks in `handleNewSharedAddress` pass (`wallet_defined_by_addresses.js:377-415`); `determineIfIncludesMeAndRewriteDeviceAddress` succeeds because `V` is one of victim's own addresses.
6. `addNewSharedAddress` persists the bogus shared address, and the victim's wallet begins treating `body.address` as a jointly-owned address.
7. Any funds later sent by the victim (or forwarded to this address by wallet logic assuming shared custody) can be unilaterally withdrawn by the attacker using only their own key for the `A` branch of the `or` condition - no victim signature or consent is ever required.

function determineIfIncludesMeAndRewriteDeviceAddress(assocSignersByPath, handleResult){
	var assocMemberAddresses = {};
	var bHasMyDeviceAddress = false;
	for (var signing_path in assocSignersByPath){
		var signerInfo = assocSignersByPath[signing_path];
		if (signerInfo.device_address === device.getMyDeviceAddress())
			bHasMyDeviceAddress = true;
		if (signerInfo.address)
			assocMemberAddresses[signerInfo.address] = true;
	}
	var arrMemberAddresses = Object.keys(assocMemberAddresses);
	if (arrMemberAddresses.length === 0)
		return handleResult("no member addresses?");
	db.query(
		"SELECT address, 'my' AS type FROM my_addresses WHERE address IN(?) \n\
		UNION \n\
		SELECT shared_address AS address, 'shared' AS type FROM shared_addresses WHERE shared_address IN(?)", 
		[arrMemberAddresses, arrMemberAddresses],
		function(rows){
		//	handleResult(rows.length === arrMyMemberAddresses.length ? null : "Some of my member addresses not found");
			if (rows.length === 0)
				return handleResult("I am not a member of this shared address");
			var arrMyMemberAddresses = rows.filter(function(row){ return (row.type === 'my'); }).map(function(row){ return row.address; });
			// rewrite device address for my addresses
			if (!bHasMyDeviceAddress){
				for (var signing_path in assocSignersByPath){
					var signerInfo = assocSignersByPath[signing_path];
					if (signerInfo.address && arrMyMemberAddresses.indexOf(signerInfo.address) >= 0)
						signerInfo.device_address = device.getMyDeviceAddress();
				}
			}
			handleResult();
		}
	);
}

// {address: "BASE32", definition: [...], signers: {...}}
function handleNewSharedAddress(body, callbacks){
	if (!ValidationUtils.isArrayOfLength(body.definition, 2))
		return callbacks.ifError("invalid definition");
	if (typeof body.signers !== "object" || Object.keys(body.signers).length === 0)
		return callbacks.ifError("invalid signers");
	try {
		var addr = objectHash.getChash160(body.definition);
	}
	catch (e) {
		return callbacks.ifError("invalid definition: " + e);
	}
	if (body.address !== addr)
		return callbacks.ifError("definition doesn't match its c-hash");
	for (var signing_path in body.signers){
		var signerInfo = body.signers[signing_path];
		if (signerInfo.address && signerInfo.address !== 'secret' && !ValidationUtils.isValidAddress(signerInfo.address))
			return callbacks.ifError("invalid member address: " + JSON.stringify(signerInfo.address));
	}
	const assocDefinitionAddresses = extractAddressPathsFromDefinition(body.definition);
	for (let signing_path in body.signers) {
		const signerInfo = body.signers[signing_path];
		if (assocDefinitionAddresses[signing_path] !== signerInfo.address)
			return callbacks.ifError("signer address at path " + signing_path + " doesn't match definition");
	}
	for (let def_path in assocDefinitionAddresses) {
		if (!body.signers[def_path])
			return callbacks.ifError("no signer for definition address at path " + def_path);
	}
	determineIfIncludesMeAndRewriteDeviceAddress(body.signers, function(err){
		if (err)
			return callbacks.ifError(err);
		validateAddressDefinition(body.definition, function(err){
			if (err)
				return callbacks.ifError(err);
			addNewSharedAddress(body.address, body.definition, body.signers, body.forwarded, callbacks.ifOk);
		});
	});
}
