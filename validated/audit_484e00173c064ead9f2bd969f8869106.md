## Title
Unchecked `UPDATE ... WHERE is_spent=0` result allows double-spend of private indivisible-asset outputs - (File: `indivisible_asset.js`)

### Summary
The external report flags `transferFrom()` calls whose boolean return value is never checked, letting a caller believe a transfer succeeded even when it silently failed. The analogous pattern in `ocore` exists in `validateAndSavePrivatePaymentChain()` in `indivisible_asset.js`, where the SQL `UPDATE` that marks a private output as spent uses a guard clause (`AND is_spent=0`) but the number of affected rows is never checked before the code unconditionally reports success via `callbacks.ifOk()`.

### Finding Description
In `indivisible_asset.js`, when saving a validated private payment chain, the code marks the consumed output as spent with: [1](#0-0) 

The `AND is_spent=0` clause is the only safeguard against marking an output "spent" twice, but nothing checks whether this `UPDATE` actually matched/updated a row. The final callback treats the whole batch as successful regardless: [2](#0-1) 

Crucially, `validatePrivatePayment()` — the function that validates the private chain before this save step — never re-checks the current `is_spent` state of the source output in the `outputs` table. It only checks a `spend_proofs` uniqueness lookup and graph inclusion (`validateSourceOutput`), not whether the output has already been consumed: [3](#0-2) 

Because private (indivisible, hidden) payments are validated and saved per-chain, off the public DAG consensus mechanism, and the actual state mutation (`is_spent=1`) is applied via an unchecked, conditionally-no-op `UPDATE`, a second private chain built to spend the very same private output can pass through the exact same code path. Its own `INSERT ... INTO inputs` succeeds (it isn't blocked by a unique-index violation for private assets the way public payments are, since `is_unique` is deliberately set to `NULL` for unstable private inputs), and its companion `UPDATE outputs SET is_spent=1 ... AND is_spent=0` silently affects 0 rows without the caller ever knowing. `callbacks.ifOk()` fires in both cases, so both the original and the duplicate/private-counterparty chain are accepted as valid.

### Impact Explanation
This directly maps to the "double-spend of a stable output" / "private payment chains" category. A malicious private-payment counterparty (e.g., a party being paid a private indivisible-asset payment through `wallet.js`'s `handlePrivatePaymentChains` flow) can craft two divergent successor chains spending the same hidden private output to two different recipients/devices. Each recipient's node independently calls `validateAndSavePrivatePaymentChain`; since the "already spent" check on the `UPDATE` is silently ignored rather than surfaced as an error, both recipients can be led to believe they legitimately received the funds, resulting in unauthorized double-spend of a private indivisible asset and fund loss for whichever party later discovers the conflict (or a supply-effective duplication of value from the issuer/other counterparty's perspective).

### Likelihood Explanation
This is reachable by any unprivileged private-payment counterparty who is a party to (or forwards) a private indivisible-asset payment chain — no special node/hub/network privileges are required, only building an alternate chain spending the same hidden output and sending both chains via the normal private-payment device/message flow (`network.handleOnlinePrivatePayment`, `private_payment.validateAndSavePrivatePaymentChain`). The check that would prevent this (verifying `is_spent`/checking `UPDATE` affected rows) is entirely absent, so likelihood of triggering the bad state (given attacker intent) is high; the only complicating factor is that the two conflicting deliveries must reach the victim nodes, which is a normal part of the private-payment protocol design (chains are relayed peer to peer / through hub).

### Recommendation
After executing `UPDATE outputs SET ... WHERE unit=? AND message_index=? AND output_index=? AND is_spent=0`, check the returned `affectedRows` (as already surfaced by `sqlite_pool.js`'s `result.affectedRows`/`insertId` wrapping) and treat 0 affected rows as a validation failure (`callbacks.ifError("output already spent")`) instead of silently continuing to `callbacks.ifOk()`. Additionally, `validatePrivatePayment()`/`validateSourceOutput()` should positively confirm the source output's `is_spent` state (or equivalent authoritative spent-tracking) before accepting the chain, not rely solely on the best-effort `UPDATE ... is_spent=0` as an implicit double-spend guard.

### Proof of Concept
1. Issuer creates a private indivisible-asset output `O` for address `A`.
2. `A` builds two independent private payment chains, `Chain1` spending `O` to recipient `R1`, and `Chain2` spending the same `O` to recipient `R2`.
3. `A` sends `Chain1` to `R1` and `Chain2` to `R2` (e.g., via device messaging / hub relay, both are normal, unprivileged operations for `A`).
4. `R1`'s node processes `Chain1`: `validatePrivatePayment` passes (no `is_spent` check), `validateAndSavePrivatePaymentChain` runs the `INSERT`/`UPDATE` queries in `indivisible_asset.js:246-296`, `UPDATE outputs SET is_spent=1 ... WHERE ... is_spent=0` succeeds (1 row affected), `callbacks.ifOk()` fires — `R1` believes payment received.
5. `R2`'s node processes `Chain2` independently (different node/db state or same node but before `R1`'s update propagates depending on timing/connection pooling): the same validation passes, and even if the `UPDATE` for `R2`'s chain affects 0 rows because `O` is already marked spent, this is never checked — `callbacks.ifOk()` still fires — `R2` also believes payment received.
6. Both `R1` and `R2` now hold what they believe are validly received private payments derived from the same source output `O`, demonstrating a double-spend that the unchecked `UPDATE` result failed to prevent.
