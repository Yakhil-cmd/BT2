### Title
StatusHandler applies GitHub 'status' webhooks to any Commit sharing a sha, regardless of which org's webhook_secret signed the payload - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` queries `Commit.where(sha: params.sha)` globally and calls `commit.create_status_from_github!(params)` on every match, without ever consulting the `stacks`/`repository_name` scoping helper that other handlers use. Since `WebhooksController#verify_signature` selects the signing organization from the attacker-controlled `repository.owner.login` field in the payload body itself, any tenant holding a legitimate `webhook_secret` for their own org can forge a `status` event naming a sha that happens to also exist in another org's `Commit` table (e.g. via a forked/shared upstream history) and inject a forged `success` status onto that unrelated commit.

### Finding Description
The broken binding, stated as an equality that must hold but doesn't: `Status.stack_id == commit.stack.repository.owner` **AND** `payload.repository.owner == commit.stack.repository.owner` should be enforced before a status is attached, but the actual code only enforces `commit.sha == params.sha`.

Code path:
1. `WebhooksController#verify_signature` picks the verifying `GitHubApp` via `repository_owner = params.dig('repository', 'owner', 'login')` [1](#0-0) [2](#0-1) . This field is entirely attacker-supplied JSON, not cryptographically bound to anything except which secret the attacker chose to sign with.
2. Once signature verification passes (using org-a's own `webhook_secret`, which org-a legitimately possesses because they configured their own GitHub App/webhook secret in a multi-tenant Shipit deployment, per `docs/setup.md`'s "Using Multiple Github Applications" section), the controller dispatches to `StatusHandler.call(params)` [3](#0-2) .
3. `StatusHandler#process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [4](#0-3) . It never calls the base `Handler#stacks`/`repository_name` helper that other handlers use to scope by `payload.dig('repository','full_name')` [5](#0-4) . Confirmed: `stacks` is defined on the base `Handler` class but `StatusHandler` does not reference it anywhere.
4. `Commit#create_status_from_github!` unconditionally creates a `Status` row via `statuses.replicate_from_github!(stack_id, github_status)` [6](#0-5) , attaching it to `commit.stack_id` — i.e., whichever stack/org actually owns that `sha`, not the org that signed the request.
5. `Commit#deployable?` is `!locked? && (stack.ignore_ci? || (success? && !blocked?))` [7](#0-6) , and `success?` derives from `Commit#status`/`state`, driven by the forged `Status` row.
6. `Api::DeploysController#create` gates deploys with `param_error!(:require_ci, "Commit is not deployable") if params.require_ci && !commit.deployable?` [8](#0-7) , and then calls `stack.trigger_deploy`, which ultimately drives `Command#start`/`PTY.spawn` with `org-b`'s `GITHUB_TOKEN`.

Existing guards fail specifically because: `verify_signature` only proves "the body was signed by whichever org's secret the attacker chose to use," not "the body's claims about `sha`/`repository` belong to that org." No model validation, `ExplicitParameters` schema, or the `stacks` scoping helper is invoked in `StatusHandler`, so nothing re-checks that the resolved `Commit`'s owning repository/org matches `repository_owner` used for signature verification.

### Impact Explanation
An attacker who is a legitimate tenant of a shared/multi-org Shipit deployment (owns a `webhook_secret` for their own org's GitHub App) can inject arbitrary CI `Status` rows (`state: 'success'`) onto **any** `Commit` record in the database that shares a sha with one of their own commits — including commits belonging to a completely unrelated org/stack they have no legitimate relationship to. This can flip `Commit#deployable?` to true for `org-b`'s commit, allowing a deploy request (which still requires the deploying user's own privileges via `require_permission :deploy, :stack`) to bypass the `require_ci: true` CI gate and proceed to `Command#start`/`PTY.spawn` using `org-b`'s credentials. This is a cross-tenant integrity violation: "a payload for one repository mutating another's stack/commit," matching the Critical impact category. Repeatable per matching sha, across every stack/org sharing commit history (forks, shared upstream, vendored branches).

### Likelihood Explanation
Requires: (a) a multi-tenant Shipit deployment configured with per-org `webhook_secret`s as documented, (b) the attacker's own org and the victim org sharing at least one commit sha (realistic for forks or shared upstream repos, and an attacker can also craft branches/histories to increase collision likelihood, though finding an exact 40-hex sha collision with an unrelated org without a shared history is not generally feasible — the realistic scenario is forks/mirrors of the same upstream), (c) the victim stack must have `require_ci: true` enforced and no other independent CI/permission gate. Attacker cost is low (one signed HTTP POST to `/webhooks`); it is fully repeatable and requires no elevated Shipit role beyond controlling their own org's webhook configuration.

### Recommendation
In `StatusHandler#process`, scope the query to the signing org before applying status: filter candidate commits through `stacks` (i.e., resolve via `Repository.from_github_repo_name(payload.dig('repository','full_name'))&.stacks`) and only call `commit.create_status_from_github!(params)` for commits belonging to stacks under that resolved repository, discarding matches on `sha` alone across unrelated repositories.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual)
test "status webhook for org-a does not attach status to org-b's commit sharing the same sha" do
  org_a_stack = shipit_stacks(:shipit) # repo "org-a/whatever"
  org_b_commit = shipit_commits(:cyclimse_first) # belongs to a different stack/repo "org-b/other"
  shared_sha = "deadbeef" * 5

  org_b_commit.update!(sha: shared_sha)

  payload = {
    "sha" => shared_sha,
    "state" => "success",
    "context" => "ci/forged",
    "repository" => { "full_name" => "org-a/whatever", "owner" => { "login" => "org-a" } }
  }

  # Binding under test:
  # payload.repository.owner ("org-a") == commit.stack.repository.owner ("org-b")? -> false
  # yet StatusHandler applies the status anyway.
  refute_equal "org-a", org_b_commit.stack.repository.owner

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  org_b_commit.reload
  # Currently FAILS (vulnerability): status gets created despite owner mismatch.
  assert_equal 0, org_b_commit.statuses.where(context: "ci/forged").count,
    "StatusHandler must not attach cross-org statuses; sha-only matching lets org-a forge status for org-b's commit"
end
```
