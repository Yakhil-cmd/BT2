### Title
Webhook Signature Verified Against `repository.owner.login` While Handlers Act on the Unverified `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App / webhook secret to validate an incoming webhook's HMAC using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (or `organization.login`) [1](#0-0) [2](#0-1) . Once the signature is accepted, every event `Handler` resolves the target `Repository`/`Stack` using an entirely different field of the same unsigned JSON body: `repository.full_name`, via `Handler#repository_name` / `Handler#stacks` [3](#0-2) . Because the HMAC signature covers the raw JSON body as a whole (`request.raw_post`) but the field used to pick the *verifying key* (`owner.login`) is logically decoupled from the field used to pick the *acted-upon repository* (`full_name`), an attacker who controls one legitimately configured GitHub organization/webhook secret can craft a payload whose `owner.login` matches their own org (so the signature check passes with a secret they can compute) while `repository.full_name` names a stack belonging to a different organization already onboarded in this Shipit instance.

### Finding Description
`Shipit.github(organization: repository_owner)` looks up per-organization GitHub App configuration (each with its own `webhook_secret`) and is only used to select which HMAC secret is used for `verify_webhook_signature` [4](#0-3) . This supports multiple organizations each with distinct GitHub App configs/webhook secrets, as documented in `secrets.development.example.yml` [5](#0-4) .

The controller flow is:
1. `verify_signature` parses `repository_owner` from the raw JSON body and fetches that organization's `GitHubApp`, then verifies `X-Hub-Signature` against the raw body using that organization's secret [6](#0-5) .
2. `create` then re-parses the same raw body and dispatches it to handlers, e.g. `PushHandler`, `StatusHandler`, `PullRequest::*Handler`, `CheckSuiteHandler` [7](#0-6) [8](#0-7) .
3. Every handler resolves the repository it will act on via `Repository.from_github_repo_name(repository_name)` where `repository_name = payload.dig('repository', 'full_name')` — a completely different JSON key than the one used for signature-organization selection [3](#0-2) .

Nothing in the code enforces that `repository.owner.login` (used to pick the verifying secret) is consistent with `repository.full_name`'s owner segment (used to pick the acted-upon `Stack`). This is the exact binding-break pattern called out in scope: *"an organization that authenticated versus the repository that is written."* Concretely: signature verification proves "this request was signed with organization A's webhook secret," but the handlers then mutate/sync state for whatever repository `full_name` claims — which can belong to organization B, as long as a `Stack`/`Repository` for `B/repo` already exists in this Shipit instance.

Exploit path: an attacker who legitimately controls (or has push access triggering webhooks on) one onboarded GitHub organization/app installation A can compute a valid `X-Hub-Signature` for a forged JSON body (since they know or can trigger A's webhook secret through real webhook deliveries or, in shared-secret/misconfigured setups, simply reuse A's secret) while setting `repository.owner.login = "A"` and `repository.full_name = "B/victim-repo"` — a repository/stack belonging to a wholly different, already-configured organization B. `PushHandler` would then queue `stack.sync_github(expected_head_sha: params.after)` for the victim stack [9](#0-8) , and `StatusHandler`/`CheckSuiteHandler`/`PullRequest::*Handler` would similarly write commit statuses, close/reopen review stacks, or mutate labels for repository B's stacks — all gated only by A's signature.

### Impact Explanation
This breaks a repository-write trust boundary between two independently authenticated GitHub organizations hosted on the same Shipit instance. It allows forged webhook events (push/status/check_suite/pull_request/membership) to be attributed to and processed against a *different* organization's `Stack`s than the one whose secret was actually verified — i.e., unauthorized writes to another repository's Shipit-tracked state (sync triggers, commit statuses, PR/review-stack lifecycle transitions). This aligns with "cross-repository writes" / "unauthorized deploy" impact criteria, since `sync_github` feeds directly into deploy eligibility and status handling.

### Likelihood Explanation
This requires the Shipit instance to be configured with **multiple** GitHub organizations (the multi-org config schema in `config/secrets.development.example.yml`) and for the attacker to control at least one of those organizations' installations, plus knowledge of matching `full_name` for a target stack in another org (which is often public information). Given these are documented, supported deployment configurations rather than misconfiguration, the likelihood is non-trivial in any multi-tenant Shipit deployment, but not present in a single-organization deployment (the default/common case) since there `github_default_organization` collapses to a single shared secret and the boundary being broken doesn't exist.

### Recommendation
In `Handler#repository_name` (and equivalently across all handlers), derive the acted-upon repository/organization from the same field(s) that `WebhooksController#repository_owner` used for signature verification, or explicitly assert that the owner segment of `repository.full_name` matches `repository.owner.login` before dispatching to handlers. Alternatively, pass the verified `repository_owner` through to `Handler.call` and have `Repository.from_github_repo_name` reject/ignore payloads where the two disagree.

### Proof of Concept
Not independently executable without live multi-org GitHub App credentials and an existing cross-org `Stack`; the trace below documents the exploitable code path:
1. Configure Shipit with two organizations, `A` and `B`, each with its own `webhook_secret` (per `config/secrets.development.example.yml` multi-org schema) [5](#0-4) .
2. Attacker controls org `A`'s GitHub App installation/webhook secret and knows `B/victim-repo` is tracked by an existing Shipit `Stack`.
3. Attacker POSTs to `/webhooks` with `X-Github-Event: push`, a body containing `"repository": {"owner": {"login": "A"}, "full_name": "B/victim-repo"}, "ref": "refs/heads/main", "after": "<attacker-chosen sha>"`, signed with org A's `webhook_secret` via `X-Hub-Signature`.
4. `verify_signature` resolves `Shipit.github(organization: "A")` and validates successfully [1](#0-0) .
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("B/victim-repo")` and calls `stack.sync_github(expected_head_sha: params.after)` on org B's stack [3](#0-2) [9](#0-8) , despite the request only being verified as originating from org A.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
