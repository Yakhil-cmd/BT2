Based on my research, I found a plausible analog in ocore's main-chain stabilization logic, which exhibits the same class of bug as CVE-2024-36615: state describing a unit is exposed to concurrent readers before the full state-transition that produced it has completed, because the in-memory cache is mutated synchronously while the remaining consistency-critical writes (and their DB commit) happen later, across an async boundary, with no lock protecting readers from observing the intermediate state.

### Title
Torn read of unit stability/sequence cache during main-chain stabilization allows unlocked concurrent validation to see an inconsistent unit state - (File: main_chain.js)

### Summary
`markMcIndexStable()` in `main_chain.js` first synchronously flips `is_stable=1` in the global in-memory caches `storage.assocUnstableUnits`/`storage.assocStableUnits` for every unit reaching the newly-stabilized MCI, and only afterwards, across several `await`/callback boundaries, resolves the `sequence` field of any `temp-bad` units in that MCI (`good` vs `final-bad`) via `handleNonserialUnits()`. Any other unit's validation running concurrently (each validation only takes a per-author-address mutex, never the global "write" lock) can call `storage.readUnitProps()`, which serves straight from the mutated cache, and observe a unit that is already `is_stable=1` but still carries its pre-resolution `sequence` value. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`writer.saveJoint()` holds the `"write"` mutex while it calls into `advanceMcStability()` → `markMcIndexStable()`, but that lock only serializes writers against each other; it does **not** block concurrent readers such as another unit's validation, which is only serialized per-author-address via `mutex.lock(arrAuthorAddresses, ...)` in `validation.validate()`. [4](#0-3) 

Inside `markMcIndexStable()`, the function:
1. Iterates `storage.assocUnstableUnits`, synchronously sets `o.is_stable = 1`, moves the object into `storage.assocStableUnits`, and deletes it from `assocUnstableUnits` — this happens purely in memory, before any DB write.
2. Only then issues `UPDATE units SET is_stable=1 ...` and, via `handleNonserialUnits()`, performs the DB queries and cache field updates that resolve pending `temp-bad` units to their final `sequence` (`good` or `final-bad`), each requiring an async round-trip. [5](#0-4) [6](#0-5) 

Between steps 1 and 2 there are multiple callback/await boundaries, during which the Node.js event loop can service other pending callbacks — including another unit's validation flow that is not blocked by any lock associated with this specific unit. That concurrent validation calls `storage.readUnitProps()`, which serves the cached object directly without re-checking the DB when `assocStableUnits[unit]` is already populated: [7](#0-6) 

This is structurally the same bug class as the FFmpeg VP9 CVE: one execution context ("decoder thread"/stabilization writer) publishes a partially-updated object into a structure that a second concurrent context ("output thread"/concurrent validator) is allowed to read, before the object's full internal consistency has been established.

### Impact Explanation
A validator that reads the torn state (`is_stable=1` with a stale `sequence`) can make an incorrect serialization decision for a competing spend that references or conflicts with the unit under resolution: `validateAuthor()`'s `checkSerialAddressUse()` / `checkForDoublespends()` logic branches on exactly the `is_stable` and `sequence` fields to decide whether a competing unit is `good`, `temp-bad`, or `final-bad`. [8](#0-7) [9](#0-8) 

If a concurrently-validating unit observes a unit as already stable while its sequence has not yet been resolved to `final-bad`, it can accept that unit's outputs as spendable/valid competitors, producing node disagreement on validity/stability of the affected units, and, in the presence of a genuine double-spend attempt timed to this window, an inconsistent acceptance of a spend that should have been rejected.

### Likelihood Explanation
Exploiting the race requires precisely timing a unit submission (or AA trigger evaluation, which reuses the same `validation.validate()` path) to land during the specific handleNonserialUnits() async window of a main-chain stabilization step for units in temp-bad/final-bad sequence, which occurs only when unstable competing (nonserial) units exist at the newly-stabilizing MCI. This is a narrow, timing-dependent window that a single unprivileged unit poster cannot directly control but could attempt to race by flooding units at the moment stabilization is expected (predictable from network state), making exploitation difficult but not implausible, consistent with the CVSS AC:H rating of the original CVE.

### Recommendation
Protect `storage.assocStableUnits`/`assocUnstableUnits` transitions with the same lock validators use to read them (or hold the `"write"` mutex until `handleNonserialUnits()` and all cache field resolutions for the stabilized MCI are complete before allowing `is_stable=1` to be observable), so that `readUnitProps()` never returns a unit whose `sequence` has not yet been finally resolved for a stable MCI.

### Proof of Concept
Not independently reproducible from the index alone; the race window is inferred from code inspection of `main_chain.js:markMcIndexStable`/`handleNonserialUnits` versus the read path `storage.js:readUnitProps`, and would require a live multi-unit timing test against a running node to confirm exploitability (start a Devin session with full repo/test access to attempt reproduction).
