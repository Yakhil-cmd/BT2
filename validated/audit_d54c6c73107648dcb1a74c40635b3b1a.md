### Title
Path traversal via unsanitized release asset filenames in `gh release download` - (File: pkg/cmd/release/download/download.go)

### Summary
`gh release download` writes each release asset to disk using the asset's `name` field taken verbatim from the GitHub API response, with no path sanitization, unlike the archive-download code path in the same file which explicitly calls `filepath.Base()` on a server-supplied filename before using it.

### Finding Description
In `downloadRun`, asset filenames used for local file paths come straight from the release JSON (`a.Name`) returned by the GitHub API for the target repository: [1](#0-0) 

That name is threaded through `downloadAsset` → `dest.Copy(fileName, resp.Body)` without any sanitization: [2](#0-1) 

`Copy` builds the destination path with `makePath`, which does a plain `filepath.Join(w.dir, name)`: [3](#0-2) 

`filepath.Join` does not stop `..` path segments; if `name` contains `..`, the resulting `fp` can resolve outside `w.dir`. The write then proceeds via `os.MkdirAll(filepath.Dir(fp), ...)` followed by `os.OpenFile(fp, O_CREATE|O_TRUNC|O_WRONLY, 0644)`: [4](#0-3) 

By contrast, the *only* other place in this file that derives a filename from external, potentially attacker-influenced data (the `Content-Disposition` header returned for the tar/zip archive download) is explicitly hardened with `filepath.Base()`: [5](#0-4) 

This asymmetry — sanitizing the header-derived name but not the API `Name` field used for individual asset downloads — is the same class of bug as the reported issue: a user-controllable/attacker-controllable input value is trusted without validating that it stays within expected bounds, and the code silently produces a bad, dangerous outcome (a file write outside the intended directory) instead of erroring out. The `--pattern` glob match (`matchAny`) is only a filter on the release asset list; it does not sanitize or restrict the literal characters allowed in `a.Name`, so a crafted name such as `../../.ssh/authorized_keys` or `../../../.bashrc` would pass through untouched if it happens to match a glob (or if no `--pattern` is supplied).

### Impact Explanation
If a victim runs `gh release download` (or `gh release download --pattern ...`) against a release published by a hostile/compromised repository owner, and that release contains an asset whose `name` field embeds `../` sequences, the CLI would attempt to write the downloaded content to a path outside the user's intended download directory, subject only to OS filesystem permissions of the invoking user. This is an unprivileged, attacker-published-content vector reachable during completely normal `gh` usage (no MITM, no leaked token, no local/admin privilege required) and matches the "file write ... outside the intended path" acceptance criterion.

The practical severity depends on whether GitHub's release-asset upload API server-side rejects or normalizes filenames containing path separators/`..` — I could not verify this from the repository alone, since that enforcement (if any) lives on the GitHub.com/GHES server side, not in this client codebase. Because of this, exploitability is not fully confirmed end-to-end from the client repo alone; the client-side code shows no defense-in-depth against a malicious `name` value, which is the concrete gap this report calls out.

### Likelihood Explanation
Medium. It requires a user to download a release from a repository controlled by (or compromised by) an attacker — a normal, everyday `gh` operation — but exploitability further requires that the GitHub API actually accepts/returns an asset `name` containing directory traversal sequences, which is unverified from the CLI codebase alone.

### Recommendation
Sanitize `a.Name` (and any other externally supplied filename) the same way the Content-Disposition path already does: apply `filepath.Base()` (and reject names that still contain path separators, are empty, or resolve to `.`/`..` after cleaning) before it is passed into `downloadAsset`/`dest.Copy`, and verify the final resolved path stays within the configured destination directory (e.g., compare against `filepath.Clean(filepath.Join(dir, name))` having `dir` as a prefix) before opening the file for writing.

### Proof of Concept
Not independently executable from the indexed codebase alone (would require an actual GitHub release whose asset `name` contains `../` sequences, which depends on GitHub API server-side validation that is outside this repo). Conceptually:
1. Attacker creates/controls a public repo and publishes a release with an asset whose `name` field is `../../../../tmp/evil.sh` (assuming the upload API does not reject it).
2. Victim runs `gh release download <tag> -R attacker/repo` (or without `--pattern`, matching "no assets to download" checks first, so at least one legitimate-looking asset must be present or match a pattern).
3. `downloadRun` builds `targets[i].name = a.Name` unmodified and calls `downloadAssets` → `downloadAsset` → `dest.Copy(fileName, ...)`.
4. `makePath` performs `filepath.Join(w.dir, "../../../../tmp/evil.sh")`, producing a path outside `w.dir`, and `os.OpenFile` writes the response body there.
