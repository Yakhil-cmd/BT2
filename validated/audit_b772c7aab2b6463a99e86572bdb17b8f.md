### Title
Webhook signature verification is keyed on the payload's `repository.owner.login`, but the acted-upon repository is keyed on the payload's `repository.full_name` - allowing cross-organization webhook forgery ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the signature against using an **attacker-controlled** field from the unverified JSON body (`repository.owner.login`), while the handler that actually performs the write (looking up the `Stack`/`Repository` and syncing it) uses a **different** attacker-controlled field from the same body (`repository.full_name`). These two fields are never required to agree, so an attacker can pick an organization whose webhook is unauthenticated (or whose secret is known/misconfigured) to pass verification, while pointing `full_name` at a repository that belongs to a completely different, protected organization.

### Finding Description
The equality that should hold is:

`organization whose secret authenticated the request == organization owning the repository that gets written to`

In `WebhooksController#verify_signature`, the organization used to fetch the verifying app is derived purely from the payload: [1](#0-0) 

Specifically: [2](#0-1) 

`repository_owner` is read from `params.dig('repository', 'owner', 'login')`, a field fully controlled by whoever sends the POST request (before any signature has been validated).

`Shipit.github(organization: repository_owner)` returns the `GithubApp` config for that org, and `verify_webhook_signature` will trivially pass if that org has no `webhook_secret` configured: [3](#0-2) 

Test fixtures confirm this is a supported, real configuration (multiple orgs, one with `webhook_secret: # nil`): [4](#0-3) 

Once `verify_signature` passes, `WebhooksController#create` dispatches the **entire unmodified payload** to the event handler: [5](#0-4) 

Handlers (e.g. `PushHandler`) resolve which `Stack`/`Repository` to act on using a **different** field of the same payload - `repository.full_name` - with no cross-check against the organization that was used for signature verification: [6](#0-5) [7](#0-6) 

Because `repository_owner` (used to select the verifying secret) and `repository.full_name` (used to select the target `Stack`) are independent, unauthenticated fields of the same JSON body, an attacker can satisfy signature verification using any organization configured without a `webhook_secret` (or one whose secret has leaked) while directing the `full_name` at a stack belonging to an entirely different, properly-secured organization.

### Impact Explanation
This breaks the authentication boundary the webhook signature is supposed to enforce: it authenticates "a request claiming to be from organization X" but not "a request about repository X". A forged `push` event can enqueue `GithubSyncJob` for an arbitrary stack, which - combined with `continuous_deployment` - can trigger an unauthorized deploy, and other handlers (`status`, `check_suite`, `pull_request`, `membership`) are equally reachable this way, letting an unprivileged external attacker manipulate CI status / merge queue state or team membership for a stack/org they do not control. This matches the Critical bucket ("an unauthorized deploy, rollback or merge") in scope.

### Likelihood Explanation
Exploitability requires: (1) any organization configured in the Shipit instance without a webhook secret (documented/supported configuration, per the fixtures) or a leaked secret for a low-value org, and (2) crafting a POST body where `repository.owner.login` names that org while `repository.full_name` names the victim stack's repo. No authentication, session, or GitHub access is required - only network access to the public webhook endpoint - making this a low-effort, unprivileged attack, directly analogous to the front-running "account acted on ≠ account bound to the authorized caller" bug class in the reference report.

### Recommendation
Verify the signature using the secret associated with the organization that actually owns `repository.full_name` (or the `Repository`/`Stack` resolved from it), not a caller-suppliable `owner.login`/`organization.login` field. Concretely, resolve the target `Repository` first, derive its organization from that trusted record, and use that organization's `webhook_secret` for `verify_webhook_signature`, rejecting the request if the derived organization has no secret configured (do not silently `return true` when a secret is absent for a multi-org deployment).

### Proof of Concept
1. Shipit is configured with two orgs: `TrustedOrg` (has a `webhook_secret`) hosting stack `TrustedOrg/prod-app`, and `OpenOrg` (no `webhook_secret` configured, e.g. as shown in `secrets_double_github_app.yml`).
2. Attacker sends:
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=anything
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "OpenOrg" },
    "full_name": "TrustedOrg/prod-app"
  }
}
```
3. `verify_signature` calls `Shipit.github(organization: "OpenOrg")`; since `OpenOrg`'s `webhook_secret` is blank, `verify_webhook_signature` returns `true` regardless of the bogus `X-Hub-Signature`.
4. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("TrustedOrg/prod-app")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")`, causing Shipit to sync/build against `TrustedOrg`'s stack despite the request never being authenticated by `TrustedOrg`'s secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
