### Title
StatusHandler binds a status update to whatever stack owns a matching `sha`, ignoring the payload's `repository` field, allowing a webhook from repository B to write a `Status` onto repository A's stack - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target stack purely from `Commit.where(sha: params.sha)`, never calling `Handler#stacks` / `Repository.from_github_repo_name` to verify that the payload's `repository` field actually corresponds to the stack that owns the commit. Because `sha` is not scoped to a repository at the database level (there is no global uniqueness constraint on `sha` across stacks), a correctly-signed `status` webhook from an attacker-controlled repository B, referencing a commit object that also exists in repository A's stack, causes `Status.replicate_from_github!` to create a `Status` row keyed to stack A's `stack_id`, even though `params`/`payload` never mentions repository A.

### Finding Description
Broken binding, stated as an equality that the code should enforce but does not:
`stack_id_used_in_replicate_from_github! == Handler#stacks.where(repo == payload.dig('repository','full_name')).stack_id`

Actual code path in `app/models/shipit/webhooks/handlers/status_handler.rb`: [1](#0-0) 

`process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` - it never calls `repository_name` or `stacks`, both defined on the base `Handler` class: [2](#0-1) 

`create_status_from_github!` then uses the found commit's own `stack_id` (not any value derived from the payload) to create the status: [3](#0-2) [4](#0-3) 

There is no filter matching `commit.stack.repository` against `payload.dig('repository','full_name')` anywhere in this call chain.

Signature verification at the controller level (`before_action :verify_signature`) only proves the webhook was legitimately sent by GitHub for the *sending* repository's org, keyed by `repository_owner` (i.e., the attacker's own org/repo B): [5](#0-4) 
It provides zero guarantee that the `sha` inside the payload "belongs" to that same repository - `Commit.where(sha: ...)` happily matches rows created for a completely different stack/repository.

Attacker request/PR: Attacker owns repository B (any public GitHub repo they control) and can obtain the exact same git commit object (same tree, parent, author, committer, timestamps, message) as a commit already ingested into Shipit for repository A's stack - trivially done by fetching/copying that object (e.g. via a shared fork lineage, or by reconstructing the object byte-for-byte from a public commit in A, which is exactly how git's content addressing works; no SHA-1 collision attack is required). The attacker pushes/PRs that commit into repository B, then repository B's GitHub App legitimately emits a `status` webhook (`state: success`) for that `sha`, correctly signed for org B. Shipit's `StatusHandler` matches the row for stack A via `Commit.where(sha: ...)` and writes the new `Status` there, using stack A's `stack_id`.

Existing guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema) all pass because they only validate that the request is a legitimately-signed `status` event for org B - none of them check that `payload['repository']` matches the stack of the commit being updated.

### Impact Explanation
An attacker who controls (or forks into) any repository can inject a `Status` (`state: success/failure/error`, arbitrary `description`/`target_url`/`context`) onto a commit belonging to an unrelated stack/tenant, as long as they can obtain a commit object with an identical `sha` to one already tracked by that victim stack. Since `success` statuses influence `deployable?`/`blocked?` and can unblock continuous delivery (`schedule_continuous_delivery`, `Hook.emit(:deployable_status, ...)`), this can cause an unauthorized deploy trigger on stack A driven entirely by an attacker-controlled repository B's webhook - matching the Critical category "a payload for one repository mutating another's stack, commit, task ... or an unauthorized deploy". This is repeatable against any stack/commit pair where the attacker can reproduce the sha.

### Likelihood Explanation
Preconditions: attacker needs a repository (owned or forked) whose GitHub App/webhook is configured to talk to the same Shipit instance, and needs to obtain a commit object identical to one already present in the victim stack (feasible for public repos via fork lineage or direct object reconstruction - not a cryptographic SHA-1 collision). No Shipit secrets, sessions, or privileged roles are required; the webhook signature is legitimately produced by GitHub for the attacker's own org. Feasibility is high for forked/mirrored repositories (a very common Shipit deployment pattern - multiple stacks tracking the same upstream repo or its forks), and the attack is fully repeatable.

### Recommendation
In `StatusHandler#process`, scope the commit lookup to the stacks resolved from the payload's `repository` field (using the existing `stacks` method on `Handler`) instead of a bare `Commit.where(sha: params.sha)`, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalent, and pass/validate `stack_id` against the resolved repository before calling `Status.replicate_from_github!`. Optionally also enforce a uniqueness constraint or explicit repository check at the `Commit` level to prevent cross-stack sha collisions from being trusted.

### Proof of Concept
Minitest plan (no live GitHub):
1. Create `stack_a` for repo `"org-a/repo-a"` and `stack_b` for repo `"org-b/repo-b"`.
2. Create `commit = Shipit::Commit.create!(stack: stack_a, sha: 'deadbeef'*5, ...)` simulating a commit already ingested for stack A.
3. Build a `status` payload with `repository.full_name = "org-b/repo-b"`, `sha = commit.sha`, `state: "success"`.
4. Stub/mock `Shipit::Repository.from_github_repo_name` and `Shipit::Webhooks::Handlers::Handler#repository_name` to raise `MiniTest::Assertion` if called; call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)`.
5. Assert the call does **not** raise (i.e., neither helper is invoked) and that `commit.statuses.last.stack_id == stack_a.id` and `stack_b.commits.where(sha: commit.sha).empty?` - proving the status was attributed to stack A purely via `sha`, with no verification against the payload's `repository` ("org-b/repo-b"), demonstrating the binding `stack_id_used == stacks_from_payload_repository` is violated.
