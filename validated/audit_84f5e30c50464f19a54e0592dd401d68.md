Confirmed: this is a genuine multi-tenant Shipit deployment (`config/secrets.yml` can define multiple GitHub orgs, each with its own `webhook_secret`, as documented in `docs/setup.md:182-209` and tested via `test/dummy/config/secrets_double_github_app.yml`), and `Shipit.github(organization:)` selects a distinct `GitHubApp`/secret per org key.

### Title
Webhook signature verified against `repository.owner.login`, but write target resolved from `repository.full_name` — cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App/`webhook_secret` to validate the HMAC signature against using the attacker-controlled field `repository.owner.login` (falling back to `organization.login`) from the unauthenticated JSON body, while every webhook handler resolves the actual repository/stack to act on using a *different* field of the same body, `repository.full_name`. Nothing binds these two fields together, so on a multi-organization Shipit instance an attacker who knows (or controls) the webhook secret for one onboarded organization can forge a payload whose `repository.owner.login`/`organization.login` names that organization (making the signature check pass) but whose `repository.full_name` names a repository belonging to a completely different, victim organization also hosted on the same instance.

### Finding Description
`verify_signature` selects the signing key before establishing any binding to what will actually be processed: [1](#0-0) 
`repository_owner` is derived straight from the untrusted payload: [2](#0-1) 

`Shipit.github(organization:)` looks up a distinct `GitHubApp` (and thus a distinct `webhook_secret`) per organization key when the multi-org config schema is used: [3](#0-2) 
This multi-tenant schema, and per-org `webhook_secret`, is a documented, supported configuration: [4](#0-3) 

Once the signature is accepted, `create` dispatches the *same raw payload* to handlers: [5](#0-4) 

But every handler resolves the repository/stack to mutate using `repository.full_name`, not `repository.owner.login`: [6](#0-5) [7](#0-6) [8](#0-7) 

This is structurally identical to the reported Vault.sol bug class: two branches of logic are supposed to operate on consistent data (`reserveUSDV`/`reserveVADER` in the audit; `repository.owner.login`/`repository.full_name` here) but a copy/paste-style mismatch means the verification step is bound to a value (`repository_owner`) that is never the same value later acted upon (`repository.full_name`). The equality that should hold — *the organization whose secret validated the signature* == *the organization of the repository actually written to* — is not enforced anywhere in code.

### Impact Explanation
On any Shipit instance configured for more than one GitHub organization (the "Using Multiple Github Applications" setup, which the engine documents and explicitly supports), an operator/admin of Organization A — who legitimately possesses Organization A's own `webhook_secret` because they configured their own GitHub App — can send a forged webhook (`push`, `pull_request`, `status`, `check_suite`, `membership`) whose `repository.owner.login`/`organization.login` says `"OrgA"` (passing `verify_signature`) but whose `repository.full_name` says `"OrgB/victim-repo"`. This lets OrgA cross into OrgB's stacks:
- `PushHandler` will enqueue `sync_github` for OrgB's stacks, i.e. cause a resync/deploy trigger on a foreign stack.
- `PullRequest::OpenedHandler`/`ReviewStackAdapter` can provision a review stack for an arbitrary existing PR of OrgB's repository, causing Shipit to check out an attacker-influenced ref/sha and execute that stack's `shipit.yml` steps on the deploy host using the real GitHub credentials for OrgB.
- `ClosedHandler`/`ReopenedHandler`/`Labeled`/`UnlabeledHandler` can archive/unarchive OrgB's review stacks.

This is a cross-repository/cross-organization write and can lead to unauthorized deploys/task execution against a repository the attacker does not otherwise control, satisfying the "cross-repository writes" / "unauthorized deploy" impact bar.

### Likelihood Explanation
Requires only that the Shipit instance be configured with more than one GitHub organization (a documented, supported deployment mode) and that the attacker control (or know) the webhook secret of any one onboarded org — something every onboarded org's own GitHub App admin legitimately has, without needing a Shipit session, `ApiClient` token, or the target org's own secret. No GitHub App private key or Shipit account is required.

### Recommendation
Bind signature verification to the same identifier that handlers use to locate the mutated resource: derive the GitHub App/secret from `repository.full_name`'s owner segment (or, better, verify the payload against *every* configured organization's secret and additionally assert that `repository.full_name`'s owner matches the organization whose secret validated), rather than trusting `repository.owner.login`/`organization.login` in isolation.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with a distinct `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. As an operator of `OrgA` (who knows `OrgA`'s `webhook_secret`), craft a `push` payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha that exists in OrgB/victim-repo>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
3. Sign the raw body with `OrgA`'s `webhook_secret` and send it to `/github/webhooks` with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "OrgA")` and the HMAC matches → request passes.
5. `PushHandler#process` resolves `Repository.from_github_repo_name("OrgB/victim-repo")` and enqueues `sync_github` for that stack, despite the signature never having been checked against `OrgB`'s secret. [9](#0-8) [10](#0-9)

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
