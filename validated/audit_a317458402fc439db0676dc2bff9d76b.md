## Analog Found

### Title
AA case logic gated on `balance[asset] == 0` can be griefed by front-running a dust deposit before the legitimate trigger is processed - (File: `aa_composer.js`, `main_chain.js`)

### Summary
The DYAD report shows that a state check ("vault must have zero assets") performed at execution time can be defeated by an unprivileged third party who deposits a trivial amount into the victim's position immediately before the victim's transaction executes, permanently changing the gating condition and blocking the victim's intended state transition. In Obyte's Autonomous Agent (AA) execution model, the analogous pattern exists: AA `case`/`init` logic frequently gates behavior on the current `balance[asset]` of the AA (e.g. "is this the first deposit, i.e. is the balance zero"), and **any unprivileged party can send funds to an AA to change that balance** before a specific victim trigger executes, exactly like Bob depositing 1 wei of wstETH into Alice's dNFT.

### Finding Description
Any unprivileged sender can pay into an AA address, and the AA composer unconditionally folds that payment into the AA's on-chain balance before evaluating the trigger's case logic: [1](#0-0) [2](#0-1) 

AA formulas reference this mutable `balance[...]` value directly in case-selection and pricing logic. The shipped `uniswap_like_market_maker.oscript` sample AA illustrates the exact "must be empty/zero to proceed" gating pattern from the report:
```
if ($asset_balance == 0 OR $bytes_balance == 0){ // initial deposit
    $issue_amount = balance[base];
    return;
}
``` [3](#0-2) 

Crucially, when multiple trigger units land on the same MCI, ocore processes them in a **deterministic but attacker-influenceable** order — sorted by DAG `level` and then unit hash, not by arrival/broadcast time a defender controls: [4](#0-3) [5](#0-4) 

An attacker who observes a victim's about-to-be-included trigger unit (e.g. in the peer-to-peer unit propagation before its MCI stabilizes) can compose and post their own tiny payment to the same AA, choosing parents/timing so that their unit obtains a lower `level`/hash and is therefore guaranteed to be processed by `handleAATriggers` before the victim's unit within the same MCI. This mirrors the report's mempool front-run: the attacker's dust deposit is applied to `balance[asset]` first, corrupting the victim's balance-gated branch selection or price/ratio computation.

### Impact Explanation
Because the AA's balance-zero (or balance-equality) check silently flips from true to false once the attacker's dust lands first, the victim's trigger falls through to the wrong branch. In the market-maker sample this means the legitimate first depositor no longer takes the "initial deposit" branch; instead the ratio-based branch computes `$current_ratio = $asset_balance / $bytes_balance` off attacker-chosen dust amounts, producing a wildly skewed `$issue_amount` for the victim (fund loss for the victim / disproportionate share for the attacker) — a concrete AA fund-loss outcome, not merely resource griefing. The same primitive can be used against any AA that gates a withdrawal/close/removal action on `balance[...]==0` (or an exact numeric match), permanently freezing or corrupting the victim's intended interaction, analogous to the reported dNFT vault-removal DoS.

### Likelihood Explanation
Likelihood is moderate to high: sending a payment to any address (including AAs) requires no special privilege, dust amounts are cheap, and the AA trigger ordering rule (`ORDER BY units.level, units.unit, address`) is public and deterministic, so an attacker who is already relaying/monitoring the network can reliably craft a competing unit that resolves ahead of the target within the same MCI. Any AA whose author writes balance-zero/equality-gated logic (a common and natural pattern, as shown in the shipped sample) is exposed.

### Recommendation
- Discourage/flag AA `oscript` patterns that gate irreversible or price-sensitive branches purely on `balance[asset] == 0` or exact equality; document this footgun prominently for AA authors (similar to the DYAD team's fix of allowing removal even with residual assets, with a clear warning).
- Where possible, have the AA track its own internal accounting state variable (`var[...]`) for "first deposit" / "should be empty" checks instead of relying on the externally-mutable `balance[...]`, since state variables are only modified by the AA's own logic and are not directly manipulable by unprivileged senders.
- Consider providing built-in oscript helpers/guidance for atomically reserving or snapshotting balances relevant to a specific trigger to reduce exposure to this dust-front-running class of issues.

### Proof of Concept
1. Deploy an AA implementing an "initial deposit" branch gated on `balance[asset]==0` (as in `uniswap_like_market_maker.oscript`).
2. Victim Alice broadcasts a unit triggering the AA's "invest in MM" case expecting the initial-deposit branch (asset balance currently zero).
3. Attacker Bob, observing Alice's pending unit, immediately composes and posts his own tiny payment (e.g., 1 unit of `$asset`) to the same AA, selecting parents so his unit's `level`/hash sorts before Alice's unit within the same MCI.
4. When the MCI stabilizes, `handleAATriggers` (`main_chain.js` / `aa_composer.js`) processes Bob's trigger first, updating `aa_balances` so `$asset_balance` is no longer 0.
5. Alice's trigger is then processed; `$asset_balance == 0` is now false, so her deposit is routed through the ratio-based branch using Bob's dust-skewed balances, producing an incorrect `$issue_amount` for Alice instead of the expected initial-deposit treatment — reproducing the report's "front-run to defeat a balance-gated action" impact inside ocore's AA execution model.
