### Title
Api::CCMenuController#stack calls `Stack.from_param!` directly, bypassing the `current_api_client.stack_id` scope - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::BaseController#stack` is the safe helper that resolves a stack through `stacks.from_param!`, which restricts lookups to `current_api_client.stack_id` when the client is stack-scoped. `Api::CCMenuController` overrides `#stack` and calls `Stack.from_param!(params[:stack_id])` directly, completely skipping the `stacks` scope, so a token issued for Stack A can be used to read the CCTray deploy status of any other Stack B.

### Finding Description
The intended binding is: for any `ApiClient` with `stack_id?` true, `stack == a member of Stack.where(id: current_api_client.stack_id)`, never any other stack.

`Api::BaseController` implements this correctly: [1](#0-0) 

But `Api::CCMenuController` defines its own private `#stack`, which resolves the stack unconditionally from `params[:stack_id]` using the unscoped `Stack.from_param!` class method instead of the scoped `stacks.from_param!` instance method: [2](#0-1) 

This controller also authenticates via a `token` query param rather than Basic Auth, but still relies on `ApiClient.authenticate`, which can return a stack-scoped `ApiClient` (`stack_id?` true): [3](#0-2) 

Exploit flow: an operator issues an ApiClient token scoped to Stack A (`read:stack` permission, `stack_id` = A). An attacker holding that token requests `GET /stacks/:stack_id/ccmenu.xml?token=<token>` with `stack_id` set to Stack B's `to_param`. `require_permission :read, :stack` only calls `current_api_client.check_permissions!(:read, :stack)`, which validates operation/scope, not the specific stack instance being accessed. `#stack` then resolves Stack B via `Stack.from_param!`, entirely ignoring `current_api_client.stack_id`, and returns Stack B's latest deploy/rollback status.

### Impact Explanation
An attacker holding an ApiClient token scoped to Stack A can read the deploy status (deploy id, completion time, running state) of any other stack in the Shipit instance, including stacks belonging to different repositories/tenants that they are not authorized to see. This is a cross-tenant unauthorized read of stack/task state, matching the "High — unauthenticated/unauthorized read of stack state, task streams or deploy output" category. It is repeatable against any stack id in the system and requires no per-stack authorization beyond holding any valid scoped token.

### Likelihood Explanation
Requires the attacker to already possess a valid `ApiClient` token scoped to at least one stack (an operator must have issued it for a legitimate purpose, e.g. embedding it in a CCTray/CI dashboard integration URL). Given that precondition, exploitation is trivial: simply substitute a different `stack_id` in the URL. No GitHub secrets, session, or elevated privileges are needed beyond the one legitimately-issued token.

### Recommendation
Change `Api::CCMenuController#stack` to use the scoped lookup consistent with the base controller:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
where `stacks` is inherited from `Api::BaseController#stacks`, which filters by `current_api_client.stack_id` when scoped.

### Proof of Concept
```ruby
# test/controllers/shipit/api/ccmenu_controller_test.rb
test "#show does not leak deploy status of a stack outside the token's scope" do
  stack_a = shipit_stacks(:shipit)
  stack_b = shipit_stacks(:cyclimse) # a different stack
  scoped_client = ApiClient.create!(stack_id: stack_a.id, permissions: %w[read:stack])

  get :show, params: { stack_id: stack_b.to_param, token: scoped_client.token }

  assert_response :forbidden # or :not_found
  # Binding under test:
  # scoped_client.stack_id == stack_a.id  (true)
  # resolved stack via `stack` helper must be a member of Stack.where(id: scoped_client.stack_id)
  # Currently CCMenuController#stack returns stack_b, violating the equality.
end
```
This test currently fails (returns 200 with Stack B's CCTray XML) because `#stack` uses `Stack.from_param!` instead of `stacks.from_param!`.
