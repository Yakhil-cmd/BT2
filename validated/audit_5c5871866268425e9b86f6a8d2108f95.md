### Title
Unsafe `_mint` / `transferFrom` in `handleERC721Transfer` Permanently Locks Bridged ERC721 NFTs in Non-Receiver Contracts — (`contracts/service_chain/bridge/BridgeTransferERC721.sol`)

---

### Summary

`BridgeTransferERC721.handleERC721Transfer` delivers bridged ERC721 tokens to the destination `_to` address without verifying that the recipient can handle ERC721 tokens. In mint-burn mode it calls `mintWithTokenURI` → `_mint` (no receiver check); in lock-unlock mode it calls `transferFrom` (no receiver check). If `_to` is a contract that does not implement `IERC721Receiver`, the NFT is permanently locked in that contract. The source-chain NFT has already been burned or locked, and the bridge nonce is consumed and marked handled before the delivery call, so the loss is irreversible.

---

### Finding Description

`handleERC721Transfer` in `BridgeTransferERC721.sol` has two delivery paths:

**Path 1 — mint-burn mode (line 67):**
```solidity
require(ERC721MetadataMintable(_tokenAddress).mintWithTokenURI(_to, _tokenId, _tokenURI), "mint failed");
```
`mintWithTokenURI` calls `_mint(to, tokenId)` directly: [1](#0-0) 

`_mint` only assigns ownership and emits `Transfer`; it never calls `_checkOnERC721Received`: [2](#0-1) 

**Path 2 — lock-unlock mode (line 69):**
```solidity
IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId);
```
`transferFrom` calls `_transferFrom`, which also performs no receiver check. Only `safeTransferFrom` invokes `_checkOnERC721Received`: [3](#0-2) [4](#0-3) 

Both paths are reached after the bridge has already consumed the nonce and marked the request as handled (lines 49–64 execute before lines 66–70): [5](#0-4) 

---

### Impact Explanation

When `_to` is a contract that does not implement `IERC721Receiver.onERC721Received`:

- **Mint-burn mode**: The NFT is minted to `_to` (succeeds, no revert), but `_to` has no way to transfer or interact with it. The NFT is permanently locked. On the source chain the NFT was already burned by `_requestERC721Transfer` (line 91): [6](#0-5) 

- **Lock-unlock mode**: The NFT is transferred from the bridge to `_to` (succeeds, no revert), but `_to` cannot move it. The bridge nonce is consumed and `handleNoncesToBlockNums[_requestedNonce]` is set, so the transfer cannot be replayed or recovered.

In both cases the user permanently loses a bridged NFT. The corrupted state is: the NFT's `_tokenOwner` mapping points to a contract that can never call `transferFrom` or `safeTransferFrom` on it, and the bridge's handle nonce is advanced past this request.

---

### Likelihood Explanation

Any user can trigger this by specifying a contract address as `_to` when calling `requestERC721Transfer` or `onERC721Received` on the source chain. No privileged access is required. The bridge operators relay the request faithfully. Common real-world scenarios include: specifying a multisig wallet, a DAO contract, a DeFi protocol address, or any contract that was not built to receive ERC721 tokens. The trigger is fully unprivileged and requires only a valid bridge transfer request.

---

### Recommendation

**In mint-burn mode**, replace `mintWithTokenURI` (which uses `_mint`) with a safe variant that calls `_safeMint`. Since `ERC721MetadataMintable` from OpenZeppelin v2 does not expose `_safeMint` publicly, the token contract should be extended or a new `safeMintWithTokenURI` function added that calls `_safeMint` instead of `_mint`.

**In lock-unlock mode**, replace `transferFrom` with `safeTransferFrom`:

```solidity
// Before (unsafe):
IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId);

// After (safe):
IERC721(_tokenAddress).safeTransferFrom(address(this), _to, _tokenId);
```

Both fixes ensure that if `_to` is a contract that cannot handle ERC721 tokens, the transaction reverts before the NFT is delivered, allowing the bridge operators to detect the failure and take corrective action rather than silently locking the asset.

---

### Proof of Concept

1. Alice owns NFT token ID `42` on the source chain.
2. Alice calls `requestERC721Transfer(nftAddress, victimContract, 42, "0x")` where `victimContract` is a deployed contract that does not implement `IERC721Receiver` (e.g., a plain multisig or any contract without `onERC721Received`).
3. In mint-burn mode: the source bridge calls `ERC721Burnable.burn(42)` — Alice's NFT is destroyed on the source chain.
4. Bridge operators observe the `RequestValueTransferEncoded` event and call `handleERC721Transfer(..., victimContract, ..., 42, ...)` on the destination bridge.
5. The destination bridge executes (in order):
   - `_setHandledRequestTxHash(txHash)` — request marked handled
   - `_updateHandleNonce(requestedNonce)` — nonce consumed
   - `ERC721MetadataMintable(nftAddress).mintWithTokenURI(victimContract, 42, uri)` — calls `_mint(victimContract, 42)` — succeeds with no revert
6. NFT token ID `42` is now owned by `victimContract` on the destination chain. `victimContract` has no `transferFrom` or `safeTransferFrom` capability for this token. The NFT is permanently locked.
7. The bridge nonce is consumed; the request cannot be replayed. Alice has lost her NFT permanently.
