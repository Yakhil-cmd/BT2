### Title
`EnvironmentVariables#interpolate` falls back to the Shipit master process's `ENV` for any `$WORD` not present in the task's environment hash - ([File: lib/shipit/environment_variables.rb])

### Summary
`Shipit::EnvironmentVariables#interpolate` substitutes `$WORD` occurrences in a deploy step string with `@env.fetch(WORD) { ENV[WORD] }` rather than failing or substituting nothing when `WORD` is absent from the task's merged environment hash. Since deploy/review steps can originate from a PR's own `shipit.yml` (when `respect_bare_shipit_file` is enabled), an attacker who controls that file can reference any environment variable name and, if that name happens to exist in the Shipit host process's own `ENV` (and not in the task's `@env`), have its value substituted directly into the command line that is executed and streamed back as task output.

### Finding Description
The claimed binding is: `value substituted for $WORD == @env[WORD]`. The actual code is:

```ruby
def interpolate(argument)
  return argument unless @env

  argument.gsub(/(\$\w+)/) do |variable|
    variable.sub!('$', '')
    Shellwords.escape(@env.fetch(variable) { ENV[variable] })
  end
end
``` [1](#0-0) 

This is `@env.fetch(WORD) { ENV[WORD] }`, i.e. `value == @env[WORD] if present, else ENV[WORD]`. The binding stated in the question is therefore broken by design: when `WORD` is not a key in `@env`, the code deliberately falls through to the Shipit master process's own `ENV`, not to "nothing" or to an error.

Call path: `TaskCommands#perform`/`#install_dependencies` builds each step as `Command.new(command_line, env:, chdir:)` where `env` is the merged hash from `TaskCommands#env`, which combines `Commands#env` (base), `@stack.env`, several task-derived keys, `deploy_spec.machine_env`, and `@task.env`. [2](#0-1) 

`Command#initialize` stores this into `@env` (stringified values), and `Command#start` calls `interpolated_arguments`, which calls `interpolate_environment_variables`, which delegates to `EnvironmentVariables.with(env).interpolate(argument)` for every argument. [3](#0-2) [4](#0-3) 

The resulting `interpolated_arguments` are what get passed to `PTY.spawn` and whose stdout is streamed back as the visible task log via `stream`/`read_stream`. [5](#0-4) 

None of the referenced guards (`EnvironmentVariables#permit`, model validations, `verify_signature`, `require_permission!`) apply here: `permit` is a separate method used only for whitelisting user/task-submitted variables against `variable_definitions`, and is not invoked anywhere in the `interpolate` path. [6](#0-5) 
There is no check anywhere in `Command`, `TaskCommands`, or `EnvironmentVariables` that rejects a `$WORD` token whose name is absent from `@env`; the fallback to `ENV[variable]` is unconditional.

Exploit flow: an attacker opens a PR on a repository/stack that has `respect_bare_shipit_file` enabled, adding to `shipit.yml` a deploy/review step whose command string includes a token like `echo $GITHUB_TOKEN` (or any other var name they suspect exists in the Shipit host's process environment, e.g. `$AWS_SECRET_ACCESS_KEY`, `$DATABASE_URL`, etc.). If that variable name is not one of the keys explicitly injected by `TaskCommands#env`/`Stack#env` for that stack, `EnvironmentVariables#interpolate` falls back to reading it straight from the master Shipit process's `ENV`, shell-escapes it, and inlines it into the argument list executed via `PTY.spawn`; the value then appears verbatim in the task's stdout stream, which is visible to anyone who can view that task's output (including, on public-facing review stacks, potentially the PR author themselves).

### Impact Explanation
If any secret-bearing environment variable exists in the Shipit master process's `ENV` (common patterns include `GITHUB_TOKEN`, cloud credentials, or other deploy-time secrets used to bootstrap the Rails process) and is not deliberately re-exported into the per-task `env` hash, an attacker-controlled `shipit.yml` step can exfiltrate it into task output that the attacker (or any viewer of that task) can read. This matches the "Critical: exfiltration of deploy-time secrets / `GITHUB_TOKEN`" impact category. The technique is repeatable against any stack that consumes attacker-influenced `shipit.yml` content and against any environment variable name the attacker can guess, not limited to `GITHUB_TOKEN`.

### Likelihood Explanation
Exploitability requires: (1) a stack configured to respect a bare/PR-supplied `shipit.yml` (`respect_bare_shipit_file`) so the attacker's step definitions are actually executed, and (2) the targeted variable name to exist in the Shipit master process's OS environment but not be present in the task's merged `env` hash (i.e., not already set by `Stack#env`, `TaskCommands#env`, or `@task.env`). Precondition (1) is an explicit, documented opt-in feature; precondition (2) depends on host/operator configuration and is outside the attacker's direct knowledge, but the attacker can probe cheaply by referencing many plausible variable names simultaneously in one step (`env | grep TOKEN`, or `$FOO $BAR $BAZ...`) and reading whichever ones resolve to non-empty values in the task log. Attacker cost is a single PR/branch push; no credentials or privileged role are required.

### Recommendation
Change `EnvironmentVariables#interpolate` to never fall back to the master process's `ENV`. If a variable is not present in the task's `@env`, either leave the literal `$WORD` token unexpanded, substitute an empty string, or raise, but do not read from `ENV[variable]`:

```ruby
def interpolate(argument)
  return argument unless @env

  argument.gsub(/(\$\w+)/) do |variable|
    name = variable.sub('$', '')
    Shellwords.escape(@env.fetch(name, ''))
  end
end
```

More generally, audit `Command#unbundled_env`/`BASE_ENV` construction as well, to ensure the master process's broader `ENV` is not otherwise exposed to task subprocesses beyond the explicitly intended `PATH` passthrough.

### Proof of Concept
```ruby
# test/unit/environment_variables_test.rb (extend existing file)
test 'interpolate leaks master process ENV for variables absent from @env' do
  ENV['GITHUB_TOKEN'] = 'secret-master-token'
  task_env = { 'ENVIRONMENT' => 'production' } # deliberately lacks GITHUB_TOKEN
  command = Shipit::Command.new('echo $GITHUB_TOKEN', chdir: Dir.tmpdir, env: task_env)

  interpolated = command.interpolated_arguments.join(' ')

  # Binding under test: substituted value should equal @env['GITHUB_TOKEN'] (nil/absent),
  # but instead equals ENV['GITHUB_TOKEN'] from Shipit's own process.
  assert_not_equal task_env['GITHUB_TOKEN'], 'secret-master-token'
  assert_includes interpolated, Shellwords.escape('secret-master-token')
ensure
  ENV.delete('GITHUB_TOKEN')
end
```
This demonstrates that `interpolated_arguments` contains the Shipit master process's `ENV['GITHUB_TOKEN']` value even though the task's own `env` hash never contained that key, confirming the leak.
