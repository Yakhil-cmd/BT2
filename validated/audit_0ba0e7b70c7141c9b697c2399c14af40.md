### Title
Webhook signature verified against the organization named in `repository.owner.login` while handlers act on the repository named in `repository.full_name`, enabling cross-organization forged webhooks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to verify the HMAC signature against using the field `repository.owner.login` (or `organization.login`) taken from the untrusted payload. Every webhook handler, however, resolves the repository it actually mutates using a *different* field of the same payload, `repository.full_name`. In a multi-organization Shipit deployment (a first-class, documented feature via `Shipit.github(organization:)` / `github_app_config`), an attacker who legitimately controls one registered organization (and therefore knows that organization's own `webhook_secret`) can produce a validly-signed webhook whose `repository.owner.login` points at their own org (so the signature check passes) while `repository.full_name` points at a completely different, victim organization's repository. This breaks the binding "organization that authenticated the webhook" == "repository that gets written to."

### Finding Description
`verify_signature` computes:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end

def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
end

`Shipit.github(organization:)` looks up per-organization webhook secrets when the app is running in multi-org mode:

Once the signature passes, `WebhooksController#create` dispatches to handlers using the whole (attacker-controlled) JSON body:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [4](#0-3) 

But every handler resolves the affected repository from a *different* field, `repository.full_name`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [5](#0-4) 

`PushHandler` uses this to trigger a sync at an attacker-chosen SHA:
```ruby
def process
  stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [6](#0-5) 

The pull-request handlers do the same with `params.repository.full_name`, e.g. opening/archiving/unarchiving review stacks or updating PR labels for a repository resolved independently of the field that was used for signature verification:
```ruby
def repository
  @repository ||= Shipit::Repository.from_github_repo_name(params.repository.full_name) || Shipit::NullRepository.new
end
``` [7](#0-6) 

Because `repository.owner.login` and `repository.full_name` are independent, attacker-controlled JSON fields inside the same signed byte stream, nothing forces `repository.full_name` to belong to the organization whose secret validated the signature. The signature only proves "this byte stream was signed by *some* organization's secret," not "this byte stream is authorized to reference *this specific* repository/organization."

### Impact Explanation
An attacker who administers (or is a legitimate member configuring) one organization tracked by a multi-tenant Shipit instance — and therefore knows that organization's own GitHub App `webhook_secret` (a secret they created themselves when setting up their own GitHub App, per `docs/setup.md`) — can forge webhook events on behalf of *any other* organization/repository tracked by the same Shipit instance. This yields:
- Forced `GithubSyncJob` runs with an attacker-chosen `expected_head_sha` against a victim's stack, corrupting the tracked HEAD state that downstream deploy/CI trust decisions rely on.
- Cross-organization archiving/unarchiving of review stacks, and mutation of pull-request metadata/labels for repositories the attacker does not own.

This is a cross-repository/cross-organization write achieved purely by crafting a payload — no access to the victim's GitHub App, webhook secret, or Shipit session is required. It matches the Critical "cross-repository writes" impact category.

### Likelihood Explanation
This requires the Shipit instance to be configured in multi-organization mode (`secrets.github` keyed by multiple organization names), which is a supported, documented configuration path (`Shipit.github_organizations`, `github_app_config`), not a deviation from how the engine is meant to be mounted. Any party legitimately onboarded as one of the tracked organizations (i.e., possessing a valid, low-privilege registration in a shared multi-tenant Shipit deployment) can mount this attack against sibling organizations sharing the instance, with no additional prerequisites beyond crafting an HTTP POST.

### Recommendation
Bind webhook-signature verification to the same repository/organization identity that handlers act upon. Concretely:
- After verifying the signature, additionally assert that `repository.full_name`'s owner matches `repository_owner` (the value used to select the webhook secret), rejecting the request otherwise.
- Alternatively, verify the signature using the organization actually owning `repository.full_name` and only that value, removing any indirection through separate `repository.owner.login`/`organization.login` payload fields.

### Proof of Concept
Assume a multi-org Shipit deployment with `secrets.github` containing entries for `attacker-org` (secret `S_a`, known to the attacker) and `victim-org` (tracked in Shipit as `victim-org/victim-repo`, with a live `Stack`).

1. Attacker crafts payload:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
2. Attacker computes `X-Hub-Signature: sha1=HMAC_SHA1(S_a, body)` using their own known secret `S_a`.
3. POST to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` computes `repository_owner == "attacker-org"`, fetches `attacker-org`'s config/secret, and the signature validates successfully.
5. `PushHandler` resolves `repository_name` from `repository.full_name == "victim-org/victim-repo"`, finds the victim's `Stack`, and calls `stack.sync_github(expected_head_sha: "deadbeef...")`, mutating state for a repository the attacker never authenticated for. [8](#0-7) [5](#0-4) [9](#0-8)

  module Webhooks
    module Handlers
      class PushHandler < Handler

          requires :ref
          requires :after

        end

        end
      end
