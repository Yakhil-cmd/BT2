### Title
Hookify rule loading binds to process CWD instead of the tool's actual target repo, enabling cross-repo rule application - (File: plugins/hookify/core/config_loader.py)

### Finding Description
`load_rules()` locates rule files with a **relative** glob pattern, `os.path.join('.claude', 'hookify.*.local.md')`, and calls `glob.glob(pattern)` with no `root_dir` argument and no reference to the actual repo/path being operated on [1](#0-0) . This means the set of rules loaded is entirely determined by `os.getcwd()` at the moment `pretooluse.py`'s `main()` runs, not by the target of the tool call.

`main()` in `plugins/hookify/hooks/pretooluse.py` calls `load_rules(event=event)` with no path argument at all [2](#0-1) , and the resulting rules are evaluated against `input_data` via `RuleEngine.evaluate_rules()` [3](#0-2) . Nowhere in `RuleEngine._rule_matches`/`_check_condition`/`_extract_field` is there any check that the rule file's directory corresponds to the `file_path` in `tool_input` (for `Edit`/`Write`/`MultiEdit`) or to the working directory implied by a `Bash` command [4](#0-3) . There is also no use of any session/workspace-scoped variable such as `CLAUDE_PROJECT_DIR` anywhere in the hookify plugin to anchor rule loading to the actual target repo — the only environment variable consulted is `CLAUDE_PLUGIN_ROOT`, which only affects `sys.path`, not rule discovery [5](#0-4) .

Consequently, if the hook process's CWD does not match the repo that the current tool call actually targets (e.g., the harness/orchestrator runs hooks from a fixed working directory shared across checked-out repos, or a stale session's CWD points at a leftover directory), `load_rules()` will silently pick up `.claude/hookify.*.local.md` files from whatever repo happens to occupy that CWD — not the repo containing the file/command actually being acted upon. An attacker who controls the content of a repo that could be checked out or left as CWD alongside a victim's target repo can plant a `.claude/hookify.*.local.md` that defines permissive event/pattern matching (e.g., an "all" event, "action: warn" only, or a `tool_matcher: '*'` with a condition unlikely to match, or an unenabled/misleading blocking rule) to have their attacker-authored rules — or lack of the victim's rules — silently take effect for the victim's actual tool call.

### Impact Explanation
This breaks the invariant that policy/hook enforcement state should be bound to the actual target repo/session rather than incidental process CWD. Concretely: (1) a victim's legitimate blocking/warning rules meant to protect repo B can be silently bypassed because `load_rules()` instead reads repo A's `.claude/hookify.*.local.md` (or none at all) when CWD is mismatched; (2) conversely, an attacker-crafted rule set from an unrelated repo can be injected into enforcement for a completely different tool call, causing wrong-target enforcement (e.g., spurious `systemMessage`/block responses, or crafted `action: warn`-only rules replacing what should be `block` rules for dangerous commands). This is a workspace/session-binding bypass matching the impact category of "approval/enforcement bypass via trust-boundary violation," though the plugin's own comments note it fails open (`sys.exit(0)` after any error) so the more severe outcome is silent bypass of intended enforcement rather than arbitrary command execution.

### Likelihood Explanation
Exploitability depends entirely on how the harness invokes `pretooluse.py`'s CWD relative to the tool call's actual target path. Per the plugin's own design, `.claude/hookify.*.local.md` are meant to be repo-local config files, and `glob.glob` here uses a bare relative path with no defensive `os.path.abspath`/root-binding, and no cross-check against `tool_input.file_path` or the session's intended repo. Any deployment scenario where the hook's CWD can diverge from the repo actually being edited (multi-repo checkouts, monorepo tooling that cd's between subprojects, stale shell sessions) will trigger this deterministically and repeatably — it requires no special privilege beyond being able to commit a `.claude/hookify.*.local.md` file into a repository that ends up co-located with, or as the CWD during, another repo's tool invocation.

### Recommendation
Bind rule discovery to the actual target of the tool call rather than `os.getcwd()`:
- Derive the repo root explicitly (e.g., from `tool_input.file_path`'s containing repo, or from a session-scoped `CLAUDE_PROJECT_DIR`/workspace root passed into the hook), and pass it into `load_rules(event=event, root_dir=<resolved_root>)`.
- Use `glob.glob(pattern, root_dir=resolved_root)` (or `os.path.join(resolved_root, '.claude', 'hookify.*.local.md')`) instead of the bare relative pattern.
- Add a defensive check in `RuleEngine`/`config_loader` that verifies the loaded rule file's directory is an ancestor of (or equal to) the path being acted on before applying that rule, rejecting rules from mismatched roots.

### Proof of Concept
Integration test plan:
1. Create two temp directories `repoA` and `repoB`. In `repoA/.claude/`, add `hookify.test.local.md` with frontmatter `event: file`, `tool_matcher: '*'`, `pattern: ".*"`, `action: warn`, and a distinctive message `"REPO_A_RULE_FIRED"`.
2. Do not add any `.claude/hookify.*.local.md` to `repoB`.
3. `os.chdir(repoA)` to simulate a CWD mismatch, then invoke `pretooluse.py`'s `main()` (or directly call `load_rules(event='file')` followed by `RuleEngine.evaluate_rules`) with `input_data = {"tool_name": "Write", "tool_input": {"file_path": os.path.join(repoB, "target.txt"), "content": "hello"}}`.
4. Assert that the result does **not** contain `"REPO_A_RULE_FIRED"` in `systemMessage` — i.e., repoA's rule must not apply to a tool call whose `file_path` targets repoB.
5. Current behavior: the assertion fails — `load_rules()` returns repoA's rule (because CWD is repoA), and `RuleEngine.evaluate_rules` matches it against the repoB-targeted `tool_input`, producing `systemMessage` containing `"REPO_A_RULE_FIRED"`, demonstrating cross-repo rule application.

```python
    def _rule_matches(self, rule: Rule, input_data: Dict[str, Any]) -> bool:
        """Check if rule matches input data.

        Args:
            rule: Rule to evaluate
            input_data: Hook input data

        Returns:
            True if rule matches, False otherwise
        """
        # Extract tool information
        tool_name = input_data.get('tool_name', '')
        tool_input = input_data.get('tool_input', {})

        # Check tool matcher if specified
        if rule.tool_matcher:
            if not self._matches_tool(rule.tool_matcher, tool_name):
                return False

        # If no conditions, don't match
        # (Rules must have at least one condition to be valid)
        if not rule.conditions:
            return False

        # All conditions must match
        for condition in rule.conditions:
            if not self._check_condition(condition, tool_name, tool_input, input_data):
                return False

        return True
```
