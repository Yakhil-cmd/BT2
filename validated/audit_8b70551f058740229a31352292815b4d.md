### Title
Members of a shared/multi-signature address can unilaterally change their own definition, silently altering the security of a jointly-created wallet - (File: definition.js, wallet_defined_by_addresses.js)

### Summary
Obyte lets multiple parties jointly create a shared address whose spending condition embeds one or more member addresses via the `['address', 'MEMBER_ADDR']` opcode. Unlike the Allo.sol case where a pool admin's authority is a *pointer* into a mutable external state (profile membership) that another actor (the profile owner) can revoke, here a co-signer's authorization slot in the shared address is a *pointer* into that member address's own definition, which the member can unilaterally change at any time via an `address_definition_change` message. The parent (shared) definition is evaluated against the member's **current** definition at spend time, not the definition that existed when the shared wallet was created and other parties contributed funds to it.

### Finding Description
When validating a definition, the `'address'` opcode does not use a fixed, agreed-upon sub-definition. It re-reads whatever definition the referenced address currently has (subject only to `last_ball_mci` stability), both during definition-syntax validation and during authentifier evaluation: [1](#0-0) [2](#0-1) 

The member's definition can be changed unilaterally and permanently by that member alone, at any time, via `address_definition_change`, resolved by `readDefinitionChashByAddress`/`readDefinitionByAddress`: [3](#0-2) 

Meanwhile, shared/composite addresses are explicitly built by combining member addresses with `['address', ...]` leaves, and the wallet layer even parses these leaves out of the definition to track cosigners: [4](#0-3) [5](#0-4) 

Because the shared address's chash is computed once at creation time but its effective authorization logic for each `['address', X]` branch is re-derived from X's *live* definition, any member X can later weaken (or otherwise change) their own definition without the consent, knowledge, or any co-signing action from the other members of the shared address. This mirrors the reported Allo.sol pattern: authority over a jointly-owned resource is derived from a relationship (profile membership / member-address definition) that a single other party fully controls and can alter unilaterally, stripping the originally-agreed security/governance of the shared resource without the resource owners' consent.

### Impact Explanation
If a member address participates in an `or`-style branch (or any construct where satisfying that one branch alone is sufficient to authorize spending), that member can retroactively weaken their own definition (e.g., adding a disclosable-secret `hash` branch, or any other permissive `or` clause) to let a third party satisfy that slot. This breaks the multisig assumption the other co-owners relied on when they contributed funds to the shared address, enabling unauthorized spending from jointly-owned funds — a direct fund-loss scenario for the other legitimate co-owners, analogous to the pool creator "losing" governance/funds because of another party's unilateral action.

### Likelihood Explanation
Any address that is a member of a previously-created shared address can trigger this at will simply by posting a normal `address_definition_change` message for itself — no special privilege, no cooperation from other cosigners, and no protocol restriction prevents it. The only requirement is that the member's own definition change be stable before the exploit unit is validated, which is standard, always-reachable behavior.

### Recommendation
When a shared/composite address commits other addresses via `['address', X]`, consider pinning the sub-definition that was disclosed/agreed to at shared-address creation time (or require that any later change to a member's definition be re-approved/re-signed by all other co-owners of the composite address) rather than dynamically resolving to whatever definition X currently has.

### Proof of Concept
1. Members A and B jointly create shared address `S = ['or', [['address', A], ['address', B]]]` intending "either A or B, each individually a single-key address, may spend," expecting this to require A's or B's original private key.
2. Funds are sent to `S`.
3. B posts an `address_definition_change` unit changing B's own definition to `['or', [['sig', B_pubkey], ['hash', {algo:'sha256', hash: H}]]]` and later discloses the preimage of `H` publicly.
4. Any third party who knows the preimage can now satisfy the `['address', B]` branch of `S`'s definition (per `definition.js:774-800`, which re-reads B's current, changed definition) and spend from `S`, even though A never agreed to this weaker condition for B's slot.

		max_mci = MAX_INT32;

	conn.query(
		"SELECT definition_chash FROM address_definition_changes CROSS JOIN units USING(unit) \n\
		WHERE address=? AND is_stable=1 AND sequence='good' AND main_chain_index<=? ORDER BY main_chain_index DESC, level DESC LIMIT 1", 
		[address, max_mci], 
		function(rows){
			var definition_chash = (rows.length > 0) ? rows[0].definition_chash : address;
			handle(definition_chash);
	});
}

// Returns a map of signing_path -> address for every ["address", ...] leaf in the definition
function extractAddressPathsFromDefinition(arrDefinition) {
	var result = {};
	function traverse(arr, path) {
		if (!Array.isArray(arr) || arr.length < 2) return;
		var op = arr[0];
		var args = arr[1];
		switch (op) {
			case 'or':
			case 'and':
				if (Array.isArray(args))
					for (var i = 0; i < args.length; i++)
						traverse(args[i], path + '.' + i);
				break;
			case 'r of set':
				if (args && Array.isArray(args.set))
					for (var i = 0; i < args.set.length; i++)
						traverse(args.set[i], path + '.' + i);
				break;
			case 'weighted and':
				if (args && Array.isArray(args.set))
					for (var i = 0; i < args.set.length; i++)
						traverse(args.set[i].value, path + '.' + i);
				break;
			case 'address':
				result[path] = args;
				break;
			case 'hash':
				result[path] = 'secret';
				break;
			case 'in merkle':
				result[path] = ''; // empty address
				break;
		}
	}
	traverse(arrDefinition, 'r');
	return result;
}
