### Title
`ERC20Transactor` credits the requested transfer amount into XCM holding without verifying the actual token balance moved, breaking on fee-on-transfer/rebasing ERC20 contracts - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` invoke an arbitrary, user-deployable ERC20 contract's `transfer` function and, on a bare `true` boolean return value, unconditionally credit/debit the **requested** `amount` into the XCM `AssetsInHolding` register — never checking the actual `balanceOf` delta of the source/destination accounts. Any ERC20 contract that charges a transfer fee, rebases, or otherwise moves less than the requested `value` (i.e. classic "fee-on-transfer" semantics) will cause the XCM holding accounting to diverge from the real on-chain balance of the shared `TransfersCheckingAccount`, exactly mirroring the audited `DonationVotingMerkleDistributionVaultStrategy` bug class (crediting `amount` from `transferFrom`'s parameter instead of the observed balance change).

### Finding Description
`withdraw_asset_with_surplus` builds an `IERC20::transferCall{ to: checking_address, value: amount }`, executes it via `pallet_revive::Pallet::<T>::bare_call`, and — as soon as the ABI-decoded return value is `true` — creates `AssetsInHolding::new_from_fungible_credit(what.id.clone(), Box::new(Erc20Credit(amount)))`, i.e. it trusts `amount` (the requested value) as the amount actually received by the checking account: [1](#0-0) 

Symmetrically, `deposit_asset_with_surplus` sends `IERC20::transferCall{ to: beneficiary, value: amount }` from the checking account and reports success purely from the boolean return value, again never confirming that the beneficiary's balance grew by `amount`: [2](#0-1) 

The `Erc20Credit` type used to represent this XCM holding is explicitly documented as *not* runtime-enforced: [3](#0-2) 

The asset matcher (`ERC20Matcher` / `IsLocalAccountKey20`) accepts **any** contract address encoded as an `AccountKey20` junction with no allow-list — i.e. any locally deployed pallet-revive contract implementing the `IERC20` selector for `transfer` qualifies as a valid XCM fungible asset: [4](#0-3) 

This transactor is wired into a real, currently-tested runtime configuration (asset-hub-westend), and is reachable through the permissionless, signed `pallet_xcm::execute` extrinsic, as exercised by the existing test `withdraw_and_deposit_erc20s`: [5](#0-4) 

Root cause parallel to the report: just like `DonationVotingMerkleDistributionVaultStrategy` records `claims[recipientId][token] += amount` from the `permitTransferFrom` request parameters instead of the actual received balance, `ERC20Transactor` records the *requested* `value` into `Erc20Credit`/`AssetsInHolding` instead of measuring the actual `balanceOf` delta of the checking account (or beneficiary) before/after the `transfer` call. Any ERC20 contract implementing a transfer fee, burn-on-transfer, or reflection/rebase mechanism — which is fully attacker-controllable since the attacker deploys the contract themselves via ordinary contract-deployment calls, then references it from an ordinary signed XCM `execute` — breaks this invariant.

### Impact Explanation
Concretely, for a fee-on-transfer ERC20 token contract `C` deployed by any user:
1. User executes `withdraw_asset` for `C` with amount `A`. The real ERC20 `transfer` call moves `A - fee` into the shared `TransfersCheckingAccount`, but `true` is returned (fee-on-transfer contracts still return `true`), so the executor credits `A` (not `A - fee`) into the XCM holding register.
2. A subsequent `deposit_asset` instruction in the same program (or a later `claim_assets` after the asset gets trapped) attempts to move the full credited `A` out of the checking account to a beneficiary. The checking account's real `C`-token balance is only `A - fee` (potentially further eroded by other in-flight XCM programs sharing the same checking account for the same contract), so the `transfer` call for `A` reverts or returns `false`.
3. This either fails the whole XCM program (with the withdrawn tokens now stuck inside the shared checking account, already debited from the user, unrecoverable through this transactor since any future deposit/claim attempt for the recorded `A` will again fail) or, in `AssetsTrapped`-based claim flows, permanently locks the trapped credit since the asset is systematically over-recorded relative to what the checking account actually holds.

This is a genuine loss/freezing of user funds triggered without any privileged role — the "malicious" precondition is simply that the attacker (or ordinary user) uses a common ERC20 pattern (fee-on-transfer / reflection token), which is entirely within an ordinary, permissionless contract deployment and XCM `execute` call. It maps to Medium severity in the audited report's class: it is not unbacked issuance or unauthorized dispatch, but a deterministic accounting break leading to fund freezing for a specific (attacker-controllable) token category, consistent with the classification of the original finding.

### Likelihood Explanation
Likelihood is high whenever any fee-on-transfer, deflationary, or rebasing ERC20 contract is used through this transactor: no governance action, no validator collusion, and no privileged origin is required — only a signed account deploying an ordinary Solidity/PVM contract and issuing a normal `pallet_xcm::execute` extrinsic with `withdraw_asset`/`deposit_asset` referencing that contract's `AccountKey20` location, exactly as demonstrated by the existing `withdraw_and_deposit_erc20s` test pattern.

### Recommendation
Do not trust the requested `amount` or the boolean return value alone. Before crediting `Erc20Credit(amount)` in `withdraw_asset_with_surplus`, read the checking account's `balanceOf` before and after the `transfer` call (or use `balanceOf` deltas) and credit the actual observed delta. Symmetrically, in `deposit_asset_with_surplus`, verify the beneficiary's/checking account's balance delta matches `amount` before reporting success, and propagate any shortfall back into the holding register (or fail the deposit while returning the un-deposited excess) rather than assuming exact-amount semantics for arbitrary ERC20 contracts.

### Proof of Concept
No executable PoC was run; a live Rust/FRAME integration reproduction (extending the existing `withdraw_and_deposit_erc20s` / `smart_contract_does_not_return_bool_fails` tests in `cumulus/parachains/runtimes/assets/asset-hub-westend/tests/tests.rs`) would need to:
1. Deploy a minimal fee-on-transfer ERC20 fixture (e.g. a variant of `MyToken` that deducts, say, 10% on every `transfer` while still returning `true`).
2. Execute an XCM program via `PolkadotXcm::execute` that `withdraw_asset`s this token then `deposit_asset`s it to a beneficiary in the same program, and assert that (a) the checking account's real `balanceOf` after withdraw is less than the credited XCM holding amount, and (b) the subsequent deposit step fails or the trapped/claimed amount can never be fully redeemed.
This was not executed in this session — deployment/compilation of a custom PVM fixture and running the emulated Asset Hub test harness requires the actual sandbox, which is outside the scope of this read-only analysis. The wiring (permissionless deployment, unrestricted `AccountKey20` matcher, existing test harness reaching the exact code paths cited above) is confirmed directly from source, but the balance-delta divergence itself is inferred from the code logic rather than an executed run.

/// A minimal imbalance tracking type that holds an ERC20 token amount.
///
/// This type implements the necessary imbalance accounting traits but does not perform
/// runtime-level balance enforcement. It's used to track ERC20 token amounts within XCM
/// asset holdings, where the actual balance constraints are enforced by the ERC20 smart
/// contract itself rather than the runtime.
struct Erc20Credit(u128);
impl UnsafeConstructorDestructor<u128> for Erc20Credit {
	fn unsafe_clone(&self) -> Box<dyn ImbalanceAccounting<u128>> {
		Box::new(Erc20Credit(self.0))
	}
	fn forget_imbalance(&mut self) -> u128 {
		let amount = self.0;
		self.0 = 0;
		amount
	}
}

impl UnsafeManualAccounting<u128> for Erc20Credit {
	fn saturating_subsume(&mut self, mut other: Box<dyn ImbalanceAccounting<u128>>) {
		let amount = other.forget_imbalance();
		self.0 = self.0.saturating_add(amount);
	}
}

impl ImbalanceAccounting<u128> for Erc20Credit {
	fn amount(&self) -> u128 {
		self.0
	}
	fn saturating_take(&mut self, amount: u128) -> Box<dyn ImbalanceAccounting<u128>> {
		let new = self.0.min(amount);
		self.0 = self.0 - new;
		Box::new(Erc20Credit(new))
	}
}

/// `Contains<Location>` implementation that matches locations with no parents,
/// a `PalletInstance` and an `AccountKey20` junction.
pub struct IsLocalAccountKey20;
impl Contains<Location> for IsLocalAccountKey20 {
	fn contains(location: &Location) -> bool {
		matches!(location.unpack(), (0, [AccountKey20 { .. }]))
	}
}

/// Fallible converter from a location to a `H160` that matches any location ending with
/// an `AccountKey20` junction.
pub struct AccountKey20ToH160;
impl MaybeEquivalence<Location, H160> for AccountKey20ToH160 {
	fn convert(location: &Location) -> Option<H160> {
		match location.unpack() {
			(0, [AccountKey20 { key, .. }]) => Some((*key).into()),
			_ => None,
		}
	}

	fn convert_back(key: &H160) -> Option<Location> {
		Some(Location::new(0, [AccountKey20 { key: (*key).into(), network: None }]))
	}
}

/// [`xcm_executor::traits::MatchesFungibles`] implementation that matches
/// ERC20 tokens.
pub type ERC20Matcher =
	MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>;

#[test]
fn withdraw_and_deposit_erc20s() {
	let sender: AccountId = ALICE.into();
	let beneficiary: AccountId = BOB.into();
	let revive_account = pallet_revive::Pallet::<Runtime>::account_id();
	let checking_account =
		asset_hub_westend_runtime::xcm_config::ERC20TransfersCheckingAccount::get();
	let initial_wnd_amount = 100_000_000_000_000_000u128;
	sp_tracing::init_for_tests();

	ExtBuilder::<Runtime>::default().build().execute_with(|| {
		// Bring the revive account to life.
		assert_ok!(Balances::mint_into(&revive_account, initial_wnd_amount));
		// Fund all accounts involved.
		assert_ok!(Balances::mint_into(&sender, initial_wnd_amount));
		assert_ok!(Balances::mint_into(&beneficiary, initial_wnd_amount));
		assert_ok!(Balances::mint_into(&checking_account, initial_wnd_amount));

		let code = compile_module_with_type("MyToken", FixtureType::Resolc)
			.expect("compile ERC20")
			.0;

		let initial_amount_u256 = U256::from(1_000_000_000_000u128);
		let constructor_data = sol_data::Uint::<256>::abi_encode(&initial_amount_u256);
		let Contract { addr: erc20_address, .. } = bare_instantiate(&sender, code)
			.transaction_limits(TransactionLimits::WeightAndDeposit {
				weight_limit: Weight::from_parts(500_000_000_000, 10 * 1024 * 1024),
				deposit_limit: Balance::MAX,
			})
			.data(constructor_data)
			.build_and_unwrap_contract();

		let sender_balance_before = <Balances as fungible::Inspect<_>>::balance(&sender);

		let erc20_transfer_amount = 100u128;
		let wnd_amount_for_fees = 10_000_000_000_000u128;
		// Actual XCM to execute locally.
		let message = Xcm::<RuntimeCall>::builder()
			.withdraw_asset((Parent, wnd_amount_for_fees))
			.pay_fees((Parent, wnd_amount_for_fees))
			.withdraw_asset((
				AccountKey20 { key: erc20_address.into(), network: None },
				erc20_transfer_amount,
			))
			.deposit_asset(AllCounted(1), beneficiary.clone())
			.refund_surplus()
			.deposit_asset(AllCounted(1), sender.clone())
			.build();
		assert_ok!(PolkadotXcm::execute(
			RuntimeOrigin::signed(sender.clone()),
			Box::new(VersionedXcm::V5(message)),
			Weight::from_parts(600_000_000_000, 15 * 1024 * 1024),
		));

		// Revive is not taking any fees.
		let sender_balance_after = <Balances as fungible::Inspect<_>>::balance(&sender);
		// Balance after is larger than the difference between balance before and transferred
		// amount because of the refund.
		assert!(sender_balance_after > sender_balance_before - wnd_amount_for_fees);

		// Beneficiary receives the ERC20.
		let beneficiary_amount =
			<Revive as fungibles::Inspect<_>>::balance(erc20_address, &beneficiary);
		assert_eq!(beneficiary_amount, erc20_transfer_amount);
	});
}
