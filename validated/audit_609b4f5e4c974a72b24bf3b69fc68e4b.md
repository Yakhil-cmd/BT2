### Title
Cross-repository commit status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler`'s `ExplicitParameters` schema (status_handler.rb:7-18) never declares a `repository` field, so `params.respond_to?(:repository)` is `false` even though `payload['repository']` is present on every GitHub status webhook. `process` (status_handler.rb:20-24) consequently looks up commits solely by `Commit.where(sha: params.sha)`, with no scoping to the repository that actually sent the webhook, and mutates every matching `Commit` row across the entire database via `create_status_from_github!`.

### Finding Description
Broken binding: `payload['repository']['full_name'] == stack_for(matched_commit).repository.full_name` is **not** enforced anywhere in this path, while the code implicitly assumes it.

Path: `WebhooksController#create` → `GithubHook#process` → `Handler.call(payload)` → `Handler#initialize` (handler.rb:21-24) sets `@payload = payload` and computes `@params = self.class.param_parser.parse!(payload)`, which strips the payload to only the declared schema fields (`sha`, `state`, `description`, `target_url`, `context`, `created_at`, `branches`). `StatusHandler#process` (status_handler.rb:20-24) then does:

```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```

This query is **global**: it is not scoped by `stack_id`, `repository_id`, or anything derived from `payload['repository']`. `Handler` does define a `stacks`/`repository_name` helper (handler.rb:32-38) that other handlers (e.g. `push_handler.rb`) use to scope work to the reporting repository, but `StatusHandler` never calls it and never reads `payload` at all — confirmed by `attr_reader :params, :payload` (handler.rb:19) being exposed but unused in `StatusHandler`.

Root cause: the repository binding is discarded twice — once structurally (the schema never captures it) and once behaviorally (even if it were captured, `process` doesn't use it to filter the `Commit` lookup).

Exploit precondition: two different Shipit-tracked stacks/repositories must have at least one `Commit` row with an identical `sha`. This is not a hash-collision requirement — it occurs naturally whenever one tracked repository is a fork of (or shares history with) another tracked repository, since Git SHA-1s are identical for unmodified shared commits. An attacker who owns/controls a fork that shares commit history with an upstream tracked repository, and for which GitHub delivers status webhooks to the Shipit installation (e.g., org-wide webhook/App configuration covering forks), can set or trigger a commit status on their own fork's commit. GitHub relays a signed, legitimate status webhook naming the fork as `repository`, but because `params` drops that field and `process` never checks it, Shipit updates the `Commit` record — and its computed `status`/`blocked?`/`deployable?` state, `schedule_continuous_delivery`, and `Hook.emit(:deployable_status, ...)` — belonging to the **upstream** repository's stack, not the fork's.

Existing guards do not stop this: `verify_signature`/`GitHubApp#verify_webhook_signature` only authenticate that the payload came from GitHub for whatever repository triggered it — they say nothing about whether that repository is allowed to mutate a *different* stack's commit rows. `drop_unhandled_event` and the `ExplicitParameters` schema do not perform any repository/stack authorization check for `StatusHandler`.

### Impact Explanation
An attacker who controls a forked/duplicated repository (sharing SHAs with a tracked upstream repository) can cause commit-status writes (`Status` records) and downstream side effects (`deployable?`/`blocked?` recomputation, `stack.schedule_merges`, `ContinuousDeliveryJob` scheduling, `Hook.emit(:deployable_status, ...)`) to be applied against the **upstream** repository's `Stack`/`Commit`, which they do not own or authenticate for. This is a payload for one repository mutating another repository's stack/commit state, matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team"). It is repeatable for every shared-SHA commit and could be used to force a false "success" status on an upstream commit, potentially unblocking/triggering continuous deployment (`schedule_continuous_delivery`) for a commit the attacker does not control merge rights over.

### Likelihood Explanation
Exploitability depends on: (1) Shipit's GitHub App/webhook configuration delivering status events for the attacker's fork to the Shipit host (org-wide webhook or App installed broadly), and (2) the existence of a shared-SHA commit between the attacker's fork and a tracked upstream stack, which is common for forks that haven't diverged on the shared history. No Shipit secrets, session, or maintainer role is needed — signature verification is satisfied naturally because the webhook is genuinely sent by GitHub for the attacker's own repository. Attacker cost is low (fork + set a status), and the action is trivially repeatable against any shared commit.

### Recommendation
Add `repository` (full name) to the `StatusHandler` `ExplicitParameters` schema, and scope the `Commit` lookup to the stack(s) belonging to that repository (reusing `Handler#stacks`/`repository_name`), e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, rejecting/ignoring matches whose commit's `stack.repository.full_name` does not equal `payload['repository']['full_name']`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "StatusHandler does not scope repository, allowing cross-repo status writes" do
  upstream_stack = shipit_stacks(:shipit)          # repository "example/upstream"
  fork_stack     = shipit_stacks(:cyclid)          # different repository, e.g. "attacker/fork"

  shared_sha = 'a' * 40
  upstream_commit = upstream_stack.commits.create!(sha: shared_sha, message: 'shared commit')
  fork_stack.commits.create!(sha: shared_sha, message: 'shared commit')

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'ci/test',
    'repository' => { 'full_name' => 'attacker/fork' } # attacker's own, legitimately-signed repo
  }

  instance = Shipit::Webhooks::Handlers::StatusHandler.new(payload)

  # Binding proof: repository field is present in payload but dropped from params
  refute instance.params.respond_to?(:repository)
  assert_equal 'attacker/fork', instance.payload.dig('repository', 'full_name')

  instance.process

  upstream_commit.reload
  # Mutation happened on a commit belonging to a different repository than the one that sent the webhook
  assert_equal 'success', upstream_commit.status.state
  refute_equal 'attacker/fork', upstream_commit.stack.repository.full_name
end
```
