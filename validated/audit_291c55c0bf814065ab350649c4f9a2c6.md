### Title
Webhook signature verification is keyed on `repository.owner.login`, but handlers act on `repository.full_name` — an org with no `webhook_secret` lets an attacker forge PR events against any repository - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects which `GitHubApp` (and thus which `webhook_secret`) to check the HMAC against solely from `params.dig('repository','owner','login')` (or `organization.login`) taken from the attacker-controlled JSON body. `GitHubApp#verify_webhook_signature` returns `true` unconditionally when that org's configured `webhook_secret` is blank. Because the org used for authentication and the repository actually mutated by the PR handlers are two independent fields of the same forged payload, an attacker can pick a Shipit-configured org with no secret purely to pass verification, while pointing `repository.full_name` (and the rest of the PR payload) at a victim repository/stack in a completely different organization.

### Finding Description
The broken binding, stated as an equality that must hold but does not:

`organization_whose_secret_verified_signature == organization_that_owns_the_repository_mutated_by_the_handler`

Trace:
1. `WebhooksController#verify_signature` computes `repository_owner` purely from the untrusted body: [1](#0-0) 
2. It fetches the `GitHubApp` for that org and calls `verify_webhook_signature`: [2](#0-1) 
3. `GitHubApp#verify_webhook_signature` short-circuits to `true` whenever the org's config has no `webhook_secret`: [3](#0-2) 
4. Once verification passes, `create` dispatches the *entire raw JSON body* — unrelated to which field was used for verification — to every registered `pull_request` handler: [4](#0-3) [5](#0-4) 

The handlers (`Handlers::PullRequest::*`, e.g. `opened_handler.rb`, `closed_handler.rb`, `review_stack_adapter.rb`) resolve the target `Repository`/`Stack` from `repository.full_name` (or equivalent nested fields) inside the same payload — a value the attacker is free to set independently of `repository.owner.login`. Nothing in `verify_signature` cross-checks that `repository.full_name`'s owner matches `repository_owner`, nor does anything re-derive `repository_owner` from `full_name`.

Exploit flow: attacker configures/knows of a Shipit org (`org-without-secret`) that is registered in `Shipit.github` config but has no `webhook_secret` set. They POST to `/webhooks` with header `X-Github-Event: pull_request`, body:
```json
{
  "action": "synchronize",
  "repository": { "owner": { "login": "org-without-secret" }, "full_name": "victim-org/victim-repo", ... },
  "pull_request": { ... }
}
```
`verify_signature` looks up `org-without-secret`'s `GitHubApp`, finds `webhook_secret` blank, and returns `true` regardless of the (missing/garbage) `X-Hub-Signature` header. The payload is then handed to the PR handlers, which locate and mutate `victim-org/victim-repo`'s review stack/PR records using attacker-supplied data — despite `victim-org` never having authenticated this request and possibly having its own, unused `webhook_secret`.

Existing guards do not catch this: `drop_unhandled_event` only checks the event name is registered, not the payload's internal consistency; `verify_signature` never validates that the org used for HMAC lookup matches the org that owns the acted-upon repository; there is no `ExplicitParameters` schema binding `repository.owner.login` to `repository.full_name`'s owner segment.

### Impact Explanation
An attacker can inject fabricated `pull_request` events (`opened`, `closed`, `reopened`, `edited`, `assigned`, `labeled`, `unlabeled`, `synchronize`) that write/update PR and review-stack state for a repository they do not own and never authenticated for, as long as some other Shipit-configured org lacks a `webhook_secret`. This is cross-tenant state manipulation: one repository's/organization's forged payload mutates another organization's stack/PR records, matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team"). The attack is fully repeatable against any repository/stack known to Shipit, requiring no session, token, or secret.

### Likelihood Explanation
Preconditions: at least one organization configured in Shipit's GitHub app settings without a `webhook_secret` (a configuration state the code explicitly tolerates via the `return true unless webhook_secret` fallback in `GitHubApp#verify_webhook_signature`) and a webhook route reachable at `/webhooks` (unauthenticated, standard mounting). Attacker cost is a single crafted HTTP POST with correct headers, no cryptographic material needed, and it is trivially repeatable/scriptable against arbitrary target repositories.

### Recommendation
Bind the signature-verification organization to the actual target repository used by the handlers: derive `repository_owner` from the same field the handlers use to resolve the `Repository`/`Stack` (e.g., parse it from `repository.full_name`'s owner segment) and require it to match `repository.owner.login`/`organization.login`, rejecting the request (422) on mismatch. Additionally, disallow bypassing verification entirely for orgs with a blank `webhook_secret`, or require an explicit "verification not required" opt-in rather than silently treating a blank secret as "always verified."

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`, no live GitHub):
1. Configure two orgs in `Shipit.github_configuration`/test secrets: `org-no-secret` (no `webhook_secret`) and `victim-org` (has a `webhook_secret`, or none needed since it's just the target).
2. Create a `Shipit::Stack`/`Repository` under `victim-org/victim-repo` with a known PR/review-stack state (e.g., no existing merge/PR record).
3. POST to `/webhooks` with `X-Github-Event: pull_request`, an arbitrary/blank `X-Hub-Signature`, and JSON body: `{"action":"synchronize","repository":{"owner":{"login":"org-no-secret"},"full_name":"victim-org/victim-repo"},"pull_request":{...targeting the victim PR...}}`.
4. Assert response is `200 OK` (not `422`), proving signature check passed via the no-secret org.
5. Assert that `victim-org/victim-repo`'s `PullRequest`/review-stack record was created/updated as a side effect (e.g., `Shipit::PullRequest.find_by(...)` reflects the forged `synchronize` payload), proving `organization_whose_secret_verified_signature ("org-no-secret") != organization_that_owns_mutated_repository ("victim-org")`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
