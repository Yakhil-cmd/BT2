### Title
Validator session-key hijack via unauthenticated `stash` parameter in `set_keys_from_ah` reachable by any AssetHub Westend account through crafted `pallet_xcm::send` Transact - ([File: substrate/frame/staking-async/ah-client/src/lib.rs])

### Summary
`pallet_staking_async_ah_client::Pallet::set_keys_from_ah` on the Relay Chain trusts a caller-supplied `stash: T::AccountId` parameter and installs it as a validator's new session keys, gating access only on `T::AssetHubOrigin::ensure_origin_or_root`, i.e. on the message having arrived from the AssetHub *parachain* as a whole. It never checks that the `stash` identity matches the specific AssetHub account that actually authored the request. This mirrors the Laci Synchroni flaw exactly: a chain-level "authentication" (the message really came from AssetHub) is conflated with account-level "authorization" (that this particular AssetHub user is entitled to control this particular `stash`).

### Finding Description
On the AssetHub side, the safe path is `pallet_staking_async_rc_client::Pallet::set_keys`: [1](#0-0) 
Here `stash = ensure_signed(origin)` is bound directly to the signer, `is_validator(&stash)` is checked, and the session-key ownership proof is verified against that same `stash`. Only after these checks does it forward `KeysMessage::SetKeys { stash, keys }` to the Relay Chain via XCM.

On the Relay Chain, the receiving extrinsic is: [2](#0-1) 
It only checks `T::AssetHubOrigin::ensure_origin_or_root(origin)`, defined in the Westend runtime as: [3](#0-2) 
i.e. it accepts *any* XCM whose resolved origin is `parachains_origin::Origin::Parachain(ASSET_HUB_ID)` — it has no way to know, and does not attempt to verify, which specific AssetHub account produced the message or whether that account is entitled to control `stash`.

The critical gap is that `rc_client::set_keys` is not the only way to reach `set_keys_from_ah`. AssetHub Westend's `pallet_xcm::Config` permits any signed account to call `pallet_xcm::send`: [4](#0-3) 
with `LocalOriginToLocation = (GeneralAdminToPlurality, SignedToAccountId32<...>)` — any signed user origin is accepted for `send`, and the message payload (an arbitrary `Xcm<()>` program, including a `Transact`) is fully attacker-controlled; `pallet_xcm::send` does not filter instruction content (that filtering, `XcmExecuteFilter`, only applies to local `execute`, not to `send`).

On the Relay Chain (Westend), the `OriginConverter` includes: [5](#0-4) 
`ChildParachainAsNative<parachains_origin::Origin, RuntimeOrigin>` converts a `Transact { origin_kind: OriginKind::Native, .. }` instruction, when the message's XCM origin register is a child-parachain location (guaranteed to be `Parachain(ASSET_HUB_ID)` by UMP transport/consensus, not by any internal AssetHub signer check), directly into `parachains_origin::Origin::Parachain(ASSET_HUB_ID)` — exactly what `EnsureAssetHub` accepts.

Because AssetHub is a system parachain, the Relay's Barrier explicitly allows *unpaid* execution for messages whose computed origin is a system parachain: [6](#0-5) 
(`AllowExplicitUnpaidExecutionFrom<(IsChildSystemParachain<ParaId>, Fellows)>`), so the attacker does not even need to fund fee payment for the crafted message to execute.

Putting this together: any signed AssetHub Westend account can call `pallet_xcm::send(dest: Location::parent(), message: Xcm([UnpaidExecution{..}, Transact{ origin_kind: OriginKind::Native, call: AhClient::set_keys_from_ah{ stash: <any validator>, keys: <attacker keys> } }]))`. The Relay Chain will accept it as coming from "AssetHub" (true) and dispatch `set_keys_from_ah` with a completely attacker-chosen `stash` and attacker-chosen `keys`, entirely bypassing AssetHub's `rc_client::set_keys` ownership-proof and signer-binding logic.

### Impact Explanation
This allows any unprivileged AssetHub account to overwrite the Relay Chain session keys of an arbitrary validator's `stash`, without ever proving ownership of that stash or possessing a valid session-key ownership proof. Consequences include: hijacking block-authoring/consensus-voting capability associated with a victim validator identity in the following session, disrupting or corrupting relay-chain consensus, and potentially causing the legitimate validator to be slashed for equivocation once the attacker's node starts producing conflicting blocks/votes under the victim's identity. This is a critical integrity break of the staking-async AH↔RC session-key bridging mechanism introduced in `pr_10666` (`staking-async: allow session keys handling on AssetHub`), unauthorized dispatch with validator-identity-takeover consequences.

### Likelihood Explanation
The prerequisite capability (a signed AssetHub account able to call `pallet_xcm::send` with an arbitrary destination/message) is a standard, unprivileged capability granted to every AssetHub Westend user by the existing `SendXcmOrigin` configuration — no governance, no stolen keys, no malicious collator/relayer is required. The attacker only needs to know a target validator's `stash` AccountId (public information) and craft the Transact call data, both trivial. The main uncertainty is confirming the precise argument/decoding format expected by `set_keys_from_ah`'s `keys: Vec<u8>` (which must decode via `T::SessionInterface::Keys` — if decoding fails the call silently returns `Ok(())` with a warning event rather than reverting, so the attacker must supply correctly encoded keys, which is straightforward since key formats are public).

### Recommendation
`set_keys_from_ah`/`purge_keys_from_ah` should not accept an arbitrary `stash` parameter authorized merely by "message came from AssetHub the parachain." Either (a) require the XCM origin to be authenticated down to the specific requesting account (e.g., via `DescendOrigin`/account-level origin conversion so the Relay Chain origin is bound to the actual AssetHub signer, and then check that resolved account equals `stash`), or (b) re-validate the session-key ownership proof on the Relay Chain side instead of trusting AssetHub's prior validation, or (c) restrict which XCM origin kinds/messages are permitted to reach this call (e.g. reject top-level `Transact` from the bare parachain origin for this specific call, only accepting it through a dedicated, non-forgeable channel such as a `DescendOrigin`-scoped sub-account or a governance-only send path).

### Proof of Concept
A full runtime PoC was not executed against a live network per program rules; this analysis is based on static tracing of the actual production configuration:
- AssetHub Westend `SendXcmOrigin` allowing any signed account to call `pallet_xcm::send`: [4](#0-3) 
- Westend Relay `OriginConverter` mapping a `Transact{origin_kind: Native}` from a child-parachain-origin message to `parachains_origin::Origin::Parachain(id)`: [5](#0-4) 
- Westend Relay Barrier allowing unpaid execution from system parachains (AssetHub qualifies): [6](#0-5) 
- `EnsureAssetHub`/`AssetHubOrigin` accepting exactly that resolved origin: [3](#0-2) 
- Vulnerable handler trusting the `stash` parameter with no signer binding: [2](#0-1) 

An integration test recreating this exact chain (AssetHubWestend user → `pallet_xcm::send` → BridgeHub/Relay `Transact`) already exists in the repo for a related origin-forgery scenario and demonstrates the same class of trust bypass through `InitiateTransfer`/`Transact` with `preserve_origin`: [7](#0-6)  — confirming the emulated test harness needed to reproduce this against the relay's `ah-client` pallet is readily available; constructing the equivalent `Transact` targeting `AhClient::set_keys_from_ah` was not executed here and should be validated with a background Devin session using the existing `substrate/frame/staking-async/integration-tests` emulated harness before formal disclosure. I could not directly inspect `pallet_xcm::send`'s exact source (`polkadot/xcm/pallet-xcm/src/lib.rs`) due to indexing limits reached in the final iteration, so the claim that `send` performs no content filtering of the supplied `Xcm<()>` program is based on well-established XCM design (content filtering via `XcmExecuteFilter` applies only to local `execute`, not `send`) rather than a direct line citation — this specific detail should be re-verified by a Devin session with full repository access before treating this finding as bounty-ready.

		pub fn set_keys(
			origin: OriginFor<T>,
			keys: Vec<u8>,
			proof: Vec<u8>,
			max_delivery_and_remote_execution_fee: Option<BalanceOf<T>>,
		) -> DispatchResult {
			let stash = ensure_signed(origin)?;

			// Only registered validators can set session keys
			ensure!(T::AHStakingInterface::is_validator(&stash), Error::<T>::NotValidator);

			// Hold deposit for key storage.
			let deposit = T::KeyDeposit::get();
			if !deposit.is_zero() {
				let current_hold = T::Currency::balance_on_hold(&HoldReason::Keys.into(), &stash);
				if current_hold < deposit {
					// Top up if current hold is below the required deposit.
					T::Currency::set_on_hold(&HoldReason::Keys.into(), &stash, deposit)?;
				}
			}

			// Validate keys: decode as RelayChainSessionKeys to ensure correct format
			let session_keys = T::RelayChainSessionKeys::decode(&mut &keys[..])
				.map_err(|_| Error::<T>::InvalidKeys)?;

			// Validate ownership proof
			ensure!(
				session_keys.ownership_proof_is_valid(&stash.encode(), &proof),
				Error::<T>::InvalidProof
			);

		pub fn set_keys_from_ah(
			origin: OriginFor<T>,
			stash: T::AccountId,
			keys: Vec<u8>,
		) -> DispatchResult {
			T::AssetHubOrigin::ensure_origin_or_root(origin)?;
			log::info!(target: LOG_TARGET, "Received set_keys request from AssetHub for {stash:?}");

			// Decode the keys from bytes (AH already validated, this is just for type conversion)
			let session_keys =
				match <<T as Config>::SessionInterface as SessionInterface>::Keys::decode(
					&mut &keys[..],
				) {
					Ok(keys) => keys,
					Err(e) => {
						// This should never happen since AH validates keys before forwarding.
						// Returning Ok() allows the event to be observed for monitoring.
						log!(
							warn,
							"InvalidKeysFromAssetHub: failed to decode keys for {:?}: {:?}",
							stash,
							e
						);
						Self::deposit_event(Event::Unexpected(
							UnexpectedKind::InvalidKeysFromAssetHub,
						));
						return Ok(());
					},
				};
