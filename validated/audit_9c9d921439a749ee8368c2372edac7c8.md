### Title
Webhook signature verification authenticates the organization named in `repository.owner.login`, not the repository actually acted upon via `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate a webhook using the organization claimed in one payload field (`repository.owner.login`, falling back to `organization.login`), but the actual event handlers act on a *different* field of the same payload — `repository.full_name` — to look up the target `Repository`/`Stack`. Because Shipit supports multiple GitHub organizations configured with independent webhook secrets on a single instance, an attacker who legitimately controls one configured organization's webhook secret can forge a payload that claims to be from their own org (so the signature validates) while pointing `repository.full_name` at a victim organization's repository, causing Shipit to act on the victim's stack.

### Finding Description
`verify_signature` picks the verification secret from the attacker-controlled JSON body itself, before any cryptographic check has occurred: [1](#0-0) 
`repository_owner` is read straight out of unauthenticated request JSON: [2](#0-1) 

`Shipit.github(organization: repository_owner)` returns the `GitHubApp` config (and thus `webhook_secret`) that matches whatever organization string is embedded in the payload; Shipit explicitly supports multiple orgs with distinct secrets on the same install, as shown by the multi-org secrets templates: [3](#0-2) 

Once the HMAC check passes, the handlers dispatched via `Shipit::Webhooks.for_event(event)` locate the *target* repository/stack using a **different** field from the same body — `params.repository.full_name` — with no re-check that its owner matches the organization whose secret validated the signature: [4](#0-3) 

This is structurally identical to the reported bug class: the entity that is authenticated (the organization identified for secret lookup) is never bound to the entity that is actually written to (the repository/stack identified by `full_name`). Since the HMAC covers the raw JSON body as a whole, an attacker cannot forge a *valid* signature for an org whose secret they don't know — but they don't need to: they only need to know the secret of **any one** org configured on the instance (e.g., their own org, which they legitimately administer and for which they can read the webhook secret from their own GitHub App settings). They can then construct a body where `repository.owner.login` (used only for secret selection) says their own org, while `repository.full_name` (used for the actual database lookup) names a victim org's repository, and sign the whole body correctly with their own known secret.

### Impact Explanation
A successful forgery lets an attacker who administers one configured GitHub organization on a shared Shipit instance push fabricated webhook events (`push`, `status`, `pull_request`, `check_suite`, `membership`) that are applied to a *different* organization's stacks/repositories/commits — e.g. triggering `GithubSyncJob` against a victim stack, injecting fake commit statuses that unblock deploy checks, or manipulating pull-request-driven review stacks/merges for a repository they do not own. This is a cross-repository write achieved by breaking the authentication↔target binding, matching the "cross-repository writes" high-impact criterion.

### Likelihood Explanation
Requires the instance to be configured with more than one GitHub organization (a documented, supported configuration — see `secrets_double_github_app.yml`), and requires the attacker to control one of those configured organizations (i.e., know its `webhook_secret`, which any admin of that org's GitHub App can view). No compromise of the victim organization's secret, no Shipit session, and no privileged Shipit account is needed — only administrative access to one's own, separately configured, lower-trust organization.

### Recommendation
After selecting the app config for signature verification, re-verify that the organization embedded in `repository_owner`/`organization.login` matches the owner segment of `repository.full_name` (or any other field the handlers key off of) before dispatching the event to handlers. Reject the webhook if these fields disagree, so the signature genuinely authenticates the entity being acted upon, not just an arbitrary field chosen by the attacker.

### Proof of Concept
1. Attacker administers `AttackerOrg`, which has a GitHub App installed on the shared Shipit instance with known `webhook_secret = S_A`.
2. Attacker crafts a `push` event body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef...",
  "repository": {
    "owner": { "login": "AttackerOrg" },
    "full_name": "VictimOrg/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(S_A, body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "AttackerOrg")`, gets `S_A`, and the HMAC matches — request passes. [5](#0-4) 
5. `PushHandler`/other handlers resolve the target stack from `repository.full_name = "VictimOrg/victim-repo"` and act on it (e.g., enqueue `GithubSyncJob` for the victim's stack) even though the signature only proved knowledge of `AttackerOrg`'s secret.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
