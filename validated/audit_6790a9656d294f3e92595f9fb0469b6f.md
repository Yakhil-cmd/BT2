## Finding

### Title
Global `DERIVABLE_ACCOUNT_ABSTRACTION` feature flag lets `allow_missing_txn_authentication_key` authorize *any* address as a secondary/fee-payer signer with no key binding, letting an unprivileged sender attach an unrelated account's address to a multi-agent transaction using an unauthenticated `NoAccountAuthenticator` slot — ([File: aptos-move/framework/aptos-framework/sources/transaction_validation.move])

### Summary
`multi_agent_common_prologue` accepts a secondary-signer entry whose auth-key hash is `option::none()` as long as `allow_missing_txn_authentication_key(secondary_address)` returns `true`. That helper returns `true` whenever the network-wide feature `DERIVABLE_ACCOUNT_ABSTRACTION` is enabled — **it does not check that `secondary_address` is actually using account abstraction at all**. Combined with the fact that a signer slot can be filled with `AccountAuthenticator::NoAccountAuthenticator` (which serializes to `AuthenticationProof::None`, i.e. `optional_auth_key() == None`) with essentially no cryptographic check tying it to the named address, an unprivileged sender can name any existing account as a secondary signer, supply no signature/key material for it, and still pass the prologue's authentication-key check for that account.

### Finding Description
- `allow_missing_txn_authentication_key` is defined as: [1](#0-0) 
  It returns `true` if `features::is_derivable_account_abstraction_enabled()` — a **global**, address-independent feature flag — is on, OR if the specific address is registered for the (non-derivable) dispatchable authenticator. The first disjunct is not scoped to the address being checked at all.

- `multi_agent_common_prologue` uses this helper to decide whether a `None` public-key hash for a secondary signer is acceptable: [2](#0-1) 
  When `signer_public_key_hash` is `option::none()`, the code no longer requires the secondary signer's auth key to match the on-chain `account::get_authentication_key`; it only requires `allow_missing_txn_authentication_key(secondary_address)`, which — once `DERIVABLE_ACCOUNT_ABSTRACTION` is enabled network-wide — is `true` for **every address**, including addresses that never opted into account abstraction and have a normal, non-abstracted authentication key.

- The `None` value for a signer's public-key hash originates from `AuthenticationProof::optional_auth_key()`: [3](#0-2) 
  It returns `None` both for `AuthenticationProof::Abstract` (which is protected because `dispatchable_authenticate`/`account_abstraction::authenticate` cryptographically binds the returned signer to the given address, per `account_abstraction.move`'s `authenticate` function asserting `master_signer_addr == signer::address_of(&returned_signer)`) **and** for `AuthenticationProof::None`, which is produced by `AccountAuthenticator::NoAccountAuthenticator` — a variant carrying no signature or key material at all: [4](#0-3) 

- `TransactionAuthenticator::verify` for the `MultiAgent`/`FeePayer` variants simply loops `signer.verify(&message)?` over each declared secondary signer: [5](#0-4) 
  For a `NoAccountAuthenticator` slot there is no signature to check against the address, so signature verification cannot reject a mismatched/attacker-controlled address in that slot.

- In `aptos_vm.rs`, only the `Abstract` proof variant triggers the address-binding `dispatchable_authenticate` call; every other case (including `AuthenticationProof::None`) falls into the `_ => Ok(serialized_signer(&sender))` branch, producing a usable `&signer` for that address with **no verification step performed at all**: [6](#0-5) 

The intent of `allow_missing_txn_authentication_key` (per its own comment, "aa verifies authentication itself") is that the `None` case is only safe because some other code path (account-abstraction's native `authenticate`) already verified control of that specific address. That invariant only holds for the `Abstract` proof kind — it does **not** hold for `NoAccountAuthenticator`, yet the Move-side check conflates all `None` cases together and additionally gates acceptance on a global flag rather than an address-specific abstraction registration.

### Impact Explanation
Once `DERIVABLE_ACCOUNT_ABSTRACTION` is enabled (a shipped, non-privileged, node-wide feature flag — not a per-account opt-in), any unprivileged party can build and submit a `MultiAgent`/`FeePayer` transaction that:
1. Names any existing account address as a secondary signer.
2. Supplies `AccountAuthenticator::NoAccountAuthenticator` for that slot (no signature).
3. Passes `TransactionAuthenticator::verify()` because that slot carries no signature to fail.
4. Passes `multi_agent_common_prologue`'s auth-key check because `signer_public_key_hash` is `None` and `allow_missing_txn_authentication_key` unconditionally returns `true` for that address.
5. Receives a usable `&signer` for the victim account inside the Move entry function body (via `serialized_signer`), without ever having proven control of that account's key, without that account ever registering an authentication function, and without the account owner's consent.

This breaks the secondary-signer control guarantee that `multi_agent_common_prologue`'s spec explicitly claims to enforce ("All secondary signer addresses are verified to be authentic through a validation process," per the spec comments), and lets execution reach entry functions with a forged capability grant for the named account.

### Likelihood Explanation
High, once the `DERIVABLE_ACCOUNT_ABSTRACTION` feature is active on the network (it is a mainstream, already-shipped feature, not an experimental/off-by-default toggle requiring privileged access). No signature, key, or on-chain approval is needed from the victim account; the attacker only needs to be the transaction sender and know the victim's address.

### Recommendation
- Make `allow_missing_txn_authentication_key` address-specific for the derivable-AA case too: it should confirm that `secondary_address` was actually authenticated via `account_abstraction::authenticate` for *this* transaction (i.e., only accept `None` when the corresponding `AuthenticationProof` was truly `Abstract` and passed the native dispatch), not merely check the global feature flag.
- Distinguish `AuthenticationProof::None` (from `NoAccountAuthenticator`) from `AuthenticationProof::Abstract` before invoking `allow_missing_txn_authentication_key`; `NoAccountAuthenticator` should never satisfy the auth-key requirement for a signer whose `&signer` capability is used in the transaction, unless there is a separate, explicit, address-scoped guarantee.
- Add regression tests (as suggested in the exploit question) verifying that `multi_agent_common_prologue`/`unified_prologue_v2` reject a `None` auth-key hash for a secondary account that has a nonzero existing authentication key and has not registered any (derivable) dispatchable authenticator, expecting `PROLOGUE_EINVALID_ACCOUNT_AUTH_KEY`.

### Proof of Concept
Move unit test sketch (mirrors the proof idea in the question):
```move
#[test(secondary = @0x123)]
#[expected_failure(abort_code = 0x10001)] // error::invalid_argument(PROLOGUE_EINVALID_ACCOUNT_AUTH_KEY)
fun test_multi_agent_prologue_rejects_none_hash_for_non_aa_account(secondary: &signer) {
    // secondary has a normal, nonzero authentication key and never registered
    // any dispatchable/derivable authenticator.
    account::create_account_for_test(signer::address_of(secondary));
    // Simulate DERIVABLE_ACCOUNT_ABSTRACTION being enabled network-wide
    // (independent of `secondary`'s own configuration).
    features::change_feature_flags_for_testing(/* enable */ vector[DERIVABLE_ACCOUNT_ABSTRACTION], vector[]);

    transaction_validation::multi_agent_common_prologue(
        vector[signer::address_of(secondary)],
        vector[option::none()],   // attacker-controlled: no auth key hash supplied
        false,
    );
    // Current behavior: passes silently because allow_missing_txn_authentication_key
    // returns true purely from the global flag, not from `secondary`'s own AA state.
}
```
At the transaction level, this corresponds to an unprivileged sender building a `TransactionAuthenticator::MultiAgent` with `secondary_signers = [AccountAuthenticator::NoAccountAuthenticator]` naming the victim's address, which passes `verify()` trivially and is then accepted by `multi_agent_common_prologue` for execution.

**Caveat / what remains unverified:** I could not directly view the body of `AccountAuthenticator::verify()` for the `NoAccountAuthenticator` variant in this index (only its downstream effects — `number_of_signatures() == 0`, `authentication_proof() == AuthenticationProof::None`, and the doc comment describing it as a legitimate "no authenticator" case for the fee payer). Based on all available evidence this variant performs no cryptographic check, but a Devin session with full repo access should confirm this method body directly, and should also check whether wallet/SDK-level or mempool-level restrictions (outside this indexed code) additionally constrain which slots may use `NoAccountAuthenticator` before concluding the exploit is fully unmitigated end-to-end.

#[derive(Clone, Debug, PartialEq, Eq)]
pub enum AuthenticationProof {
    Key(Vec<u8>),
    Abstract {
        function_info: FunctionInfo,
        auth_data: AbstractAuthenticationData,
    },
    None,
}

impl AuthenticationProof {
    pub fn is_abstracted(&self) -> bool {
        matches!(self, Self::Abstract { .. })
    }

    pub fn optional_auth_key(&self) -> Option<Vec<u8>> {
        match self {
            Self::Key(data) => Some(data.clone()),
            Self::Abstract { .. } => None,
            Self::None => None,
        }
    }
}
