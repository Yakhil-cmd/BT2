### Title
Attacker-controlled swap routes can inject unauthorized calls under the caller’s authorization - (File: contracts/controller/src/strategies/swap.rs)

### Summary
XOXNO Lending passes caller-controlled, opaque swap XDR to the configured router while the caller’s authorization remains active for the enclosing strategy call. [1](#0-0)  A malicious venue reached by that route can request an unrelated `caller` authorization, such as a token or position-NFT transfer, which simulation records as a child of the signed `swap_collateral`, `swap_debt`, or `multiply` invocation. [2](#0-1) 

### Finding Description
`swap_collateral` authorizes `caller`, verifies account ownership or delegation, and forwards the caller-supplied `swap` payload into `withdraw_and_swap_from_supply`. [3](#0-2)  `swap_tokens` rejects only an empty payload, authorizes one exact `token_in.transfer(controller, router, amount_in)`, invokes `execute_strategy`, and then measures token balances. [4](#0-3)  The controller does not bind the opaque `Bytes` payload to a governance-approved venue or pool allowlist before executing it under the caller-authorized transaction. [5](#0-4) 

This is the same class as the source report: structured input supplied for one purpose is interpreted as executable behavior. A route can satisfy the controller’s measured input/output checks while its venue also performs an unrelated contract call that requests authorization from the account owner whose `require_auth` authorized the outer strategy. [6](#0-5) 

### Impact Explanation
A victim who signs the simulated authorization tree can lose assets unrelated to the lending operation. The malicious route can both transfer an arbitrary wallet token from the victim to the attacker and return a valid swap output to the controller, so the measured-output and final-account checks still pass. [7](#0-6)  Because the injected call can name any contract and function reachable through Soroban authorization, the impact is not limited to the swapped token and can include the victim’s position NFT. [8](#0-7) 

### Likelihood Explanation
The attack requires the victim to submit or sign a transaction containing the malicious route and its resulting authorization child. That limits exploitability compared with an unauthenticated theft, but the route is opaque XDR and a fair nominal swap can make the poisoned transaction appear legitimate to a user or integration that does not independently decode every authorization child. [5](#0-4)  No privileged role, leaked key, oracle manipulation, or protocol insolvency prerequisite is needed. [1](#0-0) 

### Recommendation
Do not execute caller-selected, unallowlisted venue contracts inside an authorization-bearing strategy call. Restrict route venues and pool addresses to a governance-managed registry, or replace opaque route bytes with a bounded route manifest containing only approved contract addresses. Integrations should also reject any simulated authorization tree containing children other than the expected input-token transfer.

### Proof of Concept
1. The attacker deploys a pool-compatible contract whose swap function sends a positive `token_out` amount to the router and also invokes `token::transfer(victim, attacker, amount)` for an unrelated victim-held token.
2. The attacker constructs a valid route that names that contract as a swap venue and offers it through the victim’s swap interface.
3. The victim calls `swap_collateral(victim, account_id, current=(hub_id, USDC), amount, new=(hub_id, ETH), swap=route)`.
4. The controller authorizes only the expected `USDC.transfer(controller, router, amount)` and invokes the configured router with the opaque route. [9](#0-8) 
5. Simulation records the malicious wallet-token transfer as an additional child under the victim’s `swap_collateral` authorization.
6. If the victim signs that tree, the venue steals the unrelated token while returning enough `ETH` for the controller’s positive-output check and the account’s final risk checks to succeed. [7](#0-6)
