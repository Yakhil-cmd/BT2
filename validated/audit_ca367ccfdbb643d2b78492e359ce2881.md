Confirmed: every other handler (`check_suite_handler.rb`, `push_handler.rb`, `pull_request/*_handler.rb`) uses the `stacks` helper from the base `Handler` class, which scopes lookups via `Repository.from_github_repo_name(repository_name)&.stacks` [1](#0-0) , i.e. bound to the `repository.full_name` present in the payload. `StatusHandler#process` is the outlier: it queries `Commit.where(sha: params.sha)` with no repository filter whatsoever, then calls `commit.create_status_from_github!(params)` on every matching commit across the entire instance [2](#0-1) .

### Title
Cross-repository SHA collision lets a `status` webhook for one repository mutate another repository's commit status - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target commit(s) purely by `sha`, ignoring the `repository.full_name` field of the incoming payload, unlike every other webhook handler which scopes through `Repository.from_github_repo_name(repository_name)`. Any GitHub repository whose owner/org has the Shipit GitHub App installed can send a validly-signed `status` webhook for a SHA that happens to also exist in an unrelated repository's stack, and Shipit will write that foreign status onto the unrelated commit.

### Finding Description
The binding that should hold is: `status.repository.full_name == commit.stack.repository.full_name` before a status write is accepted for that commit. Instead, the code does:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 

`Commit.where(sha:)` is a global, unscoped lookup across all stacks/repositories in the Shipit instance. `create_status_from_github!` then calls `statuses.replicate_from_github!(stack_id, github_status)` on the commit's own `stack_id`, writing a status row tied to the victim stack using attacker-supplied `state`/`context`/`target_url`/`description` fields [3](#0-2) .

`Commit#deployable?` later reads exactly this poisoned state: `!locked? && (stack.ignore_ci? || (success? && !blocked?))` [4](#0-3) , and this feeds `Stack#next_expected_commit_to_deploy` / continuous-deployment queueing [5](#0-4) .

`verify_signature` in `WebhooksController` only checks that the payload's `X-Hub-Signature` matches the GitHub App secret for `repository_owner` taken from the payload itself [6](#0-5) . This proves the webhook truly came from GitHub for repository B's org (the attacker's own org/repo, where the App happens to be installed), not that it is authorized to touch repository A's commits. There is no additional check anywhere in the call path (`Shipit::Webhooks.for_event`, `Handler#call`, `StatusHandler#process`) that repository B's name matches the stack owning the commit being updated.

Exploit flow: attacker registers/owns repo B (in any org where the Shipit GitHub App is installed — a normal, unprivileged prerequisite for using GitHub Apps on your own repos), crafts a commit with identical tree/parent/author/committer/timestamp/message to reproduce the exact SHA of a locked commit in repo A's stack (git SHA is a deterministic hash of these fields, so byte-identical commits produce identical SHAs even across unrelated repositories), pushes it to repo B, and fires (or waits for GitHub to fire) a `status` event with `state: success` for that SHA. Shipit accepts the webhook (valid signature for repo B's org), and `StatusHandler#process` finds and updates the colliding commit in repo A regardless of which repository it belongs to.

This is a genuine cross-tenant boundary break: the `stacks` scoping helper exists precisely for this purpose and is used by `push_handler.rb`, `check_suite_handler.rb`, and all `pull_request/*_handler.rb` handlers, but `status_handler.rb` bypasses it entirely.

### Impact Explanation
A payload authenticated only for repository B ends up writing a `Status` row against a commit belonging to repository A's stack, satisfying the "payload for one repository mutating another's stack/commit" Critical category. Once an operator later unlocks the commit (a normal, expected operator action, not itself a bypass), `Commit#deployable?` recomputes using the state planted by the untrusted repository, and continuous-deployment logic in `Stack#next_expected_commit_to_deploy` can pick this commit to deploy — meaning code can be deployed/rolled out based on a "success" status that repo A's own CI/webhook_secret never authorized. This is repeatable against any stack/commit whose SHA an attacker can reproduce, and scales across all tenants sharing the Shipit instance if the GitHub App is multi-org.

### Likelihood Explanation
Preconditions: the attacker needs a repository (their own, or any repo they control) where the same GitHub App instance used by Shipit is installed, and the ability to produce a commit with byte-identical SHA to a target commit in repo A — feasible since git commit content (tree, parents, author/committer identity+timestamp, message) is fully attacker-controlled when constructing the colliding commit offline, then pushed. No Shipit session, API token, or GitHub team membership is required. Cost is low: one crafted commit + one `status` webhook. It is repeatable against arbitrary target commits whose exact metadata is known/guessable (e.g., commits merged from public PRs, where full metadata is already public).

### Recommendation
Scope `StatusHandler#process` by repository the same way other handlers do: resolve `stacks` via `Repository.from_github_repo_name(payload.dig('repository','full_name'))` and restrict the `Commit.where(sha: params.sha)` lookup to `Commit.where(sha: params.sha, stack_id: stacks.select(:id))` (or equivalent), so a status can only be applied to commits belonging to stacks whose repository matches the webhook's own `repository.full_name`.

### Proof of Concept
Minitest plan (model/controller level, no live GitHub):
1. Set up two stacks/repos: `stack_a` (repository `org-a/repo-a`) with a commit `commit_a` whose `sha` is `"deadbeef..."`, and lock it via `commit_a.lock(user)`; assert `commit_a.locked?` is true and thus `commit_a.deployable?` is false.
2. Create a second stack `stack_b` (repository `org-b/repo-b`) with no commit of that sha yet.
3. Stub `verify_signature` (`GithubHook.any_instance.stubs(:verify_signature).returns(true)` per existing test pattern) to simulate a validly-signed webhook for `org-b/repo-b`.
4. POST to `/webhooks` with `X-Github-Event: status`, body `{ sha: commit_a.sha, state: 'success', repository: { full_name: 'org-b/repo-b', owner: { login: 'org-b' } } }`.
5. Assert `commit_a.statuses.count` increased and `commit_a.reload.state == 'success'` even though the payload's `repository.full_name` never matched `stack_a`'s repository.
6. Unlock `commit_a` (`commit_a.unlock`) and assert `commit_a.deployable?` is now `true`, proving deployability was derived solely from the cross-repository-injected status — asserting the equality `commit_a.status.state == 'success'` was set by a payload where `payload['repository']['full_name'] != stack_a.repository.full_name`, which should never be permitted.
