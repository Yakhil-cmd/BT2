### Title
Cross-repository commit-status forgery via unscoped SHA lookup in `Shipit::StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits by SHA alone, with no scoping to the repository that authenticated the webhook, and mutates every matching `Commit` regardless of which `Stack`/`Repository` it belongs to. Because Git SHAs are content hashes shared across forks/mirrors, an attacker who controls their own GitHub repository/organization (and thus can legitimately trigger a correctly-signed `status` webhook from GitHub) can flip the CI state of a victim's identical commit in an unrelated stack from `success` to `failure`, blocking that victim's continuous deployment.

### Finding Description
The binding that should hold is: `repository that owns the CI gate being sabotaged == repository that authenticated the sabotage payload`. It is violated.

`WebhooksController#verify_signature` only proves the payload was genuinely signed by GitHub for *some* organization configured in Shipit — it resolves the app/secret from `params.dig('repository','owner','login')`, i.e. the org owning the *sender's* repo: [1](#0-0) [2](#0-1) 

It never checks that the payload's `sha`/`repository` corresponds to the stack actually being mutated. That binding is supposed to be enforced downstream by scoping lookups to the repository named in the payload — which the base `Handler` class supports via `stacks`/`repository_name`: [3](#0-2) 

`StatusHandler#process`, however, ignores this scoping entirely and queries `Commit` globally by SHA: [4](#0-3) 

Since Git SHAs are content-addressed, the same commit SHA can legitimately exist in `Commit` rows belonging to different `Stack`s/`Repository`s (e.g., a victim stack tracking a public upstream repo and an attacker's fork/mirror of that same repo sharing history up to a given commit). An attacker who owns a repository containing that shared commit can cause GitHub to emit a real, correctly-signed `status` webhook for it (e.g., by pushing their own CI integration or directly calling GitHub's Statuses API on a commit within their own repo/fork) with `state: failure`. `verify_signature` passes because the signature is valid for the attacker's own organization/app config, but `StatusHandler#process` then updates **every** `Commit` row with that SHA across all stacks, including the victim's, via `commit.create_status_from_github!(params)`.

That call flows into `Commit#add_status`, which recomputes `status`/`success?`/`deployable?` and fires deployable-status hooks and continuous-delivery scheduling: [5](#0-4) 

`Status#schedule_continuous_delivery` then re-evaluates the commit for CD, and a `failure` status makes `deployable?` false, so `ContinuousDeliveryJob` is not enqueued for the victim's stack — sabotaging a legitimate, in-progress continuous deployment for a repository the attacker never authenticated against. [6](#0-5) 

None of the existing guards catch this: `verify_signature` authenticates "a GitHub org", not "the specific repository the payload claims to describe and that should own the mutated stack"; `ExplicitParameters` only validates the shape of `sha`/`state`/etc., not repository ownership; and `StatusHandler` uniquely bypasses the `Handler#stacks`/`repository_name` scoping pattern that other handlers use.

### Impact Explanation
A payload authenticated only for the attacker's own repository/organization mutates `Status`/`Commit` state belonging to an unrelated victim `Stack`, flipping its CI gate to `failure` and suppressing the victim's `ContinuousDeliveryJob`. This is a genuine cross-tenant write — "a payload for one repository mutating another's stack, commit" — matching the Critical severity category. It is repeatable against any victim stack whose current HEAD commit's SHA happens to be shared with a repository the attacker controls (forks, mirrors, monorepo submodule scenarios, or any commit copied/cherry-picked identically into an attacker-owned repo), and can be repeated on every new green commit to continuously block a victim's deploys.

### Likelihood Explanation
The attacker needs: (1) a repository/organization that is a legitimate GitHub App installation Shipit already trusts (which is common in multi-org/enterprise Shipit deployments, or simply any repo where the attacker can produce a genuinely GitHub-signed `status` event), and (2) a commit whose SHA matches the victim's targeted commit, achievable whenever repos share history (forks of the target's own repo, common upstream dependencies mirrored into Shipit-tracked repos, etc.). No Shipit secrets, sessions, or privileged roles are required — only ownership of a repo covered by an already-configured GitHub App/webhook secret. This is a low-cost, fully repeatable attack once the SHA-sharing precondition is met.

### Recommendation
Scope `StatusHandler#process` to the repository named in the payload, mirroring `Handler#stacks`: resolve `stacks` (or `Repository.from_github_repo_name(payload.dig('repository','full_name'))`) and only update commits/statuses belonging to those stacks, e.g. `stacks.flat_map(&:commits).where(sha: params.sha).each { |c| c.create_status_from_github!(params) }`, instead of a global `Commit.where(sha: ...)`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status webhook from an unrelated repository must not affect another repository's commit/stack" do
  victim_stack = shipit_stacks(:shipit) # repository X
  attacker_repo_full_name = "attacker/unrelated-repo" # repository Y, distinct from victim_stack.repository

  victim_commit = victim_stack.commits.last
  victim_commit.statuses.create!(stack_id: victim_stack.id, state: 'success', context: 'ci/travis')
  victim_commit.reload
  assert_predicate victim_commit, :deployable? # pre-attack: true

  payload = {
    'sha' => victim_commit.sha,
    'state' => 'failure',
    'context' => 'ci/travis',
    'repository' => { 'full_name' => attacker_repo_full_name, 'owner' => { 'login' => 'attacker' } },
    'branches' => []
  }

  assert_no_enqueued_jobs only: ContinuousDeliveryJob do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end

  refute_predicate victim_commit.reload, :deployable? # post-attack: incorrectly false
end
```
This demonstrates that a payload naming `attacker/unrelated-repo` still mutates `victim_stack`'s commit state and suppresses its `ContinuousDeliveryJob`, confirming the broken binding.
