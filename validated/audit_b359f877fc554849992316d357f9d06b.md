### Title
Promise-yield timeout queue silently violates its "ordered by expires_at" invariant when `yield_timeout_length_in_blocks` changes, causing indefinite blocking of newer, already-expired timeouts - (File: runtime/runtime/src/lib.rs)

### Summary
The `resolve_promise_yield_timeouts` function processes the `PromiseYieldTimeout` queue strictly in FIFO/index order and explicitly relies on the comment-documented invariant that "Queue entries are ordered by expires_at" [1](#0-0) . `expires_at` is computed at receipt-creation time as `apply_state.block_height + config.wasm_config.limit_config.yield_timeout_length_in_blocks` [2](#0-1) . Because `yield_timeout_length_in_blocks` is a `RuntimeConfig` parameter that is selected per protocol version via `RuntimeConfigStore`, any protocol upgrade that changes this value breaks the assumed monotonic ordering of `expires_at` across entries enqueued before vs. after the upgrade. This is architecturally the same bug class as the Sherlock M-12 finding: a FIFO queue whose correctness depends on an externally-controlled timeout parameter never decreasing, and which stops (`break`) at the first non-expired head element instead of skipping past it.

### Finding Description
`enqueue_promise_yield_timeout` appends new `PromiseYieldTimeout { account_id, data_id, expires_at }` entries strictly at the tail of an index-based trie queue (`TrieQueueIndices` with `first_index`/`next_available_index`) [3](#0-2) [4](#0-3) . The `expires_at` value baked into each entry is `block_height_at_creation + yield_timeout_length_in_blocks` [5](#0-4) .

`resolve_promise_yield_timeouts` then pops entries strictly from the front of the queue and breaks the loop as soon as the front entry's `expires_at` exceeds the current block height:
```
// Queue entries are ordered by expires_at
if queue_entry.expires_at > apply_state.block_height {
    break;
}
``` [1](#0-0) 

This is exactly the pattern flagged in the report: the loop assumes `expires_at` is non-decreasing across the queue, but nothing enforces that. If a protocol upgrade increases `yield_timeout_length_in_blocks` (or more critically, if an older entry was created under a config with a *larger* value than a later entry created under a reduced value), an entry near the head of the queue can have a larger `expires_at` than entries queued after it. Since the loop `break`s (rather than skipping) on the first non-expired head, every later-queued — and already logically expired — yield timeout is stuck behind the still-unexpired older entry until that older entry's `expires_at` is finally reached.

Unlike the Cosmos governance case, this can't be triggered by a third-party governance vote, but it is fully reachable through the protocol's own versioned `RuntimeConfig`: `yield_timeout_length_in_blocks` is a value in `parameters.yaml`/`parameters_testnet.yaml` selected per protocol version by `RuntimeConfigStore`, and any future protocol upgrade adjusting it (in either direction) reintroduces exactly this ordering violation for any `promise_yield_create` calls straddling the upgrade boundary. Because `promise_yield_create` is a normal, unprivileged host function callable from any contract via a `FunctionCall` action [6](#0-5) , any unprivileged account can create these queue entries around an upgrade boundary, and the resulting stall affects the entire shard's yield-timeout queue (not just its own account), since the queue is processed head-first and shared across all accounts' yielded promises on the shard.

### Impact Explanation
If the head-of-queue entry's `expires_at` is anomalously large relative to entries queued after it, `resolve_promise_yield_timeouts` cannot make progress past that entry: every subsequent PromiseYield timeout on the shard — regardless of its own account, and even though it may already be logically expired per its own `expires_at` — is prevented from firing its `PromiseResume(Failed)` receipt. This means:
- Contracts relying on the promise-yield timeout guarantee (i.e., "the promise will fail after at most `yield_timeout_length_in_blocks`") no longer get that guarantee; callbacks that should resolve to `Failed` can be delayed indefinitely (until the stuck head entry's own timeout is reached), producing incorrect/stale execution results and potentially stuck gas prepayments (`prepay_gas` for the callback is already reserved and cannot be reclaimed until resolution) [7](#0-6) .
- The stall is shard-wide (affects all accounts whose yielded promises are queued behind the stuck entry), not limited to a single account, amplifying the denial-of-service.
- No consensus divergence occurs (all validators compute this deterministically the same way), so this is a functional-correctness/availability bug rather than a safety bug, but it can still cause prolonged resource lock-up (reserved gas/data ids) and broken application-level invariants for any dApp depending on yield timeouts.

### Likelihood Explanation
This requires a change to the `yield_timeout_length_in_blocks` parameter value between protocol versions while at least one `PromiseYieldTimeout` entry created under the old value remains unresolved at the time entries created under the new value are enqueued. This is a plausible but not everyday occurrence — it depends on a future protocol upgrade tuning this specific parameter, combined with long-lived pending yields spanning the upgrade boundary (which is realistic since `promise_yield_create`'s whole purpose is to await asynchronous off-chain input over potentially many blocks). I could not fully verify from the indexed snapshot files whether `yield_timeout_length_in_blocks` has already changed across historical protocol versions in this repo (the parameter snapshot diff was not retrievable in the time available); this is a latent structural risk in the queue design rather than a currently-exploited value change.

### Recommendation
Do not rely on insertion order matching `expires_at` order when the underlying timeout-length parameter can change between protocol versions. Either:
1. Freeze/pin the effective `yield_timeout_length_in_blocks` value used for expiration processing to the value that was in effect at enqueue time, and enforce (via a fatal/consistency check or explicit migration) that any parameter change is only ever additive in a way that preserves per-entry monotonicity relative to already-queued entries, or
2. Change `resolve_promise_yield_timeouts` to not break out of the loop entirely on the first non-expired head entry sitting behind entries that may have smaller `expires_at`; instead, maintain a min-heap/secondary ordering keyed by `expires_at` rather than a strict FIFO index queue, so that entries are always resolved in true expiration order irrespective of insertion order.
3. At minimum, add an explicit assertion/migration step when `yield_timeout_length_in_blocks` changes across a protocol upgrade, verifying (or forcibly draining) that no queued entry violates the new ordering assumption.

### Proof of Concept
1. Deploy a contract account `A` that calls `promise_yield_create` at block height `H0` under protocol version `V1`, where `RuntimeConfigStore` resolves `yield_timeout_length_in_blocks = T1` (large). This enqueues `PromiseYieldTimeout { expires_at: H0 + T1, ... }` at the queue tail [5](#0-4) .
2. A protocol upgrade activates at height `H1 > H0` (still `H1 < H0 + T1`), switching to protocol version `V2` where `RuntimeConfigStore` resolves `yield_timeout_length_in_blocks = T2 < T1`.
3. Any account `B` (including the same or a different, fully unprivileged account) calls `promise_yield_create` at height `H2 >= H1`, enqueuing `PromiseYieldTimeout { expires_at: H2 + T2, ... }` right after A's entry in the queue, where `H2 + T2 < H0 + T1`.
4. When block height reaches `H2 + T2` (B's logically-expired timeout height), `resolve_promise_yield_timeouts` examines the queue head — still A's entry — sees `expires_at (H0+T1) > apply_state.block_height`, and `break`s [1](#0-0) . B's already-expired timeout is never processed until block height reaches `H0 + T1`, at which point A's entry is finally popped and B's entry can then be evaluated.
5. Result: B's contract callback that was supposed to resolve with `PromiseResult::Failed` at `H2 + T2` is delayed until `H0 + T1`, an arbitrarily long, attacker/upgrade-controlled window, while B's prepaid callback gas remains reserved and unusable in the interim.

// Enqueues given timeout to the PromiseYield timeout queue
pub fn enqueue_promise_yield_timeout(
    state_update: &mut TrieUpdate,
    promise_yield_indices: &mut PromiseYieldIndices,
    account_id: AccountId,
    data_id: CryptoHash,
    expires_at: BlockHeight,
) {
    set(
        state_update,
        TrieKey::PromiseYieldTimeout { index: promise_yield_indices.next_available_index },
        &PromiseYieldTimeout { account_id, data_id, expires_at },
    );
    promise_yield_indices.next_available_index = promise_yield_indices
        .next_available_index
        .checked_add(1)
        .expect("Next available index for PromiseYield timeout queue exceeded the integer limit");
}
