### Title
`StatusHandler#process` writes GitHub commit statuses to any `Commit` row matching `sha`, regardless of which repository/organization the signed webhook actually belongs to, letting a status forged in one org flip `MergeRequest#all_status_checks_passed?` for a queued PR in an unrelated stack - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
The question's specific premise is inaccurate: `MergeRequest#all_status_checks_passed?` does not read `merge_commit.status`/`merge_commit.success?` — it reads `head.statuses_and_check_runs` via `StatusChecker`. However, the underlying webhook-provenance break is real and reachable through that same `head` commit: `StatusHandler#process` resolves target commits with a completely unscoped `Commit.where(sha: params.sha)`, with no repository/org filtering, unlike its sibling handlers.

### Finding Description
The binding that should hold is: `organization whose webhook_secret verified request.raw_post == organization owning the Commit/Stack whose Status row is created`. Trace:

- `MergeRequest#all_status_checks_passed?` — `return false unless head; StatusChecker.new(head, head.statuses_and_check_runs, stack.cached_deploy_spec).success?` [1](#0-0) . It consults the PR's `head` commit's statuses, not `merge_commit`.
- `WebhooksController#verify_signature` derives `repository_owner` from `params.dig('repository','owner','login')` and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [2](#0-1) . This only proves the payload was signed by *some* org's secret — it does not bind the payload to any specific repository.
- `StatusHandler#process` then does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [3](#0-2)  — a global, cross-tenant lookup with **no** repository or stack scoping at all.
- Compare with sibling handlers that correctly scope via the base `Handler#stacks` helper (`Repository.from_github_repo_name(repository_name)&.stacks`): `PushHandler#process` uses `stacks.not_archived.where(branch:)` [4](#0-3)  and `CheckSuiteHandler#process` uses `stacks.where(branch: ...)` [5](#0-4) . `StatusHandler` is the odd one out — it never calls `stacks`.
- `Commit#create_status_from_github!` -> `add_status { statuses.replicate_from_github!(stack_id, github_status) }`, using the *commit's own* `stack_id`, so any commit anywhere in the database whose `sha` matches gets a new `Status` row scoped to its real owning stack [6](#0-5) . `Status#after_create :enable_ci_on_stack` and `after_commit :schedule_continuous_delivery` fire on that unrelated stack as well.

Exploit flow: attacker has ordinary write/collaborator access to some repository R in organization A that is already onboarded to Shipit (so `verify_signature` succeeds using A's real webhook secret, computed by GitHub itself — the attacker never needs to know the secret). The attacker constructs a commit object with byte-identical metadata (tree, parent, author/committer identities and timestamps, message) to the `head` commit of a queued, pending `MergeRequest` in Stack B (a different repository/org, or even a different repo in the same org A), which is achievable because git SHA1 is fully determined by that public metadata and the victim PR's commit content is publicly visible. The attacker pushes that identical commit object into repo R and sets a `success` status on it via R's normal (non-Shipit) permissions. GitHub emits a genuinely-signed `status` webhook for org A. `StatusHandler#process` finds the sha-matching `Commit` row belonging to Stack B and creates a `success` `Status` on it, even though Stack B's own CI never ran or passed. `ProcessMergeRequestsJob#perform` subsequently calls `merge_request.all_status_checks_passed?` (now true) and executes `merge_request.merge!`, which calls `stack.github_api.merge_pull_request` for Stack B — an unauthorized merge [7](#0-6) .

Existing guards (`verify_signature`, `ExplicitParameters` schema, `drop_unhandled_event`) only check that *a* recognized organization's secret matches the raw body; none of them bind the payload's `repository.full_name` to the `Commit`/`Stack` being mutated, so the divergence is real.

### Impact Explanation
A webhook validly signed by organization A's secret can create a `Status` record — and thereby flip CI readiness — on a `Commit` belonging to a completely different `Stack`/organization/repository, matching the rules' explicit Critical category "a payload for one repository mutating another's stack, commit, task or team" and "an unauthorized deploy, rollback or merge." Because `Commit.where(sha:)` has no owner/stack constraint, this is repeatable against any stack whose queued PR head commit sha the attacker can replicate, and blast radius spans all tenants sharing the Shipit instance, not just one org.

### Likelihood Explanation
Requires: (1) the attacker to have ordinary GitHub write access to at least one repository in some organization already onboarded to Shipit (not the victim's target repo, and not any Shipit-specific privilege), and (2) the ability to replicate a target commit's exact metadata to reproduce its SHA1, which is straightforward for any publicly visible commit. No Shipit secret, session, or API token is needed at any point since GitHub itself computes the signature. This is a plausible, low-cost, repeatable attack given the described attacker capabilities.

### Recommendation
Scope `StatusHandler#process` the same way as `PushHandler`/`CheckSuiteHandler`: restrict the commit lookup to commits belonging to `stacks` derived from `payload.dig('repository','full_name')` (e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalent), so a webhook can only mutate commits/statuses belonging to the repository it was actually sent for.

### Proof of Concept
Minitest plan (`test/models/webhooks/handlers/status_handler_test.rb` or `test/controllers/webhooks_controller_test.rb`):
1. Create `stack_a` (org A, repo `org-a/repo`) and `stack_b` (org B, repo `org-b/other-repo`), both with a commit sharing the same `sha = "deadbeef..."`.
2. Create a `MergeRequest` on `stack_b` in `pending` state with `head` = that commit, and assert `merge_request.all_status_checks_passed?` is `false` before the webhook (no statuses yet).
3. POST to `/webhooks` with `X-Github-Event: status`, a payload whose `repository.full_name == "org-a/repo"` and `sha == "deadbeef..."`, `state: "success"`; stub `GithubHook#verify_signature` (or the real HMAC) to simulate a legitimately-signed org A request.
4. Assert `stack_a`'s commit did NOT necessarily need a match, but assert `stack_b`'s commit now has a `Status` row (`commit_b.statuses.count` increased) and `merge_request.reload.all_status_checks_passed?` is now `true`, and `assert_enqueued_with(job: ProcessMergeRequestsJob, args: [stack_b])`.
5. Assert this occurred purely from an org-A-signed payload referencing `org-a/repo`, proving the equality `signing_org(A) == owning_stack(B)` is violated.

    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?
      end

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end
