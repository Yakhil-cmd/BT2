### Title
Liquidator-controlled stale-but-valid oracle price selection allows under/over-seizure of borrower collateral in `liquidate()` — ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`v0-4-market.clar`'s `liquidate()` lets the caller supply `price-feeds` that get written to the oracle before collateral/debt are priced for the seizure calculation [1](#0-0) . The freshness check that gates which price is accepted only enforces "not older than `max-staleness`" and "not older than the previously-stored timestamp" — it does not require the *freshest* available Pyth price [2](#0-1) . Because Pyth publishes several valid price ticks per `max-staleness` window, a liquidator can choose, among multiple valid signed prices, the one that maximizes the collateral seized from a borrower for the same debt repaid, exactly analogous to the original report's "two valid Pyth prices used opportunistically in one transaction" pattern.

### Finding Description
`liquidate()` first writes attacker-supplied price feeds via `write-feeds` (feeds check), then resolves collateral price through `process-collateral-asset` and computes `coll-expected`/`coll-actual` from that single price [3](#0-2) . The amount of collateral seized is inversely proportional to `coll-price`:
```
coll-expected = coll-usd-expected * 10^decimals / coll-price
``` [4](#0-3) 

The only gate on which of Pyth's several valid concurrent price updates can be submitted is `oracle-timestamp-fresh`, which accepts any timestamp within `max-staleness` seconds of `stacks-block-time` and monotonically ≥ the last stored timestamp — it does not require the most recent Pyth tick [5](#0-4) . This mirrors the root cause in the external report: freshness ("maxAge"/`max-staleness`) is checked, but "there are no guarantees that the price at the current time is the freshest," so a caller can pick from a set of valid signed prices the one most favorable to themselves.

Shared state: the borrower's `collateral` balance and the `last-update` timestamp map are shared state primed by the liquidator's chosen price feed and consumed to compute how much of the borrower's collateral is seized — the borrower has no control over which valid price is submitted.

### Impact Explanation
By choosing the lowest valid-but-not-freshest signed collateral price available within the `max-staleness` window (rather than the true current market price), a liquidator can seize more collateral tokens than the intended liquidation-penalty design dictates for the same USD debt repaid, at the direct expense of the borrower being liquidated (and, if collateral runs out, socialized as bad debt across suppliers via the bad-debt socialization path referenced later in `liquidate()`). This is theft of borrower funds at rest (collateral) beyond the protocol's intended liquidation-penalty bound, fitting the Critical impact class (direct theft of user funds / protocol insolvency risk via inflated bad-debt socialization).

### Likelihood Explanation
Likelihood is moderate: it requires the liquidator to have access to multiple valid signed Pyth price updates within the same `max-staleness` window with differing prices (readily available during periods of price volatility, since Pyth publishes sub-second updates), and to construct/submit the `price-feeds` argument accordingly. No privileged access or flashloan is required — any permissionless liquidator calling `liquidate()` can attempt this opportunistically whenever price is moving and multiple valid ticks exist.

### Recommendation
Require that the submitted price update be the single most-recent price known to the on-chain Pyth storage contract at call time (e.g., reject if a strictly newer valid price already exists in `pyth-storage`), rather than merely bounding staleness and enforcing monotonicity. Alternatively, restrict `liquidate()`'s custom `price-feeds` argument for collateral valuation to trusted/relayer-submitted updates, and use a TWAP or last-N-price median instead of the single most-favorable spot tick for computing seized collateral.

### Proof of Concept
1. Borrower's position becomes liquidatable (LTV ≥ `LTV-LIQ-PARTIAL`) under the last committed collateral price P0.
2. Collateral asset's Pyth price ticks down transiently to P1 < P0 at some point within the last `max-staleness` seconds, then recovers to P2 (P2 > P1) by current block time; both P1 and P2 have publish-times satisfying `oracle-timestamp-fresh` relative to `stacks-block-time` at call time [2](#0-1) .
3. Liquidator calls `liquidate(borrower, collateral-ft, debt-ft, debt-amount, min-collateral-expected, receiver, (some (list P1-update)))`, causing `write-feeds` to commit P1 and `process-collateral-asset`/`calc-final-liquidation-amounts` to compute `coll-expected`/`coll-actual` using P1 instead of the true current price P2 [6](#0-5) .
4. Because `coll-expected` is inversely proportional to `coll-price`, using the lower stale-but-valid P1 yields more seized collateral tokens for the same debt repaid than using P2 would, transferring extra value from the borrower (and potentially the supplier pool via bad-debt socialization) to the liquidator.

(define-private (process-collateral-asset
  (coll-aid uint)
  (debt-actual-usd uint)
  (liq-penalty uint)
  (user-coll-balance uint)
  (assets (list 64 {
    id: uint, addr: principal, decimals: uint,
    oracle: { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint },
    collateral: bool, debt: bool, price: uint
  }))
  (coll-asset {
    id: uint, addr: principal, decimals: uint,
    oracle: { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint },
    collateral: bool, debt: bool
  }))
  
  (let (;; Calculate expected collateral in USD (with penalty bonus for liquidator)
        (coll-usd-expected (calc-liq-collateral-repay debt-actual-usd liq-penalty))
        
        ;; Handle disabled collaterals by resolving price if not in enabled assets
        (coll-asset-info (match (find-asset coll-aid assets)
                           ;; Found in enabled list: use it (already has price)
                           found found
                           ;; Not found (disabled): resolve price on demand
                           (let ((oracle-data (get oracle coll-asset))
                                 (price (unwrap-panic (price-resolve oracle-data))))
                             (merge coll-asset { price: price }))))
        (coll-price (get price coll-asset-info))
        (coll-decimals (get decimals coll-asset-info))
        (coll-expected (mul-div-down coll-usd-expected (pow u10 coll-decimals) coll-price))
        
        ;; cap at available collateral (user may not have enough)
        (coll-actual (if (> coll-expected user-coll-balance)
                         user-coll-balance
                         coll-expected)))
    {
      coll-actual: coll-actual,
      coll-expected: coll-expected,
      coll-price: coll-price,
      coll-decimals: coll-decimals
    }))

;; Calculate final liquidation amounts with proportional adjustments
;; If collateral was capped, recalculates debt proportionally
;; Returns: { debt-final-usd: uint, debt-final: uint }
(define-private (calc-final-liquidation-amounts
  (debt-actual-usd uint)
  (coll-actual uint)
  (coll-expected uint)
  (coll-price uint)
  (coll-decimals uint)
  (debt-price uint)
  (debt-decimals uint)
  (liq-penalty uint))
  
  (let ((coll-actual-usd (normalize (* coll-actual coll-price) coll-decimals false))
        ;; If collateral was capped, recalculate debt proportionally
        (debt-final-usd (if (< coll-actual coll-expected)
                           (calc-liq-debt-repay-real coll-actual-usd liq-penalty)
                           debt-actual-usd))
        (debt-final (mul-div-down debt-final-usd (pow u10 debt-decimals) debt-price)))
    {
      debt-final-usd: debt-final-usd,
      debt-final: debt-final
    }))
