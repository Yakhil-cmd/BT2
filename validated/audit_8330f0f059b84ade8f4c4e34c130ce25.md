### Title
Webhook signature verified against `repository.owner.login`/`organization.login` while event handlers act on the unverified `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
Shipit supports multiple GitHub organizations, each configured with its own webhook secret, resolved via `Shipit.github(organization: repository_owner)`. The webhook signature is verified using the secret belonging to the organization named in the payload's `repository.owner.login` (or `organization.login`) field. However, the actual GitHub repository/stack that the event operates on is resolved by every `Handler` subclass from a different, unauthenticated field of the same payload: `repository.full_name`. These two fields are never checked for consistency.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/secret to validate against using: [1](#0-0) 
with `repository_owner` computed as: [2](#0-1) 

Once the signature check passes, the full, unmodified `params` hash is dispatched to handlers: [3](#0-2) 

Every handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc.) resolves the target `Repository`/`Stack` using `Handler#repository_name`, which reads a **different** field of the payload: [4](#0-3) 

Nothing binds `repository.full_name` to `repository.owner.login`/`organization.login`. The equality that should hold and does not is:

`organization authenticated (repository.owner.login used for HMAC lookup) == repository written (repository.full_name used by Handler#stacks / Repository.from_github_repo_name)`

If a caller holds a valid webhook secret for `organization_A` (e.g., because Shipit is configured for multiple GitHub organizations, or the caller compromised/obtained one org's secret through a lower-trust channel), they can compute a valid HMAC over a JSON body where `repository.owner.login` = `organization_A` (making `verify_signature` pass) while `repository.full_name` = `organization_B/some-repo` (a repository/stack tracked in Shipit under a different organization). `PushHandler#process` will then act on stacks under `organization_B` using attacker-controlled `after` (target SHA), triggering `stack.sync_github(expected_head_sha: params.after)`: [5](#0-4) 

`MembershipHandler` is worse: it trusts `params.organization.login` directly to set `team.organization`, and adds/removes arbitrary GitHub logins from a `Team` without verifying that login is actually a member of that team on GitHub: [6](#0-5) 

Team membership drives `User#authorized?`, which gates access to the entire Shipit UI/API: [7](#0-6) 

So an attacker who can produce a validly-signed webhook for *any one* configured organization can forge a `membership` event naming a different `Shipit.github_teams` organization/team and `added` action for an arbitrary GitHub login, granting that login `authorized?` access to Shipit — escalation into `Shipit.github_teams` authorization, one of the defined High-impact outcomes.

### Impact Explanation
This breaks the trust boundary between "which organization's credential validated this request" and "which organization's data/state the request is allowed to mutate." Consequences include:
- Cross-repository/cross-organization state mutation (forged `push`/`status`/`check_suite` events triggering syncs on stacks the attacker's org has no relationship to).
- Escalation into `Shipit.github_teams` authorization via forged `membership` events that add an arbitrary GitHub login to a `Team` the attacker does not administer, granting that account `authorized?` status and full application access — matching the High severity bucket "escalation into `Shipit.github_teams` authorization."

### Likelihood Explanation
Requires the attacker to already hold a valid HMAC secret for at least one organization configured in the multi-tenant Shipit deployment (a webhook secret, which is explicitly out of scope as an assumed credential per the rules) — but the vulnerability is that this credential, once held for org A, is sufficient to forge state for org B/any other repository tracked by the instance, which is not itself gated by any separate credential. In a single-organization Shipit deployment this specific cross-org escalation is not exploitable, so the practical likelihood depends on the deployment topology (multiple organizations sharing one Shipit instance), which is a supported and documented configuration (`Shipit.github(organization:)`, `GithubOrganizationUnknown`).

### Recommendation
Bind the field used to select the verification secret to the field used to resolve the acted-upon repository/team: after computing `repository_owner` for secret selection, re-derive it from (or cross-check it against) `repository.full_name`'s owner segment (and, for `membership` events, against `params.organization.login` vs the team's already-recorded `organization`). Reject the webhook if these disagree.

### Proof of Concept
1. Shipit instance configured with two GitHub organizations, `org-a` and `org-b`, each with its own `webhook_secret` (`Shipit.github(organization: 'org-a')` / `Shipit.github(organization: 'org-b')`), both tracked in the same Shipit deployment.
2. Attacker has (or leaks) `org-a`'s webhook secret only, e.g. via a lower-privileged CI integration.
3. Attacker crafts a `push` payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker_sha>",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/victim-repo"
  }
}
```
4. Attacker signs the payload body with `org-a`'s secret and sends `X-Hub-Signature: sha1=<hmac>` and `X-Github-Event: push`.
5. `WebhooksController#verify_signature` computes `repository_owner = "org-a"`, fetches `Shipit.github(organization: 'org-a')`, and the signature verifies successfully.
6. `PushHandler#repository_name` reads `payload.dig('repository', 'full_name')` = `"org-b/victim-repo"`, resolves stacks under `org-b`, and triggers `stack.sync_github(expected_head_sha: '<attacker_sha>')` for a repository the attacker has no relationship with in `org-b`. [2](#0-1) [4](#0-3)
