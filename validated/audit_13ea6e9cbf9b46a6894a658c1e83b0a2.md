## Verdict: Valid

`TransactionAuthenticator::verify` for the `MultiAgent` variant never checks that `secondary_signer_addresses.len() == secondary_signers.len()` before iterating and verifying signatures.

### Finding Description

`TransactionAuthenticator::MultiAgent` carries two parallel lists: `secondary_signer_addresses: Vec<AccountAddress>` and `secondary_signers: Vec<AccountAuthenticator>` [1](#0-0) . The intended invariant is that each address in `secondary_signer_addresses` corresponds 1:1 to an authenticator in `secondary_signers`, so that every claimed secondary signer address is cryptographically bound to a verified signature.

However, `verify()` builds a single signing message that embeds the *entire* `secondary_signer_addresses` vector into `RawTransactionWithData::new_multi_agent`, then only loops over the (possibly shorter) `secondary_signers` vector to check signatures — with no length equality assertion anywhere: [2](#0-1) 

If an attacker submits a raw transaction with `secondary_signer_addresses = [A, B]` but `secondary_signers = [authA]` (only one authenticator), the `for signer in secondary_signers` loop iterates exactly once (verifying `authA` against the message), and `verify()` returns `Ok(())`. No error is raised for the length mismatch, and no signature is ever demanded or checked for address `B`. The FeePayer variant, which reuses the same address vector, has similar list-flattening logic without a length check either (`to_verify` is built purely from `sender` + `secondary_signers`, independent of `secondary_signer_addresses` length) [3](#0-2) .

### Impact Explanation

Any downstream code path that treats `secondary_signer_addresses` (a value taken directly from the unverified authenticator payload) as the authoritative list of authorized/participating signer accounts — for example when extracting Move `&signer` arguments for a multi-agent script/entry function — will include address `B` as an "authenticated" signer even though no signature from `B`'s key material was ever checked. This breaks the signer-binding guarantee: `verify()` succeeds while an entire claimed secondary-signer address goes completely unauthenticated, rather than the caller being told to reject the malformed authenticator.

### Likelihood Explanation

This is reachable purely from unprivileged input: any submitter can hand-craft a `SignedTransaction` with a `TransactionAuthenticator::MultiAgent` whose two vectors differ in length, then submit it via the standard REST/BCS transaction path (mempool/vm-validator call `authenticator.verify(&raw_txn)` during admission checks). No privileged key, prior approval, or peer compromise is required — it's a pure client-side construction bug in the admission-time verification logic.

### Recommendation

Add an explicit length check at the top of the `MultiAgent` (and `FeePayer`) arms of `TransactionAuthenticator::verify`:
```rust
if secondary_signer_addresses.len() != secondary_signers.len() {
    return Err(anyhow!("mismatched secondary signer address/authenticator counts"));
}
```
This should be enforced before constructing the signing message, so a malformed authenticator is rejected outright instead of silently accepting an incomplete signer set.

### Proof of Concept

```rust
// types/src/transaction/authenticator.rs (conceptual test)
let sender_auth = AccountAuthenticator::ed25519(sender_pub, sender_sig);
let secondary_addr_a = AccountAddress::random();
let secondary_addr_b = AccountAddress::random(); // never actually signs anything
let auth_a_only = AccountAuthenticator::ed25519(pub_a, sig_a);

let authenticator = TransactionAuthenticator::multi_agent(
    sender_auth,
    vec![secondary_addr_a, secondary_addr_b], // 2 addresses
    vec![auth_a_only],                        // only 1 authenticator
);

// Expectation: this should error (address/authenticator count mismatch).
// Actual behavior: verify() returns Ok(()), silently treating `secondary_addr_b`
// as a valid secondary signer with zero signature verification.
let result = authenticator.verify(&raw_txn);
assert!(result.is_err()); // FAILS today — result is Ok(())
```

**Caveat / unverified downstream scope:** I confirmed the missing length check directly in `authenticator.rs`, which is the exact defect described in the question. I was not able to fully trace, within the remaining tool budget, how `TransactionMetadata`/`AptosVM` prologue consumes `secondary_signer_addresses` (e.g., whether it re-derives signer counts from `secondary_signers` length rather than trusting the address vector), which would determine whether this manifests as full signer impersonation at execution time or is otherwise neutralized downstream. This should be verified in `aptos-move/aptos-vm/src/transaction_metadata.rs` and the prologue/epilogue Move code before treating impact as confirmed end-to-end.
