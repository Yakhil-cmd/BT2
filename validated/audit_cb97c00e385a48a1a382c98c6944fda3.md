### Title
Stack-scoped `ApiClient` token can read status of any stack via `CCMenuController` - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::BaseController` implements a scoping mechanism so that an `ApiClient` created with a `stack_id` can only operate on the stack it was granted access to. `Shipit::Api::CCMenuController` overrides the `stack` accessor and bypasses this scoping entirely, looking up the requested stack unconditionally from `params[:stack_id]` instead of from the scoped `stacks` relation. This breaks the equality "stack a token authorizes == stack the token touches."

### Finding Description
In the base API controller, access is scoped through two cooperating methods: [1](#0-0) 

`stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` when the authenticated `ApiClient` has a `stack_id` set, and `stack` resolves `params[:stack_id]` only within that restricted relation. This is the mechanism responsible for the invariant validated by the test "an api client scoped to a stack will only see that one stack": [2](#0-1) 

`ApiClient` itself supports being bound to a single `Stack`: [3](#0-2) 

`Shipit::Api::CCMenuController`, however, defines its own `stack` method that ignores the scoped `stacks` relation and resolves `params[:stack_id]` against the entire `Stack` table: [4](#0-3) 

`require_permission :read, :stack` only checks that the client possesses the `read:stack` permission string; it does not check *which* stack the client is scoped to: [5](#0-4) 

As a result, a token that was only supposed to authorize reads for Stack A (its bound `stack_id`) can be replayed against `GET /stacks/:stack_id/ccmenu.xml` (or the equivalent API route) with any other `stack_id` value and will successfully render that other stack's data — bypassing the exact restriction the `stacks`/`stack` scoping in `BaseController` was built to enforce.

### Impact Explanation
This is an unauthorized read of stack state via a token that is not authorized for that stack — the rendered CCMenu XML includes build/lock/activity status, last build label (commit SHA/deploy id), and timing data for the deploy pipeline of a stack the client was never granted access to: [6](#0-5) 

This matches the accepted High-impact category of "unauthenticated read of stack state" in effect, since the client is authenticated but not authorized for the target stack — the authorization scope is bypassed rather than checked.

### Likelihood Explanation
Exploitation requires only possession of a valid, stack-scoped `ApiClient` token (any legitimate consumer who was deliberately restricted to one stack) and knowledge/guessing of another stack's `repo_owner/repo_name/environment` param used by `Stack.from_param!`. No privileged access, GitHub credentials, or webhook secret is needed — only the restricted token itself, which is exactly the credential this scoping mechanism is meant to constrain.

### Recommendation
Change `CCMenuController#stack` to resolve through the scoped `stacks` relation (i.e., `stacks.from_param!(params[:stack_id])`) as `BaseController#stack` does, so that stack-scoped `ApiClient` tokens cannot read state for stacks outside their granted `stack_id`.

### Proof of Concept
1. Admin creates (or the app otherwise provisions) an `ApiClient` with `permissions: ['read:stack']` and `stack_id` set to Stack A only.
2. Attacker holding that token issues:
   `GET /stacks/<stack-B-repo_owner>/<stack-B-repo_name>/<stack-B-environment>/ccmenu.xml?token=<token>`
   (or with `Authorization: Basic` using the token, per `authenticate_api_client` in `CCMenuController`).
3. Because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly instead of `stacks.from_param!`, the request succeeds and returns Stack B's build/lock/deploy status, even though the token's `stack_id` is Stack A.
