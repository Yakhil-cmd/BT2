### Title
Reachable division-by-zero panic in `PoolState::token_price_x32` aborts swaps and can permanently brick trading on a pool - (File: programs/cp-swap/src/states/pool.rs)

### Summary
`PoolState::token_price_x32` performs unchecked integer division using live vault balances net of accrued fees as denominators. Rust integer division panics on a zero divisor (this is not a checked-math overflow, it aborts unconditionally in both debug and release builds). This function is called on every `swap_base_input` and `swap_base_output` invocation via `PoolState::get_swap_params`, with no upstream guard ensuring the resulting token amounts are non-zero before the division. This is the same bug class as CVE-2017-12959 (a reachable assertion/abort triggered by attacker-influenceable state), except here the "abort" is a Solana program panic that aborts the transaction rather than a long-running process, and if the zero-liquidity state is legitimately reachable, it can render the swap instruction on that pool permanently unusable.

### Finding Description
`token_price_x32` computes the two spot prices as raw ratios without checking for a zero denominator: [1](#0-0) 

It is invoked unconditionally from `get_swap_params`, which is called at the start of both swap entrypoints: [2](#0-1) [3](#0-2) 

`vault_amount_without_fee`, which `token_price_x32` calls internally, only guards against the fee amount exceeding the vault (via `checked_sub` -> `ErrorCode::InsufficientVault`); it explicitly allows the result to be exactly `0`: [4](#0-3) 

If the real (fee-excluded) balance of either token vault is ever exactly zero — i.e., the vault's token balance equals precisely the accumulated, uncollected `protocol_fees` + `fund_fees` + `creator_fees` for that token — then `token_1_amount as u128 * Q32 / token_0_amount` (or the symmetric expression) divides by zero and the transaction panics instead of returning a controlled `Result::Err`. No other check in `swap_base_input`/`swap_base_output`/`get_swap_params` precedes this division to reject a zero-liquidity state gracefully.

This differs from the intended, controlled error paths elsewhere in the program (e.g., `ErrorCode::ZeroTradingTokens`, `ErrorCode::InsufficientVault`), which convert edge cases into typed Anchor errors. Here the edge case instead reaches raw unchecked arithmetic.

### Impact Explanation
A Solana program panic aborts only the single transaction that triggered it, so this does not crash a long-running server the way the original PSPP CVE does. However, the practical effect is a permanent revert-only state for a specific instruction: once a pool's real (non-fee) liquidity for either token side is driven to zero, every subsequent `swap_base_input`/`swap_base_output` call against that pool will unconditionally panic at `token_price_x32`, rather than failing with a clean, catchable error. This effectively freezes the swap function for that pool (a form of permanent denial of service against a core, unprivileged, user-facing instruction) until new deposits restore a non-zero fee-excluded balance on both sides. Because `PoolState::get_status_by_bit(PoolStatusBitIndex::Swap)` gives no protection against this condition, and no code path proactively prevents the vaults from reaching an exact zero net-of-fees balance, this is a real robustness gap in a function reachable from every swap transaction.

### Likelihood Explanation
Reaching the exact zero condition requires the vault's real balance (vault amount minus uncollected protocol/fund/creator fees) to hit precisely zero for at least one token — for example, after LPs withdraw essentially all deposited liquidity while some `protocol_fees_token_*`/`fund_fees_token_*`/`creator_fees_token_*` remain uncollected and equal to the residual vault balance. This is a plausible, non-privileged sequence of ordinary operations (`deposit` → trading generating fees → `withdraw` down to minimal remaining liquidity), but it depends on precise rounding/accounting alignment between locked minimum liquidity, LP withdrawal amounts, and uncollected-fee balances, which I could not fully verify from the code available to me (I was unable to locate the `MINIMUM_LIQUIDITY`/initial LP-lock logic in `initialize.rs` in the indexed content to confirm whether a locked minimum LP balance always keeps the net-of-fee vault amount strictly above zero). Given this uncertainty about exact reachability guarantees, I rate this as a real code-level defect with plausible but not fully confirmed practical reachability.

### Recommendation
In `PoolState::token_price_x32` (and anywhere else vault-derived amounts are used as divisors), explicitly check both `token_0_amount` and `token_1_amount` are non-zero before dividing, and return a typed error (e.g., `ErrorCode::ZeroTradingTokens` or a new `ErrorCode::InsufficientLiquidity`) instead of allowing the raw division to execute. This converts an uncontrolled panic into the same graceful failure pattern already used elsewhere in the codebase (e.g., in `deposit`/`withdraw` via `ErrorCode::ZeroTradingTokens`).

### Proof of Concept
1. Initialize a pool and deposit liquidity as normal via `initialize`/`deposit`. [5](#0-4) 
2. Perform swaps so that protocol/fund/creator fees accrue in `pool_state.protocol_fees_token_0/1`, `fund_fees_token_0/1`, `creator_fees_token_0/1` (via `update_fees`). [6](#0-5) 
3. As the LP(s), call `withdraw` for all held LP tokens, driving the vault's real (fee-excluded) balance for one token down toward the residual accrued-fee amount, so `vault_amount_without_fee` returns `0` for that token. [7](#0-6) 
4. Call `swap_base_input` (or `swap_base_output`) as any unprivileged swapper. `get_swap_params` invokes `token_price_x32`, which computes `token_1_amount as u128 * Q32 / token_0_amount` with `token_0_amount == 0`, causing the transaction to abort with a Rust divide-by-zero panic instead of a handled Anchor error, and every subsequent swap attempt on this pool state fails the same way.                 .ok_or(ErrorCode::InsufficientVault)?,

    pub fn update_fees(
        &mut self,
        protocol_fee: u64,
        fund_fee: u64,
        creator_fee: u64,
        direction: TradeDirection,
    ) -> Result<()> {

            require_eq!(creator_fee, 0)
        }
        let is_creator_fee_on_input = self.is_creator_fee_on_input(direction)?;
        match direction {
            TradeDirection::ZeroForOne => {
                self.protocol_fees_token_0 = self
                    .protocol_fees_token_0
                    .checked_add(protocol_fee)
                    .unwrap();
                self.fund_fees_token_0 = self.fund_fees_token_0.checked_add(fund_fee).unwrap();

                if is_creator_fee_on_input {
                    self.creator_fees_token_0 =
                        self.creator_fees_token_0.checked_add(creator_fee).unwrap();
                } else {
                    self.creator_fees_token_1 =
                        self.creator_fees_token_1.checked_add(creator_fee).unwrap();
                }
            }
            TradeDirection::OneForZero => {
                self.protocol_fees_token_1 = self
                    .protocol_fees_token_1
                    .checked_add(protocol_fee)
                    .unwrap();

                    self.creator_fees_token_1 =
                        self.creator_fees_token_1.checked_add(creator_fee).unwrap();
                } else {
                    self.creator_fees_token_0 =
                        self.creator_fees_token_0.checked_add(creator_fee).unwrap();
                }

        };
        Ok(())

pub fn deposit(
    ctx: Context<Deposit>,
    lp_token_amount: u64,
    maximum_token_0_amount: u64,
    maximum_token_1_amount: u64,
) -> Result<()> {
    require_gt!(lp_token_amount, 0);
    let pool_id = ctx.accounts.pool_state.key();
    let pool_state = &mut ctx.accounts.pool_state.load_mut()?;
    if !pool_state.get_status_by_bit(PoolStatusBitIndex::Deposit) {
        return err!(ErrorCode::NotApproved);
    }
    let (total_token_0_amount, total_token_1_amount) = pool_state.vault_amount_without_fee(
        ctx.accounts.token_0_vault.amount,
        ctx.accounts.token_1_vault.amount,
    )?;
    let results = CurveCalculator::lp_tokens_to_trading_tokens(
        u128::from(lp_token_amount),
        u128::from(pool_state.lp_supply),
        u128::from(total_token_0_amount),
        u128::from(total_token_1_amount),
        RoundDirection::Ceiling,
    )
    .ok_or(ErrorCode::ZeroTradingTokens)?;
    if results.token_0_amount == 0 || results.token_1_amount == 0 {
        return err!(ErrorCode::ZeroTradingTokens);
    }
