### Title
No vulnerability found for this question.

### Summary
The `grant-signer-key` message hash intentionally omits `amount-ustx`/`num-cycles`/`bond-index`/`reward-cycle` because the grant is not a custody or value-bounding instrument — it only authorizes a specific `signer-manager` contract principal to register as the holder of `signer-key`. The actual STX/sBTC lock amounts are independently enforced against the caller's real, verified balance at the time of `stake`/`register-for-bond`, so no unbacked value can ever be created.

### Finding Description
The equality the question proposes — "stacking action authorized by signer key == exactly one grant signed for a bounded (staker, amount, cycle)" — is not the invariant this contract enforces, and is not needed for lock conservation.

`get-signer-grant-message-hash` binds only `{topic: "grant-authorization", signer-manager, auth-id}` [1](#0-0) . `grant-signer-key` checks this signature came from `signer-key`, marks the `(signer-key, signer-manager, auth-id)` tuple used exactly once, and then records `signer-key-grants { signer-key, signer-manager } -> true` [2](#0-1) . This grant only ever gates `register-signer`, which requires `contract-caller == signer` (the manager contract itself) [3](#0-2) . The signer is choosing to authorize one specific `signer-manager` *contract principal* to act as their operator — not authorizing a bounded stake.

Actual value movement is independently gated at each entry point on the *staker's own real balance*, not on the grant:
- `stake` calls `signer-manager-validate-stake` (the manager's policy hook) but then separately asserts `(>= total-balance amount-ustx)` against `(stx-account tx-sender)` — the caller's real locked+unlocked STX [4](#0-3) .
- `register-for-bond`/bond flows move real sBTC via `ft-transfer?`/`as-contract?` sBTC allowances, not synthetic minting.

`validate-stake!` (e.g. in `signer-manager.clar` / `test-pox-5-signer.clar`) is a *manager-controlled* policy callback the signer's own deployed contract implements; if the signer deploys or authorizes a manager whose `validate-stake!` accepts arbitrary amounts, that is the signer choosing to trust that specific contract's logic when they signed the grant for that `signer-manager` principal — this is the documented design ("signers can have members register at any time, they must use signer key grants instead of per-tx authorizations") [5](#0-4) . Regardless of how many stakers route through the manager, each one locks only their own verified STX/sBTC balance — no staker's lock is created that isn't backed by their real, checked funds.

### Impact Explanation
No STX or sBTC is minted, stolen, unlocked-without-backing, or double-counted. Every `stake`/`register-for-bond` call locks exactly the caller's own real balance, verified on-chain at call time [6](#0-5) . The grant only affects which manager contract is entitled to *register* under that signer key and to run its own membership policy — it does not custody or authorize a bounded pool of value. The "unbounded stacking volume" the question describes is unbounded exactly as intended: a signer key can back an arbitrarily large, arbitrarily composed pool of stakers, same as pox-4-style pooled stacking, with actual conservation enforced by each staker's individual balance check.

### Likelihood Explanation
Not applicable — the described behavior is by design, not exploitable to break lock conservation.

### Recommendation
No fix required for this specific claim. (If desired, documentation could be strengthened to make explicit that `grant-signer-key` conveys identity/registration authority only, and that any amount/period bounding is entirely the responsibility of the signer-manager contract's own `validate-stake!` implementation, which the signer is trusting when they sign the grant for that specific contract principal.)

### Proof of Concept
Not applicable — no violated invariant to demonstrate. A test showing many stakers using one `grant-signer-key`/`register-signer` pair to lock large aggregate STX would only confirm intended pooled-stacking behavior; it would not show any locked value lacking a real, checked STX/sBTC backing.

(define-public (grant-signer-key
        (signer-key (buff 33))
        (signer-manager principal)
        (auth-id uint)
        (signer-sig (buff 65))
    )
    (begin
        ;; ensure no reentrancy through signer-manager trait calls
        (try! (validate-no-reentrancy))

        ;; Only the signer contract itself can call this function to grant a signer key
        (asserts! (is-eq contract-caller signer-manager)
            ERR_UNAUTHORIZED_SIGNER_REGISTRATION
        )
        (asserts!
            (is-none (map-get? used-signer-key-grants {
                signer-key: signer-key,
                signer-manager: signer-manager,
                auth-id: auth-id,
            }))
            ERR_SIGNER_KEY_GRANT_USED
        )

        (asserts!
            (is-eq
                (unwrap!
                    (secp256k1-recover?
                        (get-signer-grant-message-hash signer-manager auth-id)
                        signer-sig
                    )
                    ERR_INVALID_SIGNATURE_RECOVER
                )
                signer-key
            )
            ERR_INVALID_SIGNATURE_PUBKEY
        )

        (asserts!
            (map-insert used-signer-key-grants {
                signer-key: signer-key,
                signer-manager: signer-manager,
                auth-id: auth-id,
            }
                true
            )
            ERR_SIGNER_KEY_GRANT_USED
        )

        (map-set signer-key-grants {
            signer-key: signer-key,
            signer-manager: signer-manager,

            true
        )

        (print {

;; Construct the message hash for validating a signer key grant. Unlike [get-signer-key-message-hash],
;; this message hash does not include `max-amount`, `period`, or `reward-cycle`. The topic is always `"grant-authorization"`.
;; The `pox-addr` field is optional. When `none`, it means the signer key can be used for any PoX address.
(define-read-only (get-signer-grant-message-hash
        (signer-manager principal)
        (auth-id uint)
    )
    (sha256 (concat SIP018_MSG_PREFIX
        (sha256 (unwrap-panic (to-consensus-buff? POX_5_SIGNER_DOMAIN)))
        (sha256 (unwrap-panic (to-consensus-buff? {
            topic: "grant-authorization",
            signer-manager: signer-manager,
            auth-id: auth-id,
        })))
    ))
)
