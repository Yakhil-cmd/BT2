### Title
Webhook signature verification silently disabled when `webhook_secret` is blank, allowing unauthenticated forged GitHub events to drive Shipit state (statuses, team membership, deploy sync) - (File: `lib/shipit/github_app.rb`)

### Summary
`WebhooksController` is the only externally-reachable, unauthenticated write path into the engine (no `ApiClient` token, no session, no GitHub App private key needed by the caller). Its sole defense is `verify_webhook_signature`, but that method treats "organization has no configured `webhook_secret`" as "verification passes," rather than "verification is impossible." Since the docs explicitly describe `webhook_secret` as *optional*, any Shipit installation for an organization that leaves it blank exposes `/webhooks` as a fully unauthenticated endpoint that will process attacker-forged `push`, `status`, and `membership` events as if GitHub sent them.

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App config to verify against using only an attacker-controlled field from the payload itself (`repository.owner.login`, falling back to `organization.login`): [1](#0-0) 

That selected `GitHubApp#verify_webhook_signature` implementation is: [2](#0-1) 

```
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```

The binding that should hold is: *"the organization asserted in the payload" == "the organization whose cryptographic secret actually authenticated this request."* When `webhook_secret` is absent for that organization's config (which the setup guide marks as `optional`), the method returns `true` unconditionally — it never inspects the `X-Hub-Signature` header at all. This breaks the binding entirely: any unauthenticated caller can name any configured organization in the payload and have the request accepted as authentic, with zero possession of any secret, private key, or token.

Downstream, this forged, "verified" payload is dispatched to handlers that mutate state directly from payload contents without any additional GitHub API cross-check:
- `PushHandler` triggers `stack.sync_github(expected_head_sha: params.after)` for any stack matching `repository.full_name` + branch [3](#0-2) 
- `StatusHandler` writes a `Status` record straight from attacker-supplied `sha`/`state`/`target_url`/`context` fields (as shown exercised in tests) [4](#0-3) 
- `MembershipHandler` creates/removes `Team`/`Membership` records from attacker-supplied `team`/`member`/`organization` fields [5](#0-4) 

`Status` records feed directly into `Stack#merge_status`/CI gating, which the merge queue and `continuous_deployment` consult to decide whether a commit is deployable — so a forged `status` webhook can mark an otherwise-blocked commit as CI-green, clearing the way for an unauthorized deploy/merge through the normal merge-queue/continuous-deployment machinery.

### Impact Explanation
This crosses the required boundary: an actor with **no credential of any kind** (no `ApiClient` token, no session, no webhook secret, no GitHub App key) can, for any organization configured without a `webhook_secret`, inject forged GitHub events that (a) forge CI status to unblock deploys via the merge queue/continuous deployment path, and (b) create/delete team memberships that back `Shipit.github_teams` authorization checks used elsewhere (`User#authorized?`) — i.e., escalation into `Shipit.github_teams` authorization, and an unauthorized-deploy vector, both of which meet the stated Critical/High impact bar.

### Likelihood Explanation
Requires only that at least one configured organization has `webhook_secret` unset — a state the shipped setup documentation explicitly presents as an acceptable, optional configuration (`docs/setup.md`: "Webhook secret (optional)"), with no runtime warning from the engine when this is the case. Any installation following the documented setup literally is exposed. No other precondition (no session, no token, no GitHub write access) is needed.

### Recommendation
Do not treat a missing `webhook_secret` as "trust everything." At minimum, `verify_webhook_signature` should fail closed (return `false`)/require configuration when no secret is set, or the engine should refuse to boot / loudly warn if any configured organization lacks a `webhook_secret`. Additionally, cross-check the organization used for signature selection against the organization actually referenced by the mutated resource (`repository.full_name`'s owner) rather than trusting the same attacker-controlled field for both purposes.

### Proof of Concept
For an organization configured without `webhook_secret` (permitted by `docs/setup.md`):
```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=anything-or-omitted

{
  "sha": "<victim-commit-sha>",
  "state": "success",
  "target_url": "https://attacker.example/fake-ci",
  "context": "ci/attacker",
  "repository": { "owner": { "login": "<configured-org-without-secret>" } }
}
```
`verify_signature` calls `verify_webhook_signature`, which returns `true` unconditionally (no secret configured), so the forged `status` event is processed by `StatusHandler` and persisted as a real `Status`, potentially clearing CI requirements for merge queue / continuous deployment on that commit — all without any credential.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
