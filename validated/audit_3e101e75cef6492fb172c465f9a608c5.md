Based on my research, I found a concrete brute-force-detection analog in the pairing subsystem, but I should be direct about its limitations before presenting it.

The Keycloak CVE is about **CWE-307 (Improper Restriction of Excessive Authentication Attempts)** — a secret-based check with no lockout/throttle after repeated failures. The closest reachable analog in ocore is the device **pairing_secret** verification in `device.js`, which is invoked from a subject that is explicitly whitelisted for messages from unknown/unpaired devices.

### Title
Improper Restriction of Excessive Pairing-Secret Verification Attempts Enables Device Pairing Hijack - (File: device.js)

### Summary
`handlePairingMessage()` in `device.js` verifies an attacker-supplied `pairing_secret` against the `pairing_secrets` table with no attempt counter, throttling, or lockout, and this code path is reachable from any unpaired/unknown device via the hub, since `"pairing"` is one of the subjects explicitly allowed from non-correspondents.

### Finding Description
A pairing code (`device_pubkey@hub#pairing_secret`) is generated by `startWaitingForPairing()`/`getOrGeneratePermanentPairingInfo()` and normally shared out-of-band (QR code, contract invite, arbiter dispute flow) to establish a trusted correspondent relationship between two devices, including for shared/multisig wallet setup (`arbiter_contract.js` embeds `my_pairing_code` built from this same secret at [1](#0-0) ).

Any device can send an unsolicited `"pairing"` `hub/message` with a guessed `pairing_secret`. This is processed even though the sender is not a known correspondent, because `"pairing"` is in the list of subjects allowed from non-correspondents: [2](#0-1) 

`handlePairingMessage` then performs a single, unthrottled DB lookup of the guessed secret with no per-secret attempt counter, no exponential backoff, and no lockout after repeated failures: [3](#0-2) 

If the guess matches (including the case where a permanent pairing secret is explicitly set to the wildcard value `'*'`, matched via `pairing_secret IN(?,'*')`), the attacker's device is unconditionally inserted/confirmed as a correspondent device and the "paired" event fires, deleting the one-time secret so no legitimate party can complete pairing afterward: [4](#0-3) 

This mirrors the Keycloak flaw's root cause: the verification of an out-of-band shared secret has no protective mechanism against repeated automated attempts, so an attacker who can send messages through a hub (an unprivileged, network-reachable capability) can attempt unlimited guesses.

### Impact Explanation
If an attacker races/guesses a still-pending `pairing_secret` before the intended party pairs, they become the "correspondent device" for that secret instead of the legitimate participant. Because pairing codes are also used to bootstrap shared/multisig address setup and arbiter-contract cosigner relationships (`arbiter_contract.js` `createAndSend`/`openDispute`/`appeal` all embed pairing codes), hijacking a pending pairing can let an attacker insert themselves into a wallet/contract negotiation flow intended for someone else, and the one-time secret is deleted on first use, permanently locking out the legitimate device from completing the intended pairing.

### Likelihood Explanation
The one-time `pairing_secret` is generated with `crypto.randomBytes(9)` (72 bits of entropy), so brute-forcing a single random secret directly is not practically feasible with current entropy — this materially limits real-world exploitability compared to the Keycloak TOTP case (which had a small, human-typable keyspace). The lack of any throttling/lockout mechanism is nonetheless a genuine CWE-307 instance and becomes higher-risk if a permanent/wildcard (`'*'`) secret is ever configured, or if the secret space is otherwise narrowed (e.g., low-entropy custom hubs, replay of leaked-but-partial codes, or future secret formats).

### Recommendation
Add attempt tracking/throttling per sending device or per pairing_secret attempt (e.g., rate-limit `"pairing"` messages from a given device_address/IP, and lock out or invalidate a pairing secret after N failed match attempts within a time window), and avoid supporting a literal wildcard (`'*'`) match value for `is_permanent` pairing secrets.

### Proof of Concept
1. Device A calls `startWaitingForPairing()`, generating a `pairing_secret` and displaying a pairing code intended for Device B.
2. Before Device B pairs, an attacker device sends a `hub/message` with `subject: "pairing"` and a guessed `pairing_secret` value directly to Device A via the hub (`sendPairingMessage`/`handlePairingMessage` path); this is accepted because `"pairing"` bypasses the known-correspondent check.
3. `handlePairingMessage` performs the lookup with no attempt limiting; the attacker can repeat step 2 with different guesses indefinitely.
4. On a match, the attacker's device is confirmed as Device A's correspondent and the one-time secret is deleted, preventing Device B from ever completing the intended pairing. [5](#0-4)

function getOrGeneratePermanentPairingInfo(handlePairingInfo){
	db.query("SELECT pairing_secret FROM pairing_secrets WHERE is_permanent=1 ORDER BY expiry_date DESC LIMIT 1", [], function(rows){
		var pairing_secret;
		if (rows.length) {
			pairing_secret = rows[0].pairing_secret;
		} else {
			pairing_secret = crypto.randomBytes(9).toString("base64");

function handlePairingMessage(json, device_pubkey, callbacks){
	var body = json.body;
	var from_address = objectHash.getDeviceAddress(device_pubkey);
	if (!ValidationUtils.isNonemptyString(body.pairing_secret))
		return callbacks.ifError("correspondent not known and no pairing secret");
	if (!ValidationUtils.isNonemptyString(json.device_hub)) // home hub of the sender
		return callbacks.ifError("no device_hub when pairing");
	if (json.device_hub.length > 200)
		return callbacks.ifError("device_hub too long");
	if (!network.isValidWsUrl(conf.WS_PROTOCOL + json.device_hub))
		return callbacks.ifError("invalid device_hub URL");
	if (!ValidationUtils.isNonemptyString(body.device_name))
		return callbacks.ifError("no device_name when pairing");
	if (body.device_name.length > 100)
		return callbacks.ifError("device_name too long");
	if ("reverse_pairing_secret" in body && !ValidationUtils.isNonemptyString(body.reverse_pairing_secret))
		return callbacks.ifError("bad reverse pairing secret");
	eventBus.emit("pairing_attempt", from_address, body.pairing_secret);
	db.query(
		"SELECT is_permanent FROM pairing_secrets WHERE pairing_secret IN(?,'*') AND expiry_date>"+db.getNow()+" ORDER BY (pairing_secret=?) DESC LIMIT 1", 
		[body.pairing_secret, body.pairing_secret], 
		function(pairing_rows){
			if (pairing_rows.length === 0)
				return callbacks.ifError("pairing secret not found or expired");
			// add new correspondent and delete pending pairing
			var safe_device_name = body.device_name.replace(/<[^>]*>?/g, '');
			db.query(
				"INSERT "+db.getIgnore()+" INTO correspondent_devices (device_address, pubkey, hub, name, is_confirmed) VALUES (?,?,?,?,1)", 
				[from_address, device_pubkey, json.device_hub, safe_device_name],
				function(){
					db.query( // don't update name if already confirmed
						"UPDATE correspondent_devices SET is_confirmed=1, name=? WHERE device_address=? AND is_confirmed=0", 
						[safe_device_name, from_address],
						function(){
							db.query("UPDATE correspondent_devices SET is_blackhole=0 WHERE device_address=?", [from_address], function(){
								eventBus.emit("paired", from_address, body.pairing_secret);
								if (pairing_rows[0].is_permanent === 0){ // multiple peers can pair through permanent secret
									db.query("DELETE FROM pairing_secrets WHERE pairing_secret=?", [body.pairing_secret], function(){});
									eventBus.emit('paired_by_secret-'+body.pairing_secret, from_address);
								}
								if (body.reverse_pairing_secret)
									sendPairingMessage(json.device_hub, device_pubkey, body.reverse_pairing_secret, null);
								callbacks.ifOk();
							});
						}
					);
				}
			);
		}
	);
