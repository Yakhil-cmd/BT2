### Title
Uncaught exception in `definition template` authentifier evaluation crashes the validating node - (File: definition.js)

### Summary
`CVE-2016-9804` describes a crash caused by processing attacker-supplied data without adequate boundary/validity checks in a parsing routine (`commands_dump`/`csr.c`), leading to an application crash on corrupted input. In `ocore`, `definition.js`'s `validateAuthentifiers()` contains an analogous pattern: a code path that evaluates a `definition template` operator inside an address definition performs a DB lookup and then unconditionally `throw`s inside an asynchronous callback if the lookup does not return exactly one row, instead of returning a validation error through the normal `cb2` error-handling channel.

### Finding Description
When validating signatures/authentifiers for a unit's author (`validateAuthentifiers`), the `evaluate()` function processes each op in the address definition tree. For the `definition template` op: [1](#0-0)

If an attacker crafts an address definition containing `['definition template', [<some_unit_hash>, {...}]]` where `<some_unit_hash>` does not correspond to a stable, sequence-good `definition_template` message (e.g., a non-existent unit, or a unit that isn't a `definition_template` app message, or one not yet stable), the query returns `0` rows and the callback executes `throw Error("not 1 template")`. Because this throw occurs inside an asynchronous `conn.query` callback, it is not caught by any surrounding `try/catch` in the calling chain (`validateAuthentifiers` → `validate()` in `validation.js`), and propagates as an uncaught exception. `network.js` installs a global `uncaughtException` handler that deliberately re-throws to crash the process: [2](#0-1) 
```
process.on('uncaughtException', (err) => {
	console.log('Uncaught exception:', err);
	...
	throw err; // crash the process to avoid ending up in an inconsistent state
});
```
This mirrors the CVE's root cause class: absence of proper bounds/condition checking on attacker-influenced data before performing an operation that the process cannot safely recover from, resulting in a crash when processing untrusted input.

The `evaluate()` function that reaches this code is invoked for every unit whose author uses (directly or via nested `address`/co-signing references) an address definition containing this op, via `validateAuthentifiers` in `definition.js`, called from `validateAuthor` during standard unit validation: [3](#0-2) 

### Impact Explanation
Any node that validates a unit signed by an address whose definition contains a `definition template` op referencing an invalid/unresolved template unit will crash with an uncaught exception. Since address definitions are attacker-controlled content included directly in posted units (new address definition change, or inline `author.definition`), and validation of authors/authentifiers happens for every full/light node processing the unit, this is a low-effort, repeatable remote crash of any node (hub, witness, or full node) that receives and validates the malicious unit — a denial of service that can prevent the network from confirming new units from affected nodes (`A:L`, no confidentiality/integrity impact — matching the CVSS vector of the source CVE).

### Likelihood Explanation
High. Creating an address definition with an invalid `definition template` reference requires no special privilege — any unit poster can define such an address and get it validated by triggering authentifier verification (e.g., signing a message from that address, or referencing it via `address`/`cosigned by`/nested definitions in a subsequently posted unit). The structural validation performed by `validateDefinition()` accepts `definition template` args syntactically without confirming template existence ahead of time (that check happens only at authentifier-evaluation time in `validateAuthentifiers`), so the crash-triggering unit can pass structural validation and reach the vulnerable code deterministically.

### Recommendation
In `definition.js`, replace the `throw Error("not 1 template")` inside the `definition template` case of `validateAuthentifiers`'s `evaluate()` (and the similar throw in `validateDefinition`'s handling, if applicable) with a call to `cb2(false)` (treating an unresolved/ambiguous template as authentication failure) instead of throwing, consistent with how other error conditions in this function are handled (e.g., the `catch` block around `arrDefiningAuthors` filtering at line 789-791 in the `address` case). Ensure all `conn.query` callbacks inside `evaluate()` funnel unexpected conditions through the `cb2`/error-callback mechanism rather than throwing synchronously inside an async callback.

### Proof of Concept
1. Attacker crafts a new address `A` whose definition includes: `['definition template', ['ZZZZZZZZZZZZZZZZZZZZZZZZZZZZZZZZZZZZZZZZZZ=', {}]]` (a syntactically valid but non-existent/never-stabilized unit hash, or a unit hash that exists but is not a stable `definition_template` message).
2. This definition passes structural checks in `validateDefinition()` (`definition.js`, lines around 802+ in the sibling function) since only `args[0]`/`args[1]` shape is checked there.
3. Attacker posts (or gets a co-signer/wallet to post) any unit authored by address `A` (or referencing `A` via `address`/`cosigned by` inside another definition) with a valid signature placeholder.
4. When any node validates this unit, `validateAuthentifiers()` reaches the `definition template` case, issues the `conn.query`, gets `rows.length === 0`, and executes `throw Error("not 1 template")` inside the async callback.
5. The uncaught exception is caught by the process-level `uncaughtException` handler in `network.js`, which re-throws it and crashes the node process, denying service and preventing that node from continuing to validate/confirm units until restarted. [4](#0-3) [2](#0-1)
