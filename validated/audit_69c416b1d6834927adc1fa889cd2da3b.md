### Title
Cross-organization team ID collision in `find_or_create_team!` allows attacker's own webhook to add members to another organization's privileged `Team` - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#find_or_create_team!` looks up a `Team` solely by `github_id` via `Team.find_or_create_by!(github_id: params.team.id)`, with no check that the `organization` on the fetched record matches `params.organization.login` from the verified webhook payload. Because `verify_signature` in `WebhooksController` only proves the payload came from *some* organization's own webhook secret (looked up by `repository_owner`/`organization.login`), an attacker who controls an org with a colliding numeric team id can get `add_member` invoked on an existing `Team` row belonging to a different, victim organization.

### Finding Description
The broken binding: `team.organization == params.organization.login` must hold for the team object on which `add_member` executes, given that `params.organization.login` is the organization whose `webhook_secret` produced a valid `X-Hub-Signature` in `verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`). This binding is never enforced.

Path:
1. `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) resolves `github_app = Shipit.github(organization: repository_owner)` using `params.dig('organization','login')` as fallback (line 61), then verifies HMAC using that organization's own configured secret. For a `membership` event with no `repository` key, `repository_owner` resolves to `params['organization']['login']` — i.e., the attacker's own org, `attacker-org`. Signing with attacker-org's own legitimately-configured `webhook_secret` passes verification trivially.
2. `MembershipHandler#process` (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-34`) calls `find_or_create_team!`.
3. `find_or_create_team!` (lines 38-43) executes `Team.find_or_create_by!(github_id: params.team.id)`. `github_id` is not scoped by organization anywhere in `Team` (`app/models/shipit/team.rb`) — there is no uniqueness validation combining `organization` + `github_id`, and the lookup itself is keyed only on `github_id`.
4. If a `Team` row already exists with that numeric `github_id` (the victim-org's privileged team, already referenced by `Shipit.github_teams`), `find_or_create_by!` returns the **existing** record without executing the block that sets `team.organization = params.organization.login`. The victim's `Team#organization` field is left untouched — but it's also never checked against `params.organization.login`.
5. Back in `#process`, `team.add_member(member)` (line 28) appends `User.find_or_create_by_login!(params.member.login)` — the attacker's own GitHub login — as a member of the victim org's `Team` record.

No downstream guard exists: `drop_unhandled_event` only checks the event type is handled; the `ExplicitParameters` schema only validates payload shape, not organization identity; there is no `require_permission!` or organization-equality check anywhere in this call path.

### Impact Explanation
The attacker (who administers their own org and its Shipit-configured webhook secret, but holds no privilege in the victim org) can insert themselves as a member of a `Team` record that Shipit treats as authoritative for authorization purposes wherever `Shipit.github_teams` / team membership gates access (e.g., `User#authorized?`, stack access, deploy permissions per `app/controllers/concerns/shipit/authentication.rb` and `lib/shipit.rb`). This is a direct escalation into `Shipit.github_teams` authorization for a victim org's privileged team using only an attacker-owned org's webhook — matching the High-severity category defined in scope. The attack is repeatable for any pre-existing `Team` row whose `github_id` happens to collide with a team the attacker creates in their own org (GitHub team ids are org-scoped, so collisions across orgs are a real possibility, especially for low, early-allocated numeric ids).

### Likelihood Explanation
Preconditions: (a) attacker must own/administer an org already configured in Shipit with its own `webhook_secret` — a legitimate, low-cost setup step for anyone whose org is onboarded; (b) a `Team` row for the victim org must already exist with a `github_id` that collides with a team id the attacker can create in their own org. Team ids are assigned sequentially per-org by GitHub, so for orgs created early or with few teams, collision is plausible/discoverable by iterating ids. No GitHub or Shipit secret beyond the attacker's own is required. The attack requires only sending one crafted, correctly-signed HTTP webhook — trivial once the org is Shipit-registered and the colliding id is found.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup/creation by both `github_id` and `organization`, and reject (or log/skip) if an existing `Team` with that `github_id` belongs to a different organization than `params.organization.login`:
```ruby
def find_or_create_team!
  team = Team.find_by(github_id: params.team.id)
  if team && team.organization != params.organization.login
    raise ArgumentError, "Team github_id #{params.team.id} belongs to a different organization"
  end
  Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login) do |t|
    t.github_team = params.team
  end
end
```
Additionally, add a database/model-level uniqueness constraint on `(github_id, organization)` (or globally reconsider whether `github_id` should be namespaced by organization) in `Team`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/membership_handler_test.rb (conceptual)
test "membership webhook from attacker-org cannot add member to victim-org's team via colliding github_id" do
  victim_team = Shipit::Team.create!(github_id: 42, organization: 'victim-org', name: 'admins', slug: 'admins', api_url: 'https://api.github.com/teams/42')

  payload = {
    'action' => 'added',
    'team' => { 'id' => 42, 'name' => 'admins', 'slug' => 'admins', 'url' => 'https://api.github.com/teams/42' },
    'organization' => { 'login' => 'attacker-org' },
    'member' => { 'login' => 'attacker' }
  }

  Shipit::Webhooks::Handlers::MembershipHandler.new(payload).process

  attacker = Shipit::User.find_by(login: 'attacker')
  # Binding under test: team.organization == params.organization.login must hold before add_member
  assert_not victim_team.reload.members.include?(attacker),
    "attacker from attacker-org must not be added to victim-org's Team via github_id collision"
end
```
This demonstrates that with the current code, `victim_team.members` would include the attacker's user record after processing a webhook signed only with `attacker-org`'s own secret, confirming the missing organization-equality check.
