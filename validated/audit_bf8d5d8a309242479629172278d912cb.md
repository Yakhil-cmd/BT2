## Title
`provision?` disjunct precedence ignores `review_stacks_enabled` for `prevent_with_label`/`allow_with_label` behaviors, letting unauthenticated PR openers create stacks on repos where review stacks are disabled - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::PullRequest::OpenedHandler#provision?` combines `repository.review_stacks_enabled` with `provisioning_behavior_allow_all?` using `&&`, but the two following disjuncts (`allow_with_label?` and `prevent_with_label?`) are combined with `||` and are never ANDed with `review_stacks_enabled`. Because Ruby's `&&` binds tighter than `||`, this makes `review_stacks_enabled` a no-op for the `prevent_with_label` and `allow_with_label` behaviors, so a `prevent_with_label` repo with `review_stacks_enabled: false` and no `provisioning_label_name` configured will still auto-provision a review stack for every PR opened with an empty/no matching label array.

### Finding Description
Binding claimed by the operator: `repository.review_stacks_enabled == false` should gate stack creation for **every** PR on that repository, regardless of `provisioning_behavior`.

Actual code, `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb:65-70`:
```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
``` [1](#0-0) 

Due to Ruby operator precedence, this parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`. `review_stacks_enabled` is scoped only to the first disjunct. If `provisioning_behavior == "prevent_with_label"`, the third disjunct alone determines the result and is entirely independent of `review_stacks_enabled`.

`pull_request_has_provisioning_label?` is `pull_request_label_names.include?(repository.provisioning_label_name)` [2](#0-1) . If `provisioning_label_name` is `nil` (default/unconfigured), and the incoming `labels` array is empty (a normal, valid payload satisfying `requires :labels, Array` from the params schema at lines 29-31), then `[].include?(nil)` is `false`, so `pull_request_has_provisioning_label?` is `false`, and `!false` is `true` — the third disjunct evaluates to `true` unconditionally.

Attack: an unprivileged GitHub user opens a PR against a repository configured with `provisioning_behavior: prevent_with_label`, `review_stacks_enabled: false`, `provisioning_label_name: nil`, with no labels attached (the default state of any freshly opened PR). `respond_to_pull_request_opened?` returns `true` [3](#0-2) , and `process` calls `ReviewStackAdapter#find_or_create!`, which unconditionally creates a `Shipit::ReviewStack`, its `PullRequest` record, and enqueues it for provisioning [4](#0-3) .

No other guard intercepts this: webhook signature verification only authenticates that the payload came from GitHub for *that* repository (not that stack creation logic honors the operator's `review_stacks_enabled` toggle), and `ExplicitParameters` only validates payload shape, not business-logic gating. The repository model itself imposes no constraint tying `review_stacks_enabled` to `provisioning_behavior_prevent_with_label?`/`allow_with_label?` [5](#0-4) .

### Impact Explanation
Any PR opener on a `prevent_with_label` (or, symmetrically, an `allow_with_label` with a label they can attach themselves) repository can force Shipit to create an unauthorized `ReviewStack`, its associated `PullRequest`, and queue provisioning — a "record written for a repository that did not authenticate it" via a config path the operator explicitly disabled. Because `review_stacks_enabled: false` is meant to be a hard off-switch for automatic stack provisioning, this is a logic bypass of that safety control across every PR on the affected repository (default outcome, not a corner case), matching the "unauthorized ... stack" Critical impact category. It is fully repeatable against any repository sharing this configuration.

### Likelihood Explanation
Preconditions: repository must have `provisioning_behavior: prevent_with_label` and `provisioning_label_name` unset/`nil` (a plausible default/misconfiguration state, since `provisioning_label_name` has no presence validation forcing it to be set when `prevent_with_label` is chosen) combined with `review_stacks_enabled: false`. No test fixture in the repo currently exercises this exact combination — the existing test `"create stacks for repos what prevent_with_label when label is absent"` uses `provisioning_enabled: true` (default) [6](#0-5) , so the `review_stacks_enabled: false` case is untested and the precedence bug is unguarded. Attacker cost is zero beyond opening a PR (or, for `allow_with_label`, additionally applying a label to their own PR, which any PR author can do). This is deterministic and repeatable on every PR against a matching repository.

### Recommendation
Fix operator precedence so `review_stacks_enabled` gates all three behaviors, e.g.:
```ruby
def provision?
  return false unless repository.review_stacks_enabled

  repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```
Add explicit parentheses/tests for all three behaviors combined with `review_stacks_enabled: false` to prevent regression.

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`, add:
```ruby
test "does not create stacks for prevent_with_label repos when review_stacks_enabled is false" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :prevent_with_label,
    label: nil
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = []

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Binding assertion: before fix, `repository.review_stacks_enabled == false` yet `Shipit::Stack.count` still increments (test fails), demonstrating `review_stacks_enabled` is not honored; after the recommended fix, the assertion `assert_no_difference` passes, restoring the equality between the operator's setting and actual stack-creation behavior.
