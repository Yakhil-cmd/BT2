### Title
AA bounce path can permanently strand refunded asset funds when the recipient is blocked by a `transfer_condition` - (File: aa_composer.js)

### Summary
The Moloch bug is about tribute tokens not being returned to the proposer if the refund transfer path is skipped/blocked. The Obyte analog is in the Autonomous Agent (AA) engine's bounce mechanism: when an AA rejects/bounces a trigger and tries to refund the sent asset back to the trigger address, the refund is itself a normal asset payment output subject to the asset's `transfer_condition`. If that condition denies the trigger address as a recipient (e.g., an attestation/whitelist condition), the refund unit fails validation, and the code has no further fallback — the funds stay trapped in the AA rather than reaching the original sender.

### Finding Description
When an AA trigger is rejected, `bounce()` composes payment messages that send the received asset (minus bounce fees) back to `trigger.address` and calls `sendUnit(messages)`: [1](#0-0) 

`sendUnit()` builds the payment payload for that asset via `completePaymentPayload`, and the resulting unit is checked by `validateAndSaveUnit`, which runs full unit validation — including any asset `transfer_condition` evaluation — before the unit is saved: [2](#0-1) 

If that validation fails (for example the asset's `transfer_condition` rejects `trigger.address` as an output recipient, mirrored by `validatePaymentInputsAndOutputs`'s condition check in `validation.js`), `sendUnit` calls `bounce(err)` again: [3](#0-2) 

But `bounce()` guards against recursion with the `bBouncing` flag: once already bouncing, a second call to `bounce()` just calls `finish(null)` and stops, without retrying with a different recipient or otherwise recovering the funds: [4](#0-3) 

Because the original trigger already delivered the tribute/asset amount into the AA's balance (that's how AAs receive funds — via unit outputs, not pull calls), and the refund attempt failed validation, the asset remains held by the AA with no completed response unit returning it. There is no pull-based/claim mechanism in the AA composer for the original sender to later retrieve the stuck balance — it is architecturally analogous to the Moloch case where tribute tokens become effectively owned by the DAO body (here, the AA's own state/balance) instead of returning to the proposer, requiring off-chain/administrative coordination through another AA execution or admin intervention to be released.

### Impact Explanation
This causes AA fund freezing: user assets sent into an AA as part of a proposal/trigger that gets rejected can become permanently stuck in the AA's balance when the specific asset in use enforces a `transfer_condition` that blocks the refund recipient (a legitimate feature of Obyte's asset system, e.g. attestor-gated or address-gated assets). This is not a hypothetical edge case — any AA author who accepts an asset with a `transfer_condition` for triggers and attempts to refund on bounce is exposed. Because the failure recurses into `bounce()` a second time and is swallowed via the `bBouncing` guard, no explicit error surfaces to alert operators that the refund silently failed to reach the user; the unit is finished with `finish(null)`, and the deposited funds remain locked in the AA's tracked balance without any programmatic path back to the sender.

### Likelihood Explanation
Likelihood is medium: it requires (1) an AA designed to accept and conditionally refund an asset that has a `transfer_condition`, and (2) a trigger address that fails that condition at the time of bounce (e.g. it lost an attestation or was blacklisted between sending the trigger and the bounce). This is a realistic scenario for AAs handling any restricted/whitelisted asset (KYC tokens, attestor-gated shares, etc.), which are supported first-class features of `assets` in ocore, not exotic misuse.

### Recommendation
- In `bounce()`/`sendUnit()`, when a bounce-refund unit fails due to output-side asset condition failure, avoid silently discarding the refund: consider retrying with an alternate recipient address supplied by the AA definition, emitting a distinguishable error/log that state clearly indicates stuck balance, or exposing the failed refund as AA state so the AA's own logic (or a follow-up trigger) can attempt recovery.
- Document for AA authors that refunding assets with `transfer_condition` during `bounce` is not guaranteed to succeed, and that AAs accepting such assets should implement their own pull-style recovery/state-tracked claim mechanism instead of relying on the built-in bounce refund.

### Proof of Concept
1. Define an asset with a `transfer_condition` that only allows outputs to addresses satisfying a certain attestation (`Definition.evaluateAssetCondition` path in `validation.js` L2643-2657).
2. Deploy an AA whose `bounce_fees` are denominated in that asset and whose logic can bounce (e.g. reject invalid triggers), relying on the AA engine's built-in bounce refund in `aa_composer.js` `bounce()` (L909-944).
3. Send a trigger from an address `A` holding the attestation, transferring the conditioned asset into the AA.
4. Before the trigger is processed (or in the same block context), have `A` lose the attestation required by the `transfer_condition` (e.g., attestor revokes/re-attests differently), so `A` no longer satisfies the condition.
5. Have the AA bounce the trigger. `sendUnit` composes the refund payment to `trigger.address = A`; `validateAndSaveUnit`/`validatePaymentInputsAndOutputs` rejects the output because the `transfer_condition` is not satisfied (L2643-2657 in `validation.js`).
6. `sendUnit`'s error handler calls `bounce(err)` again; since `bBouncing` is already `true`, `bounce()` immediately calls `finish(null)` (L909-925 in `aa_composer.js`), so no refund unit is produced and the asset balance remains inside the AA with no path back to `A`.
