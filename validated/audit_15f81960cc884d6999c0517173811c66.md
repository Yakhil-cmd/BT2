### Title
Webhook signature verification is bound to `repository.owner.login` while write actions are dispatched based on the unrelated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In a multi-organization Shipit deployment (`secrets.github` keyed by organization, see `github_app_config`), `WebhooksController#verify_signature` selects the HMAC secret to validate the request against based on `repository.owner.login` (or `organization.login`), but every webhook handler that performs a write (finds the `Stack`/`Repository` to sync, archive, unarchive, or update) does so using the completely independent `repository.full_name` field, with no cross-check that the two agree.

### Finding Description
`WebhooksController#verify_signature` computes the organization used to select the `GitHubApp` (and thus the webhook secret) purely from attacker-controlled JSON fields in the raw POST body: [1](#0-0) [2](#0-1) 

Meanwhile, `Shipit::Webhooks::Handlers::Handler#repository_name` (used by `PushHandler` and inherited/duplicated by every `PullRequest::*Handler`) resolves the repository/stack to act on from a *different* JSON field, `repository.full_name`: [3](#0-2) [4](#0-3) 

`Shipit.github(organization:)` looks up per-organization config (`secrets.github` keyed by lowercase org name) to obtain that organization's `webhook_secret`: [5](#0-4) 

Because the HMAC signature is verified against the *whole raw body* using the secret selected by `repository.owner.login`, an attacker who legitimately controls their own GitHub organization (and therefore legitimately knows that organization's own `webhook_secret`, configured by the Shipit operator for that org) can craft an arbitrary raw JSON payload, set `repository.owner.login` to their own org (so `verify_signature` picks their own valid secret and the HMAC check passes), while setting `repository.full_name` to `"VictimOrg/victim-repo"` — a repository belonging to a different organization onboarded to the same Shipit instance. The signature check never inspects `full_name`, so nothing ties the verified organization to the repository that the handler subsequently acts on.

This breaks the equality that should hold: *the organization whose secret authenticated the request* == *the repository that gets written to*. It is the "organization authenticated vs. repository written" trust binding called out in scope.

### Impact Explanation
This allows cross-repository/cross-organization writes on the shared Shipit instance: an attacker who is a legitimate member of one onboarded organization (with a valid, self-known webhook secret) can trigger `push` webhook handling (`PushHandler#process` → `stack.sync_github`) or Pull-Request webhook handling (open/close/label/archive/unarchive review stacks) against stacks belonging to a completely different organization's repository, without ever possessing that organization's webhook secret. Depending on which handler is exercised, this can cause unauthorized `GithubSyncJob` enqueuing, unwanted review-stack provisioning/deprovisioning, or forced archive/unarchive of another org's stacks — i.e., an unauthorized deploy-adjacent action across organizational trust boundaries, matching the required "cross-repository writes" impact class.

### Likelihood Explanation
Requires the Shipit instance to be configured with multiple organizations sharing the same webhook endpoint (the multi-org config path via `github_app_config`), and requires the attacker to control (or have configured) a GitHub App/webhook secret for at least one of those organizations — a realistic setup for shared/multi-tenant Shipit deployments. No GitHub-side signature forgery is needed; the attacker crafts the raw HTTP POST directly since they hold a valid secret for one org.

### Recommendation
In `WebhooksController#verify_signature`, after HMAC verification succeeds, additionally verify that the organization used to select the webhook secret matches the owner of `repository.full_name` (or reject payloads where `repository.owner.login` and the org-prefix of `repository.full_name` disagree). Handlers should also validate that the repository resolved via `full_name` belongs to the same organization that authenticated the webhook, rather than trusting `full_name` unconditionally.

### Proof of Concept
1. Shipit is configured with two organizations, `AttackerOrg` (attacker is an authorized member, knows `webhook_secret_A`) and `VictimOrg` (unrelated, uses `webhook_secret_V`), both onboarded per `docs/setup.md`'s multi-org `secrets.github` schema.
2. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "AttackerOrg" },
    "full_name": "VictimOrg/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(webhook_secret_A, body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "AttackerOrg")`, gets `webhook_secret_A`, and the signature verifies successfully.
5. `PushHandler#process` resolves `repository_name` from `repository.full_name` = `"VictimOrg/victim-repo"`, finds the corresponding `Stack`, and calls `stack.sync_github(expected_head_sha: params.after)` — an action on `VictimOrg`'s stack the attacker never authenticated for.

Note: full validation of this PoC end-to-end (e.g., confirming there is no additional, unindexed cross-check elsewhere in the request pipeline) was limited by the codebase index; a Devin session with full repository access could confirm no additional guard exists before treating this as fully verified in production.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
