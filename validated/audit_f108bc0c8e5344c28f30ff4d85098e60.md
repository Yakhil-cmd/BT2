### Title
KAIA Excess Fee Refund Hardcoded to `msg.sender` Causes Loss of Bridged Assets When Called by Smart Contracts — (`contracts/service_chain/bridge/BridgeFee.sol`)

---

### Summary

`BridgeFee._payKLAYFeeAndRefundChange` unconditionally sends the excess KLAY fee refund to `msg.sender`. When a smart contract calls `requestKLAYTransfer`, `msg.sender` is the calling contract, not the original user who funded the transaction. This causes the excess KAIA to be permanently trapped in a non-payable contract, or silently diverted to a payable contract that has no mechanism to forward it to the original user. The ERC20 path in the same contract correctly accepts an explicit `from` address for refunds, confirming the design intent is to refund the actual originating user — making the KLAY path's use of `msg.sender` an inconsistency with a real asset-loss impact.

---

### Finding Description

`BridgeFee._payKLAYFeeAndRefundChange` is called by `BridgeTransferKLAY._requestKLAYTransfer`, which is invoked by both `requestKLAYTransfer` and the fallback function. Both entry points are `external payable` with no restriction on caller type.

```solidity
// BridgeFee.sol lines 43-66
function _payKLAYFeeAndRefundChange(uint256 _feeLimit) internal returns(uint256) {
    uint256 fee = feeOfKLAY;

    if (feeReceiver != address(0) && fee > 0) {
        require(_feeLimit >= fee, "insufficient feeLimit");
        (bool ok, ) = feeReceiver.call.value(fee)("");
        require(ok, "transfer fee failed");

        uint256 feeRefund = _feeLimit.sub(fee);
        if (feeRefund > 0) {
            (bool ok, ) = msg.sender.call.value(feeRefund)("");  // ← always msg.sender
            require(ok, "refund fee failed");
        }
        return fee;
    }

    if (_feeLimit > 0) {
        (bool ok, ) = msg.sender.call.value(_feeLimit)("");  // ← always msg.sender
        require(ok, "refund fee failed");
    }
    return 0;
}

When a smart contract calls `requestKLAYTransfer` with `msg.value > _value + feeOfKLAY` (i.e., with excess fee):

- **Scenario A — calling contract is non-payable:** `msg.sender.call.value(feeRefund)("")` returns `ok = false`, triggering `require(ok, "refund fee failed")`. The entire transaction reverts. The bridge is completely unusable for any contract caller that cannot receive ETH, even though the bridge transfer itself would have been valid.

- **Scenario B — calling contract is payable:** The excess KAIA is sent to the calling contract. The original user who funded the transaction (e.g., via a multisig, a DeFi aggregator, or a proxy) never receives the refund. The KAIA is permanently diverted to the intermediary contract with no recovery path.

---

### Impact Explanation

**Scenario A (DoS):** Any smart contract that cannot receive ETH is permanently blocked from using `requestKLAYTransfer` whenever `feeLimit > feeOfKLAY`. This includes common patterns like Gnosis Safe multisigs (which reject plain ETH transfers), proxy contracts, and DeFi protocols. The bridge transfer is valid but the refund revert prevents it.

**Scenario B (KAIA loss):** When a payable intermediary contract calls `requestKLAYTransfer`, the excess KAIA fee refund is sent to the contract, not the original user. The user permanently loses the excess KAIA. This matches the Allowed Impact Gate criterion: *unauthorized fee charge affecting KAIA*.

The ERC20 path's use of an explicit `from` parameter demonstrates the system's design intent is to refund the originating user. The KLAY path's deviation from this pattern is the root cause.

---

### Likelihood Explanation

Any smart contract integration with the Kaia service-chain bridge triggers this. Multisig wallets, DeFi protocols, and bridge aggregators are common callers. The trigger requires only that the caller sends `msg.value` slightly above `_value + feeOfKLAY` — a natural occurrence when the caller does not know the exact fee in advance or when the fee changes between estimation and execution.

---

### Recommendation

Mirror the ERC20 pattern: add an explicit `refundAddress` parameter to `_payKLAYFeeAndRefundChange` and thread it through `_requestKLAYTransfer` and `requestKLAYTransfer`:

```solidity
// BridgeFee.sol
function _payKLAYFeeAndRefundChange(address refundAddress, uint256 _feeLimit) internal returns(uint256) {
    ...
    (bool ok, ) = refundAddress.call.value(feeRefund)("");
    ...
}

// BridgeTransferKLAY.sol
function _requestKLAYTransfer(address _to, address _refundAddress, uint256 _feeLimit, bytes memory _extraData) internal ... {
    uint256 fee = _payKLAYFeeAndRefundChange(_refundAddress, _feeLimit);
    ...
}

function requestKLAYTransfer(address _to, uint256 _value, address _refundAddress, bytes calldata _extraData) external payable {
    uint256 feeLimit = msg.value.sub(_value);
    _requestKLAYTransfer(_to, _refundAddress, feeLimit, _extraData);
}
```

This allows a contract caller to specify the EOA that should receive the refund, exactly as PoolTogether fixed the analogous issue.

### Proof of Concept

1. Deploy `Bridge.sol` with `feeOfKLAY = 400` and a non-zero `feeReceiver`.
2. Deploy an attacker contract `Caller` with no `receive()` function.
3. `Caller` calls `bridge.requestKLAYTransfer{value: 1500}(dest, 1000, "")`.
   - `feeLimit = 1500 - 1000 = 500`
   - `_payKLAYFeeAndRefundChange(500)` sends 400 to `feeReceiver`, then attempts `msg.sender.call.value(100)("")` → `ok = false` (Caller has no receive).
   - `require(ok, "refund fee failed")` reverts the entire transaction.
4. The bridge transfer never completes. `Caller` cannot bridge KAIA regardless of how much value it sends, as long as `feeLimit > feeOfKLAY`.

For Scenario B: replace `Caller` with a contract that has `receive() external payable {}`. Step 3 succeeds, but the 100 KAIA refund goes to `Caller`, not to the EOA user who initiated the transaction through `Caller`. The user's KAIA is lost.
