### Title
Stale in-memory account persisted after an unguarded post-callback token transfer enables hook reentry that clobbers live position state - (File: contracts/controller/src/strategies/flash_position.rs)

### Summary
The kernel bug class is a delayed event being processed against state that was already torn down — the fix is a "check the object is still valid before using it" gate. The analog in `process_flash_position` is the inverse-shaped hole: the flash guard wraps the receiver callback but is *closed* before `refund_listed_assets` performs real `token.transfer` calls, and the in-memory `account`/`Context` snapshot loaded before the callback is then blindly persisted by `strategy_finalize`. A listed refund token with a transfer hook can reenter the controller in that unguarded window, and the final persist overwrites whatever the reentrant call wrote to storage.

### Finding Description
`process_flash_position` loads the account once, wraps only `mint_and_forward` + `invoke_receiver` in `storage::with_flash_guard` (`contracts/controller/src/strategies/flash_position.rs:120-143`), then — after the guard has cleared — calls `refund_listed_assets` (`line 148`), which performs `token::Client::transfer(controller, caller, excess)` via `refund_controller_balance_delta` (`contracts/controller/src/payments.rs:41-52`). Only after this external token call does `strategy_finalize` (`line 153`) run `enforce_post_pool_solvency` and `finalize_position_flow`, which writes `account.supply_positions` and `account.borrow_positions` back via `persist_account_positions` (`contracts/controller/src/strategies/mod.rs:48-56`, `contracts/controller/src/positions/mod.rs:153-170`).

The code itself acknowledges hook reentry is reachable — the comment at line 119 says "token hooks can reenter first" and `borrow_into_controller` wraps its funding call in a nested `with_flash_guard` (`contracts/controller/src/positions/debt.rs:285`) — yet the refund leg executes `transfer` outside any guard. A token hook executing during the refund transfer faces no `require_not_flash_loaning` rejection, and Soroban memoizes `require_auth` per (contract, address) per transaction: since `caller` already authorized this controller invocation tree, a reentrant controller call passing `caller` satisfies authorization. The hook can therefore invoke e.g. `withdraw` or `borrow` on `account_id`, which loads positions from storage, mutates them, performs real token transfers, and persists. When control returns, `strategy_finalize` persists the *pre-reentry* in-memory `account`, restoring the supply/debt maps exactly as they were before the hook ran — while the tokens the hook's `withdraw`/`borrow` moved are already gone.

The same ordering exists in `repay_debt_from_controller`, where `refund_controller_balance_delta` transfers to `caller` before `strategy_finalize` (`contracts/controller/src/strategies/legs.rs:75-80`, used by `swap_debt.rs:87`, `repay_debt_with_collateral`, `migrate_blend`), and the leftover-input refund in `swap_tokens` (`contracts/controller/src/strategies/swap.rs:50-52`).

### Impact Explanation
Concrete theft/insolvency path: a hook reenters `borrow(caller, account_id, ..., amount)` during the refund transfer. The reentrant borrow mints debt shares, transfers real tokens out of the pool, and persists the new debt position. `strategy_finalize` then writes back the stale `borrow_positions` map that predates the borrow, erasing the debt shares from the ledger while the borrowed tokens remain extracted — unbacked pool outflow, i.e. protocol insolvency. The mirror path (`repay` inside the hook) burns debt in storage and pulls the payer's tokens, then the stale persist restores the debt: the user paid and still owes — theft of user funds. Both are within the accepted impact classes.

### Likelihood Explanation
Requires a listed spoke asset whose token invokes a transfer hook on outbound `transfer` — the codebase explicitly models this (`with_transfer_hook_market`, `test_flash_position_transfer_hook_cannot_reenter`), so it is a contemplated token shape, not hypothetical semantics. The attacker path is unprivileged: `flash_position(caller, account_id, spoke_id, mode, debt, amount, receiver, data, collaterals, refund_assets=[hook_token])` where `hook_token` is listed on the spoke and distinct from the collaterals (`validate_refund_assets` only requires listing and non-duplication, `flash_position.rs:217-255`). The hook must fire on a controller→caller send and know the victim's `account_id`/`caller` — both derivable from the transfer arguments. Likelihood is gated by such a token being listed, hence Medium rather than High.

### Recommendation
Extend `with_flash_guard` to cover the entire settlement tail — `collect_collateral_deposits`, `process_deposit`, `refund_listed_assets`, and `strategy_finalize` — not just funding and the callback, mirroring the "check `sk_state`/`conn` is still valid before use" fix: treat any post-callback external token call as a point where account/storage state may have changed. Alternatively, reload the account from storage (or re-validate that the persisted maps still match the in-memory `account`) immediately before `persist_account_positions` writes, and apply the same ordering fix to `repay_debt_from_controller` and `swap_tokens` refunds.

### Proof of Concept
1. Admin lists token `H` (a hook token) in the spoke; attacker supplies/borrows normally to build account `A`, or opens it inside the flash call.
2. Attacker calls `flash_position(caller=attacker, account_id=A, mode=Multiply, debt=USDC, amount=X, receiver=R, collaterals=[(XLM, min)], refund_assets=[H])`, having first dusted `H` to the controller (or arranged the receiver callback to leave an `H` balance) so `excess > 0` in `refund_controller_balance_delta`.
3. Guard closes at line 143; `refund_listed_assets` executes `H.transfer(controller → attacker)`, firing `H`'s hook with the guard off.
4. Inside the hook, call `controller.borrow(caller=attacker, account_id=A, assets=[(USDC, Y)], to=attacker)`. `require_auth(attacker)` is satisfied by memoized auth; the borrow persists `BorrowPositions` including `Y` and transfers `Y` USDC out of the pool.
5. Hook returns; `strategy_finalize` persists the stale `account.borrow_positions` loaded at step 2 — the `Y` debt position is erased from storage while `Y` tokens stay withdrawn.
6. `require_flash_position_still_open` still passes (the stale map retains the step-2 flash debt), the event publishes, and the account now holds collateral against a smaller recorded debt than the tokens actually extracted — insolvent pool.
