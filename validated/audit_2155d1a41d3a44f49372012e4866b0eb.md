## Title
Attestor list lookup for AA-issued assets skips stability/before-last-ball check, allowing attestation-gated asset transfers to be authorized by unconfirmed attestor lists - ([File: storage.js])

### Summary
`storage.readAsset()` in `storage.js` determines the current list of attestors for `spender_attested` assets by querying the most recent `asset_attestors` unit. For ordinary (non-AA) assets this query is restricted to units that are `is_stable=1 AND main_chain_index<=last_ball_mci`, i.e. only attestor-list changes that are already stable and known-before-last-ball can affect who is considered attested — the same temporal-consistency discipline enforced everywhere else in validation (e.g. `readDefinitionByAddress`, `readDefinitionChashByAddress`). But when the asset is defined by an AA (`byAA=true`), this restriction is dropped entirely: `before_last_ball_cond` becomes the empty string, so the "latest attestor list" and the attestor addresses it contains are selected from *any* `asset_attestors` unit with `sequence='good'`, regardless of stability or of being before the last ball. [1](#0-0) 

### Finding Description
`readAsset()` is called via `loadAssetWithListOfAttestedAuthors()` from `validatePayment()` whenever a unit contains a payment message for an asset, passing `objValidationState.bAA` as `bAcceptUnconfirmedAA`. When a payment is part of an AA response/trigger chain, `bAA` is true, so the asset's unconfirmed AA-posted definition is accepted and, if `spender_attested` is set, `addAttestorsIfNecessary(true)` is invoked with `byAA=true`. [2](#0-1) [3](#0-2) 

For every other consensus-relevant lookup in the codebase (definitions, witness lists, attestations themselves in `filterAttestedAddresses`), the rule is strict: only state that is stable and known no later than `last_ball_mci` may influence validation, precisely to guarantee that all nodes evaluating the same unit against the same last ball converge on the same result. `filterAttestedAddresses` enforces exactly this for the attestation records themselves: [4](#0-3) 

But the *attestor list itself* (who is authorized to attest for the asset) is fetched without that constraint in the AA-asset branch. This means the attestor list used to gate a `spender_attested` transfer can be taken from an `asset_attestors` unit that is not yet stable and/or was created after `last_ball_mci` — i.e., state that has not yet reached consensus finality. Because AAs execute deterministically only once inputs are stable, an attacker who controls (or triggers) an AA-defined asset can post an `asset_attestors` update and then, within the same or a closely following unstable unit, arrange a payment that consumes that not-yet-stable attestor list to satisfy the `spender_attested` condition — before the network has agreed the attestor-list change is final. If that `asset_attestors` unit is later voided/becomes non-serial (temp-bad/final-bad) as the DAG stabilizes, the payment that depended on it will have been provisionally accepted (and possibly relayed/acted upon) based on an attestor list that consensus ultimately rejects, while other nodes that saw a different ordering/visibility of the unstable `asset_attestors` unit may compute a different attestor set for the same last-ball, mci, and asset — a direct violation of the "only stable-before-last-ball state may affect validation" invariant that every other check in `validation.js`/`storage.js` enforces.

### Impact Explanation
This breaks deterministic consensus for `spender_attested` assets issued by AAs: different full nodes can derive different attestor sets for the same unit/last-ball because the query is not anchored to a stable, deterministic snapshot. That enables either (a) unauthorized transfer of an attestation-gated asset by leveraging an attestor-list change that has not (or will never) become final, or (b) divergent validity/acceptance decisions across nodes for the same unit (nodes disagreeing on whether the payment's attestation requirement is satisfied), both of which are DAG-consensus-breaking outcomes for a state that reachable and controllable by any AA trigger sender / AA definer.

### Likelihood Explanation
The AA-asset branch (`bAcceptUnconfirmedAA`/`byAA`) is reached on the normal path any time a payment message inside an AA-triggered unit references a `spender_attested` asset defined by an AA — this is a single-poster/trigger-sender reachable code path (post a trigger to an AA that defines a `spender_attested` asset and issues/updates its attestor list), requiring no special privileges beyond composing ordinary triggers and asset messages.

### Recommendation
Apply the same `AND main_chain_index<=? AND is_stable=1` (or an appropriately mci-bounded, deterministic equivalent for immediately-active AA state) restriction to the `asset_attestors` lookup in the `byAA` branch as is used in the non-AA branch, so that attestor-list changes must be part of the deterministic, already-agreed state visible at `last_ball_mci` before they can gate a spend — consistent with how `filterAttestedAddresses` already restricts the attestation records themselves.

### Proof of Concept
1. Define an AA that issues a `spender_attested` asset (`asset` message with `spender_attested: true`, `attestors: [A]`).
2. From the same AA (or via a chain of AA responses within one trigger execution), post an `asset_attestors` message changing the attestor list to include address `B` (attacker-controlled), then in a message emitted in the same/adjacent still-unstable unit chain, send an asset payment from `B` requiring `spender_attested`.
3. Because `readAsset()`'s `byAA` branch drops the `is_stable=1 AND main_chain_index<=last_ball_mci` filter, `B` is treated as an authorized attestor immediately, before the `asset_attestors` unit is confirmed stable — allowing the payment to pass `objAsset.spender_attested` checks in `validatePayment` even though consensus has not yet finalized that attestor-list change.
