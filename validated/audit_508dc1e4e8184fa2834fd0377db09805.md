### Title
Push webhook signed by attacker's own org's secret can trigger sync of a stack belonging to a different org's repository - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/handler.rb, app/models/shipit/webhooks/handlers/push_handler.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects the verifying `webhook_secret` using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` [1](#0-0) . The `PushHandler`/`Handler#stacks` method instead resolves the target repository from `payload.dig('repository', 'full_name')` [2](#0-1) . Because both fields are attacker-controlled JSON fields in the same raw request body, and nothing in the pipeline validates that `repository.full_name`'s owner segment matches `repository.owner.login`, an attacker who owns a GitHub App/org in Shipit (and thus knows their own `webhook_secret`) can sign a request as their own org while pointing `repository.full_name` at any other tracked repository/stack.

### Finding Description
The broken binding claimed by the question is: **org whose `webhook_secret` verified the signature == org owning every `Stack` mutated by the handler**. Tracing the code shows this binding is not enforced anywhere.

- `verify_signature` computes `github_app = Shipit.github(organization: repository_owner)` and checks the signature against that org's `webhook_secret` via `GitHubApp#verify_webhook_signature`, which does a `secure_compare` of the HMAC-SHA1 of the *raw body* against that org's secret [3](#0-2) [4](#0-3) . `repository_owner` is `params.dig('repository', 'owner', 'login')` [1](#0-0) .
- `create` then dispatches the *entire raw parsed body* to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [5](#0-4) .
- `PushHandler#process` calls `stacks.where(branch:)...` where `stacks` is defined on the base `Handler` class as `Repository.from_github_repo_name(repository_name)&.stacks`, and `repository_name` is `payload.dig('repository', 'full_name')` [2](#0-1) [6](#0-5) .

Since the raw JSON body is a single attacker-supplied document, `repository.owner.login` (used for signature-key selection) and `repository.full_name` (used for stack selection) are two independent fields with no cross-validation. An attacker who controls an org onboarded to Shipit (e.g., they operate `attacker-org` and know its `webhook_secret` because they configured their own GitHub App/webhook, or simply because they are a legitimate outside contributor whose org is a Shipit tenant) can craft:

```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "ref": "refs/heads/master",
  "after": "<sha>"
}
```

Sign it with `attacker-org`'s `webhook_secret` (valid, since they legitimately possess it), POST to `/webhooks` with `X-Github-Event: push`. `verify_signature` passes because `Shipit.github(organization: "attacker-org")` correctly verifies against their own secret. `create` then invokes `PushHandler`, which resolves `victim-org/victim-repo`'s `Stack`s by `branch` and calls `stack.sync_github(expected_head_sha: params.after)`, mutating/syncing a stack that belongs to an org the attacker never proved control over.

None of the existing guards catch this: `verify_signature` only checks the signature against the org derived from `owner.login`, never re-checking that this org matches `full_name`'s owner segment; `drop_unhandled_event` and `check_if_ping` are unrelated; the `ExplicitParameters` schema in `PushHandler` only requires `ref`/`after`, not `repository.full_name`, and even the handlers that do `requires :repository { requires :full_name }` never cross-check it against `repository.owner.login`; `Repository` model validations only constrain repo name format, not correlate it with the webhook signer.

### Impact Explanation
A successfully-forged (from the perspective of Org B) push webhook causes `Shipit::Stack#sync_github` to run for a repository/stack the attacker's org does not own, potentially triggering GitHub API sync (`GithubSyncJob`) against Org B's tracked stack using Org B's own GitHub App credentials once dispatched (`stack.sync_github` uses the stack's own repository/app config internally, so the actual GitHub read/sync happens with the correct org's token — the attacker doesn't exfiltrate Org B's secrets, but does trigger unauthorized processing/state changes tied to Org B's stack, e.g., forcing a sync attempt or affecting commit state of Org B's branch). This matches "a payload for one repository mutating another's stack" in the Critical impact category. The same class of confusion (signature-verifying org != handler-resolved-repository org) likely extends to other handlers that key off `payload`/`params.dig('repository', ...)` similarly, though `PushHandler` is the most directly demonstrable since its params schema doesn't even require `repository.full_name` to be validated against anything.

### Likelihood Explanation
Precondition: the attacker must control (or have legitimate knowledge of) a `webhook_secret` for at least one org configured in `Shipit.github(organization:)` — i.e., they must be a legitimate GitHub App owner/admin for their own org that is onboarded to this Shipit instance, or otherwise possess that org's secret. Given that, forging the `repository.full_name` field costs nothing extra — it's just a JSON string in the same request they're already allowed to sign. This is repeatable against any tracked stack of any other org, as long as the attacker knows the target's `full_name` and `branch` (both public information on GitHub). The exploit requires zero access to Org B's secrets.

### Recommendation
In `WebhooksController#verify_signature`/`create`, after verifying the signature, validate that the org derived from `repository.full_name`'s owner segment (or `organization.login`) matches `repository_owner` (the same field used to select the webhook secret) before dispatching to handlers; reject with 422 on mismatch. Alternatively, have `Handler#repository_name`/`stacks` derive the repository strictly from the same `repository_owner` field validated in the controller, or pass the verified `repository_owner` into handlers and assert equality with `payload.dig('repository', 'full_name')`'s owner before performing any stack lookup/mutation.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb
test "push forged for a different repository than the signing org does not sync victim stack" do
  victim_stack = shipit_stacks(:shipit) # repository e.g. "shopify/shipit-engine", branch "master"

  # Simulate signature verification succeeding only for 'attacker-org'
  Shipit.expects(:github).with(organization: 'attacker-org').returns(
    stub(verify_webhook_signature: true)
  )

  request.headers['X-Github-Event'] = 'push'
  forged_payload = {
    repository: { owner: { login: 'attacker-org' }, full_name: victim_stack.repository.full_name },
    ref: "refs/heads/#{victim_stack.branch}",
    after: 'deadbeef'
  }.to_json

  assert_no_enqueued_jobs do
    post :create, body: forged_payload, as: :json
  end
  # FAILS today: GithubSyncJob is enqueued for victim_stack despite signature
  # only proving control of 'attacker-org', not 'victim-org' (repository.full_name's owner).
end
```
Assertion to add on fix: `repository_owner` (derived from `repository.owner.login`, the value that selected the verifying secret) must equal the owner segment of `params.dig('repository','full_name')`; if they differ, the request must be rejected (422) before any handler runs, and no job should ever be enqueued for `victim_stack`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
