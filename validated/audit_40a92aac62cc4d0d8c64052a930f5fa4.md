### Title
`has_only()` oscript builtin allows attacker-controlled character-class negation via unescaped `^` - ([File: formula/evaluation.js])

### Summary
The external report's root cause is an incomplete/incorrect regex pattern that fails to block a dangerous input variant (`.php4`) because the validation regex was not built defensively against all attacker-supplied strings. The equivalent bug class in `ocore` is found in the `has_only` oscript builtin, which dynamically builds a `RegExp` character class from an attacker-influenceable string without neutralizing the regex metacharacter `^`, which negates a character class.

### Finding Description
`has_only(str, sub)` is implemented in `evaluate()` in `formula/evaluation.js` by constructing a regular expression character class directly from the `sub` argument: [1](#0-0) 

The code defends against only two specific escaping issues — an already-escaped `\]` sequence and a trailing unescaped backslash — then escapes literal `]` characters, and finally builds `new RegExp("^[" + sub + "]*$")`. It does not defend against `sub` beginning with `^`, which in a JS regex character class means "negate this class" (`[^...]`), nor does it neutralize the range operator `-`, which can silently create unintended character ranges. If an AA author (or trigger sender who influences `sub` through string concatenation of trigger data) supplies a value beginning with `^`, the semantics of the check are inverted: "string contains only these characters" becomes "string contains only characters NOT in this set". This is structurally the same bug class as the Xerte CVE — a validation regex is built from untrusted input without covering all metacharacters that can subvert the intended allow/deny semantics, so a downstream consumer's whitelist check silently becomes a blacklist (or vice versa) for correctly-shaped-but-malicious input.

`formula/validation.js` performs only structural validation of the `has_only` operator's arguments (that they are valid sub-expressions), not content-level sanitization of what `sub` may contain, so nothing in the validation pass blocks a leading `^` from reaching `evaluate()`. [2](#0-1) 

### Impact Explanation
`has_only` is a general-purpose oscript builtin available to any AA definition and any AA is triggered by unauthenticated/unprivileged unit posters via `trigger.data`. If an AA author writes logic such as `has_only(user_supplied_string, base_charset || trigger.data.suffix)` (or any pattern where the allow-list itself is partially derived from data) to sanitize an identifier before using it as a state-variable key, an address-like string, or a value gating a payment/output decision, an attacker can invert the check by injecting a leading `^` into the character-class portion. This lets attacker data satisfy a whitelist check it was never meant to satisfy, potentially leading the AA into a path meant to be gated behind "sanitized/safe" input — which can translate into AA fund loss, incorrect state transitions, or bypass of intended input constraints, depending on the specific AA logic. The blast radius is scoped to AAs whose logic composes the `sub` argument from anything data-dependent; it does not affect the DAG/consensus engine directly, so it is not a network-wide double-spend or supply-inflation bug, but it is a concrete "AA fund loss/freezing via bypassed application-level validation" analog reachable purely from a posted trigger unit.

### Likelihood Explanation
Exploitability depends on whether a deployed AA's oscript constructs the `sub` (character-set) argument using any data influenced by the trigger sender rather than a pure string literal. This is a plausible but not universal pattern (concatenating a "base" safe charset with a per-request suffix is a natural thing an AA author might do when building flexible validation). I could not find any bundled `.oscript` template in the indexed repo content that uses `has_only`, so I cannot confirm a first-party AA is presently affected — the risk is in the engine's builtin exposing an unsafe regex-construction primitive to third-party AA authors, analogous to how the Xerte bug is in a shared connector reused by multiple call sites.

### Recommendation
In the `has_only` case in `formula/evaluation.js`, sanitize `sub` defensively for regex character-class semantics rather than only handling `]` and trailing `\`: explicitly strip or escape a leading `^`, and either escape or explicitly document/restrict use of `-` (or escape it too, since safe listing of individual characters should not need ranges). Alternatively, avoid building a raw character class from user data entirely — enumerate `sub` characters into a `Set` and check `str` character-by-character using string comparison instead of feeding untrusted content into `RegExp` construction. Add the same regression test pattern used for `]`/trailing-backslash (`test/formula.test.js:2510-2526`) for a leading `^` case, asserting it is either treated as invalid input or interpreted literally.

### Proof of Concept
```
has_only("secret_value", "^0123456789")
```
With the current implementation, `sub = "^0123456789"` produces `RegExp("^[^0123456789]*$")`, which matches any string composed of characters *other than* the digits 0–9 — the exact opposite of the presumably intended "only digits" whitelist. Any oscript expression of the form `has_only(<attacker string>, <base_charset> || <attacker-influenced suffix>)` lets the attacker smuggle a leading `^` into the effective character class and invert the check.
