This confirms a genuine multi-tenant architecture: `Shipit.github(organization:)` resolves a distinct `webhook_secret` per organization key in `secrets.github` [1](#0-0) , and `WebhooksController#verify_signature` selects that per-org secret using `repository_owner`, which reads `params.dig('repository', 'owner', 'login')` — a field entirely separate from `repository.full_name` [2](#0-1) .

### Title
Webhook signature verification keyed on `repository.owner.login` diverges from repository resolution keyed on `repository.full_name`, enabling cross-tenant stack/PR mutation - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/handler.rb, app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb)

### Summary
`WebhooksController#verify_signature` authenticates a webhook using the org named at `repository.owner.login`, computing the HMAC against that org's own `webhook_secret` [3](#0-2) . `LabelCapturingHandler` (and all other `PullRequest` handlers, and the base `Handler#stacks`) then resolve the target `Repository` using the *different* field `repository.full_name` [4](#0-3) [5](#0-4) . Nothing enforces `repository.owner.login == full_name.split('/').first`, so an attacker who legitimately controls a real, Shipit-registered GitHub org (and thus knows/can produce its valid `webhook_secret` via a genuine GitHub webhook delivery from their own repo) can forge a raw POST body where `full_name` names an arbitrary victim-org repository while `owner.login` names their own org.

### Finding Description
The intended binding is: `verified_org == full_name_owner`, i.e., the organization whose secret validated `X-Hub-Signature` must equal the owner segment of the repository the handler subsequently mutates. In code, these are two unrelated reads of the same JSON body:
- `repository_owner` (used for HMAC verification): `params.dig('repository', 'owner', 'login')` [6](#0-5) 
- `full_name` (used for the `Repository` row lookup): `params.repository.full_name`, parsed only for `String` type by `ExplicitParameters`, with no format or cross-field check against `owner.login` [7](#0-6) .

`Repository.from_github_repo_name` performs an exact `find_by(owner:, name:)` after `downcase.split('/')` [8](#0-7)  — this is exact-match, not loose/fuzzy, so the audit prompt's specific "embedded path fragment" probe (e.g. `victim-org/repo-a; attacker-org/repo-b`) fails: `split('/')` yields `owner="victim-org"`, `name="repo-a; attacker-org"`, which never matches a real row (Repository name/owner are validated with `/\A[a-z0-9_\-.]+\z/` at creation time, so no stored row can contain `;` or spaces) [9](#0-8) . That specific probe returns `nil` → `NullRepository`, exactly as intended — **no vulnerability via that exact vector**.

However, tracing the full call sequence surfaces the real divergence: the controller's `verify_signature` and the handler's repository resolution use different fields of the same attacker-controlled JSON body. An attacker who administers `attacker-org` (a real, Shipit-configured GitHub org with its own `webhook_secret` in `secrets.github`) can, outside of GitHub's UI, POST directly to `/webhooks` with a body they construct and sign themselves:
```json
{
  "action": "opened",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "pull_request": { ... },
  "sender": { "login": "attacker" }
}
```
computing `X-Hub-Signature` with `attacker-org`'s own `webhook_secret` (which the attacker legitimately possesses, since it is their own org's configured GitHub App webhook secret). `verify_signature` calls `Shipit.github(organization: "attacker-org")` and succeeds because the signature matches attacker-org's secret and the attacker signed the exact raw body they sent [10](#0-9) . The request then reaches `Shipit::Webhooks.for_event('pull_request').each { |handler| handler.call(params) }` [11](#0-10) , and each handler (`OpenedHandler`, `LabelCapturingHandler`, etc.) resolves `repository` via `full_name = "victim-org/victim-repo"`, finding the *actual victim repository row*, and proceeds to create/mutate/archive a review stack or update PR labels belonging to `victim-org` — a repository never authenticated by this request's signature.

None of the existing guards catch this: `drop_unhandled_event` only checks the event type exists [12](#0-11) ; `ExplicitParameters` only validates types, not cross-field consistency; `verify_signature` never reads or checks `full_name` at all.

### Impact Explanation
An attacker who controls one legitimately Shipit-registered GitHub org can, for any `pull_request` (and by the same pattern `push`, `status`, `check_suite`) webhook event, cause Shipit to create, archive/unarchive review stacks, or overwrite PR labels on `stacks`/`review_stacks` belonging to a completely different org/tenant (`victim-org`) that never authorized this request. This is a payload for one repository mutating another repository's stack/PR state — a cross-tenant integrity violation, matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team"). It is fully repeatable against any repository name the attacker can guess (`owner/name` pairs are typically public GitHub identifiers), and it is not limited to `LabelCapturingHandler` — it applies to every handler under `Shipit::Webhooks::Handlers` that keys off `repository.full_name` instead of `repository.owner.login`.

### Likelihood Explanation
Requires a Shipit deployment to have **multiple GitHub organizations configured** (multi-tenant `secrets.github` keyed by org, each with its own `webhook_secret`) and the attacker to legitimately control (or compromise via low-privilege means, e.g. as an org owner with a real GitHub repo) at least one of those configured orgs — a plausible scenario for any shared/multi-tenant Shipit instance serving several GitHub orgs. No Shipit session, API token, or victim secret is required; the attacker only needs their own org's real webhook secret, which they possess by design (they can just look at their own webhook config in GitHub's org settings, or capture their own valid delivery's signature and reuse the raw body with a modified `full_name` — but note: modifying the body after having a valid signature invalidates the signature, since it is HMAC over `request.raw_post`. The attacker must instead **construct and sign their own custom body from scratch**, which they can do because they know their own org's `webhook_secret`).

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler#initialize`), assert that `payload.dig('repository', 'owner', 'login')` matches the owner segment of `payload.dig('repository', 'full_name')` before dispatching to handlers, rejecting the request (e.g. `head(422)`) on mismatch. Alternatively, derive the repository lookup key exclusively from the same field used for signature verification (`repository.owner.login` + `repository.name`), rather than trusting the independently-supplied `full_name`.

```ruby
# test/controllers/webhooks_controller_test.rb
test "rejects payload where full_name owner diverges from repository.owner.login used for signature" do
  victim = shipit_repositories(:shipit) # owner: 'shopify', name: 'shipit-engine'
  attacker_org = 'attacker-org'
  Shipit.stubs(:github_app_config).with(attacker_org).returns(webhook_secret: 'attacker-secret')

  body = {
    action: 'opened',
    number: 1,
    pull_request: { id: 1, number: 1, url: 'x', title: 't', state: 'open',
                     additions: 0, deletions: 0, head: { sha: 'a' * 40, ref: 'r' },
                     user: { login: 'attacker' }, assignees: [], labels: [] },
    repository: { owner: { login: attacker_org }, full_name: "#{victim.owner}/#{victim.name}" },
    sender: { login: 'attacker' }
  }.to_json

  signature = "sha1=#{OpenSSL::HMAC.hexdigest('sha1', 'attacker-secret', body)}"
  @request.headers['X-Github-Event'] = 'pull_request'
  @request.headers['X-Hub-Signature'] = signature

  assert_no_difference -> { victim.review_stacks.count } do
    post :create, body:, as: :json
  end
  # Currently FAILS: request passes verify_signature (org=attacker-org)
  # and LabelCapturingHandler/OpenedHandler resolve `victim` via full_name,
  # mutating victim's review_stacks despite the signature never authenticating victim-org.
end
```
Assert both sides of the binding explicitly: `Shipit.github(organization: repository_owner)` (attacker-org's secret) must equal the org that owns the row returned by `Repository.from_github_repo_name(full_name)` (victim-org) — this test demonstrates they diverge and the request is still accepted.
