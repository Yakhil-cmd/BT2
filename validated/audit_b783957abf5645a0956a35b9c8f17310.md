### Title
Cross-organization `Shipit.github_teams` membership forgery via unscoped `github_id` lookup - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`MembershipHandler#process` resolves the target `Team` by GitHub's numeric `github_id` alone, never checking that the team belongs to the organization whose webhook secret validated the request. Any organization owner configured in Shipit's multi-org `github` secrets can therefore forge a `membership` webhook, signed with their own legitimate `webhook_secret`, that names a `team.id` belonging to a *different* organization and add an arbitrary GitHub login to that team's `Membership` records.

### Finding Description
Broken binding: `Membership.exists?(team: T, user: U)` should hold **only if** GitHub itself reports `U` as a member of `T`, and `T` must belong to the organization that authenticated the inbound webhook, i.e. `T.organization == verified_org`. The code never enforces the second half of that equality.

Trace:
1. `WebhooksController#verify_signature` picks the GitHub App/secret purely from the payload-declared organization: `Shipit.github(organization: repository_owner)` where `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0) [2](#0-1) . For a `membership` event this is `params.organization.login`, e.g. `"evilcorp"`. Since Shipit supports one GitHub App config per organization (`docs/setup.md` "Using Multiple Github Applications"), the attacker who administers `evilcorp`'s own App legitimately possesses `evilcorp`'s `webhook_secret`, so `verify_webhook_signature` passes.
2. `MembershipHandler#process` then resolves the team purely by numeric id, with no scoping to the verified organization:
```
def find_or_create_team!
  Team.find_or_create_by!(github_id: params.team.id) do |team|
    team.github_team = params.team
    team.organization = params.organization.login
  end
end
``` [3](#0-2) 
If a `Team` row with that `github_id` already exists (e.g. `shipit_teams(:shopify_developers)`, `github_id: 1`, `organization: "shopify"` [4](#0-3) ), `find_or_create_by!` returns that **existing** record unchanged — the `organization` field is only set on the creation path, not verified on the lookup path.
3. `User.find_or_create_by_login!(params.member.login)` fetches the named GitHub login via `Shipit.github.api.user(login)` [5](#0-4) , so this must be a real GitHub login, but any real login the attacker names — not necessarily one associated with `evilcorp` — will do.
4. `team.add_member(member)` inserts the `Membership` row: `members.append(member) unless members.include?(member)` [6](#0-5) .

None of the existing guards catch this: `verify_signature` only authenticates *which organization* sent the webhook, not *which team* the payload may reference; `drop_unhandled_event` only checks the event type is registered; the `ExplicitParameters` schema in `MembershipHandler.params` only enforces types/presence, not cross-references to `repository_owner`; and `Team`/`Membership` have no uniqueness or ownership validation tying `github_id` to a specific organization.

Attacker exact request: a `membership` webhook POSTed to `/webhooks`, `X-Github-Event: membership`, signed with HMAC-SHA1 using `evilcorp`'s real `webhook_secret`, body:
```json
{"action":"added","organization":{"login":"evilcorp"},
 "team":{"id":1,"name":"Developers","slug":"developers","url":"https://example.com"},
 "member":{"login":"victim-employee"}}
```
Because `team.id` (1) collides with `shipit_teams(:shopify_developers).github_id`, the pre-existing `shopify_developers` Team record is fetched and mutated, granting `victim-employee` a `Membership` in a team that belongs to `shopify`, not `evilcorp`.

### Impact Explanation
This grants an attacker who controls one org's App/webhook secret the ability to insert arbitrary logins into `Membership` rows for `Team`s used in `Shipit.github_teams` authorization gating (`User#authorized?` checks `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [7](#0-6) , enforced in `force_github_authentication` [8](#0-7) ). If that named login ever authenticates to Shipit via GitHub OAuth (matched by `github_id`, independent of this fabricated row's provenance), they inherit access to a team they were never actually added to on GitHub — an authorization escalation into `Shipit.github_teams`, matching the defined "High" severity category. It is repeatable per request/team-id, and blast radius spans every tenant/organization sharing the same Shipit instance in a multi-org configuration, since team `github_id` values are global and unscoped in this lookup.

### Likelihood Explanation
Requires Shipit to be configured for multiple GitHub organizations (a documented, supported configuration in `docs/setup.md`) where the target org (`evilcorp`) is one of the configured tenants with its own `webhook_secret`, and requires the victim `Team` (e.g. `shopify_developers`) to already exist in Shipit's database (created by a legitimate prior webhook or `rake teams:fetch`). Given those preconditions — both realistic for any Shipit deployment serving several GitHub orgs — the attack costs nothing beyond a single signed HTTP POST and is trivially repeatable.

### Recommendation
In `find_or_create_team!`, scope the lookup by both `github_id` and `organization` (`params.organization.login`), and reject/raise if an existing `Team` with that `github_id` belongs to a different organization than the one that authenticated the webhook. More generally, `WebhooksController#verify_signature` should pass the verified organization into handlers so they can assert `team.organization == verified_organization` before mutating membership.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb
test ":membership webhook cannot bind another organization's team" do
  @request.headers['X-Github-Event'] = 'membership'
  team = shipit_teams(:shopify_developers) # organization: 'shopify', github_id: 1

  payload = {
    action: 'added',
    organization: { login: 'evilcorp' },
    team: { id: team.github_id, name: team.name, slug: team.slug, url: team.api_url },
    member: { login: 'attacker-chosen-login' },
    repository: { owner: { login: 'evilcorp' } }
  }.to_json

  Shipit.github(organization: 'evilcorp').expects(:verify_webhook_signature).returns(true)

  assert_no_difference -> { Membership.where(team:).count.zero? ? 0 : 1 } do
    # Binding under test: a membership added for `team` (owned by shopify)
    # must NOT be created from a webhook authenticated only for `evilcorp`.
    post :create, body: payload, as: :json
  end

  refute Membership.exists?(team:, user: User.find_by(login: 'attacker-chosen-login')),
    "evilcorp's webhook should not be able to add members to shopify's team"
end
```
This currently fails (the Membership *is* created) against `MembershipHandler#find_or_create_team!`, demonstrating the cross-organization escalation.
