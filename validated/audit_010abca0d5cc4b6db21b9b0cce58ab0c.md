### Title
Third-party supply top-up overwrites a foreign account's cached liquidation parameters, bypassing the health-factor gate on `update_account_threshold` - (File: contracts/controller/src/positions/supply.rs)

### Summary
The CVE class is an attacker-influenced write landing on a location the victim owns — a crafted name causes the tool to overwrite files the attacker has no rights to. The analog in XOXNO Lending is the permissionless `supply` top-up: any authenticated caller may add funds to an asset slot an existing foreign account already holds (`require_third_party_existing_supply`, supply.rs:78-97), and the deposit path then rebuilds that position from the *current* listing config via `account.get_or_create_supply_position(&hub_asset, &asset_config)` (supply.rs:126). An ordinary supply restamps the position's risk tuple — confirmed by the harness comment "An ordinary supply restamps an existing position; a credit does not" (`tests/test-harness/tests/controller/liquidation_seize_modes.rs:394`) — while the dedicated keeper path `update_account_threshold` applies the liquidation tuple only through `apply_gated_liquidation_params`, which refuses liquidator-favoring changes on an indebted account unless the hypothetical health factor clears 1.05 (`risk/params.rs:68-93`). The supply path carries no equivalent debt-aware gate, so a dust top-up is an unguarded overwrite of the victim's stored `liquidation_threshold` / `liquidation_bonus` / `liquidation_fees`.

### Finding Description
`process_supply` authenticates the caller, loads the target account, and for a third party checks only that every supplied `HubAssetKey` already exists in `account.supply_positions` (supply.rs:86-96). `process_deposit` then fetches the live `AssetConfig` from the spoke listing and calls `get_or_create_supply_position(&hub_asset, &asset_config)`, which for an existing slot writes the current listing parameters onto the stored `AccountPosition` before `persist_account_positions` commits the map (positions/mod.rs:153-170). The code deliberately routes keeper-driven restamping through `refresh_supply_risk_params` / `apply_gated_liquidation_params`, which detects changes that "favor the liquidator" (lower threshold or fee, higher bonus — params.rs:96-100) and skips them unless the account still clears `THRESHOLD_UPDATE_MIN_HF_RAW` (1.05) under the new threshold (params.rs:102-119), with a final post-write HF assertion (params.rs:221-234). None of this machinery is reachable from `supply`: a stranger paying one stroop of an already-held asset forces the same overwrite the keeper function deliberately blocks.

### Impact Explanation
When governance tightens a listing (lower `liquidation_threshold`, higher `liquidation_bonus`, lower `liquidation_fees`), accounts whose health would fall below the 1.05 floor are protected: `update_account_threshold` cannot push them into liquidation range, by design. Via `supply(caller, victim_account_id, spoke_id, [(held_hub_asset, dust)])`, any unprivileged address forces exactly those liquidator-favoring stamps onto the victim's position map. The victim's stored threshold then drops below the floor the risk system was built to enforce, its computed health factor falls, and the attacker can immediately `liquidate` the account and capture the liquidation bonus — theft of user funds caused by an overwrite of state the attacker does not own. This maps the CVE directly: like Git GUI writing to files outside the intended directory, the write reaches a protected location (another account's cached risk tuple) through a path that checks only the key, not the economic consequence.

### Likelihood Explanation
Reachability is unconditional: `supply` is permissionless and the only third-party check is slot existence, which the attacker can satisfy by donating dust of any asset the victim already supplies. The precondition is a governance listing update that moves liquidation parameters in a liquidator-favoring direction — a routine, timelocked parameter change, not an exceptional event. Cost is a single dust transfer the attacker is not even guaranteed to lose (it is credited to the victim, but the liquidation bonus pays for it). Severity is bounded by the size of the parameter change and victim collateral; on large positions the forced early liquidation bonus is meaningful, warranting High-to-Medium severity. One uncertainty: I could not read `get_or_create_supply_position`'s body to confirm whether it reuses `apply_gated_liquidation_params` internally; the harness test asserting "an ordinary supply restamps an existing position" while the credit path deliberately preserves the old tuple, plus the existence of a separate gated refresh function, strongly indicates the restamp is unconditional. If the restamp does route through the HF gate, the finding collapses — verification of that one function is required before relying on this.

### Recommendation
In `process_deposit` (or inside `get_or_create_supply_position` when the slot already exists and the caller is not the owner/delegate), apply the liquidation tuple only through `refresh_supply_risk_params` with `RiskRefreshScope::FullTuple`, or equivalently skip overwriting `liquidation_threshold`/`liquidation_bonus`/`liquidation_fees` on third-party top-ups and leave tuple refresh exclusively to the gated `update_account_threshold` path. Credit-mode liquidation already demonstrates the safe pattern of crediting shares without touching the receiver's stamps.

### Proof of Concept
1. Governance lists asset X; victim supplies 10,000 X and borrows, sitting at HF ≈ 1.04.
2. Governance timelock executes a listing update lowering X's `liquidation_threshold` (or raising `liquidation_bonus` / lowering `liquidation_fees`).
3. Keeper calls `update_account_threshold(caller, true, [victim])` — it reverts/skips, because `apply_gated_liquidation_params` detects a liquidator-favoring change and the victim fails `clears_min_hf` at 1.05.
4. Attacker instead calls `supply(attacker, victim_id, spoke_id, [(hub_asset_X, 1)])`. `require_third_party_existing_supply` passes because X is already in `victim.supply_positions`; `get_or_create_supply_position` restamps the position with the new listing tuple with no HF check.
5. The victim's cached threshold now reflects the tightened listing; its HF drops below 1. Attacker calls `liquidate` and seizes collateral at the (now higher) bonus.
