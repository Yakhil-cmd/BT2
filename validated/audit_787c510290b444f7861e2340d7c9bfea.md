## Title
Unauthenticated `DepositDelegatorRewards` Instruction Lets Any Unprivileged User Set `pending_delegator_rewards` on an Arbitrary Vote Account and Block Its Closure - ([File: programs/vote/src/vote_state/mod.rs])

### Summary
The reported bug class is "an unprivileged actor can point a self-controlled object at a shared/privileged accounting structure it does not own, and mutate that shared state via a function that requires no ownership relationship to the target, corrupting accounting relied upon by other parties." The closest reachable analog in `agave` is the vote program's `DepositDelegatorRewards` instruction (SIMD-0123), implemented in `deposit_delegator_rewards()` at [1](#0-0) . It only requires that the *source* account sign the lamport transfer — it never checks that the caller has any authorized relationship (staker/withdrawer/voter) to the target vote account, and it accepts **any** vote-account pubkey supplied by the caller.

### Finding Description
`deposit_delegator_rewards` is called with two attacker-controlled accounts: the vote account to credit, and a "source" account that signs the SOL transfer: [1](#0-0) 

There is no check that `source_address` (the caller) is the validator identity, authorized withdrawer, or any other privileged party for `vote_address` — any signer can target any initialized V4 vote account and call this instruction. The instruction then mutates the vote account's shared `pending_delegator_rewards` field: [2](#0-1) 

This field is later consumed by `withdraw()`, which treats a non-zero `pending_delegator_rewards` as a hard block on fully closing (zero-balance) the vote account, and additionally reserves it out of the withdrawable balance for partial withdrawals: [3](#0-2) 

Because any unprivileged party can invoke `DepositDelegatorRewards` against a vote account they do not control, an attacker can cheaply (for the price of a tiny lamport deposit) set `pending_delegator_rewards > 0` on a victim validator's vote account at will, which the withdraw-path logic then relies on to reject full closure of the account (`InstructionError::InsufficientFunds`) until the pending amount is fully paid out through block-reward distribution in `calculate_block_reward()`: [4](#0-3) 

Because the instruction has no relationship requirement between the depositor and the vote account, and it only takes a single, atomic, cheap system-program transfer with no cooldown or rate limit, an attacker can repeatedly re-inject nonzero `pending_delegator_rewards` (e.g., immediately after each epoch's distribution zeroes it out, or before the withdrawer's close transaction lands) to indefinitely deny the legitimate authorized withdrawer the ability to fully close/zero their own vote account — exactly the "arbitrary unprivileged actor manipulates shared accounting relied on by legitimate/authorized parties" bug class from the external report, mapped onto the vote-program reward-accounting path.

### Impact Explanation
This allows an unprivileged, unrelated user to grief a validator's vote account withdraw/close instruction path, effectively freezing the ability to close the account on demand, purely by racing a minimal lamport "donation" that the withdrawer never asked for and has no way to prevent or reject. This fits the "permanently frozen accounts" impact class: the closure operation on the targeted vote account can be denied indefinitely at negligible, repeatable cost to the attacker, with no privileged relationship required.

### Likelihood Explanation
The instruction is a fully permissionless account-mutating instruction requiring only a signer and the minimal lamport amount to transfer (even 1 lamport / `deposit: 0` is a documented no-op, but any nonzero deposit sets the field), gated only by feature flags (`commission_rate_in_basis_points`, `custom_commission_collector`, `block_revenue_sharing`) that are cluster-wide activation switches, not access-control checks. Once these SIMD-0123-related features are active network-wide, any account holder can exploit this against any vote account at any time.

### Recommendation
Restrict `DepositDelegatorRewards` so it can only be invoked in the intended context (e.g., during native block-revenue distribution/CPI by a system component, or with an explicit authorization check tying the depositor to a role permitted to fund that vote account), or decouple `withdraw()`'s closure gating from `pending_delegator_rewards` so a third party cannot use it to block the authorized withdrawer's ability to close the account (e.g., allow force-closure that pays out/sweeps any pending delegator rewards rather than unconditionally rejecting withdrawal).

### Proof of Concept
1. Wait for/observe `block_revenue_sharing`, `custom_commission_collector`, and `commission_rate_in_basis_points` features active.
2. Attacker (any keypair, no relationship to victim's vote account) submits `VoteInstruction::DepositDelegatorRewards { deposit: 1 }` with accounts `[victim_vote_pubkey, attacker_pubkey(signer), system_program]`, as exercised in the test harness at [5](#0-4) .
3. This succeeds unconditionally (no signer/authority relationship to the vote account is checked), setting `pending_delegator_rewards = 1` on the victim's vote account, per [6](#0-5) .
4. The victim's authorized withdrawer then attempts `Withdraw` for the full account balance to close it; the instruction fails with `InstructionError::InsufficientFunds` due to the nonzero `pending_delegator_rewards`, per the logic at [7](#0-6) .
5. The attacker can repeat step 2 every epoch (or immediately before the withdrawer's transaction) to perpetually re-arm the block, denying the withdrawer's ability to close the vote account on their own schedule.

/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }
