### Title
Webhook Organization Used for Signature Verification Is Not Bound to the Repository the Handler Acts On - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to validate a webhook against using `repository.owner.login` (or `organization.login`), but the actual handler logic that mutates state uses a *different, independently-controlled* field of the same JSON body — `repository.full_name` (`Handler#repository_name`) for most events, and, for the `status` event, no repository binding at all. This breaks the equality "organization whose secret authenticated the request == repository that is written," letting anyone who controls a GitHub App/webhook configured for *any one* organization in the Shipit instance forge webhook events that act on a completely different organization's stacks and commits.

### Finding Description
The signature check and the target-repository resolution are computed from two unrelated JSON paths of the attacker-supplied raw body:

- Org used to pick the HMAC secret: [1](#0-0) [2](#0-1) 

- Target repository used by handlers to select the `Stack`/`Repository` to act on: [3](#0-2) 

Nothing ties `repository.owner.login` (used for `verify_webhook_signature`) to `repository.full_name` (used for `stacks`). Since the whole raw POST body — including both fields — is attacker-controlled before signing, and the HMAC only proves the body was signed with *some* configured organization's `webhook_secret`, an attacker who legitimately administers the GitHub App/webhook for Organization A (and therefore knows Org A's `webhook_secret`) can submit a payload where `repository.owner.login = "org-a"` (so `Shipit.github(organization: "org-a")` is used and the signature validates) while `repository.full_name = "org-b/victim-repo"` (so the handler acts on Org B's stack).

`PushHandler` demonstrates the write path enabled by this mismatch — it resolves stacks purely from `repository.full_name` and triggers a GitHub sync: [4](#0-3) 

`StatusHandler` is even more exposed: it does not use `stacks`/`repository_name` at all, and instead looks up commits globally by `sha`, applying the forged CI status to any commit in the entire Shipit installation with a matching SHA, regardless of which repository/org it belongs to: [5](#0-4) 

This is directly analogous to the reported bug class: `PythPriceOracle.updatePrice` returns a price derived from attacker-decoded token addresses that are never checked against the collateral/credited tokens actually used by `LetterOfCredit`; here, the webhook org derived from `repository.owner.login` (used to authorize/verify) is never checked against the repository (`repository.full_name`/commit `sha`) actually used to select what gets mutated.

### Impact Explanation
Forged, cross-organization `status` events let an attacker mark an arbitrary commit (in a repository/org they do not control) as having a passing CI check. Deploy gating in Shipit relies on GitHub commit statuses (`ci.require`) to determine `Commit#deployable?`; injecting a fabricated "success" status for a target commit can make an otherwise-unreviewed/unsafe commit eligible for deploy, and can also spuriously trigger automated behaviors driven by push/status/check_suite events (`GithubSyncJob`, `RefreshCheckRunsJob`) on stacks belonging to organizations the attacker has no authorization over. This crosses the "unauthorized deploy" / cross-repository write impact tier without requiring any Shipit session, `ApiClient` token, or GitHub write access to the victim repository — only knowledge of a `webhook_secret` for some unrelated organization configured on the same Shipit instance.

### Likelihood Explanation
Requires the attacker to control (or be the legitimate integrator of) a GitHub App/webhook for at least one organization hosted on the same multi-tenant Shipit instance — a realistic scenario for any Shipit deployment serving multiple orgs/teams, since `config/secrets*.yml` shows the engine is designed to hold several independent `github:` org blocks with per-org `webhook_secret`s: [6](#0-5) 
No interaction with a victim-org admin, no Shipit account, and no privileged credential from the target org is needed — only crafting a raw HTTP POST with a self-signed HMAC.

### Recommendation
In `Shipit::Webhooks::Handlers::Handler#stacks`/`#repository_name`, and in `StatusHandler#process`, verify that the resolved repository's owner matches the organization used to select the webhook secret in `WebhooksController#verify_signature` (i.e., assert `repository.full_name.split('/').first == repository_owner`, and constrain `StatusHandler` commit lookups to commits belonging to that same organization) before performing any state-changing action.

### Proof of Concept
1. Attacker configures/administers a GitHub App for `org-a`, which is registered in Shipit's `github:` config with its own `webhook_secret_a`.
2. Attacker crafts a JSON body for the `status` event:
   ```json
   {
     "sha": "<sha of a commit belonging to org-b/victim-repo>",
     "state": "success",
     "context": "ci/required-check",
     "repository": { "owner": { "login": "org-a" }, "full_name": "org-a/whatever" },
     "branches": [{"name":"main"}]
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(webhook_secret_a, body)` and POSTs to `/webhooks`.
4. `WebhooksController#repository_owner` returns `"org-a"`, `Shipit.github(organization: "org-a")` validates the signature successfully with `webhook_secret_a`.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and applies the forged "success" status to the matching commit belonging to `org-b/victim-repo`, an organization the attacker never authenticated against nor has any authorization over.
