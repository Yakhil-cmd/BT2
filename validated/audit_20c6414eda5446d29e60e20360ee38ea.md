### Title
Cross-organization webhook confusion: verified signer organization is never bound to the repository the payload actually mutates - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret to verify the HMAC signature by reading `repository.owner.login` (or `organization.login`) straight out of the untrusted, attacker-suppliable JSON body, and only checks that the whole raw body was signed by *that* organization's `webhook_secret`. Once verified, every event handler (`Handler#repository_name`, used by `PushHandler`, `StatusHandler`, `PullRequest::*Handler`) resolves the actual `Stack`/`Repository`/`Commit` to mutate using a *different* field from the very same payload: `repository.full_name`. Nothing ties `repository.owner.login` to `repository.full_name`.

### Finding Description
`verify_signature` in [1](#0-0)  does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where `repository_owner` is `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [2](#0-1) . The `github_app` chosen this way owns a `webhook_secret` [3](#0-2) , and signature verification is `HMAC(secret, raw_post)` compared to `X-Hub-Signature` [4](#0-3) . If Shipit is configured for multiple organizations (documented multi-org config, `config/secrets.development.example.yml:18-38`), each org has its own webhook secret.

Once the signature check passes, handlers never re-check `repository.owner.login`. They instead resolve the target repository purely from `repository.full_name`:
```ruby
def repository_name
  payload.dig('repository', 'full_name')
end
``` [5](#0-4) 

`StatusHandler` uses `sha`/`state`/`context`/`description`/`target_url` from the body directly with no repository binding check at all — it just matches any `Commit` in the DB with a matching `sha` regardless of which org/stack it belongs to, and creates a `Status` from attacker-supplied fields [6](#0-5) . `PushHandler` similarly resolves stacks via `Repository.from_github_repo_name(repository_name)` (i.e., `repository.full_name`) [7](#0-6)  and triggers `stack.sync_github` for whatever `branch`/`after` the attacker supplied [8](#0-7) .

**The equality that should hold, but does not:** `organization used to select the verifying webhook_secret (repository.owner.login)` == `organization that owns the repository actually written (repository.full_name)`. Any attacker who controls an organization that Shipit is configured to trust (i.e., has installed the Shipit GitHub App on their own org and thus knows/derives a valid `webhook_secret` for it) can craft a JSON body where `repository.owner.login` = their own org (so the HMAC check passes using their own secret) while `repository.full_name` = a victim org/repo that Shipit also tracks. The signature is computed over the whole raw body (which the attacker fully controls, including both fields), so it verifies successfully, yet the handler acts on the victim's repository.

### Impact Explanation
Via `status` events, an attacker can forge arbitrary CI status entries (`state: success`, chosen `context`) for any commit SHA on a victim stack they don't own, as demonstrated by [9](#0-8) . `Status#schedule_continuous_delivery` and the state-machine transitions in `Commit` drive `stack.trigger_continuous_delivery`/`ContinuousDeliveryJob` when required CI contexts turn green [10](#0-9) , [11](#0-10) . Because required-status checks (`ci.require`) can be satisfied entirely by attacker-forged statuses on the victim's stack, this can cause an **unauthorized deploy** to be triggered for a stack the attacker has no legitimate access to — matching the Critical-severity "unauthorized deploy" criterion in scope. `push` events can similarly force `GithubSyncJob`/resyncs against a victim stack using attacker-chosen `ref`/`after` values.

### Likelihood Explanation
Exploitability requires only that the attacker control (or create) one organization that the Shipit deployment is configured to trust with a GitHub App installation/webhook secret — a routine, low-privilege setup for any multi-tenant or open Shipit instance supporting several orgs (as explicitly documented in `config/secrets.development.example.yml`). No Shipit session, `ApiClient` token, or GitHub write access to the *victim* repository is required, only the ability to install/own an app on a separate trusted org and POST to the public `/webhooks` endpoint — squarely an "unprivileged attacker" scenario per the rules.

### Recommendation
After signature verification, re-derive the organization strictly from `repository.full_name` (the field the handlers actually act on) and require it to match the `repository.owner.login`/`organization.login` used to select the signing secret, rejecting the payload if they diverge. Alternatively, bind the verified organization identity into the handler dispatch path so handlers only operate on repositories/stacks belonging to the organization whose secret validated the request.

### Proof of Concept
1. Attacker creates/owns GitHub org `attacker-org` and installs the same Shipit GitHub App there, obtaining a valid `webhook_secret` for `attacker-org` in Shipit's multi-org config.
2. Attacker crafts a `status` event body:
```json
{
  "sha": "<victim_stack_tracked_commit_sha>",
  "state": "success",
  "context": "ci/required-check",
  "description": "forged",
  "repository": { "full_name": "victim-org/victim-repo", "owner": { "login": "attacker-org" } }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(attacker-org's webhook_secret, raw_body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")`, whose secret matches, so `verified` is `true` (mirrors the exact flow validated in [12](#0-11) , just with a self-consistent org/secret pair the attacker controls).
5. `StatusHandler#process` finds `Commit.where(sha: params.sha)` — a commit belonging to `victim-org/victim-repo` — and calls `commit.create_status_from_github!(params)`, creating a forged "success" status on the victim's stack, which can satisfy `ci.require` and trigger continuous deployment.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

# frozen_string_literal: true

module Shipit
  class Status < Record
    include Common
    include DeferredTouch

    STATES = %w[pending success failure error].freeze
    enum :state, STATES.zip(STATES).to_h

    belongs_to :stack, required: true
    belongs_to :commit, required: true

    deferred_touch commit: :updated_at

    validates :state, inclusion: { in: STATES, allow_blank: true }, presence: true

    after_create :enable_ci_on_stack
    after_commit :schedule_continuous_delivery, :broadcast_update, on: :create

    delegate :broadcast_update, to: :commit

    class << self
      def replicate_from_github!(stack_id, github_status)
        find_or_create_by!(
          stack_id:,
          state: github_status.state,
          description: github_status.description,
          target_url: github_status.target_url,
          context: github_status.context,
          created_at: github_status.created_at
        )
      end
    end

    private

    def enable_ci_on_stack
      commit.stack.enable_ci!
    end

    def schedule_continuous_delivery
      commit.schedule_continuous_delivery
    end
  end
