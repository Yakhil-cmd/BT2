Based on my investigation, I found a concrete binding-break vulnerability in the webhook signature verification path.

### Title
Webhook signature verification authenticates a different field than the one used to select the target repository/stack, allowing forged events for arbitrary stacks - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and thus which `webhook_secret`) to verify a webhook's HMAC signature against using `repository_owner`, derived from `params.dig('repository','owner','login')` (falling back to `params.dig('organization','login')`). The event handlers, however, resolve the repository/stack to act on using a **different** field, `payload.dig('repository','full_name')`, in `Handler#repository_name`. These two payload fields are never cross-checked against each other, so a forged webhook body can be signed/authenticated as belonging to one organization while the mutating action is executed against a stack belonging to an entirely different, unrelated repository.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb:24-30` resolves the org used for signature verification: [1](#0-0) 

```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

Meanwhile every concrete handler (push, status, pull_request, etc.) resolves the target stacks via `Handler#repository_name`, which reads a *different* JSON key:
```
def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

Because `repository.owner.login` (used to pick which org's `webhook_secret` authenticates the request) and `repository.full_name` (used to pick which repository's stacks are acted upon) are independent, attacker-controlled JSON fields inside the same raw POST body, an attacker can craft a payload where these two fields point at different repositories/orgs. Additionally, `GitHubApp#verify_webhook_signature` is a no-op when no secret is configured for that org:
```
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [4](#0-3) 

`webhook_secret` is explicitly documented as *optional* per organization, and Shipit natively supports multi-organization configuration (`test/dummy/config/secrets_double_github_app.yml`), where different orgs can have different (or absent) `webhook_secret`s. [5](#0-4) [6](#0-5) 

**Attack path:** In a multi-org Shipit deployment where at least one configured organization has no `webhook_secret` set (a documented, supported configuration), an unauthenticated external attacker sends a POST to `/webhooks` with:
- `X-Github-Event`: e.g. `status`, `push`, `pull_request`, `check_suite`
- `repository.owner.login` = the org with no `webhook_secret` (or `organization.login` for org-level events)
- `repository.full_name` = a completely different, victim organization/repository that *is* tracked as a Shipit stack

`verify_signature` calls `Shipit.github(organization: repository_owner)`, obtains the no-secret org's `GitHubApp`, and `verify_webhook_signature` immediately returns `true` regardless of the (bogus) `X-Hub-Signature` header. The request proceeds to `WebhooksController#create`, which dispatches to handlers keyed only by `X-Github-Event`, and those handlers resolve `stacks` via `Repository.from_github_repo_name(repository_name)` — using the victim's `repository.full_name`, not the (unrelated, unauthenticated) `repository_owner`. [7](#0-6) 

### Impact Explanation
This breaks the equality that should hold: `org authenticated by signature == org whose repository is mutated`. Depending on which event type is forged, this can:
- Inject fake `status`/`commit_status` events for arbitrary commits on a victim stack (`StatusHandler`), corrupting deployability/merge-queue decisions and potentially causing an **unauthorized merge or deploy** to be triggered automatically by CI-status-driven merge queue logic.
- Forge `push` events, queuing `GithubSyncJob` for a victim stack.
- Forge `pull_request` events (opened/closed/labeled/etc.) affecting merge-queue state for a victim repository.

This matches the Critical/High impact categories: unauthorized deploy/rollback/merge via a spoofed cross-repository authorization boundary.

### Likelihood Explanation
Requires the deployment to run in the (supported, documented) multi-organization configuration with at least one organization lacking a `webhook_secret` — plausible since `webhook_secret` is explicitly optional and this is a first-class supported feature (`Shipit.github(organization:)` with per-org config, see `test/dummy/config/secrets_double_github_app.yml`). No credentials, tokens, or repository access are required — only knowledge that Shipit is deployed multi-org with a lax org, and the target stack's `owner/name`, both of which are typically discoverable/public.

### Recommendation
- Verify the webhook signature using the `webhook_secret` associated with the *actual* repository the event claims to act on (`repository.full_name`), not a separately-attacker-suppliable `repository.owner.login`/`organization.login` field.
- Cross-validate that `repository.owner.login` matches the owner portion of `repository.full_name` before dispatching to handlers.
- Consider making `webhook_secret` mandatory rather than optional, and reject/424 webhooks for orgs without a configured secret instead of silently returning `verified = true`.

### Proof of Concept
Assuming a multi-org Shipit config where `OrgLax` has no `webhook_secret` and `OrgVictim/critical-repo` is a tracked stack with a different (secret-protected) app config:

```
POST /webhooks HTTP/1.1
X-Github-Event: status
Content-Type: application/json
X-Hub-Signature: sha1=anything-invalid

{
  "repository": {
    "owner": { "login": "OrgLax" },
    "full_name": "OrgVictim/critical-repo"
  },
  "sha": "<victim-commit-sha>",
  "state": "success",
  "context": "ci/required-check",
  "branches": [{ "name": "master" }]
}
```

`verify_signature` selects `Shipit.github(organization: 'OrgLax')`, whose `verify_webhook_signature` returns `true` unconditionally (`webhook_secret` blank), so the forged signature is accepted. `StatusHandler` (via `Handler#repository_name`) then resolves stacks from `OrgVictim/critical-repo` and records a fake `success` status for the given SHA on the victim's tracked stack, despite the attacker never having any relationship with `OrgVictim`.

*Note:* I could not directly view `app/models/shipit/webhooks/handlers/status_handler.rb`/`push_handler.rb` file contents due to a tool error in the final iteration, so the exact downstream mutation logic (e.g., precisely how a forged `success` status feeds into merge-queue decisions) is inferred from the `Status`/`Commit` model references seen in `test/controllers/webhooks_controller_test.rb` and the `Handler` base class, not confirmed line-by-line in those specific handler files.
