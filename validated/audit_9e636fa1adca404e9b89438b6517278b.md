### Title
Webhook organization used for signature verification is decoupled from the repository target acted upon by handlers - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification based on `repository.owner.login` (or `organization.login`), both attacker-supplied JSON fields in the raw POST body. The actual repository that webhook handlers act upon is derived from a *different* field in the same payload — `repository.full_name` — read in `Shipit::Webhooks::Handlers::Handler#repository_name`. Nothing ties these two fields together, so a payload can be crafted where the "owner" used to pick the verifying secret differs from the "full_name" used to select the `Repository`/`Stack` that gets mutated.

### Finding Description
`verify_signature` computes the verifying GitHub App as: [1](#0-0) 
using [2](#0-1) 
i.e. `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` — both values taken straight from the unauthenticated, attacker-controlled request body (signature verification happens *after* `params` is read for this purpose but *before* the body is proven authentic for that org).

Meanwhile, every handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc.) resolves the target repository/stack via: [3](#0-2) 
which reads `payload.dig('repository', 'full_name')` — a field that is never cross-checked against `repository.owner.login`/`organization.login` used for signature selection.

In Shipit's multi-organization configuration mode, each organization has its own `webhook_secret`, looked up via: [4](#0-3) 
`Shipit.github(organization: repository_owner)` picks the secret purely from the attacker-supplied `owner.login`/`organization.login` field. If an attacker knows (or is entitled to, as an installer/admin of the GitHub App for) Organization A's webhook secret, they can POST a forged JSON body directly to the public `/webhooks` endpoint with:
- `repository.owner.login` = `"org-a"` (so `Shipit.github(organization: "org-a")` is used, whose secret the attacker knows and can HMAC-sign correctly)
- `repository.full_name` = `"org-b/victim-repo"` (an unrelated organization's real, already-configured Stack)

The HMAC is computed over the full raw body, but the secret chosen to verify it is picked from a field (`owner.login`) that is logically supposed to represent the same repository as `full_name` — and GitHub itself always keeps these consistent in genuine deliveries, but the engine never enforces that consistency itself, so nothing prevents an attacker from breaking it in a forged request.

This breaks the binding: **organization whose secret authenticated the signature == organization owning the repository actually written to**.

### Impact Explanation
With this decoupling, handlers can be triggered against a Stack belonging to an organization the attacker has no credentials for:
- `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` on any not-archived stack matching the forged `branch`, for a repository the attacker does not control the secret of. [5](#0-4) 
- `StatusHandler#process` writes a forged commit status directly against real `Commit` records, which can influence CI gating (`ci.require`/`ci.blocking`) used to unblock deploys. [6](#0-5) 

This is a cross-organization write into stacks/commits that should only be reachable by holders of that organization's own webhook secret, matching the High-impact category of escalation across a credential/repository trust boundary.

### Likelihood Explanation
Exploitation requires the attacker to know or legitimately hold a webhook secret for at least one organization configured in the multi-org Shipit deployment (e.g., because they administer the GitHub App installation for their own low-privilege org), then forge an unauthenticated POST to the shared `/webhooks` endpoint with mismatched `owner.login`/`full_name` fields. No GitHub session, `ApiClient` token, or Shipit account is required — only knowledge of one org's webhook secret, which is a realistic multi-tenant configuration scenario for this engine.

### Recommendation
Enforce that the organization/owner used to select the verifying secret is the same organization that owns `repository.full_name` before invoking handlers — e.g., derive the target repository's owner from the same trusted field used for signature verification, and reject the payload if `repository.full_name`'s owner segment does not match `repository.owner.login`/`organization.login`.

### Proof of Concept
1. Attacker controls/knows the `webhook_secret` configured for organization `org-a` in a multi-org Shipit deployment.
2. Attacker crafts a JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/victim-repo"
  }
}
```
3. Attacker computes `sha1=HMAC(webhook_secret_for_org_a, body)` and sends it as `X-Hub-Signature`, with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "org-a")` and successfully verifies the signature using `org-a`'s secret.
5. `PushHandler` is invoked with the full payload; `Handler#repository_name` returns `"org-b/victim-repo"`, and `stacks` resolves the real `org-b` Stack, triggering `sync_github` on it — despite the request never being authenticated for `org-b`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
