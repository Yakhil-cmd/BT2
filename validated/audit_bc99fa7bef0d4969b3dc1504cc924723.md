### Title
Cross-repository commit status forgery via unscoped `sha` lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates a webhook delivery against the GitHub organization named in the payload's `repository.owner.login` (or `organization.login`) field, then hands the *entire* raw payload to the matching event handler. `StatusHandler`, however, never re-checks that the commit it mutates actually belongs to that authenticated organization/repository: it looks up any `Commit` by `sha` alone and writes a status onto it. The binding that should hold — "the organization whose webhook secret signed this request" **equals** "the repository/stack whose commit gets written" — is never enforced.

### Finding Description
`WebhooksController#verify_signature` resolves the signing organization purely from attacker-suppliable payload fields: [1](#0-0) [2](#0-1) 

That check only proves the request was signed with *some* organization's configured `webhook_secret` (an org that legitimately owns a Shipit-connected GitHub App installation, e.g. the attacker's own org/repo). It says nothing about which `sha` the payload references.

`StatusHandler#process` then acts on the `sha` field with no repository/stack scoping at all: [3](#0-2) 

Compare this to every other handler in the codebase (`PushHandler`, `PullRequest::*Handler`), which all resolve `stacks`/`repository` via `Repository.from_github_repo_name(repository_name)` before acting: [4](#0-3) [5](#0-4) 

`StatusHandler` is the sole exception — it queries `Commit.where(sha: params.sha)` globally across the whole Shipit instance and calls `create_status_from_github!` on every match, which persists a `Status` and can flip the commit's CI state (deployable/mergeable): [6](#0-5) 

Because git commit SHAs are content-addressed, any two repositories sharing history — forks, mirrors, or repositories that cherry-pick/rebase the same commits — can contain `Commit` rows with an identical `sha` under two different `Stack`/`Repository` records in the same Shipit install. An attacker who legitimately owns (or controls a webhook-emitting integration on) **their own** authenticated organization can send a validly-signed `status` webhook whose `sha` matches a commit tracked in a **different** organization's stack, and Shipit will write that status onto the victim commit — something the attacker has no GitHub permission to do directly.

Equality that should hold and is broken:
`organization that signed this webhook == repository/stack whose Commit is mutated by the handler`

### Impact Explanation
A forged/malicious commit status can move a victim commit's CI state to `success`, satisfying `MergeRequest#all_status_checks_passed?` / `StatusChecker` required-status checks used by the merge queue (`app/models/shipit/merge_request.rb`) and `deployable?` gating used by deploy tooling. This can push an unreviewed or CI-failing commit into a state Shipit considers ready to merge or deploy in a repository the attacker does not control — an authorization escalation into cross-repository state that Shipit is specifically supposed to gate behind GitHub's own status/check permissions. This satisfies the "cross-repository writes" / unauthorized deploy or merge impact bar.

### Likelihood Explanation
High: the attacker needs no Shipit credentials, only the ability to trigger a legitimately-signed `status` webhook from an organization/App installation they already control (e.g., their own repo/CI integration), plus a commit SHA that happens to also be tracked as a `Commit` in a victim stack (realistic for forks/mirrors of popular repositories, which is a common Shipit deployment pattern). No race condition or timing dependency is required — the missing check is unconditional.

### Recommendation
Scope `StatusHandler#process` to the repository authenticated for this webhook delivery, mirroring every other handler:

```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```

using the inherited `stacks`/`repository_name` helpers from `Shipit::Webhooks::Handlers::Handler`, so a commit can only be updated by a status event whose signed repository/organization matches the stack that owns it.

### Proof of Concept
1. Attacker controls (or has installed a GitHub App on) organization `attacker-org`, which is a valid, separately-configured entry under `Shipit.github` with its own `webhook_secret`.
2. Attacker forks (or otherwise shares history with) the victim's tracked repository `victim-org/app`, so a specific commit `sha=deadbeef…` exists both in `attacker-org/app` (attacker's fork) and is already tracked as a `Shipit::Commit` under the `victim-org/app` stack.
3. Attacker triggers (via their own CI integration, which is entitled to POST status events for their own repo) a `status` webhook: `{"sha": "deadbeef…", "state": "success", "context": "ci/required", "repository": {"owner": {"login": "attacker-org"}}}`. GitHub signs this with `attacker-org`'s webhook secret.
4. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "attacker-org")` and successfully verifies the signature (it is legitimately signed).
5. `StatusHandler#process` executes `Commit.where(sha: "deadbeef…")` with no repository filter, finds the `victim-org/app` commit, and calls `create_status_from_github!`, marking the victim's commit `ci/required: success` even though `victim-org` never emitted this event. [7](#0-6)
