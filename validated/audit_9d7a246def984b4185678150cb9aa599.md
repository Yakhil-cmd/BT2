### Title
`BridgeTransferERC721.handleERC721Transfer` Uses `transferFrom` Instead of `safeTransferFrom`, Permanently Locking Bridged ERC721 Assets — (`contracts/service_chain/bridge/BridgeTransferERC721.sol`)

---

### Summary

`BridgeTransferERC721.handleERC721Transfer` uses the bare `IERC721.transferFrom` to deliver a bridged NFT to the destination address. Unlike `safeTransferFrom`, `transferFrom` does not invoke `onERC721Received` on the recipient and does not revert when the recipient is a contract that does not implement `IERC721Receiver`. Because all bridge state updates (nonce advancement, handled-request-hash recording, event emission) are committed **before** the token transfer, a delivery to a non-receiver contract silently succeeds on-chain while the NFT is permanently trapped, with no mechanism to retry or recover.

---

### Finding Description

`BridgeTransferERC721.sol` imports `IERC721` but does **not** apply any safe-transfer wrapper analogous to the `SafeERC20` pattern used in `BridgeTransferERC20.sol`.

In the non-`modeMintBurn` path of `handleERC721Transfer`:

```solidity
// contracts/service_chain/bridge/BridgeTransferERC721.sol  line 69
IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId);
``` [1](#0-0) 

This is called **after** the bridge has already:
1. Passed `_lowerHandleNonceCheck` and `_voteValueTransfer`
2. Written `_setHandledRequestTxHash(_requestTxHash)`
3. Written `handleNoncesToBlockNums[_requestedNonce] = _requestedBlockNumber`
4. Called `_updateHandleNonce(_requestedNonce)`
5. Emitted `HandleValueTransfer` [2](#0-1) 

The `IERC721` interface exposes both `transferFrom` and `safeTransferFrom`:

```solidity
function safeTransferFrom(address from, address to, uint256 tokenId) public;
function transferFrom(address from, address to, uint256 tokenId) public;
``` [3](#0-2) 

The OpenZeppelin ERC721 implementation's `transferFrom` does **not** call `_checkOnERC721Received`; only `safeTransferFrom` does. Therefore, when `_to` is a contract that does not implement `IERC721Receiver`, `transferFrom` completes without reverting, the NFT is owned by that contract, and the contract has no way to move it. Because all bridge state was already committed, the nonce is consumed and the request hash is marked handled — the bridge permanently considers the transfer complete.

By contrast, `BridgeTransferERC20.sol` correctly applies `using SafeERC20 for IERC20` and calls `safeTransfer`/`safeTransferFrom` throughout:

```solidity
// BridgeTransferERC20.sol line 29
using SafeERC20 for IERC20;
// line 71
IERC20(_tokenAddress).safeTransfer(_to, _value);
// line 133
IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
``` [4](#0-3) [5](#0-4) [6](#0-5) 

No equivalent protection exists for ERC721 delivery.

---

### Impact Explanation

When `_to` is a contract that does not implement `IERC721Receiver` (e.g., a multisig wallet, a DeFi vault, or any arbitrary smart contract):

- `transferFrom` succeeds silently — the NFT is now owned by `_to` but `_to` cannot transfer or use it.
- All bridge state (nonce, handled-request hash) is already finalized; the request cannot be replayed or retried.
- The bridged ERC721 asset is **permanently lost** from the user's perspective with no on-chain recovery path.

This constitutes an unauthorized permanent loss of bridged assets, matching the allowed impact gate: *"Unauthorized transfer, mint, unlock, burn, fee charge, reward distribution, or key/nonce consumption affecting KAIA, bridged assets, or system-managed funds."*

---

### Likelihood Explanation

The `_to` address is set by the user on the source chain when calling `requestERC721Transfer`. Any user who specifies a contract address that does not implement `IERC721Receiver` as the destination will trigger this path. This is a realistic scenario: users commonly bridge NFTs to multisig wallets, DAO treasuries, or protocol contracts. The bridge provides no warning or guard, and the loss is irreversible once operators submit the quorum of `handleERC721Transfer` votes.

---

### Recommendation

Replace `transferFrom` with `safeTransferFrom` in `handleERC721Transfer`:

```solidity
// Before
IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId);

// After
IERC721(_tokenAddress).safeTransferFrom(address(this), _to, _tokenId);
``` [7](#0-6) 

Note: `requestERC721Transfer` correctly uses `transferFrom` (not `safeTransferFrom`) to pull the token **into** the bridge, because the bridge contract itself does not implement `IERC721Receiver` and `safeTransferFrom` would revert. That usage is intentional and should not be changed. [8](#0-7) 

---

### Proof of Concept

1. Deploy a standard ERC721 token and register it on both the source and destination bridge contracts.
2. On the source chain, call `requestERC721Transfer(tokenAddress, contractThatLacksIERC721Receiver, tokenId, "")`. The token is pulled into the bridge via `transferFrom`; `RequestValueTransferEncoded` is emitted and `requestNonce` increments.
3. On the destination chain, operators submit quorum votes via `handleERC721Transfer(txHash, from, contractThatLacksIERC721Receiver, tokenAddress, tokenId, nonce, blockNum, uri, "")`.
4. The bridge commits all state updates (nonce, handled hash) and then calls `IERC721(tokenAddress).transferFrom(address(this), contractThatLacksIERC721Receiver, tokenId)`.
5. The call succeeds (no revert). The NFT is now owned by `contractThatLacksIERC721Receiver`, which has no `onERC721Received` and cannot transfer it.
6. The bridge nonce is consumed; the request hash is marked handled. The NFT is permanently locked with no recovery path. [9](#0-8)

    function handleERC721Transfer(
        bytes32 _requestTxHash,
        address _from,
        address _to,
        address _tokenAddress,
        uint256 _tokenId,
        uint64 _requestedNonce,
        uint64 _requestedBlockNumber,
        string memory _tokenURI,
        bytes memory _extraData
    )
        public
        onlyOperators
    {
        _lowerHandleNonceCheck(_requestedNonce);

        if (!_voteValueTransfer(_requestedNonce)) {
            return;
        }

        _setHandledRequestTxHash(_requestTxHash);

        handleNoncesToBlockNums[_requestedNonce] = _requestedBlockNumber;
        _updateHandleNonce(_requestedNonce);

        emit HandleValueTransfer(
            _requestTxHash,
            TokenType.ERC721,
            _from,
            _to,
            _tokenAddress,
            _tokenId,
            _requestedNonce,
            lowerHandleNonce,
            _extraData
        );

        if (modeMintBurn) {
            require(ERC721MetadataMintable(_tokenAddress).mintWithTokenURI(_to, _tokenId, _tokenURI), "mint failed");
        } else {
            IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId);
        }
    }
