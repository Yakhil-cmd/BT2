### Title
Webhook signature verified against `repository.owner.login`'s secret while handlers act on the unrelated `repository.full_name` field, enabling cross-organization webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the HMAC signature with based on `repository.owner.login` (or `organization.login`) pulled straight out of the untrusted JSON body, then verifies the HMAC over the raw payload bytes with that secret only. However, once the signature check passes, `create` hands the very same untrusted payload to `Shipit::Webhooks::Handlers::Handler`, whose `repository_name` (used to resolve the target `Repository`/`Stack`) reads `payload.dig('repository', 'full_name')` — a completely independent field of the same JSON body that is never cross-checked against `repository.owner.login`. The HMAC therefore only proves "this byte blob was produced by someone who knows OrgA's secret", not "this event pertains to a repository actually owned by OrgA", exactly mirroring the `OnChainLab::isValidSignature` bug where a valid signature is accepted without binding it to the specific account/target it is meant to authorize.

### Finding Description
In a documented multi-org Shipit deployment (`docs/setup.md:182-209`, `config/secrets.development.shopify.yml`), each GitHub organization has its own independent `webhook_secret`, looked up via `Shipit.github(organization: repository_owner)`: [1](#0-0) [2](#0-1) 

`lib/shipit.rb#github` resolves a per-organization `GitHubApp` and secret from config: [3](#0-2) 

`GitHubApp#verify_webhook_signature` then HMACs the *entire raw body* with that org-specific secret: [4](#0-3) 

Once verification succeeds, `create` re-parses the same JSON and dispatches it to handlers: [5](#0-4) 

Every handler (e.g. `PushHandler`) resolves its target repository/stack from `repository.full_name`, a field never compared to `repository.owner.login`: [6](#0-5) [7](#0-6) 

The binding that should hold is: `organization whose secret authenticated the request == owner of the repository/stack being acted on`. Because the signature only authenticates raw bytes and `repository.owner.login`/`organization.login` are attacker-controlled fields inside those same bytes, an attacker who knows OrgA's `webhook_secret` can craft a payload with `repository.owner.login = "OrgA"` (so `verify_signature` picks OrgA's secret and passes) but `repository.full_name = "OrgB/some-tracked-repo"` (a repository belonging to a different organization tracked by the same Shipit instance). The HMAC is computed correctly over these attacker-chosen bytes using the known OrgA secret, so it passes verification, yet `PushHandler` (or the `pull_request`/`status`/`check_suite` handlers, all of which key off `repository.full_name`) will act on OrgB's stack — e.g. triggering `stack.sync_github(expected_head_sha: ...)`, updating commit statuses, or closing/merging pull requests.

### Impact Explanation
This crosses a repository/organization write boundary: a party who only has legitimate knowledge of one organization's webhook secret (a plausible “unprivileged relative to other tenants” actor in a shared/multi-org Shipit deployment) can inject forged GitHub events that Shipit will apply to a different organization's stacks — forcing `GithubSyncJob`s, poisoning commit `Status`, or manipulating merge/pull-request state cross-repository, without ever having credentials for that other organization. This matches the High/Critical category "cross-repository writes" / "unauthorized deploy" defined in scope, since sync/status manipulation can influence CI gating and downstream automatic deploys tied to those statuses.

### Likelihood Explanation
Requires the deployment to use the documented multi-organization `github:` config (an explicitly supported, documented setup) and requires the attacker to know one tenant's webhook secret — a secret that tenant's own GitHub App administrator legitimately possesses. No Shipit session, `ApiClient` token, or repository write access on the *victim* org is needed; only a single HTTP POST to the public `/webhooks` endpoint with a correctly computed HMAC is required.

### Recommendation
After verifying the HMAC, cross-check that `repository.owner.login` (the field used to select the verification secret) matches the owner segment of `repository.full_name` (the field used to resolve the target stack), rejecting the event if they diverge. More robustly, resolve the target repository/stack strictly from the same organization context the signature was verified against, rather than trusting an independent field from the unauthenticated-until-that-point payload.

### Proof of Concept
1. Deploy Shipit with multi-org config: OrgA (`webhook_secret: secretA`) and OrgB (`webhook_secret: secretB`), both with repositories tracked as Shipit stacks.
2. Attacker (who knows `secretA`, e.g., an OrgA GitHub App admin) crafts a push payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```
3. Attacker computes `sha1=HMAC-SHA1(secretA, raw_body)` and sets it as `X-Hub-Signature`, with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgA")` (from `repository.owner.login`), verifies the HMAC against `secretA` — passes. [1](#0-0) 
5. `create` dispatches to `PushHandler`, which resolves `stacks` via `Repository.from_github_repo_name("OrgB/victim-repo")`, and queues `sync_github(expected_head_sha: "<attacker-chosen-sha>")` against OrgB's stack — despite the request never being authenticated by OrgB's secret. [7](#0-6)
