### Title
Missing cosigner verification allows any paired device to request signing on a victim's local wallet addresses - (File: wallet.js)

### Summary
`ocore`'s wallet message handler for the `"sign"` subject (received from any paired/correspondent device through the hub) is supposed to verify that the device requesting a signature is actually a legitimate cosigner of the target address before honoring the request. That check has been explicitly commented out, so any device that is merely paired with the wallet (not necessarily a cosigner of the relevant shared/multisig address) can send a `"sign"` request for an arbitrary `unsigned_unit` and have it processed by the local wallet.

`from_address` is the sender's device address, taken directly from `objectHash.getDeviceAddress(device_pubkey)` of the incoming device message and is fully attacker-controlled by any correspondent (paired) device — no relationship to `body.address`'s wallet/shared address is verified. `findAddress` returns `ifLocal` whenever the requested `address`/`signing_path` combination resolves to a key that is hosted on the local device (either the user's own single-sig address, or a leaf key inside a shared/multisig address definition): [2](#0-1) 

Once `ifLocal` fires, the handler unconditionally calls `callbacks.ifOk()` and proceeds to emit a `"signing_request"` event carrying the attacker-supplied `objUnit` (payment outputs, amounts, recipients are all attacker controlled) for the address in question: [3](#0-2) 

This is a direct CWE-285 Incorrect Access Control: the intended access check (only real cosigners of `body.address` should be able to solicit a signature) is disabled, so authorization is effectively based only on the weaker "you are a paired device" relationship rather than "you are a cosigner of this specific address." This mirrors the CVE's root cause — a protocol/message handler that dropped access-control enforcement, letting a peer request/act on data it should not be authorized to access.

### Impact Explanation
Any device that has completed the pairing protocol (`device.handlePairingMessage`, reachable by anyone knowing/guessing a pairing secret or via the `'*'` permanent-secret path) becomes a "paired device" able to reach this code path. In deployments where signing is automated (headless bot wallets, exchange/service wallets, or multisig setups where local logic auto-signs requests coming from expected correspondent devices without a manual per-request human review), this allows an unrelated paired device to solicit and obtain a signature over an attacker-chosen payment/transaction body for the victim's own address, leading to unauthorized spending of the victim's funds. Because the check that constrained requests to legitimate cosigners (`extended_pubkeys` wallet/device_address membership) was removed, the wallet cannot distinguish "trusted cosigner requesting my share of a multisig payment" from "arbitrary paired device requesting me to sign anything for any of my locally-hosted addresses."

### Likelihood Explanation
Reachability requires only that the attacker's device be paired with the victim (an ordinary correspondent relationship established via `pairing_secret`/permanent pairing code — a normal, low-friction operation), then send a crafted `"sign"` device message. No AA, unit-posting, or on-chain action is needed; this is a pure wallet-message-handling flaw exploitable directly against any correspondent.

### Recommendation
Restore (and generalize) the removed check: before honoring a `"sign"` request for a locally-hosted address, verify that `from_address` is actually one of the recognized cosigning device addresses for `body.address` (e.g., via `extended_pubkeys`/`wallet_signing_paths` for wallet-owned addresses and `shared_address_signing_paths` for shared addresses), rejecting requests from devices that are not part of that address's definition.

### Proof of Concept
1. Attacker device pairs with the victim's wallet (normal pairing flow).
2. Attacker sends a `hub/message`/`"sign"` device message with `body.address` = one of the victim's local addresses (own address or a shared-address leaf hosted locally) and `body.signing_path` matching a valid path, along with a `body.unsigned_unit` whose payment outputs send funds to an attacker-controlled address.
3. `handleMessageFromHub` → `case "sign"` → `findAddress(...).ifLocal` is invoked; because the commented-out cosigner check is absent, `callbacks.ifOk()` is called and a `"signing_request"` event is emitted for this attacker-crafted unit, using the victim's local key material or automated signer to complete the malicious transaction.
