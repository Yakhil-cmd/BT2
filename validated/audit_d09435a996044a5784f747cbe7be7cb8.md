Confirmed: `create!` adds the stack to `Shipit::ReviewStackProvisioningQueue`, which drives the automatic provisioning task pipeline (running `Command`/`PTY.spawn`-backed tasks) for the PR's branch.### Title
`provision?` ignores `review_stacks_enabled` for `allow_with_label`/`prevent_with_label` behaviors due to `&&`/`||` operator precedence - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`PullRequest::OpenedHandler#provision?` is written as `a && b || c || d`, which Ruby parses as `(a && b) || c || d`, so `review_stacks_enabled` only gates the `allow_all` branch and is never checked for the `allow_with_label` or `prevent_with_label` branches. `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` never exercises `review_stacks_enabled: false` combined with `allow_with_label`/`prevent_with_label`, so this divergence is unverified by the test suite.

### Finding Description
The claimed binding is: `review_stacks_enabled == true` is required for `provision?` to return `true`, for every `provisioning_behavior`. Tracing the code: [1](#0-0) 

parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`. This means:
- If `review_stacks_enabled == false`, `allow_with_label? == true`, and the PR carries the configured label, `provision?` returns `true`.
- If `review_stacks_enabled == false`, `prevent_with_label? == true`, and the PR does NOT carry the label, `provision?` also returns `true`.

Both diverge from the claimed binding — `review_stacks_enabled` is bypassed for two of the three behaviors. This is a genuine logic bug in the shipped code, not merely a testing gap.

The path from `process` calls `respond_to_pull_request_opened?` → `provision?`, and if true, `ReviewStackAdapter#find_or_create!` runs `create!`, which persists a `ReviewStack` and immediately calls `Shipit::ReviewStackProvisioningQueue.add(stack)`: [2](#0-1) 
This queue drives the asynchronous provisioning task pipeline (task execution against the stack's environment/branch), so an incorrectly-true `provision?` produces real downstream task execution, not just a harmless database row.

Checking the test file confirms the gap: every `allow_with_label`/`prevent_with_label` test uses the default fixture value for `review_stacks_enabled` (true) via `configure_provisioning_behavior`, which defaults `provisioning_enabled: true`: [3](#0-2) [4](#0-3) 
The only test that sets `provisioning_enabled: false` uses `behavior: :allow_all`: [5](#0-4) 
— the one branch where `review_stacks_enabled` IS correctly ANDed in, so this existing test cannot reveal the bug. No test sets `review_stacks_enabled: false` together with `allow_with_label` (or `prevent_with_label`).

No existing guard prevents this: `respond_to_pull_request_opened?` only checks `params.action == "opened"` before calling the buggy `provision?`; there is no separate `review_stacks_enabled` check anywhere else in the call path.

### Impact Explanation
When a repository administrator sets `provisioning_behavior = allow_with_label` (with a label configured) and later flips `review_stacks_enabled` to `false` intending to fully disable automatic review-stack provisioning, an unprivileged attacker who can open a pull request on that repository and attach the configured label can still cause `Shipit::Stack`/`ReviewStack` creation and enqueue it into `ReviewStackProvisioningQueue`, triggering the provisioning task pipeline against attacker-controlled branch/commit content. This is repeatable per pull request and per repository that has ever been configured this way, and it defeats the administrator's explicit intent to disable provisioning. Whether this alone rises to "Critical RCE" depends on what the provisioning task pipeline executes (that execution path is downstream of this handler and outside this file), but at minimum it is an unauthorized stack-provisioning/task-execution trigger bypassing an explicit operator-configured safety switch (`review_stacks_enabled`), matching a High/Critical-adjacent "unauthorized deploy/provision" impact.

### Likelihood Explanation
Preconditions: the repository must be tracked in Shipit, `provisioning_behavior` must be `allow_with_label` or `prevent_with_label` with a configured label, and `review_stacks_enabled` must be `false` at the time of the PR event — a configuration state entirely plausible for any administrator who toggles `review_stacks_enabled` off without also resetting `provisioning_behavior` to `allow_all`/default. No secrets, tokens, or elevated GitHub permissions are required by the attacker; opening a PR and applying a label on their own fork is sufficient. This is a pure code-logic bug (operator precedence), so it is 100% reproducible whenever the configuration precondition holds.

### Recommendation
Add explicit parentheses/`review_stacks_enabled &&` to every branch:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Apply the same fix to `LabeledHandler`, `UnlabeledHandler`, and `ReopenedHandler`, which contain the identical pattern per the grep results.

### Proof of Concept
```ruby
test "does not create stacks for allow_with_label when review_stacks_enabled is false" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :allow_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Against the current implementation, `repository.review_stacks_enabled` is `false` but `provisioning_behavior_allow_with_label?` is `true` and the label matches, so `provision?` returns `true` and this assertion fails (a stack IS created), demonstrating the binding `review_stacks_enabled == true` is not actually enforced for this branch.
