### Title
Webhook signature validated against the organization named in `repository.owner.login` while all event handlers act on the repository named in `repository.full_name` — cross-organization webhook forgery in multi-tenant GitHub App config - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate the incoming HMAC signature against by reading an **unverified** field of the payload, `repository.owner.login` (or `organization.login`), and looks up the corresponding secret via `Shipit.github(organization: repository_owner)`. [1](#0-0) 

Every actual event handler, however, resolves the repository/stack to mutate using a **different** field of the same payload, `repository.full_name`. [2](#0-1) 

Because signature verification is scoped to the org derived from `repository.owner.login` while all business logic is scoped to `repository.full_name`, an attacker who legitimately controls a GitHub App installation (and its webhook secret) for their *own* organization in a multi-tenant Shipit deployment can sign a payload where `repository.owner.login` equals their own org (so the correct secret is selected and the signature check passes) but `repository.full_name` names a repository belonging to a completely different, victim organization also hosted on the same Shipit instance.

### Finding Description
`Shipit.github` supports a multi-organization credential schema: `secrets.github` can be keyed by organization name, each with its own `webhook_secret`, and `github_app_config(organization)` performs a case-insensitive lookup of that org's specific config. [3](#0-2) 

The binding that should hold is:
`organization whose secret verified the HMAC == organization owning the repository whose Stack is mutated`

In `verify_signature`, the org used to pick the secret is taken from the payload itself, before any cryptographic check:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [4](#0-3) 

and:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
``` [5](#0-4) 

`verify_webhook_signature` performs a straightforward HMAC comparison using whichever org's secret was selected: [6](#0-5) 

Once verification succeeds, handlers dispatch purely based on `repository.full_name` — a field that was never cross-checked against `repository.owner.login`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [2](#0-1) 

The `push` handler test confirms this dispatch triggers a `GithubSyncJob` keyed on the payload's `stack_id`/`sha`, and the `status` handler test confirms an attacker-controlled payload directly creates a `Status` record (state/description/target_url) on an existing commit: [7](#0-6) 

Because `repository.owner.login` (used for auth) and `repository.full_name` (used for the actual write) are two independent, attacker-controlled JSON fields inside the same signed body, an attacker who signs with **their own** org's legitimate webhook secret can set `repository.owner.login` to their own org (to pass `verify_signature`) while setting `repository.full_name` to `victim-org/victim-repo` (to target another tenant's `Stack`).

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" binding explicitly called out as in-scope. Concretely, an attacker who administers only their own org's GitHub App installation can:
- Forge a `status` webhook that creates arbitrary CI status records (`state: success`, forged `context`/`description`) on commits belonging to a victim stack they do not own, which can satisfy `ci.require` and blocking-status gates and enable an **unauthorized deploy** of a victim stack.
- Forge `push`/`check_suite`/`membership` events that enqueue jobs (`GithubSyncJob`, `RefreshCheckRunsJob`) operating on a victim stack's data, i.e. **cross-repository writes** into another tenant's Shipit data.

This matches the Critical impact bar ("cross-repository writes" / "an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Exploitability is limited to Shipit deployments using the multi-organization credentials schema (`secrets.github` keyed by multiple orgs, i.e. a Shipit instance shared across several GitHub orgs/tenants) — this is precisely the scenario the "multi-org" config format in `lib/shipit.rb` (`github_app_config`, `github_organizations`) is built to support. [8](#0-7)  In that configuration, the attacker needs no privilege on the victim org — only legitimate control of a GitHub App/webhook secret for their own, unrelated org — which satisfies the "unprivileged attacker" requirement. In the (also common) single-organization schema this analog collapses (`github_default_organization` is `nil`, and there is only one secret for one org), so likelihood depends on multi-tenant hosting being in use.

### Recommendation
After signature verification succeeds, cross-check that the organization used to select the webhook secret (`repository.owner.login` / `organization.login`) actually matches the owner portion of `repository.full_name` used by all handlers, and reject (422) the webhook if they diverge. Alternatively, derive the single "authenticated organization" once and pass it explicitly into every handler instead of letting handlers re-derive the target repository from an independent, unauthenticated field of the same payload.

### Proof of Concept
1. Shipit is configured with `secrets.github` keyed by two organizations: `attacker-org` (with its own `webhook_secret`) and `victim-org` (hosting a Shipit `Stack` for `victim-org/app`), per the multi-org schema in `lib/shipit.rb`.
2. Attacker, who legitimately administers `attacker-org`'s GitHub App, crafts a `status` (or `push`) webhook JSON body:
   ```json
   {
     "repository": {
       "owner": { "login": "attacker-org" },
       "full_name": "victim-org/app"
     },
     "sha": "<known victim commit sha>",
     "state": "success",
     "context": "ci/required-check",
     "target_url": "https://ci.example.com/forged"
   }
   ```
3. Attacker computes `X-Hub-Signature` using `attacker-org`'s real webhook secret over the raw body.
4. `WebhooksController#verify_signature` computes `repository_owner` = `"attacker-org"`, fetches `attacker-org`'s secret, and the HMAC check passes (`app/controllers/shipit/webhooks_controller.rb:24-30,59-62`).
5. The `status` handler resolves the target repository via `repository.full_name` = `"victim-org/app"` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`) and creates/updates a `Status` on the victim's commit, as shown by the equivalent flow in `test/controllers/webhooks_controller_test.rb:42-59`, potentially satisfying `ci.require`/blocking-status checks and permitting an unauthorized deploy of `victim-org/app`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
