### Title
Secondary AA bounce forces `revert()` of the entire primary AA response, allowing a caller-chosen downstream AA to grief/block legitimate multi-AA fund flows - (File: aa_composer.js)

### Summary
`ocore`'s AA engine chains AA execution: when a primary (or intermediate) AA sends outputs to another AA address, that address is automatically triggered as a "secondary trigger" within the same atomic evaluation via `handleSecondaryTriggers()`. If that secondary AA bounces for any reason, the error is propagated back up and the *entire* primary trigger's already-computed state changes and outputs are unwound with `revert()`, exactly mirroring the TRST-H-2 pattern where a downstream/child component's failure aborts the parent's otherwise-valid operation.

### Finding Description
In `handleTrigger()`, after a unit is composed for an AA, any outputs directed to other AA addresses are recursively executed as secondary triggers: [1](#0-0) 
The recursive call sets `bSecondary = true`; its `onDone` callback converts a bounce into an `async.eachSeries` error: [2](#0-1) 
When any secondary AA in the chain bounces, the series callback checks whether the current context is itself secondary (propagate the bounce upward) or primary — in the primary case it calls `revert()`, explicitly framing it as "one of secondary AAs bounced": [3](#0-2) 
`revert()` then rolls back the database savepoint, clears all state-var changes and the pending write batch, and discards every response accumulated in `arrResponses` for the whole chain, before finally bouncing the original trigger: [4](#0-3) 
This means the correctness or availability of a primary AA's legitimate operation (e.g., a vault-style AA performing a withdrawal that forwards part of the funds to a user-specified AA address, as seen in the `fundraising_proxy.oscript` pattern of forwarding funds to a `$destination_aa`) is entirely at the mercy of any downstream AA reachable from its outputs. If that downstream AA bounces — because it lacks sufficient balance/state, hits `MAX_RESPONSES_PER_PRIMARY_TRIGGER`, or is deliberately written/manipulated to always bounce — the whole chain (including the primary AA's own otherwise valid state updates and payouts to unrelated third parties) is discarded and only a bounce-fee-minus refund is returned to the original trigger sender. [5](#0-4) 

### Impact Explanation
Any unprivileged unit poster who can get a primary AA to route part of its payment to an AA address they control (or that already exists and can be induced to bounce, e.g. by exhausting the shared `MAX_RESPONSES_PER_PRIMARY_TRIGGER` cap for the whole chain) can force the entire multi-AA transaction to be reverted. This blocks legitimate users' interactions with the primary AA (their withdrawal/operation silently fails and their bytes only partially return via the bounce fee), denying availability of funds/operations that should otherwise succeed — directly analogous to the reported "lack of child rewarder reserves" issue where a child's failure freezes a parent's fund-releasing call.

### Likelihood Explanation
Likelihood is limited by the fact that any account can freely create AAs and simply post a trigger; no privileged access is required. The main friction is that the attacker needs the primary AA's logic to route a payment to an address of the attacker's choosing (or an existing AA it depends on) — which is a common composability pattern in ocore AAs (e.g. proxy/forwarder AAs). Where such a pattern exists, triggering the griefing is straightforward and repeatable, though it only prevents/delay execution rather than steal funds; the affected user can typically retry with a different destination once aware.

### Recommendation
For chained AA calls where the primary AA does not need its own execution to be contingent on the secondary AA succeeding, provide (or default to) semantics where a secondary trigger's bounce does not `revert()` the whole primary response — e.g., treat a bouncing secondary AA the same as a failed/no-op payment attempt to that address without unwinding the primary AA's own already-valid state changes and unrelated outputs, or clearly document/limit that composability so AA authors are aware that any downstream AA in the payment graph can currently veto the entire transaction and must design fee/order-of-output accordingly.

### Proof of Concept
1. Deploy AA `Blocker` whose only message always calls `bounce("always fails")`.
2. Deploy AA `Vault` that, upon a valid withdrawal trigger, sends outputs both to the requesting user and to an address supplied in `trigger.data` (a common forwarder/proxy pattern, cf. `test/samples/fundraising_proxy.oscript`).
3. Any unprivileged user posts a trigger to `Vault` specifying `Blocker`'s address as the forwarding destination.
4. `Vault`'s state-var updates and payment to the legitimate user are computed, but because `Blocker` is triggered as a secondary AA and bounces, `handleSecondaryTriggers()` reports the error and `revert()` unwinds all of `Vault`'s state changes and outputs for that trigger, per `aa_composer.js:1743-1783`, causing the withdrawal to fail entirely instead of only the forwarded leg.
