### Title
Bounce mechanism discards refunds for all trigger assets when a single asset's amount is below its configured `bounce_fees` - (File: aa_composer.js)

### Summary
The Velar-Artha report describes a "growing liability exceeds available principal" bug class: a fee that accrues over time can exceed the value it's deducted from, and the code path that would normally return the remaining funds to the user has no fallback for that condition, so funds become permanently unrecoverable through the normal exit path. Searching ocore's AA engine for an analogous "fee-vs-amount comparison with no partial-refund fallback" pattern turns up the `bounce()` function in `aa_composer.js`, which is executed on every AA trigger that fails its formulas/conditions and is the mechanism that is supposed to return a trigger sender's assets (minus the AA's configured `bounce_fees`) back to them.

### Finding Description
When an AA bounces a trigger, `aa_composer.js` iterates over every asset sent in `trigger.outputs` and tries to build one refund payment message per asset: [1](#0-0) 

For each asset it computes `fee = bounce_fees[asset] || 0` and:
```
if (fee > amount)
    return finish(null);
```
Crucially, this is a `return`, not a `continue`. If the trigger sends **multiple assets** together (base bytes plus one or more custom assets, which is a normal, unprivileged multi-asset payment any trigger sender can construct), and just **one** of those assets has an amount smaller than the AA's `bounce_fees` entry for that asset, the loop aborts immediately via `finish(null)` — abandoning the refund for **every other asset already accumulated in `messages`**, even assets whose amounts vastly exceed their fee. No partial bounce is issued for the assets that were sufficient; the sender simply loses all of them, and the AA absorbs them with no accounting, no state update, and no message reflecting the retained funds.

This mirrors the reported bug class: a comparison between an accruing fee and an available amount, where exceeding the fee on one item silently forecloses recovery of otherwise-recoverable value that should have been split/refunded independently, with no error surfaced to the actor and no way to reclaim the value afterward (the outputs are already consumed as trigger inputs and there is no other engine-provided path to get them back).

### Impact Explanation
Any unprivileged AA trigger sender who sends a multi-asset payment to an AA that (a) has `bounce_fees` configured for more than one asset and (b) ends up bouncing (e.g., due to a condition failing, insufficient balance, or any other formula-level `bounce()`), loses the entirety of all assets in that trigger — not just the intentionally-configured `bounce_fees` — as soon as one asset's amount is below its own fee threshold. This is a concrete, unrecoverable loss of user funds (AA fund loss for the trigger sender) triggered purely by ordinary interaction with a published AA, not by a malicious peer/node/hub. It maps to the sherlock report's "value the user is entitled to becomes permanently unreachable due to an unconditional early exit in the refund/close path."

### Likelihood Explanation
This requires no special privilege or malicious counterparty — it can be triggered by any user sending a legitimate multi-asset trigger, or accidentally by a user who slightly miscalculates one of several output amounts relative to the AA's declared `bounce_fees`. AAs that accept multiple assets and declare per-asset `bounce_fees` (a documented, supported feature — see `bounce_fees: { base: ... }` used across the AA test/sample suite) are directly exposed. The bug is deterministic given the described input; only the specific combination of multi-asset trigger + one under-threshold asset is needed, which is easily reproducible.

### Recommendation
In the `bounce()` loop in `aa_composer.js`, replace the `return finish(null)` inside the `for (var asset in trigger.outputs)` loop with a `continue` (skipping only that asset, forfeiting solely its `bounce_fees` amount), while still emitting refund payment messages for all other assets whose amount exceeds their fee. Alternatively, pre-compute which assets are refundable before building any messages, and only fall back to "no bounce at all" when the base-asset check (`trigger.outputs.base < bounce_fees.base`, needed to cover the response unit's own cost) fails, since that is a genuine fee-insufficiency case, not a fee-exceeds-one-of-several-independent-amounts case.

### Proof of Concept
1. Deploy an AA with `bounce_fees: { base: 10000, ASSET_X: 5000 }` and a trigger condition formula that always bounces for a given `trigger.data` value (e.g., an invalid withdraw request), similar to `test/samples/just_a_bouncer.oscript`. [2](#0-1) 
2. Send a trigger unit with two payment outputs to the AA: `base: 1_000_000` and `ASSET_X: 4000` (i.e., below the 5000 `bounce_fees.ASSET_X`).
3. The AA formula fails, `bounce()` is invoked, `aa_composer.js` iterates the assets: for `base`, `fee=10000 <= 1_000_000`, message queued; then for `ASSET_X`, `fee=5000 > amount=4000`, hitting `return finish(null)`.
4. Result: `finish(null)` is called, no unit is composed, and the queued base-asset refund message (999,990 bytes for the sender) is discarded entirely — the trigger sender loses the full 1,000,000 bytes and 4000 units of `ASSET_X`, instead of only forfeiting the smaller `ASSET_X` amount and receiving back the vast majority of bytes sent.

### Citations

**File:** aa_composer.js (L930-944)
```javascript
		var messages = [];
		// iteration order is standardized since ECMAScript 2020
		for (var asset in trigger.outputs) {
			var amount = trigger.outputs[asset];
			var fee = bounce_fees[asset] || 0;
			if (fee > amount)
				return finish(null);
			if (fee === amount)
				continue;
			var bounced_amount = amount - fee;
			messages.push({app: 'payment', payload: {asset: asset, outputs: [{address: trigger.address, amount: bounced_amount}]}});
		}
		if (messages.length === 0)
			return finish(null);
		sendUnit(messages);
```
