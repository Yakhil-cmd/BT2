### Title
Unbounded, ever-accumulating `rewards-per-token` combined with unchecked `shares * rpt` multiplication in `compute-earned-rewards` can overflow Clarity's 128-bit `uint`, permanently freezing sBTC rewards - (File: `stackslib/src/chainstate/stacks/boot/pox-5.clar`)

### Summary
`pox-5.clar` implements a Sushi-Masterchef-style "rewards-per-token" accumulator for both the STX staker pool and each sBTC bond pool, exactly the pattern flagged in the referenced Sherlock report. Just like the audited protocol, the accumulator (`rewards-per-token-for-cycle`) is scaled by a fixed `PRECISION` constant and grows monotonically forever, and a user's earned amount is computed by multiplying their raw share balance by the accumulator difference *before* dividing back down by `PRECISION`. Unlike Solidity's 256-bit words, Clarity's `uint` is only 128 bits wide and Clarity aborts the transaction on overflow rather than wrapping. This makes the intermediate-multiplication-overflow bug class both easier to trigger and more destructive here: an overflow does not silently corrupt state, it makes every future call that touches the overflowing arithmetic permanently fail.

### Finding Description
`calculate-rewards` computes the per-token accumulator for the STX pool exactly like the audited contract's `_notifyReward`: [1](#0-0) 

and for each bond pool inside `calculate-bond-rewards`: [2](#0-1) 

Both accumulators (`cumulative-rewards-per-ustx` / `cumulative-rewards-per-sat`) are strictly increasing over the life of the contract — they are never reset, only added to — the same property the Sherlock report calls out as the root enabler ("the accumulator only grows").

The earned-amount formula then multiplies a user's raw share balance by the *difference* of two accumulator snapshots before dividing by `PRECISION`: [3](#0-2) 

This is structurally identical to the vulnerable Solidity pattern `rewardInfo.cumulatedReward * balance.lockedWithMultiplier - rewardDebt[...]`: the multiplication `shares * (rpt-current - rpt-paid)` happens on raw (un-divided) magnitudes, so it can overflow even though the final divided result would easily fit in the type. Because `get-total-shares-staked-for-cycle` can be arbitrarily small relative to `gross-accrued-rewards` (e.g. very early in a cycle, right after most participants unstake, or via a first-staker/first-reward-in-a-cycle race similar to the report's PoC), `accrued-rewards-per-ustx`/`accrued-rewards-per-sat` can become very large, and this inflated value then compounds every cycle via the `(+ current-rewards-per-token accrued-rewards-per-sat)` accumulation. When a legitimately large staker's `shares` is later multiplied against this inflated, ever-growing accumulator inside `compute-earned-rewards`, the intermediate product can exceed Clarity's `u128` maximum (~3.4e38), which is over 10^39 times smaller than Solidity's `uint256` ceiling used in the original report — making this bug class markedly easier to hit here.

Because Clarity aborts a transaction on arithmetic overflow (it does not wrap), `get-earned`, `get-earned-staker-rewards`, `claim-rewards`, and `claim-staker-rewards` — every one of which calls `compute-earned-rewards` — would revert forever for the affected signer/staker/cycle/bond combination once the overflow condition is reached: [4](#0-3) 

This permanently freezes the sBTC rewards owed to the affected principal, with no code path to reset or repair the corrupted (unreadable) entry, since the accumulators are never rewound.

### Impact Explanation
This breaks the "sBTC rewards paid == sBTC rewards earned" equality by making legitimately earned sBTC rewards permanently unclaimable once the intermediate multiplication in `compute-earned-rewards` overflows `u128`. Per the grading rubric, permanent freezing of staked sBTC/reward funds is a Critical-severity outcome. The scope is broader than the original report because the failure is not isolated to a single griefed pool: `pox-5`'s accumulator is shared/cycle-and-bond scoped and grows monotonically for the life of the contract, so any legitimate staker whose share size, combined with the accumulated `rewards-per-token`, crosses the 128-bit ceiling is bricked from claiming — with no admin lever in `pox-5.clar` to reset a single corrupted (cycle, bond, signer/staker) accumulator entry short of a full contract upgrade.

### Likelihood Explanation
Likelihood is low-to-medium and depends on operational conditions (magnitude of sBTC rewards relative to `cycle-staked-ustx`/`total-sats`, and how long the contract runs without a reset), mirroring the original Sherlock discussion. It requires either (a) a cycle/bond with a very small denominator (`cycle-staked-ustx` / `total-sats`) at the time a large reward batch is distributed, or (b) many cycles of compounding without ever pruning the accumulator, before a very large stake interacts with it. Given `pox-5` runs indefinitely and accumulators are never reset, this is a state that can be reached organically over the contract's operational life, not just at deployment — the same "not only at genesis" argument that the Sherlock escalation ultimately won on.

### Recommendation
- Divide by `PRECISION` progressively rather than deferring the whole division to the end, or perform the `shares * diff` multiplication using a wider intermediate representation/checked-safe-math helper that fails gracefully instead of aborting a claim permanently.
- Enforce a floor on `cycle-staked-ustx`/`total-sats` (or reward-per-distribution caps) analogous to Sherlock's mitigation #2/#3 recommendations, so the accumulator per unit share cannot be inflated unboundedly by a low-denominator cycle.
- Add an admin/self-healing recovery path (e.g., an accumulator rebase or migration function) so that if an entry does overflow, affected principals are not permanently locked out of already-earned rewards.

### Proof of Concept
1. A cycle N begins with `cycle-staked-ustx` extremely small (e.g., most participants unstaked, or a fresh bond/pool with only a dust-sized stake) while a sizeable sBTC reward batch (`gross-accrued-rewards`) is deposited and `calculate-rewards` is called: `accrued-rewards-per-ustx = stx-staker-rewards * PRECISION / cycle-staked-ustx` produces a very large value, which is folded permanently into `cumulative-rewards-per-ustx` via `map-set rewards-per-token-for-cycle` [5](#0-4) .
2. Repeat over subsequent cycles/reward distributions; the accumulator only ever grows (never decreases) since `cumulative-rewards-per-ustx = current + accrued`.
3. A legitimate large staker later accrues shares (`get-signer-shares-staked-for-cycle`) in a cycle where `rpt-current - rpt-paid` from step 1/2 is large enough that `shares * (rpt-current - rpt-paid)` in `compute-earned-rewards` exceeds `u128::MAX`.
4. Every future call to `get-earned`, `claim-rewards`, or `claim-staker-rewards` for that (signer/staker, cycle, bond) combination aborts with a runtime overflow error, permanently freezing that staker's already-earned sBTC rewards with no recovery path in the contract.
