### Title
Webhook signature is verified against the org derived from `repository.owner.login`, but handlers act on the unrelated `repository.full_name` field — breaking the "org authenticated == repository written" binding - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App/secret to validate a webhook against using a field taken from the still-unverified JSON body (`repository.owner.login`, or `organization.login` as fallback), then HMAC-checks the raw body against that org's `webhook_secret`. Once verification "passes," `Shipit::Webhooks::Handlers::Handler#repository_name` resolves the actual `Stack`/`Repository` to act on using a *different* field of the same payload: `repository.full_name`. Nothing ties these two fields together, so the org whose secret authenticated the request is not guaranteed to be the org whose repository/stack is mutated.

### Finding Description
- Selection of the verifying org: `app/controllers/shipit/webhooks_controller.rb` lines 24-30 and 59-62: [1](#0-0) [2](#0-1) 

- Signature check itself only compares a supplied secret to the payload, and explicitly disables checking entirely when the selected org has no secret configured (documented as "optional" in `docs/setup.md`): [3](#0-2) 

- Once `create` runs, every handler resolves the target repository/stack from a *different* payload field, `repository.full_name`, not the `owner.login` used for verification: [4](#0-3) [5](#0-4) 

The equality this breaks: `verified_secret_owner(request) == repository_written(request)` is never enforced. In a multi-org Shipit deployment (explicitly supported, see `docs/setup.md` "Using Multiple Github Applications") each org has its own independent `webhook_secret`, and `Shipit.github(organization:)` looks the app up purely by the name embedded in the attacker-controlled JSON body. An attacker only needs one configured org where signature checking is a no-op (no `webhook_secret` set — supported and called "optional" in the docs) or an org whose secret they can obtain, to set `repository.owner.login`/`organization.login` to that org while forging `repository.full_name` to point at a completely different tracked repository/stack belonging to another tenant of the same Shipit instance.

### Impact Explanation
This is a full webhook-authentication bypass across tenant/org boundaries on a public, unauthenticated endpoint (`WebhooksController` requires no session, `ApiClient`, or GitHub identity — only `verify_signature`). With a forged payload an attacker can:
- Forge `push` events (`PushHandler`) to make `stack.sync_github(expected_head_sha:)` run for a victim repository/branch, driving the stack's HEAD/expected SHA and downstream sync logic.
- Forge `status` events (`StatusHandler`) to inject fabricated commit statuses via `commit.create_status_from_github!`, which feeds into `Commit#deployable?`/CI-gating logic used by `ContinuousDeliveryJob#perform` to decide whether to `stack.trigger_continuous_delivery`.
- Forge `pull_request`/`check_suite`/`membership` events for stacks/teams that belong to other, unrelated organizations.

Chained with continuous deployment (`Shipit::ContinuousDeliveryJob`), this can result in an **unauthorized deploy** being triggered for a repository the attacker does not control, purely by exploiting the org-vs-repository binding mismatch — this matches the Critical "unauthorized deploy" impact category.

### Likelihood Explanation
Requires no privileged credentials: no `ApiClient` token, no session, no GitHub identity, no repository write access — only that the Shipit instance is configured with more than one GitHub org (a documented, supported configuration) and that at least one of those orgs has signature verification effectively disabled (also a documented, "optional" configuration per `docs/setup.md`), or that the attacker can determine/guess that org's secret. Given the docs explicitly present `webhook_secret` as optional and multi-org config as a first-class feature, this is a realistic misconfiguration rather than a purely theoretical one, but it is conditioned on that configuration state, which introduces some uncertainty about default/typical deployments.

### Recommendation
Bind the field used to select the verifying secret to the field the handlers actually act on. Concretely, after HMAC verification passes, re-derive the acting repository/stack strictly from the same trust domain that produced the verified secret (e.g., verify that `repository.full_name`'s owner segment equals the `organization`/`repository.owner.login` value used to pick the webhook secret, and reject the request otherwise). Additionally, consider refusing to route/process events for any org configured without a `webhook_secret` when the instance also serves other orgs, since a secret-less org otherwise provides an authentication bypass path into every other tenant's repositories.

### Proof of Concept
Note: I could not execute code in this environment; this is a structural PoC based on the code paths cited above, given the sandbox only allowed read-only static analysis tools.

1. Shipit instance is configured for two orgs, e.g. `attacker-org` (no `webhook_secret` set, as permitted by `docs/setup.md`) and `victim-org` (has a stack tracking `victim-org/victim-repo`).
2. Attacker POSTs directly to `/webhooks` (no auth required) with header `X-Github-Event: push` and any/absent `X-Hub-Signature`, and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. `WebhooksController#repository_owner` returns `"attacker-org"` → `Shipit.github(organization: "attacker-org")` → `verify_webhook_signature` returns `true` unconditionally because `attacker-org` has no `webhook_secret` (`lib/shipit/github_app.rb` line 77).
4. `Shipit::Webhooks::Handlers::PushHandler#process` (via `Handler#repository_name`) resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and runs `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` for the victim's stack — even though the request was never authenticated against `victim-org`'s secret at all.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
