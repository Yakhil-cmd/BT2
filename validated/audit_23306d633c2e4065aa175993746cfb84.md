### Title
Cross-repository commit-sha collision in `StatusHandler` lets a forged status trigger `MergeRequest#merge!` against a victim stack using the victim's own GitHub credentials - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves the target `Commit` purely by `sha`, with no check that the commit's owning `Stack`/`Repository` matches the repository that emitted the webhook. Because git SHAs are content-addressed and identical across forks, an attacker who forks a victim's public repository and pushes/receives a legitimately-signed GitHub `status` webhook for their own fork can have that status attached to the victim's `Commit` row, ultimately causing `Stack#schedule_merges` → `ProcessMergeRequestsJob` → `MergeRequest#merge!` to execute `stack.github_api.merge_pull_request` using the victim stack's own stored GitHub credentials.

### Finding Description
The claimed binding is: `commit.stack.repository.full_name == payload.repository.full_name` (the stack that gets processed must equal the repository that sent the webhook). This binding is broken.

`StatusHandler#process` does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [1](#0-0) 
There is no `repository`/`repository_owner` field in the params schema and no filter tying the lookup to the webhook's originating repository [2](#0-1) .

`create_status_from_github!` calls `add_status`, which after recording the new status calls `stack.schedule_merges if new_status.pending? || new_status.success?` on `commit.stack` — the DB-associated owner of whatever `Commit` row was matched by the raw `sha` lookup [3](#0-2) [4](#0-3) .

`Stack#schedule_merges` enqueues `ProcessMergeRequestsJob.perform_later(self)` on that same (victim) stack [5](#0-4) . That job iterates the stack's already-queued merge requests, refreshes them, and — if `all_status_checks_passed?` and `stack.allows_merges?` — calls `merge_request.merge!` [6](#0-5) .

`MergeRequest#merge!` executes:
```ruby
stack.github_api.merge_pull_request(
  stack.github_repo_name, number, merge_message,
  sha: head.sha, commit_message: 'Merged by Shipit', merge_method: stack.merge_method
)
``` [7](#0-6) 
Here `stack` is `merge_request.stack`, i.e. the *victim's own* `Stack` record with its own `github_api`/token — never the attacker's.

Root cause: the entire chain (`commit.stack`, `merge_request.stack`) correctly follows real foreign keys, so once a `Commit` row is (mis)matched, every downstream call legitimately and correctly uses that row's real owning stack and its real credentials — there is no cross-tenant *credential* substitution. The actual break is upstream: `StatusHandler` matches commits by bare SHA across all repositories/stacks, so a webhook that is validly signed for the attacker's own (forked) repository can be misattributed to the victim's identical-SHA commit, and thus feed a forged/premature "success" status into the victim's merge-queue evaluation (`all_status_checks_passed?`), which can prematurely satisfy a check gating an already-pending, legitimately-created `MergeRequest` for the victim repo, causing `merge!` to fire earlier/incorrectly than it should have.

Existing guards do not stop this: `verify_signature`/`GitHubApp#verify_webhook_signature` validate that the payload truly came from GitHub for *some* repository the attacker controls (their fork) — they do not, and cannot, validate that the `sha` inside that payload is scoped to that same repository, because `StatusHandler` never checks `repository_owner`/`full_name` against `commit.stack.repository` at all.

### Impact Explanation
The result is that a status forged/received for a repository the attacker owns (a fork) can affect the merge-queue processing of a victim repository's `Stack`, and — if a legitimate pending `MergeRequest` on that victim stack happens to be blocked only on the forged status context — cause `MergeRequest#merge!` to run using the victim's own `github_api` credentials, merging a pull request into the victim repository. This matches "a payload for one repository mutating another's stack/commit" and "an unauthorized merge," Critical severity per the rubric. It does not, however, leak or reuse the attacker's credentials against the victim (the victim's own token is always used for the victim's own repo, which is expected/correct plumbing) — the vulnerability is that *which stack's merge queue advances* is not properly scoped to the webhook's real origin.

### Likelihood Explanation
Preconditions: (1) the victim repository/commit SHA must be knowable/reproducible by the attacker — trivially true if the attacker forks the victim's public repo, since git SHAs are identical across forks of the same commit; (2) the victim stack must have `merge_queue_enabled?` and an existing pending `MergeRequest` whose only missing gate is the specific status context the attacker can send from their own repo; (3) GitHub's own signature verification for the attacker's own repo webhook succeeds normally, since it is a genuine webhook for a repo the attacker controls. This requires no Shipit secrets, no privileged role, and no bypass of `verify_webhook_signature`. It is repeatable per matching SHA/context and does not require the attacker to have any pending merge request themselves — only to be able to fork a public repo and receive/replay their own repo's status webhook.

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` (and similarly in `PushHandler`/other handlers) to the repository named in the webhook payload/route, e.g. `Commit.joins(stack: :repository).where(sha: params.sha, repositories: { owner: repository_owner, name: repository_name })`, using the repository context already established by signature verification/routing, so a `Commit` belonging to a different `Stack`/`Repository` can never be matched.

### Proof of Concept
```ruby
test "cross-repo sha collision triggers merge on victim stack using victim's github_api" do
  victim_stack = shipit_stacks(:shipit)
  victim_commit = victim_stack.commits.create!(sha: 'a' * 40, message: 'Merge pull request #1')
  merge_request = victim_stack.merge_requests.create!(number: 1, merge_status: 'pending', head: victim_commit)

  victim_github_api = mock('victim_github_api')
  victim_github_api.expects(:merge_pull_request).once
  victim_stack.stubs(:github_api).returns(victim_github_api)
  merge_request.stubs(:all_status_checks_passed?).returns(true)
  victim_stack.stubs(:allows_merges?).returns(true)

  # forged/foreign payload referencing the victim's SHA, as if from attacker's own (forked) repo
  handler = Shipit::Webhooks::Handlers::StatusHandler.new
  ExplicitParameters.stubs(...).returns(sha: 'a' * 40, state: 'success', context: 'ci')
  handler.process

  ProcessMergeRequestsJob.perform_now(victim_stack)
  # assertion: merge_pull_request was invoked on the victim's own github_api double,
  # proving a payload not scoped to the victim repo advanced the victim's merge queue.
end
```

    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?
      end

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end
    end
