### Title
Permanent market freeze from accrual-time RAY value overflow - (File: `common/src/rates/simulate.rs`)

### Summary
The pool computes market utilization by unscaling aggregate debt and supply with the live indexes before every accrual. Both calls use `scaled_to_original`, which panics with `MathOverflow` when the resulting RAY value no longer fits `i128`. Because every market mutation accrues first, reaching this bound permanently blocks repayment, withdrawal, liquidation, index updates, flash loans, and recapitalization for that market. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`accrue_step` reads `borrowed_original = borrowed * borrow_index` and `supplied_original = supplied * supply_index` before calculating utilization and before `update_borrow_index` can clamp the next index to `MAX_BORROW_INDEX_RAY`. [4](#0-3)  `scaled_to_original` delegates to `Ray::mul`, and the underlying `mul_div_half_up` returns `None` only after the widened `I256` quotient still cannot fit `i128`, which is converted into a `MathOverflow` panic. [5](#0-4) [6](#0-5) 

The checked index ceiling therefore does not protect the multiplication of already-stored scaled balances by the current index. [7](#0-6)  An unprivileged caller can reach the failing transition through `controller::update_indexes(caller, assets)` with the affected `HubAssetKey`; the same panic then occurs at the start of controller-routed `withdraw`, `repay`, `liquidate`, `clean_bad_debt`, and other pool mutations. [8](#0-7) 

### Impact Explanation
Once aggregate scaled debt or supply crosses `i128::MAX` in current-index terms, accrual never commits a new timestamp because the panic happens inside the first accrual chunk. Every later call repeats the same calculation and fails, leaving suppliers unable to withdraw, borrowers unable to repay, and liquidators unable to rescue or close the account. This is permanent freezing of market funds rather than a fail-closed input rejection. [9](#0-8) [10](#0-9) 

The in-repository reproduction demonstrates this exact state transition: after the overflow, the stored borrow index remains below `MAX_BORROW_INDEX_RAY`, while both withdrawal and repayment revert with `MathOverflow`. [11](#0-10) 

### Likelihood Explanation
The attacker does not need privileges, malformed storage, oracle manipulation, or a leaked key. A single funded account can build a very large market through `supply` and `borrow`, let sustained high utilization grow the index, and then call `update_indexes` to trigger the first overflowing chunk. The requirement for an exceptionally large token balance, admissible market caps, high utilization, and prolonged accrual makes this difficult on ordinary configured markets, so the appropriate severity is Medium despite the permanent impact. [12](#0-11) 

### Recommendation
Do not let index growth make stored aggregates unrepresentable. Before accrual, derive a market-specific index bound from the stored scaled balances, such as `max_index = i128::MAX * RAY / max(supplied, borrowed)`, and clamp index growth to a value safely below that bound. Alternatively, make accrual detect the overflowing unscaling and persist a bounded no-interest state that still permits repayments and withdrawals. Add a regression test asserting that after the maximum representable index is reached, `update_indexes`, `repay`, `withdraw`, and `liquidate` remain executable.

### Proof of Concept
1. In an active hub, call `supply(caller, account_id = 0, spoke_id, [(hub_asset, principal)])` with a very large valid amount of a high-decimal asset.
2. From a sufficiently collateralized account, call `borrow(caller, account_id, [(hub_asset, debt)], None)` at sustained high utilization.
3. Advance the ledger while leaving the market unaccrued.
4. Call `update_indexes(caller, [hub_asset])`.
5. `global_sync` calls `accrue_step`; `scaled_to_original(borrowed, borrow_index)` or `scaled_to_original(supplied, supply_index)` exceeds `i128` and panics before `mark_accrued` executes.
6. Subsequent `repay`, `withdraw`, `liquidate`, `clean_bad_debt`, `flash_loan`, and `recapitalize` calls for the same market all run `global_sync` first and revert identically.

```rust
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
```
