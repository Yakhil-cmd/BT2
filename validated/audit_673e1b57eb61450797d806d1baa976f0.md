### Title
AAs that key authorization or fund routing on `trigger.initial_address` are exposed to a `tx.origin`-style confused-deputy attack via secondary AA triggers - (File: aa_composer.js)

### Summary
The Obyte AA engine exposes `trigger.initial_address` to Oscript code as the address of the account that originated the entire multi-hop AA call chain, analogous to Solidity's `tx.origin`. Just like `tx.origin`, this value is automatically propagated unchanged through every intermediate ("secondary") AA in the chain, regardless of what those intermediate AAs actually intend to authorize. An AA developer who uses `trigger.initial_address` (instead of `trigger.address`, the Oscript analog of `msg.sender`) to decide whom to pay, refund, or authorize is vulnerable to exactly the confused-deputy pattern described in the external report: an attacker can interpose a malicious/compromised intermediate AA in a call chain that a victim innocently triggers, and have that intermediate AA silently forward a crafted secondary trigger to the victim AA while `trigger.initial_address` is auto-populated with the innocent victim's address.

### Finding Description
`getTrigger()` sets `trigger.address` to the immediate caller of the current unit/message (`objUnit.authors[0].address`), which is the correct analog of `msg.sender`. [1](#0-0)  Separately, `trigger.initial_address` is set once, at the very start of the chain, to the address of the account that posted the primary trigger unit. [2](#0-1) [3](#0-2) 

When a triggered AA sends payments to another AA address, `handleSecondaryTriggers()` builds a `child_trigger` for the downstream AA, and explicitly copies `initial_address`/`initial_unit` from the parent trigger unmodified:
```
var child_trigger = getTrigger(objUnit, row.address);
child_trigger.initial_address = trigger.initial_address;
child_trigger.initial_unit = trigger.initial_unit;
``` [4](#0-3) 

This means every AA anywhere in an arbitrarily long, engine-driven call chain sees the same `trigger.initial_address` — the address that funded the very first unit — no matter which (possibly malicious or attacker-controlled) intermediate AAs routed funds and data along the way. This is architecturally identical to `tx.origin` in Ethereum: it identifies "who ultimately paid for this transaction" rather than "who is directly calling me right now."

`trigger.initial_address` is documented/used in the codebase's own test suite and sample scripts as the address to refund change or send final proceeds to across chains of AAs. [5](#0-4) [6](#0-5)  This is the intended, benign use (like sending ETH change back to `tx.origin` in a multi-contract flow) — but the same primitive is available to condition state changes, authorization checks, or balance attribution, not just simple payment destinations, since it's a first-class Oscript getter available in `init`, `messages`, and `state` sections. [7](#0-6) 

The root cause is structural: nothing in `handleTrigger`/`handleSecondaryTriggers` lets a downstream AA distinguish "this secondary trigger's `trigger.data`/`trigger.outputs` were composed directly by the identified `initial_address`" from "this secondary trigger's payload was composed by an untrusted intermediate AA, merely propagating someone else's original identity." An AA author who conflates the two — using `trigger.initial_address` as an authorization/ownership key while trusting `trigger.data`/`trigger.outputs` supplied by the immediate caller (`trigger.address`, the intermediate AA) — creates the same class of bug as the audited `TradeCallee` contract: funds/authorization attributed to the "origin" identity get used to execute actions whose actual parameters were chosen by an untrusted intermediary.

### Impact Explanation
Any AA (issued by any user/developer on the network, and reachable by any address that can post a unit or fund an AA) that uses `trigger.initial_address` for balance keying, ownership checks, or privileged-action authorization instead of `trigger.address` can have its funds misdirected or its privileged logic invoked with attacker-chosen parameters, as long as the attacker can get the victim to trigger some other, unrelated, seemingly benign AA that forwards a payment/secondary trigger onward. Since AA-to-AA calls are a normal, engine-supported feature (not privileged), and the resulting `initial_address` propagation is unconditional and un-opt-outable, this is directly reachable by any unprivileged AA author or trigger-sender and can result in unauthorized spending of AA balances or state corruption attributable to a victim who never directly interacted with the exploited AA.

### Likelihood Explanation
Likelihood depends on adoption of the vulnerable pattern by third-party AA authors, but the pattern is natural and encouraged by the engine's own test suite and idiomatic examples, which use `trigger.initial_address` precisely to identify "who to ultimately credit/refund" across chains. [8](#0-7)  Any developer following this idiom for authorization rather than simple refunds is exposed, and exploitation only requires posting units/triggers, which any unprivileged network participant can do — no special privileges, hub/node compromise, or leaked keys required.

### Recommendation
- In the Oscript documentation/getters, explicitly warn that `trigger.initial_address` must never be used for authorization or balance ownership decisions, only `trigger.address` (the immediate caller) should be trusted for that purpose — mirroring standard Solidity guidance to avoid `tx.origin` for access control.
- Consider adding an engine-level primitive that lets a downstream AA verify whether `trigger.initial_address` genuinely composed the current trigger's data/outputs (e.g., an explicit "verified chain" flag or signature check), rather than blindly trusting propagated identity.
- Audit any first-party/bundled or commonly copied sample AAs for use of `trigger.initial_address` in `if` conditions gating fund transfers or state changes.

### Proof of Concept
1. Victim AA `V` is written to pay out its balance to `trigger.initial_address` whenever `trigger.data.withdraw` is set, believing this restricts withdrawals to the address that "genuinely" started the interaction:
   ```
   if: `{trigger.data.withdraw}`,
   messages: [{ app: 'payment', payload: { asset: 'base', outputs: [
       { address: "{trigger.initial_address}", amount: "{balance[base]}" }
   ]}}]
   ```
2. Attacker deploys an innocuous-looking "Proxy" AA `P` that a victim, Alice, is enticed to trigger for an unrelated purpose (e.g., a game or swap). `P`'s definition, when triggered by Alice, sends a payment to `V` together with `{data:{withdraw:true}}`.
3. When Alice triggers `P`, the AA composer processes `P`'s payment output to `V` as a secondary trigger; per `handleSecondaryTriggers()`, `child_trigger.initial_address` is set to `trigger.initial_address`, which — since Alice is the primary trigger's original sender — equals Alice's address, even though Alice never directly interacted with `V` and did not intend to authorize this specific withdrawal. [4](#0-3) 
4. `V` sees `trigger.initial_address == Alice` and `trigger.data.withdraw == true` (the latter chosen entirely by the attacker's proxy `P`, not by Alice), and pays out `V`'s balance to Alice's address — or, if `V`'s logic instead attributes/debits a stored per-`initial_address` balance for some other beneficiary address supplied in `trigger.data` by `P`, the attacker redirects `V`'s funds to themselves while the operation is falsely attributed to/blamed on Alice's identity for `V`'s bookkeeping.
