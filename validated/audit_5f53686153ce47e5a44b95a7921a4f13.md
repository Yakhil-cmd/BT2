### Title
ERC20Transactor credits/debits the XCM holding register with the *requested* transfer amount instead of the actual balance delta observed on the ERC20 contract, breaking accounting for fee-on-transfer / deflationary ERC20 tokens - (File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs)

### Summary
`ERC20Transactor` (the XCM `TransactAsset` implementation that bridges XCM's asset model to ERC20 contracts deployed on `pallet-revive`, wired in on Asset Hub Westend via `assets_common::ERC20Transactor` / `ERC20TransfersCheckingAccount`) assumes that a successful `IERC20::transfer` call (returning `true`, not reverting) always means exactly `amount` tokens moved between the caller and the checking account. This is the same "assumed value == actual value received" flaw as the FiatDAO `VotingEscrow` fee-on-transfer bug, transplanted to the FRAME/XCM boundary where the "external ERC20 contract" is a real, permissionlessly-deployable Solidity/PolkaVM contract rather than a fixed pallet asset. [1](#0-0) [2](#0-1) 

### Finding Description
`withdraw_asset_with_surplus` withdraws an ERC20 asset from a user by calling `transfer(checking_account, amount)` on the contract, and — if the call does not revert and decodes a `true` return value — credits the XCM holding register with the full requested `amount` via `Erc20Credit(amount)`, with no verification that the checking account's real balance increased by `amount`: [3](#0-2) 

Symmetrically, `deposit_asset_with_surplus` calls `transfer(beneficiary, amount)` *from* the checking account, again trusting the boolean return value as proof that exactly `amount` left the checking account: [4](#0-3) 

The `Erc20Credit` imbalance type itself documents this design choice explicitly: "This type ... does not perform runtime-level balance enforcement. It's used to track ERC20 token amounts within XCM asset holdings, where the actual balance constraints are enforced by the ERC20 smart contract itself rather than the runtime." [5](#0-4) 

Since any asset ID of the form `AccountKey20 { key, ... }` matched by `ERC20Matcher` is resolved to an arbitrary, permissionlessly-deployed `pallet-revive` contract (per the `ERC20 Asset Transactor` PRDoc), a user can deploy a token whose `transfer()` implements a fee-on-transfer/deflationary mechanic (burns or redirects a percentage) yet still returns `true`. In that case:
- On `withdraw_asset`, the checking account's real balance increases by less than `amount`, but the XCM holding register is credited with the full `amount`.
- The holding register's inflated `amount` can then be used later in the same XCM program (e.g. `DepositAsset` back out, `BuyExecution`, or forwarded through further instructions) as if the checking account truly holds that much of the token.
- On subsequent `deposit_asset` calls for that token, the transactor asks the checking account to `transfer(amount)` out, but the checking account's real ERC20 balance is now less than the cumulative `amount` that has been credited across all holding operations, since every fee-on-transfer withdrawal/deposit leaks value to the fee sink. This produces a growing wedge between XCM-internal bookkeeping and the actual, real ERC20 balance held by `ERC20TransfersCheckingAccount`, exactly mirroring the original report's "locked amount accounted != tokens actually held" invariant violation. [6](#0-5) [7](#0-6) 

### Impact Explanation
This is a Medium-severity accounting/integrity bug rather than direct fund theft of *other* users' unrelated assets: the checking account is per-contract (its real ERC20 balance is queried per token-contract address), so the blast radius is scoped to holders/positions denominated in the specific fee-on-transfer ERC20. However, because Asset Hub is a shared execution environment where any account can `pallet_xcm::execute` a local XCM program invoking this transactor (as demonstrated by the existing `withdraw_and_deposit_erc20s` test using `PolkadotXcm::execute`), the vulnerable pattern is reachable by any ordinary signed user with no privileged role. Once a fee-on-transfer token is used through the transactor by multiple parties (e.g. multiple users interacting with the same deployed token via XCM, or the token being onward-routed in a multi-hop reserve transfer), the checking account's true ERC20 balance will progressively fall below what XCM holding registers assume was withdrawn/available, causing later legitimate `deposit_asset`/`withdraw_asset` operations against that token to unexpectedly fail (`FailedToTransactAsset`) once the shortfall accumulates — a denial-of-service / value-freezing condition for that asset's XCM path, and a genuine violation of the "amount credited to XCM holding equals amount actually moved" invariant that the rest of the codebase (balances, pallet-assets, XCM reserve/teleport tests) rigorously maintains via exact issuance/holding bookkeeping.

### Likelihood Explanation
Likelihood is Medium: deploying a custom fee-on-transfer ERC20 via `pallet-revive` and invoking it through this specific transactor requires an attacker (or even an unwitting integrator) to (1) deploy a non-standard ERC20 with deflationary `transfer` semantics, and (2) route it through `pallet_xcm::execute`/reserve transfers matched by `ERC20Matcher`. No privileged role, governance action, or malicious external chain/validator is required — a plain signed extrinsic suffices, matching the "real user entry" requirement. The main mitigating factor is that this only affects tokens deliberately built with fee-on-transfer semantics (not the "well-behaved" `MyToken`/OpenZeppelin-style fixtures used in existing tests), so it will not be hit by default/typical ERC20 deployments, but it is fully within an ordinary user's control to trigger.

### Recommendation
In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, read the ERC20 `balanceOf` of the checking account (or of the source/destination) immediately before and after the `transfer` call, and credit/debit the XCM holding register with the *actual observed delta* rather than the caller-supplied `amount`. Alternatively, explicitly document and enforce (e.g., via a probe on first use, or an allow-list mechanism) that only ERC20 contracts with balance-preserving transfer semantics (transferred amount == requested amount) may be registered/matched by `ERC20Matcher`, rejecting or flagging tokens whose `balanceOf` delta does not equal the requested amount.

### Proof of Concept
No executable PoC was run against this codebase; this is a static-analysis-derived structural finding based on reading `erc20_transactor.rs` and the existing integration tests (`withdraw_and_deposit_erc20s`, `smart_contract_not_erc20_will_error`, `smart_contract_does_not_return_bool_fails`, `expensive_erc20_runs_out_of_gas`) in `cumulus/parachains/runtimes/assets/asset-hub-westend/tests/tests.rs`, none of which cover a fee-on-transfer/deflationary token scenario. [8](#0-7)  A full reproduction would require compiling and deploying a custom PolkaVM/Solidity ERC20 fixture whose `transfer()` burns a percentage while still returning `true`, then exercising `PolkadotXcm::execute` with `WithdrawAsset`/`DepositAsset` for that token's `AccountKey20` location and asserting `balanceOf(checking_account)` diverges from the sum of holding-register credits over multiple operations — this reproduction was not executed here and remains unverified; I flag this explicitly as an open verification step for a background agent with test-harness access.

/// A minimal imbalance tracking type that holds an ERC20 token amount.
///
/// This type implements the necessary imbalance accounting traits but does not perform
/// runtime-level balance enforcement. It's used to track ERC20 token amounts within XCM
/// asset holdings, where the actual balance constraints are enforced by the ERC20 smart
/// contract itself rather than the runtime.
struct Erc20Credit(u128);
impl UnsafeConstructorDestructor<u128> for Erc20Credit {
	fn unsafe_clone(&self) -> Box<dyn ImbalanceAccounting<u128>> {
		Box::new(Erc20Credit(self.0))
	}
	fn forget_imbalance(&mut self) -> u128 {
		let amount = self.0;
		self.0 = 0;
		amount
	}
}

impl UnsafeManualAccounting<u128> for Erc20Credit {
	fn saturating_subsume(&mut self, mut other: Box<dyn ImbalanceAccounting<u128>>) {
		let amount = other.forget_imbalance();
		self.0 = self.0.saturating_add(amount);
	}
}

impl ImbalanceAccounting<u128> for Erc20Credit {
	fn amount(&self) -> u128 {
		self.0
	}
	fn saturating_take(&mut self, amount: u128) -> Box<dyn ImbalanceAccounting<u128>> {
		let new = self.0.min(amount);
		self.0 = self.0 - new;
		Box::new(Erc20Credit(new))
	}
}

	fn withdraw_asset_with_surplus(
		what: &Asset,
		who: &Location,
		_context: Option<&XcmContext>,
	) -> Result<(AssetsInHolding, Weight), XcmError> {
		tracing::trace!(
			target: "xcm::transactor::erc20::withdraw",
			?what, ?who,
		);
		let (asset_id, amount) = Matcher::matches_fungibles(what)?;
		let who = AccountIdConverter::convert_location(who)
			.ok_or(MatchError::AccountIdConversionFailed)?;
		// We need to map the 32 byte checking account to a 20 byte account.
		let checking_account_eth = T::AddressMapper::to_address(&TransfersCheckingAccount::get());
		let checking_address = Address::from(Into::<[u8; 20]>::into(checking_account_eth));
		let weight_limit = WeightLimit::get();
		// To withdraw, we actually transfer to the checking account.
		// We do this using the solidity ERC20 interface.
		let data =
			IERC20::transferCall { to: checking_address, value: EU256::from(amount) }.abi_encode();
		let ContractResult { result, weight_consumed, storage_deposit, .. } =
			pallet_revive::Pallet::<T>::bare_call(
				OriginFor::<T>::signed(who.clone()),
				asset_id,
				U256::zero(),
				TransactionLimits::WeightAndDeposit {
					weight_limit,
					deposit_limit: StorageDepositLimit::get(),
				},
				data,
				&ExecConfig::new_substrate_tx(),
			);
		// We need to return this surplus for the executor to allow refunding it.
		let surplus = weight_limit.saturating_sub(weight_consumed);
		tracing::trace!(target: "xcm::transactor::erc20::withdraw", ?weight_consumed, ?surplus, ?storage_deposit);
		if let Ok(return_value) = result {
			tracing::trace!(target: "xcm::transactor::erc20::withdraw", ?return_value, "Return value by withdraw_asset");
			if return_value.did_revert() {
				tracing::debug!(target: "xcm::transactor::erc20::withdraw", "ERC20 contract reverted");
				Err(XcmError::FailedToTransactAsset("ERC20 contract reverted"))
			} else {
				let is_success = IERC20::transferCall::abi_decode_returns_validate(&return_value.data).map_err(|error| {
					tracing::debug!(target: "xcm::transactor::erc20::withdraw", ?error, "ERC20 contract result couldn't decode");
					XcmError::FailedToTransactAsset("ERC20 contract result couldn't decode")
				})?;
				if is_success {
					tracing::trace!(target: "xcm::transactor::erc20::withdraw", "ERC20 contract was successful");
					Ok((
						AssetsInHolding::new_from_fungible_credit(
							what.id.clone(),
							Box::new(Erc20Credit(amount)),
						),
						surplus,
					))
				} else {
					tracing::debug!(target: "xcm::transactor::erc20::withdraw", "contract transfer failed");
					Err(XcmError::FailedToTransactAsset("ERC20 contract transfer failed"))
				}
			}
		} else {
			tracing::debug!(target: "xcm::transactor::erc20::withdraw", ?result, "Error");
			// This error could've been duplicate smart contract, out of gas, etc.
			// If the issue is gas, there's nothing the user can change in the XCM
			// that will make this work since there's a hardcoded gas limit.
			Err(XcmError::FailedToTransactAsset("ERC20 contract execution errored"))
		}
	}

		what: AssetsInHolding,
		who: &Location,
		_context: Option<&XcmContext>,

		tracing::trace!(
			target: "xcm::transactor::erc20::deposit",
			?what, ?who,
		);
		defensive_assert!(what.len() == 1, "Trying to deposit more than one asset!");
		// Check we handle this asset.
		let maybe = what
			.fungible_assets_iter()
			.next()
			.and_then(|asset| Matcher::matches_fungibles(&asset).ok());
		let (asset_contract_id, amount) = match maybe {
			Some(inner) => inner,
			None => return Err((what, MatchError::AssetNotHandled.into())),
		};

			Some(inner) => inner,

		let ContractResult { result, weight_consumed, storage_deposit, .. } =
			pallet_revive::Pallet::<T>::bare_call(

						tracing::debug!(target: "xcm::transactor::erc20::deposit", "contract transfer failed");

					},

#[test]
fn withdraw_and_deposit_erc20s() {
	let sender: AccountId = ALICE.into();
	let beneficiary: AccountId = BOB.into();
	let revive_account = pallet_revive::Pallet::<Runtime>::account_id();
	let checking_account =
		asset_hub_westend_runtime::xcm_config::ERC20TransfersCheckingAccount::get();
	let initial_wnd_amount = 100_000_000_000_000_000u128;
	sp_tracing::init_for_tests();

	ExtBuilder::<Runtime>::default().build().execute_with(|| {
		// Bring the revive account to life.
		assert_ok!(Balances::mint_into(&revive_account, initial_wnd_amount));
		// Fund all accounts involved.
		assert_ok!(Balances::mint_into(&sender, initial_wnd_amount));
		assert_ok!(Balances::mint_into(&beneficiary, initial_wnd_amount));
		assert_ok!(Balances::mint_into(&checking_account, initial_wnd_amount));

		let code = compile_module_with_type("MyToken", FixtureType::Resolc)
			.expect("compile ERC20")
			.0;

		let initial_amount_u256 = U256::from(1_000_000_000_000u128);
		let constructor_data = sol_data::Uint::<256>::abi_encode(&initial_amount_u256);
		let Contract { addr: erc20_address, .. } = bare_instantiate(&sender, code)
			.transaction_limits(TransactionLimits::WeightAndDeposit {
				weight_limit: Weight::from_parts(500_000_000_000, 10 * 1024 * 1024),
				deposit_limit: Balance::MAX,
			})
			.data(constructor_data)
			.build_and_unwrap_contract();

		let sender_balance_before = <Balances as fungible::Inspect<_>>::balance(&sender);

		let erc20_transfer_amount = 100u128;
		let wnd_amount_for_fees = 10_000_000_000_000u128;
		// Actual XCM to execute locally.
		let message = Xcm::<RuntimeCall>::builder()
			.withdraw_asset((Parent, wnd_amount_for_fees))
			.pay_fees((Parent, wnd_amount_for_fees))
			.withdraw_asset((
				AccountKey20 { key: erc20_address.into(), network: None },
				erc20_transfer_amount,
			))
			.deposit_asset(AllCounted(1), beneficiary.clone())
			.refund_surplus()
			.deposit_asset(AllCounted(1), sender.clone())
			.build();
		assert_ok!(PolkadotXcm::execute(
			RuntimeOrigin::signed(sender.clone()),
			Box::new(VersionedXcm::V5(message)),
			Weight::from_parts(600_000_000_000, 15 * 1024 * 1024),
		));

		// Revive is not taking any fees.
		let sender_balance_after = <Balances as fungible::Inspect<_>>::balance(&sender);
		// Balance after is larger than the difference between balance before and transferred
		// amount because of the refund.
		assert!(sender_balance_after > sender_balance_before - wnd_amount_for_fees);

		// Beneficiary receives the ERC20.
		let beneficiary_amount =
			<Revive as fungibles::Inspect<_>>::balance(erc20_address, &beneficiary);
		assert_eq!(beneficiary_amount, erc20_transfer_amount);
	});
}
