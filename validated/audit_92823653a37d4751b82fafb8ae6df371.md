### Title
Cross-tenant CI status forgery via unscoped `Commit.where(sha:)` lookup in `status` webhook handler - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` only validates that the payload was signed by the `webhook_secret` belonging to `repository.owner.login` in the payload, but `StatusHandler#process` then looks up the target `Commit` purely by SHA with no scoping back to that verified owner/repository. Since commit SHAs are not guaranteed unique per-tenant in the `commits` table's indexing, an attacker who controls org A's webhook secret can sign a `status` payload naming a SHA that belongs to a commit under org B's stack, and `create_status_from_github!` will write a forged status onto B's commit.

### Finding Description
The broken binding: the code must guarantee `commit.stack.repository.owner == repository_owner_verified_in_signature`, i.e. the row being mutated belongs to the same GitHub organization/repository whose secret validated the request. Instead:

- `WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository','owner','login')` and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [1](#0-0) [2](#0-1) . This only proves the requester holds org A's `webhook_secret`; it never checks that the `sha` in the payload actually belongs to a repository owned by A.
- `StatusHandler#process` then does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`, with no join or filter on stack/repository/owner at all [3](#0-2) .
- `Commit#create_status_from_github!` writes a `Status` row using attacker-supplied `state`/`description`/`target_url` from the verified-but-irrelevant payload [4](#0-3)  (see also the dedicated `create_status_from_github!` definitions in `app/models/shipit/commit.rb`).

Contrast this with `CheckSuiteHandler#process`, which scopes through `stacks.where(branch: ...)` before touching commits [5](#0-4)  — `StatusHandler` has no equivalent scoping by stack/repository, only a bare, global `Commit.where(sha:)`.

Exploit flow: attacker owns/operates org A (any GitHub org, e.g. their own account/org) with its own registered `webhook_secret` in Shipit's multi-org config (`secrets.github.<org>`). They obtain (via legitimate means, e.g. observing a public commit or PR against B, or brute-forcing) a SHA of a commit that exists in Shipit's `commits` table under a different stack/org B. They POST a `status` webhook to `/webhooks` with `X-Github-Event: status`, `repository.owner.login = A`, `sha = <B's commit sha>`, `state = "success"`, signed with A's own `webhook_secret` (which they control). `verify_signature` passes because it only checks A's signature against A's secret. `StatusHandler#process` then finds B's `Commit` row purely by SHA (global query) and writes a forged `success` status to it, potentially unblocking or triggering a deploy on B's stack — despite B's org never having verified anything in this request.

Existing guards do not close this gap: `verify_signature` checks signature validity per-org but has no cross-check against the resource being mutated; `drop_unhandled_event` only checks the event type is handled; `ExplicitParameters` (`params do ... end` in `StatusHandler`) validates payload shape, not ownership; there is no `Repository`/`Stack` scoping anywhere in the `status` event path.

### Impact Explanation
An attacker with access to only their own org's webhook secret can write arbitrary CI status data (`state`, `target_url`, `description`) onto a commit belonging to a completely different, unrelated repository/stack that they have no relationship with. If a downstream stack has continuous-delivery/required-status logic gating deploys on status checks (`required_statuses`, `blocking_statuses` referenced on `Commit`) [6](#0-5) , a forged "success" status could unblock or trigger an unauthorized deploy on B's stack. This is repeatable against any SHA the attacker can discover, across arbitrary tenants sharing the same Shipit instance, matching the "payload for one repository mutating another's stack/commit" Critical impact category.

### Likelihood Explanation
Preconditions: the Shipit instance must be configured for multile GitHub organizations/orgs sharing one Shipit deployment (a documented supported configuration — see `docs/setup.md` "Using Multiple Github Applications" and `test/dummy/config/secrets_double_github_app.yml`) [7](#0-6) , so that org A and org B are distinct tenants with distinct secrets on the same host. The attacker needs no privilege beyond controlling their own org A's GitHub App/webhook (which they legitimately possess as the operator of that org) and knowledge of a target commit SHA in org B (obtainable from any public commit, PR, or CI log). Cost is a single crafted HTTP POST; it is fully repeatable.

### Recommendation
Scope the `status` handler's commit lookup to repositories owned by the verified organization, e.g. join through `stack.repository` and filter `Commit` to stacks whose repository owner matches the verified `repository_owner`, mirroring `CheckSuiteHandler`'s pattern of scoping through `stacks.where(...)` before touching commits. Alternatively, pass the verified `repository_owner` (or full `repository.full_name`) into the handler and require `commit.stack.repository.owner == repository_owner` before calling `create_status_from_github!`.

### Proof of Concept
Minitest plan (in `test/models/shipit/webhooks/handlers/status_handler_test.rb` or `test/controllers/webhooks_controller_test.rb`, using existing fixtures):
1. Create/seed a `Stack` for organization "B" (e.g. a repository `B/repo`), and a `Commit` under it with a known `sha` = `"deadbeef" * 5` (fixture `shipit_commits(:first)` already belongs to a `shopify/...` fixture stack — adapt or add a second stack owned by a different org).
2. Configure Shipit with two orgs, "A" and "B", each with distinct `webhook_secret`s (mirroring `test/dummy/config/secrets_double_github_app.yml`).
3. Build payload: `{"sha" => commit.sha, "state" => "success", "repository" => {"owner" => {"login" => "A"}}}`.
4. Sign the payload body with org A's `webhook_secret` and set `X-Hub-Signature` accordingly; set `X-Github-Event: status`.
5. `post :create, body: payload, as: :json` and `assert_response :ok`.
6. Assert: `commit.reload.statuses.last.state == "success"` even though `commit.stack.repository.owner` (== "B") does NOT equal the verified `repository_owner` ("A") used in `verify_signature` — i.e. assert `"A" != commit.stack.repository.owner` while the `Status` row was still created, demonstrating the binding `commit.stack.owner == verified_owner` is not enforced.

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently.
