### Title
Webhook signature is verified against the organization named in `repository.owner.login`, but the repository acted upon is resolved from the unrelated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization `webhook_secret` to validate the HMAC against using `repository_owner`, a value read from the JSON body itself. Every downstream `Handler` however resolves the `Stack`/`Repository` to mutate using a *different* payload field, `repository.full_name`. In a multi-organization Shipit deployment (`config/secrets.yml` with per-org `webhook_secret`s, as documented in `docs/setup.md`), an attacker who legitimately controls the webhook secret for one configured organization can craft a payload whose `repository.owner.login` names their own organization (so the signature check passes with the secret they know) while `repository.full_name` names a repository belonging to a different, victim organization. This breaks the intended binding "organization that authenticated == repository that is written."

### Finding Description
`verify_signature` computes the signing organization purely from attacker-controlled payload content: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

This only proves that *someone who knows organization X's `webhook_secret`* sent the request. It never binds the signature check to which repository the request will actually mutate. Every `Handler` subclass instead determines the target repository from a sibling field, `repository.full_name`: [3](#0-2) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`repository.owner.login` and `repository.full_name` are independent, attacker-supplied strings in the same JSON body; nothing enforces `full_name` starts with `owner.login`. Because Shipit supports multiple GitHub organizations each with their own `webhook_secret` (`docs/setup.md`, "Using Multiple Github Applications"; `config/secrets.development.shopify.yml`), an operator of one onboarded org (or anyone who has obtained that org's `webhook_secret`, e.g. by configuring a webhook on their own GitHub organization/App that this Shipit instance is also configured for) can produce a validly-signed payload while injecting a `repository.full_name` that references a stack belonging to an entirely different organization tracked by the same Shipit instance.

This is the direct structural analog of the reported bug: a field that is authenticated/checked (`repository.owner.login`, akin to the "vault the caller identifies as") does not match the field that is actually acted on (`repository.full_name`, akin to the ETH destination that is never validated/accounted for).

### Impact Explanation
The most concrete abusable handler is `StatusHandler`, which writes a `Status` on a commit directly from unauthenticated-against-GitHub payload fields (`sha`, `state`, `target_url`, `description`, `context`), as shown by the round-trip test `test/controllers/webhooks_controller_test.rb:42-59`, without any independent call back to GitHub to confirm the status is real. If a victim stack's deploy pipeline gates auto-deploys or merges on CI status ("Deployable" status, required checks in `shipit.yml`), an attacker who only controls the webhook secret of an unrelated organization configured on the same Shipit instance can inject a forged "success" status for a commit in the victim's repository, potentially triggering an unauthorized deploy/merge. `PushHandler`/`GithubSyncJob` are less directly exploitable since `sync_github` re-fetches truth from the real GitHub API for the resolved repository, but they still cause Shipit to perform actions (repo sync API calls) against a repository the caller was never authenticated for. This crosses the "cross-repository writes / unauthorized deploy" impact bar defined in scope.

### Likelihood Explanation
Exploitability requires the attacker to know the `webhook_secret` of at least one organization configured in the same multi-tenant Shipit instance — which is expected/legitimate knowledge for that org's own GitHub App owner, not a Shipit credential (session, `ApiClient` token, or GitHub App private key of the *victim* org). Multi-organization configuration is a documented, supported deployment mode (`docs/setup.md` "Using Multiple Github Applications"), making the scenario realistic wherever Shipit hosts stacks for more than one GitHub organization behind one instance.

### Recommendation
After signature verification, cross-check that the organization implied by `repository.full_name` (and `repository.owner.login`) matches the organization whose `webhook_secret` actually validated the signature, rejecting (422) any event where they diverge. Alternatively, resolve the target `Stack`/`Repository` first, verify the signature using that repository's own organization's secret, and only then dispatch to handlers — ensuring the same organization identity is used both to authenticate the request and to select what gets mutated.

### Proof of Concept
1. Configure Shipit with two organizations in `config/secrets.yml`, `orgA` (attacker-controlled, webhook secret known to attacker) and `orgB` (victim, hosts stack `orgB/victim-repo`).
2. Attacker crafts a JSON body:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "full_name": "orgB/victim-repo", "owner": { "login": "orgA" } }
}
```
3. Attacker computes `X-Hub-Signature` using `orgA`'s known `webhook_secret` over the raw body and sets `X-Github-Event: status`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "orgA")` and successfully verifies the signature (`app/controllers/shipit/webhooks_controller.rb:24-30`).
5. `StatusHandler` (dispatched via `Handler#repository_name` reading `orgB/victim-repo`, `app/models/shipit/webhooks/handlers/handler.rb:36-38`) creates/updates a `Status` on the victim's commit, even though the request was never authenticated for `orgB`.
