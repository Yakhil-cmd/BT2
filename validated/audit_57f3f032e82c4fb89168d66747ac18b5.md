### Title
Cross-organization commit-status forgery via webhook signature verified against a different org than the acted-upon repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret used to authenticate an inbound webhook using `repository_owner`, derived from the payload's `repository.owner.login` (or `organization.login`), but the individual webhook `Handler`s that subsequently act on the payload derive the target repository/commit independently from other payload fields (`repository.full_name`, or for `status` events, simply `sha`) without cross-checking that they belong to the same GitHub organization whose secret validated the signature.

### Finding Description
`verify_signature` does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [1](#0-0) 
where `repository_owner` reads `params.dig('repository', 'owner', 'login')` [2](#0-1) . This only proves the payload was HMAC-signed with the secret belonging to the organization named in `repository.owner.login` — it says nothing about the organization of the resources the payload's other fields will target.

Shipit supports multiple onboarded GitHub organizations, each with its own GitHub App and its own `webhook_secret`, configured independently in `config/secrets*.yml` [3](#0-2) . The webhook secret for an org's own App is visible to whoever administers that App in GitHub (the org that owns it), per the setup docs [4](#0-3) . Thus a party controlling one onboarded organization's App knows a secret that `Shipit.github(organization: repository_owner)` will accept as long as `repository.owner.login` matches that organization — regardless of what other fields the JSON body contains.

The dispatched handlers then act on unrelated identifiers from the same (attacker-controlled) body:
- `Handler#repository_name` reads `payload.dig('repository', 'full_name')` to select the `Stack`(s) to act on [5](#0-4) , completely independent from `repository.owner.login` used for signing. `PushHandler#process` triggers `stack.sync_github` for whatever stack matches that `full_name` [6](#0-5) .
- `StatusHandler#process` is worse: it doesn't even use the repository at all — it matches purely by commit SHA globally: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [7](#0-6) .

`create_status_from_github!` creates a new `Status` record for the commit [8](#0-7) , and this feeds directly into `Commit#deployable?` (`!locked? && (stack.ignore_ci? || (success? && !blocked?))`) [9](#0-8)  and `Commit#schedule_continuous_delivery`, which enqueues `ContinuousDeliveryJob` once a commit becomes deployable [10](#0-9) , and also triggers `stack.schedule_merges` when the new status becomes success/pending [11](#0-10) .

**The broken equality**: `organization authenticated by the webhook signature == organization owning the repository/commit actually mutated by the handler`. Before the attacker's forged request, only genuine GitHub deliveries for organization A can inject statuses/pushes for organization A's own commits. After the forged request, an entity that only controls organization A's GitHub App secret can inject a `status` event whose `sha` belongs to a commit tracked under organization B's stack (commit SHAs are public/known ahead of time for any repo, private or public, that the attacker can observe via any means, e.g. by being a contributor, or via a prior legitimate push webhook they observed), or a `push` event whose `repository.full_name` names organization B's repository — with a signature that only proves it was signed by organization A's key.

### Impact Explanation
This crosses the "cross-repository writes / unauthorized deploy" boundary explicitly listed as Critical impact. By forging a `status` webhook signed with an onboarded-but-unrelated organization's webhook secret, an attacker can mark an arbitrary commit belonging to a victim organization's stack as `success`, causing `Commit#deployable?` to become true and (if the stack has `continuous_deployment?` enabled) automatically scheduling a real deploy via `ContinuousDeliveryJob`, or unblocking the merge queue via `stack.schedule_merges`. Alternatively, forging a `push` event lets the attacker trigger a `sync_github` on any stack in the instance regardless of the organization the signature was verified for. Both are unauthorized actions against a repository/stack the attacker's credentials were never meant to authorize.

### Likelihood Explanation
Requires the attacker to control (or know the webhook secret of) at least one GitHub organization that has been legitimately onboarded to the shared Shipit instance — a realistic scenario for any Shipit deployment serving multiple organizations/teams, which is exactly the multi-org configuration the engine explicitly supports (`config/secrets.development.shopify.yml` example with two orgs) [3](#0-2) . No GitHub org membership, Shipit session, or API token is needed — only the ability to POST to the public `/webhooks` endpoint with a body they can sign themselves.

### Recommendation
After selecting the GitHub App/secret via `repository_owner` and verifying the HMAC, re-validate that every organization-identifying field referenced by the dispatched `Handler` (e.g. `repository.full_name`'s owner segment, and for `status`/commit-based handlers, the `Commit`'s `stack.repository`'s organization) matches `repository_owner`. Concretely: in `WebhooksController`, reject the request if `params.dig('repository', 'full_name')&.split('/')&.first` (case-insensitively) differs from `repository_owner`; and in `StatusHandler`/`CheckRunHandler` (or `Commit`), scope the `Commit.where(sha: ...)` lookup to commits whose `stack.repository.owner` matches the organization that produced a verified signature for this specific request, not merely any commit with a matching SHA anywhere in the instance.

### Proof of Concept
1. Shipit instance onboards two orgs, `attacker-org` and `victim-org`, each with its own GitHub App/`webhook_secret` (per `config/secrets.yml` structure) [3](#0-2) .
2. Attacker administers `attacker-org`'s GitHub App and therefore knows its `webhook_secret`.
3. Attacker observes/knows a commit SHA `S` belonging to a commit tracked in `victim-org`'s Shipit stack (e.g. `S` is the HEAD of an open PR, visible via GitHub UI).
4. Attacker crafts a `status` event JSON body: `{"sha": "S", "state": "success", "context": "ci/required-check", "repository": {"owner": {"login": "attacker-org"}, "full_name": "attacker-org/whatever"}}`, computes `X-Hub-Signature: sha1=HMAC(attacker_webhook_secret, body)`.
5. POSTs to `/webhooks` with `X-Github-Event: status`.
6. `verify_signature` resolves `repository_owner` = `"attacker-org"` and successfully verifies the signature against `attacker-org`'s secret [1](#0-0) .
7. `StatusHandler#process` finds the real `victim-org` `Commit` with `sha == S` (no repository scoping) and calls `create_status_from_github!`, injecting a forged `success` status [7](#0-6) .
8. If the commit is now `deployable?` and the victim stack has continuous deployment, `ContinuousDeliveryJob` is scheduled, or the merge queue proceeds — an unauthorized deploy/merge triggered entirely by an actor who only controls a different organization's webhook secret.
