### Title
SSRF and unbounded response buffering when fetching arbstore/arbiter URLs — (File: `arbiters.js`, `arbiter_contract.js`)

### Summary
A wallet peer that offers an `arbiter_contract_offer` device message can freely choose the `arbiter_address` field, which is only checked with `ValidationUtils.isValidAddress`. This address is later used to resolve an arbstore URL via the hub (`hub/get_arbstore_url`), and the wallet then makes outbound HTTP(S) requests to that URL with no scheme/host restriction and no bound on response size, mirroring the LemMinX SSRF/DoS pattern (blind request to an attacker-influenced endpoint, unbounded body read).

### Finding Description
When a paired device sends `arbiter_contract_offer`, the wallet validates only that `arbiter_address` is a syntactically valid address: [1](#0-0) 
No check is made that the offering peer's chosen arbiter is a trusted/known arbiter, nor is the resulting arbstore URL ever validated against a scheme allow-list or private-IP block list.

Once the contract is accepted, several flows resolve and fetch data from the URL associated with `arbiter_address`/`arbstore_address`:
- `arbiters.getInfo` / `arbiters.getArbstoreInfo` call `device.requestFromHub("hub/get_arbstore_url", address, ...)` and then issue a raw `http.get(url, ...)` (actually `https` module) with no validation beyond `isNonemptyString(url)`: [2](#0-1) 
- `arbiter_contract.js`'s `getArbstoreAddresses`, `openDispute`, `appeal`, and `getAppealFee` all funnel into `httpRequest(url, path, data, cb)`, which builds a raw `http.request` from `url.parse(host)` with no scheme or host validation: [3](#0-2) [4](#0-3) 

In both `requestInfoFromArbStore` (arbiters.js) and `httpRequest` (arbiter_contract.js), response bodies are accumulated into a string with `data += chunk` in an `on('data', ...)` handler, with no maximum length enforced and no request timeout set — an attacker-controlled server can stream an unbounded response and/or stall the connection, matching the "large file" DoS component of CVE-2022-0671: [5](#0-4) [6](#0-5) 

The `uri.js` `fetchUrl` helper used for `data=definition` URIs has the same unbounded-buffering pattern, though that path is invoked from local/GUI URI parsing rather than from a remotely-triggerable device/unit message: [7](#0-6) 

### Impact Explanation
Because the arbiter address in an `arbiter_contract_offer` is attacker-chosen and unauthenticated (any valid address, not necessarily a hub-vetted arbiter), a malicious paired device can steer a victim wallet toward making blind HTTP requests to a URL under the attacker's control (the URL is resolved via `hub/get_arbstore_url` for the attacker's own address, which the attacker can register as an arbiter for). This enables:
- SSRF: the victim node can be forced to send HTTP requests to internal/otherwise-unreachable hosts chosen by the attacker (e.g., internal services, cloud metadata endpoints if the wallet runs in a cloud VM), since `httpRequest`/`requestInfoFromArbStore` perform no destination filtering.
- Resource exhaustion / DoS: an attacker-controlled endpoint can send an extremely large or slow-drip response with no size cap and no timeout, tying up the wallet's event loop and memory buffering an ever-growing string (`data += chunk`), potentially crashing or hanging the wallet process during dispute/appeal flows that are part of normal core wallet operation (`openDispute`, `appeal`, `getAppealFee`, `getInfo`).

This is reachable purely from a paired-device interaction (offering/accepting an arbiter contract) without any privileged position, matching the SSRF/DoS bug class of the reported advisory.

### Likelihood Explanation
Likelihood is moderate: it requires the victim to interact with a peer device that proposes (or is proposed to accept) an arbiter contract naming an attacker-controlled/attacker-registered arbiter address, and for the victim to proceed to a step that resolves the arbstore URL (open dispute, appeal, or a simple arbiter `getInfo`/`getArbstoreInfo` lookup, which can trigger automatically when displaying contract details). Pairing with an untrusted contact and offering/accepting an arbiter-mediated contract is a normal, expected wallet workflow, so the preconditions are realistically reachable rather than requiring privileged access.

### Recommendation
- Validate that `arbiter_address` in `arbiter_contract_offer`/`arbiter_contract_shared` corresponds to a known/trusted arbiter (e.g., cross-check against a vetted arbiter registry) rather than accepting any syntactically valid address.
- In `arbiters.js` and `arbiter_contract.js`, validate the resolved arbstore URL before using it: enforce `https://` scheme, disallow private/loopback/link-local IP ranges (SSRF hardening), and consider an allow-list of known arbstore hosts.
- Add a hard cap on response size (abort/destroy the socket once a threshold, e.g. a few hundred KB–1MB, is exceeded) and a request/response timeout in `requestInfoFromArbStore`, `httpRequest`, and `fetchUrl`.
- Apply the same size/timeout hardening to `uri.js`'s `fetchUrl`.

### Proof of Concept
1. Attacker pairs with victim's wallet device.
2. Attacker registers (via the hub, or a hub they control) an "arbiter" entry for their own address `A`, with an arbstore URL pointing at an attacker-controlled server `http://attacker.example/` (or an internal-network target for SSRF, or a server that streams gigabytes of data with `Connection: keep-alive` and never ends the response for DoS).
3. Attacker sends `arbiter_contract_offer` to victim with `arbiter_address = A`. The wallet only checks `ValidationUtils.isValidAddress(body.arbiter_address)`, so the offer is accepted and stored: [8](#0-7) 
4. Victim's wallet later calls `arbiters.getInfo(A, ...)` (e.g., when viewing contract/arbiter info) or `arbiter_contract.openDispute`/`appeal`, causing `device.requestFromHub("hub/get_arbstore_url", A, ...)` to resolve to the attacker's URL, then `requestInfoFromArbStore`/`httpRequest` issues a request to that URL with no destination validation: [9](#0-8) 
5. The attacker's server either reaches an internal SSRF target through the victim's network position, or streams an unbounded response that is buffered entirely into memory via `data += chunk`, exhausting memory/CPU on the victim node.

function httpRequest(host, path, data, cb) {
	var reqParams = Object.assign(url.parse(host),
		{
			path: path,
			method: "POST",
			headers: {
				"Content-Type": "application/json",
				"Content-Length": (new TextEncoder().encode(data)).length
			}
		}
	);
	var req = http.request(
		reqParams,
		function(resp){
			var data = "";
			resp.on("data", function(chunk){
				data += chunk;
			});
			resp.on("end", function(){
				try {
					data = JSON.parse(data);
					if (data.error) {
						return cb(data.error);
					}
					cb(null, data);
				} catch (e) {
					cb(e);
				}
			});
		}).on("error", cb);
	req.write(data);
	req.end();
}

function fetchUrl(url, cb) {
	var https = require('https');
	var bDone = false;
	function returnError(err) {
		console.log(err);
		if (bDone)
			return;
		bDone = true;
		cb(err);
	}
	try {
		https.get(url, function (resp) {
			if (resp.statusCode !== 200)
				return returnError("non-200 response while trying to fetch " + url);
			var data = '';

			// A chunk of data has been recieved.
			resp.on('data', function(chunk) {
				data += chunk;
			});

			// aborted before the whole response has been received
			resp.on('aborted', function () {
				returnError("connection aborted while trying to fetch " + url);
			});

			// The whole response has been received
			resp.on('end', function () {
				if (bDone)
					return;
				bDone = true;
				cb(null, data);
			});
		}).on("error", function(err) {
			returnError("non-200 response while trying to fetch " + url + ": " + err.message);
		});
	}
	catch(err) {
		returnError(err.message);
	}
}
