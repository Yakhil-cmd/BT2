### Title
Webhook signature is bound to `organization`/`repository.owner.login`, but handlers act on the independent `repository.full_name` field, enabling cross-organization writes - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to use for HMAC verification based on `repository.owner.login` (or `organization.login`) in the JSON body, but every `Webhooks::Handlers::Handler` subclass decides *which repository/stack to mutate* using a separate, independently-controlled field: `repository.full_name`. Because the HMAC only proves "this body was signed with organization X's secret," and nothing cross-checks that `repository.full_name`'s owner equals the organization whose secret validated the request, an attacker who controls the webhook secret for **any one** organization configured on the Shipit instance can forge a signed payload that authenticates as organization X but instructs handlers to sync/mutate a stack that belongs to organization Y.

### Finding Description
The controller derives the signing key strictly from `owner.login`/`organization.login`: [1](#0-0) [2](#0-1) 

`verify_webhook_signature` only checks the HMAC against that organization's configured `webhook_secret`; it never inspects or constrains any other field of the payload: [3](#0-2) 

Every handler, however, resolves the repository to act on from a *different* payload field, `repository.full_name`, with no relationship enforced back to the organization used for signature verification: [4](#0-3) 

For example, `PushHandler` triggers `stack.sync_github` for every non-archived stack matching that (attacker-controlled) `repository.full_name` and the branch from `ref`: [5](#0-4) 

The same pattern (`Repository.from_github_repo_name(params.repository.full_name)`) is repeated across the pull-request handlers, which archive/unarchive review stacks or update `PullRequest` records for whatever repository the attacker names, independent of the organization whose secret signed the request: [6](#0-5) [7](#0-6) 

This is a direct structural analog of the reported bug class: the report's root cause is "the datum verified by the security check (index) differs from the datum actually trusted for authorization (signer address)." Here, "the datum verified" is `organization.login`/`repository.owner.login` (used to pick the HMAC key), while "the datum trusted for the write" is the unrelated `repository.full_name`. The equality that should hold — `organization_used_for_signature == owner(repository.full_name)` — is never checked.

### Impact Explanation
Shipit is explicitly multi-tenant: `Shipit.github(organization:)` looks up per-organization GitHub App config (`webhook_secret`, credentials) so a single Shipit deployment can serve many unrelated GitHub organizations/repositories, each tracked as `Stack`/`Repository` records. An attacker who is only a repository/organization admin capable of configuring **their own** organization's GitHub App webhook against this shared Shipit instance (a low, unprivileged position relative to any other tenant) can craft a raw JSON body where `organization.login`/`repository.owner.login` = their own org (so the HMAC computed with their own secret validates) but `repository.full_name` = `victim-org/victim-repo`, a repository they do not control, already tracked by Shipit for another tenant. This forged, "validly signed" request reaches handlers that:
- Force a GitHub sync (`stack.sync_github`) of the victim's stack, writing new `Commit` rows and cached state sourced from GitHub calls made with the *victim's* GitHub App credentials (a cross-repository, cross-organization write triggered without any legitimate signal from that organization).
- Archive/unarchive victim review stacks, or attach attacker-controlled pull-request metadata to victim `PullRequest` records.

This crosses the "organization that authenticated versus the repository that is written" trust boundary explicitly called out in scope, resulting in unauthorized cross-repository writes performed with another tenant's GitHub credentials — a Critical-tier impact per the stated criteria.

### Likelihood Explanation
Exploitation only requires the attacker to control (or be permitted to configure) the webhook secret/GitHub App for *any single* organization already onboarded to the shared Shipit instance — no session, `ApiClient` token, `webhook_secret` of the victim, or repository write access to the victim is needed. The attacker crafts the JSON body directly (bypassing GitHub's own webhook delivery, since Shipit accepts any POST bearing a valid `X-Hub-Signature` for the resolved organization) and simply sets `repository.full_name` to the victim's tracked repo name, which is public knowledge. This is straightforward to construct and requires no timing/race conditions.

### Recommendation
Bind the field used to select the verifying secret to the field used to resolve the acted-upon repository. Concretely:
- In `WebhooksController#verify_signature` and `Webhooks::Handlers::Handler#repository_name`, derive both the signing organization and the target repository from the **same** payload subtree (e.g., always use `repository.full_name`'s owner segment, or `repository.owner.login`, consistently) and assert equality between the two before dispatching to handlers.
- Alternatively, after signature verification succeeds using organization `O`, explicitly reject/short-circuit any handler whose resolved `repository.full_name` owner does not case-insensitively equal `O`.

### Proof of Concept
1. Attacker administers `attacker-org/attacker-repo`, which is registered in the shared Shipit instance with GitHub App webhook secret `S_attacker`.
2. Shipit also tracks `victim-org/victim-repo` (a separate tenant/stack), configured with an unrelated secret `S_victim` which the attacker does not know.
3. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeefcafefeed0000000000000000000000",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org" }
  }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(S_attacker, body)` and POSTs to `/github/webhooks`.
5. `WebhooksController#repository_owner` returns `"attacker-org"` (from `repository.owner.login`), so `Shipit.github(organization: "attacker-org")` is used and the signature verifies successfully against `S_attacker`.
6. `PushHandler` is dispatched; its `stacks` method resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `sync_github` on the victim's stacks — an action the attacker was never authorized to trigger — [5](#0-4) , [4](#0-3) .

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
