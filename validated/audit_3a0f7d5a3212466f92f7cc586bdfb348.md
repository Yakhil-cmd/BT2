### Title
Rounding in per-recipient headers-commission split can mint more spendable bytes than the payer unit actually paid - (File: headers_commission.js)

### Summary
`calcHeadersCommissions` splits a parent unit's `headers_commission` (`full_amount`) among the addresses listed in `earned_headers_commission_recipients` by rounding each recipient's share independently with `Math.round(full_amount * share / 100.0)`. Because each recipient is rounded separately instead of the remainder being distributed deterministically, the sum of the rounded amounts can exceed `full_amount`, creating spendable byte outputs that were never actually paid as commission — the same "divide-then-round-per-share overshoot" root cause as the reported reserved-token bug.

### Finding Description
Any multi-authored unit can declare `earned_headers_commission_recipients` with integer percentage shares that the validator only requires to sum to exactly 100: [1](#0-0) 

When the headers commission won by that unit is later distributed, each recipient's cut is computed independently as `Math.round(full_amount * share / 100.0)` and inserted into `headers_commission_contributions`, which is subsequently summed per address into `headers_commission_outputs` (the table from which spendable "headers_commission" inputs are read): [2](#0-1) [3](#0-2) [4](#0-3) 

Because rounding is applied to each share independently (not "largest remainder" style, not with a final residual correction against `full_amount`), the sum of the rounded per-recipient amounts is not guaranteed to equal `full_amount`. For example, with `full_amount = 3` split as two recipients with shares `50` and `50`: each gets `Math.round(3*50/100) = Math.round(1.5) = 2`, so `2 + 2 = 4` bytes are created from a `full_amount` of `3` — one extra byte materialized out of nothing. With more recipients and different share combinations this overshoot compounds (bounded by roughly half a byte per recipient), while the parent (payer) unit's `headers_commission` field itself is unaffected — it is fixed by the unit's serialized size and validated in `objectLength.getHeadersSize` against `objUnit.headers_commission`: [5](#0-4) 

These `headers_commission_outputs` rows are later consumed as validated "headers_commission" type payment inputs, i.e. real, spendable bytes: [6](#0-5) [7](#0-6) 

This is directly analogous to the reported bug: rounding of a percentage split during a distribution routine (`_reservedTokenAmountFrom` there, per-recipient `Math.round` here) causes more units of value to be created/distributed than the source amount actually backs, resulting in unbacked supply growth rather than a pure redistribution.

### Impact Explanation
Every extra byte minted this way is fully spendable base-currency, permanently increasing the circulating byte supply beyond what was ever paid in as fees/commission. This is a supply-inflation bug reachable by any unpermissioned unit author who simply crafts a multi-authored unit with a chosen `earned_headers_commission_recipients` split; no privileged role, hub cooperation, or network attack is required. While the per-unit leakage is small (bounded by roughly half a byte times the number of recipients, since shares are integer percentages), it is systematic and repeatable — an attacker can post many such units over time (each qualifying as an hc-winning child unit) to accumulate inflated commission outputs, degrading the byte:asset backing ratio network-wide, matching the accepted impact class ("supply inflation").

### Likelihood Explanation
Likelihood is straightforward to trigger: multi-author units with arbitrary recipient share splits are an ordinary, fully user-controlled protocol feature (used for shared commission distribution), validated only for `sum == 100`; no other constraint prevents choosing splits that maximize rounding overshoot (e.g., recipients whose `full_amount * share / 100` values are all just above `.5`). Winning the headers commission for a given parent unit additionally requires the crafted unit to be selected as the SHA1-based "winner" child among candidate children, which an attacker can arrange by controlling the DAG structure of their own postings (self-parenting/timing), making repeated exploitation practical over time, though each individual win only leaks a small, sub-1-unit amount.

### Recommendation
Compute recipient shares from a single running remainder instead of independently rounding each share, e.g. accumulate `assigned_so_far`, give the last recipient `full_amount - assigned_so_far`, or use `Math.floor` for all-but-the-last recipient and assign the residual to a designated recipient (or burn it) so the sum of distributed amounts is provably `<= full_amount` for every distribution. Apply the same fix to any other place using the same per-recipient-rounding pattern (e.g. `paid_witnessing.js`'s per-address commission split) and add an invariant check (as already partially present via the `bFaster`/non-`bFaster` cross-check) that explicitly asserts `SUM(amount) <= full_amount` before committing rows to `headers_commission_contributions`.

### Proof of Concept
1. Construct a 2-author unit `U` (author A, author B) with `earned_headers_commission_recipients = [{address: A, earned_headers_commission_share: 50}, {address: B, earned_headers_commission_share: 50}]` (passes validation since `50+50=100`, per `validation.js:1122`).
2. Arrange (via normal DAG posting) for `U` to become the SHA1-winner child of a parent unit `P` whose `headers_commission = 3` (i.e., `full_amount = 3` in `assocWonAmounts`).
3. `calcHeadersCommissions` computes, for each of A and B: `Math.round(3 * 50 / 100.0) = Math.round(1.5) = 2`.
4. Two rows are inserted into `headers_commission_contributions`: `(P, A, 2)` and `(P, B, 2)`, totaling `4`, even though `P` only paid `3` bytes of headers commission.
5. These are aggregated into `headers_commission_outputs` and become spendable by A and B as `headers_commission`-type inputs (`mc_outputs.calcEarnings`), so `4` real bytes end up spendable from a `3`-byte source — a `1`-byte unbacked inflation event, repeatable across many such units.

function validateHeadersCommissionRecipients(objUnit, cb){
	if (objUnit.authors.length > 1 && typeof objUnit.earned_headers_commission_recipients !== "object")
		return cb("must specify earned_headers_commission_recipients when more than 1 author");
	if ("earned_headers_commission_recipients" in objUnit){
		if (!isNonemptyArray(objUnit.earned_headers_commission_recipients))
			return cb("empty earned_headers_commission_recipients array");
		var total_earned_headers_commission_share = 0;
		var prev_address = "";
		for (var i=0; i<objUnit.earned_headers_commission_recipients.length; i++){
			var recipient = objUnit.earned_headers_commission_recipients[i];
			if (!isPositiveInteger(recipient.earned_headers_commission_share))
				return cb("earned_headers_commission_share must be positive integer");
			if (hasFieldsExcept(recipient, ["address", "earned_headers_commission_share"]))
				return cb("unknown fields in recipient");
			if (!isValidAddress(recipient.address))
				return cb("invalid recipient address checksum");
			if (recipient.address <= prev_address)
				return cb("recipient list must be sorted by address");
			total_earned_headers_commission_share += recipient.earned_headers_commission_share;
			prev_address = recipient.address;
		}
		if (total_earned_headers_commission_share !== 100)
			return cb("sum of earned_headers_commission_share is not 100");

function calcEarnings(conn, type, from_main_chain_index, to_main_chain_index, address, callbacks){
	var table = type + '_outputs';
	conn.query(
		"SELECT SUM(amount) AS total \n\
		FROM "+table+" \n\
		WHERE main_chain_index>=? AND main_chain_index<=? AND +address=?",
		[from_main_chain_index, to_main_chain_index, address],
		function(rows){
			var total = rows[0].total;
			if (total === null)
				total = 0;
			if (typeof total !== 'number')
				throw Error("mc outputs total is not a number");
			callbacks.ifOk(total);
		}
	);
}
