### Title
Webhook organization used for signature verification is independent of the repository acted upon, allowing signature-check bypass via a mismatched payload - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to validate a webhook against using one attacker-controlled JSON field, while the webhook handlers act on a repository/stack identified by a completely different, independently attacker-controlled JSON field in the same request body. An attacker can pick an organization with no `webhook_secret` configured to make signature verification a no-op, while making the payload's `repository.full_name` point at a stack belonging to any other, properly-secured organization managed by the same Shipit instance.

### Finding Description
`verify_signature` derives the signing organization from the payload itself, not from any authenticated context: [1](#0-0) [2](#0-1) 

`repository_owner` reads `params.dig('repository', 'owner', 'login')` (or `organization.login`), both of which are plain JSON fields fully controlled by whoever POSTs to `/webhooks` — this method runs before signature verification even occurs, so it cannot be trusted.

`Shipit::GithubApp#verify_webhook_signature` short-circuits to `true` whenever the selected organization has no `webhook_secret` configured: [3](#0-2) 

The webhook secret is explicitly documented as optional, and the shipped sample multi-org config shows it can be `nil` per-organization: [4](#0-3) [5](#0-4) 

Meanwhile, every event handler resolves the actual repository/stack to operate on from a *different* field of the same payload: [6](#0-5) 

Because `repository.owner.login` (used only for choosing the signing org) and `repository.full_name` (used to resolve the stack that gets written to) are two independent strings inside one forged JSON body, they need not agree. An attacker who knows (or guesses) that any one configured organization in a multi-org Shipit deployment has no `webhook_secret` set can set `repository.owner.login`/`organization.login` to that unsecured org to sail through `verify_signature`, while setting `repository.full_name` to `victim-org/victim-repo` to target a stack under a fully secured organization. This breaks the intended binding: "the organization that authenticated the request" must equal "the repository the request is allowed to write to," and here it does not.

### Impact Explanation
Once signature verification is bypassed, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` runs unauthenticated, attacker-controlled writes against the victim stack/repository: [7](#0-6) 
- `push` events enqueue `GithubSyncJob` for the targeted stack.
- `membership` events can create/attach/detach `Team`/`Membership` records for arbitrary users on arbitrary teams (as demonstrated by the handler's own test coverage), which directly affects `User#authorized?`'s check against `Shipit.github_teams`: [8](#0-7) 

This can escalate an attacker into `Shipit.github_teams` authorization or inject forged commit/status/push data for a repository they do not control — matching the "High" impact bar in scope.

### Likelihood Explanation
Exploitation requires no credentials, no repository write access, and no Shipit session — only knowledge that at least one organization configured on the target Shipit instance has no `webhook_secret` set, which is an explicitly supported/optional configuration per the setup docs. In any multi-tenant Shipit deployment where organizations differ in whether they set a webhook secret, this is directly reachable by any unauthenticated network client that can reach `/webhooks`.

### Recommendation
Do not let the payload itself choose which organization's key is used to authenticate that same payload. Either:
1. Verify the webhook signature against every configured organization's secret (or a global secret) rather than one selected via attacker-controlled payload fields, or
2. After verifying against the org derived from `repository.owner.login`, re-validate that `repository.full_name`'s owner segment matches that same organization before dispatching to handlers, and reject on mismatch, or
3. Require `webhook_secret` to be mandatory for every configured organization so `verify_webhook_signature` can never trivially return `true`.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `secured-org` (has `webhook_secret`) and `open-org` (no `webhook_secret`, as shown in `config/secrets.development.shopify.yml`).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": { "full_name": "secured-org/victim-repo", "owner": { "login": "open-org" } },
  "after": "<attacker-chosen-sha>"
}
```
3. `verify_signature` calls `Shipit.github(organization: "open-org")`, whose `verify_webhook_signature` returns `true` unconditionally because `open-org` has no `webhook_secret` [9](#0-8) .
4. `create` proceeds and `PushHandler` resolves the stack via `repository.full_name` = `secured-org/victim-repo` [10](#0-9) , enqueuing a sync job for a repository under the org whose secret was never validated.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
