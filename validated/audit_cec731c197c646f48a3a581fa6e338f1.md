### Title
`stake()` bond-to-stake rollover skips `settle-rewards`/`settle-staker-rewards`, permanently freezing/miscounting a departing signer's reward accounting - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
The Gondi finding describes a "settle" style operation (`settleWithBuyout()`) that transfers value/repays parties directly but skips the canonical accounting-update hook (`loanLiquidation()`), corrupting the pool's internal bookkeeping. `pox-5.clar`'s `stake()` function has an analogous "settle then transition" pattern used when rolling a member out of a bond into an STX-only stake, but unlike the sibling rollover path in `register-for-bond` (bond-to-bond rollover), it does not call `settle-rewards`/`settle-staker-rewards` before mutating the staker's/signer's accounting state.

### Finding Description
In `register-for-bond`'s bond-to-bond rollover path, the contract explicitly settles the old bond's/signer's rewards before mutating any shared accounting state: [1](#0-0) 
This "settle rewards before updating state" comment makes clear that `settle-rewards` / `settle-staker-rewards` must run before any of the per-cycle delegation/share maps are touched, presumably because those settle functions compute owed rewards based on the *current* accounting state and would otherwise double-count or lose track of rewards once the underlying maps have changed.

The `stake()` function implements the same kind of transition (bond membership → STX-only stake, i.e. a "buyout"/rollover of the position), refunding sBTC custody and re-registering the staker/signer delegation for the new position: [2](#0-1) 
Nowhere in this path (lines 991–1086) is `settle-rewards` or `settle-staker-rewards` invoked, even though the function deletes `protocol-bond-memberships` for `tx-sender` and adds new signer-cycle entries via `add-staker-to-signer-cycles`, exactly the kind of state mutation that the `register-for-bond` rollover treats as requiring a prior settle.

### Impact Explanation
If `settle-rewards`/`settle-staker-rewards` exist specifically to flush/checkpoint reward accounting before a membership transition (as demonstrated by their deliberate placement in the sibling `register-for-bond` rollover), omitting them in `stake()`'s bond→STX-only rollover means any reward computation that depends on settling at the transition boundary is skipped. Depending on how `settle-rewards` computes payouts elsewhere in the contract (not fully inspected due to index truncation), this could cause a signer's/staker's earned reward-cycle accounting for the terminated bond position to be dropped, double-counted on next settlement, or become permanently stale — a form of temporary/permanent freezing or double-counting of a reward commitment, mirroring the Gondi `loanLiquidation()` omission (queue/outstanding accounting left inconsistent after a state-changing settlement-like operation).

### Likelihood Explanation
This path is reachable by any staker who is an active bond member and calls the ordinary, unprivileged `stake()` entry point during their bond's rollover window — no special privileges are required, matching the "unprivileged-account analog" requirement. The likelihood of the equality actually breaking depends on the internal implementation of `settle-rewards`/`settle-staker-rewards` (whether skipping them causes a genuine accounting discrepancy or whether the subsequent per-cycle share writes independently account for the transition correctly) — this could not be fully confirmed because the definitions of `settle-rewards`/`settle-staker-rewards` and the full downstream reward-cycle reconciliation logic were not retrieved within the available tool budget.

### Recommendation
Call `settle-rewards` and `settle-staker-rewards` for the outgoing bond's signer/staker (mirroring the `register-for-bond` bond-to-bond rollover) before deleting `protocol-bond-memberships` and writing the new `staker-info`/signer-cycle entries in `stake()`'s bond-rollover branch, so that reward accounting is checkpointed consistently across both rollover paths (bond→bond and bond→stake).

### Proof of Concept
1. A staker registers for a bond via `register-for-bond`, entering `protocol-bond-memberships`.
2. Near the bond's L1-unlock window, the staker calls `stake()` (the unprivileged entry point) to roll their position from the bond into an STX-only stake, per the flow at pox-5.clar:991-1086.
3. Because `settle-rewards`/`settle-staker-rewards` are never invoked in this branch (unlike the equivalent branch in `register-for-bond`, pox-5.clar:772-785), any reward state that should have been settled at the bond boundary is skipped, while `protocol-bond-memberships` is deleted and new signer-cycle delegation is added — leaving the accounting for the terminated bond position unreconciled going forward.

*(Note: full confirmation that this causes an exploitable equality break requires inspecting the bodies of `settle-rewards` / `settle-staker-rewards`, which were not retrieved in full during this investigation; this should be verified before treating the finding as conclusive.)*

        ;; A roll-over from an existing bond is allowed when the bond's term
        ;; ends no later than this stake's first reward cycle. Already-active
        ;; bonds are rejected (overlap). Same shape as the
        ;; `register-for-bond` gate.
        (asserts!
            (not (bond-overlaps-new-position? existing-membership first-reward-cycle))
            ERR_ALREADY_STAKED
        )

        ;; A roll-over from an ending bond may only happen once that bond's
        ;; L1 collateral would have unlocked -- the same window an L1 bond
        ;; holder has to redirect their BTC. Keeps parity with the
        ;; `register-for-bond` gate so a bond's STX / sBTC can't be released
        ;; ahead of the bond's L1 unlock height.
        (try! (verify-bond-rollover-window existing-membership))

        ;;  the Staker must have sufficient total funds (locked + unlocked).
        ;;  On a roll-over the staker's STX is still locked by the ending
        ;;  bond; the node-side handler extends that lock to the new amount,
        ;;  so checking only `stx-get-balance` (unlocked) would falsely fail.
        (asserts! (>= total-balance amount-ustx) ERR_INSUFFICIENT_STX)

        ;; Refund any sBTC custodied for the rolled-over bond (zero-target
        ;; net transfer). No-op when there is no existing bond, or when the
        ;; existing bond is an L1 lock.
        (try! (roll-sbtc tx-sender old-sbtc u0))

        (try! (add-staker-to-signer-cycles tx-sender signer first-reward-cycle
            num-cycles amount-ustx true
        ))

        (map-set staker-info tx-sender {
            amount-ustx: amount-ustx,
            first-reward-cycle: first-reward-cycle,
            num-cycles: num-cycles,
            signer: signer,
        })

        ;; If this was a roll-over from a bond, clear the bond membership so
        ;; `unstake-sbtc` / `update-bond-registration` can no longer reach
        ;; the old bond. The old bond's reward shares and signer delegation
        ;; stay through its term; only the management pointer is gone.
        (map-delete protocol-bond-memberships tx-sender)
