## Analysis

The webhook signature-verification flow in this engine binds the wrong two fields together, breaking exactly the class of binding called out by the rules: "an organization that authenticated versus the repository that is written."

`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to HMAC-verify against by reading `repository_owner`, which is taken straight from the untrusted JSON body — either `repository.owner.login` or, if absent, `organization.login`: [1](#0-0) [2](#0-1) 

That secret is looked up per-organization via `Shipit.github(organization:)` / `github_app_config(organization)`, which is exactly the multi-tenant design this engine supports for hosting several GitHub orgs behind one Shipit install: [3](#0-2) [4](#0-3) 

Once the signature check passes, `create` dispatches the **entire raw payload**, unmodified, to the matching handlers: [5](#0-4) 

Every handler that decides *which repository/stack to mutate* does so via `Handler#stacks`/`#repository_name`, which reads `payload.dig('repository', 'full_name')` — again fully attacker-controlled and **never cross-checked against the `repository_owner` value that was used to pick the verifying secret**: [6](#0-5) [7](#0-6) 

`Repository.from_github_repo_name` does a raw `find_by(owner:, name:)` lookup with no relation to the verifying organization: [8](#0-7) 

In a single-org deployment (`github_default_organization` nil, the "backward compatibility" path) there's only one secret so this can't be abused cross-tenant. But in the explicitly supported multi-org configuration (`config/secrets.*.yml` keyed by org, as seen in `config/secrets.development.shopify.yml`), each org has its own `webhook_secret`. An attacker who legitimately controls a repo under `orgA` (and thus knows/receives `orgA`'s `webhook_secret` value from GitHub's webhook deliveries to their own repo) can:

1. Build a payload with `repository.owner.login = "orgA"` (or `organization.login = "orgA"`) so `verify_signature` picks `orgA`'s secret.
2. Set `repository.full_name = "orgB/victim-repo"` in the same payload — the field the handlers actually act on.
3. Sign the raw body with `orgA`'s secret and set `X-Hub-Signature` accordingly — this passes verification because `verify_signature` never looks at `full_name`, only at `owner.login`/`organization.login`.
4. `PushHandler`, `StatusHandler` (via `Commit.where(sha:)` scoped elsewhere), and other handlers then operate on `orgB`'s repository/stacks using attacker-supplied data (e.g., trigger `GithubSyncJob`, forge commit statuses via `StatusHandler`, or manipulate `MembershipHandler`/`Team` records) — none of which required any credential belonging to `orgB`.

This satisfies the required binding-break pattern (organization authenticated ≠ repository written) and requires no `ApiClient` token, no GitHub App private key, and no privileged access to the victim org — only being an authenticated GitHub user/owner of some *other* repo/org already connected to the same Shipit instance.

### Title
Webhook signature is verified against the payload's declared organization but handlers act on an independently-controlled `repository.full_name`, allowing cross-organization webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Finding Description
`WebhooksController#verify_signature` derives the signing organization from `repository.owner.login` (or `organization.login`) inside the untrusted JSON body, then verifies the HMAC using that organization's `webhook_secret`. All webhook `Handler` subclasses subsequently resolve the target `Repository`/`Stack` from a *different* field of the same payload, `repository.full_name`, with no assertion that this field's owner matches the organization whose secret validated the signature. In a multi-org Shipit deployment, an attacker who controls a repository under `orgA` knows/can obtain `orgA`'s configured `webhook_secret` (it is delivered to them by GitHub for their own repository's webhook events) and can therefore forge a signed payload whose `repository.owner.login` is `orgA` (satisfying signature verification) but whose `repository.full_name` names a stack under `orgB`.

### Impact Explanation
This allows unauthorized cross-repository/cross-organization writes: forged `push` events trigger `Shipit::Stack#sync_github` for a victim's stacks via `PushHandler`, and other handlers (status, membership, pull_request) can similarly write commit statuses, team memberships, or PR metadata attributed to a different organization's repositories — all without any credential belonging to that organization. This matches the Critical "cross-repository writes" impact class.

### Likelihood Explanation
Requires only that the attacker legitimately controls/administers a repository in some organization (`orgA`) hosted on the same multi-tenant Shipit instance as the victim (`orgB`), which is a normal, low-privilege position for many users of a shared internal deploy tool. No token, session, or GitHub App key theft is needed — just knowledge of one's own org's `webhook_secret`, which GitHub itself provides to repo admins configuring the webhook.

### Recommendation
Bind signature verification to the exact repository being mutated, not just its owner login: derive the organization used for both secret selection and the entity that handlers act on from a single authoritative field, and reject payloads where `repository.owner.login`/`organization.login` doesn't match the `owner` portion of `repository.full_name`. Alternatively, verify the signature once per configured organization's secret and only accept the payload for the matching organization's own repositories, explicitly comparing at the controller/handler boundary.

### Proof of Concept
1. Attacker owns `orgA/some-repo`, connected to shared Shipit instance; GitHub webhook delivers `orgA`'s `webhook_secret` value to attacker via its own webhook settings page.
2. Attacker crafts JSON body: `{"ref": "refs/heads/main", "after": "<sha_attacker_wants_synced>", "repository": {"owner": {"login": "orgA"}, "full_name": "orgB/victim-repo"}}`.
3. Attacker computes `X-Hub-Signature: sha1=<hmac(orgA_secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` = `"orgA"`, fetches `orgA`'s app/secret, verification succeeds.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("orgB/victim-repo")`, triggering `sync_github` on `orgB`'s stack — a write the attacker had no authorization to perform.
