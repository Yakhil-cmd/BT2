## Title
Cross-Organization Webhook Forgery via Signature/Target Field Mismatch — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
Shipit supports multi-tenant configuration where each GitHub organization has its own GitHub App and `webhook_secret` [1](#0-0) . The `WebhooksController` selects which organization's secret to verify the inbound webhook's HMAC signature against using the `repository.owner.login` field of the **unauthenticated, attacker-supplied JSON body**, while every webhook handler resolves the actual `Stack`/`Repository` to act on using the **different** `repository.full_name` field from that same body. Because these two independent, attacker-controlled fields are not bound to each other, anyone who knows the webhook secret for *any one* configured organization can forge a validly-signed webhook payload that is authenticated as belonging to their own org but whose `repository.full_name` targets a completely different organization's stack.

### Finding Description
`WebhooksController#verify_signature` computes the org used for signature verification from the payload itself:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

`Shipit.github(organization:)` looks up a distinct `webhook_secret` per configured organization [3](#0-2) , confirmed by the multi-org config schema and fixtures [4](#0-3) .

However, every default handler resolves the affected stacks using a **different** field of the same body:

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [5](#0-4) 

`PushHandler#process` then acts directly on those stacks:

```ruby
def process
  stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [6](#0-5) 

Since the HMAC signature only proves "this byte sequence was signed with organization X's secret" — it does not establish that `repository.full_name` inside that byte sequence belongs to organization X. An attacker who knows (or controls) the webhook secret for organization `attacker-org` (a legitimately configured, unprivileged tenant of this multi-tenant Shipit instance) can craft a JSON body where `repository.owner.login = "attacker-org"` (so `verify_signature` picks and successfully matches attacker-org's secret) but `repository.full_name = "victim-org/victim-repo"` (so the handler resolves and mutates a completely different organization's `Stack`). This breaks the intended binding: **the organization that authenticated the request must equal the repository being written**.

### Impact Explanation
This allows an attacker with legitimate access to only one configured (unprivileged) GitHub organization/tenant to forge webhook events that are processed against another organization's `Stack`, without ever proving control of that victim organization or repository. Concretely:
- `PushHandler` triggers `stack.sync_github(expected_head_sha:)` against the victim's stack, which — for stacks with `continuous_deployment` enabled — can lead to an **unauthorized deploy** being triggered off a forged `after` SHA.
- Other handlers sharing the same `Handler#stacks` resolution (status, check_suite, pull_request handlers) can inject forged commit statuses / check results / merge-queue state into a victim's stack, which can unblock or otherwise influence deploy gating for that stack.

This matches the Critical/High impact classes for this engine: an unauthorized deploy, and escalation of write/authorization boundaries across repositories that the caller was never authenticated for.

### Likelihood Explanation
Exploitation only requires knowledge of one organization's webhook secret (the attacker's own tenant in a multi-org Shipit deployment) and the ability to POST directly to the public, unauthenticated `/webhooks` endpoint with a custom body — no GitHub session, no `ApiClient` token, and no access to the victim organization are required. The webhooks endpoint is explicitly public/unauthenticated by design (only HMAC-verified), so this is reachable by any unprivileged external actor holding one tenant's secret.

### Recommendation
Bind the field used to select the verification secret to the same field used to resolve the affected repository/stack. Concretely:
- Verify the signature using the organization that will actually be used to look up the target repository (`repository.full_name`'s owner segment), rather than the separate `repository.owner.login`/`organization.login` fields, or
- After signature verification, explicitly assert that `repository_owner` equals the owner segment of `repository.full_name` before dispatching to any handler, rejecting the request (422) on mismatch.

### Proof of Concept
1. Attacker is a legitimate but unprivileged tenant of a multi-org Shipit instance, controlling GitHub org `attacker-org` and knowing its `webhook_secret` (configured for their own GitHub App installation).
2. Attacker crafts a push payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<sha that already exists in victim-org/victim-repo>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org secret, body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `github_app = Shipit.github(organization: "attacker-org")` and successfully verifies the signature [7](#0-6) .
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")` [8](#0-7)  and calls `stack.sync_github(expected_head_sha: ...)` on the victim's stack [6](#0-5) , even though the attacker was only authenticated for `attacker-org`.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping

    end

    end

**File:** lib/shipit.rb (L170-200)
```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
