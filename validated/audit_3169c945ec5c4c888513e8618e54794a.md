### Title
API lock actions attribute `Lock` authorship to an unauthenticated, attacker-controlled `X-Shipit-User` header identity - ([File: app/controllers/shipit/api/base_controller.rb])

### Summary
`Api::BaseController#identify_user` resolves `current_user` solely by looking up a `User` record whose `login` matches the client-supplied `X-Shipit-User` request header, with no verification that the request actually originated from that user. `Api::LocksController#create`/`#update` pass this unverified `current_user` directly into `stack.lock(params.reason, current_user)`, so a caller holding only a valid `lock:stack` API token can attribute a lock action to any existing GitHub-identity user record it names in the header.

### Finding Description
The binding that should hold is: `persisted_lock_actor == authenticated_identity_of_the_request`. In practice:

`Api::BaseController#current_user`/`#identify_user` (app/controllers/shipit/api/base_controller.rb:65-72):
```ruby
def current_user
  @current_user ||= identify_user || AnonymousUser.new
end

def identify_user
  user_login = request.headers['X-Shipit-User'].presence
  User.where('lower(login) = ?', user_login.downcase).first if user_login
end
```
This performs a plain lookup by login string taken from an HTTP header. There is no signature, no session, no OAuth check, no requirement that the API-token holder is related to that `User` record in any way — `authenticate_api_client` only validates the Basic Auth `ApiClient` token (app/controllers/shipit/api/base_controller.rb:48-61), and `require_permission!` only checks the `ApiClient`'s scope (`lock`, `stack`), never the identity in `X-Shipit-User`.

`Api::LocksController#create`/`#update` (app/controllers/shipit/api/locks_controller.rb:11-26) then call `stack.lock(params.reason, current_user)`, feeding this unauthenticated, header-derived `User` object into the lock-creation path as the acting user.

Any caller possessing a valid `lock:stack`-scoped API token (a legitimate but low-trust automation credential, not a GitHub session) can send `X-Shipit-User: <victim_login>` and have the resulting lock attributed to `victim_login`, even though that GitHub user never made the request, never authenticated, and may have no knowledge of the action. This falsifies the audit trail for a security-relevant action (locking a stack blocks all deploys), making it appear operator-authorized when it is not.

None of the listed guards prevent this: `verify_signature`/webhook checks are irrelevant to this API path; `force_github_authentication` is a web-session concern not used by `Api::BaseController` (it uses its own `current_user`/`identify_user` defined independently in `base_controller.rb`, distinct from `Shipit::Authentication#find_current_user` which is session-based); `require_permission!` only checks the token's stack/operation scope, not the actor identity; the `ExplicitParameters` schema for `LocksController` only validates `reason: String`, not any actor field.

### Impact Explanation
Any party holding a `lock:stack`-scoped `ApiClient` token can lock (or claim to unlock under) any stack it has access to while impersonating an arbitrary existing Shipit `User` (e.g., a well-known maintainer or on-call engineer) in the persisted lock's authorship/audit data. This blocks legitimate deploys for that stack while making the action appear to have been performed by the impersonated maintainer — a falsified-attribution/authentication-bypass-adjacent issue on a security-relevant control action. It is repeatable per request and against any stack the token has scope for.

### Likelihood Explanation
The attacker needs only a valid `lock:stack` API token (an "unprivileged" precondition relative to GitHub/session auth, since API tokens are commonly distributed to CI/automation and are not equivalent to a maintainer GitHub session). No GitHub secrets, webhook secret, or session cookie is required — only a header value the requester fully controls. Cost is a single HTTP request; the technique is trivially repeatable against any stack in scope.

### Recommendation
Do not derive attribution for security-relevant persisted state from `X-Shipit-User` without independent verification. Options: remove the header-based identity spoofing for write actions (locks, deploy triggers) entirely, or require that `X-Shipit-User` matches an identity that has been cryptographically bound to the request (e.g., verified via a signed assertion or matched against the `ApiClient`'s own owner), and audit-log the authenticated `ApiClient` (token) identity alongside/instead of the freely-supplied header value.

### Proof of Concept
```ruby
# test/controllers/api/locks_controller_test.rb
test "#create does not attribute the lock to a forged X-Shipit-User header" do
  victim = shipit_users(:walrus) # some legitimate maintainer fixture
  request.headers['X-Shipit-User'] = victim.login
  post :create, params: { stack_id: @stack.to_param, reason: 'Just for fun!' }
  assert_response :ok
  @stack.reload
  # Binding under test: persisted actor must equal the authenticated ApiClient identity,
  # NOT the spoofed header value.
  refute_equal victim.login, @stack.lock_author&.login # fails today: attribution == victim.login
end
```
This demonstrates that the persisted lock actor equals the attacker-chosen `X-Shipit-User` value rather than any independently authenticated identity.
