[1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) ### Title
Cross-organization webhook confusion allows an attacker's own org secret to archive/deprovision another org's ReviewStack - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/pull_request/closed_handler.rb], [File: app/models/shipit/repository.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to check the request against using `params.dig('repository', 'owner', 'login')`, while `ClosedHandler#repository` (and `Repository.from_github_repo_name`) resolves the actual target `Repository` using an entirely separate field, `params.repository.full_name`, split on `/`. Nothing cross-validates that these two independently-read subfields of the same JSON body agree, so a payload can be signed as belonging to org A while its `full_name` targets a repository owned by org B.

### Finding Description
The binding the system needs to hold is: `organization_used_for_signature_verification == owner(repository_targeted_by_handler)`, i.e. `params.repository.owner.login == owner_segment(params.repository.full_name)`.

Tracing the code:
- `WebhooksController#verify_signature` picks the `GithubApp` (and thus the `webhook_secret` used for HMAC verification) via `repository_owner`, which reads only `params.dig('repository', 'owner', 'login')` (with an `organization.login` fallback) [1](#0-0) [2](#0-1) .
- `ClosedHandler#repository` resolves the target `Repository` using `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [3](#0-2) , and `from_github_repo_name` simply splits `full_name` on `/` and looks up `owner`/`name` — it never checks `repository.owner.login` [6](#0-5) .
- `verify_webhook_signature` computes `OpenSSL::HMAC.hexdigest` over the raw body using the `webhook_secret` of whichever org `Shipit.github(organization: ...)` resolves to [5](#0-4) .

Because these two lookups are decoupled, an attacker who legitimately administers "attacker-org" on a multi-organization Shipit deployment (and therefore knows attacker-org's configured `webhook_secret`, per the documented multi-org setup) can craft a `pull_request` `closed` payload where:
- `repository.owner.login = "attacker-org"` → `verify_signature` selects and validates against attacker-org's own secret → passes.
- `repository.full_name = "victim-org/victim-repo"` → `ClosedHandler#repository` resolves the real victim repository.
- `number` = N guessed/known to match an existing provisioned ReviewStack environment `pr#{N}` under `victim-org/victim-repo`.
- `action = "closed"`.

`ClosedHandler#process` then calls `review_stack.archive!` on the victim's `ReviewStack`, which (per the question's stated call chain) leads to `stack.deprovision`, issuing real deprovisioning commands against the victim's infrastructure — entirely driven by a payload whose cryptographic signature only proves control of "attacker-org", not "victim-org".

None of the listed guards prevent this: `verify_signature` only checks the signature against the org named in the *owner* subfield, not against the org actually targeted by `full_name`; `drop_unhandled_event` and `ExplicitParameters` schema validation only check shape, not cross-field consistency; `Repository` model validations only constrain the format of `owner`/`name` strings, not that they match `repository.owner.login` from the webhook payload.

### Impact Explanation
A successfully signed payload for one org can trigger destructive lifecycle operations (`archive!` → `deprovision`, potentially involving `Command` invocations) against a ReviewStack belonging to a completely different, unrelated org/tenant. This is a payload for one repository/organization mutating another's stack — matching the Critical impact category explicitly listed ("a payload for one repository mutating another's stack, commit, task or team"). It is repeatable against any victim org sharing the same multi-tenant Shipit instance, for any guessed/known PR number with an active ReviewStack, and requires no privileges over the victim org whatsoever.

### Likelihood Explanation
This requires: (1) a Shipit deployment configured for multiple GitHub organizations (the documented multi-org `github:` config format), (2) the attacker controlling/administering at least one of those onboarded orgs (and thus its `webhook_secret`), and (3) the victim org having an active ReviewStack at a PR number the attacker can guess or observe. Attacker cost is low — crafting and POSTing a JSON payload with a valid HMAC using their own known secret is trivial; PR numbers are often sequential/discoverable. The attack is fully repeatable against any tenant repository/PR combination on the shared instance.

### Recommendation
Cross-validate the org embedded in `repository.full_name` (and/or `repository.owner.login`) against the org actually used to select the signing secret before dispatching to handlers — e.g., in `WebhooksController`, reject the request (422) if `params.dig('repository','owner','login')` does not match the owner segment of `params.dig('repository','full_name')`. Alternatively, have `Repository.from_github_repo_name`-based lookups always scope by the verified `repository_owner`, not by the untrusted `full_name` string alone.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (proof sketch)
test "cross-org pull_request closed payload archives a different org's review stack" do
  # victim-org repository with an active ReviewStack at pr#7
  victim_repo = shipit_repositories(:shipit) # owner: 'shopify' (victim-org)
  review_stack = shipit_review_stacks(:some_active_stack) # environment 'pr7', repository: victim_repo, not archived

  # Shipit configured for two orgs; attacker-org's secret is known/controlled by attacker
  Shipit.github(organization: 'attacker-org') # configured with attacker's own webhook_secret

  payload = {
    action: 'closed',
    number: 7,
    pull_request: { id: 1, number: 7, url: 'http://x', title: 't', state: 'closed',
                     additions: 1, deletions: 1, head: { sha: 'abc', ref: 'r' },
                     user: { login: 'attacker' }, assignees: [], labels: [] },
    repository: { full_name: victim_repo.full_name, owner: { login: 'attacker-org' } },
    sender: { login: 'attacker' }
  }.to_json

  signature = "sha1=#{OpenSSL::HMAC.hexdigest('sha1', attacker_org_webhook_secret, payload)}"

  @request.headers['X-Github-Event'] = 'pull_request'
  @request.headers['X-Hub-Signature'] = signature

  refute review_stack.archived?
  post :create, body: payload, as: :json
  assert_response :ok

  assert review_stack.reload.archived?, "victim-org's ReviewStack was archived by a payload signed under attacker-org's secret"
end
```
This asserts both sides of the broken binding: signature verification succeeds under `attacker-org`'s secret (left side), while the mutated resource (`review_stack.archived?`) belongs to `victim-org`'s repository (right side) — demonstrating the two are not required to match.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
