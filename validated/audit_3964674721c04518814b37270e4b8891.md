## Title
Membership webhook cross-organization team hijack via `github_id`-only lookup in `MembershipHandler#process` - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

## Summary
`MembershipHandler#find_or_create_team!` looks up an existing `Team` solely by `params.team.id` (the GitHub team's numeric `github_id`), and only sets `team.organization` inside the `find_or_create_by!` block that runs **only on creation**. When the team already exists (e.g. because it's a `Shipit.github_teams` entry belonging to a different, victim organization), the found record's `organization` is never checked against the webhook's signing organization before `team.add_member(member)` runs.

## Finding Description
The broken binding: `params.organization.login` (the org whose `webhook_secret` verified the request in `WebhooksController#verify_signature`) must equal the real owning organization of the `Team` row identified by `params.team.id`. Before and after tracing, these remain unequal and unenforced.

Path:
- `WebhooksController#verify_signature` resolves `Shipit.github(organization: repository_owner)` where `repository_owner` falls back to `params.dig('organization', 'login')` for events without a `repository` key [1](#0-0) [2](#0-1) . This only proves the request was signed with *some* configured organization's secret — it says nothing about which `Team` row the payload is allowed to touch.
- `MembershipHandler#find_or_create_team!` does `Team.find_or_create_by!(github_id: params.team.id) do |team| team.organization = params.organization.login end` — the block that assigns `organization` executes **only when a new record is created**; when a `Team` with that `github_id` already exists (e.g. a `Shipit.github_teams` entry for `victim_org`), it is simply returned unchanged [3](#0-2) .
- `process` then calls `team.add_member(member)`, appending the attacker-controlled `User` (created via `User.find_or_create_by_login!(params.member.login)`) to that team's `members` [4](#0-3) [5](#0-4) .
- `Shipit.github_teams` builds its authorization team list from configured `oauth.teams` handles, each fetched/created via `Team.find_or_create_by_handle`, giving those teams real `github_id`s tied to the real owning org [6](#0-5) .
- `User#authorized?` grants access purely based on membership in any team whose `id` is in `Shipit.github_teams.map(&:id)`, with no organization check [7](#0-6) .

Exploit flow (requires a multi-tenant Shipit deployment, as supported by `test/dummy/config/secrets_double_github_app.yml`, where the operator has configured a GitHub App for `attacker_org` in addition to `victim_org`): the attacker, who legitimately controls `attacker_org`'s own GitHub App/webhook secret, sends `X-Github-Event: membership` with `action: 'added'`, `team: { id: <victim_org's Shipit.github_teams github_id>, name, slug, url }`, `organization: { login: 'attacker_org' }`, `member: { login: 'attacker_login' }`, signed with `attacker_org`'s own `webhook_secret`. `verify_signature` succeeds because it only validates against `attacker_org`'s app config. `find_or_create_team!` finds the pre-existing victim team by `github_id` and returns it untouched; `add_member` then adds the attacker as a member of that real, privileged team.

No existing guard (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema, model validations) ties the signing organization to the `Team`'s actual `organization` column.

## Impact Explanation
The attacker's own webhook-signed request creates a `Membership` row linking their arbitrary GitHub login to a `Team` record that is part of `Shipit.github_teams`, without ever being a real member of that GitHub team or organization. Since `User#authorized?` checks only team-id membership, `current_user.authorized?` becomes true for the attacker, granting them access equivalent to legitimate `victim_org` team members — an escalation into `Shipit.github_teams` authorization across tenant boundaries. This is repeatable against any `Team` whose `github_id` the attacker can learn or guess, and applies to every team referenced in Shipit's `github_teams` authorization list.

## Likelihood Explanation
Requires: (1) a multi-organization Shipit deployment where the attacker legitimately controls a GitHub App/organization also configured in Shipit's `github:` secrets (a supported, documented configuration per `docs/setup.md` and `test/dummy/config/secrets_double_github_app.yml`); (2) the victim team's `github_id` already persisted as a `Team` row (guaranteed for any team listed in `Shipit.github_teams`, since it's fetched/created at config load); (3) knowledge or guessability of that team's numeric `github_id` (GitHub team IDs are small sequential integers, discoverable via GitHub's public/team APIs or prior webhook deliveries). Given these, the attack costs a single crafted, self-signed HTTP POST — no privileged Shipit credentials needed.

## Recommendation
In `find_or_create_team!`, verify that the found or created `Team#organization` equals `params.organization.login` before proceeding; reject (or no-op) the membership event if they differ, rather than silently operating on a pre-existing team owned by another organization.

## Proof of Concept
Minitest plan (integration/controller test) under `test/controllers/webhooks_controller_test.rb`:
1. Create fixture `Team` `victim_team` with `organization: 'victim_org'`, `github_id: 999`, included in `Shipit.github_teams` (stub `Shipit.github_teams` to include it, or add its handle to oauth config fixture).
2. Stub `Shipit.github(organization: 'attacker_org')` to be a valid configured app (e.g. via `secrets_double_github_app.yml`-style fixture) so `verify_signature` succeeds with an attacker-computed signature.
3. POST to `/webhooks` with header `X-Github-Event: membership`, body `{ action: 'added', team: { id: 999, name: 'Victim Team', slug: 'victim-team', url: '...' }, organization: { login: 'attacker_org' }, member: { login: 'attacker_login' } }`, signed with `attacker_org`'s secret.
4. Assert: `Team.count` unchanged (no new team created) — `assert_no_difference -> { Team.count }`.
5. Assert: `Membership.exists?(team_id: victim_team.id, user: User.find_by(login: 'attacker_login'))` is true.
6. Assert: `User.find_by(login: 'attacker_login').authorized?` is `true`, while `victim_team.reload.organization == 'victim_org'` (unchanged) — demonstrating `params.organization.login ('attacker_org') != victim_team.organization ('victim_org')` yet the membership/authorization was still granted, violating webhook provenance.
