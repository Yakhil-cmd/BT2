### Title
Unbounded `count_coins` in asset denomination definitions causes floating-point precision loss / overflow when computing `total_cap_from_denominations`, corrupting asset cap and issuance validation - (File: validation.js)

### Summary
When a user defines a fixed-denomination asset, `validateAssetDefinition` computes `total_cap_from_denominations` by summing `count_coins * denomination` for each denomination entry. `denomination` is bounds-checked against `constants.MAX_CAP`, but `count_coins` is validated only with `isPositiveInteger`, which imposes no upper bound at all. Because JavaScript arithmetic is double-precision floating point, an attacker can supply an astronomically large `count_coins` value, causing the multiplication and subsequent summation to lose precision or overflow toward `Infinity`, silently producing a `total_cap_from_denominations` value that no longer reflects the true intended product.

### Finding Description
In `validateAssetDefinition`, the denomination loop enforces an upper bound only on `denomination`: [1](#0-0) 
but `count_coins` is checked with `isPositiveInteger` only, which merely verifies the value is a finite float with no fractional part — for very large magnitudes (well beyond `Number.MAX_SAFE_INTEGER`) essentially any large float trivially passes this check because floats of that magnitude cannot represent fractions: [2](#0-1) 
The unchecked value is then used directly in a multiplication that determines the asset's total capped supply: [3](#0-2) 
This same unchecked `count_coins` value is stored in `asset_denominations.count_coins` (a `BIGINT` column) and is later multiplied again during issue-input validation: [4](#0-3) 
and again during coin-picking/issuance composition in `indivisible_asset.js`: [5](#0-4) 
Because all of these computations are performed in JS double-precision floats without re-validating the product against `Number.MAX_SAFE_INTEGER`, an attacker-crafted `count_coins` can push `count_coins * denomination` into a range where floating-point rounding causes different code paths (or different node versions/db backends with different numeric handling, e.g. SQLite `BIGINT` affinity vs. JS number vs. MySQL `BIGINT`) to disagree about the exact resulting integer value.

### Impact Explanation
If the computed cap/product value differs between validation time (JS float arithmetic in `validation.js`) and storage/comparison time (SQL `BIGINT` in `asset_denominations`, or repeated JS multiplication during issuance in `indivisible_asset.js`), nodes could disagree on whether an issuance amount is valid, or the same "supply cap" could be interpreted differently across code paths. This falls into the category of node disagreement on validity, and in the worst case could allow an issuer to construct a fixed-denomination asset whose declared cap and actual issuable amount diverge from what other nodes independently recompute, risking supply-inflation-like inconsistencies for the affected asset.

### Likelihood Explanation
Any unprivileged asset issuer can post an asset-definition message with `fixed_denominations: true` and `denominations` including an entry with an extremely large `count_coins` (e.g., `1e18` or larger) and a small `denomination`. No privileged role, network position, or special access is required — this is exactly the "asset issuer" attack surface named as in-scope in the rules.

### Recommendation
Add an explicit upper bound on `count_coins` (e.g., require `count_coins <= constants.MAX_CAP` and additionally require `count_coins * denomination` to be `<= constants.MAX_CAP` and representable exactly, e.g. via `Number.isSafeInteger` after the multiplication) in the denomination validation loop in `validateAssetDefinition` (validation.js) and in the mirrored AA asset-definition validator in `aa_validation.js`. Reject any denomination entry where `count_coins * denomination` is not a safe integer, before accumulating into `total_cap_from_denominations`.

### Proof of Concept
1. As any user, post an `asset` definition unit with:
```json
{
  "fixed_denominations": true,
  "cap": 9007199254740992,
  "denominations": [
    { "denomination": 1, "count_coins": 9007199254740992 }
  ],
  "is_private": false,
  "is_transferrable": true,
  "auto_destroy": false,
  "issued_by_definer_only": true,
  "cosigned_by_definer": false,
  "spender_attested": false
}
```
2. `count_coins` passes `isPositiveInteger` (it is a finite integer-valued float), and `denomination` (1) passes the `MAX_CAP` bound check.
3. `total_cap_from_denominations = 9007199254740992 * 1` is computed and compared to `payload.cap`; because the value sits exactly at `Number.MAX_SAFE_INTEGER`, further arithmetic on this value in subsequent issuance validation (`denomination * denomInfo.count_coins` in `validation.js` line 2224, or `count_coins_to_issue * denomination` in `indivisible_asset.js` line 536) risks precision-losing results, and different runtime/DB numeric representations (JS float vs. SQL `BIGINT`) can diverge, producing inconsistent validation outcomes across nodes for the same asset's issuance amount.
