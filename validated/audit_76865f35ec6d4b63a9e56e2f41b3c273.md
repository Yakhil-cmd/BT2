### Title
Secondary AA triggers expose the immediate calling AA address as `trigger.address`, causing funds to be permanently locked when a proxy/forwarder AA is used - (File: `aa_composer.js`)

### Summary
The reported bug is a class of vulnerability where a relay/forwarder contract's own address is mistaken for — and recorded as — the address of the true originating party, causing subsequent value transfers to be sent to the relay instead of the end user, where they become stuck because the relay has no logic to forward or reclaim them. Obyte's Autonomous Agent (AA) trigger-chaining mechanism reproduces the identical structural hazard: when one AA calls another AA by forwarding a payment (a "proxy" or "fundraising forwarder" pattern, as documented in the codebase's own sample AAs), the called (secondary) AA's `trigger.address` is populated with the address of the immediate calling AA — not the original human/AA that initiated the whole chain.

### Finding Description
In `getTrigger()`, the `trigger.address` field is always set to `objUnit.authors[0].address`, i.e. the author of the unit that produced the payment message: [1](#0-0) 

When a primary trigger is processed, `handlePrimaryAATrigger` copies this address into `trigger.initial_address` so the original caller can still be recovered later: [2](#0-1) 

However, when an AA response triggers another AA (a "secondary trigger", exactly the "proxy forwards funds to another contract" pattern from the report), `handleSecondaryTriggers` builds a brand-new `child_trigger` via `getTrigger(objUnit, row.address)`. Because the response unit's author is the *forwarding* AA (not the original end user), `child_trigger.address` now equals the forwarding AA's own address. Only `child_trigger.initial_address`/`initial_unit` are explicitly propagated to preserve the real originator: [3](#0-2) 

The oscript language itself exposes both `trigger.address` and `trigger.initial_address` as first-class getters, confirming that this ambiguity is a known, load-bearing distinction that AA authors must get right: [4](#0-3) 

This mirrors the report's root cause precisely: the "obvious" field that looks like it identifies the paying party (`trigger.address` / `msg.sender`) actually identifies the immediate relay/proxy in a multi-hop call, not the original party. The codebase's own sample AA, `fundraising_proxy.oscript`, demonstrates this exact "collect funds and forward to another AA" pattern (a proxy that raises funds and forwards to a `$destination_aa`): [5](#0-4) 

If any AA in such a forwarding chain refunds, bounces, or pays fees/ownership shares using `trigger.address` instead of `trigger.initial_address` (a natural mistake, since the field is misleadingly named relative to a single-hop mental model, and is exactly the mistake made in the audited Solidity contract with `msg.sender`), the payment is routed back to the forwarding AA's own balance rather than to the real end user. Because a generic AA only reacts to defined `if`/`messages` cases, an AA balance credited unexpectedly (as a plain "output" that doesn't match any trigger condition intentionally handling it) has no guaranteed mechanism to detect or re-forward that specific payment to the correct party — it is commingled with the AA's other funds and effectively unrecoverable by the original payer.

### Impact Explanation
Funds sent through a chain of AAs (a common design pattern for proxy/aggregator/forwarding AAs, as shown by the shipped sample) can become permanently misdirected to an intermediate AA's balance instead of reaching the intended end user, exactly as with the LayerZero Deployer receiving fees that the DAO owner can never claim. This is a fund-loss/fund-freezing condition reachable by any user who triggers a multi-hop AA chain, and it is triggered by AA logic that plausibly (and easily) uses the wrong of the two documented address fields.

### Likelihood Explanation
Likelihood is high: `trigger.address` vs `trigger.initial_address` is a subtle but pervasive AA-authoring decision point that every chained/proxy AA must get right, and the field naming (`trigger.address` looks like "the sender") invites exactly the same mistake documented in the external report. The engine provides no protection or warning against using the wrong field for payouts in secondary-trigger scenarios, and this is reachable by any ordinary user simply by sending a trigger unit into a chain of publicly deployed AAs.

### Recommendation
Because `trigger.address` in a secondary trigger context is easily confused with the original payer, consider requiring AA validation/documentation to strongly disambiguate the two fields (e.g., stricter linting/warnings in `formula/validation.js` when `trigger.address` is used in a payment output inside an AA that can be triggered by other AAs), or provide a getter that more explicitly identifies "the address that would receive a refund/payout for the current asset" to reduce the chance that AA authors accidentally leak funds to intermediate forwarding AAs.

### Proof of Concept
The existing test suite already demonstrates the exact mechanics of `trigger.address` diverging from `trigger.initial_address` across a chain of AAs: [6](#0-5) 
In this test, the `secondary_aa` correctly pays out to `trigger.initial_address` to reach the original `trigger_address`; if it had instead used `trigger.address`, the payment would have gone to `primary_address` (the forwarding AA) instead of the original human-controlled address — reproducing the exact "fee sent to the relay/deployer instead of the real owner" bug class from the external report.

function getTrigger(objUnit, receiving_address) {
	var trigger = { address: objUnit.authors[0].address, unit: objUnit.unit, outputs: {} };
	if ("max_aa_responses" in objUnit)
		trigger.max_aa_responses = objUnit.max_aa_responses;
	objUnit.messages.forEach(function (message) {
		if (message.app === 'data' && !trigger.data) // use the first data message, ignore the subsequent ones
			trigger.data = message.payload;
		else if (message.app === 'payment' && message.payload) {
			var payload = message.payload;
			var asset = payload.asset || 'base';
			payload.outputs.forEach(function (output) {
				if (output.address === receiving_address) {
					if (!trigger.outputs[asset])
						trigger.outputs[asset] = 0;
					trigger.outputs[asset] += output.amount; // in case there are several outputs
				}
			});
		}
	});
	if (Object.keys(trigger.outputs).length === 0)
		throw Error("no outputs to " + receiving_address);
	return trigger;
}
