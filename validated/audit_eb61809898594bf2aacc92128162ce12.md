### Title
Double invocation of async callback in private-payment chain processing can crash the node (uncaught exception) - ([File: network.js])

### Summary
`handleSavedPrivatePayments()` in `network.js` processes private-payment chains that were forwarded to it by a payment counterparty (e.g. via a hub or direct device message). The `validateAndSave` inner function contains an error-handling path that falls through after a caught exception and can invoke the `async.each` iteratee callback `cb` twice for the same chain, matching the "unhandled exception kills the process" bug class described in the engine.io advisory (GHSA-r7qp-cfhv-p84w / CVE-2022-41940), but here triggered by a malformed private-payment payload rather than a raw TCP error.

### Finding Description
Inside `validateAndSave` [1](#0-0) , the code does:
```js
var validateAndSave = function(){
    var objHeadPrivateElement = arrPrivateElements[0];
    try {
        var json_payload_hash = objectHash.getBase64Hash(objHeadPrivateElement.payload, true);
    }
    catch (e) {
        console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
        if (ws)
            sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
        deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
    }
    var key = 'private_payment_validated-'+objHeadPrivateElement.unit+'-'+json_payload_hash+'-'+row.output_index;
    privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, { ... });
};
```
There is no `return` after the `catch` block. If `objectHash.getBase64Hash()` throws (e.g. because `objHeadPrivateElement.payload` is malformed/non-serializable, which a counterparty fully controls since these payloads arrive from `unhandled_private_payments` rows populated by peer/device-supplied data), the code:
1. Calls `deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb)` inside the `catch` block — this deletes the DB row and asynchronously invokes `cb()` once the delete completes.
2. Execution then falls through past the `catch` and continues synchronously to build `key` (using an `undefined` `json_payload_hash`) and calls `privatePayment.validateAndSavePrivatePaymentChain(...)`, whose `ifOk`/`ifError`/`ifWaitingForChain` callbacks each *also* call `deleteHandledPrivateChain(..., cb)` (or `cb()` directly for `ifWaitingForChain`) [2](#0-1) .

This results in the `async.each` iteratee callback `cb` for that row being invoked twice. Depending on the version of the `async` library in use, invoking an `async.each` iteratee callback more than once throws a synchronous "Callback was already called" style error. Because this occurs off the main validation/writer mutex path, it is not wrapped in a way that funnels into a controlled error callback; it can surface as an uncaught exception. `network.js` installs a global handler that explicitly re-throws on `uncaughtException` to avoid running with corrupted in-memory state [3](#0-2) , meaning any uncaught exception anywhere in the process — including this one — crashes the whole node process, not just the connection that triggered it.

### Impact Explanation
A payment counterparty (or a hub forwarding a crafted private-payment payload) can supply a private-element chain whose head `payload` cannot be hashed by `objectHash.getBase64Hash` (e.g., containing values not supported by `getJsonSourceString`, such as `undefined`, non-finite numbers, or deeply cyclic/invalid structures reaching this code path via `JSON.parse(row.json)` at [4](#0-3) ). When the recipient wallet/hub processes it through `handleSavedPrivatePayments`, the double-callback bug is triggered, and the process-wide `uncaughtException` handler crashes the Node.js process. This affects any full node or wallet that receives and processes private payments (a private-payment counterparty), taking the node offline until manually restarted — i.e., "a network unable to confirm new units" for that node, matching the required impact bar.

### Likelihood Explanation
The trigger requires only sending a private-payment chain with a payload the sender fully controls, no privileged access or race condition is needed, and the vulnerable code path (`handleSavedPrivatePayments` → `validateAndSave`) runs automatically whenever `unhandled_private_payments` rows exist for the recipient. Reliability depends on being able to make `objectHash.getBase64Hash`/`getJsonSourceString` throw on attacker-chosen payload content and on the specific `async` version's behavior on double-callback invocation, both of which I could not fully verify from the indexed files (the `async` package version and `getJsonSourceString`'s exact throw conditions were not retrievable in this session).

### Recommendation
Add a `return` immediately after calling `deleteHandledPrivateChain(...)` inside the `catch` block in `validateAndSave` so that `cb` is only ever invoked once per chain, and audit other similar `try { } catch { ...; call cb... }` blocks in `network.js` for the same missing-`return` pattern.

### Proof of Concept
Conceptual reproduction (not verified end-to-end due to indexing limits on the `async` module version):
1. As a private-payment counterparty, construct a chain whose head element `payload` cannot be JSON-source-stringified (e.g., an object containing a non-finite number or unsupported type) and deliver it so it lands in `unhandled_private_payments`.
2. Trigger `handleSavedPrivatePayments()` processing (this happens automatically for saved/unhandled private payments).
3. `objectHash.getBase64Hash(objHeadPrivateElement.payload, true)` throws inside `validateAndSave`.
4. `deleteHandledPrivateChain(..., cb)` is called in the `catch` block; execution falls through and `privatePayment.validateAndSavePrivatePaymentChain` is invoked, whose callbacks call `deleteHandledPrivateChain`/`cb` a second time for the same `async.each` item.
5. The duplicate callback invocation throws inside the `async` library, which is not caught anywhere in this path, and propagates to the global `uncaughtException` handler in `network.js`, crashing the node process.

I could not confirm the exact `async` library version's double-callback throw behavior or a concrete payload value guaranteed to make `getJsonSourceString`/`getBase64Hash` throw from the indexed files alone; verifying these two points requires direct file/dependency access, which is a good candidate for a full Devin session to confirm exploitability precisely.
