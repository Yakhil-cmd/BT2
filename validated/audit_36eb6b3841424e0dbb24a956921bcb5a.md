### Title
Cross-tenant stack read in CCMenu API via unscoped `Stack.from_param!` bypassing `stack_id` restriction - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController#stack` overrides the base controller's scoped lookup with an unscoped `Stack.from_param!(params[:stack_id])`, so an `ApiClient` token restricted to one stack via `stack_id` can be used to read the CCMenu XML status (build status, last deploy, lock reason) of any other stack.

### Finding Description
The claimed binding is `current_api_client.stack_id == stack.id` when `current_api_client.stack_id?` is true. In `Shipit::Api::BaseController#stacks`, this binding is enforced: `@stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` and the base `#stack` method looks up via `stacks.from_param!(params[:stack_id])`, so an out-of-scope `stack_id` param raises a not-found error. [1](#0-0) 

However, `CCMenuController` overrides `#stack` to bypass the scoped `stacks` helper entirely: `@stack ||= Stack.from_param!(params[:stack_id])`, resolving directly against all stacks regardless of `current_api_client.stack_id`. [2](#0-1) 

Permission checking only validates the operation/scope string, not the stack: `check_permissions!` does `permissions.include?("#{operation}:#{scope}")` with no reference to `stack_id`. [3](#0-2)  The `require_permission :read, :stack` before_action in `CCMenuController` therefore passes for any client holding `read:stack`, irrespective of which stack it was scoped to. [4](#0-3) 

Exploit flow: attacker obtains/uses a valid `ApiClient` token whose `permissions` include `read:stack` and `stack_id` is set to `victim-org/victim-repo/production` (stack A). Attacker sends `GET /api/stacks/attacker-org/attacker-repo/production/ccmenu?token=<token>` (stack B, a different stack owned by the attacker or any target). `authenticate_api_client` (overridden in this controller) authenticates via `ApiClient.authenticate(params[:token])`. [5](#0-4)  `require_permission!` passes because it never inspects `stack_id`. `#show` then calls the overridden `#stack`, which resolves stack B directly via `Stack.from_param!` — no `stack_id` filter applied — and renders stack B's CCMenu XML (build status, last deploy, lock reason) to the caller. [6](#0-5) 

This diverges from the intended binding enforced everywhere else in the API (e.g. `Api::StacksController` and other controllers use the base `#stack`/`#stacks` scoped lookup). The override in `CCMenuController` is the sole root cause; no other guard (`verify_signature`, `ExplicitParameters`, model validations) applies to this read path since it is a GET with a token query param, not a webhook.

### Impact Explanation
A token scoped to read one stack (e.g. minted for a public or low-sensitivity repo) can be reused to read the CCMenu status of any other stack in the Shipit instance, exposing build/deploy status and lock reasons cross-tenant. This is an unauthenticated-for-that-resource read of stack state by a party never granted access to it — matching the High severity category "escalation... unauthenticated read of stack state, task streams or deploy output." Repeatable for every stack the attacker can guess/enumerate `stack_id` route params for (`:repository_owner/:repository_name/:environment`), which are effectively public identifiers (repo name/owner/environment), so the blast radius covers the entire Shipit instance's stacks.

### Likelihood Explanation
Requires the attacker to possess *any* valid `ApiClient` token with `read:stack` permission scoped to at least one stack (e.g., a token legitimately issued to them for their own repo's CI integration, common in ChatOps/CCMenu setups). Given such a token — which is a normal, low-privilege credential many integrators would legitimately hold — the attack is a single unauthenticated GET request with no other secrets needed. This is low-cost and highly repeatable once a scoped token is obtained.

### Recommendation
Remove the `#stack`/`#authenticate_api_client` overrides in `Shipit::Api::CCMenuController` and use the base controller's scoped `#stack` method (`stacks.from_param!(params[:stack_id])`), or explicitly assert `stack.id == current_api_client.stack_id` (when `stack_id?` is true) before rendering.

### Proof of Concept
In a minitest `ActionController::TestCase` (or integration test) under `test/controllers/api/ccmenu_controller_test.rb`:
1. Create `stack_a = create(:stack, repository: create(:repository, owner: 'victim-org', name: 'victim-repo'), environment: 'production')` and `stack_b = create(:stack, repository: create(:repository, owner: 'attacker-org', name: 'attacker-repo'), environment: 'production')`.
2. Create `api_client = create(:api_client, permissions: ['read:stack'], stack_id: stack_a.id)`.
3. Issue `GET :show, params: { repository_owner: stack_b.repository.owner, repository_name: stack_b.repository.name, environment: stack_b.environment, token: api_client.authentication_token }`.
4. Assert `response.status == 200` and response body contains stack B's project name/data (`assert_match(/attacker-repo/, response.body)`), proving `stack.id (== stack_b.id) != current_api_client.stack_id (== stack_a.id)` yet access was granted — the binding `stack.id == current_api_client.stack_id` is violated while returning 200 instead of the expected 403/404.
