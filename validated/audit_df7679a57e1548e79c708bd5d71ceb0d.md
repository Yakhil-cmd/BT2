### Title
Pre-publish exec-hook does not actually gate symlink publish in periodic sync mode - ([File: main.go])

### Summary
`--pre-publish-exechook-command` is documented as running "before publishing the symlink," implying it acts as a gate that can reject/delay publication of a newly-fetched commit. In the periodic (non `--one-time`) sync path, the code fires this hook asynchronously and unconditionally proceeds to publish, regardless of whether the hook has finished or succeeded. This mirrors the report's bug class: a guard/check is invoked, but the state-changing action ("publish") is not actually contingent on that check completing, so the intended protection is bypassed.

### Finding Description
`syncHooks.beforePublish` only enqueues work on a non-blocking channel and returns immediately, without waiting for the hook to run or checking its result: [1](#0-0) 

`HookRunner.Send`/`hookData.send` is explicitly non-blocking — if a hook run is already in flight, the new hash simply overwrites the previous one and the write to the trigger channel is dropped if the channel is full: [2](#0-1) 

In `SyncRepo`, `beforePublish` is called, its (always-nil, unless the runner is nil) error is checked, and then `publishSymlink` is invoked immediately afterward — there is no wait for the pre-publish hook's actual completion or success/failure status in this path: [3](#0-2) 

The only place the code actually waits for the pre-publish hook's *result* is the `--one-time` exit path, via `prePubExechookRunner.WaitForCompletion()`: [4](#0-3) 

This means that for the normal, periodic mode (the default and most common deployment pattern, since `--one-time` is opt-in), the "before publish" check is a check-then-act pattern where the act (publish) does not actually depend on the check's outcome — analogous to the reported pattern where a status/guard is not enforced at the point it should be, only cosmetically invoked.

### Impact Explanation
If an operator relies on `--pre-publish-exechook-command` as a content-validation gate (e.g., to scan/verify a newly fetched commit before it becomes visible to the consumer via `--link`), a commit that should be rejected can still be published to the live symlink because publish proceeds without waiting on the hook. This falls under "publishing wrong or partial content" — untrusted repository content that the hook is meant to vet can reach consumers regardless of the hook's verdict.

### Likelihood Explanation
This triggers on every normal (non `--one-time`) sync where `--pre-publish-exechook-command` is configured, requiring no attacker action beyond pushing a commit to the synced ref — the standard "attacker-pushed commit" trigger. It requires the operator to be using `--pre-publish-exechook-command` for gating purposes and not `--one-time` mode, which is a fairly common assumption based on the flag's documented behavior.

### Recommendation
In `SyncRepo`'s `beforePublish` handling, block on the pre-publish hook's actual completion (e.g. via a synchronous call or a wait mechanism similar to `WaitForCompletion`) and propagate failure before calling `publishSymlink`, in both periodic and one-time modes, rather than only in the `--one-time` exit path.

### Proof of Concept
Not independently reproduced in this analysis (would require running git-sync in periodic mode with a `--pre-publish-exechook-command` that fails/rejects a specific commit, then observing that the symlink is still updated to that commit while the hook is still retrying/failing) — this is inferred directly from the code paths cited above, not confirmed via execution.
