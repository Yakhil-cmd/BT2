### Title
`review_stacks_enabled` is not enforced for `allow_with_label`/`prevent_with_label` provisioning behaviors due to operator precedence bug - (File: `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb`)

### Summary
`Repository#review_stacks_enabled` is intended to be a master switch gating all PR review-stack provisioning, but in `OpenedHandler#provision?` Ruby's `&&`/`||` precedence causes it to only gate the `allow_all` clause, not the `allow_with_label` or `prevent_with_label` clauses. An attacker who can label their own PR can satisfy `allow_with_label` and cause a review stack to be provisioned even when the operator has set `review_stacks_enabled: false`.

### Finding Description
The broken binding: `repository.review_stacks_enabled == true` is required for provisioning to occur (operator's authorization truth), but the actual code evaluates:

```ruby
repository.review_stacks_enabled &&
  repository.provisioning_behavior_allow_all? ||
  (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
  (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
``` [1](#0-0) 

Because `&&` binds tighter than `||`, this parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`. `review_stacks_enabled` is ANDed only into the first disjunct. The second and third disjuncts are fully independent of `review_stacks_enabled`. `pull_request_has_provisioning_label?`/`pull_request_label_names` simply read `pull_request["labels"]` from the webhook payload, a field fully attacker-controlled on their own PR [2](#0-1) .

Exploit flow: operator sets `repository.review_stacks_enabled = false` and `provisioning_behavior = :allow_with_label` with some `provisioning_label_name`. Attacker opens a PR from their fork with `head.ref` pointing at attacker-controlled code and self-adds a label matching `provisioning_label_name` (labels on one's own PR can be applied by any contributor with issue-write access on many repos, or via the `labeled`/`opened` webhook payload construction generally — regardless, the label is attacker-supplied data in the payload). `respond_to_pull_request_opened?` calls `provision?`, which now evaluates true via the `allow_with_label? && pull_request_has_provisioning_label?` clause despite `review_stacks_enabled` being false. `process` then calls `ReviewStackAdapter#find_or_create!`, which creates a `ReviewStack` with `branch: params.pull_request.head.ref` from the attacker's fork and queues it via `Shipit::ReviewStackProvisioningQueue.add(stack)` [3](#0-2) , eventually leading to task execution of `shipit.yml` from the attacker's branch.

No other guard checks `review_stacks_enabled` before this point — `ReviewStackAdapter` and `ProvisioningHandler::Base#provision?` do not re-check it [4](#0-3) , and the existing test suite only covers the `allow_all` case combined with `review_stacks_enabled: false` (`"only provision stacks for repos with auto-provisioning enabled"` at lines 96-107), never testing `allow_with_label`/`prevent_with_label` combined with `review_stacks_enabled: false` [5](#0-4) . That gap in test coverage is exactly why this precedence bug went undetected.

### Impact Explanation
An unprivileged outside contributor can cause a `ReviewStack` to be created and queued for provisioning against a repository whose operator explicitly disabled review-stack provisioning (`review_stacks_enabled: false`), from a branch the attacker fully controls. Once provisioned, the stack's tasks run `shipit.yml` steps via `Command`/`PTY.spawn` from the attacker's `head.ref`, giving the attacker code execution on the deploy host — Critical severity (RCE via task execution using attacker-controlled repository content), and it is repeatable for any repository configured with `allow_with_label` or `prevent_with_label` plus `review_stacks_enabled: false`.

### Likelihood Explanation
Preconditions: the target repository must have `provisioning_behavior` set to `allow_with_label` (or `prevent_with_label`) with `review_stacks_enabled: false` — an operator configuration intended to fully disable review stacks while still tracking the label config, or leaving stale/misunderstood behavior settings. Attacker cost is trivial: open a PR from a fork and add/omit the configured label; no secrets, tokens, or elevated GitHub permissions are required beyond opening a PR and applying a label on their own PR. This is a straightforward, deterministic, repeatable bug (pure boolean logic error), not dependent on race conditions or timing.

### Recommendation
Fix operator precedence in `provision?` by explicitly grouping `review_stacks_enabled` across all clauses, e.g.:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Apply the same audit to `LabeledHandler`, `UnlabeledHandler`, and `ReopenedHandler`, which share similar logic per the grep results, to ensure `review_stacks_enabled` is enforced consistently everywhere provisioning decisions are made.

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` (extending the existing pattern), add:
```ruby
test "does not create stacks for allow_with_label when review_stacks_enabled is false" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :allow_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  # Binding under test: repository.review_stacks_enabled == false  vs.
  # actual provisioning decision, which should also be false.
  assert_equal false, repository.review_stacks_enabled
  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
With current code, `Stack.count` increases despite `review_stacks_enabled == false`, demonstrating the bug (test fails as written, proving the divergence exists).
