### Title
Webhook signature verification is bound to `repository.owner.login`/`organization.login` while every event handler acts on the independent, unverified `repository.full_name` field, letting an attacker who owns (or knows of) any zero-secret GitHub App forge events for a *different*, secured repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to verify the HMAC signature against using `repository_owner`, a value read straight out of the untrusted JSON body [1](#0-0) [2](#0-1) . `GitHubApp#verify_webhook_signature` returns `true` unconditionally whenever that organization has no `webhook_secret` configured [3](#0-2) , a supported/optional configuration explicitly shown in `docs/setup.md`/`config/secrets.development.shopify.yml` (`webhook_secret: # nil`). Once verification passes, every handler resolves the target `Repository`/`Stack` from a *separate* field of the same body, `payload.dig('repository', 'full_name')` [4](#0-3) , with no re-check that this repository belongs to the organization that was actually authenticated. This is exactly the "acted-upon field never covered by the verified binding" bug class from the report: the fee/shares mismatch there came from computing an amount against one state while the mutation used a different, later state; here the *authorization decision* is computed against `repository.owner.login`, while the *write* is performed against `repository.full_name`, an independent attacker-controlled field in the same payload.

### Finding Description
- `verify_signature` picks the app/secret with `Shipit.github(organization: repository_owner)` where `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` [5](#0-4) [2](#0-1) .
- If that organization's `webhook_secret` is blank/nil, `verify_webhook_signature` short-circuits to `true` for *any* signature/body combination [3](#0-2) .
- After verification passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the *entire, attacker-supplied* body to handlers [6](#0-5) .
- Every handler's `stacks`/`repository` lookup uses `payload.dig('repository', 'full_name')` exclusively - it never cross-checks it against `repository_owner` [4](#0-3) . `PushHandler`, for example, calls `stack.sync_github(expected_head_sha: params.after)` for every non-archived stack of the repository named by `full_name` [7](#0-6) , and the `status` event handler creates a `Shipit::Status` directly from payload fields (`sha`, `state`, `description`, `context`, `target_url`) as shown by the controller test asserting the created status mirrors the payload verbatim [8](#0-7) .
- Consequently, the organization whose credential authorized the request (`repository_owner`) and the repository whose state is mutated (`repository.full_name`) are two independent, attacker-controlled fields tied together by nothing but the attacker's own payload.

### Impact Explanation
An attacker who knows (from `docs/setup.md`'s own example config, or from probing) that at least one GitHub organization mounted on the instance has no `webhook_secret` set can send a completely unsigned/forged webhook whose `repository.owner.login` is that zero-secret org (satisfying `verify_signature`) but whose `repository.full_name` names a stack under a different, fully-secured organization. Handlers then act on that target stack using entirely attacker-controlled data: e.g. forging a `status` event that injects a fabricated "success" `Shipit::Status` on a commit that never passed CI, which can satisfy `ci.require` and enable an unauthorized deploy of unreviewed code, or forcing a `push`-triggered resync/continuous-deployment attempt against a repository the attacker has no access to. This crosses the report's required "unauthorized deploy" / "cross-repository writes" bar without any Shipit session, `ApiClient` token, or GitHub write access - only knowledge of the target engine's multi-org configuration.

### Likelihood Explanation
This requires no credentials at all against the target organization; it only requires that the engine's `Shipit.github` configuration contains at least one organization entry with a blank `webhook_secret` (an explicitly documented, supported configuration state), which is realistic for staging/dev GitHub Apps, low-risk internal orgs, or partially-configured multi-org deployments that legitimately proxy webhooks for several organizations through one Shipit instance. Given that `full_name`-based repository resolution is shared by essentially every handler (`Handler#repository_name`), the exploitable surface is broad once the zero-secret bypass condition is met.

### Recommendation
Bind the two values together instead of trusting the payload's `full_name` independently: after `verify_signature` succeeds, derive the acted-upon repository strictly from the same `repository_owner`/organization that was cryptographically verified (or, at minimum, assert `repository.owner.login == repository.full_name.split('/').first`) before any handler is allowed to look up or mutate a `Stack`/`Repository`. Additionally, disallow (or explicitly opt-in/whitelist) organizations configured with a blank `webhook_secret`, since `verify_webhook_signature` currently treats "no secret configured" as "always verified" rather than "reject".

### Proof of Concept
1. Instance configured with two GitHub orgs: `low-trust-org` (no `webhook_secret`, per the documented optional config) and `victim-org` (properly secured, has a Shipit stack `victim-org/protected-repo`).
2. Attacker POSTs to `/webhooks` with `X-Github-Event: status` and no valid `X-Hub-Signature`:
```json
{
  "repository": { "owner": { "login": "low-trust-org" }, "full_name": "victim-org/protected-repo" },
  "sha": "<victim commit sha pending in ci.require>",
  "state": "success",
  "context": "required-ci-check",
  "description": "forged",
  "target_url": "https://attacker.example"
}
```
3. `verify_signature` calls `Shipit.github(organization: 'low-trust-org')`; since that org's `webhook_secret` is nil, `verify_webhook_signature` returns `true` unconditionally [3](#0-2) .
4. The status-event handler resolves the target repo via `payload.dig('repository','full_name')` = `"victim-org/protected-repo"` [4](#0-3)  and creates/updates a `Shipit::Status` on the named commit using the forged `state`/`context`, matching the behavior demonstrated in the controller test [8](#0-7) .
5. If `victim-org/protected-repo`'s deploy spec lists `context` under `ci.require`, the forged "success" status satisfies the CI gate, enabling an unauthorized deploy of code that never actually passed CI - all without any credential tied to `victim-org`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
