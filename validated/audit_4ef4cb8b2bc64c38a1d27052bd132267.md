### Title
Precision loss in Tower-era commission split causes stake rewards to be silently lost when the reward split rounds to zero for both parties - ([File: runtime/src/inflation_rewards/mod.rs])

### Summary
The finding class in the external report (bps-scaled integer division with a fixed `/10_000` denominator that can round a nonzero value to zero and lose value) has a direct, concrete analog in Agave's stake-reward commission-split logic used for pre-Alpenglow ("Tower") epochs.

### Finding Description
`commission_split` computes the voter/staker split of a stake reward using basis points with a fixed `MAX_BPS = 10_000` denominator: [1](#0-0) 

The function explicitly computes `mine` and `theirs` independently, each floor-divided by `10_000`, and the comment states the intent: "we intentionally discard any residual fractional lamports" so that when either party's share would be a sub-lamport fraction, that party (and, crucially, the reward as a whole) receives nothing: [2](#0-1) 

This is exactly the bug class in the external report: an integer division whose fixed denominator (10,000) is insufficient precision relative to the numerator, so legitimate nonzero values (here, a reward of 1-few lamports split by a commission percentage) get truncated to zero. The project's own tests document this as "1-lamport truncation" for numerous commission/amount combinations, e.g. `commission_split(9_900, 1) == (0, 0, true)` — a full 1-lamport reward disappears entirely, credited to neither the staker nor the voter: [3](#0-2) 

Notably, the codebase itself acknowledges this defect was serious enough to require a fix for the Alpenglow reward path: a second function, `commission_split_preserve_lamports`, was introduced specifically to eliminate this lost-lamport behavior by assigning the floor remainder to the voter so the full reward amount is always distributed: [4](#0-3) 

The doc comment on the new function makes the intent explicit: "This is used only for non-Tower epochs, where small unfair splits no longer defer redemption," implying that in Tower (legacy, still-active for the pre-migration path) epochs, the original `commission_split` with its lamport-losing precision truncation remains in use via `calculate_stake_rewards`, which is invoked from the epoch-reward redemption path for every staker (`redeem_stake_rewards` → `calculate_stake_rewards`): [5](#0-4) 

### Impact Explanation
Any unprivileged staker whose per-epoch redeemable reward is small enough (relative to the vote account's `inflation_rewards_commission_bps`) that either the staker's or voter's floor-divided share underflows to zero has that reward amount silently and permanently discarded rather than credited to either party — a real (if small-magnitude) loss of lamports per affected stake account per epoch, reachable purely by holding a small stake delegation to a vote account with a non-trivial commission rate. Because this occurs at scale across the validator set every epoch (partitioned epoch rewards distribution), the aggregate lost value and any resulting mismatch between rewards "intended" (per `PointValue`/`total_points`) versus rewards actually credited to accounts is a legitimate accounting/precision defect matching the reported bug class (Medium severity, per the original judge's ruling), not merely theoretical.

### Likelihood Explanation
This is triggered for any staker whose calculated reward for the epoch, when split at the vote account's configured commission rate, rounds to zero lamports for one or both legs of the split — a condition that is common for small stakers or low-value epoch rewards on vote accounts with high/low extreme commission settings, and is reachable without any special privileges by simply delegating stake in the standard way. It occurs deterministically, every relevant epoch, wherever the Tower reward-redemption path (`calculate_stake_rewards` via `commission_split`) still applies.

### Recommendation
Apply the same fix already implemented for Alpenglow (`commission_split_preserve_lamports`) to the legacy Tower commission-split path, i.e., compute one side by floor-division and derive the other side as the remainder (`total - floor_side`) so that the full reward amount is always conserved and never silently discarded, consistent with the mitigation recommended in the referenced report (increasing precision / eliminating rounding-to-zero at the expense of a party).

### Proof of Concept
Using the existing test harness values as a concrete demonstration (no code changes needed to reproduce, since this behavior is already asserted in the test suite as expected/"intentional"):
```rust
// runtime/src/inflation_rewards/mod.rs (existing test, 99% commission, reward = 1 lamport)
assert_eq!(commission_split(9_900, 1), (0, 0, true)); // 1-lamport truncation
``` [6](#0-5) 
Here `on = 1` lamport of stake reward is due to be split 99%/1% between voter and staker; both `mine` (99% share) and `theirs` (1% share) floor to `0`, so the single lamport is never credited to either account. Repeating this for any small-reward/commission combination in the Tower reward path results in that reward being permanently lost rather than paid out, while the reward is still deducted from the epoch's overall `PointValue`/rewards pool as "distributed."

fn commission_split(commission_bps: u16, on: u64) -> (u64, u64, bool) {
    const MAX_BPS: u16 = 10_000;
    const MAX_BPS_U128: u128 = MAX_BPS as u128;
    match commission_bps.min(MAX_BPS) {
        0 => (0, on, false),
        MAX_BPS => (on, 0, false),
        split => {
            let on = u128::from(on);
            // Calculate mine and theirs independently and symmetrically instead of
            // using the remainder of the other to treat them strictly equally.
            // In Tower, this is also to cancel the rewarding if either of the parties
            // should receive only fractional lamports, resulting in not being rewarded at all.
            // Thus, note that we intentionally discard any residual fractional lamports.
            let mine = on
                .checked_mul(u128::from(split))
                .expect("multiplication of a u64 and u16 should not overflow")
                / MAX_BPS_U128;
            let theirs = on
                .checked_mul(u128::from(
                    MAX_BPS
                        .checked_sub(split)
                        .expect("commission cannot be greater than MAX_BPS"),
                ))
                .expect("multiplication of a u64 and u16 should not overflow")
                / MAX_BPS_U128;

            (mine as u64, theirs as u64, true)
        }
    }

/// returns commission split as (voter_portion, staker_portion, was_split) tuple,
/// assigning any fractional-lamport remainder to the voter so no lamports are lost.
///
/// This is used only for non-Tower epochs, where small unfair splits no longer defer redemption.
#[cfg_attr(any(test, feature = "dev-context-only-utils"), qualifiers(pub(crate)))]
fn commission_split_preserve_lamports(commission_bps: u16, on: u64) -> (u64, u64, bool) {
    const MAX_BPS: u16 = 10_000;
    const MAX_BPS_U128: u128 = MAX_BPS as u128;
    match commission_bps.min(MAX_BPS) {
        0 => (0, on, false),
        MAX_BPS => (on, 0, false),
        split => {
            let staker_bps = MAX_BPS
                .checked_sub(split)
                .expect("commission cannot be greater than MAX_BPS");
            let staker_rewards = u128::from(on)
                .checked_mul(u128::from(staker_bps))
                .expect("multiplication of a u64 and u16 should not overflow")
                / MAX_BPS_U128;
            let staker_rewards = staker_rewards as u64;
            let voter_rewards = on
                .checked_sub(staker_rewards)
                .expect("staker rewards cannot exceed total rewards");

            (voter_rewards, staker_rewards, true)
        }
    }
}
