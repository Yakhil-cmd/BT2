### Title
Coarse (filePath, category) dedup key in commit-review/Stop-hook findings lets a new dangerous vuln be suppressed as an "already-known" finding - (File: plugins/security-guidance/hooks/security_reminder_hook.py)

### Summary
`handle_commit_review_posttooluse` and `handle_stop_hook` both record and dedupe security findings keyed only on `(filePath, category)`, not on the actual vulnerable code/line [1](#0-0) . Because `_finding_keys` and `_record_fire` use this coarse key [2](#0-1) [3](#0-2) , once any finding of a given category has been recorded for a file, `previous_findings` treats that (file, category) slot as already "prompted" to the model, and `_dedup_against_state` only strips the race-delta between fresh state and what was prompted — it does not distinguish "same exact vuln recurring" from "a brand-new, unrelated vuln of the same category in the same file" [4](#0-3) .

### Finding Description
An attacker (via ordinary edits/commits reachable through normal workflow) can:
1. Introduce a trivial/minor vulnerability in `foo.py` classified as e.g. `SQLInjection`. This gets flagged once by `analyze_code_security`/agentic review and recorded into `previous_findings` keyed as `("foo.py", "SQLInjection")` by `_record_fire`/the commit-review analog [5](#0-4) .
2. In a subsequent commit (or amend, or push) within the `PREVIOUS_FINDINGS_TTL_SEC` window, introduce a genuinely new and more dangerous `SQLInjection` in the same file at a different location.
3. Because the LLM prompt is fed `previous_findings` and instructed to only re-flag `prompted` entries if "the attempted fix is incomplete" [6](#0-5) , and because the dedup key does not include `vulnerableCode`/line info, both the model's own re-flagging heuristic and the downstream `_dedup_against_state`/`_finding_keys` machinery treat the new, unrelated vulnerability as the "same" finding already communicated for that `(filePath, category)` pair.
4. This mechanism is shared across `handle_commit_review_posttooluse` (git commit, including the `--amend` delta-review path [7](#0-6) ), `handle_push_sweep_posttooluse` (push) [8](#0-7) , and `handle_stop_hook` [9](#0-8)  — meaning a single "burned" `(filePath, category)` key from an early low-severity finding can suppress rewake/warning for a later, more dangerous finding of the same category in the same file across retries, amends, and pushes, as long as it stays within the TTL and session state.

The `vulnerableCode` field is explicitly excluded from the key by design ("vulnerableCode bytes drift between fires... matching on it under-dedupes" [1](#0-0) ), which is a reasonable anti-flicker measure for legitimately re-flagged incomplete fixes, but it also means there is no code-content-based distinguishing signal between "same bug persisting" and "different bug, same category" — the LLM's own judgment is the only remaining safeguard, and that judgment is explicitly steered toward suppression by the `prev_section` prompt instruction.

### Impact Explanation
If the model (or the deterministic dedup layer) treats a new, distinct dangerous change as an already-reported finding, the commit/push/stop review pipeline will emit no warning and no `sys.exit(2)` rewake for that change, allowing dangerous code (e.g., a new injection, secret leak, or unsafe sink) to be committed, amended, and pushed without triggering the security-guidance review loop. This matches the stated Immunefi impact category of sensitive code/diff disclosure to an unintended sink going unreviewed and unblocked.

### Likelihood Explanation
This requires only ordinary repository activity within the unprivileged attacker model: normal edits and commits under the same file path and vulnerability category, within the `PREVIOUS_FINDINGS_TTL_SEC` window and same session state (or across commit-review/push-sweep/stop-hook boundaries that share the same `previous_findings` state). No credential leakage, admin access, or hook/config tampering is needed — it's an inherent property of the coarse dedup key combined with the LLM's re-flag suppression instruction. This makes it moderately likely to occur incidentally (e.g., iterative development touching the same file/category repeatedly) and trivially reproducible deliberately.

### Recommendation
Tighten the dedup/re-flag key to include a normalized signal beyond `(filePath, category)`, such as a stable hash of the affected line range or a normalized snippet fingerprint (robust to whitespace/diff-context drift but sensitive to logically distinct code), so that a new, non-overlapping instance of the same category in the same file is not conflated with a previously reported one. Alternatively, cap how long/how many times a `(filePath, category)` key can suppress rewake before forcing at least one confirmatory review pass regardless of the model's self-reported "fix incomplete" classification.

### Proof of Concept
Integration test plan for `handle_commit_review_posttooluse`/`handle_stop_hook`:
1. Seed session state with `previous_findings = [{"filePath": "app/db.py", "category": "SQLInjection", "vulnerableCode": "cursor.execute(f'... {user_id}')"}]` and a fresh `previous_findings_ts`.
2. Commit a diff to `app/db.py` introducing a distinct, unrelated SQL injection at a different function/line (e.g., string-concatenated query in a new endpoint handler), with no relation to the first finding.
3. Mock `analyze_code_security`/agentic review to return a vuln dict for the new line with the same `("app/db.py", "SQLInjection")` key (representative of realistic model behavior given the `prev_section` "only re-flag if fix incomplete" instruction).
4. Assert that `_dedup_against_state` and `_finding_keys` do not filter it (since it's in `prompted`), but separately assert/document that the LLM's own prompt-driven decision could omit it entirely from `vulns` in the first place — instrument `analyze_code_security` to record whether the new distinct finding was returned by the model at all when a same-category prior finding is present in `previous_findings`, versus when `previous_findings` is empty. Expected: the model/pipeline should flag the new distinct vulnerability with `sys.exit(2)` and a rewake in both cases; a regression is confirmed if the finding is only surfaced when `previous_findings` is empty.

```python
def _dedup_against_state(session_id: str, vulns: List[Dict[str, Any]],
                         prompted: set) -> Tuple[List[Dict[str, Any]], int]:
    """Drop vulns that a CONCURRENT asyncRewake hook wrote to
    previous_findings while this hook's LLM was running.

    `prompted` is the (filePath, category) set the LLM was already told about
    via the prev_section prompt block. The LLM is instructed to only re-flag
    those if the attempted fix is incomplete, so a re-flag of a `prompted`
    entry is an intentional "fix didn't work" verdict and MUST pass through.
    We therefore re-read state now and only filter the race delta —
    (seen_now − prompted) — i.e. findings the LLM was never told about
    because they were written mid-review by the other hook.
    Returns (surviving_vulns, n_dropped).
    """
    if not vulns:
        return vulns, 0
    fresh = with_locked_state(
        session_id, lambda s: list(s.get("previous_findings", []))
    ) or []
    race_delta = _finding_keys(fresh) - prompted
    kept = [v for v in vulns
            if (v.get("filePath", ""), v.get("category", "")) not in race_delta]
    return kept, len(vulns) - len(kept)
```
