### Title

Unvetted route contract can append arbitrary victim token transfers to a signed strategy authorization - (File: `contracts/swap-aggregator/src/execute/mod.rs`)

### Summary

XOXNO’s router executes attacker-controlled pool addresses embedded in `StrategyPayload`. Although the controller grants the router only one exact input-transfer authorization, Soroban simulation records any additional `sender.require_auth()`-gated token transfer performed by a route contract as another child of the user’s signed strategy invocation. If the user signs the simulated authorization tree without validating every child, a malicious route contract can transfer unrelated wallet tokens to an attacker while still returning enough output to satisfy the route.

### Finding Description

`Router::execute_strategy(sender, total_in, swap_xdr)` authenticates only `sender`, then decodes arbitrary `assets` and `ops` from `swap_xdr`. For each swap op, `execute_op` constructs `SwapHop` directly from payload-controlled `assets`; `idx_a` is the pool address, and no allowlist or code hash validates it. `dispatch_hop` then invokes the selected venue adapter against that address. [1](#0-0) [2](#0-1) 

The controller path narrows only the controller’s own grant: it authorizes one exact `token_in.transfer(controller, router, amount_in)` invocation and checks that the router did not spend more than that input. This bounds what the router may pull from the controller, but it does not prevent a subsequently invoked route contract from requesting a separate authorization from the original user. [3](#0-2) 

Soroban authorization makes the exploit conditional on the signed authorization tree. An honest tree containing only the expected controller/router invocation rejects the extra transfer, but simulation records the malicious token transfer as a child authorization. Signing that returned tree authorizes it. The repository’s regression test demonstrates a payload-selected `RogueHopPool` calling `token.transfer(alice, attacker, WALLET_BALANCE)`, simulation attaching that transfer to Alice’s `swap_collateral` authorization, and enforcement completing the theft when Alice signs the poisoned tree. [4](#0-3) [5](#0-4) [6](#0-5) 

### Impact Explanation

An unprivileged attacker can steal arbitrary tokens from a user’s wallet, including assets never supplied to or listed by the lending protocol. The attacker supplies a malicious route to a normal strategy entrypoint such as `swap_collateral(caller, account_id, collateral_asset, amount, debt_asset, swap_xdr)` or direct `Router::execute_strategy(sender, total_in, swap_xdr)`. The malicious hop returns enough output to satisfy route settlement while separately moving any wallet token named by the route contract.

The signed transaction still appears to perform the requested strategy. Consequently, route output checks, minimum output, and final account-risk checks do not bound the unrelated wallet transfer. This is theft of user funds, not merely poor execution quality: the stolen token and amount can be entirely outside the lending position.

### Likelihood Explanation

The attack is reachable by any user who can deploy or reference a contract address in a route and convince a victim to execute that route. It does not require protocol privileges, leaked keys, token noncompliance, or controller approval of the venue address. Its practical precondition is authorization-tree deception: the victim or their wallet/frontend must sign a simulated authorization containing the extra transfer child.

Simulation exposes the malicious child, so a wallet that displays and requires validation of every child invocation can prevent the exploit. That warning dependency reduces likelihood, but it does not remove the contract-level issue because `swap_xdr` explicitly permits arbitrary external pool addresses and the protocol relies on out-of-contract authorization inspection for safety.

### Recommendation

Constrain executable route pool addresses to a governance-approved venue/pool registry, or bind each venue adapter to authenticated pool metadata rather than trusting `assets[idx_a]` as arbitrary code. At minimum, reject route addresses that are not known-compatible with the selected `SwapVenue`.

Because the vulnerable surface is the authorization tree, clients should also enforce a strict authorization policy before signing:

- For controller strategies, accept only the expected controller root and the exact controller-to-router input transfer required by the strategy.
- For direct router swaps, accept only the `execute_strategy` root and exactly one `token_in.transfer(sender, router, total_in)` child.
- Reject any additional child invocation, especially token `transfer`, `transfer_from`, or `approve`, regardless of route profitability or simulated output.

### Proof of Concept

1. Attacker deploys a malicious contract implementing the ABI expected by a route adapter. Its swap function executes:

```rust
token::Client::new(&env, &victim_wallet_token)
    .transfer(&victim, &attacker, &victim_balance);
```

2. Attacker constructs a valid `StrategyPayload` whose swap instruction names the malicious contract in `assets[op.idx_a]`, a listed input token in `idx_b`, and a listed output token in `idx_c`.

3. Victim invokes a strategy such as `Controller::swap_collateral` with that `swap_xdr`.

4. The controller authorizes only `token_in.transfer(controller, router, amount_in)`, then calls `router.execute_strategy(controller, amount_in, swap_xdr)`. [7](#0-6) 

5. The router dispatches the payload-selected malicious pool. [8](#0-7) 

6. The malicious pool calls `wallet_token.transfer(victim, attacker, victim_balance)`. Simulation attaches this invocation as an additional child under the victim’s `swap_collateral` authorization.

7. If the victim signs the returned tree, the malicious transfer executes. The route can simultaneously pay a positive measured output, so `dispatch_hop` passes its measured input/output checks. [9](#0-8) 

The repository test `enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer` demonstrates the exact result: rejection with the honest empty-child tree, then successful transfer of `WALLET_BALANCE` to the attacker once the poisoned child is signed. [10](#0-9)
