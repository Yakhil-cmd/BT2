### Title
Webhook signature verified against `repository.owner.login`'s GitHub App while the event is applied to a different repository named by `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to use for HMAC verification based on the JSON field `repository.owner.login`, but every event `Handler` (base class `Handler#stacks`/`#repository_name`) determines which `Repository`/`Stack` to mutate using the independent JSON field `repository.full_name`. Because nothing binds these two attacker-controlled fields together, a webhook payload signed correctly for one configured GitHub organization can be crafted to act on a completely different tracked repository.

### Finding Description
`verify_signature` picks the app/secret to verify with, keyed off the *owner* field of the payload: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` resolves the GithubApp config purely by that organization key, and each organization can have its own (possibly blank) `webhook_secret`: [3](#0-2) 

`GithubApp#verify_webhook_signature` **trivially returns `true` when no `webhook_secret` is configured for that organization**: [4](#0-3) 

Meanwhile, every webhook `Handler` resolves the target `Repository`/`Stack` using a *different* JSON field, `repository.full_name`, with no cross-check against `repository.owner.login`: [5](#0-4) 

This is the same class of bug as the `dataCopy`/`RETURNDATACOPY` issue: verification is performed against one binding (owner→secret) while the effect is applied against a different, independently-attacker-controlled value (full_name→target repo/stack) taken from the *same* payload, with no equality enforced between them (`repository.owner.login == owner_of(repository.full_name)` is never checked).

The equality that should hold and is broken:
`organization whose secret authenticated the payload == organization that owns the repository the handler writes to`

Concretely, in a Shipit instance configured for multiple GitHub organizations (as documented and supported by `Shipit.github_organizations`/`github_app_config`), an attacker who can obtain a correctly signed delivery for *any one* of the configured organizations — including one whose `webhook_secret` is simply unset/blank (`return true unless webhook_secret`) — can set:
- `repository.owner.login` = the org whose secret they control/knows-is-blank
- `repository.full_name` = `victim-org/victim-repo` (a different, unrelated tracked repository)

`verify_signature` succeeds (verified against the attacker-controlled/blank-secret org), but `create` dispatches the event to handlers that resolve `stacks` via `full_name`, so the victim organization's stack is mutated.

### Impact Explanation
Depending on the event type dispatched this can:
- Force a `GithubSyncJob` / `sync_github` for an arbitrary tracked stack (`PushHandler`) [6](#0-5) 
- Inject a forged commit `Status` (e.g. a fake `success` CI status) for any commit sha in any tracked repository via `StatusHandler`, which can feed into deployability/merge-status checks used by the merge queue: [7](#0-6) 
- Archive/unarchive review stacks or manipulate PR-driven provisioning behavior for repos unrelated to the authenticating organization (`OpenedHandler`, `LabeledHandler`, `ClosedHandler`, etc.), all of which key off `params.repository.full_name` [8](#0-7) 

This breaks the intended per-organization webhook trust boundary and can influence deploy/merge-relevant state (fake commit statuses feeding merge gating) for repositories the forging organization has no legitimate relationship to, without requiring any Shipit session, `ApiClient` token, or GitHub App private key — satisfying the "escalation into authorization" / state-manipulation class of High-severity impact.

### Likelihood Explanation
Exploitability is conditioned on the deployment being configured for multiple GitHub organizations sharing one Shipit instance (a documented, supported configuration — see `config/secrets.development.example.yml` multi-org example) where at least one configured organization either has a blank/unset `webhook_secret`, or where the attacker legitimately controls webhook delivery for some low-value organization also tracked by the same Shipit instance. Given the "workaround" nature of secrets (`webhook_secret` is explicitly optional per `docs/setup.md`), this is a realistic operational configuration, but it does not apply to single-organization deployments where `github_default_organization` is `nil` and `repository_owner` doesn't select a different signing key.

### Recommendation
In `WebhooksController#verify_signature` (or in each `Handler`), enforce that the organization whose secret verified the signature matches the owner of `repository.full_name` used to resolve the target stacks — e.g., derive the target organization from the same `repository.owner.login`/`full_name` value used for verification, and reject the event if they disagree. Alternatively, always resolve the signing organization the same way the handler resolves the target repository (i.e., use `repository.full_name`'s owner segment for both signature verification and stack lookup) so a single JSON field cannot be forged independently from another.

### Proof of Concept
Given a Shipit instance configured with two organizations, `org-a` (webhook_secret unset/blank) and `org-b` (tracked stack `org-b/victim`):
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=<any value, or a validly computed HMAC using org-a's known/blank secret>

{
  "ref": "refs/heads/master",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/victim"
  }
}
```
`verify_signature` calls `Shipit.github(organization: "org-a")`, whose `verify_webhook_signature` returns `true` (blank secret) — bypassing verification. `WebhooksController#create` then dispatches to `PushHandler`, whose `Handler#stacks` resolves `Repository.from_github_repo_name("org-b/victim")`, triggering a forced sync (`sync_github`) on `org-b`'s stack despite the signature never having been verified against `org-b`'s secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
