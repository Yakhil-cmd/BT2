### Title
Cross-organization webhook signature confusion allows forged CI status/push events for stacks outside the authenticating organization - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
### Finding Description
`WebhooksController#verify_signature` selects the `GithubApp` (and thus the `webhook_secret` used for HMAC verification) based on `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` with a fallback to `params.dig('organization', 'login')`: [1](#0-0) [2](#0-1) 

However, once signature verification passes, the actual event handlers act on a *different* field of the same attacker-controlled JSON body. `Shipit::Webhooks::Handlers::Handler#repository_name` (the base class used by `PushHandler`, `CheckSuiteHandler`, etc.) resolves the target `Stack`/`Repository` from `payload.dig('repository', 'full_name')`: [3](#0-2) 

And `StatusHandler#process` doesn't scope by repository at all — it looks up commits globally by `sha`: [4](#0-3) 

This breaks the trust binding: **organization that authenticated (`repository.owner.login` / `organization.login`, used to pick the webhook secret) ≠ repository/stack that is actually written (`repository.full_name`, or nothing at all in `StatusHandler`)**.

In a multi-organization Shipit deployment (`config/secrets.yml` with one `GithubApp`/`webhook_secret` per organization, as documented), each onboarded organization's administrators know their own `webhook_secret` (they configure it on their own GitHub App installation): [5](#0-4) [6](#0-5) 

An attacker who administers "OrgA"'s GitHub App (and thus knows OrgA's `webhook_secret`) can POST directly to the shared `/webhooks` endpoint (no GitHub involvement required) with:
- `repository.owner.login` (or `organization.login`) = `"OrgA"` → passes `verify_webhook_signature` using OrgA's known secret,
- `repository.full_name` = `"VictimOrg/victim-repo"` → the actual target acted on by the handler,
- for the `status` event, an arbitrary `sha` belonging to any commit tracked anywhere in the Shipit instance, with `state: "success"`.

Because `verify_webhook_signature` only HMACs the raw body against the secret chosen from the *owner* field, and never cross-checks that `repository.full_name`'s owner matches the authenticated organization, the forged event is accepted and dispatched to handlers that operate on the victim's data.

### Impact Explanation
This is a cross-organization write with no legitimate authorization over the victim repository:
- Forged `push` events cause `PushHandler` to call `stack.sync_github(expected_head_sha: ...)` on stacks belonging to a completely different, unrelated organization, forcing unauthorized GitHub sync activity against victim stacks.
- Forged `status` events (`StatusHandler`) let the attacker mark **any commit sha in the entire Shipit instance** — not just their own org's — as `state: "success"`, fabricating CI green statuses via `Commit#create_status_from_github!`. Since commit/CI status is a gating input to merge-queue and continuous-delivery decision logic (`Stack#merge_status`, `Stack#deployment_checks_passed?`), an attacker who controls no more than their own org's webhook secret can inject fake successful CI status onto a victim organization's commit and influence whether that commit is treated as deployable/mergeable, i.e. cross-organization interference with deploy/merge state.

This matches "Critical - cross-repository writes / unauthorized deploy" since the write path (Stack sync, commit status) is fully cross-tenant and requires only knowledge of one organization's own webhook secret — never the victim's.

### Likelihood Explanation
Likelihood is high for any Shipit deployment onboarding multiple GitHub organizations (the documented multi-app configuration). Any organization administrator/team member who has legitimate access to configure their *own* org's GitHub App (and therefore knows their own `webhook_secret`) can exploit this with a single crafted HTTP POST — no GitHub interaction, no privileged Shipit session, and no access to the victim org is required.

### Recommendation
In `WebhooksController#verify_signature` and in `Shipit::Webhooks::Handlers::Handler`, enforce that the organization used to select/verify the webhook secret matches the owner of the repository the handler is about to act on (e.g., compare `repository.owner.login` against the owner portion of `repository.full_name`, and reject if they differ). Additionally, scope `StatusHandler#process` (and any other handler using global lookups like `Commit.where(sha:)`) to commits belonging to repositories owned by the authenticated organization, rather than performing an unscoped, instance-wide lookup by `sha`.

### Proof of Concept
1. Shipit is configured with two organizations, `OrgA` and `OrgB`, each with its own `GithubApp`/`webhook_secret` (per `docs/setup.md` "Using Multiple GitHub Applications").
2. Attacker administers `OrgA`'s GitHub App and therefore knows `OrgA`'s `webhook_secret`.
3. Attacker crafts a `status` webhook JSON body:
```json
{
  "repository": { "owner": { "login": "OrgA" } },
  "organization": { "login": "OrgA" },
  "sha": "<victim commit sha in OrgB's stack>",
  "state": "success"
}
```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>` and POSTs directly to `/webhooks` with header `X-Github-Event: status`.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and the signature validates successfully because the attacker used the correct secret for `OrgA`.
6. `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`, which runs `Commit.where(sha: params.sha)` — an unscoped, instance-wide lookup — and calls `commit.create_status_from_github!(params)` on the victim's commit belonging to `OrgB`, marking it as a successful CI status despite the attacker having no relationship to `OrgB`.
