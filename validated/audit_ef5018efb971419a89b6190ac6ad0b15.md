## Analog Found: `has_only()` character-class negation bypass in the oscript formula engine

### Title
oscript `has_only()` builds a raw regex character class from attacker-influenced input, allowing a `^` (or other regex metacharacters) to invert the intended whitelist check - (File: `formula/evaluation.js`)

### Summary
The reported CVE is a filter-bypass bug class: a special syntax construct (`{`a`b}`) is interpreted differently by the underlying SQL engine than by the pattern-matching filter that is supposed to block it, so a blocked operation slips through under an equivalent but unrecognized syntax. The closest reachable analog in ocore is the `has_only(str, charset)` oscript builtin, which is documented/used as a simple character-whitelist check but is implemented by splicing the caller-controlled `charset` argument directly into a live RegExp character class. Regex character classes have richer semantics (leading `^` negates the class, `-` creates ranges, `\` introduces escapes) than a "list of allowed characters," so any AA logic that treats `has_only()` as a safe allow-list gate over trigger-controlled data can have that gate inverted or widened by an attacker who influences the `charset` argument.

### Finding Description
`has_only` is evaluated in `exports.evaluate` in `formula/evaluation.js`: [1](#0-0) 

The code only defends against two things: an unescaped `]` that would close the class early, and a trailing `\`. It does nothing to prevent:
- a leading `^` in `sub`, which negates the entire character class (`[^...]` matches "anything except"), silently reversing the intended whitelist into a blacklist,
- `-` used to construct arbitrary ranges (e.g. widening an intended `0-9` class),
- multiple backslash-escape sequences (`\d`, `\s`, `\w`, `\p{...}` in some engines) that expand the effective character set far beyond a literal list.

This mirrors the CVE's root cause: a security-relevant check is implemented by delegating to a richer sub-language (SQL / RegExp) whose full grammar was not accounted for when the check was designed, so an input that looks like a constrained "list" is actually interpreted with the full expressive power of the underlying engine, defeating the intended restriction.

`formula/validation.js` does not add any restriction either — it only checks argument arity and activation MCI, and simply recurses into evaluating both operands: [2](#0-1) 

Both operands of `has_only` (the string being tested and the character class) can be arbitrary oscript expressions, including data derived from `trigger.data`, `params`, remote AA responses, or state variables that were themselves seeded by a previous trigger. Any AA that builds or forwards the "allowed characters" operand from data influenced by an unprivileged trigger sender inherits this bypass.

### Impact Explanation
`has_only()` is the oscript equivalent of an input-sanitization allow-list, intended for AAs to validate user-supplied strings (ticker symbols, addresses fragments, identifiers, etc.) before using them in further business logic (constructing asset names, gating payouts, building keys into state variables, etc.). Because the underlying implementation exposes full RegExp character-class semantics instead of a literal character list, an attacker who can influence the charset argument (directly, or through a chain of AA logic that forwards trigger data into it) can negate or broaden the intended check with a single `^` or `-`, causing the AA to accept data it was designed to reject. Depending on the AA's downstream logic this can lead to acceptance of malformed identifiers, corrupted state, or misdirected fund flows — i.e., AA fund loss or freezing, consistent with the impact categories in scope (this is a core-engine flaw reachable by any AA author/trigger sender, not an AA-specific typo).

### Likelihood Explanation
The flaw is 100% reachable by an unprivileged AA trigger sender: `has_only` is a documented, activated oscript builtin (gated only by `constants.aa2UpgradeMci`), evaluated identically for every node during consensus. No special privileges, network position, or node compromise are required — only a trigger unit that reaches an AA which uses `has_only` with an operand influenced by trigger/state data. Given `has_only` is explicitly documented as a "does the string contain only these characters" whitelist primitive, it is a foreseeable pattern for AA authors to pass through user-supplied allowed-character sets (e.g., configurable via AA params or previous triggers), making exploitation plausible in real AAs.

### Recommendation
Treat the `charset` argument as a literal set of characters rather than a raw regex fragment:
- Escape all regex metacharacters in `sub` (not just `]`) before constructing the `RegExp`, e.g. escape `^`, `-`, `\`, `[`, and any other characters with special meaning inside a character class, so `sub` is always interpreted as a literal set of characters.
- Alternatively, build the whitelist check without RegExp at all — e.g., split `sub` into a `Set` of literal characters and verify every character of `str` is a member of that set — eliminating character-class semantics entirely.
- Add validation-time tests to `formula/validation.js`/`formula/evaluation.js` covering `has_only` with a leading `^`, embedded `-` ranges, and combinations, to ensure the function's behavior matches the "literal character whitelist" contract implied by its name and documentation.

### Proof of Concept
1. An AA is written so that the "allowed characters" argument to `has_only` is derived (directly or indirectly) from trigger/state data, e.g.:
   ```
   $charset = trigger.data.charset; // intended to restrict e.g. to "a-z0-9"
   if (!has_only(trigger.data.name, $charset))
       bounce("invalid name");
   ```
2. A normal user sends `charset = "a-z0-9"`, restricting `name` to lowercase letters and digits, as intended by the AA author.
3. An attacker instead sends `charset = "^"` (or `"^abc"`), causing the evaluated expression to become `new RegExp("^[^" + "]*$")`/`new RegExp("^[^abc]*$")`, which now matches "any string not containing a/b/c" instead of enforcing the intended allow-list — reproducible directly against `formula/evaluation.js`'s `has_only` handler shown above with `sub = "^"` and any `str`.
4. Depending on how the AA uses the (bypassed) validation result downstream (e.g., to gate a payout condition, register an identifier, or build a state-variable key), this can be leveraged toward unintended AA state transitions or fund release that the whitelist was meant to prevent.
