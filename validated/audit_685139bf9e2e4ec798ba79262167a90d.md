### Title
Global `authorized?` team-membership check allows any authorized Shipit user to cancel merge requests on repositories/stacks they have no relation to - (File: app/controllers/shipit/merge_status_controller.rb)

### Summary
`MergeStatusController#dequeue` resolves `stack` solely from URL params (`params[:stack_id]` or owner/name/branch derived from the referrer) and then calls `merge_request.cancel!` with no per-repository authorization check. The only gate applied anywhere in the request lifecycle is `User#authorized?`, which is a global boolean membership test against `Shipit.github_teams`, independent of which repository/stack is being targeted.

### Finding Description
The claimed broken binding is: `authorized?(current_user, stack.repository)` (expected, per-repository check) vs. what is actually evaluated: `current_user.authorized?` (actual, global check), i.e. `authorized?(current_user, stack.repository) != current_user.authorized?` for any repository outside the attacker's team-configured scope.

Tracing the path: `force_github_authentication` in `app/controllers/concerns/shipit/authentication.rb` (lines 20-34) is the only authorization gate applied to every non-skipped action, and it calls `current_user.authorized?`, defined in `app/models/shipit/user.rb` lines 80-82:
```ruby
def authorized?
  @authorized ||= Shipit.github_teams.empty? || teams.where(id: Shipit.github_teams.map(&:id)).exists?
end
```
This has no repository/stack argument at all — it only checks if the user belongs to *any* team configured in `Shipit.github_teams`. It does not check whether the user's teams are associated with the specific repository/stack being acted upon.

`MergeStatusController` (app/controllers/shipit/merge_status_controller.rb) does not add any further authorization on top of this generic check. `dequeue` (lines 32-37) resolves `stack` (lines 62-81) purely from `params[:stack_id]` or `params[:referrer]`-derived owner/name, with no ownership/team check tying the requester to that specific stack's repository. It then executes:
```ruby
if (merge_request = stack.merge_requests.find_by_number(params[:number])) && merge_request.waiting?
  merge_request.cancel!
end
```
Any authenticated Shipit user who is a member of *some* team in `Shipit.github_teams` passes `force_github_authentication` and can call `dequeue` for a stack belonging to a repository unrelated to their team, cancelling another team's queued merge request.

This matches the description in the question precisely: the `authorized?` binding is evaluated as a global boolean, not scoped per-repository, and `dequeue` performs no additional per-stack ownership check before mutating `merge_request` state via `cancel!`.

### Impact Explanation
An authorized-but-unrelated Shipit user can send `DELETE /merge_status/other-org/other-repo/master/pull/42` (or via `stack_id`) and cause `merge_request.cancel!` to execute against a repository/stack outside their actual scope, mutating queue state (cancelling a queued PR) for a repository they have no legitimate relationship to. This is a cross-tenant state mutation: a request authenticated for one team's scope mutates a stack belonging to another team/repository. This matches the "Critical" impact category: *"a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge"* — cancelling a queued merge request is an unauthorized merge-queue mutation. The attack is trivially repeatable against any stack number known to the attacker (stack ids/branches are guessable/enumerable via public PR referrer URLs), across arbitrary repositories hosted by the same Shipit instance, as long as `Shipit.github_teams` is configured as a flat list rather than per-repository teams.

### Likelihood Explanation
Preconditions: the Shipit instance must have `Shipit.github_teams` configured (which is normal/default in multi-tenant setups per the code's github_teams empty-check), the attacker must have a valid Shipit session and be a member of at least one team in that global list, and there must exist a target stack/merge request for a different repository. Attacker cost is very low: only requires being a legitimate member of any configured Shipit team (i.e. any developer with access to any repository managed by that Shipit instance), no secrets or GitHub App credentials needed. This is fully repeatable and requires no race conditions or special timing — a simple authenticated DELETE request.

### Recommendation
Add a per-repository/stack authorization check in `MergeStatusController` (and any other controller that mutates state based on a `stack` resolved from params) — e.g., verify the current user's teams are associated with `stack.repository` before allowing `enqueue`/`dequeue` actions, rather than relying solely on the global `User#authorized?` boolean. Introduce something like `current_user.authorized_for?(stack.repository)` that checks team-to-repository association, and call it explicitly in `dequeue`/`enqueue` before permitting mutation.

### Proof of Concept
```ruby
# test/controllers/merge_status_controller_test.rb (new test)
test "dequeue cannot cancel a merge request belonging to another team's stack" do
  team_a = shipit_teams(:team_a) # configured in Shipit.github_teams
  team_b = shipit_teams(:team_b) # configured in Shipit.github_teams, unrelated repo
  attacker = shipit_users(:walrus) # member only of team_a
  attacker.teams << team_a

  other_stack = shipit_stacks(:shipit) # belongs to repo owned/associated with team_b only
  merge_request = other_stack.merge_requests.create!(number: 42, user: shipit_users(:codertocat))
  merge_request.update!(state: 'pending') # waiting?

  session[:user_id] = attacker.id

  assert_no_difference -> { merge_request.reload.state == 'pending' ? 1 : 0 } do
    delete :dequeue, params: { stack_id: other_stack.to_param, number: 42 }
  end

  merge_request.reload
  assert merge_request.waiting?, "merge_request should not have been cancelled by an unrelated team member"
end
```
This test authenticates as a user whose only team membership is `team_a` (unrelated to `other_stack`'s repository/team `team_b`), then issues the `dequeue` DELETE against `other_stack`'s merge request #42, and asserts that `cancel!` was not invoked (i.e., the merge request remains in `waiting?` state). Under current code, `current_user.authorized?` passes (attacker is a member of *some* `Shipit.github_teams` team), `force_github_authentication` allows the request through, and `dequeue` proceeds to cancel the merge request — the assertion fails, proving the vulnerability.
