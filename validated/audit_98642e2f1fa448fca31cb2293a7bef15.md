### Title
Weak `.strip()`-based text matching in `filter_preexisting_from_diff` lets a genuinely new malicious line be misclassified as pre-existing context, skipping LLM security review - ([File: plugins/security-guidance/hooks/gitutil.py])

### Summary
`filter_preexisting_from_diff` treats any added line whose `.strip()`ed text matches *any* removed line anywhere in the same file's diff (regardless of position) as "pre-existing," rewriting the `+` prefix to a space (context) prefix so it is excluded from what gets sent to the LLM reviewer. This match is purely textual and set-based, with no positional or file-identity correlation, so a newly-introduced malicious line can be laundered as unchanged content if its stripped text happens to equal any line that was removed elsewhere in the same diff.

### Finding Description
In `filter_preexisting_from_diff` [1](#0-0) , `removed_lines` is built as a `set()` of stripped `-` lines and `added_lines_set` as a `set()` of stripped `+` lines, with no tracking of hunk position or file region. The rewrite loop then converts any `+` line to a context line if its stripped content is `in removed_lines` [2](#0-1) . The code comment explicitly documents this exact weakness: "`.strip()` matches across indentation... and the set lets one removal mask N additions of the same stripped text" [3](#0-2) .

This is most exploitable in the full-file-rewrite case this function targets: when a Write tool rewrite deletes the entire old file and re-adds new content, `removed_lines` becomes essentially the full set of old-file lines (including common short/boilerplate lines like `}`, `pass`, `return`, or blank strings). An attacker (or a malicious contribution being reviewed) that introduces a new malicious line whose stripped text coincidentally — or deliberately, by choosing to phrase the payload identically to some other line already in the file — matches one of those removed lines will have that line silently converted to context and therefore excluded from genuinely-new content sent to the reviewer.

### Impact Explanation
This is a security-review-bypass in the `security-guidance` plugin's own enforcement path: content that should be flagged as newly-introduced (and therefore reviewed) is instead classified as pre-existing/unchanged, letting malicious new code slip past the LLM security reviewer. The comment acknowledges a backstop exists ("the diff-review prompt's previous-findings recheck"), but I was not able to fully trace or confirm within this investigation how (or whether) that recheck mechanism re-examines lines that were converted to context by this specific function, since the call sites in `security_reminder_hook.py` could not be fully inspected in the time available.

### Likelihood Explanation
Exploitability depends on the attacker being able to influence a diff/commit that this hook processes (e.g., a contributed PR/commit later reviewed via the `security-guidance` hook, or a full-file rewrite via the Write tool). The attacker does not need to control arbitrary "removed" content — it must actually exist as pre-existing text in the file — but for full-file rewrites the removed set spans the *entire* old file, making an accidental or deliberately-chosen collision (e.g., reusing a common short line, boilerplate, or duplicating text already in the file) plausible and repeatable.

### Recommendation
Make the pre-existing/new-line correlation positional and file-scoped rather than a global stripped-text set match: e.g., use a sequence-alignment/diff algorithm (like `difflib.SequenceMatcher`) between the full old-file and new-file line sequences to identify genuinely-unchanged regions, or at minimum require the match to consume one removed-line occurrence per added-line match (multiset instead of set) and only within the same hunk/local vicinity, so one incidental removed line cannot mask an unrelated new line elsewhere in the file.

### Proof of Concept
Unit test in `gitutil.py`'s test suite:
1. Construct a synthetic `diff_content` for a single file representing a full-file rewrite: include a removed line `-    pass` (from old boilerplate) and, elsewhere in the same diff, an unrelated newly-added line `+    exfiltrate(os.environ)` whose stripped text is crafted/coincides with another removed line's stripped text (e.g., both are `pass`, or duplicate the exact malicious line text under two different removed occurrences to demonstrate the "one removal masks N additions" case).
2. Call `filter_preexisting_from_diff([(file_path, diff_content)], cwd, baseline_sha)`.
3. Assert that the returned diff content still contains `+    exfiltrate(os.environ)` (or the equivalent malicious line) with the `+` prefix intact, and does NOT show it converted to a context line (`' '` prefix). A failing assertion (line converted to context) demonstrates the bypass.
