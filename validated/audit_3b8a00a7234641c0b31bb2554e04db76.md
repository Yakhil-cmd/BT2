The signature verification in `WebhooksController#verify_signature` authenticates the webhook using `Shipit.github(organization: repository_owner)`, where `repository_owner` is derived from `params.dig('repository', 'owner', 'login')` [1](#0-0) . That HMAC check only proves the request originated from *some* GitHub App installation registered under that organization's `webhook_secret` — it says nothing about which repository the event actually targets [2](#0-1) .

The handler dispatch, however, resolves the actual repository/stack to act on from a completely different, unverified field: `payload.dig('repository', 'full_name')` [3](#0-2) . `PushHandler#process` then loads stacks for that repository and calls `stack.sync_github` [4](#0-3) .### Title
Webhook signature is verified against `repository.owner.login`, but writes are dispatched using the independently-controlled `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to use for HMAC verification based on `params.dig('repository', 'owner', 'login')`, but the handler layer that actually resolves *which* `Repository`/`Stack` record to mutate uses a completely different payload field, `payload.dig('repository', 'full_name')`. Since both fields live inside the same attacker-supplied JSON body and the HMAC is computed by the attacker over their own chosen payload using their own legitimately-known secret, nothing binds "the organization whose secret authenticated this request" to "the repository the request is allowed to act on."

### Finding Description
`verify_signature` does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [5](#0-4) 

`verify_webhook_signature` only checks that the HMAC-SHA1 of the raw body matches the secret configured for that claimed organization [6](#0-5) . It does not verify that `repository.full_name` in the same payload actually belongs to that organization.

Downstream, `Handler#stacks` (used by `PushHandler` and other handlers) resolves the target using a *different* field:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [7](#0-6) 

`Repository.from_github_repo_name` splits `owner/name` straight out of that field and looks up any repository already registered in the Shipit instance, regardless of which organization authenticated the request: [8](#0-7) 

`PushHandler#process` then calls `stack.sync_github(expected_head_sha: params.after)` for every non-archived stack matching the target branch [4](#0-3) , which enqueues `GithubSyncJob`, writing new commits into that stack's commit history and — if `continuous_deployment` is enabled on that stack — can lead to an automatic deploy being triggered off the newly synced commits [9](#0-8) .

**Equality that should hold but doesn't:**
`organization authenticated by webhook signature (repository.owner.login)` == `organization/repository actually written to by the handler (repository.full_name)`.

Because Shipit is designed to be multi-tenant (multiple `github:` orgs each with their own `webhook_secret` in `config/secrets.yml`, see `config/secrets.development.shopify.yml` and `docs/setup.md`) [10](#0-9) , this means any organization onboarded onto a shared Shipit instance — who legitimately knows only their own `webhook_secret` — can forge a `push` payload where `repository.owner.login` is set to their own org (so the correct, known secret is used to pass HMAC verification) while `repository.full_name` is set to `victim-org/victim-repo`, a completely unrelated tenant's repository tracked by the same Shipit instance.

### Impact Explanation
This crosses the "an organization that authenticated versus the repository that is written" trust boundary explicitly called out as in-scope. An attacker who controls one tenant's webhook secret (an ordinary, unprivileged capability in a multi-org Shipit deployment — not a Shipit session, `ApiClient` token, or GitHub App private key) can force `GithubSyncJob` to run against another tenant's `Stack`, writing new commit records to that stack via `stack.commits.create_from_github!` and potentially auto-triggering a deploy through `continuous_deployment` — an unauthorized cross-repository/cross-tenant write and potential unauthorized deploy trigger.

### Likelihood Explanation
Requires only that the attacker administers (or has compromised) the webhook secret of *any* organization onboarded onto the same multi-tenant Shipit instance — a low-privilege capability relative to other tenants — and that they know or can guess the `owner/name` of a target repository already tracked by Shipit (repository names are not secret). No repository write access, GitHub App key, or Shipit session/API token is required.

### Recommendation
Bind repository resolution to the same organization identity that was cryptographically verified: after `verify_signature` succeeds, derive `repository_owner` once and require `payload.dig('repository', 'full_name')` (and `payload.dig('organization', 'login')`) to start with that same verified owner before resolving `Repository`/`Stack` records in `Handler#stacks`/`repository_name`. Reject or short-circuit the request (422) if the owner segment of `full_name` does not match the organization whose secret validated the signature.

### Proof of Concept
1. Shipit instance configured with two tenants: `attacker-org` (attacker knows/controls its `webhook_secret`) and `victim-org/victim-repo` (tracked stack with `continuous_deployment: true`).
2. Attacker crafts a `push` payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<any-sha-known-to-exist-upstream>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature` HMAC-SHA1 over the exact raw body using `attacker-org`'s known `webhook_secret`.
4. POSTs to `/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` looks up `Shipit.github(organization: 'attacker-org')` and successfully verifies the signature (attacker knows this secret) [2](#0-1) .
6. `PushHandler` resolves `repository_name` as `"victim-org/victim-repo"` [11](#0-10) , finds the real `victim-org/victim-repo` stack, and calls `stack.sync_github`, enqueuing `GithubSyncJob` against a repository the attacker's organization never authenticated for [4](#0-3) .

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
