### Title
Permissionless pool creation allows freeze-authority-controlled SPL token mints, enabling permanent freezing of LP funds — analogous to malicious ERC20 inclusion blocking rage-quit ([File: programs/cp-swap/src/instructions/initialize.rs])

### Summary
`initialize` (and `initialize_with_permission`) let *anyone* pair a pool with an arbitrary token mint, gated only by `is_supported_mint()`. That check whitelists any mint owned by the legacy SPL Token program unconditionally, without inspecting whether the mint has an active `freeze_authority`. Because `withdraw()` atomically transfers both `token_0` and `token_1` out of the pool vaults in a single instruction, a pool creator can seed a pool with a legacy-Token mint they control the freeze authority of, wait for LPs to deposit, then freeze the vault's token account for that mint — permanently blocking every LP's `withdraw()` call (and `swap`) for *both* sides of the pool, exactly mirroring the external report's pattern of a malicious party forcing an unwanted/weaponizable asset into a users' exit path with no opt-out.

### Finding Description
`is_supported_mint()` in `programs/cp-swap/src/utils/token.rs` returns `Ok(true)` immediately for any mint owned by the legacy `Token` program, with no inspection of the mint's `freeze_authority` field: [1](#0-0) 

For Token-2022 mints, the function only allow-lists a specific set of extensions (`TransferFeeConfig`, `MetadataPointer`, `TokenMetadata`, `InterestBearingConfig`, `ScaledUiAmount`) and rejects anything else, but this check is entirely skipped for legacy SPL Token mints: [2](#0-1) 

Both permissionless entry points call this same check and otherwise place no additional restriction on the mint's authority configuration before creating vaults and accepting deposits: [3](#0-2) [4](#0-3) 

`withdraw()` requires both transfers to succeed in the same transaction — there is no path for a user to withdraw only the "safe" side of the pool if the other token's vault account becomes frozen: [5](#0-4) 

No code anywhere in the program checks or rejects a non-null `freeze_authority` on the base SPL Token mint.

### Impact Explanation
A pool creator can retain the freeze authority on a plain SPL-Token mint used as `token_0_mint` or `token_1_mint`. Once other users deposit liquidity via `deposit`, the attacker calls the standard SPL Token `FreezeAccount` instruction against the pool's `token_0_vault`/`token_1_vault` token account. Because `withdraw()` transfers both tokens atomically, this permanently blocks `withdraw()` (and `swap_base_input`/`swap_base_output`, since those also transfer from the frozen vault) for all LPs in that pool — a permanent freeze of user/LP funds with no recovery path in the program. This is functionally identical to the reported issue: an attacker-controlled asset is forced into the fund-exit path, and once included there is no way for affected users to opt out or unwind.

### Likelihood Explanation
Pool creation is fully permissionless (`initialize`/`initialize_with_permission` can be called by any signer with attacker-chosen mint accounts), and creating an SPL-Token mint with a retained freeze authority is completely standard/default token behavior — no non-default runtime features or privileged access are required. The only precondition is that some LP deposits into the malicious pool, which is expected behavior for any newly listed pool.

### Recommendation
Reject mints (both legacy Token and Token-2022) whose `freeze_authority` is set (`COption::Some`) unless explicitly allowed, similar to how Token-2022 extensions are already allow-listed in `is_supported_mint()`. Alternatively, require that vault token accounts be verified as unfrozen before performing swap/withdraw transfers, or split `withdraw()` into independent per-token claims so a freeze on one side doesn't lock the other.

### Proof of Concept
1. Attacker creates a legacy SPL Token mint `M` and retains `freeze_authority = attacker`.
2. Attacker calls `initialize` (or `initialize_with_permission`) pairing `M` with a legitimate token `X`; `is_supported_mint` passes trivially for `M` per [6](#0-5) .
3. Victim LPs call `deposit`, funding both `token_0_vault` (or `token_1_vault`) holding `M` and the other vault holding `X`.
4. Attacker calls SPL Token `FreezeAccount` on the vault holding `M`.
5. Any victim's subsequent `withdraw` call reverts because the CPI transfer out of the frozen `M` vault fails inside `transfer_from_pool_vault_to_user`, per the atomic transfer sequence in [5](#0-4) , permanently locking both the `M` and `X` liquidity for all LPs in the pool.

pub fn is_supported_mint(
    mint_account: &InterfaceAccount<Mint>,
    mint_associated_is_initialized: bool,
) -> Result<bool> {
    let mint_info = mint_account.to_account_info();
    if *mint_info.owner == Token::id() {
        return Ok(true);
    }
    if mint_associated_is_initialized {
        return Ok(true);
