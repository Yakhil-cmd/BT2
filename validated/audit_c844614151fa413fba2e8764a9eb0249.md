## Analysis

This confirms the multi-organization GitHub App configuration model: `Shipit.github(organization:)` looks up a per-organization config (keyed by org name) from `secrets.github`, each with its own independent `webhook_secret` [1](#0-0) , and `GitHubApp#verify_webhook_signature` validates the `X-Hub-Signature` HMAC using *that org's* `webhook_secret` [2](#0-1) .

The `WebhooksController#verify_signature` selects which org's secret to verify against purely from attacker-controlled JSON in the body — `params.dig('repository', 'owner', 'login')`, falling back to `params.dig('organization', 'login')` [3](#0-2) . Once the signature check for that *claimed* org passes, `create` dispatches the entire raw payload to `Shipit::Webhooks.for_event(event)` handlers [4](#0-3) . Those handlers determine which repository/stack to act on independently, using `payload.dig('repository', 'full_name')` [5](#0-4)  — a *different* JSON field than the one used to select the verifying org/secret. `PushHandler`, all `PullRequest::*Handler`s, etc. all resolve the acted-upon repository this way [6](#0-5) [7](#0-6) .

Because `repository.owner.login` (binding used for authentication) and `repository.full_name` (binding used for the write target) are two independently-attacker-supplied fields inside the same signed body, an attacker who legitimately controls (and thus knows the `webhook_secret` for) **one** configured organization in a multi-tenant Shipit deployment can forge a payload that authenticates as their own org but names a *different* org/repo's stack as the target of `repository.full_name`. This breaks the equality: `organization that authenticated == organization/repository being written`.

### Title
Webhook Signature Verified Against `repository.owner.login`, But Handlers Act On A Different, Unverified `repository.full_name` — Cross-Organization Forgery ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/`webhook_secret` used to validate `X-Hub-Signature` based on `repository.owner.login` (or `organization.login`) taken directly from the unauthenticated request body. All webhook handlers, however, resolve the repository/stack they act on from a *different* body field, `repository.full_name`. In a multi-organization Shipit deployment, an attacker who owns/administers one configured organization (and thus knows that org's `webhook_secret`) can sign a payload as their own org while setting `repository.full_name` to point at a stack belonging to a different organization, causing Shipit to process the forged event against the victim org's stack.

### Finding Description
`Shipit.github(organization:)` supports one `webhook_secret` per organization, keyed in `secrets.github` [1](#0-0) . `verify_signature` computes `repository_owner` from the request body itself:

```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [8](#0-7) 

and uses it purely to pick which org's secret to HMAC-verify the whole raw body against:

```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [9](#0-8) 

Once verification succeeds for the *claimed* organization, the full JSON payload — including any fields not consulted during verification — is handed unchanged to the registered handlers via `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [4](#0-3) .

Handlers resolve the target repository from a separate field, `repository.full_name`, via the base `Handler#stacks`/`#repository_name` helpers:

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [5](#0-4) 

`PushHandler#process` then calls `stack.sync_github(expected_head_sha:)` on every matching stack for that `full_name`/branch [10](#0-9) , and other handlers (pull-request opened/labeled/reopened/edited/assigned) similarly locate a `Repository`/`Stack` purely from `repository.full_name` and mutate it (archive/unarchive review stacks, update pull-request records, etc.) [7](#0-6) [11](#0-10) .

Since `repository.owner.login` (authentication key selection) and `repository.full_name` (authorization target for the write) are two distinct, independently attacker-controlled strings inside the same HMAC-signed body, the signature never actually binds "the org whose secret produced this signature" to "the org/repo this event is permitted to act on." An org administrator who legitimately configured their own org's Shipit `webhook_secret` (an ordinary, non-privileged action from Shipit's perspective — they are not a Shipit admin, GitHub-team member, or `ApiClient` holder for the victim's stack) can compute a valid signature over a payload that sets `repository.owner.login` to their own org (so the signature check passes) but `repository.full_name` to a victim org's repository (so `PushHandler`, or a pull-request handler, mutates the victim's stack).

### Impact Explanation
This crosses the credential/repository boundary the engine relies on: a webhook signed by org A's secret is treated as authorization to run push-driven sync, pull-request-driven review-stack provisioning/archival, and other webhook-triggered side effects on org B's stack. This is a **cross-repository write via forged/misattributed webhook authentication** — pushing forged commit-sync events, or forging pull-request `opened`/`labeled`/`reopened` events to archive, unarchive, or provision review stacks belonging to a repository the attacker does not control. This matches the required High/Critical class of "cross-repository writes" via a broken authentication↔target binding.

### Likelihood Explanation
Medium: the precondition is a multi-tenant Shipit deployment with more than one organization's `webhook_secret` configured (i.e., `github_default_organization` non-nil and multiple keys in `secrets.github`) [12](#0-11) , and the attacker must control (or be the administrator of) at least one of those configured organizations so they can retrieve/know its `webhook_secret`. This is a realistic deployment pattern for the engine (per-org GitHub Apps are an explicitly supported config schema), but is not universal — single-organization deployments (the "backward compatibility"/no-org-key schema) are unaffected because there is only one secret to select.

### Recommendation
Do not use unauthenticated payload fields to select the verification key and then trust a *different* unauthenticated payload field for authorization. Either: (1) bind the webhook secret/signature check to the concrete `Repository`/`Stack` record the handler will act on (i.e., verify using the secret associated with `repository.full_name`, not `repository.owner.login`/`organization.login`), or (2) after signature verification, re-validate that `repository.owner.login` matches the owner implied by `repository.full_name` before dispatching to handlers, rejecting the request otherwise.

### Proof of Concept
1. Deploy Shipit configured with `secrets.github` containing two organizations, e.g. `org-a` (attacker-administered, webhook secret `S_A` known to attacker) and `org-b` (victim, contains a Shipit-tracked stack `org-b/victim-repo`).
2. Craft a GitHub `push` webhook body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(S_A, raw_body)>` using `S_A`, the secret the attacker legitimately knows for `org-a`.
4. POST to `/github/webhooks` with `X-Github-Event: push`. `verify_signature` computes `repository_owner = "org-a"`, fetches `org-a`'s `GitHubApp`, and successfully verifies the signature against `S_A` [9](#0-8) .
5. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, which resolves `repository_name` as `"org-b/victim-repo"` [13](#0-12)  and calls `stack.sync_github(expected_head_sha: params.after)` on the victim's stack [10](#0-9)  — despite the request never having been authenticated by anything belonging to `org-b`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
