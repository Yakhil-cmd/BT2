## Finding

The bug-class here is "verification/authorization computed against one binding, action performed against another" — same shape as the ERC4626 report's "amount deposited vs. shares actually received without a check tying the two together." In Shipit, the analogous binding is: **the stack an `ApiClient` token is scoped to** vs. **the stack a controller actually acts on**.

### Title
Stack-scoped `ApiClient` tokens bypass their stack restriction in `Api::CCMenuController` - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::BaseController` enforces per-token stack scoping by resolving the target stack through a `stacks` relation filtered to `current_api_client.stack_id` when the client is stack-scoped. `Api::CCMenuController` overrides the `stack` method and resolves the target stack directly from `Stack.from_param!(params[:stack_id])`, completely bypassing that scope filter. Any valid `ApiClient` token — even one intentionally created with `stack: <specific stack>` to limit exposure — grants read access to *any* stack's deploy state via this endpoint.

### Finding Description
`Api::BaseController#stack` intentionally binds the client's authorization to the stack being acted on: [1](#0-0) 

`stacks` restricts the queryable set to `current_api_client.stack_id` when the client is scoped: [2](#0-1) 

`Api::CCMenuController` overrides `stack` and resolves it directly from `Stack.from_param!(params[:stack_id])`, never consulting `current_api_client.stack_id`: [3](#0-2) 

The only authorization gate left is `require_permission :read, :stack`, which just checks the string `"read:stack"` is present in `current_api_client.permissions` — it never checks which stack the permission applies to: [4](#0-3) 

`ApiClient` explicitly supports per-stack scoping as a first-class model attribute (`belongs_to :stack, optional: true`), and this scoping is exercised in fixtures/tests (e.g. an api client scoped to one stack seeing only that stack via the index action): [5](#0-4) 

The binding that should hold is: `stack authorized by token == stack acted on by controller`. Before the request, a stack-scoped token (`stack_id = A`) is only supposed to satisfy `stacks == {A}` per `BaseController#stacks`. After hitting `CCMenuController#show` with `stack_id=B` in the URL, the controller resolves and returns deploy state for stack `B`, even though the token was never authorized for `B`. `CCMenuController` even authenticates via a raw `token` query-string param instead of Basic Auth, making these tokens easy to pass around/leak in URLs (they're literally emailed/shared as CCMenu URLs by `CCMenuUrlController`): [6](#0-5) [7](#0-6) 

### Impact Explanation
This is an unauthorized cross-stack read of stack/deploy state: a token meant to be limited to one stack (e.g., shared with a monitoring tool, or a third party, scoped via the `ApiClient` UI to a single stack) can be replayed with a different `stack_id` to read the deploy/build status (`lastBuildStatus`, `lastBuildLabel`, lock state, etc.) of every other stack in the Shipit instance. This matches the High-impact category of unauthorized read of stack state/deploy output, since the least-privilege boundary the product exposes (`ApiClient#stack`) is silently ignored by this one endpoint.

### Likelihood Explanation
No special privilege beyond possessing any valid `ApiClient` token with `read:stack` permission is required — this is exactly the kind of token that is deliberately generated with narrow, single-stack scope via `CCMenuUrlController`/`ApiClientsController` for limited-purpose integrations (CI dashboards, status widgets). The only additional step is substituting a different `stack_id` in the request path, which is trivial and requires no authentication bypass, signature forgery, or GitHub credentials.

### Recommendation
Remove `CCMenuController`'s private `stack` override, or reimplement it using the same scope-aware `stacks` lookup as `BaseController` (i.e., `stacks.from_param!(params[:stack_id])`) so that stack-scoped `ApiClient` tokens cannot be used to read state of stacks outside their `stack_id`.

### Proof of Concept
1. As a Shipit user, generate a CCMenu/API token scoped to Stack A only (e.g. via the "Fetch URL" button on Stack A's settings page, which calls `CCMenuUrlController#client` to create an `ApiClient` with `stack: A`, `permissions: ['read:stack']`).
2. Take the resulting token and issue a request to `GET /api/stacks/<owner>/<repo-B>/<env-B>/ccmenu?token=<token>` for an unrelated Stack B that the token was never scoped to.
3. Observe `Api::CCMenuController#show` returns HTTP 200 with Stack B's deploy/build status/lock state, because `stack` resolves via `Stack.from_param!(params[:stack_id])` [8](#0-7)  instead of the scope-checked `stacks` relation used elsewhere in `BaseController` [1](#0-0) .
