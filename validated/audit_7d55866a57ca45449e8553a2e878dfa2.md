### Title
Cross-tenant `Status` injection via sha-only lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits purely `Commit.where(sha: params.sha)` with no filter tying the match to the repository named in the verified webhook payload, then calls `commit.create_status_from_github!(params)` for every match across all stacks. Unlike other handlers in this codebase, it never uses `Handler#stacks` (which scopes lookups via `Repository.from_github_repo_name(repository_name)`), so a webhook validly signed for the attacker's own GitHub App/organization can write a `Status` row onto any commit in any tenant's stack that happens to share the same sha.

### Finding Description
The binding that should hold is: `payload.dig('repository', 'full_name') == commit.stack.github_repo_name` for every `Commit` a status gets attached to. This is enforced by the base class helper `Handler#stacks`, which restricts lookups to `Repository.from_github_repo_name(repository_name)&.stacks` [1](#0-0) . `StatusHandler#process`, however, bypasses this helper entirely and queries `Commit` globally by `sha` alone:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 

`Commit#create_status_from_github!` then calls `statuses.replicate_from_github!(stack_id, github_status)`, which is `find_or_create_by!(stack_id:, state:, description:, target_url:, context:, created_at:)` on the matched commit's own `stack_id` [3](#0-2) [4](#0-3) . Nowhere in this chain is `payload['repository']['full_name']` compared against the matched commit's `stack.github_repo_name`.

Webhook signature verification (`WebhooksController#verify_signature`) only checks that the payload is validly signed for the GitHub App/organization derived from `repository_owner` in the payload itself [5](#0-4) . This proves the payload was sent by whoever controls the named `repository_owner`/app secret — i.e., the attacker, for their own repo. It does nothing to constrain which `Commit` rows get matched inside the handler, since `StatusHandler` never reads `repository_name` at all.

Attack: attacker pushes/creates a commit in their own public repo whose content hash equals a sha that already exists in a victim's Shipit-tracked stack (e.g., an empty-tree commit, or any commit whose sha coincidentally/intentionally collides via content reuse — Shipit stores raw `sha` strings with no repository-scoped uniqueness constraint enforced at the `Commit.where(sha:)` lookup). Attacker then triggers (or directly POSTs) a `status` webhook for their own repo/sha with `state: success`, signed with their own app credentials. `StatusHandler.call` matches by sha only and writes a `success` `Status` onto the victim's `Commit`, changing `Commit#status`/`deployable?` and potentially triggering deploys via `schedule_continuous_delivery`.

### Impact Explanation
A `Status` row is created on a victim stack's `Commit` without the victim's repository ever emitting that webhook, satisfying "a payload for one repository mutating another's stack, commit, task or team" (Critical). Since `add_status` (invoked from `create_status_from_github!`) can flip `deployable?` to true and calls `stack.schedule_merges` / triggers `ContinuousDeliveryJob` when `new_status.success?` [6](#0-5) [7](#0-6) , this can lead to an unauthorized deploy on the victim stack if continuous deployment is enabled. This is repeatable against any tenant/stack that shares a sha with an attacker-controlled repo, and severity scales with how many Shipit-managed stacks reuse common shas (e.g., empty commits, cherry-picks, shared vendor commits).

### Likelihood Explanation
Preconditions: (1) attacker needs a GitHub App/webhook credential valid for at least one repo they control (trivial — any public repo they own, assuming Shipit's GitHub App model allows registering arbitrary orgs/repos, or a shared/global `webhook_secret` per docs); (2) a `Commit` row with the target sha must already exist in the victim's stack (achievable deterministically via known-constant-sha commits like an empty tree, or opportunistically for any sha the attacker learns from a victim's public commit history — Shipit does not require repos to be private). No Shipit session, API token, or GitHub token is required. Given the ease of engineering colliding shas (empty commits are literally identical across all repos) this is low-cost and fully repeatable.

### Recommendation
In `StatusHandler#process`, scope commit lookup through `stacks` (as other handlers do) instead of a global `Commit.where(sha:)`, e.g. `stacks.flat_map(&:commits).select { |c| c.sha == params.sha }` or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, ensuring `payload.dig('repository','full_name')` is resolved to a `Repository`/`Stack` before any `Commit` is touched.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, out of scope to write but described for the background engineer):
1. Create two `Repository`/`Stack` fixtures: `victim_repo` (`github_repo_name: "victim/repo"`) with `victim_stack`, and `attacker_repo` (`github_repo_name: "attacker/repo"`) with `attacker_stack`.
2. Create `victim_commit = Commit.create!(stack: victim_stack, sha: "same_sha_1234...")` with no statuses (`success?` false).
3. Build a `status` webhook payload with `repository.full_name = "attacker/repo"`, `sha: "same_sha_1234..."`, `state: "success"`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly (bypassing signature verification, since that's not the layer under test).
5. Assert `victim_commit.reload.statuses.count == 1` and `victim_commit.status.success?` is true — i.e., the victim's commit state changed even though the payload only ever named `attacker/repo`.
6. Contrast with a fixed implementation using `stacks`-scoped lookup, where the same payload should leave `victim_commit.statuses` empty because `attacker/repo` resolves to `attacker_stack`, not `victim_stack`.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
