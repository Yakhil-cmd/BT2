### Title
Cross-repository `Status` write via unscoped SHA lookup in `StatusHandler#process` allows forged CI status to satisfy `MergeRequest#all_status_checks_passed?` on a different Stack - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits purely by `sha`, with no verification that the sha belongs to the repository that emitted the webhook (unlike `Handler#stacks`, which scopes by `repository_name`). If a `Commit` row with the same SHA exists in a different Stack (e.g. a fork sharing history with the victim repo, or a coincidentally colliding sha across two tracked stacks), a validly-signed status webhook from repository A writes a `Status` onto the commit in Stack B, potentially matching a pending `MergeRequest`'s head there.

### Finding Description
The broken binding: `webhook_payload['repository']['full_name']` (verified via `verify_signature`/`Shipit.github(organization: repository_owner)`) is expected to equal the `repository` of the `Commit`/`Stack` that receives the write, but the code never enforces `commit.stack.repository == webhook_repository`.

```ruby
# app/models/shipit/webhooks/handlers/status_handler.rb
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

`Commit` is `belongs_to :stack` without any global sha uniqueness constraint [2](#0-1) , so multiple stacks can have `Commit` records sharing the same `sha` (this is the normal case for forks, since a fork inherits identical commit SHAs for shared history). Every other handler in this engine scopes work to the sending repository via `Handler#stacks`, which does `Repository.from_github_repo_name(repository_name)&.stacks` [3](#0-2) , but `StatusHandler` bypasses this entirely and queries `Commit` globally.

`create_status_from_github!` then creates a `Status` scoped to `commit.stack_id` (the victim's stack, not the attacker's), and if the resulting state is `pending` or `success`, schedules `ProcessMergeRequestsJob` for the victim's stack: `stack.schedule_merges if new_status.pending? || new_status.success?` inside `add_status` [4](#0-3) .

`ProcessMergeRequestsJob#perform` then calls `merge_request.refresh!` and `merge_request.all_status_checks_passed?` [5](#0-4) . Critically, `refresh!` calls `head.refresh_statuses!`, which re-fetches real statuses from GitHub via `stack.github_api.statuses(...)` and merges them in via `find_or_create_by!` [6](#0-5) . This does **not delete** the previously forged `Status` row - it only adds/reuses records. `all_status_checks_passed?` evaluates `StatusChecker.new(head, head.statuses_and_check_runs, stack.cached_deploy_spec).success?` [7](#0-6) , which is a `Status::Group` whose `select_significant_status` considers ALL contexts present, keyed by `context`, deduplicated by `uniq(&:context)` [8](#0-7) . If the attacker sets the forged status's `context` to match a `required_statuses` context configured in the victim's `shipit.yml` (`deploy_spec.merge_request_required_statuses`), the forged `success` status for that context can satisfy the requirement even if the real CI for that context on GitHub never ran or is still pending, because `uniq(&:context)` takes the **first** matching status per context (order dependent on `has_many :statuses, -> { order(created_at: :desc) }`), and a stale/forged success status can outrank a still-pending real one depending on creation-time ordering.

Existing guards fail here specifically because: `verify_signature` only checks that the payload came from a repository whose org secret matches — it says nothing about which Stack/Commit the payload is allowed to touch [9](#0-8) ; `drop_unhandled_event` and the `ExplicitParameters` schema only validate shape, not repository binding [10](#0-9) ; and the `stacks`/`repository_name` scoping helper that every other handler uses is simply not invoked by `StatusHandler`.

### Impact Explanation
An attacker who controls (or can push commits/status to) any GitHub repository tracked by the same Shipit instance can write a `Status` record into an unrelated victim Stack's commit, as long as a `Commit` row with a colliding SHA exists there (most realistically via a fork sharing history with the victim repo, or a shared template/monorepo initial commit). This is a payload-for-one-repository-mutating-another's-commit/stack primitive, and downstream it can contribute to bypassing CI-gating on `merge_queue_enabled` stacks, since the forged `Status` is not purged by `refresh!`. This matches the "payload for one repository mutating another's stack/commit... or an unauthorized merge" Critical impact category. Blast radius is scoped to Shipit instances/orgs where multiple stacks/forks share commit history, and is repeatable for every SHA collision the attacker can arrange.

### Likelihood Explanation
Requires: (1) the attacker's own repository is tracked by a Shipit instance (or otherwise able to produce a validly signed `status` webhook), (2) an unrelated victim stack that has a `Commit` row with the exact same SHA (achievable trivially by forking the victim repo, since forks share all pre-fork commit SHAs, or by any two stacks mirroring the same upstream), and (3) the victim stack has `merge_queue_enabled: true` with a pending `MergeRequest` whose `head` is that shared commit. Fully forging an arbitrary victim PR head SHA that isn't already shared history would require a SHA1 preimage/collision, which is not practically feasible; the realistic exploit surface is limited to shared-history commits (old/common commits, not the PR's unique head commit created for that PR). This constrains likelihood: the scenario described in the question (forging a completely independent, PR-specific head SHA) requires a SHA collision and is not practically achievable, but the underlying missing-repository-scoping bug in `StatusHandler#process` is real and independently exploitable for shared-history commits.

### Recommendation
Scope `StatusHandler#process` to the sending repository, mirroring `Handler#stacks`:
```ruby
def process
  stacks.flat_map(&:commits).where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
or equivalently join through `Commit.joins(:stack).merge(stacks).where(sha: params.sha)`, so a webhook can only ever create a `Status` for commits belonging to a stack whose `Repository` matches the payload's `repository.full_name`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual)
test "status webhook does not write a Status against a commit belonging to a different repository's stack" do
  victim_stack = shipit_stacks(:shipit)          # repo shopify/shipit
  attacker_stack = shipit_stacks(:cyclimse)      # repo attacker/cyclimse, different repository

  shared_sha = 'deadbeef' * 5
  victim_commit = victim_stack.commits.create!(sha: shared_sha, ...)
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, ...)

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'ci/travis',
    'repository' => { 'full_name' => attacker_stack.repository.full_name }
  }

  assert_no_difference -> { victim_commit.statuses.count } do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end
end
```
Both sides of the binding to assert: `payload['repository']['full_name']` (attacker's repo) must equal `victim_commit.stack.repository.full_name` for a write to be permitted; currently they diverge and the write still succeeds against `victim_commit`, which the fixed code must reject.
