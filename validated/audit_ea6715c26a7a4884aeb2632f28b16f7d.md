### Title
Webhook signature verification binds to `repository.owner.login`, but every event handler dispatches on `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/organization (and thus the HMAC secret used to check `X-Hub-Signature`) using `repository_owner`, taken from the attacker-controlled JSON body (`params.dig('repository','owner','login')`), while every `Shipit::Webhooks::Handlers::Handler` subclass resolves the target `Stack` using `repository_name` (`payload.dig('repository','full_name')`) from that same body. These two fields are never cross-checked, so a validly-signed payload for organization A can carry a `repository.full_name` pointing at organization B's repository.

### Finding Description
`verify_signature` in [1](#0-0)  does:

```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```

where `repository_owner` is read directly from the unauthenticated payload: [2](#0-1) . `verify_webhook_signature` only proves that the raw body was HMAC-signed with the secret belonging to whichever organization name the attacker put in `repository.owner.login` — it says nothing about the rest of the payload's content: [3](#0-2) .

Once verification passes, `WebhooksController#create` hands the entire parsed JSON to every registered handler: [4](#0-3) . Every handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, pull-request handlers, etc.) resolves the `Stack`(s) to act on via `Handler#stacks`, which looks up `Repository.from_github_repo_name(repository_name)`, and `repository_name` is `payload.dig('repository', 'full_name')` — a completely different JSON key than the one used for signature-organization selection: [5](#0-4) .

`PushHandler`, for example, uses this to trigger `stack.sync_github` on any stack matching the forged `full_name`/`branch`: [6](#0-5) .

**The broken binding, expressed as an equality that the code fails to enforce:**
`organization whose secret authenticated the request` (`repository.owner.login`) **must equal** `organization implied by repository.full_name` (the repo whose Stack rows get written). The controller enforces neither this equality nor that `repository.owner.login` is even a prefix of `repository.full_name`.

Before the attacker's request: signature validity is (correctly) scoped to org A only.
After the attacker's request: an org-A-signed payload writes/mutates Stack state belonging to org B, because the write path never re-derives the owner from the same field that was signature-checked.

### Impact Explanation
Any entity that legitimately controls (or has obtained) the webhook secret for one organization/installation registered on a shared Shipit instance (multi-tenant deployments serving several GitHub orgs from one Shipit app are explicitly supported via `Shipit.github(organization:)`) can forge webhook events — pushes, commit statuses, check-suite results, pull_request events, membership events — that are dispatched against a *different* organization's stacks/repositories. Concretely:

- `StatusHandler`/`CheckSuiteHandler` can inject fabricated green CI statuses onto commits belonging to a victim org's Stack, defeating the `ci.require` gating documented in the README (`ci.require` blocks deploys unless required contexts are green): [7](#0-6) . This directly enables an **unauthorized deploy** of a commit that never actually passed the victim's real CI, which falls under the Critical-impact category ("an unauthorized deploy") in scope.
- `PushHandler` can force `sync_github`/branch resolution on an arbitrary victim stack.
- `pull_request` handlers can manipulate merge-queue/label state on a victim's stack.

This is a cross-repository write triggered purely by possessing a webhook secret for an unrelated organization — i.e., the exact "organization authenticated versus the repository that is written" boundary the task calls out.

### Likelihood Explanation
The only prerequisite is possession of a valid webhook secret for *any one* organization/installation configured on the Shipit instance (a routine, low-privilege credential compared to write access on the victim repo) plus knowledge that the instance is shared with other orgs. No repository write access, no Shipit session, and no victim-org secret are required — the attacker only forges the payload body and signs it with their own org's secret. This is a straightforward, deterministic exploit requiring no timing races or race conditions.

### Recommendation
In `WebhooksController#verify_signature`/`#create`, derive both the verifying organization and the acted-upon repository from the *same* payload field (e.g., always require `repository.full_name` to start with `repository.owner.login/`), and reject the request (422) if `repository.owner.login` does not match the owner segment of `repository.full_name` used later by `Handler#repository_name`. Alternatively, have `Handler#stacks` re-verify that the resolved `Repository`'s owner equals the `repository_owner` that was used to select the signing secret, rejecting/no-op'ing the event otherwise.

### Proof of Concept
1. Attacker controls (or is the admin of) organization `attacker-org`, which has a GitHub App/webhook installed on the shared Shipit instance with webhook secret `S_attacker`.
2. Attacker crafts a raw JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(S_attacker, raw_body)>` and sends it with `X-Github-Event: push` (or `status`) to `/webhooks`.
4. `verify_signature` calls `Shipit.github(organization: 'attacker-org')` and successfully verifies the signature against `S_attacker` [1](#0-0) .
5. `create` dispatches to `PushHandler`, whose `stacks` resolves via `Repository.from_github_repo_name('victim-org/victim-repo')` [5](#0-4) , triggering `sync_github` (or, with the `status` event, writing a forged commit `Status`) on the victim org's Stack — despite the request having been authenticated solely with the attacker's own org's secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
