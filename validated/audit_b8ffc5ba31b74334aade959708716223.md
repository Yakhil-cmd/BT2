### Title
`status` webhook writes commit statuses without repository scoping, allowing cross-repository `release/gate` status forgery - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits purely `Commit.where(sha: params.sha)` with no repository/stack filter, unlike the base `Handler` class which provides a `stacks` helper scoped to `repository_name` from the payload. Any webhook whose signature verifies for the *sender's* repository/org can therefore mutate the status of a commit belonging to a completely different stack, as long as the SHAs collide (git commit hashes are content-derived and identical commits pushed to a fork/mirror produce identical SHAs to the upstream commit already ingested into a victim stack).

### Finding Description
The broken binding is: **the repository that authenticated the webhook signature MUST equal the repository/stack that owns the `Commit` row being mutated.** In `WebhooksController#verify_signature`, signature validation is keyed by `repository_owner` (`app/controllers/shipit/webhooks_controller.rb:24-30`, `:59-62`), i.e., it proves "this payload came from GitHub for org/repo X" — it says nothing about which `Commit`/`Stack` row may be touched.

`Handler` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) exposes a `stacks` helper that filters by `Repository.from_github_repo_name(repository_name)`, and most handlers (pull_request, push, etc.) use this to scope their writes to the repository that sent the event. `StatusHandler`, however, does not:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

`Commit.sha` is not enforced unique per repository at the DB/model layer that the handler consults — it queries across the whole `commits` table regardless of `stack_id`/`repository`. [2](#0-1) 

Exploit flow: attacker owns/controls a repository (or fork) for which they can generate a legitimately GitHub-signed `status` webhook (e.g., by installing/triggering GitHub's status API on their own repo — signature verification only checks that the payload's `repository.owner.login` matches an org Shipit knows, not that the SHA belongs to that repo). They craft/replicate a commit whose SHA is identical to a commit already present in a victim's Shipit stack (trivial via git's content-addressed hashing — pushing the same tree/parents/author/message/timestamps to their own repo yields the same SHA as the corresponding upstream commit). They then send a `status` event with `context: release/gate`, `state: success` for that SHA. `StatusHandler` finds the victim's `Commit` row purely by SHA match and calls `commit.create_status_from_github!(params)`, flipping `release/gate` to success for the victim stack/commit — with the described `review_stacks_enabled true, allow_all` configuration, this directly affects deployability/merge/gate logic (`Commit#deployable?`, `blocked?`, `stack.schedule_merges`). [3](#0-2) [4](#0-3) 

None of the existing guards prevent this: `verify_signature` only authenticates sender identity/org, not target repository ownership of the commit being written; `drop_unhandled_event` only checks event type registration; `ExplicitParameters` schema only validates payload shape, not repo scoping; there is no `require_permission!`/`stacks`-scope check inside `StatusHandler#process` at all.

### Impact Explanation
A payload authenticated for one repository can mutate a `Commit`/`Status` record — and therefore deploy-gating decisions — belonging to a different, unrelated stack, matching the Critical category "a payload for one repository mutating another's stack, commit, task or team" and potentially "an unauthorized deploy... or merge." This is repeatable against any victim stack/commit whose SHA the attacker can reproduce, and the blast radius spans all stacks/tenants sharing the Shipit instance, since the lookup is global (`Commit.where(sha:)` with no stack/repo filter).

### Likelihood Explanation
Preconditions: the attacker needs a repository capable of emitting a validly-signed `status` webhook to the shared Shipit instance (feasible if the GitHub App/webhook secret validation is org-scoped but attacker controls any onboarded repo/org, or if they can otherwise get GitHub to sign a status event for a repo they own that shares Shipit's webhook secret configuration), and a colliding SHA with a commit already present in the victim's Shipit `commits` table (achievable since commit hashes are content-derived and identical commits/forks naturally share SHAs). The victim stack must require `release/gate` and be configured `review_stacks_enabled: true, allow_all: true` for the flip to translate into ship/block behavior. This requires no privileged Shipit role, session, or API token — only the ability to trigger a webhook, matching the "unprivileged attacker" threat model.

### Recommendation
Scope `StatusHandler#process` to the repository that sent the webhook, mirroring other handlers' use of the `stacks`/`repository_name` helper — e.g., resolve `commit_stacks = stacks` (from `Repository.from_github_repo_name(repository_name)`) and restrict the query to `Commit.where(sha: params.sha, stack: commit_stacks)` (or scope through `stack.commits.find_by(sha: ...)`), so a status can only ever affect commits belonging to the authenticated repository's own stacks.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, illustrative):
1. Create `stack_a` for repository `owner/repo-a` and `stack_b` for repository `owner/repo-b`, both requiring `release/gate`; configure `stack_b` with `review_stacks_enabled: true, allow_all: true`.
2. Create `commit_b` under `stack_b` with a known `sha` (e.g. `"deadbeef..."`), and assert `commit_b.deployable?` is `false` (missing `release/gate`).
3. Build a `status` webhook payload whose `repository.full_name == "owner/repo-a"` (i.e., authenticated for stack A) but `sha == commit_b.sha`, `context: "release/gate"`, `state: "success"`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)`.
5. Assert-both-sides-of-binding: before, `commit_b.stack.github_repo_name != payload_repository_name`; after processing, assert `commit_b.reload.deployable?` changed to `true` (or `status.success?` is `true`) — proving a payload authenticated for repo A mutated stack B's commit despite the repository names never matching.
