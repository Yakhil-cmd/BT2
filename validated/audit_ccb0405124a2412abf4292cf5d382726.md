### Title
Division-by-Zero Panic in `consolidatedNode.Split()` Crashes Proposer Node During Block Finalization When Both CN and CL Staking Amounts Round to Zero — (`kaiax/staking/staking_info.go`)

---

### Summary

`consolidatedNode.Split()` divides by `totalAmount = cnAmountBig + clAmountBig` without a zero guard. When a block proposer has a non-nil `CLStakingInfo` but both its AddressBook staking amount and its CL pool staking amount are below 1 KAIA (rounding to zero after the `/params.KAIA` truncation applied in `parseCallResult`/`parsePermissionlessCallResult`), `totalAmount` is zero and `big.Int.Div` panics. This panic propagates through `FinalizeState` → `GetDeferredReward` → `specWithProposerAndFunds` / `specWithProposerAndFundsFlex`, crashing the proposer node and preventing block production for that round.

---

### Finding Description

`consolidatedNode.Split()` computes the CN/CL reward split proportionally:

```go
// kaiax/staking/staking_info.go:169-187
func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
    if c.CLStakingInfo == nil {
        return amount, big.NewInt(0)
    }
    var (
        cnAmountBig = big.NewInt(int64(c.StakingAmount))
        clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
        totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
    )
    clAmount := new(big.Int).Mul(clAmountBig, amount)
    clAmount = clAmount.Div(clAmount, totalAmount)   // ← panics if totalAmount == 0
    cnAmount := big.NewInt(0).Sub(amount, clAmount)
    return cnAmount, clAmount
}
``` [1](#0-0) 

Both `c.StakingAmount` and `c.CLStakingInfo.CLStakingAmount` are `uint64` values in KAIA, produced by integer division of the raw wei amount by `params.KAIA` (1 × 10¹⁸):

```go
// kaiax/staking/impl/getter.go:287,299
stakingAmounts[i] = big.NewInt(0).Div(a, big.NewInt(params.KAIA)).Uint64()
// ...
CLStakingAmount: big.NewInt(0).Div(clRes.StakingAmounts[i], big.NewInt(params.KAIA)).Uint64(),
``` [2](#0-1) 

Any raw balance strictly less than 1 KAIA (< 10¹⁸ wei) truncates to zero. If both the AddressBook staking contract balance and the CL pool balance are below 1 KAIA, `totalAmount == 0` and `big.Int.Div` panics.

`Split` is called from two reward-finalization paths **without any guard on the staking amounts**:

**Path A — Kore (post-Kore, pre-Osaka/Flex):**
```go
// kaiax/reward/impl/getter.go:628-637
if cn.CLStakingInfo == nil {
    break
}
cnAmount, clAmount := cn.Split(proposer)   // ← no zero-check
``` [3](#0-2) 

**Path B — Flex (post-Osaka, UseFlexReward):**
```go
// kaiax/reward/impl/getter.go:578-587
if cn.CLStakingInfo == nil {
    break
}
cnAmount, clAmount := cn.Split(proposer)   // ← no zero-check
``` [4](#0-3) 

Both paths are guarded by `config.Rules.IsPrague && si.CLStakingInfos != nil` (line 567/617), so they are only reached post-Prague when CL staking data is present. [5](#0-4) 

By contrast, the staker-reward paths (`assignStakingRewards`, `assignStakingRewardsFlex`) are safe: they only call `Split` when `cnTotalStakingAmount > minStake` or `excessInt > 0`, which guarantees `totalAmount > 0`. [6](#0-5) 

The panic propagates through:

---

### Impact Explanation

`FinalizeState` is called on every block by the proposer node during block production. A panic there crashes the proposer's goroutine (no `recover()` in the call chain), taking down the node process. The block is never broadcast; a round-change occurs and the next proposer takes over. If the affected node is the governing node (unconditionally qualified in `single` governance mode), it is repeatedly selected as proposer and repeatedly crashes until its staking state changes. This constitutes a persistent denial-of-service against a specific validator node and disrupts reward distribution for affected rounds.

---

### Likelihood Explanation

The trigger requires all three conditions simultaneously post-Prague:

1. **Validator registered in CLRegistry** (`CLStakingInfo != nil`) — any validator can self-register.
2. **AddressBook staking contract balance < 1 KAIA** — possible if the validator withdrew most stake or never deposited a full KAIA unit; the integer truncation `Div(balance, 1e18)` silently produces zero.
3. **CL pool balance < 1 KAIA** — same truncation applies to the CL pool balance.

In WeightedRandom policy, a validator with zero staking is normally demoted. However, the governing node is **unconditionally qualified** regardless of staking amount (per the valset README), making it a realistic trigger: the governing node could withdraw its AddressBook stake, register a CL pool with a dust amount, and then be selected as proposer.



---

### Recommendation

Add a zero-denominator guard in `consolidatedNode.Split()`:

```go
func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
    if c.CLStakingInfo == nil {
        return amount, big.NewInt(0)
    }
    cnAmountBig := big.NewInt(int64(c.StakingAmount))
    clAmountBig := big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
    totalAmount := new(big.Int).Add(cnAmountBig, clAmountBig)
    if totalAmount.Sign() == 0 {
        // Both staking amounts are zero; assign all reward to CN.
        return amount, big.NewInt(0)
    }
    clAmount := new(big.Int).Div(new(big.Int).Mul(clAmountBig, amount), totalAmount)
    return new(big.Int).Sub(amount, clAmount), clAmount
}
```

Additionally, consider filtering out zero-total-staking entries in `parseCallResult` and `parsePermissionlessCallResult` before they reach `CLStakingInfos`, or enforcing a minimum CL staking amount in the CLRegistry contract.

---

### Proof of Concept

1. Deploy a Kaia network with Prague hardfork enabled and `istanbul.policy == 2` (WeightedRandom).
2. Register validator `V` in the AddressBook with a staking contract holding 0.5 KAIA (< 1 KAIA → `StakingAmount = 0`).
3. Register `V`'s node ID in the CLRegistry with a CL pool holding 0.3 KAIA (< 1 KAIA → `CLStakingAmount = 0`).
4. Set `V` as the governing node (unconditionally qualified despite zero staking).
5. Wait for `V` to be selected as proposer.
6. Observe `FinalizeState` panic: `runtime error: integer divide by zero` inside `consolidatedNode.Split` at `kaiax/staking/staking_info.go:181`, crashing the node. [8](#0-7)
