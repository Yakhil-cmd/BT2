### Title
Push-Pattern KLAY Delivery in `handleKLAYTransfer` Permanently Locks Bridged KLAY When Recipient Reverts — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

---

### Summary

`handleKLAYTransfer` in `BridgeTransferKLAY.sol` uses a push pattern to deliver KLAY to the recipient (`_to`). If `_to` is a contract whose fallback reverts, the `require(ok, ...)` guard causes the entire transaction to revert, rolling back all nonce-state mutations. Because no state is ever committed for that nonce, operators can never advance past it, and the user's bridged KLAY is permanently locked in the source-chain bridge contract.

The identical structural flaw exists in `handleERC20Transfer` (`BridgeTransferERC20.sol`): `safeTransfer` to a blacklisted address (e.g., USDC) reverts the whole transaction for the same reason.

---

### Finding Description

`handleKLAYTransfer` executes in this order:

1. `_lowerHandleNonceCheck` — validates nonce is ≥ `lowerHandleNonce`
2. `_voteValueTransfer` — sets `closedValueTransferVotes[N] = true`
3. `_setHandledRequestTxHash` — sets `handledRequestTx[txHash] = true`
4. `handleNoncesToBlockNums[N] = _requestedBlockNumber`
5. `_updateHandleNonce` — advances `lowerHandleNonce`, `upperHandleNonce`, `recoveryBlockNumber`
6. `emit HandleValueTransfer`
7. `(bool ok, ) = _to.call.value(_value)("")` — **push KLAY to recipient**
8. `require(ok, "handleKLAYTransfer: transfer failed")` — **reverts entire tx if push fails** [1](#0-0) 

When step 7 fails, step 8 reverts the transaction. Solidity's revert semantics undo **all** state changes from steps 2–5:

- `closedValueTransferVotes[N]` → reset to `false`
- `handledRequestTx[txHash]` → reset to `false`
- `handleNoncesToBlockNums[N]` → reset to `0`
- `lowerHandleNonce` / `upperHandleNonce` / `recoveryBlockNumber` → unchanged

`_updateHandleNonce` advances `lowerHandleNonce` only while `handleNoncesToBlockNums[i] > 0` for consecutive `i`: [2](#0-1) 

Because `handleNoncesToBlockNums[N]` is never durably set to a non-zero value, `lowerHandleNonce` can never advance past nonce N. The nonce is permanently stuck.

The same pattern in `handleERC20Transfer` applies when `safeTransfer` reverts (e.g., USDC blacklist on `_to`): [3](#0-2) 

---

### Impact Explanation

- **Unauthorized asset lock / permanent loss of bridged KLAY**: The user already emitted `RequestValueTransfer` on the source chain; their KLAY is locked in (or burned from) the source-chain bridge. The destination bridge can never deliver it because every `handleKLAYTransfer` call for nonce N reverts.
- **`lowerHandleNonce` permanently stuck**: Because `handleNoncesToBlockNums[N]` is never committed, the nonce-advancement loop halts at N. `recoveryBlockNumber` is frozen at the block before N, causing the off-chain recovery service to replay the same events indefinitely.
- **Scope**: Matches "Unauthorized transfer … affecting KAIA, bridged assets, or system-managed funds" and "Persistent corruption of … state … that breaks … withdrawals, transfers, or settlement."

---

### Likelihood Explanation

The trigger is **unprivileged**: any user can call `requestKLAYTransfer` on the source chain and supply a contract address as `_to` whose fallback reverts on the destination chain. No special role, key, or majority-validator collusion is required. The attacker only needs to deploy a one-line reverting contract on the destination chain and use it as the transfer recipient.

---

### Recommendation

Adopt the pull-payment (claim) pattern for KLAY delivery:

1. On a failed push, record `pendingWithdrawals[_to] += _value` instead of reverting.
2. Expose a `claimKLAY()` function that lets `_to` pull their KLAY.
3. Commit all nonce-state mutations regardless of delivery success, so `lowerHandleNonce` always advances.

Alternatively, use a try/catch pattern (available in Solidity ≥ 0.6) around the low-level call and emit a `TransferFailed` event without reverting, so operators can mark the nonce handled and the recipient can claim later.

### Proof of Concept

```
// Destination chain: deploy this contract as _to
contract RevertingReceiver {
    fallback() external payable { revert("blocked"); }
}

// Source chain (attacker):
// 1. Deploy RevertingReceiver on destination chain → address R
// 2. Call bridge.requestKLAYTransfer{value: 1 ether}(R, 1 ether, "")
//    → emits RequestValueTransfer(nonce=N), KLAY locked in source bridge

// Destination chain (operators):
// 3. Operator calls handleKLAYTransfer(txHash, from, R, 1e18, N, blkNum, "")
//    → Steps 2-5 execute (state mutated)
//    → _to.call.value(1e18)("") → RevertingReceiver.fallback() reverts
//    → require(ok) reverts entire tx
//    → All state from steps 2-5 rolled back
//    → handleNoncesToBlockNums[N] == 0 forever
//    → lowerHandleNonce stuck at N
//    → User's 1 KLAY permanently locked in source bridge
```
