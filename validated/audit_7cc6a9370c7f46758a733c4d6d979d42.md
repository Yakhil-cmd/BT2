Found the binding break: the webhook's HMAC signature is verified using the organization derived from `repository.owner.login`, but the repository state that is actually mutated is selected using `repository.full_name` — a separate, unsigned-relationship field that is never cross-checked against the verifying organization.

### Title
Webhook signature verified against `repository.owner.login`'s secret while state-mutating actions are keyed on the independent, unvalidated `repository.full_name` field - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to verify the HMAC signature against using `repository_owner`, derived from `params.dig('repository', 'owner', 'login')` (or `organization.login`) [1](#0-0) . Once the signature check passes for that organization, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches to handlers that locate the target `Repository`/`Stack` using `payload.dig('repository', 'full_name')` [2](#0-1) . These are two independently attacker-suppliable JSON fields in the same request body; nothing ties the "owner" field used for signature-org selection to the "full_name" field used to select the repository actually written to.

### Finding Description
The signature check itself (`verify_webhook_signature`) is a correct HMAC-SHA1 comparison over the *entire* raw body using the secret configured for `Shipit.github(organization: repository_owner)` [3](#0-2) . Because the whole raw payload is signed, an attacker without the correct secret cannot forge an arbitrary body for that organization — this is the same protection GitHub webhooks always provide.

The design flaw is architectural rather than cryptographic: this multi-tenant engine authenticates a webhook payload against exactly one organization's secret (the one that owns `repository.owner.login`), then hands the *entire, already-verified* payload to handlers that key their side effects off a *different* field, `repository.full_name`, via `Repository.from_github_repo_name(repository_name)` [2](#0-1) . `push_handler.rb` uses this to call `stack.sync_github(expected_head_sha: params.after)` on every non-archived stack matching the branch [4](#0-3) , and the pull_request/status/check_suite handlers use the same `stacks` scoping for other Stack model mutations.

For any Shipit deployment configured with more than one `Shipit.github(organization: ...)` entry (the `secrets_double_github_app.yml` fixture in this repo demonstrates this is an explicitly supported configuration) [5](#0-4) , a party who legitimately controls (and thus can sign webhooks for) OrgA's repositories can submit a payload where `repository.owner.login` = "OrgA" (satisfies signature verification against OrgA's secret) but `repository.full_name` = "OrgB/some-repo" (used by every handler to locate the `Stack` to mutate). The equality the engine implicitly assumes — *organization that authenticated the request* == *repository whose Stack state gets written* — is never enforced anywhere in the code path from `verify_signature` through `Handler#stacks`.

### Impact Explanation
This lets an entity that is a legitimate, unprivileged GitHub webhook sender for one organization's repositories (no Shipit session, no `ApiClient` token, no `api_clients_secret`, no GitHub App private key, and no repository *write* access to the target org needed — only ordinary push/webhook-trigger events from a repo they control) inject state changes into a `Stack` belonging to a completely different organization/repository configured in the same Shipit instance: forcing `sync_github` on an unrelated stack, or driving `PullRequest`/`Commit`/`MergeRequest` state transitions for a repository never authenticated by the request. This is a cross-repository/cross-tenant write achieved purely by exploiting the disconnect between the field validated for authentication and the field acted upon for mutation — matching the reported bug class of "validated on one value, acted upon a different, uncorrelated value."

### Likelihood Explanation
Any GitHub organization can trivially craft a payload with mismatched `repository.owner.login` and `repository.full_name` values, since GitHub's webhook payloads are simply forwarded as-is and Shipit performs no cross-field consistency check. The only precondition is that the attacking party already has a legitimately signed channel to Shipit for *some* organization (i.e., they operate their own repository already connected to this Shipit instance) — this is expected, ordinary usage of a multi-tenant Shipit install, not a privileged administrative capability.

### Recommendation
After selecting the signing organization from the payload, verify that `repository.full_name`'s owner matches `repository_owner` (the same field used for signature verification) before dispatching to handlers, or better, derive the organization used for verification strictly from the same `repository.full_name` value that handlers use to resolve the `Stack`, so a single field drives both authentication and mutation.

### Proof of Concept
1. Shipit is configured with two GitHub App entries, `OrgA` and `OrgB`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker controls a repository under `OrgA` and receives real webhook deliveries from GitHub for it, so they know/can produce a validly-signed body for `OrgA`.
3. Attacker crafts (or has GitHub deliver, then modifies before... no — signature covers full body, so instead they construct their own POST) a `push` event JSON body where:
   - `repository.owner.login = "OrgA"`
   - `repository.full_name = "OrgB/target-repo"`
   - `ref = "refs/heads/main"`, `after = "<arbitrary sha>"`
4. Compute `X-Hub-Signature: sha1=HMAC_SHA1(OrgA_webhook_secret, body)` and POST to `/webhooks`.
5. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "OrgA")` and verifies successfully [6](#0-5) .
6. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("OrgB/target-repo")` [2](#0-1)  and calls `stack.sync_github(expected_head_sha: params.after)` on OrgB's stack [4](#0-3) , even though the request was authenticated only for OrgA.

Note: I was unable to fully trace `Stack#sync_github` and the downstream `GithubSyncJob` implementation within the available index (partial results only showed test references), so the exact severity of the resulting `Stack` state mutation (e.g., whether it can trigger an actual deploy vs. just commit-sync bookkeeping) could not be fully confirmed from the indexed code; a full Devin session with complete repository access would be needed to verify the precise downstream consequences of `sync_github` and whether they rise to an unauthorized deploy.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
