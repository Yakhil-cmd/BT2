## Finding

The ALPINE-CVE-2024-12243 bug class is "an inefficient (super-linear) parsing/validation algorithm that lets an attacker craft input causing pathological CPU consumption in a single-threaded process." The closest analog I could locate in `ocore--014` is a catastrophic-backtracking regular expression in the validation helper library.

### Title
Catastrophic backtracking (ReDoS) in `isValidEmail` regex used for wallet-reachable input - (File: `validation_utils.js`)

### Summary
`isValidEmail` in `validation_utils.js` uses a regex with nested unbounded quantifiers in the local-part group, a well-known ReDoS-prone pattern. [1](#0-0) 

### Finding Description
The regex `^(([^<>()\[\]\\.,;:\s@"]+(\.[^<>()\[\]\\.,;:\s@"]+)*)|(".+"))@...` contains the classic vulnerable shape `X+(\.X+)*` immediately followed by a literal `@` that is expected but can be absent in attacker input. For strings consisting of many repeated non-`@`, non-`.` characters with no trailing `@`, the regex engine explores an exponential number of ways to partition the string among the repeated groups before failing, causing the single JS event-loop thread to hang — directly analogous to the libtasn1 inefficient-algorithm DoS in the reported CVE (attacker-controlled, algorithmically-crafted input triggers super-linear/exponential processing time in a parsing/validation routine). [1](#0-0) 

`isValidEmail` is referenced from `wallet.js` (3 call sites) and `uri.js` (1 call site), i.e. it sits in wallet/contract-message-handling code paths rather than pure UI code. [2](#0-1) 

### Impact Explanation
Because ocore's unit/joint/device-message validation runs on a single Node.js event loop, a multi-second-to-unbounded regex hang triggered by a crafted "email" string received through a wallet/device-message flow (e.g., textcoin-style flows or any wallet message field that is passed through `isValidEmail`) would block that process from processing any other network activity, including validating and confirming newly received units — matching the "network unable to confirm new units" acceptance criterion, at least for the affected node/hub process.

### Likelihood Explanation
I was not able to fully confirm, within the available tool budget, the exact call sites in `wallet.js`/`uri.js` that feed externally-supplied (attacker-controlled) strings into `isValidEmail` without prior sanitation/length limits, nor whether a length cap upstream neutralizes the exponential blow-up (short strings do not trigger meaningful backtracking delay). This is the main open uncertainty and would need direct inspection of the `wallet.js`/`uri.js` call sites to confirm reachability from an unprivileged peer/counterparty with an unbounded-length string.

### Recommendation
Replace the vulnerable email regex with a non-backtracking validator (e.g., a linear-time hand-written scanner, or a regex without nested quantifiers over the same character class), and/or enforce a strict maximum length on any string passed to `isValidEmail` before matching.

### Proof of Concept
A string such as `"a".repeat(40) + "!"` (40+ repeated non-`@` characters with no `@`/`.` present, causing the `([^<>()\[\]\\.,;:\s@"]+(\.[^<>()\[\]\\.,;:\s@"]+)*)` alternative to backtrack) passed to `isValidEmail` will cause matching time to grow exponentially with input length, hanging the process for inputs of a few dozen to a few hundred characters — this must still be confirmed against the actual call sites in `wallet.js`/`uri.js` to verify no length limit is applied beforehand.

---
**Caveat:** Due to tool-call limits in this session, I was unable to read the specific `wallet.js`/`uri.js` lines that invoke `isValidEmail` to confirm the exact reachable trigger and whether an upstream length cap exists. This finding should be treated as a candidate requiring confirmation of the exact call-site context before being treated as fully validated.
