Confirmed root cause: the webhook signature is verified against the secret of the organization named in `repository.owner.login` (or `organization.login`), but the repository actually acted upon is looked up from `repository.full_name`, a separate, independently-attacker-controlled field in the same unverified JSON body.

### Title
Webhook signature verified against attacker-chosen `repository.owner.login`, not the `repository.full_name` actually acted upon - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` derives which GitHub App/organization secret to check the `X-Hub-Signature` against from `params.dig('repository','owner','login')` (falling back to `params.dig('organization','login')`), then hands the *entire unmodified raw body* to the event handlers, which independently resolve the target `Stack`/`Repository` from `params.dig('repository','full_name')`.

### Finding Description
In `app/controllers/shipit/webhooks_controller.rb`: [1](#0-0) 
`verify_signature` picks the GitHub App config via `Shipit.github(organization: repository_owner)`, where `repository_owner` reads `params.dig('repository', 'owner', 'login')`. That same untrusted JSON body is then dispatched unchanged to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` in `create`.

Handlers such as `PushHandler` resolve the stack to act on via `Handler#repository_name`, which reads a *different* JSON key, `payload.dig('repository', 'full_name')`: [2](#0-1) 

Because Shipit supports multiple GitHub Apps/organizations each with its own `webhook_secret` (see `lib/shipit/github_app.rb` and the multi-org secrets format documented in `docs/setup.md`), the signature check and the stack-resolution check are keyed off two independently attacker-supplied fields of the same JSON payload (`repository.owner.login` vs `repository.full_name`) rather than a single verified value. Nothing in the code enforces that `repository.owner.login == repository.full_name.split('/').first`.

If an attacker who legitimately controls a webhook secret for `OrgA` (e.g. because they administer a repository/organization that has Shipit's GitHub App installed and can see its webhook secret configured in that org's webhook settings, or simply because `OrgA`'s secret has otherwise leaked) can produce a validly-signed payload for `OrgA`, they can set `repository.owner.login` to `OrgA` (so `verify_signature` computes the HMAC against `OrgA`'s secret and passes) while setting `repository.full_name` to `OrgB/some-repo` (a stack tracked under a completely different, unrelated organization). The signature-check binding (`organization authenticated == organization whose secret matched`) is broken from the binding that matters for impact (`organization authenticated == organization/repository actually written to`), because the two are read from different, independently forgeable fields of the same unauthenticated JSON body.

### Impact Explanation
Handlers acting on the forged `repository.full_name` can trigger unauthorized actions against a stack that belongs to a different organization than the one whose secret validated the signature — e.g. `PushHandler` invoking `stack.sync_github(expected_head_sha:)` against an arbitrary tracked stack under another org, or `StatusHandler`/`CheckSuiteHandler`/`MembershipHandler` writing commit statuses, check runs, or team memberships for a repository/organization the attacker does not control the webhook secret for. This is a cross-organization / cross-repository write via a forged webhook that crosses the "organization that authenticated" vs "repository that is written" trust boundary called out in the rules.

### Likelihood Explanation
Exploitation requires the attacker to already possess (or have leaked to them) a valid `webhook_secret` for at least one organization onboarded to the Shipit instance — this is a real-world scenario in multi-tenant/multi-org Shipit deployments (explicitly supported per `docs/setup.md` "Using Multiple Github Applications") where different teams each manage their own GitHub App and could have differing levels of care around their webhook secret. No GitHub session, API token, or Shipit account is needed; only knowledge of one org's webhook secret and the ability to send an HTTP POST to `/webhooks`.

### Recommendation
Bind the entire webhook to a single verified organization value: after `verify_signature` succeeds, derive `repository_name`/target stack lookup using the same `repository_owner` value used for signature verification (or explicitly assert `repository.full_name.split('/').first.casecmp(repository_owner)` before dispatching to handlers). Reject the webhook if the two disagree.

### Proof of Concept
1. Shipit is configured with two orgs, `OrgA` (attacker has/obtains `webhook_secret_A`) and `OrgB` (victim org, has a tracked stack `OrgB/victim-repo`).
2. Attacker crafts a `push` payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac-sha1(webhook_secret_A, body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` looks up `Shipit.github(organization: 'OrgA')`, verifies the HMAC against `webhook_secret_A`, and passes (per `app/controllers/shipit/webhooks_controller.rb:24-30`).
5. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name('OrgB/victim-repo')` (per `app/models/shipit/webhooks/handlers/handler.rb:32-38`) and calls `stack.sync_github(expected_head_sha: ...)` on the `OrgB` stack — an action the attacker was never authorized to trigger, despite the signature only proving control of `OrgA`'s secret.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)

        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
