## Analysis

Confirmed real logic bug in the cyclic-dependency check. Let me walk through the exact mechanism.

`verify_package_no_cyclic_relationships` builds a work-queue `to_visit_modules` and repeatedly pops the lexicographically-largest `ModuleId` via `pop_last`, running `cyclic_dependencies::verify_module` on it, then removing every module in the returned `visited` set from the queue: [1](#0-0) 

The critical flaw is in how `cyclic_dependencies::verify_module_impl` computes `visited`. It runs a DFS *from the popped module's dependencies*, checking only whether the DFS ever loops back to the **original module's own `self_id`** (the `target`). Any other module encountered along the way is marked `visited` and never re-checked against its own possible cycle: [2](#0-1) 

Concretely: given modules `A -> B -> C -> B` (a genuine cycle strictly between `B` and `C`, with `A` merely depending on `B`), if `A` sorts as the lexicographically-largest `ModuleId` and is popped first:

- `verify_module(A, ...)` runs DFS with `target = A`.
- It visits `B` (inserted into `visited`), recurses into `C` (inserted into `visited`), recurses back into `B` — but since `B` is already in `visited` (`is_new = false`), the function returns `Ok(false)` without ever comparing `cursor == target` for `B` or `C` as targets themselves.
- No cycle is reported because `A` is never re-encountered.
- The returned `visited = {B, C}` is used to remove both `B` and `C` from `to_visit_modules` — **without either of them ever having `verify_module` called with `self_id = B` or `self_id = C`**, which is the only call pattern that would detect the `B <-> C` cycle.
- `to_visit_modules` becomes empty and the loop exits, returning `Ok(())` despite a real cyclic module dependency existing in the package.

This precisely matches the proof idea in the question: a package whose modules have a cycle not reached from the initial `pop_last` order passes verification.

## Impact assessment

This is a genuine correctness bug in the linkage/cyclic verifier, reachable directly by any unprivileged package publisher (attacker just crafts a module ordering/`ModuleId` naming such that the outer cycle member is popped first). The cyclic-dependency check exists specifically to prevent modules with circular references from reaching the loader, which assumes an acyclic dependency graph when resolving struct/function handles, generic instantiations, and layouts. Bypassing it lets a cyclic module bundle be published and subsequently loaded/executed by every validator and fullnode that touches the package (on publish and on every later invocation), which is a deterministic, network-wide fault — not a local/single-node issue.

However, without further evidence in this pass showing the downstream loader/type-layout code performs unbounded recursion or unsound resolution when given such a cycle (I did not trace `move-vm-runtime`'s loader path deeper here), I can't confirm this escalates all the way to **fund theft or object/state corruption** required for Critical, nor to arbitrary RCE. The most defensible impact is validator/fullnode crash (stack overflow / non-termination) triggered deterministically for all nodes processing the publish or subsequent calls — which falls into the "current-bounty network and node shutdown class" bucket (High/Medium) rather than direct fund theft.

### Title
Cyclic-dependency verifier fails to detect module cycles not involving the initially-popped module - (File: `external-crates/move/crates/move-vm-runtime/src/validation/verification/linkage.rs`)

### Summary
`verify_package_no_cyclic_relationships` relies on `cyclic_dependencies::verify_module`'s returned `visited` set to mark modules as "checked," but that set only reflects modules explored while searching for a cycle back to one specific target module. Modules visited-but-not-targeted are removed from the to-visit queue without ever being checked for cycles among themselves.

### Finding Description [3](#0-2)  pops one module at a time and trusts that `visited` (returned by [4](#0-3) ) represents modules that have been fully validated for cycles. In reality `detect_cycles` only errors when the DFS cursor equals the *original* module's `self_id`; other modules along the traversal are inserted into `visited` purely as a memoization/loop-guard, never as targets of their own cycle check.

### Impact Explanation
A crafted package can contain a genuine mutually-cyclic pair/group of modules (e.g., `B <-> C`) that is never independently verified, because it's swallowed into another module's (`A`'s) `visited` set. This package is accepted by `verify_linkage_and_cyclic_checks_for_publication` at publish time and later reused via `verify_linkage_and_cyclic_checks` on load, propagating a graph structure the rest of the VM (loader, layout resolution) does not expect, most plausibly causing crashes/non-termination deterministically across all nodes processing the package — a network/node shutdown class issue.

### Likelihood Explanation
High likelihood of triggering: an unprivileged publisher fully controls module ordering and dependency structure in a package they submit, and only needs to arrange `ModuleId`s so that the outer (non-cyclic-participant) module sorts last in `BTreeMap` order for `pop_last` to process it first.

### Recommendation
Change `verify_package_no_cyclic_relationships` to check each module's own cycle-freedom explicitly (i.e., call `cyclic_dependencies::verify_module` with every module as its own target, rather than trusting a different module's traversal to clear it), or track "fully verified" separately from "visited during someone else's traversal."

### Proof of Concept
Construct three modules in one package: `A` (depends on `B`), `B` (depends on `C`), `C` (depends on `B`), with `ModuleId`s chosen so `A`'s ID sorts greatest (so it's popped first by `BTreeMap::pop_last`). Call `verify_package_no_cyclic_relationships(&[A,B,C], ..)` and observe it returns `Ok(())` even though `B <-> C` is a real cycle — matching the exact scenario described in the question.
