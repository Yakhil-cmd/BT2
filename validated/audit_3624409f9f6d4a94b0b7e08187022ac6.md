### Title
Webhook Signature Verification Is Scoped by `repository.owner.login`, but Event Handlers Act on the Unverified `repository.full_name` / `sha` Fields — Cross-Organization Webhook Spoofing - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App (and thus which `webhook_secret`) to validate an incoming webhook against using `repository_owner`, derived from the payload's `repository.owner.login` (or `organization.login`). Every downstream event handler, however, determines *which repository/stack/commit to mutate* using a different, unauthenticated payload field: `repository.full_name` (`Shipit::Webhooks::Handlers::Handler#repository_name`) or, in the case of `StatusHandler`, the raw commit `sha` with no repository scoping at all. Because the field used to select/verify the signing secret is never checked against the field used to pick the target repository, a payload can be signed (or, when a tenant's `webhook_secret` is left blank — an explicitly documented "optional" setting) unsigned for one organization while acting on stacks/commits belonging to a completely different organization hosted on the same Shipit instance.

### Finding Description
`verify_signature` picks the GitHub App/secret via the owner login embedded in the payload: [1](#0-0) [2](#0-1) 

Signature verification for that org is `return true unless webhook_secret` — i.e., if the organization's `webhook_secret` is not configured, **any** payload claiming to be from that org is accepted unconditionally, without any HMAC check: [3](#0-2) 

`webhook_secret` is explicitly documented as optional and is shown commented out / blank in shipped configuration examples: [4](#0-3) [5](#0-4) 

Once the request clears `verify_signature`, the handler dispatch and repository resolution use a **different field** from the same untrusted JSON body — `repository.full_name` — with no cross-check against `repository.owner.login`: [6](#0-5) 

This is used, for example, by `PushHandler`, which syncs an arbitrary `expected_head_sha` into any stack matching that repository/branch: [7](#0-6) 

and by the pull-request handlers, which archive/unarchive review stacks or manipulate merge queue state based on `params.repository.full_name` alone: [8](#0-7) [9](#0-8) 

`StatusHandler` is the most severe case: it doesn't scope by repository at all, matching purely by `sha` across the entire Shipit instance's `Commit` table: [10](#0-9) 

**Binding broken:** organization authenticated (`repository_owner` used to pick `webhook_secret`) ≠ repository/commit actually written (`repository.full_name` / `sha` used by the handler). Before the fix, these two fields are implicitly assumed to always refer to the same repository, because in a genuine GitHub-originated webhook they always do. This engine never enforces that equality itself, so an attacker who can get *any* request past `verify_signature` (either by knowing/controlling one tenant org's secret, or — critically — by targeting a tenant whose `webhook_secret` is left blank, an officially supported and documented configuration) can set `repository.owner.login` to that permissive/known org while setting `repository.full_name`/`sha` to point at a stack/commit belonging to an entirely different, unrelated organization sharing the same Shipit instance (see "Using Multiple GitHub Applications" support).

### Impact Explanation
This maps to the Critical/High impact classes:
- **Unauthorized deploy/merge influence**: forging `status`/`commit_status`/`push`/`pull_request` events for another organization's stacks can create fabricated commit statuses that gate `release_status?`/continuous delivery, or force `sync_github` to pull an attacker-chosen `expected_head_sha`, or archive/unarchive review stacks — all cross-tenant, without that tenant's webhook secret.
- This is not a theoretical GitHub-side issue: the webhooks endpoint is a public, unauthenticated Rails endpoint (`skip_before_action :verify_authenticity_token`), and the only gate is `verify_signature`, which is itself bypassable per-organization when `webhook_secret` is unset — a state the project's own setup documentation calls "optional."

### Likelihood Explanation
Requires: (1) the Shipit instance hosts multiple GitHub organizations/tenants (an explicitly documented and supported deployment mode), and (2) at least one configured organization has no `webhook_secret` set, or the attacker otherwise possesses a valid secret for any one tenant. Given `webhook_secret` is marked optional in the setup docs and shown blank in the shipped example configs, this is a realistic misconfiguration, not a contrived edge case. No repository write access, session, or API token is required — only knowledge of the organization login name used in Shipit's config, which is not secret.

### Recommendation
When resolving the target repository/stack/commit for a webhook event, verify that the owning organization of `repository.full_name` (or the commit's stack repository) matches the `repository_owner` that was used to select/verify the signing secret. Additionally, `verify_webhook_signature` returning `true` when `webhook_secret` is blank should, at minimum, still require that the resolved target repository belongs to the same GitHub App/organization context that was authenticated — closing the gap between "org authenticated" and "repository written."

### Proof of Concept
Conceptual request (assuming Org "known-org" has no `webhook_secret` configured, or the attacker knows its secret), targeting a stack that actually belongs to Org "victim-org" hosted on the same Shipit instance:
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=<anything, or valid for known-org>

{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "known-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
`verify_signature` resolves the GitHub App via `known-org` (passes, e.g. because `known-org`'s `webhook_secret` is blank), but `PushHandler#stacks` resolves the target stack via `repository.full_name = "victim-org/victim-repo"`, causing `sync_github(expected_head_sha: "<attacker-chosen sha>")` to run against `victim-org`'s stack — with no verification tying `known-org` to `victim-org`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
