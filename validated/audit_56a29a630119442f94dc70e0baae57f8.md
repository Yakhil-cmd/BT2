### Title
Removing an address from a `spender_attested` asset's attestor list permanently freezes that address's existing token balance - ([File: validation.js])

### Summary
The original report shows that JOJO's `JUSDBank`/`JUSDView` deem a delisted collateral's value to be zero, which can make a previously-safe position unsafe and block withdrawal of collateral that is no longer even used to back a loan. The analogous class of bug in `ocore` is that an asset definer can post an `asset_attestors` message that removes an address from the attestor list of a `spender_attested` asset. Any wallet that is currently holding units of that asset, but is no longer in the attestor list, becomes permanently unable to spend/transfer those units, even though the tokens were legitimately received while the holder was attested and are in no way tied to any ongoing obligation.

### Finding Description
When an asset is defined with `spender_attested: true`, every payment that spends this asset must have all of its output addresses currently attested by one of the asset's attestors, checked via `storage.filterAttestedAddresses()` inside `validatePaymentInputsAndOutputs()`: [1](#0-0) 

The attestor list itself is fully mutable after the asset is created: any address can post an `asset_attestors` message (validated in `aa_validation.js`/`validation.js`) that adds or removes attestor addresses, and this is persisted into the `asset_attestors` table with no restriction requiring monotonic growth or preserving previously attested holders: [2](#0-1) [3](#0-2) 

Because `filterAttestedAddresses` is evaluated against the attestor list as of `objValidationState.last_ball_mci` (i.e., the current/most-recent list, not the list at the time the tokens were acquired), an address that held a balance of the asset while attested can be retroactively "delisted" the moment the attestor set changes. From that point on, every future payment message that lists this address as an output for that asset will fail the `"some output addresses are not attested"` check, permanently freezing the balance — the address can never move it out again, regardless of whether any loan/backing relationship exists. This mirrors the reported bug: the protocol treats the delisted entity's balance as effectively "zero-value"/unusable, without giving the holder a path to withdraw or transfer out the funds they legitimately hold.

### Impact Explanation
This is a concrete, permanent freezing of user funds enforced directly by the consensus validation code (`validation.js`), not a peer/hub-only or DoS-only issue. Any asset issuer (an ordinary, unprivileged unit poster who merely defined a `spender_attested` asset) can unilaterally and irreversibly lock the holdings of any address by posting a single `asset_attestors` unit that drops that address from the list, with no way for the affected holder to reclaim or move the trapped balance. This qualifies as an AA/user fund freezing bug of Medium severity, matching the accepted analog impact bucket ("AA fund loss or freezing").

### Likelihood Explanation
The attestor list is intentionally mutable by design (to let issuers add/remove trusted attestors as their KYC/whitelist changes), so this can happen in completely normal, non-malicious usage: an issuer simply updates the attestor list, and existing holders who fall out of it are frozen immediately without warning. Every `spender_attested` asset is inherently susceptible whenever its attestor set shrinks or changes.

### Recommendation
Track attestation status at issuance/holding time, or allow holders to withdraw/exit into a designated address (e.g., the asset definer or a burn address) even if they are no longer currently attested, similar to allowing withdrawal of delisted collateral in the original report. At minimum, consider validating `asset_attestors` updates so that removing an address that currently holds a nonzero balance of the asset is either disallowed or triggers a grace period/exit mechanism.

### Proof of Concept
1. Definer creates asset A with `spender_attested: true`, `attestors: [X]`.
2. Definer issues/pays units of asset A to address `H`, which is attested via attestor `X`.
3. Definer (or attestor logic) posts an `asset_attestors` message removing `H`'s attestation status (or replacing the attestor set such that `H` is no longer attested), processed via `writer.js` insert into `asset_attestors`.
4. `H` now attempts to spend/transfer its held balance of asset A in a new payment unit.
5. `validatePaymentInputsAndOutputs()` calls `storage.filterAttestedAddresses()`, finds `H` is not currently attested, and rejects the unit with `"some output addresses are not attested"` — permanently freezing `H`'s balance with no recovery path. [1](#0-0)
