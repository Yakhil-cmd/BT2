### Title
Webhook signature verification is bound to `repository.owner.login`, while event routing trusts the unrelated `repository.full_name` field, allowing cross-tenant forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to check against using `repository_owner`, derived from `params.dig('repository', 'owner', 'login')` (or `organization.login`). Once the signature check for that field passes, the same raw payload is handed to event handlers that instead trust the sibling field `repository.full_name` to decide which `Repository`/`Stack` the event applies to. These two fields are never cross-validated, so a payload can be crafted where they refer to different organizations/repositories.

### Finding Description
`verify_signature` computes the organization whose secret will validate the signature strictly from `repository.owner.login`: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up a per-organization `GithubApp`/webhook secret [3](#0-2) , confirming this Shipit instance is designed to host multiple, independently-configured organizations (also evidenced by the fixture set covering `shipit`, `cyclimse`, and `shopify` organizations with distinct secrets) [4](#0-3) .

Once the HMAC check succeeds, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the full, un-scoped JSON body to handlers [5](#0-4) . Every base handler resolves the target repository/stack from a *different* field, `repository.full_name`, not `repository.owner.login`: [6](#0-5) 

This pattern repeats across handlers such as `PushHandler` (`stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(...) }`) [7](#0-6)  and the pull-request handlers, which independently look up `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [8](#0-7) .

The equality that should hold but does not:
`organization whose secret authenticated the request (repository.owner.login)` == `organization/repository that the handlers act on (repository.full_name)`.

Because the signature is a valid HMAC over the *entire* raw body using the secret picked from `repository.owner.login`, an attacker who legitimately controls (and knows the webhook secret of) one onboarded organization, call it `attacker-org`, can self-sign a payload where `repository.owner.login = "attacker-org"` (to pass `verify_signature`) but `repository.full_name = "victim-org/victim-repo"` (a different, unrelated organization/repository also onboarded to the same Shipit instance). The controller only checks that *some* valid secret produced the bytes; it never confirms that secret's organization matches the repository the handler subsequently mutates.

### Impact Explanation
This breaks a deployment-trust binding explicitly called out as in-scope: "an organization that authenticated versus the repository that is written." A tenant of a shared Shipit instance can forge webhook events (e.g. `push`, `status`, `check_suite`, `pull_request`) that are attributed to and acted upon another tenant's repository/stack. Depending on the handler reached, this enables cross-repository writes (e.g. `sync_github`/`GithubSyncJob` triggering out-of-band syncs, or forged commit statuses/check-runs feeding into deploy-safety checks) without ever needing write access to the victim repository or organization — only a legitimate registration of some other organization on the same Shipit instance.

### Likelihood Explanation
Any customer/organization already onboarded onto a shared Shipit deployment (a normal, unprivileged-relative-to-other-tenants scenario) can compute a valid HMAC for their own organization's secret and simply substitute an unrelated `repository.full_name` value in the JSON body before signing — no secret-guessing, GitHub App key, or session is required, satisfying the "unprivileged attacker" bar for this multi-tenant configuration.

### Recommendation
After signature verification, re-derive `repository_owner` from the *same* `repository.full_name` value the handlers will use (or vice versa) and reject the request (422) if the owning organization implied by `repository.full_name` does not match the organization whose secret validated the signature. Alternatively, scope the webhook secret lookup itself to the specific repository being referenced (`repository.full_name`) rather than trusting a loosely related `repository.owner.login`/`organization.login` field for secret selection.

### Proof of Concept
1. Shipit hosts two onboarded organizations, `attacker-org` (secret `S_A`, known to the attacker as its own org admin) and `victim-org` (owns stack `victim-org/victim-repo`, registered with a different secret).
2. Attacker builds a JSON body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>"
}
```
3. Attacker signs the raw body with `S_A` and sets `X-Hub-Signature`, `X-Github-Event: push`.
4. `verify_signature` computes `repository_owner = "attacker-org"`, fetches `attacker-org`'s app, and validates successfully against `S_A` [1](#0-0) .
5. `PushHandler#process` resolves `stacks` from `repository.full_name = "victim-org/victim-repo"` [6](#0-5)  and calls `stack.sync_github(expected_head_sha: params.after)` on the victim's stack [7](#0-6) , even though the signature only proved control of `attacker-org`'s secret.
