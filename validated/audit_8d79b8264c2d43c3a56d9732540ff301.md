### Title
Webhook signature verification silently no-ops when `webhook_secret` is unset, allowing unauthenticated forgery of GitHub webhook events - (File: `lib/shipit/github_app.rb`)

### Summary
`GitHubApp#verify_webhook_signature` is designed to authenticate that a webhook payload actually originated from GitHub for the configured organization, and `Shipit::WebhooksController` treats a "verified" payload as fully trusted input for mutating actions (creating users/teams, granting team membership, injecting commit CI statuses, triggering syncs). However, verification is bypassed entirely whenever `webhook_secret` is blank, which is a directly documented, supported configuration value (`webhook_secret: # nil`) in `config/secrets.development.example.yml` and `docs/setup.md`. This breaks the trust binding: "payload acted on by handlers" = "payload covered by a verified signature" — in this configuration, the equality collapses to acting on a completely unauthenticated payload.

### Finding Description
The webhook controller's `before_action` chain calls `verify_signature`, which delegates to `GitHubApp#verify_webhook_signature`: [1](#0-0) 

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```

If `@webhook_secret` (set from `@config[:webhook_secret]`, see [2](#0-1) ) is blank/nil, the method returns `true` unconditionally — no HMAC comparison is performed at all. This is not a corner case: it's the literal default shipped in the example secrets files: [3](#0-2) [4](#0-3) 

`WebhooksController#verify_signature` only rejects on an explicit `false` return; when `webhook_secret` is unset it always "passes": [5](#0-4) 

Once past this check, `create` parses the raw JSON body and dispatches it directly to registered handlers with no further authentication: [6](#0-5) 

These handlers perform trust-sensitive operations directly from attacker-controlled JSON:
- `MembershipHandler` creates arbitrary `Team`/`User` records and adds/removes team membership based solely on payload content (`params.team`, `params.organization.login`, `params.member.login`): [7](#0-6) 
- `StatusHandler` creates a commit CI status (`create_status_from_github!`) for any `Commit` matching an attacker-supplied `sha`, with attacker-controlled `state`/`context`/`description`: [8](#0-7) 
- `PushHandler` triggers `stack.sync_github` for matching stacks: [9](#0-8) 

The `Handler` base class resolves the target `Repository`/`Stack` purely from the unauthenticated payload's `repository.full_name` field: [10](#0-9) 

The `WebhooksController` is mounted as a public, unauthenticated endpoint (no `ApiClient`/session/CSRF requirement — `verify_authenticity_token` is explicitly skipped): [11](#0-10) 

Because `verify_signature`'s pass/fail is entirely contingent on operator configuration of `webhook_secret`, and that field is documented as optional/nilable, any deployment following the documented example configuration exposes this endpoint to fully unauthenticated payload injection — the "GitHub identity" the endpoint is meant to authenticate is never actually checked.

### Impact Explanation
An unprivileged network attacker (no Shipit session, no `ApiClient` token, no GitHub credentials) who can reach the `/github/webhooks` endpoint of a Shipit instance configured with `webhook_secret: nil` can:
- Forge CI status updates (`StatusHandler`) for arbitrary commits, e.g. injecting a fabricated `success` status for a malicious commit SHA that Shipit's merge/deploy gating logic (CI checks) relies on — enabling an unauthorized deploy path if deploy pipelines gate on stored commit statuses.
- Create/delete `Team`/`Membership`/`User` records via `MembershipHandler`, tampering with the authorization data (`Shipit.github_teams`) that governs which GitHub identities are treated as members of privileged teams.
- Force arbitrary `GithubSyncJob`s via `PushHandler`.

This maps to the report's core pattern of a signature-covered / signature-verified boundary that is trivially escaped, analogous to the underlying "unverified assumption governs a high-value trust boundary" bug class, here materializing as authentication bypass on the webhook ingestion boundary and escalation into `Shipit.github_teams`-relevant data.

### Likelihood Explanation
This is not a hypothetical misconfiguration — `webhook_secret: # nil` is the literal default in the shipped example secrets template and is explicitly documented as optional. Any operator who follows the setup docs without independently realizing they must set a strong `webhook_secret` (the docs do not flag its absence as insecure) will have this bypass live in production. No attacker capability beyond HTTP access to the public webhook route is required.

### Recommendation
Fail closed instead of failing open: `GitHubApp#verify_webhook_signature` should reject (return `false`) rather than return `true` when `webhook_secret` is blank, or the application should refuse to boot/serve webhooks for an organization with no configured `webhook_secret`. At minimum, `docs/setup.md` and the example secrets files should not present a nil `webhook_secret` as a supported, silently-insecure default.

### Proof of Concept
1. Deploy Shipit using the documented example configuration with `webhook_secret` left blank (as in `config/secrets.development.example.yml`).
2. As an unauthenticated attacker, send:
```
POST /github/webhooks
X-Github-Event: status
Content-Type: application/json

{"sha":"<victim-commit-sha>","state":"success","context":"ci/forged","branches":[{"name":"master"}],"repository":{"owner":{"login":"victim-org"}}}
```
3. `verify_signature` calls `verify_webhook_signature(nil_or_forged_header, raw_body)`, which returns `true` immediately since `webhook_secret` is blank ( [12](#0-11) ), regardless of the actual header value.
4. `StatusHandler#process` runs and calls `commit.create_status_from_github!(params)` on any locally-tracked `Commit` matching `sha`, injecting a forged CI status the attacker fully controls ( [8](#0-7) ).

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
