## Confirmed Vulnerability

### Title
Webhook signature verification is keyed to `repository.owner.login`, but event handlers act on `repository.full_name` from the same untrusted payload, allowing cross-organization forgery in a multi-tenant configuration - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate the HMAC signature against using `repository.owner.login` (or `organization.login`) taken from the still-unverified JSON body. Once verification passes, `WebhooksController#create` dispatches the *entire* raw payload to handlers such as `PushHandler` and `StatusHandler`, which look up the target stack/commit using a **different field from the same payload**, `repository.full_name`. Because Shipit supports multiple GitHub organizations each with its own `webhook_secret` (as documented in `config/secrets.development.example.yml`), a tenant that legitimately owns organization "B" (and therefore knows B's own `webhook_secret`) can send a payload whose `repository.owner.login` is `"B"` (so verification succeeds against B's own secret) while `repository.full_name` points at a stack belonging to organization "A". This is directly analogous to the Dispatcher bug: a value is checked for one purpose (secret selection / authenticity) while a *different, unguarded* value drives the actually-executed effect.

### Finding Description
- `verify_signature` computes `repository_owner` from `params.dig('repository','owner','login') || params.dig('organization','login')` and uses it to fetch the appropriate `Shipit.github(organization: repository_owner)` app/secret: [1](#0-0) [2](#0-1) 
- After verification, the raw, fully attacker-controlled JSON is handed unchanged to the registered handlers: [3](#0-2) 
- `Handler#stacks`/`repository_name` (used by `PushHandler`) resolves the target repository via `payload.dig('repository', 'full_name')` — a completely separate JSON key from the one used for signature routing: [4](#0-3) [5](#0-4) 
- `StatusHandler` is even more direct: it looks commits up purely by `sha` (no repository/org check at all) and persists attacker-supplied `state`, `description`, `target_url`, and `context` onto any commit in the database that happens to share that sha: [6](#0-5) 
- Multi-organization webhook secrets are an explicitly supported, documented configuration: [7](#0-6) 

Nothing in `verify_signature` or in the handlers cross-checks that the organization used to select/validate the secret matches the organization embedded in `repository.full_name` (or, for `StatusHandler`, matches the repository at all). The field that is authenticated (`repository.owner.login`) and the field that determines which stack/commit is mutated (`repository.full_name`, or the bare `sha`) are two different, independently-attacker-controlled values inside the same signed blob.

### Impact Explanation
An attacker who legitimately administers organization B in a multi-org Shipit deployment (and therefore knows B's own `webhook_secret` — no privileged Shipit credential, `ApiClient` token, or GitHub App private key required) can forge:
- `push` events that cause `GithubSyncJob` to run against any stack in the instance whose repository owner is not B, feeding an attacker-chosen `expected_head_sha` into the sync/retry logic for that foreign stack, and
- `status` events (`StatusHandler`) that write arbitrary CI status (`state`, `context`, `target_url`, `description`) onto commits belonging to **any** stack (no ownership check at all), which can flip `required_statuses`/`blocking_statuses` checks used to gate `continuous_deployment` and unblock deploys/merges for a repository the attacker does not control.

This breaks the binding "organization that authenticated == repository that is written," letting an unprivileged tenant influence deploy-gating state for other tenants' stacks — an unauthorized-deploy-class impact.

### Likelihood Explanation
Requires only that the Shipit instance be configured for multiple GitHub organizations (a documented, first-class feature) and that the attacker is a legitimate app owner/admin for one of those organizations, with no access to any other tenant's secrets, Shipit sessions, or API tokens. The `/webhooks` endpoint is unauthenticated by design (it only checks the HMAC), so exploitation is a single crafted HTTP POST.

### Recommendation
Verify the signature using the same field that handlers use to resolve the target (`repository.full_name`, or equivalently derive the app/secret and the acted-upon repository from one canonical, cross-checked value). Additionally, `StatusHandler#process` should confirm the commit's stack/repository matches the organization whose secret validated the request, rather than trusting a bare `sha` match against the entire `Commit` table.

### Proof of Concept
1. Configure Shipit with two organizations, `A` and `B`, each with its own `webhook_secret` (per `config/secrets.development.example.yml`).
2. As the legitimate owner of org B (knows `B`'s `webhook_secret`), craft a `status` webhook payload:
```json
{
  "sha": "<sha of a commit belonging to stack in org A>",
  "state": "success",
  "context": "ci/required-check",
  "target_url": "https://example.com",
  "repository": { "owner": { "login": "B" } }
}
```
3. Sign the raw body with `B`'s `webhook_secret` and send it to `/webhooks` with `X-Github-Event: status`.
4. `verify_signature` resolves `repository_owner` = `"B"`, validates successfully against B's secret.
5. `StatusHandler#process` ( [8](#0-7) ) writes a forged "success" status onto the org-A commit, independent of org B's identity, potentially satisfying `required_statuses` and unblocking continuous deployment for a stack the attacker does not own.
