### Title
Unbounded `io.Copy` in `downloadAsset` allows disk/memory exhaustion via malicious release asset - ([File: pkg/cmd/extension/http.go])

### Summary
`downloadAsset` in `pkg/cmd/extension/http.go` streams an HTTP response body directly to disk with `io.Copy(f, resp.Body)` with no maximum size limit, no `context` deadline/timeout, and no use of `http.MaxBytesReader` or similar bound. Since the asset URL originates from an attacker-controlled repository's release metadata (`asset.APIURL`), a malicious release server can respond with an extremely large or infinite (chunked, never-terminating) body, causing unbounded disk consumption on the victim's machine during `gh extension install`.

### Finding Description
`Manager.installBin` (in `pkg/cmd/extension/manager.go`) calls `downloadAsset(m.client, safeurl.NewImmutableSafeURL(asset.APIURL), binPath)` using an asset URL taken from the release JSON returned by the attacker-controlled repository's GitHub release. `downloadAsset` (`pkg/cmd/extension/http.go:79-112`) performs:

```go
resp, downloadErr = httpClient.Do(req)
...
f, downloadErr = os.OpenFile(destPath, os.O_CREATE|os.O_WRONLY|os.O_TRUNC, 0755)
...
_, downloadErr = io.Copy(f, resp.Body)
``` [1](#0-0) 

There is no `Content-Length` validation before copying, no `io.LimitReader`/`http.MaxBytesReader` wrapping `resp.Body`, and the underlying `http.Client` (`m.client`) is not shown to carry a request timeout or `context.WithTimeout` bound at this call site — `http.NewRequest` is used without a context, and `httpClient.Do` will block for as long as the attacker's server keeps sending data. Since the `Content-Length` header is attacker-controlled (or can be omitted with chunked transfer encoding), the client has no reliable signal to reject the response early. This is a direct data flow from attacker-published release content (the `url` field of a release asset in the attacker's own repository) into an unbounded local file write.

Existing protections in the codebase (safeurl host validation, ghrepo/ghinstance parsing) only ensure the *destination host* of the request is legitimate (i.e., prevents SSRF/wrong-host issues) — they do nothing to bound the *size* of the response body once a legitimate-looking request is made to the attacker's own repository's release asset endpoint, which is inherently attacker-controlled infrastructure (GitHub's asset storage, but the attacker fully controls the asset content and size).

### Impact Explanation
A victim running `gh extension install <attacker-repo>` against a binary-extension release with an oversized or infinitely-streamed asset will have `gh` write an unbounded amount of data to local disk (`binPath`), exhausting disk space and potentially causing a denial of service on the victim's machine. This matches the "unbounded resource consumption / denial of service via malicious repository/extension install" impact class.

### Likelihood Explanation
- Precondition: victim must voluntarily run `gh extension install` against the attacker's repository — a normal, expected usage pattern for this feature.
- The attacker fully controls the release assets of their own repository, including the ability to serve an actual GitHub release asset of very large size, or (if `asset.APIURL` can be a self-hosted/GHES-like URL under attacker influence within the allowed host) to stream indefinitely via chunked transfer encoding.
- No user interaction beyond the standard install command is required; no elevated privileges needed.
- This is highly repeatable — every install attempt against the malicious release repeats the resource exhaustion.

### Recommendation
Wrap `resp.Body` with `io.LimitReader` (or `http.MaxBytesReader`) at a sane maximum extension binary size before copying to disk, and bind the outgoing request with a `context.WithTimeout`/`context.WithDeadline` so that slow or infinite streams are aborted. On exceeding the limit, delete the partial file and return an explicit error to the user.

### Proof of Concept
```go
func TestDownloadAsset_UnboundedBody(t *testing.T) {
    // httptest server that streams chunked, effectively-infinite data
    srv := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        flusher := w.(http.Flusher)
        w.Header().Set("Transfer-Encoding", "chunked")
        w.WriteHeader(http.StatusOK)
        buf := make([]byte, 1<<20) // 1MB chunks
        for {
            if _, err := w.Write(buf); err != nil {
                return
            }
            flusher.Flush()
        }
    }))
    defer srv.Close()

    tmp := t.TempDir()
    dest := filepath.Join(tmp, "bin")

    done := make(chan error, 1)
    go func() {
        u, _ := safeurl.NewImmutableSafeURL(srv.URL)
        done <- downloadAsset(http.DefaultClient, u, dest)
    }()

    select {
    case <-done:
        // downloadAsset returned — expected if a size cap/timeout is enforced
    case <-time.After(3 * time.Second):
        info, _ := os.Stat(dest)
        t.Fatalf("downloadAsset did not terminate; wrote at least %d bytes with no cap", info.Size())
    }
}
```
Expected (fixed) behavior: the call returns an error once the size limit is exceeded or the timeout elapses, and the partial file is bounded/cleaned up. Current behavior: the goroutine never returns within the test deadline and the destination file grows unbounded, confirming the vulnerability.
