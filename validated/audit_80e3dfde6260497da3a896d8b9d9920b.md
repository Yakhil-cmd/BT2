### Title
Unvalidated `_to` Destination Address in Bridge Request Functions Causes Permanent Loss of Bridged Assets in `modeMintBurn` Mode — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`, `BridgeTransferERC721.sol`, `BridgeTransferKLAY.sol`)

---

### Summary

The Kaia service-chain bridge contracts (`BridgeTransferERC20`, `BridgeTransferERC721`, `BridgeTransferKLAY`) expose permissionless request functions that accept a caller-supplied `_to` destination address without validating it against `address(0)`. In `modeMintBurn` mode the source-chain tokens are **burned before** the cross-chain event is emitted. If `_to == address(0)` the relayer's counterpart `handle*Transfer` call always reverts (ERC20/ERC721 `_mint` rejects `address(0)`), so the burn is irreversible and the user permanently loses their bridged assets with no recovery path.

---

### Finding Description

`_requestERC20Transfer` (lines 76–108 of `BridgeTransferERC20.sol`) performs the following sequence:

1. Validates only `_value > 0` — no check on `_to`.
2. In `modeMintBurn` mode, calls `ERC20Burnable(_tokenAddress).burn(_value)` (line 94), permanently destroying the tokens on the source chain.
3. Emits `RequestValueTransfer` with the unvalidated `_to` (lines 97–107), incrementing `requestNonce`.

The same pattern exists in `_requestERC721Transfer` (lines 74–106 of `BridgeTransferERC721.sol`): the NFT is burned at line 91 before the event is emitted, with no `_to != address(0)` guard.

For `_requestKLAYTransfer` (lines 103–124 of `BridgeTransferKLAY.sol`), KLAY is locked in the bridge and the event is emitted with an unvalidated `_to`; on the counterpart chain `_to.call.value(_value)("")` to `address(0)` succeeds but sends KLAY to the zero address (effectively burned).

The public entry points that reach these internal functions are:

- `requestERC20Transfer(address _tokenAddress, address _to, ...)` — line 124–135, `BridgeTransferERC20.sol`
- `onERC20Received(address _from, address _to, ...)` — line 111–121, `BridgeTransferERC20.sol`
- `requestERC721Transfer(address _tokenAddress, address _to, ...)` — line 121–131, `BridgeTransferERC721.sol`
- `requestKLAYTransfer(address _to, ...)` — line 132–135, `BridgeTransferKLAY.sol`

None of these validate `_to != address(0)`.

---

### Impact Explanation

**`modeMintBurn` ERC20/ERC721 (worst case — permanent, irreversible):**

1. User calls `requestERC20Transfer(token, address(0), value, feeLimit, "")`.
2. `safeTransferFrom` moves `value + feeLimit` from user to bridge.
3. `ERC20Burnable.burn(value)` destroys the tokens on the source chain — **irreversible**.
4. `RequestValueTransfer` event is emitted with `to = address(0)`.
5. Relayer calls `handleERC20Transfer(..., address(0), ...)` on the counterpart bridge.
6. `ERC20Mintable.mint(address(0), value)` reverts: `"ERC20: mint to the zero address"` (OpenZeppelin `_mint` guard, line 171 of `ERC20.sol`).
7. The handle transaction always reverts; the nonce is never consumed on the counterpart chain.
8. Tokens are permanently destroyed on the source chain with no counterpart issuance and no recovery mechanism.

**Non-`modeMintBurn` ERC20/KLAY:**

Tokens/KLAY are locked in the source bridge. The relayer's handle call reverts (ERC20 `safeTransfer` to `address(0)` reverts) or KLAY is sent to `address(0)`. Assets are permanently locked/lost with no recovery path.

**Corrupted value:** `totalSupply` of the bridged ERC20 is permanently decremented; the user's balance is zeroed; no corresponding balance appears on the counterpart chain.

---

### Likelihood Explanation

The trigger is a single unprivileged user transaction. No operator, validator, or majority collusion is required. The scenario is a realistic user error (copy-paste mistake, UI bug, programmatic zero-initialization) identical to the BitVM bridge report. The bridge is a production service-chain component actively used for cross-chain value transfer.

---

### Recommendation

Add a zero-address guard at the top of each internal request function:

```solidity
// BridgeTransferERC20.sol – _requestERC20Transfer
require(_to != address(0), "zero recipient address");

// BridgeTransferERC721.sol – _requestERC721Transfer
require(_to != address(0), "zero recipient address");

// BridgeTransferKLAY.sol – _requestKLAYTransfer
require(_to != address(0), "zero recipient address");
```

Placing the check before any token transfer or burn ensures the transaction reverts cleanly and the user retains their assets.

---

### Proof of Concept

```solidity
// Scenario: modeMintBurn ERC20 bridge, source chain
// 1. Deploy bridge with modeMintBurn = true
// 2. Register token; user holds 100 tokens

    tokenAddress,
    address(0),   // <-- unvalidated _to
    100e18,
    0,
