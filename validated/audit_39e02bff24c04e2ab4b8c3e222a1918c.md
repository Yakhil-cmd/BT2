### Title
Webhook signature verification keys on `repository.owner.login`/`organization.login` while event handlers act on the independent `repository.full_name` field, allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to use for HMAC verification based on `repository.owner.login` (falling back to `organization.login`), but the signature itself only proves the sender knows *that one org's* secret. The event handlers that subsequently act on the verified payload (`PushHandler`, all `PullRequest::*Handler`s) never re-check `repository.owner.login`; they instead resolve the target `Repository`/`Stack` purely from the sibling field `repository.full_name`. These two JSON fields are never cross-validated against each other.

### Finding Description
Shipit supports hosting multiple GitHub Apps/organizations from a single instance (`docs/setup.md`, `config/secrets.development.shopify.yml`, `test/dummy/config/secrets_double_github_app.yml`), each with its own independent `webhook_secret`: [1](#0-0) 

The controller picks the verification key like this: [2](#0-1) [3](#0-2) 

`verify_webhook_signature` HMACs the *entire* raw body with whatever secret was selected for that organization: [4](#0-3) 

Once verification succeeds, `WebhooksController#create` dispatches the parsed JSON straight to handlers: [5](#0-4) 

All handlers, including `Handler#stacks`/`#repository_name` and `PushHandler#process`, resolve the acted-upon `Repository`/`Stack` from a **different** field, `repository.full_name`, with no comparison back to `repository.owner.login`: [6](#0-5) [7](#0-6) [8](#0-7) 

The same pattern of trusting `repository.full_name` in isolation appears in every pull-request handler (`opened_handler.rb`, `labeled_handler.rb`, `unlabeled_handler.rb`, `edited_handler.rb`, `label_capturing_handler.rb`), each doing `Shipit::Repository.from_github_repo_name(params.repository.full_name)`.

**Broken binding (equality that should hold but doesn't):**
`organization authenticated by verify_signature (repository.owner.login / organization.login)` ≠ `repository that gets written by the handler (repository.full_name)`.

The bug-class is directly analogous to the reported `Reward.sol` issue: a value used to gate/verify a critical operation (`currentEpoch` gating `getClaimableAmount`) is decoupled from the value that actually drives outcomes elsewhere in the same function, letting inconsistent state slip past validation. Here, the field used to prove authenticity (`repository.owner.login`) is decoupled from the field used to decide what gets mutated (`repository.full_name`), so a valid signature for org A does not guarantee the payload only affects org A's repositories.

### Impact Explanation
Any actor who legitimately administers a GitHub App/webhook for **one** onboarded organization (Org A) on a shared Shipit instance can craft an arbitrary JSON body where:
- `repository.owner.login` = `"OrgA"` (so `Shipit.github(organization: "OrgA")` is selected and the attacker's known `webhook_secret` for OrgA produces a valid `X-Hub-Signature`), and
- `repository.full_name` = `"OrgB/protected-repo"` (an unrelated organization's repository also hosted on the same Shipit instance).

This forged, signature-valid request is accepted by `verify_signature`, and the `push` handler will look up the *real* `OrgB/protected-repo` Stack and call `stack.sync_github(expected_head_sha: params.after)`, which enqueues `GithubSyncJob` against that Stack — fetching and appending real GitHub commits for a repository the attacker does not own/administer, and can trigger deploy-pipeline side effects (e.g. continuous-deployment jobs, cached deploy spec recomputation) for that victim stack. Similarly, PR-event handlers can be tricked into creating/archiving/labelling review stacks for `OrgB` repositories. This is a cross-organization/cross-repository write triggered without any credential tied to OrgB, meeting the Critical bar of "cross-repository writes / unauthorized deploy".

### Likelihood Explanation
This requires the deployment to actually use the documented multi-organization configuration (multiple `webhook_secret`s under distinct org keys) and for the attacker to control (or know) one org's webhook secret while another org is also onboarded to the same Shipit instance — a configuration explicitly documented and supported (`docs/setup.md` "Using Multiple Github Applications"). Given that setup, no additional privilege is needed beyond administering one org's GitHub App/webhook — the payload fields are fully attacker-controlled JSON, not GitHub-enforced consistency.

### Recommendation
After selecting the verifying organization from `repository.owner.login`/`organization.login`, re-validate that the same value equals the owner segment parsed from `repository.full_name` (and, for org-only events, that `organization.login` matches) before dispatching to handlers. Reject the webhook (422) on mismatch. Alternatively, resolve the target repository via an ID/owner combination that is itself included in the signed payload and verified consistently, rather than trusting two independently-writable fields for two different purposes.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with distinct `webhook_secret`s (per `docs/setup.md` multi-org setup).
2. As the administrator of `OrgA`'s GitHub App, compute `X-Hub-Signature: sha1=<hmac>` over a crafted payload using OrgA's known `webhook_secret`:
```json
{
  "ref": "refs/heads/master",
  "after": "<existing-sha-in-OrgB/protected-repo>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/protected-repo"
  }
}
```
3. `POST /webhooks` with header `X-Github-Event: push` and the computed signature.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgA").verify_webhook_signature(...)`, which succeeds because the attacker used OrgA's real secret over the exact raw body.
5. `Shipit::Webhooks::Handlers::PushHandler` resolves `Repository.from_github_repo_name("orgb/protected-repo")` and calls `stack.sync_github(expected_head_sha: "<...>")`, enqueuing `GithubSyncJob` against a Stack the attacker does not control — confirmed by [9](#0-8)  which fetches real commits and mutates the target stack's state.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
