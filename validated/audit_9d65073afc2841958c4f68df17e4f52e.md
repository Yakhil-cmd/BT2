### Title
Malicious submodule in synced repo causes persistent sync denial by making the whole worktree checkout fail atomically - (File: `main.go`)

### Summary
The reported bug class is: an untrusted party can embed one bad item inside a list of otherwise-legitimate items that are processed atomically, so a single failure blocks the entire operation and denies the honest outcome to a legitimate participant. In `git-sync`, the analogous reachable surface is `repoSync.configureWorktree`, which performs a single atomic `git submodule update --init [--recursive]` call covering *all* submodules of the currently-fetched commit. An attacker who controls the upstream repository content (the only entity `git-sync` treats as untrusted/attacker-pushed) can add one broken/malicious submodule reference alongside legitimate content. That single submodule failure aborts the whole worktree configuration step, which in turn aborts `SyncRepo`, so the new (and all future identical) commits can never be published via the `--link` symlink.

### Finding Description
`configureWorktree` resets the worktree to the target hash and then, if submodules are enabled (default `--submodules=recursive`), runs a single git submodule command covering every submodule in one shot: [1](#0-0) 

If this command fails for any reason (e.g. a submodule with an unresolvable commit, an unreachable/blocked URL, or a submodule url that requires unexpected auth), `configureWorktree` returns the error immediately with no per-submodule isolation or fallback: [2](#0-1) 

That error propagates straight out of `SyncRepo` before the symlink is ever repointed: [3](#0-2) 

Because the failing commit is the current remote HEAD/ref, every subsequent sync attempt re-fetches the exact same broken content and hits the exact same failure — this is not a transient error, it is deterministic and repeats every `--period` indefinitely: [4](#0-3) 

In the main loop, repeated failures increment `failCount`, and if `--max-failures` is configured, the process exits and (under Kubernetes) restarts, fetches the same commit, and fails again — a permanent restart loop: [5](#0-4) 

This mirrors the IntentVault issue precisely: a single "malicious token" (here, a malicious/broken submodule) that is included alongside "legitimate rewards" (legitimate repository content) blocks the atomic operation (worktree publish) that would otherwise deliver the legitimate payload, because there is no isolation between the individual items in the batch.

### Impact Explanation
Impact is high in terms of availability: this yields persistent sync denial. Once an attacker who can push to the tracked ref/repo (or an intentionally malformed upstream) introduces a bad submodule reference, `git-sync` can never publish that commit or any later commit built on top of it, since the failure is deterministic and repeats every sync cycle. Downstream consumers relying on `--link` staying fresh are permanently stuck on stale content (or never get an initial sync at all), and with `--max-failures`/`--one-time` set this also causes the container to exit non‑zero repeatedly, causing CrashLoopBackOff in Kubernetes. Unlike the token-transfer case there is no direct fund theft here, but the "block legitimate outcome via one bad item in an atomic batch" root cause and its "persistent denial" consequence directly matches the accepted impact categories (persistent sync denial).

### Likelihood Explanation
Likelihood is medium-to-high for repositories where the tracked ref is externally writable or where `git-sync` follows a branch/tag from a repo not fully trusted by the operator (a common git-sync deployment pattern is to sync a repo that other parties can contribute to, e.g. GitOps config repos with PR merges, or submodule-based supply chains). Adding a broken submodule entry (bad URL, unreachable host, or a commit removed by force-push in the submodule) requires only ordinary push access to the synced repository or its submodules — no privileged access to git-sync's host, credentials, or `--root` is needed.

### Proof of Concept
1. Deploy `git-sync` with default `--submodules=recursive` against `--repo=<REPO>` and `--ref=<BRANCH>`.
2. In `<REPO>`, add a submodule entry in `.gitmodules`/tree pointing to a URL/commit that is guaranteed to fail (e.g., an unreachable host, or a commit hash that will be removed from the submodule's history), then commit and push it as `HEAD` of `<BRANCH>`.
3. Observe that `git-sync`'s next sync attempt fails inside `configureWorktree` at the `git submodule update --init --recursive` call [2](#0-1) , and `SyncRepo` returns an error without updating `--link` [3](#0-2) .
4. Confirm this repeats on every subsequent `--period` tick (`failCount` keeps incrementing) since the same broken commit is fetched again each time [4](#0-3) , and, if `--max-failures` is set, the process eventually calls `os.Exit(1)` [6](#0-5) , producing a permanent restart loop in Kubernetes deployments while the `--link` target never advances past the last good commit.
