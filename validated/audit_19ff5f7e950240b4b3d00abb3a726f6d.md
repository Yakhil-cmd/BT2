### Title
Unauthenticated injection of attacker-controlled "shared address" bypassing approval flow - ([File: wallet_defined_by_addresses.js])

### Summary
The GitLab CVE-2022-0125 bug class is a missing authorization check: a privileged action (importing members into a project) was performed without verifying the actor's rights over the *target* resource. The analogous ocore path is the `new_shared_address` device-message handler, which accepts and persists an arbitrary shared-address definition from any paired device without verifying that the message actually originates from, or was approved through, the legitimate shared-address creation/approval flow.

### Finding Description
Creating a shared (multisig-like) address is normally a two-step, mutually-approved process: `create_new_shared_address` → user reviews the template and approves via `approve_new_shared_address`/`approvePendingSharedAddress`, after which the initiator broadcasts the finalized `new_shared_address` message to all cosigners [1](#0-0) .

However, the receiving side of the finalized message, `handleNewSharedAddress`, performs only internal consistency checks — that `definition` hashes to `address`, that `signers` map to valid addresses, and that these match the paths extracted from the definition — but never checks that the sending device (`from_address`) is actually one of the parties who initiated or was invited into this specific shared address, nor that a corresponding `pending_shared_addresses`/approval record exists for it [2](#0-1) .

Critically, the dispatcher in `wallet.js` for the `"new_shared_address"` message type forwards the body straight to `walletDefinedByAddresses.handleNewSharedAddress` without passing or checking `from_address` at all: [3](#0-2) .

`determineIfIncludesMeAndRewriteDeviceAddress` only confirms that one of the addresses referenced in the definition belongs to `my_addresses` (i.e., the attacker can legally embed the victim's real address as one branch of an `or`/`weighted and` condition) — it does not confirm that the victim ever agreed to be joined with the specific other signer(s) in this specific definition [4](#0-3) . `validateAddressDefinition` (i.e., `Definition.validateDefinition`) only checks the definition is syntactically well-formed and has a signature branch — it enforces no relationship or trust requirement between the co-signers [5](#0-4) . Once these checks pass, `addNewSharedAddress` persists the address into the `shared_addresses` and `shared_address_signing_paths` tables unconditionally [6](#0-5) .

Any device that has paired with the victim (pairing is a low-friction, often one-directional trust action, e.g. via a QR code/link) can therefore send a crafted `new_shared_address` message such as:
```
["or", [["address", "$VICTIM_ADDRESS"], ["sig", {pubkey: "$ATTACKER_PUBKEY"}]]]
```
This is accepted and silently recorded in the victim's wallet database as a legitimate "shared address," exactly analogous to GitLab importing project members without verifying the importer's rights over the target project — here, the wallet imports a "membership"/co-signer relationship into the victim's local address book without verifying that the victim ever authorized that specific relationship.

### Impact Explanation
Once the address is recorded in `shared_addresses`, it is treated by the wallet like any legitimately created shared address: it is watched for balance/UTXO purposes (`network.js`, `inputs.js` query `shared_addresses`/`shared_address_signing_paths` when selecting spendable inputs and computing balances) [7](#0-6) . If the victim's UI subsequently shows this address as an available "joint"/"shared" address and the user pays funds into it believing it requires cooperation from a trusted co-signer, the attacker's independent `or`-branch signature (or an unbalanced `weighted and`) lets the attacker unilaterally spend the funds — resulting in outright fund loss with no cooperation from the victim required. This satisfies the "concrete unauthorized spending" bar.

### Likelihood Explanation
The prerequisite is only that the attacker's device is paired with the victim's device — a routine, low-privilege interaction (e.g., scanning a merchant's pairing code, or any counterparty relationship) — not that the attacker is a trusted wallet cosigner. No user confirmation dialog is required before the malicious shared address is written to the database, since the normal `pending_shared_addresses` approval step is entirely bypassed by directly sending `new_shared_address`. The attack is fully triggerable by one unsolicited encrypted device message.

### Recommendation
In `handleNewSharedAddress` (and the `wallet.js` dispatcher), require that the incoming `new_shared_address` message correlates to a `pending_shared_addresses`/`pending_shared_address_signing_paths` record that the local device already approved (matching `definition_template_chash`), and that `from_address` is one of the `device_address`es recorded for that pending template before persisting to `shared_addresses`. Reject any `new_shared_address` message that does not correspond to a locally-initiated-and-approved template.

### Proof of Concept
1. Attacker device pairs with victim device (standard pairing flow).
2. Attacker learns victim's real payment address `$VICTIM_ADDR` (often discoverable, e.g. via a prior payment request).
3. Attacker computes `arrDefinition = ["or", [["address", "$VICTIM_ADDR"], ["sig", {pubkey: "$ATTACKER_PUBKEY"}]]]` and `address = objectHash.getChash160(arrDefinition)`.
4. Attacker sends a `new_shared_address` message to victim's device: `{address, definition: arrDefinition, signers: {"r.0": {address: "$VICTIM_ADDR", device_address: "$VICTIM_DEVICE"}, "r.1": {address: null, device_address: "$ATTACKER_DEVICE"}}}` per `wallet.js` case handler [3](#0-2) .
5. `handleNewSharedAddress` validates syntactic consistency only and calls `addNewSharedAddress`, storing the address as a trusted shared address in the victim's wallet [8](#0-7) .
6. If the victim (or an application built on the wallet) sends funds to this "shared" address believing both parties must cooperate, the attacker spends alone using the `sig` branch, with no victim participation.

function determineIfIncludesMeAndRewriteDeviceAddress(assocSignersByPath, handleResult){
	var assocMemberAddresses = {};
	var bHasMyDeviceAddress = false;
	for (var signing_path in assocSignersByPath){
		var signerInfo = assocSignersByPath[signing_path];
		if (signerInfo.device_address === device.getMyDeviceAddress())
			bHasMyDeviceAddress = true;
		if (signerInfo.address)
			assocMemberAddresses[signerInfo.address] = true;
	}
	var arrMemberAddresses = Object.keys(assocMemberAddresses);
	if (arrMemberAddresses.length === 0)
		return handleResult("no member addresses?");
	db.query(
		"SELECT address, 'my' AS type FROM my_addresses WHERE address IN(?) \n\
		UNION \n\
		SELECT shared_address AS address, 'shared' AS type FROM shared_addresses WHERE shared_address IN(?)", 
		[arrMemberAddresses, arrMemberAddresses],
		function(rows){
		//	handleResult(rows.length === arrMyMemberAddresses.length ? null : "Some of my member addresses not found");
			if (rows.length === 0)
				return handleResult("I am not a member of this shared address");
			var arrMyMemberAddresses = rows.filter(function(row){ return (row.type === 'my'); }).map(function(row){ return row.address; });
			// rewrite device address for my addresses
			if (!bHasMyDeviceAddress){
				for (var signing_path in assocSignersByPath){
					var signerInfo = assocSignersByPath[signing_path];
					if (signerInfo.address && arrMyMemberAddresses.indexOf(signerInfo.address) >= 0)
						signerInfo.device_address = device.getMyDeviceAddress();
				}
			}
			handleResult();
		}
	);
}

function handleNewSharedAddress(body, callbacks){
	if (!ValidationUtils.isArrayOfLength(body.definition, 2))
		return callbacks.ifError("invalid definition");
	if (typeof body.signers !== "object" || Object.keys(body.signers).length === 0)
		return callbacks.ifError("invalid signers");
	try {
		var addr = objectHash.getChash160(body.definition);
	}
	catch (e) {
		return callbacks.ifError("invalid definition: " + e);
	}
	if (body.address !== addr)
		return callbacks.ifError("definition doesn't match its c-hash");
	for (var signing_path in body.signers){
		var signerInfo = body.signers[signing_path];
		if (signerInfo.address && signerInfo.address !== 'secret' && !ValidationUtils.isValidAddress(signerInfo.address))
			return callbacks.ifError("invalid member address: " + JSON.stringify(signerInfo.address));
	}
	const assocDefinitionAddresses = extractAddressPathsFromDefinition(body.definition);
	for (let signing_path in body.signers) {
		const signerInfo = body.signers[signing_path];
		if (assocDefinitionAddresses[signing_path] !== signerInfo.address)
			return callbacks.ifError("signer address at path " + signing_path + " doesn't match definition");
	}
	for (let def_path in assocDefinitionAddresses) {
		if (!body.signers[def_path])
			return callbacks.ifError("no signer for definition address at path " + def_path);
	}
	determineIfIncludesMeAndRewriteDeviceAddress(body.signers, function(err){
		if (err)
			return callbacks.ifError(err);
		validateAddressDefinition(body.definition, function(err){
			if (err)
				return callbacks.ifError(err);
			addNewSharedAddress(body.address, body.definition, body.signers, body.forwarded, callbacks.ifOk);
		});
	});
}
