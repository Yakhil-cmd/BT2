### Title
Autonomous Agent could be triggered a second time by the same unit, allowing malicious re-accrual of state/balances before the `pemCurvesFixMci` guard - (File: `aa_composer.js`)

### Summary
The Ajna report describes a function that could be called multiple times to inflate an accrued value (interest) because nothing prevented repeated invocation. The analogous class of bug in ocore is a *primary AA trigger being processed more than once for the same triggering unit*, which would let an AA's state-update logic (`var[...] += ...`, balance accounting, issuance counters, etc.) execute repeatedly for what should be a single economic event.

### Finding Description
`handleTrigger()` explicitly guards against this exact scenario with a check that only exists from a certain upgrade point (`mci >= constants.pemCurvesFixMci`): [1](#0-0) 

```
if (trigger.unit !== constants.GENESIS_UNIT && !trigger_opts.bAir && storage.assocStableUnits[trigger.unit].count_aa_responses && mci >= constants.pemCurvesFixMci)
    return bounce('a second primary trigger from the same unit is not allowed');
```

This check exists precisely because, before `pemCurvesFixMci` (and for any code path that does not go through it), the same triggering unit could cause `handlePrimaryAATrigger()` to run more than once against the same AA address, re-executing the AA's `state` messages (e.g., `var['count'] += 1`, `var['balance_x'] += amount`, `var['mm_asset_outstanding'] += issue_amount`), thereby accruing state that should only be updated once per unit — directly analogous to the "interest accrued multiple times" bug class in the report.

The trigger dispatch path builds candidate AA triggers per (mci, unit, address) tuple with a `SELECT DISTINCT`: [2](#0-1) 

and `handleAATriggers()` iterates over rows from the `aa_triggers` table and invokes `handlePrimaryAATrigger` for each row: [3](#0-2) 

`getTrigger()` aggregates all payment outputs from a single unit to the receiving AA address into one `trigger.outputs[asset]` total: [4](#0-3) 

So, absent the `count_aa_responses`-based guard, a unit that (for any reason — duplicate `aa_triggers` row insertion, node restart/retry inserting the trigger again, or historical pre-fix behavior) causes `handlePrimaryAATrigger` to be invoked twice for the same `(unit, address)` pair would re-run the full AA state-update logic a second time using the *same* trigger data, effectively doubling any `+=`/`-=` state accounting that assumes "one trigger unit = one state update." This is the same root-cause pattern as the reported issue: a state-mutating function reachable without protection against repeated execution for the same logical event.

### Impact Explanation
If a primary trigger were processed twice against the same AA, any AA that tracks balances, shares, debts, or supply via state variables incremented per trigger (e.g. `var['mm_asset_outstanding'] += $issue_amount` in a market-maker AA, or `var[$key] = var[$key] + trigger.output[[asset=...]]` in a bank AA as seen in the test fixtures) would double-count the deposit/issuance while only receiving the funds once. This directly causes AA fund loss/insolvency (the AA would think it owes/holds more than it actually received) — a concrete instance of "AA fund loss or freezing" per the Validate criteria.

### Likelihood Explanation
The presence of the explicit guard (`'a second primary trigger from the same unit is not allowed'`) gated by `mci >= constants.pemCurvesFixMci` is strong evidence that ocore's own developers identified and fixed a real double-trigger condition. Without visibility into every historical code path removed at `pemCurvesFixMci` and whether any other path (e.g., dry-run/light-client-served AA evaluation, or bAir speculative execution) still lacks this check, the exact current-day reachability of a genuine double-trigger from user input cannot be fully confirmed with the available index. This is a known/fixed condition rather than a confirmed live 0-day in the current mainline; however, it is documented directly in the source as the fix for a previously-existing vulnerability class matching the report.

### Recommendation
Verify that the `count_aa_responses` check at `aa_composer.js:1861` is applied unconditionally (not gated behind `mci >= constants.pemCurvesFixMci`) for all trigger-processing paths, including `bAir`/dry-run speculative execution and any light-wallet or getter-simulation code paths, so that no code path can execute a primary AA trigger's state-mutating messages more than once for the same triggering unit.

### Proof of Concept
Not independently reproducible from static analysis alone — the vulnerability's reachability window is bounded by `constants.pemCurvesFixMci`, and the exact conditions that previously allowed a duplicate `aa_triggers` row/duplicate primary trigger dispatch could not be fully traced within the indexed code (only `main_chain.js`'s `handleAATriggers` insertion via `SELECT DISTINCT` and `aa_composer.js`'s guard were available). A Devin session with full repo/git-history access would be needed to pinpoint the exact pre-fix code path that produced duplicate primary triggers.

function getTrigger(objUnit, receiving_address) {
	var trigger = { address: objUnit.authors[0].address, unit: objUnit.unit, outputs: {} };
	if ("max_aa_responses" in objUnit)
		trigger.max_aa_responses = objUnit.max_aa_responses;
	objUnit.messages.forEach(function (message) {
		if (message.app === 'data' && !trigger.data) // use the first data message, ignore the subsequent ones
			trigger.data = message.payload;
		else if (message.app === 'payment' && message.payload) {
			var payload = message.payload;
			var asset = payload.asset || 'base';
			payload.outputs.forEach(function (output) {
				if (output.address === receiving_address) {
					if (!trigger.outputs[asset])
						trigger.outputs[asset] = 0;
					trigger.outputs[asset] += output.amount; // in case there are several outputs
				}
			});
		}
	});
	if (Object.keys(trigger.outputs).length === 0)
		throw Error("no outputs to " + receiving_address);
	return trigger;
}
