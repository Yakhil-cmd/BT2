### Title
CCMenu token scoped to one stack (or even the auto-created "CCMenu Client" token) authorises reading CI status of any stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides `stack` to resolve `Stack.from_param!(params[:stack_id])` directly, bypassing the `stacks` scoping method inherited from `BaseController` that is supposed to restrict a token to `current_api_client.stack_id`. Combined with `Shipit::CCMenuUrlController#client` never setting `stack:` when minting the "CCMenu Client" `ApiClient`, any token with `read:stack` — whether globally scoped or nominally scoped to one stack — can fetch the CCMenu XML for every stack in the installation, not just the one the URL was generated for.

### Finding Description
The claimed binding is: `token.stack_id == stack_A.id` (the URL/token minted for stack A should only authorize stack A). In reality two independent failures break this:

1. `Shipit::CCMenuUrlController#client` (app/controllers/shipit/ccmenu_url_controller.rb:15-18) does:
```ruby
def client
  @client ||= ApiClient.create_with(permissions: %w[read:stack])
                       .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
end
```
`stack:` is never supplied, so `ApiClient#stack_id` stays `nil` (`belongs_to :stack, optional: true`, app/models/shipit/api_client.rb:8). Per `Shipit::Api::BaseController#stacks` (app/controllers/shipit/api/base_controller.rb:74-76):
```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end
```
a nil `stack_id` makes `stacks` resolve to `Stack.all`.

2. Even if (1) were fixed, `Shipit::Api::CCMenuController` never uses `stacks`/`stack` from `BaseController` — it redefines `stack` itself (app/controllers/shipit/api/ccmenu_controller.rb:29-31):
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
```
This resolves directly against `Stack`, completely ignoring any `current_api_client.stack_id` restriction. So this endpoint's authorization only checks the permission string (`read:stack` via `require_permission :read, :stack`) and never checks which stack the token is bound to. Every `read:stack` token — including intentionally stack-scoped ones such as fixture `here_come_the_walrus` (`stack: shipit`, test/fixtures/shipit/api_clients.yml:12-17) — can read `/api/stacks/*stack_id/ccmenu` for any stack, not only its own.

Attack flow: a legitimate Shipit user visits stack A's settings page and clicks "Fetch URL", which calls `CCMenuUrlController#fetch` and embeds `client.authentication_token` in the URL (app/controllers/shipit/ccmenu_url_controller.rb:7-11). That URL is commonly published publicly (CI badge/dashboard link). Anyone who obtains it — the unprivileged attacker, with no Shipit session — can replay the token against `GET /api/stacks/*stack_B/ccmenu?token=...` for any other stack B and receive stack B's CI status (name, activity, last build status/label/time, web URL), because `CCMenuController#authenticate_api_client` only requires `ApiClient.authenticate(params[:token])` to succeed (app/controllers/shipit/api/ccmenu_controller.rb:33-36) and its own `stack` method does not check scoping.

Existing guards do not stop this: `require_permission :read, :stack` only calls `current_api_client.check_permissions!(:read, :stack)` (permission string check), not a stack-identity check; there is no `force_github_authentication` on this API endpoint by design (it's meant to be polled without a session); `Stack.from_param!` has no ownership/token filter.

### Impact Explanation
An attacker holding any leaked/observed `read:stack` CCMenu token (no session, no other credentials) can read CI/build status (name, activity, last build status/label/time, web URL) for every stack hosted by the Shipit instance, not just the one the token/URL was created for. This is a cross-tenant confidentiality leak of stack state and matches the High category "unauthenticated read of stack state ... via SSRF-adjacent scoping failure" — it is not RCE or credential exfiltration, so Critical categories (command execution, token/secret leak, cross-repo mutation) do not apply. The exposure is limited to CI status metadata, is repeatable indefinitely per stack (tokens don't expire), and scales to every stack in the installation with a single captured token.

### Likelihood Explanation
No special Shipit privileges or secrets are required by the attacker; only knowledge of one valid CCMenu URL/token, which is routinely made public as a CI badge or shared with third-party CCMenu-compatible dashboards. Any Shipit installation using the built-in "Fetch URL" CCMenu feature is affected. Preconditions are: (a) `ApiClient` must have `read:stack` permission (true for the auto-created CCMenu Client and true for many manually scoped clients), and (b) the target endpoint is `Shipit::Api::CCMenuController#show`. No rate limiting or additional checks impede repeated replay against arbitrary `stack_id` values.

### Recommendation
- In `Shipit::Api::CCMenuController`, remove the local `stack` override and use the inherited, scope-aware `stack`/`stacks` method from `BaseController` so a token's `stack_id` (when set) restricts which stack can be queried.
- In `Shipit::CCMenuUrlController#client`, pass `stack:` (the target stack) into `ApiClient.create_with(...)` so each CCMenu Client token is bound to a single stack, and consider making each token unique per stack (e.g., include stack id in `find_or_create_by!` key) rather than sharing one "CCMenu Client" token across all stacks fetched by a user.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb (new test)
test "a token scoped to one stack cannot read another stack's ccmenu status" do
  stack_a = shipit_stacks(:shipit)
  stack_b = Stack.create!(repository: Repository.new(owner: 'foo', name: 'bar'), branch: 'main')

  scoped_client = ApiClient.create!(
    creator: shipit_users(:walrus),
    name: 'Scoped CCMenu Client',
    stack: stack_a,
    permissions: %w[read:stack]
  )

  # Binding under test: token authorised only for stack_a
  assert_equal stack_a.id, scoped_client.stack_id

  get :show, params: { stack_id: stack_b.to_param, token: scoped_client.authentication_token }

  # Expected: should be forbidden/not found because token is scoped to stack_a, not stack_b
  assert_not_equal 200, response.status # FAILS today: returns 200 with stack_b's CI data
end
```
Additionally, a unit test on `Shipit::CCMenuUrlController#client` should assert `client.stack_id == stack.id` after calling `fetch`, which fails today because `stack:` is never passed to `create_with`. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)
