## Title
Unbounded AA output accumulation enables DoS / fund-freezing of Autonomous Agents via dust-output spam - ([File: aa_composer.js])

### Summary
`aa_composer.js`'s `completePaymentPayload()` selects unspent outputs belonging to a triggered AA by running unbounded SQL queries (`readStableOutputs` / `readUnstableOutputsSentByAAs`) and iterating **all** returned rows synchronously in `iterateUnspentOutputs()` to accumulate enough balance for the AA's outgoing payment. Because `validatePaymentInputsAndOutputs()` explicitly **skips** the "too many inputs" limit for AA-generated payments, an attacker can cheaply spam an AA address with many small (non-dust) outputs, forcing every subsequent AA response that needs to spend its balance to walk and include an ever-growing, effectively unbounded, list of inputs — mirroring the reported crab-netting bug class where cheap repeated pushes to an unbounded array eventually break every function that must walk it.

### Finding Description
In `aa_composer.js`, when an AA needs to construct an outgoing payment (e.g., in response to a trigger, or a `send_all` output), `completePaymentPayload()` calls: [1](#0-0) 

which queries **all** unspent outputs of the AA's address with no `LIMIT`, filtering out only base-asset outputs smaller than `FULL_TRANSFER_INPUT_SIZE` (documented as anti-dust protection): [2](#0-1) 

The rows are then walked in a plain synchronous `for` loop by `iterateUnspentOutputs()`, pushing every row into `payload.inputs` until the target amount is reached: [3](#0-2) 

Crucially, `validatePaymentInputsAndOutputs()` in `validation.js` enforces `MAX_INPUTS_PER_PAYMENT_MESSAGE` for normal units, but **explicitly bypasses this cap for AA-generated payments** (`objValidationState.bAA`): [4](#0-3) 

This means an attacker can post many separate payments of small-but-non-dust amounts (each just above `FULL_TRANSFER_INPUT_SIZE`, i.e. cheap dust that still passes the anti-dust filter) to a target AA address. None of these individual transfers are limited in count by the protocol (any user can send unlimited outputs to any address over time). When the AA is later triggered and needs to spend its balance (e.g. issuing a refund, `send_all`, or bounce-fee return), `completePaymentPayload()` must read and loop through the entire accumulated output set with no cap, producing a payment message with an arbitrarily large number of inputs — since the normal `MAX_INPUTS_PER_PAYMENT_MESSAGE` check does not apply to AA responses.

### Impact Explanation
This is directly analogous to the reported "Possible DoS in crab withdraws queue" bug class: a cheap, repeatable, attacker-controlled action grows an array that critical logic must later walk in full, without a hard limit, eventually breaking that logic. Here:
- The resulting AA response unit can grow to contain an extremely large number of inputs, producing an oversized unit that may fail to validate/broadcast, or take excessive time/resources to construct and process (`iterateUnspentOutputs` and the underlying unbounded SQL scan).
- Because the AA cannot successfully complete its response (unit too large / processing degraded), its funds become effectively **frozen** — the AA cannot spend or return its balance, and the trigger unit may repeatedly bounce or fail, denying legitimate users service from that AA.
- This satisfies the "AA fund loss or freezing" and "network unable to confirm new units" impact criteria for a High-severity DoS.

### Likelihood Explanation
Any unprivileged user can trigger this by simply sending many independent small payments (above the dust floor `FULL_TRANSFER_INPUT_SIZE`) to a known AA address — no special privileges, secret keys, or network-level compromise are required. The cost to the attacker scales linearly with the number of dust outputs (bounded only by normal transaction fees), while the cost imposed on the AA (and the network node executing it) scales with total accumulated outputs each time the AA needs to spend, since the cap that would normally bound this (`MAX_INPUTS_PER_PAYMENT_MESSAGE`) is bypassed for AA payments.

### Recommendation
- Enforce `MAX_INPUTS_PER_PAYMENT_MESSAGE` (or an AA-specific reasonable cap) for AA-generated payment messages as well, splitting the response into multiple messages/units if necessary rather than bypassing the limit entirely.
- Add a `LIMIT` to the `readStableOutputs` / `readUnstableOutputsSentByAAs` queries in `aa_composer.js` sized to the maximum number of inputs the resulting message could legally contain, and handle "not enough single-pass funds" by chunking across multiple response units.
- Consider raising the anti-dust floor or introducing a per-address maximum count of tracked spendable outputs that is enforced independent of amount, similar to the recommended `EnumerableMap`-style bounded structures in the original report.

### Proof of Concept
1. Deploy or identify an existing AA address `X`.
2. From an unprivileged wallet, send a large number (e.g. tens of thousands) of separate payments of `FULL_TRANSFER_INPUT_SIZE + 1` bytes each to `X` over time — each individually valid and cheap.
3. Trigger `X` in a way that causes it to construct an outgoing payment covering (or exceeding) its accumulated balance (e.g., a `send_all` response or bounce-fee refund).
4. Observe that `completePaymentPayload()`'s `readStableOutputs`/`iterateUnspentOutputs` walks the entire unbounded output set (per `aa_composer.js` lines 1102-1155), and that `validatePaymentInputsAndOutputs()` does not reject the resulting oversized `inputs` array because `objValidationState.bAA` is true (`validation.js` lines 2136-2138), leading to a failed/oversized unit and a frozen or persistently bouncing AA.
