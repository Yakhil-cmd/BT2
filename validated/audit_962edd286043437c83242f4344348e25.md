### Title
Cross-repository commit status forgery via unscoped `Commit.where(sha:)` in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits solely by `sha`, with no scoping to the repository that authenticated the webhook. Since GitHub SHAs are not globally unique to a single repository (identical trees/parents produce identical SHA1s, and duplicate SHAs can trivially occur via cross-repo cherry-pick, rebase-onto-same-parent, or copying a shared open-source commit), an attacker who owns `attacker/evil` and can legitimately trigger their own `status` webhook can cause a status write onto a commit row belonging to `victim/target`'s stack.

### Finding Description
The broken binding: `payload.dig('repository','full_name') == repository_of(every Commit row mutated by the handler)`. This holds for every other handler that scopes through `stacks` (`Repository.from_github_repo_name(repository_name)&.stacks`, defined in `Shipit::Webhooks::Handlers::Handler#stacks`, `app/models/shipit/webhooks/handlers/handler.rb:32-38`), but `StatusHandler` never calls `stacks` at all:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
(`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`)

`WebhooksController#verify_signature` only proves the request was signed for the org identified by `repository_owner` (`params.dig('repository','owner','login')`) — it authenticates *which repository sent the webhook*, it does not constrain *which commit rows the handler is allowed to touch*. `ExplicitParameters` schema only validates types/presence of `sha`/`state`/etc., not that the SHA belongs to the claimed repository. There is no additional guard anywhere in `Commit` or `StatusHandler` tying the query to `repository_name`.

Exploit flow:
1. Attacker owns `attacker/evil`, which is also configured as (or associated with) a Shipit stack, or simply owns a GitHub App/webhook integration pointed at Shipit for their own repo.
2. Attacker crafts a commit whose SHA1 collides with a real, unmerged commit sha already present in `victim/target`'s Shipit-tracked stack (achievable deterministically: cherry-pick the exact same diff onto an identical parent/tree/author/committer metadata, or copy a shared upstream commit both repos contain — this is not a hash collision, it's the same SHA1 input producing the same hash, fully attacker-controlled and repeatable).
3. Attacker's own CI (or a raw HTTP POST crafted with the attacker's legitimately known webhook secret for their own org) posts a `status` event: `{"sha": "<colliding sha>", "state": "success", "repository": {"full_name": "attacker/evil", "owner": {"login": "attacker"}}}`.
4. `verify_signature` succeeds because the signature is valid for `attacker`'s org.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, which returns **both** the attacker's own commit row and the victim's row (different `stack_id`, same `sha`).
6. `commit.create_status_from_github!(params)` is called on the victim's commit too, writing a `Status` record via `statuses.replicate_from_github!(stack_id, github_status)`, marking the victim commit "success" and potentially unblocking `deployable?`/`schedule_continuous_delivery` on the victim's stack.

### Impact Explanation
A payload authenticated only for `attacker/evil` mutates a `Commit`/`Status` row belonging to `victim/target`'s stack — this is exactly the "payload for one repository mutating another's stack/commit" category (Critical). Concretely: the victim's commit CI status is forged green by an entity with zero access to `victim/target`, and because `Commit#add_status` triggers `stack.schedule_merges` when `new_status.success?`, this can influence merge-queue/continuous-delivery decisions on the victim stack (`app/models/shipit/commit.rb:379-384`). This is repeatable at will against any stack that happens to contain a commit whose SHA the attacker can reproduce, and does not require any privilege beyond owning a GitHub repo with a working webhook.

### Likelihood Explanation
Preconditions: victim stack must contain an unmerged commit whose SHA the attacker can reproduce in their own repo (feasible via cherry-pick/rebase of an identical patch, or a shared upstream commit — no cryptographic collision required, just identical git object). Attacker cost is low: create/own a repo, configure Shipit webhook for it (or any repo whose org is registered in `Shipit.github_teams`/GitHub App install), and post the correlating status. No Shipit credentials, sessions, or API tokens are needed — signature verification is repo/org-scoped, not commit-scoped, so it does not prevent this.

### Recommendation
Scope the commit lookup in `StatusHandler#process` to the repository that authenticated the webhook, mirroring other handlers: query via `stacks.flat_map(&:commits).where(sha: params.sha)` (or add a `stack_id: stacks.pluck(:id)` filter), so a commit is only mutated if it belongs to a stack whose `Repository` matches `payload.dig('repository','full_name')`.

### Proof of Concept
```ruby
test "status webhook for attacker repo does not update commit belonging to a different stack" do
  victim_stack = shipit_stacks(:shipit)
  attacker_stack = shipit_stacks(:cyclimse)
  sha = "deadbeef" * 5

  victim_commit = victim_stack.commits.create!(sha: sha, message: "victim", author: shipit_users(:walrus))
  attacker_commit = attacker_stack.commits.create!(sha: sha, message: "attacker", author: shipit_users(:walrus))

  assert_equal 0, victim_commit.statuses.count
  assert_equal 0, attacker_commit.statuses.count

  Shipit::Webhooks::Handlers::StatusHandler.call(
    'sha' => sha,
    'state' => 'success',
    'context' => 'ci/attacker',
    'repository' => { 'full_name' => attacker_stack.github_repo_name, 'owner' => { 'login' => attacker_stack.github_repo_owner } }
  )

  assert_equal 1, attacker_commit.reload.statuses.count
  assert_equal 0, victim_commit.reload.statuses.count, "victim/target commit must not be mutated by attacker/evil's webhook"
end
```
This test demonstrates the current code fails the second assertion (`victim_commit.reload.statuses.count` becomes `1`), proving the equality `payload.repository == repository_of(mutated_commit)` is violated.
