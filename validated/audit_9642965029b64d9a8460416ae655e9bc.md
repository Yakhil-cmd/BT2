### Title
Censorable ERC20 Token Permanently Locks Bridged Assets in `handleERC20Transfer` — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

---

### Summary

`BridgeTransferERC20.handleERC20Transfer` performs all nonce-accounting state updates before executing the token transfer. If the ERC20 token reverts on `transfer` (e.g., USDC/USDT blacklisting the recipient, or an upgradeable token turned malicious), the entire transaction reverts. Because there is no mechanism to skip or rescue a stuck nonce, the user's assets — already burned or locked on the source chain — are permanently undeliverable on the destination chain.

---

### Finding Description

`handleERC20Transfer` in `BridgeTransferERC20.sol` follows this execution order:

```
_lowerHandleNonceCheck(nonce)          // guard
_voteValueTransfer(nonce)              // operator quorum
_setHandledRequestTxHash(txHash)       // marks tx as handled
handleNoncesToBlockNums[nonce] = blk   // records block
_updateHandleNonce(nonce)              // advances lowerHandleNonce
emit HandleValueTransfer(...)          // event
IERC20(token).safeTransfer(_to, value) // ← actual asset delivery
``` [1](#0-0) 

If `safeTransfer` reverts (e.g., USDC blacklists `_to`), Solidity rolls back the entire transaction — including all state updates. The nonce is never marked handled, `handleNoncesToBlockNums[nonce]` is never set, and `lowerHandleNonce` never advances past this nonce.

`_updateHandleNonce` advances `lowerHandleNonce` only through a consecutive filled sequence:

```solidity
for (i = lowerHandleNonce; i <= limit && handleNoncesToBlockNums[i] > 0; i++) {
    recoveryBlockNumber = handleNoncesToBlockNums[i];
    ...
}
lowerHandleNonce = i;
``` [2](#0-1) [3](#0-2) 

Because nonce N's slot is never filled, `lowerHandleNonce` is permanently stuck at N. The `recoveryBlockNumber` also stalls, causing the off-chain bridge relay to keep replaying from the same block indefinitely.

The same pattern exists in `handleKLAYTransfer` where `_to.call.value(_value)("")` can revert if `_to` is a contract that rejects KLAY: [4](#0-3) 

---

### Impact Explanation

- **Permanent asset lock**: On the source chain, the user's tokens were already burned (`modeMintBurn`) or locked in the bridge contract when `RequestValueTransfer` was emitted. On the destination chain, delivery can never complete.
- **Bridge nonce stall**: `lowerHandleNonce` cannot advance past the stuck nonce, so `recoveryBlockNumber` is frozen and the relay replays the same failing block forever.
- **No admin escape hatch**: The bridge exposes `setRunningStatus`, `deregisterToken`, and `lockToken`, but none of these allow skipping a stuck nonce or rescuing funds already committed to a specific nonce. [5](#0-4) 

---

### Likelihood Explanation

USDC and USDT — both widely bridged assets — implement address blacklisting. If a user's destination address is blacklisted after the source-chain `RequestValueTransfer` is confirmed but before `handleERC20Transfer` executes, the transfer is permanently stuck. Upgradeable tokens can also have their `transfer` logic changed post-registration. No special privilege is required to trigger this: any user whose address gets blacklisted by the token issuer causes the condition. [6](#0-5) 

---

### Recommendation

1. **Add a nonce-skip / rescue function** callable by the bridge owner that marks a nonce as handled without executing the token transfer, allowing `lowerHandleNonce` to advance and releasing subsequent transfers.
2. **Wrap the token transfer in a try/catch** (Solidity ≥0.6; the bridge uses 0.5.6, so use a low-level call with a success check) and, on failure, store the amount in a claimable mapping rather than reverting the entire transaction.
3. **Alternatively**, move all state updates (nonce marking, `_updateHandleNonce`) to after a successful transfer, so a failed transfer leaves the nonce unspent and retryable with a different recipient address.

---

### Proof of Concept

1. Deploy the bridge in non-mintBurn mode with USDC as the registered token.
2. User on source chain calls `requestERC20Transfer`; tokens are locked in the source bridge; `RequestValueTransfer(nonce=5)` is emitted.
3. USDC blacklists the user's destination address.
4. Operators call `handleERC20Transfer(..., nonce=5, ...)` on the destination bridge.
5. `_setHandledRequestTxHash` and `_updateHandleNonce` execute, then `IERC20(usdc).safeTransfer(blacklistedAddr, value)` reverts.
6. The entire transaction reverts; nonce 5 is never marked handled.
7. `handleNoncesToBlockNums[5]` remains 0; `lowerHandleNonce` stays at 5.
8. All subsequent nonces (6, 7, …) can be individually handled but `lowerHandleNonce` never advances past 5, so `recoveryBlockNumber` is frozen.
9. The user's USDC on the source chain is permanently locked; no admin function can rescue it. [7](#0-6) [8](#0-7)
