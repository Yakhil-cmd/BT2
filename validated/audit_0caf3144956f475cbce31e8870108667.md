## Title
Webhook signature verified against wrong GitHub App secret due to unauthenticated `organization` field, enabling cross-organization push spoofing - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In multi-org Shipit deployments, `WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to use for HMAC verification based on `repository_owner`, a value read directly out of the *unauthenticated* JSON body, rather than out of anything the signature itself covers unambiguously as "this app". This mirrors the Vyper `slice()` class of bug: a bounds/authorization check is performed using one interpretation of attacker-controlled input, while the data actually consumed downstream is taken from a different field of the same untrusted payload, letting the two diverge.

### Finding Description
`verify_signature` picks the app/secret to check against like this: [1](#0-0) [2](#0-1) 

`repository_owner` is derived purely from `params.dig('repository','owner','login')` or `params.dig('organization','login')` — both are plain fields inside the JSON body the attacker controls, before the signature has been validated. `Shipit.github(organization: repository_owner)` then looks up a *per-organization* `webhook_secret` from `github_app_config` [3](#0-2) .

Once the request passes verification, `create` re-parses the same raw body and dispatches it to handlers such as `PushHandler`, whose `Handler#stacks`/`repository_name` methods independently read `payload.dig('repository', 'full_name')` — a *different* JSON key than the one used to select the verifying secret: [4](#0-3) [5](#0-4) 

The binding that should hold is: `organization whose secret verified the payload == organization that owns the repository the handler actually acts on`. Because the verification step and the action step read two independently-controlled fields (`repository.owner.login`/`organization.login` vs `repository.full_name`) from the same unsigned JSON body, an attacker who legitimately controls (or has leaked) the webhook secret for *any one* configured organization in a multi-org install can forge a payload whose `repository.owner.login` matches that org (so `verify_signature` succeeds using that org's secret) while `repository.full_name` names a repository belonging to a *different* org/stack. `Repository.from_github_repo_name` then resolves stacks purely by `owner/name` parsed out of `full_name`, with no cross-check against the organization used to authenticate the request [6](#0-5) .

Before: `verify_signature` and the handler both effectively assume `repository.owner.login == repository.full_name`'s owner, an invariant enforced by GitHub itself for genuine webhooks, but which is not re-checked by Shipit.
After (attack): the two fields can be set independently since nothing in the signed payload check ties them together — the signature is only over the raw bytes of the body, and the org used to select the verification key is chosen from that same forgeable body.

### Impact Explanation
If a lower-privilege organization's webhook secret is compromised (or, in setups where an org admin can view/rotate their own `webhook_secret`, is otherwise obtainable by a party who is unprivileged with respect to a *different* organization's stacks), that secret can be used to sign a payload that authenticates as "org A" while acting on "org B"'s repository/stack. This can trigger `GithubSyncJob`/`sync_github` on an unrelated stack, spoof commit `status`/`check_suite` results, or manipulate `membership`/`pull_request` state for teams and repositories outside the boundary the secret was meant to authorize — a cross-repository/cross-organization write via a webhook the target organization never actually sent, which crosses the "organization authenticated vs. repository written" trust boundary called out in scope.

### Likelihood Explanation
This only matters for multi-organization Shipit deployments (`Shipit.github_organizations` with more than one configured app/secret) — single-org / legacy config installs use one global secret and aren't exposed to this specific field confusion. Exploitation requires the attacker to already hold a valid webhook secret for at least one configured organization, which is a real but non-trivial precondition (webhook secrets are meant to be known only to the app owner side, yet in a shared multi-tenant Shipit install they are inherently distributed across multiple less-trusted organization owners). No repository write access, GitHub App private key, or Shipit user session is required — only a webhook secret for *one* org.

### Recommendation
After signature verification succeeds, re-derive and cross-validate that the organization/app whose secret matched is the same organization implied by `repository.full_name` (or whichever field the handler will actually use) before dispatching to handlers. Alternatively, compute `repository_owner` from a single canonical field and have `Handler#repository_name` reuse that same value instead of independently re-reading `repository.full_name`, so verification and action are always bound to the same field.

### Proof of Concept
1. Deploy Shipit with two configured GitHub orgs, `orgA` and `orgB`, each with its own `webhook_secret` (`secretA`, `secretB`).
2. Attacker controls/knows `secretA` (e.g., is the legitimate owner of `orgA`'s GitHub App webhook config, or it has leaked).
3. Attacker crafts a JSON push payload where `repository.owner.login = "orgA"` and `organization.login = "orgA"`, but `repository.full_name = "orgB/some-repo"`.
4. Attacker signs the raw JSON body with `secretA` and sets `X-Hub-Signature` accordingly, then POSTs to `/webhooks`.
5. `verify_signature` calls `Shipit.github(organization: "orgA")`, which succeeds because the signature matches `secretA`.
6. `create` dispatches to `PushHandler`, whose `repository_name` reads `repository.full_name` = `"orgB/some-repo"`, resolving and acting on `orgB`'s stack — despite the request only ever being authenticated for `orgA`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
