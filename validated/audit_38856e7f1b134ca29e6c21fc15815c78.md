### Title
Webhook authentication is bound to `repository.owner.login`, but the action performed is bound to `repository.full_name` — cross-repository/cross-organization webhook forgery when any configured organization has no `webhook_secret` - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the request against using `repository.owner.login` (falling back to `organization.login`), while every webhook `Handler` subsequently selects which `Repository`/`Stack` to act upon using the completely independent `repository.full_name` field from the *same* attacker-supplied JSON body. Because `GitHubApp#verify_webhook_signature` treats a missing `webhook_secret` as automatically verified, an attacker who knows (or guesses) that any organization configured on the Shipit instance has no `webhook_secret` set can forge a webhook claiming that owner, while pointing `repository.full_name` at a different, unrelated (and properly secreted) repository/stack to trigger real writes on it.

### Finding Description
Signature verification happens here: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end
...
def repository_owner
  # Fallback to the organization sub-object if repository isn't included in the payload
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

The GitHub App used to check the signature is selected purely from `repository.owner.login`/`organization.login`. If that organization's config has no `webhook_secret` set (a state the engine explicitly documents and ships as a valid/example configuration, e.g. `webhook_secret: # nil`), the check is a no-op:

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [3](#0-2) 

Sample configs in this engine ship exactly this pattern (secret intentionally left blank per-org), showing it is a supported deployment shape rather than a theoretical edge case: [4](#0-3) 

Meanwhile, once verification (trivially) passes, `WebhooksController#create` parses the same JSON body and dispatches it to event handlers: [5](#0-4) 

Every handler resolves the target `Repository`/`Stack` using a *different* field — `repository.full_name` — with no cross-check against `repository.owner.login`/the organization used for authentication:

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [6](#0-5) 

For example, `PushHandler#process` uses that mismatched-binding `stacks` lookup to trigger a real GitHub sync of the target stack based on attacker-supplied `after` sha: [7](#0-6) 

And `StatusHandler#process` writes a forged commit status (state/description/target_url) onto any existing commit matching an attacker-chosen `sha`, independent of which repository or org that commit actually belongs to: [8](#0-7) 

**Binding broken (as an equality):** `organization authenticated (repository.owner.login / organization.login, checked against that org's webhook_secret)` ≠ `repository acted upon (repository.full_name, used to resolve Stack/Repository and perform writes)`.

- Before the PR/attack: only a party holding an organization's actual `webhook_secret` could produce a validly-signed webhook that would be accepted and acted upon for repositories under that organization.
- After exploitation: any unauthenticated network attacker who identifies one organization on the instance with no `webhook_secret` configured can send an arbitrarily-signed (or even garbage-signed) webhook naming that organization as `repository.owner.login`, then set `repository.full_name` to target an entirely different repository/stack (belonging to an organization that *does* have a secret configured) and have handlers act on it as if it were a legitimate, verified webhook from GitHub.

### Impact Explanation
This crosses the "cross-repository writes" / "unauthorized deploy" bar: `PushHandler` can force a `GithubSyncJob` to sync arbitrary commits into a target stack's history, and `StatusHandler` can write arbitrary/forged commit statuses (e.g. marking unsafe commits as passing CI), which is exactly the kind of state that gates whether a commit is deployable. `MembershipHandler` and `pull_request` handlers similarly act on data keyed off `repository.full_name`/team data without owner-org cross-validation, letting an attacker manipulate team/user records or review-stack state tied to a repository they were never authenticated for.

### Likelihood Explanation
Requires only that one organization configured on the Shipit instance has no `webhook_secret` set — a state the engine's own setup docs mark as "optional" and ships example configs demonstrating (`webhook_secret: # nil`). No repository write access, no `ApiClient` token, and no session are needed — only knowledge (or a guess) of that organization's login name and any target repository's `full_name`, both of which are typically public/discoverable GitHub identifiers.

### Recommendation
Bind authentication and action to the same field: after verifying the signature for the resolved organization, re-derive/validate that `repository.full_name`'s owner segment matches the `repository_owner`/`organization.login` used to select the `webhook_secret`, and reject the webhook if they diverge. Additionally, do not treat a blank/unset `webhook_secret` as an automatic pass in multi-tenant configurations — require an explicit "webhooks disabled" flag instead of silently returning `true` from `verify_webhook_signature` when `webhook_secret` is blank.

### Proof of Concept
1. Configure Shipit with two organizations: `TrustedOrg` (has a `webhook_secret`) and `NoSecretOrg` (no `webhook_secret`, per the documented "optional" setting).
2. As an unauthenticated attacker, POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "NoSecretOrg" },
    "full_name": "TrustedOrg/some-private-repo"
  }
}
```
No `X-Hub-Signature` header, or any arbitrary value, is required.
3. `verify_signature` resolves `Shipit.github(organization: "NoSecretOrg")`, whose `verify_webhook_signature` returns `true` unconditionally since `webhook_secret` is blank.
4. `PushHandler` resolves `stacks` via `Repository.from_github_repo_name("TrustedOrg/some-private-repo")`, and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on that stack — a stack belonging to the properly-secured `TrustedOrg`, despite the attacker never possessing `TrustedOrg`'s webhook secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
