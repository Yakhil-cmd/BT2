This confirms the vulnerable binding. The signature verification and secret selection are keyed on `repository_owner` (`params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`) in `app/controllers/shipit/webhooks_controller.rb:59-62`, while the actual Stack/Repository acted upon by every handler is looked up from a completely different, unverified field: `payload.dig('repository', 'full_name')` in `app/models/shipit/webhooks/handlers/handler.rb:36-38`, which feeds `Repository.from_github_repo_name` in `app/models/shipit/repository.rb:53-56`. Nothing ties these two fields together after the signature check passes.

### Title
Webhook signature is verified against `repository.owner.login`, but the Stack that is written is looked up from the unrelated `repository.full_name` field - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to use for HMAC verification based on `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (or `organization.login`) [1](#0-0) . Once the signature check passes, `WebhooksController#create` dispatches the entire raw JSON body — including a `repository.full_name` field that was never part of the equality checked during signature selection — to the event handlers [2](#0-1) . Every handler resolves the target `Stack` purely from `payload.dig('repository', 'full_name')` [3](#0-2) , via `Repository.from_github_repo_name`, which just splits that string on `/` and looks up any matching `Repository` row, regardless of owner [4](#0-3) .

### Finding Description
The binding that should hold is: `organization authenticated by verify_webhook_signature == owner of the repository acted upon by the handler`. In practice these are two independent payload reads:
- Authentication side: `repository_owner` from `params.dig('repository', 'owner', 'login')` [1](#0-0) , used solely to pick which `GitHubApp`/`webhook_secret` config entry to HMAC-verify against, via `Shipit.github(organization:)` and `github_app_config` [5](#0-4) .
- Action side: `repository.full_name` from the same JSON body [6](#0-5) , used to find the `Stack`/`Repository` that the handler will mutate (e.g. enqueue `GithubSyncJob`, create commit `Status`, create/delete `Membership`, close pull requests, etc.).

Because Shipit supports multiple GitHub Apps, one per organization, each configured with its own `webhook_secret` [7](#0-6) , an attacker who controls (or creates) their own GitHub organization/App installed on Shipit knows their own organization's legitimate `webhook_secret`. That attacker can freely craft an HTTP POST to `/webhooks` where:
- `repository.owner.login` (or `organization.login`) is set to their own org, so `verify_signature` picks their own app's secret and the HMAC they compute with it passes [8](#0-7) .
- `repository.full_name` is set to an arbitrary `victim-org/victim-repo` string that is unrelated to the field used for authentication.

Since `verify_webhook_signature` only checks the raw body bytes against a valid HMAC, and the attacker computed that HMAC themselves over the exact payload they crafted (full_name included), the signature is valid for the whole payload — the check never binds `repository.owner.login` to `repository.full_name`. `Handler#repository_name`/`Repository.from_github_repo_name` then happily resolves and acts on the victim's `Repository`/`Stack` [4](#0-3) .

### Impact Explanation
This breaks the "organization authenticated versus repository written" trust binding explicitly called out as in-scope. Depending on which event is spoofed:
- `push` triggers `GithubSyncJob` against the victim stack's expected head sha, letting the attacker desynchronize commit tracking on a repo they don't own.
- `status`/`check_suite` handlers write fake commit `Status`/check-run state for the victim's commits (`StatusHandler`, `CheckSuiteHandler`), which can be leveraged to make merge/deploy safety checks in the victim's Shipit stack pass when they should not.
- `pull_request` handlers close/label/provision review stacks belonging to the victim repository.

Since Shipit's merge-queue and deploy gating rely on commit `Status`/check-run state recorded via these webhooks, forging status/check_suite events for a repository the attacker does not control can lead to an unauthorized merge or deploy being greenlit for that victim stack — matching the "unauthorized deploy, rollback or merge" High-impact criterion.

### Likelihood Explanation
Requires only that: (1) Shipit is configured with the multi-organization GitHub App schema (documented and supported, `lib/shipit.rb:182-200`, `docs/setup.md:182-209`), and (2) the attacker controls at least one organization/App installed on that same Shipit instance (e.g. via a legitimate but low-trust organization onboarded to a shared Shipit deployment). No repository write access to the victim repo, no GitHub App private key, and no Shipit session/API token is required — only knowledge of the attacker's own webhook secret, which they legitimately possess.

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler`), enforce that the repository/organization used to select the verification secret is the same one the handlers act upon — e.g. reject the webhook if `payload.dig('repository', 'full_name')`'s owner segment does not case-insensitively match `repository_owner`, or better, verify the signature using the GitHub App corresponding to the actual `Repository` record resolved from `full_name`, not from a value trusted before verification.

### Proof of Concept
1. Configure Shipit with two organizations, `AttackerOrg` and `VictimOrg`, each with its own GitHub App and `webhook_secret` (multi-org schema) [9](#0-8) .
2. Attacker (who owns `AttackerOrg`'s webhook secret) builds a `push` payload body:
```json
{
  "repository": { "owner": { "login": "AttackerOrg" }, "full_name": "VictimOrg/victim-repo" },
  "after": "<attacker-chosen-sha>"
}
```
3. Attacker computes `sha1=HMAC-SHA1(AttackerOrg_webhook_secret, body)` and sends it as `X-Hub-Signature`, with `X-Github-Event: push`.
4. `verify_signature` reads `repository_owner == "AttackerOrg"`, loads `AttackerOrg`'s `GitHubApp`, and `verify_webhook_signature` succeeds [8](#0-7) .
5. `create` dispatches the payload to `PushHandler`, which resolves `Repository.from_github_repo_name("victimorg/victim-repo")` and enqueues `GithubSyncJob` for `VictimOrg`'s stack [3](#0-2) , despite the signature only ever having been verified against `AttackerOrg`'s secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
