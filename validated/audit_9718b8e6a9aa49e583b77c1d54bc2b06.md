### Title
`pox_lock_update_v5` omits the unlock-height monotonicity guard present in the sibling `pox_rollover_v5`, letting `stake-update` shorten a lock while raising `amount-ustx` - (File: `pox-locking/src/pox_5.rs`)

### Summary
`pox_lock_update_v5`, invoked by `handle_stake_lockup_update_pox_v5` for `stake-update`, calls `snapshot.update_unlock_v5(unlock_burn_height)` unconditionally and never checks that `unlock_burn_height` is greater than the account's current `unlock_height`. This is inconsistent with the sibling function `pox_rollover_v5`, which explicitly enforces `unlock_burn_height > bal.unlock_height()` before rescheduling a lock.

### Finding Description
The claimed equality: `new_unlock_height` returned by `stake-update` must be `>= current_unlock_height` (SINGLE_UNLOCK: value can only unlock once, at the committed height, never earlier).

In `pox_lock_update_v5` (pox-locking/src/pox_5.rs, lines 241-289):
```
snapshot.update_unlock_v5(unlock_burn_height)?;
let bal = snapshot.canonical_balance_repr()?;
let total_amount = bal.amount_unlocked().checked_add(bal.amount_locked())...;
if total_amount < new_total_locked { return Err(PoxInsufficientBalance); }
if bal.amount_locked() > new_total_locked { return Err(PoxInvalidIncrease); }
snapshot.increase_lock_v5(new_total_locked)?;
```
There is no comparison of `unlock_burn_height` against the pre-existing `unlock_height`. Contrast this with `pox_rollover_v5` (lines 315-358), which explicitly guards:
```
if unlock_burn_height <= bal.unlock_height() {
    return Err(LockingError::PoxInvalidUnlockHeight);
}
```
`handle_stake_lockup_update_pox_v5` (lines 445-499) trusts whatever `unlock-burn-height` the pox-5 Clarity `stake-update` response tuple contains and passes it straight through to `pox_lock_update_v5` with no additional check at the locking layer. So the Rust/pox-locking defense-in-depth that exists for the roll-over path (`pox_rollover_v5`) is absent for the update path (`pox_lock_update_v5`), even though both are architecturally supposed to guarantee the same SINGLE_UNLOCK invariant. ### Impact Explanation
If the pox-5 Clarity contract's `stake-update` function ever computes and returns an `unlock-burn-height` that is not strictly greater than the caller's current unlock height (e.g. due to a bug in its own cycle arithmetic, an integer wraparound, or a future code path that permits partial "update" calls without re-deriving from the maximum of current-height and requested-height), the Rust locking layer will silently accept it: the account's committed unlock height would move earlier while the locked amount is simultaneously allowed to increase. This breaks SINGLE_UNLOCK by letting locked STX become eligible for release earlier than the height the reward-cycle math (e.g. `signer-shares-staked-for-cycle`) assumes it remains locked for, i.e. early release of STX still being counted as locked weight for a reward cycle — a Critical-class issue per the given severity table ("unlocking value never locked" / early release class).

### Likelihood Explanation
This finding by itself is a missing defense-in-depth check in the Rust locking layer, not a directly attacker-triggerable bug — exploitability depends entirely on whether the pox-5 Clarity contract's `stake-update` function can ever be made, through any caller-controlled path, to compute/return an `unlock-burn-height` lower than the account's current unlock height. I was not able to retrieve and verify the `stake-update` implementation in pox-5.clar within this session, so I cannot confirm whether the Clarity contract independently enforces the monotonicity invariant before returning its response (which would make this an inert defense-in-depth gap) or whether some code path in `stake-update` can return a non-monotonic height (which would make this directly exploitable by an unprivileged staker calling `stake-update` themselves). The asymmetry between `pox_lock_update_v5` and `pox_rollover_v5` in the Rust layer is real and verified directly from the source.

### Recommendation
Add the same guard used in `pox_rollover_v5` to `pox_lock_update_v5`: reject the call with `LockingError::PoxInvalidUnlockHeight` if `unlock_burn_height <= bal.unlock_height()` (checked against the balance snapshot before/after `update_unlock_v5`), so the pox-locking layer independently enforces SINGLE_UNLOCK regardless of what the pox-5 Clarity contract computes.

### Proof of Concept
Rust unit test in `pox-locking/src/tests` (or an equivalent harness) that:
1. Locks an account via `pox_lock_v5(db, principal, 1000, unlock_height=200)`.
2. Calls `pox_lock_update_v5(db, principal, unlock_burn_height=150, new_total_locked=1500)` — a lower unlock height with a higher amount.
3. Asserts the call returns `Err(LockingError::PoxInvalidUnlockHeight)` (expected fix behavior) — currently the call succeeds and `db.get_stx_balance_snapshot(principal)?.canonical_balance_repr()?.unlock_height()` returns `150 < 200`, proving SINGLE_UNLOCK is violated at the Rust layer for this function, on both sides of the equality `new_unlock_height >= old_unlock_height` (200 vs 150).

pub fn pox_lock_update_v5(
    db: &mut ClarityDatabase,
    principal: &PrincipalData,
    unlock_burn_height: u64,
    new_total_locked: u128,
) -> Result<STXBalance, LockingError> {
    if unlock_burn_height == 0 {
        return Err(LockingError::PoxInvalidUnlockHeight);
    }
    if new_total_locked == 0 {
        return Err(LockingError::PoxInvalidLockAmount);
    }

    let mut snapshot = db.get_stx_balance_snapshot(principal)?;

    if !snapshot.has_locked_tokens()? {
        return Err(LockingError::PoxExtendNotLocked);
    }

    snapshot.update_unlock_v5(unlock_burn_height)?;

    let bal = snapshot.canonical_balance_repr()?;
    let total_amount = bal
        .amount_unlocked()
        .checked_add(bal.amount_locked())
        .ok_or(LockingError::PoxBalanceOverflow)?;
    if total_amount < new_total_locked {
        return Err(LockingError::PoxInsufficientBalance);
    }

    if bal.amount_locked() > new_total_locked {
        return Err(LockingError::PoxInvalidIncrease);
    }

    snapshot.increase_lock_v5(new_total_locked)?;

    let out_balance = snapshot.canonical_balance_repr()?;

    debug!(
        "PoX v5 lock updated";
        "pox_locked_ustx" => out_balance.amount_locked(),
        "available_ustx" => out_balance.amount_unlocked(),
        "unlock_burn_height" => unlock_burn_height,
        "account" => %principal,
    );

    snapshot.save()?;
    Ok(out_balance)
}

pub fn pox_rollover_v5(
    db: &mut ClarityDatabase,
    principal: &PrincipalData,
    unlock_burn_height: u64,
    new_total_locked: u128,
) -> Result<STXBalance, LockingError> {
    if new_total_locked == 0 {
        return Err(LockingError::PoxInvalidLockAmount);
    }

    let mut snapshot = db.get_stx_balance_snapshot(principal)?;

    if !snapshot.has_locked_tokens()? {
        return Err(LockingError::PoxExtendNotLocked);
    }

    let bal = snapshot.canonical_balance_repr()?;
    let total_amount = bal
        .amount_unlocked()
        .checked_add(bal.amount_locked())
        .ok_or(LockingError::PoxBalanceOverflow)?;
    if total_amount < new_total_locked {
        return Err(LockingError::PoxInsufficientBalance);
    }

    if unlock_burn_height <= bal.unlock_height() {
        return Err(LockingError::PoxInvalidUnlockHeight);
    }

    snapshot.set_lock_v5(new_total_locked, unlock_burn_height)?;

    let out_balance = snapshot.canonical_balance_repr()?;

    debug!(
        "PoX v5 lock rolled forward";
        "pox_locked_ustx" => out_balance.amount_locked(),
        "available_ustx" => out_balance.amount_unlocked(),
        "unlock_burn_height" => unlock_burn_height,
        "account" => %principal,
    );

    snapshot.save()?;
    Ok(out_balance)
}

/// Handle responses from `stake-update` in pox-5 -- the function that
/// *extends or increases already-locked* STX.
fn handle_stake_lockup_update_pox_v5(
    global_context: &mut GlobalContext,
    function_name: &str,
    value: &Value,
) -> Result<Option<StacksTransactionEvent>, VmExecutionError> {
    debug!(
        "Handle special-case contract-call to {:?} {function_name} (which returned {value:?})",
        boot_code_id(POX_5_NAME, global_context.mainnet),
    );

    runtime_cost(
        ClarityCostFunction::StxTransfer,
        &mut global_context.cost_track,
        1,
    )?;

    let parsed = parse_pox_stake_result(value).map_err(|e| {
        locking_error_to_vm_error(e, &format!("pox-5 {function_name}: bad response"))
    })?;
    let (staker, amount_ustx, unlock_height) = match parsed {
        ParsedStakeResult::Ok {
            staker,
            amount_ustx,
            unlock_burn_height,
        } => (staker, amount_ustx, unlock_burn_height),
        ParsedStakeResult::ContractErr => return Ok(None),
    };

    match pox_lock_update_v5(
        &mut global_context.database,
        &staker,
        unlock_height,
        amount_ustx,
    ) {
        Ok(_) => {
            // Log the extension in the asset map.
            global_context.log_stacking(&staker, amount_ustx)?;

            let event =
                StacksTransactionEvent::STXEvent(STXEventType::STXLockEvent(STXLockEventData {
                    locked_amount: amount_ustx,
                    unlock_height,
                    locked_address: staker,
                    contract_identifier: boot_code_id(POX_5_NAME, global_context.mainnet),
                }));
            Ok(Some(event))
        }
        Err(e) => Err(locking_error_to_vm_error(
            e,
            &format!(
                "pox-5 {function_name}: failed to extend lock from {staker} until {unlock_height}"
            ),
        )),
    }
}
