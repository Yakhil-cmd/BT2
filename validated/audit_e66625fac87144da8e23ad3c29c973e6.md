## Title
Attacker-controlled repo content (e.g. an unresolvable submodule) permanently blocks the atomic worktree→symlink publish, causing persistent sync denial - (`main.go`)

### Summary
`git-sync`'s core contract is that a sync either fully succeeds (fetch → new worktree → checkout → submodule update → publish symlink) or does not publish at all, so consumers never see a partial checkout. This mirrors the audited pattern of an "atomic, all-or-nothing delivery": in the OrderBook.sol report, a single malicious/blocked leg of an atomic operation could block the entire delivery forever. In `git-sync`, the analogous multi-step pipeline in `configureWorktree`/`SyncRepo` treats checkout + submodule update as one all-or-nothing step gating the symlink publish. An attacker who can push a commit to the tracked ref can embed a submodule reference that will permanently fail to resolve/fetch, causing every subsequent sync attempt against that exact commit to fail identically, forever, with no path to publish.

### Finding Description
`configureWorktree` performs `git reset --hard <hash>` followed by `git submodule update --init [--recursive]` on the new worktree, and any error aborts the whole sync before the symlink is ever flipped: [1](#0-0) 

`SyncRepo` calls `configureWorktree` and, if it errors, returns immediately without calling `beforePublish`/`publishSymlink`/`afterPublish`, i.e. the update is not published at all: [2](#0-1) 

The outer sync loop treats such an error as a failure and retries at `--period`/`--init-period`, but if `--max-failures` (default `0`) is exceeded, the process calls `os.Exit(1)`: [3](#0-2) 

Because `git.ref` (e.g. `HEAD` of a tracked branch) is fetched from the untrusted remote each cycle, and a broken submodule reference committed by the attacker will fail to resolve on *every* attempt (same commit, same broken gitlink), the sync can never succeed for that commit. Readiness (`setRepoReady()`) is only marked after a successful sync: [4](#0-3) [5](#0-4) 

The HTTP endpoint only reports healthy/ready after the first successful sync, per the documented contract:

(See wiki: "It provides an HTTP endpoint for liveness and readiness checks, returning a 200 OK only after the first successful sync main.go:1143-1153".)

This is structurally the same bug class as the report: a single, attacker-influenced component of an "all must succeed together" operation (submodule fetch, analogous to one leg of the atomic fee transfer) can be made to fail indefinitely, and because the design never falls back to a partial/degraded publish, this failure is not self-healing — it recurs identically on every retry.

### Impact Explanation
- If the broken commit is encountered during the **initial** sync (first time `git-sync` runs against that ref/commit, e.g. new Pod, PVC wipe, or rollout), the Pod's readiness probe never returns success, and consuming containers relying on the shared volume never receive data — a persistent, total denial of the sidecar's function.
- If encountered during **steady-state** updates, `git-sync` keeps retrying the same broken commit forever (or exits/crash-loops once `--max-failures` is hit with default settings), so newer content can never be published — a persistent denial of future updates, silently stalling the deployment on stale data with no operator-visible recovery other than reverting the offending upstream commit.
- The trigger requires only push access to the tracked branch/tag (an attacker-pushed commit), not any privileged access to the `git-sync` deployment itself, aligning with the "attacker-pushed commit/ref" threat model.

### Likelihood Explanation
Any party with write access to the synced branch (e.g. a compromised CI bot, a malicious collaborator, or a supply-chain compromised dependency repo referenced as a submodule) can trivially add/point a `.gitmodules` entry to a URL or commit that cannot be fetched (unreachable host, private repo without configured credentials, or a submodule commit that doesn't exist upstream). Because `--submodules` defaults to `recursive`, this path is exercised by default without any special git-sync configuration.

### Recommendation
- Do not let a fatal, deterministic per-commit failure (e.g., submodule resolution failure) count indefinitely against `--max-failures`/crash the process without additional visibility/circuit-breaking distinct from transient network errors.
- Consider allowing `git-sync` to keep serving the last known-good published symlink target indefinitely while clearly surfacing (metrics/error-file) that the *specific* target commit is permanently unsyncable, rather than only generic retry/backoff.
- Consider an option to skip/ignore unresolvable submodules (already partially supported via `--submodules=off`) with a documented operator escape hatch, and/or exponential backoff with alerting distinguishing "stuck on bad commit" from "transient network failure."

### Proof of Concept
1. Set up an upstream repo tracked by `git-sync` with `--submodules=recursive` (the default).
2. As a user with push access to the tracked branch, add a submodule entry (`.gitmodules` + gitlink) pointing to a URL that will always fail to fetch (e.g., a host that returns 404, or a private repo with no credentials configured in `git-sync`), or a submodule commit hash that does not exist in the submodule's remote.
3. Push this commit as the new tip of the tracked ref.
4. Observe `git-sync`:
   - `git fetch` succeeds (main repo content is fetchable) — [6](#0-5) 
   - `createWorktree` succeeds — [7](#0-6) 
   - `configureWorktree`'s `git submodule update --init --recursive` fails every time — [8](#0-7) 
   - `SyncRepo` returns an error before `publishSymlink` runs, so the symlink is never updated to the new (or, on first run, any) worktree — [9](#0-8) 
5. Repeat indefinitely: since the ref still points to the same broken commit, every retry fails identically. With default `--max-failures=0`, the process exits after the very first failure; on initial sync this means the Pod never reaches ready, and on steady-state sync this means the process (and thus the Pod, under `restartPolicy: Always`) crash-loops permanently until the malicious commit is reverted upstream.
