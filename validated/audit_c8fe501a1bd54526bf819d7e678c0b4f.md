### Title
Webhook signature verification key derived from organization in webhook payload, not repository owner - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The webhook signature verification in Shipit uses the organization extracted from the webhook payload to look up the GitHub App configuration, rather than using the repository owner. An attacker can craft a webhook from a repository in one organization but claim it belongs to a different organization in the payload, causing Shipit to verify the signature against the wrong GitHub App's webhook secret.

### Finding Description
In `app/controllers/shipit/webhooks_controller.rb`, the `verify_signature` method extracts the organization from the webhook payload and uses it to retrieve the GitHub App configuration:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
end

def repository_owner
  # Fallback to the organization sub-object if repository isn't included in the payload
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

The `repository_owner` method extracts the organization name from the webhook payload itself. GitHub webhook payloads include both `repository.owner.login` and `organization.login` fields, both of which are attacker-controlled in the webhook payload.

The vulnerability is that the webhook signature is verified using the GitHub App secret associated with the organization extracted from the payload, not the organization that actually owns the repository or the organization that installed the GitHub App.

### Impact Explanation
**Critical - Authentication bypass and unauthorized deploy**

An attacker who knows:
1. The webhook URL of a Shipit instance
2. The webhook secret for Organization A (which has a GitHub App installed on Shipit)
3. A repository in Organization B

Can craft a webhook that:
- Claims to be from Organization A (in the payload's `organization.login` field)
- Actually references a repository from Organization B (in `repository.full_name`)
- Is signed with Organization A's webhook secret

This webhook will pass signature verification because Shipit will verify it against Organization A's secret (as specified in the payload). However, the webhook handler will then process it as if it came from Organization B's repository, potentially triggering deploys or other actions on stacks associated with Organization B's repositories.

The binding broken is: **organization that authenticated the webhook signature ≠ organization that owns the repository being acted upon**

### Likelihood Explanation
This vulnerability requires:
- Knowledge of a Shipit instance's webhook URL (typically public or discoverable)
- Knowledge of a webhook secret for one organization (possible if an attacker has access to that organization's GitHub App settings, or if the secret is weak/leaked)
- A repository in a different organization to target

The attack is straightforward to execute once these prerequisites are met. The vulnerability exists in the core webhook handling path and affects all webhook event types (push, status, check_suite, pull_request, membership).

### Recommendation
Verify the webhook signature using the GitHub App secret associated with the repository owner (from `repository.owner.login`), not the organization extracted from the webhook payload. Alternatively, verify against all configured GitHub App secrets and only proceed if the organization matches the one that signed the webhook.

### Proof of Concept
1. Attacker obtains webhook secret for Organization A (e.g., through leaked credentials or GitHub App settings access)
2. Attacker crafts a webhook payload with:
   - `organization.login: "OrgA"`
   - `repository.full_name: "OrgB/target-repo"`
   - `repository.owner.login: "OrgB"`
   - Signed with OrgA's webhook secret
3. Attacker sends POST to `https://shipit.example.com/webhooks` with this payload
4. Shipit extracts `repository_owner` = "OrgA" from the payload
5. Shipit verifies signature against OrgA's webhook secret (matches)
6. Shipit processes the webhook as if it came from OrgB's repository
7. If the webhook is a push event, Shipit syncs and potentially deploys OrgB's repository [2](#0-1)
