### Title
Permanent freeze of accumulated creator fees when the pool creator's token account is frozen/blacklisted by a Token-2022 mint - (File: `programs/cp-swap/src/instructions/collect_creator_fee.rs`, `programs/cp-swap/src/instructions/collect_creator_fee_permissionless.rs`)

### Summary
The creator-fee collection path always transfers accrued `creator_fees_token_0`/`creator_fees_token_1` to a token account whose owner is hard-coded as `pool_state.pool_creator`, an address fixed at pool `initialize` time with no update instruction anywhere in the program. If the mint (Token-2022, which this program explicitly supports) freezes or otherwise blocks transfers to that specific account/owner (e.g. via freeze authority or a permanent-delegate/transfer-hook style restriction), every future call to `collect_creator_fee` or `collect_creator_fee_permissionless` will revert, permanently trapping the growing creator-fee balance inside the pool vault.

### Finding Description
`CollectCreatorFee` and `CollectCreatorFeePermissionless` both derive the destination token accounts with `associated_token::authority = creator` where `creator` is constrained to `pool_state.load()?.pool_creator` [1](#0-0) [2](#0-1) . `pool_creator` is set once in `PoolState::initialize` and there is no instruction in the codebase that ever mutates it afterward (confirmed by searching the entire program for `pool_creator` usages, which are limited to `pool.rs` initialization and the two collect-fee instructions) [3](#0-2) .

Both instructions unconditionally attempt `transfer_from_pool_vault_to_user` to `creator_token_0`/`creator_token_1` and only zero out `pool_state.creator_fees_token_0/1` after both transfers succeed [4](#0-3) [5](#0-4) . The underlying transfer uses `token_2022::transfer_checked`, which is subject to Token-2022 mint-level restrictions such as the freeze extension [6](#0-5) . If the creator's ATA (or, for tokens with a default-account-state extension, any newly created ATA for that owner) is frozen, the CPI call reverts, causing the whole instruction to fail every time it's invoked — including the permissionless variant, which anyone can call but which still routes funds to the same fixed, frozen destination.

Because `creator_fees_token_0`/`creator_fees_token_1` keep accumulating with every swap (they are excluded from `vault_amount_without_fee` and sit in the vault balance) [7](#0-6) , and because there is no admin override, no alternate recipient path, and no way to change `pool_creator`, the creator-fee share of the pool becomes permanently unrecoverable once the creator's account is frozen. This exactly mirrors the reported bug class: an on-chain fixed "recipient" address that cannot be updated, and whose blacklisting/freezing by the underlying token traps protocol-managed funds forever.

### Impact Explanation
Any creator-fee amount accrued in the vault (and all future creator fees, since swaps keep routing a share into `creator_fees_token_0/1`) becomes permanently frozen and unrecoverable by anyone — not just the creator, but also the protocol, since no admin instruction can redirect or rescue these fees. This is a real, permanent loss/freeze of user-adjacent funds (pool fee accounting), fitting the "permanent freezing of user or LP funds" acceptance criterion.

### Likelihood Explanation
This requires the pool's `creator` account (or its token account) to be frozen/blacklisted by the token issuer — a realistic and common scenario for Token-2022 mints with freeze authorities, especially for tokens created via `initialize_with_permission`-style deployments where the mint may have a freeze authority retained by an issuer, or the creator's account gets frozen for compliance reasons after pool creation. Since `collect_creator_fee_permissionless` is callable by anyone and always targets the same fixed, potentially-frozen destination, once frozen, every attempt to collect these fees will fail indefinitely, with no code path to recover.

### Recommendation
Introduce a way to redirect creator fees when the current `pool_creator`'s associated token account cannot receive funds — e.g., allow the `pool_creator` to nominate/update a different receiving address (analogous to allowing `recipientAddress` to be updated), or add an admin-guarded recovery instruction that can sweep stuck creator fees to a new, functioning account chosen by governance/admin after some dispute period, rather than hard-coding the destination as an ATA of an immutable `pool_creator`.

### Proof of Concept
1. Pool is initialized with `token_0_mint` as a Token-2022 mint that has (or later gains, if freeze authority is retained) freeze capability; `pool_creator` is set to address `C` at `PoolState::initialize` [8](#0-7) .
2. Users swap through the pool; creator fees accrue in `pool_state.creator_fees_token_0` on every swap.
3. The mint's freeze authority freezes `C`'s associated token account for `token_0_mint` (a normal, permitted Token-2022 action, independent of this program).
4. Any subsequent call to `collect_creator_fee` (by `C`) or `collect_creator_fee_permissionless` (by anyone) reaches `transfer_from_pool_vault_to_user` targeting `creator_token_0`, which is frozen, so `transfer_checked` fails and the whole instruction reverts [9](#0-8) .
5. Because `pool_creator` can never be changed and there is no alternate recipient/admin sweep instruction, `creator_fees_token_0` (and any further accrued creator fees) remain locked in `token_0_vault` permanently.

pub fn collect_creator_fee(ctx: Context<CollectCreatorFee>) -> Result<()> {
    let mut pool_state = ctx.accounts.pool_state.load_mut()?;
    let creator_fees_token_0 = pool_state.creator_fees_token_0;
    let creator_fees_token_1 = pool_state.creator_fees_token_1;
    if creator_fees_token_0 == 0 && creator_fees_token_1 == 0 {
        return err!(ErrorCode::NoFeeCollect);
    }

    let signer_seeds: &[&[u8]] = &[crate::AUTH_SEED.as_bytes(), &[ctx.bumps.authority]];

    transfer_from_pool_vault_to_user(
        ctx.accounts.authority.to_account_info(),
        ctx.accounts.token_0_vault.to_account_info(),
        ctx.accounts.creator_token_0.to_account_info(),
        ctx.accounts.vault_0_mint.to_account_info(),
        ctx.accounts.token_0_program.to_account_info(),
        creator_fees_token_0,
        ctx.accounts.vault_0_mint.decimals,
        &[signer_seeds],
    )?;

    transfer_from_pool_vault_to_user(
        ctx.accounts.authority.to_account_info(),
        ctx.accounts.token_1_vault.to_account_info(),
        ctx.accounts.creator_token_1.to_account_info(),
        ctx.accounts.vault_1_mint.to_account_info(),
        ctx.accounts.token_1_program.to_account_info(),
        creator_fees_token_1,
        ctx.accounts.vault_1_mint.decimals,
        &[signer_seeds],
    )?;

    pool_state.creator_fees_token_0 = 0;
    pool_state.creator_fees_token_1 = 0;
    pool_state.recent_epoch = Clock::get()?.epoch;

            vault_0
                .checked_sub(fees_token_0)
                .ok_or(ErrorCode::InsufficientVault)?,

pub fn transfer_from_pool_vault_to_user<'a>(
    authority: AccountInfo<'a>,
    from_vault: AccountInfo<'a>,
    to: AccountInfo<'a>,
    mint: AccountInfo<'a>,
    token_program: AccountInfo<'a>,
    amount: u64,
    mint_decimals: u8,
    signer_seeds: &[&[&[u8]]],
) -> Result<()> {
    if amount == 0 {
        return Ok(());
    }
    token_2022::transfer_checked(
        CpiContext::new_with_signer(
            *token_program.key,
            token_2022::TransferChecked {
                from: from_vault,
                to,
                authority,
                mint,
            },
            signer_seeds,
        ),
        amount,
        mint_decimals,
    )
}
