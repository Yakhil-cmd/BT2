### Title
Webhook signature verification key is selected by an attacker-controlled field that is never re-validated against the repository actually mutated - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` derives the HMAC key to check the inbound webhook signature from a field taken directly out of the *unverified* JSON body (`repository.owner.login` / `organization.login`), then hands the very same unverified body to the event handlers, which act on a **different** field of that body (`repository.full_name`) to decide which `Stack`/`Commit` to mutate. In a multi-organization Shipit deployment (the officially documented "Using Multiple GitHub Applications" setup), nothing ties the organization whose secret validated the signature to the repository the handler subsequently writes to.

### Finding Description
`WebhooksController` computes the signing organization purely from body content: [1](#0-0) [2](#0-1) 

`repository_owner` is `params.dig('repository','owner','login')`, taken from the raw, unauthenticated POST body before any signature has been checked. This value selects which per-organization `GitHubApp`/`webhook_secret` is used to verify `X-Hub-Signature`: [3](#0-2) 

Once verification passes, `create` re-parses the same raw body and dispatches it, unmodified, to the registered handlers: [4](#0-3) 

The handlers, however, never look at `repository.owner.login` again — they resolve the target `Repository`/`Stack`/`Commit` from `repository.full_name` (or, for `StatusHandler`, purely from the commit `sha`, with no owner check at all): [5](#0-4) [6](#0-5) [7](#0-6) 

The binding that is broken:
`organization whose secret authenticated the request == organization that owns the repository being written`
This equality is never enforced. `repository.owner.login` (or `organization.login`) is only used to *pick a key*; `repository.full_name` (or bare `sha`, for statuses) is what is actually acted on, and the two can point at unrelated organizations/repositories within the same JSON payload.

This is the direct analog of the reported bug class: a payload field ("who signed/paid") is disjoint from the field the code actually acts on ("what gets debited/mutated"), because the two are read from independent parts of the same untrusted structure without a consistency check between them, and because the signature only proves the payload was signed with *a* key, not that the key belongs to the entity the payload claims to represent for the mutating field.

Real-world exploitability requires the Shipit instance to run in the documented multi-org mode (`config/secrets.yml` with multiple top-level org keys, e.g. `test/dummy/config/secrets_double_github_app.yml`, `config/secrets.development.shopify.yml`), where an attacker who controls (or is a legitimate collaborator/admin of) any one of the configured organizations — including one they set up themselves and pointed at Shipit, or any org whose `webhook_secret` is left unset (`return true unless webhook_secret` in `verify_webhook_signature`) — can compute or trivially bypass a valid signature for `repository_owner = <their org>` while setting `repository.full_name` (or a commit `sha` belonging to any tracked stack) to a target in a **different, unrelated organization's stack**.

### Impact Explanation
- `StatusHandler` accepts a forged CI status for an arbitrary `sha` with no repository-ownership check at all (`Commit.where(sha: params.sha)`), and successful/pending statuses schedule `ProcessMergeRequestsJob`: [8](#0-7) 
- `ProcessMergeRequestsJob` merges pull requests once `all_status_checks_passed?` returns true, which is computed from the (forgeable) status/check-run rows: [9](#0-8) [10](#0-9) 
- `MergeRequest#merge!` calls `stack.github_api.merge_pull_request(...)`, performing a real GitHub merge using the app's own credentials: [11](#0-10) 

By forging a "success"/passing status webhook for a commit that belongs to a stack in an organization the attacker does not control (verified under a different, attacker-influenced org's key), an attacker can cause Shipit to autonomously merge a pull request that never actually passed CI — an unauthorized merge performed with the app's own `GITHUB_TOKEN`-equivalent credentials, without any human deploy action. This matches the "unauthorized deploy, rollback or merge" Critical impact bucket.

### Likelihood Explanation
Exploitability is conditioned on the operator running the documented multi-organization configuration and on at least one configured organization either having no `webhook_secret` set (explicitly supported/"optional" per `docs/setup.md`) or being one the attacker administers themselves (e.g., they register their own GitHub App/org and have it added as one of the configured organizations, which is a normal onboarding flow for a shared, multi-tenant Shipit instance). Given that `webhook_secret` is documented as optional and multiple example configs in the repo ship with it commented out/nil, this is a plausible production configuration, not a purely theoretical one. No session, `ApiClient` token, or GitHub write access to the *target* repository is required — only the ability to submit a JSON POST to the public `/webhooks` endpoint with a signature valid for any one configured org.

### Recommendation
After verifying the HMAC signature, re-derive the same `repository_owner`/`organization` used for key selection and enforce that it matches the actual repository being mutated (e.g., verify `Repository.from_github_repo_name(payload.dig('repository','full_name'))&.owner == repository_owner`, and for `StatusHandler`, scope the `Commit` lookup by the stack's repository owner rather than by `sha` alone). Reject the webhook if the two disagree. Additionally, require `webhook_secret` to be present for every configured organization in multi-org mode (fail closed instead of `return true unless webhook_secret`).

### Proof of Concept
Preconditions: Shipit configured in multi-org mode (see `docs/setup.md` "Using Multiple GitHub Applications") with orgs `AttackerOrg` (attacker-controlled webhook secret, or no secret configured) and `VictimOrg` (contains a tracked stack with an open PR in the merge queue).

1. Attacker crafts a `status` webhook payload:
```json
{
  "sha": "<head sha of VictimOrg/target-repo's PR under merge queue>",
  "state": "success",
  "context": "ci/required",
  "repository": { "owner": { "login": "AttackerOrg" }, "full_name": "AttackerOrg/decoy-repo" }
}
```
2. Attacker computes `X-Hub-Signature` using `AttackerOrg`'s webhook secret (known to them because they control that org's GitHub App config), or sends any value if `AttackerOrg` has no secret configured.
3. `WebhooksController#verify_signature` reads `repository_owner = "AttackerOrg"`, looks up `Shipit.github(organization: "AttackerOrg")`, and verifies successfully.
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the `VictimOrg` commit (ownership of `repository.owner` is never re-checked), and records a "success" status.
5. `Commit#add_status` schedules `ProcessMergeRequestsJob`, which finds the PR's `all_status_checks_passed?` now true and calls `MergeRequest#merge!`, causing Shipit to merge the `VictimOrg` pull request via the app's own GitHub credentials — despite the attacker having no access to `VictimOrg`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
