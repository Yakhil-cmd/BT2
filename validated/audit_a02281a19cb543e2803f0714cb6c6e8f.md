### Title
Webhook signature is verified against an org derived from the unauthenticated payload, letting a foreign organization spoof `commit_status` (and other) events for any stack on a shared multi-org Shipit instance - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks the GitHub App/webhook secret to validate a signature by reading `repository_owner` straight out of the still-unauthenticated request body, then hands the *entire* raw JSON body to every registered handler without re-checking that the repository/commit the handler operates on actually belongs to that same organization.

### Finding Description
`verify_signature` resolves the signing secret like this: [1](#0-0) 

and `repository_owner` is read directly from the JSON body before any cryptographic check has occurred: [2](#0-1) 

`Shipit.github(organization:)` looks up a *different* `GitHubApp` (and therefore a different `webhook_secret`) per organization key in `secrets.github`, as documented for the multi-org setup: [3](#0-2) [4](#0-3) 

Once `verify_signature` passes using OrgA's secret, `create` parses the same raw body a second time and dispatches it to every handler registered for the event, with no additional binding of "the org whose secret validated this request" to "the repository/commit the handler is about to mutate": [5](#0-4) 

`StatusHandler`, the commit-status webhook handler, only requires a bare `sha` and `state` - it never checks a `repository` field at all, and looks the commit up globally across the entire database: [6](#0-5) 

`Commit.where(sha: params.sha)` is a global, cross-stack query with no organization/stack scoping: [7](#0-6) [8](#0-7) 

This is the same bug class as the report's `record()`/`_victors` issue: a loop/handler trusts an *array/field of the caller's own choosing* (here, `sha`, and implicitly "which repository this event is about") that was never actually covered by the check that authorized the call (the HMAC signature, whose *scope* is determined by an org name taken from the same untrusted payload). The binding that should hold is:

`organization whose secret validated the signature == organization owning the repository/commit the handler mutates`

but the engine only enforces `organization used to pick the secret == organization named in the payload's own `repository.owner.login` field`, which the attacker fully controls. Nothing ties the *validated* org to the *acted-upon* commit/stack.

### Impact Explanation
On any Shipit deployment using the documented multi-organization `github:` config (`lib/shipit.rb#github_app_config`, `docs/setup.md` "Using Multiple Github Applications"), an entity that legitimately controls one onboarded organization's GitHub App/webhook secret (an "unprivileged" party with respect to Shipit itself - no Shipit session, no `ApiClient` token, no repository write access to the victim repo) can craft an arbitrary JSON body, set `repository.owner.login`/`organization.login` to *their own* org so the signature check passes with their own known secret, and set the actual mutating fields (e.g. `sha`, `state`, `context`) to reference a commit that belongs to a completely different, unrelated stack/organization on the same Shipit instance. Because `StatusHandler` performs no repository/stack ownership check, this results in commit statuses being fabricated for a victim's commit. Fabricated `success` statuses feed directly into `Commit#deployable?`, `MergeRequest::StatusChecker`, and `MergeRequest#all_status_checks_passed?` / `#any_status_checks_failed?`, which gate `Commit#schedule_continuous_delivery` and `MergeRequest#merge!` (which calls `stack.github_api.merge_pull_request`): [9](#0-8) [10](#0-9) [11](#0-10) 

This can lead to an unauthorized deploy (continuous delivery firing on a spoofed "success" status) or an unauthorized merge (merge queue treating required checks as satisfied), matching the "unauthorized deploy, rollback or merge" Critical impact bucket.

### Likelihood Explanation
Likelihood is Medium: it requires the specific, but documented and supported, multi-organization configuration (`config/secrets.development.shopify.yml`, `test/dummy/config/secrets_double_github_app.yml`) where more than one external organization's GitHub App is registered against the same Shipit instance, and requires the attacker to know a target commit `sha` (often discoverable from public repos/PRs) and roughly when it will be checked. No privileged Shipit credential is needed - only control of one legitimately-onboarded org's webhook secret, which is knowledge an "unprivileged" org owner naturally has for their own App.

### Recommendation
Bind the verified organization to the object being mutated: after `verify_signature` succeeds, pass the authenticated `repository_owner`/organization down into each handler and require handlers (starting with `StatusHandler`, and auditing all others in `app/models/shipit/webhooks/handlers/`) to scope their lookups (`Commit`, `Stack`, `Repository`) to that authenticated organization instead of trusting attacker-supplied repository fields or performing unscoped global lookups.

### Proof of Concept
1. Deploy Shipit with the multi-org config shape shown in `docs/setup.md` lines 182-209, onboarding `OrgA` (attacker-controlled, e.g. a public open-source org the attacker legitimately administers) and `OrgVictim`.
2. Attacker, who knows `OrgA`'s `webhook_secret` (they configured/received it when installing their own GitHub App), crafts a raw JSON body:
   ```json
   { "repository": {"owner": {"login": "OrgA"}}, "sha": "<victim commit sha>", "state": "success", "context": "ci/required-check" }
   ```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>` and sends it to `/github/webhooks` with header `X-Github-Event: status`.
4. `verify_signature` resolves `repository_owner` as `"OrgA"` from the body (`app/controllers/shipit/webhooks_controller.rb:59-62`), fetches `OrgA`'s `GitHubApp`, and the signature validates successfully (`app/controllers/shipit/webhooks_controller.rb:24-30`).
5. `create` dispatches the body to `StatusHandler`, which finds the victim's commit purely by `sha` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-23`, `app/models/shipit/commit.rb:92-99`) - a commit that belongs to `OrgVictim`'s stack, not `OrgA`'s - and records the forged status against it.
6. If this status is one of `OrgVictim`'s required checks, `MergeRequest#any_status_checks_missing?`/`#all_status_checks_passed?` may now report success, and the merge queue or continuous-delivery job can act on a commit that never actually passed CI.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def self.by_sha(sha)
      raise AmbiguousRevision, "Short SHA1 #{sha} is ambiguous (too short)" if sha.to_s.size < 6

      commits = where('sha like ?', "#{sha}%").take(2)
      raise AmbiguousRevision, "Short SHA1 #{sha} is ambiguous (matches multiple commits)" if commits.size > 1

      commits.first
    end
