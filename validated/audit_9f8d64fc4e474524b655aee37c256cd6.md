### Title
Unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` lets a status from one repository overwrite CI state for commits with the same SHA in unrelated stacks - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` writes an incoming GitHub `status` webhook to every `Commit` row in the database matching the payload's `sha`, without filtering by the repository/stack that actually authenticated the webhook. Since `Commit` rows are keyed by `sha` per-stack and Git SHAs are content-addressed (identical content in an attacker-controlled repository produces an identical SHA), an attacker who owns a repository and gets Shipit's GitHub App installed on it can produce a legitimately-signed `status` event carrying `context: continuous-integration/travis-ci`, `state: success` for a SHA that also exists in a victim's stack, flipping that victim commit's CI status and `deployable?`.

### Finding Description
The broken invariant, stated as an equality: the set of `Commit` rows updated by a `status` webhook should equal `stacks_for(repository_name_in_payload).commits.where(sha: params.sha)`, but the actual code computes it as `Commit.where(sha: params.sha)` — i.e., **all commits in the entire database with that SHA, across every stack/repository**, are treated as authenticated by the single repository that signed the webhook. [1](#0-0) 

The base `Handler` class already provides the correct scoping primitive — a `stacks` method that resolves `Repository.from_github_repo_name(repository_name)&.stacks`, using `repository_name` taken from `payload.dig('repository', 'full_name')` (the field that `verify_signature` and GitHub's signing process actually authenticate). [2](#0-1)  `StatusHandler` simply never calls it, unlike other handlers that use `stacks` to scope their effects to the authenticated repository.

Request path: `WebhooksController#create` parses the raw JSON body and dispatches to `Shipit::Webhooks.for_event(event)` handlers after `verify_signature` checks the HMAC using `Shipit.github(organization: repository_owner)`, where `repository_owner` is read from `params.dig('repository', 'owner', 'login')`. [3](#0-2)  This verification confirms the payload came from GitHub for *the attacker's own repository* (a legitimate, correctly-signed delivery) — it does **not** confirm that the `sha` inside the payload is unique to that repository. `StatusHandler#process` then ignores the repository field entirely and only uses `params.sha`.

`Commit#create_status_from_github!` unconditionally records the status and recomputes `status`/`deployable?` for whichever `Commit` row is touched: [4](#0-3)  and `deployable?` is defined purely in terms of the commit's own `stack` and status group: [5](#0-4) . There is no cross-check that the commit's `stack.repository` matches the webhook's originating repository.

Existing guards do not prevent this: `verify_signature` authenticates that *a* GitHub App on the attacker's own org sent the request, not that the `sha` belongs to that org's repo; `drop_unhandled_event` only checks the event type is registered; the `ExplicitParameters` schema for `StatusHandler` only validates `sha`/`state`/`context` types, not repository ownership. None of these touch the missing `stacks` scoping.

Exploit flow: attacker creates a commit in a repository they own (or control content for) whose tree/parent/author/committer/timestamp/message reproduce the exact same SHA as a victim commit already tracked by a victim's Shipit stack (trivial if the attacker forks/mirrors the same upstream history, or crafts an identical commit object). Attacker triggers (via a normal GitHub Actions/Travis integration, or a manual `POST` to GitHub's status API for their own repo) a `status` event with `context: continuous-integration/travis-ci`, `state: success` for that SHA. GitHub signs and delivers this webhook to Shipit exactly as for any legitimate repository event. `StatusHandler#process` then runs `Commit.where(sha: <shared sha>).each { |c| c.create_status_from_github!(params) }`, mutating the victim's `Commit` row's status group, which can flip `deployable?` to true if `continuous-integration/travis-ci` is in the victim stack's `ci.require` and no other blocking context exists.

### Impact Explanation
A payload authenticated only for the attacker's own repository can write a `Status` record onto a `Commit` belonging to a completely different repository/stack, altering that victim commit's CI status group and `deployable?`/merge eligibility — this is a "payload for one repository mutating another's stack/commit" case, matching the Critical impact category (unauthorized deploy/rollback/merge of attacker-influenced code, since it changes which commit is considered safe to deploy on the victim stack). The blast radius covers every Shipit deployment hosting multiple stacks/repositories that could ever share a commit SHA (mirrors, forks with shared history, subtree merges, or any content-identical commit crafted by the attacker), and it is repeatable for every future status event on the shared SHA.

### Likelihood Explanation
Preconditions: Shipit's GitHub App/integration must be installed on a repository the attacker controls (a normal, low-privilege setup in orgs that allow self-service app installation or public app marketplaces), and there must be a victim stack whose tracked commit SHA collides with attacker-controlled content. Producing a SHA collision is not a cryptographic break — Git SHA-1 depends only on blob/tree/commit metadata, so an attacker who can see the victim's commit (e.g., via a public repo, a fork, or a shared upstream) can trivially reconstruct byte-identical commit objects (same tree, parent, author, committer, timestamps, message) to get an identical SHA. No secrets, sessions, or elevated GitHub permissions are needed; the attacker only needs to control content in a repo where they can trigger a `status` webhook (e.g., via their own CI integration). This makes the attack cheap, deterministic, and repeatable against any repository sharing history with an attacker-owned one.

### Recommendation
Scope `StatusHandler#process` to the repository that authenticated the webhook, exactly like other handlers do via the base class's `stacks` helper: iterate `stacks.flat_map(&:commits).where(sha: params.sha)` (or equivalently `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`) instead of the global `Commit.where(sha: params.sha)`, so a status can only ever be applied to commits belonging to stacks whose repository matches `payload.dig('repository', 'full_name')`.

### Proof of Concept
Minitest plan (no live GitHub, direct handler invocation):
1. Create two repositories, `Repository` A (`"victim/repo"`) and `Repository` B (`"attacker/repo"`), each with a `Stack` (`stack_a`, `stack_b`). Configure `stack_a.cacheable_ci_config` (or equivalent `ci.require`) to require `continuous-integration/travis-ci`.
2. Create `commit_a = stack_a.commits.create!(sha: SHARED_SHA, ...)` with no passing statuses yet — assert `commit_a.deployable? == false` (left side of equality: victim commit not deployable).
3. Create `commit_b = stack_b.commits.create!(sha: SHARED_SHA, ...)` in the attacker's stack.
4. Build a payload `{ 'sha' => SHARED_SHA, 'state' => 'success', 'context' => 'continuous-integration/travis-ci', 'repository' => { 'full_name' => 'attacker/repo', 'owner' => { 'login' => 'attacker' } } }` and call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly (bypassing controller-level signature verification, since the finding is about the handler's internal scoping, not signature bypass).
5. Reload `commit_a` and assert `commit_a.status.state == 'success'` and `commit_a.deployable? == true`, even though the payload's `repository.full_name` was `attacker/repo`, not `victim/repo` — this demonstrates the equality `stacks_for(payload.repository) == {stack_b}` is violated because `commit_a` (belonging to `stack_a`) was mutated too.
6. Assert this only happens because `StatusHandler#process` does not call the inherited `stacks` scoping method; a fixed implementation restricted to `stacks.flat_map(&:commits)` would leave `commit_a` unaffected and the test would fail without the scoping fix, proving the regression.
