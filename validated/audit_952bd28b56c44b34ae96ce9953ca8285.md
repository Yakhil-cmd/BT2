## Analysis

CVE-2016-0780 concerns improper disk-quota enforcement in Cloud Foundry that let an attacker bypass byte-accounting and consume more physical disk than what was billed against the quota, causing storage-based denial of service. The closest analog in `ocore` is the network's own "disk quota" mechanism: the anti-spam fee model that charges senders per byte for permanently storing their unit's content on every full node (`headers_commission` / `payload_commission` / `oversize_fee`), and the analogous `storage_size` accounting for AA state variables. Both of these systems measure "size" using the JavaScript string `.length` (UTF-16 code-unit count) rather than the actual number of bytes that get persisted to disk (which are UTF-8 encoded when written to LevelDB/kvstore and to the DB). This creates the same class of bug as the CVE: the accounted quota (`.length`) understates real disk consumption for any non-ASCII content.

- `object_length.js`'s `getLength()` — used to compute `headers_commission` and `payload_commission`, which are strictly checked in `validation.js` and capped by `constants.MAX_UNIT_LENGTH` — charges `value.length` for strings. [1](#0-0) 
- `validation.js` enforces that `headers_commission + payload_commission` (computed via character-length) matches the declared fee and is capped at `MAX_UNIT_LENGTH`. [2](#0-1) 
- The unit is then persisted verbatim as JSON to the kvstore (`'j\n'+objUnit.unit` → `JSON.stringify(objJoint)`), which is where the real disk bytes are consumed — UTF-8 encoded, not UTF-16 code-unit counted. [3](#0-2) 
- The same `.length`-based accounting pattern is used for AA state-variable storage-size billing (`getValueSize`), which gates how much disk an AA is allowed to consume relative to its `byte_balance`. [4](#0-3) [5](#0-4) 

Since UTF-8 encodes most non-Latin characters (Cyrillic, CJK, etc.) as 2–3 bytes and astral characters/emoji as 4 bytes (while counting as 1–2 UTF-16 units), an attacker can craft `data`/`data_feed`/AA-state-var payloads made largely of such characters to make the *actual* bytes persisted to every full node's disk substantially larger (up to ~3-4x) than what the `payload_commission`/`storage_size` fee charges for. This does not cap the disk cost — it only skews the price/byte ratio, letting an attacker pay less than intended per real byte of permanent network-wide storage, which is exactly the "quota enforcement bypass leading to disk exhaustion" bug class in CVE-2016-0780.

### Title
Disk-quota (byte-fee) miscalculation via UTF-16 length instead of UTF-8 byte size lets an attacker under-pay for permanently stored disk content - (File: object_length.js)

### Summary
`getLength()` in `object_length.js`, which underlies `headers_commission`/`payload_commission`/`oversize_fee` computation checked in `validation.js`, and `getValueSize()` in `aa_composer.js`, which underlies AA `storage_size` billing, both measure string size using JavaScript's `.length` (UTF-16 code units) instead of the actual number of bytes that are persisted to disk (UTF-8 encoded JSON in the kvstore/DB). Any unprivileged unit poster or AA can therefore make the real, permanent on-disk footprint of their content 2-4x larger than what the byte-fee model charges, simply by using non-ASCII characters.

### Finding Description
Every full node permanently stores each valid unit's JSON representation (`writer.js`, `batch.put('j\n'+objUnit.unit, JSON.stringify(objJoint))`), and this storage cost is meant to be paid for through `headers_commission` + `payload_commission`, capped by `constants.MAX_UNIT_LENGTH` and validated strictly against `objectLength.getHeadersSize`/`getTotalPayloadSize` in `validation.js`. Both of those length functions charge 1 unit of "size" per JS string character (`value.length`), which is a UTF-16 code-unit count, not the number of bytes actually serialized to disk. When the payload contains multi-byte UTF-8 characters (Cyrillic, CJK, Arabic, emoji, etc.), the JSON string that is actually written to LevelDB/the DB occupies 2 to 4 real bytes per character, while the fee/quota system only charges 1 (or 2, for astral-plane surrogate pairs) "byte" per character.

The same discrepancy exists for Autonomous Agent persistent state: `getValueSize()` (used by `updateStorageSize()` to bill an AA's `storage_size` against its `byte_balance`) also uses `.length`, so an AA (or a unit author who controls trigger data reflected into state vars) can grow real, permanently-stored key/value bytes in the kvstore faster than the enforced `byte_balance` accounts for.

Because `MAX_UNIT_LENGTH` and the commission fees are the network's core anti-spam/disk-quota mechanism (analogous to Cloud Foundry's disk quota in the CVE), this systematically under-prices real disk usage for a large class of legitimate Unicode content, letting spam units/state-writes consume more physical storage per byte paid than the design intends.

### Impact Explanation
This does not directly enable fund theft, but it breaks the network's storage-quota enforcement (the direct analog of the CVE): a poster can obtain 2-4x more permanent full-node disk storage per byte fee paid than honest ASCII content would cost, and an AA can accumulate more actual on-disk state-variable bytes than its `byte_balance` should permit. Sustained abuse (posting many `data`/`data_feed`/AA units filled with multi-byte characters up to the `MAX_UNIT_LENGTH`/`MAX_STATE_VAR_VALUE_LENGTH` character caps) inflates the real storage growth rate of every full node relative to the fees collected, degrading the economic disk-quota model that is supposed to make spam/storage-DoS prohibitively expensive — the same "disk quota not properly enforced → disk exhaustion DoS" class of impact as CVE-2016-0780.

### Likelihood Explanation
High reachability: any unprivileged unit poster can trigger this by simply choosing payload strings with non-ASCII characters in ordinary messages (e.g., `data`, `data_feed`, `text`) or via AA trigger `data`/formula-driven state assignments, with no special privileges, hub, or peer compromise needed. The `.length`-based accounting is used uniformly across the commission/fee system and the AA storage-size accounting, so the discrepancy is systemic rather than a one-off oversight.

### Recommendation
Compute size for byte-fee/quota purposes using actual UTF-8 byte length (e.g., `Buffer.byteLength(str, 'utf8')`) instead of JS string `.length` in `object_length.js`'s `getLength()` (affecting `getHeadersSize`/`getTotalPayloadSize`/`MAX_UNIT_LENGTH` enforcement) and in `aa_composer.js`'s `getValueSize()`/`checkStorageSizes()` (affecting AA `storage_size` billing), so that on-chain fees and quotas reflect the true number of bytes persisted to every full node's disk. Because this affects consensus-critical fee/commission validation, it would need a network-wide upgrade MCI gate (similar to `constants.v4UpgradeMci`) to change consistently across all nodes.

### Proof of Concept
1. Compose a unit with a `data` message whose payload is a JSON string field filled with, e.g., 1,000,000 CJK characters (each 1 char = 1 unit of `payload_commission` per `getLength`, but 3 bytes in UTF-8 once serialized).
2. `objectLength.getTotalPayloadSize(objUnit)` reports payload size ≈ 1,000,000 "bytes", well under `MAX_UNIT_LENGTH` (5,000,000), and the fee/commission the sender pays is based on this character count.
3. The unit passes `validation.js`'s commission checks (`validation.js:257-268`) and is persisted via `writer.js:688` as `JSON.stringify(objJoint)`, whose actual UTF-8 byte size is ≈3,000,000 bytes for that field alone — 3x what was charged.
4. Repeating this while staying under the character-based `MAX_UNIT_LENGTH`/fee caps lets an attacker store roughly 3x more real disk bytes per byte paid than an equivalent ASCII-only unit, across every full node in the network.
