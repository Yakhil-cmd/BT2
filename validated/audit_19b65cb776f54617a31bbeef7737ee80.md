### Title
Webhook signature verification is bound to `repository.owner.login` but event processing is bound to `repository.full_name`, allowing cross-organization webhook forgery in multi-app configurations - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In a multi-GitHub-App deployment (one `GitHubApp`/webhook secret per organization), `WebhooksController` picks which organization's secret to use for HMAC verification from an untrusted field in the JSON body, but then dispatches the event to handlers that act on a *different* untrusted field from the same body to decide which repository/stack to mutate. Nothing enforces that these two fields describe the same organization, so a signature valid for organization A's webhook secret can be replayed with a payload whose `repository.full_name` points at organization B's stacks.

### Finding Description
`Shipit.github(organization:)` supports per-organization `GitHubApp` configuration, each with its own independent `webhook_secret` (`lib/shipit.rb:170-200`, documented and fixture-tested in `docs/setup.md:182-209` and `test/dummy/config/secrets_double_github_app.yml`).

`WebhooksController#verify_signature` selects which organization's app/secret to verify against using `repository_owner`, itself derived from the still-unverified JSON body: [1](#0-0) [2](#0-1) 

After the HMAC check passes (using organization A's secret because `repository.owner.login == "A"`), `#create` re-parses the same raw body and dispatches it to the event handlers unchanged: [3](#0-2) 

Handlers resolve the target `Repository`/`Stack` using `repository.full_name`, a separate field from the same attacker-supplied JSON, with no cross-check against the field used for signature selection: [4](#0-3) 

Because GitHub itself is not involved in constructing this request (the attacker crafts the raw body and signs it themselves with a secret they legitimately know for their own organization's app), nothing prevents `repository.owner.login` from being "OrgOne" (attacker-controlled organization, secret known to attacker) while `repository.full_name` is "OrgTwo/victim-repo" (a stack belonging to an unrelated organization configured in the same Shipit instance). The verification binds "organization that authenticated" to `repository.owner.login`; the actual write path binds to `repository.full_name`. These are never checked for equality, breaking the required binding:

`organization_that_authenticated == organization_of_repository_written`

This is the direct analog of the oracle-provider report's root cause: a value that gates the trust decision (`repository_owner` → webhook secret selection) is disjoint from the value the rest of the flow actually acts on (`repository.full_name` → stack/commit mutation), and the code never re-derives or re-validates the second from the verified source.

### Impact Explanation
With a valid signature computed from an org the attacker legitimately administers, the attacker can forge webhook events (`push`, `status`, `check_suite`, `membership`, `pull_request`) that are processed as if they originated from GitHub for a repository belonging to a completely different organization hosted on the same Shipit instance. Handlers like `PushHandler` enqueue `GithubSyncJob` for that foreign stack, and `Handler#stacks`/`#repository_name` route arbitrary status/check events onto commits of stacks the attacker has no authorization over. This is a cross-organization/cross-repository write triggered by forged, unauthenticated GitHub events, matching the Critical "cross-repository writes" class in scope.

### Likelihood Explanation
Requires: (1) Shipit configured with the multi-organization `github:` schema (explicitly documented and supported, `docs/setup.md:182-209`), and (2) the attacker controlling/administering at least one of the configured organizations (i.e., knowing that organization's `webhook_secret`, which they set themselves when installing the GitHub App). Given multi-tenant Shipit deployments are an explicitly documented use case, this is a realistic configuration, though it does not affect single-organization deployments (where `repository_owner`/organization is effectively fixed to the one configured app).

### Recommendation
In `WebhooksController#verify_signature`/`#create`, after selecting the `GitHubApp` by `repository_owner` and verifying the signature, re-derive/require that every repository referenced later in the payload (`repository.full_name`, and any `organization.login`) belongs to the same organization that was authenticated. Reject the webhook if `repository.full_name.split('/').first` does not case-insensitively match the organization used for signature verification.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgOne` (attacker-administered, webhook secret known to attacker) and `OrgTwo` (victim, has stacks configured in Shipit) — per `test/dummy/config/secrets_double_github_app.yml` layout.
2. Attacker crafts a `push` payload:
```json
{
  "repository": {"owner": {"login": "OrgOne"}, "full_name": "OrgTwo/victim-repo"},
  "after": "<attacker chosen sha>"
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(OrgOne_webhook_secret, raw_body)` and POSTs to `/github/webhooks`.
4. `verify_signature` calls `Shipit.github(organization: "OrgOne")` and verifies successfully against the attacker's own secret (`app/controllers/shipit/webhooks_controller.rb:24-30`).
5. `create` dispatches to `PushHandler`, which resolves the stack via `repository.full_name` = `"OrgTwo/victim-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) and enqueues `GithubSyncJob` for a stack the attacker never authenticated against.
