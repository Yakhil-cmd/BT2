## Title
Scoped API client `stack_id` binding bypassed in `CCMenuController#stack` allows cross-stack read - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Api::BaseController` scopes all stack lookups to the authenticated `ApiClient`'s `stack_id` when the client is stack-scoped, but `Api::CCMenuController` overrides the `stack` helper with an unscoped lookup, breaking that binding.

### Finding Description
`Shipit::Api::BaseController#stacks` restricts the queryable set of stacks to the API client's own `stack_id` when one is set, and `#stack` resolves `params[:stack_id]` against that restricted scope: [1](#0-0) 

This is the mechanism that binds "the stack a token authorizes" to "the stack the request touches" for every API endpoint. `Shipit::ApiClient` supports being scoped to a single stack via `belongs_to :stack, optional: true`, and the `stack_id?` predicate (an ActiveRecord-generated attribute-presence method) is what `#stacks` checks: [2](#0-1) 

However, `Api::CCMenuController` redefines `stack` to bypass this scoping entirely, looking up any stack in the system directly by param, ignoring `current_api_client.stack_id`: [3](#0-2) 

The controller only enforces `require_permission :read, :stack`, which checks the client's `permissions` array (e.g. `read:stack`) via `ApiClient#check_permissions!`, but that check is not scope-aware — it does not verify which specific stack is being accessed: [4](#0-3) 

So any token that has been granted `read:stack` — even one deliberately scoped by an operator to a single stack (`stack_id` set) so that it can only see that stack, as is done for the auto-provisioned CCMenu client — can instead be used to fetch CI/deploy status of **any** stack in the Shipit instance by passing a different `stack_id` in the URL, because `CCMenuController#stack` never consults `current_api_client.stack_id`.

This is exactly the class of binding described in the bug-class hint: a permission ("read:stack") that a token is authorized for is checked, but the specific resource (stack) that the token is scoped/restricted to is not re-validated when the controller supplies its own unscoped resource resolver. The fixture `here_come_the_walrus` demonstrates the intended scoping semantics used elsewhere in the codebase (restricting a client to a single stack) which `CCMenuController` fails to honor: [5](#0-4) 

`CCMenuUrlController` actively creates such single-stack-scoped, `read:stack`-only tokens specifically intended for embedding in third-party CI-status tools (CCMenu), which are handed out (embedded in URLs, potentially to less-trusted consumers) under the assumption that they can only read the one stack they were minted for: [6](#0-5) 

The existing test suite for this controller only exercises the intended stack and never asserts that a scoped token is rejected for a different `stack_id`, which is consistent with the scoping bypass going unnoticed: [7](#0-6) 

### Impact Explanation
This breaks the equality: `stack a token authorizes == stack a token touches`. A single-stack-scoped `ApiClient` token (deliberately minted with the intent of restricting exposure to one stack, e.g. via `CCMenuUrlController`) can be used to read CI/build/deploy status (`lastBuildStatus`, `lastBuildLabel`, activity, lock status) for every stack in the Shipit instance instead of only its intended stack. This is an unauthenticated-scope violation / authorization bypass matching the "unauthenticated read of stack state" High-severity category in the rules, since the attacker only needs possession of any `read:stack`-scoped token (which is by design meant to be handed out more broadly, e.g., embedded in a CCMenu URL) rather than the full unscoped API credentials.

### Likelihood Explanation
Likelihood is high for any deployment that uses the CCMenu integration feature, since `CCMenuUrlController#client` automatically mints scoped, `read:stack`-only tokens for this exact purpose and encodes them into a shareable URL: [8](#0-7) 
Anyone who obtains one such URL/token (which is explicitly designed to be lower-trust and stack-restricted) can trivially swap the `stack_id` route/query parameter to read status of arbitrary stacks, requiring no additional privilege escalation.

### Recommendation
Remove the `stack` override in `Api::CCMenuController` and use the inherited, scope-aware `Api::BaseController#stack` (which resolves through `#stacks`, respecting `current_api_client.stack_id`), so that scoped API clients cannot access stacks outside their `stack_id` binding.

### Proof of Concept
1. Provision a CCMenu URL for `stack_a` via `CCMenuUrlController#fetch`, which mints an `ApiClient` with `stack_id = stack_a.id` and `permissions = ['read:stack']`. [6](#0-5) 
2. Extract the `token` query parameter from the returned `ccmenu_url`.
3. Call `GET /api/stacks/:stack_b_id/ccmenu` (a different, unrelated stack) using that same token.
4. Because `CCMenuController#stack` performs `Stack.from_param!(params[:stack_id])` without checking `current_api_client.stack_id`, the request succeeds and returns `stack_b`'s build/deploy status, despite the token being scoped only to `stack_a`. [9](#0-8)
