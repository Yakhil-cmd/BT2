### Title
Attacker-controlled route hops can abuse swap authorization to steal unrelated wallet tokens - (File: contracts/controller/src/strategies/swap.rs)

### Summary
Router-backed strategy entrypoints accept opaque `swap` route bytes and forward them to the configured router without controller-side validation of the contracts invoked by the route. A malicious route hop can therefore execute arbitrary contract code beneath the caller’s `swap_collateral`, `swap_debt`, `multiply`, or `repay_debt_with_collateral` authorization and request token transfers from that caller’s unrelated wallet balances. This is a **Medium-severity** theft-of-user-funds issue: it requires the victim to sign the poisoned authorization tree produced by simulation, but neither the controller’s exact input-transfer grant nor its output/risk checks prevent the extra child authorization.

### Finding Description
`swap_collateral` is reachable by an unprivileged caller for an account they own or delegate, taking a caller-supplied opaque `swap: Bytes` argument. [1](#0-0) [2](#0-1) 

After withdrawing the caller’s collateral, `process_swap_collateral` passes that route unchanged into `withdraw_and_swap_from_supply`. [3](#0-2) 

The shared `swap_tokens` helper only checks that the route blob is non-empty, resolves the configured router, and invokes `router.execute_strategy(&controller, &amount_in, swap)`. [4](#0-3) [5](#0-4) 

The controller correctly limits its own contract authorization to one exact `token_in.transfer(controller, router, amount_in)` invocation, but it does not inspect, decode, or restrict the third-party pool/venue addresses encoded in `swap`. [6](#0-5) [5](#0-4) 

Consequently, route-selected code can execute below the user-authorized controller invocation and make a token call requiring `caller.require_auth()`, such as `transfer(caller, attacker, caller_balance)`. During Soroban transaction simulation, that nested authorization request is recorded as a child of the caller’s root `swap_collateral` or equivalent strategy invocation; if the signed authorization tree includes it, the malicious hop transfers assets completely unrelated to the lending swap. [7](#0-6) 

The post-router checks only bound the controller’s `token_in` spend, refund controller-held leftovers, and require positive measured `token_out`; they do not bind the caller’s authorization tree to the expected transfer and do not constrain unrelated wallet-token transfers performed by route-selected code. [8](#0-7) 

### Impact Explanation
An attacker can steal any token balance held by the victim’s wallet that the rogue route contract names and the victim’s signed authorization tree includes. The lending transaction can still produce fair swap output and leave the victim’s account solvent, so collateral measurement, minimum output, and final risk checks do not detect the wallet drain. This is direct theft of user funds rather than route-quality loss or MEV.

### Likelihood Explanation
Exploitation requires an attacker to get a victim to execute a route containing the malicious hop and sign the authorization tree containing the extra token transfer. A victim that rejects unexpected authorization children is protected, and the host rejects the rogue transfer when it is absent from the signed tree. Nevertheless, the route is supplied as opaque bytes, ordinary clients commonly consume simulation-produced authorization trees, and the controller places no venue or pool allowlist between the user’s signature and attacker-selected contract code. The combination of arbitrary wallet-token impact and a realistic malicious-route/signing workflow supports Medium severity.

### Recommendation
Constrain route-selected external contracts to a governance-managed allowlist of approved venue/pool contract addresses or WASM hashes before invoking the router. The router should reject routes naming unapproved pool addresses rather than relying on callers or clients to detect malicious authorization children. As defense in depth, the controller-facing interface should expose a typed, bounded route representation or include the approved venue registry in the swap authorization flow, and clients should hard-fail any simulated authorization tree containing children beyond the expected input transfer.

### Proof of Concept
1. Alice owns a solvent lending account with USDC supplied as collateral and holds an unrelated token `ATTACK_TOKEN` in the same wallet.
2. The attacker deploys a malicious contract exposing the pool function expected by the route. That function executes `ATTACK_TOKEN.transfer(Alice, attacker, Alice_balance)` rather than only performing a swap.
3. The attacker encodes a route that passes through the malicious pool while still paying enough output asset for the router/controller settlement checks to pass.
4. Alice submits `swap_collateral(Alice, account_id, usdc_key, amount, eth_key, malicious_route)`. The controller authenticates Alice, withdraws USDC, grants only the controller’s exact input transfer, and forwards the opaque route to the router. [9](#0-8) [5](#0-4) 
5. The router invokes the attacker’s pool. The pool calls `ATTACK_TOKEN.transfer`, which requests Alice’s authorization even though that transfer is unrelated to the collateral swap.
6. Simulation records the malicious transfer as a child of Alice’s `swap_collateral` authorization. If the wallet/client signs that returned tree, the transaction succeeds, Alice receives valid swap output, and `ATTACK_TOKEN` is transferred to the attacker.

/// Authorizes, on behalf of the current contract, one `transfer(from, to, amount)`
/// call on `token_addr` made deeper in the next contract call (for example by
/// the pool). The entry allows no further sub-invocations.
pub fn authorize_transfer_as_current(
    env: &Env,
    token_addr: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
) {
    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);
