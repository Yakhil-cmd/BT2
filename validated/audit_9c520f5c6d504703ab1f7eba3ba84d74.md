### Title
Race Condition Allows Continued Use of Superseded Address Definition ("Old Keys") After a Definition Change — Analogous to Insufficient Session Expiration After Password Change ([File: validation.js])

### Summary
When an address owner rotates their signing keys via an `address_definition_change` message, ocore's unit-validation logic does not reliably prevent a party who still possesses the pre-rotation ("old") definition/keys from authoring further, competing units against the same address while the definition change is not yet stable and before the last ball. This mirrors CVE-2021-25940 (ArangoDB): a credential change (there: password; here: address definition/keys) does not immediately and unconditionally invalidate the previous credential's ability to act.

### Finding Description
Address definition changes are recorded via the `address_definition_change` message and looked up with `storage.readDefinitionByAddress`, which resolves the *currently active, stable* definition for an address as of a given `last_ball_mci` [1](#0-0) . Because this lookup only considers definitions stable at or before `last_ball_mci`, a definition change that has been posted but is not yet stable is invisible to it — the old definition (and hence the old keys) remains valid for signing purposes from the validator's point of view until the change stabilizes.

ocore's author validation in `validateAuthor` explicitly acknowledges and historically mitigated this via `checkNoPendingChangeOfDefinitionChash`, which blocks any unit from an address that has a pending (not-yet-stable) `address_definition_change`, specifically for the non-serial (forked) case: “you can't send anything before your last keychange is stable and before last ball” [2](#0-1) .

However, `checkSerialAddressUse` only routes through this old-key check when running against a DAG state *before* `constants.pemCurvesFixMci`; once the network crosses this MCI, the code skips `checkNoPendingChangeOfDefinitionChash` entirely and goes straight to `validateDefinition`:
```
var next = (objValidationState.last_ball_mci >= constants.pemCurvesFixMci || ...) ? validateDefinition : checkNoPendingChangeOfDefinitionChash;
``` [3](#0-2) 

`validateDefinition` (the new path) only verifies that the definition supplied in the unit hashes correctly to what is already on record, or, when a definition is already on file, defers to `handleDuplicateAddressDefinition` [4](#0-3) . That handler contains an explicit, unresolved acknowledgment of exactly this race:
```
// todo: investigate if this can split the nodes
// in one particular case, the attacker changes his definition then quickly sends a new ball with the old definition - the new definition will not be active yet
...
callback(); // let it be for now. Eventually, at most one of the balls will be declared good
``` [5](#0-4) 

In other words: after a user (the legitimate address owner) posts a definition change to rotate away from a compromised/old key set, an attacker who still has the old key can — while the change is pending stabilization — post a conflicting unit signed with the old definition. The old "session" (signing capability) is not invalidated the moment the legitimate change is announced; it persists until the network reaches consensus/stability on the change, and the explicit code comment shows this was a known, deliberately deferred concern ("let it be for now").

### Impact Explanation
If an attacker has obtained an address's private key (the very reason a legitimate user would rotate/change the definition, analogous to a password change after compromise), the attacker can race the legitimate definition-change unit with a conflicting unit signed by the old, compromised key before the definition change stabilizes. Depending on which branch the network eventually finalizes as "good", this can let the attacker spend funds from the address using the old key even after the victim believed they had revoked it — a direct unauthorized-spending / fund-loss scenario, and, per the code's own comment, potentially causes node disagreement ("investigate if this can split the nodes") about which unit is valid.

### Likelihood Explanation
This requires the attacker to already know the private key/authentifiers of the address being rotated away from (the same threat model as a leaked password prompting rotation in the ArangoDB analog) and to race a conflicting unit into the DAG before the legitimate `address_definition_change` becomes stable. This is a realistic scenario precisely in the "I think my key is compromised, let me rotate" case that key-rotation mechanisms are meant to protect against, and the vulnerability window (time to stabilization) is attacker-influenceable by getting the conflicting unit included before last ball. The developers' own TODO comment indicates this was recognized but not fully closed.

### Recommendation
Reinstate (or generalize) the `checkNoPendingChangeOfDefinitionChash` protection so that it is not bypassed once `last_ball_mci >= constants.pemCurvesFixMci`. Specifically, ensure that any unit authored using an address's pre-rotation definition, while a definition change for that address is unstable/pending, is rejected outright (not merely deferred with "let it be for now"), removing the reliance on the non-serial/forked-path heuristic and closing the described race explicitly for the current validation path (`validateDefinition` / `handleDuplicateAddressDefinition`).

### Proof of Concept
1. Address `A` is controlled by key `K_old`, currently also known to an attacker.
2. The rightful owner learns of exposure and posts an `address_definition_change` message for `A` switching to `K_new`, per the payload format validated in `validateInlinePayload` [6](#0-5) .
3. Before this change becomes stable and before a new last ball includes it, the attacker composes and broadcasts a conflicting unit authored by `A` using the still-active `K_old` (an author with the old definition, or omitted definition resolved via `readDefinitionByAddress`, which still returns the old definition because the change isn't stable yet) [1](#0-0) .
4. On the current (post-`pemCurvesFixMci`) validation path, this unit is accepted by `validateDefinition`/`handleDuplicateAddressDefinition` rather than being blocked outright as the old `checkNoPendingChangeOfDefinitionChash` would have done for pre-fix DAG states [3](#0-2) [5](#0-4) .
5. Depending on DAG resolution, the attacker's unit (signed with the "revoked" key) can end up on the finalized "good" sequence, spending funds the legitimate owner believed were secured by the rotation.
