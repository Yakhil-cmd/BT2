### Title
Unbounded `account_ids` in `AccountChanges`/related `StateChangesRequestView` variants allows RPC resource-exhaustion via unmetered RocksDB prefix scans - (File: chain/jsonrpc/src/api/changes.rs)

### Summary
`RpcStateChangesInBlockByTypeRequest::parse` deserializes the request body directly via `Params::parse` with no validation of the size of `account_ids` (or `keys`) before it is handed to `ChainStore::get_state_changes`, which iterates once per account/key and performs a RocksDB prefix scan for each. An attacker can submit a single `changes` RPC request with an extremely large `account_ids` list to force the node to perform a proportionally large number of DB scans and allocations in one request/response cycle.

### Finding Description
`RpcRequest::parse` for `RpcStateChangesInBlockByTypeRequest` simply calls `Params::parse(value)` with no cap on the length of `account_ids` [1](#0-0) . `StateChangesRequestView::AccountChanges { account_ids: Vec<AccountId> }` (and the other `*_ids`-based variants) place no bound on vector length [2](#0-1) . The request flows through `changes_in_block_by_type` and eventually into `ChainStore::get_state_changes`, which loops over every `account_id` and, for each one, builds a `TrieKey`/`KeyForStateChanges` and performs a RocksDB prefix (`find_exact_iter`/`find_iter`) scan, merging results into an in-memory `StateChanges` map [3](#0-2) . There is no per-request cap on `account_ids.len()` anywhere in this path, and no metering/gas-like cost is charged for view-RPC calls of this kind, so the number of DB scans and allocations grows linearly (or worse, given RocksDB seek costs) with the size of the attacker-supplied array.

However, this issue is a **request-shape / DoS-style resource consumption issue in the RPC/view layer, not a protocol-state-affecting bug**: it does not cause fund loss, gas/storage metering bypass, authorization bypass, or state divergence. The scoped question explicitly targets "RPC/validator resource exhaustion via unmetered query," which is a legitimate finding in principle, but the actual severity depends on infrastructure-level mitigations (HTTP body-size limits, load balancers, rate limiting) that are typically deployed in front of public RPC endpoints and configured at the operator level — no such caps were found in this repository's `chain/jsonrpc` crate itself (no `max_body_size`/`JsonConfig`/payload-limit configuration was found in `chain/jsonrpc/src/lib.rs`).

### Impact Explanation
A crafted `changes` (or `EXPERIMENTAL_changes`) JSON-RPC request with a very large `account_ids` array can force a single RPC/view-client thread to perform a large number of sequential RocksDB prefix scans and heap allocations, consuming CPU and memory disproportionate to the cost of sending the request. This matches the "node panic or unbounded resource use" impact class for RPC nodes specifically (view-client / non-consensus-critical path). It does not affect validators' consensus state or chain progression directly, since state-change queries are served by the view client against already-committed state, and a single overloaded RPC node does not force protocol divergence.

### Likelihood Explanation
Preconditions are minimal: only public, unauthenticated RPC access is required (no funded account, no special permissions). The request is trivially reproducible by any client capable of sending an HTTP POST with a large JSON array of account-id strings. The primary constraint is any HTTP request body size limit configured at the reverse proxy or JSON deserialization layer, which was not found to be enforced explicitly inside the `chain/jsonrpc` crate's request-parsing code for this endpoint. This makes exploitation feasible against RPC nodes that do not deploy such external protections, though it is a "soft" resource-exhaustion issue whose real-world impact is highly dependent on operator-side infrastructure rather than a core protocol/consensus bug.

### Recommendation
Add an explicit upper bound (e.g. a constant such as `MAX_ACCOUNT_IDS_PER_STATE_CHANGES_REQUEST`) checked in `RpcStateChangesInBlockByTypeRequest::parse` (or in the `From<StateChangesRequestView> for StateChangesRequest>` conversion) that rejects requests where `account_ids.len()` (or `keys.len()`) exceeds the limit, returning an `RpcStateChangesError` (e.g., a new `TooManyAccounts` variant) instead of proceeding to `get_state_changes`. Additionally, consider bounding total response size/time within `ChainStore::get_state_changes` itself as a defense-in-depth measure.

### Proof of Concept
Integration test (extending the existing `test_rpc_changes_scatter_gather`-style harness in `test-loop-tests/src/tests/sharded_rpc.rs`):
1. Build a `TwoShardHarness`/RPC test node as in `test_rpc_changes_scatter_gather` [4](#0-3) .
2. Construct a `changes` JSON-RPC request via `RpcStateChangesInBlockByTypeRequest { state_changes_request: StateChangesRequestView::AccountChanges { account_ids }, .. }` where `account_ids` contains, e.g., 1,000,000 distinct freshly-generated `AccountId` strings (none of which need to exist on-chain).
3. Send the request through `send_jsonrpc_request` as done in the existing test [5](#0-4) , measuring wall-clock time, CPU, and memory consumed by the RPC node process while handling this single request.
4. Assert that either (a) the request is rejected early with a bounded/limit error, or (b) processing time/memory stays within a small bound (e.g., under some millisecond/byte threshold) regardless of `account_ids.len()`. Currently no such rejection exists, and processing time/memory scales with `account_ids.len()`, demonstrating the unbounded resource consumption described above.
