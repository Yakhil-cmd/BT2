### Title
Webhook signature verification binds a different field (`repository.owner.login`) than the field handlers trust for repository identity (`repository.full_name`), allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate a webhook against using `repository.owner.login` (or `organization.login`), but every webhook `Handler` resolves the target `Repository`/`Stack` using the separate `repository.full_name` field. In a multi-organization Shipit deployment, the org owner who installs the GitHub App chooses and knows their own `webhook_secret` (per `docs/setup.md`), so they can HMAC-sign an arbitrary crafted payload with their own known secret while setting `repository.full_name` to point at a completely different (victim) organization's repository. Because signature verification and repository targeting are keyed off two independent fields, the "organization that authenticated" and the "repository that is written" are never checked for consistency.

### Finding Description
`verify_signature` derives the authenticating organization strictly from `repository.owner.login`: [1](#0-0) [2](#0-1) 

That organization is used only to fetch the corresponding `GitHubApp` config/secret (`Shipit.github(organization: repository_owner)` → `verify_webhook_secret`), and once the HMAC check passes, the entire raw JSON body — including any other embedded field — is treated as trusted: [3](#0-2) 

Every webhook `Handler`, however, resolves which `Stack`/`Repository` to act on using an entirely separate field, `repository.full_name`: [4](#0-3) [5](#0-4) 

Per `docs/setup.md`, each organization's GitHub App (and its `webhook_secret`) is set up and known by that organization's own admin ("Fill it with some randomly generated string, and keep it in clear on the side"): [6](#0-5) 

Because Shipit supports configuring multiple organizations under one installation (confirmed by `test/dummy/config/secrets_double_github_app.yml` and `Shipit.github(organization:)` lookups), an org admin who legitimately knows their own `webhook_secret` can HMAC-sign a payload where `repository.owner.login`/`organization.login` = their own org (so `verify_signature` picks and successfully verifies against their own known secret), while independently setting `repository.full_name` = `"victim-org/victim-repo"`. The signature check only proves "this payload was signed with attacker-org's secret" — it does not prove "this payload's target repository belongs to attacker-org." The equality that should hold — `organization authenticated == owner(repository written)` — is never enforced.

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" trust binding described as an accepted analog class. A forged `push` event can enqueue `GithubSyncJob` against a victim stack, and a forged `status`/`check_suite` event can mark an arbitrary victim commit as CI-green. If the targeted victim stack has `continuous_deployment` enabled (see `Stack#deployable?`/`trigger_continuous_delivery` in `app/models/shipit/stack.rb`), a forged successful CI status for an existing commit can trigger an unauthorized, real deploy of that stack — a cross-organization write plus an unauthorized deploy, matching the Critical/High impact categories (cross-repository writes, unauthorized deploy).

### Likelihood Explanation
Requires only that the target Shipit instance is configured with more than one GitHub organization (a documented, supported configuration) and that the attacker controls one of those organizations' GitHub Apps (which they legitimately set up and thus know the `webhook_secret` for). No compromise of the victim's secret, session, or `ApiClient` token is required — only crafting an arbitrary HTTP POST to `/webhooks` with a valid HMAC for the attacker's own known secret.

### Recommendation
After signature verification, before dispatching to handlers, verify that the repository/organization actually referenced by the payload (`repository.full_name`'s owner, or `repository.owner.login`) matches a `Repository`/`Stack` that is actually configured under the same organization that was used to select/verify the webhook secret. Reject (422) any webhook where the two do not match, i.e., enforce `repository_owner == repository.full_name.split('/').first` (case-insensitively) before handler dispatch.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` and `victim-org`, each with its own GitHub App and `webhook_secret` (per `docs/setup.md` multi-org config), and a `victim-org/victim-repo` stack with `continuous_deployment: true`.
2. As the (legitimate) admin of `attacker-org`, who knows `attacker-org`'s `webhook_secret`, craft a `status` (or `push`) event JSON body with:
   - `repository.owner.login` = `"attacker-org"` (so `WebhooksController#repository_owner` selects and successfully verifies against `attacker-org`'s secret)
   - `repository.full_name` = `"victim-org/victim-repo"`
   - `sha` = an existing commit on the victim stack, `state` = `"success"`
3. Compute `X-Hub-Signature` as `sha1=HMAC-SHA1(attacker-org-secret, raw_body)` and POST to `/webhooks` with header `X-Github-Event: status`.
4. `verify_signature` passes (attacker's own secret matches). `Shipit::Webhooks.for_event('status')` dispatches to the status handler, which uses `payload.dig('repository','full_name')` = `"victim-org/victim-repo"` to locate and update the victim's stack/commit status, potentially triggering an unauthorized continuous deployment of `victim-org/victim-repo`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
