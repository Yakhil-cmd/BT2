### Title
Signature verification keyed on `repository.owner.login` is decoupled from the `repository.full_name` used to locate the mutated stack, allowing an org with no `webhook_secret` to forge label mutations on any other org's `ReviewStack` env - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` derives the organization used for HMAC verification from `params.dig('repository','owner','login')` (or `organization.login`), while `LabelCapturingHandler` (and its siblings) locate the actual `Shipit::Repository`/`ReviewStack` to mutate via `params.repository.full_name`. These are two independently attacker-controlled JSON fields in the same forged payload, with no consistency check between them. If any org configured on the Shipit instance has no `webhook_secret` set, `GitHubApp#verify_webhook_signature` returns `true` unconditionally for a payload whose `repository.owner.login` names that org, regardless of what `repository.full_name` says — letting the attacker point `full_name` at a victim org/repo that does have a secret configured.

### Finding Description
The broken binding, stated as an equality that the code assumes but never checks: `repository_owner (used for signature verification) == owner(repository.full_name) (used for the DB lookup)`. In fact both values come from attacker-supplied JSON in the same request and can diverge freely.

- `verify_signature` computes `repository_owner` from `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0)  and passes it to `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`, calling `head(422)` only if verification fails [2](#0-1) .
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when the org's config has no `webhook_secret`: `return true unless webhook_secret` [3](#0-2) .
- `LabelCapturingHandler#repository` looks up the actual `Shipit::Repository` via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [4](#0-3) , and `Repository.from_github_repo_name` simply splits `full_name` on `/` and does a `find_by(owner:, name:)` [5](#0-4) , with no comparison back to the `repository.owner.login` value used for signature verification.
- The handler then resolves the `ReviewStack` for the (attacker-chosen) `environment` = `"pr#{params.number}"` via `ReviewStackAdapter#stack` [6](#0-5) , and persists `params.pull_request.labels.map(&:name)` onto `stack.pull_request` [7](#0-6) .
- Those label names become uppercased environment variables via `ReviewStack#env`, merged into every subsequent deploy/rollback run on that stack [8](#0-7) .

Exploit flow: the attacker picks/creates an org "attacker-org" registered on the target Shipit instance that has no `webhook_secret` configured (this is a real, supported Shipit configuration — some orgs are legitimately not configured with a secret). The attacker sends `POST /webhooks` with `X-Github-Event: pull_request`, action=`labeled`, `repository.owner.login = "attacker-org"` (so `verify_signature` calls `Shipit.github(organization: "attacker-org")`, which has no secret and returns `true` for any signature, valid or not), but `repository.full_name = "victim-org/victim-repo"` (a completely different, secured org whose review stack has `bot_login` configured). The controller does not reject this because `repository_owner` (attacker-org) and the `full_name`'s owner (victim-org) are never compared — the equality the code implicitly relies on is false and unchecked. The handler proceeds to look up the real victim repository/stack and mutate its `PullRequest#labels`, and hence its `ReviewStack#env`, without ever having authenticated a payload from `victim-org`.

Existing guards do not stop this: `verify_signature` only checks that *some* org (potentially attacker-controlled) considers the signature valid, not that the org matches the repository being mutated; `drop_unhandled_event` only checks the event type is handled, not payload consistency; the `ExplicitParameters` schema on `LabelCapturingHandler` requires the shape of `repository.full_name` but places no constraint tying it to `repository.owner.login`; `Repository.from_github_repo_name` performs no cross-check either.

### Impact Explanation
An attacker can inject arbitrary uppercased environment-variable keys/values (`"true"`) into a victim `ReviewStack`'s deploy/rollback environment by controlling only an unrelated, secret-less org's webhook acceptance path, without ever possessing the victim org's `webhook_secret`. Because auto-triggered deploys/rollbacks on that review stack execute as the configured bot identity (`bot_login`), and the injected env vars are merged into the environment passed to `Command`/`PTY.spawn` during task execution, this is a state change (label/env mutation) on a repository/stack that never authenticated the request — matching the Critical category "a payload for one repository mutating another's stack" and potentially enabling unauthorized deploy behavior driven by attacker-controlled env flags. This is repeatable against any victim org/stack as long as at least one org on the instance has no `webhook_secret` configured, and the attack scales to any number of victim repositories/stacks by varying `repository.full_name` and `number` in the forged payload.

### Likelihood Explanation
Preconditions: (1) the Shipit instance must have at least one configured GitHub org/app entry with no `webhook_secret` set — a realistic and, per the code, explicitly supported configuration (`return true unless webhook_secret`); (2) the victim org must have a `ReviewStack` (PR-based stack) already provisioned for the targeted PR number, and ideally `bot_login` configured to amplify impact. No Shipit session, API token, or any secret is required — cost is a single crafted HTTP POST with the correct JSON shape (`ExplicitParameters` schema fields must be present, all of which are attacker-controllable) and any `X-Hub-Signature` value (ignored due to the no-secret org). This is fully repeatable and requires no interaction with GitHub's real webhook infrastructure.

### Recommendation
In `Shipit::WebhooksController#verify_signature`, derive the organization used to select the `GitHubApp`/secret strictly from a value that is authoritative for the resource being mutated — and additionally validate that the org used for verification matches the owner encoded in `params.repository.full_name` before dispatching to handlers. Reject requests where `repository.owner.login`/`organization.login` does not match the owner segment of `repository.full_name`. Additionally, consider requiring a non-blank `webhook_secret` for every org that has any repositories with tracked stacks/review stacks, i.e., disallow the signature-bypass fallback (`return true unless webhook_secret`) for orgs that have registered repositories, or emit a hard failure/warning if a repository's owning org has no secret configured.

### Proof of Concept
Minitest plan (add to `test/controllers/webhooks_controller_test.rb`):
1. Configure two orgs in the test `Shipit` config: `secured-org` (with `webhook_secret: "s3cr3t"` and `bot_login: "shipit-bot"`) and `open-org` (no `webhook_secret`).
2. Create `Shipit::Repository` with `owner: "secured-org", name: "victim-repo"`, and a `Shipit::ReviewStack` with `environment: "pr42"` for it, with an existing `PullRequest` record with empty `labels`.
3. Build a `pull_request` `labeled` payload matching `LabelCapturingHandler`'s `ExplicitParameters` schema, setting:
   - `repository.full_name = "secured-org/victim-repo"`
   - `repository.owner.login = "open-org"`
   - `number = 42`
   - `pull_request.labels = [{name: "malicious"}]`
4. `POST /webhooks` with header `X-Github-Event: pull_request` and an arbitrary/garbage `X-Hub-Signature`, without ever using `secured-org`'s real `webhook_secret`.
5. Assert the response is `200 OK` (i.e., signature check passed via `open-org`'s no-secret bypass).
6. Assert `stack.reload.pull_request.labels` now includes `"malicious"`, and `stack.env["MALICIOUS"] == "true"` — demonstrating a state change on `secured-org/victim-repo`'s stack was produced by a payload that only ever authenticated against `open-org`.

Binding to test explicitly: before the request, `repository_owner_used_for_signature ("open-org") != owner_of_mutated_repository ("secured-org")`; after the request, the mutation still occurred, proving the invariant "a forged event cannot produce a state change on a stack it did not authenticate" is violated.
