### Title
`ReviewStack#env` merges unfiltered GitHub PR label names as environment-variable keys, bypassing the `deploy_spec` allow-list enforced everywhere else - ([File: app/models/shipit/review_stack.rb])

### Summary
`ReviewStack#env` takes every label attached to the associated pull request and injects it as an environment-variable key (`label_name.upcase => 'true'`) merged on top of `Stack#env`, with no check against `deploy_spec.machine_env`, `VariableDefinition` names, or `EnvironmentVariables#permit`. Every other environment source in the engine (task/deploy/rollback user-supplied `env`) is filtered through `EnvironmentVariables#permit`/`filter_deploy_envs`/`filter_rollback_envs`, but this path is not, so an unprivileged PR author can inject arbitrary-named variables into the command environment used for provisioning/dependency/deploy steps of someone else's repository.

### Finding Description
The binding that should hold is: *the set of environment-variable keys reaching `Command`/`PTY.spawn` for a stack equals the union of `Stack#env`'s fixed keys and the keys permitted by `deploy_spec.machine_env` / `VariableDefinition`s (via `EnvironmentVariables#permit`)*. `ReviewStack#env` violates this: [1](#0-0) 

Trace:
1. `LabelCapturingHandler#capture_labels` stores `params.pull_request.labels.map(&:name)` verbatim from the webhook payload, with no allow-list or character filtering, into `pull_request.labels`: [2](#0-1) 
2. `ReviewStack#env` maps each label name to an upper-cased key with value `"true"` and merges it over `super` (i.e., `Stack#env`), with no filtering step: [1](#0-0) 
3. `TaskCommands#env` merges `@stack.env` (which for review stacks is `ReviewStack#env`) directly into the environment that later has `deploy_spec.machine_env` and `@task.env` merged on top - the label-derived keys are never routed through `EnvironmentVariables#permit`: [3](#0-2) 
4. Contrast with the sanctioned filtering path used for user-supplied task/deploy/rollback env, which is explicitly whitelisted via `deploy_spec.filter_deploy_envs`/`filter_rollback_envs` → `EnvironmentVariables#permit`, which raises `NotPermitted` for any key not in the `VariableDefinition` list: [4](#0-3) [5](#0-4) 

An attacker who can only open/label a pull request against the target repository (no Shipit account, no maintainer role) controls the exact string that becomes an environment variable *name* in the shell environment used to run that repository's install/deploy/provision commands (`Command`/`PTY.spawn`), completely independent of what the repository's own `shipit.yml` `machine`/`deploy.variables` allow-list declares. Existing guards (`EnvironmentVariables#permit`, `filter_deploy_envs`, `filter_rollback_envs`, webhook signature verification, `ExplicitParameters` schema) do not intercept this: the webhook schema only validates types/presence of `labels[].name` as a `String`, not its allowed set, and no permit-based filtering is applied to `ReviewStack#env`'s output.

The one constraint is that the injected value is always the literal string `"true"` - the attacker controls the *variable name*, not its value. This still allows overriding/defining any variable name (e.g. tool-command-lookup variables such as `GIT_SSH_COMMAND`, `GIT_ASKPASS`, `BUNDLE_GEMFILE`, or custom variables a deploy script branches on) with the fixed value `"true"`, which is itself a valid POSIX no-op command for shell-invoked lookup variables, potentially causing steps that shell out to those variables to silently no-op or behave unexpectedly, depending on the specific `shipit.yml` deploy steps.

### Impact Explanation
For any repository configured with review stacks, an external PR author can force additional, arbitrary-named environment variables into the review-stack's provisioning, dependency-install, and deploy command environment, bypassing the `machine_env`/`VariableDefinition` allow-list that is supposed to bound what env vars a stack can expose. Because the attacker cannot control the *value* (fixed to `"true"`), full RCE via env-var value injection (e.g., `LD_PRELOAD=/attacker/path`) is not directly achievable from this bug alone; the demonstrable, in-scope impact is that the promised allow-list binding (`Command#unbundled_env` keys ⊆ permitted keys) is broken for every review stack, for any distinct label name chosen by an unprivileged PR author, against a repository the attacker does not own. This matches a High-severity divergence (unauthorized influence over deploy/provisioning environment for another party's stack), though it falls short of a demonstrated Critical RCE because the value is not attacker-controlled.

### Likelihood Explanation
Preconditions: the target repository must use `Shipit::ReviewStack` (review-stacks feature enabled) and have its GitHub webhook wired to Shipit (standard engine configuration, not attacker-controlled). The attacker only needs to open a pull request and add a label with an arbitrary name (or have a bot/collaborator add labels, or use `pull_request_target`-style automation) - no Shipit credentials required. Cost is trivial and fully repeatable per PR/per label, against any repository configured for review stacks.

### Recommendation
Filter the label-derived environment hash through the same allow-list mechanism used elsewhere, e.g. `EnvironmentVariables.with(labels_hash).permit(deploy_spec.machine_env.keys / VariableDefinition list)`, or drop this feature entirely if it's not intended to expose arbitrary label names as env vars. At minimum, require an explicit opt-in allow-list per repository (e.g. a `review.labels` config in `shipit.yml`) before any label name is turned into an environment variable.

### Proof of Concept
In `test/models/shipit/review_stack_test.rb` (or equivalent), construct a `ReviewStack` with a stubbed `pull_request` whose `labels` is `%w[RUBYOPT NODE_OPTIONS GIT_SSH_COMMAND BUNDLE_GEMFILE LD_PRELOAD]`, and a `deploy_spec` stub whose `machine_env` returns `{}` and `deploy_variables` returns `[]`. Assert:
```ruby
allowed_keys = stack.deploy_spec.machine_env.keys + stack.deploy_spec.deploy_variables.map(&:name)
injected_keys = stack.env.keys - Shipit::Stack.new.env.keys # keys added by ReviewStack#env beyond base Stack#env
assert (injected_keys - allowed_keys).any?, "expected unfiltered label keys to leak past the allow-list"
assert_equal 'true', stack.env['RUBYOPT']
```
This proves `stack.env`'s keys are a strict superset of the allow-list derived from `deploy_spec`, with no call to `EnvironmentVariables#permit` occurring anywhere in `ReviewStack#env`.
