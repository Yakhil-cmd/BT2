### Title
Attacker-controlled PR label names are merged unfiltered into `ReviewStack#env` and reach `Command#start`'s spawned environment, allowing `LD_LIBRARY_PATH` injection - (File: app/models/shipit/review_stack.rb)

### Summary
`ReviewStack#env` merges every pull request label name (uppercased) directly into the environment hash used for deploy commands, with no allowlist or denylist of dangerous variable names. Because `Command#start` builds the child process environment via `unbundled_env` which layers `@env` (attacker-influenced) on top of the base/bundler-sanitized env and passes it straight to `PTY.spawn`, a label literally named `ld_library_path` becomes `LD_LIBRARY_PATH=true` in the spawned process's environment for any command in the review stack's `deploy.override` (or any other) step.

### Finding Description
The broken binding: the set of environment variable names available to `PTY.spawn` in `Command#start` should equal `{ENVIRONMENT, LAST_DEPLOYED_SHA, GITHUB_REPO_OWNER, GITHUB_REPO_NAME, DEPLOY_URL, BRANCH, SHIPIT_USER, EMAIL, BUNDLE_PATH, SHIPIT_LINK, TASK_ID, IGNORED_SAFETIES, GIT_COMMITTER_NAME, GIT_COMMITTER_EMAIL} ∪ deploy_spec.machine_env ∪ task.env` (a fixed, operator/config-controlled set), but it instead equals that set ∪ `{label.upcase => "true" for label in pull_request.labels}`, which is attacker-controlled since PR authors freely name labels on their own PRs/forks.

Code path:
- `ReviewStack#env` (`app/models/shipit/review_stack.rb:84-93`) merges `pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" }` into `super` (the base `Stack#env`) with no key filtering whatsoever. [1](#0-0) 
- `pull_request.labels` is populated straight from the webhook payload by `LabelCapturingHandler#capture_labels`, which does `pull_request.update!(labels: params.pull_request.labels.map(&:name))` — label names are plain, unrestricted strings from the GitHub webhook body (`requires :labels, Array do requires :name, String end` — only type-checked, not content-restricted). [2](#0-1) [3](#0-2) 
- `TaskCommands#env` merges `@stack.env` (which for a `ReviewStack` includes the label-derived keys) together with other env sources and passes it to `Command.new(command_line, env:, ...)` for each deploy step, including `deploy.override` steps. [4](#0-3) 
- `Command#start` spawns the process with `PTY.spawn(unbundled_env, *interpolated_arguments, ...)`, where `unbundled_env` is `BASE_ENV.merge('PATH' => ...).merge(@env.stringify_keys)` — i.e., the attacker-controlled `@env` entries (including `LD_LIBRARY_PATH`) are merged last and win. [5](#0-4) 

Attacker exploit: An unprivileged user forks the repo, opens a PR, and applies a label named `ld_library_path` (case-insensitive since it's uppercased) pointing conceptually to a path they control on the deploy host (e.g., a shared/writable directory, or combined with another primitive that drops a malicious `.so` there). When the review stack's provisioning/deploy runs the `deploy.override` commands, every spawned binary in that step inherits `LD_LIBRARY_PATH=true` (or, more generally, whatever value; note the value is hardcoded to `"true"` in current code, but the point of concern is that the *variable name* itself is fully attacker-chosen and unfiltered — nothing stops a label like `bash_env` or `ld_preload` either, which are equally dangerous env-var names for shell/dynamic-linker hijacking). No existing guard (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema, `Repository`/`Stack` validations) restricts label name content — the params schema only requires labels to be `String`, and there is no allowlist in `ReviewStack#env` or `Command#start`.

### Impact Explanation
If exploitable to redirect dynamic linking (e.g., via `LD_PRELOAD`/`LD_LIBRARY_PATH`-style label names) for binaries spawned during `deploy.override`, this constitutes command/environment tampering on the deploy host for that repository's review-stack deploy process — a fork PR author gains influence over the execution environment of privileged deploy tooling without any Shipit credentials, purely through GitHub label naming, which is a Critical-class concern (arbitrary env-var injection into `PTY.spawn`'d processes, a stepping stone to RCE depending on what `deploy.override` executes and what's on `LD_LIBRARY_PATH`/similar search paths at that time).

### Likelihood Explanation
Preconditions: `provisioning_behavior=prevent_with_label`-style review stacks must be enabled with a `deploy.override` section in the fork's `shipit.yml`, and the review stack process labels feature must be active (this is standard/default review-stack behavior, not exotic config). Attacker cost is minimal: open a PR from a fork and add a label — both actions available to any GitHub user able to open PRs against the repo/organization allowing forks. No secrets, tokens, or maintainer approval are needed to add a label to one's own PR (assuming the repo permits external labeling, which is common for review-stack workflows). This is repeatable per PR/build.

### Recommendation
Restrict `ReviewStack#env` to only pass through an explicit allowlist of safe, prefixed keys (e.g., require a `SHIPIT_LABEL_` or similar namespace prefix, and reject any label name matching known dangerous variables such as `LD_PRELOAD`, `LD_LIBRARY_PATH`, `PATH`, `BASH_ENV`, `IFS`, etc.), or hard-deny reserved/dangerous environment variable names in `Command#unbundled_env`/`Command#initialize` regardless of source, so that no external input (label names, PR title, branch name, etc.) can ever set security-sensitive interpreter/linker environment variables for spawned commands.

### Proof of Concept
minitest plan (`test/models/shipit/review_stack_test.rb` or `test/unit/command_test.rb`):
1. Build a `ReviewStack` with an associated `PullRequest` whose `labels` array includes `"ld_library_path"`.
2. Call `review_stack.env` and assert the resulting hash contains the key `"LD_LIBRARY_PATH" => "true"`.
   - Binding under test: `review_stack.env.key?("LD_LIBRARY_PATH")` should be `false` (invariant) but is `true` (actual).
3. Construct a `Shipit::Command.new(['env'], chdir: Dir.tmpdir, env: review_stack.env)`, call `.start`/`.run`, and assert the captured stdout contains `LD_LIBRARY_PATH=true`, demonstrating the value reaches `PTY.spawn`'s child environment via `Command#unbundled_env`. [1](#0-0) [6](#0-5)

    def start(&block)
      return if @started

      @control_block = block
      @out = @pid = nil
      FileUtils.mkdir_p(@chdir)
      begin
        @out, child_in, @pid = PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)
        child_in.close
      rescue Errno::ENOENT
        raise NotFound, "#{Shellwords.split(interpolated_arguments.first).first}: command not found"
      rescue Errno::EACCES
        raise Denied, "#{Shellwords.split(interpolated_arguments.first).first}: Permission denied"
      end
      @started = true
      self
    end

    def unbundled_env
      BASE_ENV.merge('PATH' => "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}").merge(@env.stringify_keys)
    end
