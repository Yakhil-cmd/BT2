### Title
Any paired device can delete another party's pending multisig shared-address negotiation via unauthenticated `reject_new_shared_address` message - (File: `wallet.js`)

### Summary
The `reject_new_shared_address` device-message handler deletes a pending multi-party shared-address negotiation record by `address_definition_template_chash` alone, with no check that the sending device is actually one of the cosigners listed in `pending_shared_address_signing_paths` for that chash. This mirrors the JOJO `requestWithdraw` bug class: a state-changing operation intended to be restricted to the legitimate parties of a pending, multi-step process performs no real per-caller authorization check, so an unrelated/unprivileged actor can cancel someone else's pending action, causing denial of service.

### Finding Description
In `wallet.js`, the hub message handler for `reject_new_shared_address` only validates that the supplied chash is well-formed and then unconditionally deletes the pending shared address: [1](#0-0) 

It forwards directly to `deletePendingSharedAddress`, which performs the deletion keyed solely on `definition_template_chash`, with no `device_address` filter at all: [2](#0-1) 

This is asymmetric with the sibling `approve_new_shared_address` handler, whose underlying `approvePendingSharedAddress` at least scopes its `UPDATE` to rows matching `device_address=from_address` (so an outsider's approval has no effect): [3](#0-2) 

Because `reject_new_shared_address` has no equivalent `WHERE device_address=?` restriction, *any* correspondent device that knows (or can compute/observe) the `address_definition_template_chash` — which is just `objectHash.getChash160(arrAddressDefinitionTemplate)`, a deterministic, non-secret hash of the shared-address definition template — can wipe out `pending_shared_addresses` and all `pending_shared_address_signing_paths` rows for that negotiation, even though it is not one of the actual invited cosigners: [4](#0-3) 

This is the same root-cause pattern as the JOJO report: `requestWithdraw`'s `isWithdrawValid` allowed any caller to modify another address's pending withdrawal because the authorization check (`spender==from || allowance>=amount`) is trivially satisfiable; here the authorization check for a state-mutating "cancel my participation" message is missing entirely, letting any paired device impersonate a "reject" on behalf of a negotiation it isn't part of.

### Impact Explanation
A malicious or compromised paired device (correspondent) that has, at any point, seen or brute-forced/derived a `definition_template_chash` for a multisig/shared-address setup between other users can permanently and repeatedly delete their pending negotiation record. Because deletion also removes each participating device's already-recorded `approval_date`/`address` fields for that chash, this griefs the entire multi-party address setup: legitimate cosigners' offers, approvals and in-flight state are discarded, and the shared address (needed to receive/spend funds, e.g., for arbiter contracts or wallet co-signing) can never complete, indefinitely denying that group the ability to finalize the address. Since the handler is reachable from any correspondent hub message without further authorization, it is a general DoS primitive against other users' AA/wallet-setup flows involving shared/multisig addresses.

### Likelihood Explanation
Reaching this requires only being a paired device (a normal, unprivileged correspondent relationship) able to send arbitrary `reject_new_shared_address` hub messages, and knowledge of the target chash. The chash is not cryptographically secret — it's derived from the (often templated/predictable) address definition and is exchanged between the actual invited devices during `create_new_shared_address`/`approve_new_shared_address`, so it can also leak via a compromised or malicious cosigner, a shared hub, or by observing correlated traffic. No signature over the specific action ties the message to a particular right to cancel, unlike the approve path.

### Recommendation
Scope `deletePendingSharedAddress` (and its `reject_new_shared_address` caller) so it only deletes/affects the row(s) belonging to the sending `from_address`, analogous to how `approvePendingSharedAddress` restricts its `UPDATE ... WHERE device_address=?`. E.g., `reject_new_shared_address` should first verify a `pending_shared_address_signing_paths` row exists for `(definition_template_chash, from_address)` before deleting the pending address for the group, or should only clear that participant's row and only cascade-delete the whole negotiation once all/only the legitimate initiator rejects.

### Proof of Concept
1. Device A and Device B (and possibly more) begin creating a shared multisig address via `create_new_shared_address` → `approve_new_shared_address`; the resulting `address_definition_template_chash` is exchanged among their devices as part of the protocol.
2. Device C (any paired correspondent of either A or B, or anyone who otherwise learns/derives the chash) sends a `reject_new_shared_address` hub message with that same `address_definition_template_chash`, without being listed in `pending_shared_address_signing_paths` for it.
3. `wallet.js`'s handler (lines 228-234) calls `walletDefinedByAddresses.deletePendingSharedAddress(chash)` unconditionally, which deletes all `pending_shared_address_signing_paths` and the `pending_shared_addresses` row for that chash regardless of who sent the message.
4. Device A and B's pending shared-address negotiation is destroyed; they must restart the entire process, and Device C can repeat this indefinitely to prevent the address from ever being finalized.
