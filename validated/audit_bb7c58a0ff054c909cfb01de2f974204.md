### Title
Stale oracle snapshot remains usable after an in-callback governance price update - (File: contracts/controller/src/strategies/flash_position.rs)

### Summary
`flash_position` creates one `Context`, prefetches oracle prices, invokes a caller-selected Wasm receiver, and then deposits and risk-checks the resulting position through the same cache. [1](#0-0)  During that callback, anyone may execute a ready governance operation because `authorize_executor(None)` performs no authentication or role check. [2](#0-1)  If that ready operation targets the configured price aggregator and lowers a collateral price, the account is finalized under the now-invalid prefetched price. [3](#0-2) 

### Finding Description
`process_flash_position` requires the receiver to be deployed Wasm and excludes only the controller and pool; governance is therefore a reachable callback target. [4](#0-3)  The flow loads or creates the account, validates the requested collateral, and calls `prefetch_strategy_prices` before entering `with_flash_guard`. [5](#0-4)  The receiver callback runs inside that guard, after the debt has been minted and forwarded, but before collateral measurement, deposit, and final risk evaluation. [6](#0-5) 

A receiver can call governance’s ready-operation execute path with `executor = None`; `authorize_executor` explicitly treats `None` as permissionless. [2](#0-1)  The executed operation can resolve to the configured price-aggregator client, for example a scheduled change to an asset’s source or valuation parameters. [7](#0-6) [3](#0-2)  After the callback returns, `collect_collateral_deposits`, `process_deposit`, and `strategy_finalize` still use the `Context` whose prices were loaded before that state transition. [8](#0-7) 

This is the lending-protocol analogue of use-after-free: the callback invalidates the oracle configuration backing the retained price object, and the caller continues to consume the stale object for authorization-critical solvency arithmetic. [9](#0-8) 

### Impact Explanation
An attacker can create debt sized against a stale high collateral valuation while the atomically executed governance operation has already lowered that collateral’s current valuation. [9](#0-8)  The attacker keeps the borrowed tokens, while the finalized position is immediately undercollateralized under the new price. [10](#0-9)  If the price reduction exceeds the liquidation bonus coverage, liquidation leaves residual bad debt and pool suppliers absorb the shortfall, causing theft of user funds or protocol insolvency. [11](#0-10) 

### Likelihood Explanation
The attacker only needs a suitable governance operation to already be ready; execution is intentionally permissionless when `executor` is `None`. [2](#0-1)  The attacker can bundle the configuration transition and leveraged borrow atomically through their own Wasm receiver, rather than merely racing the operation in another transaction. [12](#0-11)  A large correction to an existing price source or decimals configuration provides the required difference between the cached and current valuations. [3](#0-2) 

### Recommendation
Treat oracle state as invalidated by the receiver callback. After `invoke_receiver` returns, force `Context` to refresh every cached price and market index used by the subsequent deposit and final risk checks, or compare a price-aggregator configuration/version epoch captured before the callback with the epoch afterward and revert on any change. [9](#0-8)  The refresh-or-revert check should run before `process_deposit`, refund processing, `require_flash_position_still_open`, and `strategy_finalize`. [8](#0-7) 

### Proof of Concept
1. Governance schedules a ready operation targeting the configured price aggregator that changes collateral asset `C`’s source or valuation parameters so its returned price falls from `P_old` to `P_new`.
2. The attacker deploys a Wasm receiver whose `execute_flash_position` callback first calls governance’s ready-operation `execute` path with `executor = None`, then transfers at least `C_min` of `C` to the controller. [2](#0-1) 
3. The attacker invokes `controller.flash_position(caller = receiver, account_id = 0, spoke_id = S, mode = Multiply, debt = D, amount = A, receiver = receiver, collaterals = [(C, C_min)], refund_assets = [])`. [13](#0-12) 
4. Before the callback, the controller prefetches `P_old`; during the callback, governance activates `P_new`; after the callback, the controller deposits `C` and passes LTV/HF checks using the retained `P_old`. [9](#0-8) 
5. The attacker retains the forwarded `D` tokens while the account’s collateral is worth `P_new`, leaving it immediately liquidatable and, when `P_new * collateral` is below the debt plus liquidation bonus, leaving unrecoverable bad debt for suppliers. [8](#0-7) [11](#0-10)
