## Analysis

The bug class from the report is: a value used to compute/verify an authenticity check is not the same value that downstream code trusts and acts upon. In `shipit-engine--023` this pattern is directly present in the webhook ingestion pipeline, breaking the binding *"organization authenticated versus the repository that is written."*

### Root cause

`Shipit::WebhooksController#verify_signature` picks which GitHub App/secret to verify the HMAC signature against using only `repository.owner.login` (or `organization.login`) taken from the **unauthenticated** JSON body: [1](#0-0) [2](#0-1) 

Signature verification itself is a no-op whenever the resolved organization has no `webhook_secret` configured — which is the documented default in every example config (`webhook_secret: # nil`): [3](#0-2) [4](#0-3) 

Once `verify_signature` passes, the raw payload is dispatched to handlers unmodified, and handlers resolve the **target repository/stack from a different field**, `repository.full_name`, via `Handler#repository_name`/`#stacks`: [5](#0-4) [6](#0-5) 

So the field that gates the trust decision (`repository.owner.login`, used to pick the org/secret) and the field that determines what gets acted upon (`repository.full_name`, used to look up the `Stack`) are **independent, attacker-controlled fields in the same unauthenticated JSON body**. `repository.owner.login` and `repository.full_name`'s owner segment do not have to match — nothing in `WebhooksController` or `Handler` cross-checks them.

### Exploitation

In a multi-organization Shipit deployment (the documented "Using Multiple Github Applications" setup — `config/secrets.development.shopify.yml`, `test/dummy/config/secrets_double_github_app.yml`, `docs/setup.md:182-209`), if **any** configured organization is left with `webhook_secret: nil` (shown as the default in every example), `verify_webhook_signature` returns `true` unconditionally for that organization: [7](#0-6) 

An unauthenticated attacker can then POST to `/webhooks` with:
- `X-Github-Event: push` (or `status`, `check_suite`, `membership`, `pull_request`)
- `repository.owner.login` = the org with no webhook secret (verification auto-passes)
- `repository.full_name` = `victim-org/victim-repo` — an entirely different, real stack registered under an org that *does* have a webhook secret configured

Because `verify_signature` never checks that `repository.owner.login` and `repository.full_name`'s owner match, and never re-derives the secret from `repository.full_name`, the forged event is accepted and dispatched to handlers operating on the victim stack:

- `status` handler creates arbitrary `Status` records (arbitrary `state`, `context`, `description`, `target_url`) for existing commits on the victim stack — this can fake a passing/required CI status, which is exactly the kind of trust bypass that leads to an **unauthorized deploy** (a normally-blocked, non-green commit becomes deployable/auto-deployed via `continuous_deployment`).
- `push` handler triggers `stack.sync_github` against the victim stack.
- `membership` handler creates `Team`/`User`/`Membership` records that feed into `Shipit.github_teams` authorization checks (`Authentication#force_github_authentication` / `current_user.authorized?`), which is explicitly listed as a High-impact escalation vector.

I could not fully trace, within tool budget, whether `membership_handler.rb`'s created `Membership` records are actually consulted by `User#authorized?`/`Shipit.github_teams` in a way that grants dashboard access (I found the handler file but not its full body or `User#authorized?`), so I present the CI-status forgery (leading to unauthorized deploy) as the primary, fully-verified impact, and flag the membership-escalation path as a secondary, unverified possibility.

### Title
Webhook organization used for signature verification differs from the repository the payload actually targets, allowing signature-check bypass for other organizations' stacks - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret to verify against using `repository.owner.login` from the unauthenticated request body, while `Webhooks::Handlers::Handler#stacks` resolves the actual target `Stack` using the separate, also attacker-controlled `repository.full_name` field. In multi-organization installs where any organization has no `webhook_secret` configured (the documented default), an attacker can pin the verification org to the secret-less organization while making the payload act on a different, victim organization's stack.

### Finding Description
- Verification org selection: `Shipit.github(organization: repository_owner)` where `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')`. [1](#0-0) 
- Signature check is bypassed entirely when that org's `webhook_secret` is blank. [3](#0-2) 
- Actual target-stack resolution uses `repository.full_name`, a different key of the same untrusted JSON body, with no cross-validation against the owner used for verification. [5](#0-4) 
- Handlers (`push`, `status`, `check_suite`, `membership`, `pull_request`) are invoked with the raw, unverified `params` regardless. [8](#0-7) 

### Impact Explanation
This breaks the binding "organization authenticated == repository that is acted upon." It allows an attacker who knows (or exploits) that one org in a multi-org install lacks a webhook secret to forge events against any other registered stack, including forging passing CI `status`/`check_suite` events that can enable an unauthorized deploy of unreviewed code — matching the "unauthorized deploy" High/Critical impact category.

### Likelihood Explanation
Requires a multi-organization Shipit configuration where at least one configured org has `webhook_secret` unset — which is the value shown in every shipped example configuration (`docs/setup.md`, `config/secrets.development.example.yml`, `test/dummy/config/secrets_double_github_app.yml`), making misconfiguration plausible in real deployments. No credentials, tokens, or GitHub write access are required — only network access to `POST /webhooks`.

### Recommendation
- Derive the organization used for signature verification and the organization used for stack/repository resolution from the **same** field, and reject the request if `repository.owner.login` does not match the owner segment of `repository.full_name`.
- Consider requiring a non-blank `webhook_secret` for every configured organization, or failing closed (422) rather than treating a blank secret as "always verified."

### Proof of Concept
Given a Shipit instance configured with two orgs, `OrgNoSecret` (no `webhook_secret`) and `VictimOrg` (has a `webhook_secret`), with a stack registered for `victimorg/victim-repo`:

```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=anything

{
  "repository": {
    "owner": {"login": "OrgNoSecret"},
    "full_name": "victimorg/victim-repo"
  },
  "sha": "<existing commit sha on victim stack>",
  "state": "success",
  "context": "required-ci-check",
  "target_url": "https://attacker.example/fake"
}
```

`verify_signature` resolves `Shipit.github(organization: "OrgNoSecret")`, whose `verify_webhook_signature` returns `true` unconditionally because `webhook_secret` is blank; the request proceeds and `StatusHandler` (via `Handler#stacks`/`Repository.from_github_repo_name("victimorg/victim-repo")`) creates a forged passing `Status` on the victim stack's commit.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
