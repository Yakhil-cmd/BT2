Based on the confirmed code, this is a solid finding: the `CCMenuController` overrides `stack` to bypass the `ApiClient`'s stack-scoping, breaking the "stack a token authorises versus a stack it touches" binding.### Title
`Api::CCMenuController` bypasses `ApiClient` stack scoping, letting a token authorized for one stack read the CCTray status of any stack - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
Every other endpoint under `Shipit::Api::BaseController` resolves the target stack through the `stacks` scope, which restricts the queryable set to the single stack an `ApiClient` is bound to when `stack_id` is set. `CCMenuController` overrides that method and looks the stack up unscoped, so a token limited to one stack can be used to read CCTray XML status for arbitrary other stacks.

### Finding Description
`ApiClient` records can optionally be scoped to a single stack (`belongs_to :stack, optional: true`) [1](#0-0) . `Api::BaseController` enforces that binding for every controller that relies on its `stacks`/`stack` helpers:

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [2](#0-1) 

This is the equality the token/stack binding is supposed to guarantee: `stack a token authorises == stack a token can touch`. Permission checks (`require_permission :read, :stack`) only validate the `permissions` array (e.g. `read:stack`) via `ApiClient#check_permissions!`; they never re-validate that the specific `params[:stack_id]` matches the client's bound stack [3](#0-2) . That job is delegated entirely to the `stacks`/`stack` scoping helper.

`CCMenuController`, however, overrides `stack` to bypass that scope entirely:

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [4](#0-3) 

It still declares `require_permission :read, :stack` [5](#0-4) , so any client possessing the `read:stack` permission passes the permission check regardless of which stack it is bound to, and then the controller resolves `stack` against the *entire* `Stack` table using the caller-supplied `params[:stack_id]`, not the client's authorized stack. Before vs. after the equality:

- Before (intended): `current_api_client.stack_id.present? ⇒ stack ∈ {current_api_client.stack}` for every read.
- After (`CCMenuController#show`): `stack = Stack.from_param!(params[:stack_id])`, i.e. `stack ∈ Stack.all`, independent of `current_api_client.stack_id`.

The `CCMenuUrlController` (used by the UI's "CCMenu URL" feature) mints exactly this kind of scoped, single-stack, `read:stack`-only token: `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')` [6](#0-5)  bound implicitly to the requested `stack` via the URL/token flow — this is the exact class of token meant to be confined to one stack, and it is the one whose confinement `CCMenuController` breaks.

### Impact Explanation
An attacker who legitimately holds (or otherwise obtains) any `ApiClient` token scoped to a single stack with `read:stack` permission — e.g. a CCMenu token generated for stack A — can call `GET /api/:stack_id/cc.xml?token=...` with an arbitrary `stack_id` for stack B, C, etc., and receive that stack's CCTray XML: name, last build status/label/time, activity, web URL, and lock status [7](#0-6) . This is an unauthorized read of stack state across a boundary the token was explicitly scoped not to cross, matching the "High — unauthenticated/unauthorized read of stack state" impact class, since the authorization model promised isolation per stack and this endpoint silently drops it.

### Likelihood Explanation
Exploitation requires no privileged action beyond possessing any legitimately-scoped, low-privilege `read:stack` token (which by design is meant to be narrowly usable, e.g. shared in a CI dashboard or embedded in a CCTray client URL). The query-string token auth path is explicitly supported (`authenticate_api_client` accepts `params[:token]`) [8](#0-7) , making the token easy to replay against a different `stack_id`. The bypass is a single-line override that is easy to trigger and requires only changing one URL parameter.

### Recommendation
Remove the `stack` override in `CCMenuController` (or reimplement it using the inherited `stacks` scope) so the endpoint honors `current_api_client.stack_id` the same way every other API controller does:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
Add a regression test asserting that a client scoped to stack A receives a 404/403 (not stack B's data) when `stack_id` is swapped to stack B.

### Proof of Concept
1. As an authenticated Shipit user, visit stack A's page and trigger the "CCMenu URL" fetch, which creates (or reuses) an `ApiClient` named `CCMenu Client` with `permissions: ['read:stack']` and returns a URL containing `token=<A-scoped token>` [9](#0-8) . (In practice such a client can also be scoped explicitly to a `stack_id` via the `ApiClients` admin UI.)
2. Take the returned token and issue: `GET /api/other-owner/other-repo/other-stack/cc.xml?token=<A-scoped token>`.
3. `authenticate_api_client` accepts the token via `ApiClient.authenticate(params[:token])` regardless of which stack it names [8](#0-7) .
4. `require_permission :read, :stack` passes because the client has `read:stack` in its `permissions` list, with no comparison against `stack_id` [3](#0-2) .
5. `stack` resolves via `Stack.from_param!(params[:stack_id])` against the full `Stack` table, returning stack B's record even though the token was only ever meant to authorize stack A [10](#0-9) .
6. The response renders stack B's `name`, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `activity`, and `webUrl` [11](#0-10)  to a caller whose token was never authorized for stack B.
