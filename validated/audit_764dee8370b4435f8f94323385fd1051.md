Confirmed: the deploy trigger is stack-scoped (`trigger_continuous_delivery` uses `next_commit_to_deploy` computed from `commits_to_deploy = commits.order(...)` on that stack, and `Deploy#schedule_continuous_delivery` / `ContinuousDeliveryJob#perform` check `stack.continuous_deployment?` and pick the stack's own next deployable commit). The exploitable gap is upstream, in `StatusHandler#process`, which resolves the target commit(s) purely by SHA with no repository/stack scoping.

### Title
Cross-repository status forgery via unscoped SHA lookup in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves target rows with `Commit.where(sha: params.sha)` across the **entire** `commits` table, with no filter on the reporting repository. Any commit sharing that SHA in a different stack/repository (e.g. a fork sharing history with an upstream, or a repo tracked by multiple stacks/environments) gets a `Status` created for the `github-actions` (or any) context, and if that other stack has `continuous_deployment` enabled, the write triggers `Commit#schedule_continuous_delivery` → `Stack#trigger_continuous_delivery`.

### Finding Description
The broken binding: the invariant should be `status.stack_id == webhook.repository.stack_id` for every `Status` created from a `status` webhook, i.e., a status reported for repository R must only ever attach to commits belonging to stacks backed by R. Instead the code enforces `status.commit.sha == params.sha` only: [1](#0-0) 

`Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` iterates over every `Commit` row in the database matching that SHA, regardless of which `stack`/repository it belongs to. Compare this to `PushHandler#process`, which correctly scopes work to `stacks.where(branch:)` for the reporting repo's branch: [2](#0-1) 

The `webhooks_controller.rb#verify_signature` guard only authenticates that the payload was signed for *an organization* (`Shipit.github(organization: repository_owner)`), not that the specific `sha` belongs to the reporting `repository.full_name`: [3](#0-2) 

Once a `Status` is created, `after_create :enable_ci_on_stack` and `after_commit :schedule_continuous_delivery` fire unconditionally for whichever stack owns that commit row: [4](#0-3) 

`Commit#schedule_continuous_delivery` (invoked on create) and `Status#schedule_continuous_delivery` both delegate into the stack's continuous delivery pipeline, which is where the amplification happens — `ContinuousDeliveryJob#perform` checks `stack.continuous_deployment?` and, if true, calls `stack.trigger_continuous_delivery`, deploying the next deployable commit on **that** stack: [5](#0-4) [6](#0-5) 

Exploit flow: an attacker who can get a validly signed `status` webhook delivered for context `github-actions` for a SHA that also exists as a commit under a victim stack (shared git history between repos in the same org/install — e.g. forks, mirrored/renamed repos, or a repo tracked by multiple Shipit stacks/environments) causes `Status.replicate_from_github!` to fire against the victim's `Commit` row. If the victim stack has `continuous_deployment: true`, this can flip the commit to `success`/`deployable`, triggering `ContinuousDeliveryJob` to ship it, or to `failure`/`error`, blocking the victim's pipeline.

Existing guards do not close this: `verify_signature` authenticates the payload's claimed *organization*, not the specific repository-to-SHA binding; `ExplicitParameters` (`params do ... end`) only validates types/shape, not ownership; there is no `stacks`-scope or `repository`-based filter anywhere in `StatusHandler#process`.

### Impact Explanation
A payload authenticated for one repository can mutate `Status`/CI state for a commit belonging to a different stack, and if that stack has `continuous_deployment` enabled, this becomes an unauthorized deploy or an unauthorized block/rollback trigger on a tenant the attacker did not authenticate against. This matches the "payload for one repository mutating another's stack/commit" Critical category. Blast radius is bounded by however many stacks/commits happen to share the reported SHA (forks, renamed/mirrored repos, or multiple environment-stacks of the same repo are the realistic vectors), and is repeatable per shared SHA.

### Likelihood Explanation
Exploitability strictly depends on: (1) the attacker being able to get a *validly-signed* `status` webhook delivered — this requires a real GitHub-originated status event for an organization/app installation Shipit trusts, which in turn requires the attacker to control a repository under that trusted org/app installation (e.g., as a legitimate contributor able to trigger CI, or with a repo that shares history/SHA with the victim's repo, such as a fork before divergence or an org repository transfer/rename); and (2) a target commit with the same SHA existing under a different, victim-owned stack with `continuous_deployment` enabled. This is not achievable from an arbitrary unrelated internet host without a validly signed webhook — the signature check does gate the "org" boundary — but nothing gates the SHA-to-repository boundary once a legitimate webhook for *any* repository in that org/install is delivered. Given multi-repo/multi-environment installs and forks are common, this is a real, low-cost, repeatable condition once the org-level signing precondition is met.

### Recommendation
Scope `StatusHandler#process` to only the stacks associated with the reporting `repository.full_name` from the payload, e.g. filter `Commit.joins(:stack).merge(Stack.where(repository: reported_repository)).where(sha: params.sha)`, mirroring the repository-scoping already used by `PushHandler`. Reject or ignore statuses whose payload repository doesn't match any tracked repository for the matched commit(s).

### Proof of Concept

1. Create two stacks, `victim_stack` (repository `victim/repo`, `continuous_deployment: true`, deploy spec requiring `github-actions`) and `attacker_stack` (repository `attacker/repo`).
2. Create `Commit` rows with the **same** `sha` under both stacks (simulating shared history, e.g. a fork).
3. Call `Shipit::Webhooks::Handlers::StatusHandler.call('sha' => shared_sha, 'state' => 'success', 'context' => 'github-actions', 'repository' => { 'full_name' => 'attacker/repo' }, ...)`.
4. Assert: `victim_stack.commits.find_by(sha: shared_sha).statuses.where(context: 'github-actions').exists?` is `true` (proving cross-repo write) — binding `status.stack_id == attacker_stack.id` (expected) vs actual `status.stack_id == victim_stack.id` diverge.
5. Assert `enqueue_jobs`/`ContinuousDeliveryJob` was scheduled for `victim_stack`, i.e., `assert_enqueued_with(job: ContinuousDeliveryJob, args: [victim_stack])`, demonstrating the unauthorized deploy trigger despite the webhook only having been signed for `attacker/repo`.
