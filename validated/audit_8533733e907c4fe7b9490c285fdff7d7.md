### Title
`MembershipHandler` grants org-B team membership using an org-A-verified webhook by matching only `team.id` - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#find_or_create_team!` resolves the target `Team` solely by the global, GitHub-wide `github_id` from the payload (`Team.find_or_create_by!(github_id: params.team.id)`), and `#process` then mutates that team's membership without ever verifying that the team's `organization` matches the organization whose secret authenticated the request. Since GitHub team ids are not scoped to a single org, a webhook that is legitimately signed by Org-A's `webhook_secret` can carry a `team.id` belonging to Org-B, and the handler will happily add/remove members on Org-B's team.

### Finding Description
The broken binding as an explicit equality that must hold but doesn't: `Team.find_by(github_id: params.team.id).organization == repository_owner` (the org that produced a valid signature for this request). In `Shipit::WebhooksController#verify_signature`, the org used to select the HMAC secret is `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0) . For a genuine GitHub `membership` event there is no `repository` key at all, so `repository_owner` falls back to `params.organization.login` — the attacker's own, legitimately-configured org, whose secret they control because they administer that org's GitHub webhook settings.

Once the signature is verified against Org-A's secret, `Shipit::Webhooks::Handlers::MembershipHandler#process` calls `find_or_create_team!`, which does:
```
Team.find_or_create_by!(github_id: params.team.id) do |team|
  team.github_team = params.team
  team.organization = params.organization.login
end
``` [2](#0-1) 

If a `Team` row with that `github_id` already exists — e.g. because it was previously resolved into `Shipit.github_teams` for Org-B via `Shipit#github_teams` / `Team.find_or_create_by_handle` [3](#0-2) [4](#0-3)  — `find_or_create_by!` returns that existing Org-B `Team` untouched (the block only runs on creation), and `process` then does `team.add_member(member)` [5](#0-4) , adding the attacker-named member to Org-B's team. Nowhere is `team.organization` compared against `params.organization.login` or the request's verified `repository_owner`.

Exploit flow: Org-A admin (attacker) crafts a `membership` `added` event body with `organization.login = "org-a"`, `team.id = <Org-B's real team github_id>`, `member.login = "attacker-controlled-user"`, signs it with Org-A's real `webhook_secret`, and POSTs it to `/webhooks`. Signature verification passes (it's genuinely Org-A's secret and body). `MembershipHandler` then adds the named member to Org-B's team, which may be a `Shipit.github_teams` team feeding into `User#authorized?`/deploy authorization.

Existing guards (`verify_signature`, `drop_unhandled_event`, the `ExplicitParameters` schema) only enforce that the *body* was signed by *some* legitimately configured org — they do not enforce that the team id inside the body belongs to that same org. The `ExplicitParameters` schema for this handler only requires `team.id` to be an `Integer`, `name`/`slug`/`url` to be `String`, with no organizational binding check [6](#0-5) .

### Impact Explanation
An attacker who administers any single small org listed in Shipit's multi-org `secrets.yml` can add arbitrary GitHub users (including themselves) to any other, victim organization's `Team` record already known to Shipit, purely by referencing that team's real (globally unique, discoverable) GitHub team id. If that victim team is part of `Shipit.github_teams`, this is a direct escalation into Shipit's authorization model — the attacker gains membership in an authorization-relevant team belonging to a completely different tenant, without ever needing that tenant's secret. This is repeatable against any Team row already persisted for any org, and matches the High-severity category ("escalation into `Shipit.github_teams` authorization").

### Likelihood Explanation
Preconditions: (1) Shipit is configured with secrets for multiple orgs, (2) the attacker legitimately administers at least one small org among them and thus knows its `webhook_secret` (a normal consequence of configuring a GitHub org webhook), (3) the victim's team already exists as a `Team` row in Shipit (e.g., resolved via `Shipit.github_teams`), and (4) the attacker can discover or guess the victim team's numeric `github_id` (team ids are enumerable/discoverable via GitHub's API for public team info or prior interactions). Given these, the attack is a single crafted HTTP POST with no rate limiting or additional secrets required, and is fully repeatable.

### Recommendation
In `MembershipHandler#find_or_create_team!` / `#process`, after resolving the team, verify `team.organization == params.organization.login` (and that this matches the organization used to verify the webhook signature); reject or raise if they diverge instead of silently mutating an existing team belonging to a different organization.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` style, illustrative only — not to be placed in `test/**` per scope, but described for the fix's verification):
1. Fixtures: `shipit_teams(:shopify_developers)` (`organization: shopify`, `github_id: 1`) and `shipit_teams(:cyclimse_cooks)` (`organization: cyclimse`, `github_id: 2`).
2. Stub `Shipit.github(organization: 'cyclimse').verify_webhook_signature` to return `true` (simulating attacker's legitimate knowledge of cyclimse's real secret).
3. POST a `membership` webhook with `organization: { login: 'cyclimse' }`, `team: { id: 1, name: 'Developers', slug: 'developers', url: '...' }` (i.e., Org-A's payload naming Org-B's `shopify_developers` team id), `member: { login: 'attacker' }`, no `repository` key.
4. Assert response is `:ok`.
5. Assert `shipit_teams(:shopify_developers).members.reload` now includes the `User` for `attacker`.
6. Assert `Shipit::Team.find_by(github_id: 1).organization == 'shopify'` (unchanged) while the request was verified under `'cyclimse'`'s secret — demonstrating `team.organization != repository_owner-derived org` yet the membership mutation still succeeded.
