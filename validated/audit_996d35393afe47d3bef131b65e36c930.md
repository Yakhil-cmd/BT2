Based on my research, I found a plausible protocol-level analog, though I want to flag the uncertainty explicitly before presenting it.

### Title
Private payments sent to an Autonomous Agent address silently increase its on-chain outputs without ever generating an `aa_triggers` row, permanently freezing funds outside the AA's tracked balance/state - (File: `ocore--017/main_chain.js`)

### Summary
The Solidity report's root cause is that `PirexRewards.claim()` can move funds into a vault contract through a code path that bypasses the vault's only balance-accounting hook (`compound()`), so the funds land in the contract without the corresponding state/fee logic executing. The structural analog in `ocore` is that `main_chain.js`'s `handleAATriggers()` — the *only* code path that inserts a row into `aa_triggers` and thus invokes `aa_composer.handlePrimaryAATrigger()` — explicitly excludes private-asset outputs from the query that detects payments to AA addresses.

### Finding Description
`handleAATriggers()` in `main_chain.js` is the sole mechanism that decides whether a payment to an address that is an AA triggers execution of that AA's oscript/bytecode: [1](#0-0) 

The `WHERE` clause contains `AND (outputs.asset IS NULL OR is_private=0)`, meaning any output whose `asset` is a private (hidden-amount) asset with `is_private=1` is excluded from the trigger-detection query. Consequently, a private payment sent to an AA's address never inserts a row into `aa_triggers`, and `handlePrimaryAATrigger()` / `handleTrigger()` in `aa_composer.js` (the only place that updates `aa_balances` via `updateInitialAABalances`, evaluates the AA's `oscript`, and performs any accounting/fee/state logic) is never invoked for that payment: [2](#0-1) [3](#0-2) 

This mirrors the external report's core defect: value can reach the target contract/address through a path that never runs the code responsible for recognizing and accounting for it — in Pirex's case `claim()` bypassing `compound()`'s balance-diff/fee logic; in `ocore`, a private payment bypassing the `aa_triggers` insertion that is the AA's only entry point for balance/state accounting (`aa_balances`, `stateVars`, `response`/oscript logic).

Because `aa_balances` (the table backing the oscript `balance[...]` reads) is populated only through this trigger path (and consistently excludes private outputs, e.g. in the balance-reconciliation query in `checkBalances()`), the AA's own `balance[asset]` value never reflects the received private amount, and the AA's oscript can never construct a response or spend against it deterministically.

### Impact Explanation
Funds sent this way are not stolen by an attacker in the classic sense, but they become **permanently untracked and effectively frozen** relative to the AA's own accounting model: the AA's business logic (fee calculation, state updates, conditional payouts) that a user expects to run upon deposit never executes, and the AA itself has no oscript-level way to "see" or reason about the deposit (`balance[...]` won't include it). This falls under "AA fund loss or freezing" impact criteria. Any AA that accepts private assets as one of its expected trigger currencies (e.g., private stablecoin/utility-asset vaults) is exposed to this class of issue for every user (or counterparty in a private-payment chain) who sends it a private payment.

### Likelihood Explanation
This requires only sending an ordinary private-asset payment (a normal, unprivileged wallet operation available to any private-payment counterparty) to an AA address — no special privileges, no race condition, and no cooperation from node operators is needed. However, I could **not fully verify** two things due to index/tool limits: (1) whether wallet-level or validation-level code elsewhere explicitly warns/blocks users from sending private assets to AA addresses (some hints of "private" checks exist in `aa_validation.js` and `wallet.js` that I was not able to fully inspect), and (2) whether this is a long-documented/intended limitation of AAs (i.e., "AAs don't support private assets") rather than an unrecognized bug. Given the explicit filtering logic and comments already present in the trigger-detection SQL, this looks like a deliberate design constraint rather than an overlooked defect, which lowers confidence that this qualifies as a genuine, previously-unknown vulnerability versus documented behavior.

### Recommendation
If unintended: either (a) reject/bounce private-asset payments to AA addresses at the validation layer so senders get immediate, deterministic feedback that funds will not trigger the AA (preventing silent freezing), or (b) extend `handleAATriggers()`/`aa_balances` accounting to also recognize private outputs (requiring the AA to somehow learn the amount, which conflicts with the privacy model) so that such payments are properly credited and can enter the AA's state logic.

### Proof of Concept
1. Deploy/define an AA that expects payments in a private asset (or in bytes/base plus a private asset) and performs logic based on `trigger.output[[asset=...]]`.
2. A private-payment counterparty sends a private payment of that asset to the AA's address using the standard private-payment protocol.
3. Because `outputs.is_private=1`, the SQL in `handleAATriggers()` (`main_chain.js:1691-1723`) never selects this output, so no row is inserted into `aa_triggers`.
4. `handlePrimaryAATrigger()`/`handleTrigger()` in `aa_composer.js` is never invoked for this unit/address pair, so `aa_balances` is never incremented and the AA's oscript logic (fee calculation, response payments, state updates) never runs for this deposit.
5. The private output remains in the `outputs` table as unspent, but the AA's own `balance[asset]` (backed by `aa_balances`) never reflects it, and the AA has no oscript path to discover or spend it deterministically — the funds are effectively stranded relative to the AA's intended accounting/business logic.

Given the uncertainty about whether this is treated as an accepted/documented limitation rather than an unrecognized vulnerability, this analog should be treated as **medium confidence** and would benefit from confirmation via a live Devin session inspecting `aa_validation.js`/`wallet.js`'s private-asset handling and any user-facing documentation on AA + private-asset interactions before being escalated.
