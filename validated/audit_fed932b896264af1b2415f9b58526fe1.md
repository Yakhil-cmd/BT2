## Analysis

The report's root cause pattern — a storage/authorization binding that is silently never enforced, producing cascading trust failures — has a direct analog in `shipit-engine`'s webhook signature verification.

### Title
Webhook signature is validated against the *sender's* organization but the `status` handler writes to commits by SHA with no repository scoping, allowing cross-repository forged commit statuses - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp`/webhook secret to validate the HMAC signature against using `repository_owner`, a field read straight out of the *unverified* JSON payload: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. [1](#0-0) [2](#0-1) 

Once the signature check passes (because it matches *some* configured organization's secret), the raw payload is parsed and dispatched to handlers with no further binding between "the organization whose secret validated the signature" and "the resource the handler actually mutates." [3](#0-2) 

`StatusHandler#process` is the clearest break: it looks up commits **purely by SHA**, with zero scoping to the repository/organization named in the payload:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [4](#0-3) 

The status fields (`state`, `description`, `target_url`, `context`) are taken verbatim from the payload and written directly, without any call back to GitHub's API to confirm the status actually exists there. [5](#0-4) 

### Finding Description
Shipit supports hosting multiple GitHub organizations under one instance, each configured with its own `GitHubApp`/webhook secret via `Shipit.github(organization:)`. [6](#0-5) 

The equality that should hold is:
`organization whose secret validated the signature == organization owning the repository/commit that the webhook handler mutates`

In the current code this equality is never enforced:
- `verify_signature` picks the verification secret from the attacker-supplied `repository.owner.login`/`organization.login` field.
- `StatusHandler` (and, by the same `Handler` base class design, other handlers rely on `repository.full_name`, a different, also-unbound field) act on data (`Commit.where(sha: ...)`) that has no relation to that owner field at all. [7](#0-6) 

Because the HMAC covers the whole raw body, an attacker who legitimately administers **any one** organization onboarded to the shared Shipit instance (and therefore knows that org's `webhook_secret`, since GitHub App webhook secrets are set by whoever configures that org's App installation — not by the Shipit application admin) can craft and validly sign an arbitrary `status` event body. Nothing stops them from setting `sha` to a commit that belongs to a completely different, unrelated organization's stack tracked by the same Shipit instance, and setting `state`/`context` to whatever they want (e.g. mark a required CI context as `success`).

### Impact Explanation
`ci.require` gates deploys/continuous delivery on named status contexts being green (`app/models/shipit/deploy_spec.rb`, `required_statuses`). [8](#0-7) 

A forged, globally-unscoped `commit_status` write lets an attacker who only controls a low-trust org's webhook secret fabricate a passing CI status for a commit that belongs to an entirely different organization's repository/stack, which can unblock an otherwise-blocked deploy or corrupt another tenant's commit history/checks page — i.e. a cross-repository write reachable without any Shipit session, `ApiClient` token, or write access to the victim repository, matching the report's "value never validated → breaks many downstream consumers" bug class.

### Likelihood Explanation
Requires only that the Shipit instance hosts more than one organization with independent GitHub App configs (a documented, supported configuration — see `secrets_double_github_app.yml` test fixture and `Shipit.github(organization:)`), and that the attacker administers one of them. No Shipit credentials, GitHub org membership in the victim org, or repository write access to the victim repo is needed. [9](#0-8) 

### Recommendation
Scope every webhook handler's data lookups (especially `StatusHandler`'s `Commit.where(sha:)`) to the repository identified by the verified payload, and additionally verify that the organization used to select the signing secret in `verify_signature` matches the organization that owns the repository being mutated by the handler — i.e. enforce the binding explicitly rather than trusting two independently-read, unrelated payload fields.

### Proof of Concept
1. Shipit instance configured with two organizations in `secrets.yml`: `orgA` (victim, hosts `orgA/app`) and `orgB` (attacker-controlled, hosts `orgB/toy`), each with its own `github.webhook_secret`.
2. Attacker, who administers `orgB`'s GitHub App and thus knows `orgB`'s `webhook_secret`, crafts a `status` event body:
```json
{
  "repository": {"owner": {"login": "orgB"}, "full_name": "orgB/toy"},
  "sha": "<sha-of-a-commit-tracked-under-orgA/app>",
  "state": "success",
  "context": "required-ci-check",
  "target_url": "https://attacker.example.com"
}
```
3. Attacker computes `X-Hub-Signature` HMAC-SHA1 over the raw body using `orgB`'s known `webhook_secret` and POSTs to `/github_hooks` with `X-Github-Event: status`.
4. `verify_signature` calls `Shipit.github(organization: "orgB")` (from `repository.owner.login`), verification succeeds because the signature was computed with `orgB`'s real secret. [1](#0-0) 
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the commit under `orgA/app`, and creates a fake "success" status for `required-ci-check` on it — a status write on a repository the attacker never authenticated against or had access to. [4](#0-3)
