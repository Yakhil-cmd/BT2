This confirms the analog mechanism precisely: when an AA response's payment message for a `spender_attested` asset targets an address that lacks attestation, the composed response unit fails validation with `"some output addresses are not attested"` [1](#0-0)  and the AA calls `bounce(err)` [2](#0-1) . Because `bounce()` only refunds the base-asset bytes the trigger sent (net of `bounce_fees`), and only for the `base` asset unless the offending asset itself has room in `bounce_fees` [3](#0-2) , any restricted (`spender_attested`) asset balance that was supposed to be paid out to that specific winner/output address stays trapped in the AA's balance forever — the AA has no way to redirect the payment to a different, attested address, since the destination address is hardcoded in AA response logic (e.g., `trigger.address` from the deterministic winner-selection code).

### Title
Reward payouts of `spender_attested` assets from an AA can be permanently frozen if the recipient address is not/no-longer attested - ([File: aa_composer.js], [File: validation.js])

### Summary
An Autonomous Agent (AA) that pays out a `spender_attested` asset (Obyte's on-chain equivalent of a permissioned/whitelisted token, analogous to a blacklist-capable token such as USDC) to a trigger-determined address (e.g., a lottery/staking-reward winner) can have that payout permanently stuck in the AA if the recipient address is not attested by the asset's attestors at payout time. This mirrors the reported issue: a "blacklisted" (here: unattested) winner cannot receive funds, and the protocol provides no mechanism to redirect the payment to a different address.

### Finding Description
`spender_attested` is an asset flag that requires every address receiving (or spending) the asset to be attested by one of the asset's `attestors`, checked via `storage.filterAttestedAddresses` / `loadAssetWithListOfAttestedAuthors` [4](#0-3) . When an AA composes and validates its response unit, any payment output for such an asset is checked against this same attestation table: if the destination address is not attested, validation fails with `"some output addresses are not attested"` [1](#0-0) .

Inside `aa_composer.js`'s `handleTrigger`, when the composed response unit fails validation (`validateAndSaveUnit`), the composer calls `bounce(err)` [5](#0-4) . The `bounce()` function reverts state changes and refunds the *trigger's incoming payment* minus `bounce_fees`, but only for assets included in `trigger.outputs` (typically `base` bytes sent to trigger the AA) [3](#0-2) . It does **not** un-do or redirect the asset balance the AA was already holding and attempting to pay out — that balance remains in the AA's internal `aa_balances` for the asset, associated with the AA address, with no code path to send it anywhere else since the AA logic hard-codes the destination as the winning/trigger address.

Since attestation status is deterministic given the last stable MC state, every subsequent attempt to trigger the same payout logic for the same address will fail identically, forever — there is no way for the AA (a static, code-defined contract) to dynamically choose an alternate destination address once deployed, unlike an EOA-controlled contract that a human operator could patch.

### Impact Explanation
Funds (the `spender_attested` asset reward) get permanently locked inside the AA's balance. Any users who contributed value that is now owed to the (unattested/"blacklisted") recipient lose access to it irrecoverably, since the AA logic cannot be changed post-deployment and has no fallback destination. This is a direct, permanent freezing of funds analogous to the reported USDC blacklist issue, matching the "AA fund loss or freezing" acceptance criterion.

### Likelihood Explanation
This requires an AA design that (a) issues or distributes a `spender_attested` asset, and (b) pays it to an address determined by protocol logic (e.g., a computed "winner" or "recipient") rather than the address that actively claims it with proof of attestation. Given `spender_attested`/`attestors` is a first-class, documented asset feature intended for compliance/whitelisting use cases (analogous to KYC-gated tokens), and AA authors are expected to build reward/distribution mechanisms using arbitrary output addresses (e.g., `test/samples/fundraising_proxy.oscript` composes a `spender_attested`-capable asset and pays it to `trigger.address` [6](#0-5) ), this is a realistic pattern rather than a contrived edge case.

### Recommendation
- Document explicitly, in AA authoring guidance, that AAs distributing `spender_attested` assets must never hard-code output addresses without first verifying attestation status via a getter/oracle check, and should implement a pull-based claim pattern (recipient sends a trigger to claim, and if it fails, the AA can retain/refund to a different address, e.g. by having the AA emit an error and let the *sender* re-trigger with a different destination) instead of push-based distribution to a possibly-unattested address.
- Consider adding an AA-callable getter (e.g., `is_attested(asset, address)`) so AA logic can conditionally choose fallback logic (e.g., issuing base asset compensation, or holding for a later re-attempt with an updated address) rather than deterministically failing forever.
- At minimum, warn users/auditors reviewing AAs that combine `spender_attested` assets with automatic (non-claim-based) payouts to trigger-supplied or computed addresses, since this can produce irrecoverable fund freezes.

### Proof of Concept
1. Define asset `A` with `spender_attested: true` and attestor set `{Attestor1}`.
2. Deploy AA `Distributor` whose logic sends asset `A` to `trigger.address` (e.g., a lottery AA sending the prize to the computed winner) — pattern shown in `test/samples/fundraising_proxy.oscript` [7](#0-6) .
3. User `Bob` (never attested by `Attestor1`, or whose attestation was later invalidated by an `address_definition_change` after the attestation, per the `main_chain_index > address_definition_changes` check in `filterAttestedAddresses` [8](#0-7) ) triggers/wins the distribution.
4. `Distributor` composes a response paying asset `A` to Bob's address. `validatePaymentInputsAndOutputs` rejects it: `"some output addresses are not attested"` [1](#0-0) .
5. `aa_composer.js` calls `bounce(err)`; only the trigger's base-byte payment (minus fees) is refunded, while the asset `A` balance intended for Bob remains stuck in `Distributor`'s AA balance permanently, since Bob's attestation status cannot change retroactively and the AA's destination logic cannot be altered.
