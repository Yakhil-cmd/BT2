### Title
Weak 128-bit effective collision resistance of `chash160` allows front-running of undisclosed address definitions ("first-use" binding) to hijack funded addresses / AA addresses — (File: `chash.js`)

### Summary
Every payment address, shared (multi-sig) address, and Autonomous Agent (AA) address in ocore is not a random identifier but is *derived deterministically from content* via `objectHash.getChash160(definition)` [1](#0-0)  and is only bound to that content the first time a matching definition is disclosed on-chain ("first use of the definition_chash") [2](#0-1) [3](#0-2) . This mirrors the `CREATE2` pattern in the original report: the "container" (address) can be known and funded well before its "content" (definition) is disclosed/finalized, and whichever content is first to match the address hash permanently owns it. Unlike Ethereum's `CREATE2`, which uses a full, unweakened 160-bit `keccak256` output, ocore's `chash160` throws away entropy: it truncates `RIPEMD160` to 128 bits and pads the remaining 32 bits with a checksum that is *fully determined by those 128 bits* rather than independent randomness. This drops the real birthday-bound collision-search cost from ~2^80 (as in the original report's Ethereum analysis) down to only ~2^64, making a "definition collision" attack dramatically more practical.

### Finding Description
`chash.getChash` computes the address as follows: [4](#0-3) 
```
hash = ripemd160(data)                 // 160 bits
truncated_hash = hash.slice(4)         // drop first 4 bytes -> 128 bits ("clean data")
checksum = getChecksum(truncated_hash) // 32 bits, deterministic function of the 128-bit clean data
chash = mix(truncated_hash, checksum)  // 160-bit encoded output
```
The checksum bits carry zero independent entropy — they are a hash-derived function of the 128-bit clean data, purely for detecting typos (à la base58check), not for strengthening collision resistance. Consequently, any two definitions whose `truncated_hash` (128 bits) match will always produce the *same* 160-bit chash (checksum recomputes identically). The effective collision-search space is therefore 2^128, giving a birthday-bound attack cost of only ~2^64 hash operations — vastly cheaper than the ~2^80 the audited report described as "feasible in 31 minutes" for a genuine 160-bit space.

Addresses in ocore are meant to be pre-computed and funded before the owning definition is ever revealed:
- Payment/shared addresses: cosigners compute and exchange `address = objectHash.getChash160(arrDefinition)` ahead of time and can receive funds before broadcasting any unit that discloses the definition, e.g. `createNewSharedAddress`/`handleNewSharedAddress` [5](#0-4)  and `deriveAddress`/wallet HD derivation [6](#0-5) .
- AA addresses are explicitly counterfactual: `address = objectHash.getChash160(arrDefinition)` is computed off-chain and funds can be sent to it before the `definition` message is ever posted [7](#0-6) ; the network only accepts/binds the address the first time a matching `definition` payload appears (`payload.address !== objectHash.getChash160(payload.definition)` check plus insertion into `aa_addresses` with `address` as PRIMARY KEY) [8](#0-7) [9](#0-8) .

Ownership binding is strictly "first come, first served" at the protocol level: `readDefinitionByAddress`/`readDefinitionChashByAddress` return `definition_chash = address` until an `address_definition_change` or an initial definition disclosure occurs [10](#0-9) , and `validateDefinition` in `validation.js` accepts *whichever* definition is broadcast first as long as its chash matches, rejecting only a later, different definition for the same address as a duplicate [11](#0-10) . `writer.js` then permanently persists this first-disclosed definition into the `definitions`/`addresses` tables [12](#0-11) .

Given the weakened ~2^64 collision cost of `chash160`, an attacker can:
1. Off-chain, brute-force a large set of candidate malicious definitions (e.g., `["sig", {pubkey: attacker_pubkey}]` or an `["or", [...]]` definition granting the attacker sole/backdoor signing rights) and index their `truncated_hash` values (meet-in-the-middle / Bloom filter, exactly as described in the source report).
2. Search for a collision against any publicly known, funded-but-undisclosed address — a shared multi-sig address published to cosigners, a textcoin address, or (most attractively) a well-known/predictable counterfactual AA address that a project intends to fund before deploying its real AA definition.
3. As soon as a match is found, submit a unit whose author (or `definition` app message, for AAs) discloses the attacker's colliding definition for that address. Since this is the "first use" of the definition_chash, `validateDefinition`/`readDefinitionByAddress` will accept it as the address's *permanent* controlling definition.
4. Any bytes/assets already sent to that address (or subsequently sent, since victims and counterparties believe the address belongs to the legitimate owner) can then be spent by the attacker under their own definition/authentifiers.

### Impact Explanation
This allows unauthorized spending / complete draining of funds sent to a pre-published or counterfactually-computed address (shared wallet address, textcoin address, or AA address) before its legitimate definition is disclosed on-chain — the same fund-loss impact class as the source report ("complete draining of the pool"). Because the definition binding is permanent and irreversible ("first use of the definition_chash"), the legitimate owner can never reclaim the address once the attacker's colliding definition has been accepted by the network, resulting in concrete unauthorized spending / AA fund loss.

### Likelihood Explanation
The attack requires an offline, non-interactive brute-force search costing roughly 2^64 hash operations due to `chash160`'s effective 128-bit entropy (checksum bits add no security) rather than the intended 160 bits. This is dramatically cheaper than the 2^80 cost that the original report already judged "feasible... in a reasonably short timeline" using a fraction of Bitcoin's hashrate. The attacker needs no special network privilege — only the ability to (a) observe or predict a target address that will receive/hold funds before its definition is disclosed (shared wallets, textcoins, and especially counterfactual AA deployments are an explicit, common ocore usage pattern) and (b) post one ordinary unit disclosing a colliding definition. This satisfies "hypothetical attack path with stated assumptions but external requirements," matching the Medium severity judged for the original finding, while the actual computational bar here is considerably lower.

### Recommendation
- Use the full hash output as address material instead of truncating to 128 bits before mixing in a checksum; if a human-readable checksum is required, append truly independent checksum bits rather than bits computed solely from the truncated hash so the real address entropy is preserved at 160 bits (or increase to a wider hash, e.g. use full `SHA-256`/`RIPEMD160` without dropping bytes, and add extra checksum bytes on top of, not carved out of, the base hash).
- For AAs and shared addresses that are meant to be funded before their definition is publicly disclosed, consider binding the "first disclosure wins" rule to an earlier, harder-to-forge commitment (e.g., requiring the address deployer to already have signed/broadcast a nonce or commitment unit at creation time) so pure `chash` collision search is not suffinal.
- Add monitoring/mitigation such as flagging identical-value definitions submitted extremely close together for the same address, or requiring a time-locked reveal-and-challenge window before newly disclosed definitions become spendable.

### Proof of Concept
1. Offline: generate N candidate attacker definitions `["sig", {pubkey: attacker_pubkey_i}]`, compute `truncated_hash_i = ripemd160(getSourceString(definition_i)).slice(4)` for each, and store in a hash table/Bloom filter (this mirrors `chash.getChash` internals) [13](#0-12) .
2. Independently enumerate/predict target addresses that are expected to receive funds pre-disclosure (shared wallet addresses distributed via `sendNewSharedAddress`, or counterfactual AA addresses computed and funded by dApp developers before broadcasting the `definition` app payload) — same as `objectHash.getChash160(arrDefinition)` used in `createNewSharedAddress` [14](#0-13) .
3. Find a match between the two sets (birthday search, ~2^64 work given the 128-bit effective space).
4. Once the target address is funded, broadcast a unit whose author declares the colliding attacker definition for that address (or, for an AA, a `definition` app message with `payload.address` == the funded AA address and `payload.definition` == attacker's colliding definition) [8](#0-7) .
5. Because `readDefinitionByAddress` finds no existing definition (`ifDefinitionNotFound`) and only checks that the chash matches, the network accepts the attacker's definition as the address's controlling definition [15](#0-14) , permanently locking out the legitimate owner and letting the attacker spend all funds already sent to the address.

function readDefinitionAtMci(conn, definition_chash, max_mci, callbacks){
	var sql = "SELECT definition FROM definitions CROSS JOIN unit_authors USING(definition_chash) CROSS JOIN units USING(unit) \n\
		WHERE definition_chash=? AND is_stable=1 AND sequence='good' AND main_chain_index<=?";
	var params = [definition_chash, max_mci];
	conn.query(sql, params, function(rows){
		if (rows.length === 0)
			return callbacks.ifDefinitionNotFound(definition_chash);
		callbacks.ifFound(JSON.parse(rows[0].definition));
	});
}

function getChash(data, chash_length){
	//console.log("getChash: "+data);
	checkLength(chash_length);
	var hash = crypto.createHash((chash_length === 160) ? "ripemd160" : "sha256").update(data, "utf8").digest();
	//console.log("hash", hash);
	var truncated_hash = (chash_length === 160) ? hash.slice(4) : hash; // drop first 4 bytes if 160
	//console.log("clean data", truncated_hash);
	var checksum = getChecksum(truncated_hash);
	//console.log("checksum", checksum);
	//console.log("checksum", buffer2bin(checksum));

	var binCleanData = buffer2bin(truncated_hash);
	var binChecksum = buffer2bin(checksum);
	var binChash = mixChecksumIntoCleanData(binCleanData, binChecksum);
	//console.log(binCleanData.length, binChecksum.length, binChash.length);
	var chash = bin2buffer(binChash);
	//console.log("chash     ", chash);
	var encoded = (chash_length === 160) ? base32.encode(chash).toString() : chash.toString('base64');
	//console.log(encoded);
	return encoded;
}
