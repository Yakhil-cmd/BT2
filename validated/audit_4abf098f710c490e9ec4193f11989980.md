### Title
`Cache::require_reserves` / `require_liquidation_buffer` validate the pool cash balance without reserving the concurrently claimable revenue, so the guaranteed liquidation buffer can be drained - ([File: contracts/pool/src/guards.rs](contracts/pool/src/guards.rs))

### Summary
The GMX issue is that a "minimum balance" invariant and a separately-claimable balance are each checked against the same token balance independently, so `balance >= min` and `balance >= claimable` together do not imply `balance >= min + claimable`. XOXNO Lending has the same shape: the liquidation buffer (a floor on `cash`) is enforced only on debt mints via `require_liquidation_buffer`, while protocol revenue shares — a concurrently claimable claim on the very same `cash` — are neither subtracted from `cash` at check time nor gated by the buffer when paid out via `burn_claimable_revenue` / `claim_revenue`.

### Finding Description
`require_liquidation_buffer` guarantees that after any borrow, `cash - draw >= reserved`, where `reserved` is `LIQUIDATION_BUFFER_BPS` of floored supply. This is documented as an invariant for every debt mint (INV-ACCT-07). [1](#0-0) 

However, `cash` in `Cache` is not partitioned: it backs both supplier principal and accrued protocol revenue. Revenue shares are minted inside `supplied` by `accrue_revenue` and `absorb_supply_as_revenue`, so the claimable amount `unscale_supply_floor(revenue)` is an outstanding claim on the same `cash` that the buffer check treats as fully available. [2](#0-1) 

Revenue is paid out by `burn_claimable_revenue`, which takes `min(cash, treasury_actual)` and debits cash, with only the utilization and supply-for-debt guards applied — `require_liquidation_buffer` is never re-checked. [3](#0-2) [4](#0-3) 

So the two predicates that are actually checked are `cash - draw >= reserved` (at borrow time) and `cash >= revenue_claim` (implicitly via `min` at claim time). Nothing enforces `cash - draw >= reserved + claimable_revenue`. A borrow can therefore push `cash` to exactly `reserved` while a large revenue balance sits unclaimed; the next claim — or even a normal supplier withdraw, which also only calls `require_reserves` rather than the buffer guard — drives `cash` below the buffer the borrow check "guaranteed." [5](#0-4) 

### Impact Explanation
The liquidation-buffer invariant is the pool's guaranteed floor of exit liquidity. Once `cash` falls below `reserved`, subsequent supplier withdraws and liquidation exits — which only require `cash >= amount` via `require_reserves` — compete for a cash pool that is smaller than the level the protocol promised to keep. The result is temporary freezing of supplier funds and failure of the documented post-borrow solvency guarantee: the market can find itself unable to pay out a withdraw that the buffer was supposed to leave headroom for. [6](#0-5) 

### Likelihood Explanation
Revenue accrues automatically on every interest update (`add_protocol_revenue`), so `revenue > 0` is the normal state of an active market, not an edge case. Any unprivileged borrower can push `cash` to the buffer boundary (`borrow` up to the point where `cash - draw == reserved`), and any unprivileged exit or the revenue claim path then depletes `cash` below `reserved` without any guard stopping it. No privileged action is needed to create the under-reserved state — only the standard accrual that mints the revenue shares in the first place.

### Recommendation
Make the buffer check account for the outstanding revenue claim on the same cash, i.e. enforce

```
cash.saturating_sub(draw) >= reserved + unscale_supply_floor(revenue)
```

in `require_liquidation_buffer` (or equivalently subtract the claimable revenue from `cash` before comparing), and apply the same buffer guard — or an explicit carve-out — on the revenue-claim path in `ops/revenue.rs::accounting` so a claim cannot itself push `cash` below `reserved`. [4](#0-3) 

### Proof of Concept
1. Supplier deposits `S` into a market; borrower activity accrues revenue `R` (scaled revenue shares inside `supplied`).
2. Attacker calls `borrow` sized so that `cash - draw` lands exactly at `reserved = LIQUIDATION_BUFFER_BPS * floor(supplied * supply_index)` — passes `require_liquidation_buffer`. [7](#0-6) 
3. A revenue claim (`claim_revenue` → `ops::revenue::apply` → `burn_claimable_revenue`) pays `min(cash, floor(revenue * supply_index))` and debits `cash`, unchecked by the buffer. [8](#0-7) 
4. `cash` is now `reserved - R_effective`, i.e. below the guaranteed buffer. Supplier withdraws or liquidation payouts totaling more than the remaining cash revert with `InsufficientLiquidity`, temporarily freezing exits even though every individual guard passed. [9](#0-8) 

One caveat I could not fully verify within the iteration limit: whether the controller's `claim_revenue` entrypoint is permissionlessly callable or restricted to the owner. The finding does not depend on it — step 3 can equally be executed by any unprivileged `withdraw` or liquidation exit draining `cash`, since none of the cash-debiting paths recheck the buffer.

```rust
pub(crate) fn require_liquidation_buffer(env: &Env, cache: &Cache, draw: i128) {
    let supplied = cache.unscale_supply_floor(cache.supplied());
    let reserved = mul_div_ceil(env, supplied, LIQUIDATION_BUFFER_BPS, BPS);
    assert_with_error!(
        env,
        cache.cash().saturating_sub(draw) >= reserved,
        CollateralError::InsufficientLiquidity
    );
}
```

```rust
    pub(crate) fn burn_claimable_revenue(&mut self) -> i128 {
        let treasury_actual = self.unscale_supply_floor(self.revenue);
        let amount = self.cash.min(treasury_actual);
        if amount <= 0 {
            return 0;
        }
        let scaled_to_burn = if amount >= treasury_actual {
            self.revenue
        } else {
            self.revenue
                .mul_ratio_ceil(&self.env, amount, treasury_actual)
        };

        assert_with_error!(
            self.env,
            scaled_to_burn != Ray::ZERO,
            GenericError::InternalError
        );
        self.revenue = self.revenue.checked_sub(&self.env, scaled_to_burn);
        self.supplied = self.supplied.checked_sub(&self.env, scaled_to_burn);
        amount
    }
```
