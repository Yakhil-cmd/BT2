### Title
Naive `---` substring split in `extract_frontmatter` lets embedded delimiters silently drop security-critical fields (e.g. `action: block`) - (File: `plugins/hookify/core/config_loader.py`)

### Summary
`extract_frontmatter` locates the YAML frontmatter boundary using `content.split('---', 2)`, which matches the literal three-character substring `---` anywhere in the text rather than requiring it to appear alone on its own line. If any frontmatter field value (e.g. a `pattern` regex like `^---$`) contains three consecutive dashes before the real closing fence, the split cuts the frontmatter short at that embedded occurrence, silently moving all subsequent lines — including `action: block` and the true closing `---` — into the unparsed `message` body. Because `Rule.from_dict` falls back to `action='warn'` when the key is missing, a rule that visually reads as `action: block` in the file is parsed and enforced as `warn` (or dropped entirely if the frontmatter dict ends up empty).

### Finding Description
`extract_frontmatter` starts by checking `content.startswith('---')` and then does `parts = content.split('---', 2)`, taking `parts[1]` as the entire frontmatter text and `parts[2]` as the message body. [1](#0-0)  This split operates on the raw string for the literal substring `---` wherever it occurs, not on lines consisting solely of `---`. Any earlier field value containing three dashes (e.g. a `pattern: ^---$` line meant to detect Markdown/YAML frontmatter delimiters, or any regex/text with `---`) is counted as the second delimiter, truncating `frontmatter_text` before the real `action:` field and shoving the remainder — including the genuine `action: block` line and the true closing `---` — into `message`. [2](#0-1) 

Downstream, `Rule.from_dict` reads `action=frontmatter.get('action', 'warn')`, so a missing `action` key (because it landed in `message` instead of `frontmatter`) silently downgrades a rule that was written and appears in the file as `action: block` to the default `warn` behavior. [3](#0-2)  In `RuleEngine.evaluate_rules`, only rules with `rule.action == 'block'` are placed in `blocking_rules` and cause a `deny`/`block` response; everything else becomes a non-blocking warning that still allows the tool call to proceed. [4](#0-3)  `load_rule_file` also treats an empty frontmatter dict as "missing YAML frontmatter" and returns `None`, silently dropping the rule from enforcement altogether in more severe truncation cases. [5](#0-4) 

Rule files are discovered purely by filesystem glob over `.claude/hookify.*.local.md` with no origin/provenance check and no schema validation — no `validate`/`sanitize`/`schema` logic exists anywhere in the plugin. [6](#0-5)  This means any such file present in a cloned repository's `.claude/` directory — regardless of whether it was created via `/hookify` or committed directly by a repository author/attacker — is loaded and enforced exactly the same way. An unprivileged attacker who controls repository content (e.g. via a malicious template repo, PR, or fork that a victim clones) can commit a `.claude/hookify.*.local.md` file that reads, on visual inspection, as a legitimate `action: block` rule guarding a dangerous behavior, while the actual parsed `Rule` object has `action='warn'` (or the rule is dropped entirely), because of an embedded `---` in an earlier field value (most plausibly in a `pattern` regex).

### Impact Explanation
This breaks the stated invariant that "rule semantics must not change because of formatting ambiguity." A rule intended and displayed as `block` for a dangerous `Bash`/`Edit`/`Stop` invocation is silently enforced as `warn` or not enforced at all, so Claude Code will execute the operation (e.g. destructive `rm -rf`, writing to a sensitive/out-of-scope file, or an unsafe `Stop`) that the user or rule author believed was hard-blocked. This maps to the "Unauthorized file read or write outside the user-approved workspace or target scope" impact category: the user's approval/enforcement expectation (block) is subverted by a parser inconsistency they cannot detect just by reading the file, and the dangerous tool call proceeds.

### Likelihood Explanation
The precondition is simply that a `.claude/hookify.*.local.md` file with a crafted frontmatter value containing `---` exists in a cloned/opened repository — no special privilege, key leakage, or social engineering is required beyond normal repository consumption. The plugin's own documentation encourages patterns matching things like `\.env$`, diff markers, or frontmatter-like content, making an embedded `---` in a `pattern` value plausible even accidentally, and trivially constructible deliberately by a malicious repo. [7](#0-6)  The bug is deterministic and 100% reproducible given such a file — there is no randomness or race condition involved.

### Recommendation
Replace the substring-based `content.split('---', 2)` with a line-anchored frontmatter delimiter check (e.g. using `re.split` with a pattern like `^---\s*$` in `re.MULTILINE` mode, or by iterating lines and only treating a line that is *exactly* `---` after stripping as a delimiter). Additionally, add explicit validation in `Rule.from_dict`/`load_rule_file` that rejects or warns loudly (rather than silently defaulting) when a rule's `action` field is absent for rules that reference dangerous operations, and consider hashing/logging the raw vs. parsed frontmatter fields so any divergence is surfaced to the user before enforcement.

### Proof of Concept
Add a unit test in `plugins/hookify/core/` (or wherever tests live) that:
1. Constructs `content` equal to:
```
---
name: block-dangerous-rm
enabled: true
event: bash
pattern: rm\s+-+rf|^---$
action: block
---

Blocked dangerous command.
```
2. Calls `frontmatter, message = extract_frontmatter(content)`.
3. Asserts `frontmatter.get('action') != 'block'` (demonstrating the field is lost/defaulted), i.e. `assert 'action' not in frontmatter`.
4. Calls `rule = Rule.from_dict(frontmatter, message)` and asserts `rule.action == 'warn'` even though the raw file explicitly states `action: block`.
5. Feeds `rule` into `RuleEngine.evaluate_rules([rule], {'hook_event_name': 'PreToolUse', 'tool_name': 'Bash', 'tool_input': {'command': 'rm -rf /'}})` and asserts the response does NOT contain `"permissionDecision": "deny"`, confirming the dangerous command is allowed to proceed despite the file visually declaring `action: block`.
