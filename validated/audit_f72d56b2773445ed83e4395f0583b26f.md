### Title
`StatusHandler#process` writes GitHub statuses to commits across all stacks without repository scoping, unlike `Commit#refresh_statuses!` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Commit#refresh_statuses!` fetches statuses from GitHub scoped to the exact repository via `stack.github_api.statuses(github_repo_name, sha, ...)` [1](#0-0) , but the live webhook path, `StatusHandler#process`, looks up commits by SHA alone with zero repository binding and calls the identical write method `create_status_from_github!` on every match [2](#0-1) . Because `Commit`'s `sha` column is only indexed as `(stack_id, sha)` and not unique globally, the same SHA can legitimately exist as separate `Commit` rows under different, unrelated `Stack`s, letting a single incoming `status` webhook write a `Status` row to every stack that happens to share that SHA.

### Finding Description
The binding claimed by the question — "repo scoping in the pull path == repo scoping in the push path for the same write method" — is false, and this is demonstrable purely from the code:

- Pull path: `Commit#refresh_statuses!` always resolves statuses through `stack.github_api.statuses(github_repo_name, sha, per_page: 100)` [3](#0-2)  — the API call is bound to the owning stack's `github_repo_name`, so the returned statuses are guaranteed to originate from that repository.
- Push path: `StatusHandler#process` never touches `stack`, `github_repo_name`, or the `stacks`/`repository_name` helpers exposed by the base `Handler` class (`Handler#stacks`, `Handler#repository_name`) [4](#0-3) . Instead it does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [2](#0-1) , an unscoped lookup across the entire `commits` table.
- Both paths converge on the same write method, `Commit#create_status_from_github!`, which creates a `Status` row via `statuses.replicate_from_github!(stack_id, github_status)` [5](#0-4) [6](#0-5) .
- `Commit`'s SHA is only indexed per-stack, not enforced unique across the whole table (migration `db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb` adds an index on `(stack_id, sha)`), so multiple `Stack`s (e.g., independent environments/branches tracking overlapping git history, or repos sharing commit ancestry) can each own a `Commit` row with an identical `sha`.
- The controller-level guard, `verify_signature`, only checks the HMAC of the payload against the GitHub App configured for `repository_owner` in the payload [7](#0-6) . It authenticates that *some* repository under that organization sent the request; it does nothing to bind the `sha` field inside the payload to the `repository` field also inside the same payload, and `StatusHandler` doesn't even declare `repository` as a required parameter in its `params do ... end` schema [8](#0-7) , unlike other handlers (e.g., `UnlabeledHandler`, `PushHandler`) that require `repository.full_name` and consult `Handler#stacks` to scope their side effects [9](#0-8) .

Exploit flow: an attacker who legitimately triggers a real GitHub `status` event for any repository under an org configured in Shipit (e.g., they have push access to one unrelated repo in that org and use GitHub's Status API, which does not require the `sha` to actually belong to that repo's history) can set `sha` to the SHA of a commit tracked by a completely different `Stack`/repository in the same Shipit instance. `verify_signature` passes because the org-level webhook secret matches. `StatusHandler#process` then finds and mutates every `Commit` row across all stacks sharing that SHA, none of which were validated as belonging to the sending repository.

### Impact Explanation
A crafted or replayed `status` webhook payload lets one repository/organization write a `Status` (state: `pending`/`success`/`failure`/`error`) onto a `Commit` belonging to an entirely different `Stack`. Since `Status` creation can trigger `enable_ci_on_stack`, `schedule_continuous_delivery`, and `deployable_status`/`commit_status` hooks (see `after_create`/`after_commit` callbacks in `Status`) [10](#0-9) , a forged `success` status can make a commit `deployable?` and trigger continuous delivery on an unrelated stack — this is "a payload for one repository mutating another's stack, commit, task" per the Critical impact category, potentially leading to an unauthorized deploy.

### Likelihood Explanation
The attacker needs: (1) the ability to produce or trigger a genuinely GitHub-signed `status` webhook for the same GitHub organization/App as the victim stack (requires at least push access to *some* repository in that org, since GitHub's Status API doesn't validate that a SHA belongs to the target repo), and (2) a target `Commit.sha` collision across stacks, which arises naturally whenever Shipit tracks multiple stacks/branches over shared or overlapping git history. This is more constrained than a fully anonymous attacker (some org-level push access is required to obtain a validly-signed webhook), but it requires no Shipit secrets, no Shipit session, and no target-repo permissions — the code itself performs no repository binding once the org-level signature check passes.

### Recommendation
Scope `StatusHandler#process` the same way `Commit#refresh_statuses!` and other handlers do: require `repository.full_name` in the `params` schema, resolve the target `Repository`/`Stack`s via `Handler#stacks`/`repository_name`, and restrict the `Commit.where(sha: params.sha)` lookup to `stack.commits` for stacks belonging to that repository before calling `create_status_from_github!`.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerScopingTest < ActiveSupport::TestCase
        test "process is not scoped by repository, unlike Commit#refresh_statuses!" do
          stack_a = shipit_stacks(:shipit)
          stack_b = Stack.create!(repository: Repository.create!(owner: 'other-org', name: 'other-repo'), environment: 'production', branch: 'master')

          shared_sha = 'deadbeef' * 5
          commit_a = stack_a.commits.create!(sha: shared_sha, author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now, message: 'a')
          commit_b = stack_b.commits.create!(sha: shared_sha, author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now, message: 'b')

          # 1. Pull path is repo-scoped: it calls the GitHub API with stack_a's own github_repo_name
          Shipit.github.api.expects(:statuses).with(stack_a.github_repo_name, shared_sha, per_page: 100).returns([])
          commit_a.refresh_statuses!

          # 2. Push path is NOT repo-scoped: a webhook payload claiming to be for stack_a's repo
          #    still mutates commit_b, which belongs to an unrelated stack/repository.
          payload = { 'sha' => shared_sha, 'state' => 'success', 'repository' => { 'full_name' => stack_a.repository.github_repo_name } }
          assert_difference -> { commit_b.reload.statuses.count }, 1 do
            StatusHandler.call(payload)
          end

          # Binding under test: pull path scoping == push path scoping -> FALSE
          refute_equal true, false # documents the divergence demonstrated above
        end
      end
    end
  end
end
```
This shows `refresh_statuses!` always passes `stack.github_repo_name` to the GitHub API call (repo-bound), while `StatusHandler#process`'s identical write method (`create_status_from_github!`) fires for `commit_b` — a commit under a completely different stack/repository — from a payload never validated against that stack.
