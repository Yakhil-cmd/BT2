### Title
Users' Funds Are Permanently Frozen in Arbiter Contract Shared Address if the Arbiter Never Posts a Resolution - (File: arbiter_contract.js)

### Summary
The `arbiter_contract` P2P escrow feature locks a buyer's payment into a shared multi-signature address whose spending conditions are generated by `deriveSharedAddress()`. The only ways to release the funds are (1) both parties mutually sign, (2) either party posts an output satisfying the other's exact terms, or (3) the arbiter (the single trusted "coordinator") posts a resolving data feed. If the counterparty refuses to cooperate and the arbiter is offline, unresponsive, compromised, or deliberately censoring the case, there is no timeout or unilateral withdrawal path, and the deposited funds are permanently stuck — mirroring the reported `TokenBridge` bug class where a single failing/censoring coordinator locks user funds with no recovery mechanism.

### Finding Description
`deriveSharedAddress()` builds the address-definition (`arrDefinition`) used for the escrow "shared address" that a payer sends funds to via `pay()`: [1](#0-0) 

For non-private assets, the "or" clause offers exactly five ways to spend funds from the shared address: mutual signature by both parties, `offeror` satisfying `acceptor`'s output, `acceptor` satisfying `offeror`'s output, or the arbiter posting a data feed `CONTRACT_<hash> = offeror_address` / `= acceptor_address`: [2](#0-1) 

Funds are moved into this shared address in `pay()`: [3](#0-2) 

When a dispute is opened, the contract enters `in_dispute` status and the wallet waits indefinitely for the arbiter to publish a resolution to the arbiter's data feed; there is no expiry logic that ever allows either party to reclaim funds unilaterally: [4](#0-3) [5](#0-4) 

Because the "in data feed" branches require BOTH the arbiter's data feed AND the winning party's own signature (`["and", [["address", …], ["in data feed", …]]]`), and there is no fallback branch with a time-based condition (e.g., `not in data feed ... AND after timeout`), if:
- the arbiter's device/hub is down,
- the arbiter is censoring/refusing to resolve the case, or
- the counterparty simply refuses to cosign a release,

then none of the five spending branches can ever be satisfied, and the coins sent to the shared address are permanently frozen. This is structurally identical to the reported `TokenBridge.setCustomContract`-class issue: a single off-chain "coordinator" (there, the bridge relayer; here, the arbiter) is a single point of failure with no built-in withdrawal/timeout safety valve for depositors.

### Impact Explanation
Any user who funds an arbiter contract (a normal wallet feature reachable by any user, not privileged) can have their locked payment (`base` or asset) permanently frozen if the counterparty is unresponsive and the arbiter/arbstore is unavailable or malicious/censoring. This is a fund-freezing vulnerability with no built-in recovery mechanism (the address definition, once fixed via `objectHash.getChash160`, cannot be changed post-hoc). This qualifies as AA/contract fund freezing per the accepted impact classes.

### Likelihood Explanation
The failure conditions (arbiter/arbstore hub goes offline, arbiter device is compromised/malicious, arbiter deliberately stalls to extort a side payment, or the counterparty is simply unresponsive/uncooperative after a dispute is opened) are realistic operational scenarios for any long-lived P2P escrow system with a single arbiter. No special privileges are required to trigger it — it happens automatically anytime the arbiter fails to respond after a dispute, which is an intended, reachable state machine transition (`paid` → `in_dispute`).

### Recommendation
Add a time-boxed unilateral recovery branch to the shared-address definition, e.g. allow the payer (or both parties by majority) to reclaim/split funds after a fixed timeout (`after timestamp` guard combined with `not in data feed`) if the arbiter has not posted a `CONTRACT_<hash>` resolution within a defined SLA. Alternatively, support arbiter rotation/appeal-to-alternate-arbiter, or a mutual "abort and refund" signature path that does not require arbiter involvement.

### Proof of Concept
1. Alice (payer) and Bob (payee) create an arbiter contract via `arbiter_contract.createAndSend`, referencing arbiter A.
2. Alice pays into the resulting `shared_address` via `pay()` (`arbiter_contract.js:692-717`).
3. A dispute arises; Alice calls `openDispute()` (`arbiter_contract.js:262-319`), setting status to `in_dispute` and registering the arbiter's address as watched for a resolution data feed.
4. Arbiter A goes offline permanently, or is compromised and refuses to post the `CONTRACT_<hash>` data feed, or Bob simply refuses to sign any cooperative release.
5. Because `deriveSharedAddress()`'s five spending conditions (`arbiter_contract.js:465-522`) all require either mutual signature, satisfying the counterparty's exact desired output, or a valid arbiter data feed plus the winner's signature, none can ever be satisfied.
6. Alice's deposited funds in `shared_address` remain frozen indefinitely with no on-chain or off-chain recovery path.

function pay(hash, walletInstance, arrSigningDeviceAddresses, cb) {
	getByHash(hash, function(objContract) {
		if (!objContract.shared_address || objContract.status !== "signed" || !objContract.me_is_payer)
			return cb("contract can't be paid");
		var opts = {
			asset: objContract.asset,
			to_address: objContract.shared_address,
			amount: objContract.amount,
			spend_unconfirmed: walletInstance.spendUnconfirmed ? 'all' : 'own'
		};
		if (arrSigningDeviceAddresses.length)
			opts.arrSigningDeviceAddresses = arrSigningDeviceAddresses;
		walletInstance.sendMultiPayment(opts, function(err, unit){								
			if (err)
				return cb(err);
			setField(objContract.hash, "status", "paid", function(objContract){
				cb(null, objContract, unit);
			});
			// listen for peer announce to withdraw funds
			storage.readAssetInfo(db, objContract.asset, function(assetInfo) {
				if (assetInfo && assetInfo.is_private)
					db.query("INSERT "+db.getIgnore()+" INTO my_watched_addresses (address) VALUES (?)", [objContract.peer_address]);
			});
		});
	});
}
