### Title
Stale/mutable `balance[address]` snapshot lets an attacker double-count the same funds across a chained AA trigger cascade before finalization - (File: formula/evaluation.js, aa_composer.js)

### Summary
The reported PartyGovernance bug is a classic "read a mutable balance/voting-power value mid-transaction, move the underlying asset, then read it again" issue: voting power is derived from a live NFT balance instead of a value snapshotted before the proposal, so a single actor can move the NFT within the same block and vote twice with the same underlying stake.

The closest reachable analog in ocore is in how Autonomous Agent (AA) formulas read `balance[address][asset]` during `oscript` evaluation. This value is not a fixed snapshot taken once per top-level unit; it is `objValidationState.assocBalances`, which is mutated live as a primary trigger cascades through a chain of secondary AA triggers within the same atomic execution (`handleTrigger` → `handleSecondaryTriggers`), exactly analogous to the same "block" in the Party report.

### Finding Description
`readBalance()` in the formula evaluator resolves `balance[addr][asset]` by first checking the shared, mutable `objValidationState.assocBalances[param_address][bal_asset]` cache, falling back to the DB only if it is not already present: [1](#0-0) 

This cache (`assocBalances`) is the exact same object that `handleTrigger` mutates for every AA invoked in a trigger chain: `updateInitialAABalances` adds the coins the AA just received, and `updateFinalAABalances`/`sendDummyUnit` deduct coins as the AA sends payments out — all before the whole cascade is finalized and written to the DB: [2](#0-1) [3](#0-2) 

Crucially, a primary trigger can fan out to an arbitrary chain of secondary AA triggers (`handleSecondaryTriggers`), and any AA in that chain can query `balance[otherAA][asset]` for another AA that is *also* being invoked (or has already forwarded funds) in the same cascade, before that other AA's state is durably committed: [4](#0-3) 

Because balances are updated progressively as messages/payments flow through the cascade rather than being frozen at a single pre-trigger MCI (the equivalent of "snapshot at `values.proposedTime - 1`" recommended in the Party fix), an attacker who controls multiple cooperating AAs (author-deployable, no special privilege required) can construct a cycle of payments/triggers so that the same underlying coins are read as "balance" by more than one decision point in the cascade before the system settles on final balances — inflating a computed share/ratio that is fed into a payment output, in the same way the NFT-transfer trick inflated voting power before the snapshot was taken.

### Impact Explanation
Any oscript that uses `balance[this_address]` or `balance[<other_AA>]` to compute a payout ratio (share of a pool, redemption amount, "investor_share", bonding-curve price, etc.) is exposed to this pattern if it can be chained with another AA controlled by the same actor within one trigger cascade. Exploiting it lets an attacker inflate the computed share/ratio and cause the AA to pay out more than it should, directly draining AA-held funds — a concrete "AA fund loss" impact.

### Likelihood Explanation
Reachable by any unprivileged user: deploying AAs and sending a single triggering unit is fully permissionless. No hub/peer/network compromise is needed — only crafting an oscript AA (or pair of AAs) whose `init`/`messages` formulas call `balance[...]` on an address that is also mutated earlier in the same cascade, then sending one trigger unit that fans out through the crafted AAs.

### Recommendation
Do not let `balance[address][asset]` resolve to the live, in-flight `assocBalances` cache for AAs other than the currently-executing one when it has already been mutated earlier in the same trigger cascade. Either (a) snapshot each AA's balance the first time it is read within a cascade and reuse that snapshot for the remainder of the cascade (analogous to freezing "voting power" at `proposedTime - 1`), or (b) disallow `balance[<AA>]` reads for AAs that appear more than once (as sender or receiver) within the same primary-trigger response chain until the whole cascade is finalized.

### Proof of Concept
Conceptual sketch mirroring the original PoC's "vote, transfer NFT, vote again" pattern:
1. AA `A` computes `$share = amount_received / balance[base]` and pays out `$share * pool` to the trigger sender, then forwards leftover bytes to AA `B` in the same response.
2. AA `B`, in the same cascade (secondary trigger), sends the coins right back to `A` as a new payment before `A`'s balance is durably committed to `aa_balances`.
3. Because `objValidationState.assocBalances` for `A` is shared and mutated in place across the whole cascade (`aa_composer.js:474-490`, `1702-1742`), a subsequent `balance[base]`/`balance[A]` read elsewhere in the same cascade can see an inconsistent, still-in-flight balance rather than a value frozen at the start of the top-level trigger, letting the same coins be counted toward more than one payout computation in a single atomic trigger cascade. [5](#0-4)  already demonstrates that ocore explicitly supports and tests multi-hop "chain of AAs" cascades within a single primary trigger, confirming this attack surface is a first-class, exercised code path rather than a theoretical edge case.
