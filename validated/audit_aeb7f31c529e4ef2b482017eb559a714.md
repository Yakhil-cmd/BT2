The vulnerability is real and confirmed by comparing `StatusHandler` against the sibling `PushHandler`, which shows the correct pattern is available but not used.

### Title
Cross-tenant Status forgery via unscoped `Commit.where(sha:)` in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits globally by `sha` across the entire database instead of scoping to the repository that authenticated the webhook, then calls `Commit#create_status_from_github!` for every match, each write scoped to that commit's own `stack_id`. Since GitHub `sha`s (e.g. the empty-tree sha `4b825dc642cb6eb9a060e54bf8d69288fbee4904`, or any coincidental sha collision across unrelated forks) are not unique to one repository, an attacker who owns a completely unrelated repository can send one legitimately-signed status webhook that writes `Status` rows onto commits belonging to other tenants' stacks.

### Finding Description
The broken binding: the set of `stack_id` values touched by processing a webhook must equal `Repository.from_github_repo_name(payload.repository.full_name).stacks.map(&:id)` (the stacks owned by the authenticating repository). Instead it equals `Commit.where(sha: params.sha).map(&:stack_id)` — every stack in the whole installation that happens to contain a commit with that sha.

Code path:
- `Shipit::WebhooksController#create` parses the payload and dispatches to `Shipit::Webhooks.for_event(event)` handlers after `verify_signature`, which only checks that the payload was signed by *some* `repository_owner`'s GitHub App secret — it proves the caller controls the named repository, not that the sha is scoped to it. [1](#0-0) 
- `Shipit::Webhooks::Handlers::Handler` provides a `stacks` helper explicitly meant to scope lookups to the authenticating repository: `Repository.from_github_repo_name(repository_name)&.stacks || Stack.none`. [2](#0-1) 
- `PushHandler#process` correctly uses this scope: `stacks.not_archived.where(branch:).find_each { ... }`. [3](#0-2) 
- `StatusHandler#process`, however, bypasses `stacks` entirely and queries `Commit.where(sha: params.sha)` — unscoped, matching commits from *any* stack/repository in the database — then calls `commit.create_status_from_github!(params)` for each. [4](#0-3) 
- `Commit#create_status_from_github!` calls `statuses.replicate_from_github!(stack_id, github_status)`, which does `find_or_create_by!(stack_id:, ...)` scoped to that commit's own `stack_id`, regardless of which repository sent the webhook. [5](#0-4) [6](#0-5) 

Exploit: an attacker registers/owns any GitHub repository configured as a Shipit repository/stack (or any repo whose commits happen to collide in sha with another tenant's commits — trivially true for the empty tree sha, which is identical across every git repository). They push a commit whose sha collides with a sha already tracked in another tenant's stack (or simply reuse the empty-tree sha, which is common in many repos' history), then send a signed `status` webhook for their own repository with that sha. Because `verify_signature` only checks the signature matches `repository_owner`'s secret, and `StatusHandler#process` never re-checks that the matched commits belong to a stack of that same repository, the handler creates `Status` rows on the victim stacks' commits as well as the attacker's own. Existing guards (`verify_signature`, `ExplicitParameters` schema, `drop_unhandled_event`) only validate signature/shape, not repository ownership of the target commit; the `stacks` scoping guard that would prevent this exists in `Handler` but is simply not invoked by `StatusHandler`.

### Impact Explanation
The attacker can write arbitrary-content `Status` rows (state/description/target_url/context/created_at, bounded by GitHub's status payload schema) onto commits belonging to other repositories/stacks that they do not control, without authenticating as those repositories. This can flip a foreign stack's `deployable?`/CI state (`Status` transitions drive `stack.schedule_merges`, `deployable_status` hooks, and continuous deployment scheduling per `Commit#add_status`) [7](#0-6) , potentially causing an unauthorized merge or deploy trigger on a stack the attacker never authenticated for. This is a payload for one repository mutating another's commit/stack state — matching the Critical category defined in scope.

### Likelihood Explanation
Preconditions are modest: the attacker needs a repository that Shipit is configured to receive webhooks from (any repository they legitimately own that has a Shipit `GithubHook`/webhook configured, which is the normal, unprivileged workflow for any repo owner), and a sha collision with a victim commit. Sha collisions are trivially achievable via the well-known empty-tree sha `4b825dc642cb6eb9a060e54bf8d69288fbee4904`, present in essentially all git histories, or by an attacker deliberately crafting/forking history to reuse a known victim sha. No secrets, sessions, or elevated roles are required — only a normal signed webhook for the attacker's own repo. The attack is repeatable against any victim stack sharing a colliding sha.

### Recommendation
In `StatusHandler#process`, scope the commit lookup to the authenticating repository's stacks, mirroring `PushHandler`, e.g. `stacks.joins(:commits).merge(Commit.where(sha: params.sha))` or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, so only commits belonging to stacks of the repository that signed the webhook are updated. [4](#0-3) 

### Proof of Concept
Minitest plan (controller test, no live GitHub):
1. In `test/controllers/webhooks_controller_test.rb`, create two stacks/repositories, e.g. reuse `shipit_stacks(:shipit)` (repository `Shopify/shipit-engine`) and `shipit_stacks(:cyclimse)` (repository `cyclimse/...`).
2. Create two `Commit` fixtures/records with the identical `sha` (e.g. the empty-tree sha), one under each stack: `commit_a = shipit_stacks(:shipit).commits.create!(sha: SAME_SHA, ...)`, `commit_b = shipit_stacks(:cyclimse).commits.create!(sha: SAME_SHA, ...)`.
3. Stub `GithubHook.any_instance.stubs(:verify_signature).returns(true)` as existing tests do.
4. POST a `status` webhook whose `repository.full_name` is `Shopify/shipit-engine` (i.e., only authenticates for `commit_a`'s repository) with `sha: SAME_SHA`.
5. Assert `Status.where(commit: [commit_a, commit_b]).count == 2` — proving a webhook authenticated only for the `Shopify/shipit-engine` repository also wrote a `Status` on `commit_b`, which belongs to the unrelated `cyclimse` repository/stack. Before the fix this assertion passes (bug present); after scoping the fix, the count should be `1` (only `commit_a`).
