### Title
Cross-organization webhook signature confusion: authenticated org vs. repository actually written - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the webhook secret to validate the HMAC signature using `repository_owner`, derived from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`) [1](#0-0) [2](#0-1) . Once the signature is accepted, every event handler independently determines which repository/stack to mutate using a *different* field of the same payload: `payload.dig('repository', 'full_name')`, via `Handler#repository_name`/`#stacks` and each handler's own `repository` method (`Repository.from_github_repo_name(params.repository.full_name)`) [3](#0-2) [4](#0-3) [5](#0-4) . Nothing ties `repository.owner.login` (the value used to pick the verifying secret) to `repository.full_name` (the value used to pick the repository that gets written to). In a multi-organization deployment (`Shipit.github_organizations`, `Shipit.github_app_config(organization)`) [6](#0-5) , each organization has its own `webhook_secret` configured under `secrets.github[organization]`. An organization admin who legitimately owns a GitHub webhook for their own org (and therefore knows/controls that org's `webhook_secret`) can craft an arbitrary raw payload — since HMAC covers the exact bytes they submit — where `repository.owner.login` equals their own org (so `Shipit.github(organization: repository_owner)` picks their own valid secret and the signature check passes) while `repository.full_name` names a completely different, unrelated repository tracked under another organization/owner in Shipit. `verify_signature` never checks that these two fields agree.

### Finding Description
The equality that should hold but is broken: `organization authenticated by verify_signature (repository.owner.login)` == `organization owning the repository actually mutated by the handler (repository.full_name's owner segment)`. `verify_signature` authenticates the *sender* only by resolving a per-organization secret from one payload field, then trusts the entire raw body (including a completely independent field) to decide what gets written. Because Rails' HMAC verification is over raw bytes the attacker fully controls, and because the attacker legitimately possesses one org's secret (via their own configured GitHub App/webhook, as documented setup), the check "is this payload well-formed and correctly signed for organization X" is conflated with "is this payload's target repository under organization X." These are never cross-checked anywhere in `WebhooksController` or `Shipit::Webhooks::Handlers::Handler`.

### Impact Explanation
An attacker with legitimate ownership of exactly one tracked organization's webhook secret can forge events (e.g. `push`, `pull_request` opened/closed/reopened/labeled, `status`, `check_suite`, `membership`) that reference an arbitrary victim repository/stack belonging to a different organization also configured in the same Shipit instance. Depending on handler, this can trigger `GithubSyncJob` on a victim stack (importing attacker-chosen "commits" data into the victim's commit history) [7](#0-6) , archive/unarchive/deprovision a victim review stack [8](#0-7) , or spoof commit statuses. This crosses a repository trust boundary the signature check is meant to enforce, matching the "cross-repository writes" / unauthorized state-changing action category.

### Likelihood Explanation
Requires the attacker to already control a legitimate webhook for at least one organization tracked by the same Shipit instance (a real but plausible multi-tenant configuration), and requires them to know the `full_name`/branch of a victim repository/stack (public information). No privileged Shipit account, API token, or GitHub token exfiltration is needed — only the ability to craft raw HTTP POSTs to the public `/webhooks` endpoint with a validly-signed-for-their-own-org body.

### Recommendation
In `WebhooksController#verify_signature` (and/or `Handler`), enforce that the organization used to select the verifying secret matches the owner of the repository the handler will act on — e.g., re-derive `repository_owner` consistently from the exact same field the handlers use (`repository.full_name`), or explicitly compare `params.dig('repository','owner','login')` against `params.dig('repository','full_name').split('/').first` and reject (422) on mismatch before dispatching to handlers.

### Proof of Concept
1. Shipit is configured with two organizations, `attacker-org` and `victim-org`, each with its own `webhook_secret` under `secrets.github`.
2. Attacker configures a webhook on their own `attacker-org` repo, obtaining/knowing `webhook_secret_attacker`.
3. Attacker crafts a raw JSON body for a `push` (or `pull_request`) event where:
   - `repository.owner.login = "attacker-org"`
   - `repository.full_name = "victim-org/victim-repo"`
   - `ref`/`after`/other fields chosen to target the victim stack's branch and desired head sha.
4. Attacker computes `X-Hub-Signature: sha1=HMAC(webhook_secret_attacker, raw_body)` themselves and POSTs to `/webhooks` [9](#0-8) .
5. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and validates successfully against the attacker's own secret [1](#0-0) .
6. `PushHandler#process` resolves the target via `Repository.from_github_repo_name("victim-org/victim-repo")` and enqueues `GithubSyncJob`/archives the victim's stack, even though the request was never signed by `victim-org`'s secret [3](#0-2) [7](#0-6) .

Note: I could not fully verify the exact production `secrets.github` YAML/credentials shape from the index (only `lib/shipit.rb`'s accessor logic was available), so exact multi-org key formatting could not be double-checked against a live credentials file — this doesn't affect the logical mismatch identified above, which is fully supported by the controller and handler code shown.

  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end
