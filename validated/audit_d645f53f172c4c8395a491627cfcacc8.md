This confirms the multi-tenant model: Shipit supports multiple GitHub organizations, each with its own `webhook_secret` configured under `secrets.github[<org>]` [1](#0-0) [2](#0-1) . `WebhooksController#verify_signature` selects which org's secret to check against by reading `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`), then calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [3](#0-2) [4](#0-3) . But `Handler#repository_name`/`#stacks`, used by every dispatched handler to locate the target `Repository`/`Stack`, reads a **different** field: `payload.dig('repository', 'full_name')` [5](#0-4) , which is then split into owner/name and looked up via `Repository.from_github_repo_name` [6](#0-5) .

Since `repository.owner.login` and `repository.full_name` are two independent JSON fields in the same attacker-supplied body, and `WebhooksController#create` forwards the raw parsed `params` unchanged to `handler.call(params)` with zero reconciliation between the two fields [7](#0-6) , a tenant that legitimately owns organization "attacker-org" (and thus knows/can compute a valid signature with `attacker-org`'s `webhook_secret`) can set `repository.owner.login = "attacker-org"` (passes signature check) while setting `repository.full_name = "victim-org/victim-repo"` (used by the handler to resolve the actual `Stack`/`Repository`/`Commit` row that gets written).

However, whether this is actually exploitable depends on details I could not fully verify in remaining time: what specific field(s) each handler (`PushHandler`, `StatusHandler`, `MembershipHandler`, `CheckSuiteHandler`, `PullRequest::*Handler`) writes to the DB, whether any of them independently re-derive the owner from `full_name` for authorization purposes elsewhere, and whether `StackCommands`/`Command#start`'s env/argv path is reachable from any of these handlers in a way that lets an attacker control argv (I did not get to trace `lib/shipit/stack_commands.rb` in depth given the iteration limit).

### Title
Webhook signature verification org (`repository.owner.login`) is never reconciled with the org used to locate the target Stack/Repository (`repository.full_name`) - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` authenticates a webhook using the organization found at `params['repository']['owner']['login']`, but every `Handler` subclass resolves the record to write using `params['repository']['full_name']` [8](#0-7) . These two fields are independently attacker-controlled in the same JSON body and are never compared, so a legitimate tenant of one organization can produce a validly-signed webhook that is dispatched against another organization's repository/stack.

### Finding Description
The binding that should hold is: `org_that_signed(webhook) == org_of(full_name_used_to_locate_stack)`. In code, the left side is computed in `repository_owner` (`params.dig('repository','owner','login') || params.dig('organization','login')`) and used only to pick the `GitHubApp`/secret for `verify_webhook_signature` [3](#0-2) . The right side is computed independently in `Handler#repository_name` from `payload.dig('repository', 'full_name')` [8](#0-7) , feeding `Repository.from_github_repo_name` which splits on `/` to find `owner`/`name` and loads the matching `stacks` [6](#0-5) . `WebhooksController#create` calls `handler.call(params)` for every matching handler with no code in between that checks these two derived owners against each other [7](#0-6) . Because Shipit is explicitly multi-tenant (`Shipit.github_organizations`, per-org `webhook_secret` in `secrets.github[<org>]` [9](#0-8) ), an org that legitimately possesses its own webhook secret can sign a payload whose `owner.login` is itself but whose `full_name` names a repository belonging to a different, victim organization.

### Impact Explanation
If exploitable end-to-end (unverified in the time available), this would let one tenant's validly-signed webhook drive writes (e.g. `GithubSyncJob` enqueue with another stack's id, `Commit`/`Status` rows, `Membership`/`Team` records) against a different organization's `Stack`/`Repository`, i.e. "a payload for one repository mutating another's stack/commit/task" — matching the Critical category in the rubric. The blast radius would be cross-tenant, and repeatable on every webhook event as long as the attacker's own org has a configured `webhook_secret`.

### Likelihood Explanation
Requires the attacker to control (own) at least one GitHub organization/installation that is itself a configured Shipit tenant with a known-to-them `webhook_secret` — this is a real precondition, not a privileged Shipit role. I was not able to fully confirm, within the remaining budget, whether every downstream handler actually uses attacker-influenced `full_name` without any secondary owner check, nor trace `StackCommands`/`Command#start` argv construction to see if this reaches process execution. This significantly limits confidence in the full "Command argv" chain part of the question.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler#initialize`), assert that the organization used to validate the signature equals the organization parsed from `repository.full_name` (or `organization.login` for org-level events) before dispatching to any handler; reject (422) on mismatch.

### Proof of Concept
Not fully certified: I identified the divergent-field root cause (`owner.login` vs `full_name`) and the unconditional `handler.call(params)` dispatch, but did not complete tracing every handler's write path or `StackCommands`/`Command#start` to certify a concrete assertable minitest showing a *written row* reflecting the unauthenticated identity within the available iterations. A conclusive PoC would need, in `test/controllers/webhooks_controller_test.rb`-style test (outside `test/**` per rules is disallowed for the final artifact, so this would need to be produced by a follow-up engineering task): stub `attacker-org`'s `GitHubApp#verify_webhook_signature` to return true, post a `push` event with `repository.owner.login = "attacker-org"` and `repository.full_name = "victim-org/victim-repo"`, and assert a `GithubSyncJob` is enqueued with `victim-org/victim-repo`'s `stack_id` while the signature was validated against `attacker-org`'s secret.
