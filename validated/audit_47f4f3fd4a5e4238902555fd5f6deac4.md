### Title
`CCMenuController#stack` bypasses `ApiClient#stack_id` scoping, allowing a stack-scoped token to read another stack's CCMenu state - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController#stack` resolves the target stack via `Stack.from_param!(params[:stack_id])` directly, instead of using `Shipit::Api::BaseController#stacks`, which is the helper that restricts lookups to `Stack.where(id: current_api_client.stack_id)` when the authenticated `ApiClient` is scoped to a single stack. Since `check_permissions!` only validates the `read:stack` permission string and never checks `stack_id`, a valid API token created for stack A can be used to fetch `ccmenu.xml` (deploy status, running state, last deploy id/timestamp) for any other stack B.

### Finding Description
The binding that should hold is: `current_api_client.stack_id == resolved_stack.id` whenever `current_api_client.stack_id?` is true (i.e., the client is scoped to one stack). `Shipit::Api::BaseController#stacks` enforces exactly this: [1](#0-0) 

But `CCMenuController` overrides `#stack` and never calls `stacks`: [2](#0-1) 

Authentication for this controller is also overridden to accept `params[:token]` in addition to BasicAuth, but this only changes how the token is read, not how the resulting `ApiClient` is scoped: [3](#0-2) 

`ApiClient.authenticate` simply verifies the signature and loads the record by id; it performs no stack-scope check: [4](#0-3) 

`check_permissions!` (invoked via `require_permission :read, :stack`) only checks that the permission string `read:stack` is present in `permissions`; it has no knowledge of `params[:stack_id]` or `current_api_client.stack_id`: [5](#0-4) [6](#0-5) 

Exploit flow: an attacker who legitimately holds an `ApiClient` token scoped to stack A (`stack_id = A`, e.g. one they created for their own project through `ApiClientsController`, or one leaked in a CI log/README) sends `GET /stacks/B/ccmenu.xml?token=<token-for-A>` where `B` is any other stack id/slug in the same Shipit instance. `authenticate_api_client` loads the `ApiClient` (id A's client) successfully since the signature is valid for that client's own id — nothing about the request ties the token to stack B. `require_permission!(:read, :stack)` passes because the client has `read:stack` in its `permissions` array regardless of which stack it's nominally scoped to. `stack` then resolves `Stack.from_param!(params[:stack_id])` = stack B directly, with no `current_api_client.stack_id?` check, and `show` renders `stack B`'s latest deploy/rollback state in the CCMenu XML response.

Existing guards that would normally prevent cross-stack access (`stacks` scoping in `BaseController`) are simply not invoked on this code path because `CCMenuController` redefines `stack` from scratch instead of reusing the inherited scoped helper.

### Impact Explanation
An attacker holding any single-stack-scoped API token (their own, legitimately obtained) can enumerate/read CCMenu status (deploy id, running/ended state, timestamp) for every other stack on the Shipit instance, not just the one their token is scoped to. This is a cross-tenant unauthenticated-relative-to-target-stack read of deploy state, matching the "unauthenticated read of stack state" High-impact category, since from the perspective of stack B, the requester is never authorized for B. It is fully repeatable against arbitrary stack ids/slugs known to the attacker (stack slugs are often guessable/public in repo names).

### Likelihood Explanation
Preconditions: the attacker needs any valid `ApiClient` token scoped to `read:stack` for at least one stack — this is a low bar since `ApiClientsController` (or an operator granting a scoped token to an external integration, e.g., a CI dashboard) can produce such a token without granting access to other stacks. No `api_clients_secret`, session, or GitHub credentials are needed beyond the one token already possessed. The request is a single unauthenticated `GET` with a query parameter; it's trivially repeatable and scriptable across every stack id in the instance.

### Recommendation
Change `CCMenuController#stack` to use the inherited scoped `stacks` helper (`stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])` directly, so that `current_api_client.stack_id?` scoping from `BaseController` is enforced consistently on this controller as well.

### Proof of Concept
Minitest plan (`test/controllers/api/ccmenu_controller_test.rb` or similar, illustrative — not to be placed under out-of-scope `test/**` for the fix, but demonstrating the bug):
1. Create `stack_a = shipit_stacks(:shipit)` and `stack_b` a second distinct stack fixture.
2. Create `api_client = ApiClient.create!(creator: ..., name: 'scoped', stack: stack_a, permissions: ['read:stack'])`.
3. Assert binding before: `api_client.stack_id == stack_a.id` and `api_client.stack_id != stack_b.id`.
4. `get "/stacks/#{stack_b.to_param}/ccmenu.xml", params: { token: api_client.authentication_token }`.
5. Assert `response.status == 200` (not 401/403).
6. Parse the XML body and assert the `<Project>` node corresponds to `stack_b` (e.g., matches `stack_b`'s latest deploy id/ended_at), proving the token issued for `stack_a` disclosed `stack_b`'s deploy state — i.e., after the request the effective binding is `requested_stack (B) != current_api_client.stack (A)` yet data for B was returned, confirming the equality is violated.
