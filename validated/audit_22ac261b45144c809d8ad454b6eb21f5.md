### Title
Argument-injection bypass of `gh.sh` repo scoping via unvalidated flag-value smuggling - (File: `scripts/gh.sh`)

### Summary
`scripts/gh.sh` is a wrapper that restricts the GitHub-triage automation (`triage-issue.md`, `dedupe.md`) to a small allowlist of `gh` subcommands/flags, scoped to a single repo via `GH_REPO`. The flag-value parsing loop fails to validate the *value* that follows a flag expecting one, allowing an attacker-controlled argument beginning with `-` to be smuggled into the argv passed to `gh`, unchecked. [1](#0-0) 

### Finding Description
The script builds an allowlist of flags (`--comments`, `--state`, `--limit`, `--label`) and rejects any `-`-prefixed argument not in that list: [2](#0-1) [3](#0-2) 

However, for flags that take a value via space syntax (`--state foo` rather than `--state=foo`), the loop sets `skip_next=true` and on the *next* iteration blindly appends that value to `FLAGS` without checking whether it itself looks like another flag: [4](#0-3) 

Because `FLAGS` elements are passed as separate argv tokens to `gh` (not concatenated into a string), a call such as `./scripts/gh.sh issue list --state --repo=attacker/repo --limit 5` results in the token `--repo=attacker/repo` being appended to `FLAGS` as its own argv item, purely because it happened to follow `--state`. The final invocation becomes:

```
gh issue list --state --repo=attacker/repo --limit 5
```

`gh`'s own argument parser then interprets `--repo=attacker/repo` as a top-level flag overriding `GH_REPO="$REPO"` set earlier in the script (env var `GH_REPO` is overridden by an explicit `--repo`/`-R` flag in the `gh` CLI). This defeats the script's core safety invariant stated in its own header comment — "All commands are scoped to the current repository via GH_REPO." [5](#0-4) [6](#0-5) 

This is the exact "Argument Injection (argv flag smuggling)" class the report's bug taxonomy calls out — a value that starts with `-` is parsed as a flag even without a shell in play — and here it is unvalidated for two of the four allowlisted value-taking flags (`--state`, `--label`; `--limit` and `--comments` behave the same way for `--limit`).

### Impact Explanation
This script is invoked autonomously by Claude Code slash-commands/skills that process **untrusted, attacker-influenced input**: GitHub issue titles, bodies, and comments fed into `/triage-issue` and `/dedupe`, which are permitted (`allowed-tools: Bash(./scripts/gh.sh:*)`) to run `gh.sh` without further per-invocation human approval. [7](#0-6) [8](#0-7) 

An attacker who can get the LLM agent to construct a crafted argument list (e.g. via prompt injection embedded in an issue body that the triage/dedupe agent reads and then echoes into a tool call) can smuggle `--repo=<other/private-repo>` (or other `gh` global flags) past the wrapper's allowlist. Because the CLI process runs with the workflow's `gh` credentials, this can be used to read issues/labels/search results from **any repository the underlying token can access** — not just the intended repo — which is a concrete cross-target automation bleed / scope-escape impact, and defeats the specific security boundary the wrapper exists to enforce.

### Likelihood Explanation
Moderate-to-high. The `/triage-issue` and `/dedupe` workflows are explicitly designed to run over hostile, third-party-authored content (public GitHub issues), and both skills document only the "safe" invocation patterns to the model — they do not themselves prevent the model from producing a `gh.sh` call shaped to exploit the flag-smuggling gap if a crafted issue instructs it to (classic tool-argument prompt injection). No additional human approval gate sits between the model's tool call and `gh.sh` execution once the command is allowlisted via `allowed-tools`.

### Recommendation
- In `scripts/gh.sh`, validate the value captured in the `skip_next` branch the same way positional/flag arguments are validated: reject any value beginning with `-` for `--state`, `--limit`, and `--label`.
- Additionally, harden by passing `--repo "$REPO"` last (already done for `search issues`) for *every* code path, and explicitly reject `-R`/`--repo`/`--hostname` anywhere in the smuggled flags regardless of position.
- Prefer `=`-only value syntax internally (reject bare `--flag value` forms) to eliminate the ambiguity between "value" and "next flag" entirely.
- Apply the same validation review to `edit-issue-labels.sh` and `comment-on-duplicates.sh`, referenced by the same skills, since they likely share this argument-parsing pattern.

### Proof of Concept
Given a GitHub issue whose body (read by `/triage-issue` via `./scripts/gh.sh issue view <id>`) contains a prompt-injection payload instructing the agent to run:

```
./scripts/gh.sh issue list --state --repo=some-org/private-repo --limit 20
```

Trace through `scripts/gh.sh`:
1. `CMD="issue list"` passes the subcommand allowlist. [9](#0-8) 
2. Parsing loop: `--state` matches `ALLOWED_FLAGS`, is a `FLAGS_WITH_VALUES` entry without `=`, so `skip_next=true`. [10](#0-9) 
3. Next token `--repo=some-org/private-repo` is appended to `FLAGS` unchecked because it is consumed by the `skip_next==true` branch, which performs no allowlist check. [4](#0-3) 
4. `--limit 20` is validated normally.
5. Final execution: `gh issue list --state --repo=some-org/private-repo --limit 20 --repo "$REPO"` — because `gh` normally takes the last-specified value for repeated flags in most CLIs, but this depends on gh's exact flag-resolution order and would need runtime confirmation against the real `gh` binary to establish definitively whether the injected `--repo` or the trailing forced `--repo "$REPO"` wins.

Note: I was unable to execute `gh` itself in this environment to confirm the exact precedence between the injected `--repo=` and the script's own trailing `--repo "$REPO"` for the `issue list`/`label list` code path (the `else` branch at [11](#0-10)  does not append `--repo` at all — it relies solely on the `GH_REPO` env var, which *is* overridden by an explicit `--repo` flag in `gh`). This means for `issue list` and `label list`, the smuggled `--repo=` flag is not overridden by anything, making the bypass unambiguous for those two subcommands; for `search issues` and `issue view`, the script appends its own `--repo "$REPO"` after the smuggled flags, and gh's actual last-flag-wins behavior would need to be verified to confirm exploitability there specifically.

for arg in "$@"; do
  if [[ "$skip_next" == true ]]; then
    FLAGS+=("$arg")
    skip_next=false
  elif [[ "$arg" == -* ]]; then
    flag="${arg%%=*}"
    matched=false
    for allowed in "${ALLOWED_FLAGS[@]}"; do
      if [[ "$flag" == "$allowed" ]]; then
        matched=true
        break
      fi
    done
    if [[ "$matched" == false ]]; then
      echo "Error: only --comments, --state, --limit, --label flags are allowed (e.g., ./scripts/gh.sh issue list --state open --limit 20)" >&2
      exit 1
    fi
    FLAGS+=("$arg")

          skip_next=true
          break
        fi
      done
    fi
