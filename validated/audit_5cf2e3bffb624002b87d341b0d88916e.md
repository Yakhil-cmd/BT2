### Title
Attacker-controlled PR label names silently override trusted `Stack#env` keys (`GITHUB_REPO_OWNER`, `DEPLOY_URL`, etc.) in `ReviewStack#env` - ([File: app/models/shipit/review_stack.rb])

### Summary
`ReviewStack#env` merges the trusted environment produced by `Stack#env` with a hash built from the pull request's labels, with the label-derived hash taking precedence in the `merge`. Because an unprivileged PR author fully controls their PR's labels via a webhook-driven update path, they can add a label whose upcased name collides with a reserved variable name (e.g. `github_repo_owner`, `deploy_url`) and force that variable's value to the literal string `"true"` for their own deploy commands.

### Finding Description
The broken binding is: `review_stack.env['GITHUB_REPO_OWNER']` should always equal `review_stack.repository.owner` (the value produced by `Stack#env`), but with a label named `github_repo_owner` attached to the PR, it instead equals `"true"`.

The code path is:
```ruby
def env
  return super unless pull_request.present?

  super
    .merge(
      pull_request
        .labels
        .each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" }
    )
end
``` [1](#0-0) 

`super` returns `Stack#env`, which is known (per README/tests) to include reserved keys such as `ENVIRONMENT`, `LAST_DEPLOYED_SHA`, `GITHUB_REPO_OWNER`, `GITHUB_REPO_NAME`, `DEPLOY_URL`, and `BRANCH`. Ruby's `Hash#merge` gives precedence to the argument hash, so any label whose upcased name matches one of these reserved keys overwrites the trusted value with the string `"true"`.

The label list is attacker-controlled: `PullRequest#labels` is updated directly from the raw GitHub webhook payload without any allow-list filtering:
```ruby
def capture_labels
  return unless pull_request = stack.pull_request
  pull_request.update!(labels: params.pull_request.labels.map(&:name))
end
``` [2](#0-1) 

Exploit flow: an attacker opens a PR against a repo with review stacks enabled, adds a label named `github_repo_owner` (or `deploy_url`) to their own PR (labels are freely settable by anyone who can open/edit a PR they own, and GitHub's `pull_request` `labeled` webhook fires for repository-scoped events without requiring maintainer status on the label itself in many configurations), which flows through `LabelCapturingHandler#process` → `PullRequest#update!(labels: ...)`. When a deploy task subsequently runs, `TaskCommands#env` calls `@stack.env`, which for a `ReviewStack` is this overridden hash, and `Command#interpolate_environment_variables` substitutes `$GITHUB_REPO_OWNER` with `Shellwords.escape('true')` instead of the actual repository owner from the verified webhook payload used elsewhere in `Stack`. [3](#0-2) [4](#0-3) 

None of the existing guards prevent this: `EnvironmentVariables#permit` allow-lists per-task variables but is not applied to the base `Stack#env`/`ReviewStack#env` hash before it reaches `Command#interpolate_environment_variables`; `ExplicitParameters` in `LabelCapturingHandler` validates the shape of the payload but not the content of label names; there is no sanitization step rejecting labels that collide with reserved environment variable names.

### Impact Explanation
An unprivileged PR author can change the value of any variable in a shell command that a deploy/rollback step interpolates via `$VARNAME`, for a repository they can open PRs against (their own fork/branch, on a repo where review stacks are enabled). This can corrupt arguments used to build git/API URLs or other command arguments in deploy steps (e.g., `cap $ENVIRONMENT deploy`, custom scripts referencing `$GITHUB_REPO_OWNER`/`$DEPLOY_URL`), executed on the deploy host. This is scoped to the attacker's own review stack/PR (not cross-tenant across unrelated repos), but it does let an unprivileged contributor manipulate command arguments that a legitimate deploy pipeline assumes come from trusted webhook data, which affects the integrity of what actually runs on the deploy host for that review stack.

### Likelihood Explanation
Preconditions: review stacks must be enabled for the target repository, and a `deploy`/`task` step must reference one of the reserved env var names (e.g., `$GITHUB_REPO_OWNER`, `$DEPLOY_URL`) via string interpolation. The attacker's cost is trivial — open a PR, add a label with the matching name, wait for the `labeled` webhook to be processed. This is fully repeatable and requires no secrets or elevated Shipit role, only the ability to add labels to a PR that triggers this stack's review workflow.

### Recommendation
In `ReviewStack#env`, do not allow label-derived keys to override reserved/system environment variables. Either merge in the opposite order (`labels.merge(super)`) so trusted `Stack#env` values always win, or explicitly filter out any label name that collides with a reserved key set (`ENVIRONMENT`, `LAST_DEPLOYED_SHA`, `GITHUB_REPO_OWNER`, `GITHUB_REPO_NAME`, `DEPLOY_URL`, `BRANCH`, etc.) before merging.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_test.rb
test "#env does not allow PR labels to override reserved stack env vars" do
  review_stack = shipit_review_stacks(:review_stack) # fixture with a pull_request
  review_stack.pull_request.update!(labels: ['github_repo_owner'])

  assert_equal review_stack.repository.owner, review_stack.env['GITHUB_REPO_OWNER']
  refute_equal 'true', review_stack.env['GITHUB_REPO_OWNER']
end
```
This asserts the binding `review_stack.env['GITHUB_REPO_OWNER'] == review_stack.repository.owner` holds even when an attacker-controlled label named `github_repo_owner` is present, which currently fails against the code at [1](#0-0) .
