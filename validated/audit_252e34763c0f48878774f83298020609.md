### Title
CCMenu token minted with `stack_id: nil` grants read access to every stack via `Api::CCMenuController#stack` bypassing scoping - (File: app/controllers/shipit/ccmenu_url_controller.rb)

### Summary
`CCMenuUrlController#fetch` mints an `ApiClient` ("CCMenu Client") without binding it to the requested stack (`stack: stack` is never passed to `create_with`), so the token's `stack_id` is `nil`. Combined with `Api::CCMenuController` overriding `stack` to call `Stack.from_param!(params[:stack_id])` directly instead of the scoped `stacks.from_param!`, any URL bearing this token authorizes reading **any** stack, not just the one whose `stack_id` appears in the path.

### Finding Description
The intended binding should be: `token.stack_id == stack.id` for the stack the CCMenu URL was generated for, and `Api::CCMenuController#show` should only ever resolve `params[:stack_id]` within `token`'s authorized stack set.

Tracing the code:
- `app/controllers/shipit/ccmenu_url_controller.rb:15-18`: `client = ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')`. This client is keyed only by `creator` + fixed `name`, and never sets `stack:`, so `ApiClient#stack_id` is `nil`. [1](#0-0) 
- `app/controllers/shipit/api/base_controller.rb:74-76`: the generic scoping helper `stacks` would restrict to `Stack.where(id: current_api_client.stack_id)` if `stack_id` were set, else falls back to `Stack.all`. [2](#0-1) 
- `app/controllers/shipit/api/ccmenu_controller.rb:29-31`: `Api::CCMenuController` doesn't even use the `stacks` scoping helper - it overrides `stack` to call `Stack.from_param!(params[:stack_id])` on the unscoped `Stack` relation directly, so scoping is bypassed regardless of `stack_id` on the token. [3](#0-2) 

Because the token is (a) never bound to a specific stack at mint time, and (b) even if it were, `Api::CCMenuController` ignores the scoping helper entirely, the only check performed is `require_permission :read, :stack`, which merely checks that the token carries the `read:stack` permission string - it says nothing about *which* stack. [4](#0-3) 

Attack: an operator generates a CCMenu URL for stack A via `GET /stacks/.../ccmenu_url` (or equivalent), pastes it into a public CI dashboard or shared Slack channel. The attacker copies the URL, replaces the `stack_id` path segment with stack B's identifier, keeping the same `token` query parameter, and requests `Api::CCMenuController#show` for stack B. Since the token's `stack_id` is `nil` and `Api::CCMenuController#stack` bypasses the `stacks` scoping helper anyway, the request succeeds and returns stack B's build/deploy status XML.

Existing guards (`require_permission!`, `check_permissions!`) only validate the permission string on the token, not stack scope, so they do not prevent this divergence. [5](#0-4) 

### Impact Explanation
An attacker who obtains any previously-generated CCMenu URL (which are commonly pasted into public CI status pages, Slack, or badges since that's their intended use) can substitute the `stack_id` in the path to read the deploy/build status (`name`, `activity`, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`) of any other stack on the Shipit instance, including private/internal repositories the attacker has no access to. This is repeatable indefinitely (the token doesn't expire) and applies across all stacks/tenants hosted on the instance, matching the "unauthenticated read of stack state" High-severity category (the attacker never needed a Shipit session or a legitimately-scoped API client - only a leaked/observed token intended for one stack).

### Likelihood Explanation
Preconditions: (1) `fetch` must have been invoked at least once by any legitimate user for any stack, minting a `read:stack`, `stack_id: nil` "CCMenu Client" token; (2) the attacker must obtain that URL, which is trivial since CCMenu URLs are explicitly designed to be embedded in public CI status tools/badges/dashboards. No Shipit secrets, sessions, or elevated privileges are required - only observing one publicly-shared URL and editing a path segment. This is a straightforward, cheap, and repeatable exploit against any Shipit deployment that uses the CCMenu integration feature.

### Recommendation
- Bind the minted `ApiClient` to the specific stack: `ApiClient.create_with(permissions: %w[read:stack], stack: stack).find_or_create_by!(creator: current_user, stack: stack, name: 'CCMenu Client')` (include `stack` in both the `create_with` attributes and the `find_or_create_by!` lookup key so distinct stacks get distinct tokens).
- Fix `Api::CCMenuController#stack` to use the scoped `stacks.from_param!(params[:stack_id])` helper from `BaseController` instead of calling `Stack.from_param!` directly, so a `stack_id`-bound token cannot be used against another stack.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb (new test)
test "a ccmenu token minted for stack A cannot read stack B" do
  stack_a = shipit_stacks(:shipit)
  stack_b = Stack.create!(repository: Repository.new(owner: "foo", name: "bar"), branch: 'main')

  # Mint token the same way CCMenuUrlController#fetch does
  client = ApiClient.create_with(permissions: %w[read:stack])
                     .find_or_create_by!(creator: shipit_users(:walrus), name: 'CCMenu Client')

  assert_nil client.stack_id # binding is broken: token.stack_id == stack_a.id does NOT hold

  get :show, params: { stack_id: stack_b.to_param, token: client.authentication_token }

  # Vulnerable behavior: succeeds and leaks stack_b data
  assert_response :ok
  assert_payload 'name', stack_b.to_param
end
```
This demonstrates the equality `token.stack_id == stack_a.id` fails to hold (it's `nil`), and despite that, the token still authorizes reading `stack_b`, proving the cross-stack read.
