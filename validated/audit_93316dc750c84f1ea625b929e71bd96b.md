### Title
Cross-tenant status forgery via global `Commit.where(sha:)` lookup enabling unauthorized merges - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` only checks that the incoming `status` webhook is signed with the `webhook_secret` of the *organization named in the payload* (`Shipit.github(organization: repository_owner)`), but `StatusHandler#process` and `Commit#create_status_from_github!` never re-check that the resolved `Commit` (looked up globally by `sha` across **all** stacks) actually belongs to that organization/repository. This lets any Shipit tenant whose org is legitimately configured with a `webhook_secret` write a `Status` (and flip `MergeRequest#all_status_checks_passed?`) for a completely unrelated stack, provided they can produce a commit object with an identical SHA (trivial via cherry-picking/copying the exact commit content into their own repo).

### Finding Description
Broken binding: `stack_id` written by `Status.replicate_from_github!` (app/models/shipit/status.rb:24-33) is expected to equal the `stack_id` of the repository whose `webhook_secret` authenticated the request, but it does not.

Trace:
1. `WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-30) resolves `github_app = Shipit.github(organization: repository_owner)` where `repository_owner` is read straight from the untrusted payload (`params.dig('repository','owner','login')`, webhooks_controller.rb:59-62), and verifies the raw body against **that org's** `webhook_secret` (`lib/shipit/github_app.rb:76-83`). This only proves the request was signed by *some org configured in Shipit*, not that it corresponds to the commit/stack that will actually be mutated. [1](#0-0) [2](#0-1) 
2. Once verified, `Shipit::Webhooks.for_event('status')` routes to `StatusHandler#process`, which resolves target commits with **no repository scoping whatsoever**:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 
3. `Commit#create_status_from_github!` writes the status using `stack_id` taken from the found commit's own `commit.stack_id`, not from the org that signed the request:
```ruby
def create_status_from_github!(github_status)
  add_status do
    statuses.replicate_from_github!(stack_id, github_status)
  end
end
``` [4](#0-3) 
4. `Status.replicate_from_github!` persists the row with that `stack_id` directly. [5](#0-4) 
5. `add_status` schedules `stack.schedule_merges` when the new status is `pending`/`success`. [6](#0-5) 
6. `MergeRequest#all_status_checks_passed?` evaluates purely from `head.statuses_and_check_runs`, so an injected success `Status` for the victim commit flips this to true. [7](#0-6) 
7. `MergeRequest#merge!` then proceeds using `stack.github_api` (which is the *victim's* GitHub App, `Stack#github_app` = `Shipit.github(organization: repository.owner)`), calling `merge_pull_request` on the victim's repo. [8](#0-7) [9](#0-8) 

Attacker's exact request: a legitimate operator/admin of some org `AttackerOrg` that Shipit has configured (`Shipit.github(organization: 'AttackerOrg')`) — and who therefore knows `AttackerOrg`'s `webhook_secret` — reproduces (via cherry-pick, or simply pushing an object with identical tree/parent/author/committer/timestamp fields) a commit whose SHA equals `MergeRequest#head.sha` of a target `Stack` belonging to a totally unrelated org `VictimOrg`. They POST to `/webhooks` with `X-Github-Event: status`, `repository.owner.login = "AttackerOrg"`, a valid `X-Hub-Signature` computed with `AttackerOrg`'s secret, and body `{"sha": "<colliding sha>", "state": "success", ...}`. `verify_signature` passes (it only checks `AttackerOrg`'s secret matches, which it does). `StatusHandler#process` then finds the victim's `Commit` by the colliding SHA (global, unscoped `Commit.where(sha:)`) and writes a `success` `Status` under the **victim's** `stack_id`, independent of which org authenticated the request.

Why existing guards fail: `verify_signature` authenticates "an org configured in Shipit sent this", not "the org that owns the commit being modified sent this." `drop_unhandled_event`, `ExplicitParameters` schema (`requires :sha, String`) and model validations do not check repository ownership of the found `Commit` against the authenticated `repository_owner`. There is no code anywhere in `StatusHandler`, `Commit#create_status_from_github!`, or `Status.replicate_from_github!` that cross-checks `commit.stack.repository.full_name` against the webhook payload's `repository.full_name`.

### Impact Explanation
A payload authenticated for one tenant's repository (`AttackerOrg`) mutates another tenant's (`VictimOrg`) `Stack`/`Commit`/`MergeRequest` state, directly matching the Critical category "a payload for one repository mutating another's stack, commit, task or team" and "an unauthorized... merge." The forged `Status` can flip `MergeRequest#all_status_checks_passed?` to true and trigger `stack.schedule_merges`, culminating in `MergeRequest#merge!` calling `stack.github_api.merge_pull_request` on the victim repository — an unauthorized merge executed using the victim's own installed GitHub App credentials. This is repeatable against any stack/commit as long as an identical-SHA commit object can be produced (trivial for public commits/PRs, since git SHAs are content-addressed and independent of the hosting repository). Blast radius spans the whole multi-tenant Shipit instance: any onboarded org can attack any other onboarded org's stacks.

### Likelihood Explanation
Preconditions: (1) Shipit is running in the documented multi-org configuration (`docs/setup.md` "Using Multiple Github Applications") with per-org `webhook_secret`s, (2) attacker legitimately administers/owns at least one org/repo already onboarded onto the same Shipit instance (so they know that org's real `webhook_secret`, as is normal for any org admin setting up their own GitHub App/webhook), (3) attacker can produce a byte-identical commit object (same tree, parent, author/committer identities and timestamps) reachable from their own repository — achievable via cherry-pick of a public commit or copying commit metadata, since SHA-1 commit hashes are computed purely from content, not repository identity. Given these are realistic and low-cost preconditions for a multi-tenant Shipit deployment, likelihood is high; the exploit is a single crafted HTTP POST, fully repeatable.

### Recommendation
Scope status handling by repository, not just by SHA: in `StatusHandler#process`, filter `Commit.where(sha: params.sha)` down to commits whose `commit.stack.repository.full_name` (and/or `owner`) matches the `repository.full_name`/`repository.owner.login` from the verified webhook payload before calling `create_status_from_github!`. Equivalently, pass the authenticated `repository_owner`/`full_name` into `create_status_from_github!` and assert it matches `commit.stack.repository.full_name` before writing the `Status`, raising/skipping otherwise.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` style, no live GitHub):
```ruby
test "status webhook signed for one repo must not write status for a commit in another stack" do
  attacker_stack = shipit_stacks(:shipit)          # repository owner: 'shopify' (or whatever fixture org)
  victim_stack   = shipit_stacks(:cyclimse)        # different repository/org
  victim_commit  = shipit_commits(:cyclimse_first) # belongs to victim_stack

  # Simulate SHA collision: attacker reproduces the victim's exact commit sha in their own repo context.
  colliding_sha = victim_commit.sha

  body = {
    'sha' => colliding_sha,
    'state' => 'success',
    'context' => 'ci/attacker',
    'branches' => [{ 'name' => attacker_stack.branch }],
    'repository' => { 'owner' => { 'login' => attacker_stack.repository.owner } } # attacker's own org
  }.to_json

  @request.headers['X-Github-Event'] = 'status'
  GithubHook.any_instance.stubs(:verify_signature).returns(true) # attacker legitimately signs with THEIR org's secret

  assert_difference -> { victim_commit.statuses.count }, 1 do
    post :create, body:, as: :json
  end

  status = victim_commit.statuses.last
  # Binding check: the status stack_id equals the victim's stack, NOT the org that signed the request
  assert_equal victim_stack.id, status.stack_id
  refute_equal attacker_stack.id, status.stack_id

  merge_request = shipit_merge_requests(:cyclimse_pending) # head == victim_commit
  assert merge_request.all_status_checks_passed?, "attacker-signed status for another org flipped victim's merge gate"

  # Optionally assert stack.github_api.merge_pull_request would be invoked for the victim's repo
  Stack.any_instance.expects(:github_api).at_least_once
  merge_request.merge!
end
```
This demonstrates: (a) a webhook signed for `attacker_stack`'s org passes `verify_signature`, (b) `Status.replicate_from_github!` writes `stack_id == victim_stack.id`, violating the intended binding, and (c) `all_status_checks_passed?`/`merge!` on the victim's `MergeRequest` proceed as a direct consequence.

        # branch was already deleted somehow
      end
      complete!
      true
    rescue Octokit::MethodNotAllowed # merge conflict
      reject!('merge_conflict')
      false
    rescue Octokit::Conflict # shas didn't match, PR was updated.
      raise NotReady
    end
