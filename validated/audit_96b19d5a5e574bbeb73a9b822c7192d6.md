### Title
Webhook stack-resolution uses unverified `repository.full_name` while signature authentication keys on `repository.owner.login` — cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification based on `repository.owner.login` (or `organization.login`) taken directly from the unauthenticated request body, then, once "verified," hands the *entire* raw payload to event handlers that resolve the target `Stack`/`Repository` using a *different* field, `repository.full_name`. Because these two fields are never cross-checked against each other, a payload can be signed with the secret belonging to one organization while acting on a repository owned by a completely different organization.

### Finding Description
The controller picks the verification key like this: [1](#0-0) 

`repository_owner` is read straight out of attacker-controlled JSON: [2](#0-1) 

Once `verify_webhook_signature(signature, request.raw_post)` passes (using `Shipit.github(organization: repository_owner)`'s `webhook_secret`), the raw, unfiltered payload is dispatched to every registered handler: [3](#0-2) 

Every handler, however, resolves the affected repository/stack independently, from `repository.full_name`, not from `repository.owner.login`: [4](#0-3) 

`Repository.from_github_repo_name` simply splits `owner/name` out of that field and looks the record up with no relation back to whichever organization's secret validated the signature: [5](#0-4) 

The same pattern repeats in every pull-request handler (`opened_handler.rb`, `labeled_handler.rb`, `unlabeled_handler.rb`, `reopened_handler.rb`, `assigned_handler.rb`, `label_capturing_handler.rb`), all of which derive `repository` from `params.repository.full_name` alone: [6](#0-5) 

Nothing in `verify_signature` or in any handler asserts that the organization named by `repository.owner.login` (the value used to pick the HMAC secret) equals the owner encoded in `repository.full_name` (the value used to locate and mutate state). Because Shipit is multi-tenant — a single instance can host many organizations, each configured with its own `webhook_secret` under `Shipit.github(organization: X)` — an attacker who is a legitimate admin of *their own* configured organization (and therefore knows *their own* `webhook_secret`, since they set up or can read their own org's webhook secret/App config) can craft a payload where `repository.owner.login` = their own org (so the signature they compute validates) but `repository.full_name` = `victim-org/victim-repo`.

The binding that should hold is:
`organization authenticated via HMAC(repository.owner.login secret) == organization owning repository.full_name acted upon by handlers`

This equality is never checked, so the two can diverge under attacker control.

### Impact Explanation
This breaks the trust boundary between "which organization's secret authenticated this webhook" and "which repository's state gets mutated." Concretely, an attacker with only legitimate access to their own configured GitHub organization on the same Shipit instance can:
- Forge `push` events for a victim repository, invoking `stack.sync_github(expected_head_sha:)` on stacks they do not own [7](#0-6) , which can influence undeployed-commit tracking and, for stacks with `continuous_deployment` enabled, downstream automatic deploy scheduling.
- Forge `pull_request` events to archive/unarchive victim review stacks or capture/alter labels on a repository they don't control, since `archive!`/`unarchive!` are invoked purely from the attacker-chosen `repository.full_name` [8](#0-7) .

This is a cross-repository write performed without the victim organization's own webhook secret, i.e. an authentication-binding bypass, matching the "cross-repository writes" / "unauthorized deploy" impact category.

### Likelihood Explanation
Requires only that the attacker administers (or can obtain the webhook secret for) at least one organization already onboarded to the same Shipit instance — a realistic scenario for a shared/multi-tenant Shipit deployment. No repository write access, GitHub App private key, or Shipit session/API token is needed; the attacker only crafts and POSTs a JSON body with a valid HMAC using their own known secret.

### Recommendation
Bind the authenticated organization to the acted-upon repository: after `verify_webhook_signature` succeeds, require that `repository.owner.login` (or `organization.login`) used for verification matches the owner encoded in `repository.full_name` before dispatching to handlers, rejecting the request (422) otherwise. Alternatively, have handlers resolve the target repository/stack using the same organization value that was authenticated, rather than trusting `full_name` independently.

### Proof of Concept
1. Shipit instance configured with two organizations: `attacker-org` (attacker is admin, knows `webhook_secret_A`) and `victim-org` (hosts a real Shipit stack, secret unknown to attacker).
2. Attacker builds a JSON body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>"
}
```
3. Attacker computes `sha1=HMAC(webhook_secret_A, raw_body)` and sets `X-Hub-Signature` accordingly, `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")` (from `repository.owner.login`), verifies successfully against `webhook_secret_A`.
5. `PushHandler#stacks` resolves via `Repository.from_github_repo_name("victim-org/victim-repo")`, and `stack.sync_github(expected_head_sha:)` is invoked on the victim's stack — a mutation performed on `victim-org`'s data despite being authenticated only against `attacker-org`'s secret.
