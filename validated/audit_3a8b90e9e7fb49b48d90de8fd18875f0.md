### Title
Webhook signature validated against an organization derived from the payload, while `StatusHandler` writes commit status globally by `sha` with no repository check, allowing cross-stack CI-status forgery and unauthorized deploy - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub organization's `webhook_secret` to validate the HMAC signature against by reading `repository.owner.login` (or `organization.login`) *out of the very payload being verified*, and the signature check is a no-op when that organization has no `webhook_secret` configured. `StatusHandler#process`, however, applies the status update by matching `Commit.where(sha: params.sha)` across the **entire Shipit instance**, with no check that the commit's repository matches the organization that signed the request. This breaks the binding "organization that authenticated == repository being written to."

### Finding Description
`WebhooksController#verify_signature` does: [1](#0-0) 
using `repository_owner`, itself taken straight from the untrusted JSON body: [2](#0-1) 

The GitHub App/organization lookup and signature check live in `lib/shipit/github_app.rb`: [3](#0-2) 
Note `return true unless webhook_secret` — if any configured organization in a multi-org Shipit deployment has no `webhook_secret` set (the documented example configs ship with `webhook_secret: # nil`), signature verification is fully bypassed for any payload whose `repository.owner.login`/`organization.login` names that organization.

Once past `verify_signature`, `WebhooksController#create` dispatches the full attacker-controlled payload to handlers: [4](#0-3) 

`StatusHandler`, unlike `PushHandler` (which scopes to `stacks` derived from `repository.full_name`), never uses the repository field at all: [5](#0-4) 

It looks up commits purely by `sha`, which is a value an attacker can freely choose to match any commit hash present in any stack tracked by the Shipit instance (SHAs are public GitHub data, easily discoverable), and then calls `commit.create_status_from_github!(params)`, which creates a `Status` record and triggers downstream side effects: [6](#0-5) 
including `schedule_continuous_delivery`, which is the trigger point for continuous-deployment automation.

The intended trust binding is: *the organization whose secret validated this webhook's signature is the same organization that owns the repository/commit being mutated by the webhook's contents.* Because (a) the org used for signature selection is read from the same untrusted payload it is meant to authenticate, and (b) `StatusHandler` performs no repository/stack scoping at all, that binding is not enforced. An attacker who can get one legitimately (or weakly/unsigned) validated `status` webhook accepted for *any* organization configured in the instance — e.g., an organization with `webhook_secret` unset, or one they have push/CI-integration access to for an unrelated, low-value repository — can set `sha` to a commit belonging to a completely different, sensitive stack and inject a forged `state: "success"` status for it.

### Impact Explanation
A forged "success" CI status on an arbitrary commit can move that commit into a deployable state and feed `schedule_continuous_delivery`/merge-queue processing (`ProcessMergeRequestsJob`), which can result in an unauthorized deploy or merge being triggered on a stack the attacker has no legitimate access to. This matches the "unauthorized deploy" impact category.

### Likelihood Explanation
Exploitation requires only the ability to have one `status` (or other unscoped handler) webhook accepted for some organization configured in the Shipit instance — this is materially easier than compromising the target stack's own organization, especially when `webhook_secret` is left unset for any configured org (a documented, apparently-supported configuration) or when the attacker legitimately controls an unrelated low-sensitivity repository/org onboarded to the same Shipit instance. No repository write access to the victim stack, no Shipit session, and no knowledge of `api_clients_secret`/`GITHUB_TOKEN` is required.

### Recommendation
- In `WebhooksController`, verify the signature using a secret that is not selected based on attacker-controlled payload content, or, at minimum, after verifying, cross-check that `repository.owner.login`/`organization.login` in the payload actually corresponds to the organization whose secret validated the request.
- In every handler (in particular `StatusHandler` and `CheckSuiteHandler`), scope the lookup to commits/stacks belonging to `payload.dig('repository','full_name')` (as `Handler#stacks`/`PushHandler` already do), rather than matching bare `sha` globally.
- Do not silently treat a missing `webhook_secret` as "signature verification passes"; require an explicit, secure secret per configured organization.

### Proof of Concept
1. Shipit is configured with two GitHub organizations, `low-value-org` (no `webhook_secret` configured, or an org the attacker has legitimate push/CI access to) and `victim-org` (the target, with a stack tracking commit `abcd123...`).
2. Attacker sends `POST /webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "abcd123...",           // real commit sha belonging to victim-org's stack
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "low-value-org" } }
}
```
3. `verify_signature` resolves `Shipit.github(organization: "low-value-org")` and either bypasses verification (`webhook_secret` unset) or validates using a secret the attacker can legitimately obtain deliveries signed with (e.g., a real GitHub webhook from their own low-value repo/org, replayed with the `sha`/`context` fields edited to target `victim-org`'s commit — because `low-value-org`'s secret still validly signs any body they can get GitHub to deliver, and nothing ties the signature to the specific commit/repo referenced inside).
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and finds the victim commit in `victim-org`'s stack, creating a forged `success` `Status`, potentially triggering continuous delivery/merge automation on `victim-org`'s stack.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
