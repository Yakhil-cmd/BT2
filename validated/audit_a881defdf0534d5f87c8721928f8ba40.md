### Title
Session Fixation on GitHub OAuth Callback — attacker-controlled session ID gets bound to victim's `User` on login (`GithubAuthenticationController#callback`) - ([File: app/controllers/shipit/github_authentication_controller.rb])

### Summary
The bug class reported for the L2 vault (an "always-writes-into-existing-state-without-re-validating-the-binding" flaw, in that case a rounding error that quietly corrupts an accounting relationship) maps in Shipit to a place where the engine writes a privileged identity into an existing, unverified piece of state: `GithubAuthenticationController#callback` binds a freshly-authenticated GitHub identity to whatever session ID the browser already carries, without invalidating/rotating that session first. This breaks the intended equality: `session_id ↔ authenticated User` should only ever be established for a session ID that the server (not the visitor) generated for that login flow.

### Finding Description
`GithubAuthenticationController#callback` is the terminus of the OmniAuth GitHub OAuth flow: [1](#0-0) 

```ruby
def callback
  return_url = request.env['omniauth.origin'] || root_path
  auth = request.env['omniauth.auth']
  return render('failed', layout: false) if auth.blank?
  session[:user_id] = sign_in_github(auth)
  session[:authenticated] = true
  redirect_to(return_url)
end
```

`sign_in_github` resolves/creates the `User` from GitHub's identity claims and stores the resulting `github_access_token`: [2](#0-1) 

Elsewhere in the engine, `session[:user_id]` is the sole binding used to resolve `current_user` for every privileged view/controller (stacks, deploys, api_clients, merge queue, etc.): [3](#0-2) 

Critically, `callback` never calls `reset_session` before assigning `session[:user_id]`. Rails' cookie-based session store (the default, see `test/dummy/config/initializers/session_store.rb`) keeps the same session id/cookie across the unauthenticated → authenticated transition unless the app explicitly regenerates it. Compare this to `logout`, which correctly calls `reset_session`: [4](#0-3) 

The only place `reset_session` is invoked on the authentication path is the *stale-credential* branch of `force_github_authentication`, not the login-success path itself: [5](#0-4) 

The trust binding that should hold is: **GitHub identity that completed OAuth == the session id minted specifically for that login**. Instead, the engine writes the resolved `User#id` into whatever session id the request already carries, which the requester (not the server) may have supplied before authentication ever began — i.e. a classic session-fixation gap.

### Impact Explanation
If an attacker can get a victim's browser to carry a session cookie/id chosen or known by the attacker (e.g., the attacker visits Shipit first to obtain a valid unauthenticated session cookie and gets it planted into the victim's browser through cookie-scoping tricks, a subdomain, or any mechanism that lets an unauthenticated visitor's session survive into the login step), and the victim then completes the real GitHub OAuth handshake in that same browser/session, `session[:user_id]` is written into the attacker-known session. The attacker can then present that same session cookie to fully impersonate the victim's Shipit session — reaching every stack/deploy/api-client page gated only by `session[:user_id]` — without ever knowing the victim's GitHub credentials. This is listed as a High-severity outcome ("session fixation / forced OAuth completion") because it escalates an unprivileged party into the victim's authenticated session and its associated `Shipit.github_teams` authorization, without needing an `ApiClient` token, webhook secret, or repository write access.

### Likelihood Explanation
The engine's own authentication concern demonstrates awareness that stale/compromised sessions need explicit invalidation (it calls `reset_session` for `requires_fresh_login?`), yet the primary sign-in transition — the moment identity is actually established — omits that call. This is a single, concrete, three-line gap in a control-flow that every Shipit deployment exercises (the whole app is `Shipit::Authentication`-gated). No exotic conditions are required beyond delivering a pre-existing session id into the victim's browser before OAuth completes, a well-known fixation technique that doesn't require credentials or GitHub App secrets.

### Recommendation
Call `reset_session` (or otherwise regenerate the session id) in `GithubAuthenticationController#callback` immediately before assigning `session[:user_id]`/`session[:authenticated]`, mirroring what is already done in `logout` and in the `requires_fresh_login?` branch of `force_github_authentication`. Regenerating the session identifier at the moment of privilege elevation (anonymous → authenticated) is the standard mitigation for session fixation.

### Proof of Concept
1. Attacker visits the Shipit instance unauthenticated and obtains a valid session cookie `S` (any endpoint that issues a Rails session cookie works, since sessions are created lazily).
2. Attacker causes the victim's browser to adopt cookie `S` for the Shipit host (e.g., via any cookie-planting vector available to the attacker — this only requires the ability to set a cookie, not to read one).
3. Victim, using the browser with cookie `S`, navigates to Shipit and completes the GitHub OAuth login flow.
4. `GithubAuthenticationController#callback` executes `session[:user_id] = sign_in_github(auth)` on the *existing* session `S` without rotating it — confirmed by the absence of any `reset_session` call in this method, contrasted with `logout` and the stale-login branch of `Shipit::Authentication#force_github_authentication`.
5. Attacker replays cookie `S` and is now recognized as the victim by `Shipit::Authentication#find_current_user` (`session[:user_id].present? && User.find_by(id: session[:user_id])`), gaining full access to the victim's stacks, deploys, and API client management pages.
