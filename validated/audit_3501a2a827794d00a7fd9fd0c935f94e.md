### Title
Missing Cosigner Authorization Check on `sign` Requests Enables Unauthorized Multisig Signing Requests - (File: wallet.js)

### Summary
In `ocore`'s device-message handler for the `sign` subject, the check that verifies the sender of a signing request is actually a legitimate cosigner of the target address has been explicitly disabled (commented out). This mirrors CVE-2025-53360's bug class: a management interface accepts privileged requests from any authenticated party instead of restricting them to authorized principals — here, any paired correspondent device can send a `sign` request for a locally-hosted multisig/multi-authored address, and `ocore` will process it (validating the unit and firing a signing prompt/auto-sign flow) without confirming the sender is one of the address's actual cosigners.

### Finding Description
`wallet.js`'s `handleMessageFromHub` handles the `"sign"` subject, used for both multisig (same address hosted on multiple devices) and multilateral signing flows. After validating the unit structure, it calls `findAddress(body.address, body.signing_path, {...})`. In the `ifLocal` callback — reached when the requested address is genuinely hosted on this device — the code explicitly skips validating that `from_address` (the device that sent the "sign" request) is actually registered as a cosigner for that wallet/address: [1](#0-0) 

The comment makes the intent explicit — "the commented check would make multilateral signing impossible" — but the removed query (`SELECT 1 FROM extended_pubkeys WHERE wallet=? AND device_address=?`) was the only mechanism that verified sender legitimacy before entering the unit validation / `signing_request` emission flow: [2](#0-1) 

By contrast, the `ifRemote` branch (proxying) does still perform the equivalent check (`other_device_addresses.includes(from_address)`), showing that the check is normally expected but was deliberately removed for the local-address code path: [3](#0-2) 

Since `from_address` is derived only from the device pubkey of any paired correspondent (`objectHash.getDeviceAddress(device_pubkey)`), and pairing with a device is a low-friction, attacker-initiatable action (`handlePairingMessage` in `device.js`), any correspondent device — not just a true cosigner of the target address — can submit crafted `sign` requests naming a victim's shared/multisig address and an arbitrary unsigned unit. This unit is passed to `network.handleOnlineJoint` for validation and then surfaces via the `signing_request` event, which downstream wallet/bot implementations (headless wallets, automated multisig signers) use to decide whether to co-sign. Because the underlying cosigner-membership check was removed, any consuming application relying on `ocore` to gate this step inherits the authorization gap.

### Impact Explanation
An unauthorized correspondent device can trigger co-signing flows for addresses it is not entitled to sign for. In deployments where the recipient device auto-processes/auto-signs `sign` requests for known local shared addresses (common in bot/headless multisig setups), this can lead to unauthorized transaction signing and potential unauthorized spending of shared-address funds, since the library-level authorization gate that should prevent non-cosigners from initiating signing on a hosted multisig address is missing.

### Likelihood Explanation
Pairing with a target device only requires knowledge of a pairing code/secret shared through normal correspondent-adding flows, and once paired, `from_address` is trusted as any correspondent for `"sign"` messages. No additional privilege beyond being a paired device is required to hit the vulnerable `ifLocal` path, making exploitation straightforward for any peer that becomes a correspondent of the victim device.

### Recommendation
Reinstate the cosigner-membership check in the `ifLocal` branch of the `"sign"` handler — verify that `from_address` is present among the recognized signers for the given `wallet`/`address` (e.g., via `extended_pubkeys`/`shared_address_signing_paths`) before proceeding to validate and surface the unit for signing, matching the equivalent check already present in the `ifRemote` branch.

### Proof of Concept
1. Attacker device pairs with the victim device as an ordinary correspondent (standard pairing flow).
2. Attacker crafts a `"sign"` device message referencing the victim's real shared/multisig `address` (learned from public unit history) and a `signing_path` valid for that address, embedding an `unsigned_unit` that spends the shared address's funds to an attacker-controlled address.
3. Victim's `ocore`-based node receives the message; `findAddress` resolves it to `ifLocal` since the address is hosted locally; the disabled check means no verification that the attacker is a listed cosigner occurs.
4. The crafted unit is validated and a `signing_request` event fires; on wallets/bots that automatically process such requests for recognized local addresses, this results in an unauthorized co-signature/transaction being produced without the requester ever having been an authorized signer.
