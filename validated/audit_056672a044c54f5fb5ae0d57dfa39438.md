### Title
Hookify `PreToolUse`/`PostToolUse` block rules keyed on `old_text` are silently bypassed by using `MultiEdit` instead of `Edit` - (File: `plugins/hookify/core/rule_engine.py`)

### Summary
The hookify plugin's rule engine gates dangerous file-edit operations by matching regex/string conditions against fields extracted from the tool call (`file_path`, `new_text`, `old_text`, `content`). `_extract_field` in `rule_engine.py` only wires up `old_text`/`old_string` extraction for the `Write`/`Edit` tool branch and never implements it for `MultiEdit`, so any rule that gates on `old_text` (e.g. "block removal of a safety check") silently never matches when the exact same code removal is performed through the `MultiEdit` tool instead of `Edit`. This is the same class of bug as the Golom finding: the validation check reads one field/path while the actually-executed operation can supply an equivalent, unvalidated field/path, letting the acting party bypass the intended control while still achieving the guarded effect.

### Finding Description
Hookify's `PreToolUse`/`PostToolUse` hooks (`plugins/hookify/hooks/pretooluse.py`, `posttooluse.py`) call `RuleEngine.evaluate_rules`, which for each rule calls `_rule_matches` → `_check_condition` → `_extract_field` [1](#0-0) .

`_extract_field` resolves a condition's `field` name to an actual value taken from `tool_input`:
- For `Write`/`Edit`, `old_text`/`old_string` is explicitly handled, returning `tool_input.get('old_string', '')` [2](#0-1) .
- For `MultiEdit`, only `file_path` and `new_text`/`content` (concatenated across the `edits` list) are handled; there is no branch that reads `old_string` from each entry in `tool_input['edits']` [3](#0-2) .

Because `_extract_field` returns `None` in this case, and `_check_condition` treats a `None` field value as an automatic non-match ("If `field_value is None: return False`") [4](#0-3) , any rule whose condition targets `old_text`/`old_string` will never fire for `MultiEdit` tool calls — regardless of what the old content actually was. `MultiEdit` is otherwise a fully valid target for hookify's "file" event matching (`tool_name in ['Edit', 'Write', 'MultiEdit']` in the hook dispatcher) [5](#0-4) , and the plugin's own documentation explicitly advertises `old_text` as a supported field for gating file edits, only caveating it as "Edit only" in a field reference table that a rule author is unlikely to notice as an enforcement gap rather than a scope note [6](#0-5) .

### Impact Explanation
A project may rely on a hookify `block` rule such as:
```yaml
event: file
conditions:
  - field: old_text
    operator: contains
    pattern: "verify_signature("
action: block
```
intended to stop the agent (whether acting on its own, under a jailbreak, or steered by a prompt-injection from untrusted content) from silently deleting a safety/security check from source code. Because `MultiEdit` performs textually identical old→new string replacements as `Edit` but is not covered by the `old_text` extraction path, the exact same edit that would be blocked via the `Edit` tool is silently approved when issued via `MultiEdit`. This is a concrete hook/approval bypass: the intended trust boundary (block dangerous code removal) is defeated purely by choosing an alternate, functionally-equivalent tool call, with no user interaction and no error surfaced (the hook returns `{}`, i.e. "allow", exactly as if no rule existed).

### Likelihood Explanation
`MultiEdit` is a normal, frequently-used Claude Code tool for making several edits to one file in a single call, so an agent (or an attacker who can influence the agent's behavior, e.g. via prompt injection in a file or web content it processes) does not need any special privilege to trigger this path — it only needs to prefer `MultiEdit` over `Edit` for the same change, which is an unremarkable and low-effort action.

### Recommendation
Extend `_extract_field`'s `MultiEdit` branch to also support `old_text`/`old_string` by concatenating `old_string` across all entries in `tool_input.get('edits', [])`, mirroring the existing handling for `new_text`/`content`:
```python
elif tool_name == 'MultiEdit':
    if field == 'file_path':
        return tool_input.get('file_path', '')
    elif field in ['new_text', 'content']:
        edits = tool_input.get('edits', [])
        return ' '.join(e.get('new_string', '') for e in edits)
    elif field in ['old_text', 'old_string']:
        edits = tool_input.get('edits', [])
        return ' '.join(e.get('old_string', '') for e in edits)
```
More generally, `_check_condition` should fail closed (block/warn) rather than silently return `False`/allow when a condition's field cannot be resolved for a given tool, so gaps like this cannot be exploited to bypass a `block` rule.

### Proof of Concept
1. Add a hookify block rule at `.claude/hookify.block-remove-check.local.md`:
```markdown
---
name: block-remove-check
enabled: true
event: file
conditions:
  - field: old_text
    operator: contains
    pattern: "verify_signature\("
action: block
---
Removing a signature verification call is not allowed.
```
2. Ask Claude Code to use the `Edit` tool to delete a line containing `verify_signature(...)` from a file — the `PreToolUse` hook fires `pretooluse.py` → `RuleEngine.evaluate_rules`, `_extract_field('old_text', ...)` returns the old string containing `verify_signature(`, the condition matches, and the operation is blocked (`permissionDecision: deny`) per `evaluate_rules` [7](#0-6) .
3. Ask Claude Code to make the identical change (same file, same old/new text) using the `MultiEdit` tool with `edits: [{"old_string": "...verify_signature(...)...", "new_string": "..."}]`. `_extract_field` for `MultiEdit` does not resolve `old_text`, returns `None`, `_check_condition` returns `False`, the rule never matches, and `evaluate_rules` returns `{}` — the removal proceeds unblocked, despite the rule being designed to prevent exactly this change.

```python
    def _rule_matches(self, rule: Rule, input_data: Dict[str, Any]) -> bool:
        """Check if rule matches input data.

        Args:
            rule: Rule to evaluate
            input_data: Hook input data

        Returns:
            True if rule matches, False otherwise
        """
        # Extract tool information
        tool_name = input_data.get('tool_name', '')
        tool_input = input_data.get('tool_input', {})

        # Check tool matcher if specified
        if rule.tool_matcher:
            if not self._matches_tool(rule.tool_matcher, tool_name):
                return False

        # If no conditions, don't match
        # (Rules must have at least one condition to be valid)
        if not rule.conditions:
            return False

        # All conditions must match
        for condition in rule.conditions:
            if not self._check_condition(condition, tool_name, tool_input, input_data):
                return False

        return True
```
