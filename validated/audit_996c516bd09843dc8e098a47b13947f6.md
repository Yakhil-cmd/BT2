### Title
Organization-fallback webhook verification lets one org's signature archive/unarchive another repo's review stack - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App/secret to verify against using `repository_owner`, which falls back to the top-level `organization.login` field when `repository.owner.login` is absent, while every `pull_request` handler (including `UnlabeledHandler`) resolves the target `Repository`/`Stack` from the independently-controlled `repository.full_name` field. In a multi-organization Shipit deployment, an attacker who can authenticate as (or exploit a secret-less config for) one configured organization can supply a `repository.full_name` pointing at a victim organization's repo, causing `UnlabeledHandler` to archive or unarchive that victim's review stack.

### Finding Description
The broken invariant, stated as an equality that must hold but doesn't:
`organization_that_authenticated_the_request == owner_of(repository.full_name_used_by_the_handler)`

- `repository_owner` is computed as `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0)  and is used solely to select which `GitHubApp` (and thus which `webhook_secret`) verifies the signature: `github_app = Shipit.github(organization: repository_owner)` [2](#0-1) .
- In a multi-org config, `Shipit.github` does an exact keyed lookup: `config = github_app_config(organization); raise GithubOrganizationUnknown, organization if config.nil?` [3](#0-2) , and per-org `webhook_secret` is optional — `verify_webhook_signature` returns `true` unconditionally `unless webhook_secret` is present [4](#0-3) . This "Using Multiple Github Applications" mode is a documented supported configuration (top-level org keys in `secrets.github`).
- `UnlabeledHandler`, however, never reads `repository.owner.login` or cross-checks it against `repository_owner`. It resolves the target repo purely from `params.repository.full_name`: `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [5](#0-4) , and its `ExplicitParameters` schema only requires `repository.full_name`, never `repository.owner` [6](#0-5) .
- Exploit: attacker sends a `pull_request`/`action=unlabeled` payload where the top-level `organization.login` field names an organization that Shipit is configured for and which the attacker can authenticate to (either they know that org's `webhook_secret`, or that org's `webhook_secret` is unset/nil so any signature is accepted), while the nested `repository` object omits `owner` but sets `full_name` to the victim's `org/repo`. `repository_owner` then falls back to the attacker's known organization and signature verification passes against that org's app. The handler then loads the victim's `Repository`/`ReviewStack` via `full_name` and calls `stack.archive!`/`stack.unarchive!` via `ReviewStackAdapter#archive!`/`#unarchive!` [7](#0-6) , mutating the victim's stack state, which — on a stack with `blocking_statuses` configured — participates in `blocked?`/deploy gating.
- Existing guards do not catch this: `verify_signature` never compares the verifying organization to the repository actually acted upon; the `ExplicitParameters` schema for `UnlabeledHandler` requires `repository.full_name` but not `repository.owner`; there is no cross-check anywhere in `webhooks_controller.rb`, `github_app.rb`, or `unlabeled_handler.rb`/`review_stack_adapter.rb` tying the verified org to the acted-upon repo's owner.

### Impact Explanation
A payload authenticated under one organization's webhook credentials (or a secret-less org) can archive or unarchive a review stack belonging to an entirely different organization/repository that never authenticated the request. This is a cross-tenant state mutation: it can silently archive an in-flight review stack (halting/removing it from provisioning) or force-unarchive/recreate one, and on stacks configured with `blocking_statuses` this state churn interacts with deploy gating logic that flips `blocked?`. This matches the "payload for one repository mutating another's stack" Critical category, though the effect here is limited to archive/unarchive of `ReviewStack` records rather than direct code execution.

### Likelihood Explanation
This requires: (1) Shipit deployed with the multi-organization GitHub App configuration (documented feature, not the default single-app setup, since in the default/legacy setup `Shipit.github` ignores the `organization:` argument entirely and always uses the single configured secret); (2) at least one configured organization with either no `webhook_secret` or a secret known to the attacker (e.g., the attacker's own org onboarded to the same Shipit instance); and (3) a victim organization/repo with review stacks and `blocking_statuses` configured on the same Shipit instance. Given those preconditions, the attack is cheap (a single crafted HTTP POST, no GitHub secrets needed for the target org) and fully repeatable against any repository name the attacker chooses.

### Recommendation
In `WebhooksController#verify_signature`/`create`, after verifying the signature, cross-check that the organization used to select the verifier matches the owner of `repository.full_name` (or any other repository field) that handlers will act on, and reject the request if they diverge. Alternatively, require handlers to resolve the target repository/stack using the same organization value that was cryptographically verified, not a separate attacker-controlled field, and make `repository.owner.login` a required, verified field.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`, but adjusted to reproduce without editing out-of-scope files):
```ruby
test "organization fallback lets one org's signature archive another org's review stack" do
  # Setup: multi-org secrets config with OrgAttacker (webhook_secret: nil) and OrgVictim (webhook_secret: 'victim-secret')
  # Precondition: a Stack (review stack) exists for "org-victim/repo" with blocking_statuses configured,
  # environment "pr1", not archived.

  payload = {
    "action" => "unlabeled",
    "number" => 1,
    "pull_request" => {
      "id" => 1, "number" => 1, "url" => "http://x", "title" => "t", "state" => "open",
      "additions" => 1, "deletions" => 1,
      "head" => { "sha" => "abc", "ref" => "feature" },
      "user" => { "login" => "attacker" },
      "assignees" => [],
      "labels" => []  # no provisioning label -> triggers archive? true if configured accordingly
    },
    "repository" => { "full_name" => "org-victim/repo" }, # no "owner" key -> fallback triggers
    "organization" => { "login" => "OrgAttacker" },        # attacker's own org, no webhook_secret
    "sender" => { "login" => "attacker" }
  }.to_json

  @request.headers['X-Github-Event'] = 'pull_request'
  @request.headers['X-Hub-Signature'] = 'sha1=anything' # accepted because OrgAttacker has no webhook_secret

  before_state = victim_stack.archived?

  post :create, body: payload, as: :json
  assert_response :ok

  # Assertion: repository_owner used for verification (OrgAttacker) != owner of repository.full_name (org-victim)
  refute_equal "OrgAttacker", "org-victim"
  # Yet the victim stack state changed despite never authenticating org-victim's webhook secret
  assert_not_equal before_state, victim_stack.reload.archived?
end
```
This demonstrates the equality `organization_that_authenticated_request == owner_of(repository.full_name)` is false, yet the mutation on `org-victim`'s stack still occurs.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
