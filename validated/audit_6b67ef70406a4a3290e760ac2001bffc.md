### Title
Webhook signature verification is bound to `repository.owner.login`, not to the repository/stack the handlers actually act on - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate the incoming HMAC signature against using `repository_owner`, computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. Once the signature check passes, `WebhooksController#create` dispatches the *entire* raw JSON payload to the registered `Shipit::Webhooks::Handlers::Handler` subclasses, which independently derive the repository/stack they act on from a *different* field: `payload.dig('repository', 'full_name')` (see `Handler#repository_name`, and per-handler `repository`/`stacks` lookups in `PushHandler`, `PullRequest::OpenedHandler`, `PullRequest::LabeledHandler`, `PullRequest::UnlabeledHandler`, `PullRequest::LabelCapturingHandler`, etc.). ### Finding Description
The binding that should hold is:
`organization whose secret authenticated the request` == `organization/repository that the dispatched handlers write to`.

In this engine, a Shipit instance can be configured with multiple GitHub organizations, each with its own `webhook_secret` (see `config/secrets.development.shopify.yml`, which documents multiple orgs sharing one Shipit deployment). `verify_signature` picks the app/secret to validate against solely from `repository.owner.login` (or the fallback `organization.login`) inside the untrusted JSON body, and the HMAC check only proves the *body as a whole* was signed with *that* organization's `webhook_secret` — it does not bind the signature to a *specific* repository belonging to that organization.

Because the handlers that actually perform the writes (`PushHandler#process`, `PullRequest::OpenedHandler#repository`, `PullRequest::LabeledHandler#stack`, `PullRequest::UnlabeledHandler#stack`, `PullRequest::LabelCapturingHandler#repository`) resolve their target purely from `repository.full_name` in the same payload, an attacker who legitimately controls (owns/administers) the GitHub App for Organization A — and therefore knows Organization A's `webhook_secret` — can craft an arbitrary JSON body where `repository.owner.login` = "OrgA" (so `verify_signature` picks OrgA's secret and the HMAC validates) but `repository.full_name` = "OrgB/victim-repo" (a completely different, unrelated organization/stack hosted on the same Shipit instance). The signature check passes because it only certifies "a holder of OrgA's secret produced this exact byte string," while the handlers dispatch based on an unrelated field within that same attacker-controlled byte string.

This is the "organization authenticated vs. repository written" binding break called out for this engine: the field verified by the signature (via `repository_owner`) is not the field the handlers use to select which repository/stack is mutated (`repository.full_name`).

### Impact Explanation
With a forged cross-organization webhook accepted, an attacker who administers Organization A's GitHub App (its own webhook secret) can:
- Force `PushHandler` to invoke `stack.sync_github` for stacks belonging to Organization B, causing Shipit to fetch/re-sync commit history and, if `continuous_deployment` is enabled, potentially trigger the deploy pipeline for a repository the attacker has no legitimate relationship to.
- Force `PullRequest::OpenedHandler`, `LabeledHandler`, `UnlabeledHandler`, `LabelCapturingHandler` to create, archive/unarchive review stacks or capture labels for pull requests on Organization B's repositories, corrupting review-stack state cross-tenant.

This crosses a repository/organization trust boundary that Shipit's webhook signature is supposed to enforce, matching the "cross-repository writes" impact category. The severity depends on how many organizations a given Shipit instance actually hosts and whether continuous deployment is enabled on the victim stack, since the concrete "unauthorized deploy" chain requires that additional condition.

### Likelihood Explanation
Exploitation requires the attacker to possess a legitimate `webhook_secret` for *some* organization configured on the target Shipit instance (i.e., they must own/administer a GitHub App entry in that instance's `Shipit.github` configuration) — this is plausible in any multi-tenant Shipit deployment where different, mutually-untrusting teams/orgs are configured on a shared instance, which is an explicitly supported configuration pattern (`config/secrets.development.shopify.yml` shows two independent orgs). No `ApiClient` token, session, or GitHub write access to the *victim* repository is required — only knowledge of an unrelated, self-controlled organization's webhook secret, and the ability to POST directly to the `/github/webhooks` endpoint with a crafted body.

### Recommendation
`verify_signature` (and/or each `Handler`) should cross-check that the organization whose secret validated the signature actually owns the repository named in `repository.full_name` before dispatching to handlers — e.g., resolve the `Repository`/`Stack` first, confirm its owner matches `repository_owner`, and reject (422) on mismatch. Alternatively, derive the signing organization strictly from the resolved `Stack`/`Repository` record rather than from unauthenticated payload fields.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` (attacker-administered) and `OrgB` (victim), each with distinct `webhook_secret`s, both hosting stacks on the same Shipit instance.
2. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef...",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature` using OrgA's known `webhook_secret` over this exact raw body (matching `Hook::DeliverySigner`/`GithubApp#verify_webhook_signature` algorithm).
4. POST to the webhooks endpoint with `X-Github-Event: push`. `verify_signature` resolves `repository_owner` = `"OrgA"`, fetches OrgA's app via `Shipit.github(organization: 'OrgA')`, and the HMAC validates successfully.
5. `Webhooks.for_event('push')` dispatches to `PushHandler`, whose `stacks` method resolves `Repository.from_github_repo_name('OrgB/victim-repo')` and calls `sync_github` on OrgB's stack — a write performed on behalf of an organization the attacker never authenticated as. [5](#0-4) [4](#0-3)
