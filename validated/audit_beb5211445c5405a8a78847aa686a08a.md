### Title
Cross-organization team-membership forgery escalates an arbitrary existing user into `Shipit.github_teams` - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#process` resolves the target `Team` solely by `params.team.id` (`github_id`), never checking that this team's `organization` matches the organization whose webhook signature was actually verified. An attacker who controls any organization onboarded into Shipit's multi-org webhook config can therefore send a `membership`/`added` event naming a real team's `github_id` belonging to a *different* organization and an arbitrary existing Shipit user's login, silently adding that user to the real team and granting them `Shipit.github_teams` authorization.

### Finding Description
The binding that should hold is:
`verified_organization (params.organization.login, authenticated via that org's webhook_secret in Shipit::WebhooksController#verify_signature)` **==** `team.organization (the org that owns the github team identified by params.team.id)`.

The code never enforces this equality:

- `Shipit::WebhooksController#verify_signature` derives `repository_owner` from `params.dig('organization', 'login')` for events without a `repository` key [1](#0-0) , then verifies the signature using `Shipit.github(organization: repository_owner)` [2](#0-1) . This only proves the payload was signed by *that* organization's configured webhook secret — it says nothing about which team the payload's `team.id` actually belongs to.
- `MembershipHandler#find_or_create_team!` looks up the team purely `Team.find_or_create_by!(github_id: params.team.id)` [3](#0-2) . If a `Team` row with that `github_id` already exists (e.g. because it's one of the real teams resolved into `Shipit.github_teams` via `Team.find_or_create_by_handle` at boot [4](#0-3) ), the `do |team| ... end` block is skipped entirely — `team.organization` is **not** re-validated or re-set to `params.organization.login`.
- `process` then unconditionally calls `team.add_member(member)` for `action == 'added'` [5](#0-4) , and `Team#add_member` just appends the member to `members` with no organization check [6](#0-5) .
- `User.find_or_create_by_login!(params.member.login)` finds any pre-existing Shipit `User` by login, including users who never interacted with the attacker's org [7](#0-6) .
- `User#authorized?` checks membership against exactly the `Shipit.github_teams` id set [8](#0-7) , so being added to one of those real teams (by `github_id` collision) directly flips `authorized?` to `true`.

Attacker's request: a `POST /webhooks` with header `X-Github-Event: membership`, signed with the attacker's own organization's webhook secret (a precondition granted by the question's scoping — the attacker's org is a configured Shipit tenant), and body:
```json
{
  "action": "added",
  "team": { "id": <github_id of a real Shipit.github_teams team>, "name": "...", "slug": "...", "url": "..." },
  "organization": { "login": "<attacker-org>" },
  "member": { "login": "bob" }
}
```
None of the existing guards (`verify_signature`, `drop_unhandled_event`, the `ExplicitParameters` schema) check that `team.id` belongs to `organization.login`; the schema only enforces types/presence, not cross-field integrity [9](#0-8) .

### Impact Explanation
A single forged webhook, correctly signed by an attacker's own (legitimately configured) organization, adds an arbitrary pre-existing Shipit user to a real authorization-bearing team without that user's or the real organization's knowledge or consent. Since `Shipit.github_teams` membership drives `User#authorized?`, this is a direct privilege escalation into Shipit's authorization set — matching the "High: escalation into `Shipit.github_teams` authorization" impact category. It is repeatable against any user login and any team `github_id` the attacker can guess or discover, and is not scoped to the attacker's own tenant/org, so it breaks tenant isolation between organizations sharing one Shipit deployment.

### Likelihood Explanation
Requires a multi-organization Shipit deployment where the attacker administers (or has webhook-secret access to) one configured organization — a documented, supported configuration (`docs/setup.md` "Using Multiple Github Applications"). The attacker needs no Shipit session, API token, or knowledge of any other org's secret — only their own org's webhook secret, which they legitimately possess as that org's admin. They additionally need the numeric `github_id` of a target team, which is often discoverable (team pages, GitHub API for public teams, or brute-forceable small integers) and the target's GitHub login (public information). The attack is a single crafted HTTP POST, trivially repeatable for any login/team pair.

### Recommendation
In `MembershipHandler#find_or_create_team!` (and generally before `add_member`/`members.delete`), verify that the existing team's `organization` equals `params.organization.login` before acting; if it doesn't match, reject/no-op the event (and log/alert) rather than mutating membership on a team owned by a different, unverified organization. Additionally, in `Team.find_or_create_by!`, use the compound key `{ github_id:, organization: }` rather than `github_id` alone so a differing organization for the same `github_id` never resolves to the pre-existing record.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual)
test ":membership from an attacker-controlled org cannot escalate a real team's member" do
  real_team = shipit_teams(:real_org_team) # github_id known, organization: "real-org"
  bob = shipit_users(:bob) # exists, no teams, authorized? == false
  Shipit.stubs(:github_teams).returns([real_team])

  request.headers['X-Github-Event'] = 'membership'
  GithubHook.any_instance.stubs(:verify_signature).returns(true) # signature verified for "attacker-org"

  post :create, as: :json, body: {
    action: 'added',
    team: { id: real_team.github_id, name: real_team.name, slug: real_team.slug, url: real_team.api_url },
    organization: { login: 'attacker-org' },
    member: { login: bob.login }
  }.to_json

  assert_response :ok
  # Broken binding demonstrated: verified org ("attacker-org") != team.organization ("real-org"),
  # yet membership was still written and authorization escalated.
  assert_not_equal 'attacker-org', real_team.reload.organization
  assert bob.reload.teams.include?(real_team)
  assert bob.authorized?
end
```
