## Title
Crafted double‑spending private‑asset payment triggers an uncaught `throw` that crashes the full node process (remote DoS) - (File: `validation.js`)

### Summary
CVE-2017-11337 describes an invalid free in Exiv2's `Action::TaskFactory::cleanup` triggered by crafted input, causing the whole process to abort (remote DoS). The `ocore` analog is a similar "crafted input reaches a defensive/unreachable code assertion that unconditionally crashes the process" bug class: in `validation.js`, the double-spend acceptance logic for private assets calls `throw Error(...)` directly inside an asynchronous DB-callback that is *not* guarded by any try/catch in the caller chain. In Node.js, a `throw` inside an async callback that has no surrounding try/catch propagates as an uncaught exception and kills the entire process — functionally the same outcome (uncontrolled process termination from adversary-controlled input) as the reported invalid-free crash.

### Finding Description
`checkForDoublespends()` resolves conflicting inputs for both public and private-asset payments. Its final callback contains: [1](#0-0) 

```
function onDone(err){
    if (err && objAsset && objAsset.is_private && !conf.bLight)
        throw Error("spend proof didn't help: "+err);
    cb2(err);
}
```

and inside `checkForDoublespends` itself the "included" branch that decides whether a conflict is resolved contains a similar defensive `throw` for cases the author believed to be unreachable: [2](#0-1) 

Both of these `throw` statements execute inside `conn.query(...)` callbacks (`checkForDoublespends`, `checkInputDoubleSpend`) that are several levels deep in `async.forEachOfSeries`/`async.eachSeries` chains driven by `validatePaymentInputsAndOutputs` → `validateMessage` → `validate()`. None of these callback layers wrap the call in try/catch, so any `throw` reached here is an uncaught exception at the Node.js event-loop level, which terminates the whole process — not just the current unit's validation.

This condition is reached whenever:
1. A private-asset payment is being validated on a full node (`objAsset.is_private && !conf.bLight`), and
2. `checkForDoublespends` returns an error because the conflicting spend of the same input is judged "included and too young / already good sequence" per `validation.js` lines 1676-1694.

An attacker who controls a private-payment chain (a normal, unprivileged capability — private payments are posted/forwarded by ordinary wallets/hubs, see `handleOnlinePrivatePayment` in `network.js`) can construct two competing spends of the same private-asset output where the second unit includes the first as an ancestor but still attempts to spend the same input. This drives the resolution path straight into the `throw`.

### Impact Explanation
An uncaught exception thrown from deep inside the validation pipeline terminates the Node.js process immediately. Any full node (hub, wallet-serving node, etc.) that processes such a crafted private-payment chain crashes, achieving the same "network unable to confirm new units" / node-crash impact class allowed by the scope: an unprivileged private-payment counterparty can knock offline any node that attempts to validate the doublespend resolution for the tainted private-asset chain, denying service to that node and its dependents.

### Likelihood Explanation
The severity is Medium: reaching the throw requires crafting a specific double-spend/ancestor relationship for a private asset (feasible for any user controlling that asset's private chain, e.g., its issuer or a colluding counterparty), but it does not require any special privilege, key leakage, or peer/hub compromise — only posting properly signed but adversarial private-payment units, matching the CVE's "remote, low-complexity crafted input" profile.

### Recommendation
- Replace the `throw Error(...)` calls in `checkForDoublespends`/`checkInputDoubleSpend` (`validation.js` lines ~1688, ~2299) with calls to the `cb`/`cb2` error-callback path so malformed/adversarial units are rejected as invalid rather than crashing the process.
- Audit other `throw Error("...unreachable...")`-style defensive assertions inside asynchronous DB-callback chains reachable from unit/private-payment validation, and convert them to callback-based error propagation, since any of them can be weaponized the same way once the "unreachable" precondition is actually reachable via adversarial input.
- Add a top-level `process.on('uncaughtException', …)` safety net is not itself a fix — the real fix is to never let externally-triggerable code paths throw synchronously; validation should always fail closed via the callback API.

### Proof of Concept
1. Issue/have access to a private asset whose spendable output can be referenced from two different units by the same or colluding authors.
2. Unit A spends private output O and gets accepted (`sequence = 'good'`) into the DAG.
3. Craft Unit B, which includes Unit A as an ancestor (so `bIncluded = true` in `checkForDoublespends`), but whose payload still attempts to spend the same private output O (a double-spend of an already "good"-sequence, included ancestor spend).
4. Submit Unit B's private payment chain to a full node via `handleOnlinePrivatePayment` (`network.js`), which routes into `privatePayment.validateAndSavePrivatePaymentChain` → unit/message validation → `validatePaymentInputsAndOutputs` → `checkForDoublespends`.
5. The resolution branch determines the conflict is on an included ancestor with `sequence === 'good'`, returns an error to `onDone`, and because the asset `is_private` and the node is not light (`!conf.bLight`), the code executes `throw Error("spend proof didn't help: "+err)`, which is uncaught and terminates the node process.
