### Title
Permanent market freeze from RAY-value overflow during interest accrual - ([File: common/src/rates/simulate.rs])

### Summary
Every market mutation first runs `interest::global_sync`, which calls `accrue_step` before executing the requested operation. [1](#0-0)  `accrue_step` multiplies total scaled debt by the borrow index and total scaled supply by the supply index before enforcing the borrow-index cap. [2](#0-1)  Those multiplications panic with `MathOverflow` when the resulting RAY-denominated aggregate no longer fits in `i128`. [3](#0-2) [4](#0-3) 

### Finding Description
A large, heavily utilized market can reach a state where `borrowed * borrow_index` or `supplied * supply_index` exceeds `i128::MAX` before `MAX_BORROW_INDEX_RAY` is reached. [5](#0-4)  `scaled_to_original` delegates this calculation to `Ray::mul`, and `mul_div_half_up` treats an unrepresentable result as a contract panic rather than a recoverable accounting state. [6](#0-5) [4](#0-3) 

The panic happens before any operation-specific logic because `synced_market` loads the market and runs `global_sync` first. [7](#0-6)  Consequently, repayment fails before debt shares are burned, withdrawal fails before supply shares are burned, and additional borrowing fails before utilization checks run. [8](#0-7) [9](#0-8) [10](#0-9) 

This is reachable through normal user operations: `supply` creates or adds collateral, `borrow` creates debt, and `update_indexes` triggers accrual. [11](#0-10) [12](#0-11) 

### Impact Explanation
Once either aggregate RAY value crosses the representable boundary, all state-changing operations for that market revert during accrual. Suppliers cannot withdraw their underlying tokens, borrowers cannot reduce debt, liquidators cannot safely operate on debt in that market, and keeper-driven index updates remain unusable. [7](#0-6)  This is permanent freezing of funds and market operation, not merely a temporary unavailable-price or paused-asset condition. [8](#0-7) [9](#0-8) 

### Likelihood Explanation
The condition requires an exceptionally large listed market and sustained debt accrual, so ordinary markets may never approach it. However, the accepted token-to-RAY domain can place a large book close enough to `i128::MAX` that later index growth crosses it before the configured index cap protects accrual. [13](#0-12)  An attacker with sufficient capital can establish the state through ordinary `supply` and `borrow` calls, while anyone can advance accrual with `update_indexes`. [11](#0-10) [12](#0-11) 

### Recommendation
Enforce a stricter market-level bound on `scaled * index` rather than relying only on the raw index ceiling. In particular, reject supply, debt, cap, or parameter states that can make `borrowed * borrow_index` or `supplied * supply_index` exceed `i128::MAX`, and perform the cap test before unscaling aggregate values. [14](#0-13)  A safer implementation would use widened arithmetic for boundary checks and clamp indexes to the maximum value that keeps both aggregate values representable. [15](#0-14) 

### Proof of Concept
1. An attacker calls `Controller::supply(caller=attacker, account_id=0, spoke_id=S, assets=[(collateral_asset, C), (target_asset, T)])`, where `T` is large enough that its RAY-normalized supply approaches the representable accounting domain and `C` provides sufficient borrowing collateral. [16](#0-15) 
2. The attacker calls `Controller::borrow(caller=attacker, account_id=A, borrows=[(target_asset, B)], to=None)` with `B` near the market’s usable liquidity, leaving a large `borrowed` scaled balance. [17](#0-16) [18](#0-17) 
3. Interest accrual raises `borrow_index` and `supply_index` until `borrowed * borrow_index` or `supplied * supply_index` no longer fits in `i128`. [14](#0-13) 
4. Any later call to `Controller::update_indexes`, `repay`, `withdraw`, or another path touching the market enters `synced_market`, reaches the same multiplication, and reverts with `MathOverflow`. [7](#0-6) [4](#0-3)

/// Computes `x * y / d` rounded half up. Requires `x >= 0`, `y >= 0`, and `d > 0`; a
/// `debug_assert` checks this in debug builds. Panics with `GenericError::DivisionByZero` if
/// `d == 0`, and with `GenericError::MathOverflow` if any other precondition is violated or if
/// the result does not fit in `i128`.
pub fn mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> i128 {
    // The zero check runs first so debug and release builds agree on a zero
    // divisor: both surface `DivisionByZero` rather than tripping the assert.
    require_nonzero_divisor(env, d);
    debug_assert!(
        x >= 0 && y >= 0 && d > 0,
        "mul_div_half_up: non-negative x, y and positive d"
    );
    try_mul_div_half_up(env, x, y, d)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow))
}
