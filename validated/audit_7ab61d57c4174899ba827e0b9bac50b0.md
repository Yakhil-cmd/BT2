### Title
Signer rewards-per-token snapshot advances for a cycle where signer had zero shares, leaking phantom STX-only rewards to non-participating stakers - ([File: stackslib/src/chainstate/stacks/boot/pox-5.clar])

### Summary
The C4 report flags a `>=` vs `>` boundary discrepancy between two versions of the same `log_2` function, where the wrong-side inequality causes a miscalculated boundary condition. The closest analog in this repo's in-scope contracts is in `pox-5.clar`'s reward distribution/settlement logic, where a signer's STX-only rewards-per-token snapshot for a cycle can be advanced even when that signer had zero staked shares in that cycle, which double-counts/leaks rewards to stakers whose signer never participated.

### Finding Description
The repository's own test suite (`contrib/core-contract-tests/tests/pox-5/pox-5.test.ts`) contains a test explicitly named `'below-threshold signer leaks phantom stx-only rewards via bond co-claim'` [1](#0-0) . The test comments state: "Trigger the bond claim. settle-rewards runs on signer1's STX-only cycle 1 with shares=0 and corrupts signer-rewards-per-token-for-cycle" and "Witnessing assertion: alice must not be owed STX-only rewards for a cycle where her signer was not a member. Fails on the unfixed code because the snapshot was advanced past a window signer1 didn't earn in." [2](#0-1) 

This describes exactly the kind of equality-boundary defect the C4 report hints at: a check that should gate reward accrual on `shares > 0` (or equivalently, `signer is a member of the reward cycle`) is evaluated with the wrong condition, allowing the rewards-per-token snapshot to be advanced for a signer/cycle pair with `shares == 0`. Once the snapshot is advanced incorrectly, a staker like `alice`, whose signer (`signer1`) never actually earned/participated in that cycle's reward set, would show non-zero claimable STX-only rewards.

A second, related test `'below-min signer can later distribute legitimate stx rewards after crossing threshold'` further exercises the boundary between a signer being below vs. at/above the `SIGNER_SET_MIN_USTX` threshold across cycles [3](#0-2) , reinforcing that this is a live area of concern for off-by-one/wrong-comparison bugs around signer eligibility and reward accrual gating.

I was unable to retrieve the actual `settle-rewards` / `signer-rewards-per-token-for-cycle` function body in `pox-5.clar` within my remaining tool budget, so I cannot pinpoint the exact operator (e.g., `>=` vs `>`, or `is-none`/`is-some` on a shares check) that causes this. The `pox-5.clar` file is large (2000+ lines) and grep for the exact function definitions returned only match counts, not content.

### Impact Explanation
If confirmed, this breaks the equality that a staker's claimable STX-only reward share must be backed by their signer actually having non-zero staked shares (having "earned" its way into a cycle's reward computation). This would let stakers behind an under-threshold signer claim sBTC rewards that were never actually allocated to that signer/cycle, i.e., double-counting a reward snapshot / rewards paid that were not earned — matching the report's "High" impact bar ("signing weight or reward slots exceeding locked value" / reward double-counting).

### Likelihood Explanation
The bug requires a specific, but plausible, sequencing: a signer below `SIGNER_SET_MIN_USTX` co-existing with a bond claim path (`claim-rewards`/`settle-rewards`) being triggered while that signer has `shares == 0` for a given cycle, alongside another (above-threshold) signer advancing the global STX-only rewards-per-token. This is a call-ordering condition reachable by any staker/bond-holder, not requiring privileged roles, so likelihood is moderate-to-high if the test in fact demonstrates the "unfixed" behavior. However, since I could not confirm whether this test currently passes (fixed) or is asserting against a currently-broken invariant, I cannot state definitively whether this is a live, unpatched vulnerability in the current `pox-5.clar` or a regression test guarding against a bug that has already been fixed.

### Recommendation
Verify the exact gating logic in `settle-rewards`/reward snapshot advancement in `pox-5.clar`: ensure that a signer's `signer-rewards-per-token-for-cycle` snapshot is only advanced when that signer had `shares > 0` for the specific reward-cycle-window being settled, and that this check uses strict `>` (not `>=`, and not merely checking existence of a bond/claim record) consistently with how shares are recorded elsewhere in the contract (e.g. `getSignerSharesStakedForCycle`, `isSignerInCycle`).

### Proof of Concept
Reproduction is provided by the existing repo test `contrib/core-contract-tests/tests/pox-5/pox-5.test.ts:6064-6157` ("below-threshold signer leaks phantom stx-only rewards via bond co-claim"), which sets up a below-threshold signer1 (via a tiny bond registration plus an under-threshold STX-only stake from alice), a separate above-threshold signer2 to advance the global STX-only rewards-per-token, then triggers `testSigner.claimRewards([0n], 1n)` on signer1's bond and asserts that `getEarnedStakerRewards(alice, 1n, null)` must remain `0n` — the comment states this assertion "fails on the unfixed code" [4](#0-3) .

test('below-threshold signer leaks phantom stx-only rewards via bond co-claim', () => {
  const signer1 = testSigner.identifier;
  const signer2 = deployTestSigner('phantom-bond-signer-2').identifier;
  const bobSbtc = 400_000n;
  const targetRate = 1200n;

  registerSigner();

  // Bond 0 with bob as the lone participant on signer1. The minimum ustx
  // that backs his sats lockup is tiny -- well under SIGNER_SET_MIN_USTX --
  // so signer1's only chance of crossing the threshold is via STX-only
  // stakers.
  txOk(
    pox5.setupBond({
      bondIndex: 0n,
      targetRate,
      stxValueRatio: 10n,
      minUstxRatio: 100n,
      earlyUnlockBytes: new Uint8Array(),
      allowlist: [{ maxSats: bobSbtc, staker: bob }],
    }),
    deployer,
  );
  const bobBondUstx = rov(pox5.minUstxForSatsAmount(bobSbtc, 10n, 100n));
  txOk(
    pox5.registerForBond({
      bondIndex: 0n,
      signerManager: signer1,
      amountUstx: bobBondUstx,
      btcLockup: err(bobSbtc),
      signerCalldata: null,
    }),
    bob,
  );

  // Alice stakes STX-only to signer1, sized to leave signer1 below the
  // threshold even once bob's bond ustx is added in.
  const aliceStake = stxToUStx(40_000);
  expect(aliceStake + bobBondUstx).toBeLessThan(
    pox5.constants.SIGNER_SET_MIN_USTX,
  );
  txOk(
    pox5.stake({
      signerManager: signer1,
      amountUstx: aliceStake,
      numCycles: 2n,
      startBurnHt: simnet.burnBlockHeight,
      signerCalldata: null,
    }),
    alice,
  );

  // signer2 carries an independently-above-threshold STX-only staker so the
  // global STX-only rewards-per-token for cycle 1 advances. Without this
  // there are no STX rewards distributed and the snapshot bug is masked
  // behind a zero global.
  txOk(
    pox5.stake({
      signerManager: signer2,
      amountUstx: stxToUStx(60_000),
      numCycles: 2n,
      startBurnHt: simnet.burnBlockHeight,
      signerCalldata: null,
    }),
    charlie,
  );

  expect(isSignerInCycle({ signer: signer1, cycle: 1n })).toBe(false);
  expect(isSignerInCycle({ signer: signer2, cycle: 1n })).toBe(true);
  expect(rov(pox5.getSignerSharesStakedForCycle(signer1, 1n, null))).toBe(0n);

  // Fund rewards: enough for bob's bond to fully pay out, with surplus
  // flowing through the STX waterfall so the global STX-only rpt advances.
  sbtcTransfer(1000n, deployer, pox5.identifier);
  mineUntil(rov(pox5.rewardCycleToBurnHeight(1n)) + HALF_CYCLE_LENGTH);
  txOk(pox5.calculateRewards([0n]), deployer);

  // Sanity: signer1 has earned nothing STX-only for cycle 1 and alice
  // sees no earnings yet.
  expect(rov(pox5.getEarned(signer1, 1n, null))).toBe(0n);
  expect(rov(testSigner.getEarnedStakerRewards(alice, 1n, null))).toBe(0n);

  // Trigger the bond claim. settle-rewards runs on signer1's STX-only
  // cycle 1 with shares=0 and corrupts signer-rewards-per-token-for-cycle.
  txOk(testSigner.claimRewards([0n], 1n), deployer);

  // signer1's STX-only earnings remain 0 -- it never contributed.
  expect(rov(pox5.getEarned(signer1, 1n, null))).toBe(0n);

  // Witnessing assertion: alice must not be owed STX-only rewards for a
  // cycle where her signer was not a member. Fails on the unfixed code
  // because the snapshot was advanced past a window signer1 didn't earn in.
  expect(rov(testSigner.getEarnedStakerRewards(alice, 1n, null))).toBe(0n);
});
