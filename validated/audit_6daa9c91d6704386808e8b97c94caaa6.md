### Title
Attacker-crafted asset with a self-referencing `transfer_condition`/`spender_attested` restriction can permanently freeze funds sent to an AA by breaking the bounce mechanism - ([File: aa_composer.js])

### Summary
The Sherlock report describes a Solidity liquidation flow that unconditionally requires transferring `liquidatedRemainUSDC` back to the liquidated user; if that user is blacklisted by the token, the mandatory transfer reverts and the whole liquidation is blocked, letting the user dodge liquidation and creating bad debt. The reachable analog in `ocore` is the Autonomous Agent (AA) bounce/response mechanism in `aa_composer.js`, which likewise performs a mandatory payment back to `trigger.address` when an AA response fails, and gives up (silently swallowing the funds) if that mandatory payment itself cannot be validated.

### Finding Description
When an AA's evaluation fails, `bounce(error)` is invoked to refund the trigger's payment back to `trigger.address` [1](#0-0) . This refund is itself just another `payment` message sent through `sendUnit(messages)`, which goes through full unit composition and validation (`validateAndSaveUnit`) before being accepted [2](#0-1) .

Critically, `bounce()` guards against infinite recursion with the `bBouncing` flag: if `sendUnit` invoked from within `bounce()` itself fails (e.g., `validateAndSaveUnit` returns an error) it calls `bounce(err)` again, but since `bBouncing` is already `true`, the function just calls `finish(null)` instead of retrying or reporting the error:
```
if (bBouncing)
    return finish(null);
bBouncing = true;
...
sendUnit(messages);
``` [1](#0-0) 

This means: if the payment being bounced back to `trigger.address` cannot pass validation, the AA trigger is finalized with **no response and no successful refund** — the funds received from the trigger unit (already stably output to the AA's address on-chain) are simply absorbed into the AA balance with no path back out, because every subsequent attempt to pay them out to that same condition-restricted address will hit the identical validation failure.

A payment can be made to permanently fail validation by an attacker who controls the asset definition. Any custom asset can carry a `transfer_condition` or set `spender_attested: true` with a chosen attestor list; these conditions are evaluated during payment validation via `Definition.evaluateAssetCondition`, and failing them causes `"transfer or issue condition not satisfied"` in `validatePaymentInputsAndOutputs` [3](#0-2) . Since asset issuance conditions are entirely author-controlled at asset-definition time [4](#0-3) , an attacker can define (or use) an asset whose `transfer_condition`/`spender_attested` restriction is guaranteed to fail specifically for outputs sent back to their own address (analogous to putting themselves on the equivalent of USDC's blacklist), then send this asset as a trigger payment to any AA. If that AA's logic ever needs to pay this same asset back to the sender (whether via the generic `bounce()` refund path, or via any explicit `payment` message the AA composes back to `trigger.address`), the mandatory outgoing payment fails validation, and per the recursive-bounce guard the AA gives up and finalizes the trigger with the funds stuck.

### Impact Explanation
This results in genuine, unrecoverable freezing of AA funds: the asset units received in the trigger are already stably output to the AA's address (real, on-chain, spent inputs), but the AA can never again successfully pay them back out because the transfer condition attached to the asset (fully controlled by the attacker/issuer) will always fail for that address. This falls squarely within the accepted impact category "AA fund loss or freezing" — no privileged role, malicious node, or network condition is required; a single unprivileged user can trigger it by sending one payment/trigger unit using an asset they define.

### Likelihood Explanation
Any unprivileged user can define a new asset with an arbitrary `transfer_condition`/`spender_attested` list (this is a normal, permitted `asset` message) and then send that asset to any target AA as a payment/trigger. Any AA that unconditionally bounces failed triggers back to `trigger.address`, or that has any code path composing a `payment` message back to the trigger sender in the same asset, is susceptible. This requires no cooperation from validators, witnesses, or other users — only a single crafted unit from the attacker.

### Recommendation
- In `aa_composer.js`, when the refund/bounce payment (or any AA-composed outgoing payment) fails validation, do not silently drop the funds via `finish(null)`. Consider tracking such "stuck" balances explicitly (e.g., crediting them to a claimable ledger entry) so they are not permanently orphaned, or bounce using only the base asset (bytes) which has no attacker-controllable transfer restrictions, decoupling refund guarantees from attacker-defined asset conditions.
- Alternatively/additionally, treat assets with `transfer_condition`/`spender_attested` as unsuitable for guaranteed automatic refunds; AA authors should be warned/encouraged (or the protocol should enforce) that bounce-style refunds only use unconditionally transferable assets, and any AA logic that must repay an incoming custom asset should have an explicit fallback (e.g., leaving the balance claimable rather than requiring an unconditional push payment) instead of assuming the push payment can always succeed.

### Proof of Concept
1. Attacker authors an `asset` definition message with `is_transferrable: true`, `spender_attested: true`, and an attestor list they control, or a `transfer_condition` referencing a fixed address/output pattern that intentionally excludes their own address as a valid recipient (this is entirely within the attacker's control per `validateAssetDefinition` [4](#0-3) ).
2. Attacker sends a payment in this asset to a target AA as a trigger unit, expecting some AA logic path to either fail (triggering `bounce()`) or to explicitly compose a return payment of that asset back to `trigger.address`.
3. When the AA attempts to pay the asset back to `trigger.address` (via `bounce()` or an explicit `payment` message), `validatePaymentInputsAndOutputs` evaluates the `transfer_condition`/attestation check and rejects the unit ("transfer or issue condition not satisfied") [3](#0-2) .
4. `sendUnit`'s call to `validateAndSaveUnit` fails and calls `bounce(err)` again; because `bBouncing` is already `true`, `bounce()` returns `finish(null)` [5](#0-4) , finalizing the trigger with no response and no successful refund.
5. The asset units received from the attacker's trigger remain stuck in the AA's balance permanently, since any future attempt to pay them out to the same restricted address will hit the identical validation failure.
