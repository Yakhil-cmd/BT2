### Title
Webhook signature is verified against a GitHub organization derived from the payload, but the event is processed for whatever repository the same payload names - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp`/`webhook_secret` to validate the HMAC signature against using `repository_owner`, a value read out of the (untrusted, unsigned-at-that-point) request body. The event is then dispatched to handlers keyed off a *different* field in the very same body (`repository.full_name`). Because `GitHubApp#verify_webhook_signature` returns `true` when no `webhook_secret` is configured for the resolved organization, an attacker who controls (or has push access to) any organization configured in the same Shipit instance without a `webhook_secret` can pick that organization for `repository.owner.login` while setting `repository.full_name`/`organization.login` to a victim stack tracked by the same instance, bypassing signature verification entirely for events that affect the victim repository.

### Finding Description
`verify_signature` runs as a `before_action`, before `create`, and resolves the app to check against solely from the payload: [1](#0-0) [2](#0-1) 

`repository_owner` is taken from `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`) — both attacker-supplied JSON fields, not yet authenticated by anything at this point in the request lifecycle.

The signature check itself: [3](#0-2) 

`return true unless webhook_secret` means any organization configured in `secrets.yml`/`Shipit.github` without a `webhook_secret` value (this is explicitly documented as *optional*, see `docs/setup.md` "Webhook secret (optional)") makes signature verification a no-op for requests that name that organization as `repository.owner.login`.

Meanwhile, `create` re-parses the same raw body and dispatches handlers using the payload's own `repository.full_name` (via `Handler#repository_name`) to look up the target `Stack`/`Repository`: [4](#0-3) 

This creates an equality that the engine implicitly relies on but never enforces:
`organization authenticated by verify_signature (repository.owner.login)` **should equal** `repository actually acted on by the handlers (repository.full_name)`.

Nothing in `WebhooksController` or `Handler` ties these two lookups together — an attacker can set them to unrelated values in the same JSON body. If any organization onboarded to the shared Shipit instance has no `webhook_secret` configured (optional per the setup docs), or if the attacker otherwise learns/obtains a secret for *any* one organization served by that instance, they can craft a request whose `repository.owner.login`/`organization.login` matches that low-security org (satisfying `verify_signature`) while `repository.full_name` names a completely different, victim stack whose GitHub organization has a properly configured secret.

### Impact Explanation
This breaks the deployment-trust boundary between "who authenticated this webhook" and "which repository/stack is written to," matching the required Critical impact class of cross-repository writes / unauthorized deploy actions. Depending on which event type is spoofed, handlers keyed only on `repository.full_name` (push → `GithubSyncJob`, status → commit status update, pull_request → merge queue transitions/close, check_suite → check-run refresh) can be triggered against a stack the attacker does not otherwise control, using nothing but network access to the Shipit `/webhooks` endpoint plus control (or a leaked/blank secret) of one unrelated organization entry on the same instance.

### Likelihood Explanation
Requires a Shipit deployment servicing more than one GitHub organization (a documented, supported configuration — see `config/secrets.development.shopify.yml` and `docs/setup.md`, which show multiple orgs configured under `github:`), and requires at least one of those organizations to have `webhook_secret` unset (explicitly called "optional" in the setup docs) or otherwise known to the attacker. This is a plausible real-world configuration for organizations onboarding Shipit incrementally, making likelihood moderate rather than purely theoretical.

### Recommendation
Bind the resolved GitHub App/organization used for `verify_signature` to the same identifier used later to select the target repository/stack, and refuse to treat "no secret configured" as an automatic pass when the payload's `repository.full_name` does not belong to that same organization. Concretely: derive the organization strictly from `repository.full_name`'s owner segment (single source of truth) rather than a separate `repository.owner.login`/`organization.login` field, and require a positive, per-organization signature match rather than defaulting to `true` when `webhook_secret` is blank.

### Proof of Concept
1. Shipit instance is configured with two organizations in `Shipit.github`: `attacker-org` (no `webhook_secret` set) and `victim-org` (has `victim-repo` stack tracked, with a configured `webhook_secret`).
2. Attacker (who only needs to be able to reach the public `/webhooks` endpoint — no Shipit session, no API token) sends:
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=anything

{
  "repository": { "owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo" },
  "after": "<attacker-chosen-sha>",
  "ref": "refs/heads/master"
}
```
3. `verify_signature` resolves `Shipit.github(organization: "attacker-org")`; since that org has no `webhook_secret`, `verify_webhook_signature` returns `true` regardless of the bogus `X-Hub-Signature` value. [5](#0-4) 
4. `create` dispatches the `push` handler using `repository.full_name == "victim-org/victim-repo"`, causing `GithubSyncJob`/deploy-triggering logic to run against `victim-repo`'s stacks as if GitHub itself had sent the event. [6](#0-5) [4](#0-3)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
