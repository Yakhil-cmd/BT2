### Title
Permanent unit-processing lockout via missing `assocUnitsInWork` cleanup in `ifNeedParentUnits` - (File: network.js)

### Summary
`handleJoint()` in `network.js` uses the in-memory map `assocUnitsInWork` as a mutual-exclusion gate so the same unit is never validated/saved twice concurrently. Every terminal validation outcome (`ifUnitError`, `ifJointError`, `ifTransientError`, `ifNeedHashTree`, `ifOk`, `ifOkUnsigned`) explicitly deletes the unit's entry from `assocUnitsInWork` before returning control. The `ifNeedParentUnits` callback, however, only deletes the entry inside the `if (bRequestPrunedContent && !bPosted)` branch. In the ordinary "parents simply not yet received" case (`bRequestPrunedContent` falsy — the overwhelmingly common outcome when a peer posts a unit whose parent hasn't propagated yet), the function returns without ever removing `unit` from `assocUnitsInWork`.

### Finding Description
`assocUnitsInWork[unit]` is set at the top of `handleJoint()`: [1](#0-0) 

and is the single re-entrancy check used across the whole codebase (peer joints, posted joints, resaved/queued joints all funnel through this gate — see the comment referencing `requestNewMissingJoints` relying on `checkIfNewUnit`): [2](#0-1) 

Compare the cleanup performed on every other validation branch: [3](#0-2) 

with `ifNeedParentUnits`, where the `delete assocUnitsInWork[unit]` statement is nested inside the pruned-content branch only: [4](#0-3) 

When a posted or received unit references a parent that is missing but not (locally) known to be pruned, `bRequestPrunedContent` is false, so the function calls `callbacks.ifNeedParentUnits(...)` and `unlock()` — but the unit's flag in `assocUnitsInWork` is never cleared. Once the missing parent eventually arrives and the dependency-resolution logic re-submits the original unit for handling (the whole point of `assocUnitsWaitingForPrunedContent`/dependency tracking is to let the unit be reprocessed once dependencies are satisfied), `handleJoint()` will immediately see `assocUnitsInWork[unit]` still truthy and short-circuit with `callbacks.ifUnitInWork()` at line 1161-1162, permanently refusing to actually validate/save that unit — the stale in-memory handle is never "unexported," exactly the class of defect described in the analog report (an object/handle that should have been released remains registered and is later dereferenced/acted upon incorrectly).

### Impact Explanation
Because the flag is process-lifetime (never expired, no TTL, no periodic sweep unlike other caches in this codebase such as `handledChainsCache`/`assocUnitsWaitingForPrunedContent`), any unit that once hit this exact branch can never be accepted again for the life of the node process, even after all of its parents are supplied. Any unit that legitimately spends the frozen unit's outputs, or otherwise depends on it in the DAG, likewise can never be confirmed by that node, which matches the accepted impact category "a network unable to confirm new units" — this occurs on the affected node without any privileged access, triggerable purely by an ordinary unit poster/peer through normal joint propagation timing.

### Likelihood Explanation
This path is reached by common, everyday events: a unit is received/posted whose parent has not yet arrived (an unprivileged unit poster or AA trigger sender only needs to have their unit relayed before its parent propagates, which routinely happens under normal network jitter, and can also be intentionally engineered by simply withholding/delaying the parent from the target node). No special peer/hub compromise is required — it is reachable from the same unprivileged "post a unit" surface explicitly in scope.

### Recommendation
In the `ifNeedParentUnits` callback of `handleJoint()`, unconditionally `delete assocUnitsInWork[unit]` (mirroring every other terminal callback) once the local joint has been queued/pended, or alternatively track and clear the flag as part of whatever mechanism re-queues the unit once its parents resolve, so the unit can be revalidated after its dependencies are eventually satisfied.

### Proof of Concept
1. Attacker (or a normal peer under adverse network timing) sends unit `A` to a node, whose `parent_units` includes unit `B` that the node does not yet have and does not consider "pruned" (`bRequestPrunedContent` = false, the default path for ordinary not-yet-downloaded parents).
2. `handleJoint(ws, A)` sets `assocUnitsInWork[A] = true`, validation calls `ifNeedParentUnits(['B'], false)`, and the function returns without clearing `assocUnitsInWork[A]`.
3. Later, `B` (and its ancestors) are received/validated/saved normally.
4. The dependency-resolution logic re-submits `A` for handling (this is the entire purpose of requesting the missing parent) — but `handleJoint(_, A)` immediately hits `if (assocUnitsInWork[A]) return callbacks.ifUnitInWork();` and never validates/saves `A`.
5. `A` (and any units built on top of it) can never be confirmed by this node for the remainder of its process lifetime. [1](#0-0) [4](#0-3)
