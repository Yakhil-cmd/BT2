### Title
Webhook signature verification validates an org-selected secret while the actual write target is taken from an unbound payload field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks a `Shipit::GitHubApp` (and therefore the HMAC secret used for verification) from `params.dig('repository','owner','login') || params.dig('organization','login')`, but every event handler (`Shipit::Webhooks::Handlers::Handler#stacks` / `#repository_name`) resolves the entity that is actually written to from a *different* payload field, `payload.dig('repository','full_name')`. The two fields are never cross-checked against each other. This is the same bug class as the reported "imprecise validation of deposit amounts": a guard is evaluated against one value (the org used to select/verify a secret) while the state-changing action is performed against a logically-independent value (the repository the write targets).

### Finding Description
`verify_webhook_signature` in `lib/shipit/github_app.rb` explicitly short-circuits to `true` when no `webhook_secret` is configured for the resolved organization: [1](#0-0) 

The controller resolves which app/secret to check *only* from `repository.owner.login` (or `organization.login`): [2](#0-1) [3](#0-2) 

Setup docs present `webhook_secret` as an optional field ("If you've set a webhook secret ... you should copy it here"), and multiple GitHub App organizations can be configured independently, each with its own optional secret: [4](#0-3) 

Meanwhile, every handler resolves the actual `Stack`/`Repository` being acted upon from `repository.full_name`, a field that is completely independent of the `owner.login`/`organization.login` field used during verification: [5](#0-4) 

For example, `PushHandler` triggers a `GithubSyncJob` for whatever stacks match `repository_name`: [6](#0-5) 

and `StatusHandler` creates a commit status (used in deployability checks) for any commit `sha` supplied in the payload, with no relation at all to `repository.owner.login`: [7](#0-6) 

**Binding broken (as an equality):** the engine's guard checks `verified(repository.owner.login)` but the write executes against `repository.full_name`. These are supposed to be the same repository/org, but nothing in the code enforces `repository.full_name`.split('/').first == repository.owner.login (or `organization.login`). If any configured organization in `secrets.github` has no `webhook_secret` set (a documented, supported configuration - see `docs/setup.md` above, and the multi-org example that repeats the same optional `webhook_secret:` key per org), `verify_webhook_signature` unconditionally returns `true` for a payload naming that organization as `repository.owner.login`/`organization.login`, regardless of the actual HMAC header. The attacker is then free to set `repository.full_name` to any other, fully-secured organization's repository that Shipit tracks, because that field is never checked against the field used for signature verification.

### Impact Explanation
An unprivileged, unauthenticated internet client (the `/webhooks` endpoint requires no session, `ApiClient` token, or any credential - it is intentionally public for GitHub to POST to) can, given knowledge of any org name configured in this Shipit instance without a `webhook_secret`, forge arbitrary webhook events against any *other* tracked repository/stack, including ones whose GitHub App does enforce a secret. Concretely:
- Forge `status` events (`StatusHandler`) to fabricate `success` commit statuses on arbitrary commit SHAs of a targeted stack, which feed directly into `Stack#deployment_checks_passed?`/deployability logic used to gate deploys — an unauthorized deploy vector.
- Forge `push` events (`PushHandler`) to force `GithubSyncJob` execution against arbitrary stacks.
- Forge `membership` events to add/remove arbitrary GitHub logins to/from `Shipit.github_teams`-backed `Team` records, which the `authorized?`/`force_github_authentication` authorization gate in `app/controllers/concerns/shipit/authentication.rb` relies on to grant application access.

This satisfies the "High" bar: escalation into `Shipit.github_teams` authorization and/or unauthorized deploy, achieved with zero credentials, purely by exploiting the mismatch between the field validated and the field acted upon.

### Likelihood Explanation
High. The only precondition is that at least one configured GitHub organization in `secrets.github` lacks a `webhook_secret` - a state the documentation itself presents as optional/default, and the multi-org configuration format is a first-class, documented feature. No credentials, sessions, or GitHub write access are required; the attacker only needs to know the target stack's `owner/repo` full name (public information for public repos) and the name of any org configured without a secret in this Shipit deployment.

### Recommendation
Bind the verified organization to the entity actually written:
- After selecting `repository_owner` for signature purposes, require that `payload.dig('repository','full_name')` (or `organization.login` for org-level events like `membership`) starts with the same, case-insensitively normalized `repository_owner` before dispatching to handlers.
- Do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is blank in production; require every configured organization to set a `webhook_secret`, or reject processing entirely if absent.
- In `Shipit::Webhooks::Handlers::Handler`, re-derive/validate `repository_name`'s owner against the same trust boundary used by `WebhooksController#verify_signature` rather than trusting it as an independent, unchecked field.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.github`: `trusted-org` (has `webhook_secret` set, hosts the real tracked stack `trusted-org/prod-repo`) and `no-secret-org` (no `webhook_secret` configured - a supported, documented setup).
2. Attacker sends, without any valid GitHub signature header, a `status` webhook POST to `/webhooks` with body:
```json
{
  "repository": { "owner": { "login": "no-secret-org" }, "full_name": "trusted-org/prod-repo" },
  "sha": "<sha-of-commit-under-review-in-trusted-org>",
  "state": "success",
  "context": "ci/required-check"
}
```
and header `X-Github-Event: status`.
3. `WebhooksController#verify_signature` resolves `Shipit.github(organization: 'no-secret-org')`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally - the request passes with no valid signature.
4. `StatusHandler#process` uses `params.sha`/`params.state` from the same payload to call `commit.create_status_from_github!`, marking the `trusted-org/prod-repo` commit as passing `ci/required-check`, even though the request was never actually signed by `trusted-org`'s GitHub App.
5. This forged status can satisfy `Stack#deployment_checks_passed?` for `trusted-org/prod-repo`, enabling an attacker-influenced/unauthorized deploy path with zero credentials.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
