### Title
Direct token transfers to the liquidity pool can become permanently stranded - (File: contracts/pool/src/lib.rs)

### Summary
The pool can hold more token balance than the sum of all market `cash` books, but exposes no entrypoint that can recover the unbooked excess. Direct donations do not increase `cash`; ordinary outbound paths are limited by the cash book, and every pool mutator is owner-only. Once all booked balances are withdrawn, donated excess remains inaccessible because no sweep or reconciliation path exists. [1](#0-0) [2](#0-1) 

### Finding Description
The pool treats token custody separately from market accounting: `transfer_out` sends tokens without checking whether the pool's actual balance exceeds tracked `cash`, while `debit_cash` rejects any transfer beyond the market's cash book. [2](#0-1) 

A user can directly call the token contract's `transfer(user, pool, amount)`. That transfer is accepted by the token contract and raises the pool's physical balance, but no pool entrypoint credits the amount to `cash` because `supply`, `repay`, and `recapitalize` are all owner-only and invoked only through the controller's measured-payment flows. [3](#0-2) [4](#0-3) 

The documented accounting model explicitly says direct donations do not increase booked cash, and multiple markets for the same token share one physical pool balance while maintaining separate books. [5](#0-4) 

### Impact Explanation
Tokens sent directly to the pool receive no supply shares, debt repayment credit, or revenue claim. They can temporarily serve as physical backing for later booked withdrawals, but they can never themselves become withdrawable through the cash book. After all booked `cash` for that token has been paid out, any excess physical balance remains stranded. This is permanent freezing of user funds. [6](#0-5) [7](#0-6) 

The issue also applies to token balances sent directly to the controller: its refund helper deliberately preserves any pre-existing controller balance and refunds only the positive balance delta created during an operation. [8](#0-7) 

### Likelihood Explanation
An unprivileged user can trigger this with a plain token transfer; no privileged role, malformed parameter, oracle failure, or external exploit is required. The likelihood depends on a user or integration mistakenly bypassing the controller and paying the pool directly, which is plausible because the pool is a normal token recipient. [9](#0-8) 

### Recommendation
Add an owner- or governance-authorized reconciliation path that can recover only the physical excess over the aggregate cash obligations for the same token across all hub markets. The recovery amount must be computed as something equivalent to:

```rust
recoverable = token.balance(pool) - sum(market.cash for every market using token)
```

Alternatively, route all recognized inbound transfers through a measured payment path and document that direct pool transfers are unrecoverable.

### Proof of Concept
1. Deploy or select a market for token `T`.
2. Through the normal controller path, have a supplier deposit `100 T`; the pool records `cash = 100` and holds `100 T`.
3. Call `T.transfer(attacker_or_user, pool, 7)` directly.
4. The pool's physical balance becomes `107 T`, while the market's `cash` remains `100`.
5. Have the supplier withdraw the full booked position. The pool debits all `100` cash and transfers `100 T`.
6. The pool still holds `7 T`, but `cash == 0`; `withdraw`, `borrow`, `claim_revenue`, and every other outbound path cannot transfer it because they are bound by booked claims or owner-only accounting.
7. The excess `7 T` remains stranded.

    /// Panics if cash reserves are below `amount`.
    pub(crate) fn require_reserves(&self, amount: i128) {
        assert_with_error!(
            self.env,
            self.cash >= amount,
            CollateralError::InsufficientLiquidity
        );
    }

    /// Increases accounting cash by `amount`. Rejects negative amounts and overflow.
    pub(crate) fn credit_cash(&mut self, amount: i128) {
        require_nonneg_amount(&self.env, amount);
        self.cash = self
            .cash
            .checked_add(amount)
            .unwrap_or_else(|| panic_with_error!(&self.env, GenericError::MathOverflow));
    }

    /// Decreases accounting cash by `amount`. Rejects negative amounts or
    /// insufficient reserves.
    pub(crate) fn debit_cash(&mut self, amount: i128) {
        require_nonneg_amount(&self.env, amount);
        self.require_reserves(amount);
        self.cash = self
            .cash
            .checked_sub(amount)
            .unwrap_or_else(|| panic_with_error!(&self.env, GenericError::MathOverflow));
    }

    /// Transfers `amount` of the market asset from the pool to `recipient`.
    ///
    /// Rejects negative amounts; zero is a no-op. Does not adjust accounting cash.

        if amount == 0 {

        tok.transfer(&self.env.current_contract_address(), recipient, &amount);

## Custody and accounting

The pool tracks cash in an accounting book. Supply, repayment, and
recapitalization credit the tokens actually received; direct donations do not
automatically increase booked cash. When a token delivers less than requested,
the pool books the smaller measured amount. Measurement cannot establish that an
arbitrary token is safe.

The same token can appear in multiple hubs. Its markets keep separate books
but share one physical pool balance. A malicious token contract can therefore
affect more than one market. See [token assumptions](../explanation/threat-model.md#token-assumptions).
