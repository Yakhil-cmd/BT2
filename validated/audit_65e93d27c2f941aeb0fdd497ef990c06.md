### Title
Webhook signature check binds the wrong organization to the repository actually written - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate a webhook against using `repository.owner.login` (falling back to `organization.login`), but the handlers that actually mutate application state (sync commits, statuses, trigger continuous deployment) select the target `Repository`/`Stack` using a *different* field, `repository.full_name`. Because Shipit supports multiple independently‑configured GitHub organizations, each with its own `webhook_secret` [1](#0-0) , an attacker who legitimately controls one onboarded organization's webhook secret can forge a raw POST to `/webhooks` whose `repository.owner.login` matches their own org (so signature verification passes with their secret) while `repository.full_name` names an entirely different, victim organization's repository that the handler acts on.

### Finding Description
`verify_signature` picks the GitHub App config to validate against purely from the payload's owner/organization login, not from anything cryptographically bound to the rest of the payload: [2](#0-1) [3](#0-2) 

The HMAC signature (`verify_webhook_signature`) only proves the raw body was signed with *some* organization's secret; it says nothing about which repository inside that body is legitimate for that organization: [4](#0-3) 

Once the request passes, `WebhooksController#create` dispatches the parsed JSON to the registered handlers for the event type: [5](#0-4) 

Handlers derive the actual `Stack`/`Repository` to operate on from a completely independent field of the same payload, `repository.full_name`: [6](#0-5) 

The push handler uses this to enqueue a `GithubSyncJob` keyed on the resolved stack and the attacker-supplied `after` SHA, as shown by the existing test expectation: [7](#0-6) 

Because `repository.owner.login` (used for auth) and `repository.full_name` (used for the write target) are two independent, unconnected fields of the same forgeable JSON body, an attacker who knows the `webhook_secret` of *any* organization configured on the instance (e.g., their own onboarded org) can sign a payload whose `owner.login` is their own org, but whose `repository.full_name`/commit data references a victim organization's stack. `verify_signature` will select and validate against the attacker's own org secret and succeed, then the handler will act on the victim's repository/stack.

This is the same class of bug as the reported PearVault issue: a value used for the authorization/verification decision (`user`/`owner` in PearVault, `repository.owner.login` in Shipit) is not the same value that the code subsequently trusts to decide whose funds/resources are affected (`receiver` in PearVault, `repository.full_name` in Shipit). The equality that should hold — "the organization whose secret authenticated this request" == "the repository this request is allowed to mutate" — is not enforced.

### Impact Explanation
An attacker controlling one onboarded organization's webhook secret can inject forged push/status/check_suite events attributed to an unrelated victim repository/stack hosted on the same Shipit instance. This lets them enqueue `GithubSyncJob` with attacker-chosen commit SHAs/metadata for the victim stack, and depending on the victim stack's `continuous_deployment` setting, this can drive an unauthorized deploy of attacker-influenced state — a cross-repository write and potentially an unauthorized deploy, matching the "Critical: cross-repository writes / unauthorized deploy" bar.

### Likelihood Explanation
This requires the attacker to know a `webhook_secret` for at least one organization configured on the shared Shipit instance — realistic in any multi-tenant deployment where multiple independent GitHub orgs are onboarded to one Shipit installation with per-org secrets, since org admins legitimately possess their own org's secret. No GitHub App private key, `api_clients_secret`, or Shipit session is required, satisfying the unprivileged-attacker requirement.

### Recommendation
Bind the field used to select the verification secret to the field used to select the write target: after selecting the GitHub App config via `repository_owner`, verify that `payload.dig('repository', 'owner', 'login')` (or `organization.login`) exactly matches the owner segment of `payload.dig('repository', 'full_name')` before dispatching to handlers, or better, resolve the target `Repository`/`Stack` by an ID/owner pair that is cross-checked against the same value used for signature-secret selection, rejecting the webhook if they diverge.

### Proof of Concept
1. Operator configures Shipit with two organizations, `attacker-org` and `victim-org`, each with its own `github.webhook_secret` (as documented in the multi-org config example).
2. Attacker, who administers `attacker-org` and knows its `webhook_secret`, crafts a JSON body:
   ```json
   {
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
     "after": "<attacker-chosen-sha>",
     "ref": "refs/heads/master"
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=<hmac>` using `attacker-org`'s known secret over this exact raw body.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"attacker-org"`, loads `Shipit.github(organization: "attacker-org")`, and the HMAC check succeeds. [8](#0-7) 
5. `PushHandler`/`Handler#stacks` resolves the target using `payload.dig('repository', 'full_name')` = `"victim-org/victim-repo"`, enqueuing a `GithubSyncJob` for the victim's stack with the attacker-chosen SHA. [6](#0-5)

## Creating the GitHub App

Shipit needs a GitHub App to authenticate users, receive Webhooks and access the API.

You can create a new one for your organization at `https://github.com/organizations/<your-org>/settings/apps/new`, or [https://github.com/settings/apps/new](https://github.com/settings/apps/new) for a regular user.

  - Homepage URL: The URL where Shipit will be deployed, e.g. `https://example.com`.
  - User authorization callback URL: It must be set to `<homepage>/github/auth/github/callback`, e.g. `https://example.com/github/auth/github/callback`.
  - Setup URL: Leave it empty.
  - Webhook URL: It must be set to `<homepage>/webhooks`, e.g. `https://example.com/webhooks`.
  - Webhook secret (optional): Fill it with some randomly generated string, and *keep it in clear on the side, you'll need it later*.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
