Found a directly analogous root cause: in `writer.js`, the `"poll"` message handler dereferences `poll.choices.length` while writing DB fields, exactly mirroring Bento4's `AP4_StszAtom::WriteFields` pattern of unconditionally reading a size/array field when serializing a parsed structure without confirming the field actually exists.

### Title
NULL/undefined dereference on `poll.choices` during unit commit crashes the node - (File: writer.js)

### Summary
`AP4_StszAtom::WriteFields` in Bento4 crashes because it writes out a sample-count-derived table without checking that the backing array actually exists/matches the declared count. The same "write fields assuming the collection is present" pattern exists in ocore's `writer.js`, in the code path that commits an already-hash-verified, accepted unit's `"poll"` message to the database.

### Finding Description
When a unit is validated and accepted, `writer.saveJoint` iterates over `objUnit.messages` and, for `message.app === "poll"`, executes:
```js
case "poll":
    var poll = message.payload;
    conn.addQuery(arrQueries, "INSERT INTO polls (unit, message_index, question) VALUES(?,?,?)", [objUnit.unit, i, poll.question]);
    for (var j=0; j<poll.choices.length; j++)
        ...
``` [1](#0-0) 
This code unconditionally reads `poll.choices.length`. It relies entirely on `validation.js` having verified beforehand that `payload.choices` is a non-empty array. If there is any path where `validateMessage`/`validateInlinePayload` accepts a `"poll"` message whose payload lacks a `choices` array (e.g. a mismatch between the payload-hash check, which only requires the JSON to hash to the declared `payload_hash`, and a permissive/incomplete field validator for the `"poll"` app, or an AA-emitted message that bypasses full field validation), `writer.js` will throw an uncaught `TypeError: Cannot read properties of undefined (reading 'length')` while inside the DB-write transaction of `saveJoint`.

This mirrors the Bento4 bug class precisely: the parser/validator establishes envelope/hash validity, but the writer trusts internal substructure (`choices` array) to exist without its own defensive check, exactly like `AP4_StszAtom::WriteFields` trusting the sample table without re-checking it.

Because `saveJoint` is invoked synchronously in the commit path for every unit that reaches this stage (in `validation.js`'s `ifOk` callback chain, shared by every full node processing the same unit), a crafted `"poll"` message that slips past `validatePayload`'s `"poll"` case but still hashes correctly would crash every full node that attempts to write the unit, not just one node — i.e., a network-wide processing halt on that unit rather than a single-node DoS, since all conforming nodes execute identical validation/writer logic on the same accepted unit.

### Impact Explanation
An uncaught exception inside `saveJoint`'s query-building step is not caught by any `try/catch` at that stage (unlike the payload-hash and unit-hash computation, which are wrapped in `try/catch` earlier in `validation.js`) [2](#0-1) . If reachable, this would abort the Node.js process for every honest node while it commits the unit, since all nodes execute the same deterministic validation+write logic and would either all crash or all get stuck retrying the same crash on catch-up — this matches the "network unable to confirm new units" impact category, rather than a mere single-node resource-DoS.

### Likelihood Explanation
This finding is **conditional and not fully proven** from the available index: I could not confirm within the reachable code that `validateInlinePayload`'s `"poll"` case (in `validation.js`) fails to enforce `isNonemptyArray(payload.choices)` before this message reaches the writer — that specific validator branch was not returned by search and could not be inspected here. If the validator does correctly enforce a non-empty `choices` array (which is the expected, standard behavior for well-maintained validation code, and consistent with the thorough validation style seen everywhere else in `validation.js`), then this specific gap does not exist and the writer code, while stylistically fragile (no defensive check mirroring Bento4's missing check), would not be reachable by an attacker.

### Recommendation
Regardless of whether the specific `"poll"` gap is provable, apply defense-in-depth consistent with the Bento4 fix (add an explicit bounds/existence check before writing): validate `Array.isArray(poll.choices) && poll.choices.length > 0` inside `writer.js`'s `"poll"` case before dereferencing `.length`, and audit all other `message.app` write-branches (`"vote"`, `"asset"`, `"asset_attestors"`, `"attestation"`) for the same "writer trusts validator" pattern, since a validation/writer field-name or shape mismatch in any of them would produce the identical uncaught-crash impact on every node.

### Proof of Concept
Not constructible with confidence from the available index: exploitation requires demonstrating a concrete unit whose `"poll"` payload lacks `choices` yet still passes `validateInlinePayload`'s poll-specific checks in `validation.js` (the exact validator branch for `"poll"` was not located in the accessible code during this investigation). Without confirming that gap, a working PoC cannot be produced; a Devin session with full repository access should inspect the `"poll"` case in `validation.js`'s `validateInlinePayload`/`validatePayload` switch to confirm or rule out the missing check before treating this as an exploitable, in-scope finding.
