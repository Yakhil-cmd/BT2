### Title
Webhook signature verification is unconditionally bypassed for any GitHub org configured without a `webhook_secret` - (File: lib/shipit/github_app.rb)

### Summary
`GitHubApp#verify_webhook_signature` returns `true` for any request whenever the organization's config hash has no `webhook_secret` set, regardless of the signature header or payload content. In a multi-tenant Shipit deployment where `github_apps`/`secrets.github` defines multiple organizations and only some of them configure a `webhook_secret`, any attacker can POST arbitrary/unsigned webhook payloads for the unsecured organization's repositories and have them processed as authentic.

### Finding Description
The broken binding: `verify_webhook_signature(signature, raw_post) == true` is claimed to imply `HMAC-SHA1(webhook_secret_of[repository_owner], raw_post) == signature`, but for orgs with `webhook_secret` blank/absent this equality never holds — the method short-circuits at `return true unless webhook_secret` in [1](#0-0) .

Path: `WebhooksController#verify_signature` resolves `github_app = Shipit.github(organization: repository_owner)` where `repository_owner` is taken directly from attacker-controlled `params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')` ( [2](#0-1) ). It then calls `github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)` and only sets a 422 status if unverified, but does not `return`/halt after `head(422)` ( [3](#0-2) ) — however this secondary bug is moot here because `verified` is `true` for unsecured orgs, so no 422 is even triggered. `Shipit.github(organization:)` builds a `GitHubApp` per-org from `secrets.github` config via `github_app_config(organization)` ( [4](#0-3) ), and `GitHubApp#initialize` sets `@webhook_secret = @config[:webhook_secret].presence`, which is `nil` if omitted/blank ( [5](#0-4) ).

Attacker request: POST `/webhooks` with `X-Github-Event: push` (or `status`/`pull_request`/`membership`/`check_suite`) and body `{"repository": {"owner": {"login": "<org-without-secret>"}, "full_name": "<tracked-repo>"}, ...}`, with any/no `X-Hub-Signature` header. Since that org has no `webhook_secret`, `verify_webhook_signature` returns `true` unconditionally, `verify_signature` never sets 422, and `#create` runs `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`, processing the forged payload as authentic for that org's stacks/repos/teams.

Existing guards do not stop this: `drop_unhandled_event` only filters unregistered event names, not authenticity; `check_if_ping` only handles `ping`; `GithubOrganizationUnknown` only triggers when the org isn't found in config at all — an org that IS configured but simply lacks `webhook_secret` passes right through.

### Impact Explanation
Any handler wired via `Shipit::Webhooks.for_event` (push → `GithubSyncJob` enqueue, status → `Status` creation, membership → `Team`/`Membership` mutation, pull_request/check_suite handlers) executes unauthenticated for every repository/organization configured without a `webhook_secret`. This is a full authentication bypass for that tenant's webhook surface — an unprivileged internet attacker can forge pushes, statuses, memberships, and CI check results, directly mutating Shipit's view of a stack's state (e.g., queuing deploys via sync, injecting fake CI status, adding/removing team memberships) without holding any secret. Repeatable indefinitely against every repository under that organization. Matches Critical severity as authentication bypass / unauthorized state mutation.

### Likelihood Explanation
Requires only that at least one org entry in Shipit's `github_apps`/`secrets.github` config omits `webhook_secret` — a realistic scenario in incremental multi-tenant rollouts where webhook secrets are configured per-org over time. No attacker secret, session, or token is needed; cost is a single unauthenticated HTTP POST.

### Recommendation
Change `verify_webhook_signature` to fail closed when `webhook_secret` is not configured (`return false unless webhook_secret`), and/or enforce at boot/config-validation time that every org entry with webhooks enabled must define a `webhook_secret`. Additionally, `verify_signature` should `return` immediately after `head(422)` instead of relying solely on setting response status (defense in depth, since `create` currently would still run even if headers were already rendered, depending on Rails behavior with `before_action` halting).

### Proof of Concept
Minitest under `test/controllers/webhooks_controller_test.rb`:
1. Configure a second org (e.g. `acme`) in test secrets/config with a `GitHubApp` whose `webhook_secret` is `nil` (mirrors production omission), tracking a stack under `acme/some-repo`.
2. `request.headers['X-Github-Event'] = 'push'`; build a push payload for `acme/some-repo` with `repository.owner.login == 'acme'`, no `X-Hub-Signature` header (or a garbage value).
3. `assert_enqueued_with(job: GithubSyncJob, args: [stack_id: acme_stack.id, expected_head_sha: payload['after']]) { post :create, body: payload.to_json, as: :json }` and `assert_response :ok`.
4. Assert both sides of the binding diverge: `Shipit.github(organization: 'acme').verify_webhook_signature('sha1=deadbeef', payload.to_json) == true` while `OpenSSL::HMAC.hexdigest('sha1', <no secret>, payload.to_json) != 'deadbeef'`, proving verification passed without validating the actual bytes.

    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

  end

  def github_organizations
