Found the analog: line 483 of `definition.js` gates the length check for `mci`/`age`/`timestamp` behind an MCI-based feature flag, meaning on older/other networks (or when `objValidationState.hasBall` is true and the retrievable MCI is below `pemCurvesFixMci`) the array-length check is skipped entirely and `args[0]`/`args[1]` are read unconditionally, similar to how the ath6kl WMI handlers read fixed offsets out of attacker-controlled buffers without validating length first.

### Title
Length check for `mci`/`age`/`timestamp` definition ops is conditionally skipped, allowing out-of-bounds array access - (File: definition.js)

### Summary
In `validateDefinition`'s `evaluate` function, the `mci`, `age`, and `timestamp` opcodes read `args[0]` (relation) and `args[1]` (value) from the unit's or asset's address-definition array. The array-length check `isArrayOfLength(args, 2)` is only enforced when an MCI-gated condition is true; otherwise the code proceeds directly to dereference `args[0]`/`args[1]` regardless of the actual shape of `args`.

Unlike sibling opcodes in the same switch (`definition template`, `seen definition change`/`has definition change`, `attested`, `in data feed`, `in merkle`, `has equal`/`has one equal`) which unconditionally call `isArrayOfLength`/`Array.isArray` before indexing, the `mci`/`age`/`timestamp` branch wraps the length check in an extra MCI condition (`last_ball_mci >= constants.pemCurvesFixMci` or the light/no-ball equivalent). When that condition is false — i.e., before the `pemCurvesFixMci` upgrade point, or for units validated without an established last-ball MCI context — the length check is bypassed entirely, and `args[0]`/`args[1]` are read from whatever value `args` happens to be (a non-array, a shorter array, `undefined`, or a string), which is directly attacker-supplied in the address/asset definition or oscript branch. `args[0]` on a string performs character-index access rather than throwing, and on `undefined` it throws a raw runtime `TypeError` inside the validation callback chain rather than returning a controlled validation error — this mirrors the ath6kl bug class of indexing into a buffer/array without first confirming its length is sufficient for the field being read (`arr[1]`, `arr[2]` style access without prior bounds validation), analogous to `ath6kl_wmi_pstream_timeout_event_rx`/`ath6kl_wmi_cac_event_rx` reading fixed offsets from an unchecked-length event payload.

### Impact Explanation
An unprivileged unit poster or AA trigger sender can craft an address/asset definition (or nested definition via `and`/`or`/`r of set`/`definition template`) containing an `mci`, `age`, or `timestamp` op whose `args` is not a proper 2-element array (e.g. a string, empty array, or single-element array) and submit it in a scenario where the MCI-gate condition fails to hold (e.g. during resolution of light-client requests or units processed with `objValidationState.hasBall` unset and a `last_ball_mci`/retrievable-MCI below `constants.pemCurvesFixMci`). This produces an uncaught exception deep in the async validation callback chain (`evaluate`) instead of a normal validation rejection. Because `validateDefinition`/`validateAuthentifiers` runs synchronously within the unit-validation pipeline used for every posted unit's address definitions and every AA's spending conditions, an unhandled exception here can crash the node process handling validation or cause it to diverge from other nodes that reach this code path under a different MCI-gate state, resulting in a denial of validation / node disagreement on unit validity.

### Likelihood Explanation
The `pemCurvesFixMci` gate suggests this behavior is a residual/legacy code path retained for backward compatibility with pre-upgrade units still being re-validated (e.g., historical unit replay, light wallets requesting proofs for old units, or testnets at lower MCI). Any node still processing units below that MCI threshold (or with `hasBall` unset and a low `getMinRetrievableMci()`) will hit the unguarded path when given crafted input, making this reachable by any address owner or AA author who structures a definition with a malformed `mci`/`age`/`timestamp` node, without needing special privileges.

### Recommendation
Remove the MCI condition from the length guard so that `isArrayOfLength(args, 2)` is enforced unconditionally for `mci`, `age`, and `timestamp`, matching the pattern used by every other multi-arg opcode in the same switch (`definition template`, `has/seen definition change`, `attested`, `in data feed`, `in merkle`). If backward compatibility with previously-stable units is a concern, apply the strict check only going forward (gate acceptance of new invalid shapes) while still defensively guarding the `args[0]`/`args[1]` reads (e.g., `Array.isArray(args) && args.length === 2`) to avoid throwing unhandled exceptions regardless of the MCI branch taken.

### Proof of Concept
1. Construct an address definition (or asset spend condition) containing `["mci", "notanarray"]` — i.e. `args = "notanarray"` (a string) instead of a 2-element array.
2. Submit a unit that references this address/asset definition for validation in a context where `objValidationState.last_ball_mci < constants.pemCurvesFixMci` (or `!objValidationState.hasBall && storage.getMinRetrievableMci() < constants.pemCurvesFixMci`), such as replay/validation of an older unit or asset.
3. Execution reaches `var relation = args[0]; var value = args[1];` without the `isArrayOfLength` check triggering, `relation` becomes `"n"` (first char of the string) and `value` becomes `"o"` rather than the intended numeric/relation fields, and `isNonemptyString`/`isNonnegativeInteger` checks fail in an unexpected way or, if `args` is `undefined`/`null`, `args[0]` throws a `TypeError`, propagating an unhandled exception through the `evaluate` callback chain used by unit validation.
