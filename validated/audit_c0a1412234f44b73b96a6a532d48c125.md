### Title
`StatusHandler` scopes commit lookup by SHA only, letting a webhook authenticated for one org set `state: success` on another org's `Commit`/`Stack`, triggering unauthorized continuous-deployment `Task` execution - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates a `status` webhook against the GitHub App configured for `repository_owner` taken from the payload's `repository.owner.login`, but `StatusHandler#process` never re-checks that owner/repository against the `Commit` it mutates — it matches purely by `params.sha` across the entire `commits` table. Because git commit SHAs are content-addressed and identical across forks, an attacker who controls a low-value org's webhook secret can name their own repository in the payload (passing signature verification) while pointing `sha` at a commit that actually belongs to a victim org's `Stack`, causing a `Status` with `state: 'success'` to be created on the victim's commit and potentially triggering that stack's continuous-deployment `Task`.

### Finding Description
The binding that should hold is: **repository/org authenticated by `verify_signature` (`repository_owner` from payload) == repository/org owning the `Commit` whose status is mutated.** Tracing the code shows this equality is never enforced for the `status` event.

- `WebhooksController#verify_signature` derives `repository_owner` solely from `params.dig('repository', 'owner', 'login')` (attacker-controlled JSON field) and validates the HMAC signature using `Shipit.github(organization: repository_owner).verify_webhook_signature`, i.e. against whichever GitHub App/org config matches that field. [1](#0-0) [2](#0-1) 

- Compare `PushHandler` and `CheckSuiteHandler`, which both scope their operations through `Handler#stacks`, resolving `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))` before touching any DB row — i.e., they tie the mutation to the payload's actual repository. [3](#0-2) [4](#0-3) [5](#0-4) 

- `StatusHandler`, in contrast, never calls `stacks`/`repository_name` at all. It matches `Commit.where(sha: params.sha)` globally, with no relation whatsoever to the payload's `repository`/`owner` fields that were just used for signature verification: [6](#0-5) 

- `Commit#create_status_from_github!` then creates a `Status` scoped to `stack_id` — the commit's *real*, pre-existing stack, not anything derived from the attacker's payload: [7](#0-6) 

- `Status` creation triggers `enable_ci_on_stack` and, on commit, `schedule_continuous_delivery` on the commit, which enqueues `ContinuousDeliveryJob` for `stack` if `deployable? && stack.continuous_deployment? && stack.deployable?`: [8](#0-7) [9](#0-8) [10](#0-9) 

- `Stack.trigger_continuous_delivery` → `trigger_deploy` builds and enqueues a `Deploy` (a `Task` subclass) that ultimately runs `Task#start`/`Command#start` with the victim stack's own `GITHUB_TOKEN`/deploy environment: [11](#0-10) 

**Exploit flow**: Attacker owns `attacker-org/some-repo` (a Shipit-configured org with a webhook secret the attacker knows because they set up that low-value org's GitHub App/secret themselves, or it's shared/misconfigured per the question's premise). Attacker learns (via public GitHub API/UI) a commit SHA `S` that is present in a victim org's tracked `Stack` (e.g. from a fork, since content-addressed SHAs are identical pre-divergence, or simply by reading the victim's public commit history). Attacker POSTs to `/webhooks` with header `X-Github-Event: status`, a valid HMAC computed with `attacker-org`'s webhook secret, and body:
```json
{"repository": {"owner": {"login": "attacker-org"}}, "sha": "S", "state": "success"}
```
`verify_signature` passes because it only checks the attacker-controlled `attacker-org` binding, and `StatusHandler` then creates a `success` `Status` on the victim's `Commit` (matched purely by SHA), scoped to the victim's real `stack_id`.

**Why guards fail**: `verify_signature` authenticates *the sender/org named in the payload*, not *the record being mutated*. `drop_unhandled_event` and `ExplicitParameters` (`StatusHandler.params`) only validate shape (`sha`, `state`, etc.), not ownership. `force_github_authentication`/`User#authorized?`/`require_permission!` are irrelevant here — this is a webhook path with no user session. No model validation on `Status`/`Commit` cross-checks `stack.repository` against any payload-owner field, since none is ever passed into the query.

### Impact Explanation
A successful request causes a `Status` (`state: success`) to be written for a `Commit`/`Stack` belonging to an org the attacker never authenticated against, and — if that stack has `continuous_deployment` enabled and the commit is otherwise `deployable?` — enqueues `ContinuousDeliveryJob` → `Stack#trigger_deploy` → a `Task`/`Deploy` that runs deploy commands (`Task#start`/`Command#start`) using the victim stack's own GitHub token/deploy credentials. This is a cross-tenant authentication-bypass write (a record mutated for a repository/org that did not authenticate the request) with potential unauthorized-deploy execution, matching the Critical category ("payload for one repository mutating another's stack/commit/task", "an unauthorized deploy"). The attack is repeatable against any commit SHA the attacker can discover, for any stack with `continuous_deployment: true`, as long as the attacker controls one org's webhook secret in the same Shipit installation.

### Likelihood Explanation
Preconditions: (1) Shipit must host multiple orgs' stacks (a common multi-tenant configuration, explicitly supported per `config/secrets.development.example.yml`'s multi-org schema), (2) the attacker must control (own, or have configured) at least one such org's GitHub App/webhook secret — a low bar since it can be their own throwaway org, (3) the attacker must know a valid commit SHA tracked by a victim `Stack` — trivial for public repos or forks, (4) the victim stack must have `continuous_deployment: true` for the RCE-adjacent deploy chain, though the cross-tenant `Status` write itself (record for a repo that didn't authenticate it) is achievable regardless of that flag. Cost per attempt is a single crafted HTTP POST with a correctly-signed HMAC using a secret the attacker legitimately possesses. This is fully repeatable and requires no privileged Shipit role, session, or victim secret.

### Recommendation
In `StatusHandler#process` (and any other handler that queries by SHA/branch alone), scope the `Commit` lookup through the same `stacks`/`Repository.from_github_repo_name(repository_name)` resolution used by `PushHandler`/`CheckSuiteHandler`, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or `Commit.joins(:stack).merge(stacks).where(sha: params.sha)`, ensuring the commit's stack's repository matches the payload's `repository.full_name` that was authenticated by `verify_signature`.

### Proof of Concept
Add to `test/controllers/webhooks_controller_test.rb` (or a new model-level minitest):
```ruby
test ":status webhook signed for org A must not create a Status on a commit belonging to org B's stack" do
  victim_stack = shipit_stacks(:shipit) # belongs to "shopify" org fixture
  victim_commit = shipit_commits(:first)
  victim_stack.update!(continuous_deployment: true)

  request.headers['X-Github-Event'] = 'status'
  # Signature verified only for "attacker-org", not for victim_stack's owner
  GithubHook.any_instance.stubs(:verify_signature).returns(true) # or stub Shipit.github(organization: 'attacker-org')

  payload = {
    'repository' => { 'owner' => { 'login' => 'attacker-org' } },
    'sha' => victim_commit.sha,
    'state' => 'success'
  }.to_json

  assert_no_difference -> { victim_commit.reload.statuses.count } do
    assert_no_enqueued_jobs(only: Shipit::ContinuousDeliveryJob) do
      post :create, body: payload, as: :json
    end
  end

  # Equality check: repository_owner authenticated ('attacker-org')
  # must equal victim_stack's actual repository owner for the write to be allowed.
  refute_equal 'attacker-org', victim_stack.repository.owner
end
```
This test currently fails against the existing `StatusHandler` (the `Status` is created and `ContinuousDeliveryJob` is enqueued) because `Commit.where(sha: params.sha)` ignores the payload's `repository`/owner entirely, confirming the broken binding.
