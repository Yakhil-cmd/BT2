## Title
Webhook signature is verified against the organization derived from `repository.owner.login`/`organization.login`, but the repository actually written to is taken unchecked from `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
Shipit supports multi-tenant GitHub App configuration, where each GitHub organization has its own `webhook_secret` [1](#0-0) . `WebhooksController#verify_signature` selects which organization's `webhook_secret` to verify the inbound `X-Hub-Signature` against by reading `repository.owner.login` (falling back to `organization.login`) straight out of the *unverified* JSON body [2](#0-1) . However, once the signature check passes, the dispatched handler (e.g. `PushHandler` via the shared `Handler#repository_name`) resolves the target repository/stack using a *different* field of the same payload, `repository.full_name`, with no cross-check against `repository.owner.login` [3](#0-2) [4](#0-3) .

### Finding Description
The equality that should hold is: **organization authenticated == repository written**. It does not.

- `verify_signature` computes `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` and uses it only to pick which `Shipit.github(organization:)` (and hence which `webhook_secret`) validates the HMAC signature [5](#0-4) .
- `GitHubApp#verify_webhook_signature` explicitly returns `true` (skips verification) when no `webhook_secret` is configured for that organization: `return true unless webhook_secret` [6](#0-5) . The example/dummy multi-org configs in this repo even ship with `webhook_secret: # nil` for each org [7](#0-6) , and `docs/setup.md` explicitly marks `webhook_secret` as optional [8](#0-7) .
- After the signature gate, `create` simply does `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [9](#0-8) . The base `Handler#stacks`/`#repository_name` methods used by every handler (push, status, check_suite, pull_request, membership) derive the acted-upon repository purely from `payload.dig('repository', 'full_name')`, looked up via `Repository.from_github_repo_name` [3](#0-2) [10](#0-9) .

Because `repository.owner.login` (used for the signature-organization selection) and `repository.full_name` (used for the actual write target) are two independently attacker-supplied strings in the same unauthenticated JSON body, there is nothing forcing them to agree. An attacker who can post to `/webhooks` (a public, unauthenticated endpoint by design — protection comes only from the signature) can set `repository.owner.login` (or `organization.login`) to any organization known to be configured **without** a `webhook_secret` (or one whose secret has otherwise leaked), while setting `repository.full_name` to `victim-org/victim-repo`, a completely different, secret-protected organization/stack tracked by this Shipit instance. `verify_signature` will pass (no secret ⇒ auto-true), and the handler will then act on the victim's stack.

### Impact Explanation
This crosses the "organization authenticated vs. repository written" trust boundary called out in scope, without requiring any Shipit session, `ApiClient` token, or `webhook_secret`/`api_clients_secret` knowledge for the *victim* organization — only for a `webhook_secret`-less (or otherwise weakly-configured) org that is *also* hosted on the same Shipit instance. Concretely, via the `push` event this forges `Stack#sync_github(expected_head_sha: <attacker chosen sha>)` against the victim's stack, injecting/advancing the recorded commit history for a repository the attacker has no legitimate access to [4](#0-3) . Because Shipit's deploy pipeline (including continuous deployment, `stack.trigger_deploy`) operates off the recorded commit list, forging sync state for a target stack can be leveraged toward an unauthorized deploy against a repository the caller does not control — matching the "unauthorized deploy" Critical impact category.

### Likelihood Explanation
Requires the operator to run this engine in the documented multi-organization mode with at least one org lacking a `webhook_secret` (a configuration explicitly presented as valid/optional in `docs/setup.md` and the shipped example configs) while other orgs on the same instance are meant to be protected. This is a realistic, encouraged deployment shape for multi-tenant Shipit instances, and requires zero credentials from the attacker — only knowledge of one org name with no secret and the target's `owner/name`, both of which are typically public GitHub organization/repo names.

### Recommendation
Do not let `repository.full_name` (or any other repository identifier used for the actual write) be trusted independently of the identifier used to select the verifying organization. Concretely:
1. In `WebhooksController#verify_signature`, derive the verifying organization strictly from the same repository identifier the handlers will use (`repository.full_name`'s owner segment), and reject the request if `repository.owner.login`/`organization.login` disagrees with the owner segment of `repository.full_name`.
2. Alternatively, once the organization used for verification is determined, pass it explicitly into `Shipit::Webhooks.for_event(...).call(params)` and have `Handler#repository_name`/`#stacks` refuse to act on any repository whose owner doesn't match the verified organization.
3. Stop treating a missing `webhook_secret` as an implicit "verification passed" for any organization that also shares an instance with organizations that do configure a secret; at minimum, warn/fail loudly when mixed-security multi-org configs are detected.

### Proof of Concept
Preconditions: A Shipit deployment configured for multiple GitHub organizations per `docs/setup.md`'s "Using Multiple Github Applications" section — e.g. `OrgA` with no `webhook_secret` configured, and `victim-org` (secured, tracked stacks) with a real `webhook_secret`.

1. Attacker (no Shipit account, no token) sends:
```
POST /webhooks HTTP/1.1
X-Github-Event: push
X-Hub-Signature: sha1=0000000000000000000000000000000000000000   (any value; ignored)

{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha40>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "victim-org/victim-repo"
  }
}
```
2. `WebhooksController#verify_signature` computes `repository_owner = "OrgA"`, calls `Shipit.github(organization: "OrgA")`, and since `OrgA` has no `webhook_secret`, `verify_webhook_signature` returns `true` immediately regardless of the bogus `X-Hub-Signature` header [6](#0-5) .
3. Request proceeds to `create`, which dispatches to `PushHandler` [11](#0-10) .
4. `PushHandler#process` resolves `stacks` via `Handler#repository_name`, which reads `payload.dig('repository','full_name')` = `"victim-org/victim-repo"` — a completely different org than the one used for signature verification — and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha40>")` on every matching, not-archived stack on `main` [12](#0-11) [3](#0-2) .

Note on verification limits: I confirmed the code paths for signature selection, the "no-secret ⇒ verified" behavior, and the handler's independent repository-resolution logic directly from source. I was not able to execute the engine to empirically confirm the full downstream effect of a forged `sync_github` call on deploy triggering in this sandbox — that end-to-end behavioral confirmation would need to be run in a live/test Shipit instance.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
