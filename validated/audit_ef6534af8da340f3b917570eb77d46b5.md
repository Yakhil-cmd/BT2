Based on my investigation, I found a solid analog to the invite-acceptance race condition in the pairing-secret acceptance flow.

### Title
Race Condition in One-Time Pairing Secret Acceptance Allows Multiple Devices to Pair Using a Single-Use Secret - (File: `device.js`)

### Summary
`handlePairingMessage()` in [1](#0-0)  checks whether a `pairing_secret` is valid, then only *afterwards* deletes it. There is no lock or atomic check-and-delete, so two concurrent `pairing` device messages carrying the same one-time secret can both pass validation before either delete executes.

### Finding Description
`handlePairingMessage(json, device_pubkey, callbacks)` is invoked from `handleMessage`/`handle_message_from_hub` for any incoming device message with `subject: "pairing"`, which is explicitly whitelisted for non-correspondents at [2](#0-1) . The handler performs:

1. A `SELECT is_permanent FROM pairing_secrets WHERE pairing_secret IN(?,'*') AND expiry_date>NOW() ...` to confirm the secret is still valid: [3](#0-2) .
2. If found, it inserts/updates `correspondent_devices` for the sender and, only for non-permanent secrets, later runs `DELETE FROM pairing_secrets WHERE pairing_secret=?` to invalidate it: [4](#0-3) .

There is no mutex (e.g. `mutex.lock`) protecting this "check-then-delete" sequence, and no transaction wraps the SELECT and the eventual DELETE together. Two `pairing` messages arriving concurrently (e.g., from two different device pubkeys, or replayed/duplicated by a hub) with the same one-time `pairing_secret` will both pass the `SELECT` before either reaches the `DELETE`, because the row is still present and unexpired. Both senders will be added as confirmed correspondents via the `INSERT ... INTO correspondent_devices` / `UPDATE ... is_confirmed=1` statements, even though the pairing secret was meant to authorize exactly one device to pair.

This mirrors the reported CVE-2024-2913 pattern: a single-use token's validity check and its invalidation are not atomic, so concurrent requests can both consume it.

### Impact Explanation
A pairing secret is meant to grant chat/wallet-pairing trust to a single intended recipient device. Successful pairing causes `correspondent_devices.is_confirmed=1`, which is the trust gate used elsewhere (e.g., `wallet.js` message handling gates such as `create_new_shared_address`, `approve_new_shared_address`, `new_wallet_address`, `new_shared_address` shown in [5](#0-4) ) to accept further wallet/multisig-related device messages from that device as a legitimate correspondent. Because the race lets an unintended second device pair using the same one-time secret, that second device becomes a confirmed correspondent and can subsequently participate in shared/multisig wallet setup flows (`wallet_defined_by_addresses.js`, `wallet_defined_by_keys.js`) intended only for the legitimately paired party, potentially being included as an unintended cosigner in wallet definitions the user did not choose, an authorization bypass that can lead to loss of exclusive control over shared funds.

### Likelihood Explanation
This is reachable by any external device/peer that learns or intercepts the pairing secret (e.g., via URI scan sharing, timing, or hub relay duplication) and races two `pairing` messages to the target's hub within the narrow window between the `SELECT` and `DELETE`. No privileged access to the hub or the node itself is required; the attacker only needs to be able to send `hub/message` justsaying messages, which is standard client behavior.

### Recommendation
Wrap the pairing-secret validation and invalidation in a single atomic operation, e.g., perform `DELETE FROM pairing_secrets WHERE pairing_secret=? AND is_permanent=0 AND expiry_date>NOW()` first and check the affected-row count (or use a `mutex.lock([pairing_secret])`/serializable transaction spanning both the SELECT and DELETE) before proceeding to add the correspondent, so only the first request that observes the secret as valid can consume it.

### Proof of Concept
1. Device A calls `startWaitingForPairing` to generate a one-time `pairing_secret` and shares the resulting pairing code (e.g., via QR/URI as parsed in [6](#0-5) ) intending only device B to use it.
2. An attacker device C also learns/guesses/observes the same `pairing_secret` before B pairs.
3. B and C send `pairing` device messages with the identical `pairing_secret` to A's hub at nearly the same time.
4. Both requests reach `handlePairingMessage` concurrently on A's node; both `SELECT` queries return the still-valid row before either `DELETE FROM pairing_secrets` executes.
5. Both B and C get inserted/updated with `is_confirmed=1` in `correspondent_devices`, and only one `DELETE` succeeds afterward — but both devices are now confirmed correspondents from a secret intended for a single recipient.

function handlePairingMessage(json, device_pubkey, callbacks){
	var body = json.body;
	var from_address = objectHash.getDeviceAddress(device_pubkey);
	if (!ValidationUtils.isNonemptyString(body.pairing_secret))
		return callbacks.ifError("correspondent not known and no pairing secret");
	if (!ValidationUtils.isNonemptyString(json.device_hub)) // home hub of the sender
		return callbacks.ifError("no device_hub when pairing");
	if (json.device_hub.length > 200)
		return callbacks.ifError("device_hub too long");
	if (!network.isValidWsUrl(conf.WS_PROTOCOL + json.device_hub))
		return callbacks.ifError("invalid device_hub URL");
	if (!ValidationUtils.isNonemptyString(body.device_name))
		return callbacks.ifError("no device_name when pairing");
	if (body.device_name.length > 100)
		return callbacks.ifError("device_name too long");
	if ("reverse_pairing_secret" in body && !ValidationUtils.isNonemptyString(body.reverse_pairing_secret))
		return callbacks.ifError("bad reverse pairing secret");
	eventBus.emit("pairing_attempt", from_address, body.pairing_secret);
	db.query(
		"SELECT is_permanent FROM pairing_secrets WHERE pairing_secret IN(?,'*') AND expiry_date>"+db.getNow()+" ORDER BY (pairing_secret=?) DESC LIMIT 1", 
		[body.pairing_secret, body.pairing_secret], 
		function(pairing_rows){
			if (pairing_rows.length === 0)
				return callbacks.ifError("pairing secret not found or expired");
			// add new correspondent and delete pending pairing
			var safe_device_name = body.device_name.replace(/<[^>]*>?/g, '');
			db.query(
				"INSERT "+db.getIgnore()+" INTO correspondent_devices (device_address, pubkey, hub, name, is_confirmed) VALUES (?,?,?,?,1)", 
				[from_address, device_pubkey, json.device_hub, safe_device_name],
				function(){
					db.query( // don't update name if already confirmed
						"UPDATE correspondent_devices SET is_confirmed=1, name=? WHERE device_address=? AND is_confirmed=0", 
						[safe_device_name, from_address],
						function(){
							db.query("UPDATE correspondent_devices SET is_blackhole=0 WHERE device_address=?", [from_address], function(){
								eventBus.emit("paired", from_address, body.pairing_secret);
								if (pairing_rows[0].is_permanent === 0){ // multiple peers can pair through permanent secret
									db.query("DELETE FROM pairing_secrets WHERE pairing_secret=?", [body.pairing_secret], function(){});
									eventBus.emit('paired_by_secret-'+body.pairing_secret, from_address);
								}
								if (body.reverse_pairing_secret)
									sendPairingMessage(json.device_hub, device_pubkey, body.reverse_pairing_secret, null);
								callbacks.ifOk();
							});
						}
					);
				}
			);
		}
	);
}
