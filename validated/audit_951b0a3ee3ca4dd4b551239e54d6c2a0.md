## Analysis

The reported bug class is: a fixed/hardcoded operation (`_current.withdraw(address(jpeg))`) that always reverts once the target has "blacklisted" that specific asset, permanently breaking a critical code path (strategy migration) and locking funds. The reachable analog in ocore is in the Autonomous Agent (AA) message-composition pipeline, `aa_composer.js`, function `handleTrigger` → `sendUnit`, where a payment message for a non-base asset is unconditionally rejected if the asset happens to be private — a static, immutable asset property fixed at asset-definition time, exactly like JPEG being permanently blacklisted in the strategy. [1](#0-0) 

If the asset is private, `cb("sending private asset from AA")` is returned, which propagates to `bounce(err)` for the whole trigger unit [2](#0-1) . Since `is_private` is set once at asset definition and cannot be changed afterward (validated in `validateAssetDefinition`), [3](#0-2)  any AA logic that is designed to distribute or pay out such an asset (e.g., an AA that manages/wraps a privately-defined asset selected via `var[]` state, `trigger.data`, or a formula) will deterministically and permanently fail every single time that code path executes, always ending in `bounce`. Any balance of that private asset the AA already holds becomes permanently unpayable through that logic branch, functionally freezing AA funds analogous to the Controller/Strategy migration being permanently bricked by the blacklisted JPEG withdraw.

### Title
AA payment logic permanently and irrecoverably bounces when the target asset is private, freezing AA funds - (File: aa_composer.js)

### Summary
`aa_composer.js`'s `sendUnit()` hardcodes a rejection of any AA-composed payment message whose asset is private (`objAsset.is_private`). Because `is_private` is an immutable, asset-definition-time property, any AA whose logic branch pays out a state-selected or trigger-selected asset that turns out to be private will always bounce on that branch, with no way for the AA author or a user to recover the funds through that logic path — mirroring the JPEG'd Controller/Strategy bug where a hardcoded withdrawal call always reverts against a blacklisted, immutable-condition asset.

### Finding Description
When an AA composes a response unit, `sendUnit()` iterates over the template's `messages` array. For non-base payment messages it loads the asset info via `storage.loadAssetWithListOfAttestedAuthors` and then applies:
```
if (objAsset.is_private) // it'll fail validation anyway due to lack of spend_proofs
    return cb("sending private asset from AA");
``` [4](#0-3) 

Any error from this per-message callback bubbles to the `async.eachSeries` completion handler, which calls `bounce(err)` for the entire unit — discarding *all* other successful messages in the same trigger response, not just the one payment [2](#0-1) .

The check exists because private-asset transfers require `spend_proofs`, which AA-generated units cannot produce, so `validatePayment`/`validatePaymentInputsAndOutputs` would reject the unit anyway [5](#0-4) . However, `is_private` is fixed forever once an asset is defined [3](#0-2) , so this isn't a transient condition — it is a permanent, asset-level property that an AA author may not control if the asset is chosen dynamically (e.g., a factory/vault-style AA that reads the target asset from `trigger.data`, `var[]` state, or another AA's response, similar in spirit to the JPEG'd `Controller` selecting a strategy-controlled asset for withdrawal). Once such an asset is selected and becomes "the" payout asset for that logic branch, every trigger that lands on that branch will deterministically bounce, and any balance of that asset already held by the AA can never be paid out through that branch.

### Impact Explanation
This causes permanent freezing of AA funds: bytes/asset previously sent to the AA (and any balance of the private asset the AA holds) become unspendable via the affected logic branch because the failure condition (`is_private`) can never change. Every trigger that would exercise this path is bounced, refunding senders their trigger outputs minus bounce fees each time, but the AA's own stored balance of the private asset stays permanently stuck since it can never be composed into a valid outgoing payment through that branch. This matches the "AA fund loss or freezing" impact class.

### Likelihood Explanation
Likelihood is moderate: it requires an AA design where the asset to be paid is not a fixed public asset known and vetted at definition time, but is selected dynamically (via `trigger.data.asset`, a `var[]` state variable set from a prior response/asset-issuance message, or `params`). This is a realistic and common AA pattern (asset-factory or asset-router AAs, similar to vault/strategy contracts choosing among managed tokens), and unlike Solidity, oscript AA definitions are immutable once deployed, so there is no way to patch the logic after the fact — only future triggers on that branch keep failing.

### Recommendation
Before composing a payment message for a non-base asset in `sendUnit()` (or ideally earlier, when a user/AA-selectable asset is captured into state), explicitly check `objAsset.is_private` and, if true, execute an alternative, well-defined failure/refund path (e.g., a dedicated `state` update or a message documented as a controlled rejection) rather than an implicit trigger-level `bounce` that discards the whole response. Additionally, AA definitions that accept asset identifiers from `trigger.data` or from other dynamic sources should be validated/guided to reject private assets at the point of selection (e.g., in the `if`/`init` formula) so the branch is never entered for un-payable assets, and any funds already credited under that asset can be surfaced via a getter/withdrawal branch that doesn't hard depend on paying out the private asset itself.

### Proof of Concept
1. Deploy an AA whose logic, on a `define`-type trigger, defines (or is pointed at) an asset via `payload.is_private` (directly, or by reading an existing private asset's unit hash from `trigger.data.asset`) and stores it as `var['payout_asset']`.
2. On a subsequent "claim/withdraw" trigger, the AA composes:
```
{ app: 'payment', payload: { asset: "{var['payout_asset']}", outputs: [...] } }
```
3. Any trigger that lands on this branch causes `sendUnit()` to hit `objAsset.is_private === true`, return `cb("sending private asset from AA")`, and the whole response bounces (per `aa_composer.js:1329-1330` and `1346-1348`).
4. Because `is_private` can never be un-set on that asset, every future trigger reaching this branch bounces identically, and any balance of that asset already credited to the AA remains permanently unpayable through this branch — funds are frozen with no code-level remediation possible short of redeploying a new AA (losing the original AA's held balance).
