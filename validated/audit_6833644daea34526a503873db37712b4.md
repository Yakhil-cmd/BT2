## Confirmed: `status` webhook handler binds by commit SHA globally, not by verified repository — cross-repository forged CI status

### Title
Webhook signature verified against `repository.owner.login`, but `status`/`push` handlers act on `repository.full_name` and global SHA lookup — allows cross-repository CI status/push forgery ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
Shipit supports multi-organization configuration, where each GitHub organization has its own `webhook_secret` [1](#0-0) . `WebhooksController#verify_signature` selects which organization's secret to HMAC-verify the raw payload against using `repository_owner`, computed as `params.dig('repository', 'owner', 'login')` (or `organization.login`) [2](#0-1) . Once verified, event handlers instead use a *different* field of the same attacker-controlled JSON body — `payload.dig('repository', 'full_name')` in the generic `Handler#repository_name` [3](#0-2)  — to resolve which `Repository`/`Stack` the event applies to. Nothing ties `repository.full_name` to `repository.owner.login`; the org whose secret authenticates the request is not enforced to be the org whose repository is written.

Worse, `StatusHandler` doesn't even use `repository_name`/`full_name` scoping at all: it looks up commits **globally by SHA** across the entire installation and writes a `Status` on any matching commit for any stack: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [4](#0-3) .

### Finding Description
The binding that should hold is: **organization that authenticated the webhook (`repository.owner.login`, used to pick the `webhook_secret`) == the repository/stack that the event is applied to**. This is exactly the class of bug from the report — a value trusted/enforced at one checkpoint (the GoldenEggFee set before mint conclusion) can be manipulated to bypass the intended protection because the enforcement point and the effect point are decoupled.

Here:
- Signature verification: `Shipit.github(organization: repository_owner)` where `repository_owner = params.dig('repository','owner','login')` [2](#0-1) .
- Event dispatch/effect: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` passes the *entire raw JSON* to handlers [5](#0-4) , and handlers resolve target repositories from `repository.full_name` [3](#0-2) , or in the `status` case from a bare SHA lookup with no owner/repo scoping whatsoever [4](#0-3) .

An attacker who legitimately administers **any one** GitHub organization onboarded to this Shipit instance (and therefore knows that org's own `webhook_secret`, which they set up themselves during GitHub App installation) can craft a raw JSON body where:
- `repository.owner.login` = their own org (so `verify_signature` selects their own known secret and the HMAC check passes), and
- `repository.full_name` = `"victim-org/victim-repo"`, or (for `status` events) simply `sha` = a real commit SHA belonging to a completely unrelated victim stack.

Because the signature covers the raw body they fully control, they can compute a valid HMAC using their own secret over this forged payload. The request passes `verify_signature`, and the handler then acts on the victim repository's stack/commit.

### Impact Explanation
For the `status` event this is unauthenticated (from the victim's perspective) **forged CI status injection** for any commit in any stack in the instance: an attacker can create a `Status` with `state: "success"` for a required CI context on a victim's commit [6](#0-5) . Status creation directly triggers `schedule_continuous_delivery` [7](#0-6)  and `stack.schedule_merges if new_status.pending? || new_status.success?` [8](#0-7) , which can cause an **unauthorized deploy or merge** of a commit that never actually passed CI on stacks with `continuous_deployment` or merge-queue enabled — matching the Critical impact bar ("unauthorized deploy, rollback or merge").

For `push`/`check_suite` events, the forged `full_name` lets the attacker trigger `stack.sync_github(expected_head_sha: ...)` or `RefreshCheckRunsJob` against a victim's stack [9](#0-8) , causing spurious/DoS-adjacent resyncs — lower severity but still a repository-authentication mismatch.

### Likelihood Explanation
Exploitability requires the attacker to control at least one GitHub organization already onboarded into the target Shipit instance's multi-org config (so they know that org's `webhook_secret`, which they configure themselves). This is a realistic scenario for any Shipit deployment serving multiple orgs/teams (the documented multi-org config format explicitly supports this [1](#0-0) ). No Shipit session, API token, or GitHub write access to the victim repo is needed — only the ability to POST directly to the `/github/webhooks` endpoint with a self-signed payload, bypassing GitHub entirely.

### Recommendation
Enforce that the organization whose secret verified the signature matches the organization actually acted upon by handlers:
- In `WebhooksController#verify_signature`, after selecting `github_app` via `repository_owner`, also validate that `payload.dig('repository','full_name')`'s owner segment equals `repository_owner` before dispatching.
- In `StatusHandler`, scope `Commit.where(sha: ...)` to commits belonging to stacks under the verified `repository_owner`/`full_name`, rather than a global SHA lookup.
- More generally, thread the verified organization through to `Handler#repository_name`/`stacks` so no handler can act on data whose repository ownership was never authenticated.

### Proof of Concept
1. Attacker owns/administers GitHub org `attacker-org`, onboarded to the Shipit instance with a known `webhook_secret_A` (they configured it themselves in the GitHub App settings).
2. Victim's Shipit instance also serves `victim-org/victim-repo`, with a real commit `sha=deadbeef...` currently showing CI as failing/pending, and `continuous_deployment: true` or merge-queue enabled.
3. Attacker builds a `status` event JSON body:
```json
{
  "sha": "deadbeef...",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(webhook_secret_A, raw_body)>`.
5. POST to `/github/webhooks` with `X-Github-Event: status`.
6. `verify_signature` resolves `repository_owner = "attacker-org"`, fetches `webhook_secret_A`, verification succeeds [10](#0-9) .
7. `StatusHandler#process` runs `Commit.where(sha: "deadbeef...")` — finds the victim's commit regardless of which org "authenticated" the request — and creates a forged `success` status [4](#0-3) , potentially triggering an unauthorized deploy/merge on `victim-org/victim-repo`.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping

    end

    def event

    end

    def repository_owner

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
