This confirms the vulnerability. Key finding: `verify_webhook_signature` returns `true` unconditionally when `webhook_secret` is blank/not configured for that organization [1](#0-0) , and even when set, the signature only proves the payload came from *some* org whose secret matches — it never binds the signature to the `repository.full_name` field the handlers actually act on, since `repository_owner` (used to pick which app/secret to verify against) and `repository_name` (used by handlers to pick the target repo/stacks) are read independently from the same untrusted JSON body [2](#0-1) [3](#0-2) .

### Title
Webhook signature verification is bound to `repository.owner.login`/`organization.login`, not to the `repository.full_name` the handlers act on, allowing cross-organization event forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
Shipit supports hosting multiple, independently-trusted GitHub organizations from a single instance, each with its own `webhook_secret` [4](#0-3) [5](#0-4) . `WebhooksController#verify_signature` selects which organization's secret to check the HMAC against using `repository_owner`, which is read straight from the untrusted JSON body (`repository.owner.login` or `organization.login`) [6](#0-5) [2](#0-1) . Once the HMAC matches that organization's secret, the whole event is dispatched to handlers unmodified [7](#0-6) . But the handlers determine *which* repository/stacks to mutate using a *different* field from the same body — `payload.dig('repository', 'full_name')` [3](#0-2) . Nothing enforces that `repository.owner.login` (used for verification) matches `repository.full_name` (used for targeting). A party who legitimately controls one configured organization's app/webhook secret can craft a validly-signed payload whose `repository.full_name` points at a completely different organization's repository tracked by the same Shipit instance.

### Finding Description
This mirrors the reported analog "auction account closed before NFT transfer": two operations that should be atomically bound (verifying *who* sent the event and deciding *what* it's about) are split across two independently-read fields of the same untrusted payload, so satisfying the first (org signature) does not guarantee the second (target repository) is trustworthy — breaking the equality `organization that authenticated == repository that is written`.

Concretely:
- `verify_signature` picks the GitHub App/secret via `repository_owner` (`app/controllers/shipit/webhooks_controller.rb:59-62`).
- HMAC is verified over the raw body using that org's `webhook_secret` (`lib/shipit/github_app.rb:76-83`).
- On success, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the parsed body to handlers like `PushHandler`, `StatusHandler`, `PullRequest::ClosedHandler`, etc. [7](#0-6) .
- Every handler resolves its target repository/stacks via `Repository.from_github_repo_name(repository_name)` where `repository_name` comes from `payload.dig('repository', 'full_name')` [3](#0-2) , completely independent of the `repository_owner`/`organization.login` field checked during signature verification.

Because Shipit is explicitly designed to host multiple distinct organizations from a single deployment ("Using Multiple Github Applications" in `docs/setup.md`), an administrator of one tenant organization's GitHub App (who legitimately knows/controls their own org's `webhook_secret`) is an "unprivileged attacker" with respect to every other tenant organization tracked by the same Shipit instance. Such an actor can send a POST to `/webhooks` with:
- `X-Github-Event: status` (or `push`)
- `X-Hub-Signature` computed with their own org's `webhook_secret`
- body: `{"repository": {"owner": {"login": "their-own-org"}, "full_name": "victim-org/victim-repo"}, "sha": "<victim commit sha>", "state": "success", ...}`

`verify_signature` succeeds (their own org's secret matches), yet `StatusHandler#process` will look up `Commit.where(sha: params.sha)` and call `commit.create_status_from_github!(params)` for a commit belonging to `victim-org/victim-repo` [8](#0-7) , i.e., they can fabricate a `success` CI status on a victim organization's commit. Similarly `PushHandler#process` triggers `stack.sync_github(expected_head_sha:)` for stacks matched by `repository.full_name`, letting the same actor forge push notifications for a victim's stacks [9](#0-8) .

### Impact Explanation
Forged "success" statuses on a victim organization's commit can defeat status/CI checks that Shipit and its `shipit.yml` deploy pipeline rely on to gate an "unauthorized deploy" for a repository the attacker does not control — this crosses the explicitly in-scope High-impact bar of "unauthorized deploy" and does so cross-repository, which also matches the Critical bar of "cross-repository writes" since the attacker (an admin of Org A) can act on Org B's tracked repository/stacks purely by forging a payload's `full_name` field.

### Likelihood Explanation
Exploitability requires only that (a) the Shipit instance is configured for multiple organizations (a documented, supported configuration — `docs/setup.md`, "Using Multiple Github Applications"), and (b) the attacker administers one such tenant's GitHub App/webhook (an intended, non-privileged relationship to the *other* tenants). No access to the victim org, no GitHub token, and no Shipit session/API client credential is required — only the ability to POST to the public `/webhooks` endpoint with a signature valid for the attacker's own org.

### Recommendation
Bind the signature-verification identity to the acted-upon repository: after selecting the GitHub App via `repository_owner`, verify that `repository_owner` also matches the owner encoded in `repository.full_name` (and reject/short-circuit otherwise) before any handler is invoked, e.g., in `WebhooksController#verify_signature` or centrally in `Handler#initialize`, mirroring the fix pattern from the reported bug of merging the two operations so one cannot be satisfied without the other.

### Proof of Concept
1. Shipit is configured with `github.OrgA.webhook_secret = "secretA"` and `github.OrgB.webhook_secret = "secretB"`, each with its own installed GitHub App, per `docs/setup.md`'s multi-org setup.
2. Attacker administers OrgA's GitHub App and therefore knows `secretA`.
3. Attacker crafts a JSON body:
```json
{
  "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgB/victim-repo"},
  "sha": "<victim commit sha in OrgB/victim-repo>",
  "state": "success",
  "context": "ci/forged"
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(secretA, body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgA"`, calls `Shipit.github(organization: "OrgA")`, and the HMAC matches — verification passes [10](#0-9) .
6. `StatusHandler#process` runs against `Commit.where(sha: params.sha)`, which resolves to the victim's commit in `OrgB/victim-repo` regardless of OrgA/OrgB mismatch, applying a forged `success` status the attacker never had any legitimate authority over.
