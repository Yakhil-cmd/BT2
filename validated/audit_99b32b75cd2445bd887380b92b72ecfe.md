### Title
Permanent device-pairing secret is unnecessarily disclosed to arbiter contract counterparties, cosigners, and third-party arbstore servers, allowing anyone who receives it to pair as a trusted device correspondent indefinitely - (File: arbiter_contract.js)

### Summary
`arbiter_contract.js` repeatedly fetches the user's **permanent** device-pairing secret via `device.getOrGeneratePermanentPairingInfo()` and embeds it in plaintext as `my_pairing_code` inside messages sent to the contract peer, to the peer's cosigners, and — critically — to an external, only semi-trusted arbstore HTTP server during `openDispute()`/`appeal()`. Because the secret is marked `is_permanent=1`, `device.js`'s `handlePairingMessage()` never deletes or expires it after use, so every recipient of that value can re-use it at any future time to pair as a fully trusted correspondent device of the victim, without further authorization from the victim.

### Finding Description
`device.getOrGeneratePermanentPairingInfo()` [1](#0-0)  retrieves (or creates once) a single `pairing_secret` row flagged `is_permanent=1` with an expiry of `2038-01-01`. This same secret is embedded as `my_pairing_code` and transmitted:

- To the contract peer on offer creation: [2](#0-1) 
- To the peer again on acceptance/response: [3](#0-2) 
- To the arbstore server (an external HTTP service selected by the *arbiter*, not by the wallet owner) when opening a dispute: [4](#0-3) 
- To the arbstore server again on appeal: [5](#0-4) 
- Indirectly propagated further to cosigners/other members via `shareContractToCosigners`, which forwards the whole contract object (including `my_pairing_code`) to every cosigner device: [6](#0-5) 

The receiving side, `device.js`'s pairing handler, accepts this secret from anyone and grants full correspondent trust: [7](#0-6) 

Crucially, the deletion-on-use logic only fires for *non-permanent* secrets:
```
if (pairing_rows[0].is_permanent === 0){ // multiple peers can pair through permanent secret
    db.query("DELETE FROM pairing_secrets WHERE pairing_secret=?", [body.pairing_secret], function(){});
``` [8](#0-7) 

Because it is permanent, **every** party that ever legitimately received `my_pairing_code` through a contract offer, a dispute submission, or a cosigner broadcast retains the ability to pair as a correspondent at any later time — this is architecturally identical to the CVE's root cause: a long-lived credential/token that grants broad trust is embedded in a field that gets disclosed to parties who should not retain standing access (in the CVE, a JWT in `ISODownloadURL` readable by any namespace-scoped viewer; here, a permanent pairing secret embedded in contract/dispute payloads readable by peers, cosigners, and the arbstore operator).

Becoming a paired correspondent is not merely cosmetic: correspondent status is a prerequisite the device-message handler in `wallet.js` uses to accept high-impact, unsolicited requests from a device address, e.g. `create_new_wallet` (multisig wallet-creation offers) is processed for any correspondent without additional authentication: [9](#0-8)  and `wallet_defined_by_keys.sendOfferToCreateNewWallet`/handler builds a shared multi-sig wallet definition from attacker-controlled cosigner data [10](#0-9) . A party that has obtained the leaked permanent pairing secret (e.g., a malicious/compromised arbstore operator, or a former contract counterparty who is no longer trusted) can silently re-pair as a correspondent and initiate such multisig wallet flows, chat-based social engineering, or other correspondent-gated flows against the victim's wallet — all without the victim ever knowingly re-sharing their pairing code.

### Impact Explanation
Any entity that legitimately or transiently receives the arbiter contract's `my_pairing_code` (a former contract counterparty, any of their cosigners, or the arbstore server chosen by the arbiter) obtains a standing, non-expiring credential that lets it re-establish itself as a trusted device correspondent of the victim at will. This defeats the security assumption that "correspondent" status is a deliberate, one-time, mutually-consented relationship, and opens the door to social-engineering the victim into signing multisig transactions or accepting attacker-controlled shared addresses, potentially resulting in loss of funds. The disclosure is analogous to CVE-2026-7163's pattern: a supposedly protected, high-trust secret is silently embedded in a data path (there, a status field readable by low-privileged viewers; here, contract/dispute payloads sent to counterparties and third-party servers) and the receiving endpoint (there, the local authenticator; here, `handlePairingMessage`) grants full trust to any holder of the secret with no additional binding to the original recipient or a one-time-use constraint.

### Likelihood Explanation
Every arbiter contract negotiation (offer, acceptance, dispute, appeal) inherently transmits this permanent secret to the counterparty and to the arbiter's arbstore server as part of normal, expected protocol flow — no attacker action is required to obtain the secret beyond acting as an ordinary counterparty or operating/compromising an arbstore server that users interact with. Because reuse is unlimited (`is_permanent=1` skips the delete-after-use step), the exposure window is unbounded, making exploitation straightforward for anyone who was ever a legitimate but subsequently distrusted party to such a contract.

### Recommendation
Do not reuse the user's single permanent pairing secret across arbiter-contract flows sent to external/semi-trusted parties (peer, cosigners, arbstore server). Generate a fresh, single-use, expiring pairing secret (as `startWaitingForPairing()` already does) for each contract/dispute interaction, and ensure `handlePairingMessage()` deletes it immediately after first use regardless of context. Avoid transmitting any pairing secret to the arbstore server at all if it is not required for pairing with the arbstore itself.

### Proof of Concept
1. Alice's wallet calls `getOrGeneratePermanentPairingInfo()` when creating an arbiter contract offer with Bob; the resulting `my_pairing_code` (containing Alice's permanent `pairing_secret`) is sent to Bob's device via `arbiter_contract_offer` (`arbiter_contract.js:21-30`).
2. Bob declines/finishes the contract, but retains the received `my_pairing_code`.
3. Separately, Alice opens a dispute on a different (or the same) contract; `openDispute()` sends the same permanent `my_pairing_code` in plaintext JSON to the arbiter's arbstore server over HTTP (`arbiter_contract.js:275-303`).
4. At any later time, Bob (or the arbstore operator, or anyone the secret leaked to) sends a `pairing` justsaying message to Alice's hub using the captured `pairing_secret` (`device.js:758-762`, `handlePairingMessage` at `device.js:797-848`).
5. Because `pairing_secrets.is_permanent=1` for this secret, the row is never deleted; Alice's device unconditionally inserts Bob (or the attacker) as a confirmed `correspondent_devices` entry (`device.js:824-832`), re-establishing full correspondent trust without any fresh consent from Alice.
6. The attacker, now a correspondent, sends `create_new_wallet` to Alice's device (`wallet.js:150-153`), initiating a multisig wallet flow that can be used to social-engineer Alice into co-signing a wallet the attacker controls, potentially leading to fund loss.

function handlePairingMessage(json, device_pubkey, callbacks){
	var body = json.body;
	var from_address = objectHash.getDeviceAddress(device_pubkey);
	if (!ValidationUtils.isNonemptyString(body.pairing_secret))
		return callbacks.ifError("correspondent not known and no pairing secret");
	if (!ValidationUtils.isNonemptyString(json.device_hub)) // home hub of the sender
		return callbacks.ifError("no device_hub when pairing");
	if (json.device_hub.length > 200)
		return callbacks.ifError("device_hub too long");
	if (!network.isValidWsUrl(conf.WS_PROTOCOL + json.device_hub))
		return callbacks.ifError("invalid device_hub URL");
	if (!ValidationUtils.isNonemptyString(body.device_name))
		return callbacks.ifError("no device_name when pairing");
	if (body.device_name.length > 100)
		return callbacks.ifError("device_name too long");
	if ("reverse_pairing_secret" in body && !ValidationUtils.isNonemptyString(body.reverse_pairing_secret))
		return callbacks.ifError("bad reverse pairing secret");
	eventBus.emit("pairing_attempt", from_address, body.pairing_secret);
	db.query(
		"SELECT is_permanent FROM pairing_secrets WHERE pairing_secret IN(?,'*') AND expiry_date>"+db.getNow()+" ORDER BY (pairing_secret=?) DESC LIMIT 1", 
		[body.pairing_secret, body.pairing_secret], 
		function(pairing_rows){
			if (pairing_rows.length === 0)
				return callbacks.ifError("pairing secret not found or expired");
			// add new correspondent and delete pending pairing
			var safe_device_name = body.device_name.replace(/<[^>]*>?/g, '');
			db.query(
				"INSERT "+db.getIgnore()+" INTO correspondent_devices (device_address, pubkey, hub, name, is_confirmed) VALUES (?,?,?,?,1)", 
				[from_address, device_pubkey, json.device_hub, safe_device_name],
				function(){
					db.query( // don't update name if already confirmed
						"UPDATE correspondent_devices SET is_confirmed=1, name=? WHERE device_address=? AND is_confirmed=0", 
						[safe_device_name, from_address],
						function(){
							db.query("UPDATE correspondent_devices SET is_blackhole=0 WHERE device_address=?", [from_address], function(){
								eventBus.emit("paired", from_address, body.pairing_secret);
								if (pairing_rows[0].is_permanent === 0){ // multiple peers can pair through permanent secret
									db.query("DELETE FROM pairing_secrets WHERE pairing_secret=?", [body.pairing_secret], function(){});
									eventBus.emit('paired_by_secret-'+body.pairing_secret, from_address);
								}
								if (body.reverse_pairing_secret)
									sendPairingMessage(json.device_hub, device_pubkey, body.reverse_pairing_secret, null);
								callbacks.ifOk();
							});
						}
					);
				}
			);
		}
	);
}
