### Title
Environment-variable whitelist bypass allows arbitrary host process env vars (secrets) to leak into task/deploy output - (File: lib/shipit/environment_variables.rb)

### Summary
`shipit.yml` step authors (i.e., anyone with GitHub write/push access to a repository connected to a Shipit stack) can reference an arbitrary `$VARIABLE_NAME` inside a deploy/task/rollback command line. Shipit's `EnvironmentVariables#interpolate` expands these references, but for any name not present in the already-whitelisted task `env` hash, it silently falls back to reading the **Shipit server process's own environment** (`ENV[variable]`), bypassing the `deploy.variables` / `rollback.variables` / task-variable whitelist that `EnvironmentVariables#permit` is supposed to enforce.

### Finding Description
Shipit enforces a strict whitelist model for environment variables that can be injected into deploy/task/rollback commands: `TaskDefinition#filter_envs` and `DeploySpec#filter_deploy_envs` / `#filter_rollback_envs` call `EnvironmentVariables.with(env).permit(variable_definitions)`, which raises `NotPermitted` for any key not declared in the stack's `shipit.yml` (`deploy.variables`, `rollback.variables`, or a task's `variables`): [1](#0-0) [2](#0-1) [3](#0-2) 

This whitelist is the binding: "an environment key permitted (declared + validated) versus an environment key spawned (actually resolvable at command execution time)". These two sides are supposed to be equal — only permitted keys should ever be resolvable.

However, the same class exposes `interpolate`, used to expand `$VAR` references embedded directly in the shell command strings that come from `shipit.yml` `steps`/`pre`/`post`/`override` (untrusted, since they are fetched from the target Git repository, not from the Shipit database): [4](#0-3) 

```ruby
def interpolate(argument)
  return argument unless @env

  argument.gsub(/(\$\w+)/) do |variable|
    variable.sub!('$', '')
    Shellwords.escape(@env.fetch(variable) { ENV[variable] })
  end
end
```

`@env.fetch(variable) { ENV[variable] }` means: if `variable` was not present in the permitted/whitelisted task env hash, fall back to Ruby's global `ENV`, i.e., the actual process environment of the Shipit web/worker process. This breaks the equality that `permit` is meant to guarantee — `permit` ensures only declared keys are copied from *user-supplied* input into the task's stored `env`, but it has no effect on `interpolate`'s ability to reach into the full server process environment for **any** variable name referenced in a `shipit.yml` command, regardless of whether it was ever declared as a variable.

The Shipit server process environment routinely contains secrets that are explicitly documented as available to it: GitHub App private key material, `webhook_secret`, `api_clients_secret`, database URLs, Rails secrets, and any other environment-based configuration used to boot the app (see `docs/setup.md` secrets.yml example referencing exactly such keys). A repository maintainer with only GitHub write access (no Shipit account, no `ApiClient` token) can add a `shipit.yml` step such as:
```yaml
deploy:
  override:
    - echo $RAILS_MASTER_KEY
```
and have the interpolation step leak the value into the task's log output, which is visible to anyone who can view the stack's task page.

### Impact Explanation
This crosses the "credential exfiltration" bar explicitly listed as Critical impact: it can expose the app's own process secrets (potentially including tokens/keys usable to further compromise the app, e.g., private keys, `api_clients_secret`, or DB credentials) to any GitHub user who can push a `shipit.yml` change to a connected repository — no Shipit session, `ApiClient` token, or privileged account required, since deploy pipelines execute automatically off repository content.

### Likelihood Explanation
High. Anyone with commit access to a repository already onboarded onto Shipit can add or modify `shipit.yml` steps (this is the normal, expected way teams configure deploy steps), and simply referencing an environment variable name is trivial and requires no special tooling — an attacker only needs to guess or discover names of secrets present in the deploy host's environment (many of which are documented in `docs/setup.md` and the `README.md` scripting docs).

### Recommendation
Remove the `ENV[variable]` fallback in `EnvironmentVariables#interpolate`; only resolve variables present in the already-whitelisted `@env` hash, and leave unmatched `$VAR` references untouched (or raise/strip them) so that the value actually spawned in the command line is provably a subset of what `permit` allowed.

### Proof of Concept
1. Attacker (any GitHub collaborator with write access to a repo already connected as a Shipit stack) commits a `shipit.yml` change:
```yaml
deploy:
  override:
    - echo "leak=$RAILS_MASTER_KEY"
```
2. A deploy is triggered for that stack (normal deploy flow).
3. `TaskCommands#perform` / `DeployCommands` build the command line via `EnvironmentVariables.with(task_env).interpolate(command_line)` [4](#0-3) 
Since `RAILS_MASTER_KEY` was never declared under `deploy.variables` and is therefore absent from the permitted `task_env` hash, `@env.fetch('RAILS_MASTER_KEY') { ENV['RAILS_MASTER_KEY'] }` returns the Shipit process's actual master key value instead of raising or leaving it blank.
4. The value is printed in the task's log output, viewable via the stack/task UI, exfiltrating a host secret with no Shipit credentials at all.
