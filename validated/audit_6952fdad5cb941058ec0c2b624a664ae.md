### Title
`/events` mount point has no authentication enforcement despite comment claiming `UserRequiredMiddleware` protects it - ([File: config/routes.rb])

### Summary
The engine mounts `Pubsubstub::StreamAction.new` directly at `/events` in `config/routes.rb`, bypassing the `Shipit::Authentication` concern entirely, and `session[:authenticated] = true` set in `GithubAuthenticationController#callback` is never read anywhere in this repository. Grepping the codebase confirms no `UserRequiredMiddleware` class is defined or inserted into `app.middleware` in `lib/shipit/engine.rb`, so the flag is dead code and the stream endpoint is unauthenticated by anything in this engine.

### Finding Description
The broken binding: the comment claims `session[:authenticated] == true` is required by `UserRequiredMiddleware` before `Pubsubstub::StreamAction` serves `/events`, i.e. `request reaches StreamAction ⇒ session[:authenticated] == true`. Tracing the actual code shows this equality never holds as an enforced invariant:

- `config/routes.rb` line 9: `mount Pubsubstub::StreamAction.new, at: "/events", as: :events` [1](#0-0) . This is a raw Rack app mount, not a controller action, so it never goes through `Shipit::Authentication#force_github_authentication` [2](#0-1) .
- `session[:authenticated] = true` is set only in `GithubAuthenticationController#callback`, with a comment claiming `/events` and `/sidekiq` rely on `UserRequiredMiddleware` to read it [3](#0-2) .
- `lib/shipit/engine.rb`'s only middleware insertions are `OmniAuth::Builder` (conditionally, for OAuth) and `Shipit::SameSiteCookieMiddleware`; no `UserRequiredMiddleware` is registered [4](#0-3) .
- A repo-wide grep for `UserRequiredMiddleware` returns zero matches outside the comment itself, confirming the class doesn't exist anywhere in this codebase.

Given this, this engine's own code provides zero enforcement on `/events`: any HTTP client — including the unprivileged attacker described in the rules — can `GET /events` and receive live `Pubsubstub` broadcast data without any session or authentication at all, in this engine as currently written.

However, per the scoping rules, this must be evaluated as a real, demonstrable path exploitable through this engine's code with a reproducible minitest and no live GitHub/host dependency. Two considerations limit the finding:

1. `Pubsubstub::StreamAction` is a third-party gem class not defined in this engine's repo; whether it independently checks `session[:authenticated]`, requires a channel token, or performs any of its own gating is outside this codebase and cannot be confirmed or denied by grepping this repo. The rules explicitly exclude "third-party gem defects with no exploit path through this engine's own code" from scope — but the inverse problem here (this engine's total absence of a wiring layer that the comment says exists) is the engine's own omission, not a gem defect, since the engine never inserts any middleware or before_action in front of the mount.
2. The proof-of-concept must be an integration test hitting `/events` and asserting the stream is served. This is buildable purely from this repo: mount the engine routes, issue `get events_path` with no session, and assert `response.status` is not `401`/`302` and that no authentication redirect occurs — since no controller `before_action` sits in front of a Rack-mounted endpoint, this is directly demonstrable without needing to inspect `Pubsubstub`'s internals.

Existing guards checked and found not applicable: `force_github_authentication` only applies to controllers that `include Shipit::Authentication` (e.g. `ShipitController`), not to Rack-mounted apps like the `/events` mount [5](#0-4) . `verify_signature`/webhook checks are unrelated (different endpoint). No `before_action` or Rack middleware sits between the router and `Pubsubstub::StreamAction` for `/events`.

### Impact Explanation
An unauthenticated attacker can subscribe to `/events` and passively receive real-time broadcast data for stacks, deploys, and tasks across all repositories/tenants configured on the Shipit instance (deploy progress, task/chunk output, stack status changes) — this matches the "High: unauthenticated read of stack state, task streams or deploy output" impact category. It does not grant write access, RCE, or credential exfiltration, so it does not rise to Critical. The blast radius is instance-wide (all stacks/tenants hosted by this Shipit installation), and it is trivially repeatable — a single unauthenticated `GET /events` request, repeatable indefinitely.

### Likelihood Explanation
No preconditions are required beyond network access to the Shipit host: the attacker needs no Shipit session, no GitHub credentials, no API token, and no team membership. The cost is a single HTTP request. This is fully consistent with the "attacker is unprivileged only" definition in the rules. The only uncertainty is whether `Pubsubstub::StreamAction` (a third-party gem, not in this repo) performs any authentication of its own that isn't visible from this engine's code — I could not verify this because that gem's source is not part of this repository/index.

### Recommendation
Add explicit authentication enforcement in front of the `/events` mount within this engine, since no `UserRequiredMiddleware` exists to do so. Options:
- Implement a real `Shipit::UserRequiredMiddleware` (matching the comment's intent) that checks `session[:authenticated]` (or better, `session[:user_id]` plus `User#authorized?`) before allowing the request to reach `Pubsubstub::StreamAction`, and register it via `app.middleware.insert_before` in `lib/shipit/engine.rb` ahead of the `/events` mount.
- Alternatively, wrap the mount in a controller action that includes `Shipit::Authentication` and proxies to the stream, rather than mounting the Rack app directly in `config/routes.rb`.
- Update/remove the stale comment in `app/controllers/shipit/github_authentication_controller.rb` once the real enforcement exists, since currently it documents a non-existent protection.

### Proof of Concept
```ruby
# test/integration/events_authentication_test.rb
require 'test_helper'

module Shipit
  class EventsAuthenticationTest < ActionDispatch::IntegrationTest
    test "UserRequiredMiddleware is not defined anywhere in the engine" do
      refute defined?(Shipit::UserRequiredMiddleware),
        "Expected no UserRequiredMiddleware class, but comment in " \
        "github_authentication_controller.rb claims it exists and is relied upon"
    end

    test "/events is reachable without any session or session[:authenticated]" do
      # No session[:user_id], no session[:authenticated] set at all
      get "/events"

      # If a middleware enforced session[:authenticated] == true, this would
      # be a 401/403 or a redirect to github_authentication_path.
      refute_equal 302, response.status
      refute_equal 401, response.status
      refute_equal 403, response.status
    end
  end
end
```
Binding under test: `session[:authenticated] == true` (LHS, claimed precondition per comment) vs. actual enforced precondition observed when hitting `/events` with no session at all (RHS, actual behavior). Both sides are compared: LHS is asserted by the comment/design intent, RHS is what `config/routes.rb`'s direct Rack mount plus the confirmed absence of `Shipit::UserRequiredMiddleware` in `lib/shipit/engine.rb` actually produces. They diverge — the endpoint is served regardless of `session[:authenticated]` because nothing in this engine's code checks it.
