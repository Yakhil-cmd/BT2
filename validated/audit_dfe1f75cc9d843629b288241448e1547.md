## Analysis

The reported bug class — protocol/platform fees rounding down instead of up, causing systematic underpayment to the fee recipient — has a direct analog in this codebase's fee-splitting logic for `protocol_fee` and `fund_fee`.

### Title
Protocol and fund fee use floor rounding instead of ceiling, causing systematic fee-ledger underpayment to the protocol/fund owner on every swap - (File: `programs/cp-swap/src/curve/fees.rs`)

### Summary
`Fees::protocol_fee` and `Fees::fund_fee` compute their share of the already-rounded-up `trade_fee` using `floor_div` (round down), while the overall `trade_fee` itself is computed with `ceil_div` (round up). This asymmetry means the amount earmarked for the protocol/fund owner is always rounded in favor of liquidity providers, on every single swap.

### Finding Description
`Fees::trading_fee` (the total fee taken from the trader) rounds up via `ceil_div`, ensuring the pool/LP side never under-collects from the trader: [1](#0-0) 

But `Fees::protocol_fee` and `Fees::fund_fee`, which carve the protocol's and fund owner's shares out of that already-collected `trade_fee`, both use `floor_div` (round down): [2](#0-1) 

These are called directly in both swap directions in `CurveCalculator::swap_base_input` and `CurveCalculator::swap_base_output`: [3](#0-2) [4](#0-3) 

Critically, the full trader-transferred amount (including `trade_fee`) is physically deposited into the input vault via `transfer_from_user_to_pool_vault`, while only `input_amount_less_fees` (input minus `trade_fee` and `creator_fee`) is used to update the constant-product invariant: [5](#0-4) [6](#0-5) 

The only bookkeeping that separates "protocol/fund owner's share" from "LP's share" of `trade_fee` is the `protocol_fees_token_*` / `fund_fees_token_*` counters incremented in `PoolState::update_fees`: [7](#0-6) 

and these counters are exactly what's later subtracted out when computing the LP-attributable vault balance in `vault_amount_without_fee`: [8](#0-7) 

Because `protocol_fee`/`fund_fee` round down while the remainder implicitly flows to LPs (it stays in the vault but is not deducted by `vault_amount_without_fee`), every swap that produces a non-exact division shifts up to 1 unit of value per fee-rate away from the protocol/fund owner and into the LP pool. This is deterministic and reachable by any unprivileged caller of `swap_base_input` or `swap_base_output`.

### Impact Explanation
This is a fee-ledger accounting defect: the protocol/fund owner is systematically under-credited relative to the pool's actual fee take, with the shortfall silently accruing to LPs on essentially every trade where `trade_fee * protocol_fee_rate` (or `fund_fee_rate`) is not exactly divisible by `FEE_RATE_DENOMINATOR_VALUE`. Over a large volume of swaps this compounds into a measurable, permanent value transfer from the protocol/fund owner to LPs, with no mechanism to recover it (it is never reconciled or truable-up elsewhere).

### Likelihood Explanation
High likelihood of occurrence: any swap where the trade fee is not a multiple of `FEE_RATE_DENOMINATOR_VALUE / protocol_fee_rate` (or `/fund_fee_rate`) triggers this rounding loss, which is the common case for arbitrary swap sizes. No special conditions or privileges are needed — a normal unprivileged `swap_base_input`/`swap_base_output` call by any trader triggers it.

### Recommendation
Round `Fees::protocol_fee` and `Fees::fund_fee` up (`ceil_div`) instead of down, consistent with how `Fees::trading_fee` and `Fees::creator_fee` already round up, so that the protocol/fund owner's earmarked share is never short-changed relative to the LP remainder.

### Proof of Concept
Given `trade_fee_rate` such that `trade_fee = 7` and `protocol_fee_rate` such that `protocol_fee_rate / FEE_RATE_DENOMINATOR_VALUE * 7` is a non-integer (e.g. `protocol_fee_rate` chosen so the exact value is `2.9999...`), `Fees::protocol_fee` (using `floor_div`) returns `2` instead of `3`. The pool vault still holds the full `7` units backing `trade_fee`, but only `2` units are tracked in `protocol_fees_token_0`; the untracked `1` unit is left in the vault where `vault_amount_without_fee` does not subtract it, so it becomes part of the LP-redeemable balance instead of the protocol owner's collectible balance. This repeats on every swap with a non-exact division.

```rust
    pub fn vault_amount_without_fee(&self, vault_0: u64, vault_1: u64) -> Result<(u64, u64)> {
        let fees_token_0 = self
            .protocol_fees_token_0
            .checked_add(self.fund_fees_token_0)
            .ok_or(ErrorCode::MathOverflow)?
            .checked_add(self.creator_fees_token_0)
            .ok_or(ErrorCode::MathOverflow)?;
        let fees_token_1 = self
            .protocol_fees_token_1
            .checked_add(self.fund_fees_token_1)
            .ok_or(ErrorCode::MathOverflow)?
            .checked_add(self.creator_fees_token_1)
            .ok_or(ErrorCode::MathOverflow)?;
        Ok((
            vault_0
                .checked_sub(fees_token_0)
                .ok_or(ErrorCode::InsufficientVault)?,
            vault_1
                .checked_sub(fees_token_1)
                .ok_or(ErrorCode::InsufficientVault)?,
        ))
```

```rust
    pub fn update_fees(
        &mut self,
        protocol_fee: u64,
        fund_fee: u64,
        creator_fee: u64,
        direction: TradeDirection,
    ) -> Result<()> {
        if !self.enable_creator_fee {
            require_eq!(creator_fee, 0)
        }
        let is_creator_fee_on_input = self.is_creator_fee_on_input(direction)?;
        match direction {
            TradeDirection::ZeroForOne => {
                self.protocol_fees_token_0 = self
                    .protocol_fees_token_0
                    .checked_add(protocol_fee)
                    .unwrap();
                self.fund_fees_token_0 = self.fund_fees_token_0.checked_add(fund_fee).unwrap();

                if is_creator_fee_on_input {
                    self.creator_fees_token_0 =
                        self.creator_fees_token_0.checked_add(creator_fee).unwrap();
                } else {
                    self.creator_fees_token_1 =
                        self.creator_fees_token_1.checked_add(creator_fee).unwrap();
                }
            }
            TradeDirection::OneForZero => {
                self.protocol_fees_token_1 = self
                    .protocol_fees_token_1
                    .checked_add(protocol_fee)
                    .unwrap();
                self.fund_fees_token_1 = self.fund_fees_token_1.checked_add(fund_fee).unwrap();
```
