### Title
Contract hash computed by naive string concatenation without field delimiters allows title/text ambiguity forgery in arbiter and prosaic contracts - (File: arbiter_contract.js, prosaic_contract.js)

### Summary
`arbiter_contract.js` and `prosaic_contract.js` compute a "contract hash" that is used as the unique, integrity-binding identifier for a contract's `title`/`text` (and other party fields) by directly concatenating the fields as raw strings with no delimiter (or with a delimiter only after a future date gate). This is the same bug class as the reported httparty CVE-2024-22049: unescaped, undelimited concatenation of attacker-controlled string fields lets an attacker shift the boundary between adjacent fields while producing an identical serialized/hashed value, so two semantically different inputs collide on the same hash.

### Finding Description
`getHashSrc` in [1](#0-0)  builds the pre-image for the contract hash. For any `creation_date` up to `exports.NEW_HASH_DATE = '2026-11-01'` [2](#0-1)  — i.e. for all contracts created today (2026-09-15) — the source string is built with `.join("")`, concatenating `title`, `text`, `creation_date`, `payer_name`, `arbiter_address`, `payee_name`, `amount`, `asset` with **no separator whatsoever**:
```
[contract.title, contract.text, contract.creation_date, payer_name || '', contract.arbiter_address, payee_name || '', contract.amount, contract.asset || 'null'].join("")
``` [3](#0-2) 

`title`, `text`, and the party names (`my_party_name`/`peer_party_name`) are all free-form, attacker-controlled strings (validated only as non-empty strings, e.g. in the `arbiter_contract_offer` handler: `[body.title, body.text, body.my_pairing_code].every(ValidationUtils.isNonemptyString)` [4](#0-3) ). Because there is no delimiter, `title="AB", text="Ctext..."` and `title="ABC", text="text..."` produce byte-identical concatenations and therefore the identical SHA-256 hash, as long as the remaining fixed-format fields (`creation_date`, `arbiter_address`, `amount`, `asset`) are unchanged. This is structurally the same root cause as the reported advisory: fields are joined without escaping/delimiting the boundary characters, so content can "bleed" from one logical field into an adjacent one while preserving the resulting hash/serialization.

`prosaic_contract.js`'s `getHash` is even more permissive — it *always* (not just pre-2026-11-01) concatenates with zero delimiter and only three fields: `contract.title + contract.text + contract.creation_date` [5](#0-4) , so any title/text split that preserves the concatenation collides.

This `hash` is not decorative — it is the trust anchor used throughout the protocol to bind the (title, text) contract content to everything downstream:
- It is verified on receipt of an offer and again after swapping payer/payee roles: `if (body.hash !== arbiter_contract.getHash(body)) return callbacks.ifError("wrong contract hash");` [6](#0-5)  and again at [7](#0-6) .
- It is embedded on-chain as `contract_text_hash` in the signed data message that both parties countersign via the shared address: `var value = {"contract_text_hash": contract.hash, "arbiter": ..., contacts_hash};` [8](#0-7) .
- Most critically, in the dispute flow, the arbiter/arbstore reconstructs the hash from a **decrypted** `contractContent.title`/`contractContent.text` supplied by the disputant and only checks that it matches the previously-agreed `body.contract_hash`/on-chain `contract_text_hash`: 
```
var expectedContractHash = arbiter_contract.getHash({ title: contractContent.title, text: contractContent.text, ... });
if (body.contract_hash !== expectedContractHash) return callbacks.ifError("wrong contract hash");
...
if (payload.contract_text_hash !== body.contract_hash) return callbacks.ifError("contract hash doesn't match the signing unit");
``` [9](#0-8) 

Because the hash cannot distinguish between different (title, text) splits that concatenate to the same string, a disputant can present the arbiter with a *different* title/text pair (e.g. altered contractual terms) than the one the counterparty actually saw and signed, while still passing the `expectedContractHash === body.contract_hash` and `payload.contract_text_hash === body.contract_hash` checks. The arbiter has no way to detect the tampering because the check is purely a hash-equality check on attacker-controlled decrypted content.

### Impact Explanation
The arbiter/arbstore dispute-resolution process is the mechanism that decides who receives the escrowed funds held at the jointly-derived shared address (`deriveSharedAddress`, `["in data feed", [[contract.arbiter_address], "CONTRACT_" + contract.hash, ...]]` [10](#0-9) ). If a disputant can present forged contract terms (a different `title`/`text` split) to the arbiter that still hashes to the value both parties committed to on-chain, the arbiter may rule based on fabricated terms it cannot cryptographically distinguish from the real ones, causing the counterparty to lose funds held in the shared/escrow address (AA/contract fund loss due to disagreement on the "true" contract content bound by a supposedly-integrity-protecting hash). This satisfies the required impact bar of concrete fund loss/freezing due to a validation flaw reachable by an unprivileged contract counterparty.

### Likelihood Explanation
Both parties to an arbiter/prosaic contract are, by design, unprivileged, mutually distrusting counterparties (this is exactly the multi-party escrow use case the feature exists for). No special network position, hub, or node compromise is needed — only crafting a `title`/`text` pair with a favorable split and later, during a real dispute, supplying an alternate split with the same concatenation to the arbiter's `arbiter_dispute_request` handler. Because `exports.NEW_HASH_DATE = '2026-11-01'` is still in the future relative to today (2026-09-15), *all currently created arbiter contracts* use the vulnerable, delimiter-free hash function; `prosaic_contract.js`'s hash function has no date gate at all and is always vulnerable.

### Recommendation
- Use a length-prefixed or explicit-delimiter encoding (as already partially implemented via `exports.DELIMITER` for the post-2026-11-01 path) for **all** contract hash computations, immediately, not gated by date — e.g. always use `getSourceString`-style typed/length-prefixed serialization (as used elsewhere in `object_hash.js`/`string_utils.js` [11](#0-10) ) instead of raw `Array.join("")`/string concatenation.
- Apply the same fix to `prosaic_contract.js`'s `getHash` (and remove/deprecate `getHashV1`'s unsafe concatenation pattern) [12](#0-11) .
- Even with a delimiter such as `"[|#|]"`, ensure the delimiter itself cannot appear inside `title`/`text`/party-name fields (reject or escape occurrences of the delimiter string in user-supplied fields), otherwise the same ambiguity persists with a different separator.

### Proof of Concept
1. Alice (payer) offers Bob (payee) an arbiter contract with, e.g., `title = "AB"`, `text = "CD refund policy: none"`, fixed `creation_date`, `arbiter_address`, `payer_name`, `payee_name`, `amount`, `asset`.
2. `hash = sha256(title + text + creation_date + payer_name + arbiter_address + payee_name + amount + asset)` per `getHashSrc` [3](#0-2) .
3. Both parties countersign a unit whose data message embeds `contract_text_hash = hash` [13](#0-12) .
4. During a dispute, the disputant sends `arbiter_dispute_request` with `encrypted_contract` decrypting to `title = "ABC"`, `text = "D refund policy: none"` (same overall concatenation, different logical split/meaning) — all other fields unchanged.
5. `expectedContractHash` computed from these forged fields equals the original `body.contract_hash`/on-chain `contract_text_hash` [9](#0-8) , so the arbiter accepts the forged contract content as authentic and adjudicates the dispute using terms the counterparty never agreed to.

function getSourceString(obj) {
	var arrComponents = [];
	function extractComponents(variable){
		if (variable === null)
			throw Error("null value in "+JSON.stringify(obj));
		switch (typeof variable){
			case "string":
				if (variable.includes(STRING_JOIN_CHAR))
					throw Error("00 byte in string value in " + JSON.stringify(obj));
				arrComponents.push("s", variable);
				break;
			case "number":
				if (!isFinite(variable))
					throw Error("invalid number: " + variable);
				arrComponents.push("n", variable.toString());
				break;
			case "boolean":
				arrComponents.push("b", variable.toString());
				break;
			case "object":
				if (Array.isArray(variable)){
					if (variable.length === 0)
						throw Error("empty array in "+JSON.stringify(obj));
					arrComponents.push('[');
					for (var i=0; i<variable.length; i++)
						extractComponents(variable[i]);
					arrComponents.push(']');
				}
				else{
					var keys = Object.keys(variable).sort();
					if (keys.length === 0)
						throw Error("empty object in "+JSON.stringify(obj));
					keys.forEach(function(key){
						if (typeof variable[key] === "undefined")
							throw Error("undefined at "+key+" of "+JSON.stringify(obj));
						if (key.includes(STRING_JOIN_CHAR))
							throw Error("00 byte in object key in " + JSON.stringify(obj));
						arrComponents.push(key);
						extractComponents(variable[key]);
					});
				}
				break;
			default:
				throw Error("getSourceString: unknown type="+(typeof variable)+" of "+variable+", object: "+JSON.stringify(obj));
		}
	}

	extractComponents(obj);
	return arrComponents.join(STRING_JOIN_CHAR);
