### Title
Batch destructive branch/worktree deletion in `/clean_gone` executes without per-item confirmation, enabling attacker-controlled remote state to widen the blast radius of a single approval - (File: `plugins/commit-commands/commands/clean_gone.md`)

### Summary
The `/clean_gone` slash command instructs Claude to run a single bash pipeline that dynamically enumerates every locally-tracked branch marked `[gone]` and force-deletes it (`git branch -D`) along with any associated worktree (`git worktree remove --force`), with no dry-run, itemized listing, or per-branch confirmation step distinct from the one-time approval of the command block. Because the set of branches acted upon is computed at execution time from `git branch -v`, and that local state is itself derived from the remote's branch set observed during `git fetch --prune`, an attacker who controls the remote prior to the user's next fetch can cause additional branches to be marked `[gone]` and have them silently swept into the same already-approved bulk deletion.

### Finding Description
Step 3 of the command pipes `git branch -v | grep '\[gone\]' | sed ... | awk ... | while read branch; do ... git worktree remove --force "$worktree"; ... git branch -D "$branch"; done` [1](#0-0) . The command text approved by the user (via Claude Code's Bash tool permission prompt) is the *script itself*, not the resolved list of branch names — those are resolved dynamically inside the `while read` loop at execution time. This means the approval dialog the user sees corresponds to "run this loop over whatever is currently marked `[gone]`," not "delete branches X, Y, Z." Any branch that becomes `[gone]` between the time the user reasons about/approves the command and the time it actually executes (e.g., because a preceding `git fetch --prune` in the same or an adjacent session picked up remote branch deletions from an attacker-controlled or compromised remote) is deleted without ever being individually surfaced to the user. There is no `--dry-run`, no itemized print-then-confirm step, and no `git worktree remove` (non-forced) fallback that would give the user or Claude a chance to abort per-item; `--force` is used unconditionally, and `git branch -D` (uppercase, unconditional force-delete) is used instead of the safer `git branch -d` which would fail on unmerged commits.

### Impact Explanation
The scoped impact is bulk unreviewed destructive action authorized by a single approval: local branches and their working-tree checkouts (which may contain uncommitted work) can be deleted based on remote-controlled `[gone]` markers, beyond what the user consciously reviewed at approval time. This matches "unauthorized/destructive file or git action performed without distinct per-item consent," since the command's own text does not name the branches it will delete — the enumeration is deferred to runtime.

### Likelihood Explanation
Requires the user to have already approved running `/clean_gone` (a realistic one-time trust decision for a "cleanup" utility) and requires the remote/fetch state to include attacker-influenced branch deletions prior to the next `git fetch --prune`/`git branch -v` — both are plausible in normal collaborative-repo workflows where the "attacker" is any party with push access to branches on the shared remote (not a privilege escalation on the victim's machine, just remote branch-state influence). The bulk-delete-without-itemization behavior is deterministic and repeatable every time the command runs against a `[gone]`-marked branch set.

### Recommendation
Modify the command to first print the fully-resolved, itemized list of branches (and their associated worktrees) that will be deleted, and require an explicit confirmation of that concrete list before the destructive loop executes — separating "approve running this cleanup script" from "approve deleting these specific N branches/worktrees." Replace unconditional `git branch -D` / `git worktree remove --force` with a dry-run preview pass followed by a second, explicit execution pass, and consider using `git branch -d` first (falling back to `-D` only with explicit override) so unmerged work is flagged rather than silently destroyed.

### Proof of Concept
Integration test plan:
1. Set up a local repo with a remote; create N local branches tracking remote branches, each with a worktree checked out.
2. Have the user approve `/clean_gone` once (simulating the single Bash-tool approval).
3. Before the script's execution step actually runs, simulate attacker-controlled remote state by deleting additional remote branches and running `git fetch --prune`, causing more local branches to flip to `[gone]`.
4. Execute the approved script and assert: (a) all `[gone]`-marked branches at execution time — including the ones that became `[gone]` only after approval — are force-deleted and their worktrees removed with `--force`; (b) no itemized list of the actually-deleted branches/worktrees was presented for confirmation prior to deletion; (c) therefore the tool performed silent batch execution rather than surfacing itemized deletions requiring explicit per-item consent, confirming the invariant violation.

   # Process all [gone] branches, removing '+' prefix if present
   git branch -v | grep '\[gone\]' | sed 's/^[+* ]//' | awk '{print $1}' | while read branch; do
     echo "Processing branch: $branch"
     # Find and remove worktree if it exists
     worktree=$(git worktree list | grep "\\[$branch\\]" | awk '{print $1}')
     if [ ! -z "$worktree" ] && [ "$worktree" != "$(git rev-parse --show-toplevel)" ]; then
       echo "  Removing worktree: $worktree"
       git worktree remove --force "$worktree"
     fi
     # Delete the branch
     echo "  Deleting branch: $branch"
     git branch -D "$branch"
   done
