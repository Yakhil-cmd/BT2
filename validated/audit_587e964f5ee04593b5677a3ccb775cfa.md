### Title
StatusHandler applies commit statuses without verifying repository ownership, allowing cross-repository status forgery - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits solely by `params.sha` and never resolves or checks `params.repository`, unlike every `PullRequest` handler (e.g. `OpenedHandler#repository`) which resolves `Shipit::Repository.from_github_repo_name(params.repository.full_name)` before acting. Because GitHub webhook signature verification is scoped per-organization (not per-repository), any repository sharing that organization's `webhook_secret` can emit a validly-signed `status` event referencing a commit SHA that also exists in a different repository's stack, causing `StatusHandler` to write a forged status onto that unrelated commit.

### Finding Description
The broken binding: `commit.stack.repository == payload.repository` should hold for every write performed by a webhook handler, but for `StatusHandler` this is never checked — only `commit.sha == params.sha` is enforced.

- `Shipit::WebhooksController#verify_signature` computes `repository_owner` from the payload and calls `Shipit.github(organization: repository_owner)`, verifying the HMAC against that organization's single configured `webhook_secret` (`app/controllers/shipit/webhooks_controller.rb:24-49`, `lib/shipit/github_app.rb:76-83`). This authenticates "a repository belonging to this GitHub org/app installation sent this event" — it does **not** authenticate "this specific repository owns this commit."
- `StatusHandler`'s params schema requires only `sha`/`state` and never declares/requires `repository` (`app/models/shipit/webhooks/handlers/status_handler.rb:7-18`), and `process` does `Commit.where(sha: params.sha).each { |c| c.create_status_from_github!(params) }` (lines 20-24) — matching across **all** stacks/repositories in the database.
- Contrast: `PullRequest::OpenedHandler#repository` (lines 50-54) resolves the repository from the payload and scopes `ReviewStackAdapter` to `repository.review_stacks`, so a forged `repository.full_name` cannot make a stack get created against another repository — confirmed by `Shipit::Repository.from_github_repo_name` / `NullRepository` fallback.

Exploit flow: an attacker who has write access to some repository `B` enrolled under the same GitHub App/organization as a target repository `A` (both share the org's `webhook_secret`) can push an existing commit object (same tree/parents/author/committer timestamps as a commit already tracked by `A`'s Shipit stack) into `B`, then use the GitHub Status API to set a status on that SHA in `B`. GitHub emits a genuinely, correctly-signed `status` webhook with `repository.full_name = "org/B"` and the shared `sha`. `verify_signature` passes (same org secret). `StatusHandler` ignores `repository` entirely and applies the forged status to the `Commit` row belonging to `A`'s stack, potentially marking it `success` and unblocking `deployable?`/`schedule_continuous_delivery` (`app/models/shipit/commit.rb:227-287`).

### Impact Explanation
A forged status written to a commit in a repository/stack the attacker does not control can make `Commit#deployable?` return true and trigger `schedule_continuous_delivery`, i.e., an unauthorized deploy path for a stack the attacker never authenticated against — matching the Critical category "a payload for one repository mutating another's stack, commit ... or an unauthorized deploy." This is repeatable against any pair of repositories sharing a GitHub App/org webhook secret, as long as the attacker can get a target SHA's git object into a repository they control (feasible when the target repo's objects are readable, e.g., internal/public repos, forks that share initial history, or repos the attacker can fetch from). ### Likelihood Explanation
Requires: (1) a GitHub App/org installation configuration where a single `webhook_secret` covers multiple distinct repositories (a common Shipit deployment pattern — organization-wide app installs), (2) the attacker has write/status-setting access to at least one repository under that same org, and (3) the ability to introduce a commit object with an identical SHA (same tree/parents/author/committer metadata) as a targeted commit into their own repository, which is achievable via `git fetch`/`git push <sha>:<ref>` if the target commit's objects are reachable. No Shipit secrets, sessions, or maintainer privileges are needed beyond ordinary write access to one in-scope repository.

### Recommendation
Require and validate `repository` in `StatusHandler`'s params schema, resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)`, and scope the `Commit` lookup to commits belonging to stacks of that repository (e.g., `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { id: repository.id })`), mirroring the pattern already used in `PullRequest::OpenedHandler#repository`.

### Proof of Concept
Add a minitest to `test/models/shipit/webhooks/handlers/status_handler_test.rb` (or the existing status handler test file):
1. Create two `Shipit::Stack`/`Shipit::Repository` fixtures, `repo_a` and `repo_b`, each with distinct `github_repo_name`.
2. Create `commit_a = Commit.create!(stack: stack_a, sha: SAME_SHA, ...)`.
3. Build a `status` webhook payload with `repository: { full_name: repo_b.github_repo_name }` and `sha: SAME_SHA`, `state: "success"`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)`.
5. Assert `commit_a.reload.status.state == "success"` even though the payload's `repository.full_name` was `repo_b`, not `repo_a` — i.e., assert `commit_a.stack.repository.github_repo_name != payload["repository"]["full_name"]` while the status was still applied.
6. Contrast assertion: repeat with `PullRequest::OpenedHandler` using a forged `repository.full_name` and confirm `repository` resolves to `Shipit::NullRepository` and no review stack/commit mutation occurs for the true repository.
