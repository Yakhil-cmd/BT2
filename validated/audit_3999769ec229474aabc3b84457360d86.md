### Title
Cross-organization webhook forgery via `WebhooksController#repository_owner` fallback → unauthenticated `PullRequest#github_pull_request` write - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/pull_request/assigned_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret used to authenticate an inbound webhook using `repository_owner`, which falls back to the top-level `organization.login` field whenever `repository.owner` is omitted from the JSON body. Because `AssignedHandler#process` independently resolves the target row using `repository.full_name`, an attacker can pick any configured organization (in particular one whose `webhook_secret` is unset) for signature verification while the payload's `repository.full_name` names an unrelated organization's repository, causing an unauthenticated request to mutate that victim repository's `PullRequest` row.

### Finding Description
Broken binding: the code implicitly assumes `organization_used_for_signature_check == organization_owning(params.repository.full_name)`. In reality:

- `org_for_signature = params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0)  is used to fetch the `GitHubApp` instance: `Shipit.github(organization: repository_owner)` inside `verify_signature` [2](#0-1) .
- `org_for_write = params.repository.full_name.split('/').first`, used only inside the handler via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [3](#0-2) .

Nothing forces these two to be the same organization. `Shipit.github` looks up per-organization config purely by the string passed to it: `config = github_app_config(organization)` and instantiates/caches a `GitHubApp` per that key [4](#0-3) . In multi-org deployments (demonstrated by the shipped fixture `test/dummy/config/secrets_double_github_app.yml` with distinct `OrgOne`/`OrgTwo` sections, each with `webhook_secret: # nil`), each organization can have an independently weak or absent `webhook_secret`. Critically, `GitHubApp#verify_webhook_signature` returns `true` unconditionally when `webhook_secret` is blank: `return true unless webhook_secret` [5](#0-4) .

`AssignedHandler`'s `ExplicitParameters` schema only `requires :repository do requires :full_name, String end` — it never requires or validates `repository.owner` [6](#0-5) , so a body that omits `repository.owner` entirely but supplies a top-level `organization.login` and a `repository.full_name` for a different org is fully valid and dispatched.

Exploit flow:
1. Attacker sends `POST /webhooks` with header `X-Github-Event: pull_request` and a body:
   ```json
   {
     "action": "assigned",
     "number": 2,
     "pull_request": { ... valid nested pull_request fields ... },
     "organization": { "login": "OrgTwo" },
     "repository": { "full_name": "OrgOne/victim-repo" },
     "sender": { "login": "attacker" }
   }
   ```
   with no `repository.owner` key.
2. `repository_owner` returns `"OrgTwo"` (the fallback branch) [1](#0-0) .
3. `verify_signature` calls `Shipit.github(organization: "OrgTwo")`; since `OrgTwo`'s `webhook_secret` is blank, `verify_webhook_signature` returns `true` regardless of the (missing/garbage) `X-Hub-Signature` header [2](#0-1) [5](#0-4) .
4. The request is dispatched to `AssignedHandler`, which resolves the target `PullRequest` via `params.repository.full_name = "OrgOne/victim-repo"` and calls `pull_request.update(github_pull_request: params.pull_request)` [7](#0-6) , mutating a row belonging to a completely different organization the attacker never authenticated against.

No existing guard closes this: `drop_unhandled_event` only checks the event type is handled, `check_if_ping` only special-cases `ping`, and `verify_signature`'s only failure mode is `GithubOrganizationUnknown` (raised only if the `organization.login` string doesn't match *any* configured org key) — it never cross-checks against `repository.full_name`'s prefix.

### Impact Explanation
An unauthenticated attacker who can send an HTTP POST to `/webhooks` (no session, no API token, no knowledge of the victim org's real webhook secret) can forge write operations that update a `PullRequest` record belonging to any tracked repository, as long as they know or can trigger an organization entry in Shipit's config with a blank/weak `webhook_secret`. This is a payload from one (attacker-controlled or arbitrary) organization mutating another organization's stack data — squarely the "payload for one repository mutating another's stack, commit, task or team" and "authentication bypass" Critical categories. The attack is fully repeatable against any `number`/`full_name` combination and any handler that keys its writes off `repository.full_name` while `verify_signature` keys off `repository_owner`.

### Likelihood Explanation
Requires: (a) the host Shipit instance to use the multi-organization GitHub config layout keyed by organization name (`TOP_LEVEL_GH_KEYS` check in `github_default_organization`) [8](#0-7) , and (b) at least one configured organization with a blank/weak `webhook_secret` (shown as the shipped example configuration in `secrets_double_github_app.yml`). Both are realistic operational states — `webhook_secret` is optional/nullable by design in `GitHubApp#initialize` (`@webhook_secret = @config[:webhook_secret].presence`) [9](#0-8) . No GitHub credentials, session, or API token are needed; the attacker only needs the target org's real name (public) and, for the forgery organization, any org key present in the Shipit deployment (which can itself be an org the attacker owns/controls if the operator lets external orgs' apps post webhooks, or one with a known-blank secret). Cost is a single crafted HTTP request; fully repeatable.

### Recommendation
Bind the organization used for signature verification to the same organization that owns the row being mutated: derive `repository_owner` strictly from `repository.full_name`'s prefix (or require `repository.owner.login` to match `repository.full_name`'s prefix) rather than falling back to an independent, attacker-suppliable `organization.login`. Additionally, require handlers that write to `Repository`-scoped records to assert the resolved repository's owner matches the same organization value used in `verify_signature`, and treat a blank `webhook_secret` in production as a misconfiguration to warn/fail loudly on, not silently accept all signatures.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_cross_org_test.rb
require 'test_helper'

module Shipit
  class WebhooksControllerCrossOrgTest < ActionController::TestCase
    tests Shipit::WebhooksController

    setup do
      # Use fixture-style multi-org config where 'OrgTwo' has webhook_secret: nil
      Shipit.stubs(:github_default_organization).returns('orgone')
      Shipit.stubs(:github_app_config).with('orgtwo').returns({ webhook_secret: nil })
      @stack = shipit_stacks(:shipit) # belongs to repository "shopify/shipit-engine" (victim org)
      @pull_request = shipit_pull_requests(:shipit_pending) # associated with @stack, number: 2
    end

    test "forged organization.login bypasses signature check and mutates victim repo's PullRequest" do
      request.headers['X-Github-Event'] = 'pull_request'
      # No X-Hub-Signature header at all, no repository.owner in body
      body = {
        action: 'assigned',
        number: @pull_request.number,
        pull_request: {
          id: 999, number: @pull_request.number, url: 'https://api.github.com/x',
          title: 'evil', state: 'open', additions: 1, deletions: 1,
          head: { sha: 'deadbeef', ref: 'evil-branch' },
          user: { login: 'attacker' },
          assignees: [{ login: 'attacker' }],
          labels: []
        },
        organization: { login: 'OrgTwo' }, # attacker-chosen org w/ blank secret
        repository: { full_name: @stack.repository.full_name }, # victim org's repo
        sender: { login: 'attacker' }
      }.to_json

      # Binding under test:
      # org_for_signature ('OrgTwo') != org_for_write (@stack.repository.full_name's owner)
      assert_not_equal 'OrgTwo', @stack.repository.full_name.split('/').first

      assert_changes -> { @pull_request.reload.github_pull_request['title'] } do
        post :create, body:, as: :json
      end

      assert_response :ok
    end
  end
end
```
This demonstrates the equality `org_for_signature == org_for_write` is false yet the write still succeeds, confirming the authentication-bypass-enabled cross-organization row write.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
