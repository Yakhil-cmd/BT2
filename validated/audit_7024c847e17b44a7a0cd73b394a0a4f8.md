This external Synthetix report describes a class of bug where code computes an "expected" derived value from a value captured *before* an external state-changing operation, then asserts/uses that expected value against the *actual* post-operation state without tolerating drift — causing a revert/DoS. Agave has a structurally analogous bug in the stake-reward distribution path, where an `assert_eq!` (a hard panic, not a graceful `Result`) compares a delegation amount computed from a stake-account snapshot taken during reward *calculation* against the live delegation amount read from the stakes cache at distribution time, several blocks later — a window during which the stake owner can mutate their own account.

### Title
Unprivileged `Split`/`Merge` on a stake account between epoch-reward calculation and distribution triggers a deterministic `assert_eq!` panic, halting the cluster - ([File: runtime/src/bank/partitioned_epoch_rewards/distribution.rs])

### Summary
`build_updated_stake_reward` recomputes the "expected" new delegation from the stake state captured during the earlier reward-**calculation** phase and asserts it must equal the delegation found in the **live** stakes cache at distribution time. If the delegation legitimately changes in between (e.g., the staker calls `Split` or `Merge`), the assertion fails and panics every validator replaying the block deterministically.

### Finding Description
During the epoch-boundary reward calculation phase, `redeem_stake_rewards` computes a new stake amount from the delegation snapshot taken at that point and, when `adjust_delegations_for_rent` is `false`, simply does `stake.delegation.stake += staker_rewards;` and returns it as part of `PartitionedStakeReward.inflation.stake`, to be applied later. [1](#0-0) 

Reward *distribution* happens across multiple later blocks/slots (one partition per block). At distribution time, `build_updated_stake_reward` fetches the **current** stake account from `stakes_cache_accounts` (i.e., whatever the account looks like *now*, not at calculation time), and — when the `relax_post_exec_min_balance_check` feature is not active — asserts that `stake.delegation.stake.saturating_add(stake_reward)` (computed from the live account) equals the previously-computed `new_stake.delegation.stake` (computed from the calculation-time snapshot): [2](#0-1) 

This is functionally the same defect pattern as the Synthetix report: code precomputes an expected downstream value (`margin`/`expected_delegation`) from an amount captured before an operation whose actual outcome can differ (`amountReceived`/live delegation after `Split`/`Merge`), and then hard-fails instead of tolerating or re-deriving from the actual result. Here the failure mode is worse than a revert — it's a Rust `assert_eq!` panic inside `Bank::store_stake_accounts_in_partition`'s call path, which every validator executes identically while replaying the same block: [3](#0-2) 

The relevant flag is gated behind a not-yet-universally-activated feature (`relax_post_exec_min_balance_check`), which appears in `FeatureSnapshot`, documented as containing "only features that have not been activated on all clusters," confirming the vulnerable `else` branch is currently reachable: [4](#0-3) 

### Impact Explanation
A stake account owner (an unprivileged, non-validator user) can perform an ordinary `Split` or `Merge` on their own stake account in the small window between the epoch-boundary reward-calculation block and the later block(s) that process their account's reward partition. This changes the live `delegation.stake` value cached in `stakes_cache_accounts` relative to what was captured during calculation, so `expected_delegation != new_stake.delegation.stake` and the `assert_eq!` panics. Because reward distribution is part of deterministic block processing executed identically by all validators, this is a cluster-wide, epoch-boundary halt — matching the "epoch-boundary halt" acceptance criterion.

### Likelihood Explanation
Reachable by any stake account owner with no special privileges, using only standard, permitted stake-program instructions (`Split`/`Merge`) that are explicitly designed to be callable at any time by the stake/withdraw authority. The only precondition is that the feature gate `relax_post_exec_min_balance_check` (which switches to the non-panicking rent-adjustment path) is not yet active on the target cluster — which the codebase's own `FeatureSnapshot` documentation states is the case for features still tracked there.

### Recommendation
Replace the `assert_eq!` in `build_updated_stake_reward` with a `DistributionError` variant that safely aborts/burns just that individual reward (consistent with the existing error-handling pattern in `store_stake_accounts_in_partition`) instead of panicking the whole validator, and/or unconditionally recompute the new delegation from the live/current stake state rather than trusting a value computed against a stale (calculation-time) snapshot, mirroring the `adjust_delegations_for_rent` branch's tolerant behavior.

### Proof of Concept
1. A staker creates a stake account and delegates it; the account is included in the delegation set at an epoch boundary.
2. At the epoch boundary, `calculate_stake_rewards_and_commissions` runs with `adjust_delegations_for_rent = false` (feature not active) and records `PartitionedStakeReward.inflation.stake` based on the delegation snapshot at that moment.
3. Before the block that distributes this specific account's partition is processed, the staker submits a `Split` (or `Merge`) instruction, mutating `delegation.stake` on the live account in `stakes_cache`.
4. When `store_stake_accounts_in_partition` → `build_updated_stake_reward` runs for that account, `expected_delegation` (derived from the now-mutated live `stake`) no longer equals `new_stake.delegation.stake` (derived from the stale calculation-time snapshot), tripping `assert_eq!` and panicking every validator processing the block.
