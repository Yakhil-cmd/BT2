### Title
Missing per-input attestation check allows an unattested co-author to spend a `spender_attested` asset - (File: validation.js)

### Summary
`CVE-2024-37769` describes a broken-permission flaw where an application checks only that *some* privileged condition is satisfied instead of verifying the *specific* actor performing the sensitive action, letting an unprivileged user reach an administrator-only capability. `ocore`'s divisible-asset payment validator has the same class of flaw for assets whose issuer set `spender_attested: true`: the code confirms that *at least one* author of the unit is attested, but never confirms that the address which actually *owns the input being spent* is attested, for `transfer` inputs.

### Finding Description
`validatePayment()` loads the subset of the unit's authors that are attested for the asset and then only performs two checks: [1](#0-0) 
- `objAsset.arrAttestedAddresses.length === 0` → reject only if **none** of the authors are attested.
- if `bIssue`, that the specific `issuer_address` is attested.

There is no equivalent check for `transfer` inputs that the address which owns the output being spent (`input.address` for multi-authored units, see `validatePaymentInputsAndOutputs`) is itself a member of `arrAttestedAddresses`. [2](#0-1) [3](#0-2) 

Because `objUnit.authors` can list multiple, unrelated addresses (multi-authored/co-signed units are a normal, unprivileged construct — any unit poster can add extra co-authors as long as each supplies valid authentifiers for its own address), an attacker who controls an address **A** holding balance of a `spender_attested` asset (an asset the attacker was never attested for) can co-author a single unit together with any other address **B** that *is* attested for that asset. The `arrAttestedAddresses` array will be non-empty (it contains **B**), satisfying `arrAttestedAddresses.length === 0` → false, so the check passes, and the payment message is allowed to spend address **A**'s (unattested) coins in a `transfer` input. `owner_address`/`arrInputAddresses` checks elsewhere only confirm the input address is *among the authors*, not that it is *attested*.

This defeats the entire purpose of `spender_attested`, which is documented/used throughout the AA/oscript ecosystem (see `test/samples/create_an_asset.oscript`, `51_attack_game.oscript`, `ico_with_milestones.oscript`) as an access-control gate restricting who may hold/spend the asset (e.g., KYC-gated tokens, whitelisted game tokens, milestone-gated ICO tokens).

### Impact Explanation
An attacker who is not attested for an asset that requires attestation to spend can nevertheless move/transfer that asset out from an address they control, as long as they co-author the spending unit with any single attested address (which could even be a throw-away address the attacker also controls and gets attested once, e.g. via a public/attestor-agnostic attestation, or colludes with a willing attested party). This is a privilege-escalation / access-control bypass on asset transfer rights — a "normal user" (unattested holder) obtains the "administrator" privilege (attested spender) — potentially enabling unauthorized transfer of restricted/whitelisted tokens, undermining compliance/KYC assumptions built into asset definitions, and causing node disagreement risk if some validators interpret attestation requirements differently pre/post this bypass being exploited. This maps to "unauthorized spending" / bypass of asset transfer conditions, one of the accepted high-severity outcomes.

### Likelihood Explanation
Reachable directly by any unprivileged unit poster: composing a multi-authored unit with a second, arbitrary co-author address is a standard, permissionless operation (each author independently signs their own path; no special privilege is needed to add authors to a payment unit). No network, node, or hub compromise is required — only crafting one ordinary payment unit with two authors. The barrier is finding/using one attested address as a co-author, which is often trivial (self-attest via a low-bar attestor, or use one's own second address if attestation criteria are weak/public).

### Recommendation
In `validatePaymentInputsAndOutputs`/`validatePayment` (validation.js), when `objAsset.spender_attested` is true, additionally verify — for every `transfer` input — that the owning address (`arrInputAddresses` entries, i.e., `input.address` for multi-authored units or the sole author for single-authored units) is contained in `objAsset.arrAttestedAddresses`, not merely that some author of the unit is attested. Reject the payment message with an error such as `"spender is not attested"` if any input's owner fails this check.

### Proof of Concept
1. Author asset `X` with `spender_attested: true` and an attestor list; have attested address **B**'s attestation recorded on-chain.
2. Have unattested address **A** receive/hold coins of asset `X` (e.g., legitimately obtained once, or issued to A improperly through another path).
3. Craft a payment unit with `authors: [A, B]` where the `payment` message for asset `X` transfers **A**'s inputs to an arbitrary output address, with valid authentifiers supplied for both A and B (B need not even be involved in the actual transfer amounts — a zero-effect co-authoring, or B co-signs a trivial unrelated `text`/second payment message in the same unit to satisfy "single-authored" checks where required).
4. `storage.loadAssetWithListOfAttestedAuthors` returns `arrAttestedAddresses = [B]`, which is non-empty, so `validatePayment` accepts the message even though A (the actual spender) was never attested.

Note: I was unable to fully trace whether an additional downstream check (e.g., in `divisible_asset.js` or `indivisible_asset.js` composer-side logic, which is client-composition code and not part of consensus validation) independently re-verifies per-input attestation before broadcasting; validation.js itself, which is the consensus-critical gate other nodes rely on, does not perform this check. A background Devin session with full repository/test access would be needed to confirm this by running/adding a targeted unit test against `validatePayment`.
