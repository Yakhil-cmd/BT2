### Title
`OpenedHandler#provision?` operator-precedence bug lets `allow_with_label`/`prevent_with_label` bypass `review_stacks_enabled=false` - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`provision?` intends `review_stacks_enabled` to gate all provisioning behaviors, but Ruby's `&&`/`||` precedence binds `review_stacks_enabled` only to the `allow_all` clause, leaving the `allow_with_label` and `prevent_with_label` clauses ungated. An outside contributor who can label their own PR can trigger stack creation and provisioning even when the operator has set `review_stacks_enabled = false`.

### Finding Description
The binding the operator expects is: `repository.review_stacks_enabled == true` is required for **any** provisioning path (AUTHORIZATION TRUTH). The actual code is: [1](#0-0) 

Because `&&` has higher precedence than `||` in Ruby, this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`

`review_stacks_enabled` is scoped only to the first disjunct. When `review_stacks_enabled = false` and `provisioning_behavior = :allow_with_label`, the first disjunct is `false`, but the second disjunct `(allow_with_label? && pull_request_has_provisioning_label?)` can still be `true` purely based on `pull_request_has_provisioning_label?`, which reads attacker-controlled data: [2](#0-1) 

An attacker opens a PR on their fork and adds a label whose `name` matches `repository.provisioning_label_name` (a value they can observe/guess, e.g. via `docs/review_stacks.md` conventions or by trial). `params.action == "opened"` and `provision?` returns `true`, so `respond_to_pull_request_opened?` passes and `process` calls: [3](#0-2) 

`ReviewStackAdapter#find_or_create!` unconditionally creates the stack and enqueues it for provisioning with no re-check of `review_stacks_enabled`: [4](#0-3) 

The created stack's `branch` is taken directly from `params.pull_request.head.ref`, i.e., the attacker's fork branch: [5](#0-4) 

None of the existing guards prevent this: `params` schema validation only checks types/presence, not label semantics; `respond_to_pull_request_opened?` only checks `action == "opened"` and `provision?`; there is no additional `review_stacks_enabled` check anywhere else in the call path before `Shipit::ReviewStackProvisioningQueue.add(stack)` queues the stack for the `TaskCommands#perform` step that runs `shipit.yml` from the attacker's ref. The existing test suite (`test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`) never exercises `allow_with_label`/`prevent_with_label` together with `provisioning_enabled: false`, so this divergence is untested and unnoticed.

### Impact Explanation
An unprivileged outside contributor can force provisioning of a review stack — and ultimately execution of `shipit.yml` from a branch they control — on a repository whose operator has explicitly disabled review stacks (`review_stacks_enabled = false`). This is repeatable per-PR/per-label and is scoped to Critical: RCE of attacker-authored steps on the deploy host via the eventual `TaskCommands#perform`/`Command`/`PTY.spawn` execution path, entirely bypassing an operator-level kill switch that should block all such provisioning regardless of behavior mode.

### Likelihood Explanation
Preconditions: the target repository must have `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` (common configurations per `docs/review_stacks.md`) while `review_stacks_enabled = false`. Attacker cost is minimal — opening a PR from a fork and adding/removing a label they fully control, no secrets, no privileged role, and no webhook signature forgery needed (this is a legitimate, correctly-signed GitHub webhook for their own PR/label action). This is trivially repeatable against any repository matching the configuration.

### Recommendation
Add explicit parentheses/grouping so `review_stacks_enabled` gates the entire disjunction, e.g.:
```ruby
def provision?
  repository.review_stacks_enabled && (
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
  )
end
```
Apply the same review to any other handler with similar `&&`/`||` chains gated by `review_stacks_enabled` (verify `reopened_handler.rb` and `unlabeled_handler.rb` for the same pattern, since `labeled_handler.rb`'s `respond_to_label_change?` correctly parenthesizes `archive? || unarchive?` separately from `review_stacks_enabled &&`).

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`, add:
```ruby
test "does not create stacks for allow_with_label repos when review_stacks_enabled is false" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,      # operator disabled review stacks
    behavior: :allow_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" } # attacker-controlled

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Binding to assert on both sides: `repository.review_stacks_enabled` (== `false`, set by operator) vs. actual gating behavior of `provision?` (currently evaluates `true` due to precedence, ignoring `review_stacks_enabled`). With the current code, this test fails (`Stack.count` increases by 1), demonstrating the bug; after applying the parenthesization fix, the test passes.
