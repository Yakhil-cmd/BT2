### Title
Unchecked integer division in `PoolState::token_price_x32` can panic on divide-by-zero when vault balances net of accrued fees drop to zero - ([File: programs/cp-swap/src/states/pool.rs])

### Summary
`token_price_x32` computes oracle prices with raw `/` integer division instead of `checked_div`. It is invoked from `get_swap_params`, which is called by both the unprivileged `swap_base_input` and `swap_base_output` instructions on every trade. If either token's "amount without fee" (vault balance minus accumulated protocol/fund/creator fees) is zero, the division panics, aborting the transaction and, more importantly, permanently blocking the swap path for that pool (any subsequent swap attempt that reaches this line will keep panicking) — a Solana-native analog of the QEMU virtio vring divide-by-zero DoS in CVE-2017-17381: an unprivileged, on-chain, attacker-reachable operation triggers a hard divide-by-zero crash instead of a graceful error.

### Finding Description
`vault_amount_without_fee` subtracts the accrued protocol/fund/creator fees from the raw vault token amount to get the "tradable" balance: [1](#0-0) 

`token_price_x32` then divides these tradable balances directly with `/`, with no `checked_div` or zero-guard: [2](#0-1) 

This function is invoked unconditionally by `get_swap_params`, which itself is called on every unprivileged `swap_base_input` / `swap_base_output` transaction: [3](#0-2) [4](#0-3) [5](#0-4) 

Unlike the rest of the codebase, which is careful to use `checked_div`/`checked_mul`/`Option`-returning arithmetic in the curve math (`fees.rs`, `constant_product.rs`), this one function uses raw integer division on values that are directly attacker-influenced: the "tradable" amount equals `vault_balance - accumulated_fees`, and a swapper fully controls trade sizes/directions across a sequence of transactions. If a token's tradable amount is driven to exactly zero (vault balance equal to the sum of `protocol_fees_token_X + fund_fees_token_X + creator_fees_token_X`), any subsequent call into `get_swap_params` for that pool — even a swap in the other direction — divides by zero in `token_price_x32` and panics.

This mirrors the CVE-2017-17381 bug class: a value that legitimate protocol logic assumes will always be non-zero (vring alignment in QEMU; tradable vault balance here) can be driven to zero through normal, permitted operations by an unprivileged party, causing an unguarded division to crash the process/transaction instead of failing safely.

### Impact Explanation
A divide-by-zero panic in an Anchor/Solana program causes the instruction to abort with a runtime panic rather than a controlled `Result::Err`. Once the tradable balance for a pool's token reaches zero, every future `swap_base_input`/`swap_base_output` call that reaches `get_swap_params` (this includes any swap regardless of direction, since both branches of `get_swap_params` call `token_price_x32`) will panic and fail, permanently denying service on that specific pool for further swaps until/unless liquidity is deposited to restore a non-zero tradable balance. This is a availability/DoS impact against the pool's swap functionality reachable by any user, satisfying "permanent freezing of ... pool" functionality for that market.

### Likelihood Explanation
Reaching a state where tradable balance is exactly zero requires the vault's raw balance to exactly equal the accumulated fee ledger for that token. The constant-product swap math (`ConstantProductCurve::swap_base_input_without_fees` / `swap_base_output_without_fees`) bounds output amounts strictly below the vault balance in ordinary conditions, so hitting an *exact* zero tradable balance via normal trading is a narrow, low-probability edge case rather than something trivially forced in one transaction. Precisely engineering vault balance to equal the exact fee-ledger sum (e.g., through very small liquidity pools, many precise trades, or dust-level pools) is plausible but not straightforward to guarantee deterministically from a single attacker-chosen transaction. I could not fully verify within the available context whether any other invariant elsewhere in the codebase (e.g., minimum liquidity locks, `require_gt!` checks) prevents this exact-zero state from ever being reached in practice — this remains an open question that would need dynamic/property testing to confirm.

### Recommendation
- Replace the raw `/` divisions in `token_price_x32` with `checked_div` and propagate `None` to a proper `Result::Err` (e.g., `ErrorCode::MathOverflow`/a new `ErrorCode::InsufficientVault` variant), consistent with the rest of the curve/fee math in the codebase.
- Alternatively, guard `token_price_x32` (and its caller `get_swap_params`) with an explicit `require_gt!(token_0_amount, 0)` / `require_gt!(token_1_amount, 0)` before computing prices, returning a controlled error instead of panicking.

### Proof of Concept
Conceptual trigger (dependent on reaching the exact-zero tradable-balance edge case discussed above, which could not be fully confirmed as reachable within one transaction from the available context):
1. Attacker/LP creates a pool and, through swaps, drives `vault_0.amount` (or `vault_1.amount`) down until it equals exactly `protocol_fees_token_0 + fund_fees_token_0 + creator_fees_token_0` (i.e., `vault_amount_without_fee` returns `0` for that token) — see the subtraction logic at `programs/cp-swap/src/states/pool.rs:213-220`.
2. Any subsequent call to `swap_base_input` or `swap_base_output` on that pool invokes `pool_state.get_swap_params(...)`, which calls `self.token_price_x32(...)` at `programs/cp-swap/src/states/pool.rs:280-281` / `294-295`.
3. `token_price_x32` executes `token_1_amount as u128 * Q32 as u128 / token_0_amount as u128` (or the symmetric expression) at `programs/cp-swap/src/states/pool.rs:226-227` with a zero divisor, causing a Rust integer-division panic and aborting the transaction — denying further swaps on the pool.

    pub fn vault_amount_without_fee(&self, vault_0: u64, vault_1: u64) -> Result<(u64, u64)> {
        let fees_token_0 = self
            .protocol_fees_token_0
            .checked_add(self.fund_fees_token_0)
            .ok_or(ErrorCode::MathOverflow)?
            .checked_add(self.creator_fees_token_0)
            .ok_or(ErrorCode::MathOverflow)?;
        let fees_token_1 = self
            .protocol_fees_token_1
            .checked_add(self.fund_fees_token_1)
            .ok_or(ErrorCode::MathOverflow)?
            .checked_add(self.creator_fees_token_1)
            .ok_or(ErrorCode::MathOverflow)?;
        Ok((
            vault_0
                .checked_sub(fees_token_0)
                .ok_or(ErrorCode::InsufficientVault)?,
            vault_1
                .checked_sub(fees_token_1)
                .ok_or(ErrorCode::InsufficientVault)?,
        ))
    }

    pub fn token_price_x32(&self, vault_0: u64, vault_1: u64) -> Result<(u128, u128)> {
        let (token_0_amount, token_1_amount) = self.vault_amount_without_fee(vault_0, vault_1)?;
        Ok((
            token_1_amount as u128 * Q32 as u128 / token_0_amount as u128,
            token_0_amount as u128 * Q32 as u128 / token_1_amount as u128,
        ))
    }

    pub fn get_swap_params(
        &self,
        input_vault_key: Pubkey,
        output_vault_key: Pubkey,
        input_vault_amount: u64,
        output_vault_amount: u64,
    ) -> Result<SwapParams> {
        let (
            trade_direction,
            total_input_token_amount,
            total_output_token_amount,
            token_0_price_x64,
            token_1_price_x64,
            is_creator_fee_on_input,
        ) = if input_vault_key == self.token_0_vault && output_vault_key == self.token_1_vault {
            let (total_input_token_amount, total_output_token_amount) =
                self.vault_amount_without_fee(input_vault_amount, output_vault_amount)?;
            let (token_0_price_x64, token_1_price_x64) =
                self.token_price_x32(input_vault_amount, output_vault_amount)?;

            (
                TradeDirection::ZeroForOne,
                total_input_token_amount,
                total_output_token_amount,
                token_0_price_x64,
                token_1_price_x64,
                self.is_creator_fee_on_input(TradeDirection::ZeroForOne)?,
            )
        } else if input_vault_key == self.token_1_vault && output_vault_key == self.token_0_vault {
            let (total_output_token_amount, total_input_token_amount) =
                self.vault_amount_without_fee(output_vault_amount, input_vault_amount)?;
            let (token_0_price_x64, token_1_price_x64) =
                self.token_price_x32(output_vault_amount, input_vault_amount)?;

            (
                TradeDirection::OneForZero,
                total_input_token_amount,
                total_output_token_amount,
                token_0_price_x64,
                token_1_price_x64,
                self.is_creator_fee_on_input(TradeDirection::OneForZero)?,
            )
        } else {
            return err!(ErrorCode::InvalidVault);
        };
