### Title
Webhook signature verification is bypassed entirely for any GitHub organization configured with a blank `webhook_secret` - (File: lib/shipit/github_app.rb)

### Summary
`GitHubApp#verify_webhook_signature` returns `true` unconditionally when `@webhook_secret` is blank, and `WebhooksController#verify_signature` calls this method using an org selected by attacker-controlled `repository.owner.login` in the request body, with no engine-side check to require or enforce a webhook secret. Documented multi-org configuration examples (`config/secrets.development.example.yml`, `config/secrets.development.shopify.yml`) explicitly show `webhook_secret:` as a valid, nil-defaulting value per organization, so any host that follows this documented pattern for one org while securing another leaves the unsecured org fully open to unsigned/forged webhooks.

### Finding Description
The broken binding: `verified == (signature is a valid HMAC-SHA1 of the raw body under org's webhook_secret)` should hold for every accepted webhook, but for orgs with `webhook_secret` blank it degrades to `verified == true` unconditionally, regardless of signature.

Code path:
1. `WebhooksController#verify_signature` at [1](#0-0)  resolves the GitHub App instance via `Shipit.github(organization: repository_owner)`, where `repository_owner` is read directly from the untrusted JSON body: [2](#0-1) .
2. `Shipit.github` at [3](#0-2)  looks up per-org config via `github_app_config(organization)`, keyed purely by the attacker-supplied organization string (case-insensitively): [4](#0-3) .
3. `GitHubApp#initialize` sets `@webhook_secret = @config[:webhook_secret].presence`, so a blank/nil secret in config becomes `nil`: [5](#0-4) .
4. `verify_webhook_signature` short-circuits: `return true unless webhook_secret` — no signature, no header, no algorithm check is even reached: [6](#0-5) .
5. Back in the controller, `verified` is `true`, so `head(422) unless verified` never fires, and the request proceeds to `create`, which dispatches the raw, unauthenticated JSON payload to all registered `Shipit::Webhooks` handlers for the event type: [7](#0-6) .

Root cause: the engine treats "no configured secret" as "signature verification passes" rather than "reject all webhooks for this org" or "require configuration." The documented example configs actively encourage leaving `webhook_secret` nil per-org: [8](#0-7) , [9](#0-8) . There is no per-org enforcement flag, no `Shipit.enforce_webhook_secret?`-style setting, and no validation that rejects a configured org lacking a secret.

Existing guards checked and confirmed insufficient: `drop_unhandled_event` only filters by event type, not authenticity [10](#0-9) ; the `GithubOrganizationUnknown` rescue only protects against organizations that aren't configured at all, not ones configured without a secret [11](#0-10) ; downstream handlers (e.g. membership, push, pull_request) perform no additional signature or identity check — they trust the controller's `verify_signature` gate.

### Impact Explanation
For any organization configured (per the engine's own documented example files) with a blank `webhook_secret`, an unauthenticated attacker can POST arbitrary, entirely unsigned JSON to `/webhooks` with `repository.owner.login` (or `organization.login`) set to that org's name and `X-Github-Event` set to any handled event (`push`, `pull_request`, `status`, `check_suite`, `membership`, etc.). This is fully repeatable and not limited to a single request — every request to that org's identity is accepted. Depending on which event/handler is targeted, this enables forged commit statuses, team/membership writes, GithubSyncJob enqueuing for stacks under that org, and other identity-bound writes attributed to a GitHub App that never actually signed anything — a critical authentication bypass matching "webhook accepted without prior authenticated signing" and "payload for one repository mutating another's records" if `repository_owner` can be spoofed relative to actual configured orgs.

### Likelihood Explanation
Preconditions: the host application must have at least one organization configured with `webhook_secret` blank/nil — which is exactly the state shown in the engine's own shipped example config files (`config/secrets.development.example.yml`, `config/secrets.development.shopify.yml`, `template.rb`) as a plausible/documented state, not a hypothetical misconfiguration invented by the attacker. No secrets, sessions, or tokens are required by the attacker — only knowledge of the org name (which is often public, e.g. visible in GitHub URLs) and the ability to send an HTTP POST. This makes exploitation trivial and fully repeatable against any such org.

### Recommendation
Do not treat an absent `webhook_secret` as "verification passes." Options: (1) make `webhook_secret` mandatory at boot/config-load time for every configured organization, failing fast if blank; (2) change `verify_webhook_signature` to `return false unless webhook_secret` (reject rather than accept) so misconfigured orgs are simply non-functional instead of open; (3) add an explicit opt-in flag if unsigned webhooks are ever intentionally desired (e.g., for local dev only, gated by `Rails.env.development?`), never as a silent production-eligible default.

### Proof of Concept

2. POST to `/webhooks` with header `X-Github-Event: pull_request`, no `X-Hub-Signature` header at all, and body `{ action: 'opened', number: 2, pull_request: 'foobar', repository: { owner: { login: 'no-secret-org' } } }.to_json`.

5. Optionally assert a side effect (e.g., a registered `pull_request` handler mock's `call` was invoked, or for `membership` event, `Team.count`/`Membership.count` changed) to show the forged webhook was fully processed as if authenticated.

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
