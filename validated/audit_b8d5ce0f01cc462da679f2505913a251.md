### Title
Uncaught exception on duplicate co-signer address in `evaluate()` crashes the full node process - (File: definition.js)

### Summary
`definition.js`'s `evaluate()` function (used both when validating a new address/asset definition and when validating authentifiers/signatures of an existing definition) contains an unguarded `throw Error("more than 1 address definition")` that is reachable from unit content supplied by an ordinary unit poster. Because ocore's `network.js` deliberately re-throws (and thus crashes the process) on **any** uncaught exception, this throw path is a concrete node-crash Denial-of-Service analog to CVE‑2025‑1394 (an internal integrity check/assert firing on attacker-influenced data and taking down the process), even though the two projects use unrelated code bases.

### Finding Description
Both `validateDefinition()` and `validateAuthentifiers()` in `definition.js` handle the `'address'` operator (a definition referencing another, "inner" address as one of the signing conditions) by looking up the inner address's already-registered definition; if it isn't found yet, they fall back to searching for a definition supplied inline by one of `objUnit.authors` in the very same unit: [1](#0-0) [2](#0-1) 

Both blocks filter `objUnit.authors` by address+chash match and then assert `arrDefiningAuthors.length` is at most 1, throwing a hard `Error` (not returned via the `cb`/`handleResult` callback used for ordinary validation failures) if it isn't:
```js
if (arrDefiningAuthors.length > 1)
    throw Error("more than 1 address definition");
```
This is a genuine `throw`, not a `return cb(err)` — it propagates up through the async call chain as an uncaught exception rather than as a validation failure. Nothing in the surrounding `validateDefinition`/`validateAuthentifiers` code, nor in `validateAuthor`/`validate()` in `validation.js`, wraps this evaluation in a try/catch that would convert it into a normal `ifUnitError`.

The precondition for hitting the `length > 1` branch is that `objUnit.authors` contains **more than one entry with the same address** whose supplied `definition` hashes to the same `definition_chash` referenced by the `'address'` operator. I was unable to find an explicit, unconditional check in `validation.js` that rejects a unit whose `authors` array contains duplicate `address` values before author-level validation and definition evaluation run (the code I inspected checks `isNonemptyArray(objUnit.authors)` and that every author address is a valid address string, but I did not confirm a dedicated "no duplicate author addresses" check executes before `validateAuthentifiers`/`evaluate()` is invoked). If such a check does not exist (or can be bypassed, e.g. via a "definition template" expansion that produces the collision only after templating), a unit crafted with two authors sharing the same address, each carrying an identical inline `definition`, and a third unrelated address's definition containing `["address", <that shared address>]`, would drive `arrDefiningAuthors.length` to 2 and trigger the throw during standard, permissionless unit validation.

### Impact Explanation
Because `network.js` installs a top-level `process.on('uncaughtException', ...)` handler that logs diagnostics and then re-throws to intentionally crash the process: [3](#0-2) 
any full/hub node that receives and processes such a unit during normal `validate()` flow (unit posted directly by an unprivileged author, no operator/hub/light-vendor privilege required) will crash. If the malicious unit propagates through the network (as any well-formed, validly-hashed unit would), every full node that validates it crashes — a network-wide denial of service that prevents new units from being confirmed, matching the "network unable to confirm new units" acceptance criterion.

### Likelihood Explanation
The `'address'` (inner-address) operator and the "definition supplied inline by an author in the same unit" fallback are ordinary, well-documented oscript definition features (used for nested/shared addresses), reachable by any address owner composing a standard payment/definition-change unit — no special privilege, AA, or hub/operator role is required. The only uncertain factor is whether ocore elsewhere rejects units with duplicate author addresses outright; this needs to be confirmed/patched regardless, because even if a duplicate-address check exists today, the `throw Error` here is inherently unsafe: any future code path that legitimately produces `arrDefiningAuthors.length > 1` (e.g., through templated/generated definitions) turns into a full-network crash instead of a rejected unit.

### Recommendation
- Replace the `throw Error("more than 1 address definition")` calls in both `validateDefinition`'s `'address'` handler (definition.js:299) and `validateAuthentifiers`'s `'address'` handler (definition.js:795) with a normal validation-failure return (`return cb("more than 1 address definition")` / `return cb2(false)`), consistent with the rest of `evaluate()`'s error handling.
- Independently verify/add an explicit check in `validation.js` that rejects units containing duplicate `authors[].address` entries before any per-author definition evaluation runs, since author-address uniqueness is a security-relevant invariant for the whole authentication/signature-checking pipeline, not just this one code path.
- Audit `definition.js` and `aa_validation.js`/`formula/*.js` for other unguarded `throw Error(...)` statements inside functions reachable directly from untrusted unit/trigger content (as opposed to `cb(err)`/`setFatalError`), given that any of them will crash the whole node due to the global `uncaughtException` handler.

### Proof of Concept
Conceptual (schema-level) PoC, to be turned into an actual signed/hashed unit by a Devin engineering session with access to the composer/test harness:
1. Create address `A` whose definition is `["address", "S"]` (i.e., `A`'s spending condition delegates to address `S`).
2. Craft a unit `U` with two authors both using address `S`:
   - `authors[0] = { address: "S", definition: D, authentifiers: {...} }`
   - `authors[1] = { address: "S", definition: D, authentifiers: {...} }`
   where `D` is a definition array such that `objectHash.getChash160(D)` equals the `definition_chash` that `S` is currently bound to (or, for a fresh address, equals `S` itself), so that `arrDefiningAuthors.filter(author => author.address === "S" && getChash160(author.definition) === definition_chash)` matches both authors.
3. Have `A` (or any address referencing `S` via `["address","S"]`) be part of `U`'s signing set, so that `evaluate()`/`validateAuthentifiers` on `A`'s definition walks into the `'address'` case and performs the inner lookup on `S`.
4. Broadcast `U`. When any full node runs `validation.validate()` → `validateAuthor` → `Definition.validateAuthentifiers` → `evaluate()`'s `'address'` case and reaches the `ifDefinitionNotFound` branch with `arrDefiningAuthors.length === 2`, it throws `Error("more than 1 address definition")`, which is uncaught and crashes the node process via the global handler in `network.js`.
