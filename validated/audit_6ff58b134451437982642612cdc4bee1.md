### Title
Push-webhook signature is verified against the org derived from `repository.owner.login`, but the stack that gets synced is selected from `repository.full_name` — an attacker with a legitimate GitHub App on an unrelated org can forge a signed webhook that acts on any other tenant's stack ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App configuration (and therefore which `webhook_secret`) to verify the HMAC signature against based on `repository_owner`, computed from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). [1](#0-0)  Once the signature is accepted, the actual event handler resolves the target `Repository`/`Stack` from a *different* JSON field in the same payload: `payload.dig('repository', 'full_name')`. [2](#0-1)  Because these two fields are never cross-checked against each other, an attacker who legitimately controls a GitHub App/organization installation configured in this Shipit instance (multi-org setup, see `docs/setup.md`) can compute a valid HMAC over a payload where `repository.owner.login` names their own org (so signature verification succeeds using their own known `webhook_secret`) while `repository.full_name` names an entirely different, victim, repository/stack. This breaks the binding "organization that authenticated == repository that is written."

### Finding Description
- Signature check: `Shipit.github(organization: repository_owner)` selects the per-organization `GitHubApp` config, then `verify_webhook_signature` HMACs the raw request body with that org's `webhook_secret`. [3](#0-2) [4](#0-3) 
- `repository_owner` is read from `params.dig('repository', 'owner', 'login')`. [5](#0-4) 
- The payload is fully attacker-controlled JSON (the controller just does `JSON.parse(request.raw_post)`), so as long as the attacker knows the `webhook_secret` for *some* configured organization (their own, legitimately installed app), they can produce a body whose `repository.owner.login` matches that org and whose HMAC verifies. [6](#0-5) 
- After verification, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches to handlers such as `PushHandler`, which resolve the acted-upon stacks purely from `payload.dig('repository', 'full_name')` via `Handler#stacks`/`#repository_name`. [2](#0-1)  `Repository.from_github_repo_name` then splits that string on `/` to find `owner`/`name` independent of whatever org was used for signature verification. [7](#0-6) 
- `PushHandler#process` then calls `stack.sync_github(expected_head_sha: params.after)` on every matching (non-archived, branch-matching) stack, using the attacker-supplied `after` SHA and `ref`. [8](#0-7) 

This is a direct analog of the reported bug class: the field covered by the trust check (`repository.owner.login`, used to pick the verifying secret) is not the field the resulting action is bound to (`repository.full_name`, used to pick the target stack) — i.e. "an organization that authenticated versus the repository that is written."

### Impact Explanation
An attacker who is a legitimate administrator of any one GitHub App/organization configured in a shared, multi-tenant Shipit instance (which the engine explicitly supports per `docs/setup.md`'s "Using Multiple Github Applications" section) can forge webhook payloads that pass signature verification under their own org's secret, but that target and mutate the state of a completely unrelated organization's/repository's `Stack` (triggering `GithubSyncJob`/`sync_github`, and depending on other handlers registered for `push`/`status`/`check_suite`/etc., other cross-repository side effects gated only by `repository.full_name`/`repository.owner.login` mismatch). This crosses a repository/tenant trust boundary using credentials that were never intended to authorize actions on the victim repository, matching the "cross-repository writes" / unauthorized state-mutation impact category for this engine.

The severity is capped by what handlers actually do with attacker-controlled `full_name`/`after`/`ref` fields; I could not fully trace `Stack#sync_github`/`GithubSyncJob` body within the remaining budget to confirm whether this can force an actual unauthorized deploy versus only an out-of-band resync, so I flag that boundary explicitly as unverified.

### Likelihood Explanation
Requires the attacker to control at least one legitimate, configured GitHub App organization on the same Shipit instance (multi-org deployments only) and knowledge of the corresponding `webhook_secret` for their own org — a realistic scenario for any organization that self-registers on a shared Shipit deployment used by multiple teams/orgs. No privileged Shipit session, `ApiClient` token, or the victim org's secret is required, satisfying the "unprivileged attacker" constraint.

### Recommendation
Bind the field used to select the verifying `webhook_secret` to the same field used to select the acted-upon repository: verify the signature using the organization implied by `repository.full_name` (or, equivalently, re-derive `repository_owner` from the exact string used later by `Handler#repository_name`), and reject the webhook if the `organization.login`/`repository.owner.login` fields disagree with the owner portion of `repository.full_name`.

### Proof of Concept
1. Configure Shipit with two organizations in `config/secrets.yml`: `attacker-org` (attacker's own legitimate GitHub App, secret known to attacker) and `victim-org` (hosts the target stack), per the multi-org config format documented in `docs/setup.md`. [9](#0-8) 
2. Attacker crafts a push webhook JSON body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen sha>",
     "repository": {
       "owner": { "login": "attacker-org" },
       "full_name": "victim-org/victim-repo"
     }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org's webhook_secret, raw_body)>` and POSTs to `/webhooks` with header `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: 'attacker-org')` and the HMAC validates successfully. [3](#0-2) 
5. `PushHandler` resolves `repository_name` as `"victim-org/victim-repo"` and runs `stack.sync_github(expected_head_sha: <attacker-chosen sha>)` against `victim-org`'s stack, despite the request never having been authenticated by `victim-org`'s webhook secret. [8](#0-7)

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
