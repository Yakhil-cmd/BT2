## Title
Unauthenticated GET /events allows reading live task/stack pubsub broadcasts - ([File: config/routes.rb])

### Summary
`mount Pubsubstub::StreamAction.new, at: "/events"` is registered directly inside `Shipit::Engine.routes.draw` as a mounted Rack app, not a controller action, so it never passes through the `Shipit::Authentication` concern's `force_github_authentication` `before_action`. Any client can subscribe to any channel by guessing/enumerating IDs (e.g., `stack.<id>`, `task.<id>`) and receive live SSE broadcasts.

### Finding Description
The broken binding: for every other resource, `AUTHORIZATION_TRUE = (current_user.logged_in? && current_user.authorized?)` is enforced before rendering via `force_github_authentication` in [1](#0-0)  included by `Shipit::ShipitController`. But `/events` is mounted as a raw Rack app in the routes file, bypassing the entire controller stack (no `before_action` can run against it because it's not an action of an `ActionController` subclass): [2](#0-1) .

Channels are named predictably from database primary keys, e.g. `"stack.#{id}"` is published on every stack update: [3](#0-2) , and the stack view subscribes clients with `subscribe events_path(channels: ["stack.#{@stack.id}"])` [4](#0-3) . An unauthenticated attacker can replicate this exact subscription request (`GET /events?channels[]=stack.<id>`, or similarly guessable task-output channels) directly against the mounted `Pubsubstub::StreamAction`, which has no knowledge of `Shipit::Authentication`, `current_user`, or `session[:user_id]` at all.

None of the existing guards apply: `force_github_authentication` only runs as a controller `before_action`, and `Pubsubstub::StreamAction` is a plain Rack endpoint mounted before any such filters can execute. There is no signature/token check on the `/events` mount in this engine's code.

### Impact Explanation
An unauthenticated party can subscribe to `stack.<id>` (or other broadcast channels used elsewhere, e.g., task/output channels used by `page_updater.js.coffee`) and receive real-time update events for any stack, without ever holding a session, `ApiClient` token, or being in `Shipit.github_teams`. This is an unauthenticated read of stack/task state — matching the "High: unauthenticated read of stack state, task streams or deploy output" impact category. It is repeatable against arbitrary stacks purely by enumerating small integer IDs, with no rate limiting or authorization check in front of the mount.

### Likelihood Explanation
No special Shipit configuration is required beyond the engine being mounted as documented (which the audit assumes). The attacker only needs network access to the Shipit host and a guessable/enumerable stack or task ID (sequential integers), which is trivial to enumerate. This is a very low-cost, highly repeatable attack path.

### Recommendation
Wrap the `/events` mount so it goes through authentication before reaching `Pubsubstub::StreamAction` — e.g., route it to a thin controller action that includes `Shipit::Authentication`/checks `current_user.authorized?` and per-channel authorization (verifying the requesting user has access to the specific stack/task referenced by the channel name) before delegating to the Pubsubstub stream, rather than mounting the Rack app directly and unconditionally.

### Proof of Concept
```ruby
# test/integration/unauthenticated_events_stream_test.rb (proposed, not present in repo)
test "GET /events without a session is not redirected to github_authentication_path" do
  stack = shipit_stacks(:shipit)
  get "/events", params: { channels: ["stack.#{stack.id}"] }

  # Binding under test: for authenticated resources, unauthenticated requests
  # are 302 redirected to github_authentication_path.
  # AUTHORIZATION_TRUTH: response.status == 302 && response.location =~ /github\/auth\/github/
  assert_not_equal 302, response.status
  assert_no_match(/github\/auth\/github/, response.headers["Location"].to_s)
end
```
Note: full verification of `Pubsubstub::StreamAction`'s exact response code/behavior (200 vs 101 vs streaming chunked response) requires inspecting the `pubsubstub` gem source, which is outside this engine's own code and was not available in the indexed repo contents; the routing-level bypass of `Shipit::Authentication`, however, is directly demonstrated in `config/routes.rb` and the `Authentication` concern above.

    module ClassMethods
      def skip_authentication(*args)
        skip_before_action(:force_github_authentication, *args)
      end
    end

    private

    def force_github_authentication
      if current_user.logged_in? && current_user.requires_fresh_login?
        Rails.logger.warn("User #{current_user.id} requires a fresh login, logging out...")
        reset_session
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      elsif Shipit.authentication_disabled? || current_user.logged_in?
        unless current_user.authorized?
          team_handles = Shipit.github_teams.map(&:handle)
          team_list = team_handles.to_sentence(two_words_connector: ' or ', last_word_connector: ', or ')
          render(plain: "You must be a member of #{team_list} to access this application.", status: :forbidden)
        end
      else
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      end
    end
