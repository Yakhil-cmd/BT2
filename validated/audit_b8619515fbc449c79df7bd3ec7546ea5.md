## Title
Virgin stake can claim all accumulated `pending_delegator_rewards` after a zero-active-stake gap - ([File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs])

## Summary
The block-revenue-sharing distribution (`calculate_block_reward`, SIMD-0123) splits a vote account's `pending_delegator_rewards` among delegators strictly proportional to `stake / total_active_stake` at the rewarded epoch, with the only safety check being `total_active_stake == 0 → 0`. Unlike the inflation-reward path, it has no check that skips or discounts stake that was *just* (re)activated after a period during which the vote account had zero active stake. `pending_delegator_rewards` itself accrues independently of `total_active_stake` via the permissionless `DepositDelegatorRewards` instruction. If a vote account's active stake drops to zero for one or more epochs while `pending_delegator_rewards` keeps accumulating, the very next staker to activate becomes 100% of `total_active_stake` and, per `calculate_block_reward`'s ratio, is paid the *entire* pending pool — exactly analogous to the wxETH "virgin stake claims all drops" bug, except here the loss falls on the delegators who legitimately earned that revenue while staked.

## Finding Description
`calculate_block_reward` computes each delegation's share of a vote account's block revenue: [1](#0-0) 

The only guard is `if total_active_stake == 0 { 0 }`; there is no equivalent of the inflation-reward path's protection for "just activated" stake: [2](#0-1) 

`total_active_stake` here is the snapshot of `reward_epoch_delegated_stakes.delegated_stakes` for the vote account at `rewarded_epoch`, produced by `calculate_activated_stake`/`Stakes::calculate_activated_stake` — i.e., the effective (warmed-up) stake for that voter at that epoch: [3](#0-2) 

`pending_delegator_rewards` accrues through the permissionless `DepositDelegatorRewards` instruction, which requires only a signature from the depositing source account — it does not require the vote account to currently have any delegated stake: [4](#0-3) [5](#0-4) 

Because `calculate_block_reward` returns `0` whenever `total_active_stake == 0` (correctly avoiding a divide-by-zero), any block revenue deposited into a vote account while it has zero active stake is neither distributed nor discarded — it simply keeps accumulating in `pending_delegator_rewards`, which is also protected from withdrawal by the vote-withdraw path: [6](#0-5) 

When a new delegation to that vote account subsequently warms up and becomes the vote account's entire `total_active_stake`, `calculate_block_reward`'s ratio `stake / total_active_stake` evaluates to (approximately) `1`, so the new stake is paid the *whole* accumulated `pending_delegator_rewards`, regardless of how briefly it has been staked or how large the deposit accrued from prior stakers.

## Impact Explanation
This results in misattributed rewards: lamports that were deposited as revenue-share owed to delegators who staked to the validator during the accrual period are instead paid entirely to whichever stake happens to be the first (or only) active delegation once `total_active_stake` becomes non-zero again. This is a direct redirection of value away from the delegators who actually earned it, satisfying the "misattributed or duplicated rewards" impact criterion. It is reachable purely through the reward-distribution/stake-accounting path (`calculate_block_reward` in the partitioned epoch rewards calculation), not through any validator/operator-privileged action — anyone can call `DepositDelegatorRewards` and anyone can create/activate a small stake delegation.

## Likelihood Explanation
The precondition — a vote account's active stake transiently dropping to zero while `pending_delegator_rewards` is non-zero, followed by fresh stake activation — is a plausible, achievable state: stake accounts can fully deactivate/withdraw, and `DepositDelegatorRewards` can be called by anyone at any time, independent of the vote account's current stake. An attacker (or even an innocent party) merely needs to activate a stake delegation to a vote account they identify as having a zero-stake epoch gap with pending rewards, then wait one warm-up epoch to collect the full pool as the sole active delegator.

## Recommendation
Mirror the "just activated" protection already used in `calculate_stake_rewards`/`redeem_delegation_rewards` for block-revenue distribution: skip (or clamp to zero) block-reward payout for a delegation activated within the epoch(s) during which `total_active_stake` for that vote account transitioned from zero to non-zero, or more generally, only allow a delegation to be paid its proportional share of `pending_delegator_rewards` that accrued while that specific stake was actively contributing to `total_active_stake`. Alternatively, disallow `DepositDelegatorRewards` (or zero-out/return unattributed pending rewards) for vote accounts observed with `total_active_stake == 0`, similar to the wxETH mitigation of not accruing drips when `totalSupply == 0`.

## Proof of Concept
1. Vote account `V` has delegators; block revenue accrues into `V.pending_delegator_rewards` via `DepositDelegatorRewards` over several epochs (SIMD-0123 flow) — `runtime/src/bank/partitioned_epoch_rewards/calculation.rs:173-232` correctly computes zero payout only when `total_active_stake == 0`.
2. All delegators to `V` deactivate/withdraw their stake; `V`'s `total_active_stake` in `reward_epoch_delegated_stakes` becomes `0` for one or more epochs. During these epochs `calculate_block_reward` returns `0` (per line 211-212), but `pending_delegator_rewards` is untouched and keeps growing from further `DepositDelegatorRewards` calls (`programs/vote/src/vote_state/mod.rs:935-988`).
3. An attacker creates a stake account and delegates a small amount to `V`, then waits for it to fully warm up so that `delegation_effective_stake(...) == total_active_stake` for `V` at the rewarded epoch.
4. At the next reward calculation, `calculate_block_reward` computes `pending_delegator_rewards * stake / total_active_stake ≈ pending_delegator_rewards` (ratio ≈ 1), and the attacker's stake account is credited the entire pool via `PartitionedStakeReward.block_reward`, distributed in `store_stake_accounts_in_partition`/`build_updated_stake_reward` (`runtime/src/bank/partitioned_epoch_rewards/distribution.rs:239-325`), even though the attacker contributed nothing during the epochs the revenue was earned.

    pub(crate) fn calculate_activated_stake(
        &self,
        next_epoch: Epoch,
        thread_pool: &ThreadPool,
        new_rate_activation_epoch: Option<Epoch>,
        stake_delegations: &[(&Pubkey, &StakeAccount)],
        use_fixed_point_stake_math: bool,
    ) -> (
        StakeHistory,
        VoteAccounts,
        DelegatedStakes,
        RewardEpochDelegatedStakes,
    ) {
        // Wrap up the prev epoch by adding new stake history entry for the
        // prev epoch.
        let (stake_history_entry, effective_delegated_stakes) = thread_pool.install(|| {
            stake_delegations
                .par_iter()
                .fold(
                    || (StakeActivationStatus::default(), HashMap::default()),
                    |(acc, mut delegated_stakes), (_stake_pubkey, stake_account)| {
                        let delegation = stake_account.delegation();
                        let activation_status = delegation_activation_status(
                            delegation,
                            self.epoch,
                            &self.stake_history,
                            new_rate_activation_epoch,
                            use_fixed_point_stake_math,
                        );
                        *delegated_stakes.entry(delegation.voter_pubkey).or_default() +=
                            activation_status.effective;
                        (acc + activation_status, delegated_stakes)
                    },
                )
                .reduce(
                    || (StakeActivationStatus::default(), HashMap::default()),
                    |(activation_status_a, delegated_stakes_a),
                     (activation_status_b, delegated_stakes_b)| {
                        (
                            activation_status_a + activation_status_b,
                            merge_delegated_stakes(delegated_stakes_a, delegated_stakes_b),
                        )
                    },
                )
        });
        let mut stake_history = self.stake_history.clone();
        stake_history.add(self.epoch, stake_history_entry);
        // Refresh the stake distribution of vote accounts for the next epoch,
        // using new stake history.
        let (vote_accounts, delegated_stakes) = refresh_vote_accounts(
            thread_pool,
            next_epoch,
            &self.vote_accounts,
            stake_delegations,
            &stake_history,
            new_rate_activation_epoch,
            use_fixed_point_stake_math,
        );
        let reward_epoch_delegated_stakes = RewardEpochDelegatedStakes {
            epoch: self.epoch,
            delegated_stakes: effective_delegated_stakes,
        };
        (
            stake_history,
            vote_accounts,
            delegated_stakes,
            reward_epoch_delegated_stakes,
        )
    }

/// Deposit delegator rewards into a vote account (SIMD-0123).
pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}

    pub(crate) fn add_pending_delegator_rewards(
        &mut self,
        amount: u64,

            TargetVoteState::V4(v4) => {
                v4.pending_delegator_rewards = v4
                    .pending_delegator_rewards
                    .checked_add(amount)
                    .ok_or(InstructionError::ArithmeticOverflow)?;
                Ok(())
            }
