### Title
Webhook signature is verified against `repository.owner.login`/`organization.login` while the repository actually mutated is resolved from the unauthenticated `repository.full_name` field, allowing cross-organization webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification based on `repository.owner.login` (falling back to `organization.login`), but every webhook handler that actually mutates state (push, pull request, etc.) resolves the target `Repository`/`Stack` from a *different* JSON field, `repository.full_name`. Because the signature only proves the payload was signed with the secret belonging to the org named in `owner.login`, and `full_name` is never cross-checked against that same org, an attacker who legitimately controls one Shipit-configured GitHub organization (and therefore knows/controls that organization's webhook HMAC secret via its installed GitHub App) can forge a payload whose `owner.login` matches their own org (so the signature check passes) while `repository.full_name` names a repository belonging to an entirely different organization managed by the same Shipit instance.

### Finding Description
`verify_signature` picks the verifying `GithubApp` purely off attacker-supplied JSON: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the per-organization `GithubApp` instance and its `webhook_secret`, and `verify_webhook_signature` only proves the raw body was HMAC-signed with *that org's* secret: [3](#0-2) 

Once verification passes, `WebhooksController#create` dispatches the *entire* parsed JSON body to handlers, with no re-validation that `owner.login` (the field that was authenticated) matches `repository.full_name` (the field that determines which record is mutated): [4](#0-3) 

Every handler resolves its target purely from `repository.full_name`: [5](#0-4) [6](#0-5) 

For the `push` event, this drives a `GithubSyncJob`/`sync_github` call against whatever stack matches `full_name`+`branch`, regardless of which org's secret actually signed the request: [7](#0-6) 

This is exactly the "organization that authenticated versus the repository that is written" binding break: the signature authenticates `X == owner.login`, but the code acts on `Y == repository.full_name`, and `X` is never proven to own `Y`.

### Impact Explanation
On a multi-tenant Shipit deployment (multiple GitHub organizations each with their own GitHub App/webhook secret configured via `Shipit.github(organization: ...)` / raising `Shipit::GithubOrganizationUnknown` for unknown orgs — evidenced by `test "unknown github organization logs and returns unprocessable entity"` and the `shopify_membership`/`cyclimse_push` fixtures using distinct secrets per org), an attacker who controls Organization A (and thus knows/can trigger delivery of Organization A's legitimate webhook secret through their own installed GitHub App) can forge a `push` webhook whose `repository.owner.login` is `"org-a"` but whose `repository.full_name` is `"org-b/some-repo"`. The signature check succeeds using org‑A's secret, yet `PushHandler` resolves and syncs/deploys the stack belonging to org‑B. This is a cross-organization/cross-repository write: it can trigger unwanted `GithubSyncJob` execution and, for stacks configured for continuous deployment, unauthorized deploy triggers against a repository/organization the attacker does not control — matching the "Critical: cross-repository writes, unauthorized deploy" impact bar.

### Likelihood Explanation
Requires the attacker to control at least one organization onboarded to the same shared Shipit instance (a realistic and unprivileged position for a multi-tenant deploy tool), and to craft the `repository.owner.login`/`full_name` mismatch in the JSON payload themselves (they fully control the payload they send once they know their own secret). No GitHub App private key, `webhook_secret` of the victim org, Shipit session, or API token is needed — only the attacker's own (unprivileged, already-known-to-them) organization secret, satisfying the "unprivileged attacker" constraint.

### Recommendation
After successful signature verification, re-derive the organization the request was authenticated for and assert that `repository.full_name.split('/').first` (or `organization.login` for org-scoped events) matches `repository_owner` used in `verify_signature`, rejecting the request otherwise. Alternatively, bind the `GithubApp`/secret used for verification into the handler dispatch so handlers can only act on repositories under the verified organization.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` and `org-b`, each with its own GitHub App and `webhook_secret` (as supported by `Shipit.github(organization:)`).
2. As the (unprivileged, non-Shipit) owner of `org-a`'s GitHub App/webhook secret, POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" }
}
```
3. Sign the raw body with `org-a`'s known `webhook_secret` using the same algorithm as `Hook::DeliverySigner`/`verify_webhook_signature` (`sha1=<hmac>` per `lib/shipit/github_app.rb` line 76-83) and set it as `X-Hub-Signature`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "org-a")` and succeeds, because the signature genuinely matches `org-a`'s secret.
5. `PushHandler#process` resolves the stack via `Repository.from_github_repo_name("org-b/victim-repo")`, which belongs to `org-b`, and triggers `stack.sync_github` for it — an org-a-authenticated request causing a mutation on an org-b resource.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
