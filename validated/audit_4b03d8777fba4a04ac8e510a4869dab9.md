### Title
Webhook signature verification key is selected from an unauthenticated field, allowing forged events to be attributed to any tracked repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` determines which GitHub App configuration (and therefore which `webhook_secret`) to use for HMAC verification by reading `repository.owner.login` (or `organization.login`) directly out of the **unauthenticated** request body, before the signature has been checked. The org-selected secret is then used only to authenticate the signature, while the handlers that actually act on the request (creating deploy jobs, statuses, etc.) operate on the *entire* parsed payload, including fields such as `repository.full_name` that are never cross-checked against the org used for verification. This mirrors the `_isZeroBytes` bug class: a field consumed to decide "is this authenticated" (`repository.owner.login`, used to pick the key) is not the same field bound by the resulting proof (the rest of the payload, notably the repo that gets written to), so the equality "org that authenticated == repo that gets written" is never enforced.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` does: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`repository_owner` is read straight from the (as-yet-unverified) request body, and is used purely to pick which of the configured GitHub Apps' `webhook_secret` to verify the signature against, per `Shipit.github`: [3](#0-2) 

`GitHubApp#verify_webhook_signature` then does: [4](#0-3) 

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```

If **any** configured organization in a multi-org setup (`Shipit.github_organizations`) has no `webhook_secret` set — which the documentation explicitly calls "optional" — then `verify_webhook_signature` unconditionally returns `true` for that org, regardless of the actual signature header. The setup docs and fixture configs (e.g. `config/secrets.development.shopify.yml`, `test/dummy/config/secrets_double_github_app.yml`) show `webhook_secret: # nil` is a supported/expected configuration: [5](#0-4) 

An attacker who knows (or guesses) that one org in the multi-org configuration has no secret can craft a payload whose `repository.owner.login`/`organization.login` names that unsecured org (to trivially pass `verify_signature`), while every other field consumed by the actual event handlers — most importantly `repository.full_name`, which handlers use to locate the target `Stack`/`Repository` record — names a completely different, secured organization/repository. Because `create` re-parses the same raw body and dispatches it unmodified to handlers: [6](#0-5) 

the org used to select/pass the signature check is never bound to the org/repo that is actually acted on. The "verified" guarantee ("this payload came from GitHub for org X") does not transitively guarantee "the repository referenced in this payload belongs to org X" — exactly the same class of defect as `_isZeroBytes` returning `true` for data it never fully validated.

### Impact Explanation
This breaks the binding "organization that authenticated == repository that is written." An external, unauthenticated attacker can forge `push`, `status`, `check_suite`, etc. webhook deliveries for any `Stack` tracked by Shipit, as long as the deployment has at least one configured GitHub organization without a `webhook_secret`. Forged `push` events enqueue `GithubSyncJob` and can drive unauthorized deploy/rollback pipeline activity; forged `status`/`check_suite` events forge commit statuses/check runs that gate merges and deploys. This can lead to unauthorized deploys or corrupted deploy-readiness state for repositories the attacker has no access to — matching the "unauthorized deploy, rollback" Critical impact bucket, and at minimum the High-impact "unauthenticated write of stack/task state" bucket.

### Likelihood Explanation
Requires a multi-organization Shipit deployment where at least one configured org has no `webhook_secret` set (a state the project's own docs present as a normal, supported, optional configuration, not a misconfiguration). No credentials, GitHub App keys, or Shipit session are required — only knowledge (or a `ping`/error-triggered discovery, or simply guessing) of the unsecured org's name. This is plausible in real deployments that mix internal orgs behind a firewall (no secret needed) with an externally reachable public org, unaware that the internal org's lack of a secret undermines authentication for all other orgs sharing the same `/webhooks` endpoint.

### Recommendation
Cross-validate that the `repository`/`organization` login used to select the verification key is consistent with, and covers, all repository-identifying fields the handlers subsequently act on (e.g., derive the acting org strictly from the same verified field, or bind the whole payload's implied org to a canonicalized value before dispatch). Additionally, do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is blank for a given org configuration in a multi-org setup — either require a secret for every org when more than one org is configured, or reject/short-circuit unsigned requests explicitly rather than treating "no secret configured" as "verification passed."

### Proof of Concept
Assume `secrets.github` configures two orgs: `unsecured-org` (no `webhook_secret`) and `secured-org` (real repos deployed via Shipit, secret set).

```http
POST /webhooks HTTP/1.1
X-Github-Event: push
Content-Type: application/json

{
  "repository": {
    "owner": { "login": "unsecured-org" },
    "full_name": "secured-org/production-app"
  },
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>"
}
```
- `repository_owner` resolves to `"unsecured-org"` → `Shipit.github(organization: "unsecured-org")` → `webhook_secret` is blank → `verify_webhook_signature` returns `true` with **no** `X-Hub-Signature` header needed.
- `verify_signature` passes; `create` dispatches the full payload (`repository.full_name = "secured-org/production-app"`) to `Shipit::Webhooks.for_event("push")` handlers, which look up the `Stack` by `secured-org/production-app` and enqueue a sync/deploy-relevant job for a repository the attacker never authenticated for.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
