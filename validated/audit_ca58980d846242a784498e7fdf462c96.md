### Title
Attacker-crafted swap route puts arbitrary contracts on the call stack beneath the caller's authorization, enabling theft of unrelated wallet tokens — ([File: contracts/controller/src/strategies/swap.rs])

### Summary
The libzypp bug class is "an attacker-controlled `path` component escapes the intended scope of a file write." The analog here is an attacker-controlled *route* component: the pool/token addresses embedded in `swap_xdr` escape the intended scope of a swap, because neither the controller nor the router allowlists which contracts a route may invoke. A malicious venue contract placed in the route runs below the victim's `require_auth` tree and can issue `token.transfer(victim, attacker, …)` for any unrelated wallet token; an honest simulation records that transfer as a child of the victim's authorization entry, and it executes if the victim signs the simulated tree.

### Finding Description
`swap_tokens` forwards the opaque `swap_xdr` bytes to the configured router after authorizing only one exact input transfer via `authorize_transfer_as_current` [1](#0-0) . The controller guards its own balances (`RouterOverspend`, `NoSwapOutput`) [2](#0-1) , but nothing constrains which contracts the route names. The router dispatches hops to payload-supplied pool addresses with no venue allowlist [3](#0-2) , and the threat model concedes "a route can put third-party code on the call stack below the caller's authorization" [4](#0-3) . The harness test demonstrates a `RogueHopPool` whose `swap` calls `token::Client::transfer(&victim, &to, &amount)` on an unrelated wallet token; recording mode attaches the transfer to the caller's `swap_collateral` auth entry, and enforcing mode executes it when the signed tree lists it [5](#0-4) [6](#0-5) .

### Impact Explanation
Theft of user funds: any token in the victim's wallet (including tokens the protocol never listed) can be moved to the attacker in the same transaction that performs an otherwise legitimate `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`, or standalone `execute_strategy`. The payload minimum-output check and the controller's balance-delta checks do not bound the loss because the stolen transfer never touches routed funds.

### Likelihood Explanation
The exploit requires the victim to sign an authorization tree that contains the rogue child transfer — i.e., a malicious or compromised route payload (e.g., served by a tampered quote or phishing flow) whose simulation output the wallet signs without inspecting children. It is not self-executing, which keeps it at Medium rather than High; but every property needed on-chain (unallowlisted hop addresses, venue code running under the caller's auth tree) is present and proven by the harness test.

### Recommendation
Constrain the route so it cannot name arbitrary contracts: maintain an on-chain venue/pool allowlist or bind hop adapters to pool addresses registered by governance, so a payload cannot graft foreign code onto the caller's auth tree. At minimum, document/enforce that clients must reject any simulated auth tree containing children other than the single input `transfer`, and consider emitting a controller-side event or check that fails the swap if unexpected sub-invocations appear in the recorded tree.

### Proof of Concept
See `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` : `UnlistedPoolRouter::execute_strategy` invokes the route's `hop_pool` [7](#0-6) ; `RogueHopPool::swap` transfers Alice's unrelated `wallet_token` to the attacker [5](#0-4) . `enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer` shows the honest tree is refused but the simulated/poisoned tree executes, leaving `wallet(alice) == 0` and `wallet(attacker) == WALLET_BALANCE` [6](#0-5) .

Note: `docs/explanation/threat-model.md:154-165` already describes this exposure and assigns mitigation to clients; if you consider that a documented/accepted design choice, this finding should be downgraded accordingly.
