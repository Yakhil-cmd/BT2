### Title
Overflowing accrued market value permanently freezes repayment and withdrawal - (File: common/src/rates/simulate.rs)

### Summary
A sufficiently large borrowed market can make `borrowed * borrow_index / RAY` exceed `i128::MAX`, causing `GenericError::MathOverflow` during routine interest accrual. Because borrow, repay, withdraw, and index updates all accrue before mutating state, the market becomes unusable and all supplier and borrower funds in that market remain locked.

### Finding Description
`Controller::update_indexes` is permissionless and forwards the selected `HubAssetKey` to the pool for accrual. [1](#0-0) [2](#0-1) 

Each accrual step first converts stored scaled debt to its current RAY-denominated value through `scaled_to_original(borrowed, borrow_index)`. [3](#0-2) [4](#0-3) 

`scaled_to_original` delegates to `Ray::mul`, which computes `scaled * index / RAY` with a result that must fit in `i128` and panics with `MathOverflow` otherwise. [5](#0-4) [6](#0-5) [7](#0-6) 

The borrow-index cap does not prevent this because `MAX_BORROW_INDEX_RAY` is applied to the next index, while the vulnerable calculation multiplies the current debt shares by the current index before checking any market-value ceiling. [8](#0-7) [9](#0-8) 

### Impact Explanation
Once the accrued debt value no longer fits in `i128`, the transaction reverts before a new `last_timestamp` or clamped market state can be committed. [9](#0-8) [10](#0-9) 

Borrow, repay, and withdraw all enter `load_leg`, which calls `synced_market`, and `synced_market` always executes `interest::global_sync` before the operation-specific accounting. [11](#0-10) [12](#0-11) [13](#0-12) [14](#0-13) 

Consequently, suppliers cannot withdraw, borrowers cannot repay, and liquidators cannot settle affected debt through the affected market after the overflow point is reached. [15](#0-14) [16](#0-15) 

This is a permanent freezing of user funds in the affected market unless a contract upgrade or other out-of-band privileged recovery path is used.

### Likelihood Explanation
An unprivileged user can call `supply` with `account_id = 0`, a valid `spoke_id`, and a positive `(HubAssetKey, amount)` leg, then borrow against the resulting account through `borrow(caller, account_id, borrows, to)`. [17](#0-16) [18](#0-17) [19](#0-18) 

The condition is reachable on a listed market whose configured caps admit enough exposure: for example, an 18-decimal deposit of `1_000_000_000 * 10^18` base units produces approximately `10^36` scaled shares, so a `borrow_index` around `170x` makes `supplied * supply_index` exceed `i128::MAX`, and `borrowed * borrow_index` crosses the same boundary at roughly `174x` for 98% utilization. [20](#0-19) [21](#0-20) [8](#0-7) 

The attack therefore requires substantial assets or an already-large market, followed by sustained borrow utilization; it does not require privileged access, leaked keys, oracle manipulation, or malformed token behavior. [17](#0-16) [1](#0-0) 

### Recommendation
Bound the product of total scaled supply/debt shares and their indexes before it reaches the `i128` domain limit, and reject new supply or borrow entries that could leave insufficient accrual headroom. [22](#0-21) [23](#0-22) 

Alternatively, compute accrued market values in `I256`, clamp them to an explicit representable market-value ceiling, and persist a safe state instead of reverting inside `scaled_to_original`. [24](#0-23) [25](#0-24) 

Add an invariant that `borrowed * borrow_index / RAY` and `supplied * supply_index / RAY` always fit in `i128`, enforced before minting additional shares and during bad-debt or revenue-share changes.

### Proof of Concept
1. On a listed 18-decimal market whose caps admit the amount, call `Controller::supply(caller, 0, spoke_id, [(HubAssetKey { hub_id, asset }, 1_000_000_000 * 10^18)])`; the controller measures the pool receipt and submits a corresponding `PoolSupplyEntry`. [26](#0-25) [27](#0-26) 
2. From a sufficiently collateralized account, call `Controller::borrow(caller, account_id, [(key, 980_000_000 * 10^18)], None)`; the pool mints debt shares and leaves utilization near 98%. [28](#0-27) [12](#0-11) 
3. After the borrow index grows beyond approximately `174 * RAY`, call `Controller::update_indexes(caller, [key])`; `accrue_step` evaluates `borrowed.mul(env, borrow_index)`, producing a quotient above `i128::MAX` and reverting with `MathOverflow`. [1](#0-0) [9](#0-8) [29](#0-28) 
4. Subsequent `withdraw`, `repay`, or `liquidate` calls repeat the same accrual before their state changes, so they revert before any shares are burned or cash is moved. [30](#0-29) [13](#0-12) [14](#0-13)

```rust
/// Computes `x * y / d` rounded half up. Requires `x >= 0`, `y >= 0`, and `d > 0`; a
/// `debug_assert` checks this in debug builds. Panics with `GenericError::DivisionByZero` if
/// `d == 0`, and with `GenericError::MathOverflow` if any other precondition is violated or if
/// the result does not fit in `i128`.
pub fn mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> i128 {
    // The zero check runs first so debug and release builds agree on a zero
    // divisor: both surface `DivisionByZero` rather than tripping the assert.
    require_nonzero_divisor(env, d);
    debug_assert!(
        x >= 0 && y >= 0 && d > 0,
        "mul_div_half_up: non-negative x, y and positive d"
    );
    try_mul_div_half_up(env, x, y, d)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow))
}
```

```rust
/// Computes `x * y / d` rounded half up. Returns `None` if `x < 0`, `y < 0`, `d <= 0`, or the
/// result does not fit in `i128`.
pub fn try_mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> Option<i128> {
    if x < 0 || y < 0 || d <= 0 {
        return None;
    }
    let half = d / 2;

    // Fast path: the biased product fits `i128`, so the whole computation is
    // native. `x * y + half` is non-negative here, so `/` is the floor the
    // widened path would produce.
    if let Some(biased) = x
        .checked_mul(y)
        .and_then(|product| product.checked_add(half))
    {
        return Some(biased / d);
    }

    let (x256, y256, d256) = to_i256_operands(env, x, y, d);
    x256.mul(&y256)
        .add(&I256::from_i128(env, half))
        .div(&d256)
        .to_i128()
}
```
