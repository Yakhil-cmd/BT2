### Title
Webhook signature verification is bypassed for any GitHub organization configured without a `webhook_secret` - ([File: lib/shipit/github_app.rb])

### Summary
This engine's webhook trust model mirrors the priority-scaling report's core pattern: a value used to make a security decision (whether to trust an inbound payload) is derived inconsistently, so an unprivileged actor can make the "verification" step a no-op while the payload is still fully acted upon. Here, `Shipit::GithubApp#verify_webhook_signature` silently returns `true` (i.e. treats the request as verified) whenever the corresponding organization's `webhook_secret` is blank, and the organization used for that check is picked directly from unauthenticated payload fields.

### Finding Description
`WebhooksController#verify_signature` derives the GitHub organization to verify against straight from the untrusted JSON body, not from any authenticated context: [1](#0-0) [2](#0-1) 

It then calls `github_app.verify_webhook_signature`: [3](#0-2) 

Note line 77: `return true unless webhook_secret`. If the resolved organization's config has no `webhook_secret` set — a state explicitly presented as a supported configuration in the shipped sample config (`webhook_secret: # nil`) — the method reports the request as verified without checking anything at all. `head(422) unless verified` therefore never fires, and `create` proceeds to run every registered handler over the raw payload: [4](#0-3) [5](#0-4) 

This is the same class of trust-binding failure the report describes: the "verified" label is applied to a request whose actual acceptance criterion (a secret-derived HMAC) was never evaluated for that code path, exactly as the EVM priority factor was nominally "scaled" but effectively became `0` and thus ineffective for low-fee transactions. Here the effective outcome is `verified = true` for organizations without a webhook secret, i.e. authentication that computes to "always pass."

### Impact Explanation
Any organization onboarded without a `webhook_secret` accepts forged webhook deliveries from anyone on the internet with no credentials at all (no `ApiClient` token, no session, no GitHub secret). Handlers dispatched via `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` include, among others, the `push` handler that enqueues `GithubSyncJob` with an attacker-chosen `expected_head_sha`/repository state, and the `membership` handler that creates/removes `Team`/`Membership`/`User` records straight from the forged payload (as shown by the webhook controller tests exercising exactly this flow). An attacker can therefore drive stack synchronization, team/user membership changes, and any other registered webhook side effects for such an organization purely by guessing/knowing its login name in the JSON body — no bypass of any real secret is required because none is checked.

### Likelihood Explanation
Likelihood depends entirely on operational configuration: this is only exploitable for GitHub organizations whose `webhook_secret` is left unset. However, the engine's own reference configuration shows this as a normal, documented value (commented `# nil`), and nothing in the code path warns or refuses to mount a webhook endpoint for such an organization — the fallback behavior of "trust everything" is silent. Given that webhook secrets are easy to omit during setup/staging and the failure mode is fail-open rather than fail-closed, this is a realistic misconfiguration hazard baked into the trust code itself, not merely a documentation gap.

### Recommendation
Change `verify_webhook_signature` to fail closed: if `webhook_secret` is blank, treat the signature as unverifiable (`return false`) rather than automatically true, and require operators to explicitly opt into disabling verification (e.g. via a distinct, clearly-named flag) instead of it being an implicit consequence of an unset secret. Additionally, consider deriving `repository_owner`/organization selection from a value that is itself cryptographically bound (or cross-checked against a known/allow-listed stack's `Repository#owner`) rather than trusting `params.dig('repository','owner','login')` unconditionally before signature validation.

### Proof of Concept
1. Configure Shipit with an organization `someorg` whose secrets entry has `webhook_secret: nil` (as shown in `config/secrets.development.shopify.yml`).
2. As an unauthenticated attacker, POST to `/webhooks` with header `X-Github-Event: push` and a body such as:
```json
{
  "repository": { "owner": { "login": "someorg" }, "full_name": "someorg/some-repo" },
  "after": "<attacker-chosen sha>"
}
```
without any `X-Hub-Signature` header (or with a bogus value).
3. `verify_signature` resolves `repository_owner` = `"someorg"`, calls `Shipit.github(organization: "someorg").verify_webhook_signature(...)`, which returns `true` immediately because `webhook_secret` is blank.
4. `create` runs the `push` handler with the forged payload, enqueuing `GithubSyncJob` for the matching stack — despite the attacker never possessing any secret, token, or session.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
