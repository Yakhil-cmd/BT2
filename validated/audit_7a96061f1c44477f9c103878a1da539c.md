### Title
Cross-repository Status webhook allows unauthorized status injection and continuous-deployment trigger - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits purely `by sha`, with no check that the webhook's own `repository.full_name` matches the repository/stack that owns the matched commit. A GitHub `status` webhook that is validly signed for the attacker's own repository/organization can therefore write a `Status` (including `state: 'success'`) onto any commit row in the `commits` table whose `sha` happens to equal the value the attacker supplies, regardless of which stack that commit belongs to.

### Finding Description
The broken binding: `params.dig('repository','full_name')` (the repo the verified webhook signature is for) should equal `commit.stack.repository.full_name` (the repo whose commit gets mutated) — but nothing enforces this.

Code path:
- `Shipit::WebhooksController#verify_signature` only checks the signature against `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight from the payload's own `repository.owner.login`/`organization.login` [1](#0-0) [2](#0-1) . This proves authenticity of "a webhook for this org/repo," not that the org/repo is authorized to touch a specific target commit.
- `StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
with no filter on stack, repository, or `params['repository']` at all [3](#0-2) .
- `Commit#create_status_from_github!` writes the status using the *found commit's own* `stack_id`: `statuses.replicate_from_github!(stack_id, github_status)` [4](#0-3) .
- That status flips `Commit#success?`/`Commit#deployable?`, which is exactly what `Stack#next_commit_to_deploy` / `Stack#trigger_continuous_delivery` consult to select and ship the next commit.

Exploit flow: attacker owns Repo A (added to Shipit, so a real GitHub-signed `status` webhook can be produced for it, e.g. via GitHub's create-status API which accepts an arbitrary `sha` string). Attacker sets `sha` = Repo B's `next_commit_to_deploy` sha and `state: 'success'`. GitHub signs and delivers this webhook using Repo A/organization A's credentials. `verify_signature` passes because it only validates against organization A's secret, not against ownership of the target commit. `StatusHandler#process` finds Repo B's commit row purely by sha match and calls `create_status_from_github!`, writing a `success` Status with `stack_id` = Repo B's stack. This makes the commit `deployable?` and Repo B's stack ends up auto-deploying a commit that Repo B's real CI never approved.

None of the existing guards stop this: `verify_signature` authenticates the payload's claimed org/repo, not the target record; `drop_unhandled_event`/`ExplicitParameters` only validate shape (`sha`, `state`, etc.), not repository scoping; there is no `Repository` or `stack` comparison anywhere in `StatusHandler` or `Commit#create_status_from_github!`.

### Impact Explanation
An attacker who controls any Shipit-tracked repository (or can otherwise produce a validly-signed `status` webhook) can inject arbitrary CI statuses (including `success`) onto commits belonging to any other tenant's stack, as long as they can supply/predict the target sha. Combined with `ignore_ci?: false` continuous-deployment stacks, this results in an unauthorized deploy of code that was never validated by the victim repository's real CI — a "payload for one repository mutating another's stack/commit" and "unauthorized deploy," both explicitly listed as Critical impact categories. The blast radius spans every stack hosted by the same Shipit instance, not just repos within one organization.

### Likelihood Explanation
Preconditions: attacker needs a repository already onboarded to the same Shipit instance (any unprivileged GitHub user who can get Shipit to track a repo, e.g. by opening it as a Shipit stack, or by being an owner/collaborator on any repo already tracked), and needs to know/guess the victim commit's sha, which is readily discoverable from the target stack's public commit list or via git history. No Shipit secrets, sessions, or API tokens are required — only the ability to make GitHub deliver a `status` event for a repo the attacker controls, with a `sha` value of their choosing. This is a normal, repeatable, low-cost webhook write against any target stack whose next-deploy commit is currently CI-unverified.

### Recommendation
In `StatusHandler#process`, restrict the commit lookup to commits whose stack's repository matches the webhook's own `params['repository']['full_name']` (and ideally its `id`), e.g. resolve `stack = Stack.for_repository(params.repository.full_name)` (or similar) and scope `stack.commits.where(sha: params.sha)` instead of a global `Commit.where(sha:)`. Apply the same repository-binding check to any other handler that looks up records purely by sha/branch without checking the payload's repository field.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` style):
```ruby
test "cross-repo status webhook must not deploy an unrelated stack" do
  stack = shipit_stacks(:shipit)
  stack.update!(ignore_ci: false, continuous_deployment: true)
  target_commit = stack.commits.create!(sha: "d" * 40, author: shipit_users(:walrus),
                                         committer: shipit_users(:walrus), message: "victim")
  # sanity: not deployable before the attack
  refute target_commit.reload.deployable?

  request.headers['X-Github-Event'] = 'status'
  attacker_payload = {
    'sha' => target_commit.sha,
    'state' => 'success',
    'branches' => [{ 'name' => stack.branch }],
    'repository' => { 'full_name' => 'attacker/repo-a', 'owner' => { 'login' => 'attacker' } }
  }.to_json
  GithubHook.any_instance.stubs(:verify_signature).returns(true) # simulate a validly-signed webhook for attacker/repo-a

  assert_difference -> { Deploy.where(stack:).count }, 1 do
    post :create, body: attacker_payload, as: :json
  end

  assert target_commit.reload.deployable?
  assert_not_equal 'attacker/repo-a', stack.repo_full_name # confirms the acting webhook's repo differs from the deployed stack's repo
end
```
This asserts both sides of the binding — the webhook's `repository.full_name` ("attacker/repo-a") is unequal to the mutated stack's `repo_full_name` — and shows `Deploy.count` for `stack` increments purely from the cross-repo payload.
