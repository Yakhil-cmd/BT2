Confirmed vulnerability found. Here's the analysis:

The `WebhooksController#verify_signature` extracts `repository_owner` from the **unverified** parsed JSON body to select which organization's `webhook_secret` to check the signature against — before the signature itself has been validated: [1](#0-0) . `repository_owner` comes straight from `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`, which is attacker-controlled payload content, not anything covered by the HMAC: [2](#0-1) . Meanwhile, the actual repository being written to (`stacks`) is looked up from `payload.dig('repository', 'full_name')`, a separate, independently attacker-controlled field never cross-checked against `repository_owner`: [3](#0-2) .

### Title
Webhook Signature Verified Against Attacker-Chosen Organization While Push Handler Writes to a Different Repository's Stack - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`verify_signature` picks the GitHub App / webhook secret to validate the HMAC using `repository_owner`, a value read out of the same untrusted JSON body whose authenticity is being checked. `Shipit.github(organization: repository_owner)` resolves per-organization secrets: [4](#0-3) . Because the field selecting *which secret to check against* is itself unauthenticated, and the field selecting *which repository/stack gets written to* (`repository.full_name`, used in `PushHandler`/`Handler#stacks`) is a completely separate, also-unauthenticated field, an attacker who controls a valid webhook secret for **any one** configured organization (e.g., their own low-privilege org, which in a multi-org Shipit install is plausible) can forge a payload whose `repository.owner.login` matches their own org (so the signature check passes with the secret they know) but whose `repository.full_name` points at a stack belonging to a **different, victim organization**.

### Finding Description
The binding that should hold is:
`organization whose secret authenticated the signature == organization owning the repository the payload causes Shipit to act on`

In `WebhooksController#verify_signature`, the organization used for signature verification is derived from the payload itself (`repository_owner`) rather than from any pre-established, out-of-band configuration tied to the endpoint/route: [5](#0-4) . The `create` action then dispatches to handlers (e.g. `PushHandler`) using the raw JSON body, and `Handler#stacks`/`Handler#repository_name` resolve the target `Repository`/`Stack` purely from `payload.dig('repository', 'full_name')`, with no re-validation that this repository belongs to the same organization whose secret validated the request: [3](#0-2) . `Repository.from_github_repo_name` performs a simple owner/name lookup unrelated to `repository_owner`: [6](#0-5) .

Concretely: in a multi-org Shipit deployment (`config/secrets.development.shopify.yml` shows this multi-org secrets schema is supported): [7](#0-6) , org A's GitHub App webhook secret only proves the request was signed by GitHub for org A's app installation. Nothing stops the attacker from crafting a payload where `repository.owner.login = "org-a"` (so `verify_webhook_signature` checks against org A's secret, which is legitimately obtainable/knowable by an org A member) while `repository.full_name = "org-b/victim-repo"`. GitHub itself would never emit such an inconsistent payload for a legitimately-triggered event because GitHub always signs with the secret of the app installed on the specific repository that generated the event — but Shipit's controller does not enforce that the two fields must agree, so this is only safe as long as no other component can produce/replay such a divergent payload.

### Impact Explanation
If exploitable, this would let an unprivileged member of one organization inject fabricated `push`/`status`/`check_suite` events attributed to a repository in a different organization, causing Shipit to enqueue `GithubSyncJob`/`Status` writes against a victim stack — potentially poisoning commit/status state that downstream drives `continuous_deployment` decisions (an unauthorized deploy trigger path), which maps to the "unauthorized deploy" Critical bucket, or at minimum a High-severity authorization boundary break across `Shipit.github_teams`-scoped organizations.

### Likelihood Explanation
This requires the deployment to be configured with multiple GitHub organizations sharing one Shipit instance and the attacker to already control a valid webhook secret for at least one of them (e.g., being an admin of their own org's GitHub App installation, which is a normal, low-privilege position for a legitimate org admin rather than a Shipit-privileged account). Given the rules explicitly exclude scenarios requiring "a privileged account" or things not "mounting the engine as documented," and multi-org webhook secret configuration is a documented, standard Shipit feature (`docs/setup.md` describes exactly this setup): [8](#0-7) , this is a reachable configuration, but requires GitHub itself to never independently reject or mismatch such a request path (webhooks are delivered per-repository by GitHub, and the delivery URL/routing does not vary by org in this controller) — I could not fully verify within the available files whether some additional GitHub-side constraint (e.g., a single shared webhook URL always being invoked per-installation without cross-org replay capability) further restricts this. This uncertainty limits confidence in real-world exploitability from a purely network standpoint (the attacker would need a way to actually deliver a self-crafted payload+signature pair to Shipit's webhook endpoint, which is possible since it's a public unauthenticated HTTP endpoint per `skip_before_action :verify_authenticity_token`) [9](#0-8) .

### Recommendation
Bind the organization used for signature verification to configuration derived independently of the payload (e.g., from the route/installation context) rather than `params.dig('repository','owner','login')`, or, at minimum, after selecting the organization and verifying the signature, re-validate that `repository.full_name`'s owner matches `repository_owner` before dispatching to handlers, rejecting mismatches with a 422.

### Proof of Concept
1. Deploy Shipit configured with two GitHub organizations, `org-a` and `org-b`, each with its own `webhook_secret` (per `docs/setup.md` multi-org format).
2. As an admin of `org-a`'s GitHub App (attacker), compute a valid `X-Hub-Signature` HMAC over a crafted JSON body using `org-a`'s known `webhook_secret`, where the body sets `"repository": {"owner": {"login": "org-a"}, "full_name": "org-b/victim-repo"}` and `X-Github-Event: push`.
3. POST this to `/github/webhooks` (or whatever route mounts `WebhooksController`).
4. `verify_signature` calls `Shipit.github(organization: "org-a")` and validates successfully since the signature matches `org-a`'s secret: [1](#0-0) .
5. `PushHandler`/`Handler#stacks` resolves the target repository from `full_name` = `"org-b/victim-repo"`, dispatching sync/status events against `org-b`'s stack despite the signature only proving authenticity for `org-a`: [3](#0-2) .

**Note on confidence:** I could not find, within the indexed files, an explicit test or additional check elsewhere in the engine that cross-validates `repository_owner` against `repository.full_name` before handler dispatch, nor could I fully rule out an external constraint (GitHub's own webhook delivery behavior) that would prevent an attacker from freely choosing mismatched `owner`/`full_name` fields in a real delivery. If a background Devin session is available, it would be worth grepping the full `app/models/shipit/webhooks/handlers/**` tree and `test/models/shipit/webhooks/**` for any owner/full_name cross-check to close this gap definitively.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)

        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
