Based on my investigation, I found a concrete analog in ocore's `spender_attested` asset mechanism.

### Title
Asset definer can permanently freeze payouts to a user by removing an attestor after the fact, causing spender-attested payments (including AA payouts) to always fail validation - (File: validation.js)

### Summary
For assets defined with `spender_attested: true`, every payment output address must currently be attested by one of the asset's *current* trusted attestors, checked at validation time via `storage.filterAttestedAddresses`/`loadAssetWithListOfAttestedAuthors`. Because the attestor list is dynamic (the definer can update it any time via an `asset_attestors` message) and is always read as of the *current* last-ball MCI rather than the state at the time attestation/coin issuance occurred, a definer (or drift in attestor policy) can make a previously-valid recipient address permanently fail the "is attested" check for any future transfer of that asset — an on-chain analog of a blacklist. This mirrors the reported `exercise()` bug: a push-style payment (whether a normal transfer or, more importantly, a payment emitted from within an AA's response) reverts entirely whenever the destination fails the recipient-side permission check, and there is no pull-based fallback.

### Finding Description
`validatePaymentInputsAndOutputs` enforces, for `spender_attested` assets, that **all** output addresses are attested before the payment is allowed: [1](#0-0) 

The attestor list used for this check is not fixed at asset-definition time — it is the *latest* stable list as of `last_ball_mci`, fetched fresh on every validation: [2](#0-1) 

The definer can update this list at will via an `asset_attestors` message, and only the definer is authorized to do so: [3](#0-2) 

`filterAttestedAddresses` only counts an address as attested if an attestation from a *currently listed* attestor exists and postdates the address's last definition change: [4](#0-3) 

This same check is used by the AA engine when an AA composes an outgoing payment in a custom asset: `sendUnit` calls `storage.loadAssetWithListOfAttestedAuthors` while building payment payloads, and any resulting validation failure is fed into `bounce()`, which discards **all** state changes for that trigger and refunds only the bounce fee: [5](#0-4) [6](#0-5) 

So, exactly like the reported `FixedStrikeOptionTeller.exercise()` case where a push transfer to a blacklisted receiver reverts the whole exercise flow, in ocore: if an AA (e.g., a vault/vesting/option-like AA) tracks a user's entitlement to a `spender_attested` asset and later tries to pay it out, and the definer of that asset has since removed the attestor that vouched for the recipient's address (or the recipient's address definition changed after attestation, per the `main_chain_index>` condition in `filterAttestedAddresses`), the payment message fails asset validation. Because there is no pull-based settlement path in the AA logic (the AA only knows how to push to `trigger.address`), the whole trigger bounces, state changes are rolled back via `ROLLBACK TO SAVEPOINT`, and the user's recorded entitlement can never be redeemed — it's stuck forever, and every subsequent redemption attempt bounces again, burning bounce fees.

### Impact Explanation
This causes AA fund freezing: any accounting AA that unconditionally pushes a `spender_attested` asset to `trigger.address` on a claim/exercise/withdraw path becomes permanently unable to deliver funds to a user whose attestation coverage lapses, while the AA's internal state still records the obligation as unfulfilled (since bounce reverts state changes). Funds effectively become locked in the AA balance with no code path to release them to the intended party, satisfying the "AA fund loss or freezing" impact bar.

### Likelihood Explanation
Reachable by a single asset issuer (who defines a `spender_attested` asset and later posts an `asset_attestors` update removing an attestor) combined with any AA author who writes a payout AA that doesn't validate attestation status before promising/pushing the asset. Both actions — defining/updating assets and triggering AAs — are permissionless single-unit operations, so this is trivially reachable without any privileged or off-chain assumption, and is the direct on-chain counterpart of a blacklist-capable ERC20.

### Recommendation
- AA design guidance / SDK helper: before pushing a `spender_attested` (or `transfer_condition`-gated) asset to a recipient, an AA should check the recipient's current attestation/condition status (e.g., via a data feed or `is_valid_signature`-style check exposed to oscript) and, if unsatisfied, keep the entitlement in a claimable/pull state (e.g., a per-address balance in state vars) rather than unconditionally pushing, so the user can attempt withdrawal again later or to an alternate attested address.
- Consider exposing an oscript primitive to query whether a specific address is currently attested for a given asset (already computable from `storage.filterAttestedAddresses`), so AA authors can branch instead of relying on validation-time failure.
- Document prominently in AA-authoring guidance that `spender_attested`/`transfer_condition` assets can cause `payment` messages to unconditionally fail based on the *current* attestor list, and that payout logic must implement pull-over-push accounting for such assets.

### Proof of Concept
1. Asset issuer (Bob) defines an asset `A` with `spender_attested: true` and an initial attestor `X` [7](#0-6) .
2. `X` attests user `U`'s address; `U` deposits into an AA `V` that credits `U`'s balance in a state var and promises to later send asset `A` to `U` on a `withdraw` trigger.
3. Bob (definer) posts an `asset_attestors` message removing `X` from the attestor list (allowed because he's the definer) [8](#0-7) .
4. `U` sends a `withdraw` trigger to `V`. `V`'s response messages include a payment of asset `A` to `U`. During `sendUnit`, `loadAssetWithListOfAttestedAuthors` recomputes the attestor list (now without `X`), so `U` is no longer attested [9](#0-8) .
5. `validatePaymentInputsAndOutputs` rejects the unit with `"some output addresses are not attested"` [10](#0-9) , `sendUnit`'s `validateAndSaveUnit` callback returns an error, and `bounce(err)` fires, rolling back all of `V`'s state changes for this trigger [6](#0-5) .
6. `U`'s credited balance remains in state (unconsumed, since the state update was rolled back) but every future withdrawal attempt repeats steps 4–5 indefinitely — `U`'s funds inside `V` are permanently frozen.
