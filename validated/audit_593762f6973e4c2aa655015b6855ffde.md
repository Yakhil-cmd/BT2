### Title
Cross-organization webhook forgery allows unauthorized team membership removal - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`MembershipHandler#process` resolves the `Team` solely by the numeric `params.team.id` (github_id), while the webhook's signature is verified against the organization derived from `params.organization.login` (or `params.repository.owner.login`), a value pulled directly from the attacker-controlled payload body. Because these two lookups are never cross-checked, an operator of any organization configured in Shipit (i.e., any org with its own `webhook_secret`) can forge a `membership` event that removes a privileged user from a *different* organization's team.

### Finding Description
The binding that should hold is: `organization_that_authenticated_signature == organization_that_owns(team.github_id)`. Tracing the code shows this is never enforced.

In `Shipit::WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`), the org used to select the HMAC secret is computed from the payload itself:
```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
For a `membership` event there is no `repository` key in the payload (membership events are org-scoped, not repo-scoped), so `repository_owner` falls back to `params['organization']['login']` — a field fully controlled by whoever is sending the webhook. `Shipit.github(organization: repository_owner)` then picks that organization's configured `webhook_secret` to verify `X-Hub-Signature` [1](#0-0) , [2](#0-1) .

Once signature verification passes (against the attacker's *own* org secret, since they set `organization.login` to their own org), `MembershipHandler#process` resolves the team purely from `params.team.id`:
```
def find_or_create_team!
  Team.find_or_create_by!(github_id: params.team.id) do |team|
    team.github_team = params.team
    team.organization = params.organization.login
  end
end
``` [3](#0-2) 

If a `Team` with that `github_id` already exists (the victim's real team), `find_or_create_by!` returns the *existing* record — the `organization` field inside the block is only used on creation and is never re-validated against the found record. The handler then executes:
```
when 'removed'
  team.members.delete(member)
``` [4](#0-3) 

Attack: attacker controls (as an admin/webhook-configuring member) some organization `attacker-org` that Shipit has been configured to trust (has its own `webhook_secret` entry). They POST to `/webhooks` with header `X-Github-Event: membership`, a valid `X-Hub-Signature` computed with `attacker-org`'s secret, and a JSON body:
```
{
  "action": "removed",
  "team": { "id": <victim_team_github_id>, "name": "...", "slug": "...", "url": "..." },
  "organization": { "login": "attacker-org" },
  "member": { "login": "victim-privileged-user" }
}
```
`verify_signature` succeeds because it only checks the signature against `attacker-org`'s secret, matching the `organization.login` claimed in the payload — it never checks that `team.id` actually belongs to `attacker-org`. `find_or_create_team!` finds the pre-existing victim `Team` by `github_id`, and `team.members.delete(member)` deletes the victim's membership.

None of the existing guards catch this: `verify_signature` only authenticates *an* organization, not that the org owns the referenced team; `drop_unhandled_event` and the `ExplicitParameters` schema only validate presence/type of fields, not cross-tenant ownership; there is no `require_permission!`/session check on webhook endpoints by design (webhooks are meant to be server-to-server); and `Team#members.delete` performs no organization-scoped authorization check.

### Impact Explanation
A successful request destroys a `Membership` record binding a privileged user to `Shipit.github_teams`, on behalf of a victim organization that never authenticated the request. This is a cross-tenant authorization bypass: an attacker who administers one configured Shipit organization can strip authorization from a user in a completely different organization's team, without ever having a Shipit session, API token, or the victim org's webhook secret. It is repeatable against any known/guessable `team.github_id` and any known GitHub login of a privileged user (both are effectively public/discoverable), matching the "escalation into/out of `Shipit.github_teams` authorization" High-severity category (removal is a precursor enabling later re-addition/takeover of the authorization slot once the legitimate member is gone).

### Likelihood Explanation
The attacker must be able to get a signed webhook accepted for *some* organization configured in Shipit — i.e., they must control (or be a member/admin capable of firing GitHub org events for) at least one organization that Shipit trusts with its own `webhook_secret`. This is a realistic scenario in any multi-tenant Shipit deployment serving multiple GitHub orgs, since each org's admins configure and can trigger their own org's webhooks legitimately, yet the code lets that trusted channel be repurposed to mutate objects belonging to unrelated orgs. The victim team's numeric `github_id` and a privileged user's login are both low-cost to obtain (GitHub team IDs are exposed via the GitHub API/UI to team viewers, and usernames are public). No GitHub App private key, `secret_key_base`, or victim's `webhook_secret` is required.

### Recommendation
In `MembershipHandler#find_or_create_team!` (and the `added` branch), verify that the resolved `Team#organization` matches `params.organization.login` (the same organization whose secret authenticated the request) before performing any mutation; reject/raise if they differ instead of silently reusing the pre-existing team record for an unrelated organization.

### Proof of Concept
Minitest under `test/models/shipit/webhooks/handlers/membership_handler_test.rb` (conceptual, no live GitHub required):
1. Arrange: create `victim_team = Team.create!(github_id: 42, organization: 'victim-org')`, and `privileged_user = User.create!(login: 'victim-privileged-user')`; add `victim_team.add_member(privileged_user)`.
2. Assert precondition: `Membership.exists?(team: victim_team, user: privileged_user)` is `true`.
3. Act: invoke `MembershipHandler.call('action' => 'removed', 'team' => { 'id' => 42, 'name' => 'n', 'slug' => 's', 'url' => 'u' }, 'organization' => { 'login' => 'attacker-org' }, 'member' => { 'login' => 'victim-privileged-user' })` — simulating that `verify_signature` already succeeded using `attacker-org`'s secret (bypassing the controller layer as handler tests do).
4. Assert: `Membership.exists?(team: victim_team, user: privileged_user)` is now `false`, and `Team.find(victim_team.id).organization` is still `'victim-org'` — proving the mutation was applied to the victim's team despite authentication being scoped to `attacker-org`.
5. This demonstrates the binding `authenticated_org == team.organization` is violated: both sides are recorded (`'attacker-org'` vs `'victim-org'`) and shown unequal at the time of mutation.
