### Title
Missing `return` after caught exception causes double-processing / re-entrant callback in private-payment handling - ([File: network.js])

### Summary
In `handleSavedPrivatePayments()` in `network.js`, the inner `validateAndSave` function catches an exception from `objectHash.getBase64Hash()` but fails to `return` from the catch block, so execution falls through to code that assumes the hash computation succeeded and to a second, redundant invocation of the validation/completion logic — mirroring the CVE-2024-8006 root cause (an error/failure branch not properly halting execution, allowing subsequent code to operate on unset/invalid state).

### Finding Description
`handleSavedPrivatePayments()` processes rows from `unhandled_private_payments`, which are populated whenever any peer (or the hub, or self) sends a `private_payment` message via `handleOnlinePrivatePayment()` [1](#0-0) . The attacker-controlled content is `arrPrivateElements`, deserialized straight from stored JSON.

Inside `validateAndSave`:
```
try {
    var json_payload_hash = objectHash.getBase64Hash(objHeadPrivateElement.payload, true);
}
catch (e) {
    console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
    if (ws)
        sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
    deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
}
var key = 'private_payment_validated-'+objHeadPrivateElement.unit+'-'+json_payload_hash+'-'+row.output_index;
privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, { ... });
``` [2](#0-1) 

`objectHash.getBase64Hash()` can throw for a payload that is not JSON-hashable (e.g., contains values `getSourceString`/`getJsonSourceString` rejects, such as objects with disallowed types, `NaN`, or excessively deep/invalid structures) — a condition fully controllable by whoever crafts `arrPrivateElements[0].payload`, since it is attacker-supplied JSON.

When the exception fires, the `catch` block already calls `deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb)`, which deletes the DB row and invokes `cb` (the `async.each` iteratee callback) to complete processing of that item. However, since there is no `return` statement after this call, execution continues to the next line, which builds `key` using the now-`undefined` `json_payload_hash`, and then unconditionally calls `privatePayment.validateAndSavePrivatePaymentChain(...)` a second time on the same `arrPrivateElements`. That second call's callbacks (`ifOk`/`ifError`/`ifWaitingForChain`) each also call `deleteHandledPrivateChain(...)` (and thus `cb`) again [3](#0-2) , and also independently drive `eventBus.emit('new_direct_private_chains', ...)`, `eventBus.emit(key, ...)`, and (on success) mark the unit for `"new_my_transactions"` emission.

The `async.each` iteratee (`cb`) being invoked twice for the same item is analogous in kind to the CVE-2024-8006 pattern: a failure path is taken but the code does not stop, so a following operation is performed on state that was never validated/prepared for that continuation. Depending on the `async` library version used, calling the per-item callback more than once can throw an internal error ("Callback was already called") which is unhandled and can crash the node process (an unhandled exception in Node.js terminates the process), or otherwise leave `assocUnitsInWork`/mutex bookkeeping and duplicate-chain processing (double insert attempt, double `saveJoint`-style state changes for the private chain) in an inconsistent state.

### Impact Explanation
This is reachable by any peer that can deliver a `private_payment`/`hub/message` payload (or a private-payment counterparty), i.e., an unprivileged network participant, matching the "private-payment counterparty" reachable-surface category. If the double-invocation triggers an unhandled exception inside `async.each`'s callback machinery, it can crash the full node process — a network-visible denial of service affecting confirmation of new units for that node, similar in severity class to the NULL-pointer crash in the CVE. Even absent a hard crash, duplicate processing of the same private chain (double emission of `new_direct_private_chains`/`new_my_transactions` and duplicate calls into `validateAndSavePrivatePaymentChain`) risks inconsistent local wallet/AA bookkeeping.

### Likelihood Explanation
Triggering `objectHash.getBase64Hash()` to throw requires crafting a `payload` object that `getSourceString`/hashing utilities reject (e.g., invalid value types, `NaN`, or structures with cyclic/foreign fields). Since `arrPrivateElements` originates from untrusted JSON sent over the wire and is only lightly validated before reaching this code path, an attacker has a direct, low-effort trigger: send a `private_payment` (or `hub/message` wrapping one) whose head element's `payload` cannot be hashed.

### Recommendation
Add a `return;` immediately after `deleteHandledPrivateChain(...)` inside the `catch` block in `validateAndSave` in `network.js`, so that once the hash computation fails and the item is deleted/`cb`'d, no further code (including the second `privatePayment.validateAndSavePrivatePaymentChain` call) executes for that row. Additionally, audit other similar `try { ... } catch (e) { ...; someAsyncCompletion(cb); }` blocks in this file (and `handleSavedPrivatePayments`'s sibling functions) for the same missing-`return` pattern to prevent callback re-entrancy.

### Proof of Concept
1. As a peer (or paired private-payment counterparty), send a `private_payment` message (or a `hub/message` justsaying containing one) with `arrPrivateElements[0].payload` set to a value that `objectHash.getBase64Hash` cannot process, e.g. include a field whose value is `NaN`, `Infinity`, or another type rejected by `string_utils.getJsonSourceString`.
2. The node calls `handleOnlinePrivatePayment` → stores the row in `unhandled_private_payments` → later `handleSavedPrivatePayments()` processes it.
3. `objectHash.getBase64Hash(objHeadPrivateElement.payload, true)` throws; the `catch` block runs `deleteHandledPrivateChain(...)`, invoking `cb()` once.
4. Execution falls through (no `return`) to `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})`, which — regardless of outcome — invokes one of its callbacks, each of which calls `deleteHandledPrivateChain(...)` again, invoking `cb()` a second time for the same `async.each` item.
5. Observe either an unhandled "callback already called" exception (crashing the process) in the `async` library, or duplicate `new_direct_private_chains`/`new_my_transactions` events and duplicate private-chain save attempts.

Note: I was not able to execute this against a live node to directly observe the crash vs. duplicate-processing outcome, since that depends on the exact `async` library version's behavior on double-invoked callbacks and on the current mutex/`assocUnitsInWork` state; a Devin session with the full repository and test harness (e.g. `test/` in this repo) would be needed to confirm empirically whether this manifests as a process crash or only as duplicate-processing side effects.

// handles one private payload and its chain
function handleOnlinePrivatePayment(ws, arrPrivateElements, bViaHub, callbacks){
	if (!ValidationUtils.isNonemptyArray(arrPrivateElements))
		return callbacks.ifError("private_payment content must be non-empty array");
	
	var unit = arrPrivateElements[0].unit;
	var message_index = arrPrivateElements[0].message_index;
	var output_index = arrPrivateElements[0].payload.denomination ? arrPrivateElements[0].output_index : -1;
	if (!ValidationUtils.isValidBase64(unit, constants.HASH_LENGTH))
		return callbacks.ifError("invalid unit");
	if (!ValidationUtils.isNonnegativeInteger(message_index))
		return callbacks.ifError("invalid message_index");
	if (!(ValidationUtils.isNonnegativeInteger(output_index) || output_index === -1))
		return callbacks.ifError("invalid output_index");

	var savePrivatePayment = function(cb){
		// we may receive the same unit and message index but different output indexes if recipient and cosigner are on the same device.
		// in this case, we also receive the same (unit, message_index, output_index) twice - as cosigner and as recipient.  That's why IGNORE.
		db.query(
			"INSERT "+db.getIgnore()+" INTO unhandled_private_payments (unit, message_index, output_index, json, peer) VALUES (?,?,?,?,?)", 
			[unit, message_index, output_index, JSON.stringify(arrPrivateElements), bViaHub ? '' : ws.peer], // forget peer if received via hub
			function(){
				callbacks.ifQueued();
				if (cb)
					cb();
			}
		);
	};
	
	if (conf.bLight && arrPrivateElements.length > 1){
		savePrivatePayment(function(){
			updateLinkProofsOfPrivateChain(arrPrivateElements, unit, message_index, output_index);
			rerequestLostJointsOfPrivatePayments(); // will request the head element
		});
		return;
	}
