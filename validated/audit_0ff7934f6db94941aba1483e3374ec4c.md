### Title
Bad-debt write-down clamps the supply index at `SUPPLY_INDEX_FLOOR_RAW`, leaving wiped suppliers phantom claims that drain subsequently deposited cash - (File: contracts/pool/src/interest.rs)

### Summary
`apply_bad_debt_to_supply_index` socializes unpaid debt by scaling the supply index toward zero, but clamps the result to `SUPPLY_INDEX_FLOOR_RAW` (`RAY/1000`) instead of zeroing supply shares. When bad debt equals or exceeds total supplied value (a full wipeout), every pre-existing supplier keeps a positive residual claim of `scaled * 0.001 RAY` that has no backing cash. The first later deposit or stray token transfer to the pool funds that phantom claim, so an unprivileged attacker who manufactures the wipeout and also holds wiped supply can withdraw real tokens they have no right to — an integer-domain analog of the CVE's underflow/under-read: a magnitude that should reach zero is clamped to a positive floor, and the ledger is then "under-read" below its true backing.

### Finding Description
In `contracts/pool/src/interest.rs`, `apply_bad_debt_to_supply_index` computes `remaining = total_supplied_value - min(bad_debt, total_supplied_value)`, multiplies the supply index by `remaining / total_supplied_value`, then applies `.max(Ray::from(SUPPLY_INDEX_FLOOR_RAW))` (lines 73–89). On a full wipeout `remaining` is 0, so the index should be 0; the clamp raises it to `0.001 RAY`, resurrecting `scaled_amount × 10^-3` of claim per supplier while `cash` is untouched (typically ~0, since the debt was never repaid).

The write-down is reached from two unprivileged paths:
- `liquidate` → `check_bad_debt_after_liquidation` → `execute_bad_debt_cleanup` (`contracts/controller/src/positions/liquidation/bad_debt.rs`) → `pool_seize_positions_call` → `seize::apply` Borrow branch → `apply_bad_debt_to_supply_index` (`contracts/pool/src/ops/seize.rs`).
- `clean_bad_debt` directly on an account already below the dust threshold.

No reciprocal mechanism zeroes `supplied` shares or blocks later withdrawals of the residual claim. `Cache::resolve_withdrawal`/`unscale_supply_floor` (`contracts/pool/src/cache/scale.rs`) happily unscale the wiped shares at the floored index, and `require_reserves` only gates on available cash — so the phantom pays out whenever cash exists. The codebase's own test `test_raw_cache_floor_clamp_strands_claim_without_supply_guard` (`contracts/pool/tests/interest.rs:372-427`) demonstrates exactly this: after the clamp, a stranded wiped position withdraws `gross == fresh_cash`, leaving `cache.cash() < fresh_claim` — i.e., a fresh supplier's deposit is drained.

### Impact Explanation
Theft of user funds / protocol insolvency. An attacker holds a large supply position plus a manufactured fully-bad debt position (e.g., borrow against an asset, then crash the collateral price via their own trades on Aquarius/Soroswap within oracle bands, or simply let an already-insolvent account reach the socializable-dust threshold and call `clean_bad_debt`). The wipeout sets the index to the floor; the attacker's wiped shares still claim `scaled * floor` tokens. Any subsequent deposit — including the attacker's own `supply` to seed cash, followed by `withdraw` of the phantom claim — converts worthless shares into real tokens at other suppliers' expense, since the redeemed cash comes from the shared physical balance while later claims remain unbacked.

### Likelihood Explanation
Requires a catastrophic (≈100% of supply value) bad-debt event on one (hub, token) market, which is an extreme but reachable state: undercollateralization from a sharp price move plus a liquidator choosing `clean_bad_debt`, or dust-threshold socialization on a thin market. Once hit, exploitation is deterministic — the phantom claim is arithmetic, not racy. Because the clamp deliberately preserves share liveness, every wiped supplier is a passive beneficiary, but the attacker can control the largest share of wiped supply. Note: whether `SUPPLY_INDEX_FLOOR_RAW`'s stranding is an accepted documented trade-off is not fully clear from the code read; the in-repo test frames it as masking an invariant violation, which supports treating it as a defect rather than intended.

### Recommendation
When `remaining == 0` (or `remaining` below a dust threshold), do not resurrect the index: either burn/zero all `supplied` shares so no claim survives, or carry the index to the floor *and* proportionally rescale stored `supplied`/`revenue` scaled amounts so `scaled * floor_index` equals the true residual value. At minimum, gate withdrawals on the wiped position by zeroing position scaled amounts during cleanup, and add a regression test asserting `unscale_supply_floor(supplied) <= cash + debt_value` after `apply_bad_debt_to_supply_index`.

### Proof of Concept
Mirroring `contracts/pool/tests/interest.rs:372-427`:

1. Market M: attacker supplies `S` tokens (scaled `p0`), and a separate attacker account borrows against collateral that becomes worthless, accruing debt `D ≥ supplied_value`.
2. Anyone calls `clean_bad_debt` → Borrow seize → `apply_bad_debt_to_supply_index`: `remaining = 0`, index clamps to `RAY/1000`. `cash == 0`, but attacker's claim is `unscale_supply_floor(p0) > 0`.
3. Attacker supplies `F = unscale_supply_floor(p0)` fresh tokens (new shares `p1`), then `withdraw(i128::MAX)` on the old position: `require_reserves` passes against `F`, paying out `gross == F`.
4. Pool cash < `unscale_supply_floor(p1)` — the fresh deposit is gone; the attacker extracted it via a claim that should have been zero.
