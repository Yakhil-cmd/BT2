### Title
Uncaught exception via live-array aliasing in `foreach`/`map`/`filter`/`reduce` iteration - (File: formula/evaluation.js)

### Summary
`foreach`/`map`/`filter`/`reduce` (`formula/evaluation.js:2345-2469`) evaluate their container expression `arr[1]` and, for arrays, iterate directly over the live reference `res.obj` (`var arrElements = bArray ? res.obj : ...`, line 2371) rather than a defensive copy. Because oscript passes wrapped objects by reference into function scopes (confirmed by the existing `object mutated by function` test in `test/formula.test.js:4581-4598`, and by `callFunction` at `formula/evaluation.js:3050-3097` which assigns scope vars/args without cloning), the callback invoked per-element can mutate the very array being iterated (e.g. via `delete($o, ...)` at `formula/evaluation.js:2301-2343`, which does `res.obj.splice(key,1)`) through a closure over the same local variable.

### Finding Description
When `bArray` is true, `arrElements` is not cloned — it is the same JS array object referenced by the oscript local variable being iterated (`formula/evaluation.js:2371`). The anonymous/named function argument (`func_expr`) captures the enclosing scope (`scopeVarNames`, `formula/evaluation.js:3067-3069`,`3103-3106`), so it can reference and mutate the same local variable inside the loop body, e.g. call `delete($o, [idx])` which performs `res.obj.splice(key, 1)` (`formula/evaluation.js:2324-2335`). Node's `async.eachOfSeries` captures the array's `.length` once at iteration start but reads `array[key]` lazily on each iteration; shrinking the array mid-iteration via `splice` causes later accesses to read past the (shifted/now shorter) live array, yielding `element === undefined` at `formula/evaluation.js:2390` (`toOscriptType(element)`). `toOscriptType` (`formula/evaluation.js:3235-3245`) has no branch for `undefined` and executes `throw Error("unknown type in toOscriptType:" + x)` — this throw is not wrapped in a try/catch and is not routed through `setFatalError`, unlike virtually every other error path in this evaluator.

This is the direct oscript analog of the CVE's bug class: the interpreter holds a live alias into a mutable structure while iterating it, and a user-controlled mutation mid-iteration (illegal/unsynchronized access analogous to njs's use-after-free during `njs_json_parse_iterator_call`) produces an unhandled fault instead of a graceful evaluation error.

### Impact Explanation
An uncaught `throw` inside the deeply nested async callback chain used by AA trigger evaluation (`aa_composer.js`) is not caught by the evaluator's own error-handling wrappers (`setFatalError`), so it propagates as an unhandled exception during AA trigger processing — which every full node performs identically while validating/executing units that trigger the AA. If this crashes the Node.js process (or leaves node state in a validation-partial condition) on every node that processes the triggering unit, it can halt AA execution/validation network-wide for that unit, i.e., "a network unable to confirm new units" that reference/trigger the affected AA. Because it is fully deterministic, all validating nodes hit the same path in the same way — so instead of divergent output, the more severe outcome is a synchronized process crash/hang across the network when the AA is triggered.

### Likelihood Explanation
Reachable by any account (unpriviledged unit poster) sending a trigger to an attacker-authored AA that defines an oscript formula using `foreach`/`map`/`filter`/`reduce` over a local array variable, with the callback function calling `delete($that_same_var, [...])` on an element near the end of the same array while it is being iterated. No special permissions, hub cooperation, or race conditions are required — the AA author fully controls the formula, and the trigger sender only needs to invoke it, which is the AA's normal, intended use pattern.

### Recommendation
- In the `foreach`/`map`/`filter`/`reduce` handler (`formula/evaluation.js:2345-2469`), snapshot `arrElements` as `res.obj.slice()` for arrays (mirroring the object branch's `Object.keys(res.obj).sort()` snapshot) before starting `async.eachOfSeries`, so in-loop mutation of the source variable cannot affect the ongoing iteration.
- Add an explicit `undefined` branch to `toOscriptType` (`formula/evaluation.js:3235-3245`) that funnels into `setFatalError` rather than throwing, as defense in depth against any other place where `undefined` might reach it.
- Add a regression test mirroring `filter over object check that a copy is returned` (`test/formula.test.js:5850-5866`) but for arrays with a callback that deletes/splices the source array mid-`foreach`/`map`/`filter`, asserting a controlled fatal error rather than a crash.

### Proof of Concept
```
$o = [1, 2, 3, 4, 5];
$f = $x, $y => {
    delete($o, [4]);   // splice out the last element while $o is being iterated by foreach below
    $y
};
foreach($o, 5, $f);
```
Because `foreach` iterates the live `$o` array reference directly (`formula/evaluation.js:2371`), the in-flight `delete` shrinks it; `async.eachOfSeries` subsequently reads a stale/out-of-range index, yielding `element === undefined`, and `toOscriptType(undefined)` (`formula/evaluation.js:2390`, `3235-3245`) throws an uncaught `Error`, escaping the evaluator's normal `setFatalError` handling during AA trigger processing. function toOscriptType(x) {
	if (typeof x === 'string' || typeof x === 'boolean' || x instanceof wrappedObject)
		return x;
	if (typeof x === 'number')
		return createDecimal(x);
	if (Decimal.isDecimal(x))
		return toDoubleRange(x);
	if (typeof x === 'object' && x !== null)
		return new wrappedObject(x);
	throw Error("unknown type in toOscriptType:" + x);
}
