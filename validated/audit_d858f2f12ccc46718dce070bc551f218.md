This confirms the vulnerability: `Api::StacksController#create` does not scope stack creation to `current_api_client.stack_id`, unlike `#index`, `#show`, `#update`, and `#destroy`, which all filter through the `stacks`/`stack` helper methods in `Api::BaseController` that restrict to `current_api_client.stack_id` when set [1](#0-0) . The `create` action builds a brand-new `Stack` from arbitrary `repo_owner`/`repo_name`/`environment`/`branch` params without any check against the client's `stack_id`, only requiring the generic `write:stack` permission [2](#0-1) .

### Title
API client scoped to a single stack can create stacks for arbitrary repositories - (File: app/controllers/shipit/api/stacks_controller.rb)

### Summary
An `ApiClient` can optionally be scoped to a single stack via `belongs_to :stack, optional: true` [3](#0-2) . This scoping is the mechanism operators use to hand out narrowly-authorized tokens (e.g., "this CI token may only touch stack X"), enforced in `Api::BaseController#stacks`/`#stack` by filtering `Stack.where(id: current_api_client.stack_id)` whenever `stack_id?` is true [1](#0-0) . However, `Api::StacksController#create` never consults this scoping — it simply builds `Stack.new(create_params)` with attacker-supplied `repo_owner`/`repo_name` and finds-or-creates the target `Repository`, then requires only the coarse `write:stack` permission via `require_permission :write, :stack, only: %i[create update destroy]` [2](#0-1) .

### Finding Description
The binding that should hold is: **stack a token authorizes == stack a token touches**. For `index`, `show`, `update`, and `destroy`, this equality is enforced through the `stacks`/`stack` private helpers, which restrict the queryable set to `current_api_client.stack_id` when the client is scoped [1](#0-0) . But `create` is exempted from this restriction entirely — it does not call `stack` or `stacks`, and instead operates on `repository = Repository.find_or_create_by(owner: repo_owner, name: repo_name)` derived purely from request params [4](#0-3) . Any token holding `write:stack` — regardless of its `stack_id` scoping — can therefore create new `Stack` records (and implicitly new `Repository` records) for repositories entirely unrelated to the stack it was provisioned for.

### Impact Explanation
This breaks the intended authorization boundary of scoped `ApiClient` tokens: an operator who issues a token scoped to one stack (e.g., a deploy bot for repo A) with `write:stack` so it can archive/unarchive or manage that one stack, unintentionally grants it the ability to register arbitrary new stacks (and repositories) across the whole Shipit instance. This is a cross-repository write achieved purely by a supposedly narrowly-scoped credential, matching the "cross-repository writes" Critical-impact category, since stack creation also triggers repository registration and subsequent GitHub sync/webhook wiring for repos the token was never meant to touch.

### Likelihood Explanation
Exploitation requires possession of a valid `ApiClient` token that is stack-scoped and has the `write:stack` permission — a configuration explicitly supported by the permission/stack-scoping model (`stack_id` + `write:stack` are independent, orthogonal settings), so this is a realistic operator misconfiguration path rather than a theoretical one. No further privilege or session is needed beyond the token itself, which the attacker in this class already holds.

### Recommendation
In `Api::StacksController#create`, when `current_api_client.stack_id?` is set, reject creation of any stack whose derived `repository`/`environment`/`branch` doesn't match the client's already-assigned `stack`, or simply disallow `create` for stack-scoped clients altogether (mirroring how `stack`/`stacks` already restrict every other action).

### Proof of Concept
1. Create an `ApiClient` scoped to `stack: shipit` with `permissions: ['write:stack']` (a plausible "give this app write access to its own stack" token, analogous to the `here_come_the_walrus` fixture but with `write:stack` added) [5](#0-4) .
2. Authenticate as that client and call:
```
POST /api/stacks
repo_name=rails&repo_owner=rails&environment=staging&branch=staging
```
3. As shown by the existing (unscoped) test `"#create creates a stack and renders it back"`, this succeeds and creates a brand-new `Stack`/`Repository` [6](#0-5)  — despite the client being scoped only to the `shipit` stack, with no check comparing the created stack to `current_api_client.stack_id`.
