### Title
Missing `return` after error path leads to processing a private-payment chain with corrupted key/state and double invocation of the completion callback - (File: network.js)

### Summary
`handleSavedPrivatePayments()` in `network.js` contains a code path analogous to the CVE-2023-2177 root cause: when a partial-initialization step fails (in the CVE, `stream_in` allocation failure; here, `objectHash.getBase64Hash()` throwing on a malformed private-payment payload), the cleanup/"free" path (`deleteHandledPrivateChain(...)`, which also invokes `cb`) runs, but execution is **not halted**, so the following code keeps using the now-stale/invalid state (`json_payload_hash` is `undefined`) and invokes the async completion callback `cb` a second time via `privatePayment.validateAndSavePrivatePaymentChain`.

### Finding Description
In `network.js`, `handleSavedPrivatePayments()` iterates unhandled private payments and, for each one, defines: [1](#0-0) 

```js
var validateAndSave = function(){
    var objHeadPrivateElement = arrPrivateElements[0];
    try {
        var json_payload_hash = objectHash.getBase64Hash(objHeadPrivateElement.payload, true);
    }
    catch (e) {
        console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
        if (ws)
            sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
        deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
    }
    var key = 'private_payment_validated-'+objHeadPrivateElement.unit+'-'+json_payload_hash+'-'+row.output_index;
    privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, { ... });
};
```

`arrPrivateElements` originates from `arrChains`/`unhandled_private_payments.json`, i.e. attacker-controlled JSON supplied by a private-payment counterparty via `handlePrivatePaymentChains` (wallet.js) or a peer via `handleOnlinePrivatePayment` (network.js), and is only shape-validated (`isNonemptyObject`, `isNonemptyString`, etc.) — its `payload` contents (numbers, nested objects, blinding factors, amounts) are not otherwise sanitized before being hashed here. [2](#0-1) 

`objectHash.getBase64Hash()` stringifies the payload through `getJsonSourceString`, which can throw for certain malformed-but-shape-valid values (this mirrors the CVE precondition of "if an allocation/step fails"). [3](#0-2) 

When that `try` block throws:
1. `deleteHandledPrivateChain(..., cb)` runs — this is the "free" step: it removes the DB row **and calls `cb`**, signalling this chain as fully handled to the surrounding `async.each` loop.
2. Execution does **not** `return` from the `catch` block (no `return` keyword before `deleteHandledPrivateChain(...)`), so control falls through to the next statement, which computes `key` using the now-`undefined` `json_payload_hash` and then calls `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})` — a second, independent async pipeline that will *also* eventually call `cb` again (via its own `ifOk`/`ifError`/`ifWaitingForChain` branches) once it completes.

This is structurally the same defect class as the SCTP bug: a failure during one part of a two-part sequence triggers cleanup/release of a resource (`deleteHandledPrivateChain` deleting the row and firing the completion callback), while the second, dependent part of the code keeps running as though nothing failed and re-uses/re-frees the same logical resource (`cb`, and the DB row referenced by `row.unit/row.message_index/row.output_index`, which `validateAndSavePrivatePaymentChain` may also try to query/delete).

### Impact Explanation
Because `cb` is invoked twice for the same iteration of `async.each`, this violates async's single-callback-invocation contract and can throw/crash inside the node process at the `async.each` completion routine, and further causes `unlock()` in `handleSavedPrivatePayments` and duplicate emission of `assocNewUnits`/events to run more than intended for a single malformed private-payment chain. This can be triggered locally by a hub, a private-payment counterparty, or a paired device sending a single crafted (but shape-valid) `private_payment` payload, matching the "private payment chains" category explicitly in scope. A reliable single-message trigger for a process crash/serialization corruption in the private-payment handling pipeline can prevent a node from correctly finishing processing of legitimate queued private payments (mirroring the CVE's DoS impact via null/invalid-state access after a partial failure).

### Likelihood Explanation
Reachable by any correspondent capable of sending a `private_payment`/`private_payment_chains` device message or posting an out-of-band private payment JSON; only requires constructing a `payload` object that is shape-valid (passes `isNonemptyObject`/`isNonemptyArray` checks) but causes `getJsonSourceString`/`getBase64Hash` to throw. I was not able to fully enumerate every value that causes `getJsonSourceString` to throw (its implementation lives in `string_utils.js`, which was not returned in the available snippets), so I cannot provide a concrete guaranteed-throwing payload from the indexed content alone — this is a limitation of the available context rather than of the vulnerability logic itself.

### Recommendation
Add a `return` immediately after the `deleteHandledPrivateChain(...)` call inside the `catch` block in `handleSavedPrivatePayments()` (network.js) so that once the error path frees/finalizes the chain and calls `cb`, no further code in `validateAndSave` executes. Additionally, guard `privatePayment.validateAndSavePrivatePaymentChain` and any other consumer of `key`/`json_payload_hash` against being invoked when hashing failed, and consider wrapping `getBase64Hash` failures with early-return patterns consistently elsewhere in this file to avoid duplicate callback invocation.

### Proof of Concept
Not able to be fully constructed from the indexed codebase alone since the exact throw conditions of `getJsonSourceString` (defined in `string_utils.js`) were not retrievable in this session. Conceptually: a private-payment counterparty sends (via `wallet.js`'s `handlePrivatePaymentChains` → `network.handleOnlinePrivatePayment` → queued into `unhandled_private_payments`) a chain whose head element's `payload` is shape-valid per the checks in `handlePrivatePaymentChains`/`handleOnlinePrivatePayment` but contains a value that makes `getJsonSourceString` throw when later processed asynchronously by `handleSavedPrivatePayments`. On processing, the `catch` block executes `deleteHandledPrivateChain(...)` (firing `cb`) and then falls through to invoke `privatePayment.validateAndSavePrivatePaymentChain(...)`, which will invoke `cb` again upon completion, violating the single-callback contract of `async.each` and corrupting the surrounding control flow.

function getBase64Hash(obj, bJsonBased) {
	var sourceString = bJsonBased ? getJsonSourceString(obj) : getSourceString(obj)
	return crypto.createHash("sha256").update(sourceString, "utf8").digest("base64");
}
