### Title
Webhook signature verification keyed on attacker-controlled `repository.owner.login` allows cross-organization event forgery / team-membership escalation - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) is used to validate the inbound HMAC signature based on `repository_owner`, a value read directly from the unauthenticated JSON payload, before any signature has been checked. If any configured organization in a multi-org `secrets.github` deployment has no `webhook_secret` set (or the attacker can otherwise select a config with a blank secret), `GitHubApp#verify_webhook_signature` unconditionally returns `true`, and the attacker-forged payload is then processed by handlers that act on a *different* field of the same payload (`repository.full_name`, `organization.login`) to identify the target stack/team. This breaks the binding "organization whose secret authenticated the request == organization/repository the handlers act on."

### Finding Description
`repository_owner` is derived straight from attacker-controlled JSON, before the signature check occurs: [1](#0-0) 

That value is fed into `Shipit.github(organization: repository_owner)`, which looks up the org's app config and instantiates/caches a `GitHubApp` for it: [2](#0-1) [3](#0-2) 

Signature verification is then performed against *that organization's* `webhook_secret`. Critically, if the secret is blank/`nil` for the selected org, verification is bypassed entirely: [4](#0-3) 

The multi-org config format documents `webhook_secret` as a per-org key that can be `nil`: [5](#0-4) 

Once `head(422)` is *not* triggered (because verification returned `true`), `create` parses the full body and dispatches it to registered handlers using the same untrusted payload: [6](#0-5) 

Handlers resolve the target `Repository`/`Stack`/`Team` using a *different* payload field than the one used for signature-org-selection — `repository.full_name` (for push/status/pull_request events) or `organization.login`/`team` (for membership events) — with no re-check that this matches the org whose secret validated the request: [7](#0-6) [8](#0-7) [9](#0-8) 

This is analogous to the reported bug class: the field the code trusts as verified/gating (`Bob`'s presumed-safe reward-address / here, the org used to select the HMAC secret) is not the same field that later actions operate on (the ETH transfer target / here, `repository.full_name`, `organization.login`, `team`). An attacker supplies a payload where `repository.owner.login` (or the `organization.login` fallback) names an org whose config has no `webhook_secret`, causing `verify_webhook_signature` to return `true` for *any* signature (including none), while the rest of the payload (`repository.full_name`, `team`, `member.login`) references a different, sensitive target — e.g., an org/repo that is fully configured with GitHub App credentials and `Shipit.github_teams` authorization.

### Impact Explanation
Successful exploitation lets an unauthenticated attacker forge GitHub webhook events for the engine:
- `MembershipHandler` creates/updates `Team` records and adds/removes arbitrary GitHub logins from a `Team` via `team.add_member(member)`/`team.members.delete(member)`, based entirely on attacker-supplied `team`/`member` sub-payloads once the (misdirected) signature check passes. Since `User#authorized?` and `force_github_authentication` gate application access on `Shipit.github_teams` membership, forging `membership` events lets an attacker grant an arbitrary GitHub account authorization into the app (escalation into `Shipit.github_teams` authorization), or remove a legitimate operator's authorization. [10](#0-9) [11](#0-10) 
- `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, and the `pull_request` handlers can be triggered against any tracked stack whose `repository.full_name` the attacker names, forcing sync jobs, status changes, or review-stack archive/unarchive actions to run for stacks unrelated to the (weakly-configured) organization used to pass the signature check.

This matches the "High: escalation into `Shipit.github_teams` authorization" impact bucket, contingent on the deployment using the multi-organization config schema (`secrets.github` keyed by org) with at least one organization configured without a `webhook_secret`.

### Likelihood Explanation
This requires a specific, but documented and supported, configuration state: multi-org `secrets.github` schema where one organization entry has a blank/`nil` `webhook_secret` (the shipped `config/secrets.development.shopify.yml` example shows `webhook_secret: # nil` as a normal, template-provided value). Given that, exploitation needs no credentials, tokens, or GitHub App keys — only a POST to the public `/webhooks` endpoint with a crafted JSON body and the correct `X-Github-Event` header. The likelihood is therefore tied to operator configuration hygiene rather than to any attacker skill; it is plausible in real deployments since the templated secrets file normalizes `webhook_secret: nil` per org.

### Recommendation
- Do not let `verify_webhook_signature` return `true` when `webhook_secret` is blank in a multi-organization configuration; treat a missing per-org webhook secret as a hard configuration error (reject the webhook) rather than an implicit bypass.
- Bind the organization used for signature verification to the *same* field(s) later trusted by handlers: validate that `repository.full_name`'s owner matches `repository_owner`/`organization.login` used for the HMAC lookup, and reject mismatches.
- Consider deriving the signing organization from a value included in the verified signature computation itself (e.g., require exact repository-to-org consistency checks after verification, not before), so a single unauthenticated payload cannot pick which secret protects it.

### Proof of Concept
Preconditions: `secrets.github` configured with at least two orgs, e.g. `orgA` (properly configured with a `webhook_secret`) and `orgB` (`webhook_secret: nil`, as in the shipped template).

1. Attacker sends:
```
POST /webhooks
X-Github-Event: membership
X-Hub-Signature: sha1=anything-or-omitted
Content-Type: application/json

{
  "action": "added",
  "team": { "id": 1, "name": "Admins", "slug": "admins", "url": "https://x" },
  "organization": { "login": "orgB" },
  "member": { "login": "attacker-controlled-account" }
}
```
2. `repository_owner` falls back to `organization.login` = `"orgB"` (no `repository` key present): [1](#0-0) 
3. `Shipit.github(organization: "orgB")` loads `orgB`'s config with `webhook_secret: nil`; `verify_webhook_signature` short-circuits to `true`: [4](#0-3) 
4. `create` dispatches the payload to `MembershipHandler`, which creates/looks up `Team` id `1` (which may correspond to a team actually used for `Shipit.github_teams` authorization on `orgA`) and adds `attacker-controlled-account` as a member: [12](#0-11) 
5. The attacker's GitHub account is now recorded as a member of that `Team`; if the corresponding GitHub login later authenticates via OAuth, `User#authorized?` grants access based on this forged membership record.

Note: This PoC assumes an operator has left one organization's `webhook_secret` unset in the multi-org schema, matching the shipped configuration template; I was unable to verify from the index whether the application enforces `webhook_secret` presence elsewhere (e.g., at boot/validation) which could mitigate this in practice — this would need to be confirmed in a running deployment.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

      class MembershipHandler < Handler
        params do
          requires :action, String
          requires :team do
            requires :id, Integer
            requires :name, String
            requires :slug, String
            requires :url, String
          end
          requires :organization do
            requires :login, String
          end
          requires :member do
            requires :login, String
          end
        end
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
      end
