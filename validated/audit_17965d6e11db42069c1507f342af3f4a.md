### Title
Webhook signature verification key is selected from an untrusted payload field that is independent of the field used to target the stack, and is skipped entirely for organizations without a `webhook_secret` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which* GitHub organization's secret to verify a webhook against using a field taken directly out of the unauthenticated JSON body (`repository.owner.login` / `organization.login`), while the handlers that actually mutate state (find and act on a `Stack`) key off a *different* field of the same untrusted body (`repository.full_name`). Nothing binds these two fields together, and if the organization selected for verification has no `webhook_secret` configured, verification is skipped unconditionally. This breaks the "organization that authenticated versus the repository that is written" trust binding called out in scope.

### Finding Description
`verify_signature` derives the organization used to pick a signing secret straight from the request body, before any authentication has happened: [1](#0-0) [2](#0-1) 

`repository_owner` is read from `params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')` — both attacker-controlled fields in the raw, not-yet-verified body.

`Shipit.github(organization: ...)` looks up per-organization config (`webhook_secret`, `app_id`, etc.) from `secrets.github`, keyed by the org name supplied by the caller: [3](#0-2) 

The actual signature check silently accepts *any* payload when that organization has no `webhook_secret` configured: [4](#0-3) 

Once `verify_signature` passes (which requires either a correctly forged HMAC for the org named in `repository.owner.login`, or that org simply having a blank `webhook_secret`), the request body is handed unmodified to every registered handler: [5](#0-4) 

Handlers do **not** re-derive the organization from `repository.owner.login` — they instead resolve the target `Stack` using `repository.full_name`: [6](#0-5) 

For example `PushHandler` uses this to find stacks and trigger `sync_github`: [7](#0-6) 

Because `repository.owner.login` (used to select the verification key) and `repository.full_name` (used to select the acted-upon `Stack`/repository) are two independent fields of the same forged JSON body, an attacker can decouple them: claim ownership under an organization X (whose `webhook_secret` is unset, so `verify_webhook_signature` unconditionally returns `true`), while setting `repository.full_name` to `Y/target-repo`, an entirely different, properly-configured organization/repository hosted on the same Shipit instance. The request sails through `verify_signature` without ever being checked against org Y's secret, yet the handler chain (push/status/check_suite/pull_request handlers) will act on org Y's stacks — e.g. triggering `sync_github`, posting fake CI/check statuses that unblock `merge_status` gating, or creating/labeling pull requests that feed the auto-merge and continuous-deployment pipeline.

This is the direct structural analog of the reported bug class: a security-relevant conditional (`setState`'s state check / here, `verify_webhook_signature`'s "no secret configured" branch) silently no-ops instead of enforcing an invariant, and the field trusted for authorization (`repository_owner`) is not the field trusted for the actual write (`repository_name`).

### Impact Explanation
Deployments using the documented multi-organization GitHub config (as shown in `config/secrets.development.shopify.yml`, which allows several orgs each with their own, independently-nullable `webhook_secret`) are exposed: any org left without a webhook secret (a state the config template explicitly allows and even shows as the default/example value) becomes a skeleton key. An attacker who can send an arbitrary HTTP request to `/webhooks` (no session, no `ApiClient` token, no GitHub credentials needed) can forge events (`push`, `status`, `check_suite`, `pull_request`) that are processed against **any other organization's stacks** on the same instance, because the code path that decides "is this authentic" and the code path that decides "what do I do with it" trust two different, attacker-supplied fields. This can trigger unauthorized syncs, fake CI/check-run statuses that unblock deploy gating, and pull-request state changes that feed continuous deployment — i.e., an unauthorized deploy/merge path, matching the High/Critical impact bar for unauthorized deploy/merge or authentication bypass.

### Likelihood Explanation
Requires only that the Shipit instance is configured with more than one GitHub organization and at least one of them lacks a `webhook_secret` — a state that the shipped example configuration (`config/secrets.development.shopify.yml`) explicitly demonstrates as valid/expected, and which is plausible during progressive onboarding of new orgs. No credentials, tokens, or repository access are required from the attacker; only a crafted HTTP POST to the public `/webhooks` endpoint.

### Recommendation
- In `WebhooksController`, derive the organization used for signature verification from the *same* value used later to resolve the target repository/stack (`repository.full_name`'s owner segment), and reject the request if `repository.owner.login`/`organization.login` disagrees with it.
- In `GitHubApp#verify_webhook_signature`, do not silently return `true` when `webhook_secret` is blank; instead treat a missing secret as a hard configuration error and refuse the webhook (fail closed), or require `webhook_secret` to be present for every configured organization at boot time.
- Ensure the org selected for verification is fully committed before any handler dispatch uses fields whose trust is not equivalent to that org.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.github`: `orgA` (no `webhook_secret` set) and `orgB` (has `webhook_secret` set, hosts a real tracked `Stack`).
2. Send:
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=anything
Body: {
  "repository": { "owner": {"login": "orgA"}, "full_name": "orgB/target-repo" },
  "ref": "refs/heads/master",
  "after": "deadbeef..."
}
```
3. `repository_owner` resolves to `orgA`; `Shipit.github(organization: 'orgA').verify_webhook_signature` returns `true` unconditionally because `orgA`'s `webhook_secret` is blank (`lib/shipit/github_app.rb:76-83`).
4. `create` proceeds and dispatches to `PushHandler`, which resolves stacks via `repository.full_name` = `orgB/target-repo` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) and calls `stack.sync_github` on `orgB`'s real stack — without ever validating the request against `orgB`'s webhook secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
