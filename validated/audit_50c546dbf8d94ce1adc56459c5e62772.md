### Title
Cross-organization webhook forgery allows escalation into `Shipit.github_teams` authorization - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to use for HMAC verification based on `repository.owner.login` (falling back to `organization.login`) taken from the untrusted request body. The handler that actually performs the privileged write — `MembershipHandler`, which creates/looks-up a `Team` and adds a `User` to it (and this `Team` can be one of `Shipit.github_teams`, the set that gates `User#authorized?`) — reads its own `organization.login` field independently, with no check that it equals the value used to select/verify the signing secret. This is the same class of bug as the reported H-01 issue: the field that is cryptographically verified is not the field that is actually acted upon, and the two are never validated against each other.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/secret like this: [1](#0-0) [2](#0-1) 

`repository_owner` is derived from `params.dig('repository', 'owner', 'login')`, falling back to `params.dig('organization', 'login')` only if `repository` is absent. This value is used solely to look up which `Shipit.github(organization:)` app (and therefore which `webhook_secret`) validates `X-Hub-Signature`.

Once signature verification passes, the raw parsed body is dispatched to handlers based on `X-Github-Event`: [3](#0-2) 

For a `membership` event, `MembershipHandler` re-parses the *same* body but only requires `organization.login`, `team`, and `member` — it never looks at `repository`: [4](#0-3) 

`find_or_create_team!` sets `team.organization = params.organization.login`, and `team.add_member(member)` adds an arbitrary GitHub login (also attacker-supplied) to that team. This team can be one of the organization-scoped teams whose membership drives global authorization: [5](#0-4) [6](#0-5) 

Because the JSON body is fully attacker-controlled (this is a public, unauthenticated endpoint gated only by `X-Hub-Signature`), and because `repository.owner.login` (used to choose the verifying secret) and `organization.login` (used to determine which `Team`/org gets written) are two independent keys in the same body, an attacker can:
1. Set `repository.owner.login` to an organization for which they can produce a valid signature (their own GitHub organization installed on a multi-org Shipit deployment — this is a legitimately-configured, supported deployment pattern per `docs/setup.md`'s "Using Multiple Github Applications" section — or any org whose `webhook_secret` is left blank, which `docs/setup.md` explicitly documents as optional).
2. Set `organization.login` to the victim organization backing one of `Shipit.github_teams`.
3. Set `team` to match an existing authorized team's `github_id`/`slug`, and `member.login` to their own (or any) GitHub login.
4. Sign the payload with the secret from step 1 and POST it to `/webhooks`.

`verify_signature` succeeds because it validates against the org selected in step 1, while `MembershipHandler` writes membership under the org/team selected in step 2 — the two are never cross-checked.

### Impact Explanation
This lets an unprivileged external attacker who controls (or can obtain a webhook secret for) any single organization configured in the multi-org `github:` secrets, or who finds an organization with no `webhook_secret` set, add an arbitrary GitHub account (their own) as a member of a `Team` that is included in `Shipit.github_teams`. Because `User#authorized?` is computed purely from `Team` membership, this directly escalates the attacker into the application's access-control group, letting them subsequently authenticate via the normal (legitimate) GitHub OAuth flow as an "authorized" Shipit user with permission to view stacks, trigger deploys/rollbacks, and manage API clients. This matches the explicitly allowed High-severity impact: "escalation into `Shipit.github_teams` authorization."

### Likelihood Explanation
Likelihood is moderate-to-high in any deployment using the documented multi-organization GitHub App configuration (a first-class, documented feature), since any org admin in that configuration inherently knows their own webhook secret and can forge a payload targeting a different org's team. It is also trivially exploitable with zero secret knowledge whenever any configured organization has left `webhook_secret` blank (which the setup docs describe as optional). The endpoint requires no authentication, session, or API token — only crafting a raw HTTP POST with a valid `X-Hub-Signature` for whichever organization the attacker can sign for.

### Recommendation
Require that the `organization.login` (or equivalent scoping field) used by each webhook `Handler` be validated to equal the `repository_owner`/organization that was used to select and verify the `X-Hub-Signature`, analogous to the H-01 fix of always trusting only the value that was actually authenticated. Concretely, `Handler` (and specifically `MembershipHandler`) should receive the verified organization from the controller (the one used in `verify_signature`) and assert it matches `params.organization.login` before creating/mutating any `Team`, rejecting the event otherwise.

### Proof of Concept
Given a multi-org configuration such as `test/dummy/config/secrets_double_github_app.yml` (`OrgOne`, `OrgTwo`, both with configurable/optional `webhook_secret`):

```
POST /webhooks
X-Github-Event: membership
X-Hub-Signature: sha1=<HMAC using OrgOne's webhook_secret>

{
  "action": "added",
  "team": { "id": 999, "name": "developers", "slug": "developers", "url": "https://example.com" },
  "organization": { "login": "OrgTwo" },
  "member": { "login": "attacker-github-login" },
  "repository": { "owner": { "login": "OrgOne" } }
}
```

`verify_signature` resolves `repository_owner` to `"OrgOne"` and validates the signature against `OrgOne`'s secret (known to the attacker), passing verification. `MembershipHandler` then processes the event using `organization.login == "OrgTwo"`, creating/finding a `Team` scoped to `OrgTwo` and adding `attacker-github-login` to it — even though the signature never proved anything about `OrgTwo`. If `OrgTwo/developers` is part of `Shipit.github_teams`, the attacker's GitHub account is now a member of an authorization-granting team, and logging in via the normal `/github/auth/github` OAuth flow will pass `User#authorized?`.     def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
