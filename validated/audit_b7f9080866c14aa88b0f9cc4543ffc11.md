### Title
Cross-repository `Status` injection via unscoped `Commit.where(sha:)` lookup flips `Commit#deployable?` for an unrelated stack - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits purely by `sha` with no repository scoping, so a `status` webhook whose signature is validated only against `params.repository.full_name`'s org can still create a `Shipit::Status` on a `Commit` belonging to a completely different stack/repository, provided the two repositories happen to share a commit sha (e.g. shared history from a common upstream/fork). This status is then folded into `Status::Group`/`Commit#deployable?` without any check that its origin repository matches `stack.repository`.

### Finding Description
Binding claimed: `stack.repository.full_name == params.repository.full_name` for every `Status` contributing to `commit.deployable?`. Tracing the code shows this is never enforced:

- `WebhooksController#verify_signature` verifies the HMAC signature using `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight from the *attacker-supplied* `payload['repository']['owner']['login']` [1](#0-0) [2](#0-1) . This only proves the request was signed by *some* org's registered GitHub App secret (org B, which the attacker owns/administers) - it says nothing about org A (the target stack's org).
- `StatusHandler#process` then resolves target commits with `Commit.where(sha: params.sha)`, with zero repository/stack filtering [3](#0-2) . Unlike `PushHandler`, which scopes through `Handler#stacks` (derived from `payload.dig('repository','full_name')`) before touching any stack [4](#0-3) [5](#0-4) , `StatusHandler` never calls `stacks` or checks `repository_name` at all.
- `Commit#create_status_from_github!` -> `statuses.replicate_from_github!(stack_id, github_status)` creates a `Status` row scoped to `commit.stack_id` (the *victim* stack) using attacker-controlled `state`/`context`/`description` [6](#0-5) [7](#0-6) .
- `Commit#deployable?` computes `success? && !blocked?`, where `success?`/`blocking?` are delegated to `status`, which is `Status::Group.compact(self, statuses_and_check_runs)` built from **all** `Status` rows attached to the commit regardless of which org's webhook created them [8](#0-7) [9](#0-8) . `Status::Group#select_significant_status` picks the first non-success/non-pending status, or all-success if none, meaning an injected `success` context can either satisfy `required_statuses` or simply add a benign context that doesn't block, tipping `blocked?`/`success?` toward true [10](#0-9) .

Attack flow: attacker registers/owns repository B (any GitHub org, with its own valid webhook secret/App), and controls a branch/PR whose HEAD commit sha collides with a commit sha already present in victim stack A's `commits` table (realistic when A's repository forked from, mirrors, or shares history with B - e.g. an open-source upstream both track). Attacker pushes a `status` webhook payload for repository B's own `full_name` and org (validly signed with org B's secret) but with `sha` equal to the shared commit hash and `state: success`, `context: <the missing required context>`. `verify_signature` passes because it only validates against org B. `StatusHandler.process` finds the `Commit` row in stack A matching that sha (since lookup is table-wide, not stack/repo-scoped) and creates a `Status` on it belonging to stack A. This can complete `required_statuses` or otherwise remove the last blocker, flipping `commit.deployable?` to `true` for stack A, enabling continuous deployment/merge without any actor from org A ever authorizing it.

Existing guards do not stop this: `verify_signature` authenticates the sender as *a* valid GitHub App installation, not as the *specific* repository's owner referenced by the sha being mutated; `drop_unhandled_event` only filters unregistered event types; there is no `ExplicitParameters` constraint tying `sha` to `repository`; and no model validation ties `Status#stack_id` to the webhook's `repository.full_name`.

### Impact Explanation
An attacker who controls an unrelated, self-registered repository (org B) can inject a fabricated `success` (or any) status onto a commit belonging to a victim stack A that they do not own or administer, provided a shared sha exists (fork/mirror/shared-history scenario). This can complete `stack.required_statuses` or eliminate `stack.blocking_statuses` obstacles, flipping `Commit#deployable?` to `true` and triggering `schedule_continuous_delivery`/merges for stack A - an unauthorized deploy decision influenced by a non-authorized org. This matches "a payload for one repository mutating another's stack/commit" / "unauthorized deploy" under Critical impact. The attack is repeatable against any victim stack sharing commit history with an attacker-controlled repo, though it is not exploitable against arbitrary unrelated shas since git commit hashes are content-addressed and won't collide without shared history/rebasing/cherry-picking scenarios.

### Likelihood Explanation
Requires: (1) attacker owns/administers a GitHub repository with a legitimately configured GitHub App/webhook secret recognized by `Shipit.github(organization:)` for org B - a low-cost precondition satisfiable by any GitHub user creating their own org/repo and installing a Shipit-compatible app if `Shipit.github_teams`/App config allows arbitrary orgs, or by using an org already configured in this Shipit instance; and (2) a commit sha that is simultaneously reachable in the attacker's repository and present in victim stack A's `commits` table - realistic for forks, mirrors, or repositories tracking a shared upstream, but not for arbitrary/unrelated victims. Given (1)+(2), the exploit is a single unauthenticated-looking (but validly-signed-by-org-B) POST to `/webhooks`, fully repeatable and scriptable.

### Recommendation
In `StatusHandler#process` (and analogously wherever `Commit.where(sha: ...)` / similar unscoped lookups are used to attach webhook data), scope the commit lookup to commits whose `stack.repository.full_name` matches `payload.dig('repository', 'full_name')`, e.g. via `stacks.flat_map(&:commits).where(sha: params.sha)` or joining `Commit -> Stack -> Repository` and filtering by `repository_name`, mirroring the pattern already used in `Handler#stacks`/`PushHandler`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status webhook from unrelated repository cannot flip deployable? for another stack's commit" do
  stack_a = shipit_stacks(:shipit) # repository "org-a/repo-a"
  commit = stack_a.commits.create!(sha: 'deadbeef' * 5, message: 'x')
  stack_a.update!(deploy_spec: build_deploy_spec_requiring_status('ci/build'))

  refute commit.deployable?, "sanity: commit should not be deployable before injected status"

  # Attacker-controlled payload signed for org B, but referencing stack A's commit sha
  payload = {
    'sha' => commit.sha,
    'state' => 'success',
    'context' => 'ci/build',
    'repository' => { 'full_name' => 'org-b/repo-b', 'owner' => { 'login' => 'org-b' } }
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(ActiveSupport::HashWithIndifferentAccess.new(payload))

  binding_repo_owner = stack_a.repository.full_name       # "org-a/repo-a"
  binding_speaker     = payload['repository']['full_name'] # "org-b/repo-b"
  refute_equal binding_repo_owner, binding_speaker, "attacker org differs from stack owner - binding should have blocked this"

  assert commit.reload.deployable?, "BUG: cross-repo status flipped deployable? without repository authorization"
end
```
This demonstrates `stack.repository.full_name` ("org-a/repo-a") != `params.repository.full_name` ("org-b/repo-b") for the `Status` that determines `deployable?`, proving the binding is not enforced.
