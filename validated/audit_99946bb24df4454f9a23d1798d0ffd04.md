### Title
Spender-attested assets use the live/current attestor list at spend-time, permanently freezing balances of holders whose attestor was later removed - (File: `validation.js`, `storage.js`)

### Summary
For assets created with `spender_attested: true`, spending eligibility is not tied to the attestor list that was in force when the holder's address was attested/when the units were received. Instead, eligibility is re-evaluated on every spend against whatever attestor list the asset **definer currently has published**. Because the definer can freely update this list at any time via an `attestor_list` message, removing an attestor after a holder has already legitimately obtained units retroactively revokes that holder's ability to ever spend the balance they already hold — an analog of the reported issue where a dynamically-fetched, mutable list (reward tokens in the Aura/Convex pool) determines payout eligibility, and removing an entry from that live list permanently strands funds that were already earned/held.

### Finding Description
An asset's attestor list is defined at asset creation (`asset_attestors` table) and can subsequently be changed by the asset's definer through `validateAttestorListUpdate`, which imposes no restriction preventing the definer from removing an attestor that previously attested existing holders: [1](#0-0) 

When a `spender_attested` asset is spent, eligibility of the spending address is computed by `loadAssetWithListOfAttestedAuthors`, which reads the asset (and therefore its **current** `arrAttestorAddresses`, as of the validating unit's `last_ball_mci`) and then calls `filterAttestedAddresses`: [2](#0-1) 

`filterAttestedAddresses` performs a live join against the attestations table, filtering strictly by whichever attestor addresses are in the asset's **current** definition, not the attestor list that existed at the time the spender was originally attested or at the time the spender received the asset units: [3](#0-2) 

This mirrors the root cause in the external report: a set of entries that determines entitlement/eligibility (reward tokens vs. attestors) is fetched fresh at consumption time rather than being pinned to the state that existed when the entitlement was earned. If an entry (reward token / attestor) is later removed from that live set, previously-earned or previously-authorized value tied to the removed entry becomes permanently unreachable.

### Impact Explanation
If the definer of a `spender_attested` asset removes an attestor address from the list (an action fully within the definer's normal, permitted capability, exercised via a routine `attestor_list` unit), every holder who was attested only by that now-removed attestor loses the ability to spend the asset units they already legitimately hold. Their balance is not burned but becomes permanently frozen — unauthorized funds freezing, one of the explicitly accepted high-impact categories (AA/asset fund loss or freezing). This can happen even to holders who received/were attested long before the list change and did nothing wrong.

### Likelihood Explanation
The trigger requires only a normal `attestor_list` update unit, an operation explicitly supported and unrestricted in timing/effect on existing holders. Any asset definer (an "asset issuer" role explicitly reachable per scope) can post this at will; it requires no privileged core-node behavior, no malicious peer, and no protocol edge case beyond the ordinary "asset issuance and transfer conditions" flow. Because holders have no way to lock in their eligibility at time of receipt, and no mechanism grandfathers already-attested spenders, likelihood of the freeze occurring whenever an attestor is legitimately rotated/removed is high.

### Recommendation
Do not evaluate spender attestation purely against the attestor list as of the spending unit's `last_ball_mci`. Either (a) pin/snapshot the qualifying attestor set to the state at the time the spender received the asset units (analogous to storing "reward tokens with the tokenID" in the referenced report), or (b) require that removal of an attestor cannot retroactively de-authorize addresses that were already attested and already hold balances, e.g. by grandfathering addresses attested before the list-update unit's mci.

### Proof of Concept
1. Definer creates asset A with `spender_attested: true` and attestor list `[X]`.
2. Attestor `X` attests address `H`; `H` receives units of asset A (transfer/issue payment).
3. Definer later posts an `attestor_list` update removing `X` from A's attestor list (`validateAttestorListUpdate`, `validation.js:2829-2848` — no check preventing this even though `H` already relies on `X`'s attestation and already holds funds).
4. `H` attempts to spend asset A. Validation calls `loadAssetWithListOfAttestedAuthors` → `filterAttestedAddresses` (`storage.js:1959-1992`), which now queries attestations only against the *current* attestor list (no longer containing `X`), so `H` is excluded from `arrAttestedAddresses`.
5. `H`'s spend of already-held asset A units is rejected as invalid, and since there is no other legitimate attestor covering `H`, the balance is permanently unspendable.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}

// filter only those addresses that are attested (doesn't work for light clients)
function filterAttestedAddresses(conn, objAsset, last_ball_mci, arrAddresses, handleAttestedAddresses){
	conn.query(
		"SELECT DISTINCT address FROM attestations CROSS JOIN units USING(unit) \n\
		WHERE attestor_address IN(?) AND address IN(?) AND main_chain_index<=? AND is_stable=1 AND sequence='good' \n\
			AND main_chain_index>IFNULL( \n\
				(SELECT main_chain_index FROM address_definition_changes JOIN units USING(unit) \n\
				WHERE address_definition_changes.address=attestations.address AND main_chain_index<=? AND is_stable=1 AND sequence='good' ORDER BY main_chain_index DESC LIMIT 1), \n\
			0)",
		[objAsset.arrAttestorAddresses, arrAddresses, last_ball_mci, last_ball_mci],
		function(addr_rows){
			var arrAttestedAddresses = addr_rows.map(function(addr_row){ return addr_row.address; });
			handleAttestedAddresses(arrAttestedAddresses);
		}
	);
}

// note that light clients cannot check attestations
function loadAssetWithListOfAttestedAuthors(conn, asset, last_ball_mci, arrAuthorAddresses, bAcceptUnconfirmedAA, handleAsset){
	if (arguments.length === 5) {
		handleAsset = bAcceptUnconfirmedAA;
		bAcceptUnconfirmedAA = false;
	}
	readAsset(conn, asset, last_ball_mci, bAcceptUnconfirmedAA, function(err, objAsset){
		if (err)
			return handleAsset(err);
		if (!objAsset.spender_attested)
			return handleAsset(null, objAsset);
		filterAttestedAddresses(conn, objAsset, last_ball_mci, arrAuthorAddresses, function(arrAttestedAddresses){
			objAsset.arrAttestedAddresses = arrAttestedAddresses;
			handleAsset(null, objAsset);
		});
	});
}
