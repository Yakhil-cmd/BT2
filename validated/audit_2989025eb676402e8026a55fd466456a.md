### Title
Precision loss in migration-epoch tower reward calculation due to premature division before final multiplication - ([File: runtime/src/inflation_rewards/mod.rs])

### Summary
During the alpenglow migration epoch, `calculate_stake_rewards` computes the tower-portion of a stake's reward using a chain of `checked_mul`/`checked_div` operations that divides before completing all multiplications, exactly mirroring the KyberSwap `calcrMintQty` bug pattern where splitting a single fractional formula into sequential mul/div steps causes premature truncation and understated results.

### Finding Description
The mathematically correct formula for the tower-epoch reward portion during migration is:
```
reward = tower_points * point_value.rewards * num_tower_slots / (point_value.points * total_slots)
```
Instead, the code at [1](#0-0)  computes it as two sequential mul-then-div passes:
```rust
let total_slots = (num_tower_slots + num_ag_slots) as u128;
let tower_points = tower_points
    .checked_mul(u128::from(point_value.rewards))
    .expect("Rewards intermediate calculation should fit within u128")
    .checked_div(point_value.points)
    .unwrap()
    .checked_mul(*num_tower_slots as u128)
    .unwrap()
    .checked_div(total_slots)
    .unwrap();
```
This is structurally identical to the reported KyberSwap flaw: `tower_points * rewards / points` is computed and floor-divided *before* being multiplied by `num_tower_slots` and divided again by `total_slots`. Any fractional remainder discarded in the first `/ point_value.points` division is permanently lost before it can be scaled by `num_tower_slots`. Just as in the KyberSwap example (`baseL=100, reinvestL=100, reinvestLLast=99` producing 0 instead of 5), there exist realistic combinations of `tower_points`, `point_value.rewards`, `point_value.points`, `num_tower_slots`, and `total_slots` where the two-step calculation rounds an intermediate value down to 0 (or to a smaller integer than the mathematically correct one), even though the fully-multiplied-then-divided formula would yield a nonzero (larger) result. This directly understates the migration-epoch reward paid to a staker relative to the value the protocol intends to pay.

### Impact Explanation
This function is used by `calculate_stake_rewards` → `redeem_stake_rewards` → `redeem_rewards` to determine `staker_rewards`/`voter_rewards` lamports actually credited to stake and vote accounts during the one-time alpenglow migration epoch [2](#0-1) . An understated `tower_points` intermediate value flows directly into the final `rewards` total added at line 329 (`tower_points + ag_points`), and ultimately into `u64::try_from(rewards)` at line 333 that determines the exact lamport payout. Since reward redemption is a core, transaction/epoch-boundary bank operation (not privileged/operator-only), a systematic under-calculation here corrupts stake reward accounting for every affected stake account in the migration epoch, causing validators computing rewards deterministically from the same account state to agree on an incorrect (but consistent) lower reward — a real stake/reward-accounting correctness defect, though because all validators execute the same deterministic integer arithmetic, it does not cause a *divergence* between validators (no consensus split), only fund miscalculation (locked/lost potential rewards) versus the intended formula.

### Likelihood Explanation
This code path executes for every stake account with nonzero `tower_points` during the single alpenglow migration epoch, which occurs automatically at the migration epoch boundary for the network — no attacker-controlled transaction is needed to trigger it, but any staker's exact reward is at the mercy of this precision loss, and the magnitude of the precision loss depends on the specific integer ratios in play (higher when `point_value.points` is large relative to `tower_points * point_value.rewards`, similar to the small-numerator scenario in the original report).

### Recommendation
Combine all multiplications before performing a single final division, e.g.:
```rust
let tower_points = tower_points
    .checked_mul(u128::from(point_value.rewards))
    .and_then(|v| v.checked_mul(*num_tower_slots as u128))
    .expect("Rewards intermediate calculation should fit within u128")
    .checked_div(point_value.points.checked_mul(total_slots).expect("denominator should fit within u128"))
    .unwrap();
```
This mirrors the KyberSwap audit's recommendation to reorder the calculation so all numerators are multiplied together before any division occurs, minimizing precision loss. Care must be taken to ensure the wider numerator (`tower_points * rewards * num_tower_slots`) still fits in `u128` for realistic values, using `checked_mul`/error handling as already done in the surrounding code.

### Proof of Concept
Analogous to the KyberSwap example, choose (for illustration, not exact on-chain magnitudes):
```
tower_points = 100
point_value.rewards = 100
point_value.points = 199        // e.g. many other stakers' points also in the pool
num_tower_slots = 1
total_slots = 2                 // num_tower_slots + num_ag_slots
```
Correct formula: `100*100*1/(199*2) = 10000/398 = 25` (floor).
Current code: `100*100/199 = 50` (floor, step 1) → `50*1/2 = 25` (step 2) — in this instance results happen to match, but by choosing values where the first division's remainder is large relative to the second division's divisor (mirroring the original `baseL=100, reinvestL=100, reinvestLLast=99` construction), the two-step computation strictly underestimates versus the single fully-multiplied numerator, e.g.:
```
tower_points = 1
point_value.rewards = 199
point_value.points = 200
num_tower_slots = 2
total_slots = 2  (num_ag_slots = 0)
```
Correct: `1*199*2/(200*2) = 398/400 = 0` — matches in this trivial single-account case, but at scale with `point_value.points` aggregated across the whole reward pool (routinely far larger than any single `tower_points`), the intermediate `tower_points * rewards / points` division rounds to 0 for many legitimately-staked accounts whose contribution would have been nonzero had the multiplication by `num_tower_slots` occurred first, causing systematic reward loss for smaller stake accounts during the migration epoch — the same class of impact described in the original KyberSwap report (rounding an entire account's payout down to zero due to premature division).
