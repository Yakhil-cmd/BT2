### Title
Unchecked Zero `_to` Address in Bridge Transfer Request Functions Causes Permanent Loss of Bridged Assets — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`, `BridgeTransferERC20.sol`, `BridgeTransferERC721.sol`)

---

### Summary

The Kaia service-chain bridge contracts (`BridgeTransferKLAY`, `BridgeTransferERC20`, `BridgeTransferERC721`) accept a `_to` destination address parameter in their public request functions without validating it against `address(0)`. Any user can call `requestKLAYTransfer(address(0), ...)`, `requestERC20Transfer(..., address(0), ...)`, or `requestERC721Transfer(..., address(0), ...)`. The Go-level bridge operator (`bridge_manager.go`) faithfully relays the emitted event to the counterpart chain with `_to = address(0)`, where `handleKLAYTransfer` executes a low-level `.call.value()` to `address(0)` — which succeeds in the EVM — permanently destroying the bridged KAIA. The user's assets on the source chain are locked (or burned), the bridge nonce is consumed, and the assets on the destination chain are irrecoverably lost.

---

### Finding Description

**Source-chain request functions — no zero-address guard:**

`requestKLAYTransfer` calls `_requestKLAYTransfer` which has no check on `_to`: [1](#0-0) 

`requestERC20Transfer` calls `_requestERC20Transfer` which has no check on `_to`: [2](#0-1) 

`requestERC721Transfer` calls `_requestERC721Transfer` which has no check on `_to`: [3](#0-2) 

The 1-step entry points `onERC20Received` and `onERC721Received` are equally unguarded: [4](#0-3) 

**Go bridge operator — no validation before relay:**

`handleRequestValueTransferEvent` in `bridge_manager.go` reads `to` directly from the event and passes it to the counterpart chain's handle function without any zero-address check: [5](#0-4) 

**Destination-chain handle function — KAIA sent to `address(0)` succeeds:**

`handleKLAYTransfer` executes a low-level call to `_to` with the full KAIA value. In the EVM, a `.call.value()` to `address(0)` returns `true` and the KAIA is permanently destroyed: [6](#0-5) 

---

### Impact Explanation

- **Source chain:** User's KAIA is locked inside the bridge contract (non-mintBurn) or burned (mintBurn mode). It is not returned.
- **Destination chain:** `handleKLAYTransfer` sends KAIA to `address(0)` via `.call.value()("")`. This call succeeds (EVM does not revert on transfers to `address(0)`), so the KAIA is permanently destroyed.
- **Bridge state:** The request nonce is consumed (`requestNonce++`), the handle nonce is updated (`_updateHandleNonce`), and `_setHandledRequestTxHash` marks the tx as handled — making the transfer irreversible and unrecoverable.
- **Net result:** Complete, permanent loss of the bridged KAIA amount for the user. No recovery path exists once the handle transaction is mined.

For ERC20 (non-mintBurn), `safeTransfer(address(0), value)` may revert depending on the token implementation, but for KAIA the loss is guaranteed. For ERC20 in mintBurn mode, `mint(address(0), value)` behavior is token-dependent.

---

### Likelihood Explanation

- **Trigger:** Any unprivileged user can call `requestKLAYTransfer(address(0), value, extraData)` directly. No special role is required.
- **Scenarios:** User error (copy-paste of zero address), a malicious UI injecting `address(0)`, or a smart contract integration that fails to validate the recipient before calling the bridge.
- **No existing guard:** Neither the Solidity contracts nor the Go relay layer (`handleRequestValueTransferEvent`) perform any zero-address check on `_to` at any point in the pipeline.

---

### Recommendation

Add a zero-address guard in `_requestKLAYTransfer`, `_requestERC20Transfer`, and `_requestERC721Transfer`:

```solidity
// In _requestKLAYTransfer:
require(_to != address(0), "BridgeTransfer: zero _to address");

// In _requestERC20Transfer:
require(_to != address(0), "BridgeTransfer: zero _to address");

// In _requestERC721Transfer:
require(_to != address(0), "BridgeTransfer: zero _to address");
```

Placing the check in the internal `_request*` functions ensures all entry points (`requestKLAYTransfer`, `requestERC20Transfer`, `requestERC721Transfer`, `onERC20Received`, `onERC721Received`) are protected with a single fix.

Optionally, add a corresponding guard in `handleKLAYTransfer` as a defense-in-depth measure:

```solidity
require(_to != address(0), "handleKLAYTransfer: zero _to address");
```

---

### Proof of Concept

1. Deploy the bridge on a simulated parent chain and child chain.
2. Fund the child bridge with KAIA (via `chargeWithoutEvent`).
3. On the parent chain, call:
   ```solidity
   bridge.requestKLAYTransfer{value: 1 ether}(address(0), 0.9 ether, "");
   // msg.value = 1 ether, _value = 0.9 ether → feeLimit = 0.1 ether
   // _requestKLAYTransfer(address(0), 0.1 ether, "") — no revert
   ```
4. The `RequestValueTransfer` event is emitted with `to = address(0)`.
5. The Go bridge operator (`handleRequestValueTransferEvent`) picks up the event and calls:
   ```go
   bi.bridge.HandleKLAYTransfer(auth, txHash, from, common.Address{}, valueOrTokenId, ...)
   ```
   on the child chain — no zero-address check.
6. `handleKLAYTransfer` executes:
   ```solidity
   (bool ok, ) = address(0).call.value(0.9 ether)("");
   require(ok, ...); // ok == true, no revert
   ```
7. 0.9 KAIA is permanently destroyed. The user's 1 KAIA on the parent chain is locked in the bridge. The bridge nonce is consumed. No recovery is possible.

func (bi *BridgeInfo) handleRequestValueTransferEvent(ev IRequestValueTransferEvent) error {
	var (
		tokenType                         = ev.GetTokenType()
		tokenAddr, from, to, contractAddr = ev.GetTokenAddress(), ev.GetFrom(), ev.GetTo(), ev.GetRaw().Address
		txHash                            = ev.GetRaw().TxHash
		valueOrTokenId                    = ev.GetValueOrTokenId()
		requestNonce, blkNumber           = ev.GetRequestNonce(), ev.GetRaw().BlockNumber
		extraData                         = ev.GetExtraData()
	)

	ctpartTokenAddr := bi.GetCounterPartToken(tokenAddr)
	// TODO-Kaia-Servicechain Add counterpart token address in requestValueTransferEvent
	if tokenType != KAIA && ctpartTokenAddr == (common.Address{}) {
		logger.Warn("Unregistered counter part token address.", "addr", ctpartTokenAddr.Hex())
		ctTokenAddr, err := bi.counterpartBridge.RegisteredTokens(nil, tokenAddr)
		if err != nil {
			return err
		}
		if ctTokenAddr == (common.Address{}) {
			return errors.New("can't get counterpart token from bridge")
		}
		if err := bi.RegisterToken(tokenAddr, ctTokenAddr); err != nil {
			return err
		}
		ctpartTokenAddr = ctTokenAddr
		logger.Info("Register counter part token address.", "addr", ctpartTokenAddr.Hex(), "cpAddr", ctTokenAddr.Hex())
	}

	bridgeAcc := bi.account

	bridgeAcc.Lock()
	defer bridgeAcc.UnLock()

	auth := bridgeAcc.GenerateTransactOpts()

	var handleTx *types.Transaction
	var err error

	switch tokenType {
	case KAIA:
		handleTx, err = bi.bridge.HandleKLAYTransfer(auth, txHash, from, to, valueOrTokenId, requestNonce, blkNumber, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[KAIA], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	case ERC20:
		handleTx, err = bi.bridge.HandleERC20Transfer(auth, txHash, from, to, ctpartTokenAddr, valueOrTokenId, requestNonce, blkNumber, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[ERC20], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	case ERC721:
		uri := GetURI(ev)
		handleTx, err = bi.bridge.HandleERC721Transfer(auth, txHash, from, to, ctpartTokenAddr, valueOrTokenId, requestNonce, blkNumber, uri, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[ERC721], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	default:
		logger.Error("Got Unknown Token Type ReceivedEvent", "bridge", contractAddr, "nonce", requestNonce, "from", from)
		return nil
	}
