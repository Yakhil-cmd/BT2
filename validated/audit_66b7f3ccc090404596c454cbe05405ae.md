### Title
Cross-organization Team identity confusion in `MembershipHandler#find_or_create_team!` allows an attacker-controlled GitHub org to write membership into an unrelated, already-authorized `Shipit::Team` - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`Team.find_or_create_by!(github_id: params.team.id)` looks up a `Team` solely by the numeric `github_id`, ignoring which organization actually signed the webhook. Because `WebhooksController#verify_signature` selects the signing org from the unauthenticated `organization.login` field of the same payload, an attacker who owns any org configured in a multi-org Shipit install can sign a `membership` webhook that references the `github_id` of a pre-existing team belonging to a different, privileged org, adding themselves as a member of that team.

### Finding Description
The broken binding: the code implicitly assumes `params.organization.login == team.organization` for every `Team` row touched by `find_or_create_team!`, but nothing enforces this equality.

Trace:
1. `WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-30) calls `Shipit.github(organization: repository_owner)`, and `repository_owner` (line 59-62) falls back to `params.dig('organization', 'login')` when there's no `repository` key in the payload. For a `membership` event there is no `repository` object, so `repository_owner` is exactly the attacker-supplied `organization.login`. The signature is verified against that org's own `webhook_secret` — which the attacker legitimately possesses since it's their own GitHub org. This passes. [1](#0-0) [2](#0-1) 

2. `MembershipHandler#process` calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id) do |team| ... end`. The block that sets `team.organization = params.organization.login` **only executes when a new record is created**; if a `Team` row with that `github_id` already exists (e.g., `critical-org`'s team, already a member of `Shipit.github_teams`), `find_or_create_by!` simply returns the existing record untouched, keeping `team.organization == 'critical-org'` while the request was authenticated by the attacker's own org. [3](#0-2) 

3. `process` then does `User.find_or_create_by_login!(params.member.login)` and `team.add_member(member)` for `action == 'added'`, adding the attacker's GitHub login to the existing critical team's memberships. [4](#0-3) 

4. `User#authorized?` checks `teams.where(id: Shipit.github_teams.map(&:id)).exists?`; if the mutated team is included in `Shipit.github_teams`, the attacker's account now returns `authorized? == true`, unlocking Shipit-wide privileged actions (deploys, rollbacks, etc., gated by `require_permission!`/`authorized?` elsewhere). [5](#0-4) 

None of `verify_signature`, `drop_unhandled_event`, or the `ExplicitParameters` schema (`params do ... end` in `MembershipHandler`) validate that `params.organization.login` matches the `organization` already stored on the `Team` identified by `github_id`. The schema only enforces types/presence, not cross-field consistency with a persisted record. [6](#0-5) 

### Impact Explanation
A user with zero legitimate relationship to `critical-org` can, using only their own GitHub org's genuine webhook secret, forge a `membership` webhook (`action: 'added'`) naming the `github_id` of an existing, higher-privilege `Team`. This adds the attacker as a member of that team's `Shipit::Team` record. If that team is part of `Shipit.github_teams`, the attacker's `User#authorized?` flips to `true`, granting access to gated deploy/rollback/merge actions across stacks that require authorization — an escalation into `Shipit.github_teams` authorization (High/Critical per the given severity rubric), repeatable at will and not scoped to any single repository/tenant, since Team membership is global infrastructure-wide state.

### Likelihood Explanation
Preconditions match a documented, supported configuration: multiple GitHub Apps/orgs (docs/setup.md "Using Multiple Github Applications"), one of which is attacker-owned with a real `webhook_secret`, and a pre-existing `Team` row for a privileged org whose numeric `github_id` the attacker can discover or guess/enumerate (team ids are often observable via public GitHub API/UI). The attacker only needs to know that `github_id` value and POST a single crafted, self-signed webhook to `/webhooks`. No Shipit session, API token, or privileged role is required. This is low-cost, deterministic, and repeatable.

### Recommendation
Scope the `Team` lookup to both the `github_id` and the authenticated `organization.login` derived from `verify_signature`, e.g. `Team.find_or_create_by!(github_id: params.team.id, organization: verified_organization)`, and reject/raise if a `Team` with that `github_id` exists under a different organization than the one that authenticated the request. More generally, `repository_owner`/the value used to select the signing `webhook_secret` should never be trusted as also authoritative for which org "owns" a resource being mutated — always cross-check the resource's stored organization against the org whose secret produced a valid signature.

### Proof of Concept
Minitest controller test (`test/controllers/webhooks_controller_test.rb` style, no live GitHub):
1. Create `orgA` config in `Shipit.github` with a known `webhook_secret_a`, and `critical-org` config with `webhook_secret_critical`.
2. Create `team = shipit_teams(:shopify_developers)` (or equivalent fixture) with `organization: 'critical-org'` and `github_id: 4242`; ensure it's included in `Shipit.github_teams` (stub `Shipit.github_teams` to include it).
3. Build a `membership` payload: `{ action: 'added', team: { id: 4242, name: 'x', slug: 'x', url: 'x' }, organization: { login: 'orgA' }, member: { login: 'attacker' } }`.
4. Sign the raw body with `webhook_secret_a` (orgA's real secret) and POST to `/webhooks` with `X-Github-Event: membership` and the correct `X-Hub-Signature`.
5. Assert response is `200`/`:ok` (i.e., signature verification passed for orgA).
6. Reload `team`; assert:
   - `team.organization == 'critical-org'` (unchanged) — left side of the binding.
   - The signing org was `'orgA'` — right side of the binding (`'orgA' != 'critical-org'`).
   - `team.members.map(&:login).include?('attacker')` is `true`.
   - `Shipit::User.find_by(login: 'attacker').authorized?` is `true`, and `Shipit.github_teams.map(&:handle).include?(team.handle)` is `true`.

These assertions demonstrate the binding `params.organization.login == team.organization` is violated while the attacker still successfully mutates and gains membership/authorization on `critical-org`'s team.
