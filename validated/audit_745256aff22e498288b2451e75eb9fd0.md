### Title
Capped asset issuance uniqueness is scoped per-address, allowing unlimited holders to each mint the full `cap` supply - (File: `validation.js`)

### Summary
An asset can be defined with a `cap` (fixed maximum supply) while `issued_by_definer_only` is `false` (a "publicly issuable, but capped" asset). The double-spend/uniqueness check that is supposed to prevent re-issuing a capped asset is scoped by `address` in this case, so unrelated addresses do not conflict with each other. As a result, any number of different addresses can each independently post a unit that issues the *entire* declared `cap` amount of the same asset, inflating total supply to `cap * N` instead of enforcing a single, global `cap`.

### Finding Description
In `validation.js`, when validating an `issue` input for an asset (`validatePaymentInputsAndOutputs`), the double-spend uniqueness key is built like this: [1](#0-0) 

For a capped asset (`objAsset.cap` truthy), `serial_number` must be `1` and is included in the uniqueness key, but the `address` filter is **only** added when `!objAsset.issued_by_definer_only`:
```
if (objAsset && !objAsset.issued_by_definer_only){
    doubleSpendWhere += " AND address=?";
    doubleSpendVars.push(address);
}
```
This mirrors the underlying DB unique constraint, which is also scoped by address: [2](#0-1) 

The asset-definition validator (`validateAssetDefinition`) only restricts the `issued_by_definer_only=true` combination (forbidding private/fixed-denomination assets in that case); it never forbids defining `cap` together with `issued_by_definer_only=false`: [3](#0-2) 

Consequently, for a "public capped asset" (cap set, `issued_by_definer_only=false`), the issue-input check `serial_number !== 1` combined with a per-address uniqueness key means: address A can post an `issue` input with `serial_number=1, amount=cap`; separately, address B can also post an `issue` input with `serial_number=1, amount=cap`. Neither conflicts with the other in the double-spend check because the query is filtered `AND address=?` for each poster individually: [4](#0-3) 

The only place that treats "capped asset" issuance as a single global event (checking `SELECT 1 FROM inputs WHERE type='issue' AND asset=?` with no `address` filter) is the AA composer's own issuance helper, which is merely a convenience for *the AA itself* deciding whether to issue — it is not a protocol-level invariant enforced on arbitrary externally-authored units: [5](#0-4) 

So while an AA that defines its own capped asset will refuse to issue it twice through its own logic, any third party can independently post a plain `payment` unit (unrelated to the AA) with an `issue` input for that same asset ID, as long as they are one of the unit authors and satisfy `serial_number=1, amount=cap`, which is exactly what the protocol-level validator permits for non-definer-restricted capped assets.

### Impact Explanation
This breaks the fundamental guarantee of `cap`: that an asset's total supply is fixed. Any AA or user pattern that defines a capped, non-`issued_by_definer_only` asset (e.g., a fundraising/market-maker share token where anyone is expected to be able to bootstrap or issue shares) can have its supply inflated arbitrarily by unrelated addresses each individually issuing the full cap amount to themselves, at zero cost beyond a standard unit fee. This is a direct supply-inflation vulnerability: downstream AAs, exchanges, or holders that rely on `cap` as an economic invariant (scarcity, redemption ratios, voting weight, etc.) would be defrauded, and legitimate holders' shares would be diluted without any corresponding payment into the system.

### Likelihood Explanation
Likelihood is high for any asset defined this way, because nothing in `validateAssetDefinition` prevents `cap` + `issued_by_definer_only:false`, and exploiting it requires only posting a normal single-authored payment unit with a crafted `issue` input — no special privilege, front-running race, or AA cooperation is required (unlike the original report, here there isn't even a need to race; every distinct address can mint independently at any time).

### Recommendation
Scope the capped-asset uniqueness/double-spend check globally (drop the `address` filter for capped assets), or forbid defining `cap` on assets where `issued_by_definer_only` is `false` in `validateAssetDefinition`, so that a `cap` can only ever be issued once, by one address, for the lifetime of the asset.

### Proof of Concept
1. Post an asset-definition unit for asset `X` with `cap: 1000000, issued_by_definer_only: false, is_private: false` (via `app: 'asset'` message, standalone or inside an AA response).
2. Address `A` posts a payment unit with `payload.asset = X`, `inputs: [{type:'issue', serial_number:1, amount:1000000}]`, `outputs:[{address:A, amount:1000000}]`. This validates and is accepted (`validation.js` lines ~2311-2353, doubleSpendWhere includes `address=A`).
3. Address `B` (unrelated) posts another payment unit with the same `payload.asset = X`, `inputs:[{type:'issue', serial_number:1, amount:1000000}]`, `outputs:[{address:B, amount:1000000}]`. Because `doubleSpendWhere` for this asset/definer combination includes `AND address=?` bound to `B`, it does not collide with A's prior issue row, and the unit validates successfully.
4. Total circulating supply of asset `X` is now `2,000,000`, double the declared `cap`, and can be repeated by any number of further addresses `C, D, …` indefinitely.
