### Title
Cross-repository status forgery via `StatusHandler#process` allows unprivileged sabotage of a victim's green commit - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits by `Commit.where(sha: params.sha)` alone, with no check that the commit's stack/repository matches the webhook payload's `repository.full_name`. An attacker who owns any repository can send a `status` webhook (signed with their own, legitimately obtained webhook secret for their own org) referencing a SHA that happens to collide with a commit tracked by a victim's Shipit stack, flipping that victim commit from `success` to `error`/`failure`.

### Finding Description
The broken binding: `payload['repository']['full_name']` (the repository the signature/`verify_signature` check authenticates) MUST equal `commit.stack.repository.full_name` (the repository whose commit status is mutated), but the code never enforces this equality.

Path: `WebhooksController#create` (`app/controllers/shipit/webhooks_controller.rb:10-15`) parses JSON and dispatches to `Shipit::Webhooks.for_event(event)`, verifying only that the payload's `repository.owner.login` matches an org Shipit knows (`verify_signature`, lines 24-49) — this authenticates "a request from org X for org X's repo," not "this SHA belongs to org X's repo."

`StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24):
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
Unlike other handlers, `StatusHandler` never calls the base `Handler#stacks` helper (`app/models/shipit/webhooks/handlers/handler.rb:32-34`), which is the only place repository scoping (`Repository.from_github_repo_name(repository_name)`) exists in this class hierarchy. It queries `Commit` globally by `sha` with zero repository/stack filter.

`Commit#create_status_from_github!` → `add_status` → `Status#replicate_from_github!` persists a new `Status` row tied to `commit.stack_id` (the victim stack), and `Status` has `after_create :enable_ci_on_stack` and `after_commit :schedule_continuous_delivery` (app/models/shipit/status.rb:18-19). A `state: 'error'`/`failure'` status makes `Commit#success?`/`deployable?` false (delegated to `status`, app/models/shipit/commit.rb), which stops `stack.trigger_continuous_delivery` and makes `MergeRequest#any_status_checks_failed?` true, causing `MergeRequest#reject!('ci_failing')` (referenced in app/models/shipit/merge_request.rb) on an otherwise mergeable victim PR.

Exploit: attacker registers/owns a webhook-enabled repository `attacker/evil`, whose signature Shipit will happily verify via `Shipit.github(organization: 'attacker-org')`. Attacker crafts a `status` event payload with `repository.full_name = 'attacker/evil'` (or owner matching a Shipit-known org they control) and `sha` equal to a real victim commit SHA (SHA collision across repos is exactly the identifier space `Commit.where(sha:)` searches — Shipit commit SHAs are global 40-hex strings and it is fully possible for a victim's tracked stack and attacker's repo to reference the same commit object, e.g. forked repos, shared submodules/vendored branches, or simply an attacker guessing/observing a public victim SHA and including it in a forged status for their own repo name). `verify_signature` passes because it only checks the org named in the payload, never that the SHA is scoped to that org's repository. `StatusHandler#process` then finds the victim's `Commit` row (same SHA, different stack) and writes an `error`/`failure` `Status` under the victim's `stack_id`.

Existing guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema) validate webhook authenticity and payload shape, not sha-to-repository ownership; they do not block this because the check operates one layer above (org-level signature) while the mutation operates on a globally-scoped `sha` lookup.

### Impact Explanation
A forged `status` webhook lets any attacker who controls a Shipit-known GitHub repository/org mark an arbitrary victim commit (identified only by its SHA) as `error`/`failure`, in a stack they do not own. This blocks `continuous_deployment` and forces `MergeRequest#reject!('ci_failing')` on a legitimate merge request — an unauthorized, cross-tenant denial of a victim's deploy/merge. This matches "a payload for one repository mutating another's stack/commit" — Critical.

### Likelihood Explanation
Requires: (1) attacker owns/controls at least one repository+org already onboarded to Shipit (so `verify_signature` succeeds using their own legitimate webhook secret — no secret theft needed), and (2) a SHA collision/reuse between the attacker's named repository and the victim's tracked commit. Note: unlike the "false success" companion finding, precise reproducibility depends on the attacker being able to reference a real victim SHA in their own payload — this is straightforward when repos are forked, when commit SHAs are publicly visible (GitHub SHAs are not secret), or when the attacker's own onboarded repo happens to share commits with the victim (fork/mirror scenarios), so it is repeatable and low-cost per request once the attacker has any onboarded repo.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to the requesting payload's repository, mirroring `Handler#stacks`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This enforces `payload.repository.full_name == commit.stack.repository.full_name` before any status mutation.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb
test "forged status for unrelated repository cannot flip a victim's green commit to failing" do
  victim_stack = shipit_stacks(:shipit) # tracks 'shopify/shipit-engine'
  victim_commit = shipit_commits(:first)
  victim_commit.statuses.create!(stack: victim_stack, state: 'success', context: 'ci')
  assert_predicate victim_commit.reload, :success?

  forged_payload = {
    'sha' => victim_commit.sha,
    'state' => 'error',
    'context' => 'ci',
    'repository' => { 'full_name' => 'attacker/evil', 'owner' => { 'login' => 'attacker-org' } }
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(forged_payload)

  refute victim_commit.reload.success?, "attacker-controlled repo payload must not flip victim's commit status"
end
```
Assert both sides of the binding: before the call, `payload['repository']['full_name'] != victim_commit.stack.repository.full_name`; after a correct fix, the status write must not occur (test should fail today against unpatched `StatusHandler#process` and pass once the repository-scoped lookup is added).     def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',

        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"

    rescue Shipit::GithubOrganizationUnknown => e

      ].join(' '))
