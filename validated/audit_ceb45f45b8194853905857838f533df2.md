### Title
Supply-cap sandwich can repeatedly block deposits - (File: `contracts/controller/src/spoke_usage.rs`)

### Summary
An unprivileged attacker can temporarily fill a spoke asset’s configured `supply_cap`, causing competing `supply` calls to revert with `SpokeSupplyCapReached`, then immediately withdraw and repeat the attack. [1](#0-0) 

### Finding Description
`Controller::supply` authenticates the caller, transfers the measured tokens to the pool, calls `LiquidityPool::supply`, and then merges the returned scaled position. [2](#0-1) 

Merging the supply leg invokes `apply_leg_usage`, which records the scaled supply increase through `Context::apply_spoke_entry`. [3](#0-2) [4](#0-3) 

`SpokeUsageContext::apply_entry` converts the configured asset-unit cap into scaled shares at the current supply index, adds the new scaled position, and rejects the transaction when the total exceeds the cap. [5](#0-4) [1](#0-0) 

An attacker can therefore submit a large `supply` first, bringing spoke usage up to the cap; a victim’s later supply transaction reverts when its merge step pushes usage above that cap. [6](#0-5) 

There is no deposit cooldown or minimum holding period: the attacker’s debt-free account can call `withdraw`, burn the newly minted shares, receive the underlying, and decrement spoke usage. [7](#0-6) [8](#0-7) 

### Impact Explanation
While the attacker holds the cap allocation, every competing deposit that would exceed the remaining cap reverts, temporarily denying normal access to `Controller::supply`. [6](#0-5) 

Because Soroban executes atomically, the victim’s failed token transfer and pool mint roll back rather than leaving funds stuck inside the pool. [9](#0-8) 

The attacker can withdraw after the victim transaction fails and reuse the same balance against later deposits, making the denial repeatable for as long as the attacker is willing to reserve the required capital. [7](#0-6) 

### Likelihood Explanation
The attack requires a listed collateral asset with a finite `supply_cap` close enough to the configured limit that the attacker can acquire and supply the remaining amount. [10](#0-9) [1](#0-0) 

The attacker only needs ordinary `supply` and `withdraw` entrypoints and ownership or delegate control of the attack account. [11](#0-10) 

A debt-free attacker skips the post-withdrawal collateral, health-factor, and minimum-collateral checks, so the temporary supply position can be closed immediately when liquidity permits. [12](#0-11) [13](#0-12) 

The attack is not necessarily free: it requires controlling enough of the capped asset to consume the available cap, and the withdrawal leg can still fail if the market lacks cash or violates its utilization guard. [14](#0-13) 

### Recommendation
Add a minimum holding period, cooldown ledger, or withdrawal delay for newly minted supply positions before they can be withdrawn, preventing the same balance from repeatedly occupying the supply cap within consecutive transaction ordering slots. [15](#0-14) 

Alternatively, reserve cap consumption before ordering-sensitive transactions or charge an economically meaningful temporary occupancy cost so griefing deposits cannot be repeated at negligible cost. [5](#0-4) 

### Proof of Concept
1. Governance configures a spoke asset with `is_collateralizable = true` and finite `supply_cap = C`. [10](#0-9) 
2. Existing spoke supply usage is `U`; the attacker owns at least `C - U` units of the asset. [5](#0-4) 
3. The attacker calls `Controller::supply(attacker, 0, spoke_id, [(hub_asset, C - U)])`, creating an account and bringing scaled supply usage to the cap. [16](#0-15) [6](#0-5) 
4. A victim calls `Controller::supply(victim, victim_account, spoke_id, [(hub_asset, amount)])` with any positive amount. [16](#0-15) 
5. The victim’s transaction transfers and mints optimistically, but `apply_spoke_entry` computes `next_scaled > cap_scaled` and reverts the entire transaction with `SpokeSupplyCapReached`. [17](#0-16) [6](#0-5) 
6. After the victim’s transaction fails, the attacker calls `Controller::withdraw(attacker, attack_account, [(hub_asset, 0)], None)`, withdrawing the full temporary position and lowering spoke usage. [18](#0-17) [19](#0-18) 
7. The attacker repeats steps 3–6 whenever another victim attempts to deposit near the cap. [20](#0-19)

    /// Buffers a scaled decrease. Zero deltas and missing rows are no-ops;
    /// overflow or negative resulting usage fails.
    pub(crate) fn apply_exit(
        &mut self,
        side: UsageSide,
        hub_asset: &HubAssetKey,
        delta_scaled: Ray,
    ) {
        if delta_scaled == Ray::ZERO {
            return;
        }
        let Some(mut usage) = self.load_usage_row(hub_asset) else {
            return;
        };
        let next = side
            .scaled(&usage)
            .checked_sub(delta_scaled.raw())
            .unwrap_or_else(|| panic_with_error!(&self.env, GenericError::MathOverflow));

        assert_with_error!(&self.env, next >= 0, GenericError::InternalError);
        side.set_scaled(&mut usage, next);
        self.usage.set(hub_asset.clone(), usage);

/// Checks supply entry gates and credits measured pool receipts.
pub(crate) fn process_deposit(
    env: &Env,
    caller: &Address,
    account: &mut Account,
    aggregated: &AggregatedPayments,
    cache: &mut Context,
) {
    validate_position_entry_gates(
        env,
        account,
        aggregated,
        cache,
        AccountPositionType::Deposit,
    );
    let pool_addr = cache.cached_pool_address();
    let mut entries: Vec<PoolSupplyEntry> = Vec::new(env);
    for (hub_asset, amount_in) in aggregated.iter() {
        let asset_config: AssetConfig = cache.require_spoke_asset(account.spoke_id, &hub_asset);
        let received = payments::transfer_amount_measured(
            env,
            &hub_asset.asset,
            caller,
            &pool_addr,
            amount_in,
            GenericError::AmountMustBePositive,
        );
        let position = account.get_or_create_supply_position(&hub_asset, &asset_config);
        entries.push_back(PoolSupplyEntry {
            action: make_pool_action(&position, received, hub_asset.clone()),
        });
    }

    let results = pool_supply_call(env, &pool_addr, &entries);
    for_each_leg(env, &entries, &results, |entry, result| {
        merge_supply_leg(env, account, &entry.action, &result, cache);
    });
}
