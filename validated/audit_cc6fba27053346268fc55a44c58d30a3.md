### Title
Pull request label names bypass environment variable allowlisting and inject arbitrary env vars (e.g. `PERL5OPT`) into `tasks.<name>.steps` processes - (File: `app/models/shipit/review_stack.rb`, `lib/shipit/task_commands.rb`)

### Summary
`ReviewStack#env` merges every pull-request label name (uppercased) into the stack's environment hash with no allowlist, and `LabelCapturingHandler` persists label names verbatim from unauthenticated webhook payloads. `TaskCommands#env` merges `@stack.env` directly into the environment used to spawn `tasks.<name>.steps` commands, without ever routing it through `EnvironmentVariables#permit`/`TaskDefinition#filter_envs`, so a fork PR's label becomes an arbitrary env var (e.g. `PERL5OPT`) handed straight to `Command#start` → `PTY.spawn`.

### Finding Description
The broken binding: `TaskCommands#env` should equal `Stack#env.merge(task_definition.filter_envs(user_supplied_env))` (i.e., only allowlisted variables reach the spawned process), but it actually equals `super.merge(@stack.env).merge(...).merge(deploy_spec.machine_env).merge(@task.env)` where `@stack.env` for a `ReviewStack` is unfiltered.

Code path:
- `ReviewStack#env` [1](#0-0)  merges `pull_request.labels.each_with_object({}) { |n,h| h[n.upcase] = "true" } ` into the base stack env with no key allowlist.
- `LabelCapturingHandler#capture_labels` persists `params.pull_request.labels.map(&:name)` directly from the webhook body [2](#0-1) , and label names accept arbitrary strings including emoji, confirmed by test `"accepts extended unicode characters (emoji) in label names"` [3](#0-2) , i.e. no format restriction rejects a label literally named `perl5opt`.
- `TaskCommands#env` merges `@stack.env` unfiltered, then builds `perform`/`install_dependencies` commands: `Command.new(command_line, env:, chdir: steps_directory)` [4](#0-3) . This is the code path for the `tasks.<name>.steps` phase.
- `EnvironmentVariables#permit`/`TaskDefinition#filter_envs` exist and are exercised only against the trigger's user-supplied `params[:env]` at `Api::TasksController#trigger` (`stack.trigger_task(params[:task_name], current_user, env: params.env)`) [5](#0-4) , and `TaskDefinition#filter_envs` [6](#0-5)  — this allowlist is never applied to `@stack.env`, so the label-derived key bypasses it entirely.
- `Command#unbundled_env` merges `BASE_ENV` with `PATH` and then `@env.stringify_keys` last, so caller-supplied env fully overrides anything in `BASE_ENV`, and the result is passed straight to `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` [7](#0-6) .

Exploit flow: an unprivileged fork-PR author creates a PR against a repository with `provisioning_behavior = allow_with_label`, applies a label named `perl5opt` (case-insensitive, becomes `PERL5OPT` after `.upcase`) via the GitHub UI, and the `pull_request` `labeled` webhook fires `LabelCapturingHandler`, persisting the label on the `PullRequest` record for the active `ReviewStack`. Any subsequent `tasks.<name>.steps` execution (custom task, restart task, etc., defined in the repo's own `shipit.yml`, which the fork PR also controls under `allow_with_label`) will include `PERL5OPT=true` in its environment. If the task's steps invoke `perl` (directly or transitively via a build tool), `PERL5OPT` is honoured at Perl startup and can inject `-M`/`-d` module-loading or debugger options, achieving code execution on the deploy host in the context of the Shipit worker.

Existing guards do not catch this: `EnvironmentVariables#permit` only guards explicit user-provided `env` params on deploy/rollback/task triggers, not `stack.env`; there is no repository/label-name format validator restricting label content; and `LabeledHandler`/`LabelCapturingHandler` only gate stack provisioning/archival state, not the content of labels captured into `env`.

### Impact Explanation
An unprivileged fork contributor can inject arbitrary environment variables into every command executed for that review stack's tasks (and deploys, since `DeployCommands#env` behaves the same way per `test/lib/shipit/deploy_commands_test.rb`), including security-sensitive interpreter env vars like `PERL5OPT`, `RUBYOPT`, `PYTHONSTARTUP`, `NODE_OPTIONS`, etc. Combined with a `shipit.yml` under the attacker's control (since `allow_with_label` review stacks read spec from the fork), this can escalate to remote code execution on the Shipit deploy host, matching the Critical RCE class. The blast radius is scoped to the repository configured with `allow_with_label`, but is fully repeatable for any PR against that repository.

### Likelihood Explanation
Requires the target repository to have `review_stacks_enabled` with `provisioning_behavior = allow_with_label` (or `prevent_with_label`, since both `ReviewStack#env` paths merge labels unfiltered) — a documented, supported configuration for open review-stack workflows. The attacker needs only fork-PR + label privileges (default for any GitHub contributor able to open PRs, and label application may itself already be gated by "labeled" permissions on GitHub — but the underlying engine flaw is independent of GitHub's label ACLs since the question's threat model treats "any user who can label their own PR" as in-scope). Attacker cost is minimal: label the PR and wait for the next task run using an interpreter honouring the injected env var.

### Recommendation
Do not merge raw, attacker-controlled pull request label names into `ENV`-facing structures without an explicit allowlist. Route `ReviewStack#env`'s label-derived keys (and `Stack#env` generally when merged in `TaskCommands#env`/`DeployCommands#env`) through the same `EnvironmentVariables#permit` allowlist used for user-supplied env, or apply a fixed prefix/namespace (e.g., `LABEL_<name>`) and strip/deny any key colliding with known sensitive interpreter/env variable names (`PERL5OPT`, `RUBYOPT`, `PYTHONSTARTUP`, `LD_PRELOAD`, `NODE_OPTIONS`, etc.). Alternatively, block-list environment variable name collisions with known interpreter-behavior-altering variables before merging into `Command#env`.

### Proof of Concept
minitest plan (`test/lib/shipit/task_commands_test.rb` or `test/models/shipit/review_stack_test.rb`):
```ruby
test "#env allows a PR label to inject PERL5OPT into tasks.<name>.steps env" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["perl5opt"]
  task = shipit_tasks(:shipit_restart)
  task.stack = stack

  env = Shipit::TaskCommands.new(task).env

  # Broken binding: env should NOT contain fork-controllable interpreter keys
  assert_equal "true", env["PERL5OPT"]   # demonstrates the injection reaches TaskCommands#env

  command = Shipit::TaskCommands.new(task).perform.first
  assert_equal "true", command.env["PERL5OPT"]
  assert_equal "true", command.unbundled_env["PERL5OPT"]  # confirms it reaches the env passed to PTY.spawn
end
```
This demonstrates that `PERL5OPT`, sourced purely from an unprivileged fork PR's label name, reaches the environment of the `tasks.<name>.steps` `Command#start`/`PTY.spawn` invocation with no allowlist filtering.
