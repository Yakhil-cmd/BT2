### Title
Malicious swap route injects unauthorized user token transfers - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary
A caller-supplied opaque `swap` payload can place attacker-controlled route code beneath the caller’s `swap_collateral`, `swap_debt`, `multiply`, or `repay_debt_with_collateral` authorization. If simulation returns—and the caller signs—an authorization tree containing an unexpected token transfer, route code can move unrelated wallet assets while the controller’s measured input/output and final-risk checks still pass.

### Finding Description
`swap_collateral` authenticates `caller` and authorizes access to the specified account, then forwards the caller-controlled `swap` payload into `withdraw_and_swap_from_supply`. [1](#0-0) [2](#0-1) 

`withdraw_and_swap_from_supply` passes that payload to `swap_tokens_or_passthrough`, which calls `swap_tokens` whenever the input and output token addresses differ. [3](#0-2) [4](#0-3) 

`swap_tokens` correctly scopes the controller’s own authority to one exact `token_in.transfer(controller, router, amount_in)` invocation, but then forwards the opaque payload unchanged to `router.execute_strategy`. [5](#0-4) [6](#0-5) 

The swap-aggregator ABI accepts that payload as raw `swap_xdr`; the controller neither decodes it nor constrains which pool, venue, token, or other contract addresses it names. [7](#0-6) 

Because `caller.require_auth()` is performed at the strategy root, a token `transfer` initiated by route-selected code and requiring the caller’s authorization is represented as a sub-invocation beneath that strategy authorization. [8](#0-7) 

The post-router checks measure only the controller’s input spend, input refund, and output receipt; they do not detect a transfer from the caller’s wallet to an attacker-selected recipient. [9](#0-8) 

### Impact Explanation
A malicious route can cause theft of arbitrary token balances held by the caller, not merely the collateral or debt amount being routed. The attacker can make the strategy produce a valid positive output and preserve the account’s final risk condition, so the caller’s unrelated wallet-token loss does not prevent transaction success. This is theft of user funds and is appropriately classified as Medium severity because it requires the victim to sign the poisoned authorization tree disclosed by simulation.

### Likelihood Explanation
Exploitation requires a malicious route payload, typically supplied by a compromised or deceptive quote source, and a user who signs the resulting authorization tree without rejecting the extra token-transfer child. An honest client can detect the injected child during simulation, which limits likelihood; however, the contract interface itself provides no structural route allowlist or payload validation to prevent the malicious auth request from being generated.

### Recommendation
Replace or supplement the opaque route payload with a structured route manifest whose venue and token addresses are validated against an allowlist before external route code is invoked. Clients should additionally decode the route and reject an authorization tree containing unexpected caller-authorization children; for `swap_collateral`, `swap_debt`, and `repay_debt_with_collateral`, an honest route should not require any child transfer from the caller. The controller’s measured-output checks should remain, but they must not be treated as a bound on damage caused by route-selected code.

### Proof of Concept
1. Alice owns an account with listed USDC collateral and separately holds an unlisted `WALLET_TOKEN`.
2. An attacker prepares `swap` bytes that route the USDC-to-ETH conversion through an attacker-controlled hop contract.
3. Alice calls `Controller::swap_collateral(alice, account_id, usdc_hub_asset, amount, eth_hub_asset, swap)`. [10](#0-9) 
4. The controller calls `alice.require_auth()`, verifies account ownership or delegation, withdraws USDC to itself, authorizes the exact controller-to-router USDC transfer, and invokes `execute_strategy(controller, amount, swap)`. [11](#0-10) [12](#0-11) 
5. Route execution reaches the attacker’s hop contract, which invokes `WALLET_TOKEN.transfer(alice, attacker, alice_balance)`.
6. Simulation records that transfer as a child of Alice’s `swap_collateral` authorization; if Alice signs that returned tree, the unrelated wallet tokens move to the attacker.
7. The router returns enough ETH for `received > 0`, the controller deposits it as collateral, and the final account-risk check can still succeed because neither check inspects the stolen `WALLET_TOKEN` transfer. [13](#0-12) [14](#0-13)
