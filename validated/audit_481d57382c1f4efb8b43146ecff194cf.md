### Title
Cross-organization team membership mutation via unverified `team.id` in `MembershipHandler` - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the verifying `webhook_secret` using `repository_owner`, which falls back to `params.dig('organization','login')` when the `repository` key is absent from the payload [1](#0-0) . `membership` events naturally omit `repository`, so an attacker who owns a legitimate GitHub organization (and thus its configured `webhook_secret`) can pass signature verification while supplying an arbitrary `team.id` that references a `Team` row belonging to a different organization. `MembershipHandler#process` then calls `team.add_member(member)` without ever checking that `team.organization` matches the org that authenticated the request [2](#0-1) .

### Finding Description
The intended binding is: **organization whose `webhook_secret` verified the request == organization whose `Team`/`Membership` rows are mutated**, i.e. `repository_owner (used in Shipit.github(organization: repository_owner))` should equal `team.organization` for the `Team` record being mutated.

Trace:
1. `verify_signature` computes `repository_owner` from `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0) . For a `membership` event, GitHub's payload has no `repository` key, so this always falls back to `organization.login`, a value fully controlled by whoever crafts the payload.
2. `Shipit.github(organization: repository_owner)` looks up the webhook secret configured for that literal org name and verifies `X-Hub-Signature` against it [3](#0-2) . If the attacker owns `attacker-org` and has configured (or legitimately has) a webhook there, they can compute a valid HMAC for any payload body using their own secret, as long as `organization.login == 'attacker-org'`.
3. Once signature verification passes, `Shipit::Webhooks.for_event('membership')` dispatches to `MembershipHandler#process` with the raw parsed params [4](#0-3) .
4. `MembershipHandler#process` calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id) { ... team.organization = params.organization.login ... }` [5](#0-4) . The `organization` assignment inside the block only runs when a **new** record is being created (ActiveRecord's `find_or_create_by!` block semantics). If a `Team` row with that `github_id` already exists — e.g., a legitimate team belonging to a victim organization, `victim-org` — the existing record is returned unchanged, and `team.organization` remains `victim-org`.
5. `process` then executes `team.add_member(member)` for `action == 'added'`, which calls `members.append(member) unless members.include?(member)` on `Team#add_member` [6](#0-5) . There is no check anywhere that `team.organization` equals `repository_owner`/`params.organization.login` used for signature verification.
6. Because `User#authorized?` grants access when `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [7](#0-6) , and `Shipit.github_teams` is built from `github.oauth_teams.map { |t| Team.find_or_create_by_handle(t) }` [8](#0-7) , if the targeted foreign `Team` happens to be one of the configured `github_teams` (the authorization-gating teams for the app), adding an arbitrary `member` row to it grants that user's Shipit account elevated authorization — without that org ever emitting a real `membership` event.

Existing guards do not close this gap: `drop_unhandled_event` only checks whether a handler is registered for the event type [9](#0-8) ; `verify_signature` only checks the HMAC against whichever org happens to be named in the payload, and explicitly logs but does not enforce any relationship between `repository_owner` and the `team`/`organization` fields used downstream; the `ExplicitParameters` schema in `MembershipHandler` requires `organization.login` and `team.id` to be present and well-typed, but never cross-validates them against each other or against the authenticated org [10](#0-9) .

### Impact Explanation
An attacker who legitimately controls a GitHub organization with its own configured `webhook_secret` in this Shipit instance can, via `POST /webhooks` with `X-Github-Event: membership`, add an arbitrary `User` (including a user account they control) to any pre-existing `Team` record (`Team#add_member`) as long as they know or guess that team's numeric GitHub `github_id`, regardless of which organization actually owns that team. This is a cross-tenant record mutation: an event authenticated for `attacker-org` mutates `Team`/`Membership` rows tied to `victim-org`. If the targeted team is part of `Shipit.github_teams`, this becomes an authorization escalation, since `User#authorized?` bases access on team membership [7](#0-6) . This matches "escalation into `Shipit.github_teams` authorization" (High) and, if the targeted team drives deploy/merge gating for other tenants' stacks, edges toward cross-tenant mutation (Critical-adjacent). The action is repeatable for any known `github_id` of a `Team` row already present in the database.

### Likelihood Explanation
Preconditions: the attacker must control a GitHub organization that has a webhook configured against this Shipit instance with a known-to-them `webhook_secret` (a realistic, low-cost precondition per the stated attacker model — "any org attacker can genuinely emit events for"). The attacker also needs to know (or brute-force/guess) the target `Team`'s GitHub numeric ID, which is knowable if the victim team is public or previously observed. No Shipit session, API token, or GitHub App secret is required. Given HMAC signing only requires the attacker's own secret, and the vulnerable code path is unconditionally reached on every `membership` webhook, the exploit is straightforward and repeatable.

### Recommendation
In `MembershipHandler#find_or_create_team!` (and generally in webhook handlers reachable via the `organization` fallback), enforce that `team.organization == params.organization.login` when the `Team` already exists, rejecting/raising if they diverge instead of silently reusing the existing record. Additionally, `WebhooksController#repository_owner`'s organization fallback should be constrained to only be trusted for handlers whose payload's `organization.login` is independently cross-checked against the resource being mutated (e.g., verify `team.organization` matches the authenticated org before any `add_member`/`delete` mutation).

### Proof of Concept
Add to `test/models/shipit/webhooks/handlers/membership_handler_test.rb` (or equivalent):
1. Create `victim_team = Team.create!(github_id: 555, organization: 'victim-org', slug: 'core', name: 'Core')`.
2. Build params: `{ 'action' => 'added', 'team' => { 'id' => 555, 'name' => 'Core', 'slug' => 'core', 'url' => 'https://...' }, 'organization' => { 'login' => 'attacker-org' }, 'member' => { 'login' => 'attacker-user' } }`.
3. Assert, before calling the handler: `victim_team.organization == 'victim-org'` and the params' `organization.login == 'attacker-org'` (the two sides of the binding do not match).
4. Call `Shipit::Webhooks::Handlers::MembershipHandler.new(params).process` (bypassing controller-level signature verification, which is orthogonal — the point is that `verify_signature` for `attacker-org` would have succeeded and dispatched to this same `process` call).
5. Reload `victim_team` and assert `victim_team.members.exists?(login: 'attacker-user')` is `true`, and assert `victim_team.reload.organization` is still `'victim-org'` (unchanged) — proving that a request authenticated as `attacker-org` mutated `victim-org`'s team membership, i.e., the equality `repository_owner (attacker-org) == team.organization (victim-org)` was never enforced despite successful signature verification.
