### Title
Cross-stack status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits to attach a GitHub status to purely by `sha`, with no check that the webhook's `repository` matches the `stack`/repository that owns the matched `Commit` row. Since `sha` is only unique per `(stack_id, sha)` and not globally, a validly-signed status webhook for a commit sha shared by two different Shipit-tracked repositories (e.g. a fork sharing history with the upstream repo) will write a `Status` onto the *other* stack's `Commit`, which `Commit#deployable?` and `Stack#next_commit_to_deploy` then treat as verified by that stack's own CI.

### Finding Description
The broken binding is: `Commit(sha=X, stack_id=A).status.success? == (CI configured on stack A's repository reported success for X)`. In reality it is `Commit(sha=X, stack_id=A).status.success? == (any GitHub-signed status webhook delivered to Shipit for sha X from ANY repository covered by any configured GitHub App/org, success or not)`.

Path:
1. `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) verifies the HMAC using `Shipit.github(organization: repository_owner)`, i.e. keyed only by the **organization/App installation** the payload's `repository.owner.login` maps to, not by the specific repository or `Stack`.
2. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
This is a bare `sha` lookup with no `stack_id`/repository filter. `Commit#create_status_from_github!` (`app/models/shipit/commit.rb:165-169`) then calls `statuses.replicate_from_github!(stack_id, github_status)`, writing the `Status` with `commit.stack_id` — the *victim* stack's id — regardless of which repository actually emitted the webhook.
3. `commits` table is only indexed/scoped uniquely on `(stack_id, sha)` (`db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`), confirming the same `sha` can legitimately exist under multiple `Stack`s (e.g. a fork tracked as its own stack, or a repository split/mirrored across two tracked stacks sharing history).
4. `Commit#deployable?` (`app/models/shipit/commit.rb:227-229`) and `Stack#deployable_commits`/`#next_commit_to_deploy` (`app/models/shipit/stack.rb:235-243,645-647`) only check `success? && !blocked?` on the `Status` records attached to that `Commit` row — they have no way to tell the status originated from an unrelated repository's CI.

Existing guards fail because `verify_signature` only proves the request came from GitHub for *some* repository in a known org/App installation — it says nothing about which `Stack`'s commits the payload is entitled to mutate. The application-level lookup in `StatusHandler` is the layer that should have enforced that binding (e.g. via `params.repository.full_name` -> matching `stack.repository`) and does not.

Exploit flow: attacker controls (or has push/CI access to) a repository that is tracked as its own `Stack` in the same Shipit instance and shares commit history with the victim's repository (e.g. it is a fork, or both are mirrors of a common upstream). Attacker pushes/labels a commit whose sha equals an old, undeployed commit sha already present in the victim stack, and gets a real GitHub `status` event (`state: success`) delivered for that sha (their own CI, or simply because that shared commit already has upstream CI results relayed by GitHub to every app installation watching either repo). The webhook is genuinely GitHub-signed for the attacker's own repo/org, passes `verify_signature`, and `StatusHandler` writes a `success` `Status` onto the victim stack's `Commit` row for that sha. `Commit#deployable?` on the victim's commit now returns true, and `Stack#next_commit_to_deploy` (bounded by `maximum_commits_per_deploy`) can select and deploy that specific historical commit via `trigger_continuous_delivery` — a deploy of attacker-chosen code that was never validated by the victim stack's own CI pipeline.

### Impact Explanation
An unauthorized write is made to a `Status`/`Commit` record belonging to a repository/stack that did not itself authenticate the payload, and — under `continuous_deployment`/`maximum_commits_per_deploy` — this can cause `Stack#trigger_continuous_delivery` to deploy a specific historical commit chosen by the attacker without it having passed the victim stack's real CI. This matches "Critical - a payload for one repository mutating another's stack/commit" and "unauthorized deploy" in the impact taxonomy. Blast radius is limited to stacks that (a) share commit history (same sha) with a repository the attacker can influence and (b) are hosted on the same Shipit instance/App installation(s); it is not a wholesale cross-tenant break for arbitrary unrelated shas (git sha collision across unrelated content is not feasible), but for forks/mirrors deliberately tracked as separate stacks it is fully repeatable per matching sha.

### Likelihood Explanation
Requires: two Shipit `Stack`s tracking repositories that share git history (common in fork-based or mirrored workflows), the victim stack configured with `maximum_commits_per_deploy` and `continuous_deployment`, and at least one shared historical commit that is otherwise non-deployable only due to missing/failing CI status on the victim's own pipeline. The attacker needs no Shipit session, API token, or secret — only the ability to have GitHub emit a genuine, correctly-signed `status` webhook for the shared sha (e.g., via their own repo's CI or an existing upstream status relay). This is a realistic but not universal precondition; it does not work against an arbitrary unrelated victim stack whose repository the attacker has never interacted with.

### Recommendation
Scope the `StatusHandler` (and analogous handlers such as `CheckSuiteHandler`/`CheckRunHandler` if similarly structured) lookups by the webhook's repository, not just `sha`. E.g., resolve `Repository`/`Stack` from `params.dig('repository', 'full_name')` first, then constrain `Commit.where(sha: params.sha, stack: matching_stacks)` before calling `create_status_from_github!`, so a status can only be attached to commits belonging to the stack(s) whose repository actually emitted the webhook.

### Proof of Concept
```ruby
test "status webhook for a shared sha only affects the reporting repository's stack" do
  victim_stack = shipit_stacks(:shipit) # tracks org/victim-repo
  attacker_stack = shipit_stacks(:cyclimse) # tracks org/attacker-fork, shares history

  shared_sha = "deadbeef" * 5
  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: "old commit", author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: 1.day.ago, committed_at: 1.day.ago)
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, message: "old commit", author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: 1.day.ago, committed_at: 1.day.ago)

  refute victim_commit.deployable?, "victim commit should not be deployable before any CI status"

  # Attacker's repo emits a validly-signed status event for the shared sha
  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'attacker-ci',
    'repository' => { 'full_name' => attacker_stack.github_repo_name, 'owner' => { 'login' => 'attacker-org' } }
  }
  Shipit::Webhooks::Handlers::StatusHandler.new.call(payload)

  # Binding under test: victim_commit.deployable? should equal
  # "CI configured on victim_stack's own repository reported success for shared_sha" (== false),
  # but the handler makes it true because of the global sha lookup.
  assert victim_commit.reload.deployable?, "unrelated victim stack's commit became deployable from a foreign repository's status"
  assert_equal victim_commit, victim_stack.next_commit_to_deploy
end
```
