### Title
Unvalidated `P2PStakingInfo.BlockNum` in Fast-Sync Allows Malicious Peer to Corrupt Staking DB — (`datasync/downloader/downloader.go`, `datasync/downloader/queue.go`)

---

### Summary

During fast sync, a malicious P2P peer can return a `P2PStakingInfo` whose `BlockNum` field is set to an arbitrary value `M`, while the corresponding `fetchResult` is for header at block `N`. Because the `validate` callback in `DeliverStakingInfos` is an explicit no-op and `commitFastSyncData` / `commitPivotBlock` use `result.StakingInfo.BlockNum` as the DB write key without cross-checking `result.Header.Number`, the staking info is persisted at key `M` instead of `N`. This leaves `N` without a DB entry and writes attacker-controlled staking data at `M`.

---

### Finding Description

**Step 1 — Staking info is fetched only for pre-Kaia interval blocks.**

`newFetchResult` sets the `stakingInfoType` pending bit only when:

```go
header.Number.Uint64() % stakingUpdateInterval == 0 && !isKaiaFork
``` [1](#0-0) 

So staking infos are requested for exactly the staking-interval boundary blocks, and only before the Kaia hardfork.

**Step 2 — The validate callback is a no-op.**

When the peer's response arrives, `DeliverStakingInfos` calls the generic `deliver` helper with a validate function that unconditionally returns `nil`:

```go
validate := func(index int, header *types.Header) error {
    // TODO-Kaia-Snapsync update validation logic
    return nil
}
reconstruct := func(index int, result *fetchResult) {
    result.StakingInfo = stakingInfoList[index]
    result.SetStakingInfoDone()
}
``` [2](#0-1) 

The `reconstruct` closure assigns the peer-supplied `P2PStakingInfo` (including its `BlockNum`) to the `fetchResult` by position, with no check that `stakingInfoList[index].BlockNum == header.Number.Uint64()`.

**Step 3 — `commitFastSyncData` and `commitPivotBlock` write using the peer-supplied `BlockNum`.**

```go
if result.StakingInfo != nil {
    d.stakingModule.PutStakingInfoToDB(result.StakingInfo.BlockNum, staking.ToStakingInfo(result.StakingInfo))
}
``` [3](#0-2) [4](#0-3) 

`PutStakingInfoToDB` writes directly to the KV store keyed by the supplied number:

```go
func (s *StakingModule) PutStakingInfoToDB(sourceNum uint64, stakingInfo *staking.StakingInfo) {
    WriteStakingInfo(s.ChainKv, sourceNum, stakingInfo)
}
``` [5](#0-4) 

**Step 4 — Contrast with the guarded `SyncStakingInfo` path.**

The staking-info recovery path (`SyncStakingInfo`) does validate `BlockNum`:

```go
if d.stakingInfoRecoveryBlocks[0] != stakingInfo.BlockNum {
    logger.Error("failed to receive expected block", ...)
    return
}
``` [6](#0-5) 

The fast-sync path has no equivalent guard.

**Step 5 — `GetStakingInfo` reads from DB first; state is unavailable post-fast-sync.**

For pre-Kaia blocks, `GetStakingInfo` tries the DB before falling back to state:

```go
if !isKaia {
    if si := ReadStakingInfo(s.ChainKv, sourceNum); si != nil {
        return si, nil
    }
}
si, err := s.getFromStateByNumber(sourceNum)
``` [7](#0-6) 

After fast sync, only the pivot block's state trie is present. State for pre-pivot blocks is unavailable, so the fallback `getFromStateByNumber` fails. A missing DB entry at `N` therefore causes `GetStakingInfo` to return an error for any block whose source interval is `N`.

---

### Impact Explanation

Two distinct harms result:

1. **Corrupted staking data at `M`**: If `M` is a valid staking-interval block that is used as the source for future block processing, the node reads attacker-controlled `NodeIds`, `StakingAmounts`, and `RewardAddrs`. This directly corrupts validator-set selection and reward distribution for the epoch governed by `M` — an unauthorized alteration of reward accounting.

2. **Missing staking data at `N`**: The correct entry for `N` is never written. Post-fast-sync, the state for `N` is unavailable, so `GetStakingInfo` returns an error for every block whose source interval is `N`. Block processing halts, causing persistent loss of chain functionality on the victim node.

Both effects are durable: the DB is written once and not automatically corrected.

---

### Likelihood Explanation

- Any node can connect as a P2P peer (permissionless).
- Fast sync is the default mode for new nodes joining a chain with significant history.
- The attacker only needs to serve staking-info responses with a crafted `BlockNum`; no cryptographic material or validator keys are required.
- The `TODO-Kaia-Snapsync update validation logic` comment confirms the missing check is a known gap, not an intentional design.

---

### Recommendation

In `DeliverStakingInfos`, replace the no-op validate with a check that the returned `BlockNum` matches the header's block number:

```go
validate := func(index int, header *types.Header) error {
    if stakingInfoList[index].BlockNum != header.Number.Uint64() {
        return fmt.Errorf("staking info block number mismatch: got %d, want %d",
            stakingInfoList[index].BlockNum, header.Number.Uint64())
    }
    return nil
}
```

Additionally, in `commitFastSyncData` and `commitPivotBlock`, use `result.Header.Number.Uint64()` as the DB key (not `result.StakingInfo.BlockNum`) and assert equality as a defense-in-depth measure.

---

### Proof of Concept

1. Stand up a fast-sync peer that serves valid headers/receipts/bodies for blocks `[1, 2*interval, 3*interval, …]` (pre-Kaia chain).
2. For the staking-info response for block `N = 2*interval`, return a `P2PStakingInfo` with `BlockNum = M` (e.g., `M = 99*interval`, a future epoch) and attacker-chosen `CouncilStakingAmounts`.
3. Let the victim complete fast sync.
4. Assert: `ReadStakingInfo(db, N)` is `nil`; `ReadStakingInfo(db, M)` contains the attacker's data.
5. Trigger `GetStakingInfo` for any block whose source interval is `N`; observe it returns an error (state unavailable) and block processing halts.
6. Trigger `GetStakingInfo` for any block whose source interval is `M`; observe it returns the attacker's staking amounts, causing incorrect reward distribution.
