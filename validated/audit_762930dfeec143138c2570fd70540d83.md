### Title
Cross-repository `Status` write via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits solely by `sha` — `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — and never restricts the query to the commit whose repository/organization matches the webhook that was actually signature-verified. Because signature verification in `WebhooksController#verify_signature` only proves the payload came from the organization identified by `repository_owner` in the (unsigned-content-wise irrelevant) JSON body, and never re-validates that organization against the target commit's stack, a webhook that is legitimately signed for organization A can still write a `Status` row onto a `Commit` belonging to organization B's stack whenever the `sha` values coincide.

### Finding Description
Binding claimed: `repository_owner` (the org whose `webhook_secret` verified `X-Hub-Signature`) must equal the organization owning every `Commit`/`Stack` row that `StatusHandler#process` mutates.

- `WebhooksController#repository_owner` reads `params.dig('repository','owner','login')` from the JSON body [1](#0-0) , and `#verify_signature` uses it to pick the `GitHubApp`/`webhook_secret` that verifies the signature [2](#0-1) . This step is sound — it does prove the payload was HMAC-signed with organization A's genuine secret.
- However, once verified, `#create` dispatches the raw parsed payload to `StatusHandler.call` with no repository context carried forward [3](#0-2) .
- `StatusHandler` only requires `sha`/`state` in its param schema — it never requires or reads `repository.full_name` [4](#0-3) .
- `StatusHandler#process` resolves the target purely by global SHA lookup: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [5](#0-4) . Unlike other handlers, it never uses the base `Handler#stacks`/`Repository.from_github_repo_name(repository_name)` scoping helper that other handlers (e.g. `PullRequest::OpenedHandler`) use to bind to the correct repository [6](#0-5) .
- `Commit#create_status_from_github!` then writes a real `Status` row tied to that commit's actual `stack_id`, and triggers `add_status`, which can flip `deployable?`, emit `Hook.emit(:deployable_status, ...)`, and schedule `ContinuousDeliveryJob` [7](#0-6) [8](#0-7) .

Exploit path: an attacker who controls a repository under an organization A that Shipit already trusts (i.e., Shipit is configured with a real `webhook_secret` for org A via `Shipit.github(organization: 'A')`) can create a commit in their own repo whose SHA is identical to a commit that already exists in a victim stack under organization B (trivially achievable if A's repo is a fork/mirror sharing history with B's tracked repo — identical tree/parent/author/committer/timestamp/message reproduces the identical SHA-1). The attacker then sets a commit status on that SHA on their own repo (via the GitHub Status API on a repo they own, or by pushing a commit and letting CI post a status) causing GitHub to send a genuinely-signed `status` webhook naming org A as `repository.owner.login`. `verify_signature` correctly validates it using org A's real secret. `StatusHandler#process` then matches the SHA against `Commit` rows globally, including org B's commit, and writes a `Status` there — a payload legitimately originating from (and verified for) org A mutates org B's stack data.

Existing guards do not stop this: `verify_signature` only checks the HMAC against `repository_owner`, it never re-checks that resolved `Commit` rows belong to that same organization; the `ExplicitParameters` schema for `StatusHandler` doesn't require/validate `repository.full_name` at all, so there's no per-repository scoping opportunity even if one wanted to add it downstream.

### Impact Explanation
A payload verified for organization A's repository writes/mutates `Status` (and consequently deployability/CD scheduling) rows belonging to organization B's stack/commit — exactly the "payload for one repository mutating another's stack/commit" Critical category. Blast radius is any multi-tenant Shipit deployment where multiple organizations/repositories are configured, and it is fully repeatable: any commit shared by SHA between an attacker-controlled repo and a victim-tracked repo can be targeted repeatedly with arbitrary status states (`success`, `failure`, `error`, `pending`), letting the attacker force or block deploy eligibility on a foreign stack without ever compromising secrets.

### Likelihood Explanation
Preconditions: Shipit must already have a configured `webhook_secret` for an organization the attacker controls a repository in (a realistic multi-tenant setup), and the attacker's repo must share at least one commit SHA with a repository tracked by the victim's stack (realistic via forks, mirrors, or shared vendored history). The attacker needs no Shipit session, API token, or victim secrets — only ordinary GitHub repo ownership and the ability to set a commit status via the GitHub API on their own repository. This is a low-cost, self-service, and repeatable attack once the SHA-sharing precondition is met.

### Recommendation
In `StatusHandler`, require `repository.full_name` in the param schema and scope the commit lookup through `Repository.from_github_repo_name(repository_name)&.stacks`/commits (mirroring `Handler#stacks`) rather than a bare `Commit.where(sha:)`, so only commits belonging to the repository named in the verified webhook payload can receive the status update.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb
test "status webhook verified for org A does not mutate a commit belonging to org B's stack with the same sha" do
  stack_b = shipit_stacks(:shipit) # belongs to org B / repo B
  shared_sha = "a" * 40
  commit_b = stack_b.commits.create!(sha: shared_sha, message: "shared commit")

  payload = {
    "sha" => shared_sha,
    "state" => "success",
    "repository" => { "full_name" => "orgA/low-value-repo", "owner" => { "login" => "orgA" } }
  }

  assert_no_difference -> { commit_b.statuses.count } do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end
end
```
Before the fix, `Commit.where(sha: shared_sha)` matches `commit_b` regardless of `payload["repository"]["owner"]["login"]` being `orgA`, so the assertion fails (a `Status` is created on org B's commit); after scoping the lookup by `repository.full_name`, the count stays unchanged.
