### Title
Cross-tenant forged commit status via sha-only `Commit` lookup and org-decoupled signature verification - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb], [File: lib/shipit/github_app.rb])

### Summary
`WebhooksController#verify_signature` resolves the signing organization solely from attacker-controlled JSON (`repository.owner.login` / `organization.login`) and `GitHubApp#verify_webhook_signature` unconditionally returns `true` when that resolved org has no `webhook_secret` configured. `StatusHandler#process` then writes a GitHub status onto **any** `Commit` row matching `params.sha` with zero check that the commit's actual stack/repository corresponds to the org used for verification, allowing a forged status to be attached to another tenant's commit.

### Finding Description
The claimed binding is: `org_used_for_verification == org_owning(Commit.where(sha: params.sha).stack.repository)`. This equality is never checked or enforced anywhere in the code path, and it is trivially false to construct.

- `repository_owner` is computed purely from the JSON body the attacker sends: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0) . This value is used only to select which configured GitHub App/org secret to check the signature against; it has no relationship to the commit that will actually be mutated.
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when the resolved org has no `webhook_secret` configured: `return true unless webhook_secret` [2](#0-1) . Since `webhook_secret` is an optional config key (`@webhook_secret = @config[:webhook_secret].presence`) [3](#0-2) , any org in the Shipit config without a secret set makes signature verification a no-op for requests naming that org, with no other authentication performed in `#create`.
- `StatusHandler#process` looks up commits by SHA alone, across the *entire* commits table, with no scoping to the repository/org named in the payload: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [4](#0-3) . `create_status_from_github!` writes directly to the matched commit's `statuses` and can flip `deployable?`/merge gating for that commit's stack [5](#0-4) [6](#0-5) .

Exploit flow: the attacker POSTs directly to `/webhooks` (no session, token, or GitHub App install needed) with `X-Github-Event: status`, a JSON body whose `repository.owner.login`/`organization.login` names an org that either (a) is unconfigured/has no `webhook_secret`, or (b) any org for which the attacker can produce a valid signature is irrelevant to whichever `sha` they place in the body. The body's `sha` field is set to a known victim commit SHA belonging to a completely different, secret-protected org/stack. Since `verify_webhook_signature` passes unconditionally for the no-secret org, and `StatusHandler#process` never checks that the payload's `repository` matches the resolved commit's actual repository, the victim's `Commit` gets a forged status recorded.

None of the existing guards close this gap: `drop_unhandled_event` only checks the event type is handled, not payload consistency; `verify_signature`'s only failure mode is HMAC mismatch or `GithubOrganizationUnknown`, neither of which fires when the org has no secret or is a legitimately configured-but-unrelated org; the `ExplicitParameters` schema for `StatusHandler` only validates types of `sha`/`state`/etc., not repository identity [7](#0-6) ; there is no model validation tying a webhook's declared repository to the commit being mutated.

### Impact Explanation
An attacker can write a forged CI/status entry onto a commit belonging to a repository/org they have no relationship with, as long as that commit's SHA is known (SHAs are routinely public/observable). This directly matches "a payload for one repository mutating another's stack, commit... or an unauthorized deploy, rollback or merge" (Critical), since `create_status_from_github!` feeds `Commit#status`/`deployable?`, which gates `stack.schedule_merges` and continuous delivery. This is repeatable against any commit SHA already present in the database, for every org that has no `webhook_secret` configured, with no rate limiting concern needed since a single crafted POST suffices per target commit.

### Likelihood Explanation
Preconditions: (1) the Shipit deployment must have at least one org entry in its GitHub config without a `webhook_secret` set (an optional field, so plausible in real deployments, especially staging/onboarding orgs or Enterprise instances configured loosely), and (2) the attacker must know a target commit SHA (trivially obtainable from public repos, PRs, or Shipit's own UI). No secrets, sessions, or privileged roles are required — only the ability to send an HTTP POST to `/webhooks`, which is explicitly in-scope for the unprivileged attacker model. This is low-cost and fully repeatable.

### Recommendation
- Never allow `verify_webhook_signature` to pass when no secret is configured; treat a missing `webhook_secret` as verification failure (fail closed), not `true`.
- Scope `StatusHandler#process` (and analogous handlers) to commits belonging to the repository named in the verified payload — e.g. join through `stack.repository` and compare against the attacker-supplied `repository.full_name`, rejecting mismatches — rather than matching by SHA alone across all tenants.
- Ensure the org resolved for signature verification is the same org enforced for the write path (single source of truth), not two independently-derived values.

### Proof of Concept
In `test/controllers/webhooks_controller_test.rb` (or a new minitest):
1. Configure two orgs in test secrets: `victim-org` (with `webhook_secret: "s3cr3t"`) and `attacker-org` (no `webhook_secret` key at all).
2. Create a `Stack`/`Repository` under `victim-org` and a `Commit` with a known `sha` on it, asserting `commit.status.unknown?` beforehand.
3. POST to `/webhooks` with header `X-Github-Event: status`, no valid `X-Hub-Signature` (or an arbitrary bogus one), and JSON body:
   ```json
   { "repository": {"owner": {"login": "attacker-org"}}, "sha": "<victim_sha>", "state": "success" }
   ```
4. Assert response is `200 OK` (not `422`), and assert `commit.reload.status.success?` is now `true` — i.e., `verified_org == "attacker-org"` while `owning_org("victim_sha") == "victim-org"`, yet the write succeeded, proving `verified_org != owning_org` but the mutation still occurred.
