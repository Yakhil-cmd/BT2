## Analysis Result

### Title
Cross-repository status forgery via unscoped commit lookup in webhook `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
The `1inch` report describes a value (`msg.value`) that is processed by the contract logic but never checked against the invariant the caller actually intends ("no ETH should move for this call path"). The Shipit analog is `Shipit::Webhooks::Handlers::StatusHandler#process`, which processes an authenticated field (`sha`) that is never checked against the invariant the signature verification actually establishes (`this payload was authenticated for organization X`). The webhook signature is verified per-organization, but the handler that writes commit status data operates on any `Commit` row in the entire database that shares that `sha`, with no scoping to the repository/organization that was actually authenticated.

### Finding Description
`WebhooksController#verify_signature` selects a GitHub App/webhook secret using only the payload's `repository.owner.login` (or `organization.login`), and validates the HMAC signature against that specific organization's secret: [1](#0-0) 

Once verified, the raw payload is dispatched to handlers for the event type: [2](#0-1) 

Most handlers correctly scope their side effects to the repository named in the payload via the `stacks`/`repository_name` helper on `Handler`: [3](#0-2) . For example, `CheckSuiteHandler` filters to `stacks.where(branch: ...)` before touching any commit: [4](#0-3) .

`StatusHandler`, however, does not use this scoping at all — it queries `Commit` globally by `sha` alone, across every stack/repository tracked by the Shipit instance: [5](#0-4) 

This is only safe if `sha` is a global unique identifier across all tracked repositories, but the schema explicitly indexes/scopes commits by `(stack_id, sha)`, not by `sha` alone: [6](#0-5) . Multiple stacks/repositories (e.g. a fork and its upstream, or repositories that share history/mirrors) can legitimately contain `Commit` rows with the identical `sha` value.

The write path affected is not cosmetic: `create_status_from_github!` feeds `add_status`, which updates `Commit#deployable?`/state, which in turn drives `MergeRequest#all_status_checks_passed?` (gating automatic PR merges) and `Stack#schedule_continuous_delivery` (gating continuous deployment): [7](#0-6) [8](#0-7) .

**Binding broken (equality that should hold but doesn't):**
`organization/repository authenticated by verify_signature` == `repository whose Commit rows StatusHandler mutates`

Before the pull-request/attack: signature verification scopes trust to one org; `StatusHandler` implicitly (and only by developer assumption) writes to that same org's commits because SHAs are "usually" unique.
After: an attacker who can cause GitHub to emit *any* legitimately-signed `status` webhook for an org/repo tracked by the same Shipit instance can flip the state of a `Commit` row belonging to a *different* stack/repository, as long as the SHA values collide (a routine occurrence for forks/mirrors that share history).

### Impact Explanation
Forcing a commit's status to `success` can:
- Unblock `MergeRequest#reject_unless_mergeable!`/`all_status_checks_passed?`, causing `ProcessMergeRequestsJob` to auto-merge a pull request that never actually passed CI in its own repository — an **unauthorized merge**.
- Satisfy `Commit#deployable?`, causing `ContinuousDeliveryJob`/`schedule_continuous_delivery` to trigger an **unauthorized deploy** of a stack whose commit never legitimately passed its own repository's checks.

Both outcomes fall squarely in the "Critical: unauthorized deploy/rollback/merge" impact bucket.

### Likelihood Explanation
The attacker only needs the ability to make GitHub deliver one legitimately-signed `status` (or equivalent) webhook event for *any* repository already onboarded to the same Shipit instance — this does not require access to the *target* stack's repository, Shipit session, API token, or any secret; GitHub itself computes and sends the valid signature for whichever org sent the event. SHA collisions across tracked repositories are realistic whenever repositories are forks, mirrors, or were migrated/renamed but retain shared history — a common pattern in organizations that manage many related services with Shipit.

### Recommendation
Scope `StatusHandler#process` (and any other handler that queries by `sha` alone) through the same `stacks`/`repository_name` mechanism used elsewhere, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This restores the invariant that only commits belonging to the repository/organization that was actually authenticated by `verify_signature` can be mutated by the webhook payload.

### Proof of Concept
1. Shipit tracks `OrgA/app` (stack `A`) and `OrgB/app-fork` (stack `B`), where `app-fork` is a fork of `app` and both installations are integrated with the same Shipit instance (each org has its own `webhook_secret`).
2. Both repositories share early commit history, so `Commit` rows for the shared ancestor commit `abc123...` exist under both stack `A` and stack `B` with the same `sha`.
3. An org member of `OrgB` (who has no access to `OrgA`) uses the GitHub Status API on their own repo `OrgB/app-fork` to post a `success` status for commit `abc123...` (perfectly legitimate action on their own repository).
4. GitHub delivers a `status` webhook to Shipit, correctly signed with `OrgB`'s real `webhook_secret`. `verify_signature` passes because `repository_owner == OrgB`.
5. `StatusHandler#process` runs `Commit.where(sha: 'abc123...')`, which matches **both** stack A's and stack B's commit rows, and marks stack A's commit as `success` even though nobody with access to `OrgA` authorized it.
6. If stack `A` has `continuous_deployment: true` or an open merge request depending on that commit's status, this triggers an unauthorized deploy/merge on `OrgA/app` — a repository the attacker never had access to.
