### Title
Unvalidated `creator` account in `InitializeWithPermission` lets pool creator address be set to `Pubkey::default()`, permanently freezing creator trading fees - (File: programs/cp-swap/src/instructions/initialize_with_permission.rs)

### Summary
In `initialize_with_permission`, the `creator` field is an `UncheckedAccount` supplied by the (unprivileged) `payer` and is never constrained to be a signer or to be non-zero, unlike the standard `initialize` instruction where `creator` is a `Signer`. This value is stored as `PoolState.pool_creator` and later used as the sole authority allowed to claim accumulated creator trading fees.

### Finding Description
`InitializeWithPermission::creator` is declared as: [1](#0-0) 
with no `Signer` constraint and no `require_keys_neq!` / non-default check, unlike the permissionless `Initialize` instruction where `creator` is a `Signer<'info>`: [2](#0-1) 

`PoolState::initialize` stores whatever pubkey is passed in as `pool_creator`, with no validation against `Pubkey::default()`: [3](#0-2) 

This `pool_creator` field is then relied upon as the exclusive claimant of accumulated `creator_fees_token_0` / `creator_fees_token_1`:
- `CollectCreatorFee` requires a real `Signer` whose address equals `pool_state.pool_creator`: [4](#0-3) 
- `CollectCreatorFeePermissionless` sends fees to an ATA owned by `pool_state.pool_creator` (no signature required for `creator`, only for `address` equality): [5](#0-4) 

Because `payer` in `initialize_with_permission` fully controls the `creator` account passed into the instruction, they can set it to `Pubkey::default()` (or any other unowned/unspendable address) when the pool is created. From that point on:
- `CollectCreatorFee` can never succeed, since nobody holds the private key to sign as `Pubkey::default()`.
- `CollectCreatorFeePermissionless` will happily create an ATA owned by `Pubkey::default()` and forward the fees there — but since no private key exists for that owner, the tokens in that ATA can never be transferred out again.

This mirrors the reported bug class: a critical authority/manager address associated with a freshly created object (`_claimManager` in the OpenQ report, `pool_creator` here) can be left as/set to the zero address by an unprivileged actor at creation time, permanently preventing the intended party from claiming funds that accrue to that role.

### Impact Explanation
Creator trading fees (`creator_fees_token_0`/`creator_fees_token_1`), which accumulate from every swap on the pool while `enable_creator_fee` is set, become permanently unclaimable/frozen if `pool_creator` is `Pubkey::default()`. This is a permanent freezing of pool funds that keep accruing over the life of the pool (accumulated in `PoolState` and backed by real tokens in the vaults per `vault_amount_without_fee`): [6](#0-5) 
Anyone can create such a pool via `initialize_with_permission` (subject to whatever permission-gating is enforced elsewhere for `payer`), so this is directly reachable by a single attacker-controlled transaction with attacker-chosen accounts.

### Likelihood Explanation
Likely reachable whenever `initialize_with_permission` is callable by a permissioned/whitelisted payer (gated by the `Permission` PDA check), since nothing in the account constraints prevents `creator` from being the system-owned zero address; it can also happen accidentally if a client passes an uninitialized/default pubkey for `creator`.

### Recommendation
Add an explicit `require_keys_neq!(ctx.accounts.creator.key(), Pubkey::default())` check (or an Anchor constraint `constraint = creator.key() != Pubkey::default()`) in `InitializeWithPermission`, mirroring the non-zero checks already used for `set_new_protocol_owner` / `set_new_fund_owner` in `update_config.rs`: [7](#0-6) 

### Proof of Concept
1. A permitted `payer` calls `initialize_with_permission`, supplying `creator = Pubkey::default()` (any zeroed/unowned pubkey works) along with valid mint/vault accounts.
2. The instruction succeeds; `pool_state.pool_creator` is set to `Pubkey::default()`.
3. Swaps occur on the pool and `creator_fees_token_0`/`creator_fees_token_1` accumulate in `PoolState` as designed.
4. `collect_creator_fee` can never be invoked successfully because no signer can produce a valid signature for `Pubkey::default()`.
5. `collect_creator_fee_permissionless` can be called, but it creates/uses an ATA whose authority is `Pubkey::default()`; the transferred fee tokens land in an account nobody can ever sign a transfer from — the funds are permanently frozen.
