Based on my investigation, the closest analog to the "signature replay with the same fee/price value" pattern exists in `pallet-nfts`'s pre-signed mint mechanism.

### Title
Pre-signed mint authorization with a fixed `mint_price` can be replayed after burn to re-mint at a stale price - ([File: substrate/frame/nfts/src/features/create_delete_item.rs])

### Summary
`Nfts::mint_pre_signed` accepts a `PreSignedMint` struct — collection, item, attributes, metadata, `deadline`, `only_account`, and `mint_price` — signed off-chain by the collection Issuer [1](#0-0) . Just like the ChainportMainBridge/SideBridge case, the signed payload fixes a monetary value (`mint_price`) and is valid until a `deadline`, but contains no nonce. The only thing preventing reuse of the very same signature is the `Item::<T,I>` existence check inside `do_mint` (`AlreadyExists`) [2](#0-1) , not any consumed-signature/nonce tracking tied to the signed message itself.

### Finding Description
`do_mint_pre_signed` validates the deadline, the `only_account` binding, and the Issuer role of the signer, then calls `do_mint`, which charges `mint_price` from the minter to the collection owner inside the `with_details_and_config` closure [3](#0-2) . `do_mint` rejects a second mint of the same `(collection, item)` via `Item::<T,I>::contains_key` [2](#0-1) , but this is state tied to the *item slot*, not to the *signature*. If the minted item is later burned, `Item::<T,I>` entry is removed by `do_burn` (consistent with the mint/burn lifecycle exposed in `substrate/frame/nfts/src/features/create_delete_item.rs`), which re-opens the `AlreadyExists` gate. The exact same `PreSignedMint { mint_price: X, deadline, .. }` payload and its original signature remain valid until `deadline`, so nothing in `validate_signature`/`do_mint_pre_signed` prevents feeding the identical signed message back in.

This directly mirrors the ChainportMainBridge/SideBridge bug class: a validator/issuer signs a message that binds a *value* (gas fee vs. mint price) and a *deadline*, with no nonce or single-use marker, so the message can be replayed as long as the surrounding state (existence of the item) is reset by an ordinary, unprivileged action (burn) available to the same user who benefits from the stale price.

### Impact Explanation
An account holding an active `PreSignedMint` authorization with a favorable `mint_price` can mint, burn, and re-mint the same item repeatedly until `deadline`, each time paying the originally signed (now possibly stale/incorrect) price rather than whatever price the Issuer intends at the time of the repeat mint. If the Issuer intended the authorization to be single-use (as implied by the presence of `mint_price` and `only_account` fields designed to gate a specific sale), this breaks that intent and allows repeated underpriced mints — an economic/business-logic violation analogous to the "same fee value" replay in the reported bug. It does not, however, allow unbacked issuance of currency or a security-critical privilege escalation; it is bounded by the `deadline` window and by the Issuer's willingness to keep signing/publishing such messages, similar to why the original Chainport report was rated Low.

### Likelihood Explanation
Reachable by any ordinary signed account with no privileged role: obtain a valid `PreSignedMint` signature from the Issuer (e.g., a public sale authorization), call `mint_pre_signed`, then call the normal `burn` extrinsic, then call `mint_pre_signed` again with the identical arguments before `deadline`. All calls go through standard signed-origin extrinsics with no special preconditions beyond owning the pre-signed data, which is exactly the attacker model allowed by the scan instructions (no privileged role, no stolen keys).

### Recommendation
Either (a) track consumed pre-signed mint authorizations independently of item existence (e.g., store a hash of the signed payload or a nonce field bound to the signer/authorization, cleared only by explicit invalidation), so burning the item cannot re-enable replay of the same signed price, or (b) require the Issuer to include a per-authorization nonce that is consumed on first use and never reset by burn, mirroring the `Nonces` pattern already used elsewhere in the codebase (e.g., the EIP-2612 `permit` pallet at `substrate/frame/assets/precompiles/src/permit.rs`, which correctly increments a nonce on `use_permit` to prevent exactly this class of replay).

### Proof of Concept
I was not able to fully verify the `do_burn` storage-removal code path in this session (the file read was truncated before the `Item::<T,I>::remove` line), so this is presented as a state-machine hypothesis requiring confirmation rather than a fully executed PoC. Existing unit tests already exercise the adjacent state transitions — `pre_signed_mints_should_work` mints with `mint_price: Some(10)`, then burns the item, then continues using new (differently-parameterized) mint data [4](#0-3)  — but no existing test re-submits the *original, unmodified* signed payload after a burn to confirm whether it succeeds and re-charges the same stale `mint_price`. A concrete reproduction would extend this test to call `mint_pre_signed` a second time with the exact original `mint_data`/`signature` after burning item `(0,0)`, and assert whether it succeeds (confirming the replay) or is rejected (falsifying the hypothesis). This must be run before treating the finding as confirmed rather than a plausible analog.
