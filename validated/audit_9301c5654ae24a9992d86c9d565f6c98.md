### Title
LP collateral price derived from manipulable Aquarius pool reserves enables forced liquidations - (File: contracts/price-aggregator/src/providers/aquarius.rs)

### Summary
XOXNO Lending prices Aquarius LP share collateral from the pool's live reserves via `fair_lp_price_wad` = `2 * sqrt(value_a * value_b) / total_shares` (common/src/oracle/lp.rs:57-87). Because `read` re-queries `get_reserves` at liquidation time (contracts/price-aggregator/src/providers/aquarius.rs:90-93) and a single-source LP oracle has no second leg to flag a deviation (`Outcome::one`, engine.rs:90-100, `Legs::One` path in `blend`, engine.rs:414-418), an unprivileged attacker can skew a thin pool's reserves with their own swap (optionally funded by the pool's own `flash_loan`) to depress the collateral price below the sanity bound, push victim positions under HF = 1, and liquidate them for the bonus.

### Finding Description
The external report's bug class is "oracle consumes pool-derived spot data that a low-liquidity pool makes cheap to move." The analog maps directly onto `aquarius::read`: it calls `aquarius_pool_reserves_call` fresh on every resolution (aquarius.rs:90-91), computes the geometric-mean fair price in `fair_lp_price_wad` (lp.rs:75-86), and only rejects when `pool_value_wad < lp.min_pool_value_wad` (aquarius.rs:118-122) or the result exits `[min_sanity_price_wad, max_sanity_price_wad]` (engine.rs:142-146). The geometric-mean formula is manipulation-resistant *upward* (imbalance can only lower `sqrt(v_a*v_b)`), but it is freely manipulable *downward*: a swap that imbalances reserves strictly reduces the priced LP value. There is no TWAP, no reserve-snapshot pinning, and no liquidity-ratio check between pools — the exact fix recommended in the report ("use specific pools") is only half-applied: a *specific* pool is bound via `bound_tokens`/`share_id` (aquarius.rs:148-160), but its reserves remain a spot read.

When the LP token's oracle has a single `AquariusLp`/`AquariusStableLp` source, `compose` returns `Legs::One` and `deviation` is hardcoded `false` (engine.rs:511-516, 95-98), so the tolerance band in `within_tolerance_band` never runs. The only guards are the sanity bounds and `min_pool_value_wad`, both static admin-chosen constants, while liquidity on Aquarius can decay after listing. The controller then consumes this price through the Context-cached strict price when computing health factor during `liquidate` (single transaction, same ledger state as the attacker's swap).

### Impact Explanation
An attacker depresses the fair price of an LP collateral token, pushing a victim's health factor below 1 mid-transaction, then calls `liquidate` in the same transaction (composed via the attacker's own contract/flash receiver). The liquidation seizes collateral at the manipulated valuation plus the HF-based bonus — theft of user funds / unearned liquidation profit. This is not fail-closed DoS: the manipulated price passes `failure()` checks as long as it stays inside the sanity band and above `min_pool_value_wad`.

### Likelihood Explanation
Reachable by any unprivileged address: only `swap` on the target Aquarius pool plus `controller.liquidate`. Attack capital can be borrowed from the protocol itself via `flash_loan`, and the skew + liquidate can be composed atomically in one Soroban transaction through an attacker contract. Likelihood is bounded by (a) how thin the configured pool is relative to `min_pool_value_wad` and the sanity band width, and (b) swap cost vs. liquidation bonus. For pools listed with modest liquidity that later thins, the manipulation cost is small — the same condition the report flags. Medium likelihood, Medium severity.

### Recommendation
- Always pair an `AquariusLp`/`AquariusStableLp` source with an independent second leg so `Legs::Two` triggers `within_tolerance_band` deviation rejection (engine.rs:427-430), rather than allowing single-source `Legs::One` for pool-derived prices.
- Enforce a tight `min_pool_value_wad` and treat `InsufficientAquariusLiquidity` near-approaches as a reason to widen the sanity check, or snapshot/TWAP reserves rather than reading `get_reserves` spot.
- Consider rejecting resolutions where the implied pool value fell by more than a configured ratio since `attest`/`set_oracle` time (analogous to the report's "50% liquidity difference" suggestion), since `pool_value_wad` is already computed at aquarius.rs:118.

### Proof of Concept
1. Admin configures `AssetOracle` for an LP share token with a single `PriceSource::AquariusLp` pointing at a thin Aquarius constant-product pool; `min_pool_value_wad` and sanity bounds are loose enough to pass `attest`/`probe_priceable`.
2. Victim supplies the LP token as collateral and borrows; HF ≈ 1.05.
3. Attacker, in one transaction via their own contract:
   a. calls `pool.flash_loan` (or uses own funds) to get token A;
   b. executes a large `swap` on the Aquarius pool, skewing `get_reserves` so that `sqrt(value_a * value_b)` drops ~10% (fair LP price can only decrease with imbalance, per lp.rs:75-76);
   c. calls `controller.liquidate(victim, ...)`: `aquarius::read` fetches the skewed reserves, `Legs::One` skips the tolerance band, price lands above `min_pool_value_wad` and inside the sanity band, victim HF < 1, liquidation succeeds and pays the attacker the bonus;
   d. back-swaps to restore the pool and repays the flash loan.
4. Net: attacker profits the liquidation bonus minus swap fees/slippage on a pool they can cheaply move; victim is liquidated at a fabricated collateral price.
