### Title
Webhook signature is verified against `repository.owner.login`, but event handlers select the target `Stack` via the independent `repository.full_name` field — allowing a legitimate but unrelated organization's webhook secret to forge events against any other organization's repository ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which* `webhook_secret` to validate the HMAC against using `repository_owner`, computed from `params.dig('repository', 'owner', 'login')` (or `organization.login`) [1](#0-0) [2](#0-1) . Once the signature check passes, the raw JSON body is dispatched unchanged to the matching `Webhooks::Handlers::Handler` subclasses via `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [3](#0-2) . Those handlers, however, select the `Stack`/`Repository` to act on using a *different* field of the same body: `repository.full_name` [4](#0-3) . Nothing in the codebase cross-checks that `repository.owner.login` (used to choose the signing secret) actually corresponds to `repository.full_name` (used to choose the write target).

### Finding Description
Shipit supports multiple GitHub organizations, each configured with its own `webhook_secret` (`Support multiple GitHub organisations. (#1151)` per the changelog) [5](#0-4) . `verify_signature` resolves the correct `GithubApp`/secret purely from the attacker-controlled JSON body:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end
``` [6](#0-5) 

`repository_owner` is:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

If an attacker legitimately controls organization "attacker-org" that is onboarded into the same Shipit instance (i.e. they know its `webhook_secret`, without any privileged Shipit account or stolen credentials for the victim), they can HMAC-sign an arbitrary JSON body with that secret while setting:
- `repository.owner.login = "attacker-org"` (so `verify_signature` picks and validates against the secret they actually know), and
- `repository.full_name = "victim-org/victim-repo"` (an unrelated repository/organization already tracked by the same Shipit instance).

The signature check only depends on the raw byte content matching the HMAC for `attacker-org`'s secret — it never inspects `full_name` — so this crafted, self-consistent-looking-but-mismatched payload passes verification. Handlers then act on `victim-org/victim-repo` because `Handler#stacks` resolves the target purely from `repository.full_name`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

This breaks the equality the trust model relies on: `organization that authenticated the request == organization whose repository is written`. Concretely, `PushHandler` will enqueue `GithubSyncJob` for the victim's stacks with an attacker-chosen `expected_head_sha` [7](#0-6) , and the `status` event handler creates a `Status` record on a specific commit sha for the resolved repository/stack based entirely on attacker-supplied `sha`, `state`, `context`, `target_url` fields [8](#0-7) . Because `Commit#deployable?` and continuous-delivery triggering depend on recorded CI `Status`es, an attacker who only controls their own unrelated organization's webhook secret can forge a passing CI status for a commit in a victim's repository/stack, which can feed directly into `continuous_deployment` triggering an actual deploy of that commit.

### Impact Explanation
This crosses the "Critical: cross-repository writes / unauthorized deploy" bar explicitly listed in scope. An attacker who legitimately owns one organization already configured in a multi-organization Shipit deployment can inject webhook events (push syncs, forged CI statuses, pull_request/review-stack provisioning, check_suite refreshes) targeting any *other* organization's repository tracked by the same instance, without ever obtaining that victim organization's `webhook_secret`, an `ApiClient` token, or repository write access on GitHub. Forged `status` events in particular can make a commit appear `deployable?`, which — combined with `continuous_deployment` — can result in an unauthorized deploy being triggered on the victim's stack.

### Likelihood Explanation
Requires only that the Shipit instance is configured for multiple GitHub organizations (explicitly supported per `lib/shipit/github_app.rb` and the changelog) and that the attacker controls (or has legitimately been given) one of those organizations' webhook secrets — a normal, unprivileged position for e.g. a self-service or partner-org onboarding model. No compromise of any other credential is needed; the mismatch is purely a missing cross-field validation in `WebhooksController` and `Handler#stacks`.

### Recommendation
In `WebhooksController#verify_signature`/`create`, after verifying the signature, assert that `repository_owner` (the value used to select the signing secret) equals the owner encoded in `repository.full_name` (or, more robustly, resolve the target `Repository`/`Stack` using the same organization value that was cryptographically authenticated, rather than trusting `repository.full_name` independently). Reject the webhook (422) if they diverge.

### Proof of Concept
Conceptual PoC (cannot be executed without a live multi-org Shipit instance, but follows directly from the code above):
1. Shipit is configured with two organizations: `attacker-org` (secret known to attacker) and `victim-org` (tracks stack for `victim-org/victim-repo`), per `lib/shipit/github_app.rb` multi-org support.
2. Attacker builds a `status` (or `push`) webhook JSON body:
   ```json
   {
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
     "sha": "<victim commit sha>", "state": "success", "context": "ci/required", "target_url": "https://evil"
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org secret, body)` and POSTs to `/github/webhooks`.
4. `verify_signature` resolves `github_app = Shipit.github(organization: "attacker-org")` and validates successfully [1](#0-0) .
5. `Shipit::Webhooks.for_event('status').each { |handler| handler.call(params) }` runs, and the handler resolves the target repository via `payload.dig('repository', 'full_name')` = `"victim-org/victim-repo"` [4](#0-3) , creating a forged `success` status against the victim's commit — potentially unlocking continuous deployment for a commit the attacker never had access to.
