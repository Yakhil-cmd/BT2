### Title
CCMenu API token is created without stack scoping, letting any Shipit user obtain a token that authorizes reading every stack's build status - (File: app/controllers/shipit/ccmenu_url_controller.rb)

### Summary
`CCMenuUrlController#fetch` generates a "ccmenu" status URL that is presented to the user as being scoped to one specific stack, but the underlying `ApiClient` token it mints is never bound to that stack. Combined with `Api::CCMenuController` also bypassing the ApiClient's stack scope when resolving the target stack, the token can be used to read the build/deploy status of any stack in the Shipit installation, not just the one it was generated for.

### Finding Description
`CCMenuUrlController#fetch` builds a per-stack URL and attaches an authentication token from a client: [1](#0-0) 

The `client` method finds or creates an `ApiClient` scoped only by `creator` and `name`, with `permissions: %w[read:stack]` — it never sets `stack:` on the record: [2](#0-1) 

`ApiClient` has an optional `belongs_to :stack`; when `stack_id` is `nil`, `Api::BaseController#stacks` treats the client as globally scoped (`Stack.all`) rather than restricted to one stack: [3](#0-2) [4](#0-3) 

`check_permissions!` only checks the operation/scope string (`"read:stack"`), never which stack is being accessed: [5](#0-4) 

Independently, `Api::CCMenuController` overrides the base controller's scoped `stack` accessor (`@stack ||= stacks.from_param!(params[:stack_id])`) with an unscoped lookup that ignores the client's `stack_id` binding entirely: [6](#0-5) 

This breaks the intended equality `stack authorized by token == stack touched by request`. The URL/token that the user believes is scoped to `stack_id=A` is, in reality, either (a) an unscoped `ApiClient` with global `read:stack` permission (because `client` never receives a `stack:` association), or (b) even if it were scoped, `CCMenuController#stack` would still bypass that scope by resolving the stack directly from `params[:stack_id]` instead of `stacks.from_param!`.

### Impact Explanation
CCMenu URLs are designed to be handed to external, semi-trusted consumers (CI dashboard tools, build-status widgets) specifically because they are meant to expose only one stack's status without full Shipit credentials. Because the token is not actually stack-scoped, anyone who obtains one such URL/token (e.g. by viewing a public dashboard, a leaked config, or a stack they legitimately have access to) can substitute any other `stack_id` in the URL and read build status, last deploy outcome, and lock state (`Xml`: `lastBuildStatus`, `lastBuildLabel`, `activity`, etc.) for every stack in the Shipit instance — including internal/production stacks the requester was never meant to see. This is an unauthorized, cross-stack read of deploy/task state via a credential that appears (and is generated to be) narrowly scoped, matching the "unauthorized read of stack state" High-impact class defined for this analysis.

### Likelihood Explanation
Any authenticated Shipit user (unprivileged with respect to other stacks) can trigger `CCMenuUrlController#fetch` for a stack they can view, and obtain a token/URL. No special permission beyond ordinary Shipit login is required to mint the token, and no code path re-derives or enforces a per-stack limitation once the token exists. This makes the escalation exploitable with a normal Shipit account and zero additional preconditions (no signature bypass, no host compromise, no admin access needed).

### Recommendation
- Scope the `ApiClient` created in `CCMenuUrlController#client` to the requested stack (`stack:` association set to the resolved stack) instead of only keying on `creator`/`name`.
- Remove the `stack` override in `Api::CCMenuController` and use the inherited, scope-aware `stacks.from_param!(params[:stack_id])` so an ApiClient's `stack_id` binding is always enforced when resolving the target stack.
- Add a regression test asserting that a CCMenu token minted for stack A returns 404/403 when used against stack B's `ccmenu` endpoint.

### Proof of Concept
1. As any authenticated Shipit user with access to stack A, call `GET /ccmenu/*stack_id` (e.g. `/ccmenu/org/repoA/production`) via `CCMenuUrlController#fetch`.
2. Observe the returned `ccmenu_url` contains a `token` parameter generated from an `ApiClient` named `"CCMenu Client"` with `permissions: ["read:stack"]` and no `stack_id` set (`ccmenu_url_controller.rb:15-18`).
3. Take that `token` and issue `GET /api/stacks/org/repoB/staging/ccmenu?token=<token>` for an unrelated stack B that the requester should not be able to probe through this channel.
4. Because `Api::BaseController#stacks` returns `Stack.all` for an unscoped client (`stack_id` nil) and `Api::CCMenuController#stack` bypasses scoping entirely regardless, the request succeeds and returns stack B's build/deploy XML status, confirming the token authorizes more than the single stack it was generated for.

```ruby
module Shipit
  class ApiClient < Record
    InsufficientPermission = Class.new(StandardError)

    belongs_to :creator, class_name: 'User'
    belongs_to :stack, optional: true

    validates :creator, :name, presence: true

    serialize :permissions, coder: Shipit.serialized_column(:permissions, type: Array)
    PERMISSIONS = %w[
      read:stack
      write:stack
      deploy:stack
      lock:stack
      read:hook
      write:hook
    ].freeze
    validates :permissions, subset: { of: PERMISSIONS }
```
