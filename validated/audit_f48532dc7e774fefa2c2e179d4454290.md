### Title
`StatusHandler#process` writes GitHub status webhooks to `Commit` rows by bare SHA with no repository/stack scoping - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves target commits via `Commit.where(sha: params.sha)` with no join or filter on `stack.repository`, so a validly-signed status webhook from *any* repository the attacker controls writes a `security/scan` status to every `Commit` row across every stack that happens to share that SHA. When a victim stack has `continuous_deployment` enabled and requires `security/scan`, this forged status can silently satisfy the requirement and trigger `ContinuousDeliveryJob` to ship.

### Finding Description
The broken binding: the code assumes `status.sha ∈ repository_that_authenticated(webhook)` implies `commit.stack.repository == repository_that_authenticated(webhook)`. In fact: [1](#0-0) 

`Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` looks up commits purely by the `sha` string across the whole `commits` table, with `belongs_to :stack` being the only repo linkage and it is never used as a filter here [2](#0-1) .

The webhook signature check only proves the payload was signed by the GitHub App/org associated with the `repository.owner.login` field found *inside the same attacker-controlled payload* — it does not bind the resulting DB writes to that repository: [3](#0-2) 

So `verify_signature` correctly authenticates "this payload really came from GitHub for org X," but `StatusHandler` then applies it to *every* `Commit` record sharing that SHA, regardless of which stack/repo that commit row belongs to.

Because git SHAs are content-addressed, the same commit object legitimately appears in multiple `Commit` rows whenever:
- a repository is tracked by multiple `Stack`s (e.g., one per branch/environment — the common Shipit topology of a `staging` stack and a `production` stack on the same repo), or
- the same commit is later merged/fast-forwarded into another tracked branch.

An attacker who can open a PR/push to a branch on that repository (as stipulated: "any unprivileged GitHub user who can open a pull request... and emit webhooks from a repository they own") can:
1. Get GitHub to send (or directly send, since only signature validity is checked, not sender identity/permissions) a `status` webhook for a SHA that is also present in the victim's protected stack's `commits` table, with `context: "security/scan"`, `state: "success"`.
2. `StatusHandler#process` finds the `Commit` row belonging to the victim stack (same SHA, different `stack_id`) and calls `create_status_from_github!`, writing a fabricated passing status to it.
3. `Commit#add_status` recomputes `status`; if the commit becomes `deployable?` (`success?` and not `blocked?`) and the victim stack has `continuous_deployment?` enabled, `schedule_continuous_delivery` enqueues `ContinuousDeliveryJob` [4](#0-3) , which can ship the commit without the real required check ever running.

None of the existing guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema on `StatusHandler`) validate that the commit being updated belongs to the repository that authenticated the request; the `params` schema only requires `sha`, `state`, and optional `context` — it has no repository field to cross-check against [5](#0-4) .

### Impact Explanation
A status write intended for one repository lands on a `Commit` belonging to a different stack — exactly the "payload for one repository mutating another's stack/commit" category. Combined with `continuous_deployment` enabled and a `security/scan` required-status policy, this can cause `ContinuousDeliveryJob` to ship a commit that never actually passed the real check, i.e., an unauthorized deploy. This is repeatable per victim stack: any time a target SHA exists (or later exists) in both the attacker-accessible repo's history and the victim stack's `commits` table, the attacker can forge the status again. Severity matches Critical - unauthorized deploy of attacker-influenced state.

### Likelihood Explanation
Preconditions: (1) attacker has push/PR access to some repository with the Shipit GitHub App/webhook properly configured (needed simply to get a validly signed webhook through `verify_signature`); (2) the target SHA is shared between a `Commit` row the attacker can naturally produce a status for and a `Commit` row in the victim's protected stack (very common when one repo is tracked by multiple Shipit stacks per branch, or when a feature branch commit is later merged upstream); (3) the victim stack has `continuous_deployment` enabled and requires the `security/scan` context. These are realistic/common Shipit configurations (multi-branch/multi-environment stacks on one repo), and the attacker cost is a single webhook/API status call — trivially repeatable.

### Recommendation
Scope the commit lookup in `StatusHandler#process` (and equivalently in `CheckRunHandler`, if it has the same pattern) by repository, not just `sha`. E.g., resolve the target repository from the webhook payload (`params.dig('repository', 'full_name')`) and join through `stack.repository` (or `Repository.find_by(...)` plus `Commit.where(sha:, stack: Stack.where(...))`) so only commits belonging to stacks tracking the authenticated repository are updated.

```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual)
test "status for security/scan is not applied cross-stack via bare sha lookup" do
  victim_stack = shipit_stacks(:shipit) # continuous_deployment: true, requires 'security/scan'
  attacker_stack = create_stack_for_different_repo!

  shared_sha = "a" * 40
  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: "shared")
  attacker_stack.commits.create!(sha: shared_sha, message: "shared")

  # Binding under test:
  # victim_commit.stack.repository == params.dig('repository') ?  -> should be required before any write
  assert_not_equal victim_stack.repository.full_name, attacker_stack.repository.full_name

  Shipit::Webhooks::Handlers::StatusHandler.new.call(
    'sha' => shared_sha, 'state' => 'success', 'context' => 'security/scan',
    'repository' => { 'full_name' => attacker_stack.repository.full_name }
  )

  victim_commit.reload
  # FAILS today: victim_commit picks up the attacker-authenticated status despite
  # never having its repository verified, potentially flipping deployable? true
  # and firing ContinuousDeliveryJob for victim_stack.
  assert_empty victim_commit.statuses.where(context: 'security/scan'),
    "status for a repo that did not authenticate this webhook must not be written to victim's commit"
end
```

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
