Based on my research, I found a concrete analog of the ImageMagick BMP integer-overflow bug (CWE‑190): a JS "overflow" via IEEE‑754 double-precision loss that happens in the multiplication step of a value that is later checked for equality, but the check is performed on the already-lossy result rather than on the safely-bounded operands — the same "check-after-the-overflow" pattern as the ImageMagick bug.

### Title
Integer/precision-overflow in asset denomination cap validation allows declaring an unbounded/mismatched capped supply - (File: `validation.js`)

### Summary
`validateAssetDefinition()` computes `total_cap_from_denominations` by multiplying and summing attacker-supplied `denomination` and `count_coins` fields, then compares the accumulated (already computed) result against `payload.cap` for exact equality. `denomination` is bounded by `constants.MAX_CAP`, but `count_coins` has **no upper bound** — it only passes `isPositiveInteger()`. This mirrors the ImageMagick flaw where the overflow-prone multiplication (`extent = width * bpp`) happens first and the sanity check is applied to the corrupted result afterward, making the check ineffective.

### Finding Description
In `validation.js`, the loop that validates an asset's fixed denominations: [1](#0-0) 

computes `total_cap_from_denominations += denomInfo.count_coins * denomInfo.denomination`. `denomInfo.denomination` is capped via `denomInfo.denomination > constants.MAX_CAP` at [2](#0-1) 
but `denomInfo.count_coins` only goes through `isPositiveInteger(denomInfo.count_coins)` at [3](#0-2) 
with no upper bound at all. JavaScript numbers are IEEE‑754 doubles, so once `count_coins * denomination` (or the running sum across up to `constants.MAX_DENOMINATIONS_PER_ASSET_DEFINITION` entries) exceeds `Number.MAX_SAFE_INTEGER` (2^53‑1), the product/sum silently loses precision — this is the JS analog of a 32-bit truncation overflow. The subsequent equality check: [4](#0-3) 

`total_cap_from_denominations && payload.cap !== total_cap_from_denominations` is evaluated on the already-corrupted (rounded) value, not on the true mathematical product. Because IEEE‑754 arithmetic is deterministic, an attacker can pick `count_coins`/`denomination` pairs whose *true* product differs from a chosen `payload.cap`, yet whose *rounded double* result exactly equals the attacker's declared `payload.cap`, so the check passes identically on every node (no consensus split, but the enforced cap is semantically wrong).

This is directly analogous to the reported bug class: an overflow occurs during a multiplication of two attacker-controlled length/count-like fields, and the guard that is supposed to catch bad results is placed after the corruption has already occurred, so it validates the wrong (already-truncated/rounded) value instead of the real one.

### Impact Explanation
The `count_coins` field for each denomination is stored per-denomination in `asset_denominations` and later drives real issuance in `indivisible_asset.js`: [5](#0-4) 

`issue_amount = count_coins_to_issue * denomination`. Because the definition-time cap-consistency check can be satisfied via floating-point rounding rather than a true mathematical equality, an asset issuer (any unpermissioned unit poster) can define a "capped" asset whose nominal `cap` does not actually correspond to the sum of `count_coins * denomination` across denominations. This lets the issuer mint quantities per denomination that don't match the declared/expected total cap, i.e. an inflation of the token's effective issuable supply relative to what wallets/observers believe the enforced cap to be — matching the "asset issuance/transfer conditions" and "supply inflation" impact categories called out in scope.

### Likelihood Explanation
Reachable by any unprivileged unit author: asset definitions are posted in ordinary units and validated through `validateAssetDefinition()`, which is invoked for every asset-definition message from any address — no special privilege, hub, or peer role required. The attacker only needs to choose numeric `count_coins`/`denomination` values that produce a float-rounding collision with a chosen `cap`; this is a pure computation the attacker can perform offline before submitting the unit.

### Recommendation
- Bound `count_coins` explicitly (e.g., `count_coins <= constants.MAX_CAP`) before it is used in any multiplication, mirroring the existing `denomination` bound.
- Perform the cap-consistency check using safe-integer arithmetic (e.g., reject if any intermediate product or running sum exceeds `Number.MAX_SAFE_INTEGER`) rather than relying on a post-hoc `===` comparison of potentially already-imprecise floating-point sums.
- Consider using `BigInt` for cap/denomination bookkeeping in `validateAssetDefinition()` and `indivisible_asset.js` to eliminate precision loss entirely.

### Proof of Concept
1. Craft an asset-definition payload with `fixed_denominations: false` (divisible, capped) and two `denominations` entries where `denomination_i <= constants.MAX_CAP` individually, but `count_coins_i` is chosen large enough (e.g., near or above `Number.MAX_SAFE_INTEGER / denomination_i`) that `count_coins_i * denomination_i` loses precision when represented as a double.
2. Compute, using standard JS double arithmetic, the resulting (rounded) `total_cap_from_denominations` value that the loop at [6](#0-5)  would produce.
3. Set `payload.cap` to that exact rounded value (not the true mathematical sum) so the equality check at [7](#0-6)  passes on every validating node.
4. Post the unit; the asset is accepted as "capped" at `payload.cap`, but the actual per-denomination `count_coins` values recorded in `asset_denominations` allow issuance amounts (via `indivisible_asset.js` `issueNextCoin`) whose true sum differs from the declared cap.

Note: I was unable to directly inspect the exact implementation of `isPositiveInteger()` in `validation_utils.js` (only its usage was returned by search, not the function body), so I cannot fully confirm whether it silently permits values beyond `Number.MAX_SAFE_INTEGER`. This should be verified against the actual source before treating the PoC as fully validated; I recommend a Devin session with full file access to confirm the precise bound (or lack thereof) enforced by `isPositiveInteger()` and to construct a concrete failing test case in `test/`.
