### Title
Cross-tenant webhook forgery via decoupled organization-verification and repository/commit-write bindings - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate an inbound GitHub webhook using an **attacker-supplied field of the same unverified payload** (`repository.owner.login`, falling back to `organization.login`), while the handlers that subsequently *act* on that payload (`StatusHandler`, `PushHandler`) key their writes off a **different, independently attacker-controlled field** (`sha` globally, or `repository.full_name`) that is never cross-checked against the organization whose secret validated the request. This breaks the same class of binding as the reported bug: "the entity that authenticated" ≠ "the entity that is written," letting an unprivileged attacker who knows (or exploits the absence of) one tenant's webhook secret forge state for a completely unrelated, higher-value stack.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/secret to check against using data taken straight out of the untrusted JSON body, before any authentication has occurred: [1](#0-0) [2](#0-1) 

`GithubApp#verify_webhook_signature` unconditionally passes verification when no `webhook_secret` is configured for that resolved organization: [3](#0-2) 

The docs explicitly document `webhook_secret` as **optional**, and multi-organization installs are a documented, supported configuration (`config/secrets.development.shopify.yml` shows two orgs side by side): [4](#0-3) 

Because `repository_owner` (used only to pick the verification key) and the fields the handlers use to locate the record to mutate are two independent, attacker-controlled strings inside the same forged body, nothing forces them to agree:
- `PushHandler`/`Handler#stacks` resolve the target purely from `payload.dig('repository','full_name')`: [5](#0-4) 
- `StatusHandler#process` resolves the target commit purely by **global SHA lookup**, with no repository/organization scoping at all: [6](#0-5) 

Concretely, the equality that should hold is:
`organization whose secret validated the request == organization owning the repository/commit being written`

but the code only enforces:
`organization named in payload.repository.owner.login (attacker-chosen) selects the secret`
`repository/commit acted upon (attacker-chosen, unrelated field) is whatever the same forged payload names`

If any organization configured on the Shipit instance has no `webhook_secret` (an explicitly supported, documented setting), an attacker with no Shipit account, no `ApiClient` token, and no GitHub repository access can send a POST to `/webhooks` naming that unsecured organization in `repository.owner.login`/`organization.login` (satisfying `verify_signature`), while placing an arbitrary `sha` (belonging to a real commit on a completely unrelated, secured stack) and `state: "success"`/matching `context` in the body of a `status` event. `StatusHandler` will create that status on the victim commit with no relation to the "authenticated" organization at all.

### Impact Explanation
Shipit stacks use commit statuses to gate deploy eligibility (`ci.require`/`ci.blocking` in `shipit.yml`, `deployable?`/CI checks logic). By forging a matching "green" CI status on a target commit belonging to a different, secured repository/stack, an unprivileged attacker can satisfy the CI-gating requirement and enable an **unauthorized deploy** of a commit that never actually passed CI — this falls squarely in the Critical impact bucket ("an unauthorized deploy"). The `PushHandler` variant of the same root cause additionally lets the attacker force `GithubSyncJob` to run against an arbitrary victim stack chosen independent of the organization that satisfied signature verification, which is a lesser but related authorization boundary violation (a stack the "authenticated" org never owns being acted upon).

### Likelihood Explanation
The precondition — at least one configured organization without a `webhook_secret` — is explicitly documented as an acceptable, optional configuration (`docs/setup.md`), not a misconfiguration outside the engine's contract, so this is reachable in legitimate deployments hosting multiple organizations (as the shipped example config itself demonstrates). No credentials, session, or GitHub write access are required — only knowledge of a target commit SHA, which is public information on GitHub. This makes the attack straightforward for any external, unprivileged actor once a low-value/no-secret org exists alongside a high-value one on the same Shipit instance.

### Recommendation
- Require every configured GitHub organization to have a non-blank `webhook_secret` and refuse to boot/serve `/webhooks` for orgs without one, rather than silently returning `true` from `verify_webhook_signature`.
- After signature verification, re-derive and enforce that the repository/commit acted upon actually belongs to the organization that was cryptographically verified (e.g., have `StatusHandler` scope its `Commit` lookup to stacks whose repository owner matches `repository_owner`/the verified org, and have `Handler#repository_name`/`stacks` validate that `repository.owner.login` is consistent with `repository.full_name`).

### Proof of Concept
1. Configure (or find) a Shipit instance with two organizations, e.g. `lowvalueorg` (no `webhook_secret`) and `secureorg` (has a `webhook_secret`), each with stacks.
2. Identify a commit SHA `S` on a `secureorg` stack that currently lacks a passing status for context `ci/required`.
3. POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "lowvalueorg" }, "full_name": "lowvalueorg/whatever" },
  "sha": "S",
  "state": "success",
  "context": "ci/required",
  "created_at": "2026-09-01T00:00:00Z"
}
```
(`X-Hub-Signature` can be any value since `lowvalueorg` has no secret.)
4. `verify_signature` resolves `Shipit.github(organization: "lowvalueorg")`, whose `verify_webhook_signature` returns `true` unconditionally. [7](#0-6) 
5. `StatusHandler#process` looks up `Commit.where(sha: "S")` — matching the `secureorg` commit regardless of the org used for verification — and creates a passing status on it, satisfying `secureorg`'s CI gate for an unauthorized deploy. [6](#0-5)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
