### Title
Webhook signature verification authenticates the organization, but push/sync handlers act on an unvalidated `repository.full_name` field — cross-organization forced sync (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
In the multi-org GitHub App configuration, `Shipit::WebhooksController#verify_signature` picks *which* webhook secret to verify the HMAC against using `repository_owner`, computed from `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`) [1](#0-0) . It then trusts the request as long as *some* configured organization's secret matches the HMAC of the raw body [2](#0-1) . However, the field actually used by the event handlers to decide **what to write** — which `Repository`/`Stack` to sync — is a separate JSON field, `repository.full_name`, read independently in `Shipit::Webhooks::Handlers::Handler#repository_name` [3](#0-2) . Nothing cross-validates that the owner segment of `repository.full_name` matches the `repository.owner.login` (or `organization.login`) that was used to select the signing key.

### Finding Description
This mirrors the double-entrypoint token bug class: verification is performed against one "address" (the org login field used to pick the `GitHubApp`/`webhook_secret`), while the state-changing action is performed against a different "address" derived from the same payload (`repository.full_name`) that is never checked for consistency with the first.

Concretely:
- `Shipit.github(organization:)` selects a `GitHubApp` instance (and thus a `webhook_secret`) purely from the attacker-controlled JSON body field `repository.owner.login` / `organization.login` [1](#0-0) [4](#0-3) .
- `verify_webhook_signature` only proves that *whoever holds the webhook secret for that named organization* produced this exact raw body [5](#0-4) .
- Once verified, `Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches to handlers such as `PushHandler`, which locate the target `Stack`s via `Repository.from_github_repo_name(repository_name)` where `repository_name` is `payload.dig('repository', 'full_name')` [6](#0-5) [3](#0-2) .

In a multi-org Shipit deployment (the schema explicitly supported and documented for "multiple Github applications for different Github organizations" [7](#0-6) ), an attacker who legitimately controls one configured organization (`OrgA`, with its own installed GitHub App and known `webhook_secret`) can:
1. Craft a JSON webhook body where `repository.owner.login` = `OrgA` (or `organization.login` = `OrgA`) but `repository.full_name` = `OrgB/victim-repo`, a stack belonging to a different organization entirely.
2. Sign this raw body with `OrgA`'s own webhook secret (which the attacker legitimately possesses, e.g. from their own GitHub App installation settings).
3. POST it to the shared `WebhooksController#create` endpoint.

`verify_signature` succeeds because the HMAC really was computed over that exact raw body with `OrgA`'s real secret — the check never inspects whether `full_name`'s owner matches `OrgA`. The handler then acts on `OrgB/victim-repo`'s `Stack`, e.g. `PushHandler` enqueues `GithubSyncJob` for the victim stack with an attacker-chosen `expected_head_sha` [6](#0-5) , and that job fetches commits/spec from the victim repository using GitHub's own credentials for that org (`stack.github_api`, derived from `Repository#github_app` keyed on the *real* stored `owner`, not from the payload) [8](#0-7)  and merges appended commits/cached deploy specs into the victim's `Stack` state [9](#0-8) .

### Impact Explanation
This breaks the binding "organization that authenticated versus the repository that is written": possession of one organization's webhook secret is treated as authorization to trigger sync/status/check-suite/pull-request processing for *any* repository/stack tracked by the Shipit instance, not just repositories under that organization. Depending on continuous-deployment configuration on the targeted stack, a forced `GithubSyncJob` run that ingests attacker-influenced commit metadata (and re-caches the deploy spec) can feed into automatic deploy triggers, meeting the "unauthorized deploy" bar for High/Critical impact. At minimum it is an unauthenticated cross-repository write into a `Stack`/`Commit` records belonging to an organization the attacker does not control.

### Likelihood Explanation
Requires the deployment to use the multi-org GitHub App configuration schema (explicitly documented and supported) and requires the attacker to control (or have compromised) the webhook secret of at least one configured organization on the same Shipit instance — a scenario the codebase treats as a normal, unprivileged tenant boundary (each org's GitHub App admin is expected to only affect their own repositories). No GitHub App private key, `GITHUB_TOKEN`, or Shipit session is needed — only the org's own `webhook_secret`, which that org's own administrators legitimately hold.

### Recommendation
After `verify_signature` succeeds, cross-validate that the organization used to select the signing key (`repository_owner`) matches the owner segment of `repository.full_name` before dispatching to handlers, e.g. reject the request if `params.dig('repository','full_name')&.split('/')&.first != repository_owner`. Alternatively, look up the `Repository`/`Stack` and enforce that its stored `owner` equals the authenticating organization before performing any write.

### Proof of Concept
1. Configure Shipit with two organizations, `orga` and `orgb`, each with its own `webhook_secret` (per the multi-org schema in `config/secrets.development.example.yml`).
2. As the `orga` administrator (attacker), compute `sig = "sha1=" + HMAC-SHA1(orga_webhook_secret, body)` for a push payload:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen sha>",
     "repository": {
       "owner": {"login": "orga"},
       "full_name": "orgb/victim-repo"
     }
   }
   ```
3. POST to `/github/webhooks` (or wherever `WebhooksController` is mounted) with header `X-Github-Event: push` and `X-Hub-Signature: sig`.
4. `verify_signature` succeeds because `Shipit.github(organization: "orga").verify_webhook_signature` correctly HMACs the raw body with `orga`'s secret [1](#0-0) .
5. `PushHandler#process` resolves `Repository.from_github_repo_name("orgb/victim-repo")` and enqueues `GithubSyncJob` for `orgb`'s stack [6](#0-5) , even though the request was authenticated solely with `orga`'s secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
