### Title
Webhook signature is verified against a GitHub organization selected from unauthenticated payload fields that are never cross-checked against the resource actually mutated - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and thus which HMAC `webhook_secret`) to validate a webhook against based on `repository_owner`, a value read straight out of the *unverified* JSON body. Once the HMAC check passes for that org, the full raw payload is handed to handlers, which independently pick the `Team`/`Repository`/`Stack` to mutate from other payload fields (`organization.login`, `repository.full_name`) that were never bound to the org whose secret validated the request.

### Finding Description
`verify_signature` computes `repository_owner` from `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0)  and uses it only to pick a `Shipit::GitHubApp` (and its `webhook_secret`) via `Shipit.github(organization: repository_owner)`, then verifies the raw body HMAC against that secret [2](#0-1) . In a multi-organization deployment, each org has its own independently configured `webhook_secret` [3](#0-2) , confirmed by `Shipit.github` selecting per-org config by name [4](#0-3) .

After this check passes, `create` re-parses the same raw body and dispatches it to handlers unmodified: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [5](#0-4) . Handlers derive the target resource from *other* fields of the same payload without re-checking they belong to the org that authenticated the request:
- `MembershipHandler` creates/updates a `Team` keyed on `params.team.id` and sets `team.organization = params.organization.login` directly from the payload, then adds/removes the named `member` from it [6](#0-5) .
- `PushHandler` locates stacks via `Repository.from_github_repo_name(repository_name)` where `repository_name = payload.dig('repository','full_name')` [7](#0-6) , and triggers `stack.sync_github(expected_head_sha: params.after)` [8](#0-7) .

Nothing in the controller or in `Handler#stacks`/`Handler#repository_name` asserts that `repository.owner.login` (used to pick the verifying secret) equals the organization that actually owns `repository.full_name`/`organization.login` used by the handler. The binding the system implicitly assumes — "the org whose secret validated this signature" == "the org/repo the handler subsequently writes to" — is never enforced as an equality check.

Team authorization is directly consumed by session authentication: `User#authorized?` checks membership in `Shipit.github_teams` [9](#0-8) , and `Shipit::Authentication#force_github_authentication` gates every engine controller on `current_user.authorized?` [10](#0-9) . `Team.add_member` is called unconditionally from the `membership` webhook handler [11](#0-10) .

### Impact Explanation
If a Shipit instance is configured with multiple GitHub Apps for multiple unrelated organizations (a documented supported configuration), an entity that legitimately controls one org's App (and thus knows that org's `webhook_secret`) can forge a `membership` webhook whose `organization.login` field names a **different**, unrelated tracked GitHub team/org, while keeping `repository.owner.login` (or omitting `repository` so the fallback `organization.login` is used for secret selection) pointed at their own org so the HMAC check passes with a secret they control. Because `MembershipHandler` trusts `params.organization.login`/`params.team` verbatim, this can add an attacker-controlled GitHub login as a member of a `Team` that is included in `Shipit.github_teams`, which is the authorization gate for the entire application (`User#authorized?`). This is a cross-organization write that escalates into `Shipit.github_teams` authorization, matching the "High" impact bucket described in the rules. A similar path exists for `push`/`status` handlers causing writes against repositories/stacks outside the org that authenticated the request.

### Likelihood Explanation
Exploitability depends entirely on the deployment running Shipit with **multiple independently-configured GitHub Apps for multiple organizations** sharing one Shipit instance and one webhook endpoint — this is a documented, supported configuration, not a misconfiguration. Within that configuration, no additional privilege beyond controlling one tenant org's App/webhook_secret is required; no repository write access, GitHub session, or Shipit credential is needed. The likelihood is bounded by how commonly the multi-org feature is used with mutually distrusting tenants, which cannot be determined from the code alone.

### Recommendation
After signature verification, re-validate that every organization/repository identifier used by a handler (`repository.owner.login`, `repository.full_name`'s owner, `organization.login`) is equal to the `repository_owner`/org whose secret validated the HMAC, and reject the webhook otherwise. Alternatively, bind the verified organization explicitly into the handler call so handlers can enforce `params.repository.owner.login == verified_organization` (and similarly for `organization.login`) before performing any find-or-create or membership mutation.

### Proof of Concept
Conceptual PoC in a multi-org configuration with orgs `attacker-org` (attacker-controlled App/secret) and `victim-org` (legitimate tenant tracked by the same Shipit instance):
1. Attacker computes `payload = {"action":"added","team":{"id":<victim_team_github_id>,"name":"Victim Admins","slug":"admins","url":"..."},"organization":{"login":"victim-org"},"member":{"login":"attacker-github-login"}}`.
2. Attacker sets `X-Github-Event: membership` and computes `X-Hub-Signature` using `attacker-org`'s `webhook_secret` (which they legitimately possess).
3. `repository_owner` falls back to `params.dig('organization','login')` = `"victim-org"` only if `repository` is absent — to force selection of `attacker-org`'s secret instead, the attacker instead sets `repository.owner.login = "attacker-org"` while keeping `organization.login = "victim-org"` (both fields independently controlled in the JSON body), so `verify_signature` calls `Shipit.github(organization: "attacker-org")` and validates successfully against the attacker's known secret.
4. `MembershipHandler#process` then creates/updates the `victim-org` `Team` (keyed by `params.team.id`) and adds `attacker-github-login` as a member via `team.add_member(member)`.
5. If that `Team` is part of `Shipit.github_teams`, the attacker's Shipit `User` record now satisfies `User#authorized?`, bypassing the intended organization-scoped access control. [12](#0-11) [13](#0-12)

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class MembershipHandler < Handler
        params do
          requires :action, String
          requires :team do
            requires :id, Integer
            requires :name, String
            requires :slug, String
            requires :url, String
          end
          requires :organization do
            requires :login, String
          end
          requires :member do
            requires :login, String
          end
        end
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
      end
    end
  end
end

      if current_user.logged_in? && current_user.requires_fresh_login?

      end
    end
