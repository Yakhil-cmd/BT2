Based on the CVE's bug class — an internal assertion/invariant that's assumed to always hold, but which a crafted edge-case input can violate, causing an unhandled crash instead of a graceful rejection — I found a directly analogous pattern in `ocore`'s payment validation logic.

### Title
Unhandled `throw Error` on stable temp-bad input causes node crash / consensus halt during payment validation - (File: validation.js)

### Summary
In `validatePaymentInputsAndOutputs()`, when validating a `transfer` input, the code assumes that once a source output's unit is stable (`main_chain_index <= last_ball_mci`), its `sequence` can only be `'good'` or `'final-bad'` — `'temp-bad'` is treated as an impossible state and handled by an unconditional `throw Error(...)` instead of a graceful validation rejection, unlike the sibling `'final-bad'` case just below it which is handled safely via `return cb(...)`.

### Finding Description [1](#0-0) 

```
var src_output = rows[0];
var bStableInParents = (src_output.main_chain_index !== null && src_output.main_chain_index <= objValidationState.last_ball_mci);
if (bStableInParents) {
    if (src_output.sequence === 'temp-bad')
        throw Error("spending a stable temp-bad output " + input.unit);
    if (src_output.sequence === 'final-bad')
        return cb("spending a stable final-bad output " + input.unit);
}
```
This is the exact bug class of CVE-2021-40083: an edge-case combination of otherwise-valid conditions (here: a stable output whose sequence resolution has not converged to `good`/`final-bad`) that the developers believed could never occur, hard-coded as a fatal assertion (`throw Error`) rather than a recoverable validation error. Any code path that reaches `checkForDoublespends`/`findStableConflictingUnits` also contains a similarly-labeled "unreachable code" assertion at [2](#0-1)  confirming the developers' own uncertainty about these invariants holding under all DAG/fork conditions. `input.unit`, `input.message_index`, and `input.output_index` in the crafted payment input come directly from an attacker-controlled unit's payload and are used unmodified to look up `src_output` [3](#0-2) , so the attacker fully controls which prior output is referenced.

The `sequence` field for a unit only transitions out of `'temp-bad'` during main-chain stabilization in `handleNonserialUnits()`, which resolves it to `'good'` or `'final-bad'` based on `findStableConflictingUnits` at the moment its MCI stabilizes [4](#0-3) . If any DAG/fork ordering or timing edge-case causes a unit's `main_chain_index` to be set (making it "stable in parents") before/without its `sequence` being resolved away from `'temp-bad'` — analogous to the NSEC3 iteration-count edge case bypassing an assumed-safe code path — the validator hits the `throw`.

### Impact Explanation
An uncaught `throw Error` inside this async DB callback in Node.js is not caught by any try/catch in the call chain of `validate()`, resulting in an unhandled exception that crashes the node process. Since this code executes for every full node validating a normally-submitted payment unit, a successfully crafted edge-case unit would crash any full node (including witnesses) that attempts to validate it, preventing that node from confirming any further units — directly matching "a network unable to confirm new units" if propagated broadly, or causing divergent node behavior (nodes that crash vs. nodes that don't see the unit) which threatens consensus availability.

### Likelihood Explanation
This requires constructing a specific DAG state where a spent output's containing unit is stable in the new unit's parents while retaining `sequence='temp-bad'` — a state the developers explicitly believed to be unreachable (see the parallel "unreachable code" comment elsewhere in the same function). Reaching it likely requires a carefully engineered set of conflicting/nonserial units and specific fork/stabilization timing, similar in spirit to the "NSEC3 with too many iterations" edge case that only manifests under an unusual but attacker-reachable combination of inputs. This makes exploitation non-trivial but not clearly impossible, since it depends purely on unit/DAG structure fully controllable by an unprivileged poster, not on any privileged or trusted role.

### Recommendation
Replace the `throw Error("spending a stable temp-bad output ...")` with a graceful validation rejection (`return cb(...)`), consistent with how the neighboring `'final-bad'` case is already handled, so that any occurrence of this state — whether truly unreachable or the result of an as-yet-undiscovered edge case — results in unit rejection rather than a process crash. Additionally, audit other "should never happen" `throw Error` assertions reachable from attacker-supplied unit content within `validation.js` (e.g. lines 2450, 2476, 1688) for the same treat-as-fatal-instead-of-reject pattern.

### Proof of Concept
1. An attacker constructs a set of units that creates a nonserial/conflicting spend at some address such that one competing unit is initially marked `sequence='temp-bad'`.
2. Through carefully timed unit submission and parent selection, the attacker gets this `temp-bad` unit's `main_chain_index` assigned (making it stable in the new unit's future parents) in a window before/without stabilization's `handleNonserialUnits` resolving its `sequence` away from `'temp-bad'`.
3. The attacker then posts a new payment unit whose `parent_units` make this `temp-bad`-but-stable unit an ancestor, and whose payment input transfers from an output of that unit.
4. When any full node validates this new unit, `validatePaymentInputsAndOutputs` reaches the `bStableInParents && src_output.sequence === 'temp-bad'` branch and throws, crashing the validating node process.
