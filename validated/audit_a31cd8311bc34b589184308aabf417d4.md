### Title
CCMenu API endpoint resolves `stack_id` param without enforcing the stack scope bound to the authenticating `ApiClient` token - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
The bug class in the external report is "value assumed vs. value actually used" — a scalar (`_amount`) is trusted for downstream accounting instead of being re-derived from what actually happened after an intermediary operation (the token transfer). The reachable analog in this engine is a binding mismatch between "the stack a token authorises" and "the stack it touches": `Shipit::Api::BaseController` derives the accessible stack set from the authenticated `ApiClient`'s `stack_id` scope, but `Shipit::Api::CCMenuController` overrides that binding and resolves the stack directly from the request parameter, ignoring the client's scope entirely.

### Finding Description
`Shipit::Api::BaseController#stacks` restricts the queryable stack set to the one the `ApiClient` is scoped to when `stack_id` is set on the token: [1](#0-0) 

Every other API controller (e.g. `Shipit::Api::StacksController#stack`) resolves the target stack through this scoped `stacks` relation: [2](#0-1) 

`Shipit::Api::CCMenuController`, however, overrides `#stack` to bypass the scoped relation and query `Stack.from_param!(params[:stack_id])` directly against all stacks in the installation: [3](#0-2) 

The controller still declares `require_permission :read, :stack`, but that check only verifies the token carries the string permission `"read:stack"` — it says nothing about *which* stack: [4](#0-3) 

So the equality the engine is supposed to preserve is: `stack authorized by token.stack_id == stack acted upon by request.stack_id`. In `CCMenuController` this becomes `stack authorized by token.stack_id != stack acted upon by request.stack_id` because the `stack_id`-scoping step from `BaseController#stacks` is skipped.

This is reachable unauthenticated-relative-to-other-stacks because the CCMenu token is deliberately handed out to third parties (CI dashboard tools) via `CCMenuUrlController`, which mints a scoped, low-privilege, read-only `ApiClient` and embeds its token in a URL: [5](#0-4) 

### Impact Explanation
A holder of one stack's CCMenu token can substitute any other stack's `stack_id` in the URL and receive that other stack's deploy/build status/output (name, last build status, last build time, activity) via `Shipit::Api::CCMenuController#show`, which is an unauthenticated read of stack state that the token was never authorized to see: [6](#0-5) 

This matches the "High" bucket in this engine's threat model: escalation into reading stack state/deploy output beyond what the token's `stack_id` scope authorizes.

### Likelihood Explanation
CCMenu tokens are routinely distributed to unprivileged parties/tools embedded in a bare URL (no basic auth header, `token` query param is the sole credential), and the `stack_id` segment of that URL is fully attacker-controlled (`scope '/stacks/*stack_id' ... get '/ccmenu' => 'ccmenu#show'`): [7](#0-6) 
No further capability beyond possessing one such token is required, and swapping the path segment is trivial.

### Recommendation
Have `CCMenuController#stack` use the same `stacks` scoping helper defined in `BaseController` (i.e. `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so the `ApiClient#stack_id` binding established at authentication time is actually enforced when resolving which stack's data to render.

### Proof of Concept
1. Stack A's maintainer visits `CCMenuUrlController#fetch` for Stack A; this creates (or reuses) an `ApiClient` with `permissions: ["read:stack"]` and (per intended design) scoped to Stack A, returning a URL like `/ccmenu/orgA/repoA/production?token=<TOKEN_A>`.
2. An attacker who obtains `TOKEN_A` (e.g. from a shared CI dashboard configuration) sends `GET /api/stacks/orgB/repoB/production/ccmenu?token=<TOKEN_A>`.
3. `CCMenuController#authenticate_api_client` authenticates `TOKEN_A` successfully via `ApiClient.authenticate`.
4. `require_permission :read, :stack` passes because `TOKEN_A` does carry `"read:stack"`.
5. `CCMenuController#stack` resolves `Stack.from_param!("orgB/repoB/production")` directly, ignoring that `TOKEN_A` is meant to be confined to Stack A, and returns Stack B's deploy status/build info in the XML response — an unauthorized cross-stack read of task/deploy state through a token that should only authorize Stack A.
