### Title
Missing cosigner authorization check in wallet "sign" hub-message handler allows any paired device to request signing of arbitrary spends from a shared/multisig address - (File: wallet.js)

### Summary
The `handleMessageFromHub` `"sign"` case in `wallet.js` resolves the address via `findAddress()` and, in the `ifLocal` branch, is supposed to verify that the device sending the `sign` request (`from_address`) is actually a registered cosigner of the wallet/address before surfacing a signing-confirmation event to the user. That check is explicitly commented out. [1](#0-0) 

### Finding Description
`findAddress(body.address, body.signing_path, ...)` only verifies that `body.address` (combined with `body.signing_path`) corresponds to one of the wallet's own local addresses/signing paths - it does not verify that the message sender (`from_address`) is one of the wallet's registered cosigners. [2](#0-1) 

Inside the `ifLocal` callback, the code that would enforce this ("sender is not cosigner of this address") is commented out, with the note "the commented check would make multilateral signing impossible": [3](#0-2) 

As a result, once the check is skipped, the handler immediately calls `callbacks.ifOk()` and unconditionally emits a `signing_request` event containing the caller-supplied unsigned unit (`objUnit`), address, and `from_address` — for *any* address and signing path the caller claims, as long as `findAddress` resolves it locally: [4](#0-3) 

This means any device that is merely paired/correspondent with the victim wallet (not necessarily a cosigner of the specific shared/multisig address in question) — or even any device address the sender can spoof via `handleMessageFromHub`'s `device_pubkey`-derived `from_address` — can trigger a signing request for one of the victim's own addresses by supplying:
- `body.address`: any address the victim controls (addresses are frequently exposed publicly once used on the DAG, or leaked in chat/shared payment flows),
- `body.signing_path`: a guessable/discoverable path such as `"r"` for singlesig, or `"r.0"`/`"r.1"` etc. for common multisig layouts,
- `unsigned_unit`: an attacker-crafted unit that spends the victim's funds to attacker-controlled outputs.

Because `findAddress` walks nested `shared_address_signing_paths`, this reaches not just single-key addresses but *shared/multisig addresses* as well — i.e., an unrelated correspondent device (not one of the actual cosigners of that shared address) can still cause the victim's wallet to raise a `signing_request` for a cosigner's key on that shared address, since the missing check would have been the only place validating "is `from_address` actually one of the cosigners for this address."

### Impact Explanation
This is a privilege-management gap: knowledge of a resource identifier (the address + signing path) is sufficient to invoke a privileged operation (soliciting a signature over an arbitrary unit) that should be restricted to actual cosigners/wallet members. Impact is bounded by the fact that the emitted `signing_request` event is intended to drive a UI confirmation dialog for a human to approve/reject — but:
- The dialog is populated using attacker-controlled `objUnit`/`from_address` data, and any automated or semi-automated signer service (e.g., unattended multisig cosigner bots, arbiter/hub-style services) that reacts to `signing_request` without independently re-validating cosigner status is directly exposed to unauthorized-spend authorization requests.
- Because the authorization gap is at the protocol-handler layer (not the UI layer), any downstream consumer of `signing_request` that trusts `from_address` as "a legitimate cosigner" (which is exactly what the removed check would have guaranteed) inherits the vulnerability.

This matches the CWE-269 pattern in the reference advisory: a privileged action (signing on behalf of a wallet) is reachable by supplying a known/guessable resource ID (address, path) without proof of membership in the authorized group (wallet cosigners).

### Likelihood Explanation
Likelihood is Medium: it requires (1) being an existing correspondent/paired device of the victim (a low bar — pairing is common for chat, shared wallets, textcoin, arbiter contracts, etc.), and (2) knowing/guessing the target address and its signing path, both of which are often derivable from prior interactions (shared address setup messages, on-chain activity, or common path conventions like `"r"`, `"r.0"`, `"r.1"`). No cryptographic secret is required to trigger the flow to the point of event emission — the missing check is exactly the one gate that would have stopped it.

### Recommendation
Restore and enforce the cosigner-authorization check before emitting `signing_request` in the `"sign"` case: query `extended_pubkeys` (for BIP44 wallets) or `shared_address_signing_paths` (for shared addresses) to confirm `from_address` is actually associated with the wallet/address and signing_path resolved by `findAddress`, and reject with `callbacks.ifError("sender is not cosigner of this address")` if not. If multilateral/dumb-contract signing legitimately requires accepting requests from non-cosigner devices for specific message-signing use cases, that exception should be scoped narrowly (e.g., only for `signed_message` requests explicitly tied to a contract flow) rather than removing the check for all "sign" requests including full unit/payment signing.

### Proof of Concept
1. Device A pairs with Device B (victim), a normal correspondent relationship (no shared wallet needed).
2. Device A learns one of Device B's addresses `X` (e.g., from a prior chat/payment or from on-chain activity) and assumes/guesses a signing path, e.g., `"r"`.
3. Device A sends a `handleMessageFromHub` message with `subject: "sign"` and body:
   ```json
   {
     "address": "X",
     "signing_path": "r",
     "unsigned_unit": { "authors": [{ "address": "X" }], "messages": [ /* payment spending X's funds to attacker address */ ] }
   }
   ```
4. On Device B, `findAddress("X", "r", ...)` resolves `ifLocal` since `X` is Device B's own address (or a shared address it participates in).
5. Because the cosigner-authorization check is commented out, Device B's wallet unconditionally calls `callbacks.ifOk()` and emits `signing_request` for the attacker-supplied unit, entering it into the signing/confirmation pipeline as if Device A were a legitimate party to a multisig signing session — even though Device A has no relationship to that specific address's cosigner set beyond being an unrelated paired correspondent.
