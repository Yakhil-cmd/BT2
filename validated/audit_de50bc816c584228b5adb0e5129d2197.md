### Title
Missing signer/ownership check in `InitializeBuffer` allows front-running to hijack buffer authority and steal deposited lamports - ([File: programs/bpf_loader/src/lib.rs])

### Summary
The `UpgradeableLoaderInstruction::InitializeBuffer` handler in Agave's BPF Loader Upgradeable program sets the buffer account's authority to whatever pubkey is passed as instruction account index 1, without requiring that pubkey (or the buffer account itself) to be a signer of the transaction. This mirrors the reported bug class: an "initialize" call that anyone can race to call first, letting an attacker seize control of an account before its intended owner does.

### Finding Description
`process_loader_upgradeable_instruction` handles `InitializeBuffer` as follows: [1](#0-0) 

The only checks performed are: (1) at least 2 accounts are supplied, and (2) the account's current state is `Uninitialized`. There is no `is_instruction_account_signer` check on either the buffer account (index 0) or the authority account (index 1). A buffer account is typically created by a legitimate deployer with `system_instruction::create_account` (funding it with rent-exempt lamports and setting its owner to `bpf_loader_upgradeable`) in one transaction, followed by a separate `InitializeBuffer` transaction to set the authority. Because the buffer pubkey is public as soon as the account-creation transaction is broadcast (or even beforehand, if derived deterministically), any unprivileged actor watching the mempool can submit their own `InitializeBuffer` instruction naming themselves as `authority_address`, and if it lands first, the legitimate `InitializeBuffer` call will fail with `AccountAlreadyInitialized`: [2](#0-1) 

Once the attacker is the recorded buffer authority, they can immediately call `UpgradeableLoaderInstruction::Close` on the buffer. The `Close` handler drains the buffer's lamports to a recipient chosen by the caller, provided the recorded authority signs: [3](#0-2) 

Since `common_close_account` validates only that the recorded `authority_address` (now the attacker's key) signs — not the original account creator/funder — the attacker can redirect the rent-exempt lamports that the victim deposited when creating the buffer account to any address of the attacker's choosing.

### Impact Explanation
This allows an unprivileged transaction sender to perform unsigned fund movement: lamports funded by the legitimate deployer into a buffer account can be stolen by an attacker who wins a front-running race on `InitializeBuffer`, without the victim ever signing away control. This satisfies the "concrete unsigned fund movement" acceptance criterion — the victim's rent deposit is drained to an attacker-controlled account they never authorized.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to observe a `CreateAccount` (for the buffer) + `InitializeBuffer` transaction pair in the mempool and successfully land a competing `InitializeBuffer` transaction with a higher priority fee/earlier slot before the legitimate one executes. This is a standard mempool front-running scenario reachable by any unprivileged sender with no special access, consistent with the reported bug class (front-running an unauthenticated "initialize" call).

### Recommendation
Add a signer requirement tying account creation to initialization, e.g.:
- Require the buffer account (index 0) to be a signer of `InitializeBuffer` (since it must have been a signer during its `CreateAccount`), so only the original creator can initialize it, or
- Perform account creation and `InitializeBuffer` atomically within the same transaction (which most tooling already does), and additionally require the payer/creator to co-sign the initialization so a racer cannot claim authority over an account they didn't create.

### Proof of Concept
1. Victim submits `system_instruction::create_account(payer, buffer_pubkey, lamports, size, bpf_loader_upgradeable::id())` followed (in a later transaction) by `InitializeBuffer` naming `victim_authority` as authority.
2. Attacker observes the pending/landed `CreateAccount` transaction (buffer_pubkey is now owned by `bpf_loader_upgradeable`, state `Uninitialized`) and submits their own `InitializeBuffer` instruction for `buffer_pubkey`, naming `attacker_pubkey` as `authority_address`, with a higher fee so it lands first — see the check at [4](#0-3) , which contains no signer requirement.
3. Victim's `InitializeBuffer` now fails with `AccountAlreadyInitialized`.
4. Attacker submits `UpgradeableLoaderInstruction::Close` with `attacker_pubkey` as the signer-authority and an attacker-controlled recipient account, per the flow at [3](#0-2) , draining the buffer's rent-exempt lamports (originally funded by the victim) to the attacker.
