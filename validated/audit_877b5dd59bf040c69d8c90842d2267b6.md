### Title
Stack-scoped API tokens can read the CI status of any stack via CCMenuController - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` re-implements its own `stack` and `authenticate_api_client` methods instead of reusing `Api::BaseController`'s scoped helpers, so a `read:stack`-permissioned `ApiClient` token that is scoped to one specific `Stack` (its `stack_id` column set) can be used to fetch the CCMenu/CI status of *any* stack in the installation, not just the one it was issued for.

### Finding Description
`Api::BaseController` defines the resource-scoping binding that every other API controller relies on: [1](#0-0) 

`stacks` restricts the visible set of stacks to `current_api_client.stack_id` when the client is stack-scoped, and `stack` resolves the requested resource only from that restricted scope (`stacks.from_param!`). This is the binding: **the stack a token authorizes == the stack the resource lookup touches**.

`Api::CCMenuController`, however, overrides both halves of this binding: [2](#0-1) 

- `stack` is redefined to call `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` model, bypassing `current_api_client.stack_id` entirely.
- `authenticate_api_client` is redefined to accept the token via a `token` query-string parameter (for CCTray/CCMenu client compatibility) but still authenticates through the normal `ApiClient.authenticate` path, producing a fully scoped `ApiClient` object — the scoping information is simply never consulted afterward.
- `require_permission :read, :stack` only checks that the token's `permissions` array contains `read:stack`; it performs no per-object authorization against `params[:stack_id]`.

So a token created with `stack_id` set to Stack A (the intended, narrow scope granted by a maintainer, e.g., via `ApiClient.create_with(permissions: %w[read:stack])` as used by `CCMenuUrlController`) still authenticates successfully and, because `CCMenuController#stack` ignores `current_api_client.stack_id`, can be handed `params[:stack_id]` for Stack B and will render Stack B's CI/build status.

This is exactly the "token authorizes stack A / code touches stack B" binding break: the equality `current_api_client.stack_id == stack.id` that `BaseController#stack` enforces for every other endpoint is not enforced here.

### Impact Explanation
This satisfies the High-impact bucket of "unauthenticated/unauthorized read of stack state" for stacks outside the token's authorized scope: an unprivileged holder of a legitimately-issued, narrowly-scoped `read:stack` token (e.g., a CCMenu URL generated for one project and shared with a third party, per `CCMenuUrlController`) gains read access to build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `activity`, `webUrl`) of every stack in the Shipit installation, including stacks whose visibility the operator explicitly intended to restrict via stack-scoped tokens. It does not grant write access or credential exfiltration, but it is a concrete confidentiality boundary break driven purely by the attacker supplying a different `stack_id` query parameter — no additional secrets, sessions, or GitHub access are required.

### Likelihood Explanation
Likelihood is high for anyone already holding any stack-scoped `read:stack` token (these tokens are explicitly designed to be shared externally — `CCMenuUrlController` builds shareable CCMenu URLs with the token embedded in the query string). No other credential, guessing, or timing is required: the attacker only needs to change the `stack_id` route parameter to any other stack's identifier, which are predictable (`owner/repo/environment` slugs, easily discoverable or enumerable).

### Recommendation
Make `Api::CCMenuController#stack` honor scoping the same way `BaseController` does, e.g. `stacks.from_param!(params[:stack_id])` instead of `Stack.from_param!(params[:stack_id])`, so a stack-scoped `ApiClient` cannot resolve a stack outside `current_api_client.stack_id`.

### Proof of Concept
1. As a Shipit admin/user, generate a CCMenu URL for Stack A via `GET /stacks/:stack_a_param/ccmenu_url` — this creates (or reuses) an `ApiClient` with `permissions: ['read:stack']` and `stack_id = StackA.id`, and returns a URL like `.../api/stacks/owner/repoA/env/ccmenu.xml?token=<TOKEN>`.
2. Share the resulting URL/token as intended (e.g., embed in a CI dashboard).
3. An attacker who has that `TOKEN` (by design, meant only for Stack A) requests:
   `GET /api/stacks/owner/repoB/env/ccmenu.xml?token=<TOKEN>`
   where `owner/repoB/env` is any other stack in the same Shipit instance.
4. `authenticate_api_client` authenticates the token successfully (`ApiClient.authenticate(params[:token])` succeeds regardless of which stack it's scoped to).
5. `require_permission :read, :stack` passes because the token has `read:stack` in `permissions`.
6. `stack` resolves via `Stack.from_param!(params[:stack_id])` = Stack B, bypassing the `current_api_client.stack_id == StackA.id` restriction.
7. The response renders Stack B's CI/build status (`lastBuildStatus`, etc.), which the token was never authorized to see.

# frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
  end
end
