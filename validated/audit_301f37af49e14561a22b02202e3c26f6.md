### Title
Webhook signature is verified against `repository.owner.login`, but the stack/action is resolved from the unrelated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App/secret used to validate the inbound webhook HMAC based on `repository.owner.login` (or `organization.login`), a field taken straight from the attacker-controllable JSON body. Once the signature "passes," every `Shipit::Webhooks::Handlers::Handler` subclass resolves the actual `Repository`/`Stack` to act on using a *different* field from the same body, `repository.full_name`. Nothing enforces that these two fields refer to the same organization, so the binding "organization that authenticated" `==` "repository that gets written to" is never checked.

### Finding Description
`verify_signature` selects the GitHub App config purely from body content: [1](#0-0) 

`repository_owner` is defined as: [2](#0-1) 

The signature is checked with `GitHubApp#verify_webhook_signature`, which validates the raw body HMAC against the `webhook_secret` configured for whichever organization `repository_owner` names — and explicitly no-ops when that organization has no secret configured: [3](#0-2) 

Shipit's own documentation shows that `webhook_secret` can legitimately be left unset for any given organization in a multi-org deployment (`config/secrets.development.example.yml` / `docs/setup.md`, "Using Multiple Github Applications"), and each organization is configured independently: [4](#0-3) 

Once `verify_signature` passes, `WebhooksController#create` dispatches the *entire same payload* to the event handlers: [5](#0-4) 

Every handler resolves which `Stack`s to mutate not from `repository.owner.login` (the field used for signing) but from `repository.full_name`: [6](#0-5) 

For example, `PushHandler` uses that repository/stack resolution to trigger a sync with an attacker-supplied target SHA: [7](#0-6) 

Because `repository.owner.login` and `repository.full_name` are two independent JSON fields in the same request body, and only the former is used to pick the verification secret while only the latter is used to pick the target stack, an attacker can craft a body where these fields disagree. If any organization configured in `Shipit.github` has `webhook_secret` unset (a documented, supported configuration), `verify_webhook_signature` returns `true` unconditionally for requests naming that organization — regardless of the `X-Hub-Signature` header — while the handler still acts on whatever `repository.full_name` the attacker put in the body, which can name a stack belonging to a completely different, properly-secured organization.

### Impact Explanation
This breaks the binding: `organization authenticated by verify_signature` should equal `organization owning the repository the handler mutates`. With the mismatch, an unauthenticated caller of the public `/webhooks` endpoint can:
- Force `PushHandler` to invoke `stack.sync_github(expected_head_sha: <attacker chosen sha>)` on stacks belonging to an organization the attacker never authenticated against, potentially triggering a `GithubSyncJob`/continuous-deployment pipeline on that stack.
- Similarly drive `StatusHandler`, `CheckSuiteHandler`, or the `pull_request/*` handlers against commits/stacks under an org they were never authorized for, since none of these handlers re-check that `repository.full_name`'s owner matches the organization used for signature verification.

This can escalate to an unauthorized deploy/rollback trigger on stacks belonging to organizations that were never the ones "authenticating" the request, which matches the High-impact category of "unauthorized deploy, rollback" via a broken authentication/authorization binding.

### Likelihood Explanation
Exploitation requires only that the multi-organization configuration documented in `docs/setup.md` is used and that at least one configured organization has `webhook_secret` left blank (explicitly supported: `webhook_secret: # nil`). No `ApiClient` token, Shipit session, or knowledge of any organization's real webhook secret is required — the attacker only needs to know the *name* of an org with no secret configured and the `full_name` of a target repository/stack tracked by the same Shipit instance, both of which are discoverable/public information. This is a design gap in `WebhooksController` and `Handler#repository_name`, not a misuse of credentials.

### Recommendation
Bind webhook authentication to the same repository field the handlers act on: after computing `repository_owner` for secret selection, verify that it matches the owner segment of `params.dig('repository', 'full_name')` (and vice versa for the `organization.login` fallback) before dispatching to handlers, rejecting the request with 422 on mismatch. Additionally, consider disallowing/warning on organizations configured with a blank `webhook_secret` in multi-org deployments, since that config silently disables signature verification for that organization's name-space entirely.

### Proof of Concept
1. Deploy Shipit configured for multiple GitHub organizations per `docs/setup.md`, where org `unsecured-org` is registered with Shipit but has `webhook_secret` left blank, and org `victim-org` (with `victim-org/target-repo` tracked as a Shipit stack) has a properly configured secret.
2. POST directly to `/webhooks` with headers `X-Github-Event: push` and no valid `X-Hub-Signature` (or any arbitrary value), and body:
```json
{
  "repository": { "owner": { "login": "unsecured-org" }, "full_name": "victim-org/target-repo" },
  "ref": "refs/heads/main",
  "after": "<attacker chosen commit sha that exists on victim-org/target-repo>"
}
```
3. `verify_signature` calls `Shipit.github(organization: "unsecured-org")`, whose `verify_webhook_signature` returns `true` unconditionally because `webhook_secret` is blank.
4. `PushHandler` resolves `stacks` from `payload.dig('repository','full_name')` = `"victim-org/target-repo"` and calls `stack.sync_github(expected_head_sha: "<attacker chosen sha>")` on the victim's stack, despite the request never having been authenticated for `victim-org`.

Note: I could not fully trace `Stack#sync_github` / `GithubSyncJob` in this session to confirm the exact downstream effect (e.g., whether it can directly trigger an automatic deploy versus only re-fetching commit history), so the precise severity of the resulting state change (info sync vs. triggered deploy) should be confirmed by a maintainer before scoring.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
