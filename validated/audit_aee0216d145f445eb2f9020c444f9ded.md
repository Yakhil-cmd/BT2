### Title
Unchecked integer multiplication in asset denomination cap validation allows supply-cap bypass / inflation - (File: validation.js)

### Summary
`validateAssetDefinition()` in `validation.js` sums `count_coins * denomination` for every entry of an attacker-controlled `denominations` array to derive `total_cap_from_denominations`, which is then compared against the asset's stated `cap`. `denomination` is bounded by `constants.MAX_CAP`, but `count_coins` is only checked with `isPositiveInteger()` and has **no upper bound**. This mirrors the GPAC `sbgp` bug class (CVE-2021-21841): an attacker-controlled count field is multiplied without an overflow/precision check and the result is trusted to gate a downstream allocation/issuance decision. [1](#0-0) 

### Finding Description
When defining a new asset, the `denominations` array is fully attacker-controlled (single-authored `asset` message): [2](#0-1) 

Only `denomInfo.denomination` is explicitly capped against `constants.MAX_CAP`: [3](#0-2) 

`denomInfo.count_coins` is validated only as `isPositiveInteger`, with no ceiling: [1](#0-0) 

Because JavaScript numbers are IEEE-754 doubles, `count_coins * denomination` (and its running sum `total_cap_from_denominations`) can be crafted to exceed `Number.MAX_SAFE_INTEGER` (2^53). Beyond this threshold, integer multiplication/addition silently loses precision (analogous to unchecked integer overflow in the GPAC C code), yet the result is still used verbatim in the equality check: [4](#0-3) 

Because the attacker also supplies `cap` in the same message, they can pick `count_coins`/`denomination` pairs whose "true" product differs from the intended value by exactly the amount lost to floating-point rounding, while the rounded product still equals the declared `cap`. The same multiplication is later used at issuance time, so the number of coins actually issuable for a denomination is derived from the same unbounded `count_coins` field, e.g. in `indivisible_asset.js`: [5](#0-4) 

and `asset_denominations` rows are persisted straight from the unchecked `count_coins`/`denomination` values in `writer.js`: [6](#0-5) 

### Impact Explanation
This lets an asset issuer construct a "capped" asset definition whose declared `cap` passes validation while the real, precision-corrected product of `count_coins * denomination` is different from what other nodes/clients compute when performing arithmetic at slightly different times or precisions (e.g. displaying/verifying total supply, or accumulating totals across multiple denominations near the 2^53 boundary). This is a supply-inflation class issue for a user-issued asset: nodes can end up disagreeing on whether the total capped supply matches the declared cap, and the issuer can mint more value than the nominal cap implies without ever failing the `payload.cap !== total_cap_from_denominations` check. This falls under "asset issuance and transfer conditions" and can result in "supply inflation" as defined in scope.

### Likelihood Explanation
Exploitability requires crafting `denominations` entries with very large `count_coins` values (still passing `isPositiveInteger`) so that the accumulated `total_cap_from_denominations` crosses the safe-integer boundary. Composing and posting an `asset` message with arbitrary `denominations`/`cap` fields is fully reachable by any unprivileged unit poster/asset issuer — no special privileges are required, matching the "unprivileged... asset issuer" reachability requirement. The main constraint is finding a combination where the double-precision rounding of the sum coincides exactly with the attacker-chosen `cap`, which is a solvable but non-trivial numeric search (there is no cryptographic obstacle, only careful selection of `count_coins`/`denomination` values).

### Recommendation
- Impose an explicit upper bound on `count_coins` (e.g., `count_coins <= constants.MAX_CAP`) in `validation.js`, mirroring the bound already applied to `denomination`.
- Perform the `count_coins * denomination` multiplication and the running sum using a safe-integer/BigInt arithmetic path, and explicitly reject any denomination or cumulative cap value that would exceed `Number.MAX_SAFE_INTEGER` before comparing to `payload.cap`.
- Apply the same bound checks at issuance time in `indivisible_asset.js`'s `issueNextCoin`, since it re-derives `issue_amount = count_coins_to_issue * denomination` from the same untrusted, persisted values.

### Proof of Concept
1. Attacker composes an `asset` message with `fixed_denominations: true`, `cap: <target>`, and a `denominations` array containing entries such as `{denomination: d1, count_coins: c1}`, `{denomination: d2, count_coins: c2}`, where `c1`, `c2` are chosen (via brute-force/binary search) so that:
   - each `di <= constants.MAX_CAP` and `ci` is a positive integer (both pass individual field checks),
   - the naive/expected sum `Σ(ci*di)` (computed exactly, e.g. with BigInt) differs from IEEE-754 double-precision result of `total_cap_from_denominations` computed by `validation.js`,
   - the double-precision result equals the attacker's declared `cap`, so the check at `validation.js:2790` passes.
2. The asset is accepted and its `asset_denominations` rows are written verbatim via `writer.js:236-242`.
3. During indivisible coin issuance (`indivisible_asset.js:516-536`), `issue_amount = count_coins_to_issue * denomination` is computed from the same oversized `count_coins`, allowing the issuer to mint coin batches whose true value diverges from the nominally validated `cap`, producing an asset supply inconsistent with what other nodes/clients believe was capped.
