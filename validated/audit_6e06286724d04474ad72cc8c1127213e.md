### Title
Webhook signature verified against organization-selected secret while handlers act on the unbound `repository.full_name` in the same payload - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification based on `repository.owner.login` (or `organization.login`) read straight out of the untrusted JSON body, then authenticates the request against that organization's `webhook_secret`. Every downstream event handler, however, resolves *which* `Stack`/`Repository`/`Commit` to mutate using a completely different field of the same body: `repository.full_name` (via `Shipit::Webhooks::Handlers::Handler#repository_name` / `#stacks`). Nothing binds these two fields together. In a multi-organization Shipit deployment (as documented by `test/dummy/config/secrets_double_github_app.yml`, each org has its own independent `webhook_secret`), an actor who legitimately controls the webhook secret for organization A can sign an arbitrary payload whose `repository.full_name` points at organization B's repository, and the controller will accept it as authentic.

### Finding Description
- `app/controllers/shipit/webhooks_controller.rb` `verify_signature` (lines 24-49) computes `repository_owner` from `params.dig('repository','owner','login') || params.dig('organization','login')`, looks up `github_app = Shipit.github(organization: repository_owner)`, and calls `github_app.verify_webhook_signature(signature, raw_post)`. [1](#0-0) [2](#0-1) 
- `Shipit.github(organization:)` / `Shipit.github_app_config(organization)` look up a per-organization `webhook_secret` from `secrets.github[organization]`, confirming that in the multi-org schema each organization owns its own independent HMAC secret. [3](#0-2) 
- `lib/shipit/github_app.rb#verify_webhook_signature` does a straightforward HMAC-SHA1 compare of the *entire raw body* against that organization's secret — it proves who signed the bytes, not that the content inside those bytes legitimately belongs to that organization. [4](#0-3) 
- Once verification passes, `WebhooksController#create` dispatches the parsed JSON to every registered handler for the event, e.g. `PushHandler`, `StatusHandler`, `CheckSuiteHandler`. [5](#0-4) 
- All handlers derive their target `Repository`/`Stack`/`Commit` from `payload.dig('repository', 'full_name')`, a completely separate field from the one used for authentication: [6](#0-5) [7](#0-6) [8](#0-7) 

This is the same bug class as the reported Vyper issue: a value that codegen/authorization implicitly assumes is bound/constant (here, "the org whose secret signed this request equals the org whose repo is being mutated") is never actually checked, so a downstream consumer (the handler dispatch) operates on attacker-controlled data that bypassed the intended trust boundary. The broken equality is: `organization authenticated (repository.owner.login used to pick the HMAC secret)` ≠ `repository actually written (repository.full_name used by handlers)`.

### Impact Explanation
An organization admin who legitimately owns a GitHub App/webhook secret configured on this Shipit instance for **their own** organization can forge a signed webhook whose `repository.full_name` names a **different** onboarded organization's repository. Depending on event type this allows:
- `push` → forces `GithubSyncJob`/`Stack#sync_github` to run against the victim org's stack with an attacker-chosen `expected_head_sha`, potentially triggering unintended sync/CacheDeploySpecJob activity on a repository the attacker was never authorized to touch.
- `status` → injects/forges arbitrary commit statuses (`Commit#create_status_from_github!`) for commits belonging to the victim organization's repositories, which can flip CI/merge-gating logic used to decide whether a pull request is safe to merge or deploy.
- `check_suite` → similarly forces `RefreshCheckRunsJob` against the victim's stacks.

This is a cross-organization write across a trust boundary that the signature check was supposed to enforce, satisfying the "cross-repository writes" / unauthorized-deploy-adjacent impact criteria in a multi-tenant Shipit installation.

### Likelihood Explanation
This requires the target Shipit instance to be configured with the multi-organization GitHub App schema (multiple orgs, each with its own `webhook_secret`), which is a supported and documented configuration (`test/dummy/config/secrets_double_github_app.yml`). Given that setup, any org onboarded to the shared instance can exploit this without needing any Shipit session, API token, or access to the victim org — only knowledge of their own org's webhook secret, which they legitimately possess. This is a realistic scenario for shared/multi-tenant Shipit deployments.

### Recommendation
Bind the field used to select the verification secret to the field used for handler dispatch: after selecting `github_app` by `repository_owner`, verify that `params.dig('repository','full_name')` (or its owner) actually belongs to the same organization used to pick the secret before invoking handlers — e.g., reject/require `repository.full_name.split('/').first.casecmp?(repository_owner)`. Alternatively, when using the multi-org schema, verify webhook signatures against the org derived from the *same* namespace that handlers use to resolve repositories, and fail closed if they diverge.

### Proof of Concept
1. Shipit is configured with multiple GitHub orgs, e.g. `OrgAttacker` (webhook_secret `S_A`) and `OrgVictim` (webhook_secret `S_V`), per `secrets_double_github_app.yml`.
2. Attacker, who administers `OrgAttacker`'s GitHub App and thus knows `S_A`, crafts a `push` (or `status`) webhook body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "full_name": "OrgVictim/victim-repo",
    "owner": { "login": "OrgAttacker" }
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(S_A, raw_body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner = "OrgAttacker"`, fetches `Shipit.github(organization: "OrgAttacker")`, and successfully verifies the HMAC (attacker signed with their own known secret) — request passes.
5. `PushHandler#process` (or `StatusHandler`) resolves the target repository/stack using `repository.full_name = "OrgVictim/victim-repo"`, and performs `stack.sync_github(...)` / creates a commit status on a repository belonging to `OrgVictim`, which the attacker never authenticated for.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
