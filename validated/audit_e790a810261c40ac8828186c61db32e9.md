### Title
Cross-stack authorization bypass in CCMenu API — stack-scoped `ApiClient` token can read status of any stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::BaseController` restricts which `Stack` an `ApiClient` may act on by intersecting the requested `stack_id` param with the set of stacks the authenticated token is bound to, but `Shipit::Api::CCMenuController` overrides the `stack` lookup with an unscoped `Stack.from_param!` call, breaking that binding.

### Finding Description
`Shipit::ApiClient` records can be scoped to a single stack via the `stack_id` column, and `BaseController#stacks` enforces this scoping for every controller that inherits from it: [1](#0-0) 

`ApiClient` itself only checks coarse-grained permission strings (e.g. `read:stack`) and never checks which specific stack is being accessed — that check is entirely delegated to callers using `stacks`/`stack`: [2](#0-1) 

`CCMenuController`, however, overrides `stack` to bypass this scoping entirely, resolving the requested stack from the full `Stack` relation instead of the token-restricted `stacks` relation, while still relying on the same coarse `require_permission :read, :stack` check: [3](#0-2) 

The binding that should hold is:
`stack_id`(s) the `ApiClient` token authorizes == `stack_id` the request actually touches.

Before the request: a token created (e.g. via `ApiClient.create_with(stack: stack_a, permissions: %w[read:stack])`) is meant to only ever resolve `stack_a` in any controller inheriting `BaseController#stack`.

After the request to `CCMenuController#show`: because `stack` is redefined as `Stack.from_param!(params[:stack_id])`, the same token can be presented with an arbitrary `:stack_id` in the URL/route and will successfully resolve and render CI/deploy status for `stack_b`, `stack_c`, etc. — stacks the token was never authorized for.

### Impact Explanation
This is a stack-authorization-scope escalation: an `ApiClient` deliberately restricted to a single stack (a legitimate, lower-privilege credential) can be used to read the deploy/CI status (`deploys_and_rollbacks`, running state, latest deploy id) of any other stack in the installation, including private/internal ones the token owner should have no visibility into. This matches the "unauthenticated/under-scoped read of stack state or deploy output" class of High-impact findings, since the authorization boundary that should gate visibility per-stack is completely skipped for this endpoint while every sibling endpoint (`Api::StacksController`, `Api::DeploysController`, etc.) correctly enforces it via `stacks`/`stack` from `BaseController`.

### Likelihood Explanation
Any holder of a stack-scoped `ApiClient` token with the `read:stack` permission (the CCMenu feature's own intended use case) can trivially exploit this by simply changing the `stack_id` segment of the CCMenu URL — no additional privileges, brute forcing, or race conditions are required, since `Stack.from_param!` accepts a publicly guessable/enumerable identifier.

### Recommendation
Remove the `stack` override in `Shipit::Api::CCMenuController` and rely on the inherited `BaseController#stack`/`stacks` methods so the lookup is always scoped to `current_api_client.stack_id` (when set), consistent with every other API controller.

### Proof of Concept
1. As an admin, create two stacks, `stack_a` and `stack_b`.
2. Create (or note the existing programmatic support for) an `ApiClient` scoped to `stack_a` only: `ApiClient.create!(creator: user, name: 'ccmenu', stack: stack_a, permissions: %w[read:stack])`.
3. Using that client's `authentication_token` as the `token` query param, request `GET /api/stacks/<stack_b_id>/ccmenu.xml`.
4. Observe the response renders `stack_b`'s deploy/CI status via `CCMenuController#show`, even though the token is scoped to `stack_a` and would be rejected by `stacks.from_param!` in any other API controller. [4](#0-3) [1](#0-0)

# frozen_string_literal: true

module Shipit
  class ApiClient < Record
    InsufficientPermission = Class.new(StandardError)

    belongs_to :creator, class_name: 'User'
    belongs_to :stack, optional: true

    validates :creator, :name, presence: true

    serialize :permissions, coder: Shipit.serialized_column(:permissions, type: Array)
    PERMISSIONS = %w[
      read:stack
      write:stack
      deploy:stack
      lock:stack
      read:hook
      write:hook
    ].freeze
    validates :permissions, subset: { of: PERMISSIONS }

    class << self
      def authenticate(token)
        find_by(id: message_verifier.verify(token).to_i)
      rescue Shipit::SimpleMessageVerifier::InvalidSignature
      end

      def message_verifier
        @message_verifier ||= Shipit::SimpleMessageVerifier.new(Shipit.api_clients_secret)
      end
    end

    def authentication_token
      self.class.message_verifier.generate(id)
    end

    def check_permissions!(operation, scope)
      required_permission = "#{operation}:#{scope}"
      unless permissions.include?(required_permission)
        raise InsufficientPermission, "This operation requires the `#{required_permission}` permission"
      end

      true
    end
  end
end

# frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
  end
end
