### Title
Unbounded loop over dust asset outputs in `aa_composer.js` `completePaymentPayload` leads to DoS of AA payment/response composition - (File: aa_composer.js)

### Summary
`AA composer`'s `sendUnit` → `completePaymentPayload` builds the payment message for an Autonomous Agent (AA) response by fetching *all* unspent outputs held by the AA's address and looping over them with `iterateUnspentOutputs`. For custom (non-base) assets, the SQL query that fetches these outputs applies **no minimum-amount / dust filter**, unlike the base-byte case which explicitly filters out outputs smaller than `FULL_TRANSFER_INPUT_SIZE` to prevent exactly this class of attack. Any unprivileged user can send an AA address an unbounded number of dust-sized outputs of a custom asset, and when the AA later composes a "send-all" payment in that asset (a common oscript pattern), the loop is forced to iterate over every single dust output without early termination, since the `continue` branch (not `break`) is taken for `send_all_output`.

### Finding Description
In `completePaymentPayload`, `readStableOutputs` builds the query that supplies rows to `iterateUnspentOutputs`: [1](#0-0) 

Note the dust-avoidance comment and filter `AND amount>=" + FULL_TRANSFER_INPUT_SIZE` only apply when `asset` is falsy (base bytes). When `asset` is set, the `WHERE` clause is simply `asset="+conn.escape(asset)` with **no amount threshold at all**, so every unspent output of that asset at the address, no matter how small, is returned. The same lack of filtering exists in `readUnstableOutputsSentByAAs`: [2](#0-1) 

`iterateUnspentOutputs` then loops over these rows, pushing every consumed output into `payload.inputs`/`arrConsumedOutputs`: [3](#0-2) 

Critically, when a `send_all_output` is present (i.e., the AA payload contains an output like `{address: X}` with no `amount`, meaning "send everything"), the loop deliberately does **not** break early once the target is reached — it `continue`s instead, forcing it to consume every single row returned by the unbounded query:
```
if (total_amount === target_amount && payload.outputs.length > 0) {
    bFound = true;
    if (send_all_output)
        continue;
    else
        break;
}
``` [4](#0-3) 

The call sites confirm both stable and unstable output sets are iterated with no cap: [5](#0-4) 

Any user can trivially create an arbitrarily large number of tiny (e.g., amount=1) outputs of some asset addressed to a target AA (e.g., by issuing a custom divisible asset and sending thousands of 1-unit outputs to the AA's address, or by repeatedly triggering the AA itself to pay tiny asset amounts back to itself/attacker-controlled state). This is directly analogous to the reported `BountyCore.getLockedFunds` issue, where an attacker floods a target contract's per-address collection (deposits there, unspent outputs here) with many low-value entries to force an unbounded loop in code that a legitimate, unprivileged operation (`refundDeposit` there, an AA's "send-all" payment response here) must execute in full.

### Impact Explanation
Because AA trigger handling is a consensus-critical, deterministic computation performed independently by every full node when processing a unit that triggers the AA, an attacker-inflated set of dust asset outputs forces every node evaluating that AA's response to perform the same expensive, unbounded loop and build an oversized `payload.inputs`/`arrConsumedOutputs` array in memory. This can:
- Significantly slow down or stall AA response composition on every full node processing the trigger unit, delaying confirmation/stability of the DAG around that AA.
- Cause the resulting payment message to exceed `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE` at validation/write time, making the AA's legitimate "send-all" response impossible to construct, effectively freezing the AA's ability to return funds of that asset to users (a fund-freezing DoS analogous to the `DepositManagerV1.refundDeposit` DoS in the source report).
- Because this executes deterministically on all nodes, it degrades network-wide processing rather than a single victim contract, matching the "network unable to confirm new units" / "AA fund loss or freezing" impact classes.

### Likelihood Explanation
Likelihood is high: creating many tiny asset outputs is cheap (bounded only by normal per-unit fees, and issuance/transfer of a self-issued asset is unrestricted to any user) and requires no special privileges — just posting ordinary payment units to the target AA's address, which is exactly the class of "unprivileged unit poster" / "AA trigger sender" reachable path this scan targets. Any AA that has a "send-all" (bounce/refund-all) payment pattern for a custom asset is exposed.

### Recommendation
Apply the same dust-avoidance filtering used for base-byte outputs to asset outputs in `readStableOutputs` and `readUnstableOutputsSentByAAs` (e.g., require `amount` to exceed some minimum viable threshold relative to the per-input storage/fee cost for that asset), and/or cap the number of rows fetched/iterated (similar to the `LIMIT constants.MAX_INPUTS_PER_PAYMENT_MESSAGE-2` bound already used in `inputs.js`'s `pickMultipleCoinsAndContinue`), so that an attacker cannot force unbounded iteration over externally-created dust outputs during AA response composition.

### Proof of Concept
1. Attacker issues a custom divisible asset (or otherwise obtains an asset that a target AA holds/handles) and sends N (e.g., 50,000) individual outputs of amount=1 of that asset to the AA's address across many transactions — since only bytes are dust-filtered, this passes.
2. A legitimate user triggers the AA in a way that causes it to compose a "send-all" payment message in that asset (e.g., `payment[[asset=...]]{outputs: [{address: recipient}]}` with no amount), a common bounce/withdraw-all oscript pattern.
3. `completePaymentPayload`'s `readStableOutputs` query returns all N dust outputs with no filtering (`aa_composer.js:1140-1155`), and `iterateUnspentOutputs` must process every one of them because the `send_all_output` branch takes `continue` instead of `break` (`aa_composer.js:1117-1123`), building an inputs array of size N.
4. This consumes proportional CPU/memory on every full node evaluating the trigger, and if N exceeds `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE`, unit validation subsequently rejects the composed payment, permanently preventing the AA from executing its "send-all" response for that asset.
