### Title
Unchecked `Currency::transfer()` result via `debug_assert!` in `claim_child_bounty` allows silent payout loss - (File: substrate/frame/child-bounties/src/lib.rs)

### Summary
`pallet-child-bounties::claim_child_bounty` performs two `T::Currency::transfer()` calls (curator fee and beneficiary payout) and only validates their outcome with `debug_assert!(...is_ok())`, a macro that is a no-op in production (non-`debug_assertions`) builds. If either transfer fails, the pallet nevertheless emits the `Claimed` event, decrements the active child-bounty counter, and deletes the child-bounty record — permanently losing the on-chain accounting link to the funds that never actually moved, exactly the "protocol assumes success while the transfer silently failed" pattern described in the ERC20 report.

`debug_assert!` compiles to nothing when `debug_assertions` is disabled — which is the default for `--release` runtime builds used in production nodes. Unlike the OpenZeppelin `SafeERC20`-style fix recommended in the source report (verify success, revert on failure), this code path has no fallback: it neither uses `?` to propagate the `DispatchResult`, nor uses `.defensive()`/`ensure!` to hard-fail the extrinsic. The subsequent state mutations (event emission, `ParentChildBounties` decrement, `ChildBounties` removal) execute unconditionally regardless of whether the transfer actually succeeded.

`Currency::transfer` (the classic `frame_support::traits::Currency` trait implemented by `pallet-balances`) can return `Err` in ordinary, non-privileged conditions — most notably when the destination account does not yet exist and the transferred amount is below the `ExistentialDeposit`, causing the deposit path to reject the transfer (`Token(BelowMinimum)`/underflow-style errors), a condition fully reachable by a normal payout: e.g., a `payout` smaller than `ExistentialDeposit` sent to a beneficiary account that has never held a balance.

### Impact Explanation
When the payout (or curator fee) transfer silently fails:
- The `Claimed` event falsely reports that `beneficiary` received `payout`.
- The child bounty record is deleted, so there is no future extrinsic path to retry or reclaim the funds through the normal child-bounty payout flow.
- The funds remain stranded in the child-bounty sub-account, effectively lost from the perspective of the intended recipient, while governance bookkeeping (`ParentChildBounties` counters, description removal) proceeds as if payment succeeded.

This is a fund-loss/integrity-break condition reachable by any signed account interacting with a completed, awarded child bounty — no privileged role or governance action required to trigger it, only a payout amount/recipient-existence combination that fails silently.

### Likelihood Explanation
The condition is not exotic: any child bounty whose final payout to a previously-unfunded beneficiary account is smaller than the chain's `ExistentialDeposit` will trip this path deterministically in a production build. Curators/bounty proposers do not need to be malicious; this can occur organically for small child bounties, and is entirely within the normal claim flow reachable by the beneficiary or any signed caller of `claim_child_bounty`.

### Recommendation
Replace the `debug_assert!` checks with proper error propagation, mirroring the ERC20 report's `safeTransferFrom` recommendation:
```rust
let fee_transfer_result = T::Currency::transfer(&child_bounty_account, curator, curator_fee, AllowDeath)?;
let payout_transfer_result = T::Currency::transfer(&child_bounty_account, beneficiary, payout, AllowDeath)?;
```
or explicitly handle failure (e.g., abort the claim, keep the child bounty in `PendingPayout`) instead of assuming success and deleting state that backs the payout guarantee.
