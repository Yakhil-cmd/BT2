### Title
Webhook signature is verified against the org derived from an unverified field while the acted-upon repository comes from a different unverified field, allowing cross-repository webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to check the HMAC signature against by reading `repository.owner.login` (or `organization.login`) straight out of the untrusted JSON body, **before** the signature has been validated. The event handlers, however, resolve the actual `Stack`/`Repository` to act on from a *different* field of the same untrusted body: `repository.full_name` (`app/models/shipit/webhooks/handlers/handler.rb`). Because Shipit supports multiple GitHub Apps keyed by organization (`Shipit.github(organization:)`, `TOP_LEVEL_GH_KEYS` in `lib/shipit.rb`), an attacker who legitimately knows the `webhook_secret` for *one* onboarded organization can forge a signature that is valid for that org, while setting `repository.full_name` to point at a stack belonging to a completely different organization/repository tracked by the same Shipit instance.

### Finding Description

- Shipit explicitly supports multiple independent GitHub Apps/organizations, each with its own `webhook_secret`, selected purely by an organization name: `TOP_LEVEL_GH_KEYS = [:app_id, :installation_id, :webhook_secret, :private_key, :oauth, :domain]` and `Shipit.github(organization: ...)` (confirmed by the multi-org fixture `test/dummy/config/secrets_double_github_app.yml` and `test/unit/shipit_test.rb`'s `.github uses indifferent access to search through the Github applications`). **The binding that is broken:** `organization authenticated (repository.owner.login used to pick webhook_secret) == organization/repository actually written (repository.full_name used to pick the Stack)`. These two values are read from two independent, attacker-controlled JSON fields in the same raw body, and nothing enforces they refer to the same repository/organization. An attacker who is an admin of "attacker-org" (a legitimate, separate organization onboarded on the same shared Shipit instance, with a webhook_secret they know because they configured their own GitHub App's webhook) can HMAC-sign a payload with their own secret while setting `repository.full_name` (and other event-specific fields) to `victim-org/victim-repo`.

Because `verify_signature` calls `Shipit.github(organization: repository_owner)` using `repository.owner.login` (which the attacker also fully controls and can independently set to `"attacker-org"`), the signature check passes using the attacker's own known secret, even though the payload's `repository.full_name` targets an entirely different, victim-owned stack.

### Impact Explanation
This breaks a deployment-trust boundary: cross-repository writes without possessing the victim organization's `webhook_secret`. Concretely, with a forged but "verified" webhook an attacker can:
- Trigger `PushHandler` to make Shipit `sync_github` a victim stack using an attacker-chosen `after` SHA (`app/models/shipit/webhooks/handlers/push_handler.rb`), potentially advancing/altering the "undeployed commits" state used to decide what gets shipped. [4](#0-3) 
- Trigger `StatusHandler` to inject arbitrary commit statuses for a victim's commits (`create_status_from_github!`), which downstream Shipit merge/deploy safety checks may rely on to decide whether a commit is deployable or mergeable. [5](#0-4) 
- Drive `pull_request` handlers (open/close/label/merge related) against a victim repository/stack.

This matches the "Critical - cross-repository writes" impact category defined for this engine: an unprivileged-relative-to-the-victim-org attacker (who is merely a legitimate participant of a different, unrelated org on the same shared Shipit instance) can manipulate deploy-relevant state (commit statuses, sync state) for a repository they have no GitHub permissions on.

### Likelihood Explanation
Requires the attacker to control (or know) the `webhook_secret` of *some* organization already configured in the same Shipit deployment's `secrets.yml`/GitHub App config — plausible in any shared/multi-tenant Shipit instance where webhook secrets are set up per-org by different, mutually-untrusted org admins, which is exactly the scenario the multi-app support (`TOP_LEVEL_GH_KEYS`, `Shipit.github(organization:)`) is built for. No GitHub write access, Shipit session, or `ApiClient` token is needed — only knowledge of one org's webhook secret, and the ability to send an HTTP request to the public `/webhooks` endpoint (unauthenticated, only signature-protected: `WebhooksController < ActionController::Base` with `skip_before_action :verify_authenticity_token`). This is a realistic, non-social-engineering, non-DoS credential/binding mismatch.

### Recommendation
Verify that the field used to select the signing organization is the same field used to resolve the target repository/stack, or better, always require the two to match: after computing `repository_owner`, also check that `payload.dig('repository', 'full_name')&.split('/')&.first` (or the equivalent org portion) equals `repository_owner`/the GitHub App's own organization before dispatching to handlers, rejecting (422) any mismatch. Alternatively, resolve the target stack/repository strictly through the same organization context that was validated by `Shipit.github(organization: ...)`, never trusting a second, independently-controlled field from the same unauthenticated payload.

### Proof of Concept
1. Shipit is configured with (at least) two organizations, e.g. `attacker-org` (with `webhook_secret = S_attacker`, known to the attacker who set up their own GitHub App per `docs/setup.md`) and `victim-org` (tracked stack `victim-org/victim-repo`, secret unknown to attacker).
2. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(S_attacker, raw_body)` using their own known secret.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")` (from `repository.owner.login`) and successfully verifies the signature against `S_attacker`.
5. `WebhooksController#create` then dispatches to `PushHandler`, which resolves `repository_name` from `repository.full_name` = `"victim-org/victim-repo"` and calls `stack.sync_github(expected_head_sha: params.after)` on the victim's stack — a repository the attacker's secret was never meant to authorize actions on.

This root cause and PoC are supported by the code paths cited above; I could not run the Ruby test suite to empirically confirm end-to-end behavior in this sandbox (no execution/terminal access), so the exploit is demonstrated via static code-path analysis rather than a runtime trace.
