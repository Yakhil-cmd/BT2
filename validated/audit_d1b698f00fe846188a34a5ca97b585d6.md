## Title
Webhook signature verification is keyed on `repository.owner.login` while all event handlers act on the independent `repository.full_name` field, allowing cross-organization webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and therefore which HMAC secret) to validate an incoming webhook against using `repository_owner`, derived from the attacker-supplied JSON body field `repository.owner.login`. However, every webhook handler (`Shipit::Webhooks::Handlers::Handler#repository_name` and all its subclasses) resolves the target `Repository`/`Stack` to mutate using a *different*, independently-controlled JSON field: `repository.full_name`. Nothing ties these two fields together, so an attacker can pick which org's trust context is used to authenticate the request while directing the resulting writes at a repository belonging to a different, victim organization.

### Finding Description
`verify_signature` picks the GitHub App config to verify against based on the payload itself: [1](#0-0) [2](#0-1) 

`repository_owner` reads `params.dig('repository', 'owner', 'login')` — an attacker-controlled string in the raw JSON body. This determines which `Shipit.github(organization:)` config (and its `webhook_secret`) is used to compute the expected HMAC in `GitHubApp#verify_webhook_signature`: [3](#0-2) 

Critically, if `webhook_secret` is blank/unset for the chosen organization (a documented, supported, optional configuration — see multi-org example `test/dummy/config/secrets_double_github_app.yml` and `docs/setup.md` "Webhook secret (optional)"), `verify_webhook_signature` returns `true` unconditionally, with **no signature check performed at all**.

Once verification passes, `WebhooksController#create` dispatches the *entire unverified* JSON body to handlers: [4](#0-3) 

Every handler resolves the repository/stack to act on via `repository.full_name`, a field completely independent of `repository.owner.login`: [5](#0-4) [6](#0-5) 

Repository lookup does a raw split-and-lookup with no correlation back to the org used for authentication: [7](#0-6) 

Because `repository.owner.login` and `repository.full_name` are two separate keys in the same JSON object, an attacker forging a webhook can set `repository.owner.login` to an organization that is configured with **no** `webhook_secret` (or one whose secret they otherwise know) while setting `repository.full_name` to `"<victim-org>/<victim-repo>"`. The `verify_signature` before_action authenticates the request against the weak/absent-secret org and passes, but the handler that actually executes (`PushHandler`, `PullRequest::*Handler`, `StatusHandler`, `CheckSuiteHandler`, `MembershipHandler`) performs writes against the victim org's `Stack`/`Repository`/`PullRequest` records, since it never re-checks that `full_name`'s owner segment matches the org used to authenticate.

The binding broken: **organization authenticated (`repository.owner.login`, verified via HMAC) ≠ repository actually written (`repository.full_name`, used unauthenticated by every handler)**. This is a direct code-level analog of the reported "missing proof validation" bug class — the verification step covers a smaller set of fields than what downstream logic trusts and acts upon.

### Impact Explanation
This allows an unprivileged external attacker (no Shipit session, no GitHub write access to the victim org) to trigger unauthorized deploys/rollback syncs (`PushHandler` → `stack.sync_github`), forge commit statuses (`StatusHandler`), forge/mutate check suite state (`CheckSuiteHandler`), and archive/unarchive/create review stacks for pull requests belonging to a repository they do not own (`PullRequest::*Handler`), as long as the Shipit instance also has an organization configured with no (or a leaked) webhook secret. This matches the Critical/High criteria of "cross-repository writes" / "unauthorized deploy or rollback."

### Likelihood Explanation
The precondition (a multi-organization Shipit deployment where at least one configured organization has no `webhook_secret`) is explicitly supported and documented as optional (`docs/setup.md`, `config/secrets.development.example.yml`, `test/dummy/config/secrets_double_github_app.yml`), so this is not an unsupported configuration. Any operator following the documented "optional" guidance for one org exposes every other configured organization's repositories to forged webhooks. The attack itself requires only crafting and POSTing a JSON body to the public `/webhooks` endpoint — no credentials, tokens, or GitHub access needed.

### Recommendation
Bind webhook signature verification to the same field used for repository resolution. Either:
1. Derive the org used for signature verification from `repository.full_name`'s owner segment instead of (or in addition to, with an equality check against) `repository.owner.login`, or
2. After identifying the target `Repository` in a handler, assert that its `owner` matches the organization that was used to successfully verify the webhook signature, rejecting the event otherwise.
Additionally, consider making `webhook_secret` mandatory (reject unsigned/unconfigured orgs by default) rather than silently returning `true` when unset.

### Proof of Concept
Given a Shipit instance configured with two orgs, `OrgOne` (no `webhook_secret` set) and `OrgTwo` (real target with stacks), an attacker sends:
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=anything (or omitted)

{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "OrgOne" },
    "full_name": "OrgTwo/victim-repo"
  }
}
```
`verify_signature` resolves `repository_owner` = `"OrgOne"`, loads `Shipit.github(organization: "OrgOne")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` without checking the signature at all. `PushHandler#process` then resolves `stacks` via `Repository.from_github_repo_name("OrgTwo/victim-repo")` and calls `stack.sync_github(expected_head_sha: params.after)` on the victim org's real stack — an unauthorized, unsigned trigger of a GitHub sync/deploy pipeline for a repository the attacker does not control.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
