### Title
Cross-organization forgery of commit statuses via unscoped `StatusHandler` bypasses per-organization webhook signature binding - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate an incoming webhook using the organization named inside the request body itself (`repository.owner.login`, falling back to `organization.login`), not any securely-established identity of the sender. Any actor who legitimately knows the webhook secret for *one* GitHub organization configured in this Shipit instance can set that organization's name in the payload to pass signature verification, while putting an arbitrary, unrelated commit `sha` in the `status` event body. `StatusHandler#process` then applies that status to `Commit.where(sha: params.sha)` — a query with **no repository or organization scoping whatsoever** — so it will match and mutate commits belonging to completely different organizations/stacks tracked by the same Shipit instance.

### Finding Description
`WebhooksController#verify_signature` computes `repository_owner` from the untrusted payload (`params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`) and uses it purely to pick which organization's `webhook_secret` to validate the signature against: [7](#0-6) 

Once the signature check passes, `WebhooksController#create` dispatches the entire parsed JSON body to the registered handler for the event type without any further binding between the verified organization and the data being acted upon: [8](#0-7) 

`StatusHandler`, which handles GitHub `status` events, only requires `sha`/`state`/etc. — it never requires or checks a `repository` field, and resolves the target purely by commit SHA across the entire `Commit` table: [9](#0-8) 

This breaks the equality the engine is supposed to enforce: **organization authenticated by the signature check == organization whose data is written**. Here, the organization used to select the webhook secret (org A, whatever the attacker puts in `repository.owner.login`) is completely decoupled from the actual data mutated (any commit, in any stack, of any organization configured in this Shipit instance, as long as the SHA happens to match). A legitimate administrator of organization A's own GitHub App/webhook configuration (who therefore knows organization A's `webhook_secret` from Shipit's per-organization GitHub config, `Shipit.github(organization:)` / `github_app_config`) can forge a `status` webhook whose signature is valid for org A, but whose `sha` targets a commit belonging to organization B's stack.

Applying a forged `success` status is not inert: `Commit#create_status_from_github!` → `Commit#add_status` calls `stack.schedule_merges` on any transition to `pending`/`success` [3](#0-2) , and `Status#schedule_continuous_delivery` fires `commit.schedule_continuous_delivery` on every new `Status` record [4](#0-3) . `ProcessMergeRequestsJob` will merge any pending merge request once `all_status_checks_passed?` [5](#0-4) , and `Deploy#schedule_continuous_delivery` triggers `ContinuousDeliveryJob` for stacks with `continuous_deployment?` enabled [6](#0-5) .

### Impact Explanation
This crosses the organizational trust boundary the webhook signature is meant to enforce, resulting in an unauthorized merge or unauthorized deploy on a repository/organization the attacker does not control — one of the explicitly listed Critical impacts. An attacker who is a legitimate admin of any single organization onboarded to this Shipit instance can inject fabricated CI success statuses for commits belonging to any other tracked organization/stack, causing merge queues to advance and continuous-deployment stacks to deploy commits that never actually passed CI in their real organization.

### Likelihood Explanation
The only prerequisite is knowledge of the webhook secret for one organization already configured in the Shipit instance (`secrets.github[<org>][:webhook_secret]`), which the owner/admin of that organization inherently possesses (they configure it when wiring up their org's webhook to Shipit). No access to the victim organization, no Shipit session, and no `ApiClient` token is required — matching the "unprivileged-attacker" scope of this analysis, since the privilege used (control of one's own org's webhook secret) grants no inherent authority over a different organization's repositories in Shipit.

### Recommendation
Bind the verified organization to the resource being mutated: require and validate that `repository.full_name` (or the commit's actual stack/repository) belongs to the same organization that was used to select the webhook secret in `verify_signature`, and reject the event otherwise. `StatusHandler` (and any handler resolving records purely by SHA, like `Commit.where(sha: params.sha)`) must scope the query to `Repository.from_github_repo_name(repository.full_name)`'s stacks, consistent with how `Handler#stacks` already does, and that repository's owner must match the signature-verified `repository_owner`.

### Proof of Concept
1. Shipit is configured with (at least) two organizations, `org-a` and `org-b`, each with its own GitHub App/webhook secret in `secrets.github`.
2. Attacker is a legitimate admin of `org-a` and therefore knows `org-a`'s webhook secret (as configured for their own GitHub organization's webhook delivery to Shipit).
3. Attacker crafts a `status` event JSON body:
   ```json
   {
     "sha": "<sha of a commit belonging to org-b's stack>",
     "state": "success",
     "context": "ci/fake",
     "repository": { "owner": { "login": "org-a" } }
   }
   ```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(org-a secret, raw_body)>` and POSTs to `/github/webhooks` with `X-Github-Event: status`.
5. `verify_signature` resolves `repository_owner` as `org-a`, validates successfully against `org-a`'s secret [10](#0-9) .
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the org-b commit, and calls `create_status_from_github!`, marking it `success` [11](#0-10) .
7. If org-b's stack has `continuous_deployment: true` or pending merge requests awaiting green CI, `ContinuousDeliveryJob`/`ProcessMergeRequestsJob` proceed to deploy/merge based on the forged status, entirely outside org-b's control.
