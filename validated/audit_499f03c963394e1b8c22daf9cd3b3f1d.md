### Title
Webhook signature check is a no-op when no `webhook_secret` is configured, letting an unauthenticated attacker forge GitHub events - ([File: lib/shipit/github_app.rb])

### Summary
`GitHubApp#verify_webhook_signature` unconditionally returns `true` when no `webhook_secret` is configured for the organization, so `WebhooksController#verify_signature` treats every inbound POST to `/webhooks` as an authentic GitHub delivery even though nothing about the request was actually verified. [1](#0-0) 

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App configuration keyed on the *unauthenticated* `repository_owner` field parsed straight out of the JSON body, then asks that app to verify the HMAC signature of the raw payload. [2](#0-1) 

The verification itself is implemented as:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [1](#0-0) 

`webhook_secret` is documented as an *optional* setting (`Webhook secret (optional)`, `webhook_secret: # nil`), so the engine explicitly supports deployments/organizations that omit it. [3](#0-2) [4](#0-3) 

When `webhook_secret` is blank for the organization matching the attacker-supplied `repository.owner.login` / `organization.login` field, `verified` is always `true`, and `create` dispatches the entire attacker-controlled JSON body to every registered handler for the `X-Github-Event` the attacker chooses: [5](#0-4) 

This breaks the binding: **"payload accepted as an authentic GitHub event" == "payload whose HMAC was verified against a secret shared only with GitHub."** With no secret configured, the left side is always true while the right side never happens — the entire payload is "acted on" without ever being covered by a signature, exactly the same class of missing-restriction as the GatewayVault `redirects[i]=j` bug, where index `i`'s state is unconditionally trusted/mutated based on an unchecked mapping.

The consequences are handler-dependent but severe:
- `PushHandler` triggers `stack.sync_github(expected_head_sha:)` for any repo full_name the attacker names, using data the attacker fully controls. [6](#0-5) 
- `Handler#stacks`/`repository_name` resolve the target purely from the unauthenticated `repository.full_name` field of the forged body. [7](#0-6) 
- The `membership` event handler creates/attaches `Team`/`User` records from forged payloads (confirmed by existing tests exercising this path), which feeds directly into `User#authorized?`, the gate that decides whether a signed-in GitHub identity is allowed to use Shipit at all. [8](#0-7) [9](#0-8) 
- The `status` handler writes a `Status` record for a commit directly from forged payload fields (`state`, `context`, `target_url`), which is the same data Shipit's `ci.require` deploy gate consults to decide whether a commit is "green." [10](#0-9) 

### Impact Explanation
An attacker with **no Shipit session, no ApiClient token, and no GitHub credentials** can, for any organization configured without a `webhook_secret`, inject arbitrary `push`, `status`, `check_suite`, `membership`, or `pull_request` events. This can (a) forge passing CI statuses on malicious commits, defeating the `ci.require` safety check that gates deploys, and (b) forge `membership` events that grant the attacker's own GitHub-authenticated `User` record membership in a `Shipit.github_teams`-recognized team, escalating them into the application's authorization boundary. Both map to the report's explicitly in-scope High/Critical impact classes ("escalation into `Shipit.github_teams` authorization," "an unauthorized deploy").

### Likelihood Explanation
Requires only that the deployer leave `webhook_secret` unset — an officially documented, supported configuration (`docs/setup.md` lists it as "optional," and the shipped example secrets template ships it as `nil`). No credential, session, or token of any kind is needed to exploit it once that (default-friendly) configuration exists.

### Recommendation
Fail closed instead of failing open: when `webhook_secret` is blank, `verify_webhook_signature` should reject the request (or the app should refuse to boot/register the webhooks route) rather than returning `true`. At minimum, require a webhook secret to be configured for any organization capable of receiving webhooks, and never treat "no secret configured" as "request is verified."

### Proof of Concept
1. Configure (or find) a Shipit organization entry with `webhook_secret: nil` (an example is shipped as `test/dummy/config/secrets.test.json`, which sets `"webhook_secret": null`). [11](#0-10) 
2. `POST /webhooks` with header `X-Github-Event: status`, body:
```json
{
  "sha": "<malicious-sha>",
  "state": "success",
  "context": "ci/required-check",
  "branches": [{"name": "main"}],
  "repository": {"owner": {"login": "<that-org>"}}
}
```
No `X-Hub-Signature` header is required — `verify_webhook_signature` returns `true` unconditionally because `webhook_secret` is blank. [12](#0-11) 
3. The forged "success" status is persisted against `<malicious-sha>`, satisfying `ci.require` for that commit despite no real CI run ever occurring.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
