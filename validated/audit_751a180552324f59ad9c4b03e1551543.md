### Title
Cross-organization webhook signature scoping allows forging commit statuses for any repository, enabling unauthorized merges/deploys - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController` verifies the `X-Hub-Signature` against the webhook secret of the organization named *inside the payload itself* (`repository.owner.login`, falling back to `organization.login`), but the `StatusHandler` that then processes the `status` event never re-checks that the commit being updated actually belongs to that organization/repository. It matches purely on `sha` across the entire installation. This breaks the intended binding "organization that authenticated == repository being written."

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/secret used to validate the HMAC based on a field read out of the *unverified* JSON body before verification occurs: [1](#0-0) [2](#0-1) 

`repository_owner` is computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` — an attacker fully controls this field. If an attacker's own organization has the Shipit GitHub App/integration installed (a legitimate, unprivileged use case supported by this multi-tenant engine, see `Shipit.github(organization:)` and `GithubApp#verify_webhook_signature`), the attacker knows a valid webhook secret for their own org and can produce a request whose signature verifies successfully: [3](#0-2) 

Once the signature check passes, the `create` action dispatches the raw payload to registered handlers for the event type, unchanged: [4](#0-3) 

For the `status` event, `Shipit::Webhooks::Handlers::StatusHandler#process` operates on **any** commit in the entire database matching the attacker-supplied `sha`, with no scoping to the `repository` (and therefore no scoping to the organization that was actually authenticated): [5](#0-4) 

This is in contrast to `PushHandler`, which correctly scopes to `stacks` derived from `payload.dig('repository', 'full_name')` via the base `Handler` class: [6](#0-5) [7](#0-6) 

`StatusHandler` never calls `stacks` or checks `repository_name` — it only requires `sha`, `state`, and optional cosmetic fields: [8](#0-7) 

So the binding that should hold — "the GitHub organization whose secret authenticated this webhook" == "the repository/commit whose status is being written" — does not hold. The signature only proves the request came from an org with a known secret; it does not constrain which commit (belonging to any other tenant/repository hosted by the same Shipit instance) can have a fabricated CI status attached.

### Impact Explanation
Commit statuses created this way feed directly into merge-queue and deploy safety gating logic (`MergeRequest::StatusChecker`, `all_status_checks_passed?`, `any_status_checks_failed?`, `Status::Group`), which are used to decide whether a pull request may be auto-merged by `ProcessMergeRequestsJob`/`MergeRequest#merge!`, and whether commits are considered deployable: [9](#0-8) [10](#0-9) 

By forging a `success` status for a `context` that a victim stack requires (`merge.require`/`ci.blocking` per README), an attacker who controls only their own unrelated GitHub organization/integration can cause the merge queue to auto-merge a pull request in a victim's repository that never actually passed CI, or unblock a deploy that should have been blocked — i.e., an unauthorized merge/deploy, matching the "Critical" impact bucket (unauthorized deploy, rollback, or merge) defined in scope.

### Likelihood Explanation
The only prerequisite is that the attacker legitimately controls a GitHub organization/App integration already configured in this Shipit instance (a standard, unprivileged onboarding scenario for a multi-tenant Shipit deployment — not a GitHub App private key theft, not a Shipit session, not an `ApiClient` token). The attacker additionally needs to know a target commit `sha`, which is routinely public (visible in GitHub PR URLs, CI links, or Shipit's own public deploy/merge-status pages). No interaction with the victim organization's credentials, GitHub App, or webhook secret is required at all. This is a straightforward, repeatable HTTP POST to `/webhooks`.

### Recommendation
In `StatusHandler#process` (and any other handler that trusts payload-scoped identifiers), scope the lookup to the authenticated organization/repository, not just `sha` globally, e.g. restrict to `stacks`/`Repository.from_github_repo_name(repository_name)` as `PushHandler` does, and additionally have `WebhooksController` pass the authenticated organization down to handlers so they can assert `commit.stack.repository.owner == authenticated_organization` before mutating state.

### Proof of Concept
1. Attacker owns/configures `attacker-org`, which is installed in this Shipit instance with a known `webhook_secret` (legitimate, low-privilege setup).
2. Attacker learns the public commit SHA of a PR head commit in `victim-org/victim-repo` that a Shipit-managed stack requires a specific CI `context` for (e.g. from the PR page or the Shipit merge-status widget).
3. Attacker crafts a `status` event payload:
   ```json
   {
     "repository": {"owner": {"login": "attacker-org"}, "full_name": "attacker-org/whatever"},
     "sha": "<victim commit sha>",
     "state": "success",
     "context": "ci/required-context",
     "target_url": "https://example.com",
     "created_at": "2026-09-01T00:00:00Z"
   }
   ```
4. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(attacker_webhook_secret, body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `attacker-org`, fetches `attacker-org`'s webhook secret, and the signature verifies successfully.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and finds the victim's commit (belonging to a completely different organization/stack), creating a fabricated `success` status on it via `commit.create_status_from_github!`.
7. `ProcessMergeRequestsJob` subsequently sees `all_status_checks_passed?` return true for the victim's pull request and merges it, or the victim's stack considers the commit deployable, despite the attacker never having interacted with `victim-org`'s repository, GitHub App, or webhook secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
