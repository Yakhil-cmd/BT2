### Title
Dust debt permanently blocks a market's last supplier from fully exiting - (File: contracts/pool/src/guards.rs)

### Summary

The pool's withdraw path enforces `require_supply_for_debt`: after burning supply shares it panics with `PoolInsolvent` if `supplied == 0` while `borrowed != 0`. Because collateral and debt live in separate `(hub, token)` books, an unprivileged attacker can open a dust borrow in market B collateralized by supply in market A, making any full withdrawal by market B's last supplier revert — indefinitely and at near-zero cost, since the attacker can repay the dust debt and reclaim collateral immediately after the victim's transaction fails.

### Finding Description

Every withdrawal runs `gate_and_debit` in `contracts/pool/src/ops/withdraw.rs:111-119`, which calls `guards::require_supply_for_debt` after `burn_position` reduces `cache.supplied`. The guard in `contracts/pool/src/guards.rs:69-73` panics whenever total supply shares are zero while total debt shares are non-zero:

```rust
// contracts/pool/src/guards.rs:69
pub(crate) fn require_supply_for_debt(env: &Env, cache: &Cache) {
    if cache.supplied() == Ray::ZERO && cache.borrowed() != Ray::ZERO {
        panic_with_error!(env, CollateralError::PoolInsolvent);
    }
}
```

The utilization guard directly above it (`require_utilization_below_max`, lines 19-34) early-returns when `supplied == 0`, so the supply-for-debt check is the only thing standing between a clean full exit and a revert. Debt shares are minted by `mint_debt` in `contracts/pool/src/cache/shares.rs:26-28` on the `borrow` leg, and per-market books mean the attacker can satisfy health/collateral requirements in a *different* market while leaving only dust debt behind in the victim's market. This mirrors the reported `_checkMinShares` DoS: a global-state post-check on withdrawal that an attacker can poison with a minimal, recoverable position.

### Impact Explanation

Temporary freezing of funds. While the attacker keeps even 1 unit of debt shares open in the market, the last supplier's `withdraw(amount = i128::MAX)` (or any withdrawal that burns their entire position) reverts. The victim retains a fallback — a partial withdrawal leaving ≥1 scaled share — so the permanently stuck portion is dust, but the griefing can be repeated forever: each time the victim submits a full exit, the attacker re-opens dust debt (via `borrow`) and later unwinds via `repay` plus collateral `withdraw`, losing only negligible interest.

### Likelihood Explanation

Low-to-medium. It requires a motivated griefer willing to keep collateral supplied in another market (capital lockup, though reclaimable after each cycle), and the victim can largely bypass it by leaving dust shares. No privileged role is needed — `borrow`, `repay`, `supply`, and `withdraw` are all unprivileged controller entrypoints — but the economic harm per attack is small (dust remainder plus forced re-submission), which lowers incentive.

### Recommendation

Do not gate ordinary withdrawals on `borrowed != 0` when `supplied == 0`. A user burning their own shares cannot create a backing shortfall that didn't already exist; solvency is already covered by `require_reserves`/`debit_cash` and the debt side is unaffected by share burns. Either drop `require_supply_for_debt` from the withdraw path (keep it for actions that add debt), or treat residual dust debt through the existing `clean_bad_debt`/`recapitalize` machinery rather than reverting the last supplier's exit.

### Proof of Concept

Scenario on a two-market setup (market A = XLM collateral, market B = USDC), pool reachable through `controller`:

1. `victim` calls `controller.supply(USDC_hub, USDC, 1_000_000)` — becomes the sole supplier of market B.
2. `attacker` calls `controller.supply(XLM_hub, XLM, large_amount)` in market A, then `controller.borrow(USDC_hub, USDC, dust)` where `dust` is any amount ≥1 that satisfies `min_borrow_collateral_usd` (attacker's XLM collateral covers it comfortably). Market B now has `borrowed > 0`.
3. All other market-B suppliers exit; `victim` submits `controller.withdraw(USDC_hub, USDC, i128::MAX, victim)`.
4. Inside `pool::withdraw::accounting` → `resolve_close_or_partial` burns all of the victim's scaled shares → `supplied == 0`, `borrowed == dust` → `gate_and_debit` → `require_supply_for_debt` panics with `PoolInsolvent`. The utilization guard does not fire because it early-returns on `supplied == 0`.
5. `attacker` immediately calls `controller.repay(USDC_hub, USDC, dust)` and `controller.withdraw(XLM_hub, XLM, i128::MAX, attacker)`, recovering everything except ~zero interest. Repeat from step 2 whenever the victim resubmits.

Expected result: the victim's full withdrawal reverts on every attempt while the attacker's round trip costs only dust-debt interest. The victim can only exit by leaving residual scaled shares, permanently stranding that dust.

**Caveat / what I could not fully verify:** my iteration budget ended before I could read `controller`'s `withdraw`/`borrow` wrappers, `repay`, and the `min_borrow_collateral_usd` enforcement, so exact entrypoint names/argument order in step 2-4 are inferred from the repo's documented surface rather than read directly; the pool-side root cause (`withdraw.rs:111-118`, `guards.rs:69-73`, `shares.rs:26-33`) is confirmed from source. It is also possible (unverified) that interest accrual minting revenue shares keeps `supplied > 0` in some configurations, which would weaken the trigger — `burn_supply`/`accrue_revenue` semantics suggest revenue only exists if accrued, so an attacker should borrow before meaningful revenue accumulates.
