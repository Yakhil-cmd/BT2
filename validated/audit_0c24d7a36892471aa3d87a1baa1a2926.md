Confirmed. The vulnerability is real and matches the required binding-break pattern: the organization whose webhook secret authenticates the signature is decoupled from the repository the payload actually acts upon.

- `WebhooksController#verify_signature` selects which organization's secret to check against using `repository_owner`, which reads `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`) — a field taken directly from the **unverified** JSON body before any signature is confirmed valid. [1](#0-0) [2](#0-1) 
- `GitHubApp#verify_webhook_signature` unconditionally returns `true` when that organization's `webhook_secret` is blank: `return true unless webhook_secret`. [3](#0-2) 
- Multi-org configuration explicitly allows `webhook_secret` to be left nil per-organization, as documented in the multi-tenant secrets template. [4](#0-3) 
- After signature "verification" passes, event handlers resolve the target **repository/stack** using a completely different field, `payload.dig('repository', 'full_name')` — never re-checked against `repository_owner`. [5](#0-4) [6](#0-5) 

This breaks the equality that should hold: `organization authenticated by verify_signature == organization owning the repository acted upon by the handler`. Since `repository.owner.login` (used only for secret selection) and `repository.full_name` (used to select the actual `Stack`/`Repository` to mutate) are independent, unvalidated fields in the same unauthenticated JSON body, an attacker who knows (or guesses) that any one configured organization has `webhook_secret` unset can send a forged webhook claiming `repository.owner.login` = that no-secret org, while setting `repository.full_name` to point at a stack belonging to an entirely different, secret-protected organization. `verify_signature` passes trivially (no secret to check), and the handler processes the forged event against the real target stack — e.g. `PushHandler` will enqueue `GithubSyncJob` for that stack with an attacker-chosen `expected_head_sha`/`ref`, or `check_suite`/`status` handlers will inject fabricated CI state that other parts of Shipit (`Stack#deployable?`, merge/deploy gating) rely on.

### Title
Webhook organization used for signature verification is decoupled from the repository the payload acts upon, allowing signature bypass via an org with no `webhook_secret` - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks the GitHub App config (and thus the HMAC secret) to validate against using the unauthenticated `repository.owner.login`/`organization.login` field from the JSON body. `GitHubApp#verify_webhook_signature` treats a blank `webhook_secret` as automatic success. Every webhook event handler, however, resolves the actual `Stack`/`Repository` to mutate from a different, equally unauthenticated field: `repository.full_name`. These two fields are never cross-checked, so an attacker can pick any configured organization that has no `webhook_secret` set, put its login in `repository.owner.login` to sail through signature verification, and put the full name of a target repository belonging to a *different*, secret-protected organization in `repository.full_name` to have the corresponding handler act on it.

### Finding Description
`verify_signature` looks up the GitHub App config via `Shipit.github(organization: repository_owner)` where `repository_owner` comes straight from the request body: [1](#0-0) [2](#0-1) 

`verify_webhook_signature` returns `true` unconditionally if that organization's `webhook_secret` is not configured: [3](#0-2) 

The Shipit multi-org secrets format explicitly supports per-organization configs, and leaving `webhook_secret` empty for a given org is a documented/valid state (see the commented `# nil` in the sample config): [7](#0-6) 

Once the before_action passes, `WebhooksController#create` dispatches to handlers with the raw parsed body: [8](#0-7) 

Every handler (`Handler#stacks`, used by `PushHandler`, etc.) resolves the actual repository/stack from `payload.dig('repository', 'full_name')` — a field that has no relationship to `repository.owner.login` used above for secret selection: [5](#0-4) [6](#0-5) 

Equality broken: `organization whose secret authenticated the request == organization owning the repository the handler mutates`. Both sides of this equality are supposed to be the same organization, but neither is actually checked against the other — `repository.owner.login` only selects a secret (which may not exist), and `repository.full_name` independently selects the mutated `Stack`.

### Impact Explanation
This allows an unauthenticated attacker to forge GitHub webhook events (push, status, check_suite, pull_request, etc.) against any Stack belonging to any organization configured in the same Shipit instance, as long as at least one configured organization has no `webhook_secret` set. Concretely:
- `PushHandler` enqueues `GithubSyncJob` with attacker-chosen `expected_head_sha`, which drives what commits Shipit will fetch/consider deployable for the victim stack.
- `status`/`check_suite` handlers can inject fabricated CI/check state that Shipit treats as real when deciding if a commit is deployable, effectively bypassing deploy gating (`Stack` deployability checks rely on this status data).
This crosses the "unauthorized deploy/rollback state manipulation via forged webhook, bypassing signature verification for cross-org resources" bar.

### Likelihood Explanation
Requires only knowledge that some organization on the shared Shipit instance is configured without a `webhook_secret` (a documented, legitimate configuration state, e.g. during initial setup as shown in `config/secrets.development.shopify.yml`) — no credentials, tokens, or session are needed, only the ability to send an HTTP POST to the public `/webhooks` endpoint with a crafted, unsigned JSON body.

### Recommendation
After resolving the target repository from `repository.full_name`, verify that the resolved `Repository`'s owning organization matches the organization whose secret was used to authenticate the signature (or, simpler, always require a webhook secret per organization and reject any org config with a blank `webhook_secret`). At minimum, cross-check `repository.owner.login` used for signature selection against the owner implied by `repository.full_name` before dispatching to handlers.

### Proof of Concept
1. Shipit instance configured with two orgs: `org-with-secret` (has `webhook_secret`) and `org-no-secret` (no `webhook_secret`, e.g. left blank during setup).
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: push` and no valid `X-Hub-Signature`, body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "org-no-secret" },
    "full_name": "org-with-secret/victim-repo"
  }
}
```
3. `verify_signature` resolves `Shipit.github(organization: "org-no-secret")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the (missing/garbage) `X-Hub-Signature` header.
4. `PushHandler` resolves `stacks` from `repository.full_name = "org-with-secret/victim-repo"` and enqueues `GithubSyncJob` for that stack with the attacker's `expected_head_sha`, even though the attacker never had `org-with-secret`'s webhook secret.
