### Title
`pallet-ranked-collective` retains a removed/demoted member's voting power in already-ongoing polls - ([File: substrate/frame/ranked-collective/src/lib.rs])

### Summary
`pallet-ranked-collective::remove_member` / `demote_member` (via `do_remove_member_from_rank` / `do_demote_member`) delete the member's rank-index storage (`Members`, `IdToIndex`, `IndexToId`, `MemberCount`) but never touch the per-poll `Voting` storage or the already-accumulated `Tally` for polls the member previously voted on. This mirrors the CVE-2019-7155 pattern: an actor loses their role in the "group" (the ranked collective) but their previously granted privilege (recorded vote weight on an in-progress "project", i.e. an ongoing poll) is not revoked, because the privilege was materialized into separate per-resource state that removal never revisits.

### Finding Description
`do_remove_member_from_rank` only unwinds indexing storage: [1](#0-0) 
and `do_demote_member` similarly only touches `remove_from_rank` / `Members`: [2](#0-1) 

Neither path iterates `Voting::<T, I>` for the removed/demoted account, nor adjusts the `Tally` of any `PollStatus::Ongoing` poll the member already voted in. Contrast this with the sibling pallet `pallet-collective`, whose `ChangeMembers::change_members_sorted` explicitly walks every open `Proposals` entry and strips outgoing members' `ayes`/`nays` from the vote list on removal: [3](#0-2) 
confirmed by the existing test `removal_of_old_voters_votes_works`: [4](#0-3) 

In `pallet-ranked-collective`, the `Tally` (bare_ayes/ayes/nays) accrued via `vote()` is only ever adjusted when: (a) the same account votes again on the same poll (diffing against `Voting::get`), or (b) `cleanup_poll` is called, but `cleanup_poll` explicitly requires the poll to no longer be `Ongoing`: [5](#0-4) 

So for any poll still `Ongoing` at the moment a member is `remove_member`'d or `demote_member`'d below the poll's `MinRankOfClass`, that member's already-cast vote (and its weight, computed from the rank they held at vote time) remains fully counted in the live `Tally` used by `Referenda`/`fellowship-core` polling logic, exactly as GitLab's CVE let a user retain in-project privileges after being pulled from the owning group.

A related historical PR, `prdoc/1.5.0/pr_2591.prdoc` ("Ensure to cleanup state in `remove_member`"), previously fixed a *different* state-cleanup gap in this same function for `IdToIndex`/`IndexToId`/`MemberCount`: [6](#0-5) 
It did not address the `Voting`/`Tally` retention issue described here.

### Impact Explanation
This is an integrity break in the governance/voting subsystem: a member's continued influence on an ongoing decision after their role has been legitimately revoked (whether by peer expulsion via `RemoveOrigin`, self-inflicted demotion cascades, or fellowship promotion/demotion cycles) can change the outcome of a poll that should reflect only current, authorized rank-weighted voters. Because `VoteWeight` scales with rank, a member demoted several ranks (or removed entirely) after voting keeps their higher, now-unauthorized vote weight locked into the tally until the poll concludes — this can tip a referendum threshold that would not have been met with the corrected (lower/absent) weight. This is a governance-integrity/unauthorized-influence issue rather than a direct fund-theft primitive, so it is best characterized as Medium severity, matching the CVE's own Medium rating and its "retains role/permission distinct from the reference group" theme.

### Likelihood Explanation
No privileged access is required to trigger this from the attacker's perspective; it happens automatically for any member who is legitimately voted out or demoted by the `RemoveOrigin`/`DemoteOrigin` while they have an outstanding vote — this is a normal, expected operational sequence for any fellowship/ranked collective (e.g. Polkadot Fellowship, Ambassador collective on Collectives-Westend/Polkadot) and does not require attacker-controlled input beyond normal participation, only correct timing (vote, then get removed/demoted while the poll is still open).

### Recommendation
On `do_remove_member_from_rank` and `do_demote_member`, before mutating rank indices, iterate `Voting::<T, I>::iter_prefix` (or a per-account secondary index) for the affected account and, for every poll still `PollStatus::Ongoing`, retract the recorded vote's weight from the poll's live `Tally` (mirroring `pallet-collective::change_members_sorted`), then remove the `Voting` entry. Alternatively, re-validate a caster's rank/eligibility at poll-close time rather than trusting the weight recorded at vote time.

### Proof of Concept
Not executed. A minimal integration test would: (1) `add_member`/`do_promote_member` an account to a rank sufficient to vote on a poll class, (2) open a poll with `T::Polls` and call `Pallet::vote` to record an `Aye` with that rank's weight in `Tally`, (3) call `remove_member` (or `demote_member` below `MinRankOfClass`) via the pallet's origins while the poll remains `Ongoing`, and (4) assert that `T::Polls::as_ongoing(poll).0` (the `Tally`) still includes the removed member's `ayes`/`bare_ayes` contribution, whereas the equivalent `pallet-collective` test (`removal_of_old_voters_votes_works`) shows the vote is stripped. This was not run against the repository; it is a proposed reproduction based on static analysis of `do_remove_member_from_rank`/`do_demote_member`/`cleanup_poll` and the contrasting `pallet-collective::change_members_sorted` behavior. No test harness execution or PoC run results are available from this analysis session.

			let mut record = Self::ensure_member(&who)?;
			let rank = record.rank;
			if let Some(max_rank) = maybe_max_rank {
				ensure!(max_rank >= rank, Error::<T, I>::NoPermission);
			}

			Self::remove_from_rank(&who, rank)?;
			let maybe_rank = rank.checked_sub(1);
			match maybe_rank {
				None => {
					Members::<T, I>::remove(&who);
					Self::deposit_event(Event::MemberRemoved { who, rank: 0 });
				},
				Some(rank) => {
					record.rank = rank;
					Members::<T, I>::insert(&who, &record);
					Self::deposit_event(Event::RankChanged { who, rank });
				},
			}
			Ok(())
		}

				new.len(),
				T::MaxMembers::get(),
			);
		}
		// remove accounts from all current voting in motions.
		let mut outgoing = outgoing.to_vec();
		outgoing.sort();
		for h in Proposals::<T, I>::get().into_iter() {
			<Voting<T, I>>::mutate(h, |v| {
				if let Some(mut votes) = v.take() {
					votes.ayes = votes
						.ayes
						.into_iter()
						.filter(|i| outgoing.binary_search(i).is_err())
						.collect();
					votes.nays = votes
						.nays
						.into_iter()
						.filter(|i| outgoing.binary_search(i).is_err())
						.collect();
					*v = Some(votes);
				}
			});
		}
		Members::<T, I>::put(new);
		Prime::<T, I>::kill();
	}
