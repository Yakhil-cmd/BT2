### Title
Webhook signature validation is scoped per-organization but the acted-upon repository is not, allowing cross-organization webhook forgery in multi-org Shipit deployments - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to validate a webhook against using an attacker-controlled field (`repository.owner.login`, or `organization.login`) from the unauthenticated request body, while the handlers that actually act on the payload key off a *different* field (`repository.full_name`) that is never tied back to the organization whose secret validated the request.

### Finding Description
The webhook endpoint is public and unauthenticated by design (`skip_before_action :verify_authenticity_token`), relying solely on `verify_signature` to establish trust: [1](#0-0) 

`repository_owner` is read straight from the untrusted JSON body: [2](#0-1) 

`verify_signature` uses this attacker-controlled `repository_owner` value to pick a `GitHubApp` instance (`Shipit.github(organization: repository_owner)`), then validates the raw body against **that org's** webhook secret: [3](#0-2) 

Shipit explicitly supports multiple GitHub organizations configured with independent per-org `webhook_secret` values in a single instance, as documented and exercised in tests: [4](#0-3) [5](#0-4) 

Critically, `verify_webhook_signature` treats a blank/unset `webhook_secret` for an org as "verification passes unconditionally": [6](#0-5) 

After `verify_signature` succeeds, `create` re-parses the same raw body and dispatches it to handlers based on `event`, with **no re-check that the payload's actual target repository belongs to the organization that was used to select the secret**: [7](#0-6) 

Handlers resolve the stacks to act on using `repository.full_name` from the payload — a field entirely independent of `repository_owner`: [8](#0-7) 

**The broken equality:** the code implicitly assumes `organization that authenticated the request == organization owning the repository being acted upon`. Nothing enforces this. An attacker can set `repository.owner.login` (or `organization.login`) to any organization configured in the Shipit instance that has no `webhook_secret` set (or whose secret is otherwise satisfied), causing `verify_signature` to pass, while setting `repository.full_name` in the very same payload to name a *completely different* repository/stack — including one belonging to another, properly-secured organization also configured in the same instance. Since `Handler#stacks` and `Handler#repository_name` only look at `repository.full_name`, the forged event is processed as if it legitimately originated from GitHub for that other repository's stack.

### Impact Explanation
This lets an unauthenticated, unprivileged attacker forge webhook events (e.g. `push`, `status`, `check_suite`, `commit_status`, `merge_status`, `pull_request`, `membership`) for stacks belonging to a different, properly-secured GitHub organization tracked by the same Shipit instance — as long as any other configured organization in that instance has no webhook secret (a supported, non-error configuration per `docs/setup.md` and the shipped `config/secrets.development.shopify.yml` template). Depending on which handler is triggered, this can:
- Force `GithubSyncJob` to re-sync/alter perceived commit/CI state for arbitrary stacks (`push`, `status`, `check_suite` handlers), which feeds into deploy eligibility decisions (`checkIsOverdue`-style trust: commit "deployable" status).
- Create arbitrary `Team`/`User` records via the `membership` handler.
- Influence merge-queue/commit-status state used to gate merges/deploys.

This does not by itself grant RCE, but it breaks the "organization authenticated vs. repository written" trust boundary and can enable an unauthorized deploy/merge decision to be triggered based on forged CI/commit status for a stack the attacker does not control, without any credential.

### Likelihood Explanation
Requires: (1) a multi-org Shipit deployment (an explicitly documented and supported configuration), and (2) at least one configured organization without a `webhook_secret`. No attacker credentials, session, ApiClient token, or repository write access are needed — only knowledge of the target Shipit host and the organization names configured on it (which can often be inferred from `Shipit.github_teams`/public stack pages). This is a plausible, not purely theoretical, deployment scenario.

### Recommendation
Bind the organization used for signature verification to the organization actually referenced by the payload's `repository.full_name`/`organization.login`, and reject the webhook if these ever diverge. Additionally, consider making per-organization `webhook_secret` mandatory (raise a hard configuration error at boot for any configured org that has no secret) rather than silently allowing unauthenticated pass-through for that org.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `OrgOne` (no `webhook_secret`) and `OrgTwo` (`webhook_secret: s3cr3t`), both tracked (as in `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker (no credentials) sends:
   ```
   POST /github/webhooks
   X-Github-Event: push
   X-Hub-Signature: sha1=anything
   Body: {
     "repository": { "owner": { "login": "OrgOne" }, "full_name": "OrgTwo/protected-repo" },
     "ref": "refs/heads/main",
     "after": "<attacker-chosen sha>"
   }
   ```
3. `verify_signature` computes `repository_owner == "OrgOne"`, selects `Shipit.github(organization: "OrgOne")`, whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` unconditionally regardless of the bogus `X-Hub-Signature`.
4. `create` dispatches the push handler, which resolves the target stack via `payload.dig('repository','full_name')` == `"OrgTwo/protected-repo"`, processing the forged event against `OrgTwo`'s stack — even though `OrgTwo` has a properly configured secret that was never checked.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",

      ].join(' '))
    end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
