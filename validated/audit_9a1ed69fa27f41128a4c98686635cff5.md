### Title
Webhook signature verification is keyed to `repository.owner.login` while every event handler acts on the independent `repository.full_name` field, letting a valid signature from one GitHub organization authorize webhook processing for a different tracked repository - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
This is the same bug class as the Wise Lending finding: a validity/authorization check is computed against one value while the value that is actually acted upon downstream is a different, independently-controlled field from the same untrusted input. In `PendlePowerFarmLeverageLogic`, the minimum-value check was evaluated using `_depositAmount` (already spread-adjusted) instead of the real initial deposit. Here, `WebhooksController#verify_signature` selects *which* organization's `webhook_secret` to validate the HMAC signature against using `repository.owner.login` (or `organization.login`) taken straight from the unverified JSON body, while the downstream `Shipit::Webhooks::Handlers::Handler#repository_name` (and all `PushHandler`, `PullRequest::*Handler`, `ReviewStackAdapter` implementations) resolve the actual `Stack`/`Repository` to mutate using the separate `repository.full_name` field from the very same body.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb#verify_signature` does: [1](#0-0) 
picking the `GitHubApp` (and therefore the `webhook_secret` HMAC key) via `repository_owner`: [2](#0-1) 

`Shipit.github(organization:)` looks up a *per-organization* app/secret only when the multi-organization config schema is used (`github_default_organization` non-nil, i.e. `secrets.github` keyed by org names): [3](#0-2) 

Meanwhile every webhook handler resolves the actual repository/stack to act on from a *different* JSON key, `repository.full_name`, never from `repository.owner.login`: [4](#0-3) 
and, e.g., `PushHandler` triggers a GitHub sync (which drives deploy status/state) for stacks matching that repository: [5](#0-4) 
Pull-request handlers similarly resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)` to archive/unarchive review stacks or update PR state, independent of `repository.owner.login`: [6](#0-5) 

All organizations' webhooks are delivered to the single shared route `POST /webhooks`, there is no per-organization endpoint segregation: [7](#0-6) 

The binding that should hold is:
`organization whose webhook_secret authenticates the signature == organization/repository that the handler chain mutates`

In a multi-organization deployment (documented as a supported configuration in `config/secrets.development.example.yml`) this binding does not hold, because the two values are read from two independently-settable JSON fields (`repository.owner.login` vs `repository.full_name`) inside the same attacker-supplied, otherwise-unverified-until-this-check payload.

### Impact Explanation
An attacker who legitimately controls (or is a collaborator/admin on) one GitHub organization/App configured in this Shipit instance's multi-org `github:` config can compute a correctly-signed HMAC using *their own* `webhook_secret` for a payload whose `repository.owner.login`/`organization.login` matches their own org (so `verify_signature` passes), but whose `repository.full_name` is forged to point at a repository belonging to a *different, unrelated* organization tracked by the same Shipit instance. Because the handlers never re-validate that `repository.full_name`'s owner matches the organization used for signature verification, this forged, attacker-signed webhook is processed against the victim organization's stacks. Depending on event type this can:
- Trigger `GithubSyncJob`/deploy state changes via `PushHandler` for a foreign stack.
- Archive/unarchive or provision `ReviewStack`s for a foreign repository via the `pull_request` handlers.
- Create/remove team memberships or users via `MembershipHandler` scoped to the attacker's own claimed organization name while manipulating state tied to another repository.

This crosses the "cross-repository writes" impact bar: an unprivileged-with-respect-to-victim-org attacker (who is only privileged in their own, unrelated org) can cause writes/state transitions against a repository/stack they do not control, using a webhook signature that is valid only for their own organization.

### Likelihood Explanation
Requires the deployment to use the documented multi-organization `github:` secrets schema (multiple orgs, each with its own `webhook_secret`/GitHub App) — a supported and documented configuration, not a misconfiguration. Within that configuration, the only "cost" to the attacker is control of one legitimate org/app entry (their own), which they inherently have as the owner of that GitHub App/webhook config. No GitHub write access to the victim repository, no Shipit session, and no knowledge of the victim's webhook secret are required — only the ability to send an HTTP POST with a self-signed payload. This satisfies the "unprivileged-attacker" and "no Shipit session/ApiClient token/GitHub write access" constraints.

### Recommendation
Cross-check that the organization/owner used to select the verification secret is the same organization referenced by `repository.full_name` before dispatching to handlers — e.g., derive `repository_owner` strictly from `repository.full_name.split('/').first` (or compare it against `repository.owner.login`/`organization.login` and reject mismatches) in `WebhooksController#verify_signature`, and have `Handler#repository_name` reject payloads where the two disagree.

### Proof of Concept
1. Deploy Shipit with the multi-organization `github:` secrets schema, containing two entries: `org-attacker` (attacker's own GitHub App/webhook secret) and `org-victim` (an unrelated tracked organization/repository).
2. Attacker crafts a `push` (or `pull_request`) webhook JSON body with:
   - `repository.owner.login = "org-attacker"`
   - `organization.login = "org-attacker"`
   - `repository.full_name = "org-victim/some-tracked-repo"`
3. Attacker signs the raw body with `org-attacker`'s `webhook_secret` (which they legitimately know, since it is their own App) and sets `X-Hub-Signature` accordingly, `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: 'org-attacker')` and successfully verifies the signature.
5. `PushHandler` (or the relevant `pull_request` handler) resolves the target using `payload.dig('repository', 'full_name')` = `"org-victim/some-tracked-repo"`, and processes the event (e.g., enqueues `GithubSyncJob`, archives/unarchives a review stack) against `org-victim`'s stack, despite the signature only proving authenticity for `org-attacker`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
