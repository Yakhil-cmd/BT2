### Title
Out-of-bounds read in EVM bytecode `PUSH1`-`PUSH32` opcode via unchecked `read_slice` - ([File: substrate/frame/revive/src/vm/evm/ext_bytecode.rs])

### Summary
`pallet-revive`'s EVM-compatibility interpreter reads immediate operand bytes for `PUSHn` opcodes via `ExtBytecode::read_slice`, which builds a raw slice with `core::slice::from_raw_parts` guarded only by a `debug_assert!` bounds check [1](#0-0) . Because `debug_assert!` compiles to a no-op in release builds, the only enforcement of "the slice fits in the bytecode buffer" disappears in production, mirroring the Oniguruma CVE pattern where a length/bound (`reg->dmin`) was trusted without a hard runtime check in the actual matching path, leading to an out-of-bounds stack/heap read from attacker-controlled input.

### Finding Description
`Interpreter` executes opcodes from bytecode uploaded by an unprivileged account deploying a Solidity/EVM-style contract via `pallet-revive` (a normal, permitted contract-deploy path, no privilege required) [2](#0-1) . For opcodes `PUSH1`..`PUSH32`, `stack::push::<N,_>` calls `interpreter.bytecode.read_slice(N)` to read the `N`-byte immediate operand that follows the opcode in the code buffer [3](#0-2) .

`read_slice` is implemented as:
```
pub fn read_slice(&self, len: usize) -> &[u8] {
    debug_assert!( /* pc + len <= bytes.len() */ , "read_slice would read out of bounds");
    unsafe { core::slice::from_raw_parts(self.instruction_pointer, len) }
}
``` [1](#0-0) 

The safety comment explicitly states "The caller ensures that `len` bytes are available from the current instruction pointer position," i.e. the actual invariant enforcement is delegated entirely to callers, with the only executable check being a debug-only assertion. `relative_jump` and `absolute_jump` have the identical pattern of "SAFETY: validated by caller" backed only by `debug_assert!` [4](#0-3) . In canonical EVM semantics, a `PUSHn` opcode placed at the tail of the code (fewer than `N` bytes remaining before code end) is legal and implicitly zero-padded by the reference EVM; this exact edge case is the natural trigger for `pc + N > bytes.len()`.

I could not verify, from the code available to me, whether the underlying `revm::bytecode::Bytecode` (the external `revm` crate dependency used here) pre-pads its stored byte buffer with trailing zero bytes to make `bytecode_ptr()`/`bytes_ref()` always safely over-readable by up to 32 bytes — this is a known technique some EVM implementations use specifically to avoid exactly this class of bug. I was not able to inspect the `revm` crate's `Bytecode::new_raw`/analysis code in this session, so I cannot confirm whether this padding neutralizes the missing check. This is the single fact that determines whether the debug-only assertion is a merely defensive belt-and-suspenders check (safe) or the sole real guard (exploitable) in release builds.

### Impact Explanation
If `revm::bytecode::Bytecode` does not guarantee sufficient trailing padding, a trailing `PUSHn` opcode with insufficient remaining bytes causes `core::slice::from_raw_parts` to construct a slice extending past the allocated buffer, and the interpreter pushes those out-of-bounds bytes onto the EVM stack as part of contract-controlled logic — a stack/heap out-of-bounds read directly analogous to the Oniguruma `mbc_enc_len`/`forward_search_range` bug (attacker-supplied "pattern"/bytecode traversed without a release-mode bound check). This could leak adjacent heap memory contents into contract-observable state (info disclosure) or, depending on allocator layout, crash the node process (deterministic chain/worker failure) when reading unmapped memory.

### Likelihood Explanation
Low-to-Medium confidence given the unresolved dependency question above. If the `revm` crate does not pad the code buffer, this is a High severity, easily attacker-triggerable OOB read for anyone permitted to deploy an EVM contract to a chain running `pallet-revive` with EVM opcode support (no privilege required, just gas/deposit for a deploy transaction). If `revm` does pad the buffer (the debug_assert would then always hold), this is not exploitable and is purely defensive dead code.

### Recommendation
Replace the `debug_assert!`-only guards in `ExtBytecode::read_slice`, `relative_jump`, and `absolute_jump` with real (non-debug) bounds checks that return an interpreter halt/error instead of proceeding to unsafe pointer arithmetic, removing reliance on caller correctness and unverified padding guarantees from the `revm` dependency.

### Proof of Concept
I was unable to execute a reproduction. This session provides only read-only codebase search tools with no Rust compiler/test execution available, and confirming exploitability requires (a) inspecting the external `revm` crate's `Bytecode` construction/padding behavior (not resolvable from this index) and (b) running a `pallet-revive` integration test deploying a contract whose code ends in a `PUSH32` with fewer than 32 trailing bytes, built in release mode (`debug-assertions = false`), to observe whether `read_slice` returns bytes beyond the buffer. This PoC was not run; the finding is reported as an unresolved candidate pending verification of the `revm::bytecode::Bytecode` padding invariant, which a Devin session with a full build/test environment could confirm or refute.

	pub fn absolute_jump(&mut self, offset: usize) {
		// SAFETY: The offset is validated by the caller to ensure it points within the bytecode

			"absolute_jump would move instruction pointer out of bounds"
		);

	}

/// Calls the EVM interpreter with the provided bytecode and inputs.
pub fn call<E: Ext>(bytecode: Bytecode, ext: &mut E, input: Vec<u8>) -> ExecResult {
	let mut interpreter = Interpreter::new(ExtBytecode::new(bytecode), input, ext);
	let tracing_enabled = tracing::if_tracing(|t| t.is_execution_tracer()).unwrap_or(false);

	let ControlFlow::Break(halt) = if tracing_enabled {
		run_plain_with_tracing(&mut interpreter)
	} else {
		run_plain(&mut interpreter)
	};
	halt.into()
}

fn run_plain<E: Ext>(interpreter: &mut Interpreter<E>) -> ControlFlow<Halt, Infallible> {
	loop {
		let opcode = interpreter.bytecode.opcode();
		interpreter.bytecode.relative_jump(1);
		exec_instruction(interpreter, opcode)?;
	}
}

/// Implements the PUSH1-PUSH32 instructions.
///
/// Pushes N bytes from bytecode onto the stack as a 32-byte value.
pub fn push<'ext, const N: usize, E: Ext>(
	interpreter: &mut Interpreter<'ext, E>,
) -> ControlFlow<Halt> {
	interpreter.ext.charge_or_halt(EVMGas(VERYLOW))?;

	let slice = interpreter.bytecode.read_slice(N);
	interpreter.stack.push_slice(slice)?;

	// Can ignore return. as relative N jump is safe operation
	interpreter.bytecode.relative_jump(N as isize);
	ControlFlow::Continue(())
}
