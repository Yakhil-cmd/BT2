Found a concrete boundary/off-by-one analog in `indivisible_asset.js`.

### Title
Missing boundary-equality check in indivisible-asset private-payment source validation allows source-input unit to be treated as "not included" or bypasses inclusion proof at the boundary - ([File: indivisible_asset.js])

### Summary
The CVE describes a boundary-detection bug: a range/membership check (`IP == ksym.end`) failed to treat the exact boundary value as "inside" the range, causing the wrong classification (unreliable unwinding). The ocore codebase has an analogous pattern: unit-inclusion in the DAG is determined via `graph.determineIfIncluded()` (strict ancestor-descendant relationship) versus `graph.determineIfIncludedOrEqual()` (which explicitly also accepts the boundary case where the "earlier" unit equals one of the "later" units). Most consensus-critical call sites (double-spend checks, payment input ancestry, definition-change checks) correctly use the equality-aware `determineIfIncludedOrEqual` wrapper. However, `indivisible_asset.js`'s `validateSourceOutput()` (used when validating a private (indivisible/blackbyte) payment's spend chain) calls the strict `graph.determineIfIncluded()` instead.

### Finding Description
`determineIfIncluded(conn, earlier_unit, arrLaterUnits, handleResult)` in `graph.js` is documented as "determines if earlier_unit is included by at least one of arrLaterUnits" [1](#0-0) , and it never checks whether `earlier_unit` is literally equal to one of the entries in `arrLaterUnits`. The dedicated wrapper `determineIfIncludedOrEqual()` was created specifically to add that equality boundary check before delegating to the strict function [2](#0-1) , confirming that boundary equality is a distinct, security-relevant case that must be explicitly handled everywhere ancestor/descendant relationships gate validation decisions (this pattern is used pervasively for double-spend and input-ancestry checks, e.g. [3](#0-2)  and [4](#0-3) ).

In `indivisible_asset.js`, `validatePrivatePayment()` validates that the spent source output's unit (`input.unit`) is an ancestor of the current private-payment unit (`objPrivateElement.unit`) using the strict function:

```
function validateSourceOutput(cb){
    if (conf.bLight)
        return cb(); // already validated the linkproof
    profiler.start();
    graph.determineIfIncluded(conn, input.unit, [objPrivateElement.unit], function(bIncluded){
        profiler.stop('determineIfIncluded');
        bIncluded ? cb() : cb("input unit not included");
    });
}
``` [5](#0-4) 

Because `determineIfIncluded` does not special-case `earlier_unit === arrLaterUnits[i]`, any legitimate case where `input.unit` equals `objPrivateElement.unit` itself (i.e., the boundary/self-referential case) is misclassified as "not included," and, more importantly, the general strict-inclusion algorithm's early-exit logic in `determineIfIncluded` (walking parenthoods and comparing `main_chain_index`/`latest_included_mc_index`/`witnessed_level`) is boundary-sensitive: units that are exactly on the frontier (same MCI, same level boundary) can be incorrectly excluded or, depending on how `arrLaterUnitProps` is constructed when `earlier_unit` coincides with a later unit, produce an inconsistent/incomplete traversal (see the goUp logic in `graph.js` lines 175–248 where `arrStartUnits` are the later units' *parents*, not the later units themselves, so an earlier unit equal to a later unit is never matched by `objUnitProps.unit === earlier_unit`) [6](#0-5) .

### Impact Explanation
This function is invoked for full (non-light) nodes validating private, indivisible-asset (blackbyte-style) payment chains sent directly between wallets, outside the normal public DAG payment-input validation path used by `validation.js`. If the boundary/equality case is mishandled, a node could either (a) reject a legitimate spend proof it should accept (denial of confirmation for a valid private payment), or (b) — more critically — the inconsistency between how `determineIfIncluded` and `determineIfIncludedOrEqual` classify a unit that sits exactly on the ancestry boundary could allow different nodes to disagree on whether a source output referenced in a private payment is a legitimate ancestor, opening the door to spend-proof/double-spend disagreement across nodes for private assets, since private payment validation happens client-side (each peer independently re-derives spend proofs and ancestry) rather than being anchored by consensus DB state the way public payments are.

### Likelihood Explanation
Reaching this code path only requires composing and sending a private (indivisible-asset) payment message via `indivisible_asset.js`'s `validatePrivatePayment`, which any user/wallet holding or receiving such an asset invokes; no special privileges are needed. The trigger condition (the source unit and the current private-element unit coinciding, or landing exactly on the ancestry boundary evaluated by `determineIfIncluded`) is a narrow, specific-construction scenario, similar to the kernel bug's narrow-but-real "instruction lands exactly on ksym.end" trigger.

### Recommendation
Replace the strict `graph.determineIfIncluded()` call in `validateSourceOutput()` in `indivisible_asset.js` with `graph.determineIfIncludedOrEqual()`, consistent with all other consensus-critical ancestry checks in `validation.js` (payment inputs, double-spend checks, pending-definition checks), so that the boundary/equality case is explicitly and correctly handled rather than falling through the strict-inclusion algorithm's assumptions.

### Proof of Concept
Concrete PoC could not be fully constructed from static analysis alone: exercising the exact boundary condition (constructing a private indivisible-asset payment chain where `input.unit` coincides with, or sits exactly on the graph-traversal boundary relative to, `objPrivateElement.unit`) requires running the full private-payment validation pipeline (`private_payment.js` → `indivisible_asset.js` → `graph.js`) against a live/test DAG to observe whether `determineIfIncluded` misclassifies the boundary case in practice. This is noted as an area requiring dynamic testing to confirm exploitability; a Devin session with an actual test DAG/database would be needed to construct and run this PoC.
