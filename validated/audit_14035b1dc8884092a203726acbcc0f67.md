### Title
Permanent market freeze via i128 overflow of total debt value during interest accrual - ([File: common/src/rates/index.rs])

### Summary
Cesanta MJS CVE-2021-46537 is a crash-from-input DoS. The analog here is an i128 overflow panic inside the pool's interest accrual: when scaled debt × borrow index exceeds `i128::MAX`, accrual panics with `MathOverflow` before the `MAX_BORROW_INDEX_RAY` clamp can engage. Since every controller verb accrues first, the entire market freezes permanently — no supply, withdraw, repay, borrow, or liquidation can ever execute again on that pool.

### Finding Description
Accrual runs through `global_sync` → `accrue_chunk` → `accrue_step` for every mutating pool operation (`contracts/pool/src/interest.rs:20-53`). Inside `accrue_step`, `calculate_supplier_rewards` computes `borrowed.mul(env, new_borrow_index)` (`common/src/rates/index.rs:80-81`), where `borrowed` is RAY-scaled debt shares and `new_borrow_index` is the freshly grown index. `Ray::mul` panics on overflow (`common/src/math/fp.rs:13-16`). `update_borrow_index` only clamps *after* the multiply (`common/src/rates/index.rs:13-19`), so the intermediate debt value `borrowed * index` can overflow `i128` while the index itself is still far below `MAX_BORROW_INDEX_RAY = 1e36` (`common/src/constants/pool.rs:19`).

An unprivileged attacker reaches this by: (1) `supply` on a high-decimals market (supply caps allow up to `max_cap_for_decimals(18) ≈ 1.7e29` base units, `common/src/validation.rs:48-56`), (2) `borrow` at near-full utilization so the rate curve sits on its steep segment, then (3) waiting — or pinging the public `update_indexes` — until compounding pushes `borrowed * borrow_index` past `i128::MAX`. The repo's own harness test proves the state: after overflow, `try_withdraw`, `try_repay`, and `try_update_indexes` all return `MathOverflow`, with `borrow_index < MAX_BORROW_INDEX_RAY` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:316-361`). There is no recovery path: accrual is unconditional on every entrypoint, so the panic is a permanent freeze, not a transient revert.

### Impact Explanation
Permanent freezing of all user funds in the affected market: suppliers cannot withdraw, borrowers cannot repay, liquidations cannot run, and `clean_bad_debt`/`recapitalize` also accrue first. All TVL and unclaimed yield in that pool are bricked. This is worse than the reference bug-class (a process crash) — it is an unrecoverable on-chain DoS.

### Likelihood Explanation
Medium. It requires whale-scale capital (a ~1e18-token supply at ~98% borrow utilization on a market with a steep rate curve) and sustained high utilization for the index to compound roughly 100x+. No privileged access is needed; `update_indexes` is permissionless. The scenario is capital-intensive but not exotic for a large-cap token market.

### Recommendation
Widen the accrual arithmetic: compute `borrowed * index` via `I256`/`mul_div` saturating paths (as `mul_div_floor_saturating` already does for supply index growth) or check `borrowed > i128::MAX / index` before multiplying and clamp the index *before* the multiply in `update_borrow_index`. Alternatively, derive a cap-aware guard in `accrue_step` that clamps `new_borrow_index` to `min(MAX_BORROW_INDEX_RAY, i128::MAX / borrowed)` so accrual saturates instead of panicking.

### Proof of Concept
`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-361` (`a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap`) is a working PoC: supply `1e9 * 10^18` of an 18-decimal asset, borrow 98% of it, advance time yearly; `try_update_indexes` fails with `MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY`, and subsequent `try_withdraw`/`try_repay` fail identically — the market is permanently frozen.
