### Title
`opened_active_stack?` omits the `!stack.archived?` guard present in every sibling predicate, letting an `opened` pull_request webhook overwrite `PullRequest#labels` on an archived stack - (File: `app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb`)

### Summary
`LabelCapturingHandler#capture_labels?` is built from four OR'd predicates (`opened_active_stack?`, `labeled_active_stack?`, `unlabeled_active_stack?`, `reopened_active_stack?`). Three of the four explicitly require `!stack.archived?`, but `opened_active_stack?` only checks `stack.present?`, so an `opened` event reaching an already-archived review stack still calls `capture_labels`, mutating that stack's `PullRequest#labels`. This label field is not cosmetic: it is fed directly into deploy-time environment variables by `Shipit::DeployCommands#env`.

### Finding Description
The broken binding, stated as an equality that should hold but doesn't:
`opened_active_stack?` should equal `opened? && stack.present? && !stack.archived?` (matching the pattern of `labeled_active_stack?`, `unlabeled_active_stack?`, and `reopened_active_stack?`), but it is actually defined as: [1](#0-0) 

`capture_labels?` ORs these four together, so the missing guard on the `opened` branch alone is enough to bypass the archived check for the whole method: [2](#0-1) 

`capture_labels` then unconditionally writes attacker-supplied label names onto `stack.pull_request`: [3](#0-2) 

Root cause: the archived-stack invariant enforced everywhere else in this handler (and in `ReviewStackAdapter#archive!`/`#unarchive!`, which explicitly gate mutation on `stack.archived?`) was simply forgotten for the `opened?` branch. [4](#0-3) 

Downstream, `PullRequest#labels` is not inert data - it is turned into deploy-process environment variables, confirmed by the shipped feature test: [5](#0-4) 

Existing guards do not prevent the divergence: `verify_signature`/webhook signature checks only authenticate that a payload came from the configured GitHub App/webhook for that repository - they say nothing about whether the `action` is semantically valid for the current stack state. `ExplicitParameters` only validates payload shape (`action` is any `String`, `number` any `Integer`), not action/state consistency. `capture_labels?`'s three sibling predicates show the intended invariant, but `opened_active_stack?` does not enforce it.

Reachable path: a repository owner (unprivileged w.r.t. Shipit/GitHub org, but administering their own repository/webhook) can produce a scenario where GitHub redelivers (or an equivalent duplicate) a stored, validly-signed `opened` delivery for a PR number whose `ReviewStack` has since been archived (e.g., PR closed → `ClosedHandler#process` archives the stack). Because `opened_active_stack?` has no archived guard, `LabelCapturingHandler` accepts this `opened` event against the archived stack and calls `capture_labels`, overwriting `PullRequest#labels` with whatever label list is present in that request body.

### Impact Explanation
Direct, demonstrated effect: an archived `Shipit::ReviewStack`'s `PullRequest#labels` field can be rewritten via a legitimately-signed `opened` webhook that should have been rejected for that stack state - a write that none of the other three action types (`labeled`, `unlabeled`, `reopened`) permit against an archived stack. Because `Shipit::DeployCommands#env` converts each label into an uppercase boolean environment variable exposed to the deploy process, this label state can persist stale or attacker-chosen flags into the environment of any subsequent deploy run for that stack (e.g., after a later `reopened`/`unarchive!` sequence, if label capture is not re-run at that point). This is scoped to the attacker's own repository/stack (no evidence of cross-tenant/cross-repository writes was found - `stack` is always resolved from `repository.review_stacks`, scoped by `params.repository.full_name`), so it does not demonstrate a cross-tenant mutation. Full "unauthorized deploy" severity additionally depends on the operator's own deploy script treating one of these label-derived env vars (e.g., a skip-tests/force-deploy convention) as a gating signal - that dependency is outside this engine's own code and could not be confirmed here.

### Likelihood Explanation
Preconditions: review stacks must be enabled for the repository (`repository.review_stacks_enabled`), the target PR's stack must have transitioned to `archived?` (normal via PR close), and the attacker needs a second `opened`-action delivery for the same PR number to reach the endpoint with a valid signature - achievable by a repository admin/owner via GitHub's "Redeliver webhook" feature on their own repository, requiring no Shipit secrets. Attacker cost is low and the divergence is deterministic and repeatable for any repository the attacker administers.

### Recommendation
Add the missing archived guard to match the other three predicates:
```ruby
def opened_active_stack?
  opened? && stack.present? && !stack.archived?
end
```
in `app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb`.

### Proof of Concept
Minitest plan (mirrors existing sibling tests such as `test/models/shipit/webhooks/handlers/pull_request/reopened_handler_test.rb`):
1. Create a `ReviewStack` with an associated `PullRequest` (`labels: []`), then call `stack.archive!(some_user)` so `stack.archived?` is `true`.
2. Build an `opened` pull_request payload (`payload_parsed(:pull_request_opened)`) reusing the same PR `number`/environment, with `pull_request.labels` set to `[{ "name" => "malicious-label" }]`.
3. Call `Shipit::Webhooks::Handlers::PullRequest::LabelCapturingHandler.new(payload).process`.
4. Assert `stack.reload.archived?` is still `true` **and** `stack.pull_request.reload.labels` is unchanged (still `[]`) — currently this assertion fails because `capture_labels` runs and sets `labels` to `["malicious-label"]`, demonstrating the missing guard versus the passing equivalent test for `reopened`/`labeled`/`unlabeled` actions which already assert no mutation on archived stacks.
