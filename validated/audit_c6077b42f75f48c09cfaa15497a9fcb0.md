### Title
Pull request label names are merged unfiltered into the spawned deploy process environment, enabling injection of `RUBYLIB`/other dangerous variables - (File: `app/models/shipit/review_stack.rb`)

### Summary
`ReviewStack#env` merges every pull-request label name (uppercased) directly into the stack's environment hash with no allow-list, and `LabelCapturingHandler#capture_labels` persists label names verbatim from the webhook payload. This unsanitized hash flows through `TaskCommands#env` → `Command#env`/`Command#unbundled_env` → `PTY.spawn`, letting a PR author on a fork inject arbitrary environment variables (e.g. `RUBYLIB`) into every task run for that review stack, including the `deploy.override` step.

### Finding Description
The broken binding: the set of environment variables reaching `PTY.spawn` for a review-stack task should equal `Stack#env ∪ (deploy_spec allow-listed variables)`; instead it equals `Stack#env ∪ {LABEL.upcase => "true" for every PR label} ∪ (allow-listed variables)`, with **no allow-list on the label-derived keys**.

Code path:
1. `LabelCapturingHandler#capture_labels` (`app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb:98-102`) writes `pull_request.update!(labels: params.pull_request.labels.map(&:name))` straight from the `pull_request.labeled`/`opened`/`unlabeled`/`reopened` webhook body, with only `ExplicitParameters` type validation (`String`), no content allow-list. [1](#0-0) 
2. `ReviewStack#env` merges those labels, uppercased, directly into the env hash, unconditionally: `super.merge(pull_request.labels.each_with_object({}) { |n,h| h[n.upcase]='true' })`. [2](#0-1) 
3. `TaskCommands#env` merges `@stack.env` (which is `ReviewStack#env` for a review stack) into the final environment used for every task, including deploys: `super.merge(@stack.env).merge(...).merge(deploy_spec.machine_env).merge(@task.env)`. [3](#0-2) 
4. `DeployCommands#steps` runs `deploy_spec.deploy_steps!` (the `deploy.override` section) using this same `env`, via `TaskCommands#perform`, constructing `Command.new(command_line, env:, chdir:)`. [4](#0-3) [5](#0-4) 
5. `Command#unbundled_env` merges `@env.stringify_keys` (the attacker-tainted hash) over `BASE_ENV`, and `Command#start` passes this straight to `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)`. `BASE_ENV` is derived from `Bundler.unbundled_env`/`Bundler.clean_env`, which normally sets `RUBYLIB` (and other Ruby load-path variables) for the deploy process; the label-derived key `"RUBYLIB" => "true"` overrides it. [6](#0-5) [7](#0-6) 

Root cause: unlike user/API-submitted deploy variables, which are sanitized through `EnvironmentVariables#permit` (`sanitize_env_vars`, raising `NotPermitted` for keys not in `deploy_variables`) at `DeploySpec#filter_deploy_envs`/`#filter_rollback_envs` and in the deploys/rollbacks/tasks controllers' `deploy_params`, the label-derived keys injected in `ReviewStack#env` never pass through any such allow-list. [8](#0-7) [9](#0-8) 

Attacker flow: unprivileged fork PR author on a repository configured with `provisioning_behavior: allow_all` opens a PR (auto-provisioning a `ReviewStack`), then labels it (webhook `pull_request.labeled`) with a label literally named `rubylib`. GitHub sends the legitimate webhook (label name preserved verbatim); `LabelCapturingHandler` persists `["rubylib"]` on `pull_request.labels`; the next deploy on that review stack computes `env["RUBYLIB"] = "true"`, which is passed to the spawned `deploy.override` process, prepending/overriding the Ruby load path so a subsequent `require` in a ruby-based deploy step can load attacker-supplied code (e.g. if `RUBYLIB` points to an attacker-writable path, or if the label content itself is later expanded — the primitive is: attacker fully controls the value/key of an env var handed unsanitized to the spawned process).

Existing guards checked and found insufficient: `ExplicitParameters` only validates label `name` is a `String`, no value restriction; `EnvironmentVariables#permit` exists but is never invoked on this merge path; `force_github_authentication`/webhook signature verification protect the webhook transport itself but not the semantic content of legitimate label webhooks; no `Repository`/`Stack` validation restricts label content.

### Impact Explanation
An attacker with fork-PR privileges on an `allow_all` review-stack-enabled repository can inject arbitrary environment-variable keys/values (uppercased label name → `"true"`) into every task (deploy, rollback, restart tasks) executed for their own review stack, reaching the `PTY.spawn` call in `Command#start`. This can override sensitive interpreter/runtime variables such as `RUBYLIB`, `BUNDLE_GEMFILE`, `GEM_PATH`, `LD_PRELOAD`-style variables (subject to what `BASE_ENV`/`unbundled_env` exposes), corrupting the deploy process's execution environment and potentially achieving code execution on the Shipit deploy host during the `deploy.override` phase — matching the Critical RCE category. The blast radius is scoped to review stacks the attacker's own PR provisions (their own environment/branch), but that is sufficient to compromise the shared Shipit deploy host process (and thus other stacks' secrets/processes reachable from that host), since `Command`/`PTY.spawn` execute on shared infrastructure.

### Likelihood Explanation
Preconditions: repository must have `provisioning_behavior: allow_all` (or `allow_with_label`) and review stacks enabled — a documented, supported configuration. Per the stated rules of engagement, the attacker is assumed capable of opening a PR from a fork and labeling it (the rules explicitly grant "label their own PR" as an attacker capability). No Shipit credentials, secrets, or GitHub App keys are required. Cost is a single PR + a label event; the primitive is repeatable on demand for every deploy/task triggered on that stack.

### Recommendation
In `ReviewStack#env`, route the label-derived hash through the same allow-list mechanism used for other variables (`EnvironmentVariables.with(...).permit(...)`), or use a fixed, prefixed, non-overridable namespace (e.g., only expose labels under a `SHIPIT_LABEL_<NAME>` style key that cannot collide with interpreter/runtime variables), and explicitly reject/strip label names that collide with reserved environment variable names (`RUBYLIB`, `PATH`, `LD_PRELOAD`, `BUNDLE_*`, `GEM_*`, etc.) before merging into the process environment reaching `Command`.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_test.rb (add)
test "[allow_all] pull request label injects RUBYLIB into deploy.override env" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["rubylib"]

  deploy = stack.trigger_continuous_delivery
  env = Shipit::DeployCommands.new(deploy).env

  assert_equal "true", env["RUBYLIB"]

  command = Shipit::Command.new("true", env:, chdir: ".")
  assert_equal "true", command.unbundled_env["RUBYLIB"]
end
```
Both sides of the intended invariant ("`deploy.override` inherits no fork-controllable key such as `RUBYLIB`") diverge: `env["RUBYLIB"]` is expected to be `nil`/absent but equals `"true"`, and `command.unbundled_env["RUBYLIB"]` (the literal hash passed to `PTY.spawn`) also equals `"true"`, proving the attacker-controlled value reaches the spawned process's environment.

    def start(&block)
      return if @started

      @control_block = block
      @out = @pid = nil
      FileUtils.mkdir_p(@chdir)
      begin
        @out, child_in, @pid = PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)
        child_in.close
      rescue Errno::ENOENT
        raise NotFound, "#{Shellwords.split(interpolated_arguments.first).first}: command not found"
      rescue Errno::EACCES
        raise Denied, "#{Shellwords.split(interpolated_arguments.first).first}: Permission denied"
      end
      @started = true
      self
    end

    def unbundled_env
      BASE_ENV.merge('PATH' => "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}").merge(@env.stringify_keys)
    end
