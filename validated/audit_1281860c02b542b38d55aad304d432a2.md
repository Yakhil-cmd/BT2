### Title
Webhook signature verified against `repository.owner.login`'s GitHub App but the event is processed against `repository.full_name` — cross-repository/cross-organization forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate an inbound GitHub webhook using one field of the JSON payload (`repository.owner.login`, falling back to `organization.login`), but every `Handlers::Handler` subclass resolves which `Repository`/`Stack` to mutate using a *different* field of the same, attacker-suppliable JSON body: `repository.full_name`. Because Shipit supports multiple independently-configured GitHub Apps (one webhook secret per organization), a signature that is valid for organization A's app does not guarantee anything about the `repository.full_name` value the handlers actually act on.

### Finding Description
`verify_signature` computes the signing organization purely from payload content: [1](#0-0) [2](#0-1) 

The chosen GitHub App/secret is looked up per-organization, as configured e.g. in `test/dummy/config/secrets_double_github_app.yml` where `OrgOne` and `OrgTwo` each have their own independent `webhook_secret`/app credentials: [3](#0-2) [4](#0-3) 

Once the signature check passes, `create` dispatches the *entire raw payload* to every registered handler for the event, unmodified: [5](#0-4) 

Every handler then determines the target `Stack`(s) using a completely different payload field — `repository.full_name` — with no re-check that it matches the organization whose secret validated the signature: [6](#0-5) [7](#0-6) 

This is precisely the analog of the RToken bug class: the report's `melt()`/`issue()` flow breaks the invariant binding "basketsNeeded" to "totalSupply" by acting on state that is checked in one place but mutated based on a different, attacker-influenced quantity. Here the equality that must hold is:

`verified_signing_org (derived from repository.owner.login / organization.login) == acted_upon_repo_owner (derived from repository.full_name)`

Nothing in `verify_signature` or in `Handler#repository_name` enforces this equality. An operator running Shipit with more than one configured GitHub App (explicitly supported and documented, see `docs/setup.md` "Using Multiple Github Applications" and the `secrets_double_github_app.yml` fixture) exposes exactly this gap: a webhook delivered by, or crafted with the secret of, App A's installation (organization A) can carry a `repository.full_name` pointing at a repository belonging to organization B. The signature check only proves "this payload was signed by organization A's webhook secret" — it proves nothing about which repository the payload claims to be about.

### Impact Explanation
Any handler that mutates state based on `repository.full_name` (e.g. `PushHandler` enqueuing `GithubSyncJob`, `StatusHandler` creating a `Status` on a commit, `CheckSuiteHandler` enqueuing `RefreshCheckRunsJob`, `MembershipHandler` creating `Team`/`Membership` rows) can be triggered against any stack/repository/organization tracked by the same Shipit instance, as long as the attacker holds (or can obtain, e.g. by being a legitimate GitHub App installer for their own org A) a valid webhook secret for *any* organization configured on the instance — not necessarily the target organization B. This is a cross-organization write: an entity trusted only for org A's repositories can inject commit statuses, force syncs, or manipulate team/membership records tied to org B's stacks, which can influence merge-queue/deploy decisions that rely on `Status` rows. This matches the "cross-repository writes" / "unauthorized deploy" Critical/High impact categories.

### Likelihood Explanation
This requires the deployment to have configured more than one GitHub App (an explicitly documented and supported configuration), and requires the attacker to control a valid webhook secret for at least one of the configured organizations (e.g., as an app installer/admin of their own, unrelated org tracked by the same Shipit instance). This is a realistic multi-tenant Shipit deployment scenario, not a hypothetical one — the engine's own test fixtures (`secrets_double_github_app.yml`) exist specifically to exercise this multi-org configuration.

### Recommendation
Bind the verified signing organization to the organization actually acted upon: after selecting `github_app = Shipit.github(organization: repository_owner)` and verifying the signature, re-derive `repository_owner` a second time from `repository.full_name` (the same field the handlers use) and reject the webhook if it disagrees with the value used to select the signing secret. Alternatively, pass the verified organization explicitly into `Webhooks.for_event(event).each { |handler| handler.call(params, verified_organization:) }` and have `Handlers::Handler#repository_name`/`#stacks` refuse to resolve any repository whose owner does not match `verified_organization`.

### Proof of Concept
1. Deploy Shipit with two configured GitHub Apps/organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker is a legitimate installer/admin of the GitHub App for `OrgA` (their own organization), and thus can produce a validly-signed webhook using `OrgA`'s `webhook_secret` (or simply replays/crafts one from their own org's real GitHub-triggered webhook infra).
3. Attacker crafts a `push` (or `status`) payload with:
   - `repository.owner.login = "OrgA"` (or `organization.login = "OrgA"`) so `verify_signature` selects and validates against `OrgA`'s secret,
   - `repository.full_name = "OrgB/victim-repo"`.
4. `WebhooksController#verify_signature` passes because `X-Hub-Signature` matches `OrgA`'s secret over the raw body.
5. `Handlers::PushHandler#stacks` resolves `Repository.from_github_repo_name("OrgB/victim-repo")` and enqueues `GithubSyncJob` / creates a `Status` for `OrgB`'s stack, even though the attacker never held credentials scoped to `OrgB`.
