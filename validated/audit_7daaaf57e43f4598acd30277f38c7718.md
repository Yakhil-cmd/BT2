Route hop contracts are invoked under the sender's authorization tree with no venue allowlist, letting a crafted route steal the caller's wallet tokens - (File: contracts/swap-aggregator/src/venues/aquarius/pool.rs)

### Summary
The "OS command injection via unsanitized configuration" class maps onto XOXNO's route-execution model: user-supplied `swap_xdr` payload names arbitrary `pool` contract addresses, and the router invokes them with `env.invoke_contract` while the swap still runs beneath the `sender`'s `require_auth` entry. Any code a hop names executes inside the caller's authorization tree, so a `token.transfer(victim, attacker, x)` issued by a rogue "pool" is recorded — and then executed — as a child of the victim's signed auth entry. The injected "command" is the route's attacker-chosen contract address; the "shell" is the Soroban authorization frame of the swap initiator.

### Finding Description
`execute_strategy` decodes an off-chain-built `StrategyPayload` whose instruction stream references an address registry of pool/venue addresses by index — no allowlist of pool or token addresses exists (`docs/explanation/threat-model.md` states "The router calls the pool and token addresses its payload names and keeps no allowlist of them"). For an Aquarius hop, `invoke_pool_swap` calls `env.invoke_contract(pool, "swap", ...)` on the payload-supplied address [1](#0-0) , and `pool_tokens`/`assert_share_token` likewise `invoke_contract` arbitrary named addresses. The direct path is `execute_strategy(sender, total_in, swap_xdr)` with `sender.require_auth()`; the composed path is controller `swap_collateral`/`swap_debt`/`repay_debt_with_collateral`/`multiply`, where `swap_tokens` authorizes exactly one `token_in.transfer` and then calls `router.execute_strategy` with the caller's bytes [2](#0-1) .

Because `require_auth` authorizes an invocation *tree*, any `require_auth` a hop's code triggers on the sender attaches as a child of the sender's existing auth entry. Simulation (recording mode) records that child into the tree the wallet signs; enforcing mode then executes it. The harness test `rogue_hop_pool_transfer_joins_caller_auth_tree.rs` proves the full chain: a route through an attacker-deployed `RogueHopPool` whose `swap` calls `token.transfer(alice, attacker, WALLET_BALANCE)` is recorded under Alice's `swap_collateral` entry and, once signed, drains her entire balance of an unlisted wallet token [3](#0-2) [4](#0-3) .

Neither mitigation bounds this: the payload `min_out` check and the controller's measured-output/final-risk gates only constrain the swap's own token flows, not unrelated transfers appended beneath the caller's auth entry. The threat model itself acknowledges "the loss is then the caller's wallet, not the routed amount, and neither the payload minimum nor the final risk gate bounds it" [5](#0-4) .

### Impact Explanation
Theft of user funds. A single unprivileged attacker deploys a rogue contract, encodes it as a hop pool in `swap_xdr`, and serves the route to a victim (malicious quote API, phishing dApp, or compromised quote path). When the victim signs the simulated transaction, the recorded tree silently contains `token.transfer(victim → attacker)`, draining arbitrary tokens in the victim's wallet — including tokens the protocol never listed — up to any amount the attacker encodes. Severity: High (requires victim signature on an attacker-crafted transaction, but the theft is total for any token held).

### Likelihood Explanation
Routes are built off-chain and passed as opaque XDR `Bytes`; callers cannot eyeball them, and wallets display auth trees inconsistently. Every `execute_strategy` user and every composed-strategy user (`swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`) is exposed — the threat model confirms "the direct `execute_strategy` path has the same exposure for every swap user". The attacker's only cost is deploying a contract and getting the victim to sign one swap, which is the normal flow for this protocol.

### Recommendation
Constrain what a route can name on-chain: maintain a governance-managed allowlist (or venue-registry) of pool addresses per `SwapVenue`, and reject hops whose `pool` is not registered, so route bytes can only select among known venue contracts rather than arbitrary code. Independently, require that venue adapters never let hop code trigger `require_auth` on the `sender` (document and enforce that clients reject any signed auth tree containing children other than the expected input transfer — the mitigation already noted in the threat model — but treat an on-chain pool allowlist as the fix, not wallet hygiene).

fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
