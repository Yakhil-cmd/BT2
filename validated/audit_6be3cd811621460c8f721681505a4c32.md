### Title
Bash-writable `.git/sg-reviewed-shas` accounting file lets an unprivileged/adversarial model bypass the security-guidance plugin's commit and push review - ([File: plugins/security-guidance/hooks/diffstate.py])

### Summary
The `security-guidance` plugin tracks which commits have already been security-reviewed in a plain, unauthenticated, append-only text file (`.git/sg-reviewed-shas`), written by `_append_reviewed_shas` [1](#0-0)  and consulted by the push-sweep logic in `_compute_push_sweep_base` to decide which commit ranges to skip re-reviewing [2](#0-1) . This is structurally the same bug class as the BakerFi `StrategySupplyBase.harvest` finding: a piece of accounting/bookkeeping state that a privileged process (the settlement/`rebalance` call in BakerFi; the push-sweep security review here) trusts to decide whether to skip a protective action, is mutable by an unprivileged actor through an ordinary, unrestricted operation (anyone calling `harvest()`; here, the Bash tool that the model already has unrestricted read/write access to).

### Finding Description
`_append_reviewed_shas` writes plaintext lines of the form `<40-hex-sha>\t<unix-ts>\t<pv>\t<vulns_found>` to a file under `.git/` [3](#0-2) . This file is not protected by any signature, HMAC, or write-lock beyond `fcntl.flock` (which only prevents concurrent-process corruption, not malicious writes) [4](#0-3) . Its only consumer-side protection is a dedup-by-sha + cap on read [5](#0-4) .

The push-sweep flow reads this file via `_load_reviewed_shas` and treats any commit whose SHA appears in it as already vetted, advancing the diff base past it and skipping LLM review entirely for the "reviewed" prefix: `_compute_push_sweep_base` walks `push_range` and stops advancing only when a commit is *not* in `reviewed` [2](#0-1) . When every pushed commit is present in the file, `handle_push_sweep_posttooluse` exits immediately with no review at all [6](#0-5) . The per-commit review path (`handle_commit_review_posttooluse`) reads the same file to decide whether a reflog-recovered SHA has "already" been reviewed [7](#0-6) .

Because the model being supervised by this plugin has an unrestricted `Bash` tool (that is precisely the actor this security-guidance plugin exists to police, per its own adversarial threat model in `RESEARCHER.md`, which explicitly treats "the model" as the attacker for hook-bypass findings), it can trivially append a forged, well-formed line for the SHA of a commit it is about to push (or has just committed) directly to `.git/sg-reviewed-shas` via a normal file write/Bash command. There is no check anywhere in `_append_reviewed_shas`/`_load_reviewed_shas` that the recorded SHA was ever actually sent through `analyze_code_security`/the agentic reviewer — the file is a bare unauthenticated ledger that the reviewed party (the model under Claude's own supervision, or any code path with filesystem access such as a compromised subagent or prompt-injected workflow) can pre-populate.

### Impact Explanation
An adversarial or prompt-injected agent session can pre-seed `.git/sg-reviewed-shas` with the SHA of a commit that introduces a real vulnerability (e.g., a backdoor, hardcoded secret, or injected sink) before committing/pushing it. Both the per-commit review hook and the push-sweep hook will treat that commit as already vetted and silently skip the LLM security analysis, so the vulnerability is never surfaced to the user — completely defeating the purpose of the `security-guidance` plugin for that commit. This is a direct, concrete bypass of a security control (analogous to "harvest" letting a user dodge the intended fee-taking step), not a theoretical best-practice concern, because the state file that gates the check has no integrity protection and lives in a location (`.git/`) the reviewed actor (Bash/model) can already write to.

### Likelihood Explanation
Likelihood is high in any session where the model has Bash access to the repository (the default and expected configuration for this plugin) and where the model is either compromised via prompt injection or is itself the untrusted party being defended against (this plugin's own stated adversary). No special privilege beyond the ordinary Bash tool already granted to the model is required — one `echo "<sha>\t$(date +%s)\t0\t0" >> .git/sg-reviewed-shas` (or equivalent write) before the actual commit/push is sufficient.

### Recommendation
- Do not let the reviewed-commit ledger be attacker/model-writable independent of an actual completed review: bind each recorded entry to a token or signature computed by the trusted hook process at the moment the review genuinely ran (e.g., an HMAC over `sha|ts` keyed by a secret not exposed to the Bash tool), and verify it on read.
- Alternatively/additionally, store the ledger somewhere outside the paths the monitored session's Bash tool can write to (e.g., a location gated by the hook's own process privileges, not `.git/` inside the working tree), or validate on load that each SHA's diff actually corresponds to a diff that was hashed and recorded by `analyze_code_security`/the agentic reviewer at write time.
- As defense in depth, treat `.git/sg-reviewed-shas` writes as sensitive-file writes requiring the same PreToolUse scrutiny as other protected paths, so a raw `Write`/`Bash` write to it triggers a permission prompt.

### Proof of Concept
1. Start a Claude Code session with the `security-guidance` plugin enabled and Bash access (default).
2. Before staging a change that introduces a vulnerability (e.g., a hardcoded secret or command-injection sink), compute the SHA the upcoming commit will have (or use the reflog fallback path window) and run:
   ```
   git rev-parse HEAD  # or precompute the tree/commit sha for the pending change
   printf "%s\t%s\t0\t0\n" "<target_sha>" "$(date +%s)" >> .git/sg-reviewed-shas
   ```
3. Make the vulnerable change, `git commit`, and `git push`.
4. Observe that `handle_commit_review_posttooluse`/`handle_push_sweep_posttooluse` treat the commit as already reviewed (`_load_reviewed_shas` returns it as present, `_compute_push_sweep_base` advances the base past it) and no LLM security finding is ever emitted for the introduced vulnerability, even though no real review occurred.

**Uncertainty note**: I could not directly view `_reviewed_shas_path`/`_load_reviewed_shas` bodies (tool budget exhausted before the final `read_file` call completed), so the exact file path derivation and any existing sha-format validation on read are inferred from the surrounding code and comments (`diffstate.py:207-220`, `security_reminder_hook.py:717-737,965-985`) rather than confirmed byte-for-byte. A Devin session with full repo access should verify `_reviewed_shas_path` and `_load_reviewed_shas` before implementing the fix.

```python
def _append_reviewed_shas(repo_root, shas, vulns_found=0):
    """Record that `shas` were reviewed. Best-effort; never raises.

    Uses fcntl.flock for the read-gc-write; appends are O_APPEND-atomic but
    GC needs the lock so concurrent CC sessions in the same clone don't race
    each other's truncation.
    """
    p = _reviewed_shas_path(repo_root)
    if not p or not shas:
        return
    import time as _time
    ts = int(_time.time())
    pv = _PV or 0
    lines = [f"{s}\t{ts}\t{pv}\t{int(vulns_found)}\n" for s in shas]
    try:
        import fcntl
        with open(p, "a+") as f:
            fcntl.flock(f.fileno(), fcntl.LOCK_EX)
            try:
                f.seek(0)
                existing = f.read().splitlines(keepends=True)
                # Dedup by sha (first column) — keep newest, then cap.
                seen = set()
                merged = []
                for ln in (existing + lines)[::-1]:
                    sha = ln.split("\t", 1)[0].strip()
                    if sha and sha not in seen:
                        seen.add(sha)
                        merged.append(ln if ln.endswith("\n") else ln + "\n")
                merged = merged[:_REVIEWED_SHAS_CAP][::-1]
                f.seek(0)
                f.truncate()
                f.writelines(merged)
            finally:
                fcntl.flock(f.fileno(), fcntl.LOCK_UN)
```

```python
def _compute_push_sweep_base(prev_upstream, push_range, reviewed):
    """Advance the diff base past the contiguous reviewed prefix.

    Spec: review `git diff B..HEAD` where `B` is the newest commit such that
    `prev_upstream..B` is entirely in `reviewed`. Returns (B, unreviewed_tail).
    `B == None` means the whole range is reviewed (caller should skip).
    `push_range` must be oldest→newest.

    Examples (✓=reviewed, ✗=not):
      [✓1, ✗2, ✓3]  → B=1, tail=[2,3]   (cannot trim suffix; Read is at HEAD)
      [✓1, ✓2, ✓3]  → B=None            (all reviewed → skip)
      [✗1, ✓2, ✗3]  → B=prev_upstream, tail=[1,2,3]
      []            → B=None
    """
    i = 0
    while i < len(push_range) and push_range[i] in reviewed:
        i += 1
    if i == len(push_range):
        return None, []
    base = push_range[i - 1] if i > 0 else prev_upstream
    return base, push_range[i:]
```
