### Title

Unvalidated strategy route can inject unauthorized user token transfers into the signed authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary

`swap_collateral`, `repay_debt_with_collateral`, `swap_debt`, and `multiply` accept attacker-influenced opaque route bytes and execute them through the configured router without constraining which contracts the route may invoke. Because the strategy root calls `caller.require_auth()`, a malicious venue reached by the route can request additional `token.transfer(caller, attacker, amount)` authorizations that simulation records beneath the caller’s strategy authorization. If the caller signs the simulated poisoned tree, the malicious venue can steal unrelated wallet tokens while still returning enough output for the lending strategy to finish successfully. This is the Soroban analogue of injecting caller-controlled content into a privileged operation: route data crosses the controller boundary and changes the authority scope beyond the intended token transfer.

### Finding Description

The public `swap_collateral` entrypoint accepts a caller-controlled `swap: Bytes` argument and forwards it unchanged into `SwapCollateralParams`. [1](#0-0) 

`process_swap_collateral` authenticates the caller, verifies account ownership or delegation, withdraws collateral, and passes the same route to `withdraw_and_swap_from_supply`. [2](#0-1) 

The common strategy helper forwards the route to `swap_tokens_or_passthrough`. [3](#0-2) 

`swap_tokens` checks only that the input amount is positive, the route is nonempty, the router does not overspend the granted input, and a positive amount of the expected output token arrives. [4](#0-3) 

The controller grants only an exact input-token transfer to the router, but it does not identify or restrict the downstream pool and token contracts named inside the route. [5](#0-4) 

The project’s threat model explicitly states that the router does not allowlist route-named pools or token addresses, and that third-party route code can place a caller-token transfer beneath the caller’s authorization entry. [6](#0-5) 

The included regression test demonstrates the behavior with a route-selected rogue pool calling `token.transfer(alice, attacker, WALLET_BALANCE)`. [7](#0-6) 

During simulation, that unrelated transfer is recorded as a child of Alice’s `swap_collateral` authorization rather than being attributed to the router or rejected at the controller boundary. [8](#0-7) 

In enforcing mode, an honest authorization tree rejects the rogue transfer, but the exact simulated poisoned tree authorizes it and transfers Alice’s entire unrelated wallet balance to the attacker. [9](#0-8) 

The same route boundary is used by `swap_debt`, `repay_debt_with_collateral`, and `multiply`, so the issue is not limited to collateral conversion. [10](#0-9) [11](#0-10) [12](#0-11) 

### Impact Explanation

A malicious route can steal token balances unrelated to the lending position from the account owner or delegate who signs the poisoned authorization tree. The measured-output and final-risk checks do not bound the loss because they inspect only the strategy’s declared input and output tokens, not additional token transfers authorized beneath the strategy root. The repository’s proof demonstrates both fair strategy completion and complete theft of an unlisted wallet token. This is theft of user funds and therefore High severity.

### Likelihood Explanation

Exploitation requires the victim to execute an attacker-supplied route and sign the authorization tree produced by simulation, so it is not an unauthenticated or fully signature-free theft. The attack is nevertheless realistic because routes are opaque bytes, commonly generated off-chain, and the malicious child authorization is mechanically included by ordinary simulation rather than requiring a host bug. Any strategy caller or delegate can be targeted, and the malicious route can satisfy the protocol checks by returning a nominally valid output.

### Recommendation

Constrain route execution so venue contracts cannot invoke token transfers under the end user’s authorization. Prefer a router boundary that allows only predeclared, venue-specific pool calls and prevents arbitrary route-selected contracts from inheriting caller authority. At minimum, expose the complete expected authorization tree before signing, make wallets reject strategy signatures containing unrelated token transfers, and consider structuring calls so the user’s authorization cannot match descendant calls outside the exact strategy transfer. The controller should also enforce a minimum expected output argument instead of treating any positive output as successful.

### Proof of Concept

The repository already contains a focused proof in `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`:

1. Alice supplies `10_000 USDC`, owns an unrelated wallet token balance of `77_770_000_000`, and the controller is configured with a router that calls the route-selected pool. [13](#0-12) 
2. The crafted route encodes a `RogueHopPool` containing `(alice, wallet_token, attacker, amount)`, plus fair USDC-to-ETH output values. [14](#0-13) 
3. Alice invokes `swap_collateral(alice, account_id, USDC, 50_000_000_000, ETH, route)`. [15](#0-14) 
4. The rogue pool executes `wallet_token.transfer(alice, attacker, amount)` during route execution. [16](#0-15) 
5. Simulation records that transfer beneath Alice’s `swap_collateral` authorization and shows Alice’s wallet token balance reduced to zero while the fair ETH output is credited. [8](#0-7) 
6. Replaying with the poisoned signed tree succeeds; replaying with the honest tree fails authorization and leaves Alice’s wallet token untouched. [9](#0-8)

That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
user.

fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
