### Title
PR label names are merged verbatim into deploy/review-stack environment, allowing `GEM_PATH`/`GEM_HOME` (and any other var) injection into `PTY.spawn` - ([File: app/models/shipit/review_stack.rb])

### Summary
`Shipit::ReviewStack#env` merges every entry of `pull_request.labels` directly into the environment hash with no allow-list or deny-list, using `label_name.upcase => "true"`. Because `TaskCommands#env` merges `@stack.env` and that result is passed straight into `Command#unbundled_env`, which is what `Command#start` feeds to `PTY.spawn`, an attacker who can label their own PR (`gem_path`, `gem_home`) can set `GEM_PATH`/`GEM_HOME` for every command run in that PR's review-stack tasks, including `install_dependencies`.

### Finding Description
Binding claimed: `GEM_PATH`/`GEM_HOME` in `Command#unbundled_env` must equal values from `Shipit.env` or `deploy_spec.machine_env` only, never from `PullRequest#labels`.

Actual code:
- `Shipit::ReviewStack#env` unconditionally merges labels into env with no filtering: [1](#0-0) 
- `TaskCommands#env` merges `@stack.env` (which is `ReviewStack#env` for review stacks) before `deploy_spec.machine_env` and `@task.env`: [2](#0-1) 
- `install_dependencies` builds each `Command` with this exact `env:`: [3](#0-2) 
- `Command#unbundled_env` merges `@env.stringify_keys` last, i.e. after `BASE_ENV`, so label-derived keys win over any legitimate `GEM_PATH`/`GEM_HOME` values from `Shipit.env`/Bundler's clean env: [4](#0-3) 
- This merged env is exactly what `Command#start` passes to `PTY.spawn`: [5](#0-4) 

Root cause: `ReviewStack#env` treats attacker-controlled `PullRequest#labels` as trusted environment-variable source with no name filtering (no allow-list, no reserved-name blocklist for `GEM_PATH`, `GEM_HOME`, `BUNDLE_*`, `PATH`, etc.). This is not a latent oversight but codified/expected behavior — there is an existing test asserting arbitrary labels become env vars: [6](#0-5) [7](#0-6) 

Attacker path: An unprivileged GitHub user opens a PR against a repo with review-stack support enabled, and adds labels `gem_path` and `gem_home` to their own PR (label add/remove is a normal PR action any contributor with issue-write can do, or via the webhook flow that captures labels from the GitHub payload into `PullRequest#labels`). No Shipit session, API token or maintainer role is required to add labels to one's own PR in many repo configurations, and the webhook handler that syncs labels into `PullRequest#labels` is triggered by normal GitHub `pull_request` events, verified only via `verify_signature`/webhook secret (an authentication gate on the request source, not on label content). Once synced, any task/deploy running for that PR's review stack — e.g. `install_dependencies` running `bundle install` — executes with `GEM_PATH=true GEM_HOME=true` (or any attacker-chosen values, since label names are freely chosen strings, not booleans — the value is fixed to `"true"` but the *name* is fully attacker-controlled) in its `PTY.spawn` environment.

Existing guards checked and why they don't prevent this: `verify_signature`/webhook signature verification only authenticates that the payload came from GitHub for that repo — it does not restrict which label names are acceptable. There is no `EnvironmentVariables#permit` call in `ReviewStack#env` restricting variable names. `deploy_spec.machine_env`/`Shipit.env` are merged but do not overwrite the label-derived keys because they are merged **before** the label merge in `Command#unbundled_env`'s merge order (`BASE_ENV` then `@env.stringify_keys` last).

### Impact Explanation
Note on severity as literally requested (`GEM_PATH=true`, `GEM_HOME=true`): setting these to the literal string `"true"` (not a real path) would not resolve to a functioning gem path an attacker controls — RubyGems would treat `"true"` as a non-existent/invalid directory, most likely breaking `bundle`/`gem` invocations (denial-of-service-like breakage of that PR's own review deploy) rather than redirecting gem resolution to an attacker-supplied bogus directory with attacker binaries. To achieve actual gem-resolution hijack (Critical/RCE), the attacker would need the env value to point to a path they control on the deploy host's filesystem, which the current mechanism (fixed `"true"` value from label name) does not provide. So the concrete RCE-via-gem-hijack scenario in the question is not fully substantiated by this code path — it demonstrates arbitrary env-variable name injection with a fixed value, not arbitrary value injection.

That said, the underlying primitive — unfiltered, attacker-named environment variables reaching `PTY.spawn` for that PR's own review-stack tasks — is real and already env-injection scoped to the labeling PR's own deploy (not cross-tenant), matching the described "scoped impact." Env-var name injection with a fixed value can still corrupt tool behavior (e.g., `BUNDLE_GEMFILE=true`, `RUBYOPT=true`) for that stack's steps, but does not by itself demonstrate credential exfiltration or code execution beyond the attacker's own review stack.

### Likelihood Explanation
Preconditions: review-stack feature enabled for the repo, attacker able to open a PR against it and get labels attached (typical for public repos accepting PRs, and depending on repo config, contributors may self-label or maintainers may label — the exact permission model for label-setting was not verified against GitHub semantics in this codebase; `PullRequest#labels` is simply synced from GitHub webhook payloads). Attacker cost is low (open a PR, add labels), fully repeatable, and confined to the attacker's own review-stack deploy given the code path traced.

### Recommendation
In `Shipit::ReviewStack#env`, reject or drop reserved/dangerous variable names (`GEM_PATH`, `GEM_HOME`, `BUNDLE_*`, `PATH`, `RUBYOPT`, `LD_PRELOAD`, etc.) before merging label-derived entries, or invert the merge order in `Command#unbundled_env`/`TaskCommands#env` so that `Shipit.env` and `deploy_spec.machine_env` always take precedence over stack/label-derived env, guaranteeing `GEM_PATH`/`GEM_HOME` can only originate from those two trusted sources.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_test.rb (or task_commands_test.rb)
test "#env does not let PR labels override GEM_PATH/GEM_HOME" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["gem_path", "gem_home"]
  task = shipit_tasks(:shipit_restart)
  task.stack = stack

  env = Shipit::TaskCommands.new(task).env

  refute_equal "true", env["GEM_PATH"]
  refute_equal "true", env["GEM_HOME"]
  # Assert instead that GEM_PATH/GEM_HOME (if present) match Shipit.env or deploy_spec.machine_env
end
```
Given current code, `env["GEM_PATH"]` and `env["GEM_HOME"]` would equal `"true"`, failing this assertion — confirming the unfiltered merge, though (per Impact Explanation) this demonstrates env-name injection with a fixed value rather than a fully attacker-controlled path for gem-resolution hijack.

    def start(&block)
      return if @started

      @control_block = block
      @out = @pid = nil
      FileUtils.mkdir_p(@chdir)
      begin
        @out, child_in, @pid = PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)
        child_in.close
      rescue Errno::ENOENT
        raise NotFound, "#{Shellwords.split(interpolated_arguments.first).first}: command not found"
      rescue Errno::EACCES
        raise Denied, "#{Shellwords.split(interpolated_arguments.first).first}: Permission denied"
      end
      @started = true
      self
    end
