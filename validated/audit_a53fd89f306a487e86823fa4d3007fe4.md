### Title
`AssignedHandler` mutates a `PullRequest` for a repository the webhook's authenticating org never owned - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which org's `webhook_secret` authenticates a request using `params.dig('repository','owner','login')`, while `AssignedHandler` (and every other `pull_request` handler) resolves the target repository independently from `params.repository.full_name`. If the attacker names a configured-but-secretless org for `owner.login`, `GitHubApp#verify_webhook_signature` returns `true` unconditionally, letting the attacker set `full_name` to point at any other tracked repository whose `PullRequest` record then gets overwritten.

### Finding Description
The broken binding is: the code implicitly assumes `params.repository.owner.login == params.repository.full_name.split('/').first`, i.e. the org used to pick the `GitHubApp`/secret in `verify_signature` is the same org that owns the repository mutated downstream. Nothing enforces this.

- `verify_signature` computes `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0)  and looks up `Shipit.github(organization: repository_owner)` [2](#0-1) .
- `GitHubApp#verify_webhook_signature` short-circuits to `true` when that org's `webhook_secret` config value is blank: `return true unless webhook_secret` [3](#0-2) . So naming any configured org with no `webhook_secret` set in `repository.owner.login` defeats signature verification entirely, with no relation to which repository is actually targeted.
- `AssignedHandler` never looks at `repository.owner.login` at all. It resolves the acted-upon repository purely from `params.repository.full_name` via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [4](#0-3) , then finds an existing `PullRequest` scoped to that repository's stacks [5](#0-4) , and on `assigned`/`unassigned` actions calls `pull_request.update(github_pull_request: params.pull_request)` [6](#0-5) .
- `PullRequest#github_pull_request=` rewrites `title`, `state`, `additions`, `deletions`, `user`, `assignees`, `labels`, and `head` (resolving/creating a `Commit` for an attacker-supplied SHA via `stack.github_api.commit(...)`) [7](#0-6) .

Exploit flow: attacker owns/controls a GitHub org (or picks an existing Shipit-configured org) that has no `webhook_secret` set. They send `POST /webhooks` with header `X-Github-Event: pull_request`, body `action: "unassigned"`, `repository.owner.login` = that secretless org, and `repository.full_name` = `victim-org/victim-repo` (a real tracked repository with an existing `PullRequest#number` matching a real open PR). `verify_signature` passes trivially because the secretless org's `verify_webhook_signature` always returns `true`. `AssignedHandler` then resolves `victim-org/victim-repo` from `full_name` and overwrites that stack's existing `PullRequest` record's title/state/labels/assignees/head commit — data belonging to a repository/org whose own secret was never checked.

Existing guards fail because `drop_unhandled_event` and the `ExplicitParameters` schema only validate structure/presence, not org/repo consistency; `force_github_authentication`, `User#authorized?`, `require_permission!`, and the `stacks` scope are session/API-token guards that don't apply to the unauthenticated `/webhooks` endpoint; and `verify_signature`'s only failure mode is `GithubOrganizationUnknown` (unconfigured org name), which does not trigger when the attacker picks a real, configured, but secretless org.

### Impact Explanation
This is a cross-tenant record-mutation bug: a request that only proves control of one (secretless) org's identity can write to the `PullRequest` of an entirely different, victim-owned repository/stack, matching the rules' explicit Critical category "a payload for one repository mutating another's stack, commit, task or team." However, for this specific handler (`AssignedHandler`/`unassigned`), the write is confined to updating an *existing* `PullRequest`'s metadata (title, state, labels, assignees, head commit reference) — it does not itself enqueue a `Task`, invoke `Command`/`PTY.spawn`, or trigger review-stack provisioning (that provisioning path belongs to `OpenedHandler`, gated on `action == "opened"`, which `AssignedHandler` never reaches). I could not find a code path in `AssignedHandler`/`PullRequest#github_pull_request=` that feeds attacker data into `Command#args` or the `PTY.spawn` environment; the only side effect beyond the record write is a GitHub API read (`stack.github_api.commit`) to resolve a commit by SHA. Given the audit's strict framing that impact must reach RCE/command-execution/credential-exfiltration/auth-bypass or record mutation for an unauthenticated repo, the record-mutation clause is satisfied, but the specific RCE/"shipit.yml execution" amplification claimed in the question is not established for this handler — that amplification applies to `OpenedHandler`, a different entrypoint not exercised by `action=unassigned`.

### Likelihood Explanation
Requires: (1) at least one org configured in Shipit's `secrets.github` without a `webhook_secret` (a legitimate, not-uncommon misconfiguration for a low-value/testing org) — the attacker only needs to know or guess its login name, not any secret; (2) the target victim repository/stack already tracked by Shipit with an existing `PullRequest` row (created via a prior legitimate `opened` webhook) matching the forged `number`. No GitHub or Shipit credentials, sessions, or team membership are needed — only the ability to send an arbitrary unauthenticated HTTP POST to `/webhooks`, which is explicitly in-scope for an unprivileged internet attacker. This is repeatable against any victim repository/stack sharing the Shipit instance, for any PR number that already has a persisted record.

### Recommendation
In `WebhooksController#verify_signature`, require `params.dig('repository','owner','login')` (or `organization.login`) to match the org implied by `params.dig('repository','full_name')`; reject the request if they diverge. Additionally, treat a blank/missing `webhook_secret` for a configured org as a hard misconfiguration error (reject signature) rather than an automatic pass in `GitHubApp#verify_webhook_signature`, or at minimum log/alert and refuse "trivially verified" webhooks whose `full_name` doesn't belong to the authenticating org.

### Proof of Concept
minitest plan (`test/controllers/webhooks_controller_test.rb` style, no live GitHub):
1. Configure `Shipit.github` with two orgs: `no-secret-org` (no `webhook_secret` key) and `victim-org` (`webhook_secret: "victim-secret"`).
2. Create `victim-org/victim-repo` as a tracked `Shipit::Repository`, a `Stack`, and a `PullRequest` with `number: 42`, `title: "original"`.
3. POST to `/webhooks` with header `X-Github-Event: pull_request`, no valid `X-Hub-Signature` (or a garbage one), and JSON body: `{"action":"unassigned","number":42,"repository":{"owner":{"login":"no-secret-org"},"full_name":"victim-org/victim-repo"},"pull_request":{...title: "PWNED", ...}, "sender":{"login":"attacker"}}`.
4. Assert response is `200 OK` (not `422`), proving `verify_signature` passed.
5. Assert `Shipit::PullRequest.find_by(number: 42, stack: victim_stack).title == "PWNED"`, proving the victim stack's record was mutated by a request that never authenticated against `victim-org`'s `webhook_secret`.
6. Assert (equality check both sides): `payload_owner_org = "no-secret-org"` vs `actual_repo_org = "victim-org"` — these differ, yet the mutation succeeded, confirming the binding is broken.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
