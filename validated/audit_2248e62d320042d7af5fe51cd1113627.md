### Title
Signature-authenticated organization does not match repository whose `PullRequest` record `AssignedHandler` mutates - (File: app/controllers/shipit/webhooks_controller.rb, lib/shipit/github_app.rb, app/models/shipit/webhooks/handlers/pull_request/assigned_handler.rb)

### Summary
`WebhooksController#repository_owner` selects which per-organization webhook secret is used to authenticate a `pull_request` webhook, falling back to `params.dig('organization','login')` when `repository.owner.login` is absent. `AssignedHandler`, whose `ExplicitParameters` schema never requires `repository.owner.login`, instead resolves the target repository purely from `params.repository.full_name`. These two fields are independently attacker-controlled in the JSON body, so a signature validated for organization A's secret can be paired with a `repository.full_name` pointing at organization B's stack, letting the handler write into a `PullRequest` record belonging to a repository that never authenticated the request.

### Finding Description
The broken binding: the code implicitly assumes `repository_owner == owner(params.repository.full_name)`. In reality:
- `repository_owner` (`app/controllers/shipit/webhooks_controller.rb:59-62`) is `params.dig('repository','owner','login') || params.dig('organization','login')`.
- `verify_signature` (`webhooks_controller.rb:24-30`) uses this value to pick the `GitHubApp` (and its `webhook_secret`) via `Shipit.github(organization: repository_owner)`.
- `AssignedHandler#repository` (`assigned_handler.rb:67-69`) instead resolves the target `Shipit::Repository` from `params.repository.full_name` via `Shipit::Repository.from_github_repo_name`.
- The handler's `ExplicitParameters` schema (`assigned_handler.rb:33-35`) only requires `repository.full_name`; it never requires `repository.owner.login`, so an attacker can omit it, forcing the controller's fallback to `organization.login`.

An attacker who controls an organization/repo whose webhook secret they know (e.g. they configured that org's GitHub App/webhook integration into a multi-org Shipit instance) can:
1. Compute a valid `X-Hub-Signature` using their own org's `webhook_secret`.
2. Set `organization.login` = their own org (drives `repository_owner` and thus signature verification via `Shipit.github`/`GitHubApp#verify_webhook_signature`, `lib/shipit/github_app.rb:76-83`).
3. Omit `repository.owner.login`.
4. Set `repository.full_name` = `"victim-org/victim-repo"` and `number` = an existing PR number on that victim stack.
5. Set `action` = `unassigned` (or `assigned`).

`AssignedHandler#process` finds the victim's `Shipit::PullRequest` by `number` + `repository.id` (from `params.repository.full_name`) and calls `pull_request.update(github_pull_request: params.pull_request)`, writing attacker-supplied title/state/assignees/labels/head sha/ref data into a record belonging to a repository the attacker never authenticated for.

This only matters when Shipit is configured with the multi-organization GitHub App schema (`secrets.github` keyed by org name; see `github_default_organization`/`github_app_config` in `lib/shipit.rb:170-200`). In legacy single-org config, `github_default_organization` is `nil`, so `Shipit.github` ignores the `organization:` argument entirely and always uses the single shared secret — the cross-org divergence has no effect there. No other guard (`drop_unhandled_event`, `ExplicitParameters`, `Repository#from_github_repo_name`) checks that the authenticated `repository_owner` matches the repository referenced inside the payload.

### Impact Explanation
An attacker owning one organization's webhook secret in a multi-org Shipit deployment can, per request, overwrite the cached `github_pull_request` JSON on any `PullRequest` record of any other organization's repository/stack, provided they know the target repo's `full_name` and an existing PR `number` (both publicly discoverable on GitHub). This is a genuine "payload for one repository mutating another's" record, and is repeatable against any repository/stack, including a production-environment stack, without any privileges on the victim organization. However, `AssignedHandler#process` itself only performs a metadata cache update (`pull_request.update(github_pull_request: ...)`); it does not directly invoke deploy, rollback, or merge, so the "unauthorized deploy/rollback/merge" impact claimed in the question is not directly demonstrated by this handler — the concretely provable impact is unauthorized cross-tenant write to a `PullRequest` record.

### Likelihood Explanation
Requires: (1) Shipit configured with the multi-organization GitHub App secrets schema (`secrets.github` keyed per-org, each with its own `webhook_secret`), and (2) the attacker legitimately controlling at least one such organization's webhook secret. Given those preconditions, exploitation cost is a single crafted HTTP POST with a valid HMAC for the attacker's own org and a fabricated JSON body — no GitHub API calls, no privileged Shipit session or API token needed, and it is fully repeatable against arbitrary victim repos/PR numbers.

### Recommendation
In `AssignedHandler` (and sibling `pull_request` handlers), require `repository.owner.login` in the `ExplicitParameters` schema and verify it matches the `repository_owner` used for signature verification (or better, derive the target repository's owner from the same field used to authenticate the webhook) before performing any lookup/update, rejecting the event if they diverge.

### Proof of Concept
Under `test/controllers/webhooks_controller_test.rb`, in a multi-org secrets fixture (two orgs `"attacker-org"` and `"victim-org"`, each with distinct `webhook_secret`) and a production-environment stack under `victim-org/victim-repo` with an existing `Shipit::PullRequest#number`:
- Build payload: `action: "unassigned"`, `number: <victim pr number>`, `repository: { full_name: "victim-org/victim-repo" }` (no `owner` key), `organization: { login: "attacker-org" }`, plus required `pull_request`/`sender` sub-objects.
- Sign with `attacker-org`'s `webhook_secret` and POST to `/webhooks` with header `X-Github-Event: pull_request`.
- Assert response is `200`/`:ok` (not `422`), i.e. `repository_owner` resolved to `"attacker-org"` and signature verification passed using `attacker-org`'s secret (`OpenSSL::HMAC.hexdigest` over the body with that secret).
- Assert the victim `Shipit::PullRequest` record's `github_pull_request` column was updated with attacker-supplied `params.pull_request` content, proving a write into `victim-org`'s stack authenticated by `attacker-org`'s secret. [1](#0-0) [2](#0-1) [3](#0-2)

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([

    rescue Shipit::GithubOrganizationUnknown => e

        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
