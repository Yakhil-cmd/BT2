### Title
Unrecoverable `has_in_flight_tx` lock in `WalletContract::rlp_execute` when a callback runs out of gas - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
`WalletContract` enforces "only one transaction in flight at a time" the same way `BridgedGovernor` enforces strict sequential message ordering: a boolean flag (`has_in_flight_tx`) gates the entry point (`rlp_execute`) and is only cleared inside the follow-up callbacks. If one of those callbacks fails to run to completion (panics, e.g. due to gas exhaustion) instead of returning a `Result`/graceful error, the entire receipt's state mutations — including the flag reset — are rolled back, leaving the contract permanently unable to accept any further `rlp_execute` calls, exactly analogous to `BridgedGovernor` becoming stuck on a non-executable relayed message.

### Finding Description
`rlp_execute` refuses to process any call while `self.has_in_flight_tx` is `true`, unconditionally returning an error response and never creating a promise or changing state in that case: [1](#0-0) 

The flag is set to `true` whenever a promise is dispatched (`rlp_execute`, and each intermediate callback), and is only reset to `false` as the very first statement inside each of the callbacks (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, `ban_relayer`): [2](#0-1) [3](#0-2) [4](#0-3) 

Because a NEAR function-call execution is atomic, if a callback panics for any reason after entry (rather than returning gracefully), *all* of its state writes — including the `self.has_in_flight_tx = false` write made at the top of the function — are reverted, and the contract state remains at whatever it was when the callback was invoked, i.e. `has_in_flight_tx = true`. The callback gas budgets are static constants plus the user-controlled `action.gas()` value taken from the RLP-encoded Ethereum transaction, not sized to cover variable-cost work performed inside the callback (JSON deserialization of an external contract's response, promise construction, etc.): [5](#0-4) [6](#0-5) 

If the gas allotted to a callback is exhausted while it executes (e.g., an oversized/expensive response from `storage_balance_of` or the address registrar, or a tightly budgeted `action.gas()`), the callback panics with "exceeded the prepaid gas" instead of reaching any of its `return` paths, and the flag reset is rolled back. Since `rlp_execute` is the only entry point and it unconditionally short-circuits while `has_in_flight_tx == true`, and there is no privileged/administrative function to clear the flag, the wallet contract instance becomes permanently unable to execute any further Ethereum-emulated transaction — mirroring the `BridgedGovernor.lzReceive` bug where a non-executable relayed message leaves the contract irrecoverably stuck because the only way to progress (or to fix the contract) is gated by the same stuck state.

### Impact Explanation
This is reachable by any unprivileged caller: a user (or an untrusted relayer acting on the user's behalf) submits a `rlp_execute` call whose downstream callback is gas-starved. Once this happens, the affected `WalletContract` instance is permanently bricked — every future `rlp_execute` call for that eth-implicit account will be rejected with "transaction already in progress," with no path to recovery (no admin reset, no upgrade mechanism visible in this contract). This constitutes a permanent denial of service against that account's wallet functionality, matching the "unrecoverable state" impact class described in the source report.

### Likelihood Explanation
The precondition is a callback running out of its statically-sized gas budget. Because `action.gas()` is attacker/user-supplied and the callback's fixed gas overhead (`RLP_EXECUTE_CALLBACK_GAS`, `ADDRESS_CHECK_CALLBACK_GAS`, `NEP_141_STORAGE_BALANCE_CALLBACK_GAS` — all hardcoded at 5 TGas or small multiples) is not guaranteed to be sufficient for all response sizes/paths (JSON parsing of arbitrary registrar/NEP-141 responses, multi-action promise construction), a caller who controls or influences the target/token contract's response size (or simply supplies borderline `action.gas()` values) can trigger this deterministically. This is a real, low-cost path from an ordinary unprivileged transaction, though it requires the caller to construct a transaction that lands exactly in the gas-exhaustion window for one of the callbacks.

### Recommendation
- Do not rely on the same state variable being both "reset to false" and later "guaranteed reset" within the same atomic call; instead, ensure the in-flight flag is only ever cleared/reset atomically with the outcome of the call, or track completion via a mechanism that cannot be reverted along with a partial failure (e.g., have a keeper/self-heal path that clears the flag when it detects an execution outcome that no longer has a pending promise).
- Size callback gas allocations defensively (bound the size of external responses that will be deserialized, or set generous fixed budgets not derived solely from `action.gas()`), and prefer catching failures before they can panic (e.g., limit/validate response sizes before calling `serde_json::from_slice`).
- Add a privileged or time-based recovery path (analogous to allowing out-of-order/unordered execution in the referenced fix) so a stuck `has_in_flight_tx` cannot permanently brick the contract instance.

### Proof of Concept
1. Deploy `WalletContract` to an eth-implicit account.
2. Craft an RLP-encoded Ethereum transaction representing an `ERC20Transfer` (or `EOABaseTokenTransfer` with `address_check`) whose `action.gas()` is set to a minimal value, and target a token/registrar contract that returns a large/expensive-to-deserialize JSON payload from `storage_balance_of`/`lookup`.
3. Call `rlp_execute`; the outer cross-contract call succeeds and schedules `nep_141_storage_balance_callback`/`address_check_callback` with gas = fixed constant + `action.gas()`.
4. The callback begins execution (having implicitly relied on eventually resetting `has_in_flight_tx` first, but the whole call is one atomic unit) and runs out of gas partway through (e.g. while deserializing the large response or constructing the follow-up promise), causing a panic.
5. The entire receipt's state changes revert, so `has_in_flight_tx` remains `true` as it was before the callback ran.
6. Any subsequent call to `rlp_execute` is rejected at lines 97-105 with "transaction already in progress," permanently, since nothing in the contract can ever set `has_in_flight_tx` back to `false` again.
