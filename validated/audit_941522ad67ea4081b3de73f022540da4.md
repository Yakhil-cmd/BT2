### Title
Cross-tenant Status forgery via sha-only matching in `StatusHandler#process` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves target commits purely by `sha`, with no check that the webhook's `repository.full_name`/`repository_owner` matches the repository of the `Commit`'s `Stack`. Since `shipit_commits` is only uniquely indexed on `(stack_id, sha)` and not globally unique on `sha`, two different stacks (tenants) tracking the same underlying git history (e.g. a mirrored/forked repository configured as a separate Shipit stack) can each hold a `Commit` row with an identical `sha`. A single, validly-signed webhook for one of those repositories will iterate every matching `Commit` regardless of which stack/repository it belongs to and call `Status.replicate_from_github!` for each, writing a `Status` row into a stack the webhook's own repository never authenticated.

### Finding Description
Binding as stated by the question ("`webhook_secret` authorizes exactly 1 stack") is not itself the root cause — `webhook_secret` in this engine is configured per GitHub App/organization (`lib/shipit/github_app.rb:44-50,76-83`), so it already legitimately authorizes every stack in that organization; that is by design, not a bug. The real broken binding is: *the repository named in the signed payload (`repository.full_name`, exactly 1) == the set of repositories whose stacks receive a new `Status` row*. This is violated whenever N>1 `Commit` rows across different stacks share the same `sha`.

Trace:
1. `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) only confirms the HMAC signature matches `Shipit.github(organization: repository_owner)`'s secret — it authenticates that the payload was sent by GitHub for that organization, it does **not** bind the payload to a specific repository/stack beyond what's inside the payload itself.
2. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) does:
```
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
There is no filter on `commit.stack.repository` vs. the payload's `repository` field at all.
3. `Commit#create_status_from_github!` → `statuses.replicate_from_github!(stack_id, github_status)` (`app/models/shipit/commit.rb:165-169`) → `Status.replicate_from_github!` (`app/models/shipit/status.rb:24-33`) creates/finds a `Status` scoped to `commit.stack_id`, for every matching commit.
4. The `sha` index (`db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`) is `(stack_id, sha)`, confirming the schema intentionally allows the same `sha` to exist under multiple different `stack_id`s (e.g. an upstream repo and its internal mirror tracked as two separate Shipit stacks, or two stacks pointed at the same GitHub repository with different `environment`s).

Attack: an unprivileged owner of repository A (which shares commit history with repository B, tracked by a different, unrelated tenant's stack) pushes a commit and lets a normal CI system post a `status` event for that commit's sha to repository A's configured Shipit webhook. GitHub signs this webhook legitimately with repository A's organization secret. `StatusHandler#process` matches the sha against **every** `Commit` row in the database with that sha — including the `Commit` belonging to stack B, which never received (and never signed) any event for its own repository — and writes a new `Status` row under stack B's `stack_id`.

Existing guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema) validate payload origin/format but never cross-check `params.dig('repository','full_name')` against `commit.stack.repository`, so none of them stop this divergence.

### Impact Explanation
A webhook event genuinely originating from repository A can cause a `Status` row (state/description/context/target_url) to be written into stack B, a different tenant's stack, without stack B's repository ever authenticating that event — this is "a payload for one repository mutating another's stack/commit" per the Critical bucket. `Status` creation also triggers `enable_ci_on_stack` and `schedule_continuous_delivery` (`app/models/shipit/status.rb:18-19`), meaning a forged/borrowed CI status for a shared sha can influence merge/continuous-deployment decisions (e.g. `ProcessMergeRequestsJob`) on a stack the attacker has no relationship with. The blast radius scales with however many stacks in the Shipit instance happen to track overlapping commit history (mirrors, forks, multi-environment stacks of the same repo).

### Likelihood Explanation
Requires: (a) Shipit configured with ≥2 stacks whose `Commit` tables can contain the same `sha` (a common, legitimate configuration for mirrored/forked repositories or multi-environment stacks of one upstream repo), and (b) the attacker being able to trigger (not forge) a genuine GitHub `status` webhook on one of the repos they control or contribute to (trivially done via a PR/branch/CI run — no secrets needed). No `webhook_secret`, session, or API token is required by the attacker; GitHub signs and delivers the event on their behalf. This is straightforward and repeatable for any Shipit deployment that tracks the same repository/commit history under multiple stacks.

### Recommendation
In `StatusHandler#process` (and analogously any other sha-keyed webhook handler), restrict matching commits to the stack(s) whose `Stack#repository` (owner/name) equals the payload's `repository.full_name`/`repository_owner`, e.g. `Commit.joins(:stack).where(sha: params.sha, shipit_stacks: { repository_id: repository_from_payload.id })`, before calling `create_status_from_github!`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual)
test "status webhook only updates the stack matching the payload's repository" do
  repo = shipit_repositories(:shopify_shipit) # repository referenced in payload
  other_repo = shipit_repositories(:cyclimse) # unrelated tenant repository

  stack_a = shipit_stacks(:shipit)      # tracks `repo`
  stack_b = Shipit::Stack.create!(repository: other_repo, environment: 'production', branch: 'master')

  shared_sha = 'deadbeef' * 5
  commit_a = stack_a.commits.create!(sha: shared_sha, author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now, message: 'a')
  commit_b = stack_b.commits.create!(sha: shared_sha, author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now, message: 'b')

  params = Shipit::Webhooks::Params.new(
    sha: shared_sha, state: 'success', context: 'ci', description: nil,
    target_url: nil, created_at: Time.now.iso8601, branches: [{ name: stack_a.branch }],
    repository: { full_name: repo.full_name, owner: { login: repo.owner } }
  )

  Shipit::Webhooks::Handlers::StatusHandler.new(params).process

  stack_ids_with_new_status = Shipit::Status.where(commit_id: [commit_a.id, commit_b.id]).pluck(:stack_id)

  assert_includes stack_ids_with_new_status, stack_a.id
  refute_includes stack_ids_with_new_status, stack_b.id, "Status was written to stack_b, whose repository never authenticated this webhook"
end
```
This test currently fails (both `stack_a.id` and `stack_b.id` are present), demonstrating that a single webhook, authenticated only for `repo`, mutates `stack_b`'s data.
