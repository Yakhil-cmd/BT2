### Title
Cross-Organization Commit-Status Forgery via `StatusHandler` Bypasses CI Gating and Enables Unauthorized Deploys - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` correctly binds the HMAC signature check to the organization named in the payload's `repository.owner.login` (or `organization.login`) field, ensuring a webhook must be signed with *that specific* configured GitHub organization's `webhook_secret`. However, `Shipit::Webhooks::Handlers::StatusHandler`, unlike `PushHandler` (which scopes work through `stacks` / `Repository.from_github_repo_name`), never re-checks the repository/organization when applying the event: it looks up target rows purely by `Commit.where(sha: params.sha)`. This breaks the equality "organization that authenticated == repository that is written": any organization configured in `secrets.github` (each with its own legitimately-held `webhook_secret`) can send a `status` webhook naming an unrelated organization's commit `sha` and have Shipit apply an arbitrary CI status to that foreign commit.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb` picks the GitHub App/secret to verify against using a field taken from the same JSON body being verified: [1](#0-0) [2](#0-1) 

This only proves "the sender knows the webhook secret belonging to the organization named in this payload" — it says nothing about whether the *content* the handler subsequently acts on (e.g. a `sha`) actually belongs to that same organization's repositories.

`PushHandler` correctly re-derives scope from the signed payload before acting, using `Repository.from_github_repo_name(repository_name)` (i.e., `payload.dig('repository', 'full_name')`) to restrict which stacks can be touched: [3](#0-2) [4](#0-3) 

`StatusHandler`, however, drops repository scoping entirely and matches purely on `sha` across the whole `Commit` table, regardless of which repository/organization owns that commit: [5](#0-4) 

Because `sha` values of public/target commits are knowable ahead of time (commit SHAs on tracked branches are visible in the Shipit UI, GitHub, etc.), any organization owner who has legitimately configured their own GitHub App/organization in a multi-org Shipit deployment (`Shipit.github_organizations`, `TOP_LEVEL_GH_KEYS`, `Shipit.github_app_config`) — and therefore legitimately possesses their *own* org's `webhook_secret` — can sign and submit a `status` event whose `repository.owner.login` is their own org (so it passes `verify_signature`), but whose `sha` field names a commit belonging to a *different* organization's stack: [6](#0-5) 

`StatusHandler#process` will happily create/attach that forged status to the foreign commit: [7](#0-6) 

Shipit uses commit statuses to gate continuous delivery and manual deploys via the `ci.require` / `ci.blocking` deploy-spec configuration (`deploy_spec.rb`, `stack.rb`, `undeployed_commit.rb`), so injecting a fabricated "success" status for a required CI context on a commit belonging to a target organization's stack can satisfy the deploy gate for that stack.

### Impact Explanation
This crosses the organization-authentication boundary described in the rules: the entity that authenticated (Org X, via its own legitimately-held webhook secret) is not the entity whose data is written (Org Y's commit/stack). By forging a passing status for a blocking/required CI check, an attacker who only controls one tenant organization in a multi-org Shipit installation can clear the CI gate for another tenant's stack and trigger/enable an unauthorized deploy — matching the "Critical: unauthorized deploy" impact bucket.

### Likelihood Explanation
Requires only that the deployment use the multi-organization `secrets.github` configuration (`TOP_LEVEL_GH_KEYS`/`github_app_config`) with more than one tenant org, and that the attacker administers (or has installed the app for) one of those orgs — a materially lower privilege bar than needing another org's `webhook_secret`, `GITHUB_TOKEN`, or an `ApiClient` token. Guessing/obtaining a target commit's `sha` is trivial since SHAs are not secrets.

### Recommendation
In `StatusHandler#process` (and any other handler that doesn't already scope by repository, such as `check_suite`/`check_run` if similarly affected), constrain the query to commits belonging to the repository named in the verified payload, mirroring `Handler#stacks`/`Handler#repository_name`, e.g. `stacks.joins(:commits).merge(Commit.where(sha: params.sha))`, and reject/no-op if the commit's stack's repository does not match `payload.dig('repository', 'full_name')`.

### Proof of Concept
1. Deploy Shipit with multi-org config: `secrets.github` containing `OrgX` (attacker-administered, webhook secret known to attacker) and `OrgY` (victim, has a stack gated by `ci.require: ["ci/required-check"]`).
2. Attacker obtains the `sha` of the undeployed commit on `OrgY`'s stack (visible in Shipit UI or GitHub).
3. Attacker crafts a `status` webhook JSON: `{"sha": "<victim_sha>", "state": "success", "context": "ci/required-check", "repository": {"owner": {"login": "OrgX"}, "full_name": "OrgX/attacker-repo"}}`, computes `X-Hub-Signature` using `OrgX`'s legitimate `webhook_secret`, and POSTs it to `/webhooks` with `X-Github-Event: status`.
4. `verify_signature` resolves `Shipit.github(organization: "OrgX")` and validates successfully.
5. `StatusHandler#process` executes `Commit.where(sha: "<victim_sha>")` (from `OrgY`) and attaches the forged "success" status, satisfying `OrgY`'s `ci.require` gate for a deploy the attacker does not otherwise control.

```ruby
module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
