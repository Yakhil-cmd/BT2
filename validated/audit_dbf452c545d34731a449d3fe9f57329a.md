### Title
Creator fees can become permanently trapped if the pool creator's associated token account is frozen/blocklisted - (File: `programs/cp-swap/src/instructions/collect_creator_fee.rs`, `programs/cp-swap/src/instructions/collect_creator_fee_permissionless.rs`)

### Summary
`PoolState.pool_creator` is fixed at pool initialization and never updatable, and both fee-collection paths hard-code the destination of accumulated creator fees to the associated token account (ATA) owned by that fixed `pool_creator`. If that specific ATA is frozen (e.g. USDC/USDT admin freeze) or the underlying mint is paused, the transfer in `collect_creator_fee`/`collect_creator_fee_permissionless` will permanently revert, and the program provides no alternate recipient or rescue/withdraw path for these accrued fees.

### Finding Description
`PoolState` stores `pool_creator` at initialization [1](#0-0) , and there is no instruction in the program that allows this address to be updated afterward (confirmed by the absence of any setter for `pool_creator` outside `initialize`). Both fee-claim instructions derive the payout token accounts as ATAs owned by this same fixed `creator`:

- `CollectCreatorFee` requires the creator to sign and pays into `creator_token_0`/`creator_token_1`, ATAs with `associated_token::authority = creator` [2](#0-1) .
- `CollectCreatorFeePermissionless` allows anyone to trigger, but still transfers into ATAs owned by the same fixed `creator` address [3](#0-2) .

Both instructions transfer the full accumulated `creator_fees_token_0`/`creator_fees_token_1` via `transfer_from_pool_vault_to_user` to those creator-owned accounts and then zero out the counters only after a successful transfer [4](#0-3) . If the underlying SPL token (e.g. USDC/USDT) freezes the specific creator ATA, or the mint is globally paused, this CPI call will revert with no way to redirect the payout, exactly mirroring the referenced report's `recipient.recipientAddress` blocklist scenario. There is no `withdraw`/rescue instruction elsewhere in the program that lets anyone (pool managers, protocol owner, or the creator via another address) reclaim these specific stuck creator fees; the only paths to move them are the two collect instructions, both bound to the same frozen destination.

### Impact Explanation
Once a creator's ATA is frozen, `creator_fees_token_0`/`creator_fees_token_1` accrued in the vaults (from ongoing swaps, since fee accrual continues regardless [5](#0-4) ) become permanently unclaimable — a genuine freezing of creator funds with no recovery mechanism in-contract. This does not affect LP or protocol fee accounting (`vault_amount_without_fee` already excludes creator fees from LP-available balance), so the blast radius is scoped to the pool creator's own fee stream, consistent with the Medium severity of the referenced report.

### Likelihood Explanation
Requires an external token-issuer action (blocklisting/freezing the specific creator ATA) which is outside attacker control but a realistic real-world event for centralized stablecoins like USDC/USDT, which are common pool assets on Raydium. Once frozen, the condition is triggered automatically and permanently on every subsequent `collect_creator_fee`/`collect_creator_fee_permissionless` call for that token side.

### Recommendation
Add an instruction allowing the pool creator (or a governance-approved fallback) to designate/update an alternate `pool_creator` address, and/or add a manager-gated rescue/withdraw instruction (similar in spirit to other Raydium fee-sweep instructions) that can redirect stuck `creator_fees_token_0`/`creator_fees_token_1` to a new, unblocked recipient account rather than being permanently locked to the original creator's ATA.

### Proof of Concept
1. Pool is initialized with `token_0_mint` = USDC and `pool_creator` = `C`. `enable_creator_fee` is true, so swaps accrue `creator_fees_token_0` in `pool_state` [6](#0-5) .
2. USDC's freeze authority freezes `C`'s associated USDC token account (independent of this program).
3. Anyone calls `collect_creator_fee_permissionless`; the instruction derives `creator_token_0` as the ATA for `creator = C` [7](#0-6)  and calls `transfer_from_pool_vault_to_user` into it [8](#0-7) .
4. SPL Token program rejects the transfer because the destination account is frozen; the whole instruction reverts and `creator_fees_token_0` is never zeroed.
5. `collect_creator_fee` (creator-signed variant) fails identically since it targets the same frozen ATA.
6. There is no other instruction to redirect or rescue `creator_fees_token_0`, so these funds remain permanently locked in `token_0_vault`.

```rust
pub fn collect_creator_fee(ctx: Context<CollectCreatorFee>) -> Result<()> {
    let mut pool_state = ctx.accounts.pool_state.load_mut()?;
    let creator_fees_token_0 = pool_state.creator_fees_token_0;
    let creator_fees_token_1 = pool_state.creator_fees_token_1;
    if creator_fees_token_0 == 0 && creator_fees_token_1 == 0 {
        return err!(ErrorCode::NoFeeCollect);
    }

    let signer_seeds: &[&[u8]] = &[crate::AUTH_SEED.as_bytes(), &[ctx.bumps.authority]];

    transfer_from_pool_vault_to_user(
        ctx.accounts.authority.to_account_info(),
        ctx.accounts.token_0_vault.to_account_info(),
        ctx.accounts.creator_token_0.to_account_info(),
        ctx.accounts.vault_0_mint.to_account_info(),
        ctx.accounts.token_0_program.to_account_info(),
        creator_fees_token_0,
        ctx.accounts.vault_0_mint.decimals,
        &[signer_seeds],
    )?;

    transfer_from_pool_vault_to_user(
        ctx.accounts.authority.to_account_info(),
        ctx.accounts.token_1_vault.to_account_info(),
        ctx.accounts.creator_token_1.to_account_info(),
        ctx.accounts.vault_1_mint.to_account_info(),
        ctx.accounts.token_1_program.to_account_info(),
        creator_fees_token_1,
        ctx.accounts.vault_1_mint.decimals,
        &[signer_seeds],
    )?;

    pool_state.creator_fees_token_0 = 0;
    pool_state.creator_fees_token_1 = 0;
```
