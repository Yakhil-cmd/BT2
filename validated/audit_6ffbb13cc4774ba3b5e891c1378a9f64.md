### Title
Stack-scoped `ApiClient` token can read CCMenu status of any stack, bypassing its token/stack binding — (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::BaseController` enforces that a stack-scoped `ApiClient` (one created with a non-nil `stack_id`) can only ever resolve stacks from the set `Stack.where(id: current_api_client.stack_id)` [1](#0-0) . `Api::CCMenuController` overrides the `stack` resolution method to look up any stack directly from the global table, discarding that binding while still relying on the same coarse `require_permission :read, :stack` check, which only validates a permission string and never re-checks the stack scope [2](#0-1) [3](#0-2) .

### Finding Description
`ApiClient` records may optionally be bound to a single `Stack` via `belongs_to :stack, optional: true` [4](#0-3) . This binding is the sole mechanism restricting a scoped token to a single stack: `BaseController#stacks` returns `Stack.where(id: current_api_client.stack_id)` when `stack_id` is present, and `BaseController#stack` resolves the requested `params[:stack_id]` only within that restricted relation, raising if it doesn't match [1](#0-0) . The permission check itself, `ApiClient#check_permissions!`, only verifies that `"read:stack"` is present in the token's `permissions` array — it performs no comparison against `stack_id` at all [3](#0-2) .

`Api::CCMenuController` (mounted at `/ccmenu/*stack_id`, see `config/routes.rb`) redefines `stack` as:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
```
This resolves `params[:stack_id]` against the entire `Stack` table, not the token-scoped `stacks` relation defined in `BaseController` [5](#0-4) . Because `require_permission :read, :stack` only calls `current_api_client.check_permissions!(:read, :stack)` — a scope-agnostic string check — a token that was created and authorised for exactly one stack (`stack_id` set, `permissions: ["read:stack"]`) is still accepted by `authenticate_api_client`/`require_permission`, and then `stack` is resolved to whatever `stack_id` the caller supplies in the URL, regardless of the token's actual `stack_id` binding.

This breaks the equality the engine is meant to enforce everywhere else:
`stack the token authorises == stack the request touches`
For every other `Api::BaseController` subclass (e.g. `Api::OutputsController`, `Api::TasksController`), this equality holds because they use the inherited `stack` method backed by the scoped `stacks` relation [6](#0-5) . `Api::CCMenuController` alone diverges and resolves `stack` unscoped.

### Impact Explanation
An attacker holding a legitimately-issued, stack-scoped `ApiClient` token (created, e.g., via console/rake or any integration that sets `stack_id`, a supported and documented model attribute) with only `read:stack` permission for stack A can query `GET /api/ccmenu/<stack_B>?token=<token>` (or via Basic auth) and receive stack B's CCMenu XML feed — including build/deploy status, lock state, last build label/time, and web URL — for a stack it was never authorised to access. This is an unauthenticated-cross-scope read of stack/deploy state, matching the High-severity category "unauthenticated read of stack state, task streams or deploy output."

### Likelihood Explanation
Likelihood is moderate: exploitation requires possession of any valid stack-scoped `ApiClient` token (a normal, intended use case for restricting a CI integration's read access to a single stack). Once such a token exists, the bypass requires only changing the `stack_id` URL segment — no additional secrets, signatures, or privilege escalation are needed, and the divergent code path is small and easily missed in review since it silently shadows the base controller's scoping method.

### Recommendation
Remove the `stack` override in `Api::CCMenuController`, or reimplement it to reuse the inherited, token-scoped `stacks` relation (e.g., `stacks.from_param!(params[:stack_id])`) so that stack-scoped tokens cannot resolve stacks outside their bound `stack_id`. Additionally, consider having `ApiClient#check_permissions!` (or a dedicated check) explicitly assert `stack_id.nil? || stack_id == requested_stack.id` for defense in depth, so any future controller cannot silently reintroduce this class of bypass.

### Proof of Concept
1. Create (e.g. via Rails console / an internal provisioning script, a supported and documented capability) an `ApiClient` scoped to Stack A: `ApiClient.create!(creator: some_user, name: "CI Token A", stack: stack_a, permissions: ["read:stack"])`.
2. Using that token, issue: `GET /api/ccmenu/<stack_B_owner>/<stack_B_name>/<stack_B_env>?token=<token>`.
3. Observe `require_permission :read, :stack` passes (the token has `read:stack`), and `Api::CCMenuController#stack` resolves Stack B via `Stack.from_param!`, returning Stack B's CCMenu XML (build status, lock reason, etc.) even though the token's `stack_id` is Stack A — confirming the token/stack binding is not enforced on this endpoint, unlike `Api::OutputsController`/`Api::TasksController`, which correctly 404/`RecordNotFound` for out-of-scope stacks under the same token.
