### Title
CCMenu API token is unscoped to any stack, granting unauthenticated read access to every stack's deploy state - ([File: app/controllers/shipit/ccmenu_url_controller.rb])

### Summary
`CCMenuUrlController#client` creates/reuses a single `ApiClient` per user with `permissions: %w[read:stack]` but never sets `stack:`, leaving `stack_id` `nil`. This token is embedded verbatim in the returned CCMenu URL, and `Api::CCMenuController#show` overrides the base controller's stack-scoping (`stack` method uses raw `Stack.from_param!` instead of the `stacks` association), so anyone holding that token token can query the deploy status of any stack in the installation, not just the one it was generated for.

### Finding Description
The binding that should hold is: `client.stack_id == stack.id` (the `ApiClient` minted for a CCMenu URL request for stack A must be scoped to stack A). In reality:

`CCMenuUrlController#client` [1](#0-0)  creates the `ApiClient` with `create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')` - no `stack:` attribute is passed, so `stack_id` is `nil`, and the same record is reused (`find_or_create_by!`) for every stack the user requests a CCMenu URL for.

`ApiClient#stack` is `belongs_to :stack, optional: true` [2](#0-1) , and `Api::BaseController#stacks` does attempt to scope by `current_api_client.stack_id` when present [3](#0-2) . But `Api::CCMenuController` overrides the `stack` accessor entirely with its own unscoped lookup:

```
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [4](#0-3) 

This bypasses the `stacks` scoping helper completely - even a properly stack-bound `ApiClient` would not be restricted here. The only authorization check performed is `require_permission :read, :stack` [5](#0-4) , which calls `ApiClient#check_permissions!` [6](#0-5)  - a pure string-membership check on the `permissions` array (`"read:stack"` present or not), with no comparison against `stack_id` or the requested `params[:stack_id]` at all.

Attack flow: A legitimate Shipit user with access only to stack A calls `GET /stacks/:owner/:repo/:env/ccmenu_url` (routed to `CCMenuUrlController#fetch`), receives a URL embedding `token=<authentication_token>`. This same token, because `stack_id` is `nil` and `CCMenuController#stack` never checks it, is valid for `GET /api/stacks/:owner2/:repo2/:env2/ccmenu.xml` for ANY other stack B, C, ... in the Shipit instance. If the URL is pasted into a public CI badge, README, or third-party status page (the documented use case for CCMenu URLs), any unauthenticated internet attacker who finds it gains read access to the deploy/task state of every stack in the installation, not merely the one the URL nominally refers to.

`authenticate_api_client` in `CCMenuController` only verifies the token's HMAC signature via `ApiClient.authenticate` [7](#0-6)  and `ApiClient.authenticate` [8](#0-7)  - it does not perform any stack-binding check, so signature validity is the only barrier, and it is satisfied by design (the attacker has a legitimately-issued, correctly signed token).

### Impact Explanation
Any URL-holder (including an unauthenticated internet party who obtains a leaked/pasted CCMenu URL) can read the CI/deploy status XML (`lastBuildStatus`, `lastBuildLabel`, lock state, etc.) for every stack configured in the Shipit instance, via `Api::CCMenuController#show`, regardless of which stack the URL was originally generated for. This is repeatable indefinitely (the token doesn't expire) and works across all repositories/environments in the install - matching "High: unauthenticated read of stack state" per the severity rubric. It is not RCE or credential exfiltration, so Critical impact is not reached, but it is a real cross-tenant confidentiality break.

### Likelihood Explanation
Preconditions: the attacker needs a valid CCMenu token, which can be obtained by (a) being any authenticated Shipit user who calls `fetch` for a stack they can see, or (b) finding one such token leaked publicly (the stated CCMenu use case - badges/status pages/CI dashboards - encourages exactly this kind of public exposure). No secrets (`api_clients_secret`, `secret_key_base`, GitHub tokens) need to be known; the token is handed out by the application itself. Given CCMenu URLs are explicitly designed to be embedded in external tooling, the likelihood of exposure is high and the exploit cost is trivial (a single unauthenticated GET request per target stack).

### Recommendation
- In `CCMenuUrlController#client`, pass `stack:` when creating/finding the `ApiClient` (e.g. scope `find_or_create_by!` by `creator`, `name`, and `stack`, and set `stack: stack` in `create_with`), so a distinct, stack-bound token is minted per stack.
- In `Api::CCMenuController`, remove the overriding `stack` method and use the inherited `stacks.from_param!(params[:stack_id])` from `Api::BaseController` so that `current_api_client.stack_id` is enforced, or explicitly add a check that `current_api_client.stack_id.nil? || current_api_client.stack_id == stack.id` before rendering.

### Proof of Concept
Minitest plan (extends existing `test/controllers/ccmenu_controller_test.rb` and `test/controllers/api/ccmenu_controller_test.rb` patterns, no live GitHub needed):

```ruby
test "CCMenu token for stack A is rejected for unrelated stack B" do
  stack_a = shipit_stacks(:shipit)
  stack_b = Stack.create!(repository: Repository.create!(owner: 'other', name: 'repo'), branch: 'main', environment: 'production')
  user = shipit_users(:walrus)
  session[:user_id] = user.id

  get :fetch, params: { stack_id: stack_a.to_param }
  data = JSON.parse(response.body)
  token = Rack::Utils.parse_nested_query(URI(data['ccmenu_url']).query)['token']

  client = ApiClient.last
  assert_nil client.stack_id # binding is broken: expected client.stack_id == stack_a.id

  get '/api/stacks/other/repo/production/ccmenu.xml', params: { token: token }
  assert_response :ok # proves token issued for stack A also authorizes stack B
end
```

The core assertion pair: expected `client.stack_id == stack_a.id` (binding claimed by the question) vs. actual `client.stack_id == nil`, followed by demonstrating the same token succeeds against `stack_b`'s CCMenu endpoint - proving the token is unscoped and grants cross-stack read access.
