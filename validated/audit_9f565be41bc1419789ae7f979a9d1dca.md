### Title
Arbitrary file overwrite via symlink following in `gh release download` - ([File: pkg/cmd/release/download/download.go])

### Summary
`destinationWriter.check` in `pkg/cmd/release/download/download.go` uses `os.Stat` (which follows symlinks) to decide whether a destination path exists, and `destinationWriter.Copy` opens the destination with `os.OpenFile(fp, os.O_WRONLY|os.O_CREATE|os.O_TRUNC, 0644)` without ever calling `os.Lstat` to detect or reject a symlink. If a symlink already exists at the computed destination path, `gh release download` will follow it and truncate/overwrite whatever file it points to.

### Finding Description
The call chain is `downloadRun` → `downloadAssets` → `downloadAsset` → `dest.Check(fileName)` → `dest.Copy(fileName, resp.Body)`. Both `Check` and `Copy` compute the destination path with `makePath` [1](#0-0) , then call the internal `check` helper which uses `os.Stat` rather than `os.Lstat`: [2](#0-1) 

`os.Stat` transparently follows symlinks, so if the destination path is a symlink pointing to an existing file, `check` treats it exactly like a regular existing file: it errors out unless `--clobber`/`--skip-existing` is set, but it never identifies or refuses the symlink itself. If the symlink is dangling (points to a non-existent path), `os.Stat` returns a not-exist error and `check` passes silently, exactly as if there were no file there at all.

`Copy` then opens the file with `O_TRUNC`, which also follows symlinks: [3](#0-2) 

This is unlike the sibling implementation in `pkg/cmd/repo/read-file/read_file.go`'s `writeToOutput`, which explicitly calls `os.Lstat` via the `lstat` helper and refuses to proceed if the target is a symlink: [4](#0-3) 

An attacker who controls a release's asset `Name` (fully attacker-controlled, taken directly from the GitHub API response) can pick a name matching a filename the victim will have as a symlink in their working directory at download time — e.g. by publishing a repository via git (git supports symlinks as tree entries) that the victim clones, and a release in the same repository with an asset named identically to that symlink. When the victim clones the repo and then runs `gh release download` from within it, the symlink at the destination path is silently followed, and `Copy`'s `O_TRUNC` open truncates and overwrites the symlink's target — e.g. `~/.bashrc`, `.git/hooks/pre-commit`, or any file reachable by a relative/absolute symlink under the download directory.

### Impact Explanation
This is an arbitrary file write/overwrite outside the intended download directory, achieved purely by an unprivileged remote actor publishing a git repository and a release, and does not require the victim to opt into `--clobber`. Overwriting files such as shell startup scripts or git hooks can lead to code execution on the victim's machine on next shell/git invocation.

### Likelihood Explanation
Preconditions: the victim must clone/checkout an attacker-controlled repository containing a symlink at a filename position, and then run `gh release download` (with a matching asset name, or no `--pattern` filter) from within that checked-out directory (or point `--dir`/`--output` at it). This is a plausible workflow (`git clone` + `gh release download` in the same repo directory is common), fully attacker-orchestrated via published content, requiring no admin/social-engineering beyond the victim running ordinary `gh`/`git` commands on attacker-published content. The bug is deterministic and repeatable once the symlink exists.

### Recommendation
In `destinationWriter.check`, use `os.Lstat` instead of `os.Stat` to detect the destination path without following symlinks, and explicitly refuse (return an error) if the path is a symlink — mirroring the `lstat`/`isSymlink` check already implemented in `pkg/cmd/repo/read-file/read_file.go`'s `writeToOutput`. Additionally, `Copy` should avoid relying solely on the earlier `check` call (in case of TOCTOU) — consider opening with `O_EXCL` when not overwriting, or performing an `Lstat` immediately before `OpenFile` and refusing symlink targets even under `--clobber`.
