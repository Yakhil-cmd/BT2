## Confirmed: DB connection leak (fd-equivalent) via crafted private-payment chain, analogous to CVE-2017-6502

### Title
Unreleased SQLite connection on duplicate-output check throw in `validateAndSavePrivatePaymentChain` - (File: private_payment.js)

### Summary
The CVE describes a crafted webp causing ImageMagick to leak a file descriptor on an error path, exhausting resources and causing DoS. In `ocore`, `private_payment.js`'s `validateAndSavePrivatePaymentChain` takes a DB connection from the pool, begins a transaction, then runs a query whose callback can `throw` before any `ifOk`/`ifError` transaction callback fires — meaning `conn.release()` is never called and the connection is never returned to the (size-limited) pool.

### Finding Description
`validateAndSavePrivatePaymentChain` is reachable by any private-payment counterparty who sends a private payment chain to a wallet/light client. It takes a connection with `db.takeConnectionFromPool`, issues `BEGIN`, and queries existing `outputs` rows matching `unit`, `asset`, `message_index` (and `output_index` only for fixed-denomination/indivisible assets): [1](#0-0) 

For divisible (non-fixed-denomination) private assets, the `output_index` filter is *not* applied, so the query can legitimately/intentionally return more than one row (e.g., a payment message with two outputs of the same asset in the same `message_index`, which is a normal divisible-payment shape). When `rows.length > 1`, the code does:
```
if (rows.length > 1)
    throw Error("more than one output "+sql+' '+params.join(', '));
``` [2](#0-1) 

This `throw` occurs inside the `conn.query` callback, *before* `transaction_callbacks.ifError`/`ifOk` are invoked and before `conn.query("ROLLBACK", ...)` / `conn.query("COMMIT", ...)` run. Consequently `conn.release()` is never reached: [3](#0-2) 

The connection pool (`sqlite_pool.js`) has a hard cap `MAX_CONNECTIONS`; once a connection's `bInUse` flag is left `true` forever (because `release()` was skipped), it is permanently unavailable, and once `arrConnections.length` reaches `MAX_CONNECTIONS`, further requests are queued indefinitely: [4](#0-3) 

This is the same bug class as CVE-2017-6502: attacker-supplied, specially-crafted input triggers an error-handling path that fails to release an OS/pool-level resource (there: file descriptor; here: a pooled sqlite connection object that itself wraps a native file/database handle), leading to gradual resource exhaustion and denial of service.

### Impact Explanation
Each crafted private payment chain that hits this path permanently strands one pooled connection. Since only an unprivileged private-payment counterparty is needed (no special permissions, no hub/peer compromise), repeated sends can exhaust `MAX_CONNECTIONS` on the victim's node/wallet. Once exhausted, `takeConnectionFromPool` calls queue forever and never resolve, which in `ocore` blocks all further DB-dependent operations — including unit validation and joint saving that also call `takeConnectionFromPool` — so the node becomes unable to validate or confirm any further units (matches the "network unable to confirm new units" bar). Additionally, the uncaught `throw Error(...)` inside an async sqlite3 callback is unhandled and can crash the Node process depending on runtime error handling, compounding the DoS.

### Likelihood Explanation
Reachable by any private-payment counterparty without needing malicious peer/hub status — this is a normal, unprivileged flow (sending someone a private payment). Constructing >1 matching `outputs` row for a divisible private asset at a fixed `(unit, asset, message_index)` is achievable with an ordinary multi-output payment message to the same recipient/asset in the same message, which is not an unusual shape for a payment. Because `output_index` is not part of the WHERE clause for divisible assets, this path is easy to hit intentionally by an attacker crafting the chain to include two matching stored outputs before delivering the "duplicate" chain, causing the >1-row branch and hence the leak on every attempt.

### Recommendation
- Ensure the connection is always released/transaction rolled back on this failure: replace the `throw` with a call into `transaction_callbacks.ifError(...)` (which issues `ROLLBACK` and `conn.release()`), rather than throwing synchronously inside the query callback.
- More generally, wrap the body of `validateAndSavePrivatePaymentChain`'s connection callback in a `try/catch` (or use `async`'s error propagation) so any thrown error triggers `ROLLBACK` + `conn.release()` before rethrowing/logging.
- Consider adding a defensive uncaughtException/connection-leak monitor that force-releases connections that have been "in use" beyond a timeout, to bound the impact of any similar oversight elsewhere.

### Proof of Concept
1. As a private-payment counterparty, construct/send to the victim a private payment chain for a divisible, private asset whose head element's payment message has two outputs sharing the same `unit`/`asset`/`message_index` (a legitimately-shaped multi-recipient divisible payment), such that the `outputs` table already contains (or will already contain, from a prior partial reveal) two rows matching that `(unit, asset, message_index)` tuple.
2. Trigger `validateAndSavePrivatePaymentChain` (e.g., via wallet/private-payment receipt handling) so the `SELECT ... FROM outputs WHERE unit=? AND asset=? AND message_index=?` returns `rows.length > 1`.
3. Observe: `throw Error("more than one output ...")` fires inside the sqlite3 query callback; `conn.release()` is never called and the transaction is left `BEGIN`-ed and unresolved.
4. Repeat step 1–3 `MAX_CONNECTIONS` times: the sqlite connection pool is exhausted; subsequent `takeConnectionFromPool` calls (used throughout validation/writer paths) queue indefinitely, halting the node's ability to validate/save further units.
