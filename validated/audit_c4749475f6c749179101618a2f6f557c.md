### Title
Missing reward settlement calls in `stake()` before mutating signer cycle shares - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
The `stake` public function in `pox-5.clar` omits the `settle-rewards`/`settle-staker-rewards` calls that its sibling entry points (`register-for-bond`, `update-bond-registration`) always perform immediately before mutating a signer's or staker's per-cycle share totals. This is directly analogous to the referenced report's bug class: a required state-initialization/settlement step is dropped from one code path while present in equivalent sibling paths, allowing the invariant it protects to be violated.

### Finding Description
`register-for-bond` explicitly settles rewards for the signer and staker before changing their share totals for a cycle: [1](#0-0) 

Similarly, `update-bond-registration` settles rewards for both the old and new signer, and for the staker, before removing/re-adding cycle memberships: [2](#0-1) 

However, `stake` — which also mutates signer-cycle share totals via `add-staker-to-signer-cycles` (and can be a roll-over path that changes an existing signer's aggregate shares) — never calls `settle-rewards` or `settle-staker-rewards` before doing so: [3](#0-2) 

The contract's per-cycle reward accounting relies on `rewards-per-token-for-cycle`, `signer-rewards-per-token-settled-for-cycle`, and `staker-rewards-per-token-settled-for-cycle` snapshots being brought current *before* the denominator (total shares for the cycle) changes — this is exactly why `register-for-bond` and `update-bond-registration` call the settle functions first. `stake` breaks this pattern: it mutates `signer-delegated-per-cycle` / share totals through `add-staker-to-signer-cycles` without first settling, so the reward-per-token delta accrued prior to this call can later be computed against a share total that already includes the new staker's contribution, or a staker's/signer's `*-settled-for-cycle` snapshot can be advanced (elsewhere) across a share change that was never checkpointed at the correct pre-change total.

### Impact Explanation
If accepted, this breaks the equality between sBTC rewards actually earned per staker/signer share and rewards paid out, i.e., it can result in sBTC rewards being paid that were not earned, or being double-counted between the previous and newly-added share holders for a cycle — matching the report's Medium/High-severity "reward accounting" bug class (missing initialization/settlement step, present elsewhere in sibling functions, omitted in one call path).

### Likelihood Explanation
Likelihood is High for reachability: `stake` is a normal, unprivileged, frequently-used entry point (any staker calling `stake` reaches the unsettled mutation), requiring no special preconditions beyond standard staking.

### Recommendation
Add `settle-rewards` and `settle-staker-rewards` calls for the signer (and, where relevant, the staker's own snapshot) inside `stake` prior to any call that mutates `signer-delegated-per-cycle` / per-cycle share totals (`add-staker-to-signer-cycles`), mirroring the pattern already used in `register-for-bond` (lines 772-776) and `update-bond-registration` (lines 895-901).

### Proof of Concept
Note: I was unable to fully trace the internal `settle-rewards`/`add-staker-to-signer-cycles` implementations within the remaining iteration budget to build a concrete step-by-step numeric exploit (e.g., exact reward-per-token arithmetic proving a double payout). The finding is based on the confirmed structural asymmetry: `register-for-bond` (lines 772-776) and `update-bond-registration` (lines 895-901) both settle rewards immediately before altering per-cycle shares, while `stake` (lines 1004-1065) performs the equivalent share-total mutation via `add-staker-to-signer-cycles` (line 1056) with no preceding settlement call. This is stated as a structural/code-path inconsistency requiring further verification of the exact reward-per-token math in `settle-rewards`/`add-staker-to-signer-cycles` (not retrievable within the remaining tool budget) before it can be confirmed as an exploitable double-count.
