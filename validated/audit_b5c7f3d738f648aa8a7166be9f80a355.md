## Confirmed candidate

Interesting: `StatusHandler#process` at [1](#0-0)  resolves target `Commit`s purely by `sha` (globally, not scoped to a repository at all), while `CheckSuiteHandler` and `PushHandler` resolve their target via `Handler#stacks`, which is scoped by `payload.dig('repository', 'full_name')` [2](#0-1) . None of these compare `full_name`'s owner segment against `repository.owner.login`/`organization.login`, which is the field `WebhooksController#verify_signature` actually uses to pick which GitHub App's `webhook_secret` authenticates the request [3](#0-2) .

### Title
Webhook signature is authenticated against `repository.owner.login`/`organization.login` while handlers act on the independently-attacker-supplied `repository.full_name` (or a global, repo-unscoped `sha`), enabling cross-organization/cross-repository writes - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the GitHub App (and thus the HMAC `webhook_secret`) used to authenticate an inbound webhook based on `repository_owner`, which is read straight out of the unauthenticated JSON body (`repository.owner.login`, falling back to `organization.login`) [3](#0-2) . Once the signature check passes for *that* organization, the event is dispatched to handlers (`app/models/shipit/webhooks.rb`) which look up the actual `Stack`/`Repository`/`Commit` to mutate using a *different* field of the same attacker-controlled body: `repository.full_name` in `Handler#stacks` [2](#0-1) , or a bare, repository-unscoped `sha` in `StatusHandler` [1](#0-0) . Nothing in the code enforces that `repository.owner.login` (the value the signature was checked against) is consistent with `repository.full_name`'s owner segment (the value that determines which stack is written to).

### Finding Description
Shipit explicitly supports multiple independent GitHub Apps/organizations sharing one Shipit instance, each with its own `webhook_secret`, selected dynamically via `Shipit.github(organization: ...)` [4](#0-3) , as documented and exercised in `test/dummy/config/secrets_double_github_app.yml` and `test/unit/shipit_test.rb` [5](#0-4) .

`WebhooksController` computes the org used for verification purely from the untrusted payload:
```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [6](#0-5) 

`verify_webhook_signature` verifies the HMAC of the *raw body* against that org's secret [7](#0-6) . Critically, `verify_webhook_signature` returns `true` unconditionally when the configured secret is blank [8](#0-7)  — a state explicitly shown as a valid/expected configuration in the example secrets files (`webhook_secret: # nil`). So any organization onboarded to the shared Shipit instance without a configured (or with a leaked) `webhook_secret` gives an attacker a way to pass `verify_signature` while fully controlling every other field of the JSON body, including `repository.full_name`, `check_suite.head_sha`/`head_branch`, and (for `status`) `sha`/`state`/`branches`.

Handlers then use those attacker-controlled fields, decoupled from `repository_owner`, to decide what to mutate:
- `Handler#stacks` resolves `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))` [2](#0-1) , used by `PushHandler` to force a `sync_github` on any stack of the attacker's choosing (any org/repo tracked by this Shipit instance) [9](#0-8) , by `CheckSuiteHandler` to schedule check-run refreshes [10](#0-9) , and by the pull-request handlers to archive/unarchive review stacks (e.g. `Repository.from_github_repo_name(params.repository.full_name)` in `ClosedHandler`/`ReopenedHandler`/`LabeledHandler`) [11](#0-10) .
- `StatusHandler` does not scope by repository at all — it matches `Commit.where(sha: params.sha)` globally across every stack in the Shipit installation and injects an attacker-chosen `state`/`context`/`description` as a real CI status on that commit [1](#0-0) , which can influence deploy readiness/merge-queue gating for a completely unrelated org's stack.

The binding that should hold — "organization whose webhook secret authenticated the request" == "repository/stack that is written" — is broken: the controller authenticates on one payload field, handlers write based on a sibling, unchecked field of the same attacker-supplied payload.

### Impact Explanation
An operator of any single organization/repo onboarded to a shared, multi-tenant Shipit deployment (i.e., anyone who can trigger or forge a webhook delivery under an org that has a blank/leaked `webhook_secret`) can forge events that mutate state for *any other organization's stacks* tracked by the same instance: forcing GitHub re-sync/commit ingestion (`PushHandler`), archiving/unarchiving a competitor's review stacks (`PullRequest` handlers), or writing arbitrary CI/status entries onto arbitrary commits system-wide (`StatusHandler`), which can gate or unblock deploys and the merge queue. This is a cross-repository/cross-organization write achieved purely through the public, unauthenticated webhook endpoint — squarely the "cross-repository writes" / "unauthorized deploy/rollback" impact class.

### Likelihood Explanation
Exploitability depends on the operator's configuration: it requires (a) multi-org Shipit deployment and (b) at least one onboarded organization whose GitHub App `webhook_secret` is unset or known to the attacker (both of which are shown as supported, "normal" configurations in this repo's own example secrets files and tests). Where that precondition holds, exploitation requires only sending a crafted POST to `/github/webhooks` with `X-Github-Event` set and a JSON body where `repository.owner.login`/`organization.login` names the attacker's own (unsecured) org while `repository.full_name` (or `sha`, for status events) names the victim's repo/commit — no GitHub session, `ApiClient` token, or repository write access is needed, only reachability of the public webhook endpoint.

### Recommendation
Do not let the field used for signature verification and the field used to select the write target diverge:
- After signature verification, re-derive the acted-upon repository strictly from the same organization that was authenticated, or better, verify the payload's `repository.owner.login` against the actual owner segment of `repository.full_name` before dispatching to handlers.
- Alternatively, when there are multiple configured GitHub organizations, try verifying the signature against every configured org's secret and only proceed if the org that verifies matches the org implied by `repository.full_name`.
- Treat a blank `webhook_secret` for any *configured* organization as unauthenticated only for that organization's own repositories — never let it grant a bypass usable to target other organizations' data. Consider making blank secrets warn loudly and requiring an explicit non-nil opt-in flag, and reject events whose `repository.full_name`'s owner doesn't match the authenticated organization.
- Scope `StatusHandler`'s `Commit.where(sha: ...)` lookup by the authenticated repository/stack rather than matching `sha` globally.

### Proof of Concept
1. Deploy Shipit configured for two organizations, `AttackerOrg` (webhook_secret left blank, as shown supported by `config/secrets.development.example.yml`) and `VictimOrg` (tracked stacks with `merge_queue_enabled`/CI gating), both installed on the same Shipit instance.
2. Attacker crafts (no valid GitHub delivery needed):
   ```
   POST /github/webhooks
   X-Github-Event: push
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen sha>",
     "repository": {
       "full_name": "VictimOrg/victim-repo",
       "owner": { "login": "AttackerOrg" }
     }
   }
   ```
   No (or an arbitrary) `X-Hub-Signature` header is required since `AttackerOrg`'s `webhook_secret` is blank, so `verify_webhook_signature` short-circuits to `true` regardless of signature content [8](#0-7) .
3. `verify_signature` computes `repository_owner = "AttackerOrg"`, authenticates successfully against `AttackerOrg`'s (blank) secret [12](#0-11) .
4. `PushHandler#process` runs `stacks` scoped by `Repository.from_github_repo_name("VictimOrg/victim-repo")` [2](#0-1) [9](#0-8) , triggering a forced `sync_github` on `VictimOrg`'s stack — a write the attacker was never authorized to make.
5. The equivalent crafted `status` event (with `sha` set to any commit hash tracked by `VictimOrg`) similarly injects a status via `StatusHandler`, since matching is entirely global (`Commit.where(sha: params.sha)`) with no organization/repository check at all [1](#0-0) .

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
