### Title
Cross-bond replay of a single L1 BTC lockup double-counts `sats-total` when two bonds share `early-unlock-bytes` - (File: `stackslib/src/chainstate/stacks/boot/pox-5.clar`)

### Summary
`construct-lockup-output-script`/`construct-lockup-script` binds a P2WSH lockup only to `staker`, `unlock-burn-height`, `staker-unlock-bytes`, and `early-unlock-bytes` — it never binds the script to a `bond-index`. `verify-l1-lockups`'s `seen-outpoints` dedup is a local fold accumulator that resets on every call, so nothing on-chain remembers that a given Bitcoin outpoint was already credited by a prior `register-for-bond`. If two bonds are configured with the same `early-unlock-bytes` (and the staker picks a large enough `unlock-burn-height` up front to satisfy both bonds' minimums), the exact same already-locked BTC output can be replayed as "proof" against a second bond, crediting `sats-total` a second time into `protocol-bonds-total-staked` for a lockup that only ever happened once.

### Finding Description
Equality claimed to be broken: `sats credited to bond B` should equal `sats locked to a script that commits to bond B specifically`. In fact the lockup script's preimage (`stackslib/src/chainstate/stacks/boot/pox-5.clar:3711-3745`, `construct-lockup-script`/`construct-lockup-output-script`) only commits to `staker`, `unlock-burn-height`, `staker-unlock-bytes`, and `early-unlock-bytes`; it contains no reference to `bond-index`. `verify-l1-lockups` (lines 1981-2019) pulls `early-unlock-bytes` from `(get-protocol-bond bond-index)` and only enforces `unlock-burn-height >= (get-bond-l1-unlock-height bond-index)` (a `>=`, not exact match) — so a single BTC output whose script was built with a sufficiently large `unlock-burn-height` and with `early-unlock-bytes` equal to bond B's early-unlock-bytes will satisfy bond B's `verify-l1-lockups` even though the funds were originally counted for bond A.

Outpoint replay protection (`seen-outpoints`, `ERR_DUPLICATE_LOCKUP_OUTPOINT`, lines 2028-2088) is local to the `fold` inside a single `verify-l1-lockups` call — it only rejects the same outpoint appearing twice within one `outputs` list. There is no persistent map recording outpoints already credited by earlier `register-for-bond` transactions, so nothing prevents feeding the same outpoint as the sole entry across two separate `register-for-bond` calls.

Path: the staker first calls `register-for-bond(bond-index=A, ...)` with a real BTC lockup at outpoint X, gets a membership under bond A, and `protocol-bonds-total-staked[A]` is incremented by `sats-total` (line ~793: `(map-set protocol-bonds-total-staked bond-index (+ current-total-staked sats-total))`). Later, during bond A's L1-unlock window, the staker calls `register-for-bond(bond-index=B, ...)` with the same lockup proof pointing at outpoint X (still unspent on Bitcoin), where bond B's `early-unlock-bytes` equals bond A's. `register-for-bond`'s rollover branch (lines 764-816) explicitly does **not** tear down bond A's per-cycle shares/total-staked ("A roll-over from an ending bond ADDS the new bond's shares but does NOT tear down the old bond's per-cycle shares/delegation"). It only overwrites the single-principal-keyed `protocol-bond-memberships` map and adds bond B's shares via `add-staker-to-bond-cycles`/`protocol-bonds-total-staked[B] += sats-total`. sBTC custody (`roll-sbtc`) is a no-op on the L1 path (`new-sbtc` is `u0` whenever `btc-lockup` is `ok`), so no funds move and nothing forces the staker to prove a second, distinct BTC lockup for bond B.

Net effect: one real Bitcoin lockup of `sats-total` sats is now counted in `protocol-bonds-total-staked` for both bond A and bond B, even though only one output was ever funded.

### Impact Explanation
This double-counts a staking commitment across two bonds' aggregate `protocol-bonds-total-staked` figures from a single real BTC lockup — matching the Critical category "double-counting a commitment or reward." Downstream reward/target-rate/signer-slot calculations that key off `protocol-bonds-total-staked` per bond would treat the same collateral as backing two bonds simultaneously, inflating apparent collateralization or reward eligibility for bond B without any additional BTC ever being locked. It is repeatable for every additional bond the staker can roll into whose `early-unlock-bytes` matches (bounded by the number of rollover-eligible bonds and the L1 unlock-window timing), though the singleton `protocol-bond-memberships` map limits it to one "current" membership at a time — the double count of `protocol-bonds-total-staked` (a lasting map entry) persists regardless.

### Likelihood Explanation
Requires: (1) the bond admin to configure two bonds (A and later B) with byte-identical `early-unlock-bytes` — this is an admin-set field via `setup-bond`, not attacker-controlled, so this precondition is outside the unprivileged attacker's control unless the admin reuses the same bytes across bonds (plausible operational sloppiness, e.g., reusing a standard early-unlock template, but not something the attacker can force); (2) the staker must pick `unlock-burn-height` large enough at initial lock time to satisfy both bonds' minimums (fully attacker-controlled, trivial); (3) the rollover must occur inside bond A's L1 unlock window (`verify-bond-rollover-window`), a normal, reachable condition for any L1-locking staker. Given precondition (1), the rest of the exploit is fully within the reach of an ordinary staker with no special privileges, using only their own already-broadcast BTC lockup. Because (1) is an admin/config choice rather than an attacker action, this is a real logic flaw but its exploitability depends on a specific operational pattern (bond admin re-using early-unlock byte templates across bond periods) rather than something the attacker alone can engineer from scratch.

### Recommendation
Bind the L1 lockup script cryptographically to `bond-index` (e.g., hash `bond-index` into the committed preimage alongside `staker`, or include it as an explicit script component) so a script constructed for bond A can never validate against bond B's `verify-l1-lockups`. Additionally, add a persistent map (e.g., `l1-lockup-used-outpoints: {txid, output-index} -> bool`) that is checked and set across *all* `register-for-bond` calls (not just within a single call's fold), so a given Bitcoin outpoint can only ever be credited once, regardless of bond-index or rollover status. Consider also tearing down or netting the prior bond's `protocol-bonds-total-staked` contribution on rollover for L1 locks, consistent with how `roll-sbtc` nets sBTC on the L2 path.

### Proof of Concept
Rust integration test plan (extending `stacks-node/src/tests/pox_5_integrations.rs` patterns already present, e.g. `check_pox_5_register_for_bond_l1_lockup_lifecycle`):
1. Bond admin calls `setup-bond` for bond-index 0 and bond-index 6 with byte-identical `early-unlock-bytes` (e.g. both `vec![0x61u8; 32]`), allowlisting the same staker in both.
2. Compute `unlock_burn_height` large enough to satisfy `get-bond-l1-unlock-height` for both bond 0 and bond 6.
3. Call `construct-lockup-output-script` for bond 0's staker/unlock-burn-height/staker-unlock-bytes/early-unlock-bytes, derive the P2WSH address, fund it once on regtest with `SATS` sats (single Bitcoin `send_to_address`).
4. `register-for-bond(bond-index=0, ...)` with the lockup proof pointing at that outpoint. Assert success, `protocol-bonds-total-staked(0) == SATS`, membership `bond-index == 0`.
5. Advance to bond 0's L1 unlock window. `register-for-bond(bond-index=6, ...)` with **the same outpoint/proof** (same tx, same output-index). Assert:
   - Either the call is rejected (expected, correct behavior) with something like `ERR_DUPLICATE_LOCKUP_OUTPOINT`/a new bond-binding error, **or**
   - The call succeeds and `protocol-bonds-total-staked(6) == SATS` **while** `protocol-bonds-total-staked(0)` is still `SATS` (not decremented) — proving `SATS` sats are now counted twice (`total-staked(0) + total-staked(6) == 2 * SATS`) even though `send_to_address` (real BTC locked) was only ever called once for `SATS` sats.
6. The assertion `sum(protocol-bonds-total-staked over all bonds) == sum(actual sats locked on Bitcoin)` should be checked before and after step 5; if it diverges (2×SATS counted vs. 1×SATS locked), the vulnerability is confirmed.
