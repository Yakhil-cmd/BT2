### Title
Cross-organization webhook forgery via signing-organization / written-repository binding mismatch - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the GitHub App / webhook secret to verify a webhook's HMAC signature using `repository_owner`, computed from `params.dig('repository', 'owner', 'login')` (fallback `organization.login`). The webhook `create` action then dispatches the *same raw payload* to handlers (e.g. `PushHandler`), which resolve the repository/stack to mutate using `payload.dig('repository', 'full_name')` via `Handler#repository_name` and `Repository.from_github_repo_name`. These two payload fields are never cross-validated against each other, so the organization whose secret authenticated the request is not enforced to match the repository that is actually written to.

### Finding Description [1](#0-0) 
computes the signing organization from `repository_owner`: [2](#0-1) 

`Shipit.github(organization:)` looks up per-organization app config (including `webhook_secret`) from `Rails.application.credentials.github`, keyed by organization name, in Shipit's documented multi-organization configuration schema: [3](#0-2) [4](#0-3) 

Once the signature check passes, `create` forwards the entire raw JSON payload, unmodified, to registered handlers: [5](#0-4) 

`Handler#repository_name` (used by `PushHandler` and other handlers) independently re-reads the repository identity from `repository.full_name` in that same payload, and looks it up globally, without regard to which organization's secret validated the request: [6](#0-5) [7](#0-6) [8](#0-7) 

In a legitimate GitHub-originated webhook, `repository.owner.login` and the owner segment of `repository.full_name` are always identical since GitHub itself populates both fields from the same repository object. But because Shipit trusts the raw client-supplied JSON body for both fields independently — using one field only to pick the HMAC secret, and a different field only to pick the mutated resource — nothing in the engine enforces that they refer to the same organization. An attacker who controls the GitHub App/webhook secret for *any* organization configured in Shipit (e.g. their own organization "OrgA", onto which they legitimately installed the Shipit GitHub App and therefore know `OrgA`'s `webhook_secret`) can craft a raw POST body where:
- `repository.owner.login` = `"OrgA"` (or `organization.login` = `"OrgA"`) — satisfies `verify_signature`, since the attacker signs the body with the `OrgA` secret they legitimately possess.
- `repository.full_name` = `"OrgB/victim-repo"` — an entirely different, victim-owned repository/stack tracked by the same Shipit instance under organization `OrgB`.

The HMAC signature is computed over the raw bytes, so it is valid for this crafted payload as long as it was signed with `OrgA`'s secret. `verify_signature` passes (`Shipit.github(organization: "OrgA")` succeeds and the signature matches). `PushHandler#process` then resolves `stacks` via `Repository.from_github_repo_name("OrgB/victim-repo")`, which performs a global, unscoped `find_by(owner:, name:)` lookup, and calls `stack.sync_github(expected_head_sha: params.after)` on every matching, non-archived stack for the target branch — regardless of which organization the signing secret belonged to.

This breaks the binding: **organization that authenticated (signing org, `repository.owner.login`/`organization.login`) == repository that is written (`repository.full_name`)**. The engine implicitly assumes these are equal because that is how the honest GitHub webhook system always constructs them, but never verifies the equality itself.

### Impact Explanation
This is a cross-repository/cross-organization write triggered purely by controlling one organization's webhook secret, which is not privileged access to the victim organization at all — it only requires the attacker to run Shipit's GitHub App on their own, attacker-controlled GitHub organization/repository (a self-service action any GitHub user can perform, generating their own `webhook_secret`). Using that secret they can forge webhook events (`push`, `pull_request`, `status`, `check_suite`) that appear valid to `verify_signature` but cause Shipit to act on any other tracked stack's repository, e.g. forcing `GithubSyncJob` execution with an attacker-chosen `expected_head_sha`, or manipulating pull-request-driven review-stack archive/unarchive/provisioning state for a completely unrelated, victim-owned repository. This meets the High-severity bar of "escalation ... unauthenticated read of stack state" territory and can lead to unauthorized triggering of sync/deploy-adjacent workflows on repositories the attacker does not own — a cross-repository state mutation authorized only by possession of an unrelated organization's webhook secret.

### Likelihood Explanation
Likelihood is high for any Shipit deployment using the documented multi-organization GitHub App configuration (`config.github.<OrgName>.webhook_secret`, as shown in `docs/setup.md` and `test/dummy/config/secrets_double_github_app.yml`), since onboarding a new organization (installing the App, getting a webhook secret) requires no interaction with or trust from the victim organization, and Shipit exposes a single shared `/webhooks` endpoint for all organizations. No repository write access, session, or `ApiClient` token is required — only the ability to construct a raw POST to `/webhooks` signed with any one configured organization's secret.

### Recommendation
In `WebhooksController#verify_signature`, or in `Handler#repository_name`/`stacks`, enforce that the organization used to select the webhook secret is the same organization referenced by `repository.full_name` (and by extension by every handler that resolves a `Repository`/`Stack` from the payload) — e.g., reject the request if `repository.full_name.split('/').first` does not case-insensitively equal `repository_owner`, before dispatching to any handler.

### Proof of Concept
1. Deploy Shipit with the multi-organization GitHub config schema, e.g. `OrgA` and `OrgB` each with distinct `webhook_secret`s (per `docs/setup.md` / `test/dummy/config/secrets_double_github_app.yml`), where `OrgB` owns a tracked repository `OrgB/victim-repo` with stack `production`.
2. As an attacker, create your own GitHub organization `OrgA`, install the Shipit GitHub App on it, and note the `webhook_secret` you configured for `OrgA` in Shipit (you legitimately know this secret since you own `OrgA`).
3. Craft a `push` event JSON body:
```json
{
  "ref": "refs/heads/production",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
4. Compute `X-Hub-Signature: sha1=<hmac-sha1(OrgA_webhook_secret, body)>` and POST it to `/webhooks` with header `X-Github-Event: push`.
5. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgA")` and validates the signature successfully (it was signed correctly with `OrgA`'s secret).
6. `PushHandler#process` resolves `Repository.from_github_repo_name("OrgB/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on `OrgB`'s `production` stack, despite the request never being authenticated by `OrgB`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
