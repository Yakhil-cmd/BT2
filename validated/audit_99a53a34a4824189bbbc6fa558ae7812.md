### Title
Hardcoded `bAllowUnresolvedInnerDefinitions = true` bypasses inner address definition validation - (File: definition.js)

### Summary
In `definition.js`, the `address` operator handler inside `validateDefinition` is supposed to require that an `address` reference inside a definition either resolve to a known, already-registered definition, or be accompanied by a matching co-author definition in the same unit — unless the caller explicitly opts into relaxed validation via `objValidationState.bAllowUnresolvedInnerDefinitions`. The actual state-based check has been commented out and replaced with a hardcoded local variable set to `true`, unconditionally allowing unresolved inner address references to pass validation regardless of the caller's intent.

### Finding Description
The `address` case in `validateDefinition`'s inner `evaluate()` function handles definitions like `['address', 'BASE32ADDR']`, which let one address's spending condition depend on another address's definition. When the referenced address's definition cannot be found in storage and is not supplied by a co-author in the current unit, the correct behavior (as documented by the commented-out line) is to consult `objValidationState.bAllowUnresolvedInnerDefinitions` — a caller-supplied flag that should be `false` during normal, security-critical unit/definition validation and `true` only in specific relaxed contexts (e.g. `wallet_defined_by_addresses.validateAddressDefinition`, which explicitly sets it to `true` for UI-side pre-validation of definition templates before any funds are at risk): [1](#0-0) 

Instead of reading the flag from `objValidationState`, the code does:
```js
ifDefinitionNotFound: function(definition_chash){
//	if (objValidationState.bAllowUnresolvedInnerDefinitions)
//		return cb(null, true);
    var bAllowUnresolvedInnerDefinitions = true;
    ...
``` [2](#0-1) 

This hardcodes the "allow unresolved" branch to always be taken, so for every real unit validation path (`validation.js`, `signed_message.js`, AA authentifier/definition checks) that calls into `validateDefinition` with `bAllowUnresolvedInnerDefinitions` unset (i.e. `false`/`undefined`), an `address`-type spending condition referencing an address whose definition is *not yet known on-chain and not co-provided in the unit* will still be treated as satisfiable (`cb(null, true)`), rather than rejected with "definition of inner address ... not found".

### Impact Explanation
An `address` condition is meant to defer authorization to another address's (possibly not-yet-defined) definition. With this bypass, an attacker can construct a definition (for a wallet address, an asset's `issue_condition`/`transfer_condition`, or an AA-controlled address condition) containing an `address` reference to an address with an as-yet-unknown/unresolved definition, and the definition will validate as if that inner condition were satisfied, without ever proving the referenced address's actual spending rules. This can let an attacker construct an address/definition that appears to require signatures/conditions it does not actually enforce, or satisfy an `address`-based authentifier check without the corresponding definition ever being resolved and evaluated — enabling unauthorized spending of funds or unauthorized approval of asset issuance/transfer conditions that were supposed to be gated by another address's definition. This is a real-money integrity issue (unauthorized spending / bypassed authorization), reachable directly by any unprivileged posted unit that uses an `address` operator in its definition.

### Likelihood Explanation
High: this code path executes for every unit that contains an `address` operator anywhere in an address definition, asset issue/transfer condition, or definition-change/authentifier evaluation, whenever the referenced address's definition isn't already known and isn't supplied by a co-author in the same unit — a condition trivially reachable by simply posting a unit that references an undefined address. No special privileges, hub cooperation, or network position are required; a normal unit poster can trigger it.

### Recommendation
Restore the intended state-driven check and remove the hardcoded override:
```js
ifDefinitionNotFound: function(definition_chash){
    if (objValidationState.bAllowUnresolvedInnerDefinitions)
        return cb(null, true);
    var arrDefiningAuthors = ...
    ...
    return cb("definition of inner address " + other_address + " not found");
}
```
Ensure `objValidationState.bAllowUnresolvedInnerDefinitions` defaults to `false`/`undefined` everywhere except the explicit relaxed pre-validation call in `wallet_defined_by_addresses.js`, and add a regression test asserting that posting a unit with an `address` condition to an unresolved, non-co-authored address fails validation.

### Proof of Concept
1. Construct address definition `['address', 'UNRESOLVED_ADDR']` where `UNRESOLVED_ADDR` has no on-chain definition and is not listed as a co-author with a matching definition in the unit.
2. Post a unit that uses this address (or an asset condition/AA definition referencing it) as an authentifier for spending, an `issue_condition`, or `transfer_condition`.
3. Call into `Definition.validateDefinition` (as `validation.js` / `signed_message.js` normally do) without setting `bAllowUnresolvedInnerDefinitions`.
4. Observe that validation still succeeds via the `ifDefinitionNotFound` branch because `bAllowUnresolvedInnerDefinitions` is hardcoded `true`, even though the referenced inner definition was never proven, demonstrating the bypass of the intended "definition of inner address not found" rejection.
