### Title
Uncaught exception during AA trigger execution crashes the node and leaves the trigger permanently stuck, halting stabilization - ([File: aa_composer.js])

### Summary
The IoTeX report describes a panic during single-action minting that unwinds past sender-eviction logic, so the action is never removed and is retried on every subsequent draft. `ocore` has an analogous pattern in AA (Autonomous Agent) trigger execution: `handleAATriggers` iterates pending `aa_triggers` rows with `async.eachSeries`, and each row's queue entry is only removed (`DELETE FROM aa_triggers ...`) *after* `handleTrigger` successfully calls its `onDone` callback.

### Finding Description
When an MCI stabilizes, `main_chain.js` inserts one row per AA trigger into the `aa_triggers` table (a persistent, committed queue) and then invokes `aa_composer.handleAATriggers()` [1](#0-0) , which is also called from `writer.js` after `saveJoint` stabilizes an MCI [2](#0-1) .

`handleAATriggers` processes each queued trigger through `handlePrimaryAATrigger` → `handleTrigger`, and only removes the row from `aa_triggers` once `handleTrigger`'s callback fires: [3](#0-2) [4](#0-3) 

`handleTrigger` and the formula evaluator it calls (`formula/evaluation.js`) are riddled with synchronous `throw Error(...)` statements reachable from ordinary control flow, not just top-level validation guards — e.g. `throw Error('bad AA definition ...')`, `throw Error("base AA not found: ...")`, `throw Error("AA not found? " + address)` in `aa_composer.js` [5](#0-4) [6](#0-5) , and `throw Error('unrecognized op '+op)` / `throw Error("function called after a return")` inside the oscript interpreter's `evaluate`/`callFunction` [7](#0-6) [8](#0-7) .

None of these throws are wrapped in a local `try/catch` around the single-trigger execution inside `handlePrimaryAATrigger`/`handleTrigger` (unlike the fixed IoTeX code, which now recovers panics right around the single-action call and routes them through the normal error/eviction path). Instead, an uncaught synchronous exception propagates all the way up the async call chain until it becomes a Node.js `uncaughtException`, which is caught globally in `network.js` and deliberately used to crash the process: [9](#0-8) 

Because the crash happens before `handleTrigger`'s `onDone` fires, the `DELETE FROM aa_triggers` never executes, so the trigger row remains in the (already-committed) `aa_triggers` table. On restart, the node resumes normal operation, and the same stuck trigger will be re-processed the next time `handleAATriggers` runs (on the next MCI stabilization it is picked up again by the same `SELECT ... FROM aa_triggers` query, since the row was never deleted) — reproducing the same exception and crash. This is the direct analog of "the same action would then be retried on every subsequent mint attempt": here it is "the same trigger is retried on every subsequent AA-trigger processing pass, each time crashing the node."

### Impact Explanation
Because AA trigger execution is deterministic and consensus-relevant (state vars, balances, and generated response units all depend on it), any node that reaches the same stable MCI will hit the identical crash when processing this trigger. If an attacker can construct an AA (or a trigger to an existing AA) whose evaluation deterministically throws one of these unguarded `Error`s (e.g., through interpreter edge cases in `formula/evaluation.js`, or corrupted/inconsistent AA-address bookkeeping hitting `throw Error("AA not found? " + address)`), every full node in the network will crash upon reaching that MCI and will crash again on restart, since the trigger row is never evicted. This can produce a persistent, repeatable network-wide halt: full nodes become unable to stabilize past the offending MCI, i.e. "a network unable to confirm new units."

### Likelihood Explanation
Reaching this code path only requires posting an ordinary unit that pays to an AA address (a primary AA trigger), which is exactly the "unpaid unit poster / AA trigger sender" capability explicitly listed as in-scope. The trigger reaches `handleTrigger`/`evaluateAA` through completely standard confirmation flow (no privileged access needed). The main open question — not fully resolved by static inspection — is which specific interpreter/state-management edge case can be reliably induced by attacker-controlled AA code/trigger data to hit one of these `throw Error(...)` paths (as opposed to being caught earlier by AA definition/trigger validation, or being routed through `bounce()`/`setFatalError()`, which are the intended non-crashing error paths). Several of the identified throws (e.g., "unrecognized op", "function called after a return", base_aa/definition-not-found assertions) look like defensive "should never happen" assertions guarding invariants that AA validation (`aa_validation.js`) is supposed to enforce beforehand; if validation fully prevents these states, exploitability requires finding a validation/execution mismatch. This determination requires deeper code-path analysis of `aa_validation.js` alongside `formula/evaluation.js`, which I could not fully complete within the available searches.

### Recommendation
Wrap the single-trigger execution boundary — i.e., the call into `handleTrigger` from `handlePrimaryAATrigger`, and/or the top of `evaluateAA`/`formulaParser.evaluate` — in a `try/catch` that converts any synchronous throw into a normal error result (equivalent to calling `bounce(err)` or an error callback), rather than letting it propagate to the process-level `uncaughtException` handler. Additionally, ensure the `aa_triggers` row for a trigger that fails this way is still removed (or explicitly marked/skipped) so it is not retried indefinitely, mirroring the IoTeX fix of converting the panic into an ordinary error that flows through existing error handling/eviction logic.

### Proof of Concept
A fully concrete PoC (a specific AA definition/oscript formula that deterministically reaches one of the unguarded `throw Error(...)` statements in `formula/evaluation.js` without being rejected first by `aa_validation.js`) could not be constructed with confidence from the available static analysis; it would require exercising `aa_validation.js`'s formula validator against the interpreter's runtime assumptions to find a mismatch case (e.g., a construct that validation accepts but evaluation's `switch(op)` does not recognize, hitting `throw Error('unrecognized op '+op)` at `formula/evaluation.js:2757-2759`, or a function-call/return-ordering edge case hitting `throw Error("function called after a return")` at `formula/evaluation.js:3063-3065`). Conceptually, the PoC shape is: post a unit paying to an AA address whose definition/data triggers this interpreter inconsistency, causing `handleTrigger` to throw synchronously before calling `onDone`, which crashes the process via `network.js:4530-4543`, while the corresponding `aa_triggers` row persists and re-triggers the crash on every subsequent stabilization/restart cycle.
