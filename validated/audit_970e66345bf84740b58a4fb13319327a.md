### Title
Cross-organization `check_suite` webhook trigger via mismatched `repository.owner.login` vs `repository.full_name` - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates a webhook using the GitHub App configured for `params.dig('repository','owner','login')`, but `Handler#stacks` (used by every webhook handler, including `CheckSuiteHandler`) resolves the target repository/stacks from the completely independent field `payload.dig('repository','full_name')`. Because nothing ties these two fields together, an attacker can sign/send a request that "verifies" against an organization with no configured `webhook_secret` while the payload's `repository.full_name` (and `check_suite.head_sha`/`head_branch`) point at a real stack belonging to a different, unrelated organization.

### Finding Description
The broken binding is: `verifying_org = params.dig('repository','owner','login')` must equal `target_org = payload.dig('repository','full_name').split('/').first`, but the code never enforces this equality.

- `verify_signature` derives the GitHub App/secret purely from `repository_owner` (`params.dig('repository','owner','login')`) and calls `github_app.verify_webhook_signature(...)`: [1](#0-0) , with `repository_owner` defined at [2](#0-1) .
- `GitHubApp#verify_webhook_signature` trivially returns `true` when no `webhook_secret` is configured for that org: [3](#0-2) .
- After "verification", `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the full raw JSON payload to `CheckSuiteHandler`: [4](#0-3) .
- `Handler#stacks` and `#repository_name` resolve the target repository from `payload.dig('repository', 'full_name')`, a field never checked against `repository_owner`: [5](#0-4) .
- `CheckSuiteHandler#process` then matches `head_branch`/`head_sha` on that resolved stack and calls `schedule_refresh_check_runs!` on the matching commit: [6](#0-5) , which enqueues `RefreshCheckRunsJob`: [7](#0-6) .

**Attacker request**: `POST /webhooks` with header `X-Github-Event: check_suite` and body:
```json
{
  "repository": {"owner": {"login": "org-a"}, "full_name": "org-b/real-repo"},
  "check_suite": {"head_sha": "<real sha in org-b stack>", "head_branch": "<real branch>"}
}
```
Since `org-a` is configured in Shipit with no `webhook_secret`, `verify_webhook_signature` returns `true` unconditionally — no signature is even required. The handler then processes the payload using `repository.full_name = "org-b/real-repo"`, resolving `org-b`'s real stack via `Repository.from_github_repo_name` and scheduling a check-run refresh on `org-b`'s commit, without the attacker ever authenticating against `org-b`.

Existing guards do not stop this: `drop_unhandled_event` only checks the event is registered; `check_if_ping` is irrelevant; `verify_signature` only checks the org named in `repository.owner.login`, never cross-validating it against `repository.full_name`; there is no `ExplicitParameters` constraint tying these fields together in `CheckSuiteHandler`'s `params do ... end` block [8](#0-7) .

### Impact Explanation
An unprivileged attacker who merely knows (a) that some organization configured in the Shipit instance has no `webhook_secret` set, and (b) a real `head_sha`/`head_branch` belonging to a different organization's stack, can force Shipit to enqueue `RefreshCheckRunsJob` against that other organization's commit — a cross-tenant trigger executed without any authentication tied to the victim org. This is repeatable for any commit/branch combination and any pair of (unsecured-org, target-org/repo) as long as the attacker can guess or observe real SHAs (which are often public, e.g., via GitHub's public API or UI). This matches the "forged webhook accepted" / "payload for one repository mutating another's stack or commit" Critical category, since the security boundary between organizations (webhook authentication) is bypassed for cross-org effect.

### Likelihood Explanation
Exploitability strictly depends on the precondition that at least one org configured in `Shipit.github` credentials lacks a `webhook_secret` (`GitHubApp#verify_webhook_signature` short-circuits to `true` in that case) — this is an operator configuration state, not guaranteed to exist in every deployment, but is expressly the scenario provided in this question and is a legitimate supported configuration state (webhook_secret is optional per `GitHubApp#initialize`: [9](#0-8) ). Given that precondition, the attack costs nothing beyond one HTTP POST with a guessable/observable SHA — no secrets, sessions, or tokens are required.

### Recommendation
Cross-validate that `repository.owner.login` used to select the signing GitHub App matches the owner segment of `repository.full_name` before dispatching to handlers, and reject the request (422) on mismatch. Alternatively, always resolve the target repository/org for handler processing from the same field that was authenticated (`repository.owner.login`), not from the independently-supplied `repository.full_name`.

### Proof of Concept
In `test/controllers/webhooks_controller_test.rb` (pattern mirrors existing `:check_suite` test at lines 75-83):
```ruby
test ":check_suite from an org with no webhook_secret cannot trigger refresh on a different org's stack" do
  # org-a has no webhook_secret configured; org-b owns @stack/commit
  org_b_stack = shipit_stacks(:shipit) # owner: shopify/shipit, branch master
  commit = shipit_commits(:first)

  request.headers['X-Github-Event'] = 'check_suite'
  body = {
    repository: { owner: { login: 'org-a' }, full_name: org_b_stack.github_repo_name },
    check_suite: { head_sha: commit.sha, head_branch: org_b_stack.branch }
  }.to_json

  Shipit.github(organization: 'org-a').stubs(:verify_webhook_signature).returns(true) # simulates no webhook_secret

  assert_no_enqueued_jobs(only: RefreshCheckRunsJob) do
    post :create, body:, as: :json
  end
end
```
Assert both sides of the binding: `params.dig('repository','owner','login') == 'org-a'` while `payload.dig('repository','full_name').split('/').first == 'shopify'` (org-b) — they diverge, and the test should assert the job is **not** enqueued once the fix cross-validates them (currently it fails because the job IS enqueued).

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
