### Title
Cross-tenant commit status forgery via unscoped `Commit.where(sha:)` lookup - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits by SHA across the **entire** `commits` table with no scoping to the repository/organization whose webhook signature was actually verified. Because `WebhooksController#verify_signature` only proves that the payload's `repository.owner.login` matches *some* organization's own `webhook_secret`, and never checks that the resolved `Commit#stack` belongs to that same organization, a validly-signed webhook from organization A can update a commit status row that is tied to organization B's `Stack`, potentially unblocking or triggering `Stack#trigger_continuous_delivery` for a victim stack.

### Finding Description
The binding that must hold is: `verified_org (repository_owner used in Shipit.github(organization:))` == `commit.stack.repository.owner (org of the Stack whose deploy gets triggered)`. This is never checked.

Code path:
- `WebhooksController#verify_signature` resolves `Shipit.github(organization: repository_owner)` from `payload.dig('repository','owner','login')` and validates `X-Hub-Signature` against **that organization's own configured `webhook_secret`** [1](#0-0) [2](#0-1) .
- Once verified, `StatusHandler#process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with **no filter on stack, repository, or organization** [3](#0-2) .
- `create_status_from_github!` writes a new `Status` row and recomputes `Commit#status`, which feeds `Commit#deployable?` (`!locked? && (stack.ignore_ci? || (success? && !blocked?))`) [4](#0-3) [5](#0-4) .
- A change in `deployable?`/simple_state schedules `ContinuousDeliveryJob` via `Commit#schedule_continuous_delivery` and `Stack#trigger_continuous_delivery`, which calls `Stack#trigger_deploy` → real deploy execution via `Command`/`PTY.spawn` for the victim's stack [6](#0-5) [7](#0-6) .

Root cause: the trust boundary established by `verify_signature` is per-organization (multiple GitHub Apps/orgs are supported, as evidenced by test fixtures like `secrets_double_github_app.yml`), but `StatusHandler` does not re-validate that the `stack_id` behind the matched `Commit` row belongs to the organization that was actually verified. Any two repositories (e.g., a victim's original repo and an attacker-controlled fork/repo that happens to share an identical commit SHA, such as an unmodified ancestor commit preserved across a fork) whose commit rows collide by SHA in the shared `commits` table let an attacker's legitimately-verified organization inject a status for a commit that actually belongs to a different organization's `Stack`.

Existing guards do not close this gap: `verify_signature` only certifies "this payload's claimed org's secret matches," it says nothing about which `Stack`/`Commit` rows may be touched; `drop_unhandled_event` and the `ExplicitParameters` schema in `StatusHandler` only validate payload shape, not repository/stack ownership; there is no `require_permission!`, `Repository` format check, or `stack.repository.owner == repository_owner` assertion anywhere in this path.

### Impact Explanation
An attacker who legitimately owns/administers **any** GitHub organization/App instance that Shipit trusts (a valid, self-configured `webhook_secret`, which is entirely normal for any onboarded tenant) can post a `status` webhook for a SHA that also exists as a `Commit` row under a *different* stack/organization. This can flip that commit's `Status` to `success`, altering `deployable?`/`blocked?` for a victim stack the attacker has no access to, and can result in an unauthorized deploy execution (`Command#start`/`PTY.spawn`) using the victim stack's own `GITHUB_TOKEN`/deploy secrets. This satisfies the "payload for one repository mutating another's stack/commit/task" and "unauthorized deploy" Critical impact categories. It is repeatable against any SHA-colliding commit row and any onboarded tenant pair sharing this instance.

### Likelihood Explanation
Requires: (1) the attacker to control an organization/App that is already configured with its own `webhook_secret` in this Shipit instance (i.e., they are a legitimate — even if otherwise unrelated — tenant, or otherwise a repo whose owner login is recognized by `Shipit.github`), and (2) a commit SHA collision between that organization's repository history and the victim's tracked stack's commit history (achievable via forking a public repo, since unmodified ancestor commits keep identical SHAs). Given multi-tenant self-hosted Shipit deployments commonly configure several orgs/Apps, and public-repo forking trivially reproduces identical historical SHAs, this is a feasible and repeatable attack path once the attacker holds any valid webhook credential in the system.

### Recommendation
In `StatusHandler#process` (and the analogous check-run handler), scope the `Commit` lookup by the verified repository/organization, e.g. join through `stack.repository` and assert `commit.stack.repository.owner.casecmp?(repository_owner)` (or pass the verified repository identity down from the controller and filter `Commit.where(sha:, stack: { repository: { owner: verified_owner, name: verified_repo_name } })`) before calling `create_status_from_github!`. Reject/skip commits whose stack's repository does not match the payload's verified repository.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, or integration test on `WebhooksController`):
1. Create two `Stack`/`Repository` fixtures for two different "organizations": `victim_stack` under `owner: 'victim-org'` and `attacker_stack`/no stack at all for `owner: 'attacker-org'`.
2. Create a `Commit` row with a shared `sha` (e.g. `'deadbeef' * 5`) belonging to `victim_stack`, with `continuous_deployment: true`, `ignore_ci?` false.
3. Stub `Shipit.github(organization: 'attacker-org')` to return a `GitHubApp` whose `webhook_secret` is known/attacker-controlled, and post a `status` payload (`repository.owner.login == 'attacker-org'`, same `sha`, `state: 'success'`) signed with that secret to `POST /webhooks` with header `X-Github-Event: status`.
4. Assert: (a) response is `200`; (b) `victim_commit.reload.status.success?` becomes true even though the payload's verified org (`attacker-org`) never equals `victim_stack.repository.owner` (`victim-org`) — i.e., assert the equality `payload_verified_owner == commit.stack.repository.owner` is **false** yet the status write still occurred; (c) stub `Command.start`/`PTY.spawn`/`Stack#trigger_deploy` and assert it is invoked for `victim_stack` as a result of `ContinuousDeliveryJob` being enqueued/performed from `Commit#schedule_continuous_delivery`.

    def trigger_continuous_delivery
      return if cached_deploy_spec.blank?

      commit = next_commit_to_deploy

      if should_resume_continuous_delivery?(commit)
        continuous_delivery_resumed!
        return
      end

        continuous_delivery_delayed!
        return
      end

      rescue Task::ConcurrentTaskRunning
      end
