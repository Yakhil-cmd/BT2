### Title
Autonomous Agents cannot be paused, upgraded, or removed once deployed, permanently exposing all connected funds to any bug in the AA logic - (File: validation.js / aa_composer.js / aa_validation.js)

### Summary
Obyte's Autonomous Agents (AAs) are the direct architectural analog of "minters" in the Frankencoin report: they are permissionless, self-governing programs that anyone can deploy and that other users then trust with funds (via payments) or with novel financial logic (oracles, auctions, AMMs, etc.). Exactly like the MintingHub example in the original finding, an AA is a "novel mechanism" whose correctness is unverified by the protocol, yet — unlike a centrally‑governed minter which at least has a 10‑day window to be denied — an AA has **no removal, pause, or upgrade path of any kind**, ever, at the protocol level.

### Finding Description
The validation code explicitly documents this immutability: [1](#0-0) 

The comment states: *"AA definition cannot be changed and its address is also its definition_chash"* — the AA's address is the content hash of its own definition, so there is no notion of "the same AA with a different/patched definition." This is enforced in `aa_validation.validateAADefinition` and in the way AA definitions are looked up: [2](#0-1) 

Once an AA address is inserted into `aa_addresses` (see `insertAADefinitions`), that row's `definition` column is immutable and is looked up by every future trigger: [3](#0-2) 

Every unit sent to the AA's address is processed by `handleTrigger`, which loads `arrDefinition` from storage and executes it unconditionally — there is no check for an admin flag, pause state, deny list, or expiry baked into the protocol itself: [4](#0-3) 

Contrast this with the *other* self-governing primitives in ocore, which explicitly support revocation:
- Asset attestor lists can be updated/removed by the definer via `asset_attestors` (`validateAttestorListUpdate`): [5](#0-4) 
- Regular addresses can change their spending definition via `address_definition_change` (`writer.js`): [6](#0-5) 
- System parameters/OP list can be voted out via `system_vote`/`system_vote_count`: [7](#0-6) 

AAs have none of these mechanisms. Any pause/limit/kill-switch must be manually coded into the AA's own oscript by its author — precisely the mitigation luziusmeisser described for Frankencoin's minters ("experimental minters should come with their own limits... They are free to include that"). If the author does not include such safeguards (or includes them incorrectly), there is no protocol-level backstop.

### Impact Explanation
If a deployed AA contains a logic bug (e.g., in balance accounting, bounce-fee handling, formula evaluation edge cases such as those parsed in `formula/evaluation.js`, or in a novel price/auction mechanism it implements), that bug is permanently and repeatedly exploitable by anyone who discovers it, because:
- Funds already sent to the AA and tracked in `aa_balances` remain reachable only through the AA's original (buggy) code path — see the balance bookkeeping in `insertAADefinitions`: [8](#0-7) 
- There is no way for any party (not the deployer, not order providers/witnesses, not the wider community) to halt trigger processing for that address once it goes live, unlike Frankencoin where a 10-day denial window at least exists.
- Continuous triggering (`handleTrigger`) means an exploitable bug leads to either unauthorized draining of AA-held funds (unauthorized spending / fund loss) or permanent lock-up of funds if the bug causes triggers to bounce/lose state indefinitely (fund freezing) — both are within the accepted impact classes for this analysis.

### Likelihood Explanation
Likelihood is inherent rather than probabilistic: this is not a rare edge case but the standing behavior of every AA ever deployed. Any AA author, including well-intentioned ones building complex financial primitives (order books, AMMs, futures contracts — see `test/samples/futures_contract.oscript`, `test/samples/uniswap_like_market_maker.oscript`), inherits this risk by default unless they hand-roll their own pause/limit logic in oscript, exactly as the original report's mitigation discussion anticipated.

### Recommendation
Because this mirrors an acknowledged, intentional design tradeoff (the Frankencoin team also declined to add minter removal, pushing the responsibility onto individual minter authors), the practical mitigations are the same as recommended there:
- Continue to strongly document/require that any AA meant to hold significant value implement its own intern pause/kill-switch logic (e.g., a state variable `paused` checked in every message case, or a time-based expiry).
- Consider a protocol-level AA deprecation/pause mechanism (e.g., a system vote to mark an AA address as "deprecated" and reject new triggers, or a time-limited AA registration similar to Frankencoin's 10-day window).
- Provide tooling and templates for safe AA patterns (e.g., a base AA with built-in pause/upgrade hooks that specialized AAs can inherit via `base_aa`).

### Proof of Concept
1. Deploy an AA with a subtle bug in its balance accounting or bounce-fee logic.
2. Users send funds to the AA address (creating outputs with `address = AA_address`).
3. Triggers arrive; `handleTrigger` loads the immutable definition and executes it.
4. The bug is exploited (e.g., balance underflow, unauthorized transfer, or permanent bounce loop).
5. No protocol mechanism exists to pause, upgrade, or remove the AA.
6. Funds are either drained or frozen indefinitely.

Example: An AA that implements a novel auction mechanism (like Frankencoin's MintingHub) could have a rounding error in price calculation that allows an attacker to acquire collateral at a discount. Once deployed, this bug is permanent and repeatable. [9](#0-8) [10](#0-9)
