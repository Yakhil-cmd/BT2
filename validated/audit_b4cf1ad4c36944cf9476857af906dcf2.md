### Title
`BridgeTransferERC20.onERC20Received()` Lacks Deposit Verification, Allowing a Registered Token to Drain the Counterpart Bridge — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

---

### Summary

`onERC20Received()` is the 1-step deposit callback for the Kaia service-chain bridge. It is declared `public` with no access-control modifier on the function itself. The only guard lives inside the `internal` helper `_requestERC20Transfer`, which checks `onlyRegisteredToken(msg.sender)`. That check verifies the *caller is a registered token contract*, but it does **not** verify that any tokens were actually transferred to the bridge before the callback was invoked. A registered token contract can therefore call `onERC20Received()` with arbitrary parameters and zero deposit, causing the bridge to emit a `RequestValueTransfer` event that the counterpart bridge operator will honour by releasing real tokens.

The same structural defect exists in `onERC721Received()` in `BridgeTransferERC721.sol`.

---

### Finding Description

**1-step deposit flow (intended):**
1. User calls `ERC20ServiceChain.requestValueTransfer()`.
2. Token contract executes `transfer(bridge, amount + feeLimit)` — tokens arrive in the bridge.
3. Token contract calls `bridge.onERC20Received(from, to, value, feeLimit, extraData)`.

**2-step deposit flow (safe):**
`requestERC20Transfer()` explicitly pulls tokens before delegating to `_requestERC20Transfer`:
```solidity
IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
_requestERC20Transfer(_tokenAddress, msg.sender, _to, _value, _feeLimit, _extraData);
``` [1](#0-0) 

**Vulnerable 1-step path:**
`onERC20Received()` calls `_requestERC20Transfer(msg.sender, ...)` with no prior balance check:
```solidity
function onERC20Received(
    address _from, address _to, uint256 _value,
    uint256 _feeLimit, bytes memory _extraData
) public {
    _requestERC20Transfer(msg.sender, _from, _to, _value, _feeLimit, _extraData);
}
``` [2](#0-1) 

Inside `_requestERC20Transfer`, the only caller check is:
```solidity
modifier onlyRegisteredToken(address _token) {
    require(registeredTokens[_token] != address(0), "not allowed token");
    _;
}
``` [3](#0-2) 

This confirms the caller is a registered token, but **not** that it transferred `_value + _feeLimit` tokens to the bridge before making the call.

**Secondary drain via `_payERC20FeeAndRefundChange`:**
When `_feeLimit > 0` and no fee is configured, the bridge transfers `_feeLimit` tokens *from its own balance* back to `_from`:
```solidity
if (_feeLimit > 0) {
    IERC20(_token).safeTransfer(from, _feeLimit);
}
``` [4](#0-3) 

A registered token contract can set `_from` to any address and `_feeLimit` to the bridge's entire token balance, draining it in a single call.

**Identical pattern in ERC721:**
```solidity
function onERC721Received(
    address _from, uint256 _tokenId, address _to, bytes memory _extraData
) public {
    _requestERC721Transfer(msg.sender, _from, _to, _tokenId, _extraData);
}
``` [5](#0-4) 

---

### Impact Explanation

**Lock/unlock mode (most severe):** `_requestERC20Transfer` emits `RequestValueTransfer` and increments `requestNonce` without any token movement on the source chain. The bridge operator's off-chain listener (`BridgeInfo.handleRequestValueTransferEvent`) observes the event and submits `handleERC20Transfer` on the counterpart chain, releasing real tokens to `_to` with no corresponding deposit. [6](#0-5) 

**Mint/burn mode:** `ERC20Burnable(_tokenAddress).burn(_value)` is called on the bridge's balance; if the bridge holds tokens, they are burned and the counterpart mints new ones — net inflation of the bridged asset supply.

**Fee-path drain:** With `_feeLimit` set to the bridge's full token balance and `_from` set to an attacker-controlled address, the bridge transfers all held tokens out via `_payERC20FeeAndRefundChange` before the event is even emitted.

Exact corrupted values: `requestNonce` is incremented without a real deposit; the counterpart bridge's token balance decreases by `_value`; the source bridge's token balance decreases by `_feeLimit` (fee-drain path).

---

### Likelihood Explanation

The trigger requires `msg.sender` to be a registered token contract. Token registration is `onlyOwner`, so the attacker surface is:
- A registered token contract that is itself upgradeable or has a re-entrancy/delegatecall path.
- A registered token contract whose owner key is compromised.
- A token contract registered in good faith that later becomes malicious (e.g., proxy upgrade).

This is a semi-trusted caller scenario. The bridge owner controls registration, but the token contract's internal logic is not constrained by the bridge. Likelihood is **Low–Medium**.

---

### Recommendation

1. **Add an explicit `onlyRegisteredToken` modifier to `onERC20Received` and `onERC721Received`** so the access-control intent is visible at the call site and cannot be accidentally removed from the internal helper.

2. **Verify the deposit occurred** by recording the bridge's token balance before and after the callback and requiring it increased by at least `_value + _feeLimit`:
   ```solidity
   function onERC20Received(...) public onlyRegisteredToken(msg.sender) {
       uint256 balBefore = IERC20(msg.sender).balanceOf(address(this));
       _requestERC20Transfer(msg.sender, _from, _to, _value, _feeLimit, _extraData);
       require(
           IERC20(msg.sender).balanceOf(address(this)) >= balBefore,
           "no deposit received"
       );
   }
   ```
   (The balance check must account for the fee refund path in `_payERC20FeeAndRefundChange`.)

3. Apply the same fix to `onERC721Received` in `BridgeTransferERC721.sol`.

---

### Proof of Concept

```
Preconditions:
  - Bridge deployed in lock/unlock mode (modeMintBurn = false).
  - MaliciousToken is registered: bridge.registerToken(MaliciousToken, counterpartToken).
  - Bridge holds 10,000 tokens from prior legitimate deposits.
  - feeReceiver == address(0) (default).

Attack:
  1. MaliciousToken.attack() calls:
       bridge.onERC20Received(
           attacker,          // _from  (fee refund target)
           victim,            // _to    (counterpart recipient)
           1,                 // _value (> 0 to pass require)
           10_000e18,         // _feeLimit = entire bridge balance
           ""
       );

  2. _requestERC20Transfer executes:
       a. onlyRegisteredToken(MaliciousToken) → passes.
       b. _payERC20FeeAndRefundChange(attacker, MaliciousToken, 10_000e18):
            feeReceiver == address(0), so:
            IERC20(MaliciousToken).safeTransfer(attacker, 10_000e18)
            → bridge balance drained to 0.
       c. RequestValueTransfer emitted with _value=1, requestNonce=N.
       d. requestNonce++.

  3. Bridge operator sees RequestValueTransfer(nonce=N, value=1, to=victim).
     Calls handleERC20Transfer on counterpart chain → releases 1 token to victim.

Result:
  - Source bridge: lost 10,000 tokens (fee-drain) + emitted a phantom request.
  - Counterpart bridge: released 1 token with no real deposit backing it.
  - requestNonce advanced, consuming a nonce slot permanently.

    function _payERC20FeeAndRefundChange(address from, address _token, uint256 _feeLimit) internal returns(uint256) {
        uint256 fee = feeOfERC20[_token];

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            IERC20(_token).safeTransfer(feeReceiver, fee);

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                IERC20(_token).safeTransfer(from, feeRefund);
            }

            return fee;
        }

        if (_feeLimit > 0) {
            IERC20(_token).safeTransfer(from, _feeLimit);
        }
        return 0;
    }

// handleRequestValueTransferEvent handles the given request value transfer event.
func (bi *BridgeInfo) handleRequestValueTransferEvent(ev IRequestValueTransferEvent) error {
	var (
		tokenType                         = ev.GetTokenType()
		tokenAddr, from, to, contractAddr = ev.GetTokenAddress(), ev.GetFrom(), ev.GetTo(), ev.GetRaw().Address
		txHash                            = ev.GetRaw().TxHash
		valueOrTokenId                    = ev.GetValueOrTokenId()
		requestNonce, blkNumber           = ev.GetRequestNonce(), ev.GetRaw().BlockNumber
		extraData                         = ev.GetExtraData()
	)

	ctpartTokenAddr := bi.GetCounterPartToken(tokenAddr)
	// TODO-Kaia-Servicechain Add counterpart token address in requestValueTransferEvent
	if tokenType != KAIA && ctpartTokenAddr == (common.Address{}) {
		logger.Warn("Unregistered counter part token address.", "addr", ctpartTokenAddr.Hex())
		ctTokenAddr, err := bi.counterpartBridge.RegisteredTokens(nil, tokenAddr)
		if err != nil {
			return err
		}
		if ctTokenAddr == (common.Address{}) {
			return errors.New("can't get counterpart token from bridge")
		}
		if err := bi.RegisterToken(tokenAddr, ctTokenAddr); err != nil {
			return err
		}
		ctpartTokenAddr = ctTokenAddr
		logger.Info("Register counter part token address.", "addr", ctpartTokenAddr.Hex(), "cpAddr", ctTokenAddr.Hex())
	}

	bridgeAcc := bi.account

	bridgeAcc.Lock()
	defer bridgeAcc.UnLock()

	auth := bridgeAcc.GenerateTransactOpts()

	var handleTx *types.Transaction
	var err error

	switch tokenType {
	case KAIA:
		handleTx, err = bi.bridge.HandleKLAYTransfer(auth, txHash, from, to, valueOrTokenId, requestNonce, blkNumber, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[KAIA], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	case ERC20:
		handleTx, err = bi.bridge.HandleERC20Transfer(auth, txHash, from, to, ctpartTokenAddr, valueOrTokenId, requestNonce, blkNumber, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[ERC20], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	case ERC721:
		uri := GetURI(ev)
		handleTx, err = bi.bridge.HandleERC721Transfer(auth, txHash, from, to, ctpartTokenAddr, valueOrTokenId, requestNonce, blkNumber, uri, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[ERC721], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	default:
		logger.Error("Got Unknown Token Type ReceivedEvent", "bridge", contractAddr, "nonce", requestNonce, "from", from)
		return nil
	}

	bridgeAcc.IncNonce()

	bi.bridgeDB.WriteHandleTxHashFromRequestTxHash(txHash, handleTx.Hash())
	return nil
