### Title
Unscoped `Commit.where(sha:)` in `StatusHandler#process` lets any repo's status webhook mutate another repo's commit status - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up every `Commit` row matching the payload `sha` with no repository/stack filter and writes a `Status` to each one. Because `Commit` SHAs are only unique per `stack_id` (`add_index :commits, %i(sha stack_id), unique: true`), a SHA shared across repositories (e.g. via a fork, mirrored repo, or another stack tracking the same repo) lets a status event validly signed for one organization mutate commit state belonging to a completely unrelated stack.

### Finding Description
The broken binding: the handler assumes `commit.stack.repository == event.repository`, but the code never checks it — `Commit.where(sha: params.sha)` (`app/models/shipit/webhooks/handlers/status_handler.rb:21`) has no `stack_id`/repository predicate. `WebhooksController#verify_signature` only validates that the payload's signature matches the GitHub App secret for `repository_owner` (the org named in the payload) [4](#0-3) ; it says nothing about which `Commit`/`Stack` rows the handler is allowed to touch. `StatusHandler` itself performs no repository check — it only validates the ExplicitParameters schema (`sha`, `state`, etc.) [5](#0-4) .

Exploit flow: attacker owns (or forks) a repository under an org that already has a working Shipit GitHub App/webhook installation. Forking a public victim repository preserves all of the victim's commit SHAs verbatim in the fork. Attacker pushes/tags in their own fork, causing GitHub to fire a legitimately-signed `status` event for their own org with `sha` equal to a commit that also exists (with a different `stack_id`) in the victim's stack, `context: "ci/integration"`, `state: "failure"`. `verify_signature` passes because the signature is valid for the attacker's own org. `StatusHandler#process` then finds **all** `Commit` rows across the DB matching that sha — including the victim's — and calls `commit.create_status_from_github!(params)` on each, via `Commit#create_status_from_github!` → `Status.replicate_from_github!` (`app/models/shipit/commit.rb:165-169`, `app/models/shipit/status.rb:24-33`). If `ci/integration` is in the victim stack's `ci.require`, this flips the victim commit's `deployable?` (`app/models/shipit/commit.rb:227-229`) via `status.rb`'s state computation, blocking or unblocking merges/deploys.

### Impact Explanation
A `status` webhook that only authenticates for the attacker's own repository/org writes `Status` records against `Commit` rows owned by other stacks/repositories — a payload for one repository mutating another's commit records, matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." This can flip `deployable?`/CI-required-context state on a victim commit, affecting merge eligibility and deploy gating for a repository the attacker never authenticated against. It is repeatable against any repository/stack that happens to share a commit SHA with a repo the attacker controls (most easily via forking).

### Likelihood Explanation
Preconditions: attacker needs a repo (fork of the victim's, or otherwise sharing a SHA) that already has a functioning Shipit GitHub App/webhook so `verify_signature` succeeds for their own org — this is cheap and available to any GitHub user who can fork a public repo and have their org onboarded to Shipit (or already has a stack). No Shipit session, API token, or secret is required. Sharing SHAs across repos via forking is a normal, zero-cost, always-available property of git, making this reliably reproducible, not a theoretical hash collision.

### Recommendation
Scope the lookup in `StatusHandler#process` to the stack(s)/repository that authenticated the event, e.g. resolve `Stack`s from `params.dig('repository','full_name')` (as `PushHandler` does) and constrain `Commit.where(sha: params.sha, stack_id: matching_stack_ids)`, rather than querying `Commit` globally by `sha` alone.
