### Title
Malicious KLAY Transfer Recipient Can Permanently Lock Bridge Funds — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

### Summary

`BridgeTransferKLAY.handleKLAYTransfer` performs an unchecked low-level call to a user-controlled `_to` address after all nonce-state updates have been written. A malicious recipient contract that always reverts causes the entire transaction to revert (including the nonce bookkeeping), permanently preventing the bridge from processing that nonce and locking the corresponding KLAY inside the bridge contract.

### Finding Description

`handleKLAYTransfer` is the on-chain settlement function called by bridge operators to deliver KLAY to the destination address that was originally specified by the user in `requestKLAYTransfer`. The function writes all state (nonce marking, `handleNoncesToBlockNums`, `_updateHandleNonce`) before making the external call:

```solidity
// BridgeTransferKLAY.sol lines 81-99
_setHandledRequestTxHash(_requestTxHash);
handleNoncesToBlockNums[_requestedNonce] = _requestedBlockNumber;
_updateHandleNonce(_requestedNonce);

emit HandleValueTransfer(...);

(bool ok, ) = _to.call.value(_value)("");   // ← user-controlled target
require(ok, "handleKLAYTransfer: transfer failed");
``` [1](#0-0) 

Because `require(ok, ...)` is placed after the external call, any failure of the callee (explicit `revert`, consuming all forwarded gas, or returning `false`) causes the entire transaction to revert, rolling back every state write above it. The nonce is therefore never durably marked as handled.

The `_to` address originates directly from the user's `requestKLAYTransfer` call on the source chain:

```solidity
// BridgeTransferKLAY.sol line 132
function requestKLAYTransfer(address _to, uint256 _value, bytes calldata _extraData) external payable {
``` [2](#0-1) 

There is no validation that `_to` is an EOA or a cooperative contract. An attacker deploys a contract whose `receive()` function always reverts (or consumes all forwarded gas), then uses that address as `_to`. Every operator attempt to settle nonce N will revert. Because `_updateHandleNonce` advances `lowerHandleNonce` only through consecutive settled nonces, the stuck nonce permanently prevents `lowerHandleNonce` from advancing past N, and the KLAY for that request is locked in the bridge forever. [3](#0-2) 

The analogous pattern in `BridgeFee._payKLAYFeeAndRefundChange` also makes bare low-level calls to `feeReceiver` and `msg.sender`, but those discard returndata and the callers are either owner-controlled or self-inflicted, so they are lower severity. [4](#0-3) 

### Impact Explanation

The KLAY deposited for nonce N is permanently locked inside the bridge contract. The user loses their bridged funds with no recovery path. Additionally, `recoveryBlockNumber` (used by the off-chain recovery scanner) stops advancing past nonce N, degrading the bridge's ability to recover from future gaps.

### Likelihood Explanation

Any user who initiates a KLAY bridge request can trigger this by setting `_to` to a contract that always reverts. No privileged access is required. The cost is only the gas for the source-chain `requestKLAYTransfer` call plus the KLAY value being sacrificed (or the attacker can use a minimal value). The attack is deterministic and repeatable.

### Recommendation

Move all state-mutating writes to after a successful delivery, or — more robustly — adopt a pull-payment pattern: record the pending KLAY credit for `_to` in a mapping and let the recipient claim it separately. This decouples delivery failure from nonce advancement. At minimum, wrap the delivery call so that a failed delivery does not revert the nonce bookkeeping:

```solidity
_setHandledRequestTxHash(_requestTxHash);
handleNoncesToBlockNums[_requestedNonce] = _requestedBlockNumber;
_updateHandleNonce(_requestedNonce);
emit HandleValueTransfer(...);

(bool ok, ) = _to.call.value(_value)("");
if (!ok) {
    pendingWithdrawals[_to] += _value;  // pull-payment fallback
}
```

### Proof of Concept

1. Attacker deploys `MaliciousReceiver` with `receive() external payable { revert(); }`.
2. Attacker calls `requestKLAYTransfer(address(maliciousReceiver), 1 ether, "")` on the source-chain bridge, sending `1 ether`.
3. The bridge operator observes the `RequestValueTransfer` event and calls `handleKLAYTransfer(..., maliciousReceiver, 1 ether, nonce, ...)` on the destination bridge.
4. The low-level call at line 98 forwards KLAY to `MaliciousReceiver.receive()`, which reverts.
5. `require(ok, ...)` reverts the entire transaction; all nonce state is rolled back.
6. Every subsequent operator retry produces the same revert.
7. `lowerHandleNonce` never advances past `nonce`; the 1 ether is permanently locked in the bridge. [5](#0-4)
