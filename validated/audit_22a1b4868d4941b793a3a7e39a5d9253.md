## Analysis

The report describes a bug class: a **secret credential is written to logs in plaintext**, letting anyone who can read the log (a lesser-privileged reader) gain full control of a protected resource (there, the DB; the "elevation" is from *log reader* to *DB owner*).

Searching ocore for equivalent "secret written verbatim to logs" patterns, the strongest analog is textcoin mnemonic logging in `wallet.js`.

A textcoin mnemonic is functionally a private key: `expandMnemonic()` derives the address, HD private key and definition directly from it [1](#0-0) , and `receiveTextCoin()`/`checkStability()` use that derived key to sign and spend the coin's balance [2](#0-1) . Anyone holding this string has unconditional custody over all funds sitting at that address — it is the exact equivalent of a "password" in the CVE analogy.

`claimBackOldTextcoins()` — a background job that automatically re-claims stale, unclaimed textcoins — prints the raw mnemonic to `console.log` on both success and failure paths, once per row fetched from `sent_mnemonics`: [3](#0-2) 

Every unclaimed textcoin's spending secret is therefore written verbatim into the node's log stream (which most deployments redirect to a file or a log-aggregation service) each time the periodic retry runs, independent of whether the claim ultimately succeeds.

### Title
Textcoin mnemonics (equivalent to private keys) are written in plaintext to application logs - (File: wallet.js)

### Summary
`claimBackOldTextcoins()` logs the full textcoin mnemonic — the secret from which the textcoin's private key and address are derived — via `console.log`, both on success and on failure, for every stale textcoin the node tries to auto-reclaim.

### Finding Description
A textcoin is created by generating a fresh BIP39 mnemonic and deriving an address from it (`expandMnemonic`), then funds are sent to that derived address; the mnemonic itself is stored in the `sent_mnemonics` table and normally only ever transmitted out-of-band (e.g. by email) to the intended recipient [4](#0-3) . Possession of the mnemonic is equivalent to possession of the private key controlling the address — anyone with the string can call `receiveTextCoin`/`expandMnemonic` and sign a spend from it [5](#0-4) .

`claimBackOldTextcoins(to_address, days)` selects all `sent_mnemonics` rows whose textcoin has not yet been claimed, then attempts to reclaim them and unconditionally logs `row.mnemonic` in plaintext for every attempt: [6](#0-5) 

This is the same bug class as CVE-2023-34097: a credential that grants full control of a protected asset (there, the DB connection; here, the textcoin funds) is written to a log sink that is more broadly readable than the credential itself should be (log files, log aggregation/monitoring pipelines, crash reporters, syslog forwarders, etc., which are commonly accessible to operators, monitoring tooling, or third parties with lower trust than the wallet process itself).

### Impact Explanation
Any actor who can read the node's stdout/log file (a common lower-privilege surface: log aggregators, shared hosting, crash/monitoring services, or anyone who later gains transient read access to disk/logs) obtains the mnemonic and can immediately derive the private key and steal the underlying funds before the intended recipient claims them, or race the recipient's claim. Because the mnemonic is the sole authorization factor for the textcoin, log exposure is equivalent to leaking a bearer private key — a direct path to unauthorized spending / fund theft, matching the CVE's "attacker gains full access" pattern.

### Likelihood Explanation
This is triggered automatically and repeatedly: `claimBackOldTextcoins` is a maintenance job that iterates over all unclaimed textcoins after `days` age and logs the mnemonic on every single attempt (success and failure), with no gating on log level or redaction. Any wallet operator running textcoin payments to email/text addresses is affected as soon as a payment goes unclaimed past the configured window, requiring no special conditions beyond normal textcoin usage.

### Recommendation
Never log the raw mnemonic. Replace both `console.log` calls in `claimBackOldTextcoins` with messages referencing only the derived address/unit (which are already non-secret), e.g. log `addrInfo.address` or the textcoin's associated `address` field from `sent_mnemonics` instead of `row.mnemonic`. Audit other call sites (e.g. `sendTextcoinEmail`, error paths in `receiveTextCoin`) to ensure the mnemonic is never included in thrown `Error` messages or `console.log`/`console.error` output, since those propagate into logs and `nonfatal_error` event data as well.

### Proof of Concept
1. Send a textcoin payment to an email address via `sendMultiPayment`, which stores the generated mnemonic in `sent_mnemonics` [7](#0-6) .
2. Do not let the recipient claim it before `days` elapses.
3. Let the node's periodic job invoke `claimBackOldTextcoins(to_address, days)`.
4. Observe the node's log output / log file containing `"claimed back mnemonic <mnemonic>, unit ..., asset ..."` or `"failed claiming back old textcoin <mnemonic>: ..."` in plaintext.
5. Any party who can read that log (log aggregation service, less-trusted co-tenant, monitoring pipeline, etc.) extracts the mnemonic and calls `expandMnemonic`/`receiveTextCoin` themselves to steal the funds.

function expandMnemonic(mnemonic) {
	var addrInfo = {};
	mnemonic = mnemonic.toLowerCase().split('-').join(' ');
	if ((mnemonic.split(' ').length % 3 !== 0) || !Mnemonic.isValid(mnemonic)) {
		throw new Error("invalid mnemonic: "+mnemonic);
	}
	mnemonic = new Mnemonic(mnemonic);
	addrInfo.xPrivKey = mnemonic.toHDPrivateKey().derive("m/44'/0'/0'/0/0");
	addrInfo.pubkey = addrInfo.xPrivKey.publicKey.toBuffer().toString("base64");
	addrInfo.definition = ["sig", {"pubkey": addrInfo.pubkey}];
	addrInfo.address = objectHash.getChash160(addrInfo.definition);
	return addrInfo;

// if a textcoin was not claimed for 'days' days, claims it back
function claimBackOldTextcoins(to_address, days){
	if (typeof days !== 'number')
		throw Error("bad days: " + days);
	db.query(
		"SELECT mnemonic FROM sent_mnemonics LEFT JOIN unit_authors USING(address) \n\
		WHERE mnemonic!='' AND unit_authors.address IS NULL AND creation_date<"+db.addTime("-"+days+" DAY"),
		function(rows){
			async.eachSeries(
				rows,
				function(row, cb){
					receiveTextCoin(row.mnemonic, to_address, function(err, unit, asset){
						if (err)
							console.log("failed claiming back old textcoin "+row.mnemonic+": "+err);
						else
							console.log("claimed back mnemonic "+row.mnemonic+", unit "+unit+", asset "+asset);
						cb();
					});
				}
			);
		}
	);
}
