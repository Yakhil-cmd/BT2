## Title
Missing chain/network domain separator in NEP-366/NEP-461 `DelegateAction` signature scheme enables cross-chain meta-transaction replay - (File: `core/primitives/src/signable_message.rs`, `core/primitives/src/action/delegate.rs`)

### Summary
The `DelegateAction`/`SignedDelegateAction` meta-transaction signing scheme (NEP-366, using the NEP-461-style `MessageDiscriminant`) binds a signature only to a NEP-number discriminant, `sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, and `public_key`. It does not include any chain/network identifier (e.g. genesis hash or `chain_id`) in the signed payload, so the same `SignedDelegateAction` bytes are valid on any NEAR-protocol chain that shares the same account/access-key/nonce state — for example a testnet or private chain bootstrapped from a mainnet state snapshot, or a chain that forks from a common ancestor.

### Finding Description
`SignableMessage::sign`/`SignedDelegateAction::verify` hash exactly the discriminant plus the borsh-serialized `DelegateAction` fields: [1](#0-0) [2](#0-1) 

The discriminant itself is only a NEP-number tag (366 for `DelegateAction`, 611 for `DelegateActionV2`), not a network/chain identifier: [3](#0-2) [4](#0-3) [5](#0-4) 

Replay protection inside a single chain is enforced entirely through on-chain state: the access-key nonce (`validate_delegate_action_key`) and `max_block_height`: [6](#0-5) 

These are chain-local counters (access key nonce, block height), not chain-global secrets. If a second NEAR-protocol chain is started from a state that happens to replicate the sender's account, access key, and nonce (e.g., a testnet/sandbox seeded from a mainnet state dump, a short-lived hard fork, or any deployment that clones account state), a `SignedDelegateAction` captured from chain A (from the transaction pool, an explorer, or a relayer log) remains fully valid on chain B, because nothing in the signed bytes ties it to a specific chain. This mirrors the reported `KinoAccountMinterUpgradable.mintBySignature` issue: the signature has no domain separator distinguishing "this signed intent is only valid on chain X," so it can be extracted and rebroadcast on another chain where the same preconditions (parent state/nonce) hold.

### Impact Explanation
If exploited on a chain that shares state with the origin chain, an attacker (any unprivileged party who can observe the relayer's mempool/transaction, which is public data) can resubmit the exact same `SignedDelegateAction` to the other chain via `Action::Delegate`/`Action::DelegateV2`, causing the delegated actions (transfers, function calls, key additions, etc.) to execute a second time without the sender's renewed consent, and with a *different* relayer paying gas on that chain. This is unauthorized action execution / state change originating purely from public transaction data, not from any new authorization by the account owner. Actual token loss or double-spend impact depends on whether such a duplicated-state chain exists and is production-relevant (e.g., testnets forked from mainnet snapshots for load-testing, or a permanent network split), which is an operational/deployment factor rather than a code guarantee.

### Likelihood Explanation
Low likelihood in typical single-mainnet operation, since exploitation requires a second live NEAR-protocol chain that duplicates the victim account's exact access-key/nonce state. Likelihood increases in any workflow where NEAR mainnet/testnet state is cloned for staging or forked (a pattern NEAR tooling explicitly supports for state-based testing), because a captured mainnet `SignedDelegateAction` would still validate against the cloned nonce/access-key state until it diverges.

### Recommendation
Bind the signed payload to a chain-specific domain separator (e.g., include the genesis hash or a protocol `chain_id` inside the `SignableMessage`/`DelegateAction` structure that is hashed and signed), analogous to EIP-712's `chainId` field, so a signature produced for one NEAR network cannot be replayed on another network even when account/nonce state coincidentally matches.

### Proof of Concept
1. Chain A (e.g., mainnet) and Chain B (e.g., a testnet/sandbox bootstrapped from a snapshot of chain A's state) both contain account `alice.near` with the same access key and the same current nonce for that key.
2. Alice signs a `DelegateAction` (nonce = N+1, `max_block_height` far in the future) and hands it to a relayer on chain A; the relayer wraps it in `Action::Delegate` and submits it, and it succeeds — bumping Alice's access key nonce to N+1 on chain A only, via `validate_delegate_action_key` in `runtime/runtime/src/actions.rs`.
3. An observer captures the `SignedDelegateAction` bytes from chain A's transaction (public data).
4. On chain B, Alice's access key nonce is still N (chain B's state has not been advanced by step 2), so the same bytes pass `SignedDelegateAction::verify` (no chain identifier checked) and `validate_delegate_action_key`'s nonce check (`delegate_nonce.nonce() > current_nonce`), and the delegated actions execute a second time on chain B, paid for by whichever relayer submits it there.

impl SignedDelegateAction {
    pub fn verify(&self) -> bool {
        let delegate_action = &self.delegate_action;
        let hash = delegate_action.get_nep461_hash();
        let public_key = &delegate_action.public_key;

        self.signature.verify(hash.as_ref(), public_key)
    }

    pub fn sign(singer: &Signer, delegate_action: DelegateAction) -> Self {
        let signature = singer.sign(delegate_action.get_nep461_hash().as_bytes());
        Self { delegate_action, signature }
    }
}

impl<'a, T: BorshSerialize> SignableMessage<'a, T> {
    pub fn new(msg: &'a T, ty: SignableMessageType) -> Self {
        let discriminant = ty.into();
        Self { discriminant, msg }
    }

    pub fn sign(&self, signer: &Signer) -> Signature {
        let bytes = borsh::to_vec(&self).expect("Failed to deserialize");
        let hash = hash(&bytes);
        signer.sign(hash.as_bytes())
    }
}
