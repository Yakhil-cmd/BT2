### Title
Cross-organization webhook forgery via organization/repository binding mismatch in `WebhooksController#verify_signature` - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to validate a webhook against using an attacker-controlled field from the *unverified* JSON body (`repository.owner.login` / `organization.login`), but the handlers that actually act on the payload use a *different* attacker-controlled field (`repository.full_name`, `organization.login`, `team.id`, etc.) to decide which `Stack`/`Repository`/`Team` gets written to. The signature only proves "this body was signed with organization X's secret" — it never proves that the repository/organization being mutated is actually organization X's. This is the same class of bug as the `refundLoan()` report: one field is used to satisfy a check, while a different, uncoupled field drives the actual effect, and the two are never forced to be equal.

### Finding Description
`verify_signature` computes the organization used to pick the verification secret from the raw JSON body before any authenticity check has occurred: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the `GitHubApp` (and its `webhook_secret`) keyed by that attacker-supplied `repository_owner` value, then verifies the raw body's HMAC against **that** organization's secret: [3](#0-2) 

Nothing ties this "organization whose secret validated the signature" to the "organization/repository/team the handler subsequently writes to". Handlers resolve their target purely from other JSON fields in the same attacker-controlled body:

- `PushHandler` resolves stacks via `stacks` (derived from `repository.full_name`) and calls `stack.sync_github`: [4](#0-3) 
- The base `Handler#stacks` looks up by `payload.dig('repository', 'full_name')`, a field independent from `repository.owner.login` used for signature selection: [5](#0-4) 
- `StatusHandler` creates a CI status on any `Commit` matching an attacker-controlled `sha`, with no repository scoping check at all: [6](#0-5) 
- `MembershipHandler` creates/updates a `Team` and adds/removes members based on `organization.login` and `team.id`, again decoupled from the value used for signature verification: [7](#0-6) 

Additionally, `verify_webhook_signature` fails open when a configured organization has no `webhook_secret` set (`return true unless webhook_secret`): [8](#0-7) . The sample multi-org config even ships with `webhook_secret: # nil` for each org: [9](#0-8) , showing this is a realistic configuration state, not a contrived edge case.

**Binding broken (equality that should hold but doesn't):**
`organization whose secret validated the HMAC` **≠** `repository/organization/team actually mutated by the handler`.

### Impact Explanation
In any Shipit deployment configured with multiple GitHub organizations (as explicitly documented in `docs/setup.md`), a party who legitimately controls a GitHub App installation (and therefore knows the `webhook_secret`) for **one** configured organization (`org-A`) can forge an HTTP POST directly to `/webhooks` with a custom JSON body:
- `repository.owner.login` (or `organization.login`) = `org-A` (used only to pick the verification secret)
- `repository.full_name` / `team.id` / `sha` = anything belonging to `org-B` or any other repository/stack managed by the same Shipit instance

Because the HMAC is computed over the attacker-chosen raw body using `org-A`'s known secret, `verify_signature` passes, and the dispatched handler then acts on the unrelated `org-B` data. Concretely this allows:
- Forging `status` events to mark arbitrary commits as `success`, potentially satisfying CI-required-status checks and unlocking deploys/merges for repositories the attacker has no legitimate access to (an unauthorized deploy path).
- Forging `push`/`check_suite` events to trigger `GithubSyncJob`/`RefreshCheckRunsJob` against arbitrary stacks.
- Forging `membership` events to add arbitrary GitHub users to a `Team`, which can affect `Shipit.github_teams`-based authorization (escalation into team-based authorization).
- If any configured org has a blank `webhook_secret` (a documented, shipped configuration pattern), an attacker with no credentials at all can forge webhooks for **every** repository managed by the Shipit instance.

This meets the "cross-repository writes" / "unauthorized deploy" (Critical) and "escalation into `Shipit.github_teams` authorization" (High) impact bars defined in scope.

### Likelihood Explanation
Requires the deployment to use the documented multi-organization `github:` configuration (explicitly supported and documented) and requires the attacker to hold legitimate webhook credentials for at least one of the configured organizations — a realistic scenario for any Shipit instance serving more than one GitHub org/team, since org admins are not privileged with respect to other orgs on the same instance. The additional fail-open path (`unless webhook_secret`) further raises likelihood since it is a plausible misconfiguration explicitly present in the shipped sample config.

### Recommendation
Bind signature verification to the same identity used for the write:
- Derive a single canonical repository/organization identity from the payload once, verify the signature using that organization's secret, and pass that verified identity into every handler instead of letting handlers independently re-derive the target repository/organization/team from separate, unauthenticated fields.
- Reject requests where `repository.owner.login`/`organization.login` does not match the owner embedded in `repository.full_name`.
- Change `verify_webhook_signature` to fail closed (reject) when `webhook_secret` is blank, rather than treating a missing secret as automatically verified.

### Proof of Concept
1. Configure Shipit with two GitHub organizations, `org-a` and `org-b`, each with its own `webhook_secret` (per `docs/setup.md`), both managed on the same Shipit instance.
2. As the legitimate owner/admin of the `org-a` GitHub App (who knows `org-a`'s `webhook_secret` only), craft a JSON body:
```json
{
  "sha": "<victim-commit-sha-in-org-b-repo>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(org-a_webhook_secret, raw_body)>`.
4. Send `POST /webhooks` with header `X-Github-Event: status` and the above body/signature.
5. `verify_signature` looks up `Shipit.github(organization: 'org-a')`, verifies the HMAC against `org-a`'s secret — which matches — and passes.
6. `StatusHandler#process` then creates a `success` status on the commit belonging to `org-b/victim-repo`, entirely outside the attacker's authorized scope, potentially satisfying required-CI checks and enabling an unauthorized merge/deploy of that commit.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
