### Title
Cross-Organization Webhook Confused Deputy: Signature Verified Against `repository.owner.login` But Stack Mutated By Unrelated `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
The analog of the oracle-drift binding break here is: **the organization whose secret authenticated the webhook ≠ the repository whose stacks are actually mutated.** `WebhooksController#verify_signature` selects which organization's webhook secret to verify the HMAC against using `repository_owner`, taken from `params.dig('repository', 'owner', 'login')` [1](#0-0) , while the actual downstream handler resolves which `Stack`s to act on using a *different* field from the same untrusted JSON body, `repository.full_name`, with no cross-check that the two agree [2](#0-1) .

### Finding Description
`WebhooksController#verify_signature` computes `repository_owner` from the payload and fetches that organization's GitHub App/webhook config via `Shipit.github(organization: repository_owner)`, then verifies `X-Hub-Signature` against that org's `webhook_secret` [3](#0-2) [4](#0-3) . This proves only that *some* legitimate holder of organization A's webhook secret sent the request — it says nothing about which repository the payload actually names.

Once verification passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the raw, attacker-controlled JSON to handlers such as `PushHandler` [5](#0-4) . `Handler#stacks` resolves the target stacks purely from `payload.dig('repository', 'full_name')` via `Repository.from_github_repo_name` [2](#0-1) [6](#0-5)  — a field that is never checked against `repository.owner.login`/`repository_owner`, the value that determined which secret was used for signature verification.

`PushHandler#process` then calls `stack.sync_github(expected_head_sha: params.after)` for every non-archived stack on the *resolved* (attacker-chosen) repository whose branch matches the payload's `ref` [7](#0-6) .

Concretely: an attacker who legitimately controls (or is an admin/member of) Organization A onboarded on this Shipit instance — and therefore knows Organization A's webhook secret because they configured it — can send a webhook with `X-Github-Event: push`, `repository.owner.login = "OrgA"` (so `verify_signature` checks the HMAC against Org A's secret, which they can produce correctly) but `repository.full_name = "OrgB/victim-repo"` (an unrelated, victim organization/repository also hosted on the same multi-tenant Shipit instance). The HMAC passes because it is validated against Org A's secret and Org A's secret was used to sign it; the handler then acts on Org B's stacks because `repository_name` is read independently from the same JSON body.

### Impact Explanation
This breaks the equality the engine is supposed to enforce: `organization authenticated (via HMAC secret) == organization whose repository/stack is written`. Any tenant with legitimate write access to their own org's webhook configuration can force `GithubSyncJob`-driven mutation (new/updated `Commit` rows, forced resync, and potentially satisfying `continuous_deployment` triggers if the attacker also knows/guesses the victim's real HEAD SHA) against an arbitrary victim stack they have no authorization over on the same multi-tenant instance — an unauthenticated cross-tenant write/trigger on another organization's stack state, matching the High-severity "unauthenticated read of stack state" / cross-repository-write class explicitly in scope.

### Likelihood Explanation
Requires only being a legitimate operator of any single organization/repository already configured in the shared Shipit instance (i.e., knowledge of one's own webhook secret, which every onboarded tenant necessarily has) — no privileged Shipit account, `ApiClient` token, or victim credentials are needed. The only extra requirement to trigger an actual state write (versus a harmless resync) is knowing the victim repo's branch name and, for auto-deploy effects, its current HEAD SHA, both of which are typically public on GitHub.

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler`), enforce that `repository.full_name`'s owner exactly matches `repository_owner`/the organization whose secret validated the signature before any handler is invoked; reject the request otherwise.

### Proof of Concept
1. Attacker is an admin of `OrgA/some-repo`, onboarded in the shared Shipit instance, and therefore knows `OrgA`'s webhook secret (`webhook_secret` configured for that org, per `lib/shipit/github_app.rb`).
2. Attacker crafts a `push` payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<victim-real-head-sha>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(OrgA_secret, raw_body)` and POSTs to `/github/webhooks`.
4. `verify_signature` looks up `Shipit.github(organization: "OrgA")` and validates the signature successfully [1](#0-0) .
5. `PushHandler` resolves stacks via `Repository.from_github_repo_name("OrgB/victim-repo")` [2](#0-1)  and calls `stack.sync_github(expected_head_sha: "<victim-real-head-sha>")` on Org B's stack [8](#0-7) , an org the attacker never authenticated against.

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
