### Title
Cross-tenant `Status` write via unscoped SHA lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` only authenticates that a webhook payload was signed by the GitHub org identified via `repository_owner` (`payload.dig('repository','owner','login')`), it never confirms that the payload's `repository.full_name` matches the `Commit` rows that get mutated. `StatusHandler#process` looks up commits by bare `sha` across the entire `commits` table and writes a `Status`, bypassing the `stacks` scoping (`Repository.from_github_repo_name(repository_name)&.stacks`) that sibling handlers (`PushHandler`, `CheckSuiteHandler`) correctly use.

### Finding Description
The claimed binding is: `repository verified by webhook_secret (payload.repository.full_name / repository_owner)` == `repository whose Commit#stack receives the Status write`.

Trace:
1. `WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-49) resolves `Shipit.github(organization: repository_owner)` and calls `verify_webhook_signature(signature, raw_post)`. This only proves the request was signed with **that organization's** `webhook_secret` — it says nothing about which specific repository/stack the payload's `sha` belongs to. Any repository owner in the org (or, per the identical per-repo `GithubHook#secret` model, any repo owner who controls their own hook secret) can produce a validly-signed `status` event for a payload whose `repository.full_name` is their own repo.
2. `WebhooksController#create` dispatches to `Shipit::Webhooks.for_event(event)` handlers, passing the full parsed JSON `params` (app/controllers/shipit/webhooks_controller.rb:10-15).
3. `StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24):
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This queries `Commit` **globally by `sha`**, with no `stack_id`/`repository` filter, and never calls the base class's `stacks` helper (`Handler#stacks`, app/models/shipit/webhooks/handlers/handler.rb:32-34) which is derived from `payload.dig('repository','full_name')`.
4. Contrast with `PushHandler#process` (`stacks.not_archived.where(branch:)...`) and `CheckSuiteHandler#process` (`stacks.where(branch: ...).each { |stack| stack.commits.where(sha: ...) }`), both of which correctly scope commit/stack lookups through `stacks`, i.e., through the attacker's own verified `repository.full_name`. `StatusHandler` is the outlier that omits this scoping.
5. `Commit#create_status_from_github!` → `statuses.replicate_from_github!(stack_id, github_status)` (app/models/shipit/commit.rb:165-169, app/models/shipit/status.rb:24-33) creates a `Status` row bound to `commit.stack_id` — the **victim's** stack, not the attacker's.

Exploit: an attacker who owns/controls a GitHub repo (and its GitHub App installation's `webhook_secret`, or per-repo `GithubHook` secret) crafts a `status` event whose `repository.full_name` is their own repo, but whose `sha` equals a SHA that also exists in a victim's `Stack` (e.g., the git empty-tree SHA `4b825dc642cb6eb9a060e54bf8d69288fbee4904`, or any SHA reused across repos/forks). The signature check passes because it validates against the attacker's own org/secret, not against the specific commit/stack being written. `StatusHandler#process` then finds every `Commit` in the DB with that SHA — including the victim's — and writes a `success`/`failure` `Status` onto it.

Existing guards do not stop this: `verify_signature` only checks org-level signature validity, `ExplicitParameters` schema only validates payload shape (`sha`, `state`, etc.), and no model validation ties `Status#stack_id` back to the requesting repository.

### Impact Explanation
A payload authenticated for the attacker's own repository is used to write a `Shipit::Status` row against a `Commit` belonging to a **different Stack/Repository** — an unauthenticated cross-tenant DB mutation. This can flip a victim commit's CI status to `success`, which (per `Status`/`Commit` callbacks such as `schedule_continuous_delivery`, `enable_ci_on_stack`) can influence merge/deploy eligibility logic (e.g., `ProcessMergeRequestsJob` enqueued on transitions to `success`/`pending`, per `test/models/commits_test.rb` webhook-transition tests) for a stack the attacker does not control. This matches the Critical category: "a payload for one repository mutating another's stack/commit/task/team." It is repeatable against any known/shared SHA (empty-tree commit, common base commits, or any SHA the attacker can predict/observe) and against arbitrary victim stacks that happen to contain a matching SHA.

### Likelihood Explanation
Preconditions: attacker needs a repository (or org) with a valid GitHub webhook configured to Shipit (any onboarded repo/org qualifies — this is the normal, low-privilege state for anyone who can add a Shipit-tracked repo/webhook to their own GitHub org), and knowledge of a SHA present in the victim stack (trivially true for the well-known empty-tree SHA, or discoverable via public commit history/forks). No Shipit session, API token, or elevated GitHub permission is required — only the ability to trigger (or directly POST, since GitHub webhook payloads are not encrypted beyond HMAC signature, which the attacker can compute themselves with their own secret) a `status` webhook for their own repo. This is cheap, scriptable, and repeatable against any victim stack sharing a SHA with the attacker's repo.

### Recommendation
Scope `StatusHandler#process` through `stacks` like `PushHandler`/`CheckSuiteHandler`, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This ensures the `Status` write only applies to commits belonging to stacks whose `Repository` matches the payload's authenticated `repository.full_name`.

### Proof of Concept
Minitest plan (controller integration test, extending `test/controllers/webhooks_controller_test.rb` patterns):
```ruby
test ":status cross-repo sha collision writes Status onto a different stack's commit" do
  request.headers['X-Github-Event'] = 'status'

  victim_commit = shipit_commits(:first) # belongs to shipit stack/repository
  shared_sha = '4b825dc642cb6eb9a060e54bf8d69288fbee4904'
  victim_commit.update!(sha: shared_sha)

  attacker_repository_params = {
    'repository' => { 'full_name' => 'attacker-org/attacker-repo', 'owner' => { 'login' => 'shopify' } } # same org as verified webhook_secret, different repo
  }

  body = {
    'sha' => shared_sha, 'state' => 'success',
    'branches' => [{ 'name' => 'master' }]
  }.merge(attacker_repository_params).to_json

  # Binding check BEFORE:
  assert_equal 'attacker-org/attacker-repo', JSON.parse(body).dig('repository', 'full_name')
  refute_equal 'attacker-org/attacker-repo', victim_commit.stack.repository.full_name

  assert_difference 'victim_commit.statuses.count', 1 do
    post :create, body:, as: :json
  end

  # Binding check AFTER: Status was written to victim's stack despite attacker-owned repository.full_name in payload
  status = victim_commit.statuses.last
  assert_equal victim_commit.stack_id, status.stack_id
  refute_equal 'attacker-org/attacker-repo', victim_commit.stack.repository.full_name
end
```
