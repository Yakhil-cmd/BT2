### Title
Tokens transferred directly to Controller are permanently unrecoverable - (File: contracts/controller/src/lib.rs)

### Summary
Medium. The Controller can hold arbitrary token balances, but its withdrawal entrypoint only releases pool-backed supply positions and neither the public nor admin API provides a generic token recovery path. [1](#0-0) [2](#0-1) 

### Finding Description
A user can transfer any Soroban token directly to `env.current_contract_address()` through the token contract without invoking a Controller entrypoint. 

The public `withdraw(caller, account_id, withdrawals, to)` path loads an existing account, requires owner or delegate authorization, and ultimately requires an existing supply position for the requested `HubAssetKey`; it does not permit withdrawal of unattributed token balances held by the contract. [3](#0-2) [4](#0-3) 

Other custody paths deliberately preserve pre-existing balances: `claim_revenue` snapshots the Controller balance and forwards only the positive delta received from the pool, while refund helpers similarly exclude balances present before an operation. [5](#0-4) [6](#0-5) 

The exposed `ControllerAdmin` implementation contains registry, deployment, configuration, pause, and upgrade functions, but no rescue or sweep function accepting a token and recipient. [2](#0-1) [7](#0-6) 

### Impact Explanation
Tokens sent to the Controller by mistake receive no supply shares, debt credit, revenue attribution, or retrievable balance delta. Because no execution path can transfer that pre-existing balance to its sender or another recipient, the funds remain permanently frozen absent a privileged contract upgrade. [6](#0-5) [8](#0-7) 

### Likelihood Explanation
The condition is reachable by a single unprivileged token-contract `transfer(user, controller, amount)` call and requires no special protocol state, attacker action, oracle behavior, or contract authorization. 

The impact is limited to the mistakenly transferred amount rather than affecting existing user positions, making this a Medium permanent-freezing issue. [9](#0-8) 

### Recommendation
Add an owner- or governance-authorized recovery entrypoint that transfers an explicit token amount from the Controller to a recipient, or otherwise document and test that direct contract transfers are donations. The recovery path should operate on the token balance directly rather than pool cash or account positions. [2](#0-1) 

### Proof of Concept
```rust
// `controller` is the deployed Controller address.
let token = token::Client::new(&env, &asset);
token.transfer(&user, &controller, &1_000);

assert_eq!(token.balance(&controller), 1_000);
```

Calling `controller.withdraw(user, account_id, vec![(hub_asset, 1_000)], Some(user))` cannot recover this balance because withdrawal requires an existing account supply position rather than arbitrary contract balance. [10](#0-9) [4](#0-3) 

Calling `controller.claim_revenue(user, vec![hub_asset])` also leaves the pre-existing `1_000` untouched because it snapshots the Controller balance before the pool call and transfers only the measured increase to the accumulator. [5](#0-4) 

No exposed Controller or `ControllerAdmin` entrypoint can subsequently move the stranded token balance. [11](#0-10) [12](#0-11)

/// Refunds only the controller balance increase since `balance_before`,
/// preserving the pre-existing balance; no-op for a nonpositive delta.
pub(crate) fn refund_controller_balance_delta(
    env: &Env,
    asset: &Address,
    balance_before: i128,
    refund_to: &Address,
) {
    let controller = env.current_contract_address();
    let excess = balance_delta_since(env, asset, &controller, balance_before);
    if excess > 0 {
        token::Client::new(env, asset).transfer(&controller, refund_to, &excess);
    }
