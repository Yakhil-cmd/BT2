### Title
AA state variables have no snapshot/locking mechanism, allowing a state-var owner to front-run a later "distribution" trigger and steal funds - (File: formula/evaluation.js, aa_composer.js)

### Summary
The Sherlock report describes an RFP strategy contract where a value (`proposalBid`) set by the recipient during registration is read again, unlocked, at `distribute()` time; the recipient front-runs the distribute call to change the bid and receive more funds than allocated. The equivalent construct in ocore is an Autonomous Agent (AA) built on the built-in `var[]` state-variable store: `state_var_assignment`/`var[]` reads always return the *current* value at the time a message/formula executes [1](#0-0) , with no primitive to pin/lock a value that was recorded during an earlier phase (e.g., "bid submission") for use unmodified during a later phase (e.g., "payout"). Any AA implementing a multi-phase bid → allocate → distribute pattern with a per-address state var is therefore reachable by the same front-run: the address that owns the var posts a new trigger to overwrite its own `var[address]['bid']` (or similar) immediately before another trigger causes the AA to read that var and pay out based on it.

### Finding Description
AA state is a simple key-value store (`stateVars[address][var_name]`) that is read and written with plain formula ops:
- `state_var_assignment` overwrites `stateVars[address][var_name].value` unconditionally, with no versioning, no "finalize" or "freeze" primitive, and no linkage to a prior computation step [2](#0-1) .
- `var[...]` reads (via `readVar`) always fetch the latest committed value for that key, either from an in-memory `stateVars` snapshot in the current trigger chain or from the persisted `aa_addresses`/state-var storage — there is no way for an AA to say "use the value of this var as it was N units ago" or to lock a var after it has been "consumed" once.
- `saveStateVars()` in `aa_composer.js` persists whichever state was last set at the moment the response unit is built, again with no historical record retained beyond `old_value`/`original_old_value`, which exist only to support `+=`/`-=` semantics within a single trigger chain, not cross-trigger auditing [3](#0-2) .

This means any AA author who implements a workflow analogous to RFPSimpleStrategy — e.g. "user registers a bid by setting `var[user]['bid']=X`", "operator triggers an `allocate` step that computes expected payout from `var[user]['bid']`", "later, a `distribute` trigger re-reads `var[user]['bid']` to actually pay it out" — is exposed to exactly the same race: because units are processed by MC order and any address can post a new trigger to the AA at any time before the "distribute" trigger becomes final, the address controlling the var can post an update to raise its own recorded bid immediately before the distribute trigger, and the AA distribute logic (reading the *live* value of `var[user]['bid']`) will compute the payout using the manipulated value rather than the one used at allocation time. Because ocore uses a DAG (not a strict FIFO mempool), the "front-running" primitive is even easier than on Ethereum: the attacker only needs their update-bid unit to be selected as a parent (or otherwise causally precede) the distribute trigger unit — something they fully control since it's their own address doing the update.

### Impact Explanation
An AA implementing this common multi-step pattern (registration → allocation snapshot → later payout) can be manipulated by the party controlling the state var to receive more funds from the AA's balance than the allocation step intended, i.e., unauthorized draining of AA-held funds analogous to the Allo "recipients receive more funds than initially expected" impact. This is a genuine fund-loss/fund-theft primitive reachable purely through posting standard trigger units — no privileged or operator role required, satisfying "AA fund loss" impact criteria.

### Likelihood Explanation
Likelihood depends on the specific AA's design: it materializes whenever an AA (a) stores a value keyed by an untrusted address, (b) uses that value in one trigger to compute an allocation/commitment, and (c) re-reads the *same, mutable* var in a subsequent trigger to determine an actual payout, without snapshotting the value into an immutable record (e.g. a separately-keyed `var['locked_bid_'+txid]`) at allocation time. Because ocore/oscript provides no built-in "freeze" or optimistic-locking primitive for state vars, and per-address state vars are trivially updatable by their owning address at any time via a new trigger, this is a straightforward and repeatable exploit for any AA that follows this common pattern, making it Medium-to-High likelihood for the class of AAs that implement multi-phase, value-locking business logic (auctions, RFPs, bonding, escrow-with-late-adjustable-bid patterns) unless the AA developer manually guards against it.

### Recommendation
- Document the risk in the oscript/AA authoring guidelines: whenever an AA design requires "lock a submitted value at time T for use at time T+1", instruct authors to copy the value into an immutable/append-only key (e.g. keyed by the triggering unit hash) at the moment of allocation, rather than re-reading the live, mutable `var[address][...]`.
- Consider adding a first-class "freeze"/"snapshot" oscript primitive (e.g., a `lock_var` op that copies a var into a write-once key) so AA authors have a supported way to avoid re-reading mutable state across phases.
- For any officially bundled/reference AA templates (auctions, RFP-like flows, bonding curves) that follow bid → allocate → distribute patterns, explicitly snapshot bid/allocation state into a unique, non-overwritable var at the allocation step, and have the distribute step consume only that snapshotted value.

### Proof of Concept
Conceptual reproduction (equivalent to the reported Solidity PoC), using ocore's `var[]` semantics:
1. AA `registerBid`: on trigger from `user`, sets `var[user]['bid'] = trigger.data.bid`.
2. AA `allocate` (triggered by an operator/paired address): reads `var[user]['bid']`, computes `var[user]['allocated_bid'] = var[user]['bid']` is *not* performed (or the AA design mistakenly re-reads `bid` directly at distribute time instead of `allocated_bid`), and instead records only that allocation happened, e.g. `var['allocated'] = 1`.
3. Attacker (the `user` address) waits until the pool is funded, then immediately before triggering `distribute`, sends another trigger to `registerBid` with a higher `bid` value — since `state_var_assignment` unconditionally overwrites `stateVars[address][var_name].value` [4](#0-3) , the stored `var[user]['bid']` is now the attacker-controlled higher value.
4. Attacker triggers `distribute`; the AA logic reads the *current* `var[user]['bid']` (as any AA reading a live var must, per the read semantics in `formula/evaluation.js`) and pays out based on the manipulated value, exceeding what was computed/expected during the `allocate` step — resulting in the AA over-paying the attacker from pooled/shared funds.

This cannot be exhaustively demonstrated against a specific bundled AA in this codebase (no reference RFP/auction AA template was found in the indexed files), so the PoC is a structural walkthrough of the underlying primitive (`state_var_assignment` overwrite + live `var[]` read) that reproduces the same race condition described in the original report, rather than a concrete exploit against a named existing AA contract.
