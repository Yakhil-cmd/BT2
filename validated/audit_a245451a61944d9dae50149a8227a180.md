Found it: `MembershipHandler#process` in `app/models/shipit/webhooks/handlers/membership_handler.rb` binds `Team` lookup to the GitHub-supplied `team.id`, but the `organization.login` field that determines which `Shipit::GithubHook::Organization` webhook secret verified the payload is only used opportunistically on team creation and is never re-validated against the team that is actually mutated on every subsequent delivery.

### Title
Membership webhook trusts payload-controlled `organization.login` for authorization scope after initial team creation, allowing cross-organization team membership tampering - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to verify the HMAC signature against by reading `repository.owner.login` or, when absent (as with `membership` events, which have no `repository` key), `organization.login` straight out of the untrusted JSON body: [1](#0-0) 
That `organization.login` field is exactly the field `MembershipHandler` later trusts to scope the mutation to a `Team`: [2](#0-1) 
The binding the app relies on is: "the organization whose secret verified this signature" == "the organization whose team membership is being mutated." On the very first delivery for a given `team.id` this holds, because `find_or_create_team!` stores `params.organization.login` into the new `Team#organization`. But on every subsequent delivery for that same `team.id`, `find_or_create_team!` finds the already-persisted `Team` by `github_id` alone and does not verify that `params.organization.login` still matches `team.organization`: [3](#0-2) 

### Finding Description
Once a `Team` exists in Shipit for `github_id = X` (created from a legitimate `membership` webhook from org A), any subsequent webhook whose signature is *valid* (i.e., correctly signed with org A's `webhook_secret`, since `Shipit.github(organization: repository_owner)` is selected using the attacker-supplied `organization.login` field) but which claims a *different* `team.id` value than what actually belongs to org A can still be processed. Conversely, and more importantly, `find_or_create_team!` keys exclusively off `params.team.id` (an attacker/organization-controlled integer field inside the JSON body), with no cross-check that the numeric `team.id` in the payload actually belongs to the organization whose secret validated the request. Because GitHub team IDs are globally unique but the code never confirms `team.id ∈ organization.login`'s teams, a party who controls (or has been granted, e.g., as an app installer) a webhook subscription for organization B can send a `membership` event referencing a `team.id` that was originally created under organization A (`Team#organization == "orgA"`), and `MembershipHandler#process` will look it up via `Team.find_or_create_by!(github_id: params.team.id)`, find the existing org-A team, and call `team.add_member(member)` / `team.members.delete(member)` on it — regardless of the fact that the payload's `organization.login` is `"orgB"`.

Because `Shipit.github_teams` (used by `User#authorized?` in `app/controllers/concerns/shipit/authentication.rb` and `app/models/shipit/user.rb`) grants or revokes application-wide access based on `Team#members`, this lets a party controlling only org B's legitimately-configured webhook (not org A's, and without needing org A's `webhook_secret`) add or remove members of an org-A-owned `Shipit::Team` that gates login authorization: [4](#0-3) , [5](#0-4) .

### Impact Explanation
This breaks the binding "organization whose signature verified the request" == "organization whose team is being mutated," letting a GitHub organization admin/App installer for an unrelated, less-trusted org B escalate a collaborator into `Shipit.github_teams`, granting them full authenticated access to the Shipit UI/API for stacks belonging to org A's repositories (deploys, rollbacks, merges, API client management). This matches the High-impact category "escalation into `Shipit.github_teams` authorization."

### Likelihood Explanation
Requires the attacker to control (or compromise) a `membership` webhook delivery for *any* organization configured in Shipit (not necessarily the target org), and to know or guess the numeric GitHub `team.id` of the target org's team — team IDs are visible via the GitHub API/UI to team members, so this is plausible in multi-org Shipit deployments. This is a realistic but not trivial-to-discover analog of the reserve-deactivation bug: a value that is checked against the *wrong* identifier (`repository.owner`/`organization.login` used only for signature routing, not for authorizing the actual mutated `Team.organization`).

### Recommendation
In `MembershipHandler#find_or_create_team!`, verify that the found/created `Team#organization` matches `params.organization.login` on every delivery, not just at creation time, and reject (or log/ignore) the event otherwise:
```ruby
def find_or_create_team!
  team = Team.find_or_create_by!(github_id: params.team.id) do |t|
    t.github_team = params.team
    t.organization = params.organization.login
  end
  raise ArgumentError, "organization mismatch" unless team.organization.casecmp?(params.organization.login)
  team
end
```

### Proof of Concept
1. Shipit is configured with two GitHub Apps/orgs, `org-a` and `org-b`, each with its own `webhook_secret`, both installed and both delivering `membership` events (a normal multi-org Shipit setup, per `docs/setup.md`).
2. `org-a` has a `Shipit::Team` (`github_id: 100`, `organization: "org-a"`) that is included in `Shipit.github_teams`, gating application access.
3. An attacker who is an org-b organization owner (privileged only within org-b, not org-a) crafts/sends (or has GitHub send, by manipulating org-b's team memberships if `team.id` collisions are engineered, or more directly if org-b is compromised) a `membership` webhook signed with org-b's `webhook_secret`, with body:
   ```json
   { "action": "added", "team": {"id": 100, "name": "...", "slug": "...", "url": "..."},
     "organization": {"login": "org-b"}, "member": {"login": "attacker"} }
   ```
4. `WebhooksController#verify_signature` selects `Shipit.github(organization: "org-b")` and validates the signature successfully (it is genuinely signed by org-b).
5. `MembershipHandler#process` calls `find_or_create_team!`, which finds the existing `Team` with `github_id: 100` (org-a's team) and calls `team.add_member(User.find_or_create_by_login!("attacker"))`, granting `attacker` membership in org-a's gating team without ever needing org-a's `webhook_secret` or any org-a privileges.
