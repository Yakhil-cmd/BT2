Confirmed: `StatusHandler#process` performs a global, unscoped lookup and applies to every matching commit regardless of which repository sent the webhook, unlike every other handler that scopes through `Handler#stacks` (keyed on `payload.repository.full_name`).### Title
Cross-tenant Status write via unscoped `Commit.where(sha:)` in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
Every other webhook handler resolves records through `Handler#stacks`, which scopes lookups to `Repository.from_github_repo_name(payload.repository.full_name)` before touching any `Stack`/`Commit`. `StatusHandler#process` breaks this contract: it queries `Commit.where(sha: params.sha)` globally and calls `create_status_from_github!` on every match, regardless of which repository's webhook delivered the payload. If the same sha exists as a `Commit` in two differently-owned stacks, a status event delivered under one repository's context writes a `Status` (and triggers side effects) on the other repository's commit too.

### Finding Description
The binding every handler is expected to uphold is: `repository_full_name in payload == repository of every record touched`. `Handler#stacks` enforces this: [1](#0-0) . `PushHandler#process` consumes it faithfully, only mutating stacks under `Repository.from_github_repo_name(repository_name)`: [2](#0-1) . `CheckSuiteHandler` likewise scopes through `stacks.where(branch: ...)` before touching commits: [3](#0-2) . All `PullRequest::*` handlers resolve `repository = Shipit::Repository.from_github_repo_name(params.repository.full_name)` before acting: [4](#0-3) .

`StatusHandler#process`, in contrast, never calls `stacks`, never resolves `repository_name`, and never references `payload.repository` at all — its `params` schema doesn't even declare a `repository` field: [5](#0-4) . It matches purely on `sha` across the entire `Commit` table and mutates every match: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [6](#0-5) .

`create_status_from_github!` writes a `Status` scoped to `commit.stack_id` (the *victim's* stack, not the caller's) and can trigger downstream effects: `enable_ci_on_stack`, `schedule_continuous_delivery`, and (via `Commit#add_status`) `Hook.emit(:deployable_status, ...)` and `stack.schedule_merges` when the new status is `pending`/`success`: [7](#0-6) [8](#0-7) [9](#0-8) .

**Path**: `POST /webhooks` with `X-Github-Event: status` → `WebhooksController#create` dispatches to `Shipit::Webhooks.for_event('status')` = `[Handlers::StatusHandler]` [10](#0-9)  → `StatusHandler.call(params)` → `process` mutates commits by sha with no repository filter.

**Why guards don't stop this**: `verify_signature` only authenticates that the payload was legitimately signed by *some* configured GitHub org, keyed off `payload.dig('repository','owner','login')` [11](#0-10) . It says nothing about which *stack* the payload is allowed to affect — that authorization is left entirely to each handler's own scoping logic, which `StatusHandler` omits. The `ExplicitParameters` schema for `StatusHandler` doesn't require `repository` at all, so there's no schema-level enforcement either.

**Attacker action**: control a legitimate GitHub repository whose webhook is registered with this Shipit instance. Trigger (or directly send, since the schema doesn't require signature-bound repository fields to correlate with the sha) a `status` event whose `sha` equals a commit sha that is also present in the target victim stack (precondition stated: same sha present in two differently-owned stacks — e.g., shared upstream history between a fork and the tracked repo). The resulting webhook is validated only against the attacker's own org's secret, yet `StatusHandler` applies the status to the victim's commit as well.

### Impact Explanation
A payload authenticated for repository A causes a `Status` write against repository B's `Commit`, changing B's commit state (e.g., to `success`), which can flip `deployable?`, emit `deployable_status`/`commit_status` hooks, and invoke `stack.schedule_merges` — potentially triggering an unauthorized deploy/merge for a stack the attacker does not own and never authenticated against. This matches the Critical category: "a payload for one repository mutating another's stack, commit, task or team" / "an unauthorized deploy, rollback or merge." Blast radius: any stack across any tenant whose tracked history shares a commit sha with an attacker-controlled repository; repeatable per shared sha, and the attacker can choose `state`, `description`, `target_url`, `context` freely in the payload.

### Likelihood Explanation
Requires: (1) attacker owns/controls a repository with an active Shipit webhook (a normal, unprivileged onboarding scenario, e.g. self-service repo registration or being a collaborator on a tracked repo), and (2) a sha collision precondition — the same real commit sha present in the victim's tracked stack, which is plausible whenever stacks track forks/mirrors of shared/open-source history. Given that precondition (explicitly assumed per the prompt), the attacker's cost is a single legitimate webhook delivery; no secrets, sessions, or elevated GitHub roles are needed. Repeatable at will.

### Recommendation
Scope `StatusHandler#process` the same way as `PushHandler`/`CheckSuiteHandler`: require `repository.full_name` in the params schema, resolve `stacks` via `Handler#stacks`, and restrict the `Commit` lookup to `stacks.joins(:commits).where(shipit_commits: { sha: params.sha })` (or equivalent) so only commits belonging to stacks under the requesting repository are updated.

```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossTenantTest < ActiveSupport::TestCase
        test "status webhook for repo A must not mutate commits belonging to repo B's stack" do
          shared_sha = "cafef00dcafef00dcafef00dcafef00dcafef00"

          repo_a = Shipit::Repository.create!(owner: "owner-a", name: "repo-a")
          stack_a = Shipit::Stack.create!(repository: repo_a, branch: "master", environment: "production")
          commit_a = stack_a.commits.create!(sha: shared_sha, author: shipit_users(:walrus),
                                              committer: shipit_users(:walrus),
                                              authored_at: Time.now, committed_at: Time.now,
                                              message: "shared commit")

          repo_b = Shipit::Repository.create!(owner: "owner-b", name: "repo-b")
          stack_b = Shipit::Stack.create!(repository: repo_b, branch: "master", environment: "production")
          commit_b = stack_b.commits.create!(sha: shared_sha, author: shipit_users(:walrus),
                                              committer: shipit_users(:walrus),
                                              authored_at: Time.now, committed_at: Time.now,
                                              message: "shared commit")

          payload = {
            "sha" => shared_sha,
            "state" => "success",
            "context" => "attacker/ci",
            "repository" => { "full_name" => "owner-a/repo-a" } # attacker only authenticates for repo-a
          }

          assert_difference -> { commit_b.statuses.count }, 0,
            "StatusHandler must not create a Status for a commit owned by an unrelated repository" do
            StatusHandler.new(payload).process
          end

          assert_difference -> { commit_a.statuses.count }, 1 do
            # (documents current unscoped behavior actually also touches commit_a legitimately)
          end
        end
      end
    end
  end
end
```
The first assertion (`commit_b.statuses.count` unchanged) is the equality check: `repository_full_name in payload ("owner-a/repo-a") == repository of every record touched`. Under current code, `Commit.where(sha: shared_sha)` matches both `commit_a` and `commit_b`, so `commit_b.statuses.count` increases by 1, failing the assertion and proving the cross-tenant write.

```ruby
module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
```

```ruby
    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
```
