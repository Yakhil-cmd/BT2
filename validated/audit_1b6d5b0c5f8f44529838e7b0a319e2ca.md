### Title
Membership webhook accepts organization-agnostic `team.id`, letting an attacker who controls any configured GitHub org add arbitrary users to a privileged `Shipit.github_teams` team - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::MembershipHandler` mutates team membership using only the numeric `team.id` from the webhook payload, without ever checking that the `team.id` actually belongs to the `organization.login` whose secret was used to validate the request signature. The webhook signature only proves the request came from *some* organization Shipit is configured for, not that the specific team being modified belongs to that organization.

### Finding Description
`WebhooksController#verify_signature` picks the HMAC secret to validate the request against using an *unverified* field taken straight out of the JSON body: `repository_owner` (`params.dig('repository','owner','login') || params.dig('organization','login')`), then calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`. [1](#0-0) 

For `membership` events there is no `repository` key, so `repository_owner` resolves to `organization.login` — the very same field the handler later trusts as the authoritative organization for the team being modified.

`MembershipHandler#process` looks up (or creates) a `Team` purely by the numeric GitHub `team.id`, then adds/removes the named member: [2](#0-1) 

If a `Team` row with that `github_id` already exists (e.g. created previously by `Team.find_or_create_by_handle` for the legitimate `Shipit.github_teams` configuration), `find_or_create_by!` returns the existing record and the initialization block (which sets `team.organization`) never runs — `team.organization` is left as whatever org actually owns that team. Nothing in `process` ever compares `params.organization.login` to `team.organization`.

The equality that should hold but doesn't:
`organization whose webhook_secret authenticated the request == organization that owns the `Team` row being mutated`

Because signature verification is scoped per-organization (`config/secrets.yml` supports multiple `github: <org>: webhook_secret: ...` entries) and `Shipit.github(organization: ...)` is looked up by the very same untrusted `organization.login`/`team.id` field, an attacker who is a legitimate admin of **any** GitHub organization onboarded to this Shipit instance (and therefore legitimately knows that organization's own `webhook_secret`) can sign a `membership` webhook themselves, claiming `organization.login` = their own org, but embed a `team.id` that in fact belongs to a completely different, privileged organization's team (e.g., one of the teams listed in `Shipit.github_teams`, which gates all UI access via `User#authorized?`): [3](#0-2) [4](#0-3) [5](#0-4) 

### Impact Explanation
This is a direct escalation into `Shipit.github_teams` authorization, one of the explicitly listed High-severity impacts. `User#authorized?` is the sole gate deciding whether a logged-in GitHub user may use the Shipit UI/API at all — it checks membership in `Team` rows referenced by `Shipit.github_teams`. By forging a `membership` "added" event that references the numeric `github_id` of one of those authorized teams, an attacker can grant themselves (or any GitHub login they choose) membership in that `Team` record, bypassing the intended org-team authorization boundary entirely — all while only ever proving control of a wholly unrelated, unprivileged GitHub organization.

### Likelihood Explanation
The attack requires: (1) the target Shipit instance being configured for more than one GitHub organization (a documented, supported configuration — `config/secrets.development.shopify.yml` shows exactly this multi-org layout), (2) the attacker controlling (or being a GitHub App admin/owner for) at least one of those onboarded, lower-trust organizations so they legitimately know its `webhook_secret`, and (3) knowledge/discovery of the target team's numeric GitHub `id` (teams' numeric IDs are visible via the GitHub API to team/org members and are otherwise guessable/enumerable, and would appear in server logs of legitimate `membership` deliveries). None of this requires a Shipit session, `ApiClient` token, or GitHub App private key. Given webhook secrets are commonly known by multiple people administering an org's GitHub App settings, this is realistically exploitable wherever multi-org Shipit deployments exist.

### Recommendation
In `MembershipHandler#find_or_create_team!` / `process`, verify that the `Team` record resolved by `github_id` has `organization == params.organization.login` (case-insensitively) before performing any membership mutation; reject/ignore the event otherwise. More generally, `WebhooksController#verify_signature` should not let payload-supplied `organization`/`repository.owner` fields silently select which secret validates the request; every handler that trusts an "organization" or "repository" field from the payload should re-derive and cross-check it against data already bound to the resource being modified (`Team#organization`, `Repository#owner`), rather than trusting the raw payload field.

### Proof of Concept
1. Shipit is configured (per documented multi-org support) with two orgs, e.g. `victim-org` (privileged, one of whose teams `T` is listed in `Shipit.github_teams`, `github_id = 12345`) and `attacker-org` (attacker is a GitHub App admin there, so they know `attacker-org`'s `webhook_secret`).
2. Team `T` (github_id `12345`, organization `victim-org`) already exists in Shipit's DB (created by `rake teams:fetch` / `Team.find_or_create_by_handle`).
3. Attacker crafts a `membership` webhook JSON body:
```json
{
  "action": "added",
  "team": {"id": 12345, "name": "Any Name", "slug": "any-slug", "url": "https://api.github.com/teams/12345"},
  "organization": {"login": "attacker-org"},
  "member": {"login": "attacker-github-login"}
}
```
4. Attacker computes `sha1=HMAC-SHA1(attacker-org's webhook_secret, raw_body)` and sends it as `X-Hub-Signature`, with `X-Github-Event: membership`, to `POST /webhooks`.
5. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` (matching the signature) and passes.
6. `MembershipHandler#process` finds the existing `Team` with `github_id == 12345` (which is `victim-org`'s privileged team, unrelated to `attacker-org`) and calls `team.add_member(member)`, adding `attacker-github-login` to it.
7. `attacker-github-login` now satisfies `User#authorized?` and can log into/use the Shipit instance despite never having any relationship to `victim-org`.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([

        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
      end
    end
  end
end
