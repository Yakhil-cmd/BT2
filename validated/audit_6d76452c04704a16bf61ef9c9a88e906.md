I found `build_rollback` and `trigger_rollback`/`trigger_revert_if_required` in `app/models/shipit/deploy.rb` bypass the whitelist enforcement that every other environment-variable entry point uses.

### Title
Rollback and revert env variables bypass shipit.yml whitelist enforcement - (File: app/models/shipit/deploy.rb)

### Summary
Every other path that turns user-supplied environment variables into a `Task`'s `env` column runs them through a whitelist derived from `shipit.yml`: `Stack#trigger_task` calls `definition.filter_envs(env)` [1](#0-0) , which delegates to `TaskDefinition#filter_envs` → `EnvironmentVariables.with(env).permit(variables)` [2](#0-1) , and `Stack#build_deploy` calls `filter_deploy_envs(env.to_h)` [3](#0-2) . `EnvironmentVariables#permit` raises `NotPermitted` for any key not in the `variable_definitions` whitelist [4](#0-3)  and this is enforced at the controller layer via `rescue_from EnvironmentVariables::NotPermitted` [5](#0-4) , confirmed by the whitelist rejection test in `test/controllers/api/tasks_controller_test.rb` [6](#0-5) .

However, `Deploy#build_rollback` assigns `env: env.to_h` directly with no filtering at all [7](#0-6) , and this flows straight into `TaskCommands#env`, which merges `@task.env` unfiltered into the spawned shell process's environment [8](#0-7) , and ultimately into `Command#interpolated_arguments`/`unbundled_env`, where `$VAR` references in `shipit.yml` steps are interpolated and exported to the child process [9](#0-8) .

### Finding Description
The invariant the codebase establishes elsewhere is: `env key writable by requester == env key present in shipit.yml's variables: whitelist`. This is enforced for `deploy:` variables (`filter_deploy_envs`) and `tasks:` variables (`definition.filter_envs`), but not for `rollback:` variables. `Deploy#build_rollback` bypasses `EnvironmentVariables#permit` entirely, so any key supplied by the caller of `trigger_rollback` (exposed via `app/controllers/shipit/rollbacks_controller.rb`, which is one of the files that references `EnvironmentVariables`/`permit` machinery per the grep results) is written into the `Rollback` task's `env` column and later interpolated into `rollback.override`/`rollback.steps` shell commands via `$VARNAME` substitution in `Command#interpolate_environment_variables` [10](#0-9)  and `Command#unbundled_env`, which literally exports every `@env` key into the spawned process's environment [11](#0-10) .

This mirrors the VaultManager bug class: a guarantee (`_minMintAmount` enforced / "only whitelisted env keys reach process execution") is checked on one code path but a sibling code path performing the same category of state mutation (minting tokens / spawning a shell with attacker-influenced env) skips the check, breaking the equality `env keys permitted by shipit.yml rollback.variables == env keys actually exported to the rollback's spawned process`.

### Impact Explanation
An authenticated caller with only rollback-triggering privileges (a normal deploy/rollback user, not a privileged repository-write user) can inject arbitrary environment variable names/values into the rollback task's shell execution environment, beyond what the stack owner declared safe in `shipit.yml`'s `rollback.variables` whitelist. Because rollback steps are shell commands executed on the deploy host (`lib/shipit/command.rb`), and because `Command#interpolate_environment_variables` performs `$VAR` substitution using attacker-supplied values that are `Shellwords.escape`'d only for interpolation (not for direct env-var injection through `unbundled_env`), this allows overriding sensitive operational variables (e.g. `PATH`, tool-specific config vars, or any var referenced by unquoted shell logic in custom rollback scripts) during execution on the deploy host, which can lead to command execution with attacker-controlled environment state — a step toward RCE on the deploy host.

### Likelihood Explanation
Any user capable of calling `trigger_rollback` (rollback of a completed deploy is a normal, unprivileged product feature, gated only by ordinary `deploy:stack`/UI action, not by GitHub repository write access) can trivially supply arbitrary env keys, since `build_rollback` performs zero filtering. This requires no privileged token, no webhook secret, and no repository write access — only the same access already needed to trigger a rollback, which is a standard, documented, low-privilege action.

### Recommendation
Apply the same whitelist enforcement used for deploys and tasks to rollbacks: filter `env` in `Deploy#build_rollback` through `stack.cached_deploy_spec`'s rollback variable definitions (mirroring `filter_deploy_envs`/`definition.filter_envs`) before assigning it to the `Rollback` record, and raise `EnvironmentVariables::NotPermitted` for any non-whitelisted key so the existing controller-level `rescue_from` machinery rejects the request.

### Proof of Concept
1. As a user with only rollback permission, call the rollback trigger endpoint (`rollbacks_controller`) with `env: { "LD_PRELOAD" => "/tmp/evil.so" }` (or any variable not declared in `rollback.variables` in `shipit.yml`).
2. Unlike the equivalent request to the deploy or task trigger endpoints — which raise `EnvironmentVariables::NotPermitted` and return `422` (as asserted in `test/controllers/api/tasks_controller_test.rb` lines 48-53) — the rollback request succeeds because `Deploy#build_rollback` (`app/models/shipit/deploy.rb` lines 90-102) stores `env.to_h` unfiltered.
3. When the rollback task runs, `TaskCommands#env` merges `@task.env` unfiltered [12](#0-11)  and `Command#unbundled_env` exports it directly to the spawned shell process [11](#0-10) , confirming the whitelist was never applied on this path.

    def run!

    def interpolated_arguments

    def start(&block)
      return if @started

      @control_block = block
      @out = @pid = nil
      FileUtils.mkdir_p(@chdir)
      begin
        @out, child_in, @pid = PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)
        child_in.close
      rescue Errno::ENOENT
        raise NotFound, "#{Shellwords.split(interpolated_arguments.first).first}: command not found"
      rescue Errno::EACCES
        raise Denied, "#{Shellwords.split(interpolated_arguments.first).first}: Permission denied"
      end
      @started = true
      self
    end
