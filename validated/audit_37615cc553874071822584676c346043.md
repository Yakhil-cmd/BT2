### Title
Front-running `update_account_threshold` (or a dust `supply` top-up) strips a victim's grandfathered liquidation parameters and makes their pending `borrow`/`withdraw` revert - (File: contracts/controller/src/risk/params.rs)

### Summary
Analogous to the `startNewRound` front-run, `update_account_threshold` is permissionless (`caller.require_auth()` only) and rewrites a *foreign* account's stored risk tuple to the currently listed values. After any governance listing tightening (`edit_asset_in_spoke` lowering `liquidation_threshold`/`loan_to_value`), every pre-existing account keeps its old, more permissive stamps until refreshed. A `borrow` reads those stored stamps but never refreshes the LT/bonus/fee tuple itself, so an attacker can front-run a victim's `borrow` (or a multi-leg `withdraw`, which only restamps the legs it touches) with `update_account_threshold(caller = attacker, has_risks = true, account_ids = [victim])` and force the victim's transaction to revert on the post-action solvency check. The same restamp is reachable even cheaper via a dust `supply` top-up on an existing supply leg, which runs `refresh_supply_risk_params` with `FullTuple` through `merge_supply_leg` [1](#0-0) .

### Finding Description
Each supply position stores its own LTV/LT/bonus/fee snapshot taken at creation; `calculate_account_risk_totals` and the borrow limit read the *stored* values, not the live listing [2](#0-1) . The tuple is only refreshed on three paths: `merge_supply_leg`, `merge_withdraw_leg`, and `update_account_threshold` — never by `borrow`. `sync_account_thresholds` iterates the victim's supply legs, applies `refresh_supply_risk_params` under `RiskRefreshScope::FullTuple`, writes the updated positions with `set_supply_positions`, and only requires the final HF ≥ `THRESHOLD_UPDATE_MIN_HF_RAW` (1.05 WAD) [3](#0-2) . The gate exists to stop the keeper from pushing an account into liquidation, but nothing stops applying the adverse tuple when it merely leaves the account at HF ∈ [1.05, old-HF]. The `caller` is arbitrary: `validation::require_authorized_caller` only does `caller.require_auth()` [4](#0-3) . The declared permissionless inventory confirms any signed caller reaches this code [5](#0-4) .

Concretely: victim has stored LT 8000; governance tightens the listing to LT 7000. Victim's pre-borrow HF_old = 1.25, so HF under LT 7000 is 1.25·(7000/8000) = 1.094 ≥ 1.05 — the restamp applies and the call succeeds. The victim's pending `borrow`, sized to leave HF ≈ 1.05 under LT 8000, now computes HF ≈ 0.92 under the new stamp and reverts on the solvency check. Without the front-run it would have succeeded, because `borrow` never re-stamps the tuple.

### Impact Explanation
- Forced revert of victim `borrow`/`withdraw` transactions (the exact "adversely force calls to revert" impact class), and permanent loss of the account's grandfathered risk parameters — once restamped, the lower LT cannot be rolled back except by another listing change.
- Temporary freezing of funds: a leveraged account restamped to a lower LT may find that every `withdraw` reverts because any collateral removal pushes HF < 1 under the new threshold, until the victim repays debt or prices move. With multiple collateral legs the effect is worse, since `withdraw` only restamps the touched legs and would otherwise have kept the more permissive LT on the rest.
- In a PvP liquidation market, competing liquidators or counterparties are incentivized to pin adverse tuples onto accounts that would otherwise keep borrowing or withdrawing.

### Likelihood Explanation
Requires a real precondition — a governance listing tightening — plus a victim account whose HF clears the 1.05 post-cut floor but whose intended action does not. Both conditions arise naturally after every `edit_asset_in_spoke` that lowers LT/LTV; the whole cohort of grandfathered accounts is exposed, and the attack costs one permissionless call per victim (or a dust top-up). It cannot push anyone below HF 1.05, so it cannot manufacture liquidations — bounding this to Medium.

### Recommendation
Restrict the adverse-tuple restamp to the account owner/delegate, or make every action path (`borrow` included) apply the current listed tuple atomically so that front-running confers no differential. Alternatively, apply grandfathered params until the position is materially changed and document that `borrow` must restamp like `supply`/`withdraw` do.

### Proof of Concept
```rust
// Standard two-asset market; preset tuple LT=8000, LTV=7500, bonus=500, fee=1200.
let mut t = LendingTest::new().standard_two_asset_dust_disabled().build();
t.supply(ALICE, "USDC", 10_000.0);              // $10,000 collateral
t.borrow(ALICE, "ETH", 4.0);                    // $8,000 debt, HF = 0.8*10000/8000 = 1.0-ish; use 3.75 for HF>1.2
let alice = t.resolve_account_id(ALICE);

// Governance tightens the listing (owner path; precondition, not the attack).
t.edit_asset_config("USDC", |c| { c.liquidation_threshold = 7_000; c.loan_to_value = 6_000; });

// ATTACK: any unprivileged address front-runs ALICE's pending borrow.
t.env.mock_all_auths();
let bob = t.get_or_create_user(BOB);
t.ctrl_client().update_account_threshold(&bob, &true, &vec![&t.env, alice]);
// ALICE's stored LT is now 7000 (post-cut HF = 1.094 >= 1.05, so the gate admits it).

// ALICE's in-flight borrow sized for LT 8000 now reverts on solvency.
assert!(t.try_borrow(ALICE, "ETH", 0.4).is_err());
```

```rust
/// Allows any authenticated caller to refresh listed supply LTV snapshots.
/// `has_risks` also refreshes gated liquidation tuples and enforces health
/// factor >= 1.05. Rejects execution during a flash loan.
pub(crate) fn update_account_threshold(
    env: &Env,
    caller: Address,
    has_risks: bool,
    account_ids: Vec<u64>,
) {
    validation::require_authorized_caller(env, &caller);

    let scope = if has_risks {
        RiskRefreshScope::FullTuple
    } else {
        RiskRefreshScope::LtvOnly
    };

    let mut cache = Context::new(env);

    for account_id in account_ids {
        cache.reset_spoke_context();
        sync_account_thresholds(env, account_id, scope, &mut cache);
    }
}
```

```rust
fn sync_account_thresholds(
    env: &Env,
    account_id: u64,
    scope: RiskRefreshScope,
    cache: &mut Context,
) {
    let Some(meta) = storage::try_get_account_meta(env, account_id) else {
        return;
    };

    let supply_positions = storage::get_supply_positions(env, account_id);
    if supply_positions.is_empty() {
        return;
    }

    // Fail closed: never update an account whose NFT owner cannot be resolved.
    let Some(owner) = storage::try_account_owner(env, account_id) else {
        return;
    };

    let full_tuple = scope == RiskRefreshScope::FullTuple;
    let borrow_positions = if full_tuple {
        storage::get_debt_positions(env, account_id)
    } else {
        Map::new(env)
    };

    storage::renew_user_account(env, account_id);

    let mut account = storage::account_from_parts(owner, meta, supply_positions, borrow_positions);
    let assets = account.supply_positions.keys();

    let mut any_changed = false;
    for hub_asset in assets.iter() {
        let Some(spoke_config) = cache.cached_spoke_asset(account.spoke_id, &hub_asset) else {
            continue;
        };
        let asset_config = AssetConfig::from(&spoke_config);

        let raw = expect_invariant(env, account.supply_positions.get(hub_asset.clone()));
        let mut updated = AccountPosition::from(&raw);

        let changed = refresh_supply_risk_params(
            env,
            cache,
            &account,
            &hub_asset,
            &mut updated,
            &asset_config,
            scope,
        );
        if !changed {
            continue;
        }

        any_changed = true;
        update_or_remove_supply_position(&mut account, &hub_asset, &updated);

        let market_index = cache.cached_market_index(&hub_asset);
        cache.record_supply_position_update(
            events::PositionAction::ParamUpd,
            &hub_asset,
            market_index.supply_index.raw(),
            0,
            &updated,
        );
    }

    if any_changed {
        storage::set_supply_positions(env, account_id, &account.supply_positions);
    }

    if full_tuple {
        let hf = calculate_account_risk_totals(
            env,
            cache,
            &account.supply_positions,
            &account.borrow_positions,
        )
        .health_factor;
        assert_with_error!(
            env,
            hf >= Wad::from(THRESHOLD_UPDATE_MIN_HF_RAW),
            CollateralError::HealthFactorTooLow
        );
    }

    cache.emit_position_batch(account_id, &account);
```

**File:** docs/reference/runbooks/liqvid-listing-params.md (L362-389)
```markdown
Each supply position stores its own LTV, LT, base bonus and liquidation fee.
It copies them from the spoke listing when it is created
(`get_or_create_supply_position`). After that, the controller uses the
stored values, not the live listing:

- HF uses the stored LT (`calculate_account_risk_totals`).
- The borrow limit uses the lower of the stored LTV and the stored LT.
- The base bonus `b0` is the USD-weighted stored bonus. The maximum bonus `M`
  comes from the stored LT. The fee is the stored fee
  (`get_account_bonus_params`).
- The curve (`H`, `K`, `f`) is not stored. Each liquidation reads it from the
  spoke. `configureSpokeCurves` changes it for all accounts of the spoke at
  the same time.

Thus an `editAssetInSpoke` that lowers LT changes only the positions created
after it and the positions that the controller refreshes. Every borrow and
every withdrawal refreshes the stored LTV of each listed supply position
without a condition. The stored LT, bonus and fee refresh together, and only
in these paths:

| Path | Code |
|---|---|
| A supply of the asset into the account | `merge_supply_leg` calls `refresh_supply_risk_params` |
| A withdrawal of the asset that is not a liquidation and leaves a balance | `merge_withdraw_leg` |
| `update_account_threshold(caller, has_risks = true, account_ids)` | `sync_account_thresholds` |

A liquidation never refreshes them. `update_account_threshold` with
`has_risks = false` refreshes the LTV only.
```
