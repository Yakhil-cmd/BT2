### Title
AA batch payout of a `spender_attested` asset can be permanently stuck if any single output address loses/lacks attestation - ([File: validation.js])

### Summary
An AA that distributes a divisible/indivisible asset with `spender_attested: true` to multiple recipients in a single `payment` message is validated atomically: the network requires *every* output address of the payment to be attested, or the entire unit (and every legitimate recipient in it) is rejected. Because AA definitions are immutable and deterministic, an AA that always attempts to pay the same set of addresses in one message will keep failing/bouncing on every re-trigger as long as one grantee is unattested — exactly the "one bad recipient blocks payment to everyone else" bug class described in the external report (there, a blacklisted USDT address stalls the whole payout loop; here, an unattested address stalls the whole payout message).

### Finding Description
When an asset is defined with `spender_attested: true`, every payment of that asset is validated with an all-or-nothing rule on the output side: [1](#0-0) 

`filterAttestedAddresses` returns the addresses that are currently attested, and if the count doesn't match `arrOutputAddresses.length` (i.e. even one address among many recipients is not attested), the whole payment message is rejected with `"some output addresses are not attested"`. [2](#0-1) 

This check applies uniformly to base-layer wallets and to AA-generated response units, since AA payment messages go through the same `validatePaymentInputsAndOutputs` path. When an AA composes a payment with multiple recipient outputs (e.g. a "round" distribution AA paying many grantees in one `app: 'payment'` message with a `spender_attested` asset), and the definer or an attestor never attests one of the grantee addresses, revokes attestation, or the address simply never gets attested in time, the resulting unit permanently fails consensus validation. The AA's `sendUnit`/`bounce` logic in `aa_composer.js` deterministically re-derives the same messages and outputs on every trigger, so the bounce is not a one-time or self-healing event: [3](#0-2) 

Unlike ordinary wallet-composed payments (where a user notices the compose-time error and can simply remove the bad output), an AA's messages are defined in the immutable `arrDefinition` (oscript) template and evaluated automatically at trigger time; there is no way for the AA to retroactively drop just the unattested output and still pay the rest, because the failure occurs at the consensus-validation layer (`validatePaymentInputsAndOutputs`), not inside the oscript formula evaluation that built the outputs.

### Impact Explanation
If a "round" or "batch payout" AA is designed to send a `spender_attested` asset to several recipients in one message, any single grantee losing (or never having) attestation status causes the whole payment to fail validation, which in turn causes the AA to bounce the trigger and refund nothing to any of the other, legitimate grantees in that batch. Because AA logic is immutable and the bad output would be re-generated identically on every subsequent identical trigger, the AA can get stuck indefinitely (until the AA author or someone else manually crafts a differently-shaped trigger/state update that avoids including the unattested address — assuming the AA design even permits that). This is a fund-freezing condition affecting multiple legitimate parties, matching the High-severity impact of the original report (funds stuck forever for other recipients due to one recipient's blacklisted/unattested status).

### Likelihood Explanation
This requires: (1) an AA (or other multi-output payment flow) that batches multiple recipients of a `spender_attested` asset into a single payment message without per-output attestation checks in the oscript logic, and (2) at least one target address that is not attested at execution time (e.g., an attestor revokes/never issues attestation, or a compromised/blacklisted-by-issuer address). Given that `spender_attested` is a documented, first-class asset feature intended for whitelisting use cases (KYC'd assets, security tokens, etc.), and AA templates frequently build outputs from state variables or trigger data without an on-chain mechanism to pre-check attestation of arbitrary future recipients, this is a realistic design pitfall rather than a purely theoretical one.

### Recommendation
- For AAs intending to distribute `spender_attested` assets to multiple recipients, avoid combining all recipients into a single payment message; instead, use a pull-based design (recipients trigger their own claim, so only their own unattested status blocks their own payment) or issue one separate response/payment per recipient so a single failure does not block the batch.
- Alternatively, expose (or use, if available) an oscript-level attestation check so the AA can filter out unattested recipients before constructing outputs, and re-route their share to a claimable/pending state instead of hard failing.
- Document prominently for AA authors that `spender_attested` assets have all-or-nothing output validation (`validation.js` `filterAttestedAddresses` check) and should not be used in batched multi-recipient AA payment messages.

### Proof of Concept
1. Define an asset `X` with `spender_attested: true` and an attestor list (`storage.js:1976-1991`, `validation.js:2725-2755`).
2. Deploy an AA whose response, on trigger, sends asset `X` to a fixed/derived list of grantee addresses in a single `payment` message (mirroring a "round distribution" pattern).
3. Ensure grantee addresses A and B are attested by the attestor, but grantee C is never attested (or has its attestation revoked via a new `address_definition_change`, per `storage.js:1960-1974`).
4. Trigger the AA. The response payment message contains outputs to A, B, and C.
5. During validation, `validatePaymentInputsAndOutputs` calls `storage.filterAttestedAddresses` on all three output addresses; since C is not attested, `arrAttestedOutputAddresses.length !== arrOutputAddresses.length`, and the message is rejected with `"some output addresses are not attested"` (`validation.js:2630-2641`).
6. The AA response bounces (`aa_composer.js:909-944`), refunding only the bounce fee logic, and *not* paying A or B either, even though they are legitimately attested and eligible.
7. Because the AA's oscript definition is immutable and deterministically reproduces the same three outputs on every subsequent identical trigger, the payout to A and B remains permanently blocked as long as C stays unattested.

function filterAttestedAddresses(conn, objAsset, last_ball_mci, arrAddresses, handleAttestedAddresses){
	conn.query(
		"SELECT DISTINCT address FROM attestations CROSS JOIN units USING(unit) \n\
		WHERE attestor_address IN(?) AND address IN(?) AND main_chain_index<=? AND is_stable=1 AND sequence='good' \n\
			AND main_chain_index>IFNULL( \n\
				(SELECT main_chain_index FROM address_definition_changes JOIN units USING(unit) \n\
				WHERE address_definition_changes.address=attestations.address AND main_chain_index<=? AND is_stable=1 AND sequence='good' ORDER BY main_chain_index DESC LIMIT 1), \n\
			0)",
		[objAsset.arrAttestorAddresses, arrAddresses, last_ball_mci, last_ball_mci],
		function(addr_rows){
			var arrAttestedAddresses = addr_rows.map(function(addr_row){ return addr_row.address; });
			handleAttestedAddresses(arrAttestedAddresses);
		}
	);
}
