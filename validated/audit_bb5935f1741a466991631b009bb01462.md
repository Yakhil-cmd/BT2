### Title
AA responses and bounce refunds are sent only to `authors[0]`, not to whoever actually funded the payment, in multi-authored AA trigger units - (File: `aa_composer.js`)

### Summary
Autonomous Agent (AA) triggers are handled by treating `objUnit.authors[0].address` as *the* "sender" (`trigger.address`), which is then used both for granting oscript access to `trigger.address` and, in the built-in bounce logic, as the destination of any refunded bytes/assets when the trigger fails to fully "bounce_fees". Unlike AA response units, which are hard-restricted to a single author (`validateAuthors` throws `"AA unit with multiple authors"` when `objValidationState.bAA`), **trigger units are not restricted to a single author**. A trigger unit can be multi-authored — e.g. because `composeJoint`/`composeDivisibleAssetPaymentJoint`/`composeIndivisibleAssetPaymentJoint` combine `paying_addresses` and `fee_paying_addresses` (or `signing_addresses`) from different wallet addresses into one unit (`arrFromAddresses = _.union(arrSigningAddresses, arrPayingAddresses).sort()`, `bMultiAuthored = arrFromAddresses.length > 1`). When such a unit triggers an AA, the AA bounces the payment (or an AA oscript explicitly refunds `trigger.address`, as seen in many sample AAs), the coins are sent to `objUnit.authors[0].address` — the lexicographically first signer — regardless of which of the co-authors actually supplied the funds that were sent to the AA.

### Finding Description
`getTrigger()` in `aa_composer.js` unconditionally sets:
```js
var trigger = { address: objUnit.authors[0].address, unit: objUnit.unit, outputs: {} };
``` [1](#0-0) 

This `trigger.address` is later used by the built-in `bounce()` function to decide where to send back any received coins that exceed `bounce_fees`:
```js
messages.push({app: 'payment', payload: {asset: asset, outputs: [{address: trigger.address, amount: bounced_amount}]}});
``` [2](#0-1) 

and is exposed to oscript as `trigger.address`, which is commonly used by AA authors to send refunds/responses back to the caller (e.g. `outputs: [{address: "{trigger.address}", amount: "{$amount}"}]` in the fundraising sample AA). [3](#0-2) 

Nothing in unit validation requires a trigger unit to be single-authored. `validateAuthors()` only enforces single authorship for **AA response** units (`objValidationState.bAA`), not for ordinary units that happen to trigger an AA:
```js
function validateAuthors(conn, arrAuthors, objUnit, objValidationState, callback) {
	if (objValidationState.bAA && arrAuthors.length !== 1)
		throw Error("AA unit with multiple authors");
``` [4](#0-3) 

`validateAATrigger()` also imposes no author-count restriction — it only checks properties of the AA-addressed outputs. [5](#0-4) 

Meanwhile, the wallet-side payment composer routinely builds multi-authored units where the "payer of the outputs" and the "payer of the transfer/commission fees" are different addresses:
```js
paying_addresses: _.union(params.paying_addresses, params.fee_paying_addresses), // addresses that pay for the transfer and commissions
``` [6](#0-5) 
```js
var arrFromAddresses = _.union(arrSigningAddresses, arrPayingAddresses).sort();
...
var bMultiAuthored = (arrFromAddresses.length > 1);
``` [7](#0-6) 

Because `objUnit.authors` is required to be sorted by address (`validateAuthors` rejects out-of-order authors), `authors[0]` is simply whichever co-signing address happens to sort first — it has no relationship to which address actually contributed the value that was sent to the AA. If the address that pays the asset/base value to the AA is not the lexicographically-first author (e.g. it is the `fee_paying_addresses` entry, or a co-signer of a shared address whose address sorts first even though a different signer supplied most of the value), then:
- any excess/refunded value from the AA's automatic `bounce()` logic, and
- any AA oscript logic that explicitly sends value "back to the sender" via `trigger.address`,

will be paid to the wrong author — an address that did not contribute the funds and has no economic claim to the refund — while the actual funder receives nothing back.

### Impact Explanation
This directly parallels the reported bug class: value that should return to the party who actually supplied the funds instead flows to a different, merely-associated address (here, a co-author of the same unit). The party whose bytes/assets were consumed permanently loses them to another author of the same transaction whenever an AA bounces or an AA script sends a refund/response to `trigger.address`. Because this can occur any time a legitimate multi-authored payment (fee-payer + asset-payer, or shared/multisig address) triggers an AA that bounces (e.g., insufficient parameters, a business-logic failure, or explicit refund messages) it is a concrete fund-misdirection/loss issue reachable by any ordinary unprivileged AA-trigger sender who composes (or is served by wallet software that composes) a multi-authored payment to an AA.

### Likelihood Explanation
Multi-authored units triggering AAs are a normal, supported flow (fee-paying vs. value-paying address separation is a first-class feature of `composeDivisibleAssetPaymentJoint`/`composeIndivisibleAssetPaymentJoint`, and shared/multisig addresses are also multi-authored). AAs bouncing (returning unused/erroneous payments) and AA oscripts that echo `trigger.address` as the refund/response target are extremely common patterns in the sample AAs shipped with the codebase, so the vulnerable code path is exercised whenever these two common features are combined — no attacker cooperation or malicious counterparty is required, only ordinary usage of fee/paying address separation together with an AA that can bounce or explicitly refunds `trigger.address`.

### Recommendation
Do not rely solely on `authors[0]` as the refund/response target for multi-authored trigger units. Options:
- Restrict AA triggers to single-authored units, mirroring the restriction already placed on AA response units in `validateAuthors`.
- Or, have `getTrigger()`/`bounce()` compute the actual payer(s) of the value sent to the AA (i.e. the addresses that own the inputs funding the payment message to the AA address) rather than defaulting to `authors[0]`, and expose that distinctly from any transaction-fee payer, similar to the "refund to" parameter recommended in the original report.

### Proof of Concept
1. Wallet composes a payment to an AA address using `composeDivisibleAssetPaymentJoint` with `paying_addresses = [B]` (owns the asset value being sent) and `fee_paying_addresses = [A]` (only pays byte fees), where `A < B` lexicographically. The resulting unit is multi-authored with `authors = [A, B]` per `_.union(...).sort()` in `composer.js`. [8](#0-7) [6](#0-5) 
2. `getTrigger()` sets `trigger.address = authors[0].address = A`, even though `A` contributed no asset value — only `B` did. [1](#0-0) 
3. The AA rejects/bounces the trigger (e.g., missing required data or insufficient amount), and `bounce()` sends the returned coins to `trigger.address` (`A`), or the AA's own oscript explicitly refunds `trigger.address`. [2](#0-1) 
4. `B`, who supplied the actual value, receives nothing back; `A`, who only paid the transaction fee, receives the full refund.
