Based on the code I reviewed, the closest reachable analog in `git-sync` is the unbounded, attacker-controlled git submodule recursion performed by `configureWorktree`, which trusts arbitrary repo content (submodule definitions) to drive `git submodule update --init [--recursive]` with no cap on submodule count, nesting depth, or fetched size.

### Title
Untrusted upstream repo content can define unbounded/recursive git submodules to cause persistent sync denial (resource-exhaustion DoS) - (File: `main.go`)

### Summary
`git-sync`'s worktree configuration step blindly runs `git submodule update --init [--recursive]` against whatever `.gitmodules` content exists in the currently-synced commit, with no limits on the number, nesting depth, or size of submodules, and no distinction between trusted and untrusted contributors to the tracked repository/ref.

### Finding Description
`configureWorktree` builds and executes the submodule-update command directly from the checked-out ref's content: [1](#0-0) 

The only bound applied is an optional `--depth` (commit history depth), which the operator may or may not set, and which does not limit the *number* or *nesting* of submodules, only the git history depth per repository. There is no validation of `.gitmodules` entries (count, recursion depth, target repo size) before invoking `git submodule update --init --recursive`. Since `.gitmodules` and submodule pointers are ordinary tracked file content, anyone who can land a commit on the synced `--ref` (e.g., a merged PR, a webhook-triggered branch update, or any writer with push access to the branch/tag git-sync follows) fully controls how many submodules are declared and how deeply they nest, including submodules that point at very large or slow-to-clone repositories, or circular/self-referential submodule graphs.

This mirrors the reported bug class: an actor who is not the "owner" of the sync target (i.e., not the git-sync operator who chose the top-level `--repo`/`--ref`) can inject unbounded auxiliary state (many/deep submodules) into a resource the operator does not fully control, degrading or breaking the resource for the legitimate consumer.

### Impact Explanation
A single malicious or compromised commit merged into the tracked ref can cause `configureWorktree` to spend excessive time, disk, network and memory recursively fetching submodules, or hang entirely on a very large/slow chain of submodules. Because `SyncRepo` must complete `configureWorktree` before `publishSymlink` is called, this directly blocks the atomic-symlink publish step described in `README.md`, resulting in persistent sync denial for every consumer relying on the `--link` directory — analogous to the original report's "rewards mechanism fails due to DoS" outcome, but here it is "sync mechanism fails due to DoS."

### Likelihood Explanation
Likelihood is moderate to high in any deployment where the tracked ref accepts contributions from users who are not fully trusted operators of the git-sync sidecar (a common CI/CD or GitOps pattern where PRs are merged by a broader team than those who configured the sidecar). No special git-sync flags are required beyond the default `--submodules=recursive` behavior, which is the tool's default.

### Recommendation
- Add explicit configurable limits on submodule fetch: max submodule count, max recursion depth (independent of `--depth`), and/or a `--submodules=off` enforcement path for untrusted refs.
- Consider running submodule updates with a bounded timeout distinct from `--sync-timeout` so a single stuck sync doesn't block indefinitely, and surface metrics/alerts when submodule update time grows abnormally.
- Document that `.gitmodules` content is fully untrusted input whenever the synced ref is writable by users other than the operator, and recommend `--submodules=off` for such repos.

### Proof of Concept
1. Attacker with push/PR-merge rights to the branch tracked by `--ref` adds hundreds of submodule entries in `.gitmodules`, each pointing to distinct or nested repositories (or a submodule that itself recursively references many more submodules).
2. `git-sync` fetches the new commit; `SyncRepo` detects `changed == true` and calls `createWorktree` then `configureWorktree`.
3. `configureWorktree` executes `git submodule update --init --recursive` against the attacker-controlled `.gitmodules`/submodule graph, consuming excessive time/network/disk, or stalling indefinitely.
4. `publishSymlink` is never reached, so the `--link` directory is never updated (or the whole sidecar becomes unresponsive), denying all downstream consumers a fresh sync — a persistent sync-denial DoS driven entirely by untrusted repo content.
