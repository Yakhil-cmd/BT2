### Title
`StatusHandler#process` mutates `Commit`/`Status` records globally by `sha` with no repository/organization scoping - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` across the entire `commits` table, without restricting to the repository/organization whose `webhook_secret` verified the request. Since `params.sha` is an attacker-controlled string inside a payload the attacker signs with their own org's `webhook_secret`, an attacker who legitimately owns a repo/App installation in `attacker-org` can create/update `Status` rows on any commit sha that happens to exist under any other tenant's stack (e.g. `victim-org`), because the binding "organization that verified the signature == organization owning the mutated commit" is never checked at the model layer.

### Finding Description
The binding that should hold is: `organization_that_signed(webhook) == organization_owning(Commit.find_by(sha: params.sha).stack.repository)`. This is enforced for every other event handler but not for `status`.

- `WebhooksController#verify_signature` resolves `Shipit.github(organization: repository_owner)` from `params.dig('repository','owner','login')` and validates the HMAC signature against that org's own `webhook_secret` [1](#0-0) . This is correct in isolation: it proves the request body was signed by `attacker-org`'s secret, and nothing more.
- The base `Handler` class provides a `stacks` helper that scopes lookups to the repository named in the payload: `Repository.from_github_repo_name(repository_name)&.stacks` [2](#0-1) . Every other handler (`PushHandler`, `CheckSuiteHandler`, the `PullRequest::*` handlers) uses this `stacks`/`repository` scoping before touching any record, e.g. `stacks.where(branch: params.check_suite.head_branch)` [3](#0-2) , `stacks.not_archived.where(branch:)` [4](#0-3) .
- `StatusHandler`, however, does not require `repository` in its params schema at all and never calls `stacks`/`repository_name`; it queries the commit table unscoped:
```
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [5](#0-4) 

Because `params.sha` is free text under attacker control, and the only enforced constraint is that the *request as a whole* was signed by *some* org (whichever org the attacker legitimately controls), the attacker only needs to know or guess a commit SHA that exists under a different org's stack (SHAs of public repos are trivially observable; commits also propagate across forks/mirrors). `Commit.where(sha:...)` will match it regardless of which repository/organization actually owns that commit row — the `commits` table has no per-request repository filter, only a `stack_id`+`sha` DB index used for internal lookups, not for authorization [6](#0-5) .

`commit.create_status_from_github!` ultimately calls `add_status`, which fires `Hook.emit(:commit_status, ...)` / `:deployable_status` and can call `stack.schedule_merges` on state transitions to `pending`/`success` [7](#0-6) . This means an attacker-signed request for `attacker-org` can flip a `victim-org` commit's CI status to `success`, potentially unblocking a merge/deploy gate for a stack they have no relationship to.

Existing guards do not catch this: `verify_signature` only proves body authenticity for the org derived from `repository.owner.login` in the payload, but `StatusHandler` never re-derives or compares that org/repository against the `Commit`/`Stack`/`Repository` actually being mutated. The `ExplicitParameters` schema for `StatusHandler` doesn't even require a `repository` key, so there is no field to scope on even if the developer wanted to.

### Impact Explanation
An attacker with a legitimate low-privilege GitHub App installation in `attacker-org` (their own repo, their own webhook secret) can write `Status` rows attributed to arbitrary commits in `victim-org`'s stacks merely by naming that SHA in a `status` webhook payload signed with `attacker-org`'s secret. This can spoof CI outcomes (`success`/`failure`/`pending`) for a repository the attacker never authenticated against, and can trigger `stack.schedule_merges`, i.e., contribute to an unauthorized deploy/merge decision for a completely separate tenant. This is a full multi-tenant boundary bypass ("payload for one repository mutating another's stack/commit"), matching the Critical impact category.

### Likelihood Explanation
Requires only the documented multi-org Shipit configuration (`Shipit.github(organization: ...)` per README/`docs/setup.md`) with at least two independent org installations sharing one Shipit instance [8](#0-7) . The attacker needs no privileged Shipit role — only their own org's `webhook_secret`, which they can obtain by owning/administering their own GitHub App installation (a legitimate, unprivileged action within their own org). Knowing a target SHA in another org's stack is easy for public repos and plausible in many private-repo scenarios (SHAs are often disclosed via status/CI badges, PR links, commit messages, etc.). The attack is repeatable against any SHA and any number of victim stacks with a single HTTP POST per attempt.

### Recommendation
In `StatusHandler`, require the `repository.full_name` (or `owner.login`) in the params schema and scope the commit lookup through `stacks`/`Repository.from_github_repo_name` the same way `PushHandler` and `CheckSuiteHandler` do, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { ... repository_name matches payload ... })`, so the mutated `Commit` must belong to the same repository/organization that the webhook signature was verified against.

### Proof of Concept
Minitest plan (controller-level, no live GitHub):
1. Configure two orgs in test secrets (`test/dummy/config/secrets_double_github_app.yml` already provides `OrgOne`/`OrgTwo` with distinct `webhook_secret`s).
2. Create `stack_a` under `OrgOne`'s repository with `commit_a` (`sha: "aaa..."`), and `stack_b` under `OrgTwo`'s repository with `commit_b` (`sha: "bbb..."`).
3. Build a `status` payload naming `sha: commit_b.sha`, `repository.owner.login: "OrgOne"` (or any repo under OrgOne), and sign it with `OrgOne`'s `webhook_secret` (correct signature for OrgOne).
4. POST to `/webhooks` with `X-Github-Event: status` and the correct `X-Hub-Signature` for OrgOne.
5. Assert: `assert_no_difference('commit_b.statuses.count') { post :create, body: payload, as: :json }` — currently this assertion **fails** because a `Status` is created on `commit_b` despite the request being signed only for `OrgOne`.
6. Additionally assert `commit_a.statuses.count` is unaffected, to show the mismatch is specifically cross-tenant (OrgOne's signed request affecting OrgTwo's commit).

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:

      webhook_secret:
      private_key:
