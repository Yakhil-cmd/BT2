### Title
Stake rewards are silently burned instead of credited when a stake account is closed/mutated between reward calculation and partitioned distribution — (File: `runtime/src/bank/partitioned_epoch_rewards/distribution.rs`)

### Summary
The partitioned epoch-rewards distribution path calculates a staker's SOL inflation reward in one phase and only attempts to credit it to the on-chain stake account several blocks later, during `store_stake_accounts_in_partition`. If crediting fails for any reason (most notably, the target stake account no longer exists), the code does not retry, does not fail the block, and does not preserve the reward for the staker — it silently discards ("burns") the reward and logs an `error!` line, exactly the same "calculate now, pay later, swallow failure" pattern flagged in the external Sherlock report for `pullReward`.

### Finding Description
Reward calculation and reward distribution are split into two separate phases that can span many blocks (`REWARD_CALCULATION_NUM_BLOCKS` and additional partitions) [1](#0-0) . During calculation, `PartitionedStakeReward` entries capturing each stake pubkey's earned reward are computed and cached [2](#0-1) .

Later, in a subsequent block, `store_stake_accounts_in_partition` attempts to actually apply that reward to the current stake account state via `build_updated_stake_reward`: [3](#0-2) 

If the stake account referenced by `partitioned_stake_reward.stake_pubkey` can no longer be found in `stakes_cache_accounts` (e.g. it was closed via `Withdraw` after deactivating, in the window between reward calculation and this partition's distribution block), `build_updated_stake_reward` returns `DistributionError::AccountNotFound` instead of crediting anything [4](#0-3) .

The caller then treats this failure not as an error condition to retry or preserve, but as a lamports-burning event: [5](#0-4) 

The reward amount is added to `stake_reward_lamports_burned`/`block_reward_lamports_burned`, which is then used only to correctly decrement the `EpochRewards` sysvar's outstanding balance [6](#0-5)  — the staker who earned the reward receives nothing, and no record credits them elsewhere. The code comment itself acknowledges this is meant to never happen ("Because stake accounts are checked in calculation, and further state mutation prevents by stake-program restrictions, there should never be rewards burned") [7](#0-6) , yet the code paths, tests (`DistributionError::AccountNotFound` is explicitly tested with `test_build_updated_stake_reward`) [8](#0-7) , and the `ArithmeticOverflow`/`UnableToSetState` variants all exist specifically to handle the case where the assumption is violated.

This mirrors the Sherlock finding precisely: a reward is computed and "owed," a later step that actually delivers it can fail, and on failure the system silently proceeds by discarding the reward rather than reverting/holding the block or otherwise guaranteeing the staker is made whole.

### Impact Explanation
A staker's already-earned inflation reward (and any block-revenue-sharing reward) for the rewarded epoch can be permanently lost (burned from capitalization) with no compensating credit to the staker, if the target stake account is closed or otherwise unavailable to the stakes cache when its partition is processed. This is a misattributed/lost-rewards condition on the primary reward-distribution path used every epoch by every delegator on the network.

### Likelihood Explanation
The distribution window for a partition-of-rewards spans a variable but potentially large number of blocks after calculation (`get_reward_distribution_num_blocks`) [9](#0-8) , giving delegated stakers ample opportunity to deactivate and fully withdraw stake in this window if their deactivation epoch matches the currently-rewarded epoch (since a `Withdraw` instruction against a fully-deactivated stake account is a normal, permission-checked, unprivileged user action). The code and its own comments concede this "should never" happen under the assumed stake-program restrictions, which indicates this is a defense-in-depth path rather than a hardened invariant — i.e., a gap between the assumption in the reward-distribution code and behaviors permitted by the stake program.

### Recommendation
Do not silently burn stake rewards on a `DistributionError`. Instead:
- Preserve the reward for the affected stake pubkey (e.g., re-route to a claimable/held account, or fail closed and re-attempt distribution) rather than discarding it from the sysvar's distributed-total tracking as burned.
- Add an explicit invariant/assertion that ties the "should never happen" comment to an enforced precondition (e.g., ensure stake-program restrictions genuinely prevent account closure for any stake pubkey present in a not-yet-distributed `PartitionedStakeReward`, or snapshot/lock those accounts for the duration of the reward interval).
- At minimum, treat `DistributionError` as a critical anomaly that halts/flags the block for validator operators rather than transparently burning lamports and continuing, consistent with the external report's recommendation to fail loudly rather than proceed with partial reward delivery.

### Proof of Concept
1. A stake account fully deactivates in epoch `N` (its final reward is calculated as a `DeactivatedStake` reward during the calculation phase of epoch `N+1`, per `store_stake_accounts_in_partition`'s handling of `RewardType::DeactivatedStake`).
2. The distribution phase spans multiple blocks. Before the block that processes this stake account's specific partition, the withdraw authority submits a `Withdraw` instruction for the full balance, closing the stake account.
3. When `store_stake_accounts_in_partition` reaches this stake pubkey's partition index, `stakes_cache_accounts.get(&partitioned_stake_reward.stake_pubkey)` returns `None` (the account state has since changed and can no longer be resolved as the expected delegation), yielding `DistributionError::AccountNotFound` [10](#0-9) .
4. The `Err(err)` branch executes: the reward is added to `stake_reward_lamports_burned`/`block_reward_lamports_burned` and logged, but never paid to the staker [11](#0-10) .
5. The staker's already-earned reward for that epoch is permanently and silently lost, matching the existing regression test `test_build_updated_stake_reward`'s `AccountNotFound` case, which the production code path treats as a burn rather than a preserved/retried credit [8](#0-7) .

    /// Calculate the number of blocks required to distribute rewards to all stake accounts.
    pub(super) fn get_reward_distribution_num_blocks(
        &self,
        rewards: &PartitionedStakeRewards,
    ) -> u64 {
        let total_stake_accounts = rewards.num_rewards();
        if self.epoch_schedule.warmup && self.epoch < self.first_normal_epoch() {
            1
        } else {
            const MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH: u64 = 10;
            let num_chunks = total_stake_accounts
                .div_ceil(self.partitioned_rewards_stake_account_stores_per_block() as usize)
                as u64;

            // Limit the reward credit interval to 10% of the total number of slots in a epoch
            num_chunks.clamp(
                1,
                (self.epoch_schedule.slots_per_epoch / MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH).max(1),
            )
        }
    }
