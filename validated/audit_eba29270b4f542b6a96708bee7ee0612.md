## Title
Signature verification binds the wrong scope to the payload's target repository — cross-organization webhook forgery via `WebhooksController#repository_owner` vs `Handler#repository_name` mismatch - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` is used to authenticate an inbound webhook based on `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0) [2](#0-1) . The base `Handler` class that actually processes the event and looks up which `Repository`/`Stack` to mutate uses a completely independent field of the same attacker-supplied JSON body: `payload.dig('repository', 'full_name')` [3](#0-2) . Since the HMAC only proves the payload was signed with *some* organization's `webhook_secret` known to Shipit — not that `repository.owner.login` and `repository.full_name`'s owner segment are the same organization the signature was computed for — an attacker who has legitimate access to one configured organization's webhook secret (e.g., their own org, when Shipit is configured per the documented multi-org setup) can forge a signed payload whose `repository.owner.login` matches their own org (satisfying `verify_signature`) while `repository.full_name` points at a completely different, victim organization's repository/stack that the attacker has no access to.

### Finding Description
This is the closest analog to the Goat Trading bug class: a value gated by a check (the withdrawal amount vs. `lpInfo.fractionalBalance`) is not the same value actually acted upon in the "last withdrawal" branch, letting the attacker route more value through the check than intended. Here, the value gated by the check (`repository.owner.login`, used to pick the trusted `webhook_secret`) is not the same value the engine writes against (`repository.full_name`, used by `Handler#repository_name` to resolve the target `Repository`/`Stack`). Both fields live in the same attacker-controlled JSON body and are independent strings with no cross-field validation, so:

- Binding that should hold: `organization authenticated by verify_signature == organization whose repository is written by the handler`.
- Actual binding enforced: `organization authenticated by verify_signature == params['repository']['owner']['login']` (attacker-controlled string) while the write target is `Repository.from_github_repo_name(params['repository']['full_name'])` (a different, independently attacker-controlled string) [3](#0-2) .

Concretely, `StatusHandler#process` writes a `CommitStatus` directly from attacker-supplied fields (`state`, `description`, `target_url`, `context`) for any `Commit` matching `params.sha`, with no re-fetch from GitHub to validate authenticity [4](#0-3) , and `CheckSuiteHandler#process` schedules check-run refreshes for arbitrary stacks matched by `repository.full_name` and branch [5](#0-4) . Both are reachable purely from the `repository.full_name` scoping resolved via `Handler#stacks`/`repository_name`, independent of the `repository_owner` value that authenticated the request.

### Impact Explanation
This crosses a real trust boundary: it allows an entity that only controls the webhook secret for organization B (e.g. their own onboarded organization in a Shipit multi-org deployment, as documented in `docs/setup.md`'s "Using Multiple Github Applications" section) to forge webhook events that mutate state (commit statuses, check-run refresh scheduling, sync triggers) for organization A's stacks, which they have no legitimate access to. Forged commit statuses can flip a commit to `success`, potentially unblocking or misrepresenting deployability decisions for a repository the attacker doesn't control — this is a cross-repository/cross-organization write achieved without any legitimate credential for the victim repo, matching the "cross-repository writes" Critical-impact criterion.

### Likelihood Explanation
Requires the attacker to control (or know the `webhook_secret` of) at least one organization configured in Shipit's multi-org `github:` secrets — a routine setup for shared/multi-tenant Shipit instances per `docs/setup.md`. No access to the victim organization, its GitHub App, or any Shipit session/API token is required; only knowledge of one org's own webhook secret and the target repository's `full_name` (public information) is needed.

### Recommendation
In `WebhooksController#verify_signature`, after selecting the GitHub App by `repository_owner`, verify that the resolved `Repository` for `payload.dig('repository','full_name')` actually belongs to that same `repository_owner`/organization before dispatching to any handler (i.e., assert `full_name.split('/').first == repository_owner`, case-insensitively). Alternatively, bind handler dispatch to the same normalized owner value used for signature verification instead of re-reading an independent field from the payload.

### Proof of Concept
1. Shipit is configured with two organizations, `AttackerOrg` (attacker-controlled installation/secret) and `VictimOrg` (target), per the multi-org `github:` secrets format shown in `docs/setup.md`.
2. Attacker builds a JSON `status` webhook payload:
   ```json
   {
     "sha": "<victim commit sha>",
     "state": "success",
     "context": "ci/forged",
     "repository": { "owner": { "login": "AttackerOrg" }, "full_name": "VictimOrg/victim-repo" }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(AttackerOrg_webhook_secret, body)`.
4. `WebhooksController#verify_signature` resolves `Shipit.github(organization: 'AttackerOrg')` via `repository_owner` and the signature verifies successfully [1](#0-0) .
5. `StatusHandler#process` is invoked and, using `params.sha`, updates the status of a real commit belonging to `VictimOrg/victim-repo` — a repository/organization the attacker never authenticated against [4](#0-3) [3](#0-2) .
