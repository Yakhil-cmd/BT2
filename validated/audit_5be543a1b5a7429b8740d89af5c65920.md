### Title
Webhook signature verification is bound to `repository.owner.login`, but the write target is bound to `repository.full_name` - unauthenticated cross-organization stack actions - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate a webhook against using `repository.owner.login` from the JSON body, while every webhook `Handler` determines which `Stack`/`Repository` to act on using the *different* field `repository.full_name`. Since `Shipit` explicitly supports per-organization webhook secrets that are documented as *optional*, any organization configured without a `webhook_secret` causes signature verification to be a no-op for that org, yet the (unverified) `full_name` field can still point at any other repository tracked by Shipit - including one belonging to an organization that does have a properly configured secret.

### Finding Description
Signature verification resolves the org to check against like this: [1](#0-0) [2](#0-1) 

That org is used purely to pick a `GitHubApp` instance, whose signature check short-circuits when no secret is configured: [3](#0-2) 

Documentation explicitly treats the webhook secret as optional per organization, and shows that multiple organizations can be configured simultaneously, each with its own (optionally blank) secret: [4](#0-3) 

However, every webhook `Handler` ignores `repository.owner.login` entirely and instead resolves the repository/stacks to mutate purely from `repository.full_name`: [5](#0-4) [6](#0-5) 

`PushHandler` then acts on whatever stacks that lookup returns, using attacker-supplied `ref`/`after` values: [7](#0-6) 

The binding that should hold is: `organization authenticated by verify_signature == owner(repository written by handler)`. Because `verify_signature` derives the org strictly from `repository.owner.login` (checked against that org's, possibly blank, secret) and the handlers derive the target strictly from `repository.full_name` (never cross-checked against `repository.owner.login`), an attacker who can reach `/webhooks` unauthenticated can set `repository.owner.login` to any organization configured in Shipit with no `webhook_secret` (bypassing the HMAC check entirely, since `verify_webhook_signature` returns `true` when `webhook_secret` is blank), while setting `repository.full_name` to `victim-org/victim-repo`, an entirely different, securely-configured organization's repository that has stacks registered in Shipit. `Repository.from_github_repo_name` and the handler's `stacks` method never re-validate that `full_name`'s owner segment matches the organization that was actually authenticated.

### Impact Explanation
This breaks the "organization authenticated vs. repository written" binding called out in the rules. With zero credentials, an attacker can trigger `PushHandler#process`, which calls `stack.sync_github(expected_head_sha: params.after)` for stacks belonging to a repository the attacker has no relationship to, forcing unauthorized state changes (sync operations, and for continuous-delivery-enabled stacks, this can feed into automatic deploy scheduling) against another organization's tracked stack. Other handlers (`status`, `check_suite`, `pull_request/*`) share the same `Handler#stacks`/`repository_name` resolution and are equally exposed to the same cross-organization targeting once the attacker picks any configured org without a secret as the "authenticated" org in the payload.

### Likelihood Explanation
Likelihood depends on operator configuration: it requires at least one organization in the multi-org `github:` config to have a blank/unset `webhook_secret` - a state the project's own setup docs present as a normal, supported, "optional" configuration rather than a misconfiguration to avoid. Any Shipit deployment onboarding multiple GitHub organizations (as the docs explicitly instruct how to do) and leaving even one org's secret unset is exposed; no attacker credential, session, or stolen secret is required.

### Recommendation
When resolving the target repository/stacks in `Shipit::Webhooks::Handlers::Handler`, cross-check that `payload.dig('repository', 'owner', 'login')` (the field the signature was verified against) matches the owner segment of `payload.dig('repository', 'full_name')`, and reject the webhook if they diverge. Additionally, consider making `webhook_secret` mandatory (or logging/alerting loudly) for any organization mapped in `Shipit.github`, since an unset secret currently disables authentication for that entire org's webhook traffic.

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.yml`: `trusted-org` (no `webhook_secret` set) and `victim-org` (has a `webhook_secret`, has a Stack registered for `victim-org/victim-repo`).
2. As an unauthenticated attacker, POST to `/webhooks` with header `X-Github-Event: push` and any/no `X-Hub-Signature`, and JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef...",
  "repository": { "owner": { "login": "trusted-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. `verify_signature` resolves `repository_owner` = `trusted-org`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally [8](#0-7) .
4. `PushHandler` resolves stacks from `repository.full_name` = `victim-org/victim-repo` [9](#0-8)  and triggers `stack.sync_github(expected_head_sha: params.after)` for that stack [10](#0-9) , even though the request was never validated against `victim-org`'s secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
