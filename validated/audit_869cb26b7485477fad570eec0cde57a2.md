## Analysis

This is a multi-tenant binding-confusion issue in `Shipit::WebhooksController`. The equality the engine relies on is:

`organization used to select the webhook secret (and thus verify the HMAC) == owner of the repository that the payload is later applied to`

but the two values are read from **independent, unauthenticated JSON fields** of the same raw body, and nothing cross-checks them.

### Root cause

`before_action :verify_signature` picks which org's `webhook_secret` to HMAC-verify against using a value taken straight out of the still-unverified JSON body: [1](#0-0) [2](#0-1) 

`repository_owner` reads `params.dig('repository', 'owner', 'login')` (or `organization.login`) from the attacker-supplied payload, and `Shipit.github(organization: repository_owner)` looks up that organization's `webhook_secret` for `verify_webhook_signature`: [3](#0-2) [4](#0-3) 

Once the HMAC check passes (proving only that the sender knows *some* configured organization's secret — e.g., their own org, which they administer on GitHub and can legitimately deliver signed webhooks for), the handlers act on a **completely different, independent field**: `repository.full_name`, which is never compared against `repository.owner.login`: [5](#0-4) [6](#0-5) 

`Repository.from_github_repo_name` then splits `full_name` on `/` and looks up the repo purely by that string, independent of which org's secret validated the request: [7](#0-6) 

### Impact

In a Shipit instance configured for multiple GitHub organizations (the per-org `github_app_config` path in `Shipit.github`), an admin/owner of **organization A** (who legitimately possesses A's `webhook_secret` because they configured the GitHub App/webhook for their own org) can POST a `push` webhook whose body sets `repository.owner.login` = `"org-a"` (to select the secret they know and sign with) but `repository.full_name` = `"org-b/victim-repo"`. `verify_signature` authenticates the request as belonging to org A (signature matches org A's secret), but `PushHandler` resolves the target stack via `full_name`, i.e. org B's repository, and calls `stack.sync_github(expected_head_sha: params.after)` on it — enqueuing a `GithubSyncJob` for a repository the attacker does not own. The same pattern reaches `PullRequest::OpenedHandler`, `ClosedHandler`, `ReopenedHandler`, and `LabelCapturingHandler`, all of which resolve the acted-upon repository purely from `params.repository.full_name` after the same org-keyed signature check, letting a cross-org actor drive review-stack provisioning/archival (`ReviewStackAdapter#create!`/`archive!`/`unarchive!`) and label capture on a victim org's stacks.

This matches the requested Critical impact of an unauthorized deploy trigger / cross-repository write: an attacker with valid credentials for one tenant reaches state-changing actions (`sync_github`, review-stack archive/unarchive/create) on a different tenant's repository, purely because the org used for authentication is never bound to the repository the payload claims to describe.

### Recommendation

After the HMAC check succeeds, re-derive `repository_owner` from a value that is provably scoped to the org whose secret matched (or, simpler, compare `payload.dig('repository','full_name')`'s owner segment against `repository_owner` and reject on mismatch) before dispatching to any handler in `Shipit::Webhooks.for_event`.

### Proof of Concept

1. Deploy Shipit configured with two GitHub orgs, `org-a` and `org-b`, each with its own `secrets.github[:org_a][:webhook_secret]` / `[:org_b][:webhook_secret]`, both hosting stacks tracked by Shipit.
2. As an attacker who is an owner/admin of `org-a` (and therefore legitimately knows `org-a`'s webhook secret because they set up the GitHub webhook themselves), craft a `push` JSON payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=HMAC_SHA1(org_a_webhook_secret, raw_body)` and POST to `/github/webhooks` with `X-Github-Event: push`.
4. `verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) resolves `repository_owner` = `"org-a"`, fetches `org-a`'s secret, and the HMAC matches — request passes.
5. `PushHandler#process` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) resolves `stacks` via `Repository.from_github_repo_name("org-b/victim-repo")` and enqueues `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` for `org-b`'s stack, even though the request was never signed by `org-b`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
