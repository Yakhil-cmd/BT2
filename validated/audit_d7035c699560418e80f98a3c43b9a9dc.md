### Title
StatusHandler#process writes statuses to any commit by sha regardless of the webhook's own repository, letting an attacker's repo freeze another stack's deploy pipeline via `blocked?` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits solely by `sha` across the entire `commits` table and writes a GitHub-supplied status onto every match, without checking that the sha belongs to the repository named in the signed webhook payload. Every sibling handler (`push_handler.rb`, `check_suite_handler.rb`, the `pull_request/*` handlers) scopes its side effects through `Handler#stacks`, which resolves `Repository.from_github_repo_name(repository_name)&.stacks`, but `StatusHandler` bypasses this entirely.

### Finding Description
The binding that should hold is: `status.commit.stack.repository.full_name == payload.dig('repository', 'full_name')` (the repository that authenticated/signed the webhook must equal the repository whose commit is being mutated). This binding is not enforced.

`StatusHandler#process` is:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

It queries `Commit` directly by `sha` with no join/filter on `stack.repository`. Compare to the base `Handler` class, which explicitly provides repo-scoping via `stacks`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [2](#0-1) 

`StatusHandler` never calls `stacks`/`repository_name` - the only guard upstream is `WebhooksController#verify_signature`, which validates the HMAC signature against `Shipit.github(organization: repository_owner)`, i.e., it proves the payload was signed for *some* organization the attacker controls (their own), not that the `sha` field inside that payload belongs to that organization's repository:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  head(422) unless verified
end
``` [3](#0-2) 

`repository_owner` is read from `params.dig('repository', 'owner', 'login')`, and the signature is verified against that owner's GitHub App secret - fully satisfiable by an attacker's own repository/App installation. Nothing in this flow re-checks the free-text `sha` field against that same repository.

Downstream, `Commit#create_status_from_github!` writes a `Status` via `statuses.replicate_from_github!`, and `add_status` runs after the write [4](#0-3) . `Status::Common#blocking?` is `!success? && commit.blocking_statuses.include?(context)` [5](#0-4) . `Commit#blocked?` then scans `stack.commits.reachable.newer_than(stack.last_deployed_commit).older_than(self).any?(&:blocking?)` [6](#0-5) , and `Commit#deployable?` requires `!blocked?` [7](#0-6) .

**Exploit flow**: An attacker who owns/controls any GitHub repository configured with a Shipit-recognized GitHub App/org can send `POST /webhooks` with `X-Github-Event: status`, a valid signature for their own org, `repository.full_name` set to their own repo, and `sha` set to the 40-hex sha of an *earlier undeployed* commit that also exists in some victim stack (a sha collision across repos is only needed as a string match in the `commits` table - e.g., shared history via fork/mirror, or an already-known sha the attacker copies from the victim's public commit history if the victim commit was ever pushed/forked into a repo the attacker controls). Because `Commit.where(sha: params.sha)` matches by sha alone, the forged `failure`/error state gets attached to the victim's commit row, flips that commit's `blocking?` to true, and cascades through `blocked?`/`deployable?` for every subsequent undeployed commit in the victim stack - despite the request never being signed for, or associated with, the victim's repository.

Existing guards do not catch this: `verify_signature` only checks the org tied to `repository.owner.login` in the payload against a valid HMAC, which the attacker satisfies for their own org; `drop_unhandled_event` and the `ExplicitParameters` schema for `StatusHandler` only validate presence/type of `sha`/`state`, not repository ownership of the sha; and no model validation on `Status`/`Commit` cross-checks the status's originating repository against the commit's stack.

### Impact Explanation
This is an unauthorized state mutation of another tenant's stack: CI/status state ("blocking" flag) is written into a victim stack's commit history by a request authenticated only for the attacker's own, unrelated repository. The downstream effect is that `Commit#deployable?`/`#blocked?` for every later undeployed commit in the victim's continuous-delivery pipeline flips to false, silently halting deploys for a stack the attacker has no relationship to and no privilege over. This matches "a payload for one repository mutating another's stack, commit ... " in the Critical impact category. It is repeatable against any stack whose commits table contains a sha that also appears (or that the attacker can otherwise place) under the attacker's own controlled repository name in the payload, and it costs the attacker nothing beyond running/controlling a repository and firing one signed webhook.

### Likelihood Explanation
Preconditions: the victim stack must have `blocking_statuses` configured (non-empty) so `blocked?` actually scans; the attacker needs a repository with an active GitHub App/webhook integration recognized by `Shipit.github(organization:)` (any onboarded org qualifies, not necessarily privileged); and the attacker needs the victim commit's sha, which for shared history (forks, cross-repo cherry-picks, mirrors) is trivially obtainable from public GitHub data. The cost is a single unauthenticated-to-the-victim HTTP POST. This is a pure code defect (missing repo-scoping specific to `StatusHandler`) rather than a theoretical construct - every sibling handler enforces the check that this one omits.

### Recommendation
Scope `StatusHandler#process` through the same repository-bound resolution used by other handlers, e.g., only update commits belonging to stacks returned by `stacks` (derived from `payload.dig('repository', 'full_name')`):
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This mirrors the pattern in `Handler#stacks`/`push_handler.rb` and ensures a webhook can only mutate commits within stacks tied to the repository it was actually signed for.

### Proof of Concept
Minitest plan (models/controller level, no live GitHub):
1. Fixtures: create two repositories/stacks, `victim_stack` (repository `victim/repo`, `blocking_statuses: ['ci/required']`) and `attacker_stack` (repository `attacker/repo`).
2. Create `victim_commit_older` in `victim_stack` with `sha: 'deadbeef...'` and a passing status for context `ci/required` (so it currently is not blocking).
3. Create `victim_commit_newer` in `victim_stack`, newer than `victim_commit_older`, with a passing/pending status.
4. Assert baseline: `refute victim_commit_newer.blocked?` and `assert victim_commit_newer.deployable?` (with appropriate success status).
5. Stub `GithubHook#verify_signature`/`verify_webhook_signature` to return true (as in `test/controllers/webhooks_controller_test.rb`), and POST to `/webhooks` with `X-Github-Event: status`, payload `{ "repository" => { "full_name" => "attacker/repo", "owner" => { "login" => "attacker" } }, "sha" => victim_commit_older.sha, "state" => "failure", "context" => "ci/required" }`.
6. Reload `victim_commit_older`; assert `victim_commit_older.blocking?` is now true even though the payload's `repository.full_name` (`attacker/repo`) does not equal `victim_stack.repository.full_name` (`victim/repo`) - explicit equality check: `assert_not_equal payload_repo_full_name, victim_stack.repository.full_name` followed by `assert victim_commit_older.reload.blocking?`.
7. Reload `victim_commit_newer`; assert `refute victim_commit_newer.deployable?` and `assert victim_commit_newer.blocked?`, proving the victim stack's CD pipeline was frozen by a webhook signed only for `attacker/repo`.
