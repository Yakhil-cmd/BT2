### Title
`OpenedHandler#provision?` fails to gate `allow_with_label`/`prevent_with_label` behaviors on `review_stacks_enabled`, allowing labeled provisioning even when review stacks are disabled - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`provision?` intends `review_stacks_enabled` to be a master switch for all three provisioning behaviors, but Ruby `&&`/`||` precedence binds `review_stacks_enabled` only to the `allow_all?` clause. If a repository is configured with `review_stacks_enabled = false` and `provisioning_behavior = allow_with_label` (or `prevent_with_label`), an attacker who can label their own pull request can still trigger `ReviewStackAdapter#find_or_create!`, creating an unauthorized stack/review stack.

### Finding Description
The claimed binding: `provision? == (review_stacks_enabled == true) && (provisioning_behavior-specific condition)` for **all** behaviors. The actual code: [1](#0-0) 

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

Due to `&&` binding tighter than `||`, this evaluates as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && label_present) || (prevent_with_label? && !label_present)`

`review_stacks_enabled` is only ANDed with the `allow_all?` term; it does not gate the `allow_with_label?` or `prevent_with_label?` terms at all. Therefore with `review_stacks_enabled = false` and `provisioning_behavior = allow_with_label`, adding the configured label to a PR makes `provision?` return `true` regardless of the disabled master switch, and `OpenedHandler#process` calls `ReviewStackAdapter#find_or_create!` [2](#0-1)  which creates a real `Stack`/`ReviewStack` record and enqueues it for provisioning [3](#0-2) .

The existing test suite only exercises `review_stacks_enabled = false` combined with `allow_all` [4](#0-3) ; there is no test covering `review_stacks_enabled = false` with `allow_with_label`/`prevent_with_label`, confirming the gap was not caught. No other guard (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters`, model validations) checks `review_stacks_enabled` against behavior in combination — `review_stacks_enabled` is a plain boolean column with no cross-field validation in `Shipit::Repository` [5](#0-4) .

Attacker path: attacker opens/owns a PR against a repository whose owner set `review_stacks_enabled=false` but left `provisioning_behavior=allow_with_label` (or configured `prevent_with_label`, where simply not labeling suffices), adds the repository's known/guessed `provisioning_label_name` to their own PR (label names are typically visible in the repo's label list), and sends the `pull_request.opened` webhook (which GitHub sends automatically, or which can be replayed if webhook signing isn't in the attacker's threat exclusion — here we only need the normal GitHub-triggered webhook path). `provision?` returns `true`, and a `ReviewStack` is created/provisioned against the repository owner's intent.

### Impact Explanation
A review stack is created and queued for provisioning for a repository whose administrator explicitly disabled review-stack provisioning (`review_stacks_enabled = false`). This is a record written (a `Stack`/`ReviewStack` and its provisioning queue entry) that the repository owner did not authorize, and depending on the host application's `ProvisioningHandler`, could trigger real infrastructure provisioning and eventually deploy/build execution against untrusted PR branches — matching "an unauthorized deploy" impact category. The blast radius is scoped to repositories that are in this specific misconfigured state (master switch off, behavior still set to a label-based mode); it is repeatable for every PR/label combination on that repository, but does not cross into other tenants' repositories since `repository.from_github_repo_name` scopes lookups strictly to the named repo [6](#0-5) .

### Likelihood Explanation
Requires a specific, non-default repository configuration: `review_stacks_enabled = false` combined with `provisioning_behavior` still set to `allow_with_label` or `prevent_with_label` (a plausible state reachable via independent API/UI toggling of these two columns, as posited in the question, or via the repository settings form which exposes provisioning_behavior and label fields independent of the enabled checkbox [7](#0-6) ). Given that state, the attacker only needs the ability to label their own PR (or omit a label for the `prevent_with_label` case), which is trivial for anyone with write access to a fork/branch that can open PRs and apply labels they control. No secrets or privileged roles required.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates the entire expression, e.g.:
```ruby
def provision?
  return false unless repository.review_stacks_enabled

  repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

### Proof of Concept
Add a minitest in `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` (or a dedicated truth-table test) enumerating `(review_stacks_enabled, provisioning_behavior, label_present)` and asserting `Shipit::Stack.count` only increases for `review_stacks_enabled == true && provisioning_behavior == allow_all`, or the respective label conditions when enabled — and explicitly asserting **no** stack is created for `review_stacks_enabled: false, behavior: :allow_with_label, label: present` and `review_stacks_enabled: false, behavior: :prevent_with_label, label: absent`:

```ruby
test "does not create stacks when review_stacks_enabled is false, even with allow_with_label + label present" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:, provisioning_enabled: false, behavior: :allow_with_label, label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Running this against the current implementation demonstrates `Shipit::Stack.count` increases by 1 despite `review_stacks_enabled = false`, proving the OR-chain fails to bind the master switch across all provisioning behaviors.
