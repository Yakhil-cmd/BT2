### Title
Webhook signature is validated against an attacker-chosen organization while the write target is taken from an unverified `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification based on an attacker-controlled field in the JSON body (`repository.owner.login`), but the code path that actually mutates state (`PushHandler`/`Handler#stacks`) resolves the target `Repository`/`Stack` from a *different* field in the same body (`repository.full_name`). Because these two fields are never checked for consistency, an actor who legitimately controls (and thus knows the `webhook_secret` for) one organization configured in Shipit can forge a signature that validates under their own organization's secret while pointing the payload's `repository.full_name` at a completely different, victim organization's stack.

### Finding Description
`verify_signature` computes the organization used to pick the verification secret directly from request-controlled JSON: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` returns a `GithubApp`/config object holding that specific organization's `webhook_secret`, and `verify_webhook_signature` HMACs the raw body with it: [3](#0-2) 

Once verification passes, the full raw JSON body is dispatched unchanged to the event handler: [4](#0-3) 

But the handler resolves the actual `Repository`/`Stack` to act on from a *different* JSON field, `repository.full_name`, with no cross-check against the `repository.owner.login` used for signing: [5](#0-4) [6](#0-5) 

`PushHandler#process` then triggers a real sync against whatever `Stack` was resolved from `full_name`, using `params.after` (attacker-supplied) as the expected head SHA: [7](#0-6) 

The binding that should hold is: **organization whose secret authenticated the request == organization that owns the repository/stack being written to**. Because `repository_owner` (used to select the secret) and `repository.full_name` (used to select the write target) are independent, attacker-controlled fields in the same unsigned-at-the-field-level JSON body, this binding is not enforced. An attacker who administers (and therefore knows the webhook secret of) one org's Shipit GitHub App installation - call it `attacker-org` - can:
1. Build a JSON body with `repository.owner.login = "attacker-org"` and `repository.full_name = "victim-org/victim-repo"`, `ref`, and `after` set to an SHA of their choosing.
2. Sign the raw body with `attacker-org`'s `webhook_secret` and set it as `X-Hub-Signature`.
3. POST to `/webhooks`. `verify_signature` looks up `Shipit.github(organization: "attacker-org")` and validates successfully because the attacker knows that secret.
4. `Shipit::Webhooks.for_event('push').each { |handler| handler.call(params) }` runs `PushHandler`, which uses `repository.full_name` ("victim-org/victim-repo") to find the real `Repository`/`Stack` and calls `stack.sync_github(expected_head_sha: params.after)`, using the *victim's* configured GitHub App/API credentials (via `stack.github_api`, resolved from the victim's own `owner`, not from the attacker's org).

### Impact Explanation
This lets an attacker who is not a member of, and has no write access to, the victim organization/repository force a `GithubSyncJob` to run against the victim stack with an attacker-chosen `expected_head_sha`. `GithubSyncJob` fetches and appends commits from GitHub for the victim repo up to that SHA and, if new commits are appended, can feed continuous-deployment logic on the victim stack (`Stack#lock_reverted_commits!`, `CacheDeploySpecJob`, and downstream continuous delivery). This is a cross-repository/cross-organization write triggered by credentials scoped to a different organization - an authentication/authorization boundary bypass that can lead to an unauthorized deploy pipeline action on a repository the attacker does not control.

### Likelihood Explanation
Requires the attacker to be a legitimate administrator (or holder of the `webhook_secret`) for at least one organization configured in this Shipit instance's `github:` config - a scenario explicitly supported by the multi-org configuration format shown in `config/secrets.development.shopify.yml`. No GitHub App private key, `GITHUB_TOKEN`, `ApiClient` token, or session on the victim's side is needed; only knowledge of one's own org's webhook secret is required, which is inherent to being an org's GitHub App administrator. This is a plausible, low-privilege attacker path in any deployment supporting more than one configured GitHub organization.

### Recommendation
After signature verification, validate that the payload's `repository.full_name` (and `repository.owner.login`) belongs to the same organization whose secret was used to verify the signature (i.e., `repository_name.split('/').first == repository_owner`), rejecting the webhook with 422 otherwise. Do not let a handler resolve write targets from a field that isn't cross-checked against the value used to select verification credentials.

### Proof of Concept
1. Configure two orgs in `config/secrets.yml`: `attacker-org` (secret known to attacker) and `victim-org` (has a Stack tracking `victim-org/victim-repo`).
2. Craft body: `{"ref":"refs/heads/main","after":"<attacker-chosen sha>","repository":{"owner":{"login":"attacker-org"},"full_name":"victim-org/victim-repo"}}`.
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org secret, body)>`.
4. POST to `WebhooksController#create` with `X-Github-Event: push`.
5. Observe `verify_signature` passes (uses attacker-org's secret via `repository_owner`), then `PushHandler` resolves and syncs `victim-org/victim-repo`'s Stack via `Repository.from_github_repo_name` and `Handler#repository_name` reading `full_name` — i.e., [5](#0-4)  is invoked against a stack outside the authenticating organization.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
