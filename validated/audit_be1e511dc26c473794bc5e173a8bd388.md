### Title
Webhook signature verified against attacker's org while `pull_request` handlers act on a victim repository named via `repository.full_name` - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/pull_request/edited_handler.rb)

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and thus the HMAC secret) to validate the request using `repository.owner.login` from the untrusted payload, but the `pull_request` handlers (e.g. `EditedHandler`) resolve the target `Repository`/`Stack` using the independent `repository.full_name` field. Because these two fields are never cross-checked, an attacker who owns any GitHub organization that is configured in Shipit without a `webhook_secret` can forge a `pull_request`/`edited` payload whose `repository.owner.login` points to their own no-secret org (making `verify_webhook_signature` return `true` unconditionally) while `repository.full_name` names an arbitrary victim repository, causing the handler to mutate that victim's `PullRequest`/stack record.

### Finding Description
The broken binding is the implicit invariant: `repository_owner used to verify signature == organization owning repository.full_name used by the handler`. These are never asserted equal.

- `Shipit::WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-30) picks the app config via `Shipit.github(organization: repository_owner)`, where `repository_owner` is `params.dig('repository','owner','login') || params.dig('organization','login')` (line 59-62) — fully attacker-controlled JSON.
- `GitHubApp#verify_webhook_signature` (lib/shipit/github_app.rb:76-83) does `return true unless webhook_secret` — if the resolved org's Shipit config has no `webhook_secret` configured, **any** payload, with or without a valid `X-Hub-Signature`, is accepted. [1](#0-0) [2](#0-1) 

- Once verification passes, `create` dispatches to all `pull_request` handlers, including `Shipit::Webhooks::Handlers::PullRequest::EditedHandler`, which resolves the target repository using a completely separate field: `Shipit::Repository.from_github_repo_name(params.repository.full_name)`, then looks up `Shipit::PullRequest` by `number` scoped to that repository's stacks, and calls `pull_request.update(github_pull_request: params.pull_request)` if found. [3](#0-2) 

Exploit: attacker registers/owns a GitHub org `attacker-org` that has been added to Shipit's configuration but left without a `webhook_secret` (a legitimate, unprivileged, low-cost misconfiguration state that Shipit permits — many orgs onboarded without secrets, or an attacker convinces an operator to add a public/no-secret sandbox org). Attacker POSTs to `/webhooks` with header `X-Github-Event: pull_request` and a JSON body:
```json
{
  "action": "edited",
  "number": 42,
  "pull_request": { "id": 1, "number": 42, "url": "...", "title": "pwn", "state": "open",
    "additions": 0, "deletions": 0,
    "head": {"sha":"...", "ref":"..."},
    "user": {"login":"attacker"}, "assignees": [], "labels": [] },
  "repository": { "owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo" },
  "sender": {"login":"attacker"}
}
```
`verify_signature` resolves `repository_owner` = `attacker-org`, finds its `GitHubApp` config has no secret, and returns `true` regardless of the `X-Hub-Signature` header (attacker can even omit it). `EditedHandler` then resolves `repository` via `full_name = "victim-org/victim-repo"`, finds the victim's `PullRequest` row for PR #42, and overwrites `github_pull_request` with attacker-supplied JSON — a write to a repository/stack the attacker never authenticated against.

Existing guards do not catch this:
- `drop_unhandled_event` only checks event name presence, not payload consistency.
- `ExplicitParameters` schema (`params do ... end` in `EditedHandler`) validates types/presence of `repository.full_name` but never compares it to the org used for signature verification.
- `verify_signature`'s `GithubOrganizationUnknown` rescue only fires if the org name in the payload isn't configured at all — it does nothing to prevent using a *different but valid, no-secret* org as the verification target while acting on another org's repository.

### Impact Explanation
A single unsigned/forged HTTP request lets an attacker write attacker-controlled `github_pull_request` JSON (title, state, sha, ref, assignees, labels) onto a victim's `Shipit::PullRequest` record tied to a completely different repository/stack, as long as any Shipit-configured org lacks a `webhook_secret`. This is a cross-tenant/cross-repository state-manipulation primitive matching the "Critical" category ("a payload for one repository mutating another's stack/commit/task"). It is repeatable against any repository whose full name the attacker knows, for every `pull_request` sub-handler (`OpenedHandler`, `ClosedHandler`, `LabeledHandler`, etc.), since all of them independently trust `params.repository.full_name` while the shared signature check trusts only `repository.owner.login`.

### Likelihood Explanation
Precondition: at least one org configured in `Shipit.github_teams`/app config without a `webhook_secret`. This is a realistic deployment/config gap (e.g., a sandbox/demo org, or migration in progress) rather than a hypothetical; the code even ships `return true unless webhook_secret` as a deliberate default-permissive fallback. Attacker cost is a single unauthenticated HTTP POST with no valid GitHub credentials, no session, no API token — fully within the stated unprivileged attacker capability. Fully repeatable and scriptable against arbitrary victim repos/PR numbers.

### Recommendation
In `WebhooksController#verify_signature`, derive the verifying organization consistently with the org actually referenced by `repository.full_name` (not the separate, independently attacker-suppliable `owner.login`/`organization.login` field), or explicitly assert `repository.full_name.split('/').first == repository_owner` before dispatch. Additionally, do not treat a blank `webhook_secret` as automatic verification success in production; require an explicit "unsecured" opt-in per org, and log/alert loudly when accepting unsigned webhooks.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` style, no live GitHub):
1. Configure two orgs in test secrets: `victim-org` (with `webhook_secret: "s3cr3t"`) and `attacker-org` (no `webhook_secret`, matching `test/dummy/config/secrets_double_github_app.yml` pattern).
2. Create `victim_repo = Shipit::Repository.create!(owner: "victim-org", name: "victim-repo", ...)`, a `Stack` for it, and a `Shipit::PullRequest` with `number: 42` and some baseline `github_pull_request` value.
3. POST to `/webhooks` with header `X-Github-Event: pull_request`, no valid `X-Hub-Signature` for `victim-org`'s secret (or an arbitrary/garbage signature), and body `action: "edited"`, `repository: {owner: {login: "attacker-org"}, full_name: "victim-org/victim-repo"}`, `number: 42`, forged `pull_request` payload.
4. Assert response is `200 OK` (not `422`), proving signature verification passed via `attacker-org`'s missing secret.
5. Reload `pull_request` from DB and assert `pull_request.github_pull_request` now equals the attacker-forged payload — i.e., assert the equality `repository_owner (verified) == "attacker-org"` while `pull_request.stack.repository.owner == "victim-org"` still holds, demonstrating the two never matched yet the write succeeded.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
