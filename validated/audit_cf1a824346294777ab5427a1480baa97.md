### Title
Hookify frontmatter parser silently downgrades `action: block` rules to `warn` via naive `split('---', 2)` - (File: `plugins/hookify/core/config_loader.py`)

### Summary
`extract_frontmatter` splits the entire file content on the literal substring `---` using `content.split('---', 2)` instead of parsing line-delimited YAML markers. Any `---` occurring inside a frontmatter value (e.g., a `pattern` field matching a command that legitimately contains `---`, such as diff headers or hyphen sequences) prematurely truncates the frontmatter block, pushing subsequent keys — including `action: block` — into the discarded "message" text. The resulting `Rule` object silently defaults to `action: 'warn'` even though the on-disk file visibly declares `action: block`.

### Finding Description
`extract_frontmatter` (`plugins/hookify/core/config_loader.py:87-195`) does:
```python
parts = content.split('---', 2)
frontmatter_text = parts[1]
message = parts[2].strip()
``` [1](#0-0) 

This treats `---` as a raw substring delimiter across the whole file rather than as line-anchored YAML fence markers. If any line inside the intended frontmatter block (e.g. a `pattern:` value) contains the three-character sequence `---` — which is common in real-world Bash/diff patterns (e.g. unified-diff `--- a/file`, or a pattern like `rm -rf /important --- confirm`) — the second `---` found by `split` terminates the frontmatter region early. All keys after that point, including `action: block`, end up inside `message` (parts[2]) and are never parsed into the frontmatter dict.

`Rule.from_dict` then computes `action=frontmatter.get('action', 'warn')` [2](#0-1)  — since `action` key is missing from the truncated dict, it silently defaults to `'warn'`.

`load_rule_file` only rejects the file if `frontmatter` is completely empty [3](#0-2) ; a partially-parsed dict (with `name`, `enabled`, `event`, truncated `pattern`) still passes this check, so the malformed rule is silently loaded and enforced with the wrong action.

Reachability: `.claude/hookify.*.local.md` files are ordinary repository content (created via `/hookify`, per `plugins/hookify/commands/hookify.md`, or committed directly by any repo contributor). `pretooluse.py`/`stop.py` load these files via `load_rules()` → `load_rule_file()` → `extract_frontmatter()` on every Bash/Edit/Write/Stop event [4](#0-3) , and `RuleEngine.evaluate_rules` treats `action == 'block'` as blocking and anything else (including the silently-downgraded `'warn'`) as non-blocking, allowing the operation to proceed [5](#0-4) . No validation, schema check, or delimiter-integrity check exists anywhere in this path to catch the truncation.

### Impact Explanation
A rule file that a repository maintainer (or `/hookify` itself) authored with `action: block` to stop dangerous operations (e.g., blocking `rm -rf`, force-pushes, secret-file edits) can be silently neutered into a non-blocking `warn` rule purely because its `pattern` value contains the substring `---`. An attacker who can influence rule content (e.g., via a PR adding a "security" hookify rule, or via conversation content fed to `/hookify` that shapes the generated pattern) can craft a rule that *appears* to block a dangerous command in the visible markdown file but is actually parsed as `warn`, letting the dangerous tool call execute unblocked. This breaks the stated invariant that a deny rule must never be parsed into a non-blocking configuration, enabling unauthorized command/file execution that the repo's own security guardrail was supposed to prevent — a genuine trust-boundary bypass with real security impact (e.g., unblocked destructive Bash commands, unblocked edits to sensitive files, or unblocked session termination bypassing "require-tests-before-stop" style guards).

### Likelihood Explanation
Highly feasible and fully deterministic: no privileges beyond normal repo/file access are required, and no timing or race conditions are involved. Any hookify rule author (attacker-controlled repo content, or a maintainer/LLM auto-generating a rule) that writes a `pattern`, `message`, or other multi-word frontmatter value containing `---` will trigger this every time. This is not a hypothetical edge case — diff-related patterns, markdown horizontal rules, and simple triple-hyphen strings are common in text a security rule might legitimately want to match. Repeatable via a straightforward unit test on `extract_frontmatter`.

### Recommendation
Rewrite `extract_frontmatter` to parse frontmatter delimiters strictly by line (e.g., only treat a line that is exactly `---` — optionally with trailing whitespace — as a fence marker), for example using `re.match(r'^---\s*$', line)` when scanning lines, or using a proper YAML parser (`yaml.safe_load`) bounded by the first and second lines matching `^---$`. Additionally, `load_rule_file` should reject/quarantine rule files where a `block`-labeled section is unexpectedly absent from the parsed dict, and ideally validate `action` is one of the known enum values with a fail-closed (not fail-open-to-warn) default when the file text visibly references `action: block` but parsing produced no such key (i.e., detect and reject truncation rather than silently defaulting).

### Proof of Concept
Unit test targeting `plugins/hookify/core/config_loader.py`:
```python
from hookify.core.config_loader import extract_frontmatter, Rule

content = """---
name: block-dangerous-rm
enabled: true
event: bash
pattern: rm -rf /important --- confirm delete
action: block
---

Blocked dangerous rm command!
"""

frontmatter, message = extract_frontmatter(content)
rule = Rule.from_dict(frontmatter, message)

# The file visibly declares action: block, but due to the '---' inside the
# pattern value, split('---', 2) truncates frontmatter before reaching
# 'action: block', so it is silently dropped.
assert 'action' not in frontmatter          # BUG: action key lost
assert rule.action == 'warn'                # BUG: block silently downgraded to warn
```
Integration-level PoC: place the same content in `.claude/hookify.block-dangerous-rm.local.md` in a test repo, invoke `plugins/hookify/hooks/pretooluse.py` with a Bash `tool_input.command` matching the truncated pattern (`rm -rf /important`), and assert the hook output does NOT contain `"permissionDecision": "deny"` (i.e., the dangerous command is allowed to proceed despite the file declaring `action: block`).
