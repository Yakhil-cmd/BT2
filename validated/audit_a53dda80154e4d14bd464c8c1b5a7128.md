### Title
Tokens transferred directly to the Pool or Controller are permanently stranded — there is no sweep path and no book entry can ever pay them out - (File: contracts/pool/src/ops/repay.rs)

### Summary
The analog of the Symmio finding is real in XOXNO Lending's own shape: any token balance held by a Pool or the Controller above what the accounting books track (a "donation", an accidental direct `transfer`, or a residual Controller balance) is permanently locked. The Pool pays out only amounts derived from its `cash`/shares books, and the Controller's refund helper explicitly preserves its pre-existing balance. No entrypoint — permissionless or owner-gated — can move the surplus out.

### Finding Description
The Pool is the single physical custodian for all `(hub_id, asset)` spoke books over one shared token balance. Its `cash` field is pure bookkeeping, and the Pool README states tokens are credited "on the controller's word, without verifying the transfer" — the only reconciliation against `token.balance()` is inside `flash_loan` [1](#0-0) . A test in the audit suite pins the consequence directly: "An unsolicited donation belongs to no market's cash book" and sits in custody forever on top of the booked amounts [2](#0-1) .

Every outbound leg is bounded by the book or by a measured inbound amount:

- `withdraw`/`borrow` pay out only booked `cash` via `require_reserves`/`debit_cash` [3](#0-2) .
- `repay` refunds only `amount - net_repay`, i.e. the declared overpayment — never custody surplus [4](#0-3) .
- `recapitalize` refunds only `amount - applied` where `applied ≤ backing_shortfall` [5](#0-4) .
- `claim_revenue` burns `revenue` shares — book entries; a donation mints no shares and cannot be claimed even by the owner [6](#0-5) .

On the Controller side, `refund_controller_balance_delta` refunds only the balance *increase* measured during the current call and deliberately preserves any pre-existing balance, so tokens already sitting on the Controller are never forwarded [7](#0-6) . Neither contract exposes a `sweep`/rescue function: the full Pool surface contains no token-recovery entrypoint, and every mutator is `#[only_owner]` where the owner is the Controller itself [8](#0-7) .

This is exactly the Symmio pattern: residual collateral sits in the contract; users cannot retrieve it (it backs no shares and no `cash` entry names them); and admins cannot retrieve it either (revenue claims are share-based, and there is no admin sweep).

### Impact Explanation
Permanent freezing of funds. Any token amount sent directly to a Pool or Controller address — mistaken transfers, fee-on-transfer residue, or leftovers pushed by an integrated contract — is locked forever. Because custody exceeds booked `cash`, the surplus cannot be claimed by suppliers (claims are share/index based), cannot be claimed by revenue, and cannot be swept by the owner. The funds contribute nothing to the protocol and are unrecoverable by design.

### Likelihood Explanation
The trigger is a single unprivileged `token.transfer(to = pool_or_controller)` — explicitly within the reachable surface (direct token transfers to the pool or controller). On Stellar, SAC `transfer` to a contract is a routine mistake; hub/spoke markets sharing one physical Pool balance make the Pool address a high-traffic deposit target (users who bypass the controller or an integrator that settles against the pool address directly). Each occurrence freezes value permanently and also silently widens the custody/book gap.

### Recommendation
Either add an owner-gated sweep on the Pool (and Controller) that transfers `token.balance - sum(booked cash)` of surplus to the treasury, or add a permissionless `donate`/`recapitalize-anyone` path that converts measured surplus into `cash`/revenue shares so the value is book-claimed rather than inert. At minimum, have `refund_controller_balance_delta`-style flows credit pre-existing Controller balances into a claimable book instead of preserving them forever.

### Proof of Concept
1. User calls `token.transfer(user, pool, X)` directly (no controller involvement).
2. `pool.get_sync_data(hub_asset)` shows `cash` unchanged while `token.balance(pool)` grows by `X` — the test at `tests/test-harness/tests/pool_money_flow_audit.rs:86-96` pins exactly this state.
3. No reachable call frees `X`:
   - `controller.recapitalize(payer, hub_asset, X)` measures only new inbound receipts and refunds `X` — but only from what was actually transferred in this call (`pool/src/ops/recapitalize.rs:52-55`), leaving the earlier donation untouched.
   - `withdraw`/`borrow` revert or under-pay because `require_reserves` reads the `cash` book, not custody.
   - `claim_revenue` burns revenue shares; the donation minted none.
   - For tokens stuck on the Controller, `refund_controller_balance_delta` explicitly skips the pre-existing balance (`controller/src/payments.rs:41-51`) and no sweep exists.
4. `X` remains locked in the contract indefinitely — matching the reported bug class: no user path and no admin path recovers it.

/// Refunds only the controller balance increase since `balance_before`,
/// preserving the pre-existing balance; no-op for a nonpositive delta.
pub(crate) fn refund_controller_balance_delta(
    env: &Env,
    asset: &Address,
    balance_before: i128,
    refund_to: &Address,
) {
    let controller = env.current_contract_address();
    let excess = balance_delta_since(env, asset, &controller, balance_before);
    if excess > 0 {
        token::Client::new(env, asset).transfer(&controller, refund_to, &excess);
    }
