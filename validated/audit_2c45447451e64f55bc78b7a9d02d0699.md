## Analysis

This confirms the multi-organization GitHub App configuration (`Shipit.github_organizations`, `github_app_config`, `TOP_LEVEL_GH_KEYS`) creates a per-organization `webhook_secret`, and that this secret is optional (`docs/setup.md` explicitly says "Webhook secret (optional)"; `config/secrets.development.example.yml` ships with `webhook_secret: # nil`). ### Title
Webhook signature is verified against `repository.owner.login`'s app config while the acted-upon stack is selected from the independent `repository.full_name` field, allowing cross-repository forged pushes when any configured organization has no `webhook_secret` - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` chooses which GitHub App configuration (and thus which `webhook_secret`) to validate the HMAC signature against based on `repository.owner.login` (or `organization.login`) taken from the unauthenticated request body. Once verification passes, `Shipit::Webhooks::Handlers::Handler#stacks` resolves the target repository/stack using an entirely different, independently-attacker-controlled field of the same payload: `repository.full_name`. Because these two fields are never cross-checked, and because `webhook_secret` is documented as optional per organization, any organization onboarded to a multi-org Shipit instance without a configured `webhook_secret` becomes a "skeleton key" organization: an attacker can address the signature check to that no-secret organization while pointing `repository.full_name` at a completely unrelated stack belonging to a different, secret-protected organization, and have the handler act on it.

### Finding Description
- Multi-organization support stores a separate `webhook_secret` per org in `Shipit.github(organization:)` / `github_app_config` (`lib/shipit.rb`).
- `GitHubApp#verify_webhook_signature` explicitly short-circuits to `true` when `webhook_secret` is blank: `return true unless webhook_secret` (`lib/shipit/github_app.rb:76-77`).
- `WebhooksController#verify_signature` picks the app/secret to check purely from `repository_owner`, itself parsed straight out of the unauthenticated JSON body (`repository.owner.login` / `organization.login`) (`webhooks_controller.rb:24-62`).
- The event handlers that actually perform state-changing actions (queue `GithubSyncJob`, archive/unarchive review stacks, etc.) resolve the target `Repository`/`Stack` from `repository.full_name` in the very same body (`handlers/handler.rb:32-38`, `handlers/push_handler.rb`), with no requirement that `full_name`'s owner match `repository_owner`.
- Binding broken: `organization authenticated (repository.owner.login, checked against a possibly-secret-less config) ≠ repository that is written (repository.full_name, unchecked)`. Before the attack, these two fields always come from the same real GitHub-issued payload and are consistent; after a forged request, an attacker sets them independently.
- Exploit precondition: at least one organization configured in `Shipit.github` (multi-org mode) has no `webhook_secret` set — a state the project's own setup documentation calls out as optional and shows as the default (`webhook_secret: # nil`). No credential, token, or private key is required to exploit this; the attacker never needs to know any organization's real secret.

### Impact Explanation
An unauthenticated attacker can POST a forged `push` (or other handled) webhook to `/webhooks` with `repository.owner.login` set to the no-secret-configured organization and `repository.full_name` set to any tracked stack belonging to a different, "secured" organization. This passes signature verification (because the secret-less org's `verify_webhook_signature` trivially returns `true`) and then causes `PushHandler#process` to invoke `stack.sync_github(expected_head_sha: params.after)` against the victim stack, forcing a sync toward an attacker-chosen `after` SHA on a repository/organization the attacker does not own. This is a cross-repository/cross-organization state manipulation via forged webhook — matching the "cross-repository writes" / unauthorized deploy-adjacent impact category, since sync operations feed directly into what commit/SHA a stack considers deployable and can influence subsequent deploy/merge behavior.

### Likelihood Explanation
Likelihood is High only in the specific but explicitly documented and encouraged deployment shape: multi-organization Shipit (`github_app_config`) where an operator leaves `webhook_secret` empty for one org (shown as the default/example value in the repo's own docs and secrets templates) while other configured organizations do have secrets. Any operator following the documented setup for organizations that don't care about a webhook secret (it's marked optional) creates this exposure engine-wide, without needing any additional attacker privilege, session, or token — only network reachability of the public `/webhooks` endpoint.

### Recommendation
- Require the `repository.owner.login` (or `organization.login`) used to select the signing key to also match the owner encoded in `repository.full_name` before dispatching to handlers, rejecting mismatches regardless of signature outcome.
- Do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is blank in multi-organization configurations; either require a secret for every organization or scope any secret-less org strictly to itself so it cannot be used to authorize payloads referencing other organizations' repositories.
- Consider validating that the webhook payload's `repository.owner.login` is consistent with `repository.full_name`'s owner segment as a general defense-in-depth check in `Handler#repository_name` / `stacks`.

### Proof of Concept
Preconditions: Shipit configured with multi-org `Shipit.github` where organization `no-secret-org` has `webhook_secret: nil`, and a tracked stack exists for `victim-org/victim-repo`.

```
POST /webhooks HTTP/1.1
X-Github-Event: push
Content-Type: application/json
(no X-Hub-Signature required / any value works)

{
  "ref": "refs/heads/master",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "no-secret-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
- `verify_signature` computes `repository_owner` = `"no-secret-org"`, calls `Shipit.github(organization: "no-secret-org")`, whose `verify_webhook_signature` returns `true` unconditionally (no secret configured).
- `create` re-parses the body and dispatches to `PushHandler`, whose `repository_name` (via `Handler#repository_name`) reads `"victim-org/victim-repo"` from the same body, finds the real `Stack`, and calls `stack.sync_github(expected_head_sha: "deadbeef...")` — a forged sync of an unrelated, secret-protected organization's stack.     def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

      head(422) unless verified

      Rails.logger.info([

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
