Analysis:

`native_write_module_event_to_store` uses `context.stack_frames(1)` to fetch the direct Move caller of `write_module_event_to_store`, and checks that this caller's module id matches the module id encoded in the event's `struct_tag` (the type `T`) [1](#0-0) . The public entry point `aptos_framework::event::emit<T>` is a regular (non-inline) function that directly calls the native `write_module_event_to_store<T>` [2](#0-1) ; since natives don't push their own Move call frame, `stack_frames(1)` from inside the native resolves to the actual bytecode frame of whichever function called `emit<T>`, i.e., the module whose code executed the `emit` call — regardless of how that call was reached (direct call, or via a dynamic-dispatch `CallFunction` tail-call into a target function). Move's VM always pushes a genuine call frame per actual function invocation (including dispatch targets used by `dispatchable_fungible_asset`/`account_abstraction` natives), so the frame reported is bound to the code that is truly executing, not to metadata an attacker can forge [3](#0-2) [4](#0-3) . This is the same pattern used and documented for `init::get_caller_address_and_module_id`, which relies on identical direct-caller semantics [5](#0-4) .

For an attacker's module B to make the emitting identity resolve to a *different* module A, B would need module A's own code to be the frame that directly calls `emit<T>` with a `T` defined in A — but that is precisely the correct/intended behavior (A is genuinely emitting its own event), not spoofing. There is no path by which a proxy/delegate frame (module B) can cause the native to record module A's identity while B's code is actually the one invoking `emit`, because the check compares the *real* calling frame's module id (from the interpreter's frame stack) against the type's module id, and both are derived from ground-truth VM state, not attacker-supplied data.

Separately, and dispositively per the review's boundary conditions: this code path is internal Move VM/native execution logic invoked during contract execution, not part of the transaction-admission boundary (mempool, vm-validator, authenticator, sender/signer/fee-payer binding). It has no bearing on sender, secondary-signer, fee-payer, sequence number, expiry, or chain-id binding at admission time, so even if a defect existed here it would fall outside the required admission-impact scope.

## F. Dynamic dispatch / control transfer (`NativeResult::CallFunction`)

Natives that, instead of returning a value, instruct the VM to call into another Move function with the remaining arguments. The dispatch target is encoded in the last argument (a `FunctionInfo` struct that the native unpacks):

- `dispatchable_fungible_asset::dispatchable_withdraw`
- `dispatchable_fungible_asset::dispatchable_deposit`
- `dispatchable_fungible_asset::dispatchable_derived_balance`
- `dispatchable_fungible_asset::dispatchable_derived_supply`
- `account_abstraction::dispatchable_authenticate`

All five share a single Rust implementation (`native_dispatch`) that:
1. Pops the `FunctionInfo` argument to extract `(ModuleId, Identifier)`.
2. Checks (via `traversal_context().check_is_special_or_visited` or `legacy_check_visited`) that the target module has already been loaded *in this transaction*. This is a precondition to dispatch — gas for the dispatch target must have been charged earlier via `function_info::load_function_impl`.
3. Returns `SafeNativeError::FunctionDispatch { module, func, ty_args, args }`, which `make_native` translates to `NativeResult::CallFunction`.

**Trickiness**: Paranoid-mode stack typing requires the *argument order* of the native to exactly match the target Move function (except for the trailing `FunctionInfo` consumed by the native). This is an unwritten ABI between native and Move signature that the new VM must preserve.

## I. Caller-frame introspection (interpreter peek)

Natives that examine their caller's stack frame:

- `event::write_module_event_to_store` — `context.stack_frames(1)` and asserts that the caller's module ID matches the *struct's* module ID, preventing cross-module event emission. Aborts if the caller is a script.
- `debug::native_stack_trace`, `debug::print_stack_trace` (and the `_old_` legacy variants) — `context.print_stack_trace(&mut s)` for human-readable traces.

**Trickiness**: `event::write_module_event_to_store` makes a *security-relevant* decision based on caller introspection. The new VM must be able to give natives a reliable view of the caller without leaking implementation details of the new calling convention.
