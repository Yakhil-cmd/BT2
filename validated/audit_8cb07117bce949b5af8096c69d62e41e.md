### Title
Cross-organization webhook forgery via per-organization signature bypass - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In multi-organization Shipit deployments, the webhook signature check selects which GitHub App's `webhook_secret` to validate against based on an attacker-controlled field of the *unauthenticated* payload (`repository.owner.login` / `organization.login`), rather than the repository the event actually targets. Because `verify_webhook_signature` unconditionally returns `true` when the selected organization has no `webhook_secret` configured (a documented, supported setting), an attacker can bind a forged event to any configured organization that has no secret while using the payload's `repository.full_name` to write to a stack belonging to a *different*, fully-secured organization.

### Finding Description
`WebhooksController#verify_signature` derives the organization used to pick the verifying `GitHubApp` config purely from the request body, before the signature has been validated: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` then short-circuits to `true` whenever that organization's config has no `webhook_secret` set: [3](#0-2) 

Shipit explicitly supports configuring multiple GitHub organizations, each with its own independent `webhook_secret`, exactly as shown in the test fixture `secrets_double_github_app.yml` (two orgs, each with its own `webhook_secret`), and the setup docs and example secrets file document `webhook_secret` as an optional field that can be left `nil`: [4](#0-3) [5](#0-4) 

Once `verify_signature` passes (which it trivially does for the org that has no secret configured), `WebhooksController#create` dispatches the *entire* raw JSON body — not scoped to the "authenticating" organization — to the registered handlers: [6](#0-5) 

This breaks the intended binding: "the organization whose secret authenticated the request" == "the repository/organization that is actually written." The `repository.owner.login` field used to pick the signing key and the `repository.full_name` field used by handlers (e.g. push/status/check_suite handlers, confirmed to key off `full_name`) are independent, attacker-controlled fields inside the same unauthenticated payload. An attacker can therefore set `owner.login`/`organization.login` to an organization configured on the instance with no `webhook_secret`, while setting `repository.full_name` to a stack under a different, fully-secured organization, and the forged event will be processed as if it legitimately came from GitHub for that secured repository.

### Impact Explanation
This allows an unauthenticated attacker to inject arbitrary `push`, `status`, or `check_suite` events for a securely-configured organization's stacks by riding on a co-configured organization that has no webhook secret. Forged `status`/`check_suite` events can flip commit CI status used to gate deploy eligibility, and forged `push` events enqueue `GithubSyncJob` for the target stack — enabling deploy-gating bypass / unauthorized state changes on a repository the attacker has no access to. This matches the Critical category "unauthorized deploy, rollback."

### Likelihood Explanation
Requires a Shipit instance configured with more than one GitHub organization where at least one configured organization intentionally omits `webhook_secret` (an explicitly documented, supported configuration in this engine, not a host misconfiguration). Given this precondition, exploitation requires only a single unauthenticated HTTP POST with a crafted JSON body — no credentials, tokens, or prior session needed.

### Recommendation
Bind signature verification to the same identity that is subsequently acted upon: verify the HMAC using the secret belonging to the organization that owns `repository.full_name` (not a separately-derived `owner.login`/`organization.login` field), and reject the webhook if the two disagree. Consider also refusing verification (rather than defaulting to `true`) when an organization's `webhook_secret` is unset in multi-org configurations, or require all configured organizations to define a secret once any organization does.

### Proof of Concept
1. Configure Shipit with two organizations: `SecureOrg` (has `webhook_secret` set, owns a monitored stack) and `OpenOrg` (no `webhook_secret`, as permitted by the documented config schema).
2. POST to `/github/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<sha of SecureOrg/app commit>",
  "state": "success",
  "context": "ci",
  "repository": { "full_name": "SecureOrg/app", "owner": { "login": "OpenOrg" } }
}
```
3. `repository_owner` resolves to `OpenOrg`; `Shipit.github(organization: "OpenOrg").verify_webhook_signature` returns `true` unconditionally because `OpenOrg` has no `webhook_secret`.
4. `create` parses the same raw body and dispatches to the `status` handler, which updates the commit status for `SecureOrg/app` — a forged status for a repository the attacker never authenticated against.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
