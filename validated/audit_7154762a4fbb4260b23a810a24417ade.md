Based on my investigation, the closest analog in `polkadot-sdk` to the AlephZeroAMM farm contract is `pallet-asset-rewards` (`substrate/frame/asset-rewards/src/lib.rs`), which implements the same "Synthetix StakingRewards"-style JIT reward algorithm described in the report. However, the specific bug class in the report does not transfer to this pallet.

### Why the analog does not hold

**Root cause of the original bug**: the AlephZeroAMM farm contract allows a pool to be configured with a `Vec<AccountId>` of `reward_tokens` that can contain **duplicate token addresses** (e.g. `[WOOD, WOOD]`). Because rewards are tracked per-index in this vector but the "undistributed" withdrawal calculation subtracts accumulated rewards keyed by token address (not index), a duplicate entry causes one index's accumulated (but unclaimed) rewards to be excluded from the "distributed" accounting, letting the owner reclaim tokens users have already earned.

**Why `pallet-asset-rewards` cannot exhibit this**:

1. Each `PoolInfo` has exactly one `reward_asset_id: AssetId` field, not a vector of reward-token identifiers, so there is no possibility of a duplicate-index accounting mismatch — there's nothing to key by index at all. [1](#0-0) 

2. The admin-only reclaim path, `cleanup_pool`, explicitly guards against any outstanding stakers before returning the pool's reward-asset balance to the admin: it checks `PoolStakers::<T>::iter_key_prefix(pool_id).next().is_none()` and errors with `NonEmptyPool` otherwise. A staker's `PoolStakers` entry is only removed once both their staked `amount` and unclaimed `rewards` are zero (see `unstake` and `harvest_rewards`), so as long as any staker has unclaimed rewards, `cleanup_pool` cannot execute and the admin cannot withdraw the pool's reward-asset balance. [2](#0-1) [3](#0-2) [4](#0-3) 

3. When `total_tokens_staked` is zero (the only case in which `cleanup_pool`'s precondition can hold), `reward_per_token` returns the already-stored value unchanged rather than continuing to accrue, so there is no way for further "hidden" unclaimed rewards to accumulate between the last staker leaving and cleanup. [5](#0-4) 

I also checked `pallet-nomination-pools`' `RewardPool`, which similarly tracks a single reward currency per pool via counters (`last_recorded_reward_counter`, `total_rewards_claimed`, `total_commission_claimed`) rather than a vector of token identifiers, and admin/root access to excess reward-account funds was deliberately restricted to the pool owner (and only in the ED-reduction case) per [6](#0-5) , which is a different, already-mitigated concern unrelated to duplicate-token accounting.

Since the vulnerable pattern requires a caller-supplied vector of reward-token identifiers with no duplicate check, and no FRAME reward-distribution pallet in this codebase uses such a structure, there is no reachable analog.

		/// Cleanup a pool.
		///
		/// Origin must be the pool admin.
		///
		/// Cleanup storage, release any associated storage cost and return the remaining reward
		/// tokens to the admin.
		#[pallet::call_index(8)]
		pub fn cleanup_pool(origin: OriginFor<T>, pool_id: PoolId) -> DispatchResult {
			let who = ensure_signed(origin)?;

			let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
			ensure!(pool_info.admin == who, BadOrigin);

			let stakers = PoolStakers::<T>::iter_key_prefix(pool_id).next();
			ensure!(stakers.is_none(), Error::<T>::NonEmptyPool);

			let pool_balance = T::Assets::reducible_balance(
				pool_info.reward_asset_id.clone(),
				&pool_info.account,
				Preservation::Expendable,
				Fortitude::Polite,
			);
			T::Assets::transfer(
				pool_info.reward_asset_id,
				&pool_info.account,
				&pool_info.admin,
				pool_balance,
				Preservation::Expendable,
			)?;

			if let Some((who, cost)) = PoolCost::<T>::take(pool_id) {
				T::Consideration::drop(cost, &who)?;
			}

			Pools::<T>::remove(pool_id);

			Self::deposit_event(Event::PoolCleanedUp { pool_id });

			Ok(())
		}
