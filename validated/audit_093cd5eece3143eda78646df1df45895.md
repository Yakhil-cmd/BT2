### Title
Cross-organization webhook confusion: signature verified against `repository.owner.login`'s app while the actual write target is selected by `repository.full_name` - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App/organization secret to authenticate a webhook with by reading `repository.owner.login` (or `organization.login`) out of the untrusted JSON body, but the handler that actually acts on the payload resolves the target repository/stack from a *different* field, `repository.full_name`. In a multi-organization Shipit deployment (explicitly supported, see `docs/setup.md` "Using Multiple Github Applications"), nothing ties these two fields together, so a party who legitimately controls one configured organization's GitHub App (and therefore knows its `webhook_secret`) can forge a signed payload whose `repository.full_name` names a stack that belongs to a *different* configured organization.

### Finding Description
`repository_owner` is used purely to select the verification key: [1](#0-0) 
That key is looked up via `Shipit.github(organization: repository_owner)` and the raw body is HMAC-verified against that specific organization's `webhook_secret`: [2](#0-1) [3](#0-2) 

Once the signature check passes, the *entire raw params hash* — not just the fields that were used for org selection — is dispatched to handlers: [4](#0-3) 

Handlers, however, resolve the target `Repository`/`Stack` using a separate field, `repository.full_name`, with no cross-check against `repository.owner.login`: [5](#0-4) 

The `push` handler then acts on whatever stacks that lookup returns, triggering `sync_github`/`GithubSyncJob` for arbitrary matched stacks: [6](#0-5) 

Configuration confirms multiple independent organizations, each with their own `webhook_secret`, can coexist in one Shipit instance: [7](#0-6) 

This is the same class of bug as the external report: a value (`allowed[this][virtualExchangeAddress]`) is written based on one piece of state while a different, unguarded piece of state is what should have gated the operation, letting a value/binding intended to be scoped to one context leak into another. Here, the "scope" is organization/app-secret, and the "leak" is that the field which selects the verification secret (`repository.owner.login`) is decoupled from the field that selects the write target (`repository.full_name`).

The equality that should hold but is never checked:
`organization used to verify signature (repository.owner.login)` == `organization implied by the repository actually written to (repository.full_name)`.

Before the attack: an org's webhook secret only authorizes webhooks whose payload content genuinely originates from GitHub for that org's repos (GitHub itself always sends consistent `owner.login`/`full_name` pairs). After the attack: an attacker owning Org A's GitHub App can craft an arbitrary payload with `repository.owner.login = "OrgA"` (to select Org A's secret) and `repository.full_name = "OrgB/victim-repo"` (to target another tenant's stack), sign it with Org A's own secret, and have Shipit accept it as if it were a genuine event for Org B's repository.

### Impact Explanation
This breaks the trust boundary between tenants of a multi-org Shipit deployment: an actor who only controls one configured GitHub organization (which is by design not privileged with respect to other organizations' repos) can forge push/status/check_suite/membership events that Shipit accepts as authentic for a stack belonging to a completely different organization. Depending on which handler is targeted this can trigger `GithubSyncJob` syncing/deploy-related state, fabricate commit `Status`, or manipulate `Membership`/`Team` records tied to another org's stacks — i.e., cross-repository state manipulation for repos the attacker has no GitHub-side access to.

### Likelihood Explanation
Requires a Shipit instance configured with more than one GitHub organization (a documented, supported configuration) and requires the attacker to control (or previously have controlled) one of those organizations' GitHub App webhook secret — a credential boundary weaker than being a collaborator or having access to the victim organization/repo. No Shipit session, API token, or private key is needed; only the ability to construct and POST an HMAC-signed HTTP request to `/webhooks`.

### Recommendation
In `WebhooksController#verify_signature`, after verifying the signature, cross-check that the organization implied by `repository.full_name` (or `organization.login` for org-level events) matches the organization (`repository_owner`) whose secret validated the request, and reject the request (422) if they differ. Equivalently, `Handler#repository_name`/`stacks` should re-derive the owning organization and assert it equals the one that authenticated the webhook before resolving stacks.

### Proof of Concept
1. Deploy Shipit with two organizations configured, `OrgA` and `OrgB`, each with their own GitHub App and `webhook_secret` (per `docs/setup.md` multi-org setup), and a stack tracking `OrgB/victim-repo`.
2. As the (otherwise unprivileged w.r.t. OrgB) owner/admin of `OrgA`'s GitHub App, craft a JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>` and send `POST /webhooks` with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "OrgA")` and successfully verifies the signature against `OrgA`'s secret.
5. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("OrgB/victim-repo")` and enqueues `GithubSyncJob` for `OrgB`'s stack, even though the request was never authenticated by `OrgB`'s GitHub App. [8](#0-7) [9](#0-8)

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

        request.raw_post

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
