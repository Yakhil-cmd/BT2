### Title
Cross-tenant status forgery via unscoped `Commit.where(sha:)` lookup in StatusHandler - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits by `sha` alone, with no constraint tying the match to the organization/repository that authenticated the webhook. Because git SHAs are content-addressed, any repository owner (including a fork of the victim's repo, or one sharing history/objects with it) can genuinely trigger a GitHub `status` webhook, signed with their own org's legitimate `webhook_secret`, that names a `sha` also present in an unrelated victim stack, causing Shipit to write an attacker-controlled status onto the victim's commit.

### Finding Description
The binding claimed by the question is: `organization_that_authenticated_payload == organization_owning_commit_row_being_mutated`. Tracing the code:

- `WebhooksController#verify_signature` resolves `repository_owner` from the payload's `repository.owner.login` and validates the HMAC signature against that organization's `webhook_secret` via `Shipit.github_app.verify_webhook_signature` [1](#0-0) [2](#0-1) . This proves the payload was genuinely emitted by GitHub for a repository owned by that organization — it does **not** prove anything about which `sha` values are legitimate to report on.
- Once verified, `StatusHandler#process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with zero scoping by `stack_id`, `repository_id`, or any relationship to the authenticating organization/repository [3](#0-2) .
- `Commit#create_status_from_github!` unconditionally creates a `Status` record from the payload's `state`/`description`/`target_url`/`context` fields for whatever commit row was matched [4](#0-3) .

Root cause: the equality the signature check enforces (payload authenticity for org A) is disjoint from the equality the handler needs (commit row belongs to org A's stack). Since SHA-1 commit IDs are derived purely from tree/parent/commit-metadata content, an attacker who forks or otherwise obtains byte-identical commit objects to those in a victim's stack (a very common scenario for public/shared repos, forked PRs, or repos sharing a common upstream history) can call the real GitHub Statuses API (`POST /repos/{attacker_org}/{attacker_repo}/statuses/{sha}`) on their own repository for that shared SHA. GitHub then emits a `status` webhook, correctly signed with the attacker's own configured `webhook_secret`, naming that identical `sha`. `verify_signature` passes because it only checks that org A's secret matches — it has no knowledge of, and does not check, which stacks/repositories in the Shipit DB own commits with that SHA. `StatusHandler` then blindly applies the status to every `Commit` row across the entire instance with a matching SHA, including the victim's stack in an unrelated org/tenant.

No existing guard prevents this: `verify_signature` only authenticates org A; the `ExplicitParameters` schema in `StatusHandler.params` validates types, not repository binding; there is no `stack`/`repository` lookup by `repository.full_name` anywhere in the handler.

### Impact Explanation
An attacker can write an arbitrary `state` (e.g. `success`), `description`, and `target_url` onto any commit in any stack across the entire Shipit instance whose SHA they can reproduce — most easily by forking the victim's repository (a normal, unprivileged GitHub action) and calling the Statuses API on their fork for a shared commit. This can flip a `Status::Group` from pending/failing to `success`, potentially unblocking a merge or deploy gated on CI status for a completely unrelated tenant/stack that never authenticated this write. This is a cross-repository write of one tenant's data caused by a payload from another tenant, matching the "payload for one repository mutating another's stack/commit/task/team" Critical category.

### Likelihood Explanation
Preconditions: attacker must own/control an org configured in Shipit with a valid `webhook_secret` (a normal onboarded tenant, not a privileged role) and must be able to produce or observe a commit SHA that also exists in a victim stack — trivially achievable by forking the victim repo (shared history/objects yield identical SHAs) or by any other means of obtaining byte-identical commit content. No GitHub/Shipit secrets, session, or elevated permissions are required beyond what any normal onboarded org already has. The attack is fully repeatable against any commit SHA the attacker can reproduce, across arbitrary victim stacks, at no cost beyond routine GitHub API calls the attacker is authorized to make on their own repository.

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` to only commits belonging to stacks whose repository matches `params.repository.full_name` (or equivalent owner/repo identity carried in the payload), analogous to how other webhook handlers resolve the target `Stack`/`Repository` before mutating state. Reject or ignore status updates for commits outside the authenticated repository/organization.

### Proof of Concept
Minitest plan (no live GitHub calls; use existing webhook signing test helpers):
1. Create two `Stack` fixtures under two different repositories/orgs, `org_a/repo_a` and `org_b/repo_b`, each with `webhook_secret` configured for its respective org (mirroring `test/dummy/config/secrets.yml` patterns already used in `test/controllers/webhooks_controller_test.rb`).
2. Create a `Commit` under `org_b/repo_b`'s stack with a specific `sha` = `"deadbeef..."`.
3. Build a `status` event JSON payload where `repository.owner.login == "org_a"`, `repository.full_name == "org_a/repo_a"`, `sha == "deadbeef..."`, `state == "success"`.
4. Sign the payload with `org_a`'s `webhook_secret` and POST it to `/webhooks` with header `X-Github-Event: status`.
5. Assert the response is `200 OK` (signature accepted).
6. Assert: `org_b`'s commit (`sha == "deadbeef..."`) now has a `Status` record with `state == "success"` created from this payload — i.e. `commit_b.reload.statuses.last.state == "success"` — even though the authenticating organization was `org_a`, not `org_b`. This demonstrates `organization_that_authenticated_payload ("org_a") != organization_owning_commit_row_being_mutated ("org_b")`, confirming the broken binding.
