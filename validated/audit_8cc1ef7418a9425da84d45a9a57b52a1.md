### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup enabling forced deploy/block on `ignore_ci` stacks - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target commit(s) for an incoming `status` webhook purely by bare SHA, with no repository/stack scoping, unlike the base `Handler` class's `stacks` helper which scopes by `repository.full_name`. Combined with `Commit#deployable?`, which on an `ignore_ci: true` stack ignores CI status entirely (`stack.ignore_ci? || (success? && !blocked?)`), any webhook sender who can get a validly-signed `status` event accepted for *any* repository can flip the state of a commit that also exists (same SHA) in a different, victim stack.

### Finding Description
The broken binding: the code implicitly assumes `status.repository.full_name == commit.stack.repository.full_name` for every `Commit` matched by SHA, but this is never checked.

- `StatusHandler#process` does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [1](#0-0) 
This looks up **every** `Commit` row across **all** stacks/repositories sharing that SHA — it never calls the base `Handler#stacks` scoping helper (`Repository.from_github_repo_name(repository_name)&.stacks`) that other handlers rely on [2](#0-1) .

- `create_status_from_github!` appends a new `Status` and re-evaluates deployability/merge scheduling via `add_status`, which calls `stack.schedule_merges` on success/pending transitions [3](#0-2) .

- `Commit#deployable?` on a stack configured with `ignore_ci: true` completely bypasses the CI/status check: `!locked? && (stack.ignore_ci? || (success? && !blocked?))` [4](#0-3) . Since `ignore_ci?` short-circuits, the actual `success?`/`state` value written by the forged status is not even required for deployability on that stack — but the write still occurs, corrupts the commit's status history, and (per `add_status`) can trigger `stack.schedule_merges` and `Hook.emit(:deployable_status, ...)` for the victim's stack based on a status payload that never authenticated against that stack's repository.

Exploit flow: an attacker forks/clones a public repository so that a commit with an identical SHA exists both in a repository they control and in the victim's tracked repository (git SHAs are content-addressed, so an identical commit — as from a genuine fork — has an identical SHA across repos). The attacker triggers (or has GitHub trigger) a `status` webhook on their own repository/organization for that SHA with `context: security/scan`, `state: success`. `WebhooksController#verify_signature` validates the HMAC signature using the webhook secret configured for `repository_owner` taken from the **payload's own `repository.owner.login` field** [5](#0-4) [6](#0-5)  — i.e., it only proves the request came from *some* configured GitHub App/org that legitimately owns that SHA's repo, not that it is authorized for the victim's stack. `StatusHandler#process` then writes the status to **every** `Commit` row matching that SHA, including the victim's, regardless of which repository actually authenticated the webhook.

Existing guards do not prevent this: `verify_signature` only proves the webhook is authentic for *the sender's own organization*, not that the sender's repository matches the target stack's repository [7](#0-6) . `ExplicitParameters` schema only validates payload shape, not repository ownership [8](#0-7) . No `Repository`/`Stack` model validation ties a `Status` write back to the originating repository, since `StatusHandler` never consults `repository_name`/`stacks` at all.

### Impact Explanation
A payload authenticated for repository A can write a `Status` row (and trigger merge-scheduling / deployable-status hooks) against a `Commit` belonging to stack/repository B, as long as both repositories happen to share a commit SHA (trivially true for forks, cherry-picks, or any commit whose exact tree/parents/timestamps/message the attacker can reproduce). This is a "payload for one repository mutating another's stack/commit" — squarely a Critical-class cross-tenant write, matching the rules' Critical bucket for "a payload for one repository mutating another's stack, commit, task or team." It is repeatable against any stack that shares a SHA with an attacker-reachable repository and is not limited to a single victim.

### Likelihood Explanation
Preconditions: the attacker needs (a) a repository whose organization is registered with a Shipit GitHub App/webhook secret so `verify_signature` succeeds for *that* org, and (b) a commit SHA shared with the target victim stack (achievable by forking or replaying identical commit content). This is realistic in typical open-source/fork-heavy environments where any external contributor's fork shares SHAs with upstream. The `ignore_ci: true` detail in the question amplifies impact (deployability doesn't even depend on the forged status's correctness) but the core cross-repository write bug exists independent of `ignore_ci`. Cost to the attacker is low: one webhook POST with a valid signature for their own org.

### Recommendation
Scope `StatusHandler#process` (and any other bare-SHA lookups) by the originating repository, mirroring `Handler#stacks`: only update `Commit` records whose `stack` belongs to `Repository.from_github_repo_name(repository_name)`, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or join through `Stack` filtered by the payload's `repository.full_name`, and drop/ignore statuses for commits outside that scope.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`-style):
1. Create `repository_a` (`org/repo-a`) and `repository_b` (`org-victim/repo-b`), each with a `Stack`; set `stack_b.ignore_ci = true` and configure `stack_b.required_statuses`/`stack.required_statuses` to include `security/scan`.
2. Create `Commit.create!(stack: stack_a, sha: 'deadbeef...')` and `Commit.create!(stack: stack_b, sha: 'deadbeef...')` (same SHA, simulating a shared fork commit).
3. Build a webhook payload: `{ 'repository' => { 'full_name' => 'org/repo-a', 'owner' => { 'login' => 'org' } }, 'sha' => 'deadbeef...', 'context' => 'security/scan', 'state' => 'success' }`.
4. Assert binding before: `commit_b.status.state != 'success'` (or `commit_b.statuses.count == 0`).
5. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)`.
6. Assert binding after: `commit_b.reload.statuses.exists?(context: 'security/scan', state: 'success')` is `true`, proving repository A's authenticated payload mutated repository B's commit — even though the payload's `repository.full_name` was `org/repo-a`, never `org-victim/repo-b`.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end

      ].join(' '))
    end
