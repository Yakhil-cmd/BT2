### Title
Membership webhook lets an attacker-controlled GitHub org write `Membership` rows into another org's `Team` - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#process` resolves the target `Team` solely by `params.team.id` (the GitHub team's numeric ID) via `Team.find_or_create_by!(github_id: params.team.id)`, and never validates that the resolved (or newly labeled) team's `organization` matches the organization that authenticated the webhook (`repository_owner`, used in `verify_signature`). In a multi-org Shipit deployment, an attacker who administers their own onboarded GitHub org can sign a `membership` webhook with their own org's `webhook_secret` while embedding a victim org's team `github_id`, causing Shipit to add the attacker's GitHub login as a member of the victim's team.

### Finding Description
The broken binding: `team.organization == repository_owner` (the organization whose secret verified the request) is assumed but never enforced.

- `WebhooksController#verify_signature` selects the GitHub App/secret to verify with using `repository_owner`, derived directly from the untrusted payload's `repository.owner.login` (or `organization.login` fallback): `Shipit.github(organization: repository_owner)` then `github_app.verify_webhook_signature(...)` [2](#0-1) . Verification only proves the request was signed by *some* configured org's secret — the one named in `repository.owner.login` — not that the rest of the payload (team/organization) is consistent with it.
- `MembershipHandler#process` calls `find_or_create_team!`, which looks up (or creates) a `Team` purely by `github_id: params.team.id`: `Team.find_or_create_by!(github_id: params.team.id) do |team| team.organization = params.organization.login end` [3](#0-2) . The `team.organization =` assignment inside the block only runs on *creation*; if a `Team` row with that `github_id` already exists (e.g., the victim's real team, previously synced), it is returned unchanged regardless of what org's secret verified the current request.
- `process` then does `team.add_member(member)` for `action: 'added'`, which appends the (possibly attacker-created) `User` to `team.members` [4](#0-3) , [5](#0-4) .

Attacker request: attacker administers `attacker-org`, an org legitimately configured in `Shipit.github` with its own `webhook_secret` (per the multi-org setup documented) [6](#0-5) . Attacker POSTs to `/webhooks` with header `X-Github-Event: membership`, a valid `X-Hub-Signature` computed with `attacker-org`'s webhook secret, and body:
```json
{"action":"added","team":{"id":<victim_team_github_id>,"name":"x","slug":"x","url":"x"},
 "organization":{"login":"attacker-org"},"member":{"login":"attacker"},
 "repository":{"owner":{"login":"attacker-org"}}}
```
`repository_owner` resolves to `attacker-org`, so `Shipit.github(organization: 'attacker-org')` verifies successfully using the attacker's own secret. `Team.find_or_create_by!(github_id: victim_team_github_id)` finds the pre-existing victim `Team` and returns it untouched; `team.add_member(User.find_or_create_by_login!('attacker'))` inserts a `Membership` row linking the attacker's user to the victim's `Team`.

Existing guards do not stop this: `verify_signature` only authenticates *which org's secret* signed the bytes, it does not cross-check `params.organization.login`, `params.team.*`, or the resolved `Team#organization` against `repository_owner` [7](#0-6) . The `MembershipHandler` `ExplicitParameters` schema only checks types/presence, not organizational ownership [8](#0-7) . No model validation on `Team`/`Membership` enforces `organization` consistency at write time.

### Impact Explanation
This writes a `Membership` (and potentially mutates `Team` name/slug/url via `github_team=` if the team didn't previously exist) for a GitHub team owned by a different organization than the one that authenticated the request — a cross-tenant write into another org's data, matching the "payload for one repository mutating another's ... team" Critical category. More importantly, `User#authorized?` grants Shipit login/access when `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [1](#0-0) ; if the victim team is one of the configured `Shipit.github_teams`, this bug lets the attacker (or an attacker-created bogus user) escalate into being recognized as an authorized member of that team, i.e., escalation into `Shipit.github_teams` authorization. The attack is repeatable against any guessable/sequential `github_id` and is not limited to a single victim org — it can be replayed against every team in every other tenant org hosted on the same Shipit instance.

### Likelihood Explanation
Requires a multi-org Shipit deployment where the attacker legitimately administers (or has been granted install of) one org with its own configured `webhook_secret`, per the documented multi-org setup [6](#0-5) . GitHub team IDs are sequential integers and can be enumerated/brute-forced. No Shipit session, API token, or victim secrets are needed — only the attacker's own org's webhook secret, which they control. This is a low-cost, fully repeatable attack once the multi-tenant precondition holds.

### Recommendation
In `MembershipHandler#find_or_create_team!` / `#process`, verify that the resolved `Team#organization` equals `params.organization.login` (and that this equals the authenticated `repository_owner`) before performing `add_member`/`delete`; raise/reject (or drop the event) on mismatch instead of silently operating on an unrelated org's team.

### Proof of Concept
minitest (webhooks_controller_test.rb style):
1. Create `victim_team = Team.create!(github_id: 999, organization: 'victim-org', slug: 'devs', name: 'Devs', api_url: 'https://x')`.
2. Configure two orgs in test github config (`victim-org`, `attacker-org`), each with distinct `webhook_secret`.
3. Stub/compute a valid `X-Hub-Signature` using `attacker-org`'s secret over the JSON body below.
4. POST `/webhooks` with `X-Github-Event: membership`, that signature, and body: `{"action":"added","team":{"id":999,"name":"x","slug":"x","url":"x"},"organization":{"login":"attacker-org"},"member":{"login":"attacker"},"repository":{"owner":{"login":"attacker-org"}}}`.
5. Assert `response.status == 200` (proving verification succeeded via attacker-org's secret only — `victim_team.organization != 'attacker-org'`, the broken binding).
6. Assert `Membership.exists?(team_id: victim_team.id, user_id: User.find_by(login: 'attacker').id)` is `true`.
