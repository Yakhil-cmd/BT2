### Title
Webhook signature verification uses `repository.owner.login` while `EditedHandler` (and sibling PR handlers) mutate rows using an unrelated `repository.full_name`, allowing a payload validly signed for one org to write PR metadata into another org's `PullRequest` row - (File: `app/models/shipit/webhooks/handlers/pull_request/edited_handler.rb`)

### Summary
`WebhooksController#verify_signature` picks the HMAC secret to check against based on `params.dig('repository','owner','login')` (or `organization.login`), but `EditedHandler#repository` (and `Handler#stacks`) resolve the record to mutate using the independent, attacker-controlled `params.repository.full_name` field. Nothing in the request path ties these two fields together, so a webhook signed with a legitimately-known secret for org A can carry a `repository.full_name` pointing at org B's stack, causing org A's payload content to be written into org B's `PullRequest` row.

### Finding Description
The broken binding, stated as an equality that the code assumes but never enforces:

`org used to verify HMAC (params.dig('repository','owner','login'))` == `org owning the row mutated (params.repository.full_name.split('/').first)`

Trace:
1. `WebhooksController#verify_signature` derives `repository_owner` purely from JSON body fields and looks up the matching `Shipit.github(organization: repository_owner)` app/secret to validate `X-Hub-Signature` against. [1](#0-0) [2](#0-1) 

2. Once verified, the raw JSON is dispatched to handlers unchanged: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. [3](#0-2) 

3. `EditedHandler#repository` resolves the actual `Shipit::Repository` to operate on using `params.repository.full_name` - a completely separate field from the one used in step 1, with no consistency check between them. [4](#0-3) 

4. `EditedHandler#process` then finds the `PullRequest` scoped only by `number` and that resolved `repository.id`, and overwrites it with attacker-supplied `params.pull_request` (title, head ref, labels, assignees, etc.). [5](#0-4) 

5. The same `full_name`-driven-lookup / owner-independent pattern recurs across the base `Handler` class and every sibling PR handler (`closed_handler.rb`, `label_capturing_handler.rb`, `labeled_handler.rb`, `opened_handler.rb`, `reopened_handler.rb`, `unlabeled_handler.rb`, `assigned_handler.rb`), confirming this is systemic, not an EditedHandler-only quirk. [6](#0-5) 

Exploit flow: An attacker who administers their own GitHub org ("attacker-org") that is one of the multiple orgs configured on a shared/multi-tenant Shipit instance (e.g. as shown by `test/dummy/config/secrets_double_github_app.yml`, which configures `OrgOne`/`OrgTwo` each with its own `webhook_secret`) knows their own org's legitimate `webhook_secret`. They:
- Open (or use an existing) real PR number `N` against the victim's repo `victim-org/victim-repo` (a normal, unprivileged GitHub action).
- Craft a `pull_request` "edited" JSON body with `repository.owner.login = "attacker-org"` and `organization.login` absent/consistent with attacker-org, but `repository.full_name = "victim-org/victim-repo"`, `number = N`, and `pull_request.title/body/head.ref/labels` set to arbitrary attacker-chosen content.
- Sign the raw body with `sha1=HMAC-SHA1(attacker-org's webhook_secret, body)` and POST to `/webhooks` with `X-Github-Event: pull_request`.

`verify_signature` looks up `Shipit.github(organization: "attacker-org")` and validates successfully because the attacker used their own genuine secret - the check never inspects `repository.full_name`. `EditedHandler` then resolves the victim's `Repository`/`Stack`/`PullRequest` via `full_name` and overwrites that PR row's metadata with the attacker's payload.

Why existing guards fail: `drop_unhandled_event` only checks event type is handled; `verify_signature`/`GithubApp#verify_webhook_signature` only validate the HMAC against the secret for the org named in the payload (attacker's own org), not the org actually being mutated; there is no `ExplicitParameters` rule or model validation cross-checking `repository.owner.login` against `repository.full_name`.

### Impact Explanation
An attacker can overwrite title, head branch ref, labels, and assignee metadata on an arbitrary victim repository's `PullRequest` record that they do not own, control, or have any authenticated relationship to, using only a signature valid for their own unrelated org - this is a payload for one repository mutating another repository's stack/PR record. This matches the Critical category "a payload for one repository mutating another's stack, commit, task or team". It is repeatable against any victim repository/stack hosted on the same shared Shipit instance, for any PR number the attacker can create or knows exists, and generalizes to the sibling handlers (`closed`, `labeled`, `unlabeled`, `reopened`, `opened`, `assigned`) that share the identical `full_name`-only resolution pattern, widening the blast radius across all tenants of a multi-org Shipit deployment.

### Likelihood Explanation
Preconditions: the Shipit instance must be multi-tenant, i.e. configured with more than one GitHub org/App (each with its own `webhook_secret`), and the attacker must administer at least one of those configured orgs (a legitimate, low-privilege position for a customer of a shared internal Shipit deployment). Given that, the attacker's cost is trivial: compute one HMAC-SHA1 signature with a secret they legitimately possess and send one crafted HTTP POST - no GitHub/Shipit secrets belonging to the victim are needed. In a single-tenant Shipit install (only one org configured) this specific path is not exploitable, since the attacker would have no legitimate `webhook_secret` at all.

### Recommendation
In `WebhooksController#verify_signature`, and in `Handler`/`EditedHandler` (and all sibling PR handlers), enforce that the org used to select/verify the webhook secret is the same org that owns the repository named in `repository.full_name` (e.g., assert `params.repository.full_name.split('/').first.casecmp(repository_owner) == 0` before dispatch, rejecting mismatches with 422). More robustly, resolve the `Repository`/`Stack` to mutate by an ID/owner value that was authenticated as part of signature verification rather than trusting a second, independently-controlled field in the same unauthenticated JSON body.

### Proof of Concept
Add a minitest (e.g. in `test/controllers/webhooks_controller_test.rb` or `test/models/shipit/webhooks/handlers/pull_request/edited_handler_test.rb`) that:
1. Configures two orgs in `Shipit.github` config (mirroring `secrets_double_github_app.yml`'s `OrgOne`/`OrgTwo` with distinct `webhook_secret`s).
2. Creates a victim `Repository`/`Stack`/`PullRequest` under `OrgTwo/victim-repo` with `number: 7`, original title `"legit title"`.
3. Builds a `pull_request` "edited" JSON payload with `repository: { full_name: "OrgTwo/victim-repo" }`, `repository.owner.login` (or top-level `organization.login`) `== "OrgOne"`, `number: 7`, `pull_request.title: "PWNED"`.
4. Computes `sha1=HMAC-SHA1(OrgOne_webhook_secret, raw_body)` and sets it as `X-Hub-Signature`, then POSTs to `/webhooks` with `X-Github-Event: pull_request`.
5. Asserts before: `binding_lhs = "OrgOne"` (org whose secret verified the HMAC), `binding_rhs = "OrgTwo"` (org owning the mutated `PullRequest`'s stack/repository) - i.e. `refute_equal binding_lhs, binding_rhs`.
6. Asserts the request returns `200 OK` (signature accepted) and `victim_pull_request.reload.title == "PWNED"`, proving the attacker-signed-for-OrgOne payload mutated an OrgTwo-owned row.
