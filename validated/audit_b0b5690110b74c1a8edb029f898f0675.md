### Title
Wallet Contract can become permanently locked (`has_in_flight_tx` stuck `true`) if the relayer-ban receipt's `DeleteKey` action fails atomically with `ban_relayer` - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
The Wallet Contract's relayer-banning mechanism couples key revocation (`delete_key`) and the state-reset call (`ban_relayer`) into a single atomic receipt/batch. Because NEAR receipts are all-or-nothing (a failing action aborts the whole receipt and rolls back all of its state changes), any failure of the `delete_key` sub-action prevents `ban_relayer` from ever running, leaving the `has_in_flight_tx` flag stuck at `true` forever, with no other code path able to reset it. This mirrors the reported Open Oracle bug class: a state-mutating recovery/reset mechanism is entangled with revoking a key, such that if the key-revocation step doesn't succeed, the contract is left in an unrecoverable state requiring redeployment/migration to fix.

### Finding Description
`rlp_execute` sets `self.has_in_flight_tx = true` whenever it schedules a promise, including the "ban relayer" recovery path [4](#0-3) . The only method that resets `has_in_flight_tx` back to `false` in that recovery path is the private `#[private] ban_relayer` callback [5](#0-4) .

`create_ban_relayer_promise` builds this recovery path as a *single* batched promise containing two actions on the same receipt: `delete_key(pk)` followed by `function_call_weight("ban_relayer", ...)`: [6](#0-5) 

Because NEAR executes the actions in a receipt sequentially and, if any action fails, aborts the whole receipt and rolls back state [7](#0-6) [1](#0-0) , if `delete_key(pk)` fails (e.g. `DeleteKeyDoesNotExist`, which does exist as an error kind: [8](#0-7) ), then `ban_relayer` never executes and `has_in_flight_tx` is never reset. Every subsequent call to `rlp_execute` will immediately short-circuit with "transaction already in progress" without doing anything else [9](#0-8) , permanently bricking the wallet contract with no built-in recovery.

Such a failure of the `delete_key` action is plausible: it fires whenever `env::signer_account_id() == current_account_id` and any `Error::Relayer` is returned by `inner_rlp_execute` or `address_check_callback` — including in a delayed-error scenario after other asynchronous state changes to the same access key (e.g., the user or another concurrent flow removing/replacing that same key) might have already removed the key by the time this promise executes on-chain, or if the relayer key were already revoked by a race between two rapidly submitted faulty transactions.

### Impact Explanation
If triggered, the wallet contract becomes permanently unusable: `has_in_flight_tx` stays `true` forever, since only `ban_relayer`, `rlp_execute_callback`, `address_check_callback`, and `nep_141_storage_balance_callback` reset it, and none of those can run once the entangled receipt fails atomically. This is a denial-of-service against the user's own wallet contract (an unprivileged, permissionless account that any relayer/user can drive into this state), requiring redeployment or manual state surgery to recover — directly analogous to the reported bug where the recovery/update path is entangled with key invalidation and a failure there leaves the contract unrecoverable.

### Likelihood Explanation
Likelihood is moderate: it requires a specific race or edge condition where the `delete_key` action targeting the relayer's own public key fails at execution time (after the earlier synchronous decision to ban was made). This could occur due to a concurrent transaction removing the same key first, or other state race conditions between the initial `rlp_execute` and the asynchronous execution of the ban receipt. It is not trivially reproducible on every relayer failure (the existing tests in `relayer.rs` all show successful revocation), but the code contains no safeguard, retry, or alternate reset path if the key-delete step fails, which is a structural design gap.

### Recommendation
Decouple the reset of `has_in_flight_tx` from the success of `delete_key`. For example, split the promise chain so that `ban_relayer` (or an equivalent reset) always executes regardless of whether `delete_key` succeeds, e.g. by using `.then(...)` instead of batching them as atomic actions in the same receipt, or by resetting `has_in_flight_tx` unconditionally in a callback that inspects `promise_result` rather than relying on the whole batched receipt to succeed.

### Proof of Concept
Not independently reproduced in this analysis; conceptually: call `rlp_execute` with a relayer using its own access key on the wallet account such that it returns `Error::Relayer` (any of the existing failure paths, e.g. `test_relayer_invalid_sender`), but first (in a concurrent/racing transaction) issue a `DeleteKey` action removing that same relayer public key before the resulting `create_ban_relayer_promise` receipt executes. The `delete_key` sub-action inside `create_ban_relayer_promise` will then fail with `DeleteKeyDoesNotExist`, causing the whole receipt (including the `ban_relayer` call) to fail and roll back, leaving `has_in_flight_tx == true` permanently. pub(crate) fn action_delete_key(
    config: &RuntimeConfig,
    state_update: &mut TrieUpdate,
    account: &mut Account,
    result: &mut ActionResult,
    account_id: &AccountId,
    delete_key: &DeleteKeyAction,
) -> Result<(), RuntimeError> {
    let access_key = get_access_key(state_update, account_id, &delete_key.public_key)?;
    if let Some(access_key) = access_key {
        if let Some(gas_key_info) = access_key.gas_key_info() {
            delete_gas_key(
                config,
                state_update,
                account,
                result,
                account_id,
                &delete_key.public_key,
                &access_key,
                gas_key_info,
            )?;
        } else {
            delete_regular_key(
                &config.fees,
                state_update,
                account,
                account_id,
                &delete_key.public_key,
                &access_key,
            );
        }
    } else {
        result.result = Err(ActionErrorKind::DeleteKeyDoesNotExist {
            public_key: delete_key.public_key.clone().into(),
            account_id: account_id.clone(),
        }
        .into());
    }
    Ok(())
}
