### Title
Block-revenue-sharing rewards (`pending_delegator_rewards`) become permanently unspendable when a vote account has zero delegated stake in the reward epoch - (File: `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`)

### Summary
Under SIMD-0123 block-revenue sharing, lamports are deposited into a vote account's `pending_delegator_rewards` field and are meant to be paid out to stake delegators pro-rata to their share of the vote account's total delegated stake at the reward epoch. `calculate_block_reward()` computes this payout by dividing by `total_active_stake`, the delegated stake recorded for that vote account in `reward_epoch_delegated_stakes`. If a vote account has no delegated stake for the rewarded epoch, the function short-circuits and returns `0` for every (non-existent) delegation, so none of the accumulated `pending_delegator_rewards` is distributed. Separately, the vote program's withdraw path explicitly reserves `pending_delegator_rewards` and refuses to let the authorized withdrawer touch it. The combination means these lamports can become permanently unspendable: never distributed (no delegators to distribute to) and never withdrawable (protected reserve), mirroring the reported bond-interest bug where interest accrues but there is no bond supply/borrower left to receive it.

### Finding Description
`calculate_block_reward()` looks up the vote account's `pending_delegator_rewards` and divides it among stake delegations proportional to `total_active_stake`, which is taken from the reward epoch's `reward_epoch_delegated_stakes` snapshot: [1](#0-0) 

When `total_active_stake == 0` — i.e., no stake was delegated to that vote account for the rewarded epoch — the function returns `0`, and because there are no stake delegations at all in that case, the outer per-delegation loop in `calculate_stake_rewards_and_commissions` never runs for that vote account, so nothing is deducted from `pending_delegator_rewards`: [2](#0-1) 

`pending_delegator_rewards` is funded via the permissionless `DepositDelegatorRewards` instruction, which transfers lamports into the vote account and increments the field with no check on whether the vote account currently has any delegated stake: [3](#0-2) [4](#0-3) 

Independently, the vote program's `withdraw()` logic treats `pending_delegator_rewards` as a protected reserve that cannot be withdrawn by the authorized withdrawer, as confirmed by unit tests showing withdrawal is blocked once it would dip into the pending-rewards reserve and full account closure is blocked while `pending_delegator_rewards > 0`: [5](#0-4) 

The combined effect: if a validator's vote account loses all delegated stake (all delegators fully undelegate/withdraw) while `pending_delegator_rewards > 0`, or if `DepositDelegatorRewards` is used to deposit into a vote account that currently has zero delegated stake, the deposited lamports have no possible destination — they cannot be distributed (no delegation exists to receive them) and cannot be withdrawn (reserved by the withdraw check). This is structurally identical to the reported bug: a value pool (`bond`/interest ↔ `pending_delegator_rewards`) is paid out proportionally to a denominator (`bond supply`/`borrowers` ↔ `total_active_stake`/stake delegations) without verifying the denominator is non-zero/non-empty before assuming a distribution path exists.

### Impact Explanation
This results in lamports becoming permanently frozen inside a vote account: not distributable to any delegator (because none exists for that vote account in the reward epoch) and not recoverable by the authorized withdrawer (explicitly reserved). Unlike a normal deferred-until-restake scenario, if the vote account never again attracts delegated stake, these funds are stuck indefinitely with no code path to recover or redistribute them — a frozen-funds condition analogous to "stuck bond interest" in the reference finding.

### Likelihood Explanation
`DepositDelegatorRewards` is permissionless (any signer with lamports can call it) and requires no check that the target vote account currently has delegated stake, so triggering the zero-denominator condition only requires depositing into a vote account whose stake has been (or is about to be) fully undelegated — a state reachable without any privileged/validator role, matching the single-borrower liquidation scenario in the source report.

### Recommendation
Before allowing (or while processing) block-revenue-sharing distribution, verify that a vote account has non-zero delegated stake for the rewarded epoch. Concretely: (1) in `calculate_block_reward`, when `total_active_stake == 0`, surface this as an unresolved/held reward rather than silently leaving it un-distributable with no future recomputation guarantee; and/or (2) in `deposit_delegator_rewards`, reject deposits into vote accounts with zero currently-delegated stake, or (3) relax the `withdraw()` reserve so pending rewards can eventually be reclaimed by the authorized withdrawer if no stake has been delegated to the vote account for some bounded period, preventing indefinite lock-up.

### Proof of Concept
1. Enable `block_revenue_sharing` and related features (`commission_rate_in_basis_points`, `custom_commission_collector`) for a V4 vote account with zero delegated stake (e.g., a freshly created vote account, or one whose delegators have all deactivated/withdrawn stake as of the current reward epoch's `reward_epoch_delegated_stakes` snapshot).
2. Call `DepositDelegatorRewards` (`programs/vote/src/vote_state/mod.rs:936`) to deposit lamports, incrementing `pending_delegator_rewards`.
3. Advance through an epoch boundary; in `calculate_stake_rewards_and_commissions`, because there are no stake delegations pointing at this vote account, `calculate_block_reward` is never invoked for it and `pending_delegator_rewards` is untouched.
4. Attempt to withdraw via the vote program's `withdraw()` instruction — observe (per `test_withdraw_with_pending_delegator_rewards`, `programs/vote/src/vote_state/mod.rs:5817`) that withdrawal is capped at `lamports - rent - pending_delegator_rewards`, so the pending amount can never be withdrawn.
5. With no delegator ever attracted to this vote account, the deposited lamports remain permanently inaccessible.

pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}
