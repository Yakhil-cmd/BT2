### Title
Webhook signature verification keyed on attacker-controlled `repository.owner.login` while handlers dereference the independent `repository.full_name` field lets a secret-less org's identity forge writes onto any other org's `PullRequest`/`User` rows - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/pull_request/assigned_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` config (and thus which HMAC secret) to validate the request against using `repository_owner`, derived from `params.dig('repository','owner','login')`. `AssignedHandler` (and every other `pull_request` handler) instead resolves the target `Repository`/`Stack`/`PullRequest` using the independent, equally attacker-authored `params.repository.full_name` field. Because these two JSON fields are never cross-checked, an attacker who can name any Shipit-configured org that has no `webhook_secret` set can pass signature verification "as" that org while pointing `repository.full_name` at a completely different, secured victim repository, causing real writes (`PullRequest#update`, `User.find_or_create_by_login!`) against that victim's tracked pull request.

### Finding Description
Broken binding (stated as an equality that must hold but doesn't):
`Shipit.github(organization: params.repository.owner.login).webhook_secret` used to authenticate the request **must equal** the secret of the org that owns `params.repository.full_name`, the value the handler actually acts on. The code never enforces this.

Trace:
1. `verify_signature` computes `repository_owner` from `params.dig('repository','owner','login')` and looks up `Shipit.github(organization: repository_owner)` [1](#0-0) [2](#0-1) .
2. `GitHubApp#verify_webhook_signature` returns `true` unconditionally when `webhook_secret` is blank for that org [3](#0-2) .
3. `AssignedHandler#repository` (and every sibling handler) resolves the acted-upon repository from the *separate* `params.repository.full_name` field via `Shipit::Repository.from_github_repo_name` [4](#0-3) [5](#0-4) .
4. `AssignedHandler#process` looks up the matching `PullRequest` scoped to that resolved repository's stacks by `number`, and if found calls `pull_request.update(github_pull_request: params.pull_request)` [6](#0-5) .
5. `PullRequest#github_pull_request=` writes `title`, `state`, `additions`, `deletions`, `labels`, and, critically, `self.user = User.find_or_create_by_login!(...)` and `self.assignees = ... User.find_or_create_by_login!(github_user.login) ...` using logins taken verbatim from the attacker-authored JSON body [7](#0-6) .

Exploit flow: attacker sends `POST /webhooks` with header `X-Github-Event: pull_request`, body `{"action":"assigned","number":<real victim PR number>,"repository":{"owner":{"login":"secretless-org"},"full_name":"victim-org/victim-repo"},"pull_request":{...,"assignees":[{"login":"anything-attacker-wants"}], ...}}`. Verification passes because `secretless-org` has no configured `webhook_secret`; the handler then mutates the real `PullRequest` belonging to `victim-org/victim-repo`.

Existing guards do not stop this: `drop_unhandled_event` only checks the event type is registered; `ExplicitParameters` schema only enforces field *types*, not cross-field consistency between `repository.owner.login` and `repository.full_name`; `verify_signature`'s `GithubOrganizationUnknown` rescue only fires if the named org is entirely absent from config, not if it exists but has no secret.

### Impact Explanation
The victim's real `PullRequest` row (assignees, author `user`, title, state, additions/deletions, labels) is mutated with attacker-fabricated GitHub logins, and new `User` rows are created attributed as assignees/author of a real, victim-repo-owned pull request. This is a payload nominally "authenticated" under one org's (secret-less) identity mutating another org/repository's tracked data — matching the Critical bucket ("a payload for one repository mutating another's stack, commit, task or team" / forged webhook accepted as authentic). The `head` commit portion is constrained (it must resolve to a real commit via `stack.github_api.commit` using the victim's own GitHub App credentials, or already exist locally), so no credential exfiltration occurs, but the assignee/author/label/title/state fields are fully forgeable. This is repeatable against any tracked PR number in any repository, as long as one secret-less org exists in the Shipit deployment's github config.

### Likelihood Explanation
Requires: (a) a multi-org (or single-org) Shipit deployment where at least one configured GitHub org/app entry has `webhook_secret` left blank — an explicitly supported, documented configuration (`webhook_secret: # nil` in the example secrets file) [8](#0-7) ; (b) the attacker must know that org's name (discoverable, e.g. published in Shipit UI/README, or simply the org they were invited to). No GitHub secrets, Shipit session, or maintainer role is needed — the attacker only crafts an arbitrary HTTP POST. Given a secret-less org exists, the attack is cheap, deterministic, and repeatable against every tracked PR number.

### Recommendation
Enforce that the org used to select the webhook signature key matches the org embedded in `repository.full_name` before dispatching to handlers (i.e., derive `repository_owner` from `full_name`'s prefix rather than the separate `owner.login` field, or explicitly reject payloads where they disagree). Additionally, treat a blank `webhook_secret` as "signature required but never satisfiable" only for genuinely unauthenticated demo setups, and warn/refuse in production configurations where some orgs have secrets and others do not, to prevent one weak org from being used to forge webhooks for other, secured orgs.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (new test)
test "secret-less org identity cannot be used to forge writes on a different org's PullRequest" do
  # victim org/repo has webhook_secret configured and owns a real tracked PullRequest
  victim_repository = shipit_repositories(:shipit) # owner has a webhook_secret in test config
  victim_pull_request = shipit_pull_requests(:review_stack_review)
  victim_pull_request.update!(number: 4242)

  # Equality that must hold: org used for signature verification == org owning repository.full_name
  signing_org = "secretless-org"
  target_full_name = victim_repository.github_repo_name

  Shipit.stubs(:github).with(organization: signing_org).returns(
    Shipit::GitHubApp.new(signing_org, { webhook_secret: nil })
  )

  request.headers['X-Github-Event'] = 'pull_request'
  body = payload_parsed(:pull_request_assigned).merge(
    "number" => victim_pull_request.number,
    "repository" => { "owner" => { "login" => signing_org }, "full_name" => target_full_name },
  )
  body["pull_request"]["number"] = victim_pull_request.number
  body["pull_request"]["assignees"] = [{ "login" => "forged-attacker-login" }]

  assert_no_difference -> { User.where(login: "forged-attacker-login").count }, "expected no forged User row from a payload signed under an unrelated org" do
    post :create, body: body.to_json, as: :json
  end

  victim_pull_request.reload
  assert_not_includes victim_pull_request.assignees.map(&:login), "forged-attacker-login",
    "victim PullRequest must not be mutated by a payload authenticated under a different org's (secret-less) identity"
end
```
Both assertions are expected to **fail** against the current code (the forged `User` row is created and the victim `PullRequest`'s assignees are overwritten), demonstrating the cross-tenant write.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
