### Title
Missing cross-field validation of `spender_attested`/`attestors` in AA "asset" message templates permanently bricks asset-issuance branches and burns trigger senders' bounce fees - (File: aa_validation.js)

### Summary
`aa_validation.js`'s handling of the `asset` app inside an AA definition validates each asset field's type individually but never cross-validates that `spender_attested: true` requires a non-empty `attestors` list (or that `attestors` must be absent when `spender_attested` is false). This is exactly analogous to the reported `OpNetVaultAutoDeploy._validateConfig()` bug: a configuration that passes the "define-time" validator but is guaranteed to fail at "use-time" validation, and — because AA code is immutable once defined — the flaw can never be corrected.

### Finding Description
For real (non-AA) asset definitions, `validateAssetDefinition()` in `validation.js` correctly cross-checks the two fields: [1](#0-0) 

But when the same `asset` app appears as a message inside an **AA definition** (a template whose fields may later be formulas evaluated at trigger time), `aa_validation.js` only validates that each field is either a boolean or a valid formula, and validates the *format* of `attestors`/`denominations` only if the field happens to be present — it never checks the relationship between `spender_attested` and `attestors`: [2](#0-1) 

This means an AA author can publish (and successfully validate) an AA definition where the `asset` message payload contains a literal `spender_attested: true` with no `attestors` field at all (or vice versa: `attestors` present while `spender_attested` is `false`). `validateAADefinition` has no path that rejects this, since it never invokes the same cross-check that `checkAttestorList()` enforces for real units: [3](#0-2) 

At runtime, when the AA fires and composes the real response unit containing the `asset` message, that composed unit goes through the ordinary unit-validation pipeline (`validateInlinePayload` → `validateAssetDefinition`) exactly like any other posted unit: [4](#0-3) 
There, `checkAttestorList(payload.attestors)` is invoked because `spender_attested` is `true`, and `checkAttestorList(undefined)` deterministically returns `"attestors not defined"`, causing the composed unit to fail validation: [1](#0-0) 

Because this failure happens inside `saveJoint`/message-processing during AA response-unit composition, the AA's whole response for that trigger fails and the AA bounces the trigger (refunding the trigger amount minus `bounce_fees`), exactly as with any other bounced trigger. Since AA definitions in Obyte are immutable once posted, **this branch of the AA can never be fixed** — every future trigger that reaches the flawed `asset`-issuance branch will deterministically bounce forever.

### Impact Explanation
- Any trigger sender who invokes the flawed asset-issuance branch of such an AA permanently loses their `bounce_fees` (base-currency AA fund loss for the sender), forever, with no way for the AA author to remedy it because AA code cannot be redefined.
- This is a concrete, self-inflicted-but-user-impacting fund loss: unlike a normal application bug that a developer can fix by redeploying, the ocore trust model relies on immutable, validated-at-definition AA code; the missing cross-check silently permits a "definition-valid but forever-broken/fund-losing" AA to be published and trusted by users interacting with it, exactly mirroring the reported bug's "config passes validation but deployment/execution always fails" pattern.
- Severity is Medium: it does not enable double-spend, supply inflation, or consensus divergence, but it is a genuine, unrecoverable fund-loss vector reachable by any unprivileged AA author and triggered by any unprivileged trigger sender.

### Likelihood Explanation
Likelihood is high in the sense that it requires no privileged access — any user can author and post an AA definition, and `validateAADefinition` will accept the flawed template as long as individual field types are correct. Any other user triggering that specific branch (issuing/defining the asset) will suffer the loss. It could occur unintentionally (an AA author simply forgetting to add `attestors` while hardcoding `spender_attested: true`), making it a realistic footgun rather than a purely theoretical edge case.

### Recommendation
When both `spender_attested` and `attestors` (or their absence) are **not** formulas (i.e., resolved to literal/static values at AA-definition time), `aa_validation.js` should perform the same cross-check that `validateAssetDefinition()` performs for real units:
- If `spender_attested === true` (literal), require `attestors` to be present and pass `checkAttestorList`.
- If `spender_attested === false` (literal) or absent, reject if `attestors` is present.
For cases where either field is a formula (dynamic), the cross-check cannot be done statically, but this should be documented/flagged, and ideally the runtime message-composition path in `aa_composer.js` should validate the fully-resolved `asset` payload with `validateAssetDefinition`-equivalent cross-checks *before* attempting to send/bounce, so that failures can be surfaced more clearly, though this does not change the fundamental fund-loss-per-trigger economics since AA logic remains immutable.

### Proof of Concept
1. Author and post an AA definition containing:
```
{
  app: 'asset',
  payload: {
    cap: 1e6,
    is_private: false,
    is_transferrable: true,
    auto_destroy: false,
    fixed_denominations: false,
    issued_by_definer_only: true,
    cosigned_by_definer: false,
    spender_attested: true
    // no "attestors" field at all
  }
}
```
2. `validateAADefinition` (via `aa_validation.js` lines 301-335) accepts this AA definition because `spender_attested` is a valid boolean and there is no cross-check requiring `attestors` when it is `true`; the AA is posted and becomes immutable.
3. Any user sends a trigger that causes this AA to execute the `asset` message. `aa_composer.js` composes the real unit and it is passed through `validateMessage`/`validateInlinePayload` → `validateAssetDefinition` (`validation.js` lines 2745-2750), which calls `checkAttestorList(undefined)` and returns `"attestors not defined"` (`validation.js` lines 2850-2864).
4. The AA response fails and bounces the trigger, refunding trigger amount minus `bounce_fees` — the trigger sender permanently loses the bounce fee on every subsequent attempt to use this AA branch, with no possibility of the AA author fixing the immutable code.

		return "too many attestors";
