### Title
Webhook signature verification keys off `repository.owner.login`/`organization.login` while event handlers act on the independently-supplied `repository.full_name`, allowing a GitHub App secret from one org to authorize writes against a stack in a different org/repo - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to use for HMAC verification based on `params.dig('repository','owner','login')` (falling back to `organization.login`), then validates the raw request body against that org's secret [1](#0-0) . Once the signature check passes, `Handler#stacks` resolves the target `Stack` using a *separate* field of the same attacker-controlled JSON body: `payload.dig('repository', 'full_name')` [2](#0-1) . Because the HMAC only proves "this body was signed by the secret belonging to the org named at `repository.owner.login`," and does not bind that org to the `repository.full_name` value acted on, these two fields can be made to disagree.

### Finding Description
The verified equality the engine is implicitly relying on is:
`org_that_authenticated (repository.owner.login) == repo_that_gets_written (repository.full_name)`

But nothing enforces this. `verify_signature` computes `repository_owner` from the payload itself (not from a route/URL binding to a specific installation) and does `Shipit.github(organization: repository_owner)` to fetch that org's `webhook_secret`, then does a constant-time HMAC compare of the header against the raw body [3](#0-2) . The full parsed payload — including `repository.full_name` — is then handed unmodified to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [4](#0-3) .

`PushHandler` (and other handlers) then resolve the `Stack`/`Repository` to act on purely via `payload.dig('repository', 'full_name')` [5](#0-4) , and trigger `stack.sync_github(expected_head_sha: params.after)` for every matching, non-archived stack on the matching branch [6](#0-5) .

If a single Shipit instance manages stacks for multiple GitHub organizations (each with its own configured `webhook_secret`/GitHub App, as shown in `config/secrets.development.shopify.yml` [7](#0-6) ), a user who legitimately controls a repo/webhook secret in Org A can forge a payload whose `repository.owner.login` (or top-level `organization.login`) says "Org A" (so verification succeeds against Org A's known secret) while `repository.full_name` says "OrgB/some-repo". `verify_signature` will authorize the request using Org A's secret, but the handler will act on Org B's stack. This crosses the exact deployment-trust boundary the audit report is about: the entity whose credential was checked is not the entity being written.

Because this endpoint is unauthenticated aside from the HMAC (no session, no `ApiClient` token, no repository write access required — the attacker only needs to be able to produce/replay a webhook body of their choosing to the public `/webhooks` endpoint using a secret they legitimately hold for their own org), this does not fall under the excluded "requires an ApiClient token / GitHub App private key / repository write access" categories; it only requires knowledge of one org's `webhook_secret`, which by design many outside collaborators/CI systems can trigger (GitHub servers sign with it, but the signing material is just an HMAC secret string configured per org, not cryptographically tied to the specific repository name inside the payload).

### Impact Explanation
An attacker who can get GitHub (or a spoofed sender knowing Org A's `webhook_secret`) to deliver a signed push/status/check_suite payload can cause `PushHandler` to invoke `stack.sync_github` on a stack belonging to an entirely different repository/org than the one whose secret authorized the request, and other handlers (`status`, `check_suite`, `membership`, `pull_request`) similarly trust `repository.full_name`/`organization.login` independent from the authenticating owner. This can trigger unwanted CI-state changes, spurious sync/merge/deploy-adjacent side effects, or membership/team changes against a stack the attacker does not control the org for — an unauthorized cross-repository write/state change, matching the report's "signature covers less than what's acted upon" bug class.

### Likelihood Explanation
Requires: (1) a multi-org Shipit deployment (documented and supported via `config/secrets.*.yml` multiple github orgs), and (2) the attacker to already possess (or leak) one org's `webhook_secret` used purely for HMAC signing — a much lower bar than repository write access, an `ApiClient` token, or a GitHub App private key, since webhook secrets are often shared with lower-trust integrations/relays. Exploitation only requires crafting an HTTP POST with mismatched `repository.owner.login` vs `repository.full_name` fields and a valid HMAC for the former's secret.

### Recommendation
Bind the verification identity to the acted-upon identity: after computing `repository_owner` for secret selection, re-derive/validate that `payload.dig('repository','full_name')` belongs to that same `repository_owner`/organization before dispatching to handlers (e.g., assert `full_name.split('/').first.casecmp(repository_owner).zero?`), or resolve the target `Stack`/`Repository` using the verified organization rather than trusting `full_name` alone.

### Proof of Concept
1. Configure Shipit with two orgs, `org-a` (secret `SECRET_A`) and `org-b` (secret `SECRET_B`), each with stacks.
2. Craft a push payload:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/target-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(SECRET_A, raw_body)>` using the known `SECRET_A`.
4. POST to `/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` resolves `repository_owner` = `org-a`, fetches `Shipit.github(organization: 'org-a')`, and the signature matches → request passes [8](#0-7) .
6. `PushHandler#stacks` resolves via `Repository.from_github_repo_name('org-b/target-repo')` and calls `sync_github` on Org B's stack [2](#0-1) [6](#0-5) , despite the request only being authenticated as belonging to Org A.

Note: full confirmation that this constitutes an unauthorized "deploy/rollback/merge" (vs. only a sync/state read) requires tracing everything `sync_github` and each handler subsequently triggers across the full handler set, which was only partially explored here (`PushHandler` confirmed; other handlers like `status`/`check_suite`/`pull_request` were only spot-checked for the same `repository_name`/`payload.dig('repository','full_name')` pattern via `Handler#stacks`, not individually re-verified line by line).

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
