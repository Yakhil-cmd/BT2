The `WebhooksController` picks that secret based on `repository_owner`, which is a field parsed from the untrusted JSON body: `params.dig('repository', 'owner', 'login')` (or the `organization` payload key) — a field that is completely independent of the `repository.full_name` field the handlers actually act on.### Title
Webhook signature verification keys off a different payload field than the repository handlers act on, allowing cross-organization webhook forgery in multi-GitHub-App deployments - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate the HMAC signature against using `repository_owner` (`params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`), while every downstream `Webhooks::Handlers::Handler` resolves the target `Repository`/`Stack` to act on using a *different* field of the same untrusted JSON body: `payload.dig('repository', 'full_name')`. In a multi-organization deployment (`Shipit.github_organizations`, `github_app_config`) each organization has its own independent `webhook_secret`. Because the field used to pick the verification secret and the field used to pick the acted-upon repository are not the same and are not cross-checked against each other, an attacker who knows (or who benefits from a blank/misconfigured) `webhook_secret` for organization A can forge a signature valid for "organization: A" while setting `repository.full_name` to `"B/some-repo"`, causing Shipit to process privileged actions (sync commits, archive/unarchive stacks, create review-stack deployments, close/label PRs) for organization B's repositories without ever presenting a signature that GitHub actually computed for B.

### Finding Description
The verification callback:

    request.headers['X-Hub-Signature'],
    request.raw_post

  head(422) unless verified
  ...
end

def repository_owner

end

selects the `GitHubApp` config (and thus the HMAC secret) by `repository.owner.login`. `Shipit.github` resolves per-organization config from `secrets.github` keyed by org name when running in the multi-app schema documented for installations spanning several GitHub organizations: [2](#0-1) [3](#0-2) 

Every event handler, however, resolves the *actual* repository/stack to operate on from a completely independent field, `repository.full_name`:
```ruby

end
``` [4](#0-3) 
and this same pattern (`Repository.from_github_repo_name(params.repository.full_name)`) is repeated by every concrete handler (push, pull-request opened/closed/labeled/reopened/unlabeled), which then mutate stacks (`sync_github`, `archive!`, `unarchive!`, provisioning of review stacks): [5](#0-4) [6](#0-5) [7](#0-6) 

Nothing enforces that `repository.owner.login` (used to pick the verifying secret) equals the owner encoded in `repository.full_name` (used to pick the target `Repository`/`Stack`). The developer's implicit assumption — mirroring the root cause pattern in the referenced report, where a check on one condition was wrongly treated as covering an unrelated code path — is that these two fields always describe the same repository because that is how legitimate GitHub webhook payloads are constructed. Since the entire body is attacker-controlled before signature verification decides which secret to check it against, this assumption does not hold for a crafted, self-consistent-looking payload: `repository.owner.login = "orgA"` (verified with orgA's secret) but `repository.full_name = "orgB/some-repo"` (acted on by the handler). This is exactly the binding class called out in the rules: *"an organization that authenticated versus the repository that is written."*

Additionally, `GitHubApp#verify_webhook_signature` trivially returns `true` whenever `webhook_secret` is blank/unset for the resolved organization:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [8](#0-7) 
so in any multi-org installation where at least one configured organization has no `webhook_secret` set (shown as the default/example value `webhook_secret: # nil` in the setup docs and sample secrets files), an attacker only needs to name that unsecured organization as `repository.owner.login` while pointing `repository.full_name` at any other org's tracked repository, and the signature check passes unconditionally — with zero secret knowledge required. ### Impact Explanation
This lets an unauthenticated, unprivileged attacker (no Shipit session, no `ApiClient` token, no GitHub App private key) trigger privileged webhook-driven actions against a *different* organization's tracked stacks/repositories than the one whose signature check they satisfied: forcing commit syncs (`GithubSyncJob`), archiving/unarchiving stacks, and creating/deprovisioning review-stack deployments via `ReviewStackAdapter`. This crosses the "cross-organization write" / "unauthorized deploy or state change" boundary defined as High/Critical impact in scope, since it lets an attacker who only controls (or exploits a misconfigured) organization A cause writes against organization B's repositories/stacks that were never authorized by B's GitHub App or webhook secret.

### Likelihood Explanation
Likelihood is high specifically for the documented multi-organization deployment mode (`docs/setup.md`, "Using Multiple Github Applications") where per-organization `webhook_secret`s are set independently, since it only requires that at least one configured organization uses no webhook secret, or that the attacker can obtain/guess one org's secret to target every other org tracked by the same Shipit instance. This is a routine, unauthenticated network-reachable path (`/webhooks`), requiring only a crafted HTTP POST — no privileged credentials of any kind.

### Recommendation
Cross-validate the payload's `repository.owner.login`/`organization.login` against `repository.full_name`'s owner segment before verification is deemed successful, or better, derive the verification organization *strictly* from the same field(s) the handlers use to resolve the target repository, so a single, consistent field determines both which secret verifies the payload and which repository is acted upon. Additionally, disallow (or explicitly flag as insecure) blank `webhook_secret` configuration for any organization in a multi-app deployment, since it silently disables signature verification for that organization's namespace while remaining fully attacker-selectable via the payload.

### Proof of Concept
1. Deploy Shipit configured with the multi-organization GitHub App schema (`secrets.github` keyed by `OrgA`/`OrgB`), where `OrgA.webhook_secret` is unset/nil (as shown in the documented example) and `OrgB` has real tracked repositories/stacks.
2. POST to `/webhooks` with header `X-Github-Event: push` and a JSON body:
```json
{
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  },
  "ref": "refs/heads/main",
  "after": "<attacker chosen sha>"
}
```
3. `verify_signature` resolves `Shipit.github(organization: "OrgA")`; since `OrgA.webhook_secret` is blank, `verify_webhook_signature` returns `true` unconditionally regardless of the (even absent) `X-Hub-Signature` header.
4. `PushHandler#process` resolves `Repository.from_github_repo_name("OrgB/victim-repo")` and enqueues `GithubSyncJob` for OrgB's stack, causing Shipit to sync/act on OrgB's repository state — an action never authorized by OrgB's GitHub App/webhook secret. [11](#0-10) [5](#0-4)
