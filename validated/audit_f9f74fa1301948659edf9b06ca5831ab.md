### Title
Stack-scoped API token bypasses its `stack_id` restriction on CCMenu status endpoint - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the base controller's stack resolution and loads the target `Stack` directly from the request parameter instead of through the caller's `ApiClient`-scoped stack relation, breaking the binding between the stack a token is authorized for and the stack it actually reads.

### Finding Description
`ApiClient` records can be scoped to a single stack via `stack_id`. The base API controller enforces this scoping through the `stacks`/`stack` helper methods: `stacks` returns `Stack.where(id: current_api_client.stack_id)` when the client is stack-scoped, and `stack` is derived from that scoped relation via `stacks.from_param!(params[:stack_id])`. [1](#0-0) 

`CCMenuController`, however, defines its own `stack` method that bypasses this scoping entirely, resolving the stack directly from the unscoped `Stack` model:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [2](#0-1) 

`require_permission :read, :stack` only checks that the token's `permissions` array contains `read:stack` — it never re-checks that the requested `stack` equals the stack the `ApiClient` is scoped to: [3](#0-2) 

So the equality that should hold — `current_api_client.stack_id == stack.id` (when the client is stack-scoped) — is violated. Any valid token carrying `read:stack`, even one deliberately narrowed to a single unrelated stack, can request CCMenu XML for any other stack by supplying a different `stack_id` in the URL, because `CCMenuController#stack` never consults `current_api_client.stack_id`.

This is structurally the same class of trust-binding gap as the audited bug (a check that is supposed to gate on one value but is actually keyed on an attacker-controlled/unrelated value), here manifesting as an authorization-scope bypass instead of an unbounded loop.

### Impact Explanation
This allows a holder of any low-privilege, narrowly-scoped API token (e.g., one intentionally issued to a third-party CI dashboard for a single low-sensitivity stack) to read the CI/deploy status (`lastBuildStatus`, `lastBuildLabel`, `activity`, etc.) of every other stack in the Shipit instance, including stacks it was never granted access to. This matches the "High" impact category: unauthenticated/unauthorized read of stack state.

### Likelihood Explanation
Any organization that issues stack-scoped `ApiClient` tokens (a documented, supported feature) for least-privilege integrations is affected. Exploitation requires only possession of one such token (no special privileges beyond what is normally distributed to CI/monitoring integrations) and a simple parameter change in the request URL/query string.

### Recommendation
Change `CCMenuController#stack` to resolve through the scoped `stacks` relation (as the rest of the API controllers do), e.g. `stacks.from_param!(params[:stack_id])`, so that stack-scoped tokens cannot query stacks outside their assigned `stack_id`.

### Proof of Concept
1. Create/obtain an `ApiClient` scoped to `stack_id: X` with `permissions: ['read:stack']` (a normal least-privilege integration token).
2. Authenticate as this client and issue `GET /api/stacks/Y/cc.xml` (or the equivalent CCMenu route) where `Y` is a different stack the token was never granted.
3. Observe that the response returns Y's build/deploy status XML, even though the token's `stack_id` binds it only to X — demonstrating the scope bypass via `CCMenuController#stack`.
