### Title
`repository_owner` (webhook-verifier selector) diverges from `params.repository.full_name` (handler target selector), allowing cross-organization webhook forgery into a `merge_queue_enabled` stack - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects which `GitHubApp` (and thus which `webhook_secret`) validates the signature using `repository_owner`, defined as `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0) . Every `pull_request` handler, including `LabelCapturingHandler`, instead resolves the *target* repository/stack from the independent field `params.repository.full_name` [2](#0-1) . Because the schema only requires `repository.full_name` and not `repository.owner.login` [3](#0-2) , an attacker who omits `repository.owner.login` can steer the verifier to a different org (`organization.login`) than the org whose repo/stack is actually acted upon.

### Finding Description
The broken binding is the implicit invariant: `organization_used_to_verify_signature == organization_that_owns_the_acted_upon_repository`. In code these are two independently attacker-controlled JSON fields that are never cross-checked.

- Verification path: `verify_signature` calls `Shipit.github(organization: repository_owner)` then `github_app.verify_webhook_signature(signature, raw_post)` [4](#0-3) . `repository_owner` falls back to `params.dig('organization','login')` when `repository.owner.login` is absent [1](#0-0) .
- `Shipit.github(organization:)` looks up per-organization config via `github_app_config(organization)`, and Shipit explicitly supports multi-organization deployments where each org has its own (possibly unset) `webhook_secret` [5](#0-4) , documented in `docs/setup.md` "Using Multiple Github Applications" and exemplified in `test/dummy/config/secrets_double_github_app.yml` where `webhook_secret` is commented as `# nil` for each org.
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally `unless webhook_secret` is present [6](#0-5) . Thus for any organization configured in Shipit without a `webhook_secret` (the documented default), signature verification always succeeds regardless of the actual `X-Hub-Signature` header.
- Target path: `LabelCapturingHandler#repository` resolves `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [2](#0-1) , and `stack` is looked up via `ReviewStackAdapter#stack` using only `environment: "pr#{params.number}"` scoped to that repo's review stacks [7](#0-6) [8](#0-7) . Nothing here re-derives or checks against `repository_owner`/`organization.login` used at verification time.

Exploit request: attacker POSTs to `/webhooks` with `X-Github-Event: pull_request`, body:
```json
{
  "action": "unlabeled",
  "number": 7,
  "pull_request": {..., "labels": [{"name":"SOME_ENV=malicious"}], "head": {...}},
  "repository": {"full_name": "victim-org/victim-repo"},
  "sender": {"login": "attacker"},
  "organization": {"login": "attacker-controlled-or-secretless-org"}
}
```
`repository_owner` resolves to `"attacker-controlled-or-secretless-org"`, selecting a `GitHubApp` instance whose `webhook_secret` is unset (a documented, common configuration) or otherwise known/controlled by the attacker, so `verify_webhook_signature` returns `true` for an arbitrary/forged signature. `drop_unhandled_event` passes since `pull_request` is a handled event. The handler then processes against `victim-org/victim-repo`'s review stack, calling `pull_request.update!(labels: params.pull_request.labels.map(&:name))` on the victim's `PullRequest` record [9](#0-8) , and `ReviewStack#env` uppercases every persisted label name into an environment variable set to `"true"` merged into the stack's deploy/task environment [10](#0-9) .

None of the existing guards stop this: `drop_unhandled_event` only checks the event type, not payload consistency; the `ExplicitParameters` schema for `LabelCapturingHandler` requires `repository.full_name` but not `repository.owner.login`, so omission is schema-legal; `verify_signature`'s only defense is the per-org secret, and the org used for that defense is not the org the payload claims to target.

### Impact Explanation
This is a payload-for-one-organization-authenticating-actions-against-another-organization's-stack scenario, matching the "Critical" category (payload for one repository mutating another's stack). Concretely: (1) arbitrary environment-variable-shaped strings get written into the victim `ReviewStack`'s deploy environment via crafted label names, reaching any downstream `Command`/`PTY.spawn` environment merge for that stack's deploys/tasks; (2) on a `merge_queue_enabled: true` stack, once the PR's head commit status turns green, `Commit#add_status` triggers `stack.schedule_merges` [11](#0-10) , and `ProcessMergeRequestsJob#perform` calls `merge_request.merge!` which invokes `stack.github_api.merge_pull_request(...)` [12](#0-11) [13](#0-12) . This exists independent of the injected label but confirms the review stack's merge machinery is fully live once labels/state are attacker-influenced through a forged-org webhook. This is repeatable against any repository/organization tracked by the same Shipit instance as long as at least one configured org lacks (or has a known/attacker-controlled) webhook secret, and blast radius spans all tenants hosted by that Shipit deployment.

### Likelihood Explanation
Preconditions: a multi-organization Shipit deployment (explicitly documented and supported) where at least one configured GitHub organization has no `webhook_secret` set (the shipped example configs default to `# nil`) or whose secret the attacker can obtain by controlling that org's own GitHub App settings. Attacker cost is a single unauthenticated HTTP POST with a crafted JSON body; no Shipit session, API token, or GitHub App credentials for the victim org are required. This is fully repeatable and scriptable against any stack whose `repository.full_name` the attacker knows.

### Recommendation
Derive the verification organization strictly from `repository.full_name` (i.e., split the owner from the required, schema-enforced field) rather than from the independently-suppliable `repository.owner.login`/`organization.login`, and reject the webhook if `repository.owner.login` (when present) or the parsed owner of `repository.full_name` does not match the organization selected for verification. Additionally, require `repository.owner.login` in the top-level payload validation before dispatch, and fail closed if `webhook_secret` is unset for any organization in production configurations.

### Proof of Concept
minitest under `test/controllers/shipit/webhooks_controller_test.rb` (or `test/models/shipit/webhooks/handlers/pull_request/label_capturing_handler_test.rb` for the handler-only path):
1. Configure two orgs via `secrets_double_github_app.yml`-style config: `VictimOrg` (has `webhook_secret: "victimsecret"`), `AttackerOrg` (no `webhook_secret`).
2. Create a `Shipit::Stack`/`ReviewStack` for `VictimOrg/victim-repo`, `merge_queue_enabled: true`, with an existing pending `MergeRequest`/PR at `pr7`.
3. Build a `pull_request` `unlabeled` payload with `repository: {full_name: "VictimOrg/victim-repo"}` (no `owner` key), `organization: {login: "AttackerOrg"}`, and forged/garbage `X-Hub-Signature`.
4. Assert equality-before: `repository_owner` computed from payload equals `"AttackerOrg"`, while `params.repository.full_name` equals `"VictimOrg/victim-repo"` — these differ.
5. POST to `/webhooks` with `X-Github-Event: pull_request` and the forged signature; assert response status `200` (not `422`), proving verification passed against `AttackerOrg`'s (secret-less) `GitHubApp` instead of `VictimOrg`'s.
6. Assert the victim `PullRequest#labels` was updated per the attacker's payload, and/or that `ReviewStack#env` for the victim stack now contains the attacker-chosen uppercased key — demonstrating a payload verified under one organization mutated another organization's stack state.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

    end
```
