### Title
Same L1 Bitcoin lockup output can be re-credited across multiple `register-for-bond` calls, allowing double-counted sBTC-backed bond shares — (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
`pox-5.clar`'s `verify-l1-lockups`/`validate-l1-lockup` functions only deduplicate Bitcoin lockup outpoints *within a single call* (the `seen-outpoints` accumulator starts as an empty list on every invocation). There is no persistent, contract-wide registry of already-consumed L1 outpoints, so the same Bitcoin lockup transaction output can be submitted as proof in more than one `register-for-bond` call, crediting the same locked BTC sats multiple times toward bond share accounting.

### Finding Description
`validate-l1-lockup` verifies a Merkle proof, block header, script, and amount for a claimed BTC lockup output, and rejects duplicates only via an in-memory `seen-outpoints` list that is freshly initialized to `(list)` for every call to `verify-l1-lockups`: [1](#0-0) 

The per-output dedup guard `(asserts! (is-none (index-of? seen-outpoints outpoint)) ERR_DUPLICATE_LOCKUP_OUTPOINT)` only prevents the *same* outpoint from being counted twice *inside one list of outputs passed in a single transaction*: [2](#0-1) 

Nothing in the code I inspected persists consumed outpoints in a data map (e.g., a `used-l1-outpoints` map) that would survive across transactions/calls. As a result, a staker who has a single valid BTC lockup output can call `register-for-bond` (or the underlying bond-registration path that calls `verify-l1-lockups`) more than once, each time submitting the identical `{tx, output-index, header, leaf-hashes, ...}` proof, and each call will independently pass all checks and add `(get amount output)` to the `sum` used to credit `amount-sats` for the bond — this is the value that feeds `roll-sbtc`/`total-sbtc-staked` and the bond's share accounting (`total-shares-staked-for-cycle`, `signer-shares-staked-for-cycle`), i.e. the same mechanism that in Scenario 1 of the referenced Loop report let a single set of externally-verifiable funds be counted more than once toward a credited position.

This breaks the equality that sats credited to a staker's bond position must correspond 1:1 to sats actually and newly locked on Bitcoin (each BTC output can back only one credited position, once).

### Impact Explanation
This is a double-counting of a Bitcoin-lockup commitment: a single locked amount of BTC is credited into `total-sbtc-staked`/bond shares multiple times, entitling the staker to bond rewards, min-uSTX ratios (`min-ustx-for-sats-amount`), and reward-share proportions in excess of the BTC actually locked. Because bond rewards (`calculate-bond-rewards`, `get-rewards`) and reserve accounting distribute real sBTC/STX based on these share totals (see `calculate-rewards`/`get-total-shares-staked-for-cycle` in `pox-5.clar`), inflated shares directly dilute honest participants and can extract more sBTC rewards than were ever backed by real BTC lockups — an unbacked/duplicated credit of locked value. This matches the Critical impact bucket (double-counting a commitment or reward, unbacked minting of value against a locked amount).

### Likelihood Explanation
Likelihood is moderate-to-high assuming `register-for-bond` (or any other bond/lockup registration entrypoint) calls `verify-l1-lockups` more than once over the contract's lifetime for the same staker/output — which appears structurally possible since the guard against reuse is scoped to a single call's `fold`, not to any contract-level state. No special privileges are needed; a staker only needs to resubmit their own previously-used valid Bitcoin proof.

### Recommendation
Persist consumed outpoints in a durable map (e.g., `(define-map used-l1-outpoints {txid: (buff 32), output-index: uint} bool)`), and have `validate-l1-lockup` check/set this map (instead of, or in addition to, the transient `seen-outpoints` list) so a given Bitcoin output can never be credited toward more than one bond registration for the life of the contract.

### Proof of Concept
1. Staker locks BTC in a valid timelock output matching `construct-lockup-output-script` for their principal and bond.
2. Staker calls `register-for-bond` with a `lockups` list containing that single output; `verify-l1-lockups` validates it and credits `amount-sats` to their bond position (`roll-sbtc`, `total-shares-staked-for-cycle` updated).
3. Staker calls `register-for-bond` again (e.g., rolling into a new bond period, or re-registering) supplying the *same* `{tx, output-index, header, leaf-hashes, amount, unlock-burn-height}` proof.
4. Because `seen-outpoints` in `validate-l1-lockup`'s accumulator is re-initialized to `(list)` at the start of this new call (line 2013), the duplicate check does not fire, and the same BTC output is credited a second time, inflating the staker's `amount-sats`/bond shares without any additional BTC being locked.
