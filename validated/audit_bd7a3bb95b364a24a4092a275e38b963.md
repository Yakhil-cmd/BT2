### Title
Webhook signature is verified against the organization named in the payload, but handlers act on the repository/commit named elsewhere in that same (attacker‑controlled) payload — allowing cross‑organization webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
In a multi‑organization Shipit deployment (`config/secrets.yml` with a `github:` section keyed by organization), each GitHub organization has its own `webhook_secret`. `WebhooksController#verify_signature` selects *which* secret to verify the inbound webhook against using `repository_owner`, a value read straight out of the untrusted JSON body (`repository.owner.login` or `organization.login`). Once the signature check passes, the raw, unvalidated body is dispatched to event handlers that determine *what to act on* using a different field of the same body (`repository.full_name`), or, in the case of the status handler, no repository scoping at all. Nothing enforces that the organization used to pick the verifying secret is the same organization/repository the handler subsequently mutates.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/secret purely from the payload itself: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` resolves a distinct `webhook_secret` per organization key in `secrets.github`: [3](#0-2) 

After the signature is accepted, the entire (attacker‑supplied) body is handed to handlers unmodified: [4](#0-3) 

`Handler#stacks`/`#repository_name`, used by `PushHandler`, `CheckSuiteHandler`, `PullRequest` handlers, etc., resolves the *target* repository from `payload.dig('repository', 'full_name')` — a field completely independent from the `repository.owner.login`/`organization.login` field used for signature-org selection: [5](#0-4) 

`StatusHandler` is even weaker: it doesn't consult `repository`/`stacks` at all, it looks up `Commit` purely by `sha`, globally across the entire installation: [6](#0-5) 

Because a genuine GitHub-issued payload always has `repository.owner.login` consistent with `repository.full_name`'s owner segment, and a real `status` event's `sha` always belongs to the repository that generated it, this consistency is never validated by Shipit itself — it is only true because GitHub is the one producing the JSON. An attacker who legitimately administers *any* organization configured in this same multi‑org Shipit instance (and therefore legitimately knows *that org's* `webhook_secret`, which is not a Shipit credential and not listed among the excluded prerequisites) can:

1. Craft a raw JSON body with `repository.owner.login` = `"attacker-org"` (so `verify_signature` fetches and validates against `attacker-org`'s secret) but with `repository.full_name` = `"victim-org/victim-repo"` (or, for the `status` event, simply reuse the victim's real, publicly-visible commit `sha`).
2. Sign the raw body with `attacker-org`'s own `webhook_secret` using HMAC-SHA1, exactly as `verify_webhook_signature` expects: [7](#0-6) 
3. POST it to the shared `/github/webhooks` endpoint. `verify_signature` succeeds (it only checks that the body was signed by `attacker-org`'s key — it never checks that `attacker-org` is entitled to speak for `victim-org/victim-repo`).
4. The dispatched handler (`push`, `check_suite`, or `status`) then acts on `victim-org`'s stacks/commits: enqueuing `GithubSyncJob`/`RefreshCheckRunsJob` for a stack the attacker does not own, or — most damaging — injecting a forged, locally-trusted CI `Status` (`state: "success"`) against the victim's real commit sha via `StatusHandler`.

This is a direct analog of the reported bug class: the binding "the organization that authenticated the request" == "the repository/commit the handler subsequently writes to" is never enforced, exactly as the original report showed the binding "the strike the signer priced" == "the strike stored for the position" was never enforced.

### Impact Explanation
A forged `status` webhook writes a locally-trusted `Status` record for an arbitrary commit sha in the installation, independent of which organization/repository actually owns that commit. If the target stack's `ci.require` gates deploys on that status context, an attacker who controls only their own unrelated organization's webhook secret can manufacture a false "green" CI status for a target stack they have no legitimate relationship with, undermining the CI gate that guards deploys/merges. Forged `push`/`check_suite` events likewise let an outside organization trigger sync/check-run jobs against a stack it does not own. This crosses the "unauthorized deploy" / "cross-repository writes" impact bar defined in scope.

### Likelihood Explanation
Requires only that the attacker be a legitimate administrator of one organization/GitHub App installation configured in a shared, multi-tenant Shipit deployment (a normal, unprivileged-relative-to-the-victim-org position), plus knowledge of the victim's commit sha (trivially obtainable for public repositories, or observable from Shipit's own commit list/API for repos it already tracks). No `ApiClient` token, GitHub App private key, or the victim organization's `webhook_secret` is needed — only the attacker's own org's secret, which they hold legitimately.

### Recommendation
- In `WebhooksController#verify_signature`, after verifying the signature for the resolved organization, re-derive `repository_owner`/`organization` from the payload and require it to equal the organization actually configured for the `Repository`/`Stack` the handler will touch — i.e., look up the target `Repository` first and verify against *its* configured organization's secret, not an organization name taken opportunistically from the payload.
- In `Handler#stacks`, cross-check that `payload.dig('repository','owner','login')` (the field used to select the verifying secret) matches the owner segment of `repository_name`/`full_name` before resolving stacks.
- In `StatusHandler`, scope the `Commit` lookup by the repository named in the same verified payload (and confirm that repository belongs to the organization whose secret validated the signature), rather than a global, repository-agnostic `Commit.where(sha:)`.

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.yml`: `attacker-org` (secret `S_A`) and `victim-org` (secret `S_V`), each with an active `Repository`/`Stack`.
2. As an authorized admin of `attacker-org`'s GitHub App, build a `status` event body:
```json
{
  "sha": "<real HEAD sha of victim-org/victim-repo>",
  "state": "success",
  "context": "ci/required-check",
  "repository": {
    "full_name": "attacker-org/attacker-repo",
    "owner": { "login": "attacker-org" }
  }
}
```
3. Compute `X-Hub-Signature: sha1=` + `HMAC-SHA1(S_A, raw_body)`.
4. `POST /github/webhooks` with `X-Github-Event: status` and the above signature.
5. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and succeeds because the signature matches `S_A`.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the `victim-org/victim-repo` commit record (created when Shipit previously synced that repo), and calls `commit.create_status_from_github!(params)`, inserting a forged "success" status for the victim's stack/commit — despite the request never being signed with `victim-org`'s `webhook_secret` (`S_V`).

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
