### Title
Webhook signature verification is bound to `repository.owner.login`, not to the `repository` object the handlers act on, enabling cross-organization webhook forgery in multi-tenant configs - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
This is a structural analog of the `DefaultAccount#fallback` bug: in that report, a payload field (`value`) was acted upon by the runtime but not covered by the same guarantee that protects the rest of the call. Here, the field that selects *which secret is used to authenticate the whole payload* (`repository.owner.login` / `organization.login`) is not guaranteed to be the same field that downstream handlers use to decide *which repository/stack is mutated* (`repository.full_name`/id). In Shipit's multi-organization GitHub App mode, this breaks the intended binding: `organization whose secret verified the payload == organization owning the repository that gets written to`.

### Finding Description
`WebhooksController#verify_signature` selects the `GitHubApp` (and therefore the webhook secret) used to validate the HMAC based on data extracted from the still-unverified request body: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
end
...
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization:)` looks up a distinct, independently-configured `webhook_secret` per organization when the multi-org schema is used (`github_app_config`/`github_organizations` in `lib/shipit.rb`): [3](#0-2) 

Because the HMAC is computed over `request.raw_post` and any operator who legitimately administers one tenant organization in this Shipit instance controls that organization's `webhook_secret`, that operator can construct an arbitrary valid signature for **any** body they like, as long as `repository.owner.login` (or `organization.login`) in that body names their own org — i.e. the field that selects the verifying secret. Nothing forces the `repository.full_name`/`id` fields — which are what the event handlers (e.g. the push handler that enqueues `GithubSyncJob`, or the `status`/`membership` handlers) actually use to resolve a `Stack`/`Repository`/`Team` to mutate — to reference a repository owned by that same organization. The signature check validates "this body was HMAC'd with OrgA's secret"; it does not validate "the repository referenced anywhere in this body belongs to OrgA."

### Impact Explanation
In a multi-tenant Shipit deployment where several unrelated GitHub organizations are each configured with their own `webhook_secret` (as documented in `test/dummy/config/secrets_double_github_app.yml`), a party that only holds credentials for their own org's webhook secret can forge a signed payload whose `repository.owner.login`/`organization.login` names their own org (so it passes `verify_signature`) while the `repository` object's `full_name`/id fields point at a different tenant's repository. This lets an attacker with no access to the other tenant push forged `push`, `status`, `check_suite`, `pull_request`, or `membership` events against that other tenant's stacks/teams — triggering unauthorized `GithubSyncJob`s, forged commit statuses, or team/membership manipulation cross-tenant, i.e. cross-repository writes without the corresponding organization's real webhook secret.

### Likelihood Explanation
Exploitation requires the deployment to run in the multi-organization GitHub App configuration with more than one tenant registered, and the attacker to already legitimately hold a valid `webhook_secret` for at least one of those tenants (a low-privilege, tenant-scoped credential, not `GITHUB_TOKEN`/`api_clients_secret`/session access). This is a realistic scenario for shared/managed Shipit instances serving multiple orgs, since Shipit is explicitly designed to support that (`docs/setup.md`, `test/dummy/config/secrets_double_github_app.yml`).

### Recommendation
After computing `verified`, cross-check that every organization-identifying field actually referenced by the dispatched handler (`repository.full_name`'s owner segment, `repository.owner.login`, and `organization.login` if present) are mutually consistent and match the organization whose secret validated the signature, rejecting the webhook with `422` otherwise. Alternatively, scope `webhook_secret`s per-repository/stack instead of per-organization so that possessing one tenant's secret cannot be used to forge events referencing a different tenant's repositories.

### Proof of Concept
1. Configure two organizations in `secrets.yml` (as in `test/dummy/config/secrets_double_github_app.yml`): `OrgOne` with `webhook_secret: s1`, `OrgTwo` with `webhook_secret: s2`. Assume the attacker legitimately administers `OrgOne` and knows `s1`.
2. Attacker crafts a `push` JSON body:
   ```json
   { "repository": { "owner": {"login": "OrgOne"}, "full_name": "OrgTwo/private-repo" }, "after": "<attacker-chosen-sha>" }
   ```
3. Attacker signs the raw body with `s1`: `sha1=HMAC-SHA1(s1, body)` and sets `X-Hub-Signature`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgOne")`, retrieves `OrgOne`'s `webhook_secret` (`s1`), and successfully verifies the signature (`app/controllers/shipit/webhooks_controller.rb:24-30,59-62`).
5. `create` dispatches to `Shipit::Webhooks.for_event('push')`, whose handler resolves the target `Stack` by `repository.full_name` (`OrgTwo/private-repo`), enqueuing a sync/status update for `OrgTwo`'s repository despite the attacker never possessing `OrgTwo`'s `webhook_secret`.

Note: I was unable to fully inspect `app/models/shipit/webhooks/handlers/push_handler.rb` in this session (tool budget exhausted) to confirm the exact field it keys on for stack resolution; this should be verified directly against that handler before treating this as fully confirmed, though the controller-level signature-selection flaw shown above is confirmed from source.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
