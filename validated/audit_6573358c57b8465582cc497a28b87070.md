## Confirmed analog

In multi-organization mode, `Shipit.github(organization:)` picks a per-organization `GitHubApp` config from `secrets.github`, and each org's `webhook_secret` is documented and coded as **optional**. [1](#0-0) [2](#0-1) 

`WebhooksController#verify_signature` chooses which org's app/secret to verify against using `repository_owner`, which is read from the JSON body's `repository.owner.login` (or `organization.login`) field: [3](#0-2) 

`GithubApp#verify_webhook_signature` **unconditionally returns `true` when that org's `webhook_secret` is blank**: [4](#0-3) 

After "verification," the controller dispatches the *entire raw payload* to handlers unscoped by the org used for verification: [5](#0-4) 

Every handler determines which `Repository`/`Stack`/`Team` to mutate from a **different** field, `repository.full_name` (or `organization.login` for membership events), which is never checked against `repository.owner.login`: [6](#0-5) [7](#0-6) [8](#0-7) 

This is the same bug class as the Mantle DA report: a value is used to satisfy a boundary/authorization check (`dataStoreId`/`repository.owner.login`) while a *different, uncorrelated* value is the one actually acted upon (`dataStoreId-1` retrieval/`repository.full_name` or `organization.login` mutation target). The broken equality is:

`org authorized to sign the webhook (repository.owner.login checked by verify_signature)` ≠ `repository/organization actually written by the handler (repository.full_name / organization.login)`

## Exploit path

1. Operator configures Shipit for multiple GitHub organizations, one of which has no `webhook_secret` set (an explicitly supported, documented configuration) — e.g. `orgA` has no secret, `orgB` (the real, actively-deployed org) has one.
2. Unauthenticated attacker POSTs to `/webhooks` with `X-Github-Event: status` (or `membership`, `push`, etc.) and a body where `repository.owner.login` = `"orgA"` but `repository.full_name` = `"orgB/production-repo"` (for `membership`, `organization.login` is the field actually trusted — set that to `orgB`).
3. `repository_owner` resolves to `orgA`; `Shipit.github(organization: 'orgA')` returns an app whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the (attacker-supplied or missing) `X-Hub-Signature` header.
4. `create` then dispatches the full JSON body to `Shipit::Webhooks.for_event('status')`, whose `StatusHandler#process` looks up commits purely by `sha` (global, not scoped by org) and calls `create_status_from_github!`, or `MembershipHandler#process` adds the attacker-supplied `member.login` to a `Team` scoped by `organization.login == 'orgB'`.

## Impact

- **`membership` event → privilege escalation into `Shipit.github_teams`**: attacker adds an arbitrary GitHub login as a member of a team recognized by `Shipit.github_teams`/`oauth_teams`, which gates `authorized?` on every controller via `Shipit::Authentication#force_github_authentication`. Combined with GitHub OAuth login as that (possibly attacker-controlled) login, this is authentication/authorization bypass. [9](#0-8) [10](#0-9) 
- **`status` event → forged CI status**: `Commit#create_status_from_github!` is called with attacker-controlled `state`/`context`, which can satisfy `required_statuses`/CI gating used to determine `deployable?`, enabling an unauthorized deploy of a commit that never actually passed CI.
- **`push`/`check_suite` events**: can trigger sync jobs / check-run refresh against any tracked stack cross-org.

## Caveat

This requires the deployment to run in the documented **multi-organization** mode with at least one configured org lacking a `webhook_secret` (explicitly supported/documented as optional). In single-org mode, or if all orgs have a `webhook_secret` set, the bypass via blank secret does not apply, though the underlying design flaw (verification org ≠ mutation org/repo, taken from different payload fields) still exists and would be exploitable if any org's secret were weak/leaked. I was not able to fully verify whether other code paths (e.g., `Repository.from_github_repo_name`) apply any additional owner/org cross-check that might mitigate this beyond what's shown above.

### Title
Webhook signature verification is keyed on `repository.owner.login`/`organization.login` while handlers act on a different, uncorrelated payload field (`repository.full_name`/`organization.login` for team membership) - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub organization's app/secret to validate a webhook against using `repository.owner.login` (falling back to `organization.login`), but the handlers that actually mutate state (`StatusHandler`, `MembershipHandler`, `PushHandler`, etc.) key their lookups off different, independent fields in the same JSON body (`repository.full_name`, `organization.login`). Because per-organization `webhook_secret` is optional, any organization configured without one causes `verify_webhook_signature` to always return `true`, letting an unauthenticated attacker forge events that are verified against the secret-less org but that mutate data belonging to any other org/repo/team tracked by the Shipit instance.

### Finding Description
- Verification org selection: `app/controllers/shipit/webhooks_controller.rb:59-62` (`repository_owner`) feeds into `Shipit.github(organization: repository_owner)` at line 25.
- Signature bypass on blank secret: `lib/shipit/github_app.rb:76-77` — `return true unless webhook_secret`.
- Unscoped dispatch: `app/controllers/shipit/webhooks_controller.rb:10-15` passes the full raw JSON to all registered handlers for the event, with no re-validation tying the mutated resource back to the org that was "verified."
- Handler mutation target uses a different field: `app/models/shipit/webhooks/handlers/handler.rb:36-38` (`repository.full_name`); `membership_handler.rb:15-17,39-41` (`organization.login`); `status_handler.rb:20-24` (global `Commit.where(sha:)`, not org-scoped at all).

### Impact Explanation
- If any configured GitHub organization lacks a `webhook_secret` (an explicitly documented, optional setting), any unauthenticated attacker can send arbitrary forged webhook events that are treated as verified, and target any other organization/repository/team tracked by the instance by simply setting the "acted upon" fields (`repository.full_name`, `organization.login`) to the victim org.
- `membership` events allow adding arbitrary GitHub logins to `Team`s that gate `Shipit.github_teams` authorization — High/Critical: authorization escalation.
- `status` events allow forging commit CI status, which can satisfy deploy-gating checks and enable an unauthorized deploy — Critical.

### Likelihood Explanation
Requires a specific but explicitly-supported and documented configuration (multi-org GitHub setup where at least one org has no `webhook_secret`, e.g. an org that isn't actively deploying but is still configured). No credentials, tokens, or prior access are required — just network access to the public `/webhooks` endpoint.

### Recommendation
Bind webhook signature verification to the exact same resource identifier the handlers act on. Concretely: derive `repository_owner` and the acted-upon repository/org from the same normalized field, require every organization to have a non-blank `webhook_secret` (removing the "optional" bypass, or making it opt-in with prominent warnings and defense-in-depth like org allow-lists), and cross-check that `repository.full_name`'s owner matches the org whose secret validated the payload before dispatching to handlers.

### Proof of Concept
1. Configure `secrets.github` with two orgs: `orgA` (no `webhook_secret`) and `orgB` (has stacks/teams and a `webhook_secret`).
2. `POST /webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "team": {"id": 1, "name": "Deployers", "slug": "deployers", "url": "https://example.com"},
  "organization": {"login": "orgB"},
  "member": {"login": "attacker-controlled-login"},
  "repository": {"owner": {"login": "orgA"}}
}
```
No `X-Hub-Signature` header, or any garbage value, is required.
3. `verify_signature` resolves `repository_owner` = `"orgA"`, whose blank `webhook_secret` makes `verify_webhook_signature` return `true`.
4. `MembershipHandler#process` runs using `organization.login == "orgB"`, adding `attacker-controlled-login` to a team associated with `orgB`, which may be one of `Shipit.github_teams` gating access to that Shipit instance.

    # Backward compatibility

    else

    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations

  end

  end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',

        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",

        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
