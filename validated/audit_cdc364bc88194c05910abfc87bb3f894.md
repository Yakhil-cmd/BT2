### Title
Cross-tenant Status injection via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits purely by `sha`, with no check that the commit's owning stack/repository matches the repository that authenticated the webhook. Because SHA-1 git commit hashes are content-addressed and reproducible across repositories, an attacker who owns any repository can trigger a GitHub status webhook — authenticated only against *their own* org's webhook secret — whose free-form `description`/`target_url`/`context` gets persisted as a `Status` row on a completely different tenant's commit/stack.

### Finding Description
The claimed binding is: `Status.target_url`/`description` displayed under tenant B's stack == a value that came from a payload verified against tenant B's webhook secret.

Tracing the code:
- `WebhooksController#verify_signature` verifies the HMAC signature using `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight from the payload's `repository.owner.login` [1](#0-0) . This only proves the payload was legitimately sent by GitHub for the attacker's own org/repo — it says nothing about which commit the payload's `sha` refers to.
- `StatusHandler` only requires `sha`/`state` and accepts free-form `description`, `target_url`, `context`, `created_at` with **no repository/full_name field, no ownership check**: [2](#0-1) .
- `process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — this is a **global, unscoped lookup across all stacks/repositories in the installation**, matched solely by `sha`: [3](#0-2) .
- `Commit#create_status_from_github!` calls `statuses.replicate_from_github!(stack_id, github_status)`, where `stack_id` is taken from the *matched commit's own* `stack_id` (tenant B), not from the webhook payload: [4](#0-3) .
- `Status.replicate_from_github!` persists `description`, `target_url`, `context`, `created_at` verbatim from the attacker-controlled payload onto that row: [5](#0-4) .

Root cause: signature verification is scoped to the *organization owning the payload's declared repository*, but the actual DB write (`Commit.where(sha:)`) is scoped only by `sha`, with no join/filter against `stack.repository.full_name` matching the authenticated repository. Since git commit SHA-1s are reproducible byte-for-byte across independent repositories (attacker can `git fetch` a public commit from tenant B's repo and push the identical commit object into a repository A they own), the attacker can produce a real, validly-signed GitHub status webhook for repo A whose `sha` collides with a commit ingested into tenant B's stack. `StatusHandler` then writes attacker-supplied `target_url`/`description` onto tenant B's `Status`, attributed to tenant B's `stack_id`.

None of the existing guards prevent this: `verify_signature` validates the org matches the payload's *own* declared repo, not the target stack; `drop_unhandled_event` only filters by event type; the `ExplicitParameters` schema for `StatusHandler` has no repository field to validate against; there is no `subset`/format validator on `Status` fields restricting them to same-repo origin.

### Impact Explanation
An attacker who controls any GitHub repository (or any CI/integration capable of posting a `status` event for their own repo) can write attacker-controlled `target_url`, `description`, and `context` strings into another tenant's `Status` records, which are rendered in that tenant's stack UI as CI/status information without any indication of a foreign origin. This is a "payload for one repository mutating another's stack/commit" scenario — Critical per the impact rubric. It is repeatable against any tenant/stack whose commits are known/public (attacker can pick any target commit sha they can reproduce), and blast radius spans the whole Shipit installation, not just repos in the attacker's own GitHub organization.

### Likelihood Explanation
Preconditions: attacker needs (1) a GitHub repository they control (trivial — any free GitHub account), and (2) the ability to reproduce a target commit's exact SHA — achievable by fetching the target public commit and pushing the identical object into their own repo (SHA is a hash of tree/parents/author/committer/timestamps/message, all reproducible by copying the object), and (3) the ability to fire the standard GitHub Status webhook (e.g., via GitHub's Statuses API, hooked up through their own CI on repo A, or a third-party status-posting integration). No Shipit secrets, sessions, or tokens are needed. This is realistically feasible for any public target repository and is fully repeatable.

### Recommendation
Scope the commit lookup in `StatusHandler#process` (and other handlers doing `Commit.where(sha:)` lookups) to commits whose `stack.repository` matches the payload's authenticated `repository.full_name`, e.g. `Commit.joins(:stack).merge(Stack.where(repository: matching_repo)).where(sha: params.sha)`, rather than a bare global sha lookup.

### Proof of Concept
Minitest plan (no live GitHub, using existing webhook test infra):
1. Create `stack_a` bound to repo `"attacker/repo-a"` and `stack_b` bound to repo `"victim/repo-b"`, each with the sha `shared_sha`, using `Commit.create!(stack: stack_a, sha: shared_sha, ...)` and `Commit.create!(stack: stack_b, sha: shared_sha, ...)` (simulating the real-world SHA collision precondition).
2. Post a `status` webhook payload with `repository.full_name = "attacker/repo-a"`, `sha: shared_sha`, `target_url: "http://evil.example/payload"`, signed with `stack_a`'s (or org A's) webhook secret, to `POST /webhooks`.
3. Assert: `Status.where(commit: stack_b.commits.find_by(sha: shared_sha)).last.target_url == "http://evil.example/payload"` — i.e., the value supplied only in a payload authenticated for repo A ends up on stack B's `Status`, even though no request was ever signed with stack B's webhook secret.
4. Compare against the intended binding: `stack_b`'s `Status#target_url` should only ever be settable by a payload verified against `stack_b`'s (`victim/repo-b`'s) webhook secret — assert this is violated.
