### Title
Unfiltered `BASH_ENV` injection via PR label name reaches `deploy.override` process env - (File: app/models/shipit/review_stack.rb)

### Summary
`ReviewStack#env` merges every pull request label name (uppercased) into the stack environment hash with no key allowlist, unlike the explicit `env` parameter path which is sanitized by `EnvironmentVariables#permit`. Because this unfiltered hash flows into `TaskCommands#env` → `Command#start` → `PTY.spawn(unbundled_env, ...)`, an attacker who can label their own review-stack PR (e.g., with label `bash_env`) can set `BASH_ENV=true` in the spawned deploy process's environment, causing bash to source an attacker-committed file named `true` before running the `deploy.override` script.

### Finding Description
The broken binding: the process environment reaching `PTY.spawn` for a review stack's `deploy.override` step should equal `Command::BASE_ENV.merge(machine env from shipit.yml).merge(EnvironmentVariables.permit(deploy_variables))` — i.e. every key must be allowlisted by `deploy_variables`. In practice it equals that plus an **unfiltered** hash derived from PR label names.

Trace:
- `ReviewStack#env` merges `pull_request.labels.each_with_object({}) { |n,h| h[n.upcase] = "true" }` into the stack env with no key allowlist: [1](#0-0) 
- PR labels are persisted straight from the webhook body with no key restriction by `LabelCapturingHandler#capture_labels`: [2](#0-1) 
- `TaskCommands#env` merges `@stack.env` (which is `ReviewStack#env` for review stacks) directly into the full task/deploy environment, with no call to `EnvironmentVariables.permit`: [3](#0-2) 
- `DeployCommands` (a `TaskCommands` subclass) runs `deploy.override` steps via `perform`, passing that same unfiltered `env:` to each `Command.new`: [4](#0-3) [5](#0-4) 
- `Command#start` spawns the process with `unbundled_env`, which merges `@env.stringify_keys` (including the attacker-supplied `BASH_ENV`) on top of `BASE_ENV`/`PATH`, with no key filtering at all: [6](#0-5) 

Contrast this with the deliberately sanitized path: user-submitted deploy `env` params are filtered through `filter_deploy_envs`/`EnvironmentVariables#permit`, which raises `NotPermitted` for any key not declared in `deploy_variables`: [7](#0-6) [8](#0-7) . This allowlist exists specifically because arbitrary env keys reaching the deploy process are dangerous, but `ReviewStack#env`'s label-derived keys never pass through it.

Attacker flow: open a PR from a fork against a repository with `review_stacks_enabled` and `provisioning_behavior` of `allow_with_label` (or `allow_all`), apply the label `bash_env` to that PR, and ensure the fork branch commits a file literally named `true` at the deploy working directory root containing malicious bash code. On the next `deploy.override` run (a shell script, typically with a `#!/bin/bash` shebang), bash — regardless of script content — sources `$BASH_ENV` unconditionally for non-interactive, non-login invocations, executing the attacker's `true` file with the privileges of the Shipit deploy host process.

Existing guards do not stop this: webhook signature verification only authenticates that the payload came from GitHub, not that label content is safe; `LabelCapturingHandler`'s params schema only requires `labels[].name` to be a `String`, imposing no character/keyword restriction; and `EnvironmentVariables#permit`/`filter_deploy_envs` is never invoked on the label-derived hash.

### Impact Explanation
Arbitrary code execution on the Shipit deploy host in the context of the deploy process for the targeted repository's review stack — Critical RCE per the Immunefi/HackerOne classification for `Command`/`PTY.spawn`. The attack is repeatable against any repository that has review stacks enabled with `allow_with_label`/`allow_all`, requiring only the ability to label a PR and to commit a file to the fork branch. Blast radius is limited to the deploy host process for that stack, but since Shipit deploy hosts commonly hold `GITHUB_TOKEN` and other deploy-time secrets in the base environment, an attacker with code execution in the spawned process can exfiltrate those values, compounding the impact.

### Likelihood Explanation
Preconditions: the target repository must have `review_stacks_enabled` and a `provisioning_behavior` of `allow_with_label` or `allow_all`; per the stated threat model, an unprivileged attacker can open a PR from a fork and label their own PR. Attacker cost is low — one PR, one label, one committed file named `true`. The mechanism (bash sourcing `$BASH_ENV` for non-interactive shells) is a standard, well-documented bash behavior, making exploitation reliable and repeatable once the preconditions are met.

### Recommendation
Restrict the keys merged from PR labels in `ReviewStack#env` to a safe, non-overlapping namespace (e.g., prefix all label-derived keys with a fixed, non-shell-significant prefix such as `SHIPIT_LABEL_`), or explicitly deny any label name that collides with a security-sensitive environment variable (`BASH_ENV`, `ENV`, `LD_PRELOAD`, `PATH`, `IFS`, etc.). More robustly, route the label-derived hash through `EnvironmentVariables#permit` with an explicit allowlist, consistent with how `filter_deploy_envs`/`filter_rollback_envs` already sanitize user-submitted env vars.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_test.rb (new test)
test "#env does not allow labels to inject BASH_ENV into the deploy process" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["bash_env"]

  env = Shipit::DeployCommands.new(stack.trigger_continuous_delivery).env

  # Broken binding demonstrated: label-derived env is unfiltered.
  assert_equal "true", env["BASH_ENV"]

  # Expected invariant (currently violated): deploy.override env should never
  # contain a fork-controllable BASH_ENV key.
  refute env.key?("BASH_ENV"), "deploy env must not allow fork-controlled BASH_ENV"
end
```
This demonstrates that `Shipit::DeployCommands#env` (built from `ReviewStack#env`) contains an attacker-controlled `BASH_ENV` key reaching the same `env` hash passed to `Command.new`/`PTY.spawn`, with no allowlist filtering applied, unlike the sanitized `filter_deploy_envs` path.

    def start(&block)
      return if @started

      @control_block = block
      @out = @pid = nil
      FileUtils.mkdir_p(@chdir)
      begin
        @out, child_in, @pid = PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)
        child_in.close
      rescue Errno::ENOENT
        raise NotFound, "#{Shellwords.split(interpolated_arguments.first).first}: command not found"
      rescue Errno::EACCES
        raise Denied, "#{Shellwords.split(interpolated_arguments.first).first}: Permission denied"
      end
      @started = true
      self
    end

    def unbundled_env
      BASE_ENV.merge('PATH' => "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}").merge(@env.stringify_keys)
    end
