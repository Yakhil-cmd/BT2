### Title
Unvalidated `P2PStakingInfo.BlockNum` in FastSync Allows Malicious Peer to Corrupt Staking DB at Arbitrary Block Numbers — (`datasync/downloader/queue.go`, `datasync/downloader/downloader.go`)

---

### Summary

During FastSync, the `DeliverStakingInfos` function in `queue.go` contains a deliberately empty `validate` callback (marked `// TODO-Kaia-Snapsync update validation logic`). This means a malicious peer can return a `P2PStakingInfo` whose `BlockNum` field is set to any arbitrary value. Both `commitFastSyncData` and `commitPivotBlock` then call `PutStakingInfoToDB(result.StakingInfo.BlockNum, ...)` using the peer-supplied `BlockNum` as the DB key, never cross-checking it against the validated `result.Header.Number`. The result is that the staking DB can be written at an attacker-chosen block number, corrupting the validator set and reward distribution data for that epoch.

---

### Finding Description

**Step 1 — No-op validation in `DeliverStakingInfos`** [1](#0-0) 

The `validate` closure passed to the generic `deliver` function unconditionally returns `nil`. There is no check that `stakingInfoList[index].BlockNum == header.Number.Uint64()`. The `reconstruct` closure blindly assigns the peer-supplied `P2PStakingInfo` (including its `BlockNum`) to `result.StakingInfo`.

**Step 2 — Peer-supplied `BlockNum` used as DB key**

In `commitFastSyncData`: [2](#0-1) 

In `commitPivotBlock`: [3](#0-2) 

Both functions call `PutStakingInfoToDB(result.StakingInfo.BlockNum, ...)`. The `result.Header` is the cryptographically-validated header (its hash is verified against the skeleton chain), but `result.StakingInfo.BlockNum` is entirely peer-controlled and is never compared to `result.Header.Number`.

**Step 3 — DB key determines which epoch uses the data** [4](#0-3) 

`GetStakingInfo(num)` computes `sourceNum = sourceBlockNum(num, ...)` and reads `ReadStakingInfo(s.ChainKv, sourceNum)`. If the attacker has written corrupted data at `sourceNum`, that data is returned directly from the DB without re-verification. The fallback to state is only reached when the DB entry is absent; a present-but-wrong entry is consumed as-is.

**Step 4 — DB write is unconditional** [5](#0-4) 

`WriteStakingInfo` writes whatever `StakingInfo` it receives at whatever `num` it is given, with no bounds or consistency check.

**Contrast with the recovery path**, which *does* validate: [6](#0-5) 

The `SyncStakingInfo` recovery goroutine explicitly checks `d.stakingInfoRecoveryBlocks[0] != stakingInfo.BlockNum` and aborts on mismatch. The FastSync path has no equivalent guard.

---

### Impact Explanation

A malicious FastSync peer can write staking info for block N (a legitimate staking-interval block) into the DB slot for an arbitrary block M. Consequences:

1. **Block M's staking slot is overwritten** with data from block N — wrong `NodeIds`, `RewardAddrs`, and `StakingAmounts` for that epoch.
2. **Block N's staking slot is never written** — the node falls back to state, which is unavailable during FastSync, causing `getFromStateByNumber` to fail and the node to use an empty `StakingInfo`.
3. Both effects cause **wrong validator set selection and incorrect KAIA reward distribution** for the affected epochs, meeting the "unauthorized reward distribution affecting KAIA" impact gate.

The staking info is explicitly described as the primary input for validator set and reward distribution: [7](#0-6) 

---

### Likelihood Explanation

- FastSync is the standard mode for any new node joining the network.
- P2P peer connections are permissionless; any node can act as a sync peer.
- The attack requires only that the malicious peer be selected as the staking-info provider for one or more blocks, which is the normal operation of `ReserveStakingInfos`.
- No cryptographic break, key compromise, or validator-majority collusion is required.

---

### Recommendation

In `DeliverStakingInfos`, replace the no-op `validate` closure with an actual check:

```go
validate := func(index int, header *types.Header) error {
    if stakingInfoList[index].BlockNum != header.Number.Uint64() {
        return fmt.Errorf("staking info block number mismatch: got %d, want %d",
            stakingInfoList[index].BlockNum, header.Number.Uint64())
    }
    return nil
}
```

Additionally, in `commitFastSyncData` and `commitPivotBlock`, use the validated header number as the DB key rather than the peer-supplied field:

```go
d.stakingModule.PutStakingInfoToDB(result.Header.Number.Uint64(), staking.ToStakingInfo(result.StakingInfo))
```

### Proof of Concept

1. Stand up a fork test with a chain where `StakingUpdateInterval = 1000`.
2. Configure a malicious peer that, when asked for staking info for block hash of block 2000, returns a `P2PStakingInfo` with `BlockNum = 3000` (a different staking interval block) and fabricated `RewardAddrs`.
3. Run FastSync against this peer.
4. After sync, assert:
   - `ReadStakingInfo(db, 3000)` returns the fabricated data (attacker-chosen `RewardAddrs`).
   - `ReadStakingInfo(db, 2000)` returns `nil`.
5. Call `GetStakingInfo(2001)` (which computes `sourceNum = 1000`) — this will succeed from state. Call `GetStakingInfo(3001)` (which computes `sourceNum = 2000`) — DB miss, state unavailable during FastSync, returns error or empty info.
6. Observe that reward distribution for the epoch covering blocks 3001–4000 uses the attacker-supplied validator set from the DB entry at 3000.

func (s *StakingModule) GetStakingInfo(num uint64) (*staking.StakingInfo, error) {
	isKaia := s.ChainConfig.IsKaiaForkEnabled(new(big.Int).SetUint64(num))
	sourceNum := sourceBlockNum(num, isKaia, s.stakingInterval)

	// Try cache first
	if si, ok := s.stakingInfoCache.Get(sourceNum); ok {
		return si.(*staking.StakingInfo), nil
	}

	// Only before Kaia, try the database
	if !isKaia {
		if si := ReadStakingInfo(s.ChainKv, sourceNum); si != nil {
			s.stakingInfoCache.Add(sourceNum, si)
			return si, nil
		}
	}
