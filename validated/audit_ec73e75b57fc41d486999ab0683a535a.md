Found it: `HooksController#create` in the API namespace binds the created `Hook` to a stack derived from the URL path, but does not verify the resource against the stack an `ApiClient` token is authorized for.

### Title
Stack-scoped API token can create/read/modify global (unscoped) webhook configuration - ([File: app/controllers/shipit/api/hooks_controller.rb])

### Summary
An `ApiClient` token can be limited to a single stack via `stack_id` [1](#0-0) . The `stacks`/`stack` helpers correctly restrict stack-scoped resources such as deploys and tasks to that one stack. However `Shipit::Api::HooksController` computes its own scope independently via `stack_id`, which returns `nil` whenever `params[:stack_id]` is absent [2](#0-1) , and `Hook.where(stack_id: nil)` are the **global** hooks that fire for every stack in the installation [3](#0-2) .

### Finding Description
`config/routes.rb` mounts hooks both nested under a stack (`/api/stacks/*stack_id/hooks`) and at the top level (`/api/hooks`) [4](#0-3) . Both routes point to the same `HooksController`, whose `hooks`/`hook` scoping is keyed only off `params[:stack_id]` [5](#0-4) , not off the `stacks`/`stack` helpers that enforce `current_api_client.stack_id` restriction. `require_permission :write, :hook` only checks that the token has the generic `write:hook` permission bit [6](#0-5) , `check_permissions!` never compares the client's authorized stack against the resource actually being written [7](#0-6) . So a token issued (and displayed to its owner) as "restricted to stack X" can hit the un-nested `/api/hooks` route and create/update/destroy a global hook (`stack_id: nil`) that delivers events for **every** stack, or enumerate/modify hooks belonging to other stacks it was never meant to touch, as long as it possesses `write:hook`/`read:hook`. This is exactly the audit's bug class: the token's authorized stack scope (equivalent to "credit"/binding intended to equal the resource acted on) diverges from the stack the write actually touches — `authorized_stack == acted_on_stack` is broken.

### Impact Explanation
Global hooks deliver a signed payload (with the hook's own `secret`) to an attacker-controlled `delivery_url` for every deploy/rollback/lock/commit_status/merge/pull_request event across the entire Shipit installation, not just the one stack the token owner was granted [8](#0-7) . This is a cross-repository/cross-stack information exfiltration and write primitive achievable with a token that was supposed to be confined to a single stack, matching the "cross-repository writes / unauthorized escalation into authorization scope" impact bar.

### Likelihood Explanation
Requires possession of a stack-scoped `ApiClient` token with `write:hook` or `read:hook` permission — a token an operator would reasonably believe is confined to one stack. Given such a token (a normal, lower-trust credential many integrations receive), exploitation is a single unauthenticated-scope-check-bypassing API call to `/api/hooks`, no other privilege needed.

### Recommendation
Make `HooksController#hooks`/`#hook` honor `current_api_client.stack_id` the same way `BaseController#stacks`/`#stack` do: if the client is stack-scoped, restrict to `Hook.where(stack_id: current_api_client.stack_id)` and reject requests to the global `/api/hooks` collection (or requests naming a different `stack_id`) instead of deriving scope solely from the request path.

### Proof of Concept
1. Create an `ApiClient` with `stack_id: <stack A>.id` and permissions `["write:hook"]`.
2. Using that token, `POST /api/hooks` (the un-nested route) with `delivery_url`, `events: ["deploy"]` — no `stack_id` param.
3. `HooksController#stack_id` returns `nil` (params[:stack_id] absent), so `hooks` resolves to `Hook.where(stack_id: nil)`, creating a **global** hook that will fire on deploys for every stack in the Shipit instance, even though the token was authorized only for stack A. [9](#0-8)
