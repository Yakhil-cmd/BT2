`check_permissions!` in [1](#0-0)  only checks that the operation/scope string (e.g. `read:stack`) is in the client's `permissions` array — it never checks `stack_id`. Stack scoping is entirely delegated to the `stacks`/`stack` helper methods in `BaseController`.

### Title
Cross-stack unauthorized read via `Api::CCMenuController#stack` bypassing scoped lookup - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Api::CCMenuController` overrides `#stack` to call `Stack.from_param!(params[:stack_id])` directly instead of using the tenant-scoped `stacks.from_param!` from `BaseController`, so an `ApiClient` token scoped to stack A can fetch CCMenu build-status XML for any other stack B by ID/permalink.

### Finding Description
The intended binding is: the stack resolved by any Api controller's `#stack` method must be an element of `Stack.where(id: current_api_client.stack_id)` when `current_api_client.stack_id?` is true, as enforced by `BaseController#stacks`/`#stack` ( [2](#0-1) ).

`Api::CCMenuController` breaks this binding by redefining `#stack` to call `Stack.from_param!(params[:stack_id])` directly, without going through `stacks` ( [3](#0-2) ). This method resolves any stack in the system regardless of `current_api_client.stack_id`.

Attack flow: attacker holds a valid API token for `ApiClient` with `permissions=['read:stack']` and `stack_id=A.id`. `require_permission :read, :stack` is declared on the controller ( [4](#0-3) ) and is enforced via `ApiClient#check_permissions!`, which only checks that `"read:stack"` is present in the `permissions` array — it never compares `stack_id` to the requested stack ( [1](#0-0) ). The attacker sends `GET /stacks/:stack_id/ccmenu.xml?token=<token>` (per `authenticate_api_client` override reading the token from `params[:token]`, [5](#0-4) ) with `:stack_id` set to stack B's `to_param`. `#show` calls `stack.deploys_and_rollbacks.last` and renders the CCMenu XML for stack B ( [6](#0-5) ), which exposes stack B's latest deploy/rollback status, branch, and environment info to a token that was never granted access to stack B.

All other Api subcontrollers I inspected (`StacksController`, `CommitsController`, `DeploysController`, `LocksController`, `MergeRequestsController`, `OutputsController`, `ReleaseStatusesController`, `RollbacksController`, `TasksController`, `HooksController`) correctly call `stack`/`stacks` inherited from `BaseController` (or `stacks.from_param!` as `StacksController` does, [7](#0-6) ), preserving the scoping. `CCMenuController` is the sole exception.

### Impact Explanation
An attacker with any valid stack-scoped `read:stack` token can read the CCMenu build-status feed (latest deploy/rollback id, status, timestamp) for every stack in the Shipit instance, not just the one their token was issued for. This is an unauthenticated-for-that-resource read of stack state across tenants — matching the High severity category ("unauthenticated read of stack state ... for a repository that did not authenticate it"). It does not expose secrets or allow writes/deploys, and is limited to the data exposed by the `shipit/ccmenu/project` view (deploy id, timestamp, running status), so it does not rise to Critical.

### Likelihood Explanation
The attacker needs only a legitimately issued, narrowly-scoped `ApiClient` token with `read:stack` permission for any single stack (a low bar — e.g., an internal integration credential for one team's stack). No GitHub secrets, sessions, or admin roles are required. The target stack B only needs to exist and be enumerable/guessable via its `to_param` (id or repo/env-based permalink, depending on `Stack#to_param`/`from_param!` implementation). The request is a single unauthenticated-beyond-token `GET`, fully repeatable against arbitrary stack IDs.

### Recommendation
Remove the `#stack` override in `Api::CCMenuController` and use the inherited, properly scoped `stack` method from `BaseController` (i.e., delete lines 29-31 of `app/controllers/shipit/api/ccmenu_controller.rb` and let it fall through to `stacks.from_param!(params[:stack_id])`), so CCMenu requests are subject to the same `current_api_client.stack_id` scoping as every other Api endpoint.

### Proof of Concept
Minitest plan (no live GitHub needed):
1. Create `stack_a = shipit_stacks(:shipit)` and `stack_b` (a second stack, different repo/environment).
2. Create `api_client = ApiClient.create!(creator: shipit_users(:walrus), name: 'scoped', permissions: ['read:stack'], stack: stack_a)`.
3. Generate `token = api_client.authentication_token`.
4. `get "/stacks/#{stack_b.to_param}/ccmenu.xml", params: { token: token }`.
5. Assert current (vulnerable) behavior: `response.status == 200` and body contains stack B's project name — demonstrating cross-stack leak.
6. After the fix (using scoped `stack`), assert `response.status == 404` (or whatever `ActiveRecord::RecordNotFound` maps to), matching the behavior already verified for `Api::StacksController#show` with the same token/`stack_b` combination returning 404.
