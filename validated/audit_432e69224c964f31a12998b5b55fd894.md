### Title
In-memory cache marks a conflicting unit `temp-bad` before its DB transaction commits, with no rollback if the write later fails - (File: writer.js)

### Summary
`writer.saveJoint()` mutates the shared, process-wide `storage.assocUnstableUnits` cache to mark a competing unit's `sequence` as `'temp-bad'` while still inside an uncommitted DB transaction. If the transaction that carries this side-effect subsequently fails and is rolled back, the persisted `sequence` on disk reverts to `'good'`, but the in-memory cache mutation is never undone — the shared object stays marked `temp-bad` for the remainder of the process's runtime. This mirrors the ntfs3 CVE-2025-38615 pattern: a shared, live object (there: an inode reachable via dentry alias; here: a unit object reachable via `storage.assocUnstableUnits` and used by every subsequent validation) gets permanently marked "bad" as a side effect of an operation that itself did not durably succeed, with no path to cancel/undo that marking.

### Finding Description
When validating a new unit that conflicts with an existing unstable unit on the same address (a potential double-spend), `validateAuthor()`'s `checkSerialAddressUse()` in `validation.js` schedules an additional SQL update to flip the loser's `sequence` to `'temp-bad'`: [1](#0-0) 

That scheduled query is executed by `writer.saveJoint()`. Crucially, when the additional query text matches `/temp-bad/`, the writer directly mutates the **in-memory, shared** cache entry for the conflicting unit *before* the surrounding DB transaction is committed: [2](#0-1) 

This happens at the very start of `initConnection`'s callback, i.e. before any of the later operations (`updateBestParent`, `updateLevel`, `updateMainChain`, `preCommitCallback`, batch write to kvstore) have run or succeeded. Those later operations can still fail (`err` is captured at line 662), causing the surrounding SQL transaction to be `ROLLBACK`ed instead of `COMMIT`ed: [3](#0-2) 

The error-recovery path only clears `assocUnstableMessages[objUnit.unit]` and calls `storage.resetMemory(conn)` — but `resetMemory` operates against the just-failed unit's own bookkeeping; the `objConflictingUnitProps.sequence = 'temp-bad'` mutation made at line 71 is a mutation on a **different, unrelated unit object** (the loser of the conflict) that was applied unconditionally and speculatively, with no corresponding revert regardless of whether the write ultimately commits or rolls back.

Because `storage.assocUnstableUnits` is the authoritative, globally shared in-process cache consulted by every subsequent validation (`checkSerialAddressUse`, `main_chain.js` stabilization logic that inspects `.sequence` when computing final serial ordering, etc.), a spuriously-and-permanently `temp-bad`-marked unit will be treated as non-serial/losing in all future comparisons, even though the database itself still shows it as `'good'` after the rollback. This is exactly the "cancel set bad [object] after operation fails" bug class: the marking action is not conditioned on, and not undone by, the failure/rollback of the operation that was supposed to justify it.

### Impact Explanation
`sequence` determines whether a unit's payment inputs are treated as valid/unique (serial) or as void (`final-bad`/`temp-bad`, excluded from stabilization and eventually archived). A unit incorrectly and permanently stuck at `'temp-bad'` in the shared cache, while the database says `'good'`, creates a persistent disagreement between a node's in-memory validation state and its on-disk truth for the rest of the process's uptime:
- The affected unit's payment(s) could be permanently treated as non-serial by this node while other honest nodes (or this node after a restart re-reading truth from DB) treat it as good — a node disagreement on validity/serial-ness that can manifest as unauthorized loss of spendability for the legitimate unit's outputs, or incorrect double-spend resolution once the "winner" is later archived/purged based on stale in-memory state (`main_chain.js` stabilization and `joint_storage.purgeUncoveredNonserialJoints` rely on `sequence` from the DB, but downstream serial-address-use checks and validation of subsequent units by the same address consult the in-memory cache first, per `checkSerialAddressUse`).
- Because the mutation persists only in the affected node's process memory, it produces divergent local behavior (freezing/incorrectly rejecting future spends from an address, or misjudging stability of a chain) versus the network's actual consensus state — a node-disagreement/availability-of-confirmation class impact.

### Likelihood Explanation
This requires only a legitimate double-spend/conflicting-unit scenario reaching `validateAuthor()`'s serial-address-use conflict path (`objValidationState.arrAdditionalQueries` populated with a `temp-bad` update) combined with any later failure in the same `saveJoint()` call before commit (e.g., `updateBestParent`/`updateLevel`/`updateMainChain`/`preCommitCallback` throwing, or the AA-trigger commit path failing) — a reachable path from any unprivileged user submitting two conflicting units to the same address. No special privileges are required; only two units from the same address with an address-def-triggered conflict, one of which is followed by a later-stage write failure, are needed.

### Recommendation
Defer the in-memory `sequence = 'temp-bad'` mutation of `storage.assocUnstableUnits[conflicting_unit]` until the transaction is confirmed committed (move the mutation into the success branch of `commit_fn`, alongside other cache updates that are already conditioned on `!err`), or explicitly revert it in the `if (err) { ... }` rollback branch of `writer.js` so that a failed/rolled-back write can never leave a shared, live unit object in a "bad" state that disagrees with persisted DB truth.

### Proof of Concept
1. Post unit A from address X (accepted as `'good'`).
2. Post unit B from the same address X that conflicts with A (a double-spend at the same address), such that `checkSerialAddressUse()` in `validation.js:1334-1339` schedules an `arrAdditionalQueries` entry to set A's `sequence='temp-bad'`.
3. During `writer.saveJoint()` for unit B, before the surrounding SQL transaction commits, the loop at `writer.js:58-74` immediately sets `storage.assocUnstableUnits[A].sequence = 'temp-bad'` in the shared cache.
4. Arrange (or simply rely on any natural occasional failure of) one of the later async operations in the same `saveJoint()` call (`updateBestParent`, `updateLevel`, `updateMainChain`, or a throwing `preCommitCallback`) to fail, causing `err` to be set at `writer.js:662` and the transaction to `ROLLBACK` at `writer.js:702`.
5. After rollback, `SELECT sequence FROM units WHERE unit=A` shows `'good'` (unchanged, transaction rolled back), but `storage.assocUnstableUnits[A].sequence` remains `'temp-bad'` in the running process's memory, since nothing reverts it — verifiable by inspecting `storage.assocUnstableUnits[A]` after the failed write and comparing it to the DB row.
