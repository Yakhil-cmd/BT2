### Title
Webhook signature verification keys off `repository.owner.login` while every handler acts on the attacker-controlled `repository.full_name` — enabling cross-organization forged push/status/check events - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to validate the HMAC signature against using `repository_owner`, a field read straight out of the *unverified* JSON body. Every webhook `Handler` (in `app/models/shipit/webhooks/handlers/handler.rb`) then locates the `Stack`/`Repository` to act on using a *different* field from the same unverified body: `repository.full_name`. Nothing binds these two fields together. An attacker who legitimately controls the GitHub App/webhook secret for *any one* organization configured in this Shipit instance can forge a webhook whose `repository.owner.login` matches their own org (so the signature check passes) while `repository.full_name` names a stack belonging to a completely different, unrelated organization also hosted on the same Shipit instance. This is directly analogous to the reported Blackhole bug: the entity that is authenticated (the pair address / here, the signing organization) is not the entity that is actually acted upon (the deposit / here, the target repository).

### Finding Description
- `verify_signature` in `app/controllers/shipit/webhooks_controller.rb:24-49` does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where `repository_owner` (line 59-62) is `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` — both taken from the raw, attacker-supplied JSON body, before any cryptographic check has happened. [1](#0-0) [2](#0-1) 

- `Shipit.github(organization:)` in `lib/shipit.rb:170-181` looks up a *per-organization* `GitHubApp` (and thus a per-organization `webhook_secret`) when Shipit is configured for multiple GitHub organizations, as documented in `docs/setup.md` ("Using Multiple Github Applications") and exercised by `test/dummy/config/secrets_double_github_app.yml`. [3](#0-2) [4](#0-3) 

- Once the signature is accepted, `Handler#stacks` (used by every handler, e.g. `PushHandler`, `CheckSuiteHandler`) resolves the target using an entirely different, still-unverified field:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [5](#0-4) 

- `PushHandler#process` uses that resolved stack, plus attacker-supplied `after` (the target SHA) and `ref` (the branch), to trigger a repository sync:
```ruby
stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
``` [6](#0-5) 

- `CheckSuiteHandler` and `StatusHandler` similarly act on `stacks`/`Commit.where(sha:)` derived from body content that is disjoint from the field used for signature-organization selection. [7](#0-6) [8](#0-7) 

The binding that should hold is:
`organization whose secret produced a valid signature == organization that owns the repository being acted upon`

but the code only enforces:
`organization named in payload.repository.owner.login == organization whose secret produced the signature`

with **no** check that `payload.repository.owner.login == owner(payload.repository.full_name)`, and no check that the resolved `Stack`/`Repository` actually belongs to the organization used for signing.

### Impact Explanation
On a Shipit deployment configured with multiple GitHub organizations (the officially documented and supported "Using Multiple Github Applications" setup), any actor who controls the webhook secret for one hosted organization (e.g., because they are an admin of a GitHub App installed for their own, unrelated org "OrgA" onto the same shared Shipit instance) can forge a `push` (or `check_suite`/`status`) webhook where:
- `repository.owner.login = "OrgA"` (so the HMAC check passes with OrgA's secret), and
- `repository.full_name = "OrgB/production-app"` (an org they have no access to at all).

Shipit will accept this event and call `stack.sync_github(expected_head_sha: <attacker-chosen sha>)` against the OrgB stack. If continuous deployment/continuous delivery is enabled on the target stack, this can trigger unintended sync/refresh-status/check-run flows and downstream deploy pipeline behavior driven by attacker-chosen `ref`/`after`/`sha` values for a repository the attacker does not control — a cross-organization write into another tenant's deployment state, achieved purely by forging the un-signed correlation between the authenticated principal (signing organization) and the acted-upon principal (target repository/stack).

### Likelihood Explanation
Requires the host to run the documented multi-organization configuration (multiple GitHub orgs behind one Shipit instance, each with its own `webhook_secret`) and requires the attacker to legitimately possess a valid webhook secret for at least one of the configured organizations (e.g., because they administer their own org's GitHub App that happens to also be onboarded to the shared Shipit instance). This is a realistic deployment topology explicitly supported and documented by the engine (`docs/setup.md`, `secrets_double_github_app.yml`), not a hypothetical misconfiguration. No GitHub App private key, `ApiClient` token, or Shipit user session is needed — only a webhook secret the attacker is entitled to have for their own org.

### Recommendation
Bind the verified organization to the acted-upon repository: after computing `github_app`/`repository_owner` for signature verification, re-derive the owner from `repository.full_name` (or the resolved `Repository#owner`) and require it to match `repository_owner`/the organization whose secret validated the signature before dispatching to any `Handler`. Alternatively, scope `Handler#stacks` lookups to `Repository.where(owner: repository_owner)` so a signature valid for org A can never resolve a stack belonging to org B.

### Proof of Concept
1. Configure Shipit with two organizations per `docs/setup.md`'s multi-app schema: `OrgA` (secret `SECRET_A`, attacker has legitimate access) and `OrgB` (secret `SECRET_B`, unrelated, hosts stack `OrgB/production-app` on branch `main`).
2. Attacker builds a `push` payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/production-app" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(SECRET_A, raw_body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgA")` and verifies successfully against `SECRET_A`. [1](#0-0) 
5. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, whose `Handler#repository_name` reads `full_name = "OrgB/production-app"`, resolving `OrgB`'s stack and calling `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")`, despite the attacker never being authenticated for or authorized on `OrgB`. [5](#0-4) [6](#0-5)
