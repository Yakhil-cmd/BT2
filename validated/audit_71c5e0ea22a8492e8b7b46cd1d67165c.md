Confirmed: `User#authorized?` grants access if the user belongs to any team in `Shipit.github_teams`, which is populated from `Team` records via `Shipit.github_teams`. Since `find_or_create_team!` in `MembershipHandler` looks up teams solely by `github_id` with no scoping to the organization that produced a valid signature, this is exploitable.### Title
Membership webhook team lookup is unscoped to the signing organization, allowing cross-tenant `Shipit.github_teams` escalation - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`WebhooksController#verify_signature` only proves that a request body was signed with the `webhook_secret` of `repository_owner` (an organization the attacker can legitimately administer as its own Shipit-configured GitHub org). It does not, and cannot, prove that the `team`/`organization` fields inside that self-crafted JSON body are truthful. `MembershipHandler#find_or_create_team!` then looks up (or creates) a `Team` solely by `params.team.id` (`github_id`), with no check that `params.organization.login` (or `repository_owner`) matches the `organization` already stored on that `Team` row.

### Finding Description
The broken binding, stated as an equality that should hold but does not:

`signing_organization (repository_owner, whose webhook_secret validated request.raw_post) == team.organization (the org that actually owns the Team row mutated by the handler)`

Trace:
- `WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-49) computes `repository_owner` from `params.dig('repository','owner','login')` and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(signature, raw_post)`. This only validates HMAC integrity of the body against `attacker-org`'s own secret — it says nothing about whether the `team`/`organization` fields embedded in that body describe reality.
- `MembershipHandler#process` (app/models/shipit/webhooks/handlers/membership_handler.rb:22-34) calls `find_or_create_team!`, then `User.find_or_create_by_login!(params.member.login)`, then `team.add_member(member)`.
- `find_or_create_team!` (membership_handler.rb:38-43):
```ruby
Team.find_or_create_by!(github_id: params.team.id) do |team|
  team.github_team = params.team
  team.organization = params.organization.login
end
```
This looks up by `github_id` alone — a value fully attacker-controlled inside the signed body, not verified against GitHub. If a `Team` row already exists with that `github_id` (belonging to some legitimate org present in `Shipit.github_teams`), `find_or_create_by!` returns that existing record without running the block, so `team.organization` is left untouched — but crucially, the code never validates that `params.organization.login` / `repository_owner` equals that pre-existing `team.organization` before proceeding to mutate membership.
- `Team#add_member` (app/models/shipit/team.rb:41-43) then appends the attacker-controlled `member` (created via `User.find_or_create_by_login!`) into `team.memberships`.
- `User#authorized?` (app/models/shipit/user.rb:80-82) grants access whenever `teams.where(id: Shipit.github_teams.map(&:id)).exists?` — i.e., membership in any team returned by `Shipit.github_teams` is sufficient for global authorization across stacks/tasks/deploys.

Existing guards do not stop this: `verify_signature` only authenticates *which secret signed the bytes*, not the semantic content of `team`/`organization` fields; `ExplicitParameters` schema on `MembershipHandler` (membership_handler.rb:7-21) only enforces types/presence, not cross-field consistency with `repository_owner`; there is no `require_permission!`/ownership check tying the `Team.github_id` lookup to the authenticating organization.

Exploit: Attacker administers `attacker-org`, adds it as a `Shipit::GithubHook::Organization` (a legitimate, low-privilege onboarding action), then sends `POST /webhooks` with `X-Github-Event: membership`, body `{action:'added', team:{id:<github_id of an existing privileged Team>, name:'x', slug:'x', url:'x'}, organization:{login:'attacker-org'}, member:{login:'attacker'}, repository:{owner:{login:'attacker-org'}}}`, signed with `attacker-org`'s real secret. `repository_owner` resolves to `attacker-org`, the signature verifies, and `find_or_create_team!` returns the pre-existing privileged `Team`, into which `attacker` is added as a member.

### Impact Explanation
The attacker gains membership in an arbitrary pre-existing `Team` (by guessing/observing its `github_id`, which is not a secret — team IDs are visible via GitHub's API/UI to team members and often deducible), causing `User#authorized?` to return `true` for the attacker across every stack/task/deploy gated by `Shipit.github_teams`, matching the defined **High** severity category ("escalation into `Shipit.github_teams` authorization"). This is repeatable against any `Team` whose `github_id` the attacker can determine, and is fully cross-tenant: an org with no relationship to the target team can inject a membership record into it purely because the lookup key (`github_id`) is not scoped to the authenticating organization.

### Likelihood Explanation
Preconditions: `Shipit.github_teams` non-empty (a very common production configuration, since it's the primary access-control mechanism); attacker must control/administer at least one org that is configured in Shipit as a `Shipit::GithubHook::Organization` with its own `webhook_secret` (per the problem statement, this is given/assumed feasible and is a low-privilege, self-service action in typical Shipit deployments where any org whose repos are onboarded gets hook credentials); attacker must know/guess the `github_id` of a target team. Attacker cost is a single crafted HTTP POST with a correctly computed HMAC using a secret they legitimately possess for their own org — no GitHub or Shipit operator secrets required. This is feasible and repeatable.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup/creation to the authenticated organization, e.g. `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`, and additionally validate that `params.organization.login` equals `repository_owner`/the organization used to verify the webhook signature before performing any lookup or mutation. Reject (422) membership events where the embedded `organization.login` does not match the signature-verified organization.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (minitest, no live GitHub)
test ":membership from a foreign org can inject membership into another org's team" do
  target_team = shipit_teams(:shopify_developers) # belongs to org "shopify"
  attacker_login = 'attacker'

  GithubHook.any_instance.stubs(:verify_signature).returns(true)
  Shipit.stubs(:github).returns(stub(api: stub(user: stub(id: 999, login: attacker_login))))

  @request.headers['X-Github-Event'] = 'membership'
  body = {
    action: 'added',
    team: { id: target_team.github_id, name: 'x', slug: 'x', url: 'x' },
    organization: { login: 'attacker-org' },
    member: { login: attacker_login },
    repository: { owner: { login: 'attacker-org' } }
  }.to_json

  assert_difference('Membership.count', 1) do
    post :create, body: body, as: :json
    assert_response :ok
  end

  attacker_user = User.find_by(login: attacker_login)
  assert target_team.reload.members.include?(attacker_user)

  Shipit.github_teams.stubs(:map).returns([target_team.id])
  assert attacker_user.authorized?, "attacker gained authorized? via foreign org's forged membership webhook"
end
```
Assertions on both sides of the equality: before the request, `attacker_user` is not a member of `target_team` and `target_team.organization != 'attacker-org'`; after the request, `Membership.count` increases and `target_team.members.include?(attacker_user)` is true, and `attacker_user.authorized?` becomes true — despite `repository_owner`/signing organization (`attacker-org`) never equaling `target_team.organization` (`shopify`).
