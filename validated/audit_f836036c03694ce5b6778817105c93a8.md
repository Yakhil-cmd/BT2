### Title
`clean_gone.md` performs destructive git operations (`branch -D`, `worktree remove --force`) without an `allowed-tools` restriction, unlike sibling commands - ([File: plugins/commit-commands/commands/clean_gone.md])

### Summary
`commit.md` and `commit-push-pr.md` both declare an `allowed-tools: Bash(git ...):*` frontmatter key that scopes the command to specific, benign git subcommands (`add`, `status`, `commit`, `push`, `checkout --branch`, `gh pr create`). `clean_gone.md`, the only command in the plugin that performs irreversible/destructive operations (force-removing worktrees and force-deleting branches), has no `allowed-tools` key at all, meaning its execution is not scoped to the specific git subcommands its body uses.

### Finding Description
`plugins/commit-commands/commands/commit.md` and `commit-push-pr.md` both open with a frontmatter block containing `allowed-tools: Bash(git <subcommand>:*), ...`, explicitly enumerating the exact git subcommands the command is permitted to invoke [1](#0-0) [2](#0-1) .

`clean_gone.md`'s frontmatter only contains a `description` field — no `allowed-tools` key is present [3](#0-2) . Yet its body instructs execution of `git branch -v`, `git worktree list`, and a loop that runs `git worktree remove --force "$worktree"` and `git branch -D "$branch"` for every branch matching `[gone]` [4](#0-3) . These are the most destructive git operations among all three commands in the plugin: `-D` force-deletes a branch even if unmerged, and `worktree remove --force` discards a worktree even with uncommitted/dirty state.

The comparison across all three `*.md` files in `plugins/commit-commands/commands/` shows an inconsistent authorization model: the two commands with the narrowest, most reversible operations (`add`, `status`, `commit`, `push`, PR creation) explicitly declare a restrictive `allowed-tools` allowlist, while the one command with irreversible, forced destructive git operations declares none.

### Impact Explanation
Without a scoped `allowed-tools` restriction, `clean_gone.md`'s execution is not bound to only the git subcommands shown in its body — the frontmatter-declared allowlist is the mechanism other commands in this same plugin use to constrain what Bash invocations are permitted during a slash-command run. Because `clean_gone.md` lacks that constraint, the effective governance of what it can execute is weaker precisely for the command most capable of causing irreversible data loss (unmerged branches deleted, worktrees force-removed regardless of dirty state). This is a proportionality/authorization-model inconsistency rather than a remote-exploit vector: the risk is scoped to local repository state loss if the command's shell logic is manipulated or misfires, not to a broader Claude Code trust-boundary bypass.

### Likelihood Explanation
This is a static, always-present property of the shipped file — no special preconditions beyond a user invoking `/clean_gone` are needed to observe the missing restriction, and it is deterministically reproducible via static frontmatter inspection.

### Recommendation
Add an `allowed-tools` key to `clean_gone.md` mirroring the pattern in `commit.md`/`commit-push-pr.md`, e.g. restricting to the exact subcommands used: `Bash(git branch:*), Bash(git worktree:*)` (or more narrowly, only `git branch -v`, `git worktree list`, `git worktree remove`, `git branch -D` if the frontmatter syntax supports subcommand-level granularity), so authorization scope is proportional to the command's destructive capability, consistent with the other two commands in the same plugin.

### Proof of Concept
Static invariant test over `plugins/commit-commands/commands/*.md`:
1. Parse YAML frontmatter of each `.md` file.
2. Extract the command body and search for destructive git patterns: `git branch -D`, `--force`.
3. Assert: for every file where such a pattern is found, the frontmatter must contain a non-empty, non-wildcard `allowed-tools` key whose value's `Bash(...)` entries correspond to the specific git subcommands used in the body.
4. Running this test against the current three files: `commit.md` and `commit-push-pr.md` pass (no destructive patterns, and/or restrictive `allowed-tools` present); `clean_gone.md` fails the assertion because it contains both `git branch -D` and `--force` yet has no `allowed-tools` key — confirming the inconsistency.
