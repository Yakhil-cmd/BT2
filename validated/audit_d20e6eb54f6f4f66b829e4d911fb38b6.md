### Title
`ERC20Transactor` credits/debits the nominal requested amount instead of the amount actually moved by `IERC20::transfer`, breaking custodial accounting for non-standard (fee-on-transfer/deflationary) ERC20 tokens - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

### Summary
`ERC20Transactor`, wired into Asset Hub Westend's `AssetTransactors` and reachable through the permissionless `pallet_xcm::execute` extrinsic, uses a shared custodial `ERC20TransfersCheckingAccount` to back XCM `WithdrawAsset`/`DepositAsset` operations for any ERC20 contract matched by `ERC20Matcher`. On a successful `transfer()` call it unconditionally credits/debits the exact `amount` that was *requested*, never checking the actual balance change of the checking account or beneficiary. Standard ERC-20 semantics do not guarantee `balanceOf` moves by exactly `value` — deflationary/fee-on-transfer tokens are a well-known, common non-adversarial token class that returns `true` while transferring less. This is the same violated invariant as the referenced Sherlock report (assumed transferred amount == requested amount, no before/after balance check).

### Finding Description
`ERC20Matcher` matches any local `(0, [AccountKey20{..}])` location with no allow-list, so any contract deployed via the permissionless `pallet_revive` instantiate flow can be used as an XCM asset id: [3](#0-2) 

The transactor is wired into the production Asset Hub Westend XCM config: [4](#0-3) 

In `withdraw_asset_with_surplus`, the code calls `IERC20::transferCall` moving `amount` from the user to the checking account, and on `Ok(true)` immediately constructs `AssetsInHolding::new_from_fungible_credit(what.id.clone(), Box::new(Erc20Credit(amount)))` using the *requested* `amount`, not the actual balance delta of the checking account (lines 168-203). Symmetrically, `deposit_asset_with_surplus` calls `transferCall` from the checking account to the beneficiary for the full nominal `amount` held in the register (lines 253-279), again with no verification that the beneficiary actually received `amount`.

This is exactly the missing check identified in the report: "getting the received amount by calculating the difference of token balance (using `balanceOf`) before and after the transfer" is absent. The codebase elsewhere demonstrates awareness of this exact class of bug — `pallet-asset-conversion-ops` explicitly compares the expected balance against the actual value returned by `T::Assets::transfer` and rejects with `Error::<T>::PartialTransfer` if they differ: [5](#0-4) 

`ERC20Transactor` has no equivalent safeguard, even though it interacts with fully attacker-influenced, arbitrary-bytecode Solidity contracts via `pallet_revive::bare_call`.

### Impact Explanation
The `ERC20TransfersCheckingAccount` is a single shared custodial pool across *all* users and *all* XCM operations for a given ERC20 asset id, over time. Each `WithdrawAsset` of a deflationary/fee-on-transfer token increases the checking account's real on-chain balance by only `amount - fee`, while the XCM holding register (and anything built from it, e.g. subsequent `DepositAsset`/forwarding) is credited with the full nominal `amount`. This breaks the invariant that "sum of nominal balances currently checked out equals the checking account's real balance": 
- Some `DepositAsset` calls for previously-withdrawn (over-credited) amounts will fail when the checking account's real balance is insufficient (`FailedToTransactAsset`/ERC20 revert), analogous to the reported `settleContract`/`reclaimContract`/`withdrawFees` failures.
- More severely, because the checking account is a shared pool, an attacker's over-credited holding can be redeemed against balance that was actually contributed by other, unrelated users of the same asset id, which is a value-extraction/fund-loss vector against those other users, not just a DoS.

### Likelihood Explanation
No privileged role is required. Contract deployment via `pallet_revive` and XCM `execute` are both ordinary, permitted user actions; existing production tests already show a full, unprivileged `bare_instantiate` + `PolkadotXcm::execute` withdraw/deposit round trip for an arbitrary ERC20 contract: [6](#0-5) [7](#0-6) 

Deflationary/fee-on-transfer ERC-20 tokens are a real, non-malicious token class deployed in the wild, so this does not even require a deliberately adversarial contract — any user bridging in or interacting with such a token through this transactor triggers the mismatch.

### Recommendation
In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, read `balanceOf` of the checking account (or beneficiary) before and after the `transferCall`, and use the observed delta — not the requested `amount` — when constructing/consuming `AssetsInHolding` credits, mirroring the `balance1 == T::Assets::transfer(...)` pattern already used in `pallet-asset-conversion-ops`.

### Proof of Concept
No PoC was executed against a live network or test harness; this is a conceptual/static analysis based on reading `erc20_transactor.rs` and the existing integration tests (`withdraw_and_deposit_erc20s`, `smart_contract_not_erc20_will_error`) that prove the end-to-end reachability of `bare_instantiate` (arbitrary contract deploy) → `PolkadotXcm::execute` with `WithdrawAsset`/`DepositAsset` targeting an `AccountKey20` asset id. A concrete reproduction would require substituting the `MyToken` fixture used in `withdraw_and_deposit_erc20s` with a deflationary variant (`transfer` returns `true` but only credits `value - fee` to `to`), then asserting: (1) `AssetsInHolding` is credited with the full nominal `amount` while `balanceOf(checking_account)` only increased by `amount - fee`; (2) a subsequent `DepositAsset` for the full nominal amount either reverts due to insufficient real balance or succeeds by drawing down balance contributed by other users' prior deposits of the same token — this compilation/run was not performed here.

	fn withdraw_asset_with_surplus(
		what: &Asset,
		who: &Location,
		_context: Option<&XcmContext>,
	) -> Result<(AssetsInHolding, Weight), XcmError> {
		tracing::trace!(
			target: "xcm::transactor::erc20::withdraw",
			?what, ?who,
		);
		let (asset_id, amount) = Matcher::matches_fungibles(what)?;
		let who = AccountIdConverter::convert_location(who)
			.ok_or(MatchError::AccountIdConversionFailed)?;
		// We need to map the 32 byte checking account to a 20 byte account.
		let checking_account_eth = T::AddressMapper::to_address(&TransfersCheckingAccount::get());
		let checking_address = Address::from(Into::<[u8; 20]>::into(checking_account_eth));
		let weight_limit = WeightLimit::get();
		// To withdraw, we actually transfer to the checking account.
		// We do this using the solidity ERC20 interface.
		let data =
			IERC20::transferCall { to: checking_address, value: EU256::from(amount) }.abi_encode();
		let ContractResult { result, weight_consumed, storage_deposit, .. } =
			pallet_revive::Pallet::<T>::bare_call(
				OriginFor::<T>::signed(who.clone()),
				asset_id,
				U256::zero(),
				TransactionLimits::WeightAndDeposit {
					weight_limit,
					deposit_limit: StorageDepositLimit::get(),
				},
				data,
				&ExecConfig::new_substrate_tx(),
			);
		// We need to return this surplus for the executor to allow refunding it.
		let surplus = weight_limit.saturating_sub(weight_consumed);
		tracing::trace!(target: "xcm::transactor::erc20::withdraw", ?weight_consumed, ?surplus, ?storage_deposit);
		if let Ok(return_value) = result {
			tracing::trace!(target: "xcm::transactor::erc20::withdraw", ?return_value, "Return value by withdraw_asset");
			if return_value.did_revert() {
				tracing::debug!(target: "xcm::transactor::erc20::withdraw", "ERC20 contract reverted");
				Err(XcmError::FailedToTransactAsset("ERC20 contract reverted"))
			} else {
				let is_success = IERC20::transferCall::abi_decode_returns_validate(&return_value.data).map_err(|error| {
					tracing::debug!(target: "xcm::transactor::erc20::withdraw", ?error, "ERC20 contract result couldn't decode");
					XcmError::FailedToTransactAsset("ERC20 contract result couldn't decode")
				})?;
				if is_success {
					tracing::trace!(target: "xcm::transactor::erc20::withdraw", "ERC20 contract was successful");
					Ok((
						AssetsInHolding::new_from_fungible_credit(
							what.id.clone(),
							Box::new(Erc20Credit(amount)),
						),
						surplus,
					))
				} else {
					tracing::debug!(target: "xcm::transactor::erc20::withdraw", "contract transfer failed");
					Err(XcmError::FailedToTransactAsset("ERC20 contract transfer failed"))
				}
			}
		} else {
			tracing::debug!(target: "xcm::transactor::erc20::withdraw", ?result, "Error");
			// This error could've been duplicate smart contract, out of gas, etc.
			// If the issue is gas, there's nothing the user can change in the XCM
			// that will make this work since there's a hardcoded gas limit.
			Err(XcmError::FailedToTransactAsset("ERC20 contract execution errored"))
		}
	}

/// `Contains<Location>` implementation that matches locations with no parents,
/// a `PalletInstance` and an `AccountKey20` junction.
pub struct IsLocalAccountKey20;
impl Contains<Location> for IsLocalAccountKey20 {
	fn contains(location: &Location) -> bool {
		matches!(location.unpack(), (0, [AccountKey20 { .. }]))
	}
}

/// Fallible converter from a location to a `H160` that matches any location ending with
/// an `AccountKey20` junction.
pub struct AccountKey20ToH160;
impl MaybeEquivalence<Location, H160> for AccountKey20ToH160 {
	fn convert(location: &Location) -> Option<H160> {
		match location.unpack() {
			(0, [AccountKey20 { key, .. }]) => Some((*key).into()),
			_ => None,
		}
	}

	fn convert_back(key: &H160) -> Option<Location> {
		Some(Location::new(0, [AccountKey20 { key: (*key).into(), network: None }]))
	}
}

/// [`xcm_executor::traits::MatchesFungibles`] implementation that matches
/// ERC20 tokens.
pub type ERC20Matcher =
	MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>;

#[test]
fn withdraw_and_deposit_erc20s() {
	let sender: AccountId = ALICE.into();
	let beneficiary: AccountId = BOB.into();
	let revive_account = pallet_revive::Pallet::<Runtime>::account_id();
	let checking_account =
		asset_hub_westend_runtime::xcm_config::ERC20TransfersCheckingAccount::get();
	let initial_wnd_amount = 100_000_000_000_000_000u128;
	sp_tracing::init_for_tests();

	ExtBuilder::<Runtime>::default().build().execute_with(|| {
		// Bring the revive account to life.
		assert_ok!(Balances::mint_into(&revive_account, initial_wnd_amount));
		// Fund all accounts involved.
		assert_ok!(Balances::mint_into(&sender, initial_wnd_amount));
		assert_ok!(Balances::mint_into(&beneficiary, initial_wnd_amount));
		assert_ok!(Balances::mint_into(&checking_account, initial_wnd_amount));

		let code = compile_module_with_type("MyToken", FixtureType::Resolc)
			.expect("compile ERC20")
			.0;

		let initial_amount_u256 = U256::from(1_000_000_000_000u128);
		let constructor_data = sol_data::Uint::<256>::abi_encode(&initial_amount_u256);
		let Contract { addr: erc20_address, .. } = bare_instantiate(&sender, code)
			.transaction_limits(TransactionLimits::WeightAndDeposit {
				weight_limit: Weight::from_parts(500_000_000_000, 10 * 1024 * 1024),
				deposit_limit: Balance::MAX,
			})
			.data(constructor_data)
			.build_and_unwrap_contract();

		let sender_balance_before = <Balances as fungible::Inspect<_>>::balance(&sender);

		let erc20_transfer_amount = 100u128;
		let wnd_amount_for_fees = 10_000_000_000_000u128;
		// Actual XCM to execute locally.
		let message = Xcm::<RuntimeCall>::builder()
			.withdraw_asset((Parent, wnd_amount_for_fees))
			.pay_fees((Parent, wnd_amount_for_fees))
			.withdraw_asset((
				AccountKey20 { key: erc20_address.into(), network: None },
				erc20_transfer_amount,
			))
			.deposit_asset(AllCounted(1), beneficiary.clone())
			.refund_surplus()
			.deposit_asset(AllCounted(1), sender.clone())
			.build();
		assert_ok!(PolkadotXcm::execute(
			RuntimeOrigin::signed(sender.clone()),
			Box::new(VersionedXcm::V5(message)),
			Weight::from_parts(600_000_000_000, 15 * 1024 * 1024),
		));

		// Revive is not taking any fees.
		let sender_balance_after = <Balances as fungible::Inspect<_>>::balance(&sender);
		// Balance after is larger than the difference between balance before and transferred
		// amount because of the refund.
		assert!(sender_balance_after > sender_balance_before - wnd_amount_for_fees);

		// Beneficiary receives the ERC20.
		let beneficiary_amount =
			<Revive as fungibles::Inspect<_>>::balance(erc20_address, &beneficiary);
		assert_eq!(beneficiary_amount, erc20_transfer_amount);
	});

fn smart_contract_not_erc20_will_error() {
	let sender: AccountId = ALICE.into();
	let beneficiary: AccountId = BOB.into();
	let revive_account = pallet_revive::Pallet::<Runtime>::account_id();
