### Title
`InitializeBuffer` instruction of the upgradeable BPF loader has no authority/signer verification, allowing front-running takeover of an uninitialized buffer account - (File: `programs/bpf_loader/src/lib.rs`)

### Summary
The `UpgradeableLoaderInstruction::InitializeBuffer` handler in `process_loader_upgradeable_instruction` only checks that the target account's state is `UpgradeableLoaderState::Uninitialized`, then unconditionally sets the account's `authority_address` to whatever pubkey is passed as account index 1 — with **no signature requirement on that authority account, and no signature requirement tying the call to the account's creator**. [1](#0-0) 

### Finding Description
When a user deploys an upgradeable BPF program, the typical (and often necessary, given transaction size limits) workflow is:
1. Send a `system_instruction::create_account` transaction to allocate/fund a new account owned by `bpf_loader_upgradeable`, sized for the buffer.
2. Send a separate `UpgradeableLoaderInstruction::InitializeBuffer` transaction against that same account to set its `authority_address` and transition it from `Uninitialized` to `Buffer { authority_address }`.
3. Send subsequent `Write` transactions (which do require the authority to sign, per lines 173-201) to fill in program bytes.
4. Finally send `DeployWithMaxDataLen` to create the executable program.

Between steps 1 and 2, the buffer account exists on-chain in state `Uninitialized`, owned by the loader, with a known public address (visible in any pending/confirmed transaction). The `InitializeBuffer` instruction itself requires only 2 accounts and does **not** require:
- The buffer account to be a signer,
- The "authority" account (account index 1) to be a signer,
- Any relationship between the caller and the account's original creator.

```rust
UpgradeableLoaderInstruction::InitializeBuffer => {
    instruction_context.check_number_of_instruction_accounts(2)?;
    let mut buffer = instruction_context.try_borrow_instruction_account(0)?;

    if UpgradeableLoaderState::Uninitialized != buffer.get_state()? {
        return Err(InstructionError::AccountAlreadyInitialized);
    }

    let authority_key = Some(*instruction_context.get_key_of_instruction_account(1)?);

    buffer.set_state(&UpgradeableLoaderState::Buffer {
        authority_address: authority_key,
    })?;
}
``` [2](#0-1) 

This is the exact bug class described in the external report: an initializer function that is reachable by anyone before the legitimate owner calls it, allowing "taking over" the object being initialized via front-running. Here, any unprivileged transaction sender who observes the pending/known buffer address can submit their own `InitializeBuffer` instruction naming themselves (or an arbitrary key) as `authority_address` before the legitimate deployer's `InitializeBuffer` transaction lands, because the state check (`Uninitialized`) is satisfied and there is no signer gate. Once initialized with an attacker-controlled authority, the account is set (only `SetAuthority`/`Close` by the current authority, or `Write`/`DeployWithMaxDataLen` gated on the current authority signing, can change it further — see lines 549-576 and 242-254). The legitimate deployer's subsequent `Write` or `DeployWithMaxDataLen` calls will fail because the authority they attempt to sign with (`instruction_context.is_instruction_account_signer(1)?` checks against `authority_address`) no longer matches.

### Impact Explanation
The impact is a targeted denial-of-service / hijack against program deployers: the attacker can prevent a specific buffer account from ever being usable by its intended owner, forcing the deployer to abandon the account (losing the rent-exempt lamports funded into it, unless the attacker cooperates to close/reassign it). Because the attacker becomes the sole authority of that Buffer, they could also maliciously overwrite the bytes with their own `Write` calls and drive `DeployWithMaxDataLen` themselves, deploying an attacker-controlled program at the address the victim had allocated/funded (if the corresponding `ProgramData`/`Program` accounts are also under attacker control or a mismatched deploy is attempted). This does not directly cause unsigned fund movement, but it does allow an unprivileged attacker, via a single ordinary transaction, to seize control over an account whose creation transaction they merely observed — matching "CPI privilege escalation"-adjacent account takeover semantics for the loader-managed Buffer object.

### Likelihood Explanation
Likelihood is limited by two factors that reduce but do not eliminate exploitability:
- Most CLI/SDK deploy tooling atomically combines `create_account` + `InitializeBuffer` in the same transaction when the buffer is small enough to fit, which would make front-running impossible (atomicity protects same-transaction instructions). However for larger programs requiring the buffer to be created first and filled via many subsequent `Write` calls, tooling MAY split `create_account` and `InitializeBuffer` into separate transactions, or a user could manually construct the two steps separately, exposing a race window.
- The buffer account's address is typically an ephemeral, freshly generated keypair not known to any observer until the `create_account` transaction is broadcast/confirmed, so exploitation requires an attacker actively watching the mempool/gossip for `create_account` transactions targeting `bpf_loader_upgradeable`-owned accounts and reacting within the block-inclusion window — a realistic front-running scenario for MEV-aware actors on the same or a subsequent slot.

I was unable to fully confirm, within the available tool budget, whether `cli/src/program.rs`'s program-deploy path always combines `create_account` and `InitializeBuffer` atomically in one transaction (which would fully mitigate this for the CLI path) — the file read was cut off before reaching the buffer-creation logic. If it does combine them atomically, the CLI's own deploy flow is safe, but the instruction handler itself remains unprotected for any other caller (SDKs, custom tooling, or manual instruction construction) that does not enforce this invariant.

### Recommendation
Add a signer requirement to `InitializeBuffer` — e.g., require the buffer account itself (or a designated creator/authority passed at `create_account` time) to sign the `InitializeBuffer` instruction, mirroring the signer check already present in `Write` (lines 187-190) and `SetAuthority` (lines 569-572). At minimum, document and enforce that `create_account` and `InitializeBuffer` must always be submitted as a single atomic transaction by all tooling, and consider having `system_instruction::create_account`-created loader-owned accounts require the same key to also sign `InitializeBuffer`.

### Proof of Concept
1. Victim submits `system_instruction::create_account(payer, buffer_pubkey, lamports, size, bpf_loader_upgradeable::id())` in transaction T1, creating `buffer_pubkey` in `UpgradeableLoaderState::Uninitialized` state.
2. Attacker observes T1 (pending or just-confirmed) and immediately submits `UpgradeableLoaderInstruction::InitializeBuffer` for `buffer_pubkey` with instruction account 1 = `attacker_pubkey`, before the victim's own `InitializeBuffer` transaction lands.
3. `process_loader_upgradeable_instruction` (programs/bpf_loader/src/lib.rs:158-172) allows this because the only check is `UpgradeableLoaderState::Uninitialized != buffer.get_state()?`; no signature from `attacker_pubkey` or from `buffer_pubkey` is required.
4. `buffer_pubkey`'s state becomes `Buffer { authority_address: Some(attacker_pubkey) }`.
5. Victim's later `InitializeBuffer` transaction now fails with `InstructionError::AccountAlreadyInitialized` (line 164), and victim's `Write`/`DeployWithMaxDataLen` transactions using their own key as authority fail `IncorrectAuthority`/`MissingRequiredSignature` checks (lines 182-190, 242-250), permanently denying the victim use of the funded account while the attacker now controls it.
