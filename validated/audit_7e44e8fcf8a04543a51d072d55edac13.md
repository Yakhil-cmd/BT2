### Title
Cross-repository status forgery via global `Commit.where(sha:)` lookup — ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler` validates only the shape of `sha`, `state`, and `context` via `ExplicitParameters::Parameters`, then resolves commits with `Commit.where(sha: params.sha)` — a query with no repository/stack filter at all. The `repository` block in the webhook payload is used exclusively by `Handler#repository_name`/`#stacks` for other handlers and by the controller's signature-verification lookup, but `StatusHandler#process` never calls `stacks` or cross-checks `commit.stack.repository` against the payload's `repository`, so any commit row sharing that `sha` — including one belonging to a completely different repository/stack — gets a forged status written to it.

### Finding Description
Broken binding, stated explicitly: the set of fields validated by `StatusHandler.params` — `{sha, state, description, target_url, context, created_at, branches}` — is claimed to equal the set of fields used to scope the mutation in `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [1](#0-0) . In reality the mutation-scoping set is exactly `{sha}` — `repository` is absent from both the validated params and the write-scoping query.

Trace:
- `WebhooksController#create` parses the raw JSON body and dispatches it to every handler for the event, with no per-repository/stack scoping at the controller level [2](#0-1) .
- `verify_signature` only determines *which* app/org secret to use for HMAC verification via `repository_owner` (`params.dig('repository', 'owner', 'login')`); a successful verification proves the request was signed for *some* org's webhook secret, not that the enclosed `sha` belongs to that org's repository [3](#0-2) [4](#0-3) .
- `Handler#repository_name`/`#stacks` exist to resolve `Repository.from_github_repo_name(repository_name)&.stacks`, but `StatusHandler` never invokes them [5](#0-4) .
- `Commit#create_status_from_github!` unconditionally writes a new `Status` on whatever `Commit` row was matched, regardless of that commit's `stack`/repository [6](#0-5) .

Exploitable path (fork-based SHA collision, no secret theft required): GitHub SHA1s are computed from tree+parent+metadata, so an unmodified commit shared between a fork and its upstream has an *identical* `sha` in both repositories' git history. An attacker:
1. Forks the victim's repository (`repository B`) into their own repository (`repository A`) they fully own/control.
2. Because Shipit is multi-tenant, if the attacker's own org/repo `A` is (or becomes) a legitimate Shipit-connected repository, GitHub will sign real `status` webhooks for `A` using the correctly configured webhook secret for that org — satisfying `verify_signature` legitimately, with no secret exfiltration needed.
3. The attacker triggers (or crafts, via any mechanism that causes GitHub to emit a `status` event for repo `A`) a `status` webhook whose `sha` is one of the commits shared with upstream `B`, and sets `state: "success"` on a context the victim stack treats as blocking/required.
4. `Commit.where(sha: params.sha)` matches the row in `B`'s stack (because the sha is identical), and `create_status_from_github!` writes a forged success status onto the victim's commit, satisfying `blocked?`/`deployable?` checks that gate continuous delivery [7](#0-6) .

No existing guard closes this gap: `verify_signature` authenticates the org that signed the request, not the repository named inside the payload against the row being mutated; `drop_unhandled_event` only filters by event type; the `ExplicitParameters` schema never declares or checks `repository`; there is no `Repository`/`Stack` scoping applied before the `Commit.where` call.

### Impact Explanation
A payload legitimately signed for attacker-owned repository `A` mutates a `Commit`/`Status` row belonging to an unrelated stack/repository `B`, which matches the rule's Critical category ("a payload for one repository mutating another's stack, commit... or an unauthorized deploy"). Forged success statuses on required/blocking contexts can unblock `deployable?`/`blocked?` gating and trigger `schedule_continuous_delivery`, leading to an unauthorized deploy of a commit that never actually passed CI. This is repeatable against any target repository the attacker can fork (public repos, or private repos the attacker has read access to fork), and scales across every stack sharing that commit's `sha` in the Shipit database.

### Likelihood Explanation
Preconditions: the attacker's own org/repo must be a Shipit-connected tenant (so a genuine webhook signature is obtainable) — plausible in any self-serve multi-tenant Shipit deployment where teams add their own repos as stacks. The attacker needs a target repository that is public/forkable and has at least one commit whose status the victim stack treats as gating. Cost is low (fork + normal GitHub webhook delivery, or a direct POST with a validly signed body for their own tenant); no privileged Shipit role, session, or secret is required. This is fully repeatable per target commit/stack.

### Recommendation
Scope the write in `StatusHandler#process` (and any other SHA-keyed handler) to commits belonging to the repository named in the payload, e.g. filter `Commit.where(sha: params.sha)` through `stacks` (`Repository.from_github_repo_name(repository_name)&.stacks`) before iterating, and add `repository.full_name` to the validated `params` schema so the binding between validated fields and mutation scope actually holds.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb (conceptual, no live GitHub)
test "status webhook scoped to repo A mutates a commit belonging to repo B" do
  repo_b = shipit_repositories(:shipit)
  stack_b = shipit_stacks(:shipit)
  commit_b = stack_b.commits.create!(sha: "a" * 40, message: "shared commit")

  payload = {
    "sha" => commit_b.sha,
    "state" => "success",
    "context" => "ci/fake",
    "repository" => { "full_name" => "attacker/repo-a" } # unrelated repo
  }

  # Binding under test: validated fields == write-scoping fields
  params = Shipit::Webhooks::Handlers::StatusHandler.new(payload).params
  refute_respond_to params, :repository # repository never validated/exposed

  assert_difference -> { commit_b.statuses.count }, 1 do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end

  commit_b.reload
  assert_equal "success", commit_b.status.state
  # commit_b belongs to stack_b/repo_b, yet payload only named "attacker/repo-a" —
  # proving repository scope was never enforced during the mutation.
end
```

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
