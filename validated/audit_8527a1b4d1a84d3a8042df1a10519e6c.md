## Title
`MembershipHandler#process` binds a `Team` by `github_id` alone, letting a webhook validly signed by any registered organization grant membership in a Team belonging to a *different* organization - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

## Summary
`WebhooksController#verify_signature` only proves that the request was signed with the `webhook_secret` of *some* organization known to Shipit (`repository_owner`, taken from `params['organization']['login']`) [1](#0-0) [2](#0-1) . `MembershipHandler#find_or_create_team!` then looks up (or creates) a `Team` solely by `params.team.id`, without ever checking that `params.organization.login` matches the `organization` of the resolved `Team` [3](#0-2) . Because `find_or_create_by!` only assigns attributes from the block when *creating* a new record, an already-existing `Team` for organization B is returned unmodified when org A supplies its `github_id`, and `team.add_member(member)` / `team.members.delete(member)` executes against that org-B team using only org-A's signature [4](#0-3) .

## Finding Description
The intended binding is: *a `Membership` row for team T is created/removed only in response to a membership event that GitHub actually generated for T's own organization*, i.e. `Membership.team.organization == params.organization.login` used for signature verification. This binding is never enforced.

Path:
1. `WebhooksController#create` parses the JSON body and dispatches to `Shipit::Webhooks.for_event(event)` handlers, calling `MembershipHandler.call(params)` for `X-Github-Event: membership` [5](#0-4) .
2. `verify_signature` computes `repository_owner` from `params.dig('organization','login')` (membership payloads have no `repository` key) and validates the signature against `Shipit.github(organization: repository_owner)`'s `webhook_secret` [1](#0-0) . This only proves the sender knows org A's secret - a secret that org A's own legitimate GitHub webhook configuration would supply, and which Shipit's multi-org support (`Shipit.github(organization:)`) implies can differ per registered organization.
3. `MembershipHandler#process` calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id) { |team| team.organization = params.organization.login }` [3](#0-2) . If a `Team` row with that `github_id` already exists (created earlier by org B's legitimate webhook, `github_id` being GitHub's team ID, not scoped per-organization by this lookup), the block is skipped entirely and the pre-existing org-B `Team` object is returned as-is.
4. `process` then executes `team.add_member(member)` (for `action == 'added'`) using `member = User.find_or_create_by_login!(params.member.login)` - a GitHub login fully controlled by the attacker [6](#0-5) . This writes a `Membership` row linking an attacker-chosen user to org B's `Team`, even though the request was authenticated only against org A's secret.

None of the existing guards close this gap: `verify_signature` authenticates *an* organization, not *the* organization owning the named team; `drop_unhandled_event` only filters by event type; the `ExplicitParameters` schema in `MembershipHandler` validates payload shape (`team.id`, `organization.login`, `member.login`) but never cross-checks them against each other; and `Team#github_hooks` (scoped by `Team::REQUIRED_HOOKS`) is not consulted at all inside `process`, so it provides no runtime protection.

## Impact Explanation
If the referenced `Team` is one of `Shipit.github_teams` used by `User#authorized?` (`Shipit.github_teams.empty? || teams.where(id: Shipit.github_teams.map(&:id)).exists?`) [7](#0-6) , an attacker controlling any organization registered in Shipit (and thus possessing that organization's own valid `webhook_secret` for their own legitimate integration) can forge a `membership` "added" event naming a `team.id` that belongs to a *different, authorization-relevant* organization/team, and an arbitrary GitHub login of their choosing. This creates a `Membership` row for that login in the privileged team, which - the next time that user logs in or is looked up - grants `authorized?` privileges in Shipit (deploy/rollback/merge access) without GitHub itself ever reporting that membership for the real team's organization. This is a cross-tenant authorization corruption, matching the "escalation into `Shipit.github_teams` authorization" High-severity category. It is repeatable for any `github_id` the attacker can guess or discover (team IDs are often enumerable/observable via GitHub's public API) and for any GitHub login.

## Likelihood Explanation
Exploitation requires: (a) Shipit configured with multiple organizations (`Shipit.github(organization:)` multi-org support), (b) the attacker legitimately controlling or having compromised one org's own webhook secret (their own org's webhook, which they can view since they configured it - not a "secret" from Shipit's perspective, just their own credential), and (c) knowledge of the target team's `github_id` in another org. Given (a)-(c), the attack is a single crafted HTTP POST to `/webhooks` with a correct `X-Hub-Signature` for org A and forged `team`/`member` fields - trivial and fully repeatable, no rate limiting or additional secrets needed.

## Recommendation
In `MembershipHandler#find_or_create_team!` (and `#process`), verify that `params.organization.login` matches the `organization` of the resolved (or newly created) `Team` before mutating memberships; reject/raise if they differ. Additionally, scope the `Team.find_or_create_by!` lookup by `github_id` *and* `organization` together rather than `github_id` alone, so a `github_id` collision or cross-org replay cannot resolve to another organization's team record.

## Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/membership_handler_test.rb` style, or extending `test/controllers/webhooks_controller_test.rb`):
```ruby
test "membership webhook signed by org A cannot mutate a team belonging to org B" do
  # Setup: two orgs configured, each with its own webhook_secret
  # (mirrors test/dummy/config/secrets_double_github_app.yml multi-org setup)
  team_b = shipit_teams(:my_team) # organization: "org_b", github_id: 4242

  payload = {
    'action' => 'added',
    'team' => { 'id' => team_b.github_id, 'name' => team_b.name, 'slug' => team_b.slug, 'url' => team_b.api_url },
    'organization' => { 'login' => 'org_a' }, # attacker's own org, valid secret
    'member' => { 'login' => 'attacker_login' },
  }

  # sign with org_a's real webhook_secret
  signature = compute_hmac_signature(Shipit.github(organization: 'org_a').webhook_secret, payload.to_json)

  post shipit.webhooks_path, params: payload.to_json,
       headers: { 'X-Github-Event' => 'membership', 'X-Hub-Signature' => signature,
                  'CONTENT_TYPE' => 'application/json' }

  assert_response :ok

  # Binding check: membership for team_b (org_b) must NOT be created from an org_a-signed request
  refute team_b.members.exists?(login: 'attacker_login'),
    "Expected no Membership row for org_b's team created via org_a's webhook signature"
end
```
Before the fix, this test fails (the attacker-controlled login is added as a member of `team_b`); after enforcing `params.organization.login == team.organization`, the request is rejected/ignored and the assertion passes.
