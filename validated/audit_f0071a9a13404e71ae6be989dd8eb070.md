I have sufficient evidence to confirm the finding. `StatusHandler#process` uses a global, unscoped `Commit.where(sha:)` lookup, unlike other handlers that scope through `Handler#stacks` (which filters by `Repository.from_github_repo_name(repository_name)`).### Title
Cross-stack/cross-repository status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target `Commit` records purely by bare `sha`, with no join or filter on the repository/organization that authenticated the webhook. Combined with `Commit#schedule_continuous_delivery`, which fires `ContinuousDeliveryJob` whenever a commit becomes `deployable?` on a `continuous_deployment?` stack, a status event legitimately authenticated for one repository can flip the CI state of a commit belonging to an entirely different stack that happens to share the same SHA, forcing an unwanted deploy or block there.

### Finding Description
The broken binding the code should enforce is: `status.repository == commit.stack.repository` for every `Status` record created from a webhook. In practice the code enforces only `status.sha == commit.sha`.

- `Shipit::WebhooksController#create` dispatches the parsed JSON body to `Shipit::Webhooks.for_event(event)` handlers after `verify_signature`, which only checks the HMAC signature against the `Shipit.github(organization: repository_owner)` webhook secret for the *organization* named in the attacker-controlled JSON (`params.dig('repository','owner','login')`) — it performs no per-repository scoping and is orthogonal to which `Stack`/`Commit` rows get touched. [1](#0-0) 
- `Shipit::Webhooks::Handlers::Handler` provides a `stacks` helper that resolves `Repository.from_github_repo_name(repository_name)&.stacks`, i.e. the correct repo-scoped restriction, and other handlers (e.g. `PushHandler`) use it. [2](#0-1) 
- `StatusHandler#process`, however, ignores `stacks`/`repository_name` entirely and queries `Commit` globally by `sha`: [3](#0-2) 
- `Commit belongs_to :stack`, and `Commit.sha` is not unique per repository/organization in the schema/model — any stack in the entire Shipit instance whose `Commit` row has a matching `sha` (e.g., two stacks tracking the same underlying repository under different environments, forked repositories sharing history, or an attacker replaying identical raw git commit bytes to reproduce an identical SHA1 in a repo they control) gets its status mutated: [4](#0-3) 
- `Commit#create_status_from_github!` → `add_status` records the new `Status`, and on relevant transitions calls `schedule_continuous_delivery`, which enqueues `ContinuousDeliveryJob` whenever `deployable? && stack.continuous_deployment? && stack.deployable?`: [5](#0-4) [6](#0-5) 
- `ContinuousDeliveryJob#perform` then calls `stack.trigger_continuous_delivery` unconditionally once the stack looks deployable and unoccupied: [7](#0-6) 

Exploit flow: an attacker who can trigger a valid, signature-passing `status` event for *any* repository/organization already registered with the Shipit instance (their own repo/fork within that organization/App installation) sends `context: 'release/gate'`, `state: 'success'`, `sha: <sha shared with, or forged to equal, a commit already tracked in a victim stack>`. `StatusHandler` writes this status to every `Commit` row across the whole instance with that `sha`, including the victim's, regardless of which repository actually authenticated the request. If the victim stack has `continuous_deployment` enabled and was only blocked on the `release/gate` status, this write makes the commit `deployable?` and enqueues `ContinuousDeliveryJob`, which ships it.

None of the listed guards prevent this: `verify_signature` authenticates an organization, not a specific repository, and is bypassed entirely by the SHA-based global lookup which never re-checks repository identity; `drop_unhandled_event` and the `ExplicitParameters` schema only validate presence/type of `sha`/`state`/`context`, not ownership; there is no `Repository`/`Stack` scoping check anywhere in `StatusHandler` or `Commit#create_status_from_github!`.

### Impact Explanation
A payload correctly authenticated for one repository mutates the CI state (`Status`) of a commit belonging to a different stack/repository, which is explicitly listed as a Critical-severity impact category ("a payload for one repository mutating another's stack, commit, task or team"). When the victim stack has `continuous_deployment` enabled, this forged status can make an already-tracked commit pass its "deployable" check and trigger an unauthorized deploy via `ContinuousDeliveryJob#perform` → `stack.trigger_continuous_delivery`, i.e., an unauthorized deploy of code the victim never approved through CI. The blast radius spans every stack across the Shipit instance whose `Commit.sha` happens to coincide with an attacker-influenced SHA — most plausibly stacks tracking the same repository under different environments (a common Shipit topology), but also any repository within the same GitHub App/organization installation.

### Likelihood Explanation
Preconditions: (1) the attacker must be able to get one `status` webhook past `verify_signature`, which requires knowing/matching a webhook secret configured for *some* organization already registered with the target Shipit instance — this is realistic if the attacker owns a repository under that same GitHub App installation/organization (e.g., they can push commits and set commit statuses on their own repo in the org); (2) a victim `Stack` must have a `Commit` row with a matching `sha`, which is straightforward when multiple stacks track the same repository (staging/production) or when git history/forks are shared; (3) the victim stack must have `continuous_deployment` enabled and be otherwise deployable. Given standard Shipit deployments — a single GitHub App installed across many repos of an org, and multiple Stacks per repo for different environments — these preconditions are common, making the attack realistically repeatable per targeted SHA/stack.

### Recommendation
Scope `StatusHandler#process` to only update commits belonging to stacks resolved from the authenticated `repository_name` (using the existing `stacks` helper from `Handler`), e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or an explicit join `Commit.joins(:stack).merge(stacks).where(sha: params.sha)`, mirroring how `PushHandler` and other handlers already scope to the webhook's own repository.

```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossStackTest < ActiveSupport::TestCase
        test "a status authenticated for repo A must not flip CI state for a commit in unrelated stack B sharing the same sha" do
          attacker_repo_stack = shipit_stacks(:shipit)          # attacker-controlled / authenticated repo's stack
          victim_stack = shipit_stacks(:cyclimse)                # unrelated victim stack
          victim_stack.update!(continuous_deployment: true)
          # ensure deploy_spec requires 'release/gate' and victim stack is otherwise deployable/unoccupied

          shared_sha = "a" * 40
          attacker_commit = attacker_repo_stack.commits.create!(sha: shared_sha, author: shipit_users(:shipit), authored_at: Time.now, committer: shipit_users(:shipit), committed_at: Time.now)
          victim_commit = victim_stack.commits.create!(sha: shared_sha, author: shipit_users(:shipit), authored_at: Time.now, committer: shipit_users(:shipit), committed_at: Time.now)

          # Binding under test: status.repository == commit.stack.repository
          # LHS (should be enforced): only attacker_repo_stack's commit status should change
          # RHS (actual behavior): victim_commit's status also changes

          params = OpenStruct.new(sha: shared_sha, state: "success", context: "release/gate", description: nil, target_url: nil, created_at: Time.now.to_s)

          assert_no_enqueued_jobs(only: ContinuousDeliveryJob) do
            StatusHandler.new({
              "sha" => shared_sha, "state" => "success", "context" => "release/gate",
              "repository" => { "full_name" => attacker_repo_stack.github_repo_name, "owner" => { "login" => attacker_repo_stack.repository.owner } }
            }).process
          end

          victim_commit.reload
          # FAILS today: victim_commit gains a 'release/gate' success status it never authenticated,
          # even though the webhook only authenticated attacker_repo_stack's repository.
          assert_nil victim_commit.statuses.find_by(context: "release/gate"),
            "victim stack's commit should not receive a status from a webhook authenticated for a different repository"
        end
      end
    end
  end
end
```
Note: exact fixture/stack names (`shipit_stacks(:cyclimse)`) and `deploy_spec` `release/gate` requirement setup would need to be adapted to the repo's actual fixtures; this test demonstrates the required assertions on both sides of the broken binding (`Commit.where(sha:)` global match vs. the intended per-repository scoping).
