### Title
Cross-organization CI status forgery via webhook signature/repository-scope mismatch - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret used to validate `X-Hub-Signature` based on `repository_owner` (`params.dig('repository','owner','login')`), which is per-organization in a multi-org Shipit deployment. Once the signature check passes, `Shipit::Webhooks::Handlers::StatusHandler#process` acts on the payload by looking up commits **globally**, with no re-check that the commit's owning stack/repository matches the organization whose secret was used to authenticate the request: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`. This breaks the binding "organization that authenticated == repository that is written."

### Finding Description
Shipit supports multiple GitHub organizations, each configured with its own `webhook_secret` (`config/secrets.development.shopify.yml`, `lib/shipit/github_app.rb`). The webhook signature is verified using whichever secret corresponds to the `repository.owner.login` field taken from the **unauthenticated, attacker-supplied JSON body**: [1](#0-0) [2](#0-1) 

This means any party who legitimately controls one configured organization (e.g. their own org in a shared Shipit instance, with a webhook they registered themselves and whose secret they therefore know) can produce a validly-signed payload as long as `repository.owner.login` equals that org's name, and the signature is computed with that org's real secret — even though the rest of the payload (in particular, `repository.full_name` or `sha`) can reference an entirely different, unrelated repository/stack that they do not own.

The `status` event handler amplifies this because it does not scope by repository at all — it performs a bare, cross-stack `Commit.where(sha:)` lookup: [3](#0-2) 

Compare this with `PushHandler`/`CheckSuiteHandler`, which at least scope through `stacks` (derived from `repository.full_name`): [4](#0-3) [5](#0-4) 

But even `full_name`-scoped handlers are not protected against the core issue: the field used to select the verifying secret (`repository.owner.login`) and the field used to decide what gets acted upon (`repository.full_name`, or in the `status` handler's case, nothing at all) are independent, attacker-controlled strings inside the same signed body. The signature only proves "some org's secret signed this exact byte stream," not "the repository referenced in this payload belongs to the signing organization." Shipit never cross-checks that `repository.owner.login == repository.full_name.split('/').first`.

Git commit SHAs are 40-character hex identifiers that are frequently public (visible in a public GitHub repo, in Shipit's own UI/API for public stacks, in PR URLs, CI logs, etc.), so an attacker can typically obtain the SHA of a victim commit they want to forge a status for.

### Impact Explanation
Using a webhook signed with the attacker's own (legitimately controlled) organization secret, the attacker can inject an arbitrary commit `Status` (e.g., `state: success`, on any `context`) onto a **victim's** commit in a completely different stack, via `Commit#create_status_from_github!`. Status objects feed directly into:
- `MergeRequest::StatusChecker` / `any_status_checks_failed?` / `any_status_checks_missing?`, which gate the merge queue (`reject_unless_mergeable!`, `merge!`) [6](#0-5) 
- `Commit#deployable?` / `Stack#deployable?`, which gate deploy eligibility [7](#0-6) 

By forging a fabricated "green" CI status on a victim commit, an attacker without any relationship to the victim organization/repository can cause that commit to satisfy required-status checks it never legitimately passed, enabling an **unauthorized merge** through the merge queue and/or an **unauthorized deploy** of code that never passed real CI. This matches the Critical impact bucket ("an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Requires the attacker to control at least one organization/App configured in a shared, multi-tenant Shipit instance (an unprivileged position with respect to the victim org) and to know a target commit SHA (frequently public). No access to the victim's GitHub App, webhook secret, or Shipit session/API token is needed — only the ability to send a raw HTTP POST with a correctly-signed body for their own organization. This is a straightforward confused-deputy exploitation once multi-org support is enabled, which the codebase explicitly supports (`Shipit.github(organization:)`, per-org `webhook_secret`).

### Recommendation
- After signature verification, validate that `repository.owner.login` (the org whose secret authenticated the request) matches the owner segment of `repository.full_name` used by the handler to select records to mutate, rejecting the webhook otherwise.
- In `StatusHandler`, scope the `Commit` lookup by repository/stack (using `stacks`/`repository_name`, as `PushHandler` and `CheckSuiteHandler` already do) rather than a bare, cross-tenant `Commit.where(sha:)`.
- Consider binding each `GithubHook`/webhook secret to a specific repository/stack rather than resolving it dynamically from an unauthenticated field in the request body.

### Proof of Concept
1. Attacker controls organization `attacker-org`, configured in Shipit's `github:` secrets with `webhook_secret: S`. This is legitimate access to their own org, not to the victim.
2. Attacker obtains the SHA of a commit in `victim-org/victim-repo`'s tracked stack (public repo/PR/CI page).
3. Attacker builds a `status` event JSON body:
   ```json
   {
     "sha": "<victim commit sha>",
     "state": "success",
     "context": "ci/required-check",
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" }
   }
   ```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(S, body)` using their own known secret `S`.
5. POST to `/github/webhooks` with `X-Github-Event: status`.
6. `verify_signature` resolves `repository_owner` = `attacker-org`, fetches `attacker-org`'s app/secret, verification succeeds.
7. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — finds the victim's commit (owned by a completely different stack/org) and calls `create_status_from_github!`, creating a forged "success" status on it.
8. The victim's merge queue / deploy eligibility now treats this commit as passing the `ci/required-check` context, even though it never ran on GitHub.

    def merge!
      raise InvalidTransition unless pending?

      raise NotReady if not_mergeable_yet?

      stack.github_api.merge_pull_request(
        stack.github_repo_name,
        number,
        merge_message,
        sha: head.sha,
        commit_message: 'Merged by Shipit',
        merge_method: stack.merge_method
      )
      begin
        if stack.github_api.pull_requests(stack.github_repo_name, base: branch).empty?
          stack.github_api.delete_branch(stack.github_repo_name, branch)
        end
      rescue Octokit::UnprocessableEntity
        # branch was already deleted somehow
      end
      complete!
      true
    rescue Octokit::MethodNotAllowed # merge conflict
      reject!('merge_conflict')
      false
    rescue Octokit::Conflict # shas didn't match, PR was updated.
      raise NotReady
    end

    def all_status_checks_passed?
