### Title
`review_stacks_enabled` is bypassed by an operator-precedence bug in `provision?`/`unarchive?`, allowing attacker-controlled `shipit.yml` execution on disabled repositories - (File: `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb`)

### Summary
`OpenedHandler#provision?` and `ReopenedHandler#unarchive?` intend to gate all review-stack auto-provisioning behind `repository.review_stacks_enabled`, but Ruby's `&&`/`||` precedence makes the check apply only to the `allow_all` branch. When `provisioning_behavior` is `allow_with_label` or `prevent_with_label`, a `ReviewStack` is created and queued for provisioning even if `review_stacks_enabled` is `false`. This lets an attacker who can label their own PR (per the threat model) get a `ReviewStack` provisioned from their fork's `head.ref`, whose `shipit.yml` steps are later executed verbatim by `Command#start`/`PTY.spawn` with `unbundled_env` (including `GITHUB_TOKEN`).

### Finding Description
The intended binding is: `stack_created_or_unarchived == true` implies `repository.review_stacks_enabled == true`, for every `provisioning_behavior`.

The actual code in `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb`: [1](#0-0) 
```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```
Because `&&` binds tighter than `||` in Ruby, this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && label_present) || (prevent_with_label? && !label_present)`

So when `provisioning_behavior` is `allow_with_label` and the provisioning label is present — or `prevent_with_label` and the label is absent — `provision?` returns `true` **regardless of `review_stacks_enabled`**. The identical pattern exists in `ReopenedHandler#unarchive?`: [2](#0-1) 

By contrast, `LabeledHandler#respond_to_label_change?` and `UnlabeledHandler#respond_to_label_change?` correctly AND `review_stacks_enabled` at the top level, so only the `opened`/`reopened` paths are affected.

Exploit flow:
1. Attacker forks the target repo, opens a PR from their fork (`head.ref` is attacker-controlled), and adds the repository's configured provisioning label to their own PR (granted attacker capability per the threat model).
2. GitHub sends a `pull_request` `opened` webhook. `OpenedHandler#process` calls `provision?`, which evaluates true via the `allow_with_label?` branch even though `review_stacks_enabled` is `false`.
3. `ReviewStackAdapter#find_or_create!` creates a `ReviewStack` with `branch: params.pull_request.head.ref` and queues it via `Shipit::ReviewStackProvisioningQueue.add(stack)`. [3](#0-2) 
4. On provisioning/deploy, `Shipit::DeploySpec::FileSystem` reads `shipit.yml` from the checked-out attacker branch and builds `TaskDefinition`s from it, whose `steps` are attacker-controlled strings. [4](#0-3) 
5. Those steps are turned into `Command` objects and executed via `Command#start`, which spawns them with a shell through `PTY.spawn(unbundled_env, *interpolated_arguments, ...)`, and `unbundled_env` merges in `GITHUB_TOKEN`. [5](#0-4) 

Existing guards fail here specifically because the top-level gate (`review_stacks_enabled`) is supposed to be a master switch but the boolean expression's precedence excludes two of the three `provisioning_behavior` branches from that gate.

### Impact Explanation
An attacker who can only open/label their own pull request obtains execution of arbitrary shell commands on the Shipit deploy host (Critical RCE) and can exfiltrate `GITHUB_TOKEN` from the spawned process's environment, on any repository where `provisioning_behavior` is `allow_with_label` or `prevent_with_label`, irrespective of the operator having explicitly disabled `review_stacks_enabled`. This is repeatable per PR/branch and confined to repositories using those two behaviors, but it defeats the intended master kill-switch for the review-stacks feature.

### Likelihood Explanation
Requires the target repository to have `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` (a configuration many teams may set while separately trying to disable review stacks via `review_stacks_enabled = false`, expecting it to be authoritative). No secrets or elevated privileges are needed — only the ability to open a PR and apply/remove a label on it, both attacker-controlled per the stated threat model. Cost is a single webhook-triggering PR action; the bug is deterministic (pure boolean logic), not a race condition.

### Recommendation
Fix operator precedence so `review_stacks_enabled` gates every branch, e.g.:
```ruby
def provision?
  return false unless repository.review_stacks_enabled

  repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```
Apply the same fix to `ReopenedHandler#unarchive?`.

### Proof of Concept
Add to `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`:
```ruby
test "does NOT create stacks for allow_with_label repos when review_stacks_enabled is false" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :allow_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Before the fix, this assertion fails: `provision?` returns `true` and a `Shipit::Stack` is created and queued for provisioning even though `repository.review_stacks_enabled` is `false`, demonstrating the broken equality `stack_created == true` while `review_stacks_enabled == false`. An equivalent test should be added for `ReopenedHandler#unarchive?`.
