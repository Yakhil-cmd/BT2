### Title
Unbounded-length private payment chain processing enables DoS against a wallet recipient - ([File: private_payment.js])

### Summary
`indivisible_asset.js`'s `parsePrivatePaymentChain()`/`validateAndSavePrivatePaymentChain()` and their entry points (`wallet.js:handlePrivatePaymentChains`, `network.js:handleOnlinePrivatePayment`) process the attacker-supplied array `arrPrivateElements` (a private-payment chain) with no maximum length check, analogous to the unbounded `orderbook` loop in the Knox finding.

### Finding Description
A private (indivisible-asset) payment is delivered to a recipient as an ordered chain of private elements (`arrPrivateElements`), one element per hop of the coin's transfer history, sent directly device-to-device or via a hub with `handlePrivatePaymentChains(ws, body, from_address, callbacks)` [1](#0-0) . The only structural validation performed on `body.chains` checks that each element is a non-empty object with the expected fields — it never bounds `c.length` (the chain length) or `arrChains.length` (the number of chains) [2](#0-1) .

Each chain is handed to `network.handleOnlinePrivatePayment()`, which for non-light nodes calls straight into `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, ...)` [3](#0-2) [4](#0-3) .

For the indivisible-asset case, `validateAndSavePrivatePaymentChain()` calls `parsePrivatePaymentChain()`, which iterates the *entire* attacker-controlled array with `async.forEachOfSeries`, and for **every** element performs `validatePrivatePayment()` — itself several sequential DB queries (`initPrivatePaymentValidationState`, spend-proof lookup, `determineIfIncluded`, and a full `validation.validatePayment()` call) — with no cap on `arrPrivateElements.length` anywhere in the call path [5](#0-4) [6](#0-5) .

A grep across the codebase for chain-length guards (`MAX_..._CHAIN`, "chain too long", "too many elements") found no such limit anywhere in `private_payment.js`, `indivisible_asset.js`, `wallet.js`, or `network.js` for this code path (the only related hits were catchup-chain limits, which are unrelated). This is exactly the "unbounded length loop" bug class from the report: an attacker-controlled array is iterated with no size bound and each iteration performs non-trivial, blocking synchronous work (multiple DB round-trips per element).

### Impact Explanation
A malicious private-payment counterparty (anyone who can send a device message / hub-forwarded private payment to a victim, which requires no special privilege — any user can pair with or message another user, and a hub simply forwards) can craft a very large `arrPrivateElements` array (many chained hops) referencing either real or crafted unit/message/output references. When delivered to the victim's wallet via `handlePrivatePaymentChains`, the wallet will synchronously walk the entire chain performing DB reads and hashing for every element before it can return a validation result.

Because `mutex.lock(["saved_private"], ...)` and `mutex.lock('handleJoint')` serialize private-payment handling, and because `handledChainsCache`/`assocValidatedByKey` gating on this path is per-request, a sufficiently long attacker-supplied chain can consume large amounts of CPU/DB time on the victim node, delaying or effectively blocking processing of legitimate incoming private payments and normal transaction validation while the oversized chain is being parsed — a node-level DoS that can cause a wallet to fail to confirm/process pending private payments (temporary fund unavailability), matching the "unbounded loop causes DoS, user funds locked temporarily" impact class from the reference report.

### Likelihood Explanation
Likelihood is moderate-to-high for a targeted attack: the attacker needs only to be a correspondent (pairable via device address) of the victim, or to route the payload through a hub the victim uses, both of which are attacker-reachable without special privilege. No proof-of-work or fee is required to construct or send a private-payment chain message (it's a device-level JSON message, not an on-DAG unit consuming bytes/fees), so the cost to the attacker to build an arbitrarily long array is negligible compared to the victim's processing cost — a classic asymmetric DoS.

### Recommendation
Add an explicit maximum length check on `body.chains` (number of chains) and on each individual chain array (`arrPrivateElements.length`) in `wallet.js:handlePrivatePaymentChains` before any processing begins, and mirror the same bound in `network.js:handleOnlinePrivatePayment` / `private_payment.js:validateAndSavePrivatePaymentChain` so that the check is enforced regardless of entry point (direct network handler, hub-forwarded wallet handler, or `handleSavedPrivatePayments` replay path). Reject any chain exceeding the limit (e.g., `constants.MAX_PRIVATE_CHAIN_LENGTH`) before invoking `parsePrivatePaymentChain`/`validateDivisiblePrivatePayment`.

### Proof of Concept
1. As device A, pair with victim device B (normal wallet pairing, no privilege required).
2. Construct a `private_payment` / `chains` payload where `chains[0]` is an array of, e.g., 50,000 chained private elements, each referencing the previous element's unit/message_index/output_index (fields can reference the same handful of previously-issued private outputs to make construction cheap, or arbitrary but structurally-valid placeholder data sufficient to pass the `isNonemptyObject`/`isNonemptyString` checks in `wallet.js:959-971` before deeper validation fails).
3. Send this payload to victim's device via the hub (`handlePrivatePaymentChains`) or directly (`handleOnlinePrivatePayment`).
4. Observe that the victim node spends significant time inside `parsePrivatePaymentChain`'s `async.forEachOfSeries` loop, issuing DB queries for each of the 50,000 elements sequentially, delaying processing of legitimate private payments and other mutex-guarded operations (`saved_private`, `handleJoint`) held during this time.

Note: I was not able to execute this against a running node to measure exact wall-clock impact; the analysis above is based on static code review of the validation/handling call chain and confirms the absence of any length-bound check in the relevant files.

// arrPrivateElements is ordered in reverse chronological order
function parsePrivatePaymentChain(conn, arrPrivateElements, callbacks){
	var bAllStable = true;
	var issuePrivateElement = arrPrivateElements[arrPrivateElements.length-1];
	if (!issuePrivateElement.payload || !issuePrivateElement.payload.inputs || !issuePrivateElement.payload.inputs[0])
		return callbacks.ifError("invalid issue private element");
	var asset = issuePrivateElement.payload.asset;
	if (!asset)
		return callbacks.ifError("no asset in issue private element");
	var denomination = issuePrivateElement.payload.denomination;
	if (!denomination)
		return callbacks.ifError("no denomination in issue private element");
	async.forEachOfSeries(
		arrPrivateElements,
		function(objPrivateElement, i, cb){
			if (!objPrivateElement.payload || !objPrivateElement.payload.inputs || !objPrivateElement.payload.inputs[0])
				return cb("invalid payload");
			if (!objPrivateElement.output)
				return cb("no output in private element");
			if (objPrivateElement.payload.asset !== asset)
				return cb("private element has a different asset");
			if (objPrivateElement.payload.denomination !== denomination)
				return cb("private element has a different denomination");
			var prevElement = null; 
			if (i+1 < arrPrivateElements.length){ // excluding issue transaction
				var prevElement = arrPrivateElements[i+1];
				if (prevElement.unit !== objPrivateElement.payload.inputs[0].unit)
					return cb("not referencing previous element unit");
				if (prevElement.message_index !== objPrivateElement.payload.inputs[0].message_index)
					return cb("not referencing previous element message index");
				if (prevElement.output_index !== objPrivateElement.payload.inputs[0].output_index)
					return cb("not referencing previous element output index");
			}
			validatePrivatePayment(conn, objPrivateElement, prevElement, {
				ifError: cb,
				ifOk: function(bStable, input_address){
					objPrivateElement.bStable = bStable;
					objPrivateElement.input_address = input_address;
					if (!bStable)
						bAllStable = false;
					cb();
				}
			});
		},
		function(err){
			if (err)
				return callbacks.ifError(err);
			callbacks.ifOk(bAllStable);
		}
	);
}
