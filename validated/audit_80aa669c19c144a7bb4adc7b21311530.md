### Title
Webhook organization/repository binding mismatch allows cross-tenant repository sync trigger - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate the HMAC signature against using an attacker-supplied field from the *same unverified JSON body* (`repository.owner.login`, falling back to `organization.login`), while the handlers that actually act on the payload (e.g. `Shipit::Webhooks::Handlers::PushHandler` via `Handler#repository_name`) key off a *different* field in that same body (`repository.full_name`) to look up the `Repository`/`Stack` to sync. The engine never checks that these two identifiers agree.

### Finding Description
`verify_signature` computes `repository_owner` from the raw, unverified payload and uses it to fetch the corresponding app config/secret via `Shipit.github(organization: repository_owner)`: [1](#0-0) [2](#0-1) 

`Shipit.github` resolves a per-organization secret in the multi-tenant config schema: [3](#0-2) 

Once the HMAC check passes for whatever organization name was embedded in `repository.owner.login`, the same raw JSON is handed to the event handlers. `Handler#repository_name`/`#stacks` derives the target repository purely from `repository.full_name` in that body, with no cross-check against the organization whose secret validated the signature: [4](#0-3) [5](#0-4) 
`Repository.from_github_repo_name` looks the repo up purely by owner/name string parsed out of that field, again independent of the organization that authenticated the request: [6](#0-5) 

**Binding broken:** the organization whose webhook secret authenticated the request (`repository.owner.login` / `organization.login`) is not equal to the repository namespace the handlers execute against (`repository.full_name`). In a single-tenant deployment (one GitHub App, one secret) this is inert because the same secret gates every repository. But the config format explicitly supports **multiple organizations, each with an independent `webhook_secret`**, as documented and implemented in `github_app_config`/`TOP_LEVEL_GH_KEYS`: [7](#0-6) [8](#0-7) 

In that multi-org setup, an attacker who legitimately controls a GitHub App/webhook secret for **their own** onboarded organization ("Org A") can sign an arbitrary JSON body with Org A's secret while setting `repository.owner.login` (or `organization.login`) to `"OrgA"` (so `verify_signature` picks Org A's secret and the HMAC matches) but setting `repository.full_name` to `"OrgB/target-repo"` — a repository belonging to a different, unrelated tenant ("Org B") hosted on the same Shipit instance. Because the signature check and the repository-resolution logic consult two different fields of the same attacker-controlled body, the forged webhook is accepted and dispatched to handlers that act on Org B's stacks (e.g. `PushHandler#process` calling `stack.sync_github(expected_head_sha: ...)`, or the `pull_request` handlers which similarly resolve repositories via `Repository.from_github_repo_name` from the body).

### Impact Explanation
This lets a tenant that only controls its own GitHub App/webhook secret inject GitHub-sourced state changes (push-triggered syncs, PR-driven review-stack lifecycle events, check-run refreshes) into another tenant's stacks without ever possessing that tenant's credentials or repository access. This is a cross-tenant write into another organization's `Stack`/`Repository` records driven by attacker-controlled webhook content — matching the "cross-repository writes" / authorization-boundary-crossing class called out as in-scope impact.

### Likelihood Explanation
Requires the target Shipit instance to be configured in the multi-organization mode (multiple entries under `github:` each with their own `webhook_secret`), and requires the attacker to control (or have configured) a legitimate webhook secret for at least one onboarded organization — both are supported, documented configurations, not privileged Shipit accounts or stolen credentials. No `ApiClient` token, session, or GitHub App private key is needed; only the ability to send an HTTP POST to `/webhooks` with a validly-signed-for-one-org, cross-referencing-another-org body.

### Recommendation
After `verify_signature` passes, re-derive the repository/organization strictly from the same field used for signature-secret selection (or vice versa), and reject/ignore any webhook where `repository.full_name`'s owner segment does not match the organization (`repository.owner.login` / `organization.login`) whose secret validated the HMAC. Alternatively, validate the payload against every configured organization's secret and record which organization matched, then enforce in `Handler#stacks` that the resolved `Repository#owner` equals that matched organization before dispatching.

### Proof of Concept
1. Deploy Shipit with multi-org config: Org A (`webhook_secret: secretA`) and Org B (`webhook_secret: secretB`), each with onboarded repositories/stacks.
2. As an operator/attacker with legitimate access to Org A's webhook configuration (e.g. Org A's own GitHub App settings), craft a push payload:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": { "full_name": "OrgB/target-repo", "owner": { "login": "OrgA" } }
}
```
3. Sign the raw body with `secretA` and send `X-Hub-Signature: sha1=<hmac>` and `X-Github-Event: push` to `/webhooks`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgA"`, fetches Org A's secret, and the HMAC validates (`app/controllers/shipit/webhooks_controller.rb:24-30`).
5. `PushHandler#process` resolves the target via `payload.dig('repository','full_name')` = `"OrgB/target-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`, `push_handler.rb:12-17`), calling `stack.sync_github` on Org B's stack — despite the request never being signed by Org B's secret.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
