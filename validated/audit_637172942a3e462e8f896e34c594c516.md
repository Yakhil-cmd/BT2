### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` corrupts victim `Stack#merge_status` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the target commit(s) for an incoming GitHub `status` webhook purely by matching the commit `sha` string across the entire `commits` table, with no scoping to the repository/stack that the verified webhook payload names. Because git commit hashes are content-addressed and identical across forks/mirrors of the same history, a status event legitimately delivered from an attacker-controlled repository can be applied to a `Commit` row that belongs to a completely different (victim) `Stack`, corrupting that stack's `Stack#merge_status`.

### Finding Description
The broken binding, stated as an equality that should hold but does not: `payload.repository.full_name == stack_of(commit_that_receives_the_status).repository.full_name`.

`StatusHandler#process` is:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

This query is scoped only by `sha`; it does not filter by `stack_id`, `repository_id`, or anything derived from `params.repository`. `Commit#create_status_from_github!` then unconditionally replicates the status onto that commit's own `stack` via `statuses.replicate_from_github!(stack_id, github_status)`: [2](#0-1) [3](#0-2) 

`Stack#merge_status` and its helper `branch_status` then read this corrupted `Status` when computing the classification exposed by `MergeStatusController#show/check` (unauthenticated) and the CI API: [4](#0-3) [5](#0-4) 
`skip_authentication only: %i[check show]` confirms this endpoint is reachable without a Shipit session. [6](#0-5) 

Root cause / why guards don't stop it: `WebhooksController#verify_signature` authenticates the payload's *organization* (via `Shipit.github(organization: repository_owner)` and `GitHubApp#verify_webhook_signature`), i.e., it proves "this event really came from GitHub for the org named in `repository.owner.login`." It does **not** prove, and cannot prove, that the `sha` field inside that payload is unique to that repository — SHA-1 commit identifiers are a function of tree/parent/author/committer/timestamps only, and are therefore identical across any two repositories that share the same commit (the ordinary case for a fork or mirror). Because a legitimate, correctly-signed GitHub `status` event from an attacker's own (forked) repository can carry the exact same `sha` as a commit already ingested into a victim `Stack`, `Commit.where(sha: params.sha)` will match the victim's `Commit` row too, and the status is written there. `drop_unhandled_event`, `ExplicitParameters` schema validation on `StatusHandler`, and model validations on `Repository`/`Stack` play no role here since none of them re-scope the commit lookup by repository.

Attack flow:
1. Attacker forks/mirrors the victim's public repository into a repo they control (or otherwise obtains a repo whose history overlaps a commit already tracked in the victim `Stack`), and connects that repo as a Shipit stack so GitHub delivers signed webhooks to Shipit for it.
2. Attacker creates (or has CI create) a commit status (`state: 'success'`) on that shared commit `sha` in their own repository.
3. GitHub signs and delivers this `status` webhook to Shipit; `verify_signature` passes because it is a genuine signed webhook for the attacker's own org/repo.
4. `StatusHandler#process` finds the `Commit` row(s) with that `sha` — including the victim's row belonging to the victim `Stack` — and calls `create_status_from_github!`, inserting a `success` `Status` for the victim's stack.
5. `Stack#merge_status`/`branch_status` for the victim stack now classifies that previously pending/unknown commit as `success`, changing `merge_status` output (e.g., from `pending`/non-`success` to `success`), consumed by `app/views/shipit/merge_status/success.html.erb`, `MergeStatusController#check` (unauthenticated), and `allows_merges?`. [7](#0-6) 

### Impact Explanation
The victim's `Stack#merge_status` — a shipped-readiness/merge-gating signal — can be flipped by an attacker with no interaction from the victim and no privileged credentials, purely by exploiting the content-addressed nature of git shas and the unscoped `Commit.where(sha:)` lookup. This affects: (a) the unauthenticated `merge_status` HTML/JSON views and the CI badge endpoint (`check`), an unauthenticated-read consequence (High); and (b) `Stack#allows_merges?`, which gates the merge queue's automatic merging (`merge_status == 'success'`), meaning a forged status could contribute to an unauthorized/incorrect merge decision for a repository the attacker never authenticated against (Critical: a payload for one repository mutating another's stack/commit state). The attack is repeatable against any victim stack whose commit history overlaps (via fork/mirror) a repository the attacker can register and post statuses on.

### Likelihood Explanation
Preconditions: the attacker needs (1) a repository they control that shares at least one commit sha with the victim's tracked history — trivially achieved by forking/mirroring a public repo — and (2) that repository registered as a Shipit stack so GitHub webhooks reach Shipit's `/webhooks` endpoint with a validly-signed payload for that org. Both are within reach of an "unprivileged" GitHub user per the threat model (open PRs, push to forks, connect their own repos), no Shipit secrets or GitHub App keys are required, and the webhook itself is genuinely signed by GitHub, not forged. This makes the attack highly feasible and repeatable, limited mainly by needing at least one shared commit sha between attacker- and victim-tracked repositories.

### Recommendation
Scope the commit lookup in `StatusHandler#process` (and any equivalent handler using bare `sha` matching, e.g. `CheckSuiteHandler`/`CheckRunHandler` if similarly implemented) to commits belonging to the stack(s) whose repository matches the verified webhook's `repository.full_name`/`repository.owner.login`, e.g. joining through `Stack`/`Repository` (`Commit.joins(stack: :repository).where(sha: params.sha, repositories: { owner: ..., name: ... })`) instead of a bare `Commit.where(sha: params.sha)`.

### Proof of Concept
Minitest plan (model-level, no live GitHub, mirrors `test/models/shipit/stack_test.rb` merge_status specs):
```ruby
test "cross-repo status forgery corrupts victim merge_status" do
  victim_stack = shipit_stacks(:shipit)          # repo A
  attacker_stack = shipit_stacks(:cyclimse)      # repo B (different repository)

  shared_sha = 'deadbeef' * 5  # 40-char sha representing content shared between forks

  victim_commit = victim_stack.commits.create!(sha: shared_sha, author: shipit_users(:shipit),
    authored_at: Time.now, committer: shipit_users(:shipit), committed_at: Time.now, message: 'shared')
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, author: shipit_users(:walrus),
    authored_at: Time.now, committer: shipit_users(:walrus), committed_at: Time.now, message: 'shared')

  before = victim_stack.reload.merge_status

  # Attacker-authored, correctly-signed webhook payload naming attacker_stack's repository,
  # but with the shared sha
  params = Shipit::Webhooks::Handlers::StatusHandler::Params.new(
    sha: shared_sha, state: 'success', context: 'attacker/ci', branches: []
  )
  Shipit::Webhooks::Handlers::StatusHandler.new(params).process

  after = victim_stack.reload.merge_status

  assert_not_equal before, after   # merge_status classification changed with no victim-side action
  assert victim_commit.reload.statuses.exists?(state: 'success', stack_id: victim_stack.id)
end
```
This asserts the binding `repository named in payload == repository whose merge_status changed` is violated: the status is attributed to `attacker_stack`'s webhook but written onto `victim_commit`/`victim_stack`, flipping `victim_stack.merge_status`.

      maximum_commits_per_deploy && (undeployed_commits_count > maximum_commits_per_deploy * backlog_leniency_factor)
    end

      undeployed_commits.each do |commit|

      end
