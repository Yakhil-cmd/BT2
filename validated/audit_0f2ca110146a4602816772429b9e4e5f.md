### Title
Webhook signature verification is keyed off an attacker-controlled `repository.owner.login`/`organization.login` field that is independent from the `repository.full_name` field used to select the Stack that gets mutated - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which* per-organization webhook secret to verify the HMAC signature against using `repository_owner`, a value read directly out of the unauthenticated, attacker-supplied JSON body. The event handlers, however, resolve the `Stack`/`Repository` that will actually be mutated using a completely different JSON key, `repository.full_name`. Because both values are independent, unauthenticated fields inside the same payload, an attacker can pick an organization whose config verifies weakly (or has no `webhook_secret` configured, in which case verification is skipped entirely) for the "authenticating" field, while pointing `repository.full_name` at a victim organization's stack for the "acted upon" field.

### Finding Description
`WebhooksController#verify_signature` derives the organization used to fetch the GitHub App config/secret purely from request-controlled JSON: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up the config keyed by that same attacker-controlled string and instantiates a `GitHubApp` for it: [3](#0-2) 

If that organization's config has no `webhook_secret` set, `GitHubApp#verify_webhook_signature` short-circuits and returns `true` for *any* payload/signature pair: [4](#0-3) 

Meanwhile, every webhook `Handler` subclass (push, status, check_suite, membership, pull_request) resolves the `Repository`/`Stack` to act on from a **different** JSON key, `repository.full_name`, which is never cross-checked against `repository_owner`: [5](#0-4) 

Since `/webhooks` is an unauthenticated, `verify_authenticity_token`-exempt endpoint reachable by anyone (not just GitHub), and the entire JSON body including both `repository.owner.login` and `repository.full_name` is attacker-supplied, these two fields can be set inconsistently: `repository.owner.login` (used only for choosing/bypassing the signature secret) can name any organization the attacker controls or one with no configured secret, while `repository.full_name` (used to select the actually-mutated `Stack`) can name a victim's repository.

This is the structural analog of the reported bug class: the field covered by the trust check (`repository_owner`, akin to `msg.sender`) is not the same field the code actually operates on (`repository.full_name`, akin to `_policyHolderAddr`).

### Impact Explanation
By forging a payload with mismatched owner/full_name fields, an unauthenticated attacker can inject fabricated events for a stack belonging to an organization/repository they have no legitimate webhook access to:
- `push` events create fake `Commit` records and trigger `GithubSyncJob` against a victim's stack.
- `status` events set arbitrary CI statuses on a victim's commit, which feeds directly into `Commit#deployable?` and can therefore unlock/force an otherwise-blocked deploy.
- `check_suite`/`membership`/`pull_request` handlers can similarly be spoofed for a stack outside the attacker's authenticated organization.

This is a cross-repository/cross-organization write achieved without the correct webhook secret, and can lead to an unauthorized deploy being unblocked via forged CI status — matching the Critical impact bar (cross-repository writes / unauthorized deploy).

### Likelihood Explanation
Exploitability depends on the attacker being able to make `verify_webhook_signature` pass for some `repository_owner` value while claiming a different `repository.full_name`. This is trivially true whenever any configured organization omits `webhook_secret` (documented as optional), or whenever the attacker legitimately controls one small org/repo installed on the same Shipit instance and knows that org's secret — they can then sign the payload correctly for their own org while pointing `full_name` at the victim stack. In single-organization (legacy) configurations where `github_default_organization` is `nil`, `repository_owner` is not used for config lookup, so the mismatch requires a multi-org Shipit deployment; this is a common configuration supported by `Shipit.github_organizations`/`github_app_config`.

### Recommendation
Verify that `repository.owner.login` (or `organization.login`) used to select the signing secret is consistent with `repository.full_name` before dispatching to any handler, and reject requests where they diverge. Additionally, make `webhook_secret` mandatory per configured organization (fail closed instead of `return true unless webhook_secret` in `GitHubApp#verify_webhook_signature`), and have handlers double-check that the resolved `Repository`'s owner matches the organization whose secret validated the signature.

### Proof of Concept
1. Attacker controls (or is aware of) organization `attacker-org`, configured in Shipit's `secrets.github` with no `webhook_secret` (or with a known secret).
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: push` and a body such as:
```json
{
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org" }
  },
  "after": "<attacker-chosen sha>",
  ...
}
```
3. `WebhooksController#repository_owner` returns `attacker-org` [2](#0-1) ; `Shipit.github(organization: "attacker-org")` resolves that org's (secret-less) `GitHubApp`, and `verify_webhook_signature` returns `true` without any real signature [4](#0-3) .
4. `PushHandler`/other handlers resolve the target stack via `payload.dig('repository', 'full_name')` = `"victim-org/victim-repo"` [5](#0-4) , causing `GithubSyncJob` (or a fake commit status) to be applied to the victim's stack despite the request never being validated against victim-org's webhook secret.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
