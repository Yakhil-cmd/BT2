### Title
API-token holder can impersonate any GitHub `User` as deploy/task/lock/merge author via unauthenticated `X-Shipit-User` header - ([File: app/controllers/shipit/api/base_controller.rb])

### Summary
The `SecuritizeBridge` report describes a binding that is checked but not actually enforced consistently (`msg.value == cost` where `cost` can silently drift). The structural analog in this engine is `Shipit::Api::BaseController#identify_user`, which derives the `current_user` used to attribute privileged actions (deploys, rollbacks, task triggers, locks, merges) from a client-supplied header, `X-Shipit-User`, that is never covered by the actual authentication mechanism (the HTTP Basic `ApiClient` token). The credential that is cryptographically verified (the API token) is not the same identity that is bound to and recorded for the action performed.

### Finding Description
`authenticate_api_client` verifies only the bearer token via `ApiClient.authenticate` (HMAC-signed id, see `app/models/shipit/api_client.rb:24-27`), which proves the caller possesses a valid `ApiClient` token and its associated `permissions`/`stack_id` scope. This authentication says nothing about which `Shipit::User` is making the request.

Separately, `current_user` is derived like this: [1](#0-0) 

```
def current_user
  @current_user ||= identify_user || AnonymousUser.new
end

def identify_user
  user_login = request.headers['X-Shipit-User'].presence
  User.where('lower(login) = ?', user_login.downcase).first if user_login
end
```

This header is attacker-controlled and entirely outside the cryptographic envelope of the API token — the token's `message_verifier.verify` only signs the `ApiClient` id, never the acting user login. Any holder of a valid, sufficiently-permissioned `ApiClient` token can set `X-Shipit-User` to the login of any existing `Shipit::User` (e.g., an administrator, or the login corresponding to a `Shipit.github_teams` member) and every downstream action records/executes as that user:

- `Api::DeploysController#create` → `stack.trigger_deploy(commit, current_user, ...)` [2](#0-1) 
- `Api::TasksController#trigger` / `#abort` → `stack.trigger_task(..., current_user, ...)` / `task.abort!(aborted_by: current_user)` [3](#0-2) 
- `Api::LocksController#create` / `#update` → `stack.lock(params.reason, current_user)` [4](#0-3) 
- `Api::MergeRequestsController#update` → `MergeRequest.request_merge!(stack, params[:id], current_user)` [5](#0-4) 

The test suite explicitly confirms this is "claimed" (i.e., asserted, not verified) identity: [6](#0-5) 

The binding that should hold is: `identity cryptographically proven by the request's credential == identity attributed to / acting on the resulting Task/Deploy/Lock/MergeRequest`. Before the request: only the `ApiClient` token's owning `creator`/permissions are proven. After processing `X-Shipit-User`: the recorded `user`/`aborted_by`/`requested_by` is an arbitrary claimed `Shipit::User`, decoupled from any verified credential — breaking the equality entirely.

### Impact Explanation
This is not "unauthorized deploy/rollback" in the sense of bypassing the `deploy:stack` permission check (that permission gate remains intact via `require_permission`), but it enables **audit-trail/authorization-boundary forgery**: a caller who holds a legitimately scoped API token (e.g., a CI integration with `deploy:stack` permission on one stack) can impersonate any registered `Shipit::User` — including privileged team members — as the actor of the deploy, rollback, task, lock, or merge request. Any authorization or workflow logic elsewhere in Shipit that trusts `Task#user`/`Deploy#user` as a proof of "who did this" (audit logs, notifications, "author" attribution surfaced in UI/webhooks) is silently forgeable. This is a genuine crossing of an identity/authentication boundary: the verified credential (`ApiClient` token) and the identity bound to the resulting record diverge, which is exactly the "GitHub identity vs. the `User` bound to the session/action" class called out in scope.

### Likelihood Explanation
High for any deployment where third-party or lower-trust systems are issued `ApiClient` tokens scoped to a single stack (a common integration pattern, evidenced by `here_come_the_walrus` fixture in `test/fixtures/shipit/api_clients.yml`). No additional secrets are required beyond the token that was already intentionally issued to that integration; forging the header costs nothing.

### Recommendation
Do not allow the API layer to accept a client-supplied identity claim without independent verification. Either remove `X-Shipit-User` entirely and always attribute API-triggered actions to a dedicated "service" user tied to the authenticated `ApiClient`, or require the acting-user claim to be authenticated separately (e.g., only trusted internal API clients — flagged as such in the `ApiClient` record — may set this header, and it must be validated against team membership/authorization, not merely login existence).

### Proof of Concept
1. Obtain (or be issued) any valid `ApiClient` token with `deploy:stack` permission scoped to `stack_id: S` (as in fixture `here_come_the_walrus`).
2. `POST /api/stacks/S/deploys` with header `X-Shipit-User: <admin-login>` and `sha: <valid_sha>`.
3. Observe (per `test/controllers/api/deploys_controller_test.rb:49-54`) that `Deploy.last.user == <admin User>`, even though the request was authenticated solely by the scoped API token, proving the recorded actor identity is entirely decoupled from the verified credential.
