### Title
Stale owner votes are replayed as valid approvals after owner removal/re-addition in `multisig_account` - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
`MultisigAccount.owners` can be freely modified via `add_owner(s)`, `remove_owner(s)`, and `swap_owner(s)`, all of which funnel into `update_owner_schema`. However, votes cast on **pending** `MultisigTransaction`s are stored per-transaction in a `SimpleMap<address, bool>` (`transaction.votes`) that is never touched by `update_owner_schema`. Approval/rejection counts are computed by `num_approvals_and_rejections_internal`, which iterates the *current* owners list and looks up each owner's entry in `transaction.votes`. If an owner is removed and later re-added (e.g. `swap_owner`/`remove_owner` followed by `add_owner` with the same address, or `swap_owners` cycling the same address back in), any vote that address previously cast on a still-pending transaction becomes valid again automatically — without that owner casting a new vote after re-joining the account.

### Finding Description
- `update_owner_schema` (lines ~1586-1660 in `multisig_account.move`) mutates `multisig_account_ref_mut.owners` (add/remove) but never iterates `multisig_account_ref_mut.transactions` to purge or invalidate votes belonging to removed owners: [1](#0-0) 
- Votes are stored keyed by owner address on the `MultisigTransaction` itself and set once at creation time (`transaction.votes.add(creator, true)` in `add_transaction`): [2](#0-1) 
- Quorum computation (`num_approvals_and_rejections_internal`) walks the *current* `owners` vector and simply checks whether that address has an entry in `transaction.votes`, with no notion of "when" the vote was cast relative to owner-list changes: [3](#0-2) 
- This same helper is used both by transaction execution cleanup (`remove_executed_transaction` → `transaction_execution_cleanup_common`) and by the VM-prologue-level multisig validation (per the module spec, `validate_multisig_transaction` is invoked by the VM as part of transaction admission and its quorum check is documented as depending on this same approval-count state): [4](#0-3) 

This mirrors the external report's bug class exactly: a "manager set" (owners) can be reconfigured at any time, and doing so does not reset/invalidate state (per-transaction votes) that was recorded under the old configuration. When the previous state is later reactivated by re-adding the same address, it is silently treated as current, valid input to an authorization decision (quorum/admission), rather than requiring fresh consent from the reinstated owner.

### Impact Explanation
This is an approval-validation flaw at the transaction admission boundary for multisig accounts: the VM's `validate_multisig_transaction` prologue and the execution-cleanup quorum check can accept an approval set that includes a "ghost" approval — a vote cast by an address during a *previous* tenure as owner, not re-affirmed after being re-admitted to the owner set. This can let a multisig transaction reach quorum and execute (moving funds, rotating keys, changing further account config) with fewer genuinely current approvals than `num_signatures_required` intends, i.e., unauthorized execution under a manipulated/wrong approval set — directly matching the "Authenticator/multisig approval validation accepting the wrong approval set" admission-gate category.

### Likelihood Explanation
Requires the multisig account's own control flow (an executed multisig proposal) to remove and later re-add the same owner address while transactions remain pending in the queue (multisig-v2 enhancement allows up to `MAX_PENDING_TRANSACTIONS = 20` pending transactions at once, increasing the window). This is a plausible operational sequence (e.g., temporarily rotating out a compromised or unavailable owner and reinstating them later) rather than a contrived edge case, and does not require any privileged/off-protocol assumption beyond the normal owner-management flow that the contract itself exposes.

### Recommendation
When `update_owner_schema` removes an owner, purge that owner's vote entries from all pending `MultisigTransaction`s (or equivalently, re-key/version votes so that a re-added owner's historical votes cannot be replayed as current approvals). Alternatively, track a "membership epoch" per owner and require `num_approvals_and_rejections_internal` to only count votes cast while the voter held continuous owner status.

### Proof of Concept
1. Multisig account `M` has owners `[A, B, C]`, `num_signatures_required = 2`.
2. `A` creates transaction `T` (sequence number `S`); `A`'s vote is auto-recorded as approve (`transaction.votes = {A: true}`).
3. Owners execute a proposal removing `A` (`remove_owner(M, A)`) — `T` remains pending (only 1 approval, quorum not met, so it isn't auto-executed/removed).
4. Owners execute a later proposal re-adding `A` (`add_owner(M, A)`), intending this to be a "fresh" re-admission with no implicit trust carried over.
5. `B` approves `T`. Now `num_approvals_and_rejections_internal` iterates current owners `[B, C, A]`, finds `B: true` and — critically — `A: true` (the stale vote from step 2, never purged) → quorum of 2 is reached with only one *actual* current approval (`B`), and `T` executes even though `A` never voted after being reinstated.

        creator: address,
        multisig_account: address,

            );
        };

        // The transaction creator also automatically votes for the transaction.

        let sequence_number = multisig_account_resource.next_sequence_number;
        multisig_account_resource.next_sequence_number = sequence_number + 1;
        multisig_account_resource.transactions.add(sequence_number, transaction);
        emit(
            CreateTransaction { multisig_account: multisig_account, creator, sequence_number, transaction }
        );

    inline fun num_approvals_and_rejections_internal(owners: &vector<address>, transaction: &MultisigTransaction): (u64, u64) {
        let num_approvals = 0;
        let num_rejections = 0;

        let votes = &transaction.votes;
        owners.for_each_ref(|owner| {
            if (simple_map::contains_key(votes, owner)) {
                if (*simple_map::borrow(votes, owner)) {
                    num_approvals += 1;
                } else {
                    num_rejections += 1;
                };
            }
        });

        (num_approvals, num_rejections)
    }

    fun update_owner_schema(
        multisig_address: address,
        new_owners: vector<address>,
        owners_to_remove: vector<address>,
        optional_new_num_signatures_required: Option<u64>,
    ) {
        assert_multisig_account_exists(multisig_address);
        let multisig_account_ref_mut =
            borrow_global_mut<MultisigAccount>(multisig_address);
        // Verify no overlap between new owners and owners to remove.
        new_owners.for_each_ref(|new_owner_ref| {
            assert!(
                !vector::contains(&owners_to_remove, new_owner_ref),
                error::invalid_argument(EOWNERS_TO_REMOVE_NEW_OWNERS_OVERLAP)
            )
        });
        // If new owners provided, try to add them and emit an event.
        if (new_owners.length() > 0) {
            multisig_account_ref_mut.owners.append(new_owners);
            validate_owners(
                &multisig_account_ref_mut.owners,
                multisig_address
            );
            emit(AddOwners { multisig_account: multisig_address, owners_added: new_owners });
        };
        // If owners to remove provided, try to remove them.
        if (owners_to_remove.length() > 0) {
            let owners_ref_mut = &mut multisig_account_ref_mut.owners;
            let owners_removed = vector[];
            owners_to_remove.for_each_ref(|owner_to_remove_ref| {
                let (found, index) =
                    vector::index_of(owners_ref_mut, owner_to_remove_ref);
                if (found) {
                    vector::push_back(

                        vector::swap_remove(owners_ref_mut, index)
                    );
                }
            });

    /// `validate_multisig_transaction` is called by the VM as part of the transaction prologue.
    /// The timelock change added `ETIMELOCK_NOT_EXPIRED` as a new abort path, separate from the
    /// existing `ENOT_ENOUGH_APPROVALS` quorum failure. This spec documents the verifiable
    /// abort vectors; the quorum, timelock, and payload-match aborts depend on transaction-
    /// level state (and, for timelock, an inline helper plus the optional
    /// `MultisigAccountTimeLock` resource) and are left to `pragma aborts_if_is_partial`.
    spec validate_multisig_transaction(owner: &signer, multisig_account: address, payload: vector<u8>) {
        use std::signer;
        pragma aborts_if_is_partial;
        let multisig_account_resource = global<MultisigAccount>(multisig_account);
        let sequence_number = multisig_account_resource.last_executed_sequence_number + 1;
        let owner_addr = signer::address_of(owner);

        // The multisig account must exist (assert_multisig_account_exists).
        aborts_if !exists<MultisigAccount>(multisig_account);
        // The signer must be an owner of the multisig account (assert_is_owner).
        aborts_if !vector::spec_contains(multisig_account_resource.owners, owner_addr);
        // Sequence-number arithmetic must not overflow.
        aborts_if multisig_account_resource.last_executed_sequence_number + 1 > MAX_U64;
        // The pending transaction must exist at the next sequence number
        // (assert_transaction_exists).
        aborts_if !table::spec_contains(multisig_account_resource.transactions, sequence_number);
    }
