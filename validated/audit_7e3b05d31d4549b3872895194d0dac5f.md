### Title
Double-counting of a single STX lock across the stake→bond rollover boundary via stale `signer-set-ll` entries - ([File: stackslib/src/chainstate/stacks/boot/pox-5.clar])

### Summary
`register-for-bond`'s STX-only rollover check validates only the *current* `staker-info` entry's `(first-reward-cycle + num-cycles) <= first-reward-cycle` (new bond) to gate against overlap, then deletes `staker-info` while leaving the already-written per-cycle `signer-set-ll`/delegation entries from the original `stake` call untouched. When a staker first calls `unstake` to shrink the logical term of `staker-info` and immediately rolls into a bond whose cycle range intersects the *original* (pre-unstake) term, the STX is counted once via the old stake's stale per-cycle entries and again via the new bond's `add-staker-to-signer-cycles` write, for the overlapping cycles.

### Finding Description
The broken equality: `stake counted once per cycle == STX locked once` — for the overlapping cycles this becomes `stake counted twice per cycle != STX locked once`.

Code path:
1. `stake` (pox-5.clar ~1021-1080) calls `add-staker-to-signer-cycles tx-sender signer first-reward-cycle num-cycles amount-ustx true`, which writes one `signer-set-ll` entry per cycle in `[first-reward-cycle, first-reward-cycle+num-cycles-1]`. For Alice: `first=1, num=6` → entries written for cycles 1–6. [1](#0-0) 
2. `unstake` mutates only the `staker-info` map to a shortened logical term (e.g. unlock at cycle 2), as evidenced by the test comment "the new gate compares the raw `staker-info` entry's unlock cycle against the new bond's first cycle". There is no `remove-staker-from-signer-cycles` function anywhere in `pox-5.clar` (confirmed via search), so the per-cycle `signer-set-ll` entries for cycles 2–6, written in step 1, are architecturally impossible to retract.
3. `register-for-bond` reads the *post-unstake* `staker-info` and checks only `(<= (+ first-reward-cycle stake-info) first-reward-cycle-of-bond)` against this now-shortened value. [2](#0-1)  This check passes even though the stale signer-cycle entries for cycles 3–6 (bond 1's active range) still exist in storage.
4. `register-for-bond` then calls `add-staker-to-signer-cycles tx-sender signer first-reward-cycle BOND_LENGTH_CYCLES amount-ustx false`, writing fresh entries for the bond's cycles (3–8 in the test), and only deletes `staker-info` (not the stale `signer-set-ll` rows). [3](#0-2) 

The code's own comment concedes this design point for the "clean" rollover-without-unstake case: "the old stake's signer-cycle memberships stay intact... through its original term" — deliberately leaving the pre-existing entries in place. That is safe only when the old stake's term ends *before* the new bond starts (no cycle overlap), which is what the gate is supposed to guarantee using the *original* (unshortened) term. Once `unstake` is interposed, the gate is checked against a logically-shortened term while the underlying `signer-set-ll` rows still reflect the *original, unshortened* term — reintroducing exactly the overlap the gate was designed to prevent.

### Impact Explanation
For the overlapping cycles (3–6 in the reproduction), Alice's `amount-ustx` is counted in `total_ustx_locked`/signer-weight computations twice: once from the stale entries written by the original `stake` call (now orphaned, since `staker-info` no longer points to them but `signer-set-ll` still does), and once from the new bond's entries written by `register-for-bond`. This inflates signer weight/voting power for signer selection and reward distribution without any additional STX being locked — a double-counted commitment. This matches the Critical impact category ("double-counting a commitment or reward").

### Likelihood Explanation
Preconditions: an STX-only staker with a term long enough to extend past a future bond's start after being shortened by `unstake`; a bond set up and the staker allowlisted for it; the call sequence `unstake` → `register-for-bond` within the same cycle (as in the existing `pox-5.test.ts` "STX-only staker can unstake and roll into a bond" test). All of this is achievable by an ordinary unprivileged staker using only their own STX/sBTC and public entry points — no privileged role required. It is repeatable per rollover and does not require special timing beyond ordinary transaction ordering the attacker already controls.

### Recommendation
Either (a) have `unstake` also physically remove/rewrite the `signer-set-ll` (and any bond-cycle delegation) entries for the cycles beyond the new shortened unlock cycle, or (b) have `register-for-bond`'s overlap gate use the *original, unshortened* `staker-info` term (ignoring any `unstake`-shortened value) so the non-overlap invariant it depends on actually holds against the entries physically present in `signer-set-ll`.

### Proof of Concept
Extend the existing `pox-5.test.ts` scenario "STX-only staker can unstake and roll into a bond on the same cycle" (lines 4730-4812) with:
1. After `register-for-bond` succeeds, walk `get-signer-set-item-for-cycle`/equivalent read-only for cycles 3 through 6 for `signer`.
2. Assert Alice's `amount-ustx` contribution appears only once per cycle in the signer's total; currently it will appear counted via both the stale pre-unstake `stake` entry and the new bond entry, so `total_ustx_locked` for cycle 3 (say) equals `2 * stakeAmount` instead of `stakeAmount`, while `stx-account(alice).locked` is only `stakeAmount`.
3. Compare `sum(signer_totals_for_cycle) == stx-account(alice).locked` (should hold) vs. actual observed value (fails, off by `stakeAmount`) to confirm the double count.
