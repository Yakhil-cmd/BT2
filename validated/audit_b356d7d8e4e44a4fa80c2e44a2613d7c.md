## Title
Cross-Stack Authorization Bypass in CCMenu API via Unscoped `Stack.from_param!` Lookup - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::ApiClient` supports being scoped to a single stack via `belongs_to :stack, optional: true` and `stack_id`, and every other API endpoint in the engine (via `Api::BaseController#stacks`/`#stack`) enforces that scoping. `Api::CCMenuController`, however, overrides `#stack` to resolve the target stack directly from the unscoped `Stack` model, breaking the binding between "the stack a token is authorized for" and "the stack the request actually touches."

### Finding Description
`Api::BaseController` defines the canonical, scope-respecting stack resolution used by the rest of the API: [1](#0-0) 

`stacks` is filtered to `current_api_client.stack_id` when the client is scoped, and `stack` is derived from that filtered relation, so `Api::StacksController#stack` (and other controllers relying on the base helper) correctly return `RecordNotFound` for any stack outside the token's authorized `stack_id`: [2](#0-1) 

`Api::CCMenuController` instead defines its own `#stack` that bypasses this scoping entirely, resolving directly against the global `Stack` collection: [3](#0-2) 

The only authorization check applied is `require_permission :read, :stack`, which is enforced by `ApiClient#check_permissions!`. That method only checks whether the string `"read:stack"` is present in the client's `permissions` array — it has no notion of *which* stack the permission applies to: [4](#0-3) 

The result is a broken equality: `current_api_client.stack_id (the stack the token authorizes)` ≠ `params[:stack_id] (the stack the request touches)`. Any `ApiClient` bearing `read:stack` — including one an administrator deliberately scoped to a single stack by setting `stack_id` — can pass an arbitrary `stack_id` to `Api::CCMenuController#show` and receive deploy/build status for a stack it was never granted access to, because the scoping check that every other controller relies on is skipped here.

### Impact Explanation
This is an authorization-boundary violation matching the "stack a token authorizes versus a stack it touches" analog. A stack-scoped API token (the mechanism specifically meant to restrict a client to one stack) can be used to read build/deploy state — `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`, lock state — for any stack in the Shipit instance, as shown by the CCMenu XML fields under test: [5](#0-4) 

This is an unauthorized cross-stack read of stack/deploy state by a credential that should be confined to a single stack, i.e., an escalation of a narrowly-scoped `ApiClient` token into unauthenticated-equivalent read access to any stack's deploy status.

### Likelihood Explanation
Exploitation requires only possession of any valid `ApiClient` token with the `read:stack` permission (the least-privileged, most commonly issued permission) — no elevated permission, GitHub credentials, or session is needed. Every scoped `ApiClient` (`stack_id` set) is affected equally to an unscoped one, since `CCMenuController#stack` never consults `stack_id` at all.

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the scoped `stacks` collection (as `Api::BaseController` and `Api::StacksController` do), e.g. `stacks.from_param!(params[:stack_id])`, so the client's `stack_id` binding is honored, or explicitly re-validate `current_api_client.stack_id.nil? || current_api_client.stack_id == stack.id` before rendering.

### Proof of Concept
1. Administrator creates an `ApiClient` scoped to `stack_A` with `permissions: ["read:stack"]` and `stack: stack_A` (intending it to only read `stack_A`'s state).
2. Attacker (holder of this token) issues `GET /api/stacks/:stack_B_id/ccmenu.xml` (or via `token` query param, per `CCMenuController#authenticate_api_client`) using `stack_B`'s id, a stack unrelated to the token's `stack_id`.
3. `require_permission :read, :stack` passes because the token has `"read:stack"` in `permissions`, regardless of the specific stack.
4. `stack` resolves via `Stack.from_param!(params[:stack_id])`, ignoring `current_api_client.stack_id`, and returns `stack_B`.
5. The response renders `stack_B`'s deploy status, last build label/time, and web URL — data the token was never authorized to see.
