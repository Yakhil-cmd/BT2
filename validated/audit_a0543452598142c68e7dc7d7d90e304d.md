### Title
Unauthenticated real-time task/stack output exfiltration via `/events` (Pubsubstub::StreamAction) mounted with no access control - ([File: config/routes.rb], [File: lib/shipit/engine.rb])

### Summary
`config/routes.rb` mounts `Pubsubstub::StreamAction.new` directly at `/events` as a bare Rack endpoint, and `lib/shipit/engine.rb`'s `shipit.config` initializer only wires `Pubsubstub.redis_url = Shipit.redis_url.to_s` — it never registers any authorization hook for that mount. Because mounted Rack apps do not inherit `ApplicationController`/`Shipit::ShipitController` `before_action` filters, `force_github_authentication` (in `app/controllers/concerns/shipit/authentication.rb`) never runs for requests to `/events`, and there is no `channel_subscription_authorized_by` method or equivalent anywhere in this engine's code.

### Finding Description
Claimed binding: `channel_subscription_authorized_by(stack) == true` before a client may receive events on `task.<id>` / `stack.<id>` channels.

Actual state in the repo: this method/check does not exist anywhere in the codebase (confirmed via search — zero matches for `channel_subscription_authorized_by`). The mount point is: [1](#0-0) 

This is a raw Rack app mount, not a Shipit controller action, so it never passes through `Shipit::Authentication#force_github_authentication`: [2](#0-1) 

The only place authentication for `/events` is even mentioned is a code comment in `github_authentication_controller.rb`, which states that `/events` (and `/sidekiq`) are supposed to be protected by a `UserRequiredMiddleware` keyed off `session[:authenticated]`: [3](#0-2) 

However, `UserRequiredMiddleware` does not exist anywhere in this engine's source tree (no file defines it, and it is not registered in `lib/shipit/engine.rb`'s middleware stack, which only adds `SameSiteCookieMiddleware` conditionally): [4](#0-3) 

Real task/stack broadcasts use exactly the channel naming scheme an attacker would target — e.g. `"stack.#{id}"` published from `Stack#broadcast_update`, and task-output channels rendered client-side via `subscribe events_path(channels: [...])` in views such as `merge_requests/index.html.erb` and `repositories/show.html.erb`: [5](#0-4) [6](#0-5) 

Attack: an unauthenticated internet client sends `GET /events?channels=task.<id>` (or `stack.<id>`), guessing or enumerating small sequential integer IDs (Shipit uses auto-increment PKs). Since the mount has no authentication or per-channel authorization, the connection is accepted and any subsequent `Pubsubstub.publish` to that channel — including task output chunks written as the task/deploy executes — is streamed to the attacker in real time, with no session, no `ApiClient` token, and no verification that the requester has any relationship to the stack/repository owning that task.

Existing guards do not intervene: `force_github_authentication`, `require_permission!`, `verify_signature`/`verify_webhook_signature`, and the API `stacks` scoping all live in controllers reachable through normal Rails routing, not through the mounted `Pubsubstub::StreamAction` Rack app, so none of them execute on this path.

### Impact Explanation
An attacker gains a live feed of task/deploy output for an arbitrary stack/task ID, repeatable against any ID by iterating small integers, with no authentication barrier. This is an unauthenticated read of task/stack streamed output across tenants (any repository/stack hosted on the same Shipit instance), matching the "High - unauthenticated read of stack state, task streams or deploy output" impact category. Task output can include environment/command echoes and any diagnostic text a deploy task prints, which may include sensitive values depending on the task's commands.

### Likelihood Explanation
No special Shipit configuration, secrets, GitHub App keys, or privileged role is required — only the ability to send an HTTP GET to the Shipit host and knowledge/guessing of a numeric task or stack ID, both of which are low-cost and fully repeatable (IDs are sequential, so enumeration is trivial). This is exploitable purely through this engine's own routing/mount configuration and initializer code, with no live GitHub interaction needed for the PoC.

### Recommendation
Add an authorization layer in front of `/events` within this engine (not relying on undocumented/absent host-app middleware): wrap the `Pubsubstub::StreamAction` mount with a Shipit controller/middleware that runs `force_github_authentication` (or API-client authentication) and validates that the requested channel names correspond to a stack/task/repository the authenticated identity is authorized to view before allowing the subscription, e.g., an actual `channel_subscription_authorized_by(stack)` check performed against `current_user.authorized?` or `current_api_client` scope prior to invoking `Pubsubstub::StreamAction`.

### Proof of Concept
```ruby
# test/integration/events_stream_unauthenticated_test.rb
require 'test_helper'

module Shipit
  class EventsStreamUnauthenticatedTest < ActionDispatch::IntegrationTest
    test "unauthenticated client can subscribe to an arbitrary task channel" do
      task = shipit_tasks(:cyclimse_deploy) # belongs to a stack the client never accessed
      channel = "task.#{task.id}"

      # no session, no cookies, no Authorization header set
      get "/events", params: { channels: channel }, headers: { 'Accept' => 'text/event-stream' }

      assert_response :success # no redirect to github_authentication_path, no 401/403

      Pubsubstub.publish(channel, { output: "SECRET_COMMAND_OUTPUT" }.to_json, name: 'chunk')

      # binding under test: channel_subscription_authorized_by(stack) == true is never evaluated
      assert_includes response.body, "SECRET_COMMAND_OUTPUT"
    end
  end
end
```
Expected/actual: the request succeeds and the attacker-controlled connection receives the published chunk with no session and no membership check against the task's stack, confirming the binding is broken.

    def force_github_authentication
      if current_user.logged_in? && current_user.requires_fresh_login?
        Rails.logger.warn("User #{current_user.id} requires a fresh login, logging out...")
        reset_session
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      elsif Shipit.authentication_disabled? || current_user.logged_in?
        unless current_user.authorized?
          team_handles = Shipit.github_teams.map(&:handle)
          team_list = team_handles.to_sentence(two_words_connector: ' or ', last_word_connector: ', or ')
          render(plain: "You must be a member of #{team_list} to access this application.", status: :forbidden)
        end
      else
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      end
    end
