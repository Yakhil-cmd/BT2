### Title
Webhook `X-Hub-Signature` verification uses a different organization/repository field than the one handlers act on, allowing cross-tenant event forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to HMAC-verify the raw payload against using `repository.owner.login` (or `organization.login`) pulled out of the *attacker-supplied, unverified* JSON body. Once the signature check passes, the event handlers identify the actual target (`Repository`/`Stack`/`Team`) using a **different field of the same payload** — `repository.full_name`, or in the membership case a numeric `team.id` — without ever cross-checking that this target actually belongs to the organization whose secret was used to authenticate the request.

### Finding Description
`verify_signature` computes `repository_owner` purely from the untrusted body: [1](#0-0) 
and uses it to pick the `GitHubApp` (and thus the `webhook_secret`) to validate the signature against: [2](#0-1) 

`GitHubApp#verify_webhook_signature` HMACs the secret it was configured with against the raw body: [3](#0-2) 

The actual handlers dispatched after verification, however, resolve their target from a *different* field of the same JSON body. The generic `Handler` base class resolves the affected stacks from `repository.full_name`, not `repository.owner.login`: [4](#0-3) 

`StatusHandler` applies a forged CI state to *any* commit matching a `sha`, with no repository/stack scoping at all: [5](#0-4) 

`MembershipHandler` looks up an existing `Team` purely by its numeric GitHub `github_id`, and only sets `organization` on first creation — it never re-validates that the team belongs to the organization whose signature was checked: [6](#0-5) [7](#0-6) 

Equality broken: `organization_whose_secret_signed(payload) == organization_that_the_handler_acts_on(payload)` is assumed but never enforced, because both sides are read from independent, unauthenticated fields of the attacker's own JSON body.

### Impact Explanation
Any actor who is an admin of one legitimate organization/repository already registered in this Shipit instance (i.e., who legitimately possesses that org's `webhook_secret` because they configured it themselves) can sign an arbitrary payload with their own secret while setting the "target" fields of the payload to point at a *different, victim* stack/team:
- Forge a `status` event for any commit `sha` in the system (not scoped to their own repo) to flip CI status to `success`, defeating deploy-gating checks — `Commit.where(sha: params.sha)` has no owner/stack constraint.
- Forge a `push` event with `repository.full_name` set to a victim repository, triggering `stack.sync_github(expected_head_sha:)` for a stack they do not own.
- Most severely, forge a `membership` event whose `team.id` matches an existing `Team#github_id` that is part of `Shipit.github_teams` (the set of teams whose membership grants `User#authorized?`), adding the attacker's own GitHub login as a member of that team — this is a direct escalation into `Shipit.github_teams` authorization, i.e., an authentication-bypass into the whole application (`app/models/shipit/user.rb:80-82`, `app/controllers/concerns/shipit/authentication.rb:26-30`).

This matches the required "High/Critical" impact bar: escalation into `Shipit.github_teams` authorization, and potentially unauthorized deploys via forged status checks.

### Likelihood Explanation
The only prerequisite is that the attacker controls (or can obtain) the `webhook_secret` for *any one* organization already registered in the Shipit instance's `github` config — which is expected to be self-service in multi-tenant Shipit deployments (each org/team registers its own GitHub App/webhook secret, as shown in `config/secrets.development.shopify.yml`). No GitHub org admin rights over the *victim* org, no `ApiClient` token, and no session are required — only knowledge of one valid `webhook_secret` for some tenant of the shared engine, which an unprivileged but legitimate onboarding org would possess. Discovering a victim `Team#github_id` or a commit `sha` to target is feasible via GitHub's own public APIs.

### Recommendation
Bind the two fields at verification time: after computing `repository_owner` and locating the target repository/team from the payload, require that the resolved `Repository`/`Team#organization` matches the organization whose `webhook_secret` was actually used to validate the signature, rejecting (422) any mismatch before invoking handlers. For `MembershipHandler`, scope the `Team.find_or_create_by!` lookup by `github_id` **and** `organization` together instead of `github_id` alone.

### Proof of Concept
1. Attacker legitimately administers `attacker-org`, which is registered in Shipit with `webhook_secret = S`.
2. Attacker crafts a `membership` webhook JSON body:
```json
{
  "action": "added",
  "team": { "id": <victim_team_github_id>, "name": "Developers", "slug": "developers", "url": "..." },
  "organization": { "login": "attacker-org" },
  "member": { "login": "attacker-login" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(S, body)` — valid, because `repository_owner` resolves to `"attacker-org"` per `app/controllers/shipit/webhooks_controller.rb:59-62`, and `GitHubApp#verify_webhook_signature` for `attacker-org` succeeds.
4. `MembershipHandler#find_or_create_team!` finds the existing `Team` row by `github_id == victim_team_github_id` (belonging to the victim organization) and calls `team.add_member(attacker_user)`.
5. If that team's id is in `Shipit.github_teams`, `attacker-login`'s `User#authorized?` now returns `true`, granting full access to the Shipit instance.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
