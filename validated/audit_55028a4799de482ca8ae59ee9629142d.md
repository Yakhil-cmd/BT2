### Title
Hub-side `handlePairingMessage` performs no rate limiting on repeated pairing-secret guesses, enabling brute-force pairing with a peer's wallet - ([File: device.js])

### Summary
Any device that can authenticate to a hub (which requires nothing more than generating an ECDSA keypair, per `hub/login`) can repeatedly send `pairing` messages guessing another user's `pairing_secret`. The hub validates the guess against `pairing_secrets` and, on failure, simply calls `ifError` with no throttling, delay, or attempt counter — mirroring the exact bug class in the referenced advisory (auth check present, but no anti-brute-force guess limiting).

### Finding Description
`handlePairingMessage` in `device.js` is the hub-side handler invoked when any logged-in device sends a `pairing` justsaying/message. It checks the guessed `body.pairing_secret` against the `pairing_secrets` table: [1](#0-0) 

If the guess doesn't match a live, non-expired secret, it simply returns `callbacks.ifError("pairing secret not found or expired")` and the caller can immediately retry with another guess — there is no counter, exponential backoff, IP/device-based lockout, or delay of any kind on failed attempts. This is functionally identical to the reported "Telegram webhook missing guess rate limiting" bug class: an authentication token check exists, but repeated wrong guesses are not throttled.

Reaching this function only requires the ability to log in as *a* device to the hub, which is achieved via `hub/login` in `network.js` by presenting a self-generated pubkey/signature pair (no invitation or prior relationship needed): [2](#0-1) 

Once logged in, an attacker-controlled device can send arbitrary numbers of `pairing` messages with different `pairing_secret` guesses to brute-force a weak/short-lived secret shared through a URI such as `byteball:PUBKEY@HUB#SECRET`. The permanent pairing secret is generated with `crypto.randomBytes(9)` (72 bits of entropy), and one-time pairing secrets use the same generator: [3](#0-2) 

While 72 bits is not trivially brute-forceable online given normal network latency, the complete absence of rate limiting removes any defense-in-depth against secrets that are shorter, reused, leaked in part, or guessed via side channels (e.g. QR-code partial capture, shoulder-surfing, or secrets embedded in support tickets/logs with only a few characters redacted). Any hub operator or unprivileged network participant emulating hub protocol can throttle-free hammer this endpoint.

### Impact Explanation
Successful pairing-secret guessing lets an attacker register itself as a `correspondent_device` for the victim's device address: [4](#0-3) 

Once paired, an attacker can pose as a legitimate correspondent to a wallet, AA-related counterparty, or arbiter-contract counterparty — enabling social-engineering-free abuse of flows that trust an already-paired device (e.g., `arbiter_contract.js` sends contract offers/pairing codes directly over the paired device channel), potentially leading to private-payment-chain interception, unauthorized shared-address setup requests, or contract impersonation. This aligns with the "private-payment counterparty / paired device" reachable actor class in scope.

### Likelihood Explanation
Likelihood is limited by the entropy of `crypto.randomBytes(9)` under normal conditions, but is elevated whenever: (a) the pairing secret is a short-lived one-time secret intentionally shared over a low-entropy channel, (b) an attacker has partial knowledge of the secret, or (c) an attacker targets the wildcard permanent secret `'*'` path explicitly allowed in the SQL (`pairing_secret IN(?,'*')`), which some deployments may use as an "open pairing" mode — combined with no throttling, this becomes a purely computational/network-bound brute force with zero cost to the attacker beyond bandwidth.

### Recommendation
Add rate limiting / exponential backoff / attempt counting to `handlePairingMessage` (or upstream in the `pairing` command dispatch) keyed by requesting device address or connection, similar to the fix pattern for GHSA-vcx4-4qxg-mfp4 — throttle repeated failed pairing-secret guesses (e.g., delay responses or lock out a device/IP after N consecutive failures) rather than only rejecting bad guesses.

### Proof of Concept
1. Attacker generates a device keypair and logs into the victim's hub via `hub/login` (no invitation required).
2. Attacker sends repeated `pairing` justsaying messages with different `pairing_secret` guesses targeting the victim's permanent or one-time pairing secret.
3. `handlePairingMessage` rejects each wrong guess with `ifError` and no delay/lockout, allowing unlimited-speed retries.
4. On a correct guess, the attacker's device is inserted into `correspondent_devices` for the victim, completing an unauthorized pairing that can be leveraged for arbiter-contract, shared-address, or private-payment interactions. [5](#0-4)

function handlePairingMessage(json, device_pubkey, callbacks){
	var body = json.body;
	var from_address = objectHash.getDeviceAddress(device_pubkey);
	if (!ValidationUtils.isNonemptyString(body.pairing_secret))
		return callbacks.ifError("correspondent not known and no pairing secret");
	if (!ValidationUtils.isNonemptyString(json.device_hub)) // home hub of the sender
		return callbacks.ifError("no device_hub when pairing");
	if (json.device_hub.length > 200)
		return callbacks.ifError("device_hub too long");
	if (!network.isValidWsUrl(conf.WS_PROTOCOL + json.device_hub))
		return callbacks.ifError("invalid device_hub URL");
	if (!ValidationUtils.isNonemptyString(body.device_name))
		return callbacks.ifError("no device_name when pairing");
	if (body.device_name.length > 100)
		return callbacks.ifError("device_name too long");
	if ("reverse_pairing_secret" in body && !ValidationUtils.isNonemptyString(body.reverse_pairing_secret))
		return callbacks.ifError("bad reverse pairing secret");
	eventBus.emit("pairing_attempt", from_address, body.pairing_secret);
	db.query(
		"SELECT is_permanent FROM pairing_secrets WHERE pairing_secret IN(?,'*') AND expiry_date>"+db.getNow()+" ORDER BY (pairing_secret=?) DESC LIMIT 1", 
		[body.pairing_secret, body.pairing_secret], 
		function(pairing_rows){
			if (pairing_rows.length === 0)
				return callbacks.ifError("pairing secret not found or expired");
			// add new correspondent and delete pending pairing
			var safe_device_name = body.device_name.replace(/<[^>]*>?/g, '');
			db.query(
				"INSERT "+db.getIgnore()+" INTO correspondent_devices (device_address, pubkey, hub, name, is_confirmed) VALUES (?,?,?,?,1)", 
				[from_address, device_pubkey, json.device_hub, safe_device_name],
				function(){
					db.query( // don't update name if already confirmed
						"UPDATE correspondent_devices SET is_confirmed=1, name=? WHERE device_address=? AND is_confirmed=0", 
						[safe_device_name, from_address],
						function(){
							db.query("UPDATE correspondent_devices SET is_blackhole=0 WHERE device_address=?", [from_address], function(){
								eventBus.emit("paired", from_address, body.pairing_secret);
								if (pairing_rows[0].is_permanent === 0){ // multiple peers can pair through permanent secret
									db.query("DELETE FROM pairing_secrets WHERE pairing_secret=?", [body.pairing_secret], function(){});
									eventBus.emit('paired_by_secret-'+body.pairing_secret, from_address);
								}
								if (body.reverse_pairing_secret)
									sendPairingMessage(json.device_hub, device_pubkey, body.reverse_pairing_secret, null);
								callbacks.ifOk();
							});
						}
					);
				}
			);
		}
	);
}
