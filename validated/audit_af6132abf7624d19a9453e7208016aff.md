### Title
CCMenu API endpoint bypasses per-stack `ApiClient` scoping, letting a stack-scoped token read build status for any stack - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::BaseController` scopes stack lookups to the `ApiClient`'s authorized stack when the token is stack-scoped, but `Shipit::Api::CCMenuController` overrides that lookup with an unscoped query, breaking the binding between "the stack a token authorizes" and "the stack the request actually touches."

### Finding Description
`ApiClient` records can be scoped to a single stack (`stack_id`), and `Shipit::Api::BaseController#stacks` is the mechanism that enforces this scope: [1](#0-0) 

`#stack` (used by every other API controller) resolves the requested `stack_id` param only from within that scoped relation, so a token restricted to Stack A raises `RecordNotFound`/404 when a param for Stack B is supplied.

`Shipit::Api::CCMenuController`, however, defines its own private `stack` method that queries `Stack` directly, completely bypassing the `stacks` scoping helper: [2](#0-1) 

The only authorization check performed before `#show` runs is `require_permission :read, :stack`, which validates the client's `permissions` array (e.g. `read:stack`) but never checks whether the requested `stack_id` matches `current_api_client.stack_id`: [3](#0-2) [4](#0-3) 

This is the same bug class as the reported `RouteDescription.routingFee`: a value that is supposed to be bound/constrained by a security-relevant relationship (fee tied to `> 0` intent vs. actual enforced range; here, "stack accessible" tied to "stack authorized by token") but the enforcement point silently omits the actual binding check, letting the caller supply any value (`1 wei` / any other `stack_id`) and still pass.

Equality that should hold: `stack_touched_by_request == stack_authorized_by(current_api_client)` (when `current_api_client.stack_id?` is true). After the CCMenu controller's override, this equality is never checked; `stack_touched_by_request` is fully attacker-controlled via the `stack_id` path param regardless of `current_api_client.stack_id`.

Before the flaw (`Api::StacksController`, `Api::DeploysController`, etc. using inherited `#stack`): a stack-scoped `ApiClient` token can only ever resolve `stacks.from_param!(...)`, i.e. its own stack.
After (`Api::CCMenuController`): the same token resolves `Stack.from_param!(params[:stack_id])` — any stack in the installation.

### Impact Explanation
This qualifies as the High-severity category "unauthenticated/unauthorized read of stack state, task streams or deploy output": a holder of any valid `ApiClient` token scoped to one stack (e.g. an external CI/monitoring integration issued a `read:stack`-only, stack-scoped token) can enumerate `stack_id` values and read `deploys_and_rollbacks` status, lock state, and build metadata (`lastBuildStatus`, `lastBuildLabel`, `webUrl`, etc.) for every other stack in the Shipit installation, including private/internal repositories the token was never meant to see. It is a cross-stack information disclosure that defeats the multi-tenant isolation `ApiClient.stack_id` is designed to provide.

### Likelihood Explanation
Likelihood is high for anyone who already possesses a legitimately-issued, stack-scoped API token (the normal/expected way CCMenu tokens are minted, see `CCMenuUrlController#client` which creates clients with `read:stack` permission bound to a specific stack). No privilege escalation, secret theft, or additional credentials are required — only changing the `stack_id` route/query parameter on an otherwise valid, authenticated request.

### Recommendation
Remove the `stack` override in `Shipit::Api::CCMenuController` (or reimplement it via `stacks.from_param!(params[:stack_id])`) so CCMenu lookups honor the same `ApiClient.stack_id` scoping enforced by `Shipit::Api::BaseController#stacks`.

### Proof of Concept
1. Create/obtain a stack-scoped `ApiClient` token authorized only for Stack A with `read:stack` permission (e.g. via `Shipit::CCMenuUrlController#client`, which does exactly this: `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(...)` bound implicitly to one stack's CCMenu URL).
2. Send `GET /ccmenu/*stack_id?token=<token>` for Stack A — succeeds as expected.
3. Send the same request but replace the `stack_id` path segment with Stack B's identifier (a stack the token was never granted access to).
4. Observe `Api::CCMenuController#stack` resolves via `Stack.from_param!(params[:stack_id])` (app/controllers/shipit/api/ccmenu_controller.rb:29-31), ignoring `current_api_client.stack_id`, and the response renders Stack B's build status/deploy history — confirming the cross-stack read.
