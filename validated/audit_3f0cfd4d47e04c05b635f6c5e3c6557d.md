### Title
Staking Info Written to DB Before Block Validation in Fast Sync, No Rollback on `InsertReceiptChain` Failure — (`datasync/downloader/downloader.go`)

### Summary
In `commitFastSyncData`, peer-supplied staking info is unconditionally persisted to the KV database before `InsertReceiptChain` validates the corresponding blocks. If `InsertReceiptChain` returns an error, the staking info write is not rolled back, leaving attacker-controlled reward addresses permanently stored at `stakingInfoKey(sourceNum)`.

### Finding Description
`commitFastSyncData` iterates over `fetchResult` objects and calls `d.stakingModule.PutStakingInfoToDB` for each result that carries staking info, then calls `d.blockchain.InsertReceiptChain`. [1](#0-0) 

`PutStakingInfoToDB` delegates directly to `WriteStakingInfo`, which performs an unconditional `db.Put` with no validation of the staking info content against any on-chain commitment, header hash, or state root. [2](#0-1) 

There is no database transaction wrapping both the staking info write and the receipt chain insertion, and no compensating delete is issued on the error path. The same pattern is present in `commitPivotBlock`. [3](#0-2) 

`DeliverStakingInfos` accepts staking info from any P2P peer with no authentication of the sender's authority or validation of the `BlockNum` field. [4](#0-3) 

### Impact Explanation
A malicious P2P peer connected to a node in fast sync mode can:
1. Deliver `StakingInfo` with attacker-controlled reward addresses targeting an arbitrary `sourceNum`.
2. Deliver invalid receipts for the same blocks, causing `InsertReceiptChain` to fail.
3. The staking info is now durably stored at `stakingInfoKey(sourceNum)` with no rollback.

All future reward calculations that read staking info for that `sourceNum` will use the poisoned reward addresses, redirecting KAIA block rewards to attacker-controlled accounts. [5](#0-4) 

### Likelihood Explanation
Requires the victim to be in fast sync mode and the attacker to be an accepted P2P peer during that session. Fast sync is the default for new nodes and nodes that have fallen significantly behind. P2P peer connections are permissionless on the public network. Likelihood is medium.

### Recommendation
Move `PutStakingInfoToDB` to after a successful return from `InsertReceiptChain`, or wrap both operations in a batch/transaction that is atomically committed only on success. At minimum, add a compensating `DeleteStakingInfo` call on the error path. Additionally, validate the staking info content against a commitment in the block header before persisting it.

### Proof of Concept
Build an integration test that:
1. Constructs a `fetchResult` batch where each result has a `StakingInfo` with attacker-controlled reward addresses.
2. Delivers the batch to `commitFastSyncData` with receipts that will cause `InsertReceiptChain` to return an error.
3. Confirms `commitFastSyncData` returns a non-nil error.
4. Reads `stakingInfoKey(sourceNum)` directly from the KV store and asserts the poisoned staking info is present, demonstrating no rollback occurred. [6](#0-5) [7](#0-6)
