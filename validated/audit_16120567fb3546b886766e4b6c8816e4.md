### Title
Cross-organization webhook forgery via webhook-secret/repository binding mismatch - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to verify a webhook's HMAC against using the `repository.owner.login` (or `organization.login`) field taken from the *same, attacker-suppliable* JSON body it is about to validate. In a multi-tenant Shipit deployment (multiple orgs, each with its own GitHub App and its own `webhook_secret`), nothing ties the organization whose secret validated the signature to the organization/repository that the downstream event handlers actually act on (e.g., `repository.full_name` used to resolve the target `Stack`). This mirrors the `price()` bug's root cause: two values that are supposed to represent the same underlying "thing" (the authenticating principal and the entity ultimately written to) are computed/scaled independently and can diverge.

### Finding Description
`Shipit.github(organization:)` supports a multi-org configuration where each organization key in `secrets.github` has its own independent config, including its own `webhook_secret`: [1](#0-0) 

`WebhooksController#verify_signature` picks the org (and therefore the secret) to validate against using a field pulled out of the untrusted JSON payload itself: [2](#0-1) [3](#0-2) 

The HMAC check in `GitHubApp#verify_webhook_signature` only proves that the raw body was signed with *whatever secret was selected* — it says nothing about whether the `repository.owner.login` used to pick that secret matches other identity fields (e.g. `repository.full_name`) inside that same body that the event handlers (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, PR handlers) subsequently use to resolve which `Stack`/`Repository` to act on: [4](#0-3) 

Because the field used to select the signing secret (`repository.owner.login`) and the field used to resolve the target repository (`repository.full_name`) both live inside the same attacker-controlled JSON body, and only the former is bound to the verified secret, an organization that legitimately owns/operates its own GitHub App in the multi-tenant setup (and thus legitimately knows its own `webhook_secret`) can forge a payload where `repository.owner.login` = its own org (so signature verification succeeds), while `repository.full_name` names a *different* organization's repository. The equality that should hold — `organization authenticated by the signature == organization whose repository is written to` — is broken because only the owner-login sub-field is checked, not the full repository identity that downstream code trusts.

### Impact Explanation
This lets an operator/admin of one tenant organization forge validly-signed webhook events (`push`, `status`, `check_suite`, `pull_request`, `membership`) that Shipit will process as if they originated from a different organization's repository, since the raw-body HMAC only proves possession of *a* configured secret, not that the claimed repository belongs to that secret's organization. Depending on which handler is targeted this can drive `GithubSyncJob`/status updates/merge-queue processing against a `Stack` that belongs to a repository the attacker does not control — a cross-organization write/trust violation consistent with the "organization that authenticated versus the repository that is written" binding class called out as in-scope.

### Likelihood Explanation
Exploitability depends entirely on the deployment being multi-tenant (multiple orgs each with independently configured GitHub Apps/`webhook_secret`s in `secrets.github`), which is an explicitly supported configuration path (`github_organizations`, `github_app_config`) rather than a hypothetical setup. Any tenant org operator, without needing a Shipit session, `ApiClient` token, another org's secret, or repository write access to the victim repository, can attempt this by simply signing an arbitrary payload with their own legitimately-known secret.

### Recommendation
Bind the verified organization to every identity field the downstream handlers rely on, not just `repository.owner.login`/`organization.login`. Concretely, after selecting the org from the payload and verifying the signature, re-derive/validate that `repository.full_name`'s owner segment equals the same `repository_owner` used to pick the secret (reject if they differ), or better, resolve the `Stack`/`Repository` strictly by an identifier that is cross-checked against the authenticated organization before any handler runs.

### Proof of Concept
Note: I was not able to fully inspect `push_handler.rb` / `status_handler.rb` in this pass (ran out of tool calls) to confirm the exact field(s) they use to resolve the `Stack`, so the following is based on the `GithubSyncJob` enqueue behavior observed in `test/controllers/webhooks_controller_test.rb` (`":push with the target branch queues a GithubSyncJob"`) which enqueues based on the payload's repository data:

1. Multi-tenant Shipit configured with `secrets.github` containing keys `org-a` and `victim-org`, each with its own `webhook_secret`.
2. Attacker legitimately controls `org-a`'s GitHub App and therefore knows `org-a`'s `webhook_secret`.
3. Attacker crafts a JSON body:
```json
{
  "repository": { "owner": { "login": "org-a" }, "full_name": "victim-org/private-repo" },
  "after": "<attacker-controlled-sha>"
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(org-a-secret, body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` computes `repository_owner = "org-a"`, fetches `org-a`'s app/secret, and the HMAC check passes because the attacker legitimately knows that secret.
6. The `push` handler processes the payload against `repository.full_name = "victim-org/private-repo"`, acting on a `Stack` outside the authenticated organization's control. [5](#0-4) [1](#0-0)

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
