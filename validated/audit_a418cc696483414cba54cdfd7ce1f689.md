### Title
`pallet-psm::mint()` discards the actual amount transferred by `T::Fungibles::transfer`, minting internal asset against an assumed (not verified) external deposit - ([File: substrate/frame/psm/src/lib.rs])

### Summary
`pallet_psm::Pallet::mint` computes `effective_external` as the amount of external asset that should be pulled from the caller, calls `T::Fungibles::transfer(external_asset, &who, &psm_account, effective_external, Preservation::Expendable)?` to move it into the PSM reserve, and then unconditionally mints `internal_to_user` (+ fee) based on `effective_external`/`internal_equivalent` — without checking that the `Ok` value returned by `transfer` (the actual amount that entered the reserve) equals `effective_external`. This is the same missing-invariant pattern as Notional's `depositExactToMintPrimeCash()`, which fails to verify `netTransferExternal == actualTransferExternal`.

### Finding Description
`T::Fungibles: fungibles::Mutate<T::AccountId, AssetId = T::AssetId, Balance = BalanceOf<T>>` — the `transfer` method of that trait returns `Result<Self::Balance, DispatchError>`, where the `Ok` value is documented as the *actual* amount transferred (which, per the trait semantics, may be adjusted, e.g. increased to sweep dust when a `keep_alive`/`Preservation` mode forces full-balance transfer, or reduced under `BestEffort` precision paths reachable in generic `Mutate` implementations).

In `mint()`: [1](#0-0) 
the call `T::Fungibles::transfer(external_asset.clone(), &who, &psm_account, effective_external, Preservation::Expendable)?;` discards its `Ok(actual_amount)` return value entirely — the `?` only propagates an `Err`, the success value is dropped. The subsequent `mint_into` calls then credit `internal_to_user` and `fee` computed from `effective_external`/`internal_equivalent`, with no assertion that the PSM reserve account actually received `effective_external` of `external_asset`.

Because `T::Fungibles` is a generic associated type (`Config::Fungibles`), whatever concrete implementation a runtime plugs in (e.g. a custom `fungibles::Mutate` adapter, an asset with non-standard debit/credit semantics, or any future/derived asset class with rounding, fee, or dust-sweeping behavior baked into its `transfer`) can legally return an actual amount different from the requested one while still returning `Ok`. The pallet has no defensive `ensure!(actual == effective_external, ...)` to catch this, unlike its sibling `redeem()` path, which at least defensively checks the reserve (`get_reserve`) before paying out, or `pallet_asset_conversion_ops`, which explicitly checks `balance2 == T::Assets::transfer(...)?` and returns `Error::<T>::PartialTransfer` on mismatch: [2](#0-1) 

This shows the codebase itself recognizes "verify actual transferred amount before proceeding" as the correct pattern elsewhere, but `pallet-psm::mint` omits it — mirroring exactly the Notional bug class: minting/crediting an amount assumed to equal a requested transfer, without confirming the transfer actually delivered that amount.

### Impact Explanation
If the configured `T::Fungibles` implementation (or any future external asset backing it) ever returns an actual transferred amount smaller than requested while still returning `Ok` (analogous to a fee-on-transfer/rebasing token in the EVM report), `pallet-psm` would:
- Record `PsmDebt` increased by `internal_equivalent` even though the reserve received less than `effective_external` of the external asset.
- Mint `internal_to_user` + `fee` fully backed by an insufficient reserve deposit, breaking the 1:1 peg backing invariant that the whole PSM design (and its debt-ceiling accounting) depends on.
- This directly threatens insolvency/undercollateralization of the internal stablecoin, which is a core invariant of a peg-stability module.

This is a Medium-class impact analog: it does not by itself demonstrate value with the currently wired standard `pallet-assets`/`pallet-balances` fungibles adapters (which do not exhibit fee-on-transfer behavior and transfer exactly the requested amount under `Preservation::Expendable` in the non-dust-sweep case), but the pallet's code is not defensively checking the invariant, and its own sibling code elsewhere in the repo (`asset-conversion-ops`) treats this check as necessary security practice.

### Likelihood Explanation
Low-to-Medium. Exploitability is contingent on the runtime's chosen `T::Fungibles` implementation returning an actual amount different from requested while returning `Ok` — this cannot be demonstrated as reachable purely from the standard `pallet-assets`/`pallet-balances` `Mutate` implementations shipped in this SDK, which transfer exactly the requested amount in the `Expendable`, non-full-balance-sweep case. It becomes a real bug only if a runtime integrator wires a non-standard/foreign asset backend (e.g. an XCM-derived remote asset, a wrapped asset with internal fees, or any 3rd-party `fungibles::Mutate` impl) as `T::Fungibles` for `pallet-psm`.

### Recommendation
Capture and verify the actual amount transferred before minting/crediting:
```rust
let actual_external = T::Fungibles::transfer(
    external_asset.clone(),
    &who,
    &psm_account,
    effective_external,
    Preservation::Expendable,
)?;
ensure!(actual_external == effective_external, Error::<T>::PartialTransfer);
```
mirroring the pattern already used in `substrate/frame/asset-conversion/ops/src/lib.rs`.

### Proof of Concept
No concrete PoC was executed. This finding is a structural/code-audit analog: the missing invariant check (`actual == expected` after `T::Fungibles::transfer`) was located and confirmed by direct inspection of `mint()` at [3](#0-2) . A full reproduction would require instantiating `pallet-psm`'s mock runtime with a custom `fungibles::Mutate` implementation whose `transfer` legitimately returns `Ok(actual)` with `actual < requested` (not achievable with the standard `pallet-assets`/`pallet-balances` backends bundled in this repo, which were not observed to exhibit such behavior in the reviewed code paths). I was not able to verify within the available iterations whether any concrete `T::Fungibles` implementation wired into a real polkadot-sdk runtime configuration for `pallet-psm` can produce this mismatch; this remains unconfirmed and is flagged as a defensive-coding gap rather than a proven exploitable path against the currently shipped asset backends.
