### Title
Webhook signature verification org (`repository.owner.login`) diverges from the org whose repository/stack is mutated (`repository.full_name`) — cross-org forged webhook triggers unauthorized re-provisioning - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb`)

### Summary
`WebhooksController#verify_signature` derives the signing organization from `params.dig('repository','owner','login')`, while `ReopenedHandler#repository` resolves the actual `Shipit::Repository` record from the independent field `params.repository.full_name` via `Repository.from_github_repo_name`. These two JSON fields are never cross-checked, so an attacker who controls their own org's webhook secret can forge a payload naming a victim repository in `full_name` while keeping `owner.login` pointed at their own org, passing signature verification while operating on the victim's stack.

### Finding Description
The broken binding, stated as an equality that must hold but doesn't: `organization_that_signed_the_request (params.repository.owner.login) == organization_owning_the_mutated_stack (Repository.from_github_repo_name(params.repository.full_name).owner)`.

Code path:
- `WebhooksController#verify_signature` computes `repository_owner` purely from `params.dig('repository', 'owner', 'login')` [1](#0-0)  and uses it to select the GitHub App/secret used for HMAC verification: `Shipit.github(organization: repository_owner)` then `github_app.verify_webhook_signature(...)` [2](#0-1) .
- `ReopenedHandler#repository` resolves the real DB `Repository` used for all subsequent logic strictly from `params.repository.full_name`, a completely separate JSON field: `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [3](#0-2) .
- The `ExplicitParameters` schema for this handler only requires `repository.full_name`; it does not require or validate `repository.owner.login` at all, and nothing anywhere reconciles the two fields [4](#0-3) .
- `#unarchive?` then evaluates against the **victim's real** `Repository` config (`review_stacks_enabled`, `provisioning_behavior_*`, `provisioning_label_name`) pulled straight from the database [5](#0-4) .
- `#process` calls `stack.unarchive!`, which via `ReviewStackAdapter#unarchive!` adds the stack to `Shipit::ReviewStackProvisioningQueue` and calls `stack.unarchive!` inside a transaction, resulting in re-provisioning (Commands/deploys run for the victim's stack) [6](#0-5) .

Attacker's exact request: `POST /webhooks` with header `X-Github-Event: pull_request`, JSON body with `action: "reopened"`, `repository.full_name: "victim-org/victim-repo"`, `repository.owner.login: "attacker-org"`, `pull_request.labels` crafted to satisfy the victim repo's configured `provisioning_behavior` (e.g. no label for `allow_all`, or absence of label for `prevent_with_label`), and `X-Hub-Signature` computed with the attacker's own org's `webhook_secret` (which the attacker legitimately knows, since it is their own repository's GitHub App installation secret). Because `verify_signature` only ever looks at `repository.owner.login` (here "attacker-org") to pick which secret to check against, this signature is valid, even though the mutated repository/stack belongs to "victim-org".

Existing guards do not close this gap: `drop_unhandled_event` only checks the event type is registered; `ExplicitParameters` only validates presence/shape of fields, not owner/full_name consistency; `GithubOrganizationUnknown` handling only rejects unknown orgs, not mismatched ones; there is no code anywhere comparing `repository.owner.login` to the owner segment of `repository.full_name`.

### Impact Explanation
An attacker who has any active Shipit-integrated GitHub org (i.e., their own org/repo is registered with Shipit, giving them a legitimate webhook secret for "attacker-org") can forge webhooks that mutate an unrelated victim repository's `ReviewStack`. Specifically they can force `Shipit::ReviewStackProvisioningQueue.add(stack)` and `stack.unarchive!` to run for the victim's stack, causing re-provisioning, which per `ReviewStackAdapter#unarchive!` runs deploy `Command`s on the victim's stack outside of any GitHub-authenticated action from the victim's own repository. This is a payload for one org mutating another org's stack/task and triggering an unauthorized deploy — matching the Critical impact category (forged webhook accepted as authentic; unauthorized deploy). It is repeatable against any victim repository whose full name and provisioning configuration the attacker can learn (both typically public information for open-source repos), for as long as the corresponding `ReviewStack` exists and is archived (or missing, triggering creation+provisioning).

### Likelihood Explanation
Preconditions: `review_stacks_enabled` must be true for the victim repository, and the archived `ReviewStack` for the targeted PR number must exist (or none, triggering auto-creation); the attacker needs their own Shipit-registered org/repo webhook secret (a trivial precondition — any Shipit customer org onboarded normally has this) and knowledge of the victim's `provisioning_behavior`/label name, which is normally discoverable from the victim's public PR/label configuration. The attacker cost is a single crafted HTTP POST with a valid HMAC signed by their own secret — no interaction with the victim's GitHub App, no Shipit session, and no privileged role is required. This is fully repeatable against any repository whose full name is known.

### Recommendation
In `WebhooksController#verify_signature`, and in every PullRequest handler's `#repository` resolution, ensure the organization used to select/verify the webhook secret is the same organization that owns the repository being mutated. Concretely: derive `repository_owner` from the owner segment of `params.repository.full_name` (or equivalently validate `params.repository.owner.login == full_name.split('/').first`) before calling `Shipit.github(organization: repository_owner)`, and reject the request (422) if they diverge.

### Proof of Concept
Minitest under `test/controllers/webhooks_controller_test.rb` (or `test/models/shipit/webhooks/handlers/pull_request/reopened_handler_test.rb` if testing at the handler level bypassing the controller signature check to isolate this specific model-level divergence):

1. Setup: create `victim_repository` (owner: `victim-org`, name: `victim-repo`) with `review_stacks_enabled = true`, `provisioning_behavior = :allow_all`. Create an archived `ReviewStack` for PR number N under `victim_repository`.
2. Configure two GitHub App orgs in test config: `attacker-org` with `webhook_secret = "attacker-secret"` and `victim-org` with `webhook_secret = "victim-secret"` (distinct, unknown to attacker).
3. Build payload: `action: "reopened"`, `repository.full_name: "victim-org/victim-repo"`, `repository.owner.login: "attacker-org"`, `number: N`, minimal valid `pull_request` fields.
4. Sign the raw payload body with `attacker-secret` (HMAC-SHA1), set as `X-Hub-Signature` header, and `X-Github-Event: pull_request`.
5. Assert on the equality binding: before the request, `repository_owner_from_payload ("attacker-org") != victim_repository.owner ("victim-org")`.
6. POST to `/webhooks` with this payload/signature.
7. Assert `response.status != 422` (signature accepted, since it validates against `attacker-org`'s secret, not `victim-org`'s).
8. Assert `Shipit::ReviewStackProvisioningQueue.add` was invoked (or stub/mock and assert called) with the victim's `ReviewStack`, and/or assert `victim_review_stack.reload.archived? == false` after the request — demonstrating that a payload signed by attacker-org's secret mutated victim-org's stack.
