### Title
Balance-derived spot-price formulas in Autonomous Agents can be manipulated atomically via chained AA triggers - (File: aa_composer.js, formula/evaluation.js, test/samples/uniswap_like_market_maker.oscript)

### Summary
Ocore's Autonomous Agent (AA) engine natively supports the exact primitive that made the Maverick oracle exploit possible: a price/exchange-rate that is derived from the current on-chain reserve balance of a contract, combined with the ability to atomically chain multiple contract calls (and roll back everything on failure) within a single unit — functionally equivalent to a flash loan. Any AA that prices assets from its own `balance[...]`, exactly as shown in ocore's own shipped example AA (`uniswap_like_market_maker.oscript`), is exposed to the same reserve-manipulation attack described in the Maverick report.

### Finding Description
The oscript formula language exposes a `balance[asset]` / `balance[address][asset]` operator that returns the AA's *current* balance, which already includes the funds sent in the very same trigger being processed: [1](#0-0) 

Because this value is read live during evaluation of the current trigger, any AA that builds a constant-product/spot-price formula from it is subject to the same class of manipulation as `MavEthOracle.getPriceInEth()`, which derived price from live Maverick pool reserves. Ocore ships exactly such an AMM-style example that computes an instantaneous price via `$p = $asset_balance * $bytes_balance` and prices a swap from `balance[base]` / `balance[$asset]`: [2](#0-1) [3](#0-2) 

Unlike a plain single EVM transaction, ocore additionally provides a native, no-cost equivalent of a "flash loan": a primary AA trigger can synchronously spawn secondary AA triggers (an AA's outgoing payment to another AA address triggers that AA within the *same unit*, in the *same DB transaction*), and the whole chain is committed or entirely rolled back atomically: [4](#0-3) [5](#0-4) 

This chaining is exercised and confirmed working across multiple AA hops in ocore's own test suite (`chain of AAs`, 3-hop `issue recently defined asset`), proving that several AA invocations can be composed and executed atomically as a single logical operation: [6](#0-5) [7](#0-6) 

If any AA in the chain bounces, the whole operation reverts with no economic loss to the attacker beyond the bounce fee, since `bounce()`/`revert()` unwind state changes and balances within the same atomic transaction: [8](#0-7) 

Combining these two native features (balance-derived pricing + atomic multi-hop AA chaining with free rollback) reproduces the exact primitive Maverick's attacker used a flash loan for: an attacker can, in one unit, (1) send an oversized swap to a balance-priced AA to skew its `asset_balance`/`bytes_balance` ratio, (2) within the same atomic unit trigger a second action (either back into the same AA's other case branch, e.g. "invest"/"divest", or into a paired AA that reads the now-manipulated `balance[]`/state of the first) that is priced off the skewed ratio, and (3) unwind the initial swap in the same unit, all of which either fully commits (profit extracted from the AMM) or fully reverts (no loss) — a risk-free reserve-manipulation attack against any AA following ocore's own documented AMM pattern.

### Impact Explanation
An attacker can drain value from any deployed AA whose swap/exchange-rate/oracle logic is based on the AA's own `balance[...]` (the pattern ocore's official sample explicitly recommends and other AAs are likely to copy), by momentarily skewing the reserve ratio and exploiting a paired/chained action priced off that skewed ratio, then reversing the position — all atomically and with the ability to freely roll back if unprofitable. This is direct unauthorized extraction of AA funds (asset issued by the AMM or bytes/base reserves), i.e. concrete AA fund loss, matching a Medium/High severity oracle/price-manipulation finding.

### Likelihood Explanation
The attack requires no privileged access — any address can post a unit with a data/payment trigger. The building blocks (balance[]-based pricing formulas and multi-hop atomic AA chaining) are core, documented, intentionally supported ocore/oscript features (not a bug in the engine itself), and ocore's own bundled sample AA demonstrates the vulnerable pricing pattern as a reference implementation, making it likely that real-world AAs built by following ocore's examples/documentation would inherit this exact weakness. The atomic all-or-nothing execution model makes the exploit essentially risk-free for the attacker.

### Recommendation
- Update ocore's official example AAs (e.g. `uniswap_like_market_maker.oscript`) and any developer documentation to avoid instantaneous `balance[...]`-derived spot pricing, and instead recommend TWAP-style or externally-attested price sources (e.g., `data_feed[...]`), or explicit reentrancy/atomicity guards (e.g., disallow pricing an action when the primary trigger's unit contains more than one payment/message affecting the same asset pair, or require a minimum number of confirmed MCIs between deposit and pricing).
- Consider adding engine-level primitives (e.g., a "locked" flag or `number_of_responses`/call-depth-aware guard) that AA authors can use to detect/prevent same-unit reentrant manipulation of reserve-derived AMMs, since `number_of_responses` and `previous_aa_responses` are already exposed to oscript (as seen in `test/aa_composer.test.js` chain-of-AAs test) and could be leveraged for such guards.

### Proof of Concept
1. Deploy an AA modeled directly on ocore's shipped `uniswap_like_market_maker.oscript` sample, which prices `$asset`⇄`base` swaps from `$p = balance[$asset] * balance[base]` computed live within the trigger (lines 102-123, 124-145 of the sample).
2. Attacker unit U contains, in order:
   a. A large payment message swapping `base`→`$asset` (or vice versa) into the AMM AA, which the AMM AA processes using the "exchange" case, moving its live balances.
   b. A payment output from the AMM's response routed to a second attacker-controlled AA (a secondary trigger, chained atomically per `aa_composer.js:handleSecondaryTriggers`), which immediately reads the now-skewed reserves via `balance[...]`/`var[...]` and triggers a further favorable action (e.g., a follow-up "invest"/mint or a second swap back) before the first swap's price would naturally correct.
   c. Because steps (a) and (b) execute in the same unit under one `BEGIN…COMMIT` (`aa_composer.js:93-115`), and any bounce anywhere in the chain reverts the whole batch (`aa_composer.js:909-945`, `1671-1756`), the attacker can structure the chain so it only commits when net profitable, discarding it (at bounce-fee cost only) otherwise.
3. Result: the attacker extracts value from the AMM's reserves using a single, atomically-reverting unit — no external flash loan needed, since ocore's native secondary-trigger chaining plus balance-based pricing already provides the "borrow, manipulate, repay" primitive.
