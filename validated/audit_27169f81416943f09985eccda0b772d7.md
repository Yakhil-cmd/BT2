### Title
`CCMenuUrlController#client` mints an unscoped `ApiClient` (no `stack:` set), allowing its token to read any stack's CCMenu XML - ([File: app/controllers/shipit/ccmenu_url_controller.rb])

### Summary
`CCMenuUrlController#fetch` issues a `read:stack` API token via an `ApiClient` created without a `stack` association, so `stack_id` is `nil`. Because the authorization model treats `stack_id.nil?` as "no restriction" rather than "restricted to no stack," and `Api::CCMenuController` doesn't even apply that scoping, the resulting token can be replayed against `/api/1/stacks/:B/ccmenu.xml` for any stack `B` the attacker does not have access to.

### Finding Description
The intended binding is: `current_api_client.stack_id == A` (the stack for which the CCMenu URL was requested), so that the token is only valid for stack A's CCMenu feed. In `CCMenuUrlController#client`: [1](#0-0) 

the `ApiClient` is created via `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')` with no `stack:` attribute, so `stack_id` is persisted as `nil` for every user's very first CCMenu client (and reused thereafter via `find_or_create_by!` on `creator`+`name` only). `ApiClient` declares `belongs_to :stack, optional: true`, confirming `stack_id` is nullable by design: [2](#0-1) .

`Api::BaseController` encodes the authorization scoping rule that a `nil` `stack_id` means *unrestricted* access, not *no* access: [3](#0-2) 

`current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` — when `stack_id` is `nil`, `stacks` resolves to `Stack.all`. This convention exists for `UnlimitedApiClient`/admin-style tokens, but the CCMenu token generator accidentally produces the same "unlimited" shape.

Compounding this, `Api::CCMenuController` overrides `#stack` to bypass even that scoped `stacks` helper entirely: [4](#0-3) 

using `Stack.from_param!(params[:stack_id])` unscoped, so regardless of `stack_id` being set or not, any valid `read:stack` token authenticates against any `:stack_id` in the URL. `require_permission :read, :stack` only checks `permissions.include?('read:stack')` [5](#0-4)  — it never compares `current_api_client.stack_id` to the requested stack, so it does not catch the divergence.

Attack: an authenticated Shipit user with read access only to stack A visits `GET /stacks/:A/ccmenu_url`, receiving a URL containing `token=<ApiClient#authentication_token>` for their CCMenu client (`stack_id: nil`). They then use that same token against `GET /api/1/stacks/:B/ccmenu.xml?token=...` for any stack B, and `Api::CCMenuController` renders B's build/deploy XML successfully.

### Impact Explanation
The attacker obtains a valid `read:stack` bearer token and can use it to read build status, activity, last build label/time and web URL for any stack in the Shipit instance, not just the one they requested it for — this is cross-tenant/cross-repository disclosure of stack and deploy state. It matches the High-severity category of "unauthenticated/unauthorized read of stack state, task streams or deploy output" since the token was never actually authorized for stack B. The exposure is repeatable indefinitely (the token doesn't expire) and scales to every stack hosted on the instance.

### Likelihood Explanation
Preconditions are minimal: the attacker only needs an ordinary authenticated Shipit session and read access to any one stack (to trigger `/ccmenu_url`); `Shipit.api_clients_secret` can be any configured value since it's only used to sign/verify the token, not to restrict its scope. No GitHub secrets, webhook secrets, or elevated roles are required. The flow is fully deterministic and requires a single GET request plus reuse of the returned token — trivial and reliably reproducible.

### Recommendation
Set the `stack:` attribute when creating/finding the CCMenu `ApiClient` (e.g. scope `find_or_create_by!` on `creator`, `name`, and `stack`, and pass `stack: stack` into `create_with`), and fix `Api::CCMenuController#stack` to use the inherited scoped `stacks.from_param!` (or explicitly verify `current_api_client.stack_id == stack.id`) instead of calling `Stack.from_param!` directly.

### Proof of Concept
In `test/controllers/api/ccmenu_controller_test.rb` / a new combined test:
1. Log in as a user with read access only to `stack_a` (`shipit_stacks(:shipit)`), `GET :fetch, params: { stack_id: stack_a.to_param }` on `CCMenuUrlController`.
2. Assert `ApiClient.last.stack_id.nil?` is true (proving the binding `stack_id == stack_a.id` is broken).
3. Assert `ApiClient.authenticate(ApiClient.last.authentication_token).stack_id?` returns `false`.
4. Create `stack_b = Stack.create!(repository: Repository.new(owner: 'other', name: 'repo'), branch: 'main')` (unrelated to the user).
5. `GET :show, params: { stack_id: stack_b.to_param, token: ApiClient.last.authentication_token }` against `Api::CCMenuController`.
6. Assert `response.status == 200` and the XML payload's `name` equals `stack_b.to_param`, proving the token minted for stack A discloses stack B's build/deploy data.
