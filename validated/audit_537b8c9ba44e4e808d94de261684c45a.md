### Title
`handleKLAYTransfer` Push-Transfer to Unpayable `_to` Permanently Locks KAIA and Corrupts Bridge Nonce State — (File: `contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

---

### Summary

`BridgeTransferKLAY.handleKLAYTransfer` uses a push pattern to deliver KAIA to the recipient `_to`. If `_to` is a contract without a payable fallback, the push fails, the entire transaction reverts, and the nonce is never consumed. Because there is no skip/cancel mechanism, `lowerHandleNonce` is permanently stuck at that nonce, the KAIA for that request is permanently locked in the bridge, and the VT recovery system loops indefinitely.

---

### Finding Description

`handleKLAYTransfer` in `BridgeTransferKLAY.sol` performs all nonce-state updates first, then pushes KAIA to `_to`:

```solidity
_setHandledRequestTxHash(_requestTxHash);          // (1) mark tx hash handled
handleNoncesToBlockNums[_requestedNonce] = ...;    // (2) record block number
_updateHandleNonce(_requestedNonce);               // (3) advance lowerHandleNonce
emit HandleValueTransfer(...);                     // (4) emit event

(bool ok, ) = _to.call.value(_value)("");          // (5) push KAIA
require(ok, "handleKLAYTransfer: transfer failed");// (6) revert if push fails
``` [1](#0-0) 

Because step (6) reverts the entire transaction, all state changes from steps (1)–(4) are also reverted. The operators can retry, but every retry will fail identically because `_to` is still unpayable. There is no owner-callable skip, cancel, or nonce-override function anywhere in the contract hierarchy.

The `_to` address is fully attacker-controlled: any user can call `requestKLAYTransfer` and supply any address as `_to`, including a contract with no payable fallback. [2](#0-1) 

The `_updateHandleNonce` loop advances `lowerHandleNonce` only while `handleNoncesToBlockNums[i] > 0` for consecutive nonces starting at `lowerHandleNonce`:

```solidity
for (i = lowerHandleNonce; i <= limit && handleNoncesToBlockNums[i] > 0; i++) {
    recoveryBlockNumber = handleNoncesToBlockNums[i];
    delete handleNoncesToBlockNums[i];
    delete closedValueTransferVotes[i];
}
lowerHandleNonce = i;
``` [3](#0-2) 

Since nonce N is never successfully handled, `handleNoncesToBlockNums[N]` remains 0 forever. Every subsequent call to `_updateHandleNonce` (for nonces N+1, N+2, …) exits the loop immediately at `i = N`, leaving `lowerHandleNonce` permanently stuck at N.

---

### Impact Explanation

| Corrupted value | Effect |
|---|---|
| `lowerHandleNonce` stuck at N | Never advances; `recoveryBlockNumber` frozen at block of nonce N−1 |
| `handleNoncesToBlockNums[N]` never set | Loop in `_updateHandleNonce` always exits at N |
| `closedValueTransferVotes[N+1…]` never deleted | Unbounded storage growth |
| KAIA for nonce N | Permanently locked in destination bridge; user's KAIA on source chain also permanently locked |
| VT recovery system (`vt_recovery.go`) | Loops indefinitely re-attempting nonce N, consuming operator resources |

The KAIA locked in the destination bridge is a direct loss of bridged assets. The source-chain KAIA is also unrecoverable because the bridge contract has no refund path for failed destination transfers. [4](#0-3) 

---

### Likelihood Explanation

The trigger is fully unprivileged: any user can call `requestKLAYTransfer` (or the fallback) with `_to` set to any contract address. The cost to the attacker is only the KAIA sent in the request (which is also permanently locked, but the attacker may consider this acceptable for a griefing attack). The attack can be repeated for multiple nonces at low incremental cost.

---

### Recommendation

1. **Pull pattern**: Instead of pushing KAIA to `_to` inside `handleKLAYTransfer`, record the pending balance in a mapping and let `_to` withdraw it via a separate `claim()` function. This decouples nonce advancement from delivery success.
2. **Skip mechanism**: Add an owner-callable `skipHandleNonce(uint64 nonce)` that advances `lowerHandleNonce` past a permanently stuck nonce, allowing the bridge to continue operating even if one delivery is irrecoverable.
3. **Validate `_to` on request**: Reject requests where `_to` is a known non-payable address (though this is difficult to enforce on-chain for arbitrary contracts).

//    → require(ok) reverts entire tx
//    → all state changes reverted; closedValueTransferVotes[N] = false again
//
// 4. Operators retry indefinitely — same result every time.
//
// 5. lowerHandleNonce permanently stuck at N.
//    recoveryBlockNumber frozen at block of nonce N-1.
//    1 KAIA permanently locked in destination bridge.
//    VT recovery system loops forever re-attempting nonce N.
```

The `_lowerHandleNonceCheck` confirms nonces above N can still be handled (bridge not fully halted), but `lowerHandleNonce` never advances, `recoveryBlockNumber` never advances, and the locked KAIA is irrecoverable without a contract upgrade. [5](#0-4) [6](#0-5)
