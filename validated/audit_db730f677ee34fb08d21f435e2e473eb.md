### Title
Cross-Organization Webhook Forgery via Signature/Repository Field Mismatch - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to verify a webhook against based on `params.dig('repository', 'owner', 'login')` (or `organization.login`), but the downstream `Handler` classes resolve the *target* repository/stack using a completely different field, `payload.dig('repository', 'full_name')`. In a multi-organization Shipit deployment, an attacker who legitimately controls (and thus knows the `webhook_secret` of) one onboarded GitHub organization can forge a webhook whose `repository.owner.login` matches their own org (so it authenticates), while `repository.full_name` names a stack belonging to a *different* organization configured on the same Shipit instance.

### Finding Description
`WebhooksController#verify_signature` picks the `GitHubApp` (and its `webhook_secret`) via `repository_owner`: [1](#0-0) [2](#0-1) 

Shipit explicitly supports multiple independently configured GitHub Apps/organizations, each with its own `webhook_secret`, looked up via `Shipit.github(organization:)`: [3](#0-2) [4](#0-3) 

Once the signature check passes, the raw parsed JSON `params` (the *entire attacker-controlled body*, not just the verified sub-field) is dispatched unchanged to event handlers: [5](#0-4) 

Every handler (`PushHandler`, `StatusHandler` via `Commit.where(sha:)`, `CheckSuiteHandler`) resolves the acting stack(s) through `Handler#stacks`, which uses a *different* JSON field, `repository.full_name`, to look up the `Repository`: [6](#0-5) [7](#0-6) 

Because HMAC verification only proves "this byte sequence was signed by organization X's secret" — it does not constrain which *fields* inside that byte sequence the application is allowed to trust for authorization decisions — the application implicitly assumes `repository.owner.login == repository.full_name.split('/').first`. Nothing enforces this. The `StatusHandler` and `PushHandler` never check that the field used to select the signing secret matches the field used to select the target repository: [8](#0-7) [9](#0-8) 

The broken binding, expressed as an equality that the code assumes but never enforces:
`repository_owner (used to select webhook_secret for verification)` == `repository.full_name.owner (used to select the Stack/Repository actually mutated)`.

### Impact Explanation
Any party who legitimately owns/administers **one** GitHub organization onboarded to a shared multi-tenant Shipit instance (and therefore knows that organization's `webhook_secret`, which they themselves configured per `docs/setup.md`) can forge signed webhook deliveries whose `repository.full_name` names a stack under **any other** organization configured on the same instance. This lets the attacker:
- Forge `status` events (`state: success`) for arbitrary commit SHAs on a victim repository, which feed `Commit#create_status_from_github!` and influence `Stack#deployable?`'s `deployment_checks_passed?` gate used to decide whether a deploy can proceed: [10](#0-9) 
- Forge `push` events that trigger `GithubSyncJob`/`stack.sync_github` for a victim stack with an attacker-chosen `after` SHA.
- Forge `check_suite` events that mark check runs on a victim's commits.

Forging deployment-gate status for a repository the attacker does not control, without ever needing that repository's own secret, credentials, or write access, crosses the "unauthorized deploy" authorization boundary called out as an in-scope Critical/High impact.

### Likelihood Explanation
Requires a multi-tenant Shipit deployment with more than one GitHub organization configured (`docs/setup.md` explicitly documents and supports this), and the attacker must legitimately administer at least one such tenant. No privileged Shipit account, `ApiClient` token, or repository write access on the *victim* repository is required — only knowledge of a webhook secret the attacker is entitled to know for their own onboarded org, which is a normal, low-privilege capability in this multi-tenant configuration.

### Recommendation
In `Handler#repository_name` (and everywhere a stack/repository is resolved from webhook payload), derive the repository/organization strictly from the same value that was used and proven during `verify_signature` (e.g., pass the verified `repository_owner`/organization down to handlers and require `repository.full_name`'s owner segment to match it exactly), rejecting any webhook where these two fields diverge.

### Proof of Concept
1. Shipit is configured with two GitHub organizations, `attacker-org` and `victim-org`, each with its own `webhook_secret` (per `docs/setup.md:181-209`).
2. Attacker, who administers `attacker-org`'s GitHub App, knows `attacker-org`'s `webhook_secret`.
3. Attacker crafts a JSON body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "sha": "<victim commit sha>",
  "state": "success"
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org secret, body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` resolves `repository_owner` = `"attacker-org"` from the payload [2](#0-1) , loads `attacker-org`'s `GitHubApp`, and the signature verifies successfully since it was signed with that org's real secret.
6. `create` dispatches the full body to `Shipit::Webhooks.for_event('status')`, invoking `StatusHandler`, which looks up `Commit.where(sha: params.sha)` — a global, org-agnostic lookup — and creates a forged `success` status on a commit that in fact belongs to `victim-org/victim-repo`, influencing that stack's deployability without any credential belonging to `victim-org`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently.
