## Title
Missing dust-amount filter on non-base asset outputs sent to an AA enables a spam-dust attack that forces costly/oversized response payments, risking fund loss or freezing - (File: aa_composer.js)

### Summary
The Sherlock report describes a Solidity vault that has no minimum deposit/withdraw amount, allowing an attacker to flood the contract with dust transactions that later get replayed inside an unbounded `for` loop (`acceptWithdrawRequest`), wasting gas and corrupting bookkeeping. The equivalent weak point in `ocore` is the coin-selection logic used by Autonomous Agents (AAs) to fund their own outgoing payments: for the base asset a minimum-output filter exists explicitly to defeat dust spam, but the same filter is **not** applied to custom (non-base) assets, and the resulting payment message is exempt from the normal per-message input cap when it is generated by an AA.

### Finding Description
When an AA composes an outgoing payment in `aa_composer.js`, it selects unspent outputs to use as inputs via `readStableOutputs()` / `readUnstableOutputsSentByAAs()` and consumes them one by one in `iterateUnspentOutputs()`: [1](#0-0) 

The base-asset branch explicitly filters out any output smaller than `FULL_TRANSFER_INPUT_SIZE`, with a comment stating the exact purpose is to prevent a dust attack: [2](#0-1) 

However, when `asset` is set (i.e. any custom/non-base asset), the WHERE clause only filters `is_spent=0` and `sequence='good'` — there is **no minimum-amount condition at all** for custom assets: [3](#0-2) [4](#0-3) 

`iterateUnspentOutputs()` then greedily consumes every returned row until the target amount is reached, with no cap on the number of inputs it may add: [5](#0-4) 

Normally, `validatePaymentInputsAndOutputs()` rejects payment messages with more than `MAX_INPUTS_PER_PAYMENT_MESSAGE` (128) inputs — but this check is explicitly skipped for AA-generated messages: [6](#0-5) 

Any unprivileged unit poster can pay a custom asset to an AA address in tiny denominations (e.g. amount = 1) in ordinary `payment` messages, which are validated and accepted normally (`isPositiveInteger(output.amount)` only requires `> 0`): [7](#0-6) 

Because there is no per-asset dust floor and no input-count cap for AA responses, an attacker can pre-seed an AA's balance in a target asset with thousands of 1-unit outputs. The next time that AA needs to pay out that asset (in response to any trigger, including from legitimate users), `completePaymentPayload()` will pull in large numbers of these dust inputs to reach the required amount, producing an oversized unit (potentially approaching `MAX_UNIT_LENGTH = 5e6` bytes) and consuming disproportionate byte fees paid out of the AA's own balance.

### Impact Explanation
This falls in the accepted impact categories ("AA fund loss or freezing" / "network unable to confirm new units"):
- **AA fund loss**: the AA pays byte fees for consuming hundreds/thousands of tiny inputs it did not choose to accumulate, effectively draining its base-asset balance for fees while distributing negligible attacker-controlled value.
- **AA freezing**: if the number of dust inputs required to satisfy a response payment pushes the composed unit past `MAX_UNIT_LENGTH` (or otherwise makes the response unaffordable in fees), the AA's response bounces or repeatedly fails, and the legitimate asset balance the AA holds becomes unspendable/stuck, since every subsequent attempt re-selects the same dust set deterministically (`ORDER BY main_chain_index, unit, output_index`).

### Likelihood Explanation
Likelihood is high: sending many small-amount `payment` messages of a custom asset to a known AA address is a normal, unprivileged, and cheap action requiring no special permissions — the same operation legitimate users perform to fund AAs, just repeated with dust amounts. The lack of a floor mirrors exactly the missing-minimum-amount root cause identified in the original report, and the deterministic FIFO-style ordering guarantees the AA is forced to process the dust before any larger, useful outputs.

### Recommendation
Apply the same dust-prevention floor used for the base asset to custom assets in `readStableOutputs()` and `readUnstableOutputsSentByAAs()` (e.g., ignore asset outputs below a configurable minimum, or scale the minimum to the current AA-response byte-fee cost per additional input), and/or cap the number of inputs `iterateUnspentOutputs()`/`completePaymentPayload()` will accumulate for AA-generated payments regardless of the `!objValidationState.bAA` validation exemption, so a single response payment can't be forced to include an unbounded number of attacker-supplied dust inputs.

### Proof of Concept
1. Deploy/target an existing AA that holds or is expected to hold balance of a custom asset `X` and that responds to triggers by paying out asset `X` (e.g. `test/samples/order_book_exchange.oscript` "withdraw funds" case, which pays `trigger.data.asset` back to the caller).
2. As an unprivileged user, send several thousand separate `payment` messages of asset `X` to the AA's address with `amount: 1` each — all pass `validatePaymentInputsAndOutputs` since `isPositiveInteger(1)` is valid and no per-asset dust floor exists (`aa_composer.js:1149-1154,1167-1172`).
3. Trigger the AA's withdraw/payout logic for asset `X`. `completePaymentPayload()` calls `readStableOutputs`/`readUnstableOutputsSentByAAs` and `iterateUnspentOutputs` consumes the dust outputs one-by-one (`aa_composer.js:1102-1138`) without any per-message input cap, because `validation.js:2137` exempts AA-issued payments from `MAX_INPUTS_PER_PAYMENT_MESSAGE`.
4. Observe the AA either pays excessive byte fees to move the dust, or the composed response unit grows large enough that it can no longer be sent, leaving the AA's real asset balance stuck.
