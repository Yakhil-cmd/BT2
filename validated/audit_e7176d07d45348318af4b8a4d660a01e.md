### Title
`gh skill update` re-fetches skill content using an attacker-reclaimable `owner/repo` name as the sole trust anchor, allowing silent replacement of installed skill content - ([File: pkg/cmd/skills/update/update.go])

### Summary
The reported Fusion Swap bug is a class of "identifier reuse enables data substitution": a resource is addressed by a reusable identifier (maker + order_id), and once the original resource is destroyed, an attacker can recreate a resource at the exact same identifier with different (malicious) data, causing a program that trusts the identifier to unknowingly operate on attacker data. The closest reachable analog in `gh` is `gh skill update`, which re-resolves and re-downloads skill content strictly by the `(host, owner, repo)` string tuple recorded in the locally installed `SKILL.md` frontmatter, with no binding to an immutable identity for the repository.

### Finding Description
When a skill is installed, `gh` records provenance metadata (`github-repo`, `github-tree-sha`, `github-path`) in the installed `SKILL.md` frontmatter [1](#0-0) . `internal/skills/source.ParseMetadataRepo` parses this back into a plain `owner/repo` pair via `ghrepo.FromFullName`, with no repository ID, no pinned commit requirement by default, and no verification that the repository is the "same" entity that was originally installed from [2](#0-1) .

`gh skill update` then keys its per-repo work strictly by this `(host, owner, repo)` string tuple (`repoKey{host, owner, repo}`), calls `discovery.ResolveRef(...)` to fetch the latest ref/commit for that owner/repo, and diffs the resulting tree SHA against the locally stored `treeSHA` to decide whether to overwrite the installed skill in place [3](#0-2) .

GitHub allows repository names (and, after account deletion or rename, owner/organization names) to be reused by a different, unrelated account once the original is deleted or renamed. Because the update flow has no persistent, immutable anchor (such as a numeric repo ID) tying the locally installed skill to the specific repository it was originally fetched from, an attacker who successfully claims the same `owner/repo` string after the legitimate repository is deleted or renamed can publish a repository with the same skills path and a higher tree SHA. The next `gh skill update` run for any user who previously installed skills from that name will resolve to the attacker's repository, treat it as an "update" (since local `treeSHA` differs from the newly resolved one), and silently overwrite the local skill files with attacker content [4](#0-3) [5](#0-4) .

This mirrors the Fusion Swap root cause precisely: the identifier (`maker+order_id` there, `owner/repo` string here) is reusable, its reuse is not tracked or prevented by the trusting party (the escrow account, here the update flow), and the trusting party ends up operating on attacker-controlled data reached via the reused identifier instead of the originally-verified data.

### Impact Explanation
Skills installed by `gh skill install`/`update` are meant to be read (and in agent contexts, executed/interpreted) by AI coding agents (GitHub Copilot, Claude Code, Cursor, etc.) [6](#0-5) . A successful substitution lets a remote, unprivileged attacker (who merely needs to register a now-available `owner/repo` name on GitHub) plant arbitrary instructions/content that will be trusted and loaded by the victim's coding agent the next time `gh skill update` runs — without any prompt in the common `--all`/non-interactive flow, and with only a generic "Updated `<name>`" message shown to the user. This can lead to prompt injection against the agent, exfiltration guidance, or malicious code being surfaced to the agent as a "trusted, previously-verified" skill.

### Likelihood Explanation
Exploitation requires: (1) an existing user having previously installed a skill from `owner/repo`, and (2) the attacker being able to claim that exact `owner/repo` name on GitHub after the legitimate one becomes available (via repository deletion/rename or organization/user rename — a known, real-world GitHub namesquatting risk pattern). This is plausible but requires a name to become free, which is a meaningfully lower-likelihood precondition than the original Fusion Swap bug (where the attacker directly controls order creation/cancellation timing). It is not a MITM, local-attacker, or admin-only scenario — the attacker is a fully unprivileged remote party publishing content on GitHub, and the victim triggers the vulnerable path via a routine `gh skill update`.

### Recommendation
Bind installed-skill provenance to an immutable identifier rather than a mutable name string: store and verify the GitHub repository's immutable numeric ID (or node ID) alongside `github-repo` in the frontmatter metadata, and have `gh skill update` fetch/compare the current repository's ID against the stored one before treating any diff as a legitimate update. If the ID does not match (i.e., the name was reused by a different repository), refuse to auto-update and require explicit user confirmation with a clear warning that the source repository appears to have changed identity, analogous to the recommended fix for Fusion Swap (a persistent record preventing silent reuse of a reclaimed identifier).

### Proof of Concept
1. User runs `gh skill install alice/cool-skills some-skill`; `gh` records `github-repo: https://github.com/alice/cool-skills` and a `github-tree-sha` in the installed `SKILL.md` [1](#0-0) .
2. `alice` later deletes or renames the `cool-skills` repository (or the `alice` account itself is renamed/deleted and the name becomes available).
3. An attacker registers `alice/cool-skills` (or a repo of the same name under a newly claimed `alice` account) with a `skills/some-skill/SKILL.md` containing malicious content and a fresh tree SHA.
4. The victim later runs `gh skill update --all` (or confirms interactively); `updateRun` resolves `(github.com, alice, cool-skills)` to the attacker's repository via `discovery.ResolveRef`/`DiscoverSkills`, sees `remote.TreeSHA != s.treeSHA`, and calls `updateSkillInPlace`, overwriting the local skill with attacker content [7](#0-6) [5](#0-4) .
5. The victim's AI agent subsequently reads/executes the now-malicious `SKILL.md` as a trusted, previously-installed skill.

Note: I was unable to fully verify the exact non-interactive default behavior (`--all` auto-confirm without any prompt) beyond what's shown in the excerpt above and did not trace `updateSkillInPlace`'s full body (lines beyond 420) due to iteration limits; this may contain additional mitigations (e.g., a secondary owner/repo re-verification not visible in the reviewed excerpt) that should be checked before treating this as fully confirmed.

// ParseMetadataRepo extracts repository information from skill metadata.
func ParseMetadataRepo(meta map[string]interface{}) (ghrepo.Interface, bool, error) {
	if meta == nil {
		return nil, false, nil
	}

	repoValue, _ := meta["github-repo"].(string)
	if repoValue == "" {
		return nil, false, nil
	}

	repo, err := ParseRepoURL(repoValue)
	if err != nil {
		return nil, true, err
	}

	return repo, true, nil
}
