### Title
`CCMenuController#stack` bypasses `ApiClient` stack-scoping, allowing a stack-scoped token to read the CI status of any stack - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::BaseController` enforces that a stack-scoped `ApiClient` can only resolve stacks from the set the token is authorized for, but `CCMenuController` overrides `#stack` to resolve directly against the global `Stack` model, breaking that binding.

### Finding Description
`ApiClient` can be scoped to a single stack via `stack_id` [1](#0-0)  and `Shipit::Api::BaseController` enforces this scoping when resolving `stack` for API endpoints: `stacks` is restricted to `Stack.where(id: current_api_client.stack_id)` when the client has a `stack_id`, and `stack` is resolved from that restricted set via `stacks.from_param!` [2](#0-1) . `require_permission :read, :stack` only checks that the client's `permissions` list contains `read:stack` — it does not check which specific stack is being accessed [3](#0-2) .

`CCMenuController` overrides `#stack` to bypass the scoped `stacks` helper entirely, resolving the stack directly from the unscoped `Stack` model using the client-supplied `params[:stack_id]`: [4](#0-3) 

Because `require_permission :read, :stack` (declared at the top of the controller) is a blanket permission check with no stack-scoping, and the overridden `#stack` method never consults `current_api_client.stack_id`, a token that is supposed to be authorized only for one stack (e.g. the `here_come_the_walrus` fixture, scoped to `stack: shipit` with only `read:stack` permission [5](#0-4) ) can be used to fetch `show` for **any** `stack_id` in the system, not just the one it was issued for.

This is exactly the "stack a token authorises versus a stack it touches" binding: `current_api_client.stack_id == params[:stack_id]` is checked in the base controller's scoped `#stack`, but that check is silently dropped in `CCMenuController`.

### Impact Explanation
An attacker holding a stack-scoped `ApiClient` token (issued for read-only CI-status polling of one stack, e.g. embedded in a CCMenu/CI-status-widget URL, which is inherently more exposed than a general API token since it is designed to be placed in third-party CI dashboard tools and passed via query string) can supply an arbitrary `stack_id` param to read deploy/build status (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`, activity) for any other stack in the Shipit instance, including stacks belonging to different repositories/teams that the token was never meant to see. This matches the in-scope High-severity impact: "unauthenticated read of stack state, task streams or deploy output" via escalation past the token's authorized stack scope.

### Likelihood Explanation
Exploitation only requires possessing a valid, narrowly-scoped `ApiClient` token with `read:stack` permission (the minimal, "read-only, single-stack" token type that Shipit explicitly supports and that this rule set treats as within the unprivileged-attacker's reach for this class of finding) and knowledge/guessing of another stack's `to_param` (owner/repo/env/branch, which is generally discoverable/enumerable). No signature forgery, no privileged account, and no additional credential is needed beyond the low-privilege token itself — the vulnerability is a straightforward authorization-scope bypass in a single controller method.

### Recommendation
Make `CCMenuController#stack` route through the same scoped resolution used elsewhere, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
reusing `BaseController#stacks`, so that a client's `stack_id` restriction is honored consistently across all API controllers, including `CCMenuController`.

### Proof of Concept
1. Create (or obtain) an `ApiClient` scoped to `stack_id` = Stack A with permission `read:stack` only (mirrors the `here_come_the_walrus` fixture).
2. Using that client's `authentication_token`, call `GET /api/stacks/:stack_id_of_other_stack_B/ccmenu.xml?token=<token>` (per `authenticate_api_client` override accepting `params[:token]` [6](#0-5) ).
3. Because `#stack` resolves `Stack.from_param!(params[:stack_id])` against the full `Stack` table rather than the client's restricted `stacks` scope [7](#0-6) , and `require_permission :read, :stack` only checks the flat permission list, the request succeeds and returns Stack B's build/deploy status, even though the token is only authorized for Stack A.
