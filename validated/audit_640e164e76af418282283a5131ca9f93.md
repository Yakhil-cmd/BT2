This confirms the vulnerability. The multi-tenant configuration (`Shipit.github_app_config`) supports distinct `webhook_secret` per organization, and `WebhooksController#verify_signature` selects which secret to verify against based solely on `params.dig('repository', 'owner', 'login')`, while every event handler (`Handler#repository_name`, used by `PushHandler`, `StatusHandler` via `Commit.where(sha:)`, `CheckSuiteHandler`, and the `PullRequest::*Handler` classes) resolves the target `Stack`/`Repository`/`Commit` from the entirely separate `repository.full_name` field of the same attacker-supplied JSON body.

### Title
Webhook signature verification keys off `repository.owner.login` while all handlers act on the unrelated `repository.full_name`, allowing cross-organization forged events - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp`/`webhook_secret` to validate a webhook's `X-Hub-Signature` using `repository_owner`, computed from `params.dig('repository', 'owner', 'login')`. Once the signature is accepted, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the *entire, attacker-controlled* JSON body to handlers. Every handler (`Shipit::Webhooks::Handlers::Handler#repository_name`, and duplicated logic in the `PullRequest::*` handlers) resolves the `Repository`/`Stack`/`Commit` to mutate from `payload.dig('repository', 'full_name')` — a field that is never checked against `repository_owner` and is never covered by the signing key selection logic.

### Finding Description
Shipit supports installing multiple GitHub Apps, one per organization, each with its own `webhook_secret` (`config/secrets.development.example.yml`, `lib/shipit.rb#github_app_config`). Any org administrator who installs Shipit's GitHub App on their own organization configures (and therefore knows) that org's `webhook_secret`. [1](#0-0) [2](#0-1) 

Signature verification only binds the request to `repository_owner`:

```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization: repository_owner)` then looks up that organization's app config and verifies the HMAC over the raw body with `github_app.verify_webhook_signature`, using that organization's secret. [3](#0-2) 

Every handler, however, ignores `repository_owner` entirely and instead resolves the record to act on using a sibling field, `repository.full_name`: [4](#0-3) [5](#0-4) 

Since the JSON body is a single blob signed as a whole, but only one field of it (`repository.owner.login`) determines *which secret verifies the signature*, while a different field (`repository.full_name`) determines *which repository/stack is written to*, an attacker who administers organization `attacker-org` (with Shipit's GitHub App installed and its own known `webhook_secret`, a normal, unprivileged, self-service action) can craft a payload:

```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "ref": "refs/heads/main",
  "after": "<arbitrary sha>"
}
```

They compute a valid `X-Hub-Signature` themselves using `attacker-org`'s own webhook secret (no need to go through GitHub at all — it's a raw POST to Shipit's `/webhooks` endpoint) and POST it directly. `verify_signature` looks up `Shipit.github(organization: 'attacker-org')`, verifies successfully against `attacker-org`'s own secret, and the request is accepted. `PushHandler#process` then resolves `stacks` via `Repository.from_github_repo_name('victim-org/victim-repo')`, entirely unrelated to `attacker-org`, and calls `stack.sync_github(expected_head_sha: ...)` on the victim's stack.

The same decoupling affects `StatusHandler` (creates a `Status` for any `Commit` matching `params.sha`, regardless of repository, which feeds `ci.require` gating before deploys), `CheckSuiteHandler`, and the `PullRequest::OpenedHandler` / `ClosedHandler` / `ReopenedHandler` / `Labeled`/`UnlabeledHandler` (provision, archive, or unarchive review stacks for any repository named in `repository.full_name`) — none of which validate that the resolved repository's owning organization matches `repository_owner`, the organization whose secret produced the valid signature.

If a configured organization has no `webhook_secret` at all (shown as `# nil` in `config/secrets.development.example.yml`), `verify_webhook_signature` returns `true` unconditionally for a signature check on that org, making the forgery trivial with no secret knowledge required — an attacker just needs `repository.owner.login` to equal any org name that has no configured secret. [6](#0-5) 

### Impact Explanation
This breaks the binding: `organization authenticated (repository_owner used for signature verification) == organization whose repository is written (repository.full_name used by handlers)`. An unprivileged actor who merely installs/configures Shipit's GitHub App on their own org can:
- Forge `push` events to trigger `GithubSyncJob`/`sync_github` on any other tenant's `Stack` (`PushHandler`).
- Forge `status` events to create arbitrary CI `Status` records (success/failure/description/target_url) on any `Commit` across any repository (`StatusHandler`), which can bypass `ci.require` checks gating deploys elsewhere in the app, contributing to an unauthorized deploy.
- Forge `pull_request` events to provision, archive, or unarchive review stacks belonging to repositories they don't own.

This qualifies as High: escalation of authorization boundaries across tenants/repositories via a spoofed webhook, and it materially assists an unauthorized deploy path by forging commit CI status for a repository the attacker does not control.

### Likelihood Explanation
Any entity able to install Shipit's GitHub App on a GitHub organization they control (a normal, self-service configuration step, not a privileged Shipit credential) can immediately exploit this without any further access. The only "secret" needed is one they configured themselves; in installations where a webhook secret is left blank for some org, no secret is needed at all.

### Recommendation
Bind the record resolved by handlers to the same organization used for signature verification. Concretely, `Shipit::Webhooks::Handlers::Handler#stacks`/`#repository_name` (and each duplicated `repository` method in the `PullRequest::*Handler` classes) should verify that the resolved `Repository`'s owner matches `repository_owner`/the verified organization from the controller (e.g., pass the verified organization into `handler.call` and reject/ignore records whose owner does not match), rather than trusting `repository.full_name` in isolation.

### Proof of Concept
1. Configure Shipit with two orgs, `attacker-org` (webhook_secret known to attacker) and `victim-org` (hosts `Stack` for `victim-org/victim-repo`).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": {"owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo"},
  "ref": "refs/heads/main",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef"
}
```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(attacker-org's webhook_secret, raw_body)>` and send it.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")` and verifies successfully using `attacker-org`'s secret.
5. `PushHandler#process` resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and enqueues `GithubSyncJob` against `victim-org`'s `Stack`, even though the signing organization was `attacker-org`. [7](#0-6)
