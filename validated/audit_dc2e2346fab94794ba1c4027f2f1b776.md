### Title
Review-target confusion via attacker-controlled post-commit hook stdout bypasses commit security review - ([File: plugins/security-guidance/hooks/security_reminder_hook.py])

### Summary
`handle_commit_review_posttooluse` selects the SHA to review by taking the *last* regex match of `_COMMIT_SHA_RE` anywhere in the concatenated Bash stdout+stderr, while the corroborating diffstat check (`_COMMIT_DIFFSTAT_PATTERNS`) is applied to the whole buffer rather than being bound to that specific match. A malicious repo-shipped hook (e.g. a `core.hooksPath`-based husky/lint-staged `post-commit` script, which is tracked in-repo and runs automatically after `git commit`) can print a decoy `[label <sha>]`-shaped line pointing to an arbitrary, attacker-chosen but *valid* object in the same repository (e.g. an old benign commit) after git's own real `[branch <real-sha>] subject` line. Because that fabricated line becomes the last match, and the genuine diffstat text from git's own commit summary is still present earlier in the buffer, `commit_succeeded` is true and `git show -p <attacker-chosen-sha>` is executed instead of the real, just-made commit — so the actually malicious diff is never sent to the LLM reviewer.

The code comment explicitly acknowledges the "last match wins" heuristic exists to skip *pre*-commit/husky decoy lines that appear *before* git's real summary line, but it does not account for hook output that runs *after* git prints the real summary — e.g. a `post-commit` hook. Git hooks configured via `core.hooksPath` (the mechanism husky/lint-staged use) can be tracked inside the repository itself, so cloning a malicious repo and running `git commit` executes attacker-authored hook code automatically as part of the normal commit flow — no privilege escalation or social engineering required, matching the stated threat model ("attacker controls commit message/hook stdout text ... via a repo's own pre-commit hook script").

Because `_COMMIT_DIFFSTAT_PATTERNS` is checked against the *entire* `bash_output` rather than being anchored to the same line/section as the chosen SHA, git's own genuine "`N files changed`" diffstat (emitted for the real commit) satisfies the corroboration requirement even though the SHA ultimately used comes from an unrelated, forged bracket appended afterward by the hook. There is no subsequent check that the resolved SHA equals `git rev-parse HEAD` in `repo_root` for the non-amend path (unlike `_resolve_amend_pre_sha`, which does perform such a HEAD-prefix binding check for the amend-delta path): [4](#0-3) 

`git show -p <sha>` then succeeds against the attacker-chosen (but valid) object and its diff is what gets sent to `analyze_code_security`/`agentic_review`, completely bypassing review of the actual new commit's contents: [5](#0-4) 

### Impact Explanation
This is a review-target confusion / security-control bypass: the intended commit-review guardrail (meant to catch vulnerabilities introduced in a commit before the agent proceeds) is silently pointed at an unrelated, attacker-chosen commit. The actually malicious code introduced by the real commit is never analyzed, and the hook still reports success/no-findings, giving false assurance. This matches the "trust-boundary bypass in review/export logic" impact category — a security review meant to gate on real committed content can be defeated by data the attacker fully controls (repo-tracked hook output).

### Likelihood Explanation
Preconditions: the attacker needs to control repository content only (a repo-tracked hooks directory referenced by `core.hooksPath`, as husky/lint-staged commonly configure via `npm install`/`prepare` scripts), and the victim needs to run `git commit` inside that repo with Claude Code's security-guidance plugin active. No elevated privileges, leaked credentials, or social engineering beyond "clone and use this repo" are required, and the attack is fully repeatable on every commit made in the repository.

### Recommendation
Bind the reviewed SHA to the commit actually produced by requiring it to match (or be verified equal to, via `git rev-parse HEAD`/`git cat-file`) `repo_root`'s current HEAD (or the specific `HEAD@{0}` reflog entry as already done in `_resolve_amend_pre_sha`), rather than trusting the last bracketed token in free-form stdout. At minimum, restrict SHA extraction to the diffstat's immediately-adjacent context (same block as the matched "`files changed`"/"`create mode`" lines) instead of scanning across the full concatenated buffer, and/or ignore any hook output after the genuine `[branch sha]` line by locating that line via `git`'s own well-known summary format prefix before applying `_COMMIT_SHA_RE.findall`.

### Proof of Concept
Unit test in `security_reminder_hook.py`'s test suite:
1. Create a temp git repo, make one benign commit `C0` (capture its SHA).
2. Simulate a malicious repo by crafting `bash_output` as:
   ```
   [main <realSHA>] real commit message
    1 file changed, 1 insertion(+)
   [decoy C0[:7]]
   ```
   where `<realSHA>` is the actual new commit just made and the last line mimics forged post-commit hook stdout pointing at `C0`.
3. Call `handle_commit_review_posttooluse` (or directly exercise `_COMMIT_SHA_RE.findall(bash_output)[-1]` + the `commit_succeeded` predicate) and assert that the resolved SHA equals `subprocess.run(["git","rev-parse","HEAD"], cwd=repo).stdout.strip()`.
4. Expected (current, failing) behavior: the extracted SHA equals `C0` instead of HEAD, and `git show -p C0` is executed — demonstrating the review-target confusion. A fuzz variant should feed random bracketed decoy strings appended after a real commit summary and assert the invariant `extracted_sha == git_rev_parse_head` always holds; it currently does not.
