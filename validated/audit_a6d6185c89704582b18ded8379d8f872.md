### Title
Cross-repository commit-status forgery via unscoped `StatusHandler` webhook processing - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates an incoming GitHub webhook against the secret of the organization named *inside the payload itself* (`repository.owner.login`), but the `status` event handler then acts on *any* commit across the entire Shipit installation that matches the submitted `sha`, without checking that the commit actually belongs to a stack/repository owned by that authenticated organization. This breaks the binding "organization authenticated == repository written."

### Finding Description
`WebhooksController#verify_signature` picks the `GithubApp` (and thus the HMAC secret) to verify against using `repository_owner`, which is read straight out of the untrusted payload: [1](#0-0) [2](#0-1) 

This only proves the request was signed by *some* organization registered in `Shipit.github`, not that the payload's claims are limited to that organization's own repositories/stacks.

Every other event handler scopes its side effects through `Repository.from_github_repo_name(repository_name)` before touching any stack, e.g. `Handler#stacks`: [3](#0-2) 
used by `PushHandler`: [4](#0-3) 
and by `CheckSuiteHandler`: [5](#0-4) 

`StatusHandler`, however, never calls `stacks` / `Repository.from_github_repo_name` at all — it resolves the target purely by SHA, globally: [6](#0-5) 

Because `Commit.where(sha: params.sha)` is not scoped to the repository named in the payload, and the signature check is only bound to *which organization* sent the request (not *which repository's commits* that organization is allowed to affect), an org that legitimately owns one Shipit-tracked repository can forge a signed `status` webhook whose `repository` object names its own org (so signature verification passes), but whose `sha` matches a commit belonging to a completely different, unrelated stack/repository (potentially owned by a different organization in the same multi-tenant Shipit install, as the shipped config explicitly supports multiple `github:` org entries, each with an independent `webhook_secret`): [7](#0-6) 

### Impact Explanation
`Commit#create_status_from_github!` writes CI status (state/description/target_url/context) onto the matched commit. Commit status/check state is used by Shipit to gate whether a commit is deployable/mergeable. An attacker who controls (or compromises) any one organization/repository configured in the same Shipit instance can forge a "success" status on a commit belonging to a different repository/stack they do not control, without ever needing a Shipit session, an `ApiClient` token, or write access to the target repository. This is a cross-repository write and can enable an unauthorized deploy of another organization's stack — meeting the Critical impact bar.

### Likelihood Explanation
Requires the attacker to control (or have compromised the webhook secret of) at least one organization/GitHub App installation registered in the shared Shipit instance — a realistic scenario in any multi-org Shipit deployment (explicitly supported and documented via `config/secrets.*.yml` multiple `github:` entries). Target commit SHAs are not secret (visible via normal GitHub history/API), so no brute-forcing or collision is required — the attacker just needs to know a target commit's SHA in the victim repository.

### Recommendation
In `StatusHandler#process`, scope the commit lookup through the repository named in the verified payload, mirroring `PushHandler`/`CheckSuiteHandler`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }
  end
end
```
i.e., always resolve `Commit` via `Repository.from_github_repo_name(repository_name)`/`stacks`, never via a global, repository-unscoped `Commit.where(sha:)`.

### Proof of Concept
1. Attacker's organization `attacker-org` is registered in the shared Shipit deployment (its own `github.attacker-org.webhook_secret` is known to the attacker, as they administer that GitHub App).
2. Attacker learns a target commit SHA `deadbeef...` belonging to `victim-org/victim-repo`, tracked by a different stack in the same Shipit instance (SHAs are public).
3. Attacker crafts a `status` event JSON body:
```json
{
  "sha": "deadbeef...",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org_webhook_secret, body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `WebhooksController#verify_signature` resolves `repository_owner` to `attacker-org`, fetches `attacker-org`'s `GithubApp`, and the HMAC verifies successfully (lines cited above).
6. `StatusHandler#process` runs `Commit.where(sha: "deadbeef...")` — unscoped to `attacker-org` — finds the victim's commit in `victim-org/victim-repo`'s stack, and calls `create_status_from_github!`, writing a forged `success` status onto it, without the attacker ever having access to `victim-org`.
