### Title
Webhook signature verification key is selected from a different field than the repository the handler actually writes, allowing cross-tenant forged commit statuses - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` picks the HMAC secret to validate a webhook against the **organization login** taken from the payload, while the event `Handler` classes (`push`, `check_suite`, `status`) look up the target `Repository`/`Commit` using an entirely different, unchecked payload field (`repository.full_name`, or nothing at all for `status`). The two values are never compared, so a webhook that is *correctly* signed for org A can be crafted to act on org B's data. This is the same class of bug as the reported `pairFor`/`SinkConverter` issue: the value the system authenticates against (the sink/organization side) is not the value it operates on (the pair/repository side), and the two are silently allowed to diverge.

### Finding Description
`WebhooksController#verify_signature` derives the verification key from: [1](#0-0) [2](#0-1) 

`repository_owner` falls back to `params.dig('organization', 'login')` when `repository` is absent, and `Shipit.github(organization: repository_owner)` selects that org's configured `webhook_secret` to verify the HMAC. This means the signature only proves "this request was signed with org X's secret" — it proves nothing about which repository the payload's other fields describe.

Once verification passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the raw, attacker-supplied JSON to handlers such as `PushHandler`, `CheckSuiteHandler`, and `StatusHandler`. These derive the target repository from a completely independent field: [3](#0-2) 

`repository_name` reads `payload.dig('repository', 'full_name')` — a value never checked against `repository_owner`/`organization.login` used for signing. Worse, `StatusHandler` doesn't even consult `stacks`/`repository_name` at all: [4](#0-3) 

It looks up `Commit.where(sha: params.sha)` globally across the entire Shipit instance and calls `commit.create_status_from_github!(params)`, which sets `state`, `description`, `target_url`, and `context` on the matching commit — irrespective of which org/repo actually owns that commit.

The broken equality is: `verified_org (organization.login used to pick webhook_secret) == written_repository_owner (repository.full_name owner acted upon by the handler)`. Nothing in `WebhooksController` or `Handlers::Handler` enforces this.

### Impact Explanation
Any tenant/org onboarded into a multi-org Shipit deployment (i.e., one that legitimately knows its own org's `webhook_secret`, because that value must be supplied when configuring the webhook delivery on the GitHub side) can sign an arbitrary JSON body with its own secret and set the `repository`/`sha` fields to point at a **different** organization's stack or commit. For the `status` event this lets the attacker forge a passing (`state: success`) CI status on any commit sha in the system, including commits belonging to a victim stack that gates continuous deployment on required CI statuses (`Commit#deployable?` / `required_statuses`). That can cause an unauthorized deploy to proceed on a victim's stack, matching the "unauthorized deploy" Critical-impact category.

### Likelihood Explanation
Exploitation only requires POSTing to the public `/webhooks` (or engine-mounted) endpoint with a body signed using a webhook secret the attacker legitimately possesses for their own organization — no session, `ApiClient` token, or GitHub credentials for the victim are required. This is a normal capability of any org that has been given a Shipit webhook integration, making the likelihood high in any environment where more than one organization is configured.

### Recommendation
Enforce the same identity on both sides of the check:
- In `WebhooksController`/`Shipit::Webhooks`, after signature verification, re-derive the repository owner strictly from `params.dig('repository','owner','login')` and reject the event if it disagrees with `repository_owner` used to select the verifying secret.
- In `Handlers::Handler`, when resolving `stacks`/commits, cross-check that the resolved `Repository`'s owner matches the organization whose secret verified the request, and reject cross-org events (`StatusHandler` in particular must not do an unscoped global `Commit.where(sha:)` lookup without validating that the payload's repository belongs to that commit's stack).

### Proof of Concept
1. Attacker administers GitHub org `evil-org`, which is legitimately configured in Shipit with its own `webhook_secret` (`S_evil`), because that secret must be supplied when the org's admin configures GitHub's webhook delivery settings.
2. Attacker crafts a `status` event payload:
```json
{
  "organization": { "login": "evil-org" },
  "repository": { "full_name": "evil-org/evil-repo" },
  "sha": "<sha of a commit belonging to victim-org/victim-repo>",
  "state": "success",
  "context": "ci/required-check"
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(S_evil, raw_body)>` and POSTs to the webhooks endpoint with `X-Github-Event: status`.
4. `verify_signature` resolves `repository_owner` to `"evil-org"` (from `organization.login`, since a full `repository` object isn't needed for that fallback logic [2](#0-1) ), fetches `evil-org`'s `webhook_secret`, and the signature validates successfully because it was in fact signed with that secret.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — which matches the victim's commit regardless of repository — and calls `create_status_from_github!`, forging a passing CI status on a commit in `victim-org/victim-repo`'s stack [4](#0-3) .
6. If `victim-org/victim-repo`'s stack has continuous deployment enabled gated on that CI context, this forged status can trigger an unauthorized deploy.
