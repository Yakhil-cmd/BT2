### Title
Unauthenticated `throw Error` inside async DB callback in payment input validation crashes the node - ([File: validation.js])

### Summary
`validatePaymentInputsAndOutputs()` in `validation.js` contains multiple hard `throw Error(...)` invariant checks that execute inside asynchronous `conn.query` callbacks while processing a `transfer` payment input of an ordinary (base or non-fixed-denomination) unit. An unprivileged unit poster can craft a payment message whose `input.unit` references a stable output whose `sequence` is `'temp-bad'`, which trips `throw Error("spending a stable temp-bad output " + input.unit)` [1](#0-0) , or trigger the sibling `throw Error("more than 1 src output")` check on the same query result set [2](#0-1) . This is the same bug class as the TensorFlow `CTCGreedyDecoder` `CHECK_LT` report: an invariant that "should never happen" is enforced with a hard abort instead of a graceful, catchable error path.

### Finding Description
`validate()` in `validation.js` runs unit validation for every newly received/posted joint and dispatches to `validateMessages` → `validatePayment` → `validatePaymentInputsAndOutputs` [3](#0-2) . Inside the `transfer` input case, the code queries the database for the source output of the referenced input and then checks `src_output.sequence`:

```
conn.query(... "WHERE units.unit=?", [...], function(rows){
    if (rows.length > 1)
        throw Error("more than 1 src output");
    ...
    if (bStableInParents) {
        if (src_output.sequence === 'temp-bad')
            throw Error("spending a stable temp-bad output " + input.unit);
``` [4](#0-3) 

Because this `throw` happens inside the callback of `conn.query`, it is not synchronously wrapped by the calling function's `try/catch` (the top-level `try` in `validate()` only wraps the initial `objectHash.getUnitHash` check and is already out of scope by this point) [5](#0-4) . An exception thrown asynchronously like this becomes an uncaught exception on the Node.js event loop. Unlike the many `callback("some error string")` patterns used throughout the same function for ordinary invalid input (which safely propagate the error back to `ifUnitError`) [6](#0-5) , these specific checks use `throw`, meaning they were written as "should never happen" invariants — precisely the `CHECK_LT`-style pattern from the CVE. The rest of `validate()`'s error-handling machinery (`ifUnitError`, `ifJointError`, `ifTransientError`) is unreachable once the callback throws, because the throw escapes the `async.series`/callback chain entirely.

There are several similar hard-throw invariants reachable from attacker-supplied unit content in the same function and nearby validation helpers, e.g. `throw Error("no src_coin")`, `throw Error("no src_output")`, `throw Error("no denomination in src coin")`, `throw Error("no src coin amount")` for private fixed-denomination transfers [7](#0-6) , and `throw Error("more than one record per denomination?")` in `validateIndivisibleIssue` [8](#0-7) . The `sequence === 'temp-bad'` case is the most directly attacker-triggerable: `temp-bad` is a normal, database-recorded state assigned to units that fail non-serial validation, so any node that has ever seen a conflicting/non-serial unit will have such rows, and a subsequent unit spending that stable output as a `transfer` input reaches the `throw` deterministically.

### Impact Explanation
An unhandled synchronous throw inside a database callback is not caught by Node's normal control flow and results in an uncaught exception that terminates the ocore process (a network node, hub, or wallet backend) unless an external supervisor restarts it. Any node processing a maliciously crafted but well-formed unit (referencing a stable `temp-bad` output as a transfer input) can be crashed remotely by an unprivileged unit poster — this matches the "network unable to confirm new units" / node-crash impact class accepted by the validation rules, analogous to the TensorFlow `CHECK`-fail DoS.

### Likelihood Explanation
Triggering the `temp-bad` condition requires the target node to already have committed such an output to its `units`/`outputs` tables, which happens naturally whenever conflicting non-serial units are processed (a routine, permissionless occurrence in this DAG-based ledger). Constructing a unit whose payment input references that unit/message_index/output_index as a `transfer` input requires no special privileges — any address holder posting a new unit can shape `payload.inputs` freely; only the address-authorship and standard structural checks that precede this code path need to be satisfied, all of which are achievable by a normal unprivileged actor.

### Recommendation
Replace the `throw Error(...)` invariant checks inside `validatePaymentInputsAndOutputs` (and the related `validateIndivisibleIssue` helper) with the standard callback-based error propagation used elsewhere in this function, i.e. `return cb("spending a stable temp-bad output " + input.unit)` / `return cb("more than 1 src output")`, so that these conditions surface as ordinary `ifUnitError` results instead of aborting the process. Audit all other `throw Error(...)` statements inside asynchronous DB callbacks reachable from attacker-controlled unit content in `validation.js` and convert them to the callback-error pattern as well.

### Proof of Concept
1. Post/propagate a unit `A` whose payment causes some output `O` (unit `U`, message_index `M`, output_index `I`) to be recorded with `sequence='temp-bad'` and later become stable (main_chain_index ≤ some future last_ball_mci) — a routine occurrence from a normal double-spend/non-serial conflict.
2. Craft and post a new unit `B` containing a payment message with `inputs: [{ type: "transfer" (implicit), unit: U, message_index: M, output_index: I }]`, otherwise structurally valid (correct author, signature, parents, last_ball referencing an MCI at or after `O` becomes stable).
3. When any node validates `B`, `validatePaymentInputsAndOutputs` queries the source output for `U`/`M`/`I`, finds `bStableInParents === true` and `sequence === 'temp-bad'`, and executes `throw Error("spending a stable temp-bad output " + input.unit)` inside the `conn.query` callback [1](#0-0) , crashing the validating node process with an uncaught exception.
