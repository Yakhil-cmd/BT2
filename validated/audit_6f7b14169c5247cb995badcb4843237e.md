### Title
Webhook organization/signature binding is decoupled from the repository actually mutated, allowing cross-tenant commit-status forgery and CI-gate bypass - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate an incoming webhook against using an attacker-controlled field from the *unverified* JSON body (`repository.owner.login` / `organization.login`), and `GitHubApp#verify_webhook_signature` trivially returns `true` whenever that organization has no `webhook_secret` configured. Once "verified", the full raw payload is handed to event handlers unchanged, and at least one handler (`StatusHandler`) resolves the object it mutates (`Commit`) purely by an attacker-supplied `sha`, with no scoping to the organization/repository that was used for the authentication decision. This breaks the equality **organization authenticated == repository/commit written**, letting an attacker impersonate the identity used for signature selection while writing state that belongs to a different, unrelated stack/repository hosted on the same Shipit instance.

### Finding Description
`WebhooksController#verify_signature` computes the verifying organization from the payload before any cryptographic check occurs: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` looks up that organization's configured secret and — critically — bypasses HMAC verification entirely if no secret is configured for it: [3](#0-2) 

Leaving `webhook_secret` unset per-organization is a documented, supported configuration in multi-app setups (`github.<org>.webhook_secret` is optional), as shown in the setup docs and the dummy multi-org fixture where both orgs ship with `webhook_secret: # nil`: [4](#0-3) [5](#0-4) 

After this "verification" step, the controller dispatches the entire raw payload to handlers with no further binding of the authenticated organization to what is mutated: [6](#0-5) 

Most handlers scope themselves to the correct repository via `Handler#stacks`/`#repository_name`, which is derived from the same `repository.full_name` field: [7](#0-6) 

However `StatusHandler` does not use this scoping at all — it resolves the target `Commit` purely by the attacker-supplied `sha`, globally across every stack/repository tracked by the entire Shipit instance: [8](#0-7) 

Combining these facts: an attacker can send a forged `status` webhook whose `repository.owner.login`/`organization.login` names any organization configured in this Shipit instance that has no `webhook_secret` set (a valid, documented configuration). `verify_webhook_signature` returns `true` unconditionally for that organization, so the request passes authentication with **no secret, no signature, and no prior access** at all. The attacker then puts an arbitrary `sha` value in the payload — one that belongs to a commit tracked under a *different*, properly-secured organization's stack — and `StatusHandler` will happily create/update a GitHub-style commit status (e.g., `state: success`) on that unrelated commit, because the lookup is entirely unscoped by organization or repository.

### Impact Explanation
This is a genuine cross-tenant write that crosses a trust boundary the webhook signature is supposed to enforce: the organization whose identity was used to pass authentication is not the organization whose data is mutated. The concrete consequence is forging a CI/status check (e.g. marking a commit `success`) on a commit belonging to a repository/stack the attacker has no access to. Because commit deployability gating in Shipit is built on these recorded commit statuses, an attacker can flip a victim commit from "not deployable" to "deployable" without any GitHub write access to the victim repository, undermining the CI-gate safety check that legitimate deploy triggers rely on. This aligns with the "escalation into authorization / unauthorized deploy" impact class: it doesn't grant RCE directly, but it removes a safety control gating what commits are eligible to ship, in a completely different tenant's stack, while requiring zero credentials from the attacker.

### Likelihood Explanation
Likelihood is high in any Shipit deployment supporting multiple GitHub organizations (the documented multi-app `secrets.yml` format), where at least one configured organization has not set a `webhook_secret` — which is explicitly supported and shown as a valid state in the shipped test fixtures/docs. An attacker only needs to know (or guess) that organization's login name; no secret, token, or session is required, since `verify_webhook_signature` short-circuits to `true` for that org. The commit `sha` values needed are typically public git commit hashes and easy to discover from GitHub itself.

### Recommendation
- Scope every webhook handler's data lookups (especially `StatusHandler`'s `Commit.where(sha:)`) to the repository identified by the same `repository.full_name`/organization that was used for signature verification, not by content-addressed fields alone.
- Do not allow `verify_webhook_signature` to silently return `true` when a per-organization `webhook_secret` is unset; either require a secret for every configured organization or treat missing-secret organizations as unverifiable/rejected.
- Reconsider deriving the verifying organization from unauthenticated JSON payload fields before any cryptographic check is performed.

### Proof of Concept
1. Operate (or identify) a Shipit instance configured with multiple GitHub organizations (multi-app `secrets.yml`), where organization `OrgX` has no `webhook_secret` set (a supported/documented configuration, as shown in `docs/setup.md` and `test/dummy/config/secrets_double_github_app.yml`).
2. Send `POST /webhooks` (or the mounted equivalent) with header `X-Github-Event: status` and a JSON body:
   ```json
   {
     "repository": { "owner": { "login": "OrgX" }, "full_name": "OrgX/anything" },
     "sha": "<sha of a commit belonging to victim org's tracked stack>",
     "state": "success"
   }
   ```
   with no valid `X-Hub-Signature` (or any arbitrary value).
3. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "OrgX")`, whose `webhook_secret` is `nil`, so `verify_webhook_signature` returns `true` unconditionally — the request is accepted (`app/controllers/shipit/webhooks_controller.rb:24-30`, `lib/shipit/github_app.rb:76-83`).
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and calls `create_status_from_github!` on any matching commit — including commits belonging to entirely different, properly-secured organizations — because the lookup has no repository/organization scope (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`).

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
