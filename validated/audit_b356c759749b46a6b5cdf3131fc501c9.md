### Title
Cross-tenant Team membership write via `MembershipHandler#find_or_create_team!` looking up by global `github_id` regardless of signing organization - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`WebhooksController#verify_signature` only proves that a `membership` payload was signed with the webhook secret belonging to the organization named in that same payload (`params.organization.login`), it does not prove that organization actually owns the `team.id` referenced in the body. `MembershipHandler#find_or_create_team!` then looks up the `Team` purely by the GitHub-global `github_id`, so if that ID already belongs to a `Team` owned by a different (victim) organization in the Shipit database, the attacker's self-signed request mutates the victim's team membership instead of creating a new one scoped to the attacker's own org.

### Finding Description
The binding the code implicitly relies on is: `verified_organization(params.organization.login) == owning_organization(Team.find_by(github_id: params.team.id))`. In reality the code only establishes `verified_organization(params.organization.login) == params.organization.login` (a tautology - the signature check is inherently self-referential to whichever organization is named in the same payload), and never checks it against the team's actual `organization` column.

Path:
1. `WebhooksController#verify_signature` resolves `Shipit.github(organization: repository_owner)` where `repository_owner` falls back to `params.dig('organization','login')` for events without a `repository` key [1](#0-0) [2](#0-1) . This means an attacker who registers/owns any organization configured in Shipit (with any `webhook_secret`, even a freshly self-registered one) can compute a valid `X-Hub-Signature` for a payload whose `organization.login` is their own org.
2. `Shipit::Webhooks.for_event('membership')` dispatches unconditionally to `Handlers::MembershipHandler` [3](#0-2) .
3. `MembershipHandler#process` calls `find_or_create_team!`, which resolves the `Team` by `github_id: params.team.id` alone: `Team.find_or_create_by!(github_id: params.team.id) do |team| ... end` [4](#0-3) . The block that sets `team.organization = params.organization.login` only executes on **create**; if a `Team` row with that `github_id` already exists (belonging to a legitimate, unrelated organization), the existing record is returned unchanged and unrelated to the attacker's claimed `organization.login`.
4. `process` then does `team.add_member(member)` or `team.members.delete(member)` using the attacker-supplied `member.login`, mutating the membership of the victim's team [5](#0-4) .

Exploit request: attacker configures their own GitHub organization/app in Shipit with a legitimate `webhook_secret`, then POSTs to `/webhooks` with `X-Github-Event: membership`, a valid `X-Hub-Signature` computed with their own secret, and a JSON body: `action: "added"`, `organization: {login: "attacker-org"}` (to pass `verify_signature`), `team: {id: <victim-team-github_id>, name, slug, url}`, `member: {login: "attacker-controlled-user"}`. Because the team lookup ignores the signing organization, this appends the attacker's chosen GitHub login to the victim organization's `Team`, and `Team#refresh_members!`/membership-derived authorization elsewhere in the app (`Shipit.github_teams`, `User` membership checks) would see this attacker-controlled user as a legitimate member of that team.

Why existing guards fail: `verify_signature` is designed for single-tenant HMAC validation per organization and correctly rejects forged signatures for a *given* organization, but it was never intended to authorize cross-references to global GitHub team IDs supplied inside the body of an unrelated organization's own signed payload. There is no model validation tying `Team#organization` to the `organization.login` on update, and `ExplicitParameters` only validates shape/types, not provenance.

### Impact Explanation
An attacker who controls any Shipit-registered organization (even a freshly self-registered one with its own `webhook_secret`) can, per request, add or remove arbitrary GitHub logins from any `Team` record already known to Shipit, as long as they can supply/guess that team's numeric `github_id` (GitHub team IDs are not secret and are sequential/enumerable, and may already be visible in existing Shipit data or GitHub API responses). This is a cross-tenant write - "a payload for one repository/organization mutating another's ... team" - and because team membership commonly gates deploy/rollback authorization via `Shipit.github_teams`, this can escalate an attacker-controlled account into a privileged team, matching the Critical impact category (authorization bypass / unauthorized team mutation) and potentially the High category (escalation into `Shipit.github_teams` authorization). The action is fully repeatable against any team ID for as long as the attacker's own org+secret pair remains configured.

### Likelihood Explanation
Preconditions: the attacker needs any organization registered in Shipit's GitHub app configuration with a `webhook_secret` (per the audit prompt, even self-registered orgs qualify) and knowledge of the target `Team`'s numeric GitHub `github_id`. No Shipit session, API token, or knowledge of the target organization's own secret is required. The attack is a single unauthenticated HTTP POST with a computed HMAC, requiring no interaction from GitHub itself - fully reproducible offline.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup by both `github_id` AND `organization` (e.g., `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`), or explicitly verify that any existing matching `Team#organization` equals `params.organization.login` before proceeding, raising/dropping the event otherwise.

### Proof of Concept
Minitest (`test/controllers/webhooks_controller_test.rb` style, illustrative - not to be placed under out-of-scope paths but describing exact assertions expected):
```ruby
test "membership event cannot mutate a team owned by a different organization" do
  victim_team = shipit_teams(:shopify_developers) # organization: 'shopify', github_id: X
  attacker_org = 'attacker-org'
  Shipit.stubs(:github).with(organization: attacker_org).returns(
    stub(verify_webhook_signature: true)
  )

  @request.headers['X-Github-Event'] = 'membership'
  payload = {
    action: 'added',
    team: { id: victim_team.github_id, name: victim_team.name, slug: victim_team.slug, url: victim_team.api_url },
    organization: { login: attacker_org },
    member: { login: 'attacker-controlled-user' }
  }.to_json

  assert_no_difference -> { victim_team.reload.members.count } do
    post :create, body: payload, as: :json
    assert_response :ok
  end
end
```
Before the fix, `victim_team.members.count` increases and `assert_response :ok` passes, proving `organization.login == attacker_org` (signature check) while `team.organization == 'shopify'` (actual owner) diverge and the write still succeeds.
