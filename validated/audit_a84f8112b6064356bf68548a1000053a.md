### Title
Cross-tenant `Status` row injection via unscoped `Commit.where(sha:)` in `StatusHandler#process` racing `MergeRequest#refresh!` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)`, with no filter tying the write to the repository/organization that the inbound webhook was authenticated for. [1](#0-0)  Because the `commits` table only enforces a `(sha, stack_id)` uniqueness constraint (not a global-unique `sha`), the same SHA string can legitimately back rows on multiple different stacks, and a validly-signed webhook for one organization/repo can overwrite `Status` rows belonging to a commit tracked by an unrelated stack. [2](#0-1) 

### Finding Description
Binding claimed: `webhook signer authenticated for organization X` == `only entity permitted to write Status rows for commits belonging to stacks owned by organization X`. This binding is broken.

`WebhooksController#verify_signature` authenticates the *payload's claimed organization* (`repository_owner`, itself read straight out of the attacker-controlled JSON body) against `Shipit.github(organization: repository_owner).verify_webhook_signature`. [3](#0-2)  This check proves only "this request was really signed by GitHub for *some* app/org configured in Shipit" — it says nothing about which *repository* or *commit* the event concerns.

Once past that gate, `StatusHandler#process` does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [1](#0-0) 
This is a global, unscoped lookup — no join/filter on `commit.stack.repository` matching the payload's `repository.full_name`/`repository.owner.login`. Compare this to `PushHandler#process`, which scopes its target set through `stacks` (repository-bound) before acting. [4](#0-3)  `StatusHandler` has no equivalent scoping.

`create_status_from_github!` then calls `Status.replicate_from_github!`, a `find_or_create_by!` write keyed by `(stack_id, context, state, description, target_url, created_at)`: [5](#0-4)  a new attacker-controlled row for that `context` is inserted for the victim's commit's `stack_id` — no ownership check against the requesting webhook's repository is performed anywhere in this call chain.

`Commit#refresh_statuses!` (invoked from `MergeRequest#refresh!` → `head.refresh_statuses!`) writes through the exact same `create_status_from_github!` method, [6](#0-5)  and `MergeRequest#refresh!` itself gates merges via `all_status_checks_passed?`, which reads `head.statuses_and_check_runs` (i.e. every `Status` row on that commit, including any injected by the webhook path). [7](#0-6) [8](#0-7) 

Exploit flow: an attacker who has write access to at least one repository whose GitHub App installation is configured in Shipit (this can be an org member's own unrelated repo, or their own org if Shipit is configured for multiple organizations, as documented in `secrets.development.shopify.yml`) sets a commit status via the GitHub Statuses API using the victim's target commit SHA (public information visible on any PR page). GitHub emits a genuinely-signed `status` webhook for the attacker's own repository. `verify_signature` authenticates it correctly for the attacker's org/repo. `StatusHandler#process`, however, matches `Commit.where(sha:)` against *every* commit row sharing that SHA — including the victim's commit tracked under a completely different stack/organization — and writes a new `Status` row into it. If this interleaves with `RefreshMergeRequestJob` → `MergeRequest#refresh!` → `head.refresh_statuses!` polling GitHub for the legitimate state, the final row observed by `StatusChecker`/`all_status_checks_passed?` can be the attacker's forged one, directly gating `merge!`.

Existing guards do not stop this: `verify_signature` authenticates organization identity, not commit/repository ownership of the write target; `ExplicitParameters` on `StatusHandler` only validates payload shape (`sha`, `state`, etc.), not authorization scope; there is no `require_permission!`/`Repository` equality check anywhere in this handler.

### Impact Explanation
An attacker with write access to any single repository covered by a Shipit-configured GitHub App installation can inject arbitrary `Status` rows (`state`, `description`, `target_url`, `context`) onto **any commit row in the Shipit database that happens to share that SHA**, regardless of which stack/organization it belongs to. Because `Status` rows feed `StatusChecker`/`all_status_checks_passed?`, this is a write into a merge-gating decision for a repository the attacker never authenticated against — matching the Critical category "a payload for one repository mutating another's stack/commit... or an unauthorized deploy, rollback or merge." The blast radius is any stack whose tracked commits can share a SHA with a commit reachable by the attacker (duplicate/forked history, multi-environment stacks on the same repository, or any SHA collision achievable through the GitHub Statuses API), and is repeatable per request since there's no additional check preventing repeated forged writes.

### Likelihood Explanation
Preconditions: the attacker needs (a) write access to at least one repository under a GitHub App installation configured in this Shipit instance (satisfies "repository they own" per the threat model), and (b) a target commit SHA that also exists as a `Commit` row under a different stack (achievable via shared/forked git history, or duplicate stacks over the same repository, both of which the schema explicitly permits via the `(sha, stack_id)` composite unique index rather than a global-unique `sha`). No secrets, sessions, or maintainer status are required. The race with `RefreshMergeRequestJob` is a timing win, not a hard precondition — a losing race still leaves a forged row sitting in the table for subsequent evaluations.

### Recommendation
Scope `StatusHandler#process` (and any other handler resolving targets purely by SHA) to only touch `Commit` rows whose `stack.repository` matches the webhook's authenticated repository, e.g. `Commit.joins(stack: :repository).where(sha: params.sha, repositories: { owner: ..., name: ... })`, mirroring the repository-bound scoping already used in `PushHandler`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "process does not write statuses onto commits owned by a different repository/stack" do
  victim_stack = shipit_stacks(:shipit)          # org A
  attacker_stack = shipit_stacks(:cyclimse)      # org B, different repository
  shared_sha = "deadbeef" * 5

  victim_commit = victim_stack.commits.create!(sha: shared_sha, ...)
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, ...)

  attacker_payload = OpenStruct.new(
    sha: shared_sha, state: "success", context: "ci/required",
    description: "forged", target_url: nil, created_at: Time.now.iso8601,
    branches: []
  )

  # Simulate the concurrent legitimate poll writing "pending" first
  victim_commit.create_status_from_github!(
    OpenStruct.new(state: "pending", context: "ci/required", description: nil,
                    target_url: nil, created_at: 1.minute.ago)
  )

  # Attacker's genuinely-signed webhook for THEIR OWN repo, but matching SHA
  Shipit::Webhooks::Handlers::StatusHandler.new(attacker_payload).process

  victim_commit.reload
  final_status = victim_commit.statuses.where(context: "ci/required").last

  # BROKEN BINDING: victim's stack_id row was overwritten by attacker's webhook
  assert_equal "success", final_status.state
  assert_equal "forged", final_status.description
  assert_equal victim_stack.id, final_status.stack_id
end
```
This demonstrates the equality `authenticated_org_for_webhook == authorized_writer_for_commit.stack.owning_org` fails: the write lands on `victim_stack`'s commit despite the webhook only being authenticated for the attacker's own (different) repository/org.
