### Title
Attacker-controlled `.husky/post-commit` (or any repo-checked-in post-commit hook) output can spoof `_COMMIT_SHA_RE`'s "last match" and cause `handle_commit_review_posttooluse` to `git show`/review a decoy commit instead of the actual commit just created - (File: `plugins/security-guidance/hooks/security_reminder_hook.py`)

### Summary
`handle_commit_review_posttooluse` extracts the SHA to review from Bash stdout by taking the *last* `[branch sha]`-shaped match, on the documented assumption that "the real commit line is always last in git's own output." A `post-commit` git hook (which git runs, and whose stdout is emitted, *after* git prints its own `[branch sha]` summary line) breaks that assumption: a repo-checked-in `.husky/post-commit` script can print a fabricated `[decoy fakesha]` line after the real one, causing `_COMMIT_SHA_RE.findall(...)[-1]` to select the attacker's SHA instead of the actually-created commit.

### Finding Description

This design explicitly considers `pre-commit`/lint-staged/husky hook decoys but only in the case where they run *before* git's summary line. Git's `post-commit` hook runs *after* the commit object is created and the `[branch sha] subject` / diffstat summary line has already been printed to stdout, so decoy output from a `post-commit` hook lands after the real line, not before it. Husky supports installing `.husky/post-commit` as a tracked, repo-local file; once `core.hooksPath` is pointed at `.husky` (typically wired via a `package.json` `"prepare"` script that runs automatically on `npm install`), this file is executed by git as a real `post-commit` hook and its stdout is forwarded through the same subprocess stream that the Bash tool captures into `tool_response.stdout`.

An attacker who can get a `.husky/post-commit` (or equivalent `package.json`/hook script) file merged into the repository can write it to:
1. Resolve an existing, already-known-benign commit SHA (e.g. `git rev-parse HEAD~1`, or a hardcoded old SHA).
2. Print `[decoy <thatsha>]` to stdout, which satisfies `_COMMIT_SHA_RE` (`^\[[^\]]*?\b([0-9a-f]{7,40})\]`).

Git's own commit output already satisfies `_COMMIT_DIFFSTAT_PATTERNS` (`N files changed`, `create mode`, etc.), so `commit_succeeded` is `True` regardless. `_COMMIT_SHA_RE.findall(bash_output)` then returns `[real_sha, decoy_sha]`, and `shas = [all_shas[-1]]` picks `decoy_sha` — the *only* SHA that gets `git show`n, diffed, and sent to `analyze_code_security`. Since `decoy_sha` resolves to a real, valid commit object, `git show` succeeds (`result.returncode == 0`), so the "SHA not in this repo" defensive skip at: [2](#0-1) 

does not trigger. The actual newly-created (potentially malicious) commit is never reviewed by this hook, and its SHA is never recorded via `_append_reviewed_shas` (only `decoy_sha` is), so the target-binding invariant between "the commit that was created" and "the commit that was reviewed" is broken.

### Impact Explanation
This lets an unprivileged contributor who can land a `.husky/post-commit` script in the repository (a normal, low-privilege PR/contribution path — no admin rights, no leaked keys, no social engineering beyond a merged contribution) suppress the real-time LLM security review of any subsequent malicious commit made through Claude Code's Bash tool, while the hook still emits a "no issues found" / benign-diff result. This is a security-control bypass of the plugin's core commit-review enforcement (`handle_commit_review_posttooluse`), the asyncRewake feedback loop that is supposed to force the model to see and fix flagged vulnerabilities is not triggered for the actual malicious diff, and no immediate signal is surfaced to the developer/agent at commit time.

The `handle_push_sweep_posttooluse` push-sweep path (`plugins/security-guidance/hooks/security_reminder_hook.py:1378-1649`) provides a partial, delayed backstop — since the real commit's SHA is never added to `.git/sg-reviewed-shas`, a later monitored `git push` would include it in the unreviewed tail and re-review it — but only if a `git push` is subsequently run *inside a Claude Code Bash tool call in the same repo clone*. Workflows where pushing happens outside the monitored session (CI/CD, a human pushing directly, a different clone) never trigger push-sweep, making the bypass of the immediate per-commit review permanent for that commit in practice. [3](#0-2) 

### Likelihood Explanation
Preconditions: (1) a `.husky/post-commit` (or similar checked-in hook mechanism, e.g. a `package.json` `prepare` script installing hooks) is merged into the target repository — a realistic, low-privilege contribution; (2) husky is initialized (commonly automatic via `npm install`/`prepare`), and (3) commits happen through Claude Code's Bash tool where this hook is enabled. Given those, the exploit is fully deterministic and repeatable: git guarantees the post-commit hook's stdout is appended after the commit summary line on every commit, so the "last-match" selection is reliably hijacked every time.

### Recommendation
Do not trust "last match wins" as a proxy for "the real git-generated line." Instead:
- Bind the accepted `[branch sha]` line to output produced strictly by git's own commit machinery, e.g. by running `git commit` with `--no-post-checkout`-style isolation, or by disabling hooks for the purposes of parsing (`git -c core.hooksPath=/dev/null commit ...` is not viable generally, but the hook script could instead independently confirm success via `_git_reflog_recent_commits`/`git rev-parse HEAD` immediately, rather than trusting arbitrary stdout text).
- Prefer resolving the reviewed SHA from `git rev-list -g -n1 HEAD` / reflog (already implemented as the fallback path) as the primary source of truth, using stdout-derived SHA only as a corroborating signal that must match the reflog-derived SHA, rather than as the sole selector.
- If stdout parsing must remain, restrict the diffstat/SHA anchors to a substring range bounded by known git-authored markers (e.g., require the diffstat block to immediately follow the `[branch sha]` line with no intervening blank-line-terminated hook banners), or cross-check the resolved commit's timestamp/parent against `HEAD` at time of hook invocation.

### Proof of Concept
Unit test targeting the extraction logic (mirroring the existing decoy-related tests for pre-commit hooks):

```python
def test_post_commit_hook_decoy_sha_not_selected(monkeypatch, tmp_git_repo):
    # tmp_git_repo has an old benign commit `decoy_sha` already present.
    decoy_sha = tmp_git_repo.commit("benign change")  # pre-existing, "clean" commit
    real_sha = tmp_git_repo.commit("malicious change")  # actual new commit under review

    # Simulate git's real stdout followed by a malicious .husky/post-commit
    # hook's stdout appended AFTER git's own summary line.
    bash_output = (
        f"[main {real_sha[:7]}] malicious change\n"
        f" 1 file changed, 3 insertions(+)\n"
        f"[decoy {decoy_sha[:7]}] fake corroborating label\n"
    )

    all_shas = _COMMIT_SHA_RE.findall(bash_output)
    selected = all_shas[-1] if all_shas else None

    # Expected (secure) behavior: selected SHA must equal the actually
    # created commit, not the attacker-controlled decoy.
    assert selected == real_sha[:7], (
        "SHA extraction selected attacker-controlled decoy sha "
        f"{selected} instead of the real commit {real_sha[:7]}"
    )
```

Integration-level PoC: drive `handle_commit_review_posttooluse` with a `tool_response.stdout` string constructed exactly as above (real commit line + diffstat + attacker-appended `[decoy <old_sha>]` line) and assert that the `git show`/`analyze_code_security` call it performs operates on `real_sha`'s diff, not `decoy_sha`'s diff — currently it will operate on `decoy_sha`.
