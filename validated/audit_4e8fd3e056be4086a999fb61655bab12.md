### Title
Webhook signature is verified against the organization derived from `repository.owner.login`, but every event handler acts on the unrelated `repository.full_name` field — allowing cross-repository/cross-tenant forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification based on `params.dig('repository','owner','login')` (or `organization.login`), but every downstream `Webhooks::Handlers::Handler` subclass resolves the *target* repository/stack to act on using the completely independent `params.dig('repository','full_name')` field [1](#0-0) . These two payload fields are never checked against each other, so the field that is cryptographically authenticated is not the field that determines which repository gets written to.

### Finding Description
In a multi-organization Shipit deployment, `Shipit.github(organization: repository_owner)` looks up a distinct `GitHubApp`/secret per organization key in `secrets.github` [2](#0-1) . `verify_webhook_signature` then HMACs the *raw payload bytes* with that organization's secret and compares it to `X-Hub-Signature` [3](#0-2) . This proves only that *some* party who knows organization `repository_owner`'s webhook secret sent this exact byte string — it says nothing about which repository the payload's `repository.full_name` field claims to represent.

Every `Handler` subclass, however, ignores `repository_owner`/`organization.login` entirely and instead resolves the acted-upon repository via `Repository.from_github_repo_name(payload.dig('repository','full_name'))`:
- Base `Handler#stacks` / `#repository_name` [4](#0-3) 
- `PushHandler#process`, which walks `stacks` and calls `stack.sync_github(expected_head_sha: params.after)` [5](#0-4) 
- `pull_request/closed_handler.rb`, which resolves `repository` from `params.repository.full_name` and calls `review_stack.archive!` [6](#0-5) 
- `pull_request/assigned_handler.rb` and `edited_handler.rb`, which likewise key off `params.repository.full_name` to find and mutate a `PullRequest`/`ReviewStack` [7](#0-6) 

Because `repository.owner.login` (used to pick the verifying secret) and `repository.full_name` (used to pick the write target) are independent, unvalidated JSON fields in the same attacker-controlled payload, an attacker who legitimately administers **any one** organization/repository already integrated with this Shipit instance — and therefore knows that organization's `webhook_secret` — can craft a payload where:
- `repository.owner.login = "attacker-org"` (so `Shipit.github(organization: "attacker-org")` picks their own known secret and `verify_webhook_signature` succeeds), while
- `repository.full_name = "victim-org/victim-repo"` (so the handler resolves and mutates a Shipit stack that belongs to a completely different, victim organization the attacker has no access to).

This breaks exactly the binding called out in scope: *"an organization that authenticated versus the repository that is written."* The equality that should hold — `organization_that_signed(payload) == owner_of(repository_that_gets_written(payload))` — does not, because the controller authenticates one field and every handler writes based on a different, unauthenticated field.

### Impact Explanation
Depending on event type, this enables an attacker who only controls their own org's webhook secret to forge state-changing events against a victim organization's Shipit stacks:
- `push` events forge `stack.sync_github(expected_head_sha: ...)` on a victim stack [8](#0-7) , which can desynchronize/refresh commit history used by later deploy/merge decisions.
- `pull_request` "closed" events forge `review_stack.archive!` on a victim review stack [9](#0-8) , an unauthorized destructive action.
- `status`/other handlers act on `Commit.where(sha:)` globally, independent of any owner check at all [10](#0-9) , letting an attacker inject fabricated commit statuses for shared commit SHAs across repositories, which can influence deploy-gating checks.

This is a cross-repository/cross-tenant write achieved by an attacker who is unprivileged with respect to the victim organization, matching the Critical-tier "cross-repository writes" / "unauthorized deploy, rollback or merge" impact bar.

### Likelihood Explanation
Requires the attacker to already be a legitimate account holder for at least one organization/repository onboarded to the same multi-tenant Shipit instance (i.e., they know their own org's `webhook_secret`, which is normal for anyone administering their own GitHub App/webhook config) — no privileged Shipit account, no `ApiClient` token, and no access to the victim's secret are needed. Multi-org configuration is a supported, documented deployment mode (`secrets.github` keyed by organization) [11](#0-10) , so this is reachable in any deployment using per-organization GitHub Apps.

### Recommendation
In `WebhooksController#verify_signature`, additionally assert that the organization used for signature verification matches the owner embedded in `repository.full_name` (or `organization.login`) before dispatching to handlers, and have handlers reject/ignore any payload where these disagree, rather than trusting `full_name` alone for repository resolution.

### Proof of Concept
1. Shipit is configured with two organizations, `attacker-org` and `victim-org`, each with its own `webhook_secret` in `secrets.github`.
2. Attacker knows `attacker-org`'s `webhook_secret` (they administer that org's GitHub App/webhook).
3. Attacker POSTs to `/webhooks` with header `X-Github-Event: pull_request` and body:
```json
{
  "action": "closed",
  "number": 42,
  "pull_request": { ... },
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "sender": { "login": "attacker" }
}
```
4. Signs the raw body with `attacker-org`'s known `webhook_secret` and sets `X-Hub-Signature` accordingly.
5. `verify_signature` calls `Shipit.github(organization: "attacker-org")` (from `repository.owner.login`) and successfully verifies the signature [12](#0-11) .
6. `PullRequest::ClosedHandler` resolves `repository` via `params.repository.full_name` = `"victim-org/victim-repo"` and calls `review_stack.archive!` on the victim's stack [13](#0-12) , an unauthorized write the attacker has no legitimate access to trigger.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
