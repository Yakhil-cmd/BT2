### Title
`/events` (Pubsubstub::StreamAction) is mounted with no authentication, allowing unauthenticated cross-tenant deploy-output streaming - ([File: config/routes.rb])

### Summary
`/events` is mounted directly as a raw Rack endpoint (`Pubsubstub::StreamAction`) rather than as a `Shipit::ShipitController` action, so it never passes through the `force_github_authentication` before_action that gates every other page in the engine. Since channel names are simply `"stack.#{stack.id}"` / `"task.#{task.id}"`-style deterministic strings derived from sequential primary keys, any unauthenticated internet client can subscribe to `/events?channels[]=stack.<id>` (or the task/output channel) for any stack/repository and receive that tenant's live deploy/task update events.

### Finding Description
The broken binding: the claim `readable_channel(client) == channel_belongs_to_authorized_stack(client)` is assumed by every page (`app/views/shipit/stacks/show.html.erb:1`, `app/views/shipit/stacks/all_tasks.html.erb:1`, `app/views/shipit/repositories/show.html.erb:1`, merge_requests index) which embed `events_path(channels: ["stack.#{@stack.id}"])` [1](#0-0)  only after the enclosing controller action has already run `force_github_authentication` / authorization checks for that stack. That equality is broken because the actual `/events` request goes to a separately mounted Rack app that bypasses this check entirely:

- `config/routes.rb` mounts `Pubsubstub::StreamAction.new` at `/events` at the top level of `Shipit::Engine.routes.draw`, outside any controller/`before_action` scope: [2](#0-1) .
- All authentication/authorization for the engine is implemented as a Rails controller concern, `Shipit::Authentication`, included into `Shipit::ShipitController` via `include Shipit::Authentication` which registers `before_action :force_github_authentication` [3](#0-2) [4](#0-3) .
- A `rack.mount` target (`Pubsubstub::StreamAction`) is not a `Shipit::ShipitController` subclass and has no `before_action`; Rails routing dispatches directly to its `#call`, never invoking `force_github_authentication`, `current_user.authorized?`, or any team/stack-scoping check [5](#0-4) .
- Channel names are fully deterministic and low-entropy, built from auto-increment primary keys/stack ids that the attacker can observe or brute-force (e.g. `"stack.#{stack.id}"`, `"repository.#{repository.id}"` as seen used for legitimate subscriptions in `app/views/shipit/stacks/show.html.erb:1`, `app/views/shipit/repositories/show.html.erb:1`, and confirmed independently by test helpers asserting `channel == "stack.#{stack.id}"` in `test/models/commits_test.rb:949` and `test/models/status_test.rb:61`) [6](#0-5) [7](#0-6) .

Exploit flow: an unauthenticated attacker (no session, no `ApiClient` token, not in `Shipit.github_teams`) sends `GET /events?channels[]=stack.1` (incrementing the id) directly to the Shipit host. Because this hits the mounted Pubsubstub Rack app and not a `Shipit::ShipitController` action, `force_github_authentication` never fires, so the request is served regardless of `current_user.authorized?`. The attacker receives an SSE stream of `update`/task events for that stack — including any repositories/tenants other than their own — with no relationship to that stack required.

Existing guards do not apply here: `force_github_authentication`, `User#authorized?`, and `Shipit.github_teams` are all controller-level constructs applied via `before_action` on `ApplicationController`/`ShipitController` subclasses [8](#0-7) ; they have no way to intercept a request routed to a directly-mounted Rack endpoint such as `Pubsubstub::StreamAction`. There is no separate authorization layer inside Pubsubstub itself verifiable in this repo (the gem is a third-party dependency not vendored here), and no engine-level Rack middleware was found enforcing session/auth checks ahead of routing (`lib/shipit/engine.rb` only configures OmniAuth and SameSite middleware, neither of which blocks unauthenticated requests) [9](#0-8) .

### Impact Explanation
An attacker who is a completely unauthenticated internet user can, per request, obtain the live real-time task/deploy output event stream (`update` events, task status changes, output chunk notifications) for any stack/repository hosted on the Shipit instance, simply by guessing or enumerating small integer stack/task ids. This is repeatable against arbitrary stacks by iterating ids and is not limited to the attacker's own repositories — it crosses tenant boundaries entirely. This matches the "High" impact category: unauthenticated read of stack state/task streams/deploy output.

### Likelihood Explanation
No Shipit or repository-side secret configuration is needed; the attacker only needs network access to the Shipit host and knowledge (or brute-forced guesses) of small sequential ids, both trivially obtainable since ids are exposed throughout the UI/API (stack pages, task pages) to any user with any account, or even inferable from public URLs. The attack costs a single unauthenticated HTTP GET per channel and is fully repeatable/enumerable.

### Recommendation
Do not mount `Pubsubstub::StreamAction` unauthenticated at the top level. Wrap it behind an authenticating Rack middleware or a thin controller action that: (1) requires a valid Shipit session (or scoped API token), (2) resolves the requested channel(s) to a `Stack`/`Repository`, and (3) verifies `current_user.authorized?` and any repository-level ACL before allowing the subscription, only forwarding to Pubsubstub after that check succeeds (or use per-channel signed/unguessable channel tokens instead of raw incrementing ids).

### Proof of Concept
minitest plan (integration test, no live GitHub):
1. Create two stacks belonging to different repositories, `stack_a` and `stack_b`, via fixtures.
2. Without setting any session (`session[:user_id]` absent, i.e., anonymous client), issue `get "/events", params: { channels: ["stack.#{stack_b.id}"] }`.
3. Assert the response is `200`/`text/event-stream` rather than a redirect to `github_authentication_path` or a `403`.
4. Publish a `Pubsubstub.publish("stack.#{stack_b.id}", ...)` event and assert the anonymous client's SSE body/stream includes that event, proving cross-tenant read without any authentication:
```ruby
assert_response :success
assert_no_match(/github_authentication/, response.body) # not redirected to login
```
This demonstrates the binding `authenticated_and_authorized_for(stack_b) == can_read_channel("stack.#{stack_b.id}")` is false — an anonymous, unauthorized client can read the channel.

# frozen_string_literal: true

module Shipit
  module Authentication
    extend ActiveSupport::Concern

    included do
      before_action :force_github_authentication
      helper_method :current_user
    end

    module ClassMethods
      def skip_authentication(*args)
        skip_before_action(:force_github_authentication, *args)
      end
    end

    private

    def force_github_authentication
      if current_user.logged_in? && current_user.requires_fresh_login?
        Rails.logger.warn("User #{current_user.id} requires a fresh login, logging out...")
        reset_session
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      elsif Shipit.authentication_disabled? || current_user.logged_in?
        unless current_user.authorized?
          team_handles = Shipit.github_teams.map(&:handle)
          team_list = team_handles.to_sentence(two_words_connector: ' or ', last_word_connector: ', or ')
          render(plain: "You must be a member of #{team_list} to access this application.", status: :forbidden)
        end
      else
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      end
    end

    def current_user
      @current_user ||= find_current_user || AnonymousUser.new
    end

    def find_current_user
      session[:user_id].present? && User.find_by(id: session[:user_id])
    end
  end
