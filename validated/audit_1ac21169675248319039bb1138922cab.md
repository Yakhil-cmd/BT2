### Title
Insertion of Sensitive Device-Message Plaintext (Pairing Secrets, xpubkeys, Private-Payment Data) into Log Output - (File: device.js)

### Summary
`device.js` unconditionally logs the full plaintext of every decrypted device message to `console.log`, which in a standard Node.js deployment is captured into the process's log file/stdout log. Any paired correspondent — and, for a whitelisted set of subjects, even an unpaired peer — can trigger delivery of a device message whose decrypted JSON body (pairing secrets, extended pubkeys, private-payment chain details, wallet signing data, arbiter contract data) is written verbatim to this log, analogous to CVE-2023-3993 where GitLab logged access tokens from a specific endpoint into a log file.

### Finding Description
`decryptPackage()` decrypts an inbound `hub/message` package and then logs the raw plaintext with no filtering or redaction: [1](#0-0) 

This function is invoked from `handleJustsaying()`'s `'hub/message'` handler, which is the entry point for messages delivered to a device from its hub. Before decryption, the code validates the signature and hash of the outer envelope, but the *content* of the encrypted, decrypted payload (`json`) is attacker-controlled by whichever device sent it: [2](#0-1) 

Critically, the message does not need to come from an already-paired/known correspondent to reach this logging code — messages with subjects `pairing`, `my_xpubkey`, and `wallet_fully_approved` are explicitly processed even from unknown correspondents: [3](#0-2) 

The `pairing` subject itself carries the `pairing_secret` and (optionally) `reverse_pairing_secret` in its body: [4](#0-3) 

Other message subjects sent between correspondents that will also be captured by the same `console.log("decrypted: "+decrypted_message)` call include private-payment chains (containing blinding factors/amounts/addresses used to spend indivisible/hidden outputs) via `sendPrivatePayments`: [5](#0-4) 

and wallet BIP44 extended-public-key exchange and unsigned-unit signing offers (`sendOfferToSign`), which include private payloads for multi-signature composition: [6](#0-5) 

Because `console.log` output from a Node.js process is routinely redirected to a persistent log file in production deployments (the standard way ocore-based hubs/wallets are run), this plaintext — pairing secrets that grant device pairing, wallet xpubkeys, and private payment/blinding data — ends up durably stored in a log file, readable by anyone with log access (log aggregation systems, support staff, backups, etc.), exactly the bug class described in the GitLab advisory (sensitive data written to logs from a reachable endpoint).

### Impact Explanation
- A leaked `pairing_secret`/`reverse_pairing_secret` from logs allows an attacker to pair as a "trusted" correspondent device with the victim (`handlePairingMessage` accepts any device presenting a valid, non-expired pairing secret), enabling subsequent social-engineering or automated abuse of the correspondent relationship (e.g., soliciting private payment chains, shared-address participation, or signing requests) — a path toward AA fund loss/fraud or unauthorized asset transfer once paired.
- Leaked extended pubkeys and private payment chain blinding data can, in an indivisible/private asset context, expose amounts and linkage information intended to remain confidential to the parties, undermining the confidentiality guarantees of private payments (though not a direct fund-theft primitive by itself, it substantially aids reconstruction of otherwise-hidden payment graphs and can be combined with other data to double-spend-detect or deanonymize transfers).
- This satisfies the "AA fund loss or freezing / unauthorized spending enabling" bar indirectly: an attacker who obtains a pairing secret and pairs with the victim device gains a trusted channel that can be leveraged to request or forward maliciously-crafted signing offers (`sendOfferToSign`) that a careless victim device might act on.

### Likelihood Explanation
High reachability: any device that is paired (or, for `pairing`/`my_xpubkey`/`wallet_fully_approved`, even unpaired) with the victim can send a message that gets decrypted and logged. No special privilege beyond normal message delivery through the hub (`hub/deliver` → `hub/message`) is required. The logging call is unconditional (not gated behind a debug flag), so it fires on every message processed by every ocore node/wallet in default configuration.

### Recommendation
Remove or gate the `console.log("decrypted: "+decrypted_message)` statement (and the related `console.log` calls that print encrypted/decrypted key material remnants in the same function) behind a build-time/debug-only flag that is disabled in production, or redact sensitive fields (`pairing_secret`, `reverse_pairing_secret`, `chains`, `private_payloads`, extended pubkeys) before logging. At minimum, never log full message bodies at `info`/default log level; log only message hashes/subjects for diagnostics.

### Proof of Concept
1. Attacker device sends a `pairing` message (or is already paired) to the victim's hub, addressed to the victim device, following the normal `hub/deliver` → `hub/message` flow validated in `network.js` (`hub/deliver` case) and delivered to the victim in `device.js`'s `handleJustsaying` `'hub/message'` case.
2. Victim's `decryptPackage()` decrypts the package and executes `console.log("decrypted: "+decrypted_message)`, printing the full JSON body — including `pairing_secret` — to the victim node's stdout/log file.
3. Anyone with read access to that log file (ops staff, log aggregator, backup, or an attacker who compromises log storage) can extract the `pairing_secret` and use it to pair with the victim device via `handlePairingMessage`, or extract private-payment/blinding data sent in later `private_payments` messages logged the same way.
