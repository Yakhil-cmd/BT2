### Title
Webhook organization-authentication bypass across repositories via decoupled `repository.owner.login` vs `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The analog for the "min-amount computed for one leg but applied to a different redemption path" class of bug is present in Shipit's webhook trust boundary: the field used to select and verify the cryptographic signature (`repository.owner.login`) is not the same field used by the event handlers to decide which `Stack`/`Repository`/`Commit` gets mutated (`repository.full_name`). Both fields live in the same attacker-supplied JSON body, so the "organization that authenticated" binding and the "repository that is written" binding can be made to diverge.

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App/secret to verify against using `repository_owner`, derived purely from the incoming payload: [1](#0-0) [2](#0-1) 

`verify_webhook_signature` in turn returns `true` unconditionally when no `webhook_secret` is configured for that organization: [3](#0-2) 

This "no secret configured" state is not an exotic edge case — it is the shipped default in the setup templates (`webhook_secret: # nil`) for any organization that hasn't opted into signature verification: [4](#0-3) 

Once the request passes `verify_signature` (trivially, for an org with no secret), every event handler resolves the actual repository/stack to act on from a *different* payload field — `repository.full_name` — completely independent of the `repository.owner.login` used for authentication: [5](#0-4) 

The same pattern repeats in every concrete handler (`PushHandler`, `StatusHandler`, and all `PullRequest::*Handler` classes), which never cross-check that `repository.full_name` belongs to the organization that was actually authenticated: [6](#0-5) [7](#0-6) [8](#0-7) 

This is structurally identical to the reported bug class: the value that is "checked" (`repository.owner.login`, used to pick the verification key) is not the value that the downstream, security-relevant action actually operates on (`repository.full_name`, used to look up the `Stack`/`Commit` to mutate). An attacker only needs to know of a single organization configured in the Shipit instance without a `webhook_secret` (a supported, documented configuration, not a privileged credential) to satisfy `verify_signature`, then set `repository.full_name` in the same JSON body to point at a `Stack` belonging to an entirely different, properly-secured organization.

**Equality broken:** `organization authenticated (repository.owner.login → github_app/secret used)` == `repository actually written (repository.full_name → Stack/Commit resolved by handler)` — before the fix these are independently attacker-controlled fields in one unsigned-for-that-org payload; they should be one and the same trust domain.

### Impact Explanation
With the binding broken, an external, completely unauthenticated attacker (no Shipit session, no `ApiClient` token, no `webhook_secret`, no repository write access — they merely need one org in the fleet configured without a webhook secret, which is the shipped default) can:
- Forge `status` events targeting any `Commit` by `sha` across any stack (`StatusHandler#process` iterates `Commit.where(sha: params.sha)` with no repository scoping at all), injecting fabricated CI/deploy statuses that can gate `release_status_context`/continuous-deployment checks on stacks belonging to a different, secured organization — this can result in an **unauthorized deploy**.
- Forge `push` events causing `sync_github` for stacks under a targeted (different) organization.
- Forge `pull_request` events to archive/unarchive (deprovision or reprovision) review stacks belonging to another organization's repositories.

This crosses the "unauthorized deploy" / cross-organization-write impact bar defined in the rules.

### Likelihood Explanation
Requires only: (1) at least one organization onboarded to the Shipit instance without a configured `webhook_secret` — the documented default state in the setup templates — and (2) knowledge/guess of a target `repository.full_name` tracked by the instance (repository names are not secret). No GitHub credentials, no Shipit account, and no prior repository access are needed; the request is a single unauthenticated POST to the public `/webhooks` endpoint.

### Recommendation
Bind the two fields together: after resolving the `Repository`/`Stack` via `repository.full_name`, verify that its owning GitHub organization matches the organization whose secret was used for signature verification (`repository_owner`). Reject the event if the resolved repository's organization does not match `repository_owner`, regardless of whether that organization requires a signature. Consider also requiring `webhook_secret` to be present for all configured organizations, or applying the strictest applicable policy when any org in a shared instance has signature verification disabled.

### Proof of Concept
1. Shipit instance configured with two GitHub Apps: `OrgWithoutSecret` (no `webhook_secret`, per the shipped template) and `OrgWithSecret` (properly secured), both tracked in the same Shipit deployment, e.g. `OrgWithSecret/victim-repo` has an active `Stack` with continuous delivery gated on a `release_status_context`.
2. Attacker crafts a `status` webhook payload:
```json
{
  "repository": { "owner": { "login": "OrgWithoutSecret" }, "full_name": "OrgWithSecret/victim-repo" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "<release_status_context>"
}
```
3. Attacker sends `POST /webhooks` with header `X-Github-Event: status` (no valid `X-Hub-Signature` needed since `OrgWithoutSecret` has no secret).
4. `WebhooksController#verify_signature` resolves `Shipit.github(organization: 'OrgWithoutSecret')`, whose `verify_webhook_signature` returns `true` unconditionally (`webhook_secret` blank), so the request passes.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and creates a status from the forged payload on the victim commit under `OrgWithSecret/victim-repo`, potentially satisfying that stack's deployability/continuous-delivery gating despite the request never having been authenticated for `OrgWithSecret`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
