### Title
Fee-on-Transfer ERC20 Token Causes Bridge Undercollateralization in Lock/Unlock Mode — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

### Summary

`requestERC20Transfer` in `BridgeTransferERC20.sol` records and emits the caller-supplied `_value` in the `RequestValueTransfer` event without verifying the actual token amount received after `safeTransferFrom`. When a fee-on-transfer (FoT) ERC20 token is registered on the bridge, the source bridge receives fewer tokens than `_value + _feeLimit`, but the counterpart bridge is instructed to release the full `_value` to the recipient. In lock/unlock mode (`modeMintBurn = false`), this permanently undercollateralizes the source bridge and allows the counterpart bridge's reserves to be drained proportionally to the FoT rate.

### Finding Description

`requestERC20Transfer` performs a `safeTransferFrom` for `_value + _feeLimit`, then immediately passes the original `_value` to `_requestERC20Transfer` without measuring the actual received balance: [1](#0-0) 

```solidity
function requestERC20Transfer(...) public {
    IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
    _requestERC20Transfer(_tokenAddress, msg.sender, _to, _value, _feeLimit, _extraData);
}
```

Inside `_requestERC20Transfer`, the nominal `_value` is emitted in the cross-chain event without adjustment: [2](#0-1) 

The counterpart bridge's `handleERC20Transfer` then mints or transfers the full `_value` to the recipient: [3](#0-2) 

The 1-step path (`onERC20Received`) has the same flaw: `ERC20ServiceChain.requestValueTransfer` transfers `_amount + _feeLimit` to the bridge (with FoT deduction), then calls `onERC20Received` with the original `_amount`: [4](#0-3) 

`_payERC20FeeAndRefundChange` in `BridgeFee.sol` also does not account for FoT when paying the fee receiver and refunding the user, compounding the balance discrepancy: [5](#0-4) 

Token registration is `onlyOwner`, so a FoT token must be registered by the bridge owner: [6](#0-5) 

However, once registered, **any user** can call `requestERC20Transfer` with it, and the accounting error is triggered on every call.

### Impact Explanation

In lock/unlock mode (`modeMintBurn = false`), the source bridge holds registered tokens as collateral backing the counterpart bridge's releases. With a FoT token at rate `r`:

- Source bridge receives: `(_value + _feeLimit) × (1 − r)`
- After fee/refund payouts, bridge retains: `(_value + _feeLimit) × (1 − r) − _feeLimit`
- Counterpart bridge releases: `_value`
- **Net shortfall per transfer:** `(_value + _feeLimit) × r`

Repeated transfers drain the counterpart bridge's ERC20 reserves by the FoT rate on every bridging operation. The corrupted value is the `valueOrTokenId` field in the `RequestValueTransfer` event — it is set to the nominal `_value` rather than the actual net amount the source bridge holds after the FoT deduction.

In mint/burn mode (`modeMintBurn = true`), the `burn(_value)` call at line 94 will revert because the bridge's actual balance is less than `_value` after FoT deductions, so that path self-protects via revert. The lock/unlock path has no such protection. [7](#0-6) 

### Likelihood Explanation

The bridge owner must register the FoT token. This is a semi-trusted action, but:
1. The owner has no on-chain mechanism to detect whether a token charges transfer fees.
2. Some tokens are upgradeable and can become FoT after registration.
3. Once registered, any unprivileged user triggers the accounting error on every `requestERC20Transfer` call.

### Recommendation

In `requestERC20Transfer`, measure the actual received balance before and after `safeTransferFrom` and pass the net received amount (minus `_feeLimit`) as the bridged value:

```solidity
function requestERC20Transfer(
    address _tokenAddress, address _to,
    uint256 _value, uint256 _feeLimit, bytes memory _extraData
) public {
    uint256 _before = IERC20(_tokenAddress).balanceOf(address(this));
    IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
    uint256 _after = IERC20(_tokenAddress).balanceOf(address(this));
    uint256 actualReceived = _after.sub(_before);
    require(actualReceived >= _feeLimit, "insufficient received for fee");
    uint256 actualValue = actualReceived.sub(_feeLimit);
    _requestERC20Transfer(_tokenAddress, msg.sender, _to, actualValue, _feeLimit, _extraData);
}
```

Apply the same before/after balance pattern in `onERC20Received`. Alternatively, document that FoT tokens are explicitly unsupported and add a revert guard (e.g., check `balanceOf` delta equals `_value + _feeLimit`).

### Proof of Concept

Assume token `XYZ` charges a 10% FoT fee and is registered on the bridge in lock/unlock mode.

1. User calls `requestERC20Transfer(XYZ, bob, 100, 10, "")`.
2. `safeTransferFrom(user, bridge, 110)` executes; bridge receives `99` (10% deducted).
3. `_payERC20FeeAndRefundChange` pays `fee` to feeReceiver and `feeRefund` to user, totaling `10` tokens leaving the bridge. Bridge now holds `89`.
4. `RequestValueTransfer` event emits `valueOrTokenId = 100`.
5. Bridge operator observes the event and calls `handleERC20Transfer(..., 100, ...)` on the counterpart bridge.
6. Counterpart bridge transfers `100` tokens to `bob`.
7. **Result:** source bridge holds `89` tokens; counterpart bridge paid out `100`. Net loss of `11` tokens per transfer, accumulating until the counterpart bridge is drained. [1](#0-0) [2](#0-1) [3](#0-2)

    function _payERC20FeeAndRefundChange(address from, address _token, uint256 _feeLimit) internal returns(uint256) {

            require(_feeLimit >= fee, "insufficient feeLimit");
