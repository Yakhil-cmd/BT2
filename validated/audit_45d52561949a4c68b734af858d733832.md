### Title
Front-running `initialize`/`initialize_with_permission` to hijack the deterministic pool PDA and dictate an attacker-controlled initial price - (File: `programs/cp-swap/src/instructions/initialize.rs`)

### Summary
The `PoolState` address for a given `(amm_config, token_0_mint, token_1_mint)` triple is a fully deterministic PDA, and `initialize`/`initialize_with_permission` are open to any signer with no prior claim mechanism, mirroring the `SuperPool` root cause (predictable next-deployment address + unprotected creation), but here the analog manifests as pool-creation front-running rather than share-dilution.

### Finding Description
`create_pool` derives the pool address purely from public inputs: [1](#0-0) 

Because `amm_config`, `token_0_mint`, and `token_1_mint` are all public, any observer can precompute the exact `pool_state`, `token_0_vault`, `token_1_vault`, and `lp_mint` addresses for a token pair before the legitimate creator's transaction lands, exactly as the `SuperPool` address was predictable from the factory's deployer/nonce in the original report. `initialize` is callable by anyone (`creator: Signer<'info>`, no allowlist) and takes attacker-chosen `init_amount_0`/`init_amount_1`: [2](#0-1) [3](#0-2) 

The pool's initial price/liquidity is derived solely from whatever amounts land in the vaults during this call: [4](#0-3) 

Unlike the `SuperPool` case, the vaults here are PDAs (`POOL_VAULT_SEED`) that only the program itself can initialize via CPI-signed `create_or_allocate_account`/`initialize_account3` inside `create_token_account`, so an outside attacker cannot pre-fund the not-yet-existing vault with an SPL token donation the way a griefer could `transfer` tokens straight into a predictable `CREATE`-derived EOA/contract address in the Sherlock report. That specific "donate to inflate shares" vector is not reproducible verbatim. What is reproducible is the underlying primitive the report flags — a *predictable creation address with no protection against a competing creation call* — which here lets an attacker win the race to `initialize` the exact same `(amm_config, token_0_mint, token_1_mint)` PDA first, with an extreme, attacker-chosen `init_amount_0`/`init_amount_1` ratio (subject only to `lock_lp_amount = 100` and `CurveCalculator::validate_supply`). Once the attacker's transaction lands, the `PoolState` account is initialized, and the legitimate creator's subsequent `initialize` call for the same pair fails outright (the PDA/account is already initialized), permanently denying that specific pool-pair creation at a fair price and instead leaving the market with a pool whose starting price was unilaterally set by the attacker.

### Impact Explanation
This breaks core "create a fairly-priced pool" functionality for a given token pair/config combination: the first caller to win the race permanently determines the pool's genesis price and the intended creator can no longer create that pool at all (single PDA per pair+config). This matches the Sherlock M-3 classification rationale ("breaks core contract functionality, rendering the contract useless") even though the specific mechanic (share-dilution via ERC20 donation) does not carry over 1:1 due to PDA-gated vault creation.

### Likelihood Explanation
Any user monitoring the mempool/RPC for pending `initialize` calls (front-running is trivial and cheap on Solana, requiring only priority fees) can submit a competing `initialize` for the same `(amm_config, token_0_mint, token_1_mint)` with minimal `init_amount_0/1` values engineered to just clear `lock_lp_amount` (100) and `CurveCalculator::validate_supply`, at negligible cost.

### Recommendation
Add a creator-authorization or commit-reveal step to pool creation (e.g., require pool creation to go through a permissioned path per (config, pair), or let the intended creator "reserve" the PDA before the funded initialize call), and/or bound acceptable initial price ratios (oracle-checked or capped skew) so a racing attacker cannot set an arbitrary genesis price.

### Proof of Concept
Not independently verifiable/executable in this pass — I was only able to trace the account-derivation and initialize-flow code (`create_pool`, `initialize`, `create_token_account`) and confirm the PDA determinism and lack of creator gating; I could not run a live PoC against a validator in this session, and could not fully confirm whether any additional guard (e.g., `require_eq!(is_signer, true)` branch on mismatched `pool_account_info.key()`) is exercised by default clients to block this race, since that check is only hit `if pool_account_info.key() != expect_pda_address`, which is not the case for a standard client call using the canonical PDA.
