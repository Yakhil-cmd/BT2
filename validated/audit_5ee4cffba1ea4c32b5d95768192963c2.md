## Analog Found: `stake-update` in pox-5.clar Skips Reward Settlement When Changing Signers

### Title
Staker reward loss/miscount when switching signers via `stake-update` without settling old/new signer reward snapshots - (File: `stackslib/src/chainstate/stacks/boot/pox-5.clar`)

### Summary
The Truflation `migrateUser()` bug arises because stake is moved (`withdraw`) from an old owner to a new owner without first calling the reward-accounting hook (`updateReward`) for the correct account, permanently stranding rewards on the abandoned address. `pox-5.clar` contains the same structural pattern: `stake-update` [1](#0-0)  lets a staker move their locked STX from `old-signer-manager` to a new `signer-manager` mid-lock, and does so by calling `remove-staker-from-cycles` then `add-staker-to-signer-cycles` [2](#0-1)  **without** first calling `settle-rewards` / `settle-staker-rewards` for either the old or the new signer.

Contrast this with `update-bond-registration`, the contract's other "change signer mid-stream" function, which explicitly settles both signers' and the staker's reward snapshots *before* moving shares: [3](#0-2) 

That settle-then-move pattern exists precisely to prevent the reward-per-token accounting from being corrupted when share ownership moves between signer buckets mid-cycle — the exact class of bug reported in M-2 (moving position ownership without carrying/settling the earned-but-unclaimed reward state).

### Finding Description
In `update-bond-registration`, before shares are removed from `current-signer` and re-added to the new `signer`, the contract settles both the outgoing and incoming signer's global reward-per-token accumulator and the staker's personal snapshot against each:
```
(settle-rewards current-signer current-cycle (some bond-index))
(settle-rewards signer current-cycle (some bond-index))
(settle-staker-rewards current-signer current-cycle (some bond-index) tx-sender)
(settle-staker-rewards signer current-cycle (some bond-index) tx-sender)
``` [4](#0-3) 

This settlement is required because moving shares between signer buckets changes each signer's `shares-staked` total mid-cycle; without settling first, the reward-per-token math (which is a function of `earned / shares-staked` deltas since the last settlement point) becomes inconsistent for the departing signer's remaining reward accrual and for the staker's baseline (`rpt-paid`) on the new signer.

`stake-update` performs the analogous cross-signer share migration for plain (non-bond) STX stakers — moving `amount-ustx` shares from `old-signer` to `signer` — but has no equivalent `settle-rewards`/`settle-staker-rewards` calls: [5](#0-4) 

`add-staker-to-signer-cycles` is the same underlying primitive used by both `stake`, `stake-update`, and the bond-registration flow to update the per-cycle, per-signer share-staked maps that back the reward-per-token calculation (as seen used identically in the bond-registration path at lines 907-909 and 917-919 of the same file). Since `stake-update` mutates those same maps for the old and new signer without settlement, any STX-denominated reward accrual tied to signer share buckets (the same mechanism `getEarned`/`settle-rewards` service for bonds) would either be stranded on the old signer's un-settled snapshot or become computable against a corrupted baseline on the new signer.

### Impact Explanation
If plain STX stakers accrue signer-bucket rewards through the same `rpt`/`settle-rewards` machinery used for sBTC bond rewards (which the shared use of `add-staker-to-signer-cycles`/`remove-staker-from-cycles` strongly implies), then switching signers via `stake-update` mid-cycle would freeze or corrupt the staker's already-earned-but-unclaimed reward for that cycle on the old signer, and/or allow incorrect (potentially inflated or zeroed) reward computation against the new signer — matching the in-scope "sBTC rewards paid that were not earned or counted twice" / "temporary freezing of staked funds' rewards" impact class. This is High/Medium depending on whether funds become permanently unclaimable (Critical/High) or only temporarily stuck until the next settlement event naturally occurs (Medium).

### Likelihood Explanation
Likelihood is moderate: `stake-update`'s signer-change path is a normal, unprivileged, user-facing operation (not an admin/edge-case migration), so it would be triggered far more often than the Truflation scenario (which required key loss). Any staker who calls `stake-update` with a different `signer-manager` than their `old-signer-manager` mid-cycle would hit this code path.

### Recommendation
Add the same settlement calls used in `update-bond-registration` to `stake-update` before `remove-staker-from-cycles`/`add-staker-to-signer-cycles` execute: settle rewards for both `old-signer` and `signer` at `current-cycle`, and settle the staker's personal snapshot against both signers, using `bond-index none` (or whatever sentinel plain STX stakers use) to match the reward domain being mutated.

### Proof of Concept
Concrete reproduction requires exercising the reward-per-token accrual mechanism (`calculate-rewards`, `settle-rewards`, `get-earned`) against a plain STX staker (bond-index `none`) before and after a `stake-update` signer switch, analogous to the existing test `'bond signer update does not duplicate staker rewards on new signer'` [6](#0-5) , but there is no equivalent test present in the codebase for the `stake-update` path exercising signer changes together with reward accrual — this gap itself is corroborating evidence that the settlement step was omitted for that code path.

**Uncertainty**: I was not able to fully confirm within the available context whether plain (`bond-index none`) STX stakers actually accrue per-signer STX rewards through the same `settle-rewards`/`rpt` mechanism, or whether that reward machinery is exclusively used for sBTC bond rewards. This distinction determines whether the missing settlement calls in `stake-update` are a real reward-loss bug or a benign omission (if plain STX stake-update never touches reward-bearing state). Confirming this requires reading the full reward-accounting section of `pox-5.clar` (definitions of `settle-rewards`, `settle-staker-rewards`, `get-earned`, and how `bond-index: none` is treated in those functions), which was not available in the retrieved context.

(define-public (stake-update
        (signer-manager <signer-manager-trait>)
        (old-signer-manager <signer-manager-trait>)
        (cycles-to-extend uint)
        (amount-increase uint)
        (signer-calldata (optional (buff 500)))
    )
    (let (
            (signer (contract-of signer-manager))
            (old-signer (contract-of old-signer-manager))
            (current-info (unwrap! (get-staker-info tx-sender) ERR_NOT_STAKING))
            ;; This is the first cycle where their STX would be unlocked
            (prev-unlock-cycle (+ (get first-reward-cycle current-info)
                (get num-cycles current-info)
            ))
            (unlock-cycle (+ prev-unlock-cycle cycles-to-extend))
            (new-lock-amount (+ (get amount-ustx current-info) amount-increase))
            (current-cycle (current-pox-reward-cycle))
            (first-reward-cycle (+ current-cycle u1))
            (num-cycles (- unlock-cycle current-cycle u1))
        )
        ;; Reject during the prepare phase since next-cycle data is mutated
        (try! (verify-not-prepare-phase))

        ;; Validate that the staker can join this signer
        (try! (signer-manager-validate-stake signer-manager tx-sender
            first-reward-cycle num-cycles new-lock-amount u0 false
            signer-calldata
        ))

        ;; Validate that `old-signer-manager` matches their current signer
        (asserts! (is-eq old-signer (get signer current-info))
            ERR_INVALID_OLD_SIGNER_MANAGER
        )

        ;; The signer must have been registered already, and its signer key
        ;; grant must still be active.
        (try! (verify-signer-key-grant signer
            (unwrap! (get-signer-info signer) ERR_SIGNER_NOT_FOUND)
        ))

        ;;  lock period must be in acceptable range.
        (asserts! (check-pox-lock-period num-cycles) ERR_INVALID_NUM_CYCLES)

        ;; Must have enough unlocked STX
        (asserts! (>= (get unlocked (stx-account tx-sender)) amount-increase)
            ERR_INSUFFICIENT_STX
        )

        ;; Remove the staker from all existing cycles
        (try! (remove-staker-from-cycles tx-sender (+ u1 current-cycle)
            (- prev-unlock-cycle current-cycle u1) true
        ))

        (try! (add-staker-to-signer-cycles tx-sender signer (+ u1 current-cycle)
            num-cycles new-lock-amount true
        ))

        (map-set staker-info tx-sender {
            amount-ustx: new-lock-amount,
            first-reward-cycle: (get first-reward-cycle current-info),
            num-cycles: (+ (get num-cycles current-info) cycles-to-extend),
            signer: signer,
        })

test('bond signer update does not duplicate staker rewards on new signer', () => {
  const signer1 = testSigner.identifier;
  const signer2Contract = deployTestSigner('bond-update-dup-signer-2');
  const signer2 = signer2Contract.identifier;
  const aliceSbtc = 480000n;

  registerSigner();

  txOk(
    pox5.setupBond({
      bondIndex: 0n,
      targetRate: 1500n,
      stxValueRatio: 10n,
      minUstxRatio: 100n,
      earlyUnlockBytes: new Uint8Array(),
      allowlist: [{ maxSats: aliceSbtc, staker: alice }],
    }),
    deployer,
  );
  txOk(
    pox5.registerForBond({
      bondIndex: 0n,
      signerManager: signer1,
      amountUstx: stxToUStx(50_000),
      btcLockup: err(aliceSbtc),
      signerCalldata: null,
    }),
    alice,
  );
  txOk(
    sbtc.transfer({
      recipient: pox5.identifier,
      amount: 1200n,
      sender: deployer,
      memo: null,
    }),
    deployer,
  );

  mineUntil(rov(pox5.rewardCycleToBurnHeight(1n)) + HALF_CYCLE_LENGTH);
  txOk(pox5.calculateRewards([0n]), deployer);

  txOk(
    pox5.updateBondRegistration({
      signerManager: signer2,
      signerCalldata: null,
      oldSignerManager: signer1,
    }),
    alice,
  );

  // Alice has already accrued the entire 1200 on signer1. Switching signers
  // before claiming should not create a phantom claimable balance on signer2.
  expect(rov(testSigner.getEarnedStakerRewards(alice, 1n, 0n))).toBe(1200n);
  expect(rov(signer2Contract.getEarnedStakerRewards(alice, 1n, 0n))).toBe(0n);
});
