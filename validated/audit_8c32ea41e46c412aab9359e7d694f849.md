### Title
Stack-scoped ApiClient tokens can read CI status of any stack via CCMenu endpoint - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController#show` bypasses the stack-scoping enforcement that every other API endpoint relies on, letting a token that is only authorized for one stack read the CCTray/CCMenu build status of any stack in the installation.

### Finding Description
Every other API controller resolves the target stack through `Shipit::Api::BaseController#stack`, which is deliberately scoped to the calling `ApiClient`: [1](#0-0) 

`stacks` restricts the visible set to `Stack.where(id: current_api_client.stack_id)` when the client has a `stack_id`, otherwise falls back to `Stack.all`. This is the codebase's authorization equality: *stack(s) the ApiClient is bound to == stack(s) its token may touch*. This scoping is exercised and asserted elsewhere, e.g. "an api client scoped to a stack will only see that one stack" and the repo-filtered `#index` test, confirming `stack_id` scoping is a real, tested security boundary.

`CCMenuController`, however, overrides `stack` to resolve the record directly, without going through the scoped `stacks` relation: [2](#0-1) 

`require_permission :read, :stack` only checks that the string `"read:stack"` is present in `ApiClient#permissions` — it does not check which stack the permission applies to: [3](#0-2) 

So any token that has `read:stack` (which is exactly the permission granted to every CCMenu client created by `CCMenuUrlController#client`) can be replayed against `GET /api/stacks/*stack_id/ccmenu` for a **different** `stack_id` than the one it was scoped to, and `CCMenuController#stack` will happily resolve and render that other stack's data via `Stack.from_param!(params[:stack_id])`, ignoring `current_api_client.stack_id`. [4](#0-3) 

### Impact Explanation
This breaks the binding "a stack a token authorises versus a stack it touches." An attacker who obtains (or is legitimately issued) a CCMenu token scoped/intended for stack A — the token is passed as a URL query parameter (`?token=...`), so it is exposed in browser history, CI status-bar tools, proxy logs, etc. — can query `/api/stacks/<owner>/<repo>/<environment>/ccmenu` for any other stack B and receive that stack's build/deploy status (last deploy id, whether a deploy is running, when it ended). This is an unauthorized cross-stack read of deploy/task state, matching the High-impact category "unauthorized read of stack state ... deploy output."

### Likelihood Explanation
Any holder of a valid `read:stack`-permission token (the only kind CCMenu issues) can trivially change the `stack_id` route segment to enumerate other stacks; no additional privilege or session is required beyond possessing one legitimately-issued CCMenu token. Because stack identifiers (`owner/repo/environment`) are often predictable/enumerable, this is straightforward to exploit.

### Recommendation
Change `CCMenuController#stack` to reuse the scoped `stacks` relation from `BaseController` instead of an unscoped `Stack.from_param!`, i.e. `stacks.from_param!(params[:stack_id])`, so that a stack-scoped `ApiClient` cannot resolve stacks outside its `stack_id`.

### Proof of Concept
1. A user calls `GET /ccmenu/*stack-A` (`CCMenuUrlController#fetch`), which creates/reuses an `ApiClient` named "CCMenu Client" with permission `read:stack` and returns a URL containing `?token=<T>` for stack A.
2. An attacker who obtains `<T>` (e.g., from a leaked CI dashboard URL) issues `GET /api/stacks/*stack-B/ccmenu?token=<T>` for an unrelated stack B.
3. `CCMenuController#authenticate_api_client` finds a valid `ApiClient` via `ApiClient.authenticate(params[:token])`.
4. `require_permission :read, :stack` passes because the client has `read:stack` in its permissions list (permission is not stack-specific).
5. `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly (bypassing `BaseController#stacks`'s scoping), resolving stack B even though the token/client was only ever meant to be used against stack A.
6. The response renders stack B's build status (`app/views/shipit/ccmenu/project.xml.builder`), leaking cross-stack deploy state to a token holder who was not authorized for stack B.

# frozen_string_literal: true

require 'uri'

module Shipit
  class CCMenuUrlController < ShipitController
    def fetch
      uri = URI(api_stack_ccmenu_url(stack_id: stack.to_param))
      uri.query = { 'token' => client.authentication_token }.to_query
      render(json: { ccmenu_url: uri.to_s })
    end

    private

    def client
      @client ||= ApiClient.create_with(permissions: %w[read:stack])
                           .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
    end

    def stack
      @stack ||= Stack.from_param!(params[:stack_id])
    end
  end
