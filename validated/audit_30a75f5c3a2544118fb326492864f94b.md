### Title
Asset `spender_attested` / `transfer_condition` restrictions can permanently freeze AA-held asset balances - (File: validation.js)

### Summary
An asset issuer can define an asset with `spender_attested: true` and/or an arbitrary `transfer_condition`. These restrictions are enforced on *every* transfer of the asset, not just the initial issuance, and the definer can change the attestor whitelist at any time via an `asset_attestors` message. If an AA (a "smart contract" in Obyte) accepts deposits of such an asset from users in order to later forward/refund it to arbitrary recipient addresses, the AA's own outgoing payment is a normal `payment` message that is fully re-validated the same way as a user payment. If the recipient address the AA needs to pay is not on the attestor list (or does not satisfy the `transfer_condition`), the AA's payment fails validation and bounces, permanently trapping the asset balance inside the AA with no way to route around the restriction — directly analogous to EigenLayer's `thirdPartyTransfersForbidden` disabling `DelegationManager` withdrawals.

### Finding Description
When an asset defines `spender_attested: true`, `validatePaymentInputsAndOutputs` requires that **all** output addresses of any transfer of that asset be attested by the asset's attestor list before the payment is considered valid: [2](#0-1) 

The attestor list itself is fully controlled by the asset's `definer_address` — only the definer may add/remove attestors via an `asset_attestors` message, and this can be done at any point after the asset is created: [3](#0-2) 

Similarly, an asset can carry an arbitrary `transfer_condition` (an oscript-like Definition expression) which is evaluated on every transfer, independent of who currently holds the coins: [4](#0-3) 

This is unrelated to the initial acceptance of the deposit into the AA (which the definer/attacker could arrange to satisfy, e.g. by getting the AA's own address attested or the deposit condition satisfied) — the risk is on the *outgoing* leg. When an AA composes an outgoing `payment` message to any output address, that message goes through the exact same protocol-level validation via `validateAndSaveUnit` inside `aa_composer.js`'s `sendUnit`, which calls `completePaymentPayload` and then commits the unit; if validation fails, the AA simply `bounce()`s and the funds remain unspent in the AA's balance: [5](#0-4) 

There is no mechanism for the AA (or a "withdrawer" analog) to route the asset through an intermediary or otherwise bypass the third-party-controlled attestor/condition check — the check is a network consensus rule enforced identically for every author, exactly like EigenLayer's `staker == withdrawer || !thirdPartyTransfersForbidden` check that made `DelegationManager` unable to withdraw to any third party.

### Impact Explanation
Any AA (acting like a smart-contract vault, DEX, bridge, or payment router) that accepts a `spender_attested` or `transfer_condition`-restricted asset can have its balance of that asset become permanently unspendable the moment the definer removes an intended recipient from the attestor list (or the condition can never be satisfied for arbitrary recipients). Because the AA's state machine has already recorded the deposit (state vars updated) but the corresponding payout unit is rejected and bounced, user funds held by the AA in that asset are frozen indefinitely — a direct loss/freezing of AA funds, matching the "Medium" impact class of the original report (funds cannot be withdrawn).

### Likelihood Explanation
Any user or the asset issuer itself can trigger this: simply define (or already control) an asset with `spender_attested: true` or a restrictive `transfer_condition`, get users/AAs to accept it as a valid input, and then (for `spender_attested`) publish an `asset_attestors` update removing the AA's target recipients, or (for `transfer_condition`) design the condition so it can never be satisfied for outputs other than the definer/attestor set. No special privileges beyond being the asset's definer (a role any user can create for themselves by issuing the asset) are required, and the AA logic itself does not need to be flawed — this is a property of the underlying asset system that any single-poster asset-issuer can weaponize against any AA that handles third-party assets generically.

### Recommendation
- When an AA (or wallet) accepts a non-base asset as a deposit that it intends to later forward to arbitrary third-party addresses, require/validate upfront that the asset has `spender_attested: false`, no `transfer_condition`, and `cosigned_by_definer: false`, rejecting deposits of assets with these restrictions rather than accepting them into managed balances.
- Consider exposing a query helper (e.g., a getter or documented pattern in AA templates) that lets AA authors detect these restrictive asset flags before accepting deposits, to avoid inadvertently building payment routers/vaults that can be permanently frozen by an asset definer's later `asset_attestors` update.
- Document clearly for AA developers that `spender_attested`/`transfer_condition` are consensus-level, definer-controlled restrictions that apply to *every* future transfer, not just issuance, so that AAs cannot assume a successfully-accepted deposit implies a successfully-payable withdrawal.

### Proof of Concept
1. Attacker creates asset `A` with `spender_attested: true` and an initial attestor list that includes some victim AA's address `AA_addr` (satisfying `validateAttestorListUpdate` since attacker is `definer_address`) — see `validation.js:2829-2848`.
2. Attacker (or any user) sends asset `A` to `AA_addr` as a deposit trigger; validation passes because `AA_addr` is currently attested (`validation.js:2630-2641`), and the AA's state logic records the deposit and schedules a future payout to some third-party recipient `R` (e.g., a withdrawal address chosen by the depositor).
3. Attacker publishes a new `asset_attestors` message (single-authored by `definer_address`, per `validation.js:2841`) that removes `R` (and any address not controlled by the attacker) from the attestor list.
4. When the AA's logic later composes the payout `payment` message with output address `R`, `aa_composer.js`'s `sendUnit`/`completePaymentPayload` builds and validates the unit; `validatePaymentInputsAndOutputs` rejects it because `R` is not attested (`validation.js:2634-2638`), so `validateAndSaveUnit` fails and the AA `bounce()`s (`aa_composer.js:1405-1413`).
5. Because bouncing simply reverts the response but does not change the fact that the AA's balance already includes the deposited asset `A`, and every future attempt to pay it to `R` (or any non-attested address) will fail identically, the deposited `A` tokens are permanently stuck in the AA — unauthorized freezing of funds with no recovery path, analogous to the cited EigenLayer `DelegationManager` issue.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");

			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
