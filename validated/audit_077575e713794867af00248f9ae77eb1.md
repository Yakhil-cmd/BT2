## Title
AMM-style AA swap patterns compute output from live pool balances with no slippage protection, letting a trigger sender be sandwiched via front-run/back-run trigger units - (File: test/samples/uniswap_like_market_maker.oscript)

## Summary
The reported bug is that `costToHeal()`/`heal()` compute a payment amount from a live, manipulable price quote and execute the trade against that same live price with no bound/slippage check, letting an attacker sandwich the victim. The same bug class exists in Obyte's own reference AMM pattern for Autonomous Agents: the `exchange bytes to asset` / `exchange asset to bytes` cases compute the output amount from the AA's *current* balances at the moment the trigger executes, and the trigger sender has no way to specify a minimum acceptable output. Because AA triggers are ordinary units whose processing order is deterministic and known in advance once main-chain-stable, an attacker can insert a manipulative trigger before the victim's trigger executes, changing the pool ratio, and reverse it afterward — a classic sandwich attack with no on-chain protection.

## Finding Description
In `test/samples/uniswap_like_market_maker.oscript` the swap logic is: [1](#0-0) [2](#0-1) 

Both cases derive `$amount` purely from `balance[$asset]` and `balance[base]` read *at execution time* of the trigger unit, using a constant-product formula (`$p = $asset_balance * $bytes_balance`). There is no `min_amount`/`max_slippage` parameter in `trigger.data` that the AA checks against before paying out, unlike the `invest in MM` case which does at least assert `$expected_asset_amount != trigger.output[[...]]` for LP shares. A user who wants to swap must decide how much to send *before* the trigger stabilizes, based on the pool state they observe at composition time — exactly the "quote now, execute later, no bound" pattern from the reported issue.

The processing order of triggers landing in the same MCI is fully deterministic and derivable in advance: [3](#0-2) [4](#0-3) 

Both queries order pending/competing triggers by `(mci, level, unit, address)`. Since `level` is derived from the parent set an author chooses when composing their unit, and units are visible on the DAG (in `storage.assocUnstableUnits` / broadcast to peers) before they are stable, an attacker who observes the victim's pending swap-trigger unit can:
1. Compose their own manipulative swap trigger targeting the same AA, choosing parents/tips that keep its `level` lower than the victim's unit (or otherwise controlling its position in the eventual `ORDER BY level, unit` sort for the MCI where both land), so it is guaranteed to execute first.
2. That manipulative trigger shifts `balance[$asset]`/`balance[base]` unfavorably for the victim just before the victim's swap executes with its pre-computed `$amount` expectation, but the AA has no mechanism to reject the trade or cap the slippage.
3. After the victim's trigger executes at the worse rate, the attacker submits a second trigger (also ordered before any other party can intervene, since it only needs to land in a later or the same MCI) to reverse the price shift and capture the difference, completing the sandwich.

This mirrors the reported vulnerability precisely: a two-step "compute expected amount → execute trade" pattern with an unauthenticated, unbounded price source (the AA's own live balance) and no slippage guard, reachable by any unprivileged AA trigger sender.

## Impact Explanation
Any AA implementing this widely-referenced constant-product/AMM pattern (which ships as ocore's own official sample) suffers direct value extraction from ordinary swap participants: victims receive materially less output (or pay materially more) than the rate they observed when composing their unit, with the difference captured by the attacker who can engineer trigger ordering. This is a concrete unauthorized-value-transfer / fund-loss condition for AA users, not merely a resource/DoS issue, satisfying the "AA fund loss" criteria.

## Likelihood Explanation
Any user of a network node can observe unstable/pending units in the DAG before they are stable, and any unprivileged address can post a competing trigger unit to the same AA. Because trigger execution order is a fully deterministic function of `(mci, level, unit, address)` that is computable by anyone before stabilization, an attacker does not need any privileged position — only the ability to post two ordinary payment units to a known public AMM AA address, making this readily and repeatedly exploitable against any deployed AA that follows the documented pattern.

## Recommendation
Update the sample/reference AMM pattern (and, by extension, the documentation guiding AA authors) to require a `trigger.data` slippage-protection parameter — e.g., `min_amount`/`max_price` — analogous to what the `invest in MM` case already does, and `bounce()` if the computed output would violate it:
```
if ($amount < trigger.data.min_amount)
    bounce('slippage exceeded');
```
Additionally, document for AA authors that trigger execution order (`level`, `unit` hash) is attacker-influenceable/predictable, so any price-sensitive AA logic must include an explicit, trigger-specified bound rather than relying on the AA's live state as an implicit "quote."

## Proof of Concept
1. Deploy the `uniswap_like_market_maker.oscript` AA (or any AA following its `exchange bytes to asset` pattern) with an existing bytes/asset balance ratio.
2. Victim observes the current ratio, computes an expected `$amount` off-node, and broadcasts a swap-trigger unit sending `>1e5` bytes.
3. Attacker sees the victim's unstable unit on the DAG, and immediately composes and broadcasts their own swap-trigger unit (large asset sale) built on parents chosen so its `level` sorts before the victim's unit for the eventual shared MCI (per the `ORDER BY level, unit` logic in `main_chain.js`/`aa_composer.js`).
4. When both units stabilize in the same MCI, the attacker's trigger executes first (per deterministic ordering), shifting `balance[base]`/`balance[$asset]`.
5. The victim's trigger then executes against the shifted balances, receiving a smaller `$amount` of asset than expected, with no `bounce()` check to prevent it.
6. Attacker posts a second trigger reversing their initial trade, realizing a profit equal to the value extracted from the victim's swap.
