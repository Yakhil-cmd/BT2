### Title
Cross-tenant webhook forgery via unmatched `repository.owner.login` and `repository.full_name` fields - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In a multi-organization Shipit deployment (multiple GitHub Apps configured for different organizations, as documented for the `Shipit.github(organization:)` scheme), `WebhooksController#verify_signature` selects which organization's webhook secret validates the inbound HMAC signature using `repository_owner`, a value read straight out of the unverified JSON payload. Once the signature check passes, the actual event handlers (`PushHandler`, `StatusHandler`, PR handlers, etc.) resolve the target `Stack`/`Repository`/`Commit` using a *different* field from the same payload: `repository.full_name`. Nothing binds these two fields together, so a party who legitimately holds the webhook secret for **one** onboarded organization can forge a payload whose `repository.owner.login` matches their own org (so the signature check passes) while `repository.full_name` names a repository belonging to a **different, unrelated** organization also hosted on the same Shipit instance.

### Finding Description
`WebhooksController` verifies inbound webhooks like this: [1](#0-0) 

`repository_owner` is derived purely from attacker-supplied JSON, before any cryptographic check has occurred: [2](#0-1) 

`Shipit.github(organization: repository_owner)` selects the `GitHubApp` instance (and thus the `webhook_secret`) for that specific claimed organization: [3](#0-2) 

The Shipit engine explicitly supports and documents hosting multiple independent GitHub organizations behind one instance, each with its own app/webhook secret: [4](#0-3) 

Once `verify_signature` passes, `WebhooksController#create` dispatches the *entire unverified payload* to every handler for the event: [5](#0-4) 

Every handler resolves the target repository/stack from a **separate** field, `repository.full_name`, with no cross-check against the `repository.owner.login`/`organization.login` value that was used to pick the signing secret: [6](#0-5) [7](#0-6) [8](#0-7) 

Binding that should hold: `repository_owner` (the field authenticated by the HMAC signature check) `== owner(repository.full_name)` (the field the handlers actually act on). The engine never enforces this equality — it is exactly the same class of bug as the hardcoded-address report: a value that gates a trust decision (which secret authorizes the request) is disjoint from the value that is actually acted upon (which tenant's data gets mutated).

### Impact Explanation
An attacker who is a legitimate GitHub App installer/administrator for **Organization A** (and therefore knows Organization A's `webhook_secret`, which they are entitled to configure/rotate on their own installation) can sign an arbitrary payload with that secret, set `repository.owner.login` (or `organization.login`) to `"OrganizationA"` to pass `verify_signature`, and set `repository.full_name` to `"OrganizationB/some-repo"` — a repository belonging to a completely different tenant on the same Shipit instance that Organization A has no access to. This is a **cross-repository write**: the forged webhook can inject status updates onto arbitrary commits of Organization B's stacks (`StatusHandler#process` calls `commit.create_status_from_github!(params)` for any `sha` in the DB matching the attacker-chosen value) or trigger sync/provisioning flows scoped to Organization B's stacks (`PushHandler`, `check_suite`, pull-request archive/unarchive handlers), all without ever holding a credential for Organization B.

### Likelihood Explanation
This requires a multi-organization Shipit configuration (explicitly documented and supported by the engine) and requires the attacker to control/know the webhook secret of at least one onboarded organization — a credential they legitimately possess for their own tenant, not a credential belonging to the victim tenant. Given that Shipit is designed to be a shared, multi-tenant deploy platform (the very reason the multi-org config schema exists), any customer/organization onboarded onto a shared instance can mount this attack against any other tenant on the same instance. No `ApiClient` token, session, or victim-owned secret is required — only the attacker's own legitimately-provisioned webhook secret for their own organization.

### Recommendation
After the HMAC signature is verified, cross-check that the organization implied by `repository.full_name` (and any other repository/organization identifiers used later by handlers) matches the `repository_owner`/`organization` value that authenticated the request, and reject the webhook (422) on mismatch. Alternatively, resolve the target `Repository`/`Stack` using the already-authenticated organization identity rather than re-parsing an unrelated field from the same untrusted payload.

### Proof of Concept
1. Deploy Shipit configured with two organizations, e.g. `OrgOne` and `OrgTwo`, each with its own GitHub App and `webhook_secret` (matching `test/dummy/config/secrets_double_github_app.yml`), each with stacks tracking their own repos.
2. As an attacker who administers `OrgOne`'s GitHub App installation, craft a JSON payload for a `status` event:
```json
{
  "repository": { "owner": { "login": "OrgOne" }, "full_name": "OrgTwo/victim-repo" },
  "sha": "<sha of a commit belonging to an OrgTwo stack>",
  "state": "success",
  "context": "ci/attacker",
  "target_url": "https://attacker.example.com"
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1 of raw body using OrgOne's webhook_secret>` and POST it to `/github/webhooks` (or wherever `WebhooksController` is mounted) with `X-Github-Event: status`.
4. `verify_signature` calls `Shipit.github(organization: "OrgOne")` (from `repository.owner.login`) and the signature validates successfully because it was signed with OrgOne's secret.
5. `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`, which uses `payload['sha']` directly (unrelated to org matching) to look up and mutate a commit belonging to `OrgTwo`'s stack — a write to a tenant the attacker never authenticated against.

**Uncertainty**: I could not fully verify from the index whether the production routing config mounts a single shared `/github/webhooks` endpoint for all organizations versus per-organization endpoints (this would affect whether the attack requires guessing the correct endpoint), nor could I confirm every downstream handler's exact mutation semantics (e.g., `check_suite`/`membership` handlers) since some handler files were not returned by the index. A Devin session with full repository access would be needed to confirm route mounting and enumerate all handler impacts precisely.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
