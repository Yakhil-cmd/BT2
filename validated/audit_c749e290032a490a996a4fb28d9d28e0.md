### Title
Webhook Signature Verified Against `repository.owner.login`, But `status` Handler Trusts Global `sha` Match — Cross-Organization Forged CI Status Enables Unauthorized Deploy - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to validate a webhook signature against using the payload's `repository.owner.login` (or `organization.login`) field. [1](#0-0) [2](#0-1)  But once verified, the `status` event handler acts on a completely different, unscoped field: it matches commits purely by `sha` across the entire `Commit` table, with no check that the commit belongs to a repository owned by the organization whose secret validated the request. [3](#0-2)  This mirrors the report's bug class — verifying/aggregating against the wrong field/quantity instead of the one that actually matters for the action taken.

### Finding Description
Shipit supports multi-tenant configuration where each GitHub organization has its own GitHub App and its own `webhook_secret`. [4](#0-3)  `Shipit.github(organization:)` looks up the app/secret keyed by organization name. [5](#0-4) 

In `WebhooksController`:
```
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [6](#0-5) 

This correctly proves that the request's HMAC matches the secret owned by whichever organization is named in `repository_owner`. Since the attacker owns that organization's GitHub App/secret (it's their own org), they can self-sign an arbitrary JSON body containing any other fields they like — the signature only proves "this org's secret produced this exact byte stream," not "this org owns the repository this payload claims to reference."

Once verification passes, `create` dispatches the parsed body to handlers for the event type:
```
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [7](#0-6) 

For `status` events, `StatusHandler#process` does:
```
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 
Note there is no reference to `repository.full_name`/`repository.owner` at all here — any commit anywhere in the Shipit instance sharing that `sha` is affected, regardless of which stack/repository/organization it belongs to. `create_status_from_github!` writes a `Status` record directly from attacker-supplied `state`, `description`, `target_url`, `context`, and `created_at`. [8](#0-7)  Commit `deployable?` and CI gating are derived from these `Status` records' `state` (verified by tests asserting `deployable?` is true when status is `success`). [9](#0-8) 

**The binding that is broken:** `organization authenticated (repository.owner.login used to pick the webhook secret) == organization/repository actually written (commit matched only by sha, in `StatusHandler`)`. Before the attacker's request, these coincide because GitHub itself signs and routes hooks per-installation. After a forged request from an attacker who legitimately controls their own org's GitHub App/secret, the two sides diverge: the verified organization is the attacker's own, but the entity mutated (a `Commit`/`Status`) can belong to any other organization's stack whose commit happens to share the same `sha`.

Because git commit SHAs are content-addressed, an attacker can trivially reproduce an identical SHA to a target commit by forking/cloning a public repository being deployed via Shipit (or copying the tree/parent/author/committer/timestamps of a known target commit) into their own attacker-owned repository/organization, then firing a `status` webhook that GitHub (or a hand-crafted request signed with their own secret) sends for that SHA.

The `push` handler (`PushHandler`) exhibits the same pattern (`Repository.from_github_repo_name(payload.dig('repository','full_name'))`, a field distinct from `repository_owner` used for signature routing) [10](#0-9) [11](#0-10) , but its downstream effect (`GithubSyncJob`) re-fetches commits from the real GitHub API scoped to the stack's actually-configured `repository.owner` [12](#0-11) , so it is self-correcting and not exploitable for data injection — only for triggering excess sync jobs (out of scope: rate limiting/resource exhaustion). The `status` handler has no such re-verification step, making it the concretely exploitable variant.

### Impact Explanation
A forged `success` status can make an otherwise unreviewed/unbuilt commit `deployable?` in a victim organization's stack, enabling an unauthorized deploy through Shipit's normal deploy flow — this maps directly to the "unauthorized deploy" Critical impact category. It also allows an attacker to poison CI state (`failure`/`error`) on a victim's commits, disrupting the victim's release process, and to write attacker-controlled `description`/`target_url` content that will be rendered in the victim's UI.

### Likelihood Explanation
Exploitation only requires the attacker to control a repository/organization already configured in the target Shipit instance's multi-org GitHub App list (a legitimate but low-privilege tenant, explicitly documented as a supported configuration) — no access to the victim's GitHub org, no Shipit session, and no `ApiClient` token is required. Reproducing an identical commit SHA is straightforward for public repositories or any repository whose git history the attacker can access/fork. This is a realistic, unprivileged-attacker path.

### Recommendation
`StatusHandler` (and any other handler that does not already scope by `repository.full_name`) must verify that the matched `Commit`'s stack belongs to the same repository/organization that the payload — and the verified signature — actually asserts, e.g., by joining through `Repository.from_github_repo_name(payload.dig('repository','full_name'))` and restricting the `Commit.where(sha:)` lookup to that repository's stacks, mirroring the base `Handler#stacks`/`#repository_name` helper already used by other handlers. More generally, `repository_owner` used in `verify_signature` should be reconciled with (or ideally derived from) the same field each handler actually consumes, so the field covered by the signature routing and the field acted upon can never diverge.

### Proof of Concept
1. Configure/assume Shipit multi-org setup: attacker legitimately controls `github: { AttackerOrg: { webhook_secret: S_a, ... }, VictimOrg: { webhook_secret: S_v, ... } }`. [13](#0-12) 
2. Attacker forks/reproduces a commit from `VictimOrg/victim-repo` that Shipit already tracks, obtaining an identical `sha` (git SHAs are content-addressed).
3. Attacker crafts a `status` event JSON payload:
   ```json
   {
     "repository": {"owner": {"login": "AttackerOrg"}, "full_name": "AttackerOrg/attacker-repo"},
     "sha": "<victim commit sha>",
     "state": "success",
     "description": "forged",
     "context": "ci/forced"
   }
   ```
4. Attacker signs this payload with `S_a` (their own legitimate secret) and sends it to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` resolves `repository_owner` to `AttackerOrg`, verifies against `S_a`, and passes. [1](#0-0) 
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the matching victim commit (owned by `VictimOrg`'s stack), and calls `create_status_from_github!(params)`, writing a `success` `Status` for it. [3](#0-2) 
7. The victim commit is now marked deployable in Shipit's UI/API without any CI having actually run in `VictimOrg`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
