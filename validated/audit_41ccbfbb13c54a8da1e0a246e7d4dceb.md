This confirms the finding: `CCMenuController#stack` bypasses the stack-scoping enforced by `BaseController#stack`. The base controller correctly restricts stack access to `current_api_client.stack_id`'s stack (via the `stacks` scope) at [1](#0-0) , but `CCMenuController` overrides `stack` to call `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` model at [2](#0-1) . ### Title
API token scoped to one stack can read CCMenu status of any other stack - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides the stack-lookup helper inherited from `BaseController` in a way that drops the per-token stack scoping, letting any `read:stack`-permissioned `ApiClient` — even one explicitly scoped to a single stack — read the CI status (`CCMenuController#show`) of every other stack in the installation.

### Finding Description
`ApiClient` records can optionally be scoped to a single stack via `belongs_to :stack, optional: true` [4](#0-3) . `BaseController` enforces this scoping generically: `stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` when the client is scoped, and the shared `stack` helper resolves `params[:stack_id]` only within that scoped relation [1](#0-0) . Multiple controllers (e.g. `StacksController#stack` in the same base flow) rely on this scoped `stack` method for authorization.

`CCMenuController`, however, defines its own private `stack` method that resolves `params[:stack_id]` directly against the unscoped `Stack` model, bypassing the `stacks` scoping entirely [2](#0-1) . The controller's only access control is the class-level `require_permission :read, :stack` declaration [5](#0-4) , which is implemented by `ApiClient#check_permissions!`, a purely string-based permission check (`"#{operation}:#{scope}"` membership in `permissions`) that has no knowledge of which stack the client is bound to [3](#0-2) .

This reproduces the report's bug class: the credential that is verified (the `ApiClient` token, authenticated via `ApiClient.authenticate(params[:token])` at [6](#0-5) ) authorizes an operation on a specific stack, but the actual resource acted upon (`params[:stack_id]`) is never checked against that authorization — exactly like `validatorSetId` being accepted from the untrusted submission input instead of being bound to the verified data. Here, "the stack a token authorizes" (its `stack_id` column) and "the stack it touches" (`params[:stack_id]`) are two different, unconnected values.

### Impact Explanation
Any holder of a `read:stack`-scoped token for one stack (e.g. obtained legitimately for a single project's CI badge, as generated by `CCMenuUrlController` at [7](#0-6) ) can enumerate `stack_id` values and read deploy/build status (`lastBuildStatus`, `activity`, lock state, etc.) for every stack managed by the Shipit instance, including stacks belonging to unrelated repositories/teams. This is an unauthorized read of stack state across scope boundaries — matching the "High" impact tier (escalation into authorization scope / unauthenticated read of stack state).

### Likelihood Explanation
Exploitation requires only a valid, low-privilege `read:stack` API token scoped to any single stack — no special access, no cryptographic secret guessing, and no interaction with GitHub credentials. The `stack_id` parameter is a simple path segment (`owner/repo/environment`), easily guessed or discovered from public repository names, making this trivially reachable by anyone already holding one legitimate scoped token.

### Recommendation
Change `CCMenuController#stack` to reuse the scoped lookup from `BaseController` (i.e., `stacks.from_param!(params[:stack_id])`) instead of querying `Stack` directly, so that stack-scoped `ApiClient` tokens cannot access stacks outside their `stack_id` binding.

### Proof of Concept
1. As an admin, create an `ApiClient` scoped to `stack: shipit-a` with permission `read:stack` (as done via `CCMenuUrlController#client`, `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(...)` [7](#0-6) ), obtaining its `authentication_token`.
2. As the attacker holding that token, issue: `GET /ccmenu/other-owner/other-repo/production?token=<token>`.
3. Because `CCMenuController#stack` resolves `Stack.from_param!(params[:stack_id])` without checking `current_api_client.stack_id`, the request succeeds and returns `other-owner/other-repo`'s CI status/XML, despite the token being scoped only to `shipit-a`.
