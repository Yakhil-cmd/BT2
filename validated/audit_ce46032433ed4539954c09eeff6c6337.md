### Title
Cross-organization webhook spoofing via unverified `repository.owner.login` used to select the signature-checking config while handlers act on `repository.full_name` - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App configuration (and therefore which `webhook_secret`) to verify the request against using `repository_owner`, a value read straight out of the still-unverified JSON body. The event handlers that actually mutate state (e.g. `PushHandler`) instead key off a *different* field of the same unverified body, `repository.full_name` (`Handler#repository_name`). In a multi-org deployment where at least one configured organization has no `webhook_secret` set, `GitHubApp#verify_webhook_signature` unconditionally returns `true` for that organization, letting an attacker "authenticate" as the org with no secret while writing to a stack belonging to a completely different, victim organization.

### Finding Description
`WebhooksController` runs signature verification as a `before_action`: [1](#0-0) 

The organization used to pick the verifying `GitHubApp` instance is derived directly from the raw JSON body, before any cryptographic check has occurred: [2](#0-1) 

`GitHubApp#verify_webhook_signature` treats a blank `webhook_secret` as automatically valid: [3](#0-2) 

Meanwhile the code path that actually performs the state change (`create` → handler dispatch) parses and forwards the *entire* body to handlers, and those handlers resolve the target `Repository`/`Stack` from a different, independently-attacker-controlled field: [4](#0-3) [5](#0-4) [6](#0-5) 

This engine explicitly supports multiple GitHub App configurations keyed by organization, each with its own independent `webhook_secret`, resolved via `Shipit.github_app_config`/`Shipit.github`: [7](#0-6) 

The fixture used in the engine's own test suite for this multi-org mode configures two organizations, `OrgOne` and `OrgTwo`, both with `webhook_secret` left blank: [8](#0-7) [9](#0-8) 

**The equality the code assumes but never enforces**: `organization authenticated by verify_signature (params.repository.owner.login)` == `repository actually written by the handler (params.repository.full_name)`. Nothing ties these two payload fields together, and the value used to pick the verifying secret is itself untrusted (it comes from the same unauthenticated body being verified). When any onboarded organization is configured with no `webhook_secret` — a state the engine's own multi-org fixture demonstrates as a supported configuration — `verify_webhook_signature` returns `true` for *any* signature header (or none at all) as long as `repository.owner.login` in the forged body matches that unsecured organization. The attacker can then set `repository.full_name` to `victim-org/victim-repo`, and the `PushHandler` (or any other handler keyed off `repository.full_name`) will process the event as if it legitimately originated from GitHub for the victim's stack.

### Impact Explanation
This breaks the authentication boundary between "which org's secret validated this webhook" and "which org's repository/stack gets mutated." An unauthenticated attacker who can send an HTTP POST to `/webhooks` can:
- Trigger `GithubSyncJob` for an arbitrary victim stack (`PushHandler#process` → `stack.sync_github`), forcing unscheduled syncs.
- Trigger `MembershipHandler` to create/modify `Team`/`Membership` records for a Team even when the actual authenticating org has nothing to do with that team, if `organization.login` is similarly divorced from the verified org, since membership webhook trust is likewise rooted only in the payload's own claimed organization.
- More broadly, any handler that derives its target `Stack`/`Repository`/`Team` from body fields distinct from the field used to select the verifying secret is reachable by an unauthenticated actor as long as one org in the deployment has no webhook secret configured (which the engine's own fixtures show as a valid supported state, and which `setup.md` documents as "optional").

This matches the "authentication bypass" / "cross-repository writes" tier: an unauthenticated request can cause writes/scheduling against a stack whose owning organization never authenticated the request.

### Likelihood Explanation
Likelihood depends on operator configuration: it requires at least one onboarded GitHub organization without a `webhook_secret` set (multi-org mode). The engine explicitly supports and tests this multi-org mode (`secrets_double_github_app.yml`), and `docs/setup.md` documents `webhook_secret` as "(optional)", meaning this is a realistic, engine-sanctioned deployment shape, not a contrived edge case. No credentials, session, or repository access are required — a raw unauthenticated HTTP POST to `/webhooks` is sufficient.

### Recommendation
- Do not use payload-supplied `repository.owner.login`/`organization.login` to select the verifying secret before the signature has been checked; instead verify the raw body against *every* configured organization's active secret (or bind webhooks to a specific stack via a per-hook secret) and only trust organization/repository claims in the body once a verification with a matching, correctly-scoped secret succeeds.
- Require `webhook_secret` to be present for all configured GitHub App organizations, or explicitly forbid verification from ever succeeding on a blank secret in multi-org mode.
- Ensure that the field used to authenticate (`repository.owner.login`) and the field used to select the target resource (`repository.full_name`) are cross-checked for consistency (e.g. assert `repository.full_name` starts with `#{repository.owner.login}/`) before dispatching to handlers.

### Proof of Concept
1. Deploy Shipit with multi-org GitHub App config, where `OrgOne` has `webhook_secret: nil` (as in `secrets_double_github_app.yml`) and a victim organization `VictimOrg` has a real, secret webhook secret and owns a tracked stack `VictimOrg/victim-repo`.
2. Send, without any secret/token:
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=0000000000000000000000000000000000000000

{
  "ref": "refs/heads/master",
  "after": "<attacker-controlled sha>",
  "repository": {
    "owner": { "login": "OrgOne" },
    "full_name": "VictimOrg/victim-repo"
  }
}
```
3. `repository_owner` resolves to `OrgOne`; `Shipit.github(organization: 'OrgOne')` has `webhook_secret` blank, so `verify_webhook_signature` returns `true` regardless of the (bogus) `X-Hub-Signature`.
4. `PushHandler#process` resolves the target via `repository.full_name` = `VictimOrg/victim-repo`, matching the real victim stack, and calls `stack.sync_github(expected_head_sha: ...)`, queuing `GithubSyncJob` for the victim's stack — even though the victim organization's secret was never checked.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
