## Analog Found

### Title
`liquidate-multi` batch atomicity is broken by `unwrap-panic` calls reachable inside `liquidate`, letting one malformed position abort liquidation of every unrelated victim bundled in the same call - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
The kubo advisory shows that a single attacker-controlled malformed block, decoded on a shared/batched code path with no panic recovery, terminates processing for everyone sharing that path (the whole daemon). Zest's `liquidate-multi` has the same shape: it is explicitly documented as fault-isolated ("Failed liquidations return error codes but don't revert entire batch"), but the `liquidate` function it maps over contains multiple `unwrap-panic` calls on attacker-influenceable data. A Clarity `unwrap-panic` failure aborts the *entire* transaction, not just the offending list element, so one bad position silently breaks the documented isolation guarantee and reverts every other liquidator's legitimate liquidation bundled in the same call.

### Finding Description
`liquidate-multi` is a thin wrapper around `map`: [1](#0-0) 

Each element is dispatched through `call-liquidate`, which calls `liquidate` directly and returns its raw response with no `match`/rescue wrapper: [2](#0-1) 

The doc comment on the function promises independent failure handling: "Failed liquidations return error codes but don't revert entire batch." That promise only holds if every internal failure path returns via `(err ...)` (which `map` tolerates), not via `unwrap-panic` (which aborts the whole tx, including any state changes already staged for earlier list items, since Clarity is atomic per-transaction).

`liquidate` itself contains several `unwrap-panic` calls that are evaluated eagerly inside `let` bindings, *before* the `asserts!` checks that would otherwise reject bad input gracefully:

- `scale-debt-for-liquidation` unwraps the index cache unconditionally: [3](#0-2) 

- The "other-debt-repayable" / "remaining-debt-to-repay" branches unwrap the same cache again: [4](#0-3) 

- The bad-debt socialization branch unwraps a bounded-list append: [5](#0-4) 

The index feeding these unwraps, `index-cache`, is itself a resource shared across all callers within the same block/timestamp: [6](#0-5) 
It is primed only for assets present in the specific borrower's own debt/collateral list, via `accrue-user-debts`/`accrue-user-collateral`: [7](#0-6) 

If any single position entry in a `liquidate-multi` batch reaches one of these `unwrap-panic` calls with an unpopulated/mismatched cache entry — e.g. a `debt-ft`/`collateral-ft` argument that does not correspond to an asset actually present in that borrower's `pos-full` list, or any other edge case that leaves `get-cached-indexes` returning `none` for that `aid` at the current `stacks-block-time` — the runtime panics and the entire `liquidate-multi` transaction reverts, undoing every other position's liquidation in the same call, even though those were correctly specified and would otherwise have succeeded.

### Impact Explanation
`liquidate-multi` exists specifically so a keeper/bot can process many unrelated unhealthy positions ("Each position can have different: borrower, collateral asset, debt asset") in a single atomic call for gas efficiency. When one position in that shared batch triggers `unwrap-panic`, all the other, unrelated borrowers' legitimate liquidations bundled in the same transaction are rolled back with them. This is a shared-batch state (the `map` over `positions`, and the underlying `index-cache`) primed/poisoned by one entry and consumed by all others — delaying liquidation of otherwise-liquidatable, unrelated victims' positions and increasing the window during which their collateral can deteriorate into unsocialized bad debt, i.e. temporary freezing of funds for the protocol/suppliers whose liquidation-driven debt repayment is denied for that block. This lands in the in-scope "temporary freezing of funds" impact category.

### Likelihood Explanation
No privileged role is required. Any account can call `liquidate-multi` with attacker-chosen position tuples; a malicious keeper (or a borrower deliberately steering their own position into the described edge state) only needs to get their poisoned entry included alongside a legitimate liquidator's batch to grief it, and the pervasive, uncaught use of `unwrap-panic` throughout `liquidate`'s hot path makes such an entry easy to construct.

### Recommendation
Wrap each `call-liquidate` invocation's internal logic so that all `unwrap-panic` calls on attacker/caller-influenced data (`get-cached-indexes`, `as-max-len?` on `fresh-debt-list`, etc.) are replaced with `unwrap!`/`match` returning a proper `(err ...)` value that `map` can carry per-element without aborting the whole transaction, matching the behavior the function's own doc comment already promises.

### Proof of Concept
1. Two unrelated borrowers, Alice and Bob, are both liquidatable in the same block.
2. A keeper submits `liquidate-multi` with `[position-for-Alice (correct debt-ft), position-for-Bob (debt-ft pointing to an asset not present in Bob's actual debt list / not yet cached this block)]`.
3. `map call-liquidate positions` executes Alice's liquidation successfully first (state staged), then reaches Bob's entry; `scale-debt-for-liquidation`'s `(unwrap-panic (get-cached-indexes debt-aid))` returns `none` and panics.
4. The Clarity VM aborts the whole transaction; Alice's otherwise-successful liquidation is rolled back along with Bob's, contradicting the function's documented "don't revert entire batch" guarantee and leaving both unhealthy positions unliquidated for that block.

(define-private (scale-debt-for-liquidation
  (debt-final uint)
  (coll-actual uint)
  (curr-scaled uint)
  (asset-id uint))
  (let (;; convert debt amount to scaled units for storage
        (borrow-index (get index (unwrap-panic (get-cached-indexes asset-id))))
        (scaled-debt (mul-div-down debt-final INDEX-PRECISION borrow-index))
        ;; cap at current debt (prevent over-repayment)
        (scaled-to-remove (if (> scaled-debt curr-scaled) curr-scaled scaled-debt))
        (debt-to-repay (mul-div-up scaled-to-remove borrow-index INDEX-PRECISION))
        ;; If debt was capped, scale collateral proportionally
        (coll-final (if (< scaled-to-remove scaled-debt)
                        (mul-div-down coll-actual scaled-to-remove scaled-debt)
                        coll-actual)))
    {
      scaled-to-remove: scaled-to-remove,
      debt-to-repay: debt-to-repay,
      coll-final: coll-final
    }))

;; Liquidates multiple positions atomically
;; Each position can have different: borrower, collateral asset, debt asset, and debt amount
;; Prevents front-running attacks that prevent bad debt socialization
;; Note: price-feeds not supported in batch - update prices separately or use individual liquidate()
;; Returns list of responses - one per position (ok/err)
;; Failed liquidations return error codes but don't revert entire batch
(define-public (liquidate-multi

                                      collateral-ft: <ft-trait>,
                                      debt-ft: <ft-trait>,
                                      debt-amount: uint,
                                      min-collateral-expected: uint })))
  (ok (map call-liquidate positions)))
