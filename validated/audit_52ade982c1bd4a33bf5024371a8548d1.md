### Title
Webhook signature verified against `repository.owner.login` but write actions target `repository.full_name` - organization/repository binding mismatch - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to validate an inbound webhook's HMAC signature using `repository.owner.login` (falling back to `organization.login`) from the JSON body, but every downstream `Webhooks::Handlers::Handler` subclass resolves the repository/stack it actually acts on from a different, independently-controlled field in the same body: `repository.full_name`.

### Finding Description
`verify_signature` picks the app config with: [1](#0-0) 
using [2](#0-1) 

`Shipit.github(organization:)` resolves the per-organization webhook secret from `secrets.github`: [3](#0-2) 

Once the signature check passes, `WebhooksController#create` dispatches the raw parsed JSON, unmodified, to every registered handler for the event: [4](#0-3) 

Every handler (push, pull_request, status, etc.) then determines the actual repository/stacks to operate on from `repository.full_name`, not `repository.owner.login`: [5](#0-4) [6](#0-5) 

There is no assertion anywhere that `repository.full_name` must begin with `repository.owner.login` (or `organization.login`). Because the HMAC covers the whole raw body, an attacker cannot forge a signature without a valid secret — but Shipit explicitly supports **multiple organizations, each with its own GitHub App and its own `webhook_secret`** (see the multi-org config in `test/dummy/config/secrets_double_github_app.yml`, and `Shipit.github_organizations` / `github_app_config` in `lib/shipit.rb`). This equality is the binding that should hold but doesn't:

`organization authenticated (repository.owner.login used to pick the secret) == repository actually written to (repository.full_name used by handlers)`

Before the fix, both sides are assumed equal because GitHub itself always sends a consistent payload. After an attacker who legitimately controls Org A's webhook secret (e.g., an admin of a GitHub App installed on Org A, which Shipit trusts and has configured) crafts a raw POST body where `repository.owner.login = "org-a"` but `repository.full_name = "org-b/target-repo"`, they can self-sign the payload with Org A's secret and pass `verify_signature`, while the handler layer acts on Org B's stacks — an organization/repository pair the attacker has no legitimate authority over.

### Impact Explanation
This lets an actor who is trusted only for Organization A cause writes/actions against Organization B's stacks in a multi-organization Shipit deployment, e.g.:
- Forcing `GithubSyncJob` to fetch and ingest commits into Org B's stack (`app/jobs/shipit/github_sync_job.rb`), using Shipit's own credentials for Org B, potentially triggering downstream deploy pipeline behavior for a repository the attacker doesn't control.
- Archiving/unarchiving Org B's review stacks via `ClosedHandler`/`ReopenedHandler` (`app/models/shipit/webhooks/handlers/pull_request/closed_handler.rb`, `reopened_handler.rb`).
- Creating/mutating `Team`/`User` records via the `membership` handler under an org context that doesn't match the authenticated secret.

This is a cross-organization/cross-repository write performed by an entity whose trust should be scoped only to its own organization, matching the "cross-repository writes" impact class.

### Likelihood Explanation
Requires: (1) the target Shipit instance configured with more than one GitHub App/organization (a documented, supported configuration), and (2) the attacker possessing a valid webhook secret for at least one configured organization (e.g., they administer that org's GitHub App or have visibility into its webhook deliveries). This is a realistic scenario for any Shipit deployment shared across independently-administered orgs/teams, but not exploitable against single-organization deployments where all repos share the same trust root.

### Recommendation
In `WebhooksController#verify_signature` (or in `Webhooks::Handlers::Handler`), assert that `repository.full_name`'s owner segment matches the `repository.owner.login` / `organization.login` used to select the webhook secret, and reject the payload (422) if they diverge, before dispatching to any handler.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` and `org-b`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. As an entity holding `org-a`'s webhook secret, craft a `push` event JSON body:
```json
{
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/target-repo" },
  "after": "<sha>", ...
}
```
3. Compute `X-Hub-Signature: sha1=HMAC-SHA1(org-a-secret, body)` and `X-Github-Event: push`, then POST to `/webhooks`.
4. `verify_signature` resolves `Shipit.github(organization: "org-a")` and validates successfully against `org-a`'s secret (`app/controllers/shipit/webhooks_controller.rb:24-30`).
5. `PushHandler`/`Handler#repository_name` resolves the target repo from `full_name` = `org-b/target-repo` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`), enqueuing `GithubSyncJob` against `org-b`'s stack despite the request only being authenticated for `org-a`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
