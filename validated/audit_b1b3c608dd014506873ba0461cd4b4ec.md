## Valid Analog Found

### Title
Hookify hook scripts fail open on exceptions, letting a crafted tool call bypass `block` rules - (File: `plugins/hookify/hooks/pretooluse.py`)

### Summary
The Solidity report describes a `try/catch` in `StakeVault.leave()` that is meant to tolerate a misbehaving `stakeManager` but, on any revert (including a maliciously-forced one), falls back to a "safe"/successful code path instead of failing closed — letting an attacker force the exception and get the favorable outcome anyway. The `hookify` plugin's hook executors (`pretooluse.py`, `posttooluse.py`, `stop.py`, `userpromptsubmit.py`) have the same structural flaw: a top-level `try/except Exception` around rule evaluation that, on *any* exception, always emits an empty/benign result and `sys.exit(0)` — the "allow" outcome — instead of failing closed. Because a normal user (or the model acting on user-controlled tool_input content) fully controls the values fed into `RuleEngine.evaluate_rules`, they can construct inputs that deliberately raise an exception during evaluation, causing a `block` rule (e.g. one meant to stop `rm -rf`, secret-file edits, or "no-tests-before-stop") to be silently skipped.

### Finding Description
`pretooluse.py` wraps `load_rules()` + `RuleEngine.evaluate_rules()` in a `try/except Exception` block whose handler only emits a `systemMessage` and then unconditionally exits `0` in `finally`: [1](#0-0) 

The same fail-open pattern exists in `posttooluse.py`, `stop.py`, and `userpromptsubmit.py`: [2](#0-1) [3](#0-2) 

`RuleEngine.evaluate_rules` is what decides whether a matching rule should `deny`/`block` a tool call: [4](#0-3) 

But field extraction, `_extract_field`, only narrowly guards a few known error types (e.g. `FileNotFoundError`/`PermissionError` for transcript reads) and otherwise assumes well-typed input. For example, for `MultiEdit` it does `e.get('new_string', '')` over each item in `tool_input['edits']` without validating that each item is a dict: [5](#0-4) 

If `edits` contains a non-dict element (e.g. a string or `null`), `.get` raises `AttributeError`, which is not caught anywhere inside `rule_engine.py` — it propagates out of `evaluate_rules` and is caught only by the hook script's outer `except Exception`, which discards the block decision and lets the tool call proceed as if no rule matched at all.

This mirrors the `StakeVault.leave()` root cause exactly: a `try/catch` designed to prevent a DoS from an unexpected failure instead converts a "should-fail/should-block" condition into a "succeeds/allowed" outcome, and the condition triggering that fallback is attacker-reachable.

### Impact Explanation
A user (or content injected into `tool_input`, e.g., a MultiEdit call generated based on untrusted context) can deliberately shape a malformed `edits` array, an unexpected field type, or any other input that trips an uncaught exception in `_extract_field`/`_rule_matches`. This causes the `PreToolUse` hook to skip evaluation of all configured `block` rules for that call — e.g. bypassing a `hookify.dangerous-rm.local.md` rule intended to block `rm -rf`, or a rule blocking edits to `.env`/secrets files — resulting in the tool call executing without the intended safety gate. This is a genuine local hook-bypass / unauthorized-action trust-boundary issue: the security control (`block` action in a `PreToolUse` hook) can be defeated by a crafted tool input crafted to raise inside rule evaluation.

### Likelihood Explanation
Moderate-to-high. Any Bash/Edit/Write/MultiEdit tool_input is attacker/model influenced, and the extraction logic makes type assumptions (e.g. dict items in `edits`) that are not enforced anywhere before reaching `RuleEngine`. Triggering an uncaught exception only requires constructing a tool call whose `tool_input` violates these assumptions — no special privileges are needed, since `hookify` rules are typically deployed exactly to restrict what an agent/session is allowed to do.

### Recommendation
- Do not fail open on unexpected exceptions in hook executors. When rule evaluation raises, and any loaded rule for that event has `action: block`, the hook should return a deny/block decision (or at minimum re-raise / exit non-zero) rather than defaulting to "allow."
- Harden `RuleEngine._extract_field`/`_check_condition` to validate types defensively (e.g., skip malformed `edits` entries instead of raising) so a parsing error in one condition doesn't silently disable rule enforcement for the whole event.
- Add a dedicated "evaluation failed" response distinct from "no rule matched," and let each rule declare a fail-safe policy (fail-open vs fail-closed) instead of hardcoding fail-open in every executor.

### Proof of Concept
1. Configure a `block` rule, e.g. a `.claude/hookify.block-secrets.local.md` rule with `event: file`, `action: block`, matching `file_path` against `\.env$`.
2. Have the agent issue a `MultiEdit` tool call whose `tool_input.edits` array contains a non-dict element, e.g. `{"file_path": ".env", "edits": ["not-a-dict-object"]}`.
3. `RuleEngine._extract_field` executes `e.get('new_string', '')` on the string element `"not-a-dict-object"`, raising `AttributeError: 'str' object has no attribute 'get'`. [6](#0-5) 
4. This exception propagates out of `evaluate_rules()` up to `pretooluse.py`'s outer `try`, is swallowed by `except Exception`, and the script `sys.exit(0)`s with only a `systemMessage`, producing no `permissionDecision: deny`. [7](#0-6) 
5. Claude Code treats the missing/empty hook output as "no restriction," and the `MultiEdit` on `.env` proceeds despite the configured `block` rule — the security gate is bypassed via the same "exception-in-fallback-path grants the favorable outcome" pattern as the `StakeVault.leave()` bug.

```python
def main():
    """Main entry point for PreToolUse hook."""
    try:
        # Read input from stdin
        input_data = json.load(sys.stdin)

        # Determine event type for filtering
        # For PreToolUse, we use tool_name to determine "bash" vs "file" event
        tool_name = input_data.get('tool_name', '')

        event = None
        if tool_name == 'Bash':
            event = 'bash'
        elif tool_name in ['Edit', 'Write', 'MultiEdit']:
            event = 'file'

        # Load rules
        rules = load_rules(event=event)

        # Evaluate rules
        engine = RuleEngine()
        result = engine.evaluate_rules(rules, input_data)

        # Always output JSON (even if empty)
        print(json.dumps(result), file=sys.stdout)

    except Exception as e:
        # On any error, allow the operation and log
        error_output = {
            "systemMessage": f"Hookify error: {str(e)}"
        }
        print(json.dumps(error_output), file=sys.stdout)

    finally:
        # ALWAYS exit 0 - never block operations due to hook errors
        sys.exit(0)
```
