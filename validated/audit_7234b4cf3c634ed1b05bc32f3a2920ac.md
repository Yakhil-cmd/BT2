### Title
Fee-on-Transfer ERC20 Token Causes Destination Bridge Liquidity Drain or Unconditional Revert — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

---

### Summary

`BridgeTransferERC20.requestERC20Transfer` pulls `_value + _feeLimit` tokens from the caller via `safeTransferFrom`, but does not verify the amount actually received. When a fee-on-transfer ERC20 is used, the bridge receives less than `_value + _feeLimit`. The function then unconditionally emits `RequestValueTransfer` with the caller-supplied `_value`, causing the destination bridge to release `_value` tokens to the recipient — more than was ever deposited on the source side. In `modeMintBurn` mode the discrepancy surfaces earlier as an unconditional revert when `burn(_value)` is called against an insufficient balance.

---

### Finding Description

`requestERC20Transfer` at line 133 pulls exactly `_value + _feeLimit` from the caller:

```solidity
IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
_requestERC20Transfer(_tokenAddress, msg.sender, _to, _value, _feeLimit, _extraData);
``` [1](#0-0) 

Inside `_requestERC20Transfer`, the bridge first pays the bridge-level fee and refund from its own balance (lines 91, 74, 78), then either burns `_value` (line 94) or keeps it locked, and finally emits `RequestValueTransfer` with the caller-supplied `_value` (line 102):

```solidity
uint256 fee = _payERC20FeeAndRefundChange(_from, _tokenAddress, _feeLimit);
if (modeMintBurn) {
    ERC20Burnable(_tokenAddress).burn(_value);
}
emit RequestValueTransfer(..., _value, ...);
``` [2](#0-1) 

`_payERC20FeeAndRefundChange` transfers `fee` to `feeReceiver` and `feeLimit - fee` back to the sender, both from the bridge's token balance: [3](#0-2) 

For a fee-on-transfer token with rate `r > 0`, the bridge actually receives:

```
actual = (value + feeLimit) × (1 − r)
```

After paying the bridge fee and refund (`feeLimit` total outflow), the bridge holds:

```
locked = actual − feeLimit = value × (1 − r) − feeLimit × r  <  value
```

**`modeMintBurn = true` path:** `burn(_value)` is called against a balance of `locked < _value`. The ERC20 burn reverts unconditionally for any fee-on-transfer token, making the function permanently unusable for that token class.

**`modeMintBurn = false` path:** The bridge locks only `locked < _value` tokens but emits `RequestValueTransfer` with `_value`. The destination bridge's `handleERC20Transfer` then executes `safeTransfer(_to, _value)` at line 71, releasing the full `_value` to the recipient: [4](#0-3) 

The destination bridge therefore pays out `_value − locked > 0` tokens more than were ever deposited on the source side. Repeated transfers drain the destination bridge's entire ERC20 reserve.

The same flaw exists in the `onERC20Received` (1-step) path at line 120, where the token contract calls the bridge after transferring tokens — the bridge again trusts the caller-supplied `_value` without measuring actual receipt: [5](#0-4) 

---

### Impact Explanation

**`modeMintBurn = false`:** Unauthorized drain of destination bridge's ERC20 reserves. Each cross-chain transfer of a fee-on-transfer token causes the destination bridge to release `_value` tokens while only `locked < _value` were deposited. The shortfall accumulates until the destination bridge is emptied. This is an unauthorized transfer of bridged assets from system-managed funds.

**`modeMintBurn = true`:** Unconditional revert (DoS) for any fee-on-transfer token. The bridge becomes permanently non-functional for that token without any privileged intervention.

---

### Likelihood Explanation

Any registered fee-on-transfer ERC20 token triggers the bug. The bridge owner registers tokens, but fee-on-transfer tokens are a common token design (deflationary tokens, tokens with protocol fees, rebasing tokens with negative rebase). No special privilege is required beyond calling `requestERC20Transfer` with a registered fee-on-transfer token. The trigger is a normal user action.

---

### Recommendation

Measure the actual received amount by snapshotting the bridge's token balance before and after `safeTransferFrom`, and use the delta as the true deposited amount. Emit `RequestValueTransfer` with the actual deposited amount (after subtracting `feeLimit`) rather than the caller-supplied `_value`:

```solidity
function requestERC20Transfer(...) public {
    uint256 balBefore = IERC20(_tokenAddress).balanceOf(address(this));
    IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
    uint256 actualReceived = IERC20(_tokenAddress).balanceOf(address(this)).sub(balBefore);
    uint256 actualValue = actualReceived > _feeLimit ? actualReceived.sub(_feeLimit) : 0;
    require(actualValue > 0, "zero actual value after fee");
    _requestERC20Transfer(_tokenAddress, msg.sender, _to, actualValue, _feeLimit, _extraData);
}
```

Apply the same fix to `onERC20Received`.

---

### Proof of Concept

1. Deploy the bridge in `modeMintBurn = false` mode. Register a fee-on-transfer ERC20 token (1% transfer fee) on both source and destination bridges. Pre-fund the destination bridge with 1000 tokens.
2. Alice calls `requestERC20Transfer(token, bob, 100, 0, "")` on the source bridge.
3. `safeTransferFrom(alice, bridge, 100)` executes; the bridge receives 99 tokens (1% fee deducted by the token).
4. `_requestERC20Transfer` emits `RequestValueTransfer(..., 100, ...)`. The source bridge locks 99 tokens.
5. The bridge operator observes the event and calls `handleERC20Transfer(..., bob, token, 100, ...)` on the destination bridge.
6. The destination bridge executes `safeTransfer(bob, 100)`, sending 100 tokens to Bob.
7. Net: source bridge received 99, destination bridge paid 100. Destination bridge lost 1 token.
8. Repeat 1000 times: destination bridge is fully drained while source bridge holds 99,000 tokens.

In `modeMintBurn = true` mode, step 4 instead calls `burn(100)` against a balance of 99, reverting unconditionally and permanently blocking cross-chain transfers for this token.

    function _payERC20FeeAndRefundChange(address from, address _token, uint256 _feeLimit) internal returns(uint256) {
        uint256 fee = feeOfERC20[_token];

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            IERC20(_token).safeTransfer(feeReceiver, fee);

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                IERC20(_token).safeTransfer(from, feeRefund);
            }

            return fee;
        }

        if (_feeLimit > 0) {
            IERC20(_token).safeTransfer(from, _feeLimit);
        }
        return 0;
    }
