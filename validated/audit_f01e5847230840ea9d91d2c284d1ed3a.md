### Title
StatusHandler#process mutates Commits across all stacks sharing a SHA, bypassing repository-scoped `stacks` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` — unscoped by repository — and calls `commit.create_status_from_github!(params)` on every match, unlike every other handler which restricts writes to `Handler#stacks`, itself derived from `payload.dig('repository', 'full_name')`. Because Git commit SHAs are content-addressed and identical across forks/shared history, any Shipit-tracked repository that shares a commit with an unrelated stack's tracked repository can be used to inject a real, GitHub-signed `status` webhook that writes a `Status` row into the unrelated stack's `Commit`.

### Finding Description
The broken binding, stated as an equality that should hold but does not:

`∀ commit mutated by Handler#process: commit.stack ∈ Handler#stacks` (i.e. `Repository.from_github_repo_name(payload.repository.full_name).stacks`)

For `StatusHandler`, this equality fails by construction: `StatusHandler#process` never references `stacks` or `repository_name` at all. [1](#0-0) [2](#0-1) 

Every other handler in the engine (`PullRequest::OpenedHandler`, `ClosedHandler`, `EditedHandler`, `ReopenedHandler`, `LabelCapturingHandler`, `UnlabeledHandler`) resolves a `repository` from `params.repository.full_name` and scopes its mutation through that repository's own stacks/review_stacks before writing. `StatusHandler` is the sole exception: it queries `Commit.where(sha: params.sha)` globally across the entire `commits` table and mutates every match via `commit.create_status_from_github!(params)`, which delegates to `Status.replicate_from_github!(stack_id, ...)` using each matched row's own `stack_id` — not any stack derived from the verified payload. [3](#0-2) [4](#0-3) 

`WebhooksController#verify_signature` only proves that the payload was signed with the webhook secret belonging to `params.dig('repository','owner','login')` — i.e., that the request genuinely originated from GitHub for *that* repository/org. It does not, and cannot, prove anything about which SHAs are legitimately "owned" by that repository, because Git SHAs are content hashes shared across forks and shared history. [5](#0-4) [6](#0-5) 

Exploit flow:
1. Attacker forks (or otherwise obtains push access to) a repository, call it `attacker/repo`, that is configured as a Shipit-tracked repository. This repo shares git object history (and therefore commit SHAs) with an unrelated `victim/repo` also tracked by Shipit (e.g. a public open-source repo attacker forked, or a SHA the attacker discovered via Shipit's public dashboard/API per the stated precondition).
2. Using their own legitimate write access to `attacker/repo`, the attacker sets a commit status (`state: "error"`) on that shared SHA via the real GitHub API/UI. GitHub genuinely fires a `status` webhook to Shipit, correctly signed with `attacker`'s org's `webhook_secret`.
3. `verify_signature` passes because the signature is valid for `attacker`'s org.
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, which matches the `Commit` row belonging to `victim/repo`'s stack (because the SHA is identical), and calls `create_status_from_github!`, writing an `error` `Status` into the victim's stack, potentially affecting `blocked?`/`deployable?` gating and CI-based deploy behavior for that unrelated tenant. [7](#0-6) 

### Impact Explanation
This is a cross-repository write: a `status` webhook that is authentically signed for `attacker/repo` mutates a `Commit`/`Status` record belonging to a completely unrelated `victim` stack, with no involvement of the victim's own GitHub App secret. This can flip CI/deployability state (`blocking?`/`deployable?`) and trigger downstream hooks (`deployable_status`, `ProcessMergeRequestsJob`) for the victim's stack, matching the "payload for one repository mutating another's stack/commit" Critical category. The attack is repeatable against any stack whose tracked repository shares commit history (forks, mirrors, or previously-observed SHAs) with a repository the attacker controls or can trigger events for. [8](#0-7) 

### Likelihood Explanation
Preconditions: the attacker needs (a) a Shipit-tracked repository they control (or push/status-setting rights to), and (b) a target SHA that also exists as a `Commit` row in an unrelated tracked stack — obtainable by forking a public repo that Shipit tracks, or by matching previously observed SHAs via Shipit's public dashboard/API as described. No Shipit secret, session, or API token is required; only ordinary GitHub repository permissions on the attacker's own repo, which real GitHub webhooks will sign normally. This is fully repeatable and requires no signature forgery.

### Recommendation
Scope `StatusHandler#process` the same way every other handler is scoped: resolve the repository from `payload.dig('repository', 'full_name')` and restrict the `Commit` lookup to `stacks` (or `stacks.flat_map(&:commits)`/`Commit.where(sha: params.sha, stack: stacks)`) instead of an unscoped `Commit.where(sha: params.sha)`, so a `Status` is only ever created against commits belonging to stacks of the repository that the verified webhook payload actually names.

### Proof of Concept
In `test/models/webhooks/handlers/status_handler_test.rb` (or equivalent):
1. Create two stacks/repositories, `repo_a` and `repo_b`, each with a `Commit` row sharing the identical `sha` value (simulating shared fork history).
2. Build a `status` webhook payload with `repository.full_name = "org/repo_a"` and the shared `sha`, `state: "error"`.
3. Spy on `StatusHandler#stacks` (e.g. `StatusHandler.any_instance.expects(:stacks).never` or a mocked spy) and call `StatusHandler.call(payload)`.
4. Assert: `stacks` is never invoked (proving the repository-scoping method is bypassed).
5. Assert: `repo_b`'s `Commit` row (belonging to an unrelated repository/stack from the payload's `repository.full_name`) now has a `Status` with `state == "error"` — i.e. `commit_b.statuses.count == 1` and `commit_b.state == "error"`, despite the payload only ever declaring `repo_a` as its repository.
6. This demonstrates `commit_b.stack ∉ Repository.from_github_repo_name("org/repo_a").stacks` yet `commit_b` was mutated, proving the invariant violation.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
