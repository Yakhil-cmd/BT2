### Title
Cross-tenant commit-status forgery via unscoped `Commit.where(sha:)` in `StatusHandler` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits purely by `sha` with no scoping to the repository/organization that the webhook signature authenticated, then writes attacker-supplied `state`/`target_url`/`description` onto every matching `Commit` row across the entire Shipit instance. Because the payload's own `repository.owner.login` selects which secret verifies the request, `verify_signature` only proves the payload legitimately came from *some* authenticated org — it proves nothing about which `Commit` rows that org is allowed to touch, and `StatusHandler` never re-checks that binding.

### Finding Description
The broken binding: `repository_owner_of(payload)` (the org whose `webhook_secret` validated the request) **should equal** `commit.stack.repository.owner` for every `Commit` mutated by that payload. `WebhooksController#verify_signature` only checks the former via `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [4](#0-3) ; it never restricts the handler's writes to that org's stacks. `StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [3](#0-2) 
`Commit.sha` is not unique across `Stack`s in the schema, and no `stack_id`/`repository_id` filter is applied, unlike `PushHandler` and `Handler#stacks`, which explicitly scope by `Repository.from_github_repo_name(repository_name)` before acting [1](#0-0) [2](#0-1) . `create_status_from_github!` writes the attacker-supplied `state` straight into `statuses.replicate_from_github!` [5](#0-4) , which can flip the commit's aggregate `state` to `success`, unblocking any deploy gate keyed on commit status.

Exploit flow: attacker has a legitimately onboarded repository/org in a multi-tenant Shipit deployment (Shipit explicitly supports "Using Multiple Github Applications", one secret per org) [6](#0-5) . They sign a `status` webhook correctly with their own org's `webhook_secret` (passing `verify_signature` legitimately), but set `sha` to a value equal to a real commit sha belonging to a victim's `Stack` in a different org (achievable via genuinely shared commit objects — e.g., identical template-initialized initial commits — since matching a specific sha requires literally identical git object content, not a SHA-1 break). Because `Commit.where(sha:)` matches globally, `commit.create_status_from_github!(params)` fires on the victim's `Commit` row even though the request never authenticated anything about the victim's org or repository.

Existing guards do not close this: `verify_signature` validates sender authenticity per-org but not per-target-row; `ExplicitParameters` only validates payload shape (`sha`/`state`/`target_url` types), not ownership [7](#0-6) ; and `Handler#stacks`/`repository_name`, which would provide the correct scoping, is simply unused by `StatusHandler`.

### Impact Explanation
A correctly-authenticated webhook from Org B can write a `success`/`failure`/`error` status with an attacker-chosen `target_url`/`description` onto a `Commit` belonging to Org A's `Stack`, i.e., "a payload for one repository mutating another's commit," matching the Critical impact category. This can flip `commit.state` and unblock deploy gates or `continuous_deployment` triggers on the victim stack (`create_status_from_github!` → `add_status` can enqueue `ProcessMergeRequestsJob`/deploys as shown in tests) [8](#0-7) . It is repeatable against any `sha` value the attacker can reproduce in their own commit history, across any tenant sharing the Shipit instance.

### Likelihood Explanation
Requires: (1) a multi-tenant Shipit deployment where the attacker already legitimately controls a webhook-signing org/repo (a precondition, not a privilege escalation within a single-org deployment where all repos share one `webhook_secret` and the attacker would need to already be inside that trust boundary); (2) the ability to produce a commit whose sha exactly matches a target victim sha — feasible only where the underlying git object (tree, parents, author/committer name+email+date, message) is literally identical, e.g. shared template/fork ancestry, not a general SHA-1 collision. Given these preconditions, the exploit costs a single crafted `POST /webhooks` request and is fully repeatable.

### Recommendation
Scope `StatusHandler#process` to the requesting repository, mirroring `PushHandler`: use `stacks` (or `Repository.from_github_repo_name(repository_name)`) to constrain the `Commit` lookup, e.g. `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, so a payload can only mutate commits belonging to stacks whose repository matches the payload's own `repository.full_name`.

### Proof of Concept
```ruby
test "status webhook from one repository cannot alter another repository's commit" do
  victim_stack = shipit_stacks(:shipit)
  attacker_stack = shipit_stacks(:cyclimse)
  shared_sha = "cafef00dcafef00dcafef00dcafef00dcafef00"

  victim_commit = victim_stack.commits.create!(sha: shared_sha, author: shipit_users(:walrus),
    committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now, message: "shared ancestor")

  request.headers['X-Github-Event'] = 'status'
  body = {
    'sha' => shared_sha, 'state' => 'success', 'target_url' => 'http://evil.example.com',
    'repository' => { 'full_name' => attacker_stack.github_repo_name, 'owner' => { 'login' => attacker_stack.repository.owner } }
  }.to_json

  post :create, body:, as: :json

  victim_commit.reload
  assert_not_equal 'success', victim_commit.state,
    "attacker-signed webhook for attacker's own repo must not mutate a commit belonging to a different repository"
end
```
