### Title
Open redirect in OAuth callback via unvalidated `omniauth.origin` - ([File: app/controllers/shipit/github_authentication_controller.rb])

### Summary
`GithubAuthenticationController#callback` sets `return_url = request.env['omniauth.origin'] || root_path` and calls `redirect_to(return_url)` with no host/path validation. Since `omniauth.origin` is populated from the `origin` query parameter supplied on the initiating `GET /github/auth/github` request (via OmniAuth's request phase), any unauthenticated attacker can craft a link that forces a victim through a genuine GitHub OAuth login and then redirects the victim's authenticated browser to an attacker-controlled URL.

### Finding Description
The intended binding is: `return_url` must resolve only to a path within the Shipit host (i.e., `return_url =~ /\A\/(?!\/)/` or equivalent same-origin check). In the actual code: [1](#0-0) 

`return_url` is taken directly from `request.env['omniauth.origin']`, which OmniAuth's default `RequestPhase`/`CallbackPhase` populates from the `origin` request parameter of the initiating request and later copies back from `session['omniauth.origin']` into `env['omniauth.origin']` at callback time. Nothing in this engine validates that value is a relative path or restricted to the app's own host — `redirect_to(return_url)` is called unconditionally.

The only place in this codebase that legitimately sets `origin` is `force_github_authentication`, which always uses `request.original_url` (same-host, safe): [2](#0-1) 

However, an attacker doesn't need to go through that code path — they can directly link a victim to `GET /github/auth/github?origin=https://attacker.example`. OmniAuth stores that attacker-supplied value and, after the victim completes a legitimate OAuth handshake with GitHub, `callback` reads it back unfiltered and redirects the victim's browser to `https://attacker.example`.

None of the existing guards (`force_github_authentication`, `User#authorized?`, session checks) apply here since this is the unauthenticated entry point of the flow itself — the vulnerability is in trusting client-supplied redirect data, not in access control on the callback action.

### Impact Explanation
This is an open redirect that occurs immediately after a real, successful GitHub OAuth login, i.e., "forced OAuth completion" — the attacker cannot steal the session cookie itself (it is set via `Set-Cookie` on the Shipit host and is not exposed to the attacker's page), so this does not directly yield token/session exfiltration or an unauthorized deploy on its own. The demonstrable impact is limited to: the victim is deceived into completing an authentication flow initiated by the attacker and lands on an attacker-controlled page immediately afterward, which can be used for phishing (e.g., a fake "session expired, please re-enter your GitHub credentials" page) or chained with other unrelated vulnerabilities. The claim that this can be combined with "a follow-up CSRF-able deploy action" is not substantiated in this codebase — no evidence was found of CSRF protection being disabled on deploy-triggering endpoints, and demonstrating that would require a separate finding. As presented, this maps to the High category "session fixation / forced OAuth completion," not to the Critical "unauthorized deploy" claim in the question.

### Likelihood Explanation
Trivial to trigger: no Shipit or GitHub secrets, no privileged role, and no special repository configuration are required. The attacker only needs to get a victim who has (or is willing to establish) a Shipit account to click a link of the form `/github/auth/github?origin=https://attacker.example`. Cost is a single crafted URL; it is repeatable against any victim/tenant since the flaw is in shared, per-request-only state (`omniauth.origin`), not tied to a specific repository or stack.

### Recommendation
Validate `return_url` before redirecting: only allow relative paths within the app (e.g., reject absolute URLs / URLs with a `host` component, or use `url_for` against `Shipit::Engine.routes` with an allow-list), for example:
```ruby
return_url = request.env['omniauth.origin']
return_url = root_path unless return_url.present? && return_url.start_with?('/') && !return_url.start_with?('//')
redirect_to(return_url)
```

### Proof of Concept
```ruby
# test/controllers/github_authentication_controller_test.rb
test ":callback redirects to attacker-controlled external origin" do
  auth = OmniAuth::AuthHash.new(
    credentials: OmniAuth::AuthHash.new(token: 's3cr3t'),
    extra: OmniAuth::AuthHash.new(raw_info: OmniAuth::AuthHash.new(
      id: 44, name: 'Shipit User', email: 'shipit-user@example.com',
      login: 'shipit-user', avatar_url: 'https://example.com',
      api_url: 'https://github.com/api/v3/users/shipit-user'
    ))
  )
  @request.env['omniauth.auth'] = auth
  @request.env['omniauth.origin'] = 'https://attacker.example'

  get :callback

  # Binding under test: return_url must equal a same-host path, e.g. root_path.
  # Actual: return_url resolves to the attacker-controlled absolute URL.
  assert_redirected_to 'https://attacker.example'
  refute_equal root_path, response.location
end
```
This confirms `redirect_to(return_url)` sends the now-authenticated victim's browser to the attacker's URL, proving the same-host redirect binding is absent.

    end
