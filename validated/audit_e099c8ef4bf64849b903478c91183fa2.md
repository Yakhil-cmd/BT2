### Title
`hash`-only address definitions allow front-running / theft of funds when the secret is revealed on-chain before finality - (File: `definition.js`)

### Summary
The Vader report's root cause is that authorization to withdraw funds is not bound to a specific, single beneficiary and becomes visible/available to anyone before the withdrawing action is atomically finalized, letting an attacker race in and claim the funds themselves. The `hash` authentifier type in ocore's address-definition language exhibits the same class of problem: a `['hash', {hash: H}]` spending condition is satisfied by *anyone* who can supply a preimage matching `H` in the `r` authentifier slot, without binding the resulting payment to the original secret-holder's identity or output address.

### Finding Description
`definition.js` implements the `hash` op both at definition-validation time and at authentifier-validation time: [1](#0-0) [2](#0-1) 

The validation logic only checks that `sha256(assocAuthentifiers[path]) === args.hash`; it does not check who submits the unit, what outputs the unit pays to, or whether the unit's outputs match any previously agreed beneficiary. Compare this with `sig`, where the authentifier is an ECDSA signature over the *specific unit* being posted (`objValidationState.unit_hash_to_sign`), binding the authorization to the exact set of outputs in that unit: [3](#0-2) 

For `hash`, the "secret" is a static value that, once disclosed anywhere (in a peer-to-peer payment channel message, an unstable/pending unit broadcast to the network, or an off-chain HTLC-style exchange), authorizes spending from the address for *any* unit an attacker chooses to construct, with *any* outputs. In ocore, units are not instantly final: a unit is only "final" once it is stable behind the main chain, and until then it can be intercepted, and a conflicting unit built from the same address/inputs can compete to become the "good" one while the original becomes `final-bad` (double-spend resolution logic lives in `validateAuthor`'s `findConflictingUnits`, cited earlier from `validation.js`).

This produces exactly the Vader pattern:
1. Party A reveals/broadcasts a unit spending from a `hash`-secured address (the "claim" transaction, analogous to `Vader.redeemToMember()` being called after USDV was sent).
2. Before that unit reaches finality, an attacker observing the network extracts the disclosed secret from the pending unit (or from off-chain messaging preceding it, e.g. `wallet.js` secret-based signing paths at [4](#0-3) ).
3. The attacker crafts a new unit, authored by the same address, using the identical secret as the `hash` authentifier, but redirecting the payment outputs to the attacker's own address.
4. If the attacker's unit wins the conflict-resolution race (earlier level/first-seen, or simply propagates and stabilizes first), the legitimate claimant's unit becomes `final-bad`, and the attacker walks away with the funds — mirroring how the Vader front-runner intercepts `redeemToMember()` and steals the swept balance.

### Impact Explanation
Any address whose spending condition is (or contains, in a non-conjunctive way) a bare `hash` authentifier is vulnerable to unauthorized fund theft once the secret becomes observable prior to finality. This is a direct, concrete path to unauthorized spending/double-spend of funds at that address — matching the "concrete unauthorized spending" / "double-spend of a stable output" bar for Medium/High severity, since the authorization primitive itself does not bind to a specific recipient or transaction, unlike `sig`.

### Likelihood Explanation
Likelihood depends on usage: any protocol or user-composed address definition that uses `hash` as a standalone or disjunctive (`or`) condition — e.g., for HTLC-like cross-chain swap patterns, or a "first to reveal wins" claim mechanism — is directly exposed. The `hash` authentifier lacks any protocol-level requirement that it be combined with a `sig` or an output-matching condition (`has {what: output, address, amount}` as used correctly in `arbiter_contract.js`'s `deriveSharedAddress` for its escrow logic, which instead binds spending to specific counter-outputs). Since nothing in `validateDefinition` enforces that `hash` must be paired with a binding condition, a developer/user composing an address definition can inadvertently (or through a documented sample) create such an exposed address, and a network-observing attacker only needs to see the secret in an unstable/pending unit to race a conflicting spend.

### Recommendation
- Discourage/disallow use of `hash` as a standalone/OR-branch spending condition without also requiring a binding condition (e.g., mandate combination with a `has {what: 'output', address: ..., amount: ...}` filter, as already done correctly in `arbiter_contract.js`), so that revealing the secret does not by itself authorize redirecting funds to an arbitrary address.
- Add a definition-validation-time warning/rejection in `definition.js`'s `case 'hash'` handling when `hash` appears without being intersected (`and`) with an output-binding filter, similar to the "protect against combining several contracts" guard used in `arbiter_contract.js`.
- Document clearly (in oscript/ojson docs and in wiki §2.5 "Addresses, Definitions and Data Feeds") that `hash`-only definitions are unsafe for any protocol where the secret is disclosed before the claiming unit is stable/final.

### Proof of Concept
1. Create address `A` with definition `["hash", {hash: sha256("mysecret")}]`.
2. Party A (the legitimate claimant) constructs and broadcasts unit `U1`, authored by `A`, with authentifier `r = "mysecret"`, paying outputs to `A`'s own destination address.
3. Before `U1` stabilizes (becomes final on the main chain), an attacker who observed `U1` on the network extracts `authentifiers.r = "mysecret"`.
4. Attacker constructs unit `U2`, also authored by `A`, using the same authentifier `r = "mysecret"` (passes `definition.js`'s `case 'hash'` check identically), but with outputs paying the attacker's address instead.
5. Both `U1` and `U2` spend the same inputs from address `A` and conflict; per `validation.js`'s `findConflictingUnits`/serial-address-use logic, only one can become `sequence='good'`. If `U2` propagates/stabilizes ahead of `U1` (attacker races with better connectivity or lower latency), `U1` becomes `final-bad` and the attacker's `U2` claims the funds — reproducing the Vader front-running theft pattern.
