Found the relevant analog: `asset_attestors` message type, which lets an asset's **definer** unilaterally update the trusted-attestor list for a `spender_attested` asset at any time, with no check for pending/in-flight units that were composed against the old attestor list.## Title
Asset definer can change the `spender_attested` attestor list at any time, orphaning already-composed/in-flight payments and denying legitimate senders/receivers - (File: `validation.js`, `storage.js`)

### Summary
This maps to the Sherlock finding's root cause: a privileged party can update a critical reference/config (`Queue`/`Auction` address) at any time with no check for "operations that are already in flight relying on the old configuration," causing pending user funds/state to become stuck or rejected. In ocore, the analogous privileged, unrestricted, always-updatable reference is the **attestor list of a `spender_attested` asset**, which the asset's `definer_address` can change via an `asset_attestors` message at any time, with no restriction tied to outstanding payments that were composed (or partially composed, e.g. private-payment chains) against the previous attestor list.

### Finding Description
When an asset is defined with `spender_attested: true`, every payment involving that asset (issue, transfer, and even outputs) must involve only addresses attested by the current attestor list, both for issuer and for output addresses: [1](#0-0) [2](#0-1) 

The definer can freely update this attestor list at any time by posting an `asset_attestors` message; the only checks are that the sender is the asset definer, the new list is well-formed, and only one update per asset per unit: [3](#0-2) [4](#0-3) 

Crucially, there is **no check for outstanding/pending state** dependent on the old attestor list — unlike address key changes, where ocore explicitly guards against acting on stale/pending definitions via `checkNoPendingChangeOfDefinitionChash`/`checkNoPendingDefinition` in `validation.js`: [5](#0-4) 

No equivalent guard exists for `asset_attestors`. `storage.readAsset()` always fetches the **most recent stable attestor list** at validation time regardless of what list was in effect when a payment was composed: [6](#0-5) 

This is functionally the same bug class as the Sherlock report: the definer plays the role of `VaultAdmin`, and the attestor list plays the role of the `Queue`/`Auction` contract address — a critical reference that downstream logic depends on, updatable unilaterally and without regard for units that are already composed, broadcast, or pending stabilization against the previous value.

The impact is amplified for **private payments**, whose chains can be built, sent to counterparties, and held un-broadcast for extended periods (design intent, per `network.js`'s `handleOnlinePrivatePayment`/`handleSavedPrivatePayments` queuing of `unhandled_private_payments`). If the definer rotates the attestor list while such a chain is outstanding: [7](#0-6) 
- Payments to an address that was attested when composed, but is no longer attested by the time the unit reaches validation, are rejected with `"some output addresses are not attested"` — funds effectively get stuck for the sender (must be re-composed) and any private chain built on the old output becomes impossible to redeem as intended.
- Conversely, if the definer removes an attestor who already possesses in-flight coins from an issuer, the previous holder can find their subsequent transfer rejected at `"owner address is not attested"`, freezing their asset holdings mid-chain: [8](#0-7) 

### Impact Explanation
This is a Medium-severity availability/fund-freezing issue analogous to the reported bug: a privileged actor (asset definer) can unilaterally invalidate previously-valid, in-flight transaction state (including private payment chains already delivered to counterparties) without any check for pending dependents, causing user funds to become undeliverable/stuck and requiring re-composition, and for private/indivisible assets potentially orphaning coins that cannot be re-issued (the "issue serial_number already used" style state, or a coin that was already spent to a now-unattested address and cannot be re-spent along the intended chain).

### Likelihood Explanation
Likelihood is Medium: this requires a `spender_attested` asset (an opt-in, definer-chosen feature) and an active definer who updates the attestor list while payments are outstanding. This is a normal, expected admin action (attestor lists are explicitly designed to be updatable — see the schema comment "must subsequently publish and update the list of trusted attestors"), so the trigger condition is not adversarial; it can happen from ordinary operational attestor rotation colliding with normal payment latency (network propagation, private-payment holding periods, main-chain stabilization delay).

### Recommendation
When validating a payment against a `spender_attested` asset, consider snapshotting/pinning the attestor list applicable to the payment (e.g., by referencing the attestor-list unit the payment was composed against, similar to how `last_ball_mci` pins validation-time state), or require attestor-list changes to only take effect after some grace period / not affect outputs/inputs from before the change's stabilization for addresses that were valid at composition time. At minimum, document this design tradeoff, since composed-but-unbroadcast or unstable-but-broadcast payments have no protection against attestor-list changes made after composition but before stabilization.

### Proof of Concept
1. Definer creates asset `X` with `spender_attested: true`, `is_transferrable: true`, `attestors: [A1]`. Attestor `A1` attests address `Bob`.
2. Alice (already attested via A1) composes a divisible-asset payment to `Bob` using `divisible_asset.js`'s `composeDivisibleAssetPaymentJoint`, which checks attestation only at composition time: [9](#0-8) 
3. Before Alice's unit stabilizes (or even before it's broadcast, for a private asset held as an offline chain), the definer posts an `asset_attestors` message removing `Bob` from the attestor list (or replacing `A1` with `A2`, and `Bob` isn't yet attested by `A2`).
4. When Alice's unit is validated (`validatePaymentInputsAndOutputs` in `validation.js`), the attestor check now runs against the new list via `storage.filterAttestedAddresses`, and `Bob` no longer qualifies: [10](#0-9) 
5. The unit is rejected with `"some output addresses are not attested"`, even though it was valid when composed and sent. Alice's spendable coin (already consumed/marked as an input elsewhere in her wallet flow) must be re-composed, and if this was a private payment already delivered to Bob offline, Bob is now holding a payment chain he cannot get accepted by the network, and Alice cannot easily reclaim the same coin without conflicting double-spend risk.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}

function checkAttestorList(arrAttestors){
	if (!isNonemptyArray(arrAttestors))
		return "attestors not defined";
	if (arrAttestors.length > constants.MAX_ATTESTORS_PER_ASSET)
		return "too many attestors";
	var prev="";
	for (var i=0; i<arrAttestors.length; i++){
		if (!isValidAddress(arrAttestors[i]))
			return "invalid attestor address: "+JSON.stringify(arrAttestors[i]);
		if (arrAttestors[i] <= prev)
			return "attestors not sorted";
		prev = arrAttestors[i];
	}
	return null;
}
