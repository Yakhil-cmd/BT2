### Title
Unbounded, unpaginated submodule processing in `configureWorktree` allows an attacker-controlled commit to cause persistent sync denial - (File: main.go)

### Summary
`git-sync`'s worktree configuration step invokes `git submodule update --init [--recursive]` on every synced commit with no limit on the number, size, or nesting depth of submodules declared in `.gitmodules`. This mirrors the reported bug class in the external report: an untrusted, attacker-controlled data set (there: registered operators/keys; here: submodule entries in a synced commit) is processed by a function with no bound or pagination, and that unbounded processing is on the critical path of a core, repeatedly-invoked operation (`getKeys()`/`getOperators()` there; the sync loop's `SyncRepo` → `configureWorktree` here).

### Finding Description
`configureWorktree` runs the submodule update unconditionally for every new hash whenever `--submodules` is not `off`: [1](#0-0) 

There is no cap on:
- the number of `[submodule "..."]` entries in `.gitmodules`,
- the recursion depth when `submodules=recursive`,
- or the size/history of each submodule repository being cloned/updated.

The only bound applied is `--depth`, which limits commit history per submodule but not the count or nesting of submodules. This call happens inside `SyncRepo`, which itself is wrapped by a single overall deadline `--sync-timeout` (default 120s): [2](#0-1) 

If an attacker with push access to the synced repository (an "attacker-pushed commit", consistent with the accepted threat model) adds a very large number of submodules, or deeply nested recursive submodules, the `submodule update --init --recursive` invocation can exceed `--sync-timeout` on every attempt. Because the outer sync loop simply logs the error, increments `failCount`, and retries at `--period` forever (unless `--max-failures` is set), this is not a transient failure — it repeats identically each cycle since the fetched commit and its `.gitmodules` content never change: [3](#0-2) [4](#0-3) 

### Impact Explanation
This results in persistent sync denial: `git-sync` never successfully publishes a new symlink target once such a malicious commit is fetched, and (depending on `--max-failures`, default `0` = retry forever) will spin indefinitely re-attempting the same expensive/timing-out submodule operation, consuming CPU/network/disk on every cycle without making progress. This matches the "persistent sync denial" impact bar accepted for this scan.

### Likelihood Explanation
Likelihood depends on the trust model of the source repository: exploitation requires write/push access to the repository configured via `--repo` (or a compromised upstream). This is analogous to the "attacker creates multiple wallets" pattern in the original report — no privileged git-sync configuration is required, only the ability to introduce a commit with excessive submodule breadth/depth, which is explicitly a permitted attack path per this scan's rules (attacker-pushed commit/ref).

### Recommendation
Add explicit limits/pagination-equivalent controls around submodule processing, e.g.:
- a configurable maximum submodule count and/or recursion depth before invoking `git submodule update`,
- pre-scanning `.gitmodules` for the synced commit and refusing/erroring out (rather than hanging) if limits are exceeded,
- treating a sync-timeout specifically during submodule update as a fatal, reported condition distinct from generic retryable failures so operators are alerted rather than looping silently.

### Proof of Concept
1. Configure `git-sync --repo=<attacker-writable-repo> --root=/tmp/git --submodules=recursive`.
2. Attacker pushes a commit to that repo whose `.gitmodules` declares a very large number of submodule entries (or a small number of submodules that recursively reference each other/nested chains many levels deep).
3. On the next sync cycle, `configureWorktree`'s `git submodule update --init --recursive` call takes longer than `--sync-timeout`; `SyncRepo` returns an error, `main`'s loop logs it and retries every `--period` indefinitely (with default `--max-failures=0`, retries forever), so the symlink target is never updated for this or any subsequent commit until the offending commit is removed from the fetch history or the operator intervenes.

Note: I could not execute this locally within the tool constraints (no terminal access); the analysis is based on static review of `main.go`'s `configureWorktree`, `SyncRepo`, and the main retry loop shown above. A background Devin session with repo/terminal access would be needed to empirically time a large-submodule PoC against `--sync-timeout`.
