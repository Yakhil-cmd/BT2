### Title
KLAY Bridge Fallback Function Hardcodes `msg.sender` as Destination Recipient, Causing Permanent Fund Loss for Account Abstraction Wallet Users — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

### Summary

The fallback function in `BridgeTransferKLAY` unconditionally passes `msg.sender` as the recipient address on the counterpart chain. Account abstraction (AA) wallets (e.g., Safe) do not share the same address across different chains, so any AA wallet user who sends KLAY directly to the bridge contract will have their funds delivered to an address they do not control on the destination chain, resulting in permanent loss.

### Finding Description

`BridgeTransferKLAY.sol` exposes two entry points for KLAY bridging:

1. `requestKLAYTransfer(address _to, ...)` — caller explicitly supplies the destination address.
2. The Solidity 0.5.x unnamed fallback `function () external payable` — hardcodes `msg.sender` as `_to`. [1](#0-0) 

```solidity
// () requests transfer KLAY to msg.sender address on relative chain.
function () external payable {
    _requestKLAYTransfer(msg.sender, feeOfKLAY, new bytes(0));
}
```

`_requestKLAYTransfer` emits a `RequestValueTransfer` event with `_to = msg.sender`: [2](#0-1) 

The Go-side bridge manager (`node/sc/bridge_manager.go`) reads the `To` field directly from the event and calls `HandleKLAYTransfer` on the counterpart bridge with that address: [3](#0-2) 

`handleKLAYTransfer` on the destination bridge then sends KLAY to `_to` with no further validation: [4](#0-3) 

The full end-to-end path is therefore:

```
user sends KLAY to bridge contract
  → fallback() fires
  → _requestKLAYTransfer(_to = msg.sender)
  → RequestValueTransfer event (to = msg.sender)
  → bridge operator reads event, calls HandleKLAYTransfer(to = msg.sender)
  → destination bridge sends KLAY to msg.sender address on destination chain
```

For an EOA the source and destination addresses are identical, so this is harmless. For an AA wallet (Safe, Argent, etc.) the contract address on the source chain is almost certainly not deployed at the same address on the destination chain, or is owned by a different party.

### Impact Explanation

KLAY sent through the fallback path by an AA wallet user is delivered to an address the user does not control on the destination chain. The transfer is irreversible: the bridge nonce is consumed, the source-chain KLAY is locked/burned, and the destination-chain KLAY is sent to the wrong address. The user suffers a total, permanent loss of the bridged amount.

The corrupted value is the `to` field in the `RequestValueTransfer` event, which propagates unchanged through the operator relay into `HandleKLAYTransfer` and the final `_to.call.value(_value)("")` transfer.

### Likelihood Explanation

- Any user who sends KLAY directly to the bridge contract address (a natural, wallet-agnostic action) triggers the fallback.
- AA wallet adoption is growing; Safe alone reports millions of users and billions in assets.
- The explicit `requestKLAYTransfer` function exists as a workaround, but the fallback is the simpler, more discoverable path and is actively tested and documented.
- No guard in the contract or the Go relay prevents the wrong address from being used.

### Recommendation

Remove or restrict the fallback function so that it reverts with a descriptive error directing users to call `requestKLAYTransfer` with an explicit `_to` address:

```solidity
function () external payable {
    revert("Use requestKLAYTransfer(address _to, ...) to specify destination address");
}
```

Alternatively, if the fallback must be kept for backward compatibility, add a prominent warning in documentation and consider emitting a distinct event so off-chain tooling can flag same-address cross-chain transfers.

### Proof of Concept

1. Deploy the bridge on a parent chain (e.g., Kaia mainnet) and a service chain.
2. Create a Safe multisig wallet on the parent chain at address `0xAA...`.
3. Confirm that `0xAA...` is **not** a Safe controlled by the same owners on the service chain (standard Safe deployments differ by chain state/nonce).
4. Send KLAY directly to the bridge contract from `0xAA...` (triggering the fallback).
5. Observe the `RequestValueTransfer` event: `from = 0xAA...`, `to = 0xAA...`.
6. The bridge operator calls `HandleKLAYTransfer(..., _to = 0xAA...)` on the service-chain bridge.
7. KLAY is delivered to `0xAA...` on the service chain — an address the original Safe owners do not control.
8. Funds are permanently lost.

The test suite itself confirms the fallback sets `to = user1.address` (same as `from`): [5](#0-4)
