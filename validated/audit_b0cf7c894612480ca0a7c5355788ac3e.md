### Title
Webhook signature verification keys on `repository.owner.login` while event handlers act on the unrelated `repository.full_name` field, allowing cross-organization webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate the HMAC signature against using `repository_owner`, a value read straight out of the untrusted JSON payload. Every downstream `Webhooks::Handlers::Handler` subclass, however, resolves the target `Stack`/`Repository` using a *different* payload field, `repository.full_name`. Because these two fields are never cross-checked, an attacker who legitimately controls one GitHub organization (and therefore knows/controls its `webhook_secret`) can forge a signature that Shipit accepts, while pointing the event body at a completely different organization's repository.

### Finding Description
`verify_signature` computes:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [1](#0-0) 
where
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

In Shipit's multi-organization mode, each organization has its own GitHub App and its own `webhook_secret` (`Shipit.github_app_config(organization)`), and `verify_webhook_signature` uses `SecureCompare.secure_compare` against `OpenSSL::HMAC.hexdigest(..., webhook_secret, message)`. [3](#0-2) [4](#0-3) 

Once the signature check passes, `WebhooksController#create` dispatches the raw parsed `params` to the matching handler:
```ruby
Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
``` [5](#0-4) 

All handlers (`PushHandler`, `StatusHandler`, pull-request handlers, etc.) inherit `Handler#stacks`, which resolves the repository from a *different* payload field:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [6](#0-5) 

`repository.owner.login` (used to pick the verification key) and `repository.full_name` (used to pick the acted-upon `Stack`) are independent, attacker-controlled JSON fields inside the same HMAC-signed body — the HMAC covers the raw bytes but says nothing about the semantic relationship between these two fields. Nothing in `WebhooksController` or `Handler` enforces that `repository.full_name` actually starts with `repository.owner.login/`.

This is a direct analog of the reported bug class ("an organization that authenticated versus the repository that is written"): the *authentication scope* (organization whose secret validated the request) and the *authorization scope* (repository whose Stack is mutated) are bound to two unrelated, independently forgeable fields, exactly as `xmsg_.to` was checked separately from the sender validation in the external report's OmniPortal case.

### Impact Explanation
An attacker who is an admin of, or otherwise controls, GitHub App `attacker-org` (with a known/leaked `webhook_secret` for that org — a routine, low-privilege position for a self-service multi-tenant Shipit deployment) can send a POST to `/webhooks` with:
- `X-Hub-Signature` computed from `attacker-org`'s own secret (valid, since verification keys off `repository.owner.login`)
- `repository.owner.login = "attacker-org"` (satisfies signature lookup)
- `repository.full_name = "victim-org/victim-repo"` (used by the handler to select the target `Stack`)

For a `push` event this triggers `PushHandler#process`, which calls `stack.sync_github(expected_head_sha: params.after)` on the victim's stack for a branch matching the payload's `ref`, forcing an unauthorized re-sync/spec cache job against a repository the attacker never has GitHub access to. [7](#0-6) 
For a `status` event, `StatusHandler#process` writes attacker-supplied `state`, `description`, and `target_url` as a commit status directly onto any victim commit whose sha the attacker can guess or has observed, potentially manipulating CI/deployability gating used to decide whether a commit is safe to ship. [8](#0-7) 
This maps to "cross-repository writes" and can influence "an unauthorized deploy" decision, satisfying the Critical/High impact bar.

### Likelihood Explanation
Likelihood is Medium: it requires the attacker to control a legitimate GitHub App installation configured in Shipit's multi-organization `secrets.github` map (i.e., they must be an authorized tenant of at least one organization on the same Shipit instance), which is a realistic scenario for shared/multi-tenant Shipit deployments as documented in `docs/setup.md`'s "Using Multiple Github Applications" section. No GitHub access to the victim's org/repo is required — only knowledge of the victim's `repository.full_name` and, for status forgery, a commit sha.

### Recommendation
In `WebhooksController#verify_signature` (or in each `Handler`), enforce that the field used to select the verifying secret and the field used to select the target `Stack`/`Repository` refer to the same owner. Concretely:
- Reject the webhook (`head(422)`, non-crashing) if `repository.full_name.split('/').first` does not case-insensitively equal `repository_owner`.
- Alternatively, resolve the target stack/repository using the same organization value that was used for signature verification, rather than trusting `repository.full_name` independently.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` and `victim-org`, each with its own GitHub App and `webhook_secret` (multi-org mode per `docs/setup.md`).
2. As an authorized admin of `attacker-org`'s GitHub App, compute:
   ```
   body = {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen sha>",
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
   }.to_json
   signature = "sha1=" + HMAC_SHA1(attacker_org_webhook_secret, body)
   ```
3. `POST /webhooks` with header `X-Github-Event: push`, `X-Hub-Signature: <signature>`, body `body`.
4. `verify_signature` computes `repository_owner => "attacker-org"`, fetches `attacker-org`'s app, and the HMAC validates successfully (`app/controllers/shipit/webhooks_controller.rb:24-30`).
5. `PushHandler` (invoked via `Shipit::Webhooks.for_event('push')`) resolves `repository_name => "victim-org/victim-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`) and calls `sync_github` on the victim's `Stack`, without the attacker ever authenticating to `victim-org`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
