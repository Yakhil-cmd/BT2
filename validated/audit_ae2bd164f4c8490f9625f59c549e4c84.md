### Title
Bad-debt write-down clamps `supply_index` to a positive floor instead of zeroing residual shares, letting wiped positions drain future deposits - (File: contracts/pool/src/interest.rs)

### Summary
The exiv2 bug is a missing validation of the relationship between a total size and an offset/size pair, producing invalid state. The analog in XOXNO Lending is `apply_bad_debt_to_supply_index`, which caps `bad_debt` at the total supplied value but then clamps the resulting `supply_index` **up** to `SUPPLY_INDEX_FLOOR_RAW` instead of recognizing that the residual claim relationship no longer holds. When bad debt equals or exceeds total supplied value, all supply shares should be worthless, yet the floor clamp leaves them with a positive redemption value.

### Finding Description
`apply_bad_debt_to_supply_index` computes `capped = bad_debt.min(total_supplied_value)`, reduces the index pro-rata, and then applies `new_supply_index.max(SUPPLY_INDEX_FLOOR_RAW)` (contracts/pool/src/interest.rs:80-88). On a full wipeout (`bad_debt >= total_supplied_value`), `reduction_factor` is 0 and the correct new index is 0 — but the floor clamp raises it to `RAY/1000`. The scaled `supplied` shares are never burned or zeroed, so `unscale_supply_floor(old_scaled, floor_index)` returns a positive "phantom" claim backed by nothing.

The pool's own unit tests prove the theft path: `test_raw_cache_floor_residual_can_consume_fresh_cash_without_supply_guard` and `test_raw_cache_floor_clamp_strands_claim_without_supply_guard` (contracts/pool/tests/interest.rs:317-428) show a stranded holder withdrawing exactly a fresh depositor's full deposit via `resolve_withdrawal` → `require_reserves` → `burn_supply` → `debit_cash`, leaving the honest supplier's claim unbacked. A third test (`test_raw_cache_seizure_residual_would_drain_fresh_cash_without_supply_guard`, lines 431-495) shows the same via the liquidation seize path.

The permissionless path is `controller::clean_bad_debt` / `liquidate` (both in the allowed entrypoint list), which socialize unrecoverable debt through this function.

### Impact Explanation
Theft of user funds. After a market suffers a full bad-debt wipeout (which is precisely when `clean_bad_debt` is invoked — dust-threshold positions whose collateral cannot cover debt), any subsequent depositor's real tokens are immediately claimable by holders of wiped-out shares. First-in, first-out withdrawal means stranded share holders steal fresh deposits until cash is exhausted; the fresh supplier's position is unbacked and unrecoverable.

### Likelihood Explanation
Reachable by any unprivileged address once bad debt ≥ total supplied value exists — the exact scenario `clean_bad_debt` exists for (positions so small/worthless that liquidation cannot recover them). The attacker only needs to hold pre-wipeout supply shares and wait for (or provide) any post-wipeout deposit before withdrawing. No privileged role, oracle manipulation, or timing race is required; the residual claim persists indefinitely.

### Recommendation
On full wipeout, do not clamp the index up to `SUPPLY_INDEX_FLOOR_RAW` while shares remain outstanding — either allow the index to reach zero, or burn/zero `supplied` (and reconcile `revenue`) atomically when `remaining == 0`. The floor exists to avoid a zero index for future accrual, so the correct fix is to reset the share base (e.g., zero `supplied`/`revenue` alongside the floored index) so no unbacked claim survives.

### Proof of Concept
The behavior is already encoded in the repository's own tests:

1. Alice holds supply shares; a borrower's position becomes bad debt ≥ total supplied value. Keeper calls `clean_bad_debt`; `apply_bad_debt_to_supply_index` clamps `supply_index` to `SUPPLY_INDEX_FLOOR_RAW` (interest.rs:88).
2. Alice's shares still unscale to `> 0` asset units (`unscale_supply_floor`), despite the wipeout.
3. Bob calls `controller.supply(hub, token, amount)` depositing `amount = stranded` tokens; pool `cash = amount`.
4. Alice calls `controller.withdraw(hub, [(token, 0)])` (0 = withdraw-all sentinel); `resolve_withdrawal` pays out `gross = amount` — Bob's entire deposit.
5. `cash = 0 < bob_claim`: Bob's funds are stolen.

The test names explicitly state "without supply guard," indicating none exists in the exercised path, but the controller-level wiring was not fully inspected within the available iterations.
