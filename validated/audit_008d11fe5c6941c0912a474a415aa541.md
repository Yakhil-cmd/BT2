### Title
Operators Can Execute Asset Transfers When Bridge Is Stopped — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`, `BridgeTransferERC20.sol`, `BridgeTransferERC721.sol`)

---

### Summary

The Kaia service-chain bridge uses `isRunning` as its pause/stop mechanism. All user-facing request functions correctly enforce `require(isRunning, "stopped bridge")`, but the three operator-callable handle functions — `handleKLAYTransfer`, `handleERC20Transfer`, and `handleERC721Transfer` — contain no such check. When the bridge owner stops the bridge (e.g., in response to a security incident), operators can still call these functions to transfer KLAY, ERC20, and ERC721 assets out of the bridge contract.

---

### Finding Description

`BridgeTransfer.sol` declares `isRunning` as the bridge's operational gate: [1](#0-0) 

`setRunningStatus(false)` (or its alias `start(false)`) is the owner's mechanism to halt all value transfers: [2](#0-1) 

All three user-facing request paths correctly enforce this gate:

- `_requestKLAYTransfer`: [3](#0-2) 
- `_requestERC20Transfer`: [4](#0-3) 
- `_requestERC721Transfer`: [5](#0-4) 

However, the three operator-callable handle functions carry **no `isRunning` check**:

`handleKLAYTransfer` — modifiers are only `onlyOperators` and `nonReentrant`: [6](#0-5) 

`handleERC20Transfer` — modifier is only `onlyOperators`: [7](#0-6) 

`handleERC721Transfer` — modifier is only `onlyOperators`: [8](#0-7) 

The actual asset-moving lines in each handle function execute unconditionally once the vote threshold is met:

- KLAY transfer: [9](#0-8) 
- ERC20 transfer/mint: [10](#0-9) 
- ERC721 transfer/mint: [11](#0-10) 

---

### Impact Explanation

When the bridge owner calls `setRunningStatus(false)` to halt the bridge (e.g., after detecting an exploit or a misconfiguration), operators can still call `handleKLAYTransfer`, `handleERC20Transfer`, or `handleERC721Transfer` to move KLAY, ERC20 tokens, or ERC721 NFTs out of the bridge contract to arbitrary recipient addresses. In `modeMintBurn = true` mode, operators can additionally mint unbounded ERC20/ERC721 tokens to arbitrary addresses. This directly violates the invariant that a stopped bridge performs no asset transfers.

---

### Likelihood Explanation

The default `operatorThresholds[VoteType.ValueTransfer]` is `1`, meaning a single registered operator can unilaterally execute a handle transfer without any co-signer. The bridge owner may stop the bridge precisely because an operator key is suspected compromised; the missing guard means the stop provides no protection against that operator draining the bridge. The trigger requires only a registered operator address — no external service compromise or majority-validator collusion.

---

### Recommendation

Add `require(isRunning, "stopped bridge")` at the top of each handle function, or extract it into a shared modifier in `BridgeTransfer.sol` and apply it to `handleKLAYTransfer`, `handleERC20Transfer`, and `handleERC721Transfer`.

---

### Proof of Concept

1. Deploy the bridge with default threshold (1 operator).
2. Register `operator` as an operator.
3. Fund the bridge with 10 KLAY.
4. Owner calls `start(false)` — bridge is stopped.
5. `operator` calls `handleKLAYTransfer(txHash, from, attacker, 10 ether, nonce, blockNum, "")`.
6. The call succeeds: `require(isRunning)` is never checked; KLAY is transferred to `attacker`.
7. Bridge balance is now 0 despite being in a stopped state.

The same sequence applies to `handleERC20Transfer` (drains or mints ERC20) and `handleERC721Transfer` (drains or mints ERC721), all while `isRunning == false`.
