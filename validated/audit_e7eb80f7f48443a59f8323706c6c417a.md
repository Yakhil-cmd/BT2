### Title
Uncontrolled recursion in address/asset definition evaluation causes stack-overflow DoS during unit validation - (File: definition.js)

### Summary
`definition.js`'s `validateDefinition()` and `validateAuthentifiers()` each implement an `evaluate()` function that recursively walks an address/asset spending-condition tree (`'and'`, `'or'`, `'not'`, `'r of set'`, `'weighted and'`, `'address'`, `'definition template'`). Unlike the structurally similar recursive evaluators in `formula/validation.js`, `formula/evaluation.js`, and `aa_validation.js`, this recursion has **no call-stack-depth interruption** (no periodic `setImmediate` break, no `MAX_DEPTH` check) — it only tracks a cumulative `complexity`/`count_ops` counter. By contrast, the other oscript/formula/AA evaluators explicitly guard against this exact class of bug: [4](#0-3) [5](#0-4) [6](#0-5) 

### Finding Description
An unprivileged user can post a unit that defines a new address (author `definition`), changes an address definition, or defines an asset's `issue_condition`/`transfer_condition`, all of which are boolean-expression trees validated by `validateDefinition`'s `evaluate()` in `definition.js`. Operators such as `'not'` recurse directly and synchronously:
```
case 'not':
    evaluate(args, path, true, cb);
    break;
```
and `'and'`/`'or'`/`'r of set'`/`'weighted and'` recurse per-branch via `async.eachSeries`, which, because the callback chain executes synchronously in this codebase's usage pattern, still grows the native call stack one frame per nesting level.

The only bound enforced is a cumulative `complexity`/`count_ops` counter checked at the top of every call: [7](#0-6) 

This bounds the *number of nodes* evaluated but does not by itself prevent deep, narrow nesting (e.g., a long chain of nested `'not'` wrappers, or `'and'`/`'or'` chains with a single deeply-nested branch) from accumulating call-stack frames before the counter threshold is reached, since the check happens per-recursive-call rather than as a hard depth ceiling with an interrupt mechanism. `validateAuthentifiers`'s own `evaluate()` (lines 646+) has the same shape and is fully synchronous recursion through the same operator set with no depth interruption at all — the only depth limiter for it is that `validateDefinition` runs first, so it inherits `validateDefinition`'s (weaker) protection.

This mirrors the CVE-2021-46195 root cause: recursive parsing/evaluation of attacker-supplied nested structures with no explicit recursion-depth ceiling, allowing a crafted input to exhaust the call stack.

### Impact Explanation
If a crafted, deeply-nested address/asset definition can drive the evaluator past V8's default stack limit before the `complexity`/`count_ops` cap trips, the node process validating that unit throws an uncaught `RangeError: Maximum call stack size exceeded`, crashing (or hanging, depending on error handling) the validating node. Because address definitions and asset conditions are validated by every node that processes a unit referencing them (any full node, hub, or witness), a single malicious unit could be used to crash validating nodes that receive it — a node-disagreement/availability impact reachable purely by posting a unit as an ordinary, unprivileged user (no elevated network or peer role required).

### Likelihood Explanation
Reachability is straightforward — any address owner, AA trigger author, or asset issuer can submit a definition/condition tree with arbitrary nesting shape. The actual crash depends on whether the configured `MAX_COMPLEXITY`/`MAX_OPS` values are large enough (or the depth-vs-node-count ratio achievable, e.g., via a single-branch `'not'`/`'and'` chain) to reach V8's stack limit before the counter check trips — I could not confirm the exact numeric limits during this investigation (only match locations, not file contents, were retrievable), so I cannot claim certainty that the threshold is exploitable versus that it caps out safely below the practical stack-overflow depth. This is the main uncertainty in this finding, and it should be verified with a live/sandbox reproduction (construct a unit definition consisting of `['not', ['not', [...]]]` nested to the `MAX_OPS`/`MAX_COMPLEXITY` limit and confirm whether it throws a native stack error before the logical validation error is returned).

### Recommendation
Add the same protection already used elsewhere in the codebase to `definition.js`'s two `evaluate()` functions (`validateDefinition` and `validateAuthentifiers`): track a recursion depth counter separate from `complexity`/`count_ops`, enforce a hard `MAX_DEPTH`, and periodically interrupt the call stack with `setImmediate` (as done in `aa_validation.js`'s `validate()` and `formula/validation.js`/`formula/evaluation.js`'s `evaluate()`), so a deeply-nested definition tree fails validation gracefully instead of risking a native stack overflow.

### Proof of Concept
1. Construct an address definition (or asset `issue_condition`/`transfer_condition`) that is a long, narrow chain of nested `'not'` operators wrapping a single valid leaf (e.g., `['not', ['not', ['not', ... , ['sig', {...}] ... ]]]`), with nesting depth chosen to stay under `MAX_OPS`/`MAX_COMPLEXITY` but as deep as the limits allow.
2. Post a unit whose author uses this definition (new address definition or definition-change), or an asset definition unit with this as its `transfer_condition`.
3. Have a node validate the unit via `validateAuthentifiers`/`validateDefinition` in `definition.js` and observe whether it throws `RangeError: Maximum call stack size exceeded` instead of returning a normal validation error — this would confirm the crash is reachable within the enforced complexity limits.
