### Title
Webhook signature is verified against the organization derived from `repository.owner.login`, but the stack that gets written to is resolved from the independent, unverified `repository.full_name` field - allowing a cross-organization forged webhook to trigger syncs/deploys on another org's stack (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
The C4 report's root cause is a "verify against X, act on Y" mismatch: `Trading` approves/authorizes fee movement for one accounting flow but the transfer that actually executes reads a different, unguarded amount. The exact analog exists in `Shipit`'s webhook pipeline: the HMAC signature check picks its secret using one field of the untrusted JSON payload (`repository.owner.login`), while the handler that performs the actual state-mutating action (triggering a sync/deploy job on a `Stack`) resolves its target from a *different*, unrelated field of the same untrusted payload (`repository.full_name`). Nothing binds these two fields together, so a valid signature for organization A does not guarantee the acted-upon repository/stack actually belongs to organization A.

### Finding Description
`WebhooksController#verify_signature` selects which `GitHubApp` (and therefore which `webhook_secret`) to validate the inbound signature against by reading `repository_owner`, which is computed purely from the untrusted request body: [1](#0-0) [2](#0-1) 

Once the signature is deemed `verified` for that organization's secret, `create` dispatches the *entire raw payload* to the registered handlers: [3](#0-2) 

Every handler (e.g. `PushHandler`) resolves the target `Stack` not via `repository.owner.login` (the field that was authenticated) but via `repository.full_name`, an entirely separate JSON field that was never checked for consistency with the owner used for signature verification: [4](#0-3) [5](#0-4) 

`Repository.from_github_repo_name` looks up stacks purely by the `full_name` string, with no additional ownership check tying it back to the verified organization.

**The broken equality:** `organization authenticated by signature == organization/repository that gets written to` does not hold, because the controller derives the verifying secret from `repository.owner.login` while the handler layer derives the write target from `repository.full_name` — two independent fields of the same attacker-influenced JSON body.

### Impact Explanation
In a multi-tenant Shipit deployment (multiple entries under the `github:` key in `secrets.yml`, one per organization, each with its own `webhook_secret` known to that organization's own administrators/webhook configuration), an actor who legitimately knows organization A's `webhook_secret` (because they administer org A's GitHub App per the documented setup flow) can POST directly to the public `/webhooks` endpoint with a JSON body where `repository.owner.login = "orgA"` (so `verify_signature` validates against the secret they know) but `repository.full_name = "orgB/victim-repo"`. The signature check passes because it is computed and verified purely against `orgA`'s secret and the raw body the attacker crafted themselves; the handler then locates and acts on `orgB`'s stack — e.g. `PushHandler` calling `stack.sync_github(...)` — an unauthorized cross-repository/cross-organization write triggered by a party with no legitimate relationship to `orgB`.

This matches the rule's "Critical" bucket for cross-repository writes / unauthorized deploy triggers: the webhook endpoint is unauthenticated by any Shipit session or `ApiClient` token — it is a public endpoint gated solely by the HMAC check, and that check does not bind the verified organization to the acted-upon repository.

### Likelihood Explanation
The `/webhooks` endpoint is intentionally public (no session, no `ApiClient` token) so that GitHub can reach it. Exploiting the flaw requires only knowledge of *any one* organization's `webhook_secret` configured on the Shipit instance — which, per `docs/setup.md`, is a value the org's own operators generate and hold "in clear on the side." Any tenant/organization admin on a shared Shipit instance therefore already possesses everything needed to forge a payload naming a different organization's repository, without needing that other organization's secret, private key, or GitHub credentials. This is a realistic likelihood for any multi-org Shipit deployment.

### Recommendation
In `Handler#stacks`/`repository_name` (and any other handler that derives its target from `full_name`), cross-check that the resolved repository's owner matches the organization whose `webhook_secret` was used to authenticate the request (i.e., pass down and enforce `repository_owner` from `WebhooksController` through to the handler, rejecting payloads where `repository.full_name`'s owner segment does not match `repository.owner.login`/the verifying organization).

### Proof of Concept
1. Deploy Shipit with two orgs configured in `secrets.yml`: `orgA` (secret known to attacker, who administers orgA's GitHub App) and `orgB` (victim, stack `orgB/victim-repo` exists in Shipit).
2. Attacker crafts a JSON push payload:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-controlled sha>",
     "repository": {
       "owner": { "login": "orgA" },
       "full_name": "orgB/victim-repo"
     }
   }
   ```
3. Attacker computes `sha1=HMAC(secret_of_orgA, payload_body)` and sends:
   ```
   POST /webhooks
   X-Github-Event: push
   X-Hub-Signature: sha1=<computed>
   <payload_body>
   ```
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "orgA")` (from `repository.owner.login`), and the signature validates successfully because it was computed with `orgA`'s own known secret. [1](#0-0) 
5. `create` dispatches to `PushHandler`, whose `stacks` method resolves the target using `repository.full_name = "orgB/victim-repo"`, completely bypassing any check that this repo belongs to `orgA`. [4](#0-3) 
6. `PushHandler#process` triggers `stack.sync_github(expected_head_sha: params.after)` on `orgB`'s stack — an unauthorized action on a stack the attacker has no legitimate relationship to. [5](#0-4)
