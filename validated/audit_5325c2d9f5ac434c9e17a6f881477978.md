This confirms the vulnerability. `User#authorized?` at `app/models/shipit/user.rb:80-82` checks `teams.where(id: Shipit.github_teams.map(&:id)).exists?` — purely by team `id`, with no re-verification of organization. Combined with `MembershipHandler#find_or_create_team!` at `app/models/shipit/webhooks/handlers/membership_handler.rb:38-42`, which does `Team.find_or_create_by!(github_id: params.team.id)` and only sets `team.organization` inside the creation block (never executed when the row already exists), the org binding is never re-checked on lookup.

The critical piece is `WebhooksController#verify_signature` at `app/controllers/shipit/webhooks_controller.rb:24-49`: it picks the GitHub App/secret to verify against via `repository_owner`, which is read straight from the attacker-controlled payload (`repository.owner.login` or fallback `organization.login`). An attacker who owns `attacker-org` with a legitimately installed GitHub App can sign a `membership` payload with their own real `webhook_secret`, set `organization.login: "attacker-org"` (or matching `repository.owner.login`) so `verify_signature` passes using `attacker-org`'s own secret, while setting `team.id` to the `github_id` of a `Team` row already in `Shipit.github_teams` that actually belongs to `victim-org`. Because the lookup is `find_or_create_by!(github_id:)` with no check that `team.organization == params.organization.login`, the existing victim-org `Team` row is returned and `team.add_member(User.find_or_create_by_login!(params.member.login))` grants the attacker's GitHub login membership in that team, making `User#authorized?` true for them.

### Title
Cross-organization team hijack via unchecked `github_id` lookup in `MembershipHandler#find_or_create_team!` - (`app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`MembershipHandler#find_or_create_team!` looks up teams solely by `github_id` without verifying that the payload's `organization.login` matches the `Team`'s stored `organization`. Since `WebhooksController#verify_signature` selects the verifying GitHub App/secret from the attacker-controlled `repository_owner`/`organization.login` field, an attacker owning any legitimately GitHub-App-installed organization can send a validly-signed `membership` event referencing a victim `Team`'s `github_id`, adding themselves as a member and passing `User#authorized?`.

### Finding Description
Broken binding (should hold, but is never checked): `Team#organization == params.organization.login` for the row matched by `Team.find_or_create_by!(github_id: params.team.id)`.

- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) picks the app/secret with `Shipit.github(organization: repository_owner)`, and `repository_owner` (`app/controllers/shipit/webhooks_controller.rb:59-62`) is read directly from attacker-supplied JSON (`repository.owner.login`, falling back to `organization.login`). An attacker who legitimately installed Shipit's GitHub App on their own `attacker-org` can produce a genuinely valid `X-Hub-Signature` for any payload as long as `repository_owner` resolves to `attacker-org`. [1](#0-0) 
- `MembershipHandler#find_or_create_team!` (`app/models/shipit/webhooks/handlers/membership_handler.rb:38-43`) does `Team.find_or_create_by!(github_id: params.team.id) { |team| team.organization = params.organization.login }`. The block that sets `organization` only runs on *creation*; when a row with that `github_id` already exists (the victim's team), it is returned unmodified and unchecked against `params.organization.login`. [2](#0-1) 
- `MembershipHandler#process` then calls `team.add_member(User.find_or_create_by_login!(params.member.login))` (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-28`), inserting a `Membership` for the attacker's own GitHub login into the victim's `Team`. [3](#0-2) 
- `User#authorized?` (`app/models/shipit/user.rb:80-82`) authorizes based purely on `teams.where(id: Shipit.github_teams.map(&:id)).exists?`, with no re-check of organization, so the newly created `Membership` immediately grants authorization. [4](#0-3) 

Exploit flow: attacker enumerates/knows the victim `Team`'s `github_id` (public GitHub team id), then POSTs `/webhooks` with `X-Github-Event: membership`, a valid `X-Hub-Signature` computed with `attacker-org`'s own `webhook_secret`, and a body `{"action":"added","team":{"id":<victim_github_id>,...},"organization":{"login":"attacker-org"},"member":{"login":"attacker-login"},"repository":{"owner":{"login":"attacker-org"}}}`. `verify_signature` passes (real secret, real org), `find_or_create_team!` returns the victim's `Team` row by id alone, and the attacker's login becomes a member.

### Impact Explanation
This is a High-severity escalation into `Shipit.github_teams` authorization: an attacker with no relationship to the victim organization can gain membership in a `Team` referenced by `Shipit.github_teams`, and thus have `User#authorized?` return true, granting them equivalent authenticated access to Shipit as legitimate members of the victim's team — for repositories/stacks tied to that access model. The attack is repeatable against any `Team`/`github_id` known to the attacker and does not require any secret belonging to the victim organization.

### Likelihood Explanation
Preconditions: `Shipit.github_teams` non-empty (a documented, common configuration — see `docs/setup.md`'s `oauth.teams` setting) and the attacker running any legitimately GitHub-App-installed org so their own webhook fires with a real `webhook_secret`. GitHub team ids are discoverable from public org team pages/API. No Shipit secrets, sessions or privileged roles are required, and the request is a single unauthenticated POST, making this cheap and repeatable.

### Recommendation
In `MembershipHandler#find_or_create_team!`, verify `params.organization.login` against the found `Team#organization` on every lookup (not only at creation), and raise/drop the event on mismatch instead of silently reusing the existing record. Additionally, tie `repository_owner`/`verify_signature`'s app selection more strictly to the actual signing organization rather than trusting `organization.login` from the unverified body before signature validation, or validate that `params.organization.login` matches the app configured for `repository_owner` post-verification.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`-style, no live GitHub):
1. Seed `Team.create!(github_id: 42, organization: 'victim-org', slug: 'developers', ...)` and stub `Shipit.github_teams` to include it.
2. Configure a second organization `attacker-org` in `Shipit.secrets.github` with its own `webhook_secret`.
3. Compute a valid `X-Hub-Signature` using `attacker-org`'s `webhook_secret` over a JSON body: `{"action":"added","team":{"id":42,"name":"x","slug":"x","url":"http://x"},"organization":{"login":"attacker-org"},"member":{"login":"attacker-login"},"repository":{"owner":{"login":"attacker-org"}}}`.
4. POST to `/webhooks` with `X-Github-Event: membership` and that signature.
5. Assert `response.status == 200`, assert a `Membership` row now exists linking `attacker-login`'s `User` to the `Team` with `github_id: 42`, and assert `User.find_by(login: 'attacker-login').authorized?` is `true` — demonstrating the binding `Team#organization == params.organization.login` was never enforced.
