### Title
Untyped/undomain-separated signature scheme in `is_valid_sig` / `is_valid_signed_package` enables signature replay across AAs and networks - (File: `formula/evaluation.js`, `signed_message.js`, `object_hash.js`)

### Summary
Obyte exposes two generic oscript primitives to AA authors that let an AA verify an arbitrary address's ECDSA signature over application-chosen data: `is_valid_sig(message, pem_key, sig)` and `is_valid_signed_package(signed_package, address)`. Both ultimately hash and verify "naked", untyped payloads with no domain separator (no target-AA address, no network/`alt` identifier, no purpose/type tag baked in by the platform). This is exactly the root cause described in the Rigor report: whoever controls the signed bytes decides the semantics, so the same signature can be replayed wherever the byte layout happens to match, unless every individual AA author manually reinvents a full domain-separation scheme.

### Finding Description
- `is_valid_sig` (`formula/evaluation.js:1704-1734`) takes an oscript-evaluated `message` string, a PEM public key, and a signature, and calls `signature.verifyMessageWithPemPubKey` / `verifyMessageWithSecp256k1PemPubKey` (`signature.js:27-70`) directly on the raw message bytes. There is no unit hash, no chain/AA binding, no type prefix - the "message" is whatever string the AA definition constructs from trigger data. [1](#0-0) [2](#0-1) 

- `is_valid_signed_package` (`formula/evaluation.js:1657-1701`) accepts a `signed_message` object supplied by the trigger and validates it via `signed_message.validateSignedMessage`, which in turn hashes the package with `objectHash.getSignedPackageHashToSign` and checks the address's on-chain definition against it. [3](#0-2) [4](#0-3) 

- `getSignedPackageHashToSign` (`object_hash.js:97-103`) only strips `authentifiers` and hashes the remaining object (`signed_message`, `version`, `last_ball_unit`, `authors`). It does not include the network identifier (`alt`), nor any AA address, asset id, or purpose tag - the platform leaves complete freedom to the application over what `signed_message` contains. [5](#0-4) 

Because the platform-level primitive gives no built-in guarantee that a signature is scoped to (a) a specific network (mainnet vs testnet share the same address format and same signing keys - `alt` is not part of the hashed payload), (b) a specific AA/consumer of the signature, or (c) a specific function/purpose, any AA whose author naively checks `is_valid_sig`/`is_valid_signed_package` over a generic payload (e.g. `{action, amount, asset}`) is exposed to the same four classes of attack described in the Rigor report:
1. Reuse across different AAs that happen to expect the same JSON shape for `signed_message`/`message`.
2. Reuse across networks (a signature produced for testnet is valid on mainnet for the same address, and vice versa, since `alt`/chain id is not part of the signed bytes).
3. Reuse across different functions of the same AA/oscript definitions that branch on the same signed field set.
4. Phishing: since the payload format is generic (arbitrary strings/objects), a malicious dApp can present a "harmless" signing request whose bytes happen to satisfy another AA's `is_valid_sig` condition.

### Impact Explanation
Any unprivileged AA trigger sender who can obtain (through phishing, cross-AA byte-format collision, or network replay) a previously produced signature can submit it as trigger `data`, causing a victim AA that gates fund release/authorization on `is_valid_sig`/`is_valid_signed_package` to treat the replayed signature as fresh authorization. Since AAs commonly use these primitives as an off-chain "oracle attestation" or "authorization" pattern (address ownership proof, price/data attestation, permissioned action approval), a successful replay results in unauthorized AA fund release/spending or bypass of an authorization gate that the AA author believed was single-use/single-purpose - a concrete AA fund loss scenario. This is the same fundamental class of bug as the referenced Rigor finding: signature reuse enabled by the absence of a mandatory domain separator at the primitive/library level, pushing the entire security burden onto every individual AA author who uses these primitives.

### Likelihood Explanation
Likelihood is moderate-to-high for AAs that use these primitives as a signature-based authorization gate without independently re-implementing a full domain-separation scheme (embedding AA address, network id, and a purpose/nonce field inside the signed payload themselves), since the primitives themselves provide none of these guarantees. Given that `is_valid_sig`/`is_valid_signed_package` are documented, general-purpose oscript functions intended to be reused across many different AAs, cross-AA byte-format collisions and phishing scenarios are realistic, and the mainnet/testnet replay path is deterministic once such an AA exists on both networks with the same address (address derivation only depends on the definition, not on network).

### Recommendation
Introduce mandatory domain separation at the platform level for both primitives:
1. Include the network identifier (`alt`) in `getSignedPackageHashToSign` and require it in the payload consumed by `is_valid_sig`/`is_valid_signed_package`, exactly as it is already meaningfully differentiated in unit hashing.
2. Require/auto-inject the consuming AA's address (or a caller-supplied domain tag) into the hashed payload for `is_valid_signed_package`, and document/encourage the same discipline for `is_valid_sig` message construction (e.g., provide a helper that concatenates `this_address`, `alt`, and a type tag before hashing).
3. Provide built-in oscript helpers (analogous to EIP-712's typed-data hashing) so AA authors are not required to hand-roll domain separation themselves, mirroring the report's core recommendation to adopt a standardized typed-signing scheme instead of ad hoc raw hashing.

### Proof of Concept
1. Deploy AA `A` that on trigger checks `is_valid_signed_package(trigger.data.signed_package, some_address)` where `signed_message = {action:"withdraw", amount:100}` and, on success, sends `amount` of funds to the trigger sender.
2. Deploy (or have already deployed on another network/dApp) AA `B` with an identical `signed_message` shape used for an unrelated, harmless purpose (e.g., a vote/attestation) that `some_address`'s owner willingly signs off-chain via `signed_message.signMessage` (`signed_message.js:28-112`).
3. Attacker captures the `signed_package` object produced for AA `B` (or for the same AA on testnet) and resubmits it unmodified as `trigger.data.signed_package` to AA `A` on mainnet.
4. `signed_message.validateSignedMessage` (`signed_message.js:255-303`) recomputes `getSignedPackageHashToSign` on the naked package and validates the address's authentifiers against it - since no network/AA-specific tag was part of the hashed bytes, verification succeeds and AA `A` releases funds to the attacker, even though the address owner never intended to authorize this withdrawal.

function verifyMessageWithPemPubKey(message, signature, pem_key, bPostPemCurvesFix) {
	var contentB64 = pem_key
		.replace("-----BEGIN PUBLIC KEY-----", "")
		.replace("-----END PUBLIC KEY-----", "")
		.replace(/\s/g, "");
	var der = Buffer.from(contentB64, 'base64');
	var algIdStart = der[1] <= 0x7F ? 4 : der[1] === 0x81 ? 5 : der[1] === 0x82 ? 6 : -1;
	if (algIdStart >= 0 && der.slice(algIdStart, algIdStart + SECP256K1_ALG_ID.length).equals(SECP256K1_ALG_ID)
			&& bPostPemCurvesFix)
		return verifyMessageWithSecp256k1PemPubKey(message, signature, der);

	var verify = crypto.createVerify('SHA256');
	verify.update(message);
	verify.end();
	var encoding = ValidationUtils.isValidHexadecimal(signature) ? 'hex' : 'base64';
	try {
		return verify.verify({key: pem_key}, signature, encoding);
	} catch(e) {
		console.log("exception when verifying with pem key: " + e);
		return false;
	}
}

function getSignedPackageHashToSign(signedPackage) {
	var unsignedPackage = _.cloneDeep(signedPackage);
	for (var i=0; i<unsignedPackage.authors.length; i++)
		delete unsignedPackage.authors[i].authentifiers;
	var sourceString = (typeof signedPackage.version === 'undefined' || signedPackage.version === constants.versionWithoutTimestamp) ? getSourceString(unsignedPackage) : getJsonSourceString(unsignedPackage);
	return crypto.createHash("sha256").update(sourceString, "utf8").digest();
}
