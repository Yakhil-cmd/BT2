### Title
Webhook signature check authenticates the org named in `repository.owner.login`, but every event handler acts on the unverified `repository.full_name` / other payload fields, letting an attacker forge events for any tracked repo by targeting an org with no `webhook_secret` configured - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App config (and thus which `webhook_secret`) to check against using a value read straight out of the untrusted payload, then event handlers act on a different, equally untrusted field from the same payload to decide which `Stack`/`Repository`/`Team` to mutate. When Shipit is configured for more than one GitHub organization (a supported, documented configuration, see `config/secrets.development.shopify.yml`) and any one of those organizations has no `webhook_secret` set (explicitly called "optional" in `docs/setup.md`), `GitHubApp#verify_webhook_signature` returns `true` unconditionally for that organization. An attacker can therefore submit a completely fabricated, unsigned webhook body whose `repository.owner.login` (or `organization.login`) matches the org lacking a secret, while `repository.full_name` (or other identifying fields) names a *different*, fully protected org/repo that Shipit tracks - and have it processed as authentic.

### Finding Description
The signature check: [1](#0-0) 
selects the GitHub App/secret using `repository_owner`: [2](#0-1) 

That value comes straight out of the JSON body the "attacker" (unauthenticated POST to `/webhooks`) supplies. The underlying verification is a no-op when the selected org's secret is blank: [3](#0-2) 

Meanwhile, every downstream handler resolves the target repository from a *separate* field of the same attacker-controlled payload, `repository.full_name`, with no re-check that it matches the organization that was actually authenticated: [4](#0-3) [5](#0-4) 

So the equality that should hold - `organization whose secret authenticated the request == organization/repository the handler writes to` - is not enforced. `repository.owner.login` (used only to pick a webhook secret) and `repository.full_name` (used to find the `Repository`/`Stack` to act on) are independent, unauthenticated strings in the same POST body. Multi-org support is a first-class, documented deployment mode: [6](#0-5) 
and `webhook_secret` is explicitly optional: [7](#0-6) 

### Impact Explanation
If any configured organization has no `webhook_secret`, an attacker with no Shipit session, no `ApiClient` token, and no knowledge of any real secret can forge arbitrary GitHub webhook events (`push`, `pull_request`, `membership`, `status`, `check_suite`, etc.) that get processed as if they came from GitHub for any repository Shipit tracks, by simply setting `repository.owner.login`/`organization.login` to the unsecured org while pointing `repository.full_name` at the target org/repo. Concretely this can:
- Trigger `stack.sync_github(expected_head_sha:)` for arbitrary stacks via forged `push` events.
- Auto-provision stacks and inject fabricated pull-request metadata via `PullRequest#github_pull_request=`.
- Most severely, forge a `membership` "added" event naming an arbitrary GitHub login as a member of a `Shipit::Team`, directly escalating that identity into `Shipit.github_teams` authorization (`User#authorized?` checks team membership) - matching the "escalation into `Shipit.github_teams` authorization" High-impact category.

This is a real authentication-vs-authorization binding break reachable by a fully unprivileged network attacker, contingent only on a documented, "optional" operator configuration gap rather than any credential compromise.

### Likelihood Explanation
Likelihood depends on deployment configuration: it requires (a) multi-organization GitHub App configuration (documented/supported) and (b) at least one configured organization having a blank `webhook_secret` (explicitly optional per setup docs, and thus plausible in real deployments, e.g., a low-traffic secondary org added without a secret). Given webhook secret is opt-in rather than enforced, and Shipit explicitly supports multiple orgs, this is a realistic misconfiguration rather than a purely theoretical one.

### Recommendation
- Require `webhook_secret` to be present for every configured organization (fail closed instead of `return true unless webhook_secret`).
- After verifying the signature, re-derive the organization/repository strictly from the same trusted, verified fields used for verification, and reject the payload if `repository.full_name`'s owner does not match the organization whose secret was used to authenticate it.
- Consider binding webhook processing to the specific `Shipit.github(organization:)` instance that succeeded verification instead of re-deriving identity from the payload for handler dispatch.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `orgA` (no `webhook_secret`) and `orgB` (has a secret, and has tracked repositories/teams).
2. POST to `/webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "organization": { "login": "orgA" },
  "team": { "id": 123, "slug": "developers", "name": "Developers", "url": "http://example.com" },
  "member": { "login": "attacker-github-login" },
  "repository": { "owner": { "login": "orgA" } }
}
```
No `X-Hub-Signature` header is required because `verify_webhook_signature` short-circuits to `true` for `orgA` (see `lib/shipit/github_app.rb#76-83`). If `team.id` corresponds to a `Shipit::Team` that is part of `orgB`'s `Shipit.github_teams`, membership is created, and once `attacker-github-login` completes normal OAuth login, `User#authorized?` returns `true`, granting access that should have required `orgB` credentials.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
```
