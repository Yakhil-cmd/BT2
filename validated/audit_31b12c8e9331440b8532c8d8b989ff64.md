### Title
Webhook signature is verified against an organization inferred from the payload, but the repository/commit that gets written is resolved from a different, independently-controlled payload field - allowing cross-repository status/commit writes ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` computes the signing organization used to look up the correct `webhook_secret` from `repository.owner.login`, falling back to `organization.login` if the former is absent. [1](#0-0)  The event handlers, however, resolve which `Repository`/`Stack`/`Commit` to mutate from a completely independent payload field, `repository.full_name`. [2](#0-1)  Nothing ties the two together: the engine never asserts that the organization whose secret validated the HMAC signature is the same organization that owns the repository being acted upon. Worse, `StatusHandler` doesn't even use the `stacks`/`repository_name` scoping helper at all - it updates any `Commit` in the entire Shipit instance matching a given `sha`, with no repository check whatsoever. [3](#0-2) 

### Finding Description
`verify_signature` derives `repository_owner` from the JSON body itself (`params.dig('repository','owner','login') || params.dig('organization','login')`) and uses it to select which configured GitHub App/`webhook_secret` should validate `X-Hub-Signature`. [4](#0-3)  `Shipit.github(organization:)` supports multiple configured organizations (raising `Shipit::GithubOrganizationUnknown` for unrecognised ones), so a Shipit instance backing more than one GitHub org/App has more than one valid `webhook_secret`. [5](#0-4) 

Once the signature check passes, `Handler.call(params)` (i.e. `new(params).process`) runs with the raw, attacker-supplied JSON. [6](#0-5)  The base `Handler#stacks`/`#repository_name` helpers read `payload.dig('repository', 'full_name')` - a field that is never cross-checked against the `repository_owner`/`organization.login` value used for signature verification. [2](#0-1) 

Concretely:
- The equality the engine implicitly relies on is: `organization_used_to_verify_signature == owner(repository_being_written)`.
- Before the attacker's request: this equality holds only because, in normal GitHub-originated traffic, `repository.owner.login`/`organization.login` and `repository.full_name`'s owner segment always agree (GitHub itself fills them in consistently).
- After the attacker's crafted request: the attacker (who legitimately possesses/knows the `webhook_secret` for org A, e.g. because they run their own low-privilege test repository/organization onboarded to the same Shipit instance) sends a payload where `organization.login` = "org-A" (so the HMAC is computed/verified with org A's secret) while `repository.full_name` = "org-B/some-repo" - a repository belonging to an entirely different, victim organization also registered in this Shipit instance. The signature check passes (it only validates org A's secret against the raw body), but the handler acts on org B's `Repository`/`Stack`/`Commit` records.
- `StatusHandler` is the sharpest case: it performs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with **no repository scoping at all**, so a signature valid for any one onboarded organization lets the attacker forge a commit status (`state`, `context`, `target_url`, `description`) for any commit sha known to exist anywhere in the Shipit instance, regardless of which org/repo it belongs to. [7](#0-6) 

### Impact Explanation
Forged/cross-org commit statuses are used by Shipit to gate deployability and continuous delivery decisions elsewhere in the engine. An attacker who only holds a valid webhook secret for their own low-privilege organization/App can inject a fake "success" status on a commit belonging to a stack they have no access to, and if that stack has `continuous_deployment` enabled, this can trigger an unauthorized deploy - satisfying the "Critical: unauthorized deploy" bar. Even short of triggering an actual deploy, this is a concrete cross-repository/cross-organization write (fabricated CI status, `PushHandler`-triggered `sync_github` calls, or PR label/merge-state mutations via the same `repository.full_name` trust gap) into a Stack the attacker's credentials were never authorized to touch.

### Likelihood Explanation
This requires the Shipit instance to be configured with more than one GitHub organization/App (each with its own `webhook_secret`) - a supported, documented multi-tenant configuration, not a misconfiguration. Given that, any unprivileged holder of a webhook secret for one onboarded, low-privilege organization can exploit this purely by crafting a JSON body; no `ApiClient` token, GitHub App private key, or repository write access is needed. This matches the allowed rules (attacker only needs "an organization that authenticated versus the repository that is written" mismatch, no session/token required).

### Recommendation
In `WebhooksController#verify_signature`, after determining `repository_owner` and validating the signature, re-derive the owning organization from `repository.full_name` as well and reject the request (422) if it disagrees with the organization whose secret validated the signature. Additionally, `Handler#stacks`/`StatusHandler#process` should always scope lookups (including `Commit.where(sha:)`) by the verified repository/organization rather than trusting `repository.full_name` unchecked.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` and `org-b`, each with its own GitHub App/`webhook_secret` (multi-org config supported by `Shipit.github(organization:)`).
2. As a user who only knows `org-a`'s `webhook_secret` (e.g. an org-a repo admin with no rights on org-b), build a `status` event JSON body:
   ```json
   {
     "sha": "<sha of a commit belonging to an org-b stack>",
     "state": "success",
     "context": "ci/forged",
     "organization": { "login": "org-a" }
   }
   ```
   Note there's no `repository` key needed for `StatusHandler`, since it never checks it.
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(org-a secret, raw_body)>` and POST to `/github/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` succeeds because org-a's secret validates the signature (`app/controllers/shipit/webhooks_controller.rb:24-30`).
5. `StatusHandler#process` updates the status of the org-b commit (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`), even though the attacker never had any credential tied to org-b.

module Shipit
