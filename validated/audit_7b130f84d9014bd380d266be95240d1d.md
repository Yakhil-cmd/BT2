### Title
Cross-tenant PullRequest assignee mutation via webhook signature verified against attacker-controlled organization naming a victim repository - ([File: app/models/shipit/webhooks/handlers/pull_request/assigned_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret used to verify `X-Hub-Signature` based on `params.dig('repository','owner','login')` [1](#0-0) [2](#0-1) , while `PullRequestAssignedHandler#process` resolves the repository/`PullRequest` to mutate from the independent `params.repository.full_name` field of the same attacker-supplied JSON body [3](#0-2) . Because nothing binds these two fields together, and because `verify_webhook_signature` trivially returns `true` when the resolved org's `webhook_secret` is blank [4](#0-3) , an attacker who controls any Shipit-configured organization with no webhook secret can forge a payload naming a victim repository/PR and have its assignees overwritten.

### Finding Description
The broken binding is: `organization used to verify X-Hub-Signature (params.repository.owner.login)` == `organization owning the repository/PullRequest whose assignees are written (params.repository.full_name)`.

Trace:
1. `WebhooksController#verify_signature` computes `repository_owner = params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` and calls `Shipit.github(organization: repository_owner)` to fetch the `GitHubApp` config/secret to check the HMAC against [5](#0-4) .
2. `Shipit.github_app_config` simply looks up the organization key in `secrets.github`, with no other validation, and `GitHubApp#verify_webhook_signature` returns `true` unconditionally if that org's `webhook_secret` is blank/unset [6](#0-5) [4](#0-3) . Multiple test/example configs in this repo demonstrate multi-org setups where `webhook_secret` is left nil per org [7](#0-6) .
3. `PullRequestAssignedHandler#process` never re-checks which org authenticated the request. It derives the target `repository` solely from `params.repository.full_name` via `Shipit::Repository.from_github_repo_name` and finds/updates the `PullRequest` scoped to that repository's stacks [8](#0-7) .
4. Since `repository.owner.login` (used for signature routing) and `repository.full_name` (used for the actual write) are both attacker-controlled fields inside the same unauthenticated JSON body, an attacker can set them to different values: `repository.owner.login = "attacker-org"` (a Shipit-configured org with no webhook secret) while `repository.full_name = "victim-org/victim-repo"`.

Exploit flow: attacker sends `POST /webhooks` with header `X-Github-Event: pull_request`, any `X-Hub-Signature` value (or none, matching format `sha1=...`), and body:
```json
{
  "action": "assigned",
  "number": <victim PR number>,
  "pull_request": { ...valid schema..., "assignees": [{"login": "attacker"}], ... },
  "repository": { "full_name": "victim-org/victim-repo", "owner": { "login": "attacker-org" } },
  "sender": { "login": "attacker" }
}
```
`verify_signature` authenticates this against `attacker-org`'s (secret-less) config and passes trivially; the handler then updates the victim's `Shipit::PullRequest#assignees` (and other PR metadata) for `victim-org/victim-repo` [9](#0-8) .

Existing guards do not prevent this: `drop_unhandled_event` only checks the event type is registered [10](#0-9) ; the `ExplicitParameters` schema only validates types/presence, not owner/full_name consistency [11](#0-10) ; `Repository#from_github_repo_name` performs a plain lookup with no ownership cross-check [12](#0-11) .

### Impact Explanation
A payload authenticated for one tenant/organization mutates `PullRequest` records belonging to a different tenant's repository — an unauthorized cross-tenant write matching the "payload for one repository mutating another's ... record" Critical category. The attacker can repeatedly forge `assigned`/`unassigned` events for any repository/PR number tracked by Shipit, corrupting `assignee`/`assignees` metadata that may feed downstream merge-authorization or review-stack display logic. Blast radius covers every stack/repository configured in the same Shipit instance, not just the attacker's own.

### Likelihood Explanation
This requires: (a) the Shipit instance to be configured in multi-organization mode (`secrets.github` keyed by org) with at least one org that has no `webhook_secret` set — a configuration pattern shown as valid/expected in this repo's own fixtures and docs [13](#0-12)  and (b) the attacker to know or control that org's name (e.g., their own org onboarded to the same Shipit instance). Given those preconditions — plausible in any shared/self-hosted multi-tenant Shipit deployment during initial setup or for orgs where a secret was never configured — the attack costs a single unauthenticated HTTP POST and is fully repeatable against arbitrary victim repositories/PR numbers already tracked by Shipit.

### Recommendation
Cross-check `params.repository.owner.login` against the owner segment of `params.repository.full_name` before processing (reject mismatches), and/or resolve the target `Repository`/`Stack` using the same organization that authenticated the signature rather than trusting `repository.full_name` independently. Additionally, warn/refuse to boot when any configured org has a blank `webhook_secret` in production.

### Proof of Concept
minitest under `test/controllers/webhooks_controller_test.rb` (or `test/models/shipit/webhooks/handlers/pull_request/assigned_handler_test.rb`):
1. Configure two orgs, `attacker_org` (no `webhook_secret`) and `victim_org` (with a secret), via `Shipit.stubs(:secrets)`/fixtures similar to `secrets_double_github_app.yml`.
2. Create `victim_repo` owned by `victim_org` with a `Stack` and a `PullRequest` (`number: 2`) whose `assignees` is `[]` (binding: `pull_request.stack.repository.owner == "victim_org"`).
3. POST to `/webhooks` with `X-Github-Event: pull_request`, `X-Hub-Signature: sha1=deadbeef` (or any value), and body `repository.owner.login = "attacker_org"`, `repository.full_name = "victim_org/victim_repo"`, `number: 2`, `action: "assigned"`, `pull_request.assignees: [{"login": "attacker"}]`.
4. Assert response is `:ok` (not `:unprocessable_entity`), i.e. `verify_signature` passed using `attacker_org`'s config (left side of the binding = `attacker_org`).
5. Reload `pull_request` and assert `pull_request.assignees.map(&:login) == ["attacker"]`, proving the write landed on `victim_org`'s `PullRequest` (right side of the binding = `victim_org`) — demonstrating the two sides of the equality diverged.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
