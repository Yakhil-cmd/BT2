### Title
Unauthenticated webhook forgery bypasses GitHub team authorization when `webhook_secret` is unset - (File: lib/shipit/github_app.rb)

### Summary
`GitHubApp#verify_webhook_signature` returns `true` whenever no `webhook_secret` is configured, exactly mirroring the `WhitelistToken#isWhitelisted` pattern in the external report (protection silently defaults to "allow all" when unconfigured). Because `webhook_secret` is documented and shipped as an optional/blank setting, `WebhooksController` will accept and process **unsigned, attacker-forged** GitHub webhook payloads, including `membership` events that grant `Team` membership used by `Shipit.github_teams` authorization.

### Finding Description
`WebhooksController#verify_signature` delegates trust entirely to `GitHubApp#verify_webhook_signature`: [1](#0-0) 

That method's actual logic is: [2](#0-1) 

`return true unless webhook_secret` is the binding break: the field that is supposed to gate "authenticated GitHub organization" vs. "any HTTP client" collapses to always-true when the operator has not filled in `webhook_secret`. This is not a hypothetical misconfiguration — the shipped example config explicitly documents this key as optional/blank: [3](#0-2) 

`WebhooksController` itself requires no session, no `ApiClient` token, and skips CSRF protection, so it is reachable by any unauthenticated network client: [4](#0-3) 

Once signature verification is neutralized, an attacker can POST a forged `membership` event. Shipit dispatches this event to `Handlers::MembershipHandler`: [5](#0-4) 

which (per `test/controllers/webhooks_controller_test.rb`, membership tests) creates/updates a `User` from attacker-supplied `login`/`member` fields and calls `Team#add_member`: [6](#0-5) 

`User#authorized?` — the gate enforced on every controller action via `Authentication#force_github_authentication` — trusts exactly this `Membership` record, not a live GitHub team check: [7](#0-6) [8](#0-7) 

**Binding broken:** `GitHub organization that authenticated the webhook` (intended to equal the org whose signature was verified) ≠ `organization on whose behalf Team/Membership records are written`, because the signature check is a no-op when `webhook_secret` is blank.

### Impact Explanation
This escalates directly into `Shipit.github_teams` authorization — an impact explicitly called out as High. An attacker who has (or creates) any GitHub login can forge a `membership` webhook naming their own `login`/github id and the `organization`/`team` slug required by `Shipit.github_teams`, causing Shipit to create a `Membership` row for them without ever verifying real GitHub team membership. They then complete a normal OAuth login as that identity and `authorized?` returns `true`, granting full access to stack management, deploy triggering, and any other authenticated Shipit functionality — a full authorization bypass on any deployment without `webhook_secret` configured.

### Likelihood Explanation
Likelihood is high for any installation that has not explicitly set `webhook_secret` (a value that ships blank by default in the example config and is documented as something operators "should" set only "if" they configured one on the GitHub App side, i.e., treated as optional). No credentials, sessions, or tokens are required to reach `WebhooksController#create` — only knowledge of the public `/webhooks` (or repository-specific) endpoint and event name.

### Recommendation
Reject webhook delivery when `webhook_secret` is not configured, instead of silently trusting the request:
- Change `verify_webhook_signature` in `lib/shipit/github_app.rb` to `return false unless webhook_secret` (or hard-fail application boot when a GitHub App is configured without a webhook secret).
- Additionally, do not let `membership`-webhook-created `Membership` rows alone satisfy `authorized?`; periodically or synchronously reconcile against `Team#refresh_members!` (live GitHub API) before trusting a webhook-asserted membership for authorization decisions.

### Proof of Concept
1. Deploy Shipit with a GitHub App config that leaves `webhook_secret` blank (the shipped default, e.g. `config/secrets.development.example.yml`).
2. As an unauthenticated attacker, `POST /webhooks` (or the repo/org-scoped webhook route) with header `X-Github-Event: membership` and no/garbage `X-Hub-Signature`, body:
```json
{
  "action": "added",
  "organization": { "login": "<org-required-by-shipit.github_teams>" },
  "team": { "id": 1, "name": "developers", "slug": "developers", "url": "https://example.com" },
  "member": { "login": "<attacker-github-login>" }
}
```
3. `verify_webhook_signature` returns `true` (no secret configured) → request is processed → `Team.find_or_create_by_handle`/`Team#add_member` creates a `Membership` linking `attacker-github-login`'s `User` to the required `Team`.
4. Attacker completes standard GitHub OAuth login as `attacker-github-login` via `GithubAuthenticationController#callback`.
5. `User#authorized?` now returns `true` because a `Membership` row exists, granting the attacker full authenticated access to the Shipit instance despite never actually belonging to the required GitHub team.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

        reset_session
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
