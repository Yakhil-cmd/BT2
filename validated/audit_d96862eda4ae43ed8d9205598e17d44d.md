### Title
Cross-repository commit-status forgery via unscoped `Commit` lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates an incoming GitHub `status` webhook only at the *organization* level, deriving the signing secret from `params.dig('repository','owner','login')`. Once the HMAC check passes for that organization, the payload is dispatched to `Shipit::Webhooks::Handlers::StatusHandler`, which never re-checks the `repository` field. It instead resolves the target `Commit` rows purely by `sha`, across the *entire* `commits` table, and writes a GitHub-supplied CI status onto every matching row regardless of which stack/repository it belongs to.

### Finding Description
`WebhooksController#verify_signature` computes `repository_owner` from the payload and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`: [1](#0-0) [2](#0-1) 

This proves only that the *organization* owning some repository signed the payload with its `webhook_secret` (`lib/shipit/github_app.rb#verify_webhook_signature`). It never binds the check to the specific repository named in `params['repository']['full_name']`.

`StatusHandler#process` then looks up commits with no repository/stack scoping at all: [3](#0-2) 
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
`Commit` rows are `belongs_to :stack`, and the same git SHA is legitimately reused across many `Stack` rows — e.g. a repository tracked by both a `staging` and `production` stack, or a fork sharing history with the upstream repo (the schema even indexes `[sha, stack_id]` as unique rather than `sha` alone, confirming SHA collisions across stacks are expected and normal: `db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`). Because `StatusHandler` matches on `sha` alone, a webhook that is validly signed for organization X but originates from a repository the attacker controls within that same organization (e.g. their own fork, which shares commit SHAs with the upstream repo) can write a spoofed CI status onto the `Commit` row of a completely different, unrelated `Stack` — including a production stack the attacker has no access to.

This is the same class of bug as the reported ERC20 issue: an action (`burnFrom`/here, "set commit status") is executed based on partial state (`user`/here, `sha`) while a dependent invariant (`totalSupply`/here, "which repository this status belongs to") is never checked, breaking the implicit binding between the authenticated scope (organization) and the mutated resource (a specific stack's commit).

### Impact Explanation
A forged/replayed "success" status on a production stack's commit can:
- Flip `Commit#state`/`deployable?` to `success`, satisfying `Stack#should_resume_continuous_delivery?` and triggering `ContinuousDeliveryJob`/`ProcessMergeRequestsJob` (`app/models/shipit/commit.rb#add_status`), causing an **unauthorized deploy or merge** of a commit the attacker never had permission over.
- Because the attacker only needs write/status access on some *other* repository under the same GitHub organization (not the victim repository), this is a genuine **cross-repository write / unauthorized deploy** — the highest listed Critical impact category.

### Likelihood Explanation
Requires: (a) the attacker to be able to trigger a `status` event that is validly signed by the same organization's `webhook_secret` — achievable by owning/forking a repository within that org and using the GitHub Statuses API on a commit that shares a SHA with a commit already tracked by the victim stack; (b) that SHA to exist in the victim stack's `commits` table, which happens naturally whenever multiple stacks track overlapping history (very common Shipit deployment topology: staging + production stacks off the same repo, or repos with shared upstream history). No `ApiClient` token, session, or GitHub App private key is needed — only an authentic GitHub `status` webhook delivery for a repository within the target organization.

### Recommendation
Scope the commit lookup in `StatusHandler#process` (and analogous handlers) by the `repository`/`stack` implied by `params.repository.full_name`, not by `sha` alone, e.g. resolve the `Repository`/`Stack` from the payload first and query `stack.commits.where(sha: params.sha)` instead of `Commit.where(sha: params.sha)` globally.

### Proof of Concept
1. Attacker is a member of (or has any repo under) GitHub organization `acme`, which has Shipit's GitHub App/webhook installed with a single org-level `webhook_secret`.
2. Attacker forks/mirrors `acme/victim-repo` into `acme/attacker-repo`, preserving an existing commit `sha` that is already deployed/tracked by `acme/victim-repo`'s production `Stack` in Shipit.
3. Using their own push/status access on `acme/attacker-repo`, the attacker sets a commit status (`state: success`) on that same `sha` via the GitHub Statuses API.
4. GitHub delivers a `status` webhook for `acme/attacker-repo`, correctly signed with `acme`'s `webhook_secret`; `WebhooksController#verify_signature` passes because it only checks the organization.
5. `StatusHandler#process` executes `Commit.where(sha: params.sha)`, which also matches the `Commit` row belonging to `acme/victim-repo`'s production stack, and calls `create_status_from_github!(params)` on it, injecting a fake "success" status and potentially triggering an unauthorized continuous deployment on the victim stack. # frozen_string_literal: true

```ruby
module Shipit
  class WebhooksController < ActionController::Base
    skip_before_action :verify_authenticity_token, raise: false
    before_action :check_if_ping, :drop_unhandled_event, :verify_signature

    respond_to :json

    def create
      params = JSON.parse(request.raw_post)
      Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }

      head(:ok)
    end

    private

    def drop_unhandled_event
      # Acknowledge, but do nothing
      head(204) unless Shipit::Webhooks.for_event(event).present?
    end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
  end
```
