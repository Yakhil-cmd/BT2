### Title
`ERC20Transactor::withdraw_asset_with_surplus`/`deposit_asset_with_surplus` credit XCM holding based on ERC20 `transfer()` return value only, without verifying actual balance change - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor` (Asset Hub Westend's XCM `TransactAsset` implementation for ERC20 tokens backed by `pallet-revive`) determines success of a token move purely from the boolean return value / non-revert status of the underlying Solidity `transfer()` call, never checking the actual balance delta of the sender/receiver. Any ERC20 contract that returns `true` (or doesn't revert) while moving less than the requested `amount` — e.g. a fee-on-transfer / deflationary / rebasing token, or one with custom transfer hooks — causes the transactor to mint an `AssetsInHolding` credit (`Erc20Credit(amount)`) for the full requested amount even though the `ERC20TransfersCheckingAccount` (or beneficiary) received strictly less.

### Finding Description
`withdraw_asset_with_surplus` calls the ERC20 contract's `transfer(checking_address, amount)` via `pallet_revive::Pallet::<T>::bare_call`, and only checks:
1. `return_value.did_revert()`
2. `IERC20::transferCall::abi_decode_returns_validate(...)` for the boolean success flag [1](#0-0) 

If both checks pass, it unconditionally constructs `AssetsInHolding::new_from_fungible_credit(what.id.clone(), Box::new(Erc20Credit(amount)))` for the full `amount` requested by the XCM message — not the amount actually observed to have arrived at `ERC20TransfersCheckingAccount`. [2](#0-1) 

The symmetric `deposit_asset_with_surplus` path (used when releasing ERC20 XCM holding to a beneficiary) has the identical pattern: it transfers from the checking account to the beneficiary and treats a `true`/non-revert return as full success, again without confirming the beneficiary's balance increased by `amount`. [3](#0-2) 

`Erc20Credit` is explicitly documented as *not* runtime-enforced — "this type implements the necessary imbalance accounting traits but does not perform runtime-level balance enforcement... the actual balance constraints are enforced by the ERC20 smart contract itself" — which is precisely the assumption broken by non-standard ERC20 semantics (fee-on-transfer, deflationary burn-on-transfer, rebasing, or transfer hooks that silently redirect part of the value). [4](#0-3) 

The matched asset is any `AccountKey20`-keyed location whose `key` is a contract address deployed via `pallet-revive` — i.e. attacker-deployable and attacker-controlled — matched through `ERC20Matcher`, and this transactor is wired directly into Asset Hub Westend's production `AssetTransactors` tuple, reachable from ordinary user-issued `pallet-xcm::execute`/`send` (e.g. `WithdrawAsset`/`DepositAsset` instructions), no privileged origin required. [5](#0-4) 

This is the direct FRAME/XCM analog of the reported `CollateralManager::_deposit` bug class: a token-moving operation is validated only by the callee's self-reported success signal (Solidity return bool / no-revert; here, ERC20 `transfer()` return bool / no-revert), never by an independent before/after balance check on the actually-affected account.

### Impact Explanation
Because the resulting `AssetsInHolding::Erc20Credit(amount)` is treated by the XCM executor as fully-backed holding of `amount` tokens, subsequent XCM instructions (e.g. `DepositAsset`, `TransferAsset`, reserve-transfer onward legs) will account for and move `amount` even though the `ERC20TransfersCheckingAccount` only actually holds `amount - fee`. This creates unbacked/phantom XCM-internal accounting relative to the real ERC20 contract balance of the checking account: over time, or on a single sufficiently large withdrawal of a fee-on-transfer/deflationary token, the checking account balance runs below what the XCM subsystem believes it "owns", so a later legitimate `deposit_asset_with_surplus` for other flows through the same checking account can fail (funds stuck) or, if the fee mechanism instead re-mints/rebalances asymmetrically, the discrepancy silently produces value drift between on-chain ERC20 balance and the XCM asset-holding ledger. This affects an attacker's own token contract, but the checking account (`ERC20TransfersCheckingAccount`) is a shared system account used by all users' ERC20 XCM operations, so the corrupted accounting is not isolated to the attacker.

### Likelihood Explanation
Deploying a non-standard ERC20 contract on `pallet-revive` and referencing it in an XCM `WithdrawAsset`/`DepositAsset` message is a normal, unprivileged, self-serve user action — no governance, no validator/collator collusion, and no special permission is needed to register or reference the contract via `AccountKey20` location matching. The only requirement is a token contract with fee-on-transfer / hook-based logic that still returns `true`/doesn't revert, which is straightforward and common in the wider ERC20 ecosystem (many real-world fee-on-transfer tokens exist).

### Recommendation
In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, read the ERC20 `balanceOf` of the destination account (checking account or beneficiary) before and after the `transfer()` call (or use `transferFrom`-style pull with an explicit balance check), and only mint an `Erc20Credit`/consider the deposit successful for the amount actually observed to have arrived, rather than trusting the boolean return value/non-revert status alone.

### Proof of Concept
No executable PoC was run. Constructing one requires: deploying a fee-on-transfer ERC20 contract via `pallet-revive` on Asset Hub Westend (or the runtime's mock/test harness), registering/using its `AccountKey20` location as an XCM asset, and issuing a `pallet_xcm::execute` message with `WithdrawAsset`/`DepositAsset` referencing that contract, then asserting that `AssetsInHolding` credited by `withdraw_asset_with_surplus` (`amount`) exceeds the actual increase in the `ERC20TransfersCheckingAccount`'s on-chain ERC20 balance. This is architecturally analogous to the existing `expensive_erc20_runs_out_of_gas` test in `asset-hub-westend/tests/tests.rs` (which exercises the same transactor via `pallet_xcm::execute` with a custom deployed contract) and could be adapted with a fee-on-transfer contract instead of a gas-expensive one. [6](#0-5) 

I was not able to locate an existing test in the indexed code that specifically exercises a fee-on-transfer/non-standard-return ERC20 contract against this transactor, so I cannot confirm whether this exact scenario has already been tested and rejected/accepted upstream; this should be verified with a live Devin session with full repository and test-execution access before filing.

#[test]
fn expensive_erc20_runs_out_of_gas() {
	let sender: AccountId = ALICE.into();
	let beneficiary: AccountId = BOB.into();
	let revive_account = pallet_revive::Pallet::<Runtime>::account_id();
	let checking_account =
		asset_hub_westend_runtime::xcm_config::ERC20TransfersCheckingAccount::get();
	let initial_wnd_amount = 10_000_000_000_000u128;

	ExtBuilder::<Runtime>::default().build().execute_with(|| {
		// Bring the revive account to life.
		assert_ok!(Balances::mint_into(&revive_account, initial_wnd_amount));

		// Fund all accounts involved.
		assert_ok!(Balances::mint_into(&sender, initial_wnd_amount));
		assert_ok!(Balances::mint_into(&beneficiary, initial_wnd_amount));
		assert_ok!(Balances::mint_into(&checking_account, initial_wnd_amount));

		// This contract does a lot more storage writes in `transfer`.
		let code = compile_module_with_type("MyTokenExpensive", FixtureType::Resolc)
			.expect("compile ERC20")
			.0;

		let initial_amount_u256 = U256::from(1_000_000_000_000u128);
		let constructor_data = sol_data::Uint::<256>::abi_encode(&initial_amount_u256);
		let Contract { addr: non_erc20_address, .. } = bare_instantiate(&sender, code)
			.transaction_limits(TransactionLimits::WeightAndDeposit {
				weight_limit: Weight::from_parts(500_000_000_000, 10 * 1024 * 1024),
				deposit_limit: Balance::MAX,
			})
			.data(constructor_data)
			.build_and_unwrap_contract();

		let wnd_amount_for_fees = 1_000_000_000_000u128;
		let erc20_transfer_amount = 100u128;
		let message = Xcm::<RuntimeCall>::builder()
			.withdraw_asset((Parent, wnd_amount_for_fees))
			.pay_fees((Parent, wnd_amount_for_fees))
			.withdraw_asset((
				AccountKey20 { key: non_erc20_address.into(), network: None },
				erc20_transfer_amount,
			))
			.deposit_asset(AllCounted(1), beneficiary.clone())
			.build();
		// Execution fails but doesn't panic.
		assert!(PolkadotXcm::execute(
			RuntimeOrigin::signed(sender.clone()),
			Box::new(VersionedXcm::V5(message)),
			Weight::from_parts(2_500_000_000, 120_000),
		)
		.is_err());
	});
