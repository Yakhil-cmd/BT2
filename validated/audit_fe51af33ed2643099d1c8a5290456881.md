### Title
Webhook signature verification is decoupled from the repository the event actually mutates, permitting unauthenticated cross-repository webhook forgery when any configured GitHub organization lacks a `webhook_secret` — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which organization's HMAC secret to check *against the same untrusted JSON body it is trying to authenticate*, and `GitHubApp#verify_webhook_signature` silently treats "no secret configured" as "signature valid." No code path ever re-checks that the organization used to authenticate the request actually corresponds to the `repository.full_name` that the event handlers subsequently act on. This is the same class of bug as the report: a value that is authenticated (organization identity) is not equal to the value that is actually written/executed (repository the event handler mutates).

### Finding Description
`WebhooksController#verify_signature` derives the org used for signature checking straight from the untrusted payload: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` unconditionally returns `true` when the resolved organization has no `webhook_secret` configured: [3](#0-2) 

`webhook_secret` is explicitly documented as optional per organization: [4](#0-3) 

Once the signature check passes (trivially, for the org with a blank secret), every handler resolves the target repository purely from the same attacker-controlled JSON body, with no binding back to the organization that was "authenticated": [5](#0-4) [6](#0-5) 

The binding that should hold is:
`organization authenticated by verify_signature == organization owning repository.full_name acted upon by the handler`

Because `repository_owner` (used to pick the secret) and `repository.full_name` (used by every handler to resolve `Repository`/`Stack`) are two independent, fully attacker-controlled fields inside one HTTP-forged JSON body — and the check on the first is void whenever any configured org has no secret — an unprivileged, unauthenticated internet client can satisfy the "authenticated organization" requirement using the org that lacks a secret while pointing `repository.full_name` at any repository/stack tracked by the Shipit instance, including ones belonging to completely different, properly-secured organizations.

### Impact Explanation
With signature verification defeated for one blank-secret organization, an outside attacker with zero Shipit credentials can:
- Force-trigger `GithubSyncJob` on arbitrary stacks via the `push` handler [7](#0-6) 
- Archive/unarchive review stacks and close pull request review stacks via the `pull_request` handlers (`opened`, `closed`, `labeled`, `unlabeled`, `reopened`), all resolving the repository from the same unauthenticated `full_name` field [8](#0-7) 
- Create commit `Status` records and mutate team/membership state via the `status`/`membership`/`check_suite` handlers.

Because these actions are not scoped to the organization that was nominally "authenticated," and because commit statuses feed into deployability checks used by continuous deployment, this can escalate to unauthorized state changes on stacks (and potentially unauthorized deploy paths) belonging to organizations that have correctly configured their webhook secret — purely because a different, unrelated organization on the same Shipit instance left `webhook_secret` blank. This matches the "Critical – unauthorized deploy / cross-repository writes" bucket.

### Likelihood Explanation
Likelihood is Medium: it requires at least one configured GitHub organization on the shared Shipit instance to have no `webhook_secret` set (explicitly documented as an "optional" setting), which is a realistic and easy-to-overlook misconfiguration in multi-organization deployments — not a purely theoretical state, and not something that requires any credential, session, or GitHub write access from the attacker.

### Recommendation
Bind the authenticated organization to the repository actually being acted upon: after `verify_signature` succeeds, re-derive the organization that owns `repository.full_name` (e.g., via `Repository.from_github_repo_name`) and reject the request (or re-authenticate) if it doesn't match `repository_owner`/the app configuration that produced a valid (non-bypassed) signature. Additionally, stop treating a missing `webhook_secret` as an implicit "always valid" signature; either require a secret for every configured organization or, at minimum, scope the leniency so it cannot be used to authorize events for repositories outside that specific organization.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `orgA` (no `webhook_secret` set — allowed per docs) and `orgB` (properly configured with a real webhook secret and a tracked stack for `orgB/private-repo`).
2. As an unauthenticated attacker, POST directly to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": { "full_name": "orgB/private-repo", "owner": { "login": "orgA" } }
}
```
No `X-Hub-Signature` header (or any garbage value) is required.
3. `verify_signature` resolves `Shipit.github(organization: 'orgA')` (since `repository_owner` == `orgA`), calls `verify_webhook_signature`, which returns `true` unconditionally because `orgA` has no `webhook_secret` [9](#0-8) .
4. `PushHandler#process` then resolves the stack via `Repository.from_github_repo_name('orgB/private-repo')` and enqueues `sync_github` for it [7](#0-6) , despite the attacker never having authenticated against `orgB` at all.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
