### Title
Cross-repository status forgery via unscoped SHA lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by bare SHA with no repository/stack scoping, so any GitHub organization that Shipit is configured for can send a `status` webhook whose signature is validated only against that sender's own organization, yet the resulting `Status` record is written onto every `Commit` row across the entire database that happens to share that SHA. Since a `success` status transition on a commit calls `stack.schedule_merges` and can flip a commit's deployability, an attacker who controls a repository sharing a SHA with a victim stack (e.g. via a fork, cherry-pick, or simply reusing a well-known SHA such as an empty-tree/initial commit) can force merge-queue advancement or deployability changes on a stack they never authenticated for.

### Finding Description
The broken binding is: `webhook.repository_owner (used in Shipit::WebhooksController#verify_signature) == commit.stack.repository.owner` (the repository that actually should be affected). In `StatusHandler#process`:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

there is no `.where(stack: ...)` or repository filter — every `Commit` row in the whole table matching `sha` is updated, regardless of which repository/organization the webhook was authenticated against. The controller's signature check only proves that the sender controls the organization named in `params['repository']['owner']['login']`:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  head(422) unless verified
``` [2](#0-1) 

It never checks that the `sha` being reported by that organization actually belongs to a commit that belongs to that same organization's repository. `StatusHandler` also never re-derives the repository from the payload to filter the `Commit.where` query.

Once `create_status_from_github!` runs, `add_status` fires:
```ruby
stack.schedule_merges if new_status.pending? || new_status.success?
``` [3](#0-2) 
which enqueues merge queue processing for the victim's stack, and a `success` state also changes `commit.deployable?`/`commit.state`, which upstream code (deploy, review-stack, merge-queue) treats as ready.

Exploit flow:
1. Attacker owns/administers a GitHub repository, `attacker/evil`, registered as a Shipit organization Shipit is configured to verify (`Shipit.github(organization: repository_owner)` must resolve — this requires the attacker's org to be a configured GitHub App/organization known to Shipit).
2. Attacker crafts a commit whose SHA collides or is deliberately identical to a SHA already present in the victim stack's `commits` table (trivial when both repos share a common ancestor/fork, cherry-pick, or empty initial commit — SHA1 collision is not required, only sha equality with a commit that already exists as a `Shipit::Commit` row, which happens naturally for forked repositories or shared history).
3. Attacker POSTs a `status` webhook to `/webhooks` with `context: ci/kubernetes`, `state: success`, `sha: <shared sha>`, signed with their own valid webhook secret for `attacker/evil`.
4. `verify_signature` passes because the signature is valid for the attacker's own organization.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — this matches the victim's `Commit` row too (no stack/repo filter), and `create_status_from_github!` writes a `success` status for `ci/kubernetes` on the victim commit.
6. `add_status` observes the transition and calls `stack.schedule_merges` on the **victim's stack**, and/or marks the commit deployable, forcing merge-queue advancement or ship decisions the victim's own CI never authorized.

Existing guards do not stop this: `verify_signature` only authenticates the organization named in the payload, not the target stack/repository of the `sha`; `drop_unhandled_event` only checks the event type is registered; there is no `ExplicitParameters` repository field validated against the commit's stack; `Repository`/`Stack` model validations don't constrain which repository a `Commit` row's SHA can be updated from.

### Impact Explanation
An attacker-controlled webhook write reaches a stack/repository that never authenticated it — the exact "payload for one repository mutating another's stack/commit" scenario. Concretely it can flip a victim commit's CI status to `success` for a required context (`ci/kubernetes`), triggering `stack.schedule_merges` and altering deployability, which can be leveraged to force a merge or unblock deployment for code the victim's own CI never approved. This matches the Critical impact category: unauthorized deploy/merge triggered from another tenant's repository. Blast radius: any Shipit installation hosting multiple stacks/organizations is affected, and the attack is repeatable for any SHA overlap, most easily via forked repositories that share commit history with the victim.

### Likelihood Explanation
Preconditions: attacker needs a repository (or forked/related repository) registered under a GitHub organization that Shipit already trusts to verify webhook signatures (`Shipit.github(organization: repository_owner)` must succeed, i.e., attacker's org is a configured GitHub App install target) and a SHA that also exists as a `Shipit::Commit` in the victim stack — realistic for forked repos, shared submodules/mono-repo scenarios, or cherry-picked commits, which is common practice. Attacker cost is a single unauthenticated HTTP POST once they can sign with their own valid credentials (a normal GitHub webhook from their own repo, no Shipit secrets needed). This is fully repeatable and requires no privileged Shipit role.

### Recommendation
Scope `StatusHandler#process` (and any other bare-SHA lookups such as `CheckSuiteHandler`) to only the commits belonging to the stack(s)/repository whose `full_name`/`owner` matches the authenticated webhook payload, e.g. `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { owner: repository_owner, name: repository_name })`. More generally, thread the verified repository identity from `WebhooksController` into every handler and enforce it as a hard filter before any DB write.

### Proof of Concept
minitest plan (`test/models/webhooks/handlers/status_handler_test.rb` or extending `test/controllers/webhooks_controller_test.rb`):
1. Create two stacks/repositories: `victim/repo` (with `merge_queue_enabled: true`, required status `ci/kubernetes`) and `attacker/evil`.
2. Create a `Shipit::Commit` with `sha: "deadbeef...".freeze` under `victim/repo`'s stack, with state not yet `success`.
3. Assert baseline: `commit.state != 'success'` and stack's merge queue has not been scheduled (`ProcessMergeRequestsJob` not enqueued for `victim_stack`).
4. Stub `GithubHook.any_instance.stubs(:verify_signature).returns(true)` (or stub `Shipit.github(organization: 'attacker').verify_webhook_signature` to return true) to simulate a validly-signed webhook from `attacker/evil`.
5. POST `/webhooks` with `X-Github-Event: status`, body `{ "sha" => "deadbeef...", "state" => "success", "context" => "ci/kubernetes", "repository" => { "owner" => { "login" => "attacker" }, "full_name" => "attacker/evil" } }`.
6. Assert both sides of the binding: BEFORE, `repository_owner` in the request (`"attacker"`) != `victim_stack.repository.owner` (`"victim"`); AFTER the request, `commit.reload.state == 'success'` and `assert_enqueued_with(job: ProcessMergeRequestsJob, args: [victim_stack])` — proving the victim stack was mutated by a webhook authenticated for a different repository. # frozen_string_literal: true

module Shipit
  class WebhooksController < ActionController::Base
    skip_before_action :verify_authenticity_token, raise: false
    before_action :check_if_ping, :drop_unhandled_event, :verify_signature

    respond_to :json

    def create
      params = JSON.parse(request.raw_post)
      Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }

      head(:ok)
    end

    private

    def drop_unhandled_event
      # Acknowledge, but do nothing
      head(204) unless Shipit::Webhooks.for_event(event).present?
    end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
  end
