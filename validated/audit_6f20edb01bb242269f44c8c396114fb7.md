**Analysis:** The premise that an attacker can "craft the serialized prologue args" independently of the transaction's actual `chain_id` field is incorrect. In `run_script_prologue`, the `chain_id` value passed into the Move prologue call is read directly from `txn_data.chain_id()` [1](#0-0)  — this is deserialized from the signed `RawTransaction`'s `chain_id` field, and the serialized args (`MoveValue::U8(chain_id.id())`) are constructed by the VM node itself from that trusted, already-signature-verified field [2](#0-1) , not supplied independently by the attacker over the wire.

Since `chain_id` is part of the `RawTransaction` that is hashed and signed, any attempt to submit a testnet-signed transaction with a different `chain_id` value than what it was originally signed with would invalidate the signature during authenticator verification (which happens before/alongside prologue execution), so the transaction would be rejected for signature failure rather than reaching the chain-id check with a forged value. There is no code path where an unprivileged caller controls the `chain_id` argument passed into `prologue_common`'s `assert!(chain_id::get() == chain_id, ...)` check independently of the signed transaction content [3](#0-2) .

The check `chain_id::get() == chain_id` in `prologue_common` compares the on-chain configured chain ID against the value taken from the signed, hash-committed transaction field — there is no bypass mechanism for an unprivileged attacker to decouple these. This binding is sound as implemented.
