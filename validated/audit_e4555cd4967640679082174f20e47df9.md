### Title
HOP "best-effort promotion" makes private hand-off blobs permanently public on-chain, defeating the protocol's own privacy guarantee - ([File: substrate/client/hop/src/promotion.rs])

### Summary
`sc-hop` (the "Hand-Off Protocol") is explicitly designed to keep sender-to-recipient hand-off data *off-chain* — "HOP keeps short-lived hand-off data off-chain until it actually needs permanence" [1](#0-0) . Delivery is scoped to specific recipients via per-recipient ephemeral keys that only the intended recipient can use to `claim`/`ack` the blob [2](#0-1) . However, if the intended recipient(s) do not claim/ack in time, `HopMaintenanceTask::tick` unconditionally submits the *entire raw blob* on-chain via `promoter.promote(data, ...)`, turning ephemeral, recipient-scoped private data into permanent, world-readable on-chain storage [3](#0-2) .

### Finding Description
The design intent of HOP is privacy-by-scoping: a sender uploads a blob and generates a unique ephemeral keypair per recipient, sharing the private key out-of-band; the collator "verifies signatures on claim/ack without learning recipient identities" [2](#0-1) . This is precisely the kind of "hand-off only to the intended party" guarantee that the Aleo incident violated for a different transport (email) — private material reaching parties who were never supposed to receive it.

HOP's `insert` accepts arbitrary attacker/user-controlled `data` (any bytes, since the node is "agnostic about what... 'authorized to submit'... mean[s]" and delegates only size/authorization checks to the runtime, not content sensitivity) [4](#0-3) . The stated purpose (private hand-off) implies the data can be sensitive (identity documents, keys, PII, etc., mirroring the Aleo case), yet the *fallback path* — the "best-effort on-chain promotion" — is not conditioned on the recipient's opt-in, on redaction, or on any privacy check at all:

- `HopMaintenanceTask::tick` fetches `get_promotable` entries nearing expiry and, for entries not confirmed on-chain, calls `promoter.promote(data, signer, signature, submit_timestamp)`, submitting the raw blob to the local transaction pool with no access control on who can subsequently read it [5](#0-4) .
- The runtime API `create_promotion_extrinsic` bakes the full data bytes into an on-chain extrinsic/storage item [6](#0-5) .
- Nothing in the promotion path re-checks whether *any* recipient actually wants (or consented to) permanent publication — "submit implies consent to promote" is stated as the protocol semantic for the **sender**, not the recipient [7](#0-6) . The unclaimed data of an *unaware, non-consenting recipient* who simply never got around to claiming in time is made permanent and public, visible to every node/observer of the chain — a strictly worse exposure than the Aleo incident, which merely sent files to ten wrong email addresses.

This is a genuine, reachable, unprivileged flow: any account permitted by `can_account_promote` submits `hop_submit` over RPC with real data and real recipients (no governance/privileged role needed), and if the recipient does not `claim`+`ack` within `retention_secs - buffer_secs`, the maintenance task automatically promotes the blob on-chain without any additional gate.

### Impact Explanation
Data that the protocol's own documentation frames as sensitive, ephemeral, and recipient-scoped ("private hand-off data") becomes permanently, publicly readable by anyone who can read chain storage/extrinsics, once retention nears expiry — regardless of whether the intended recipient consented to publication or even knows the promotion happened. This is an information-leakage class issue analogous to the Aleo report (private data reaching parties who should never see it), but with unbounded audience (the entire network) rather than 10 emails. Severity is bounded to Medium because: (1) it requires the sender to have chosen data sensitive enough that leaking matters, (2) it is the documented/intended fallback behavior (not a random bug) rather than an authentication bypass, and (3) it does not directly cause loss of funds or chain integrity breakage — it is a confidentiality/design issue in a client-side add-on module, matching the "Information Leakage" bug class of the source report rather than a theft/unbacked-issuance class.

### Likelihood Explanation
High likelihood of occurrence in normal operation: any entry whose recipient fails to claim/ack before `buffer_secs` before expiry (a common, non-adversarial scenario — recipient offline, missed the timestamp window, or simply chooses not to receive it) is automatically promoted on-chain by design, with no recipient consent check anywhere in the code path shown (`tick` → `get_promotable` → `promote`) [3](#0-2) .

### Recommendation
Do not promote raw blob content on-chain as a silent fallback. Options: (a) only promote a commitment/hash of the data (already used for content addressing) instead of the plaintext, letting the recipient retrieve the plaintext off-chain via a separate authenticated channel; (b) require explicit recipient (not just sender) consent/opt-in before allowing promotion of the raw bytes; (c) document loudly and make promotion default-off, requiring node operators/runtimes to explicitly enable plaintext promotion with a warning that "unclaimed HOP data becomes permanently public."

### Proof of Concept
Not executed against a live network, per constraints. Code-path reproduction (static): 
1. `hop_submit(data=<sensitive bytes>, recipients=[R])`, `signer`, `signature`, `submit_timestamp` via `HopRpcServer::submit` → `HopDataPool::insert` stores blob + meta [8](#0-7) .
2. Recipient `R` does not call `hop_claim`/`hop_ack` before `retention_secs - buffer_secs` elapses.
3. `HopMaintenanceTask::tick` selects the entry via `get_promotable`, confirms it is not yet on-chain, and calls `promoter.promote(data, signer, signature, submit_timestamp)`, which builds and submits an unsigned extrinsic carrying the full `data` bytes on-chain [9](#0-8) , [6](#0-5) .
4. Existing unit test `tick_promotes_near_expiry_entries` in `promotion.rs` demonstrates this exact flow deterministically (mock promoter receives the plaintext `data`) confirming the mechanism fires without any recipient-side gate [10](#0-9) . No further live-network execution was performed; this is a logical/design tracing exercise consistent with the constraints (no test run against public networks, no fabricated results).

Note: this `sc-hop` module is a bespoke/non-standard addition to this fork of `polkadot-sdk` (not present in mainline Polkadot SDK as far as I could verify from the index); I was unable to confirm whether this module is deployed on any live Parity/Snowbridge bounty-in-scope network, and file-list membership alone is not sufficient for bounty eligibility per the program rules. This caveat should be verified before treating the finding as bounty-eligible.

		// Promote near-expiry entries one at a time to bound peak memory.
		if let Some(ref promoter) = self.promoter {
			const PROMOTION_BATCH_SIZE: usize = 10;
			let hashes =
				self.hop_pool
					.get_promotable(current_block, self.buffer_secs, PROMOTION_BATCH_SIZE);
			for hash in hashes {
				// First, ask the runtime whether this hash is already on-chain.
				// If so, the previous attempt (or a third party) already
				// landed it — flag locally and stop touching the chain.
				match promoter.is_promoted_on_chain(hash.as_fixed_bytes()) {
					Ok(true) => {
						self.hop_pool.mark_promoted(&hash);
						tracing::info!(
							target: "hop",
							hash = ?hex::encode(hash),
							"HOP entry already on-chain — flagged locally"
						);
						continue;
					},
					Ok(false) => {},
					Err(e) => {
						// Treat runtime-API failures as "unknown", which means
						// proceed with submission. Worst case we resubmit a
						// duplicate; the on-chain check will catch it next cycle.
						tracing::warn!(
							target: "hop",
							hash = ?hex::encode(hash),
							error = %e,
							"is_promoted_on_chain failed; assuming not on-chain"
						);
					},
				}

				let (data, signer, signature, submit_timestamp) =
					match self.hop_pool.get_with_auth(&hash) {
						Some(t) => t,
						None => continue,
					};
				let size = data.len();
				let result = promoter.promote(data, signer, signature, submit_timestamp);
				// Backoff on every attempt — both Ok (submitted to local pool, may
				// or may not get included) and Err (pool rejected). Without this,
				// every cycle would resubmit the same extrinsic for the entry's
				// lifetime, wasting fees and authorization budget if the runtime
				// pallet does not deduplicate.
				self.hop_pool.record_promotion_attempt(
					&hash,
					current_block,
					self.check_interval_blocks,
				);
				match result {
					Ok(()) => tracing::info!(
						target: "hop",
						hash = ?hex::encode(hash),
						size,
						"Submitted HOP promotion extrinsic; awaiting on-chain confirmation"
					),
					Err(e) => tracing::warn!(
						target: "hop",
						hash = ?hex::encode(hash),
						error = %e,
						"Failed to submit HOP promotion extrinsic; will back off"
					),
				}

	fn tick_promotes_near_expiry_entries() {
		let dir = TempDir::new().unwrap();
		let pool = test_pool(1024 * 1024, 100, &dir);
		let (_, signer) = test_recipient();

		let hash = pool
			.insert(vec![42u8; 10], bv(vec![signer]), SENDER_A, dummy_auth().0, dummy_auth().1, 0)
			.unwrap();

		let promoter = Arc::new(MockPromoter::new(false));
		let task = HopMaintenanceTask::new(
			pool.clone(),
			Some(promoter.clone()),
			Arc::new(|| 80), // current block = 80
			180,             // buffer_secs = 180 > retention=100 → in window
			60,
		);

		task.tick();

		assert_eq!(promoter.call_count(), 1);
		assert_eq!(promoter.calls()[0], vec![42u8; 10]);

		// Entry stays in the pool (not yet confirmed on-chain) and is excluded
		// from the next promotable batch by the post-attempt backoff window.
		assert!(pool.has(&hash));
		let promotable = pool.get_promotable(80, 180, usize::MAX);
		assert!(promotable.is_empty(), "back-off should suppress immediate re-promotion");
	}
