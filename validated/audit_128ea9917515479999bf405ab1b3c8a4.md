### Title
Malicious swap routes can execute unauthorized token transfers under the caller’s authorization - ([File: contracts/controller/src/strategies/swap.rs])

### Summary
The `swap_collateral` strategy accepts caller-controlled `StrategySwap` bytes and forwards them to the configured router while authorizing the router to pull the swap input. Because route venue addresses are not constrained to audited pool contracts, a crafted route can place attacker-controlled contract code below the caller’s authorization and cause an unrelated token transfer to be recorded as a signed sub-invocation. If the caller signs that simulated authorization tree, the route can drain tokens from the caller’s wallet while still returning valid swap output to the account.

### Finding Description
`swap_collateral` requires caller authentication and verifies that the caller owns or delegates the target account before invoking `withdraw_and_swap_from_supply` with the caller-controlled `swap` payload. [1](#0-0) 

The shared strategy path sends that opaque payload to the configured router via `router.execute_strategy`, after authorizing only the intended token transfer from the controller to the router. [2](#0-1) 

The authorization helper explicitly creates a single `transfer(from, to, amount)` authorization with no additional sub-invocations, which bounds the controller’s intended grant but does not prevent route-selected third-party code from requesting further authorization from the original caller. [3](#0-2) 

The protocol threat model confirms that the router invokes pool and token addresses named by the route payload without an allowlist, allowing attacker-controlled code to execute below the caller’s authorization entry. [4](#0-3) 

A route-selected contract can therefore invoke `token.transfer(victim, attacker, amount)` for a token unrelated to the lending position, and Soroban records that transfer as a child of the victim’s `swap_collateral` authorization. [5](#0-4) 

The regression test demonstrates that the malicious route still supplies fair `ETH` output to Alice’s lending account while transferring Alice’s entire unrelated wallet-token balance to the attacker. [6](#0-5) 

### Impact Explanation
An attacker can steal any token held by a user who signs the poisoned authorization tree, not merely the collateral amount routed through `swap_collateral`. [7](#0-6) 

The theft is not bounded by the strategy’s input amount, minimum output, or final account solvency checks because it spends wallet assets directly through the user’s signed authorization. [8](#0-7) 

This qualifies as theft of user funds under a Medium severity: arbitrary balances can be taken, but exploitation requires the victim to execute a strategy using the attacker’s route and sign the returned authorization tree.

### Likelihood Explanation
The attacker needs no privileged role: they only need to supply a malicious `swap` payload to an authorized account owner or delegate through `swap_collateral`. [9](#0-8) 

The route can still return enough output for the transaction to pass the controller’s positive-output and final-risk checks, making the malicious authorization less obvious during execution. [10](#0-9) 

Exploitation requires user interaction because the rogue token transfer is rejected unless it appears in the authorization tree signed by the victim. [11](#0-10) 

That interaction requirement lowers likelihood, but wallets or integrators that do not decode nested route authorization can present the poisoned tree as an ordinary strategy signature.

### Recommendation
Restrict strategy routes to governance-allowlisted venue contracts or define a route schema that can be decoded and validated by the controller before forwarding it to the router. At minimum, the router should reject arbitrary pool addresses and execute only typed, allowlisted venue calls.

Clients should also simulate the transaction, decode the complete authorization tree, and reject any strategy authorization containing children other than the expected protocol token movement. [12](#0-11) 

### Proof of Concept
1. Alice owns a funded lending account and also holds an unrelated wallet token controlled by her address.
2. The attacker deploys `RogueHopPool`, whose `swap` function executes `token::transfer(alice, attacker, alice_balance)` for that unrelated token. [13](#0-12) 
3. The attacker constructs a `swap_collateral` route naming this rogue contract as a hop while still producing fair output for Alice’s account. [14](#0-13) 
4. Alice invokes `swap_collateral(caller, account_id, current, from_amount, new, swap)` with that route; simulation records the rogue token transfer as a child invocation under her authorization. [15](#0-14) 
5. If Alice signs the returned tree, the transaction succeeds, Alice’s unrelated wallet balance becomes zero, and the attacker receives `WALLET_BALANCE`. [16](#0-15)

That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
user.

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}
