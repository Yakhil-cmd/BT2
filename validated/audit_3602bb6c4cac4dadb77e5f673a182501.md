### Title
`status` webhook writes commit status by bare SHA with no repository scoping, allowing cross-stack state manipulation - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits solely by `Commit.where(sha: params.sha)`, with no filter on the repository that authenticated the webhook. Any repository whose commit history shares a SHA with a commit already recorded in another stack's `commits` table (e.g. a fork sharing pre-divergence history, or a mirrored/renamed repository) can push a `failure` status for `ci/smoke` and have it applied to the victim stack's commit, flipping its deployability.

### Finding Description
The claimed-safe binding is: `commit.stack_id == webhook.repository_id` (a status should only ever be written to commits belonging to the repository/stack that authenticated the webhook). The actual code breaks this: [1](#0-0) 

`process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — there is no join/filter against `params.dig('repository', ...)` or against the stack that owns the webhook. Any `Commit` record in the database with a matching `sha`, regardless of which `Stack`/`Repository` it belongs to, receives the status write via `commit.create_status_from_github!` → `add_status`: [2](#0-1) [3](#0-2) 

`add_status` reads `previous_status`/`new_status` from `Status::Group.compact` and, on state transitions, calls `stack.schedule_merges` and evaluates `deployable?`/`blocked?` for the *victim's* stack, using the delegated `required_statuses`/`blocking_statuses` from `stack` (`app/models/shipit/commit.rb:57-58`, `:227-237`). So a `failure` status attached under context `ci/smoke` can flip `deployable?` to `false` (blocking a pending deploy/merge) purely because the SHA collided with another repository's commit row.

Upstream, `WebhooksController#verify_signature` only checks that the request signature matches the secret associated with `repository_owner` (`params.dig('repository','owner','login')`), i.e. it authenticates that *some* repository under that GitHub organization sent the payload — it does not verify that the `sha` in the payload actually belongs to *that* repository's git objects: [4](#0-3) 

Nothing downstream (`StatusHandler`, `Commit.create_status_from_github!`, `Status#replicate_from_github!`) re-validates that the SHA is reachable in the repository named in the payload. Since git commit SHAs are content-addressed, two different repositories can legitimately contain identical commit objects (e.g. a fork before it diverges, or a repository renamed/re-added to Shipit), meaning a `Commit` row with the same `sha` can exist under two different `stack_id`s. An attacker who controls (or forks/mirrors) a repository sharing history with the victim's tracked repository can send a correctly-signed `status` webhook from their own repo with `context: ci/smoke`, `state: failure`, and the shared SHA, and the write lands on the victim's `Commit` row.

### Impact Explanation
This is a payload from one repository mutating another repository's stack/commit state — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." Concretely: the victim stack's required `ci/smoke` context flips to `failure`, `Commit#deployable?`/`#blocked?` change, `stack.schedule_merges` and continuous-delivery scheduling behavior are affected, and any pending automatic merge/deploy gated on that status can be blocked (or, with an inverse `success` status, forced). This is repeatable against any stack that has a commit whose SHA collides with a commit reachable from a repository the attacker controls (forks are the common vector), so the blast radius scales with however many stacks/forks share git history with a given upstream.

### Likelihood Explanation
Preconditions: the attacker needs a repository under a GitHub organization already configured in Shipit (so `verify_signature` succeeds for their own repo), and the target `sha` must correspond to a `Commit` row that already exists for the victim stack (naturally true for any commit pushed to the victim stack before or shared via forking/rebasing history). No Shipit credentials, GitHub App keys, or org membership beyond owning/forking a tracked repository are required — this is well within the declared "unprivileged attacker" capability (push to a fork, or simply reference a shared ancestor commit). The attack is a single unauthenticated `POST /webhooks` request with a valid signature for the attacker's own repo, entirely repeatable.

### Recommendation
Scope `StatusHandler#process` (and the analogous check-run/commit-status handlers) to the repository that authenticated the webhook: join `Commit` to `Stack`/`Repository` via `params.dig('repository', 'full_name')` (or `id`) and only update commits whose `stack.repository` matches the payload's repository, e.g. `Commit.joins(:stack).merge(Stack.where(repository: Repository.from_github_repo_name(params.dig('repository','full_name')))).where(sha: params.sha)`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status webhook does not affect commits belonging to another repository's stack" do
  victim_stack = shipit_stacks(:shipit)
  victim_commit = victim_stack.commits.create!(sha: 'a' * 40, message: 'victim commit')

  attacker_stack = create_stack(repository: create_repository(full_name: 'attacker/repo'))
  attacker_commit = attacker_stack.commits.create!(sha: 'a' * 40, message: 'attacker commit') # shared SHA

  before = victim_commit.reload.deployable?

  payload = Shipit::Webhooks::Handlers::StatusHandler::Params.new(
    sha: 'a' * 40, state: 'failure', context: 'ci/smoke'
  )
  Shipit::Webhooks::Handlers::StatusHandler.new(payload).process

  after = victim_commit.reload.deployable?

  # Binding under test: victim_commit.stack_id must remain unaffected by attacker_stack's webhook
  assert_equal before, after, "victim commit's deployability changed due to a status from an unrelated repository"
end
```
This demonstrates that `StatusHandler#process`'s unscoped `Commit.where(sha:)` lookup lets a status intended for `attacker_stack` mutate `victim_stack`'s commit state.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end

      ].join(' '))
