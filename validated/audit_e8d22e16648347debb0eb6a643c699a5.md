### Title
Missing zero-address validation on `creator` account in `initialize_with_permission` permanently freezes creator fees - ([File: programs/cp-swap/src/instructions/initialize_with_permission.rs])

### Summary
`InitializeWithPermission`'s `creator` account is declared as a plain, unvalidated `UncheckedAccount` and is written directly into `PoolState.pool_creator` without any check that it is a non-zero, controllable address. Every subsequent creator-fee withdrawal path (`collect_creator_fee`, and the recipient-account derivation in `collect_creator_fee_permissionless`) is keyed off this stored `pool_creator` value, so an attacker-chosen zero/uncontrollable `creator` value causes all accrued creator fees for that pool to become permanently unrecoverable — the exact "zero token" bug class from the external report (unchecked address parameter stored and later used to move funds), applied to a Solana/Anchor account instead of an EVM constructor argument.

### Finding Description
In `InitializeWithPermission`, `creator` has no `address`, `signer`, or ownership constraint: [1](#0-0) 

Only `payer` must sign and hold a valid `Permission` PDA: [2](#0-1) 

The attacker-controlled `creator.key()` is passed straight into `pool_state.initialize(...)` and persisted as `pool_creator` with no non-zero / not-default-Pubkey check: [3](#0-2) 

Downstream, `collect_creator_fee` requires the *signer* to equal `pool_state.load()?.pool_creator`: [4](#0-3) 

and `collect_creator_fee_permissionless` derives the fee-recipient ATA using that same stored `pool_creator` as `associated_token::authority`: [5](#0-4) [6](#0-5) 

If `pool_creator` is set to `Pubkey::default()` (the all-zero System-Program address) or any other address for which no private key exists, no transaction can ever be signed by that key, so `collect_creator_fee` can never succeed for that pool, and `collect_creator_fee_permissionless` will happily create an ATA owned by that unreachable authority and transfer fees into it — funds that can never be moved out again.

### Impact Explanation
Every trade routed through a pool created via `initialize_with_permission` accrues `creator_fees_token_0`/`creator_fees_token_1` in `PoolState` (per the fee-split logic used by swaps). If `pool_creator` is the zero/uncontrollable address, 100% of the accumulated creator-fee share for that pool's entire lifetime is permanently and unrecoverably frozen — a direct, ongoing loss of LP/trader-derived fee revenue with no possible remediation (no admin override for creator fees exists in the reviewed code paths). This satisfies "permanent freezing of user or LP funds."

### Likelihood Explanation
`initialize_with_permission` is reachable by any account holding a valid `Permission` PDA (a "pool creator" role in this permissioned deployment flow), which per the reachable-surface rules is an unprivileged pool-creator action. The only requirement to trigger the bug is supplying `Pubkey::default()` (or any unspendable pubkey) as the `creator` account in a single `initialize_with_permission` transaction — no race condition, no special timing, and no additional privilege needed. This can happen either through attacker intent (to grief a pool or as an accounting trick) or through an honest integrator mistake (e.g., a client passing an uninitialized/zeroed pubkey), both of which the missing validation fails to catch.

### Recommendation
Add an explicit constraint in `InitializeWithPermission` rejecting the default/zero pubkey for `creator`, e.g. `constraint = creator.key() != Pubkey::default() @ ErrorCode::InvalidCreator`, mirroring the recommendation in the external report to validate non-zero addresses before persisting them into stored state that later gates fund transfers.

### Proof of Concept
1. Attacker (or naive integrator) obtains/holds a valid `Permission` PDA account (`payer` is a permissioned pool creator).
2. Attacker calls `initialize_with_permission` supplying `creator = Pubkey::default()` (or any pubkey with no known private key) along with valid `token_0_mint`/`token_1_mint`/vault/lp-mint accounts.
3. `pool_state.initialize(...)` stores `pool_creator = Pubkey::default()` — [3](#0-2) .
4. Normal swaps occur on the pool, accruing `creator_fees_token_0`/`creator_fees_token_1` in `PoolState`.
5. Any attempt to call `collect_creator_fee` fails permanently because no signer can ever match `pool_creator == Pubkey::default()` — [4](#0-3) .
6. `collect_creator_fee_permissionless` can be called by anyone, but it only creates an ATA owned by `Pubkey::default()` and moves the fees there — [6](#0-5)  — and those tokens remain forever inaccessible since no keypair controls that authority.
