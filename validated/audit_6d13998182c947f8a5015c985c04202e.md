### Title
Unescaped `trustDomain` interpolated into SAN regex weakens certificate identity matching in `buildVerificationPolicy` - ([File: pkg/cmd/release/shared/attestation.go])

### Summary
`buildVerificationPolicy` builds the SAN regex for Sigstore certificate identity matching by directly interpolating the `trustDomain` string (sourced from `api.Client.GetTrustDomain()`, i.e. the `meta` API response of the host `gh` is pointed at) into `fmt.Sprintf("^https://%s\\.releases\\.github\\.com$", trustDomain)` without `regexp.QuoteMeta` escaping. A host controlling that API response (e.g., an attacker-operated GHES-like endpoint that the victim points `gh` at) can inject regex metacharacters into `trustDomain`, widening the SAN match pattern used by `verify.NewSANMatcher`.

### Finding Description
`VerifyAttestation` in [1](#0-0)  calls `v.AttClient.GetTrustDomain()` and passes the resulting string straight into `buildVerificationPolicy`. `GetTrustDomain` fetches this value from the `meta` REST endpoint of whatever host the client was constructed against and returns `resp.Domains.ArtifactAttestations.TrustDomain` verbatim, with no validation of its character set [2](#0-1) . In `buildVerificationPolicy`, this untrusted string is interpolated unescaped into the SAN regex: [3](#0-2) . Additionally the issuer matcher in the same function is `verify.NewIssuerMatcher("", ".*")`, i.e., it already accepts any issuer, so the SAN regex is the only identity-binding check on the certificate. If `trustDomain` contains regex metacharacters (e.g. `.*`, `|`, an unescaped `.`), the resulting compiled regex can match a broader set of SAN strings than the literal intended domain, in principle allowing a maliciously-crafted certificate SAN to satisfy the pattern where it should not.

However, the `attClient` used in the affected `gh release verify-asset` path is always constructed with `baseRepo.RepoHost()` [4](#0-3) , and `api.NewLiveClient`'s `githubAPI.REST` call routes through the standard `gh` API client for that host — for this call to return attacker-controlled data, the victim must already be operating `gh` against an attacker-controlled/malicious GHES-like host, which is an explicitly in-scope precondition for this question ("victim runs verify-asset against a GHES-like host ... controls responses from a host the victim points gh at").

### Impact Explanation
If exploitable, this would fall into the verification/authorization bypass class: an attacker-controlled GHES host could theoretically cause the SAN matcher to accept a wider set of certificate identities than intended, weakening the sigstore certificate-identity check performed by `verify.NewCertificateIdentity`. However, the actual exploitability is limited: the attacker already fully controls the host and the `meta`/attestation API responses at that point (this is the same threat scenario as "victim configured `gh` to a malicious/compromised GHES instance"), so the attacker can already return whatever attestation bundle and trust domain they like from `GetByDigest`/`getBundle`, and the certificate itself is issued by Sigstore/Fulcio infrastructure that is not under the attacker's control — regex widening of the SAN match does not by itself let the attacker forge a valid Fulcio-issued certificate with an arbitrary SAN. The regex-injection weakens defense-in-depth of the identity check but does not on its own demonstrate a concrete additional compromise beyond what the attacker already achieves by controlling the target host's API responses in the first place.

### Likelihood Explanation
Low practical likelihood as a standalone exploit: it requires the victim to already be pointing `gh` at an attacker-operated/compromised host (a strong precondition equivalent to full host compromise from the victim's perspective), and even then, actually leveraging the widened regex requires the attacker to also obtain or forge a Fulcio-signed certificate whose SAN happens to satisfy the loosened pattern — which is not shown to be independently achievable from this code path alone.

### Recommendation
Escape `trustDomain` with `regexp.QuoteMeta` before interpolating it into the SAN pattern in `buildVerificationPolicy` (`pkg/cmd/release/shared/attestation.go`), and consider validating that `trustDomain` matches an expected safe character set (e.g., `^[a-zA-Z0-9.-]+$`) before use, defense-in-depth regardless of the issuer-matcher being permissive.

		return "", err

func (c *LiveClient) getTrustDomain(u safeurl.SafeURL) (string, error) {
	var resp MetaResponse

	bo := backoff.NewConstantBackOff(getAttestationRetryInterval)
	err := backoff.Retry(func() error {
		restErr := c.githubAPI.REST(c.host, http.MethodGet, u.String(), nil, &resp)
		if restErr != nil {
			if shouldRetry(restErr) {
				return restErr
			} else {
				return backoff.Permanent(restErr)
			}
		}

		return nil
	}, backoff.WithMaxRetries(bo, 3))

	if err != nil {
		return "", err
	}
