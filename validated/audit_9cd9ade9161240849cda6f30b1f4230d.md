### Title
`pending_delegator_rewards` is never decremented after block-reward distribution, causing duplicated reward payouts and permanently frozen vote-account lamports - ([File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs])

### Summary
`calculate_block_reward()` computes each stake account's share of a vote account's `pending_delegator_rewards` field and pays that share out to stake accounts every epoch that block-revenue sharing is active, but nothing in the reward-calculation or reward-distribution path ever decrements `pending_delegator_rewards` on the vote account itself. This mirrors the reported `GaugeV1.notifyRewardAmount()` bug class: an amount is read from a stored "pot" value and paid out, but the corresponding debit against that pot is missing, so the same funds are computed as distributable again and again, and the tracked liability is never reconciled with what has actually been paid.

### Finding Description
`calculate_block_reward()` reads the vote account's `pending_delegator_rewards` via `vote_state.pending_delegator_rewards()` and calculates a per-stake-account share proportional to `stake / total_active_stake`: [1](#0-0) 

This value is fed into `calculate_stake_rewards_and_commissions()`, which is gated only by the `block_revenue_sharing` feature flag, and produces a `PartitionedStakeReward.block_reward` for every stake delegation: [2](#0-1) 

At distribution time, `build_updated_stake_reward()` credits `partitioned_stake_reward.block_reward` directly onto the **stake account's** lamports via `checked_add_lamports`, and `store_stake_accounts_in_partition()` tallies `block_reward_lamports_distributed` for capitalization/metrics purposes: [3](#0-2) [4](#0-3) 

Crucially, at no point in this path (nor anywhere in `programs/vote/src/vote_state/mod.rs`, `handler.rs`, or `vote_processor.rs`) is `pending_delegator_rewards` decremented as a consequence of block-reward distribution. The only mutator of the field is `add_pending_delegator_rewards()`, invoked from the `DepositDelegatorRewards` instruction handler: [5](#0-4) [6](#0-5) 

The field is otherwise only read — by `calculate_block_reward()` for computing payouts, and by `withdraw()`, which uses `pending_delegator_rewards` to compute the minimum balance a vote account must retain (`min_rent_exempt_balance + pending_delegator_rewards`) and to block closing the account entirely while `pending_delegator_rewards > 0`: [7](#0-6) 

The result is analogous to the reported bug: `calculate_block_reward()` behaves like `notifyRewardAmount()` using a stale pot value (`balanceOf(address(this))`/`pending_delegator_rewards`) to determine a distributable amount, but the corresponding "transferFrom"/debit step that should reduce that pot never executes. Concretely:
1. Each epoch that `block_revenue_sharing` is active, stakers are paid a share of the *same* `pending_delegator_rewards` value again, since it is never reduced by what was already distributed. This duplicates payouts across epochs from one deposit.
2. The lamports actually credited to stake accounts are freshly added (`checked_add_lamports`) and folded into `self.capitalization` as newly distributed/minted supply, rather than being debited from the vote account that nominally "owns" `pending_delegator_rewards`. The vote account's lamports (and its `pending_delegator_rewards` bookkeeping value) never shrink, so `withdraw()` permanently reserves `pending_delegator_rewards` lamports in the vote account — a value that has effectively already been "spent" via block-reward payouts to stakers — permanently locking those funds from ever being withdrawable and preventing vote-account closure indefinitely (`ActiveVoteAccountClose`/`InsufficientFunds` guard against `pending_delegator_rewards`).

### Impact Explanation
This produces duplicated/misattributed rewards: stakers of a validator receive repeated payouts computed off a never-decremented pot, which inflates `self.capitalization` improperly relative to what was actually deposited via `DepositDelegatorRewards`. It also produces a permanently frozen liability inside every vote account that has ever received a delegator-rewards deposit, since `pending_delegator_rewards` lamports remain locked by `withdraw()`'s balance check forever, even though those lamports were never actually consumed to pay out the stake rewards that were computed against them.

### Likelihood Explanation
This triggers deterministically and automatically on every epoch boundary once the `block_revenue_sharing` feature and `custom_commission_collector`/`commission_rate_in_basis_points` features are active and any vote account has a non-zero `pending_delegator_rewards` (via `DepositDelegatorRewards`, itself unprivileged and reachable by any signer with lamports). No malicious input or special conditions beyond a routine deposit and normal epoch reward calculation are required.

### Recommendation
After a block reward is calculated and successfully distributed to a stake account (or, more precisely, after the full round of block-reward distribution for an epoch based on a given vote account's `pending_delegator_rewards` completes), decrement `pending_delegator_rewards` on that vote account by the total amount actually distributed for that epoch, and ensure the corresponding lamports are properly accounted for (debited from the vote account rather than freshly minted) to keep the deposit/payout ledger consistent.

### Proof of Concept
Note: this is a logic/state-consistency finding based on static analysis of the reward-calculation and reward-distribution code paths (`calculation.rs`, `distribution.rs`, `vote_state/mod.rs`, `vote_state/handler.rs`, `vote_processor.rs`); I was not able to execute the runtime reward pipeline end-to-end in this session to empirically confirm capitalization drift across multiple epochs, so the exact numeric divergence is unverified but the code-level absence of any decrement site for `pending_delegator_rewards` outside test helpers is confirmed by exhaustive `grep_search` across the whole repository, which found the field written to only in `add_pending_delegator_rewards()` and in unit-test setup code: [5](#0-4) 
A conceptual reproduction:
1. Call `DepositDelegatorRewards` on a `VoteStateV4` account, setting `pending_delegator_rewards = D`.
2. Advance through an epoch boundary with `block_revenue_sharing` active; `calculate_block_reward()` distributes `D` proportionally to delegators as `block_reward`, and stake account lamports increase accordingly.
3. Advance through a second epoch boundary without any new deposit; `pending_delegator_rewards` is still `D` (unchanged), so `calculate_block_reward()` distributes the *same* `D` again to delegators.
4. Inspect the vote account via `withdraw()`: it still refuses to release the reserved `D` lamports, and refuses full account closure while `pending_delegator_rewards > 0`, even though `D` has already been paid out via block rewards in step 2 (and again in step 3).

/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }
}

/// Deposit delegator rewards into a vote account (SIMD-0123).
pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}
