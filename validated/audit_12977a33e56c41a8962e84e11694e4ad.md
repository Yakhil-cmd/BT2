### Title
Unauthorized spending of a "final-bad" (invalid) output via stale/pruned-content recovery bypassing the stability check - ([File: validation.js])

### Summary
CVE-2022-3541 is a use-after-free in a Linux driver where freed data is retrieved and reused without validating that the underlying object is still legitimate. The reachable analog in `ocore--003` is a logic gap in `validatePaymentInputsAndOutputs` (`validation.js`) that lets a crafted unit spend an output that belongs to a `final-bad` (i.e., already-invalidated/"freed") source unit, by exploiting the ephemeral, TTL-based pruned-joint cache (`archiving.js`) that was added to let outputs of stripped units still be looked up. The output was never part of the accepted ("good") DAG state, so accepting a spend of it is equivalent to spending money that was never legitimately issued.

### Finding Description
When a `payment` input of type `transfer` is validated, the code first checks whether the referenced source output is stable relative to the spending unit's last ball (`bStableInParents`). Only in that case does it unconditionally reject spends of `final-bad` (or throw on `temp-bad`) source outputs: [1](#0-0) 

If `bStableInParents` is false (the spending unit deliberately references an older `last_ball_unit` whose `main_chain_index` is lower than the source output's `main_chain_index`), this guard is skipped entirely. The code then falls into the branch that handles a locally pruned/stripped output (address column is `NULL` because it was archived), and — if the unit's actual sequence is `final-bad` and its `main_chain_index` is below `storage.getMinRetrievableMci()` — recovers the address/amount from an in-memory cache instead of rejecting the spend outright: [2](#0-1) 

That cache is populated only when a unit is voided/pruned (`archiving.cachePrunedJoint`), and is served back to any peer via `get_joint` before even checking the database: [3](#0-2) [4](#0-3) 

Content recovered from a *remote, untrusted* peer for this exact purpose is accepted after only a unit-hash check (`allHashesAreValid`), not a check that the unit is actually eligible to be spent from: [5](#0-4) [6](#0-5) 

The remaining checks below this point (`bStableInParents && sequence !== 'good'`, asset/denomination match, address ownership) do not re-reject a `final-bad` source once its address/amount have been filled in via the recovery path, because `bStableInParents` is false by construction and the explicit `sequence === 'final-bad'` rejection at line 2459 only fires when `bStableInParents` is true. A `final-bad` unit is, by definition, one whose messages/outputs lost the double-spend/serialization resolution and were never applied to anyone's balance in the accepted ("good") sequence. Treating its output as spendable — merely because the *content* (address/amount) could be honestly recovered — reintroduces value that never legitimately entered circulation.

### Impact Explanation
An attacker who authors a unit can:
1. Reference an old `last_ball_unit` so that `bStableInParents` is false for an input spending a known `final-bad` output that has already been pruned locally by the validating node (`main_chain_index < min_retrievable_mci`).
2. Ensure the pruned content is recoverable (either from a cooperating/attacker-controlled peer that still has it within the 1‑hour `PRUNED_JOINT_CACHE_TTL_ms`, or by having served/cached it themselves earlier).
3. Have the node accept the spend of an output that was never actually credited in the canonical ("good") DAG state.

This is concrete unauthorized spending / supply inflation: value that should not exist becomes spendable, and different nodes may disagree about whether the unit is valid depending on their local `min_retrievable_mci` and pruned-cache contents at validation time, causing node disagreement on validity.

### Likelihood Explanation
Reaching this path requires: (a) an already-resolved double-spend/serialization conflict producing a `final-bad` unit with an output the attacker (or a colluding author) controls, (b) that unit's MCI already below the validating node's `min_retrievable_mci`, and (c) crafting `last_ball_unit`/parents so the new spending unit's `last_ball_mci` is lower than that MCI while still passing all other unit-formation constraints (parents, timestamps, etc.). This is a non-trivial but fully attacker-controlled combination of unit fields — no privileged access, hub, or peer compromise is needed; it's reachable purely by posting a crafted unit.

### Recommendation
Reject spending any input whose underlying unit `sequence` is `final-bad` (or `temp-bad`) unconditionally, regardless of `bStableInParents` or whether the pruned content can be recovered. The pruned-content recovery mechanism (`archiving.getCachedOutput`/`cachePrunedJoint`) should only ever be used to recover metadata for units whose sequence is `good`, never to resurrect spendability of `final-bad` outputs. Move the `sequence === 'final-bad'` check outside the `bStableInParents` guard in `validation.js` around line 2456-2474.

### Proof of Concept
1. Node A and Node B accept two conflicting units spending the same output; one becomes `good`, the other `final-bad` (call it `U_bad`), and eventually its MCI falls below `min_retrievable_mci`, so its content is stripped and its full joint kept only transiently in `assocCachedPrunedJoints`.
2. Attacker crafts unit `U_evil` with an input referencing `U_bad`'s (now non-existent) output, and deliberately sets `U_evil.last_ball_unit` to an old unit whose `main_chain_index` is lower than `U_bad`'s `main_chain_index`, making `bStableInParents` false in `validatePaymentInputsAndOutputs`.
3. Attacker posts `U_evil` to a node while the pruned content of `U_bad` is still recoverable from some peer (or the attacker relays previously legitimately-obtained content). Validation reaches the `!src_output.address` branch, finds `sequence === 'final-bad'` and `main_chain_index < min_retrievable_mci`, and — instead of rejecting — attempts recovery via `archiving.getCachedOutput`/the `ifNeedParentUnits`/`tryRecoverPrunedContentOfFinalBadUnit` flow in `network.js`.
4. Once content is recovered and hash-verified, `src_output.address`/`amount` are populated and the spend of the never-legitimate `U_bad` output proceeds through the remaining checks, being accepted as a valid spend.

/*jslint node: true */
"use strict";
var db = require('./db.js');

// in-memory holdover of joints we just voided (stripped final-bad units), so that for a while after pruning
// we can still serve their full content to peers and recover from spends that raced the pruning locally
const PRUNED_JOINT_CACHE_TTL_ms = 60 * 60 * 1000;
let assocCachedPrunedJoints = {};

function cachePrunedJoint(objJoint){
	assocCachedPrunedJoints[objJoint.unit.unit] = { objJoint: objJoint, expiry_ts: Date.now() + PRUNED_JOINT_CACHE_TTL_ms };
}

function getCachedPrunedJoint(unit){
	const cached = assocCachedPrunedJoints[unit];
	if (!cached)
		return null;
	return cached.objJoint;
}
