### Title
Session fixation via missing `reset_session` in `Shipit::GithubAuthenticationController#callback` - (File: `app/controllers/shipit/github_authentication_controller.rb`)

### Summary
`GithubAuthenticationController#callback` writes `session[:user_id] = sign_in_github(auth)` directly into whatever session already exists for the request, never calling `reset_session` first. If an attacker can plant a known session id in a victim's browser before the victim completes the GitHub OAuth flow, the attacker's pre-known session id becomes a fully authenticated session for the victim once the callback fires, giving the attacker post-login access to that session.

### Finding Description
The broken binding: the session identifier `request.session.id` (the underlying cookie-store session key) before the callback should not equal `request.session.id` after the callback if the two "owners" of the session differ across the trust boundary of authentication. In `GithubAuthenticationController#callback`: [1](#0-0) 

`session[:user_id] = sign_in_github(auth)` is set on the existing session object without calling `reset_session`, unlike `logout`, which correctly calls `reset_session`: [2](#0-1) 

`sign_in_github` resolves/creates the `User` from `auth.extra.raw_info` and returns its `id`, which is written straight into the current session hash: [3](#0-2) 

`current_user`/`find_current_user` in `Shipit::Authentication` then trusts whatever `session[:user_id]` holds: [4](#0-3) 

`GithubAuthenticationController` also inherits from `ActionController::Base` directly (not `ShipitController`/`ApplicationController`), so it does not carry the app's `protect_from_forgery with: :exception` setting that other controllers get: [5](#0-4) [6](#0-5) 

Route exposes `callback` for both GET and POST: [7](#0-6) 

Exploit flow: an attacker capable of planting a known session id in the victim's browser prior to the victim beginning/finishing the real GitHub OAuth dance (e.g., via cookie tossing on a shared parent domain, or any mechanism that lets them set the `_session_id` cookie on the victim's browser to an attacker-known value) benefits because `reset_session` is never invoked at the point of login. When the victim later legitimately completes OAuth with GitHub, the same (attacker-known) session id is simply mutated to carry `session[:user_id] = victim.id`. The attacker, who already knows that session id, can now present it and be treated as the victim by `find_current_user`.

Why existing guards don't stop this: `force_github_authentication` only checks `current_user.logged_in?` and `authorized?`; it never validates session-id freshness or rotates the session id on privilege escalation, and `find_current_user` trusts `session[:user_id]` unconditionally. There is no CSRF token check on this controller and no session id rotation call (`reset_session`) anywhere on the authentication-success path.

### Impact Explanation
If successful, the attacker gains a fully authenticated session as the victim (or vice versa) without ever needing the victim's GitHub credentials, `github_access_token`, or Shipit's secrets. From there, the attacker can act as the victim across the app — trigger deploys/rollbacks via `Shipit::TasksController#create`, view task output, or take any action the victim's account is authorized for. This matches the explicitly listed High-severity category "session fixation / forced OAuth completion." It is repeatable per victim who can be lured into the fixation setup, though it is not repeatable against arbitrary stacks/repositories without also compromising the victim's own permissions.

### Likelihood Explanation
The genuinely exploitable precondition is nontrivial: the attacker must be able to set/fix a specific session id in the victim's browser before the victim's browser completes OAuth (classic session fixation precondition — e.g., cookie tossing via a shared/broader cookie `domain`, or another mechanism to inject a cookie into the victim's browser for this host). Rails' default cookie-store session generally makes the session id itself opaque and set by the server on first request, so the realistic attack surface depends on how the host app configures `session_store` (cookie domain scope, `secure`/`same_site` flags) — configuration outside this engine's direct control. Given that precondition is met, the rest of the chain (no `reset_session` on login) is deterministic and requires no secrets, no GitHub App access, and no privileged role, matching the attacker capability model in the rules.

### Recommendation
Call `reset_session` in `Shipit::GithubAuthenticationController#callback` before assigning `session[:user_id]`, mirroring the pattern already used in `#logout`, so the session id is rotated on every successful authentication:
```ruby
def callback
  return_url = request.env['omniauth.origin'] || root_path
  auth = request.env['omniauth.auth']
  return render('failed', layout: false) if auth.blank?

  user_id = sign_in_github(auth)
  reset_session
  session[:user_id] = user_id
  session[:authenticated] = true
  redirect_to(return_url)
end
```
Additionally, consider having `GithubAuthenticationController` inherit standard CSRF protections consistent with the rest of the app.

### Proof of Concept
```ruby
# test/controllers/github_authentication_controller_test.rb
test ":callback rotates the session id on login (no fixation)" do
  # Simulate attacker pre-fixing a session id before OAuth completes.
  pre_login_session_id = @request.session.id

  auth = OmniAuth::AuthHash.new(
    credentials: OmniAuth::AuthHash.new(token: 's3cr3t'),
    extra: OmniAuth::AuthHash.new(
      raw_info: OmniAuth::AuthHash.new(
        id: 44, name: 'Shipit User', email: 'shipit-user@example.com',
        login: 'shipit-user', avatar_url: 'https://example.com',
        api_url: 'https://github.com/api/v3/users/shipit-user'
      )
    )
  )
  @request.env['omniauth.auth'] = auth

  get :callback

  post_login_session_id = @request.session.id

  # Binding under test: session id BEFORE login must differ from session id AFTER login.
  refute_equal pre_login_session_id, post_login_session_id,
    "Expected session id to be rotated on login to prevent session fixation"
end
```
This test currently fails against `GithubAuthenticationController#callback` because no `reset_session` call exists, demonstrating the session id is never rotated across the authentication boundary. [1](#0-0)
