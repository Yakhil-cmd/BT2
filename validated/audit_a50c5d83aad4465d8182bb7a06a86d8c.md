### Title
Webhook signature is verified against the payload's `repository.owner.login` but Shipit acts on the payload's `repository.full_name`, letting an attacker who controls one onboarded GitHub organization forge events for any other tracked repository - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and therefore which `webhook_secret`) to validate a delivery against using `repository_owner`, i.e. `params.dig('repository', 'owner', 'login')` [1](#0-0) . All downstream event handlers, however, resolve the target Shipit `Repository`/`Stack` using a *different* field of the same attacker-supplied JSON body: `payload.dig('repository', 'full_name')` [2](#0-1) . Nothing ties these two fields together, so the signature only proves "this payload was signed with the secret belonging to the organization named in `repository.owner.login`" - it does not prove that the `repository.full_name` referenced elsewhere in the same payload actually belongs to that organization.

### Finding Description
In a multi-tenant Shipit deployment (explicitly supported and documented in `docs/setup.md`, "Using Multiple Github Applications" [3](#0-2) ), each onboarded GitHub organization has its own `webhook_secret` configured in `secrets.yml` and known to that organization's own administrators (they set it when creating the GitHub App).

`Shipit.github(organization: repository_owner)` looks up the `GithubApp` instance for the organization named in the payload, and `verify_webhook_signature` HMAC-validates the raw body against that organization's secret [4](#0-3) . This only proves the sender knows *some* onboarded organization's secret - typically their own.

Every handler, however, ignores `repository.owner.login` for authorization purposes and instead loads the target repository/stack via `repository_name = payload.dig('repository', 'full_name')` [5](#0-4) , e.g. `PullRequest::OpenedHandler#repository` [6](#0-5) , or the push handler's `GithubSyncJob` enqueue path exercised in `test/controllers/webhooks_controller_test.rb` [7](#0-6) .

Because a single JSON body can legally contain `repository.owner.login = "attacker-org"` (satisfying signature verification with the attacker's own secret) while `repository.full_name = "victim-org/victim-repo"` (a completely unrelated repository tracked by the same Shipit instance under a different onboarded organization), an administrator of any one onboarded organization can forge webhook deliveries that Shipit will treat as authentic for any other organization's repository.

The binding that should hold is:
```
organization authenticated by verify_signature == organization owning the repository acted upon by the handler
```
This binding is broken: the controller authenticates one field of the payload while the handlers act on a sibling, unverified-relative-to-owner field of the same payload.

### Impact Explanation
An attacker who is merely an admin of their own onboarded GitHub organization (not privileged in Shipit, no Shipit session, no `ApiClient` token, no access to the victim repository) can forge:
- `status` events, injecting fabricated commit statuses onto arbitrary commits of a victim stack (`Handlers::StatusHandler`), which feed directly into CI-gating logic (`ci.require`) that decides whether a commit is eligible for deploy - enabling an unauthorized deploy of a commit that never actually passed CI.
- `push` events, enqueuing `GithubSyncJob` for a victim stack.
- `pull_request` events, driving `ReviewStackAdapter` provisioning for a victim repository's review stacks.
- `membership` events, creating arbitrary teams/users cross-organization.

This crosses an organization/repository trust boundary and can lead to an unauthorized deploy, satisfying the "Critical" impact bar (unauthorized deploy) defined in scope.

### Likelihood Explanation
Requires only that the Shipit instance be configured for multiple GitHub organizations (a documented, supported configuration) and that the attacker administers one of those onboarded organizations - no compromise of the victim organization, no Shipit account, and no token is needed. The forged HTTP request to `/webhooks` is trivial to construct once the attacker's own `webhook_secret` is known (which they legitimately possess for their own org).

### Recommendation
After `verify_signature` resolves `repository_owner` and the matching `GithubApp`, re-derive/validate that every organization referenced elsewhere in the payload (notably `repository.full_name`'s owner segment, and `sender`/`organization` fields used by handlers) matches `repository_owner` before dispatching to handlers; alternatively, pass the verified organization into each handler and have `Handler#stacks` filter/require repositories to belong to that organization instead of trusting `repository.full_name` alone.

### Proof of Concept
1. Deploy Shipit configured with two organizations, `attacker-org` (attacker is admin, knows `webhook_secret_A`) and `victim-org` (tracks stack `victim-org/victim-repo`), per the multi-org config in `docs/setup.md`.
2. Attacker crafts a `status` (or `push`) webhook JSON body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check",
  "target_url": "https://attacker.example/fake",
  "description": "forged"
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC_SHA1(webhook_secret_A, body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `verify_signature` resolves `repository_owner == "attacker-org"`, fetches `attacker-org`'s `GithubApp`, and successfully verifies the signature against `webhook_secret_A` [8](#0-7) .
5. `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`, which uses `Handler#stacks`/`repository_name` derived from `payload.dig('repository','full_name') == "victim-org/victim-repo"` [2](#0-1) , creating a forged, "verified" commit status on the victim's stack despite the attacker never having authenticated as or against `victim-org`.

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently.     def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
