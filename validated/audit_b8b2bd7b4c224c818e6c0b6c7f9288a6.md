### Title
Unbounded recursion in `readAllControlAddresses` when shared-address definitions form a cycle - (File: wallet_defined_by_addresses.js)

### Summary
`readAllControlAddresses` recursively expands the set of "control addresses" of a shared address by repeatedly joining `shared_address_signing_paths`, without tracking already-visited addresses or bounding recursion depth [1](#0-0) . A paired device can create shared addresses whose member/signer graph references another shared address that (directly or indirectly) references the first one back, via the attacker-reachable `new_shared_address`/`handleNewSharedAddress` device-message handler [2](#0-1) , invoked from `wallet.js`'s message dispatcher [3](#0-2) . This mirrors the CVE-2016-7122 bug class: a crafted, cyclic structure causes an infinite/unbounded processing loop because the parser/consumer never records "already seen" nodes.

### Finding Description
`readAllControlAddresses(conn, arrAddresses, handleLists)` queries `shared_address_signing_paths` for rows whose `shared_address` is `IN(arrAddresses)`, collects any newly discovered "control addresses" (addresses that can sign for the given shared addresses), and unconditionally recurses with the union of the newly discovered addresses:

```
function readAllControlAddresses(conn, arrAddresses, handleLists){
	...
	conn.query(
		"SELECT DISTINCT address, shared_address_signing_paths.device_address, ...",
		[arrAddresses],
		function(rows){
			if (rows.length === 0) return handleLists([], []);
			var arrControlAddresses = rows.map(...);
			var arrControlDeviceAddresses = ...;
			readAllControlAddresses(conn, arrControlAddresses, function(arrControlAddresses2, arrControlDeviceAddresses2){
				handleLists(_.union(arrControlAddresses, arrControlAddresses2), _.union(arrControlDeviceAddresses, arrControlDeviceAddresses2));
			});
		}
	);
}
``` [1](#0-0) 

There is no set of already-visited shared addresses, and no depth limit, so if the `shared_addresses`/`shared_address_signing_paths` tables contain a cycle (address A lists address B as a member/signer, and B lists A back), each recursive call re-discovers the same addresses and the function never terminates (or grows indefinitely accumulating `_.union` results and DB queries).

The data that creates these rows is populated from `new_shared_address` device messages, which are only sanity-checked for structural validity (correct chash, presence of signer entries, addresses being syntactically valid) but not for graph acyclicity between independently-created shared addresses:

```

		...

			...
			addNewSharedAddress(body.address, body.definition, body.signers, body.forwarded, callbacks.ifOk);

``` [2](#0-1) 

Because two independent shared addresses A and B can each have valid, hash-consistent definitions (their own chash only commits to their own definition, not to whether the *other* one references them back), a paired device (correspondent) can:
1. Create shared address B whose definition includes address A as a member ("address" leaf = A).
2. Send `new_shared_address` for B; my node stores it via `addNewSharedAddress`, which inserts rows into `shared_address_signing_paths` [4](#0-3) .
3. Create/possess shared address A whose definition includes B as a member and send it similarly.

Once both are stored, any subsequent call to `readAllControlAddresses` (e.g., triggered when a new shared address is added, since `addNewSharedAddress` calls `forwardNewSharedAddressToCosignersOfMyMemberAddresses`/emits `new_address`, and consumers such as wallet balance / notification code call `readAllControlAddresses` per `wallet.js`) will recurse forever between A and B, because the function has no visited-set/cycle guard.

### Impact Explanation
This causes the local wallet/light-node process handling the shared address (specifically the node whose device stores/tracks these shared addresses) to hang in unbounded recursion/DB querying, exhausting the event loop, DB connection pool, and eventually memory/stack, denying that peer's wallet service (unable to process further balance/transaction updates that depend on `readAllControlAddresses`). This matches the reachable classes allowed by the rules (wallet/contract message handling reachable from a paired device), and the impact is "a node unable to confirm/process new units/messages" for that wallet instance — a concrete denial-of-service on the victim's own wallet logic triggered purely by messages from a paired device, with no special/malicious-node/network-level assumption beyond the device pairing that ocore already requires for `new_shared_address` messages.

### Likelihood Explanation
Medium likelihood: it requires the attacker to be a paired correspondent device (already assumed reachable per rules: "paired device"), able to construct two (or more) shared-address definitions that reference each other as members, and send both via the standard `new_shared_address` message flow. No cryptographic secret or on-chain unit posting is required — only local wallet bookkeeping tables (`shared_addresses`, `shared_address_signing_paths`) which are populated directly from received device messages after only structural (chash) validation, not cross-address cycle validation.

### Recommendation
- In `readAllControlAddresses`, maintain an accumulating visited-set of already-processed addresses and exclude them from `arrControlAddresses` before recursing (i.e., `_.difference(arrNewControlAddresses, arrAllKnownAddresses)`), terminating once no new addresses are discovered — analogous to the pattern already used in `graph.js`'s `goUp`/`goDown` (`arrNewStartUnits = _.difference(arrNewStartUnits, arrKnownUnits)`) [5](#0-4) .
- Additionally, consider validating in `handleNewSharedAddress`/`addNewSharedAddress` that adding a new shared address does not create a cycle in the member-address graph, or impose a maximum recursion/query depth as a defense-in-depth measure.

### Proof of Concept
1. Attacker (a paired correspondent device) creates shared address `B` whose definition template resolves an `["address", A]` leaf pointing at victim's existing shared address `A` (or vice versa), and sends `new_shared_address` for `B` to the victim; victim stores it via `addNewSharedAddress`.
2. Attacker also causes/possesses a definition for `A` that in turn includes `["address", B]` as a member leaf (e.g., by controlling or colluding on both shared addresses, or by getting the victim to accept a `new_shared_address` for `A` that references `B`), and sends it as well.
3. Any code path that calls `wallet_defined_by_addresses.readAllControlAddresses` for `A` or `B` (e.g., wallet balance/notification logic reachable in `wallet.js`) will recurse indefinitely between `A` and `B`, hanging the victim wallet process.

Note: I could not fully trace every runtime call site that triggers `readAllControlAddresses` after a `new_shared_address` (only `wallet.js` and `wallet_defined_by_addresses.js` reference it, and the wallet.js call site's exact triggering context was not fully inspected due to iteration limits), so exact end-to-end triggering conditions should be verified by a follow-up code review/test before treating this as a confirmed, fully wired DoS chain.

	if (!ValidationUtils.isArrayOfLength(body.definition, 2))
		return callbacks.ifError("invalid definition");

		return callbacks.ifError("invalid signers");

		var addr = objectHash.getChash160(body.definition);
	}
	catch (e) {
		return callbacks.ifError("invalid definition: " + e);
	}
	if (body.address !== addr)
		return callbacks.ifError("definition doesn't match its c-hash");
	for (var signing_path in body.signers){
		var signerInfo = body.signers[signing_path];
		if (signerInfo.address && signerInfo.address !== 'secret' && !ValidationUtils.isValidAddress(signerInfo.address))
			return callbacks.ifError("invalid member address: " + JSON.stringify(signerInfo.address));
	}
	const assocDefinitionAddresses = extractAddressPathsFromDefinition(body.definition);
	for (let signing_path in body.signers) {
		const signerInfo = body.signers[signing_path];
		if (assocDefinitionAddresses[signing_path] !== signerInfo.address)
			return callbacks.ifError("signer address at path " + signing_path + " doesn't match definition");

			if (err)
				return callbacks.ifError(err);
			addNewSharedAddress(body.address, body.definition, body.signers, body.forwarded, callbacks.ifOk);
		});
	});
