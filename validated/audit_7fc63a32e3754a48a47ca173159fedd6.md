Confirmed: `UniversalAliases = Nothing` on People, Coretime, Collectives, Encointer, and BridgeHub chains (only Asset Hub configures non-`Nothing` `UniversalAliases`, and only for its own trusted bridge networks). This closes the `UniversalOrigin` spoofing vector entirely for the chains in question.

### Analysis

The exploit hypothesis requires an attacker on a sibling parachain to make the XCM executor believe the message originated from `RelayChainLocation` or `AssetHubLocation`, so that `LocationAsSuperuser<(Equals<RelayChainLocation>, Equals<AssetHubLocation>), RuntimeOrigin>` converts it to `RawOrigin::Root`, e.g. on People: [1](#0-0) 

This fails for two independent reasons:

1. **The XCM origin is not attacker-controlled data — it is fixed by the message-delivery channel.** The `origin` passed into `xcm_executor::XcmExecutor::prepare_and_execute`/`do_execute` for an inbound HRMP message is set by the parachain runtime's XCMP/UMP/DMP message-processing code based on which channel/sender queue the message actually arrived on (i.e., derived from the real sending `ParaId`), not from any field inside the XCM program itself. An attacker on parachain X can only ever cause the executor's origin to start as `Location{parents:1, interior:[Parachain(X)]}`.

2. **`DescendOrigin` cannot forge a different top-level identity — it only appends junctions onto the existing (channel-derived) origin.** Starting from `(1, [Parachain(X)])`, `DescendOrigin` can only produce deeper locations like `(1, [Parachain(X), ...])`; it can never produce `(1, [Parachain(1000)])` (Asset Hub) or `(1, [])` (Relay) since it cannot remove or rewrite the leading `Parachain(X)` junction.

3. **`UniversalOrigin` (the only instruction that can claim an entirely different location) is gated by `Config::UniversalAliases`, which is `Nothing` on People, Coretime, Collectives, Encointer, and BridgeHub**, e.g.: [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) 
This means an attacker's `UniversalOrigin` instruction is unconditionally rejected on these chains — there is no configured `(bridge_location, consensus_junction)` pair that would let a sibling parachain claim to be Relay or Asset Hub. Only Asset Hub itself defines non-`Nothing` `UniversalAliases`, and even there it only authorizes specific bridged-network junctions (Kusama/Ethereum global consensus via bridge hubs), not sibling-parachain spoofing of `AssetHubLocation`/`RelayChainLocation`: [6](#0-5) 

4. Additionally, the `Barrier`/`WithComputedOrigin` logic on every one of these chains only ever computes origin by applying `DescendOrigin`-style narrowing to the already channel-bound origin, and `TrustedAliasers` (`AliasChildLocation`, `AliasAccountId32FromSiblingSystemChain`, `AliasOriginRootUsingFilter<AssetHubLocation, Everything>`, `AuthorizedAliasers<Runtime>`) only allow aliasing into child locations of the real sender or explicitly-authorized targets — none permit a sibling parachain to alias into `AssetHubLocation` or `RelayChainLocation` itself, e.g.: [7](#0-6) 

Since the channel-bound origin can never be rewritten to equal `RelayChainLocation` or `AssetHubLocation` by any combination of `DescendOrigin` (narrowing-only) and `UniversalOrigin` (blocked by `UniversalAliases = Nothing`), `LocationAsSuperuser` can never resolve a sibling-parachain-originated message to `RawOrigin::Root` on any of these system parachains.
