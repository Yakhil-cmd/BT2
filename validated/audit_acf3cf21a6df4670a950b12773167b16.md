### Title
Pull request labels are merged into task/command environment last, allowing `BUNDLE_GEMFILE` (and other Bundler-scrubbed variables) re-injection into `bundle exec`/`bundle install` invocations - ([File: app/models/shipit/review_stack.rb])

### Summary
`ReviewStack#env` (app/models/shipit/review_stack.rb:84-93) turns every GitHub PR label into an environment variable named `LABEL.upcase => "true"` with no denylist, and this hash flows unfiltered through `TaskCommands#env` (lib/shipit/task_commands.rb:33-48) into `Command#unbundled_env` (lib/shipit/command.rb:103-105), where it is merged **after** `Command::BASE_ENV`. Since `BASE_ENV` is computed once from `Bundler.unbundled_env`/`ENV` at class-load time (lib/shipit/command.rb:17-18) and intentionally nils out Bundler-internal variables such as `BUNDLE_GEMFILE`, a PR label literally named `bundle_gemfile` resurrects `BUNDLE_GEMFILE=true` for every `bundle install`/`bundle exec` step run for that review stack's tasks.

### Finding Description
Binding claimed: `BASE_ENV['BUNDLE_GEMFILE']` (scrubbed to `nil` by `Bundler.unbundled_env`) should equal `Command#unbundled_env['BUNDLE_GEMFILE']` for the final env passed to `PTY.spawn`. Tracing the code shows this does **not** hold:

- `Command::BASE_ENV = unbundled_env.merge((ENV.keys - unbundled_env.keys).map { |k| [k, nil] }.to_h)` [1](#0-0)  — any Bundler-scoped var (e.g. `BUNDLE_GEMFILE`) present in the shipit worker's `ENV` but scrubbed by `Bundler.unbundled_env` becomes an explicit `nil` entry.
- `Command#unbundled_env` merges `@env.stringify_keys` last: `BASE_ENV.merge('PATH' => ...).merge(@env.stringify_keys)` [2](#0-1) , so any key in `@env` unconditionally overrides the scrubbed `nil`.
- `@env` for a task command is built by `TaskCommands#env`, which merges `@stack.env` [3](#0-2) .
- For a `ReviewStack`, `env` injects one entry per PR label with **no allowlist/denylist**: `pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" }` [4](#0-3) .
- Labels are captured verbatim from GitHub webhook payloads by `LabelCapturingHandler#capture_labels`, which calls `pull_request.update!(labels: params.pull_request.labels.map(&:name))` with no content filtering [5](#0-4) .

Exploit flow: an attacker who controls labels on a PR that has a Shipit `ReviewStack` (per the stated threat model, "label their own PR") applies a label named `bundle_gemfile`. This produces `env['BUNDLE_GEMFILE'] = "true"`. When the review stack's task runs `install_dependencies`/`perform` (e.g. `bundle install`, `bundle exec ...`), `Command#start` spawns the process via `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` [6](#0-5)  with `BUNDLE_GEMFILE=true` set relative to the checked-out working directory. Since the attacker also controls the PR branch content (they can commit a file literally named `true` containing arbitrary Ruby `Gemfile` DSL, e.g. a custom gem `source`/`eval`), Bundler will load that attacker-authored file as the Gemfile and execute arbitrary Ruby on the deploy host.

No existing guard intercepts this: `EnvironmentVariables#permit`/interpolation is used for shell-string interpolation, not for filtering which keys are allowed into the process env; there is no allowlist on label names before they become environment variable keys; `Command::BASE_ENV`'s scrub is unconditionally overridable because `@env` is merged last with no denylist re-check.

### Impact Explanation
An attacker able to label a PR tied to a Shipit-managed `ReviewStack` can achieve arbitrary Ruby code execution on the Shipit deploy host during any subsequent `bundle`-based build/deploy/task step for that stack — this is Critical RCE via `Command`/`PTY.spawn`. The blast radius is scoped to the repository/stack whose PR the attacker controls (their own repo/fork with review stacks enabled), but from there arbitrary code execution on the shared deploy worker can pivot to secrets available to that host (e.g. `GITHUB_TOKEN`, other stacks' deploy credentials if shared infrastructure), extending impact beyond the single tenant.

### Likelihood Explanation
Preconditions: the target repository must have Review Stacks enabled (`review_stacks_enabled`), and the attacker must be able to both (a) apply/have a label named `bundle_gemfile` (or another Bundler-scrubbed var name) captured onto the PR's `pull_request.labels`, and (b) control the PR branch's file content (trivial, since it's their own branch/fork). Per the stated threat model this is achievable by "any GitHub user who can open a pull request... and label their own PR" without any Shipit credentials. No signature bypass or secret is needed — the exploit only depends on Shipit's own review-stack env-merging logic. This is fully repeatable per PR/label change and does not require live GitHub in tests (values can be set directly on the `PullRequest` fixture as existing tests do).

### Recommendation
Apply a strict allowlist (or denylist of `BUNDLE_*`, `RUBYOPT`, `RUBYLIB`, `GEM_*`, `LD_PRELOAD`, `PATH`, etc.) when converting PR labels into environment variables in `ReviewStack#env`, and/or re-apply the `Command::BASE_ENV` scrub *after* merging `@env` in `Command#unbundled_env` for any key that Bundler explicitly nils, so that user-controlled env values can never resurrect Bundler-internal isolation variables.

### Proof of Concept
```ruby
# test/lib/shipit/command_test.rb (new)
test "user-supplied env cannot resurrect Bundler-scrubbed BUNDLE_GEMFILE" do
  scrubbed = Shipit::Command::BASE_ENV['BUNDLE_GEMFILE']
  assert_nil scrubbed, "Precondition: Bundler.unbundled_env must scrub BUNDLE_GEMFILE"

  command = Shipit::Command.new('bundle exec true', env: { 'BUNDLE_GEMFILE' => 'true' }, chdir: '.')
  # Vulnerable behavior (current code):
  assert_equal 'true', command.unbundled_env['BUNDLE_GEMFILE']
  # Expected/fixed behavior:
  # assert_nil command.unbundled_env['BUNDLE_GEMFILE']
end

# test/lib/shipit/task_commands_test.rb (extend existing label test)
test "#env does not let PR labels reintroduce BUNDLE_GEMFILE" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["bundle_gemfile"]
  task = shipit_tasks(:shipit_restart)
  task.stack = stack

  env = Shipit::TaskCommands.new(task).env
  # Vulnerable behavior (current code):
  assert_equal 'true', env['BUNDLE_GEMFILE']
  # Expected/fixed behavior:
  # assert_nil env['BUNDLE_GEMFILE']
end
```
Both assertions demonstrate the equality binding (`BASE_ENV['BUNDLE_GEMFILE'] == nil` vs. final `unbundled_env['BUNDLE_GEMFILE'] == 'true'`) is broken, confirming label-derived env can override Bundler's intentional scrub.
