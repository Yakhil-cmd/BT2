## Title
Stack-scoped `ApiClient` tokens can read CI/deploy status of any stack via the CCMenu endpoint - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
The reported ERC20 bug class is: a contract enforces an authorization check in one place (recipient identity) but performs the sensitive action against a *different*, unchecked value, so the trust binding "party authorized == party acted upon" is broken. The engine analog is `Shipit::Api::CCMenuController`, where the binding "stack a token is authorized to read == stack the controller renders" is broken: the token's stack scope is verified generically via `require_permission :read, :stack`, but the actual stack object used to render results is looked up unscoped, bypassing the very mechanism (`BaseController#stacks`) that restricts an `ApiClient` to its assigned stack.

### Finding Description
`Shipit::Api::BaseController` establishes the scoping contract used by every other API controller: an `ApiClient` created with a `stack_id` may only ever resolve stacks from a pre-filtered relation: [1](#0-0) 

`require_permission!` (invoked by `require_permission :read, :stack`) only checks that the client's `permissions` array includes `"read:stack"` — it never checks *which* stack is being accessed: [2](#0-1) 

So the only place that enforces "this token may only see the stack it was scoped to" is the `stacks`/`stack` helper in `BaseController`. `CCMenuController` overrides `stack` and bypasses that scoping entirely, resolving the stack directly from all stacks regardless of `current_api_client.stack_id`: [3](#0-2) 

`CCMenuController` also supports authenticating via a `token` query-string parameter instead of the `Authorization` header, which is how CCMenu/CCTray clients are meant to poll it unauthenticated in a browser context: [4](#0-3) 

Any valid `ApiClient` token that has the `read:stack` permission — including one deliberately scoped to a single stack via `stack_id` (e.g. the `here_come_the_walrus` fixture) — passes `require_permission :read, :stack` and then `stack` resolves whatever `stack_id` is present in the URL, not the one the token is bound to. The route is `GET /api/stacks/*stack_id/ccmenu`, and the `stack_id` segment is fully attacker-controlled: [5](#0-4) 

Every other API controller (`StacksController`, `DeploysController`, `HooksController`, etc.) relies on the inherited `stack`/`stacks` methods and is therefore correctly scoped, as shown by the existing test asserting scoped clients only see their own stack in `StacksController#index`: [6](#0-5) 

No equivalent cross-stack test exists for `CCMenuController`, and its own test suite only exercises the client's own stack: [7](#0-6) 

### Impact Explanation
An `ApiClient` token that is legitimately scoped to Stack A (with `read:stack` permission) can request `GET /api/stacks/<owner>/<repo>/<env>/ccmenu?token=<token>` for Stack B (any other stack in the installation) and receive Stack B's `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `activity`, and deploy `webUrl`. This is an unauthenticated-scope read of another stack's deploy/build state that the token holder was never granted access to, matching the "High" impact category of unauthorized read of stack state/deploy output through a broken authorization scoping binding.

### Likelihood Explanation
Exploitation requires only possession of any valid, unprivileged `ApiClient` token scoped to one stack (a routine, low-privilege credential many integrations hold) and knowledge/guessing of another stack's `owner/repo/environment` path, which is often predictable or discoverable (e.g., via the `stacks#index` UI/API for globally-scoped tokens, or common naming conventions). No special access or social engineering is needed beyond having one working API token.

### Recommendation
Remove the `stack` override in `CCMenuController` (or reimplement it using the inherited `stacks.from_param!` scope) so that stack resolution is subject to the same `current_api_client.stack_id` restriction enforced everywhere else, and add a regression test asserting a stack-scoped token cannot fetch CCMenu data for a different stack.

### Proof of Concept
1. Create/observe an `ApiClient` scoped to Stack A only, e.g. fixture `here_come_the_walrus` (`stack: shipit`, permission `read:stack`): [8](#0-7) 
2. Using that client's `authentication_token`, issue `GET /api/stacks/<owner>/<other-repo>/<env>/ccmenu?token=<token>` for a *different* Stack B.
3. `authenticate_api_client` succeeds because the token is valid. `require_permission :read, :stack` succeeds because the client has `read:stack`. `stack` resolves Stack B via `Stack.from_param!`, bypassing the `stacks` scope that would otherwise raise/`Stack.none` for a client restricted to Stack A.
4. The response renders Stack B's build/deploy status XML, which the token holder was not authorized to see.
