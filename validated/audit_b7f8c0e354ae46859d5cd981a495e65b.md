This confirms my hypothesis: `verify_signature` in `WebhooksController` picks the verification secret/app based only on `repository.owner.login` (the "organization"), while every event handler (`PushHandler`, `StatusesController`-like handlers, pull-request handlers, etc.) resolves the target `Stack`/`Repository` using `repository.full_name` — a distinct field of the same signed JSON body. Since Shipit supports multiple independently-configured GitHub Apps/organizations (`docs/setup.md` "Using Multiple Github Applications", `lib/shipit.rb#github_app_config`), an org admin who legitimately controls one configured GitHub App (and thus its `webhook_secret`) can sign an arbitrary payload where `repository.owner.login` equals their own org (so the correct/expected secret is selected and validates) while `repository.full_name` names a repository belonging to a *different* configured org/stack. Downstream handlers trust `full_name` without ever checking it against the org that was cryptographically authenticated, letting the attacker inject a forged `push`/`pull_request`/`status` event that drives Shipit's sync, statuses, or review-stack provisioning for a repository outside their own org.

### Title
Webhook signature verification authenticates the sending organization but handlers act on an unrelated `repository.full_name` from the same payload - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp`/secret to validate the HMAC signature against using `repository.owner.login` (or `organization.login`) taken from the untrusted JSON body itself, then validates the signature with that org's secret. Every webhook handler (`PushHandler`, pull-request handlers, etc.) however identifies which `Repository`/`Stack` to mutate using `repository.full_name`, a sibling field in the same payload, without any check that it belongs to the organization whose secret validated the request.

### Finding Description
`repository_owner` is computed purely from request data: [1](#0-0) 
and used to pick the `GitHubApp` (and therefore secret) used for verification: [2](#0-1) 
Shipit explicitly supports multiple independently configured GitHub Apps, one per organization, each with its own `webhook_secret`: [3](#0-2) [4](#0-3) 
Meanwhile, the base `Handler` class and all concrete handlers (`PushHandler`, pull-request handlers, etc.) resolve the target repository/stack from `repository.full_name`: [5](#0-4) [6](#0-5) 

The binding that should hold is: `organization that authenticated the request == organization owning the repository the handler writes to`. Because `verify_signature` only proves "this body was signed by the app registered for `repository.owner.login`," and handlers separately trust `repository.full_name`, an attacker who is a legitimate admin of Org A (and thus knows Org A's `webhook_secret`, which they configured themselves when installing their own GitHub App instance) can craft a JSON body where `repository.owner.login = "OrgA"` (so signature verification picks and passes Org A's secret) but `repository.full_name = "OrgB/victim-repo"`. `verify_signature` succeeds, and `PushHandler` (or pull-request handlers) then acts against `OrgB/victim-repo`'s stack, triggering a `GithubSyncJob`, statuses, or review-stack provisioning for a repository outside the attacker's authenticated organization.

### Impact Explanation
This breaks the equality "organization that authenticated == repository being written," allowing an attacker who legitimately controls one onboarded GitHub App to forge sync/push/status/pull-request events for stacks belonging to a completely different organization also hosted on the same Shipit instance, triggering unauthorized deploy syncs and other stateful side effects. This aligns with the "High" impact bar (escalation across repository/authorization boundaries triggering unauthorized state changes) — it does not achieve full RCE or credential exfiltration, but it does cross a documented cross-repository trust boundary without any privileged Shipit account.

### Likelihood Explanation
Requires the attacker to control (or have configured) at least one legitimate GitHub App entry in Shipit's multi-org `secrets.github` configuration — a scenario explicitly documented and supported by Shipit (`docs/setup.md`, "Using Multiple Github Applications"). No Shipit session, `ApiClient` token, or privileged Shipit account is needed; only knowledge of one org's own webhook secret, which the attacker sets themselves during onboarding.

### Recommendation
When resolving the target repository/stack in `Handler#stacks`/`#repository_name`, verify that the resolved repository's owner matches the organization used to select and validate the webhook signature (`repository_owner` in `WebhooksController`), rejecting the event otherwise. Alternatively, only accept `repository.full_name` values whose owner segment matches the verified `repository_owner`.

### Proof of Concept
1. Configure Shipit with two GitHub Apps: `OrgA` (attacker-controlled, secret known to attacker) and `OrgB` (victim, tracked stack `OrgB/victim-repo`), per `docs/setup.md`'s multi-org example.
2. Attacker crafts a `push` webhook JSON body: `{"ref": "refs/heads/main", "after": "<malicious-sha>", "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgB/victim-repo"}}`.
3. Attacker computes `X-Hub-Signature: sha1=HMAC(OrgA_webhook_secret, body)` and POSTs to `/webhooks`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgA")`, verifies successfully against `OrgA`'s secret.
5. `PushHandler#process` resolves `stacks` via `repository.full_name` = `OrgB/victim-repo`, enqueuing `GithubSyncJob` against the victim's stack, despite the request never being authenticated by `OrgB`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
