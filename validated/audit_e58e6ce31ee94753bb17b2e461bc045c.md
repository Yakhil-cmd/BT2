### Title
Cross-repository status webhook mutates arbitrary victim stack's commit status and triggers unauthorized continuous deployment - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits purely by `sha` with no scoping to the repository/stack that authenticated the webhook, so a `status` event signed for the attacker's own GitHub organization can create a `Status` on a commit belonging to an unrelated victim stack. If that commit is the victim stack's next undeployed commit and the stack has `continuous_deployment: true`, this flips `Commit#deployable?` to true and drives an unattended deploy.

### Finding Description
The broken binding is: `webhook.repository_owner (signature-verified org) == commit.stack.github_repo_name (org whose stack is mutated)`. This is **not enforced**.

`WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-30) only checks that the raw payload is validly signed by `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight from the attacker-controlled payload (`params.dig('repository', 'owner', 'login')`, line 59-62). It proves *who sent the payload* but never binds that identity to which `Commit`/`Stack` rows may be touched.

`StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24):
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This queries `Commit` globally by `sha` across the entire installation, with no `stack_id`/`github_repo_name` filter tying the result back to `repository_owner`. `Commit#create_status_from_github!` (app/models/shipit/commit.rb:165-169) then calls `statuses.replicate_from_github!(stack_id, github_status)`, using the *victim's own* `stack_id`, not anything derived from the attacker's payload.

Given the stated precondition (a sha shared between a commit the attacker can drive a status for and the victim stack's next undeployed commit), the created `Status` triggers `Status#after_commit :schedule_continuous_delivery` (app/models/shipit/status.rb:19,42-44) → `Commit#schedule_continuous_delivery` (app/models/shipit/commit.rb:281-287):
```ruby
def schedule_continuous_delivery
  return unless deployable? && stack.continuous_deployment? && stack.deployable?
  ContinuousDeliveryJob.set(wait: RECENT_COMMIT_THRESHOLD).perform_later(stack)
end
```
`Commit#deployable?` is `!locked? && (stack.ignore_ci? || (success? && !blocked?))`; the attacker-forged `success` status flips it true. `ContinuousDeliveryJob#perform` (app/jobs/shipit/continuous_delivery_job.rb:10-21) calls `stack.trigger_continuous_delivery` (app/models/shipit/stack.rb:210-229), which resolves `next_commit_to_deploy` (stack.rb:235-243) and calls `trigger_deploy`, writing a real `Deploy` record and enqueuing it — for the victim stack the attacker never authenticated for.

None of the existing guards close this gap: `verify_signature` validates signer identity, not target scope; `drop_unhandled_event` only filters unregistered event types; the `ExplicitParameters` schema in `StatusHandler.params` only validates payload shape (`sha`, `state`, etc.), not ownership; there is no `Repository`/`Stack` lookup keyed by the payload's `repository.full_name` anywhere in this handler.

### Impact Explanation
A `Status` record is written for, and a `Deploy` is triggered on, a stack the attacker never authenticated a webhook for — this is exactly the "payload for one repository mutating another's stack/commit" and "unauthorized deploy" category (Critical). The attacker fully controls `state`, `description`, `target_url`, and `context` of the forged status, and can repeat this against any stack in the installation whose next undeployed commit happens to share a sha with a commit under the attacker's control, with no interaction from the victim required. Blast radius spans every `continuous_deployment: true` stack in the tenant.

### Likelihood Explanation
Requires: (1) attacker owns a GitHub org/repo with the Shipit GitHub App installed (achievable by any GitHub user for their own org, no Shipit privilege needed), (2) a sha collision/shared sha between a commit the attacker can drive statuses for and the victim stack's next undeployed commit (an explicit precondition of this question, not independently proven here), (3) victim stack has `continuous_deployment: true`. Given the precondition is granted, the rest of the exploit requires only a single unauthenticated-to-Shipit HTTP POST to `/webhooks` with a validly-signed status payload for the attacker's own repo — no Shipit session, token, or secret needed beyond what the attacker's own GitHub App installation already grants them.

### Recommendation
Scope `StatusHandler#process` to the repository that authenticated the webhook, e.g. resolve `Stack`/`Commit` via `github_repo_name` derived from `params.repository.full_name` (or equivalent) in addition to `sha`, rejecting/ignoring commits that belong to a different repository than the one that signed the request.

### Proof of Concept
```ruby
test "status webhook for repo A creates a Status and triggers deploy on unrelated stack B with same commit sha" do
  attacker_repo_full_name = "attacker/attacker-repo"
  victim_stack = shipit_stacks(:shipit) # continuous_deployment: true
  victim_commit = victim_stack.next_commit_to_deploy_before_status # arrange a locked/pending commit
  shared_sha = victim_commit.sha

  GithubHook.any_instance.stubs(:verify_signature).returns(true)
  request.headers['X-Github-Event'] = 'status'
  body = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'ci/attacker',
    'created_at' => Time.now.iso8601,
    'repository' => { 'full_name' => attacker_repo_full_name, 'owner' => { 'login' => 'attacker' } }
  }.to_json

  assert_enqueued_with(job: ContinuousDeliveryJob, args: [victim_stack]) do
    assert_difference '-> { victim_commit.reload.statuses.count }', 1 do
      post :create, body:, as: :json
    end
  end
  assert_predicate victim_commit.reload, :deployable?

  assert_difference '-> { victim_stack.deploys.count }', 1 do
    perform_enqueued_jobs(only: ContinuousDeliveryJob)
  end
end
```
Assert on both sides of the equality: `repository_owner` from the signed payload (`"attacker"`) is not equal to `victim_commit.stack.github_repo_name`'s owner, yet the `Status`, `deployable?` transition, and `Deploy` all occur on `victim_stack`.     def trigger_continuous_delivery
      return if cached_deploy_spec.blank?

      commit = next_commit_to_deploy

      if should_resume_continuous_delivery?(commit)
        continuous_delivery_resumed!
        return
      end

      if should_delay_continuous_delivery?(commit)
        continuous_delivery_delayed!
        return
      end

      begin
        trigger_deploy(commit, Shipit.user, env: cached_deploy_spec.default_deploy_env)
      rescue Task::ConcurrentTaskRunning
      end
    end

    def schedule_merges
      ProcessMergeRequestsJob.perform_later(self)
    end

    def next_commit_to_deploy
      commits_to_deploy = commits.order(id: :asc).newer_than(last_deployed_commit).reachable.preload(:statuses)
      if maximum_commits_per_deploy
        commits_with_max_applied = commits_to_deploy.limit(maximum_commits_per_deploy)
        deployable_commits(commits_with_max_applied) || deployable_commits(commits_to_deploy)
      else
        deployable_commits(commits_to_deploy)
      end
    end
