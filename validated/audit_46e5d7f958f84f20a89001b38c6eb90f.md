### Title
API clients can impersonate arbitrary Shipit users via the unauthenticated `X-Shipit-User` header - ([File: app/controllers/shipit/api/base_controller.rb])

### Summary
The bug class in the external report is that a payload field (`msg.value` used for the LZ fee) is acted upon by privileged logic (`endpoint.send`) but is not covered by any verification that ties it to the caller's actual intent/authorization. The engine analog is the `X-Shipit-User` HTTP header: it is read directly from the request and used to set `current_user` for all attribution/authorization-sensitive actions in the API namespace, but it is never validated against the identity that actually authenticated the request (the `ApiClient` token). This breaks the binding "GitHub identity versus the `User` bound to the session/request".

### Finding Description
`Api::BaseController#authenticate_api_client` verifies only the `ApiClient` bearer token via HTTP Basic auth against `ApiClient.authenticate`: [1](#0-0) 

Separately, `current_user` for API requests is derived from an attacker-controlled header with no verification at all: [2](#0-1) 

`identify_user` simply looks up any `User` record by `login`, taken verbatim from the `X-Shipit-User` request header, and returns it as `current_user`. Nothing ties this to the `ApiClient` (`creator`, permissions, or the `Authorization` token). The `check_permissions!` performed by `require_permission!` only validates the `ApiClient`'s scope/stack binding: [3](#0-2) 

This `current_user` value (freely chosen by the caller of a valid API token) is then passed into privileged, attributed operations across the API surface:
- Stack locking: `stack.lock(params.reason, current_user)` [4](#0-3) 
- Deploy triggering: `stack.trigger_deploy(commit, current_user, ...)` [5](#0-4) 
- Rollback triggering / task abort: `deploy.trigger_rollback(current_user, ...)`, `active_task.abort!(aborted_by: current_user, ...)` [6](#0-5) 
- Task abort/trigger: `task.abort!(aborted_by: current_user)`, `stack.trigger_task(params[:task_name], current_user, ...)` [7](#0-6) 
- Merge request handling: `MergeRequest.request_merge!(stack, params[:id], current_user)` [8](#0-7) 

Equality before the attacker's request:
`authenticated_principal (ApiClient token owner/creator) == attributed_identity (current_user used in stack.lock/trigger_deploy/etc.)`

After sending a request with an arbitrary `X-Shipit-User: <victim-login>` header and a valid (even narrowly-scoped) API token:
`authenticated_principal (holder of the ApiClient token) != attributed_identity (current_user, spoofed as victim)`

The binding that a `User` action is actually being performed by that `User` (or a verified proxy for them) is broken: any caller holding a valid `ApiClient` bearer token for a given permission (e.g., `deploy:stack` scoped only to one stack) can attribute deploys, rollbacks, task aborts, locks, and merge-request actions to any existing `User` record simply by setting this header, regardless of whether that user ever authorized, or is even aware of, the action.

### Impact Explanation
This does not itself bypass the `ApiClient` permission/scope check (an attacker still needs a valid token with the relevant permission for the relevant stack), so it is not a full authentication bypass by itself. However, it breaks a load-bearing identity binding relied on by downstream authorization/audit logic (`aborted_by`, `lock_author`, deploy/rollback triggering author, merge request requester). Any system, hook, or process that trusts `current_user`/the recorded actor (e.g., `Stack#lock`, `Task#abort!`, `MergeRequest.request_merge!`) as a genuine indicator of who requested the action is deceived, letting a caller with a legitimate but limited API token perform ships/rollbacks/locks/merges "as" an arbitrary, potentially more privileged user. This is a spoofing/impersonation vector on the identity used for authorized, unauthorized-deploy-adjacent actions.

### Likelihood Explanation
Likelihood is Medium-to-High for anyone who already possesses a valid `ApiClient` token (which is the documented, supported way of calling the API): no further secret or session is needed — only setting a plain HTTP header (`X-Shipit-User`) to an arbitrary existing login is required, as confirmed by the test suite referencing this header for deploy/rollback/task requests.

### Recommendation
Do not trust the `X-Shipit-User` header as an authoritative identity. Either remove impersonation via header entirely and always attribute actions to the `ApiClient`/its `creator`, or require that "acting as user X" be an explicit, verified capability of the specific `ApiClient` (e.g., only allow `UnlimitedApiClient`, or clients explicitly granted an "impersonate" permission tied to a specific user/team, and validate the header value against that grant) so the header contributes to the audit trail only when covered by verified authorization, analogous to including the LZ fee/claim gas in the same authenticated call rather than trusting an unverified side-channel value.

### Proof of Concept
1. Obtain (or be issued) a valid, narrowly-scoped `ApiClient` token, e.g. permissions `['deploy:stack']` scoped to `stack_id: X` (see fixture `here_come_the_walrus` in `test/fixtures/shipit/api_clients.yml`).
2. Send `POST /api/stacks/:id/deploys` (or `/rollbacks`, `/tasks/:task_name`, lock `PATCH`, or merge-request `PATCH`) with `Authorization: Basic <token>` and header `X-Shipit-User: <victim-login>` where `<victim-login>` is any existing `User` in the DB (e.g. an admin who is a member of `Shipit.github_teams`).
3. `Api::BaseController#identify_user` resolves `current_user` to the victim `User` record purely from the header, with no check that the token belongs to or is authorized to act as that user.
4. The deploy/rollback/lock/merge action is recorded and executed with the victim attributed as the actor (`current_user`), even though the victim never made the request. [2](#0-1)

      def create
        commit = stack.commits.by_sha(params.sha) || param_error!(:sha, 'Unknown revision')
        param_error!(:force, "Can't rollback a locked stack") if !params.force && stack.locked?
        deploy = stack.deploys.find_by(until_commit: commit) || param_error!(:sha, 'Cant find associated deploy')
        rollback_env = stack.filter_rollback_envs(params.env)

        response = nil
        if !params.force && stack.active_task?
          param_error!(:force, "Can't rollback, deploy in progress")
        elsif stack.active_task?
          active_task = stack.active_task
          active_task.abort!(aborted_by: current_user, rollback_once_aborted_to: deploy, rollback_once_aborted: true)
          response = active_task
        else
          response = deploy.trigger_rollback(current_user, env: rollback_env, force: params.force, lock: params.lock)
        end

        render_resource(response, status: :accepted)
      end
