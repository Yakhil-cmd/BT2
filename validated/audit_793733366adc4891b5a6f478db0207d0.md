Based on my analysis, I found a strong analog to the Liquity trove state-handling bug in ocore's AA (Autonomous Agent) trigger processing pipeline.

### Title
Unhandled cache-miss state for `trigger.unit` in AA duplicate-trigger check crashes the writer/consensus pipeline - (File: aa_composer.js)

### Summary
Just as the Liquity strategy assumed a trove could only be in one of two coarse states (existing/non-existing) when `adjustTrove()` actually reverts on any state other than `active`, ocore's `handleTrigger()` in `aa_composer.js` assumes that any stable trigger unit is unconditionally present in the in-memory `storage.assocStableUnits` cache, and dereferences a property on it without a defensive check. If that assumption is violated, an unprivileged AA trigger sender can cause an uncaught exception during unit/AA processing, crashing whichever node is executing the trigger.

### Finding Description
In `handleTrigger()`, the code guards against a second primary trigger from the same unit like this: [1](#0-0) 

`storage.assocStableUnits[trigger.unit]` is accessed and `.count_aa_responses` is read off it without checking whether the entry exists. This mirrors the Liquity bug pattern: the code implicitly assumes the "trigger unit" object is always in one specific state (present, with a `count_aa_responses` field) rather than handling the case where it is absent from the cache (analogous to a trove being in an unexpected non-`active` state).

`assocStableUnits` is a bounded, prunable in-memory cache of recently-stabilized units; entries are removed once the min-retrievable MCI advances past them, via `storage.updateMinRetrievableMciAfterStabilizingMci`, called from `markMcIndexStable()` in `main_chain.js` before AA triggers for that MCI are queued and eventually handled: [2](#0-1) [3](#0-2) 

AA triggers are persisted to the `aa_triggers` table and processed asynchronously/afterward (not necessarily in perfect lock-step with cache pruning), and `checkBalances()`/other logic explicitly acknowledges that unhandled triggers can be pending for a while: [4](#0-3) 

If processing of a queued trigger is delayed long enough (e.g., during catch-up with many MCIs advancing quickly, or a backlog of pending `aa_triggers`), the trigger's own unit can be pruned out of `storage.assocStableUnits` before `handleTrigger()` runs for it. At that point `storage.assocStableUnits[trigger.unit]` is `undefined`, and `.count_aa_responses` throws a `TypeError` ("Cannot read properties of undefined"), which is an unhandled JS exception inside the synchronous write/trigger-handling pipeline.

### Impact Explanation
An uncaught exception inside `handleTrigger()` — which executes under the `write` mutex as part of MCI stabilization/AA processing — crashes the node process executing it. Because trigger processing order and cache-pruning thresholds are consensus-relevant, this can affect any/all full nodes that reach the same backlog condition, not just one operator. This matches the "network unable to confirm new units" impact category: nodes that crash while processing AA triggers cannot continue validating/writing new units until restarted, and any AA execution relying on this code path is blocked, mirroring how the Liquity strategy's `harvest()`/`withdraw()` became permanently broken and had to be manually pulled from the vault.

### Likelihood Explanation
The trigger path is reachable by any unprivileged user who sends a payment to any AA address (a primary trigger) — this is normal DApp usage and requires no special privilege. The precondition (the trigger's own trigger-unit falling out of `assocStableUnits` before its queued trigger is processed) requires a backlog/catch-up scenario, so it is not trivially forced on demand by a single unit, but it is a genuinely reachable state given normal node operation under load, unlike a purely theoretical edge case — this raises it above "low" severity because the resulting failure mode is a full crash rather than a graceful bounce.

### Recommendation
Before dereferencing `storage.assocStableUnits[trigger.unit]`, check that the entry exists; if it was pruned from the cache, fall back to reading `count_aa_responses` (or the equivalent duplicate-trigger indicator) from the database (`units` table) instead of assuming in-memory cache presence, mirroring how other lookups in the codebase (e.g., `readAssetInfo`, `readUnitProps`) gracefully fall back to DB queries when the cache misses.

### Proof of Concept
1. An unprivileged user submits a valid primary trigger unit to an AA address.
2. The unit stabilizes; `main_chain.js`'s `markMcIndexStable()` queues it as a row in `aa_triggers` and calls `updateMinRetrievableMciAfterStabilizingMci`, which prunes old entries from `storage.assocStableUnits` as the min-retrievable MCI advances.
3. If trigger processing is delayed (e.g., the node is catching up through many further MCIs, causing many more prunings, or the `aa_triggers` backlog is large — acknowledged as a real scenario in `checkBalances()`), by the time `handleTrigger()` finally runs for the queued trigger, `storage.assocStableUnits[trigger.unit]` is `undefined`.
4. Line `aa_composer.js:1861` throws a `TypeError` when accessing `.count_aa_responses` on `undefined`, crashing the node process handling the write/trigger batch.
