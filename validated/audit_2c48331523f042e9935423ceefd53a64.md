### Title
Cross-repository Status injection via SHA-scoped `Commit` lookup in `StatusHandler#process` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves commits with a global, unscoped `Commit.where(sha: params.sha)` query, while the webhook's authenticity is only verified against the sending repository's own owner/org via `WebhooksController#verify_signature`. Because git commit SHAs are content-derived and are shared identically across forks/mirrors of the same history, a legitimate, correctly-signed `status` webhook from an attacker-owned Repository B can carry a SHA that also exists as a `Commit` row belonging to an unrelated Stack in Repository A, causing a `Status` row to be written onto Repository A's commit.

### Finding Description
The claimed binding is: `repository_owner` (used in `Shipit.github(organization: repository_owner)` at `app/controllers/shipit/webhooks_controller.rb` line 25 to select which webhook secret verifies the payload) `==` the repository whose `Commit`/`Stack` data gets mutated in `StatusHandler#process`.

Tracing the code:
- `WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-49) only checks that the raw payload signature matches the HMAC secret configured for `repository_owner` (`params.dig('repository','owner','login')`). This proves the request genuinely came from GitHub *for that owner/repo*, nothing more. [1](#0-0) 
- `StatusHandler#process` then does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — there is no filter by `stack_id`, `repository`, or any binding back to the repository that authenticated the webhook. [2](#0-1) 
- `Commit` has no unique/scoping constraint tying `sha` to a particular repository beyond `belongs_to :stack`; `Commit.by_sha` and other finders operate globally across the `commits` table. [3](#0-2) 

Root cause: git SHAs are content hashes of (tree, parent(s), author, committer, message, timestamps), not repository-scoped identifiers. Forks and mirrors of the same upstream history naturally share identical commit SHAs with the origin. If Shipit tracks a Stack against the upstream Repository A, and an unprivileged attacker forks that repository as their own Repository B (a normal GitHub feature, requiring no special privilege), any commit SHA inherited from the shared history is identical between A and B. When the attacker's fork emits a genuine `status` event (e.g., by opening a PR, pushing a branch, or having any CI/service post a status to their own fork for that shared commit), GitHub signs it with Repository B's/organization B's own `webhook_secret`. `verify_signature` succeeds because it is validating exactly what it claims — a real GitHub webhook for org B — but `StatusHandler#process` then indiscriminately matches that SHA against all `Commit` rows in the database, including the one belonging to Stack A/Repository A, and writes a `Status` row onto it via `commit.create_status_from_github!(params)` → `statuses.replicate_from_github!`.

None of the listed guards prevent this: `verify_signature` authenticates the sender org but never checks the sender matches the repository owning the matched `Commit`; there is no `ExplicitParameters` constraint enforcing repository identity beyond `sha`/`state`; no model validation on `Commit`/`Status` ties the write back to the authenticated repository.

### Impact Explanation
An attacker who owns/forks Repository B can cause arbitrary `Status` rows (with attacker-chosen `state`, `description`, `target_url`, `context`) to be attached to a `Commit` belonging to a completely different Stack/Repository A that shares no organization, team, or Shipit configuration with B — this is exactly the "payload for one repository mutating another's stack/commit" Critical-severity category. Since `Commit#create_status_from_github!` feeds into `Status::Group` computation, which drives `deployable?`, `blocked?`, and `schedule_continuous_delivery`, a forged/cross-tenant status can influence whether Stack A's commit is considered "green" (or blocked), which is a step toward unauthorized deploys if the stack has continuous delivery enabled and the attacker can supply a `success` state for a shared SHA that Stack A is waiting to deploy.

### Likelihood Explanation
Preconditions: Repository A must be a public/forkable repo tracked by a Shipit Stack (typical setup), and Repository B must be a fork (or otherwise share history) of Repository A, owned by the attacker — trivially achievable by any GitHub user with zero privileges. No Shipit secrets, sessions, or API tokens are needed; the attacker only needs GitHub's native fork/webhook mechanics, which they fully control on their own repository. The attack is repeatable against any Stack whose repository is public and forkable, and costs only a `git fork` + a benign action that triggers a `status` event on the fork (many third-party integrations/services do this automatically). This is a realistic, low-cost, repeatable path.

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` (and any other SHA-keyed handler) by the repository that the webhook was verified against — join through `Stack` and filter by `stack.repository_owner`/`stack.repository_name` matching `params.dig('repository','owner','login')` and `params.dig('repository','name')`, e.g. `Commit.joins(:stack).where(sha: params.sha, shipit_stacks: { repository_owner: ..., repository_name: ... })`. More generally, thread the authenticated repository identity from `WebhooksController` into every handler and require an exact repository match before mutating any `Commit`/`Stack` record.

### Proof of Concept
Minitest integration test (`test/controllers/webhooks_controller_test.rb`-style, no live GitHub, using `Shipit.github` stub / fixture webhook secrets):
1. Create `stack_a` under repository `orgA/repo` with a `Commit` row `commit_a` with `sha = "deadbeef...".`
2. Create `stack_b` under repository `orgB/fork` (different org, no shared team) — no commit row needed for B, or optionally one to prove B's own commit also gets a status independently.
3. Build a `status` webhook JSON payload: `{"sha": commit_a.sha, "state": "success", "repository": {"name": "fork", "owner": {"login": "orgB"}}}`.
4. Sign the raw body with `orgB`'s configured `webhook_secret` (as `Shipit.github(organization: "orgB")` would validate) and POST to `/webhooks` with header `X-Github-Event: status` and `X-Hub-Signature` computed from orgB's secret.
5. Assert response is `200 ok` (signature accepted for orgB).
6. Assert `commit_a.reload.statuses.count` increased by 1 and the new `Status`'s `state == "success"`, proving a Repository-B-authenticated webhook mutated Repository A's commit — i.e., `repository_owner` used for verification (`orgB`) != owner of the mutated `Commit`'s stack (`orgA`), demonstrating the broken binding.
