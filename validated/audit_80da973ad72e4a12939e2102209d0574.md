### Title
AA-definition validation gate bypassed for dynamically generated (formula-based) nested AA definitions - ([File: aa_validation.js])

### Summary
`aa_validation.validateAADefinition` is the single authorization/soundness gate that all AA definitions must pass before being accepted as a valid, fund-controlling Autonomous Agent (structural checks, `hasFieldsExcept` whitelisting, `bounce_fees`/`getters` checks, and formula complexity/op-count limits). This gate is fully applied only when a `definition`-app payload is a literal `['autonomous agent', {...}]` array. When the payload is instead an oscript formula (`{$child_aa}`), `aa_validation.js` explicitly skips all structural/complexity validation of the eventual definition, trusting that it will be "checked later." However, the actual runtime-generated definition, produced by `aa_composer.js`'s `replace()` during AA execution, is never re-validated with `validateAADefinition`. It is persisted directly via `storage.insertAADefinitions`, which only calls `aa_validation.determineGetterProps` — a function that assumes the definition is already valid and merely extracts getter metadata.

### Finding Description
`validateAADefinition` inspects a `definition`-app message inside an AA template: [1](#0-0) 

When `mci >= constants.aa2UpgradeMci` and the payload's `definition` (or `definition[1]`) is itself an oscript formula string rather than a literal array/object, the function immediately calls `cb2()` and **skips** every structural check that would otherwise apply to a nested AA definition (`isArrayOfLength`, `hasFieldsExcept`, `isNonemptyObject`, etc.). This is intentional, by design, because the concrete content can only be known at trigger time.

At trigger time, `aa_composer.js`'s `replace()` function evaluates these formulas and substitutes the computed value directly into the message payload, with no subsequent call to `validateAADefinition`: [2](#0-1) [3](#0-2) 

The comment at line 617 even acknowledges the dynamic nature of this path ("app=definition is also replaced using the current trigger and vars ... has to generate `{}`-formulas in order to be dynamic") but there is no accompanying re-validation step.

Once the response unit containing this freshly computed `definition` message is composed, `writer.js` extracts all such payloads and hands them straight to `storage.insertAADefinitions`: [4](#0-3) 

`storage.insertAADefinitions` does not call `aa_validation.validateAADefinition`; it only calls `aa_validation.determineGetterProps`, which explicitly assumes the definition is already valid ("assumes the definition is valid"): [5](#0-4) [6](#0-5) 

By contrast, the only code path that does invoke the full `validateAADefinition` gate is `validation.js`'s handling of a *human-posted* `definition` message: [7](#0-6) 

This is structurally the same bug class as GHSA-vwjc-v7x7-cm6g: a hardening/validation gate (`validateAADefinition`'s structural + complexity checks, analogous to ArcadeDB's `checkPermissionsOnDatabase(UPDATE_SECURITY)`) is enforced on one entry point (literal, human-posted AA definitions) but is bypassed on an alternate, reachable entry point (AA-generated definitions produced via oscript formulas and persisted through `storage.insertAADefinitions`).

### Impact Explanation
An AA author can craft an `init`/message formula that builds an object at runtime (via computed keys and `bObjectResultAllowed`, as demonstrated in the existing test `test/aa_composer.test.js:922-1010` "AA with generated definition of new AA") and post it as a nested `definition` message. Because the structural whitelist (`hasFieldsExcept`, `aaApps` message-type whitelist, `bounce_fees`/`getters` shape checks) and the static complexity/op-count limits (`MAX_COMPLEXITY`/`MAX_OPS`, enforced only inside `validateAADefinition`'s `validateFormula`) are never applied to this generated object, it is possible to register a permanent, fund-controlling AA address (`chash160` of the generated definition) whose internal structure was never checked against the invariants the rest of the codebase (and other network nodes) assume for any object in `aa_addresses`. This can produce a definition that different node/validator code paths treat inconsistently (unknown message `app` values, malformed `asset`/`payment` sub-objects, unmetered complexity), risking AA fund loss/freezing or node disagreement on validity when that AA is subsequently triggered, since normal defenses assume every entry in `aa_addresses` has already passed `validateAADefinition`.

### Likelihood Explanation
Any unprivileged unit poster can define an AA whose `init`/message code programmatically constructs a nested AA definition and posts it as a `definition`-app message — this is a supported, documented AA feature (already exercised by existing unit tests), not a hypothetical edge case. No special permission beyond normal AA authoring is required, making the reachable path directly comparable to the "any user authorized for the DB" precondition in the original ArcadeDB report.

### Recommendation
Centralize the AA-definition safety gate: after `aa_composer.js`'s `replace()` produces the concrete `definition` payload for a `definition`-app message, run it through `aa_validation.validateAADefinition` (with the appropriate `mci`) before it is included in the response unit / passed to `storage.insertAADefinitions`. `storage.insertAADefinitions` should refuse to persist any AA definition that has not been confirmed valid by `validateAADefinition`, rather than assuming validity and only extracting getter props via `determineGetterProps`.

### Proof of Concept
1. Author AA `factory` with an `init` formula that builds `$child = ['autonomous agent', { <object deliberately violating hasFieldsExcept / message app whitelist / bounce_fees shape / complexity limits> }]` and computes `$child_address = chash160($child)`.
2. `factory`'s messages include `{ app: 'definition', payload: { definition: '{$child}' } }` (formula form), which passes `validateAADefinition` unchecked per `aa_validation.js:208-223` since the payload is a formula.
3. Trigger `factory`; `aa_composer.js` `replace()` evaluates `$child` and writes the resulting non-compliant object directly into the `definition` message of the response unit.
4. `writer.js` extracts this payload and `storage.insertAADefinitions` persists it into `aa_addresses` after only running `determineGetterProps` — the malformed/oversized definition is now a permanently active AA address that never passed `validateAADefinition`'s structural or complexity checks.
