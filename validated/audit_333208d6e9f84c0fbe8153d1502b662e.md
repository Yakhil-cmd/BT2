### Title
Stack-scoped API tokens can read the CCMenu status of any stack, not just the stack they are authorized for - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::ApiClient` supports being scoped to a single stack via its `stack_id` column, and `Api::BaseController` enforces that scope for every controller that reads `stack` through the shared helper. `Api::CCMenuController` overrides that helper and resolves the stack directly from `Stack.from_param!(params[:stack_id])`, never consulting the client's `stack_id`. This breaks the binding "the stack an `ApiClient` token authorizes == the stack the endpoint actually touches," letting any client holding `read:stack` (even one deliberately scoped to a single stack) read the CCMenu build status of every stack in the instance.

### Finding Description
`ApiClient` permission checks are two-layered: an operation/scope check (`read:stack`, `write:stack`, ...) via `check_permissions!`, and a per-record scope check performed by filtering the `Stack` relation to `current_api_client.stack_id` when the client is stack-bound: [1](#0-0) 

This is the mechanism relied on by every other authenticated resource controller (`stacks_controller`, `tasks_controller`, `hooks_controller`) because they call `stack` / `stacks.from_param!`, which is defined once in `BaseController`: [2](#0-1) 

`Api::TasksController` and `Api::HooksController` both rely on this same `stack` helper (no local override), so their per-record enforcement is correctly bound to the client's `stack_id`: [3](#0-2) [4](#0-3) 

`Api::CCMenuController`, however, redefines `stack` to call `Stack.from_param!` directly, bypassing the `stacks` scoping entirely, while still only requiring the generic `read, :stack` permission: [5](#0-4) 

The `ApiClient` model itself demonstrates that stack-scoped tokens are a real, intentional feature — `check_permissions!` only checks the operation/scope string, not the stack association, so the "which stack" boundary is entirely dependent on controllers correctly calling `stacks.from_param!`: [6](#0-5) 

Fixtures confirm the supported use case of a stack-scoped client with only `read:stack`: [7](#0-6) 

The equality that should hold is:
`current_api_client.stack_id (the stack the token is authorized for)` == `stack (the stack whose data is rendered)`

Before the CCMenu request: this equality holds for every other resource endpoint because they use `stacks.from_param!`.
After a request to `Api::CCMenuController#show` with a stack-scoped client's Basic-Auth token but an arbitrary `stack_id` in the URL: the equality is broken — `stack` resolves to whatever `params[:stack_id]` names, regardless of `current_api_client.stack_id`.

### Impact Explanation
This is an unauthenticated-scope escalation: a token that an operator deliberately restricted to a single stack (e.g., the `here_come_the_walrus` pattern, or any client created with `stack:` set and only `read:stack`) can enumerate and read the CI/CD status (`lastBuildStatus`, `lastBuildLabel`, `activity`, lock state) of every other stack managed by the Shipit instance by simply changing the `stack_id` path segment. This matches the "unauthorized read of stack state" High-impact category, since the intended per-token repository/stack boundary is silently not enforced for this one endpoint while appearing to be enforced (and is enforced) everywhere else.

### Likelihood Explanation
Likelihood is high for any deployment that issues stack-scoped API tokens (a documented, supported configuration) and exposes the CCMenu endpoint (`/api/*/ccmenu`, used for CI dashboard integrations such as CCTray/CCMenu clients). No special privilege is needed beyond possessing any valid `read:stack`-scoped credential; the attacker only needs to know or guess another stack's `to_param` (owner/repo/env, which is often public/guessable), and swap it into the URL.

### Recommendation
Have `Api::CCMenuController#stack` resolve the record through the same `stacks` (or `stacks.from_param!`) helper used by `BaseController`, instead of calling `Stack.from_param!` directly, so the `current_api_client.stack_id` restriction is honored consistently across all authenticated read endpoints.

### Proof of Concept
1. Create a stack-scoped `ApiClient` restricted to `stack_a` with permission `read:stack` only (as in the `here_come_the_walrus` fixture pattern).
2. Authenticate to `Api::CCMenuController#show` using this client's Basic-Auth token, but request `GET /api/:stack_b_owner/:stack_b_repo/:stack_b_env/ccmenu.xml` (a different stack the client was never scoped to).
3. Because `Api::CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly rather than `stacks.from_param!`, the request succeeds and returns `stack_b`'s build status/activity, even though `current_api_client.stack_id` points to `stack_a`. [8](#0-7)

    validates :creator, :name, presence: true

    PERMISSIONS = %w[
      read:stack
      write:stack
      deploy:stack
      lock:stack
      read:hook
      write:hook
    ].freeze
    validates :permissions, subset: { of: PERMISSIONS }

    class << self
      def authenticate(token)
        find_by(id: message_verifier.verify(token).to_i)
      rescue Shipit::SimpleMessageVerifier::InvalidSignature
      end

      def message_verifier
        @message_verifier ||= Shipit::SimpleMessageVerifier.new(Shipit.api_clients_secret)
      end
    end

    def authentication_token
      self.class.message_verifier.generate(id)
    end

    def check_permissions!(operation, scope)
      required_permission = "#{operation}:#{scope}"
      unless permissions.include?(required_permission)
        raise InsufficientPermission, "This operation requires the `#{required_permission}` permission"
      end

      true
    end
