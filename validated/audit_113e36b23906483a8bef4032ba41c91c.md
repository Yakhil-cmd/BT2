### Title
`StatusHandler#process` writes to `Commit` records globally by SHA without scoping through `stacks`, allowing a webhook for one repository to mutate a commit's status in another repository's stack - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler` inherits `Handler#stacks` and `Handler#repository_name` but its `#process` method never calls `stacks`; instead it queries `Commit.where(sha: params.sha)` across the entire `commits` table and calls `commit.create_status_from_github!(params)` on every match, regardless of which repository the webhook actually authenticated for. Other handlers (e.g. `CheckSuiteHandler`) correctly scope to `stacks.where(...)` before touching commits, so this is a structural deviation, not intentional design.

### Finding Description
The claimed binding, verified by inspection:
- Broken side (actual code): `Commit.where(sha: params.sha)` — a global, unscoped ActiveRecord query over the entire `commits` table [1](#0-0) 
- Expected side (repository-safe pattern used elsewhere): `stacks.where(...)` then commits scoped to that stack, as seen in `CheckSuiteHandler#process`: `stacks.where(branch: ...).each { |stack| stack.commits.where(sha: ...) }` [2](#0-1) 

`Handler#stacks` exists specifically to scope a webhook's effect to the repository named in `payload.dig('repository', 'full_name')`: `Repository.from_github_repo_name(repository_name)&.stacks || Stack.none` [3](#0-2) . `StatusHandler` never invokes this method, so its data source is not bound to the repository that produced/authenticated the webhook.

Path: `WebhooksController#create` parses the raw JSON body and dispatches it to `Handlers::StatusHandler.call(params)` after `verify_signature`, which validates the HMAC signature against `Shipit.github(organization: repository_owner)`, where `repository_owner` is read from the payload's `repository.owner.login` [4](#0-3) [5](#0-4) . This signature check authenticates that the payload really came from GitHub for the *organization* named in the payload — it says nothing about which *commit rows* the handler is allowed to touch.

`Commit.sha` is a git SHA and is content-addressed: forks/mirrors of the same upstream history — a common pattern when an organization tracks multiple Shipit stacks (e.g. staging/production repos, or forks) that share commit ancestry — will have identical rows with the same `sha` value across *different* `stack_id`s in the `commits` table. Because `StatusHandler#process` matches purely on `sha` with no `stack_id`/`repository_name` filter, a genuine, correctly-signed GitHub status webhook triggered by an action on Repository A (which the attacker legitimately owns/administers and for which the signature check passes) will also match and mutate `Commit` rows belonging to Repository B's stack if B shares that SHA in its history, via `commit.create_status_from_github!(params)` [1](#0-0) . That call creates a `Status` record for a stack the attacker's webhook never authenticated for, and it can flip that commit's deployability state: `create_status_from_github!` → `add_status` → recomputes `status`, fires `Hook.emit(:deployable_status, ...)`, and schedules `stack.schedule_merges` if state becomes `pending`/`success` [6](#0-5) [7](#0-6) . `schedule_merges`/continuous delivery being triggered on Stack B means the forged status on a shared SHA can unblock or trigger an unauthorized deploy for Stack B.

None of the existing guards catch this: `verify_signature` only checks the payload is genuinely from GitHub for the named organization/repository — it does not restrict which `Commit` rows the handler may write, and `ExplicitParameters` only validates the shape of `sha`/`state`/etc., not repository ownership [8](#0-7) .

### Impact Explanation
A correctly-signed status webhook for Repository A (owned/administered by the attacker) can write a `Status` record on a `Commit` belonging to a different `Stack`/repository B, provided both share a commit SHA (a realistic scenario for forked or mirrored repositories tracked as separate Shipit stacks). This is a cross-repository write of stack/commit state that was never authenticated for the target stack, matching the Critical category "a payload for one repository mutating another's stack, commit ... or an unauthorized deploy". It is repeatable for every shared SHA and can be chained to trigger `stack.schedule_merges`/continuous delivery on the victim stack via a `pending`/`success` state transition.

### Likelihood Explanation
Preconditions: the attacker must legitimately control (or trigger real GitHub status events for) at least one repository that Shipit has an app installation/webhook secret for, and that repository must share commit history/SHAs with a victim stack (fork, mirror, or repository split scenario). This is a plausible, low-cost configuration in organizations using Shipit across related repos. No secrets, sessions, or privileged Shipit roles are required beyond normal GitHub repository ownership, satisfying the "unprivileged attacker" constraint.

### Recommendation
Scope `StatusHandler#process` through `stacks` the same way `CheckSuiteHandler` does, e.g. iterate `stacks` derived from `repository_name` and only update commits belonging to those stacks (`stacks.joins(:commits).where(commits: { sha: params.sha } )` or `stacks.each { |stack| stack.commits.where(sha: params.sha).each { |c| c.create_status_from_github!(params) } }`), removing the global `Commit.where(sha:)` lookup.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerTest < ActiveSupport::TestCase
        test "#process never scopes through #stacks, unlike CheckSuiteHandler" do
          payload = {
            'repository' => { 'full_name' => 'shopify/repo-a' },
            'sha' => 'deadbeef',
            'state' => 'success'
          }
          handler = StatusHandler.new(payload)
          handler.expects(:stacks).never
          handler.process
        end

        test "cross-repository write: status for repo A mutates a commit belonging to repo B's stack sharing the same SHA" do
          stack_a = shipit_stacks(:shipit) # tracked repo A
          stack_b = shipit_stacks(:cyclimse) # different repo/stack, shares a commit sha with A
          shared_sha = 'sharedsha1234567890abcdef1234567890abcd'

          commit_a = stack_a.commits.create!(sha: shared_sha, message: 'shared', authored_at: Time.now, committed_at: Time.now)
          commit_b = stack_b.commits.create!(sha: shared_sha, message: 'shared', authored_at: Time.now, committed_at: Time.now)

          payload = {
            'repository' => { 'full_name' => stack_a.github_repo_name }, # webhook authenticated for repo A only
            'sha' => shared_sha,
            'state' => 'success'
          }

          assert_difference -> { commit_b.reload.statuses.count }, 1 do
            StatusHandler.call(payload)
          end
        end
      end
    end
  end
end
```
The first assertion demonstrates the structural claim (`StatusHandler` never calls `#stacks`) with `Mocha`'s `expects(:stacks).never`. The second demonstrates the concrete exploit: a webhook payload whose `repository.full_name` names only repo A still creates a `Status` on a `Commit` belonging to stack B, confirming the cross-repository write.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
