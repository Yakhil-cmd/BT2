This confirms the exploitable binding: `Shipit.github(organization:)` selects an entirely separate `GitHubApp` (own `webhook_secret`, `app_id`, `private_key`) per organization when the multi-org config schema is used (`config/secrets.development.example.yml:18-38`, `docs/setup.md:182-209`, `test/dummy/config/secrets_double_github_app.yml`). Signature verification is bound to whichever organization is chosen by `WebhooksController#repository_owner`, but the actual repository acted upon by handlers is chosen independently from `payload.dig('repository', 'full_name')`.## Finding: Cross-organization / cross-repository commit-status forgery in `StatusHandler` breaks the webhook-authentication ↔ repository-write binding

### Title
Webhook signature is verified against one GitHub organization's secret, but `StatusHandler` writes commit statuses without checking which repository the authenticated request belongs to - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
The analog to the SortedTroves bug (a value used for one purpose diverges from the value used for another, related purpose) exists in Shipit's webhook pipeline: the *organization whose secret authenticated the webhook* is never checked against the *repository/stack the handler actually mutates*, for the `status` event.

### Finding Description
`WebhooksController#verify_signature` picks which `GitHubApp` (and therefore which `webhook_secret`) to verify the HMAC against based on `repository_owner`, itself taken straight from the untrusted payload: [1](#0-0) [2](#0-1) 

Shipit explicitly supports configuring **multiple independent GitHub Apps/organizations on a single instance**, each with its own `webhook_secret`, `app_id` and `private_key`: [3](#0-2) [4](#0-3) 

Once `verify_signature` passes (using whichever org's secret matched the attacker-controlled `repository_owner`/`organization.login` field), the raw payload is dispatched unchanged to the event handlers: [5](#0-4) 

Most handlers scope their side effects to the repository named in the payload via `Handler#stacks` / `Repository.from_github_repo_name(repository_name)`: [6](#0-5) 

But `StatusHandler#process` does **not** use this scoping at all — it looks up commits globally by SHA, with no repository/stack filter: [7](#0-6) 

So the binding that should hold is:
`organization that authenticated the request == repository/stack whose Commit is written`

But `StatusHandler` breaks it: the write target is picked solely by matching `params.sha` against every `Commit` row in the database, independent of which organization's `webhook_secret` verified the request.

### Impact Explanation
An attacker who legitimately administers (and therefore knows the `webhook_secret` for) **one** organization/app configured on a shared Shipit instance (e.g. `OrgA` in `test/dummy/config/secrets_double_github_app.yml`) can forge a `status` webhook, sign it with `OrgA`'s secret, set `repository.owner.login`/`organization.login` to `OrgA` so `verify_signature` passes, but set `sha` to the (public) commit SHA of a stack belonging to a completely different tenant/organization (`OrgB`) tracked by the same Shipit instance. `StatusHandler` will happily attach an attacker-controlled status (`state`, `context`, `target_url`, `description`) to `OrgB`'s commit: [7](#0-6) 

Because Shipit's continuous-delivery gating and merge queue rely on commit statuses to decide whether a commit is deployable/mergeable, this is a cross-repository write that can unlock an unauthorized deploy or merge for a stack the attacker has no legitimate relationship with — meeting the "cross-repository writes / unauthorized deploy or merge" Critical-impact bar.

Note: this is specific to `StatusHandler`. Other multi-tenant-sensitive handlers correctly scope by `repository_name`/`stacks`, e.g. `CheckSuiteHandler`: [8](#0-7) 

### Likelihood Explanation
Requires the Shipit deployment to use the multi-organization GitHub App configuration (explicitly documented and supported) and requires the attacker to control/administer at least one of the configured organizations (able to see its `webhook_secret`), plus knowledge of a target commit SHA in another tenant's tracked repository (trivially obtainable if that repository is public, or via any prior interaction). This is a realistic scenario for any Shipit-as-a-service deployment serving multiple orgs, hence Likelihood is assessed as Medium given the specific multi-org precondition, but the discovered root cause is concrete and directly exploitable once that precondition holds.

### Recommendation
`StatusHandler#process` (and any other handler that does not scope through `Handler#stacks`) must bind the authenticated organization/app to the repository being mutated: either (a) restrict the `Commit.where(sha: params.sha)` lookup to commits belonging to stacks whose `Repository#owner` matches the organization that authenticated the signature, or (b) require and validate a `repository.full_name` in the `status` payload and use the existing `stacks` scoping helper instead of a bare, cross-tenant SHA lookup.

### Proof of Concept
1. Deploy Shipit with the documented multi-org config (`OrgA`, `OrgB`), each with distinct `webhook_secret`s, tracking stacks for `OrgA/repoA` and `OrgB/repoB` respectively.
2. As an attacker who controls `OrgA`'s GitHub App installation (and thus knows `OrgA`'s `webhook_secret`), craft a JSON body:
```json
{
  "sha": "<known commit sha tracked under OrgB/repoB>",
  "state": "success",
  "context": "ci/forged",
  "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgA/repoA"}
}
```
3. Compute `X-Hub-Signature: sha1=<hmac(OrgA_webhook_secret, body)>` and POST it to `/github/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "OrgA")` and verifies successfully.
5. `StatusHandler#process` executes `Commit.where(sha: params.sha)` and creates the forged status on the `OrgB/repoB` commit, even though only `OrgA`'s secret authenticated the request.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
