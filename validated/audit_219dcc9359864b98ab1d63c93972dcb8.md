### Title
Missing mutex serialization when saving private (divisible/indivisible) asset payment chains allows a double-spend race condition - (File: `private_payment.js`)

### Summary
`private_payment.js`'s `validateAndSavePrivatePaymentChain` (and its callers) validates and writes private-payment chains to `outputs`/`inputs` using only a per-connection SQL `BEGIN`/`COMMIT` transaction, with no global mutex serialization. Every other path in ocore that mutates unit/asset state (`network.js` `handleJoint`, `composer.js`/`divisible_asset.js`/`indivisible_asset.js` `getSavingCallbacks`, `writer.js` `saveJoint`) explicitly takes the `handleJoint` or `write` mutex before validating+writing. This is analogous to CVE-2024-35990 (xilinx_dpdma): several code paths that mutate shared state omit the locking that parallel sibling paths rely on, opening a window for concurrent, conflicting writes.

### Finding Description
`validateAndSavePrivatePaymentChain` in `private_payment.js` (lines 23–119) is invoked to validate and persist a private payment chain (a chain of hidden outputs/inputs shared only between the payer, payee, and cosigners). It:
1. Takes a fresh DB connection from the pool and issues `BEGIN`.
2. Performs a `SELECT` to check whether the output has already been recorded (duplicate check).
3. If not a duplicate, delegates to `indivisible_asset.js`/`divisible_asset.js` `validateAndSavePrivatePaymentChain`, which issues `INSERT`/`UPDATE` statements against `inputs`/`outputs` (including `is_unique`, `is_spent` flags) and then `COMMIT`s. [1](#0-0) [2](#0-1) 

Crucially, none of this sequence acquires `mutex.lock(['handleJoint'])`, `mutex.lock(['write'])`, or `mutex.lock(['private_write'])` — the locks that every other "validate-then-write" flow in the codebase relies on:
- `network.js` `handleJoint` wraps `validation.validate` + `writer.saveJoint` in `mutex.lock(['handleJoint'], ...)`. [3](#0-2) 
- `composer.js`/`divisible_asset.js`/`indivisible_asset.js` `getSavingCallbacks` explicitly take `mutex.lock('handleJoint')` before calling `validation.validate` and `writer.saveJoint`. [4](#0-3) [5](#0-4) 
- Even the double-spend "ununique" fix-up for private assets inside `validation.js` explicitly serializes via `mutex.lock(["private_write"], ...)` before mutating `inputs.is_unique`. [6](#0-5) 

`private_payment.js`'s save path is the odd one out: it is reachable directly from the network layer when receiving private payments, and — critically — its caller in `network.js`, `handleSavedPrivatePayments`, explicitly processes multiple pending private chains **in parallel** via `async.each` with the comment "handle different chains in parallel": [7](#0-6) 

Because each parallel invocation opens its own pooled DB connection and its own `BEGIN`/`COMMIT` transaction, two private-payment chains that reference the same source output (e.g., an attacker submitting two conflicting private elements chains spending the same hidden output to two different addresses, via two peers or twice via the same peer with different message content) can each run their duplicate/spend-proof checks and inserts concurrently before either commits. The `SELECT`-then-`INSERT`/`UPDATE` duplicate check in `private_payment.js` (lines 62–103) is not atomic with respect to a second, concurrently-running transaction on a different connection, since neither transaction can see the other's uncommitted writes. [8](#0-7) 

### Impact Explanation
If two conflicting private chains spending the same private-asset output are processed concurrently, both transactions can pass their "already exists"/duplicate checks (each is blind to the other's in-flight, uncommitted write) and both can successfully `INSERT` competing `inputs` rows and `UPDATE` the same `outputs` row's `is_spent`/`is_unique` state. This produces two independently-recorded valid-looking spends of the same private-asset output — i.e., a double-spend of a private asset that is not caught by ocore's normal double-spend serialization (`private_write` mutex in `validation.js`) because that code path is never entered for privately-delivered chains. This is a concrete unauthorized-spending / double-spend outcome reachable by a private-payment counterparty (the class explicitly listed as in-scope in the rules).

### Likelihood Explanation
Reaching this requires only a peer capable of sending two private-payment messages that reference the same source output to the victim node within a short window (`handleOnlinePrivatePayment` → `unhandled_private_payments` → periodic `handleSavedPrivatePayments` sweep, which explicitly fans work out in parallel). No privileged access, hub cooperation, or node compromise is required — an ordinary wallet/counterparty in a private-asset transaction can trigger it by crafting two private elements referencing the same output and delivering them through two connections (or having them queued together so the periodic sweep processes them in the same batch).

### Recommendation
Serialize saving of private payment chains the same way every other unit-writing path is serialized: wrap `validateAndSavePrivatePaymentChain` in `private_payment.js` with `mutex.lock(['handleJoint'])` (or a dedicated `private_write`/`private_chain-<unit>-<message_index>-<output_index>` lock key) before the duplicate check and the subsequent DB transaction, mirroring the pattern already used in `composer.js`, `divisible_asset.js`, `indivisible_asset.js`, and `network.js`'s `handleJoint`. Alternatively, key the lock on `[unit, message_index, output_index]` (or the referenced `src_unit`/`src_message_index`/`src_output_index`) to prevent two chains that spend the same output from running the check-then-write sequence concurrently.

### Proof of Concept
1. Craft a private asset payment (asset with `is_private=1`) referencing a specific source output `(src_unit, src_message_index, src_output_index)`.
2. Build two distinct private-element chains, `chainA` and `chainB`, each spending that same source output to a different recipient address, each internally consistent (matching output hash / spend proof for its own claimed path).
3. Deliver `chainA` and `chainB` to the victim node in quick succession (e.g., via `private_payment` network messages from two connections, or queued into `unhandled_private_payments` before a `handleSavedPrivatePayments` sweep) so that `network.js`'s `async.each`-based parallel processing (lines 2444–2461) picks both up in the same batch.
4. Each chain's `validateAndSavePrivatePaymentChain` call opens its own DB connection/transaction; because neither transaction commits before the other's duplicate `SELECT` runs, both duplicate checks pass and both `INSERT`/`UPDATE` sequences against `inputs`/`outputs` succeed.
5. Inspect the `inputs`/`outputs` tables: the same source output now backs two "unique" spends recorded as valid, demonstrating a double-spend of the private asset that the normal `private_write`-mutex-guarded double-spend logic in `validation.js` never had a chance to catch.
