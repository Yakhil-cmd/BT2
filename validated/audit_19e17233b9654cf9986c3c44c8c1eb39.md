## Analysis: Unstable/manipulable oracle-AA data feed short-circuit in `data_feed[[]]` — analog to Sturdy price-manipulation

The Sturdy exploit relied on a lending protocol pricing collateral off a manipulable, not-yet-finalized on-chain price source (an AMM pool) within the same atomic operation as the exploit, before the manipulation could be corrected. Ocore has a structurally analogous path: when a formula's `data_feed[[...]]` operator is evaluated **inside an AA** (`bAA === true`), it is allowed to short-circuit on a *single unstable* data-feed post authored by another AA, bypassing the persisted/stable value entirely.

### Root cause

`formula/evaluation.js`'s `data_feed` case passes the AA context flag `bAA` straight through as the `unstable_opts` argument to `dataFeeds.readDataFeedValue`: [1](#0-0) 

In `data_feeds.js`, `readDataFeedValue` treats any truthy `unstable_opts` as "include unstable AA-authored data feed posts", scanning `storage.assocUnstableMessages` for messages authored by AA addresses (`objUnit.bAA`) that are within `[min_mci, max_mci]`: [2](#0-1) 

Critically, if exactly one such unstable candidate is found and `ifseveral === 'last'` (the default), the function **returns immediately with that unstable value**, without ever consulting the persisted/stable data-feed store: [3](#0-2) 

This is not the general-purpose behavior — outside of AA execution (e.g. address-definition `in data feed` authentifiers) `bAA` is explicitly `false`, disabling unstable inclusion: [4](#0-3) 

So the vulnerable behavior is specific to AA-to-AA composition, exactly the pattern used for price-oracle AAs (e.g. AMM/curve-style price AAs, as seen in the test fixtures using `data_feed[[oracles=..., feed_name='GBYTE_USD_MA']]`): [5](#0-4) 

### Attack scenario (analog of Sturdy)

1. A victim DeFi-style AA ("Lending/AMM AA") is written to price collateral or swaps by reading `data_feed[[oracles="<PriceOracleAA_address>", feed_name="PRICE"]]`, where `PriceOracleAA` is itself an AA that computes/posts a price (e.g. derived from pool reserves), analogous to Sturdy trusting a Balancer pool.
2. An attacker triggers `PriceOracleAA` in a way that transiently skews its computed price (e.g. via a large one-sided trade against the pool, exactly like the Balancer-pool manipulation in the real Sturdy hack), causing it to post a manipulated `data_feed` value. This response unit is only *unstable* at this point — not yet finalized.
3. In the same unstable window, the attacker triggers the victim AA (directly, or chains it as a secondary trigger). The victim's `data_feed[[...]]` read hits the `bIncludeUnstableAAs` branch in `readDataFeedValue`, finds the single manipulated unstable candidate from `PriceOracleAA`, and returns it immediately — bypassing whatever correct/stable price was previously recorded.
4. The victim AA computes and sends an output (loan disbursement, collateral release, swap payout) based on the manipulated, not-yet-final price. Once that response unit's payment is posted, it is effectively an irreversible fund movement, even though the price data that justified it was never durably confirmed.

### Impact

This lets an attacker who can influence an AA-based price/oracle contract's transient (unstable) state extract disproportionate value from any consumer AA that reads that oracle via `data_feed[[]]`, mirroring the *price manipulation → fund loss* pattern in the Sturdy incident. Because the short-circuit happens on data that is explicitly unstable, it also means the victim AA's fund-affecting decision is based on state that is not yet guaranteed final by consensus, i.e., AA fund loss driven by an oracle price that had not achieved stability.

### Recommendation
`readDataFeedValue`'s unstable/AA short-circuit path (`data_feeds.js` lines 211-273) should not allow a single unstable AA-authored data feed post to fully override/bypass the stable, persisted value; at minimum, price-oracle consuming AAs need a formula-level option to demand only stable (`is_stable=1`) data feed values, and the "single-candidate short-circuit" optimization should not skip checking whether a more authoritative stable value exists for the same oracle/feed_name. [6](#0-5)
