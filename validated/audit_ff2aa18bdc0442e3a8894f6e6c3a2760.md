### Title
Attacker-controlled repository content can cause `git-sync` to exceed `--sync-timeout` repeatedly and permanently abort via `--max-failures`, resulting in persistent sync denial - (File: main.go)

### Summary
`git-sync` fetches and checks out arbitrary content pushed by a remote git repository owner/committer. Because the sync loop bounds each attempt with `--sync-timeout` and aborts the whole process after `--max-failures` consecutive failures, a party who can push oversized or pathologically-structured commits/history to the tracked repo (an untrusted content source, analogous to the "attacker deposits to hit the mint limit" pattern in the PoolTogether report) can force every sync attempt to exceed the timeout, driving `failCount` past `--max-failures` and causing `git-sync` to call `os.Exit(1)`, permanently halting synchronization until an operator manually restarts the sidecar.

### Finding Description
The main sync loop wraps every call to `SyncRepo` in a context bounded by `*flSyncTimeout`, and tracks consecutive failures against `*flMaxFailures`: [1](#0-0) 

If a sync attempt does not complete within the timeout (e.g., `git fetch`/`git worktree add`/checkout of an unusually large tree, deeply nested history, or huge blobs added upstream), `SyncRepo` returns an error, `failCount` increments, and once `failCount >= maxFailures`, the process exits entirely rather than retrying indefinitely: [2](#0-1) 

This mirrors the mint-limit DoS pattern in the report: a bound/limit check (`--sync-timeout` per attempt, `--max-failures` cumulative) that is meant to protect against transient conditions can instead be deliberately and repeatedly triggered by content the attacker controls (commits/refs pushed to the synced repository), turning a protective limit into a permanent denial-of-service vector. Once `os.Exit(1)` fires, the git-sync sidecar stops entirely — it does not just skip one cycle — so the consumer container is left serving stale data indefinitely (or, on `--one-time` init, never publishes at all) until an external supervisor (e.g., Kubernetes) restarts the pod and the same attacker-authored history triggers the same timeout/failure sequence again, forming a persistent restart loop.

### Impact Explanation
This qualifies under "persistent sync denial": legitimate consumers of the shared volume never receive updates because git-sync itself terminates rather than degrading gracefully. In a Kubernetes sidecar deployment this manifests as CrashLoopBackOff for the pod, since a restarted `git-sync` will re-attempt the same fetch/checkout of the attacker-authored ref and hit the same timeout again if the underlying content problem (huge blob, huge tree, pathological history) is not resolved.

### Likelihood Explanation
Requires that the tracked `--ref` (branch/tag/HEAD) be updated by an untrusted party with push access to the repository being synced (i.e., an attacker-pushed commit as described in scope), and that the pushed content is large/expensive enough to exceed `--sync-timeout` (default 120s) consistently across `--max-failures` attempts (or indefinitely if `--max-failures` is unset/negative, meaning retries continue forever but the sidecar is still perpetually non-functional). No credentials, malicious operator, or leaked keys are needed — only push access to content that is fetched, matching the "untrusted repo content" reachability requirement.

### Recommendation
- Consider decoupling "the fetch of new content took too long" from "operator intervention needed": e.g., after repeated timeouts on a specific ref/hash, keep serving the last-known-good symlink target instead of exiting the whole process, and only alert/exit if this is the very first sync (steady-state failures should not be fatal for a sidecar with content already published).
- Bound the cost of processing untrusted history more aggressively by default (e.g., always honor `--depth`/`--filter` for automatic ref-tracking regardless of prior manual full clones) so a single malicious push cannot make every future sync heavier.
- Emit metrics distinguishing timeout-based failures from other errors so operators can detect this DoS pattern quickly.

### Proof of Concept
1. Deploy `git-sync` tracking `--ref=main` on a repository where an untrusted collaborator (or CI bot with push rights) can commit.
2. Attacker pushes a commit introducing an extremely large blob/tree (or many nested submodules that must each be cloned) sized so that `git fetch` + `git worktree add`/checkout for that commit exceeds `--sync-timeout` (e.g., default 120s) under the sidecar's resource limits.
3. Each sync loop iteration in `main.go` (lines 1052-1063) times out, incrementing `failCount`.
4. Once `failCount >= *flMaxFailures`, `main.go:1059-1062` calls `os.Exit(1)`, terminating the sidecar.
5. Because the ref (`main`) still points at the oversized commit, any restart of the container repeats steps 3-4, producing a persistent inability to sync and — if it's the initial sync — the symlink/consumer contract is never published at all.
