### Title
Cross-Tenant CI Status Forgery via Unscoped Commit Lookup in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::WebhooksController#verify_signature` authenticates a webhook by selecting a GitHub App configuration keyed on the attacker-controlled `repository.owner.login` (or `organization.login`) field of the JSON body, and verifies the HMAC signature against that organization's `webhook_secret`. Once the signature is verified, the raw payload is handed to `Shipit::Webhooks::Handlers::StatusHandler#process`, which resolves the target `Commit` **solely by `sha`**, with no re-check that the commit actually belongs to a stack whose repository/organization matches the organization whose secret produced the valid signature. This breaks the trust binding `organization authenticated == repository/stack written`, mirroring the reported bug class (a value trusted for authorization is never actually verified for the resource being mutated).

### Finding Description
`app/controllers/shipit/webhooks_controller.rb` picks the verification key like this: [1](#0-0) [2](#0-1) 

The organization used to select the GitHub App config (and therefore the `webhook_secret` used in `verify_webhook_signature`) comes straight out of the unverified JSON body (`params.dig('repository','owner','login')` / `params.dig('organization','login')`). This scheme exists explicitly to support "Using Multiple GitHub Applications", where each tenant organization has its own app/secret, per `docs/setup.md`.

After the signature check passes (proving only that *some* configured org's secret signed this exact byte stream), the raw payload is dispatched to the registered handler: [3](#0-2) 

For the `status` event, `StatusHandler#process` looks up commits **by SHA only**, with no scoping to the repository/organization that produced the signature: [4](#0-3) 

Unlike other handlers such as `PushHandler`, which at least scope lookups through `Repository.from_github_repo_name(repository_name)` (base `Handler#stacks`), `StatusHandler` bypasses that scoping entirely and matches any `Commit` row in the database with the given `sha`, across all stacks/tenants: [5](#0-4) 

The created status directly mutates deploy-readiness state: `Status#after_create` calls `enable_ci_on_stack` and `schedule_continuous_delivery`: [6](#0-5) [7](#0-6) 

**The equality that is broken:** `Shipit.github(organization: repository_owner)` (the org whose secret authenticated the request) is treated as if it equals the stack/repository that the handler actually writes to, but nothing in `StatusHandler` (or `Handler#stacks`) enforces that equality — the commit is matched globally by `sha`.

### Impact Explanation
In a multi-tenant Shipit deployment (the documented "Using Multiple GitHub Applications" configuration), each tenant organization's own GitHub App administrators legitimately know their own organization's `webhook_secret` (they configure it themselves in their GitHub App settings) but have no privilege over any other tenant's stacks and no Shipit session/API token. Such an unprivileged-relative-to-other-tenants attacker can:
1. Sign an arbitrary JSON payload with their own org's `webhook_secret` (valid signature).
2. Set `repository.owner.login` to their own org (so the correct/known secret is selected and verification passes).
3. Set the `sha` field to a commit SHA belonging to a *different* tenant's stack (SHAs are often predictable/public, e.g. visible on GitHub or in the target's own public commit history) and `state: "success"` with a matching `context`.

This injects a forged CI success status onto a commit in a completely unrelated stack/organization, which can satisfy `ci.require` checks and unblock `commit.deployable?`, enabling an **unauthorized deploy** on a repository the attacker does not control. This aligns with the "unauthorized deploy" and "cross-repository writes" Critical-impact buckets in scope.

### Likelihood Explanation
Likelihood is moderate-to-high in any deployment using the documented multi-org configuration: no Shipit account, API token, or GitHub write access to the victim repository is required — only knowledge of a valid `webhook_secret` for *any one* onboarded organization (which that organization's own admins possess by design) and a target commit SHA (often discoverable via public GitHub history, PRs, or CI logs). The `status` webhook endpoint is unauthenticated apart from the HMAC check, and `StatusHandler` performs no additional authorization.

### Recommendation
Scope `StatusHandler` (and any other handler using global lookups) to the repository/organization that was actually authenticated for the request, e.g., by requiring `repository.full_name` in the handler params and filtering `Commit.where(sha: params.sha)` through `Repository.from_github_repo_name(params.repository.full_name)&.stacks` (mirroring the base `Handler#stacks` helper), and additionally verifying that the resolved repository's configured organization matches the organization whose secret validated the signature in `WebhooksController#verify_signature`.

### Proof of Concept
1. Deploy Shipit configured with multiple GitHub App orgs, e.g. `orgA` and `orgB`, each with `stacks` tracking their own repositories (`config/secrets.yml` per `docs/setup.md` "Using Multiple Github Applications").
2. As the administrator of `orgA`'s own GitHub App, obtain `orgA`'s `webhook_secret` (self-known, not privileged relative to `orgB`).
3. Identify a commit `sha` in a stack belonging to `orgB` (e.g., from a public PR or commit page) requiring CI status `context: "ci/required"`.
4. Craft payload:
```json
{
  "sha": "<orgB-target-sha>",
  "state": "success",
  "context": "ci/required",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgA/some-repo" }
}
```
5. Compute `X-Hub-Signature: sha1=<hmac-sha1(orgA_webhook_secret, raw_body)>` and POST to `/webhooks` with `X-Github-Event: status`.
6. `WebhooksController#verify_signature` selects `orgA`'s app via `repository_owner` ("orgA") and validates the signature successfully.
7. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, matches the `orgB` commit (no repository scoping), and calls `commit.create_status_from_github!(params)`, creating a `success` status on `orgB`'s stack — potentially satisfying its `ci.require` and enabling deploy, without any credential or access to `orgB`.
