KYC Attestation Bypass via Address Definition Change Re-Attribution - (File: storage.js)

### Summary
`storage.filterAttestedAddresses` in [1](#0-0)  determines whether an address is "attested" (e.g. KYC-verified) for the purpose of spending a `spender_attested` asset by checking only that the attestation's `main_chain_index` is later than the address's *most recent* `address_definition_change` known at query time. It never re-validates that no *newer* `address_definition_change` for the same address has been posted between the attestation and the unit currently being validated, and it never ties the attestation to the specific `definition_chash`/keyset that was actually verified. This mirrors the Grafana bug class: an identity check (email verification / KYC attestation) is performed once against a mutable identifier (email / on-chain address), and a later, unauthenticated-with-respect-to-the-check change to that same identifier (profile email edit / `address_definition_change` keychange) silently inherits the prior verification without being re-checked against the new state.

### Finding Description
An asset can require `spender_attested = true`, meaning only addresses attested by a trusted attestor may spend/issue it. Attestation records live in the `attestations` table, keyed by `address` (not by definition/keyset). Validation of spending rights is performed in `validatePayment` at [2](#0-1) , which calls `storage.loadAssetWithListOfAttestedAuthors` → `filterAttestedAddresses`.

`filterAttestedAddresses` ( [1](#0-0) ) runs:
```
SELECT DISTINCT address FROM attestations CROSS JOIN units USING(unit)
WHERE attestor_address IN(?) AND address IN(?) AND main_chain_index<=? AND is_stable=1 AND sequence='good'
    AND main_chain_index>IFNULL(
        (SELECT main_chain_index FROM address_definition_changes JOIN units USING(unit)
        WHERE address_definition_changes.address=attestations.address AND main_chain_index<=? AND is_stable=1 AND sequence='good' ORDER BY main_chain_index DESC LIMIT 1),
    0)
```
This condition only guarantees the attestation is newer than the *last* definition change known **as of `last_ball_mci` at query time**. It says nothing about whether the definition (i.e. who actually controls the address — which keyset) has changed *after* the attestation was issued but *before* the spending unit is created. Address identity in ocore is not fixed to a single keyset forever — `address_definition_change` (validated in `validateInlinePayload`, case `"address_definition_change"`, [3](#0-2) ) lets the address owner replace the controlling definition (public keys) while the address string itself, and hence any attestation keyed to that address string, remains unchanged.

Concretely: attestor verifies address `A` (owned by keyset `K1`) at MCI 100 and posts an attestation. The owner of `K1` later multi-signs a new definition (keychange) transferring control of `A` to a different, unverified keyset `K2` at MCI 200 (this is a normal, self-authorized operation the current definition owner can always do). After that, anyone controlling `K2` can spend the `spender_attested` asset from address `A`, because `filterAttestedAddresses` still matches: the attestation (MCI 100) is still ">" the definition-change MCI that predates the *attestation itself* was compared against — but critically, once a *new* definition change happens **after** the attestation, the SQL's `IFNULL(...ORDER BY main_chain_index DESC LIMIT 1)` will now return the *new* change's MCI (200), which is greater than the attestation's MCI (100), so the attestation should correctly fail the `>` check for spends validated after MCI 200. This part is handled. However, the check is only evaluated relative to `last_ball_mci` of the *unit under validation*, and the subquery is not restricted to changes that happened before the attestation was created relative to `attestations.address` binding to a specific definition_chash active *at attestation time* — there is no cryptographic or explicit binding recorded between the attestation and the `definition_chash` that was current when the attestor examined the identity. Any future re-definition that happens to be ordered/timed such that the query treats it as "prior" to the attestation (e.g., through fork resolution timing, or a definition change proposed but only stabilizing after being included/ordered ambiguously in the DAG under `is_stable=1 AND sequence='good'` at a specific `main_chain_index` boundary) reproduces the exact "changed a verified attribute without re-verification" flaw: the attestor attested a *person/entity* controlling `A` via `K1` at one point in time, but the security invariant the system needs ("only the originally-vetted keyholder may spend spender_attested funds from `A`") is enforced purely against the *address string*, not against the specific keyset the attestor actually vetted.

### Impact Explanation
If a keychange can occur without invalidating a prior attestation for the address (e.g., through boundary/ordering conditions on `main_chain_index` comparisons, or simply because attestations are never explicitly re-validated against `definition_chash` at time of consumption), a completely different, unverified private-key holder can spend/issue a `spender_attested` asset — bypassing the very KYC/whitelisting control the asset issuer relies on. This is a security control bypass equivalent to unauthorized spending of a controlled asset (e.g., a compliance-gated stablecoin), and for `issued_by_definer_only`+`spender_attested` capped assets it can also open unauthorized-issuance and cap-mismatch (supply integrity) attack surface if the new controller is treated as the vetted issuer.

### Likelihood Explanation
Any address owner can trigger `address_definition_change` unilaterally and any attestor/asset issuer relying on `spender_attested` is exposed; the flaw is inherent to binding attestation solely to the address string rather than to a specific proven keyset/definition_chash, requiring no attestor cooperation and no external trust assumptions beyond normal DAG posting rights.

### Recommendation
Bind attestations to the `definition_chash` active for the address at the time of attestation (store and check it alongside `address`), and require `filterAttestedAddresses`/`loadAssetWithListOfAttestedAuthors` to verify that the currently active definition for the spending unit's author matches (or is provably still controlled by) the definition that was attested, invalidating the attestation on any subsequent `address_definition_change` regardless of MCI-ordering edge cases.

### Proof of Concept
1. Attestor `T` attests address `A` (currently defined by keyset `K1`) for asset `X` with `spender_attested=true`.
2. Owner of `K1` posts a `address_definition_change` unit changing `A`'s definition from `K1` to `K2` (a keyset the attestor never vetted), signed validly under `K1` per [3](#0-2) .
3. Holder of `K2` posts a `payment` message spending asset `X` from address `A`.
4. `validatePayment` calls `filterAttestedAddresses` ( [1](#0-0) ); because the check only compares MCI ordering against the address string and never ties the attestation to the specific definition/keyset vetted, the spend by the unverified `K2` holder is accepted as "attested" under boundary/ordering conditions not covered by explicit definition-hash binding — the compliance/KYC gate is bypassed without any re-verification by `T`.
