### Title
Silent self-issuance of uncapped assets when an AA's UTXO balance falls short of a computed payment amount, causing unbacked supply inflation - (File: aa_composer.js)

### Summary
When an Autonomous Agent (AA) response tries to send a payment for an asset amount computed from formula-level state (e.g. `balance[$asset]`, ratio calculations, or accumulated state vars), `aa_composer.js` builds the payment by collecting actual unspent UTXOs belonging to the AA. If those UTXOs don't cover the required `target_amount`, instead of always bouncing the trigger (rolling back state), the composer falls back to silently minting new units of the asset via `issueAsset()` when the asset is uncapped and either not restricted to definer-only issuance or the AA itself is the definer. This mirrors the PoolTogether `PrizeVault` root cause: a mismatch between an internally-computed “amount owed” and the actually-available backing funds is resolved by a code path that doesn't fail loudly, but instead produces an inconsistent/incorrect result (there: silent failed transfer; here: silent unbacked mint).

### Finding Description
In `sendUnit()` → `completePaymentPayload()` (`aa_composer.js`), the composer first tries to fund a payment output using the AA's real UTXOs: [1](#0-0) 

`readStableOutputs` and `readUnstableOutputsSentByAAs` only return outputs that are either stable or unstable-but-authored-by-another-AA: [2](#0-1) 

Ordinary (non-AA) senders' unstable outputs, and dust below `FULL_TRANSFER_INPUT_SIZE`, are excluded from this UTXO pool. If, after exhausting both queries, `bFound` is still false, the code does **not** simply bounce — for a non-base asset it attempts `issueAsset()`: [3](#0-2) 

```
var issue_amount = objAsset.cap || (target_amount - total_amount);
```

Only if `issueAsset()` itself errors (`issued_by_definer_only && address !== objAsset.definer_address`) does the trigger bounce: [4](#0-3) 

For any asset that is uncapped (`cap` unset) and not restricted to `issued_by_definer_only`, or where the AA itself is the asset's definer, this fallback silently issues brand-new, unbacked units of the asset equal to the shortfall (`target_amount - total_amount`) rather than reverting the trigger. Many production AA patterns compute payout amounts purely from oscript-level accounting (`balance[$asset]`, ratio/AMM formulas, state-var counters such as `var['mm_asset_outstanding']`) as shown in the shipped samples: [5](#0-4) 

These formulas assume `balance[$asset]` accurately reflects what the AA can actually pay out. But the UTXO set actually usable by `completePaymentPayload` (stable + AA-sent-unstable only) can diverge from the AA's nominal internal balance — e.g. right after receiving funds from a non-AA sender that haven't stabilized yet, or due to dust-filtering, or due to concurrent pending AA responses spending the same balance. When that divergence causes a shortfall, the composer's fallback is asset self-issuance instead of a bounce, permanently inflating the total supply of the asset by units that have no economic backing.

This directly parallels the external report's root cause: an internal accounting value (`previewWithdraw`/shares math in Solidity; `balance[$asset]`/formula math in oscript) is trusted to match the actually redeemable/spendable funds, and when it doesn't, the code takes a "recovery" branch (`transfer` returning `false` silently; `issueAsset` minting silently) rather than failing atomically.

### Impact Explanation
Unlike the Solidity case (locked user funds), the ocore analog results in supply inflation: an AA can end up minting new units of a divisible, uncapped asset that are not backed by any deposited value, diluting all existing holders of that asset. Because the mint happens inside the same atomic AA-response unit, it is committed together with any state changes, and once done cannot be undone — there is no separate "revert" step, so the unbacked coins permanently enter circulation. This qualifies as Medium/High severity per the "supply inflation" acceptance criterion.

### Likelihood Explanation
Reachable by any unprivileged unit poster who triggers an AA: no special privileges are required, only sending a trigger unit to an AA whose oscript computes a payout for an uncapped, non-definer-restricted asset (or an asset the AA itself defined) from formula-level balance/state accounting rather than from a guaranteed exact UTXO match. Many published AA patterns in this repo (`uniswap_like_market_maker.oscript`, ICO/milestone samples, asset-issuing chains) follow exactly this pattern of computing payout amounts from `balance[asset]`/state vars, making the precondition realistic. Triggering the actual divergence requires timing (e.g. racing unstable inputs, or spending against not-yet-stable received funds) or an oscript author's rounding/accounting bug, which is a plausible but not guaranteed occurrence — hence Medium likelihood.

### Recommendation
- In `completePaymentPayload`, do not fall back to `issueAsset()` silently to cover shortfalls that stem from a mismatch between intended payout and actually spendable UTXOs; instead, bounce the trigger whenever the requested `target_amount` for a non-issuance payment message exceeds the AA's verified real balance, regardless of whether the asset is capped/definer-restricted.
- If self-issuance-on-shortfall is an intentional design feature (e.g. to support "issue on demand" asset AAs), gate it behind an explicit oscript declaration/opt-in rather than making it the default recovery path for any ordinary payment message whose funding UTXOs are insufficient.
- Ensure `balance[$asset]` (and any similarly exposed formula built-ins) are documented and, ideally, guaranteed to equal exactly the set of UTXOs that `completePaymentPayload` will use (stable + AA-authored-unstable), so oscript authors cannot unintentionally compute payouts the composer cannot literally back — closing the semantic gap that enables the silent-mint fallback.

### Proof of Concept
Conceptual PoC (could not be fully executed/verified within this investigation due to the complexity of setting up AA state/UTXO timing in ocore's test harness; flagged as an area requiring further validation by a live Devin session with test execution):
1. Deploy an AA whose oscript defines an asset with `cap` unset, `issued_by_definer_only: false` (or `true` with the AA as definer), and a case that pays out an amount derived from `balance[$asset]` or an internal counter (e.g., the `uniswap_like_market_maker.oscript` divest logic at [6](#0-5)  which computes `round($investor_share * balance[$asset])`).
2. Send the AA a trigger from an address whose earlier payment output to the AA is still unstable (non-AA sender), so that `readStableOutputs`/`readUnstableOutputsSentByAAs` in [2](#0-1)  cannot pick it up as spendable, even though the formula-level `balance[$asset]` counts it.
3. Trigger the divest/withdraw case; `completePaymentPayload` finds insufficient real UTXOs (`bFound` false) and falls through to `issueAsset()` at [4](#0-3) , minting `target_amount - total_amount` new units of the asset instead of bouncing.
4. Verify (via `test/aa_composer.test.js`-style harness, e.g. the pattern used in `dryRunPrimaryAATrigger` tests at [7](#0-6) ) that the resulting response unit contains a `type: "issue"` input for the asset and that total outstanding supply now exceeds what was ever deposited.

			function issueAsset(cb2) {
				var objAsset = assetInfos[asset];
				if (objAsset.issued_by_definer_only && address !== objAsset.definer_address)
					return cb2("not a definer");
				var issue_amount = objAsset.cap || (target_amount - total_amount);

				function addIssueInput(serial_number){
					var input = {
						type: "issue",
						amount: issue_amount,
						serial_number: serial_number
					};
					payload.inputs.unshift(input);
					total_amount += issue_amount;
					var change_amount = total_amount - target_amount;
					if (change_amount > 0)
						payload.outputs.push({ address: address, amount: change_amount });
					cb2();
				}
				
				if (objAsset.cap) { // only our AA can issue, no unstable consensus-breaking issues possible
					conn.query("SELECT 1 FROM inputs WHERE type='issue' AND asset=?", [asset], function(rows){
						if (rows.length > 0) // already issued
							return cb2('already issued');
						addIssueInput(1);
					});
				}
				else{
					conn.query( // filtered by our AA's address, all equally visible on all nodes
						"SELECT MAX(serial_number) AS max_serial_number FROM inputs WHERE type='issue' AND asset=? AND address=?",
						[asset, address],
						function(rows){
							var max_serial_number = (rows.length === 0) ? 0 : rows[0].max_serial_number;
							addIssueInput(max_serial_number+1);
						}
					);
				}
			}
