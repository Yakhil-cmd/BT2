### Title
AA can irrevocably act on a data-feed value from a unit that is only tentatively "good" and can later flip to `final-bad` at stabilization - ([File: data_feeds.js])

### Summary
The Sherlock report describes a two-step oracle resolution (UMA report → negRiskAdapterOperator confirmation) where the borrower-lending protocol treats the first, provisional step as final and lets the lender seize collateral before the second, authoritative step (the one that can actually reverse the outcome) has completed. The root cause is checking an intermediate/tentative state instead of the truly final one before allowing an irreversible action.

Obyte's own oscript/AA data-feed mechanism has the same structural weakness: `dataFeeds.readDataFeedValue()` lets an AA formula (`data_feed[[...]]`, `in_data_feed[[...]]`) read a data-feed value from a unit whose `sequence` is currently `'good'` but which is **not yet stable**. The unit's final validity (`good` vs `final-bad`) is only definitively decided at DAG stabilization time in `main_chain.js`'s `markMcIndexStable()`/`handleNonserialUnits()`, which can still flip a currently-`good` unit to `final-bad` if a conflicting/double-spending unit is discovered before stabilization completes.

### Finding Description
`readDataFeedValue()` in [1](#0-0)  supports an `unstable_opts` mode where, instead of waiting for a stable, DB-committed data feed, it scans `storage.assocUnstableMessages` for `data_feed` messages posted by units that are merely `sequence === 'good'` at the moment of the read:

```
if (objUnit.sequence !== 'good')
    continue;
```

This "good" status is provisional. The true, final classification of a unit's sequence (`good` vs `temp-bad` vs `final-bad`) is only settled during main-chain stabilization in `main_chain.js`, where `handleNonserialUnits()` explicitly re-evaluates sequence based on conflicting units discovered at stabilization time: [2](#0-1) 

Only once a unit is stabilized as `final-bad` are its unstable data-feed payloads discarded rather than committed: [3](#0-2) 

This mirrors the reported bug class exactly: the "good" sequence at read time is the analog of the UMA oracle's initial report, and the stabilization-time re-evaluation (which can still produce `final-bad`) is the analog of the negRiskAdapterOperator's later, authoritative override. The oscript formula layer (`data_feed`/`in_data_feed` in `formula/evaluation.js`) passes `bAA` through to `readDataFeedValue`/`dataFeedExists` as the `unstable_opts` flag, so an AA trigger evaluated while the network processes new units can consume a data-feed value from a unit that has not yet passed its final serial-conflict check: [4](#0-3) [5](#0-4) 

If the AA immediately sends payments (e.g., pays out collateral, resolves a bet, unlocks funds) based on that value, and the underlying data-feed-posting unit is later determined `final-bad` at stabilization (its content voided per `light.js` `processHistory`'s handling of `assocProvenUnitsNonserialness` and `archiving.generateQueriesToArchiveJoint(..., 'voided', ...)`) [6](#0-5) , the AA's response is already sent, its payment is already made, and the response cannot be retroactively undone — exactly the "collateral already seized before the market outcome is truly final" scenario in the report.

### Impact Explanation
An AA that reads oracle data via the unstable/`bAA`-inclusive path can execute an irreversible fund transfer (payment, asset issuance, state change) using the value of a unit that is subsequently invalidated (`final-bad`) at stabilization. This causes AA fund loss/incorrect payout: the AA (and its counterparties) act on a value that never becomes canonically true, analogous to a lender seizing collateral before the negRiskMarket outcome is authoritatively fixed. This is a fund-loss/fund-freezing class issue (Medium/High), matching the required impact bar.

### Likelihood Explanation
Exploitability requires: (1) an oracle/AA address whose data-feed-posting unit can be made to conflict (double-spend/non-serial) with another unit authored by the same address before stabilization, and (2) a consuming AA configured to use the unstable-inclusive read (`unstable_opts`/`bAA`, or `all_unstable`) on a data feed rather than waiting for stability. This is a deliberate performance/UX trade-off feature (fast reaction to AA-to-AA messages before full stability) rather than a purely accidental defect, but it carries the same "acted on a non-final value" risk described in the report, and any AA author choosing this option (or a malicious oracle-AA racing a conflicting unit) can trigger it.

### Recommendation
For any AA logic that performs irreversible actions (payments, asset transfers, collateral release) based on a data feed value, avoid the `unstable_opts`/`all_unstable` unstable-read path, or require that the source unit be confirmed stable and `sequence='good'` (i.e., verified only via the stable DB path, not `storage.assocUnstableMessages`) before treating the value as final — mirroring the report's fix of checking only the fully-determined outcome, not the intermediate one.

### Proof of Concept
1. An address `O` (posting as an AA, `objUnit.bAA === true`) posts a `data_feed` unit `U1` with `outcome=1`, currently accepted with `sequence='good'` while still unstable.
2. A consuming AA `C` evaluates `data_feed[[oracles="O", feed_name="outcome"]]` (or `in_data_feed[[...]]`) using the default AA unstable-read path in `readDataFeedValue`/`dataFeedExists` [7](#0-6) , sees `outcome=1`, and immediately sends an irreversible payment/state change (e.g., releases collateral) in its response.
3. Before `U1` stabilizes, address `O` (or an attacker controlling a doublespend against `O`) gets a conflicting unit accepted such that `findConflictingUnits`/`handleNonserialUnits` at stabilization time resolves `U1` to `sequence='final-bad'` [8](#0-7) .
4. `U1`'s data-feed payload is discarded rather than committed to the stable data-feed KV store [9](#0-8) , meaning the canonical, final data feed never actually contained `outcome=1` — yet AA `C` already irreversibly acted on it in step 2.
