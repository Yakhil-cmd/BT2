### Title
Webhook signature verified against `repository.owner.login`, but stack lookup uses unrelated `repository.full_name` - cross-repository write / unauthorized sync via forged webhook - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
This is an analog of the "check function omits the guard that should bind the verified value to the acted-upon value" bug class from the report (`isTransferable()` skipping `notNull`). In `SablierFlowBase`, one function read `_streams[streamId]` without the modifier that ties `streamId` to a verified/existing stream. In Shipit's webhook pipeline, the field that is cryptographically verified (`repository.owner.login`, used to pick which GitHub App's `webhook_secret` authenticates the request) is never bound to the field that is actually used to locate and mutate a `Stack`/`Repository` (`repository.full_name`). The two fields are read independently from the same untrusted JSON body, so a request can be legitimately signed for one organization while its handler-visible content points at a completely different, unrelated tracked repository.

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App configuration to validate the HMAC signature using `repository_owner`, which is `params.dig('repository', 'owner', 'login')` (or `organization.login` as fallback): [1](#0-0) [2](#0-1) 

Once the signature check passes, `create` dispatches the raw parsed `params` to the matching handler(s): [3](#0-2) 

Handlers, however, resolve the target `Repository`/`Stack` from a *different* field of the same body, `repository.full_name`, with no cross-check that it corresponds to `repository.owner.login`: [4](#0-3) 

For example, `PushHandler#process` uses `stacks` (derived from `repository.full_name`) to trigger a GitHub sync on arbitrary matching stacks: [5](#0-4) 

The same pattern (locating the repository via `params.repository.full_name`, independent of the org used for signing) recurs in the pull-request handlers (`opened_handler.rb`, `closed_handler.rb`, `reopened_handler.rb`, etc.), all of which resolve `repository` purely off `full_name`: [6](#0-5) 

**Binding broken:** *"organization that authenticated" ≠ "repository that is written."* The organization whose `webhook_secret` produced a valid HMAC over the raw body (`repository.owner.login`) is never required to equal the organization/repository that the handler code actually looks up and mutates (`repository.full_name`).

**Before the attacker's request:** a validly-signed webhook for organization `A` can only affect repositories that legitimately belong to `A`, because GitHub itself always emits internally-consistent `owner.login` and `full_name` fields, and nothing in Shipit enforces this relationship independently.

**After the attacker's request:** an entity that knows organization `A`'s `webhook_secret` (e.g., an org admin who configured their own GitHub App/webhook for a low-privilege stack hosted on the same shared Shipit instance) can hand-craft an HTTP POST with a valid HMAC-SHA1 signature computed from `A`'s secret, set `repository.owner.login` = `A` (so `verify_signature` passes), but set `repository.full_name` = `victim-org/victim-repo` (a stack tracked under organization `B` on the same instance). Since the handler resolves the acted-upon repository solely via `full_name`, the forged event is processed against `victim-org/victim-repo`, e.g. triggering `GithubSyncJob`/`stack.sync_github` for a repository the attacker has no legitimate relationship with.

### Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" boundary explicitly called out as in-scope. On a Shipit instance configured for multiple GitHub organizations (a supported and documented configuration, see `config/secrets.development.shopify.yml`), a party who only administers one onboarded org's webhook secret can force writes/state changes (commit sync, deployable status changes, PR/review-stack provisioning, archiving/unarchiving) against stacks belonging to a different, unrelated organization also hosted on the instance. This is a cross-repository write achieved purely by forging an HTTP request with a secret the attacker legitimately possesses for their *own* org, not for the victim's — satisfying the "Critical: cross-repository writes" bucket.

### Likelihood Explanation
Requires only that the attacker control (or know) one onboarded organization's `webhook_secret` in a multi-org Shipit deployment — a documented, supported deployment shape — and be able to send an arbitrary HTTP POST to the public `/github/auth/*`-adjacent webhooks endpoint (which is unauthenticated apart from the signature). No GitHub App private key, `ApiClient` token, or session is needed. The only limiting factor is that the deployment must host repositories belonging to more than one organization under one Shipit installation, which is an explicitly documented multi-org configuration (`config/secrets.development.shopify.yml`, `secrets_double_github_app.yml`).

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler#repository_name`), enforce that the value used to select and validate the webhook secret (`repository.owner.login` / `organization.login`) equals the owner segment of the value used by the handler to resolve the target repository (`repository.full_name`). Reject the request (e.g., with `head(422)`) if they diverge, so the authenticated organization and the mutated repository are always the same entity.

### Proof of Concept
1. Configure Shipit with two organizations, `orgA` and `orgB`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. As an attacker who is an admin of `orgA` and thus knows `orgA`'s `webhook_secret`, craft a JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "orgB/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(orgA_webhook_secret, body)>` and set `X-Github-Event: push`.
4. POST to `/github_webhook` (or the mounted webhooks path). `verify_signature` resolves `Shipit.github(organization: 'orgA')` and successfully verifies the signature.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name('orgB/victim-repo')`, and calls `stack.sync_github(expected_head_sha: params.after)` on `orgB`'s stack — a repository never covered by `orgA`'s signature — despite the attacker never possessing any credential tied to `orgB`. # frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
