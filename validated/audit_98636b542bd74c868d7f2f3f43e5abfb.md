### Title
Skill lockfile entries keyed only by skill name allow cross-source overwrite of provenance/trust records - (File: internal/skills/lockfile/lockfile.go)

### Summary
`gh`'s skills feature persists an install record for every installed skill in `~/.agents/.skill-lock.json` via `RecordInstall`. The record is stored in a map keyed solely by `skillName`, with no incorporation of the skill's source (`host`, `owner`, `repo`). This mirrors the reported `txnHash` collision bug: a value derived from an insufficient subset of the "transaction" fields is used as a map key, so two logically distinct entities (here, skills installed from two different GitHub repositories) can collide on the same key and the later one silently overwrites the earlier one's trust/provenance metadata.

### Finding Description
`RecordInstall` builds the persisted entry and stores it keyed by `skillName` alone: [1](#0-0) 

The `entry` struct records `Source`, `SourceType`, `SourceURL`, `SkillFolderHash` (a tree SHA used as an integrity/version indicator), and `PinnedRef`: [2](#0-1) 

`skillName` originates from user-controlled/attacker-controlled input: it is the display/install name of a skill discovered in a remote (attacker-published) repository, e.g. `opts.SkillName` passed through the install flow: [3](#0-2) 

Because the map key `f.Skills[skillName]` (`internal/skills/lockfile/lockfile.go:38`, `:119`, `:125`) does not include `owner`, `repo`, or `host`, an attacker who publishes a skill under the same name as a previously-installed, legitimately-sourced skill (e.g. `git-commit` from `trusted-org/skills`) can cause the user to install their skill under that same name from a different repository. The subsequent `RecordInstall` call overwrites the existing lockfile entry, replacing the legitimate `Source`, `SourceURL`, and `SkillFolderHash` with the attacker's values — exactly analogous to how `txnHashToTransaction[txnHash]` and `txnToThresholdSet[txnHash]` in the original bridge bug are silently overwritten because `txnHash` didn't include the source chain/address.

### Impact Explanation
The lockfile is the durable record of "what was installed and from where" for the skills feature — a security-sensitive subsystem given `gh`'s own disclaimer that "Skills are not verified by GitHub and may contain prompt injections, hidden instructions, or malicious scripts": [4](#0-3) 

If provenance tracking for a given skill name can be silently overwritten by installing a same-named skill from an unrelated, attacker-controlled repository, the recorded `Source`/`SkillFolderHash` no longer reliably identifies which content is actually on disk, undermining any trust or review workflow that relies on this record (e.g., the "review before use" guidance references source/SHA). This is the same class of impact as the original finding: loss of integrity of an approval/provenance record due to key collision, not a full RCE by itself, but a namespace-collision that corrupts trust metadata used by the skills ecosystem.

### Likelihood Explanation
Likelihood is moderate: it requires no privilege beyond publishing a public GitHub repository with a skill whose name matches one the victim has already installed from elsewhere, then getting the victim to run `gh skill install <attacker>/<repo>` (or similar) — a normal, expected `gh` workflow, with no MITM, no local access, and no leaked credentials required.

### Recommendation
Key the `.skill-lock.json` `Skills` map (and any related lookups) by a composite identifier that includes `host`, `owner`, `repo`, and `skillName` (or `skillPath`) rather than `skillName` alone, so that skills from different sources sharing the same display name cannot collide and overwrite each other's provenance records. If a name collision is detected during install, surface an explicit warning/prompt to the user distinguishing the existing source from the new one.

### Proof of Concept
1. Install a skill `git-commit` from `trusted-org/skills`, recording it in `.skill-lock.json` with `Source: "trusted-org/skills"` and its `SkillFolderHash`.
2. Publish an unrelated repository `attacker/evil-skills` containing a skill also named `git-commit`.
3. Run `gh skill install attacker/evil-skills` and select/install `git-commit`.
4. `RecordInstall("github.com", "git-commit", "attacker", "evil-skills", ...)` is called and overwrites `f.Skills["git-commit"]` in place (`internal/skills/lockfile/lockfile.go:119-136`), replacing the original `Source`/`SkillFolderHash` with the attacker's values — with no error or key-collision detection, matching the original report's "later transaction overrides former" pattern.

Note: I was unable to fully enumerate every downstream consumer of the `Skills` map (beyond the writer in `RecordInstall`) before running out of tool calls, so I cannot confirm every security decision that reads this specific lockfile entry; the `gh skill update` flow appears to derive its trust decisions primarily from each skill's local `SKILL.md` frontmatter rather than this lockfile, which may limit (but does not eliminate) the practical blast radius of this specific collision.

func RecordInstall(host, skillName, owner, repo, skillPath, treeSHA, pinnedRef string) error {
	lockPath, err := lockfilePath()
	if err != nil {
		return err
	}
	if err := os.MkdirAll(filepath.Dir(lockPath), 0o755); err != nil {
		return fmt.Errorf("could not create lock directory: %w", err)
	}

	lockedFile, unlock, err := acquireFLock()
	if err != nil {
		return err
	}
	defer unlock()

	f, err := readFrom(lockedFile)
	if err != nil {
		return err
	}

	now := time.Now().UTC().Format(time.RFC3339)

	existing, exists := f.Skills[skillName]
	installedAt := now
	if exists {
		installedAt = existing.InstalledAt
	}

	f.Skills[skillName] = entry{
		Source:          owner + "/" + repo,
		SourceType:      "github",
		SourceURL:       ghinstance.HostPrefix(host) + owner + "/" + repo + ".git",
		SkillPath:       skillPath,
		SkillFolderHash: treeSHA,
		InstalledAt:     installedAt,
		UpdatedAt:       now,
		PinnedRef:       pinnedRef,
	}

	return writeTo(lockedFile, f)
}
