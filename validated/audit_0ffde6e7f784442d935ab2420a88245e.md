### Title
Bridge KLAY Fallback Function Lacks Maximum Fee Protection, Enabling Silent Overpayment — (File: `contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

---

### Summary

The `BridgeTransferKLAY` fallback function hard-codes `feeOfKLAY` as the `_feeLimit` at execution time, giving users no mechanism to bound the fee they pay. If bridge operators raise `feeOfKLAY` between when a user broadcasts a fallback transaction and when it is mined, the user silently transfers less KAIA to the counterpart chain than intended, with no revert and no refund. The explicit `requestKLAYTransfer` path does not share this flaw.

---

### Finding Description

`BridgeTransferKLAY.sol` exposes two user-facing entry points for KAIA bridge requests:

**Fallback (vulnerable)** [1](#0-0) 

```solidity
function () external payable {
    _requestKLAYTransfer(msg.sender, feeOfKLAY, new bytes(0));
}
```

The `_feeLimit` argument is set to the **current** `feeOfKLAY` at execution time.

**`requestKLAYTransfer` (protected)** [2](#0-1) 

```solidity
function requestKLAYTransfer(address _to, uint256 _value, bytes calldata _extraData) external payable {
    uint256 feeLimit = msg.value.sub(_value);
    _requestKLAYTransfer(_to, feeLimit, _extraData);
}
```

Here `feeLimit = msg.value − _value`. If the actual fee exceeds this, the call reverts with `"insufficient feeLimit"`.

Inside `_payKLAYFeeAndRefundChange`, the guard is: [3](#0-2) 

```solidity
function _payKLAYFeeAndRefundChange(uint256 _feeLimit) internal returns(uint256) {
    uint256 fee = feeOfKLAY;                      // re-read at execution time
    if (feeReceiver != address(0) && fee > 0) {
        require(_feeLimit >= fee, "insufficient feeLimit");
        ...
        uint256 feeRefund = _feeLimit.sub(fee);   // always 0 for fallback path
        ...
    }
}
```

When the fallback is used, `_feeLimit == feeOfKLAY` and `fee == feeOfKLAY` (both read at the same execution block), so `require(_feeLimit >= fee)` is trivially `true` regardless of how much the fee has grown. The amount credited to the counterpart chain is: [4](#0-3) 

```solidity
emit RequestValueTransfer(
    ...
    msg.value.sub(_feeLimit),   // = msg.value − feeOfKLAY (execution-time)
    ...
);
```

If `feeOfKLAY` rose from `F_old` to `F_new` after the user signed the transaction, the user receives `(F_new − F_old)` fewer KAIA on the destination chain, with the surplus going to `feeReceiver`. There is no revert, no refund, and no user-controlled guard.

---

### Impact Explanation

- **Asset impact**: KAIA is silently redirected from the user's cross-chain transfer to the fee receiver. The `RequestValueTransfer` event records the reduced amount, which bridge operators use to determine how much to release on the counterpart chain. The user's on-chain KAIA is already spent; the shortfall is unrecoverable.
- **Invariant broken**: Users who call the fallback expect to transfer `msg.value − F_old` KAIA. The contract transfers `msg.value − F_new` KAIA without any user consent or revert path.
- **Scope match**: Unauthorized fee charge affecting KAIA.

---

### Likelihood Explanation

Operators are semi-trusted and can legitimately update `feeOfKLAY` at any time via `setKLAYFee`. A fee change that lands in the same block as a pending fallback transaction — or in a block between broadcast and inclusion during network congestion — silently increases the fee paid. The fallback is the natural entry point for simple KAIA bridge transfers (e.g., wallet sends to bridge address), making it the most commonly used path.

---

### Recommendation

**Short term**: Deprecate or remove the fallback function. Users should be directed to `requestKLAYTransfer`, which already provides fee-limit protection via the `_value` parameter.

**Long term**: If a fallback is retained, add a `maxFeeIn` parameter (or encode it in calldata) so users can make the transaction revert when `feeOfKLAY` exceeds their acceptable limit — mirroring the protection already present in `requestKLAYTransfer`.

---

### Proof of Concept

1. Bridge operators set `feeOfKLAY = 0.1 KAIA`.
2. Alice broadcasts a fallback transaction sending `1.4 KAIA`, expecting `1.3 KAIA` to be bridged.
3. Before Alice's transaction is mined, operators execute `setKLAYFee(0.4 KAIA, nonce)` (requires threshold votes, but is a normal operational action).
4. Alice's fallback executes: `_feeLimit = feeOfKLAY = 0.4 KAIA`. The guard `require(0.4 >= 0.4)` passes. `feeRefund = 0`.
5. `RequestValueTransfer` emits `value = 1.4 − 0.4 = 1.0 KAIA`.
6. Bridge operators on the counterpart chain release `1.0 KAIA` to Alice instead of `1.3 KAIA`.
7. Alice loses `0.3 KAIA` to the fee receiver with no revert and no recourse.

        uint256 fee = feeOfKLAY;

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            (bool ok, ) = feeReceiver.call.value(fee)("");
            require(ok, "transfer fee failed");

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                (bool ok, ) = msg.sender.call.value(feeRefund)("");
                require(ok, "refund fee failed");
            }

            return fee;
