### Title
Unbounded loop over all network-wide unstable units in `dataFeedExists`/`readDataFeedValue` allows attacker-triggered AA-evaluation slowdown across all nodes - (File: data_feeds.js)

### Summary
`data_feeds.js`'s `dataFeedExists()` and `readDataFeedValue()` iterate `for (var unit in storage.assocUnstableMessages)` over **every currently-unstable unit in the entire DAG**, whenever the caller is an AA (`bAA`/`unstable_opts` truthy), to find matching `data_feed` messages authored by the requested oracle addresses. This mirrors the `getDelegatorMetadata` bug class (unbounded loop over an attacker-influenceable collection) but here the collection size is **global**, not scoped to the caller, and the cost is paid on **every full node** validating the triggering unit.

### Finding Description

These are invoked from oscript's `data_feed[[...]]` and `in_data_feed[[...]]` formula operators in `formula/evaluation.js`: [3](#0-2) [4](#0-3) 

with `bAA` computed as: [5](#0-4) 

which is `true` for essentially every normal AA-trigger evaluation (i.e., not just light-client/getter contexts). This means that for **every** `data_feed`/`in_data_feed` call executed while validating/handling an AA trigger, the node walks the *entire* set of unstable units in the DAG (regardless of how many units the AA itself, the oracle, or the trigger sender actually touch), filtering only by `_.intersection(arrAddresses, objUnit.author_addresses)`.

Any unprivileged unit poster can grow `storage.assocUnstableMessages` by broadcasting many low-value units (unstable units accumulate naturally under load, or can be inflated deliberately since spacing units costs only ordinary fees, not a security deposit proportional to DAG-wide impact). Once the unstable set is large, **every** AA anywhere in the network that calls `data_feed`/`in_data_feed` pays the full O(size of unstable set) cost, on **every full node**, because AA execution must be replayed deterministically by all validating nodes.

Critically, the complexity/cost-accounting system that is supposed to bound AA computation (`MAX_OPS`/`MAX_COMPLEXITY`, assigned via `validateDataFeed`/`validateDataFeedExists` in `formula/validation.js`) assigns a **fixed** complexity cost to the `data_feed`/`in_data_feed` opcodes, independent of the true, unbounded cost that scales with the size of `storage.assocUnstableMessages`. The accounting model assumes O(1)-ish cost per data-feed lookup, but the actual implementation is O(total unstable units in the whole DAG) whenever executed in AA context — an unaccounted, unbounded loop exactly analogous to the reported `getDelegatorMetadata` issue, except here the "attacker-controlled input size" is the entire network's currently-unstable unit set rather than a single caller's own records.

### Impact Explanation
Because every full node must execute the identical AA logic to validate and write the triggering unit, an attacker who inflates the number of unstable units (by flooding the DAG with low-cost units, which is far cheaper than the resulting validation cost multiplier for every node running data-feed-consuming AAs) can substantially slow down validation of AA trigger units across the whole network. Since unit validation/AA execution is synchronous per-unit processing on the write path, this degrades the network's overall unit-confirmation throughput and can stall processing of the main chain during the attack window — matching the "network unable to confirm new units" impact category. It does not directly cause fund loss, but it undermines the complexity-based DoS protection the AA engine relies on, since the cost model does not account for this data-feed lookup path's true growth factor.

### Likelihood Explanation
Medium. It requires (a) at least one AA that uses `data_feed`/`in_data_feed` (extremely common pattern for oracle-based AAs) and (b) an attacker growing the unstable-unit set, which is achievable through ordinary unit spam (paid for at standard fees, not scaled to the damage inflicted). No privileged role, hub/peer compromise, or protocol-level exploit is needed — a normal unit poster reaching an AA trigger is sufficient to realize the cost amplification; growing the unstable set only requires posting additional ordinary units, something any unprivileged user can do.

### Recommendation
Bound the in-memory scan in `dataFeedExists`/`readDataFeedValue` by indexing `assocUnstableMessages` (or a derived structure) by author address so lookups are limited to units authored by the oracle addresses actually requested, rather than iterating the entire unstable-unit map. Alternatively, cap the number of unstable units scanned per call and update the AA formula complexity/op accounting (`formula/validation.js`'s `validateDataFeed`/`validateDataFeedExists`) to reflect a cost proportional to the current size of `storage.assocUnstableMessages`, so that the cost-bounding mechanism (`MAX_OPS`/`MAX_COMPLEXITY`) meaningfully limits this attack surface as originally intended.

### Proof of Concept
1. Attacker broadcasts a large number of ordinary, cheap units to inflate `storage.assocUnstableMessages` (naturally accumulates while units remain unstable; can be amplified by delaying stabilization via low-witnessed-level branches or simply high throughput of low-value units).
2. Attacker (or any user) triggers any deployed AA whose oscript uses `data_feed[[oracles=..., feed_name=...]]` or `in_data_feed[[...]]`.
3. During AA evaluation (on every full node validating this trigger unit), `dataFeeds.readDataFeedValue`/`dataFeedExists` executes `for (var unit in storage.assocUnstableMessages)` over the full, attacker-inflated unstable set, `forEach`-ing every message of every such unit: [6](#0-5) 
4. Because the formula-complexity accounting (`formula/validation.js`) charges a fixed cost for `data_feed`/`in_data_feed` irrespective of the size of `assocUnstableMessages`, this loop's true cost is unbounded by the AA's declared `MAX_OPS`/`MAX_COMPLEXITY`, letting the attacker amplify validation cost network-wide for a fixed, low cost of unit spam.
