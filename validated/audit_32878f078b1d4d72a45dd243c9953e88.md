### Title
Missing WebAuthn `CollectedClientData.type` ceremony-binding check allows any client-data type (e.g. registration `webauthn.create`) to be accepted as an authentication assertion - (File: `types/src/transaction/webauthn.rs`)

### Summary
`PartialAuthenticatorAssertionResponse::verify()` deserializes `CollectedClientData` from `client_data_json` and checks only the `challenge` field before proceeding to signature verification. It never checks the `ty` (`type`) field against the expected ceremony type (`webauthn.get`), which the WebAuthn spec (§7.2 step 11: "Verify that the value of C.type is the string webauthn.get") mandates.

### Finding Description
The `verify` function [1](#0-0)  deserializes `CollectedClientData` and only validates `collected_client_data.challenge` against the expected challenge derived from the raw transaction. It then proceeds directly to constructing `verification_data` and checking the signature [2](#0-1) . The `ty` field of `CollectedClientData` is never read or compared anywhere in this function or in the surrounding module.

This is empirically demonstrated by the existing test `verify_real_partial_authenticator_assertion_response_from_spc`, which constructs a `CollectedClientData` with `"type": "payment.get"` (not even the expected `webauthn.get` or an obvious forgery like `webauthn.create`), and asserts that `paar.verify(&raw_txn, &any_public_key)` returns `Ok(())` [3](#0-2) . This confirms the `type` field is entirely unconstrained by the verification logic — any string value is accepted as long as the challenge and signature check out.

Since the signature material is computed purely from `authenticator_data` and `sha256(client_data_json)` [4](#0-3) , and the challenge inside `client_data_json` is the only field cross-checked against the transaction, an attacker who obtains (or a WebAuthn authenticator that produces) a signed `CollectedClientData` with the transaction's challenge but `type: "webauthn.create"` (a registration-ceremony assertion) would still pass `verify()`.

### Impact Explanation
This breaks the ceremony-type binding that WebAuthn relies on to distinguish registration flows (`navigator.credentials.create()`) from authentication flows (`navigator.credentials.get()`). Per spec, an authenticator produces registration and authentication signatures over different structures/ceremonies, and relying parties must reject cross-ceremony reuse via the `type` check. Because Aptos's implementation never enforces this, a `CollectedClientData` blob produced (or replayable) from a registration-flow client that happens to embed the correct challenge could be accepted as a valid authentication signature, allowing acceptance of the "wrong ceremony" signature as transaction authentication — undermining the authenticator's guarantee about what operation the user actually approved.

### Likelihood Explanation
Exploitability depends on whether an attacker (or a permissive/misbehaving client library) can obtain a signature over `authenticator_data || sha256(client_data_json)` where `client_data_json.type` is `webauthn.create` and `client_data_json.challenge` matches the target raw transaction's SHA3-256 digest, signed by the victim's registered secp256r1 key. This requires tricking a user's authenticator/browser into performing a registration ceremony with the transaction hash as the challenge — a nontrivial but realistic client-side social-engineering/UX-confusion vector (e.g., malicious dApp calling `navigator.credentials.create()` with a crafted challenge instead of `.get()`), since nothing on the Aptos verification side rejects it.

### Recommendation
Add an explicit check in `PartialAuthenticatorAssertionResponse::verify()` that `collected_client_data.ty == ClientDataType::Get` (rejecting `Create` or any other value) before proceeding with challenge/signature verification, matching WebAuthn §7.2 step 11.

### Proof of Concept
The existing test in the same file already demonstrates the gap, as it never enforces `type == webauthn.get`: [3](#0-2) 

A minimal additional test to explicitly demonstrate the "registration type accepted as authentication" case would mirror `get_collected_client_data` in `api/src/tests/webauthn_secp256r1_ecdsa.rs` but set `ty: ClientDataType::Create` instead of `ClientDataType::Get` [5](#0-4) , sign it, and call `verify()` — it would currently return `Ok(())` since no type check exists.

fn generate_verification_data(authenticator_data_bytes: &[u8], client_data_json: &[u8]) -> Vec<u8> {
    // Let hash be the result of computing a hash over the clientData using SHA-256.

    // See <https://www.w3.org/TR/webauthn-3/#sctn-fido-u2f-sig-format-compat>
    [authenticator_data_bytes, &client_data_json_hash]

}
