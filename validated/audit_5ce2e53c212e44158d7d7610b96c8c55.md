### Title
Cross-organization webhook status/check forgery via organization-scoped signature verification without repository binding - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret used to authenticate an inbound GitHub webhook based on `repository_owner` (the `repository.owner.login`, or `organization.login`) taken from the *unverified* JSON body [1](#0-0) . The organization identity used to pick the signing secret is never bound to which repository/stack the resulting event handlers actually act on. `Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits globally by `sha` with no repository scoping at all, and other handlers scope by `repository.full_name`, a field taken from the same unverified payload rather than from anything cross-checked against the org that authenticated the request [2](#0-1) [3](#0-2) .

### Finding Description
The equality that should hold is: **organization that authenticated the webhook == repository/stack that the webhook event is permitted to mutate**. This engine breaks that binding.

- `repository_owner` is computed purely from attacker-controlled JSON fields (`repository.owner.login` or `organization.login`) before signature verification occurs: [4](#0-3) .
- That value is used only to select which configured GitHub App/organization's `webhook_secret` to HMAC-verify the raw body against: [1](#0-0)  and [5](#0-4) . In a multi-org configuration (explicitly documented and supported: "Using Multiple Github Applications"), each organization has its own independent `webhook_secret`.
- Once the signature check passes (using the secret belonging to *organization A*), `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` runs the handlers over the full, still-attacker-controlled `params` [6](#0-5) .
- `StatusHandler#process` never re-derives or checks the repository/org at all — it matches `Commit.where(sha: params.sha)` across the *entire* database and calls `create_status_from_github!` on whatever commits happen to have that SHA, regardless of which repository/organization they belong to [2](#0-1) .
- Other handlers (`PushHandler`, `CheckSuiteHandler`) do scope by repository, but via `Handler#repository_name`, which reads `payload.dig('repository', 'full_name')` — a field independent of, and never validated against, the `repository_owner`/`organization.login` value used for signature-secret selection [3](#0-2)  and [7](#0-6) , [8](#0-7) .

Concretely: if a Shipit instance is configured for multiple GitHub organizations (Org A and Org B, each with its own `webhook_secret`), a party who legitimately controls Org A's GitHub App/webhook configuration (and therefore knows Org A's `webhook_secret`) can craft and correctly HMAC-sign a payload where `organization.login`/`repository.owner.login` = `"OrgA"` (so `verify_signature` succeeds against Org A's secret) but the body's `sha` (for `status` events) matches a commit belonging to an entirely different stack under Org B, or `repository.full_name` (for `push`/`check_suite` events) names an Org B repository. The signature check has no way to detect this mismatch because it never inspects `repository.full_name`/commit ownership — it only uses `repository_owner` to *pick a key*, not to *scope what is written*.

### Impact Explanation
This lets an attacker who only has legitimate GitHub App/webhook credentials for one onboarded organization forge CI/status and check-run outcomes for commits/stacks belonging to a completely different organization on the same Shipit instance:
- `status` events create arbitrary `Status` records (`create_status_from_github!`) on any commit in the system by SHA collision-free targeting, including marking third-party commits as CI-`success`.
- `check_suite` events can trigger `schedule_refresh_check_runs!` on victim commits by supplying a matching `head_sha`/`head_branch` for the victim stack's branch, forged under the attacker's own org authentication.

Because Shipit's continuous-deployment / merge-safety logic (`Stack`, `Commit`, `UndeployedCommit`, `MergeRequest`) consumes these CI status/check-run states to decide whether commits are safe to deploy or merge, an attacker forging green statuses for a victim organization's commits can push the victim stack toward an unauthorized/automatic deploy or merge decision it would not otherwise have reached — this crosses into the "unauthorized deploy" and "cross-repository writes" impact tier. This requires no Shipit session, no `ApiClient` token, and no write access to the victim repository — only knowledge of the attacker's own organization's webhook secret, which is a credential boundary distinct from the victim's.

### Likelihood Explanation
Requires: (1) the Shipit instance is configured with multiple GitHub organizations/apps (a documented, supported configuration), and (2) the attacker has legitimate control of one onboarded organization's webhook secret (e.g., is an admin of that org's GitHub App, which is a normal, unprivileged-relative-to-the-victim-org capability). Given that, forging a valid signature for their own org while targeting another org's data requires no additional exploitation — only crafting the JSON payload's `sha`/`full_name` fields to diverge from `repository.owner.login`. This is a Medium-to-High likelihood in genuine multi-tenant deployments of this engine, and does not depend on the host failing to mount the engine as documented.

### Recommendation
Bind the repository/stack acted upon to the same organization identity used to select and verify the signature:
- In `WebhooksController`, after determining `repository_owner`, also resolve `payload.dig('repository', 'full_name')`'s owner segment and reject the request if it doesn't match `repository_owner` (or `organization.login`).
- In `Shipit::Webhooks::Handlers::StatusHandler`, scope `Commit.where(sha: params.sha)` through the handler's own `stacks`/`repository_name` helper (as `PushHandler`/`CheckSuiteHandler` already partially do), and additionally verify the resolved repository's owner matches the authenticated `repository_owner`.
- Pass the verified `repository_owner` down to handlers explicitly rather than only using it once, ephemerally, inside `verify_signature`.

### Proof of Concept
Given a Shipit deployment configured with two organizations, `OrgA` and `OrgB`, each with distinct `webhook_secret`s (per `docs/setup.md`'s "Using Multiple Github Applications"), and the attacker has legitimate access to `OrgA`'s webhook secret (e.g., they administer `OrgA`'s installed GitHub App):

1. Attacker obtains/knows a commit SHA belonging to `OrgB`'s stack (e.g., visible publicly on GitHub or via Shipit's public commit history UI).
2. Attacker crafts a JSON body:
```json
{
  "sha": "<OrgB-victim-commit-sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "OrgA" } }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC_SHA1(OrgA_webhook_secret, raw_body)` and sends it to `/github_webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` computes `repository_owner = "OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and the HMAC check passes because the attacker signed with the correct `OrgA` secret [1](#0-0) .
5. `StatusHandler#process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [2](#0-1) , which matches and updates the `OrgB` victim commit — never checking that this commit belongs to `OrgA`.
6. The victim `OrgB` commit now has a forged "success" status from an event that was only ever authenticated as coming from `OrgA`.

I was unable to fully trace how `Status`/`create_status_from_github!` feeds into `Stack`'s continuous-deployment trigger logic within the remaining iteration budget (files `app/models/shipit/commit.rb`, `app/models/shipit/stack.rb`, `app/models/shipit/status/*.rb` were only partially grepped, not read in full), so the exact mechanics of how a forged status leads to an actual unauthorized deploy trigger are inferred from method names (`deployable?`, `trigger_continuous_delivery`, `success?`) rather than fully confirmed line-by-line. This should be verified directly in those files before treating the "unauthorized deploy" escalation as fully proven; the cross-organization data-integrity break itself (forging CI state for another org's commit while authenticated as a different org) is confirmed by the cited code.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
