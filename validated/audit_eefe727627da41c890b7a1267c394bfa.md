### Title
`StatusHandler#process` writes a GitHub Status onto any Commit row matching the SHA globally, without verifying the webhook's `repository.full_name` owns that commit's stack - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits purely `Commit.where(sha: params.sha)` and calls `create_status_from_github!` on every match, never restricting to the repository named in the verified webhook payload. Signature verification only proves the webhook came from the GitHub organization matching `payload.dig('repository','owner','login')`, not that the commit being mutated belongs to that same repository, so a valid signed `status` event for attacker-owned repo A can write a Status onto a Commit row belonging to victim repo B whenever the SHAs collide.

### Finding Description
The binding that must hold is: `repository named in the verified webhook payload (payload.dig('repository','full_name')) == repository owning the Commit row(s) mutated by process`. Tracing the code shows this binding is never enforced for `status` events.

- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`, which authenticates that the request came from GitHub for the organization named in the payload — it says nothing about which specific commit rows the handler is allowed to touch.
- `Handler` (`app/models/shipit/webhooks/handlers/handler.rb`) provides a `stacks` helper (`Repository.from_github_repo_name(repository_name)&.stacks`) specifically meant to scope handler logic to the stacks belonging to the payload's named repository. Other handlers use it correctly, e.g. `CheckSuiteHandler#process` (`app/models/shipit/webhooks/handlers/check_suite_handler.rb:13-17`) does `stacks.where(branch: ...).each { |stack| stack.commits.where(sha: ...) ... }`, explicitly filtering to the repository's own stacks before touching any commit.
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) does not call `stacks` at all:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This queries `Commit` globally by `sha`, with no `stack_id`/`repository` filter, then calls `Commit#create_status_from_github!` (`app/models/shipit/commit.rb:165-169`) which creates a `Status` row tied to `stack_id` and triggers `add_status`, which can emit `Hook.emit(:commit_status/:deployable_status, ...)` and even call `stack.schedule_merges` (`app/models/shipit/commit.rb:374-384`) on tenant B's stack.

Exploit flow: attacker owns repo A (with a legitimate, correctly-configured webhook to Shipit) and creates a commit with SHA `S` (e.g., by pushing an empty-tree/orphan commit — SHAs depend only on tree/parent/author data, so an attacker with knowledge of a target SHA occurring in another tenant's repo, e.g. from a shared vendored dependency bump or cherry-picked commit, can reproduce or discover that exact SHA in their own repo, or simply have their CI provider fire a `status` webhook for any SHA string they control including one guessed/observed to also exist as a `Commit` row for tenant B). Attacker triggers (via their own CI integration, which they legitimately control for repo A) a signed `status` webhook: `{"repository": {"full_name": "attacker/repoA", "owner": {"login": "attacker"}}, "sha": "S", "state": "success", ...}`. This passes `verify_signature` because it's a legitimately signed webhook for the attacker's own org/repo. `StatusHandler#process` then finds ALL `Commit` rows across ALL stacks with `sha == S`, including victim's commit under `shipit_stacks(:tenant_b)` linked repo `victim/repoB`, and writes a `Status` row for it, potentially flipping the commit to `success` and unblocking deploys/merges on tenant B's stack — with no relationship between `attacker/repoA` and `victim/repoB` ever checked.

### Impact Explanation
This is a cross-repository/cross-tenant write: a webhook authenticated only for repository A causes `Status` (and downstream deploy/merge scheduling) mutation on repository B's `Commit`/`Stack` records that A never authenticated. Since `deployable?`/`schedule_continuous_delivery`/`stack.schedule_merges` are all driven by status state, a forged/attacker-controlled "success" status can make an otherwise-unverified commit appear CI-green and unblock continuous deployment or auto-merge on a victim stack. This matches the "Critical: a payload for one repository mutating another's stack, commit, task or team" category. The attack is repeatable against any SHA collision the attacker can produce or discover, and the blast radius spans every Shipit-managed stack that happens to share a commit SHA with the attacker's repository (common with shared vendored dependencies, cherry-picks, or repository forks/mirrors where identical commits legitimately exist across multiple Shipit-tracked repos).

### Likelihood Explanation
Preconditions: the attacker needs a repository with a legitimately configured GitHub webhook pointed at the Shipit instance (something any GitHub user can set up for their own repo, no Shipit privileges needed), and a SHA collision with a commit tracked by a victim's Shipit stack. SHA collisions are realistic in practice for vendored dependency bump commits, cherry-picks across mirrored/forked repos, or any workflow where the same commit is applied to multiple repositories tracked by the same Shipit instance — this is exactly the scenario the question specifies. No Shipit secrets, sessions, or API tokens are required; only the attacker's own repo and its own GitHub webhook configuration (which is entirely under the attacker's control) are needed. This is fully repeatable and requires no privileged Shipit role.

### Recommendation
Scope `StatusHandler#process` to the repository named in the verified webhook payload, mirroring `CheckSuiteHandler`, e.g.:
```ruby
def process
  stacks.flat_map(&:commits).select { |c| c.sha == params.sha }.each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
or more efficiently, join through `Repository.from_github_repo_name(repository_name)` to restrict `Commit.where(sha: params.sha)` to `stack_id IN stacks.pluck(:id)` before calling `create_status_from_github!`.

### Proof of Concept
Minitest plan for `test/controllers/webhooks_controller_test.rb` (or `test/models/webhooks/handlers/status_handler_test.rb`):
1. Create `stack_a` linked to repository `attacker/repoA`, and `stack_b` linked to repository `victim/repoB`.
2. Create a `Commit` under `stack_b` with `sha: 'deadbeef...'` (`tenant_b_commit`).
3. Assert-before: `Shipit::Status.where(commit: tenant_b_commit).count == 0`.
4. POST to `/webhooks` with header `X-Github-Event: status`, a valid signature computed with the org-appropriate `webhook_secret` for `attacker`, and JSON body: `{"repository": {"full_name": "attacker/repoA", "owner": {"login": "attacker"}}, "sha": "deadbeef...", "state": "success", "context": "ci/attacker"}`.
5. Assert-after: `Shipit::Status.where(commit: tenant_b_commit).count == 1` and `tenant_b_commit.reload.status.state == 'success'`, proving a webhook authenticated only for `attacker/repoA` mutated a Status belonging to `victim/repoB`'s commit — violating the equality `payload repository == repository owning the mutated Commit`.
