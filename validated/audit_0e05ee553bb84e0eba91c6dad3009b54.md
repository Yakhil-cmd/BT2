### Title
Escrowed funds in an arbiter contract's shared address can be frozen forever if the arbiter never resolves a dispute - (File: arbiter_contract.js)

### Summary
`arbiter_contract.js` implements a two-party escrow ("contract") whose funds are held in a shared multisig address whose spending conditions are generated by `deriveSharedAddress()`. The only ways to release the escrowed funds are (a) a voluntary, unilateral payment by one of the two parties to the other, or (b) a ruling posted by the designated arbiter as a `data_feed` message. There is no time-boxed fallback: if the arbiter never rules (lost keys, went offline, or acts maliciously/negligently) and neither counterparty is willing to voluntarily release funds to the other side, the funds sit in the shared address permanently, exactly as in the reported analog where `setReadyForPayout` gated all payouts behind a single operator role.

### Finding Description
When a contract is created, `deriveSharedAddress()` builds the definition for the shared address that will hold the escrowed payment: [1](#0-0) 

For public/non-fixed-denomination assets, the "voluntary settlement" branches require the *paying* party (`offeror_address`) to sign **and** actually produce an output paying the full amount to the counterparty (`[1][1]`), or the counterparty to sign and refund the full amount back to the payer (`[1][2]`): [2](#0-1) 

The only other branches that can release funds are the arbiter-signed data-feed rulings: [3](#0-2) 

These are exercised via `openDispute()`, which forwards the case to the arbiter/arbstore and simply waits for a response: [4](#0-3) 

and the "arbiter response" listener, which only acts if/when the arbiter's device eventually posts a `data_feed` unit naming a winner: [5](#0-4) 

There is no code path that lets either party unilaterally reclaim the escrowed funds, nor any mechanism to change the arbiter, expire the contract, or force a default outcome after some deadline. The `ttl` field only governs how long the initial pending *contract offer* remains valid before the shared address/escrow is even created: [6](#0-5) 

it has no effect once the money is already in the shared address in `paid`/`in_dispute` status. `appeal()` only re-routes the dispute to the same arbstore/arbiter and still requires that party to respond: [7](#0-6) 

So if the arbiter (or the arbstore they are registered under) permanently disappears, loses their private key, or simply refuses to rule, and the disputing counterparty also refuses any voluntary settlement, the coins locked in the shared address (base bytes or an issued/private asset) become permanently unspendable — the same "single point of failure controls the payout, no unprivileged fallback exists" root cause as the reported `setReadyForPayout` issue, just realized through a data-feed-gated multisig address instead of an access-controlled function.

### Impact Explanation
Real user funds (native bytes or any asset used in the contract, including private assets) placed into the arbiter-contract shared address can become permanently locked with no path to recovery for either counterparty. This is a direct, concrete loss/freezing of funds for ordinary, unprivileged users who use this feature exactly as designed (posting payments/private-payment chains into a shared address governed by oscript authentifiers), matching the "AA/contract fund freezing" impact class.

### Likelihood Explanation
Likelihood is realistic rather than purely theoretical: arbiters are third-party device operators who can lose their pairing/device key, go offline, or simply ignore a dispute (there is no bond, penalty, or forced-timeout in this code path to compel a ruling), and one of the two counterparties has every incentive to refuse voluntary settlement once a dispute exists (that is precisely why disputes happen). Any pair of users who use `arbiter_contract.js` to escrow value under an unresponsive/malicious arbiter can trigger this permanently.

### Recommendation
Add a deadline/expiry branch to the shared-address definition produced in `deriveSharedAddress()` (e.g., an `["and", [["address", X], ["after", deadline]]]` style clause) that lets one or both parties reclaim/split the funds unilaterally once a fixed timeout since `paid`/`in_dispute` has elapsed without an arbiter ruling, removing the single point of failure on the arbiter.

### Proof of Concept
1. Alice and Bob create an arbiter contract with Carol as arbiter; Alice (`me_is_payer`) sends the escrow amount into the shared address derived by `deriveSharedAddress()` (`arbiter_contract.js:454-544`).
2. A dispute arises; Bob refuses to accept a refund and Alice refuses to authorize the full payout to Bob, so neither of the voluntary "has output" branches (`arbiter_contract.js:494-512`) can be satisfied.
3. Bob calls `openDispute()` (`arbiter_contract.js:262-311`); Carol's device key is lost/she never responds — the `new_my_transactions`/`data_feed` listener at `arbiter_contract.js:878-901` never fires because no ruling unit is ever posted.
4. No other spending path exists in the shared-address definition (`arbiter_contract.js:465-481`) and there is no timeout logic anywhere in `arbiter_contract.js` or the DB schema (`ttl` only applies pre-escrow, `initial-db/byteball-sqlite.sql:884-906`).
5. The funds in the shared address remain permanently unspendable.

function appeal(hash, cb) {
	getByHash(hash, function(objContract){
		if (objContract.status !== "dispute_resolved")
			return cb("contract can't be appealed");
		var command = "hub/get_arbstore_url";
		var address = objContract.arbiter_address;
		if (objContract.arbstore_address) {
			command = "hub/get_arbstore_url_by_address";
			address = objContract.arbstore_address;
		}
		device.requestFromHub(command, address, async function(err, url){
			if (err)
				return cb("can't get arbstore url:", err);
			err = await fillArbstoreAddresses(objContract);
			if (err)
				return cb(err);
			device.getOrGeneratePermanentPairingInfo(function(pairingInfo){
				var my_pairing_code = pairingInfo.device_pubkey + "@" + pairingInfo.hub + "#" + pairingInfo.pairing_secret;
				var data = JSON.stringify({
					contract_hash: hash,
					my_pairing_code: objContract.my_pairing_code,
					my_address: objContract.my_address,
					contract: {title: objContract.title, text: objContract.text, creation_date: objContract.creation_date, me_is_payer: objContract.me_is_payer, my_address: objContract.my_address, peer_address: objContract.peer_address, my_party_name: objContract.my_party_name, peer_party_name: objContract.peer_party_name, arbiter_address: objContract.arbiter_address, amount: objContract.amount, asset: objContract.asset},
				});
				httpRequest(url, "/api/appeal/new", data, function(err, resp) {
					if (err)
						return cb(err);
					setField(hash, "status", "in_appeal", function(objContract) {
						cb(null, resp, objContract);
					});
				});
			});
		});
	});
