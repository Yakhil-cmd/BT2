### Title
Attestation-based access/spend conditions cannot be revoked once granted, permanently exposing attested-gated funds - ([File: storage.js])

### Summary
The `attested` definition operator and the `spender_attested` asset restriction in ocore grant permanent, irrevocable access once a trusted attestor posts a single attestation for an address. The underlying check is a pure existence query — it never looks at the *content* or *recency* of subsequent attestations from the same attestor — so an attestor has no protocol-level way to undo a mistaken or malicious attestation, mirroring the "grant now, can't revoke later" root cause of the Sherlock M-1 finding (role/permission granted, immediately exploited, revocation has no effect on what was already unlocked).

### Finding Description
`filterAttestedAddresses()` in [1](#0-0)  determines whether an address counts as "attested" by simply checking whether *any* row exists in the `attestations` table from one of the allowed attestor addresses, after the address's last definition change:

```
SELECT DISTINCT address FROM attestations CROSS JOIN units USING(unit)
WHERE attestor_address IN(?) AND address IN(?) AND main_chain_index<=? AND is_stable=1 AND sequence='good'
  AND main_chain_index>IFNULL(... last definition change of that address ..., 0)
```

This query has no concept of "latest" attestation state or revocation — it only asks "did this attestor ever attest this address (since the address's keys last changed)?" Once true, it stays true forever, regardless of what the attestor posts afterward.

This existence-only check is used in two security-critical places:
1. The `attested` address-definition operator, evaluated in [2](#0-1) , which lets an address's spending definition include `['attested', [address, [attestor,...]]]` as an unlock condition (e.g. `['or', [['sig', ...], ['attested', ...]]]`).
2. The `spender_attested` asset restriction, checked in `validatePayment` and `validatePaymentInputsAndOutputs`: [3](#0-2)  and [4](#0-3) , and for private assets at [5](#0-4) .

An asset issuer (or address owner) who intends to use attestation as a gate (e.g., KYC/AML on a regulated asset, or "role" grant enabling spend of a shared address) grants the malicious/mistaken user a single attestation. That user can then immediately spend the attested-gated asset or satisfy the `attested` condition on an address. If the attestor realizes the mistake and tries to "revoke" by posting a corrective attestation, the protocol logic still returns true because it only checks for existence of *any* qualifying attestation row — the correction is never consulted by `filterAttestedAddresses`. The only way to truly invalidate the grant is for the *attested address itself* to change its own definition (keychange), which is entirely out of the attestor's control and defeats the purpose of attestor-controlled access.

### Impact Explanation
Any asset or address definition relying on `attested`/`spender_attested` for access control is permanently compromised by a single erroneous or malicious attestation. This can lead to unauthorized, irrevocable spending rights over attestation-gated assets (loss of funds for asset holders/issuers) or over funds locked behind an `attested` condition in an address definition, exactly analogous to the reported scenario where a role, once granted, cannot be meaningfully revoked before it is exploited.

### Likelihood Explanation
Attestation-gated assets (KYC-style tokens) and `attested` conditions in address definitions are a documented, supported feature of ocore, so this is a directly reachable, standard usage pattern — not a contrived edge case. Any attestor mistake, compromised attestor key, or social-engineering of an attestor produces an unrecoverable grant the moment a single attestation unit becomes stable.

### Recommendation
Change the attestation-gate check to consider only the *latest* attestation from each attestor (as is already done for the `attestation[[...]]` formula operator with `ifseveral='last'`), and define a standard revocation payload/field so that an attestor can explicitly invalidate a prior attestation. `filterAttestedAddresses()` and the `attested` opcode evaluation should be updated to respect this "last attestation wins" / explicit-revocation semantics instead of pure existence.

### Proof of Concept
1. Asset X is defined with `spender_attested: true` and `attestors: [ATTESTOR]`.
2. `ATTESTOR` mistakenly posts an `attestation` message for `MALICIOUS_ADDRESS`.
3. Once that unit is stable, `filterAttestedAddresses()` (storage.js:1959) returns `MALICIOUS_ADDRESS` as attested for any subsequent query.
4. `MALICIOUS_ADDRESS` immediately issues/spends asset X (validation.js:2115-2122, 2632-2641).
5. `ATTESTOR` posts a new attestation unit attempting to mark `MALICIOUS_ADDRESS` as revoked/unverified.
6. `filterAttestedAddresses()` still returns `MALICIOUS_ADDRESS` in the attested set, because the SQL only checks for existence of a qualifying row, not the latest attestation's content — `MALICIOUS_ADDRESS` retains spend rights on asset X indefinitely.
