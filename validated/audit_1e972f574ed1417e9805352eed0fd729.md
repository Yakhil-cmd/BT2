## Title
Multisig owner's explicit rejection (or approval) vote can be overridden by a false "implicit vote" when the same owner calls execute/reject — broken approval-set invariant - ([File: aptos-move/framework/aptos-framework/sources/multisig_account.move])

## Summary
`can_execute`, `can_reject`, and `validate_multisig_transaction` in the `multisig_account` module compute vote tallies by taking the real approval/rejection counts and then conditionally adding an "implicit vote" for the calling owner. The condition used to decide whether to add that implicit vote only checks whether the owner has voted *in that specific direction* (`has_voted_for_approval` / `has_voted_for_rejection`), not whether the owner has voted *at all*. This lets an owner who has explicitly cast a vote in one direction have an extra, contradictory vote silently added in the other direction merely by invoking `can_execute`/`can_reject` (which is exactly what `validate_multisig_transaction`, the VM-invoked prologue hook, does).

## Finding Description
`validate_multisig_transaction` is registered as the prologue hook the Aptos VM calls "during mempool transaction validation and as the first step of transaction execution" for multisig-account transactions [1](#0-0) . It gates admission of a multisig transaction by checking that quorum has been reached:

```move
if (features::multisig_v2_enhancement_feature_enabled()) {
    assert!(can_execute(address_of(owner), multisig_account, sequence_number), ...);
}
...
let (num_approvals, _) = num_approvals_and_rejections(multisig_account, sequence_number);
if (!has_voted_for_approval(multisig_account, sequence_number, address_of(owner))) {
    num_approvals += 1;
};
assert!(num_approvals >= num_signatures_required(multisig_account), ...);
``` [2](#0-1) 

`num_approvals_and_rejections` already tallies the *true* votes: for each owner that has voted, it increments `num_approvals` or `num_rejections` based on their actual recorded vote [3](#0-2) . That base count is therefore already correct and complete.

The subsequent "implicit vote" logic is meant to say: *"if the executing owner hasn't voted yet, treat their act of execution as an implicit approval."* However, the guard condition is `!has_voted_for_approval(...)`, defined as:

```move
inline fun has_voted_for_approval(multisig_account: address, sequence_number: u64, owner: address): bool {
    let (voted, vote) = vote(multisig_account, sequence_number, owner);
    voted && vote
}
``` [4](#0-3) 

If the owner has explicitly *rejected* the transaction (`voted = true, vote = false`), `has_voted_for_approval` returns `false`, so `!has_voted_for_approval` is `true`, and `num_approvals` is incremented by 1 anyway — even though this owner's rejection was already correctly counted (as a rejection) in the base tally from `num_approvals_and_rejections`. The condition fails to distinguish "never voted" from "explicitly voted the other way."

The exact same flaw is mirrored in `can_execute`:
```move
public fun can_execute(owner: address, multisig_account: address, sequence_number: u64): bool {
    assert_valid_sequence_number(multisig_account, sequence_number);
    let (num_approvals, _) = num_approvals_and_rejections(multisig_account, sequence_number);
    if (!has_voted_for_approval(multisig_account, sequence_number, owner)) {
        num_approvals += 1;
    };
    is_owner(owner, multisig_account) &&
        sequence_number == last_resolved_sequence_number(multisig_account) + 1 &&
        num_approvals >= num_signatures_required(multisig_account) && can_execute_with_timelock(...)
}
``` [5](#0-4) 

and in `can_reject`, which uses the symmetric `has_voted_for_rejection` guard, so an owner who explicitly *approved* gets an unwarranted implicit rejection counted when they call `can_reject`:
```move
public fun can_reject(owner: address, multisig_account: address, sequence_number: u64): bool {
    ...
    if (!has_voted_for_rejection(multisig_account, sequence_number, owner)) {
        num_rejections += 1;
    };
    is_owner(owner, multisig_account) &&
        sequence_number == last_resolved_sequence_number(multisig_account) + 1 &&
        num_rejections >= num_signatures_required(multisig_account)
}
``` [6](#0-5) 

The correct guard should have been "the owner has not voted at all" (`!voted`), not "the owner has not voted in this particular direction."

## Impact Explanation
This breaks the multisig approval-set invariant that transaction admission ("this multisig transaction may execute/be rejected") must reflect only the owners' real, explicit votes plus at most one legitimate implicit vote from an owner who never voted. Concretely:

- An owner who explicitly **rejected** a multisig transaction can still call the execute entry point themselves; `validate_multisig_transaction`/`can_execute` will silently add a fabricated approval on their behalf, on top of their already-counted rejection, potentially supplying the missing vote needed to reach `num_signatures_required` and causing a transaction to execute that should have failed admission due to insufficient real approvals.
- Symmetrically, an owner who explicitly **approved** a transaction can call `execute_rejected_transaction`/`can_reject` and get an unwarranted implicit rejection counted, potentially forcing removal of a transaction that had legitimate quorum to execute.

This is a direct violation of the "Pre-validation mismatch that causes a transaction which should fail admission to execute and commit" admission pivot, and of the multisig approval-set binding pivot: unprivileged owners (any single account in the owner set, even a minority with no real quorum) can manipulate the vote tally counted at the VM prologue boundary to force wrong admission outcomes for multisig-gated transactions (which can be transfers, module publishes, governance actions, etc., depending on what the multisig account is used for).

## Likelihood Explanation
Any owner of a `multisig_account` can trigger this: it only requires (1) casting an explicit vote in one direction, then (2) invoking the entry point associated with the opposite outcome (`execute` a rejected txn, or attempt to execute a transaction with insufficient real approvals). No special privilege beyond ordinary owner membership is needed, and the buggy code path (`validate_multisig_transaction`) is exercised on every multisig transaction submission once `multisig_v2_enhancement_feature_enabled` is on. This makes exploitation straightforward and repeatable for any owner set with the feature flag enabled.

## Recommendation
Change the guard conditions in `can_execute`, `can_reject`, and `validate_multisig_transaction`'s implicit-vote logic to check "has the owner voted at all" rather than "has the owner voted in this specific direction," e.g.:
```move
inline fun has_voted(multisig_account: address, sequence_number: u64, owner: address): bool {
    let (voted, _) = vote(multisig_account, sequence_number, owner);
    voted
}
```
and replace `!has_voted_for_approval(...)` / `!has_voted_for_rejection(...)` with `!has_voted(...)` in `can_execute`, `can_reject`, and `validate_multisig_transaction`, so that an owner who already voted (in either direction) never has a contradictory implicit vote added.

## Proof of Concept
1. Create a `multisig_account` with 3 owners (`owner_1`, `owner_2`, `owner_3`) and `num_signatures_required = 2`, with `multisig_v2_enhancement_feature_enabled`.
2. `owner_1` calls `create_transaction` (implicitly approves, as creator). Real approvals = 1.
3. `owner_2` calls `reject_transaction` — real tally: approvals = 1, rejections = 1. Quorum for execution (2) is not met.
4. `owner_2` (who just rejected) now attempts to execute the transaction (calls the VM path that invokes `validate_multisig_transaction`, or calls `can_execute(owner_2, ...)`):
   - `num_approvals_and_rejections` returns `(1, 1)` (owner_1 approved, owner_2 rejected).
   - `has_voted_for_approval(owner_2)` is `false` (owner_2's vote is `false`/reject), so the code does `num_approvals += 1`, producing `num_approvals = 2`.
   - `2 >= num_signatures_required (2)` → `can_execute` returns `true`, and `validate_multisig_transaction` allows execution — even though only 1 of 3 owners actually approved and one explicitly rejected.

This can be confirmed against the existing test pattern for `test_implicit_vote_counts_toward_override` [7](#0-6) , by substituting an explicit `reject_transaction` call for the "owner_3 hasn't voted" scenario and observing that `can_execute` still returns `true` for the rejecting owner.

*(Note: I was not able to execute the Move unit tests directly in this environment to empirically confirm the runtime behavior; the finding is based on static analysis of the `has_voted_for_approval`/`has_voted_for_rejection` semantics versus their usage sites. A Devin session with the ability to run `aptos move test` against this module would be needed to fully confirm the PoC end-to-end.)*

    inline fun num_approvals_and_rejections_internal(owners: &vector<address>, transaction: &MultisigTransaction): (u64, u64) {
        let num_approvals = 0;
        let num_rejections = 0;

        let votes = &transaction.votes;
        owners.for_each_ref(|owner| {
            if (simple_map::contains_key(votes, owner)) {
                if (*simple_map::borrow(votes, owner)) {
                    num_approvals += 1;
                } else {
                    num_rejections += 1;
                };
            }
        });

        (num_approvals, num_rejections)
    }
