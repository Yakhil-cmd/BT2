### Title
CCMenu Endpoint Bypasses Stack-Scoped API Client Authorization - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::CCMenuController` overrides the `stack` accessor used by every other API controller and resolves the target stack directly from `Stack`, instead of from the `stacks` relation that enforces the `ApiClient#stack_id` scoping. This lets a token that is only authorized for one stack read the CI/deploy status (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, lock state, etc.) of any other stack in the installation.

### Finding Description
`Api::BaseController` defines the authorization-scoping primitive used by all API resources: [1](#0-0) 

`stacks` restricts the visible set of stacks to `current_api_client.stack_id` when the client was created scoped to a single stack (as done by `CCMenuUrlController#client`, which creates a `read:stack` client tied to one stack): [2](#0-1) 

Every other resource controller (`StacksController`, `TasksController`, `MergeRequestsController`, etc.) relies on the inherited `stack` method, which goes through `stacks.from_param!(...)` and therefore respects that scoping.

`Api::CCMenuController`, however, redefines `stack` to bypass the scoped relation entirely: [3](#0-2) 

`require_permission :read, :stack` only checks that the string `"read:stack"` is present in `ApiClient#permissions` — it does not verify which stack the permission applies to: [4](#0-3) 

So the only binding meant to restrict a stack-scoped token to *its* stack (`current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`) is silently dropped by this one controller, which instead does `Stack.from_param!(params[:stack_id])` — i.e., any stack in the system, selected purely from attacker-controlled `params[:stack_id]`.

This is the analog of the reported `toInt`/`fromInt` mismatch: the code that should apply a scale/scope conversion (`stacks`, i.e., "convert token to its authorized stack set") is swapped for an unscoped one (`Stack`, "all stacks"), breaking the equality `stack a token authorises == stack a token touches`.

### Impact Explanation
An `ApiClient` token that is deliberately scoped to a single stack (e.g. created via the "CCMenu URL" feature, `ccmenu_url_controller.rb`, or any application-created client with `stack_id` set and only `read:stack` permission) can be replayed against `GET /api/1/stacks/:stack_id/ccmenu.xml` with a different `stack_id` and will successfully return that other stack's build/deploy status, lock reason, and last build label — data the token holder was never authorized to see. This is an unauthorized cross-stack read of stack state, matching the High-impact category of "unauthenticated read of stack state" via an authorization scope that should have prevented it.

### Likelihood Explanation
Any holder of a valid, narrowly-scoped `read:stack` API token (which Shipit explicitly designs to be handed out for limited purposes such as CI dashboards/CCMenu integrations) can exploit this with a single unauthenticated-repo-side HTTP request — just changing the `stack_id` path/query parameter. No additional privilege or secret is required beyond possessing one legitimately-scoped token.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the inherited, scope-respecting accessor (i.e. remove the override, or implement it as `stacks.from_param!(params[:stack_id])`) so that stack-scoped `ApiClient` tokens cannot access stacks outside their authorized `stack_id`.

### Proof of Concept
1. Create a stack-scoped API client (as `CCMenuUrlController#client` does) with `stack_id = A` and `permissions = ["read:stack"]`, and obtain its `authentication_token`.
2. Using that token, issue `GET /api/1/stacks/:B/ccmenu.xml` where `B` is a different stack's identifier.
3. Because `Api::CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` rather than `stacks.from_param!(params[:stack_id])`, `require_permission!(:read, :stack)` only checks the generic `"read:stack"` permission string, and the request succeeds, returning stack `B`'s CCMenu XML (name, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`) — despite the token being authorized only for stack `A`.
