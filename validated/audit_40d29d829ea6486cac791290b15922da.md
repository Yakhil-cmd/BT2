### Title
`StatusHandler#process` writes commit statuses by bare SHA with no repository/stack scoping, letting a webhook from one repository mutate a commit status in a different tenant's stack - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` and calls `create_status_from_github!` on every match, with no filter on `repository`/`stack_id`. Because `sha` is not unique across `Stack`s (each `Stack`/`ReviewStack` keeps its own `Commit` rows), a `status` webhook that is valid for one repository can flip the `ci/jenkins` status of a commit belonging to an unrelated stack that happens to share the same SHA (a shared base commit, an empty-tree commit, a common ancestor between a fork and upstream, etc.). This is compounded by a genuine operator-precedence bug in `provision?`/`unarchive?` in the pull-request handlers that can provision or unarchive a review stack even when `Repository#review_stacks_enabled` is `false`.

### Finding Description
The broken binding: the intended invariant is `commit.stack.repository == webhook.repository` for every write performed by a `status` event, i.e. a status for repo R must only ever touch `Commit` rows whose `stack.repository_id == R.id`. The actual code enforces no such equality: [1](#0-0) 

`Handler` (the base class) already exposes a repository-scoped `stacks` helper built from `payload.dig('repository', 'full_name')`: [2](#0-1) 

but `StatusHandler` never uses it - it queries `Commit` directly by bare `sha`, so any `Commit` row anywhere in the database with a matching SHA (belonging to any stack, of any repository) gets `create_status_from_github!` applied, which calls `statuses.replicate_from_github!` and can toggle `Status::Group` state, deployability, blocking, and merge scheduling via `stack.schedule_merges`: [3](#0-2) [4](#0-3) 

An attacker who owns/controls any repository wired to the same Shipit/GitHub App instance as the victim can emit a `status` event with `context: ci/jenkins`, `state: failure` and a SHA value that also exists as a `Commit` row in a victim stack (e.g. a shared base commit, an initial/empty commit, or a commit common to a fork and its upstream). Because `StatusHandler` performs no repository check, the write lands on the victim's `Commit`, corrupting `blocked?`/`deployable?` computation and `stack.schedule_merges` for a stack the attacker never authenticated against.

This is compounded by a separate, real bug in the review-stack provisioning gate. `provision?`/`unarchive?` are written as: [5](#0-4) 
Because `&&` binds tighter than `||` in Ruby, this parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)` - the last two disjuncts never reference `review_stacks_enabled` at all. So with `provisioning_behavior` set to `allow_with_label` (label present) or `prevent_with_label` (label absent), a review stack is provisioned/unarchived even when the repository's `review_stacks_enabled` flag is `false`. The identical pattern exists in `ReopenedHandler#unarchive?`. This widens the pool of live `Commit`/`Stack` rows an attacker can target via the SHA-collision path above, on repositories the operator believed had review stacks disabled.

No existing guard prevents this: `ExplicitParameters` only validates the shape of the `status` payload, not repository ownership of the target commit; `verify_signature`/GitHub App webhook verification only proves the payload came from GitHub for *some* installation, it does not scope the effect of `StatusHandler#process` to that installation's repository; and `Commit` has no unique constraint or scope tying SHA lookups to `stack_id`/`repository_id` in this handler.

### Impact Explanation
A crafted `status` webhook for a SHA shared with a victim stack causes a write (status/state flip) against a repository/stack that never authenticated that webhook - this is the "payload for one repository mutating another's stack, commit... " Critical-impact category. The flip can alter `deployable?`/`blocked?` and trigger `stack.schedule_merges`, i.e. force or block a deploy/merge decision on the victim stack without the victim's CI ever reporting that state. Blast radius is any stack/review-stack on the same Shipit instance whose `Commit.sha` collides with a SHA the attacker can produce (shared ancestor commits, forks, or common boilerplate commits), and it is repeatable for every such colliding SHA.

### Likelihood Explanation
Preconditions: attacker needs to be able to emit a `status` webhook accepted by the shared Shipit instance (own/control a repository wired to the same GitHub App/organization) and needs a SHA that also exists as a `Commit` row in the victim's stack. SHA collisions across repositories occur naturally for forks (shared history before divergence) and for well-known boilerplate commits; an attacker who forks the victim's repo trivially shares many ancestor SHAs. Given that, exploitation cost is a single HTTP `POST /webhooks` request, fully repeatable, and requires no Shipit credentials.

### Recommendation
1. Fix `StatusHandler#process` to scope the `Commit` lookup to the requesting repository, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalently join through `Stack`/`Repository` using the base `Handler#stacks` helper, so a status can only ever update commits belonging to the repository that authenticated the webhook.
2. Fix the operator precedence bug in `OpenedHandler#provision?` and `ReopenedHandler#unarchive?` by adding explicit parentheses so `review_stacks_enabled` gates every branch: `repository.review_stacks_enabled && (allow_all? || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?))`.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`):
```ruby
test "status for repo A does not mutate a commit belonging to repo B's stack" do
  repo_a = shipit_repositories(:shipit)
  repo_b_stack = shipit_stacks(:shipit) # different repository
  shared_sha = "a" * 40

  commit_b = repo_b_stack.commits.create!(sha: shared_sha, message: "shared ancestor")

  payload = {
    'sha' => shared_sha,
    'state' => 'failure',
    'context' => 'ci/jenkins',
    'repository' => { 'full_name' => repo_a.github_repo_name }
  }

  before_state = commit_b.reload.status.state
  Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  after_state = commit_b.reload.status.state

  # Binding under test: commit_b.stack.repository == repo_a  -> should be false,
  # so processing repo_a's status must NOT change commit_b's state.
  assert_equal before_state, after_state
end
```
A failing assertion (state changes despite `commit_b.stack.repository != repo_a`) demonstrates the unscoped write documented above.
