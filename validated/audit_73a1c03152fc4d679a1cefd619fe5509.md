### Title
`AssetConversionOps::migrate_to_new_account` can be permanently blocked by an unprivileged attacker pre-creating an asset account at the deterministic new pool address - (File: substrate/frame/asset-conversion/ops/src/lib.rs)

### Summary
`pallet-asset-conversion-ops::migrate_to_new_account` moves a pool's balances from a legacy-derived account (`prior_account`) to a new deterministically-derived account (`new_account`). Before transferring, it unconditionally calls `T::Assets::touch(...)` / `T::PoolAssets::touch(...)` on `new_account` whenever the prior account held a deposit-based ("non-sufficient") asset account. `touch`, which is backed by `pallet_assets::do_touch`, unconditionally fails with `Error::AlreadyExists` if an `Account` entry already exists for that asset/account pair [1](#0-0) . Because `new_account`'s address is fully computable in advance by anyone via `PoolLocator::address(pool_id)` [2](#0-1) , an attacker with no privileges can pre-fund that address with a dust amount of asset1/asset2/lp_token before the pool owner ever calls the migration extrinsic, causing the migration to permanently revert. This mirrors the structure of the reported PirexGmx bug: a permissionless precondition (`Account` must not already exist at the target) is defeated by an attacker who front-runs the migration by depositing into the future migration target, blocking state transition forever.

### Finding Description
`migrate_to_new_account` is a `Signed`, permissionless extrinsic [3](#0-2) . It computes `prior_account`/`new_account` purely from `pool_id` via `Self::addresses` and `T::PoolLocator::address` [2](#0-1)  — both are pure, public functions of the asset pair, so `new_account` is knowable to anyone before the migration extrinsic is ever dispatched.

For each of `asset1`, `asset2`, and the LP token, if the prior account held a deposit-backed existence reason (`AssetsRefund::deposit_held` returns `Some`), the code mints a compensating deposit and then calls:
```
T::Assets::touch(asset1.clone(), &new_account, &depositor)?;
``` [4](#0-3) 

`touch` is backed by `pallet_assets::Pallet::do_touch`, whose very first check is:
```
ensure!(!Account::<T, I>::contains_key(&id, &who), Error::<T, I>::AlreadyExists);
``` [1](#0-0) 

This check is unconditional — it does not distinguish "account was legitimately created for this migration" from "account already existed for some unrelated reason." Any signed account can create an `Account` entry for `asset1`/`asset2`/the LP token at `new_account` ahead of time — e.g. by giving `new_account` a native-balance provider reference (a plain existential-deposit transfer) and then transferring a small non-zero amount of the target asset to it, which creates an `Account<T,I>` entry under `ExistenceReason::Consumer` [5](#0-4) . This requires no privileged role, no governance, and only the attacker's own funds and normal `pallet-assets::transfer`/`balances::transfer` calls, which are explicitly listed as "Permissionless Functions" of `pallet-assets` [6](#0-5) .

Because `#[pallet::call]` dispatch is wrapped in an atomic storage transaction, the `Error::AlreadyExists` returned from `touch` aborts and rolls back the entire `migrate_to_new_account` call — no assets are moved. Since `new_account` is deterministic and does not get destroyed simply because a call reverted, the attacker's pre-created `Account` entry for that asset persists, and the migration can never succeed for that pool, permanently. The attacker only needs to do this once per pool that they wish to grief and does not even need to hold LP tokens or interact with the pool itself, unlike the underlying PirexGmx report which required the attacker to actually deposit/receive the tracked vester tokens.

### Impact Explanation
This blocks a legitimate, permissionless state-migration path (`migrate_to_new_account`) for any asset-conversion pool whose `asset1`/`asset2`/LP token was created with a deposit-backed ("non-sufficient") existence reason on the prior account — i.e., the common case where pool assets require a deposit rather than being self-sufficient. Once blocked, the pool's liquidity remains stuck at the legacy account-derivation address, and the pool can never be migrated to the corrected account-derivation scheme by this extrinsic. This is a griefing/DoS of a specific runtime migration utility rather than a direct fund theft, matching a Medium-severity classification analogous to the judged severity of the referenced report (`M-01`, Medium after judge review).

### Likelihood Explanation
Likelihood is high for any chain that ships `pallet-asset-conversion-ops` and needs to migrate any non-sufficient-asset pool: the target address is public and computable off-chain by anyone, the griefing transactions (fund `new_account` with ED, then a tiny asset transfer) are cheap, ordinary, permissionless operations, and the attack can be executed any time before, or repeated immediately after, an attempted (and failed) migration.

### Recommendation
- Before calling `T::Assets::touch`/`T::PoolAssets::touch` on `new_account`, check `AccountTouch::should_touch` (already part of the `AccountTouch` trait [7](#0-6) ) and skip the touch if the account already exists and is otherwise usable, or explicitly detect and handle the "account already exists but is not ours" case instead of failing the whole migration.
- Alternatively, have the migration verify that any pre-existing `Account` entry at `new_account` is empty/inert and reconcile it rather than aborting, or reserve/lock the `new_account` address at pool-creation time so it cannot be pre-seeded by third parties.
- Add a regression test analogous to the existing `cannot_block_pool_creation` test [8](#0-7)  but targeting `migrate_to_new_account`, asserting that pre-funding the computed `new_account` with dust of the pool's assets does not permanently block migration.

### Proof of Concept
I was not able to execute a test in this environment (read-only ask mode, no build/test tooling available), so this is a structural/code-path analysis rather than an executed reproduction. A concrete integration test to confirm this would extend `substrate/frame/asset-conversion/ops/src/tests.rs`:

1. Set up a pool with `asset1`/`asset2` created as non-sufficient (`is_sufficient = false`), matching the existing `migrate_pool_account_id_with_native`/`migrate_pool_account_id_with_insufficient_assets` setups [9](#0-8) [10](#0-9) , and add liquidity so `prior_account` holds a deposit-backed `Account` for at least one asset.
2. Before calling `migrate_to_new_account`, as an unrelated attacker account: compute `new_account = AssetConversionOps::addresses(&pool_id).1` (or `PoolLocator::address`), fund `new_account` with the native existential deposit, then call `Assets::transfer` (or `mint`, if permitted by the mock) of a small amount of `asset1`/`asset2` into `new_account`, creating an `Account<T,I>` entry there.
3. Call `AssetConversionOps::migrate_to_new_account(...)` and assert it now fails with `pallet_assets::Error::AlreadyExists` (propagated through the `?` on `T::Assets::touch(...)`), instead of the expected `Ok`.
4. Confirm the pool's balances remain stuck at `prior_account` and that retrying the migration continues to fail indefinitely (the attacker's `Account` entry is never removed by a failed/reverted call).

Failed guard: `pallet_assets::functions::do_touch`'s `ensure!(!Account::<T, I>::contains_key(&id, &who), Error::<T, I>::AlreadyExists)` [1](#0-0)  is the check an unprivileged attacker can trip by pre-creating the account, and `AssetConversionOps::migrate_to_new_account` calls `touch` unconditionally without first checking whether the pre-existing account is benign [4](#0-3) . I was unable to inspect the exact body of `pallet_assets`'s `AccountTouch` trait implementation (only located it via `grep`, not read in full) to confirm it does not internally special-case pre-existing accounts before delegating to `do_touch`; this should be verified in the background session before filing/fixing.

	pub(super) fn new_account(
		who: &T::AccountId,
		d: &mut AssetDetails<T::Balance, T::AccountId, DepositBalanceOf<T, I>>,
		maybe_deposit: Option<(&T::AccountId, DepositBalanceOf<T, I>)>,
	) -> Result<ExistenceReasonOf<T, I>, DispatchError> {
		let accounts = d.accounts.checked_add(1).ok_or(ArithmeticError::Overflow)?;
		let reason = if let Some((depositor, deposit)) = maybe_deposit {
			if depositor == who {
				ExistenceReason::DepositHeld(deposit)
			} else {
				ExistenceReason::DepositFrom(depositor.clone(), deposit)
			}
		} else if d.is_sufficient {
			frame_system::Pallet::<T>::inc_sufficients(who);
			d.sufficients.saturating_inc();
			ExistenceReason::Sufficient
		} else {
			frame_system::Pallet::<T>::inc_consumers(who)
				.map_err(|_| Error::<T, I>::UnavailableConsumer)?;
			// We ensure that we can still increment consumers once more because we could otherwise
			// allow accidental usage of all consumer references which could cause grief.
			if !frame_system::Pallet::<T>::can_inc_consumer(who) {
				frame_system::Pallet::<T>::dec_consumers(who);
				return Err(Error::<T, I>::UnavailableConsumer.into());
			}
			ExistenceReason::Consumer
		};
		d.accounts = accounts;
		Ok(reason)
	}

#[test]
fn cannot_block_pool_creation() {
	new_test_ext().execute_with(|| {
		// User 1 is the pool creator
		let user = 1;
		// User 2 is the attacker
		let attacker = 2;

		let ed = get_native_ed();
		assert_ok!(Balances::force_set_balance(RuntimeOrigin::root(), attacker, 10000 + ed));

		// The target pool the user wants to create is Native <=> WithId(2)
		let token_1 = NativeOrWithId::Native;
		let token_2 = NativeOrWithId::WithId(2);

		// Attacker computes the still non-existing pool account for the target pair
		let pool_account =
			<Test as Config>::PoolLocator::address(&(token_1.clone(), token_2.clone())).unwrap();
		// And transfers the ED to that pool account
		assert_ok!(Balances::transfer_allow_death(
			RuntimeOrigin::signed(attacker),
			pool_account,
			ed
		));
		// Then, the attacker creates 14 tokens and sends one of each to the pool account
		for i in 10..25 {
			create_tokens(attacker, vec![NativeOrWithId::WithId(i)]);
			assert_ok!(Assets::mint(RuntimeOrigin::signed(attacker), i, attacker, 1000));
			assert_ok!(Assets::transfer(RuntimeOrigin::signed(attacker), i, pool_account, 1));
		}

		// User can still create the pool
		create_tokens(user, vec![token_2.clone()]);
		assert_ok!(AssetConversion::create_pool(
			RuntimeOrigin::signed(user),
			Box::new(token_1.clone()),
			Box::new(token_2.clone())
		));

		// User has to transfer one WithId(2) token to the pool account (otherwise add_liquidity
		// will fail with `AssetTwoDepositDidNotMeetMinimum`)
		assert_ok!(Balances::force_set_balance(RuntimeOrigin::root(), user, 10000 + ed));
		assert_ok!(Assets::mint(RuntimeOrigin::signed(user), 2, user, 10000));
		assert_ok!(Assets::transfer(RuntimeOrigin::signed(user), 2, pool_account, 1));

		// add_liquidity shouldn't fail because of the number of consumers
		assert_ok!(AssetConversion::add_liquidity(
			RuntimeOrigin::signed(user),
			Box::new(token_1.clone()),
			Box::new(token_2.clone()),
			10000,
			100,
			10000,
			10,
			user,
		));
	});
}
