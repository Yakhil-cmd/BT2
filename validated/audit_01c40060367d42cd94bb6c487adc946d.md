The reported issue is that `PriceOracle.sol` depends on Chainlink's `FeedRegistry`, an external infrastructure contract that only exists on Ethereum mainnet, so the same code fails when deployed to Optimism/Arbitrum. This is a deployment/dependency-availability defect, not a logic flaw with attacker-controlled input violating an invariant — there is no signed extrinsic, XCM message, or contract call path involved, and no check that an attacker bypasses.

In `polkadot-sdk`, the closest analog is `pallet-oracle` (formerly Acala's Honzon oracle), which is a self-contained FRAME pallet: authorized operators call `feed_values` and the pallet aggregates/stores data directly in its own storage, with no dependency on an external chain-specific registry contract like Chainlink's `FeedRegistry`. [1](#0-0)  Its permission model is enforced via `T::Members::contains` / root origin checks in `ensure_account`, and there's no equivalent "registry must exist on this chain" precondition since the pallet is compiled directly into each runtime rather than calling out to a shared external contract. [2](#0-1) 

Because pallet-oracle (and other price-related FRAME code such as `pallet-broker`'s `sale_price` API or Snowbridge's ETH/DOT fee ratio) is deployed per-runtime with its own storage and doesn't rely on a single chain-specific external registry the way `FeedRegistry` does, there is no reachable Polkadot SDK analog to this cross-chain infrastructure-availability defect. [3](#0-2)  This finding class (dependency/config-only, no attacker-controlled violated check) is explicitly out of scope per the analog-search method.
