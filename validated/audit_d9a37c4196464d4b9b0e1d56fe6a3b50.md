### Title
Cross-org signature confusion allows forging `pull_request` `labeled` events that write attacker-chosen env vars into a victim's already-existing `ReviewStack` - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`, `app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects which `GitHubApp` config to use for HMAC verification based on `params.dig('repository','owner','login')`, but the actual repository the handlers act on is resolved from the independent, attacker-controlled field `params.repository.full_name`. If any org configured in Shipit has a blank `webhook_secret`, an attacker can set `repository.owner.login` to that org (bypassing signature verification entirely per `GitHubApp#verify_webhook_signature`'s `return true unless webhook_secret`) while setting `repository.full_name` to a victim repository under a different, secret-protected org. `LabelCapturingHandler` then persists attacker-chosen label names onto the victim's existing `ReviewStack`'s `PullRequest`, which `ReviewStack#env` turns into uppercased environment variables merged into the deploy environment.

### Finding Description
The claimed invariant is: `repository_owner used to select the verifying webhook_secret == repository identified by params.repository.full_name` (the repo whose config authenticated the request must be the repo that gets mutated). This does not hold.

- `verify_signature` computes `repository_owner` from `params.dig('repository','owner','login')` and picks the `GitHubApp` config via `Shipit.github(organization: repository_owner)`, then calls `verify_webhook_signature`: [1](#0-0) 
- `GitHubApp#verify_webhook_signature` returns `true` immediately when the resolved org's config has no `webhook_secret` configured: [2](#0-1) 
- Once verification passes, `WebhooksController#create` parses the raw body and dispatches to handlers using the entire JSON payload, unconstrained by which org "verified" it: [3](#0-2) 
- `LabelCapturingHandler` (and sibling handlers) resolve the acted-upon repository from `params.repository.full_name`, a field completely independent from `repository.owner.login`: [4](#0-3) 
- It then persists attacker-supplied label names onto the resolved stack's existing `PullRequest`, gated only by `stack.present? && !stack.archived?` — **not** by `review_stacks_enabled**: [5](#0-4) [6](#0-5) 
- `ReviewStack#env` converts those persisted label names into uppercased env vars merged into the deploy environment: [7](#0-6) 

Exploit request: attacker POSTs to `/webhooks` with `X-Github-Event: pull_request`, body `{"action":"labeled","number":<pr>,"pull_request":{...,"labels":[{"name":"<ATTACKER-ENV-PAYLOAD>"}]},"repository":{"owner":{"login":"no-secret-org"},"full_name":"victim-org/victim-repo"},"sender":{"login":"attacker"}}`. Because `no-secret-org` is configured in Shipit without a `webhook_secret`, `verify_signature` passes unconditionally regardless of the `X-Hub-Signature` header, yet the handler mutates the `victim-org/victim-repo` review stack.

**Correction to the question's premise:** the "review_stacks_enabled false provisioning precedence bug" is not required for this handler. `LabelCapturingHandler#capture_labels?` never checks `review_stacks_enabled` — it only requires that a `ReviewStack` already exists for that PR's environment and is not archived (`labeled_active_stack?` at line 62-64). Such a stack can pre-exist from before the setting was toggled off, or be created by `OpenedHandler`/other means. So the "provision? precedence bug" is not the mechanism enabling this — the actual root cause is purely the cross-field signature/target mismatch described above, applicable independent of `review_stacks_enabled`'s current value.

### Impact Explanation
An attacker who identifies (a) any org configured in Shipit with a blank `webhook_secret`, and (b) a victim repository with an existing, non-archived review stack, can inject arbitrary environment-variable names/values (uppercased label names → `"true"`) into that victim stack's deploy environment without ever authenticating against the victim org's actual secret. This is a payload for one repository (the no-secret org) mutating another repository's stack (`victim-org/victim-repo`), matching the Critical "payload for one repository mutating another's stack" class. Depending on what the injected env var name collides with (e.g., variables consumed unsanitized by deploy scripts/`Command`/`PTY.spawn`), this can escalate toward command/environment injection during deploy execution, though full RCE requires that the victim's deploy scripts trust/interpolate stack env vars in a dangerous way — that downstream step is outside `label_capturing_handler.rb` itself and not verified here.

### Likelihood Explanation
Requires: (1) at least one org configured in Shipit's multi-org GitHub App config without a `webhook_secret` (a real, documented misconfiguration risk given `verify_webhook_signature`'s blank-secret bypass), and (2) a target review stack already existing and unarchived for a real PR number in the victim repo. No GitHub App credentials, sessions, or API tokens are needed — only unauthenticated `POST /webhooks`. This is trivially repeatable for any PR number/environment on any repository once a single no-secret org exists in the Shipit config.

### Recommendation
Bind the field used for org/secret selection to the field used for repository resolution — verify that `params.repository.full_name`'s owner matches `repository_owner` used for signature selection, and reject events where the two orgs are inconsistent. Additionally, treat a blank `webhook_secret` as a hard misconfiguration (refuse to verify/accept, rather than silently returning `true`) in `GitHubApp#verify_webhook_signature`.

### Proof of Concept
Minitest under `test/controllers/webhooks_controller_test.rb` and/or `test/models/shipit/webhooks/handlers/pull_request/label_capturing_handler_test.rb`:
1. Configure two orgs in `Shipit.github_apps`/config: `"no-secret-org"` with `webhook_secret: nil`, and `"shopify"` (or the fixture org) with a real `webhook_secret`.
2. Create a `ReviewStack` under `shopify/shipit-engine` (fixture repo) via `OpenedHandler`, matching `create_stack` helper pattern in `label_capturing_handler_test.rb` lines 139-152.
3. Build a `pull_request` `labeled` payload where `repository.owner.login = "no-secret-org"` but `repository.full_name = "shopify/shipit-engine"`, with `labels: [{"name" => "INJECTED"}]`.
4. POST to `/webhooks` with `X-Github-Event: pull_request` and an arbitrary/garbage `X-Hub-Signature` header (or omitted).
5. Assert response is `200`/`204` (not `422`), and assert `stack.reload.pull_request.labels` includes `"INJECTED"`, and `stack.env["INJECTED"] == "true"` per `ReviewStack#env` (review_stack.rb lines 84-93) — proving the no-secret org's blank-secret bypass authenticated a mutation on the `shopify` org's stack.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
