### Title
Permissionless `update_account_threshold` lets any attacker stamp worsened risk parameters onto a victim's account, reverting in-flight transactions and freezing withdrawals - (File: contracts/controller/src/risk/params.rs)

### Summary

The H01 bug class is a griefing attack: an unprivileged caller consumes/invalidates state that an honest user's transaction depends on, causing that user's operation to revert while the attacker's own call "succeeds" at the reservation step. XOXNO Lending has a structurally identical shape in `Controller::update_account_threshold`, which is explicitly permissionless (`scripts/permissionless_entrypoints.txt`, [1](#0-0) ) and lets any authenticated caller rewrite a **victim's** stored `loan_to_value` (and, gated, liquidation tuple) to the current spoke config.

### Finding Description

`update_account_threshold(env, caller, has_risks, account_ids)` only requires `require_authorized_caller` on `caller` — there is no check that `caller` is the account owner or delegate ( [2](#0-1) ). For each `account_id` in `account_ids`, `sync_account_thresholds` loads the victim's supply positions and calls `refresh_supply_risk_params` ( [3](#0-2) ).

The critical asymmetry is in `refresh_supply_risk_params`: the LTV stamp `position.loan_to_value = effective_config.loan_to_value` is applied **unconditionally** in `LtvOnly` scope — with no health-factor gate and no solvency check ( [4](#0-3) ). Only the liquidation tuple (threshold, bonus, fees) is protected by the `favors_liquidator` + `clears_min_hf` gate ( [5](#0-4) ). The final `hf >= 1.05` assertion in `sync_account_thresholds` is also skipped entirely when `has_risks == false` ( [6](#0-5) ).

So whenever the stored LTV is stale relative to current config — e.g., after governance lowers a spoke asset's LTV via `edit_asset_in_spoke`, or when a position was created under a different effective config — an attacker can call `update_account_threshold(attacker, false, [victim_id])` and permanently write the worse LTV into the victim's `supply_positions`, exactly mirroring the H01 pattern of "reserve/consume state via a permissionless path so the victim's subsequent operation executes under invalidated assumptions."

Concretely, the victim's `get_ltv_collateral_usd` (LTV-weighted collateral, the borrowing limit per [7](#0-6) ) drops. Any in-flight or subsequent `borrow`, `withdraw`, `multiply`, `swap_collateral`, or `repay_debt_with_collateral` that was sized against the old LTV reverts; and since `min_borrow_collateral_usd` is an LTV-weighted floor enforced on "borrows, withdrawals and strategies" ( [8](#0-7) ), a sufficiently large LTV cut can push a leveraged victim below the floor, making their withdrawals revert until the position is deleveraged or params change.

### Impact Explanation

- **Griefing / transaction invalidation (direct H01 analog):** a victim's signed borrow/withdraw/strategy transaction computed against the pre-stamp LTV reverts once the attacker front-runs the restamp — the same "attacker's call succeeds, honest user's call now invalid" shape as the `userInteractionNumber` reservation.
- **Temporary freezing of funds:** pushing a victim below `min_borrow_collateral_usd` blocks their `withdraw` (the floor is enforced on withdrawals) until they repay debt or parameters move back — an accepted impact class.
- No direct theft: liquidation parameters remain HF-gated, so the attacker cannot force a liquidation solely through this path.

### Likelihood Explanation

The attack is costless to trigger (one permissionless call, batchable over many `account_ids` at once) and requires no capital. Its *harmfulness* depends on a precondition: stored LTV must be worse than what the victim relies on, which in practice follows an admin LTV reduction or config divergence. This is the main limiter — absent an LTV change, the call is a no-op (`changed == false`). Because the harmful stamp would eventually be applied by legitimate keepers anyway, the incremental damage is the *timing* wedge (front-running a victim's transaction) plus the floor-breach freeze. Medium severity at best; arguably Low if the floor-breach path is unreachable because the HF gate indirectly bounds LTV impact.

### Recommendation

- Gate `LtvOnly` restamps the same way the liquidation tuple is gated: skip writing a *lower* `loan_to_value` to a position if doing so would drop the account's LTV-weighted collateral below `min_borrow_collateral_usd` or below the value needed to cover open borrows.
- Alternatively, restrict `update_account_threshold` so that only the account owner/delegate (or a governance-approved keeper) can apply *worsening* parameter changes to an account, while leaving improving restamps permissionless.

### Proof of Concept

1. Admin lowers `loan_to_value` for spoke asset `A` via `edit_asset_in_spoke`.
2. Victim with existing supply in `A` submits `borrow(...)` sized at the old borrowing limit (or a `withdraw` that needs LTV-weighted collateral ≥ `min_borrow_collateral_usd`).
3. Attacker front-runs with `controller.update_account_threshold(attacker, false, [victim_id])`. `sync_account_thresholds` writes the reduced LTV into the victim's position with no solvency check (`refresh_supply_risk_params`, LtvOnly branch).
4. Victim's transaction reverts (insufficient LTV-weighted collateral / below floor). Repeated calls keep the victim frozen; attacker pays only fees.

Note: this conclusion is source-based; I did not execute a reproduction, and I could not fully verify the exact call site where `min_borrow_collateral_usd` is enforced on `withdraw` — that path should be confirmed before relying on the freezing impact over the weaker revert-only impact.

pub(crate) fn apply_gated_liquidation_params(
    env: &Env,
    cache: &mut Context,
    account: &Account,
    hub_asset: &HubAssetKey,
    position: &mut AccountPosition,
    effective_config: &AssetConfig,
) {
    if favors_liquidator(position, effective_config)
        && !account.debt_free()
        && !clears_min_hf(
            env,
            cache,
            account,
            hub_asset,
            position,
            effective_config.liquidation_threshold,
        )
    {
        return;
    }

    position.liquidation_threshold = effective_config.liquidation_threshold;
    position.liquidation_bonus = effective_config.liquidation_bonus;
    position.liquidation_fees = effective_config.liquidation_fees;
}

pub(crate) fn update_account_threshold(
    env: &Env,
    caller: Address,
    has_risks: bool,
    account_ids: Vec<u64>,
) {
    validation::require_authorized_caller(env, &caller);

    let scope = if has_risks {
        RiskRefreshScope::FullTuple
    } else {
        RiskRefreshScope::LtvOnly
    };

    let mut cache = Context::new(env);

    for account_id in account_ids {
        cache.reset_spoke_context();
        sync_account_thresholds(env, account_id, scope, &mut cache);
    }
}
