## Title
A single incompatible asset bundled into an AA's multi-asset payment response permanently blocks *all* payouts in that response - ([File: aa_composer.js])

### Summary
In `sendUnit()` inside `aa_composer.js`, an Autonomous Agent's response messages (which can contain several `payment` messages paying out different assets/tokens to different users in one trigger execution) are processed in a single `async.eachSeries` loop. Each non-base asset is resolved via `storage.loadAssetWithListOfAttestedAuthors`, and if resolution/validation fails for **any one** of the assets in the response, the callback returns an error which is propagated to `bounce(err)`, discarding the **entire** unit - including all other unrelated, otherwise-valid payment messages bundled in the same response. [1](#0-0) 

### Finding Description
This mirrors the reported `MultiRewards` bug class: a loop that pays out multiple tokens/assets to users, where a single bad element in the loop reverts (bounces) the whole operation. In ocore's AA engine, when an AA response contains multiple `payment` messages for different assets (e.g., paying users in several tokens at once, similar to a multi-reward vault), the composer loads each asset's definition and rejects the whole response if any single asset is invalid for AA-originated payments: [2](#0-1) 

Notably, if the asset is `is_private`, the code unconditionally fails with `"sending private asset from AA"`, because AAs structurally cannot produce the private spend-proofs required to send a private asset: [3](#0-2) 

Unlike token pausing in the ERC-20 analog (which can be temporary), an asset's `is_private` flag (and other properties like `fixed_denominations`, `issued_by_definer_only`, `cosigned_by_definer`) is set permanently at asset-definition time and can never change: [4](#0-3)  shows definition-time validation of asset flags, and assets are stored immutably once defined via `writer.js`'s asset insertion logic [5](#0-4) .

If an AA's oscript logic accepts a user/trigger-supplied asset identifier and subsequently always bundles a payment in that asset together with other legitimate payments in its response (a common pattern for AAs that let users register/attach their own asset, as seen in `futures_contract.oscript` and `uniswap_like_market_maker.oscript`, which pay out multiple different assets in the same response) [6](#0-5) , an attacker can register a **private** asset (or an asset causing `completePaymentPayload` to fail, e.g. no spendable outputs the AA can source it from). From that point forward, **every** trigger that causes the AA to compose a response including a payment in that asset will always `bounce()`, discarding not just the tainted payment but also any co-bundled legitimate payment to other unrelated users/assets in the same response - a persistent, unfixable-by-governance DoS, since the flawed asset property can never be corrected and the oscript typically has no logic to conditionally drop or skip a single failing payment message from the batch.

### Impact Explanation
High: once a malformed/private asset is baked into an AA's state (e.g., stored in a `var[]` and referenced unconditionally in future `messages` blocks), every AA response that must include a payment in that asset alongside other payments will permanently bounce, freezing legitimate payouts bundled with it. Because ocore asset properties (`is_private`, etc.) are immutable, there is no way to remove/replace the offending asset from the AA's logic without redeploying/migrating the AA - directly analogous to the original report's finding that there was no way to remove a bad reward token from `rewardTokens`.

### Likelihood Explanation
Medium: requires a specific AA design pattern - one that trusts a user/trigger-controlled asset ID and unconditionally bundles a payment in that asset with other payments in future responses (a fairly common DeFi-style pattern, e.g. multi-asset distribution/exchange AAs shown in the sample oscripts). An attacker only needs to define a `is_private:true` asset and get the AA to register it as a payout asset once.

### Recommendation
- In `sendUnit()`'s message loop, do not fail the entire batch when one payment message's asset is invalid; instead skip/drop only that specific message (already partially done for `fixed_denominations`, but not for `is_private`/other unrecoverable asset states) and continue processing the rest, similar to Infrared's adopted fix of skipping failing transfers.
- Encourage/require AA oscript patterns that validate asset properties (e.g., reject `is_private` assets) at the time a user-supplied asset is registered into persistent state, rather than only at payout time.
- Document/warn AA authors that asset properties are immutable and that AAs must validate any user-supplied asset before persisting it as a payout target.

### Proof of Concept
1. Attacker defines a private asset `X` (`is_private: true`) via a normal `asset` message.
2. Attacker sends a trigger to a vulnerable AA that accepts a user-chosen asset id in `trigger.data.asset` and stores it in `var[]` for future use as a payout asset (pattern seen in oscript samples that pay multiple assets in one response, e.g. `futures_contract.oscript`/`uniswap_like_market_maker.oscript`).
3. On a subsequent trigger (from the attacker or any other user) that causes the AA to build a response containing a payment message for asset `X` bundled together with a legitimate payment (e.g., base bytes) to another user, `sendUnit()`'s loop calls `storage.loadAssetWithListOfAttestedAuthors` for `X`, sees `objAsset.is_private === true`, and returns `"sending private asset from AA"` from the `async.eachSeries` callback.
4. `bounce(err)` is invoked, discarding the whole response - including the legitimate bundled payment to the innocent user - and this repeats for every future trigger that would produce this bundled response, permanently blocking payouts.
