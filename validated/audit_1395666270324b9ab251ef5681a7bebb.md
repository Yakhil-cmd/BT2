### Title
Webhook organization-signature binding is decoupled from the repository the payload actually targets, allowing cross-organization event forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub organization's `webhook_secret` to validate a webhook against using `repository.owner.login` from the *untrusted* JSON body, while every event `Handler` resolves the actual `Stack`/`Repository` to act on using a *different* field of the very same body, `repository.full_name`. Because these two fields are independent and both fully attacker-controlled when the request is crafted, an attacker who legitimately owns any GitHub organization/repository connected to this Shipit instance (and therefore knows that organization's `webhook_secret`, since they configured the GitHub App/webhook themselves) can compute a valid HMAC over a payload whose `repository.owner.login` matches their own org (satisfying signature verification) while `repository.full_name` names a completely different, victim-owned repository tracked by the same Shipit instance.

The binding that should hold is: `organization whose secret authenticated the request == organization that owns the repository being acted upon`. Because `repository_owner` (used only for HMAC-secret selection) and `repository_name`/`full_name` (used for the actual `Stack` lookup and mutation) are two independently-settable JSON fields inside the same HMAC-covered body, an attacker who knows *any* configured organization's `webhook_secret` can produce a validly-signed body for that organization while making the payload's `repository.full_name` point at a stack belonging to an entirely different, uninvolved organization also hosted on the same Shipit instance. Signature verification (`OpenSSL::HMAC` over `request.raw_post`) only proves the sender knew *some* org's secret — it says nothing about which repository the enclosed content is entitled to reference.

### Impact Explanation
This breaks the "organization authenticated versus the repository that is written" trust binding called out as an analog target: a party with no relationship to a victim's repository can inject spoofed GitHub events (`push`, `status`, `check_suite`, etc.) that Shipit will process as if they came from the victim's own GitHub organization, as long as the attacker administers any other org configured on the same multi-tenant Shipit deployment (documented and supported via `config/secrets*.yml` multi-org github config, see `test/dummy/config/secrets_double_github_app.yml`). This can drive `GithubSyncJob`, `RefreshCheckRunsJob`, and other state-changing background jobs against a stack the attacker does not own or have write access to, using attacker-chosen SHAs/status payloads — corrupting the victim stack's tracked commit/CI state and downstream automation (merge-queue/continuous-deployment decisions) that key off that state, without ever needing the victim's `webhook_secret`, an `ApiClient` token, or repository access.

### Likelihood Explanation
Likelihood is realistic in any multi-tenant Shipit deployment (the documented, supported configuration format supports multiple `github:` organizations each with its own `webhook_secret`). Any attacker who is themselves an administrator of one of the configured organizations — a routine, unprivileged position relative to *other* tenants' repositories — can exploit this without any additional access.

### Recommendation
Bind the signature-selection organization to the resolved repository before any handler acts: after verifying the signature, re-derive `repository_name`/`full_name` and assert that its owner matches `repository_owner` (the same field used to pick the `webhook_secret`), rejecting the request (422) on mismatch. Alternatively, resolve the target `Repository`/`Stack` first from a trusted mapping (installation ID → allowed repositories) rather than trusting arbitrary fields inside the unauthenticated-until-verified JSON body.

### Proof of Concept
1. Attacker configures/owns GitHub org `attacker-org`, installed on the shared Shipit instance with its own `webhook_secret` (`S_attacker`), as supported by the multi-org config format (`test/dummy/config/secrets_double_github_app.yml`).
2. Attacker crafts a `push` payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(S_attacker, body)` themselves and POSTs directly to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")` and validates successfully because the attacker knows `S_attacker`. [1](#0-0) 
5. `PushHandler` resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim's stack, which the attacker neither owns nor has any credentials for. [5](#0-4)
