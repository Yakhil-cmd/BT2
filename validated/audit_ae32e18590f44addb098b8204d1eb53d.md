Confirmed: `Handler#stacks` resolves the target `Repository`/`Stack` using `payload.dig('repository', 'full_name')` [1](#0-0) , while `WebhooksController#verify_signature` selects which GitHub App/secret to verify against using `params.dig('repository', 'owner', 'login')` [2](#0-1) [3](#0-2) . These are two different sub-fields of the same untrusted JSON body, and nothing enforces that `repository.full_name`'s owner segment matches `repository.owner.login`.

### Title
Webhook organization used for signature verification is decoupled from the repository written to, allowing cross-organization webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In a multi-organization Shipit deployment (the `github: { orgA: {...}, orgB: {...} }` config form documented in `docs/setup.md`), `WebhooksController#verify_signature` picks the `GitHubApp`/`webhook_secret` to verify the request against based on `repository.owner.login` in the JSON body, but the actual `Repository`/`Stack` that the event handler mutates is resolved from the separate `repository.full_name` field. An attacker who legitimately controls a GitHub App installation for Org A (and thus knows Org A's `webhook_secret`, which they set themselves at app-creation time) can send a signed webhook whose `repository.owner.login` is `"orgA"` (so it validates against the secret they know) but whose `repository.full_name` is `"orgB/victim-repo"`, causing the payload to be processed as if it came from Org B.

### Finding Description
`verify_signature` computes `repository_owner` from the payload and fetches `Shipit.github(organization: repository_owner)` to obtain the webhook secret used for HMAC verification:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [3](#0-2) 
This same raw body is later handed unmodified to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` in `create` [4](#0-3) . Every `Handler` subclass resolves the repository/stack to act on via `payload.dig('repository', 'full_name')` [5](#0-4) , a field the signature check never inspects. Because the HMAC (`verify_webhook_signature` in `lib/shipit/github_app.rb`, lines 76-83) is computed correctly over the full raw body, the signature is valid — it just doesn't prove the `owner.login` and `full_name` fields are internally consistent, and the two fields are used for two different trust decisions (which secret to trust vs. which repository to act on).

### Impact Explanation
Any actor who owns/administers a GitHub App installation for one organization onboarded onto a shared Shipit instance (multi-org config) can forge push/status/deploy/pull_request webhooks that are attributed to any *other* onboarded organization's repositories, since they control that field independently of the signature-selection field. Depending on the handler (e.g. push handler enqueuing `GithubSyncJob`, status handler updating commit statuses used for deploy gating), this can influence sync state and commit statuses of a stack belonging to a repository the attacker has no legitimate access to — a cross-repository write.

### Likelihood Explanation
Requires a multi-organization Shipit deployment where the attacker legitimately controls the GitHub App/webhook secret for at least one onboarded organization — a configuration explicitly documented and supported (`docs/setup.md`, "Using Multiple GitHub Applications"). No stolen credentials, GitHub session, or Shipit account is needed beyond that.

### Recommendation
In `Handler#repository_name` / `stacks`, also verify that `payload.dig('repository', 'owner', 'login')` matches the owner segment of `payload.dig('repository', 'full_name')`, and reject/ignore the event otherwise; or better, have `verify_signature` derive the app/secret to check from the full repository ownership context that handlers use, not a separately-parsed sub-field.

### Proof of Concept
1. Deploy Shipit with multi-org config containing `orgA` (attacker-controlled app, known `webhook_secret_A`) and `orgB` (victim org with stacks in Shipit).
2. Craft payload: `{"repository": {"owner": {"login": "orgA"}, "full_name": "orgB/victim-repo"}, "after": "<arbitrary sha>", ...}`.
3. Sign the raw body with `webhook_secret_A` using HMAC-SHA1 as `X-Hub-Signature`, POST to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner == "orgA"`, verifies successfully against `webhook_secret_A`.
5. `create` dispatches to the push handler, which resolves the target via `full_name == "orgB/victim-repo"`, enqueuing a `GithubSyncJob`/updating state for the victim's stack.
