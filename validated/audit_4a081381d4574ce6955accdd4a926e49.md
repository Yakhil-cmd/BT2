### Title
`WalletContract` `has_in_flight_tx` re-entrancy-style guard can get permanently stuck at `true`, freezing the wallet forever - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
`WalletContract::rlp_execute` uses a manually-maintained boolean flag, `has_in_flight_tx`, to guarantee only one Ethereum-emulated transaction is "in flight" at a time, exactly like the Buyout contract's `State.LIVE` guard that only clears on completion of a promise chain. Every private callback (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, `ban_relayer`) resets the flag to `false` as its very first statement, and re-sets it to `true` if it schedules another promise. Because NEAR rolls back *all* state writes of a receipt when that receipt fails, any panic/`OutOfGas` occurring later in one of these callback functions discards the `has_in_flight_tx = false` write as well, leaving the flag stuck at `true` with no other code path in the contract able to clear it.

### Finding Description
`WalletContract` documents the invariant explicitly: [1](#0-0) 

`rlp_execute` refuses to start a new transaction while the flag is `true`: [2](#0-1) 

The flag is cleared as the first line of every callback, and re-armed only if a subsequent promise is scheduled: [3](#0-2) [4](#0-3) 

`nep_141_storage_balance_callback`'s gas budget for its own logic is fixed plus the user-controlled `action.gas()`, and it must build one or two `Promise::function_call` batch actions whose cost scales with the (attacker/user controlled) `method_name`/`args` byte length before it can finish and commit the `false` reset: [5](#0-4) [6](#0-5) 

Per nearcore's own runtime documentation, when a receipt's execution fails, all state changes made by that receipt (including the `has_in_flight_tx = false` write made as the first line of the function) are rolled back: [7](#0-6) 

Because these callback methods are `#[private]`, no external account can invoke them directly to fix the flag, and there is no other method in the contract that ever writes `has_in_flight_tx`. If any one of these callback receipts fails outright (e.g. `OutOfGas`, or any future panic introduced in that code path) rather than returning a controlled `ExecuteResponse{ success: false, .. }`, the flag reverts to (or remains) `true` permanently, and `rlp_execute` will reject every future transaction with `"transaction already in progress, please try again later."` forever — this exactly mirrors the reported Buyout bug where the `LIVE` state could never return to `INACTIVE`.

### Impact Explanation
Once `has_in_flight_tx` gets stuck at `true`, the affected `WalletContract` (an eth-implicit account) becomes permanently unusable: `rlp_execute` — the sole entry point for the account owner to move funds or interact with other contracts — will unconditionally reject every future transaction. Since the wallet is an eth-implicit account with no other privileged recovery mechanism in this contract, any $NEAR or token balances controlled by that address become permanently inaccessible through the wallet-contract protocol. This is a concrete asset-lock/DoS analogous to the vault being permanently unable to reach `INACTIVE` in the original report, reachable purely by an ordinary user/relayer submitting a transaction through `rlp_execute` — no validator or node privilege required.

### Likelihood Explanation
Reaching this requires only that one of the scheduled callback receipts fail outright instead of gracefully returning an `ExecuteResponse::success = false`. The `nep_141_storage_balance_callback` and `address_check_callback` paths construct new promise batch actions (whose gas cost scales with attacker/user-influenced `method_name`/`args` sizes and `receiver_id` length) inside a fixed gas budget (`NEP_141_STORAGE_BALANCE_CALLBACK_GAS`/`ADDRESS_CHECK_CALLBACK_GAS` plus user-supplied `action.gas()`), making an `OutOfGas` failure plausible if `action.gas()` is set very low relative to the constructed action's size. This does not require a malicious validator, network manipulation, or any privileged role — only a single crafted RLP transaction routed through `rlp_execute`.

### Recommendation
- Never let the "in-flight" flag reset rely on state written inside the same receipt that can still fail after the reset; instead, persist a durable transaction-id/state that is idempotently recoverable, or explicitly split gas so no user-controlled parameter (`action.gas()`, `args` length, `method_name` length) can push the callback's *own* bookkeeping logic beyond its guaranteed gas budget.
- Add a dedicated, permissionless "unstick" mechanism (e.g., a timeout-based force-reset of `has_in_flight_tx`, similar to NEAR's own `promise_yield`/timeout resume pattern) so a stuck flag can be recovered without requiring the original promise chain to succeed.
- Ensure every scheduled callback reserves enough gas headroom independent of user-supplied `action.gas()`/payload sizes, and add tests that specifically induce `OutOfGas` inside `nep_141_storage_balance_callback`/`address_check_callback` to confirm `has_in_flight_tx` cannot become permanently stuck.

### Proof of Concept
1. Attacker/user signs an Ethereum transaction (via `rlp_execute`) representing a `TransactionKind::EthEmulation(EthEmulationKind::ERC20Transfer)` with `receiver_id` unregistered for the token, a very large `method_name`/`args` in the underlying `FunctionCall` action, and `action.gas()` set to a small value.
2. `rlp_execute` succeeds, sets `has_in_flight_tx = true`, and schedules `storage_balance_of` followed by `.then(nep_141_storage_balance_callback(...))` with gas `NEP_141_STORAGE_BALANCE_CALLBACK_GAS + action.gas()`. [8](#0-7) 
3. The `storage_balance_of` call returns `None` (receiver not registered), so `nep_141_storage_balance_callback` must build two `function_call` batch actions using the large `method_name`/`args`, whose host-function gas cost is proportional to their byte length. [9](#0-8) 
4. If the constructed actions' cost exceeds the callback's fixed gas budget, the callback receipt fails with `OutOfGas`; per NEAR's rollback semantics this discards the `self.has_in_flight_tx = false;` write from line 202 as well as everything else done in that receipt. [10](#0-9) 
5. `has_in_flight_tx` remains permanently `true`; every subsequent `rlp_execute` call is rejected with `"transaction already in progress, please try again later."`, permanently freezing the wallet, exactly as the Buyout `State.LIVE` flag could never revert to `INACTIVE`. [11](#0-10)

    #[payable]
    pub fn rlp_execute(
        &mut self,
        target: AccountId,
        tx_bytes_b64: String,
    ) -> PromiseOrValue<ExecuteResponse> {
        // To ensure user actions are executed in the desired order,
        // having multiple transactions in flight at the same time is
        // not allowed.
        if self.has_in_flight_tx {
            return PromiseOrValue::Value(ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(
                    "Error: transaction already in progress, please try again later.".into(),
                ),
            });
        }
        let current_account_id = env::current_account_id();
        let predecessor_account_id = env::predecessor_account_id();
        let result = inner_rlp_execute(
            current_account_id.clone(),
            predecessor_account_id,
            target,
            tx_bytes_b64,
            &mut self.nonce,
        );

        match result {
            Ok(promise) => {
                self.has_in_flight_tx = true;
                PromiseOrValue::Promise(promise)
            }
            Err(Error::Relayer(_)) if env::signer_account_id() == current_account_id => {
                let promise = create_ban_relayer_promise(current_account_id);
                self.has_in_flight_tx = true;
                PromiseOrValue::Promise(promise)
            }
            Err(e) => PromiseOrValue::Value(e.into()),
        }
    }

    #[private]
    pub fn nep_141_storage_balance_callback(
        &mut self,
        token_id: AccountId,
        receiver_id: AccountId,
        action: near_action::Action,
        caller_deposit: Option<CallerDeposit>,
    ) -> PromiseOrValue<ExecuteResponse> {
        self.has_in_flight_tx = false;
        let maybe_storage_balance: Option<StorageBalance> = match env::promise_result(0) {
            PromiseResult::Failed => {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some(format!("Call to NEP-141 {token_id}::storage_balance_of failed")),
                });
            }
            PromiseResult::Successful(value) => match serde_json::from_slice(&value) {
                Ok(x) => x,
                Err(_) => {
                    return PromiseOrValue::Value(ExecuteResponse {
                        success: false,
                        success_value: None,
                        error: Some("Unexpected response from NEP-141 storage_balance_of".into()),
                    });
                }
            },
        };
        let current_account_id = env::current_account_id();
        let ext = WalletContract::ext(current_account_id).with_static_gas(RLP_EXECUTE_CALLBACK_GAS);
        let promise = match maybe_storage_balance {
            Some(_) => {
                // receiver_id is registered so we can send the transfer
                // without additional actions. Note: in the standard NEP-141
                // implementation it is impossible to have `Some` storage balance,
                // but have it be insufficient to transact.
                match action_to_promise(token_id, action)
                    .map(|p| p.then(ext.rlp_execute_callback(caller_deposit)))
                {
                    Ok(p) => p,
                    Err(e) => {
                        return PromiseOrValue::Value(e.into());
                    }
                }
            }
            None => {
                // receiver_id is not registered so we must call `storage_deposit` first.
                let storage_deposit_args =
                    format!(r#"{{"account_id": "{receiver_id}"}}"#).into_bytes();
                let transfer_function_call = match action {
                    near_action::Action::FunctionCall(x) => x,
                    _ => {
                        return PromiseOrValue::Value(ExecuteResponse {
                            success: false,
                            success_value: None,
                            error: Some(
                                "Expected function call action to perform NEP-141 transfer".into(),
                            ),
                        });
                    }
                };
                Promise::new(token_id)
                    .function_call(
                        "storage_deposit".into(),
                        storage_deposit_args,
                        NEP_141_STORAGE_DEPOSIT_AMOUNT,
                        NEP_141_STORAGE_DEPOSIT_GAS,
                    )
                    .function_call(
                        transfer_function_call.method_name,
                        transfer_function_call.args,
                        transfer_function_call.deposit,
                        transfer_function_call.gas,
                    )
                    .then(ext.rlp_execute_callback(caller_deposit))
            }
        };
        self.has_in_flight_tx = true;
        PromiseOrValue::Promise(promise)
    }

    pub fn rlp_execute_callback(
        &mut self,
        caller_deposit: Option<CallerDeposit>,
    ) -> ExecuteResponse {
        self.has_in_flight_tx = false;
        let n = env::promise_results_count();

        if n == 0 {
            // `rlp_execute_callback` is called directly in the case of an emulated self-transfer.
            return ExecuteResponse { success: true, success_value: None, error: None };
        } else if n > 1 {
            return ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(format!(
                    "Invariant violation: this callback comes after a single promise. n={n}"
                )),
            };
        }

        match env::promise_result(0) {
            PromiseResult::Failed => {
                // The cross-contract call failed, refund the caller if needed
                if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
                    let refund_promise = env::promise_batch_create(&account_id);
                    env::promise_batch_action_transfer(
                        refund_promise,
                        NearToken::from_yoctonear(yocto_near.into()),
                    );
                }

                ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Failed Near promise".into()),
                }
            }
            PromiseResult::Successful(value) => {
                ExecuteResponse { success: true, success_value: Some(value), error: None }
            }
        }
    }

    #[private]
    pub fn ban_relayer(&mut self) -> ExecuteResponse {
        self.has_in_flight_tx = false;
        ExecuteResponse {
            success: false,
            success_value: None,
            error: Some("Error: faulty relayer".into()),
        }
    }
