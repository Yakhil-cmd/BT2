### Title
Zero-fee `AmmConfig`/pool configuration permanently bricks `swap_base_input`/`swap_base_output` via a hidden zero-denominator revert in `Fees::split_creator_fee` - (File: `programs/cp-swap/src/curve/fees.rs`)

### Summary
`AmmConfig.trade_fee_rate` and `AmmConfig.creator_fee_rate` (and the pool's `enable_creator_fee`/`creator_fee_on` flags) can be set to values that make `trade_fee_rate + creator_fee_rate == 0` for a given trade direction. When that happens, `Fees::split_creator_fee` divides by this zero sum, its guard returns `None` instead of panicking, and that `None` propagates all the way up through `CurveCalculator::swap_base_input`/`swap_base_output` into the `swap_base_input`/`swap_base_output` instructions, which then always revert with `ErrorCode::ZeroTradingTokens`. Every unprivileged swapper is permanently unable to trade in the affected direction until the admin changes the configuration again — the same "legitimate value causes hidden division causing permanent instruction revert" bug class as the reference report.

### Finding Description
`Fees::split_creator_fee` divides `total_fee` by `trade_fee_rate + creator_fee_rate`: [1](#0-0) 

The `floor_div` helper it calls explicitly guards against a zero denominator by returning `None` rather than panicking: [2](#0-1) 

`CurveCalculator::swap_base_input` and `swap_base_output` call `split_creator_fee` unconditionally whenever `is_creator_fee_on_input` is true, and propagate `None` via `?`: [3](#0-2) [4](#0-3) 

The instructions `swap_base_input`/`swap_base_output` then turn that `None` into a hard revert on every single call: [5](#0-4) [6](#0-5) 

Nothing prevents `trade_fee_rate + creator_fee_rate` from reaching zero. `create_amm_config` and `update_amm_config`'s helper setters only require the sum to be **strictly less than** `FEE_RATE_DENOMINATOR_VALUE`, never that it be greater than zero: [7](#0-6) [8](#0-7) 

There is a second, easier trigger path: `PoolState.adjust_creator_fee_rate` unconditionally zeroes the creator fee rate whenever `enable_creator_fee` is false, independent of `AmmConfig.creator_fee_rate`: [9](#0-8) 

But `is_creator_fee_on_input` (which determines whether `split_creator_fee` is even invoked) is derived only from `PoolState.creator_fee_on`, not from `enable_creator_fee`: [10](#0-9) 

So a pool where `creator_fee_on` marks a direction as "on input" but `enable_creator_fee = false`, combined with an `AmmConfig.trade_fee_rate = 0` (a fully valid, non-malicious "fee-free pool" configuration allowed by the checks above), causes `trade_fee_rate(0) + creator_fee_rate(0) = 0` for every swap in that direction — hitting the zero-denominator branch on every single call.

### Impact Explanation
Once this configuration state is reached, `swap_base_input` and `swap_base_output` for the affected trade direction (and both directions if `creator_fee_on == BothToken`) will **always** return `ErrorCode::ZeroTradingTokens` and revert, for every unprivileged user, permanently, until an admin manually raises `trade_fee_rate` (or `creator_fee_rate`) again. This is a full denial of service of the pool's core swap functionality — the same impact class (division-by-zero-triggered permanent revert of a core function) that the reference finding rates Medium.

### Likelihood Explanation
Reaching `trade_fee_rate = 0` requires no special validation bypass — it is explicitly a value the admin setters accept (`assert!(... < FEE_RATE_DENOMINATOR_VALUE)` allows 0). A zero trading fee is a plausible, non-malicious business decision (e.g., a promotional fee-free pool), and `enable_creator_fee = false` combined with a nonzero `creator_fee_on` setting is also a plausible configuration state a pool creator could set without realizing the interaction. The bug is triggered purely by configuration state, not by any attacker-controlled swap parameters, and is deterministic once triggered.

### Recommendation
- In `create_amm_config`/`update_amm_config` (and wherever `enable_creator_fee`/`creator_fee_on` are set), add a check that `trade_fee_rate + creator_fee_rate > 0` whenever the pool's configuration implies `split_creator_fee` will be invoked (i.e., whenever a direction can have `is_creator_fee_on_input == true`).
- Alternatively, short-circuit in `CurveCalculator::swap_base_input`/`swap_base_output`: only call `Fees::split_creator_fee` when `trade_fee_rate + creator_fee_rate > 0`, and treat the `total_fee == 0` case (or zero denominator) as `creator_fee = 0, trade_fee = 0` instead of propagating `None`.

### Proof of Concept
1. Admin calls `create_amm_config` (or `update_amm_config` with `param = 0`) to set `trade_fee_rate = 0` on an `AmmConfig`, which is accepted because the only check is `trade_fee_rate + creator_fee_rate < FEE_RATE_DENOMINATOR_VALUE` [11](#0-10) .
2. A pool is initialized against this config with `enable_creator_fee = false` and `creator_fee_on` set such that `is_creator_fee_on_input` is `true` for `ZeroForOne` (or `BothToken`) [10](#0-9) .
3. Any unprivileged user calls `swap_base_input`; `adjust_creator_fee_rate` returns `0` for `creator_fee_rate` because `enable_creator_fee` is false [9](#0-8) .
4. Inside `CurveCalculator::swap_base_input`, `is_creator_fee_on_input` is true, so `Fees::split_creator_fee(total_fee, 0, 0)` is invoked; `floor_div` sees `fee_denominator == 0` and returns `None` [2](#0-1) .
5. The `?` operator in `swap_base_input` calculator function propagates `None`, and the instruction handler converts it into `err!(ErrorCode::ZeroTradingTokens)`, reverting the transaction [12](#0-11) . This repeats for every subsequent swap attempt in that direction, regardless of amount, permanently.

pub fn floor_div(token_amount: u128, fee_numerator: u128, fee_denominator: u128) -> Option<u128> {

    }

}
