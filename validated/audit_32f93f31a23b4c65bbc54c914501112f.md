### Title
Stale `is_spent` flag on outputs cascaded to `final-bad` freezes unrelated stable balances - (File: main_chain.js)

### Summary
`propagateFinalBad()` in `markMcIndexStable()` marks a spending unit `final-bad` and clears `inputs.is_unique`, but never reverts `outputs.is_spent` on the source outputs that unit consumed. Just like the Mantle oracle counted a withdrawal as "reward" because the validator's `WithdrawalDone` status hadn't yet caught up with the actual withdrawal event, ocore leaves an output's `is_spent=1` status set even after the unit that "spent" it is retroactively invalidated — the flag lags behind the true state of the DAG.

### Finding Description
When "spend unconfirmed" is allowed (`constants.spendUnconfirmedUpgradeMci`), a unit may spend an output of an unstable-but-`good` ancestor and inherit that ancestor's sequence [1](#0-0) . At write time, `writer.js` unconditionally sets `outputs.is_spent=1` for every transfer input, independent of whether the spending unit will ultimately be confirmed `good` [2](#0-1) .

Later, during stabilization, if an ancestor unit becomes `final-bad`, `propagateFinalBad()` cascades `final-bad` status to every unit that spent that ancestor's outputs, clears their `inputs.is_unique`, but **does not** reset `outputs.is_spent` back to `0` for the outputs those cascaded-bad units consumed [3](#0-2) . Only when a `final-bad` unit later ages past `min_retrievable_mci` and gets archived/stripped does `archiving.js` finally issue the compensating `UPDATE outputs SET is_spent=0 ...` via `generateQueriesToUnspendTransferOutputsSpentInArchivedUnit()` [4](#0-3) . Between the moment a unit is cascaded to `final-bad` and the moment it is voided, its source outputs remain incorrectly flagged as spent.

This is exactly the analog to the Mantle bug: a boolean/status field (`is_spent`, analogous to `WithdrawalDone`) is treated as authoritative for classification (spendable vs. not) even though the authoritative event (the input's `sequence`/`is_unique`) has already changed and the flag has not been synchronized. The repository itself documents this exact discrepancy in a diagnostic tool: `tools/compare_vote_balances.js` explicitly compares an "OLD" balance calculation (`is_spent=0 AND ... sequence='good'`) against a "NEW" one (`NOT EXISTS` a good, stable spender) and states: *"A difference means the OLD method undercounts a voter's balance because a future unstable unit spent their stable output and was later propagated to final-bad, leaving is_spent=1 on the output while no good unit claims it in spent_rows"* [5](#0-4) .

### Impact Explanation
Because outputs are freely spendable by whoever they were paid to, the propagation is not limited to the original double-spender's own coins: `propagateFinalBad` looks for *any* unit (regardless of author) that later spent an output produced by the newly-final-bad unit [6](#0-5) . A completely uninvolved third party who receives an unconfirmed payment and immediately re-spends it together with their own unrelated, already-stable coins (a normal wallet behavior once "spend unconfirmed" is enabled) can have their own legitimate stable outputs marked `is_spent=1` and effectively frozen — unspendable by coin-selection logic that filters on `is_spent=0` (`inputs.js`, `indivisible_asset.js`, `balances.js`, `wallet.js`) — until the poisoned unit eventually ages out and is archived/voided. This is a concrete fund-freezing condition and a wallet/balance-accounting divergence reachable by an ordinary unprivileged unit poster via a simple double-spend, matching the "AA fund loss or freezing" / "node disagreement on validity" impact classes.

### Likelihood Explanation
Triggering requires only: (1) posting a unit, (2) creating a conflicting double-spend of one of its outputs so the branch eventually resolves `final-bad`, and (3) having a third party (or the attacker themselves) spend the doomed unit's output together with other coins before the conflict resolves — all of which are ordinary, permissionless wallet operations once "spend unconfirmed" transactions are allowed. No privileged role, hub, or network-level compromise is needed, making this readily reachable by any unit poster.

### Recommendation
When `propagateFinalBad()` (and any other path that flips a unit to `final-bad`) processes a cascaded-bad unit, immediately issue the same `UPDATE outputs SET is_spent=0 WHERE unit=? AND message_index=? AND output_index=?` (and the equivalent for `headers_commission_outputs`/`witnessing_outputs`) that `archiving.generateQueriesToUnspendOutputsSpentInArchivedUnit` performs at void time, rather than deferring the unspend until the unit is later stripped. This keeps `is_spent` synchronized with `sequence`/`is_unique` at the moment finality is determined, eliminating the window in which a genuinely unspent, stable-good output is unusable.

### Proof of Concept
1. Address `A` posts unit `U1` with output `O1` paid to `A` itself (or anyone).
2. `A` double-spends the same input in two competing units `U1a`/`U1b`; assume `U1a` will eventually resolve `good`, `U1b` `final-bad`.
3. Before finality is resolved, victim `V` receives `U1b`'s output `O2` and (with "spend unconfirmed" enabled) immediately composes a new unit `U2` spending `O2` together with `V`'s own unrelated, already-stable output `O3`. `writer.js` sets `is_spent=1` on both `O2` and `O3` at save time [2](#0-1) .
4. When the DAG stabilizes and `U1b` is determined `final-bad`, `markMcIndexStable`→`propagateFinalBad` cascades `U2` to `final-bad` too (since `U2` spent `U1b`'s output) and clears `inputs.is_unique`, but leaves `outputs.is_spent=1` on `O3` [7](#0-6) .
5. `V`'s `O3` — a perfectly valid, stable, `good` output never actually consumed by any surviving unit — is now unspendable by `V`'s wallet (coin selection filters `is_spent=0`) until `U2` eventually ages past `min_retrievable_mci` and gets archived/voided, at which point `generateQueriesToUnspendTransferOutputsSpentInArchivedUnit` finally resets `is_spent=0` [4](#0-3) . In the interim, `V`'s funds are frozen, and any balance query using the `is_spent`-based method (as the repo's own `tools/compare_vote_balances.js` demonstrates) undercounts `V`'s real balance [8](#0-7) .

function generateQueriesToUnspendTransferOutputsSpentInArchivedUnit(conn, unit, arrQueries, cb){
	conn.query(
		"SELECT src_unit, src_message_index, src_output_index \n\
		FROM inputs \n\
		WHERE inputs.unit=? \n\
			AND inputs.type='transfer' \n\
			AND NOT EXISTS ( \n\
				SELECT 1 FROM inputs AS alt_inputs \n\
				WHERE inputs.src_unit=alt_inputs.src_unit \n\
					AND inputs.src_message_index=alt_inputs.src_message_index \n\
					AND inputs.src_output_index=alt_inputs.src_output_index \n\
					AND alt_inputs.type='transfer' \n\
					AND inputs.unit!=alt_inputs.unit \n\
			)",
		[unit],
		function(rows){
			rows.forEach(function(row){
				conn.addQuery(
					arrQueries, 
					"UPDATE outputs SET is_spent=0 WHERE unit=? AND message_index=? AND output_index=?", 
					[row.src_unit, row.src_message_index, row.src_output_index]
				);
			});
			cb();
		}
	);
}

async function balancesOldWay(addresses) {
	const strAddresses = addresses.map(db.escape).join(', ');

	const bal_rows = await db.query(`
		SELECT address, SUM(amount) AS balance
		FROM outputs
		LEFT JOIN units USING(unit)
		WHERE address IN(${strAddresses}) AND is_spent=0 AND asset IS NULL AND is_stable=1 AND sequence='good'
		GROUP BY address`);

	const balances = {};
	for (const { address, balance } of bal_rows)
		balances[address] = balance || 0;

	const spent_rows = await db.query(`
		SELECT inputs.address, SUM(outputs.amount) AS spent_balance
		FROM units
		CROSS JOIN inputs USING(unit)
		CROSS JOIN outputs ON src_unit=outputs.unit AND src_message_index=outputs.message_index AND src_output_index=outputs.output_index
		CROSS JOIN units AS output_units ON outputs.unit=output_units.unit
		WHERE units.is_stable=0 AND +units.sequence='good'
			AND +output_units.is_stable=1 AND +output_units.sequence='good'
			AND inputs.address IN(${strAddresses}) AND type='transfer' AND inputs.asset IS NULL
		GROUP BY inputs.address`);

	for (const { address, spent_balance } of spent_rows) {
		if (balances[address])
			balances[address] += spent_balance;
		else
			balances[address] = spent_balance;
	}

	return balances;
}
