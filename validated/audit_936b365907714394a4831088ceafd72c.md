### Title
Reusable L1 Bitcoin lockup proof allows the same locked sats to be credited to multiple bond registrations - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
`verify-l1-lockups` / `validate-l1-lockup` in `pox-5.clar` deduplicate Bitcoin lockup outpoints only *within a single call* via a locally-initialized `seen-outpoints` accumulator, and there is no persistent, contract-level map recording which L1 `(txid, output-index)` pairs have already been credited to a staker's sats total. This lets the same on-chain BTC lockup transaction be re-submitted in a separate `register-for-bond` (or equivalent rollover) call — e.g. for a different `bond-index` — to credit the identical locked sats a second time toward `total-shares-staked-for-cycle`, without any additional BTC ever being locked.

### Finding Description
`verify-l1-lockups` initializes the duplicate-tracking accumulator fresh on every invocation: [1](#0-0) 

and `validate-l1-lockup` only rejects duplicates it finds inside that same fold (`seen-outpoints`), guarding against submitting the identical output twice *in one list*: [2](#0-1) 

There is no companion durable map (e.g. `used-outpoints`/`processed-lockups`) anywhere in the contract that persists a consumed outpoint across transactions — a `grep` for such state across the repo returns no matches in `pox-5.clar`. Consequently, a staker can:
1. Submit a genuine, valid L1 lockup proof for outpoint `O` (amount `A` sats) as part of `register-for-bond` for `bond-index 0`, crediting `A` sats to `total-shares-staked-for-cycle`/`signer-shares-staked-for-cycle` for that bond.
2. Submit the exact same proof for outpoint `O` again in a later `register-for-bond`/rollover call for a different `bond-index` (or reuse it after the first bond's lock window logic permits another registration), crediting `A` sats a second time.

Because `amount-sats` derived from `verify-l1-lockups` directly feeds the reward-weight calculation (`total-sats` in `calculate-bond-rewards`, and `get-total-shares-staked-for-cycle` used in `calculate-rewards`): [3](#0-2) 

double-crediting the same physically-locked BTC inflates the attacker's share of the sBTC rewards pool at the expense of other bonds/stakers, breaking the equality "sats credited by an L1 proof == sats actually locked on Bitcoin" and causing double-counting of a single BTC commitment.

### Impact Explanation
This falls under the Critical bucket: "double-counting a commitment or reward." The attacker does not need to lock any additional BTC; the same physical lockup is presented multiple times to inflate `total-sats`/`signer-shares-staked-for-cycle`, entitling the attacker to a disproportionate share of `calculate-rewards`' `gross-accrued-rewards` sBTC pool, which is real sBTC contributed by/owed to other participants (or the reserve).

### Likelihood Explanation
Requires only an unprivileged staker with one genuine BTC lockup transaction and the ability to call `register-for-bond` (or the rollover path) more than once with the same lockup data across different `bond-index` values or timing windows. No admin, signer, or other user's key is required — only the attacker's own valid L1 proof, reused.

### Recommendation
Persist every accepted `(txid, output-index)` pair in a durable `define-map` keyed globally (not per-call), and reject any `validate-l1-lockup`/`verify-l1-lockups` invocation whose outpoint already appears in that map, across all bond indices and stakers, not just within the current call's fold.

### Proof of Concept
Not independently executable from the index alone — I could not confirm within the available context whether `register-for-bond`'s surrounding checks (e.g. `ERR_ALREADY_REGISTERED`, per-bond allowlist/rollover gating) fully close this path for every combination of `bond-index`/rollover sequencing, since I was not able to read the complete `register-for-bond` function body before the tool budget was exhausted. This should be verified by tracing all call sites of `verify-l1-lockups` end-to-end (register-for-bond, any rollover/extend entry points) to confirm whether a persistent outpoint map is genuinely absent across all of them, and whether existing "already registered" guards incidentally prevent the double-credit scenario described.
