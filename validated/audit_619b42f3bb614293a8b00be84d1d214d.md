## Title
Cross-organization webhook forgery via decoupled signature-verification org and target-repository fields - ([File: app/controllers/shipit/webhooks_controller.rb])

## Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to use for HMAC verification based on `repository_owner` — a value pulled from the untrusted, attacker-supplied JSON payload (`repository.owner.login`, falling back to `organization.login`). The handlers that actually act on the payload (e.g. `Shipit::Webhooks::Handlers::Handler#stacks`/`#repository_name` and `PushHandler`) instead resolve the target stack from a *different* payload field, `repository.full_name`. Since both fields live in the same unsigned-until-verified JSON body and are never cross-checked against each other, an attacker who legitimately controls (or has installed) a Shipit-configured GitHub App for one organization can compute a valid signature for that org while pointing `repository.full_name` at a stack belonging to a completely different organization also configured in the same Shipit instance.

## Finding Description
`verify_signature` computes the org used for secret lookup independently of the org actually referenced by the rest of the payload: [1](#0-0) [2](#0-1) 

```
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization:)` looks up the per-organization webhook secret when Shipit is configured with multiple GitHub Apps (one per organization), which the project explicitly supports and documents: [3](#0-2) [4](#0-3) 

The signature is verified over the *entire raw body*, but that does not stop an attacker from crafting a body where `repository.owner.login` (used only to pick the verification secret) and `repository.full_name` (used to pick the *actual target*) refer to two unrelated organizations — nothing binds these two fields together.

The handler layer resolves the target purely from `repository.full_name`: [5](#0-4) 

```
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`PushHandler`, for example, uses this `stacks` scope directly to sync stacks based on attacker-controlled `ref`/`after` fields: [6](#0-5) 

Concretely, given a Shipit instance configured for `OrgA` and `OrgB` (each with its own GitHub App/webhook secret, as shown in `test/dummy/config/secrets_double_github_app.yml`): [7](#0-6) [8](#0-7) 

An attacker who is an admin of `OrgB` (and thus legitimately knows `OrgB`'s `webhook_secret`, since GitHub App owners can view/rotate their own app's webhook secret) can send:
```json
{
  "repository": {
    "owner": { "login": "OrgB" },
    "full_name": "OrgA/victim-repo"
  },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>"
}
```
signed with `OrgB`'s secret. `verify_signature` passes because it only checks `repository_owner` == `"OrgB"` against `OrgB`'s secret. `PushHandler` then resolves the stack via `repository.full_name` = `"OrgA/victim-repo"`, i.e. a stack belonging to an org the attacker has no legitimate relationship to, and calls `stack.sync_github(expected_head_sha: ...)` on it.

This breaks the trust binding: **organization that authenticated (`OrgB`, via its webhook secret) ≠ repository that is written/acted upon (`OrgA`'s stack)**.

## Impact Explanation
The webhook dispatch mechanism (`Shipit::Webhooks.for_event`) routes many event types through handlers that all inherit this same `repository_name`/`stacks` resolution (`push`, `check_suite`, `pull_request` variants). Any handler that mutates the state of a stack/commit belonging to another organization solely because the attacker forged a payload with a mismatched `owner.login` vs `full_name` is a cross-organization write, one of the explicitly enumerated Critical impacts (cross-repository writes / unauthorized state changes across trust boundaries). At minimum this allows an attacker with legitimate access to one org's GitHub App configuration to trigger GitHub sync jobs, and depending on the handler reached, to influence review-stack archival/unarchival or PR-label-driven provisioning actions, for repositories/stacks that belong to a different, unrelated organization also hosted on the same Shipit instance.

## Likelihood Explanation
This is only exploitable when a single Shipit deployment hosts multiple GitHub organizations via the multi-app configuration schema (`github: { orgA: {...}, orgB: {...} }`), which is an explicitly supported and documented configuration. In that configuration, no additional privilege beyond "control of one of the configured orgs' webhook secret" (something the attacker legitimately possesses for their own org) is required — there is no session, API token, or repository-write access needed to exploit the mismatch itself.

## Recommendation
Bind the two fields together before trusting either: after signature verification succeeds for `repository_owner`, re-validate that `repository.full_name`'s owner segment matches the same `repository_owner`/organization used to select the webhook secret, and reject the request otherwise. Alternatively, verify the signature using an org derived and locked from `repository.full_name` (the value the handlers actually act on) rather than a separately-parsed `owner.login`/`organization.login` field.

## Proof of Concept
1. Configure Shipit with two GitHub Apps for `OrgA` and `OrgB` as in `test/dummy/config/secrets_double_github_app.yml`, each with its own known `webhook_secret`.
2. As an attacker who administers `OrgB`'s GitHub App (and therefore knows `OrgB`'s `webhook_secret`), craft a `push` event JSON body:
   ```json
   {
     "repository": {"owner": {"login": "OrgB"}, "full_name": "OrgA/victim-repo"},
     "ref": "refs/heads/main",
     "after": "deadbeef"
   }
   ```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(OrgB_webhook_secret, body)>` and POST to `/webhooks` with header `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgB")` and successfully verifies the signature against `OrgB`'s secret (see `app/controllers/shipit/webhooks_controller.rb:24-30`, `lib/shipit/github_app.rb:76-83`).
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("OrgA/victim-repo")` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`, `app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) and invokes `sync_github` on stacks belonging to `OrgA`, despite the request never being signed by anything associated with `OrgA`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
