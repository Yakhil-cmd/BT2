### Title
Webhook signature verification is skipped entirely when an organization has no `webhook_secret` configured, letting an unauthenticated attacker forge `membership` events to grant themselves `Shipit.github_teams` authorization - (File: `lib/shipit/github_app.rb`)

### Summary
The `WhereIsMyDragonTreasure` report is about a reward-claim function acting on attacker-controlled parameters that were never actually covered by the protocol's verification logic. The structural analog here is `GitHubApp#verify_webhook_signature`, which is supposed to bind every inbound webhook to the organization's registered secret, but silently treats "no secret configured" as "verified."

### Finding Description
`WebhooksController#verify_signature` picks which `GitHubApp` (and therefore which `webhook_secret`) to validate against using data taken directly from the unauthenticated request body: `repository_owner` is read from `params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`. [1](#0-0) [2](#0-1) 

That resolved `GitHubApp` instance then verifies the signature with:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [3](#0-2) 

`webhook_secret` for an organization comes straight from config and is explicitly documented as optional (`Webhook secret (optional): ...`), and the example secrets files ship with it commented out/blank. [4](#0-3) [5](#0-4) 

This breaks the binding: `organization the request claims to be from` == `organization whose secret actually signed the payload`. If any configured organization has a blank `webhook_secret` (the documented default), `verify_webhook_signature` returns `true` for **any** payload claiming to belong to that organization, regardless of who sent it - there is no signature check to bypass, because none is enforced.

The most impactful handler reachable through this path is `MembershipHandler`, which is dispatched for the `membership` event without any additional authentication and directly mutates authorization-relevant state:
```ruby
def process
  team = find_or_create_team!
  member = User.find_or_create_by_login!(params.member.login)
  case params.action
  when 'added'
    team.add_member(member)
  ...
``` [6](#0-5) 

`Team#add_member` appends arbitrary `Membership` rows, and `User#authorized?` (used by the `force_github_authentication` before_action on every controller) grants access to any user whose `teams` intersect `Shipit.github_teams`: [7](#0-6) [8](#0-7) [9](#0-8) 

So an attacker who knows (or guesses) the organization's login and any already-registered team's GitHub `id`, can POST a forged, unsigned `membership` webhook naming their own already-logged-in Shipit user's login as `member`, and the handler will create the `Membership` row unconditionally - escalating that attacker-controlled account into the authorized team, without ever needing a valid webhook secret, `ApiClient` token, or GitHub App credential.

### Impact Explanation
This is a direct escalation into `Shipit.github_teams` authorization (explicitly listed as a High-severity impact) achieved purely by exploiting the "no secret configured -> verification trivially passes" behavior of `verify_webhook_signature`, i.e., an authentication-boundary bypass on the webhook endpoint rather than a documented deployment misconfiguration requiring privileged access. It requires no session, no `ApiClient` token, and no GitHub credentials of any kind — only an already-existing (unauthorized) Shipit login and knowledge of the organization name and a team's numeric GitHub id (discoverable via the public GitHub API, since `Team#github_id` mirrors GitHub team IDs).

### Likelihood Explanation
Reasonably likely wherever an operator follows the documented "optional" webhook secret guidance and leaves `webhook_secret` blank for an organization (the packaged `config/secrets.development.example.yml` and `config/secrets.development.shopify.yml` both show it as nil/blank by default). The `/webhooks` endpoint is public and unauthenticated by design (it must be, to receive GitHub webhooks), so the only gate protecting it is `verify_webhook_signature` — and that gate is a no-op exactly when the secret is unset.

### Recommendation
`verify_webhook_signature` should fail closed, not open, when no secret is configured (e.g., reject the request or require `webhook_secret` to be mandatory at configuration-load time), and the `Webhook secret (optional)` guidance in `docs/setup.md` should be corrected to state it is required. Additionally, membership/team mutations should not be derived solely from attacker-suppliable webhook payload fields without confirming that the enclosing signature bound to a real, non-empty secret for that specific organization.

### Proof of Concept
1. Deploy Shipit with an organization configured without `webhook_secret` (the documented default/optional path), e.g. `secrets.yml`:
```yaml
github:
  someorg:
    app_id: ...
    installation_id: ...
    webhook_secret: # blank
```
2. As an unauthenticated network client, `POST /webhooks` with header `X-Github-Event: membership` and no (or garbage) `X-Hub-Signature`, body:
```json
{
  "action": "added",
  "team": { "id": <existing_team_github_id>, "name": "Developers", "slug": "developers", "url": "https://api.github.com/teams/1" },
  "organization": { "login": "someorg" },
  "member": { "login": "<attacker_shipit_login>" }
}
```
3. `verify_webhook_signature` returns `true` unconditionally (no secret configured), `MembershipHandler#process` runs, and a `Membership` linking the attacker's user to the team is created.
4. The attacker's existing Shipit session now satisfies `User#authorized?` via `Shipit.github_teams`, granting access to deploy/rollback/merge actions gated behind team authorization.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
