### Title
Cross-organization Status Webhook Forgery via Unscoped Commit Lookup Bypasses Per-Organization Signature Binding - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates an inbound webhook against the GitHub App/secret belonging to the organization named in the payload's `repository.owner.login` (or `organization.login`) field [1](#0-0) [2](#0-1) . That verification only proves the sender knows the webhook secret of the organization named in the payload — it does not, and cannot, constrain which records the resulting handler is allowed to mutate. `StatusHandler#process`, however, looks up commits globally by SHA with no repository or organization scoping at all: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [3](#0-2) . Every other handler (`PushHandler`, `CheckSuiteHandler`) resolves the target through `Repository.from_github_repo_name(repository_name)` before touching any stack [4](#0-3) [5](#0-4) , but `StatusHandler` is the outlier that never checks that the commit it is writing a status for actually belongs to the organization whose secret validated the request.

### Finding Description
Shipit supports one GitHub App configuration per organization, each with its own independent `webhook_secret`, as documented in `docs/setup.md` and exercised by `test/dummy/config/secrets_double_github_app.yml` (`OrgOne`, `OrgTwo`, each with distinct `webhook_secret`) [6](#0-5) .

The binding the system is supposed to enforce is:
`organization whose secret authenticated the request == organization/repository whose data is written by the handler`

`WebhooksController#verify_signature` derives the authenticating organization purely from attacker-supplied JSON (`params.dig('repository', 'owner', 'login')`) [2](#0-1)  and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [7](#0-6) . This confirms only that the request was signed with *that org's* secret — nothing about which commit, stack, or repository the event actually affects.

Once verification passes, the full raw `params` are handed unchanged to every registered handler for the event type: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [8](#0-7) . `StatusHandler` then resolves its target purely by commit SHA, system-wide, with no dependency on `repository.owner.login` (the very field used for signature selection) or `repository.full_name` (the field every other handler uses to scope the write) [9](#0-8) .

Because commit SHAs are 40-character hex digests that are public information (visible in any repo's git history, PRs, CI logs, etc.) and are not organization-specific, an attacker who legitimately controls a webhook secret for **any one** organization configured on the Shipit instance (e.g., their own low-value org/repo `OrgTwo`) can craft a `status` event payload whose `repository.owner.login` is `OrgTwo` (so it authenticates against `OrgTwo`'s secret) but whose `sha` value matches a commit belonging to a totally unrelated, higher-value stack under `OrgOne`. `verify_signature` succeeds (correct secret for the named organization), yet `StatusHandler` writes the forged status onto `OrgOne`'s commit via `commit.create_status_from_github!(params)`.

### Impact Explanation
Commit statuses are consumed by Shipit's merge-queue and deploy-readiness logic (`Shipit::MergeRequest`, `Shipit::Status::Group`, `DeploySpec`) to decide whether a commit is deployable/mergeable [10](#0-9) . By injecting a forged "success" status for a commit belonging to a stack under an organization the attacker never legitimately authenticated for, the attacker can satisfy required-status checks and push an unauthorized commit through the merge queue / deploy gate for that unrelated repository — this is a cross-organization write and can lead to an unauthorized deploy or merge, matching the Critical impact bar for this engine (cross-repository writes / unauthorized deploy or merge).

### Likelihood Explanation
Requires only that the attacker control (own) a single organization configured on the shared Shipit instance — a low bar for a multi-tenant Shipit deployment serving several organizations behind one instance, which the engine explicitly supports (`secrets_double_github_app.yml`, per-org GitHub Apps in `lib/shipit/github_app.rb`). No repository write access, GitHub App private key, session, or `ApiClient` token to the *victim* organization is needed — only the attacker's own legitimately-issued webhook secret for their own org, plus a public commit SHA from the victim repo.

### Recommendation
`StatusHandler` (and any handler that does not go through `stacks`/`Repository.from_github_repo_name`) must verify that the commit(s) it updates belong to a repository whose owner matches the organization that authenticated the request (`repository.owner.login`/`repository_owner` used in `verify_signature`), not just match by SHA globally. Concretely, scope the lookup to `Repository.from_github_repo_name(payload.dig('repository','full_name'))&.stacks&.joins(:commits)&.where(sha: params.sha)` instead of an unscoped `Commit.where(sha: ...)`.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgOne` (victim, private/sensitive) and `OrgTwo` (attacker-controlled), each with its own `webhook_secret`, as in `test/dummy/config/secrets_double_github_app.yml`.
2. Attacker knows `OrgTwo`'s webhook secret (they administer that org/repo's Shipit webhook).
3. Attacker looks up a public commit SHA on `OrgOne/victim-repo` (e.g., from GitHub's public commit history/PR).
4. Attacker POSTs to `/webhooks` with header `X-Github-Event: status` and body:
   ```json
   {
     "repository": {"owner": {"login": "OrgTwo"}, "full_name": "OrgTwo/attacker-repo"},
     "sha": "<victim commit sha from OrgOne/victim-repo>",
     "state": "success",
     "context": "ci/required-check"
   }
   ```
   signed with `X-Hub-Signature` computed using `OrgTwo`'s `webhook_secret`.
5. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "OrgTwo")` and verifies successfully (`app/controllers/shipit/webhooks_controller.rb:24-30`).
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the `OrgOne` commit (unscoped), and calls `commit.create_status_from_github!(params)`, injecting a forged "success" status onto a commit in an organization the attacker never authenticated for (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`).
