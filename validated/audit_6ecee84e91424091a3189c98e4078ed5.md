### Title
`StatusHandler#process` writes GitHub status records by SHA alone, allowing a webhook signed for one repository to mutate commit state belonging to a completely different stack/repository - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves target `Commit` rows exclusively via `Commit.where(sha: params.sha)`, never consulting `payload.dig('repository', 'full_name')` or `Handler#stacks` as every other handler does. Because `sha` is not unique across stacks/repositories in the `commits` table, a webhook that is validly signed for `attacker/evil` can create a `Shipit::Status` row against a commit that belongs to `victim-org/prod`, provided a `Commit` row with the identical `sha` exists in both stacks.

### Finding Description
Broken binding: `repository_owner` used in `WebhooksController#verify_signature` (`attacker/evil`) MUST equal the `repository.full_name` that owns the `Commit` row(s) actually mutated by `StatusHandler#process`, but no code enforces this.

Path:
1. `Shipit::WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) only checks that the request signature matches the GitHub App secret for `repository_owner = params.dig('repository','owner','login')`. This proves the payload genuinely came from GitHub for that organization/repo installation — it says nothing about which `Commit` rows may be touched.
2. `WebhooksController#create` dispatches to `Shipit::Webhooks.for_event(event)` handlers, passing the raw payload straight through [1](#0-0) .
3. Every other handler in this module scopes its writes through `Handler#stacks`, which resolves `Repository.from_github_repo_name(repository_name)&.stacks` using `payload.dig('repository', 'full_name')` [2](#0-1) .
4. `StatusHandler#process`, however, does not call `stacks` or `repository_name` at all — it looks up commits purely by `sha`: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [3](#0-2) .
5. `Commit#create_status_from_github!` writes a `Shipit::Status` row tied to `stack_id` for whichever commit was matched, `stack:` here comes from the matched `Commit`'s own `belongs_to :stack`, not from the payload's repository [4](#0-3) .
6. `sha` has no uniqueness constraint scoped to a single stack in this model — `Commit` rows across different stacks/repositories can and do share the same `sha` value (e.g., forks preserve commit SHAs exactly, since Git commit hashes are content-addressed).

Exploit flow: attacker owns `attacker/evil`, which has the Shipit GitHub App installed and thus a valid `webhook_secret` for `repository_owner = attacker`. Attacker forks `victim-org/prod` (or otherwise obtains a commit whose SHA byte-matches a commit already tracked in `victim-org/prod`'s Shipit stack) into `attacker/evil`, then legitimately calls the GitHub Status API for that SHA within their own repo (`POST /repos/attacker/evil/statuses/{sha}`). GitHub delivers a `status` webhook to Shipit signed with the `attacker/evil` installation secret and payload `repository.full_name = "attacker/evil"`, `sha = <shared sha>`, `state: "success"`. `verify_signature` passes because the signature is valid for `attacker`. `StatusHandler#process` then matches `Commit.where(sha: ...)` — which returns rows for *both* `attacker/evil`'s tracked commit *and* `victim-org/prod`'s commit if the latter has a `Commit` row with that same sha in Shipit's database — and writes a `success` `Status` for `victim-org/prod`'s commit despite the payload never having proven authorization over `victim-org/prod`.

This bypasses the intended per-repository isolation that every other handler enforces via `Handler#stacks`/`repository_name`.

### Impact Explanation
An attacker who controls only their own repository can flip the CI status (`success`/`failure`/`pending`) of a commit belonging to an unrelated tenant's stack, without ever authenticating against that tenant's repository. Since `deployable?` on `Commit` depends on `success?` (derived from `status`, which aggregates `statuses`) [5](#0-4) , and `schedule_continuous_delivery` triggers `ContinuousDeliveryJob` when a commit becomes deployable and the stack has continuous deployment enabled [6](#0-5) , this can lead to an **unauthorized deploy** of `victim-org/prod` triggered purely by a forged/cross-tenant status write. This matches the Critical impact category: "a payload for one repository mutating another's stack, commit ... or an unauthorized deploy". The blast radius is cross-tenant: any Shipit instance hosting multiple repositories/organizations is affected, and the attack is repeatable against any commit whose SHA is duplicated across stacks (most easily achieved via forking, since Git preserves commit SHAs across forks).

### Likelihood Explanation
Preconditions: (1) attacker must own/control a repository with the Shipit GitHub App installed (achievable by any GitHub user installing a public GitHub App on their own repo — no privileged Shipit role required); (2) a `Commit` row for the target victim commit must already exist in Shipit's database with a byte-identical SHA to a commit reachable from the attacker's repository — trivially satisfied by forking the victim's public repository, since forking does not rewrite SHAs; (3) the attacker must be able to trigger (or wait for) a status webhook for that SHA scoped to their own fork, which is a normal, unprivileged GitHub operation. No secrets, sessions, or Shipit roles are required. This is feasible and repeatable at will against any target repository that is public (forkable) and already tracked by the victim's Shipit instance.

### Recommendation
Scope `StatusHandler#process` to only the commits belonging to stacks for the reporting repository, mirroring every other handler: filter `Commit.where(sha: params.sha, stack: stacks)` (using `Handler#stacks`, derived from `payload.dig('repository','full_name')`) instead of an unscoped `Commit.where(sha: ...)`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status event for attacker/evil does not create a status on a victim stack's commit sharing the same sha" do
  victim_commit = shipit_commits(:victim) # belongs to victim-org/prod stack
  attacker_repository = shipit_repositories(:attacker_evil) # attacker/evil, distinct stack

  payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'repository' => { 'full_name' => 'attacker/evil' },
  }

  assert_no_difference -> { victim_commit.statuses.count } do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end
end
```
Before the fix, `Commit.where(sha: params.sha)` matches `victim_commit` regardless of `payload['repository']['full_name']`, and `assert_no_difference` fails, demonstrating the cross-tenant write. After scoping through `Handler#stacks`/`repository_name`, the test passes because the victim's commit is excluded when the payload's repository does not own it.
