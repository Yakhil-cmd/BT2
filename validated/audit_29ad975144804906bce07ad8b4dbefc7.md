### Title
Mutable `spender_attested` Attestor List Lets an Asset Definer Freeze a Party's Ability to Transfer or Repay an Asset, Causing AA Fund Loss/Forfeiture - ([File: validation.js])

### Summary
The external report describes a Pausable ERC-20 debt token whose issuer can `pause()` transfers, preventing a borrower from repaying a Cooler loan before expiry and causing an unjust default. ocore has a structurally identical, protocol-level "pause" primitive: an asset defined with `spender_attested: true` can have its authorized-spender list frozen or emptied at any time by the asset's `definer_address` via a subsequent `asset_attestors` message, and validation unconditionally rejects any payment (input spend or output) involving an address that is not on the current attestor-approved list. Any AA (e.g. an escrow/loan/marketplace agent) that accepts or pays out such an asset and enforces a time-based settlement/default/forfeiture rule can have counterparties' funds permanently frozen or forfeited if the definer (or the attestors) revoke attestation for the relevant address before the deadline.

### Finding Description
An asset can be created with `spender_attested: true` [1](#0-0) , which requires a list of `attestors` to be published, and requires that transacting addresses be attested by one of them [2](#0-1) .

Crucially, the attestor list is **not fixed at issuance**. The asset `definer_address` can publish a new `asset_attestors` message at any later time to redefine (including emptying or replacing) the attestor list: [3](#0-2) 

Once a new attestor list unit is stable, `readAsset`/`loadAssetWithListOfAttestedAuthors` picks up "the latest list of trusted attestors" [2](#0-1) , and any subsequent attestations from the removed attestors, or lack of attestation for a given address, causes that address to no longer be considered attested.

Payment validation then unconditionally enforces this attestation for every payment of a `spender_attested` asset — both for spending an input (`owner address is not attested`) and for every output address (`some output addresses are not attested`): [4](#0-3) [5](#0-4) 

This same check applies to the issuer for the base spend path [6](#0-5) .

Because attestation is checked at validation time against the "current" list rather than being fixed when the coins were received, a definer (or its attestors) can retroactively revoke attestation for an address that already legitimately holds coins of the asset, at which point:
- That address can no longer construct a valid `payment` spending those coins (its own transfer/repayment reverts validation as "owner address is not attested").
- No third party can send coins of that asset *to* that address either (output address check).

This is functionally identical to a `pause()`/blacklist call on an ERC-20: token holders retain a balance on paper, but any transfer touching the frozen address is rejected by protocol validation.

### Impact Explanation
Any AA (autonomous agent) built to hold or exchange a `spender_attested` asset as collateral/debt/settlement token — analogous to Cooler's Pausable-debt-token scenario — is exposed. For example, an escrow/lending AA (patterned like the loan-with-collateral extension mentioned in `things_registry_and_marketplace.oscript` [7](#0-6) , or milestone/expiry-driven AAs such as `ico_with_milestones.oscript` and `51_attack_game.oscript` which gate state transitions on `timestamp` [8](#0-7) ) that requires a borrower to send a `spender_attested` asset back to the AA before an expiry:
- If the definer revokes the borrower's attestation before the deadline, the borrower's repayment unit fails validation and can never be included, causing the AA's time-based default/liquidation logic to trigger and seize the borrower's collateral — unauthorized loss of borrower funds.
- Symmetrically, if the AA itself needs to pay out a `spender_attested` asset to a counterparty whose attestation was revoked, the AA's own outgoing payment message fails validation (`aa_composer.js` does not pre-check `spender_attested`/attestor status before composing sends, so the bounce happens only at validation), which can leave funds stuck/frozen inside the AA.

This is a Medium-severity issue: it requires a `spender_attested` asset definer to act adversarially (or simply update its attestor policy) at an inopportune time, but it directly leads to loss/forfeiture of counterparty funds or the freezing of AA balances, matching "AA fund loss or freezing" and "unauthorized... loss" impact criteria.

### Likelihood Explanation
`spender_attested` is a supported, documented asset feature exercised in tests and multiple official oscript sample AAs (`ico_with_milestones.oscript`, `51_attack_game.oscript`, `fundraising_proxy.oscript`, `futures_contract.oscript`) as a building block for AA-issued tokens. While built-in AA-issued assets in these examples are created with `spender_attested: false`, nothing prevents a general-purpose AA (escrow, lending, marketplace) from accepting a *third-party* `spender_attested` asset as payment/collateral, at which point the definer of that asset — not the AA nor the counterparty — fully controls whether that counterparty can ever move the asset again. Given that this mirrors a well-known real-world bug class (pausable/blacklistable tokens breaking time-locked DeFi protocols), and the attestor-list update is a normal, unrestricted single-message operation available to any asset definer at any mci, the likelihood of this being triggered (intentionally or through routine attestor-policy changes) in a live AA-based lending/escrow product is realistic.

### Recommendation
- For AAs that accept externally-defined `spender_attested`/otherwise conditionally-transferable assets as debt/collateral, document/require using only assets without mutable transfer-blocking properties (`spender_attested: false`, no `transfer_condition` that depends on external revocable state), or explicitly validate the current attestation status of all involved counterparties before allowing a loan/escrow to be opened.
- Consider adding a protocol-level or AA-level "escape hatch" pattern (e.g., allow repayment/withdrawal via an alternate unattested address, or add a grace-period/oracle-based fallback) so that a definer's post-hoc attestor list change cannot unilaterally force a default when the underlying obligation could otherwise be met.
- At minimum, flag in AA-authoring guidance that `asset_attestors` updates by a third-party definer are a live "pause" vector and must be accounted for in any deadline/liquidation logic that touches externally-controlled assets.

### Proof of Concept
1. Address D defines an asset A with `spender_attested: true` and an initial attestor list including attestor X [9](#0-8) .
2. Attestor X attests borrower address B as eligible to hold/spend asset A.
3. An escrow/lending AA `L` is set up (pattern per `ico_with_milestones.oscript`/`51_attack_game.oscript`) that accepts asset A as collateral from B and requires B to send asset A back to `L` before `timestamp > $expiry_ts`, otherwise `L`'s state logic forfeits B's collateral to another party after expiry.
4. B sends asset A to `L` as collateral; `L` records the loan and expiry.
5. Before expiry, D (the asset definer) publishes a new `asset_attestors` message for asset A that no longer attests B (e.g., removes X or replaces the list) [3](#0-2) .
6. When B attempts to post a `payment` unit transferring asset A back to `L` to repay/redeem, validation rejects it: `owner address is not attested` [10](#0-9) , so the unit can never become valid/stable.
7. Expiry passes; `L`'s timestamp-gated logic finalizes the default/forfeiture branch, and B's collateral is lost, exactly mirroring the Cooler Pausable-token default scenario.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
