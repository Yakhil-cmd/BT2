### Title
Cross-organization webhook forgery via mismatch between the organization used to select the signature-verification secret and the repository actually written by the webhook handlers - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App configuration (and its `webhook_secret`) to use for HMAC verification based on `repository.owner.login` / `organization.login` in the untrusted JSON body, while the actual event handlers that mutate state resolve the target `Repository`/`Stack` from a *different* field of the same body, `repository.full_name`, without ever checking that it belongs to the organization that was used to verify the signature. In a multi-organization Shipit deployment (multiple entries under `secrets.github`, each with its own `webhook_secret`), an attacker who legitimately knows the webhook secret for *one* onboarded organization can forge a signed payload whose `repository.full_name` points at a repository belonging to a *different* onboarded organization, causing Shipit to act on that victim repository/stack as if the request had been authenticated by GitHub for it.

### Finding Description
`verify_signature` computes the signing organization purely from body content: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` then resolves a `GitHubApp` instance configured for that organization key, each with its own independently configured `webhook_secret`: [3](#0-2) 

`verify_webhook_signature` only checks that the raw body's HMAC matches *that* organization's secret; it makes no assertion about which repository the body actually references: [4](#0-3) 

Once the signature passes, `create` dispatches the raw JSON to the handlers unmodified: [5](#0-4) 

Every handler, however, resolves the repository/stack to act on from `repository.full_name`, a field that was never checked against `repository.owner.login`: [6](#0-5) 

For example `PushHandler` triggers a GitHub sync on any stack matching the (attacker-controlled) branch of that repository: [7](#0-6) 

`StatusHandler` writes an arbitrary CI status onto any commit whose SHA is supplied in the payload: [8](#0-7) 

Pull-request handlers (e.g. `closed_handler.rb`, `labeled_handler.rb`, `opened_handler.rb`) likewise resolve their target `Repository` from `params.repository.full_name` and archive/unarchive/provision review stacks accordingly: [9](#0-8) 

**Binding broken:** `organization authenticated (repository.owner.login, used to select the verification secret) == organization/repository written (repository.full_name, used by every handler to locate the Repository/Stack to mutate)`. Before the attack, this equality normally holds because GitHub itself sends consistent payloads signed with the correct per-repo secret. After the attacker's forged request, the left side is the attacker's own onboarded organization (whose secret they legitimately know) while the right side is an arbitrary other onboarded repository — the equality is broken, and the engine still treats the request as authenticated for that unrelated repository.

### Impact Explanation
This is a cross-organization/cross-repository write achieved without any GitHub credentials, `ApiClient` token, or Shipit session for the victim repository/organization — only knowledge of a webhook secret belonging to some other organization configured in the same multi-tenant Shipit instance is required. Concrete consequences per handler:
- `StatusHandler` lets the attacker forge a "success" CI status on any commit of a victim stack, which is used elsewhere in the engine to gate deployability — this can be used to make an otherwise non-deployable/failing commit appear green, contributing to an unauthorized deploy.
- `PushHandler` forces `stack.sync_github(expected_head_sha:)` on a victim stack for an attacker-chosen ref/branch, causing Shipit to re-sync state against an attacker-influenced expectation.
- The pull-request handlers can archive/unarchive review stacks or trigger provisioning behavior on a victim repository the attacker has no legitimate access to.

This maps to the "unauthorized deploy" / cross-repository-writes class of impact defined in scope.

### Likelihood Explanation
Requires the target Shipit deployment to be configured for multiple GitHub organizations (`secrets.github` with per-org sub-keys and distinct `webhook_secret`s), and requires the attacker to legitimately control at least one such onboarded organization (a realistic scenario for a shared/multi-tenant Shipit instance serving several teams/orgs). No privileged Shipit account, `ApiClient` token, or GitHub write access to the victim repository is needed — only the ability to craft and sign an HTTP POST to `/webhooks`.

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler`), assert that the organization portion of `repository.full_name` (or `repository.owner.login`) used by the handler to resolve the target repository matches the `repository_owner` that was used to select the verification secret, rejecting the request (422) otherwise. Alternatively, verify the signature using the secret associated with the resolved target `Repository`'s owner rather than a value taken from an unauthenticated field of the payload itself.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.github`, `attacker-org` (secret `S_A`, known to the attacker because they administer that org's webhook) and `victim-org` (a repository the attacker does not control), matching the multi-org setup exercised in `test/dummy/config/secrets_double_github_app.yml`.
2. Attacker crafts a JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<victim-commit-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(S_A, body)` and sends `POST /webhooks` with `X-Github-Event: push`.
4. `verify_signature` computes `repository_owner = "attacker-org"`, loads `Shipit.github(organization: "attacker-org")`, and successfully verifies the signature using `S_A` [1](#0-0) .
5. `PushHandler` (via `Handler#repository_name`) resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github(expected_head_sha: params.after)` on the victim's stack [10](#0-9) [7](#0-6)  — despite the signature only having proven that the requester knows `attacker-org`'s secret, not anything about `victim-org`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
