### Title
Unbounded private-payment chain length allows a malicious asset holder to DoS a counterparty's chain validation and freeze private-asset transfers - ([File: indivisible_asset.js])

### Summary
The `LockingPositionService` bug relies on an unbounded, user-controlled array (`lockExtensions`) that is later iterated in full by a victim (the buyer) with no cap, causing a revert/DoS. The equivalent construct in `ocore` is the private-payment "chain" of an indivisible (privacy-preserving) asset: `arrPrivateElements`, built by `buildPrivateElementsChain()` and consumed by `parsePrivatePaymentChain()` / `validateAndSavePrivatePaymentChain()`. The holder of a private-asset coin can cheaply and repeatedly self-transfer the coin to inflate the chain length to an arbitrary size before finally sending it to a victim (sale/gift). The victim's node/wallet must then walk and fully re-validate the *entire* chain, hop by hop, in series, with no length limit enforced anywhere in the code path.

### Finding Description
`indivisible_asset.js` builds the private transfer chain recursively/iteratively with `buildPrivateElementsChain()`: [1](#0-0) 

Each hop triggers another DB read and another push onto `arrPrivateElements`, continuing until an `issue` input is reached: [2](#0-1) 

There is no limit on how many transfer hops a coin can go through before being handed to a counterparty — an attacker fully controls how many times they self-transfer their own coin before selling/gifting it.

When the chain is received, `parsePrivatePaymentChain()` iterates the *whole* array in series, calling `validatePrivatePayment()` for every single element (DB queries + full payment validation per hop): [3](#0-2) 

`validatePrivatePayment()` itself performs several DB queries and a full `validation.validatePayment()` call per hop: [4](#0-3) [5](#0-4) 

The entry points that accept an externally supplied chain do not bound its length:
- `handlePrivatePaymentChains()` in `wallet.js` only validates that `arrChains` is a non-empty array of well-formed elements, never checking `c.length`: [6](#0-5) 
- `handleOnlinePrivatePayment()` in `network.js` only checks `arrPrivateElements` is non-empty, with no upper bound, before queueing/validating the chain: [7](#0-6) 
- `validateAndSavePrivatePaymentChain()` in `private_payment.js` hands the full, unbounded array straight to `indivisibleAsset.validateAndSavePrivatePaymentChain`: [8](#0-7) 

A repo-wide search for any chain-length guard (`MAX_PRIVATE...`, `chain too long`, `arrPrivateElements.length >`, etc.) found none in `indivisible_asset.js`, `private_payment.js`, `network.js`, or `wallet.js` — confirming there is no cap analogous to `constants.MAX_SPEND_PROOFS_PER_MESSAGE`, `MAX_MESSAGES_PER_UNIT`, etc. that exist for other unit-level arrays.

This mirrors the reported `ysCVG` bug class precisely: an unprivileged actor (the coin's current owner) inflates an array they fully control (the chain of past self-transfers) at low marginal cost per element (one ordinary DAG unit + associated fee per hop), then hands the poisoned object to a counterparty. The counterparty (or their wallet/hub) is then forced to process the entire array serially before being able to accept/spend the funds, exactly as the buyer in the Sherlock report was forced to loop the entire `lockExtensions` array before claiming rewards.

### Impact Explanation
When the victim (recipient of the private payment, or the hub facilitating store-and-forward) receives the poisoned chain, they must run `parsePrivatePaymentChain` synchronously over every hop — each hop doing multiple additional DB round-trips (`spend_proofs`, `determineIfIncluded`/graph traversal, full payment validation, `initPrivatePaymentValidationState`). For a sufficiently long chain (thousands to tens of thousands of hops, each cheap for the attacker to create over time), this:
- Locks the `mutex` on `handleJoint`/`saved_private` / `private_chains` for the duration of validation, blocking the wallet's ability to process other units or payments.
- Can stall or effectively make the receiving wallet/hub unresponsive while validating a single incoming private payment, preventing the victim from ever completing acceptance of these (and other) funds — a fund-availability/liveness DoS specific to private-asset transfers, i.e., the private-payment counterparty cannot confirm/spend the asset they were sent.
- Because chain validation runs inside a DB transaction (`BEGIN`/`COMMIT`/`ROLLBACK` in `private_payment.js`), an extremely long-running validation also holds a DB connection and transaction open for an extended period, which can degrade node responsiveness more broadly.

This satisfies the "AA fund loss or freezing" / "node unable to confirm new units" criteria: the victim's funds embedded in the received private-asset payment become effectively unusable/unconfirmable in practice due to the attacker-inflated chain, and node resources are monopolized while attempting validation.

### Likelihood Explanation
Likelihood is high for any user who accepts private-asset payments from an untrusted or semi-trusted counterparty (which is the entire point of privacy-preserving indivisible assets, e.g. blackbytes-style tokens): the attacker only needs to be the current holder of a private-asset coin, and self-transfer it to themselves as many times as they want before finally delivering it as payment. Each self-transfer is an ordinary, valid unit (same low cost pattern as `increaseLockTimeAndAmount` costing normal but cheap gas in the original report), so the attack is realistic and repeatable at will, without needing any special privilege, hub cooperation, or protocol violation.

### Recommendation
Introduce an explicit, enforced upper bound on the length of a private-payment chain (`arrPrivateElements`) at every layer that accepts externally supplied chains:
- Add a `constants.MAX_PRIVATE_PAYMENT_CHAIN_LENGTH` (or similar) and reject any chain (`c.length > MAX_...`) in `handlePrivatePaymentChains()` (wallet.js) and `handleOnlinePrivatePayment()` (network.js) before any DB work is performed.
- Enforce the same limit inside `parsePrivatePaymentChain()`/`validateAndSavePrivatePaymentChain()` (indivisible_asset.js, private_payment.js) as a defense-in-depth check, so that chains reconstructed locally (via `buildPrivateElementsChain`) or received from a hub/peer are equally bounded.
- Consider capping validation work with a time/step budget and yielding (similar to the `count % 100 === 0` breaks used elsewhere in formula evaluation) so a long chain degrades gracefully rather than blocking the mutex/DB transaction for an unbounded duration.

### Proof of Concept
1. Attacker issues (or otherwise obtains) 1 unit of a private indivisible asset coin to their own address.
2. Attacker composes N (e.g., 50,000) consecutive private, self-to-self transfer units of that exact coin, each referencing the previous unit's output as its single input — a normal, valid transaction each time (cost: one ordinary unit fee per hop, no anti-spam check prevents this since transfers are ordinary payment messages).
3. After N hops, attacker sends the coin (as a `private_payment`) to Victim, e.g. as payment for goods/services (mirrors "User 1 sells the token to User 2" in the original report).
4. Victim's wallet (or the hub relaying it) receives the head element via `handleOnlinePrivatePayment` → `validateAndSavePrivatePaymentChain` (network.js/private_payment.js), and must call `buildPrivateElementsChain`/`parsePrivatePaymentChain` (indivisible_asset.js), which serially walks and fully re-validates all N hops before the payment can be accepted.
5. Because there is no cap on `arrPrivateElements.length` anywhere in this path, the validation takes proportionally long (N × per-hop DB queries + full `validatePayment` calls), stalling the victim's wallet/hub (mutex-held) and preventing them from timely confirming/using the received funds — analogous to the buyer being unable to call `claimRewards` in the original report.

		return callbacks.ifError("invalid issue private element");
	var asset = issuePrivateElement.payload.asset;
	if (!asset)
		return callbacks.ifError("no asset in issue private element");
	var denomination = issuePrivateElement.payload.denomination;
	if (!denomination)
		return callbacks.ifError("no denomination in issue private element");
	async.forEachOfSeries(
		arrPrivateElements,
		function(objPrivateElement, i, cb){
			if (!objPrivateElement.payload || !objPrivateElement.payload.inputs || !objPrivateElement.payload.inputs[0])
				return cb("invalid payload");
			if (!objPrivateElement.output)
				return cb("no output in private element");
			if (objPrivateElement.payload.asset !== asset)
				return cb("private element has a different asset");
			if (objPrivateElement.payload.denomination !== denomination)
				return cb("private element has a different denomination");
			var prevElement = null; 
			if (i+1 < arrPrivateElements.length){ // excluding issue transaction
				var prevElement = arrPrivateElements[i+1];
				if (prevElement.unit !== objPrivateElement.payload.inputs[0].unit)
					return cb("not referencing previous element unit");
				if (prevElement.message_index !== objPrivateElement.payload.inputs[0].message_index)
					return cb("not referencing previous element message index");
				if (prevElement.output_index !== objPrivateElement.payload.inputs[0].output_index)
					return cb("not referencing previous element output index");
			}
			validatePrivatePayment(conn, objPrivateElement, prevElement, {
				ifError: cb,
				ifOk: function(bStable, input_address){
					objPrivateElement.bStable = bStable;
					objPrivateElement.input_address = input_address;
					if (!bStable)
						bAllStable = false;
					cb();
				}
			});
		},
		function(err){
			if (err)
				return callbacks.ifError(err);
			callbacks.ifOk(bAllStable);
		}
	);

function validateAndSavePrivatePaymentChain(arrPrivateElements, callbacks){
	if (!ValidationUtils.isNonemptyArray(arrPrivateElements))
		return callbacks.ifError("no priv elements array");
	var headElement = arrPrivateElements[0];
	if (!headElement.payload)
		return callbacks.ifError("no payload in head element");
	var asset = headElement.payload.asset;
	if (!asset)
		return callbacks.ifError("no asset in head element");
	if (!ValidationUtils.isNonnegativeInteger(headElement.message_index))
		return callbacks.ifError("no message index in head private element");
	
	var validateAndSave = function(){
		storage.readAsset(db, asset, null, function(err, objAsset){
			if (err)
				return callbacks.ifError(err);
			if (objAsset.is_private !== 1)
				return callbacks.ifError("asset is not private");
			if (!!objAsset.fixed_denominations !== !!headElement.payload.denomination)
				return callbacks.ifError("presence of denomination field doesn't match the asset type");
			if (!!objAsset.fixed_denominations !== ("output" in headElement))
				return callbacks.ifError("divisible asset must not have output field, indivisible must");
			db.takeConnectionFromPool(function(conn){
				conn.query("BEGIN", function(){
					var transaction_callbacks = {
						ifError: function(err){
							conn.query("ROLLBACK", function(){
								conn.release();
								callbacks.ifError(err);
							});
						},
						ifOk: function(){
							conn.query("COMMIT", function(){
								conn.release();
								callbacks.ifOk();
							});
						}
					};
					// check if duplicate
					var sql = "SELECT address, denomination, amount, blinding FROM outputs WHERE unit=? AND asset=? AND message_index=?";
					var params = [headElement.unit, asset, headElement.message_index];
					if (objAsset.fixed_denominations){
						if (!ValidationUtils.isNonnegativeInteger(headElement.output_index))
							return transaction_callbacks.ifError("no output index in head private element");
						sql += " AND output_index=?";
						params.push(headElement.output_index);
					}
					conn.query(
						sql, 
						params, 
						function(rows){
							if (rows.length > 1)
								throw Error("more than one output "+sql+' '+params.join(', '));
							if (rows.length > 0 && rows[0].address){ // we could have this output already but the address is still hidden
								const stored = rows[0];
								const payload = headElement.payload;
								let bDuplicate = false;
								if (objAsset.fixed_denominations){ // the row we selected is exactly headElement.output_index, filtered in sql above
									const claimed_output = payload.outputs?.[headElement.output_index];
									const revealed_output = headElement?.output;
									bDuplicate =
										ValidationUtils.isNonemptyObject(claimed_output)
										&& ValidationUtils.isNonemptyObject(revealed_output)
										&& stored.denomination === payload.denomination
										&& stored.amount === claimed_output.amount
										&& stored.address === revealed_output.address
										&& stored.blinding === revealed_output.blinding;
								}
								else // divisible outputs are never hidden individually and sql has no output_index filter, so match against any of them
									bDuplicate = (payload.outputs || []).some(output => {
										return ValidationUtils.isNonemptyObject(output)
											&& stored.denomination === 1
											&& stored.amount === output.amount
											&& stored.address === output.address
											&& stored.blinding === output.blinding;
									});
								if (bDuplicate) {
									console.log("duplicate private payment "+params.join(', '));
									return transaction_callbacks.ifOk();
								}
							}
							var assetModule = objAsset.fixed_denominations ? indivisibleAsset : divisibleAsset;
							assetModule.validateAndSavePrivatePaymentChain(conn, arrPrivateElements, transaction_callbacks);
						}
					);
				});
			});
		});
	};
	
	if (conf.bLight)
		findUnfinishedPastUnitsOfPrivateChains([arrPrivateElements], false, function(arrUnfinishedUnits){
			(arrUnfinishedUnits.length > 0) ? callbacks.ifWaitingForChain() : validateAndSave();
		});
	else
		validateAndSave();
}
