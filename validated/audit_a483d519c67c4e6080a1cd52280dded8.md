## Analysis

The Kairos report's root cause—crediting a fixed "amount" in contract bookkeeping while trusting an ERC20's `transfer()` call to have actually moved that exact amount, when fee-on-transfer tokens deduct a portion—has a direct, demonstrable analog in Polkadot SDK's `ERC20Transactor`, the `TransactAsset` implementation that lets `pallet-xcm`/XCM executor move ERC20 tokens (via `pallet-revive`) on Asset Hub Westend. [1](#0-0) [2](#0-1) 

The `ERC20Matcher` matches **any** location of the shape `{parents:0, AccountKey20{key}}` to the transactor — there is no registry/allow-list check, so any contract address, including one the caller just deployed themselves via permissionless `pallet-revive` contract instantiation, is a valid "asset" for this transactor. [3](#0-2) 

The PR that introduced this feature confirms the matching is purely shape-based, keyed off the raw contract address: [4](#0-3) 

### Title
ERC20Transactor credits/moves the nominal `amount` instead of the actual ERC20 balance delta, permanently stranding fee-on-transfer token balances in `TransfersCheckingAccount` - (File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs)

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` call the ERC20 `transfer()` function and only check its boolean return value to decide success; they never verify that the checking account's actual balance changed by `amount`. Any signed user can deploy an arbitrary fee-on-transfer ERC20 contract via `pallet-revive` and reference it in an XCM program executed through `pallet_xcm::execute`, causing the shared `TransfersCheckingAccount` to accumulate an accounting deficit relative to what the runtime believes it holds.

### Finding Description
`withdraw_asset_with_surplus` calls `IERC20::transferCall{ to: checking_address, value: amount }` from the user's account, and on a `true` return it unconditionally credits `AssetsInHolding` with `Erc20Credit(amount)` — the *requested* amount, not the amount the checking account actually received: [5](#0-4) 

If the ERC20 contract at that address implements fee-on-transfer semantics (deducts a cut and still returns `true`), the checking account's real balance increases by `amount - fee`, while the XCM holding register — and thus everything downstream in the XCM program (deposits, trapped-asset accounting, refunds) — treats the credit as the full `amount`.

Symmetrically, `deposit_asset_with_surplus` transfers `amount` out of the checking account to a beneficiary using the same unchecked pattern — it trusts the boolean return of `transfer()` without confirming the beneficiary actually received `amount`: [6](#0-5) 

Because `TransfersCheckingAccount` is a single shared account for *all* ERC20 assets handled by this transactor (configured once per runtime), the deficit created by one user's fee-on-transfer withdrawal is not isolated to that user — it silently erodes the pooled balance backing every credit issued for that asset: [7](#0-6) 

There is no reachability barrier requiring privileged access: `pallet-revive` contract deployment is a standard permissionless signed extrinsic, and the resulting contract address is a valid XCM asset location purely by its `AccountKey20` shape — no governance-gated foreign-asset registration is needed for this transactor (unlike `ForeignFungiblesTransactor`, which typically requires `pallet-assets` registration).

### Impact Explanation
Each withdraw of a fee-on-transfer ERC20 through this transactor credits the XCM holding register with more than the checking account actually gained. Over repeated cycles, the checking account's real on-chain ERC20 balance falls behind the cumulative credits the runtime has issued for that asset. Eventually a legitimate deposit for a *different, honest* user of the same asset can fail because the checking account no longer holds enough tokens to cover the ERC20 `transfer()` call, and the difference becomes permanently unrecoverable through this transactor's logic (it always assumes withdraw/deposit move exactly `amount`). This is a fund-freezing/accounting-integrity bug reachable by any unprivileged user, matching Medium severity in the original Kairos finding rather than a theft primitive (no new tokens are minted; existing user funds risk being stranded).

### Likelihood Explanation
Likelihood is moderate: it requires (1) deploying a custom fee-on-transfer ERC20 contract via `pallet-revive` (trivial, permissionless), and (2) driving that contract's address through the `ERC20Transactor` via a local XCM program (`pallet_xcm::execute` with `WithdrawAsset`/`DepositAsset`), which is a standard, non-privileged operation once the asset transactor is wired into a runtime's `AssetTransactors` (currently only Asset Hub Westend per `xcm_config.rs`). No governance, validator, or relayer cooperation is needed.

### Recommendation
After each `IERC20::transfer` call in `withdraw_asset_with_surplus`/`deposit_asset_with_surplus`, read back the actual balance delta of the sender/checking account (or recipient) via `balanceOf` before and after the call, and use that measured delta — not the caller-supplied `amount` — when constructing the `AssetsInHolding` credit or when reporting success for the deposit path. Alternatively, reject assets/contracts whose transfer does not preserve amount (fail closed if actual delta != requested amount) rather than assuming ERC20 compliance.

### Proof of Concept
Not executed against a live network. Reproduction path (would require a local Rust/FRAME integration test against `asset-hub-westend-runtime`):
1. Deploy a minimal fee-on-transfer ERC20 (e.g., 10% fee deducted on every `transfer`, returns `true`) via `pallet_revive::Pallet::instantiate_with_code` from a signed account.
2. Fund the deployer with tokens; build a local XCM program `WithdrawAsset((AccountKey20{key: contract}, amount)) -> DepositAsset(beneficiary)` and submit via `pallet_xcm::execute` as a signed extrinsic.
3. Observe: `withdraw_asset_with_surplus` credits `amount` into holding despite the checking account real balance only increasing by `amount * 0.9`; `deposit_asset_with_surplus` then attempts to move the full `amount` out again, further deducting fees, and the checking account's true ERC20 balance depletes below what subsequent legitimate credits assume.
This was traced statically from the transactor code paths cited above; no test harness run/log is available in this analysis, so PoC execution status is **not run**.

/// `Contains<Location>` implementation that matches locations with no parents,
/// a `PalletInstance` and an `AccountKey20` junction.
pub struct IsLocalAccountKey20;
impl Contains<Location> for IsLocalAccountKey20 {
	fn contains(location: &Location) -> bool {
		matches!(location.unpack(), (0, [AccountKey20 { .. }]))
	}
}

/// Fallible converter from a location to a `H160` that matches any location ending with
/// an `AccountKey20` junction.
pub struct AccountKey20ToH160;
impl MaybeEquivalence<Location, H160> for AccountKey20ToH160 {
	fn convert(location: &Location) -> Option<H160> {
		match location.unpack() {
			(0, [AccountKey20 { key, .. }]) => Some((*key).into()),
			_ => None,
		}
	}

	fn convert_back(key: &H160) -> Option<Location> {
		Some(Location::new(0, [AccountKey20 { key: (*key).into(), network: None }]))
	}
}

/// [`xcm_executor::traits::MatchesFungibles`] implementation that matches
/// ERC20 tokens.
pub type ERC20Matcher =
	MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>;
