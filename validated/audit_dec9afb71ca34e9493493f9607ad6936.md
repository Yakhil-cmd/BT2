### Title
Cross-repository commit-status forgery via SHA collision in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates a `status` webhook against the GitHub organization/App configured for the `repository.owner.login` (or `organization.login`) found in the payload [1](#0-0) [2](#0-1) . However, once the signature is accepted, `Shipit::Webhooks::Handlers::StatusHandler#process` writes the resulting commit status to **any** `Commit` record in the entire Shipit database whose `sha` matches the payload, with no scoping to the repository/stack that the verified organization owns [3](#0-2) . This breaks the binding "organization that authenticated == repository that is written": the signature only proves the sender controls org A, but the write lands on any stack (potentially belonging to org B) whose commit happens to share that SHA.

### Finding Description
- The `verify_signature` step in `WebhooksController` derives `repository_owner` from the payload and looks up `Shipit.github(organization: repository_owner)` to validate the HMAC signature against that organization's `webhook_secret` [4](#0-3) . This proves only that the request was signed by whoever owns the webhook secret for that one organization/repository.
- Other handlers correctly scope their effects to the repository named in the payload via `Handler#stacks`, which resolves `Repository.from_github_repo_name(repository_name)` using `payload.dig('repository', 'full_name')` [5](#0-4) , e.g. `PushHandler` only touches stacks under that repository [6](#0-5) .
- `StatusHandler`, however, does **not** use `repository_name`/`stacks` at all. It queries `Commit.where(sha: params.sha)` globally and calls `create_status_from_github!` on every match, across all stacks/repositories in the Shipit instance [7](#0-6) .
- `Commit#create_status_from_github!` persists the forged status and can flip a commit's computed `status`/`deployable?` state, which feeds `Stack#trigger_deploy`, continuous-delivery scheduling, and merge-queue advancement (`schedule_merges`) for whatever stack owns that commit [8](#0-7) [9](#0-8) [10](#0-9) .

Because `sha` is only a 40-hex-char git object id and Shipit's `Commit.by_sha`/`params.sha` matching is a plain string match (not scoped per-repository), any two independent repositories tracked by the same Shipit instance that happen to record a commit with an identical SHA (e.g. a shared upstream commit, cherry-picks, forks, vendored history, or any two repos with a common ancestor commit) allow an attacker who legitimately controls one onboarded organization/repository (and therefore possesses a valid webhook signature for that org) to forge a `status` event that marks an *unrelated* repository's commit as `success`, unblocking or blocking its deploy pipeline, without ever having write access to that other repository.

### Impact Explanation
This is a cross-repository write: an actor authenticated only for organization/repo A can alter deploy-readiness state (`deployable?`, CI gating, merge-queue advancement) of commits belonging to repo B, which Shipit was never told repo A had any relationship with. This can directly enable an unauthorized deploy in an unrelated stack (marking a required status as `success` when it is really unset/failed upstream on GitHub), matching the Critical-tier "unauthorized deploy" impact category, since Shipit's own deploy-safety gates (`required_statuses`, `blocking_statuses`, `deployable?`) are driven by these locally stored statuses rather than a live re-check of the correct repository.

### Likelihood Explanation
Exploitation requires: (1) the attacker to have onboarded/control at least one repository configured in the target Shipit instance with a working webhook secret (a realistic scenario for any multi-tenant or multi-team Shipit deployment where many independent teams' repos are registered under different orgs but processed by the same Shipit app), and (2) a SHA collision between a commit they can push in their own repo and a commit already tracked in the target stack. Genuine SHA-1 collisions are impractical to engineer directly, but git history sharing is common (shared parent commits, template repos, forks, cherry-picked/rebased commits, vendored subtree commits, or CI-generated commits with identical content/timestamps) meaning identical SHAs across otherwise unrelated `Commit` records tracked by the same Shipit install are plausible without needing a cryptographic attack, especially in monorepo/fork/template-heavy organizations. This is a design flaw (missing repository scoping) rather than a theoretical cryptography exploit, so it is triggerable deterministically whenever a matching SHA exists.

### Recommendation
Scope `StatusHandler#process` to only commits belonging to the repository named in the verified payload, mirroring `Handler#stacks`/`repository_name`, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
More generally, audit all webhook handlers to ensure every write is scoped through `Handler#stacks` (derived from the verified `repository.full_name`), rather than trusting global lookups keyed only by attacker-supplied identifiers such as `sha`.

### Proof of Concept
1. Attacker registers/owns Repository X under Organization A in the target Shipit instance (a normal, permitted onboarding) and receives a valid `webhook_secret` for org A.
2. Attacker arranges (or opportunistically finds) that a commit with SHA `S` exists both in their own repository X and in the target's unrelated Repository Y/stack (e.g. via a shared open-source dependency commit, forked history, or template repository commit that both X and Y have merged).
3. Attacker crafts a GitHub `status` webhook payload for repository X with `sha=S`, `state=success`, and any `context` matching one of Y's `required_statuses`, then signs it with org A's `webhook_secret` (which they legitimately possess) and POSTs it to `/github/webhooks`.
4. `WebhooksController#verify_signature` validates the signature against org A successfully [4](#0-3) .
5. `StatusHandler#process` runs `Commit.where(sha: S)`, which also matches the commit in Y's stack, and calls `create_status_from_github!`, marking Y's commit as passing the required status check even though the attacker has no relationship with Y or its GitHub organization [3](#0-2) .
6. Y's stack now considers that commit `deployable?` for merge-queue/continuous-delivery purposes, potentially triggering an unauthorized deploy.
