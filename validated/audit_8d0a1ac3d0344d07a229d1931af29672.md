### Title
Bridge Token Type Confusion in `requestERC721Transfer` Allows ERC20 Fee Bypass and Permanent Asset Loss in `modeMintBurn` Mode — (`contracts/service_chain/bridge/Bridge.sol`, `BridgeTransferERC721.sol`, `BridgeTokens.sol`)

---

### Summary

The Kaia service-chain `Bridge` contract inherits both `BridgeTransferERC20` and `BridgeTransferERC721` and exposes both `requestERC20Transfer` and `requestERC721Transfer` as public entry points on the same contract. The shared token registry (`BridgeTokens`) stores only a `(token → counterpartToken)` address mapping with **no token-type field**. Neither `requestERC721Transfer` nor its internal helper `_requestERC721Transfer` validates that the supplied token address is actually an ERC-721 contract. Because `IERC721.transferFrom(from, to, tokenId)` and `IERC20.transferFrom(from, to, amount)` share the same 4-byte selector (`0x23b872dd`), and `ERC721Burnable.burn(uint256)` and `ERC20Burnable.burn(uint256)` share selector `0x42966c68`, a user can call `requestERC721Transfer` with a registered ERC-20 token address. This produces two distinct impacts depending on the bridge's `modeMintBurn` flag:

1. **Non-`modeMintBurn`**: ERC-20 bridge fee is silently bypassed.
2. **`modeMintBurn`**: The user's ERC-20 tokens are burned on the source chain, but the destination-chain `handleERC721Transfer` call reverts permanently (selector mismatch on `mintWithTokenURI`), causing irreversible loss of bridged assets.

---

### Finding Description

`Bridge.sol` inherits from `BridgeTransferERC20` and `BridgeTransferERC721`:

```solidity
// Bridge.sol L25
contract Bridge is BridgeCounterPart, BridgeTransferKLAY, BridgeTransferERC20, BridgeTransferERC721 {
```

The token registry in `BridgeTokens.sol` stores only addresses, with no type discriminator:


The `onlyRegisteredToken` modifier only checks presence in the registry:

```solidity
// BridgeTokens.sol L32-35
modifier onlyRegisteredToken(address _token) {
    require(registeredTokens[_token] != address(0), "not allowed token");

```

`requestERC721Transfer` and `_requestERC721Transfer` apply only this modifier — no type check:

```solidity

    address _to,
    uint256 _tokenId,
    bytes memory _extraData

    public
{
    IERC721(_tokenAddress).transferFrom(msg.sender, address(this), _tokenId);
    _requestERC721Transfer(_tokenAddress, msg.sender, _to, _tokenId, _extraData);

```

```solidity
// BridgeTransferERC721.sol L73-106
function _requestERC721Transfer(...) internal
    onlyRegisteredToken(_tokenAddress)
    onlyUnlockedToken(_tokenAddress)
{
    require(isRunning, "stopped bridge");
    ...

        ERC721Burnable(_tokenAddress).burn(_tokenId);   // same selector as ERC20Burnable.burn
    }
    emit RequestValueTransferEncoded(

```

The ERC-20 fee is only charged inside `_requestERC20Transfer` via `_payERC20FeeAndRefundChange`:

```solidity
// BridgeTransferERC20.sol L91

```

```solidity
// BridgeFee.sol L68-88

    uint256 fee = feeOfERC20[_token];
    if (feeReceiver != address(0) && fee > 0) {
        require(_feeLimit >= fee, "insufficient feeLimit");
        IERC20(_token).safeTransfer(feeReceiver, fee);
        ...
    }
    ...
}
```

This path is never reached when `requestERC721Transfer` is used.

### Impact Explanation

**Non-`modeMintBurn` (lock/unlock mode)**:

- `IERC721(erc20Addr).transferFrom(user, bridge, tokenId)` resolves to ERC-20's `transferFrom`, locking `tokenId` amount of ERC-20 tokens in the bridge.
- The event emits `TokenType.ERC721` with `fee = 0`.
- The counterpart bridge's `handleERC721Transfer` calls `IERC721(counterpartErc20).transferFrom(bridge, to, tokenId)`, which resolves to ERC-20's `transferFrom`, successfully releasing `tokenId` amount of ERC-20 tokens to the recipient.
- **Result**: Full cross-chain ERC-20 transfer completes with zero fee paid, stealing from the fee receiver.

**`modeMintBurn` mode**:

- Same first step: `tokenId` amount of ERC-20 tokens transferred to bridge.
- `ERC721Burnable(erc20Addr).burn(tokenId)` resolves to `ERC20Burnable.burn(tokenId)`, burning those tokens from the bridge.
- On the destination chain, `handleERC721Transfer` calls `ERC721MetadataMintable(counterpartErc20).mintWithTokenURI(to, tokenId, uri)`. This selector does not exist on ERC-20 contracts, so the call reverts.
- The bridge operator retries indefinitely; the nonce can never be settled.
- **Result**: ERC-20 tokens are permanently burned on the source chain with no corresponding mint on the destination chain — irreversible loss of bridged assets.

---

### Likelihood Explanation

The `Bridge` contract is a single deployed contract exposing both `requestERC20Transfer` and `requestERC721Transfer` publicly. Any user who has approved the bridge to spend their ERC-20 tokens can call `requestERC721Transfer` with a registered ERC-20 token address. The only prerequisite is that the operator has registered the ERC-20 token (standard operational setup). The selector collision between ERC-20 and ERC-721 `transferFrom` and `burn` functions makes the call succeed silently without revert. Likelihood is **low-medium** (requires intentional misuse or user error, but no privileged access beyond normal token approval).

---

### Recommendation

Add a token-type field to `BridgeTokens` and enforce it at the entry points:

```solidity
// BridgeTokens.sol
enum TokenStandard { ERC20, ERC721 }
mapping(address => TokenStandard) public tokenStandards;

function registerToken(address _token, address _cToken, TokenStandard _standard)
    external onlyOwner onlyNotRegisteredToken(_token) {
    ...
    tokenStandards[_token] = _standard;
}

modifier onlyERC721Token(address _token) {
    require(tokenStandards[_token] == TokenStandard.ERC721, "not an ERC721 token");
    _;
}
modifier onlyERC20Token(address _token) {
    require(tokenStandards[_token] == TokenStandard.ERC20, "not an ERC20 token");
    _;
}
```

Apply `onlyERC721Token` to `_requestERC721Transfer` and `onlyERC20Token` to `_requestERC20Transfer`.

### Proof of Concept

1. Operator deploys `Bridge` with `modeMintBurn = false` and registers ERC-20 token `T` (with non-zero fee `feeOfERC20[T] = F`).
2. Alice holds 1000 units of `T` and approves the bridge for 1000.
3. Alice calls `bridge.requestERC721Transfer(T, bob, 1000, "0x")`.
4. `IERC721(T).transferFrom(alice, bridge, 1000)` resolves to ERC-20's `transferFrom` — 1000 tokens locked in bridge. No fee deducted.
5. Event emitted: `RequestValueTransferEncoded(ERC721, alice, bob, T, 1000, nonce, 0, ...)`.
6. Counterpart bridge operator calls `handleERC721Transfer(..., counterpartT, 1000, ...)`.
7. `IERC721(counterpartT).transferFrom(bridge, bob, 1000)` resolves to ERC-20's `transferFrom` — 1000 tokens released to Bob.
8. Alice transferred 1000 ERC-20 tokens cross-chain, paying **zero fee** instead of `F`.

For `modeMintBurn = true`, step 4 additionally burns the 1000 tokens, and step 6 reverts permanently — 1000 tokens destroyed with no recovery path. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5)

```text
    function _payERC20FeeAndRefundChange(address from, address _token, uint256 _feeLimit) internal returns(uint256) {
        uint256 fee = feeOfERC20[_token];

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            IERC20(_token).safeTransfer(feeReceiver, fee);

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                IERC20(_token).safeTransfer(from, feeRefund);
            }

            return fee;
        }

        if (_feeLimit > 0) {
            IERC20(_token).safeTransfer(from, _feeLimit);
        }
        return 0;
    }
```
