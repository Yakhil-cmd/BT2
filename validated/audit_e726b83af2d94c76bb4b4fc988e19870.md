## Arithmetic Proof of Trigger Condition

Let `E = VRankEpoch`, `c = floor(E/8)`, `epochStart_{N+1} = (N+1)*E`.

```
cpNum = calcCheckpointBlock((N+1)*E, c)
      = (N+1)*E - ((N+1)*E % c)
```

Write `E = 8c + r` where `r = E % 8`. Then:

```
(N+1)*E % c = (N+1)*(8c + r) % c = (N+1)*r % c
```

- If `E % 8 == 0` → `r = 0` → `cpNum = (N+1)*E` (epoch start itself, no cross-epoch read).
- If `E % 8 != 0` → `r >= 1`. For any `N+1` where `(N+1)*r % c != 0`, `cpNum < (N+1)*E`, i.e., `cpNum` is a block in epoch N.

**Concrete example:** `E = 17`, `c = 2`, `r = 1`. For `N+1` odd: `(N+1)*1 % 2 = 1`, so `cpNum = (N+1)*17 - 1` (last block of epoch N). Since `(N+1)*17 - 1` is even (= divisible by `c=2`), a checkpoint was written there by `PostInsertBlock`. `loadPFSCheckpointInEpoch` returns that checkpoint, and `lookupPFSSeed` returns `(epochStart_{N+1}, epoch_N_pfs_map)`.

## Verdict

The bug is **real and code-confirmed**, but its exploitability depends on whether `VRankEpoch` is constrained to be divisible by 8 in production configuration. The code itself has no such guard. If `VRankEpoch % 8 != 0` is ever used (e.g., `VRankEpoch = 100`, `200`, `17`, etc.), the epoch N+1 PFS/CFS maps are seeded with epoch N's accumulated scores at every affected epoch boundary, corrupting validator failure scores and downstream reward distribution.

### Title
Cross-Epoch Checkpoint Seed Contamination in `loadPFSCheckpointInEpoch` / `loadCPMatrixCheckpointInEpoch` — (`kaiax/vrank/impl/init.go`)

### Summary
When `VRankEpoch` is not divisible by 8, `loadPFSCheckpointInEpoch` and `loadCPMatrixCheckpointInEpoch` resolve the checkpoint block for the first block of epoch N+1 to a block inside epoch N, loading epoch N's accumulated PFS/CFS scores as the seed for epoch N+1. This corrupts the failure score maps for epoch N+1 with prior-epoch data, causing incorrect validator ranking and incorrect KAIA reward distribution.

### Finding Description
`scoreCheckpointInterval()` returns `VRankEpoch / 8` (integer division). `loadPFSCheckpointInEpoch(blockNum)` computes `cpNum = calcCheckpointBlock(blockNum, checkpointInterval) = blockNum - (blockNum % checkpointInterval)` and reads whatever checkpoint is stored at `cpNum`, with no guard that `cpNum >= calcEpochStart(blockNum, vrankEpoch)`.

When `VRankEpoch % 8 != 0`, the epoch start `(N+1)*VRankEpoch` is not divisible by `checkpointInterval`, so `cpNum` falls back into epoch N. A checkpoint always exists at `cpNum` (since `cpNum` is by construction divisible by `checkpointInterval` and `PostInsertBlock` writes a checkpoint at every such block). The epoch-N checkpoint is then returned as the seed for epoch N+1.

The in-memory cache probe (`lookupPFSCache`) correctly limits its lookback to within the current epoch, but the DB checkpoint probe does not, creating an asymmetry that only manifests on cold start or cache miss at epoch boundaries.

### Impact Explanation
Epoch N+1 PFS and CFS maps start with epoch N's accumulated failure counts instead of zero. Validators and candidates who accumulated failures in epoch N are penalized again in epoch N+1. The CFS-derived validator set selection (`GetCFS` → `generateCFSFromCPMatrix` → `byzantineFilter`) and PFS-based proposer ranking are both corrupted, leading to incorrect KAIA reward distribution for the entire epoch N+1.

### Likelihood Explanation
Triggered automatically by normal block processing whenever `VRankEpoch % 8 != 0` and the epoch boundary condition `(N+1)*r % c != 0` holds (where `r = VRankEpoch % 8`, `c = VRankEpoch / 8`). No privileged access, no attacker action required — the corruption is deterministic and self-inflicted by the node's own `PostInsertBlock` → `GetPFS` path. Likelihood depends entirely on whether production `VRankEpoch` is always a multiple of 8; the code has no enforcement of this.

### Recommendation
In `loadPFSCheckpointInEpoch` and `loadCPMatrixCheckpointInEpoch`, add an epoch boundary guard:

```go
func (v *VRankModule) loadPFSCheckpointInEpoch(blockNum uint64) (uint64, map[common.Address]uint64, bool) {
    epochStart := calcEpochStart(blockNum, v.vrankEpoch())
    cpNum := calcCheckpointBlock(blockNum, v.scoreCheckpointInterval())
    if cpNum < epochStart {   // ← guard: do not cross epoch boundary
        return 0, nil, false
    }
    pfs := ReadCheckpointPFS(v.ChainKv, cpNum)
    if pfs == nil {
        return 0, nil, false
    }
    return cpNum, pfs, true
}
```

Apply the same fix to `loadCPMatrixCheckpointInEpoch`. Alternatively, enforce `VRankEpoch % 8 == 0` at config validation time.

### Proof of Concept
Set `VRankEpoch = 17` (so `checkpointInterval = 2`). Process blocks through epoch 0 (blocks 0–16) and into epoch 1 (block 17). At block 16 (`16 % 2 == 0`), a checkpoint is written with epoch 0's accumulated PFS. When `GetPFS(17)` is called: `calcCheckpointBlock(17, 2) = 16`, `ReadCheckpointPFS(db, 16)` returns epoch 0's map (non-nil), `lookupPFSSeed` returns `(17, epoch0_pfs)`, and `applyBlocksForPFS(17, 17, epoch0_pfs)` produces epoch 1's PFS seeded with epoch 0's scores. An exhaustive test over `VRankEpoch ∈ [8, 256]` checking that `loadPFSCheckpointInEpoch(epochStart)` returns `nil` or a checkpoint at `>= epochStart` will fail for all `VRankEpoch` not divisible by 8 where the arithmetic condition holds.
