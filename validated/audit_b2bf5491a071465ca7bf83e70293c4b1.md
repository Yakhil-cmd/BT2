`StatusHandler#process` matches commits by SHA globally, ignoring the repository that authenticated the webhook - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret using `repository_owner` derived from the payload, correctly binding signature verification to the org named in the payload. But `StatusHandler#process` never re-checks that binding: it looks up commits with `Commit.where(sha: params.sha)` across the entire `commits` table, with no scoping to the repository/org that was actually authenticated, unlike the base `Handler#stacks` helper which properly scopes via `Repository.from_github_repo_name(repository_name)`.

### Finding Description
The binding the security model relies on is: `repository_owner used to select webhook_secret` == `repository_owner of every row mutated by the handler`. Before tracing: this should hold because `verify_signature` picks `Shipit.github(organization: repository_owner)` [1](#0-0) , and `repository_owner` comes straight from `params.dig('repository', 'owner', 'login')` [2](#0-1) .

After tracing `StatusHandler`, the binding breaks: `#process` does not consult `repository_owner`/`repository_name` at all — it only uses `params.sha`: [3](#0-2) 

Compare this to the base `Handler` class, which does provide a repository-scoped `stacks` helper other handlers use (e.g. `CheckSuiteHandler`): [4](#0-3) [5](#0-4) 

`StatusHandler` uses the raw `Commit` model directly instead of `stacks`-scoped commits, so any commit sharing the same `sha` anywhere in the database — regardless of which repository/stack it belongs to — receives the status via `commit.create_status_from_github!(params)` [3](#0-2) , which calls `Commit#create_status_from_github!` and mutates the real `stack_id` via `statuses.replicate_from_github!(stack_id, github_status)` [6](#0-5) .

Exploit flow: attacker configures their own legitimate org (`Shipit.github` multi-org config, a real, distinct `webhook_secret`) [7](#0-6) . Because forks of a repository share identical git object hashes for unmodified commits, any commit SHA present in Org A's tracked repository is also a valid, resolvable SHA in the attacker's own fork of that repository (no cryptographic SHA-1 collision needed — just fork and reuse the real SHA). The attacker sends `POST /webhooks` with header `X-Github-Event: status`, a valid `X-Hub-Signature` computed with their own org's `webhook_secret`, and a JSON body where `repository.owner.login` = attacker's own org (so `verify_signature` succeeds using the attacker's own secret) but `sha` = a real commit SHA belonging to Org A's tracked commit. `WebhooksController#create` then dispatches to `StatusHandler.call(params)` [8](#0-7) , and `#process` finds and mutates Org A's `Commit` row, creating a forged `Status`.

Existing guards do not stop this: `verify_signature` only authenticates that the payload was signed by *some* configured org's secret — it never asserts that the `Repository` named in the payload actually owns the `sha` being mutated. `ExplicitParameters` schema for `StatusHandler` only requires `sha`/`state`/etc. as types, not repository identity [9](#0-8) , and no model validation on `Commit`/`Status` enforces that the acting webhook's authenticated org matches `commit.stack.repository.owner`.

### Impact Explanation
An unprivileged attacker who merely configures their own separate org/webhook_secret pair in Shipit's multi-org config (a legitimate, low-privilege action, not requiring any secret belonging to Org A) can inject arbitrary CI `Status` (state: `success`/`failure`/`pending`, arbitrary `description`/`target_url`/`context`) onto commits belonging to Org A's stacks, as long as the SHA is shared (trivial via forking a public repo). If a stack's continuous deployment or merge gating depends on required statuses (`stack.deployable?`, `deployable?`) [10](#0-9) , forging a `success` status can enable an unauthorized deploy of Org A's stack — this is "a payload for one repository mutating another's stack/commit" and can lead to "an unauthorized deploy," matching the Critical impact category. The attack is repeatable against any repository whose commits/SHAs the attacker can discover (public forks trivially expose all upstream SHAs).

### Likelihood Explanation
Preconditions are low-cost and fully attacker-controlled: register/administer a distinct org that is configured in `Shipit.github` (multi-org deployments are explicitly documented and supported) [7](#0-6) , obtain that org's own `webhook_secret` (which the attacker controls, since it's their own org's GitHub App config), and know or discover a target commit's SHA (trivial for public repos via forking). No access to Org A's secrets, sessions, or GitHub App keys is required. This is straightforwardly reproducible with a single crafted HTTP POST.

### Recommendation
In `StatusHandler#process`, scope the commit lookup through the authenticated repository, mirroring the base `Handler#stacks` helper, e.g. resolve `stacks` (or `Repository.from_github_repo_name(repository_name)`) and query `stacks.flat_map(&:commits).where(sha: params.sha)` (or `Commit.joins(stack: :repository).where(sha: params.sha, repositories: { owner: repository_owner, name: repository_name })`) instead of an unscoped `Commit.where(sha: ...)`. Add `requires :repository do requires :full_name, String end` to the `params` schema so the handler is forced to consult repository identity, matching the pattern used by other handlers like `PullRequest::AssignedHandler`.

```ruby
          # attacker's fork happens to contain the same sha object as org-a's commit

          payload = {
            'sha' => org_a_commit.sha,
            'state' => 'success',
            'repository' => { 'full_name' => 'org-b/repo-b', 'owner' => { 'login' => 'org-b' } }
          }

          assert_no_difference -> { org_a_commit.statuses.count } do

          end
        end
      end
    end
  end
end
```
