### Title
Cross-organization webhook signature binding allows forging `membership` events to inject arbitrary users into another org's `Team` - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret used to validate `X-Hub-Signature` via `repository_owner`, which for `membership` events falls back to `params.dig('organization', 'login')` — a value fully controlled by the payload itself. `MembershipHandler` then uses `params.team.id` (a numeric GitHub team id) to look up or add members to a `Team`, with no check that `params.organization.login` (used for signing) is the actual organization owning that `team.id`.

### Finding Description
Broken binding (equality that should hold but doesn't):
`org_used_for_signature = params.organization.login` **must equal** `org_that_actually_owns(params.team.id)` — but nothing enforces this.

Code path:
- `verify_signature` computes `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0)  and picks the webhook secret via `Shipit.github(organization: repository_owner)` [2](#0-1) . For a `membership` event the payload has no top-level `repository` key, so `repository_owner` resolves to `organization.login`, a value the attacker fully controls in the JSON body they sign themselves with their own org's secret.
- `MembershipHandler` requires `team.id`, `organization.login`, and `member.login` from the same attacker-controlled payload [3](#0-2) , then does:
```ruby
team = find_or_create_team!
member = User.find_or_create_by_login!(params.member.login)
team.add_member(member) # for action == 'added'
``` [4](#0-3) 
- `find_or_create_team!` does `Team.find_or_create_by!(github_id: params.team.id) { |team| team.organization = params.organization.login }` [5](#0-4) . Lookup is keyed **only** on `github_id`, with no verification that the signed org actually owns that team. If the `Team` row already exists (e.g. it's one of the teams seeded via `Shipit.github_teams`, used for authorization in `User#authorized?` [6](#0-5) ), the block is skipped and the existing (correct) `organization` is left untouched — but `team.add_member(member)` still runs unconditionally, adding an attacker-chosen `member.login` as a member of that team.
- If the `Team` row does not yet exist, the attacker's forged `organization.login` is written directly into `team.organization`, effectively fabricating cross-org team ownership.

Exploit flow: an attacker who owns any organization with a valid webhook secret in `Shipit`'s multi-org GitHub config (`Shipit.github(organization:)` / `secrets.github`) crafts a `membership` "added" JSON payload where `organization.login` = their own org (so `verify_signature` picks their own secret and passes), `team.id` = the numeric GitHub id of a team belonging to `Shipit.github_teams` (e.g. `shopify_developers`), and `member.login` = any GitHub login they want to add. They sign the raw body with their own org's `webhook_secret` and POST it to `/webhooks`. Signature verification succeeds because it only checks that the signature matches *some* organization's secret that the attacker legitimately controls — it never checks that this organization owns `team.id`.

Existing guards do not stop this: `check_if_ping`/`drop_unhandled_event` only gate on event type [7](#0-6) ; `ExplicitParameters` (`MembershipHandler.params`) only validates shape/types, not cross-field org/team ownership; there is no `require_permission!`/`authorized?` check anywhere in the webhook path since it's unauthenticated by design (webhooks use signature, not session).

### Impact Explanation
A successful request lets an attacker with no Shipit privileges add an arbitrary GitHub login as a member of a `Team` belonging to a different organization, including teams that are part of `Shipit.github_teams`. Since `User#authorized?` grants access based on `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [6](#0-5) , this is an escalation into `Shipit.github_teams` authorization — the attacker can grant themselves (or anyone) Shipit access without belonging to the real GitHub organization/team. This is repeatable against any known team id and any member login, and the blast radius spans every organization/team configured in the Shipit instance, since only knowledge of a numeric `team.id` is required.

### Likelihood Explanation
Preconditions: the Shipit deployment must be multi-org configured (`Shipit.github` supports multiple organizations, each with its own `webhook_secret`), and the attacker must control at least one such organization with `membership` webhooks enabled/registered against this Shipit instance (which is plausible in any multi-tenant Shipit setup where several orgs' webhooks point at the same host). `team.id` values are discoverable via GitHub's public/team API or by observing legitimate webhook traffic. The attack requires no session, API token, or GitHub App private key — only a webhook secret the attacker legitimately owns for their own org — making it low-cost and repeatable.

### Recommendation
In `MembershipHandler#find_or_create_team!` (and any handler using `params.organization.login` to write org/team associations), verify that the signing organization (the one that passed `verify_signature`) matches `params.organization.login` used inside the payload, and additionally verify — via the GitHub API or a strict mapping — that `params.team.id` truly belongs to that same organization before creating/reusing a `Team` record. In `WebhooksController`, consider passing the resolved `repository_owner` (the org used for signature verification) into the handler and rejecting the event if it doesn't match `params.organization.login` used by the handler for writes.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (illustrative)
test "membership event signed by org A cannot inject a member into org B's team" do
  # Precondition: a Team already exists for shopify's real team (simulating Shipit.github_teams seeding)
  shopify_team = Team.create!(organization: 'shopify', slug: 'developers', name: 'Developers', github_id: 424242)

  payload = {
    action: 'added',
    team: { id: 424242, name: 'Developers', slug: 'developers', url: 'https://api.github.com/teams/424242' },
    organization: { login: 'attacker-org' },
    member: { login: 'attacker-controlled-login' }
  }.to_json

  # Signed with attacker-org's OWN legitimate webhook secret (configured for attacker-org, not shopify)
  signature = 'sha1=' + OpenSSL::HMAC.hexdigest('sha1', attacker_org_webhook_secret, payload)

  post '/webhooks', params: payload, headers: {
    'X-Github-Event' => 'membership',
    'X-Hub-Signature' => signature,
    'CONTENT_TYPE' => 'application/json'
  }

  assert_response :ok # verify_signature passed using attacker-org's secret

  shopify_team.reload
  refute shopify_team.members.exists?(login: 'attacker-controlled-login'),
    "attacker should NOT be able to add a member to shopify's team by signing with attacker-org's secret"
end
```
Both sides of the equality (`org used to verify signature` vs `org that owns team.id 424242`) diverge (`attacker-org` vs `shopify`) yet the request is accepted and `team.add_member` still executes, confirming the vulnerability. Note: this repo's index did not expose a `GithubHook::Organization` ActiveRecord model as referenced in the question; the webhook secret selection observed is driven by `Shipit.github(organization:)` / `secrets.github` multi-org config [8](#0-7) , so the PoC fixture setup should use that mechanism (e.g. `test/dummy/config/secrets_double_github_app.yml`) rather than a `GithubHook::Organization` model, which could not be confirmed to exist in this codebase.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
