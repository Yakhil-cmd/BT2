Based on my research, I found a structurally analogous bug-class in ocore's data-feed key construction, though I was unable to fully confirm within available iterations whether `feed_name` character content is restricted (e.g., disallowing `\n`) in the message-level validator (`validation.js`). ### Title
Data-feed key-boundary injection via unescaped newlines in `feed_name`/`address` allows an oracle to forge matches for `in_data_feed`/`data_feed` lookups - (File: data_feeds.js)

### Summary
`data_feeds.js` builds LevelDB key-range boundaries for data-feed lookups by directly concatenating the untrusted `feed_name` (and `address`) strings with the `\n` delimiter that is also used internally to separate the semantic fields of the key (`df\naddress\nfeed_name\ntype\nvalue\nmci`). Neither `dataFeedByAddressExists` nor `readDataFeedByAddress`/`readDataFeedValue` escapes or rejects embedded `\n` bytes in `feed_name`, and `definition.js`'s validation of the `in data feed` operator only checks `isNonemptyString(feed_name)` and a max length, not its character set.

### Finding Description
The vulnerable pattern mirrors the CVE: an untrusted, attacker-supplied string (`URI` in XML::Sig; `feed_name`/`value` in ocore) is spliced into a query expression using a delimiter character (`'` in XPath; `\n` in the LevelDB key scheme) without checking that the value cannot itself contain that delimiter. In `dataFeedByAddressExists`: [1](#0-0) 
the range boundaries (`options.gte`, `options.lt`, etc.) are built as `'df\n'+address+'\n'+feed_name+'\n'+type+...`. Because `feed_name` is posted verbatim by any address as a JSON object key inside a `data_feed` message payload, and the definition-level validator for the `in data feed` oscript operator does not forbid `\n` in `feed_name`: [2](#0-1) 
an oracle can craft a `feed_name` containing embedded `\n` characters that alter how many logical fields the resulting key appears to have when scanned with `gte`/`lt`/`gt`/`lte` prefix bounds, in the same way the unescaped `'` in the CVE closes the XPath string literal early and lets injected content control which node matches.

The same unescaped concatenation exists in `readDataFeedByAddress`: [3](#0-2) 
and is used both by the `oscript` `in data feed` authentifier condition (address-unlock condition) and by `data_feed`/`in_data_feed` AA formula operators: [4](#0-3) [5](#0-4) 

### Impact Explanation
If a crafted `feed_name` can shift the intended key-range boundary (e.g., by injecting a fake `\n<type>\n<value>\n<mci>` suffix that the range-scan's `lt`/`gt` bound no longer excludes as intended), a malicious oracle could make its own posted data feed satisfy an `in data feed`/`in_data_feed` condition that references a *different* nominal `feed_name`, or vice versa suppress/duplicate a match. Because `in data feed` guards address-unlock conditions and AA trigger logic often relies on `data_feed`/`in_data_feed` to release funds or make payment decisions, a successful boundary bypass could let a single malicious address unlock funds it should not be able to unlock, or manipulate an AA's decision (fund loss/freezing), all reachable from a single posted unit — matching the required "unauthorized spending / AA fund loss" impact bar.

### Likelihood Explanation
This requires the attacker to control the exact byte layout of the LevelDB range keys well enough to make the range-scan actually admit unintended keys, which depends on the internal encoding of `type`, `string_utils.encodeDoubleInLexicograpicOrder`, and `string_utils.encodeMci`. I could not fully verify from the index whether `validation.js`'s data-feed message app validator (the payload/message-level validator, as opposed to the definition/oscript-level validator I confirmed) already restricts object keys (feed names) to a safe charset excluding `\n`/`\0`, which would neutralize this. This is a real gap in my confirmation — I was not able to retrieve those exact lines before running out of iterations.

### Recommendation
Validate that `feed_name` (and, defensively, `address`) cannot contain the `\n` delimiter byte (or any control byte used in the key scheme) at the point the `data_feed` message payload is validated in `validation.js`, and/or at the `in data feed` definition validator in `definition.js`, in addition to the existing length check. As defense-in-depth, key-building functions in `data_feeds.js` should reject or escape delimiter characters in `feed_name`/`address` before constructing key-range boundaries.

### Proof of Concept
Not able to construct a concrete byte-exact PoC without confirming the message-level validator behavior and the exact output format of `string_utils.encodeDoubleInLexicograpicOrder`/`encodeMci`, which were not available within the remaining tool budget. Recommend a Devin session with full repo/terminal access to: (1) inspect `validation.js`'s data-feed payload validator for feed_name charset restrictions, (2) if unrestricted, post a test `data_feed` message with `feed_name` containing embedded `\n` via a local test node, and (3) verify whether `dataFeedByAddressExists`/`readDataFeedByAddress` range scans return matches for a differently-named `in_data_feed`/`in data feed` condition than the one posted.
