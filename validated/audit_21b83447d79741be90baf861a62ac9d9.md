### Title
API-scoped CCMenu Token Bypasses Its `stack_id` Authorization Scope, Allowing Unauthorized Read of Another Stack's Deploy State - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`ApiClient` tokens can be scoped to a single stack via the `stack_id` association, and `Api::BaseController` enforces that scope by resolving `stack` through the `stacks` helper, which restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` when the token is scoped. `Api::CCMenuController` overrides `stack` to bypass this scoping entirely, querying `Stack.from_param!(params[:stack_id])` against *all* stacks regardless of the authenticated token's `stack_id` restriction.

### Finding Description
`Api::BaseController` defines the trust binding between an `ApiClient` token and the stacks it is allowed to touch: [1](#0-0) 

This binding is: `token.stack_id == nil ? any stack : stack.id == token.stack_id`, and it is meant to hold for every controller action that resolves `stack` from `params[:stack_id]`.

`Api::CCMenuController` inherits from `BaseController` and requires `read:stack` permission, but redefines `stack` to skip the scoped `stacks` collection and hit `Stack.from_param!` directly on the full `Stack` relation: [2](#0-1) 

Because `show` calls `stack.deploys_and_rollbacks.last`, the effective binding actually enforced is `token.permissions.include?("read:stack") == true`, not `stack.id == token.stack_id`. Any authenticated `ApiClient` (including a token deliberately created and scoped to a single, low-sensitivity stack — e.g., a CCMenu badge token as generated by `CCMenuUrlController`) can supply an arbitrary `params[:stack_id]` and read deploy/rollback state (`id`, `ended_at`, `running?`, and rendered XML fields) for any other stack in the Shipit instance, including stacks the token was never authorized to see.

Root cause: the "stack a token authorizes" (`current_api_client.stack_id`, enforced in `BaseController#stacks`) and the "stack a request actually touches" (`Stack.from_param!(params[:stack_id])` in `CCMenuController#stack`) are decoupled — the controller-specific override silently drops the scoping check that the parent class establishes.

### Impact Explanation
This breaks the authorization binding `token.stack_id == stack.id` that the platform relies on to let operators hand out narrowly-scoped tokens (e.g., for embedding in CI dashboards, status badges, or third-party CCMenu clients) without granting visibility into unrelated stacks. An attacker holding any valid `read:stack` token — even one deliberately scoped to a single, non-sensitive stack — can enumerate `stack_id` parameters and read deploy/rollback status of other stacks. This matches the "High — unauthenticated read of stack state, task streams or deploy output" impact category, since the scoped token is the intended narrow-privilege credential and the endpoint should not honor requests outside its `stack_id` scope.

### Likelihood Explanation
Likelihood is high for any deployment that issues stack-scoped `ApiClient` tokens (the `ApiClient` model explicitly supports `belongs_to :stack, optional: true` and the UI/`CCMenuUrlController` flow generates such tokens for embedding). Exploitation requires only a valid, scoped, `read:stack`-permitted token and knowledge/guessing of another stack's `to_param` (typically `owner/repo/env`, often predictable or discoverable), with no additional privilege, session, or GitHub credential needed.

### Recommendation
Remove the `stack` override in `Api::CCMenuController` (or reimplement it using the inherited `stacks.from_param!(params[:stack_id])` from `BaseController`) so that the `current_api_client.stack_id` scoping is consistently enforced across all API controllers, including CCMenu.

### Proof of Concept
1. As a Shipit admin, create (or have the app create via `CCMenuUrlController#fetch`) an `ApiClient` scoped to `stack_id = A` with permission `read:stack`, and obtain its `authentication_token`.
2. Using that token, issue: `GET /api/stacks/B/owner/env/cctray.xml?token=<token>` (i.e., set `params[:stack_id]` to a *different* stack `B` that the token was not scoped to).
3. Observe that `Api::CCMenuController#stack` resolves `Stack.from_param!(params[:stack_id])` on the full `Stack` table (bypassing `current_api_client.stack_id` filtering in `BaseController#stacks`), and the response returns `stack B`'s deploy/rollback status (`lastBuildStatus`, `lastBuildLabel`, etc.) even though the token is only authorized for stack `A`.
