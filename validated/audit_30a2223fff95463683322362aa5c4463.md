### Title
Inconsistent `is_aa` vs `definition` AA-visibility checks in oscript evaluation - (File: `formula/evaluation.js`)

### Summary
The `extcodehash` finding is a class of bug where two code paths that are supposed to answer the same yes/no question about an address's state ("does it have code / is it an account with code") use different, non-equivalent conditions and can therefore diverge on edge cases. `ocore`'s oscript/formula engine contains an analogous pattern: the `is_aa` operator and the `definition` operator both answer "is address X a known Autonomous Agent as of `mci`", but they are implemented with different validation logic, so they can disagree on the same address/mci pair.

### Finding Description
In `formula/evaluation.js`, the `is_aa` case simply trusts the `mci` column stored in the `aa_addresses` table: [1](#0-0) 
```
case 'is_valid_address':
case 'is_aa':
	...
	conn.query("SELECT 1 FROM aa_addresses WHERE address=? AND mci<=?", [res, mci], function (rows) {
		cb(rows.length > 0);
	});
```

By contrast, the `definition` case, for the very same purpose (deciding whether an address is a currently-visible AA at `mci`), does an additional stabilization check via `readUnitProps` before trusting the AA definition, explicitly because an AA "could be defined later, e.g. by fresh AA": [2](#0-1) 
```
case 'definition':
	...
	storage.readAADefinition(conn, addr, mci, function (arrDefinition, definition_unit) {
		if (arrDefinition) {
			if (bAA)
				return cb(new wrappedObject(arrDefinition));
			// could be defined later, e.g. by fresh AA
			storage.readUnitProps(conn, definition_unit, function (props) {
				if (props.main_chain_index === null || props.main_chain_index > mci)
					return cb(false);
				cb(new wrappedObject(arrDefinition));
			});
			return;
		}
		...
```

Both ultimately rely on `storage.readAADefinition`, whose underlying query already filters `mci<=?` against the `mci` column recorded in `aa_addresses`: [3](#0-2) 

However, `insertAADefinitions` (called from `writer.js`/`main_chain.js`) records this `mci` for AA-defined ("parameterized"/nested) AAs using the *validation* mci (`validation_mci`) passed in, not necessarily the eventual real stabilization `main_chain_index` of the defining unit — this is exactly why the `definition` operator bothers to re-verify against `readUnitProps(...).main_chain_index` before trusting the row. The `is_aa` operator skips this re-verification entirely and only checks the stored `mci` column. [4](#0-3) 

### Impact Explanation
Because `is_aa(addr)` and `definition(addr)` (and by extension oscript logic branching on "is this an AA") can be evaluated to different boolean results for the exact same address and `mci` in the exact edge case the code comment flags (freshly/nested AA-defined AAs whose stored `mci` does not yet correspond to a stabilized definition), an AA author relying on `is_aa()` to gate a payment or trust decision could have the trigger AA treat an address as an already-live AA when it is not truly stabilized, or vice versa. This is a divergence between two supposedly equivalent state checks in the same deterministic AA execution engine — analogous to the `extcodehash` inconsistency — and can lead to AA fund loss/misrouting (e.g., paying/trusting a not-yet-final AA) if the AA logic depends on `is_aa` rather than `definition` for the same purpose.

### Likelihood Explanation
This requires the specific edge case explicitly called out by the code's own comment ("could be defined later, e.g. by fresh AA") — i.e. an AA that defines another (parameterized/base) AA, where the stored `mci` in `aa_addresses` for the nested AA does not equal its actual stabilized `main_chain_index`. This is a narrow, specific scenario (nested/parameterized AA definitions), making likelihood low, similar to the low-probability rating given to the original `extcodehash` finding.

### Recommendation
Make `is_aa` use the same stabilization check as `definition`: after finding a row in `aa_addresses`, call `storage.readUnitProps` (or equivalent) on the defining unit and confirm `main_chain_index !== null && main_chain_index <= mci` before returning `true`, so both oscript primitives agree on AA visibility for any given `mci`.

### Proof of Concept
1. An AA (`base_aa`) defines a nested/parameterized AA `child_addr` inside its response, so `insertAADefinitions` is invoked with `bForAAsOnly=true` and records `mci` for `child_addr` in `aa_addresses` using the passed-in `validation_mci`/`mci`, not yet the final stabilized `main_chain_index` of the unit that created it.
2. Before the defining unit's `main_chain_index` in `readUnitProps` reflects a value `<= mci` under evaluation, another AA calls `is_aa(child_addr)` in its oscript formula: this returns `true` because `formula/evaluation.js` lines 2201-2213 only checks the stored `mci` column.
3. The same AA (or a different one) calling `definition(child_addr)` at the same `mci` calls the extra `readUnitProps` check (lines 1634-1638) and returns `false`, because the true `main_chain_index` of the defining unit is `null` or greater than `mci`.
4. The two primitives disagree on whether `child_addr` is a live AA for the identical evaluation context, which can be exploited by an AA author to construct logic that behaves inconsistently depending on which primitive is used, e.g., releasing funds to `child_addr` under the assumption it is a validated AA endpoint when `definition()`-based logic in the same or a different AA would have rejected it as not-yet-visible.

		if (arrDefinition[0] !== 'autonomous agent')
