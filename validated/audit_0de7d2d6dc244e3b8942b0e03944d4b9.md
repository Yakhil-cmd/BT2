### Title
Webhook signature is verified against the organization in `repository.owner.login`, but stack/commit lookup uses the unrelated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App / webhook secret to validate the HMAC signature against using `repository_owner`, computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`: [1](#0-0) [2](#0-1) 

Once the signature check passes, `create` dispatches the raw parsed JSON to the registered handlers unmodified: [3](#0-2) 

Every handler (`PushHandler`, `StatusHandler` (via `Commit.where(sha:)`), `CheckSuiteHandler`, pull-request handlers, etc.) resolves the target `Stack`/`Repository`/`Commit` not from `repository.owner.login`, but from an entirely separate field, `repository.full_name`, via `Handler#stacks`/`#repository_name`: [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) 

`Repository.from_github_repo_name` splits `full_name` on `/` and does a straight `find_by(owner:, name:)` lookup with no cross-check against `repository.owner.login`: [8](#0-7) 

Nothing in `Hash#dig('repository','owner','login')` vs `Hash#dig('repository','full_name')` enforces that these two attacker-controlled JSON fields agree. The HMAC signature covers the whole raw payload, but which *secret* is used to check that HMAC is selected using `owner.login`, while the record that is actually looked up and mutated is selected using `full_name`. This is exactly the "TOCTOU-style" analog called out in the report class: a value used to authorize (`webhook_secret` keyed by `repository.owner.login`) is not the same value that is subsequently acted upon (`repository.full_name`).

An attacker who is an admin of any GitHub organization/repository that has its own GitHub App installed on this Shipit instance (and therefore legitimately knows that org's `webhook_secret`, as configured per-organization in `secrets.github.<org>.webhook_secret`) can:
1. Sign a payload with their own org's secret so `verify_webhook_signature` succeeds (`repository_owner` = their own org).
2. Set `repository.full_name` inside that same payload to `"othertenant/some-other-stack"`, a completely unrelated repository/stack hosted by a different tenant on the same Shipit instance.
3. Send this as a `push`, `status`, or `check_suite` event.

Because the handler’s repository/stack resolution keys off `full_name`, not `owner.login`, the forged event is applied to the victim organization's `Stack`/`Commit` records — e.g. triggering `PushHandler#process` → `stack.sync_github(expected_head_sha:)` on a foreign stack, or `StatusHandler#process` → `commit.create_status_from_github!(params)` which fabricates a CI status (`state: "success"`) on a foreign commit.

### Impact Explanation
This breaks the binding "an organization that authenticated versus the repository that is written" explicitly called out as in-scope: the org whose secret validated the request is not the org whose stack/commit is mutated. Forging a `status` event with `state: "success"` for an arbitrary commit sha on a victim's stack can inject a fake passing CI status; combined with Shipit's continuous-deployment logic (deploy conditions based on commit statuses/check runs), this can move an unrelated, cross-tenant stack toward an unauthorized deploy — matching the "Critical: unauthorized deploy" / "cross-repository writes" criteria in the rules.

### Likelihood Explanation
The attacker needs their own org's webhook secret (something a legitimate but unprivileged-relative-to-the-victim org owner has, since they administer their own GitHub App installation) and needs to know/guess the victim's `owner/name` full_name, which is public information (visible in Shipit's own stack URLs) — no access to the victim repository, its GitHub App, or its webhook secret is required. This is realistic in any multi-tenant Shipit deployment where several organizations are configured under `secrets.github`.

### Recommendation
In `WebhooksController#verify_signature`/`create` (and/or `Handler#repository_name`), cross-check that `payload.dig('repository','owner','login')` (the value used to pick the verifying secret) matches the owner segment of `payload.dig('repository','full_name')` before dispatching to handlers, rejecting the request (422) on mismatch.

### Proof of Concept
1. Shipit is configured with two orgs, `attacker-org` and `victim-org`, each with its own `webhook_secret` (`secrets.github.attacker-org.webhook_secret`, `secrets.github.victim-org.webhook_secret`), and `victim-org/app` exists as a Stack.
2. Attacker (owner of `attacker-org`, knows its `webhook_secret`) builds a `push` payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/app"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac_sha1(attacker-org webhook_secret, raw_body)>` and POST to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and the signature validates successfully.
5. `PushHandler#stacks` resolves via `repository.full_name` = `"victim-org/app"`, matching the real victim `Stack`, and enqueues `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` for a repository the attacker never had access to — demonstrating the cross-organization write.
