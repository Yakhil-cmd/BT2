### Title
Unbounded per-condition full-collection rescans in address/asset definition `has`/`has one`/`sum` filters cause CPU amplification - (File: definition.js)

### Summary
`Rack::Utils.select_best_encoding` is quadratic because it re-scans the entire parsed header collection once for every wildcard entry instead of caching/limiting the work per entry. The ocore analog is `evaluateFilter()` inside `validateAuthentifiers()` in `definition.js`, which is invoked once per `has`/`has one`/`has equal`/`has one equal`/`sum` node found while evaluating an address or asset spending-condition tree. Each invocation performs a fresh, unbounded scan of the *entire* `objUnit.messages` array and every `inputs`/`outputs` array within it, with no memoization across sibling filter nodes in the same definition tree.

### Finding Description
`evaluateFilter(op, filter, handleResult)` re-iterates `objUnit.messages` and, for matching payment messages, `payload.inputs` or `payload.outputs`, on every single call: [1](#0-0) [2](#0-1) 

The definition-tree evaluator dispatches to this function for `has`/`has one` (via `augmentMessagesAndEvaluateFilter`) and for `sum`/`has equal`/`has one equal`, each of which is just another leaf in an `and`/`or`/`r of set`/`weighted and` tree: [3](#0-2) [4](#0-3) 

The recursive tree evaluator `evaluate()` only bounds the *number* of tree nodes via `complexity`/`count_ops` counters incremented once per node: [5](#0-4) 

Crucially, these counters bound how many filter *nodes* can appear in a definition, but they do **not** account for the cost of the O(messages × inputs/outputs) work each `evaluateFilter` call performs. Just like the Rack bug — where the fix was to compute `accept_encoding.map(&:first)` once instead of once per wildcard — here the full message/input/output scan should be cached/computed once per unit and reused across all filter nodes, not repeated for every `has`/`sum` leaf. An attacker who controls both the address definition (posted in the same unit or referenced by it) and the payment messages of that unit can maximize `messages.length` and `inputs`/`outputs` length (each bounded by `MAX_INPUTS_PER_PAYMENT_MESSAGE`/`MAX_OUTPUTS_PER_PAYMENT_MESSAGE`/`MAX_MESSAGES_PER_UNIT`, exact values not confirmed from the index) and stack multiple `has`/`sum` conditions inside an `and`/`or`/`r of set` tree (each such node consuming only 1 complexity point) to multiply the number of full O(n) rescans performed during validation of a single unit.

I was unable to retrieve the exact numeric values of `constants.MAX_COMPLEXITY`, `constants.MAX_OPS`, `constants.MAX_MESSAGES_PER_UNIT`, `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE`, and `constants.MAX_OUTPUTS_PER_PAYMENT_MESSAGE` from the index (searches located the identifiers in `constants.js` but content wasn't returned before the tool budget ran out); confirming the exact worst-case multiplier requires reading `constants.js` directly.

### Impact Explanation
Every unit that is validated goes through `validateDefinition`/`validateAuthentifiers` for its address definitions and (if applicable) asset issue/transfer conditions. An attacker who posts a single unit with a crafted definition (many `has`/`sum` leaves inside `and`/`or`) referencing a payment message with the maximum allowed number of inputs/outputs forces the validating node to repeat full linear scans of the message/input/output arrays once per leaf node, multiplying CPU cost for that single unit's validation. Because every full node performs this same validation before accepting/relaying the unit, this is a network-wide CPU amplification affecting all nodes that validate the unit — a denial-of-service vector reachable by any unprivileged unit poster, consistent with the CWE-400/407 classification of the source report.

### Likelihood Explanation
The construct is reachable directly from unit content that any user can post — no special privileges, hub/hub-operator, or network position is required. The `and`/`or`/`r of set`/`weighted and` combinators are ordinary, documented address-definition primitives, and `has`/`has one`/`sum`/`has equal`/`has one equal` are ordinary spending-condition primitives, so building a deeply-repeated filter tree is straightforward. The only limiting factors are the (unconfirmed) numeric constants bounding definition complexity, ops, and messages/inputs per unit, which determine whether the resulting amplification is severe enough to be practically exploitable.

### Recommendation
Refactor `evaluateFilter`/`validateAuthentifiers` in `definition.js` to precompute the list of relevant inputs/outputs (optionally per filter "what"/asset combination) once per unit validation and reuse it across all `has`/`has one`/`sum` nodes in the same tree, rather than rescanning `objUnit.messages` from scratch on every node evaluation — mirroring the fix pattern in the Rack advisory (hoist the expensive recomputation out of the per-item loop). Additionally, consider counting the cost of `evaluateFilter` (proportional to `messages.length * inputs/outputs.length`) toward the existing `complexity`/`count_ops` budget in `evaluate()` at [6](#0-5)  so that node validators can bound total work rather than just node count.

### Proof of Concept
Conceptual PoC (exact numeric limits need to be confirmed against `constants.js`):
1. Craft a unit whose address (or asset) definition is a large `and`/`or` tree containing the maximum number of `has`/`sum` leaves allowed by `MAX_COMPLEXITY`/`MAX_OPS`.
2. In the same unit, include a payment message with the maximum allowed number of inputs/outputs (`MAX_INPUTS_PER_PAYMENT_MESSAGE`/`MAX_OUTPUTS_PER_PAYMENT_MESSAGE`), and/or the maximum number of messages per unit.
3. Post the unit for validation. Each `has`/`sum` leaf triggers a full independent scan of `objUnit.messages`/`inputs`/`outputs` in `evaluateFilter` ( [1](#0-0) ), so total validation cost scales with `(number of filter leaves) × (messages) × (inputs/outputs per message)` instead of a single linear pass, amplifying CPU time for every validating node relative to a definition with a single filter condition.
