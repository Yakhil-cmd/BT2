### Title
Orphaned `tmp-err-*` temp files accumulate in `--root` when process is killed between `os.CreateTemp` and `os.Rename` in `writeContent` - ([File: pkg/logging/logging.go])

### Finding Description
`(*Logger).writeContent` implements a create-temp-then-rename pattern: it calls `os.CreateTemp(l.root, "tmp-err-")`, writes content, and then `os.Rename`s the temp file to the final `errorFile` path. [1](#0-0) 

This function is reachable every sync cycle through `log.Error` and `log.ExportError`, both of which are invoked whenever `SyncRepo` fails (e.g., on a broken/corrupt ref). [2](#0-1) [3](#0-2) 

The main sync loop wraps each `SyncRepo` call in a per-cycle `context.WithTimeout(context.Background(), *flSyncTimeout)`. [4](#0-3) 

However, this `ctx` is passed to git subcommands (`git.Run`, `git.fetch`, etc.) — it is **not** wired to `os.CreateTemp`/`os.Write`/`os.Rename` in `writeContent`, since those are plain blocking syscalls that ignore Go contexts entirely. A context deadline expiring cannot "kill" `writeContent` mid-flight the way described in the question — Go doesn't preempt goroutines that way, and there's no `os.Exit` or signal delivery tied to the sync-timeout context expiring inside the logging path itself. The only way `writeContent` would be interrupted mid-execution (leaving a temp file with no matching rename) is an external SIGKILL of the whole process (e.g., OOM-kill, kubelet killing the container, or a real crash) — none of which the question's threat model (unprivileged attacker who only controls repo content/refs) can trigger. The attacker can force `ExportError`/`log.Error` to run every period by force-pushing a broken ref, but cannot control process termination timing to line up with the microseconds-wide window between `CreateTemp` and `Rename`.

Additionally, there is no cleanup routine anywhere in the codebase that removes stale `tmp-err-*` files left in `--root` (no `Glob`/`RemoveAll` targeting that prefix was found), so *if* such an orphan were ever created (e.g., by a real crash unrelated to attacker input), it would persist indefinitely. But this is a general robustness/best-practice gap, not something the attacker can trigger repeatably from a normal fetch-failure loop without already possessing the ability to crash/kill the process — which is outside the stated attacker capability set (unprivileged, no exec, no mount/pod-spec control).

### Impact Explanation
Even in the worst case, each fetch failure produces at most one `writeContent` call per sync period (bounded by `--period`, minimum 10ms in practice but realistically seconds), and each call, on success, atomically replaces the single `errorFile` via rename — it does not accumulate multiple live temp files under normal, uninterrupted execution. The scenario requires the process to be repeatedly killed exactly inside the ~microsecond `CreateTemp`→`Rename` window on every cycle, which cannot be induced by ref/content manipulation alone.

### Likelihood Explanation
Not exploitable by the stated attacker. The attacker can force repeated `ExportError`/`writeContent` invocations by keeping a ref broken, but cannot cause SIGKILL-timed process termination mid-write from outside the container without additional privileges (node access, ability to send signals, or control of the Pod's restart/liveness behavior), which are explicitly out of scope. The `--sync-timeout` context does not propagate into `writeContent`'s file operations, so context expiry alone does not kill or interrupt this function.

### Recommendation
No fix required based on the stated threat model. If defense-in-depth is desired regardless: add a best-effort cleanup pass at startup (and/or before each `writeContent` call) that globs and removes stale `tmp-err-*` files in `--root` older than some threshold, similar to patterns used elsewhere in the codebase for worktree cleanup.

### Proof of Concept
Not applicable — no code-level PoC can demonstrate attacker-triggered (ref/content-only) process termination lining up with the `CreateTemp`/`Rename` window; doing so requires external process-kill capability outside the granted attacker model.

// Error implements logr.Logger.Error.
func (l *Logger) Error(err error, msg string, kvList ...any) {
	l.Logger.WithCallDepth(1).Error(err, msg, kvList...)
	if l.errorFile == "" {
		return
	}
	payload := struct {
		Msg  string
		Err  string
		Args map[string]any
	}{
		Msg:  msg,
		Args: map[string]any{},
	}
	if err != nil {
		payload.Err = err.Error()
	}
	if len(kvList)%2 != 0 {
		kvList = append(kvList, "<no-value>")
	}
	for i := 0; i < len(kvList); i += 2 {
		k, ok := kvList[i].(string)
		if !ok {
			k = fmt.Sprintf("%v", kvList[i])
		}
		payload.Args[k] = kvList[i+1]
	}
	jb, err := json.Marshal(payload)
	if err != nil {
		l.Logger.Error(err, "can't encode error payload")
		content := fmt.Sprintf("%v", err)
		l.writeContent([]byte(content))
	} else {
		l.writeContent(jb)
	}
}

// ExportError exports the error to the error file if --export-error is enabled.
func (l *Logger) ExportError(content string) {
	if l.errorFile == "" {
		return
	}
	l.writeContent([]byte(content))
}
