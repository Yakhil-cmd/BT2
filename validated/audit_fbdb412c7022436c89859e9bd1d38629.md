## Title
Webhook signature verification is bound to the organization named in the untrusted payload, not to the repository the event handlers act on, allowing a valid webhook secret from one onboarded org to forge events against another org's stacks - ([File: app/controllers/shipit/webhooks_controller.rb])

## Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate a webhook against based on a field taken from the **unverified** JSON body (`repository.owner.login` / `organization.login`), then, once "verified", every `Webhooks::Handlers::Handler` subclass resolves the target `Stack`/`Repository` using a *different* field from the same unverified body (`repository.full_name`). Nothing ties the two together, so the equality the signature is supposed to enforce - "the organization whose secret signed this request" == "the organization whose repository this event acts on" - is never checked.

## Finding Description
`Shipit` supports multiple GitHub organizations on a single engine instance, each with its own independent `webhook_secret` in `secrets.github` [1](#0-0) , resolved through `Shipit.github(organization:)` / `Shipit.github_app_config` [2](#0-1) .

The webhook entry point picks which organization's secret to verify against using a value pulled straight out of the raw request body, before any cryptographic check has occurred: [3](#0-2) [4](#0-3) 

Once `verify_signature` passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the same parsed body to handler classes [5](#0-4) . Every handler resolves the affected repository/stacks from a *different* field of that same body: [6](#0-5) 

Neither the controller nor the base `Handler` cross-validates that `repository.owner.login` (used to pick the verifying secret) matches the owner embedded in `repository.full_name` (used to pick the acted-upon repository). Since this endpoint accepts any raw HTTP POST (it does not depend on the request actually having originated from GitHub's relay, only on the HMAC matching some configured org's secret), an attacker who legitimately controls one onboarded GitHub organization - and therefore possesses that organization's own `webhook_secret` (configured when that org's Shipit GitHub App was set up) - can:
1. Craft an arbitrary JSON payload with `repository.owner.login` set to their **own** organization (so `Shipit.github(organization: repository_owner)` resolves to their own, legitimately-known secret and `verify_webhook_signature` succeeds), and
2. Set `repository.full_name` to `"victim-org/victim-repo"` - a repository belonging to a completely different tenant hosted on the same Shipit instance.

The signature check binds trust to "org A signed this," but the handler dispatch binds action to "act on whatever `repository.full_name` says," and those are never required to be the same organization. This exactly mirrors the reported bug class: a value used for one authorization decision (`royaltyVault.royaltyAsset` vs. `payableToken`, here: signing org vs. acted-upon repository) is never checked for consistency with the value later relied upon for the actual state change.

## Impact Explanation
Concretely reachable handlers let the attacker act against a victim org's stacks using only their own org's webhook secret:
- `PushHandler#process` runs `stack.sync_github(expected_head_sha: params.after)` against every non-archived stack of the victim repo matching the pushed branch [7](#0-6) , forcing `GithubSyncJob` to run using the Shipit app's own GitHub credentials against a repository the attacker does not own.
- `StatusHandler#process` creates a `Status` record on an arbitrary victim commit sha directly from attacker-controlled `state`/`context`/`description` fields [8](#0-7) , letting the attacker inject a forged "success" CI status into Shipit's own status bookkeeping for a commit that never actually passed CI on GitHub - `Commit#create_status_from_github!` and downstream deploy-gating logic consume these `Status` rows.
- `CheckSuiteHandler#process` schedules a check-run refresh for arbitrary victim commits [9](#0-8) .

Forged "success" statuses feeding Shipit's own deployability checks can enable an **unauthorized deploy** on a stack belonging to an organization the attacker does not control, which matches the report's High-severity impact bar (unauthorized deploy) even though this analog requires the attacker to already legitimately administer some other onboarded org on the same instance - it crosses the trust boundary between tenants, not within one.

## Likelihood Explanation
This requires the Shipit instance to be configured in the documented multi-organization mode (multiple entries under `secrets.github`, each with `webhook_secret` [10](#0-9) ) and requires the attacker to be a legitimate administrator of at least one of those onboarded organizations (able to read/know their own webhook secret, or simply able to configure it during onboarding). Given that constraint it is a straightforward, repeatable HTTP POST with no cryptographic breaking involved - only a payload field the code fails to cross-check.

## Recommendation
In `WebhooksController#verify_signature` (or in `Webhooks::Handlers::Handler`), after signature verification succeeds, assert that the organization whose secret validated the request actually owns the repository named in `repository.full_name` / used to resolve `stacks`. Concretely: derive `repository_owner` once, verify the signature with it, and then require `payload.dig('repository', 'owner', 'login')` used by the handler to resolve `Repository.from_github_repo_name(repository_name)` matches the same, already-verified owner - rejecting (422) any event whose acted-upon repository owner differs from the verifying organization.

## Proof of Concept
1. Configure two organizations, `org-a` and `org-b`, each with distinct `webhook_secret`s under `secrets.github` (multi-tenant setup as documented) [11](#0-10) .
2. As an administrator of `org-a`, compute a valid HMAC-SHA1 signature for a crafted JSON body using `org-a`'s own `webhook_secret`, per `DeliverySigner`/`verify_webhook_signature` logic [12](#0-11) , where the body is:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/victim-repo"
  }
}
```
3. POST this body to `/webhooks` with `X-Github-Event: push` and `X-Hub-Signature: sha1=<computed>`.
4. `verify_signature` resolves `repository_owner` = `"org-a"`, fetches `org-a`'s config, and the HMAC matches, so the request passes [3](#0-2) .
5. `PushHandler` resolves `repository_name` = `"org-b/victim-repo"` from the same payload and runs `sync_github` against `org-b`'s stacks [6](#0-5) [7](#0-6) , an action gated on `org-a`'s secret but executed against `org-b`'s repository.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
