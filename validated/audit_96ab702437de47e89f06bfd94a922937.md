### Title
Unsanitized peer-controlled contract text/title injected into wallet chat display via `prosaic_contract_offer`/`prosaic_contract_response` device messages - ([File: wallet.js])

### Summary
`wallet.js`'s `handleMessageFromHub` accepts `prosaic_contract_offer` and `prosaic_contract_response` device messages from any paired correspondent and re-emits the peer-supplied `title`/`text` fields verbatim as a chat `"text"` event that the wallet UI renders to the user, with no stripping of control/escape characters — the same bug class as the reported `openssl_encrypt` "info" terminal-injection CVE (unsanitized metadata printed/rendered to the user, letting an attacker repaint/forge the displayed verification text).

### Finding Description
When a paired device sends a `prosaic_contract_offer`, `wallet.js` validates only structural fields (address validity, hash, date format) and then does: [1](#0-0) 
storing the attacker-controlled `body.title`/`body.text` and immediately emitting them as a normal chat `"text"` event:
```
var chat_message = "(prosaic-contract:" + Buffer.from(JSON.stringify(body), 'utf8').toString('base64') + ")";
eventBus.emit("text", from_address, chat_message, ++message_counter);
```
On contract response, the peer-chosen `title` (stored from the original, also peer-supplied, offer) is concatenated directly into a plain-text chat message: [2](#0-1) 
```
eventBus.emit("text", from_address, "contract \""+objContract.title+"\" " + body.status, ++message_counter);
```
Neither `title` (`VARCHAR(1000)`) nor `text` (`TEXT`, unbounded) is checked for or stripped of terminal/ANSI control sequences before being handed to `eventBus.emit("text", …)`, which per the code comment "the wallet should have an event handler that displays the text to the user": [3](#0-2) 
The generic `"text"` message path applies only cosmetic regex stripping of the contract/dispute markup tags themselves, not of control characters: [3](#0-2) 
The same unsanitized `title`/`text` pattern also exists in `arbiter_contract.js`'s `createAndSend`/`store`, where a peer-controlled `title`/`text` (plus `amount`/`asset`) is persisted and surfaced to the counterparty's wallet UI for contract review/signature confirmation: [4](#0-3) [5](#0-4) 

### Impact Explanation
A malicious paired device (a correspondent the victim has legitimately paired with, e.g., for a prosaic/arbiter contract or shared address) can embed terminal/ANSI escape sequences or other control characters in the `title`/`text` of a contract offer. Because this content is displayed by the wallet UI as trusted "contract" verification text — the exact text the user relies on before approving `respond("accepted", …)` which triggers `composer.composeAuthorsAndMciForAddresses` and message signing — an attacker can repaint/forge what the user sees (e.g., hide or alter the true contract terms, disguise a malicious "accepted"/"declined" status, or spoof a different party name/amount context) to induce the user to sign or fund a shared address/contract they did not actually intend to approve. This maps to the CVE class of forging verification information shown to the user, and in the ocore context that forged confirmation directly precedes user-authorized signing/funding actions, creating a path toward unauthorized spending (the user is deceived into co-signing a shared address / accepting arbiter contract terms different from what is displayed).

### Likelihood Explanation
Any device the user has paired with (a normal, low-privilege trust relationship — not requiring hub or node compromise) can send `prosaic_contract_offer`/`prosaic_contract_response`/`arbiter_contract_offer` messages with arbitrary `title`/`text` content; the only server-side checks are on hash, date format, and address validity, none of which constrain the character set of `title`/`text`. This is trivially reachable by simply crafting the JSON payload sent over `sendMessageToDevice`.

### Recommendation
Strip or escape terminal control characters (e.g. `\x1B`, other C0/C1 control codes) from `title` and `text` fields in `prosaic_contract_offer`, `prosaic_contract_response`, `prosaic_contract_shared`, and the analogous `arbiter_contract_*` handlers in `wallet.js`/`arbiter_contract.js` before storing them and before emitting them via `eventBus.emit("text", …)`, and document that any downstream UI must treat these fields as attacker-controlled untrusted display strings.

### Proof of Concept
1. Pair a malicious device with the victim's wallet.
2. Send a `prosaic_contract_offer` device message with `title`/`text` containing ANSI escape sequences designed to overwrite/hide prior terminal or UI output (e.g. `\x1b[2J\x1b[H` plus forged "verified" text), satisfying only the existing checks (valid addresses, correct hash, valid `creation_date`).
3. The victim's wallet receives and stores the offer and displays the injected `chat_message` unmodified via the `"text"` event.
4. Repeat with `prosaic_contract_response` using a crafted `objContract.title` value to forge the "accepted/declined" notification text shown to the user before they rely on it to proceed with signing/funding the shared address.

Note: The concrete rendering/sanitization behavior lives in the wallet UI layer, which is outside this repository (`ocore`); this analysis is based on what `ocore` supplies to that UI layer via `eventBus.emit("text", …)` without sanitization.
