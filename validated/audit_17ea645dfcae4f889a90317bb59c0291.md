### Title
Webhook signature is verified against an attacker-chosen organization while the event is applied to a different, attacker-chosen repository - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and therefore which HMAC `webhook_secret`) to validate a webhook payload against using `repository_owner`, a value taken directly from the unauthenticated request body (`params.dig('repository','owner','login')` or `params.dig('organization','login')). Once the signature check passes, `create` dispatches the *entire same payload* to handlers, which independently determine the repository/stack to mutate using a different field, `payload.dig('repository','full_name')` in `Shipit::Webhooks::Handlers::Handler#repository_name`. Because the org used to pick the verification secret and the repo used to pick the mutated stack are two independently attacker-supplied fields in the same JSON body, they are never required to agree.

### Finding Description
In a multi-organization Shipit deployment (documented in `docs/setup.md` "Using Multiple Github Applications"), each configured GitHub organization has its own `webhook_secret` in `secrets.yml`, retrieved via `Shipit.github(organization: ...)`: [1](#0-0) 

The webhook endpoint verifies authenticity like this: [2](#0-1) 

Note that `repository_owner` is derived purely from the JSON body (`params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`), so it is fully attacker-controlled in the request that is being verified.

Once `verify_signature` passes, `create` forwards the same raw payload to the registered handlers: [3](#0-2) 

Every handler resolves the target repository/stack from a *different* field of the same payload, `repository.full_name`, not `repository.owner.login`: [4](#0-3) [5](#0-4) 

For example `PushHandler` calls `stack.sync_github(expected_head_sha: params.after)` for every stack of the resolved repository, and `StatusHandler` writes commit statuses: [6](#0-5) [7](#0-6) 

**The broken binding**: the code implicitly assumes `repository.owner.login` (used to select the signing organization) equals the owner segment of `repository.full_name` (used to select the mutated repository/stack). Nothing in `verify_signature` or in `Handler#repository_name` enforces this equality. An operator who legitimately controls one configured GitHub App/organization ("Org A", with a known `webhook_secret`) can compute a valid `X-Hub-Signature` for a payload whose `repository.owner.login` is `"org-a"` (so the signature check passes using Org A's secret) while `repository.full_name` is set to `"org-b/victim-repo"` (so the handler acts on Org B's stack). This breaks the equality:

`organization that authenticated (repository.owner.login → Org A's secret) == repository that is written (repository.full_name → Org B's repo)`

### Impact Explanation
This allows cross-organization/cross-repository writes without any credential belonging to the victim organization: an attacker who only holds the webhook secret for their own configured org can force `sync_github`, commit-status creation, `check_suite` refreshes, pull-request label/assignment updates, or membership changes against a completely unrelated repository/stack that belongs to a different organization configured on the same Shipit instance. This matches the "Critical - cross-repository writes / unauthorized deploy/rollback trigger" impact bucket, since `sync_github` can advance the deployable head and downstream deploy automation for a stack the attacker does not own.

### Likelihood Explanation
Requires a Shipit instance configured with more than one GitHub organization/app (an explicitly documented, supported configuration in `docs/setup.md`). The attacker must control one of the configured orgs (and thus know that org's own `webhook_secret`, which they legitimately possess as the owner of that GitHub App installation) but needs zero credentials belonging to the victim organization/repository. No Shipit account, session, or API token is required — only the ability to POST to the public `/webhooks` endpoint with a validly-signed body for their own org.

### Recommendation
After `verify_signature` succeeds, enforce that the organization whose secret validated the signature actually owns the repository referenced by the payload's `repository.full_name`/`repository.owner.login` used by the handlers — e.g. compare `repository_owner` against the owner segment resolved by `Handler#repository_name`, and reject the request if they differ. Alternatively, resolve the target `Repository`/`Stack` first and verify the signature using the `webhook_secret` associated with that repository's actual `owner`, rather than a value taken independently from the payload body.

### Proof of Concept
1. Shipit is configured with two orgs in `secrets.yml`: `org-a` (attacker-controlled GitHub App, secret known to attacker) and `org-b` (victim, stack `org-b/victim-repo` configured in Shipit).
2. Attacker crafts a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha, e.g. a stale/old commit>",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(org-a's webhook_secret, raw_body)` — valid, since they legitimately know `org-a`'s secret.
4. POST to `/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` reads `repository_owner` → `"org-a"`, fetches `org-a`'s app, and verification succeeds against the correct-but-irrelevant secret.
6. `create` dispatches to `PushHandler`, which resolves `repository_name` from `repository.full_name` → `"org-b/victim-repo"`, finds `org-b`'s stacks, and calls `stack.sync_github(expected_head_sha: params.after)` — mutating a stack in an organization the attacker does not control and for which the attacker never proved knowledge of the correct webhook secret.

    # Backward compatibility
    # nil signifies the single github app config schema is being used

    end

    @github[organization] ||= GitHubApp.new(organization, config)
  end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
