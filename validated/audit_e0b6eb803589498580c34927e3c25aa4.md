### Title
Webhook signature is verified against the org derived from `repository.owner.login`, but Shipit's handlers act on the unrelated `repository.full_name` field, letting any onboarded GitHub org forge status/push/check events for another org's stacks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` picks the HMAC secret to validate a webhook against by reading `repository.owner.login` (or `organization.login`) out of the *same, attacker-supplied* JSON body, via `Shipit.github(organization: repository_owner)`. [1](#0-0) [2](#0-1)  Every downstream `Webhooks::Handlers::Handler` subclass, however, resolves *which repository/stack to mutate* using a completely different field of that same body: `repository.full_name`. [3](#0-2)  In a multi-org deployment (the documented `config/secrets.*.yml` schema supports several GitHub orgs, each with its own `webhook_secret`) [4](#0-3)  this creates a mismatch: the signature only proves "this request knows OrgA's webhook secret," but the handler code trusts `repository.full_name`, which can name a stack belonging to any other onboarded org (OrgB, OrgC, ...).

### Finding Description
`Shipit.github(organization:)` looks up per-organization config (`app_id`, `webhook_secret`, etc.) keyed by whatever organization name is passed in. [5](#0-4)  The controller passes `repository_owner`, computed strictly from the untrusted JSON payload:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

So the signature check only establishes: "the sender knows the secret configured for org X," where X is *self-reported* in the body. It does **not** establish that X is the org that actually owns the repository the handlers will act on, because `repository.owner.login` and `repository.full_name` are independent, uncorrelated strings inside the same JSON blob, and Shipit's business logic uses only `repository.full_name`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

`StatusHandler`, `PushHandler`, `CheckSuiteHandler`, and all the `PullRequest::*Handler`s follow the same pattern - they look up a `Commit`/`Repository`/`Stack` by fields taken from the body (`sha`, `repository.full_name`) with **no cross-check** that the resolved repository belongs to the organization whose secret was used for signature verification. [6](#0-5) [7](#0-6) 

Because an attacker who legitimately administers a GitHub org "OrgA" that is onboarded to this Shipit instance can configure a real GitHub webhook on their own repo pointing at Shipit, they control the exact HMAC signature Shipit expects for "OrgA" (they know/observe OrgA's `webhook_secret` value functionally by being able to trigger real signed deliveries, and can replay/craft arbitrary bodies signed with that secret via a curl-based forged delivery, since GitHub webhook secrets are typically also visible/settable by org admins on the GitHub side). By setting:
* `repository.owner.login` = `"OrgA"` (so `verify_signature` selects OrgA's app/secret and passes),
* `repository.full_name` = `"OrgB/victim-repo"` (a repository under a *different*, unrelated org OrgB that also happens to be onboarded to the same Shipit instance),

the attacker produces a payload that passes `verify_signature` yet is processed by handlers as if it originated from OrgB's repository - because the handler never re-checks `repository.owner.login` or ties it to the resolved `Repository` record.

This is the equality the code is supposed to maintain but does not:
`organization whose secret authenticated the request == organization owning the repository the handler mutates`

Instead the code enforces only:
`organization whose secret authenticated the request == organization named in repository.owner.login (self-reported, attacker controlled)`
while separately trusting `repository.full_name` (also self-reported, attacker controlled, and never checked against `repository.owner.login`) to select the target `Stack`/`Commit`.

### Impact Explanation
The most damaging handler is `StatusHandler`, which creates a `Status` on any `Commit` matching the forged `sha` for the resolved repository, regardless of which org's secret validated the request:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [8](#0-7) 
`Commit.where(sha:)` is a global lookup not scoped to a repository at all, so a forged, but validly-*signed-by-a-different-org* status event can flip CI status ("success"/"failure") for a commit belonging to a completely unrelated stack. Since `shipit.yml`'s `ci.require` gate relies on these `Status` records to decide whether a commit is deployable, this can be used to satisfy CI requirements for a commit the attacker does not control, contributing to an unauthorized deploy path. `PushHandler` similarly triggers `stack.sync_github` for the resolved (out-of-org) stack, and `CheckSuiteHandler`/`PullRequest::*Handler`s perform state changes (archiving/unarchiving review stacks, updating PR metadata) on stacks outside the authenticating org's control.

### Likelihood Explanation
Exploitation requires the attacker to be an administrator of at least one GitHub organization that is already onboarded to the target Shipit instance (so they can obtain/observe that org's webhook secret through legitimate GitHub webhook configuration), and requires the Shipit instance to be running the multi-organization GitHub config (`Shipit.github(organization:)` keyed lookup) with more than one org onboarded. This is a realistic configuration for any Shipit deployment shared across multiple GitHub organizations, which the engine explicitly documents and supports. [4](#0-3)  No repository write access, GitHub App private key, or `api_clients_secret` is needed - only administrative control of one onboarded org's webhook configuration, which is a materially weaker privilege than the org actually targeted.

### Recommendation
In `WebhooksController#verify_signature` (and/or `Webhooks::Handlers::Handler`), bind the two values together: after resolving the target `Repository`/`Stack` via `repository.full_name`, verify that its `owner` matches the `repository_owner` (or `organization.login`) that was used to select the signing secret, and reject the event (422) if they diverge. This restores the invariant that the org whose secret validated the signature is the same org whose repository is being mutated.

### Proof of Concept
1. Configure a Shipit instance with the multi-org GitHub schema, onboarding `OrgA` (attacker-administered) and `OrgB` (victim) as shown in `config/secrets.development.shopify.yml`. [4](#0-3) 
2. As an admin of `OrgA`, configure/observe a real GitHub webhook delivery from an `OrgA` repo to the Shipit `/github_hooks` endpoint (event `status`), obtaining a validly-signed body (or independently deriving the ability to produce `X-Hub-Signature` for `OrgA`'s configured `webhook_secret`).
3. Craft a payload where:
   - `sha` = the sha of a commit belonging to a stack under `OrgB/victim-repo`,
   - `repository.owner.login` = `"OrgA"`,
   - `repository.full_name` = `"OrgB/victim-repo"`,
   - `state` = `"success"`, `context` = the CI context required by `OrgB/victim-repo`'s `shipit.yml` `ci.require`.
4. Sign the raw body with `OrgA`'s `webhook_secret` and POST it to `/github_hooks` with `X-Github-Event: status`.
5. `verify_signature` resolves `Shipit.github(organization: "OrgA")` and the signature validates successfully. [1](#0-0) 
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and calls `create_status_from_github!`, creating a "success" status on `OrgB`'s commit despite the request never being authenticated against `OrgB`'s secret. [8](#0-7) 

Note: I could not fully verify at what point/how GitHub webhook secrets become practically knowable to an org admin versus being purely server-side Shipit configuration secrets (this depends on operational practices outside the indexed code, e.g., whether the same secret value is shared between the GitHub-side webhook config and Shipit's `secrets.github` entry, which is typical setup but not verifiable purely from this repository). This affects the practical likelihood but not the root-cause code defect itself, which is clearly present: signature-selection field and mutation-target field are different, uncorrelated, attacker-controlled JSON fields.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
