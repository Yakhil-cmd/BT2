### Title
Stack-scoped ApiClient token bypasses its stack authorization in CCMenuController - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` authenticates a caller-supplied `token` param against `ApiClient` but resolves the target `Stack` with an unscoped lookup, breaking the binding "stack a token authorizes" == "stack it touches" that every other API controller enforces through `Shipit::Api::BaseController`.

### Finding Description
`Shipit::Api::BaseController#stacks` restricts the queryable `Stack` set to the token's own `stack_id` when the `ApiClient` is stack-scoped: [1](#0-0) 

Every controller under `Shipit::Api` that calls the inherited `stack` method is protected by this scoping. `CCMenuController`, however, overrides both the authentication and the stack-resolution methods: [2](#0-1) 

`authenticate_api_client` still calls `ApiClient.authenticate(params[:token])`, which validates the signed token and returns the matching `ApiClient` record (with its associated `stack_id`, permissions, etc.): [3](#0-2) 

But the overridden `stack` method ignores `current_api_client.stack_id` entirely, doing `Stack.from_param!(params[:stack_id])` against the full `Stack` table instead of the scoped `stacks` relation used everywhere else: [4](#0-3) 

The only authorization check performed is `require_permission :read, :stack`, which merely checks that `"read:stack"` is present in the client's `permissions` array — it does not verify which stack the permission was granted for: [5](#0-4) [6](#0-5) 

The signed token cryptographically only binds an `ApiClient` id (via `SimpleMessageVerifier`); it never binds the target `stack_id` into the signature payload itself — the scoping is enforced purely by application code that looks up `current_api_client.stack_id` and constrains the `Stack` relation. Because `CCMenuController` reimplements stack lookup without that constraint, the equality **"stack a token authorizes" == "stack it touches"** is broken: a valid, signed token that is only supposed to authorize reads of Stack A can be used with `?stack_id=B&token=...` to read Stack B's CI status/deploy state, as long as the token has the generic `read:stack` permission.

### Impact Explanation
This matches the "High" tier: unauthenticated escalation into stack-scoped authorization — an `ApiClient` token deliberately restricted to one stack (e.g. the CCMenu tokens minted by `CCMenuUrlController`, or any stack-scoped client created by an administrator) can be replayed against `CCMenuController#show` for any other stack to read its deploy status, last build label/time, and lock state. This is a read of stack state outside the token's intended authorization boundary.

### Likelihood Explanation
Any holder of a valid `read:stack`-permissioned token (which is routinely embedded in CCMenu URLs, e.g. for CI dashboard integrations, as generated by `CCMenuUrlController`) can trivially trigger this by changing the `stack_id` query parameter — no privileged access, session, or additional secret is required beyond possession of one token meant for a single stack.

### Recommendation
Have `CCMenuController#stack` reuse the scoped `stacks` relation from `BaseController` (i.e., `stacks.from_param!(params[:stack_id])`) instead of querying `Stack` directly, so that stack-scoped `ApiClient` tokens cannot be used to access other stacks.

### Proof of Concept
1. Administrator creates (or the engine auto-creates via `CCMenuUrlController#client`) an `ApiClient` scoped to `stack_id = A` with `permissions: ["read:stack"]`, and obtains its `authentication_token`.
2. Attacker (who obtained this token, e.g. from an exposed CCMenu URL for stack A) sends:
   `GET /api/1/stacks/<B_owner>/<B_repo>/<B_branch>/ccmenu.xml?token=<A's token>`
3. `authenticate_api_client` in `CCMenuController` validates the token via `ApiClient.authenticate` and succeeds (token is valid, signature checks out).
4. `require_permission :read, :stack` passes because the client's `permissions` includes `"read:stack"` regardless of which stack it was scoped to.
5. `stack` resolves `Stack.from_param!(params[:stack_id])` against stack B directly, bypassing the `stacks` scoping that would have restricted the client to stack A only.
6. The response renders stack B's deploy status/build info even though the token was only meant to authorize stack A.
