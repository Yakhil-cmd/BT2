### Title
Webhook signature verification is bound to `repository.owner.login`/`organization.login` while write actions are bound to `repository.full_name`, enabling cross-organization webhook forgery when any configured GitHub org has no `webhook_secret` - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which per-organization `GitHubApp` (and therefore which `webhook_secret`) to validate the request against based on `repository.owner.login` (or `organization.login`) taken directly from the untrusted, attacker-supplied JSON body. [1](#0-0) [2](#0-1)  The handler that actually performs the write action (e.g. `PushHandler`) resolves the target `Repository`/`Stack` using a *different* field from the same body: `repository.full_name`. [3](#0-2)  Because `GitHubApp#verify_webhook_signature` short-circuits to `true` whenever that organization's `webhook_secret` is blank (documented as optional), any organization configured without a secret becomes a skeleton key: an attacker can set `repository.owner.login` to that secret-less org to pass verification, while setting `repository.full_name` to any other tracked repository, causing Shipit to execute webhook side effects (sync, status updates, PR handling) against a target it never actually authenticated.

### Finding Description
- The verification path picks the app config purely off attacker-controlled JSON: [1](#0-0) [2](#0-1) 

- `Shipit.github(organization:)` looks up per-org config from `secrets.github` (multi-org schema), and `GitHubApp#verify_webhook_signature` explicitly bypasses HMAC checking when that org has no secret configured: [4](#0-3) [5](#0-4) 

- The `webhook_secret` is explicitly documented as optional per organization in the multi-org configuration schema: [6](#0-5) [7](#0-6) 

- After the (bypassable) signature check, `WebhooksController#create` dispatches the *entire raw payload* to handlers, none of which re-derive or cross-check the organization used for signing: [8](#0-7) 

- Every handler resolves its target purely from `repository.full_name`, independent of `repository.owner.login`/`organization.login` used earlier for signature selection: [3](#0-2) [9](#0-8) 

The broken equality is: `organization used to select/verify the HMAC secret (repository.owner.login) == organization that actually owns the repository being mutated (repository.full_name)`. These are two independently attacker-controlled fields in the same unsigned-until-verified JSON body, and the code never enforces that they match.

### Impact Explanation
In a multi-organization Shipit deployment (the documented, supported configuration where `secrets.github` is keyed by organization, each with its own optional `webhook_secret`), if even one configured organization omits its `webhook_secret`, an unauthenticated internet attacker can:
1. POST to the public `/webhooks` endpoint with `X-Github-Event: push` (or `status`, `check_suite`, `pull_request`, etc.).
2. Set `repository.owner.login` (or `organization.login`) to the secret-less organization's name, causing `verify_webhook_signature` to return `true` unconditionally — no valid GitHub signature is required.
3. Set `repository.full_name` to any repository tracked under a *different*, secret-protected organization.
4. The dispatched handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, pull-request handlers, etc.) resolves the `Stack`/`Repository` from `repository.full_name` and executes real side effects — e.g. `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)`, and status/check-suite handlers can forge CI state that Shipit trusts for deploy safety.

This is an authentication bypass that lets an unprivileged, unauthenticated attacker forge GitHub webhook events for a repository they never authenticated against, directly manipulating stack/commit state Shipit relies on to gate deploys.

### Likelihood Explanation
Requires a specific but explicitly documented deployment shape: multi-org `secrets.github` configuration where at least one configured organization has no `webhook_secret` (the docs call it optional and many teams may leave low-risk/internal orgs unset). Given that shape, exploitation requires zero credentials, zero repository access, and no GitHub App key — just an HTTP POST to the public webhook endpoint.

### Recommendation
Enforce that the field used to select the verifying `GitHubApp`/secret is the same field trusted for subsequent handler dispatch, and refuse to treat a webhook as authenticated for a secretless org unless it is scoped in a way that can't be attributed to other organizations. Concretely: derive `repository_owner` from `repository.full_name`'s owner segment (the same field handlers use) rather than a separately attacker-suppliable field, and never allow `verify_webhook_signature` to silently pass for the config of one org while acting on data belonging to another. Consider making `webhook_secret` mandatory in multi-org mode, or reject payloads whose `repository.owner.login` disagrees with the owner segment of `repository.full_name`.

### Proof of Concept
Given a multi-org config:
```yaml
production:
  github:
    unprotected-org:
      app_id: 1
      installation_id: 1
      private_key: ...
      # webhook_secret intentionally absent
    victim-org:
      app_id: 2
      installation_id: 2
      private_key: ...
      webhook_secret: real-secret
```

Attacker request (no signature needed):
```
POST /webhooks
X-Github-Event: push

{
  "ref": "refs/heads/master",
  "after": "<attacker chosen sha>",
  "repository": {
    "owner": { "login": "unprotected-org" },
    "full_name": "victim-org/protected-repo"
  }
}
```
`repository_owner` resolves to `unprotected-org` → `verify_webhook_signature` returns `true` (no secret configured) → `head(422)` is skipped → `PushHandler` resolves `Repository.from_github_repo_name("victim-org/protected-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker chosen sha>")`, acting on `victim-org`'s stack despite never proving possession of `victim-org`'s webhook secret.     def verify_webhook_signature(signature, message)
```ruby
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
```

```markdown
## Creating the GitHub App

Shipit needs a GitHub App to authenticate users, receive Webhooks and access the API.

You can create a new one for your organization at `https://github.com/organizations/<your-org>/settings/apps/new`, or [https://github.com/settings/apps/new](https://github.com/settings/apps/new) for a regular user.

  - Homepage URL: The URL where Shipit will be deployed, e.g. `https://example.com`.
  - User authorization callback URL: It must be set to `<homepage>/github/auth/github/callback`, e.g. `https://example.com/github/auth/github/callback`.
  - Setup URL: Leave it empty.
  - Webhook URL: It must be set to `<homepage>/webhooks`, e.g. `https://example.com/webhooks`.
  - Webhook secret (optional): Fill it with some randomly generated string, and *keep it in clear on the side, you'll need it later*.
  - Repository permissions:
    - Checks: Read & write
    - Commit statuses: Read-only
    - Contents: Read & write (to allow merging)
    - Deployments: Read & write
    - Issues: Read & write (to allow closing related issues on merge)
    - Metadata: Read-only
    - Pull requests: Read & write
```

```ruby
module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
```
