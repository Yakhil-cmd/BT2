### Title
Unsigned-unit placeholder-signature bypass allows acceptance of units with forged/invalid signatures - (File: definition.js)

### Summary
`objJoint.unsigned` directly controls `objValidationState.bUnsigned`, which is honored by the `sig` opcode evaluator in `Definition.validateAuthentifiers` to skip real ECDSA verification whenever the supplied authentifier begins with `"-"`. This flag is attacker-controlled input on the joint envelope (not something restricted to internal composer/estimation paths), so a peer can submit a joint with `unsigned:true` and dash-prefixed placeholder "signatures" for any address and have the authentifier check report success without any real signature verification, mirroring the TiDB bug class of an authentication check being bypassable via a crafted request flag.

### Finding Description
`validate()` in [1](#0-0)  sets `objValidationState.bUnsigned = true` directly from the attacker-supplied `objJoint.unsigned` field, with no restriction on who may set this field (it is one of the two allowed top-level fields for unsigned joints, per the field whitelist at [2](#0-1) ).

This `bUnsigned` flag then reaches `Definition.validateAuthentifiers`, where the `sig` opcode explicitly bypasses real signature verification: [3](#0-2) 
```
if (algo === 'secp256k1'){
    if (objValidationState.bUnsigned && signature[0] === "-") // placeholder signature
        return cb2(true);
    var res = ecdsaSig.verify(objValidationState.unit_hash_to_sign, signature, args.pubkey);
```

Because `bAuthors` still requires `isNonemptyObject(objAuthor.authentifiers)` and nonempty-string authentifiers (validation.js `validateAuthor`), an attacker only needs to supply a placeholder authentifier value like `"-"` for each required signing path to satisfy `validateAuthentifiers` with `res=true`, without possessing any private key for the address whose funds/AA/asset condition is being spent.

The unsigned path is intended purely for local UI "unsigned unit" flows (fee/complexity estimation before a hardware wallet/cosigner actually signs), and the caller-side handling in `network.js`'s `ifOkUnsigned` callback treats this as a special, non-persisting result (`callbacks.ifOkUnsigned()` at [4](#0-3) , and `validate()` for light clients returns `ifOkUnsigned(true)` for `objJoint.unsigned` at [5](#0-4) ). However, for full (non-light) nodes, `objJoint.unsigned` is still accepted as one of the two whitelisted fields ( [2](#0-1) ) and flows all the way through `validateAuthor` → `Definition.validateAuthentifiers` before any full-node-specific gate rejects it. I was not able to fully verify, within the available context, whether `writer.saveJoint` or any full-node-specific caller definitively rejects `objJoint.unsigned=true` before this authentifier check is reached and its `ifOkUnsigned` result is discarded, or whether some intermediate handler (e.g., `handleJoint` in `network.js`, `writer.saveJoint`) also short-circuits unsigned joints earlier. This is a limitation of static analysis via the code index; a Devin session with full file access and the ability to trace `saveJoint`/`handleJoint` end-to-end (and to run the validator against a crafted unsigned joint) would be needed to confirm whether the bypassed signature check can actually lead to a persisted, spendable unit, or whether it is fully contained to the local-estimation code path.

### Impact Explanation
If the `bUnsigned`/placeholder-signature path is reachable from a network-submitted joint on a full node (not just light-client estimation) and its `ifOkUnsigned` result can be converted into a saved/broadcast unit, this would let an attacker construct valid-looking units for addresses they don't control — i.e., authentication (signature) bypass — enabling unauthorized spending, AA fund draining, or asset transfer without a valid private key. That would map to High/Critical severity under this program's rubric.

### Likelihood Explanation
Unconfirmed. This depends entirely on whether `objJoint.unsigned=true` from an external/network unit is processed through the full validation pipeline that ends in real persistence, or whether it is exclusively used internally for wallet fee-estimation and immediately discarded (as the `ifOkUnsigned` callback naming and the light-client shortcut strongly suggest). Without tracing `writer.saveJoint` and `network.js`'s `handleJoint`/`handleOnlineJoint` end-to-end for the `unsigned` flag, I cannot confirm real-world exploitability.

### Recommendation
A Devin session with full repository access should:
1. Trace every caller of `validation.validate` to confirm whether `objJoint.unsigned=true` can originate from a network peer (vs. only from local composer/estimation calls) and reach `writer.saveJoint`.
2. Confirm whether `ifOkUnsigned` results are ever written to the DB / broadcast, or purely used for local fee estimation.
3. If a network-reachable path exists, reject `objJoint.unsigned` unconditionally for any unit not originating from the node's own composer (e.g., require a local-only flag rather than trusting the joint's own field), and never allow the `bUnsigned` placeholder-signature bypass in `definition.js`'s `sig` opcode for units received over the network.

### Proof of Concept
Not constructed — reachability of the `unsigned` code path from a network-submitted joint to unit persistence could not be confirmed within the available index/context, so a concrete PoC unit cannot be responsibly asserted without that confirmation. A background Devin session should trace `network.js: handleOnlineJoint`/`handleJoint` and `writer.saveJoint` for the `unsigned` flag to build or refute a PoC.
