## Title
Cross-repository commit-status forgery via unscoped `sha` lookup in `StatusHandler` — ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
The `Handler` base class exposes a `stacks`/`repository_name` scoping helper derived from the verified webhook payload's `repository.full_name`, but `StatusHandler#process` never uses it. It resolves the target commit purely by `sha`, globally across the whole `commits` table, and writes GitHub CI state onto whatever commit matches — regardless of which repository/organization the signed webhook actually came from.

### Finding Description
`WebhooksController#verify_signature` authenticates a webhook by selecting the GitHub App/secret for the organization named in the payload (`repository_owner`) and validating the HMAC over the raw body: [1](#0-0) 

This correctly proves the payload was signed by GitHub for *that* organization/repository. However, once the event is dispatched to handlers, `StatusHandler#process` ignores which repository the event belongs to and looks up commits solely by `sha`: [2](#0-1) 

Contrast this with the base `Handler` class, which defines exactly the scoping primitive that should have been used (`stacks` derived from `payload.dig('repository', 'full_name')`), but `StatusHandler` doesn't call it: [3](#0-2) 

`Commit.where(sha: params.sha)` runs against the entire `commits` table with no `stack_id`/repository filter, so if a commit with that SHA exists under a *different* stack (a different repository, potentially owned by a completely different GitHub organization), it will be updated: [4](#0-3) 

The equality that should hold is: **organization authenticated by the webhook signature == repository whose commit is written**. Before the flaw, only status webhooks originating from a stack's own repository organization should be able to move that stack's commit's CI state. After the flaw, any organization holding a valid signed `status` webhook for *any* stack configured in this Shipit instance can write a status onto a commit that lives in *any other* stack, as long as it can get GitHub to fire a `status` event citing that other commit's SHA (e.g., by calling `POST /repos/{attacker_owner}/{attacker_repo}/statuses/{sha}` with a SHA value copied from the public commit history of the victim repository — GitHub's Statuses API does not require the SHA to belong to the repo the status is posted against).

`create_status_from_github!` → `statuses.replicate_from_github!` then persists this attacker-controlled state/context on the victim commit: [5](#0-4) 

### Impact Explanation
The forged status directly feeds the deploy/merge safety gates:
- `Commit#deployable?` requires `success? && !blocked?`, driven by the injected status: [6](#0-5) 
- `MergeRequest#all_status_checks_passed?` / `#reject_unless_mergeable!` consult the same status data before auto-merging a pull request: [7](#0-6) 

By injecting a fabricated `success` status (or clearing a `blocking` status) for a commit belonging to a stack the attacker does not control, an attacker holding only status-write privileges on some unrelated, low-privileged GitHub organization/repo integrated with this Shipit instance can make an otherwise CI-failing or CI-pending commit in a *different* organization's stack appear deployable, triggering an unauthorized deploy via continuous deployment, or an unauthorized merge via the merge queue (`ProcessMergeRequestsJob` → `merge_request.merge!`). This satisfies the "unauthorized deploy...or merge" Critical-impact criterion.

### Likelihood Explanation
Requires only that the attacker control (or be a collaborator/status-reporter on) any single GitHub organization/repository whose commit-status webhooks are wired to this Shipit instance — no Shipit credentials, `ApiClient` token, or `webhook_secret` knowledge is needed, since the webhook is a real, GitHub-signed delivery. The attacker also needs the target commit's SHA, which is public information on the victim repository. This is a realistic multi-tenant Shipit deployment scenario (one instance serving many orgs/stacks), matching the report's core lesson: a signature/authentication check (per-organization) does not imply the underlying data mutation is scoped to that same trust boundary.

### Recommendation
In `StatusHandler#process` (and any other handler that resolves objects purely by cross-tenant-ambiguous keys like `sha`), scope the lookup to the stacks belonging to the repository named in the verified payload, mirroring the `Handler#stacks` helper already provided by the base class, e.g. restrict `Commit.where(sha: params.sha)` to `stacks.flat_map(&:commits)` / `Commit.where(sha: params.sha, stack_id: stacks.select(:id))` before calling `create_status_from_github!`.

### Proof of Concept
1. Attacker controls (or has status-write access to) `attacker-org/throwaway-repo`, which is one of the many organizations with the Shipit GitHub App installed and status webhooks enabled for this Shipit instance.
2. Attacker finds the public commit SHA `S` of a commit in `victim-org/victim-repo` that currently has a failing/pending CI status blocking deploys, e.g. from the victim repo's public commit page.
3. Attacker calls GitHub's Statuses API: `POST /repos/attacker-org/throwaway-repo/statuses/S` with `{"state":"success","context":"ci/whatever"}`.
4. GitHub fires a legitimately signed `status` webhook to Shipit for `attacker-org`; `verify_signature` passes because it only checks `attacker-org`'s secret.
5. `StatusHandler#process` runs `Commit.where(sha: S)`, finds the commit in `victim-org/victim-repo`'s stack (already synced into Shipit), and writes the forged `success` status onto it via `create_status_from_github!`.
6. The victim commit now reports as deployable/mergeable, and continuous delivery or the merge queue acts on it — an unauthorized deploy or merge occurs.
