### Title
Webhook signature verification keys on `repository.owner.login`/`organization.login`, but event routing keys on `repository.full_name` — an org whose secret authenticated the request can forge events against another org's repositories - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary

### Finding Description
`Shipit::WebhooksController#verify_signature` selects the `GitHubApp` (and therefore the webhook secret used to validate `X-Hub-Signature`) using only `repository_owner`, which is read straight out of the untrusted, self-signed request body: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

Once the signature check passes, the actual event handlers resolve the target `Repository`/`Stack` from an entirely different field of the same JSON body — `repository.full_name` — via `Handler#repository_name`: [3](#0-2) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`Repository.from_github_repo_name` performs a plain `owner/name` split with no cross-check against the org that was used to verify the signature: [4](#0-3) 

Shipit explicitly supports hosting multiple independent GitHub organizations from a single instance, each with its own `webhook_secret`, resolved via `Shipit.github(organization:)`/`github_app_config`: [5](#0-4) [6](#0-5) 

Because the field used to pick *which secret validates the request* (`repository.owner.login`) is disjoint from the field used to pick *which repository/stack the request acts on* (`repository.full_name`), an attacker who legitimately knows/controls the webhook secret for **one** configured organization (Org A) can submit a payload where `repository.owner.login = "OrgA"` (so it authenticates against Org A's secret) while `repository.full_name = "OrgB/victim-repo"` (a repository belonging to a different organization hosted on the same Shipit instance). The signature check passes, and the handler acts on Org B's stack.

The binding broken:
`organization whose signature authenticated the request` ≠ `repository whose Stack is written to by the handler`.

### Impact Explanation
Handlers that trust `repository.full_name` after this shared `verify_signature` pass can be abused across the organization boundary Shipit's multi-org configuration is meant to enforce:

- `PushHandler` enqueues `stack.sync_github(expected_head_sha:)` for any matching stack of the forged repo, driving `GithubSyncJob`, which fetches commits via `stack.github_api` (an org-scoped GitHub App client resolved from the *victim* repo's owner) and appends them, causing `stack.schedule_merges` to run for commits the attacker chose. [7](#0-6) [8](#0-7) 

- `StatusHandler` writes forged CI statuses onto arbitrary existing `Commit` rows by `sha` (no repository ownership check at all beyond the shared sha lookup), which can flip `Commit#add_status` transitions and trigger `stack.schedule_merges` — i.e., faking a "success" status to unblock an automatic merge/deploy pipeline for a stack belonging to an organization the attacker does not control. [9](#0-8) [10](#0-9) 

This is a cross-repository/cross-organization write and can result in unauthorized deploys/merges for a stack outside the attacker's authenticated organization boundary, satisfying the "cross-repository writes / unauthorized deploy, rollback or merge" impact bar.

### Likelihood Explanation
Exploitation requires the attacker to be able to produce a validly-signed webhook body for **any one** organization configured in the multi-org `github` secrets block (`docs/setup.md` "Using Multiple GitHub Applications"), which is a supported, documented deployment topology explicitly intended to let independent orgs be hosted side-by-side with isolated GitHub Apps/secrets. The `/webhooks` endpoint itself requires no session, `ApiClient` token, or Shipit-level privilege — only knowledge of one org's `webhook_secret` (which, in this documented multi-tenant model, is scoped to and legitimately available to that org's own GitHub App administrator, who has no expected trust relationship with other orgs hosted on the same Shipit instance). Note also that `webhook_secret` is documented as optional; if any configured org omits it, `verify_webhook_signature` returns `true` unconditionally for payloads claiming that org, making forgery trivial with zero credentials for anyone who can reach the endpoint.

### Recommendation
After verifying the signature, cross-check that the organization used to select the signing app (`repository.owner.login` / `organization.login`) matches the owner embedded in `repository.full_name` (and any other repository/org identifiers the specific handler consumes) before dispatching to handlers. Reject the webhook if these disagree.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own GitHub App and `webhook_secret` (per `docs/setup.md`).
2. Attacker knows `OrgA`'s `webhook_secret` (e.g., is `OrgA`'s GitHub App admin) but has no relationship to `OrgB`.
3. Attacker crafts a `push` payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(OrgA_webhook_secret, body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: "OrgA")` and validates successfully against `OrgA`'s secret.
6. `PushHandler#stacks` resolves `Repository.from_github_repo_name("OrgB/victim-repo")` and enqueues `GithubSyncJob`/`sync_github` for `OrgB`'s stack, despite the request never being authenticated by `OrgB`'s secret.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
```
