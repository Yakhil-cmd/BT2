### Title
Withdraw permanently bricked (LP funds frozen) if either pool-vault token becomes non-transferable, since burn+both transfers are atomic with no partial-withdrawal fallback - (`programs/cp-swap/src/instructions/withdraw.rs`)

### Summary
`withdraw()` burns the user's LP tokens and then transfers both `token_0` and `token_1` out of the pool vaults in a single atomic instruction. If either vault's token becomes non-transferable at the SPL Token/Token-2022 CPI level (e.g., the mint's `freeze_authority` freezes the pool's vault token account — a standard, non-extension field present on ordinary SPL Token mints, not filtered by `is_supported_mint`), the whole instruction reverts every time it is attempted, permanently denying withdrawal of the *other*, perfectly healthy token as well. This mirrors the reported class of bug: a single bad/frozen asset in a batched, all-or-nothing operation blocks legitimate closing/liquidation-style access to the rest of the assets.

### Finding Description
`withdraw()` computes `token_0_amount`/`token_1_amount`, burns the LP tokens, then unconditionally performs two sequential CPI transfers: [1](#0-0) 

Both `transfer_from_pool_vault_to_user` calls must succeed or the entire instruction (including the LP burn) reverts, because Solana instructions are atomic. There is no code path that allows a user to withdraw only the healthy token while skipping the frozen one, and no admin/emergency function exists that bypasses `safe_transfer`-style CPI failures the way the original report recommends.

The mint-vetting logic `is_supported_mint` only rejects Token-2022 *extensions* it doesn't recognize (e.g. `TransferHook`, `PermanentDelegate`, `DefaultAccountState`); it does **not** inspect or restrict the base-layer `freeze_authority` field that exists on both legacy SPL Token and Token-2022 mints, and it unconditionally approves any mint owned by the legacy `Token::id()` program: [2](#0-1) 

Consequently a pool can be freely created (permissionlessly, via `initialize`) with a widely-used token that has a freeze authority (e.g., many stablecoins support account-level freezing/blacklisting). If that authority ever freezes the pool's vault token account for one side of the pair — a realistic, externally-triggerable event exactly analogous to the "hack/bad token" scenario in the source report — `withdraw()` will fail forever for that pool, because the CPI transfer for the frozen vault will always error out and there is no fallback that lets LPs redeem the still-healthy other token.

`deposit()` has the same atomic two-transfer structure and is symmetrically affected for adding liquidity, though the more severe impact is on `withdraw()`, since it blocks LPs from ever recovering already-deposited funds.

### Impact Explanation
This permanently freezes LP funds in the pool: LPs can never burn their LP tokens to reclaim their share of the un-frozen token, since the same transaction that would return it also requires the frozen-token transfer to succeed. There is no owner/admin path in the reachable, unprivileged surface (`deposit`, `withdraw`, `swap_base_input/output`, `collect_creator_fee*`) that lets funds be rescued once one vault becomes non-transferable. This is a permanent freezing of LP funds, matching the Medium-severity impact bar (permanent freezing of user/LP funds).

### Likelihood Explanation
Pool creation via `initialize`/`initialize_with_permission` is permissionless and only filters a narrow allow-list of Token-2022 extensions; it does not check for or reject mints with a set `freeze_authority`, which is common even among plain legacy SPL tokens. Any pool paired with such a token is exposed the moment the token issuer exercises a normal, expected token-administration action (freezing a specific account) — no attacker-controlled transaction or malicious validator is required, only ordinary token issuer behavior that the pool design does not defend against.

### Recommendation
- At `initialize`/`initialize_with_permission` time, reject (or clearly flag) mints whose `freeze_authority` is set (for both legacy and Token-2022 mints), similar to how Token-2022 extensions are already vetted in `is_supported_mint`.
- Alternatively/additionally, provide a decoupled or per-token withdrawal path (e.g., allow burning LP tokens against a single side, or an emergency sweep that tolerates one leg's CPI failure) so a frozen vault on one token does not lock out withdrawal of the other, healthy token.

### Proof of Concept
1. A pool creator calls `initialize` pairing `token_0` = a normal SPL-Token mint with a live `freeze_authority` (e.g., a stablecoin) and `token_1` = any other token; `is_supported_mint` approves both because `token_0` is owned by `Token::id()` and is unconditionally accepted at line 340-342 of `programs/cp-swap/src/utils/token.rs`.
2. LPs deposit into the pool via `deposit`, receiving LP tokens.
3. `token_0`'s freeze authority freezes the pool's `token_0_vault` token account (a normal, permitted SPL-Token operation available to any mint with a freeze authority; independent of the AMM program).
4. Any LP calls `withdraw`; the CPI to transfer `token_0` out of `token_0_vault` in `programs/cp-swap/src/instructions/withdraw.rs:188-201` fails, causing the whole instruction (including the `token_1` transfer at lines 203-216 and the LP burn at lines 179-186) to revert.
5. `withdraw` can never succeed again for this pool while `token_0_vault` stays frozen, permanently trapping both `token_0` and `token_1` liquidity for every LP.

pub fn is_supported_mint(
    mint_account: &InterfaceAccount<Mint>,
    mint_associated_is_initialized: bool,
) -> Result<bool> {
    let mint_info = mint_account.to_account_info();
    if *mint_info.owner == Token::id() {
        return Ok(true);
    }
    if mint_associated_is_initialized {
        return Ok(true);
    }
    let mint_data = mint_info.try_borrow_data()?;
    let mint = StateWithExtensions::<spl_token_2022::state::Mint>::unpack(&mint_data)?;
    let extensions = mint.get_extension_types()?;
    for e in extensions {
        if e != ExtensionType::TransferFeeConfig
            && e != ExtensionType::MetadataPointer
            && e != ExtensionType::TokenMetadata
            && e != ExtensionType::InterestBearingConfig
            && e != ExtensionType::ScaledUiAmount
        {
            return Ok(false);
        }
    }
    Ok(true)
}
