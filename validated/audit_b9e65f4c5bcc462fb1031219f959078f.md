### Title
Webhook signature verification keys on `repository.owner.login` while handlers act on the (independently forgeable) `repository.full_name` field, allowing cross-organization/cross-repository writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to validate the HMAC against using `repository_owner`, a value parsed out of the *untrusted, attacker-supplied* JSON body itself, before the signature has been checked. Once the signature passes, the same raw payload is handed to event handlers that instead key off a *different* field, `repository.full_name` (via `Handler#repository_name`), to decide which `Stack`/`Repository` records to mutate. Because Shipit supports multiple GitHub organizations each with its own `webhook_secret`, an attacker who legitimately controls one onboarded organization's webhook secret can craft a payload where `repository.owner.login` (used for signature-key selection) names their own org, while `repository.full_name` (used for actually processing the event) names a repository belonging to a different organization hosted on the same Shipit instance.

### Finding Description
`verify_signature` computes the organization used to look up the verification secret directly from request data: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` resolves a distinct `GitHubApp` (and thus a distinct `webhook_secret`) per organization when the multi-org config schema is used: [3](#0-2) 

The HMAC check itself only proves the raw body was signed with *some* configured org's secret — it does not bind the signature to any specific field inside that body: [4](#0-3) 

After signature verification succeeds, every webhook `Handler` resolves the target `Stack`s using a completely different payload field, `repository.full_name`: [5](#0-4) 

This creates exactly the class of binding violation described in the reference bug (a value used for one purpose being detached from the value used for the actual effectful operation): **the organization whose secret authenticated the request ≠ the repository whose records are written**. A participant who controls the webhook secret for `OrgA` (a legitimately onboarded organization on this shared Shipit instance) can sign a payload where `repository.owner.login = "OrgA"` (so `verify_signature` picks `OrgA`'s secret and passes) but `repository.full_name = "OrgB/target-repo"` (a different organization's repository also hosted on the instance). Downstream handlers such as `PushHandler`, `StatusHandler`, and `CheckSuiteHandler` all resolve `stacks` purely from `repository.full_name` and then mutate `OrgB`'s data: [6](#0-5) [7](#0-6) [8](#0-7) 

The `push` event's effect is particularly severe: it directly enqueues `GithubSyncJob`, which mutates commit history, marks the target stack's repository accessible/inaccessible, and can trigger downstream deploy-spec caching for a `Stack`/`Repository` the attacker does not own: [9](#0-8) 

### Impact Explanation
This crosses the "organization authenticated versus repository written" trust boundary explicitly called out as in-scope: a request cryptographically authenticated for `OrgA` results in state changes to a `Stack` that belongs to `OrgB`. Concretely this permits an unprivileged holder of one organization's webhook secret to inject forged commit statuses (`StatusHandler` → `Commit#create_status_from_github!`), trigger CI-check refresh cycles (`CheckSuiteHandler`), or force `GithubSyncJob` to run against another organization's repository — a cross-repository write achieved purely by exploiting the mismatch between the field used for authentication routing and the field used for authorization/target-selection, without ever holding a Shipit session, API token, or the target organization's own webhook secret.

### Likelihood Explanation
Exploitation requires the attacker to already legitimately control at least one organization's GitHub App/webhook secret configured on the same shared Shipit deployment (the documented multi-org config schema in `docs/setup.md`/`secrets_double_github_app.yml`). This is a real, supported deployment topology (not a mis-deployment), so the precondition is reasonable in any multi-tenant Shipit instance, though it does not apply to single-org deployments where all repositories necessarily share one secret and `repository_owner`/`repository.full_name` are trivially consistent.

### Recommendation
Do not select the verification secret from an untrusted, unauthenticated field parsed out of the same body being verified. Either: (1) bind webhook secret selection to a value that cannot be attacker-controlled independent of `repository.full_name` (e.g. resolve the organization strictly from `repository.full_name`'s owner segment, ensuring the two fields are the same derivation), or (2) after successful signature verification, re-validate that the organization whose secret matched is exactly the owner segment of `repository.full_name`, rejecting the webhook if they diverge.

### Proof of Concept
1. Deploy Shipit with the multi-org config (`config/secrets.yml` using per-organization `github` keys, as in `test/dummy/config/secrets_double_github_app.yml`), onboarding both `OrgA` (attacker-controlled webhook secret) and `OrgB` (victim organization/repository also hosted on this instance).
2. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>` using `OrgA`'s known secret.
4. `POST /webhooks` with `X-Github-Event: push`. `verify_signature` resolves `repository_owner` = `"OrgA"`, fetches `OrgA`'s `GitHubApp`, and the HMAC matches → request is accepted.
5. `PushHandler#process` resolves `stacks` via `Handler#repository_name` = `payload.dig('repository','full_name')` = `"OrgB/victim-repo"`, and enqueues `GithubSyncJob` against `OrgB`'s stack — a write the attacker was never authorized to trigger.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
