### Title
Webhook signature is verified against the organization named in `repository.owner.login`, while handlers resolve the target repository from the independent `repository.full_name` field, allowing cross-organization commit-status/stack forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to validate an inbound webhook against using `repository.owner.login` (with a fallback to `organization.login`). The actual event handlers, however, resolve which `Repository`/`Stack` to act on using a completely different JSON field: `repository.full_name` (`Handler#repository_name`). Because the HMAC signature only proves "this body was signed by *some* organization's registered secret," and not "the org that signed it matches the repository the handler will mutate," a party who legitimately owns any one GitHub organization configured in a multi-org Shipit deployment can forge a webhook whose `repository.owner.login` points at their own org (so the signature check passes with their own known `webhook_secret`) while `repository.full_name` points at a totally different, victim organization's repository tracked by the same Shipit instance.

### Finding Description
- `WebhooksController#verify_signature` picks the app/secret to verify against solely from `repository_owner`: [1](#0-0) [2](#0-1) 

- Shipit explicitly supports multiple independent GitHub Apps/organizations, each with its own `webhook_secret`, looked up by the `organization` argument: [3](#0-2) 

- Once the signature is accepted, `Shipit::Webhooks.for_event(event)` dispatches the *same raw payload* to handlers such as `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, all of which inherit repository resolution from the base `Handler` class: [4](#0-3) 

- That resolution uses `repository.full_name`, a field completely independent from `repository.owner.login` used for signature/org selection. `PushHandler` is a concrete, verified example that acts on whatever stacks match `repository_name`: [5](#0-4) 

- The test suite confirms `StatusHandler` (registered for the `status` event) creates a `Status` record on a commit resolved this same way, i.e., it performs a real write keyed off attacker-supplied `full_name`/`sha` fields inside the signed body: [6](#0-5) 

- Handler registration for `status`, `push`, `check_suite`, and `membership` all flow through this same signature/resolution split: [7](#0-6) 

**The broken binding, stated as an equality that the code fails to enforce:**
`organization authenticated by verify_signature (repository.owner.login / organization.login)` ⇎ `repository/stack written by the handler (repository.full_name)`

Nothing in `WebhooksController` or `Handler` asserts that these two payload fields refer to the same repository/organization. An attacker only needs valid signing credentials for **any** organization configured in the Shipit instance (i.e., legitimate access to their own GitHub App's webhook secret, which is a normal, unprivileged capability for an org admin in a multi-tenant Shipit deployment) — not credentials for the victim organization/repository being targeted.

### Impact Explanation
This breaks the trust boundary between organizations in a multi-org Shipit deployment (explicitly supported per `docs/setup.md`'s "Using Multiple Github Applications" section). An attacker who administers Org A (with its own registered GitHub App/webhook secret) can forge webhook events that write to Stacks/Repositories belonging to Org B, which they have no legitimate access to:
- Via `StatusHandler`, they can create arbitrary commit `Status` records on a victim repository's commits (`test/controllers/webhooks_controller_test.rb:42-59` shows this write path), which is a cross-organization/cross-repository write of state Shipit uses to gate deploy behavior.
- Via `PushHandler`/`CheckSuiteHandler`, they can trigger sync/check-run refresh jobs against a victim's stack with attacker-chosen SHAs.

This constitutes a cross-repository write performed by an attacker without any credential belonging to the targeted organization — matching the Critical-tier impact category of "cross-repository writes."

I was not able to fully trace, within the remaining investigation budget, whether the forged `Status` writes alone are sufficient to satisfy a victim stack's `ci.require` deployability gate and unlock an actual unauthorized deploy (that logic lives in `Commit`/`Stack` deploy-spec code I could not fully inspect in this session). That escalation path is plausible given `ci.require` is documented to gate deploys on commit statuses, but should be verified directly against `app/models/shipit/commit.rb` and the `DeploySpec` before treating it as confirmed Critical rather than the already-confirmed cross-repository write.

### Likelihood Explanation
Medium-to-High. Exploitability requires only that the attacker legitimately controls (or compromises) one GitHub organization/App registered in a multi-org Shipit instance — a materially lower bar than requiring a Shipit session, an `ApiClient` token, or the victim organization's own `webhook_secret`. Multi-org configuration is a documented, supported Shipit deployment mode, not an edge case.

### Recommendation
In `WebhooksController#verify_signature`, and in `Handler#repository_name`/`#stacks`, ensure the organization used to select/verify the webhook signature is the same organization that owns the repository the handler will act upon. Concretely: after resolving `repository.full_name` in the handler, re-derive its owner and assert it matches the same organization key (`repository_owner`) whose secret validated the signature — or better, verify the signature using the organization derived from the resolved `Repository`/`Stack` record itself rather than an unvalidated field copied from attacker-controlled JSON.

### Proof of Concept
1. Attacker administers `attacker-org`, a GitHub organization/App registered in the same multi-org Shipit instance, and knows `attacker-org`'s `webhook_secret`.
2. Attacker crafts a `status` (or `push`) webhook JSON body where:
   - `repository.owner.login` = `"attacker-org"` (used only for signature org selection)
   - `repository.full_name` = `"victim-org/victim-repo"` (an existing Shipit-tracked repository the attacker doesn't control)
   - other required fields (`sha`, `state`, `context`, etc., per `test/controllers/webhooks_controller_test.rb:42-59`) targeting a real commit of the victim stack.
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(attacker-org's webhook_secret, raw_body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")` and successfully verifies the signature using the attacker's own known secret (`app/controllers/shipit/webhooks_controller.rb:24-30`).
5. `Webhooks.for_event("status")` dispatches to `StatusHandler`, which resolves the target commit/stack via `repository.full_name` = `"victim-org/victim-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) and creates a forged `Status` record on the victim's commit, as demonstrated by the equivalent legitimate-path test in `test/controllers/webhooks_controller_test.rb:42-59`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end
