### Title
`CheckReplacable` allows cross-type replacement of `AccountKeyFail` slots, enabling `RoleFeePayer` lock bypass — (`blockchain/types/accountkey/account_key.go`)

### Summary
`CheckReplacable` only enforces `AccountKeyFail`'s non-updatability when the new key has the same type. When the new key is a different type (e.g., `AccountKeyPublic`), it skips `AccountKeyFail.CheckUpdatable` entirely and calls `newKey.CheckInstallable`, which returns `nil` for any valid public key. This allows the `RoleAccountUpdate` key holder to replace a `RoleFeePayer = AccountKeyFail` slot with an attacker-controlled key and persist it to state.

### Finding Description
`CheckReplacable` (line 124–129 of `account_key.go`) is the sole gate for slot-level key replacement in `AccountKeyRoleBased.CheckUpdatable`. Its logic is:

```
if oldKey.Type() == newKey.Type():
    return oldKey.CheckUpdatable(newKey, blockNum)   // AccountKeyFail blocks here
else:
    return newKey.CheckInstallable(blockNum)          // AccountKeyFail is never consulted
```

`AccountKeyFail` is designed to be permanently non-updatable — its `CheckUpdatable` always returns `ErrAccountKeyFailNotUpdatable`. But the cross-type branch completely bypasses this, delegating only to the new key's installability check. A valid `AccountKeyPublic` always passes `CheckInstallable`. The result is that any holder of `RoleAccountUpdate` can submit a `TxTypeAccountUpdate` replacing the `RoleFeePayer = AccountKeyFail` slot with an arbitrary public key, which is then written to state via `stateDB.UpdateKey`.

### Impact Explanation
The `RoleFeePayer = AccountKeyFail` pattern is the protocol mechanism for permanently disabling fee-delegated transaction signing on an account. Once bypassed, the attacker-controlled `RoleFeePayer` key can sign fee-delegated transactions (`TxTypeFeeDelegated*`), causing KAIA gas fees to be charged to the victim account without authorization. This constitutes unauthorized fee charge affecting KAIA assets — a direct match to the allowed impact gate.

### Likelihood Explanation
The attacker must control the `RoleAccountUpdate` key of the target account. This is a legitimate, non-compromised key role. In multi-party setups where `RoleTransaction`, `RoleAccountUpdate`, and `RoleFeePayer` are held by different parties, the `RoleAccountUpdate` holder can unilaterally unlock the fee-payer role against the intent of the account design. The transaction is a standard `TxTypeAccountUpdate` submittable via public RPC.

### Recommendation
`CheckReplacable` must explicitly reject replacement of an `AccountKeyFail` old key regardless of the new key's type:

```go
func CheckReplacable(oldKey AccountKey, newKey AccountKey, currentBlockNumber uint64) error {
    if oldKey.Type() == AccountKeyTypeFail {
        return kerrors.ErrAccountKeyFailNotUpdatable
    }
    if oldKey.Type() == newKey.Type() {
        return oldKey.CheckUpdatable(newKey, currentBlockNumber)
    }
    return newKey.CheckInstallable(currentBlockNumber)
}
```
