### Title
Cross-repository commit status forgery via unscoped SHA lookup - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves target commits purely by `Commit.where(sha: params.sha)` with no repository, stack, or branch scoping, unlike `PushHandler#process` which scopes stacks by `.where(branch:)`. Since git commit SHAs are content-addressed and preserved across forks, an attacker who forks a victim repository (or otherwise obtains a commit with an identical SHA) can trigger a legitimately-signed `status` webhook from their own repository that mutates the victim's tracked commit status in another stack.

### Finding Description
The broken binding: the question implies `branches` filtering (as used by `WebhooksController`/`PushHandler`) constrains which commits a webhook can affect; in reality, for `StatusHandler`, `params.branches` is accepted but **never read** — `commit.create_status_from_github!(params)` runs for every row returned by `Commit.where(sha: params.sha)` regardless of whether `branches` is present, empty, or omitted. [1](#0-0) 

The controller (`WebhooksController#create`) performs signature verification against the payload's own `repository_owner`/organization, then simply dispatches: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` — there is no repository-to-stack binding check at the controller layer for `status` events. [2](#0-1) 

`Handler` base class exposes a `stacks` helper scoped by `repository_name` from the payload, but `StatusHandler#process` does not use `stacks` at all — it queries the global `Commit` table by `sha` only. [3](#0-2) 

Contrast with `PushHandler#process`, which does scope by `stacks.not_archived.where(branch:)` before acting — confirming that branch/repository-tracking checks exist elsewhere in the same module but are absent in `StatusHandler`. [4](#0-3) 

Because `Commit#sha` is not scoped uniquely per repository at the database query level in this handler, and Git preserves commit SHAs across forks, an attacker can:
1. Fork the victim repository (any public repo tracked by Shipit), obtaining commits with identical SHAs to the upstream/victim.
2. Post a commit status on their own fork for that SHA (a normal, unprivileged GitHub action on their own repository).
3. GitHub emits a `status` webhook for the attacker's repository, correctly signed with the attacker's own installation/webhook secret — `verify_signature` passes because it validates the signature for the attacker's own `repository_owner`, not that the SHA belongs to that repository.
4. `StatusHandler.call(payload)` → `Commit.where(sha: params.sha)` matches the victim's `Commit` row (belonging to a different `Stack`/repository) and calls `commit.create_status_from_github!(params)`, writing an attacker-controlled `state`/`description`/`target_url` status onto the victim's commit.

Existing guards do not close this: `verify_signature` only proves the webhook truly came from the attacker's own (or a valid) organization/app installation, not that the referenced SHA belongs to that repository. [5](#0-4)  The `ExplicitParameters` schema only validates parameter shapes/types (`requires :sha, String`, `accepts :branches, Array`) and does not enforce that `branches` be non-empty or that `sha` belong to the reporting repository. [6](#0-5) 

### Impact Explanation
A status webhook from an attacker-controlled repository can write a forged CI/status result (`state`, `description`, `target_url`) onto a commit belonging to a victim stack in a completely different repository via `Commit#create_status_from_github!` → `Status::Group`/`add_status`. Since `add_status` can trigger `Hook.emit(:deployable_status, ...)` and `stack.schedule_merges` when the new status is `success`/`pending`, a forged "success" status can make an otherwise-blocked victim commit appear `deployable?` (`!locked? && (stack.ignore_ci? || (success? && !blocked?))`) [7](#0-6) , potentially triggering continuous deployment/merge scheduling for a repository the attacker never controls. This is a payload from one repository mutating another repository's commit/stack state — matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team").

### Likelihood Explanation
Preconditions: the victim repository must be public or forkable by the attacker (typical open-source setup on Shipit), and the attacker needs a Shipit-tracked webhook installation on their own fork (standard GitHub App/webhook install flow, not privileged). Attacker cost is low: fork the repo, push/set a commit status on a commit whose SHA matches an existing victim commit (trivial since forks share history), and let GitHub deliver the `status` webhook. This is repeatable against any repository whose commits the attacker can replicate via fork, and does not require any Shipit secret, session, or API token.

### Recommendation
Scope commit lookup by repository/stack, not by global SHA. In `StatusHandler#process`, restrict the query to commits belonging to the stacks associated with `payload.dig('repository', 'full_name')` (mirroring the `stacks` helper already defined on `Handler`), e.g. iterate over `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalent, instead of unscoped `Commit.where(sha: params.sha)`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual)
test "status from unrelated repository mutates victim commit status" do
  victim_stack = shipit_stacks(:shipit)
  victim_commit = victim_stack.commits.create!(sha: 'a' * 40, message: 'victim commit')

  attacker_repository_payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'repository' => { 'full_name' => 'attacker/unrelated-repo' }, # attacker's own repo, not victim_stack's
  }

  assert_equal 0, victim_commit.statuses.count

  Shipit::Webhooks::Handlers::StatusHandler.new(attacker_repository_payload).process

  victim_commit.reload
  assert_equal 1, victim_commit.statuses.count
  assert_equal 'success', victim_commit.statuses.last.state
  # Binding broken: repository_name in payload ("attacker/unrelated-repo") != victim_stack's repository,
  # yet victim_commit received the forged status because StatusHandler#process
  # never scopes Commit.where(sha:) by repository/stack.
end
```
