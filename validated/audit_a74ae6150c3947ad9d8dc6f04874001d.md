### Title
`StatusHandler` mutates CI status for commits in **any** repository/stack sharing a SHA, bypassing the per-repository scoping every other handler enforces - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits solely by `Commit.where(sha: params.sha)` with no repository/stack scoping, unlike all other handlers which resolve their target stacks via `Handler#stacks` (`Repository.from_github_repo_name(repository_name)&.stacks`). Because a status webhook is verified only against the sending repository's `webhook_secret`, but the handler then updates the CI status of every `Commit` row across the entire database that shares that SHA, a status event legitimately signed for repository A can mutate commit state belonging to repository B/stack B.

### Finding Description
The binding that should hold, mirroring every other handler, is:

`repository_name (from verified payload.dig('repository','full_name')) == repository owning the stacks/commits mutated by the handler`

This holds for handlers like `OpenedHandler`, `ClosedHandler`, `LabeledHandler`, etc., which all restrict their targets through `stacks` (`Handler#stacks`, [1](#0-0) ), which resolves to `Repository.from_github_repo_name(repository_name)&.stacks`.

`StatusHandler#process` never calls `stacks` or filters by repository at all: [2](#0-1) 

It queries `Commit.where(sha: params.sha)` across the whole table and calls `commit.create_status_from_github!(params)` for every match, regardless of which stack/repository that commit belongs to. `Commit#create_status_from_github!` then writes the status scoped to *that commit's own* `stack_id`: [3](#0-2) 

The commits table has an index on `(stack_id, sha)` (not a global unique index on `sha`), so multiple `Commit` records belonging to different `Stack`/`Repository` records can legitimately share the same SHA (e.g., mirrored/forked repositories, monorepo commits reused across split repos, or coincidental history overlap after a repository rename/re-creation with same shipit `Repository` disabled and another attached). The webhook's HMAC signature check (`verify_signature`/`GitHubApp#verify_webhook_signature` in `app/controllers/shipit/webhooks_controller.rb`) only proves the *event was sent by repository A's configured secret* — it says nothing about which `Commit` rows should be touched, and `StatusHandler` never re-derives or checks that constraint the way `Handler#stacks` would.

So the attacker's flow: attacker controls (or is the owner of) repository A's status webhook (self-inflicted status webhook is fully within an unprivileged GitHub repo owner's control), and a `Commit` with the identical SHA also exists on stack B (a different `Repository`). Sending a status webhook for repository A with that SHA causes `StatusHandler` to write a `Status` for the commit on stack B as well, changing stack B's CI/deployability decision (`Commit#deployable?`, `blocked?`, continuous delivery scheduling) — none of which was authorized by repository B's owner or secret.

### Impact Explanation
An attacker who owns/controls a status webhook for one repository (trivially available to any GitHub user with push access to their own repo/fork) can inject or forge CI status for a commit belonging to a completely unrelated stack/repository, as long as a SHA collision exists between the two. This can flip a commit from failing to "success", unblocking automatic/continuous deployment (`schedule_continuous_delivery`) or unblocking manual deploys gated on CI status, for a repository the attacker does not control. This matches "payload for one repository mutating another's stack, commit... state" — Critical severity — because it is a direct authentication/authorization-scoping bypass: the signature legitimately proves origin repository A, but the write lands on repository B's records.

### Likelihood Explanation
Exploitability is contingent on a SHA collision existing between a commit tracked on the attacker's stack and a commit tracked on the victim's stack. This is not guaranteed for arbitrary target repositories (a real SHA-256/SHA-1 collision across unrelated content is infeasible), but it is realistic and attacker-achievable in common real-world topologies: forks, mirrors, repositories transferred/renamed while old `Repository`/`Stack` rows for the same commits remain, or any organization mirroring the same git history into two different Shipit-tracked repositories. In such setups the attacker fully controls the trigger (send one signed webhook from their own repo) with no other privilege needed. The vulnerability is structural — no additional secret or role is required — but its practical reach is limited to the intersection of "repositories with colliding commit SHAs," which is a real but non-universal precondition.

### Recommendation
Scope `StatusHandler#process` the same way every other handler is scoped: only update commits that belong to a stack under `Repository.from_github_repo_name(repository_name)`. E.g., iterate `stacks.flat_map(&:commits).where(sha: params.sha)` (or `Commit.where(sha: params.sha, stack_id: stacks.pluck(:id))`) instead of an unscoped `Commit.where(sha: params.sha)`.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`-style, no live GitHub):
1. Create `repository_a = Repository.create!(...)`, `stack_a = Stack.create!(repository: repository_a, ...)`, `commit_a = stack_a.commits.create!(sha: 'deadbeef', ...)`.
2. Create `repository_b = Repository.create!(...)`, `stack_b = Stack.create!(repository: repository_b, ...)`, `commit_b = stack_b.commits.create!(sha: 'deadbeef', ...)` (same SHA, different repository/stack).
3. Build a signed status payload naming `repository_a.github_repo_name`/`full_name` with `sha: 'deadbeef'`, `state: 'success'`, signed with `repository_a`'s (or the app-wide) `webhook_secret`.
4. POST to `/webhooks` (through `Shipit::WebhooksController`) or call `StatusHandler.call(payload)` directly.
5. Assert both `commit_a.statuses.count` and `commit_b.statuses.count` increased — i.e., `commit_b.reload.statuses.count == before_b + 1` even though the request was only authenticated for `repository_a`. Contrast with an equivalent test on `OpenedHandler`/`LabeledHandler` where an analogous cross-repository payload leaves `stack_b` untouched because those handlers use `stacks` scoped to `repository_name`.
