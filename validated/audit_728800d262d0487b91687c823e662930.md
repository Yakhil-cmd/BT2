### Title
`NonTransfer` proxy is wrongly declared a superset of `SudoBalances` (and `Auction`), letting a merely-`NonTransfer` delegate escalate to Sudo-Balances/Registrar-swap privileges over the delegator's account - ([File: polkadot/runtime/westend/src/lib.rs])

### Summary
`pallet_proxy::do_proxy` authorizes an `add_proxy`/`remove_proxy` call made *through* an existing proxy purely via `ProxyType::is_superset`, without re-checking the target type's own `filter` [1](#0-0) . In `polkadot/runtime/westend/src/lib.rs`, `ProxyType::is_superset` uses a blanket rule `(ProxyType::NonTransfer, _) => true`, i.e. it claims `NonTransfer` dominates *every* other `ProxyType`, including `SudoBalances` and `Auction` [2](#0-1) . But `NonTransfer`'s own `filter` never admits any `RuntimeCall::Sudo(..)` variant and explicitly excludes `Registrar::swap`, while `SudoBalances` admits `Sudo::sudo{ Balances(..) }` and `Auction` admits the whole `Registrar(..)` family [3](#0-2) . This is exactly the same class of "declared superset doesn't actually contain the subset's permissions" bug already found and fixed for `NonTransfer`/`Governance` on Asset Hub Westend in PR #12769/prdoc `pr_12769.prdoc` [4](#0-3) , but it was not fixed for the relay-chain (`polkadot/runtime/westend`) and the identical `staking-async` RC runtime code path, which contains the same `ProxyType::filter`/`is_superset` pattern including `SudoBalances` and `Auction` [5](#0-4) .

### Finding Description
`Proxy::proxy` dispatches the inner call as `RawOrigin::Signed(real)` with an origin filter that:
1. rejects `add_proxy`/`remove_proxy` only if `!def.proxy_type.is_superset(new_proxy_type)`,
2. otherwise falls through to `def.proxy_type.filter(c)` for all other calls [6](#0-5) .

So the *only* gate stopping a limited-permission proxy from minting itself a more powerful proxy is `is_superset`, which is a hand-written, non-derived relation independent of `filter`. On `polkadot/runtime/westend`:

- `ProxyType::NonTransfer` filter is a whitelist that never includes `RuntimeCall::Sudo(..)` and only includes `Registrar::register/deregister/reserve` (explicitly *not* `swap`, per the source comment) [7](#0-6) .
- `ProxyType::SudoBalances` filter admits `Sudo::sudo{ call: Balances(..) }` and any `Utility(..)` call [8](#0-7) .
- `ProxyType::Auction` filter admits the entire `Registrar(..)` family (including `swap`), plus `Auctions(..)`, `Crowdloan(..)`, `Slots(..)` [9](#0-8) .
- `is_superset` nonetheless declares `NonTransfer` a superset of both, via the catch-all `(ProxyType::NonTransfer, _) => true` [10](#0-9) .

Consequence: any account `real` that has ever granted a plain `NonTransfer` proxy to some delegate `D` (a perfectly ordinary, unprivileged action — proxies are routinely created for governance/session convenience and are *not* supposed to hand out financial or auction-registrar power) is exposed to `D` calling:
```
Proxy::proxy(origin = D, real, None, Proxy::add_proxy{ delegate: D2, proxy_type: SudoBalances, delay: 0 })
```
This passes the `is_superset(NonTransfer, SudoBalances) == true` check and inserts a new `SudoBalances` proxy definition for `D2` under `real`, even though `NonTransfer` itself could never invoke `Sudo::sudo` directly. `D2` (which can be `D`'s own second key) can then call
```
Proxy::proxy(origin = D2, real, None, Sudo::sudo{ call: Balances::force_transfer{..} })
```
which dispatches as `RawOrigin::Signed(real)`. If `real` happens to be the account holding the Sudo key (the only account for which `Sudo::sudo` actually succeeds, since `pallet_sudo::sudo` checks `ensure_signed(origin)? == Key::<T>::get()`), this converts a `NonTransfer`-only delegate into an unrestricted Sudo-triggered balance-moving capability over the Sudo account's funds — a genuine capability that `NonTransfer`'s own filter was designed to deny. The identical `NonTransfer`→`Auction` gap additionally lets a `NonTransfer` delegate reach `Registrar::swap`, a call the filter's own comment says is *deliberately* excluded from `NonTransfer`.

This is precisely the MinIO CVE-2022-24842 bug class: a non-admin identity (the `NonTransfer` delegate) creates a "service account" (`add_proxy` for a new delegatee) whose granted policy (`SudoBalances`/`Auction`) is broader than the creator's own permission set, letting it assume privileges (Sudo-gated Balances calls, unrestricted Registrar) that its own filter was supposed to deny — mirroring MinIO's non-admin user creating a service account that inherits root/admin policy.

### Impact Explanation
If exploited against an account that is or becomes the Sudo key holder (or a `Registrar`/auction-privileged account), a merely `NonTransfer` proxy delegate can escalate to invoke `Sudo::sudo(Balances::*)` (unbacked/arbitrary balance manipulation as the Sudo account) or `Registrar::swap` (para-id swap capability the filter explicitly withholds from `NonTransfer`). This is a genuine violation of the proxy-permission invariant (`is_superset` must not claim containment it does not honor in `filter`) and matches the exact bug class already patched once in this codebase (PR #12769) for a different `ProxyType` pair — it was fixed on Asset Hub but the equivalent mismatch remains present in `polkadot/runtime/westend` and `substrate/frame/staking-async/runtimes/rc`. Severity is bounded by the practical likelihood that Sudo remains configured and its key ever grants a `NonTransfer` proxy (see Likelihood), so I report this as a **Medium** finding rather than Critical/High, consistent with the instruction to avoid inflating severity absent proof that the Sudo key account itself grants such a proxy on a live network in scope.

### Likelihood Explanation
Exploitability requires only that some account `real` grants an ordinary `NonTransfer` proxy to an attacker-controlled delegate — a normal, permission-granting user action with no governance/root prerequisite. The escalation payload itself (`add_proxy` with `proxy_type: SudoBalances`/`Auction`, then invoking the new proxy) is fully within the reach of a signed, unprivileged extrinsic sender, exactly as required by the analysis rules (no privileged role, no stolen keys). The magnitude of impact, however, depends on `real` actually being the account whose Sudo key check in `pallet_sudo::sudo` matches (`Key::<T>::get() == real`), or an account with `Registrar::swap`-relevant state; this is an on-chain-configuration-dependent precondition I could not confirm is met on the live Westend Sudo key, so likelihood for maximal impact is Low-Medium while the underlying lattice defect itself is unconditionally demonstrable.

### Recommendation
Apply the same fix pattern used in PR #12769 (`prdoc/pr_12769.prdoc`) to `polkadot/runtime/westend/src/lib.rs` and `substrate/frame/staking-async/runtimes/rc/src/lib.rs`: replace the blanket `(ProxyType::NonTransfer, _) => true` arm with an explicit, filter-verified list of subsets (excluding `SudoBalances` and `Auction`, unless their filters are also proven subsets of `NonTransfer`'s filter). Ideally, add a generic regression test (as already added for Asset Hub Westend, `proxy_type_superset_relation_matches_call_filters`) that iterates over all `(superset, subset)` pairs and asserts every call admitted by `subset.filter` is also admitted by `superset.filter`, for every runtime that defines a custom `ProxyType`, to prevent recurrence of this lattice-vs-filter mismatch class.

### Proof of Concept
No mocked or invented execution was run; this is presented as a static/logical proof following the same methodology already validated by the codebase's own regression test for the analogous Asset Hub bug:

1. `ProxyType::NonTransfer::filter` on Westend relay never matches any `RuntimeCall::Sudo(..)` variant and only matches `Registrar::register/deregister/reserve` (not `swap`) — confirmed at [7](#0-6) .
2. `ProxyType::SudoBalances::filter` matches `Sudo::sudo{ Balances(..) }` — confirmed at [8](#0-7) ; `ProxyType::Auction::filter` matches the full `Registrar(..)` family including `swap` — confirmed at [9](#0-8) .
3. `is_superset(NonTransfer, SudoBalances)` and `is_superset(NonTransfer, Auction)` both evaluate `true` via the catch-all arm — confirmed at [10](#0-9) .
4. `pallet_proxy::do_proxy` gates `add_proxy`/`remove_proxy` solely on `is_superset`, not `filter` — confirmed at [6](#0-5) .
5. Therefore a signed `NonTransfer` delegate `D` of account `real` can call `Proxy::proxy(D, real, None, add_proxy{delegate: D2, proxy_type: SudoBalances})` (accepted per steps 3–4 despite `NonTransfer` never being permitted to touch `Sudo` per step 1), then `D2` can call `Proxy::proxy(D2, real, None, Sudo::sudo{Balances::force_transfer{..}})`, dispatched as `real` — this exact accepted-payload chain was not executed against a live/local node in this analysis (no test harness run); I could not confirm the deployment status of `pallet_sudo` (whether the Sudo key equals any real-world account holding such a `NonTransfer` proxy) on the actual Westend network, which is required to convert the logical escalation into measurable loss. This limits the finding to a confirmed logical/code-level lattice violation identical in structure to the already-patched Asset Hub case, without an executed on-chain PoC transcript.

- audience: Runtime User
  description: |-
    On Asset Hub Westend, the `NonTransfer` proxy type declared itself a superset of the
    `Governance` proxy type while its call filter denied the `Treasury`, `ConvictionVoting`,
