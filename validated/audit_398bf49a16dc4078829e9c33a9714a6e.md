### Title
`transfer` on zToken vaults accepts `tx-sender`-based authorization, letting a malicious intermediate contract move a victim's vault shares - (File: `mainnet/contracts/vault/v0-vault-stx.clar`, and equivalents `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`)

### Summary
The original report describes `TradeCallee` authorizing a fund transfer by checking `tx.origin == trader` instead of validating that the immediate/intended caller actually signed the specific order, letting an attacker's contract siphon the victim's assets whenever the victim merely calls the attacker's contract. The Zest zToken vault contracts contain the direct Clarity analog: their `transfer` function authorizes moves of a user's zft (vault share) balance if `tx-sender` (Clarity's exact equivalent of `tx.origin` — the original transaction signer, unaffected by intermediate `contract-call?`s) equals the named `from` principal, with no requirement that the *immediate* caller be the owner or be otherwise authorized for that specific transfer.

### Finding Description
Every zToken vault's `transfer` function is guarded only by: [1](#0-0) 

```
(define-public (transfer (amount uint) (from principal) (to principal) (memo (optional (buff 34))))
  (begin
    (try! (accrue))
    (asserts! (or (is-eq tx-sender from) (is-eq contract-caller from)) (err u4))
    (asserts! (not (is-eq current-contract to)) ERR-TOKENIZED-VAULT-PRECONDITIONS)
    (try! (ft-transfer? zft amount from to))
    (match memo to-print (print to-print) 0x)
    (ok true)))
```

The same pattern (`or (is-eq tx-sender from) (is-eq contract-caller from)`) is present in `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdc.clar`, and `v0-vault-usdh.clar`, each confirmed by grep to contain the identical two-clause check.

In Clarity semantics, `tx-sender` is the principal that signed the *entire* transaction (i.e., the exact analog of Solidity's `tx.origin`) and does **not** change as the call passes through further `contract-call?`s (it only changes inside an explicit `as-contract` wrapper). `contract-caller` is the *immediate* invoking principal (analog to `msg.sender`). Because the check accepts a match on either value, any contract `M` invoked by a victim within the same transaction can call:

```
(contract-call? .v0-vault-stx transfer amount tx-sender ATTACKER none)
```

Since `tx-sender` still equals the victim (the check does not require `contract-caller == from`), the assertion passes, and `M` — despite being neither the token owner nor an approved spender — moves the victim's zft (vault share) balance to `ATTACKER`. This is functionally identical to the reported bug: the victim's transaction origin is used as blanket proof of authorization for an action the victim never actually approved, and any untrusted contract reachable in the victim's call chain (e.g., a "swap router," "yield aggregator," or any dApp the victim is lured into calling) can exploit it.

### Impact Explanation
The zft shares represent a user's principal deposit/collateral in the vaults (STX, sBTC, stSTX, stSTXbtc, USDC, USDH) — real, at-rest user funds, and these shares are also used directly as collateral in the market contracts. An attacker's contract that a victim is induced to call can transfer the victim's entire zft balance to the attacker in one transaction, with no prior approval and no signature from the victim specific to that transfer. This is direct theft of user funds at rest, landing on the **Critical** impact tier.

### Likelihood Explanation
Exploitation requires only a straightforward social-engineering step already covered by the report's own exploit scenario: get a victim to call an attacker-deployed contract (a common pattern in DeFi — fake aggregators, "airdrop claim" contracts, etc.). Once that happens, the theft is a single, deterministic `contract-call?` inside the attacker's contract with no additional preconditions (no oracle, no price manipulation, no privileged role needed). The `contract-caller` half of the `or` clause was very likely intended to allow trusted intra-protocol composability (e.g., `market.clar` calling `transfer` on behalf of the user when it is the direct caller), but the `tx-sender` half independently and unnecessarily reintroduces the tx.origin-style authorization flaw regardless of whether `contract-caller` is honest.

### Recommendation
Remove the `tx-sender`-based branch of the authorization check and require `is-eq contract-caller from` only, so the transfer is only authorized when the *immediate* caller is the owner of the funds (matching the standard SIP-010 safe pattern used correctly elsewhere), or add an explicit post-condition / allowance mechanism if cross-contract composability without an explicit caller-is-owner match is truly required.

### Proof of Concept
1. Victim calls attacker-deployed contract `evil-router`, believing it performs a benign action (e.g., a swap or claim).
2. Inside `evil-router`, the attacker's code executes: `(contract-call? .v0-vault-stx transfer (ft-get-balance zft tx-sender) tx-sender 'ATTACKER none)`.
3. Because this call chain never uses `as-contract`, `tx-sender` remains the victim throughout, satisfying `(is-eq tx-sender from)` in `v0-vault-stx.clar` line 755 even though `contract-caller` is `evil-router`, not the victim.
4. `ft-transfer? zft amount from to` executes, and the victim's zSTX (or zsBTC/zstSTX/zUSDC/zUSDH/zstSTXbtc) balance is transferred entirely to the attacker's address, with the victim never having called `transfer` directly or approved the specific action.
