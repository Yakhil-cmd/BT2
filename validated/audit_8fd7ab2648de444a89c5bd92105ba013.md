### Title
Unhandled type-coercion exception in oscript formula evaluator can crash all full nodes processing an AA trigger - ([File: formula/evaluation.js])

### Summary
The formula evaluator's internal type-conversion helpers `toOscriptType()` and `toJsType()` throw a raw, uncaught `Error` whenever they encounter a value that is not one of the expected oscript primitive representations (string, boolean, `Decimal`, `wrappedObject`). These functions are on the deterministic AA-trigger execution path that every full node runs identically when processing a posted trigger/AA response, analogous to the reported `downcast_uint256()` issue where an out-of-range value read from chain state causes every node to fail identically instead of gracefully rejecting the unit.

### Finding Description
`toOscriptType(x)` and `toJsType(x)` are pure switch-like converters used throughout `formula/evaluation.js` to move values between the "oscript" representation (used inside formula evaluation, e.g. `Decimal`, `wrappedObject`) and native JS types (used for storage of state vars, response vars, and getter/`map`/`filter`/`reduce` results): [1](#0-0) 

Both functions end with an unconditional `throw Error(...)` for any value that doesn't match the expected set of types. These are called in numerous places along the deterministic AA execution path that is invoked for every posted trigger unit and every AA response, e.g.:
- `stateVars2assoc()` / `assoc2stateVars()`, used when saving/loading AA state variables: [2](#0-1) 
- Result finalization of `addUpdatedStateVarsIntoPrimaryResponse()` in `aa_composer.js`, which calls `toJsType(state.value)` on every updated state variable before it is written into the AA response and persisted: [3](#0-2) 
- The `map`/`filter`/`reduce` formula operators, which call `toJsType(r)` on the return value of a local or remote getter function: [4](#0-3) 
- `executeGetterInState()`, used for local/remote getter calls: [5](#0-4) 

Because AA execution (`handleAATriggers` / `handleTrigger` in `aa_composer.js`) is triggered by any address posting a payment/trigger to an AA, and because oscript formulas (defined by the AA author but evaluated against attacker/trigger-controlled `trigger.data`, state, and remote-getter results) determine intermediate values passed through these converters, a code path that produces a value outside the type set these functions expect (e.g. `undefined` from an unset local variable, uninitialized state var, or a result value that slips past the normal `setFatalError` guards) results in a synchronous, unguarded JS exception. Unlike the rest of the evaluator, which funnels invalid states through `setFatalError()` to produce a controlled "bad formula" rejection, `toOscriptType`/`toJsType` do not go through this error-handling convention and instead `throw`.

This mirrors the reported bug class exactly: a value derived from state that can be manipulated into an out-of-range/unexpected representation causes an unhandled failure instead of a graceful rejection, and because the same deterministic code executes on every full node handling the trigger, the fault is reproduced identically everywhere.

### Impact Explanation
An uncaught exception thrown synchronously inside the deterministic AA-trigger-processing pipeline (which runs inside `mutex.lock`/`db.query` callback chains without a surrounding try/catch at this depth) propagates up and crashes the Node.js process on every full node that processes the same trigger unit — this includes witnesses and any node that has caught up to that MCI. Since AA response computation is mandatory for a unit to become stable and for the DAG to advance, a reproducible crash here would halt confirmation of subsequent units network-wide until node operators patch/filter the offending case, matching the "freezing the chain" impact class of the external report (network unable to confirm new units due to node disagreement/crash on validity, requiring an out-of-band fix).

### Likelihood Explanation
Likelihood is Low-to-Medium: reaching a value type that these functions do not recognize likely requires a specific combination of oscript constructs (e.g., unassigned locals, uninitialized/deleted state vars, or a getter/remote-call return path that bypasses `setFatalError`) rather than a single simple crafted unit. I was not able to fully trace, within the available tool budget, a concrete guaranteed-reachable formula/trigger payload that forces `toJsType`/`toOscriptType` to receive `undefined` (or another unhandled type) rather than being intercepted earlier by validation (`aa_validation.js`) or by `setFatalError`. This is a gap in my analysis — a background engineering session with the ability to run the formula test suite and fuzz oscript AST inputs would be needed to construct a concrete reproduction unit.

### Recommendation
- Convert the terminal `throw Error(...)` in `toOscriptType()` and `toJsType()` (formula/evaluation.js:3244, 3254) into a caller-visible error signal consistent with the rest of the evaluator's `setFatalError()` convention, so unexpected types cause the triggering unit/AA response to be treated as invalid rather than crashing the process.
- Audit all call sites of `toOscriptType`/`toJsType` (state var (de)serialization, `map`/`filter`/`reduce`, getter execution) to ensure a `null`/error return is checked and mapped to a `setFatalError` / formula-validation failure instead of allowing an exception to escape.
- Add defensive fallback handling (analogous to returning `Option`/`Result` instead of unwrapping) so that any value from state, triggers, or remote getters that does not conform to the expected type set fails the specific AA response with a normal error rather than raising a process-level exception.

### Proof of Concept
Not constructed — a definitive PoC requires crafting an oscript AA definition/trigger sequence that forces a value into `toOscriptType`/`toJsType` outside `{string, boolean, Decimal, wrappedObject, object}` (e.g., via an uninitialized local variable, a deleted/never-set state var referenced through `map`/`filter`, or a getter returning `undefined`) while bypassing prior `setFatalError` guards. This would need to be verified empirically against `test/formula.test.js`/`test/aa.test.js` in a full development environment, which is outside the scope of this read-only analysis.

function toOscriptType(x) {
	if (typeof x === 'string' || typeof x === 'boolean' || x instanceof wrappedObject)
		return x;
	if (typeof x === 'number')
		return createDecimal(x);
	if (Decimal.isDecimal(x))
		return toDoubleRange(x);
	if (typeof x === 'object' && x !== null)
		return new wrappedObject(x);
	throw Error("unknown type in toOscriptType:" + x);
}

function toJsType(x) {
	if (x instanceof wrappedObject)
		return x.obj;
	if (Decimal.isDecimal(x))
		return x.toNumber();
	if (typeof x === 'string' || typeof x === 'boolean' || typeof x === 'number' || (typeof x === 'object' && x !== null))
		return x;
	throw Error("unknown type in toJsType:" + x);
}
