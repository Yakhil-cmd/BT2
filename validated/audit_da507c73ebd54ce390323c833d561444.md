### Title
Cross-organization webhook forgery via attacker-controlled organization selector combined with blank-`webhook_secret` bypass - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects *which* GitHub App configuration (and therefore which `webhook_secret`) is used to validate an inbound webhook's HMAC signature based on a field read directly out of the unauthenticated JSON body (`repository.owner.login` or `organization.login`), while the payload's `repository.full_name` — a separate, unrelated field in that same unverified body — is what actually determines which `Stack`/`Repository` gets acted upon by the handler that runs afterward. This breaks the equality "organization whose secret authenticated the request" == "repository that is written to by the request", exactly analogous to the reported class of bug where a value that drives privileged behavior is not the same value covered by the security check.

### Finding Description
`WebhooksController#verify_signature` picks the `GitHubApp` (and thus the `webhook_secret` used for HMAC verification) using `repository_owner`, which is parsed straight from the untrusted JSON payload before any cryptographic check has passed: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` unconditionally returns `true` when the selected organization's `webhook_secret` is blank/unset: [3](#0-2) 

Meanwhile, the field that actually determines the target of the action — which repository/stack is mutated — is a *different* field of the same JSON body, read later, after "verification": [4](#0-3) 

In a documented and supported multi-organization Shipit deployment (config keyed by org name, each with its own `webhook_secret`), it is normal/expected for some orgs to have no `webhook_secret` configured, as shown in the shipped example configs: [5](#0-4) [6](#0-5) 

An unauthenticated caller (this is a public HTTP endpoint reachable by anyone who can guess/know the URL — it is not gated by any Shipit session, API token, or GitHub App key) can send a crafted request directly:
- `repository.owner.login` (or `organization.login`) = the name of any configured org that has a blank `webhook_secret` — this makes `Shipit.github(organization: repository_owner).verify_webhook_signature` return `true` regardless of the (even absent/garbage) `X-Hub-Signature` header.
- `repository.full_name` = `owner/repo` of an entirely different, security-conscious organization's tracked repository (whose real `webhook_secret` the attacker does not know).

Because these two fields are never cross-checked against each other, the `verify_signature` before_action passes (organization A's blank secret), while `PushHandler`/`StatusHandler` act on organization B's `Repository`/`Stack` (looked up via `repository.full_name`): [7](#0-6) [8](#0-7) [9](#0-8) 

The multi-org resolution mechanism (`Shipit.github`) confirms organization is looked up purely by name/string from the config, with no binding back to the repository field used by the handler: [10](#0-9) 

### Impact Explanation
This lets an unauthenticated network attacker forge webhooks on behalf of a fully-secured GitHub organization/repository as long as *any other* configured organization on the same Shipit instance has a blank `webhook_secret`. Concretely this enables:
- Forged `status` events via `StatusHandler#process`, which calls `commit.create_status_from_github!(params)` on commits of the targeted org's stack — allowing an attacker to inject fabricated CI/commit statuses for a repository they do not control, which can influence merge-queue/deploy gating decisions.
- Forged `push` events via `PushHandler#process`, which triggers `stack.sync_github(expected_head_sha:)` for stacks belonging to the targeted repository, causing Shipit to re-sync/act against attacker-chosen state.

This matches the "cross-repository writes" / "unauthorized deploy" impact class: an attacker authenticates as (bypasses auth for) organization A but writes state belonging to organization B's tracked repository, purely because the field verified and the field acted upon are decoupled.

### Likelihood Explanation
Requires a specific but realistic and *documented* deployment shape: a single Shipit instance configured with more than one GitHub organization (explicitly supported and documented at `docs/setup.md`'s "Using Multiple Github Applications" section) where at least one organization's `webhook_secret` is left blank (also shown as a normal example configuration, not a misconfiguration flagged anywhere in the code). Given the webhook endpoint requires no authentication of any kind (`skip_before_action :verify_authenticity_token`, no session/API token check), any attacker who can reach the instance over HTTP can attempt this with zero credentials, needing only to know one blank-secret org's name (discoverable from public GitHub org listings for that Shipit host) and the target's `owner/repo` full name.

### Recommendation
- Never select the verification secret from unauthenticated request content. If multiple organizations are configured, verify the incoming signature against *every* configured organization's secret (or key the endpoint by an unforgeable URL/path component per organization) rather than trusting `repository.owner.login`/`organization.login` from the JSON body.
- Do not treat a blank `webhook_secret` as an automatic verification pass in `GitHubApp#verify_webhook_signature`; require an explicit "signature verification disabled" opt-in, and refuse cross-organization actions from a request that verified against a different org's key than the one implied by the acted-upon repository.
- After verification, assert that the organization used to resolve `webhook_secret` matches the organization actually implied by `repository.full_name`/`repository.owner.login` used by the handler, rejecting mismatches.

### Proof of Concept
Preconditions: Shipit instance configured with orgs `blank-secret-org` (no `webhook_secret`) and `victim-org` (has a real, secret-protected repo/stack tracked by Shipit, e.g. `victim-org/app`).

```
POST /github/webhooks HTTP/1.1
X-Github-Event: status
Content-Type: application/json

{
  "sha": "<victim commit sha tracked by Shipit>",
  "state": "success",
  "context": "ci/forged",
  "repository": {
    "full_name": "victim-org/app",
    "owner": { "login": "blank-secret-org" }
  }
}
```
- `verify_signature` calls `Shipit.github(organization: "blank-secret-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of any (or missing) `X-Hub-Signature` header.
- `StatusHandler` then resolves `Commit.where(sha: params.sha)` and calls `create_status_from_github!`, writing a forged "success" status onto `victim-org/app`'s commit despite the attacker never possessing `victim-org`'s webhook secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
