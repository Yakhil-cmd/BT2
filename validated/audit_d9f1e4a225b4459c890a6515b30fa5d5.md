### Title
Webhook signature verification uses an attacker-controlled organization field that is decoupled from the repository actually acted upon, allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / webhook secret to validate an inbound webhook against using a value taken directly from the **unverified** JSON payload (`repository.owner.login`, falling back to `organization.login`). In a multi-organization Shipit deployment (the officially documented "Using Multiple Github Applications" configuration), this creates an equality that is never enforced: `organization that authenticated the signature` != `repository that the handler subsequently writes to`.

### Finding Description
`verify_signature` computes the signing organization from the raw, attacker-suppliable request body before any cryptographic check happens: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization:)` resolves a distinct `GitHubApp` instance (and thus a distinct `webhook_secret`) per organization key when Shipit is configured with multiple GitHub Apps, as documented in `docs/setup.md` "Using Multiple Github Applications" and exercised in `test/dummy/config/secrets_double_github_app.yml`: [3](#0-2) 

Once the signature is accepted, the actual event handler resolves the target stack(s) using a *different* field of the same JSON body — `repository.full_name` — with no cross-check against `repository.owner.login`: [4](#0-3) 

Because `repository.owner.login` (used to select the signing secret) and `repository.full_name` (used to select the target repository/stack) are independent JSON fields inside the same unsigned-at-parse-time payload, an attacker who legitimately controls one onboarded GitHub organization (and therefore knows/can generate valid signatures using that organization's `webhook_secret`) can craft a payload where:
- `repository.owner.login` = their own organization (so the signature check passes using their known secret), and
- `repository.full_name` = a victim organization's repository that also has a Stack configured in the same Shipit instance.

The signature verification succeeds (it's a valid HMAC for the attacker's own org), yet the handler processes the event against the victim's repository/stack.

### Impact Explanation
Depending on the event type, this can be abused for cross-repository forged events without the victim organization's webhook secret:
- `status` events: `StatusHandler` will create fabricated commit statuses on a victim's commits [5](#0-4) , which can be used to satisfy required-status checks that gate deployability/merge in the victim's stack — an unauthorized bypass of deploy/merge safety gates.
- `push` events: `PushHandler` triggers `GithubSyncJob` for the victim stack [6](#0-5) , causing Shipit to sync/append commit records outside of the victim's real GitHub activity.

This breaks the trust boundary of "the organization whose secret authenticated this request" vs. "the repository being written to," matching the requested analog class (owner/authorization check applied to the wrong entity than the one mutated).

### Likelihood Explanation
Exploitability requires that the Shipit instance is configured for multiple GitHub organizations (a documented, supported configuration) and that the attacker controls or has onboarded at least one of those organizations' webhook secrets — a realistic scenario for shared/multi-tenant Shipit deployments serving several orgs. No privileged Shipit session, API token, or GitHub App private key is required; only knowledge of one legitimate organization's own `webhook_secret`, which that organization's own maintainers legitimately possess.

### Recommendation
After verifying the signature, cross-check that the resolved signing organization actually matches `repository.owner.login`/`organization.login` used by the handler for repository resolution (or resolve the signing organization strictly from `repository.full_name`'s owner component and reject if it disagrees with `repository.owner.login`). Alternatively, look up the `Stack`/`Repository` first, derive its bound organization from stored configuration, and use that (not payload-controlled data) to select the webhook secret for verification.

### Proof of Concept
1. Configure Shipit with two GitHub Apps: `attacker-org` (attacker controls this org and knows its `webhook_secret`) and `victim-org` (has a Stack tracked in the same Shipit instance).
2. Attacker crafts a JSON body such as:
```json
{
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  },
  "sha": "<victim commit sha>",
  "state": "success"
}
```
3. Attacker computes `X-Hub-Signature` using `attacker-org`'s known `webhook_secret` over the raw body.
4. POST to `/webhooks` with header `X-Github-Event: status`.
5. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and successfully verifies the signature against the attacker's own secret [7](#0-6) .
6. `StatusHandler#process` resolves the target via `repository.full_name` = `victim-org/victim-repo` and writes a forged "success" status onto the victim's commit [5](#0-4) , despite the attacker never having the victim's `webhook_secret`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end
