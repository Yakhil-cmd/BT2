## Title
Multisig payload binding to the approved transaction can be bypassed when `abort_if_multisig_payload_mismatch` is disabled, letting an owner execute an arbitrary payload under a different multisig transaction's approvals - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
`create_transaction` stores the *full* target payload on-chain (`payload_hash = none`), and owners vote to approve/reject that exact transaction based on this stored payload. At execution time, the VM calls `validate_multisig_transaction(owner, multisig_account, payload)` with a `payload` value that is independently reconstructed from whatever `TransactionExecutableRef` the executor's raw transaction actually carries [1](#0-0) . The check that this executor-supplied `payload` actually equals the on-chain `transaction.payload` that owners voted on is gated behind the feature flag `abort_if_multisig_payload_mismatch_enabled()` [2](#0-1) .

### Finding Description
`validate_multisig_transaction` performs quorum/timelock checks correctly, but the binding between "what was approved" and "what will execute" is only enforced conditionally:

```
// aptos-move/framework/aptos-framework/sources/multisig_account.move:1361-1385
if (transaction.payload_hash.is_some()) {
    let payload_hash = transaction.payload_hash.borrow();
    assert!(sha3_256(payload) == *payload_hash, error::invalid_argument(EPAYLOAD_DOES_NOT_MATCH_HASH));
};

if (features::abort_if_multisig_payload_mismatch_enabled()
    && transaction.payload.is_some()
    && !payload.is_empty()
) {
    let stored_payload = transaction.payload.borrow();
    assert!(payload == *stored_payload, error::invalid_argument(EPAYLOAD_DOES_NOT_MATCH));
}
``` [3](#0-2) 

For transactions created via `create_transaction` (the common path, which stores the full payload rather than just a hash), `transaction.payload_hash` is `option::none()` [4](#0-3) , so the hash-based check never runs. The only remaining check that binds execution to the approved content is the second `assert!`, and it is entirely skipped unless the `abort_if_multisig_payload_mismatch_enabled` feature is turned on. Since this appears to be a feature-gated addition to existing logic, on any deployment/version/testnet configuration where the flag is off, an owner (who is otherwise authorized to call `validate_multisig_transaction`/execute the multisig entry point, and satisfies quorum via other owners' votes) can supply a "provided_payload" derived from a different `TransactionExecutableRef` than what was actually approved, and it will pass the (skipped) equality check as long as the raw transaction the VM constructs still resolves to a non-empty `payload` and the `payload_hash` branch is not taken.

This breaks the core admission invariant for multisig: "the account set approved payload X" must be the one that executes with `multisig_account`'s authority. If the flag is off, the executing owner effectively decouples the voted-on content from the executed content, executing content of their choosing under the multisig account's signer.

### Impact Explanation
If exploitable (i.e., in any configuration where `abort_if_multisig_payload_mismatch` is not enabled), an owner with sufficient collusion or by simply reaching quorum through legitimately collected votes for *transaction A* could execute an entirely different payload (transaction B) once quorum on A is met, since the execution-time equality check is compiled out. This is a wrong-approval-set / broken-binding admission bug: the multisig account's signer authority is exercised for content that was never actually voted on by the required threshold of owners, which can lead to unauthorized fund transfers, capability grants, or governance actions signed as the multisig account.

### Likelihood Explanation
This depends entirely on the on-chain/runtime state of the `abort_if_multisig_payload_mismatch_enabled` feature flag, which I could not confirm is default-on or default-off, nor whether it has already been permanently activated (and its gating code path removed) on the current mainnet/testnet release corresponding to this repo snapshot. The presence of the feature-flag branch (rather than an unconditional binding assert) at minimum indicates this behavior was previously (or still could be, on chains that have not activated the flag) exploitable, and demonstrates a real, non-hypothetical admission gap in the framework source. I was unable to verify the flag's current activation status or historical default within the available indexed files.

### Recommendation
Make the payload/hash binding check for `create_transaction`-created multisig transactions unconditional, independent of the `abort_if_multisig_payload_mismatch_enabled` feature flag, so that any owner-supplied `payload` at execution time is always required to equal the on-chain-approved `transaction.payload` when it is present (regardless of feature-flag state), analogous to how the `payload_hash` branch is already unconditionally enforced.

### Proof of Concept
Conceptual PoC (could not be executed/verified against actual on-chain feature-flag state):
1. On a network where `abort_if_multisig_payload_mismatch_enabled` is disabled, owner A calls `create_transaction(owner, multisig_account, payload_A)` where `payload_A` transfers funds to A's own address.
2. Owners B and C, seeing `payload_A` via `get_transaction`, vote to approve it, reaching quorum (e.g., 3-of-3 or whichever threshold), believing they are approving `payload_A`.
3. Owner A submits the actual execution transaction with `TransactionExecutableRef::EntryFunction(payload_B)` — a different, more damaging payload (e.g., transferring the multisig's entire balance to A).
4. In `run_multisig_prologue`, `provided_payload` is derived from `payload_B` [1](#0-0) .
5. `validate_multisig_transaction` is invoked with this `payload_B` bytes. Since `transaction.payload_hash` is `none` (created via `create_transaction`) and the mismatch-check feature is disabled, no assertion compares `payload_B` to the approved `payload_A`.
6. `execute_multisig_transaction` in the VM subsequently fetches/executes based on the same unchecked `provided_payload` [5](#0-4) , running `payload_B` with the multisig account's signer authority despite only `payload_A` having received quorum approval.
