### Title
Missing ReDoS protection in `RuleEngine._regex_match`/`compile_regex` allows attacker-controlled rule patterns to hang `pretooluse.py` via catastrophic backtracking - ([File: plugins/hookify/core/rule_engine.py])

### Finding Description
`compile_regex()` compiles any `pattern` string from a rule's YAML frontmatter with no complexity/shape validation, and `_regex_match()` calls `regex.search(text)` directly against attacker-influenceable `tool_input` fields (e.g. Bash `command`, Edit `new_string`) with no per-match time bound. [1](#0-0) [2](#0-1) 

Rules are loaded from any `.claude/hookify.*.local.md` file, with `pattern`/`conditions[].pattern` taken verbatim from YAML frontmatter and stored on the `Rule`/`Condition` objects with no sanitization. [3](#0-2) [4](#0-3) 

`pretooluse.py` (and `posttooluse.py`) load these rules and evaluate every `regex_match` condition against the corresponding tool_input field before approving/denying every Bash/Edit/Write/MultiEdit tool call. [5](#0-4) [6](#0-5) 

Notably, a sibling plugin (`security-guidance/hooks/extensibility.py`) already implements a heuristic ReDoS-shape detector (`_has_redos_structure`, `_REDOS_SHAPES`, `_ALT_UNDER_REP`) for exactly this class of pattern (nested quantifiers, wildcard groups under repetition, overlapping alternation), demonstrating this is a recognized risk in this codebase that was not applied to `hookify`'s `rule_engine.py`. [7](#0-6) 

An attacker who can place a `.claude/hookify.<name>.local.md` file with a `pattern` like `(a+)+$` (or `(.*)*`, or overlapping alternation under repetition) targeting `event: bash`/`field: command` (or `field: new_string` for file events), and who can also influence the matched text (e.g. via a crafted long string ending in a non-matching character, delivered through a Bash command argument or a file edit's `new_string`), can force catastrophic backtracking during `regex.search()`.

### Impact Explanation
This is scoped DoS of the approval pipeline, not arbitrary code execution or data exfiltration. The `hooks.json` manifest sets an explicit per-invocation `"timeout": 10` for `PreToolUse`/`PostToolUse`, which bounds each single hang to roughly 10 seconds rather than making it truly indefinite. [8](#0-7) 
However, because the malicious rule persists on disk and is re-loaded and re-evaluated on every subsequent matching tool call, an attacker can repeatedly stall (near-)every Bash command or file edit that matches the rule's `tool_matcher`/event, degrading the approval pipeline's usability/availability across the session rather than causing a single indefinite lockup.

### Likelihood Explanation
Feasible if the attacker can drop or commit a `.claude/hookify.*.local.md` file (e.g., in a shared/cloned repo) and can also cause matching tool_input content to flow through Bash commands or file edits (e.g., via a crafted diff/PR content that a user or agent later edits/reads). Repeatable on every matching tool invocation as long as the rule file remains present and enabled.

### Recommendation
Apply the same defense already present in `plugins/security-guidance/hooks/extensibility.py` to `plugins/hookify/core/rule_engine.py`: validate/reject rule patterns exhibiting known catastrophic-backtracking shapes (nested quantifiers, wildcard groups under repetition, overlapping alternation) at rule-load time in `config_loader.py`/`compile_regex()`, and additionally enforce a hard wall-clock timeout around each `regex.search()` call in `_regex_match()` (e.g., via a watchdog thread/subprocess or a length cap on `text`), falling back to "no match" on timeout so a single crafted pattern cannot stall the hook.

### Proof of Concept
Fuzz/unit test plan:
1. In a test for `rule_engine.compile_regex`/`RuleEngine._regex_match`, construct adversarial pattern/text pairs, e.g. pattern `r"(a+)+$"` with text `"a" * 30 + "!"`, or pattern `r"(.*)*"` with a long non-matching string.
2. Call `RuleEngine()._regex_match(pattern, text)` wrapped in a wall-clock timeout (e.g. `faulthandler`/`multiprocessing` with a 500ms budget) and assert the call returns within the budget.
3. Show it currently fails (hangs beyond budget) for `(a+)+$` against strings with tens of `a`s, demonstrating unbounded backtracking growth, while patterns rejected by `extensibility.py`'s `_has_redos_structure` for the same shapes would be caught if that check were reused in `rule_engine.py`/`config_loader.py`.
4. After the fix, assert all fuzzed pattern/text pairs return within the time budget (either matched, not matched, or rejected at load time).

```python
    def _regex_match(self, pattern: str, text: str) -> bool:
        """Check if pattern matches text using regex.

        Args:
            pattern: Regex pattern
            text: Text to match against

        Returns:
            True if pattern matches
        """
        try:
            # Use cached compiled regex (LRU cache with max 128 patterns)
            regex = compile_regex(pattern)
            return bool(regex.search(text))

        except re.error as e:
            print(f"Invalid regex pattern '{pattern}': {e}", file=sys.stderr)
            return False
```

```python
def load_rules(event: Optional[str] = None) -> List[Rule]:
    """Load all hookify rules from .claude directory.

    Args:
        event: Optional event filter ("bash", "file", "stop", etc.)

    Returns:
        List of enabled Rule objects matching the event.
    """
    rules = []

    # Find all hookify.*.local.md files
    pattern = os.path.join('.claude', 'hookify.*.local.md')
    files = glob.glob(pattern)

    for file_path in files:
        try:
            rule = load_rule_file(file_path)
            if not rule:
                continue

            # Filter by event if specified
            if event:
                if rule.event != 'all' and rule.event != event:
                    continue

            # Only include enabled rules
            if rule.enabled:
                rules.append(rule)

        except (IOError, OSError, PermissionError) as e:
            # File I/O errors - log and continue
            print(f"Warning: Failed to read {file_path}: {e}", file=sys.stderr)
            continue
        except (ValueError, KeyError, AttributeError, TypeError) as e:
            # Parsing errors - log and continue
            print(f"Warning: Failed to parse {file_path}: {e}", file=sys.stderr)
            continue
        except Exception as e:
            # Unexpected errors - log with type details
            print(f"Warning: Unexpected error loading {file_path} ({type(e).__name__}): {e}", file=sys.stderr)
            continue

    return rules
```

```python
# Catastrophic backtracking: nested quantifiers, overlapping alternations
# under repetition, and wildcard groups under repetition. Static check, not a
# proof — catches the common shapes that hang the hook on every edit.
_REDOS_SHAPES = [
    re.compile(r"\([^()]*[+*][^()]*\)[+*?]"),  # nested quantifier: (a+)*  (a*b)*
    re.compile(r"\(\.\*[^()]*\)[+*]"),         # wildcard group: (.*)*
]
_ALT_UNDER_REP = re.compile(r"\(([^()]*)\|([^()|]*)(?:\|[^()]*)*\)[+*]")


def _has_redos_structure(regex: str) -> bool:
    """Heuristic catastrophic-backtracking check. Not a proof. Catches:
      - nested quantifiers ((a+)*, (a*b)+)
      - wildcard groups under repetition ((.*)*)
      - alternation under repetition where one branch is a prefix of another
        ((a|aa)*, (ab|a)*) — these overlap and explode on non-matching input.
    Does NOT flag non-overlapping alternation ((a|b)*) which is safe."""
    if any(p.search(regex) for p in _REDOS_SHAPES):
        return True
    for m in _ALT_UNDER_REP.finditer(regex):
        branches = [b for b in m.group(0).strip("()*+").split("|") if b]
        for i, a in enumerate(branches):
            for b in branches[i + 1:]:
                # If one branch is a literal prefix of another, the alternation
                # overlaps and the engine backtracks combinatorially.
                if a.startswith(b) or b.startswith(a):
                    return True
    return False
```
