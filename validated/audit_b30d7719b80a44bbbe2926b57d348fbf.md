### Title
Front-runnable channel-nonce (`var['period']`) allows the losing party to DOS a legitimate fraud-proof claim in the reference payment-channel Autonomous Agent - (File: `test/samples/payment_channels.oscript`)

### Summary
The reference off-chain payment-channel AA template shipped in `test/samples/payment_channels.oscript` binds every off-chain, Muon/oracle-less peer signature (`sentByPeer`) to the current value of a state variable `var['period']`, exactly analogous to the nonce used by Symmetry's Muon uPnL signatures. Because `period` is only advanced by on-chain triggers (`confirm closure` / `fraud proof`) that any of the two channel counterparties can send, the party who is about to be caught lying about the amount it spent can watch the DAG for the honest counterparty's incoming `fraud_proof` trigger and race a `confirm closure` (or another period-incrementing) trigger of its own so that, by the time the `fraud_proof` unit is processed, `var['period']` no longer equals the `period` embedded in the honest counterparty's pre-signed message, causing the check to bounce and the fraud proof to fail.

### Finding Description
The channel logic stores a monotonically increasing `period` counter in AA state and requires every peer-signed message used in `start closing` and `fraud proof` cases to carry the same `period`: [1](#0-0) 

`period` is advanced only in two places, `confirm closure` and a successful `fraud proof`: [2](#0-1) 

The `confirm closure` case can be triggered immediately (without waiting for `$close_timeout`) by whichever party did **not** initiate the closing: [3](#0-2) 

This is structurally identical to the Symmetry issue: the fraud-proof / liquidation-style transaction is authorized by an off-chain signed message that embeds a sequence value (`period` here, `nonce` there) which is checked for equality against on-chain state at execution time (`is_valid_signed_package` + `signed_message.period != var['period']`), while the counterparty is free to submit an ordinary, always-available state-changing trigger (`confirm closure`) that mutates that same sequence value before the pending transaction is processed. Because Obyte units are gossiped and only become stable/executed once they get included on the main chain, an attacker monitoring the network for the honest party's incoming `fraud_proof` unit can race in their own `confirm closure` trigger so it gets processed by the AA first, incrementing `period` and invalidating the pending fraud-proof unit's signed message (`bounce('signed for a different period of this channel')`).

### Impact Explanation
If the race succeeds, the party that under-reported the amount it spent to its counterparty (the "lie") permanently avoids the fraud-proof penalty (loss of the entire remaining channel balance) that the protocol is specifically designed to impose. The victim, having already obtained a valid `sentByPeer` signature proving the fraud, cannot get it accepted because the state has moved on, and the channel closes using the fraudulent, previously-claimed balances. This is a direct loss of funds for the honest party and a bypass of the core security guarantee of the payment-channel construction (fraud-proof punishment), matching the "AA fund loss" impact category.

### Likelihood Explanation
The attack requires no special privileges beyond being one of the two channel counterparties (already an "AA trigger sender" as defined by the channel), and no secret keys beyond the ones the design already assumes each party holds. The race only requires observing the counterparty's `fraud_proof` unit as it propagates and submitting a competing `confirm closure` trigger before it stabilizes/executes — feasible given normal DAG propagation timing, especially because `confirm closure` is a trivial, single-field trigger (`trigger.data.confirm`) with no signature dependency, so it can be produced and broadcast far faster than the honest party's more complex fraud-proof trigger.

### Recommendation
Do not allow the non-initiating party to unilaterally advance the channel `period`/close the channel (via `confirm closure`) while a period-scoped, signature-backed claim (fraud proof) can still be pending; e.g., require a dispute window during which `confirm closure` is disabled once any `fraud_proof`-eligible signed message referencing the current `period` has been broadcast, or make the fraud-proof check independent of `period` equality (e.g., accept any signed message whose `period` is **less than or equal to** the period being finalized, rather than requiring strict equality), so that a same-period or earlier signature obtained honestly cannot be invalidated by a race to increment `period`.

### Proof of Concept
1. Party A opens a channel with Party B and spends more off-chain to B than A intends to admit at closing time (A holds a signed message `sentByPeer` from itself to B proving the true, higher `amount_spent` for the current `period`).
2. A calls `start closing` claiming a lower `transferredFromMe`, setting `var['close_initiated_by'] = 'A'` and locking in the understated `spentByA`. [4](#0-3) 
3. B, holding A's genuine higher-amount signed message for the same `period`, broadcasts a `fraud_proof` trigger to claim the entire remaining balance. [5](#0-4) 
4. Before B's `fraud_proof` unit becomes stable/executed by the AA, A (the non-initiator is B, so B could confirm — but symmetrically, if B is the liar and A initiated closing on B's behalf, A can immediately fire `confirm closure` since `close_initiated_by != $party` for A) races in a `confirm closure` trigger, which is processed first and executes `var['period'] += 1`.
5. B's `fraud_proof` unit is then processed against the new `period`; the check `trigger.data.sentByPeer.signed_message.period != var['period']` now evaluates true, so the AA bounces with `'signed for a different period of this channel'`, and B's valid fraud evidence is discarded — funds are already released to A/B under the fraudulent closing balances from step 2.
