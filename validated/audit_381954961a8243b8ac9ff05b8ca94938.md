### Title
Cross-repository Status forgery bypasses `deployment_checks`/CI gating and force-resumes paused continuous delivery - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves target commits purely by SHA (`Commit.where(sha: params.sha)`) with no repository/stack scoping, unlike every other webhook handler in the engine which resolves the target stack via `Repository.from_github_repo_name(repository_name)`. A correctly-signed `status` webhook for *any* repository sharing a GitHub App/organization webhook secret with Shipit can therefore mutate `Status` records — and thus `Commit#deployable?` — of a completely unrelated stack whose commit happens to share the same SHA, forcing a paused/delayed continuous-delivery pipeline to resume.

### Finding Description
The binding that must hold before a status update is applied is:
`commit.stack.repository.full_name == payload.repository.full_name`

That equality is never checked. Compare the base handler's scoping helper: [1](#0-0) 
which every other handler (`PushHandler`, `PullRequest::*Handler`, `CheckSuiteHandler`) relies on to filter by `Repository.from_github_repo_name`, against `StatusHandler#process`: [2](#0-1) 
which queries `Commit.where(sha: params.sha)` globally, across every stack/repository in the Shipit instance, and calls `commit.create_status_from_github!(params)` on each match.

`Status#after_create`/`after_commit` then unconditionally runs: [3](#0-2) [4](#0-3) 
which schedules `ContinuousDeliveryJob`, which calls `Stack#trigger_continuous_delivery`: [5](#0-4) 
`should_delay_continuous_delivery?` re-evaluates `commit.deployable?` (now flipped to `true` by the forged status) and `deployment_checks_passed?`: [6](#0-5) 
If the forged status makes the commit `deployable?` and `deployment_checks_passed?` is a stack-agnostic check that already passes, `trigger_deploy` runs, calling `continuous_delivery_resumed!`: [7](#0-6) 

Existing guards examined and why they don't stop this:
- `verify_signature` in `WebhooksController` validates the HMAC against `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight out of the attacker-supplied JSON body (`params.dig('repository','owner','login')`), not from any independently authenticated channel: [8](#0-7) 
This still requires knowledge of the correct `webhook_secret` for the claimed org to pass HMAC verification — it stops truly out-of-org forgery — but GitHub App / webhook secrets are typically provisioned per **organization** (single `@config[:webhook_secret]` in `GitHubApp`, see `lib/shipit/github_app.rb` lines 44-57, 76-83), not per repository. Any repository within that same organization/app installation (including one the attacker legitimately owns/administers under that org, or a fork sharing commit history) produces a validly-signed `status` webhook. Because `StatusHandler` does not additionally check that the payload's `repository.full_name` matches the target commit's stack repository, a legitimately-signed webhook from repo A can mutate commits belonging to stack B's repository C, as long as A and C share a commit SHA (common ancestor, shared vendored history, mirror, or identical commit content) — this is exactly the "payload for one repository mutating another's stack/commit" critical-impact category.

### Impact Explanation
A forged/legitimate-but-misdirected `status` event for a SHA shared across repositories lets an attacker with push/CI access to one repository under the trusted webhook-secret domain flip `deployable?` on a commit belonging to an entirely different stack/repository/tenant, forcing `continuous_delivery_resumed!` and an unauthorized deploy (`Deploy` record created, `trigger_deploy` executed) on a stack whose `deployment_checks` are still failing. This is repeatable against any stack whose tracked commit SHA can be made to coincide with a SHA the attacker can emit a status for (shared base commits, forks, mirrors, monorepo history). Matches the Critical category: "a payload for one repository mutating another's stack, commit, task or team" and "an unauthorized deploy."

### Likelihood Explanation
Requires: (1) `Shipit.deployment_checks` configured for the victim stack, (2) the attacker's own repository/webhook shares the same organization-level `webhook_secret` as the victim stack's repository (common in single-org multi-repo Shipit deployments), and (3) the attacker's status event references a SHA that also exists in the victim stack's commit table (e.g. shared history, fork, mirrored repo, or subtree). Precondition (2)/(3) narrow feasibility versus a fully out-of-tenant attacker, but the core code defect — no repository scoping in `StatusHandler#process` — is unconditionally present and trivially reachable via a single, cheap, legitimately-signed webhook once those preconditions are met.

### Recommendation
Scope `StatusHandler#process` the same way as the other handlers: resolve the target stack(s) via `Repository.from_github_repo_name(payload.dig('repository','full_name'))` (the `stacks` helper already defined in `Handler`), and only update commits belonging to that repository's stacks, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` instead of the unscoped `Commit.where(sha: params.sha)`.

### Proof of Concept
Add to a new/existing test file (e.g. `test/models/webhooks/handlers/status_handler_test.rb`) a minitest asserting the equality holds only after scoping is added:
```ruby
test "cross-repo forged status does not resume a different stack's continuous delivery" do
  victim_stack = shipit_stacks(:shipit) # tracks Shipit.deployment_checks-gated repo
  victim_stack.update!(continuous_deployment: true)
  Shipit.deployment_checks = FailingChecks # stub .call to false
  victim_stack.trigger_continuous_delivery
  assert victim_stack.continuous_delivery_delayed?

  other_repo_commit = shipit_commits(:cyclimse_first) # different repository/stack
  # force SHA collision to simulate shared history
  other_repo_commit.update_column(:sha, victim_stack.next_commit_to_deploy.sha)

  payload = ExplicitParameters::Parameters.new(
    sha: other_repo_commit.sha, state: 'success', context: 'ci/other-repo'
  )
  assert_no_difference "Deploy.count" do
    Shipit::Webhooks::Handlers::StatusHandler.call(
      'sha' => other_repo_commit.sha, 'state' => 'success',
      'repository' => { 'full_name' => 'attacker/other-repo' }
    )
  end
  assert victim_stack.reload.continuous_delivery_delayed?, "victim stack must remain delayed"
end
```
Before the fix this fails (`Deploy.count` increases and `continuous_delivery_delayed?` becomes false) because `StatusHandler` matches `victim_stack`'s commit purely by SHA; after scoping by repository it passes.

      return if cached_deploy_spec.blank?
