### Title
Rounding error when splitting headers commission among multiple `earned_headers_commission_recipients` causes byte supply drift (inflation or permanent loss) - (File: `headers_commission.js`)

### Summary
`calcHeadersCommissions()` splits a winning unit's headers commission (`full_amount`, an integer number of bytes) among several `earned_headers_commission_recipients` by independently rounding each recipient's share with `Math.round(full_amount * share / 100.0)`. Because each recipient's payout is rounded separately rather than the residual being tracked, the sum of the rounded payouts can differ from `full_amount`. The commission-splitting logic in `paid_witnessing.js` (`Math.round(payload_commission / count_paid_witnesses)` applied identically to every paid witness) has the same defect. There is no mechanism anywhere in the codebase to recover an under-distributed remainder or to prevent an over-distributed excess.

### Finding Description
`calcHeadersCommissions()` computes, for each unit that wins headers commission, a `full_amount` (the fixed `headers_commission` paid by the parent/payer unit) and distributes it to one or more recipients defined in `earned_headers_commission_recipients`: [1](#0-0) [2](#0-1) 

When there is a single recipient with 100% share, `full_amount` is passed through unmodified, avoiding any rounding. But whenever the winning unit has ≥2 `earned_headers_commission_recipients` (allowed and validated only for "sum of shares == 100", not for rounding safety), each recipient's payout is computed independently via `Math.round(full_amount * share / 100.0)`: [3](#0-2) 

Because JavaScript's `Math.round` always rounds `.5` up, splitting an odd `full_amount` between two recipients at 50/50 rounds *both* halves up (e.g., `full_amount=101` → `round(50.5)=51` for each recipient → `51+51=102`), silently minting one extra byte that was never actually paid by anyone. Conversely, with 3+ unevenly-weighted recipients, the sum of independently rounded shares can fall short of `full_amount`, permanently losing bytes because there is no leftover-tracking or "dust" recipient.

These rounded, uncorrected amounts are written to `headers_commission_contributions` and then aggregated with `SUM(amount)` into `headers_commission_outputs`, which becomes spendable via `headers_commission` inputs: [4](#0-3) [5](#0-4) 

The resulting `headers_commission_outputs` rows are later spent as real network inputs (validated and summed in `mc_outputs.calcEarnings`/`validatePaymentInputsAndOutputs`): [6](#0-5) 

The exact same class of bug exists in `paid_witnessing.js`, where `payload_commission` is divided by `count_paid_witnesses` and each of the `count_paid_witnesses` recipients gets `Math.round(payload_commission / count_paid_witnesses)` — the sum of `count_paid_witnesses` identical roundings systematically differs from `payload_commission`: [7](#0-6) [8](#0-7) 

Nothing in the schema or code reconciles this drift; `headers_commission_outputs`/`witnessing_outputs` simply record whatever the (possibly incorrect) rounded sum happens to be, and this becomes real spendable bytes on the DAG.

### Impact Explanation
- **Inflation**: An attacker who controls both authors of a multi-authored unit (a completely normal, unprivileged action — anyone can post a 2-of-2-authored unit and freely choose `earned_headers_commission_recipients` shares) can arrange an odd `headers_commission` amount split 50/50 between two addresses they control. Every time such a unit wins headers commission, the rounding of both halves upward mints one extra byte that was never paid for by any other party, permanently increasing the circulating base-currency supply credited to the attacker. This can be repeated indefinitely by spamming such units.
- **Permanent loss**: With unevenly weighted or ≥3-way splits, the sum of independently rounded shares can be less than `full_amount`; the shortfall is never recorded in `headers_commission_outputs` for any address and is permanently unspendable — a silent, unrecoverable loss of bytes from circulation.
- The same systemic drift, at protocol scale (not attacker-controlled) but continuous, occurs in `paid_witnessing.js`'s witness-commission split for every unit with more than one paid witness, since count_paid_witnesses and payload_commission are rarely evenly divisible.

Both effects break the DAG's fundamental invariant that the total money supply is conserved and each byte fee paid corresponds to bytes actually payable to recipients — matching the impact class the report describes (funds permanently lost/locked, or additional value materialized without being paid for).

### Likelihood Explanation
Multi-authored units with custom `earned_headers_commission_recipients` shares are a normal, fully user-controlled feature (no special privilege required, as evidenced by `composer.js` letting any caller supply `earned_headers_commission_recipients`). Winning headers commission from a parent is probabilistic per unit but can be repeated over many self-authored unit chains, so the inflation path is straightforward to trigger deliberately and repeatedly. The witnessing-side rounding loss/gain happens automatically on virtually every stable MC unit with more than one paid witness, making it a continuous, unavoidable systemic drift.

### Recommendation
- When splitting `full_amount` among `earned_headers_commission_recipients` (and similarly for `payload_commission` among paid witnesses), compute all-but-the-last recipient's share with rounding, then assign the last recipient the exact remainder (`full_amount - sum_of_others`) instead of independently rounding every share. This guarantees the total distributed equals `full_amount` exactly, eliminating both the inflation and the loss vectors.
- Add a protocol-level invariant check/test asserting that `SUM(headers_commission_contributions.amount)` per payer unit equals `punits.headers_commission`, and similarly for `witnessing_outputs` vs `payload_commission`, to catch regressions.

### Proof of Concept
1. Attacker controls addresses A and B, and posts a 2-of-2-authored unit U with `earned_headers_commission_recipients = [{address:A, share:50}, {address:B, share:50}]` (valid per `validateHeadersCommissionRecipients`, since 50+50=100).
2. U becomes the headers-commission "winner" for some parent unit P whose `headers_commission` (`full_amount`) is an odd integer, e.g. 101 bytes.
3. In `calcHeadersCommissions()`, for A: `Math.round(101*50/100) = Math.round(50.5) = 51`; for B: same calculation → 51. Total credited = 102 bytes, one more than the 101 bytes actually paid by P.
4. `headers_commission_outputs` now contains 102 spendable bytes for A+B combined even though only 101 were ever paid — the extra byte is later validated and spendable as legitimate network currency via `validatePaymentInputsAndOutputs`'s `headers_commission` input handling.
5. Repeating this with many such units lets the attacker accumulate unlimited "free" bytes, inflating total supply.

		var prev_address = "";
		for (var i=0; i<objUnit.earned_headers_commission_recipients.length; i++){
			var recipient = objUnit.earned_headers_commission_recipients[i];
			if (!isPositiveInteger(recipient.earned_headers_commission_share))
				return cb("earned_headers_commission_share must be positive integer");
			if (hasFieldsExcept(recipient, ["address", "earned_headers_commission_share"]))
				return cb("unknown fields in recipient");
			if (!isValidAddress(recipient.address))
				return cb("invalid recipient address checksum");
			if (recipient.address <= prev_address)
				return cb("recipient list must be sorted by address");
			total_earned_headers_commission_share += recipient.earned_headers_commission_share;
			prev_address = recipient.address;
		}
		if (total_earned_headers_commission_share !== 100)
			return cb("sum of earned_headers_commission_share is not 100");
	}
	cb();
}
