### Title
Missing zero-address validation for the `creator` account in `initialize_with_permission` permanently locks pool creator fees - (File: `programs/cp-swap/src/instructions/initialize_with_permission.rs`)

### Summary
`initialize_with_permission` accepts an arbitrary, unvalidated `creator` account and stores it as `pool_creator` in `PoolState`, exactly mirroring the reported `Token.sol::updateFounders` pattern where a wallet address parameter is persisted with no check against `address(0)` (or any other unclaimable/incorrect value).

### Finding Description
In `InitializeWithPermission`, `creator` is declared as a plain `UncheckedAccount` with no signer requirement and no `constraint`/`address` check: [1](#0-0) 

This account is passed straight into `pool_state.initialize(...)` as the pool's `pool_creator` field: [2](#0-1) 

Only `payer` is required to be a signer and to hold a valid `permission` PDA; `creator` is completely attacker-controlled data in the instruction's account list, so the caller (whoever holds a valid `permission` account) can set `creator` to `Pubkey::default()` (address(0)) or to any other address that has no matching private key.

Once a pool is created this way, all creator-fee accounting continues to accrue against that pool (`pool_state.creator_fees_token_0/1`) via the swap-fee split logic, regardless of the validity of `pool_creator`.

The only permissioned way to claim these fees is `collect_creator_fee`, which requires the caller to be a `Signer` whose key equals `pool_state.pool_creator`: [3](#0-2) 

If `pool_creator == address(0)` (or any address without a corresponding keypair), nobody can ever produce a valid signature for that account, so `collect_creator_fee` can never succeed for that pool.

Note: the program also exposes `collect_creator_fee_permissionless.rs`, which appears intended as a fallback path for creator-fee collection without the creator's signature; I was not able to fully verify within this session whether that instruction correctly handles/redirects fees when `pool_creator` is address(0) or another unclaimable value. If it does not special-case this, the freezing described below is permanent; if it does, the impact may be reduced to loss-of-intended-recipient rather than total freezing, but the root-cause input-validation gap in `initialize_with_permission` remains.

### Impact Explanation
Every swap on an affected pool routes a defined share of trade fees into `creator_fees_token_0`/`creator_fees_token_1` in `PoolState` (per the `CreatorFeeOn` configuration set at pool creation). If `pool_creator` was set to address(0) (or an equivalent unclaimable address) at pool-creation time, those accumulated fees sit in the pool's token vaults but can never be withdrawn through the signer-gated `collect_creator_fee` path — this is a freezing-of-funds condition on LP/protocol-designated creator fees, analogous in class to the original report's "funds can go to/be stuck at address(0)."

### Likelihood Explanation
Reaching this requires only a single transaction to `initialize_with_permission` by any account already holding a valid `permission` PDA (i.e., any account approved to create permissioned pools) — no privileged program-admin key is required, and the caller fully controls the `creator` field value with no on-chain check preventing `Pubkey::default()`. The regular `initialize` (permissionless) instruction is not affected, because there `creator` is enforced to be `Signer<'info>` (an address with no known private key cannot practically be supplied as a signer), so this issue is confined to the permissioned pool-creation path.

### Recommendation
Add an explicit validation on the `creator` account in `InitializeWithPermission`, e.g. `require_keys_neq!(creator.key(), Pubkey::default())`, and consider requiring `creator` to be a recognized/owned account (or requiring it to co-sign, similar to `initialize`) before persisting it as `pool_state.pool_creator`.

### Proof of Concept
1. Obtain a valid `permission` PDA for `payer` (as required by `initialize_with_permission`'s account constraints) — this is the only "privilege" needed and is the intended entry condition for this instruction. [4](#0-3) 
2. Call `initialize_with_permission` supplying `creator = Pubkey::default()` (address(0)) in the accounts list; the instruction performs no check on this value and stores it via `pool_state.initialize(...)`. [2](#0-1) 
3. Perform swaps against the newly created pool; trade fees accrue into `pool_state.creator_fees_token_0/1` per the configured `creator_fee_on` split.
4. Attempt `collect_creator_fee`: it requires `creator: Signer` whose key equals `pool_state.pool_creator` (`Pubkey::default()`), which can never be signed for, permanently freezing the accrued creator fees for that pool (absent a verified alternate recovery path in `collect_creator_fee_permissionless`).
