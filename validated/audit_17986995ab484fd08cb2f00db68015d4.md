## Title
API token stack-scope bypass in `CCMenuController` — token authorized for one stack can read any stack - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::BaseController` enforces that a stack-scoped `ApiClient` (one created with a specific `stack_id`) can only resolve stacks through `stacks.from_param!(params[:stack_id])`, where `stacks` is filtered to `Stack.where(id: current_api_client.stack_id)` when the client is scoped. `Shipit::Api::CCMenuController`, however, overrides `stack` and resolves it directly with `Stack.from_param!(params[:stack_id])`, bypassing the scoping entirely. This breaks the equality that should hold: *the set of stacks a token is authorized for == the set of stacks the endpoint actually touches*.

### Finding Description
`BaseController` defines the canonical, scope-respecting lookup: [1](#0-0) 

`stacks` restricts the visible `Stack` set to `current_api_client.stack_id` when the client is scoped, and `stack` resolves the `:stack_id` param only within that restricted relation. This is the mechanism other API controllers (e.g. `Api::StacksController`) rely on to keep a stack-scoped token from touching stacks outside its `stack_id`.

`Api::CCMenuController` overrides this method and skips the scoping: [2](#0-1) 

`stack` here calls `Stack.from_param!(params[:stack_id])` directly on the `Stack` model, with no reference to `current_api_client.stack_id`. It also overrides `authenticate_api_client` to additionally support authenticating via the `token` query param (for CCTray/CI clients), reinforcing that this controller is meant to be reachable with a stack-scoped token, yet the stack lookup ignores that scope.

The only enforced check is a permission check (`require_permission :read, :stack`), which validates the *operation* (`read:stack`) but not the *object* (whether the token's `stack_id` matches the requested `params[:stack_id]`): [3](#0-2) 

This is precisely the "stack a token authorises vs stack it touches" binding: `current_api_client.stack_id` is the field that defines what the token is scoped to authorize, but `params[:stack_id]` (attacker-controlled) is the field the controller actually acts on when building the response, and the code never asserts they're equal.

### Impact Explanation
An `ApiClient` scoped to stack A (`stack_id` set at creation, e.g. fixture `here_come_the_walrus`) is meant to only be able to read stack A's status via the API, per `require_permission :read, :stack` and the `stacks`/`stack` scoping used everywhere else in the API. Via `CCMenuController#show`, that same token can instead pass an arbitrary `stack_id` param and receive `deploys_and_rollbacks`, deploy status (success/failure), and stack name for *any* stack in the Shipit install — an unauthorized read of stack/task state (deploy status information) for repositories/environments the token was never granted access to. This matches the High-impact category "unauthenticated/unauthorized read of stack state, task streams or deploy output" for a token with narrower authorized scope, without needing a session, `webhook_secret`, `api_clients_secret`, or any privileged credential beyond the (deliberately scoped-down) token itself.

### Likelihood Explanation
High. `CCMenuController#show` is a simple, unauthenticated-by-role, single-parameter GET endpoint (`stack_id`) reachable by any holder of a valid, even minimally-scoped, `ApiClient` token (including tokens meant to be handed to CI/CCTray tools with intentionally restricted `stack_id` scope). No other precondition (organization, repo write access, session) is required — only possession of a stack-scoped token, which is the normal, low-privilege credential this endpoint is designed to accept.

### Recommendation
Remove `CCMenuController`'s custom `stack` override, or make it respect `current_api_client.stack_id` the same way `BaseController#stacks`/`#stack` do, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
reusing the inherited `stacks` scoping instead of calling `Stack.from_param!` directly on the unscoped model.

### Proof of Concept
1. Create two stacks, `stack_a` (`id=1`) and `stack_b` (`id=2`).
2. Create an `ApiClient` scoped to `stack_a` only (`stack_id: 1`, permissions include `read:stack`) — e.g. as done for fixture `here_come_the_walrus`, which is asserted elsewhere to only see stack `shipit` via `Api::StacksController#index`: [4](#0-3) 
3. Using that token's `authentication_token`, call:
```
GET /api/1/ccmenu.xml?token=<here_come_the_walrus_token>
```
where `1` corresponds to `stack_b`'s param (a stack this client was never scoped to).
4. `CCMenuController#authenticate_api_client` accepts the token via the `token` param, and `CCMenuController#stack` resolves `Stack.from_param!(params[:stack_id])` without checking `current_api_client.stack_id`, so the request returns `stack_b`'s CCTray XML (name, last build status, last build label) — data the token was never authorized to read, unlike the equivalent `Api::StacksController#show`, which would 404/scope-filter it away.
