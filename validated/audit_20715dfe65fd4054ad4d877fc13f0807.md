### Title
Cross-organization forged commit status via `StatusHandler` unscoped `Commit.where(sha:)` lookup - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` binds trust to the GitHub organization named in the payload's `repository.owner.login` field [1](#0-0) [2](#0-1) , but `Shipit::Webhooks::Handlers::StatusHandler#process` does not verify that the commit it mutates actually belongs to that organization's repository — it looks up commits globally by SHA across the *entire* Shipit installation. This is the same bug class as the reported EIP-712 issue: a value that is used to compute/authorize the action (`repository.owner.login`, verified by HMAC) is not the same value that scopes the write (`sha`, unauthenticated to any particular repo/organization).

### Finding Description
The webhook signature check picks the GitHub App/organization to verify against solely from `repository.owner.login` (or `organization.login`) in the JSON body: [1](#0-0) [2](#0-1) 

The HMAC (`X-Hub-Signature`) does cover the full raw request body (so an attacker cannot alter `sha` after having it validated by a *different* org's secret) — but the HMAC only proves "this exact payload was signed by whoever holds `Shipit.github(organization: repository_owner)`'s webhook secret." It does **not** prove any relationship between the fields inside that payload and the repository that ends up being mutated. Shipit explicitly supports hosting multiple GitHub organizations, each with its own independently‑administered GitHub App and `webhook_secret` [3](#0-2) . An organization admin fully controls their own GitHub App's webhook secret, and can therefore freely construct and correctly sign arbitrary JSON payloads as long as `repository.owner.login` matches their own org.

`StatusHandler` then processes that already-"verified" payload: [4](#0-3) 

`Commit.where(sha: params.sha)` is not scoped by `repository_name`/stack/organization at all — unlike `PushHandler`, which correctly restricts to `stacks` derived from `repository.full_name` [5](#0-4) , and unlike the base `Handler` class which provides exactly this scoping mechanism (`stacks`/`repository_name`) [6](#0-5)  but `StatusHandler` never uses it.

This produces the following equality break: **the organization that authenticated the webhook (`repository.owner.login`, verified via HMAC) ≠ the repository/stack whose commit is written (looked up globally by `sha`, an attacker-choosable but publicly-known git SHA)**. Any organization with its own legitimately configured GitHub App on this Shipit instance can sign a `status` event where `repository.owner.login` is their own org (passing signature verification) while `sha` is a real commit SHA belonging to a completely different organization's stack (public information visible via GitHub UI/API).

### Impact Explanation
`Commit#create_status_from_github!` writes an arbitrary GitHub-style status (`state`, `description`, `target_url`, `context`) for that foreign commit [7](#0-6) . This directly affects deployability logic: `deployable?` depends on `success?` derived from these statuses [8](#0-7) , and `schedule_continuous_delivery` triggers a `ContinuousDeliveryJob` whenever the commit becomes deployable and the target stack has continuous deployment enabled [9](#0-8) . A cross-org attacker who forges a "success" status for a victim commit already sitting undeployed on a continuously-deployed victim stack can trigger an unauthorized deploy of that commit — meeting the "unauthorized deploy" impact bar. It can also mark a legitimately bad/malicious commit as passing CI to defeat `blocking_statuses`/manual review gating on `deployable?`/`blocked?`.

### Likelihood Explanation
Requires only that the attacker administers *some* GitHub organization/App that is configured on the same Shipit instance (a legitimate, low-privilege setup for multi-tenant Shipit deployments per the documented "Using Multiple Github Applications" pattern), and knowledge of a target commit SHA in another organization's stack, which is public on GitHub. No Shipit session, `ApiClient` token, or victim's `webhook_secret` is needed — only the attacker's own webhook secret for their own org, which is inherently attacker-controlled.

### Recommendation
In `StatusHandler#process`, scope the commit lookup to the repository named in the payload, consistent with `PushHandler` and the `Handler#stacks`/`repository_name` helpers, e.g. restrict to `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalently look up via `Repository.from_github_repo_name(repository_name)`'s stacks before touching `Commit`. More generally, every handler that trusts `repository.owner.login` for signature verification must scope its side effects to that same repository/organization, not perform global, cross-tenant lookups keyed only on attacker-supplied identifiers like `sha`.

### Proof of Concept
1. Attacker administers `attacker-org`, which has its own GitHub App configured in this Shipit instance's `github:` secrets (per `docs/setup.md` multi-org setup), giving them the org's `webhook_secret`.
2. Attacker identifies `victim_sha`, a real commit SHA in `victim-org/victim-repo`, a stack tracked by the same Shipit instance with continuous deployment enabled.
3. Attacker POSTs to `/github/hooks` (mounted `WebhooksController#create`) a `status` event body:
```json
{
  "repository": { "owner": { "login": "attacker-org" } },
  "sha": "<victim_sha>",
  "state": "success",
  "description": "forced success",
  "context": "ci/attacker"
}
```
4. Attacker signs the raw body with `attacker-org`'s own `webhook_secret` and sets `X-Hub-Signature: sha1=<hmac>`.
5. `WebhooksController#verify_signature` resolves `Shipit.github(organization: 'attacker-org')` and validates successfully, since the attacker legitimately owns that secret [1](#0-0) .
6. `StatusHandler.call(params)` runs `Commit.where(sha: victim_sha)` — matching the victim's commit regardless of organization — and calls `create_status_from_github!`, marking it successful [4](#0-3) .
7. If `victim-org/victim-repo`'s stack is undeployed at that commit and has `continuous_deployment?` enabled, `schedule_continuous_delivery` enqueues a deploy of a commit the attacker chose, without any of the victim's own CI ever reporting success [9](#0-8) .

Note: I was not able to fully trace `ContinuousDeliveryJob`'s exact deploy-trigger conditions or the routing configuration mounting `WebhooksController` (only `config/routes.rb` excerpts were available) within the indexed context; a Devin session with full repository access would be needed to confirm the exact route path and any additional guard conditions on continuous deployment before treating this as fully weaponizable to an unconditional deploy.
