### Title
`register-for-bond`/`stake` roll-overs alter an existing bond/stake position without tripping the `Pox` post-condition gate - (File: `pox-locking/src/pox_5.rs`)

### Summary
The `Pox` transaction post-condition and `with-pox` in-contract allowance are documented as gating "position-altering PoX-5 operations... that act on a principal's existing stacking/bond position": `unstake`, `unstake-sbtc`, `update-bond-registration`, `announce-l1-early-exit`. But `stake` and `register-for-bond` can also alter an existing position — via the bond↔stake roll-over feature — and neither the dispatcher's action-logging list nor the `with-pox`/`Pox` semantics cover them, so a roll-over escapes a permission gate that is supposed to protect the staker's existing position.

### Finding Description
`pox-locking/src/pox_5.rs::handle_contract_call` only calls `global_context.log_pox_action(staker)` for `"unstake" | "unstake-sbtc" | "update-bond-registration" | "announce-l1-early-exit"`: [1](#0-0) 

Yet `stake-5.clar`'s `stake` and `register-for-bond` explicitly support "roll-overs": a staker with an *existing* bond can roll into a new bond or an STX-only stake, and vice versa, carrying the STX lock forward and clearing/replacing the prior bond/stake membership record: [2](#0-1) [3](#0-2) 

This is documented explicitly in the CHANGELOG as a "position-altering" operation on par with the four gated ones:
> "pox-5: support seamless rollovers between bond and STX-only staking positions... In these cases, the STX lock is carried forward (amount may go up or down) with no release."

The `Pox` post-condition/allowance system is designed precisely to let a staker's position be defended against unwanted alteration by a contract acting on their behalf (`restrict-assets?`/`as-contract?` + `with-pox`), and the doc for `with-pox` states it gates "a position-altering PoX action — calling the active PoX contract to `unstake`, `unstake-sbtc`, `update-bond-registration`, or `announce-l1-early-exit`": [4](#0-3) 

Because `stake`/`register-for-bond` are excluded from `log_pox_action`, a wrapper contract given only `with-staking` (or no `with-pox` allowance at all) can invoke `register-for-bond`/`stake` on a staker's existing bond/stake and roll it into a different position (different signer/bond, different unlock schedule, different sBTC custody) — an alteration of the *existing* position — without the `Pox` post-condition/`with-pox` gate ever seeing it. The staker (or protocol relying on transaction-level `Pox` post-conditions/`with-pox` allowances to protect an existing position from being touched by an untrusted intermediary contract) has no way to block or detect this specific class of position mutation, even though the contract's own design intends the four-function boundary to be the complete boundary for "acts on a principal's existing position."

This is the direct analog of `fs.openAsBlob()` bypassing Node's `--experimental-permission` system: a data/action path that should be constrained by the permission mechanism (the `Pox` gate/`with-pox` allowance) reaches the same class of effect (mutating an existing locked position) through an alternate, un-gated entry point (`stake`/`register-for-bond` roll-over) that the permission system's authors did not include in its coverage list.

### Impact Explanation
This breaks the equality the `Pox`/`with-pox` mechanism is supposed to enforce: "every state-altering action on an existing stacking/bond position is covered by the gate." Via the roll-over path, a staker's signer assignment, unlock height (may be extended or shortened) and locked-amount composition can be changed by a contract that was only granted `with-staking` (or no PoX allowance), producing an unsigned/unauthorized stacking action from the staker's perspective at the permission-boundary the protocol explicitly built for this purpose. This matches the "unsigned stacking action" / "signing weight or reward slots exceeding locked value" category (High) since a rollover can move the staker to a different signer's reward slot and alter locked-value scheduling without being caught by the intended permission check — though the underlying `stake`/`register-for-bond` function itself still requires `tx-sender` to be the staker, so it cannot be used to attack a *different* principal's funds; it can only be used by an intermediary contract to move the calling staker's own position in ways `with-pox`/`Pox` was designed to let the staker block.

### Likelihood Explanation
Requires a staker to route a `stake`/`register-for-bond` call through an intermediary contract (e.g., a pooling or wrapper contract using `restrict-assets?`) while relying on `with-pox`/`Pox` post-conditions to control what that contract can do to their position — exactly the scenario the `with-pox` allowance's own documentation describes as its purpose. Given the contract explicitly ships this allowance system for `unstake`/`unstake-sbtc`/`update-bond-registration`/`announce-l1-early-exit`, and separately ships roll-over support for `stake`/`register-for-bond` with equivalent position-mutating semantics, the gap is a straightforward coverage omission rather than a hypothetical edge case.

### Recommendation
Extend the `Pox`-action logging (and the `with-pox` documentation/semantics) in `pox-locking/src/pox_5.rs::handle_contract_call` to also record a PoX action for `stake` and `register-for-bond` calls that execute a roll-over (i.e., where the staker already held a bond/stake membership prior to the call), so that `Pox` post-conditions and `with-pox` allowances correctly gate every code path that can alter an existing bond/stake position, consistent with the feature's own stated coverage.

### Proof of Concept
1. Alice holds an active bond (via `register-for-bond`) or STX-only stake (via `stake`) in pox-5.
2. Alice grants a wrapper contract `Wrapper.roll` only `(with-staking uX)` (or nothing) inside `restrict-assets?`, believing `with-pox`'s absence prevents the wrapper from touching her *existing* position, per the documented `with-pox` semantics.
3. Once inside the bond/stake's L1-unlock/roll-over window, `Wrapper.roll` calls `contract-call? pox-5 register-for-bond ...` (or `stake ...`) as Alice's `tx-sender`, hitting the roll-over branch (`bond-overlaps-new-position?` / `verify-bond-rollover-window` pass), which clears Alice's prior membership and re-establishes her position under new terms (new signer/bond-index/unlock height): [5](#0-4) 
4. `pox-locking`'s `handle_contract_call` does not call `log_pox_action` for `"stake"`/`"register-for-bond"`, so `AssetMap::did_pox_action(&alice)` remains `false`: [1](#0-0) 
5. A transaction-level `Pox(NotPerformed)` post-condition, or the absence of `with-pox` inside `restrict-assets?`, therefore does **not** flag or roll back this position change, even though it altered Alice's existing bond/stake exactly as the four explicitly-gated functions do.
