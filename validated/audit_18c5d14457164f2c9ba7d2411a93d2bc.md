### Title
Webhook signature verification is scoped to `repository.owner.login`/`organization.login` while event handlers act on the unrelated `repository.full_name` field, allowing cross-organization/cross-repository forgery in multi-tenant deployments - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to validate the HMAC signature against using `repository_owner` (`repository.owner.login`, falling back to `organization.login`), but the actual webhook handlers (`Handler#stacks`/`repository_name`, and every handler that calls `Shipit::Repository.from_github_repo_name(params.repository.full_name)`) act on the independent, attacker-controlled `repository.full_name` field. Because these two payload fields are never cross-checked, an attacker who can produce a valid signature for *any* configured organization (including one intentionally left with no `webhook_secret`) can point `repository.full_name` at a stack belonging to a completely different, properly-secured organization and have Shipit process the forged event against it.

### Finding Description
`Shipit::WebhooksController#verify_signature` picks the app/secret used for HMAC verification purely from the organization/owner named in the payload: [1](#0-0) [2](#0-1) 

`repository_owner` is read from `params.dig('repository', 'owner', 'login')` (or `organization.login`) — a JSON field fully controlled by the unauthenticated POST body, before any signature has been validated. This field only decides which `Shipit.github(organization: ...)`/`GitHubApp` (and hence which HMAC secret) is used: [3](#0-2) 

Critically, `verify_webhook_signature` returns `true` unconditionally when that organization's `webhook_secret` is blank/nil (a documented, supported configuration — see `test/dummy/config/secrets_double_github_app.yml` and `config/secrets.development.shopify.yml`, both showing `webhook_secret: # nil` per-org): [4](#0-3) 

Once the request passes `verify_signature`, `WebhooksController#create` dispatches the *entire attacker-controlled JSON body* to the handlers: [5](#0-4) 

Every handler resolves the target stack/repository from `params.repository.full_name` — a field that is never checked against `repository.owner.login`/`organization.login` used earlier for signature routing: [6](#0-5) [7](#0-6) 

This is the exact class of bug the reference report describes: a payload field (`assetsDiscount`/lock state) that is acted upon by privileged logic (`accPnlPerToken`, share price) without being bound to the field that was actually verified/committed. Here, the field verified for authenticity (`repository.owner.login`, used solely to pick the HMAC secret) is a different field from the one that determines what gets written (`repository.full_name`, used to select the `Stack`/`Repository` to mutate). In a single-tenant Shipit install this is moot because there is only one org/secret. But `lib/shipit.rb#github`/`github_app_config` and the documented "Using Multiple GitHub Applications" feature explicitly support multiple organizations, each with its own (optionally absent) `webhook_secret`: [8](#0-7) [9](#0-8) 

In that supported multi-org configuration, an attacker who knows (or who benefits from a misconfigured/absent) `webhook_secret` for **any** onboarded organization can craft a payload where:
- `repository.owner.login` (or `organization.login`) = the organization whose secret is weak/known/absent → passes `verify_signature`.
- `repository.full_name` = `"<victim-org>/<victim-repo>"` → resolved by the handler to write into a stack belonging to a **different**, properly-secured organization that the attacker has no credentials for.

### Impact Explanation
This breaks the binding `organization authenticated == repository written`, which is explicitly listed as an in-scope trust boundary. Depending on the event type, the attacker can:
- Forge `status` events to inject arbitrary CI/commit statuses on commits of a victim stack via `StatusHandler#process` → `Commit#create_status_from_github!`, which can flip deploy/merge gating logic. [10](#0-9) 
- Forge `push` events to trigger `GithubSyncJob`/`stack.sync_github`, causing Shipit to fetch and append attacker-influenced commit metadata into a victim stack's queue. [11](#0-10) 
- Forge `pull_request` `closed`/`labeled` events to archive/unarchive review stacks belonging to a victim repository. [12](#0-11) 

This does not directly hand over `GITHUB_TOKEN` or achieve RCE, but it does allow cross-repository writes to stack/commit/status state that the deploy pipeline trusts, and can influence merge/deploy gating for a repository the attacker does not control — matching the Critical "cross-repository writes" / "unauthorized deploy" category if it results in triggering a deploy pipeline action, or at minimum the High "escalation" category via manipulation of stack/commit state across organizational boundaries.

### Likelihood Explanation
Exploitability depends entirely on operator configuration: the engine must be configured with multiple GitHub organizations (a documented, supported feature), and at least one of those organizations must have a guessable/leaked/absent `webhook_secret`. Given `webhook_secret: nil` is shown as a normal example value in the shipped config templates (`config/secrets.development.shopify.yml`, `test/dummy/config/secrets_double_github_app.yml`), operators following the documentation are plausibly exposed. Likelihood is therefore configuration-dependent rather than universal, but the code itself performs no cross-field validation regardless of configuration, so the vulnerability is a latent design flaw in the engine, not merely a deployment mistake.

### Recommendation
Bind the field used to select/verify the signing secret to the same field used to resolve the target repository/stack. Concretely, `WebhooksController#verify_signature` should derive the verifying organization from the same `repository.full_name` (or repository id) that handlers use for lookup, and/or handlers should assert that `params.repository.owner.login`/`organization.login` matches the organization portion of `params.repository.full_name` before processing. Additionally, treat a `nil`/blank `webhook_secret` for a named organization as "reject all webhooks for this org" rather than "accept unconditionally," to avoid one weakly configured org undermining the security of others.

### Proof of Concept
1. Deploy Shipit with multi-org config (`config/secrets.yml`) containing:
   - `OrgAttacker` (webhook_secret: nil, or a known/leaked secret)
   - `OrgVictim` (webhook_secret: strong, unknown to attacker) with a real onboarded stack `OrgVictim/app`.
2. Attacker POSTs to `/github/webhooks` (or the engine's mounted webhook path) with:
   - Header `X-Github-Event: status`
   - Body: `{"repository": {"owner": {"login": "OrgAttacker"}, "full_name": "OrgVictim/app"}, "sha": "<victim commit sha>", "state": "success", ...}`
   - `X-Hub-Signature` computed with `OrgAttacker`'s secret (or omitted/anything if `OrgAttacker.webhook_secret` is nil).
3. `verify_signature` calls `Shipit.github(organization: "OrgAttacker")`, whose `verify_webhook_signature` returns `true` (secret blank or attacker-known secret matches).
4. `StatusHandler#process` runs unrestricted using `params.sha`, creating a forged "success" status on a commit belonging to `OrgVictim/app`, despite the attacker never having valid credentials for `OrgVictim`.

      return true unless webhook_secret

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
