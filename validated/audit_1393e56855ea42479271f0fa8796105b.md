## Title
Stack-scoped API tokens bypass their `stack_id` restriction in the CCMenu API endpoint - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::ApiClient` tokens can be minted with a `stack_id` that is supposed to restrict the token to a single stack [1](#0-0) , and `Api::BaseController#stacks`/`#stack` enforce that restriction for every other API endpoint [2](#0-1) . `Api::CCMenuController` overrides `#stack` to resolve the target stack directly from `Stack.from_param!(params[:stack_id])` instead of the scoped `stacks.from_param!`, so the `stack_id` restriction that the token authorizes is never checked against the stack it actually touches [3](#0-2) .

### Finding Description
The intended binding is: **stack a token authorizes == stack the request touches**. `ApiClient#stack_id?`-restricted tokens are meant to be confined to one stack, as demonstrated by the fixture `here_come_the_walrus` (`stack: shipit`, `permissions: [read:stack]`) and the accompanying test asserting "an api client scoped to a stack will only see that one stack" for `Api::StacksController#index` [4](#0-3) .

That restriction is implemented once, centrally, in `Api::BaseController`:
```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [2](#0-1) 

`Api::CCMenuController` inherits from `BaseController` and declares `require_permission :read, :stack` [5](#0-4) , but it redefines `#stack` to bypass the scoped `stacks` relation entirely:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [6](#0-5) 

Because `require_permission` only checks that the client's `permissions` array contains `read:stack` (`ApiClient#check_permissions!`) [7](#0-6)  and never re-validates `current_api_client.stack_id` against the resolved `stack`, any token that merely has `read:stack` — even one explicitly scoped to a single stack at creation time — can be replayed with an arbitrary `stack_id` param to read another stack's status through `#show`.

### Impact Explanation
`CCMenuController#show` renders `shipit/ccmenu/project`, which exposes the target stack's deploy/build state: `lastBuildStatus` (derived from `merge_status`, including whether the stack is `locked`/`backlogged`), `activity` (whether a deploy is currently running), `lastBuildTime`, `lastBuildLabel` (deploy id), and `webUrl` [8](#0-7) . A caller holding a token restricted to stack A can retrieve this operational/deploy-state data for stack B, which the token was never authorized to access — this is the "unauthenticated read of stack state" class of impact (the token that authenticates the request is not the token that authorizes reading that specific stack).

### Likelihood Explanation
Exploitation requires possession of any valid, stack-scoped `read:stack` API token (Basic-Auth header or `?token=` query param, per `authenticate_api_client`) [9](#0-8) . Such tokens are routinely created by the product's own `CCMenuUrlController#client`, which mints a `read:stack` client tied to a specific user/stack pairing and returns the token embedded in a URL [10](#0-9) . Anyone who legitimately has one such CCMenu URL/token for one stack can trivially change the `stack_id` parameter to enumerate and read the CI/deploy status of every other stack in the installation — no privilege escalation beyond having any one scoped token is needed.

### Recommendation
Remove the `#stack` override in `Api::CCMenuController` (or reimplement it using the inherited `stacks` relation) so that stack-scoped tokens are confined exactly as they are everywhere else in the API:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
This restores the `current_api_client.stack_id? -> Stack.where(id: current_api_client.stack_id)` narrowing performed in `Api::BaseController#stacks` for the CCMenu endpoint as well.

### Proof of Concept
1. Create (or obtain, e.g. via `CCMenuUrlController#fetch`) an `ApiClient` scoped to `stack_id = A` with permission `read:stack` (mirrors fixture `here_come_the_walrus`) [4](#0-3) .
2. Authenticate to `GET /api/:stack_id/ccmenu` (or the equivalent CCMenu XML route) using that token's Basic-Auth credentials, but set `stack_id` in the request to a different stack `B` that the token was never granted access to.
3. `authenticate_api_client` succeeds (the token itself is valid) and `require_permission :read, :stack` passes because the client's `permissions` includes `read:stack` [7](#0-6) .
4. `CCMenuController#stack` resolves stack `B` directly via `Stack.from_param!` [6](#0-5) , bypassing the `current_api_client.stack_id` check that `Api::StacksController` and other endpoints enforce, and the response discloses stack `B`'s build/deploy status [8](#0-7) .
