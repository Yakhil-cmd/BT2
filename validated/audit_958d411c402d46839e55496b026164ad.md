### Title
Webhook signature verification is bound to the attacker-supplied `repository.owner.login` field, not the repository the handlers actually act on - allowing forged webhook events for secured orgs when *any* configured org has no `webhook_secret` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which HMAC secret) is used to validate an inbound webhook based on a field taken from the **unverified** JSON body, while the handlers that actually mutate state key off a *different* field from that same unverified body. The value used to choose the verification secret and the value used to decide what gets written are never cross-checked, so the "organization that authenticated" and the "repository that is written" bindings can diverge.

### Finding Description
`verify_signature` picks the `Shipit.github(organization:)` instance to verify against using `repository_owner`, which is read straight out of the JSON payload *before* any signature is verified: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`GithubApp#verify_webhook_signature` unconditionally trusts the request if the selected app has no `webhook_secret` configured: [3](#0-2) 

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```

The `webhook_secret` is explicitly documented as **optional** per GitHub App/organization: [4](#0-3) 

and multi-organization deployments with heterogeneous secrets (one org with a secret, one org without) are an officially supported, tested configuration: [5](#0-4) 

Once `head(422)` is skipped (verification returns `true`), `create` parses the same unverified body and dispatches it to handlers keyed by the `X-Github-Event` header and by whatever repository/commit identifiers the payload itself contains (e.g. `repository.full_name`, `sha`, `after`) - not by `repository_owner`: [6](#0-5) [7](#0-6) 

Because `repository_owner` (used only to *choose the verification key*) and the fields the handlers act on (`repository.full_name`, `sha`, etc., used to *select the Stack/Commit that gets written*) come from the same untrusted JSON but are never reconciled, an attacker can craft a payload where `repository.owner.login` names an organization/app configured with no `webhook_secret` (satisfying `verify_signature` trivially), while `repository.full_name` / commit `sha` reference a Stack belonging to a *different*, secured organization. The webhook handlers (e.g. the `status` handler, which creates a `Status` record for an arbitrary commit `sha` scoped only by `repository.full_name`) will process the payload as if it were an authentic, signed event for that other, secured stack.

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" binding: verification authenticates the request against org A's key, but the write happens against org B's repository/stack. Depending on which webhook handler fires, this allows an unauthenticated party to:
- inject a fabricated `success` commit status onto a targeted stack's commit, which — combined with `continuous_deployment`/`merge_queue_enabled` — can cause an unauthorized deploy or unauthorized PR merge without real CI passing, and
- trigger `GithubSyncJob`/other handlers against a stack they do not control the underlying repository for.

This matches the required Critical/High impact bar ("an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Exploitability is conditional: it requires the Shipit deployment to be configured with at least one GitHub App/organization that has no `webhook_secret` set (an explicitly supported and documented configuration, as shown by the test fixtures), and another organization/stack whose repository the attacker wants to target. Given `webhook_secret` is described in the setup docs as "(optional)", real-world multi-tenant Shipit instances plausibly include at least one such org, making the precondition realistic without requiring any credential, token, or repository write access from the attacker.

### Recommendation
Do not use an attacker-supplied field to select the verification key independently from the field(s) the handlers act on. Concretely:
- Require `verify_signature` to succeed against the app entry matching the request's *installation*, and additionally validate that `repository.full_name`'s owner matches the same organization used for verification (reject if they differ) before dispatching to handlers.
- Alternatively, require every configured GitHub App to have a non-blank `webhook_secret`, removing the "no-secret" bypass path entirely, and fail closed (`head(422)`) rather than optionally trusting unsigned payloads.

### Proof of Concept
1. Deploy Shipit with two organizations configured (as in `test/dummy/config/secrets_double_github_app.yml`): `OrgOne` with a `webhook_secret`, `OrgTwo` with none.
2. Send `POST /webhooks` with `X-Github-Event: status` and a JSON body:
```json
{
  "repository": { "owner": { "login": "OrgTwo" }, "full_name": "OrgOne/secured-repo" },
  "sha": "<commit sha belonging to an OrgOne-owned stack>",
  "state": "success",
  "context": "ci/required-check"
}
```
No `X-Hub-Signature` header (or any arbitrary value) is required.
3. `repository_owner` resolves to `OrgTwo`; `Shipit.github(organization: 'OrgTwo')` has no `webhook_secret`, so `verify_webhook_signature` returns `true` and the request is not rejected.
4. `create` dispatches the `status` handler, which looks up the commit by `sha` under `OrgOne/secured-repo` and records a forged `success` status for it, independent of `OrgTwo` ever being involved with that repository.

I could not fully trace the internal implementation of `Shipit::Webhooks::Handlers::StatusHandler` or `Shipit.github`'s organization-lookup logic (`lib/shipit.rb`) within the indexed context, so the exact commit-lookup/scoping mechanics of the `status` handler should be re-verified directly in the repository before treating this PoC as final.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
```
