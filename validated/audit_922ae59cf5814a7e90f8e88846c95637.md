### Title
Webhook signature verification selects the HMAC secret from an attacker-controlled `organization`/`repository.owner.login` field that is never bound to the `repository.full_name` the handler actually mutates - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` derives *which organization's* webhook secret to validate a signature with from an unauthenticated field inside the JSON body itself, then processes the same body's `repository.full_name` to decide *which stack/repository* gets written to. The two values are never cross-checked, so satisfying signature verification for organization "A" does not guarantee the payload actually pertains to organization "A" — the handler can be made to write to a stack belonging to a completely different, unrelated organization "B".

### Finding Description
`verify_signature` picks the verifying `GitHubApp` using data taken straight out of the still-unverified request body: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up per-organization GitHub App configuration (webhook secret, oauth, etc.) keyed by that same attacker-supplied string, which is a supported, documented multi-tenant configuration (see `test/dummy/config/secrets_double_github_app.yml`): [3](#0-2) 

`GitHubApp#verify_webhook_signature` treats a missing/unset `webhook_secret` as automatically valid: [4](#0-3) 

This is a documented, optional setting (`webhook_secret` "if you've set a webhook secret..."), so some configured organizations in a multi-org deployment can legitimately have no secret at all.

Once `verify_signature` passes (either because the named organization has no secret, or because the attacker knows *that particular* organization's secret), `create` dispatches the exact same raw JSON body to event handlers: [5](#0-4) 

Handlers resolve the target stack from a *different* field of the payload — `repository.full_name` — with no relationship enforced back to the `repository.owner.login` (or `organization.login`) value that was used to pick the verifying secret: [6](#0-5) [7](#0-6) 

The status handler is even more direct: it creates a `Status` record for an arbitrary commit sha straight from the payload, as shown by the existing test suite (`:state create a Status for the specific commit`): [8](#0-7) 

**Broken binding (equality that should hold but doesn't):**
`organization whose secret authenticated the HTTP request` == `organization/repository whose stack is mutated by the handler`

Before the fix: attacker crafts a JSON body where `repository.owner.login` (or top-level `organization.login`) = "OrgA" (an organization configured in Shipit with no webhook secret, or one whose secret the attacker knows), while `repository.full_name` = "OrgB/victim-repo" (a completely different, security-sensitive organization/stack). `verify_signature` authenticates the request against OrgA's config (trivially, since OrgA has no secret or a known secret) and lets the request through. `PushHandler`/`StatusHandler`/etc. then act on OrgB's stack using `repository.full_name`, which was never covered by the authentication decision made for OrgA.

After a correct fix, the organization used to select the verifying secret would be re-derived from (and asserted equal to) the organization actually referenced by `repository.full_name`/`organization.login` used inside the handlers, so a payload cannot claim to be from OrgA while writing to OrgB.

### Impact Explanation
This allows cross-organization/cross-repository writes without possessing the target organization's credentials: an attacker only needs to satisfy verification for *any* one organization configured in the Shipit instance (trivial if that organization has no `webhook_secret` configured, which is an explicitly supported, documented configuration) to inject forged `status`, `push`, `check_suite`, or `membership` events that mutate stacks/commits/teams belonging to an entirely different, properly-secured organization. Forged `status` events can mark a victim commit's CI as green, which can influence merge-queue and deploy readiness decisions for that stack — an unauthorized-deploy-class impact.

### Likelihood Explanation
This is only exploitable in installations that use the multi-organization GitHub App configuration schema (`secrets.github` keyed by organization name, as documented and exercised by `secrets_double_github_app.yml`), and requires at least one configured organization to either have no `webhook_secret` set or one whose secret has otherwise been obtained. Given `webhook_secret` is explicitly optional per the setup documentation, this is a realistic misconfiguration rather than a purely theoretical one, and requires no Shipit session, API token, or privileged account — only the ability to POST to the public webhook endpoint.

### Recommendation
Bind the organization used to select the verifying webhook secret to the organization actually acted upon by the handler: after determining `repository_owner`, re-validate that every entity the dispatched handler will mutate (`repository.full_name`'s owner, `organization.login` for membership events, etc.) belongs to that same verified organization before processing, and reject the event otherwise. Additionally, consider making `webhook_secret` mandatory (removing the `return true unless webhook_secret` bypass in `GitHubApp#verify_webhook_signature`) so an unset secret cannot silently disable authentication for an entire organization.

### Proof of Concept
1. Deploy Shipit with the multi-org GitHub App configuration schema (`secrets.github` containing e.g. `OrgA` with no `webhook_secret` and `OrgB` fully configured and in production use), per `test/dummy/config/secrets_double_github_app.yml`.
2. POST to `/webhooks` with header `X-Github-Event: status` and any/no `X-Hub-Signature`, and a JSON body:
```json
{
  "sha": "<victim-commit-sha-in-OrgB-stack>",
  "state": "success",
  "context": "ci/required-check",
  "organization": { "login": "OrgA" },
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
3. `verify_signature` resolves `Shipit.github(organization: "OrgA")`, whose `webhook_secret` is unset, so `verify_webhook_signature` returns `true` regardless of the signature header — see [4](#0-3)  and [9](#0-8) .
4. The `status` handler processes the same body and creates/updates a `Status` for the sha under `OrgB/victim-repo`'s stack (per the equivalent behavior verified in `test/controllers/webhooks_controller_test.rb` lines 42-59), even though the request was never authenticated as originating from `OrgB`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
```
