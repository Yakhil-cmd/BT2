Confirmed exploit chain: `StatusHandler#process` in `app/models/shipit/webhooks/handlers/status_handler.rb` matches commits by `sha` alone with no repository/organization scoping, and `Commit.create_status_from_github!` triggers `Status` creation which fires `schedule_continuous_delivery` -> can enqueue an actual deploy on a stack whose commit SHA happens to match.

### Title
Webhook signature verified against attacker-controlled organization, but status/state written to any repository's commit by SHA alone, enabling forged CI status and unauthorized deploy trigger - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to use for HMAC verification based on attacker-supplied payload fields (`repository.owner.login` / `organization.login`), while several webhook handlers (most notably `StatusHandler`) act on data using different, independently attacker-controlled fields (`sha`, `repository.full_name`) with no cross-check that they belong to the organization whose secret was used to sign the request.

### Finding Description
`verify_signature` in [1](#0-0)  computes `repository_owner` from the payload itself (`params.dig('repository','owner','login') || params.dig('organization','login')`, see [2](#0-1) ) and uses it to pick which `Shipit.github(organization:)` app config (and thus which `webhook_secret`) to verify the HMAC signature against, per `GithubApp#verify_webhook_signature` in [3](#0-2) . Shipit supports multiple independently configured GitHub Apps/organizations, each with its own `webhook_secret` (see `docs/setup.md` "Using Multiple Github Applications").

Once the signature check passes, the payload is dispatched to handlers, e.g. `StatusHandler`: [4](#0-3) 
This looks up commits **globally by `sha`** — `Commit.where(sha: params.sha)` — with no filter on `repository.full_name`, `repository.owner`, or the organization that was actually used to verify the signature. `create_status_from_github!` creates a `Status` record, which in turn calls `schedule_continuous_delivery` ( [5](#0-4) ), which can enqueue a real deploy for any stack whose commit shares that SHA, per the continuous-deployment trigger logic in `Commit`/`Stack#trigger_continuous_delivery` ( [6](#0-5) ).

The equality that should hold but doesn't:
`organization used to verify signature == organization that owns the repository/commit acted upon`

If Shipit is configured with multiple GitHub organizations (each independently administered, each with its own `webhook_secret` known to that org's own administrators), an attacker who legitimately administers their **own** small/throwaway organization "attacker-org" (with their own valid `webhook_secret`) can:
1. Correctly sign a webhook payload using their own org's `webhook_secret` so `verify_signature` passes (`repository.owner.login` = `"attacker-org"`).
2. Set the `sha` field (for `status` events) or `repository.full_name` (for `push`/`pull_request` events, see `Handler#repository_name` at [7](#0-6)  and consumers like `PushHandler` at [8](#0-7) ) to reference a **victim** stack/commit entirely unrelated to their own organization.
3. Because none of the handlers re-validate that the acted-upon repository/commit belongs to the same organization whose secret verified the request, the forged status is accepted and applied to the victim commit.

### Impact Explanation
This crosses the "authenticated organization vs. repository actually written" trust boundary explicitly in scope. Concretely, an attacker with only their own (attacker-controlled) GitHub organization credentials — no access to the victim repository, no Shipit session, no API token — can inject a fabricated `success` CI status onto an arbitrary victim commit tracked by Shipit. If that stack has `continuous_deployment: true`, this directly triggers an **unauthorized deploy** (`Status#schedule_continuous_delivery` → `Commit#schedule_continuous_delivery` → `ContinuousDeliveryJob` → `Stack#trigger_continuous_delivery` → `trigger_deploy`), bypassing the real CI/status checks the target org relies on. This satisfies the Critical bar "unauthorized deploy."

### Likelihood Explanation
Requires: (a) the Shipit instance configured for multiple GitHub organizations (documented supported configuration), and (b) the attacker controls at least one of those configured organizations (a low bar — GitHub Apps/orgs are freely creatable, and Shipit's model does not distinguish "trusted" vs "less-trusted" configured orgs). No repository write access, Shipit session, or API token is required — only the ability to send an HTTP POST with a validly-HMAC'd body using a webhook secret the attacker legitimately possesses for their own org. This is a realistic, low-effort attack for any Shipit deployment onboarding multiple orgs/customers.

### Recommendation
After signature verification, re-derive and enforce that the organization associated with the payload's `repository.full_name` (via `Repository.from_github_repo_name`) matches the organization whose `webhook_secret` was used to verify the signature (`repository_owner` in `WebhooksController`). Reject the webhook (422) if they diverge. Apply this check centrally, e.g. in `WebhooksController#create` or in `Handler#stacks`, rather than per-handler.

### Proof of Concept
1. Configure Shipit with two organizations, `victim-org` (secret unknown to attacker) and `attacker-org` (secret known to attacker, e.g. because the attacker created and installed their own GitHub App/organization).
2. Attacker crafts a `status` event JSON body:
```json
{
  "sha": "<sha-of-a-victim-org-commit-tracked-by-shipit>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" } }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac(attacker-org's webhook_secret, body)>` and POSTs to `/github/webhooks`.
4. `verify_signature` resolves `Shipit.github(organization: 'attacker-org')`, verifies successfully with the attacker's own secret.
5. `StatusHandler#process` finds the victim's `Commit` purely by `sha` (no org check) and creates a `success` `Status`, which — if the victim stack has continuous deployment enabled — triggers an unauthorized deploy.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
