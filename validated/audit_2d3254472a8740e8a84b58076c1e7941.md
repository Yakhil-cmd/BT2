This maps well to the Notional/Aura report — the pattern is: a *technically valid* token/asset variant slips past a filter meant for the "normal" case, so it can be accepted into a contract's balance but never programmatically forwarded out again, permanently stranding it.

### Title
AA payment messages silently drop fixed-denomination (indivisible) assets, permanently stranding received funds - (File: aa_composer.js)

### Summary
When an Autonomous Agent (AA) composes its response messages, `completePaymentPayload()`/`sendUnit()` in `aa_composer.js` explicitly skips constructing inputs/outputs for any asset whose definition has `fixed_denominations: true` (indivisible assets), and later filters out the entire payment message for that asset from the outgoing unit. However, the AA freely accepts such assets as trigger payments and credits them to its balance in `updateInitialAABalances()`. This mirrors the Notional/Aura issue: a token variant (stash AURA) is a valid, receivable reward, but a downstream filter (`_isInvalidRewardToken()`) rejects it from the only code path that could move it back out, permanently trapping the funds.

### Finding Description
`getTrigger()` accepts payments of any asset type into `trigger.outputs`, with no restriction on `fixed_denominations`: [1](#0-0) 

`updateInitialAABalances()` then unconditionally credits this asset to the AA's `aa_balances` entry, treating it the same as any divisible asset: [2](#0-1) 

But when the AA later tries to compose a payment message that spends this same asset (e.g. to forward it, reinvest it, or pay it back to a user), `sendUnit()` explicitly bails out of building that payment's inputs/outputs: [3](#0-2) 

and a second pass removes any remaining payment message that references a `fixed_denominations` asset from the final message list entirely: [4](#0-3) 

The root cause is that `completePaymentPayload()` builds outputs using an arithmetic `amount` (computed by AA formula logic, picking whatever unspent inputs sum to the target) which is fundamentally incompatible with fixed-denomination/indivisible assets, whose inputs/outputs must match specific denomination values, not arbitrary computed amounts. Rather than surface an error to the AA author (bounce) so the trigger and its funds are rejected/refunded, the code silently drops only that one payment message and proceeds with the rest of the response, permanently leaving the credited balance for that asset in the AA with no code path capable of spending it back out via ordinary `amount`-based payment logic.

### Impact Explanation
Any legitimate AA that accepts arbitrary/attacker-chosen assets as payment (a common oscript pattern, e.g., "accept any asset the user sends and forward/exchange it") will silently and permanently strand any fixed-denomination asset sent to it. The AA continues operating normally (no revert, no bounce), giving the illusion of success while the received funds become permanently unspendable by ordinary payment-message logic, since the composer always filters out that asset's payment. This is a fund-freezing bug reachable by any unprivileged user simply posting a payment of a fixed-denomination asset to a vulnerable AA.

### Likelihood Explanation
High likelihood: fixed-denomination (indivisible) assets are a standard, protocol-supported asset type in ocore (governed by the `asset` message's `fixed_denominations` field), and AAs that generically process `trigger.output[[asset!=base]]` to forward/exchange arbitrary assets are common in oscript examples (see `test/samples/bouncer_infinite_cycle.oscript`, `a_bank_without_percent.oscript`, etc.). Any user (not privileged) can trigger the condition simply by paying such an asset into the AA. No special conditions or race are required.

### Recommendation
When composing a payment message whose asset has `fixed_denominations: true`, `sendUnit()` should not silently drop the message; it should either: (1) bounce the trigger so the whole unit (including the received fixed-denomination asset) is refunded to the sender, or (2) support constructing denomination-based inputs/outputs for that asset type so it can actually be forwarded/spent. Silently filtering the message out while still crediting/keeping the balance should be disallowed.

### Proof of Concept
1. Deploy an AA whose messages include generic logic like: "on receiving any asset X, credit balance and later send it back to the sender" (pattern seen in `test/samples/bouncer_infinite_cycle.oscript`).
2. Define an asset with `fixed_denominations: true` (an indivisible/denominated asset).
3. Send a trigger unit paying this asset to the AA. `getTrigger()`/`updateInitialAABalances()` accept it and credit `aa_balances`. [5](#0-4) 
4. The AA's payment message intended to forward this asset back is silently filtered out during `sendUnit()`: [6](#0-5) [7](#0-6) 
5. The response unit succeeds (no bounce), but the fixed-denomination asset balance remains in `aa_balances` for that AA address forever, with no path in `sendUnit()` capable of spending it out again.
