### Title
Untyped/domain-unbound data signing in `signed_message`/`is_valid_signed_package` enables cross-order and cross-network signature reuse - (File: object_hash.js / signed_message.js / formula/evaluation.js)

### Summary
`getSignedPackageHashToSign()` in `object_hash.js` hashes an application-defined "signed_message" package without any built-in type tag, contract/AA-address domain separator, or chain/network identifier. The same generic signing/verification primitive (`signed_message.js:validateSignedMessage`, exposed to oscript via `is_valid_signed_package`) is used by arbitrary AAs to authenticate off-chain user data (e.g., trade orders), exactly mirroring the Rigor "untyped data signing" bug class: signatures are portable across any consumer that accepts the same generic envelope shape, because the hash preimage is only the raw fields the application chose to put in `signed_message`, with no mandatory binding to the specific AA, purpose, or network.

### Finding Description
`getSignedPackageHashToSign` [1](#0-0)  computes `sha256(getSourceString(unsignedPackage))` over exactly the fields the application supplied (`signed_message`, `authors`, optional `last_ball_unit`/`timestamp`/`version`). There is no fixed type-hash, no AA/contract address, and (when `last_ball_unit` is absent, i.e. not network-aware) no binding to any specific chain/network state at all, as seen in `signed_message.js:validateSignedMessage`, which explicitly supports both a network-aware and a network-agnostic mode [2](#0-1) .

This primitive is exposed to oscript authors through `is_valid_signed_package(trigger.data.orderX, address)`, used verbatim in the sample AA `order_book_exchange.oscript` to authenticate off-chain-signed trade orders [3](#0-2) . The AA derives its own replay-protection id from a handful of order fields (`sha256($order1.address || sell_asset || buy_asset || sell_amount || price || last_ball_unit)`), but this de-duplication key is entirely application-chosen and not part of what `getSignedPackageHashToSign` binds. Nothing in the core signing primitive forces:
- inclusion of the consuming AA's own address (no domain separator), so the exact same signed package format can be presented to a different AA that also calls `is_valid_signed_package` with a matching schema and be accepted there too;
- inclusion of a mandatory nonce/expiry, leaving replay protection fully delegated to each AA author, who may omit or mis-implement it (unlike the executed/`amount_left` bookkeeping in this specific sample, many/most AAs consuming signed data will not derive as careful a dedup key);
- a chain/network identifier binding the signature to one ocore-based network. `ocore` is the shared codebase behind many independently deployed networks (Obyte mainnet, testnet, and third-party forks); the same seed/private key on two such networks produces the same address, and a `signed_message` package produced for one network is valid on any other network's AA that accepts the same schema, exactly like Rigor's cross-chain replay scenario.

This is the same root cause pattern as the Rigor finding: a generic "hash whatever fields are given, sign the hash" utility reused across multiple unrelated application contexts, with the burden of domain separation shifted entirely onto the (arbitrarily many, security-naive) AA authors rather than being enforced by the core primitive.

### Impact Explanation
Because `is_valid_signed_package`/`getSignedPackageHashToSign` provide no automatic binding to the consuming AA, an off-chain signature authored by a user for one AA (e.g., a trade order, price quote, or authorization intended for AA X) can be replayed as trigger data against any other AA Y that happens to call `is_valid_signed_package` on a structurally compatible payload. If AA Y's oscript does not independently reconstruct the exact same strict dedup/expiry/domain checks that AA X's author implemented (a reasonable expectation given each AA is written independently and the core API gives no help here), a malicious AA trigger sender can reuse someone else's signed order/quote to drain balances, mis-price trades, or otherwise cause fund loss/freezing in AA Y — a concrete AA fund-loss scenario reachable by any unprivileged trigger sender who has observed a previously broadcast signed package (trigger data is public on-chain).

### Likelihood Explanation
Exploitability is entirely conditional on how individual AA authors use `is_valid_signed_package`: it requires two (or more) deployed AAs that accept compatible signed-package schemas and at least one of them failing to add its own address/nonce/expiry binding inside the signed payload — a plausible but not universal condition. The core-protocol root cause (missing domain separator/type-hash/chain-id in `getSignedPackageHashToSign`) is unconditionally present and verifiable by code inspection; likelihood of a working exploit against a specific pair of AAs is Medium, contingent on ecosystem AA design, while the underlying design flaw itself is High-confidence.

### Recommendation
Extend `getSignedPackageHashToSign` (and the `signed_message` schema validated in `signed_message.js`) to mandatorily include a domain separator analogous to EIP-712: require the payload to carry (and the hash to bind) a `purpose`/`type` tag and, where used to authenticate to a specific AA, the target AA's address, plus a network/genesis identifier. Update `is_valid_signed_package` in `formula/evaluation.js` to accept an optional required-domain argument (e.g., `is_valid_signed_package(pkg, address, domain)`) that is checked against a field baked into the hashed package, so that replay across AAs/networks fails by default rather than relying on every AA author to reimplement bespoke dedup logic correctly.

### Proof of Concept
1. AA `Orders` accepts trigger data `{order: {signed_message: {sell_asset, buy_asset, sell_amount, price}, authors: [...], last_ball_unit}}` and validates it with `is_valid_signed_package(trigger.data.order, address)` per `object_hash.js:97-103` / `signed_message.js:117-303`.
2. A user signs such a package once via `wallet.js:signMessage` → `signed_message.js:signMessage`, producing `objUnit` with `authentifiers` over `objectHash.getSignedPackageHashToSign(objUnit)` [4](#0-3) .
3. A second, independently authored AA `Orders2` (or the same AA deployed on a different ocore-based network sharing the user's address) also validates trigger data with `is_valid_signed_package(trigger.data.order, address)` but does not reconstruct the exact dedup key `Orders` used.
4. The attacker submits the identical previously-observed signed package as trigger data to `Orders2`; `is_valid_signed_package` succeeds because the hash/signature only ever covered the generic fields, never `Orders2`'s own address or a network id, allowing the order to be replayed/executed against balances it was never intended for.

function getSignedPackageHashToSign(signedPackage) {
	var unsignedPackage = _.cloneDeep(signedPackage);
	for (var i=0; i<unsignedPackage.authors.length; i++)

	var sourceString = (typeof signedPackage.version === 'undefined' || signedPackage.version === constants.versionWithoutTimestamp) ? getSourceString(unsignedPackage) : getJsonSourceString(unsignedPackage);
	return crypto.createHash("sha256").update(sourceString, "utf8").digest();
}
