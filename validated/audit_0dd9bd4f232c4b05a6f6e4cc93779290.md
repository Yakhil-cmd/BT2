### Title
`OpenedHandler#provision?` operator-precedence bug bypasses `review_stacks_enabled: false` for `allow_with_label`/`prevent_with_label` repos - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::PullRequest::OpenedHandler#provision?` combines `repository.review_stacks_enabled` and the three `provisioning_behavior` predicates with `&&`/`||` without parentheses, so `review_stacks_enabled` only gates the `allow_all` branch, not `allow_with_label` or `prevent_with_label`. The settings UI presents `review_stacks_enabled` as the master on/off switch with `provisioning_behavior` as a subordinate refinement, giving operators no indication that the behavior select remains active even when the checkbox is unchecked, which is exactly the mismatch the code produces.

### Finding Description
The intended binding, as implied by the settings page, is: `review_stacks_enabled == false` ⇒ no stack is ever provisioned for any pull request, regardless of `provisioning_behavior`. The label at [1](#0-0)  calls the checkbox "Dynamically provision stacks for Pull Requests?" and the behavior select immediately below it [2](#0-1)  is described only in terms of which PRs get provisioned "when" a given behavior is selected, with no mention that it functions independently of the checkbox, and no conditional disabling/hiding of the select tied to the checkbox state.

The actual code does not honor that contract:

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
``` [3](#0-2) 

Because `&&` binds tighter than `||` in Ruby, this parses as:

`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`

`review_stacks_enabled` is therefore ANDed only with the `allow_all?` term. When `provisioning_behavior` is `allow_with_label` (or `prevent_with_label`), the enum guarantees `allow_all?` is `false` [4](#0-3) , so the first disjunct is always `false` and `review_stacks_enabled` has no effect at all on the outcome — only the label-based term controls it.

Exploit flow: an operator sets `review_stacks_enabled: false` and `provisioning_behavior: allow_with_label` intending review stacks to be completely off. Any unprivileged GitHub user who can open a pull request against the tracked repository and apply/carry the configured `provisioning_label_name` (or, for `prevent_with_label`, simply omit it) triggers the `opened` webhook. `respond_to_pull_request_opened?` calls `provision?` [5](#0-4) , which evaluates true due to the precedence bug, and `ReviewStackAdapter#find_or_create!` creates a `ReviewStack` and enqueues it for provisioning [6](#0-5) , which will invoke `stack.provisioner.up` once the provisioning queue processes it [7](#0-6) .

No existing guard prevents this: webhook signature verification only authenticates that the event genuinely came from GitHub for that repository (which it does — the attacker's own PR triggers a real, correctly-signed webhook), it does not enforce the intended provisioning policy. The `ExplicitParameters` schema on `OpenedHandler` only validates payload shape, not authorization semantics. The bug is purely a logic/precedence defect in `provision?`.

### Impact Explanation
Any external contributor able to open a PR (and control its labels) against a repository the operator explicitly configured to have review-stack provisioning **off** (`review_stacks_enabled: false`) can still cause Shipit to create a `Shipit::ReviewStack` record and drive it through the provisioning state machine, invoking `provisioner.up` for that stack/environment. This is an authorization bypass: a resource the operator disabled is exercised anyway, for a repository whose owner did not consent to automatic provisioning for arbitrary contributors. It is repeatable per-PR/per-relabel and applies to every repository configured with `allow_with_label` or `prevent_with_label` while `review_stacks_enabled` is false, i.e., every repo operator who tried to use the "off by default, opt in via label" pattern that the settings page implies is possible.

### Likelihood Explanation
Preconditions: a repository must be tracked by Shipit with review stacks integration configured, `provisioning_behavior` set to `allow_with_label` or `prevent_with_label`, and `review_stacks_enabled` left/set to `false`. No secrets, sessions, or special GitHub permissions are needed by the attacker beyond the ability to open a PR (and, for `allow_with_label`, apply a label they can typically set themselves via GitHub's default "anyone can label their own PR" or maintainer-open-label policies, or trivially satisfy `prevent_with_label` by doing nothing). This is a straightforward, deterministic, always-reproducible logic bug, not a race condition or timing issue.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates the entire expression:

```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Also verify `LabeledHandler`/`UnlabeledHandler`/`ReopenedHandler` equivalents are not similarly affected (the `LabeledHandler#respond_to_label_change?` reviewed here already correctly ANDs `review_stacks_enabled` across the whole condition [8](#0-7) , but `ReopenedHandler` was not inspected in this session and should be checked for the same precedence pattern).

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`), asserting the binding `review_stacks_enabled == false ⇒ no stack created`:

```ruby
test "does NOT create a stack when review_stacks_enabled is false, even with allow_with_label + matching label" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,   # operator believes this fully disables provisioning
    behavior: :allow_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Given the current implementation, this assertion fails: a stack IS created (`Shipit::Stack.count` changes by 1), proving `provision?` returns `true` despite `review_stacks_enabled == false`, contradicting the settings page's stated contract at [1](#0-0) .
