### Title
Missing `return` after malformed-payload catch causes the async iterator callback to fire twice in `handleSavedPrivatePayments` - ([File: network.js])

### Summary
`network.js`'s `handleSavedPrivatePayments()` processes queued private-payment chains that were received from a peer or the hub. Inside `validateAndSave()`, when computing the hash of the head private element's payload throws, the `catch` block reports the error and calls `deleteHandledPrivateChain(..., cb)`, but execution does **not** stop there — the function falls through to compute `key` (using the now-`undefined` `json_payload_hash`) and unconditionally calls `privatePayment.validateAndSavePrivatePaymentChain(...)`, whose callbacks (`ifOk`/`ifError`/`ifWaitingForChain`) each also call `cb()`. This mirrors the CVE-2026-46027 bug class: a message/chain that is still in an "early/invalid" state (payload could not even be hashed) is nevertheless allowed to fall through into code paths that assume the state has been fully established, resulting in the shared per-item completion callback being invoked more than once. [1](#0-0) 

### Finding Description
`handleSavedPrivatePayments(unit)` reads rows from `unhandled_private_payments` and processes each one in `async.each(rows, function(row, cb){...}, finalCb)`. Each row is a private-payment chain that was queued earlier by `handleOnlinePrivatePayment()` — reachable by any private-payment counterparty (a peer/hub correspondent sending a `private_payment` justsaying or `private_payments` device message) without any privileged access. [2](#0-1) 

Inside `validateAndSave()`:
```
try {
    var json_payload_hash = objectHash.getBase64Hash(objHeadPrivateElement.payload, true);
}
catch (e) {
    console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
    if (ws)

    deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);   // calls cb() eventually
}
var key = 'private_payment_validated-'+objHeadPrivateElement.unit+'-'+json_payload_hash+'-'+row.output_index;
privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {
    ifOk: function(){ ...; deleteHandledPrivateChain(..., cb); ... },
    ifError: function(error){ ...; deleteHandledPrivateChain(..., cb); },
    ifWaitingForChain: function(){ ...; cb(); }
});
``` [1](#0-0) 

There is no `return` (nor an `else`) after the `catch` block, so once `objectHash.getBase64Hash()` throws, the function still proceeds to call `privatePayment.validateAndSavePrivatePaymentChain()` on the very same `arrPrivateElements`, whose payload is already known to be un-hashable/malformed. Any of the callbacks passed to that function (`ifOk`, `ifError`, `ifWaitingForChain`) will call `cb` again — i.e., the `async.each` iteratee callback `cb` for this row is invoked twice. Calling an `async` iteratee callback more than once is explicitly documented by `async` as producing undefined/erroneous behavior (the library throws or silently corrupts control flow depending on version), and in this codebase `cb` may also be the callback passed into `deleteHandledPrivateChain`, so `deleteHandledPrivateChain` and DB deletion logic execute twice concurrently on the same row.

A single unprivileged private-payment counterparty (or a wallet forwarding textcoin/private chains to itself) can trigger this at will: any payload for which `objectHash.getBase64Hash()` throws (e.g., a payload deliberately shaped to contain a value the hashing routine cannot serialize/hash, or that violates the hashing library's structural assumptions) causes the double-callback condition every time that row is (re)processed by `handleSavedPrivatePayments`, which is periodically re-invoked (e.g. from `eventBus` triggers and from `handleOnlinePrivatePayment`'s `ifNew`/`ifKnownUnverified` paths) for every unhandled private payment still queued in the DB.

### Impact Explanation
Calling the shared `async.each` completion callback twice for the same item is a serious control-flow-integrity bug in Node.js: it can throw an uncaught exception ("Callback was already called") depending on the async library version/usage, corrupt the `assocNewUnits` bookkeeping, or cause the surrounding `mutex.lock(["saved_private"], ...)` to be released/relocked incorrectly (double `unlock`/`cb` interleavings), and it also causes duplicate DELETE queries against `unhandled_private_payments`. In the worst case this can crash the wallet/light-node process handling private payments (an availability impact, matching the CVSS A:H characteristic of the source CVE) or leave the mutex-protected `saved_private` critical section in an inconsistent state, blocking further processing of legitimately queued private payments network-wide for that node. This is reachable purely from an unprivileged private-payment counterparty crafting a malformed payload — no elevated trust is required.

### Likelihood Explanation
High. Any counterparty in a private-payment/textcoin exchange controls the content of `arrPrivateElements[...].payload` end-to-end before it is even validated (it is queued in `unhandled_private_payments` before validation succeeds, see `savePrivatePayment()` in `handleOnlinePrivatePayment`), so triggering the `getBase64Hash` throw path is fully attacker-controlled and requires no race condition beyond normal message delivery. [3](#0-2) 

### Recommendation
Add a `return` (or restructure with an `if/else`) immediately after the `deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb)` call inside the `catch` block in `validateAndSave()`, so that once the payload hash computation fails, the function does not fall through to compute `key` or call `privatePayment.validateAndSavePrivatePaymentChain()` again on the same, already-rejected element. This mirrors the upstream kernel fix's approach of guarding state access so it is only reached once the relevant object/step has actually completed successfully.

### Proof of Concept
1. As a private-payment counterparty (or paired device), send (via `handleOnlinePrivatePayment`) a private-payment chain whose head element's `payload` is shaped so that `objectHash.getBase64Hash(payload, true)` throws (e.g., a payload with a field whose JSON/hash serialization the hashing library rejects — the exact trigger depends on `object_hash.js`'s hashing rules, which were not fully inspectable in this pass due to index truncation).
2. Because `arrPrivateElements.length` may be `>1` in light mode or the chain is otherwise queued as `ifNew`/`ifKnownUnverified`, the payload is stored via `savePrivatePayment()` into `unhandled_private_payments` before validation. [4](#0-3) 
3. When `handleSavedPrivatePayments()` next processes this row, `validateAndSave()` hits the `catch` branch, calls `deleteHandledPrivateChain(..., cb)`, and then — due to the missing `return` — falls through and calls `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})`, whose `ifError` (or another) callback invokes `cb` a second time for the same `async.each` item. [1](#0-0) 

Note: I was not able to fully verify the exact byte-for-byte payload shape that makes `objectHash.getBase64Hash` throw, nor the exact runtime behavior of the specific `async` version in use when an iteratee callback is invoked twice, since the full contents of `object_hash.js` and the `async` dependency were not available within the indexed context. A Devin session with full repository/dependency access would be needed to construct and run a concrete PoC and confirm the exact crash/exception behavior.
