### Title
`borrow`/`withdraw` allow an arbitrary `to` recipient without rejecting contract addresses, permanently freezing funds sent to contracts without token logic - (File: contracts/controller/src/positions/mod.rs)

### Summary
The controller's `borrow` and `withdraw` entrypoints accept a user-supplied `to: Option<Address>` recipient. The only sanity check, `require_external_recipient`, rejects the pool and controller addresses but does not reject other contract addresses. On Soroban, a token balance held by a contract address can only be spent by that contract itself invoking `transfer` under its own `require_auth`; a contract that has no token-transfer logic can never move the funds. An account owner or delegate who passes a contract address as `to` permanently locks the borrowed/withdrawn tokens.

### Finding Description
`process_borrow` and `process_withdraw` both resolve `let recipient = to.unwrap_or_else(|| caller.clone())` and then call `require_external_recipient(env, &mut cache, &recipient)` before settlement:

```rust
// contracts/controller/src/positions/mod.rs:36-43
pub(crate) fn require_external_recipient(env: &Env, cache: &mut Context, recipient: &Address) {
    let pool = cache.cached_pool_address();
    assert_with_error!(
        env,
        *recipient != env.current_contract_address() && *recipient != pool,
        FlashLoanError::InvalidFlashloanReceiver
    );
}
``` [1](#0-0) 

The check's documented intent is bookkeeping integrity ("Pool self-transfers debit cash without moving tokens; controller receipts would remain unclaimed by balance-delta accounting"), not recipient safety. Any other contract address passes:

```rust
// contracts/controller/src/positions/debt.rs:45-57
let recipient = to.unwrap_or_else(|| caller.clone());
let mut cache = Context::new(env);
require_external_recipient(env, &mut cache, &recipient);
...
settle_borrow(env, &mut account, &recipient, &aggregated, &mut cache);
``` [2](#0-1) 

`settle_borrow` forwards `recipient` to `pool_borrow_call`, and the pool performs `transfer_out(&receiver, ...)` on the token. The same shape exists in `process_withdraw` (contracts/controller/src/positions/supply.rs:140-157), where `settle_withdraw` pays `recipient` directly. [3](#0-2) 

Neither `require_owner_or_delegate` nor any downstream code restricts `to` to the caller, the account owner, or a non-contract address. This is the direct analog of the reported `L2ECOBridge.withdrawTo()` bug class: a funds-out entrypoint with a caller-controlled destination and no contract-recipient guard.

### Impact Explanation
Permanent freezing of user funds. A Stellar token contract records balances per `Address`; spending from a contract address requires that contract to authorize a `transfer` invocation from its own code. Tokens sent to a contract that was not designed to custody and re-emit that token (e.g., the position-NFT contract, the governance contract, an aggregator, or any unrelated contract the user pastes by mistake) are locked forever — there is no recovery path in the controller, pool, or token, and no admin sweep on the lending side. The burn of supply shares / mint of debt shares already occurred, so the user's position is debited while the underlying is unrecoverable.

### Likelihood Explanation
Medium. The vulnerability requires user error (passing a contract address as `to`), but the entrypoint explicitly invites a custom recipient via `to: Option<Address>`, and integrators routing withdrawals through wrapper contracts are a realistic pattern in this codebase's own documentation (contracts/position-nft and the `DataKey::VaultAccount` adapter flow in skills/xoxno-lending-contracts/positions.md). This matches the original report's Medium severity: accidental loss, not exploitable theft, but fully preventable by a cheap check. Note that Soroban does not expose an `is_contract` primitive as cleanly as EVM's `extcodesize`; the practical mitigation is a whitelist or requiring `to` to sign, not a code-size check — see the recommendation.

### Recommendation
Restrict `to` for `borrow` and `withdraw` so funds can only leave to an address that can actually authorize token transfers:

- Extend `require_external_recipient` to additionally reject any address that is a contract — on Soroban this is best approximated by requiring `recipient.require_auth()` (an EOA can always authorize; an arbitrary contract address can only authorize if it explicitly opts in via `require_auth` on its own address, which itself signals the contract intends to receive). Alternatively,
- Constrain `to` to `caller` or `account.owner`, eliminating the arbitrary-recipient foot-gun entirely while preserving the owner/delegate flows.
- At minimum, document and emit a warning path; the check costs nothing relative to the token transfer.

### Proof of Concept
```rust
// Attacker-free, self-inflicted flow — single unprivileged user:
// 1. ALICE owns account_id with USDC supply.
// 2. ALICE calls:
controller.withdraw(
    &alice,
    &account_id,
    &vec![&env, (hub_asset(USDC), 1_000_000_000i128)],
    &Some(position_nft_contract_address.clone()), // `to`
);
// 3. require_external_recipient passes: recipient is neither the
//    controller nor the pool.
// 4. Pool burns ALICE's supply shares and transfer_out()s the USDC
//    to the position-NFT contract address.
// 5. The NFT contract has no method that invokes token.transfer with
//    its own auth — the 1,000 USDC is permanently frozen, and ALICE's
//    supply position is already reduced.
```
The identical shape works through `borrow(account_id, borrows, Some(contract_addr))`: the account mints real debt shares while the borrowed principal lands on a contract that can never move it.

pub(crate) fn process_withdraw(
    env: &Env,
    caller: &Address,
    account_id: u64,
    withdrawals: &Vec<HubPayment>,
    to: Option<Address>,
) -> Vec<HubPayment> {
    validation::require_authorized_caller(env, caller);

    let mut account = storage::get_account(env, account_id);
    require_owner_or_delegate(env, account_id, caller, &account.owner);

    let recipient = to.unwrap_or_else(|| caller.clone());
    let mut cache = Context::new(env);
    require_external_recipient(env, &mut cache, &recipient);
    let aggregated = payments::aggregate_payments(env, withdrawals, payments::ZeroLeg::MeansAll);

    let paid = settle_withdraw(env, &mut account, &recipient, &aggregated, &mut cache);
