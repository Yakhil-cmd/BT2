Confirmed: `TaskCommands#env` calls `.merge(@stack.env)` which for a `ReviewStack` invokes `ReviewStack#env`, and this merge happens entirely outside of `EnvironmentVariables#permit`.## Analysis of the Claimed Binding

**Binding claimed:** `EnvironmentVariables.with(env).permit(deploy_variables) == unfiltered_label_env` should hold for every path that injects attacker-influenced keys into the deploy/task process environment. This fails because the label-derived env never passes through `permit`.

## Trace

- `Api::DeploysController`/`DeploysController` route the `env` HTTP param through `Stack#build_deploy` → `filter_deploy_envs(env.to_h)` → `EnvironmentVariables.with(env).permit(deploy_variables)`, which raises `EnvironmentVariables::NotPermitted` for any key not in `deploy_spec.deploy_variables` [1](#0-0) [2](#0-1) [3](#0-2) .
- `Shipit::ReviewStack#env` merges every PR label name (upcased) as a key with value `"true"` directly into the returned hash, with **no call to `EnvironmentVariables#permit`**: [4](#0-3) .
- Labels reach this method via `LabelCapturingHandler#capture_labels`, triggered by GitHub webhook events (`opened`, `labeled`, `unlabeled`, `reopened`) on a PR that has an active, non-archived stack — no repository-maintainer or Shipit privilege is required to label your own PR: [5](#0-4) .
- `TaskCommands#env` (used by both `DeployCommands` and other task commands) does `super.merge(@stack.env)...merge(@task.env)` — the `@stack.env` merge is exactly where the unfiltered, label-derived keys enter the environment eventually passed to `Command`/`PTY.spawn`, entirely bypassing the whitelist check applied to `@task.env`: [6](#0-5) .
- This is confirmed by existing tests showing labels flow through unchecked: [7](#0-6)  and [8](#0-7) , contrasted with the HTTP-path enforcement tests: [9](#0-8)  and [10](#0-9) .

## Important caveat on impact

The label mechanism only lets the attacker choose the **key** (the upcased label name); the **value is hardcoded to `"true"`** by `ReviewStack#env` — the attacker cannot inject an arbitrary value/string. This meaningfully limits (but does not eliminate) exploitability: classic env-based RCE primitives (`LD_PRELOAD`, `BASH_ENV`, `RUBYOPT`, `NODE_OPTIONS`, etc.) require attacker-controlled *values* pointing at attacker-controlled payloads/paths, not merely presence with the literal string `"true"`. With this constraint, most of these vectors fail closed (invalid option/path errors) rather than executing arbitrary code. I could not construct a concrete, demonstrable RCE, secret-exfiltration, or cross-tenant-mutation payload using only attacker-chosen keys fixed to `"true"` — the `Command`/`PTY.spawn` RCE category in the rubric requires a demonstrated payload, and "boolean env var flip" alone doesn't meet that bar without a specific vulnerable downstream tool being named and shown to be reachable from this stack's own `shipit.yml` steps.

That said, the underlying control gap is real and precisely matches the question's framing: the whitelist invariant (`EnvironmentVariables::NotPermitted`) that the HTTP `env` param is subject to is **not** applied to the label-derived keys merged into `Stack#env`/`ReviewStack#env`, even though both reach the same `Command#env`/`PTY.spawn` sink via `TaskCommands#env`.

### Title
Unwhitelisted PR-label-derived keys bypass `EnvironmentVariables#permit` before reaching deploy/task process environment - (File: app/models/shipit/review_stack.rb)

### Summary
`Shipit::ReviewStack#env` merges every PR label name (attacker-controlled, upcased) directly into the stack's environment hash without ever calling `EnvironmentVariables#permit`, unlike the HTTP `env` deploy/rollback param which is strictly whitelisted against `deploy_spec.deploy_variables`/`rollback_variables`. This lets any PR author inject arbitrary-named environment variable keys (fixed value `"true"`) into the same `Command`/`PTY.spawn` environment used for deploys and tasks on their review stack.

### Finding Description
The intended invariant is `EnvironmentVariables.with(env).permit(deploy_variables) == label_derived_env`, enforced consistently for every source of attacker-influenced process environment reaching `Command`. The HTTP path enforces this: `Api::DeploysController`/`DeploysController` → `Stack#build_deploy` → `DeploySpec#filter_deploy_envs` → `EnvironmentVariables#permit`, raising `EnvironmentVariables::NotPermitted` for unknown keys (`app/models/shipit/deploy_spec.rb:174-180`, `lib/shipit/environment_variables.rb:13-18`). The PR-label path does not: `LabelCapturingHandler#capture_labels` (triggered by an unprivileged PR author labeling their own PR) persists `pull_request.labels`, and `ReviewStack#env` merges `label_name.upcase => "true"` for every label directly into the hash returned by `super`, with no whitelist check (`app/models/shipit/review_stack.rb:84-93`). That hash is merged into `TaskCommands#env` via `.merge(@stack.env)` (`lib/shipit/task_commands.rb:33-48`), which feeds `Command#env` and ultimately `PTY.spawn` for every deploy/task step run against the review stack. Root cause: `ReviewStack#env` never routes through `DeploySpec#filter_deploy_envs`/`EnvironmentVariables#permit`, so the whitelist that exists specifically to prevent PR authors from injecting arbitrary process environment variables is bypassed for this identical class of attacker-controlled input.

### Impact Explanation
Any key name of the attacker's choosing is injected into the environment of shell commands executed for their own review stack's deploys/tasks, with the value fixed to the literal string `"true"`. This bypasses the exact whitelist mechanism (`EnvironmentVariables::NotPermitted`) the codebase otherwise enforces for this class of input. The blast radius is scoped to the attacker's own review stack (the labels only affect that stack's `pull_request`), not other tenants' stacks. Because the value is hardcoded to `"true"` rather than attacker-controlled, I could not demonstrate a concrete RCE, secret-exfiltration, or cross-repository-mutation payload meeting the Critical/High bar defined in the rubric — the realistic effect is unauthorized/unfiltered environment key injection (a control-bypass bug) rather than a proven code-execution or credential-exfiltration exploit.

### Likelihood Explanation
Preconditions: `review_stacks_enabled` on the repository, and any PR label name attacker adds to their own PR (cost: opening a PR and applying a label they control, e.g. via a repo they own with review stacks enabled, or any PR they can label). No Shipit session, API token, or GitHub secret is required. The divergence is trivially and repeatably reproducible against the attacker's own review stack.

### Recommendation
Route `ReviewStack#env`'s label-derived hash (and any other stack-level env sources) through the same `DeploySpec#filter_deploy_envs`/`EnvironmentVariables#permit` whitelist used for the HTTP `env` param, so label-derived keys are constrained to `deploy_spec.deploy_variables`/`rollback_variables` (or a dedicated explicit allowlist for label-triggered flags) before being merged into `Stack#env`/`TaskCommands#env`.

### Proof of Concept
```ruby

test "#env bypasses EnvironmentVariables.permit for pull request labels" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["NODE_OPTIONS"]

  # Contrast: the HTTP path enforces the whitelist and rejects this exact key
  assert_raises(Shipit::EnvironmentVariables::NotPermitted) do
    Shipit::EnvironmentVariables.with("NODE_OPTIONS" => "x").permit(stack.deploy_variables)
  end

  assert_equal "true", stack.env["NODE_OPTIONS"]
```

Both sides of the claimed equality diverge: the HTTP-triggered `deploy_params`/`filter_deploy_envs` path raises `NotPermitted` for `NODE_OPTIONS`, while `ReviewStack#env["NODE_OPTIONS"]` succeeds unfiltered and reaches `TaskCommands#env`/`Command#env` for any deploy or task run against that review stack.
