## Title
Multisig transaction payload substitution bypasses owner-approval binding when `abort_if_multisig_payload_mismatch` is not enabled - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

## Summary
`validate_multisig_transaction`, the VM-invoked admission function for multisig transactions, only compares the caller-supplied execution `payload` against the on-chain approved payload when the feature `abort_if_multisig_payload_mismatch_enabled` is turned on. When that feature is off (its default/legacy state for backward compatibility), a transaction created with `create_transaction` (full payload stored on-chain and voted on by owners) can be executed with an entirely different, unapproved payload, because the only enforced check in that code path is skipped.

## Finding Description
`create_transaction` stores the caller-approved payload on-chain in `MultisigTransaction.payload` (with `payload_hash` set to `None`): [1](#0-0) 

Owners vote to approve/reject that specific stored transaction via `vote_transanction`/`approve_transaction`: [2](#0-1) 

At execution time, the VM prologue calls `validate_multisig_transaction(owner, multisig_account, payload)`, where `payload` is supplied fresh by whoever submits the executing transaction (not necessarily re-derived from the stored `MultisigTransaction`). The function contains two independent payload-integrity checks:

1. If `payload_hash` is set (i.e., the transaction was created via `create_transaction_with_hash`), the supplied payload is always hashed and compared: [3](#0-2) 

2. If the full payload was stored on-chain instead (`create_transaction` path, `payload_hash` is `None`), the match is only enforced when the feature flag is enabled:
```
if (features::abort_if_multisig_payload_mismatch_enabled()
    && transaction.payload.is_some()
    && !payload.is_empty()
) {
    let stored_payload = transaction.payload.borrow();
    assert!(payload == *stored_payload, error::invalid_argument(EPAYLOAD_DOES_NOT_MATCH));
}
``` [4](#0-3) 

When this feature is disabled, no comparison at all occurs between the payload that owners approved (`transaction.payload`) and the payload that will actually be executed under the multisig account's signer authority. The quorum, sequence-number, and timelock checks earlier in `validate_multisig_transaction` only validate that *a* transaction at that sequence number achieved sufficient approvals — they never re-bind that approval to the specific bytes being executed in this code path. This breaks the admission invariant that "the executed payload equals the payload the signer set approved," which is the multisig analogue of validating an authenticator/approval set against the correct bound message.

## Impact Explanation
Any address that is one owner of a k-of-n multisig account (or the fee payer/executor submitting the transaction envelope) can cause the multisig account to execute an arbitrary payload of their choosing, as long as *some* transaction at the correct sequence number reached quorum with a stored full payload. Since the multisig signer capability grants full authority of that account, this allows unauthorized state transitions (e.g., arbitrary fund transfers, governance actions, or module calls) under the multisig account's identity — i.e., execution proceeds despite the admission check that is supposed to bind execution to the specific approved payload being effectively a no-op. This matches the "Pre-validation mismatch that causes a transaction which should fail admission to execute and commit" and "wrong approval set" impact categories.

## Likelihood Explanation
Exploitability depends entirely on whether `abort_if_multisig_payload_mismatch_enabled` is active on a given network/version. I was not able to confirm within this investigation whether the feature defaults to enabled or disabled on current mainnet/testnet deployments (this would require checking `aptos-move/framework/move-stdlib/sources/configs/features.move` default feature vector and on-chain `Features` resource state, which I did not get to inspect before running out of budget). If the feature is off by default or not yet enabled on a given chain, the bypass is directly reachable by any multisig owner without any additional privilege. If the feature is already enabled everywhere in practice, this is a legacy/dead code path with reduced real-world exploitability. This uncertainty should be resolved before treating this as confirmed-exploitable in production.

## Recommendation
Remove the feature gate on the payload-mismatch check for `create_transaction`-created (full on-chain payload) transactions, or fail closed by default: always compare `payload == *stored_payload` when `transaction.payload.is_some()`, independent of `abort_if_multisig_payload_mismatch_enabled`. If backward compatibility is a concern, gate the *new, stricter* error message/behavior, but never allow silent skip of payload verification for a stored full payload.

## Proof of Concept
1. Owner A creates a multisig transaction with `create_transaction(owner_A, multisig_addr, payload_benign)` — this transfers a small amount to a known address, and is stored fully on-chain.
2. Owners B, C (up to the k-of-n threshold) call `approve_transaction` on that specific `sequence_number`, believing they are approving `payload_benign`.
3. On the network state where `abort_if_multisig_payload_mismatch_enabled` is disabled, the transaction executor submits an execution transaction referencing the same `multisig_account` and `sequence_number`, but supplies `payload_malicious` (e.g., draining the account) instead of `payload_benign`.
4. `validate_multisig_transaction` passes: quorum check succeeds (approvals were counted against the sequence number, not the payload bytes), `payload_hash` is `None` so check (1) is skipped, and check (2) is skipped because the feature flag is off.
5. The VM executes `payload_malicious` under the multisig account's authority, despite it never having received the required owner approvals.
