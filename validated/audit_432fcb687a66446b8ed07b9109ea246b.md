### Title
Asset definer can unilaterally update the attestor list of a `spender_attested` asset at any time, freezing already-issued/held tokens for arbitrary holders - ([File: validation.js])

### Summary
Similar to the OpenQ finding where a bounty issuer can retroactively change `requireKYC`/`payoutTokenAddress`/schedules after users have already committed to the bounty and block withdrawal of the prize, an ocore asset's `definer_address` (the "issuer" of a `spender_attested` asset) can retroactively edit the asset's attestor list at any point after issuance and distribution, via the `asset_attestors` message. Because payment validation always re-reads the *current, latest* attestor list rather than the list in force when a holder received the asset, the definer can freeze the ability of any existing token holder to move their already-owned tokens, without their consent and with no protection or "lock-in" of terms at receipt time.

### Finding Description
When an asset is created with `spender_attested: true`, `validateAssetDefinition` requires an initial `attestors` list [1](#0-0) . This list is not immutable: the definer can post a new `asset_attestors` message at any later time to replace it, and `validateAttestorListUpdate` only checks that the sender is the original `definer_address`, not that any holder consents or that a grace period has passed: [2](#0-1) 

When any payment (not just issuance) of a `spender_attested` asset is validated, `readAsset`/`loadAssetWithListOfAttestedAuthors` fetch the *latest* attestor list as of `last_ball_mci` (the most recent stable `asset_attestors` unit for that asset), not the list that existed when the payer originally received the tokens: [3](#0-2) 

`validatePayment` then requires that at least one author of the spending unit is attested by that current list, or the payment is rejected outright with "none of the authors is attested": [4](#0-3) 

So a malicious (or simply careless) asset definer can:
1. Issue a `spender_attested` asset with an initial, seemingly reasonable attestor list, inducing users to acquire/hold/transact the asset.
2. Later post a new `asset_attestors` unit that removes all attestors (or replaces them with addresses that will never attest anyone), or an attestor could simply refuse to keep attesting.
3. Any existing holder whose address is not attested under the new list immediately loses the ability to spend/transfer their already-held balance of that asset — their funds become frozen — mirroring the OpenQ bug where the issuer could flip `requireKYC`/`setInvoiceRequired` at will to block withdrawal after user commitment.

This is directly analogous to the reported bug class: a privileged party (issuer/definer) can change contract-level state that other unprivileged parties (holders/spenders) rely on, after those parties have already committed value, with no on-chain lock or timelock protecting them.

### Impact Explanation
Holders of a `spender_attested` asset can have their existing balances frozen at will by the asset definer, at any time, for any or all counterparties, with no recourse. This is a fund-freezing condition reachable by any address that holds units of such an asset — a class of impact explicitly listed as acceptable ("AA fund loss or freezing" analog applied to asset holders relying on a definer-controlled condition).

### Likelihood Explanation
Any asset definer can trigger this merely by posting a single `asset_attestors` message; no special privileges beyond being the original definer are required, and this is a straightforward, always-available capability of the protocol layer (not a hub/network-level or operator-only path). Users interacting with `spender_attested` assets have no way to know or enforce that the attestor list will remain constant, since dynamic list edits are exactly what `asset_attestors` is designed to allow.

### Recommendation
Consider decoupling *spendability of already-received outputs* from the *current* attestor list: e.g., record/snapshot the attestor list (or an attestation valid-as-of MCI) at the time an output is created, and validate spends of that output against the list in force at receipt time (or at least allow a grace/expiry period) rather than always requiring the latest list. Alternatively, document explicitly (and make prominent in wallets) that `spender_attested` assets carry an ongoing freeze risk controlled entirely by the definer, so holders can make an informed risk assessment before acquiring such assets.

### Proof of Concept
1. Definer `D` issues asset `A` with `spender_attested: true` and `attestors: [X]`.
2. User `U` receives a payment output of asset `A` (validated fine, since `X` currently attests `U`).
3. `D` posts an `asset_attestors` message for asset `A` with a new `attestors` list that does not include `X` (or any address willing to attest `U`) — validated by `validateAttestorListUpdate` since `D` is still `definer_address` [5](#0-4) .
4. `U` attempts to spend their asset `A` output. `validatePayment` re-reads the attestor list via `storage.loadAssetWithListOfAttestedAuthors`/`readAsset`, which now returns the new list [6](#0-5) .
5. Since `U`'s address is not attested under the new list, `validatePayment` rejects the spend with "none of the authors is attested" [7](#0-6) , permanently freezing `U`'s previously valid balance.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
