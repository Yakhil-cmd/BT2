### Title
Webhook signature verification uses `repository.owner.login` while all `pull_request` handlers resolve state on `repository.full_name`, letting a payload "authenticated" by one org's (secret-less) config create/mutate a `ReviewStack` on a different org's repository, bypassing `review_stacks_enabled` via the `provision?` precedence bug - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb`, `app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects the `GitHubApp` used to authenticate a webhook using `params.dig('repository','owner','login')`, but every `pull_request` handler resolves the actual `Shipit::Repository` (and therefore the `Stack`/`ReviewStack` it mutates) using `params.repository.full_name`. An attacker who names a no-secret (or unknown-to-them-but-secretless) org in `repository.owner.login` while pointing `repository.full_name` at a victim org's repository can get the signature check to trivially pass and still have the handlers act on the victim repository. Combined with a precedence bug in `OpenedHandler#provision?`, this lets an attacker force-provision a `ReviewStack` even when `review_stacks_enabled` is `false`, after which `LabelCapturingHandler` persists attacker-chosen PR label names as uppercase environment variables via `ReviewStack#env`.

### Finding Description
The broken invariant, stated as an equality that must hold but doesn't:
`org_used_to_verify_signature (params.repository.owner.login)` MUST equal `org_whose_repository_is_mutated (params.repository.full_name.split('/').first)`.

Trace:
- `Shipit::WebhooksController#verify_signature` picks the GitHub App config purely from `repository_owner` (`params.dig('repository','owner','login')`) [1](#0-0) [2](#0-1) .
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when that org has no configured `webhook_secret` [3](#0-2) . An attacker only needs `repository.owner.login` to reference any org whose config has `webhook_secret: nil` (a supported, documented multi-org configuration, see `test/dummy/config/secrets_double_github_app.yml`) — no secret is needed at all.
- Every `pull_request` handler, however, resolves the repository/stack it actually mutates from a completely different field, `params.repository.full_name`: `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [4](#0-3) [5](#0-4) . Nothing cross-checks this against `repository.owner.login`.
- `Shipit::Webhooks.default_handlers['pull_request']` runs `OpenedHandler` before `LabelCapturingHandler` on every `pull_request` event [6](#0-5) .
- `OpenedHandler#provision?` has an operator-precedence bug: `repository.review_stacks_enabled && repository.provisioning_behavior_allow_all? || (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) || (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)` [7](#0-6) . `review_stacks_enabled` only gates the first (`allow_all?`) disjunct; the `allow_with_label` and `prevent_with_label` disjuncts are evaluated independently of `review_stacks_enabled`. So if the target repository's `provisioning_behavior` is `prevent_with_label` and the forged PR lacks the provisioning label, `provision?` is `true` and a `ReviewStack` is created via `ReviewStackAdapter#find_or_create!` even though `review_stacks_enabled` is `false`.
- Once the stack exists, `LabelCapturingHandler#opened_active_stack?` only checks `opened? && stack.present?` — no `review_stacks_enabled` gate at all [8](#0-7)  — so it writes `params.pull_request.labels.map(&:name)` onto the stack's `PullRequest` [9](#0-8) .
- `ReviewStack#env` merges those label names, upcased, as `"true"`-valued environment variables into the stack's environment [10](#0-9) , which is consumed by `DeployCommands#env`/`TaskCommands#env` feeding the process environment for deploy/task execution (confirmed by `test/lib/shipit/deploy_commands_test.rb` and `test/lib/shipit/task_commands_test.rb`).

Attacker's exact request: unauthenticated `POST /webhooks` with `X-Github-Event: pull_request`, body `action: "opened"`, `repository.owner.login` = an org configured with no `webhook_secret` (or any org they can freely choose per the multi-org config schema), `repository.full_name` = `"victim-org/victim-repo"`, and `pull_request.labels` containing attacker-chosen names. No `X-Hub-Signature` value needs to be genuine relative to the victim org.

Why existing guards fail: `verify_signature` never compares `repository_owner` to `repository.full_name`'s owner; `drop_unhandled_event` only checks the event type is registered; `ExplicitParameters` schemas only validate types/presence, not cross-field consistency; `Repository#owner`/`#name` format validators only constrain string shape, not which org authenticated the call; `provision?`'s intended gate (`review_stacks_enabled`) doesn't actually apply to two of its three disjuncts.

### Impact Explanation
An unauthenticated remote attacker can cause the Shipit application to accept a webhook it believes was authenticated for org A (no secret configured) but which actually creates/mutates a `ReviewStack`/`PullRequest` belonging to org B's repository — a payload nominally scoped to one repository mutating another repository's stack, matching the Critical "payload for one repository mutating another's stack" class. This is repeatable against any repository whose owning org's app config is discoverable/guessable and which has any provisioning behavior other than a review-stacks-enabled-gated `allow_all`, regardless of the operator's intent to keep review stacks disabled (`review_stacks_enabled: false`). The direct, provable outcome is unauthorized state creation (a new `ReviewStack`, `PullRequest` record) and injection of attacker-chosen environment-variable names/values (`LABEL_NAME=true`) into that stack's execution environment for subsequent deploy/task commands. Whether this escalates further to `PTY.spawn` command execution depends on whether the victim's `shipit.yml`/deploy scripts interpret an attacker-named boolean env var dangerously (e.g., feature-flag driven script paths); that link is configuration-dependent and not directly proven here, so the immediately provable, in-scope impact is unauthorized cross-tenant provisioning/state-mutation, not confirmed RCE.

### Likelihood Explanation
Preconditions: a multi-org Shipit deployment (`Shipit.github(organization: ...)` per-org config, a documented supported feature) where at least one configured org has no `webhook_secret` (also a documented, valid configuration in `secrets.development.shopify.yml`/`test/dummy/config/secrets_double_github_app.yml`); the target ("victim") repository must have `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` (not exclusively `allow_all`) for the `review_stacks_enabled: false` bypass to matter. Attacker cost is a single crafted HTTP POST, no credentials, no GitHub App access, no session — fully within the declared unprivileged attacker capability. It is repeatable per PR number/environment and across any repository reachable via `Repository.from_github_repo_name`.

### Recommendation
- In `Shipit::WebhooksController#verify_signature`, derive the authenticating organization strictly from `repository.full_name`'s owner segment (or validate that `repository.owner.login` and `repository.full_name`'s owner match) instead of trusting `repository.owner.login`/`organization.login` independently.
- Fix the `provision?` operator precedence in `OpenedHandler` (and mirror in `LabeledHandler`/`UnlabeledHandler`/`ReopenedHandler` if similarly affected) so `review_stacks_enabled` gates all three disjuncts, e.g. `repository.review_stacks_enabled && (allow_all? || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?))`.
- Add a `review_stacks_enabled` guard to `LabelCapturingHandler#opened_active_stack?` (and siblings) so label capture cannot occur for repositories where review stacks are disabled.
- Treat `webhook_secret: nil` orgs as non-authenticating for any event whose `repository.full_name` does not belong to that same org.

### Proof of Concept
Minitest plan (no live GitHub, use `test/dummy` fixtures/config):
1. In `test/dummy/config/secrets_double_github_app.yml`-style setup, configure org `OrgOne` with `webhook_secret: nil` and org `OrgTwo` (owning the victim repository) with a real `webhook_secret` and `review_stacks_enabled: false`, `provisioning_behavior: prevent_with_label`.
2. Assert the binding before: `Shipit.github(organization: 'OrgOne').verify_webhook_signature(anything, anything)` returns `true` regardless of signature (since `webhook_secret` is blank) — `assert Shipit.github(organization: 'OrgOne').verify_webhook_signature('sha1=garbage', 'irrelevant')`.
3. POST to `/webhooks` with `X-Github-Event: pull_request`, no valid signature for `OrgTwo`, body: `{"action":"opened","number":N,"repository":{"owner":{"login":"OrgOne"},"full_name":"OrgTwo/victim-repo"},"pull_request":{...,"labels":[{"name":"injected"}]}}`.
4. Assert response is `:ok` (not `422`), proving signature bypass.
5. Assert `Shipit::ReviewStack.find_by(environment: "pr#{N}")` was created under `OrgTwo/victim-repo` even though that repository's `review_stacks_enabled` is `false` — proving the `provision?` precedence bypass.
6. Assert `stack.pull_request.labels` includes `"injected"` and `stack.env["INJECTED"] == "true"`, proving `LabelCapturingHandler` mutated the victim stack's environment from a request "authenticated" by an unrelated, secret-less org.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
