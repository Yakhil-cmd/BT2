### Title
Hash-Locked Nodes Permanently Reject Re-Proposed Locked Block Due to Stale `lockedHash` After `WriteRound` Mutates Block Hash — (`consensus/istanbul/core/preprepare.go`)

---

### Summary

In `handlePreprepare`, when a node is hash-locked, the code calls `WriteRound` to stamp the current round into the local copy of the locked proposal's header, then compares the incoming proposal's hash against `c.current.GetLockedHash()`. Because `WriteRound` mutates `header.Extra[31]` (the round byte in the vanity area), the block hash changes — but `lockedHash` is never updated to reflect the new round. The comparison therefore always evaluates to `false`, causing every hash-locked node to send a round change instead of accepting the re-proposed locked block. This repeats across every subsequent round, permanently preventing hash-locked nodes from committing and stalling consensus if enough nodes are affected.

**Step 5 — The fatal comparison in `handlePreprepare`.**

```go

    header := c.current.Preprepare.Proposal.Header()
    c.backend.Sealer().WriteRound(header, c.currentView().Round.Int64())
    c.current.Preprepare.Proposal = c.current.Preprepare.Proposal.WithSeal(header)
    // c.current.Preprepare.Proposal.Hash() is now H_R+1
    // BUT c.current.GetLockedHash() is still H_R — never updated

    if preprepare.Proposal.Hash() == c.current.GetLockedHash() {
        // H_R+1 == H_R → always FALSE
        ...
    } else {
        c.sendNextRoundChange("handlePreprepare. HashLocked, but received hash is different from locked hash")
    }
}
``` [6](#0-5) 

The code updates `c.current.Preprepare.Proposal` to carry round R+1 but never calls `LockHash()` or otherwise updates `c.current.lockedHash`. `GetLockedHash()` returns the stale `H_R` forever. [7](#0-6) 

The comparison `H_R+1 == H_R` is always `false`. Every hash-locked node unconditionally sends a round change.

**Step 6 — The cycle repeats.**

`sendNextRoundChange` calls `catchUpRound`, which calls `updateRoundState` with `roundChange=true`, preserving `lockedHash = H_R` again. [8](#0-7) 

At round R+2, the proposer stamps R+2, producing `H_R+2`. The comparison `H_R+2 == H_R` fails again. The loop is permanent.

---

### Impact Explanation

**Liveness failure / consensus stall.** Hash-locked nodes can never accept the re-proposed locked block in any subsequent round. They are permanently stuck emitting round changes.

- If the number of hash-locked nodes ≥ f+1 (the weak-certificate threshold), the entire network stalls: non-locked nodes cannot assemble a quorum of commits either, because the locked nodes keep advancing the round.
- If fewer than f+1 nodes are locked, non-locked nodes may eventually commit (with round R+k in Extra), but the locked nodes remain stuck in round-change loops until they resync from the network — a durable loss of liveness for those validators.

The "chain split" framing in the question is overstated: BFT safety prevents two distinct blocks from being committed at the same height by honest nodes. The actual impact is **persistent consensus stall / liveness failure**, which qualifies as consensus divergence on honest nodes and durable loss of core chain functionality.

---

### Likelihood Explanation

Hash-locking occurs whenever a node accumulates a quorum of PREPARE or COMMIT messages before the round timer expires. This is a normal protocol path, not an exotic edge case. A network partition, a slow proposer, or a Byzantine validator selectively withholding commit messages can reliably trigger it. No privileged access, key compromise, or majority collusion is required — the bug fires from ordinary P2P consensus message delivery.

---

### Recommendation

After stamping the new round into the local locked proposal, update `lockedHash` to match:

```go
if c.current.IsHashLocked() {
    header := c.current.Preprepare.Proposal.Header()
    c.backend.Sealer().WriteRound(header, c.currentView().Round.Int64())
    c.current.Preprepare.Proposal = c.current.Preprepare.Proposal.WithSeal(header)
    c.current.LockHash()  // ← re-anchor lockedHash to the round-updated hash

    if preprepare.Proposal.Hash() == c.current.GetLockedHash() {
        ...
    }
}
```

Alternatively, compare `preprepare.Proposal.Hash()` against `c.current.Preprepare.Proposal.Hash()` (the already-updated local copy) instead of `c.current.GetLockedHash()`.

### Proof of Concept

1. Start a 4-validator network (f=1, quorum=3).
2. At sequence S, round 0: proposer broadcasts block B₀ (Extra[31]=0, hash=H₀). All 4 nodes receive enough PREPAREs to call `LockHash()` → `lockedHash = H₀`.
3. Before any COMMIT reaches quorum, inject a round-change (e.g., drop commit messages to 2 nodes). All nodes move to round 1.
4. The round-1 proposer (hash-locked) calls `sendPreprepare` → stamps Extra[31]=1 → broadcasts B₁ (hash=H₁≠H₀).
5. The 2 hash-locked receivers enter `handlePreprepare`: update local proposal to H₁, compare H₁==H₀ → false → `sendNextRoundChange`.
6. The 2 non-locked receivers accept B₁, send PREPAREs, but cannot reach quorum=3 without the locked nodes.
7. Round timer fires → round 2. Repeat from step 4 with Extra[31]=2. The locked nodes compare H₂==H₀ → false → round change again.
8. Assert: no block is ever committed at sequence S. The chain is permanently stalled.

func (c *core) sendPreprepare(request *bft.Request) {
	logger := c.logger.NewWith("state", c.state)

	header := request.Proposal.Header()
	c.backend.Sealer().WriteRound(header, c.currentView().Round.Int64())
	request.Proposal = request.Proposal.WithSeal(header)

	// If I'm the proposer and I have the same sequence with the proposal
	if c.current.Sequence().Cmp(request.Proposal.Number()) == 0 && c.isProposer() {
		curView := c.currentView()
		preprepare, err := bft.Encode(&bft.Preprepare{
			View:     curView,
			Proposal: request.Proposal,
		})
		if err != nil {
			logger.Error("Failed to encode", "view", curView)
			return
		}

		c.broadcast(&bft.Message{
			Hash: request.Proposal.ParentHash(),
			Code: bft.MsgPreprepare,
			Msg:  preprepare,
		})
	}
}
