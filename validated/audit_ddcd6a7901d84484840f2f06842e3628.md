## Title
Race condition in `handlePrivatePaymentChains`'s `cancelAllKeys` cross-cancels unrelated concurrent private-payment validations - (File: wallet.js)

### Summary
`handlePrivatePaymentChains` in `wallet.js` registers per-chain `eventBus.once(key, …)` listeners keyed only by `unit-payload_hash-output_index`, and on any validation failure calls a `cancelAllKeys()` helper that indiscriminately removes **all** listeners registered under those key strings via `eventBus.removeAllListeners(key)`. Because the same key namespace (`'private_payment_validated-' + unit + '-' + json_payload_hash + '-' + output_index`) is shared globally across every concurrent invocation of `handlePrivatePaymentChains`/`handleSavedPrivatePayments` for the same private element, one message's failure can wipe out the pending listener of a completely unrelated, concurrently-processing message for the identical private element, causing the second message's completion callback to never fire. This is the same bug class as the referenced Nethermind fix: an unsynchronized "cancel" operation racing with concurrent "wait" registrations on a shared resource.

### Finding Description
In [1](#0-0) , `handlePrivatePaymentChains` builds a local map `assocValidatedByKey` and, for every chain, computes:
```
var key = 'private_payment_validated-'+objHeadPrivateElement.unit+'-'+json_payload_hash+'-'+output_index;
``` [2](#0-1) 

When `network.handleOnlinePrivatePayment` reports `ifQueued` (the typical outcome for light clients / deferred validation), it registers `eventBus.once(key, …)`: [3](#0-2) 

`cancelAllKeys` is defined as:
```
var cancelAllKeys = function(){
	for (var key in assocValidatedByKey)
		eventBus.removeAllListeners(key);
};
``` [4](#0-3) 

`eventBus.removeAllListeners(key)` removes **every** listener registered on that event key on the global `eventBus`, not just the one registered by the current `handlePrivatePaymentChains` call. Because `key` is derived purely from `unit`/`payload_hash`/`output_index` (content of the private element), it is identical across separate, concurrent invocations of `handlePrivatePaymentChains` that happen to reference the same private chain element (e.g., the same private payment forwarded to the same device both directly and via `forwardPrivateChainsToOtherMembersOfSharedAddresses`/`forwardPrivateChainsToOtherMembersOfOutputAddresses`, or received simultaneously from the hub and from a peer). The actual asynchronous validation and event emission for that key happen later, in `network.js`'s `handleSavedPrivatePayments`, which emits `eventBus.emit(key, bValid)` exactly once when validation of the underlying `unhandled_private_payments` row completes: [5](#0-4) 

If invocation A's chain for this key fails validation (or errors out) before invocation B's `eventBus.once(key, …)` fires, A's `cancelAllKeys()` call strips B's listener from the bus. B's `checkIfAllValidated()` will then never be reached for that key: `assocValidatedByKey[key]` stays `false` forever in B's closure, so B never emits `all_private_payments_handled`, never calls `callbacks.ifOk()`/`ifError()` completion for that batch, and never forwards the chain via `forwardPrivateChainsToOtherMembersOfOutputAddresses` at [6](#0-5) .

This mirrors the referenced Nethermind bug class exactly: an unsynchronized cancel/dispose routine that can tear down state (here, event listeners) belonging to a concurrently-running operation because both operations share a keyed resource without proper isolation or locking.

### Impact Explanation
An unprivileged private-payment counterparty (anyone who can send/forward a private payment chain to a victim's wallet or device, including through legitimate forwarding paths that duplicate delivery of the same chain) can trigger this race by causing two concurrent `handlePrivatePaymentChains` calls to reference the same private element key, and making one of them fail validation. The victim wallet then permanently stalls processing of the other, valid, private payment: it is left in `unhandled_private_payments` and never advances/forwards, and the caller/UI waiting on `all_private_payments_handled`/`ifOk` never receives a callback. This is a denial-of-progress on private payments for the affected user (funds/UX freezing on private payment chains), reachable purely by message timing from a counterparty, not requiring any privileged/network position.

### Likelihood Explanation
Exploitability requires only that two deliveries of a private chain referencing the same `(unit, payload_hash, output_index)` be received/processed close enough in time by the same node — a realistic scenario given ocore's forwarding logic re-sends the same chains to shared/output address members, and light wallets can receive the same private payment both directly and via hub forwarding. No cryptographic or privileged capability is needed; the attacker only needs to make one of the concurrent deliveries fail validation (e.g., by sending a chain that fails at any point) to trigger `cancelAllKeys()` while a sibling valid delivery is still pending on the same key.

### Recommendation
Scope listener cleanup to the specific invocation instead of using the shared `eventBus`, e.g., by capturing the exact listener function added by `eventBus.once(key, fn)` and removing only that function (`eventBus.removeListener(key, fn)`) rather than calling `eventBus.removeAllListeners(key)`. Alternatively, use a per-invocation unique event key/namespace, or add a reference-counting/synchronization mechanism so that a key's listeners are only cleared when no other concurrent invocation still needs them — analogous to adding a lock around cancel/dispose to serialize with in-flight waiters, as was done in the referenced Nethermind fix.

### Proof of Concept
1. Craft two distinct `private_payment` hub messages (bodies for `handlePrivatePaymentChains`) whose `arrChains` differ in overall content/cache_key (so `handledChainsCache` dedup does not short-circuit either) but both contain a chain element with identical `unit`, `payload_hash`, and `output_index` (e.g., embed the same private element together with different sibling chains in each message).
2. Deliver message A and message B to the victim node in quick succession so that both invocations of `handlePrivatePaymentChains` reach the `ifQueued` branch and register `eventBus.once(key, …)` for the same `key` (as computed at [2](#0-1) ).
3. Arrange for message A's shared-key chain to fail deferred validation in `network.js`'s `handleSavedPrivatePayments` (e.g. malformed sibling data) so its emitted `eventBus.emit(key, false)` triggers A's `cancelAllKeys()`.
4. Observe that B's registered listener for `key` is now gone (removed via `eventBus.removeAllListeners(key)`), so when the underlying valid element for B is subsequently confirmed, B's callback for that key never fires; B's `assocValidatedByKey` remains partially `false` forever, and B never completes (`callbacks.ifOk`/`all_private_payments_handled` for B's batch never fire), stalling that private payment permanently on the victim's node.
