### Title
Webhook Signature Verified Against `repository.owner.login` While Handlers Trust `repository.full_name` — Organization/Repository Binding Break - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
This is a valid analog to the reported bug class: a trust boundary (the value cryptographically covered by the verification step) diverges from the value actually acted upon downstream, allowing an attacker who possesses a valid webhook secret for one GitHub organization to forge events that mutate stacks belonging to a different repository/organization.

### Finding Description
Multi-org Shipit configurations register a distinct `webhook_secret` per GitHub organization [1](#0-0) . `WebhooksController#verify_signature` selects which organization's secret to validate the HMAC against purely by reading the *payload's own* `repository.owner.login` field (falling back to `organization.login`): [2](#0-1) 

Critically, the signature only proves that *some* organization's configured secret produced this exact byte string; it says nothing about which repository the payload's other fields refer to. Downstream, `Handler#stacks` resolves the target `Repository`/`Stack` using a *different* payload field, `repository.full_name`: [3](#0-2) 

`PushHandler#process` then calls `stack.sync_github` for every matching, non-archived stack on that resolved repository, and `sync_github` triggers a real git fetch/deploy pipeline against GitHub using the app's own credentials [4](#0-3) .

`repository.owner.login` and `repository.full_name` are two independent JSON fields inside the same signed payload — nothing enforces `full_name.split('/').first == owner.login`. An attacker who legitimately controls (or has leaked) the webhook secret for organization `attacker-org` can construct a payload where:
- `repository.owner.login = "attacker-org"` (used only to pick the secret for HMAC verification — verification passes),
- `repository.full_name = "victim-org/victim-repo"` (used by `Handler#stacks`/`Repository.from_github_repo_name` to select the actual `Stack` acted upon).

This breaks the equality that should hold: `organization that authenticated == repository that is written`. Instead the engine authenticates as `attacker-org` but writes/acts on any repository resolvable via `Repository.from_github_repo_name`, regardless of which org owns it in Shipit's own database.

### Impact Explanation
A successful forgery lets an attacker trigger `GithubSyncJob`/`sync_github` against a victim's stack, causing Shipit to fetch and process attacker-influenced ref data as if it came from GitHub, an unauthorized action against a repository/stack the attacker's org has no relationship to. Depending on which webhook event/handler is abused (`push`, `status`, `check_suite`, `pull_request`), this can affect commit status records, CI check state used for deploy gating, or trigger sync jobs that pull attacker-controlled refs — an unauthorized cross-repository interaction that Shipit's per-organization webhook isolation is meant to prevent. This aligns with the High-severity bucket ("escalation" / "unauthorized" cross-boundary write) named in the rules, since it is a webhook-secret-scoped isolation bypass rather than a full unauthenticated compromise.

### Likelihood Explanation
Exploitation requires possession of a valid webhook secret for *at least one* configured organization in a multi-org Shipit deployment (an unprivileged party relative to the *other* organizations, but a legitimate credential holder for their own org — this is exactly the "unprivileged-attacker … organization that authenticated versus the repository that is written" pattern the rules call out, not a scenario requiring `webhook_secret` theft from the target org). Single-org deployments (`github_default_organization` non-nil path is skipped) are not affected since there is only one secret to check against; the risk is specific to multi-tenant/multi-org Shipit installations, which the codebase explicitly supports via `github_app_config`/`TOP_LEVEL_GH_KEYS` [5](#0-4) .

### Recommendation
Bind the field used for secret selection to the field used for repository resolution: after `verify_signature` succeeds, re-derive/cross-check that `repository.owner.login` (or `organization.login`) matches the owner segment of `repository.full_name` before dispatching to handlers, or resolve the target `Repository` scoped to the authenticated organization instead of trusting `full_name` in isolation. Reject the webhook (422) on mismatch.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` (secret `S1`) and `victim-org` (secret `S2`), each with an installed Shipit stack, per the multi-org config schema in `lib/shipit.rb`.
2. Craft a `push` event JSON body:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-controlled sha>",
     "repository": {
       "owner": { "login": "attacker-org" },
       "full_name": "victim-org/victim-repo"
     }
   }
   ```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(S1, raw_body)>` using the attacker's own known secret `S1`.
4. POST to `/webhooks`. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and verifies successfully against `S1` [6](#0-5) .
5. `PushHandler` is invoked with the full payload; `Handler#stacks` resolves `Repository.from_github_repo_name("victim-org/victim-repo")` [3](#0-2)  and triggers `stack.sync_github(expected_head_sha: params.after)` on the victim's stack, despite the request never having been signed with `victim-org`'s secret `S2`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
```
