### Title
Webhook organization used for HMAC verification is decoupled from the repository the event actually targets, allowing cross-organization event forgery - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
The reported smart-contract issue is that a claim's data is split across two contracts (NFT and Claiming) with no cross-check tying the two halves together, so an attacker can manipulate one side (e.g. `maxInvocations`) without the other side (`tournamentBPS`/`otherBPS`) being re-validated, breaking the intended distribution invariant. The structural analog in shipit-engine is that webhook signature verification is bound to one field of the JSON payload (`repository.owner.login`) while the actual repository/stack that gets mutated is selected from a *different, unchecked* field of the same payload (`repository.full_name`). Nothing enforces that these two fields refer to the same organization, so a party who legitimately owns a GitHub App installation for one org (and thus knows that org's `webhook_secret`) can compute a valid signature while pointing the event at a repository belonging to a different organization.

### Finding Description
`WebhooksController#verify_signature` selects which app/secret to use for HMAC validation using `repository_owner`, which reads `params.dig('repository', 'owner', 'login')` (or `organization.login`) from the untrusted, attacker-supplied JSON body: [1](#0-0) 

Downstream, `Shipit::Webhooks::Handlers::Handler#repository_name` (used by `PushHandler` and others to locate the `Stack` to act on) reads a *different* key from the same payload — `payload.dig('repository', 'full_name')` — with no cross-check that this repository belongs to the organization that was used to validate the signature: [2](#0-1) 

`PushHandler#process` uses that lookup to enqueue a sync against any matching stack, using attacker-controlled `after` (target SHA) and `ref` (branch): [3](#0-2) 

Shipit explicitly supports multiple independent GitHub App configurations, keyed by organization name, each with its own `webhook_secret`: [4](#0-3) 

`GitHubApp#verify_webhook_signature` only proves that the request body was signed with *some org's* secret — it never proves that the `repository.full_name` used elsewhere in the body actually belongs to that org: [5](#0-4) 

**Broken binding (as an equality):**
`organization that authenticated the request (repository.owner.login → webhook_secret used)` should equal `repository whose stacks get mutated (repository.full_name → Repository.from_github_repo_name)`. The code never asserts this equality; it only asserts "some app config's secret matches the raw body," and separately, "some field in that same body names a target repo."

An attacker who is the legitimate owner/admin of a GitHub organization that has installed the Shipit GitHub App (a normal, unprivileged setup step available to anyone who can create a GitHub App and have it installed on an org they control) knows that org's `webhook_secret`. They can:
1. Take that org's `webhook_secret` (which they legitimately possess for their own org).
2. Construct a payload where `repository.owner.login` (or `organization.login`) is set to their own org (so `Shipit.github(organization: repository_owner)` selects their own app/secret and the HMAC check passes).
3. Set `repository.full_name` to `"victim-org/victim-repo"` — a repository/stack actually tracked by this Shipit instance under a different, victim organization.
4. Compute a valid `X-Hub-Signature` over the full raw body using their own org's secret and POST it to the shared `/webhooks` endpoint.

`verify_signature` passes (their org's secret matches), but `PushHandler` then resolves the stack via `full_name`, which points at the victim's stack, and enqueues `stack.sync_github(expected_head_sha: params.after)` with an attacker-chosen SHA/branch for a repository the attacker's org has no relationship to.

### Impact Explanation
This lets an unprivileged party who legitimately controls only their own GitHub organization's Shipit App installation forge push events against arbitrary other organizations' repositories/stacks tracked by the same Shipit instance. Depending on stack configuration (e.g. `continuous_deployment: true`), a forged sync can drive an unauthorized deploy/rollback pipeline or manipulate deploy/commit state for a repository the attacker does not own — a cross-repository write and potential unauthorized deploy, matching the "Critical: cross-repository writes / unauthorized deploy" impact bucket.

### Likelihood Explanation
Exploitability only requires an attacker to control a GitHub App installation on any organization already configured in Shipit's multi-org `secrets.yml`, which is a normal, low-privilege administrative capability over their own org, not a Shipit credential or repository write access to the victim. The mismatch between the field used for authentication (`repository.owner.login`) and the field used for authorization/routing (`repository.full_name`) is a straightforward, deterministic logic flaw with no timing or race conditions involved.

### Recommendation
Bind the two halves of the trust decision together instead of validating them independently:
1. After successfully verifying the HMAC signature for `repository_owner`, re-derive the target repository strictly from `repository.owner.login`/`organization.login` (the same value used for signature selection), not from a separate `repository.full_name` string.
2. In `Handler#repository_name` / `Handler#stacks`, verify that the resolved `Repository`'s owner matches the same organization whose secret validated the request, rejecting the event otherwise.
3. Consider signing/validating a canonical `(owner, repo)` tuple as a single unit rather than trusting independent JSON keys for authentication vs. routing.

### Proof of Concept
1. Attacker creates/owns GitHub org `attacker-org` and installs their own Shipit-compatible GitHub App on it, obtaining `webhook_secret_attacker` (a normal setup step for their own org — not a Shipit credential).
2. Confirm `victim-org/victim-repo` is a tracked `Stack` on the shared Shipit instance.
3. Build payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
4. Compute `X-Hub-Signature: sha1=HMAC_SHA1(webhook_secret_attacker, raw_body)`.
5. POST to `/webhooks` with header `X-Github-Event: push`.
6. `verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) resolves `repository_owner` as `attacker-org`, loads that org's `webhook_secret_attacker`, and the HMAC matches → request accepted.
7. `Shipit::Webhooks::Handlers::PushHandler` (`app/models/shipit/webhooks/handlers/push_handler.rb`) resolves stacks via `Handler#repository_name` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`), which reads `full_name = "victim-org/victim-repo"`, and enqueues `sync_github(expected_head_sha: "<attacker-chosen-sha>")` against the victim's stack — despite the request never being signed by, or authorized for, `victim-org`.

      verified = github_app.verify_webhook_signature(

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
