### Title
Global, un-scoped `sha` lookup in `StatusHandler#process` lets a status webhook from one repository/stack write CI status onto a same-sha commit belonging to a different stack, flipping `UndeployedCommit#deploy_disallowed?` from true to false - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves the commits to update by `Commit.where(sha: params.sha)` with no scoping to the reporting repository, while `Commit#sha` is only unique per `stack_id` (see the `index_commits_on_stack_id_and_sha` migration), not globally. A legitimately signed status webhook for a stack the attacker controls therefore also writes a `Status` row on any other stack's commit that happens to share the same sha, and `Commit#deployable?` / `UndeployedCommit#deploy_disallowed?` read that status without ever checking which repository actually reported it.

### Finding Description
The broken binding is: `victim_commit.deploy_disallowed?` (shown in the deploy UI to the victim operator) `== f(victim_repository's own CI statuses only)`.

- `app/controllers/shipit/webhooks_controller.rb:24-30` selects the GitHub App / webhook secret to verify against using `repository_owner` taken from the incoming payload, and `verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`) checks the HMAC against that org's secret. This correctly proves the request came from GitHub for *that org*, but it says nothing about which specific `Commit` rows in the database should be touched.
- `app/models/shipit/webhooks/handlers/status_handler.rb:20-24`:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This performs a **global** lookup by `sha` across the whole `commits` table, with no `stack_id`/`repository` filter and no cross-check against `params.repository`. The `params` schema for this handler (`requires :sha`, `:state`, ...) doesn't even require/validate a `repository` field for cross-checking.
- `Commit` is `belongs_to :stack`, and the DB uniqueness constraint on `sha` is scoped to `(stack_id, sha)` (`db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`), meaning the same sha string can legitimately exist as separate `Commit` rows under different stacks (e.g., two Shipit stacks tracking repositories that share git history — forks, mirrors, or a byte-identical commit constructed from the same tree/parents/author/committer/timestamps, which produces an identical SHA-1 by design of git's content-addressing).
- `Commit#create_status_from_github!` → `statuses.replicate_from_github!` writes a new `Status` for that commit, and `Commit#deployable?` (`app/models/shipit/commit.rb:227-229`) is `!locked? && (stack.ignore_ci? || (success? && !blocked?))`, delegating `success?`/`state` to `status`, which is derived purely from the `statuses` just written — with no origin/repository check.
- `UndeployedCommit#deploy_disallowed?` (`app/models/shipit/undeployed_commit.rb:39-41`) is `!deployable? || !stack.deployable?` — it directly inherits this now-poisoned `deployable?`.

Exploit flow: the attacker owns/controls a repository X that is tracked as its own Shipit stack (a normal, honestly-onboarded integration, so their `status` webhooks pass `verify_signature` using X's own org's real webhook secret). The attacker crafts (or naturally has, via shared git history/fork) a commit in repo X whose SHA-1 is identical to a commit that already exists in the victim's stack/repository. The attacker triggers (or fakes, via any status-posting mechanism available to them for their own repo, e.g. their own CI, or a status they are permitted to post on their own repo) a `status` event with `state: success` for that sha. GitHub delivers (or the attacker's own legitimate integration delivers) this webhook, `verify_signature` passes because it is genuinely signed for the attacker's own org, and `StatusHandler#process` then updates **every** `Commit` row across the whole database matching that sha — including the victim's commit under the victim's stack. The victim's `UndeployedCommit#deploy_disallowed?` then flips from `true` (blocked, no successful status from the victim's own CI) to `false` (green/deployable), even though the victim repository's real CI never posted anything.

None of the existing guards catch this: `verify_signature` only authenticates the *organization* the payload claims to be from, not which `Commit`/`stack` rows may be mutated; `drop_unhandled_event` only checks the event type is handled; the `ExplicitParameters` schema for `StatusHandler` doesn't require or validate `repository` at all, so there is no field available to cross-check against the target stack's repository even if the code wanted to; `Repository`/`Stack` model validations don't constrain which stack a `Commit` with a given sha belongs to.

### Impact Explanation
This is a payload for one repository's webhook mutating another repository's stack/commit state — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." Concretely, an attacker-controlled repository's `status` webhook writes a fabricated `success` `Status` onto a victim's `Commit`, causing the victim's deploy button/UI (`deploy_button` in `app/helpers/shipit/stacks_helper.rb`) to show the commit as `allowed` even though the victim's own CI never ran or is still failing. If the victim operator then manually clicks deploy, an untested/unvetted commit is deployed via `Stack#trigger_deploy`, i.e., an unauthorized deploy driven by a forged/cross-tenant status. This is repeatable against any stack whose tracked commit sha the attacker can reproduce or share, and the blast radius spans every stack hosted on the same Shipit instance (not scoped to a single tenant/organization), because the lookup has no stack/repository boundary at all.

### Likelihood Explanation
Preconditions: the attacker needs (a) at least one Shipit-tracked stack/repository under their own control that can deliver correctly-signed `status` webhooks (a normal, low-privilege integration setup that many Shipit deployments allow any onboarded team/repo to have), and (b) a commit whose SHA-1 collides with a target victim commit — trivially achievable when repos share git ancestry (forks/mirrors of the same upstream, common in mono-org setups) or by locally constructing a byte-identical commit object (same tree, parents, author/committer identities and timestamps, message) which is fully within the attacker's control for content they already know (e.g., a public commit). No secrets, sessions, or elevated GitHub permissions are required beyond what the attacker already has for their own repository/stack. This is fully repeatable and requires no timing tricks or race conditions.

### Recommendation
Scope `StatusHandler#process` to the reporting repository: require and use `params.repository.full_name` to resolve the specific `Shipit::Repository`/`Stack`(s) whose git history the reported sha actually belongs to (mirroring how `CheckSuiteHandler` scopes by `stacks.where(branch: ...)`), and restrict the `Commit.where(sha: ...)` lookup to `commits` belonging to that repository's stacks only, e.g. `repository.stacks.commits.where(sha: params.sha)`. Add a `requires :repository { requires :full_name, String }` to the handler's `ExplicitParameters` schema so the field is always present and validated.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_cross_repo_test.rb
require "test_helper"

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossRepoTest < ActiveSupport::TestCase
        test "status webhook from one repo cannot flip deploy_disallowed? for another stack's commit with the same sha" do
          victim_stack = shipit_stacks(:shipit)          # victim's own stack/repo
          attacker_stack = shipit_stacks(:cyclimse)       # attacker-controlled stack/repo

          shared_sha = "a" * 40
          victim_commit = victim_stack.commits.create!(sha: shared_sha, message: "victim work")
          # no successful status yet -> blocked
          undeployed = UndeployedCommit.new(victim_commit, index: 0)
          assert_predicate undeployed, :deploy_disallowed?

          # Attacker's own commit (same sha, different stack) exists too
          attacker_stack.commits.create!(sha: shared_sha, message: "attacker's identical-sha commit")

          # Attacker's legitimately-signed status webhook for their own repo/org
          payload = {
            "sha" => shared_sha,
            "state" => "success",
            "context" => "ci/attacker",
            "repository" => { "full_name" => attacker_stack.repository.full_name,
                               "owner" => { "login" => attacker_stack.repository.owner } }
          }

          StatusHandler.new(payload).process

          victim_commit.reload
          undeployed = UndeployedCommit.new(victim_commit, index: 0)

          # BUG: this currently becomes false even though the victim repo's own CI never ran
          refute_predicate undeployed, :deploy_disallowed?, "victim commit was marked deployable by a status forged via a different repository's webhook"
        end
      end
    end
  end
end
```
Both sides of the equality (`deploy_disallowed?` before/after) should be compared: before the attacker's webhook it is `true`, and if the fix scoping `StatusHandler` to the reporting repository is not applied, it becomes `false` after — demonstrating the cross-repository mutation.
