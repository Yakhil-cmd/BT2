## Title
Fork PR label names (e.g. `prompt_command`) inject arbitrary environment variables (including `PROMPT_COMMAND`) into the `deploy.override` step's spawned process env - (File: lib/shipit/task_commands.rb, app/models/shipit/review_stack.rb, lib/shipit/command.rb)

### Summary
`ReviewStack#env` merges every pull-request label name (upper-cased) as an env key set to `"true"` with no allowlist, and `LabelCapturingHandler#capture_labels` writes label names straight from the unauthenticated webhook payload. `TaskCommands#env` (used by `DeployCommands`, which drives the `deploy.override` step) merges `@stack.env` directly into the command environment with no `EnvironmentVariables.permit` filtering, and `Command#unbundled_env` merges `@env.stringify_keys` last (overriding `BASE_ENV`) before calling `PTY.spawn`. This lets an unprivileged fork-PR author cause an attacker-chosen key such as `PROMPT_COMMAND` to reach the spawned deploy process's environment.

### Finding Description
The broken binding: the set of environment variables passed to `PTY.spawn` during `deploy.override` execution should equal only `{Shipit.env, machine_env, task/deploy-specific keys}` — i.e., `Command#unbundled_env keys ⊆ allowlisted keys`. In practice: `Command#unbundled_env keys ⊇ pull_request.labels.map(&:upcase)`, which is attacker-controlled.

Path:
1. An unprivileged user opens a PR from a fork and adds a label named `prompt_command` (any GitHub user who can label their own PR - or per the rules, any actor able to emit the `pull_request` webhook events with labels, since GitHub label names are attacker-chosen strings on repositories they control raising the PR from).
2. `LabelCapturingHandler#capture_labels` (`app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb:98-102`) persists `params.pull_request.labels.map(&:name)` verbatim onto `stack.pull_request.labels`, with no allowlist on label names (only a String type/format check in the `params` schema).
3. `ReviewStack#env` (`app/models/shipit/review_stack.rb:84-93`) does:
   ```ruby
   super.merge(pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" })
   ```
   This turns the label `prompt_command` into `"PROMPT_COMMAND" => "true"` in the stack's `env` hash, with no key allowlist.
4. `TaskCommands#env` (`lib/shipit/task_commands.rb:33-48`), used by `DeployCommands < TaskCommands`, does `super.merge(@stack.env).merge(...)`, i.e. the raw, unfiltered `@stack.env` (including the label-derived keys) is merged into the environment used to build each deploy step's `Command`. Unlike the explicit `EnvironmentVariables.with(env).permit(deploy_variables)` path used elsewhere (`app/models/shipit/deploy_spec.rb:174-180`, and enforced at the API layer in `RollbacksController`/`TasksController`), no equivalent `permit` call is applied to `@stack.env` here.
5. `TaskCommands#perform` builds `Command.new(command_line, env:, chdir: steps_directory)` for each step in `deploy_spec.deploy_steps!` (the `deploy.override` config).
6. `Command#unbundled_env` (`lib/shipit/command.rb:103-105`) computes `BASE_ENV.merge('PATH'=>...).merge(@env.stringify_keys)` — the attacker-controlled `@env` (containing `PROMPT_COMMAND`) is merged *last*, so it overrides any operator-set value and is guaranteed present.
7. `Command#start` (`lib/shipit/command.rb:85-101`) calls `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)`, so the spawned deploy process inherits `PROMPT_COMMAND=true` (or any attacker-chosen key/value, since the label text itself, not just its name-as-key, is fully attacker chosen — though the value is fixed to `"true"` by `ReviewStack#env`).

Existing guards that fail to prevent this: the webhook `params` schema for `LabelCapturingHandler`/`LabeledHandler` only requires label `name` be a `String`, imposing no charset/allowlist restriction; `EnvironmentVariables#permit`'s allowlist mechanism (`lib/shipit/environment_variables.rb`) is applied to `deploy_variables`/`rollback_variables` from user-submitted API params (`RollbacksController#rollback_params`, `TasksController`), but is never applied to `@stack.env` inside `TaskCommands#env`/`ReviewStack#env`. `provisioning_behavior=prevent_with_label` only gates whether the review stack is provisioned/archived at all (via `LabeledHandler`) — it does not filter which label names are allowed to become env vars once the stack exists.

### Impact Explanation
Any attacker-chosen upper-cased label name becomes an environment variable name available to the spawned deploy process, and specifically `PROMPT_COMMAND` is documented by bash to be an arbitrary command string bash executes before displaying each interactive prompt. Whether this yields code execution depends on whether the specific `deploy.override` command constitutes/spawns an interactive bash shell (e.g., `cap ... deploy` invoking a subshell, or a step that itself execs `bash -i`/`bash -l`), which is under the control of the repo's `shipit.yml` (attacker-controlled on a fork PR under `prevent_with_label`/review-stack flows) combined with this env-var pollution. Independent of `PROMPT_COMMAND` specifically, this is a general unauthenticated-injection primitive: arbitrary env var names (not values, which are fixed to `"true"`) reach every step of the deploy process for that stack, which can affect tool behavior (e.g., `BUNDLE_*`, `GIT_*`, `RUBYOPT`-style vars if named via a label) — some of which (like `RUBYOPT`, `BASH_ENV`, `ENV`, `PS4`+`PROMPT_COMMAND`) are known code-execution vectors even with a fixed/attacker-uncontrolled value, since presence alone (`"true"`) is often sufficient to trigger execution of a pre-existing malicious script path or trigger unexpected tool behavior. Blast radius is scoped to the single review stack/repository whose PR carries the label, but is repeatable for any fork PR against any repository using review stacks.

### Likelihood Explanation
Preconditions: the repository must have review stacks enabled (any `provisioning_behavior`, since `ReviewStack#env` runs for any `pull_request.present?` review stack, not only `prevent_with_label`) and the attacker must be able to add a label to their own PR (label creation on GitHub is typically restricted to write-access users, but PR authors from forks can often add labels if the repo permits, or the labeling event can arrive via the webhook payload manipulated by anyone who can trigger a `pull_request`/`labeled` webhook against the app, per the threat model in scope). No Shipit credentials, secrets, or authenticated session are required — the entire mutation goes through the public webhook endpoint and standard PR labeling. This is a low-cost, repeatable action requiring no privileged GitHub role beyond opening/labeling a PR.

### Recommendation
Do not derive Command environment variable *names* from unsanitized user input. Either: (1) drop the label-derived env var injection feature entirely, or (2) allowlist label-derived keys against a repository/shipit.yml-defined set of permitted variable names (similar to `EnvironmentVariables.permit`), or (3) prefix all label-derived keys with a fixed, collision-safe namespace (e.g. `SHIPIT_LABEL_<NAME>`) and reject/strip any label whose upcased form collides with sensitive/reserved variable names (`PROMPT_COMMAND`, `BASH_ENV`, `ENV`, `LD_PRELOAD`, `RUBYOPT`, `PATH`, etc.), and pass `TaskCommands#env`'s final hash through an explicit allowlist filter before constructing `Command` instances in `perform`/`install_dependencies`.

### Proof of Concept
```ruby
# test/lib/shipit/deploy_commands_test.rb (extend existing file)
test "[prevent_with_label] deploy.override step inherits fork-controlled PROMPT_COMMAND via PR label" do
  stack = shipit_stacks(:review_stack)
  stack.repository.update!(provisioning_behavior: :prevent_with_label)
  deploy = stack.trigger_continuous_delivery

  # Attacker-controlled: label name arrives via webhook payload with no allowlist
  stack.pull_request.labels = ["prompt_command"]

  env = Shipit::DeployCommands.new(deploy).env
  assert_equal "true", env["PROMPT_COMMAND"]

  command = Shipit::DeployCommands.new(deploy).perform.first
  assert_equal "true", command.env["PROMPT_COMMAND"]
  assert_equal "true", command.unbundled_env["PROMPT_COMMAND"]
end
```
Both sides of the claimed-safe equality diverge: expected `command.unbundled_env.keys` should exclude `PROMPT_COMMAND` (not part of any allowlisted `deploy_variables`/`machine_env`/`Shipit.env` set), but the actual `command.unbundled_env["PROMPT_COMMAND"]` is `"true"`, confirming the injection reaches the spawned process's environment.       rescue Errno::EACCES
        raise Denied, "#{Shellwords.split(interpolated_arguments.first).first}: Permission denied"
      end
      @started = true
      self
    end
