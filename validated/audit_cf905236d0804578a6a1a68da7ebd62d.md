## Analysis

The bug class in the Firedancer report is: a component (`fd_shred`) is trusted to produce a payload, but the consumer (`fd_store`/`fd_ext_blockstore_insert_shreds`) only validates a subset of framing fields (`shred_sz`, `stride`, `shred_cnt`) and then blindly acts on unvalidated inner fields (`pkts[i].shred.fec_set_idx`), letting the *producer identity that was accepted* diverge from *the data actually operated on downstream*.

The closest structural analog in shipit-engine is in `WebhooksController` / `Shipit::Webhooks::Handlers::Handler`: the field used to select **which GitHub App/organization's secret authenticates the request** is not the same field used to select **which repository/stack the payload is applied to**. [1](#0-0) 
`verify_signature` picks the verifying `github_app` using `repository_owner`, which is `params.dig('repository','owner','login')` (falling back to `params.dig('organization','login')`): [2](#0-1) 

Once the HMAC check passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` hands the **entire raw JSON body** to handlers, unmodified. Every handler, however, resolves the target repository/stack using a *different* field — `repository.full_name` — not the org/owner field that gated signature verification: [3](#0-2) 
`PushHandler` similarly looks up stacks via `stacks` (i.e. `full_name`) and calls `stack.sync_github`: [4](#0-3) 
and `StatusHandler` writes a `Status` for any commit matching `params.sha` regardless of which org's secret authenticated the request: [5](#0-4) 

Because Shipit supports multi-organization configuration (`docs/setup.md`), each org has its own independent `webhook_secret`: [6](#0-5) 

The full raw request body is what's HMAC'd (`request.raw_post`), so whoever holds a valid secret for **any** configured organization can compute a valid signature over **any** JSON body they construct — including one whose `repository.owner.login` matches their own org (satisfying `verify_signature`) but whose `repository.full_name` names a repository/stack belonging to a *different* tracked organization. The binding being broken is: **organization whose secret authenticated the request == repository the handlers actually act on**. This lets an attacker who legitimately controls (or leaks) one org's Shipit-configured GitHub App webhook secret forge `push` or `status` events against a completely different repository/stack tracked by the same Shipit instance — e.g., posting a fake `success` CI status for a commit in another org's repo, which, combined with `continuous_deployment`, triggers a real unauthorized deploy via `Commit#add_status` → `stack.schedule_merges`/`schedule_continuous_delivery`: [7](#0-6) [8](#0-7) 

I was not able to fully verify from the index whether the multi-org lookup path (`Shipit.github(organization:)`) enforces that the resolved app's installation is actually scoped only to that literal `full_name`'s namespace at the GitHub API level (i.e., whether there's any additional cross-check elsewhere in `lib/shipit/github_app.rb` I haven't seen) — the file is large and I only saw a portion of it. If such a repository-ownership cross-check exists it would need to be confirmed against `full_name`'s owner before considering this exploitable.

### Title
Cross-organization webhook forgery via organization/repository binding mismatch - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` authenticates an inbound GitHub webhook using the HMAC secret of the GitHub App tied to `repository.owner.login` (or `organization.login`), but the event handlers that subsequently act on the payload resolve their target Stack/Commit using the unrelated `repository.full_name` field. No code ties the two together.

### Finding Description
Since HMAC-SHA1/256 verification covers the entire raw request body, anyone possessing a valid `webhook_secret` for organization A (a legitimate GitHub App configured in Shipit's multi-org `secrets.yml`) can compute a valid signature for an arbitrary JSON payload where `repository.owner.login == "OrgA"` but `repository.full_name == "OrgB/some-repo"`. `verify_signature` only checks the signature against OrgA's secret and passes. The event is then dispatched to handlers (`PushHandler`, `StatusHandler`, pull-request handlers, etc.) which all resolve the acted-upon repository/stack via `payload.dig('repository','full_name')`, i.e. OrgB's repository — never re-validating that `full_name`'s owner matches the authenticating org.

### Impact Explanation
An attacker who controls a legitimate GitHub App/webhook secret for one org tracked by a Shipit instance can forge `status` webhooks that inject fabricated CI status records for commits in a completely different org's tracked repository, and forge `push` events to trigger `sync_github` against another org's stack. Combined with `continuous_deployment`, a forged "success" status can autonomously trigger an unauthorized deploy of a real commit — this maps to the "unauthorized deploy" Critical impact category.

### Likelihood Explanation
Requires the attacker to hold (or leak) a valid `webhook_secret` for at least one organization configured in the Shipit instance's multi-org setup — a scenario explicitly supported and documented (`docs/setup.md`). No `ApiClient` token, GitHub App private key, or Shipit session is required; only the shared HMAC secret of one org's app.

### Recommendation
After signature verification, re-derive/validate that the org used for verification (`repository.owner.login`/`organization.login`) matches the owner segment of `repository.full_name` before dispatching to handlers, or bind handler repository resolution to the same field used for the signature-verification lookup.

### Proof of Concept
1. Configure two orgs in `secrets.yml` (as documented), each tracked in Shipit with its own repo/stack.
2. As holder of OrgA's `webhook_secret`, construct a `status` (or `push`) payload with `repository.owner.login = "OrgA"` and `repository.full_name = "OrgB/tracked-repo"`, `sha` set to a real commit hash in OrgB's tracked stack, `state: "success"`.
3. Compute `X-Hub-Signature` using OrgA's `webhook_secret` over the raw JSON body.
4. POST to `/github/webhooks` (or the mounted webhooks endpoint); `verify_signature` passes (uses OrgA's secret matching `owner.login`), and `StatusHandler#process` creates a `Status` on OrgB's commit — potentially triggering continuous deployment for OrgB's stack despite the attacker having no credentials for OrgB.
