### Title
Cross-organization CI status forgery via unscoped commit SHA lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects the signing secret to validate a webhook using the organization derived from `repository.owner.login` (or `organization.login`) in the *unverified* JSON body [1](#0-0) [2](#0-1) . Once the signature is accepted for that organization, `StatusHandler#process` applies the status update purely by matching `sha` against *all* commits in the database, with no check that the commit's stack/repository actually belongs to the organization whose secret was used to authenticate the request: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [3](#0-2) . The base `Handler` class does expose a `repository_name`/`stacks` scoping helper [4](#0-3) , but `StatusHandler` never uses it to constrain the lookup.

### Finding Description
The equality that should hold is:
`organization authenticated by verify_signature (repository.owner.login in the request body) == organization/repository whose data is mutated by the handler`

Before the attacker's request: commit `C` with `sha = S` belongs to stack `victim/repo` under organization `OrgB`, tracked with CI requirements in its `shipit.yml` (`ci.require`) gating `continuous_deployment?` [5](#0-4) .

An attacker only needs push/webhook-secret knowledge for some organization `OrgA` that is also onboarded to the same Shipit instance (e.g. they are a legitimate admin of an unrelated repo/org configured in Shipit). They craft a `status` event body:
```json
{
  "sha": "<S, the victim commit sha>",
  "state": "success",
  "repository": { "owner": { "login": "OrgA" } }
}
```
and sign it with `OrgA`'s webhook secret. `WebhooksController#verify_signature` computes `repository_owner` = `"OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and validates the HMAC successfully [6](#0-5) . The request is accepted and dispatched to `Shipit::Webhooks.for_event('status')` → `StatusHandler` [7](#0-6) .

`StatusHandler#process` then looks up `Commit.where(sha: params.sha)` — this is a *global* query across the whole `commits` table, unfiltered by any repository/organization association [3](#0-2) . It matches commit `C` belonging to `OrgB`'s stack and calls `commit.create_status_from_github!(params)`, which persists a forged status (e.g. `success`) via `add_status` [8](#0-7) [9](#0-8) .

After the attack: commit `C`'s `deployable?` now reflects a forged passing status, `blocked?` may be bypassed, and `schedule_continuous_delivery` fires `ContinuousDeliveryJob` for `OrgB`'s stack if continuous deployment is enabled [10](#0-9) [5](#0-4) . The binding "organization that authenticated" ≠ "repository/stack that is written" is broken: `OrgA`'s signature authorized a write to `OrgB`'s commit/stack.

### Impact Explanation
This allows an attacker who only controls (or knows the webhook secret of) one organization/repo onboarded to a shared Shipit instance to inject fabricated CI statuses for commits belonging to any other organization's stacks, bypassing `ci.require`/blocking-status gating and triggering an unauthorized deploy via continuous delivery for a repository the attacker has no legitimate access to. This matches the Critical impact category "an unauthorized deploy."

### Likelihood Explanation
Likelihood is High for any Shipit deployment hosting multiple organizations/repositories (the common case, since `Shipit.github` is resolved per-organization and multiple orgs can be configured with distinct secrets) [11](#0-10) . The attacker needs only the sha of the target commit (visible from public GitHub activity, PRs, or the Shipit UI itself) and their own legitimate webhook secret — no compromise of the victim organization or its GitHub credentials is required.

### Recommendation
Scope `StatusHandler#process` (and any handler that queries by `sha` alone) to commits belonging to stacks whose repository matches `payload.dig('repository', 'full_name')`, mirroring the `stacks` helper already defined in the base `Handler` class, e.g. `stacks.flat_map(&:commits).select { |c| c.sha == params.sha }`, or add an explicit `repository_id`/`stack_id` constraint to the `Commit.where(sha: params.sha)` query so that the authenticated organization from `verify_signature` is provably the same one whose commit is mutated.

### Proof of Concept
1. Onboard/admin a repo under `OrgA` in the shared Shipit instance and obtain its configured webhook secret (legitimately available to an org admin).
2. Identify a target commit sha `S` belonging to a stack in `OrgB` (e.g. from GitHub's public commit history or the Shipit UI).
3. Send `POST /webhooks` with header `X-Github-Event: status`, body `{"sha":"S","state":"success","repository":{"owner":{"login":"OrgA"}}}`, and `X-Hub-Signature` computed as `sha1=` + HMAC-SHA1(OrgA_webhook_secret, raw_body).
4. `verify_signature` passes (secret matches `OrgA`); `StatusHandler` finds commit `S` regardless of repository and records a forged `success` status, potentially unblocking/triggering a deploy on `OrgB`'s stack.

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
