### Title
Webhook signature is verified against the organization named in `repository.owner.login`, but handlers act on the repository named in `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to use for HMAC verification based on `repository.owner.login` (falling back to `organization.login`), while every webhook `Handler` resolves the *actual* repository/stack to act on via `repository.full_name`. Nothing binds these two payload fields together cryptographically. An attacker who controls (or is a member of) any GitHub organization configured in Shipit **without** a `webhook_secret` (an explicitly supported, "optional" configuration per the setup docs) can post a forged webhook whose `owner.login` names that secret-less org (so signature verification trivially passes) while `repository.full_name` names a completely different, secured victim stack. The dispatched handler then acts on the victim repository/stack using an "authentication" that never touched the victim organization's secret.

### Finding Description
`verify_signature` looks up the GitHub App/secret purely from the owner field of the untrusted payload: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` returns `true` unconditionally whenever the resolved app has no `webhook_secret` configured — a state the docs explicitly describe as optional ("Webhook secret (optional)"): [3](#0-2) [4](#0-3) 

Once the (trivially passed) signature check succeeds, `WebhooksController#create` dispatches the raw, attacker-controlled payload to every registered handler for the event: [5](#0-4) 

Every handler, however, resolves its target repository/stack from a *different* field of the same payload — `repository.full_name` — not from `repository.owner.login`: [6](#0-5) 

`PushHandler`, for example, uses that repository resolution to trigger a real sync against matching stacks: [7](#0-6) 

and `StatusHandler` is confirmed (via its test) to persist an arbitrary GitHub commit `Status` (state/description/target_url) for any commit SHA named in the payload, independent of the organization whose "authentication" was checked: [8](#0-7) 

**The broken binding, as an equality that fails to hold:**
`organization authenticated by verify_signature (repository.owner.login / organization.login)` ≠ `repository actually written to by the Handler (repository.full_name)`

Before the attacker's request: only a legitimately-signed webhook from GitHub, for organization `X`, can affect stacks belonging to `X`'s repositories (signature secret and acted-upon repository are the same trust domain).

After the attacker's request: a forger who only knows that organization `A` (any org configured in Shipit without a webhook secret) exists can make the signature check pass, then supply `repository.full_name = "B/victim-repo"` for an unrelated, secured organization `B`, and have the dispatched handler act on `B`'s stack/commits — despite `B`'s secret never being involved in verification at all.

### Impact Explanation
This lets an unauthenticated attacker forge webhook events (push, status, pull_request, check_suite, membership) against **any** stack/repository configured in the Shipit instance, as long as at least one configured GitHub organization in the multi-org config lacks a `webhook_secret` (an explicitly documented, supported setup). Concretely reachable effects include:
- Forging commit `status` for a victim repository's commit SHA (`StatusHandler`), which is the exact signal Shipit's UI/gating logic uses to represent CI state on a commit before a human triggers a deploy — undermining the "green build" precondition operators rely on before shipping.
- Forcing `GithubSyncJob`/`stack.sync_github` execution against a victim stack via forged `push` events, injecting attacker-chosen `after` SHAs into a stack the attacker has no GitHub write access to.
- Forging `membership`/`pull_request` events that mutate `Team`/`User` records or the review-stack lifecycle for repositories outside the attacker's control.

This is a cross-organization write: actions attributed to "organization A's webhook" are actually executed against organization B's repository state, which the report rules classify under cross-repository writes / unauthorized deploy-adjacent tampering.

### Likelihood Explanation
Likelihood is Medium: the attacker needs no privileged Shipit session, `ApiClient` token, or any of the victim's secrets — only knowledge that some organization in the multi-org `github:` config is running without a `webhook_secret` (an explicitly supported and documented configuration choice, not a misconfiguration Shipit warns against) and the target victim's `full_name`, which is public information. This is entirely unprivileged and requires no host-application deviation from documented setup.

### Recommendation
Bind the verified organization to the repository actually acted upon: after computing `repository_owner` for signature verification, re-derive it from (and cross-check equality against) the owner segment of `repository.full_name`/`repository.owner.login` used by `Handler#repository_name`, and reject the webhook if they diverge. Additionally, discourage/disallow leaving `webhook_secret` blank for any organization in production (fail closed instead of `return true unless webhook_secret` in `GitHubApp#verify_webhook_signature`), since a single secret-less org in a multi-org install currently defeats signature verification for that org's namespace entirely.

### Proof of Concept
1. Shipit is configured with multiple GitHub orgs (per `docs/setup.md` "Using Multiple Github Applications"), where `OrgA` has `webhook_secret: nil` and `OrgB` (running a real, secured stack, e.g. `OrgB/victim-repo`) has a real secret configured.
2. Attacker sends:
```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=anything   # irrelevant, will be accepted

{
  "sha": "<victim commit sha>",
  "state": "success",
  "description": "forged",
  "context": "ci/forged",
  "target_url": "https://attacker.example",
  "repository": { "full_name": "OrgB/victim-repo", "owner": { "login": "OrgA" } }
}
```
3. `verify_signature` resolves `repository_owner` → `"OrgA"`, calls `Shipit.github(organization: 'OrgA').verify_webhook_signature(...)`, which returns `true` unconditionally because `OrgA.webhook_secret` is blank [9](#0-8) .
4. `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`, which resolves the target commit/stack using `repository.full_name = "OrgB/victim-repo"` and creates a forged `Status` record for `OrgB`'s commit — with the attacker never possessing `OrgB`'s webhook secret.

I was unable to fully read `PullRequest::ClosedHandler`/`OpenedHandler` bodies in this session (only confirmed via grep that they use `full_name`), so I cannot state with certainty whether they perform direct GitHub-side writes (e.g., merges) beyond local DB state changes; that would need direct file inspection to confirm the strongest possible impact tier.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
