### Title
Missing `return` after error path causes duplicate finalization of a private‑payment chain (double free / double‑release analog) - (File: network.js)

### Summary
`gf_list_del`'s double-free frees the same list node twice, corrupting memory. The closest reachable analog in `ocore` is in `handleSavedPrivatePayments()`'s `validateAndSave` closure, where a caught exception path fails to `return`, causing the same DB row / async-iteration slot to be finalized (deleted and its completion callback `cb()` invoked) twice — once in the `catch` branch and again inside `privatePayment.validateAndSavePrivatePaymentChain`'s `ifOk`/`ifError` handlers.

### Finding Description
In `network.js`, `handleSavedPrivatePayments()` iterates unhandled private-payment rows with `async.each` and calls `validateAndSave()` for each one: [1](#0-0) 

If `objectHash.getBase64Hash(objHeadPrivateElement.payload, true)` throws (e.g. because the stored private-payment JSON payload contains a value that `getJsonSourceString`/`getBase64Hash` cannot serialize/hash deterministically), the `catch` block calls `deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb)` — which deletes the DB row and invokes `cb()` — but execution does **not** `return` out of `validateAndSave`: [2](#0-1) 

Control falls through to the code after the `catch` block, which still calls `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})`. Its `ifOk`/`ifError` handlers unconditionally call `deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb)` a **second time**: [3](#0-2) 

This is the double-free analog: the same `cb` (the per-item completion handle for `async.each`, analogous to a resource handle that should be released exactly once) is invoked twice for one item, and the same DB row is targeted for deletion twice. `deleteHandledPrivateChain` itself does not guard against double invocation: [4](#0-3) 

Unlike `mutex.js`'s `exec()`, which explicitly guards against double-release with `if (!bLocked) throw Error("double unlock?")`, there is no such guard here: [5](#0-4) 

Calling `cb()` twice for the same item breaks `async.each`'s internal completion accounting. In `async` (caolan/async), invoking an item's callback a second time can decrement/complete the internal counter prematurely, causing the final callback (`unlock()` and the `new_my_transactions`/`new_direct_private_chains` event emission) to fire before other items in the same batch have finished processing. In addition, `privatePayment.validateAndSavePrivatePaymentChain` still executes fully after the row has already been deleted from `unhandled_private_payments`, so a payment whose hash could not be computed can still be validated and saved into wallet/DB state and reported (`sendResult`, `eventBus.emit`) as `accepted`, alongside the earlier error notification for the same private element.

### Impact Explanation
Because the "saved_private" mutex lock can be released (`unlock()`) while sibling items are still mid-processing (early/duplicate completion of `async.each`), other queued `handleSavedPrivatePayments` invocations could begin operating concurrently on the shared `unhandled_private_payments` table and private-payment write paths outside of the intended serialization, risking inconsistent private-payment/private-chain state (partially processed vs. re-processed chains). Additionally, a private-payment chain that failed early sanity checks can still be pushed through `validateAndSavePrivatePaymentChain` and reported as accepted, potentially causing a private payment counterparty to have a chain marked "accepted" in the wallet/UI when its head could not even be hashed — a correctness/fund-accounting defect in the private-payment code path reachable purely by a private-payment counterparty sending a payload that trips the hashing exception.

### Likelihood Explanation
Reaching this path requires an unprivileged private-payment counterparty (or paired device) to send a private-payment payload whose head element cannot be deterministically JSON-hashed by `getJsonSourceString`, which is a narrow but externally-reachable input surface (data arrives via `unhandled_private_payments` rows populated from received/private-payment device messages). No special privileges or node/hub cooperation are required, only a malformed/edge-case payload from the payment counterparty.

### Recommendation
Add a `return` after the `deleteHandledPrivateChain` call in the `catch` block of `validateAndSave` in `network.js`, and add a completion guard (similar to `mutex.js`'s `bLocked` check) inside `deleteHandledPrivateChain` or at the `cb` call sites to make double invocation impossible/fail loudly, e.g.:
```js
catch (e) {
    console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
    if (ws)
        sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
    return deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
}
```

### Proof of Concept
1. As a private-payment counterparty, craft a private-payment chain whose head element's `payload` includes a value that makes `getJsonSourceString`/`getBase64Hash` throw (e.g. a value type not handled by the deterministic JSON-source-string serializer, or extremely deep/circular-like structures that trigger an internal error) and send it to the victim node so it is persisted into `unhandled_private_payments`.
2. Trigger `handleSavedPrivatePayments()` (called on normal private-payment processing flow) for that row.
3. Observe: `validateAndSave` enters the `catch` block, calls `deleteHandledPrivateChain(...)` (delete #1, `cb()` call #1), then falls through and calls `privatePayment.validateAndSavePrivatePaymentChain`, whose `ifOk`/`ifError` handler calls `deleteHandledPrivateChain(...)` again (delete #2, `cb()` call #2) — verifying the double completion/double delete and the premature `unlock()`/`new_my_transactions` firing relative to sibling items still in-flight in the same `async.each` batch.

Note: I could not fully trace `getJsonSourceString`'s exact throw conditions (its implementation in `string_utils.js` was not indexed in my search results), so the precise payload shape needed to trigger the exception is not verified end-to-end — this is a gap requiring a full Devin session with file access to `string_utils.js` to construct a concrete triggering payload.
