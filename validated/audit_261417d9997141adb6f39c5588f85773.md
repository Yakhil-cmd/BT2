### Title
Webhook signature is verified against the org derived from `repository.owner.login`, while every handler acts on the unrelated `repository.full_name`/`sha` fields - allowing a holder of one org's webhook secret to inject CI statuses / push syncs for a stack belonging to a different org - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The reported bug class is "a value is trusted/acted upon before/around a validation step that doesn't actually cover it, so the check and the action bind to different things." In `WebhooksController`, the field used to pick *which* HMAC secret validates the signature (`repository.owner.login`) is not the field the handlers use to determine *which* `Stack`/`Commit` the webhook payload is applied to (`repository.full_name`, `sha`). In a single-org deployment this gap is unreachable, but Shipit explicitly supports (`docs/setup.md`, `config/secrets.development.shopify.yml`) hosting multiple independent GitHub App installs — each with its own `webhook_secret` — inside one Shipit instance.

### Finding Description
`WebhooksController#verify_signature` picks the `GitHubApp`/secret to validate against using only the org name extracted from the untrusted body: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` resolves a distinct `GitHubApp` (and thus a distinct `webhook_secret`) per organization key in `secrets.github`: [3](#0-2) 

Once `verify_webhook_signature` passes (HMAC-SHA1 of the *entire* raw body against the secret belonging to whichever org the attacker put in `repository.owner.login`), `create` dispatches the *whole* JSON body to the event handlers unmodified: [4](#0-3) 

But the handlers never look at `repository.owner.login` again — they resolve the target `Repository`/`Stack`/`Commit` from other, independently-controlled fields in the same body:
- `PushHandler` uses `repository.full_name` (via `Handler#repository_name`) and `ref`/`after` to enqueue a sync for a matched `Stack`: [5](#0-4) [6](#0-5) 
- `StatusHandler` uses only `sha`/`state`/`description`/`target_url`/`context` to create a `Status` on **any** `Commit` row across the whole install matching that sha, with zero relation to which org's secret produced a valid signature: [7](#0-6)  and it is persisted verbatim via `Status.replicate_from_github!`: [8](#0-7) 

Because the HMAC signature is computed over the whole raw body, the field split does not by itself let an attacker with *no* secret forge anything. The break is specifically for an attacker who **legitimately controls one org's webhook_secret** (e.g. they operate their own GitHub org/App that is one of the configured `secrets.github` entries, or that secret has otherwise leaked for one tenant) in a multi-org Shipit install that also serves other, unrelated orgs' stacks. Such an attacker can freely author the entire JSON body — including `repository.owner.login` (set to their own org, so `verify_signature` selects *their* known secret and the HMAC check passes) and `repository.full_name`/`sha` (set to point at a *different* org's tracked repository/commit) — sign it correctly with their own secret, and have it processed as if GitHub itself delivered it for the victim repository. This equality that should hold — `organization whose secret authenticated the request == organization owning the repository being written` — is broken: the check authenticates org A, the mutation writes org B's `Stack`/`Commit`.

### Impact Explanation
Via `StatusHandler`, the attacker can inject arbitrary CI `Status` records (`state: success`, forged `context`) onto commits belonging to a stack/org they have no legitimate relationship with. `Commit#create_status_from_github!` → `add_status` schedules `ProcessMergeRequestsJob` when the new status is `pending`/`success`: [9](#0-8)  and `MergeRequest#all_status_checks_passed?`/`ProcessMergeRequestsJob` will merge a pending pull request once required statuses appear to pass: [10](#0-9) [11](#0-10) . This can produce an **unauthorized merge** on a victim repository the attacker does not control on GitHub, satisfying the Critical-impact bucket ("unauthorized deploy, rollback or merge"). Via `PushHandler`, the attacker can also force-enqueue `GithubSyncJob` for an arbitrary stack with an attacker-chosen `expected_head_sha`, though actual commit content is still pulled from the real GitHub API, limiting that particular vector to disruption rather than direct write.

### Likelihood Explanation
This is only reachable when a Shipit instance is configured with the multi-organization `github:` schema (explicitly documented and supported), and the attacker is the legitimate operator/holder of the webhook secret for one of the *other* configured organizations in that same instance. This is a real, supported multi-tenant configuration (see `docs/setup.md` "Using Multiple Github Applications" and `config/secrets.development.shopify.yml`), so the precondition is plausible for any shared/multi-org Shipit deployment, without requiring any Shipit session, ApiClient token, or GitHub write access to the victim repository.

### Recommendation
After selecting the `GitHubApp`/secret to verify against, cross-check that the same organization also owns the repository the payload claims to mutate (e.g., verify `repository.full_name.split('/').first` matches the `repository_owner` used to pick the secret, and that the resolved `Repository`/`Stack`'s configured organization matches the authenticating org) before invoking any handler. Handlers should reject payloads whose target repository's organization does not match the organization whose secret validated the signature.

### Proof of Concept
1. Configure Shipit with two GitHub orgs, `attacker-org` (secret known to the attacker) and `victim-org` (hosting a tracked `Stack`/`Commit`), per the multi-org schema in `docs/setup.md`.
2. Attacker crafts a `status` event body:
```json
{
  "sha": "<sha-of-a-real-commit-on-victim-org's-tracked-stack>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/some-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org-webhook-secret, raw_body)` and POSTs to `/github_hooks` (or the mounted webhooks endpoint).
4. `verify_signature` calls `Shipit.github(organization: 'attacker-org')` and validates successfully because the attacker used their own known secret. [1](#0-0) 
5. `StatusHandler#process` matches `Commit.where(sha: params.sha)` — the victim commit — and creates a forged `success` `Status` on it, with no re-check of `attacker-org` vs. the commit's actual owning stack. [12](#0-11) 
6. If this makes all required statuses pass on a queued merge request, `ProcessMergeRequestsJob` merges the victim's pull request.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end

    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?
      end

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end
    end
