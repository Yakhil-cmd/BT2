### Title
`provision?` operator-precedence bug bypasses `review_stacks_enabled` gate for `prevent_with_label` (and `allow_with_label`) - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`OpenedHandler#provision?` uses `repository.review_stacks_enabled && repository.provisioning_behavior_allow_all? || (...)` where Ruby's operator precedence makes `&&` bind before `||`. This means `review_stacks_enabled` only gates the `allow_all?` disjunct, not the `allow_with_label?` or `prevent_with_label?` disjuncts, so a repository with `review_stacks_enabled == false` still auto-provisions a review stack whenever its `provisioning_behavior` is `prevent_with_label` and the PR has no matching label (the default case for any PR that omits the label).

### Finding Description
The binding the code is supposed to enforce is: `review_stacks_enabled == true` gates *all* provisioning behaviors, i.e. `provision? == review_stacks_enabled && (allow_all? || (allow_with_label? && label) || (prevent_with_label? && !label))`. The actual code at [1](#0-0)  is:

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

Because `&&` has higher precedence than `||` in Ruby, this parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && label) || (prevent_with_label? && !label)`. The last two disjuncts are entirely independent of `review_stacks_enabled`. So for a repository configured with `provisioning_behavior: prevent_with_label` and `review_stacks_enabled: false`, any pull request opened without the provisioning label makes `provision?` return `true`.

Attacker's exact action: open a pull request (or push one from a fork) against a repository configured with `provisioning_behavior_prevent_with_label` and `review_stacks_enabled == false`, with no labels applied — the default state of any newly opened PR before a maintainer labels it. `respond_to_pull_request_opened?` at [2](#0-1)  only checks `params.action == "opened" && provision?`, so no other guard blocks this. `process` then calls `ReviewStackAdapter#find_or_create!` [3](#0-2) , which calls `create!`, persisting a `Shipit::Stack` with `branch: params.pull_request.head.ref` (the attacker-controlled branch) and enqueuing it via `Shipit::ReviewStackProvisioningQueue.add(stack)` [4](#0-3) . This eventually drives a provisioning `Task` that checks out and runs commands from the attacker's branch/`shipit.yml`.

None of the existing guards catch this: `respond_to_pull_request_opened?` doesn't independently check `review_stacks_enabled`; it delegates entirely to the buggy `provision?`. The `ReopenedHandler#unarchive?` method at [5](#0-4)  has the identical bug. By contrast, `LabeledHandler#respond_to_label_change?` and `UnlabeledHandler#respond_to_label_change?` correctly AND `repository.review_stacks_enabled` as a separate top-level condition (`repository.review_stacks_enabled && (archive? || unarchive?)`), so only `OpenedHandler` and `ReopenedHandler` are affected.

### Impact Explanation
An attacker who can open (or reopen) a pull request against any repository configured with `provisioning_behavior: prevent_with_label` — regardless of whether that repository's maintainer ever enabled review stacks (`review_stacks_enabled == false`) — can force Shipit to create a `Shipit::Stack` record and enqueue it for provisioning. This leads to task execution (`shipit.yml` steps) against a repository/branch that was never authorized for dynamic provisioning, i.e., unauthorized stack creation and command execution — matching the Critical category "a payload for one repository mutating another's stack ... or an unauthorized deploy". It is repeatable against any repository sharing this misconfiguration and does not require the label at all (the default state of a fresh PR).

### Likelihood Explanation
Preconditions: the target repository must have `provisioning_behavior == prevent_with_label` set (an intentional, documented, valid configuration per `docs/review_stacks.md`) while `review_stacks_enabled == false` (e.g., an operator disabled review stacks temporarily, or configured the behavior before flipping the enable checkbox, or the settings independently toggled at different times — plausible since they're separate form fields [6](#0-5) ). No label is needed — this is the default unlabeled state of a PR, so attacker cost is simply opening a normal pull request. This is fully repeatable and requires zero special privileges beyond opening a PR.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates the entire expression:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
      (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
      (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Apply the same fix to `ReopenedHandler#unarchive?`.

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`, add:
```ruby
test "does not create stacks for repos with review_stacks disabled even when prevent_with_label and no label present" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = []

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Before the fix, `assert_no_difference` fails because `Shipit::Stack.count` increases by 1, proving `review_stacks_enabled == false` (left side of the intended binding) does not equal the effective gate applied (right side, which is always `true` on this branch) for the `prevent_with_label` path.
