### Title
Missing quorum enforcement and unbounded `threshold_size` system vote can disable the anti-spam oversize fee network-wide - (File: `main_chain.js`, `validation.js`, `storage.js`)

### Summary
`ocore` implements an on-chain governance mechanism (`system_vote` / `system_vote_count` messages) that lets any address vote, weighted by its byte balance, to set network-wide parameters, including `threshold_size`, which directly controls the anti-spam "oversize fee" charged on large units. Unlike the report's `Proposal.sol`, quorum here is neither a fixed minimum share of total supply nor is it enforced as a hard requirement — the code merely expands the voting time window until an arbitrary self-referential condition is met, and for `threshold_size` there is no upper bound at all, unlike its sibling parameters (`base_tps_fee`, `tps_interval`, `tps_fee_multiplier`) which all have explicit maxima. This mirrors issues #1 and #2 of the external report (no minimum votes for quorum, no upper bound on a governance-adjustable parameter).

### Finding Description
Any unpriviledged unit author can post a `system_vote` message with `subject: "threshold_size"`. Validation only requires it to be a positive integer ≥ 1000, with **no upper bound**: [1](#0-0) 

Compare this to the numerical votes for `base_tps_fee`, `tps_interval`, and `tps_fee_multiplier`, which are explicitly capped: [2](#0-1) 

The vote is counted in `countVotes()` in `main_chain.js`. Quorum is handled by an ever-expanding time window that stops either when a share of `SYSTEM_VOTE_MIN_SHARE` (10%) of `TOTAL_WHITEBYTES` has voted, **or** when the window has been expanded all the way back to the parameter's activation timestamp — whichever comes first. There is no hard failure or minimum-participation requirement; whatever votes exist in that window are used regardless of how small their total weight is relative to the network: [3](#0-2) 

For numerical subjects like `threshold_size`, the outcome is just the (weighted) median of whatever votes were cast within that window: [4](#0-3) 

This value becomes the new `system_vars.threshold_size`, and is used by `getOversizeFee()` to decide whether a unit must pay any anti-spam fee for its size: [5](#0-4) 

If `threshold_size` is voted to an extremely large value (nothing bounds it, e.g. `Number.MAX_SAFE_INTEGER`), then `size <= threshold_size` will always hold true for realistic unit sizes, so `getOversizeFee()` returns `0` for every unit on the network, permanently disabling the byte-size-based anti-spam fee that the protocol relies on to discourage oversized units and AA-generated bloat.

### Impact Explanation
`threshold_size` gates the oversize fee mechanism used both for regular payments and AA-generated response units (`aa_composer.js`, `inputs.js`, `composer.js`, `wallet.js` all call `getOversizeFee`/reference `threshold_size`). Disabling this fee removes the economic disincentive against posting maximally-sized (up to `MAX_UNIT_LENGTH`), storage-heavy units and AA triggers/responses. Since posting a `system_vote` requires no special privilege — only stake weighted by non-privileged byte balances that choose to participate within the auto-expanding window — an attacker (or small colluding minority relative to the *entire* supply, since quorum is not measured against total supply but only against participating voters) can push `threshold_size` to an unbounded value. This can be abused to flood the network with large units without paying the intended fee, degrading the network's ability to process/confirm units economically (storage growth, node resource exhaustion) — a network-availability class impact.

### Likelihood Explanation
Reachability is straightforward: any address with a nonzero byte balance can post a `system_vote` unit for `threshold_size`; no owner-only or hub-only privilege is required, and there's no `SET_PARAM_ROLE`-style gate as in the reported contract. The likelihood of a *successful* attack depends on the attacker/colluders' ability to dominate the voting pool during the expanding window (not the entire token supply, since the loop's quorum check is a soft heuristic that terminates regardless), which is a lower bar than obtaining majority of total supply. The absence of any upper bound (unlike the three sibling numerical votes, which are all explicitly capped) indicates this is an oversight rather than a deliberate design choice, strengthening confidence this is a real gap.

### Recommendation
1. Add an explicit upper bound to `threshold_size` in the `system_vote` validation switch in `validation.js` (mirroring the caps already present for `base_tps_fee`, `tps_interval`, and `tps_fee_multiplier`), chosen to keep the oversize-fee curve meaningful (e.g., bounded relative to `MAX_UNIT_LENGTH`).
2. Make the quorum check in `countVotes()` (`main_chain.js`) a hard requirement rather than a soft loop terminator — e.g., require a minimum absolute share of `TOTAL_WHITEBYTES` to have voted before applying a new value, and otherwise keep the previous value in effect instead of accepting whatever was collected once the window is exhausted.

### Proof of Concept
1. An attacker (or a set of colluding addresses) that controls a sufficient portion of the *actively voting* byte balance posts a `system_vote` unit: `{app: 'system_vote', payload: {subject: 'threshold_size', value: 9007199254740991}}` — this passes validation since only a lower bound (`>= 1000`) is enforced (`validation.js:1884-1892`).
2. A `system_vote_count` unit for `threshold_size` is posted/triggers counting; `countVotes()` computes the weighted median of the votes present in the (self-terminating) time window and stores this huge value into `system_vars` (`main_chain.js:1878-1910`).
3. From this point on, `storage.getOversizeFee()` returns `0` for every unit whose size is below the new `threshold_size` (`storage.js:1162-1165`), i.e., effectively for all realistically-sized units, permanently disabling the byte-size anti-spam fee network-wide until a subsequent vote lowers it again (which faces the same weak-quorum problem).

function getOversizeFee(objUnitOrSize, mci, bAA) {
	let size;
	if (typeof objUnitOrSize === "number")
		size = objUnitOrSize; // must be already without temp data fee
	else if (typeof objUnitOrSize === "object") {
		if (!objUnitOrSize.headers_commission || !objUnitOrSize.payload_commission)
			throw Error("no headers or payload commission in unit");
		// AA-generated units pay the oversize fee based on the unit size excluding its payment messages to avoid swelling the fee while spending dust outputs
		const payload_commission = (bAA && mci >= constants.pemCurvesFixMci)
			? objectLength.getTotalPayloadSize({ ...objUnitOrSize, messages: objUnitOrSize.messages.filter(message => message.app !== 'payment') })
			: objUnitOrSize.payload_commission;
		size = objUnitOrSize.headers_commission + payload_commission - objectLength.getPaidTempDataFee(objUnitOrSize);
	}
	else
		throw Error("unrecognized 1st arg in getOversizeFee");
	const threshold_size = getSystemVar('threshold_size', mci);
	if (size <= threshold_size)
		return 0;
	return Math.ceil(size * (exp(size / threshold_size - 1) - 1));
}
