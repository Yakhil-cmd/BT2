### Title
Unvalidated `amount` in the previous private-chain element causes an uncaught `throw` and daemon crash during indivisible private-payment validation - ([File: validation.js])

### Summary
When validating a chain of private (fixed-denomination / indivisible) asset payments, `validatePaymentInputsAndOutputs` asserts `isPositiveInteger(src_coin.amount)` and `throw`s a hard, unguarded `Error` if it fails. `src_coin.amount` is populated in `indivisible_asset.js` directly from the **not-yet-validated** previous chain element supplied by the sending counterparty, so a malicious private-payment counterparty can supply a bogus `amount` (0, negative, non-numeric, or missing) in an earlier chain element and crash the receiving node, analogous to CVE-2017-0375 where a malformed BEGIN cell hit an unguarded assertion (`tor_assert`) and killed the Tor daemon.

### Finding Description
`validatePaymentInputsAndOutputs()` in `validation.js` handles the `"transfer"` input case for private, fixed-denomination assets specially, because the source output can't be looked up in the database (the whole chain is validated before anything is saved): [1](#0-0) 

```
if (objAsset && objAsset.is_private && objAsset.fixed_denominations){
    if (!objValidationState.src_coin)
        throw Error("no src_coin");
    var src_coin = objValidationState.src_coin;
    if (!src_coin.src_output)
        throw Error("no src_output");
    if (!isPositiveInteger(src_coin.denomination))
        throw Error("no denomination in src coin");
    if (!isPositiveInteger(src_coin.amount))
        throw Error("no src coin amount");
```

`src_coin` is constructed in `indivisible_asset.js`'s `validatePrivatePayment()` for the `"transfer"` case, taking `amount` straight from `objPrevPrivateElement`, i.e. the element that is chronologically earlier in the chain and represented by `arrPrivateElements[i+1]`: [2](#0-1) 

Critically, `parsePrivatePaymentChain()` walks the chain with `async.forEachOfSeries` from index 0 upward, and for element `i` it passes `prevElement = arrPrivateElements[i+1]` — which has **not yet been through `validatePrivatePayment()`** at the time it is used to build `src_coin` for element `i`: [3](#0-2) 

So the only checks performed on the previous element's hidden output before its `amount` is trusted are `isNonemptyObject(objPrivateElement.output)` and the output-hash check on the *revealed* output object — neither of which constrains the `amount` field inside `payload.outputs[input.output_index]` of the *unrevealed* previous element. An attacker fully controls this JSON blob (it's their own private element in the chain they are sending), so they can set `amount` to `0`, a negative number, a string, or omit it entirely.

This reaches an ordinary (non-hub, non-operator) actor: private payments arrive over the wire via `network.js`'s `handleOnlinePrivatePayment()`, which forwards straight into `private_payment.js` → `indivisible_asset.js`: [4](#0-3) [5](#0-4) 

The resulting `throw` happens synchronously inside a `db.query`/`async.forEachOfSeries` callback with no enclosing `try/catch`, so it becomes an uncaught exception. `network.js` explicitly re-throws inside its `uncaughtException` handler to terminate the process: [6](#0-5) 

### Impact Explanation
Any private-payment counterparty (a normal wallet/device sending a legitimate-looking private chain for a fixed-denomination private asset) can remotely crash the recipient's ocore-based node/hub process. This is a full daemon-exit denial of service, matching the "no impact rejection" bar because it directly halts the ability of the targeted node to process further units/payments until restarted — the same bug class and impact as CVE-2017-0375 (malformed input → unguarded assertion → daemon exit).

### Likelihood Explanation
High likelihood: it requires no special privileges, no network position, and no cryptographic break — only crafting a JSON private-element chain with an invalid `amount` in a non-head element referenced by a `"transfer"` input, and sending it as a normal private payment to any peer/wallet that uses a private fixed-denomination (indivisible) asset. No signature over the hidden `amount` field is checked before it is trusted for `src_coin`.

### Recommendation
- In `indivisible_asset.js`’s `validatePrivatePayment()`, validate `prev_hidden_output.amount` (and other fields taken from `objPrevPrivateElement`) with `isPositiveInteger` *before* using it to populate `objValidationState.src_coin`, and return `callbacks.ifError(...)` instead of relying on downstream code.
- In `validation.js`, replace the `throw Error(...)` assertions guarding `src_coin` in `validatePaymentInputsAndOutputs` with `return callback(...)` unit/joint errors, so malformed/incomplete state produced by attacker-controlled data results in a graceful validation failure rather than a process crash.
- More generally, audit all `throw` statements reachable from externally-supplied unit/private-payment data (this file has many) and convert unrecoverable invariant violations that can be triggered by remote input into regular validation errors.

### Proof of Concept
1. Attacker sends a private (indivisible/fixed-denomination) asset payment chain (`arrPrivateElements`) to a victim wallet/hub via the normal `private_payment` P2P message, handled by `network.js`’s `handleOnlinePrivatePayment` → `private_payment.js` → `indivisible_asset.js`.
2. The chain has ≥2 elements. The tail (chronologically earliest, index `n-1`) is a valid `"issue"` element. The element immediately after it in time (index `n-2`, i.e. `objPrevPrivateElement` for the element being validated at index `n-2`) has, inside its `payload.outputs[output_index]`, an `amount` field set to `0` (or omitted, negative, or a string) while everything else about it (output_hash, blinding) is crafted to pass the earlier `expected_output_hash` check for whichever element it's the "current" element for.
3. When `parsePrivatePaymentChain` validates the element at index `n-3` (the one whose input transfers from the tampered element), `validatePrivatePayment` builds `objValidationState.src_coin.amount = prev_hidden_output.amount` (the tampered `0`/invalid value) without validating it.
4. `validation.validatePayment` → `validatePaymentInputsAndOutputs` reaches the `"transfer"` branch for the private fixed-denomination asset, evaluates `isPositiveInteger(src_coin.amount)` as `false`, and executes `throw Error("no src coin amount")`.
5. The uncaught exception propagates to `network.js`’s `process.on('uncaughtException')` handler, which re-throws and terminates the node process — denial of service against the recipient.
