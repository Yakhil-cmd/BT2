## Title
Cross-repository / cross-organization commit-status forgery via unscoped SHA lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` updates commit statuses by looking up commits **globally by SHA only**, without any scoping to the repository the webhook actually originated from. This breaks the binding between "the GitHub organization/repository whose webhook signature was verified" and "the repository whose data gets written," allowing a validly-signed `status` webhook from one repository/organization to write CI status onto commits belonging to a *different* repository/stack whenever the same commit SHA exists in both (e.g., forked repositories, or repositories that share git history, which is a normal and common configuration for Shipit users deploying multiple downstream/forked stacks of the same upstream project).

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App configuration — and thus the HMAC secret used to validate the webhook — based on the repository owner/organization embedded in the payload: [1](#0-0) [2](#0-1) 

This establishes an implicit trust binding: *organization/repo A's secret authenticates payloads claiming to originate from repo A*. Handlers are expected to only act on data belonging to that same repository. Most handlers respect this by resolving `stacks`/`Repository` via `payload.dig('repository', 'full_name')`: [3](#0-2) 

and, e.g., `CheckSuiteHandler` correctly scopes lookups through `stacks` before touching commits: [4](#0-3) 

However, `StatusHandler` ignores repository scoping entirely and queries the `Commit` table globally by SHA: [5](#0-4) 

Because `Commit.where(sha: params.sha)` is not filtered by `stack`/`repository`, any commit in the entire Shipit installation whose SHA matches — regardless of which repository/stack it belongs to, and regardless of which organization's webhook secret was used to authenticate the request — will have `create_status_from_github!` invoked on it. This is exploitable whenever the same SHA exists in more than one tracked repository, which routinely happens with forks/mirrors of the same upstream project (a common Shipit use-case, since many teams add several `Repository`/`Stack` records that fork or mirror the same codebase).

The equality that should hold but is broken: `repository authenticated by the webhook signature == repository whose Commit records are written`. Before the fix this would require: `Commit.where(sha:).where(stack: stacks)` similar to `CheckSuiteHandler`.

### Impact Explanation
A GitHub webhook for repository/org A (validly signed with org A's webhook secret, requiring no privileged Shipit credentials — an attacker just needs to control CI or push a commit that produces a status event on a repo they have write access to) can create/replicate a "success" `Status` on a commit belonging to an unrelated `Stack` in a different repository/organization tracked by the same Shipit instance, as long as SHAs collide (fork scenario). Since `create_status_from_github!` feeds into `Commit#add_status`, which can trigger `ProcessMergeRequestsJob` and continuous-deployment logic (`stack.commits.last_deployed_commit`/CD checks throughout `deploys_test.rb`), this can result in an **unauthorized deploy** being triggered for a stack the attacker does not control, purely by forging a legitimate-looking status webhook for a repo they do control but that happens to share commit history with the victim's fork/repository. This satisfies the "unauthorized deploy" Critical-impact criterion without requiring any Shipit session, API token, or the target organization's webhook secret.

### Likelihood Explanation
Requires: (1) the attacker controls (or can push CI statuses to) any repository tracked by the same Shipit instance, and (2) a commit SHA collision with the victim stack's repository — which is not a hash-collision attack but simply exploiting the fact that forked/mirrored repositories share identical commit SHAs for identical history. This is a realistic, low-effort scenario for any Shipit deployment that tracks multiple stacks for forks of the same codebase (a supported and common configuration, as shown by the multi-org config support in `lib/shipit.rb`).

### Recommendation
Scope the `StatusHandler` lookup to the repository indicated by the payload, mirroring `CheckSuiteHandler`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
using the inherited `Handler#stacks` (which resolves `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))`), so a webhook can only affect commits belonging to the repository it was actually signed for.

### Proof of Concept
1. Shipit instance tracks two `Repository`/`Stack` records: `org-a/app` (upstream) and `org-b/app-fork` (a fork sharing full git history), each configured under Shipit's multi-org GitHub App schema with distinct `webhook_secret`s.
2. Attacker has push/CI access to `org-b/app-fork` (their own fork) and knows/controls its webhook secret (standard GitHub App webhook flow — no Shipit credentials needed).
3. Attacker (or their CI) sends a `status` event for commit SHA `abc123` (a commit shared by both forks) with `state: success`, signed correctly with `org-b`'s webhook secret.
4. `WebhooksController#verify_signature` validates the signature against `org-b`'s secret only — as intended.
5. `StatusHandler#process` executes `Commit.where(sha: 'abc123')`, which matches the commit belonging to `org-a/app`'s stack as well (same SHA, different repository), and calls `create_status_from_github!` on it.
6. If `org-a/app`'s stack has continuous deployment enabled and this status transitions the commit to a deployable state, a deploy for `org-a/app` is triggered — despite the request never being authenticated against `org-a`'s webhook secret.
