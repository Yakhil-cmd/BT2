### Title
Cross-organization signature confusion allows a secret-less org's webhook to rewrite a victim org's `PullRequest#title`/`body` - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/pull_request/edited_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and thus the webhook secret) to verify against using `repository.owner.login` from the untrusted payload, while `EditedHandler#process` resolves the `Repository`/`PullRequest` to mutate using the independent `repository.full_name` field from that same payload. Because these two fields are never checked for consistency, and `GitHubApp#verify_webhook_signature` trivially returns `true` when the selected org has no `webhook_secret` configured, an attacker can "verify" a forged payload under any secret-less configured org while naming an arbitrary victim repository/PR in `full_name`, overwriting that victim PR's `title`/`body`.

### Finding Description
The broken binding: `org_used_for_signature_verification == org_owning_pull_request_record_being_written` is assumed but never enforced.

- `org_used_for_signature_verification = params.dig('repository','owner','login')`, read in `repository_owner` [1](#0-0) , then used to pick the `GitHubApp` instance: `Shipit.github(organization: repository_owner)` [2](#0-1) .
- `GitHubApp#verify_webhook_signature` short-circuits to `true` when that org has no configured `webhook_secret`: `return true unless webhook_secret` [3](#0-2) . A multi-org config with a secret-less org is a supported/documented pattern, as shown in the fixture `test/dummy/config/secrets_double_github_app.yml` where both `OrgOne` and `OrgTwo` have `webhook_secret: # nil`.
- `org_owning_pull_request_record = params.repository.full_name` split on `/`, used independently by `EditedHandler#repository` → `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [4](#0-3) , which then locates the victim's `PullRequest` by `number` scoped to that repository and overwrites it: `pull_request.update(github_pull_request: params.pull_request) if pull_request.present?` [5](#0-4) .

Nothing in the request path checks that `repository.owner.login` (used to pick the verifying `GitHubApp`) matches the owner segment inside `repository.full_name` (used to pick the row to mutate) — they are two independent strings inside the same attacker-supplied JSON body, and `ExplicitParameters` schema in `EditedHandler` only requires `repository.full_name` to be present, not that it be internally consistent with anything else [6](#0-5) .

Exploit flow:
1. Attacker knows a configured Shipit GitHub org, `secretless-org`, that has no `webhook_secret` set (a legitimate multi-tenant configuration, as demonstrated by the shipped double-app secrets fixture).
2. Attacker knows/observes the `full_name` and PR `number` of a victim repository/PR tracked by a different, properly-secured org, `victim-org/victim-repo`.
3. Attacker POSTs to `/webhooks` with header `X-Github-Event: pull_request`, JSON body: `{"action":"edited","number":<victim PR number>,"repository":{"full_name":"victim-org/victim-repo","owner":{"login":"secretless-org"}},"pull_request":{...,"title":"ATTACKER STRING","body":"ATTACKER STRING",...},"sender":{"login":"attacker"}}`, with any/no `X-Hub-Signature` header.
4. `verify_signature` resolves `Shipit.github(organization: "secretless-org")`, whose `verify_webhook_signature` returns `true` unconditionally, so the request passes with `head(422)` never called [2](#0-1) .
5. `EditedHandler#process` runs, resolves `Repository` via `full_name` ("victim-org/victim-repo"), finds the victim's `PullRequest` by number, and overwrites `title`/`body` with attacker-controlled content.

`drop_unhandled_event` doesn't block this (pull_request is a handled event), `ExplicitParameters` doesn't cross-validate fields, and there's no model validation tying `PullRequest`/`Repository` writes back to the org that signed the request.

### Impact Explanation
A single unauthenticated HTTP POST lets an attacker overwrite the `title` and `body` of any tracked `PullRequest` belonging to any repository/org, as long as any one org in the Shipit deployment is configured without a `webhook_secret`. This is a cross-tenant write: the org that "authenticated" the request is not the org whose data is mutated. Since PR title/body can be rendered in the Shipit UI and potentially matched against merge-command regexes elsewhere in the app, this is a content-injection primitive into another tenant's records, repeatable against arbitrary repositories/PR numbers tracked by Shipit. This matches "a payload for one repository mutating another's stack, commit, task or team" — Critical.

### Likelihood Explanation
Preconditions: the Shipit instance must have at least one configured GitHub org/app without a `webhook_secret` (a supported configuration pattern, not a misconfiguration Shipit rejects) and must track the victim repository under a separate org. Given those, exploitation is a single crafted unauthenticated HTTP request with no secrets, sessions, or GitHub write access needed — trivially repeatable against any PR number in any tracked repository.

### Recommendation
Enforce that the org used to select/verify the webhook signature matches the org embedded in `repository.full_name` before dispatching to handlers — e.g., in `WebhooksController#verify_signature`/`#create`, reject the request (422) if `params.dig('repository','full_name')&.split('/')&.first&.downcase != repository_owner&.downcase`. Additionally, treat a secret-less org as "verification succeeded only for that org's own repos," not as a blanket bypass for arbitrary `repository.full_name` values.

### Proof of Concept
Add to `test/controllers/webhooks_controller_test.rb` (or a new test) using the existing `test/dummy/config/secrets_double_github_app.yml` multi-org, no-secret fixture:

```ruby
test "pull_request edited event verified under a secret-less org can rewrite a victim org's PullRequest" do
  # victim PR tracked under a different, properly configured org
  victim_pr = shipit_pull_requests(:review_stack_review) # belongs to org e.g. "shopify"
  original_title = victim_pr.title

  request.headers['X-Github-Event'] = 'pull_request'
  payload = JSON.parse(payload(:pull_request_opened))
  payload['action'] = 'edited'
  payload['number'] = victim_pr.number
  payload['pull_request']['title'] = 'ATTACKER STRING'
  payload['pull_request']['body'] = 'ATTACKER STRING'
  # keep repository.full_name pointing at the victim repo,
  # but claim ownership under a secret-less configured org
  payload['repository']['full_name'] = victim_pr.stack.repository.github_repo_name
  payload['repository']['owner']['login'] = 'orgone' # configured with webhook_secret: nil

  assert_equal 'orgone', payload.dig('repository', 'owner', 'login')
  refute_equal 'orgone', victim_pr.stack.repository.owner

  post :create, body: payload.to_json, as: :json
  assert_response :ok

  assert_equal 'ATTACKER STRING', victim_pr.reload.title
  refute_equal original_title, victim_pr.title
end
```

Binding assertion before the fix: `payload.dig('repository','owner','login')` ("orgone", secret-less) `!=` `victim_pr.stack.repository.owner` (the org that actually owns the mutated PR row), yet the write still succeeds — proving the divergence. After applying the recommended fix, the same request should return `422` and `victim_pr.reload.title` should remain unchanged.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
