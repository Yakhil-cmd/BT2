Confirmed: no normalization/validation exists anywhere in the codebase for the `action` field — `Rule.from_dict` at [1](#0-0)  passes `frontmatter.get('action', 'warn')` through unchanged, and `evaluate_rules` performs a strict case-sensitive comparison.

### Title
Case-sensitive `action` comparison in `RuleEngine.evaluate_rules` silently demotes intended-blocking rules to warning-only, allowing dangerous Bash/Edit operations to proceed - (File: plugins/hookify/core/rule_engine.py)

### Summary
`RuleEngine.evaluate_rules` classifies a matched rule as blocking only if `rule.action == 'block'` (exact lowercase match), while `Rule.from_dict` stores the frontmatter `action` value verbatim with no normalization. A rule file with `action: Block`, `action: BLOCK`, or `action: " block"` matches the rule's conditions (e.g. a dangerous `rm -rf` Bash pattern) but falls into the `warning_rules` branch, which only emits a `systemMessage` and never sets `hookSpecificOutput.permissionDecision: "deny"` — so the dangerous operation is allowed to execute.

### Finding Description
`Rule.from_dict` at [2](#0-1)  reads `action=frontmatter.get('action', 'warn')` directly from the parsed YAML frontmatter without lowercasing or validating the value. `RuleEngine.evaluate_rules` then checks `if rule.action == 'block':` at [3](#0-2)  to sort matched rules into `blocking_rules` vs `warning_rules`. Only `blocking_rules` triggers the deny path — for `PreToolUse`/`PostToolUse` events this returns `hookSpecificOutput.permissionDecision: "deny"` at [4](#0-3) ; for `Stop` events it returns `decision: "block"` at [5](#0-4) . Any non-exact-lowercase value (`Block`, `BLOCK`, ` block`, trailing/leading whitespace, etc.) falls through to the `warning_rules` branch at [6](#0-5) , which only returns a `systemMessage` and allows the tool call to proceed — the hook scripts (`pretooluse.py`, `posttooluse.py`, `stop.py`) print this result and always `sys.exit(0)`, so Claude Code treats the operation as permitted. Documentation and examples (README.md, hookify.md) consistently show lowercase `action: block`/`action: warn`, so a rule file with mixed-case `action` looks legitimate to a reviewer and to `/hookify:list`, which merely echoes the raw frontmatter field back into its table with no re-validation, per [7](#0-6) .

### Impact Explanation
This breaks the "deny means deny" invariant of the hookify blocking mechanism: a rule intended to block destructive Bash commands (`rm -rf`, `dd if=`, `mkfs`) or dangerous file edits silently degrades into a non-blocking warning due to a single case difference in a config value, with no error, log warning, or `/hookify:list` indication that the rule lost its enforcement power. This can be introduced via a malicious PR/commit that adds or edits a `.claude/hookify.*.local.md` file with `action: Block` (plausible typo or intentional sabotage) into a project relying on hookify for guardrails, causing dangerous operations that the user believed were blocked to execute unimpeded — a trust-boundary/approval-bypass style impact on the local protection mechanism.

### Likelihood Explanation
High feasibility: any actor able to add or modify a `.claude/hookify.*.local.md` file (e.g., via a merged PR, a shared/template repo, or an automated rule-generation flow) can trivially use `Block`/`BLOCK`/whitespace-padded variants instead of `block`. No privilege escalation is needed beyond normal content-contribution channels, and the bug is 100% deterministic and repeatable — it requires no timing or race condition, just a case mismatch in a YAML field.

### Recommendation
Normalize the `action` field when constructing `Rule` (e.g., `action=frontmatter.get('action', 'warn').strip().lower()` in `Rule.from_dict`), and/or make the comparison in `evaluate_rules` case-insensitive (`rule.action.strip().lower() == 'block'`). Additionally, validate `action` against the allowed set (`{'warn', 'block'}`) at load time and emit a visible warning (surfaced via `/hookify:list` and `load_rule_file`) for unrecognized values instead of silently treating them as `warn`.

### Proof of Concept
Unit test against `RuleEngine.evaluate_rules`:
```python
import pytest
from hookify.core.config_loader import Rule, Condition
from hookify.core.rule_engine import RuleEngine

@pytest.mark.parametrize("action_value", ["block", "Block", "BLOCK", " block", "block "])
def test_block_action_case_sensitivity(action_value):
    rule = Rule(
        name="block-dangerous-rm",
        enabled=True,
        event="bash",
        action=action_value,
        conditions=[Condition(field="command", operator="regex_match", pattern=r"rm\s+-rf")],
        message="Dangerous rm blocked!"
    )
    engine = RuleEngine()
    input_data = {
        "hook_event_name": "PreToolUse",
        "tool_name": "Bash",
        "tool_input": {"command": "rm -rf /important/data"}
    }
    result = engine.evaluate_rules([rule], input_data)
    if action_value == "block":
        assert result.get("hookSpecificOutput", {}).get("permissionDecision") == "deny"
    else:
        # BUG: case-varied 'block' values fail to deny, operation is allowed
        assert result.get("hookSpecificOutput", {}).get("permissionDecision") != "deny"
```
Expected result today: only `action_value == "block"` produces `permissionDecision == "deny"`; all case-varied/whitespace variants pass through as warnings, demonstrating the silent bypass.
