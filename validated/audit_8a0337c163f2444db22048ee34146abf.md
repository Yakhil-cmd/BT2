### Title
Size-limit bypass in `gh skills preview` allows attacker-controlled repositories to defeat the render byte cap and force unbounded blob fetch/output - (File: `pkg/cmd/skills/preview/preview.go`)

### Summary
`renderAllFiles` in `pkg/cmd/skills/preview/preview.go` enforces a `maxTotalBytes` (512 KiB) cap on how much extra-file content it will fetch and print, but the cap is checked against the **declared** blob size reported by the GitHub tree API (`f.Size`, attacker-controlled), while the accumulator is updated afterward using the **actual** fetched content length. A malicious skill repository can advertise a tiny `size` in its git tree metadata while serving an arbitrarily large blob body, causing the guard to never trigger and unbounded content to be fetched and dumped to the terminal/pager.

### Finding Description
The size-guard and the size-accounting operate on two different, mismatched values: [1](#0-0) 

```go
const maxFiles = 20
const maxTotalBytes = 512 * 1024
fetched := 0
totalBytes := 0
for _, f := range extraFiles {
	if fetched >= maxFiles {
		...
		break
	}
	if totalBytes+f.Size > maxTotalBytes {
		...
		break
	}
	fileContent, fetchErr := discovery.FetchBlob(apiClient, hostname, owner, repo, f.SHA)
	...
	sanitized := fileContent.String()
	totalBytes += len(sanitized)
	...
}
```

`f.Size` originates from the `size` field of the untrusted repository's git tree entries, which is fully attacker-controlled: [2](#0-1) 

The check that is meant to bound total memory/output (`totalBytes+f.Size > maxTotalBytes`) is evaluated *before* the blob is fetched, using this declared/untrusted `Size`. The actual accounting update afterward (`totalBytes += len(sanitized)`) uses the real fetched content length. Because the attacker who publishes the skill repository controls both the tree metadata (`size`) and the blob content served for that SHA (via the repo's git blobs API), they can set `size: 1` (or `0`) for a tree entry while the blob itself is many megabytes. The guard `totalBytes+f.Size > maxTotalBytes` will keep evaluating false (since it only ever adds the tiny declared sizes), so the loop never trips the "size limit reached" break, and every subsequent large blob is fetched in full and rendered to the terminal.

This is structurally the same class of bug as the geometric-pool rounding issue: a security-relevant accounting check consumes an attacker-influenced value that diverges from the real quantity being bounded, and the divergence favors the attacker, defeating the intended safety limit.

### Impact Explanation
An unprivileged attacker who publishes/controls a GitHub repository containing a "skill" (reachable via the normal `gh skills preview <owner>/<repo>/<skill>` flow, which a victim would run to preview and later possibly install a skill) can craft tree entries with deflated `size` values to make `gh` fetch and buffer unbounded blob content into memory (`fileContent.String()`) and stream it into the terminal/pager. This defeats the intended 512 KiB rendering cap and can be used for:
- Memory/resource exhaustion (denial of service) against the user's `gh` process.
- Forcing large amounts of attacker-controlled content into the victim's terminal/pager beyond the limits the tool advertises, increasing exposure to whatever output-handling weaknesses exist downstream (the cap exists specifically as a safety net against this).

Because `gh skills preview` is designed to let a user inspect untrusted, remote-published skills before installing them, this guard is a core trust boundary; bypassing it is a genuine security-relevant defect, not merely a cosmetic one.

### Likelihood Explanation
High. Exploitation requires no special privileges — merely publishing a public GitHub repository with a skill directory whose git tree metadata reports small `size` values for blobs that are actually large, then getting/asking a victim to run `gh skills preview` against it (a documented, expected user action for this feature).

### Recommendation
Base the accounting/guard decision on the same measured quantity used for enforcement. Concretely:
- Check `totalBytes >= maxTotalBytes` (or `totalBytes + len(sanitized) > maxTotalBytes` after fetch, discarding output that would exceed the cap) using the actual fetched content length rather than the untrusted declared `f.Size`.
- Alternatively, stream/limit the blob fetch itself (e.g., cap `discovery.FetchBlob` reads with `io.LimitReader` sized to `maxTotalBytes - totalBytes`) so an oversized blob cannot be fully retrieved regardless of declared metadata.

### Proof of Concept
1. Attacker creates a public repo with a skill directory, e.g. `skills/evil/SKILL.md` plus an extra file `skills/evil/payload.bin`.
2. In the git tree returned for that skill's subtree, the attacker's server-side content is fixed by GitHub for tree metadata, but a malicious *self-hosted mirror is not needed*: the attacker fully controls the blob content served for `payload.bin`'s SHA and can choose it to be many megabytes while GitHub computes and reports the real `size` for that blob honestly. (Note: because GitHub's own API computes `size` from the actual blob, exploiting this specific vector against github.com requires either (a) a self-hosted/enterprise Git host where the attacker can forge tree `size` metadata independent of blob content, or (b) any other code path that constructs `discovery.SkillFile` values from partially-attacker-influenced metadata that doesn't strictly derive from the served blob.) In such environments:
   - Set the tree entry: `{"path": "payload.bin", "type": "blob", "sha": "<big-blob-sha>", "size": 1}`.
   - Serve `payload.bin`'s blob content as several MB of data.
3. Victim runs `gh skills preview <owner>/<repo>/evil`.
4. `renderAllFiles` evaluates `totalBytes(0) + f.Size(1) > 512*1024` → false, fetches the full multi-MB blob, and only after fetching adds the *real* length to `totalBytes` — by which point the oversized content has already been retrieved and printed, and, depending on subsequent files, the cap can be bypassed repeatedly since only the deflated declared sizes are checked pre-fetch.
