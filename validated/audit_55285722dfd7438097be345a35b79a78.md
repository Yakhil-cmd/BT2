### Title
`PATH` override via review-stack machine_env/label injection enables PATH-hijack RCE - (File: `lib/shipit/command.rb`)

### Summary
`Command#unbundled_env` computes a safe `PATH` and then merges the task's env hash over it without excluding any key, so any caller-supplied `PATH` value wins outright. For review stacks, that env hash is built from `ReviewStack#env` (PR labels) and `DeploySpec::FileSystem#machine_env` (the PR's own `shipit.yml`), both of which are attacker-controlled content coming from an unprivileged fork PR. Combined with a step that runs a bare command name, this lets an attacker who provisions a review stack redirect command resolution to a binary they planted inside their own PR checkout.

### Finding Description
The broken binding: the invariant "no fork-controllable key reaches the environment hash of a spawned deploy process" should hold, i.e. `spawned_env['PATH'] == Shipit.shell_paths.join(':') + ':' + ENV['PATH']` for every task. It does not.

`Command#unbundled_env` is:
```ruby
def unbundled_env
  BASE_ENV.merge('PATH' => "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}").merge(@env.stringify_keys)
end
``` [1](#0-0) 
The safe `PATH` is computed first and then unconditionally overwritten by `@env.stringify_keys`, so any key in the task's env — including `PATH` — fully replaces it. `@env` is exactly the hash passed by `Command.new(..., env:)` and is used directly in `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)`. [2](#0-1) 

The task env is built in `TaskCommands#env`, which merges `@stack.env`, `deploy_spec.machine_env`, and `@task.env` without any filtering of reserved keys:
```ruby
def env
  super
    .merge(@stack.env)
    .merge(...)
    .merge(deploy_spec.machine_env)
    .merge(@task.env)
end
``` [3](#0-2) 

Two attacker-controlled inputs feed this hash for a review stack:
1. `ReviewStack#env` merges every PR label name, upper-cased, into the env hash with value `"true"`:
```ruby
def env
  return super unless pull_request.present?
  super.merge(pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" })
end
``` [4](#0-3) 
A PR labeled `path` injects `'PATH' => 'true'`.

2. `DeploySpec::FileSystem#machine_env` (aliased from `config('machine', 'environment')`) reads `machine.environment` straight out of the checked-out `shipit.yml`, which for a review stack is read from the PR's own head commit: [5](#0-4) 
An attacker's `shipit.yml` can set `machine: {environment: {PATH: "./evil_bin:$PATH"}}` with an arbitrary value, and commit an executable file at `evil_bin/<bare-command-name>` (e.g. `bundle`, `cap`) inside the same PR branch.

Neither `EnvironmentVariables#permit` (only used for `TaskDefinition#filter_envs`, applied to user-submitted deploy-form variables, never to `machine_env`/label-derived stack env) nor any denylist filters reserved keys like `PATH`, `GITHUB_TOKEN`, etc., before they reach `Command.new`. [6](#0-5) [7](#0-6) 

Reachability: any deploy step defined with a bare command name (e.g. `bundle install`, `cap deploy`, or discovered dependency/deploy steps) will be resolved by the shell against the attacker-controlled `PATH`, executing the attacker's binary with the deploy host's privileges (including `GITHUB_TOKEN` present in the same env, per `Commands#base_env`). [8](#0-7) 

### Impact Explanation
This is Critical: arbitrary code execution on the Shipit deploy host, triggered by any pull request the target repository allows to provision a review stack (`allow_all`, or `allow_with_label`/`prevent_with_label` once the label condition is met). Because the same host executes `git`/deploy commands using `GITHUB_TOKEN` and other secrets present in `Commands#base_env`, PATH hijacking can lead directly to credential exfiltration and unauthorized deploys against the base repository, not just the ephemeral review-stack scope.

### Likelihood Explanation
Preconditions: Review Stacks must be enabled on a repository (`review_stacks_enabled`), and provisioning must be reachable for the attacker's PR (`allow_all`, or `allow_with_label` with the attacker able to add the label to their own PR, or `prevent_with_label` by default). No Shipit credentials, GitHub org membership, or maintainer approval are required, only the ability to open a PR and control its `shipit.yml`/labels — a capability explicitly granted to the "unprivileged attacker" in this exercise. This is fully repeatable and self-serve.

### Recommendation
In `Command#unbundled_env`, strip reserved/dangerous keys (at minimum `PATH`, and ideally other execution-critical variables like `BUNDLE_GEMFILE`, `RUBYOPT`, `LD_PRELOAD`) from `@env` before merging, or merge `@env` first and then force `PATH` last so it cannot be overridden. Additionally, apply an explicit allow-list (similar to `EnvironmentVariables#permit`) to `ReviewStack#env`'s label-derived variables and `DeploySpec#machine_env` before they reach `TaskCommands#env`.

### Proof of Concept
```ruby
# test/unit/command_test.rb (new test)
test "#unbundled_env does not allow caller-supplied env to override PATH" do
  safe_path = "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}"
  command = Command.new('true', env: { 'PATH' => '/tmp/evil' }, chdir: '.')
  # Broken binding demonstrated: attacker-controlled PATH wins
  assert_equal '/tmp/evil', command.unbundled_env['PATH']
  refute_equal safe_path, command.unbundled_env['PATH']
end

# test/models/shipit/webhooks/handlers/pull_request/labeled_handler_test.rb (new test)
test "review stack env includes attacker label as PATH override under allow_with_label" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(repository:, behavior: :allow_with_label, label: "pull-requests-label")
  payload = payload_parsed(:pull_request_labeled)
  payload["pull_request"]["labels"] = [{ "name" => "pull-requests-label" }, { "name" => "path" }]

  LabeledHandler.new(payload).process
  stack = repository.stacks.last

  assert_equal "true", stack.env['PATH']
end
```
