### Title
Missing zero-address recipient check in `sui::balance::send_funds` / `sui::coin::send_funds` permanently strands funds sent to `@0x0` - (File: crates/sui-framework/packages/sui-framework/sources/balance.move)

### Summary
The external Surge report's root cause is an asymmetric validation: one setter (`setFeeMantissa`) enforces "if the value is non-zero, the associated address must not be `address(0)`", while the sibling setter (fee-recipient setter) has no equivalent check, letting the invariant be silently violated post-hoc and value routed to the null address. The Sui framework's address-balance ("funds accumulator") API has the same missing-invariant shape: `send_funds` accepts an arbitrary `recipient: address` with **no check that it is non-zero**, and nothing downstream can ever redeem funds credited to `@0x0`.

### Finding Description
`sui::balance::send_funds` and its `sui::coin::send_funds` wrapper forward directly into `sui::funds_accumulator::add_impl`, which credits the funds-accumulator entry for whatever `recipient` address is supplied, with no validation at all: [1](#0-0) [2](#0-1) 

The only way to ever get funds back out of the accumulator is `redeem_funds`, which consumes a `Withdrawal<T>`. A `Withdrawal` can only be constructed (outside of the object-funds path) for `WithdrawFrom::Sender` or `WithdrawFrom::Sponsor`, both of which are resolved from the **actual signer(s)** of a real transaction (`tx_context.sender()` / `tx_context.sponsor()`): [3](#0-2) [4](#0-3) 

`@0x0` is the reserved system address — it is only ever the `sender` of system transactions (e.g. `funds_accumulator`'s own `create_staking_rewards` gates on `ctx.sender() == @0x0`) and cannot correspond to a real keypair that could sign a user transaction as `WithdrawFrom::Sender`. Consequently, whatever gets merged into the `@0x0` accumulator slot via `send_funds` has no code path that can ever construct a matching `Withdrawal` to redeem it — the deposit is permanent and irrecoverable, structurally identical to fee shares being minted to `address(0)` in the Solidity report: the setter/entry point that moves value to a recipient never validates that the recipient is non-null, even though the framework elsewhere treats `@0x0` as a privileged/unreachable sentinel.

### Impact Explanation
Balance/Coin value routed to `@0x0` via `balance::send_funds` / `coin::send_funds` (directly, or transitively through any higher-level Move package built on the address-balance primitive — e.g. fee-splitting, referral-share, or payout logic that computes a recipient dynamically and doesn't special-case an unset/default address) becomes permanently unspendable SUI or token supply. This matches the allowed "unintended permanent burning below the 10B cap" / "permanent fund lock" High-severity impact class, since it is a state corruption reachable purely from unprivileged public input with no admin, validator, or governance involvement.

### Likelihood Explanation
Likelihood is limited by the fact that sending value to `@0x0` requires an explicit (or programmatically-derived) `recipient` argument equal to the zero address, which in the simplest case is self-inflicted user/dApp error (analogous to sending ETH to `address(0)`, generally treated as user error rather than a protocol bug). It becomes a more serious, third-party-affecting issue only when a Move package built on top of `send_funds` computes the recipient from external/attacker-influenced or uninitialized state (e.g., a default `address` field that was never set) and pays out user or protocol funds to it — the same "downstream setter never re-validates" pattern as the Sherlock report. No additional protections exist in the framework to catch this at the primitive layer.

### Recommendation
Add `assert!(recipient != @0x0, EInvalidRecipient)` (or equivalent) in `sui::balance::send_funds` (and transitively `sui::coin::send_funds`) / `sui::funds_accumulator::add_impl`, mirroring the non-zero-address invariant that already exists implicitly for withdrawal (`Sender`/`Sponsor` can never resolve to `@0x0`), so that deposits can never be made to an address from which they are structurally unredeemable.

### Proof of Concept
1. Build a PTB that creates a `Balance<SUI>` (e.g., via `coin::into_balance` on a split gas coin).
2. Call `sui::balance::send_funds<SUI>(balance, @0x0)`.
3. Execute the transaction — it succeeds, and the accumulator for `@0x0`/`SUI` is credited.
4. Attempt to construct any `FundsWithdrawalArg`/`Withdrawal<Balance<SUI>>` for owner `@0x0` from a normal user transaction — impossible, because `WithdrawFrom::Sender`/`Sponsor` always resolve to the real transaction signer(s), and no signer can be `@0x0`. The deposited value is permanently locked. [1](#0-0)
