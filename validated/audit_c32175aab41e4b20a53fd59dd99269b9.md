### Title
Webhook signature verification binds only the payload's `repository.owner`/`organization` login to a GitHub App config, not to the `repository.full_name` a handler acts on, allowing cross-organization forgery when any configured org lacks a `webhook_secret` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to verify a webhook against using `repository_owner`, a value read directly out of the unauthenticated request body [1](#0-0) [2](#0-1) . Signature verification itself is skipped entirely whenever that selected organization has no `webhook_secret` configured: `GitHubApp#verify_webhook_signature` returns `true` unconditionally in that case [3](#0-2) . Every event handler, however, resolves which `Stack`/`Repository`/`Commit` to mutate using a *different* payload field, `repository.full_name`, with no check that it belongs to the organization that was actually verified (or bypassed) [4](#0-3) [5](#0-4) .

### Finding Description
The equality the system implicitly relies on is:

`organization authenticated via repository_owner == organization owning the repository.full_name that gets written to`

This equality is never enforced. In a multi-org Shipit deployment (a documented, supported configuration — see `docs/setup.md` "Using Multiple Github Applications" and the shipped templates `config/secrets.development.example.yml` / `config/secrets.development.shopify.yml`, which both ship with `webhook_secret:` left blank per org) [6](#0-5) , an attacker can:

1. Send a POST to `/webhooks` with `X-Github-Event: status` (or `push`, `check_suite`, etc.) and set `repository.owner.login`/`organization.login` to any org configured in `Shipit.github` that has `webhook_secret` unset.
2. `verify_signature` looks up that org's `GitHubApp` and calls `verify_webhook_signature`, which returns `true` immediately because `webhook_secret` is blank — no HMAC check is performed at all [3](#0-2) .
3. The event is then dispatched to handlers using the full attacker-controlled JSON body. Handlers key entirely off `payload.dig('repository', 'full_name')` to find `Stack`s to act on [4](#0-3)  — this can point at a Stack belonging to a *completely different, properly-secured* organization, since there is no cross-check against the org used in step 2.
4. For the `status` event, `StatusHandler#process` creates a `Status` record with attacker-chosen `state` for any `Commit` matching the attacker-supplied `sha` in that unrelated stack [5](#0-4) .

### Impact Explanation
Creating a `Status` with `state: 'success'` triggers `Status#schedule_continuous_delivery` on create [7](#0-6) , and if that target stack has continuous deployment enabled, `Commit#state` becoming `'success'` is exactly the condition Shipit's own test suite documents as sufficient to enqueue a `ContinuousDeliveryJob` and create a new `Deploy` [8](#0-7) . Since `deployable?` gating is satisfied purely via commit statuses (`ci.require`) with no re-verification of who authenticated the webhook, this is a path from an unauthenticated request to an **unauthorized deploy** of a repository/organization the attacker does not control — matching the report's Critical impact class ("unauthorized deploy"). The equivalent applies to `push` webhooks (forcing `GithubSyncJob` runs against an unrelated stack) and `check_suite`/`membership` events.

### Likelihood Explanation
This requires no credentials, no session, and no GitHub App keys — only that the Shipit operator has configured more than one GitHub organization and left `webhook_secret` empty for at least one of them, which is the exact shape shown in the project's own example configs [9](#0-8) . `docs/setup.md` marks `webhook_secret` as "(optional)" [10](#0-9) , and the org selection used for verification (`repository_owner`) is fully attacker-controlled from the same unauthenticated payload the signature is supposed to cover.

### Recommendation
- Never allow `verify_webhook_signature` to return `true` when a secret is absent for an org that is *not* the org whose repository is actually referenced; at minimum, require `webhook_secret` to be present for every configured organization in multi-org mode, or reject webhooks for organizations without a configured secret instead of silently accepting them.
- After choosing `repository_owner` for verification, additionally assert that `payload.dig('repository', 'full_name')`'s owner matches `repository_owner` before dispatching to handlers, so the org that authenticated the webhook is provably the org whose data is mutated.

### Proof of Concept
1. Configure two orgs in `Shipit.github`: `secure-org` (has `webhook_secret` set) and `insecure-org` (no `webhook_secret`, as in the shipped templates).
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "organization": { "login": "insecure-org" },
  "repository": { "full_name": "secure-org/victim-repo", "owner": { "login": "insecure-org" } },
  "sha": "<victim commit sha with CD enabled>",
  "state": "success",
  "context": "ci/required"
}
```
3. `verify_signature` resolves `Shipit.github(organization: 'insecure-org')`, whose `verify_webhook_signature` returns `true` unconditionally (no secret) regardless of any/no `X-Hub-Signature` header.
4. `StatusHandler` creates a `Status(state: 'success')` on the commit belonging to `secure-org/victim-repo`, which — if that stack has `continuous_deployment: true` — enqueues `ContinuousDeliveryJob` and creates a `Deploy`, per the exact mechanics asserted in `test/models/commits_test.rb:233-243`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
