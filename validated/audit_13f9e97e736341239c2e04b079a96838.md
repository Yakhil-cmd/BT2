### Title
`StatusHandler` scopes status writes only by `sha`, letting a webhook authenticated for one GitHub organization mutate commits owned by another organization's stack - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits with a global `Commit.where(sha: params.sha)` query and never checks that the `repository` in the payload matches the stack/org that owns that commit. `WebhooksController#verify_signature` only proves that the request was signed with the `webhook_secret` of the organization named in the payload's own `repository.owner.login`/`organization.login` field, not the organization that owns the target commit. Since Git commit SHAs are content-addressed and identical commits are shared between a repository and any fork of it, an attacker who owns/administers a registered org can get GitHub to emit a genuine, validly-signed `status` event referencing a SHA that is also present in another org's stack (e.g., a shared ancestor commit from forking the victim repo), and `StatusHandler` will happily create/update a `Status` on that foreign commit.

### Finding Description
Broken binding: the equality required is `organization_that_signed(payload) == organization_that_owns(Commit.where(sha: params.sha))`. Tracing the code shows this is never enforced.

- `WebhooksController#verify_signature` resolves the signing org purely from attacker-controlled JSON: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0)  and then verifies the HMAC using `Shipit.github(organization: repository_owner)` [2](#0-1) . This only proves the request was signed by *some* org's secret matching whatever `repository_owner` the attacker put in the JSON; it does not bind that org to any specific commit/stack.
- `Shipit::Webhooks::Handlers::Handler` defines `repository_name`/`stacks` helpers that scope by `payload.dig('repository', 'full_name')` [3](#0-2) , but `StatusHandler` never calls `stacks` or `repository_name` at all.
- `StatusHandler#process` only requires `:sha` and `:state` in its schema (no `:repository` requirement) [4](#0-3)  and resolves target commits with an unscoped, global query: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [5](#0-4) .
- `Commit#create_status_from_github!` writes a `Status` and fires stack-level hooks (`Hook.emit(:commit_status, stack, ...)`, `stack.schedule_merges`) based solely on `commit.stack`, with no re-check of which org's webhook authenticated the request [6](#0-5) [7](#0-6) .

Exploit flow: the attacker registers/administers Org A (or any org already onboarded to Shipit) and forks a public repository whose stack lives under Org B in Shipit. Because Git commits are content-addressed, commits that exist in the upstream history (shared ancestors, or any commit the attacker cherry-picks/merges unchanged into their fork) retain the exact same SHA in both repos. The attacker triggers any GitHub action in their own fork that causes GitHub to send a `status` event for that shared SHA (CI status update, or a commit status API call they make on their own repo/commit). GitHub signs this webhook using Org A's real `webhook_secret`. `verify_signature` succeeds because `repository_owner` correctly resolves to Org A and the signature matches Org A's key - the check itself is not bypassed, it is simply checking the wrong binding. `StatusHandler` then updates the `Status` for every `Commit` row anywhere in the database with that SHA, including the one belonging to Org B's stack, without ever verifying that Org A is the owner of that commit/stack.

### Impact Explanation
A validly-authenticated webhook from Organization A results in a write (`Status` creation, `Hook.emit(:commit_status/deployable_status, stack, ...)`, and potentially `stack.schedule_merges` on `pending?`/`success?`) against Organization B's stack/commit, without Organization B's participation. This is a cross-tenant data/state mutation triggered by an org that never had signing authority over the affected repository, matching the "payload for one repository mutating another's stack/commit" critical-impact category. Because `stack.schedule_merges` can be triggered by a forged `success` status, this can also influence merge queue / continuous-delivery decisions for the victim stack (e.g., masking a still-failing/blocking check with a forged passing status), which can affect deploy eligibility for another tenant's stack.

### Likelihood Explanation
Preconditions: attacker administers any GitHub org that is already registered with Shipit (so a `webhook_secret` exists for it) and needs a target SHA that is shared between their fork and the victim repository's tracked commits - trivially available for any public repo the attacker forks, since ancestor/shared commits keep identical SHAs. No secrets, tokens, or elevated Shipit roles are required; the attacker never needs to know the `webhook_secret` value itself, because GitHub computes and sends the signature. The only "cost" is running a normal GitHub workflow (fork + trigger a status update) in a repo the attacker fully controls. This is repeatable against any stack that shares commit history with a repo the attacker can fork, which is broad given how forks/mirrors work on GitHub.

### Recommendation
`StatusHandler` (and any other handler using cross-tenant-identifying fields like `sha` alone) must scope lookups by the repository named in the payload, not just by `sha`. Use the existing `Handler#repository_name`/`stacks` helper to restrict the query, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)`, or add `requires :repository` to `StatusHandler`'s param schema and filter `Commit.joins(:stack).where(sha: params.sha, stacks: { repository_id: Repository.from_github_repo_name(params.repository.full_name)&.id })`, ensuring the org that signed the webhook (`repository_owner` used in `verify_signature`) matches the repository that owns the commit being mutated.

### Proof of Concept
Minitest plan under `test/controllers/webhooks_controller_test.rb` and/or `test/models/webhooks/handlers/status_handler_test.rb` (structure, not literal file changes):
1. Create two `Repository`/`Stack` pairs: `stack_a` under org `"attacker-org"`, `stack_b` under org `"victim-org"`.
2. Create a `Commit` under `stack_b` with `sha: "deadbeef..."`.
3. Stub `Shipit.github(organization: "attacker-org")` to return a `GithubApp`/`GithubHook` whose `verify_webhook_signature` returns `true` (simulating a real, validly-signed webhook from attacker-org).
4. POST to `/webhooks` with header `X-Github-Event: status` and JSON body: `{"repository": {"full_name": "attacker-org/some-fork", "owner": {"login": "attacker-org"}}, "sha": "deadbeef...", "state": "success"}`.
5. Assert equality-before: `repository_owner` resolved by the controller equals `"attacker-org"`, while the commit's true owner (`commit.stack.repository.owner`) equals `"victim-org"` - the two differ.
6. Assert response is `200 OK` (signature verification passes) and that `stack_b`'s commit now has a `Status` record with `state: "success"` created - i.e., Org A's signed request mutated Org B's commit, confirming the vulnerability. A fix should make this assertion fail (no status created, or a 4xx/no-op response) once the handler is scoped by repository.
