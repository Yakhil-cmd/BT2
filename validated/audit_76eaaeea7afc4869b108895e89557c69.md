### Title
CCMenuController#stack bypasses `stack_id` scoping, allowing any single-stack-scoped token to read every stack's CI status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::BaseController` defines a `stacks` scope that restricts lookups to `Stack.where(id: current_api_client.stack_id)` when the client is stack-scoped, and `stack` is defined as `stacks.from_param!(params[:stack_id])`. `Api::CCMenuController` overrides `stack` to call `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` relation, completely skipping the `stacks` scoping method and thus the `current_api_client.stack_id?` check.

### Finding Description
The intended binding is: `stack_requested ∈ Stack.where(id: current_api_client.stack_id)` must hold whenever `current_api_client.stack_id?` is true.

In `Api::BaseController`: [1](#0-0) 
the `stacks` method enforces this binding, and `stack` (the version used by every other API controller) delegates to it.

`Api::CCMenuController` redefines `stack` to bypass this entirely: [2](#0-1) 

`show` calls `stack` (the overridden version) and renders the CI status XML for whatever `stack_id` was supplied in the URL, with no comparison to `current_api_client.stack_id`: [3](#0-2) 

The only guard applied is `require_permission :read, :stack`, which only checks that the client's `permissions` array contains `"read:stack"` — it does not check `stack_id`: [4](#0-3) 

So a client created with `stack_id = A` and `permissions = ["read:stack"]` passes `require_permission!` for *any* `stack_id` in the URL, because that check never touches `stack_id` at all. The existing test suite for this controller only ever exercises a single stack (`shipit_stacks(:shipit)`) and never asserts scoping against a second stack, so the divergence is untested: [5](#0-4) 

**Attacker request**: `GET /api/ccmenu/<other_stack_id_or_slug>?token=<attacker's_token_scoped_to_stack_A>` — repeated for every known stack identifier/slug — returns 200 with that stack's CCMenu XML (build status, last build label/time, lock status) regardless of the attacker's `stack_id` scope.

Neither `verify_signature`, `force_github_authentication`, nor any model validator is in the reachable path here since this is a token-authenticated API action, and `authenticate_api_client` in CCMenuController only verifies the token is valid, not that it's scoped to the requested stack: [6](#0-5) 

### Impact Explanation
An attacker holding one legitimately issued, narrowly-scoped ApiClient token (scoped to a single stack, permission `read:stack`) can enumerate and read the CI/deploy status (build success/failure, last build label, timestamp, lock status) of every stack across every tenant on the Shipit instance, by iterating `stack_id`/slug values against `/api/ccmenu/:stack_id`. This is an unauthenticated-for-other-tenants read of stack state exposed via a token that should not have visibility into those stacks — cross-tenant information disclosure, matching the "High - unauthenticated read of stack state" impact category. It does not expose secrets or allow mutation, so it is not Critical, but it is a real, repeatable, per-request confidentiality break across tenant boundaries.

### Likelihood Explanation
Preconditions: attacker needs one valid ApiClient token scoped to any single stack with `read:stack` permission — this is a normal, low-privilege credential many integrations (e.g., CI badges) are issued. No GitHub secrets, session, or admin access needed. The attack is trivial to execute (a GET loop over `Stack` ids/slugs) and fully repeatable against arbitrary stacks with no rate limiting evaluated in this issue. Feasibility is high given only a single legitimately scoped token is required.

### Recommendation
Remove the `stack` override in `Api::CCMenuController` (or have it delegate to the inherited `stacks.from_param!(params[:stack_id])` from `BaseController`) so that the `current_api_client.stack_id?` scoping is applied consistently, matching all other API controllers.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb
test "a token scoped to one stack cannot read another stack's CCMenu status" do
  scoped_client = ApiClient.create!(
    creator: @user,
    name: 'scoped',
    stack: @stack, # scoped to shipit_stacks(:shipit)
    permissions: ['read:stack']
  )

  Shipit::Stack.find_each do |other_stack|
    next if other_stack.id == @stack.id

    get :show, params: { stack_id: other_stack.to_param, token: scoped_client.authentication_token }

    # Binding under test: other_stack.id ∈ Stack.where(id: scoped_client.stack_id) must be false,
    # so this must NOT return 200.
    assert_not_equal 200, response.status,
      "expected stack #{other_stack.id} to be inaccessible to client scoped to stack #{@stack.id}, got #{response.status}"
  end
end
```
This test iterates every `shipit_stacks` fixture with a client scoped to a single stack, and asserts non-200 (403/404) for stacks outside `client.stack_id`; with the current code, all iterations return 200, proving the bypass.
