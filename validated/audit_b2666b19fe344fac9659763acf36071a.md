### Title
Webhook signature verification is skipped for any organization with an unset `webhook_secret`, letting an unauthenticated attacker forge deploy‑triggering GitHub events - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` picks which organization's webhook secret to check based on an attacker-controlled field of the unauthenticated JSON body (`repository.owner.login`), and `GitHubApp#verify_webhook_signature` unconditionally accepts the request when that organization has no `webhook_secret` configured. Because `webhook_secret` is documented as optional and the engine explicitly supports multiple GitHub App configs (one per organization), any organization onboarded without a webhook secret becomes an open door: an attacker can forge `push`/`status`/`check_suite` events for any repository under that organization with no credentials at all, potentially triggering unauthorized deploys.

### Finding Description
`verify_signature` derives the org whose secret should be checked purely from the incoming payload: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` resolves the app config for that organization via `github_app_config`, and then `verify_webhook_signature` is called: [3](#0-2) 

Note the guard clause: `return true unless webhook_secret`. If the organization's config has no `webhook_secret` set, **any** signature (or no signature at all) is accepted. This is a supported, documented configuration state — the setup docs describe the webhook secret as "(optional)", and the engine's own multi-org test fixture shows organizations configured with an explicitly blank `webhook_secret`: [4](#0-3) [5](#0-4) 

Multi-organization resolution itself is a first-class feature of the engine: [6](#0-5) 

Once `verify_signature` passes, the actual event handler acts on the repository named in the very same attacker-controlled JSON body: [7](#0-6) 

The binding that is broken is: **the organization whose credential the signature check authenticates against == the repository the handler subsequently writes to**. Both sides are read from the same unauthenticated payload, and the "authentication" step degenerates to a no-op whenever that organization's secret is blank. There is no cryptographic tie between "this request really came from GitHub for org X" and "the org X is the one Shipit will act on behalf of" once `webhook_secret` is unset — verification silently becomes `true` regardless of the payload's authenticity.

### Impact Explanation
An attacker with no Shipit account, no `ApiClient` token, and no GitHub credentials can POST a crafted JSON body to `/webhooks` claiming `repository.owner.login` = an organization configured with a blank `webhook_secret`, and `repository.full_name` = any repository/stack tracked by Shipit under that organization. Because the signature check for that org is bypassed entirely, Shipit will process the forged `push`, `status`, or `check_suite` event as if GitHub sent it — updating commit status/deployability. Combined with `continuous_deployment` (`Stack.schedule_continuous_delivery` / `ContinuousDeliveryJob`), this can result in an **unauthorized deploy** of an attacker-chosen commit, which matches the Critical impact bar ("an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Likelihood depends on operational configuration: it requires at least one organization in the Shipit multi-org GitHub App setup to have no `webhook_secret`. This is realistic because (a) the setup docs explicitly mark the secret as optional, and (b) the repository's own test fixtures model exactly this configuration for multiple organizations, suggesting it's a supported and not-uncommon setup (e.g., a staging/secondary org added without going back through the full secret-provisioning checklist). No credentials, sessions, or tokens are required to exploit it — only network access to the public `/webhooks` endpoint.

### Recommendation
- Require `webhook_secret` to be present for every configured organization; fail closed (reject with 422) instead of returning `true` when it is absent, rather than only warning.
- Additionally verify that the organization used for signature verification is consistent with, and authorized to act on, the repository named in the payload before dispatching to handlers.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `OrgOne` (has `webhook_secret`) and `OrgTwo` (no `webhook_secret`, as in `test/dummy/config/secrets_double_github_app.yml`), each with repositories/stacks tracked by Shipit.
2. As an unauthenticated attacker, POST to `/webhooks` with header `X-Github-Event: status` and no (or a garbage) `X-Hub-Signature` header, body:
```json
{
  "sha": "<any commit sha tracked in a Shipit stack under OrgTwo>",
  "state": "success",
  "target_url": "https://ci.example.com/fake",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "OrgTwo" }, "full_name": "OrgTwo/some-repo" }
}
```
3. `verify_signature` calls `Shipit.github(organization: "OrgTwo").verify_webhook_signature(...)`, which returns `true` because `OrgTwo`'s `webhook_secret` is blank — no valid GitHub signature was ever required.
4. The forged status is recorded against the commit; if the corresponding required CI check now shows green and `continuous_deployment` is enabled, Shipit will auto-deploy that commit without any real GitHub event ever having occurred.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
