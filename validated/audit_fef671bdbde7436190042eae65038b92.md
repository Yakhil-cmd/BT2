### Title
Unbounded submodule/fetch processing under a shared `--sync-timeout` causes persistent sync denial - (File: main.go)

### Summary
git-sync's per-sync work (fetch, reset, worktree create, submodule init/update) all runs under a single `context.WithTimeout(ctx, *flSyncTimeout)` [1](#0-0)  that is threaded into every `git.Run` call, including `git submodule update --init [--recursive]` [2](#0-1) . There is no cap on the number or size of submodules, refs, or objects that a single upstream commit can introduce, so a party with push access to the tracked repo can commit content that makes one complete `SyncRepo` pass exceed `--sync-timeout` every single time, permanently blocking git-sync from ever completing another sync.

### Finding Description
`SyncRepo` performs `fetch` → `reset --soft` → `createWorktree` (`git worktree add`) → `configureWorktree` (checkout + submodule update) as one atomic unit before it publishes anything via the symlink [3](#0-2) . All of the underlying `git` invocations share the same `ctx`, which is bound by `*flSyncTimeout` (default 120s) [1](#0-0) [4](#0-3) .

The submodule step is unbounded: `git.submodules != submodulesOff` triggers `git submodule update --init [--recursive] [--depth N]` over however many `.gitmodules` entries exist in the fetched commit, with no limit on count, nesting depth (for `recursive`), or per-submodule size [5](#0-4) . This mirrors the reported bug class — a resource-bounded per-call operation (`processWithdrawals`, bounded by gas) can be starved by an attacker who inflates the amount of unbounded work (zero-value withdrawals) that must be processed before legitimate work can proceed. Here, the "amount of work" is the number/size of submodules (or fetched objects) in a single commit, and the "bounded resource" is `--sync-timeout` wall-clock time, shared by the whole `fetch`+`checkout`+`submodule` sequence with no ability to make partial, resumable progress.

If a single sync attempt cannot finish within `--sync-timeout`, the git subprocess is killed via `exec.CommandContext` when the context deadline passes, `Run` returns a `context.DeadlineExceeded` error [6](#0-5) , and `SyncRepo` returns an error without publishing anything [7](#0-6) . The outer loop then increments `failCount`, sleeps `waitTime`, and retries the entire sequence from scratch (fetch again, reset again, worktree again, submodule update again) [8](#0-7) [9](#0-8) . There is no incremental/resumable state across attempts — each retry redoes the same unbounded submodule work, so the outcome (timeout) repeats indefinitely.

### Impact Explanation
Because the offending commit becomes the new `FETCH_HEAD`/target ref, every subsequent sync attempt re-fetches and re-processes it, hitting the same timeout each time. This is a persistent, self-perpetuating denial of sync: the currently-published symlink (previous good state) is never advanced, and no future legitimate commit is ever synced either, since fetch always targets the current HEAD of the branch/ref which includes the malicious commit. If `--max-failures` is a finite (non-negative) value, git-sync will eventually call `os.Exit(1)` [10](#0-9) , crash-looping the sidecar container. This matches the "persistent sync denial" acceptance category.

### Likelihood Explanation
This requires an attacker capable of pushing a commit to the ref/branch that git-sync is configured to follow (an "attacker-pushed commit" scenario explicitly in scope). No privileged operator or leaked credentials are needed — only ordinary push/contributor access to the upstream repository, or the ability to get such a commit merged. Given `--submodules` defaults to `recursive` [11](#0-10) , the more dangerous variant (deep/wide submodule graphs) is the out-of-the-box behavior, increasing likelihood in any deployment syncing a repo with less-trusted contributors.

### Recommendation
- Do not treat `--sync-timeout` as a single unit spanning fetch, checkout, and (potentially recursive) submodule initialization; apply independent, smaller timeouts/limits to submodule operations, or bound the total number/depth of submodules processed per sync.
- Consider adding an explicit configurable limit on submodule count/recursion depth, and fail fast with a clear, actionable error rather than silently retrying the same unbounded work forever.
- On repeated timeout for the same target hash, consider surfacing a distinct "stuck ref" condition (rather than generic failure/backoff) so operators can intervene (e.g., pin `--ref` to a prior known-good hash) before `--max-failures` triggers a crash loop.

### Proof of Concept
1. Attacker (with push access to the tracked branch) commits a `.gitmodules` file referencing an extremely large number of submodules (or a small number of submodules pointing at very large/slow-to-clone repos), then pushes to the branch git-sync follows.
2. git-sync's next poll fetches the new commit as `FETCH_HEAD`/`remoteHash`, detects `changed = true`, and proceeds into `configureWorktree`, running `git submodule update --init --recursive` over all entries [2](#0-1) .
3. The combined fetch+checkout+submodule-update time exceeds `--sync-timeout` (default 120s) [1](#0-0) ; `exec.CommandContext` kills the in-flight git process and `Run` returns a deadline-exceeded error [6](#0-5) .
4. `SyncRepo` returns an error before `publishSymlink` is reached, so the `--link` target is never updated; `failCount` increments and the loop retries after `waitTime` [8](#0-7) [9](#0-8) .
5. Every retry re-fetches the same malicious commit and repeats the same unbounded submodule work, reproducing the timeout indefinitely — a persistent sync denial (and, if `--max-failures` is finite, an eventual process crash-loop via `os.Exit(1)`).
