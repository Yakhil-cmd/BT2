### Title
Re-running `configureWorktree` on the already-published worktree during process restart breaks the atomic-publish guarantee - (File: main.go)

### Summary
`git-sync`'s core safety contract is that the `--link` symlink only ever points at a fully-built, immutable worktree, and that in-place worktree checkout is never performed on a directory that is currently being served [1](#0-0) . `SyncRepo` violates this guarantee in one specific path: on the first sync after a process (re)start (`git.syncCount == 0`), it re-runs `configureWorktree` — which does `git reset --hard` and `git submodule update` — directly on the *current, already-published* worktree, not on a fresh isolated one. If this operation is interrupted (context timeout, OOM-kill, crash), the live, symlinked worktree is left partially checked out, and there is no mechanism to detect or repair that damage, mirroring the report's core theme: a failure/edge-case path exists where the system can end up in a bad state with no remediation.

### Finding Description
In `SyncRepo`, when `currentHash == remoteHash`, `changed` is `false`, and `newWorktree` is simply set to `currentWorktree` — the worktree the `--link` symlink currently points at [2](#0-1) . Despite `changed` being `false`, the code still calls `configureWorktree(ctx, newWorktree)` whenever `git.syncCount == 0`:

```go
if changed || git.syncCount == 0 {
    ...
    newWorktree := currentWorktree
    if changed {
        ... createWorktree ...
    }
    if err := git.configureWorktree(ctx, newWorktree); err != nil {
        return false, "", err
    }
``` [3](#0-2) 

`configureWorktree` performs `git reset --hard <hash> --` and, if submodules are enabled, `git submodule update --init [--recursive]` directly inside that worktree path [4](#0-3) . `syncCount == 0` is true on every fresh process start (e.g. container restart, crash-loop, rolling update) even when the on-disk state is already correct, so this branch runs against the *live, symlinked* worktree that consumers are actively reading from — not an isolated new worktree as the atomic-publish design intends.

If `git reset --hard` or `git submodule update` is interrupted mid-operation — via the per-sync `--sync-timeout` context deadline (`flSyncTimeout`), an OOM-kill, or a `SIGKILL` of the `git` subprocess — the live worktree is left with a mix of old and new files, or missing submodule content, while the `--link` symlink continues to point at it, unaware that the target has been mutated in place. `sanityCheckWorktree` (which only checks `dirIsEmpty`, `rev-parse HEAD`, and `fsck --connectivity-only`) is not invoked in this code path at all for the `changed==false` case, and even where it is invoked elsewhere in the file it is explicitly documented as insufficient: "this does not guarantee that the worktree has all the files checked out - git could have died halfway through and the repo will still pass this check" [5](#0-4) . There is no equivalent of `transferDebt`/insolvency-style compensation here — no re-validation, no rollback, and no repair mechanism for a worktree corrupted while already published.

### Impact Explanation
Consumers of the `--link` path (e.g., an Nginx pod, config-loader, or static site generator sidecar) can observe a partially-updated, internally inconsistent checkout for an unbounded period, since nothing detects or heals the corruption until a subsequent `changed` sync replaces the worktree wholesale. This is a "publishing wrong or partial content" outcome achievable purely from restart/timeout timing interacting with an attacker-controlled remote (e.g., a large or slow-to-materialize submodule tree designed to exceed `--sync-timeout`), without any special privileges beyond controlling the synced repository's content/size.

### Likelihood Explanation
Requires a process restart (common in Kubernetes: OOM, rolling update, crash-loop, node eviction) landing exactly at `syncCount == 0` while `changed == false`, combined with an interruption during `configureWorktree`. An attacker who controls the repository content can increase likelihood by making submodule initialization or checkout slow enough to collide with `--sync-timeout`, but the interruption also depends on external timing (restart cadence, OOM pressure), so likelihood is moderate rather than trivially reproducible on demand.

### Recommendation
Never mutate the worktree that `--link` currently points to. On process restart, treat `syncCount == 0` the same as any other reconciliation: only call `configureWorktree` on a newly created worktree (via `createWorktree`), verify it with a strengthened `sanityCheckWorktree` (one that also confirms submodules are fully initialized and the working tree matches `git status --porcelain`/`diff --quiet` against the target hash, not just `fsck --connectivity-only`), and only then atomically swap the symlink — exactly as is already done for the `changed == true` case.

### Proof of Concept
1. Start `git-sync` against a repo with a submodule/large tree tuned so that `git submodule update --init` takes longer than `--sync-timeout`.
2. Let the first sync complete normally so `--link` points at a live, correctly checked-out worktree.
3. Kill/restart the `git-sync` process (simulating a container restart) so `syncCount` resets to `0`, but `currentHash == remoteHash` on the next run.
4. On restart, `SyncRepo` re-enters the `git.syncCount == 0` branch and calls `configureWorktree` on `currentWorktree` (the currently-published worktree) [3](#0-2) .
5. Trigger a timeout/kill mid-`git submodule update` (or `reset --hard`) on that in-place run; the already-published worktree is now left partially checked out while `--link` still points at it, and no cleanup, sanity re-check, or repair mechanism exists to detect or fix this in the current code path.
