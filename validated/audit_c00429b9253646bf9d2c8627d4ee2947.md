### Title
Webhook signature is verified against the organization derived from `repository.owner.login`, but handlers act on the unrelated `repository.full_name` field, allowing cross-organization stack writes — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate a request against using the untrusted field `repository.owner.login` (or `organization.login`) from the JSON body itself. Once the signature check passes, every webhook `Handler` (push, pull_request, membership, etc.) instead selects the actual repository/stack to mutate using a *different* field from the same body, `repository.full_name`. No code anywhere checks that the two fields agree, so the "organization whose secret authenticated the request" and "the repository that gets written to" are never the same equality that the design implicitly assumes.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb` resolves the signing organization purely from payload content, before the signature has been verified: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization:)` looks up a distinct `GitHubApp` (and distinct `webhook_secret`) per configured organization key in `secrets.github` (multi-tenant mode, exactly as shown in `config/secrets.development.shopify.yml` with `somegithuborg` / `someothergithuborg`), via `lib/shipit.rb`: [3](#0-2) 

The actual signature check itself is: [4](#0-3) 

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```

Meanwhile, every `Handler` resolves the target repository/stack from a completely different key in the same request body: [5](#0-4) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`PushHandler`, `PullRequest::OpenedHandler`, `PullRequest::ReopenedHandler`, `PullRequest::LabelCapturingHandler`, etc. all independently re-derive `params.repository.full_name` and act on whatever `Repository`/`Stack` that resolves to, e.g.: [6](#0-5) 

Because `repository_owner` (used to pick the verifying secret) and `repository.full_name` (used to pick the write target) are two independent fields of the same attacker-supplied JSON body, and nothing cross-validates that `repository.full_name` belongs to `repository_owner`, the equality the system needs — `organization that authenticated == organization that owns the repository being written` — is never enforced in code.

### Impact Explanation
In a multi-tenant Shipit deployment (multiple organizations configured under `secrets.github`, as documented/sampled in `config/secrets.development.shopify.yml`), a request whose signature validates for organization A (either because the requester can produce a valid signature for A — e.g., A's `webhook_secret` is unset, hitting the `return true unless webhook_secret` bypass in `lib/shipit/github_app.rb:77` — or because the requester otherwise controls a valid signature for A) can carry a `repository.full_name` pointing at organization B's repository. The handler will then archive/unarchive stacks, create review stacks, or trigger a `GithubSyncJob`/deploy pipeline sync for organization B's stack, even though only organization A's identity was ever authenticated. This is a cross-repository/cross-tenant write performed by an entity that only "authenticated" for a different, unrelated organization.

### Likelihood Explanation
Exploitability depends on obtaining a valid signature for *any* onboarded organization whose secret can be forged or is unset — the code explicitly allows the latter (`return true unless webhook_secret`), which the shipped sample secrets file demonstrates as a normal configuration shape (`webhook_secret: # nil`). Once any one organization in a multi-org install is in that state, the missing cross-check turns it into a skeleton key for writing to every other organization's stacks in the same installation.

### Recommendation
After signature verification succeeds, re-derive `repository_owner` from the verified organization and require that `payload.dig('repository', 'full_name')` (and `payload.dig('organization', 'login')` for org-scoped events) actually belongs to that same organization before dispatching to any `Handler`. Reject the request (`head(422)`) on mismatch, and additionally disallow/alert on organizations configured with a blank `webhook_secret` in non-development environments.

### Proof of Concept
1. Configure `secrets.github` with two organizations, e.g. `orgA` (no `webhook_secret` set) and `orgB` (has a real stack/repository).
2. POST to `/webhooks` with:
   - `X-Github-Event: push`
   - Body: `{"repository": {"owner": {"login": "orgA"}, "full_name": "orgB/victim-repo"}, "ref": "refs/heads/main", "after": "<sha>"}`
   - Any (or missing) `X-Hub-Signature` header.
3. `WebhooksController#verify_signature` calls `Shipit.github(organization: "orgA")`, whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb:77`).
4. `PushHandler#process` runs using `payload.dig('repository', 'full_name') == "orgB/victim-repo"`, locating and syncing/deploying `orgB`'s stack — a write to an organization whose identity was never authenticated by this request.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
