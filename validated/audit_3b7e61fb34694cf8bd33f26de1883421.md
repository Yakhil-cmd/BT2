### Title
Creator fees can be permanently locked if the pool creator's associated token account becomes frozen/blacklisted - ([File: programs/cp-swap/src/instructions/collect_creator_fee.rs])

### Summary
`collect_creator_fee` and `collect_creator_fee_permissionless` always route accumulated `creator_fees_token_0`/`creator_fees_token_1` to the `pool_creator`'s associated token account, which is derived deterministically and cannot be redirected. If the mint's freeze authority (or a Token-2022 default-account-state/permanent-delegate style mechanism) blacklists that specific ATA or the `pool_creator` address, the transfer CPI reverts and the fee amounts remain permanently stuck in the pool vaults, exactly analogous to the reported `recoverERC20()` issue where funds are hard-coded to a single, non-redirectable recipient.

### Finding Description
Both instructions derive the destination account as an ATA owned by the immutable `pool_creator` field recorded in `PoolState` at pool creation: [1](#0-0) 

`collect_creator_fee_permissionless` similarly hard-codes the recipient to `pool_state.pool_creator`, only decoupling who pays for account creation, not who receives the funds: [2](#0-1) [3](#0-2) 

Both instructions call `transfer_from_pool_vault_to_user`, which uses `token_2022::transfer_checked`; if the destination ATA (owned by the frozen/blacklisted `pool_creator`) is frozen by the mint's freeze authority, or the mint enforces a deny-list via Token-2022 extensions, this call reverts: [4](#0-3) 

Because the entire instruction reverts on transfer failure, `pool_state.creator_fees_token_0`/`creator_fees_token_1` are never zeroed out, so the accrued fees remain locked in the pool's token vaults with no alternative path to withdraw them. `pool_creator` is set once at pool initialization and there is no `update_pool_creator`/`set_pool_creator` admin instruction found in the codebase to change the recorded creator address, so there is no way to redirect future collections to an unblacklisted destination — the funds are permanently stuck in the vault forever (they are not fully recoverable via `withdraw`, since `creator_fees_token_0/1` are tracked separately from LP-share ownership and only released via `collect_creator_fee*`).

By contrast, `withdraw()` lets the LP owner supply an arbitrary `token_0_account`/`token_1_account` (only constrained by mint, not by ownership of `owner`), so LPs can route around a frozen ATA — this is not affected. The creator-fee collection path has no such flexibility.

### Impact Explanation
This is a Medium-severity fund-freezing issue: creator trading fees (a portion of every swap, tracked per-pool in `creator_fees_token_0`/`_1`) accumulate indefinitely in the pool vault and become permanently unclaimable if the pool creator's token account for either vault mint is frozen or blacklisted by the mint's freeze/deny mechanism. This does not affect LP principal or protocol/fund fees (those have configurable recipients in `collect_protocol_fee`/`collect_fund_fee`), but it does affect all future creator-fee accruals for that pool once the creator's account is frozen, since it cannot be redirected.

### Likelihood Explanation
Likelihood is not high, similar to the reported analog: it requires the specific mint (token_0 or token_1 of the pool) to have a freeze authority (or Token-2022 permanent-delegate/default-frozen-state extension) that later blacklists the pool creator's address. Given Raydium CP Swap supports arbitrary Token-2022 mints with such extensions, this is a realistic configuration, but requires an external mint-authority action against the specific creator address.

### Recommendation
Add an instruction allowing the current `pool_creator` (or a designated authority) to update the `pool_creator` field in `PoolState`, or allow `collect_creator_fee`/`collect_creator_fee_permissionless` to accept a caller-specified beneficiary token account (guarded by an `onlyCreator`-style signer check similar to `recipient()`/`owner()` overrides suggested in the referenced report), so fees can be redirected to an unblacklisted account instead of being permanently locked.

### Proof of Concept
1. Pool is created with `token_0_mint` being a Token-2022 mint that has a freeze authority (or default-frozen-state extension) — this is permitted since the program accepts arbitrary Token-2022 mints via `token_0_program`/`vault_0_mint`.
2. Swaps accrue non-zero `creator_fees_token_0` in `PoolState`.
3. The mint's freeze authority freezes the creator's associated token account for `token_0_mint` (or, using default-account-state, all new ATAs for that owner start frozen).
4. Any call to `collect_creator_fee` or `collect_creator_fee_permissionless` attempts `transfer_from_pool_vault_to_user` into `creator_token_0`, which reverts due to the frozen destination account.
5. Since the transaction reverts, `pool_state.creator_fees_token_0` is never decremented, and there is no alternate instruction to redirect or reclaim these fees — they remain locked in `token_0_vault` indefinitely.

pub fn transfer_from_pool_vault_to_user<'a>(
    authority: AccountInfo<'a>,
    from_vault: AccountInfo<'a>,
    to: AccountInfo<'a>,
    mint: AccountInfo<'a>,
    token_program: AccountInfo<'a>,
    amount: u64,
    mint_decimals: u8,
    signer_seeds: &[&[&[u8]]],
) -> Result<()> {
    if amount == 0 {
        return Ok(());
    }
    token_2022::transfer_checked(
        CpiContext::new_with_signer(
            *token_program.key,
            token_2022::TransferChecked {
                from: from_vault,
                to,
                authority,
                mint,
            },
            signer_seeds,
        ),
        amount,
        mint_decimals,
    )
}
