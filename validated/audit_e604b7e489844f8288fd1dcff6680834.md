## Finding

### Title
Unauthenticated `device_address` routing hijack in shared-address definitions allows fund freezing for multi-sig wallets - (File: wallet_defined_by_addresses.js)

### Summary
The reported CVE (CVE-2021-27803) is a "corner case in peer addition" bug: wpa_supplicant added a peer entry to internal state based on an unauthenticated P2P provision-discovery request without validating that the request actually corresponds to the peer it claims, corrupting internal bookkeeping. The analogous pattern in `ocore` exists in the handling of the `new_shared_address` device message, where a *signing-path → device_address* routing table for a multi-signature address is populated from data supplied by an arbitrary paired correspondent, without verifying that the sender is actually one of the signers of that address or has any right to declare who "owns" a given signing path.

### Finding Description
A paired device (any correspondent in `correspondent_devices`, not necessarily a genuine co-signer of a shared/multisig address) can send a `new_shared_address` message that is routed to `wallet_defined_by_addresses.handleNewSharedAddress()`: [1](#0-0) 

`handleNewSharedAddress` validates that `body.address` is the chash160 of `body.definition`, and that each `signing_path`'s member address in `body.signers` matches the address found at that path inside the definition: [2](#0-1) 

However, it never verifies that the sending device (`from_address`) is actually the `device_address` claimed for any signing path, nor that `from_address` is even a party to the shared address at all. The `device_address` field of `body.signers` — which controls where future "sign" requests for that member/path will be routed — is accepted as-is and persisted: [3](#0-2) 

`determineIfIncludesMeAndRewriteDeviceAddress()` only rewrites the device address for signing paths whose member address is *my own* address; it does nothing to validate device addresses claimed for other (non-local) members of the multisig address: [4](#0-3) 

The insert into `shared_address_signing_paths` uses `INSERT OR IGNORE`, so if the shared address is *new* to the victim (has not been created locally yet), an attacker-supplied `device_address` for another member's signing path will be accepted and stored as-is: [5](#0-4) 

The comment in `approvePendingSharedAddress` explicitly documents that `device_address` is trusted as "where this signing key lives or is reachable through" and is used to forward signing requests, confirming that this field drives real signing/routing decisions rather than being purely informational: [6](#0-5) 

This mirrors the CVE's root cause: an entry describing "which peer/device is responsible for X" is added to persistent internal state on receipt of a single unauthenticated message, without cross-checking that the sender is authorized to make that claim.

### Impact Explanation
Since `shared_address_signing_paths.device_address` determines which device receives the `sign` request when composing a payment from a shared (multisig) address, an attacker who is merely a paired correspondent of the victim (e.g., after a normal pairing/chat interaction, not necessarily a co-owner of any wallet) can pre-register a shared address definition naming legitimate victims as co-signers but claiming that one member's signing key is reachable through the attacker's own device address. Because `INSERT OR IGNORE` protects only addresses already known locally, this works for any shared address the victim has not yet locally instantiated. When the victim later attempts to spend from that address, the signature request for the hijacked path is sent to the attacker's device instead of the legitimate co-signer, so the transaction can never be completed — permanently freezing funds sent to that shared/multisig address (denial of funds), and undermining consistent node state about a wallet's true co-signer set.

### Likelihood Explanation
The `new_shared_address` message is one of the subjects allowed to be processed without additional per-message capability checks beyond existing pairing (`handleMessageFromHub` dispatches directly to `walletDefinedByAddresses.handleNewSharedAddress`), and pairing itself is cheap and attacker-initiated (see `handlePairingMessage`, reachable via a pairing secret an attacker can obtain or via a permanent `'*'` pairing secret many wallets/services use). No cryptographic proof ties `device_address` to the actual signing key owner, only the address itself is checked against the definition. This makes the corner case directly reachable by any paired device without further privilege.

### Recommendation
- Require that `device_address` claims in `new_shared_address` be corroborated, e.g., only accept/update a `device_address` for a signing path from the party that legitimately owns that path (via a signed statement from the member address, or only via the offer/approval flow in `createNewSharedAddressByTemplate`/`approvePendingSharedAddress`, rather than the unauthenticated forwarded `new_shared_address` path).
- Reject `new_shared_address` messages from senders that are not already a `my_addresses`/cosigner correspondent for any signing path they are attempting to introduce, and require confirmation from the actual owner of each non-local member address before persisting its routing device.
- Consider requiring UI confirmation before persisting a brand-new shared address whose member device routing cannot be independently verified.

### Proof of Concept
1. Attacker device A pairs with victim device V (via a normal or permanent pairing secret).
2. Attacker crafts `arrDefinition` = `["and", [["address", V_ADDR], ["address", COSIGNER_ADDR]]]` where `V_ADDR` and `COSIGNER_ADDR` are addresses the attacker knows belong to the intended victim wallet participants (observable on-chain or via prior interaction).
3. Attacker computes `address = chash160(arrDefinition)` and sends device message `subject: "new_shared_address"`, `body: {address, definition: arrDefinition, signers: {"r.0": {address: V_ADDR, device_address: V_DEVICE}, "r.1": {address: COSIGNER_ADDR, device_address: ATTACKER_DEVICE}}}` to V.
4. `handleNewSharedAddress` passes all checks (address matches hash, per-path address matches definition) and calls `addNewSharedAddress`, persisting `ATTACKER_DEVICE` as the routing device for `COSIGNER_ADDR`'s signing path in V's `shared_address_signing_paths` table — before V ever learns the real shared address from the legitimate co-signer.
5. When V later tries to spend from `address`, the "sign" request for `r.1` is sent to `ATTACKER_DEVICE`, which never returns a valid signature, permanently blocking the multisig spend.

function determineIfIncludesMeAndRewriteDeviceAddress(assocSignersByPath, handleResult){
	var assocMemberAddresses = {};
	var bHasMyDeviceAddress = false;
	for (var signing_path in assocSignersByPath){
		var signerInfo = assocSignersByPath[signing_path];
		if (signerInfo.device_address === device.getMyDeviceAddress())
			bHasMyDeviceAddress = true;
		if (signerInfo.address)
			assocMemberAddresses[signerInfo.address] = true;
	}
	var arrMemberAddresses = Object.keys(assocMemberAddresses);
	if (arrMemberAddresses.length === 0)
		return handleResult("no member addresses?");
	db.query(
		"SELECT address, 'my' AS type FROM my_addresses WHERE address IN(?) \n\
		UNION \n\
		SELECT shared_address AS address, 'shared' AS type FROM shared_addresses WHERE shared_address IN(?)", 
		[arrMemberAddresses, arrMemberAddresses],
		function(rows){
		//	handleResult(rows.length === arrMyMemberAddresses.length ? null : "Some of my member addresses not found");
			if (rows.length === 0)
				return handleResult("I am not a member of this shared address");
			var arrMyMemberAddresses = rows.filter(function(row){ return (row.type === 'my'); }).map(function(row){ return row.address; });
			// rewrite device address for my addresses
			if (!bHasMyDeviceAddress){
				for (var signing_path in assocSignersByPath){
					var signerInfo = assocSignersByPath[signing_path];
					if (signerInfo.address && arrMyMemberAddresses.indexOf(signerInfo.address) >= 0)
						signerInfo.device_address = device.getMyDeviceAddress();
				}
			}
			handleResult();
		}
	);
}
