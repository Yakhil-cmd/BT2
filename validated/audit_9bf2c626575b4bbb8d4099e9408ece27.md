### Title
Webhook signature is verified against `repository.owner.login`/`organization.login` while the actual write target is selected from the unverified `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/organization config (and therefore which `webhook_secret`) to validate the incoming payload against using `repository_owner`, which is read from the JSON body itself (`repository.owner.login`, falling back to `organization.login`). Once the signature check passes, the payload is dispatched unmodified to event handlers, which independently resolve the target `Stack`/`Repository` using a *different* field of the same attacker-controlled body: `repository.full_name`. Because the field used to pick the verifying secret and the field used to pick the write target are not the same, and neither is bound to the other by the signature check, an organization that successfully authenticates a webhook is not necessarily the organization that owns the repository actually acted upon.

### Finding Description
Verification flow:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

The `github_app` (and thus which per-organization `webhook_secret` HMAC to check against) is looked up solely by `repository_owner`, a value taken straight from the unauthenticated JSON body. The HMAC itself only proves the payload was signed by *some* known organization's shared secret; it says nothing about which repository the payload's other fields refer to.

Once `verify_signature` passes, `create` dispatches the same raw, attacker-controlled `params` to handlers:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [2](#0-1) 

Handlers such as `PushHandler` resolve the actual repository/stack to act on using a completely different field, `repository.full_name`, not `repository.owner.login`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 
```ruby
def process
  stacks
    .not_archived
    .where(branch:)
    .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [4](#0-3) 

This is the trust-binding break the analog rules call for: "organization that authenticated" (`repository.owner.login`, used to pick the verifying secret) versus "repository that is written" (`repository.full_name`, used by the handler to pick the `Stack`/`Repository`). Nothing in `verify_signature` cross-checks that `repository.full_name` actually belongs to the organization identified by `repository_owner`. In a multi-organization Shipit deployment (`config/secrets.yml` supports one `webhook_secret` per organization, as documented in `docs/setup.md`), an attacker who controls (or has compromised) the GitHub App/webhook secret for their own, unrelated organization "attacker-org" can forge a payload where:
- `repository.owner.login` = `"attacker-org"` (satisfies signature verification, since that's the secret used to sign it)
- `repository.full_name` = `"victim-org/victim-repo"` (used by `PushHandler`/`Handler#stacks` to select the real target `Stack`)

Because the signature only proves "attacker-org" produced this payload, but the handler acts on whatever `full_name` says, the attacker can trigger `GithubSyncJob`/`stack.sync_github` (and, depending on which webhook events downstream handlers accept, other repository-scoped actions) against a `victim-org/victim-repo` stack they have no legitimate access to. [5](#0-4) 

### Impact Explanation
This crosses the "cross-repository writes" / "unauthorized deploy" bar from the Critical/High impact list: an attacker who only controls one organization's webhook secret (their own repository configuration, not a privileged credential to Shipit itself) can force sync/deploy-adjacent state changes (e.g. triggering `GithubSyncJob` for arbitrary target stacks, spoofing commit/check statuses, or manipulating membership/PR-driven flows) against stacks belonging to a different, victim organization that is also configured on the same shared Shipit instance — something the deployment-trust model (one secret per org, scoping actions to that org's own repos) is meant to prevent.

### Likelihood Explanation
Exploitability requires: (1) the Shipit instance configured for multiple GitHub organizations sharing one engine instance (an explicitly supported and documented configuration in `docs/setup.md`/`config/secrets.development.shopify.yml`), and (2) the attacker controlling or being a legitimate webhook sender for at least one of those organizations (i.e., possessing that organization's own `webhook_secret`, not Shipit-privileged credentials — this does not require an `ApiClient` token, session, or GitHub App private key, matching the unprivileged-attacker requirement). Given that, forging the cross-repository fields is a matter of crafting an arbitrary JSON body and signing it with the attacker's own legitimate secret — no cryptographic bypass is needed, only the missing binding between `repository_owner` and `repository.full_name`.

### Recommendation
Bind the verified organization to the repository actually acted upon: after signature verification succeeds for organization `O`, require that `repository.full_name`'s owner segment (or `repository.owner.login`) equals `O`, and reject (422) any payload where they differ, before dispatching to handlers. Equivalently, have `Handler#repository_name`/`stacks` resolution consult the same organization value used during signature verification rather than trusting `repository.full_name` alone.

### Proof of Concept
1. Deploy Shipit configured for two organizations, `attacker-org` (attacker legitimately owns/controls this org's GitHub App and thus knows its `webhook_secret`) and `victim-org` (has a `Stack` configured on the same Shipit instance, e.g. `victim-org/victim-repo`).
2. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org's webhook_secret, body)>` and POSTs to `/github/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")` and verifies successfully (the attacker legitimately knows that secret) — [6](#0-5) .
5. `PushHandler` resolves stacks via `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on the victim's stack — [3](#0-2) [4](#0-3) , causing the victim's stack to sync/act on attacker-chosen commit data despite the attacker having no relationship to `victim-org`.
