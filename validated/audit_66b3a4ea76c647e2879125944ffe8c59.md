### Title
`sonarqube` status webhook flips required-context state for any stack sharing the SHA, unscoped by repository - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves affected commits by `Commit.where(sha: params.sha)` with no repository filter, unlike the base `Handler` class which provides a `stacks` helper scoped via `Repository.from_github_repo_name(repository_name)`. Any organization/repository that can produce a validly-signed `status` webhook for its own repo can flip the `sonarqube` status of a commit sharing the same SHA in a completely unrelated stack, including a production-environment stack, forcing that stack's deployability/merge/block state to change.

### Finding Description
The broken binding: the code implicitly assumes `commit.stack.github_repo_name == payload['repository']['full_name']` (i.e., the sending repository authenticates only commits belonging to it), but this equality is never checked in `StatusHandler#process`: [1](#0-0) 

Contrast with the base `Handler` class, which does provide repository scoping via `stacks`/`repository_name`, but `StatusHandler` does not use it and instead queries `Commit` globally by SHA: [2](#0-1) 

The webhook pipeline (`WebhooksController#create` → `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`) verifies only the HMAC signature against the *sending organization's* configured secret via `verify_signature`, and does not verify that the `repository.full_name` in the payload matches the commit(s) being mutated: [3](#0-2) 

Once `commit.create_status_from_github!(params)` writes the new status, `add_status` recomputes `Status::Group` state and, if the simple state changed, triggers `stack.schedule_merges` and emits `deployable_status`/`commit_status` hooks purely based on the recomputed status, with no re-check of which repository produced the update: [4](#0-3) 

`deployable?`/`blocked?` are derived from `status`/`blocking_statuses`, so a `failure` status for context `sonarqube` (if configured as required/blocking on the victim stack) directly flips `deployable?`/`blocked?` for that stack: [5](#0-4) 

**Exploit flow:** An attacker who owns/controls repository A (with an app installed / webhook configured for org A, which is a normal, unprivileged setup — the attacker only needs to trigger a `status` event from their own repo, e.g., by pushing a commit and having their own CI or a script relay a status webhook) sends `POST /webhooks` with `X-Github-Event: status`, a valid signature for org A, and a payload `{repository: {full_name: "attacker/repoA", owner: {login: "attacker"}}, sha: "<victim-sha>", context: "sonarqube", state: "failure"}`. If any commit in the Shipit database — belonging to a victim stack in a different repository/org, e.g., a production-environment stack — happens to share that SHA (which is fully plausible: SHAs are content-addressed and identical commits, cherry-picks, shared library commits, or merge commits can produce the same SHA across repos/forks, and an attacker can also engineer SHA reuse by forking/mirroring or forcing the same tree+parent+commit metadata), `StatusHandler` updates the status on that victim commit too, changing its `deployable?`/`blocked?` state.

Existing guards do not stop this: `verify_signature` only proves the payload originated from *some* configured organization, not that the SHA it names belongs to that organization's repository; `drop_unhandled_event` only filters unhandled event types; there is no `ExplicitParameters` check on `repository.full_name` vs. commit ownership; and `StatusHandler` never calls the `stacks`/`repository_name` scoping helper defined in the base `Handler`.

### Impact Explanation
A payload authenticated for repository A mutates commit/task state belonging to repository/stack B — this is exactly the "payload for one repository mutating another's stack/commit" category (Critical). If stack B is a production-environment stack that requires the `sonarqube` context and is running continuous deployment, flipping it to `failure` can block deploys/merges (denial of legitimate release) or, conversely, a forged `success` status (same code path, different `state`) could allow an unqualified/malicious commit to become "deployable," enabling an unauthorized deploy. The blast radius spans all stacks/tenants hosted by the same Shipit instance whenever SHA collision (accidental or attacker-engineered) occurs across repositories.

### Likelihood Explanation
Preconditions: the attacker needs a repository (their own) with a valid webhook signature they can trigger — a low-cost, unprivileged capability per the rules. The victim stack must be configured with the `sonarqube` context as required/blocking and be a production environment. The main constraining factor is causing a SHA collision between the attacker's authenticated repository and the victim's commit — this is not guaranteed per-request but is a realistic scenario for forked/mirrored repos, shared submodules, or engineered git objects (identical author/committer/timestamp/tree/parent producing identical SHA-1), and the finding is squarely a missing-authorization-scope bug rather than a probabilistic one: the code path performs no scoping at all, so the vulnerability is real and repeatable once a shared SHA exists.

### Recommendation
Scope `StatusHandler#process` (and any other handler using bare `Commit.where(sha: ...)`) to only the repository that authenticated the webhook, mirroring the base `Handler#stacks` helper, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This enforces the invariant that a status only affects commits within the repository that authenticated the webhook.

### Proof of Concept
minitest plan (in `test/models/shipit/webhooks/handlers/status_handler_test.rb`, illustrative):
```ruby
test "a status for one repository does not affect a commit sharing the same SHA in another stack" do
  victim_stack = shipit_stacks(:shipit) # production environment stack requiring 'sonarqube'
  victim_stack.update!(environment: 'production')
  victim_commit = victim_stack.commits.create!(sha: 'a' * 40, message: 'victim commit')
  # sanity: victim currently deployable
  before_deployable = victim_commit.reload.deployable?

  attacker_payload = {
    'sha' => victim_commit.sha,
    'state' => 'failure',
    'context' => 'sonarqube',
    'repository' => { 'full_name' => 'attacker/other-repo', 'owner' => { 'login' => 'attacker-org' } },
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(attacker_payload)

  after_deployable = victim_commit.reload.deployable?

  # Binding under test: victim_commit.stack.github_repo_name == attacker_payload['repository']['full_name']
  # This is false, yet the state changed:
  assert_equal before_deployable, after_deployable,
    "status for attacker/other-repo must not change deployability of #{victim_stack.github_repo_name}'s commit"
end
```
This test demonstrates that `before_deployable != after_deployable` (state flips) despite the repository named in the payload never matching the victim stack's repository, confirming the cross-repository write.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
