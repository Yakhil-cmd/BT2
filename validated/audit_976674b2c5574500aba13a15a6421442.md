### Title
Unhandled `throw Error` on malformed private-payment hidden-output amount crashes the receiving node - (File: validation.js, indivisible_asset.js)

### Summary
`validatePaymentInputsAndOutputs()` in `validation.js` enforces several "should never happen" invariants on `objValidationState.src_coin` with bare `throw Error(...)` statements instead of routing the error through the normal `callback(err)` path used everywhere else in unit validation. A private-payment counterparty can craft a private-payment chain whose hidden-output `amount` field is not a positive integer; that value is copied verbatim into `src_coin.amount` by `indivisible_asset.js` without validation, then later triggers an uncaught exception deep inside an async callback chain, crashing the receiving wallet/hub process. This is analogous to CVE-2021-20272, where a crafted request could reach an `assert()`-style invariant check and crash the server.

### Finding Description
For private, fixed-denomination assets, transfers are validated purely from data supplied by the sender of the private-payment chain (no DB lookup, since the outputs are hidden). `indivisible_asset.js` builds the `src_coin` object directly from the attacker-supplied previous private element: [1](#0-0) 

Notably, `prev_hidden_output.amount` (taken straight from `objPrevPrivateElement.payload.outputs[input.output_index]`, fully attacker-controlled) is assigned to `src_coin.amount` with no type/range check.

Later, when this `src_coin` is consumed in `validatePaymentInputsAndOutputs()` for a `transfer` input of a private fixed-denomination asset, the code asserts invariants with bare throws rather than passing errors to the `cb`/`callback` chain used elsewhere in the same function: [2](#0-1) 

Because `src_coin.amount` was never validated as a positive integer when it was constructed, an attacker can set it to `0`, a negative number, a string, or omit it, and reach:
```
if (!isPositiveInteger(src_coin.amount))
    throw Error("no src coin amount");
```
This `throw` executes inside a deeply nested async callback (`async.forEachOfSeries` item callback, itself inside `validatePayment` → `validatePaymentInputsAndOutputs`), invoked from `indivisible_asset.js`'s `validatePrivatePayment`/`parsePrivatePaymentChain`, which in turn is invoked from device-message/chat private-payment handling (`wallet.js`) when a counterparty sends a private payment chain. There is no `try/catch` wrapping this call chain to convert the thrown exception into a rejected/handled error; it propagates as an uncaught exception and crashes the Node.js process, exactly the "crafted input reaches an internal invariant/assertion → process crash" pattern from CVE-2021-20272.

### Impact Explanation
Any wallet or hub node that receives a private payment (a normal, unprivileged interaction — e.g. via chat/device message private-asset transfer) from a malicious counterparty can be crashed remotely and repeatably. This is a denial-of-service against the receiving node/wallet process: it cannot confirm or process any further units until restarted, satisfying the "network unable to confirm new units" impact bucket for the affected party. No privileged keys or special roles are required — only being a private-payment counterparty, which is an explicitly in-scope attacker profile.

### Likelihood Explanation
High. Any user who can receive a private, fixed-denomination-asset payment/chain from another wallet user is exposed. Crafting a private-payment chain with an invalid hidden-output `amount` for one hop, referenced by the next hop's `input.output_index`, requires no signing-key compromise — the attacker fully controls their own outgoing message content sent to the victim.

### Recommendation
- In `indivisible_asset.js`, validate `prev_hidden_output.amount` (must be a positive integer, and consistent with encoding of hidden output before hash) before assigning it to `objValidationState.src_coin.amount`, and return `callbacks.ifError(...)` on failure instead of allowing bad data downstream.
- In `validation.js`, replace the `throw Error(...)` invariant checks around `src_coin` (missing `src_coin`, `src_output`, `denomination`, `amount`) with calls to `cb(err)`/`callback(err)`, consistent with the rest of the validation error-handling convention, so malformed attacker-supplied data results in a rejected/handled validation error rather than an uncaught exception.
- Audit other `throw Error(...)` invariant assertions reachable from attacker-controlled unit/message/private-payment content (in `validation.js`, `indivisible_asset.js`, `aa_composer.js`) for the same unhandled-exception-on-crafted-input pattern.

### Proof of Concept
1. Attacker (as a private-payment counterparty) constructs a private-payment chain (`arrPrivateElements`) for a private, fixed-denomination asset, following the normal chain format used by `wallet.js`/`indivisible_asset.js`.
2. In one intermediate hidden output entry (not the one revealed for that hop's own validation, but one that will be referenced by the *next* hop's `input.output_index`), the attacker sets `amount` to `0`, a negative value, or omits it, while keeping `output_hash` consistent so the earlier per-hop hash checks pass for that hop.
3. Attacker sends the crafted chain to the victim wallet as a normal private payment (device message).
4. Victim's node processes it via `parsePrivatePaymentChain` → `validatePrivatePayment` → `validation.validatePayment` → `validatePaymentInputsAndOutputs`.
5. `src_coin.amount` (copied from the crafted hidden output) fails `isPositiveInteger`, hitting `throw Error("no src coin amount")` at `validation.js:2424`, which is uncaught anywhere in the call chain and crashes the victim's Node.js process. [2](#0-1) [3](#0-2)
