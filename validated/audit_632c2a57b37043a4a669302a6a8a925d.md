### Title
AA `bounce()` forfeits all received assets with zero refund when only one bounce-fee asset is underpaid - ([File: aa_composer.js])

### Summary
### Finding Description
When an Autonomous Agent's oscript definition fails to produce a valid response (bad formula, insufficient balance, cap/limit exceeded, etc.), `handleTrigger()` calls `bounce(error)` to refund the funds the trigger sender attached, minus the AA's configured `bounce_fees`. `bounce_fees` is a per-asset map (base + any number of other assets) set once, immutably, in the AA definition, exactly like the hardcoded `eligibleWEVE` cap in the Velodrome contracts. [1](#0-0) 

The refund logic iterates over every asset present in `trigger.outputs` and computes `fee = bounce_fees[asset] || 0`. If for **any single asset** `fee > amount` (i.e. the sender attached less of that asset than the AA's configured bounce fee for it), the function immediately does `return finish(null)` — aborting the loop and refunding **nothing at all**, not even for the other assets in the same trigger that already had enough to fully cover their own bounce fee and were queued for a refund: [2](#0-1) 

Because the trigger's outputs were already credited into the AA's balance earlier in `updateInitialAABalances()` (and this happens before any bounce fee/messages logic), by the time `bounce()` runs the coins have already been irrevocably transferred to the AA's balance. If `bounce()` then exits via the `fee > amount` early return, the assets are simply absorbed by the AA — with no compensating output, no error path, and no way for the sender to reclaim them.

### Impact Explanation
This is a direct analog of the Velodrome WeVE bug: (1) an irrevocable action (payment to the AA, already recorded on the DAG and credited to the AA's balance) is followed by (2) a downstream check against an immutable, hardcoded per-asset cap (`bounce_fees`), and (3) if that check fails, there is **no refund path** — the entire payment, including amounts of unrelated assets that individually satisfied their bounce fee, is permanently lost. Any AA author who configures `bounce_fees` for more than one asset (a legitimate, documented feature) exposes every caller to potential permanent loss of funds if the caller misjudges the amount of even one secondary asset while otherwise paying enough base bytes and enough of the "real" asset being transacted (e.g., a redemption/exchange AA that also demands a small anti-spam fee in a second asset). This qualifies as AA fund loss under a genuine, reachable condition — not a privileged or operator-only path; any unit poster/AA trigger sender can trigger it, intentionally or accidentally.

### Likelihood Explanation
Likelihood is Medium: it requires an AA that defines `bounce_fees` for more than one asset (a supported and documented capability) and a trigger sender who sends insufficient (but nonzero, non-covering) amount of just one of those fee assets while sending an otherwise correct/valuable payment (base bytes plus a significant amount of another asset). This can happen accidentally (fee estimation error, stale AA parameters, wallet UI not surfacing multi-asset bounce fees) or be deliberately exploited by an attacker sending a victim's funds through a maliciously crafted trigger that intentionally underpays one minor fee asset to strand the rest of the payment in the AA.

### Recommendation
Change the refund logic in `bounce()` so that failing to cover the bounce fee for one asset does not cancel refunds for other assets that already have sufficient balance. For example, first compute per-asset refund messages for every asset that fully covers its own fee, and only withhold (forfeit to the AA) the specific asset(s) that fail to cover their fee — do not use a single `fee > amount` condition to unconditionally abort/discard already-computed refunds for unrelated assets: [2](#0-1) 

### Proof of Concept
1. Deploy an AA with `bounce_fees: {base: 10000, X: 100}` where `X` is some asset used as an anti-spam/secondary fee, and whose main logic (e.g. a redemption case gated by a hardcoded cap in a state var) will legitimately bounce under some condition.
2. A user sends a trigger with `outputs: {base: 10000, X: 50, WEVE_LIKE_ASSET: 1000000}` — enough base to cover the base bounce fee, enough `WEVE_LIKE_ASSET` to be the intended redemption payment, but only 50 of `X` (less than the configured 100 fee).
3. The AA's main logic fails (e.g. cap exceeded) and calls `bounce(err)`.
4. In `bounce()`, the loop reaches asset `X`: `fee (100) > amount (50)` → `return finish(null)` is executed immediately, before/regardless of the fact that `base` and `WEVE_LIKE_ASSET` both had sufficient/excess amounts that would have produced full refund messages.
5. No response messages are sent at all. `base`, `X`, and the large `WEVE_LIKE_ASSET` amount are all permanently retained in the AA's balance with no way for the sender to recover them.

	function bounce(error) {
		console.log('bouncing with error', error, new Error().stack);
		objStateUpdate = null;
		error_message = error_message ? (error_message + ', then ' + error) : error;
		if (trigger_opts.bAir) {
			assignObject(stateVars, originalStateVars); // restore state vars
			assignObject(trigger_opts.assocBalances, originalBalances); // restore balances
			if (!bSecondary) {
				for (let a in trigger.outputs)
					if (bounce_fees[a])
						trigger_opts.assocBalances[address][a] = (trigger_opts.assocBalances[address][a] || 0) + bounce_fees[a];
			}
		}
		if (bBouncing)
			return finish(null);
		bBouncing = true;
		if (bSecondary)
			return finish(null);
		if ((trigger.outputs.base || 0) < bounce_fees.base)
			return finish(null);
		var messages = [];
		// iteration order is standardized since ECMAScript 2020
		for (var asset in trigger.outputs) {
			var amount = trigger.outputs[asset];
			var fee = bounce_fees[asset] || 0;
			if (fee > amount)
				return finish(null);
			if (fee === amount)
				continue;
			var bounced_amount = amount - fee;
			messages.push({app: 'payment', payload: {asset: asset, outputs: [{address: trigger.address, amount: bounced_amount}]}});
		}
		if (messages.length === 0)
			return finish(null);
		sendUnit(messages);
	}
