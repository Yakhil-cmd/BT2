### Title
Webhook signature verification authenticates the payload's `repository.owner`/`organization.login`, while every event handler acts on the payload's `repository.full_name` — allowing cross-organization webhook forgery under multi-GitHub-App configuration - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App (and thus the `webhook_secret` used to validate `X-Hub-Signature`) based on `repository_owner`, computed as `params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`. Every downstream event handler, however, resolves the target repository/stack using an entirely different field of the same JSON body: `payload.dig('repository', 'full_name')`. Because both fields live in the same attacker-authored JSON body and only one of them participates in the org-selection logic (not the signature computation itself), a party who legitimately knows the `webhook_secret` for *any* organization configured in a multi-org Shipit deployment can forge a valid signature for a payload whose `repository.full_name` points at a different organization's repository.

### Finding Description
Signature check: [1](#0-0) 
`repository_owner` used to pick the app/secret: [2](#0-1) 

`Shipit.github(organization:)` resolves a distinct `GitHubApp` (and distinct `webhook_secret`) per organization key when Shipit is configured with multiple GitHub Apps: [3](#0-2) [4](#0-3) 

But the actual repository/stack lookup used by every handler is keyed off a *different* field, `repository.full_name`, not `repository.owner.login`: [5](#0-4) 

This means the binding the signature is supposed to establish — "this payload was authorized by organization X" — is not the same as the binding the handlers rely on — "this payload governs repository X/Y". `repository.owner.login` and `repository.full_name`'s owner segment are never cross-validated. An attacker who is a legitimate installer/admin of Org A's own GitHub App (and therefore legitimately possesses Org A's `webhook_secret`, since GitHub App owners set that secret themselves when creating the app per `docs/setup.md`'s multi-org instructions) can craft a JSON body with:
- `organization.login` / `repository.owner.login` = `"OrgA"` (used only for signature-org selection)
- `repository.full_name` = `"OrgB/some-repo"` (used by every handler to find the target `Repository`/`Stack`)

and sign it with Org A's `webhook_secret`. `verify_signature` succeeds because it only checks the HMAC against Org A's secret using `repository_owner == "OrgA"`; it never confirms that `full_name` starts with `"OrgA/"`. The forged event is then dispatched to handlers such as `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, `MembershipHandler`, and the `PullRequest::*` handlers, all of which resolve the affected `Repository`/`Stack` purely from `repository.full_name`: [6](#0-5) [7](#0-6) [8](#0-7) 

This is a direct analog of the reported bug class: a field ("repository owner") is checked/authenticated, while a different field ("repository full_name") is the one actually acted upon — exactly the "organization authenticated versus repository written" trust-binding break called out in scope.

### Impact Explanation
With `PushHandler`, a forged event triggers `stack.sync_github(expected_head_sha:)` against Org B's stack — a cross-repository/cross-organization action originating from a signature that only proves knowledge of Org A's secret. Depending on `shipit.yml`/continuous-delivery configuration on Org B's stack, a synced push can cascade into an actual deploy being triggered, and `StatusHandler` lets the forger inject fabricated commit statuses (`create_status_from_github!`) that CI-gating logic (`ci.require`) relies on to permit deploys/merges. This crosses the "cross-repository writes" / "unauthorized deploy" bar for Critical impact, since it lets an entity trusted only for Org A inject state and trigger actions against Org B's stacks without ever having been granted access to Org B.

### Likelihood Explanation
Exploitability requires the Shipit instance to be configured with **multiple GitHub Apps for multiple organizations**, a documented and supported configuration (`docs/setup.md`, "Using Multiple Github Applications"). The attacker only needs legitimate ownership/administration of one of the configured orgs (thus knowing that org's own `webhook_secret`, which they themselves generate) — no compromise of the target org or of Shipit itself is required. This is realistic for any Shipit deployment shared across multiple, mutually-untrusted GitHub organizations, which is precisely the scenario the multi-app feature exists to support.

### Recommendation
After signature verification succeeds for `repository_owner`, verify that `payload.dig('repository', 'full_name')` (and `payload.dig('organization', 'login')` where present) is actually owned by that same, verified `repository_owner` before dispatching to handlers — e.g., reject the webhook (422) if `repository.full_name.split('/').first.casecmp?(repository_owner)` is false. Alternatively, derive `repository_owner` strictly from `repository.full_name` itself (single source of truth) rather than from the separate `repository.owner.login`/`organization.login` fields, so the field used for secret selection and the field used for repository resolution can never diverge.

### Proof of Concept
1. Shipit is configured with two orgs, `OrgA` and `OrgB`, each with its own GitHub App and `webhook_secret` (per `docs/setup.md`'s multi-app schema).
2. Attacker administers `OrgA`'s GitHub App and therefore knows `OrgA`'s `webhook_secret`.
3. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": { "full_name": "OrgB/target-repo", "owner": { "login": "OrgA" } }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<hmac_sha1(OrgA_webhook_secret, raw_body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `WebhooksController#verify_signature` computes `repository_owner = "OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and the HMAC check passes since it was signed with `OrgA`'s secret.
6. `Webhooks.for_event('push')` dispatches to `PushHandler`, which resolves the stack via `payload.dig('repository', 'full_name')` = `"OrgB/target-repo"`, and calls `stack.sync_github(expected_head_sha: ...)` on Org B's stack — despite the request only ever proving possession of Org A's secret.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
