### Title
Malicious Fast-Sync Peer Can Inject Fake Staking Info at Arbitrary Epoch Key, Corrupting Validator Set and Reward Distribution — (`datasync/downloader/queue.go`, `datasync/downloader/downloader.go`)

---

### Summary

During fast sync (pre-Kaia fork), the staking-info delivery path has a deliberately skipped validation step. A malicious P2P peer can return a `P2PStakingInfo` whose `BlockNum` field is set to an arbitrary epoch block M while the corresponding `fetchResult` belongs to epoch block N. Because `commitFastSyncData` and `commitPivotBlock` key the DB write on `result.StakingInfo.BlockNum` (not on `result.Header.Number`), the attacker's data lands at key M, the correct entry for N is never written, and `GetStakingInfo` subsequently serves the attacker-controlled validator/reward addresses for all blocks whose source epoch is M.

---

### Finding Description

**Step 1 — Staking info is scheduled only for pre-Kaia epoch blocks.**

`newFetchResult` sets the `stakingInfoType` pending bit only when `header.Number % stakingUpdateInterval == 0 && !isKaiaFork`. [1](#0-0) 

**Step 2 — Delivery validation is a no-op.**

`DeliverStakingInfos` passes a `validate` closure that unconditionally returns `nil` (marked `TODO-Kaia-Snapsync`). No field of the returned `P2PStakingInfo` — including `BlockNum` — is checked against the requested header. [2](#0-1) 

**Step 3 — `reconstruct` blindly assigns the peer-supplied struct.**

The generic `deliver` loop pairs `stakingInfoList[index]` with the `fetchResult` for `request.Headers[index]` by position. The peer can set `stakingInfoList[0].BlockNum = M` while `request.Headers[0].Number = N`; the mismatch is never detected. [3](#0-2) 

**Step 4 — Both commit functions key the DB write on the attacker-supplied `BlockNum`.**

`commitFastSyncData`: [4](#0-3) 

`commitPivotBlock`: [5](#0-4) 

Both call `PutStakingInfoToDB(result.StakingInfo.BlockNum, ...)`, writing attacker-controlled data at key M and leaving key N absent.

**Step 5 — `GetStakingInfo` trusts the DB entry without state verification.**

For pre-Kaia blocks, `GetStakingInfo` reads the DB at `sourceNum` and returns immediately if an entry exists, with no cross-check against the actual blockchain state. [6](#0-5) 

If the attacker stored fake data at M, every call to `GetStakingInfo` for blocks whose `sourceBlockNum` resolves to M returns the attacker's `NodeIds`, `RewardAddrs`, `StakingAmounts`, `KEFAddr`, and `KIFAddr`.

---

### Impact Explanation

On a pre-Kaia chain (or any chain where fast sync covers pre-Kaia epoch blocks):

- **Validator-set corruption**: `NodeIds` and `StakingAmounts` drive weighted-random proposer selection. Attacker-supplied values redirect proposer rights.
- **Reward-distribution corruption**: `RewardAddrs`, `KEFAddr`, and `KIFAddr` determine where block rewards and treasury funds are sent. Attacker-supplied addresses redirect KAIA rewards.
- **Missing epoch N entry**: `GetStakingInfo` for blocks needing epoch N finds no DB entry and falls back to `getFromStateByNumber(N)`. After fast sync, the state for pre-pivot blocks is not available, so this call fails, potentially halting block processing for the affected epoch range.

---

### Likelihood Explanation

Any node that connects to a malicious peer during fast sync is exposed. No authentication of peer-supplied staking data exists. The attacker only needs to be a reachable P2P peer; no privileged key or majority-validator collusion is required. The `TODO` comment in the validate closure confirms the gap is known and unaddressed.

---

### Recommendation

1. In `DeliverStakingInfos`, implement the `validate` closure to assert `stakingInfoList[index].BlockNum == header.Number.Uint64()`. Reject the entire delivery if any entry mismatches.
2. In `commitFastSyncData` and `commitPivotBlock`, use `result.Header.Number.Uint64()` as the DB key, not `result.StakingInfo.BlockNum`.
3. Optionally, after writing, verify the stored `StakingInfo.SourceBlockNum` equals the key.

---

### Proof of Concept

```
1. Attacker runs a Kaia node and advertises itself as a fast-sync peer.
2. Victim node (pre-Kaia chain, fast sync) requests staking info for epoch block N.
3. Attacker responds with P2PStakingInfo{BlockNum: M, CouncilRewardAddrs: [attacker_addr], ...}.
4. queue.DeliverStakingInfos: validate() returns nil; reconstruct assigns the struct to fetchResult[N].
5. commitFastSyncData: PutStakingInfoToDB(M, fake_data) — DB[M] = fake, DB[N] = absent.
6. GetStakingInfo(N+1): sourceNum = N → DB[N] = nil → getFromStateByNumber(N) → state unavailable → error.
7. GetStakingInfo(M+1): sourceNum = M → DB[M] = fake_data → returns attacker's RewardAddrs.
8. Block rewards for the epoch [M+interval, M+2*interval) are distributed to attacker_addr.
```
