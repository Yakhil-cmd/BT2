### Title
Webhook signature is verified against `repository.owner.login`, but every event handler acts on the independent `repository.full_name` field, letting one authenticated GitHub organization forge deploy-triggering webhooks for stacks belonging to a different organization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate a webhook using `repository_owner`, a value read from `params.dig('repository','owner','login')` (or `organization.login`) of the raw JSON body [1](#0-0) . Once the signature check passes, every registered event handler (`PushHandler`, the `PullRequest::*` handlers, etc.) independently re-reads a *different* field of the same attacker-controlled JSON body - `payload.dig('repository','full_name')` - to decide which `Repository`/`Stack` to mutate [2](#0-1) . Nothing ties `repository.owner.login` (the field the signature covers) to `repository.full_name` (the field that is actually acted upon). This is the exact class of bug the report describes: two related code paths derive state from overlapping-but-independent fields of the same input, and the field that is cryptographically covered is not the field that is ultimately trusted for the write.

### Finding Description
Shipit supports multiple independently configured GitHub Apps/organizations, each with its own `webhook_secret`, as shown in the multi-org fixture `test/dummy/config/secrets_double_github_app.yml` (`OrgOne`, `OrgTwo`, each with a distinct `webhook_secret`) [3](#0-2) . `Shipit.github(organization:)` looks up the `GitHubApp` instance for the org named by `repository_owner`, and `verify_webhook_signature` checks the HMAC using that org's `webhook_secret` [4](#0-3) .

Crucially, `repository_owner` is computed purely from the JSON body the caller supplies:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [5](#0-4) 

This value is used **only** to pick which secret to verify against. It is never compared to the field the handlers actually use to locate the target repository/stack:
```ruby
def repository_name
  payload.dig('repository', 'full_name')
end
``` [6](#0-5) 

`PushHandler#process` uses `stacks` (built from `repository_name`) to find non-archived stacks on the pushed branch and calls `stack.sync_github(expected_head_sha: params.after)` [7](#0-6) . The Pull Request handlers likewise resolve `repository` from `params.repository.full_name` to find/create/archive `ReviewStack`s [8](#0-7) .

Because the signature only proves possession of *some* org's `webhook_secret`, and that org is identified by `repository.owner.login`, an attacker who legitimately controls one onboarded GitHub organization (and therefore knows that org's `webhook_secret`, since it is set by whoever creates that org's GitHub App) can send a raw POST to `/webhooks` with:
- `repository.owner.login` = their own organization (so `verify_signature` succeeds using their own known secret), and
- `repository.full_name` = `"<victim-org>/<victim-repo>"` (a repository belonging to a different organization tracked by the same Shipit instance).

`verify_signature` will pass because it only checked the secret associated with the attacker's own org, but every handler will operate against the victim organization's `Repository`/`Stack`, because they trust `full_name` unconditionally.

### Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" trust boundary explicitly called out as in-scope. Concretely, an attacker who administers Organization A (and thus its GitHub App webhook secret) can forge a `push` event naming Organization B's repository in `repository.full_name`. `PushHandler` will call `stack.sync_github(expected_head_sha:)` for Organization B's stack, forcing an unauthorized GitHub sync/refresh cycle and injecting an attacker-chosen `expected_head_sha` into another organization's deploy pipeline - this can trigger unwanted continuous-deployment behavior or interfere with the victim's release state without ever having the victim's GitHub credentials or Shipit session. This is a cross-repository/cross-organization write achieved purely by crafting an unauthenticated-with-respect-to-target-repo JSON body, matching the High-impact bucket ("cross-repository writes" / "unauthorized deploy").

### Likelihood Explanation
Exploitability requires only that the attacker be an authenticated admin of *any* GitHub organization/App already configured in the same Shipit instance (a legitimate, unprivileged-relative-to-the-victim position in multi-tenant Shipit deployments) - no access to the victim's secrets, session, or `ApiClient` tokens is needed. The vulnerable comparison gap (`repository.owner.login` vs `repository.full_name`) is unconditional in the shipped controller/handler code and does not depend on any non-default configuration choice.

### Recommendation
After `verify_signature` succeeds, re-derive the organization from the same field the handlers use (`repository.full_name`'s owner segment) and confirm it matches the organization whose secret validated the signature (or vice versa: pick the app to verify against by parsing the owner out of `full_name` rather than the separate `repository.owner.login`/`organization.login` field). Reject the webhook if the two disagree.

### Proof of Concept
1. Shipit is configured with two organizations, `OrgA` and `OrgB`, each with distinct `webhook_secret`s (as in `test/dummy/config/secrets_double_github_app.yml`), both tracked by the same Shipit instance.
2. Attacker (an admin of `OrgA`'s GitHub App) knows `OrgA`'s `webhook_secret`.
3. Attacker crafts a JSON payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```
4. Attacker computes `X-Hub-Signature` using `OrgA`'s known `webhook_secret` over the raw body and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: "OrgA")` and validates successfully against `OrgA`'s secret [1](#0-0) .
6. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("OrgB/victim-repo")` [2](#0-1)  and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on `OrgB`'s stack, despite the request having been authenticated only against `OrgA`'s secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
