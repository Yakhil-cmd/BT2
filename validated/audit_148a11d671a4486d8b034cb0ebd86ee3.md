### Title
Aura/BABE import-queue rejects future-slot headers and bans the *relaying* peer instead of deferring the block - ([File: substrate/client/consensus/aura/src/import_queue.rs])

### Summary
Substrate's Aura and BABE `Verifier::verify()` implementations treat any block header whose slot is more than one slot ahead of the local wall clock as an immediate, permanent verification failure. This failure is reported up to `sc-network-sync`'s `ChainSync`, which drops/penalizes the network peer that served the block via `BadPeer(peer, rep::VERIFICATION_FAIL)` — even though the block may become perfectly valid once the recipient's clock catches up, and even though the penalized peer is merely the one who *relayed* the header, not necessarily its author. This is the same invariant violation described in the Nervos CKB advisory: "BlockTimeTooNew should not be considered invalid" / peers should not be banned for serving a merely-future, not-yet-valid block.

### Finding Description
`check_header_slot_and_seal` (Aura) explicitly classifies a header whose slot is ahead of `slot_now` as `SealVerificationError::Deferred`: [1](#0-0) 

The doc comment for `CheckedHeader::Deferred` and the accompanying `FIXME #1019` note make clear that the *intended* design was to defer and re-queue such headers later, not to reject them outright: [2](#0-1) [3](#0-2) 

However, in the actual `AuraVerifier::verify` implementation, the `Deferred` case is converted straight into a hard `Err(...)`, permanently failing verification for that header rather than deferring it: [4](#0-3) 

The BABE verifier does exactly the same thing: [5](#0-4) [6](#0-5) 

That `Err(String)` returned from the `Verifier` propagates through the import queue as `BlockImportError::VerificationFailed(peer_id, e)`. In `ChainSync::on_block_response`/import-result handling this is mapped directly to dropping the serving peer with a negative reputation penalty: [7](#0-6) 

Crucially, the `peer_id` being penalized here is whichever peer *served/relayed* the block to this node during sync — it is not necessarily the block's author, and the header could later become perfectly valid once local time (or the observer's clock) advances past the slot boundary. This is structurally identical to the CKB advisory's root cause: a header that is merely ahead of the local clock (rather than cryptographically/semantically invalid) is treated as a permanently-invalid block and its peer is punished, creating an incentive/tooling for an attacker to split honest peers from the network by crafting block timestamps right at the drift boundary and having them relayed by unwitting honest nodes.

The `PoW` consensus client has the analogous `Error::TooFarInFuture` variant as well: [8](#0-7) 

The `pallet-timestamp` inherent-level check (`InherentError::TooFarInFuture`) is a separate, related mechanism operating at block-execution time (30s drift, `is_fatal_error() == true`) which similarly hard-fails rather than deferring: [9](#0-8) [10](#0-9) 

### Impact Explanation
This is a Medium/network-health issue analogous to the CKB advisory: honest peers can be penalized (and, depending on the accumulated reputation cost/threshold in `sc-network`, eventually disconnected/banned) merely for relaying a header that is slightly ahead of the receiving node's clock — a situation that occurs naturally due to ordinary NTP/clock skew between geographically distributed nodes, and which an adversary can deliberately engineer (craft a header at the exact allowed-drift boundary) to cause disproportionate reputation damage to honest relayers and potentially degrade network connectivity/partition tolerance. It does not directly cause loss of funds, unauthorized dispatch, or consensus safety failure — it is a peer-scoring/availability robustness issue, consistent with the "Medium" severity of the original CKB advisory.

### Likelihood Explanation
Likelihood is proportional to normal, non-adversarial clock skew across the network (moderate — happens without any attacker involvement) plus the possibility of an attacker deliberately timing a block near the allowed-drift boundary (`slot_now + 1`) to trigger `VerificationFailed` on nodes whose clocks lag slightly, causing those nodes to punish the (innocent) peers that relayed the block to them. I could not verify from the index alone the exact reputation-cost magnitude of `rep::VERIFICATION_FAIL` or the ban/disconnect threshold in `sc-network`'s peer-reputation system, so I cannot confirm whether a single such event causes an outright disconnect versus only a reputation deduction that requires repeated occurrences to escalate to a ban. This uncertainty should be resolved by reading `substrate/client/network/src/peer_info.rs` / reputation threshold constants directly, which the current index snippets did not surface.

### Recommendation
Implement the deferred-header re-queue path that the `FIXME #1019` / `CheckedHeader::Deferred` design already anticipates: instead of converting `Deferred` into a hard verification failure (and thus a `BadPeer` drop), the import queue should hold the header until `slot_now` catches up to the header's slot, then re-attempt verification, only penalizing the peer if the header is still invalid at that later point (bad signature, wrong author, excessive drift beyond a much larger bound, etc.). This mirrors the CKB fix: don't ban a peer merely for serving an as-of-yet-unripe, potentially-valid block.

### Proof of Concept
No executable PoC was run; this is a static-analysis code-path trace based on the cited files. To reproduce/demonstrate: run two nodes with clocks skewed by slightly more than one slot duration, have the fast-clock node author (or an attacker craft) a block whose slot equals `local_slot_now + 1` (just past the fast node's `slot_now + 1` drift tolerance as seen by the slow node), and observe via logs (`aura.header_too_far_in_future` / `babe.header_too_far_in_future` telemetry, `substrate/client/consensus/aura/src/import_queue.rs:252` / `substrate/client/consensus/babe/src/lib.rs:1093`) that the slow node rejects the block and, in `ChainSync`, issues `DropPeer(peer, rep::VERIFICATION_FAIL)` against the node that relayed it, per `substrate/client/network/sync/src/strategy/chain_sync.rs:907-922`. I was not able to execute this scenario or inspect the numeric reputation threshold within the available tool budget, so the actual disconnect behavior (vs. mere reputation decrement) remains unverified and should be confirmed by a Devin session with terminal access before filing for bounty consideration.
