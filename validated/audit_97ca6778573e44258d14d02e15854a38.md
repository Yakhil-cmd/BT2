## Finding [1](#0-0) 

### Title
Unbounded LevelDB Key-Range Scan in `data_feedByAddressExists` Reachable via AA `data_feed`/`in_data_feed` Formula Ops - (File: `data_feeds.js`)

### Summary
`dataFeedByAddressExists()` in `data_feeds.js` answers `data_feed`/`in_data_feed` oscript conditions (and the `'in data feed'` authentifier op in `definition.js`) by opening a LevelDB key stream over the range of all `df\n<address>\n<feed_name>\n<type>...` keys and iterating every matching record until a hit is found or the stream is exhausted, with **no `limit` for the `>`, `>=`, `<`, `<=` and `!=` relations**. [2](#0-1) [3](#0-2) 

### Finding Description
`data_feed`/`in_data_feed` in AA formulas take `oracles` and `feed_name` as evaluated expression parameters, not fixed literals — any AA whose formula derives the oracle address or feed name from `trigger.data` lets the trigger sender pick which feed is queried at call time. [4](#0-3) [5](#0-4) 

The `'in data feed'` authentifier condition in `definition.js`, reachable from ordinary (non-AA) unit signature validation, forwards straight into `dataFeeds.dataFeedExists`, which for the AA-independent path (`bAA=false`) falls through to `dataFeedByAddressExists` for every address supplied. [6](#0-5) 

An attacker can act as their own oracle, post a very large number of `data_feed` messages for a single `feed_name`/address pair (this is unbounded — any unit poster can attach `data_feed` payloads), and then trigger an AA (or use an address definition) whose `data_feed`/`in data feed` condition queries a relation/value that never matches recent entries (e.g., `relation: '<'` with a value below everything ever posted, or a nonexistent `feed_name`/oracle combination close to one with huge volume). The scan then walks the entire matching key range in the underlying LevelDB store synchronously per call, similar to the reported aim bug where querying many tracked `Text` objects causes the server to iterate a large table and become unresponsive.

### Impact Explanation
AA trigger processing runs serially under the `['aa_triggers']` mutex during main-chain stabilization. [7](#0-6) 
Because Node.js is single-threaded, a long-running key-stream scan invoked from `handlePrimaryAATrigger` -> formula evaluation -> `dataFeedByAddressExists` blocks the event loop, stalling processing of subsequent AA triggers and other queued network/validation work on that node for the duration of the scan. Repeated triggering (each an ordinary, unprivileged unit) can keep the node busy long enough to delay stabilization and confirmation of new units, matching the "network unable to confirm new units" impact bar.

### Likelihood Explanation
Exploitation requires: (1) posting many `data_feed` messages under one's own address (fully permitted, no privilege needed), and (2) triggering an AA (or presenting a unit for `'in data feed'` authentifier evaluation) that queries that feed with a non-matching relation/value so the scan cannot short-circuit. This is straightforward for any unit poster/AA trigger sender and does not require any hub, peer, or operator cooperation.

### Recommendation
Add an explicit `limit` (and/or a maximum scanned-record counter with early abort) to the LevelDB key stream in `dataFeedByAddressExists` for all relation types, not just `=`, and bound the total number of records inspected before giving up, propagating a bounded/failed result rather than scanning without limit. Consider charging the AA's oscript execution "complexity"/op-cost budget for data-feed lookups proportional to the number of records actually scanned, so attacker-controlled feed volume cannot be used to stall trigger processing for free.

### Proof of Concept
1. Attacker address `X` posts N (e.g., 100k) `data_feed` messages with `feed_name = "f"` and increasing numeric values, all authored by `X`.
2. Attacker deploys (or uses an existing) AA whose formula executes `data_feed[[oracles=$trigger_oracle, feed_name=$trigger_feed, relation='<', value=-1e15]]` where `$trigger_oracle`/`$trigger_feed` come from `trigger.data`.
3. Attacker sends a trigger unit setting `trigger.data.oracle = X`, `trigger.data.feed = "f"`.
4. `dataFeedByAddressExists` is invoked with `relation:'<'`, bound to a value below every posted entry, forcing it to stream through all N records in `data_feeds`/kvstore before returning `false`.
5. Repeating the trigger (or combining with more oracle posts) increases the per-call scan cost, degrading AA-trigger and (via single-threaded blocking) overall node processing.
