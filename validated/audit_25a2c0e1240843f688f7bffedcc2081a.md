### Title
Cross-organization webhook forgery via mismatched "signing organization" vs. "acted-upon repository" fields - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate the HMAC signature with based on `repository_owner`, a value taken from the JSON body itself (`repository.owner.login`, falling back to `organization.login`). However, every webhook `Handler` resolves the actual repository/stack to mutate using a *different* field of the same attacker-supplied JSON body: `repository.full_name`. Because these two fields are never checked for consistency, a party who legitimately possesses the webhook secret for one configured GitHub organization can forge a signed payload whose `repository.owner.login` matches their own org (so signature verification passes) while `repository.full_name` points at a repository belonging to a *different* organization configured in the same Shipit instance. This breaks the trust binding: "organization that authenticated" == "repository that is written".

### Finding Description
`verify_signature` picks the app/secret to verify with purely from body content: [1](#0-0) [2](#0-1) 

The `repository_owner` (used only to choose the HMAC key) is completely independent from `repository.full_name`, which is what every handler actually uses to locate and mutate state: [3](#0-2) 

Shipit explicitly supports multiple GitHub Apps/organizations, each with its own independently generated `webhook_secret`, configured side by side in the same instance: [4](#0-3) [5](#0-4) 

Given this multi-tenant configuration model, the party who controls (created/owns) the GitHub App for Organization A only knows Organization A's `webhook_secret`. Nothing in `verify_signature` or in the handlers ties the HMAC-authenticated organization to the repository namespace being written. An attacker who is a legitimate GitHub App owner/admin for Organization A — but has no authorization on Organization B's repositories — can compute a valid `X-Hub-Signature` over a payload using Organization A's secret while setting:
- `repository.owner.login` = "org-a" (so `repository_owner` resolves to `org-a`, and the HMAC check succeeds against `org-a`'s secret)
- `repository.full_name` = "org-b/victim-repo" (so `Handler#repository_name`/`#stacks` resolves to Organization B's `Repository`/`Stack`)

This forges a fully "verified" webhook for a repository the attacker does not control.

### Impact Explanation
The `PushHandler` acts on whichever stacks are resolved from the forged `repository.full_name`, syncing them with an attacker-chosen `expected_head_sha`: [6](#0-5) 

This lets an attacker with authenticated-but-unrelated organization credentials trigger `GithubSyncJob`/`sync_github` on another organization's stack — an unauthorized cross-repository/cross-organization side effect that they have no legitimate right to invoke, since normal access to that stack would require GitHub App installation permissions or Shipit membership on Organization B, neither of which the attacker holds. Other handlers (`PullRequest::*Handler`, `MembershipHandler`, `StatusHandler`, `CheckSuiteHandler`) are reachable the same way and similarly resolve their target purely from body content (`params.repository.full_name`), so the same forged-signature technique lets the attacker archive/unarchive review stacks, inject GitHub team membership records, or otherwise mutate state belonging to an organization outside the one whose secret actually signed the request. This satisfies the "organization that authenticated versus the repository that is written" binding violation and the "unauthorized deploy" / "cross-repository writes" impact bar.

### Likelihood Explanation
Exploitation only requires the attacker to be the legitimate operator/admin of any one GitHub organization/App that is configured in the target Shipit instance (a realistic and even encouraged multi-org deployment pattern per `docs/setup.md`), plus knowledge of that organization's own `webhook_secret` (which they legitimately possess, as they created it). No access to Organization B's secret, GitHub credentials, or Shipit account is required — only the ability to send a single crafted HTTP POST to the shared `/webhooks` endpoint with a signature computed from their own secret.

### Recommendation
Bind the verified signature to the same organization/repository namespace the handlers actually act on: derive `repository_owner` from `repository.full_name`'s owner segment (or verify that `repository.owner.login` and the owner portion of `repository.full_name` match) before dispatching to handlers, and reject the request if they diverge. Alternatively, pass the verified `repository_owner`/GithubApp identity into each `Handler` and have `stacks`/`repository_name` resolution scope lookups to that verified organization only, instead of trusting the raw JSON body's `repository.full_name` unconditionally.

### Proof of Concept
1. Configure (as in `docs/setup.md`) two GitHub Apps/orgs in `secrets.yml`: `org-a` (attacker-owned, secret known to attacker) and `org-b` (victim, has a Shipit `Stack` tracking `org-b/victim-repo`).
2. Build a `push` payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(org-a-secret, raw_body)>` using the attacker's own `org-a` webhook secret.
4. POST to `/webhooks` with header `X-Github-Event: push`.
5. `WebhooksController#verify_signature` calls `Shipit.github(organization: "org-a")` (from `repository.owner.login`) and successfully verifies the HMAC using `org-a`'s secret, per [1](#0-0) .
6. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("org-b/victim-repo")` and enqueues `sync_github(expected_head_sha: "<attacker-chosen-sha>")` on Organization B's stack, per [6](#0-5)  and [3](#0-2) , despite the request never being signed by Organization B's secret.

## Creating the GitHub App

Shipit needs a GitHub App to authenticate users, receive Webhooks and access the API.
