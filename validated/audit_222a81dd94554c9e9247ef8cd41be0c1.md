### Title
Webhook signature is verified against the organization derived from `repository.owner.login`, while the events are actually applied to the repository identified by `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/organization secret to validate the incoming webhook's HMAC signature against by reading `repository.owner.login` (or `organization.login`) out of the still-unauthenticated JSON body itself, then verifies the raw body against that org's `webhook_secret`. The event handlers, however, resolve the actual `Repository`/`Stack` to act on using a *different* field of the same payload, `repository.full_name`. Because `GitHubApp#verify_webhook_signature` explicitly returns `true` when the selected org has no `webhook_secret` configured, an attacker who can guess or discover the name of any configured organization that has no `webhook_secret` set can send an unsigned/unauthenticated request whose `repository.owner.login` points at that org, while `repository.full_name` points at a completely different, protected repository, and have the event handler act on it as if it were legitimately signed.

### Finding Description
- `verify_signature` picks the signing organization purely from payload content that has not yet been authenticated: [1](#0-0) [2](#0-1) 

- `GitHubApp#verify_webhook_signature` treats a missing `webhook_secret` as an automatic pass, with no signature check performed at all: [3](#0-2) 

- Once `verify_signature` passes (for *any* reason, including the org having no secret), `create` dispatches the entire raw JSON body to the event handlers: [4](#0-3) 

- The handlers, however, resolve which `Repository`/`Stack` the event is *for* using `repository.full_name`, a completely separate field from the one used to pick the verifying org: [5](#0-4) 

This is exactly the "organization authenticated vs. repository written" binding: the code verifies "does this body carry a valid signature for org X (from `repository.owner.login`)" but then acts as "apply this body's contents to repo Y (from `repository.full_name`)" without ever checking X == owner(Y). If X has no configured `webhook_secret`, the signature check is a no-op, and Y can be any stack tracked by the installation, including ones belonging to organizations that *do* have a properly configured `webhook_secret`.

Concretely, `StatusHandler` uses attacker-supplied `sha`/`state`/`context` to create a `CommitStatus` for any commit already known to Shipit, regardless of which org that commit's repository belongs to: [6](#0-5) 
Those statuses feed directly into `ci.require`/`ci.blocking` evaluation used by `DeploySpec`/`MergeRequest` to decide whether a commit is deployable/mergeable, so forging a `success` status for a required context can clear the gate for a deploy or an automated merge. [7](#0-6) [8](#0-7) 

### Impact Explanation
This breaks the binding "an organization that authenticated versus the repository that is written," matching the category explicitly called out as valid analog for this scan. An unprivileged attacker who has learned the name of any org onboarded to the Shipit instance without a `webhook_secret` (a legitimate, supported configuration state per `GitHubApp#initialize`/`verify_webhook_signature`) can:
- Send an unsigned POST to `/webhooks` with `X-Github-Event: status`, `repository.owner.login` = the secret-less org, and `repository.full_name`/`sha` pointing at a commit belonging to a different, protected stack.
- Have `StatusHandler` create arbitrary CI statuses for that commit, satisfying `ci.require`/blocking-status checks and enabling an **unauthorized deploy or merge** on a stack the attacker has no legitimate access to — one of the explicitly accepted High/Critical impacts for this program.

### Likelihood Explanation
Likelihood depends on the operator running a multi-organization Shipit App configuration where at least one onboarded org has no `webhook_secret` set (an explicitly supported code path, not a hypothetical misconfiguration the code rejects). Given that fallback path exists in `verify_webhook_signature` by design, and org names are frequently public/discoverable (they're GitHub org handles), this is readily reachable by an unprivileged network attacker with no Shipit session, API token, or GitHub write access.

### Recommendation
Bind signature verification to the same repository the handlers act on: derive the verifying organization from `repository.full_name`'s owner (not `repository.owner.login`/`organization.login`), or, better, verify the signature for every organization configured for that specific repository/stack and reject if none match. Additionally, reconsider silently accepting unsigned webhooks when `webhook_secret` is blank — at minimum, scope such trust to events whose `repository.full_name` belongs to that same secret-less org.

### Proof of Concept
1. Configure Shipit (as per supported multi-org config) with two orgs: `org-a` (no `webhook_secret`) and `org-b` (`webhook_secret` set, and it owns a real, protected stack tracked by Shipit, e.g. `org-b/protected-repo`).
2. As an unauthenticated network client, POST to `/webhooks` with:
   - `X-Github-Event: status`
   - No `X-Hub-Signature` header (or any bogus value)
   - Body:
     ```json
     {
       "sha": "<commit sha of org-b/protected-repo required-context commit>",
       "state": "success",
       "context": "<the ci.require context>",
       "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/protected-repo" }
     }
     ```
3. `verify_signature` resolves `Shipit.github(organization: "org-a")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally and the request passes.
4. `StatusHandler#process` looks up `Commit.where(sha: ...)` (belonging to `org-b/protected-repo`) and creates a forged `success` status for it, potentially satisfying the required CI check and unlocking an unauthorized deploy/merge on `org-b`'s stack, despite the attacker never possessing `org-b`'s `webhook_secret`.

Note: I was unable to fully trace `ci.require`/`blocking_statuses` gate logic to the exact deploy/merge decision points (deep files under `app/models/shipit/deploy_spec.rb`, `merge_request.rb`) beyond confirming they consume `CommitStatus` records populated by this handler; a Devin session with full file access would be needed to confirm the exact automated-merge or auto-deploy trigger paths in this specific engine version.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
