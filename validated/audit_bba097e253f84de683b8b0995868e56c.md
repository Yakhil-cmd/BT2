## Analysis

I traced the flag/value parsing loop in `scripts/gh.sh` and the downstream `gh` invocation to check whether an attacker-controlled search query starting with `-` could turn into command execution. [1](#0-0) 

The loop classifies each argv token as a flag (if it starts with `-` and its base name exactly matches an entry in `ALLOWED_FLAGS`) or as positional otherwise, and uses `skip_next` to consume the following token as that flag's value when the flag requires a value and doesn't use `=` syntax. [2](#0-1) 

Key points that defeat the hypothesized exploit:

1. **No shell re-interpretation of argument content.** `FLAGS` and `POSITIONAL` are bash arrays, and the final `gh` invocations expand them with `"${FLAGS[@]}"`/`"${POSITIONAL[0]}"` — properly quoted array expansions. [3](#0-2)  A string such as `--limit; rm -rf` stays a single argv token throughout; there is no `eval`, `sh -c`, or unquoted interpolation anywhere in the script, so embedded `;` or shell metacharacters are never parsed by a shell — they are passed to `gh` as literal argument text (which `gh` would reject as an invalid value, not execute).

2. **Exact-match flag comparison limits misclassification.** A token is only treated as an allowed flag if `"${arg%%=*}"` exactly equals one of `--comments`, `--state`, `--limit`, `--label`. [4](#0-3)  A query like `--limit; rm -rf` does not exactly equal `--limit`, so `matched=false` and the script exits with the "only ... flags are allowed" error before reaching `gh` at all. [5](#0-4) 

3. **Edge case where the query exactly equals an allowed flag name** (e.g. query is literally `--limit`) does cause misclassification: it's added to `FLAGS`, `skip_next` is set, and the next legitimate token gets consumed as its "value," shifting the arrays. However, the worst outcome is a malformed/erroring `gh` invocation or a wrong search string — not shell command execution, not privilege escalation, and not a bypass of the `repo:`/`org:`/`user:` qualifier check, since that check only inspects `POSITIONAL[0]` which is used verbatim, and it still only reaches `gh` as a literal argv string. [6](#0-5) 

4. The `--repo "$REPO"` scoping is always appended after the user-controlled `FLAGS`, so even if `FLAGS` is polluted, the command remains scoped to the configured repository. [7](#0-6) 

Since there is no code path where the misclassified flag/positional content is passed to a shell for interpretation, and the only allowed flags (`--comments`, `--state`, `--limit`, `--label`) do not themselves cause `gh` to execute arbitrary commands, the described attack (search query causing "downstream gh CLI to receive unintended flags" leading to `rm -rf` execution) does not have a viable exploit path in this script.

# Separate flags from positional arguments
POSITIONAL=()
FLAGS=()
skip_next=false
for arg in "$@"; do
  if [[ "$skip_next" == true ]]; then
    FLAGS+=("$arg")
    skip_next=false
  elif [[ "$arg" == -* ]]; then
    flag="${arg%%=*}"
    matched=false
    for allowed in "${ALLOWED_FLAGS[@]}"; do
      if [[ "$flag" == "$allowed" ]]; then
        matched=true
        break
      fi
    done
    if [[ "$matched" == false ]]; then
      echo "Error: only --comments, --state, --limit, --label flags are allowed (e.g., ./scripts/gh.sh issue list --state open --limit 20)" >&2
      exit 1
    fi
    FLAGS+=("$arg")
    # If flag expects a value and isn't using = syntax, skip next arg
    if [[ "$arg" != *=* ]]; then
      for vflag in "${FLAGS_WITH_VALUES[@]}"; do
        if [[ "$flag" == "$vflag" ]]; then
          skip_next=true
          break
        fi
      done
    fi
  else
    POSITIONAL+=("$arg")
  fi
done
