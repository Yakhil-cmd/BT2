### Title
Unauthenticated `membership` webhook forging grants access to `Shipit.github_teams` authorization - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
The Code4rena finding (M-21) is about a verification step trusting a coarse identifier (address) instead of the exact leaf content it should be bound to, letting an attacker satisfy the check without the intended per-item authorization. The same pattern exists in `Shipit`'s webhook pipeline: the *only* gate protecting the `membership` webhook event is a per-organization HMAC signature check that can be a no-op, while the event handler unconditionally trusts the payload to mutate `Team` membership — the very set consulted by `Shipit.github_teams` for application authorization.

### Finding Description
`WebhooksController#verify_signature` picks which organization's secret to check against based on a field taken straight from the untrusted payload (`repository.owner.login` or `organization.login`), then calls `GitHubApp#verify_webhook_signature`: [1](#0-0) [2](#0-1) 

`verify_webhook_signature` explicitly returns `true` when no `webhook_secret` is configured for that organization: [3](#0-2) 

The setup documentation itself marks the webhook secret as optional: [4](#0-3) 

So for any organization configured (in `secrets.github`) without a `webhook_secret`, `verify_signature` accepts *any* POST to `/webhooks` with an `X-Github-Event` header matching that org, without any cryptographic binding to GitHub at all.

Once accepted, `WebhooksController#create` dispatches the parsed body straight to the handler for the event: [5](#0-4) 

For `membership` events, `Shipit::Webhooks::Handlers::MembershipHandler#process` trusts the payload's `team.id` and `member.login` completely: it looks up or creates a `Team` by the raw `github_id` from the payload, resolves/creates a `User` by the raw `member.login`, and directly grants or revokes membership: [6](#0-5) 

`Team` records are the same records consulted by the authorization gate: `Authentication#force_github_authentication` requires the current user to belong to one of `Shipit.github_teams`: [7](#0-6) [8](#0-7) 

Because `find_or_create_team!` matches on `github_id` only, and a legitimate authorized team's `github_id` will already exist in the database (created earlier via `Team.find_or_create_by_handle`/`fetch_and_create_from_github`), a forged `membership` webhook whose `team.id` equals that already-known `github_id` will resolve to the *same* authorized `Team` row and add the attacker-chosen `member.login` to it — with no verification that this actually happened on GitHub.

The binding broken: "webhook accepted for organization X (or unconditionally, if X has no `webhook_secret`)" is treated as equivalent to "this specific `team`/`member` mutation genuinely originated from GitHub for that team," when in fact the per-leaf action (adding an arbitrary login to an arbitrary, potentially security-relevant `Team`) is never independently authenticated — it rides entirely on the coarse, sometimes absent, organization-level signature.

### Impact Explanation
An attacker who identifies (or already knows, e.g. by being a legitimate member of a Shopify org channel, or simply guessing/enumerating) the numeric GitHub `team.id` of a team listed in `Shipit.github_teams`, and finds/targets an organization entry in `secrets.github` that has no `webhook_secret` configured, can POST a forged `membership` webhook adding their own GitHub login to that authorized team. `User.find_or_create_by_login!` will fetch/create the corresponding `Shipit::User`, and on next login that user will pass `authorized?` and gain full access to the Shipit instance (deploy, rollback, merge capabilities) — an authorization-escalation into `Shipit.github_teams`, one of the explicitly listed High-impact outcomes.

### Likelihood Explanation
This requires: (1) at least one organization in the multi-tenant `secrets.github` config without a `webhook_secret` (explicitly documented as optional, so realistic for any operator who skips that optional field or for smaller/secondary orgs in a multi-org setup), and (2) knowledge of the target `Team`'s GitHub `team.id` (numeric IDs that are often enumerable/discoverable and not treated as secret). No GitHub credentials, Shipit session, or API token are required — only network access to the `/webhooks` endpoint, which is unauthenticated by design.

### Recommendation
- Do not allow `verify_webhook_signature` to silently succeed when `webhook_secret` is blank; require every configured organization to have a webhook secret, or reject/ignore mutating events (`membership`, `push`, etc.) for organizations without one.
- Make `MembershipHandler` (and other handlers that mutate authorization-relevant state) re-verify sensitive facts against the GitHub API (e.g., confirm the member is actually part of the team via `Shipit.github(organization:).api`) rather than trusting webhook payload fields for security-relevant grants.
- Scope `Team` matching in `find_or_create_team!` to also require the `organization` login to match the expected owner, and reconcile `github_id` collisions defensively.

### Proof of Concept
1. Configure (or find) an org entry in `secrets.github` without a `webhook_secret` (per `docs/setup.md`, this is optional) — e.g. organization `victim-org`.
2. Determine the numeric `github_id` of a `Team` already tracked by Shipit that is part of `Shipit.github_teams` (created via `Team.find_or_create_by_handle`).
3. Send, without any authentication or secret knowledge:
```
POST /webhooks
X-Github-Event: membership
Content-Type: application/json

{
  "action": "added",
  "team": { "id": <known_authorized_team_github_id>, "name": "Developers", "slug": "developers", "url": "https://github.com/x" },
  "organization": { "login": "victim-org" },
  "member": { "login": "attacker-github-login" }
}
```
4. `WebhooksController#verify_signature` resolves `github_app = Shipit.github(organization: "victim-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally [9](#0-8) .
5. `MembershipHandler#process` runs, finds the existing authorized `Team` by `github_id`, creates/finds `User` `attacker-github-login`, and calls `team.add_member(member)` [10](#0-9) .
6. Attacker authenticates via the normal GitHub OAuth flow with `attacker-github-login`; `User#authorized?` now returns `true` because the user belongs to a `Team` in `Shipit.github_teams` [8](#0-7) , granting full access to the Shipit application.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
```
