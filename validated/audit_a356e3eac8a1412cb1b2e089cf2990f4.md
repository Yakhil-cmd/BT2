### Title
Cross-repository status forgery advances merge queue via unscoped `Commit.where(sha:)` lookup - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits solely by `sha`, with no filter on the repository/stack that produced the webhook, unlike every other webhook handler in the codebase which resolves `repository = Shipit::Repository.from_github_repo_name(params.repository.full_name)` before touching any record. Because Git commit SHAs are content hashes that are identical across any repository containing byte-identical commit objects (e.g., a fork of the victim's repo, which necessarily shares SHAs with the upstream history), a `status` webhook that is fully authenticated for the attacker's own repository/organization can still write a `success` status onto a `Commit` row belonging to a completely different stack, driving that stack's `MergeRequest` toward `merge!`.

### Finding Description
The broken binding: `params.repository.full_name` (the repository the webhook signature authenticates) should equal `commit.stack.repository.full_name` (the repository whose `Commit`/`MergeRequest` gets mutated). It does not.

- `StatusHandler#process`:
```
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 
This queries `Commit` across **all stacks/repositories** by `sha` alone — `sha` is only unique per `(sha, stack_id)` per the DB index [2](#0-1) , confirming the schema itself expects the same sha to legitimately exist under multiple stacks. Every sibling handler (`OpenedHandler`, `ClosedHandler`, `LabeledHandler`, etc.) resolves `repository = Shipit::Repository.from_github_repo_name(params.repository.full_name)` first and scopes all further lookups through that repository/stack [3](#0-2) ; `StatusHandler` is the outlier that skips this scoping entirely.

`Handler#stacks`/`repository_name` exist as helpers precisely for this purpose but `StatusHandler` never uses them [4](#0-3) .

`create_status_from_github!` writes the status and, on transition to `pending`/`success`, schedules `ProcessMergeRequestsJob` for the commit's own `stack` [5](#0-4) [6](#0-5) . `ProcessMergeRequestsJob#perform` then calls `merge_request.refresh!`, `merge_request.all_status_checks_passed?`, and if true, `merge_request.merge!` [7](#0-6) . `all_status_checks_passed?` evaluates `StatusChecker.new(head, head.statuses_and_check_runs, ...).success?` [8](#0-7) , and `merge!` calls `stack.github_api.merge_pull_request(...)` [9](#0-8) .

Signature verification (`verify_signature`) authenticates the webhook per **organization** derived from `params['repository']['owner']['login']` via `Shipit.github(organization: repository_owner)` [10](#0-9) . This correctly proves the payload originated from GitHub for that organization/app installation — but it says nothing about which repository's sha-namespace the payload should be allowed to affect. It authenticates the sender, not the target scope, so it does not stop the divergence: an attacker with a GitHub App installation on their own account/org (or any org configured in Shipit that the attacker controls a repo in) can legitimately post/receive a real, correctly-signed `status` event for **their own** repository, whose payload's `sha` field the attacker fully controls the meaning of merely by forking the victim's repository (a fork shares identical commit SHAs with upstream by construction) and setting a commit status on that shared sha via the ordinary GitHub Status API.

Exploit flow:
1. Attacker forks/clones the victim repository (public read access), obtaining a local copy containing the exact same commit object (identical SHA) as the victim's open PR head, which is queued in the victim stack's merge queue (`merge_queue_enabled?` true, `MergeRequest#pending?`).
2. Attacker's own repository (with the GitHub App/webhook installed on an org/account the attacker controls) posts a `success` status on that shared sha via ordinary GitHub commit-status API calls against their own repo.
3. GitHub sends a genuinely signed `status` webhook to Shipit for the attacker's repository/organization; `verify_signature` passes because it is a real GitHub webhook for that org.
4. `StatusHandler#process` ignores `params.repository` and does `Commit.where(sha: params.sha)`, matching the victim stack's `Commit` row by sha alone, and calls `commit.create_status_from_github!(params)`, writing a `success` status onto the victim's commit.
5. `Commit#add_status` schedules `ProcessMergeRequestsJob` for the **victim** stack.
6. The job calls `all_status_checks_passed?` → true, then `merge_request.merge!` → `stack.github_api.merge_pull_request` merges the victim's PR — with no direct interaction with the victim repository by the attacker at all.

### Impact Explanation
This is an unauthorized merge of a queued pull request in the victim repository, triggered entirely by a status the attacker forged against their own repository. It is a Critical-severity finding under "a payload for one repository mutating another's stack/commit/task/team" / "an unauthorized deploy, rollback or merge." The attack is repeatable against any victim stack with the merge queue enabled, as long as the attacker can obtain a repository (a fork, or any repo sharing identical commit content/SHA) with commits that coincide by SHA with a pending merge request's head — trivially achievable via forking, since forks preserve upstream commit SHAs verbatim. Blast radius spans any tenant/stack configured with `merge_queue_enabled?` in the installation.

### Likelihood Explanation
Preconditions are modest and attacker cost is low: the attacker needs (a) a public/forkable victim repository with the merge queue enabled and a pending `MergeRequest`, and (b) any repository under an organization/account where Shipit's GitHub App/webhook is installed and under the attacker's control (their own fork/org), so they can post a genuine, correctly-signed webhook. No Shipit credentials, session, or GitHub token belonging to the victim are required — only ordinary GitHub actions on repositories the attacker owns. This is highly feasible and repeatable.

### Recommendation
Scope `StatusHandler#process` (and its `Commit` lookup) to the repository identified in the webhook payload, mirroring every other handler: resolve `repository = Shipit::Repository.from_github_repo_name(params.repository.full_name)`, and restrict the `Commit` query to `commit.stack.repository == repository` (e.g., `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { id: repository.id })`) before calling `create_status_from_github!`.

### Proof of Concept
Minitest plan (model/handler-level, no live GitHub):
1. Create two stacks/repositories: `victim_stack` (repository `victim/repo`, `merge_queue_enabled: true`) and `attacker_stack`/repository (`attacker/repo`).
2. Create a `Commit` under `victim_stack` with `sha: "deadbeef..."` and a pending `MergeRequest` whose `head` is that commit; stub `head.statuses_and_check_runs` requirements so that `all_status_checks_passed?` becomes `true` only once a `success` status exists.
3. Also create a `Commit` under `attacker_stack` with the **same** `sha: "deadbeef..."`.
4. Build a `status` webhook payload with `sha: "deadbeef..."`, `state: "success"`, and `repository.full_name: "attacker/repo"`.
5. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly (bypassing controller-level signature verification, which is out of scope for this bug and assumed to pass legitimately).
6. Assert: `victim_commit.reload.statuses.count` increased by 1 (status was written to the victim's commit despite the payload naming `attacker/repo`).
7. `Shipit.github.api.expects(:merge_pull_request).once` and run `ProcessMergeRequestsJob.perform_now(victim_stack)`; assert it is called, proving the victim PR is merged as a direct result of a status webhook that only referenced the attacker's own repository — with `assert_equal victim_merge_request.reload.merge_status, "merged"` (or equivalent completed state) as the final assertion on the broken binding (`params.repository.full_name` "attacker/repo" != `commit.stack.repository.full_name` "victim/repo").

    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?
      end

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end
    end
