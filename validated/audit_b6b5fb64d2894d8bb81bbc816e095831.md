### Title
Unfunded `recapitalize` books phantom cash and refunds real tokens to an arbitrary payer — the pool applies an invalid "config" (a cash credit whose funding was never verified) instead of keeping the prior valid state - (File: contracts/pool/src/ops/recapitalize.rs)

### Summary
`Pool::recapitalize` credits `cash` and refunds the excess to `payer` purely on the caller's word, without measuring the pool's token balance before/after. This mirrors CVE-2021-46943's class: an invalid input (a cash "settlement" that never settled) overwrites the previously valid accounting, and the corrupted book later drives over-sized payouts — the on-chain equivalent of the kernel's 4 GiB allocation. `recapitalize` is listed among the permissionless controller entrypoints (`scripts/permissionless_entrypoints.txt`), and the pool explicitly does not re-validate the inbound transfer, trusting the controller's payment path.

### Finding Description
`recapitalize::accounting` computes `applied = min(amount, backing_shortfall)`, calls `cache.credit_cash(applied)` and `cache.commit()`, then `apply` unconditionally executes `outcome.cache.transfer_out(&payer, outcome.refund)` where `refund = amount - applied` — a real token transfer out of pool custody to the caller-chosen `payer`. [1](#0-0) 

There is no balance check anywhere: the pool README states `supply`, `repay` and `recapitalize` "all credit `cash` on the controller's word, without verifying the transfer", and the only `token.balance()` reconciliation in the contract is inside `flash_loan`. [2](#0-1) 

The codebase's own pool test proves the failure mode end-to-end: `test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody` calls `recapitalize` for the full custody balance with no funding transfer, the pool's token balance drops to 0 while the `cash` book still reports the full deposit, and a subsequent supplier `withdraw` passes `require_reserves` (which reads the book) only to fail inside the SAC transfer — a pool that reports itself solvent but cannot pay. [3](#0-2) 

Any direct token transfer made to the pool before the call is also invisible: `refund` is computed from `amount` and the shortfall only, never from an observed balance delta, so a caller can combine or omit funding and still steer the refund.

### Impact Explanation
Two concrete impacts, both reachable in one call by an unprivileged address via the controller `recapitalize` entrypoint:

1. **Theft of pool funds.** With `amount > backing_shortfall`, `transfer_out(payer, refund)` sends real tokens to `payer`. If the controller path does not first pull `amount` from the caller (the pool cannot distinguish funded from unfunded calls, as the test demonstrates), the refund leg pays out existing supplier custody to the attacker.
2. **Permanent freezing / insolvency.** `credit_cash(applied)` inflates the book without custody. `require_reserves` and the solvency guards read the book, so exits are admitted and then abort inside the token transfer (`BalanceError` 10), permanently freezing suppliers' withdrawals and letting borrows draw on non-existent liquidity. [4](#0-3) 

### Likelihood Explanation
The trigger is a single call with `(hub_asset, payer = attacker, amount)` chosen above the backing shortfall — no timing, price, or governance precondition. The only mitigating factor is whatever the controller does before delegating: the pool-layer invariant "tokens arrived before any cash-crediting call" is unenforced on-chain, and the pool test shows the corrupted state is committed and survives rollback-free. If the controller's `recapitalize` performs a strict `token.transfer` from the caller of exactly `amount` before invoking the pool, the theft leg collapses to a wash; the phantom-cash bookkeeping hazard remains for any path where the inbound transfer is partial or routed elsewhere (the pool cannot tell).

### Recommendation
Measure settlement instead of trusting it: in `recapitalize::apply`, record `token.balance(pool)` before crediting, require `applied <= balance_after - balance_before` (or snapshot-then-verify as `flash_loan` already does with strict equality), and compute `refund` from the observed delta rather than `amount - applied`. Revert without committing `cache` when the inbound transfer is short, so the previous valid `cash` is never overwritten by an unverified config — exactly the fix the CVE applies to `set_fmt`.

### Proof of Concept
The repository already contains the executable PoC in `contracts/pool/tests/flows.rs::test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody`:

1. Supplier deposits 10,000,000,000 units; `cash == token.balance(pool)` (fixture guard).
2. Attacker calls `recapitalize(hub_asset, payer = attacker, custody)` with no funding; `token.balance(pool) == 0`, `state.cash >= deposit`.
3. Supplier calls `withdraw` → passes `require_reserves` on the book → reverts with SAC `BalanceError` (10), receiver balance 0, book still overstated.

Reproduced verbatim in the pool test-suite; reachability through the controller depends on whether its `recapitalize` handler performs a prior exact-amount pull transfer, which is the single unverified link in this chain.

pub(crate) fn accounting(
    env: &Env,
    hub_asset: HubAssetKey,
    amount: i128,
) -> RecapitalizationOutcome {
    require_nonneg_amount(env, amount);
    let mut cache = ops::renewed_market(env, &hub_asset);

    let applied = amount.min(guards::backing_shortfall(&cache));
    let refund = amount
        .checked_sub(applied)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow));

    cache.credit_cash(applied);
    cache.commit();
```

#[test]
fn test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody() {
    let t = TestSetup::new();
    let token = token::Client::new(&t.env, &t.asset);
    let token_admin = token::StellarAssetClient::new(&t.env, &t.asset);
    let payer = Address::generate(&t.env);
    let receiver = Address::generate(&t.env);

    // A legitimate supplier, with custody moved in as the controller would.
    let deposit = 10_000_000_000i128;
    token_admin.mint(&t.pool, &deposit);
    let supplied = t
        .client()
        .supply(&t.sup(0, deposit))
        .get_unchecked(0)
        .position
        .scaled_amount;
    assert_eq!(
        t.state_snapshot().cash,
        token.balance(&t.pool),
        "fixture guard: book and custody must still agree after the deposit"
    );

    // Drain every token via an unfunded refund.
    let custody = token.balance(&t.pool);
    t.client().recapitalize(&hub(&t.asset), &payer, &custody);
    assert_eq!(token.balance(&t.pool), 0, "custody is gone");

    let book = t.state_snapshot().cash;
    assert!(
        book >= deposit,
        "the book still claims more than the supplier's deposit: {book}"
    );

    // The supplier's exit clears the pool's own liquidity guard -- the book
    // says the cash is there -- and then fails in the token transfer.
    let outcome = t
        .client()
        .try_withdraw(&receiver, &false, &t.wdr(supplied, i128::MAX, 0));
    assert!(
        outcome.is_err(),
        "the withdraw cannot be paid, so it must fail"
    );
```
