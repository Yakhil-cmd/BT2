### Title
Webhook signature verification is silently bypassed when a GitHub organization has no configured `webhook_secret`, allowing unauthenticated `membership` events to add arbitrary users to `Shipit.github_teams`-authorized teams - (File: lib/shipit/github_app.rb)

### Summary
`WebhooksController#verify_signature` delegates authentication of every inbound `/webhooks` payload to `GitHubApp#verify_webhook_signature`. That method returns `true` unconditionally whenever the resolved organization has no `webhook_secret` configured, which is an explicitly supported, documented configuration state. In that state, none of the payload fields are covered by any verification at all, and an unauthenticated caller can POST a crafted `membership` event that gets processed by `MembershipHandler`, creating/looking up a `Team` and adding an arbitrary `User` (by GitHub login) to that team. If that team is one of `Shipit.github_teams`, this directly grants the attacker-chosen account access to the entire Shipit instance, bypassing the `authorized?` gate in `app/controllers/concerns/shipit/authentication.rb`.

### Finding Description
The bug-class in the reference report is: a state-changing operation (`transfer`) is allowed to silently overwrite/act on protected storage because the identifying key (`paymentId`) is not actually bound/verified against prior state, letting an unprivileged caller manipulate a value that should only be settable once by a trusted, prior action.

The analogous binding here is: **"the organization identified as authenticating a webhook" MUST equal "the organization whose HMAC secret cryptographically verified the payload."** This binding is broken by design in the fallback branch of the verifier: [1](#0-0) 

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```

`webhook_secret` is populated straight from `config[:webhook_secret]`, which the project's own setup documentation marks as **optional**: [2](#0-1) 

The controller entry point trusts this verifier completely and only rejects the request with a 422 if `verified` is falsy — when `webhook_secret` is blank, `verified` is always `true`, so **every** field of the payload (`X-Github-Event`, `organization.login`, `team.*`, `member.login`, `action`) is accepted with zero cryptographic authentication: [3](#0-2) 

For the `membership` event, `MembershipHandler#process` trusts these unauthenticated fields to find-or-create a `Team` and to find-or-create a `User` by login fetched live from `Shipit.github.api.user(login)`, then unconditionally appends that user as a team member when `action == 'added'`: [4](#0-3) [5](#0-4) 

Team membership is exactly the record used by the authorization gate that determines whether a logged-in GitHub user is allowed to use the Shipit instance at all: [6](#0-5) [7](#0-6) 

**Before the attacker's request:** the attacker's own GitHub account (or any account they choose by login) is not a member of any team configured in `Shipit.github_teams`, so `current_user.authorized?` is `false` and the app renders `403 Forbidden`.

**After the attacker's request:** by POSTing an unsigned `membership` webhook naming their own login as `member.login` and an existing `Shipit.github_teams` team's GitHub `id`/`slug` as `team`, the attacker's `User` record gains a `Membership` row to that `Team`. On their next OAuth login, `authorized?` now evaluates `true`, and they are granted full access to the Shipit instance (viewing/creating deploys, stacks, tasks, etc., subject to further per-action checks) — despite having never gone through GitHub's real team-membership grant.

### Impact Explanation
This is a genuine authentication/authorization bypass reachable by a fully unauthenticated network attacker (no Shipit session, no `ApiClient` token, no GitHub App private key, no repository write access required — only knowledge of the organization login and team id/slug/name, several of which are discoverable via GitHub's public API). It matches the report's High-impact bucket: "escalation into `Shipit.github_teams` authorization." Because it stems purely from the engine's own `verify_webhook_signature` short-circuit and the unauthenticated processing pipeline in `WebhooksController`/`MembershipHandler`, it is not dependent on the host failing to mount the engine as documented — it is present in any properly-mounted installation that follows the documented "webhook secret (optional)" setup instructions in `docs/setup.md`.

### Likelihood Explanation
Likelihood is meaningfully gated by whether the operator configured a `webhook_secret` for the targeted organization. The project explicitly documents the secret as optional (`docs/setup.md`, `config/secrets.development.example.yml` show `webhook_secret: # nil`), so it is reasonable to expect real-world deployments — especially ones that never intended to receive third-party integrations, or that were bootstrapped from the example template without changing every field — to run with this field blank for one or more configured organizations. No rate limiting or additional authentication guards this endpoint beyond the signature check itself, and the payload shape required by `MembershipHandler` is small and fully documented by GitHub's own webhook payload schema.

### Recommendation
Change `verify_webhook_signature` to fail closed instead of fail open when `webhook_secret` is blank (e.g., reject/422 the request, or require `Shipit.github(organization:)` to be considered misconfigured/disabled for webhook processing until a secret is set), rather than treating "no secret configured" as "signature verified." At minimum, `MembershipHandler` (and any other handler that mutates authorization-relevant state such as team membership) should not process events for organizations lacking a configured `webhook_secret`.

### Proof of Concept
Preconditions: organization `acme` is configured in Shipit without a `webhook_secret` (a documented-as-optional configuration), and team `acme/admins` (github team id `123`) is listed in `Shipit.github_teams`.

1. Attacker logs into Shipit via GitHub OAuth with their own low-privilege GitHub account (`attacker-login`); `authorized?` is `false`, so they get `403 Forbidden`.
2. Attacker sends, without any `X-Hub-Signature` header (or any arbitrary value — it is never checked when the secret is blank):

```
POST /webhooks HTTP/1.1
Host: shipit.example.com
X-Github-Event: membership
Content-Type: application/json

{
  "action": "added",
  "team": { "id": 123, "name": "Admins", "slug": "admins", "url": "https://api.github.com/teams/123" },
  "organization": { "login": "acme" },
  "member": { "login": "attacker-login" }
}
```

3. `WebhooksController#verify_signature` calls `Shipit.github(organization: 'acme').verify_webhook_signature(nil, raw_post)`, which returns `true` because `webhook_secret` is blank [1](#0-0) .
4. `MembershipHandler#process` runs, creating/finding `Team` `acme/admins` and `User` `attacker-login`, then calls `team.add_member(member)` [4](#0-3) .
5. Attacker reloads the Shipit UI (or re-authenticates); `current_user.authorized?` now returns `true` because their `User` has a `Membership` in `acme/admins`, one of `Shipit.github_teams` [6](#0-5) , granting them access to the application.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

        request.raw_post

      head(422) unless verified

    end
