### Title
TPS-fee anti-spam calculation depends on the poster-chosen distance between unit timestamp and `last_ball_unit` timestamp, allowing fee-window manipulation - (File: storage.js)

### Summary
`storage.getLocalTps`/`getLocalTpsFee` compute the anti-spam TPS fee as `count / elapsed`, where `elapsed = objUnitProps.timestamp - objLastBallUnitProps.timestamp`. This is structurally the same bug class as the reported TWAP issue: a rate/average is computed over a window whose length is entirely determined by the distance between two attacker-influenceable points (here, the new unit's own `timestamp` and the `timestamp` of the `last_ball_unit` the author chooses to reference), rather than a fixed, protocol-enforced window.

### Finding Description
`getLocalTps` in [1](#0-0)  walks back from `objUnitProps` through its DAG ancestry to `last_ball_mci`, counting units, and divides that count by `elapsed = objUnitProps.timestamp - objLastBallUnitProps.timestamp` (falling back to a constant `elapsedTimeWhenZero` only if the difference is exactly 0). `getLocalTpsFee` then feeds this `tps` value into the fee formula `base_tps_fee * (exp(tps/tps_interval) - 1)` at [2](#0-1) .

Both `objUnitProps.timestamp` (the new unit's own declared timestamp) and `objUnitProps.last_ball_unit` (hence its timestamp, `objLastBallUnitProps.timestamp`) are chosen by the unit's author when composing the unit, via `parent_composer.pickParentUnitsAndLastBall` [3](#0-2) . Unlike the timestamp itself, which is checked only against "not too far in the future" in `validation.js`, there is no check enforcing that `last_ball_unit`'s timestamp be recent relative to the new unit's timestamp — only that it be a valid stable ancestor ball reachable from the parents. The same `elapsed` computation is used again at validation time in `validateTpsFee` at [4](#0-3) , which calls the identical `storage.getLocalTpsFee` with an `objUnitProps` built directly from the untrusted `objUnit.last_ball_unit` and `objUnit.timestamp` fields [5](#0-4) .

By deliberately referencing an older-than-necessary but still valid stable `last_ball_unit` (maximizing `elapsed` while minimizing the ancestor `count`), an unprivileged unit poster can artificially depress the computed local `tps`, and thus the required anti-spam `min_tps_fee`, well below what actually reflects the current network load. Conversely, by referencing a very recent `last_ball_unit` close to the unit's own timestamp, `elapsed` shrinks toward zero and `tps` spikes, which — combined with the `min_acceptable_tps_fee` floor derived from `storage.getCurrentTpsFee`/`getMinAcceptableTpsFeeMultiplier` [6](#0-5)  — can be used to force other addresses' otherwise-valid low-fee units to look artificially cheap or, in the reverse direction, to game the multiplier used elsewhere.

### Impact Explanation
The TPS fee mechanism is ocore's core anti-spam/anti-DoS defense that gates how many units the network will accept per unit time (the "network unable to confirm new units" scenario this defense exists to prevent). Because the fee owed is derived from a self-selected, unbounded "distance from last ball" window analogous to the reported TWAP timeframe bug, an attacker can pick the window that minimizes their `min_tps_fee` requirement in `validateTpsFee`, evading the intended fee scaling that should track actual recent throughput. This directly weakens the anti-spam guarantee that TPS fees are supposed to enforce network-wide, which is the same functional guarantee that the analog TWAP price bug undermines (a value that should reflect real conditions over a fixed window instead reflects an attacker-chosen window).

### Likelihood Explanation
Any account composing a normal unit controls `timestamp` and (within DAG-validity constraints) can select which stable ball to reference as `last_ball`/`last_ball_unit`, provided it is an ancestor of the chosen parents. No special privilege (witness/OP, hub, or protocol-level access) is required — this is reachable by ordinary "posted unit" construction, matching the required threat-model (unprivileged unit poster). The exact bound on how far back a valid `last_ball_unit` can be chosen while other DAG-parent constraints are satisfied was not fully verified from available code (validation.js's constraints on parent/last_ball freshness were only partially inspected within reasoning-budget limits), so the magnitude of exploitable time skew is not fully quantified here.

### Recommendation
Do not let the TPS-fee window depend solely on the author-chosen `last_ball_unit`/`timestamp` pair. Instead, bound `elapsed` to the network's own measured time (e.g., derive it from the MC's own advancing timestamps at fixed, protocol-defined MCI intervals, as already done for the network-wide `getCurrentTps`/`getCurrentTpsFee` calculation) or clamp `last_ball_mci`/`last_ball` staleness relative to the unit's own MCI so that an attacker cannot lengthen or shrink the counted window merely by choice of ancestor ball.

### Proof of Concept
Conceptual PoC (based on code paths, not executed):
1. Compose a unit A from address X with `timestamp = T`.
2. Instead of referencing the freshest valid stable ball as `last_ball_unit` (as the normal composer flow does via `pickParentUnitsAndLastBall`), manually set `last_ball_unit` to an older stable ball `B` whose `timestamp = T - Δ` for a large `Δ`, while still satisfying DAG ancestor/parent constraints.
3. `storage.getLocalTps` computes `elapsed = T - (T-Δ) = Δ` (large), driving `tps → count/Δ` toward 0, hence `getLocalTpsFee` and the `min_tps_fee` required by `validateTpsFee` toward the base rate regardless of actual current network load.
4. Submit many such units cheaply, each individually passing `validateTpsFee`'s `min_tps_fee`/`min_acceptable_tps_fee` checks despite high real-time load, undermining the anti-spam fee scaling.

Full confirmation that DAG/parent-selection rules permit arbitrarily old `last_ball_unit` choices (vs. being constrained to the freshest available ball) requires further review of `parent_composer.js`/`validation.js`'s free-unit and best-parent selection logic beyond what was inspected here.

async function getLocalTps(conn, objUnitProps, count_units = 1) {
	const unit = objUnitProps.unit;
	const objLastBallUnitProps = await readUnitProps(conn, objUnitProps.last_ball_unit);
	const elapsed = (objUnitProps.timestamp - objLastBallUnitProps.timestamp) || elapsedTimeWhenZero;
	const last_ball_mci = objLastBallUnitProps.main_chain_index;
	let count = count_units;
	let visited = {};
	let arrProps = [objUnitProps];

	while (true) {
		let arrParentProps = [];
		for (let props of arrProps) {
			if (!props.best_parent_unit)
				throw Error(`no best parent in props of ${props.unit}`);
			const parent_units = props.unit === unit ? [props.best_parent_unit] : props.parent_units;
			for (let parent_unit of parent_units) {
				if (visited[parent_unit])
					continue;
				const parentProps = await readUnitPropsWithParents(conn, parent_unit);
				if (parentProps.main_chain_index <= last_ball_mci && parentProps.main_chain_index !== null)
					continue;
				if (!parentProps.bAA) // AA responses are counted elsewhere via max_aa_responses of their trigger
					count += getCountUnitsPayingTpsFee(parentProps);
				visited[parent_unit] = true;
				arrParentProps.push(parentProps);
			}
		}
		if (arrParentProps.length === 0)
			break;
		arrProps = arrParentProps;
	}
	if (count === count_units && last_ball_mci > 0 && constants.COUNT_WITNESSES > 1)
		throw Error(`getLocalTps count=${count}, elapsed=${elapsed}, ${JSON.stringify(objUnitProps)}`);
	return count / elapsed;

async function getLocalTpsFee(conn, objUnitProps, count_units = 1) {
	const objLastBallUnitProps = await readUnitProps(conn, objUnitProps.last_ball_unit);
	const last_ball_mci = objLastBallUnitProps.main_chain_index;
	const base_tps_fee = getSystemVar('base_tps_fee', last_ball_mci); // unit's mci is not known yet
	const tps_interval = getSystemVar('tps_interval', last_ball_mci);
	const tps_fee_multiplier = getSystemVar('tps_fee_multiplier', last_ball_mci);
	const tps = await getLocalTps(conn, objUnitProps, count_units);
	console.log(`local tps at ${objUnitProps.unit} ${tps}`);
	const tps_fee_per_unit = Math.round(tps_fee_multiplier * base_tps_fee * (exp(tps / tps_interval) - 1));
	return count_units * tps_fee_per_unit;
}
