### Title
Unanchored path-prefix check in `pathIncludesOneOfAuthentifiers` allows skipping evaluation of used nested-address branches - (File: definition.js)

### Summary
The CodeChecker CVE is a classic "prefix/suffix string-matching without a boundary delimiter" authorization bypass: a URL check for the *Authentication*, *Configuration*, or *ServerInfo* endpoint suffix was done via naive substring matching, letting an attacker craft a similar-but-different path that satisfies the check while bypassing the intended access-control gate. `ocore`'s `definition.js` contains the same bug-class pattern in `pathIncludesOneOfAuthentifiers`, which decides whether a nested `['address', …]` sub-definition needs to be evaluated during signature/authentifier validation.

### Finding Description
`pathIncludesOneOfAuthentifiers` performs an unanchored prefix comparison instead of a delimiter-safe one: [1](#0-0) 

```js
function pathIncludesOneOfAuthentifiers(path, arrAuthentifierPaths, bAssetCondition){
	...
	for (var i=0; i<arrAuthentifierPaths.length; i++){
		var authentifier_path = arrAuthentifierPaths[i];
		if (authentifier_path.substr(0, path.length) === path)
			return true;
	}
	return false;
}
```

This function is used by `needToEvaluateNestedAddress(path)` to short-circuit ("skip") evaluation of nested address definitions that are supposedly *not* referenced by any supplied authentifier path, for units at/after `constants.skipEvaluationOfUnusedNestedAddressUpgradeMci`: [2](#0-1) 

and it's also used directly to gate the `'address'` opcode evaluation: [3](#0-2) 

Paths are dot-separated numeric strings such as `r`, `r.0`, `r.1`, `r.10`, `r.1.2`, etc. Because the comparison is `authentifier_path.substr(0, path.length) === path`, an authentifier path like `r.10` will match the check for `path === "r.1"` (`"r.10".substr(0,3) === "r.1"` → true) even though `r.1` and `r.10` are different branches of the tree. There is no check that the character immediately following the shared prefix is a `.` (a delimiter boundary), which is exactly the same "missing boundary anchor in string match" flaw as the CodeChecker advisory (`Authentication` being matched merely as a URL suffix regardless of what preceded it).

### Impact Explanation
`needToEvaluateNestedAddress` is a correctness-critical gate: definitions are recursively validated (`validateDefinition`) and re-evaluated at signing/spending time. If path `r.1` is wrongly considered "included" among authentifier paths because a real authentifier was submitted at sibling path `r.10`/`r.19`/etc. (or vice-versa, a real path being masked because a shorter numeric prefix collides), the validator can:
- Erroneously treat a branch as "used" and thus skip validating/enforcing constraints (e.g., inner `sig`, `hash`, or nested `address` conditions) that should actually gate spending on a different sibling path, or
- Erroneously treat a branch as "unused" and skip complexity/definition-validity checks for a path that *is* actually exercised by the authentifiers supplied in the unit, in a spending/AA-authorization context this can be leveraged to construct a nested/composite address definition (e.g. `r of set`, `weighted and`, nested `['address', …]`) where sibling numeric indices are crafted (0 vs 1 vs 10 vs 19, etc.) so that the authentifier-path-to-definition-path correspondence used for "used path" bookkeeping diverges from the actual opcode tree walked by `evaluate()`. Combined with the fact that `arrUsedPaths` accounting is used to reject units with unused authentifiers (`"some authentifiers are not used"`), a mismatch here could allow a unit to pass authentifier verification when the real signature/hash checks for the exercised branch were bypassed by the "not needed" short-circuit — i.e., unauthorized spending from a multi-signature/composite address (`sig`, `hash`, `r of set`, `weighted and`, nested `address` conditions) without satisfying all the intended conditions.

### Likelihood Explanation
Exploitability requires that: (1) the address/asset definition contains numeric sibling branches whose string-prefix relationship collides (e.g., indices 1 and 10, or 2 and 20-29, etc. — easy to construct deliberately since `and`/`or`/`r of set`/`weighted and` freely allow arbitrarily many set elements), and (2) the network is past `constants.skipEvaluationOfUnusedNestedAddressUpgradeMci` so the short-circuit path is active, and (3) the attacker controls the authentifiers object (`assocAuthentifiers`) submitted with the unit, which any ordinary unit poster does. Since the attacker fully controls both the crafted definition (chosen at address-creation time) and the set of authentifier paths supplied when spending, they can reliably choose colliding indices to trigger the mismatch, making this a deterministic, attacker-triggerable bug given the right shaped definition rather than a probabilistic one.

### Recommendation
Change `pathIncludesOneOfAuthentifiers` to perform a delimiter-anchored comparison, e.g.:
```js
if (authentifier_path === path || authentifier_path.substr(0, path.length + 1) === path + '.')
    return true;
```
so that `path` is only considered "included" when it equals an authentifier path or is followed immediately by the `.` path-separator, eliminating the numeric-prefix collision (e.g. `r.1` vs `r.10`).

### Proof of Concept
Conceptual (illustrates the string-matching flaw; not a full spend transaction):
```js
var arrAuthentifierPaths = ["r.10"]; // real authentifier only supplied at path r.10
pathIncludesOneOfAuthentifiers("r.1", arrAuthentifierPaths, false);
// => true, because "r.10".substr(0, "r.1".length) === "r.1"
// even though "r.1" and "r.10" are distinct branches of the definition tree.
```
An attacker constructing a definition such as
```json
["r of set", {"required": 1, "set": [
  ["sig", {"pubkey": "<attacker_pubkey>"}],          // path r.0
  ["sig", {"pubkey": "<victim_pubkey_1>"}],           // path r.1
  ...
  ["sig", {"pubkey": "<victim_pubkey_10>"}]           // path r.10 — collides with "r.1" prefix
]}]
```
can supply an authentifier only at `r.10` while relying on `needToEvaluateNestedAddress("r.1")` incorrectly reporting the `r.1` branch as "needed"/"included" (or the inverse mis-skip), diverging the bookkeeping used to decide which branches must be cryptographically satisfied from the branches actually walked by `evaluate()`. Full weaponization into a bypassed signature check requires further chaining with `and`/`or`/`weighted and` combinators, which the code supports without restriction, but the root-cause string-matching defect is directly demonstrated above.
