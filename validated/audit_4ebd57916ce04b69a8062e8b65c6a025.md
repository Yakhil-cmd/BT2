### Title
AA authors relying on `trigger.initial_address` for authorization can be tricked by a malicious intermediary AA in a chained trigger (tx.origin-style confused-deputy) - (File: aa_composer.js)

### Summary
The reported issue is that a Connext relayer executing an untrusted `xReceive` contract can be drained if the foreign code checks `tx.origin` instead of the immediate caller, letting a malicious contract in the call path impersonate the relayer. The ocore equivalent is `oscript`'s AA-to-AA trigger chaining mechanism, where `trigger.address` is the *immediate* caller (equivalent to `msg.sender`) while `trigger.initial_address` is the *original* human/unit that started the whole chain of AA responses (equivalent to `tx.origin`), and it is propagated unchanged through every hop of a secondary-trigger chain, no matter how many untrusted AAs relay the payment in between.

### Finding Description
`getTrigger()` builds a fresh `trigger` object for every unit that pays an AA, using the immediate author of that unit as `trigger.address`: [1](#0-0) 

`handleTrigger()` only sets `trigger.initial_address`/`trigger.initial_unit` once, at the very first (primary) trigger, and leaves it untouched afterward: [2](#0-1) 

When an AA response itself pays another AA address, `handleSecondaryTriggers()` builds a *child* trigger whose `address` is the calling AA (the new "immediate sender"), but it explicitly copies `initial_address`/`initial_unit` from the parent trigger, so it always still points at the original human unit author, however many AAs are chained in between: [3](#0-2) 

This mirrors the classic `tx.origin` vs `msg.sender` confusion: `trigger.address` is the safe, cryptographically-attributable “immediate caller”, while `trigger.initial_address` is a value that persists across an arbitrary number of hops through code that the destination AA does not control or trust (any secondary AA can be attacker-authored, exactly like the unreliable `xReceive` code in the original report). Documentation and sample AAs in the repo actively encourage using `trigger.initial_address` to route funds/refunds back to "the original sender" across AA chains, e.g.: [4](#0-3) [5](#0-4) 

If an AA author instead uses `trigger.initial_address` (rather than `trigger.address`) as an authorization key — e.g. `if (trigger.initial_address == var['owner'])`, or `var[trigger.initial_address] += ...` to credit a balance/permission — a malicious secondary AA that a victim user's payment happens to be routed through (directly or via a multi-hop chain of AAs, including ones the victim never intended to trust) can craft its own outgoing `data`/`payment` messages while the platform still stamps the resulting trigger with the original human's `initial_address`. The malicious AA fully controls the `data` payload and the `outputs` of its own response unit (i.e., which address ultimately receives funds), so it can steer the victim AA into performing an action that is gated on "this request originates (at some point in history) from address X" while directing the *effects* (fund withdrawal, state mutation) to itself.

### Impact Explanation
Any AA that authorizes privileged operations (withdrawals, permission grants, state changes crediting/debiting balances) using `trigger.initial_address` instead of `trigger.address` is exposed to a confused-deputy attack: a malicious AA anywhere along a forwarding chain can impersonate the original initiator for authorization purposes while redirecting the actual fund flow or state effects to itself. This is a medium-risk footgun in the oscript/AA execution model (same severity classification and same root cause as the reported Connext issue), reachable by any unprivileged AA author who defines a forwarding/chaining AA, and by any user who is lured into sending a trigger through such a chain.

### Likelihood Explanation
Likelihood is moderate: it requires (1) a victim AA design that authorizes on `trigger.initial_address` rather than `trigger.address`, and (2) a payment/data path that routes through an attacker-controlled intermediary AA before reaching the victim AA (e.g. proxy/aggregator/forwarding AAs, which are a common and documented AA pattern in this codebase, as seen in the "chain of AAs" and remote-function-calling test patterns). Because the platform actively provides and encourages `trigger.initial_address` for cross-hop routing without documenting the authorization pitfall, AA authors are likely to reach for it in exactly the wrong context (permission checks) rather than only for refund routing.

### Recommendation
Document explicitly (in the oscript/AA reference) that `trigger.initial_address` must never be used for authorization/access-control decisions, only `trigger.address` (the immediate, cryptographically-verified caller) should be used for that purpose — analogous to the "never use `tx.origin` for authorization" guidance in Solidity. Consider adding a lint/warning in AA validation (`validation.js`/formula validation) when `trigger.initial_address` is compared for equality against a stored/state address in a `bounce`/guard context, to help AA authors avoid this footgun.

### Proof of Concept
1. User Alice sends bytes to Proxy AA `P` (a legitimate, benign forwarding AA she trusts) that simply forwards payments plus `trigger.data` to whatever AA address is specified in the trigger payload.
2. Attacker crafts a message so that `P` forwards Alice's payment to a malicious AA `M`.
3. `M`'s response sends a payment/data message to Victim AA `V`. Because `M`'s response unit is a secondary trigger, `handleSecondaryTriggers()` sets `child_trigger.address = M` (correct — the immediate sender) but leaves `child_trigger.initial_address = Alice` (aa_composer.js:1722-1727, unchanged from the top of the chain).
4. `V`'s oscript contains logic such as `if (trigger.initial_address == var['owner']) { pay(trigger.data.amount, trigger.data.to); }`, intending "only the original account owner (Alice) can direct a payout." Because `trigger.initial_address` is still Alice's address, the check passes even though `M` (untrusted) crafted `trigger.data.to` and `trigger.data.amount`.
5. `M` sets `trigger.data.to` to its own address, causing `V` to pay out Alice-authorized funds to `M` instead of Alice, without Alice ever directly interacting with `M` or `V`.

```javascript
function getTrigger(objUnit, receiving_address) {
	var trigger = { address: objUnit.authors[0].address, unit: objUnit.unit, outputs: {} };
	if ("max_aa_responses" in objUnit)
		trigger.max_aa_responses = objUnit.max_aa_responses;
	objUnit.messages.forEach(function (message) {
		if (message.app === 'data' && !trigger.data) // use the first data message, ignore the subsequent ones
			trigger.data = message.payload;
		else if (message.app === 'payment' && message.payload) {
			var payload = message.payload;
			var asset = payload.asset || 'base';
			payload.outputs.forEach(function (output) {
				if (output.address === receiving_address) {
					if (!trigger.outputs[asset])
						trigger.outputs[asset] = 0;
					trigger.outputs[asset] += output.amount; // in case there are several outputs
				}
			});
		}
	});
	if (Object.keys(trigger.outputs).length === 0)
		throw Error("no outputs to " + receiving_address);
	return trigger;
}
```
