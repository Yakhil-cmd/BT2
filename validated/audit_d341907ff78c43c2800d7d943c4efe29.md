### Title
Missing sender-authorization check on remote signing requests lets any paired device trigger local signing for addresses it does not co-sign - ([File: wallet.js])

### Summary
`ocore--005`'s wallet-side handler for the `"sign"` device message (used for both multisig-same-address signing and multilateral/"dumb-contract" signing) never verifies that the peer device asking for a signature (`from_address`) is actually a legitimate cosigner of the wallet that owns `body.address`. The relevant authorization check exists in the source but is explicitly commented out, mirroring the `act` Artifacts V4 bug class where a caller-supplied identifier (`workflow_run_backend_id` in `act`, `body.address`/`from_address` here) is accepted and used to trigger privileged control-plane behavior without checking it belongs to the requester.

### Finding Description
In `wallet.js`, the `"sign"` case of `handleMessageFromHub` validates the shape of the request (address format, signing path format, unit structure, private-payload hashes) but delegates the actual authorization decision to `findAddress`, and in the `ifLocal` callback the developer explicitly disabled the ownership check: [1](#0-0)

`findAddress` itself only checks whether `body.address`/`body.signing_path` resolves to a locally-hosted key (`row.device_address === device.getMyDeviceAddress()`); it never checks who sent the request: [2](#0-1) 

Because the ownership/authorization comparison (`sender is a cosigner of this wallet`) is commented out — exactly as `validateRunIDV4` in the `act` advisory left the run-ID ownership comparison commented out — any device that is merely *paired* with the wallet (not necessarily a cosigner of the specific multisig/shared address in question) can send a `"sign"` message naming any local address/signing path it can guess or learn, and the wallet will:
1. Accept the request (`callbacks.ifOk()`), confirming that this exact address/signing_path is hosted locally.
2. Fire the `signing_request` event with an attacker-supplied `unsigned_unit` (and `assocPrivatePayloads`), which downstream UI/automation layers use to solicit/produce a signature: [3](#0-2) 

The `ifRemote` branch of `findAddress`, by contrast, still performs the correct check (`other_device_addresses.includes(from_address)`) before forwarding: [4](#0-3) 

showing that the intended design (and the comment) is aware ownership *should* be checked for local signing too, but it was intentionally left out to support multilateral signing, without narrowing the exemption to cases where that is actually appropriate (e.g., non-multisig/dumb-contract addresses).

### Impact Explanation
This lets an unprivileged, paired counterparty (any device that has previously exchanged pairing with the victim wallet — analogous to the "AA trigger sender / paired device" actor class in scope) probe and drive the signing workflow for wallet addresses it has no legitimate right to co-sign:
- It can confirm the existence/local-hosting of an address+signing_path combination (address/key enumeration).
- It can inject an arbitrary `unsigned_unit`/`private_payloads` for that address and force the wallet to raise a `signing_request` event, which is the same code path that ultimately produces a valid signature share for a multisig transaction chosen by the attacker.
- In any automated/headless consumer of this event (bots, exchange or service wallets that programmatically respond to `signing_request` without a human-verified confirmation each time), this can be leveraged to obtain unauthorized signature shares for spending/asset-moving units, i.e., loss of funds from a shared/multisig address, matching the "unauthorized spending" impact bar required by the analog rules.

### Likelihood Explanation
Reaching this path requires only that the attacker's device be paired with the victim (a normal, low-privilege relationship established for legitimate correspondents, contract counterparties, or shared-address cosigners), and knowledge/guess of `body.address` and `body.signing_path` for a locally hosted key — both of which are shared during normal shared-address setup (`new_shared_address`, `create_new_shared_address` messages) and thus learnable by any device that was ever a counterparty in a shared address, even for a different signing path than the one it is actually authorized for. No cryptographic secret or hub compromise is needed, since the missing check is purely in application-level authorization logic.

### Recommendation
Restore an authorization check in the `ifLocal` branch of the `"sign"` handler that verifies `from_address` is a legitimate cosigner for `body.address` (or, if multilateral/"dumb contract" signing genuinely requires accepting signing requests from non-cosigner correspondents, restrict that exemption narrowly to the specific address types/paths where a foreign author signs a different address in the same unit, rather than removing the check for every locally-hosted address/signing path). At minimum, ensure automated/headless consumers of `signing_request` re-validate `from_address` against the address's `wallet_signing_paths`/`shared_address_signing_paths` before producing or forwarding a signature.

### Proof of Concept
1. Device B pairs with Device A (owner of wallet `W`) through any legitimate pairing flow (e.g., as a shared-address cosigner candidate, or simply a correspondent added via `new_shared_address`/contract flows) — this reveals or lets B learn a valid `(address, signing_path)` pair hosted on A that B is *not* actually authorized to co-sign (e.g., a path belonging to a different cosigner set).
2. B sends A a hub message:
   ```json
   {
     "subject": "sign",
     "body": {
       "address": "<A's locally hosted address>",
       "signing_path": "<valid path for that address>",
       "unsigned_unit": { "authors": [{"address": "<A's address>", "authentifiers": {"r": ""}}], "messages": [ ... attacker-chosen payment ... ] }
     }
   }
   ```
3. On A, `handleMessageFromHub` reaches the `"sign"` case, passes all structural checks, and `findAddress` resolves `ifLocal` because the address/path is hosted locally on A — with no verification that B is entitled to request a signature for this address.
4. `callbacks.ifOk()` is returned to B, and `eventBus.emit("signing_request", ...)` fires with B's crafted `unsigned_unit`, driving A's wallet toward producing a signature for a transaction B constructed, despite B never being an authorized cosigner for that specific address/path.

		FROM my_addresses JOIN wallets USING(wallet) JOIN wallet_signing_paths USING(wallet) \n\
		WHERE address=? AND signing_path=?",

			if (rows.length > 1)
