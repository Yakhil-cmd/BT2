### Title
Unauthenticated Node Crash via Crafted `spend_proofs` Address Mismatch in Payment Validation - ([File: validation.js])

### Summary
`checkForDoublespends()`, invoked from `validateSpendProofs()` while validating any posted unit containing a private-payment `spend_proofs` placeholder, contains a `throw Error(...)` sanity check that assumes a returned conflicting record's `address` will always be one of the current unit's author addresses. An unprivileged unit poster can violate this assumption with a single crafted unit, turning the assumed-unreachable branch into an unhandled exception that crashes every full node that validates the unit — analogous to CVE-2020-14702, where a network-reachable actor triggers an unhandled server condition resulting in a repeatable crash / complete denial of service.

### Finding Description
When a unit contains a `payment` message with `payload_location: "none"` (a private-payment placeholder), the unit must supply `spend_proofs`, each with a `spend_proof` hash and an optional `address` (defaulting to the first author's address): [1](#0-0) [2](#0-1) 

The SQL query filters `spend_proofs` rows by the exact `(spend_proof, address)` pair supplied by the attacker, and `checkForDoublespends()` compares the returned row's `address` against the current unit's author addresses: [3](#0-2) 

```js
if (arrAuthorAddresses.indexOf(objConflictingRecord.address) === -1)
    throw Error("conflicting "+type+" spent from another address?");
``` [4](#0-3) 

Because `spend_proofs` records (spend_proof hash + address, without any private payload data) are public and observable on the network (broadcast as part of any private-payment carrier unit), an attacker can:
1. Observe an existing `(spend_proof, address)` pair belonging to some other, unrelated address that is already stored in the `spend_proofs` table.
2. Craft their own unit, authored by their own address(es), with a `spend_proofs` entry reusing that exact `spend_proof` value and explicitly setting `address` to the foreign address from step 1 (the field is attacker-controlled per-entry, per `objSpendProof.address`).
3. Post/broadcast this unit.

The SQL query in `validateSpendProofs` matches on the attacker-supplied `(spend_proof, address)` pair, so the returned `objConflictingRecord.address` will equal that foreign address — which is not among `arrAuthorAddresses` of the attacker's unit — causing the `throw Error(...)` sanity check to fire.

This `throw` occurs deep inside asynchronous callback chains under `mutex.lock` in `validation.validate()`/`handleJoint()`, i.e., not inside a `try/catch` that funnels back to `ifUnitError`. It becomes an uncaught exception, which the global handler in `network.js` deliberately re-throws to crash the process: [5](#0-4) 

Since every full node that receives and validates this broadcast unit runs the identical logic, the crash is deterministic and reproducible across the network — a "frequently repeatable crash" as in the CVE, rather than a single-node fluke.

### Impact Explanation
A single crafted unit posted by any ordinary, unprivileged user can crash every full node (and hub) that validates it, since `handleJoint`/`validation.validate` is invoked on every node receiving the broadcast unit. This meets the "network unable to confirm new units" bar: a coordinated or repeated posting of such units can be used to repeatedly crash/restart full nodes network-wide, disrupting consensus availability. This matches CVSS Availability-only impact of the referenced CVE.

### Likelihood Explanation
Likelihood is high: no special privileges, witness status, or AA authorship is required — only the ability to author and broadcast a normal unit with a `payment` message using `payload_location: "none"` and a `spend_proofs` array, plus knowledge of one publicly-visible `(spend_proof, address)` pair already present in another node's `spend_proofs` table (obtainable by observing broadcast private-payment carrier units). No cryptographic secret or private data (the payment amount/payload) is required — only the hash and address fields, which are transmitted in the clear.

### Recommendation
Change the sanity-check `throw Error(...)` in `checkForDoublespends()` (validation.js line ~1673) into a soft validation failure (`return cb2("conflicting "+type+" spent from another address")` or similar) that gets routed to `ifUnitError`, instead of crashing the process. More generally, audit other `throw Error` statements inside `validateMessages`/`checkForDoublespends`/`validateAuthor` code paths that are reachable from externally-supplied unit content, to ensure attacker-influenced data cannot trigger developer "should never happen" assertions that terminate the process.

### Proof of Concept
1. Monitor the network for any broadcast unit containing a `payment` message with `payload_location: "none"` and a `spend_proofs` entry; record its `spend_proof` hash and `address`.
2. Construct a new unit authored by an attacker-controlled address, with a `payment` message (`payload_location: "none"`) whose `spend_proofs` array contains one entry: `{ spend_proof: <observed_hash>, address: <observed_foreign_address> }`.
3. Broadcast the unit to the network.
4. On every full node, `validateSpendProofs` → `checkForDoublespends` finds the row (`address` = observed foreign address) not present in `arrAuthorAddresses` of the attacker's unit, executes `throw Error("conflicting spend proof spent from another address?")`, which propagates as an uncaught exception and crashes the node process via the `process.on('uncaughtException')` handler.
