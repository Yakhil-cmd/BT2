### Title
Unhandled `throw` in data-feed tie-break comparator crashes node during AA trigger evaluation - (File: data_feeds.js)

### Summary
`readDataFeedValue()` in `data_feeds.js` sorts candidate unstable data-feed messages with a comparator that `throw`s a bare `Error` whenever two candidates cannot be strictly ordered (i.e., they tie on both `latest_included_mc_index` and `level`). This is structurally the same bug class as ALPINE-CVE-2026-42009: a comparator responsible for ordering items by sequence-like keys does not correctly/safely handle duplicate/tied keys, producing undefined behavior — here an uncaught synchronous exception instead of the DTLS reordering corruption, but with the same denial-of-service consequence.

### Finding Description
`readDataFeedValue` collects candidate values from `storage.assocUnstableMessages` for `data_feed` messages authored by unstable/AA units, then sorts them: [1](#0-0) 

```js
arrCandidates.sort(function (a, b) {
    if (a.latest_included_mc_index < b.latest_included_mc_index)
        return -1;
    ...
    if (a.level < b.level) return -1;
    if (a.level > b.level) return 1;
    if (bIncludeAllUnstable) // still ambiguous, sort randomly (it's OK outside AAs)
        return 1;
    throw Error("can't sort candidates "+a+" and "+b);
});
```

`bIncludeAllUnstable` is only true when `unstable_opts === 'all_unstable'`. The call site in `formula/evaluation.js` for the `data_feed` oscript operator passes `bAA` (a boolean) as `unstable_opts`: [2](#0-1) 

Since `bAA` is `true`/`false` and never the string `'all_unstable'`, `bIncludeAllUnstable` is always `false` inside AA trigger/formula evaluation. Consequently, whenever two or more parallel unstable candidate messages (from `storage.assocUnstableMessages`, populated by units posted by any user/AA, filtered only by `sequence==='good'` and matching author addresses/mci range) tie on both `latest_included_mc_index` and `level`, the comparator throws a synchronous `Error` from inside `Array.prototype.sort`, which is not caught anywhere on the call path (`getDataFeed` → `dataFeeds.readDataFeedValue` → sort callback). There is no global `uncaughtException` handler protecting this path (only `network.js` installs one, unrelated to formula evaluation), so this throw propagates out of the synchronous sort call and crashes the Node.js process.

This is directly analogous to the reported CVE: a sort/ordering comparator that is supposed to totally order items by sequence-like fields (`latest_included_mc_index`, `level`) fails to gracefully handle a duplicate/tied case, causing undefined behavior (here: an unhandled exception) instead of a defined fallback ordering — exactly the "duplicate sequence numbers not handled correctly" bug class, but reachable from any address able to get its unit accepted into the DAG (not merely a hostile peer/TLS endpoint).

### Impact Explanation
Two independent, unstable units at the same DAG level, both containing `data_feed` messages for the same `feed_name` matching the query filters (same value or `value===null`), authored by addresses within the queried `arrAddresses` set and with the same `latest_included_mc_index`, are enough to trigger the throw the moment any AA (or trigger evaluation, since `bAA` gates unstable inclusion) calls `data_feed[[...]]` over that address set with `ifseveral` not `'abort'` (default is `'last'`). Because units at the same level, from parallel branches, commonly share the same `latest_included_mc_index` in ordinary DAG operation, this is not a contrived edge case — any AA author or a user racing two units into parallel branches referencing the same oracle addresses can trigger it deterministically once accepted by the network. Since the throw is deterministic and would occur identically on every full node processing the AA trigger (as this happens during consensus-critical AA/trigger evaluation), it results in every node that evaluates this trigger crashing, which stops the network from confirming further units that depend on processing this AA — a network-wide denial of service, matching the "network unable to confirm new units" acceptance bar.

### Likelihood Explanation
Reachable by an ordinary unprivileged AA author defining a data_feed[[...]] read over oracle addresses, combined with any user (or the AA/oracle addresses themselves) posting two sibling units at the same level with matching data-feed content and equal `latest_included_mc_index`. No special network position, hub/peer compromise, or leaked key is required — only crafting/posting units, which is exactly the trust boundary this scan is scoped to (unprivileged unit poster / AA trigger sender).

### Recommendation
Remove the `throw` from the comparator in `readDataFeedValue` (data_feeds.js) and replace it with a deterministic, always-total tie-breaker (e.g., fall back to comparing `unit` hash lexicographically) regardless of `bIncludeAllUnstable`, so ties are resolved deterministically instead of throwing. Additionally, wrap `Array.prototype.sort` calls that can encounter attacker-influenced data with defensive comparators that never throw, and consider catching/reporting formula-evaluation errors instead of letting them propagate as uncaught exceptions.

### Proof of Concept
1. Deploy/observe an AA (or any oscript context evaluated with `bAA=true`) that reads `data_feed[[oracles="ADDR1:ADDR2", feed_name='x', ifseveral="last"]]` (default `ifseveral` is `'last'`, not `'abort'`).
2. Have two units, each posted by one of `ADDR1`/`ADDR2` (or by AAs sending responses on their behalf), each containing message `{app:'data_feed', payload:{x: <same value or arbitrary if value filter is null>}}`, constructed as parallel free units at the same DAG level with the same `latest_included_mc_index` (e.g., both units have identical parent sets besides themselves, submitted concurrently referencing the same last stable ball).
3. Once both units are accepted as unstable ("good" sequence) and the AA/trigger evaluates the `data_feed[[...]]` expression referencing both addresses, `readDataFeedValue` builds `arrCandidates` with two entries having equal `latest_included_mc_index` and equal `level`.
4. `arrCandidates.sort(...)` reaches the final branch and executes `throw Error("can't sort candidates ...")`, crashing the node process handling this trigger evaluation (data_feeds.js lines 255-267, formula/evaluation.js line 646).
