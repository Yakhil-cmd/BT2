## Title
Hookify PreToolUse hook fails open (silently allows dangerous Bash/Write/Edit operations) on any rule-engine error, config parse failure, or missing dependency - (File: `plugins/hookify/hooks/pretooluse.py`)

### Summary
The external report describes a Chainlink oracle function that has no fallback path when the price feed becomes unavailable, causing `latestRoundData` to revert and deny service. The closest reachable analog in this repository is the `hookify` plugin's `PreToolUse` executor, which enforces user-defined "block" rules (e.g. blocking dangerous `rm -rf`, sensitive file edits) before a tool call runs. Instead of the oracle's problem (fail-closed DoS), this code has the inverse and more severe defect: on *any* failure of the security-check dependency chain — import failure, malformed `.claude/hookify.*.local.md`, JSON parse error, or any exception in `RuleEngine.evaluate_rules` — the hook silently falls back to **allowing** the tool call rather than blocking it, defeating the very enforcement the plugin exists to provide.

### Finding Description
`pretooluse.py` is registered as a `PreToolUse` hook and is responsible for evaluating user-authored blocking rules against `Bash`/`Write`/`Edit`/`MultiEdit` tool calls before they execute [1](#0-0) .

If the `hookify` package cannot be imported (e.g. `CLAUDE_PLUGIN_ROOT` unset, corrupted install, Python path issue), the script does not block — it prints a system message and exits `0`, which is the "allow" outcome for the hook contract: [2](#0-1) 

The `main()` function wraps rule loading and evaluation in a single broad `try/except Exception`, and its `finally` clause unconditionally calls `sys.exit(0)` — i.e., no matter what fails (stdin JSON parse error, `load_rules()` raising, `RuleEngine.evaluate_rules()` raising), the tool call proceeds unblocked: [3](#0-2) 

This fail-open behavior compounds with `config_loader.load_rules()`, which independently swallows I/O errors, parsing errors, and any unexpected exception per rule file, silently dropping the corresponding rule from the active set rather than surfacing a hard failure: [4](#0-3) 

The rule engine itself is the sole mechanism that turns a matched "block" rule into a `permissionDecision: "deny"` output: [5](#0-4) 

Since every failure mode upstream of this function (import error, load error, evaluation exception) results in exit 0 with no deny decision, an attacker-controlled or environment-triggered failure (a malformed rule file, an encoding error, a path issue after plugin reinstall, etc.) causes the security check to be skipped entirely rather than defaulting to a safe/blocking state — the same root-cause pattern as the reported issue (a single external dependency failure removes the safety check), but here it manifests as a concrete authorization bypass instead of merely a revert/DoS.

### Impact Explanation
`hookify` rules are the user's explicit safety net for blocking dangerous Bash commands (e.g. `rm -rf`) or edits to sensitive files. When the dependency chain backing this check fails for any reason, the tool call that should have been denied is instead silently allowed to execute with no warning beyond a `systemMessage` that many callers may not surface prominently. This is a direct approval-bypass of a locally configured tool-authorization control, allowing unauthorized shell/file actions to proceed exactly during the failure window that a user would expect the control to be most necessary (e.g. because the rule file itself is malformed/corrupted).

### Likelihood Explanation
The trigger surface is broad and easily reached without any privilege escalation: a syntactically malformed `.claude/hookify.*.local.md` file, an environment where `CLAUDE_PLUGIN_ROOT` is briefly unset during plugin reload, a Unicode/encoding issue in a rule file, or any unexpected exception in the hand-rolled YAML-ish frontmatter parser (`extract_frontmatter`) is sufficient to disable the block. Because the parser in `config_loader.py` is custom (not a standard, well-tested YAML library) and is intentionally permissive about error handling ("log and continue"), the probability of hitting an unhandled parsing edge case in ordinary rule authoring is non-trivial, and every such case fails open.

### Recommendation
Invert the default: when rule loading or evaluation cannot complete successfully, fail closed for any rule set that includes `action: block` semantics — or at minimum, clearly distinguish "no rules matched" from "rules could not be evaluated" in the hook's JSON output and deny (or explicitly ask) rather than silently exiting 0. Concretely:
- In `pretooluse.py`, do not blanket-catch `Exception` and exit 0; on unexpected errors, return a `permissionDecision: "ask"` (or `"deny"`) hookSpecificOutput so the user is prompted/blocked rather than silently passed through.
- In `config_loader.load_rules()`, surface load/parse failures to the caller (e.g. via a status flag) instead of only logging to stderr and dropping the rule, so `pretooluse.py` can decide to fail closed when a rule file it depends on is unreadable/malformed.
- Add a regression test asserting that a corrupted rule file or a `RuleEngine` exception does not result in tool execution proceeding unchecked.

### Proof of Concept
1. Create `.claude/hookify.test.local.md` with an intentionally malformed frontmatter/body that triggers an unhandled exception inside `RuleEngine._check_condition` or `extract_frontmatter` (e.g. a condition dict missing required keys causing a `KeyError` that isn't in the caught tuple, or any not-yet-anticipated exception type).
2. Configure the same rule to `action: block` for `Bash` commands matching `rm -rf`.
3. Invoke a `Bash` tool call with `rm -rf /some/path`.
4. Observe that `pretooluse.py`'s `except Exception` branch fires, prints a `systemMessage`, and calls `sys.exit(0)` with no `permissionDecision: "deny"` — the destructive command is passed straight through, even though the rule author explicitly intended it to be blocked [6](#0-5) .

```python
def main():
    """Main entry point for PreToolUse hook."""
    try:
        # Read input from stdin
        input_data = json.load(sys.stdin)

        # Determine event type for filtering
        # For PreToolUse, we use tool_name to determine "bash" vs "file" event
        tool_name = input_data.get('tool_name', '')

        event = None
        if tool_name == 'Bash':
            event = 'bash'
        elif tool_name in ['Edit', 'Write', 'MultiEdit']:
            event = 'file'

        # Load rules
        rules = load_rules(event=event)

        # Evaluate rules
        engine = RuleEngine()
        result = engine.evaluate_rules(rules, input_data)

        # Always output JSON (even if empty)
        print(json.dumps(result), file=sys.stdout)

    except Exception as e:
        # On any error, allow the operation and log
        error_output = {
            "systemMessage": f"Hookify error: {str(e)}"
        }
        print(json.dumps(error_output), file=sys.stdout)

    finally:
        # ALWAYS exit 0 - never block operations due to hook errors
        sys.exit(0)
```
