### Title
Unreferenced-limit-free fetch + pre-worktree `reset --soft` permanently pins oversized attacker-supplied history in `git.root`, causing unrecoverable disk exhaustion on `createWorktree` failure - ([File: main.go])

### Summary
`repoSync.SyncRepo` runs `git fetch` (unbounded by any size limit) and then unconditionally executes `git reset --soft remoteHash --` to update the ref *before* attempting `createWorktree`. If `createWorktree` subsequently fails (e.g., disk-full triggered by the fetch itself), the fetched objects are already resident in `.git/objects` and now reachable from the updated ref, so they are never eligible for garbage collection, and the failure path skips `cleanup()` entirely, leaving the disk pressure permanent until an operator manually intervenes.

### Finding Description
In `main.go`, `SyncRepo` calls `git.fetch(ctx, git.ref)` [1](#0-0)  with no flag or code path that bounds the total byte size of fetched objects — only `--depth` (commit depth, not byte size) is supported [2](#0-1) . After fetching, `SyncRepo` performs `git reset --soft remoteHash --` against `git.root` (not the worktree) before calling `createWorktree` [3](#0-2) . This reset moves the branch/ref pointer to `remoteHash`, making every newly fetched object reachable from that ref regardless of whether `createWorktree` subsequently succeeds.

`createWorktree` uses `--no-checkout`, so its own disk footprint is minimal (just worktree admin metadata) [4](#0-3) ; a disk-full condition here plausibly occurs immediately after a huge fetch has consumed nearly all remaining space. When `createWorktree` returns an error, `SyncRepo` returns immediately [5](#0-4) , and the outer sync loop only calls `git.cleanup(ctx)` (which does worktree pruning, reflog expiry, and `git gc`) in the success branch, not on error [6](#0-5) . Even if `cleanup` did run, the objects are reachable from the just-reset ref, so `git gc` would not reclaim them. On the next sync attempt, the fetch of the same ref is cheap (objects already present) and only `createWorktree` is retried — meaning the huge object set never gets re-evaluated or discarded, and disk pressure persists indefinitely until the operator manually clears `--root` or frees space.

No existing flag limits object/pack size; `--depth` only reduces commit depth, not blob/tree size, so a single huge blob still transfers in full during fetch.

### Impact Explanation
This is a resource-exhaustion / permanent-stall condition: an attacker who controls the content of the repository/ref that git-sync is configured to fetch (per the given threat model) can push an oversized blob or history once, causing `--root`'s disk usage to permanently balloon with content that is unreachable from any published worktree/symlink yet un-collectible by GC. This matches the "permanent sync wedging or resource exhaustion" impact class — the sidecar's volume fills and stays filled, potentially crashing or degrading the pod and any other containers sharing the volume, without a code-driven recovery path.

### Likelihood Explanation
No non-default flags are required beyond normal operation (`--repo`, `--root`); this is default git-sync behavior with no fetch-size-limiting mechanism available at all. It requires the attacker to be able to write oversized content to the ref git-sync is watching (consistent with the "attacker controls repo content and refs" precondition) and requires the target volume to be modestly size-constrained relative to the pushed history so `createWorktree` fails after `fetch`+`reset` succeed — a realistic scenario for any bounded PVC.

### Recommendation
- Ensure `cleanup()` (or an equivalent GC/prune pass) also runs on the failure path, and specifically after a fetch/reset succeeded but worktree creation failed, so unreachable-by-worktree data can at least be evaluated for collection when safe.
- Consider not moving the root's ref (`reset --soft`) until after `createWorktree` succeeds, so a failed worktree creation doesn't leave the fetched commit reachable and permanently retained.
- Add an optional fetch size/byte cap (e.g., via `git.filter`/partial clone with size limits, or a new `--max-fetch-size`-style flag) so operators can bound how much untrusted repo content can be pulled per sync.

### Proof of Concept
Integration test sketch:
1. Create a local bare repo; mount `--root` on a small (e.g. 50MB) tmpfs/loopback filesystem.
2. Push a single huge blob (>40MB) to the ref git-sync watches.
3. Run `git-sync` once against this constrained root.
4. Assert: `git fetch` succeeds (fills most of the volume), `reset --soft` succeeds, `createWorktree`'s `git worktree add` fails with ENOSPC.
5. Assert `SyncRepo` returns an error, the error-file (`--export-error`) or logs show the ENOSPC failure (honesty check), and `du -sh $ROOT/.git` remains large across a subsequent forced re-run (proving the fetched objects were retained and not reclaimed by any cleanup pass), demonstrating the volume stays wedged near-full indefinitely.
