### Title
Webhook signature is verified against the organization named in the payload, but the handlers write to repositories/commits chosen from separate, uncross-checked payload fields - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the HMAC against using a value taken from the very payload being verified (`repository.owner.login` or `organization.login`). Once that per-organization signature check passes, the whole raw payload is handed to handlers that resolve *which repository or commit to mutate* using different fields of the same payload (`repository.full_name` in `Handler#repository_name`, or a bare `sha` lookup with no repository scope in `StatusHandler`). Nothing ties the identity used to select the verifying secret to the identity of the resource actually written. Anyone who controls a legitimate `webhook_secret` for one organization configured on this Shipit instance can therefore forge a validly-signed payload whose `repository.owner.login` matches their own org (so the correct secret is picked and the HMAC passes) while `repository.full_name`/`sha` target a completely different organization's repository or commit.

### Finding Description
Signature verification: [1](#0-0) 

`repository_owner` is derived straight from the untrusted, not-yet-verified JSON body: [2](#0-1) 

`Shipit.github(organization: repository_owner)` selects the `GithubApp`/`webhook_secret` used only for that organization, and `verify_webhook_signature` HMACs the *entire* raw body with that secret: [3](#0-2) 

After verification, the same raw payload is dispatched to handlers via `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`: [4](#0-3) 

`Handler#stacks`/`#repository_name` resolve the target repository from `payload.dig('repository', 'full_name')` - a field independent of `repository_owner`, which was only used to pick the verifying secret: [5](#0-4) 

`PushHandler` then syncs any stack matching that (attacker-chosen) `full_name`/branch to an attacker-chosen `after` sha: [6](#0-5) 

`StatusHandler` is even less scoped: it matches commits purely by `sha` with no repository/organization filter at all, so a forged `status` event can attach an arbitrary state (e.g. `success`) to any commit sha existing in *any* stack tracked by the instance: [7](#0-6) 

That forged "success" status is exactly what `Commit#deployable?` and `Stack#next_expected_commit_to_deploy` rely on to decide continuous-deployment eligibility: [8](#0-7) [9](#0-8) 

**Binding broken:** `organization authenticated by verify_signature == organization/repository whose state the handlers write` is assumed but never enforced. The equality that should hold is:
`repository_owner (used to pick webhook_secret) == repository.full_name.owner (used to select the Repository/Stack acted upon)` — this is never checked; both are independently attacker-controlled fields of the same signed blob, and the signature only proves "some secret holder signed this exact byte string," not "the org that owns that secret owns the repository referenced inside it."

### Impact Explanation
On a Shipit instance configured with multiple GitHub organizations (the documented multi-org `github:` config in `docs/setup.md`), anyone who legitimately controls (or has compromised) the webhook secret for *one* onboarded organization can:
- Force `GithubSyncJob`s for any stack belonging to any other tracked organization/repository via a forged `push` event (`PushHandler`).
- Forge CI `status` events (`state: success`) for arbitrary commit shas across any stack on the instance, bypassing real CI and enabling continuous-deployment logic (`Commit#deployable?`, `Stack#trigger_continuous_delivery`) to authorize an unauthorized deploy of a repository the attacker has no legitimate relationship with.

This crosses the "organization authenticated vs. repository written" trust boundary and results in an unauthorized deploy / cross-repository write, matching the Critical/High impact bar (unauthorized deploy; cross-repository writes).

### Likelihood Explanation
Requires only knowledge of one organization's already-configured `webhook_secret` on a multi-tenant Shipit deployment (e.g. an org admin who legitimately manages that org's GitHub App, but has no Shipit account, no `ApiClient` token, and no access to any other organization's repositories). No Shipit session or repository write access is needed for the target repository — only the ability to send an HTTP POST to `/github_webhooks` (or equivalent mounted path) with a forged payload signed with their own org's secret.

### Recommendation
After verifying the signature, re-derive the organization/repository actually referenced by the payload fields the handlers use (`repository.full_name`, or the owner encoded in it) and require it to match `repository_owner` used to select the verifying secret. Additionally, scope `StatusHandler`'s `Commit.where(sha:)` lookup to commits belonging to stacks under the verified organization, rather than a global, repository-agnostic sha match.

### Proof of Concept
1. Attacker administers GitHub org `attacker-org`, which is one of several organizations configured in this Shipit instance's `github:` secrets, and knows its `webhook_secret`.
2. Attacker crafts a JSON body for a `status` event:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/private-repo" },
  "sha": "<sha of a commit on victim-org/private-repo tracked by this Shipit instance>",
  "state": "success"
}
```
3. Attacker computes `sha1=HMAC(webhook_secret_of_attacker_org, raw_body)` and sends it as `X-Hub-Signature`, with `X-Github-Event: status`.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")` (from `repository.owner.login`), successfully verifies the HMAC using `attacker-org`'s secret.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the victim's commit regardless of organization — and calls `create_status_from_github!`, marking it `success`.
6. If `victim-org`'s stack has continuous deployment enabled, this forged green status can trigger an automatic deploy of that commit, none of which the attacker was authorized to influence.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)

        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
