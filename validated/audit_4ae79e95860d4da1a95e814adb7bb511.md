### Title
StatusHandler updates commit statuses for any stack whose commit shares a sha, without validating `params.repository.full_name` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
Every other webhook handler (`ClosedHandler`, `LabeledHandler`, `OpenedHandler`, `ReopenedHandler`) resolves the target stacks via `Handler#stacks`, which calls `Repository.from_github_repo_name(repository_name)` using the verified `params.repository.full_name`. `StatusHandler#process` never calls `stacks` or `Repository.from_github_repo_name` at all — it looks up commits globally by `Commit.where(sha: params.sha)`, so a signed webhook for repository A can write a `Status` row against a `Commit`/`Stack` that belongs to a completely different repository B, if the two happen to share a commit sha.

### Finding Description
The broken binding: for every other handler, `repository.full_name` (verified payload) == `Repository.from_github_repo_name(...).stacks` target — enforced via `Handler#stacks` at [1](#0-0) . For `StatusHandler`, this equality is never established.

`StatusHandler#process` is:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 

`Commit.where(sha:)` is a bare `Commit` (ActiveRecord `Shipit::Record`) query with no `stack_id` or repository scoping — `Commit belongs_to :stack` [3](#0-2) , and stacks reference arbitrary repositories. The handler therefore updates the status of **every** commit row across **every** stack in the installation that has a matching sha, regardless of which repository's payload triggered the webhook.

`WebhooksController#verify_signature` only checks that the raw payload's HMAC matches the secret for `repository_owner` (`params.dig('repository','owner','login')`) — i.e., it proves the payload genuinely came from GitHub for that named repository, but it does nothing to constrain which `Commit`/`Stack` rows the handler is allowed to touch [4](#0-3) . Since `StatusHandler` never reads `repository.full_name` to scope the query (unlike `Handler#repository_name`/`#stacks`), the "same repository" invariant the signature check is meant to protect is not enforced downstream.

Exploit flow: attacker owns/administers repository `attacker/repo` (installed on the Shipit GitHub App, or any org whose webhook secret they legitimately have because they administer that repo) and pushes/creates a commit whose sha collides with a sha already recorded in some other, unrelated stack's `commits` table (realistic for empty commits, generated boilerplate/license commits, or repos forked from the same upstream that share history). GitHub then sends (or the attacker replays, since they hold the legitimate secret for their own repo) a `status` event for `attacker/repo` with that `sha`. `verify_signature` succeeds because the signature genuinely matches `attacker/repo`'s secret. `StatusHandler` calls `Commit.where(sha: params.sha)` and finds the colliding `Commit` row belonging to the victim stack, then calls `commit.create_status_from_github!(params)`, writing a forged `Status` (arbitrary `state`, `description`, `target_url`, `context`) onto the victim's commit. This can flip `deployable?`/CI-gating checks (`blocking_statuses`, `required_statuses`) on the victim stack, potentially unblocking or triggering `schedule_continuous_delivery` on a stack the attacker never authenticated against [5](#0-4) .

### Impact Explanation
A payload authenticated only for repository A causes writes on a `Status`/`Commit` belonging to stack/repository B, and can flip the effective deploy-gating state (`deployable?`, `blocked?`) of that unrelated stack, potentially enabling `schedule_continuous_delivery` for a commit the attacker does not control. This is a cross-repository/cross-tenant record mutation caused by a payload that never authenticated the target repository, matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team").

### Likelihood Explanation
Requires: (1) attacker controls a repository connected to Shipit (or can otherwise get a validly-signed `status` webhook delivered/replayed for a repo they own) and (2) a sha collision between a commit in the attacker's repo and a commit already tracked in a victim stack. Collisions are non-trivial for real distinct source trees (SHA-1 pre-image/collision) but are realistic in narrower cases explicitly named in the question — repositories forked from a common upstream sharing early history, or repos containing identical boilerplate/empty/no-op commits (same tree, same parent, same author/committer timestamps) — where the resulting commit object hash is byte-identical and thus the sha is identical by construction, not by cryptographic attack. In those cases the exploit is fully repeatable and requires no privileged access.

### Recommendation
Make `StatusHandler` scope its lookup to the stacks belonging to the verified `repository.full_name`, mirroring the other handlers, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
using the inherited `Handler#stacks`/`#repository_name` so the same repository-binding invariant enforced everywhere else also applies here.

### Proof of Concept
Minitest plan (no live GitHub):
```ruby
test "StatusHandler never scopes by repository and can update another repository's commit" do
  from_github_repo_name_called = false
  Shipit::Repository.stub(:from_github_repo_name, ->(*) { from_github_repo_name_called = true; nil }) do
    stack_a = shipit_stacks(:shipit)          # repo "shopify/shipit-engine" (example)
    stack_b = shipit_stacks(:cyclimse)        # a different repository entirely
    colliding_sha = SecureRandom.hex(20)
    commit_b = stack_b.commits.create!(sha: colliding_sha, message: "x", ...)

    payload = {
      'repository' => { 'full_name' => stack_a.github_repo_name },
      'sha' => colliding_sha,
      'state' => 'success',
      'context' => 'ci/attacker'
    }

    Shipit::Webhooks::Handlers::StatusHandler.call(ActionController::Parameters.new(payload))

    # Assert Handler#stacks / Repository.from_github_repo_name was never consulted
    refute from_github_repo_name_called

    # Assert the status landed on stack_b's commit despite payload naming stack_a's repository
    commit_b.reload
    assert_equal 'success', commit_b.status.state
  end
end
```
This demonstrates `StatusHandler` bypasses the `repository.full_name` binding that `Handler#stacks` enforces for all sibling handlers, and mutates a commit/stack that the request never authenticated against.
