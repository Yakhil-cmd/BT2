### Title
Cross-organization commit-status spoofing via unscoped `sha` lookup breaks org-authentication vs. repository-written binding, enabling an unauthorized deploy - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates an inbound GitHub `status` webhook by resolving the signing organization from `repository.owner.login` (or `organization.login`) in the JSON body, and validating the HMAC against that organization's own `webhook_secret`. [1](#0-0)  Once the signature is accepted, the entire raw payload is dispatched to `Shipit::Webhooks::Handlers::StatusHandler`, whose `process` method does not re-check any repository/organization binding — it looks up commits **globally by `sha` alone** and writes attacker-controlled status fields:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 

The `StatusHandler` parameter schema requires only `sha`, `state`, and optional `description`/`target_url`/`context`/`created_at`/`branches` — it does **not** require or constrain `repository`. [3](#0-2)  This is the analog binding break: the organization whose secret authenticated the request (`repository.owner.login`) is never the same value used to scope the write (a bare `sha`, matched engine-wide against every `Commit` row regardless of which `Stack`/`Repository` it belongs to).

### Finding Description
Shipit supports multiple GitHub organizations each with their own independently-configured GitHub App and `webhook_secret`. [4](#0-3)  Any organization admin who legitimately installs their own GitHub App into Shipit knows their own org's `webhook_secret` and can therefore produce a validly-signed `X-Hub-Signature` for requests whose `repository.owner.login` equals their own organization — this is the exact "malicious owner" primitive from the external report (an owner-level, unprivileged-relative-to-other-orgs actor abusing a shared processing pipeline).

`verify_signature` only checks that the signature matches the org named in the payload's `repository.owner.login`/`organization.login` field:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [5](#0-4) 

Once this passes, `WebhooksController#create` blindly forwards the full parsed body to all handlers for the event:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [6](#0-5) 

For the `status` event, this is `Handlers::StatusHandler`. [7](#0-6)  Because `StatusHandler#process` resolves commits by `sha` with no join/filter to `repository.full_name`/organization, an attacker who controls **only their own org's webhook secret** can supply `sha` equal to a commit that belongs to a completely different organization's stack tracked in the same Shipit instance, along with `state: "success"` and arbitrary `context`/`description`/`target_url`. This creates a `Status` row on that foreign commit:
```ruby
def create_status_from_github!(github_status)
  add_status do
    statuses.replicate_from_github!(stack_id, github_status)
  end
end
``` [8](#0-7) 

That `Status` creation cascades into deploy-triggering logic: `Status#schedule_continuous_delivery` fires on create, and `Commit`/`Deploy` continuous-delivery logic can enqueue `ContinuousDeliveryJob`, which calls `stack.trigger_continuous_delivery` when the target stack has `continuous_deployment` enabled and no deploy is in flight. [9](#0-8) [10](#0-9)  This is corroborated by the engine's own tests demonstrating that creating a `success` status on a commit with CD enabled triggers a new `Deploy`:
```ruby
test "updating state to success triggers new deploy when stack has continuous deployment" do
  @stack.reload.update(continuous_deployment: true)
  ...
  assert_enqueued_with(job: ContinuousDeliveryJob, args: [@stack]) do
    @stack.commits.last.statuses.create!(stack_id: @stack.id, state: 'success', context: 'ci/travis')
  end
``` [11](#0-10) 

The binding equality that should hold but does not is:
`organization authenticated by X-Hub-Signature (repository.owner.login)` == `organization/repository whose commit status is mutated (params.sha's owning Stack/Repository)`.

Before the attacker's request: signature verification and the write target are implicitly assumed to be the same repository because legitimate GitHub webhooks always send a signature computed for the same repo/org whose event is being described. After the attacker's crafted request: the signature is valid for Org A (attacker's own org), but the write (`Commit.where(sha: ...)`) can land on a commit owned by Org B's stack, entirely bypassing any check that the acting org is authorized to write status for that repository.

### Impact Explanation
This allows an attacker who administers any single organization onboarded into a shared Shipit instance to forge CI status for arbitrary commits belonging to any other organization's tracked repository, and — if that other stack has continuous deployment enabled — to trigger an **unauthorized deploy** on a stack they do not own or have any legitimate relationship to. This matches the "High" impact bucket defined by the rules ("escalation into `Shipit.github_teams` authorization ... unauthorized deploy, rollback or merge") since a cross-tenant write results in a deploy action outside the attacker's authorization boundary.

### Likelihood Explanation
Likelihood is Medium: it requires the attacker to control at least one organization's `webhook_secret` configured in the same shared Shipit deployment (a realistic scenario for any multi-tenant Shipit instance per the documented "Using Multiple Github Applications" setup), and to know or guess a `sha` value belonging to a target stack (SHAs are public information visible via GitHub/the target repo's commit history, and are also often exposed by Shipit's own UI/API for that stack). No repository write access, GitHub App private key, or Shipit session/API token is required — only knowledge of one's own organization's webhook secret, which every onboarded organization owner necessarily has.

### Recommendation
Scope the `status` handler's commit lookup (and other handlers relying on bare identifiers) to the same repository that produced the authenticated signature. Concretely, require and validate `repository.full_name` in `StatusHandler#params`, and filter `Commit.where(sha: params.sha)` by joining through `stack: :repository` matched against `Shipit::Repository.from_github_repo_name(payload.dig('repository','full_name'))`, mirroring the pattern already used in `PullRequest` handlers (e.g. `EditedHandler#pull_request`, which joins through `stacks: :repositories`). [12](#0-11)  More generally, `WebhooksController#verify_signature`'s resolved `repository_owner`/organization should be threaded into every handler and enforced as an authorization boundary, not merely used for HMAC selection.

### Proof of Concept
1. Attacker legitimately administers `EvilOrg`, which is configured in Shipit's `secrets.yml` with a known `webhook_secret` (`evil_secret`) as documented for multi-org installs. [4](#0-3) 
2. Attacker learns the `sha` of a commit tracked by `VictimOrg/victim-repo`'s Shipit stack (e.g., from GitHub's public commit history or the target stack's public Shipit dashboard).
3. Attacker crafts a JSON body:
```json
{
  "sha": "<victim-commit-sha>",
  "state": "success",
  "context": "ci/travis",
  "repository": { "owner": { "login": "EvilOrg" }, "full_name": "EvilOrg/some-repo" }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(evil_secret, body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` resolves `repository_owner` = `"EvilOrg"`, fetches `Shipit.github(organization: "EvilOrg")`, and validates successfully since the attacker signed with their own valid secret. [1](#0-0) 
6. `StatusHandler#process` executes `Commit.where(sha: "<victim-commit-sha>")`, finds the commit belonging to `VictimOrg`'s stack, and creates a `success` `Status` on it via `create_status_from_github!`. [2](#0-1) 
7. If `VictimOrg`'s stack has `continuous_deployment: true` and is not already deploying, `Status#schedule_continuous_delivery` → `ContinuousDeliveryJob` → `stack.trigger_continuous_delivery` fires, producing an unauthorized `Deploy` on `VictimOrg`'s stack, exactly as demonstrated by the engine's own test for this code path. [11](#0-10)
