### Title
Cosigner-shared arbiter-contract status is trusted without validating the state-machine transition - ([File: arbiter_contract.js])

### Summary
`arbiter_contract.store()` is explicitly documented as trusting cosigner-supplied contract data ("contracts shared by cosigners are trusted to reflect their true status") and writes the peer/cosigner-supplied `status` field directly into `wallet_arbiter_contracts` without re-deriving or validating it against the actual on-DAG state of the shared address, unlike every other status transition in the file (`respond`, `pay`, `complete`, `openDispute`, `appeal`) which explicitly check the current status before transitioning.

### Finding Description
Every legitimate status transition performed locally is guarded by a precondition check on the current status, e.g. `respond()` requires `status === "pending"/"accepted"` [1](#0-0) , `pay()` requires `status === "signed"` [2](#0-1) , and `complete()` requires `status === "paid"/"in_dispute"` [3](#0-2) . This is the analog of `VaultFactory.createVault()`: only the validated, gated creation/transition path is supposed to be the source of truth for a contract's state.

However, `store()` accepts `bFromCosigner` and directly inserts whatever `status` value a shared party supplies, bypassing the guarded transition functions entirely: [4](#0-3) . This function is invoked directly from the `arbiter_contract_shared` device-message handler in `wallet.js`, which validates only the hash of the immutable fields (title/text/date/parties/amount/asset) — the hash formula `getHashSrc()` never includes `status` — and that "my address" is shared with the sending device, before calling `arbiter_contract.store(body, true)` with the attacker/cosigner-controlled `status` [5](#0-4) . Because `status` is excluded from `getHash()`/`getHashSrc()` [6](#0-5) , an untrusted correspondent that is (or becomes) a "cosigner" of one of the multisig addresses used in the contract can present any `status` value (e.g. `"completed"`, `"in_dispute"`, `"dispute_resolved"`) for a hash that otherwise matches a legitimately-created contract, and this becomes trusted local state — exactly the "owner adds unvalidated vault out-of-band" bug class, where a privileged/trusted party (`bFromCosigner`) is allowed to insert state that should only ever be reached through the validated transition path.

### Impact Explanation
Local wallet UI/state and downstream automated logic key off `wallet_arbiter_contracts.status` for deciding what actions to take next (e.g., `pay()`, `complete()`, dispute-watch registration in the `eventBus` listeners at the bottom of the file, and multisig cosigning workflow). If a cosigner or corrupted correspondent injects a fabricated `status` for a contract not yet actually at that state, other cosigning devices can be led to believe the contract is further along than it truly is (e.g., "completed"/"cancelled") and may refuse to co-sign a legitimate pending payment, or the local instance may proceed to `pay()`/`complete()` based on a falsified precondition, given `getByHash` is used to source `objContract.status` in these flows. This is a medium-severity integrity issue in the arbiter-contract state machine — it does not directly forge on-chain fund movement (the DAG-level shared address definition and payment conditions in `deriveSharedAddress` still require genuine signatures/data-feed conditions to actually move funds), but it can cause fund-release logic to act on falsified local state and disagreement between cosigning devices about the contract's true status.

### Likelihood Explanation
Reachable by any paired/cosigning device (an unprivileged actor in a multi-cosigner arbiter-contract wallet) simply by sending an `arbiter_contract_shared` message with a crafted `status` field for a hash matching an existing contract's immutable fields — no signature over `status` is required since it's excluded from the hash computation. This requires the attacker to be a correspondent device already added as a cosigner (or be able to spoof being one), which is a normal, low-friction step in the intended arbiter-contract cosigning workflow.

### Recommendation
Include `status` (or derive it independently) in the hash/authenticity check for shared contract data, or, more robustly, refuse to accept a `status` value via `store()`/`arbiter_contract_shared` that skips required intermediate states; instead, re-validate any incoming status against the actual on-DAG state (units, shared-address definition, data feeds) before persisting it, mirroring the checks already performed in `respond()`, `pay()`, and `complete()`.

### Proof of Concept
1. Attacker device is added as a cosigner to a wallet address used as `my_address`/`peer_address` in an arbiter contract with hash `H` (computed from title/text/date/parties/amount/asset only).
2. Attacker crafts a `arbiter_contract_shared` message with the correct immutable fields (reproducing hash `H`) but sets `status: "completed"` (or `"in_dispute"`) despite the contract truly being in `"pending"`.
3. `wallet.js`'s handler for `arbiter_contract_shared` validates only field completeness and the hash of immutable fields [5](#0-4) , then calls `arbiter_contract.store(body, true, ...)`, which inserts the falsified `status` directly [4](#0-3) .
4. The victim device's local `wallet_arbiter_contracts.status` now reflects the falsified state, which is read by `getByHash()` and used to gate subsequent actions (`pay`, `complete`, dispute-watch registration), without any of the on-DAG preconditions that legitimate transitions require.

function getHashSrc(contract) {
	const payer_name = contract.me_is_payer ? contract.my_party_name : contract.peer_party_name;
	const payee_name = contract.me_is_payer ? contract.peer_party_name : contract.my_party_name;
	const payer_address = contract.me_is_payer ? contract.my_address : contract.peer_address;
	const payee_address = contract.me_is_payer ? contract.peer_address : contract.my_address;
	const src = contract.creation_date > exports.NEW_HASH_DATE
		 ? [contract.title, contract.text, contract.creation_date, payer_address, payer_name || '', contract.arbiter_address, payee_address, payee_name || '', contract.amount, contract.asset || 'null'].join(exports.DELIMITER)
		 : [contract.title, contract.text, contract.creation_date, payer_name || '', contract.arbiter_address, payee_name || '', contract.amount, contract.asset || 'null'].join("");
	return src;
}

function getHash(contract) {
	return crypto.createHash("sha256").update(getHashSrc(contract), "utf8").digest("base64");
}
