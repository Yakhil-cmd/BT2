### Title
Cross-org multi-tenant GitHub App config lets an attacker-authenticated `pull_request` `unassigned` webhook mutate a victim repository's `PullRequest` record - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`, `app/models/shipit/webhooks/handlers/pull_request/assigned_handler.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects the `GitHubApp` (and thus the HMAC secret) to validate a webhook using `repository_owner`, which is read from `params.dig('repository','owner','login')`. `Shipit::Webhooks::Handlers::PullRequest::AssignedHandler`, however, resolves the repository to mutate using an entirely independent field, `params.repository.full_name`, via `Shipit::Repository.from_github_repo_name`. Because these two fields are never cross-checked, an attacker who controls a GitHub org configured in Shipit with a blank/no `webhook_secret` can forge a signature-exempt request whose `repository.full_name` names a *different*, victim-owned repository, causing `AssignedHandler#process` to `update` that victim's persisted `PullRequest` row.

### Finding Description
The broken binding is the implicit equality the code assumes but never enforces:
`Shipit.github(organization: repository_owner).verify_webhook_signature(...) == true` should imply `repository_owner == owner_of(params.repository.full_name)`.

Trace:
1. `Shipit::WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-30) computes `repository_owner` from `params.dig('repository','owner','login')` (line 59-62) and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(signature, raw_post)`.
2. `GitHubApp#verify_webhook_signature` (lib/shipit/github_app.rb:76-83): `return true unless webhook_secret`. If the org selected by `repository_owner` is configured in Shipit (`github_app_config`) but has no `webhook_secret` set (or blank), the signature check is bypassed entirely and returns `true` for *any* payload/signature.
3. `AssignedHandler#process` (app/models/shipit/webhooks/handlers/pull_request/assigned_handler.rb:41-45) never looks at `repository_owner`; it derives the target repository solely from `params.repository.full_name` through `Shipit::Repository.from_github_repo_name` (app/models/shipit/repository.rb:53-56), which parses `"owner/name"` straight from that string and does a plain `find_by(owner:, name:)` lookup with no relation to the org that authenticated the request.
4. `pull_request` (assigned_handler.rb:53-65) then looks up the `Shipit::PullRequest` joined to that resolved repository by `number`, and `process` calls `pull_request.update(github_pull_request: params.pull_request)`.

Exploit: the attacker registers/controls a GitHub org `A` that the Shipit operator has configured (e.g., for legitimate use) but for which `webhook_secret` is empty or unset. The attacker sends `POST /webhooks` with header `X-Github-Event: pull_request`, an `X-Hub-Signature` of any value, and a JSON body where `repository.owner.login = "A"` (so `verify_signature` selects org A's config, which has no secret and trivially "verifies") but `repository.full_name = "victim-org/victim-repo"` and `action = "unassigned"`, with `number` set to an existing PR number on a victim stack. `drop_unhandled_event` passes since `pull_request` is handled; `verify_signature` passes because org A has no secret; `AssignedHandler` then updates the victim's `PullRequest` row identified by `victim-org/victim-repo` + `number`, writing attacker-controlled `pull_request` JSON (title, assignees, labels, sha, etc.) into the victim's persisted record.

Existing guards do not prevent this:
- `drop_unhandled_event` only checks that a handler exists for the event type, not repository identity.
- `verify_signature` only binds trust to `repository_owner`, never to `repository.full_name`.
- `ExplicitParameters` schema in `AssignedHandler` requires `repository.full_name` but has no `repository.owner.login` requirement, and does not compare the two.
- No model validation or webhook-handler check enforces `Repository#owner == params.dig('repository','owner','login')`.

The "shared commit SHA with attacker repo stack" element of the question does not add a distinct mechanism here — `AssignedHandler#process` never performs a bare-SHA status/commit lookup; it identifies the target purely by `repository.id` + PR `number` from the join in `pull_request` (lines 53-65). The exploitable primitive is entirely the owner/full_name divergence, independent of shared commit SHAs.

### Impact Explanation
A payload authenticated by one repository/org's (weak or absent) secret can write into a completely different, victim-owned `Shipit::PullRequest` record — this is exactly the "payload for one repository mutating another's stack/commit" Critical category. The attacker can overwrite `github_pull_request` JSON for any PR number that exists on the victim's stacks, which is read elsewhere (e.g., PR title/state/labels display, possibly influencing merge/label-driven automation depending on downstream `PullRequest` consumers). This is repeatable against any repository/PR number as long as the attacker can identify one Shipit-configured GitHub org lacking a webhook secret.

### Likelihood Explanation
Preconditions: the Shipit deployment must have at least one org configured in `secrets.github` (multi-org schema, `github_default_organization` non-nil) with a blank/absent `webhook_secret` for that org, while other orgs on the same instance have real repos/stacks. This is a plausible but not universal misconfiguration — operators may intentionally leave a secret blank during onboarding, or a legacy/test org may lack one. Given that precondition, the attack costs a single unauthenticated HTTP request with no signature knowledge and is fully repeatable. Without such a misconfigured org, `verify_webhook_signature` requires the true HMAC secret of the org named in `repository.owner.login`, and there's no way to derive that secret for an org you don't control — so likelihood is directly gated by that specific configuration weakness rather than being universally exploitable.

### Recommendation
In `Shipit::WebhooksController#verify_signature`, derive `repository_owner` from `params.repository.full_name`'s owner segment (not `repository.owner.login`), or explicitly assert `params.dig('repository','owner','login') == params.dig('repository','full_name').split('/').first` before proceeding. Additionally, in every `Webhooks::Handlers` pull_request handler (including `AssignedHandler`), verify that the resolved `Shipit::Repository#full_name` matches the `repository_owner` used to authenticate the request. Consider also disallowing/warning on GitHub App configs with a blank `webhook_secret` in a multi-org deployment.

### Proof of Concept
Minitest plan (extends `test/controllers/webhooks_controller_test.rb` style, no live GitHub):
1. Configure two orgs in test credentials: `"attacker-org"` with `webhook_secret: ""` (or nil) and `"victim-org"` with a real `webhook_secret`.
2. Create `victim_repo = Shipit::Repository.create!(owner: "victim-org", name: "victim-repo")`, a `Shipit::Stack` on it, and a `Shipit::PullRequest` with `number: 42` and some baseline `github_pull_request` JSON.
3. POST to `/webhooks` with header `X-Github-Event: pull_request`, `X-Hub-Signature: "sha1=bogus"`, and body:
```json
{
  "action": "unassigned",
  "number": 42,
  "pull_request": { "id": 1, "number": 42, "url": "...", "title": "ATTACKER TITLE", "state": "open",
                     "additions": 0, "deletions": 0,
                     "head": {"sha": "deadbeef", "ref": "attacker-branch"},
                     "user": {"login": "attacker"}, "assignees": [], "labels": [] },
  "repository": { "owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo" },
  "sender": {"login": "attacker"}
}
```
4. Assert response is `200 OK` (signature "verified" because `attacker-org` has no secret).
5. Reload `pull_request` and assert `pull_request.github_pull_request["title"] == "ATTACKER TITLE"` — proving the attacker-authenticated request (via `attacker-org`) mutated `victim-org/victim-repo`'s PR record, demonstrating the equality `repository_owner == owner_of(full_name)` is violated and exploited.
