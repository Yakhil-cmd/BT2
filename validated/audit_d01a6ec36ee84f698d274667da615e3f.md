### Title
Unmeasured `repay`/`recapitalize` overpayment refund drains pool custody - (File: contracts/pool/src/ops/repay.rs)

### Summary
`ops::repay::accounting` computes `overpayment = amount - net_repay` purely from the caller-declared `action.amount`, then `apply` transfers it out via `transfer_out` without ever bounding it by the tokens actually received or by `require_reserves`. `ops::recapitalize::accounting` has the same shape: `refund = amount - applied` where `applied = min(amount, backing_shortfall)`, and the refund is paid out of real custody with no receipt measurement and no reserve check. An unprivileged caller can declare an arbitrary `amount`, send nothing, and have the pool transfer the "excess" out of suppliers' funds. [1](#0-0) [2](#0-1) 

### Finding Description
The external report's bug class is a computed distribution value (`z_proceed`) that is never checked against the reserves it is paid from (`z_proceed ≤ I`) and whose post-scaling invariant is never re-verified. The XOXNO analog is the refund leg of the measured-receipt settlement paths:

- In `ops::repay::apply`, `outcome.cache.transfer_out(payer, outcome.overpayment)` sends tokens to the payer where `overpayment` was derived from `resolve_repay(amount, position)` — i.e., `amount - debt_ceil` — using only the declared `action.amount`, not a measured balance delta. `credit_cash(net_repay)` books only the net part, and `transfer_out` does not call `require_reserves` or debit `cash`. [3](#0-2) 
- In `ops::recapitalize::apply`, `refund = amount - applied` is paid out the same way: when the market has no backing shortfall, `applied = 0`, so the entire declared `amount` becomes the refund while `cash` is credited zero. [4](#0-3) 

The invariant documentation claims token-funded credit uses measured receipt (INV-ACCT-03) and that cash is the reserve book whose debits reject insufficient reserves (INV-ACCT-02), but neither refund path measures receipt nor checks reserves — the payout is validated only against a declared number, exactly the missing `z_proceed ≤ I` check. [5](#0-4) 

This is not theoretical: the pool's own test suite demonstrates it. `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` calls `repay` on a market with zero debt, transfers nothing in, and asserts the whole `custody_before` balance is paid to the payer as "overpayment" — "the whole amount is refunded out of real custody with the book untouched." [6](#0-5) 

### Impact Explanation
Theft of user funds / protocol insolvency. `repay` and `recapitalize` are in-scope unprivileged entrypoints. On any market with low or zero outstanding debt (repay) or no backing shortfall (recapitalize — the normal state of a healthy market), an attacker sets `amount` equal to the pool's token balance, authorizes as `payer`, transfers nothing, and receives a refund equal to real supplier deposits held in custody. The cash book is never debited, so the theft is invisible to `require_reserves` accounting and can be repeated until custody is empty. [7](#0-6) 

### Likelihood Explanation
High. It requires no privileged role, no oracle manipulation, no price movement, and no pre-existing position — only a direct call to the pool's `repay` (or `recapitalize`) with a fabricated `amount` and the attacker as `payer`. The only precondition is that declared `amount` exceeds current debt/shortfall, which is trivially satisfiable. The pool test fixture itself executes exactly this sequence end-to-end. One caveat I could not fully verify in this session: whether the pool entrypoint additionally enforces that the caller is the controller or measures the inbound token delta elsewhere (e.g., in `lib.rs`/`load_leg`); the test demonstrating custody drain calls the pool client directly, which suggests no such guard exists on this path. [8](#0-7) 

### Recommendation
Bind each refund to value actually received and to the reserve book, mirroring the report's `z_proceed ≤ I` fix:

1. Measure the pool's real token balance delta for the call and compute `overpayment = min(amount - net_repay, measured_receipt - net_repay)` in `ops::repay::accounting` (and equivalently `refund = min(amount - applied, measured_receipt - applied)` in `ops::recapitalize::accounting`).
2. Route both refunds through the cash book: `debit_cash(refund)` (or an explicit `require_reserves(refund)`) before `transfer_out`, so a refund can never exceed tracked reserves.
3. Add a post-condition assertion that `net_repay + overpayment ≤ measured_receipt` for repay, and `applied + refund ≤ measured_receipt` for recapitalize. [9](#0-8) [4](#0-3) 

### Proof of Concept
On a pool market with zero borrowed shares and token balance `B` held in custody:

```rust
// attacker = payer; no tokens are transferred to the pool
client.repay(
    &attacker,
    &RepayAction { position: Ray::ZERO, amount: B, .. },
);
// resolve_repay: debt_ceil == 0 → overpayment == B, net_repay == 0
// RepayRoundsToZeroShares assert passes (net_repay == 0 disjunct)
// transfer_out(attacker, B) pays the full custody balance; cash book untouched
assert_eq!(token.balance(&attacker), B);
```

This is precisely the scenario pinned by `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody`, which asserts `actual_amount == 0` while `custody_before` is paid out. [7](#0-6)  The `recapitalize` variant is identical with `amount = B` on a market with no backing shortfall: `applied = 0`, `refund = B`. [4](#0-3)

pub(crate) fn apply(
    env: &Env,
    payer: &Address,
    action: &PoolAction,
) -> (PoolPositionMutation, MarketStateSnapshot) {
    let outcome = accounting(env, action);

    outcome.cache.transfer_out(payer, outcome.overpayment);
    (outcome.mutation, outcome.snapshot)
}

/// Accrues interest, resolves the repay amount into burned debt shares and
/// overpayment, burns the shares, and credits the net repay to cash without
/// transferring the overpayment refund. Panics if a positive net repay would
/// burn zero scaled shares.
pub(crate) fn accounting(env: &Env, action: &PoolAction) -> RepayOutcome {
    let (mut cache, position) = ops::load_leg(env, action);
    let amount = action.amount;

    let (burned, overpayment) = cache.resolve_repay(amount, position);
    let net_repay = amount
        .checked_sub(overpayment)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow));
    assert_with_error!(
        env,
        net_repay == 0 || burned.raw() > 0,
        GenericError::RepayRoundsToZeroShares
    );

    let position = position.checked_sub(env, burned);
    cache.burn_debt(burned);

    cache.credit_cash(net_repay);

    let snapshot = cache.commit();
    let mutation = cache.position_mutation(position, net_repay);
    RepayOutcome {
        cache,
        mutation,
        snapshot,
        overpayment,
    }
}

pub(crate) fn accounting(
    env: &Env,
    hub_asset: HubAssetKey,
    amount: i128,
) -> RecapitalizationOutcome {
    require_nonneg_amount(env, amount);
    let mut cache = ops::renewed_market(env, &hub_asset);

    let applied = amount.min(guards::backing_shortfall(&cache));
    let refund = amount
        .checked_sub(applied)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow));

    cache.credit_cash(applied);
    cache.commit();

    RecapitalizationOutcome {
        cache,
        mutation: PoolAmountMutation {
            actual_amount: applied,
        },
        refund,
    }
}

Reserve checks use tracked market cash; token donations alone do not increase

### INV-ACCT-03 — Token-funded credit uses measured receipt

Token-funded supply, repayment and recapitalization credit the pool's measured
balance increase. Strategy supply follows the same supply path, and strategy
repayment also measures pool receipt. Requested amounts alone do not determine
credit.

Repayment and recapitalization can refund unused receipt. Share conversion
retains its own rounding, and measurement depends on the token's balance
reports. Liquidation Credit mode moves existing collateral shares without
incoming collateral tokens.

/// The refund gap is not specific to `recapitalize`. Two pool legs refund an
/// excess derived from a declared inbound amount, not from the cash book:
/// `ops::recapitalize::apply` (the excess over the shortfall) and
/// `ops::repay::apply` (the excess over the debt). Neither refund debits `cash`
/// or passes `require_reserves`.
///
/// A repay against a market with no debt makes the entire declared amount an
/// overpayment: `current_debt_ceil` is zero, so `resolve_repay` takes the
/// full-close branch and `net_repay` is zero. The `RepayRoundsToZeroShares`
/// assert in `ops::repay::accounting` passes on its `net_repay == 0` disjunct,
/// and the whole amount is refunded out of real custody with the book untouched.
#[test]
fn test_unfunded_repay_overpayment_refund_also_pays_out_of_custody() {
    let t = TestSetup::new();
    let token = token::Client::new(&t.env, &t.asset);
    let payer = Address::generate(&t.env);

    let custody_before = token.balance(&t.pool);
    let before = t.state_snapshot();
    assert_eq!(
        before.cash, custody_before,
        "fixture guard: book and custody must start in sync"
    );
    assert_eq!(before.borrowed, 0, "fixture must carry no debt");

    // Nothing transferred in, no debt to retire: the whole amount is "excess".
    let credited = t
        .client()
        .repay(&payer, &t.ract(0, custody_before))
        .get_unchecked(0)
        .actual_amount;
    assert_eq!(credited, 0, "no debt was retired, so nothing is credited");
    assert_unfunded_refund_drained_custody(&t, &payer, custody_before, &before);
}
