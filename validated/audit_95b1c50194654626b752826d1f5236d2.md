### Title
Off-chain signed messages (`is_valid_signed_package` / `signed_message.validateSignedMessage`) carry no protocol-enforced expiration, allowing stale orders/payments to be replayed at a later, economically unfavorable time - ([File: signed_message.js])

### Summary
The oscript primitive `is_valid_signed_package()`, backed by `signed_message.validateSignedMessage()` in `signed_message.js`, is the mechanism AAs use to accept off-chain, user-signed intents (limit orders, payment-channel updates, order-book trades). Just like Uniswap's router accepting `deadline = block.timestamp` and providing "zero protection," ocore's signed-message validator accepts an optional `timestamp` field but never checks it against current time, and the only chain-relative field, `last_ball_unit`, is used purely to pick the signer's address definition/MCI, not to bound message validity.

### Finding Description
`validateSignedMessage` explicitly allows a `timestamp` field in the signed payload (`ValidationUtils.hasFieldsExcept(objSignedMessage, ["signed_message", "authors", "last_ball_unit", "timestamp", "version"])`, [1](#0-0) ), but that field is never read or compared to `Date.now()` or to `last_ball_timestamp` anywhere in the function. The only temporal anchor, `last_ball_unit`, is resolved solely to obtain `last_ball_mci`/`last_ball_timestamp` for definition lookups, not for expiry enforcement [2](#0-1) . Once a signature validates, the calling AA has no protocol-level guarantee that the signed message is fresh — it can be resubmitted at any future block.

The sample AAs shipped with the codebase corroborate that this is a real, unresolved gap left to AA authors: the order-book exchange sample explicitly notes the missing check with a `// to do check expiry` comment right where two signed orders are matched and executed [3](#0-2) , and the payment-channel sample similarly consumes `sentByPeer` signed messages without any expiry/staleness bound on the signed balance update, relying only on `channel` and `period` fields for freshness [4](#0-3) .

### Impact Explanation
Because the protocol-level `is_valid_signed_package` gives no expiry guarantee, an old signed order (e.g., a favorable-price limit order or an outdated payment-channel balance update) that a user forgot to invalidate can be posted and executed long after market conditions changed, exactly mirroring the Uniswap "missing deadline" bad-trade/MEV scenario. In an order-book AA, this can cause the signer to be filled at a stale, unfavorable price (fund loss). In a payment-channel AA, an outdated `sentByPeer` state could be replayed if the AA logic does not independently track monotonic state, contributing to disputed settlements.

### Likelihood Explanation
Likelihood is moderate: exploitation requires (1) a signer producing a signed order/message without independently embedding and checking an application-level expiry, and (2) a counterparty or bot holding and later broadcasting that stale signature. The core library's design pushes all expiry logic to AA authors, and the shipped sample code demonstrates that even the reference examples leave this unaddressed, increasing the chance that real-world AAs built by following these templates inherit the gap.

### Recommendation
Add first-class expiry support to the signed-message primitive: allow (and encourage) an `expiry_ts` field inside `signed_message`, and have `is_valid_signed_package`/`validateSignedMessage` reject packages whose `expiry_ts` (or `timestamp` field, if repurposed for this) is older than `last_ball_timestamp`/current MC timestamp. At minimum, update the documentation and sample AAs (`order_book_exchange.oscript`, `payment_channels.oscript`) to include the recommended expiry check instead of leaving a `// to do` comment, since these samples are widely used as templates.

### Proof of Concept
1. Alice signs an order via `signed_message.signMessage` to sell asset A for asset B at price P, intending it to be valid only briefly, with no `expiry_ts` embedded.
2. The order-book AA (following the shipped `order_book_exchange.oscript` pattern) posts the trigger with `trigger.data.order1`/`order2` and matches orders using only `is_valid_signed_package(...)` for signature validity [5](#0-4) .
3. Weeks later, after asset A's fair price has moved far from P, another party (or a bot) submits Alice's still-validly-signed order together with a matching counter-order.
4. `signed_message.validateSignedMessage` accepts the signature purely on cryptographic/definition grounds [6](#0-5) ; the AA executes the stale trade, filling Alice at the outdated price P with no protocol-level recourse, replicating the reported "missing deadline" loss scenario.
