### Title
Webhook signature verified against attacker's own GitHub organization while events are applied to a victim repository's Stack - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App/organization's `webhook_secret` to validate a webhook against by reading `params.dig('repository','owner','login')` (falling back to `organization.login`) from the **attacker-controlled JSON body**, not from any authenticated source. Once the signature check passes, the very same attacker-controlled `params` (including `repository.full_name`) is handed to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`, which resolves the target `Stack`/`Repository` by `full_name`. Nothing ties the organization used for signature verification to the organization/repository that the handlers actually act on.

### Finding Description
`Shipit` supports hosting multiple GitHub organizations, each with its own GitHub App and `webhook_secret`, as documented in `docs/setup.md` ("Using Multiple Github Applications") and implemented by `Shipit.github(organization:)`: [1](#0-0) 

The webhook entrypoint selects the org whose secret is used to verify the HMAC purely from the JSON payload: [2](#0-1) [3](#0-2) 

`repository_owner` is derived from `params.dig('repository', 'owner', 'login')`, a field fully controlled by whoever sends the POST body — GitHub itself only ever sets this consistently with the delivered event, but an arbitrary HTTP client hitting `/webhooks` can set it to any organization name for which a `GitHubApp`/`webhook_secret` is configured (including an organization the attacker legitimately owns and has installed their own copy of the Shipit-compatible GitHub App on, thereby knowing that organization's `webhook_secret`).

After `verify_signature` passes, `create` dispatches the **unmodified** attacker-controlled `params` to all handlers for the event: [4](#0-3) 

Handlers such as the push handler resolve the affected `Stack`/`Repository` using `repository.full_name` from that same payload (as also seen in the analogous lookup pattern `Repository.from_github_repo_name(full_repo_name)` used elsewhere for repo resolution). Because `repository.owner.login` (used to pick the signing secret) and `repository.full_name` (used to pick the affected repository) are independent, attacker-controlled fields in the same JSON body, there is no cryptographic binding between "the organization whose secret validated this webhook" and "the repository/stack the handler will mutate."

This is the direct analog of the Hubble finding: two separate governance/verification paths exist (per-organization webhook-secret verification vs. per-repository target resolution), and the second path is not covered by the guarantee established by the first, letting one signed identity be silently substituted for another.

### Impact Explanation
An attacker who controls (or installs) their own GitHub App on an organization already configured in Shipit's multi-org `secrets.github` map (knows that organization's `webhook_secret`) can forge a valid-looking `X-Hub-Signature` for a payload whose `repository.owner.login` is their own org, while setting `repository.full_name` (and other fields) to point at a victim repository/stack hosted on the very same Shipit instance under a different organization. Because `verify_signature` only checks that *some* known org's secret matches, and the handlers act on the unrelated `full_name`, the attacker can inject forged `push`, `status`, `check_suite`, etc. events for a repository they do not own — e.g. queuing `GithubSyncJob`, creating bogus commit statuses, or otherwise manipulating the deploy/CI state that Shipit uses to decide whether a commit is deployable. This crosses a repository trust boundary using only the attacker's own (self-controlled) webhook secret — an unauthorized write into another organization's Stack state.

### Likelihood Explanation
This requires: (1) the Shipit instance to be configured for multiple GitHub organizations (a documented, supported configuration), and (2) the attacker to control at least one of the configured organizations' GitHub App/webhook_secret (trivially achievable if they can install their own App, which is the normal onboarding flow for any org added to the multi-tenant config). No Shipit session, API token, or other Shipit credential is required — only knowledge of a webhook secret for an organization the attacker legitimately controls. Given that `docs/setup.md` explicitly documents and encourages the multi-org setup, this is a realistic deployment scenario.

### Recommendation
Bind the signature-verification organization to the repository being acted on: after selecting the GitHub App by `repository_owner`, verify that `repository.full_name`'s owner matches `repository_owner` (or, better, look up the `Stack`/`Repository` first and confirm it belongs to the exact same organization whose secret validated the request) before dispatching to handlers. Reject the webhook if these do not match.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` (attacker controls the GitHub App/installs it themselves, so knows `webhook_secret_A`) and `victim-org` (hosts the Stack the attacker wants to tamper with).
2. Craft a push-event JSON body:
```json
{
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org" }
  },
  "after": "<attacker-chosen sha>"
}
```
3. Compute `X-Hub-Signature: sha1=<hmac(webhook_secret_A, body)>` using the attacker's own known secret.
4. POST to `/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: 'attacker-org')` and validates successfully against `webhook_secret_A`.
6. `create` forwards the same `params` to the push handler, which resolves `victim-org/victim-repo`'s `Stack` from `full_name` and enqueues `GithubSyncJob`/updates commit state for a repository the attacker never authenticated against.

Note: I was not able to fully inspect `app/models/shipit/webhooks/handlers/push_handler.rb` and `app/models/shipit/repository.rb`'s exact `full_name` resolution logic within the available context/tool budget; the exact handler code should be reviewed to confirm the precise lookup call, though the general Stack/Repository resolution by `full_name`, independent of the org used for signature verification, is corroborated by `Repository.from_github_repo_name` usage elsewhere and by `webhooks_controller.rb`'s `repository_owner` logic shown above.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end
```

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
