### Title
Unauthenticated webhook signature bypass when `webhook_secret` is unset allows forged `membership` events to grant unauthorized application access - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and thus which `webhook_secret`) to validate a request against based on an attacker-controlled field taken from the *unverified* JSON body, and `GithubApp#verify_webhook_signature` unconditionally treats an unconfigured `webhook_secret` as "verified: true." Since Shipit's own documentation marks `webhook_secret` as optional, any deployment (or any single organization in a multi-org config) that leaves it unset accepts **arbitrary, unsigned webhook payloads**. Combined with `MembershipHandler`, which creates `Team`/`Membership` records straight from the payload with no cross-check against real GitHub state, an unauthenticated attacker can forge a `membership` "added" event that inserts themselves (any `User` they control by login) into a `Team` matching `Shipit.github_teams`, bypassing the `current_user.authorized?` gate that otherwise restricts the whole application to members of specific GitHub teams.

### Finding Description
`WebhooksController` picks the GitHub App/organization config used for signature verification from data inside the yet-unauthenticated request body: [1](#0-0) [2](#0-1) 

`repository_owner` is read via `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` — fully attacker-controlled JSON, parsed before any signature check. This value is used to fetch `Shipit.github(organization: repository_owner)`, and that org's `verify_webhook_signature` is then called: [3](#0-2) 

Critically, `return true unless webhook_secret` means that if the selected organization's `webhook_secret` is `nil`/blank, **every** signature check for that organization short-circuits to `true` regardless of what signature (or none) was supplied. The project's own setup docs and secrets templates explicitly list `webhook_secret` as optional (`webhook_secret: # nil`): [4](#0-3) [5](#0-4) 

Once the request reaches `create`, the raw JSON is dispatched to handlers purely based on the attacker-supplied `X-Github-Event` header/body, with no further authenticity check: [6](#0-5) 

`MembershipHandler#process` trusts the payload to create/find a `Team` and a `User`, and to add that user as a team member: [7](#0-6) 

`Team#add_member` performs no additional validation against GitHub — it just appends the given `member`: [8](#0-7) 

That membership directly feeds the authorization check every controller runs via `Shipit::Authentication`: [9](#0-8) [10](#0-9) 

**The trust binding broken:** the organization whose credentials (`webhook_secret`) are used to authenticate the request is derived from unauthenticated attacker input, and when that org's secret happens to be unset (a documented, supported, default-ish configuration), the "verified signature" gate degenerates into "always verified." The webhook processing pipeline (`Team`, `Membership`, `User`) then acted on as if it came from GitHub, with no re-validation, breaking: *organization that authenticated == organization the record is written for*.

### Impact Explanation
If any configured GitHub organization in `Shipit.github` has no `webhook_secret` set (explicitly supported/optional per `docs/setup.md` and the shipped secrets templates), an unauthenticated network attacker can:
1. POST directly to `/webhooks` with `X-Github-Event: membership`, a `repository`/`organization` payload naming that org, `action: "added"`, an arbitrary `team` object matching (or creating) one of the teams in `Shipit.github_teams`, and a `member.login` of a GitHub account they control.
2. This creates/updates a `Team` and adds the attacker's `User` as a member, with zero signature/authenticity requirement.
3. The attacker then authenticates normally via the real GitHub OAuth flow (`GithubAuthenticationController`) as that same GitHub login, and `current_user.authorized?` now returns `true` because their `User` row has a `Membership` in a `Shipit.github_teams` team — even though they were never actually added to that team on GitHub.

This is an authorization-bypass escalation into `Shipit.github_teams` gating, which the rules explicitly classify as **High** impact ("escalation into `Shipit.github_teams` authorization"). It requires no session, no `ApiClient` token, no webhook secret knowledge, and no privileged account — only that the deployment left `webhook_secret` unset for at least one configured organization, which is a documented, supported configuration rather than a misuse of the engine.

### Likelihood Explanation
Likelihood depends entirely on operator configuration: exploitable only when `webhook_secret` is unset for at least one organization. This is realistic because:
- The shipped example/templates (`config/secrets.development.example.yml`, `test/dummy/config/secrets.yml`, `docs/setup.md`) all show `webhook_secret` as optional/commented as `# nil`.
- Multi-org deployments (`config/secrets.development.shopify.yml`, `secrets_double_github_app.yml`) configure secrets per-organization; an operator could easily configure a secret for their primary org while forgetting a secondary one, and the code still fully dispatches events for that org.
- No compensating control exists elsewhere in the webhook pipeline (no IP allowlisting, no re-verification against the GitHub API for team membership at the time of use).

Note: I could not fully verify from the indexed code whether Shipit ever "re-fetches" team membership from GitHub at some later point (e.g., a periodic sync) that would eventually correct a forged `Membership`; `Team#refresh_members!` exists but is not shown to run automatically on every request, so the forged membership persists and is usable until such a refresh runs.

### Recommendation
- Make `webhook_secret` mandatory (raise/refuse to boot, or reject all webhooks for an org) rather than silently treating an absent secret as "verified," i.e., remove/replace `return true unless webhook_secret` in `GithubApp#verify_webhook_signature` with a fail-closed default, and only permit skipping verification behind an explicit, loudly-documented `disable_webhook_verification` flag akin to `Shipit.disable_api_authentication`.
- Do not let signature verification's organization selection be derived from unauthenticated payload content that later feeds record creation without cross-validation; verify the signature first using a single well-known deployment-wide secret when possible, or verify against every configured org's secret rather than only the one implied by attacker-controlled fields.
- For `MembershipHandler`, consider corroborating high-trust events (team membership changes that affect authorization) with a live GitHub API call rather than trusting the webhook payload verbatim.

### Proof of Concept
Given an operator config with `github.someorg.webhook_secret: nil` (a documented supported configuration) and `Shipit.github_teams` including `someorg/admins`:

```bash
curl -X POST https://shipit.example.com/webhooks \
  -H "X-Github-Event: membership" \
  -H "Content-Type: application/json" \
  -d '{
        "action": "added",
        "team": { "id": 999999, "name": "Admins", "slug": "admins", "url": "https://api.github.com/teams/999999" },
        "organization": { "login": "someorg" },
        "member": { "login": "attacker-github-login" }
      }'
```

Because `Shipit.github(organization: "someorg").webhook_secret` is `nil`, `verify_webhook_signature` returns `true` for any/no `X-Hub-Signature` header (`lib/shipit/github_app.rb:76-77`). `MembershipHandler#process` then creates the `Team` (if absent) and `User.find_or_create_by_login!("attacker-github-login")`, adding a `Membership` (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-34`, `app/models/shipit/team.rb:41-43`). The attacker subsequently logs in through the normal GitHub OAuth flow as `attacker-github-login`; `User#authorized?` (`app/models/shipit/user.rb:80-82`) now finds a matching `Membership` and grants access past `force_github_authentication` (`app/controllers/concerns/shipit/authentication.rb:20-34`).

```ruby
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([

        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",

      ].join(' '))
    end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
    def force_github_authentication
      if current_user.logged_in? && current_user.requires_fresh_login?
        Rails.logger.warn("User #{current_user.id} requires a fresh login, logging out...")
        reset_session
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      elsif Shipit.authentication_disabled? || current_user.logged_in?
        unless current_user.authorized?
          team_handles = Shipit.github_teams.map(&:handle)
          team_list = team_handles.to_sentence(two_words_connector: ' or ', last_word_connector: ', or ')
          render(plain: "You must be a member of #{team_list} to access this application.", status: :forbidden)
        end
      else
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      end
    end
```
