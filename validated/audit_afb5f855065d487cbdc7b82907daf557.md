### Title
Cross-organization commit-status forgery via unscoped `sha` lookup in `StatusHandler` bypasses per-org webhook authentication - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StandardSettings.onOwnershipTransferred()` trusted a caller-controlled callback without verifying it was still bound to the correct owner/pair record, allowing a party who could reach the call to overwrite `pairInfos[]` for a pair it did not legitimately own. The structurally equivalent binding failure in `shipit-engine` is that `WebhooksController#verify_signature` authenticates a webhook payload against the **organization/installation named in that payload** [1](#0-0) , but the `status` event handler then mutates commit/deploy-gating state by matching **only on `sha`, globally across the whole database**, with no re-check that the resolved `Commit`/`Stack` actually belongs to the authenticated organization [2](#0-1) .

### Finding Description
The equality that should hold is:
`organization whose webhook_secret authenticated this request == organization that owns the repository/commit being written to`.

`WebhooksController#verify_signature` derives `repository_owner` from the payload itself (`params.dig('repository','owner','login')` or `organization.login`), fetches that org's `GitHub App`/`webhook_secret` via `Shipit.github(organization: repository_owner)`, and verifies the HMAC signature against that secret [3](#0-2) . This only proves the payload was signed with the secret configured for the org named in the payload — it says nothing about which `Commit`/`Stack` the handler ultimately mutates.

`StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [2](#0-1) 

This query is **not scoped to `repository_name`/`repository_owner`** at all — unlike `PushHandler`, which correctly resolves `stacks` via `Repository.from_github_repo_name(repository_name)` before acting [4](#0-3)  and [5](#0-4) . Because `sha` is a 40-hex-char field, and Git commit SHAs are **not secret** (they're public in commit history, PR diffs, CI logs, etc.), any organization/installation that has the Shipit GitHub App installed (and therefore possesses a valid, correctly-signed `status` webhook for its own — otherwise unrelated — repository) can craft a `status` event whose `sha` field is copied from a commit belonging to a **completely different repository/organization** tracked by the same Shipit instance. The signature check passes (it is genuinely signed by Org A's secret for an Org A event), but `Commit.where(sha:)` matches the record belonging to Org B, and `create_status_from_github!` writes a forged status (e.g. `state: 'success'`, arbitrary `context`/`description`/`target_url`) onto Org B's commit [6](#0-5) .

Written commit statuses directly feed `Commit#deployable?` and `Commit#blocked?`, which gate whether a commit is eligible for deployment and continuous delivery:
```ruby
def deployable?
  !locked? && (stack.ignore_ci? || (success? && !blocked?))
end
``` [7](#0-6)  and, when combined with `stack.continuous_deployment?`, can directly trigger an automatic deploy: `schedule_continuous_delivery` fires `ContinuousDeliveryJob` once a commit becomes `deployable?` [8](#0-7) .

### Impact Explanation
This breaks the "organization authenticated versus repository written" binding explicitly called out as in-scope. An attacker who controls (or has push/webhook-triggering rights on) any single repository/org whose GitHub App installation is configured in this Shipit instance can forge a `success` (or any) commit status for a commit belonging to an unrelated, more privileged repository/stack tracked by the same instance, without ever needing that repository's own webhook secret, an `ApiClient` token, or write access to the target repo. On a stack with `continuous_deployment` enabled and CI-status-gated deploys, this can trigger an unauthorized deploy of the target repository — satisfying the "unauthorized deploy" Critical-impact criterion.

### Likelihood Explanation
Requires only: (1) the attacker's own org/repo has the Shipit GitHub App installed (a normal, low-privilege prerequisite already assumed satisfiable by any onboarded org, not requiring a Shipit session/token), and (2) the attacker can obtain a real 40-char SHA of a commit on the victim stack (public information via GitHub UI/API, CI logs, PR pages). No cryptographic secret of the victim org is needed. This is a realistic, low-effort cross-tenant attack in any multi-organization Shipit deployment.

### Recommendation
1. Scope `StatusHandler#process` (and any other handler that looks up records purely by attacker-supplied identifiers, e.g. via `Commit.where(sha:)`) to the repository named in the payload, analogous to `PushHandler`'s use of `stacks`/`Repository.from_github_repo_name(repository_name)`.
2. Additionally verify that `repository_name`'s owner matches the `repository_owner` whose secret was used to verify the signature, closing the same class of gap end-to-end.
3. Consider deriving the authorized scope once in `Handler` (already has `repository_name`) and forcing all handlers that mutate per-repository data to filter through it rather than global lookups by SHA/id alone.

### Proof of Concept
1. Attacker's org "attacker-org" has the Shipit GitHub App installed and is a valid `repository_owner` recognized by `Shipit.github(organization: 'attacker-org')`, giving the attacker a legitimate way to produce a correctly HMAC-signed `status` webhook payload (e.g. by pushing a commit/status update to their own repo, or by controlling a CI system connected to their own repo that sends real GitHub `status` webhooks).
2. Attacker obtains the `sha` of a commit in the target stack "victim/repo" (e.g. from a public PR).
3. Attacker crafts (or relays) a `status` webhook with `sha` = victim commit's SHA, `state: "success"`, and any `context`, but leaves `repository.owner.login` = `attacker-org` so `verify_signature` validates against `attacker-org`'s webhook secret.
4. `WebhooksController#create` dispatches to `StatusHandler`, which executes `Commit.where(sha: params.sha)` [2](#0-1) , matches the victim's `Commit` record (SHAs are effectively globally unique), and calls `create_status_from_github!`, writing a forged `success` status onto it.
5. If `victim/repo`'s stack has `continuous_deployment` enabled and this status makes the commit `deployable?`, `ContinuousDeliveryJob` is scheduled, resulting in an unauthorized deploy triggered entirely by an attacker with no access to `victim/repo`.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([

        "unknown_organization=#{e.message}",

      ].join(' '))
    end
