### Title
Unvalidated swap routes can attach unauthorized token transfers to a user's signed authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary

The Controller accepts opaque caller-supplied swap-route bytes and passes them to the configured router after authorizing only the Controller's intended input transfer. Because the route can name attacker-controlled venue contracts, a rogue hop can execute arbitrary Soroban calls beneath the user's top-level authorization. In particular, it can request `token.transfer(user, attacker, amount)` for a wallet token unrelated to the lending operation. Soroban simulation records that request as a child of the user's `swap_collateral`/strategy authorization entry; if the user signs the returned poisoned authorization tree, the transfer executes.

### Finding Description

`swap_collateral` is a public Controller operation that authenticates `caller`, authorizes the account owner or delegate, and forwards caller-controlled `swap` bytes into the collateral-swap path. [1](#0-0) 

The common swap helper requires only that the payload be non-empty. It snapshots balances, authorizes one exact Controller-to-router input transfer, and invokes `router.execute_strategy(&controller, &amount_in, swap)` with the opaque payload. [2](#0-1) 

The subsequent checks bound only the Controller's input balance, refund unused Controller-held input, and require a positive Controller-held output. They do not inspect the route's venue addresses or prevent route-selected code from adding another child invocation that requires the original caller's authorization. [3](#0-2) 

This maps directly to dependency confusion: the intended dependency is a legitimate swap venue, while an attacker can substitute a rogue venue with the expected interface inside caller-provided route data. The protocol relies on payload/router behavior to select the execution source rather than enforcing an on-chain venue allowlist at the Controller boundary.

The repository contains a regression test demonstrating the condition. A route names an attacker-deployed pool, and that pool calls an unrelated wallet token's `transfer(victim, attacker, WALLET_BALANCE)`. [4](#0-3) [5](#0-4) 

Simulation records the unauthorized wallet transfer as a child of the user's `swap_collateral` authorization entry, and signing that tree makes it execute. [6](#0-5) [7](#0-6) 

### Impact Explanation

An attacker can steal arbitrary SEP-41/Stellar-asset tokens held in a user's wallet, including tokens never supplied to or listed by the protocol. The malicious route can still deliver a fair swap output, so the lending operation can appear successful while an unrelated wallet transfer is embedded in the authorization tree.

This is theft of user funds rather than merely poor route quality: the Controller's measured output checks do not constrain additional calls made by route-selected contracts beneath the user's authorization.

### Likelihood Explanation

Likelihood is Medium. The attack requires the victim to submit a poisoned route and sign an authorization tree containing an unexpected token-transfer child. An attacker can deliver such a payload through a malicious or compromised quote/source-generation path, phishing interface, or copied route bytes. The victim does not need to grant a standing allowance, approve the attacker's contract, or interact with the rogue venue directly.

The theft is not automatic from an attacker-submitted transaction because the victim must authorize the operation. Nevertheless, the dangerous child invocation is produced dynamically by simulation and may be difficult for an ordinary wallet user or integrating client to distinguish unless it specifically rejects unexpected authorization children.

### Recommendation

Enforce route-source integrity rather than trusting arbitrary route-selected contracts:

- Maintain a governance-managed allowlist of approved router venues/pool adapters and reject route hops outside it.
- Alternatively, constrain route payloads to decoded, protocol-defined venue identifiers that resolve only to approved implementations.
- Require wallets and SDK transaction builders to reject strategy authorization trees containing unexpected children; an honest Controller strategy should not need a caller-authorized token transfer other than the explicitly intended operations.
- Add a regression test that treats any extra caller-authorized child produced by route execution as a failure.

### Proof of Concept

1. Deploy a malicious contract exposing the venue `swap` interface expected by the router.
2. Encode a route whose `hop_pool` is that malicious contract, while `token_in`, `token_out`, and `min_out` describe an otherwise valid `USDC -> ETH` swap.
3. Have the malicious `swap` call:

   ```rust
   token::Client::new(&env, &victim_wallet_token)
       .transfer(&victim, &attacker, &victim_balance);
   ```

   The repository's `RogueHopPool` implements exactly this behavior. [5](#0-4) 

4. The victim calls `swap_collateral(caller, account_id, USDC_market, amount, ETH_market, route)`, where `caller` is the victim and `route` is the poisoned payload. The Controller forwards the bytes to the configured router. [1](#0-0) [8](#0-7) 

5. Simulation returns an authorization tree whose root is the victim's `swap_collateral` call and whose child is `wallet_token.transfer(victim, attacker, WALLET_BALANCE)`. The test asserts that the victim's wallet balance becomes zero and the attacker receives `WALLET_BALANCE`. [9](#0-8) 

6. If the victim signs and submits that returned tree, enforcement mode accepts the child and completes both the fair lending swap and the unrelated wallet theft. [7](#0-6)

fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
