### Title
Cross-tenant CI status forgery via unscoped commit SHA lookup unblocks `Commit#blocked?` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the target `Commit` purely by `sha`, with no check that the webhook's origin repository matches the `stack`'s configured repository. An attacker who forks a public target repo shares the exact commit SHAs of the blocking commit's ancestry, and can trigger a legitimately-signed GitHub status webhook from their own fork for that shared SHA, causing Shipit to attach a forged "success" `Status` to the victim stack's commit, flipping `Status::Group` selection and defeating `Commit#blocked?`.

### Finding Description
The claimed binding is: `status.repository (origin of the webhook) == commit.stack.repository (the stack that owns the commit being updated)`. Tracing the code shows this binding is never enforced:

- `Shipit::WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) only checks that the webhook is validly signed for `repository_owner` derived from the payload's own `repository`/`organization` field — it authenticates "a real webhook from *some* repo the app is installed on," not "a webhook for *this particular* stack's repo."
- `StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [1](#0-0) 
This query is **not scoped by `stack_id` or repository at all** — it matches any `Commit` row in the entire database sharing that `sha`, regardless of which repository's webhook produced the event.

- `Commit#create_status_from_github!` → `add_status { statuses.replicate_from_github!(stack_id, github_status) }` uses the **victim commit's own** `stack_id`, so the forged `Status` row is legitimately attributed to the victim's stack. [2](#0-1) 

- `Status::Group#initialize` deduplicates statuses by context, keeping the first occurrence of `statuses.to_a` which is ordered `created_at: :desc` (`has_many :statuses, -> { order(created_at: :desc) }`, `app/models/shipit/commit.rb:12`), before sorting for display:
```ruby
visible_statuses = reject_hidden(statuses.to_a.uniq(&:context))
``` [3](#0-2) 
`StatusHandler` accepts an attacker-controlled `created_at` (`accepts :created_at, String`, line 13), so an attacker can set a `created_at` later than the real failing status, guaranteeing their forged status wins the `uniq(&:context)` dedup for the same `context` string.

- `Status::Common#blocking?` is `!success? && commit.blocking_statuses.include?(context)` (`app/models/shipit/status/common.rb:46-48`). Once the forged row (state: `success`) becomes the significant status for that context, `blocking?` becomes `false` for the intervening commit.

- `Commit#blocked?` (`app/models/shipit/commit.rb:231-237`) then evaluates `stack.commits.reachable.newer_than(...).older_than(self).any?(&:blocking?)`, which is now `false` because the intervening commit's `blocking?` was flipped, and `deployable?` (line 227-229) becomes `true`.

**Attacker's exact path**: fork a public repo tracked by Shipit (fork shares git history/SHAs with upstream by construction — no SHA-1 break needed); enable/trigger a status-producing event on the fork for the shared ancestor SHA (e.g., push a commit status via the GitHub API on the attacker's own repo, or via any CI hooked to the fork) with `context` matching the victim's known blocking check name (discoverable from the target repo's public PR checks) and a fresh `created_at`; GitHub sends a validly-signed `status` webhook for the attacker's own repository to Shipit's `/webhooks` endpoint; `verify_signature` passes because the signature/owner match the attacker's own repo, not the victim's; `StatusHandler#process` looks up commits **by SHA only** and writes the forged status onto the victim's `Commit` row.

**Why existing guards fail**: `verify_signature` authenticates "who sent this webhook" but never checks "does this webhook's repository match the repository of the Shipit stack whose commit is about to be mutated." No model validation or `ExplicitParameters` schema constrains `Commit.where(sha:)` to the originating repository.

### Impact Explanation
A successful forgery lets an unprivileged attacker (who merely owns a fork of a target repository) inject arbitrary CI status data into another tenant's stack's commit, defeating the blocking-status deploy gate and enabling an unauthorized deploy of a commit that legitimately failed CI/should be blocked. This is a cross-tenant integrity violation: a payload originating from repository A (attacker-controlled) mutates state belonging to stack/repository B (victim), matching the "payload for one repository mutating another's stack/commit" and "unauthorized deploy" criteria — Critical severity.

### Likelihood Explanation
Preconditions: the victim repository must be public (or otherwise forkable) and tracked by Shipit with a real blocking-status check configured; the attacker needs only to fork it (standard, unprivileged GitHub action) and be able to produce a status webhook event from their own fork for the shared ancestor SHA (trivial via GitHub's Status API on their own repo, or by wiring any CI to their fork). No Shipit credentials, webhook secret, or GitHub App key are needed — the webhook is authentically signed by GitHub for the attacker's own installation. This is fully repeatable against any public repo/stack combination and does not require breaking SHA-1.

### Recommendation
In `StatusHandler#process`, verify that the webhook's originating repository (`params.dig('repository', 'full_name')`) matches the `full_name` of the repository owning the `stack` of each matched `Commit`, and skip/reject updates where they don't match. More generally, scope the `Commit.where(sha: ...)` lookup by the stack(s) belonging to the webhook's repository rather than a bare, global SHA match.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb` equivalent logic):
1. Create two `Stack`s/`Repository`s, `victim_repo` ("acme/target") and `attacker_repo` ("evil/fork"), each with its own `Commit` row sharing the identical `sha` (simulating shared fork ancestry).
2. On `victim_repo`'s stack, configure a blocking status context (e.g., `"ci/tests"`), create a `Status` with `state: "failure"`, `context: "ci/tests"`, `created_at: t0` on the shared-sha commit, and assert `commit.blocking?` is `true` and `blocked?` for a later commit is `true`.
3. Simulate the attacker's webhook: build params `{ sha: shared_sha, state: "success", context: "ci/tests", created_at: t0 + 1.hour, repository: { full_name: "evil/fork", owner: { login: "evil" } } }` and invoke `Shipit::Webhooks::Handlers::StatusHandler.new.call(params)` (bypassing only the outer signature check, which is orthogonal to this bug since it validates the attacker's own repo, not the victim's).
4. Assert both sides of the binding: before, `status.repository_full_name` (attacker's "evil/fork") != `commit.stack.repository.full_name` ("acme/target"); after processing, a new `Status` row exists with `stack_id == victim_stack.id` sourced from the attacker's payload — confirming the binding was violated.
5. Reload the victim commit and assert `commit.blocking?` is now `false`, `stack_head.blocked?` is `false`, and `deployable?` is `true`, proving the deploy gate was bypassed.
