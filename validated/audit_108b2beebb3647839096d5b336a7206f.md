Confirmed: `Handler#stacks` and `Handler#repository_name` derive the target repository from `payload.dig('repository', 'full_name')` [1](#0-0) , while `WebhooksController#verify_signature` derives the organization used to select the signing secret from a *different* JSON field: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [2](#0-1) . These two fields are never cross-checked against each other, and `verify_webhook_signature` returns `true` unconditionally whenever `webhook_secret` is blank/unset for the selected organization [3](#0-2) , a configuration explicitly documented as optional/nullable (`webhook_secret: # nil`) [4](#0-3) .

### Title
Webhook authentication binds to `repository.owner.login`/`organization.login` but writes are keyed on the unverified `repository.full_name`, enabling cross-organization stack writes - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/handler.rb)

### Summary
The webhook controller selects which GitHub App/organization secret to verify a delivery's HMAC signature against using `repository.owner.login` (falling back to `organization.login`) [5](#0-4) . Every downstream `Handler` subclass, however, resolves the actual repository/stack that gets mutated from the completely separate `repository.full_name` field of the same, unauthenticated JSON body [1](#0-0) . Because GitHub webhook secrets are optional per organization (`webhook_secret` may be `nil`) and `verify_webhook_signature` treats a blank secret as automatically verified [3](#0-2) , an unprivileged attacker can craft a payload whose `repository.owner.login`/`organization.login` names any organization configured without a webhook secret, while setting `repository.full_name` to `victim-org/victim-repo`. The request passes `verify_signature` (secret blank ⇒ `true`) yet the handler acts on `victim-org/victim-repo`'s stacks.

### Finding Description
The equality that should hold is: `organization that authenticated the request == organization owning the repository being written`. Before the request: only GitHub, holding `victim-org`'s webhook secret, can produce a valid signature for events touching `victim-org/*` stacks. After an attacker's crafted POST: the authentication check consults `Shipit.github(organization: repository_owner)` where `repository_owner` is read straight from the attacker-supplied body (`params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`) [6](#0-5) [5](#0-4) . If that organization has no `webhook_secret` configured, `verify_webhook_signature` short-circuits to `true` with no signature check at all [3](#0-2) . The request is then dispatched to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [7](#0-6) , and every handler independently re-reads `repository.full_name` from the same untrusted payload to locate the `Stack`/`Repository` to act on [1](#0-0) , e.g. `PushHandler#process` triggers `stack.sync_github` for any stack matching the branch on that repository [8](#0-7) , and pull-request handlers resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)` to archive/create review stacks [9](#0-8) . Because `repository.owner.login` and `repository.full_name` are independent keys inside the same forgeable JSON, nothing enforces they refer to the same repository.

### Impact Explanation
This crosses the "cross-repository writes" / "unauthorized deploy" bar: an attacker who controls or knows of any organization onboarded to the Shipit instance without a webhook secret can trigger `GithubSyncJob`, create/archive review stacks, or post commit statuses for a *different, unrelated* organization's repositories/stacks that they have no GitHub access to, purely by mismatching two JSON fields in an unauthenticated POST.

### Likelihood Explanation
Likelihood depends on at least one onboarded organization having a blank `webhook_secret`, which the shipped example configs explicitly show as a supported, unset-by-default value (`webhook_secret: # nil`) [4](#0-3) ; multi-organization setups make this more likely since not every org owner may configure a secret. No authentication, session, or GitHub credential is required by the attacker.

### Recommendation
Bind the authenticated identity to the acted-upon resource: derive the organization used both for signature verification and for repository/stack resolution from the *same* field, and reject the payload if `repository.owner.login` does not match the owner segment of `repository.full_name`. Additionally, consider making `webhook_secret` mandatory (refusing to process events for organizations without one) rather than treating a blank secret as implicitly verified.

### Proof of Concept
1. Configure Shipit with two organizations: `victim-org` (has `webhook_secret` set) and `attacker-org` (no `webhook_secret`, i.e., `nil`).
2. Attacker sends `POST /github/webhooks` with header `X-Github-Event: push` and no valid `X-Hub-Signature`, with body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": { "full_name": "victim-org/victim-repo", "owner": { "login": "attacker-org" } }
}
```
3. `verify_signature` calls `Shipit.github(organization: "attacker-org")`; since `attacker-org` has no `webhook_secret`, `verify_webhook_signature` returns `true` unconditionally [3](#0-2) .
4. `PushHandler` reads `repository.full_name` = `"victim-org/victim-repo"` [1](#0-0)  and enqueues `GithubSyncJob`/other writes against `victim-org`'s stacks, without ever needing `victim-org`'s webhook secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
