### Title
Webhook Signature Verification Keys the Trusted Organization/Secret Off an Unverified Payload Field, Allowing Cross-Organization Repository Writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` derives *which* GitHub App/organization (and therefore which `webhook_secret`) is used to validate the HMAC signature from a field taken out of the still-unauthenticated request body, rather than from a value that is bound to the credential actually used to sign the request. This breaks the intended binding: **organization authenticated == repository the engine subsequently acts on**.

### Finding Description
`verify_signature` computes the organization to check against like this: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight out of `params` — i.e., out of the same JSON body whose authenticity the signature check is supposed to establish — *before* that body has been verified. `Shipit.github(organization: repository_owner)` then resolves the `GithubApp`/`webhook_secret` for **that claimed organization**, and the HMAC is validated against **that** secret: [3](#0-2) 

This design is confirmed by the test suite, which explicitly stubs `Shipit.github(organization: 'shopify')` per-request and expects an org-specific `verify_webhook_signature` call: [4](#0-3) 

and by the existence of a dedicated `Shipit::GithubOrganizationUnknown` rescue path, showing the engine is built to serve multiple organizations, each with its own webhook secret: [5](#0-4) 

Once `head(:ok)`/`head(422)` logic passes, `WebhooksController#create` re-parses the same raw body and dispatches it, unmodified, to the registered handlers (e.g. the push handler that queues `GithubSyncJob`, as seen in the fixture-driven test asserting `GithubSyncJob` args are taken from `params['repository']`/`params['after']`): [6](#0-5) [7](#0-6) 

Because the field used to *pick the trust anchor* (`repository.owner.login`) and the field used to *pick the repository/stack that gets acted upon* (`repository.full_name`, consumed later by the handlers) live in the very same attacker-controlled JSON body, an attacker who legitimately controls a webhook secret for **any one** organization configured in the Shipit instance can forge a payload whose `repository.owner.login` matches their own org (so the HMAC check passes against their known secret) while `repository.full_name`/other repository identifiers point at a completely different organization's repository. The signature only proves "this body was signed with org A's secret" — it says nothing about the truthfulness of the repository fields inside that same body, yet those fields drive which Stack/repository is subsequently synced, statused, merged, etc.

This is the exact class of bug described in the reference report: a value used to establish trust (bridge-delivered/verified amount vs. hop parameters it never re-validates) is silently trusted to also govern a different, more sensitive decision (which counterparties/final hop absorb the delta) without re-deriving that decision from a verified source.

### Impact Explanation
An attacker who legitimately owns (or has hijacked) the webhook secret for one organization registered with the Shipit instance can forge webhook events (push, status, check_suite, pull_request, membership, etc.) that are accepted as authentic for **any other organization's repositories** tracked by the same Shipit installation. Depending on which handler is triggered, this can drive `GithubSyncJob`, commit `Status` creation, `RefreshCheckRunsJob`, membership/team mutations, or merge-request processing against a victim organization's Stack — i.e., cross-repository/cross-organization writes to Shipit's internal state using a credential that was never authorized for that organization. This matches the report's Critical-band "cross-repository writes" impact category.

### Likelihood Explanation
Exploitation requires only a valid webhook secret for *some* organization already registered in the multi-tenant Shipit deployment — not for the victim organization, and not any Shipit session/API token/GitHub App private key. Any environment configuring more than one organization behind a shared Shipit instance is affected, and no interaction beyond a single crafted HTTP POST to `/webhooks` is needed.

### Recommendation
Do not select the verification secret from a field inside the unauthenticated payload. Instead, tie the webhook delivery to an organization/installation via a channel that is itself part of the cryptographic binding (e.g., verify against every configured organization's secret and require the discovered organization to also match `installation.id`/`repository.owner.id` from GitHub's own numeric IDs cross-checked against a pre-registered installation-to-org mapping stored server-side), or run one secret per app installation but confirm the resolved organization's ID against the same installation used to deliver the request, not a login string echoed back inside the body.

### Proof of Concept
1. Shipit is configured with GitHub App installations for `org-A` and `org-B`, each with distinct `webhook_secret`s.
2. Attacker is an admin of `org-A` and thus knows `org-A`'s `webhook_secret` (a normal, unprivileged-with-respect-to-`org-B` capability).
3. Attacker builds a push payload JSON body:
   - `repository.owner.login = "org-A"`
   - `repository.full_name = "org-B/victim-repo"`
   - `after = <attacker-chosen sha>`
4. Attacker computes `X-Hub-Signature: sha1=HMAC(org-A secret, body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `WebhooksController#verify_signature` computes `repository_owner = "org-A"`, fetches `org-A`'s app/secret via `Shipit.github(organization: "org-A")`, and the HMAC check succeeds (per `app/controllers/shipit/webhooks_controller.rb:24-30,59-62`).
6. `create` dispatches the same body to the push handler, which reads `repository.full_name = "org-B/victim-repo"` and enqueues `GithubSyncJob`/updates commit state for `org-B`'s Stack, even though `org-B`'s webhook secret was never used or known to the attacker.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
