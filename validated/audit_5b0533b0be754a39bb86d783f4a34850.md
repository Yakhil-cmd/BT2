### Title
Rounding independently-computed headers-commission shares before summing mints/loses bytes - ([File: headers_commission.js])

### Summary
`headers_commission.js` splits a payer unit's `headers_commission` among the `earned_headers_commission_recipients` of the winning child unit by rounding each recipient's share **independently** with `Math.round()`, then only later aggregating those already-rounded amounts with `SUM()` into `headers_commission_outputs`. Because the consensus rule only guarantees that the recipients' `earned_headers_commission_share` percentages sum to exactly 100 (an integer constraint checked once, unrelated to the final byte amounts), the sum of the independently-rounded byte amounts can end up **greater than** (or less than) the actual `headers_commission` collected from the payer unit. This is the same rounding-before-summing root cause as the reported PoolTogether issue, but here it can literally mint or destroy bytes.

### Finding Description
When a stable child unit with multiple authors wins the headers commission race, `calcHeadersCommissions()` computes, for each recipient address, an integer amount from the recipient's percentage share of the *full* commission amount: [1](#0-0) 

For the SQL/mysql path the exact same operation is expressed with `ROUND(...)`: [2](#0-1) 

and again per-parent for multi-recipient splits: [3](#0-2) 

These per-recipient rounded contributions are inserted into `headers_commission_contributions` and later aggregated purely by `SUM(amount)` with no cross-check against the original `headers_commission` field of the payer unit: [4](#0-3) 

The only consensus-level validation on the recipient list is that the declared percentage shares (integers) sum to exactly 100 — it does not, and cannot, guarantee that `Σ round(hc * share_i / 100)` equals `hc`: [5](#0-4) 

The recipient list itself is fully attacker-controlled: any multi-authored unit can declare `earned_headers_commission_recipients` with arbitrary integer shares (as long as they sum to 100), and this list is persisted verbatim and later used at redistribution time: [6](#0-5) 

Because `Math.round()` rounds each share to the nearest integer independently, the sum of rounded parts can exceed the true (real-valued) total whenever the fractional remainders of several shares are each ≥ 0.5. For a payer unit with `headers_commission = hc` and recipients with shares e.g. 33/33/34:
```
round(hc*0.33) + round(hc*0.33) + round(hc*0.34)
```
can be strictly greater than `hc` for many values of `hc` (see PoC). Every extra byte produced this way becomes a real, spendable `headers_commission_outputs` entry, redeemable later via a `headers_commission`-type payment input (validated in `validation.js` against `mc_outputs.calcEarnings`, which simply reads back the summed table) — i.e., bytes are created without any unit having actually paid that amount in fees.

### Impact Explanation
This is a supply-inflation bug in the base-currency fee-redistribution mechanism: an attacker can author small units with multiple authors and hand-picked `earned_headers_commission_share` values so that, whenever such a unit wins the headers-commission race, the sum of rounded per-recipient shares exceeds the payer unit's real `headers_commission`. The excess bytes are indistinguishable from legitimately-earned commission and become spendable balance, permanently increasing the circulating byte supply beyond what any node fee actually paid. Because every full node computes the same deterministic (buggy) result, this does not cause consensus disagreement/forks, but it does allow an attacker to systematically mint bytes over many units, which is a direct asset-inflation vulnerability. The inverse case (rounding down net) instead permanently freezes a fraction of legitimately earned commission, a smaller integrity/loss issue but same root cause.

### Likelihood Explanation
Any user can author a multi-author unit and freely choose `earned_headers_commission_recipients` shares (only constrained to sum to 100 and be positive integers), and headers-commission winners are decided pseudorandomly by hash tie-break among sibling units — so an attacker fully controls the share vector on their own unit and merely needs it to occasionally win the race, which happens routinely for legitimate reasons in the DAG. Repeating this over many low-`headers_commission` units makes exploitation practical and low-cost.

### Recommendation
Round shares using a scheme that preserves the exact total, e.g. the largest-remainder method: compute floor(hc*share_i/100) for all recipients, sum the floors, and distribute the remaining `hc - Σfloor` one byte at a time to the recipients with the largest fractional remainders (using a canonical/deterministic tie-break such as address order, consistent with existing determinism requirements). This guarantees `Σ amount_i == hc` exactly for every payer unit, eliminating both the inflation and the freezing cases.

### Proof of Concept
1. Author a unit `U` with 3 authors and `earned_headers_commission_recipients` = `[{addrA,33},{addrB,33},{addrC,34}]` (sums to 100, passes `validateHeadersCommissionRecipients`).
2. Arrange (as is routine in the DAG) for `U` to be selected as the header-commission winner (`getWinnerInfo`) for a parent unit whose `headers_commission = 5` bytes.
3. `calcHeadersCommissions()` computes:
   - `round(5*33/100) = round(1.65) = 2`
   - `round(5*33/100) = round(1.65) = 2`
   - `round(5*34/100) = round(1.70) = 2`
   - Sum inserted into `headers_commission_contributions` = 6, while the payer unit's actual `headers_commission` is only 5.
4. `headers_commission_outputs` for that mci now holds 6 spendable bytes sourced from a unit that only paid 5 — 1 byte has been minted out of thin air, later spendable via a normal `headers_commission` input in a payment message (validated only via `mc_outputs.calcEarnings`, which just re-reads this inflated sum).
5. Repeating this pattern (attacker controls both the recipient-share vector and can create many small, multi-authored units) accumulates inflation over time. [1](#0-0) [5](#0-4)

function validateHeadersCommissionRecipients(objUnit, cb){
	if (objUnit.authors.length > 1 && typeof objUnit.earned_headers_commission_recipients !== "object")
		return cb("must specify earned_headers_commission_recipients when more than 1 author");
	if ("earned_headers_commission_recipients" in objUnit){
		if (!isNonemptyArray(objUnit.earned_headers_commission_recipients))
			return cb("empty earned_headers_commission_recipients array");
		var total_earned_headers_commission_share = 0;
		var prev_address = "";
		for (var i=0; i<objUnit.earned_headers_commission_recipients.length; i++){
			var recipient = objUnit.earned_headers_commission_recipients[i];
			if (!isPositiveInteger(recipient.earned_headers_commission_share))
				return cb("earned_headers_commission_share must be positive integer");
			if (hasFieldsExcept(recipient, ["address", "earned_headers_commission_share"]))
				return cb("unknown fields in recipient");
			if (!isValidAddress(recipient.address))
				return cb("invalid recipient address checksum");
			if (recipient.address <= prev_address)
				return cb("recipient list must be sorted by address");
			total_earned_headers_commission_share += recipient.earned_headers_commission_share;
			prev_address = recipient.address;
		}
		if (total_earned_headers_commission_share !== 100)
			return cb("sum of earned_headers_commission_share is not 100");
	}
	cb();
}
