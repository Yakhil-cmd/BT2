### Title
Webhook signature is verified against the claimed organization, not against the repository the payload actually mutates - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate a request against using a field taken from the JSON body itself (`repository.owner.login`, or `organization.login` as a fallback), but none of the downstream event handlers re-check that this same organization owns the repository that is actually acted upon. The repository/stack that gets mutated is instead resolved from a *different* field of the same payload, `repository.full_name`, with no cross-check against the organization whose secret validated the signature.

### Finding Description
`verify_signature` derives the signing organization purely from the request body: [1](#0-0) [2](#0-1) 

It fetches `Shipit.github(organization: repository_owner)` and validates the HMAC signature using that organization's configured `webhook_secret`: [3](#0-2) 

This confirms only that *some* body was signed by *some* configured organization's secret — it does not bind that organization to which repository/stack the event will operate on.

Every handler (e.g. `PushHandler`) instead resolves the target `Stack`/`Repository` using a completely separate JSON field, `repository.full_name`, taken from `Handler#repository_name`: [4](#0-3) [5](#0-4) 

Because `verify_signature` and the handler each read a *different* JSON field to decide (a) which secret authenticates the request and (b) which repository the request acts on, an attacker who legitimately controls one configured organization's GitHub App/`webhook_secret` (e.g., their own tenant in a multi-organization Shipit deployment, as shown by the multi-org secrets layout) can sign an arbitrary payload with their own organization's secret while setting `repository.full_name` to a victim stack belonging to a *different* configured organization: [6](#0-5) 

The equality that should hold but doesn't: `organization authenticated by the signature == organization that owns the repository being written`. `verify_signature` checks `Shipit.github(organization: params.dig('repository','owner','login'))`, while `Handler#stacks` acts on `Repository.from_github_repo_name(payload.dig('repository','full_name'))` — these two lookups are never cross-validated against each other.

### Impact Explanation
This breaks the trust boundary between organizations/tenants configured on the same Shipit instance. An org whose GitHub App is legitimately configured (and whose `webhook_secret` its own admins therefore know) can forge webhook events (`push`, `status`, `check_suite`, `membership`, `pull_request`) that are processed as if they came from GitHub for a completely different organization's repositories/stacks. This can trigger unwanted `GithubSyncJob` runs, spoofed commit `Status` records that influence deploy/merge gating, or bogus `RefreshCheckRunsJob`/`membership` mutations against a stack the attacker does not own — i.e., cross-repository writes/state manipulation outside the attacker's authorized organization boundary.

### Likelihood Explanation
Requires the deployment to host more than one organization's GitHub App configuration (explicitly supported, as shown by the multi-org `config/secrets*.yml` layout) and requires the attacker to be a legitimate admin/owner of one of those configured organizations (they know their own org's `webhook_secret` by design, since they configure their own GitHub App). No GitHub token, Shipit session, or `ApiClient` credential of the victim organization is required — only knowledge of the attacker's own, already-provisioned organization secret, crafting a raw signed HTTP POST to `/github/webhooks`.

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler`), enforce that the organization whose secret validated the signature (`repository_owner`) matches the owner encoded in `repository.full_name` (and `organization.login` when used) before dispatching to any handler. Reject the webhook (422) on mismatch.

### Proof of Concept
1. Deployment hosts two configured orgs: `org-a` (attacker-controlled GitHub App, attacker knows its `webhook_secret`) and `org-b` (victim, has a Shipit `Stack` for `org-b/victim-repo`).
2. Attacker crafts a JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac(webhook_secret_of_org_a, body)>` and sets `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` = `"org-a"`, fetches `Shipit.github(organization: "org-a")`, and the signature validates successfully.
5. `PushHandler#process` resolves the target stacks via `Repository.from_github_repo_name("org-b/victim-repo")`, and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on the victim's stack — despite the request only ever being authenticated against `org-a`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
