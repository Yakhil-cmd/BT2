### Title
Webhook signature is verified against the org derived from `repository.owner.login`, but every event handler acts on the repository named by `repository.full_name` - allowing cross-organization / cross-repository writes - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks which per-organization `webhook_secret` to validate the HMAC signature with based on `repository_owner`, a value read straight out of the untrusted, not-yet-verified JSON body. Every webhook handler, however, resolves the target `Stack`/`Repository` to mutate using a *different* field of the same body: `repository.full_name`. Nothing ties these two fields together, so a payload that is validly signed for organization A can freely name a repository belonging to organization B, and Shipit will act on B's stacks.

### Finding Description
The verification step is: [1](#0-0) [2](#0-1) 

`repository_owner` is taken from `params.dig('repository', 'owner', 'login')` (or `organization.login`) and used to select the `Shipit.github(organization: repository_owner)` config, whose `webhook_secret` is then HMAC-checked against the raw body.

Every handler, in contrast, resolves the acted-upon repository from a sibling but distinct field: [3](#0-2) 

`PushHandler`, `CheckSuiteHandler`, `StatusHandler`, `MembershipHandler`, and the `PullRequest::*` handlers all consume `params`/`payload` fields (`repository.full_name`, `organization.login`, `sha`, etc.) that are never cross-checked against the value used for signature routing: [4](#0-3) [5](#0-4) [6](#0-5) 

Shipit is explicitly designed to run multi-tenant, with one `webhook_secret` per GitHub organization configured in `secrets.yml`: [7](#0-6) 

This is the exact equality the scan rules call out: "an organization that authenticated versus the repository that is written." Here:
`organization whose webhook_secret authenticated the request (repository.owner.login)` ≠ `organization/repository whose Stack rows are mutated (repository.full_name)`.

### Impact Explanation
An attacker who legitimately controls (or has been handed) the GitHub App/webhook secret for **any one** organization configured in the Shipit instance (a very low-trust position — merely being an org admin who set up their own low-value org's integration, or having the secret leaked for a low-value org) can forge a validly-signed webhook body claiming `repository.owner.login = their-org` (to pass signature verification with their own secret) while setting `repository.full_name = victim-org/victim-repo` (or `organization.login = victim-org` for the `membership` event). Consequences per handler:

- `PushHandler`: triggers `stack.sync_github(expected_head_sha:)` on any stack of the victim repository, forcing Shipit to resync from an attacker-chosen SHA.
- `StatusHandler`: injects arbitrary commit statuses (`create_status_from_github!`) onto commits of an unrelated repository/stack, which can satisfy `ci.require` checks configured in `shipit.yml` and enable an **unauthorized deploy**.
- `CheckSuiteHandler`: schedules check-run refreshes for arbitrary stacks/commits, similarly influencing deploy gating.
- `MembershipHandler`: creates/mutates `Team`/`User` membership records tied to `organization.login`, independent of which secret authenticated the call.

This is a cross-organization/cross-repository write vulnerability that can lead to an unauthorized deploy, matching the Critical impact bar defined in the rules ("cross-repository writes... or an unauthorized deploy").

### Likelihood Explanation
Exploitation requires only knowledge of one organization's `webhook_secret` in a multi-org Shipit deployment — a credential with far lower privilege than repository write access, an `ApiClient` token, or a GitHub App private key. Multi-org configuration is a documented, supported pattern (`config/secrets.development.shopify.yml`), and nothing in `WebhooksController` or `Shipit::Webhooks::Handlers::Handler` cross-validates that the signing organization matches the repository named in the payload. No GitHub session, TLS interception, or social engineering is needed — the attacker crafts and POSTs the JSON body directly to the `/webhooks` endpoint with a correctly computed `X-Hub-Signature`.

### Recommendation
After signature verification succeeds, re-derive the acting organization strictly from the already-verified `repository_owner`/`organization.login`, and reject (or scope) any handler processing where `repository.full_name`'s owner segment does not match the organization whose secret validated the signature. Concretely, pass the verified `repository_owner` into `Handler.call` and have `Handler#stacks` filter `Repository.from_github_repo_name(repository_name)` only when its owner equals the verified organization.

### Proof of Concept
1. Configure Shipit (as documented) with two orgs, `attacker-org` and `victim-org`, each with its own `webhook_secret` (`config/secrets.development.shopify.yml` pattern).
2. Attacker knows/controls `attacker-org`'s `webhook_secret` (e.g., they administer that GitHub App installation).
3. Attacker crafts a `status` webhook body:
   ```json
   {
     "sha": "<victim-commit-sha>",
     "state": "success",
     "context": "ci/required-check",
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
   }
   ```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org_webhook_secret, body)` and sends it to `/webhooks` with `X-Github-Event: status`.
5. `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:25-30`) resolves `repository_owner = "attacker-org"`, fetches `attacker-org`'s secret, and the signature validates.
6. `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`, which locates `Commit.where(sha: params.sha)` — matching the victim's commit — and calls `create_status_from_github!(params)` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`), injecting a forged "success" status on `victim-org/victim-repo`'s commit, potentially satisfying `ci.require` and enabling deploy of that commit despite the attacker never having any credential tied to `victim-org`.
