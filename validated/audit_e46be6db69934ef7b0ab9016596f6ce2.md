### Title
AA `data_feed()` formula can consume a value from a not-yet-final "good" unit that later becomes `final-bad`, letting a self-conflicting oracle/AA author extract an AA response for data that is subsequently voided - ([File: data_feeds.js])

### Summary
`readDataFeedValue()` in `data_feeds.js` has an `unstable_opts`/`bAA` path that lets an AA's `data_feed()` formula pick up feed values from units that are **not yet stable**, filtered only by the unit's *current, provisional* `sequence === 'good'` flag. That flag is not final: `validation.js`/`main_chain.js` show a unit's `sequence` can start as `'good'`, later flip to `'temp-bad'`, and finally resolve to `'final-bad'` once a conflicting (double-spending) unit from the same author is discovered and the MCI stabilizes. If an AA response is computed using such a provisional `'good'` data-feed unit before the real conflict is known, the AA's fund-moving response is already produced and cannot be undone once the feed-posting unit is later voided as `final-bad`. This mirrors the ToBet pattern: an action is taken based on transient, not-yet-final state, and the state is subsequently invalidated ("rolled back") while the externally visible effect (the payout/response) persists.

### Finding Description
`dataFeeds.readDataFeedValue()` supports reading data-feed values from `storage.assocUnstableMessages` when `unstable_opts` (passed as `bAA` from AA formula evaluation) is truthy: [1](#0-0) 

The only finality gate applied is `objUnit.sequence !== 'good'` — i.e. it excludes only units *already known* to be bad, not units whose sequence is merely provisional: [2](#0-1) 

This function is invoked directly from the AA formula's `data_feed()` operator with `bAA` as the `unstable_opts` argument, so AA response logic can read still-unstable feed data: [3](#0-2) 

The `sequence` value is not final at the time it is `'good'`. `validation.js`'s `checkSerialAddressUse()` shows that a unit is marked `'good'` only in the absence of *currently known* conflicting units, and can be downgraded to `'temp-bad'`/`'final-bad'` later as soon as a conflicting unit is detected — this detection is a function of what has propagated to the node so far, not of DAG-topological finality: [4](#0-3) 

The actual, irreversible resolution of `'temp-bad'` sequence units into `'good'` or `'final-bad'` only happens during MC stabilization, in `handleNonserialUnits()`: [5](#0-4) 

Crucially, when a unit that carried unstable payload (including `data_feed` messages) is finally stabilized as `'final-bad'`, its payload is silently dropped and never written into the durable data-feed KV index: [6](#0-5) 

Putting this together: at the time an AA trigger is processed (which itself only happens after the *trigger unit's own* mci is stable, per `handleAATriggers`/`markMcIndexStable`), the AA's `data_feed()` call may read a **different, still-unstable** unit's data-feed payload whose `sequence` is merely `'good'` for now. If that data-feed unit's author later posts (or already has pending) a conflicting/double-spending unit that wins the DAG-ordering, the data-feed unit becomes `'final-bad'` and its payload is discarded — but the AA has already computed and posted its (irreversible) response based on that value.

### Impact Explanation
This can cause a network-visible, exploitable state inconsistency:
- An address that both authors data-feed units and controls conflicting/double-spend inputs can arrange for a data-feed unit to be observed as `'good'` while an AA evaluates it, get a favorable AA response (payment, state change) computed and posted, and then let the conflicting unit win, causing the data-feed unit to resolve to `'final-bad'` and vanish from the canonical feed history.
- Because AA responses are deterministic functions of locally-observed unstable state (which is itself a function of real-time p2p propagation, not of the DAG's eventual deterministic order), different full nodes could, in principle, observe different sets of qualifying unstable AA-authored feed units at the moment they execute the same primary trigger, causing them to compute different AA response outputs for the same trigger — a **node disagreement on validity**, which nodes normally treat as fatal (units must be byte-identical/deterministic).
- The direct exploitable outcome is an AA fund loss: the AA pays out based on a data value that is retroactively voided, and the loss is not clawed back.

### Likelihood Explanation
Exploitation requires:
1. An attacker-controlled address that is itself an AA (since the `bAA` filter in `readDataFeedValue`/`dataFeedExists` restricts unstable candidates to units authored by AA addresses, i.e. `objUnit.bAA`), or an AA-composed chain of responses, posting a `data_feed` message as part of its own response, and
2. That AA-response unit having (or being made to have) a conflicting/double-spend input from an unrelated pending unit by the same author-controlled AA logic, timed so that the conflict is not yet resolved when a *victim* AA's trigger consumes the feed via `data_feed()`.

This is a non-trivial, multi-step timing attack requiring precise control over unit ordering and network propagation, and depends on a victim AA actually using `data_feed()` against an oracle/AA whose feed-posting units can plausibly become non-serial. It is realistic in composability scenarios (AA-to-AA data feeds) but not as simple to trigger as the original ToBet bug (which exploited an off-chain polling loop with no finality concept at all).

### Recommendation
Restrict the AA `data_feed()`/`dataFeedExists()` unstable lookup path so that it never returns a value from a unit whose `sequence` could still change — e.g., require that the unstable data-feed unit have no known unstable inputs at all (i.e., only trust units that are inherently sequence-immutable, or require full stabilization for AA-to-AA data-feed use), or explicitly reject/defer AA execution until any data-feed unit it depends on is fully stable. At minimum, document/verify that this unstable-read path cannot introduce cross-node nondeterminism in AA responses, and add a check that voids/reprocesses any AA response whose underlying `data_feed` input unit was later found to be `final-bad`.

### Proof of Concept
Conceptual PoC (cannot be executed without live multi-node network/timing control):
1. Deploy AA `Oracle` and AA `Victim`, where `Victim`'s bounce/response formula uses `data_feed(['oracles' => 'Oracle', 'feed_name' => 'X'])`.
2. Have `Oracle` (itself an AA) post two conflicting outputs/units where the first posts a `data_feed` message with `X = favorable_value`, and a second, conflicting (double-spending the same AA-state input) unit that will ultimately win in the DAG.
3. Trigger `Victim` while the first `Oracle` unit is still unstable but temporarily `sequence='good'` (per `checkSerialAddressUse` in `validation.js`), so `readDataFeedValue`'s unstable-AA path in `data_feeds.js` returns `favorable_value` and `Victim` issues a payout based on it.
4. Allow the network to resolve the conflict such that the `data_feed`-posting unit becomes `sequence='final-bad'` at stabilization (`main_chain.js` `handleNonserialUnits`), discarding its payload (`main_chain.js` `saveUnstablePayloads`) — the payout from step 3 is already final and cannot be reversed. 					return 1;

			var feed = arrCandidates[arrCandidates.length - 1];
			objResult.value = feed.value;
			objResult.unit = feed.unit;
			objResult.mci = feed.mci;
			return handleResult(objResult);
		}
