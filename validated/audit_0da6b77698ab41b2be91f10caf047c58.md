### Title
Bad-debt socialization computes the loss write-down against a stale accrual index/lindex for "other" debt assets - (File: `mainnet/contracts/vault/v0-vault-usdc.clar`, function `socialize-debt`)

### Summary
The Gangsterfinance report describes an "incorrect dividends" bug where a shared distribution value was computed against data that was not refreshed for the party consuming it, causing the wrong amount to be attributed as gain/loss to stakeholders. The closest reachable analog in the in-scope vault code is `socialize-debt`, which writes down the supplier-facing liquidity index (`lindex`) — effectively the LP "dividend"/redemption-rate state — using the vault's own cached `index`/`lindex`/`total-assets()` **without first calling `accrue`**, unlike every other state-mutating vault entrypoint (`deposit`, `redeem`, `system-borrow`, `system-repay`, `flashloan`), which all begin with `(u (try! (accrue)))`.

### Finding Description
In each vault (e.g. `v0-vault-usdc.clar`), `socialize-debt` is called by `market.clar`'s `socialize-debt-asset` fold helper during a liquidation that leaves a borrower with no collateral (bad debt): [1](#0-0) 

Crucially, `market.clar`'s `liquidate` only calls `vault-system-repay` (which triggers `accrue`) for the **debt-aid actually being liquidated**: [2](#0-1) 

But when the borrower has bad debt on **other** asset vaults (`stripped-debt-list`/`fresh-debt-list`, built from `filter-out-debt-asset` over the position's full debt list), those other vaults are socialized directly via `vault-socialize-debt`/`socialize-debt-asset` **without any prior call to those vaults' own `accrue`**: [3](#0-2) 

Inside the target vault, `socialize-debt` computes the write-down entirely from the vault's currently stored (potentially stale, since-last-accrual) state: [4](#0-3) 

Compare this to every other public vault entrypoint, which explicitly refreshes the index/lindex first: [5](#0-4) 

Because `debt-reduction` (`mul-div-down scaled-amount idx INDEX-PRECISION`) and `old-total-assets` (`total-assets` → uses `total-debt` which is `calc-cumulative-debt(principal-scaled, index)`) are both derived from a stale `idx`/`lindex` if the "other" vault has not been touched since some earlier block, the writedown ratio applied to `lindex`:

```
new-lindex = current-lindex * (old-total-assets - debt-reduction) / old-total-assets
```

is computed against an accounting snapshot that omits interest that should have already accrued to suppliers between `last-update` and the current block. This under- or overstates the fraction of the pool's assets being written off relative to the true (post-accrual) total-assets, so the reduction applied to LP suppliers' redemption index (`lindex`) does not match the real economic loss ratio for that asset's pool.

The `map-set index-cache` refresh that follows in `socialize-debt-asset` (line 892-895 in `v0-4-market.clar`) calls `vault-accrue` **after** the write-down has already been applied to the stale base, so it does not correct the ratio — it only re-syncs the market's index cache to the vault's now-updated (but already miscalculated) state.

### Impact Explanation
All LP suppliers of the "other" (not currently-liquidated) vault share the `lindex`-based liquidity index used to compute their redeemable balance via `convert-to-assets-preview`. If the write-down ratio is computed against a stale, under-accrued `total-assets`, suppliers as a group are socialized for a bad-debt loss using an incorrect basis — the redemption rate for the affected ztoken diverges from the value it should have after correctly accruing pending interest first. This is a shared-pool value miscalculation imposed on unprivileged supplier principals by the liquidator/borrower/keeper interaction they have no control over, matching "a socialization charged to all suppliers." Depending on the direction of the drift (positive or negative pending interest at the time), this either permanently freezes/erodes a slice of LP yield or temporarily misprices the ztoken, which lands in the Temporary/permanent freezing of unclaimed yield impact tier.

### Likelihood Explanation
This path only triggers when: (1) a liquidation occurs, (2) it fully exhausts the borrower's collateral (bad debt), and (3) the borrower held debt in more than one asset/vault, so that a vault other than the one being repaid in the same transaction needs `socialize-debt` called on it. The multi-asset bad-debt path is a normal (not attacker-privileged) liquidation outcome — any liquidator triggering it is enough; no special permission or DAO action is required. The magnitude of the miscalculation depends on how much time has elapsed since that other vault's `last-update`, which is exactly analogous to the "stale index primed/consumed" pattern flagged as in-scope.

### Recommendation
Call `(try! (accrue))` at the start of `socialize-debt` in each vault (mirroring `deposit`/`redeem`/`system-borrow`/`system-repay`/`flashloan`) so `index`, `lindex`, and `last-update` are refreshed before computing `debt-reduction`, `old-total-assets`, and the resulting `new-lindex` write-down. Alternatively, have `market.clar`'s `socialize-debt-asset` call `vault-accrue` for the target `asset-id` before invoking `vault-socialize-debt`, ensuring the loss ratio is always computed on a freshly-accrued basis.

### Proof of Concept
Not independently reproduced against a live fork; this is derived from static analysis of the vault/market contracts, since a full end-to-end PoC would require simulating multi-asset bad-debt liquidation timing (elapsed blocks between accruals on the "other" vault) which was not verified with the available tooling. The core, verifiable fact is the code-level asymmetry: `socialize-debt` omits the `(try! (accrue))` call present in every sibling public vault function, and `market.clar`'s bad-debt fold (`socialize-debt-asset`) never accrues the "other" asset vaults before calling `vault-socialize-debt` on them, only after. (define-public (socialize-debt (scaled-amount uint))
  (let ((scaled-principal (var-get principal-scaled))
        (borrowed (var-get total-borrowed))
        (idx (var-get index))
        (current-assets (var-get assets))
        (current-lindex (var-get lindex))
        (old-total-assets (total-assets))
        (debt-reduction (mul-div-down scaled-amount idx INDEX-PRECISION))
        (principal-reduction (if (> scaled-principal u0)
                                (mul-div-down scaled-amount borrowed scaled-principal)
                                u0))
        ;; Write down lindex proportionally to loss in total-assets
        (new-lindex (if (and (> old-total-assets u0) (> old-total-assets debt-reduction))
                       (mul-div-down current-lindex (- old-total-assets debt-reduction) old-total-assets)
                       u0)))

    (try! (check-caller-auth))
    (asserts! (> scaled-amount u0) ERR-AMOUNT-ZERO)

    (var-set lindex new-lindex)
    (var-set principal-scaled (if (> scaled-principal scaled-amount) (- scaled-principal scaled-amount) u0))
    (var-set total-borrowed (if (> borrowed principal-reduction) (- borrowed principal-reduction) u0))
    (var-set assets (if (> current-assets principal-reduction) (- current-assets principal-reduction) u0))
