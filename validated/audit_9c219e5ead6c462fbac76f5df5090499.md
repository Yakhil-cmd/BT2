### Title
Stale oracle price survives a governance `set_oracle` executed inside `flash_position` - (File: contracts/controller/src/context.rs)

### Summary
`flash_position` snapshots every required price before invoking the receiver, then evaluates and persists the newly created debt using those cached prices after the receiver returns. A receiver can execute a ready governance operation that replaces the collateral asset's oracle during the callback, leaving the controller to value the new collateral with the pre-transition price.

### Finding Description
`process_flash_position` calls `prefetch_strategy_prices` before minting and forwarding the flash debt and before invoking the receiver. [1](#0-0) 

`Context::fetch_prices` populates `token_prices` only for assets that are not already cached, and `cached_price` later returns the retained feed rather than re-reading the aggregator. [2](#0-1) 

The receiver callback can call the separate governance contract. `Governance::execute` permits anyone to execute a ready operation when `executor` is `None`. [3](#0-2) 

A ready `ConfigureAssetOracle` operation executes `set_oracle` on the price aggregator. [4](#0-3)  The aggregator accepts that call because governance is its owner, and `set_oracle` replaces the registered configuration. [5](#0-4) 

After the callback, the controller measures collateral receipts, deposits them, checks that the flash position remains open, and calls `strategy_finalize`. [6](#0-5)  `strategy_finalize` then performs the final solvency checks through the same `Context`, so it still sees the oracle snapshot obtained before the governance state transition. [7](#0-6) 

This is the same bug class as the Linux report: a value is read before an operation that can invalidate it, and the stale value is dereferenced after that state transition instead of being refreshed under the equivalent lock.

### Impact Explanation
An attacker can open a flash-position account whose collateral is sufficient only under the pre-callback oracle price. The flash-borrowed asset is converted into the declared collateral, the stale valuation passes the final health-factor and collateral checks, and the account is persisted with debt exceeding its value under the oracle configuration installed during the callback.

The borrowed asset is real pool liquidity controlled by suppliers. Once the account is valued by the new oracle, it is undercollateralized and can be liquidated or cleaned up as bad debt, socializing the shortfall into the pool. This permits theft of user funds or protocol insolvency when the price reduction is large enough.

### Likelihood Explanation
The attack needs a valid oracle-replacement operation that is already `Ready`; it does not require the attacker to hold the governance owner, proposer, executor, oracle-provider, or pool role. Execution with `executor=None` is permissionless, and the receiver callback is already an intended unprivileged extension point. [8](#0-7) 

A deployed Wasm receiver can encode the target aggregator, function, operation arguments, predecessor, and salt in `data`, execute the operation, swap the forwarded debt into the collateral asset, and transfer that collateral to the controller. The operation is not an invalid parameter or leaked-key path: it is an authorized, ready governance transition executed at a time chosen by the attacker.

### Recommendation
Do not reuse a pre-callback price for post-callback risk acceptance. After `invoke_receiver` returns, explicitly invalidate or replace `token_prices` for every asset used by the new or modified position and fetch fresh feeds from the aggregator before `process_deposit`, final solvency checks, and persistence.

The same treatment should apply to other externally mutable values relied on after a receiver or router callback, including market indexes and spoke/pool parameters when those caches are used for final acceptance. Alternatively, make the price aggregator expose a monotonically increasing configuration/version token and require the post-callback version to equal the version observed during prefetch.

### Proof of Concept
1. Governance has a ready `ConfigureAssetOracle` operation for collateral token `C`. The old feed values `C` at `P_old`; the replacement values it at `P_new`, where `P_new < P_old` and the replacement is a valid configured oracle.
2. The attacker calls:

```text
flash_position(
  caller = attacker,
  account_id = 0,
  spoke_id = S,
  mode = Multiply,
  debt = { hub_id = H, asset = D },
  amount = debt_amount,
  receiver = attacker_receiver,
  data = encoded_ready_governance_operation,
  collaterals = [({ hub_id = HC, asset = C }, min_c)],
  refund_assets = []
)
```

3. The controller loads the new account and caches `D` and `C` prices before the callback. [9](#0-8) 
4. `mint_and_forward` creates the debt and transfers the measured `debt_amount` receipt to `attacker_receiver`. [10](#0-9) 
5. Inside `execute_flash_position`, the receiver invokes:

```text
governance.execute(
  executor = None,
  target = price_aggregator,
  function = "set_oracle",
  args = ready_operation_args,
  predecessor = zero_bytes,
  salt = ready_operation_salt
)
```

6. The receiver swaps the borrowed `D` for `C` and transfers at least `min_c` of `C` to the controller.
7. The controller measures the received collateral, deposits it, and runs `strategy_finalize` using `P_old`, although the aggregator now resolves `C` at `P_new`. [2](#0-1) [6](#0-5) 
8. Choose values such that:

```text
C_received * P_old >= debt_amount * D_price / max_ltv
C_received * P_new <  debt_amount * D_price
```

The transaction persists a solvent-looking account under the stale price. A subsequent valuation or liquidation uses the new oracle and exposes the position as undercollateralized, leaving the pool with the resulting loss.
