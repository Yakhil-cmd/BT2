## Confirmed Root Cause

`Shipit::WebhooksController#verify_signature` selects **which GitHub App's webhook secret to validate against** based on `repository_owner`, which is read directly from the attacker-supplied payload:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`Shipit.github(organization:)` looks up per-organization config in a multi-org deployment (`Shipit::Engine`/`lib/shipit.rb` `github_app_config`), and `verify_webhook_signature` **unconditionally returns true if that org's `webhook_secret` is blank**:

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [2](#0-1) 

Meanwhile, every webhook handler (`Handler#stacks`) resolves the **target repository/stack to act on** from a *different* field of the same payload — `repository.full_name` — not `repository.owner.login`:

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

This creates exactly the "organization that authenticated versus the repository that is written" binding break: the signature check is scoped to `repository.owner.login`, but the actual mutation (e.g. `PushHandler#process` triggering `stack.sync_github`) is scoped to `repository.full_name`, and nothing enforces that these two fields refer to the same organization.

### Title
Webhook signature verification is scoped to an attacker-chosen organization (`repository.owner.login`) that is decoupled from the target repository actually acted upon (`repository.full_name`) — (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
In multi-GitHub-App deployments (`Shipit.github_organizations`, documented in `docs/setup.md` "Using Multiple Github Applications"), `WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate the HMAC signature against using the attacker-controlled `repository.owner.login` field of the JSON payload. If **any** configured organization has no `webhook_secret` set (the documented/example default is `webhook_secret: # nil`), `GitHubApp#verify_webhook_signature` returns `true` unconditionally for that organization, regardless of the actual `X-Hub-Signature` header. An attacker can therefore submit an unsigned/arbitrary-signature webhook whose top-level `repository.owner.login` names the unsecured organization, while `repository.full_name` (the field every `Webhooks::Handlers::Handler` subclass — `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, `MembershipHandler`, PR handlers — actually uses to resolve the target `Stack`/`Repository` via `Repository.from_github_repo_name`) names a repository belonging to a *different, properly secured* organization.

### Finding Description
`repository_owner` is derived purely from request body content the attacker fully controls:
`params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. This value picks the `GitHubApp` instance (and hence the `webhook_secret`) used for signature verification via `Shipit.github(organization: repository_owner)`. Handlers, however, never consult `repository_owner`; they resolve state-changing targets from `payload.dig('repository', 'full_name')`. There is no code path that verifies `repository.owner.login` matches the owner segment of `repository.full_name`. The security boundary (signature verification) and the effective authorization boundary (which stack gets mutated) are bound to two independently attacker-writable fields of the same unauthenticated JSON body.

### Impact Explanation
Where the operator has configured more than one GitHub organization (a documented, supported configuration) and at least one of those organizations does not set a `webhook_secret` — which is the shown default/example in `config/secrets.development.example.yml` and `docs/setup.md` — an unauthenticated attacker can forge webhook events (e.g. `push`) that pass signature verification while targeting a *different* organization's real, secured stacks. This lets an outsider trigger `stack.sync_github` (`PushHandler`), fabricate commit statuses (`StatusHandler`) that gate deploy eligibility, or manipulate check-run/membership state for repositories they do not control — an unauthorized action taken against a repository whose organization's credentials were never actually verified. This satisfies the "unauthorized deploy" / cross-repository-write class of impact, mirroring the reported bug class where a check is bound to a value ("owner.login"/lock MAXTIME-start) different from the value actually consumed downstream ("full_name"/lock end-start).

### Likelihood Explanation
Requires the operator to run Shipit against multiple GitHub organizations with at least one unsecured `webhook_secret` — a configuration explicitly documented and shown with blank secrets in the shipped examples, making it plausible in real deployments that adopted multi-org support without setting a secret on every entry (e.g. treating one org as "internal"/trusted). No credentials, session, or prior access are needed by the attacker; only knowledge of the target's `full_name` and the name of the unsecured org, both discoverable.

### Recommendation
Verify that the organization used to select the signing secret is the same organization actually addressed by `repository.full_name` (and `organization.login` for org-scoped events) before dispatching to handlers, and reject the request if they diverge. Alternatively, remove the "return true when secret is blank" bypass in `GitHubApp#verify_webhook_signature` and require every configured organization to have a non-blank `webhook_secret`, or derive the app/secret used for verification from the same authoritative field the handlers use for target resolution (`repository.full_name`'s owner segment), not from a separate, independently-controllable field.

### Proof of Concept
Not independently executed against a live app (no filesystem/terminal access in this session); the exploit is derivable directly from the cited code:
1. Configure two orgs, `SecureOrg` (real target, `webhook_secret: real-secret`) and `OpenOrg` (`webhook_secret:` blank) — a supported configuration per `docs/setup.md`.
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "OpenOrg" }, "full_name": "SecureOrg/target-repo" }
}
```
with any/garbage `X-Hub-Signature`.
3. `repository_owner` resolves to `"OpenOrg"`; `Shipit.github(organization: "OpenOrg").verify_webhook_signature` returns `true` unconditionally because `OpenOrg`'s `webhook_secret` is blank — the before_action passes.
4. `PushHandler.call(params)` runs, resolving `Repository.from_github_repo_name("secureorg/target-repo")` from `repository.full_name`, and invokes `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on `SecureOrg`'s real stack — an unauthorized action against a repository whose signature was never actually validated.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
