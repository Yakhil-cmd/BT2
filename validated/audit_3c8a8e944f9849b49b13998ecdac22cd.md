Based on the investigation, I found a concrete analog to the reported bug class in `headers_commission.js`'s stable-unit headers-commission redistribution logic (the sqlite path, used when `conf.storage !== 'mysql'`).

### Title
Headers commission is permanently lost when a parent unit's only reachable children all become `final-bad` (branch-dependent fund loss) - (File: `headers_commission.js`)

### Summary
`calcHeadersCommissions()` redistributes the `headers_commission` that each stable parent unit pays to whichever one of its (grand)child units "wins" the commission. If none of a parent's candidate children survive as `sequence='good'`, the code silently drops that parent's commission instead of recording any contribution or carrying it forward, permanently stranding the corresponding bytes.

### Finding Description
For every stable parent unit (`punits`), the algorithm collects candidate children on the same or next MC index and picks a single winner via `getWinnerInfo()`, which then receives the parent's `headers_commission` recorded in `headers_commission_contributions`, and later aggregated into `headers_commission_outputs` (the only table from which headers-commission inputs can ever be spent, see `mc_outputs.calcEarnings` usage in `validation.js` around L2582-L2599).

In the JS-side implementation used for sqlite storage, when a parent's candidate children are filtered down to those with `sequence === 'good'`: [1](#0-0) 
if `arrCandidateChildren.length === 0` (all same/next-MCI children of that parent ended up `final-bad`, e.g. due to a fork the parent unit was on the losing side of, or the winning branch simply not authoring any children), the function returns without adding an entry to `assocChildrenInfos` for that `payer_unit` at all: [2](#0-1) 

Because that payer is never added to `assocChildrenInfos`, it never enters `assocWonAmounts`, so no row is ever inserted into `headers_commission_contributions` for it, and consequently the subsequent aggregation step: [3](#0-2) 
never produces a `headers_commission_outputs` row for that parent's MCI/commission amount. Since `headers_commission_outputs` is the only source from which `headers_commission` inputs can be constructed and spent (enforced in `validation.js` via `mc_outputs.calcEarnings`/`getMaxSpendableMciForLastBallMci`): [4](#0-3) 
the bytes that were already earmarked as that parent unit's `headers_commission` (deducted from the unit's total value when it was validated/posted) become permanently unspendable — nobody can ever claim them. This mirrors the reported bug class exactly: a "distribution period" (here, one parent unit's commission) for which the recipient set is momentarily empty (here, `_totalSupply`-equivalent being zero children) is simply skipped, and the accrued value for that period is dropped from the accounting entirely instead of being carried over or refunded, so it is locked forever.

This differs from ordinary/expected fee burning because the commission is a fixed, already-known amount tied 1:1 to a specific unit — the loss is a bookkeeping omission (silently `return`ing on an empty array) rather than an intentional protocol rule, and it is fully reachable by any ordinary unit poster who ends up on a momentarily divergent branch (which happens routinely under normal DAG forking/finality resolution, not just malicious behavior).

### Impact Explanation
Every affected parent unit's `headers_commission` (which scales with the unit's header size, i.e. non-trivial value for busy senders/hubs) is permanently removed from the spendable byte supply with no path to recovery — effectively burning user funds without any output ever being created for them. Over time and across many units that get orphaned onto losing branches, this compounds into a nontrivial and unpredictable loss of user-owned commission funds, which is a fund-loss issue affecting ordinary, unprivileged unit posters. It also creates an accounting mismatch: the value was already deducted from the byte-tracking (declared as `headers_commission` on the unit) but no corresponding spendable output is ever generated to offset it.

### Likelihood Explanation
This can occur any time a legitimately posted unit acts as a headers-commission payer for a child that subsequently becomes non-serial/`final-bad` (a routine consequence of normal parallel unit authoring and DAG stabilization, not an attack), with no other same/next-MCI child unit remaining `good`. This is not an edge case requiring privileged access — every regular network user who occasionally posts units on a competing/losing sub-branch can trigger it, so likelihood is realistically medium-to-high over the life of the network, even though no single occurrence is attacker-controlled with certainty.

### Recommendation
When `arrCandidateChildren.length === 0` for a payer unit, do not silently skip it. Instead, either (a) carry the commission forward to be considered together with the next MC index's candidate pool so it is not orphaned, or (b) explicitly redirect it to a well-defined fallback recipient (e.g., the payer's own author, mirroring the "single author, no eligible child" fallback path already used elsewhere in this file), ensuring every stable parent unit's `headers_commission` always results in exactly one `headers_commission_contributions`/`headers_commission_outputs` entry.

### Proof of Concept
1. Author unit `P` (parent) that authors two children `C1` and `C2` on the same or next MC index (e.g., via a temporary DAG fork/race between two nodes/wallets), where `C1` is on the eventually-adopted branch and `C2` is discarded.
2. Suppose `C1` itself later becomes `final-bad` for an unrelated reason (e.g., it is later proven to conflict/double-spend and is marked non-serial), and `C2` was never actually posted as `good` either (or was itself pruned as `final-bad`), so that by the time `calcHeadersCommissions()` runs, `storage.assocStableUnitsByMci[parent.main_chain_index].filter(...)` and `...[parent.main_chain_index+1].filter(...)` both yield zero `good` children for `P`.
3. `calcHeadersCommissions()` reaches `arrCandidateChildren.length === 0` and does `return;` for `P`, per `headers_commission.js` L107-108.
4. No row is ever written for `P` into `headers_commission_contributions`, hence none into `headers_commission_outputs`.
5. `P`'s `headers_commission` amount (visible in the `units` table as `P.headers_commission`) can never be referenced by any future `headers_commission` input in `validation.js`, because `mc_outputs.calcEarnings`/`getMaxSpendableMciForLastBallMci` only ever look at `headers_commission_outputs`, which contains no entry for `P`'s MCI/amount — the funds are permanently stuck.
