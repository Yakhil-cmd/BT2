### Title
Malicious route pool can consume the caller’s authorization and drain unrelated wallet tokens - ([File: contracts/swap-aggregator/src/venues/mod.rs])

### Summary
A route-selected pool is invoked while the caller’s top-level authorization is active, and production code does not constrain the pool address to a trusted venue. A malicious pool can therefore request an unrelated `token.transfer(victim, attacker, amount)` during a signed `swap_collateral`, `swap_debt`, `multiply`, `repay_debt_with_collateral`, or direct `execute_strategy` transaction; simulation records it as an authorization child, and signing the simulated tree makes the theft authorized.

### Finding Description
`swap_collateral` accepts caller-controlled route bytes and passes them into the strategy path after only caller/account authorization and market checks. [1](#0-0) [2](#0-1) 

The controller authorizes only the exact router input transfer, but then calls `execute_strategy` with the attacker-supplied route. [3](#0-2) 

The router reads pool and token addresses from the caller-controlled `assets` registry, decodes the venue opcode, and dispatches the hop without a pool allowlist. [4](#0-3) [5](#0-4) [6](#0-5) 

For example, a Soroswap hop invokes `get_reserves` and `swap` on `hop.pool`, so the selected contract receives arbitrary execution inside the signed call stack. [7](#0-6) [8](#0-7) 

The measured input/output checks only protect the router’s balances of the declared hop tokens; they do not prevent the malicious pool from invoking another token contract against the victim. [9](#0-8) 

### Impact Explanation
A victim who signs the poisoned simulated authorization tree loses unrelated wallet tokens, not merely the routed collateral. The malicious pool can request any token transfer on behalf of the victim and route the proceeds to the attacker while still returning enough declared output token for the route checks to succeed. [10](#0-9) 

This is theft of user funds. The bounded checks for router overspend and positive output do not cover a third token pulled directly from the victim by code below the authorized call. [11](#0-10) 

### Likelihood Explanation
The attack requires the victim to submit and sign a malicious route, so it is not fully unilateral. However, routes are opaque XDR supplied by external quote or trading software, and the poisonous authorization appears as an additional child under an otherwise valid transaction rather than as an explicit allowance or obvious wallet-drain operation. [12](#0-11) 

An unprivileged attacker can deploy the pool, provide enough output liquidity to satisfy `min_out`, and distribute the route through a compromised or deceptive quoting path. This supports a Medium severity finding rather than High because victim signature and simulation of the malicious authorization tree remain required. [9](#0-8) 

### Recommendation
Do not allow route payloads to name arbitrary pool contracts. Store an operator-approved pool registry keyed by venue and token pair, or otherwise verify `hop.pool` against a trusted registry before dispatching it. [5](#0-4) 

Until contract-level venue allowlisting exists, clients must simulate every route, decode the complete authorization tree, and reject any child invocation other than the exact expected input-token transfer. A route containing a `transfer` from the caller to any unrelated recipient must not be signed. [13](#0-12) 

### Proof of Concept
1. Victim owns supplied USDC collateral and also holds an unrelated `VICTIM_TOKEN` in their wallet.
2. Attacker deploys `RoguePool`, storing `(victim, VICTIM_TOKEN, attacker, amount)`.
3. Attacker builds a `StrategyPayload` whose Soroswap hop sets:
   - `idx_a = RoguePool`
   - `idx_b = USDC`
   - `idx_c = ETH`
   - `min_out` equal to an amount of ETH the attacker is willing to return.
4. Victim calls `swap_collateral(caller=victim, account_id, current=USDC_key, amount, new=ETH_key, swap=payload)`.
5. The controller authorizes only `USDC.transfer(controller, router, amount)` and invokes `execute_strategy`. [14](#0-13) 
6. The router dispatches to `RoguePool` because `idx_a` is payload-controlled. [15](#0-14) 
7. `RoguePool.get_reserves` returns reserves that make the Soroswap adapter request a positive output; `RoguePool.swap` then executes `VICTIM_TOKEN.transfer(victim, attacker, amount)` and sends ETH to the router. [7](#0-6) [16](#0-15) 
8. Simulation records the unrelated transfer beneath the victim’s `swap_collateral` authorization. If the victim signs that tree, enforcement accepts it.
9. Router settlement still succeeds because its USDC input was consumed and its ETH balance increased, while `VICTIM_TOKEN` moved directly from the victim to the attacker. [9](#0-8)

    if total_in <= 0 {
        panic_with_error!(&env, Error::InvalidAmount);
    }

    let StrategyPayload {
        amounts,
        assets,
        ops,
    } = payload;
    let program = Program::decode(&env, &ops, assets.len(), amounts.len());

    let input_token = assets.get_unchecked(program.token_in);
    let output_token = assets.get_unchecked(program.token_out);
