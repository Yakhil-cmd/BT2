### Title
Webhook signature verification is bound to `repository.owner.login`, not to the `repository.full_name` that handlers act on, allowing cross-org webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App/org config used to validate the `X-Hub-Signature` HMAC by reading `repository.owner.login` (or `organization.login`) out of the *unverified* JSON body. Every webhook handler (`PushHandler`, `PullRequest::OpenedHandler`, `PullRequest::ReopenedHandler`, etc.) instead resolves the target `Repository`/`Stack` using a *different* field of the same unverified body: `repository.full_name`. These two fields are never cross-checked against each other.

### Finding Description
`verify_signature` computes `repository_owner` and fetches per-organization config with it: [1](#0-0) [2](#0-1) 

```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization:)` looks up per-org secrets (`webhook_secret`, `oauth`, etc.) — this is the multi-tenant config path documented in `test/dummy/config/secrets_double_github_app.yml` and `docs/setup.md`, where each org has its own `webhook_secret`.

Meanwhile, the base `Handler` class and concrete handlers resolve the actual `Repository`/`Stack` acted upon using a *separate* field from the same payload: [3](#0-2) 

```
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

and `PushHandler#process` uses this to sync a `Stack`: [4](#0-3) 

`Repository.from_github_repo_name` splits `full_name` on `/` and looks up by `owner`/`name` columns independently of anything checked during signature verification: [5](#0-4) 

**The broken binding (equality that should hold but doesn't):**
`repository.owner.login` (used to select the HMAC key / verifying org) == `owner` prefix of `repository.full_name` (used to select the `Repository`/`Stack` written to).

Because Rails' `JSON.parse` simply materializes whatever object the attacker sends, nothing prevents `repository.owner.login` from being `"attacker-org"` while `repository.full_name` is `"victim-org/victim-repo"`. `verify_signature` will fetch and check the HMAC against `attacker-org`'s `webhook_secret` (which the attacker legitimately possesses if they administer that org's GitHub App installation in a multi-org Shipit deployment, as documented for the `secrets_double_github_app.yml` pattern), while every downstream handler will act on `victim-org/victim-repo`.

### Impact Explanation
This breaks the "organization that authenticated" vs "repository that is written" trust binding explicitly called out as in-scope. An attacker who legitimately controls (or knows the webhook secret for) one org configured in a multi-org Shipit instance can forge `push`, `pull_request`, `status`, `check_suite`, etc. events that are processed as if they originated from a completely different, unrelated repository/org. Concretely:
- `PushHandler` triggers `stack.sync_github(expected_head_sha:)` → `GithubSyncJob`, letting an attacker manufacture spoofed sync activity for a victim stack they don't control, feeding attacker-chosen `after` SHAs into commit-append logic.
- `PullRequest::OpenedHandler`/`ReopenedHandler`/etc. can create or unarchive review stacks for the victim repository using attacker-supplied PR metadata.
- Because `Repository.from_github_repo_name` matches purely on string content of `full_name`, no additional authorization check ties the verified org back to the acted-upon repository anywhere in this path.

This satisfies the High-severity bar ("escalation into cross-repository writes"/state changes) since it lets a party authenticated only for org A drive webhook-triggered state changes (deploy pipeline sync, review-stack lifecycle) for org B's tracked stacks.

### Likelihood Explanation
Requires the attacker to control (or know the webhook secret of) at least one organization configured in Shipit's multi-org GitHub App setup — plausible in any self-service/multi-tenant Shipit deployment where different orgs' admins each configure their own `webhook_secret` (as shown by `secrets_double_github_app.yml`). Once that precondition holds, forging the cross-referenced payload is trivial (just crafting JSON with mismatched `repository.owner.login` and `repository.full_name`), and no other check in `WebhooksController` or `Handler` reconciles the two fields.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler`), derive the organization used both for signature verification and for repository resolution from a single, mutually-validated source — e.g., require `repository.full_name.split('/').first.casecmp(repository_owner) == 0` before processing, or resolve organization strictly from `repository.full_name` and drop the separate `repository.owner.login`/`organization.login` lookup used only for verification.

### Proof of Concept
1. Shipit is configured with two GitHub Apps/orgs, `attacker-org` (attacker knows its `webhook_secret`, e.g. because they administer that org's app) and `victim-org` (tracked stack `victim-org/victim-repo` exists in Shipit).
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and validates the HMAC using `attacker-org`'s `webhook_secret`, which the attacker computed correctly and sends as `X-Hub-Signature`. Verification passes.
4. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")`, finds the victim stack, and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")`, causing Shipit to process a forged sync/deploy-pipeline event for a repository the attacker never controlled or was authenticated for.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
