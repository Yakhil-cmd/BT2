## Title
Cross-Organization Forgery of Commit CI Status via Webhook Signature/Commit-Lookup Mismatch, Enabling Unauthorized Merge Queue Auto-Merge - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates an incoming GitHub `status` webhook against the GitHub App/organization derived from the payload's own `repository.owner.login` field, but `StatusHandler#process` then writes a commit status by looking up `Commit.where(sha: params.sha)` **globally, with no scoping to that organization or repository at all**. Any attacker who legitimately controls a Shipit-configured GitHub App/org (and therefore knows that org's `webhook_secret`) can forge a `status` event whose `sha` field matches a commit belonging to a *different* organization's repository, and Shipit will happily write a fabricated CI status onto that unrelated commit — potentially triggering the merge queue to auto-merge a pull request in a repository the attacker has no access to.

### Finding Description
Shipit supports multiple GitHub organizations/GitHub Apps in one deployment, each with its own `webhook_secret`, as shown in the multi-org secrets fixture [1](#0-0) .

The webhook signature check derives the signing organization purely from the untrusted JSON payload: [2](#0-1) [3](#0-2) 

This establishes the intended binding: `signature valid ⇒ organization == repository_owner`. However, the equality that actually matters for a write — `organization authenticated == organization owning the record being mutated` — is never enforced, because most handlers extend `Handler`, which scopes writes to `Repository.from_github_repo_name(payload.dig('repository','full_name'))` [4](#0-3) , but `StatusHandler` bypasses this entirely: [5](#0-4) 

`Commit.where(sha: params.sha)` is a database-wide lookup with no `stack_id`/`repository_id`/organization filter. Git SHAs are effectively unique per-commit-content but are *public knowledge* (visible on any GitHub commit/PR page, and Shipit itself publicly displays commit shas on stack pages), so an attacker does not need privileged access to the victim's repository to learn the target `sha` — they only need to know it, and to control any org whose webhook secret Shipit trusts.

The written status then feeds directly into merge automation: [6](#0-5) [7](#0-6) 

`add_status` calls `stack.schedule_merges` whenever the new status is `pending` or `success`, which processes the merge queue and, if all required checks pass, calls `MergeRequest#merge!`, which uses Shipit's own `GITHUB_TOKEN`-equivalent credentials to merge the pull request on the real GitHub repository: [8](#0-7) .

### Impact Explanation
This breaks the binding "an organization that authenticated versus the repository that is written." A forged `success` (or otherwise favorable) status injected for a victim commit can satisfy `StatusChecker`/merge-queue requirements and cause Shipit to merge a pull request in a repository entirely unrelated to the attacker's authenticated organization — an unauthorized merge using the app's own GitHub credentials. This matches the Critical impact category (unauthorized merge) defined in scope.

### Likelihood Explanation
Exploitation requires only: (1) the attacker administers/knows the webhook secret of any single GitHub App/organization configured in the same Shipit instance (a normal, unprivileged-relative-to-other-tenants credential they legitimately hold for their own org), and (2) knowledge of the target commit's SHA, which is publicly discoverable via GitHub for any commit/PR. No Shipit session, `ApiClient` token, or victim-org credentials are needed, making this practically reachable in any multi-tenant Shipit deployment.

### Recommendation
Scope `StatusHandler#process` (and any other handler performing writes) to the organization/repository that authenticated the webhook, not just the raw `sha`. E.g., require and use `payload.dig('repository', 'full_name')` to resolve the specific `Repository`/`Stack` and constrain `Commit.where(sha:, stack: stack)` (or verify the resolved repository's owner matches the organization used in `verify_signature`) before applying the status update.

### Proof of Concept
1. Deploy Shipit configured with two orgs, `attacker-org` and `victim-org`, each with distinct GitHub Apps/`webhook_secret`s (as supported by `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker, who administers `attacker-org`, knows its `webhook_secret`.
3. Attacker looks up the public SHA of a pending commit/PR on `victim-org/some-repo` (e.g. from the GitHub PR page).
4. Attacker crafts a `status` event body:
   ```json
   {
     "sha": "<victim commit sha>",
     "state": "success",
     "context": "ci/required-check",
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/decoy-repo" }
   }
   ```
5. Attacker signs it with `attacker-org`'s `webhook_secret` (`X-Hub-Signature: sha1=...`) and POSTs to `/webhooks` with `X-Github-Event: status`.
6. `verify_signature` resolves `repository_owner` = `attacker-org`, verifies successfully against `attacker-org`'s secret.
7. `StatusHandler#process` runs `Commit.where(sha: "<victim commit sha>")`, finds the victim's commit (belonging to `victim-org`), and creates a `success` status on it, potentially triggering `stack.schedule_merges` and an unauthorized merge of the victim's pull request.

module Shipit
  module Webhooks

      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String

          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
    end
