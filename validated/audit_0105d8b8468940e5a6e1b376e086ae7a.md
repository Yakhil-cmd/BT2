### Title
Asset attestation checks use the definer's current attestor list instead of the list valid when the attestation was posted, allowing spender-attested asset restrictions to be bypassed - (File: storage.js)

### Summary
`storage.readAsset()` / `storage.filterAttestedAddresses()` determine whether an address is allowed to hold/spend a `spender_attested` asset by intersecting the `attestations` table with `objAsset.arrAttestorAddresses`, which is only the **latest** attestor list for the asset as of `last_ball_mci`. The query does not verify that the `attestor_address` who posted a given `attestation` unit was actually a member of the attestor list **at the mci the attestation itself was created**. This is the same root-cause pattern as the referenced Blackhole finding: a per-entity classification ("is this address currently an authorized attestor?") that can change over time is evaluated using its *current* value and then retroactively applied to a *historical* record (the attestation unit), instead of checking the classification as it stood when that historical record was produced.

### Finding Description
`readAsset()` in `storage.js` resolves the attestor list for an asset as follows: [1](#0-0) 

`objAsset.arrAttestorAddresses` is populated with only the most recently published `asset_attestors` list at or before `last_ball_mci` — it says nothing about who was an attestor at any *earlier* mci.

This list is then used, unconditionally, to filter historical attestation records: [2](#0-1) 

The `attestations` table stores every `attestation` message ever posted by any address for any other address, with no built-in restriction that the attesting address must currently (or ever) be a recognized attestor for the asset — attestation is a generic message app, and it is validated independently of any asset's attestor list at the time it is created (validated generically in `validation.js`/`writer.js`, not tied to `asset_attestors`). The binding between "attestor_address" and "is a legitimate attestor for asset X" is established only later, at spend/payment-validation time, in `filterAttestedAddresses`, using whatever the attestor list happens to be **at the last_ball_mci of the unit currently being validated** — not the attestor list that existed when the attestation unit itself was created.

Consequently: an address `C` can post an `attestation` for user `X` at some early mci (mci=10), at a time when `C` is *not yet* on the asset's attestor list (or has already been removed from it). If the asset definer later (mci=50) adds `C` to the attestor list via an `asset_attestors` message, then any subsequent payment validated with `last_ball_mci >= 50` will compute `arrAttestorAddresses` including `C`, and `filterAttestedAddresses` will find `X`'s old attestation from `C` and treat `X` as attested — even though `C` had no attestor authority at the moment the attestation was actually issued.

This mirrors the smNFT report exactly: `locked[tId].isSMNFT` (current classification) gates whether a historical vote-power record counts; here, "is `attestor_address` currently on the attestor list" gates whether a historical `attestation` record counts, instead of "was `attestor_address` on the attestor list when the attestation was made."

### Impact Explanation
`spender_attested` is a hard security gate used in `validatePayment()` to restrict who may hold, issue, or spend a regulated/whitelisted asset: [3](#0-2) 

If the attestor-membership check can be satisfied retroactively by an attestation created before the attester had authority, an attacker can pre-position a self-serving or colluding "attestation" for a target address at a time when the attesting address is not yet an attestor, then later get that same address added to the attestor list (e.g., a compromised or later-recruited attestor). The target address becomes unconditionally treated as "attested" for the asset from that point on, bypassing the intended KYC/whitelisting control. This directly threatens asset issuers relying on `spender_attested`/`issued_by_definer_only`-style controls (e.g. compliance-gated tokens) — a Medium/High severity issue affecting asset transfer/issuance conditions, matching the category "asset issuance and transfer conditions."

### Likelihood Explanation
The steps are all achievable by unprivileged, ordinary posters: anyone can post an `attestation` message app at any time for any address (this requires no special permission and is not tied to being an already-recognized attestor). The asset definer routinely updates attestor lists over the asset's lifetime via `asset_attestors` messages — this is a normal, expected operation, not an attack in itself. The only requirement for exploitation is that an address which posted an attestation earlier is later added to (or was earlier removed from and functionally still recognized because of) the attestor list — a scenario plausible in any long-lived asset with attestor rotation. No malicious node/hub/peer behavior is required; this is purely a unit/validation-logic issue reachable from ordinary AA/asset usage.

### Recommendation
When validating whether an address is "attested" for a `spender_attested` asset, `filterAttestedAddresses`/`readAsset` should verify that the specific `attestation` unit's `attestor_address` was part of the attestor list that was in effect **at the mci of that attestation unit itself** (i.e., join against the `asset_attestors` list that was active at the attestation's own `main_chain_index`, not the list active at the payment's `last_ball_mci`). Concretely, for each candidate attestation row, look up the attestor list valid as of that attestation's `main_chain_index` (analogous to how `readDefinitionByAddress`/`readDefinitionAtMci` correctly resolve historical definitions by mci) and require `attestor_address` be a member of that historical list, not merely the current/latest one.

### Proof of Concept
1. Asset `Z` is created with `spender_attested=true` and an empty/initial attestor list.
2. At mci=10, address `C` (not yet an attestor) posts `["attestation", {address: X, attestor_address: C, ...}]` claiming `X` is compliant. This message is accepted by generic message validation since `attestation` posting has no dependency on the asset's attestor list.
3. At mci=50, the asset definer posts an `asset_attestors` update adding `C` to `Z`'s attestor list (a routine, legitimate operation, e.g. onboarding a new attestor).
4. At mci=100, `X` attempts to receive/spend asset `Z` in a payment. `validatePayment()` calls `storage.loadAssetWithListOfAttestedAuthors(conn, 'Z', 100, [X], ...)`, which calls `readAsset()` → `arrAttestorAddresses` = latest list at or before mci 100 = `[C, ...]`.
5. `filterAttestedAddresses` finds `X`'s attestation from `C` (posted at mci=10, `main_chain_index<=100`) and returns `X` as attested.
6. The payment validation in `validation.js` (lines 2115-2122) passes the `arrAttestedAddresses.indexOf(owner_address)` check, allowing `X` to spend/hold `Z`, even though `C` had zero attestor authority at the time it actually vouched for `X`.
