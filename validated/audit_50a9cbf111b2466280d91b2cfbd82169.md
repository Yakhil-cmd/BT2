### Title
Hookify rule enforcement is bound to transient process CWD instead of the approved repo root, allowing silent rule-set swap on directory drift - ([File: plugins/hookify/core/config_loader.py])

### Summary
`load_rules()` resolves the rule-file glob with a bare relative path (`os.path.join('.claude', 'hookify.*.local.md')`), so the set of enforced hookify rules is determined entirely by the hook subprocess's current working directory at invocation time, not by any fixed, user-approved project root. Because every hookify hook (`pretooluse.py`, `posttooluse.py`, `stop.py`, `userpromptsubmit.py`) calls `load_rules()` this way without ever consulting `input_data['cwd']` against a pinned session root or `CLAUDE_PROJECT_DIR`, a CWD change mid-session (e.g., a Bash `cd` into a nested checkout, submodule, or symlinked directory) causes subsequent tool calls to be evaluated against a different repository's `.claude/hookify.*.local.md` rule set than the one the user configured/approved.

### Finding Description
`load_rules()` builds its glob pattern purely relative to `os.getcwd()`: [1](#0-0) 

All four hook entry points invoke it the same way, with no attempt to bind the lookup to a fixed project root: [2](#0-1) 

Claude Code's own hook input schema documents that `cwd` is passed explicitly in the hook JSON payload precisely because a session's working directory is not static — the harness clearly anticipates hooks may need to reason about which directory they are operating in: [3](#0-2) 

Other plugins in this same codebase demonstrate the correct pattern of anchoring project-scoped config loading to an explicit `cwd`/`CLAUDE_PROJECT_DIR` value rather than the bare process CWD: [4](#0-3) 

Hookify's own command documentation reinforces that rule placement — and therefore rule scope — is defined purely by "the current working directory," with no mention of anchoring to the directory Claude Code was originally launched from once that directory has changed: [5](#0-4) 

Exploit flow: a user sets up `block`/`warn` hookify rules at their project root (e.g., blocking `rm -rf`, or blocking edits to `.env`/credential files). Ordinary repository content (a README, code comment, issue text, or a nested git submodule/symlinked directory reachable without any special privilege) leads the agent to run a Bash `cd` into a nested or sibling directory before performing a sensitive operation — this is a completely normal automation flow, not a privilege escalation. Because Claude Code's Bash tool persists shell state across calls in a session, the working directory stays changed for later tool calls. When the next PreToolUse/PostToolUse hook fires, `load_rules()` globs `.claude/hookify.*.local.md` relative to the new CWD:
- If the nested directory has no `.claude/` rules, the user's root-level block rules silently stop being enforced for all subsequent tool calls (bypass).
- If the nested directory contains its own `.claude/hookify.*.local.md` files (attacker-plantable via a submodule, vendored copy, or symlink checked into the repo), those attacker-controlled rules are loaded and enforced instead of the user-approved ones (policy substitution).

No code in `config_loader.py`, `pretooluse.py`, `posttooluse.py`, `stop.py`, or `userpromptsubmit.py` re-anchors the glob to `input_data['cwd']` captured at session start, `CLAUDE_PROJECT_DIR`, or any other session-bound repo identifier, so nothing stops this drift.

### Impact Explanation
Scoped impact: wrong-repo rule enforcement/bypass — a user's approved `block` rules (e.g., preventing destructive `rm -rf`, preventing edits to secret files) can be silently disabled or replaced once the agent's working directory drifts away from the original project root, which is a trust-boundary bypass of the security policy the user explicitly configured via `/hookify`. This maps to the "approval bypass / trust-boundary bypass" bounty category since a block-action rule is the closest hookify has to an approval gate, and its target binding is not fixed to the user-approved repository.

### Likelihood Explanation
Preconditions: a multi-root or nested-checkout workspace (submodule, vendored copy, symlinked directory, or simply a subdirectory the agent is led to `cd` into) plus at least one Bash `cd` during the session — both of which are ordinary, unprivileged, repo-content-reachable events (e.g., following instructions in a README or task description). No admin rights, leaked keys, or social engineering of the user are required beyond normal task-following/prompt-injection via committed content. This is straightforward to reproduce deterministically since `load_rules()`'s behavior is a direct, unconditional function of `os.getcwd()`.

### Recommendation
Bind hookify's rule discovery to a fixed project root rather than the transient process CWD: capture `input_data['cwd']` (or `CLAUDE_PROJECT_DIR`) once at session start (e.g., via `SessionStart`) and pass/persist that root through to every hook invocation, then resolve `.claude/hookify.*.local.md` against that pinned root, ignoring any subsequent `cd` drift. At minimum, `load_rules()` should accept an explicit base directory argument instead of always defaulting to `os.getcwd()`, and the hook entry points should pass the session's original approved root.

### Proof of Concept
Integration test plan:
1. Create two temp directories, `repoA/.claude/hookify.block-rm.local.md` (action: block, event: bash, pattern: `rm\s+-rf`) and `repoB/.claude/` with no rules (or with a permissive rule of its own).
2. Simulate a session: invoke `pretooluse.py` (or call `load_rules()`/`RuleEngine` directly) with `os.chdir('repoA')` and a `tool_input` containing `rm -rf /tmp/x`; assert the result contains `"permissionDecision": "deny"` (block enforced).
3. Simulate CWD drift: `os.chdir('repoB')` (representing a prior Bash `cd` into a nested/symlinked directory), then invoke the hook again with the same `rm -rf /tmp/x` command whose `tool_input.file_path`/target still conceptually belongs to `repoA`.
4. Assert failure: the hook returns `{}` (no block) even though the operation targets the originally-approved repo, proving the enforced rule set followed the transient CWD rather than the session's approved target repository.
5. Repeat in reverse (start in `repoB`, drift to `repoA`) to show rule-set swap in both directions, confirming the invariant "filesystem target binding must stay fixed to user-approved repo" is violated.
