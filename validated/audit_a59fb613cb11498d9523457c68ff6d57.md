### Title
CCMenu API endpoint bypasses ApiClient stack scoping, allowing a single-stack token to read any stack's deploy status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
This is a structural analog of the Sherlock M-31 finding: a security-relevant scope/authorization check that exists at the "trust boundary" is silently skipped by one code path, allowing a credential that is only supposed to authorize a narrow context (one TSS/one stack) to be replayed/used against a broader context (any nonce/any stack).

### Finding Description
`Shipit::Api::BaseController` binds an `ApiClient` token to a specific `Stack` when the client record has a `stack_id`. All stack lookups are supposed to go through the scoped `stacks` relation: [1](#0-0) 

`stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` when the client is scoped, and only falls back to `Stack.all` for unscoped clients. `require_permission :read, :stack` (used across API controllers) only checks the generic `permissions` array on `ApiClient` — it never checks which stack is being touched: [2](#0-1) 

`Api::StacksController` correctly reuses the scoped helper (`stacks.from_param!`): [3](#0-2) 

However, `Api::CCMenuController` overrides `stack` with an unscoped lookup that bypasses the `current_api_client.stack_id` binding entirely: [4](#0-3) 

This is exactly the pattern in the report: the authorization primitive (`stack_id` on the `ApiClient`, analogous to the TSS nonce) is created and intended to gate every access, but one write/read path (`update_tss` not resetting nonce ≈ `CCMenuController#stack` not applying the scope) forgets to enforce it, so a credential legitimately minted for context A (stack A / TSS A) is silently accepted for context B (stack B / TSS B).

Any authenticated Shipit user can self-service mint a stack-scoped, `read:stack`-only `ApiClient` for a stack they have access to, via the CCMenu URL feature: [5](#0-4) 

That token is intentionally restricted to one stack (`current_api_client.stack_id`), but because `CCMenuController#stack` ignores this binding, the same Basic-Auth token can be replayed against `GET /api/stacks/:stack_id/ccmenu.xml` for any other `stack_id` in the system, returning that other stack's latest deploy/rollback state (id, timestamps, success/running status).

### Impact Explanation
This breaks the binding "a stack a token authorizes ⟺ a stack it touches." A token minted (and displayed to the user) as scoped to Stack A can be used, unmodified, to read deploy/task status of Stack B, C, … — i.e., unauthorized cross-stack read of task/deploy state. This matches the High-severity bucket defined by the rules ("unauthenticated read of stack state, task streams or deploy output" via an authorization boundary that should have limited the token to one stack but didn't).

### Likelihood Explanation
Any regular, non-privileged Shipit user with read access to at least one stack can generate this token through the normal UI (`CCMenuUrlController#fetch`), with no admin/privileged role or GitHub write access needed. Exploiting it only requires guessing/enumerating another stack's numeric or slug identifier and replaying the same Basic-Auth header against a different `stack_id` in the URL — no additional credentials, TLS interception, or social engineering required.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the scoped `stacks` helper from `BaseController` (i.e., `stacks.from_param!(params[:stack_id])`) instead of the unscoped `Stack.from_param!(params[:stack_id])`, so the `current_api_client.stack_id` binding is enforced consistently with every other API controller.

### Proof of Concept
1. As a normal logged-in user with access to Stack A, visit Stack A and use the "CCMenu URL" feature; this creates a `read:stack`-scoped `ApiClient` bound to Stack A (`stack_id` set) and returns its `authentication_token`. [6](#0-5) 
2. Send `GET /api/stacks/<Stack-B-id>/ccmenu.xml` using Basic Auth with that same token, where Stack B is a stack the user/token was never scoped to.
3. Because `CCMenuController#stack` calls `Stack.from_param!` directly rather than the scoped `stacks` relation, the request succeeds and returns Stack B's latest deploy/rollback status, even though the token's `stack_id` only authorizes Stack A. [7](#0-6)

require 'uri'

module Shipit
  class CCMenuUrlController < ShipitController
    def fetch
      uri = URI(api_stack_ccmenu_url(stack_id: stack.to_param))
      uri.query = { 'token' => client.authentication_token }.to_query
      render(json: { ccmenu_url: uri.to_s })
    end

    private

    def client
      @client ||= ApiClient.create_with(permissions: %w[read:stack])
                           .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
    end

    def stack
      @stack ||= Stack.from_param!(params[:stack_id])
    end
  end
