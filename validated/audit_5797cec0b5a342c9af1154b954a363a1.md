### Title
Webhook signature is verified against the org derived from `repository.owner.login`, but handlers act on the unrelated `repository.full_name` / `organization.login` fields, letting a valid signer for one configured GitHub org mutate/impersonate state for a different org's repos and teams - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
In multi-org Shipit deployments (`config/secrets.*.yml` with per-org `github:` keys), `WebhooksController#verify_signature` selects which org's `webhook_secret` to verify the HMAC signature against using only `repository.owner.login` (or `organization.login`) from the payload. The rest of the payload — including `repository.full_name` (used by every `Handler` to resolve the target `Stack`) and, for the `membership` event, `organization.login`/`team`/`member` (used to add/remove `Team` membership) — is never bound to that same org by the signature check. Anyone who legitimately knows one configured org's `webhook_secret` (i.e., has admin access to that org's GitHub App/webhook settings, not a Shipit account) can forge a payload whose `repository.owner.login` matches "their" org (to pass `verify_signature`) while `repository.full_name`/`organization.login` point at a completely different org tracked by this Shipit instance.

### Finding Description
`verify_signature` computes the authorizing org purely from the top-level `repository.owner.login`/`organization.login` field: [1](#0-0) [2](#0-1) 

The signature itself is verified only against that org's `webhook_secret`: [3](#0-2) 

But `Handler#stacks`/`#repository_name`, used by every event handler (push, status, check_suite, pull_request, etc.) to decide *which* `Stack`/`Repository` gets mutated, reads `repository.full_name` — a field the signature check never inspected or cross-checked against the org it authenticated: [4](#0-3) 

For example `PushHandler` triggers `stack.sync_github` for whatever stack matches that `full_name`: [5](#0-4) 

Even more impactful, `MembershipHandler` trusts `params.organization.login` and `params.member.login`/`params.team` directly to create/find a `Team` and add or remove members from it — again with no tie to the org whose secret validated the request: [6](#0-5) 

Team membership is exactly the authorization gate for the whole application (`User#authorized?` checks membership in `Shipit.github_teams`): [7](#0-6) 

`Shipit.github(organization:)` confirms that multi-org configs are a supported, documented mode (each org has its own `webhook_secret`, `oauth`, and `teams`): [8](#0-7) 

**The broken binding, stated as an equality that fails to hold:**
`org authenticated by verify_signature (repository.owner.login used to pick webhook_secret)` ≠ `org/repository actually written by the handler (repository.full_name / organization.login used for Stack lookup and Team mutation)`.

Concretely: attacker knows `OrgA`'s `webhook_secret` (legitimate holder of that secret for OrgA's own GitHub App/webhook config, not a Shipit user). They POST a payload where `repository.owner.login = "OrgA"` (so `Shipit.github(organization: "OrgA")` is selected and the HMAC computed with OrgA's secret validates), but `repository.full_name = "OrgB/victim-repo"` and, for the `membership` event, `organization.login = "OrgB"`. The signature check passes because it only ever looked at OrgA's secret and OrgA's login field; the handler layer then acts on OrgB's stack/team using attacker-supplied `member.login`/`action`.

### Impact Explanation
This crosses the "escalation into `Shipit.github_teams` authorization" bar explicitly called out as High severity: via the `membership` webhook, an attacker who controls a valid `webhook_secret` for *any one* configured org can add an arbitrary GitHub login (including their own) to a `Team` object belonging to a *different* org's authorization team, satisfying `User#authorized?` and gaining access to that other org's stacks/deploys inside Shipit. It can also be used to force `stack.sync_github`, forged CI `status`, or `check_suite` results on a victim org's stacks via `PushHandler`/`StatusHandler`/`CheckSuiteHandler`, influencing deploy/merge decisions for repositories the attacker does not control — an unauthorized-deploy-adjacent impact.

### Likelihood Explanation
Requires a Shipit deployment configured with the multi-org `github:` schema (documented, supported feature) and requires the attacker to already legitimately hold the `webhook_secret` for at least one of the configured orgs (e.g., they administer that org's GitHub App). This is a lower bar than compromising a Shipit `ApiClient` token, a GitHub App private key, or the full app itself, and is exactly the class of "authenticated as X but acts as Y" trust-binding break the report targets — the org used to select the verifying secret and the org/repo the mutation applies to are two independent, uncorrelated payload fields.

### Recommendation
After `verify_signature` selects the org from `repository.owner.login`/`organization.login`, re-validate that the same value equals the org portion of `repository.full_name` (and, for `membership`, that `organization.login` matches the authenticated org) before dispatching to handlers, rejecting the request with `422` on mismatch.

### Proof of Concept
1. Configure Shipit with two orgs, `OrgA` and `OrgB`, each with distinct `webhook_secret`s (as in `config/secrets.development.shopify.yml`).
2. As someone who administers `OrgA`'s GitHub App/webhook (knows `OrgA`'s `webhook_secret`), craft a `membership` event payload:
```json
{
  "action": "added",
  "team": {"id": 1, "name": "Deployers", "slug": "deployers", "url": "https://example.com"},
  "organization": {"login": "OrgB"},
  "member": {"login": "attacker-github-login"},
  "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgA/whatever"}
}
```
3. Compute `X-Hub-Signature` as `sha1=` + HMAC-SHA1 of the raw body using `OrgA`'s `webhook_secret`.
4. POST to `/github/webhooks` with `X-Github-Event: membership`. `verify_signature` resolves `repository_owner` → `"OrgA"`, verifies successfully against `OrgA`'s secret [1](#0-0) .
5. `MembershipHandler#process` then creates/finds `OrgB`'s team and adds `attacker-github-login` as a member [6](#0-5) , granting the attacker `authorized?` status for `OrgB`'s stacks if that team is in `Shipit.github_teams` [7](#0-6) , despite never possessing `OrgB`'s webhook secret or any `OrgB` credential.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
