### Title
RAY-scaled interest accrual overflows before the borrow-index cap, permanently freezing a market - (File: common/src/rates/simulate.rs)

### Summary
An unprivileged borrower can create a sufficiently large debt position, let interest accrue, and then make `accrue_step` panic when converting scaled debt to its RAY value; because every market mutation accrues first, the market can no longer be repaid, withdrawn from, or liquidated without a code change. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`Controller::update_indexes` is permissionless except for caller authorization and forwards the selected markets to `pool_update_indexes_call`. [4](#0-3) [5](#0-4)  The pool processes each selected market through `global_sync`, which calls `accrue_step` for every elapsed chunk before committing state. [6](#0-5) [7](#0-6) 

`accrue_step` computes `borrowed_original` and `supplied_original` through `scaled_to_original`, then computes the next index and accrued rewards. [1](#0-0)  `scaled_to_original` performs `scaled.mul(index)`, which evaluates `scaled * index / RAY` and panics with `MathOverflow` when the result exceeds `i128`. [8](#0-7) [9](#0-8) [10](#0-9) 

The borrow-index ceiling does not prevent this value overflow because `update_borrow_index` multiplies `old_index * interest_factor` before applying `MAX_BORROW_INDEX_RAY`, and the preceding debt-value multiplication can overflow even earlier. [11](#0-10) [12](#0-11) 

The repository’s regression test demonstrates the reachable state: after creating a very large high-utilization market, repeated accrual eventually returns `MathOverflow`, while the stored index remains below `MAX_BORROW_INDEX_RAY`; subsequent withdraw and repay calls fail with the same error. [13](#0-12) 

### Impact Explanation
Once `borrowed * borrow_index` exceeds the representable `i128` range, every future accrual panics before `last_timestamp` advances or the cache commits, so the same condition is evaluated again on every retry. [14](#0-13) [15](#0-14) 

Ordinary supply, borrow, withdraw, and repay legs all load the market through `load_leg`, which calls `synced_market` and therefore runs the overflowing accrual before processing the requested operation. [16](#0-15)  The regression test confirms that this is not merely a failing view or transaction-local denial of service: withdrawals, repayments, and liquidations remain unavailable after the overflow state is reached. [3](#0-2) 

The result is permanent freezing of all user funds in the affected market absent a contract upgrade, matching the report’s malformed-state-to-persistent-DoS bug class rather than a single rejected transaction. [2](#0-1) [17](#0-16) 

### Likelihood Explanation
The attack path uses only public controller operations: `supply` to fund the debt market and collateral, `borrow` to create high utilization, and `update_indexes` to trigger accrual. [18](#0-17) [4](#0-3) 

The caller needs enough listed collateral to pass the controller’s ordinary solvency checks and enough tokens to create a market whose scaled debt times its future index exceeds `i128::MAX`. [19](#0-18) [8](#0-7)  The checked-in test constructs that exact state and verifies the permanent failure mode, so feasibility is demonstrated rather than hypothetical. [13](#0-12) 

### Recommendation
Make accrual value-cap-aware instead of merely index-cap-aware: calculate the largest borrow index that keeps `borrowed * index` representable, clamp `new_borrow_index` to the lesser of that value bound and `MAX_BORROW_INDEX_RAY`, and derive rewards from the clamped index. [11](#0-10) [20](#0-19) 

The same bound must be applied to supplied value before `scaled_to_original`, and the overflow check should happen before `update_borrow_index` performs its uncapped multiplication. [12](#0-11)  A saturating or widened-integer value calculation is preferable to panicking, and the regression should assert that repay, withdraw, liquidation, and `update_indexes` continue to function at the clamp. [21](#0-20) [17](#0-16) 

### Proof of Concept
1. On a listed market configured to accept the position, one caller invokes `supply(caller, 0, spoke_id, [(debt_asset, debt_market_liquidity), (collateral_asset, required_collateral)])` and receives `account_id`. [22](#0-21) [23](#0-22) 
2. The caller invokes `borrow(caller, account_id, [(debt_asset, borrowed_amount)], Some(caller))`, creating sustained high utilization after passing the normal post-borrow solvency gate. [24](#0-23) [25](#0-24) 
3. After enough ledger time has elapsed for `borrowed * borrow_index` to exceed `i128::MAX`, anyone calls `update_indexes(caller, [debt_asset])`; `scaled_to_original` panics with `MathOverflow`. [5](#0-4) [26](#0-25) [10](#0-9) 
4. Calls such as `repay(caller, account_id, [(debt_asset, 1)])` and `withdraw(caller, account_id, [(debt_asset, 1)], None)` continue to panic because both paths accrue the market before mutating it. [27](#0-26) [28](#0-27) [16](#0-15)

/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();

/// Computes `floor(x * y / d)`, saturating to `i128::MAX` (or `i128::MIN` for a negative
/// quotient) instead of panicking if the result does not fit in `i128`. Panics with
/// `GenericError::DivisionByZero` if `d == 0`.
pub fn mul_div_floor_saturating(env: &Env, x: i128, y: i128, d: i128) -> i128 {
    require_nonzero_divisor(env, d);
    if let Some(quotient) = x
        .checked_mul(y)
        .and_then(|product| div_floor_i128(product, d))
    {
        return quotient;
    }
    let (x256, y256, d256) = to_i256_operands(env, x, y, d);
    div_floor_i256(
        env,
        &x256.mul(&y256),
        &d256,
        quotient_is_nonnegative(x, y, d),
    )
    .to_i128()
    .unwrap_or(if quotient_is_negative(x, y, d) {
        i128::MIN
    } else {
        i128::MAX
    })

/// Third parties may only add to existing supply positions. Returns the account id.

    spoke_id: u32,

    let aggregated = payments::aggregate_positive_payments(env, assets);
    let mut cache = Context::new(env);

        env,
        caller,
        account_id,
        spoke_id,
        PositionMode::Normal,
        account::AccountGuard::Supply,
        &mut cache,

    require_third_party_existing_supply(env, account_id, acct_id, caller, &account, &aggregated);

    process_deposit(env, caller, &mut account, &aggregated, &mut cache);

        env,
        acct_id,
        &account,
        &mut cache,
        PositionSides::Supply,
        false,
    );
    acct_id
}
