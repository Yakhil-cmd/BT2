I have sufficient evidence to render a verdict. Confirming the key facts: `ReviewStack#env` merges attacker-controlled uppercased label names as keys with a fixed value `"true"`, with no allowlist, into an env hash that flows unfiltered through `TaskCommands#env` and `Command#unbundled_env` into `PTY.spawn`, while the only allowlist mechanism in the codebase (`EnvironmentVariables#permit`) is applied solely to the *user-submitted HTTP `env` param* (in `TasksController#task_params`, `DeploysController#deploy_params`, `RollbacksController#rollback_params`), never to `stack.env`/`ReviewStack#env`.### Title
Unallowlisted `BASH_ENV`-shaped env-key injection via PR label name reaches `PTY.spawn` in `Command#start` - (File: app/models/shipit/review_stack.rb, lib/shipit/task_commands.rb, lib/shipit/command.rb)

### Summary
`ReviewStack#env` merges `pull_request.labels.each_with_object({}) { |n,h| h[n.upcase]='true' }` into the stack's environment hash with **no key allowlist**, and this hash flows through `TaskCommands#env` (`.merge(@stack.env)`), `Commands#env`, and `Command#unbundled_env` (`BASE_ENV.merge(...).merge(@env.stringify_keys)`) straight into `PTY.spawn(unbundled_env, *interpolated_arguments, ...)` in `Command#start`. `LabelCapturingHandler#capture_labels` persists label names verbatim from the webhook payload (`pull_request.update!(labels: params.pull_request.labels.map(&:name))`), so any string an actor can get into a PR's label list becomes an env-var **key** on the deploy host, unlike the one place in the codebase that does allowlist env keys (`EnvironmentVariables#permit`, used only for the HTTP `env` params in `TasksController`, `DeploysController`, `RollbacksController`).

### Finding Description
The claimed invariant — "the set of keys in the environment hash passed to `PTY.spawn` is restricted to the deploy spec's `machine_env` and declared `VariableDefinition` names" — is **false** for review-stack tasks.

Trace:
- `LabelCapturingHandler#capture_labels` (`app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb:98-102`) writes `params.pull_request.labels.map(&:name)` directly to `PullRequest#labels`, subject only to the `ExplicitParameters` schema requiring `String` (`params do ... requires :labels, Array do requires :name, String end end`), with no character/allowlist restriction.
- `ReviewStack#env` (`app/models/shipit/review_stack.rb:84-93`) does `super.merge(pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" })` — any label name becomes an env key, unconditionally, value fixed to `"true"`.
- `TaskCommands#env` (`lib/shipit/task_commands.rb:33-48`) does `super.merge(@stack.env).merge(...).merge(deploy_spec.machine_env).merge(@task.env)` — `@stack.env` (including the label-derived keys) is merged with no call to `EnvironmentVariables#permit`/`filter_deploy_envs`.
- `Command#unbundled_env` (`lib/shipit/command.rb:103-105`): `BASE_ENV.merge('PATH' => ...).merge(@env.stringify_keys)` — `@env` (the merged task env) overrides `BASE_ENV` with **no key restriction**.
- `Command#start` (`lib/shipit/command.rb:85-101`): `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` — this is the exact environment handed to the spawned process for `install_dependencies` (`bundle install ...`) and other `shipit.yml` steps.

By contrast, `EnvironmentVariables#permit` (`lib/shipit/environment_variables.rb:13-18,35-44`) is the only allowlist mechanism in the codebase, and it is invoked exclusively on the user-supplied HTTP `env` param in `TasksController#task_params`, `DeploysController#deploy_params`, and `RollbacksController#rollback_params` — never on `Stack#env`/`ReviewStack#env`. Existing guards (`verify_signature`, `ExplicitParameters` schema, `force_github_authentication`, `require_permission!`) validate *authenticity of the webhook* and *authorization to trigger tasks via HTTP*, but do nothing to constrain *which keys* a PR label can inject into the deploy-time environment — they are orthogonal to this divergence.

Exploit flow: an attacker opens/labels a PR against a repository with review stacks enabled (`Repository#review_stacks_enabled`, `provisioning_behavior_allow_all?` or label-gated), naming a label `BASH_ENV` (webhook `pull_request.labeled`/`opened` triggers `LabelCapturingHandler`/`OpenedHandler`/`LabeledHandler`). The label becomes `stack.env['BASH_ENV'] = "true"`. Because the attacker also controls the checked-out branch content (the task's working directory used as `chdir` for `install_dependencies`/`steps`), they can commit a file literally named `true` containing shell commands. If the review stack's dependency/deploy step is executed by a shell that honors `BASH_ENV` for non-interactive execution (e.g., scripts with a `#!/bin/bash` shebang, or hosts where `/bin/sh` is bash), that file is sourced before the intended command runs, achieving code execution in the context of the Shipit deploy process/host.

### Impact Explanation
This is an arbitrary environment-*key* injection into every subprocess Shipit spawns for a review-stack's tasks (`install_dependencies`, `perform`, `fetch`, git operations sharing `@stack.env`) — critically, it is not restricted to “safe” value overriding: an attacker fully controls the key name and (loosely) the value context via cwd file placement, letting them target loader/behavior variables (`BASH_ENV`, `RUBYOPT`, `BUNDLE_GEMFILE`, etc.) that influence Ruby/Bash/Bundler startup behavior in ways declared `VariableDefinition`s and `machine_env` were never meant to expose. Realized exploitation (e.g., via `BASH_ENV`) depends on host shell configuration (whether the invoked interpreter is bash and processes `BASH_ENV` in the given invocation mode), so the concrete RCE proof is environment-dependent — but the underlying flaw (unbounded env-key injection reaching `PTY.spawn`) is unconditional and directly falsifies the stated invariant. This affects only the repository/stack whose PR the attacker controls (not cross-tenant by default), but within that stack/host process it is a credible path to code execution on the deploy host, matching the Critical RCE class if the host's shell honors the injected loader variable.

### Likelihood Explanation
Preconditions: the target repository must have review stacks enabled (`review_stacks_enabled` + `provisioning_behavior_allow_all?`, or an `allow_with_label`/`prevent_with_label` behavior the attacker can also satisfy by labeling their own PR, per `OpenedHandler#provision?`/`LabeledHandler#archive?`/`unarchive?`). The attacker must be able to open a PR and apply a label to it — note that on real GitHub, adding labels to a PR normally requires "triage"/"write" permission on the repo, which an arbitrary fork contributor typically does not have; this is a real-world mitigating factor not modeled by the code itself, but it is presupposed as an attacker capability in this question's threat model. Given that capability, the attack is cheap and repeatable (one webhook + one label + one file commit per attempt) and requires no secrets, tokens, or privileged roles.

### Recommendation
Restrict `ReviewStack#env`'s label-derived keys to a repository-configured allowlist (mirroring `EnvironmentVariables#permit`/`VariableDefinition`), or drop the label→env-var mechanism entirely in favor of an explicit, admin-controlled mapping. At minimum, run every value produced by `ReviewStack#env` (and any other `Stack#env` override) through `EnvironmentVariables#permit` against the stack's declared `deploy_variables`/`machine_env` keys before merging into `TaskCommands#env`, so `Command#unbundled_env`/`PTY.spawn` can never receive attacker-chosen key names.

```ruby
require "test_helper"

module Shipit
  class ReviewStackEnvInjectionTest < ActiveSupport::TestCase
    test "PR label name becomes an unallowlisted env KEY reaching Command#unbundled_env" do
      stack = shipit_stacks(:review_stack)
      stack.pull_request.labels = ["BASH_ENV"]

      task = shipit_tasks(:shipit_restart)
      task.stack = stack

      env = Shipit::TaskCommands.new(task).env
      assert_equal "true", env["BASH_ENV"], "attacker-controlled label name injected as env KEY"

      command = Shipit::Command.new("bundle install", env:, chdir: task.working_directory)

        "no allowlist: injected key survives into the exact hash passed to PTY.spawn"
    end

    test "EnvironmentVariables#permit is never applied to ReviewStack#env, unlike controller-submitted env" do
      stack = shipit_stacks(:review_stack)
      stack.pull_request.labels = ["BASH_ENV"]

      # Controller-submitted env IS filtered:
      assert_raises(Shipit::EnvironmentVariables::NotPermitted) do
        Shipit::EnvironmentVariables.with("BASH_ENV" => "true").permit(stack.deploy_variables)

      # But ReviewStack#env bypasses this entirely:
      assert_equal "true", stack.env["BASH_ENV"]
    end
  end
end
```

```ruby
    def permit(variable_definitions)
      return {} unless @env

    def interpolate(argument)
      return argument unless @env

      argument.gsub(/(\$\w+)/) do |variable|
        variable.sub!('$', '')
        Shellwords.escape(@env.fetch(variable) { ENV[variable] })
      end
    end

    private

    def initialize(env)
      @env = env
    end

    def sanitize_env_vars(variable_definitions)
      allowed_variables = variable_definitions.map(&:name)

      allowed, disallowed = @env.partition { |k, _| allowed_variables.include?(k) }.map(&:to_h)

      error_message = "Variables #{disallowed.keys.to_sentence} have not been whitelisted"
      raise NotPermitted, error_message unless disallowed.empty?

      allowed
    end
```
