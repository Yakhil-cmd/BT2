### Title
Unbounded `fsck --connectivity-only` cost in `sanityCheckRepo` can exceed `--sync-timeout` under `--git-gc=off`, causing permanent sync stall - (File: main.go)

### Summary
`repoSync.sanityCheckRepo` unconditionally runs `git fsck --no-progress --connectivity-only` against the full object graph on every repo validation pass (called from `initRepo`, and reachable each sync cycle). [1](#0-0)  Because this cost scales with the total number of reachable objects/refs and is never bounded by a sub-timeout, an attacker who can push a large or adversarially-shaped object graph (e.g., many refs, deep history, or pathological merge topologies) can inflate this single git invocation's runtime. Under `--git-gc=off`, git's own periodic packing/pruning that would otherwise keep the object store compact is disabled by the operator, so the ever-growing raw object count directly translates into ever-growing `fsck` cost with no automatic mitigation.

### Finding Description
`sanityCheckRepo` is called from `initRepo`, which itself is invoked as part of the repo-preparation step at the start of a sync cycle. [2](#0-1)  The check runs `dirIsEmpty`, `rev-parse --show-toplevel`, then `fsck --no-progress --connectivity-only`, and finally a lock-file check. [3](#0-2)  The `fsck --connectivity-only` invocation walks every reachable object from every ref to verify graph connectivity; its cost is proportional to the size/shape of the object graph, not to the size of the current fetch delta.

An attacker who has push access to the source repository (an explicitly allowed capability in this threat model) can grow the object graph over time (new refs/branches/tags, large trees, deep commit chains, or high ref counts) without ever triggering compaction, because `--git-gc=off` is a supported, documented flag that disables git's own gc-based upkeep. Each sync cycle, the fsck check therefore does strictly increasing work. If that work exceeds the time budget available under `--sync-timeout`, the repo-preparation step (and thus the whole sync) fails repeatedly, and `initRepo` never succeeds — meaning the synced content is never refreshed (or, worse, the wiped/reinitialized path at `main.go:1381-1386` can be triggered repeatedly if the check fails after wipe, thrashing the volume).

I was not able to fully trace the exact body of `repoSync.cleanup()` (worktree pruning, `reflog expire`, and `gc` invocation ordering relative to `sanityCheckRepo`, and how `--sync-timeout` is applied as a context deadline around these calls) before exhausting available tool calls, so the precise interaction between `cleanup()`'s sub-steps and the timeout wrapper is not independently confirmed here. The core mechanism — `fsck --connectivity-only` cost being unbounded and directly attacker-influenced via pushed refs/objects, combined with `--git-gc=off` removing the mitigating compaction — is confirmed directly in `sanityCheckRepo`.

### Impact Explanation
If the sanity/fsck check reliably exceeds the configured `--sync-timeout`, `git-sync` can enter a persistent failure loop where it can never validate the repo as usable, so it never advances the published worktree. This matches the "permanent denial of updates" impact class: consumers of the synced volume stop receiving updates indefinitely, even though the attacker never gains code execution, secret access, or write access outside `--root`.

### Likelihood Explanation
This requires two things to co-occur: (1) the operator has set the non-default `--git-gc=off` flag (a documented, supported setting), and (2) an attacker with push access deliberately grows the object graph large/complex enough to make `fsck --connectivity-only` expensive relative to the configured `--sync-timeout`. Growing an object graph via ordinary pushes is straightforward and repeatable; whether a *specific* commit/ref shape can make `fsck --connectivity-only` disproportionately (e.g., super-linearly) expensive versus simply "large" is a property of git's own fsck implementation, not something I could confirm from this repo's code alone. This is a plausible but not fully proven exploit primitive without a `--git-gc=off` operator choice plus sufficient repository growth over time.

### Recommendation
- Run `sanityCheckRepo`'s `fsck` under an explicit sub-timeout/context, independent from (and smaller than) `--sync-timeout`, so a slow fsck fails fast and clearly rather than silently consuming the whole sync budget.
- Consider bounding or making optional the connectivity check (e.g., skip/throttle fsck when the object count exceeds a configurable threshold, or run it asynchronously outside the sync-timeout critical path).
- Emit metrics/logging for fsck duration so operators running with `--git-gc=off` can detect growing check costs before they cause full sync failures.

### Proof of Concept
Not independently reproduced here. A validation approach would be: stand up a local git server, disable gc (`--git-gc=off`), script repeated pushes that grow the ref/object count substantially each cycle, and run `git-sync` with a fixed `--sync-timeout`; assert that `sanityCheckRepo`'s `fsck` step duration trends upward across cycles and eventually causes sync failures logged as timeout/context-deadline errors, while `--root` file/byte counts continue to grow unbounded. This was not executed as part of this analysis; confirming the precise growth-to-cost relationship of `git fsck --connectivity-only` and the exact `cleanup()`/timeout wiring would require further code reading (`repoSync.cleanup`, the sync loop's context/timeout setup) that could not be completed within the available tool-call budget.

// sanityCheckRepo tries to make sure that the repo dir is a valid git repository.
func (git *repoSync) sanityCheckRepo(ctx context.Context) bool {
	git.log.V(3).Info("sanity-checking git repo", "repo", git.root)
	// If it is empty, we are done.
	if empty, err := dirIsEmpty(git.root); err != nil {
		git.log.Error(err, "can't list repo directory", "path", git.root)
		return false
	} else if empty {
		git.log.V(3).Info("repo directory is empty", "path", git.root)
		return false
	}

	// Check that this is actually the root of the repo.
	if root, _, err := git.Run(ctx, git.root, "rev-parse", "--show-toplevel"); err != nil {
		git.log.Error(err, "can't get repo toplevel", "path", git.root)
		return false
	} else {
		root = strings.TrimSpace(root)
		if root != git.root.String() {
			git.log.Error(nil, "repo directory is under another repo", "path", git.root, "parent", root)
			return false
		}
	}

	// Consistency-check the repo.  Don't use --verbose because it can be
	// REALLY verbose.
	if _, _, err := git.Run(ctx, git.root, "fsck", "--no-progress", "--connectivity-only"); err != nil {
		git.log.Error(err, "repo fsck failed", "path", git.root)
		return false
	}

	// Check if the repository contains an unreleased lock file. This can happen if
	// a previous git invocation crashed.
	if lockFile, err := hasGitLockFile(git.root); err != nil {
		git.log.Error(err, "error calling stat on file", "path", lockFile)
		return false
	} else if len(lockFile) > 0 {
		git.log.Error(nil, "repo contains lock file", "path", lockFile)
		return false
	}

	return true
}
