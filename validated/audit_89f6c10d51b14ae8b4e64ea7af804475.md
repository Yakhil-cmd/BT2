### Title
Webhook signature verified against `repository.owner.login`, but the payload acted on is selected by `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
This is only relevant for multi-tenant Shipit deployments that configure per-organization GitHub Apps (`Shipit.github(organization:)`). In that mode, `WebhooksController#verify_signature` picks the HMAC secret to validate the request using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')`, while every webhook `Handler` resolves the actual repository/stack to mutate using a completely different field, `payload.dig('repository', 'full_name')`. Because the HMAC only proves "this payload's bytes were signed by whichever org's secret matched `repository.owner.login`," and never proves the mapping between that owner and `repository.full_name`, an attacker controlling a GitHub organization with its own Shipit App installation (and thus its own valid `webhook_secret`) can sign a payload where `owner.login` is their own org but `full_name` is set to `victim-org/victim-repo`.

### Finding Description
`verify_signature` derives the signer identity solely from `owner.login`: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up the App config (and its `webhook_secret`) purely by that organization string: [3](#0-2) 

Once the HMAC check passes, `WebhooksController#create` dispatches the entire raw JSON to handlers: [4](#0-3) 

But every `Handler` (e.g. `PushHandler`) resolves the target `Repository`/`Stack` from `repository.full_name`, not from the `owner.login` field that was authenticated: [5](#0-4) [6](#0-5) 

This is exactly the "organization authenticated versus the repository that is written" binding: the signature proves authorization for `owner.login`, but the code that actually runs (`stack.sync_github`, commit status creation, membership team/user creation, `RefreshCheckRunsJob`, etc.) acts on whatever `repository.full_name` says, with no check that `full_name`'s owner segment equals the authenticated `owner.login`.

### Impact Explanation
An attacker who owns/administers any GitHub organization that has installed a Shipit GitHub App for this instance (a normal, unprivileged, self-service action for legitimate multi-tenant Shipit users — they know their own org's `webhook_secret`) can forge a signed webhook whose `repository.full_name` points at a stack belonging to a different organization/repository. Depending on the event type this lets the attacker cause the target stack to run `sync_github` (fetch/ingest attacker-chosen commit SHAs, `Handlers::PushHandler`), inject fabricated commit statuses (`StatusHandler` → `Commit#create_status_from_github!`) affecting merge/deploy gating on the victim stack, or mutate check-suite state (`RefreshCheckRunsJob`) for a repository the attacker does not own — all without ever needing write access to the victim repository or a valid Shipit session/API token. This crosses the "cross-repository writes" bar for a High/Critical-adjacent finding under the stated rules.

### Likelihood Explanation
Requires the deployment to be running with the multi-org GitHub App configuration (`github_default_organization` non-nil, i.e. `secrets.github` keyed by multiple organization names) rather than the legacy single-app mode; in single-app mode there is only one secret and this analog collapses. Given that support, exploitation only requires the attacker to control any one onboarded organization (their own), craft one JSON payload, and sign it with their own legitimate secret — no privileged access to Shipit itself.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler#repository_name`), require that the owner segment of `repository.full_name` (and/or `organization.login` for org-scoped events) matches the `repository_owner`/organization whose secret validated the signature, and reject the webhook (422) on mismatch before dispatching to any handler.

### Proof of Concept
1. Deploy Shipit configured for multiple GitHub orgs, e.g. `secrets.github: { attacker-org: {webhook_secret: S1, ...}, victim-org: {webhook_secret: S2, ...} }` — this is the documented multi-tenant setup in `config/secrets.development.shopify.yml`.
2. Attacker, who legitimately controls `attacker-org` and knows `S1` (they installed/administer the App), builds a `push` event payload:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen sha>",
     "repository": { "full_name": "victim-org/victim-repo", "owner": { "login": "attacker-org" } }
   }
   ```
3. Compute `X-Hub-Signature: sha1=HMAC(S1, raw_body)` using their own org's secret.
4. POST to `/webhooks` with `X-Github-Event: push`. `verify_signature` calls `Shipit.github(organization: 'attacker-org')` (from `repository.owner.login`) and the HMAC validates successfully.
5. `WebhooksController#create` dispatches to `Handlers::PushHandler`, which resolves the target via `payload.dig('repository', 'full_name')` = `"victim-org/victim-repo"`, causing `victim-org/victim-repo`'s stacks to run `sync_github(expected_head_sha: "<attacker-chosen sha>")` — a cross-organization/cross-repository effect the attacker was never authorized to trigger.
