### Title
Integer-overflow bypass of the `count`/array-length check in `verifyBlobKzgProofBatch` allows out-of-bounds reads - (File: bindings/java/ckzg_jni.c)

### Summary
`Java_ethereum_ckzg4844_CKZG4844JNI_verifyBlobKzgProofBatch` validates array sizes with `blobs_size != count_native * BYTES_PER_BLOB`, but this multiplication is computed modulo 2^64 in `size_t`, so a `count_native` far larger than the real element count can still satisfy the check while the huge value is passed straight into `verify_blob_kzg_proof_batch`, causing it to read/allocate far beyond the actual JVM-backed buffers.

### Finding Description
The equality the code relies on is `blobs_size (== real byte-array length, bounded to a 32-bit `jsize`) == count_native * BYTES_PER_BLOB (mod 2^64)`. Since `BYTES_PER_BLOB = 2^17`, the product mod 2^64 only depends on the low 47 bits of `count_native`; any bits at position 47 and above vanish from the check but remain part of the actual `count_native` value passed to `verify_blob_kzg_proof_batch`.

Concretely: allocate a `blobs` byte array with exactly one blob's worth of data (131072 bytes = `BYTES_PER_BLOB`). Pass `count = 1 + 2^47` (a legal, non-negative `jlong`, well within `Long.MAX_VALUE`). Then:
```
count_native = 1 + 2^47
count_native * BYTES_PER_BLOB mod 2^64 = (1 + 2^47) * 2^17 mod 2^64 = 2^17 + 2^64 mod 2^64 = 2^17 = 131072
```
This equals `blobs_size`, so the check at ckzg_jni.c:436 (and the analogous ones for `commitments_bytes_size`/`proofs_bytes_size` at lines 444/452, which are satisfied the same way if commitments/proofs arrays are similarly sized) passes, even though `count_native` itself is astronomically larger than the real number of elements (1). [1](#0-0) 

`count_native` (the huge value) is then handed unchanged to `verify_blob_kzg_proof_batch(&out, blobs_native, commitments_native, proofs_native, count_native, settings)`. [2](#0-1) 

Inside `verify_blob_kzg_proof_batch`, `n` is documented and trusted as "the actual size of the arrays," with no independent bound-check against the caller's real buffer size — it allocates `n`-sized scratch arrays and then loops `for (size_t i = 0; i < n; i++)` reading `blobs[i]`, `commitments_bytes[i]`, `proofs_bytes[i]` directly from the JNI-obtained pointers, which only actually point to a 131072-byte (single-blob) buffer. [3](#0-2) 

None of the existing guards catch this: `bytes_to_bls_field`/`bytes_to_kzg_commitment` validate per-element byte content but are only invoked as many times as `n` dictates, so they get called on out-of-bounds memory; `deduplicate_commitments` and the `n==0`/`n==1` short-circuits are irrelevant here since `n` (huge) doesn't hit those paths; there is no `assert` guarding `n` against the real buffer length; and the JNI binding's own length checks are exactly what is defeated by the overflow.

### Impact Explanation
This is High severity: a single malicious blob sidecar (a tiny 131072-byte blob plus a crafted 64-bit `count`) reaching this JNI entry point causes `verify_blob_kzg_proof_batch` to read wildly out of bounds of the JVM-pinned byte arrays (and to try to `malloc`/loop over an astronomically large `n`), producing memory corruption or a crash/abort on every node using the Java (Teku/Besu) binding that calls this native method with an attacker-influenced `count`.

### Likelihood Explanation
Exploitability strictly depends on whether the calling Java code (outside this repo, e.g. Teku/Besu) passes `count` as a value independently derived/attacker-influenced rather than always computing it consistently as `blobs.length / BYTES_PER_BLOB` from the same array it hands to the native call. Within this repository the native function itself provides no additional safeguard against the overflow, so the bug is a real defect in `ckzg_jni.c`'s bounds-check logic reachable any time the two inputs (`blobs` array length and `count`) become decoupled at the call site. I could not fully verify from the code available in this repo whether the actual Teku/Besu caller code always derives `count` safely from the same length used to build `blobs`, since that caller code lives outside this repository.

### Recommendation
Replace the multiplication-based size check with an overflow-safe check, e.g. verify `count_native <= (SIZE_MAX / BYTES_PER_BLOB)` before multiplying, or equivalently derive `count_native` directly from `blobs_size / BYTES_PER_BLOB` (with a remainder check) instead of trusting the caller-supplied `count` at all, and apply the analogous fix to the commitments/proofs checks.

### Proof of Concept
1. In `CKZG4844JNITest.java` style, construct `byte[] blobs = new byte[BYTES_PER_BLOB]` (131072 bytes) filled with a valid random blob, and matching single commitment/proof arrays (48 bytes each).
2. Call `CKZG4844JNI.verifyBlobKzgProofBatch(blobs, commitments, proofs, 1L + (1L << 47))`.
3. Assert that the JNI-side check `blobs_size != count_native * BYTES_PER_BLOB` at ckzg_jni.c:436 evaluates false (i.e., the exception is NOT thrown) — this proves the two sides considered equal are not truly equal (`count_native = 1+2^47` vs. real element count `1`).
4. Observe the process crash (SIGSEGV) or, under ASan/valgrind in a native unit test calling `verify_blob_kzg_proof_batch(&ok, blobs_native, commitments_native, proofs_native, (uint64_t)(1 + (1ULL<<47)), &s)` directly with only 1-element-sized buffers, confirming heap-buffer-overflow reads beyond the allocated `Blob`/`Bytes48` arrays.

```c
C_KZG_RET verify_blob_kzg_proof_batch(
    bool *ok,
    const Blob *blobs,
    const Bytes48 *commitments_bytes,
    const Bytes48 *proofs_bytes,
    uint64_t n,
    const KZGSettings *s
) {
    C_KZG_RET ret;
    g1_t *commitments_g1 = NULL;
    g1_t *proofs_g1 = NULL;
    fr_t *evaluation_challenges_fr = NULL;
    fr_t *ys_fr = NULL;
    fr_t *poly = NULL;

    /* Exit early if we are given zero blobs */
    if (n == 0) {
        *ok = true;
        return C_KZG_OK;
    }

    /* For a single blob, just do a regular single verification */
    if (n == 1) {
        return verify_blob_kzg_proof(ok, &blobs[0], &commitments_bytes[0], &proofs_bytes[0], s);
    }

    /* We will need a bunch of arrays to store our objects... */
    ret = new_g1_array(&commitments_g1, n);
    if (ret != C_KZG_OK) goto out;
    ret = new_g1_array(&proofs_g1, n);
    if (ret != C_KZG_OK) goto out;
    ret = new_fr_array(&evaluation_challenges_fr, n);
    if (ret != C_KZG_OK) goto out;
    ret = new_fr_array(&ys_fr, n);
    if (ret != C_KZG_OK) goto out;
    ret = new_fr_array(&poly, FIELD_ELEMENTS_PER_BLOB);
    if (ret != C_KZG_OK) goto out;

    for (size_t i = 0; i < n; i++) {
        /* Convert each commitment to a g1 point */
        ret = bytes_to_kzg_commitment(&commitments_g1[i], &commitments_bytes[i]);
        if (ret != C_KZG_OK) goto out;

        /* Convert each blob from bytes to a poly */
        ret = blob_to_polynomial(poly, &blobs[i]);
        if (ret != C_KZG_OK) goto out;

        compute_challenge(&evaluation_challenges_fr[i], &blobs[i], &commitments_g1[i]);

        ret = evaluate_polynomial_in_evaluation_form(
            &ys_fr[i], poly, &evaluation_challenges_fr[i], s
        );
        if (ret != C_KZG_OK) goto out;

        ret = bytes_to_kzg_proof(&proofs_g1[i], &proofs_bytes[i]);
        if (ret != C_KZG_OK) goto out;
    }
```
