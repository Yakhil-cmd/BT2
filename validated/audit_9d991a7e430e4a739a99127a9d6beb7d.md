### Title
`StatusHandler` writes GitHub commit statuses without repository/stack scoping, allowing a webhook authenticated for one organization to forge CI status for a commit sha belonging to a different repository - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits purely by `Commit.where(sha: params.sha)` with no repository or stack filter, unlike the base `Handler#stacks` helper (`Repository.from_github_repo_name(repository_name)&.stacks`) used by other handlers. [1](#0-0) [2](#0-1) 
Any correctly-signed `status` webhook (signed with the secret configured for the org named in the attacker-controlled `repository.owner.login`/`organization.login` field of the JSON body) can mutate the status of a `Commit` row belonging to **any** stack in the Shipit instance, as long as that commit's `sha` matches. This is a cross-tenant integrity issue for shared-sha scenarios (forks, cherry-picks, shared history), but it is **not** an unauthenticated bypass: the request still has to pass `verify_signature`.

### Finding Description
The invariant the question wants tested is: *"a `status` event only affects the repository/stack whose secret authenticated it."* Tracing `WebhooksController#create` → `verify_signature` → `Shipit::Webhooks.for_event('status')` → `StatusHandler.call(params)`:

- `repository_owner` used to select which `GitHubApp`/secret to verify against is read straight from the JSON body (`params.dig('repository','owner','login') || params.dig('organization','login')`), not from any authenticated GitHub identity. [3](#0-2) 
- `verify_webhook_signature` only understands the legacy `sha1=` HMAC scheme (`X-Hub-Signature`), rejecting anything that isn't `algorithm == 'sha1'`; it never checks the modern `X-Hub-Signature-256` header. However, it still performs a `secure_compare` against `OpenSSL::HMAC.hexdigest('sha1', webhook_secret, message)`. [4](#0-3) 
  This means an attacker **without knowledge of the target org's `webhook_secret`** cannot forge the HMAC just by choosing sha1 over sha256 — HMAC-SHA1 is still keyed and unbroken here. The "legacy algorithm" gap is real (GitHub deprecated `X-Hub-Signature`), but it does not by itself let an unprivileged attacker with no secrets produce a valid signature for an arbitrary organization, **except** in the special case `return true unless webhook_secret` (line 77) — i.e., orgs with no `webhook_secret` configured accept *any* signature, including none.
- Given a correctly-authenticated request (attacker owns a repo/org integrated with Shipit, so they legitimately know their own `webhook_secret`, or the target org has no secret configured), `StatusHandler#process` never re-checks that `params.sha`'s commit belongs to a stack under the authenticating repository. `Commit.where(sha: params.sha).each { |c| c.create_status_from_github!(params) }` iterates over **every** `Commit` row across **every** stack/repository that happens to share that sha. [1](#0-0) 

Because git commit hashes are content-addressed, the same sha can legitimately exist in multiple Shipit-tracked repositories (a fork of the victim repo, a repo that cherry-picked/rebased the same commit, or a shared submodule/mono-history setup). If the attacker's own (secret-known) organization has a stack tracking a repository that happens to contain a commit with the same sha as a commit already ingested into a victim's stack (e ineligible commit lookup is table-wide, not org-scoped), a `status` event signed with the attacker's own secret will flip the status on the victim's `Commit` row too, via `create_status_from_github!` → `add_status`, which can toggle `deployable?`/`blocked?` and trigger `Hook.emit(:deployable_status, ...)`, `stack.schedule_merges`, etc. [5](#0-4) [6](#0-5) 

The `review_stacks_enabled: false` / "provisioning precedence" angle raised in the question is a separate claim about `OpenedHandler#provision?` and `ReviewStackAdapter`, which is repository-scoped via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` and correctly gated by `repository.review_stacks_enabled`. [7](#0-6) 
I found no code path where `review_stacks_enabled: false` still results in provisioning a review stack — `provision?` requires `repository.review_stacks_enabled` for the `allow_all` branch, and the other branches (`allow_with_label`/`prevent_with_label`) are documented, tested behaviors of the provisioning-behavior feature, not evidence of a "precedence bug" that provisions despite `review_stacks_enabled == false`. No test or code confirms such a bug exists; the claim in the question is unsubstantiated by the code I could trace.

### Impact Explanation
The real, demonstrable defect is: `StatusHandler` writes to `Commit`/`Status` rows without verifying the commit belongs to a stack under the repository/org that authenticated the request. This matches the "payload for one repository mutating another's ... commit" impact category, but only under the precondition that a commit sha is shared across repositories/organizations that are both integrated with the same Shipit instance — this is not a purely "any internet user with zero prior relationship" attack; it requires the attacker to control (or know the secret for) at least one org/repo already registered in Shipit, and for a sha collision with the victim's tracked commit to exist (realistically achievable via forks, since forked commits keep identical shas). It does not grant RCE, credential exfiltration, or forged deploy triggers by itself — `create_status_from_github!` only writes `Status`/`ReleaseStatus`-adjacent state and can influence merge-queue scheduling and deploy-gating decisions, not command execution.

### Likelihood Explanation
- Requires the attacker to already be an authenticated party to *some* org/repo integrated with this Shipit instance (i.e., they know a valid `webhook_secret` for at least one tracked org, or that org has none configured).
- Requires a real sha collision between a commit in the attacker's authenticated repo and a commit tracked in the victim's stack — trivially achievable for forks of the same upstream repo (both contain identical commit shas for shared history), which is a realistic and common Shipit configuration (review stacks / PR-based repos).
- The "legacy sha1 header only" gap does not, by itself, allow forging without the secret; it is a protocol-modernization concern, not a currently exploitable authentication bypass against orgs with a `webhook_secret` set.
- The `review_stacks_enabled` "precedence bug" premise could not be corroborated in the traced code.

### Recommendation
1. Scope `StatusHandler#process` to the repository that authenticated the webhook, e.g., filter `Commit.where(sha: params.sha)` by `stack: repository.stacks` (mirroring `Handler#stacks`), so a status update from repo/org A cannot touch commits belonging to stacks under a different repository.
2. Additionally support/require `X-Hub-Signature-256` (HMAC-SHA256) in `GitHubApp#verify_webhook_signature`, rejecting the legacy `sha1` scheme once all consumers have migrated, per GitHub's own deprecation guidance.
3. Do not silently `return true unless webhook_secret` — treat a missing configured secret as a hard failure (422) rather than an implicit signature bypass.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status event does not affect commits belonging to a different repository/stack" do
  other_repo   = create_repository(github_repo_name: "attacker/other-repo")
  other_stack  = create_stack(repository: other_repo)
  shared_sha   = "deadbeefcafefeed0000000000000000000001"

  victim_commit   = shipit_commits(:first) # belongs to shipit_stacks(:shipit)
  victim_commit.update!(sha: shared_sha)

  colliding_commit = other_stack.commits.create!(sha: shared_sha, message: "shared history")

  payload = {
    "sha" => shared_sha,
    "state" => "failure",
    "context" => "ci/attacker",
    "repository" => { "owner" => { "login" => "attacker" }, "full_name" => "attacker/other-repo" }
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  # EQUALITY BEING TESTED:
  # victim_commit.statuses(after) == victim_commit.statuses(before)   -- should hold if scoping is correct
  # colliding_commit.statuses(after) includes the new failure status  -- expected, same-org write

  assert_equal 0, victim_commit.reload.statuses.where(context: "ci/attacker").count,
    "status handler must not write statuses for commits outside the authenticating repository"
  assert_equal 1, colliding_commit.reload.statuses.where(context: "ci/attacker").count
end
```
This test currently fails against the shipped `StatusHandler`, since `Commit.where(sha: shared_sha)` matches both `victim_commit` and `colliding_commit` and updates both, confirming the missing repository/stack scoping described above.

      already_deployed = deployed?

      yield
      reload # to get the statuses into the right order (since sorted :desc)

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }

      end

        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
