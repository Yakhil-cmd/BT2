### Title
Delimiter Injection in Arbiter Contract Hashing Allows Title/Text Boundary Forgery and Dispute-Content Spoofing - (File: arbiter_contract.js)

### Summary
`arbiter_contract.getHashSrc()` builds the SHA-256 preimage for a contract's `hash` by naively joining attacker-controlled, unescaped strings (`title`, `text`, party names, amount, asset, addresses) with a fixed, non-unique delimiter `"[|#|]"`. Because none of the joined fields are checked to be free of the delimiter sequence (nor length-prefixed), a contract party fully controls both the content and the field boundaries of the string that gets hashed. This is the same root cause as CVE-2019-12520 (Squid): concatenating untrusted substrings with an ambiguous separator lets an attacker make two semantically different inputs collapse to an identical hashed identity, letting downstream consumers of that hash disagree about the "real" content behind it.

### Finding Description
`getHashSrc()` in `arbiter_contract.js` builds the hash source as: [1](#0-0) 

`title` and `text` are free-form strings supplied by whichever side originates the arbiter contract offer, and are validated only for non-emptiness — never for absence of the delimiter substring: [2](#0-1) 

`getHash()` simply SHA-256's this concatenation and is never re-parsed back into fields — but it is treated as a strong, collision-resistant identifier throughout the arbiter/dispute flow:
- It keys `wallet_arbiter_contracts` (`getByHash`, `INSERT`, `INSERT IGNORE` in `store()`), so contracts sharing a computed hash overwrite/short-circuit each other: [3](#0-2) [4](#0-3) 
- It is embedded directly into the on-chain shared-address oscript definition (`"CONTRACT_" + contract.hash` data-feed key), which is the mechanism that decides who receives the escrowed funds: [5](#0-4) 
- During a dispute, the counterparty submits an **encrypted** `contractContent` (containing `title`/`text`/party names) to the arbiter/arbstore, and the wallet re-derives `expectedContractHash` from those decrypted fields and only checks that it matches `body.contract_hash`: [6](#0-5) 

Because `title` and `text` are joined with a fixed, unescaped delimiter, an attacker who controls the contract (as offeror or as the party who ends up submitting the encrypted dispute content) can construct two different `(title, text)` pairs that concatenate to the identical byte string across the `title[|#|]text` boundary — e.g. `title="Agreement A[|#|]", text="hidden malicious clause"` vs. `title="Agreement A", text="[|#|]hidden malicious clause"` — both hash identically as long as the remaining joined fields (`creation_date`, `payer_address`, `payer_name`, `arbiter_address`, `payee_address`, `payee_name`, `amount`, `asset`) are unchanged. More generally, since `DELIMITER` ("[|#|]") is just an ordinary printable string with no reservation against user input, the attacker can freely choose *where* the logical boundary between `title` and `text` falls while keeping `hash` fixed to whatever value they need to match a previously agreed-upon, honestly-signed contract hash.

This directly parallels CVE-2019-12520's flaw: Squid computed a cache key from a concatenation of decoded userinfo + domain without a safe, non-ambiguous separator, letting an attacker's crafted userinfo be reinterpreted as a domain/path boundary and poison the cache for an unrelated URL. Here, the wallet computes an "identity key" (the contract hash) from a concatenation of untrusted strings without a safe separator, letting an attacker reinterpret the title/text boundary while preserving the hash that is cryptographically bound to fund-release logic.

### Impact Explanation
The contract `hash` is the anchor that ties the human-readable contract terms (`title`, `text`, party names) to the on-chain payment/dispute machinery (`CONTRACT_<hash>` data feed key controlling shared-address fund release, and `contract_text_hash` embedded in the signed data message). If an attacker can produce alternate `title`/`text` splits that hash identically to a legitimately agreed contract, they can:
- Present forged contract content (with a different displayed clause/split) during dispute resolution (`arbiter_dispute_request` handling) that still passes the `expectedContractHash === body.contract_hash` check, misleading the arbiter into resolving the dispute based on manipulated text while the cryptographic anchor still matches.
- Cause hash collisions between locally-stored contracts (`wallet_arbiter_contracts.hash` is the join/lookup key), so that `INSERT IGNORE` in `store()` silently drops a distinct contract and all later `getByHash()` lookups, status updates, and payment/dispute logic act on the wrong contract's stored terms (wrong amount/party/asset).

Because the arbiter's dispute resolution directly determines which address receives the escrowed funds via the shared-address definition, arbitration based on spoofed content can lead to fund loss/misdirection for one of the contract parties — a concrete "AA/contract fund loss" outcome reachable by a private-payment counterparty (the arbiter-contract offeror or acceptor), which is within the stated in-scope actor set.

### Likelihood Explanation
Any wallet user who initiates or accepts an arbiter contract (`createAndSend`/`respond`) fully controls their own `title`, `text`, and party name fields — no special privileges are required. Crafting two field splits that hash identically is a trivial string-manipulation exercise (not a cryptographic collision) because the attacker is the one supplying the string boundaries, not attacking someone else's honestly-generated hash. The complexity is low; the only requirement is that the feature (arbiter contracts / arbitration disputes) be in use, which is a standard, exposed wallet workflow.

### Recommendation
- Change `getHashSrc()`/`getContactsHash()` to use an unambiguous, length-prefixed or otherwise injective encoding for each field (e.g., reuse `string_utils.getSourceString`/`getJsonSourceString`, which already prefix by type and reject embedded join characters) instead of naive delimiter-joining of raw strings.
- Explicitly reject `title`, `text`, and party-name values that contain `exports.DELIMITER` (or any reserved sequence) before hashing/storing, on both the sending and receiving sides.
- When validating dispute content (`arbiter_dispute_request`), require that `title`/`text`/party names be individually length-prefixed or otherwise unambiguous before being folded into `expectedContractHash`, so no two distinct `(title, text)` splits can ever produce the same hash.

### Proof of Concept
1. Party A calls `createAndSend` with a legitimate contract: `title = "Refund Policy"`, `text = "No refunds after 30 days."`, other fields fixed.
   - `getHashSrc` produces: `Refund Policy[|#|]No refunds after 30 days.[|#|]<date>[|#|]<payer>[|#|]<payer_name>[|#|]<arbiter>[|#|]<payee>[|#|]<payee_name>[|#|]<amount>[|#|]<asset>`.
2. Party A (acting maliciously, e.g., when later assembling the encrypted dispute package sent to the arbiter/arbstore in `openDispute`) instead encrypts `contractContent = { title: "Refund Policy[|#|]No refunds after 30 days.", text: "" , ... }` (shifting the entire original text into the title field across the delimiter boundary), or any other split of the same concatenated bytes.
3. Both `getHashSrc` invocations produce byte-identical strings (`title[|#|]text` boundary moved, but full concatenation preserved), so `getHash()` yields the same `contract_hash`/`expectedContractHash`.
4. In `wallet.js`'s `arbiter_dispute_request` handler, `expectedContractHash === body.contract_hash` passes despite the arbiter now seeing different logical `title`/`text` values than what the honest counterparty believes was agreed, since the check only compares hashes, not the semantic field split: [7](#0-6) 

**Note on confidence**: I could not find any existing sanitization or delimiter-rejection logic for `title`/`text`/party-name fields anywhere in `arbiter_contract.js` or the `arbiter_contract_offer`/`arbiter_contract_shared`/`arbiter_dispute_request` handlers in `wallet.js`, confirming the gap. However, I was not able to fully trace how the arbstore server (external, not in this repo) uses `contractContent.title`/`text` in its dispute UI/resolution process, so the exact operational impact on fund movement depends on arbstore-side behavior that is outside this repository's scope.

function getHashSrc(contract) {
	const payer_name = contract.me_is_payer ? contract.my_party_name : contract.peer_party_name;
	const payee_name = contract.me_is_payer ? contract.peer_party_name : contract.my_party_name;
	const payer_address = contract.me_is_payer ? contract.my_address : contract.peer_address;
	const payee_address = contract.me_is_payer ? contract.peer_address : contract.my_address;
	const src = contract.creation_date > exports.NEW_HASH_DATE
		 ? [contract.title, contract.text, contract.creation_date, payer_address, payer_name || '', contract.arbiter_address, payee_address, payee_name || '', contract.amount, contract.asset || 'null'].join(exports.DELIMITER)
		 : [contract.title, contract.text, contract.creation_date, payer_name || '', contract.arbiter_address, payee_name || '', contract.amount, contract.asset || 'null'].join("");
	return src;
}
