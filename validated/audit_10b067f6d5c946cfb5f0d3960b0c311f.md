Cross-organization webhook signature confusion lets an attacker's no-secret org validate a forged `pull_request.unlabeled` event that mutates another org's `PullRequest`/`ReviewStack` state - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` picks which GitHub App/org's `webhook_secret` to validate against using `params.dig('repository', 'owner', 'login')`, while `LabelCapturingHandler` resolves the actual `Repository`/`Stack` to mutate using the independently attacker-controlled `params.repository.full_name`. In a multi-org configuration where at least one configured org has no `webhook_secret`, an attacker can make these two fields diverge, so the signature check validates against an org with no secret while the mutation lands on a different, real, secret-protected org's `PullRequest`.

### Finding Description
The broken binding: **the org whose `webhook_secret` verified the request** should equal **the org that owns the repository the handler mutates**. Concretely: `Shipit.github(organization: repository_owner)` (where `repository_owner = params.dig('repository','owner','login')`) must equal the owner of `Shipit::Repository.from_github_repo_name(params.repository.full_name)`. Nothing in the code enforces this.

Code path:
- `Shipit::WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-49) computes `repository_owner` from `params.dig('repository', 'owner', 'login')` and fetches `github_app = Shipit.github(organization: repository_owner)`. [1](#0-0) 
- `GitHubApp#verify_webhook_signature` short-circuits to `true` when the resolved org has no configured `webhook_secret`: `return true unless webhook_secret`. [2](#0-1) 
- `LabelCapturingHandler#repository` resolves the repository to mutate from a *different* field, `params.repository.full_name`, via `Shipit::Repository.from_github_repo_name`, completely independent of `repository_owner` used for signing. [3](#0-2) 
- `capture_labels` then persists attacker-controlled label names onto the resolved stack's `PullRequest`: `pull_request.update!(labels: params.pull_request.labels.map(&:name))`. [4](#0-3) 
- Those persisted label names later become uppercased environment variables in `ReviewStack#env`, feeding into deploy/task commands. [5](#0-4) 

Exploit flow: Shipit is configured with multiple GitHub Apps per org (`Shipit.github_organizations`, `github_app_config`) as documented in `test/dummy/config/secrets_double_github_app.yml`, where at least one org (e.g. `OrgTwo`) has `webhook_secret: # nil`. The attacker crafts a JSON body where `repository.owner.login = "OrgTwo"` (the no-secret org) but `repository.full_name = "victim-org/real-repo"` (a real repository belonging to a different, secret-protected org, whose review-stack the attacker knows about, e.g. from a PR they opened there). They send `X-Github-Event: pull_request` with `action: "unlabeled"` and any/garbage `X-Hub-Signature`. `verify_signature` resolves `Shipit.github(organization: "OrgTwo")`, which has no `webhook_secret`, so `verify_webhook_signature` returns `true` regardless of the (garbage) signature — the request passes. `Shipit::Webhooks.for_event('pull_request')` then dispatches to `LabelCapturingHandler`, which resolves the repository via `params.repository.full_name` = `victim-org/real-repo`, finds the real stack/`PullRequest` there, and overwrites its `labels` with attacker-supplied names, none of which were verified by `victim-org`'s secret.

Existing guards fail because: `verify_signature` never checks that `repository_owner` (used to select the verifying secret) matches the owner implied by `repository.full_name` (used by the handler to select the mutated record); the `ExplicitParameters` schema in the handler only validates types/presence of `repository.full_name`, not its owner-consistency with the top-level `repository.owner.login`; and `verify_webhook_signature`'s `return true unless webhook_secret` design assumes signature verification is scoped per-repository-owner, which is violated here because the two fields can differ.

### Impact Explanation
An attacker who controls no secret at all can, in a multi-org deployment where any single configured org lacks a `webhook_secret`, forge state-mutating webhooks against any other configured org's repositories/stacks whose full name they can discover. This is a cross-tenant state manipulation matching the "payload for one repository mutating another's stack" Critical impact category: the attacker overwrites `PullRequest#labels` on the victim's `ReviewStack`, which flow into `ReviewStack#env` as uppercased environment variables consumed by deploy/task commands — a foothold for further tampering with deploy behavior (e.g., toggling `ALLOW_...`/feature-flag-like label env vars used by `shipit.yml` conditionals). The attack is repeatable against any stack in any org as long as one org in the same Shipit instance has no `webhook_secret` configured.

### Likelihood Explanation
Preconditions: a multi-org Shipit deployment (per `github_organizations`/`github_app_config`) where at least one configured org omits `webhook_secret` (the codebase's own example configs, e.g. `config/secrets.development.example.yml` and `test/dummy/config/secrets_double_github_app.yml`, show `webhook_secret: # nil` as an accepted/expected configuration), and a target repository/stack in a different, properly-secured org. Attacker cost is a single unauthenticated HTTP POST with a crafted JSON body and an arbitrary/garbage `X-Hub-Signature` header — no valid signature, session, token, or team membership is required. This is trivially repeatable and scriptable.

### Recommendation
In `WebhooksController#verify_signature`, derive the verifying organization consistently with the org actually acted upon by each handler, and additionally validate that `repository.owner.login` matches the owner segment of `repository.full_name` before trusting either. More robustly, resolve the target `Repository`/`Stack` first (or at minimum parse the owner out of `full_name`) and verify the signature using that owner's `webhook_secret`, rejecting the request (422) if `repository.owner.login` and `repository.full_name`'s owner segment disagree. Also reconsider `GitHubApp#verify_webhook_signature`'s `return true unless webhook_secret` default — treat a missing `webhook_secret` as "reject all webhooks for this org" rather than "accept all", unless explicitly opted into open mode.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
