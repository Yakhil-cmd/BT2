### Title
Cross-tenant status fan-out via unscoped `Commit.where(sha:)` lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by `sha` alone with no repository/stack scoping, then writes a GitHub status to every matching `Commit` row across the entire installation. Since git SHAs are determined by content, not repository membership, a single signed webhook from one repository can write statuses onto commits belonging to unrelated stacks/tenants that happen to share that SHA (e.g., a shared empty initial commit).

### Finding Description
The broken binding: `stacks_mutated_by_webhook == 1` (the single authenticated repository) is expected, but in code it becomes `stacks_mutated_by_webhook == N` for any N stacks holding a `Commit` row with the same `sha`.

The handler is:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

This query is not scoped to `stack_id` or the authenticated repository at all, unlike the base `Handler` class, which provides a `stacks` helper explicitly scoped via `Repository.from_github_repo_name(repository_name)`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [2](#0-1) 

`StatusHandler` never calls `stacks`; it queries the global `Commit` table by `sha` only. `create_status_from_github!` then unconditionally writes a new status:
```ruby
def create_status_from_github!(github_status)
  add_status do
    statuses.replicate_from_github!(stack_id, github_status)
  end
end
``` [3](#0-2) 

`add_status` further triggers `Hook.emit(:commit_status, ...)` and can call `stack.schedule_merges`, propagating the effect into each victim stack's automation. [4](#0-3) 

`WebhooksController#verify_signature` only verifies that the payload was legitimately signed by the GitHub App for the `repository_owner`/`organization` named in the payload; it says nothing about which `Commit` rows the handler is permitted to touch:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  head(422) unless verified
``` [5](#0-4) 

So an attacker who owns `attacker/repoA`, connects it to Shipit, and pushes/tags a commit that reproduces a SHA already present in other stacks' `Commit` tables (trivially achievable for empty or boilerplate initial commits, or any SHA an attacker can learn from a target's public repo and then fabricate identical tree/commit content for in their own repo), can send one legitimately-signed `status` webhook from their own repository naming that shared SHA. `StatusHandler` will find and mutate every `Commit` row across all tenants with that SHA, not just the one belonging to the attacker's authenticated repository.

### Impact Explanation
A single webhook from an attacker-controlled, legitimately connected repository writes a forged commit status (`success`/`failure`/`pending`, arbitrary `description`/`target_url`/`context`) onto commits in unrelated victims' stacks. Because `deployable?`/`blocked?` and continuous-delivery scheduling depend on commit status, a forged `success` status can make an otherwise-blocked commit `deployable?` and trigger `schedule_continuous_delivery`/`stack.schedule_merges`, potentially causing an unauthorized deploy in a victim's stack. This is a cross-tenant write where a payload for one repository mutates another's stack/commit, matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team... or an unauthorized deploy").

### Likelihood Explanation
Preconditions: attacker owns/controls a GitHub repository connected to the target Shipit instance (a normal, low-privilege onboarding action for many public Shipit deployments), and at least one victim stack has a `Commit` row whose `sha` the attacker can reproduce (trivial for shared boilerplate/empty initial commits, or any commit the attacker can copy content-for-content into their own repo history). No Shipit session, API token, or GitHub secret is required — only a validly signed webhook from the attacker's own repository, which GitHub sends automatically on any status event from that repo. This is fully repeatable against arbitrary stacks sharing a colliding SHA.

### Recommendation
Scope the commit lookup to the authenticated repository, mirroring the base `Handler#stacks` helper, e.g.:
```ruby
def process
  stacks.flat_map { |stack| stack.commits.where(sha: params.sha) }.each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
or equivalently `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Create three stacks `stack_a` (repo `owner-a/repo-a`), `stack_b` (repo `owner-b/repo-b`), `stack_c` (repo `owner-c/repo-c`).
2. Create a `Commit` with identical `sha: "deadbeef" * 5` under each stack (`stack_a.commits.create!(sha: sha, ...)`, same for b and c).
3. Build a status payload naming only `repository.full_name = "owner-a/repo-a"` with `sha: sha, state: "success"`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)`.
5. Assert: `commit_a.reload.status.state == "success"` (expected, same-tenant).
6. Assert the broken binding: `commit_b.reload.status.state == "success"` and `commit_c.reload.status.state == "success"` — both true today despite the webhook never authenticating for `owner-b/repo-b` or `owner-c/repo-c`, proving the fan-out across unrelated stacks (`stacks_mutated == 3` instead of the expected `1`).

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
