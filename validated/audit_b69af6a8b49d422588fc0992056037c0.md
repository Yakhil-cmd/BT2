Confirmed: `CompilationError::WasmerCompileError { msg }` and `CompilationError::WasmtimeCompileError { msg }` both carry a free-form `msg: String` derived from `err.to_string()` on the underlying compile error [1](#0-0) , and this `msg` string is preserved (not discarded) when converted into the on-chain `near_primitives::errors::CompilationError::WasmerCompileError { msg }` via the `From::WasmtimeCompileError { msg } => Self::WasmerCompileError { msg }` conversion [2](#0-1) . `CompilationError` derives `BorshSerialize`/`BorshDeserialize` with `use_discriminant`, meaning the exact `msg` text is part of the deterministic on-chain-serialized `ActionError`/execution outcome [3](#0-2) .

However, `precompile` itself only reaches `CompilationError::PrepareError` or `WasmtimeCompileError` through `compile_and_cache` → `compile_uncached`, which first runs `prepare::prepare_contract` (a deterministic, protocol-versioned bytecode validation/instrumentation pass) and only falls through to `engine.precompile_module` — with a comment explicitly stating this path is "for defense in depth" because the runtime-independent preparation code is expected to "fully catch all invalid wasms" [4](#0-3) . So under normal operation, malformed/attacker-crafted wasm is expected to be rejected deterministically by `prepare_contract` (yielding `PrepareError`, whose variant is a fixed enum discriminant, not free text) before ever reaching the backend compiler.

The one place where wasmtime-internal, potentially engine/backend-dependent text (`err.to_string()`) can leak into the deterministic outcome is exactly the defense-in-depth `WasmtimeCompileError { msg }` arm — i.e., a wasm module that `prepare::prepare_contract` accepts as valid but that wasmtime's compiler backend (Winch on `x86_64` vs Cranelift elsewhere, per the engine config in `WasmtimeVM::new_for_target`) rejects with an *error message whose text depends on the compiler backend/version* [5](#0-4) . Since the network's protocol/consensus is homogeneous per environment (backend selection is `cfg!(target_arch)`-gated and, per the accompanying code comment, aarch64/Cranelift is explicitly a "development environment" fallback, not production), and because this fallback exists purely to satisfy Rust's `#[cfg(target_arch)]` compile-time gate rather than being an attacker-triggerable runtime choice, I cannot confirm from the code alone that mainnet validators/RPC nodes actually run on mixed architectures that would diverge on the same input. I was unable to fully verify (within the available index) whether current mainnet/testnet validator sets are strictly homogeneous x86_64, or whether any deployed node runs the Cranelift fallback in production — that would need to be checked in deployment/ops configuration outside this repo, or via a live Devin session with build/test access.

Given the available evidence, this is a real, narrow but plausible latent divergence surface (backend-dependent error message text is protocol-serialized) gated behind a "defense in depth" path that should be unreachable for any wasm accepted by `prepare_contract`, and the actual exploitability hinges on production nodes running heterogeneous wasmtime compiler backends/versions on the *same* protocol version — a precondition I could not confirm from this repository alone.

### Title
Backend-dependent `WasmtimeCompileError` message text serialized into deterministic on-chain outcome - (File: `runtime/near-vm-runner/src/wasmtime_runner/mod.rs::WasmtimeVM::compile_uncached` / `precompile`)

### Summary
`precompile` (via `compile_and_cache`/`compile_uncached`) only reaches wasmtime's native compiler on wasm bytecode that has already survived NEAR's own deterministic `prepare_contract` validation pass, and this path is explicitly documented as "defense in depth" for cases the runtime-independent checks fail to catch. If such a case exists, the resulting `CompilationError::WasmtimeCompileError{ msg }` — whose `msg` is `err.to_string()` from the underlying wasmtime/Cranelift/Winch error — is propagated verbatim into the Borsh-serialized, consensus-relevant `ActionError`/`FunctionCallError` outcome.

### Finding Description
An attacker deploys a `DeployContract` wasm module crafted to pass `prepare::prepare_contract`'s instrumentation/validation but fail native compilation in wasmtime (e.g. exceeding an internal Cranelift/Winch compiler limit not enforced by `prepare_contract`). On `precompile`/`compile_and_cache`, `self.engine.precompile_module(&prepared_code)` fails and the error text is captured as `CompilationError::WasmtimeCompileError { msg: err.to_string() }` [6](#0-5) . This `msg` is forwarded unchanged into `near_primitives::errors::CompilationError::WasmerCompileError { msg }` [7](#0-6)  and Borsh-serialized as part of the protocol-relevant `ActionError` [3](#0-2) . If two nodes use different wasmtime versions or compiler backends (the engine config selects Winch on `x86_64` and Cranelift otherwise, per `WasmtimeVM::new_for_target`) [5](#0-4) , the exact error text (and thus the serialized outcome/state root) can differ for byte-identical input, since `err.to_string()` is not a normalized, protocol-defined enum but raw compiler diagnostic text.

Existing checks: `prepare::prepare_contract` is intended to make wasmtime compilation deterministic and successful for all wasm passing its checks, so in the intended design this arm should be unreachable — I could not verify from the available code index whether a concrete bypass (a module accepted by `prepare_contract` but rejected differently by different wasmtime backends/versions) currently exists, nor whether production validators run heterogeneous backends/versions concurrently on the same protocol version.

### Impact Explanation
If such a divergent module exists and production nodes run heterogeneous wasmtime backends/versions, this would cause a real state/outcome divergence (different serialized `ActionError` text → different receipt/outcome hash → different state root) for byte-identical chunk input, matching NEAR's "unintended chain split requiring hard fork" Critical impact class. Absent a confirmed backend-divergent module and confirmed heterogeneous production deployment, this remains a design-risk observation rather than a demonstrated exploit.

### Likelihood Explanation
Low-to-unknown feasibility as demonstrated: it requires (1) a wasm module that passes `prepare_contract`'s deterministic checks yet is rejected by wasmtime's compiler with backend/version-dependent text, and (2) production nodes concurrently running different wasmtime compiler backends or versions on the same protocol version — both preconditions unverified in this repository. This is architecturally the single spot where non-enum, free-text compiler output re-enters consensus state, but no concrete PoC input triggering divergent backend behavior was found or constructed.

### Recommendation
Do not serialize raw `err.to_string()` compiler diagnostics into consensus-relevant state; replace `WasmtimeCompileError { msg }`/`WasmerCompileError { msg }` with a normalized, backend-independent error classification (e.g., a small closed enum of reasons) so that any two conforming nodes produce byte-identical `ActionError` regardless of wasmtime version/backend. Additionally, treat any wasm module that passes `prepare_contract` but fails native compilation as a `prepare_contract` gap and tighten `prepare_contract`'s checks to eliminate reliance on the compiler's own error text for consensus outcomes.

### Proof of Concept
Unit/integration test plan (not executed, requires Devin session with build access):
1. Build two `WasmtimeVM` instances configured with different `Strategy` (Winch vs Cranelift) or different wasmtime crate versions, using identical `Config`.
2. Craft a wasm module (fuzz `prepare::prepare_contract`'s accepted output space) that is accepted by `prepare_contract` but rejected by one backend and not the other, or rejected by both with different `to_string()` text.
3. Call `precompile`/`compile_and_cache` on both instances with the identical `ContractCode` bytes.
4. Assert: if the resulting `Result<_, CompilationError>` variant or `msg` text differs between the two runs, this proves the divergence; run the same chunk end-to-end through `execute_function_call` on both configurations and assert identical `ActionError`, `state_root`, and `gas_burnt` — a mismatch confirms the vulnerability.
