### Title
`StatusHandler#process` writes `Status` records across stacks by raw commit SHA with no repository/organization ownership check - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves target commits via `Commit.where(sha: params.sha)` with no scoping to the repository/organization that sent the webhook, and `Status` validates only `state` inclusion before persisting. Because the `commits` table's uniqueness constraint is `(sha, stack_id)` rather than a global unique `sha`, the same SHA can legitimately exist as separate `Commit` rows in multiple, unrelated stacks, letting a validly-signed webhook from one tracked repository write a `Status` onto another tenant's commit.

### Finding Description
The claimed binding: `AUTHORIZATION_TRUTH` requires `webhook_repository.full_name == commit.stack.repository.full_name` (or equivalent) before any write; here that equality is never checked.

Code path:
- `WebhooksController#verify_signature` authenticates the *sender* by looking up `Shipit.github(organization: repository_owner)` from the payload's own `repository.owner.login` and checking the HMAC signature [1](#0-0) . This proves the payload was signed by *some* configured GitHub App/org — it never binds the payload's `sha` to that org's repositories.
- `StatusHandler#process` then does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with `params` schema only requiring `sha`/`state` as strings [2](#0-1) . `Commit.where(sha: ...)` is a global query, not scoped to the stack/repository the signature verified.
- `Commit#create_status_from_github!` calls `statuses.replicate_from_github!(stack_id, github_status)` [3](#0-2) , and `Status#replicate_from_github!`/validation checks only `state` inclusion in `STATES` [4](#0-3) .
- Confirming that SHA collisions across stacks are structurally possible (not a hash-collision requirement): the DB index is `add_index :commits, %i(sha stack_id), unique: true` [5](#0-4) , i.e. uniqueness is per-stack, so the same SHA is expected/allowed to appear as distinct `Commit` rows in different stacks (this occurs naturally whenever a repository is forked and the fork is separately tracked by Shipit — history before the fork point shares identical commit SHAs).

Exploit flow: attacker owns/controls a repository that is itself tracked as a Shipit stack (satisfies "emit webhooks from a repository they own"), giving them a legitimately signed webhook channel for their own org. They fork (or otherwise obtain) a victim repository also tracked by Shipit, so a shared historical commit SHA exists in both stacks' `Commit` tables. The attacker sends a `status` event webhook, correctly signed for their own org, with `sha` set to the shared value and `state: 'success'`. `Commit.where(sha:)` returns both their own commit and the victim's commit, and `create_status_from_github!` is invoked on both indiscriminately, writing a `Status` for the victim's stack that the victim's repository never sent.

Existing guards fail because `verify_signature` only authenticates the request's claimed organization, not that the `sha` inside the payload actually belongs to a repository of that organization; and `Status`/`Commit` model validations only constrain `state` to the four enum values, with no `repository.full_name`/stack-ownership predicate anywhere in the path.

### Impact Explanation
A `Status` write on the victim's commit is not inert: `add_status`/`create_status_from_github!` drives `deployable_status` webhook emission, `ProcessMergeRequestsJob` enqueuing, and continuous-delivery scheduling based on state transitions, as shown by existing tests exercising exactly this path [6](#0-5) . On a victim stack with `continuous_deployment` enabled, forcing a `success` state onto a shared commit can trigger an unauthorized deploy of that stack — a cross-tenant write escalating into an unauthorized deploy, matching the Critical impact category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy"). This is repeatable against any victim stack sharing a commit SHA with an attacker-controlled tracked repository (e.g., via fork history).

### Likelihood Explanation
Preconditions: the attacker must already have a repository registered as a Shipit stack under some org with a webhook path they can legitimately trigger (achievable by adding/forking a repo they own into Shipit, which requires no elevated Shipit role, just repo ownership and GitHub App installation permission on their own repo), and a victim stack must share at least one commit SHA (trivially satisfied for the pre-fork-point history of any forked, Shipit-tracked open-source project). No secrets, sessions, or `Shipit.github_teams` membership are needed. This is feasible and repeatable at low cost for any Shipit deployment that tracks forkable/public repositories.

### Recommendation
In `StatusHandler#process` (and analogously `CheckSuiteHandler`/similar handlers), scope the `Commit` lookup by the webhook's own repository, e.g. join through `Stack`/`Repository` and require `commit.stack.repository.full_name == params.dig('repository', 'full_name')` (or organization/repo id) before calling `create_status_from_github!`, rejecting/skipping any matched commit whose stack does not belong to the reporting repository.

### Proof of Concept
Minitest plan (`test/models/commits_test.rb` or a webhook controller test):
1. Create two stacks, `stack_attacker` (repo `attacker/repo`) and `stack_victim` (repo `victim/repo`), each with a `Commit` sharing the same `sha` value (mirroring a shared fork history commit).
2. Assert `Commit.where(sha: sha).count == 2` and that the two commits belong to different `stack_id`s — establishing the LHS/RHS of the binding are equal only if a repository-match check exists; show it doesn't.
3. Invoke `Shipit::Webhooks::Handlers::StatusHandler.call(params)` (or POST `/webhooks` with `X-Github-Event: status`, signed for `attacker`'s org) with `sha:` the shared sha and `state: 'success'`, `repository: { full_name: 'attacker/repo', owner: { login: 'attacker' } }`.
4. Assert `stack_victim`'s commit now has a `Status` with `state == 'success'` (`assert_equal 'success', stack_victim_commit.reload.state`), proving the victim's stack was mutated by a payload authenticated only for `attacker/repo`.
5. Using Mocha, assert no method resembling repository-match/ownership scoping (e.g., `Repository#full_name`, a stack/organization-membership predicate) is ever invoked between `Handler#process` and the `Status` `INSERT` — confirming the described absence of an authorization check on this path.
