### Title
Unauthenticated SSE event stream via `/events` mount exposes stack update broadcasts - (File: config/routes.rb)

### Summary
`config/routes.rb` mounts `Pubsubstub::StreamAction.new` directly as a Rack endpoint at `/events`, bypassing `Shipit::ShipitController` and its `include Shipit::Authentication` before_action entirely, since `mount` does not route through any Shipit controller. Any unauthenticated client can `GET /events?channels[]=stack.<id>` and receive live `update` events (`{id, updated_at}`) published by `Stack#broadcast_update` for any stack ID.

### Finding Description
The broken binding is: `force_github_authentication gated this mount == true` is actually **false**. `Shipit::Authentication#force_github_authentication` is wired in only via `Shipit::ShipitController` [1](#0-0) , which is a controller superclass — the before_action mechanism only fires for requests dispatched to actions of controllers that include this concern. `mount Pubsubstub::StreamAction.new, at: "/events", as: :events` in `config/routes.rb` line 9 wires a raw Rack endpoint directly into the router [2](#0-1) , which is dispatched without ever touching `ShipitController`, `ApplicationController`, or any `before_action`. There is no controller, no `force_github_authentication`, and no channel-authorization check anywhere in this engine wrapping that mount.

`Pubsubstub::StreamAction` accepts a `channels` param and subscribes the SSE connection to those pubsub channels, and the engine's own views construct channel names directly from `stack.id`, e.g. `subscribe events_path(channels: ["stack.#{@stack.id}"])` [3](#0-2)  and `app/views/shipit/merge_requests/merge_requests/index.html.erb` line 1. `Stack#broadcast_update` publishes to exactly that channel name on every update: `Pubsubstub.publish("stack.#{id}", { id:, updated_at: }.to_json, name: 'update')`, triggered via `after_commit :broadcast_update, on: :update` [4](#0-3) [5](#0-4) . Since stack IDs are small sequential integers and channel names are trivially predictable/guessable/enumerable, an attacker only needs to request `/events?channels[]=stack.1`, `stack.2`, etc.

Existing guards fail because none of them apply to this route: `force_github_authentication` never executes (not a controller action), and there is no channel-membership/authorization check in the engine's routing or in `Stack`/`Repository` models restricting which channels a given SSE client may subscribe to.

### Impact Explanation
An unauthenticated attacker can continuously receive live `updated_at`/`id` broadcast events for any stack across any tenant/repository hosted on the Shipit instance, by iterating stack IDs. This is an unauthenticated read of live stack state, matching the High-severity category "unauthenticated read of stack state, task streams, or deploy output." It is fully repeatable and scales to every stack ID on the instance — the disclosed payload itself is minimal (`id`, `updated_at`) but it confirms activity/update timing on stacks the attacker has no authorization to view, and combined with predictable stack IDs enables blind enumeration of tenant stack existence and update cadence.

### Likelihood Explanation
No preconditions beyond network access to the Shipit host are required — no session, no API token, no GitHub credentials. The attacker cost is a single unauthenticated HTTP GET with a guessed/enumerated `channels[]=stack.<id>` parameter, and it can be repeated indefinitely against every stack ID on the instance. This is trivially and cheaply exploitable.

### Recommendation
Do not mount `Pubsubstub::StreamAction` unauthenticated. Wrap it behind a controller/route constraint that enforces `Shipit::Authentication#force_github_authentication` (or an equivalent authorization check) before allowing an SSE subscription, and additionally validate that the requested `channels[]` values correspond to stacks the authenticated user is authorized to view (e.g., verify `current_user.authorized?` and that the `stack.<id>` channel maps to a stack whose repository the user can access) before establishing the Pubsubstub subscription.

### Proof of Concept
Minitest (`ActionDispatch::IntegrationTest`) plan:
1. Create a `Shipit::Stack` fixture with a known `id` (no login/session set).
2. Stub/mock `Pubsubstub::StreamAction#call` (or use `Pubsubstub.expects(:publish)` similar to the pattern in `test/models/status_test.rb` lines 58-63) to assert the subscription/callback path is reached.
3. Issue `get "/events", params: { channels: ["stack.#{stack.id}"] }` with no session cookie and no `Authorization` header.
4. Assert the response is not a redirect (`302` to `github_authentication_path`) and not `401`/`403` — i.e., the request enters the Pubsubstub Rack app and establishes/attempts an SSE subscription, in contrast to any other Shipit route (e.g., `get stack_path(stack)`) which should redirect unauthenticated users to the GitHub auth flow via `force_github_authentication`.
5. Compare against a control request to a normal controller route (e.g. `stack_tasks_list_path`) with no session, asserting it *does* redirect/403, to demonstrate the binding divergence: `force_github_authentication gated this mount == false` while `force_github_authentication gated this route == true`.
