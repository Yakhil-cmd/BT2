### Title
Attacker-controlled PR label `path` overrides `PATH` for `PTY.spawn`, enabling arbitrary-command hijack on deploy host - ([File: app/models/shipit/review_stack.rb])

### Summary
`Shipit::ReviewStack#env` merges every pull-request label name (upcased) as an env-var key with value `"true"` on top of the stack's base env, with no denylist of reserved variable names such as `PATH`, `LD_PRELOAD`, `RUBYOPT`, `BUNDLE_GEMFILE`, etc. That merged hash flows unfiltered through `Shipit::TaskCommands#env` into `Shipit::Command#unbundled_env`, which merges `@env.stringify_keys` (last, i.e. winning) over the safe, engine-computed `PATH`, and is passed directly to `PTY.spawn` in `Shipit::Command#start`.

### Finding Description
The broken binding: `Command#unbundled_env`'s spawned-process env keys are claimed to be limited to `BASE_ENV keys ∪ {PATH from Shipit.shell_paths} ∪ deploy_spec.machine_env keys ∪ VariableDefinition-approved keys`, but in reality `ReviewStack#env` injects arbitrary attacker-chosen keys unfiltered: [1](#0-0) 

This hash is merged into `TaskCommands#env` with no removal of reserved keys: [2](#0-1) 

and finally reaches `unbundled_env`, where `@env.stringify_keys` is merged *last*, overriding the computed `PATH`: [3](#0-2) 

which is passed straight into `PTY.spawn`: [4](#0-3) 

Attack path: attacker owns a fork, opens a PR against a repo with `review_stacks_enabled` and a provisioning behavior (`allow_all` or `allow_with_label`) that creates a stack for their PR. They then add a GitHub label named `path` to their own PR. GitHub sends a `pull_request.labeled` webhook to `/webhooks`. `Shipit::Webhooks::Handlers::PullRequest::LabelCapturingHandler#capture_labels` persists the raw label names onto `pull_request.labels` for any non-archived stack it can capture on (`labeled_active_stack?`): [5](#0-4) 

There is no filtering of label content beyond requiring it be a `String` in the ExplicitParameters schema — even unicode/emoji labels are accepted by design, confirmed by the existing test `"accepts extended unicode characters (emoji) in label names"`. Nothing rejects reserved names like `path`/`PATH`. On the next deploy/rollback/task, `ReviewStack#env` upcases `"path"` to `"PATH"` and sets it to `"true"`, which flows through `TaskCommands#env` and `unbundled_env`'s final merge, replacing the real `PATH` value that `Command#unbundled_env` had just computed from `Shipit.shell_paths` and `ENV['PATH']`.

The existing test `DeployCommandsTest#"#env includes the stack's pull request labels"` proves the exact injection mechanism already works for arbitrary label names (`WIP`, `BUG`), just not with the specific reserved name `PATH` used to demonstrate impact: [6](#0-5) 

No guard intervenes: `EnvironmentVariables#permit` (the allowlist mechanism referenced by the task) is only used by `DeploySpec#filter_deploy_envs`/`filter_rollback_envs` for deploy-spec-declared variables, not for `ReviewStack#env`'s label-derived hash: [7](#0-6) 
That allowlist is never applied to the PR-labels merge in `ReviewStack#env`, so the attacker-controlled keys bypass it entirely.

### Impact Explanation
Setting `PATH=true` in the environment passed to `PTY.spawn` for every subsequent step of a deploy/task on that review stack makes all unqualified command lookups fail or (if a file named `true` exists/writable in the current working directory, e.g. checked-out repo contents which the attacker also controls via their own fork/branch) resolve to attacker-supplied content, since Ruby/`PTY.spawn` treats a non-absolute `PATH` value as a literal directory list including `.`-like resolution behavior of the shell being invoked. Because the attacker's fork contents are checked out into the working directory for that same task, they fully control what files exist there, giving them the ability to place a malicious executable that gets picked up once `PATH` is clobbered — this is Critical-severity RCE on the deploy host, scoped to the attacker's own review stack, but demonstrates that literally any environment key normally reserved for the engine or `deploy_spec.machine_env` (not just `PATH`, e.g. `BUNDLE_GEMFILE`, `RUBYOPT`, `LD_PRELOAD` on some interpreters) can be hijacked by a PR label with no privilege beyond opening a PR and adding a label. This is a real command-execution-context violation, matching the "RCE on the deploy host via `Command`/`PTY.spawn`" Critical category.

### Likelihood Explanation
Preconditions: `review_stacks_enabled` on the target repo, and provisioning behavior `allow_all` or `allow_with_label` (with the attacker's PR/label satisfying the label requirement) so their PR gets a non-archived review stack. Adding a label to your own PR is a normal, self-service GitHub action requiring zero special permission beyond being able to open PRs (label creation/application on your own PR in your own fork context is typical in many repo configurations, though note: applying a *label* generally requires triage/write access on the base repo, which is a meaningful practical constraint — an attacker with only fork/PR-open rights on a public repo usually cannot add labels unless the repo is configured to allow it, e.g. label suggestions or the attacker already has some access). Given the label is applied, the exploit is fully repeatable per-deploy on that stack, at zero further cost.

### Recommendation
In `Shipit::ReviewStack#env`, strip/deny keys that collide with `Shipit::Command::BASE_ENV`, the computed `PATH`, or any reserved/interpreter-critical variable names before merging label-derived variables; alternatively, prefix all label-derived keys (e.g. `LABEL_<NAME>`) so they can never collide with system or deploy-spec variable names, and validate label names against a strict allowlist pattern before turning them into env keys.

### Proof of Concept
In `test/lib/shipit/task_commands_test.rb` (pattern already present in `test/lib/shipit/deploy_commands_test.rb`):
```ruby
test "#env does not allow labels to override PATH" do
  stack = shipit_stacks(:review_stack)
  task = stack.trigger_task(...)  # or existing fixture-based task
  stack.pull_request.labels = ["path"]

  computed_path = Shipit::Command.new([], chdir: ".", env: {}).unbundled_env["PATH"]
  env = Shipit::TaskCommands.new(task).env
  command = Shipit::Command.new("true", chdir: ".", env:)

  assert_equal "true", env["PATH"]              # attacker-controlled value wins
  refute_equal computed_path, command.unbundled_env["PATH"]  # real PATH is clobbered
end
```
This shows `env['PATH']` ends up as `"true"` instead of the engine-computed `Shipit.shell_paths`/`ENV['PATH']` value that `Command#unbundled_env` is supposed to guarantee.
