### Title
Cross-Organization Webhook Forgery via Signature/Repository Binding Mismatch - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
### Finding Description
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to use for HMAC verification based on `repository_owner`, computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`, and passed to `Shipit.github(organization: repository_owner)`. [1](#0-0) [2](#0-1) 

However, once the signature is accepted, every event handler independently determines the repository/stack to act on using a *different* field from the same untrusted JSON body: `payload.dig('repository', 'full_name')`. [3](#0-2) 

Both `repository.owner.login` and `repository.full_name` originate from the same attacker-controlled JSON payload. There is no code that enforces that the organization used to select the verification secret (`repository.owner.login`) actually matches the organization portion of `repository.full_name`. In genuine GitHub-generated payloads these two are always consistent, but a forged payload sent directly to `/github_hooks` can set them independently.

Shipit explicitly supports per-organization GitHub App configuration, each with its own distinct `webhook_secret`, `app_id`, and `private_key`: [4](#0-3) 

This creates the exact binding break the scan is looking for: **the organization whose secret authenticated the request ≠ the repository the handler subsequently writes to.** An actor who legitimately controls the GitHub App/webhook configuration for Organization A (and therefore knows Org A's `webhook_secret`, e.g. because they administer that org's own Shipit-connected GitHub App) can craft a raw JSON body where:
- `repository.owner.login` = `"OrgA"` (selects OrgA's secret for `verify_webhook_signature`)
- `repository.full_name` = `"OrgB/private-repo"` (a stack belonging to a completely different, unrelated organization also hosted on the same Shipit instance)

They sign the entire raw body with OrgA's known secret and POST it to the shared `/github_hooks` endpoint. `verify_signature` passes (correct org secret, correct HMAC over the exact bytes), and `WebhooksController#create` dispatches the parsed payload to every handler for the event type, e.g. `PushHandler`, `StatusHandler`, `PullRequest::OpenedHandler`. Each of these resolves the target `Stack`/`Repository`/`Commit` purely from `repository.full_name` (or, for `StatusHandler`, from `sha` lookup across all commits regardless of org) — never re-checking that this matches the organization that authenticated the request. [5](#0-4) [6](#0-5) [7](#0-6) 

### Impact Explanation
This is a cross-repository/cross-organization write: an attacker who knows only their own organization's webhook secret can inject fabricated `push`, `status`, or `pull_request` events for a stack belonging to an entirely different organization hosted on the same Shipit instance. Concretely:
- `PushHandler` enqueues `GithubSyncJob`/triggers `stack.sync_github` for Org B's stack, forging what Shipit believes is the current HEAD of Org B's branch.
- `StatusHandler` can inject fabricated commit statuses (`commit.create_status_from_github!`) onto Org B's commits, which can satisfy `required_statuses`/`blocking_statuses` checks used to gate `continuous_deployment`, potentially enabling an **unauthorized deploy** of code that never actually passed CI.
- `PullRequest::OpenedHandler` can force creation/provisioning of Org B review stacks.

This falls under the specified Critical impact categories: cross-repository writes and potentially an unauthorized deploy triggered via forged status checks.

### Likelihood Explanation
Exploitability requires the attacker to legitimately possess a valid `webhook_secret` for at least one organization configured in the same multi-tenant Shipit deployment (a realistic scenario for any Shipit instance shared across multiple orgs/teams, since each org configures/owns its own GitHub App credentials per `config/secrets.*.yml`). No access to Org B's secret, `ApiClient` tokens, or GitHub App credentials for Org B is required — only network access to the shared `/github_hooks` endpoint and knowledge of one's own org's secret, both of which are normal for an org that has legitimately integrated with the Shipit instance.

### Recommendation
After successfully verifying the signature, enforce that the organization used to select the verification key (`repository_owner`/`organization.login`) matches the owner portion of `repository.full_name` (and any other repository-identifying fields consumed by handlers) before dispatching the event, rejecting mismatches with `422`.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with distinct `webhook_secret`s, both having Shipit-tracked repositories/stacks.
2. As someone with legitimate knowledge of `OrgA`'s `webhook_secret` (e.g., the GitHub App owner for OrgA), craft a raw JSON body for a `push` event:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen-sha>",
     "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/private-repo" }
   }
   ```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, raw_body)>`.
4. `POST /github_hooks` with header `X-Github-Event: push`.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and the HMAC verifies successfully.
6. `PushHandler#process` (via `Handler#stacks`/`repository_name`) resolves the stack using `repository.full_name` = `"OrgB/private-repo"`, and triggers `stack.sync_github` on Org B's stack — despite the request never being authenticated by Org B's credentials.
