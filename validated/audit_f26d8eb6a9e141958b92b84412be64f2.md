### Title
`Team.find_or_create_by_handle` binds `Shipit.github_teams` to a `github_id`-mismatched Team row created by a forged `membership` webhook - (File: `app/models/shipit/team.rb`, `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`MembershipHandler#find_or_create_team!` keys Team creation on the fully attacker-controlled `params.team.id` (as `github_id`) while `Team.find_or_create_by_handle`, used to resolve `Shipit.github_teams`, keys lookup on `(organization, slug)` only. When webhook signature verification is bypassed (no `webhook_secret` configured for the target org), an attacker can forge a `membership` webhook that both creates a `Team` row matching a configured handle (e.g. `shopify/developers`) and immediately adds themselves as a member, and if this happens before `Shipit.github_teams` is first memoized, the attacker's forged row - not a GitHub-verified one - becomes the authorization anchor.

### Finding Description
The broken binding: `Shipit.github_teams` resolution for handle `"shopify/developers"` should satisfy `(Team.organization, Team.slug) == (real GitHub org, real GitHub team slug for that handle)` with `Team.github_id == real GitHub team id`. Instead, `Team.find_or_create_by_handle` (`app/models/shipit/team.rb:18-21`) does:

```ruby
def find_or_create_by_handle(handle)
  organization, slug = handle.split('/').map(&:downcase)
  find_by(organization:, slug:) || fetch_and_create_from_github(organization, slug)
end
``` [1](#0-0) 

This matches any existing row by `(organization, slug)` alone, irrespective of `github_id` authenticity. `Shipit.github_teams` memoizes the result on first access:

```ruby
def github_teams
  @github_teams ||= github.oauth_teams.map { |t| Team.find_or_create_by_handle(t) }
end
``` [2](#0-1) 

Meanwhile, `MembershipHandler#find_or_create_team!` (`app/models/shipit/webhooks/handlers/membership_handler.rb:38-43`) keys the row on `github_id: params.team.id`, and sets `organization` from `params.organization.login`, both attacker-controlled fields from the webhook body:

```ruby
def find_or_create_team!
  Team.find_or_create_by!(github_id: params.team.id) do |team|
    team.github_team = params.team
    team.organization = params.organization.login
  end
end
``` [3](#0-2) 

The `membership` handler's `process` also immediately performs `team.add_member(member)` for the attacker-specified member on `action: 'added'`: [4](#0-3) 

Reaching this handler requires only passing `WebhooksController#verify_signature`, which is a no-op whenever the target organization has no `webhook_secret` configured:

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [5](#0-4) 

and `repository_owner`/`organization.login` is read straight from attacker-supplied JSON to pick which `GitHubApp` instance's (potentially unconfigured) secret to check: [6](#0-5) 

The `MembershipHandler` params schema (`requires :team do requires :id, Integer ... end`) only enforces types, not values — the attacker can freely choose `team.id`, `team.slug`, `organization.login`, and `member.login`: [7](#0-6) 

**Exploit flow:** On an instance where the target org's `webhook_secret` is unset (or before `Shipit.github_teams` has ever been resolved after a cache-clearing deploy), the attacker POSTs to `/webhooks` with header `X-Github-Event: membership` and body `{action: 'added', team: {id: <attacker chosen>, slug: 'developers', name: 'x', url: 'x'}, organization: {login: 'shopify'}, member: {login: '<attacker-github-login>'}}`. This creates a `Team` row with `organization: 'shopify', slug: 'developers', github_id: <attacker chosen>` and adds the attacker as a member via `Membership`. When `Shipit.github_teams` is later evaluated (e.g. on the next request hitting `force_github_authentication`), `find_or_create_by_handle('shopify/developers')` finds this row by `(organization, slug)` and memoizes it as the authorization anchor — with the attacker already a member.

Existing guards do not stop this: `verify_signature` is bypassed by design when no secret is set (not a bug per se, but the enabling precondition); `drop_unhandled_event` does not filter `membership`, which is a registered handler; the `ExplicitParameters` schema validates types only, not values or GitHub-side authenticity; there is no cross-check that `github_id` in a forged webhook corresponds to a real GitHub team, nor any validation binding `(organization, slug)` uniqueness against `github_id`.

### Impact Explanation
An unauthenticated attacker can pre-empt or fork the `Team` row backing a configured `Shipit.github_teams` entry and immediately grant themselves membership in it via `Membership`, before any legitimate GitHub-sourced row for that handle exists. Once `Shipit.github_teams` memoizes this forged row, `User#authorized?`-gated actions (session access to stacks, task streams, deploy triggers) treat the attacker as belonging to the privileged team, i.e. escalation into `Shipit.github_teams` authorization. This is scoped to whichever org/handle the attacker targets and is only exploitable while the target org's webhook secret is unset and before the corresponding `github_teams` entry is first resolved — a narrow but real window (fresh boot, cache-cleared deploy, secret rotation gap).

### Likelihood Explanation
Requires: (1) the target organization's `GitHubApp` config to have no `webhook_secret` set (an operator configuration gap, explicitly acknowledged as the "blank-secret gap" precondition, not a secret the attacker must possess), (2) the attacker's forged request racing ahead of the first `Shipit.github_teams` memoization for that handle. No Shipit session, API token, or GitHub secret is needed by the attacker. This is not repeatable against an already-memoized/already-populated team (subsequent `find_by` calls before process restart return the same row and `find_or_create_by_handle` won't re-run), so it is a one-shot-per-boot race rather than an arbitrary repeatable attack, but is reproducible on any deploy/restart cycle if the misconfiguration persists.

### Recommendation
Bind `Team.find_or_create_by_handle` and `MembershipHandler#find_or_create_team!` on the same authoritative key. Concretely: have the membership webhook handler resolve teams via GitHub API team lookup (organization + slug fetched from GitHub, not trusted from the payload) rather than trusting `params.team.id` as `github_id` directly; and/or have `find_or_create_by_handle` validate/refresh against `fetch_and_create_from_github` (verifying `github_id` matches GitHub's canonical team id) rather than trusting any pre-existing `(organization, slug)` row blindly. Additionally, require `webhook_secret` to be configured for every organization referenced in `Shipit.github_teams`, and refuse to memoize `Shipit.github_teams` from a `Team` row that was never confirmed via a signed webhook or direct GitHub API fetch.

### Proof of Concept
```ruby
# test/models/team_test.rb (conceptual addition)
test "find_or_create_by_handle binds to a forged Team row with mismatched github_id" do
  # Simulate forged membership webhook creating a Team keyed by (organization, slug)
  # with an attacker-chosen github_id, before any real GitHub-sourced row exists.
  forged_team = Shipit::Team.find_or_create_by!(github_id: 999_999) do |team|
    team.organization = 'shopify'
    team.slug = 'developers'
    team.name = 'Fake Developers'
    team.api_url = 'https://example.com/fake'
  end

  attacker = Shipit::User.find_or_create_by_login!('attacker-login') # mocked github API
  forged_team.add_member(attacker)

  resolved = Shipit::Team.find_or_create_by_handle('shopify/developers')

  # Binding equality claimed broken:
  # resolved.github_id (real GitHub team id for shopify/developers) == forged_team.github_id (attacker chosen)
  assert_equal forged_team.id, resolved.id
  refute_equal REAL_SHOPIFY_DEVELOPERS_GITHUB_ID, resolved.github_id
  assert_includes resolved.members, attacker
end
```
This demonstrates `find_or_create_by_handle` matching and returning the attacker's forged row (with attacker already a member) instead of fetching/validating the real GitHub team, confirming the `(organization, slug)` vs `github_id` key mismatch.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
