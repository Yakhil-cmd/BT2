## Title
Webhook signature validated against the payload's own `repository.owner.login`, while status/push handlers act on repository/commit data with no matching binding - cross-tenant status injection & unauthorized deploy - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
This maps the `checkTransfer` bug class (one field verified, a different field acted upon) onto Shipit's webhook trust boundary: `WebhooksController#verify_signature` selects *which org's* `webhook_secret` to validate the HMAC against using a field taken from the same untrusted JSON body it is about to verify, and the handlers that subsequently act on that body do not re-check that the "verified" organization actually owns the resource being mutated.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/org whose secret is used to check `X-Hub-Signature` from the payload itself: [1](#0-0) [2](#0-1) 

`repository_owner` reads `params.dig('repository', 'owner', 'login')`. Shipit is explicitly designed to host multiple, independently-configured GitHub Apps/orgs behind one shared `/webhooks` endpoint, each with its own `app_id`, `installation_id`, and `webhook_secret`: [3](#0-2) [4](#0-3) 

The signature check only proves "this request was signed with *some registered org's* secret" - it never confirms that org actually owns the repository/commit the payload claims to describe. After `verify_signature` passes, `create` dispatches the entire attacker-supplied JSON straight to the event handler: [5](#0-4) 

`StatusHandler` (the `status` event) is the sharpest instance of the missing binding: it never scopes to a repository/stack at all, it matches purely by `sha` across the entire installation: [6](#0-5) 

`Commit#create_status_from_github!` then persists whatever `state`/`context`/`description` was supplied as a real `Status` record on that commit: [7](#0-6) [8](#0-7) 

The binding that is broken, expressed as an equality that should hold but doesn't:
`org whose secret signed the request == org that owns the repository/commit the payload mutates`

For push/pull_request handlers, the same gap exists one level up: they resolve the target purely from `payload.dig('repository', 'full_name')` (`Handler#repository_name`, `PushHandler#process`) - a field that is never cross-checked against `repository_owner` (the field the signature was verified against): [9](#0-8) [10](#0-9) 

### Impact Explanation
Any tenant onboarded onto a shared multi-org Shipit instance (i.e., anyone who legitimately knows the `webhook_secret` for their own configured GitHub App/org) can:
- Forge a `status` webhook with `sha` set to a real, known commit SHA belonging to an unrelated victim stack in a different org, injecting a fabricated `success` status for a required CI context. Because `Status` creation triggers `schedule_continuous_delivery`, this can cause Shipit to autonomously trigger a deploy of that (unreviewed/failing) commit for the victim stack if continuous deployment is enabled - an unauthorized deploy driven entirely by a forged webhook, matching the "unauthorized deploy" Critical/High impact criterion.
- Forge `push`/`repository`-scoped events with a `repository.owner.login` matching their own org (to pass the secret lookup) but a `repository.full_name`/other repository identifier pointing at a victim org's repo, to force syncs or side effects (e.g. `sync_github`) on stacks they don't own.

### Likelihood Explanation
This requires only being a legitimate, low-trust tenant of a shared Shipit deployment (knowledge of one's own org's `webhook_secret`, which such a tenant necessarily has when they configured their own GitHub App), not a compromised admin, `ApiClient` token, or GitHub org write access to the victim. The `StatusHandler` path additionally requires only knowledge of a target commit's SHA, which is public on GitHub. No race condition, DoS, or social engineering is needed - this is a straightforward crafted-request exploit against the trust binding itself.

### Recommendation
- Have `StatusHandler` (and other handlers) resolve and filter commits/stacks strictly by `Repository.from_github_repo_name(payload.dig('repository','full_name'))` and reject if that repository's owner doesn't match `repository_owner`.
- In `WebhooksController#verify_signature`, after determining the signing org, verify that every repository-identifying field used downstream (`repository.full_name`, `repository.owner.login`, `organization.login`) is mutually consistent, and reject the webhook otherwise.

### Proof of Concept
1. Register/operate a tenant org ("orgB") on the shared Shipit instance with its own configured `webhook_secret` (known to the attacker as the org's own GitHub App owner).
2. Look up the real commit SHA of a target commit belonging to a victim stack in an unrelated org ("orgA/victim-repo"), tracked by Shipit (visible via GitHub's public commit history).
3. Craft a `status` event JSON body: `{"sha": "<victim-sha>", "state": "success", "context": "<required-ci-context>", "repository": {"owner": {"login": "orgB"}, "full_name": "orgB/some-repo"}}`.
4. Sign it with `HMAC-SHA1(orgB_webhook_secret, body)` and POST to `/webhooks` with `X-Github-Event: status` and `X-Hub-Signature`.
5. `verify_signature` resolves `repository_owner` = `orgB`, finds orgB's app, and the signature validates successfully.
6. `StatusHandler#process` executes `Commit.where(sha: "<victim-sha>")` - matching the real commit under `orgA/victim-repo` - and creates a forged `success` `Status`, potentially satisfying `commit.deployable?` and triggering continuous delivery for the victim stack.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
