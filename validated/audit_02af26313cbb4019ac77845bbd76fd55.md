### Title
Cross-tenant Team resolution in `find_or_create_team!` allows one org's verified webhook to delete another org's team Membership - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::MembershipHandler#find_or_create_team!` resolves a `Team` row solely by `params.team.id` (GitHub team `github_id`), with no check that `params.organization.login` matches that team's stored `organization`. Because `WebhooksController#verify_signature` authenticates the payload against the organization named in the payload itself (attacker-controlled, and truthfully the attacker's own org), a webhook that is 100% validly signed by an attacker's own GitHub organization can still be routed to mutate a `Team`/`Membership` row that legitimately belongs to a different organization, including deleting a legitimate operator's membership.

### Finding Description
The broken binding: the code assumes `team.organization == params.organization.login` for every `Team` row reached via `find_or_create_team!`, but this is never enforced.

Path:
1. `WebhooksController#verify_signature` computes `repository_owner` as `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0)  and verifies the signature using `Shipit.github(organization: repository_owner)` [2](#0-1) . Membership payloads have no `repository` key, so `repository_owner` becomes `organization.login` — the attacker's own org. Signature verification therefore succeeds legitimately, using the attacker's own webhook secret, for a payload the attacker fully controls.
2. `MembershipHandler#process` calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id)` [3](#0-2) . The `teams` table has no filter tying this lookup to `organization`; the only unique index is `["organization", "slug"]`, and `github_id` has no per-organization scoping at all [4](#0-3) . If `params.team.id` matches an existing row's `github_id` (a value the attacker controls in their own payload and can learn about a target team, e.g. via GitHub's team API or by having once observed it), `find_or_create_by!` returns that existing `Team`, regardless of which organization actually owns it.
3. `process` then executes `team.members.delete(member)` for `action == 'removed'` [5](#0-4) , deleting the `Membership` row joining the resolved (victim) `Team` to the named `User`.

Attacker request: attacker sends `POST /webhooks` with header `X-Github-Event: membership`, a valid `X-Hub-Signature` computed with their own org's webhook secret, and JSON body `{"action":"removed","team":{"id":<victim_team_github_id>,"name":...,"slug":...,"url":...},"organization":{"login":"attacker-org"},"member":{"login":"victim-operator"}}`. `verify_signature` passes because it authenticates only that `attacker-org`'s secret matches — it never confirms that `attacker-org` is the actual owner of team `<victim_team_github_id>`.

Existing guards do not stop this: `verify_signature` authenticates provenance of the org named in the payload, not authorization over the specific `team.id` referenced; `ExplicitParameters` only validates types/presence, not cross-field ownership; `drop_unhandled_event` only checks the event type is handled at all.

### Impact Explanation
An attacker who controls a legitimate GitHub organization (any organization with Shipit's app/webhook installed, satisfying `Shipit.github_teams`... note: actually any org configured with a webhook secret in `Shipit.github`, not necessarily one in `Shipit.github_teams`) can send a fully self-signed webhook that deletes an arbitrary `Membership` row for any `Team` whose `github_id` they can supply, deleting the row linking a legitimate operator (potentially a member of `Shipit.github_teams`) to their authorizing team. This is a cross-tenant mutation: a payload authenticated for one organization writes/deletes state belonging to a different organization's team, matching the "payload for one repository/org mutating another's ... team" Critical category. Per the prompt's explicit framing, this is scoped as unauthorized cross-tenant mutation, not availability/DoS, since it demonstrates the same unchecked-lookup primitive that (in the `added` branch) allows privilege escalation into `Shipit.github_teams`.

### Likelihood Explanation
Preconditions: the attacker needs (a) their own GitHub organization with Shipit webhooks configured (fully within attacker control, no secrets needed), and (b) knowledge of the numeric `github_id` of the victim team they want to attack (team IDs are visible to team members and via GitHub's team APIs/UI, not treated as secret by GitHub, though also not trivially enumerable by an outsider without some information disclosure). Attacker cost is a single crafted HTTP POST with a signature computed from their own known secret — trivial and fully repeatable against any team whose `github_id` becomes known.

### Recommendation
In `find_or_create_team!`, scope the lookup by both `github_id` and `organization` (matching `params.organization.login`), and refuse to mutate/delete membership on a `Team` whose stored `organization` does not equal the payload's verified `organization.login`. E.g., `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`, and additionally hard-fail (raise/drop) if an existing `Team` with that `github_id` exists under a different `organization`, rather than silently reusing it.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/membership_handler_test.rb`, not shown in scope but illustrating the required assertions):
```ruby
team = shipit_teams(:legit_team) # organization: 'victim-org', github_id: 4242
membership = Shipit::Membership.create!(team: team, user: shipit_users(:walrus))

payload = {
  'action' => 'removed',
  'team' => { 'id' => team.github_id, 'name' => team.name, 'slug' => team.slug, 'url' => team.api_url },
  'organization' => { 'login' => 'attacker-org' }, # different org than team.organization
  'member' => { 'login' => shipit_users(:walrus).login },
}

assert_difference -> { team.reload.members.count }, -1 do
  Shipit::Webhooks::Handlers::MembershipHandler.call(payload)
end
```
Both sides of the binding to assert: before, `team.organization == 'victim-org'` while the verified webhook organization is `'attacker-org'` (`'victim-org' != 'attacker-org'`); after the call, `Shipit::Membership.exists?(team: team, user: shipit_users(:walrus))` is `false`, proving a webhook authenticated for `attacker-org` mutated a `Membership` belonging to `victim-org`'s `Team`.
