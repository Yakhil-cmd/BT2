### Title
Asset definer can permanently freeze AA/user funds held in a `spender_attested` asset by replacing the attestor list - (File: `validation.js`, `storage.js`)

### Summary
Assets with `spender_attested: true` require both sender and all recipient addresses to be attested by the asset's *current* attestor list before any payment (including a payment made by an AA acting as escrow/exchange) is accepted. The attestor list is fully controlled by the asset definer and can be replaced at any time via an `asset_attestors` message. Because payment validation always re-resolves attestations against the *latest* attestor list rather than the one in effect when funds were received, the definer can retroactively invalidate previously valid attestations for an address (including an AA's own address), permanently preventing that address/AA from ever moving out the restricted-asset balance it already holds.

### Finding Description
When an asset has `spender_attested = true`, `storage.readAsset()` fetches only the most recent `asset_attestors` list for that asset: [1](#0-0) 
Attestations are then filtered against this *current* attestor set in `filterAttestedAddresses()`: [2](#0-1) 
During validation of any payment of that asset, the payment is rejected unless:
1. at least one author (the sender) is currently attested, and the issuer is attested for issues, `validation.js`: [3](#0-2) 
2. every single output address is currently attested, `validation.js`: [4](#0-3) 

The attestor list itself is defined solely by the asset definer and can be overwritten at will: [5](#0-4) 

There is no requirement that an address, once attested, stay attested: swapping the attestor list to a different attestor address (one that never attested the AA/user in question) instantly makes any address that was previously "attested" fall out of the current attested set, because `filterAttestedAddresses` only counts attestations issued by attestors that are in `objAsset.arrAttestorAddresses` — the *latest* list, not the list that was active when the address deposited funds.

This is directly analogous to the reported bug class: a restricted, off-protocol admin (here, the asset definer/attestor authority instead of a USDC/USDT admin) can unilaterally and unconditionally make previously-valid holders unable to move their balance, with no fallback mechanism built into the asset or the consuming AA logic. An AA that accepts a `spender_attested` asset (e.g., as part of an escrow, DEX, or fundraising flow such as `test/samples/fundraising_proxy.oscript`) has no privileged key and cannot work around a definer-controlled deny-list change: any outgoing payment of the asset from the AA is validated by the same rules and will be rejected once the AA's own address (or the intended recipient) is not attested by the new list, even though the AA had no code path to detect or react to that risk in advance.

### Impact Explanation
Funds of the restricted asset already deposited into any address — most importantly into an AA acting as an escrow/exchange/vault — can become permanently unspendable the moment the asset definer republishes the attestor list to exclude the AA's own address or the intended recipient. Since AAs are pure deterministic bytecode with no privileged "admin bypass," and ordinary user-controlled addresses also can't move the asset if they fall outside the newly published attestor set, the balance is frozen indefinitely with no on-protocol remedy. This matches "AA fund loss or freezing" impact criteria.

### Likelihood Explanation
`spender_attested` assets and the ability to update the attestor list via `asset_attestors` are standard, always-available protocol features usable by any asset definer — no special protocol trust or hard fork is required. Any AA author who accepts such an asset as payment (a plausible and even encouraged design for KYC/whitelisted-asset use cases) exposes itself and its users to this risk the first time the definer rotates attestors. The likelihood is Medium: it requires the specific combination of a `spender_attested` asset being used by an AA/other holder, and the definer changing the list (which could be malicious or simply an innocuous key-rotation/attestor-replacement event), but nothing in the protocol prevents or warns about it.

### Recommendation
- When checking `spender_attested` for a *transfer* (not issuance), consider allowing attestations that were valid under the attestor list in effect when the address most recently received the asset (i.e., pin attestor validity at receipt time), rather than always re-resolving against the newest list.
- Alternatively/additionally, document explicitly (and possibly warn in AA validation) that AAs holding `spender_attested` assets are exposed to definer-driven freezing, so AA authors can avoid or mitigate accepting such assets as durable AA balances.
- Consider disallowing removal of previously-attested addresses from being "un-attested" retroactively, e.g. by keeping a per-address "last known attested" snapshot rather than requiring live membership in the current attestor list on every subsequent payment.

### Proof of Concept
1. Definer creates asset A with `spender_attested: true`, `is_transferrable: true`, `attestors: [Attestor1]`, per `validateAssetDefinition` rules (`validation.js:2725-2827`).
2. `Attestor1` attests address `AA_addr` (an Autonomous Agent) and address `U1` (a user), satisfying `validation.js:2115-2122` and `validation.js:2630-2641` so that `U1 -> AA_addr` payments of asset A validate and are accepted, and the AA custodies the balance (e.g., as deposit/escrow logic).
3. Later, the definer posts `asset_attestors` with a brand-new `attestors: [Attestor2]` (per `validation.js:2829-2847`, only the definer's signature is required — no consent from AA or existing holders needed).
4. `Attestor2` never attests `AA_addr` (or `U1`).
5. Any subsequent attempt by the AA to send asset A back to `U1` (e.g., a refund/withdrawal response) is validated against the *current* attestor list only (`storage.js:1921-1946`, `storage.js:1960-1974`), so `filterAttestedAddresses` returns no attested addresses for `AA_addr`/`U1`, and `validation.js:2115-2122` / `2630-2641` reject the payment with "none of the authors is attested" / "some output addresses are not attested."
6. The AA has no mechanism to bypass this check (it is pure formula logic, not a privileged actor), so the asset A balance already held by `AA_addr` is permanently frozen.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
