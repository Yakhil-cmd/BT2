### Title
Webhook signature check keys on `repository.owner.login`, but handlers act on the independent `repository.full_name`/`sha` fields — cross-organization webhook forgery in multi-org installations - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects *which* GitHub App config (and therefore which `webhook_secret`) to verify the HMAC signature against, based solely on `params.dig('repository','owner','login')` (falling back to `params.dig('organization','login')`). Every event handler that subsequently runs (`PushHandler`, `StatusHandler`, pull-request handlers, etc.) independently re-reads other fields of the very same, attacker-supplied JSON body — `repository.full_name`, `sha`, `state`, etc. — to decide which `Repository`/`Stack`/`Commit` to mutate. Nothing ties the "owner" used to pick the verification secret to the "repository" that ends up written.

### Finding Description
In a multi-org Shipit installation (explicitly documented and supported, see `docs/setup.md` "Using Multiple Github Applications" and `lib/shipit.rb#github_app_config`), each GitHub organization has its own independent config, including its own `webhook_secret`, which can legitimately be blank/unset for some orgs (as shown in `config/secrets.development.shopify.yml` and `test/dummy/config/secrets_double_github_app.yml`, both configuring multiple orgs with `webhook_secret: # nil`).

`verify_signature` in [1](#0-0)  does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where `repository_owner` is read directly from the untrusted payload: [2](#0-1) .

`GitHubApp#verify_webhook_signature` trivially passes when that specific org has no configured secret: [3](#0-2) 
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
```

Once `verify_signature` passes, `create` dispatches the entire raw JSON to registered handlers for the event type: [4](#0-3) . Those handlers resolve the target `Repository`/`Stack`/`Commit` from a *different* field of the same payload than the one used for org selection, e.g.:
- `PushHandler` triggers a sync for stacks matching `ref`/`branch` on `stacks` scoped only by whatever the base `Handler` resolves — no cross-check against `repository_owner`: [5](#0-4) 
- `StatusHandler` writes a GitHub-style commit status onto any `Commit` matching `params.sha`, purely by SHA lookup, with no repository/owner check at all: [6](#0-5) 
- Pull-request handlers explicitly resolve the acted-upon repository from `params.repository.full_name`, independent of `repository_owner`: [7](#0-6) 

Because `repository_owner` (used to choose the verification secret) and the repository actually acted upon (`repository.full_name`, or in `StatusHandler`'s case, nothing at all beyond `sha`) are read from independent JSON keys in the same unauthenticated-until-verified body, an attacker can submit a payload where `repository.owner.login` names an organization configured in this Shipit instance with a blank `webhook_secret` (satisfying `verify_signature` trivially), while other fields (`sha`, or a `repository.full_name` belonging to a different, real organization's stack) target a stack/commit that has nothing to do with that unauthenticated org. This breaks the intended binding: *"the organization whose secret authenticated the request" should equal "the repository the handler is about to write to."*

### Impact Explanation
This crosses the "unauthorized write" boundary explicitly called out in scope: a request that never proves knowledge of the *target* organization's webhook secret can still, via a different, weakly-configured org's identity, cause the `StatusHandler` to fabricate/overwrite commit-status webhook state (`Commit#create_status_from_github!`) on any commit by SHA regardless of org, which can flip `deployable?`/CI-blocking checks used to gate deploys and merges (`MergeRequest#reject_unless_mergeable!`, `all_status_checks_passed?`), or cause `PushHandler`/pull-request handlers to trigger `GithubSyncJob`s, archive/unarchive review stacks, or manipulate merge-queue state for stacks belonging to organizations the attacker never authenticated against. This can lead to unauthorized deploys/merges being enabled by forged CI status, satisfying the "unauthorized deploy, rollback, or merge" bar in scope.

### Likelihood Explanation
Requires only that the Shipit instance is configured with more than one GitHub organization (a documented, supported configuration) and that at least one of those organizations has no `webhook_secret` set — a state the repository's own example/dev configs demonstrate is a normal, even encouraged (optional secret) setup. No GitHub App private key, session, or `ApiClient` token is needed; the attacker only POSTs directly to the public `/webhooks` endpoint.

### Recommendation
Bind the verified organization to the exact repository/stack acted upon: after `verify_signature` succeeds, re-derive the acting `Repository`/`Stack` using the same `repository_owner`/org used for verification (or the resolved `GitHubApp`'s configured organization) and reject the event if `repository.full_name`'s owner (or, for `StatusHandler`, the `Commit`'s `Stack`'s `Repository#owner`) does not match. Consider requiring `webhook_secret` to be mandatory for any multi-org configuration, or scoping the HMAC verification key strictly to the org actually referenced by every field consumed by the eventual handler, not just the one used to pick the secret.

### Proof of Concept
1. Deploy a Shipit instance configured with two GitHub orgs, e.g. mirroring `test/dummy/config/secrets_double_github_app.yml`: `OrgOne` (no `webhook_secret`) and `OrgTwo` (has stacks with real commits/CI gating).
2. POST to `/webhooks` with header `X-Github-Event: status` and a body:
```json
{
  "repository": { "owner": { "login": "OrgOne" }, "full_name": "OrgOne/throwaway" },
  "sha": "<sha of a real commit belonging to an OrgTwo-owned stack>",
  "state": "success",
  "context": "ci/required-check"
}
```
No valid `X-Hub-Signature` is required because `Shipit.github(organization: "OrgOne").verify_webhook_signature` returns `true` immediately (`webhook_secret` blank).
3. `StatusHandler#process` looks up `Commit.where(sha: params.sha)` — which matches the OrgTwo commit — and calls `create_status_from_github!`, forging a passing CI status for a repository/org the attacker never authenticated against, potentially unblocking that commit for deploy/merge.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
