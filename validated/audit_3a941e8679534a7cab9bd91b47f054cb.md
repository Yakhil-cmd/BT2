Confirmed: `deriveAddress` in `wallet_defined_by_keys.js:544-570` builds every co-signer's `$pubkey@device_address` slot from **all** rows currently present in `extended_pubkeys` for that `wallet`, and `addDeviceXPubKey` (the handler for the `my_xpubkey` network message, explicitly whitelisted "allowed from non-correspondents") writes into that same table keyed only by `wallet` + `device_address` derived from the sender's pubkey, with no check that `from_address` is one of the device addresses that were actually assigned to this wallet's signing paths at creation time (`wallet_signing_paths`, populated once in `addWallet`). This is analogous to the kernel bug: a persistent identifier (the `wallet` id / durable handle) can be "reconnected to" (populated with cosigner data) by any sender who merely knows the id, without validating that the sender is the identity that was actually assigned that role when the resource was created.

### Title
Missing validation that a `my_xpubkey`/`wallet_fully_approved` sender is an actual assigned cosigner of the target wallet - ([File: wallet_defined_by_keys.js])

### Summary
`device.js` explicitly allows the `my_xpubkey` and `wallet_fully_approved` device-message subjects to be processed from **non-correspondents** [1](#0-0) , and `wallet.js` routes them straight into `walletDefinedByKeys.addDeviceXPubKey`/`handleNotificationThatWalletFullyApproved` using only the cryptographically-verified `from_address` of the sender, with no check that this device is one of the co-signers originally enumerated for the target `wallet` [2](#0-1) .

### Finding Description
A multi-device/multisig `wallet` is a persistent object identified by a hash (`wallet` id) that is fixed once at creation together with the exact set of authorized co-signer `device_address`es, stored in `wallet_signing_paths` [3](#0-2) . Analogous to the durable-handle CVE, where the server should verify that a reconnecting client is the same identity that originally opened the handle, ocore should verify that any device sending wallet-membership state (`my_xpubkey`, `wallet_fully_approved`) for a given `wallet` id is one of the addresses recorded as a legitimate member of that wallet.

Instead, `addDeviceXPubKey` performs an unconditional `INSERT ... IGNORE INTO extended_pubkeys (wallet, device_address)` followed by an `UPDATE ... SET extended_pubkey=?` keyed only on `(wallet, device_address)` supplied by the message [4](#0-3) . There is no join/check against `wallet_signing_paths` to confirm `device_address` (i.e., `from_address`) was ever assigned a signing path in that wallet. Likewise `handleNotificationThatWalletFullyApproved` blindly inserts/updates the `member_ready_date` for the caller-supplied `device_address` [5](#0-4) .

Because `deriveAddress` derives every multisig output address by iterating over **all rows currently in `extended_pubkeys` for that wallet** and substituting `$pubkey@device_address` in the wallet's definition template [6](#0-5) , and `checkAndFullyApproveWallet`/`checkAndFinalizeWallet` decide wallet readiness by checking whether every row currently joined to the wallet has `approval_date`/`member_ready_date` set [7](#0-6) , an attacker who merely learns/guesses a target `wallet` id (transmitted openly in multiple device messages such as `create_new_wallet`) can inject `(wallet, my_device_address, attacker_xpubkey)` and cause the wallet-approval bookkeeping to be manipulated without ever being a real assigned member (`wallet_signing_paths` is untouched, but bookkeeping tables governing approval completion are polluted). This directly parallels the CVE's root cause: state that should only be mutated by the original owner (of the durable handle / wallet slot) can be mutated by any unauthorized identity because ownership is never re-validated on the persistent identifier.

### Impact Explanation
This can corrupt the approval/readiness state of a co-signed wallet shared with other devices (premature "wallet_completed" events, spurious cosigner rows returned by `readCosigners`, which throws only if the injected address happens to have no `correspondent_devices` entry, and otherwise silently pollutes cosigner metadata used before wallet completion), leading to node/wallet disagreement about which multisig wallet is ready to receive/spend funds and potential fund-freezing/loss scenarios for the legitimate cosigners who rely on `full_approval_date`/`ready_date` to decide when the shared address can safely receive or release funds.

### Likelihood Explanation
The `wallet` id is a base64 SHA-256 hash of the creator's initial xpubkey [8](#0-7)  and is not secret — it is transmitted in plaintext device messages (`create_new_wallet`, `my_xpubkey`, `wallet_fully_approved`) to intended cosigners over the hub, and an attacker device does not need to be a correspondent of the victim to send `my_xpubkey`/`wallet_fully_approved` (explicitly whitelisted). Any attacker who observes or is told a wallet id (e.g., an indirect participant, a device that was later removed as a cosigner, or one that intercepts the id through any channel) can immediately send these messages.

### Recommendation
In `addDeviceXPubKey` and `handleNotificationThatWalletFullyApproved`, before inserting/updating `extended_pubkeys`, verify that `wallet_signing_paths` (or the wallet's `definition_template`) actually designates `device_address` as an assigned member of `wallet`; reject the update otherwise. Consider also re-validating on every step of `checkAndFullyApproveWallet`/`checkAndFinalizeWallet` that only rows corresponding to `wallet_signing_paths.device_address` are counted.

### Proof of Concept
1. Attacker device (unpaired, not a correspondent) learns/observes a victim's multisig `wallet` id (e.g., relayed in a `create_new_wallet` offer to a third co-signer, or leaked via any chat/paste).
2. Attacker sends a device message `{subject: "my_xpubkey", body: {wallet: "<observed_wallet_id>", my_xpubkey: "<attacker_xpubkey>"}}` to the victim device. Because `my_xpubkey` is in `arrSubjectsAllowedFromNoncorrespondents`, it is processed even though attacker is not a correspondent [1](#0-0) .
3. `wallet.js`'s handler calls `walletDefinedByKeys.addDeviceXPubKey(body.wallet, from_address, body.my_xpubkey, callbacks.ifOk)` with no membership check [9](#0-8) .
4. `addDeviceXPubKey` inserts a row into `extended_pubkeys` for `(wallet, attacker_device_address)` and marks `approval_date` [4](#0-3) , corrupting the wallet's cosigner/approval bookkeeping despite the attacker never having been assigned to `wallet_signing_paths` for this wallet.

**Uncertainty**: I could not fully trace whether a downstream flow uses `extended_pubkeys` rows directly to authorize a *spend* (vs. bookkeeping/derivation only) beyond `deriveAddress`'s address-definition substitution, since `deriveAddress`'s template substitution for a device_address that isn't referenced in `arrDefinitionTemplate` would simply be an unused parameter (not necessarily change the derived address itself, since `Definition.replaceInTemplate` only substitutes placeholders that exist in the template). The concretely provable impact is corruption of wallet approval/readiness state and cosigner bookkeeping (`readCosigners`, `checkAndFullyApproveWallet`, `checkAndFinalizeWallet`), which can cause node/wallet disagreement on wallet completion status; a full path to unauthorized fund movement would require further confirmation of how `full_approval_date`/`ready_date` gate actual spend/receive logic, which I was not able to verify within the available context.

function checkAndFinalizeWallet(wallet, onDone){
	db.query("SELECT member_ready_date FROM wallets LEFT JOIN extended_pubkeys USING(wallet) WHERE wallets.wallet=?", [wallet], function(rows){
		if (rows.length === 0){ // wallet not created yet or already deleted
		//	throw Error("no wallet in checkAndFinalizeWallet");

			return onDone ? onDone() : null;
		}
		if (rows.some(function(row){ return !row.member_ready_date; }))
			return onDone ? onDone() : null;

			if (onDone)

function checkAndFullyApproveWallet(wallet, onDone){
	db.query("SELECT approval_date FROM wallets LEFT JOIN extended_pubkeys USING(wallet) WHERE wallets.wallet=?", [wallet], function(rows){
		if (rows.length === 0) // wallet not created yet
			return onDone ? onDone() : null;
		if (rows.some(function(row){ return !row.approval_date; }))
			return onDone ? onDone() : null;
		db.query("UPDATE wallets SET full_approval_date="+db.getNow()+" WHERE wallet=? AND full_approval_date IS NULL", [wallet], function(){
			db.query(
				"UPDATE extended_pubkeys SET member_ready_date="+db.getNow()+" WHERE wallet=? AND device_address=?",

				function(){
					db.query(
						"SELECT device_address FROM extended_pubkeys WHERE wallet=? AND device_address!=?",

							// let other members know that I've collected all necessary xpubkeys and ready to use this wallet

							});
							checkAndFinalizeWallet(wallet, onDone);

		});
	});
