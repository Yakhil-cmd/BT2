### Title
Webhook signature is verified against the payload's `repository.owner.login` while the acted-upon record is resolved from `repository.full_name`, letting a webhook signed with one org's secret write to another org's stack - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification from a field taken directly out of the unauthenticated JSON body (`repository.owner.login`, falling back to `organization.login`), then, once verification "succeeds," hands the very same untrusted body to event handlers that resolve the target `Stack`/`Repository` from a *different* field of the same body (`repository.full_name`). Nothing ties these two fields together, so the org whose secret authenticated the request is not enforced to be the org whose data gets mutated. [1](#0-0) 

### Finding Description
`verify_signature` picks the signing org purely from attacker-controlled JSON: [2](#0-1) [3](#0-2) 

It calls `Shipit.github(organization: repository_owner)` and verifies the raw body against *that* organization's `webhook_secret`: [4](#0-3) 

Once `head(422)` is not triggered, `create` dispatches the full, attacker-supplied JSON to the registered handlers for the event type: [5](#0-4) 

Handlers such as `PushHandler` resolve the target `Stack` using `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))` — a completely separate field from the one used to select the verification secret: [6](#0-5) [7](#0-6) [8](#0-7) 

Shipit explicitly supports multiple, independently-secreted GitHub Apps/organizations sharing one instance (documented multi-tenant configuration), and the app already ships fixtures showing two distinct organizations/stacks (`shipit` and `cyclimse`) coexisting behind one webhook endpoint: [9](#0-8) [10](#0-9) 

Because the two lookups (verification-org vs. acted-upon-repository) are independent, a tenant who legitimately controls one onboarded organization (and therefore genuinely knows/controls that organization's own `webhook_secret`, since they configured the GitHub App on their own org) can POST a forged, self-signed payload where:
- `repository.owner.login` (or `organization.login`) = their own org → passes `verify_signature` using their own real secret,
- `repository.full_name` = `"<victim-org>/<victim-repo>"` → resolved by the handler to act on another tenant's `Stack`.

This breaks the intended binding "organization that authenticated == repository that is written," letting one tenant's traffic mutate another tenant's stack state without ever knowing the victim's `webhook_secret`.

### Impact Explanation
Depending on event type, the forged payload can be routed to any registered handler and reach a victim stack that the attacker has no legitimate access to:
- `push`: forces `GithubSyncJob` to resync a victim stack up to an attacker-chosen `expected_head_sha`, mutating the victim's commit list/cache state. [11](#0-10) 
- `status`: creates/attaches arbitrary commit statuses on victim commits, which feed the merge-queue "ready to ship" gating logic. [12](#0-11) 
- `pull_request` events (opened/closed/(un)labeled): create, archive, or unarchive Review Stacks belonging to the victim repository via `Repository.from_github_repo_name(params.repository.full_name)`. [13](#0-12) 

This is a cross-repository/cross-tenant write triggered without possessing the victim's webhook secret, which matches the "cross-repository writes" / merge-queue-influencing High-Critical impact criteria in scope.

### Likelihood Explanation
Exploitability requires the attacker to legitimately control at least one organization/GitHub App already onboarded to the shared Shipit instance (a documented, supported multi-org configuration). No access to the victim's secrets, session, or repository is needed — only the attacker's own, self-controlled webhook secret and the ability to send an HTTP POST to the shared `/webhooks` endpoint with a crafted body. This is realistic in any Shipit deployment onboarding more than one organization/team, which the codebase's own test fixtures and docs demonstrate as a supported topology.

### Recommendation
After verifying the HMAC, re-derive and enforce the acted-upon repository/organization strictly from the same trusted field used for verification (or verify that `repository.full_name`'s owner segment matches `repository_owner`) before dispatching to handlers. Alternatively, verify the signature per-repository (looking up the `Repository`/`Stack` from `full_name` first, then verifying with that repository's own configured organization secret) so the two lookups can never diverge.

### Proof of Concept
1. Onboard/attacker-control organization `cyclimse` on a shared Shipit instance (has its own real `webhook_secret`, per `github_hooks.yml`/`docs/setup.md` multi-org config).
2. Craft a `push` webhook body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker_chosen_sha>",
  "repository": {
    "full_name": "Shopify/shipit-engine",
    "owner": { "login": "cyclimse" }
  }
}
```
3. Compute `X-Hub-Signature` using `cyclimse`'s real (attacker-known) `webhook_secret`, set `X-Github-Event: push`, and POST to `/webhooks`.
4. `verify_signature` calls `Shipit.github(organization: "cyclimse")` and succeeds because the body was actually signed with `cyclimse`'s secret.
5. `PushHandler` resolves `Repository.from_github_repo_name("Shopify/shipit-engine")` and enqueues `GithubSyncJob` against Shopify's stack — a repository the attacker's org has no relationship to.

Note: I could not find any additional cross-check elsewhere in `app/**`/`lib/shipit/**` (e.g., in `Handler`, `Repository`, or job classes) that ties the verified organization back to the repository being mutated; the binding appears to be missing throughout the webhook dispatch path.

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
