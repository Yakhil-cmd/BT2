### Title
Cross-repository CI status forgery via global commit-sha lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler` updates commit CI status by looking up commits **only by SHA, globally across the entire database**, and never checks that the SHA actually belongs to the repository named in the webhook payload that was HMAC-verified. This breaks the trust binding "organization/repository whose webhook signature was verified" ≟ "repository whose tracked commit status gets mutated," letting a status event delivered for one repository silently flip CI state on a commit that is also tracked under a completely different Stack/repository (e.g. via a fork sharing identical commit SHAs), potentially unblocking merges/deploys that depend on required status checks.

### Finding Description
`WebhooksController#verify_signature` only proves that the raw JSON body was signed with the secret belonging to the organization named in the payload (`repository.owner.login` / `organization.login`): [1](#0-0) 

That is the only binding the signature check establishes — it says nothing about which specific repository's data may be mutated once the payload is dispatched to a handler.

For most events, the base `Handler` class re-derives the target `Stack`s by scoping through `Repository.from_github_repo_name(repository_name)`, tying processing back to the `repository.full_name` field of the (now-verified) payload: [2](#0-1) 

`StatusHandler`, however, never calls `stacks` / `repository_name` at all. It parses only `sha`, `state`, and related fields, and updates **every** `Commit` record in the entire application matching that `sha`, irrespective of which repository the webhook actually came from: [3](#0-2) 

Because Git commit SHAs are content-addressed and identical across forks/clones of the same history, a `status` event that is legitimately and validly signed for **repository A** (e.g. a fork) can carry a `sha` that is identical to a commit Shipit also tracks under an unrelated **Stack B** (e.g. the upstream repository). `StatusHandler#process` will happily apply the status to `Stack B`'s commit, even though the verified signature only vouches for repository A's organization.

This is a direct binding break of the kind described in the report's abstracted rule: *"a payload field acted on but never covered by the verified signature"* — here, the `repository`/stack-scoping field is present in the signed payload but is never consulted by the handler that actually performs the mutation.

### Impact Explanation
Commit CI/status state feeds directly into merge and deploy gating logic:
- `MergeRequest#reject_unless_mergeable!` relies on `any_status_checks_missing?` / `any_status_checks_failed?`, both built on `StatusChecker.new(head, head.statuses_and_check_runs, ...)`. [4](#0-3) 
- `Stack#branch_status` walks `undeployed_commits` and uses each commit's `status.simple_state` to decide whether the stack is deployable. [5](#0-4) 

If an attacker can forge a "success" status on a shared commit SHA from a repository they control (any fork covered by the same GitHub App/org webhook configuration), they can make Shipit believe required CI checks passed on the real tracked repository's commit, clearing the way for an automatic merge via the merge queue or an automatic/continuous deploy — an unauthorized ship, which is the Critical-tier impact defined for this engine.

### Likelihood Explanation
Exploitation requires the attacker to be able to trigger a validly-signed `status` webhook for *some* repository whose organization Shipit trusts (i.e., a repository within an org/app installation Shipit is configured for), and for that repository to share a commit SHA with the targeted tracked repository — trivially true for a fork of the tracked repository, since forks inherit identical commit history/SHAs. No Shipit session, API token, or deploy privilege is required; only the ability to set a commit status on a repository under an org already integrated with Shipit (e.g. by pushing a status via a personal access token/CI on one's own fork). This is a realistic path for any org member/contributor who is not a `Shipit.github_teams`-authorized deployer.

### Recommendation
Scope `StatusHandler#process` the same way the base `Handler` scopes other events: resolve the target `Stack`/`Repository` from `payload.dig('repository', 'full_name')` first, and only update `Commit` records that belong to that repository's stacks, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` instead of the unscoped `Commit.where(sha: params.sha)`.

### Proof of Concept
1. Shipit tracks `Stack` for `upstream/repo`, which has commit `SHA_X` with a `pending`/missing required status check blocking merge/deploy.
2. Attacker (an org member with no Shipit deploy privileges) forks `upstream/repo` into `attacker/repo` within the same GitHub org/app installation that Shipit trusts; the fork contains the identical commit `SHA_X`.
3. Attacker sets a `success` status on `SHA_X` in `attacker/repo` via the GitHub Statuses API (they own the fork, no special access to `upstream/repo` needed).
4. GitHub delivers a `status` webhook to Shipit, signed with the (legitimately known) secret for that org — signature verification in `WebhooksController#verify_signature` passes.
5. `StatusHandler#process` executes `Commit.where(sha: 'SHA_X')`, which matches the commit belonging to `upstream/repo`'s `Stack`, and records the forged `success` status against it.
6. `upstream/repo`'s Stack now reports the commit as CI-passing, allowing an unauthorized merge/deploy to proceed for a repository the attacker never had write access to.

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
