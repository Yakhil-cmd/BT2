### Title
`Api::CCMenuController#stack` bypasses the ApiClient stack scope, letting a stack-scoped token read any stack's build/deploy state - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Api::CCMenuController` overrides the `stack` lookup method used by `Api::BaseController` and, in doing so, drops the scoping that restricts a stack-bound `ApiClient` token to the single stack it was issued for. This breaks the invariant "the stack a token authorizes == the stack it touches," the same class of parameter/scope-substitution bug as the reported `Tranche::redeem` issue, where a value meant to be validated/scoped for one specific target ends up being used against an arbitrary one.

### Finding Description
`Api::BaseController` enforces per-token stack scoping through two cooperating methods: [1](#0-0) 

`stacks` restricts the resolvable set to `Stack.where(id: current_api_client.stack_id)` when the authenticated `ApiClient` has a `stack_id`, and `stack` resolves the requested `params[:stack_id]` only within that restricted relation via `stacks.from_param!(...)`. This is the binding that guarantees a stack-scoped token can only ever resolve to its own stack.

`Api::CCMenuController`, which also inherits from `BaseController` and requires only `read:stack` permission, redefines `stack` to bypass this scoping entirely: [2](#0-1) 

Here `Stack.from_param!(params[:stack_id])` is called directly against the full `Stack` relation, ignoring `current_api_client.stack_id`. `ApiClient#check_permissions!` only checks the permission string (`read:stack`), never the `stack_id` association: [3](#0-2) 

So a token that was created scoped to one stack (e.g. fixture `here_come_the_walrus`, scoped to `shipit`) authenticates successfully and passes the `read:stack` permission check, but the actual stack object it operates on is chosen from `params[:stack_id]` with no relation to the token's `stack_id`. This is structurally the same defect pattern as the report: `redeem`'s `shares` parameter was routed into `withdraw`'s `assets` code path, using the wrong semantic binding; here, a token whose authorization is defined by `stack_id` is routed into a stack lookup that ignores `stack_id`, using the wrong semantic binding (a purely user-supplied `params[:stack_id]`).

The token can also be supplied via the query string, not just via `Authorization` header/`ApiClient` model: [4](#0-3) 

### Impact Explanation
Any holder of a legitimately-issued, single-stack-scoped `read:stack` token (e.g. a CCMenu token minted by `CCMenuUrlController` for one stack, as seen in `app/controllers/shipit/ccmenu_url_controller.rb`) can request `/api/stacks/:stack_id/ccmenu.xml?token=...` for **any other stack id** in the deployment and receive that stack's build/deploy status (last deploy id, running/failed state, lock status) — information the token was never authorized to see. This is a cross-stack authorization-scope violation: the invariant "stack authorized by token == stack actually returned" is broken, matching the "stack a token authorises versus a stack it touches" binding called out in the analog rules. It amounts to unauthorized read of stack state across stack boundaries using a token that is legitimately scoped to a different, unrelated stack.

### Likelihood Explanation
Exploitation requires only possession of any valid stack-scoped `read:stack` ApiClient token (routinely generated and even embedded in URLs by `CCMenuUrlController`), and knowledge/guessing of another stack's `stack_id` param (stack slugs are `owner/repo/branch`-style identifiers, often predictable or discoverable via the stacks list UI). No signature, private key, or elevated privilege is needed beyond a token that would normally only grant visibility into one stack.

### Recommendation
Make `Api::CCMenuController#stack` honor the same scoping as the base controller instead of querying `Stack` directly, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
reusing the inherited `stacks` helper (or equivalently checking `current_api_client.stack_id.nil? || current_api_client.stack_id == resolved_stack.id`) so a stack-scoped token can never resolve a stack outside its authorized scope.

### Proof of Concept
1. Create/obtain an `ApiClient` scoped to `stack_a` with `read:stack` permission (as fixture `here_come_the_walrus` demonstrates, or as minted by `CCMenuUrlController#fetch`).
2. As an attacker holding this token, request:
   `GET /api/stacks/<other_org>/<other_repo>/<other_branch>/ccmenu.xml?token=<stack_a-scoped-token>`
3. Observe the response returns build/deploy status XML for the unrelated `stack_b`, even though the token's `stack_id` is bound to `stack_a` and `check_permissions!` never validates that association — confirmed by tracing `Api::CCMenuController#stack` (`app/controllers/shipit/api/ccmenu_controller.rb:29-31`) directly calling `Stack.from_param!` instead of the scoped `stacks.from_param!` used everywhere else in `Api::BaseController` (`app/controllers/shipit/api/base_controller.rb:74-80`).
