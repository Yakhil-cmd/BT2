## Analysis

The CVE describes an installer that copies a sensitive secret (LUKS keyfile, normally mode `0600`) into a globally-readable file, allowing any local user to read the secret and decrypt protected data.

The analogous bug class in `ocore--019` is writing a secret that grants control over funds to disk without restrictive permissions, using the default (world-readable) file mode.

### Vulnerable code

`wallet.js`'s `storePrivateAssetPayload` function serializes the **textcoin mnemonic** (the private key material from which the claiming address and its signing key are derived, via `expandMnemonic`) together with the private payment chains (which include amounts, blinding factors, and addresses needed to claim the asset), and persists them to disk using an unrestricted `fs.writeFile`: [1](#0-0)

`fs.writeFile` is called with no `mode` option, so Node.js defaults to `0o666` (masked by the process umask, typically resulting in world- or group-readable `0644` on most systems). This is exactly analogous to the Calamares bug: a secret that should be tightly protected (`0600`-equivalent) is instead written with default, broadly-readable permissions.

This function is invoked from the private-payment sending path in `sendMultiPayment`, whenever a user sends a private asset as an unpaired "textcoin" and supplies `opts.getPrivateAssetPayloadSavePath`: [2](#0-1) 

The `mnemonic` here is the same value used by `expandMnemonic` to derive the spending private key/address for the textcoin: [3](#0-2) 

Notably, elsewhere in the codebase the project explicitly hardens app-data directories to `0700` for sensitive local storage (e.g., the RocksDB key-value store directory): [4](#0-3) 

This shows restrictive permissions are the project's intended practice for sensitive local files, making the unrestricted `fs.writeFile` in `storePrivateAssetPayload` an inconsistency/oversight rather than a deliberate design choice.

### Title
Unrestricted file permissions on saved private-textcoin payload disclose spending mnemonic - (File: wallet.js)

### Summary
`storePrivateAssetPayload` in `wallet.js` writes a zip file containing the textcoin `mnemonic` and its private payment chains to an arbitrary user-supplied path using `fs.writeFile` without specifying a restrictive file mode, resulting in a world/group-readable file (default `0666` masked by umask, typically `0644`).

### Finding Description
When a wallet user sends a private asset as a textcoin to an unpaired recipient, `sendMultiPayment`'s `preCommitCb` calls `storePrivateAssetPayload(fullPath, cordovaPathObj, mnemonic, arrChainsOfRecipientPrivateElements, ...)` [5](#0-4) . That function zips `{mnemonic, chains}` and writes it via `fs.writeFile(fullPath, zipFile, cb)` with no mode argument [6](#0-5) . The `mnemonic` is exactly the secret from which `expandMnemonic` derives the private key (`xPrivKey`) and address controlling the funds locked to that textcoin [7](#0-6) . Any co-resident process or user on the same machine/filesystem with default read access to the destination directory can read this file and reconstruct the private key, exactly mirroring the CVE's pattern of copying a protected secret (LUKS keyfile, `0600`) into a globally readable location.

### Impact Explanation
Exposure of the mnemonic file lets any local reader derive the private key and address for the private textcoin's funds and claim/spend them before the intended recipient, i.e., theft of funds (unauthorized spending) equivalent to concrete financial loss for the sender/intended recipient.

### Likelihood Explanation
This is triggered on every ordinary use of the "save private asset payload to a file" flow when sending private textcoins to unpaired recipients — no attacker interaction is required beyond ordinary shared-machine or shared-storage access (e.g., mobile device app storage, shared desktop `/tmp`, cloud-synced folder), which is a common real-world condition.

### Recommendation
When writing the private payload file, explicitly set restrictive permissions, e.g. `fs.writeFile(fullPath, zipFile, { mode: 0o600 }, cb)`, matching the restrictive mode already used for the app's sensitive data directories elsewhere in the codebase (see `kvstore.js`).

### Proof of Concept
1. User A sends a private asset via `sendMultiPayment` as a textcoin, with `opts.getPrivateAssetPayloadSavePath` returning a path on a shared/multi-user filesystem or synced folder.
2. `storePrivateAssetPayload` writes the zip containing `mnemonic` and `chains` with default permissions (world/group readable).
3. Any other local user or process with read access to that path opens the file, extracts `mnemonic`, calls the same `expandMnemonic` logic to derive the private key, and claims the asset via `receiveTextCoin` before the intended recipient does.
