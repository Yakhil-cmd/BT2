## Analysis

The reported bug describes an unbounded, non-linear fee (`getSlippageFee`) that scales with trade size and can approach 100% of the traded value, with no protocol-level cap to prevent the loss. The closest analog in ocore is the **oversize fee** mechanism, which grows *exponentially* with the extra size of a unit and is applied to real coin balances (including AA-held funds), without any consensus-level cap.

`storage.getOversizeFee` computes the fee as an exponential function of unit size relative to `threshold_size`: [1](#0-0) 

This fee is deducted directly from the payer's inputs and is enforced as mandatory during payment balance validation for base-asset payments — `total_input` must equal `total_output + headers_commission + payload_commission + oversize_fee + tps_fee + burn_fee + vote_count_fee`, with no upper bound check on `oversize_fee` relative to the payment amount: [2](#0-1) 

The wallet-side composer (used for user-initiated transactions) is aware of the risk and defends against it: after building the unit, it explicitly checks that `oversize_fee + tps_fee` does not exceed `max_fee_ratio` times the base fees, and aborts composition otherwise: [3](#0-2) 

However, `aa_composer.js`, which builds and sends payment units autonomously in response to AA triggers (a path directly reachable by any unprivileged AA trigger sender), computes and applies `oversize_fee` via `storage.getOversizeFee` but contains **no equivalent `max_fee_ratio` (or any) cap check** before finalizing and validating the unit: [4](#0-3) 

Grepping the codebase confirms `max_fee_ratio` only appears in `wallet.js`, `composer.js`, `divisible_asset.js`, and `indivisible_asset.js` — never in `aa_composer.js`, which is the module responsible for AA-generated payments.

### Title
Unbounded exponential oversize fee can consume AA balances during AA-generated payments — ([File: aa_composer.js])

### Summary
AA trigger senders can cause an Autonomous Agent to compose response payments whose size (via bounce messages, oversized data payloads, or many outputs) pushes `headers_commission + payload_commission` far above `threshold_size`. Because `oversize_fee` grows exponentially with excess size via `storage.getOversizeFee`, and `aa_composer.js` applies this fee to the AA's payment without any `max_fee_ratio`-style cap (unlike the wallet composer), the resulting fee can consume a large fraction — or effectively all — of the value being transferred/held by the AA, with no protocol-level revert to protect the AA's funds.

### Finding Description
`storage.getOversizeFee` computes `Math.ceil(size * (exp(size/threshold_size - 1) - 1))`, an exponential (not linear) function of the amount by which a unit's size exceeds `threshold_size` (default 10000 bytes per `initial_votes.js`). [5](#0-4)  When AAs send response payments (base-asset), `aa_composer.js`'s `sendUnit`/`completePaymentPayload` logic computes this fee via `storage.getOversizeFee(objUnit, last_ball_mci, true)` and folds it into the required output amount, deducting it from AA funds during input/output balancing: [6](#0-5)  and finalizes it at unit completion: [7](#0-6) .

Unlike the ordinary wallet path in `composer.js`, which explicitly guards against this by rejecting the composed unit if `additional_fees > max_ratio * size_fees` [8](#0-7) , `aa_composer.js` has no analogous check. The consensus-level validation in `validatePaymentInputsAndOutputs` merely requires the balance equation to hold exactly (`total_input === total_output + ... + oversize_fee + ...`) and never rejects a unit for having a disproportionate `oversize_fee` [2](#0-1) . Any bounce message, growth in `messages`, embedded data, or growing output list an AA composes in response to a trigger (which an unprivileged trigger sender can influence, e.g. via message size, number of outputs, or embedded data in the trigger unit consumed by the AA formula) can push unit size well past `threshold_size`, and the exponential growth means even a moderate overshoot produces a fee comparable to or exceeding the transferred amount.

### Impact Explanation
Since the fee is exponential in the size overshoot, an attacker who can influence how large an AA's response unit becomes (through trigger data, causing bounce messages, or driving the AA to emit many outputs/messages) can cause the AA to burn a disproportionate share of its own balance or of funds meant for a payout, without any circuit breaker. This directly parallels the H-09 finding: a fee formula whose growth is unbounded relative to the value moved, applied without a protocol-enforced ceiling for this reachable path — leading to AA fund loss for legitimate trigger interactions or facilitating a denial-of-funds/griefing attack against AAs that process user-supplied data of variable size.

### Likelihood Explanation
`aa_composer.js`'s trigger handling is reachable by any address that can send a trigger unit to an AA (an unprivileged action). Any AA whose response size depends even partly on trigger-controlled data (e.g., data payloads, dynamic bounce messages, or output counts influenced by user input) is exposed. The absence of the `max_fee_ratio` guard that exists in the ordinary wallet path (present specifically to prevent exactly this class of loss) strongly suggests this is an overlooked gap rather than an intentional design choice, increasing confidence this is a genuine oversight.

### Recommendation
Add the same (or an AA-appropriate) `max_fee_ratio`/absolute cap check used in `composer.js` to `aa_composer.js`'s `sendUnit`, comparing `oversize_fee` (and `tps_fee`, if applicable) against the base `headers_commission + payload_commission`, and bounce/fail the trigger response instead of completing the unit when the ratio is exceeded, mirroring the protection already present in `composer.js`. [3](#0-2) 

### Proof of Concept
Conceptual reachable path (exact PoC values require live threshold_size/testnet parameters, not verifiable purely from static review):
1. An attacker sends a trigger unit to a target AA whose formula echoes back trigger-supplied data (e.g., large `data` message content, or produces many response messages/outputs proportional to trigger input) causing the AA's composed response unit's `headers_commission + payload_commission` to exceed `threshold_size` (10000, per `initial_votes.js` line 35) substantially.
2. `aa_composer.js` computes `storage.getOversizeFee(objUnit, last_ball_mci, true)` on the oversized unit [9](#0-8) ; due to the exponential term `exp(size/threshold_size - 1) - 1`, doubling the overshoot size roughly squares the fee growth factor.
3. The AA's payment inputs are consumed to cover this fee with no `max_fee_ratio` check preventing the unit from being finalized, unlike in `composer.js`. [3](#0-2) 
4. `validatePaymentInputsAndOutputs` accepts the unit as long as the balance equation holds, regardless of how disproportionate `oversize_fee` is to the transferred value. [2](#0-1)

function getOversizeFee(objUnitOrSize, mci, bAA) {
	let size;
	if (typeof objUnitOrSize === "number")
		size = objUnitOrSize; // must be already without temp data fee
	else if (typeof objUnitOrSize === "object") {
		if (!objUnitOrSize.headers_commission || !objUnitOrSize.payload_commission)
			throw Error("no headers or payload commission in unit");
		// AA-generated units pay the oversize fee based on the unit size excluding its payment messages to avoid swelling the fee while spending dust outputs
		const payload_commission = (bAA && mci >= constants.pemCurvesFixMci)
			? objectLength.getTotalPayloadSize({ ...objUnitOrSize, messages: objUnitOrSize.messages.filter(message => message.app !== 'payment') })
			: objUnitOrSize.payload_commission;
		size = objUnitOrSize.headers_commission + payload_commission - objectLength.getPaidTempDataFee(objUnitOrSize);
	}
	else
		throw Error("unrecognized 1st arg in getOversizeFee");
	const threshold_size = getSystemVar('threshold_size', mci);
	if (size <= threshold_size)
		return 0;
	return Math.ceil(size * (exp(size / threshold_size - 1) - 1));
}
