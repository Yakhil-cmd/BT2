### Title
Cross-repository/cross-tenant Status injection via unscoped sha lookup - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits solely by `Commit.where(sha: params.sha)` without ever restricting the search to the stacks belonging to the payload's `repository` field (via `Handler#stacks` / `Repository.from_github_repo_name`). Any commit sha that happens to exist in more than one tenant's `Commit` table (which is fully possible since git shas are content-addressed, not repository-scoped) will receive a forged status from a webhook that legitimately only concerns a completely different, unrelated repository.

### Finding Description
The broken binding, stated explicitly: for a `status` webhook, we require `commit.stack_id == Handler#stacks.resolve(payload['repository']['full_name'])`, i.e. the stack that gets the new `Status` must be the stack owned by the repository named in the payload.

Actual code: [1](#0-0) 
`process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — it never calls `stacks`, `repository_name`, or `Repository.from_github_repo_name`, both of which are defined on the base `Handler` class and used by other handlers such as the pull-request handlers. [2](#0-1) 

`create_status_from_github!` then writes the status using the **commit's own** `stack_id` (from the DB row, not from the payload): [3](#0-2) 

So the write is not "arbitrary stack_id from attacker input" — it uses whichever stack the matched `Commit` row belongs to. The real defect is that the *matching* step is entirely sha-based and global across all tenants: `Commit.where(sha: ...)` has no `stack_id`/`repository` filter at all, so if the same sha exists as a row in Stack A (an unrelated repository/tenant) and also as a row in Stack B (the attacker's own tracked repository), a webhook that GitHub genuinely sends for repository B's commit will also mutate Stack A's commit status.

Because git commit shas are a deterministic hash of tree, parent, author/committer identities and timestamps, and message, an attacker who can observe (e.g. via a public repo, or a previously-open/rejected PR they authored) the exact content of a commit that ended up merged into a completely different tracked repository (A) can reproduce that same commit (same tree/parents/timestamps/authors/message) inside their own tracked repository (B) — no cryptographic collision needed, since the inputs are literally identical. Once that identical-sha commit is pushed/referenced in B, GitHub will emit a `status` (or `check_suite`) event for B with that sha, honestly signed for B's owner via `verify_signature`, which correctly validates only that the payload came from GitHub for repository B's organization: [4](#0-3) 
This signature check says nothing about repository-level ownership of the sha itself — it only proves the payload is genuinely from GitHub for organization B, which is exactly what happens.

`WebhooksController#create` then dispatches unconditionally to `StatusHandler`, which finds every `Commit` row across the whole installation with that sha and writes/updates its `Status`, deployable-status hooks, and potentially schedules `ProcessMergeRequestsJob`/continuous delivery for Stack A — a stack that never authenticated or authorized anything from B.

None of the existing guards catch this: `verify_signature` is organization/owner-scoped, not sha/commit-scoped; `drop_unhandled_event` only checks the event type is handled; the `ExplicitParameters` schema for `StatusHandler` only validates the shape of `sha`/`state`/etc., not which stack they apply to; and `Handler#stacks`/`repository_name`, which exist precisely to perform this binding, are simply never invoked by this handler.

### Impact Explanation
A successful request causes a `Status` record (with attacker-chosen `state`, `context`, `description`, `target_url`) to be created against a commit belonging to an entirely different tenant's stack (`Stack` A), without A's repository ever appearing in the payload. Depending on state transitions this can flip a commit from failing to `success`, unblocking deploys, triggering `ContinuousDeliveryJob` if continuous deployment is enabled on A, or firing `deployable_status`/`commit_status` webhooks that downstream automation in A relies on. This is a genuine "payload for one repository mutating another's stack/commit" scenario, matching the Critical impact category (unauthorized deploy/rollback trigger, cross-tenant data mutation). It is repeatable against any repository/commit whose sha the attacker can reproduce and any repository the attacker can get tracked by Shipit (their own).

### Likelihood Explanation
Preconditions: (1) the attacker needs at least one repository tracked as a Shipit stack that they control and that receives genuine GitHub webhooks (self-service stack creation or an existing tracked fork/mirror satisfies this); (2) the attacker needs to know the exact byte-for-byte content (tree, parents, author/committer identity+timestamp, message) of a commit that is tracked in a victim stack — plausible for public repositories, or via a previously rejected PR whose branch/commit the attacker retains. No Shipit secrets, sessions, or API tokens are required; GitHub itself signs the genuine webhook for the attacker's own repository. This is a moderate-cost, fully repeatable attack (once achieved, it can be repeated for any sha collision the attacker manufactures).

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to the stacks resolved from the payload's repository, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalently join through `Handler#stacks` (already defined on the base class) before matching by sha, mirroring what the pull-request handlers do with `repository_name`/`Repository.from_github_repo_name`.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, not run live against GitHub):
1. Create `stack_a` with repository `owner-a/repo-a` and a `Commit` `commit_a` with `sha: 'deadbeef...'`.
2. Create `stack_b` with repository `owner-b/repo-b` (attacker-controlled) and no commit with that sha.
3. Build a `status` webhook payload with `repository.full_name = 'owner-b/repo-b'` and `sha: commit_a.sha`, `state: 'success'`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)`.
5. Assert: `commit_a.statuses.count` increased by 1 and `commit_a.statuses.last.state == 'success'`, even though `payload['repository']['full_name']` never equals `stack_a`'s repository name.
6. Additionally assert (via `Shipit::Webhooks::Handlers::Handler#stacks`/`Repository.from_github_repo_name` mocking) that these methods are never invoked by `StatusHandler#process`, confirming the missing repository-scope binding.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
