### Title
Webhook signature verified against `repository.owner.login` while all handlers dispatch by unrelated `repository.full_name` — cross-organization / cross-repository writes - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/handler.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization config (and therefore which `webhook_secret`) to verify the HMAC signature against using `repository_owner`, derived from `params.dig('repository', 'owner', 'login')`. Every event handler, however, resolves the target `Repository`/`Stack` to mutate using an entirely different, independently-controlled field of the same payload: `payload.dig('repository', 'full_name')`. Because the HMAC only proves the request was signed with *some* configured organization's secret, not that the acted-upon repository belongs to that organization, a party who can produce a validly-signed webhook for one configured organization can forge the `repository.full_name` field to target a stack belonging to a completely different organization/repository.

### Finding Description
`verify_signature` in `WebhooksController` computes the org to check against from the payload itself: [1](#0-0) [2](#0-1) 

`verify_webhook_signature` in `GitHubApp` just checks the HMAC of the raw body against that organization's `webhook_secret`: [3](#0-2) 

Once the signature check passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the parsed payload to every handler for that event type. Every handler resolves its target stacks via the base `Handler#stacks`, which reads a *different* payload field — `repository.full_name` — with no cross-check against `repository.owner.login`: [4](#0-3) 

`Repository.from_github_repo_name` simply looks up by `owner/name` parsed out of that `full_name` string, again independent of whichever org's secret validated the request: [5](#0-4) 

Shipit explicitly supports hosting multiple GitHub organizations side-by-side, each with its own `webhook_secret`, exactly as shown in the sample multi-org secrets file: [6](#0-5) [7](#0-6) 

**The broken equality:** the engine implicitly assumes
`organization whose secret validated the signature == owner of the repository the handler will act on`,
but nothing enforces this. The signature only proves "signed by org X's secret"; the handler acts on whatever `repository.full_name` says, which can name org Y's repository. An entity holding org X's `webhook_secret` (e.g., an org admin who configured their own Shipit GitHub App, or anyone who can trigger/replay a signed delivery for their own onboarded org) can freely forge `repository.full_name` to point at any other onboarded repository/stack, because HMAC-signing is computed over whatever bytes the signer chooses to send — it does not bind the *value* of `repository.owner.login` to `repository.full_name`.

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" trust binding explicitly called out as in-scope. Concretely, a forged payload with `repository.owner.login = "orgX"` (so `verify_signature` uses orgX's known secret and passes) but `repository.full_name = "orgY/victim-repo"` causes handlers such as `PushHandler` to invoke `stack.sync_github(expected_head_sha: params.after)` on orgY's stack: [8](#0-7) 

or drives `pull_request`/`status`/`membership`/`merge` handlers against orgY's stacks, teams, or commits. This is a cross-organization/cross-repository write triggered without any credential belonging to the target organization — satisfying the Critical "cross-repository writes" impact bar.

### Likelihood Explanation
Requires only that the attacker be a legitimate webhook sender for one org already onboarded onto the shared Shipit instance (i.e., knows/controls that org's `webhook_secret`, which they need for their own repos to function with Shipit anyway) — no privileged access to the *target* organization/repository is needed. In any multi-tenant Shipit deployment (the officially supported multi-org config shape shown in `secrets.development.shopify.yml`), this is directly reachable by any onboarded-but-unprivileged org's webhook credential holder.

### Recommendation
Bind the two fields together: after selecting the organization to verify against, require that `repository.full_name`'s owner component matches `repository_owner`/the selected organization before dispatching to handlers, e.g. add a check in `WebhooksController#verify_signature` (or in `Handler#stacks`) that rejects the payload if `payload.dig('repository', 'owner', 'login')` does not match the owner segment of `payload.dig('repository', 'full_name')`, and additionally verify that the resolved `Repository#owner` matches the organization whose secret validated the signature.

### Proof of Concept
1. Shipit is configured with two organizations, `orgX` and `orgY`, each with its own `webhook_secret` (as in `config/secrets.development.shopify.yml`).
2. Attacker controls (or is an admin of) `orgX`, which is legitimately onboarded to the same Shipit instance, and thus knows/controls `orgX`'s `webhook_secret`.
3. Attacker crafts a `push` event payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "orgX" },
    "full_name": "orgY/victim-repo"
  }
}
```
4. Attacker computes `X-Hub-Signature = sha1=HMAC(orgX_webhook_secret, raw_body)` and POSTs to `/webhooks`.
5. `verify_signature` calls `Shipit.github(organization: "orgX")` and the HMAC check passes (correct secret for `orgX`) — [1](#0-0) .
6. `PushHandler#process` resolves stacks via `repository.full_name = "orgY/victim-repo"` and calls `stack.sync_github(expected_head_sha: params.after)` on `orgY`'s stack — [8](#0-7)  — even though the request was never signed by `orgY`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
