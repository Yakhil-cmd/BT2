### Title
Unvalidated `Codespace.WebURL` from GitHub API response passed directly to OS browser launcher - ([File: pkg/cmd/codespace/code.go])

### Finding Description
`(*App).VSCode` retrieves a `Codespace` object via `selector.Select(ctx)`, which internally calls `internal/codespaces/api.API.GetCodespace` to fetch codespace metadata from whatever host `gh` is configured against (`GH_HOST`/enterprise endpoint). When `useWeb` is set, the code assigns `codespace.WebURL` directly to `browseURL` with no scheme or host validation: [1](#0-0) 
The only manipulation performed is optional query-string editing for the `insiders` flag; there is no allow-listing of scheme (`https://`) or host (`github.com`/configured `GH_HOST`) before the value is handed to the OS-level URL launcher: [2](#0-1) 
`a.browser.Browse` is implemented via the vendored `github.com/cli/go-gh/v2/pkg/browser` package, which shells out to platform-specific openers (`xdg-open`, `open`, `rundll32 url.dll,FileProtocolHandler`, etc.): [3](#0-2) 
Because `GetCodespace` returns whatever JSON the API host supplies, an attacker who controls responses from a host the victim has pointed `gh` at (e.g. a self-hosted/enterprise `GH_HOST` endpoint) can set `WebURL` to an arbitrary string — including a `file://` path, a non-github origin, or a custom/registered URI scheme (e.g. `outlook:`, `ms-word:`, or other locally-registered protocol handlers) — with no host/scheme allow-listing anywhere in this call chain to stop it.

### Impact Explanation
This enables the attacker-controlled API endpoint to force the victim's OS-level URL launcher (`xdg-open`/`open`/`rundll32`) to open an arbitrary URI of the attacker's choosing. Depending on what is installed/registered on the victim's machine, this can invoke local file access (`file://`) or trigger arbitrary locally-registered custom URI-scheme handlers — a known "unvalidated URL open leading to local handler invocation" class of impact. It does not achieve remote code execution by itself since `Browse` passes the string as a single argument to the OS opener rather than through a shell, and most modern default browsers ignore `javascript:` URIs launched externally, but the missing scheme/host check is a genuine gap against the intended "victim only ever opens github.com/GH_HOST codespace web URLs" invariant.

### Likelihood Explanation
Requires the victim to have `gh` configured against, or making requests to, an endpoint the attacker controls (e.g. a malicious/compromised enterprise `GH_HOST`), and to run `gh cs code -w`. This matches the stated precondition ("attacker controls responses from a host the victim points gh at"), which is within the defined threat model. No local access, admin rights, or token leakage is required beyond that.

### Recommendation
Validate `codespace.WebURL` before passing it to `a.browser.Browse`: parse it with `net/url`, require `scheme == "https"`, and require the host to match the expected codespaces web domain (or the configured `GH_HOST`/`ghinstance` host) before opening it, rejecting or erroring on any other scheme/host.

            }, nil
        },
    }

    app := NewApp(..., browser, am, ...)
    err := app.VSCode(context.Background(), selectorFor("monalisa-cs"), false, true)
    // Expect: browser.Browse is never invoked with a non-https/non-expected-host URL,
    // or VSCode returns an error instead of opening the untrusted URL.
    browser.Verify(t, "") // current behavior: Browse IS called with "file:///etc/passwd", demonstrating the gap
}

Running this against current code shows `a.browser.Browse` is invoked with the attacker-supplied `WebURL` unchanged, confirming the missing validation described above.
