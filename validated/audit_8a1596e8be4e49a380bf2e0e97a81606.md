### Title
CCMenuController#stack bypasses ApiClient stack scoping, letting a stack-scoped token read any stack - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::BaseController` enforces per-token stack scoping by resolving `params[:stack_id]` through a `stacks` collection that is restricted to `current_api_client.stack_id` when the client is scoped to a stack. `Shipit::Api::CCMenuController` overrides `#stack` with its own implementation that queries `Stack.from_param!(params[:stack_id])` directly, never consulting `current_api_client.stack_id`, so any valid `read:stack` token can retrieve CCMenu build status for any stack regardless of which stack it was issued for.

### Finding Description
The intended binding is: `current_api_client.stack_id == resolved(stack, params[:stack_id])` whenever `current_api_client.stack_id?` is true. `BaseController` implements this via: [1](#0-0) 
which restricts the queryable stacks to the client's own `stack_id` before resolving `params[:stack_id]`.

`CCMenuController`, however, defines its own `stack` method that ignores this scoping entirely: [2](#0-1) 
`Stack.from_param!(params[:stack_id])` is queried against all stacks in the system, not `stacks.from_param!(...)`. The only gate before `show` runs is `require_permission :read, :stack`, which calls `ApiClient#check_permissions!`: [3](#0-2) 
This checks only that the `permissions` array contains `read:stack` — it never compares `stack_id`. So the equality that should hold (`current_api_client.stack_id == stack.id` when the client is stack-scoped) is never evaluated on the CCMenu path, even though the identical scoping already exists and is exercised elsewhere (e.g. `Api::StacksController`'s use of the shared `stacks`/`stack` helpers, confirmed by the "an api client scoped to a stack will only see that one stack" test).

`ApiClient#authentication_token` / `.message_verifier` only sign/verify the row id: [4](#0-3) 
`Shipit::SimpleMessageVerifier` is a plain HMAC over the id string, no additional claims: [5](#0-4) 
This is not itself a forgeable weakness (the attacker cannot mint a token for an id they don't own), but it does mean the *only* place stack authorization for CCMenu could be enforced is the `stack_id` column read at request time — and `CCMenuController` never reads it.

Exploit flow: attacker legitimately obtains a `read:stack` token scoped to stack A (e.g., via `CCMenuUrlController#fetch`, which creates/reuses an `ApiClient` with `permissions: %w[read:stack]`): [6](#0-5) 
Using this same token (`Authorization: Basic` or `?token=`), the attacker issues `GET /api/stacks/<owner>/<repo>/<env>/ccmenu?token=<token>` for stack B instead of stack A. `CCMenuController#authenticate_api_client` accepts the token (it is valid for the attacker's own client row) and `#stack` resolves stack B unconditionally, returning stack B's build/deploy status XML.

### Impact Explanation
The attacker obtains unauthenticated (from stack B's perspective) read access to stack B's build status, last build label/time, activity and lock state via the CCMenu XML feed, for any stack in the Shipit instance, using a token that was only ever authorized for stack A. This is a cross-tenant/cross-stack information disclosure and matches the High severity category "unauthenticated read of stack state." It is fully repeatable against any stack_id the attacker can guess or enumerate (stack ids/slugs are typically `owner/repo/environment`, often discoverable), with no rate limiting or additional signature needed. It does not directly permit RCE, deploys, or code execution, so it does not rise to Critical.

### Likelihood Explanation
Preconditions are modest: the attacker needs one legitimate `read:stack`-scoped CCMenu token (obtainable by any user with UI/API access to trigger `CCMenuUrlController#fetch` for a stack they can already view) and knowledge of the target stack's `owner/repo/environment` triple. No secrets (`api_clients_secret`, `secret_key_base`, GitHub credentials) are needed. The attacker cost is a single authenticated HTTP GET per target stack, and the attack is trivially repeatable across all stacks hosted on the instance.

### Recommendation
Make `CCMenuController#stack` honor the same scoping as the rest of the API by using the inherited `stacks`/`stack` helpers (or explicitly checking `current_api_client.stack_id.blank? || current_api_client.stack_id == resolved_stack.id`) instead of calling `Stack.from_param!` directly, so a stack-scoped token can only ever resolve to its own stack.

### Proof of Concept
minitest plan (in `test/controllers/api/ccmenu_controller_test.rb`):
1. Create `stack_a = shipit_stacks(:shipit)` and `stack_b = Stack.create!(repository: Repository.new(owner: 'foo', name: 'bar'), branch: 'main')`.
2. Create `client = ApiClient.create!(creator: shipit_users(:walrus), name: 'scoped', permissions: %w[read:stack], stack_id: stack_a.id)`.
3. Assert the binding before the request: `assert_equal stack_a.id, client.stack_id`.
4. `get :show, params: { stack_id: stack_b.to_param, token: client.authentication_token }`.
5. Assert `response.status == 200` and that the returned XML's `name` attribute equals `stack_b.to_param` — proving a token scoped to `stack_a.id` (`client.stack_id`) successfully read `stack_b`, i.e., `client.stack_id != stack_b.id` yet access was granted, violating the intended binding.
6. Contrast with `Api::StacksController#index`/`#show`, where the same scoped client (`authenticate!(:here_come_the_walrus)`-style fixture) is correctly restricted to its own stack, showing the divergence is specific to `CCMenuController`.

module Shipit
  class SimpleMessageVerifier < ActiveSupport::MessageVerifier
    def initialize(secret, **options)
      options[:serializer] ||= ToS
      super(secret, **options)
    end

    private

    def encode(data)
      data.to_s
    end

    def decode(data)
      data
    end

    module ToS
      def self.dump(object)
        object.to_s

        payload
      end
    end
  end
