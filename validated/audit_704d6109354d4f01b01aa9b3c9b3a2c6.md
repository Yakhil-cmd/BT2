### Title
CCMenu API token scope-widening due to missing `stack:` on `ApiClient.find_or_create_by!` - (File: app/controllers/shipit/ccmenu_url_controller.rb)

### Summary
`CCMenuUrlController#client` creates (or reuses) an `ApiClient` with `stack_id` left `nil`, even though the token is minted from a per-stack CCMenu URL endpoint intended to expose only that stack's status. Because `Api::BaseController#stacks` treats a blank `stack_id` as "no restriction" and falls back to `Stack.all`, the resulting token — nominally issued for one repository's CI dashboard — authorizes `read:stack` access across every stack in the installation.

### Finding Description
The intended binding is `token.authorized_stacks == {stack}` (the single stack for which the CCMenu URL was requested via `/stacks/:owner/:repo/:branch/ccmenu_url`). The actual binding, due to this code, is `token.authorized_stacks == Stack.all`.

Code path:
- `CCMenuUrlController#fetch` computes `stack` from `params[:stack_id]` [1](#0-0) , but `#client` calls `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')` without ever including `stack: stack` in the attributes [2](#0-1) .
- `ApiClient` declares `belongs_to :stack, optional: true`, so the row persists with `stack_id == nil` [3](#0-2) .
- On any subsequent API request authenticated with that token, `Api::BaseController#stacks` evaluates `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` — since `stack_id` is nil, it resolves to `Stack.all` [4](#0-3) .
- Because `find_or_create_by!` is keyed only on `(creator, name)`, every subsequent visit to the CCMenu URL page for *any* stack by the same user reuses this same unscoped client row — one "CCMenu Client" per user, valid for `read:stack` on all stacks.

`CCMenuUrlController` inherits from `ShipitController`, which requires `force_github_authentication` — the visitor must be a logged-in, `Shipit.github_teams`-authorized user to reach `#fetch` at all [5](#0-4) [6](#0-5) . This contradicts part of the question's premise that team membership isn't needed to hit this controller — it is. No existing guard (`verify_signature`, `require_permission!`, model validations) checks or restores `stack_id` on the token itself; `require_permission!`/`check_permissions!` only validate the permission string, not the stack scope [7](#0-6) .

### Impact Explanation
Any single-stack CCMenu token, once obtained by a third party (e.g., pasted into a public CI badge config, shared in chat, or intercepted from an insecure CCMenu client), grants `read:stack` over `Stack.all` — every repository/stack managed by that Shipit installation, not just the one the URL nominally names. This is a cross-tenant authorization scope violation: a credential scoped to repository A discloses stack/task/deploy state for repositories B, C, D, etc. This matches the "High — unauthenticated read of stack state, task streams or deploy output" category, since the token behaves far more broadly than any operator or reviewer would expect from a per-repository CCMenu integration.

### Likelihood Explanation
Requires: (1) a Shipit user who is a member of `Shipit.github_teams` to visit `.../ccmenu_url` for some stack (a routine, unprivileged-within-Shipit action many CI-status-widget users perform), and (2) that resulting URL/token later reaching an outside party. CCMenu URLs are, by design, meant to be embedded in third-party monitoring tools and are not treated as highly sensitive by end users, making leakage plausible (shared dashboards, public CI config, browser extensions). No GitHub or Shipit secrets are needed to trigger the bug itself — it is a straightforward Rails model/controller logic gap, deterministically reproducible.

### Recommendation
Pass `stack: stack` into the `find_or_create_by!`/`create_with` call (and include `stack` in the uniqueness key so distinct stacks get distinct client rows), e.g.:
```ruby
ApiClient.create_with(permissions: %w[read:stack])
         .find_or_create_by!(creator: current_user, stack: stack, name: 'CCMenu Client')
```
This ensures `stack_id` is persisted so `Api::BaseController#stacks` correctly scopes to `Stack.where(id: current_api_client.stack_id)` instead of falling back to `Stack.all`.

### Proof of Concept
In a minitest under `test/controllers/shipit/ccmenu_url_controller_test.rb`-equivalent style (or a model/controller test hitting `Api::BaseController#stacks` directly):
1. Create two stacks, `stack_a` and `stack_b`.
2. As an authorized user, call the equivalent of `CCMenuUrlController#client` logic directly: `client = ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: user, name: 'CCMenu Client')`.
3. Assert `client.stack_id.nil?` — confirming the token is unscoped.
4. In a stub/instance of `Api::BaseController` (or via `ApiController` request using `client.authentication_token`), assert `controller.send(:stacks)` (with `@current_api_client = client`) returns a relation equal to `Stack.all` (includes both `stack_a` and `stack_b`), rather than being restricted to `stack_a`.
5. Contrast with the fixed behavior: after passing `stack: stack_a`, assert `stacks` returns only `Stack.where(id: stack_a.id)`, excluding `stack_b`.
