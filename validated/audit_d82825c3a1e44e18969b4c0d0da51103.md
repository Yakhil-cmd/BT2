### Title
Webhook signature is verified against a GitHub organization derived from query-string-overridable `params`, while the actually-processed payload is parsed independently from the raw body, allowing cross-repository/cross-stack writes with a forged organization identity - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks the GitHub App (and thus the `webhook_secret` used for HMAC verification) using `repository_owner`, which is read from Rails' merged `params` object. `WebhooksController#create` independently re-parses `request.raw_post` into a *separate* local `params` variable and dispatches that to the webhook handlers. Because Rails' `ActionDispatch::Http::Parameters#parameters` merges `query_parameters` **over** `request_parameters` (the parsed body), an attacker can put a `repository[owner][login]` query-string value that differs from the JSON body actually signed and processed. This breaks the intended binding: `organization that authenticated == repository/commit actually written`, mirroring the Sherlock report's pattern of "acted on but not covered by the verification".

### Finding Description [1](#0-0) [2](#0-1) [3](#0-2) 

- `verify_signature` (a `before_action`) computes `repository_owner` via `params.dig('repository', 'owner', 'login')`. This `params` is the standard Rails `ActionController::Parameters`, built by merging GET query parameters over the parsed JSON body (`request_parameters.merge(query_parameters)` in `ActionDispatch::Http::Parameters`), so a same-named query-string field silently overrides the body's field for this lookup.
- `Shipit.github(organization: repository_owner)` then selects which org's `webhook_secret` is used to validate `X-Hub-Signature` against `request.raw_post`.
- `create` re-parses `request.raw_post` into its own local `params` and hands that raw, signed body straight to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` — with no re-check that the body's own `repository`/`organization` fields match the one used to select the verifying secret.
- Handlers such as `StatusHandler#process` (`Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`) and `PushHandler#process` (triggers `stack.sync_github` for any stack on the matching branch) operate purely on data taken from the body, matched globally by `sha`/`branch`, not scoped to the organization that was actually verified. [4](#0-3) [5](#0-4) 

This is the same class of bug as the report: the code checks/authorizes based on one signal (`numRequested` / here, the query-string-influenced `repository_owner`) but acts on unrelated/broader data (all payloads / here, the raw-body `repository`, `sha`, `branch` fields used by handlers), so an attacker can make the "requested" (authenticated) scope diverge from the "acted on" scope.

### Impact Explanation
An attacker who has legitimate control of one GitHub App/org integration registered in this Shipit instance (i.e., they know that org's own `webhook_secret`, which they are entitled to as the owner of that integration) can:
1. Sign a payload with their own org's secret.
2. Override `repository_owner` via the query string so `verify_signature` validates against their own org's secret (passes).
3. Put an arbitrary `sha`/`state`/`branch` in the signed JSON body, targeting a commit/stack that belongs to a completely different, victim repository/stack in the same Shipit instance.

This lets the attacker inject a forged CI status onto arbitrary commits (`StatusHandler`) or force an unscheduled GitHub resync of an unrelated stack (`PushHandler`/`GithubSyncJob`), i.e., a **cross-repository/cross-stack write** performed under a spoofed authenticated identity. Forged "success" statuses can bypass status-check gating relied on before deploys, contributing to an **unauthorized deploy** path.

### Likelihood Explanation
Requires the attacker to control at least one legitimate GitHub App/org configuration on the Shipit instance (something a multi-tenant Shipit deployment commonly grants to many teams), plus knowledge of Rails' query-over-body params precedence — no privileged Shipit account, `ApiClient` token, or GitHub write access to the victim repo is needed. This matches the sherlock finding's "attacker submits both requested and unrequested data to exploit a mismatched scope" pattern, rated Medium there; here the potential blast radius (writing across stacks) makes it a credible High-severity analog for this engine.

### Recommendation
- Derive `repository_owner` (and any org used for signature verification) exclusively from `request.raw_post`'s parsed JSON, never from the merged `params`/query string.
- After signature verification, enforce that the `repository`/`organization` fields inside the verified raw body match the organization whose secret validated the signature before dispatching to handlers.
- Consider parsing the body once and passing that single parsed value through both `verify_signature` and `create`, eliminating the two independent parses that can diverge.

### Proof of Concept
1. Attacker owns/operates GitHub org `attacker-org`, registered as a Shipit GitHub App integration with known `webhook_secret_A`.
2. Attacker crafts JSON body (a valid GitHub `status` event) referencing a commit `sha` that belongs to victim stack `victim/repo`, with `state: "success"`, and computes `X-Hub-Signature: sha1=HMAC(webhook_secret_A, body)`.
3. Attacker sends:
   `POST /webhooks?repository[owner][login]=attacker-org` with `X-Github-Event: status`, the above `X-Hub-Signature` header, and the crafted body.
4. `verify_signature` resolves `repository_owner` to `attacker-org` (from the query string, overriding whatever `repository.owner.login` is/isn't in the body), fetches `attacker-org`'s `webhook_secret_A`, and validates successfully. [6](#0-5) 
5. `create` re-parses the raw body and dispatches to `StatusHandler`, which writes a forged "success" status onto the victim's commit, unrelated to `attacker-org`. [1](#0-0) [4](#0-3)

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
