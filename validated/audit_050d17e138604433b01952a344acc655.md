### Title
`Api::CCMenuController` Lets a Stack-Scoped API Token Read the CI Status of Any Stack - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::CCMenuController` re-implements stack resolution instead of using the scoped helper defined in `Api::BaseController`, so a token that is supposed to be restricted to a single stack can be used to read the deploy/rollback status of any stack in the installation.

### Finding Description
`Api::BaseController` defines the canonical, scope-respecting resolution of which stacks a given `ApiClient` may see: [1](#0-0) 
`stacks` is restricted to `current_api_client.stack_id` when the client is scoped to one stack, and `stack` derives from that restricted collection via `from_param!`. This is the binding the whole API authorization model relies on: *the stack a token authorises == the stack it can touch*.

`Api::CCMenuController` inherits from `BaseController` and declares `require_permission :read, :stack`, which only checks that `read:stack` is present in the token's `permissions` list: [2](#0-1) 
`check_permissions!` never looks at `stack_id` — the scoping enforcement is solely delegated to the `stack`/`stacks` helper methods in `BaseController`. However, `CCMenuController` overrides `stack` directly against the global `Stack` model instead of the scoped `stacks` collection: [3](#0-2) 
Since `authenticate_api_client` here just authenticates the token positionally from `params[:token]` (bypassing Basic Auth) without re-checking scope either: [4](#0-3) 
any client holding a token with `read:stack` permission — even one explicitly minted and scoped to a single stack, such as the CCMenu client created by `CCMenuUrlController#client` — can supply an arbitrary `stack_id` in the URL and retrieve the CCMenu XML (deploy/rollback status) for any stack, not just the one the token was scoped to.

The narrow, single-stack CCMenu tokens are exactly the mechanism this bypasses: `CCMenuUrlController` creates a token scoped only to `permissions: %w[read:stack]` with no explicit stack restriction bound at issuance time, and relies on the caller only ever supplying that one `stack_id`, but nothing in `CCMenuController` prevents substituting a different `stack_id`: [5](#0-4) 
More critically, this pattern generalizes to any `ApiClient` that is deliberately scoped via `stack:` (see fixture `here_come_the_walrus`, scoped to the `shipit` stack) and has `read:stack` in its permission list — that token, intended to see status for one stack only, can be pointed via `params[:token]`/`params[:stack_id]` at the CCMenu endpoint for a different stack it was never authorized against. [6](#0-5) 

### Impact Explanation
This matches the in-scope High-severity category "unauthenticated read of stack state, task streams or deploy output" — here more precisely an authenticated-but-out-of-scope read: an `ApiClient` token bound to one stack can read the deploy/rollback status (last deploy id, ended_at, running state) of every other stack in the deployment, violating the fundamental scoping guarantee `Api::BaseController#stacks`/`#stack` is meant to provide for every other API endpoint.

### Likelihood Explanation
Any holder of a valid, narrowly-scoped API token (e.g., a CI dashboard integration or a CCMenu-generated URL, which by design is often embedded in less-trusted client tools/dashboards) can trivially exploit this by changing the `stack_id` query parameter to enumerate other stacks' CI status — no privilege escalation, signature forgery, or additional secrets are required beyond possessing one legitimately-issued scoped token.

### Recommendation
Make `Api::CCMenuController#stack` resolve through the scoped `stacks` collection defined in `BaseController` (i.e., `stacks.from_param!(params[:stack_id])`) instead of querying the global `Stack` model directly, so the `stack_id` scoping restriction on the authenticated `ApiClient` is honored consistently with the rest of the API surface.

### Proof of Concept
1. Create (or reuse) an `ApiClient` scoped to `stack: shipit` with `permissions: ['read:stack']` (e.g., via `CCMenuUrlController#client` or the `here_come_the_walrus` fixture) and obtain its `authentication_token`.
2. Send `GET /api/stacks/:other_stack_id/ccmenu.xml?token=<that token>` where `:other_stack_id` refers to a stack the token was never scoped to.
3. Observe the response renders `shipit/ccmenu/project` with the deploy/rollback status of the unrelated stack, confirming `Api::CCMenuController#stack` (`Stack.from_param!(params[:stack_id])`) bypasses the `current_api_client.stack_id` scoping enforced everywhere else in `Api::BaseController#stacks`.
