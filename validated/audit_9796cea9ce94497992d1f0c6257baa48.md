### Title
Cross-organization team hijack via unscoped `github_id` lookup in `MembershipHandler#find_or_create_team!` - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::MembershipHandler#find_or_create_team!` looks up teams solely by the GitHub-global numeric `github_id`, with no check that the organization named in the webhook payload actually owns that team record. Any organization that is a legitimate tenant of this multi-tenant Shipit instance (and therefore has its own valid `webhook_secret`) can sign a `membership` webhook naming another organization's team ID and add arbitrary GitHub users to that team, since `verify_signature` only proves *who sent the request*, not *which team the request may mutate*.

### Finding Description
The broken binding, stated explicitly: the code must ensure `signed_by_organization == team.organization`, but it only ever proves `signed_by_organization == params.dig('organization','login')`.

Trace:
1. `Shipit::WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0)  . A `membership` event payload has no top-level `repository` key, so `repository_owner` becomes the attacker-controlled `organization.login` (`"evilcorp"`).
2. `Shipit.github(organization: repository_owner)` resolves to the `GithubApp`/hook config for `evilcorp`, and `verify_webhook_signature` checks the `X-Hub-Signature` against `evilcorp`'s own `webhook_secret` [2](#0-1) [3](#0-2) . This succeeds because `evilcorp` is a real, independently configured tenant with its own valid secret — signature verification proves nothing about ownership of the *team* referenced inside the payload.
3. `MembershipHandler#process` calls `find_or_create_team!`, which runs `Team.find_or_create_by!(github_id: params.team.id)` [4](#0-3) . The lookup key `github_id` is GitHub's globally unique numeric team ID (not scoped by organization), and `Team` has no uniqueness/ownership validation tying `github_id` to `organization` at read time — the `organization=` assignment only happens inside the `find_or_create_by!` block, which is skipped entirely when the row already exists (i.e., precisely the attack case). The pre-existing victim `Team` row (e.g. `shipit_teams(:shopify_developers)`, `github_id: 1`) is returned unchanged.
4. `team.add_member(User.find_or_create_by_login!(params.member.login))` [5](#0-4) [6](#0-5)  then creates a `Membership` row linking the attacker's GitHub login to the victim's team.
5. `User#authorized?` checks `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [7](#0-6) ; if the hijacked team is in `Shipit.github_teams` (configured via `oauth.teams`, resolved through `Team.find_or_create_by_handle` [8](#0-7) ), the attacker's new membership makes `authorized?` return true, granting them access equivalent to a legitimate member of that privileged team.

None of the existing guards catch this: `verify_signature` authenticates the sender org, not the target team; `drop_unhandled_event` only checks that a handler exists for the event type; the `ExplicitParameters` schema on `MembershipHandler` only validates payload shape (`team.id`, `organization.login`, `member.login` types), not cross-organization consistency; there is no `require_permission!`/`force_github_authentication` check in this controller path since webhooks are inherently unauthenticated aside from the HMAC signature.

### Impact Explanation
A successfully signed webhook from **any** onboarded organization can add or remove members of a **different** organization's `Team` record, as long as it knows/guesses the target's numeric GitHub team ID. If that team is referenced in `Shipit.github_teams` (the authorization gate for the whole app, or for stack-level permissions depending on configuration), this is a straightforward authentication/authorization bypass: an attacker-controlled GitHub identity gains membership in a privileged Shipit team it never legitimately belonged to, satisfying `User#authorized?` and any downstream `require_permission!` checks gated on team membership. This matches the "High - escalation into `Shipit.github_teams` authorization" (and arguably "Critical - authentication bypass") impact category. The attack is repeatable against any team whose `github_id` is known or brute-forced, and is not limited to a single stack — it is a cross-tenant issue affecting the whole Shipit instance's authorization model.

### Likelihood Explanation
Preconditions: the attacker must control (or be) a legitimate tenant organization already configured in Shipit with its own valid `webhook_secret` (as stated in the prompt's precondition), and must know/guess a target team's numeric `github_id` (GitHub team IDs are sequential/enumerable and not secret). No Shipit session, API token, or GitHub credentials for the victim org are required. Given that this app is designed to support multiple GitHub organizations as tenants (each with `Shipit.github(organization:)` config), and cross-tenant boundaries are the entire point of this check, the likelihood is high once any second tenant with adversarial intent exists.

### Recommendation
In `Shipit::Webhooks::Handlers::MembershipHandler#find_or_create_team!`, scope the lookup by both `github_id` **and** `organization` (e.g. `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`), and reject/raise when an existing team with that `github_id` belongs to a different `organization` than the one that signed the request, rather than silently returning the mismatched record.

### Proof of Concept
Minitest plan under `test/controllers/webhooks_controller_test.rb` (no live GitHub):
1. Fixtures: `shipit_teams(:shopify_developers)` has `organization: 'shopify'`, `github_id: 1`. Add/stub a second `GithubHook::Organization` fixture for `organization: 'evilcorp'` with its own `webhook_secret`, and stub `GithubHook.any_instance.stubs(:verify_signature).returns(true)` (as existing tests do) or stub `Shipit.github(organization: 'evilcorp').verify_webhook_signature` to return `true` while leaving `Shipit.github(organization: 'shopify')` untouched.
2. `assert_equal 'shopify', shipit_teams(:shopify_developers).organization` — state the binding before the request.
3. POST `/webhooks` with `X-Github-Event: membership`, signature computed/stubbed for `evilcorp`, body:
   `{ action: 'added', team: { id: shipit_teams(:shopify_developers).github_id, name: 'Developers', slug: 'developers', url: 'http://example.com' }, organization: { login: 'evilcorp' }, member: { login: 'attacker' } }`.
4. Assert `assert_response :ok`.
5. Assert `Membership.exists?(team: shipit_teams(:shopify_developers), user: User.find_by(login: 'attacker'))` is `true`.
6. Assert `shipit_teams(:shopify_developers).reload.organization == 'shopify'` still (team ownership unchanged) while membership was mutated by `evilcorp`'s signature — proving the binding `signed_by == team.organization` was violated (`'evilcorp' != 'shopify'`) yet the mutation succeeded.
7. If `Shipit.github_teams` includes this team in test setup, additionally assert `User.find_by(login: 'attacker').authorized?` is `true`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
