### Title
`DenyReserveTransferToRelayChain` bypass via `SetAppendix`/`SetErrorHandler` nested XCM payloads - (File: `system-parachains/asset-hubs/asset-hub-kusama/src/xcm_config.rs`)

### Summary
Asset Hub Kusama's `Barrier` wraps `DenyReserveTransferToRelayChain` directly in `DenyThenTry` without the `DenyRecursively` combinator that other chains in this same repository (e.g. Bridge Hub Polkadot, Bulletin Polkadot) explicitly use for this exact deny-filter. Because `DenyReserveTransferToRelayChain`'s `ShouldExecute` implementation only scans the top-level instruction slice passed to the executor, a signed user can embed the disallowed `InitiateReserveWithdraw`/`DepositReserveAsset`/`TransferReserveAsset { .. (1, Here) .. }` instruction inside a `SetAppendix` or `SetErrorHandler` payload, which is executed later in the same executor context without a fresh `Barrier::should_execute` call, evading the deny check.

### Finding Description
The `Barrier` type is defined as: [1](#0-0) 

`DenyReserveTransferToRelayChain` is invoked once via `DenyThenTry` at the top of `XcmExecutor::prepare`/`execute`, and its implementation (in the `xcm-builder` dependency, not vendored in this repo) checks whether *any* instruction in the top-level message slice matches the barred reserve-transfer-to-relay-chain instructions. This top-level scan does not recurse into the nested `Xcm<Call>` payloads carried by `SetAppendix(xcm)` or `SetErrorHandler(xcm)`. Those nested payloads are stored by the executor and run later — after the main program completes or errors — inside the same execution call, without re-invoking `Barrier::should_execute`. Consequently, a user who submits a top-level program such as `[WithdrawAsset(...), SetAppendix(Xcm(vec![DepositReserveAsset { dest: (1, Here), .. }])), <innocuous instruction that completes/errors>]` via `PolkadotXcm::execute` (available to any signed account per `ExecuteXcmOrigin = EnsureXcmOrigin<RuntimeOrigin, LocalSignedOriginToLocation>` and `XcmExecuteFilter = Everything`) causes the barred reserve-transfer instruction to run in the appendix/error-handler phase, entirely outside the scope inspected by `DenyReserveTransferToRelayChain`. [2](#0-1) 

That this is a real, previously-recognized gap is corroborated by the fact that other chains in the same repository explicitly wrap the same filter in `DenyRecursively` to close it: [3](#0-2) [4](#0-3) 

`DenyRecursively` exists specifically to walk into `SetAppendix`/`SetErrorHandler` (and similarly-nested) instruction sequences and re-apply the inner filter, which the plain, un-recursed `DenyReserveTransferToRelayChain` used on Asset Hub Kusama/Polkadot, Bridge Hub Kusama, Coretime Kusama/Polkadot, Encointer, People Kusama/Polkadot, and Collectives Polkadot does not do.

Note: the "nested `Transact` re-dispatching `PolkadotXcm::transfer_assets`" vector mentioned in the question is *not* a real bypass — each `Transact`-dispatched call that internally calls `pallet_xcm::transfer_assets` builds and executes a brand-new top-level XCM program via a fresh call into the executor, which re-triggers `Barrier::should_execute`/`DenyReserveTransferToRelayChain` from scratch and would still be denied. The genuine bypass is limited to `SetAppendix`/`SetErrorHandler` nested payloads within a single top-level execution.

### Impact Explanation
A signed user can move reserve assets to the Relay Chain via a route the runtime policy explicitly intends to forbid (`DenyReserveTransferToRelayChain`), by hiding the forbidden instruction inside a `SetAppendix`/`SetErrorHandler` payload of a locally-executed or inbound XCM program. This is a policy-bypass allowing disallowed reserve-asset flows to the Relay Chain, matching the scoped impact.

### Likelihood Explanation
Preconditions are minimal: any signed account can call `PolkadotXcm::execute` (or have an inbound message crafted to the same effect) since `ExecuteXcmOrigin`/`XcmExecuteFilter` impose no meaningful restriction here. Constructing a program with `WithdrawAsset` + `SetAppendix`/`SetErrorHandler` containing `DepositReserveAsset`/`InitiateReserveWithdraw`/`TransferReserveAsset` targeting `(1, Here)` is a standard XCM v4 program, fully within `MaxInstructions` and weight limits. This is repeatable by any user at will.

### Recommendation
Wrap `DenyReserveTransferToRelayChain` in `DenyRecursively` in the `Barrier` definitions of Asset Hub Kusama and Asset Hub Polkadot (and the other affected chains — Bridge Hub Kusama, Coretime Kusama/Polkadot, Encointer, People Kusama/Polkadot, Collectives Polkadot), matching the pattern already used in Bridge Hub Polkadot and Bulletin Polkadot:
```rust
pub type Barrier = TrailingSetTopicAsId<
	DenyThenTry<
		DenyRecursively<DenyReserveTransferToRelayChain>,
		( ... )
	>,
>;
```

### Proof of Concept
xcm-emulator integration test:
1. Fund a test account on Asset Hub Kusama with KSM.
2. Submit `PolkadotXcm::execute` with an XCM program:
   `[WithdrawAsset(ksm), SetAppendix(Xcm(vec![DepositReserveAsset { assets: All.into(), dest: Location::parent(), xcm: Xcm(vec![]) }])), ClearOrigin]`
   where the primary program instructions (after the appendix is set) trigger completion of the main program (so the appendix executes).
3. Assert on the Relay Chain side that the sovereign/derived account of Asset Hub receives the deposited reserve asset (i.e., the transfer succeeded), while a direct top-level submission of `DepositReserveAsset { dest: Location::parent(), .. }` (without `SetAppendix` wrapping) is rejected with `ProcessMessageError::Unsupported`/`Barrier` error.
4. Expected assertions: the appendix-wrapped case succeeds (bug reproduced) whereas the direct top-level case is denied, demonstrating the inconsistency and confirming the bypass.
