### Title
Webhook signature verification is scoped to an attacker-chosen `repository.owner.login`, decoupled from the `repository.full_name` actually mutated by the handler, allowing cross-tenant forged webhooks - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and thus the webhook secret) to verify the HMAC signature against using `params.dig('repository','owner','login')`, while `#create` and the pull-request handlers act on an entirely separate field, `params.dig('repository','full_name')`. No code anywhere checks that these two identify the same organization, so an attacker can pick an organization key that has no `webhook_secret` configured (or one whose secret they somehow know) to satisfy verification, while pointing the actual mutation at a different, victim organization's repository.

### Finding Description
The claimed binding is: `organization_verified_against_bytes == organization_owning_full_name`. Tracing the code shows this equality is never enforced.

- `verify_signature` computes `repository_owner` purely from attacker-controlled JSON: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0) .
- It uses that value to fetch a `GitHubApp` and verify the raw body against it: `github_app = Shipit.github(organization: repository_owner)` then `github_app.verify_webhook_signature(...)` [2](#0-1) .
- `Shipit.github` in multi-tenant mode looks up config strictly by the passed `organization` key: `config = github_app_config(organization)` [3](#0-2) .
- `GitHubApp#verify_webhook_signature` short-circuits to `true` if that organization's config has no `webhook_secret`: `return true unless webhook_secret` [4](#0-3) .
- `#create` re-parses the same raw body and dispatches to handlers using the event type only, with no re-check of `repository_owner`: `params = JSON.parse(request.raw_post); Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [5](#0-4) .
- `OpenedHandler#repository` resolves the target repository from a completely different field, `params.repository.full_name`, via `Shipit::Repository.from_github_repo_name` [6](#0-5) [7](#0-6) .
- If provisioning is enabled for that resolved repository, `ReviewStackAdapter#create!` creates a `ReviewStack` with attacker-controlled `branch` (from `pull_request.head.ref`) and stores the attacker-controlled PR title/body via `build_pull_request.update!(github_pull_request: params.pull_request)` [8](#0-7) .

Root cause: `repository_owner` (used to pick the verifying secret) and `repository.full_name` (used to pick the mutated repository/organization) are two independent, both attacker-supplied JSON fields with no cross-validation anywhere in `WebhooksController`, `Handler`, or `Repository.from_github_repo_name`. As long as the attacker names an organization key (`org-a`) that Shipit's multi-tenant `github_apps` config has with no `webhook_secret` set, `verify_webhook_signature` returns `true` for *any* body/signature combination, including a body whose `repository.full_name` names a totally different organization's private repo (`org-b/private-repo`).

Existing guards do not close this gap:
- `drop_unhandled_event` only filters by event type, not organization [9](#0-8) .
- The `GithubOrganizationUnknown` rescue only fires when the organization key is entirely absent from config, not when it exists but lacks a secret [10](#0-9) .
- `ExplicitParameters` schemas in the handlers validate types/presence of fields but perform no cross-repository consistency check [11](#0-10) .
- This entire path only matters in the multi-tenant `github_apps` configuration; in single-app mode `github_default_organization` is `nil` and `Shipit.github` always resolves to the single shared `secrets.github` config regardless of the `organization:` argument, per `def github(organization: github_default_organization) ... if github_default_organization.nil? then config = secrets.github` [3](#0-2) , so single-app deployments are not exposed by this specific divergence.

### Impact Explanation
An attacker who can send arbitrary HTTP POSTs to `/webhooks` (no auth required — the endpoint skips CSRF and has no other authentication) can forge a `pull_request` `opened` event for any repository already registered in Shipit with review stacks enabled, bypassing signature verification entirely, provided the deployment uses multi-tenant `Shipit.github_apps` config and at least one configured organization has no `webhook_secret` set. This results in creation of a `Shipit::ReviewStack` for a repository/org the attacker does not control, with attacker-controlled branch name and PR metadata, which is provisioning of infrastructure (`ReviewStackProvisioningQueue.add`) triggered without any legitimate signal from GitHub. This is a cross-tenant write ("a payload for one repository mutating another's stack"), matching the Critical severity category.

### Likelihood Explanation
Exploitability is conditioned on the operator running Shipit in the multi-org `github_apps` mode and having at least one configured organization without a `webhook_secret`. Given that, the attack has zero cost: a single unauthenticated POST with a crafted JSON body and the `X-Github-Event: pull_request` header, no valid `X-Hub-Signature` needed. It is fully repeatable against any repository already onboarded for review stacks in Shipit, for as long as any org in the config lacks a secret. The precondition (an org configured without `webhook_secret`) is a real supported state in the code (`@webhook_secret = @config[:webhook_secret].presence` allows this), not a hypothetical.

### Recommendation
In `WebhooksController#verify_signature`, after successful HMAC verification, bind the verified organization to the payload's actual `repository.full_name` owner (e.g. reject the request unless `repository_owner.downcase == params.dig('repository','full_name').split('/').first.downcase`). Additionally, do not allow `verify_webhook_signature` to silently return `true` for organizations with a missing `webhook_secret`; instead treat a missing secret as a hard misconfiguration that rejects all webhooks for that organization (fail closed rather than fail open).

### Proof of Concept
Minitest (`ActionDispatch::IntegrationTest`) plan:
1. Seed `Shipit.github_apps`-style multi-org test config with `org-a` having no `webhook_secret` and `org-b` (irrelevant secret set/unset) owning an existing `Shipit::Repository` `org-b/private-repo` with `review_stacks_enabled: true`, `provisioning_behavior: allow_all`.
2. Build JSON body: `{"action":"opened","number":1,"pull_request":{...,"head":{"ref":"attacker-branch"},"user":{"login":"attacker"},"labels":[]},"repository":{"owner":{"login":"org-a"},"full_name":"org-b/private-repo"},"sender":{"login":"attacker"}}`.
3. `post webhooks_path, params: body, headers: {'X-Github-Event' => 'pull_request', 'Content-Type' => 'application/json'}` with no `X-Hub-Signature` header (or an arbitrary invalid one).
4. Assert response is `200`, not `422`.
5. Assert `Shipit::ReviewStack.where(repository: org_b_repo, environment: 'pr1').exists?` is `true`, proving the equality `organization_verified ('org-a', no secret) == organization_owning_full_name ('org-b')` does not hold yet the write succeeded.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
