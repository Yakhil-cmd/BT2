### Title
`provision?` never applies `review_stacks_enabled` to the `prevent_with_label` (or `allow_with_label`) disjuncts due to Ruby operator precedence, letting an unprivileged PR author provision a review stack while `review_stacks_enabled=false` - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`PullRequest::OpenedHandler#provision?` combines `review_stacks_enabled` with the provisioning-behavior checks using `&&`/`||` without parentheses, so `&&` binds tighter and `review_stacks_enabled` is only applied to the `allow_all?` branch. Any PR opened without the provisioning label against a repository configured with `provisioning_behavior: prevent_with_label` will create a `ReviewStack` and enqueue it for provisioning even if `review_stacks_enabled` is `false`.

### Finding Description
Binding claimed vs. actual: `review_stacks_enabled == value consulted when evaluating (prevent_with_label? && !label)`. Tracing the code: [1](#0-0) 

Because `&&` has higher precedence than `||` in Ruby, this line parses as:

`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`

`review_stacks_enabled` is grouped only with `provisioning_behavior_allow_all?`; it is never consulted by the `allow_with_label?` or `prevent_with_label?` disjuncts. So for the actual equality: LHS = "value the code intends to check" (should gate all provisioning modes) vs RHS = "value actually read" (only gates `allow_all`) — these diverge for `prevent_with_label` and `allow_with_label` configurations.

Exploit flow: an unprivileged GitHub user opens a pull request with no labels against a repository whose `review_stacks_enabled` is `false` and `provisioning_behavior` is `prevent_with_label`. `process` calls `respond_to_pull_request_opened?` → `provision?` → the third disjunct `(prevent_with_label? && !pull_request_has_provisioning_label?)` evaluates true regardless of `review_stacks_enabled`. `ReviewStackAdapter#find_or_create!` then creates a `ReviewStack` and calls `Shipit::ReviewStackProvisioningQueue.add(stack)`: [2](#0-1) 

The queue subsequently provisions the stack: [3](#0-2) 

No existing guard catches this: the `ExplicitParameters` schema only validates payload shape, `respond_to_pull_request_opened?` only checks `action == "opened"` and delegates to the broken `provision?`, and there is no separate check re-verifying `review_stacks_enabled` downstream in `ReviewStackAdapter` or `ReviewStackProvisioningQueue`.

The existing test suite masks this because its only `prevent_with_label` test uses the default `provisioning_enabled: true`: [4](#0-3) [5](#0-4) 

### Impact Explanation
An attacker who can merely open a pull request (no Shipit credentials, no repo write access needed beyond opening a PR from a fork) triggers creation of a `ReviewStack` row and a provisioning-queue entry for a repository that explicitly disabled review stacks. Provisioning subsequently runs the repository's configured provisioning handler against the PR's head branch/checkout — exactly the automated-execution path `review_stacks_enabled=false` is meant to block. This is repeatable per pull request/repository configured this way and constitutes unauthorized stack creation/provisioning that bypasses an explicit configuration boundary (`review_stacks_enabled`), matching the Critical category of "a record written / provisioning triggered for a repository that did not authorize it."

### Likelihood Explanation
Preconditions: the target repository must have `review_stacks_enabled=false` and `provisioning_behavior=prevent_with_label` (or `allow_with_label`, which is likewise unaffected by `review_stacks_enabled`). No secrets, sessions, or privileged roles are required — only the ability to open a pull request without the provisioning label, which any GitHub user with fork/PR rights on the repository has. This is a pure logic bug always present under these configurations, cost is a single PR, and it is fully repeatable.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates every disjunct, e.g.:
```ruby
def provision?
  repository.review_stacks_enabled && (
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
  )
end
```

### Proof of Concept
minitest plan (add to `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`):
```ruby
test "does not create stacks for prevent_with_label repos when review_stacks_enabled is false" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,   # review_stacks_enabled = false
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = []  # no label -> !has_label? is true

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Before the fix, this assertion fails: `Shipit::Stack.count` increases by 1 and `Shipit::ReviewStackProvisioningQueue.add` is invoked, because `review_stacks_enabled` (false) is never read by the `prevent_with_label` disjunct in `provision?`. After applying the recommended parenthesization, `provision?` returns `false` and no stack/queue entry is created.
