### Title
Cross-Organization Webhook Forgery via Signature Verification Keyed on Attacker-Controlled `repository.owner.login` Field, Decoupled from the Repository Actually Acted Upon - (`app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to use for HMAC verification based on the attacker-supplied `repository.owner.login` field of the JSON payload, while the actual write operations dispatched afterwards (`Handler#stacks`) are keyed on the *separate* `repository.full_name` field of the same payload. In a multi-organization Shipit deployment, an attacker who knows (or controls) the webhook secret for any one configured GitHub organization can forge a signed payload whose `repository.owner.login` matches that known-secret organization but whose `repository.full_name` names a completely different, victim stack, causing Shipit to sync commits, update statuses, or process pull-request/check-suite events for a repository whose organization never authenticated the request.

### Finding Description
`WebhooksController` validates every inbound webhook with a single HMAC check before dispatching handlers: [1](#0-0) 

Concretely: [2](#0-1) [3](#0-2) 

`repository_owner` is read straight from the untrusted JSON body (`params.dig('repository', 'owner', 'login')`), and it is used to pick which per-organization `GitHubApp` (and thus which `webhook_secret`) is used to verify the signature: [4](#0-3) 

Shipit explicitly supports multiple independently configured GitHub organizations, each with its own `webhook_secret`, exactly so that a compromised/known secret for one org does not affect another: [5](#0-4) 

After the signature check passes, `WebhooksController#create` parses the same raw body and dispatches to handlers, which resolve the target `Stack`/`Repository` using a *different* field of the same payload — `repository.full_name` — with no cross-check against `repository.owner.login`: [6](#0-5) [7](#0-6) 

Because the signature verification and the object-of-action resolution are computed from two independent, both attacker-controlled, fields of the same POST body, there is no invariant enforced that "the organization whose secret validated this request" equals "the repository this request is going to mutate". Handlers such as `PushHandler` (`app/models/shipit/webhooks/handlers/push_handler.rb`) then act on `stacks` resolved purely from `repository.full_name`: [8](#0-7) 

This is confirmed by `Shipit.github` accepting an arbitrary `organization` argument and looking up a completely independent secret/config per org, with no relation enforced to any other field in the request: [9](#0-8) 

**Binding that should hold:** `organization_whose_secret_verified_signature == organization_that_owns_the_repository_being_written_to`.
**Binding actually enforced:** none — the two values are read from two independent JSON fields in the same attacker-supplied body, and only the first is covered by the HMAC signature semantics that GitHub normally guarantees end-to-end; here Shipit itself lets the attacker pick both independently.

### Impact Explanation
In any Shipit installation using the documented multi-organization `github:` config (`docs/setup.md#using-multiple-github-applications`), an attacker who is an administrator/owner of *any one* of the configured GitHub organizations (and therefore legitimately knows that org's `webhook_secret`, as they configured the GitHub App for it) can:
1. Compute a valid HMAC-SHA1 signature over a crafted JSON body using their own org's known `webhook_secret`.
2. Set `repository.owner.login` in that body to their own org login (so `verify_signature` picks their own known secret and passes).
3. Set `repository.full_name` in the same body to `victim-org/victim-repo`.
4. POST directly to `/github/webhooks` (bypassing GitHub entirely — this endpoint accepts any raw POST with a matching `X-Hub-Signature`).

This causes cross-repository writes: `GithubSyncJob` will be enqueued and will fetch/merge commit history into the victim stack, `StatusHandler` will create/alter commit statuses, `CheckSuiteHandler`/`PullRequest` handlers will process spoofed check/PR state changes for the victim stack — all attributed as legitimate GitHub-originated events for a repository the attacker's credentials were never authorized against. This falls squarely under the listed Critical impact category of "cross-repository writes" and can lead to triggering unauthorized deploys on the victim stack (e.g., via continuous deployment paths driven by `GithubSyncJob`/status updates).

### Likelihood Explanation
This requires only that the Shipit instance be configured for multiple GitHub organizations (a documented, supported configuration) and that the attacker be an admin of one of those organizations — no privileged Shipit session, `ApiClient` token, or access to the victim org is needed, matching the "unprivileged attacker" and "no Shipit session/token" constraints of scope. The webhook endpoint is intentionally public (`skip_before_action :verify_authenticity_token`), and the vulnerable code path (`verify_signature` keying off `repository.owner.login`, `Handler#stacks` keying off `repository.full_name`) is unconditionally in every request.

### Recommendation
After verifying the HMAC signature, re-derive/validate that the organization used to select the `webhook_secret` (`repository_owner`) matches the owner portion of `repository.full_name` (and/or the `organization.login` if present) before dispatching any handler; reject the request (422) on mismatch. Alternatively, always verify against every configured organization's secret only if that organization's login is consistent across all owner-identifying fields in the payload, or resolve the target repository/stack first and verify strictly against that repository's configured organization's secret rather than a value chosen independently by the attacker.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` (attacker knows/owns its `webhook_secret`) and `victim-org` (has a Shipit `Stack` tracking `victim-org/victim-repo`), per `docs/setup.md`'s multi-org schema (as exercised in `test/dummy/config/secrets_double_github_app.yml`).
2. Craft body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha that exists on victim repo, or any sha for GithubSyncJob to fetch>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org's webhook_secret, body)>`.
4. `POST /github/webhooks` with header `X-Github-Event: push`, the above signature, and the crafted body.
5. `WebhooksController#verify_signature` calls `Shipit.github(organization: 'attacker-org')` (per `repository_owner`), which succeeds because the signature was computed with that org's secret — request is accepted (`app/controllers/shipit/webhooks_controller.rb:24-38`).
6. `create` dispatches `PushHandler`, whose `stacks` is resolved via `Repository.from_github_repo_name('victim-org/victim-repo')` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`), enqueuing `GithubSyncJob` for the victim's stack — a write performed on a repository whose organization never validated this request.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
