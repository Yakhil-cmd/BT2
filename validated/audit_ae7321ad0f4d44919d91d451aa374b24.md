### Title
Replay of the Same Bitcoin L1 Lockup Output Across Multiple `register-for-bond` Calls Allows Double-Counting of Sats Never Additionally Locked - (File: `stackslib/src/chainstate/stacks/boot/pox-5.clar`)

### Summary
`pox-5.clar`'s L1-lockup verification path (`verify-l1-lockups` / `validate-l1-lockup`) only de-duplicates Bitcoin outpoints *within a single call* via a locally-scoped `seen-outpoints` accumulator that is reset to `(list)` on every invocation. There is no persistent, contract-level map recording outpoints that have already been credited to a staker across separate `register-for-bond` (or later re-registration/roll) calls. This mirrors the class of bug in the referenced report: two logically distinct operations (verifying a *new* BTC lock vs. re-presenting a proof of a lock already counted) end up sharing the same acceptance path, so a value that should only be credited once can be credited multiple times.

### Finding Description
`validate-l1-lockup` initializes `seen-outpoints: (list)` fresh for every call to `verify-l1-lockups` [1](#0-0) , and the duplicate check `(asserts! (is-none (index-of? seen-outpoints outpoint)) ERR_DUPLICATE_LOCKUP_OUTPOINT)` only prevents the *same* outpoint from appearing twice in the `outputs` list of the *same* call [2](#0-1) . The rest of the checks (script hash match, amount match, header/merkle proof validity, unlock-height floor) are all satisfiable repeatedly by resubmitting the exact same Bitcoin transaction output/proof data in a subsequent, independent transaction [3](#0-2) .

Because there is no global map tracking which Bitcoin outpoints have already been credited to a staker/bond (no `define-map` for used L1 outpoints was found anywhere in `pox-5.clar`), a staker can present the same BTC lockup proof again in a later call that consumes `verify-l1-lockups` (e.g. a follow-up `register-for-bond`/roll into a new bond index), and the sats sum returned by `verify-l1-lockups` would be accepted as valid a second time, since each call's fold state is independent.

### Impact Explanation
If the sats total returned by `verify-l1-lockups` is used to increase `protocol-bonds-total-staked`, `total-sbtc-staked`-equivalent L1 accounting, or the staker's `amount-sats` bond membership (as suggested by usage patterns seen in `unstake-sbtc`/`roll-sbtc` and bond membership state at [4](#0-3) ), then replaying the same BTC lockup proof lets an attacker inflate their credited sats without locking any additional BTC. This breaks the core equality that pox-5 relies on: *sats credited == sats actually and newly locked on Bitcoin*. The consequence is double-counting of a commitment (inflated reward shares / lowered effective STX-lock ratio for the same real collateral), which the rules classify as Critical impact (double-counting a commitment/reward, or crediting sats never locked on Bitcoin).

### Likelihood Explanation
This requires no privileged role — any staker who has previously submitted a valid L1 lockup can independently resubmit the identical `tx`/`header`/`leaf-hashes`/`output-index` payload (which is public, since it's Bitcoin chain data) in a new `register-for-bond`-class call. The only gating conditions (`unlock-burn-height`, `minimum-unlock-height`, non-duplicate-within-call) are all satisfied trivially by re-use across calls. This makes the likelihood high, limited only by whatever call-level gating (e.g., "already has a membership" checks) exists in the calling function, which I was not able to fully trace given tool-call limits.

### Recommendation
Persist a durable map (e.g., `l1-lockup-outpoints-used: { txid: (buff 32), output-index: uint } -> bool`) that is checked and set as outpoints are validated in `validate-l1-lockup`, so that once a specific Bitcoin outpoint has been credited to a staker, any future presentation of the same outpoint (in the same or a different call) is rejected with a duplicate-outpoint error, mirroring the intra-call check but made global and persistent across the contract's lifetime.

### Proof of Concept
1. Staker locks BTC via the timelock script and constructs a valid `lockups` proof for output `(txid, output-index)`.
2. Staker calls `register-for-bond` (bond 0), which calls `verify-l1-lockups` → `validate-l1-lockup`, passing all asserts, crediting `amount` sats to the staker's bond.
3. Later, staker calls a follow-up bonding action (e.g., roll to bond 6 / re-register) supplying the *same* `(txid, output-index, tx, header, leaf-hashes)` proof again.
4. Because `seen-outpoints` is re-initialized to `(list)` per call at [5](#0-4)  and no contract-level persistent record of previously-used outpoints exists, all `asserts!` in `validate-l1-lockup` pass again, and the sats amount is counted a second time toward the staker's credited sats without any new BTC being locked.

**Caveat / uncertainty**: I was not able to fully trace the complete body of `register-for-bond`/`update-bond-registration` (only partial context was available via search) to confirm whether an outer-level check (e.g., "already registered for this exact outpoint set") independently blocks this replay before reaching `verify-l1-lockups`. The absence of any `define-map` keyed on Bitcoin outpoints anywhere in `pox-5.clar` is the strongest evidence supporting this finding, but a full read of the calling functions would be needed to rule out an alternate mitigating check.
