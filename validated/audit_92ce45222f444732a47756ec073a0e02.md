### Title
Live re-read of `total_issuance`/`active_issuance` in `pallet-referenda`'s support/approval checks lets a permissionless `Balances::burn` shrink the electorate denominator and tip a marginal referendum into passing - ([File: substrate/frame/referenda/src/lib.rs])

### Summary
`pallet-conviction-voting`'s `Tally::support`/`approval` divide the aye/nay vote weight by `Total::get()`, which resolves to the *current* total or active issuance of the native currency. `pallet-referenda::is_passing` (and everything that calls it — `service_referendum`, `nudge_referendum`, `decision_time`) re-evaluates this ratio live, on every block/nudge, rather than against a value snapshotted when the referendum entered deciding/confirming. Because `pallet-balances` exposes a fully permissionless `burn` extrinsic that immediately reduces `TotalIssuance`/`ActiveIssuance`, any signed account can shrink the denominator of `support()`/`approval()` at will, artificially inflating the computed support/approval percentage and helping a referendum that is currently *not* clearing its track's `min_support`/`min_approval` curve to cross the threshold and get confirmed. This is the same root-cause pattern as the Pyth Governance report: a voter-weight/threshold ratio whose denominator is the mutable, attacker-influenceable token supply, read at settlement time rather than pinned at vote-cast time.

### Finding Description
- `Tally::support`/`approval` (conviction-voting) compute `Perbill::from_rational(self.support, Total::get())` and `Perbill::from_rational(self.ayes, self.ayes+self.nays)`. [1](#0-0) 
- `Total` is bound to `Get<Votes>` in the runtime config as `TotalIssuanceOf<Balances, AccountId>` (relay-chain style) or `ActiveIssuanceOf<Balances, AccountId>` (staking-async RC runtime), both of which simply forward to `pallet_balances`'s live issuance storage on every call — there is no caching/snapshotting. [2](#0-1) [3](#0-2) 
- `pallet-referenda::is_passing` is the function that decides whether a referendum is in a "Passing" state (used to start/continue/abort the confirmation window and to finally confirm approval); it calls `tally.support(id)` and `tally.approval(id)` fresh, every time it's invoked from `service_referendum`/`nudge_referendum`. [4](#0-3) [5](#0-4) 
- `pallet-balances` exposes a signed, permissionless `burn` call that reduces `TotalIssuance` immediately and irreversibly (distinct from sending to a "burn address," which does not touch issuance). [6](#0-5) [7](#0-6) 

The attacker entry point is a normal signed extrinsic (`Balances::burn`), no privileged origin required. The affected state (`support`/`approval` percentage that gates `ConfirmStarted`/`Confirmed`/enactment scheduling) depends on this attacker-manipulable denominator at exactly the moments the pallet checks it (start-of-deciding, each `nudge_referendum`, and the moment the confirm-period alarm fires), not on a value fixed when the referendum entered its confirming phase.

### Impact Explanation
If exploited, an attacker who is a large token holder (holding tokens outside those locked for voting) can burn a portion of that holding right before a scheduled `nudge_referendum`/alarm tick to depress `Total::get()` and push a referendum whose current `tally.support`/`approval` is marginally below the track's `min_support`/`min_approval` curve into the "Passing" state, causing it to start/continue confirming and ultimately be `Confirmed` and scheduled for enactment via `schedule_enactment`. This grants unauthorized dispatch of whatever call the referendum carries (potentially root-level actions depending on track), matching the "attacker obtains governance authority" impact class flagged in the source report.

### Likelihood Explanation
Reachability is real (permissionless extrinsic, live-read arithmetic, no privileged prerequisite), but exploitation is economically gated: to move `support`/`approval` by a meaningful amount the attacker must destroy a comparable fraction of the chain's *entire* issuance (e.g., DOT/KSM total supply is in the billions), which is the same "burn cost vs. governance payoff" trade-off the original report models. This mirrors the report's own caveat that the attack "only makes sense" when the marginal percentage needed is small and the value of controlling the proposal outcome exceeds the burn cost. On tracks with small `min_support` floors late in the decision/confirm period (curves are `LinearDecreasing`/`Reciprocal` toward low floors), the required burn to tip a marginal vote could be comparatively modest. I could not fully verify, within the available context, the exact `min_support` floor values and decision-period timing for every live track (only rococo/collectives sample tracks were inspected), nor whether any track-specific safeguard (e.g., a snapshot of issuance at decision start) exists elsewhere in downstream runtime configuration that I did not locate.

### Recommendation
- Snapshot `total_issuance`/`active_issuance` once when a referendum begins deciding (or at referendum submission) and use that fixed value for all subsequent `support`/`approval` computations for that referendum's lifetime, instead of calling `Total::get()` live on every `is_passing` check.
- Alternatively, require `Balances::burn` (and any other issuance-reducing action) to respect an `active_issuance`/deciding-referenda freeze, or rate-limit/delay the effect of burns on referenda that are currently in their confirmation window.

### Proof of Concept
No executable local reproduction was run (out of scope for this analysis pass; only static/code-path verification was performed). Evidence supporting reachability:
- `Balances::burn` is a real, signed, unprivileged extrinsic that decrements `TotalIssuance` synchronously: verified at `substrate/frame/balances/src/lib.rs:850-874` and `substrate/frame/balances/src/impl_currency.rs:336-351`, with a passing unit test showing immediate issuance reduction (`burn_works`, `substrate/frame/balances/src/tests/dispatchable_tests.rs:339-384`).
- `Tally::support`/`approval` divide by the live `Total::get()` (`substrate/frame/conviction-voting/src/types.rs:64-79`), and `Total` is wired to `TotalIssuanceOf`/`ActiveIssuanceOf` in shipped runtimes (`substrate/bin/node/runtime/src/lib.rs:1028-1038`; `substrate/frame/staking-async/runtimes/rc/src/governance/mod.rs:38-49`).
- `is_passing`/`service_referendum` re-read this ratio on every nudge (`substrate/frame/referenda/src/lib.rs:1315-1329`, `1183-1222`), with no snapshot of issuance taken at deciding/confirming start.
A minimal integration test to demonstrate this concretely would: (1) submit and decide a referendum whose `tally.support` sits just under `track.min_support`'s current curve value, (2) have a second, unrelated signed account call `Balances::burn` for enough of its own balance to shrink `TotalIssuance` so that `Perbill::from_rational(tally.support, TotalIssuance)` crosses the curve threshold, (3) call `nudge_referendum` and observe the referendum transition to `ConfirmStarted`/`Confirmed` where it previously would not have. This was not executed against the test harness in this pass, so exploitation is demonstrated by code-path analysis only, not by an executed test run.

	/// Determine whether the given `tally` would result in a referendum passing at `elapsed` blocks
	/// into a total decision `period`, given the two curves for `support_needed` and
	/// `approval_needed`.
	fn is_passing(
		tally: &T::Tally,
		elapsed: BlockNumberFor<T, I>,
		period: BlockNumberFor<T, I>,
		support_needed: &Curve,
		approval_needed: &Curve,
		id: TrackIdOf<T, I>,
	) -> bool {
		let x = Perbill::from_rational(elapsed.min(period), period);
		support_needed.passing(x, tally.support(id)) &&
			approval_needed.passing(x, tally.approval(id))
	}

	// Burn funds from the total issuance, returning a positive imbalance for the amount burned.
	// Is a no-op if amount to be burned is zero.
	fn burn(mut amount: Self::Balance) -> Self::PositiveImbalance {
		if amount.is_zero() {
			return PositiveImbalance::zero();
		}
		<TotalIssuance<T, I>>::mutate(|issued| {
			*issued = issued.checked_sub(&amount).unwrap_or_else(|| {
				amount = *issued;
				Zero::zero()
			});
		});

		Pallet::<T, I>::deposit_event(Event::<T, I>::Rescinded { amount });
		PositiveImbalance::new(amount)
	}
