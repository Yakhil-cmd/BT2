### Title
Incomplete Windows reserved-filename check allows alternate-data-stream bypass targeting reserved device names - ([File: pkg/cmd/release/download/download.go])

### Finding Description
`isWindowsReservedFilename` only strips everything after the **first** `.` and does a case-insensitive comparison against a static list of reserved device names (`CON`, `PRN`, `AUX`, `NUL`, `COM0-9`, `LPT0-9`): [1](#0-0) 

The function does not strip Windows Alternate Data Stream (ADS) syntax (`:`), nor does it account for trailing dots/spaces that Windows itself trims from filenames. An attacker who publishes a GitHub release in their own repo fully controls the `name` field of a release asset (`a.Name`), which flows unchecked into this function: [2](#0-1) 

For an asset named `CON:stream` or `COM1:foo`, `strings.Split(filename, ".")[0]` returns the whole string unchanged (no `.` present), so `"CON:STREAM"` / `"COM1:FOO"` never match the reserved-name list, and the check silently passes. However, on Windows, `CreateFile`/`os.OpenFile` treats the substring before the first `:` as the base filename and the remainder as an ADS name — meaning `CON:stream` still resolves to the reserved `CON` device, not a regular file. The value later reaches `filepath.Join` and `os.OpenFile` in `Copy`: [3](#0-2) 

Because the intended defense is entirely name-string based and the colon-stripping/extension-handling logic is incomplete, this specific defense-in-depth check can be bypassed for this class of names.

### Impact Explanation
On a Windows victim machine, `gh release download` on an attacker's release containing an asset named `CON:stream` (or similar) would bypass the reserved-filename guard and call `os.OpenFile` against a Windows reserved device path instead of a plain file. Depending on the device (`CON`, `COM1`, etc.) this can cause the download to hang, error unpredictably, or write attacker-supplied bytes to a device stream instead of disk — a functional/availability issue (denial-of-service against the local `gh` process) rather than path traversal, code execution, or credential exfiltration. It does not achieve arbitrary file write **outside** the destination directory (path confinement itself is not broken — `filepath.Join(dir, name)` still resolves under `dir`), and it does not disclose credentials or provide code execution, so it falls short of the "Critical" impact classes (RCE, credential theft, auth bypass, cross-host request) required by the bounty impact rules.

### Likelihood Explanation
Trivial precondition: attacker only needs to publish a public release with an asset named e.g. `CON:stream` in a repo/fork they control, then have the victim run `gh release download` against it on a Windows machine. Fully repeatable and requires no privileges beyond normal release publishing.

### Recommendation
Harden `isWindowsReservedFilename` to also strip everything from the first `:` (and handle trailing dots/spaces) before comparing against the reserved-name list, e.g. `filename = strings.SplitN(filename, ":", 2)[0]` prior to the existing `.`-split/uppercase logic.

### Proof of Concept
```go
func TestIsWindowsReservedFilename_ADSBypass(t *testing.T) {
    // Current implementation misses these because no '.' is present
    // and the colon is not stripped.
    assert.True(t, isWindowsReservedFilename("CON:stream"))   // currently FALSE (bug)
    assert.True(t, isWindowsReservedFilename("COM1:foo"))     // currently FALSE (bug)
}
```
Run on the current implementation: both assertions fail, confirming the bypass of the reserved-filename guard called at `download.go:203` before assets reach `destinationWriter.Copy` -> `os.OpenFile` (`download.go:442`).

Given the confirmed but limited impact (DoS/odd device behavior on victim's Windows box, not path-confinement break or RCE/credential leak), this should be reported as a moderate hardening issue rather than a Critical vulnerability.
