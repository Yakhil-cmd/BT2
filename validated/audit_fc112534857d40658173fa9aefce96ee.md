### Title
Unbounded `i128` multiplication in index accrual permanently freezes a whale market before the borrow-index cap can engage - (File: common/src/rates/index.rs)

### Summary
The gnark fix replaced a platform-dependent limb count with `bits.Len` so multiplication overflow is detected correctly. The analog here is `i128` product overflow detection in the fixed-point accrual path: `update_borrow_index` multiplies `old_index * interest_factor` **before** clamping to `MAX_BORROW_INDEX_RAY`, and `scaled_to_original`/debt valuation multiplies `borrowed * index` in raw `i128`. For a large market the debt valuation overflows `i128` long before the index cap engages, and since every verb accrues first via `global_sync`, the market is bricked — no repay, withdraw, liquidate, or even `update_indexes` succeeds.

### Finding Description
In `common/src/rates/index.rs`, `update_borrow_index` computes `old_index.mul(env, interest_factor)` in `i128` and only afterwards compares to `MAX_BORROW_INDEX_RAY` (lines 13-19). Likewise `update_supply_index` computes `supplied.mul(env, old_index)` (line 34) and `calculate_supplier_rewards` computes `borrowed * index` valuations (line 80). `Ray::mul` bottoms out in `fp_core::mul_div_half_up`, which panics with `GenericError::MathOverflow` when the result does not fit `i128` — the widened `I256` path only rescues the intermediate product, not a result exceeding `i128` (`common/src/math/fp_core.rs:122-143`).

Every state-changing entrypoint runs `global_sync` → `accrue_chunk` → `accrue_step` first (`contracts/pool/src/interest.rs:20-53`), so once `borrowed * new_index` exceeds `i128::MAX`, the panic is on every path. The index cap was intended to bound growth, but the pre-clamp multiply and the debt revaluation overflow first.

The repository's own test harness proves this end state: `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:316-361`) shows a ~1e27-unit market at 98% utilization on the steep XLM rate curve panics with `MATH_OVERFLOW` inside `scaled_to_original`, `borrow_index < MAX_BORROW_INDEX_RAY`, and `withdraw`/`repay` both revert with the same error.

### Impact Explanation
Permanent freezing of funds: once the scaled-debt valuation crosses `i128::MAX`, suppliers cannot withdraw, borrowers cannot repay, liquidators cannot liquidate, and `update_indexes` itself reverts. There is no recovery path because accrual is unconditional. Impact class: permanent freezing of funds / contract unable to operate.

### Likelihood Explanation
Requires a very large market (order 1e9 × 10^18 units, i.e. an 18-decimal asset with whale-scale supply) and sustained high utilization on a steep rate curve so the index compounds to ~170x before the cap. An unprivileged attacker can create and grow such a market via `supply`/`borrow` with their own capital; no privilege is needed. Likelihood is low for current realistic assets (hence Medium, not High), but it is a deterministic cliff rather than a race, and anyone can push the market over it by supplying and borrowing at high utilization — or simply wait for organic accrual. Notably the asserted bound in `docs/reference/formulas.md` is wrong per the test's own comment, so this is an under-documented edge, not an accepted ADR trade-off.

### Recommendation
- Perform the cap check against a widened `I256` product, or clamp `new_index` via `mul_div_floor_saturating` before comparing, so the cap engages instead of the multiply overflowing.
- Bound scaled-position sizes (`borrowed`, `supplied`) so that `position * MAX_BORROW_INDEX_RAY` always fits `i128` — e.g., enforce at listing/borrow time via `require_cap_within_asset_domain`-style validation.
- At minimum, let `update_indexes` saturate the index at the cap on overflow rather than panic, so a one-way ratchet cannot brick the market.

### Proof of Concept
```rust
// tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320
let mut t = LendingTest::new()
    .with_market(big("BIG18", 18, xlm_curve()))
    .with_market(col())
    .with_max_utilization_disabled_all_markets()
    .build();
lift_caps(&t, "BIG18", 18);
let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);
t.borrow_raw(ALICE, "BIG18", principal / 100 * 98);

loop {
    t.advance_time(YEAR_SECS);
    if let Err(e) = t.try_update_indexes_for(&["BIG18"]) { break e; }
}
// update_indexes panics MATH_OVERFLOW in scaled_to_original while
// borrow_index < MAX_BORROW_INDEX_RAY; then:
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```
Overflow sites: `update_borrow_index` pre-clamp multiply (`common/src/rates/index.rs:14`), `supplied * old_index` (`index.rs:34`), `borrowed * index` (`index.rs:80`), all panicking via `fp_core::mul_div_half_up` (`common/src/math/fp_core.rs:108-118`) on the unconditional `global_sync` path (`contracts/pool/src/interest.rs:20-53`).
