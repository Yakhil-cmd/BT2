### Title
Webhook signature verification is bound to `repository.owner.login`, but the handlers that mutate state trust the independent, unverified `repository.full_name` field, enabling cross-organization forgery in multi-org deployments - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which GitHub App/webhook secret to authenticate a delivery with by reading `repository.owner.login` (falling back to `organization.login`) out of the *unverified* JSON body, then HMAC-verifies the raw body against that org's secret.<cite repo="Camomtat/shipit-engine--006" path="app/controllers/shipit/webhooks_controller.rb" start="24-30" end="59-62" /> Once verification passes, the actual handlers that mutate data (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`) don't re-derive the target from the same `repository.owner.login`/secret used to authenticate — they instead look up the target repository via the independent `repository.full_name` field.<cite repo="Camomtat/shipit-engine--006" path="app/models/shipit/webhooks/handlers/handler.rb" start="32-38" end="32-38" />

### Finding Description
This is structurally analogous to the Wildcat finding: a value used to establish trust (`repository.owner.login`, which selects the secret used for the equality "payload signature == HMAC(secret_of(repository.owner.login), raw_body)") is not the same value later trusted to determine *what is written* (`repository.full_name`, used by `Handler#repository_name` → `Repository.from_github_repo_name` → `stacks`). Both fields live in the same attacker-influenced JSON body but are never cross-checked against each other.

In a single-org Shipit deployment this is harmless, since there is only one secret and `repository.owner.login` necessarily equals the owner prefix of `repository.full_name` for genuine GitHub deliveries. But Shipit explicitly documents and supports multi-organization deployments, where each org has its own GitHub App, own `webhook_secret`, and own admin who legitimately possesses that secret (they typed it into `config/secrets.yml` themselves).<cite repo="Camomtat/shipit-engine--006" path="lib/shipit/github_app.rb" start="44-57" end="44-57" /> Nothing in `Shipit::GithubApp#verify_webhook_signature` or in `WebhooksController#verify_signature` binds the secret owner to the `repository.full_name` that downstream handlers use for lookups: `verify_signature` only checks the HMAC of the whole raw body against the secret chosen via `repository_owner`.<cite repo="Camomtat/shipit-engine--006" path="lib/shipit/github_app.rb" start="76-83" end="76-83" />

An administrator of Org B (who legitimately knows only Org B's `webhook_secret`, and has no privileges over Org A's stacks/repositories in the shared Shipit instance) can therefore craft an arbitrary JSON body where:
- `repository.owner.login` = `"org-b"` (so `WebhooksController#repository_owner` selects Org B's GithubApp and its secret for verification), and
- `repository.full_name` = `"org-a/private-repo"` (an entirely different, unrelated repository tracked by a different stack).

Sign that body with Org B's known `webhook_secret` and POST it to `/github/webhooks`. `verify_signature` passes because it only checks that the HMAC matches Org B's secret; it never checks that `repository.full_name`'s owner segment equals `repository.owner.login`.<cite repo="Camomtat/shipit-engine--006" path="app/controllers/shipit/webhooks_controller.rb" start="59-62" end="59-62" /> The event is then dispatched to handlers, e.g. `PushHandler`, which resolves the target purely from `repository.full_name` via `Handler#repository_name`/`stacks`, and calls `stack.sync_github(expected_head_sha: params.after)` on Org A's stacks.<cite repo="Camomtat/shipit-engine--006" path="app/models/shipit/webhooks/handlers/push_handler.rb" start="12-17" end="12-17" /> `StatusHandler` similarly writes a fabricated commit status onto any commit matching an attacker-chosen `sha` regardless of which org's secret authenticated the request.<cite repo="Camomtat/shipit-engine--006" path="app/models/shipit/webhooks/handlers/status_handler.rb" start="20-24" end="20-24" /> `CheckSuiteHandler` likewise acts on `stacks` resolved from the forged `repository.full_name`.<cite repo="Camomtat/shipit-engine--006" path="app/models/shipit/webhooks/handlers/check_suite_handler.rb" start="13-17" end="13-17" />

Note: `MembershipHandler` is not exploitable this way because membership payloads have no `repository` key, so `repository_owner` falls back to `organization.login`, and `MembershipHandler` also reads `params.organization.login` directly — the value used for verification and the value used for the write are the same field in that one case.<cite repo="Camomtat/shipit-engine--006" path="app/controllers/shipit/webhooks_controller.rb" start="59-62" end="59-62" /> <cite repo="Camomtat/shipit-engine--006" path="app/models/shipit/webhooks/handlers/membership_handler.rb" start="15-21" end="15-21" />

### Impact Explanation
This breaks the binding "organization whose secret authenticated the delivery == repository that is written," enabling cross-repository/cross-organization writes: an actor who is only trusted for Org B can inject fabricated pushes, statuses, and check-suite results against Org A's stacks in the same Shipit instance, which is explicitly listed as a Critical impact ("cross-repository writes"). Depending on downstream consumption, this can also influence deploy gating (fake `status` events feeding `create_status_from_github!`, fake `check_suite` triggering refresh of check runs) affecting whether Org A's stacks are considered deployable.

### Likelihood Explanation
Requires the attacker to control (or be an admin of) at least one GitHub organization/App configured in the same multi-tenant Shipit instance — this is an unprivileged position relative to the *victim* organization's repositories, matching the "unprivileged attacker" framing of the rules (no Shipit session, `ApiClient` token, or victim-org credentials are needed). The multi-org configuration is a documented, supported feature, so the precondition is realistic for any shared/multi-tenant Shipit deployment.

### Recommendation
In `WebhooksController#verify_signature`/`repository_owner`, after selecting the GitHub App by `repository.owner.login` (or `organization.login`), assert that this same owner matches the owner segment of `repository.full_name` before dispatching to handlers; reject (422) on mismatch. Alternatively, have each `Handler` re-validate that `repository.full_name`'s owner equals the organization that authenticated the webhook (passed down from the controller) rather than trusting `repository.full_name` unconditionally.

### Proof of Concept
1. Deploy Shipit configured for two orgs, `org-a` and `org-b`, each with its own `webhook_secret` (per `docs/setup.md`'s multi-org example).
2. As the admin of `org-b` (who set/knows `org-b`'s `webhook_secret`), craft a `push` event JSON body:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen sha>",
     "repository": { "owner": { "login": "org-b" }, "full_name": "org-a/private-repo" }
   }
   ```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(org-b webhook_secret, body)>` and send it to `/github/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#repository_owner` reads `"org-b"`, `Shipit.github(organization: "org-b")` is used to verify — signature matches, request is accepted.<cite repo="Camomtat/shipit-engine--006" path="app/controllers/shipit/webhooks_controller.rb" start="24-30" end="24-30" />
5. `PushHandler#process` resolves `stacks` via `repository.full_name` = `"org-a/private-repo"` and calls `sync_github` on Org A's stack, even though the delivery was never authenticated by anything Org A controls.<cite repo="Camomtat/shipit-engine--006" path="app/models/shipit/webhooks/handlers/handler.rb" start="32-38" end="32-38" /> <cite repo="Camomtat/shipit-engine--006" path="app/models/shipit/webhooks/handlers/push_handler.rb" start="12-17" end="12-17" />
