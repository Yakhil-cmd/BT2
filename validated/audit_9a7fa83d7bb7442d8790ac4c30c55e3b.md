### Title
Webhook signature verified against `repository.owner.login` while event handlers dispatch on the independent `repository.full_name` field, allowing cross-repository status/sync injection - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
Shipit supports hosting multiple GitHub organizations in a single instance, each with its own `webhook_secret` [1](#0-0) . Incoming webhooks are authenticated by looking up the `GitHubApp` for the organization named in `repository.owner.login` (or `organization.login`) and verifying the HMAC signature with *that* organization's secret [2](#0-1) [3](#0-2) . However, once the signature passes, every event handler resolves the target `Repository`/`Stack` using a *different* JSON field, `repository.full_name`, with no cross-check against `repository.owner.login` [4](#0-3) .

### Finding Description
This is analogous to the Chainlink report's core issue: a return value used to establish trust (`updatedAt`) is decoupled from the value actually consumed by dependent logic (the price), so a check on one field doesn't guarantee correctness of the other. Here, the binding broken is: **the organization whose credential authenticated the request** (`repository.owner.login`, used to pick the `GitHubApp`/`webhook_secret` in `Shipit.github(organization: repository_owner)`) **≠ the repository that is actually written to** (`repository.full_name`, used by `Handler#repository_name` / `Handler#stacks`).

`GitHubApp#verify_webhook_signature` only checks the HMAC of the raw body against the secret of the organization selected by `repository_owner` [5](#0-4) . Nothing enforces that `full_name` (used everywhere downstream) is actually owned by that same organization. An operator running Shipit for multiple organizations (as explicitly documented) configures independent `webhook_secret`s per org [6](#0-5) . Any org owner/admin who is a legitimate tenant of the Shipit instance controls their own `webhook_secret` and can therefore produce a validly signed payload where `repository.owner.login` is their own org (so the signature check passes with their own secret) but `repository.full_name` names a victim repository/stack tracked under a different tenant.

Handlers such as `PushHandler` (`stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(...) }`) [7](#0-6)  and `StatusHandler` (`Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`) [8](#0-7)  act purely on attacker-supplied `sha`/`full_name`/state fields, resolving repositories/stacks/commits with no re-verification that the authenticated organization owns them.

### Impact Explanation
`StatusHandler` directly persists a fabricated commit status (`state`, `context`, `description`) for any `sha` present in Shipit's database, regardless of which org's secret signed the request [9](#0-8) . Commit deployability is gated by required/blocking statuses (`Commit#deployable?`, `Stack#required_statuses`/`blocking_statuses`) [10](#0-9) . By injecting a forged `success` status for a required/blocking CI context on a victim's commit, a tenant of a shared Shipit instance can flip `deployable?` to true and enable an unauthorized deploy of a repository they do not own — matching the Critical "unauthorized deploy" impact class.

### Likelihood Explanation
This requires the Shipit instance to be configured for multiple GitHub organizations (a documented, supported configuration) and for the attacker to control a legitimate GitHub App/webhook installation for one of those tenant organizations — i.e., an unprivileged-with-respect-to-the-victim-repo attacker who is nonetheless a valid tenant of the shared instance. No `webhook_secret`, `GITHUB_TOKEN`, or session of the target org is needed; the attacker uses only their own org's credentials.

### Recommendation
In `WebhooksController#verify_signature` / `Handler`, cross-validate that `repository.owner.login` (the organization whose secret authenticated the request) matches the owner segment of `repository.full_name` before dispatching to any handler, rejecting mismatched payloads with `422`.

### Proof of Concept
1. Shipit instance configured with two tenant orgs, `attacker-org` (secret known to attacker) and `victim-org` (tracks stack `victim-org/app`, branch `main`, with `ci/required` as a required status).
2. Attacker crafts a `status` event payload: `{"sha": "<victim commit sha>", "state": "success", "context": "ci/required", "repository": {"full_name": "victim-org/app", "owner": {"login": "attacker-org"}}}`.
3. Attacker signs the raw body with `attacker-org`'s webhook secret and sends it with header `X-Hub-Signature`.
4. `WebhooksController#verify_signature` looks up `Shipit.github(organization: "attacker-org")` and the signature verifies successfully [2](#0-1) .
5. `StatusHandler#process` resolves commits by `sha` only and creates a forged `success` status for `victim-org/app`'s commit [8](#0-7) , satisfying the required-status gate and enabling deployment of that commit without any legitimate CI success or victim-org credential involvement.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

**File:** lib/shipit.rb (L170-200)

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
