### Title
Permissionless `update_account_threshold` lets any account restamp another user's liquidation terms and LTV without owner consent - ([File: contracts/controller/src/risk/params.rs](contracts/controller/src/risk/params.rs))

### Summary
The CVAT bug class is a mutating endpoint that checks only that *a* user authenticated, not that the caller owns the resource being modified. `Controller::update_account_threshold` is the direct analog: any authenticated caller may pass arbitrary `account_ids` and rewrite each victim's stored `loan_to_value`, and — with `has_risks = true` — their `liquidation_threshold`, `liquidation_bonus`, and `liquidation_fees`. The only protection is a post-update health-factor floor of 1.05 WAD, which does not prevent an attacker from choosing *when* a victim absorbs a liquidator-favoring parameter change. A third-party `supply` top-up triggers the same unconditional restamp for the supplied asset, providing a second unauthorized path.

### Finding Description
`update_account_threshold` authenticates the caller via `require_authorized_caller` but never checks that the caller owns, or is a delegate of, any account in `account_ids`. For each target, `sync_account_thresholds` loads the victim's positions and calls `refresh_supply_risk_params`, which unconditionally writes `position.loan_to_value = effective_config.loan_to_value` before any gating [1](#0-0) . With `FullTuple` scope (`has_risks = true`), `apply_gated_liquidation_params` also overwrites the victim's `liquidation_threshold`, `liquidation_bonus`, and `liquidation_fees`; the sole check is `clears_min_hf` requiring post-update HF ≥ 1.05, applied only when the change `favors_liquidator` and the account has debt [2](#0-1) . The function then persists the rewritten positions with `storage::set_supply_positions` [3](#0-2) .

The gating is asymmetric in the attacker's favor: it guarantees the victim survives the *instant* of the restamp, but nothing prevents the attacker from applying a lowered liquidation threshold (or raised bonus/fees) at a strategically chosen moment — e.g., immediately after governance tightens parameters but before a price drawdown — so that the victim enters liquidation sooner and the liquidator extracts a larger bonus than the terms the owner actually accepted. A second path exists: `process_supply` lets any third party top up a victim's existing supply position, and `merge_supply_leg` unconditionally calls `refresh_supply_risk_params` with `RiskRefreshScope::FullTuple` on that position [4](#0-3) [5](#0-4) . Even `LtvOnly` restamps degrade the victim's stored LTV snapshot, reducing borrowing headroom the owner never agreed to forfeit.

This mirrors the CVE precisely: the endpoint authenticates a caller but performs a PATCH on resources (other users' positions) it does not authorize per-resource.

### Impact Explanation
Loss of user funds / premature liquidation. After a governance risk-parameter tightening, an attacker can force-apply the harsher liquidation tuple to every account with HF ≥ 1.05 at the moment of their choosing, instead of letting the owner restamp on their own schedule (which the lazy-restamp design otherwise grants). Victims then get liquidated earlier and pay higher bonuses/fees than their stored terms warranted; the value flows to liquidators and the protocol. The LTV-only variant additionally imposes an unconsented reduction of borrowing capacity. Impact is bounded by the 1.05 HF gate and by the fact that applied parameters come from the current spoke config, so the attacker cannot invent arbitrary values — consistent with Medium severity.

### Likelihood Explanation
Requires a governance parameter change that `favors_liquidator` (lowered `liquidation_threshold`, raised `liquidation_bonus`, or lowered `liquidation_fees`) or a lowered LTV — a routine risk-management operation. Any unprivileged address can then call `update_account_threshold(true, [victim_ids])` permissionlessly; no special position, capital, or timing edge is needed beyond submitting the transaction. Motivation exists for liquidators competing to position victims under worse terms before adverse price moves.

### Recommendation
Gate `update_account_threshold` (and third-party `supply`-triggered restamps) so that only the account owner or an active delegate may apply `FullTuple`/liquidator-favoring restamps to an account. Concretely: in `sync_account_thresholds`, after resolving `owner`, enforce `require_owner_or_delegate(env, account_id, &caller, &owner)` whenever the scope is `FullTuple` or when the effective config `favors_liquidator` relative to the stored tuple; keep permissionless refresh only for strictly account-favoring updates. For `process_supply`, restrict the `FullTuple` restamp in `merge_supply_leg` to owner/delegate callers, or fall back to `LtvOnly` (or no restamp) for third-party top-ups of existing positions.

### Proof of Concept
1. Governance calls `edit_asset_in_spoke` lowering `liquidation_threshold` (and/or raising `liquidation_bonus`) for a hub asset held by victim account `V` (HF ≈ 1.2). `V`'s stored position retains the old, safer tuple because restamps are lazy.
2. Attacker (any account) calls `controller.update_account_threshold(attacker, true, vec![V])`.
3. `sync_account_thresholds` resolves `V`'s owner but never compares it to `caller`; `apply_gated_liquidation_params` sees the change `favors_liquidator`, `clears_min_hf` passes (HF ≥ 1.05), and `V`'s `liquidation_threshold`/`bonus`/`fees` are overwritten and persisted via `set_supply_positions` [6](#0-5) .
4. `V` is now liquidatable under the tightened terms at a price level the owner never accepted; the attacker liquidates via `controller.liquidate(...)` capturing the raised bonus.
5. Alternative trigger without `update_account_threshold`: attacker calls `supply(attacker, V, spoke, [(hub_asset, dust)])`; `require_third_party_existing_supply` passes because `V` already holds the asset, and `merge_supply_leg` applies the same `FullTuple` restamp [4](#0-3) [5](#0-4) .

    env: &Env,
    account_id: u64,
    scope: RiskRefreshScope,
    cache: &mut Context,

    let Some(meta) = storage::try_get_account_meta(env, account_id) else {
        return;
    };

    let supply_positions = storage::get_supply_positions(env, account_id);
    if supply_positions.is_empty() {
        return;
    }

    // Fail closed: never update an account whose NFT owner cannot be resolved.
    let Some(owner) = storage::try_account_owner(env, account_id) else {
        return;
    };

    let full_tuple = scope == RiskRefreshScope::FullTuple;
    let borrow_positions = if full_tuple {
        storage::get_debt_positions(env, account_id)
    } else {
        Map::new(env)
    };

    storage::renew_user_account(env, account_id);

    let mut account = storage::account_from_parts(owner, meta, supply_positions, borrow_positions);
    let assets = account.supply_positions.keys();

        let Some(spoke_config) = cache.cached_spoke_asset(account.spoke_id, &hub_asset) else {
            continue;

            cache,
            &account,
            &hub_asset,
            &mut updated,

            scope,

            continue;
