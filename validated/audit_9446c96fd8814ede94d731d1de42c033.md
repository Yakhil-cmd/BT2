### Title
Cross-repository CI status forgery via organization/repository binding mismatch in webhook signature verification - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to check the HMAC signature against using the `repository.owner.login` (or `organization.login`) field of the payload, but `StatusHandler#process` never re-checks that the commit it mutates actually belongs to the repository/organization that was authenticated. It resolves the target purely by global `sha` lookup. This breaks the binding: `organization that authenticated == repository that is written`.

### Finding Description
`verify_signature` picks the app config to verify against like this: [1](#0-0) 
and `repository_owner` is taken straight from the untrusted JSON body: [2](#0-1) 

The signature is HMAC'd over the *entire* raw body, so an attacker cannot forge signatures without knowing the corresponding organization's `webhook_secret` — except that `GitHubApp#verify_webhook_signature` silently treats a blank secret as "verified": [3](#0-2) 
This is a documented "optional" setting for multi-organization installs (`docs/setup.md`), so a Shipit deployment configured with several `github` organizations where one entry omits `webhook_secret` is fully within intended/documented usage, not a misconfiguration outside scope.

Once `verify_signature` passes for *any* configured organization (including one with no secret), the base `Handler` class and `StatusHandler` do not re-derive or re-check which organization/repository owns the target record: [4](#0-3) 
`StatusHandler#process` looks up `Commit.where(sha: params.sha)` **globally across the entire database**, with no scoping to the repository/organization whose signature was just checked: [5](#0-4) 

This is exactly the same trust-binding gap as the reported `allocate_constant`/`fq2` bug class: a downstream operation acts on data (`commit`, resolved solely by `sha`) that was never actually covered by the check that gated the request (signature validated for organization X, but the record mutated may belong to organization Y). The equality that should hold — `organization verified in verify_signature == organization owning the commit mutated in StatusHandler` — does not hold.

`create_status_from_github!` → `add_status` has real effect: it can flip a commit's aggregate CI state and, on success/pending transitions, triggers `stack.schedule_merges`: [6](#0-5) [7](#0-6) 
and can make a commit `deployable?` for continuous delivery: [8](#0-7) [9](#0-8) 

### Impact Explanation
An unprivileged external attacker who can produce a validly-signed webhook for *any one* organization configured on the Shipit instance (trivially, an org whose `webhook_secret` is left blank, a supported configuration per `docs/setup.md`'s multi-org example) can forge a `status` event referencing an arbitrary `sha` belonging to a commit tracked under a completely different organization/repository/stack. Because `StatusHandler` resolves the commit by SHA alone with no ownership check, the attacker can inject a fabricated "success" CI status onto that unrelated commit, causing `stack.schedule_merges` to fire and potentially triggering an unauthorized deploy/merge on a stack the attacker has no relationship with. This satisfies "unauthorized deploy, rollback or merge" / "cross-repository writes."

### Likelihood Explanation
Requires only that the Shipit deployment has at least two configured GitHub organizations (a documented supported configuration) where the attacker knows or controls one org name that has no `webhook_secret` set, plus the target commit's SHA (SHAs are not secret — visible in git history, PRs, CI links, etc.). No repository write access, session, API token, or knowledge of any real secret is required, satisfying the unprivileged-attacker constraint.

### Recommendation
`StatusHandler` (and any handler resolving records purely by content like `sha`) must scope lookups by the repository/organization that was actually verified during signature checking (e.g., join through `stacks: { repositories: { id: repository.id } }` as other handlers already do — see `PullRequest::AssignedHandler#pull_request`), rather than trusting a global, unscoped `Commit.where(sha:)`. Additionally, `verify_webhook_signature`'s "no secret configured ⇒ verified" fallback should be reconsidered or at minimum documented as unsafe for multi-organization deployments where any other org is expected to remain protected.

### Proof of Concept
1. Configure (or identify) a Shipit instance with two organizations, `attacker-org` (no `webhook_secret` set) and `victim-org` (properly secured, hosts the target stack).
2. Find any commit SHA belonging to a repository tracked under `victim-org`'s stack (public PR/commit).
3. POST to `/webhooks` with header `X-Github-Event: status`, no valid `X-Hub-Signature` needed since `attacker-org` has no secret:
```
{
  "repository": {"owner": {"login": "attacker-org"}},
  "sha": "<victim commit sha>",
  "state": "success"
}
```
4. `verify_signature` resolves `Shipit.github(organization: "attacker-org")`, whose `verify_webhook_signature` returns `true` unconditionally (blank secret).
5. `StatusHandler#process` executes `Commit.where(sha: "<victim commit sha>")`, found regardless of organization, and calls `create_status_from_github!`, potentially flipping the commit to `success` and invoking `stack.schedule_merges` on the victim stack.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
