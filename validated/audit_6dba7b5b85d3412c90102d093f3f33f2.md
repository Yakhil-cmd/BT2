### Title
Bridge Operator Can Front-Run KAIA/ERC20 Transfer Requests to Extract Excess Fees — (`contracts/service_chain/bridge/BridgeFee.sol`, `contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

---

### Summary

The Kaia service-chain bridge reads `feeOfKLAY` and `feeOfERC20` from mutable contract storage at the moment a user's `requestKLAYTransfer` / fallback / `requestERC20Transfer` transaction executes, not at the moment the user signs and submits it. Bridge operators can change these fee values between submission and execution, causing users to pay more in fees than they consented to — a direct, unauthorized KAIA/ERC20 charge.

---

### Finding Description

`BridgeFee.sol` stores two operator-controlled fee parameters:

```solidity
uint256 public feeOfKLAY = 0;
mapping (address => uint256) public feeOfERC20;
``` [1](#0-0) 

Both `_payKLAYFeeAndRefundChange` and `_payERC20FeeAndRefundChange` read these values at execution time:

```solidity
function _payKLAYFeeAndRefundChange(uint256 _feeLimit) internal returns(uint256) {
    uint256 fee = feeOfKLAY;          // ← read at execution time
    ...
    require(_feeLimit >= fee, "insufficient feeLimit");
``` [2](#0-1) 

```solidity
function _payERC20FeeAndRefundChange(address from, address _token, uint256 _feeLimit) internal returns(uint256) {
    uint256 fee = feeOfERC20[_token]; // ← read at execution time
``` [3](#0-2) 

The fallback function passes the **current** `feeOfKLAY` as the `feeLimit`, giving the user zero ability to cap the fee they accept:

```solidity
function () external payable {
    _requestKLAYTransfer(msg.sender, feeOfKLAY, new bytes(0));
}
``` [4](#0-3) 

Operators change fees via `setKLAYFee` / `setERC20Fee`, which require only a configurable threshold of operator votes (default threshold = 1, meaning a single operator/owner can act alone): [5](#0-4) 

---

### Impact Explanation

**Fallback path (worst case — direct KAIA loss):**

A user sends `1.4 KAIA` via the fallback expecting `feeOfKLAY = 0.4` (transfer = 1.0 KAIA). An operator front-runs and raises `feeOfKLAY` to `1.3`. When the user's transaction executes:

- `feeLimit = feeOfKLAY = 1.3` (read at execution time)
- `require(msg.value > feeLimit)` → `1.4 > 1.3` → passes
- Transfer amount = `msg.value − feeLimit = 1.4 − 1.3 = 0.1 KAIA`
- Fee paid = `1.3 KAIA` (vs. the `0.4 KAIA` the user expected)

The user loses `0.9 KAIA` in excess fees transferred to `feeReceiver`. This is an unauthorized KAIA charge.

**`requestKLAYTransfer` path (denial of service / forced revert):**

A user sends `1.5 KAIA` with `_value = 1.0`, so `feeLimit = 0.5`. If the operator raises the fee above `0.5`, the `require(_feeLimit >= fee)` check reverts the transaction, locking the user out until they resubmit with a higher `msg.value`.

**ERC20 path:** Same pattern applies via `_payERC20FeeAndRefundChange`. [6](#0-5) 

---

### Likelihood Explanation

- The default `operatorThreshold` for configuration votes is **1**, meaning the bridge owner alone can change fees atomically in a single transaction.
- The service-chain bridge is a production component used for cross-chain value transfer of KAIA and ERC20 tokens.
- The fallback function provides **no user-specified fee cap**, making it the highest-risk entry point.
- The attack requires no special privileges beyond being a registered operator (or the bridge owner), and no external service compromise. [4](#0-3) 

---

### Recommendation

1. **Add a `maxFee` parameter to `requestKLAYTransfer` and the fallback.** The user should specify the maximum fee they accept. Revert if `feeOfKLAY > maxFee` at execution time.

2. **For the fallback function specifically**, since it cannot accept parameters, consider removing it or replacing it with a named function that accepts an explicit fee cap.

3. **For ERC20 transfers**, add a check: if `feeOfERC20[token]` at execution time exceeds the user-supplied `_feeLimit`, revert rather than silently charging the full `_feeLimit`.

Example fix for `_payKLAYFeeAndRefundChange`:
```solidity
function _payKLAYFeeAndRefundChange(uint256 _feeLimit, uint256 _maxAcceptableFee) internal returns(uint256) {
    uint256 fee = feeOfKLAY;
    require(fee <= _maxAcceptableFee, "fee exceeds user maximum");
    ...
}
```

---

### Proof of Concept

1. Bridge is deployed with `feeOfKLAY = 0.4 KAIA` and `feeReceiver` set.
2. User observes `feeOfKLAY = 0.4` and submits a fallback transaction sending `1.4 KAIA` (intending to transfer `1.0 KAIA`).
3. Before the user's transaction is mined, the operator calls `setKLAYFee(1.3 KAIA, configNonce)` — with threshold=1 this takes effect immediately in the same block or the next.
4. User's fallback executes: `feeLimit = feeOfKLAY = 1.3`, `fee = 1.3`, `require(1.4 > 1.3)` passes.
5. `feeReceiver` receives `1.3 KAIA`; user's counterpart chain receives only `0.1 KAIA`.
6. User has lost `0.9 KAIA` in excess fees with no recourse.

    function _payKLAYFeeAndRefundChange(uint256 _feeLimit) internal returns(uint256) {
        uint256 fee = feeOfKLAY;

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            (bool ok, ) = feeReceiver.call.value(fee)("");
            require(ok, "transfer fee failed");

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                (bool ok, ) = msg.sender.call.value(feeRefund)("");
                require(ok, "refund fee failed");
            }

            return fee;
        }

        if (_feeLimit > 0) {
            (bool ok, ) = msg.sender.call.value(_feeLimit)("");
            require(ok, "refund fee failed");
        }
        return 0;
    }
```
