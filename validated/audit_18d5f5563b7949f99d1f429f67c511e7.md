### Title
Amend-delta review trusts unverified reflog HEAD@{1} as a reviewed baseline, letting a hard-reset-then-amend land unreviewed malicious code - (File: `plugins/security-guidance/hooks/security_reminder_hook.py`)

### Summary
`_resolve_amend_pre_sha` accepts *any* commit at `HEAD@{1}` as the "pre-amend" baseline for the delta review, as long as `HEAD@{0}`'s reflog subject is `commit (amend)` and `HEAD@{1}` isn't itself an amend. It never checks that the object at `HEAD@{1}` was ever actually reviewed by the plugin (i.e., that it came from a monitored `git commit` invocation). An attacker can move `HEAD` to an arbitrary, already-existing, malicious commit object via `git reset --hard <sha>` (or checkout/cherry-pick/fetch) — an operation that never goes through the `git commit` Bash matcher and is therefore never reviewed — and then run a single, visible `git commit --amend --no-edit`. `_resolve_amend_pre_sha` will treat that unreviewed malicious commit as the trusted pre-amend baseline, the diff between it and the amended HEAD is empty, and the review is silently skipped (`skip_reason=35`).

### Finding Description
The delta-review gate in `handle_commit_review_posttooluse` computes: [1](#0-0) 

`_resolve_amend_pre_sha` only validates the *shape* of the reflog around the amend (HEAD@{0} is `commit (amend)`, HEAD@{1} is not itself an amend, and the caller's parsed post-amend SHA matches HEAD@{0}) — it never validates that HEAD@{1}'s tree content was previously reviewed: [2](#0-1) 

Attack flow:
1. Attacker (in a normal cloned-repo Claude Code session) obtains or fabricates a commit object with malicious content that never passes through the monitored `git commit` command — e.g. `git fetch`, `git cherry-pick`, or `git commit-tree`/`git update-ref` — then runs `git reset --hard <malicious-sha>`. None of these operations match `_GIT_COMMIT_RE`/`_GIT_PUSH_RE`, so `handle_commit_review_posttooluse` never fires for this content, and it is never added to `.git/sg-reviewed-shas` or `previous_findings`.
2. Attacker runs a single, plainly visible `git commit --amend --no-edit` (or with a trivial message edit, no tree change). This matches the Bash matcher and enters `handle_commit_review_posttooluse` via the normal, non-reflog-fallback path (`commit_succeeded` via stdout, `_reflog_shas` empty, `len(all_shas) <= 1`, `commit_invocations <= 1`), satisfying all three amend-delta guards.
3. `_resolve_amend_pre_sha` returns `HEAD@{1}` (the malicious reset target) as `pre_amend_sha`, purely because the reflog shape matches — it has no way to know that content was never reviewed.
4. `git diff pre_amend_sha post_amend_sha` is empty (amend didn't change the tree), so the hook hits the "message-only amend" skip path and exits with no warning: [3](#0-2) 

The Stop hook does not compensate. `compute_v2_review_set` only widens `dirty_now` past the working-tree status when `head_at_capture` is an ancestor of the new `HEAD` (a fast-forward via commit/merge): [4](#0-3) 

A `git reset --hard` to an unrelated existing commit is not a fast-forward, so `_is_ancestor` returns `False`, `dirty_now` stays empty (working tree is clean post-reset/amend), and `review_set = dirty_now & changed_since = ∅`, causing the Stop hook to skip with an empty review set: [5](#0-4) 

The net effect matches the audited invariant violation: the counter/dedup machinery (reusing HEAD@{1} as an implicitly "already covered" baseline) causes a genuinely new, in-scope dangerous commit to reach `HEAD` — and potentially get pushed — without ever triggering a warning or rewake on either the commit-review or Stop-hook surface.

### Impact Explanation
This allows attacker-controlled code that was never inspected by any of the plugin's three review layers to land on the repository's `HEAD` and subsequently be executed or pushed, effectively bypassing the security-guidance plugin's approval/warning gate entirely for a normal, unprivileged, single-command action (`git commit --amend`). This matches "Unauthorized local command/code execution that bypasses Claude Code's review/approval controls," since the mechanism exists specifically to catch and rewake on dangerous diffs before they're acted upon further.

### Likelihood Explanation
Requires only ordinary git operations available to any user/agent in a normal cloned repo — no privilege escalation, no leaked keys, no social engineering. The preconditions (an existing malicious commit object reachable via `git reset --hard`, `cherry-pick`, or `commit-tree`, followed by a single visible `--amend --no-edit`) are trivially scriptable and repeatable, and the guard conditions in `handle_commit_review_posttooluse` that gate the delta path are exactly the "normal" single-amend case, not an edge case.

### Recommendation
`_resolve_amend_pre_sha` (or its caller) should only trust `HEAD@{1}` as a review baseline if it can verify that SHA was previously recorded as reviewed (e.g., present in `.git/sg-reviewed-shas` via `_load_reviewed_shas`), or if the reflog action for `HEAD@{1}` itself is `commit` (not `reset`, `pull`, `checkout`, `cherry-pick`, etc.). If unverifiable, fall back to a full `git show` review of the amended commit instead of a delta, and the "empty delta ⇒ skip" fast path (`skip_reason=35`) should only apply once the baseline's provenance is confirmed reviewed.

### Proof of Concept
Integration test plan (pseudo-shell + hook invocation):
1. In a fresh test repo, create commit `A` (benign) via `git commit` — allow it to be reviewed normally (or stub `analyze_code_security`).
2. Fabricate a malicious commit object `M` off-path: `git commit-tree` with a tree containing e.g. `eval(input())`/`os.system` payload, `git update-ref refs/heads/tmp M`, then `git reset --hard M` (never invoking `git commit`) — confirm no PostToolUse fire occurs for `M` (`_GIT_COMMIT_RE` doesn't match `reset`/`update-ref`).
3. Run `git commit --amend --no-edit` and feed the resulting `tool_input`/`tool_response` (with the real `[branch sha]` stdout line) into `handle_commit_review_posttooluse`.
4. Assert: `_resolve_amend_pre_sha` returns `M`'s sha; `git diff M amend_sha` is empty; the hook exits 0 with `emit_metrics({"skipped": True, "skip_reason": 35, ...})` and no findings recorded — i.e., `M`'s malicious content is never sent to `analyze_code_security`.
5. Separately drive `handle_stop_hook` with `baseline_sha` captured before step 2 and `head_at_capture` = `A`; assert `compute_v2_review_set` returns an empty `review_paths` (`skip_reason=9`) because `_is_ancestor(A, amend_sha)` is `False` and the working tree is clean.
6. Together, steps 4 and 5 demonstrate that the malicious content in `M` reaches `HEAD` with zero warnings/rewakes from either surface.

```python
def _resolve_amend_pre_sha(repo_root, expected_post_sha=None):
    """For a `git commit --amend` we just ran, return the pre-amend SHA via
    reflog, or None if it can't be safely determined.

    expected_post_sha: the post-amend SHA the caller parsed from bash stdout
    (or reflog). If provided, HEAD@{0} of `repo_root` must match it (prefix
    compare — bash stdout SHAs are abbreviated, reflog %H is 40 chars) before
    we trust the reflog-derived pre-amend SHA. This guards against the
    cross-repo case (`cd ../other && git commit --amend && cd -`) where
    `repo_root` happens to have its own recent amend that's unrelated to
    the bash command we're reviewing.

    We require HEAD@{0}'s reflog subject to start with `commit (amend)` —
    otherwise our `--amend` regex matched something that didn't actually
    perform an amend (e.g., `git commit --amend --dry-run`, aliased commands,
    aborted amends), and HEAD@{1} would be the wrong commit. Also requires
    HEAD@{1} to NOT itself be an amend, since back-to-back amends would have
    HEAD@{1} as the previous-amend's post state — the original commit we
    want to compare against is then HEAD@{2}, but at that point we're
    reaching and fall back to a full review.

    Bytes + decode('utf-8', errors='replace'): reflog subjects embed commit
    subjects, which git stores as raw bytes (commit messages may be latin-1
    / cp1252 / etc.). text=True would raise UnicodeDecodeError (a
    ValueError, not OSError) on non-UTF8 bytes and crash the hook.
    """
    if not repo_root:
        return None
    try:
        r = subprocess.run(
            [*GIT_CMD, "log", "-g", "-2", "--format=%H|%gs", "HEAD"],
            cwd=repo_root, capture_output=True, timeout=5,
        )
    except (subprocess.TimeoutExpired, FileNotFoundError, OSError):
        return None
    if r.returncode != 0:
        return None
    stdout_text = r.stdout.decode("utf-8", errors="replace")
    lines = [ln for ln in stdout_text.splitlines() if "|" in ln]
    if len(lines) < 2:
        return None
    head0_sha, _, head0_subj = lines[0].partition("|")
    head1_sha, _, head1_subj = lines[1].partition("|")
    if not head0_subj.startswith("commit (amend)"):
        return None
    if head1_subj.startswith("commit (amend)"):
        return None
    # Cross-repo guard: the post-amend SHA the caller is about to review must
    # match HEAD@{0} of repo_root. Otherwise the bash command was likely run
    # in a different repo than repo_root, and the reflog we just read is
    # unrelated. Prefix-compare: expected_post_sha is typically the 7-char
    # abbreviated SHA captured from bash stdout by _COMMIT_SHA_RE (git's
    # default core.abbrev floor), while head0_sha is the full 40-char %H —
    # strict equality would always fail and silently disable the delta path.
    if expected_post_sha and not head0_sha.startswith(expected_post_sha):
        return None
    return head1_sha or None
```
