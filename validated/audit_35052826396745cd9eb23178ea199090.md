### Title
Cross-tenant `Status` write via SHA-only lookup in `StatusHandler#process` triggers unauthorized `ContinuousDeliveryJob` fan-out - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
The `status` webhook handler resolves target commits purely by `sha`, with no scoping to the repository named in the authenticated webhook payload. Because `Commit.sha` is not globally unique (only indexed per `stack_id`), a single signed webhook from an attacker's own repository can write a `Status` and trigger `schedule_continuous_delivery` / `ContinuousDeliveryJob` on every unrelated stack that happens to have a commit with the same SHA.

### Finding Description
The broken binding: the webhook is only authenticated for `repository.full_name == "attacker/repo"`, so it should be true that `stack.repository.full_name == "attacker/repo"` for every stack touched. Instead, `StatusHandler#process` does: [1](#0-0) 

`Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — this queries across the entire `commits` table with no `stack_id`/`repository` filter. `WebhooksController#verify_signature` only validates the HMAC signature against the GitHub App keyed by `repository_owner` extracted from the payload: [2](#0-1) 

This proves the payload was legitimately sent by that one organization/repo, but it does not constrain which `Commit`/`Stack` rows the handler is allowed to mutate. The `commits` table has an index on `(stack_id, sha)`, not a uniqueness constraint on `sha` alone (per `db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`), confirming the same SHA can legitimately exist across many unrelated stacks (e.g., identical upstream commits, cherry-picks, or mirrored history).

For each matching commit, `create_status_from_github!` → `add_status` runs: [3](#0-2) [4](#0-3) 

and `Status` itself independently schedules continuous delivery on `after_commit`: [5](#0-4) 

`Commit#schedule_continuous_delivery` then enqueues `ContinuousDeliveryJob.perform_later(stack)` whenever the commit is `deployable?` and `stack.continuous_deployment?`: [6](#0-5) 

Since `Commit.where(sha:)` iterates over commits belonging to arbitrary stacks/repositories, this fan-out happens per matched stack, entirely decoupled from which repository the webhook was actually authenticated for. No guard (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema on `StatusHandler`) checks `params.repository` against `commit.stack.repository`; the `repository` field is not even required in the handler's params schema.

### Impact Explanation
An attacker who owns/controls any GitHub repository tracked by the same Shipit instance can, by pushing commits and/or replaying `status` webhooks with `state: success` for SHAs known to exist in other tenants' repositories, write `Status` rows and trigger unauthorized `ContinuousDeliveryJob` (and thus real deploys, via `stack.trigger_continuous_delivery`) against stacks belonging to unrelated repositories/teams. This is a payload-for-one-repository-mutating-another's-stack/commit scenario and can produce an unauthorized deploy — matching the Critical impact category. The blast radius scales with the number of unrelated stacks sharing any commit SHA with the attacker's repository at the time of the webhook.

### Likelihood Explanation
Preconditions: the victim stacks must have `continuous_deployment: true` and be otherwise deployable (`Stack#deployable?`), and must contain a `Commit` record with a SHA matching one the attacker can produce/know (trivial for public commits, forks, or common upstream history). The attacker needs no Shipit credentials — only the ability to trigger a legitimate, signed `status` webhook for a repository they control (owning any GitHub repo hooked to the instance is sufficient; the signature only proves authenticity for that org). This is realistically automatable by sweeping known public SHAs across popular projects. Feasibility is high and the action is repeatable per SHA collision.

### Recommendation
In `StatusHandler#process` (and analogously any other SHA-keyed webhook handler), scope the `Commit` lookup to the stack(s) whose `repository` matches the authenticated `params.repository.full_name` (and, ideally, `params.repository.owner`) instead of a bare `sha` match, e.g. join through `Stack` and filter by `repository`. Consider also enforcing this invariant at the model layer (e.g. a scope like `Commit.where(sha:).joins(:stack).where(stack: { repository: expected_repo })`) so any future handler can't reintroduce the same class of bug.

### Proof of Concept
Minitest plan (webhooks controller or handler test):
1. Create three stacks in fixtures/setup, each with a distinct `repository` (e.g. `attacker/repo`, `victim-a/repo`, `victim-b/repo`), each with `continuous_deployment: true` and each deployable.
2. Create one `Commit` per stack, all sharing the identical `sha` value (e.g. `"deadbeef" * 5`), each already having passing/deployable prerequisites (CI ignored or an existing green status) so `deployable?` is true.
3. Assert the binding before the request: `attacker_stack.repository != victim_a_stack.repository` and `!= victim_b_stack.repository`.
4. Send one signed webhook POST to `/webhooks` with `X-Github-Event: status`, body `{ sha: shared_sha, state: 'success', repository: { full_name: 'attacker/repo', owner: { login: 'attacker' } } }`, stubbing `verify_signature`/`Shipit.github` for `attacker` org only.
5. Assert `ContinuousDeliveryJob` is enqueued with args `[attacker_stack]`, `[victim_a_stack]`, and `[victim_b_stack]` (e.g. via `assert_enqueued_with` for each, or inspecting `enqueued_jobs`), proving the single attacker-authenticated webhook fanned out `Status` writes and deploy triggers to stacks whose repository never matched the authenticated payload.

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )

        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",

      ].join(' '))

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
