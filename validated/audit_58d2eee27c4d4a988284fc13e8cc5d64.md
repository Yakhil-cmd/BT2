### Title
Webhook signature verification is keyed off `repository.owner.login` while every event handler acts on `repository.full_name`, allowing a valid signer for one configured GitHub organization to write to stacks owned by a different organization - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which per-organization webhook secret to check the HMAC against using `repository_owner` (`params.dig('repository','owner','login')`), but every `Shipit::Webhooks::Handlers::Handler` subclass resolves the target `Repository`/`Stack` using a different field from the same JSON body: `params.dig('repository','full_name')` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`). Because Shipit natively supports multiple GitHub organizations each with its own secret (`lib/shipit.rb:170-200`, `Shipit.github(organization:)`), the field used to pick the signing secret is not the field used to determine which tenant's data gets mutated. This is the same class of bug as the Wormhole `refundChain`/`targetChain` mismatch: two conceptually related values, extracted from the same message, are used inconsistently for authentication vs. for the actual state-changing operation.

### Finding Description
- `verify_signature` in `app/controllers/shipit/webhooks_controller.rb:24-49` does:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
- `Handler#stacks`/`#repository_name` in `app/models/shipit/webhooks/handlers/handler.rb:32-38` (and the `PushHandler`, `PullRequest::*Handler`s that inherit or duplicate this pattern) resolve the actual target using:
```ruby
def repository_name
  payload.dig('repository', 'full_name')
end
```
- `Shipit.github(organization:)` (`lib/shipit.rb:170-200`) looks up a distinct config/secret per organization key (`github_app_config(organization)`), confirming multi-tenant support where each org has its own `webhook_secret`.
- Nothing in the controller or in any handler asserts that the owner encoded in `repository.owner.login` matches the owner encoded in `repository.full_name`. Both are attacker-supplied fields inside the same raw POST body whose bytes are what get HMAC'd - the signature covers the bytes, but the *secret chosen* to validate those bytes is selected from one field while the *effect* of processing is driven by another, independent field.
- Consequently, anyone who can produce a valid signature for **any one** configured organization (e.g., a legitimate admin/integrator of their own low-privilege org in a multi-org Shipit deployment) can craft a payload where `repository.owner.login` = their own org (so `Shipit.github(organization: 'their-org')`'s secret is used and passes) while `repository.full_name` = `"other-org/other-repo"`. The handlers then act entirely on `full_name`, e.g. `PushHandler#process` triggers `stack.sync_github(expected_head_sha: params.after)` on stacks belonging to `other-org`, and `PullRequest::OpenedHandler` looks up `Shipit::Repository.from_github_repo_name(params.repository.full_name)` and can create/unarchive review stacks and provision deploys for that unrelated repository.

### Impact Explanation
This breaks the equality that should hold: `organization whose secret authenticated the request == owner of the repository the request is allowed to mutate`. In a multi-organization Shipit deployment, this allows a party who legitimately controls (or, per the "unconfigured org" degenerate case, controls nothing at all if any org has no `webhook_secret` set) one organization's webhook signing capability to trigger unauthorized cross-repository/cross-organization state changes: syncing branches, creating/archiving review stacks, and driving deploy pipelines for a completely different organization's stacks that they have no legitimate relationship to. This is a cross-repository/cross-tenant write, matching the "Critical: cross-repository writes / unauthorized deploy" impact category.

### Likelihood Explanation
This requires the deployment to configure more than one GitHub organization (a supported, documented feature - see `test/dummy/config/secrets_double_github_app.yml`), and the attacker to be a legitimate holder of a webhook secret for at least one of those organizations (or for any organization whose `webhook_secret` is left blank, which `GitHubApp#verify_webhook_signature` treats as "always verified" - `lib/shipit/github_app.rb:76-83`). Given multi-org support exists specifically to let independent teams/orgs share one Shipit instance, the trust boundary between those orgs is exactly what this bug crosses, making exploitation realistic whenever the feature is used as designed.

### Recommendation
In `WebhooksController#verify_signature`, after verifying the HMAC for the organization derived from `repository_owner`, additionally assert that `repository_owner` matches the owner segment of `repository.full_name` (and of `organization.login`, when present) before dispatching to handlers. Alternatively, have every handler derive the target repository owner from the same field that was cryptographically bound to the verified secret, rejecting payloads where the two diverge.

### Proof of Concept
1. Deploy Shipit configured with two organizations, `org-a` and `org-b`, each with its own `webhook_secret` (as supported by `Shipit.github(organization:)`).
2. Attacker is a legitimate webhook integrator for `org-a` (knows `org-a`'s `webhook_secret`, e.g. because they set up the GitHub App/webhook for their own repo under `org-a`).
3. Attacker POSTs to `/github/webhooks` with `X-Github-Event: push` and a JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" }
}
```
4. `repository_owner` resolves to `"org-a"`; `Shipit.github(organization: "org-a")` returns `org-a`'s `GitHubApp`, whose secret the attacker knows, so `verify_webhook_signature` passes for a signature the attacker computed themselves over the raw body.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("org-b/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on `org-b`'s stack, even though the attacker never proved control over `org-b`. module Shipit
  module Webhooks

      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
