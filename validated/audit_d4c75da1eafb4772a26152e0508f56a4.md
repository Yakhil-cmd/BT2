### Title
Caller-controlled swap routes can hide unauthorized wallet transfers in the signed authorization tree - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary
A user-supplied `swap` payload is forwarded unchanged to the configured router while the account owner’s `swap_collateral`, `swap_debt`, or `repay_debt_with_collateral` authorization remains active for the whole call tree. If that route reaches attacker-controlled code, the code can request an additional `token.transfer` from the caller; Soroban records it as a child of the caller’s signed controller authorization. A victim that signs the simulation-produced tree therefore authorizes both the intended collateral swap and theft of unrelated wallet assets.

### Finding Description
`swap_collateral` accepts an opaque `Bytes` route and passes it into `SwapCollateralParams` without constraining the contracts reachable from that route. [1](#0-0)  The handler authenticates `caller` and verifies account ownership or delegation before executing the strategy. [2](#0-1)  The controller then calls `router.execute_strategy(&controller, &amount_in, swap)`, passing the attacker-influenced payload directly to the router. [3](#0-2) 

The controller correctly limits its own router grant to one exact `token_in` transfer, but that only bounds assets already held by the controller. [4](#0-3)  It does not prevent route-selected code below the router from asking the original caller for an unrelated authorization that can be attached beneath the caller’s signed root invocation.

The regression test demonstrates this authorization behavior: a route-selected rogue pool calls `transfer(victim, attacker, amount)` during `swap_collateral`. [5](#0-4)  Simulation records that token transfer as a child of Alice’s `swap_collateral` authorization, and signing that tree causes Alice’s unrelated wallet balance to reach the attacker. [6](#0-5)  Enforced authorization rejects the same transfer when omitted from the signed tree, but executes it when the simulation-produced poisoned tree is signed. [7](#0-6) 

### Impact Explanation
An attacker can steal arbitrary spendable token balances from a user who signs a malicious route authorization tree. The stolen amount is not limited to the collateral supplied to the lending strategy, because the injected child invocation can name a different token, recipient, and amount. The strategy can still return a valid measured output and pass the controller’s final accounting and risk checks while the independent wallet transfer succeeds.

### Likelihood Explanation
Exploitation requires the victim to submit an attacker-supplied or attacker-modified route and sign the resulting authorization tree. That is plausible where routes are generated off-chain or presented through an integrating application, because the encoded route and authorization tree are difficult for users to audit. A completely honest client that decodes and rejects unexpected child invocations prevents the attack, so the issue is Medium rather than High.

### Recommendation
Do not allow swap routes to invoke arbitrary pool or venue addresses. Maintain governance-controlled venue/pool registries or cryptographically bind route hops to approved contracts before execution. In addition, reject routes whose simulation introduces any caller-authorization child other than the expected swap input transfer, and provide a canonical authorization-tree verifier for integrators.

### Proof of Concept
The dedicated test constructs `UnlistedPoolRouter`, which decodes the caller-supplied route and invokes its selected `hop_pool`. [8](#0-7)  `RogueHopPool::swap` transfers a preconfigured unrelated wallet token from Alice to the attacker. [5](#0-4) 

The test then calls:

```text
swap_collateral(
    alice,
    alice_account_id,
    USDC hub asset,
    SWAP_IN_USDC,
    ETH hub asset,
    malicious_route,
)
```

After simulated authorization recording, the `wallet_token.transfer(alice, attacker, WALLET_BALANCE)` invocation appears beneath Alice’s `swap_collateral` root authorization. [9](#0-8)  Signing that recorded tree reduces Alice’s wallet balance to zero, transfers `WALLET_BALANCE` to the attacker, and still deposits the expected swap output into Alice’s account. [10](#0-9)
