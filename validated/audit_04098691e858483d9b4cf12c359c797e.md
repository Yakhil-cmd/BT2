### Title
Orphaned `pending_delegator_rewards` in vote accounts with no delegated stake can be captured entirely by the first delegator to activate stake - (File: `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`)

### Summary
Vote accounts accumulate `pending_delegator_rewards` (SIMD-0123 block-revenue-sharing pool) via `deposit_delegator_rewards()` with no check that the vote account currently has any delegated/active stake. When block rewards are later distributed via `calculate_block_reward()`, the entire pool is split strictly among whatever stake is delegated to that vote account *at the rewarded epoch*, proportional to `stake / total_active_stake`. If deposits accumulate while `total_active_stake == 0` (or is small), the first staker(s) to delegate afterward capture the whole backlog of `pending_delegator_rewards`, analogous to the "first depositor captures orphaned rewards" bug class described in the external report for `sdeusd.move`.

### Finding Description
`deposit_delegator_rewards()` in `programs/vote/src/vote_state/mod.rs` transfers lamports into the vote account and unconditionally accumulates them into `pending_delegator_rewards` via `add_pending_delegator_rewards()`: [1](#0-0) [2](#0-1) 

There is no assertion that the vote account currently has any delegated stake (i.e., no analog to the report's recommended `assert!(total_supply(management) > 0, ENoActiveStakers)`).

At reward-distribution time, `calculate_block_reward()` computes each stake account's share of `pending_delegator_rewards` purely as a proportion of currently delegated stake to total active stake for that vote account at the rewarded epoch: [3](#0-2) 

If `total_active_stake == 0` at the time of deposit, `calculate_block_reward` simply returns 0 for that epoch (no distribution happens, and — critically — `pending_delegator_rewards` is not reduced), so the deposited lamports sit dormant in the vote account's `pending_delegator_rewards` field. As soon as stake is delegated to the vote account (even a small amount) and becomes active, the block-reward split formula pays out based on `stake / total_active_stake`, meaning the newly delegated stake (which did not exist when the rewards were deposited) receives its proportional share of the entire accumulated backlog — not just of rewards deposited after it staked.

This mirrors the reported bug class: rewards distributed into a pool without any check for active participants, combined with an allocation scheme that doesn't account for "when" a participant joined relative to the reward deposit, lets a subsequent staker capture rewards that were never earned by their capital.

### Impact Explanation
This allows lamports transferred via `DepositDelegatorRewards` (block revenue sharing, SIMD-0123) to be misattributed: they are meant to compensate stakers who backed the validator during block production, but a staker who joins *after* the deposit — while the vote account had zero or low delegated stake — can receive rewards proportional to their stake against the full accumulated pool, siphoning rewards away from the parties that should have earned them. This is a misattribution/duplication-style reward theft matching the "concrete theft or misattributed rewards" acceptance criteria. It affects the reward distribution path in the stake/vote program accounting (`runtime/src/bank/partitioned_epoch_rewards`), which is in scope.

### Likelihood Explanation
Likelihood is Low-to-Medium: it requires (1) a validator or delegator to call `DepositDelegatorRewards` while the vote account has zero or very low active delegated stake (plausible for newly created or delinquent/low-stake vote accounts, or during stake churn between epochs) and (2) timing subsequent stake delegation to land within the same rewarded epoch before the pool is otherwise diluted by legitimate large stakers. Both conditions are achievable without any privileged role — deposits and stake delegation are unprivileged-user actions.

### Recommendation
Either:
1. Reject or hold `DepositDelegatorRewards` deposits when `total_active_stake` for the target vote account is zero (analogous to the report's `ENoActiveStakers` check), or
2. Change `calculate_block_reward` to track pending rewards per-epoch-cohort (e.g., snapshot `pending_delegator_rewards` and the stake set at deposit time) rather than allowing all currently delegated stake to retroactively claim a share of a backlog accumulated before that stake was active, or
3. When `total_active_stake == 0` at distribution time, burn/return the pending amount instead of leaving it to be claimed later by unrelated stakers.

### Proof of Concept
1. Create vote account `V` with zero delegated stake.
2. Call `DepositDelegatorRewards` on `V` for `X` lamports — `pending_delegator_rewards` becomes `X`, `total_active_stake == 0`, so `calculate_block_reward` returns 0 for this epoch and the deposit is not distributed/burned. [4](#0-3) 
3. Attacker delegates stake `S` to `V`, becoming its only/primary delegator once `S` is active.
4. At the next rewarded epoch, `total_active_stake = S`, and `calculate_block_reward` awards `pending_delegator_rewards * S / S = X` entirely to the attacker's stake account, even though `X` was deposited before the attacker had any stake delegated. [5](#0-4) 

Note: I could not find code in `programs/vote/src/vote_state/mod.rs` or `calculation.rs` that decrements/resets `pending_delegator_rewards` proportionally per-epoch or tracks a deposit timestamp/epoch cohort; the field appears to only ever be additively increased by deposits and implicitly "spent" via the block-reward calculation, which supports the above analysis, but I was unable to fully trace the store/subtract path within the available index due to file-size truncation in `calculation.rs` (lines beyond the retrieved excerpts were not indexed). A Devin session with full repo access would be needed to confirm whether `pending_delegator_rewards` is ever partially decremented per distributed amount or fully zeroed after each distribution, which would refine the precise magnitude of the orphaned-rewards window.

/// Deposit delegator rewards into a vote account (SIMD-0123).
pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}

/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }
