### Title
Cross-organization Team hijack via `github_id`-only lookup in `MembershipHandler#find_or_create_team!` - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`MembershipHandler#find_or_create_team!` resolves a `Team` solely by `github_id: params.team.id`, with no check that the payload's `organization.login` matches the `organization` already stored on that `Team` row. Because Shipit supports multiple independently-configured GitHub organizations (each with its own webhook secret via `Shipit.github_app_config`), a legitimately onboarded-but-malicious organization can send a correctly-signed membership webhook that reuses another organization's team id, silently joining an attacker-controlled user to that team.

### Finding Description
The broken binding is: the code should enforce `Team#organization == params.organization.login` for any team matched, but instead only enforces `Team#github_id == params.team.id`: [1](#0-0) 

`find_or_create_by!(github_id: params.team.id)` performs a lookup keyed only on `github_id`. If a `Team` row with that `github_id` already exists (created previously for organization B), the block passed to `find_or_create_by!` is never executed for existing records — `team.organization = params.organization.login` only runs on creation, not on lookup — so the existing team's `organization` field is left untouched, but the found `Team` object is nonetheless the real, privileged team belonging to organization B.

Signature verification is scoped per-organization, using the payload's own `organization`/`repository.owner.login` to select which `GitHubApp` (and thus which `webhook_secret`) to validate against: [2](#0-1) [3](#0-2) 

This means a webhook claiming `organization.login = "attacker-org"` is verified using `attacker-org`'s own configured `webhook_secret` — which the party administering `attacker-org`'s GitHub App legitimately controls. This is by design and is not itself a signature bypass; the attacker-org's own event is correctly authenticated as coming from attacker-org. The vulnerability is that authentication of "this webhook really came from org attacker-org" does **not** imply authorization to mutate a `Team` row that was created for/by a different organization. `Team.rb`'s `github_hooks` association is scoped by `organization`, and every org is expected to independently subscribe to `REQUIRED_HOOKS = %i[membership]`: [4](#0-3) 

But `find_or_create_team!` never joins through that scoping — it trusts the numeric `team.id` in the payload body across organizational boundaries.

Attack flow:
1. Attacker administers real org `attacker-org`, onboarded into Shipit with its own `webhook_secret` (a normal, legitimate integration).
2. Org B ("real-org") already has `Shipit::Team(github_id: 999, organization: "real-org")` present in `Shipit.github_teams` (visible to the attacker via GitHub's public team page URL, `.../orgs/real-org/teams/<slug>` → numeric id sometimes exposed via API/URL for public teams).
3. Attacker POSTs to `/webhooks` with header `X-Github-Event: membership`, signed with `attacker-org`'s own valid `webhook_secret`, body: `{"action":"added","team":{"id":999,"name":"x","slug":"x","url":"x"},"organization":{"login":"attacker-org"},"member":{"login":"attacker"}}`.
4. `verify_signature` validates successfully (attacker-org's own secret, attacker-org's own signature).
5. `MembershipHandler#process` calls `find_or_create_team!`, which finds the *existing* `Team(github_id: 999)` (belonging to real-org) and calls `team.add_member(member)`, creating a `Membership` linking the attacker's GitHub login to real-org's privileged team.

Existing guards do not stop this: `verify_signature` only authenticates *which organization sent the request*, not *which resources that organization is allowed to reference*; `drop_unhandled_event` and the `ExplicitParameters` schema only validate shape/presence of fields, not cross-org ownership; there is no `require_permission!`/organization-equality check in `find_or_create_team!` or `Team` model validations.

### Impact Explanation
A malicious but legitimately-onboarded organization can add arbitrary attacker-controlled GitHub logins as members of any `Shipit::Team` whose `github_id` is known (team ids are visible via GitHub UI/API for public teams, or guessable as small sequential integers). Since `Shipit.github_teams` membership is used for authorization decisions elsewhere in the app (team membership drives `User` authorization for the teams configured in `Shipit.secrets.github[...][:oauth][:teams]`), this is a direct escalation into `Shipit.github_teams` authorization for a different, victim organization — matching the High severity category ("escalation into `Shipit.github_teams` authorization"). The blast radius spans every tenant/organization hosted by the same Shipit instance, since `Team` records are not otherwise isolated per organization at lookup time. This is repeatable against any team whose `github_id` the attacker can learn, for as long as the attacker's own organization remains configured in Shipit.

### Likelihood Explanation
Preconditions: Shipit must be configured in the multi-organization mode (`secrets.github` keyed by organization, per `github_default_organization`/`github_app_config`), with at least two organizations onboarded — the attacker's own (real, but malicious-admin-operated) organization, and the victim organization. The attacker needs only their own org's webhook secret (which they legitimately possess as the org's own GitHub App administrator) and the victim's public team id. No brute force, no secret theft, no privileged Shipit access is required. This is a low-cost, deterministic, single-request exploit, fully repeatable.

### Recommendation
Scope the `Team` lookup in `find_or_create_team!` by both `github_id` and `organization` (i.e., `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`), and treat a `github_id` collision against a different `organization` as a hard error (raise/log/reject) rather than silently reusing the row, since GitHub team ids are meant to be globally unique and a mismatch indicates either misconfiguration or an attack.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/membership_handler_test.rb (conceptual)
test "membership webhook from a different organization cannot hijack another org's team" do
  victim_team = Shipit::Team.create!(github_id: 999, organization: 'real-org', name: 'Admins', slug: 'admins', api_url: 'https://x')

  payload = {
    action: 'added',
    team: { id: 999, name: 'Admins', slug: 'admins', url: 'https://x' },
    organization: { login: 'attacker-org' },
    member: { login: 'attacker' }
  }

  # Signed/authenticated as attacker-org (its own valid webhook secret)
  Shipit::Webhooks::Handlers::MembershipHandler.new.call(payload.deep_stringify_keys)

  attacker = Shipit::User.find_by!(login: 'attacker')

  # BEFORE fix: this passes, proving the vulnerability
  assert_includes victim_team.reload.members, attacker

  # EXPECTED (fixed) behavior: no Team should be found/created for attacker-org
  # with real-org's github_id, and no Membership should be created.
end
```
Binding checked: `params.organization.login` ("attacker-org") vs `Team#organization` for `github_id: 999` ("real-org") — they diverge, yet `find_or_create_team!` returns the `real-org` `Team` row and permits mutation, confirming the vulnerability.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
