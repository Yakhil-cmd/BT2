This confirms the core mechanism. `StatusHandler#process` iterates `Commit.where(sha: params.sha)` with **no repository/stack scoping whatsoever** [1](#0-0) , and calls `commit.create_status_from_github!(params)` on every matching row, regardless of which repository authenticated the webhook. `create_status_from_github!` -> `add_status` writes a `Status` record via `statuses.replicate_from_github!(stack_id, github_status)`, which recomputes `deployable?`/`blocked?` and fires `schedule_merges` for `success`/`pending` states [2](#0-1) [3](#0-2) .

The signature check (`verify_signature`) only proves the payload came from the GitHub App installation for `repository_owner` derived from the payload itself [4](#0-3) ; it does not constrain which commit rows the handler is allowed to touch. Cross-repository `Commit`/`Status` mutation via unscoped SHA lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by bare SHA with `Commit.where(sha: params.sha)`, with no filter on the repository/stack that authenticated the webhook. Because the `commits` table's index is `(stack_id, sha)` and not a global-unique constraint on `sha`, any two stacks (e.g. an upstream repo and any fork sharing git history) can hold rows with the identical SHA, letting a webhook validly signed for a totally unrelated repository write a `Status` (e.g. `review/approved` / `success`) onto a victim stack's commit.

### Finding Description
The broken binding: the code implicitly assumes `Commit.where(sha: params.sha) == commits belonging to the repository that sent this webhook`, but the actual query is `Commit.where(sha: params.sha)` over the entire table with no `stack_id`/repository filter: [1](#0-0) 

`WebhooksController#verify_signature` only checks that the payload's cryptographic signature matches the GitHub App configured for `repository_owner` extracted from the same attacker-controlled payload [4](#0-3) ; it proves the request came from *some* GitHub org/repo the app is installed on, but does nothing to constrain which `Commit` rows the handler can mutate afterward. There is no per-stack/per-repository scoping anywhere in `StatusHandler`, and the schema only indexes `sha` together with `stack_id` (`db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`), confirming duplicate SHAs across different stacks are an expected, unhandled condition rather than something the model rejects.

Exploit flow:
1. Attacker owns/administers a repository (e.g. a public fork of the victim's repo) that Shipit tracks as its own stack, sharing commit history/SHAs with the victim repo (common for forks of public projects, or any two stacks pointed at overlapping/rebased history).
2. Attacker sets a commit status (`context: review/approved`, `state: success`) on a shared SHA in their own repository via the normal GitHub API for their own repo — a legitimate action GitHub allows any repo owner to perform.
3. GitHub emits a real, correctly-signed `status` webhook to Shipit for the attacker's repository.
4. `StatusHandler#process` finds **all** `Commit` rows across **all** stacks matching that SHA — including the victim's — and calls `commit.create_status_from_github!(params)` on each, via `Commit#create_status_from_github!` → `add_status` → `statuses.replicate_from_github!` [2](#0-1) .
5. `add_status` recomputes `deployable?`/`blocked?` state transitions and, for `success`/`pending` states, calls `stack.schedule_merges` [3](#0-2) , which can unblock a required `review/approved` gate on the victim's stack and trigger merges/deploys the victim never authorized.

No existing guard (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema) checks that the matched `Commit#stack` corresponds to the repository that authenticated the webhook.

### Impact Explanation
A payload authenticated for repository A can flip required-context gating (`review/approved` / `success`) and drive merge/deploy scheduling for repository B's stack, purely because they share a commit SHA — this is a cross-tenant/cross-repository write, matching the Critical category "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge." The attacker gains the ability to force a `success` status (satisfying a required check) or, symmetrically, poison a commit with a `failure`/`error` status to block a legitimate deploy, on any victim stack whose commit history overlaps with a repository the attacker controls.

### Likelihood Explanation
Preconditions are modest: the attacker needs their own tracked repository/stack in Shipit and a commit SHA shared with the victim (trivially true for forks of public repos, which is a common Shipit use case). No Shipit session, API token, or webhook secret is needed beyond the ability to legitimately set a status on their own repo via GitHub, which any repo owner can do. The action is repeatable against any stack sharing history, at low cost.

### Recommendation
Scope the lookup by repository, not just SHA — e.g., resolve the `Stack`/`Repository` from the webhook payload (as `PushHandler` and other handlers do) and constrain `Commit.where(stack_id: stack.id, sha: params.sha)` before calling `create_status_from_github!`, rejecting or ignoring matches outside the authenticated repository.

### Proof of Concept
minitest plan (no live GitHub):
1. Create two stacks/repositories, `victim_stack` and `attacker_stack`, each with a `Commit` sharing the same `sha` value (simulating a forked/shared history).
2. Set up `victim_stack` such that `review/approved` is a required status for deployability (per `deploy_spec`/`required_statuses`).
3. POST to `/webhooks` with `X-Github-Event: status`, a body `{ sha: <shared_sha>, state: 'success', context: 'review/approved', repository: { owner: { login: attacker_org } } }`, stubbing `verify_webhook_signature` to return `true` for the attacker's org only.
4. Assert, before the request: `victim_stack.commits.find_by(sha: shared_sha).deployable? == false` (or `blocked?/status` reflecting missing `review/approved`).
5. After posting, assert: `victim_stack.commits.find_by(sha: shared_sha).deployable? == true` (or that a `Status` row was created on the victim's commit) — proving the attacker-authenticated webhook for their own repo mutated the victim stack's commit state, violating "A `review/approved` status affects only the repository that authenticated it."
