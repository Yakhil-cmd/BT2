### Title
Attacker can grief a validator's epoch stake reward via lamport-balance overflow front-running - (File: `runtime/src/bank/partitioned_epoch_rewards/distribution.rs`)

### Summary
The reward distribution code adds a fixed calculated reward amount to a stake account's lamport balance, mirroring the external report's pattern of a hard-coded fixed amount being combined with an attacker-influenced total. Any unprivileged transaction sender can inflate the lamport balance of an arbitrary stake account before the epoch-reward distribution phase, causing the fixed reward addition to overflow and be silently discarded (burned) instead of paid, denying that staker's/validator's rewards for the epoch.

### Finding Description
`Bank::build_updated_stake_reward` computes the post-reward balance of a stake account by adding the pre-calculated, fixed `inflation.stake_reward` and `block_reward` amounts onto the stake account's current lamport balance: [1](#0-0) 

These reward amounts (`stake_reward`, `block_reward`) are computed and fixed during the reward *calculation* phase, based on stake and vote credit history, and are stored as a `PartitionedStakeReward` to be applied later during the *distribution* phase, over multiple blocks/epoch height partitions (analogous to the fixed 12 ETH auto-stake amount in the referenced report, which is computed once but applied later against a value that can move).

Because lamport transfers via the System program only require the *source* account to be a system-owned account — the *destination* account's owner is not restricted — any unprivileged transaction sender can transfer lamports directly to a target stake account (owned by the stake program) at any time, including in the window between reward calculation and reward distribution. By repeatedly/precisely inflating a target stake account's balance close to `u64::MAX`, an attacker can make `checked_add_lamports` fail with `ArithmeticOverflow` when the fixed reward is later added: [2](#0-1) 

The caller `store_stake_accounts_in_partition` handles this failure not by retrying, deferring, or crediting the reward elsewhere, but by burning the stake reward and block reward for that specific stake account and logging an error — the funds are removed from circulation and the entitled staker never receives the reward: [3](#0-2) 

A dedicated overflow test in the codebase confirms this exact failure path (`DistributionError::ArithmeticOverflow`) is reachable simply by pre-loading a stake account with an inflated lamport balance: [4](#0-3) 

This is the direct analog of the external report: a fixed amount (`_autoStakeWithSyndicate`'s 12 ETH stake amount / here, the fixed `stake_reward`+`block_reward`) is added against a balance/counter (`totalStaked` / here, the stake account's lamport balance) that an unprivileged, un-permissioned third party can manipulate ahead of time, causing the fixed-amount operation to revert/fail and the intended beneficiary to be denied their entitlement.

### Impact Explanation
Successful griefing causes concrete, unsigned loss of funds: the staker's and/or validator's rightful inflation/block reward for the epoch is permanently burned rather than credited, reducing the total token supply and denying the legitimate stakeholder their earned reward. Because this happens deterministically inside `distribute_epoch_rewards_in_partition`, which runs identically on all validators processing the same block, it does not itself cause consensus divergence, but it is a concrete stake/reward-accounting corruption reachable purely through a normal, unprivileged System-program transfer transaction. Any staker's account can be targeted, so the impact scales to arbitrary validators/delegators in the epoch reward set.

### Likelihood Explanation
Likelihood is low-to-moderate: reaching `u64::MAX` requires an attacker to either already hold or be able to move an enormous number of lamports into the target account (practically infeasible on real economics, since total lamport supply is far below `u64::MAX`, but not physically impossible given `u64::MAX` ≈ 18.4 quintillion lamports vs. current supply). Under current mainnet economics this specific overflow path is not economically reachable by a real attacker, which meaningfully lowers real-world likelihood compared to the original 12 ETH griefing report (which required only a trivial 1 gwei stake). It is nonetheless a legitimate, currently-reachable code path with no access control preventing anyone from funding any account to attempt it, and no on-chain limit preventing a determined actor (e.g. an entity controlling a large fraction of total supply, or future supply growth) from executing it against a chosen target.

### Recommendation
- Reject/clamp the reward-add path instead of silently burning: on `ArithmeticOverflow`, cap the credited amount to `u64::MAX` (saturating add) rather than dropping the entire reward, so a partial reward is preserved rather than zero.
- Consider explicit validation/limits so lamports added to a stake account by unrelated transfers cannot push balances into a range that would break fixed-amount reward math (e.g., warn/report or refuse to further inflate stake accounts near `u64::MAX` beyond legitimate stake/rent purposes).
- Add telemetry/alerting (beyond the existing `error!` log) so operators can detect and investigate reward-burn events tied to suspicious pre-inflated account balances.

### Proof of Concept
1. Identify a target stake account `S` that is scheduled to receive stake/block rewards in the upcoming epoch reward distribution.
2. Submit unprivileged System-program transfer transactions to send lamports to `S` until its balance is within `stake_reward + block_reward - 1` of `u64::MAX` (feasible only if attacker controls a sufficiently large lamport balance).
3. When the bank reaches the reward-distribution block height for `S`'s partition, `Bank::build_updated_stake_reward` calls `account.checked_add_lamports(partitioned_stake_reward.inflation.stake_reward)` / `block_reward`, which overflows and returns `Err(DistributionError::ArithmeticOverflow)` (mirrored exactly by the existing unit test using an `overflowing_account` pre-set to `u64::MAX - stake_reward - block_reward + 1`, at [4](#0-3) ).
4. `store_stake_accounts_in_partition` catches the error and burns the reward instead of crediting `S`, permanently denying the reward to the legitimate staker.
