### Title
Tokens pushed to the controller or pool outside the declared collateral/refund lists are silently stranded with no recovery path - (File: contracts/controller/src/strategies/flash_position.rs)

### Summary
The OpenQ report describes funds sent "by error" alongside a deposit that the contract ignores in its accounting and can never return. The XOXNO Lending analog exists in `flash_position`: during the receiver callback, any token the receiver pushes to the controller that is not declared in `collaterals` (credited as supply) or `refund_assets` (returned to the caller) is neither credited nor refunded, and the codebase explicitly states there is no sweep endpoint. The same black hole exists for direct token transfers to the pool, whose `cash` book only moves on controller-instructed amounts.

### Finding Description
In `process_flash_position`, the controller snapshots balances only for the caller-declared `collaterals` and `refund_assets` before invoking the receiver (`snapshot_balances` at lines 125–130), then:
- `collect_collateral_deposits` (lines 325–352) measures deltas only for declared collateral assets and deposits them.
- `refund_listed_assets` (lines 372–384) refunds deltas only for declared refund assets, and `refund_controller_balance_delta` refunds only the delta above the pre-callback baseline — so even a later `flash_position` cannot touch a stranded balance because it sits inside the baseline.

Any token the receiver transfers to the controller outside both lists is stranded permanently. The project documentation confirms this is deliberate-but-unrecoverable behavior: "Undeclared callback assets receive neither credit nor refunds. There is no controller sweep endpoint" (docs/reference/endpoints.md), mirrored in INV-STRAT-04: returned tokens "remain uncredited if in neither list" (docs/reference/invariants.md).

Analogously, the pool credits `cash` only on controller-declared amounts — `supply`, `repay` and `recapitalize` credit `cash` "on the controller's word, without verifying the transfer" (contracts/pool/README.md trust table). A user who calls `token.transfer(user, pool, X)` directly receives no supply shares, no debt reduction, and no refund; the tokens sit in pool custody above the `cash` book with no entrypoint that can return them (refunds are bounded by the amount just sent in; `claim_revenue` is owner-only and bounded by revenue shares).

The unprivileged path: any address calls `controller.flash_position(caller, account_id, spoke_id, mode, debt, amount, receiver, data, collaterals, refund_assets)` with their own Wasm receiver. If the receiver pushes a token absent from both lists (e.g., a wrong-asset swap output, a misconfigured declaration, or an extra asset intended as a donation), the call succeeds, the position opens, and the pushed tokens are locked on the controller forever. The integration test `tests/integration/flows/flash_position.sh` explicitly encodes this: "Extra undeclared asset is not deposited... The undeclared USDC is not credited."

### Impact Explanation
Permanent freezing of user funds: tokens pushed to the controller (or pool) by an unprivileged caller are unrecoverable — no credit, no refund, no sweep. This matches the original report's impact ("protocol tokens lost by the funder" with no refund path). Unlike OpenQ, the stranded funds cannot be claimed by a later claimer either — the balance-delta baseline mechanism protects pre-existing controller balances, so the loss is total with no beneficiary. Severity is bounded by the self-inflicted nature: Medium.

### Likelihood Explanation
Low-to-moderate. It requires a caller to build a flash receiver that transfers an undeclared token to the controller, or a user to transfer directly to the pool — both are operator/integration mistakes rather than an attack. However, the failure is silent (the transaction succeeds and the position opens), so there is no signal to the integrator that funds were dropped, mirroring the original where the deposit succeeded while `msg.value` was ignored.

### Recommendation
Mirror the original recommendation — revert rather than silently keep. Concretely:
1. In `flash_position`, after `refund_listed_assets`, sweep-check that the controller's balance delta of every token touched during the callback is zero, or require the receiver to enumerate all pushed assets. Practically: after the callback, compare the controller's balance of each asset in `extra_assets` plus any token the receiver could plausibly push — or simpler, add a documented `sweep`/`rescue` entrypoint gated to the governance/accumulator address so stranded tokens are recoverable rather than burned.
2. For the pool, add an owner-only `skim`/`rescue` that transfers `token.balance(pool) - cash` to the accumulator, since every `cash`-crediting path already verifies its own measured inbound delta — any excess is by definition orphaned.

fn collect_collateral_deposits(
    env: &Env,
    controller: &Address,
    collaterals: &Vec<(HubAssetKey, i128)>,
    before: &Map<Address, i128>,
) -> Vec<(HubAssetKey, i128)> {
    let mut deposits: Vec<(HubAssetKey, i128)> = Vec::new(env);
    for (hub_asset, min_amount) in collaterals.iter() {
        let baseline = before
            .get(hub_asset.asset.clone())
            .unwrap_or_else(|| panic_with_error!(env, GenericError::InternalError));
        let delta = balance_delta_since(env, &hub_asset.asset, controller, baseline);
        assert_with_error!(
            env,
            delta >= min_amount,
            StrategyError::CollateralMinimumNotMet
        );
        if delta > 0 {
            deposits.push_back((hub_asset, delta));
        }
    }
    assert_with_error!(
        env,
        !deposits.is_empty(),
        StrategyError::CollateralMinimumNotMet
    );
    deposits
}

pub(crate) fn refund_controller_balance_delta(
    env: &Env,
    asset: &Address,
    balance_before: i128,
    refund_to: &Address,
) {
    let controller = env.current_contract_address();
    let excess = balance_delta_since(env, asset, &controller, balance_before);
    if excess > 0 {
        token::Client::new(env, asset).transfer(&controller, refund_to, &excess);
    }
}
