### Title
`StatusHandler#process` mutates commits by global SHA lookup with no repository scoping, unlike `PushHandler`/`PullRequestHandler` handlers which scope via `Handler#stacks` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Handler#stacks` scopes every mutation to `Repository.from_github_repo_name(repository_name).stacks`, and `PushHandler#process` (and all `PullRequest::*Handler`s) build their queries from that scoped relation before touching any record. `StatusHandler#process`, however, resolves its mutation target as `Commit.where(sha: params.sha)` with no repository predicate at all, so any commit anywhere in the database sharing that SHA is mutated regardless of which repository the inbound, validly-signed webhook actually belongs to.

### Finding Description
Binding claimed: for every `Handler` subclass, `mutation_target_set == stacks_scoped_records_for(payload.repository.full_name)`.

- `Handler#stacks` (app/models/shipit/webhooks/handlers/handler.rb:32-38) computes `Repository.from_github_repo_name(repository_name)&.stacks`.
- `PushHandler#process` (app/models/shipit/webhooks/handlers/push_handler.rb:12-17) mutates only `stacks.not_archived.where(branch:)` — satisfies the binding.
- `PullRequest::*Handler`s likewise start from `stacks` (confirmed by `from_github_repo_name` usage across `pull_request/*_handler.rb`).
- `StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24) instead does:
```
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
It never calls `stacks`, never calls `Repository.from_github_repo_name`, and never checks `commit.stack.repository`. The binding is broken: the mutation set is the *global* set of commits matching a SHA, not the set scoped to the requesting repository.

Root cause and exploit path: `verify_signature` in `app/controllers/shipit/webhooks_controller.rb:24-49` verifies the HMAC against the GitHub App configured for `repository_owner` (`params.dig('repository','owner','login')`), i.e. it only proves the event genuinely came from GitHub for *that* organization/repo — it says nothing about which `sha` values are legitimate to touch. Git commit SHA-1s are content-addressed and repository-independent: if an attacker's own repository (which they legitimately administer and which has the Shipit GitHub App installed) contains a commit with byte-identical content (message, tree, parents, author/committer timestamps) to a commit already tracked by a victim's stack — trivially achievable by forking/mirroring a public commit, or by cherry-picking/replaying known commit metadata — then setting a commit status on that commit via the real GitHub API in the attacker's own repository produces a fully legitimate, correctly-signed `status` webhook whose `repository.full_name` is the attacker's own repo but whose `sha` collides with the victim's tracked commit.

Because `StatusHandler` does no repository check, `Commit.where(sha: params.sha)` matches the victim's `Commit` record and calls `commit.create_status_from_github!(params)` on it (app/models/shipit/commit.rb:165-169), which persists a new `Status` on the victim's commit and runs `add_status`, emitting `Hook.emit(:deployable_status, ...)` and potentially calling `stack.schedule_merges` (app/models/shipit/commit.rb:366-386), i.e. it can flip a foreign stack's commit into a "success"/deployable state and trigger downstream automation (`schedule_continuous_delivery`, app/models/shipit/commit.rb:281-287) despite the attacker never having any relationship to that stack or repository.

None of the existing guards stop this: `verify_signature` validates only the sender's own organization's signature (irrelevant to which SHA is targeted), `ExplicitParameters` only validates payload shape (`sha`, `state`, etc. as strings), and `ActiveRecord` model validations on `Repository`/`Stack` never run because no `Repository` lookup happens in `StatusHandler` at all.

### Impact Explanation
An attacker who administers any repository with the Shipit GitHub App installed can inject arbitrary CI status records (including fabricated "success" statuses) onto commits belonging to any other repository/stack tracked by the same Shipit instance, as long as they can reproduce a matching commit SHA (achievable for any commit whose exact content is known/public, e.g. via forking, mirroring, or cherry-picking). This can move a victim commit into a "deployable" state and trigger `schedule_continuous_delivery`, i.e. an unauthorized deploy signal for a repository the attacker never authenticated for — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team" / "an unauthorized deploy". The attack is repeatable against any commit SHA the attacker can reproduce, across the whole Shipit-tracked fleet, not limited to one victim.

### Likelihood Explanation
Preconditions: the attacker must own/administer at least one repository with the Shipit GitHub App/webhook installed (or otherwise be able to trigger a validly signed `status` event for a repo they control), and must be able to reproduce a commit with an identical SHA to a targeted victim commit. The latter is trivial when the target commit's exact byte content is knowable (public open-source commits, forks, mirrors, vendored upstream commits) since git SHA-1 is purely a function of commit content and independent of the hosting repository. No secrets, sessions, or elevated privileges of any kind are required — only ordinary GitHub repo-owner capabilities. This is realistically and repeatably exploitable wherever Shipit tracks any commit whose content is also reachable/reproducible by an unprivileged repository owner.

### Recommendation
Make `StatusHandler#process` scope through `stacks` exactly like `PushHandler`/`PullRequestHandler` do, e.g. resolve commits as `stacks.flat_map(&:commits).select { |c| c.sha == params.sha }`, or more directly `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, so a status webhook can only mutate commits belonging to stacks whose repository matches `Repository.from_github_repo_name(repository_name)`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_cross_repo_test.rb
class StatusHandlerCrossRepoTest < ActiveSupport::TestCase
  test "PushHandler does not touch an unrelated repository's stack" do
    victim_repo = shipit_repositories(:shipit)
    attacker_repo = Shipit::Repository.create!(owner: 'attacker', name: 'evil')
    victim_stack = shipit_stacks(:shipit)
    original_head = victim_stack.commits.last

    cross_repo_push_payload = {
      'ref' => "refs/heads/#{victim_stack.branch}",
      'after' => 'deadbeef',
      'repository' => { 'full_name' => attacker_repo.full_name,
                         'owner' => { 'login' => attacker_repo.owner } }
    }

    Shipit::Webhooks::Handlers::PushHandler.new(cross_repo_push_payload).process

    assert_equal original_head, victim_stack.reload.commits.last
  end

  test "StatusHandler mutates a commit belonging to an unrelated repository" do
    victim_stack = shipit_stacks(:shipit)
    victim_commit = victim_stack.commits.create!(sha: 'a' * 40, message: 'shared content')
    attacker_repo = Shipit::Repository.create!(owner: 'attacker', name: 'evil')

    cross_repo_status_payload = {
      'sha' => victim_commit.sha,
      'state' => 'success',
      'context' => 'ci/attacker-forged',
      'repository' => { 'full_name' => attacker_repo.full_name,
                         'owner' => { 'login' => attacker_repo.owner } }
    }

    assert_difference -> { victim_commit.reload.statuses.count }, 1 do
      Shipit::Webhooks::Handlers::StatusHandler.new(cross_repo_status_payload).process
    end
  end
end
```
Both tests use the same repository-mismatch pattern; `PushHandler` correctly no-ops on the unrelated repository while `StatusHandler` writes a `Status` record onto the victim's commit — demonstrating the asymmetry.
