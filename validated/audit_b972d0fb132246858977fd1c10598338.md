### Title
Cross-organization webhook signature confusion allows unauthenticated escalation into `Shipit.github_teams` authorization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to validate a webhook against using one field of the *unverified* JSON body (`repository.owner.login`, falling back to `organization.login`), while the `MembershipHandler` that actually mutates `Team`/`Membership` records acts on a *different* field of the same body (`organization.login`) that is never checked against the field used to pick the verifying secret. Because `GitHubApp#verify_webhook_signature` unconditionally returns `true` when the selected organization has no `webhook_secret` configured (an explicitly documented "optional" setting), an attacker can pick an organization with no secret to short-circuit verification while pointing the actual team-mutation logic at a different, secured organization.

### Finding Description
`repository_owner` is read straight out of the not-yet-verified payload: [1](#0-0) 

This value is used to pick the `GitHubApp` instance whose secret validates the signature: [2](#0-1) 

`verify_webhook_signature` treats an *unset* `webhook_secret` as automatic success, independent of the actual signature header or body content: [3](#0-2) 

The docs explicitly present `webhook_secret` as optional per-organization, so a multi-org Shipit deployment can legitimately have one organization configured without a secret while others have one: [4](#0-3) 

Meanwhile, the `membership` event handler ignores `repository.owner.login` entirely and instead trusts `organization.login` (and attacker-supplied `team`/`member` sub-objects) to create/update `Team` and `Membership` rows: [5](#0-4) 

This breaks the intended binding: **organization whose secret authenticated the request == organization whose team/membership state is mutated**. An attacker can craft a body containing `repository.owner.login = "org-without-secret"` (used only to select a verifier that trivially passes) and `organization.login = "victim-org"` (used by the handler to create/modify a `Team` and add a `member`). No `Repository` or `repository.full_name` field is required for the `membership` event, so the mismatch is fully exploitable without ever touching a real repository.

`Team.find_or_create_by!(github_id: params.team.id)` has no uniqueness constraint tying `organization`/`slug` to a single legitimate record (only `github_id` is used as the lookup key, and there is no application-level or, as far as could be confirmed, schema-level uniqueness index on `organization`+`slug` in the code inspected): [6](#0-5) 

so an attacker can create a brand-new `Team` row (with an arbitrary `github_id`) whose `organization`/`slug` combination matches a handle configured in `Shipit.github_teams` (`oauth.teams`), then add themselves (via `params.member.login`, matching their own real GitHub login used to log in through OAuth) as a member: [7](#0-6) [8](#0-7) 

Because `current_user.authorized?` only checks team membership by handle, a forged `Team`/`Membership` pair is sufficient to satisfy `force_github_authentication` after a normal OAuth login with the attacker's own GitHub account.

### Impact Explanation
This crosses the "GitHub identity vs. `User` bound to the session" / "escalation into `Shipit.github_teams` authorization" boundary called out in scope: an attacker with no repository access, no `ApiClient` token, and no knowledge of any `webhook_secret` (they only need one org in the deployment to have no secret configured, which is a documented, legitimate configuration state, not a misuse of the engine) can grant their own GitHub account membership in a Shipit-recognized team for an org they have no relationship to, and thereby pass the application's authorization gate to reach stacks, deploys, and rollbacks.

### Likelihood Explanation
Requires: (1) a multi-organization Shipit deployment (explicitly documented and supported), (2) at least one configured organization without a `webhook_secret` (explicitly documented as optional), and (3) knowledge of another org's login name and a team handle configured in `Shipit.github_teams` (both are typically public/discoverable). No credentials, tokens, or elevated access are required — only an HTTP POST to the public `/webhooks` endpoint. This is a moderate-likelihood, high-impact issue contingent on that documented-optional configuration choice.

### Recommendation
- Bind webhook signature verification and payload interpretation to the *same* field: verify using the same organization identifier that the handler will act upon for every event type (not "repository owner OR organization", chosen independently from what handlers subsequently read).
- Do not allow `verify_webhook_signature` to unconditionally return `true` when `webhook_secret` is blank; either require a secret for every configured organization or fail closed.
- Add a uniqueness constraint (DB index and model validation) on `Team#organization`/`Team#slug` (or on `github_id` scoped globally) to prevent forged duplicate `Team` rows from shadowing legitimate ones referenced by `Shipit.github_teams`.

### Proof of Concept
1. Deploy Shipit with two GitHub App configs: `org-no-secret` (no `webhook_secret`) and `victim-org` (has `Shipit.github_teams` including `"victim-org/developers"`).
2. POST to `/webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "team": { "id": 999999111, "name": "Fake", "slug": "developers", "url": "https://example.com" },
  "organization": { "login": "victim-org" },
  "member": { "login": "attacker-github-login" },
  "repository": { "owner": { "login": "org-no-secret" } }
}
```
   omitting/forging the `X-Hub-Signature` header (it is never checked, since `org-no-secret` has no configured secret).
3. `verify_signature` resolves `repository_owner` to `"org-no-secret"`, `verify_webhook_signature` returns `true` unconditionally.
4. `MembershipHandler#process` creates a new `Team` with `organization: "victim-org"`, `slug: "developers"`, and adds `attacker-github-login` as a member.
5. The attacker logs in via normal GitHub OAuth with `attacker-github-login`; `Shipit.github_teams` resolves `"victim-org/developers"` to the forged `Team`, and `current_user.authorized?` returns `true`, granting access to `victim-org`'s stacks.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def force_github_authentication
      if current_user.logged_in? && current_user.requires_fresh_login?
        Rails.logger.warn("User #{current_user.id} requires a fresh login, logging out...")
        reset_session
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      elsif Shipit.authentication_disabled? || current_user.logged_in?
        unless current_user.authorized?
          team_handles = Shipit.github_teams.map(&:handle)
          team_list = team_handles.to_sentence(two_words_connector: ' or ', last_word_connector: ', or ')
          render(plain: "You must be a member of #{team_list} to access this application.", status: :forbidden)
        end
      else
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      end
    end
