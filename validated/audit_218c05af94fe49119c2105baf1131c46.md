### Title
Webhook signature verification is scoped by an attacker-controlled `repository.owner.login` field that is never cross-checked against the repository/stack the event actually mutates - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification based on `repository_owner`, a value read directly out of the unauthenticated, unverified JSON body. This is the same class of bug as the ERC20 report: a value that is *acted upon* (here: "which secret authorizes this webhook") is never itself covered by (or reconciled with) the thing that is supposed to guarantee integrity (the signature check tied to the correct tenant). In a multi-organization Shipit deployment where any configured organization has no `webhook_secret`, an attacker can pick that organization's name for `repository.owner.login` to trivially satisfy signature verification, while the rest of the JSON payload (used by the actual event handlers to resolve the stack/repository to act on) references a different, "protected" repository.

### Finding Description
`verify_signature` computes `repository_owner` from the raw request body and uses it to pick the `GitHubApp` instance/secret to verify against: [1](#0-0) [2](#0-1) 

`repository_owner` is taken from `params.dig('repository', 'owner', 'login')` (or `organization.login`) - a field inside the same untrusted payload that the caller controls before any signature has been validated.

`Shipit.github(organization:)` resolves the app config per-organization: [3](#0-2) 

`GitHubApp#verify_webhook_signature` intentionally short-circuits to `true` when the resolved organization's `webhook_secret` is blank: [4](#0-3) 

The `create` action then dispatches the *entire* payload (not just the fields used for organization selection) to event handlers, which resolve the actual stack/repository independently of `repository_owner`: [5](#0-4) 

The test suite confirms that `repository.owner.login` is a payload fragment merged independently of any other repository identity field (e.g. `full_name`) across many event types (`status`, `membership`, `push`, etc.): [6](#0-5) 

There is no code path that reconciles the organization used for signature verification with the organization/repository actually referenced by the rest of the payload that the handler acts on. The binding that should hold is:
`organization whose secret validated this request == organization owning the repository/stack the event handler mutates`
but the code only enforces `organization whose secret validated this request == repository.owner.login (attacker-supplied)`, with no re-validation that this equals the repository actually processed.

### Impact Explanation
If a Shipit instance is configured with multiple GitHub organizations (per `lib/shipit.rb#github_app_config`/`github_organizations`) and even one of them has no `webhook_secret` configured (an explicitly supported/optional setting), any unauthenticated attacker can craft a JSON body claiming `repository.owner.login` (or `organization.login`) equal to that unsecured org to make `verify_webhook_signature` return `true` unconditionally, while embedding a `repository.full_name`/other identity fields pointing at a different, secured organization's repository/stack. The dispatched handlers (`Shipit::Webhooks.for_event`) then act on that payload as if it were a legitimately signed GitHub event for the targeted stack - enabling forged `push`, `status`, `membership`, `pull_request`, etc. events against stacks that belong to organizations whose secrets the attacker never had. This can drive unauthorized deploy triggers, sync jobs, membership/team mutations, or merge/lock state changes without any credential - a "cross-repository writes"/"unauthorized deploy" style impact.

### Likelihood Explanation
Exploitability depends entirely on deployment configuration: it requires (a) a multi-organization Shipit deployment and (b) at least one configured organization without a `webhook_secret`. This is a realistic, admin-driven misconfiguration explicitly permitted by the code (`webhook_secret` is optional per-organization, not globally validated as mandatory), and the docs even show organizations configured without one for local/dev use. No credential, session, or GitHub write access is needed by the attacker - only an unauthenticated `POST` to the public webhooks endpoint. Likelihood is therefore Medium: it is not exploitable against every deployment, only against those with an unsecured organization in a multi-org configuration, but the engine itself provides no safeguard preventing or warning against this state.

### Recommendation
- Enforce that every configured organization in a multi-org deployment has a non-blank `webhook_secret`; refuse to boot / raise misconfiguration errors otherwise, rather than silently treating a missing secret as "always verified."
- After signature verification succeeds, re-derive the organization/repository the event handler will act on from the verified payload and assert it matches the organization whose secret validated the request (i.e., bind `repository_owner` used for verification to the repository actually processed), rather than trusting the payload's internal consistency implicitly.
- Consider not allowing `verify_webhook_signature` to return `true` when `webhook_secret` is unset in production/multi-org mode; only allow that fallback for a single, explicitly unauthenticated deployment mode.

### Proof of Concept
1. Deploy Shipit with `github:` configured for two organizations, e.g. `SecureOrg` (has `webhook_secret: <secret>`) and `OpenOrg` (no `webhook_secret` set), per the schema handled by `Shipit.github_app_config`.
2. As an unauthenticated attacker, send:
```
POST /webhooks
X-Github-Event: push
Content-Type: application/json

{
  "repository": { "owner": { "login": "OpenOrg" }, "full_name": "SecureOrg/protected-repo" },
  "after": "<attacker-chosen-sha>",
  "ref": "refs/heads/master"
}
```
No `X-Hub-Signature` header (or an arbitrary garbage one) is required.
3. `repository_owner` resolves to `"OpenOrg"`; `Shipit.github(organization: "OpenOrg")` returns a `GitHubApp` with `webhook_secret` blank, so `verify_webhook_signature` returns `true` unconditionally per `lib/shipit/github_app.rb:77`.
4. `create` proceeds and dispatches the full payload (referencing `SecureOrg/protected-repo`) to the `push` handler, which resolves and acts on the `SecureOrg` stack - a forged event accepted without ever knowing `SecureOrg`'s webhook secret.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
