### Title
Webhook signature verification binds the GitHub App secret to `repository.owner.login`, but handlers act on the unrelated `repository.full_name`, enabling cross-organization/cross-repository forgery in multi-org deployments - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In a multi-organization Shipit deployment (supported via the `github:` config hash keyed by organization, as documented in `config/secrets.development.example.yml`), `WebhooksController#verify_signature` selects which GitHub App/webhook secret to use for HMAC verification based on `repository.owner.login` (or `organization.login`) taken from the attacker-controlled JSON body, but the actual event handlers act on a completely different field, `repository.full_name`, to look up the `Repository`/`Stack` records to mutate. Nothing ties these two fields together, so a party who only knows the webhook secret for one organization can forge a signed payload whose `owner.login` matches their known org (to pass verification) while `full_name` points at a repository belonging to a different organization/App, causing Shipit to act on that unrelated repository.

### Finding Description
`WebhooksController#verify_signature` picks the signing/verification secret using `repository_owner`: [1](#0-0) [2](#0-1) 

The signature check only proves that the requester knows the secret associated with the organization named by `repository.owner.login` (or `organization.login`); it does not constrain any other field of the JSON body, including `repository.full_name`.

Once verification passes, `create` dispatches the raw JSON to the registered handlers: [3](#0-2) 

All handlers derive the actual target `Stack`/`Repository` from `repository.full_name`, not from `repository.owner.login`: [4](#0-3) 

For example, `PushHandler` uses that lookup to enqueue a sync against real stacks: [5](#0-4) 

Because `owner.login` (used for secret selection) and `full_name` (used for the actual write) are two independent, attacker-supplied fields inside the same signed body, an attacker who obtained/knows the webhook secret configured for their own organization ("orgA") can craft a payload:
```json
{
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/target-repo" },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>"
}
```
sign it with orgA's secret (which they legitimately hold), and send it to `/webhooks`. `repository_owner` resolves to `"orgA"`, `Shipit.github(organization: "orgA")` is used to verify, and the HMAC computed over the full attacker-controlled raw body validates successfully. The handler layer, however, resolves the target via `full_name`, landing on `orgB/target-repo`'s `Stack`, which is unrelated to orgA and was never protected by orgA's secret.

This is the same root-cause shape as the referenced report: a verification step is performed against a subset/derived value at one point in time, while a materially different value is used for the subsequent state-changing action, without re-checking that the two are consistent — analogous to `SavingsVest.setParams` changing `protocolSafetyFee`/`vestingPeriod` without re-accruing/re-validating against the value the last accrual used.

### Impact Explanation
Depending on which webhook event is forged, this allows:
- `PushHandler`: triggering `GithubSyncJob`/deploy-relevant sync activity against a stack that belongs to a repository never protected by the attacker's secret — a cross-repository action, matching the Critical "cross-repository writes" impact bucket.
- Membership-style events (per `test/controllers/webhooks_controller_test.rb`, `:membership` webhooks create `Team`/`User`/`Membership` records) could be forged the same way to add/remove memberships tied to teams outside the attacker's own organization, which is an escalation path into `Shipit.github_teams` authorization (High impact), since `User#authorized?` and `Shipit::Authentication#force_github_authentication` gate access based on team membership. [6](#0-5) [7](#0-6) 

### Likelihood Explanation
This requires the attacker to already control (know) the webhook secret configured for at least one organization in a multi-org Shipit deployment — a realistic scenario for any org admin/integrator among several tenants sharing one Shipit instance, but not a fully "no credential" scenario. It does not require repository write access to the target org, an `ApiClient` token, or a GitHub App private key, and is exploitable purely by crafting an HTTP POST to `/webhooks`. This is only relevant to installations using the multi-organization `github:` config schema.

### Recommendation
When verifying and dispatching webhooks, cross-check that the organization used to select the verification secret (`repository.owner.login` / `organization.login`) matches the organization implied by every other repository-identifying field the handlers will use (`repository.full_name`'s owner segment) before invoking handlers, rejecting the request otherwise. Alternatively, bind the located `Repository`/`Stack` records to the verified organization explicitly inside `Handler#stacks`, rather than trusting `full_name` alone.

### Proof of Concept
1. Configure Shipit with two orgs, `orgA` and `orgB`, each with its own `webhook_secret`, per `config/secrets.development.example.yml`.
2. Register a `Stack` under `orgB/target-repo`.
3. As someone who knows only `orgA`'s webhook secret, POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{"repository": {"owner": {"login": "orgA"}, "full_name": "orgB/target-repo"}, "ref": "refs/heads/main", "after": "<sha>"}
```
4. Sign the raw body with `orgA`'s `webhook_secret` and set `X-Hub-Signature` accordingly.
5. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "orgA")` and validates the signature successfully.
6. `PushHandler#process` resolves the target stack via `full_name` = `orgB/target-repo` and enqueues `stack.sync_github`, acting on `orgB`'s repository despite the request only ever being authenticated against `orgA`'s secret.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
