### Title
Membership webhook trust escalation into `Shipit.github_teams` authorization when no `webhook_secret` is configured for an organization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`GithubApp#verify_webhook_signature` treats a missing per-organization `webhook_secret` as an automatic pass, so `WebhooksController#verify_signature` never actually authenticates the sender for that organization. `MembershipHandler#process` trusts the (now unauthenticated) `organization`/`member` fields from the webhook body to create/attach `Team` and `Membership` records, directly feeding `User#authorized?`, which checks membership in `Shipit.github_teams`. This mirrors the reported bug class: a binding ("this request is authenticated as coming from GitHub for organization X") is assumed everywhere downstream but is silently absent for one configuration path, letting an unprivileged caller cross a trust boundary it should not be able to cross.

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App config for the organization derived from the payload and asks it to verify the HMAC signature: [1](#0-0) [1](#0-0) 

The actual verification method short-circuits to `true` whenever no secret is configured for that organization: [2](#0-1) 

`webhook_secret` is explicitly documented as optional in the setup guide (`# nil` in `config/secrets.development.example.yml` and "Webhook secret (optional)" in `docs/setup.md`), so this is a supported deployment configuration, not a misconfiguration bug.

When this binding ("signature verified" == "sender is really GitHub") is absent, any unauthenticated caller can `POST /webhooks` with `X-Github-Event: membership` and a crafted JSON body. `MembershipHandler#process` unconditionally trusts the payload's `organization.login`, `team.*`, and `member.login` fields to find-or-create a `Team` and add/remove a `User` as its member: [3](#0-2) 

Team membership is exactly what `User#authorized?` checks to gate access to the whole application: [4](#0-3) 

So an attacker who knows (a) an organization name configured in Shipit with no `webhook_secret`, and (b) the `github_id` of a `Shipit.github_teams` team (discoverable via the public GitHub API), can forge a `membership` webhook naming their own GitHub login as the added member of that team, with zero credentials against Shipit itself.

### Impact Explanation
This is an authentication bypass on the webhook trust boundary that escalates into `Shipit.github_teams` authorization — explicitly one of the High-severity impacts called out for this engine (`escalation into Shipit.github_teams authorization`). Once the attacker's GitHub login is a member of an authorized `Team`, logging in via OmniAuth (`GithubAuthenticationController#callback` → `User.find_or_create_from_github`) grants them full access to protected Shipit UI/API endpoints gated by `force_github_authentication`/`current_user.authorized?`.

### Likelihood Explanation
The only precondition is that the operator has not set `github.webhook_secret` for the targeted organization — a state the project's own documentation presents as a normal, optional configuration, not a hardening requirement. No GitHub App private key, `ApiClient` token, or Shipit session is required to send the forged webhook; the attacker only needs the target organization's `login`, the target team's `github_id`/`slug`/`name`/`url` (all public via GitHub's API), and their own GitHub login.

### Recommendation
Do not treat an absent `webhook_secret` as implicit trust. Either require `webhook_secret` to be present for every configured organization (fail closed at boot/config-load time if missing), or, at minimum, refuse to process privilege-relevant events (`membership`, and anything that mutates `Team`/`Membership`) when no secret is configured, instead of silently returning `true` from `verify_webhook_signature`.

### Proof of Concept
1. Identify a Shipit deployment where organization `acme` has no `webhook_secret` configured (per the documented optional setting).
2. Look up (via GitHub's public API) the `github_id`, `slug`, `name`, `url` of a team referenced by `Shipit.github_teams` for `acme`.
3. `POST /webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "team": { "id": <team_github_id>, "name": "<team name>", "slug": "<team slug>", "url": "<team url>" },
  "organization": { "login": "acme" },
  "member": { "login": "attacker-github-login" }
}
```
No `X-Hub-Signature` header is required because `verify_webhook_signature` returns `true` when no secret is configured for `acme`.
4. `MembershipHandler#process` creates the `Team` (if needed) and adds `attacker-github-login` as a member.
5. The attacker signs in via GitHub OAuth; `User#authorized?` now returns `true` because their `User` record belongs to a `Team` in `Shipit.github_teams`, granting them access to the protected application.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
