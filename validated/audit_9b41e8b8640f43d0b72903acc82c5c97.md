Confirmed: `Repository#github_app` resolves the GitHub App/API client used for real GitHub-facing actions strictly from the stack's own stored `owner` field (`Shipit.github(organization: owner)`), which is completely independent of whichever organization's webhook secret validated the inbound request. This confirms the two sides of the broken binding never have to match.

### Title
Webhook organization used for signature verification is not bound to the repository the payload actually mutates - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App config (and thus which `webhook_secret`) to validate a delivery against using `repository_owner`, a value read from the JSON body itself (`params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`). Once the signature is accepted, `create` dispatches the same raw JSON to event handlers that resolve the target `Stack`/`Repository` from a *different* field of the same body, `payload.dig('repository', 'full_name')`. Nothing ties the two fields together, so a signature that is valid for organization A's webhook secret is accepted as authorization to act on any repository name embedded elsewhere in the payload, including one belonging to organization B.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb:24-49` does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where `repository_owner` (`app/controllers/shipit/webhooks_controller.rb:59-62`) reads `repository.owner.login` (falling back to `organization.login`) straight from the untrusted, attacker-supplied JSON body, and `Shipit.github(organization:)` (`lib/shipit.rb:170-181`) looks up a per-organization `webhook_secret` from `secrets.github`, per the multi-org config schema shown in `config/secrets.development.shopify.yml`.

Once this passes, `create` (`app/controllers/shipit/webhooks_controller.rb:10-15`) parses the same body and dispatches it to handlers such as `Shipit::Webhooks::Handlers::Handler#repository_name` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`), which is used by `PushHandler#process` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) to load `stacks` via `Repository.from_github_repo_name(repository_name)`. That lookup, and all the pull-request handlers (`opened_handler.rb`, `reopened_handler.rb`, `labeled_handler.rb`, etc.), key off `repository.full_name`, a sibling field of `repository.owner.login` in the exact same JSON body but never cross-checked against it.

The binding that should hold is:
`organization whose webhook_secret validated the signature == organization owning the repository the handler subsequently mutates`

The code only enforces "some field named `repository.owner.login` (or `organization.login`) matches a configured org with a working secret" — analogous to the reported bug's `||` check that only requires one side of a two-part invariant to hold. It never asserts that `repository.full_name`'s owner segment is the same organization. `Repository#github_app` (`app/models/shipit/repository.rb:100-102`) independently re-derives the GitHub App/API client from the stack's own stored `owner` column, confirming the two lookups are wired to entirely different, unrelated sources of truth.

### Impact Explanation
Any party holding a legitimately-configured `webhook_secret` for one organization in the multi-org `secrets.github` schema (each organization's own team creates and knows its own GitHub App's webhook secret, per `docs/setup.md`'s "Creating the GitHub App" instructions) can craft a signed payload whose `repository.owner.login` matches their own org (so verification succeeds) while `repository.full_name` names a stack/repository belonging to a *different* organization sharing the same Shipit instance. This lets the sender trigger `Stack#sync_github` on an unrelated repository, flip pull-request/review-stack archive/unarchive/provisioning state, or feed forged `status`/`check_suite` state into the target's commit statuses and deploy pipeline — an unauthorized deploy/state-mutation across a repository/organization boundary the sender has no authorization over on GitHub itself.

### Likelihood Explanation
Requires only knowledge of a valid `webhook_secret` for *any one* organization configured in the shared Shipit instance — not privileged access to the *target* organization, not a Shipit session, API token, or GitHub write access to the victim repo. In any deployment onboarding multiple organizations (the documented multi-org `secrets.github` schema), each onboarded org's own maintainers legitimately possess their own org's secret, making this a realistic, low-friction escalation path from "trusted for org A" to "can force actions against org B."

### Recommendation
After verifying the signature, re-derive the same organization/owner used for verification from `payload.dig('repository', 'full_name')` (or `organization.login`) and require them to be identical (`&&`, not independent lookups) before dispatching to handlers; reject the request with 422 if the owner segment of `repository.full_name` does not match `repository_owner`.

### Proof of Concept
1. Shipit is configured with `secrets.github` containing two orgs, `orgA` and `orgB`, each with its own `webhook_secret` (as in `config/secrets.development.shopify.yml`).
2. Attacker (a maintainer of `orgA`, knows `orgA`'s `webhook_secret`, has no access to `orgB`) builds a `push` payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(orgA_webhook_secret, body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "orgA")` → verification succeeds using `orgA`'s secret.
5. `create` dispatches to `PushHandler`, which resolves `Repository.from_github_repo_name("orgB/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on a stack the attacker never authenticated against.
