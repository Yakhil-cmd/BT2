### Title
Webhook signature verification org does not match the repository mutated by `ClosedHandler` - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/pull_request/closed_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects the GitHub App config/secret to validate a webhook's HMAC using `repository.owner.login` (or `organization.login`) read directly from the attacker-controlled JSON body, while `ClosedHandler` (and sibling PR handlers) locate the `Shipit::Repository` to mutate using the separate `repository.full_name` field. Nothing enforces that these two fields refer to the same org, so a valid signature computed with the attacker's own org secret can be paired with a victim's repo/stack reference.

### Finding Description
The broken binding, as an equality that must hold but is never checked: `repository_owner_used_for_signature (params.dig('repository','owner','login'))` == `owner_segment_of(params.repository.full_name)`.

Trace:
- `WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0)  and uses it to fetch the GitHub App config/secret via `Shipit.github(organization: repository_owner)`, then verifies `X-Hub-Signature` against the raw POST body with that org's `webhook_secret` [2](#0-1) .
- `Shipit.github` looks up the app config purely by the organization name passed in, with no other identity check [3](#0-2) .
- Once the signature is accepted, `WebhooksController#create` dispatches the parsed JSON to handlers for the event, unchanged [4](#0-3) .
- `ClosedHandler#repository` resolves the actual `Shipit::Repository` using `params.repository.full_name` (a completely separate JSON field from `repository.owner.login`) via `Shipit::Repository.from_github_repo_name` [5](#0-4) .
- `ClosedHandler#process` then calls `review_stack.archive!`, which is `ReviewStackAdapter#archive!`, performing real state mutation: `stack.deprovision` and `stack.archive!(user)` [6](#0-5) .
- The `ClosedHandler` params schema only requires `repository.full_name`; it does not require or validate `repository.owner.login` at all [7](#0-6) .

Exploit flow: an attacker who legitimately controls `attacker-org` and its Shipit-configured `webhook_secret` crafts a JSON body where `repository.owner.login` = `"attacker-org"` (so `verify_signature` fetches attacker-org's own secret and the HMAC over the raw body, computed by the attacker with their own secret, validates) but sets `repository.full_name` = `"victim-org/victim-repo"`, `action: "closed"`, and `number: N` matching a real open review stack. The signature check only ever inspects `repository.owner.login`/`organization.login`; it never inspects `repository.full_name`, so the mismatch goes undetected. The dispatched `ClosedHandler` then resolves and mutates the victim's real `Shipit::Repository`/`ReviewStack`.

Existing guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema, `GithubOrganizationUnknown` handling) all key off `repository.owner.login`/`organization.login`, none of which are cross-checked against `repository.full_name`'s owner segment, so the divergence is not prevented anywhere in this path.

### Impact Explanation
A single crafted, correctly-signed webhook lets an attacker who owns any Shipit-integrated GitHub org archive and deprovision another tenant's review stack for an arbitrary victim `owner/repo` and PR number, without any privilege on that victim repo. This is a cross-repository write reachable purely through webhook provenance confusion, matching the "payload for one repository mutating another's stack" Critical impact category. The same broken binding (owner-for-signature vs. owner-in-`full_name`) is shared by other PR handlers built the same way (`OpenedHandler`, `ReopenedHandler`, `LabeledHandler`, `UnlabeledHandler`, `AssignedHandler`, `EditedHandler`), so the blast radius extends beyond `ClosedHandler` to review-stack creation/unarchival/label-driven provisioning across arbitrary tenants sharing the same Shipit instance.

### Likelihood Explanation
Precondition is modest: the attacker only needs to own one GitHub org already onboarded to the target Shipit instance with a configured `webhook_secret` (a normal, legitimate Shipit tenant setup, not a privileged internal role). No access to the victim org, no Shipit session, and no other secrets are required. The attacker fully controls the JSON body and headers of the webhook POST, so crafting the mismatched `owner.login`/`full_name` payload and a valid HMAC is trivial and fully repeatable against any known victim `owner/repo` + PR number.

### Recommendation
In `WebhooksController#verify_signature` (or in the shared `Handler` base class), after resolving `repository_owner`, also derive the owner segment from `params.dig('repository', 'full_name')` (and from `params.dig('pull_request', 'base', 'repo', 'full_name')` where relevant) and reject the request (422) unless they match. Alternatively, have handlers pin the `Shipit::Repository` lookup to the org whose secret verified the request rather than trusting `full_name` alone.

### Proof of Concept
Minitest plan (controller test, no live GitHub):
1. In `test/controllers/webhooks_controller_test.rb`, configure two orgs in test secrets: `attacker-org` with a known `webhook_secret`, and `victim-org` (or reuse `shopify`) with an existing `Shipit::Repository` "victim-org/victim-repo" that has a provisioned, non-archived `Shipit::ReviewStack` for PR #2.
2. Build a `pull_request_closed` payload (based on `payload(:pull_request_closed)`) with:
   - `repository.owner.login` = `"attacker-org"`
   - `repository.full_name` = `"victim-org/victim-repo"`
   - `action` = `"closed"`, `number` = 2
3. Compute `signature = "sha1=" + OpenSSL::HMAC.hexdigest('sha1', attacker_org_webhook_secret, payload_json)`.
4. `request.headers['X-Github-Event'] = 'pull_request'`, `request.headers['X-Hub-Signature'] = signature`.
5. Assert: `post :create, body: payload_json, as: :json` returns `:ok` (signature accepted using attacker-org's secret).
6. Assert (the broken binding proof): `assert stack.reload.archived?` and `assert_equal 'deprovisioning', stack.provision_status` for the victim's `ReviewStack`, demonstrating that `repository_owner` used for signature verification (`"attacker-org"`) diverged from the owner segment of `repository.full_name` (`"victim-org"`), yet the victim stack was still mutated.
