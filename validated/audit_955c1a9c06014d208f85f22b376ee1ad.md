I examined the FRAME precompiles that most resemble the ERC4626 periphery pattern (a wrapper contract that pre-pulls funds via `transferFrom` before calling an inner function that itself debits the same account), including:

- `substrate/frame/asset-conversion/precompiles/src/lib.rs` — `add_liquidity`, `swap_exact_tokens_for_tokens`, `swap_tokens_for_exact_tokens`, `remove_liquidity`. Each of these calls `caller_account_id(env)` once and passes it straight into a single pallet dispatch (`MutateLiquidity::add_liquidity`, `Swap::swap_exact_tokens_for_tokens`, etc.), which performs exactly one `T::Assets::transfer(...)` internally. [1](#0-0) [2](#0-1) 
- `substrate/frame/assets/precompiles/src/lib.rs` — `transfer`/`transferFrom` each call `pallet_assets::do_transfer`/`do_transfer_approved` exactly once. [3](#0-2) 
- `substrate/frame/psm/src/lib.rs` — single transfer from caller to reserve account, then mint. [4](#0-3) 
- `substrate/frame/revive/src/exec.rs` `transfer`/`initial_transfer` — value transfer happens exactly once per call frame based on `frame.value_transferred`, and is skipped entirely for delegate calls to avoid double-transferring. [5](#0-4) [6](#0-5) 

None of these exhibit the reported bug-class pattern of a periphery layer pulling funds via one transfer and then invoking a second function that independently re-debits the same account for the same amount. Each entry point performs a single, atomic debit before crediting, and pallet-level functions (`do_add_liquidity`, `do_transfer`, `transfer_and_die`) are the sole place where funds move — there is no separate "periphery" pre-transfer step layered in front of an ERC4626-like vault call within this codebase. I found no reachable FRAME/XCM/precompile analog demonstrating a user being charged twice for a single logical operation.
