### Title
Missing `write`-mutex locking around main-chain stability advancement during catch-up allows concurrent corruption of stability bookkeeping - ([File: network.js / main_chain.js])

### Summary
`network.js`'s `tryToAdvanceStabilityPointForCatchupAATrigger()` drives an early, opportunistic main-chain-stability advance (`markMcIndexStable`/`stabilizeMci`) while a node is catching up, but it never takes the `"write"` mutex key that guards every other code path that mutates the same main-chain/stability state (`storage.assocStableUnits`, `storage.assocUnstableUnits`, `is_stable`/`main_chain_index` rows). This is the same bug class as CVE-2026-53049 (gfs2 calling log-flush routines that require exclusion, without holding the flush lock): a maintenance/background routine calls the shared "flush"-equivalent function while omitting the lock that the primary writer path always holds for it.

### Finding Description
The canonical path that mutates main-chain/stability state is `writer.saveJoint()`, which explicitly acquires the `"write"` mutex before doing anything to `storage.assocUnstableUnits`/`storage.assocStableUnits` or calling `main_chain.updateMainChain()`/`main_chain.advanceMcStability()`: [1](#0-0) 

That lock is held across the entire mutation, including chained stabilization of further MCIs: [2](#0-1) 

Likewise, the purge path explicitly nests `"write"` inside `"handleJoint"` before touching the same unstable-unit cache: [3](#0-2) 

However, `network.js`'s catch-up helper `tryToAdvanceStabilityPointForCatchupAATrigger()` opens its own DB connection and drives stability advancement using only the `"handleJoint"` lock obtained deep inside `main_chain.determineIfStableInLaterUnitsAndUpdateStableMcFlag()` — it never requests `"write"`: [4](#0-3) 

Inside `main_chain.js`, the actual mutation of `main_chain_index`/`is_stable` and of `storage.assocStableUnits`/`storage.assocUnstableUnits` is performed by `stabilizeMci()`/`markMcIndexStable()`, guarded only by the `"handleJoint"` key acquired here: [5](#0-4) [6](#0-5) [7](#0-6) 

Because `"write"` and `"handleJoint"` are independent mutex keys in `mutex.js` (a lock on one key does not block a lock on a different key), any writer-side code path that mutates the same in-memory caches and DB rows while holding only `"write"` (but not `"handleJoint"`) can run fully concurrently with this catch-up stability-advance path. Both paths update the same non-atomic in-memory `storage.assocUnstableUnits`/`storage.assocStableUnits` structures and the same `units.is_stable`/`main_chain_index` columns using separately opened SQL transactions, so interleaved execution can leave the caches and DB in an inconsistent combination (e.g., a unit removed from `assocUnstableUnits` by one path while the other still expects it there, or double invocation of `markMcIndexStable`/AA-trigger insertion for the same MCI), exactly mirroring the gfs2 pattern of "log flush functions... require exclusion against concurrent transactions" being invoked without the lock that other callers rely on.

### Impact Explanation
`markMcIndexStable` is the single authority that flips `is_stable`, finalizes `sequence` (`good`/`final-bad`), and enqueues AA triggers (`aa_triggers` table) for an MCI; `storage.assocStableUnits`/`assocUnstableUnits` back every downstream validation and payment/double-spend decision. A race here can cause a node to compute or record stability/sequence differently from the rest of the network, or to duplicate/omit AA-trigger scheduling for a stabilized MCI — i.e., node disagreement on validity/stability of a supposedly-stable unit/output, and potential double execution or loss of AA triggers (fund loss/duplication in AAs).

### Likelihood Explanation
This path is only reachable while `bCatchingUp` is true and a "possible AA" transient validation error occurs for an attacker-controlled unit during catch-up, which an unprivileged unit poster can trigger deterministically by crafting a unit that references an AA whose predecessor trigger has not yet been executed. The race window depends on interleaving with a concurrent write, which is timing-dependent but realistically achievable by flooding the node with units during catch-up (a normal operational scenario, not requiring a malicious peer/node).

### Recommendation
Make `tryToAdvanceStabilityPointForCatchupAATrigger()` (and the `stabilizeMci`/`markMcIndexStable` path it triggers) acquire the same `"write"` mutex key that `writer.saveJoint()` uses before mutating `storage.assocStableUnits`/`assocUnstableUnits` or the `units` table, in addition to (or instead of) `"handleJoint"`, so that all mutators of main-chain stability state serialize on one consistent lock, mirroring the upstream gfs2 fix of adding the missing `sd_log_flush_lock` acquisition around the flush routines.

### Proof of Concept
1. Start a full node in catch-up mode (`bCatchingUp = true`).
2. Post a unit referencing an AA whose predecessor trigger MCI is not yet stabilized so `validation.validate` returns `ifTransientError("possible AA")`, causing `network.js` to call `tryToAdvanceStabilityPointForCatchupAATrigger(objJoint)`. [8](#0-7) 
3. Concurrently drive normal unit ingestion so `writer.saveJoint()` is executing its `"write"`-locked `main_chain.updateMainChain`/`advanceMcStability` section for a different unit at the same MCI boundary. [9](#0-8) 
4. Because the two paths use disjoint mutex keys, both can concurrently call into `markMcIndexStable`/mutate `storage.assocStableUnits`/`assocUnstableUnits` for overlapping MCIs, producing divergent `is_stable`/`sequence` state or duplicated `aa_triggers` rows between this node and peers that did not race.

	const unit = objUnit.unit;

		return;

		const props = storage.assocUnstableUnits[parent_unit];
		return props && props.is_on_main_chain && !props.is_stable;
	});
	if (!parent_unit)
		return;

	const conn = await db.takeConnectionFromPool();

	console.log(`AA parent ${parent_unit} stable in free units ${arrFreeUnits.join(', ')}? ${bStable}`);
	await conn.query("COMMIT");
	conn.release();
}

async function stabilizeMci(mci) {
	const conn = await db.takeConnectionFromPool();
	await conn.query("BEGIN");
	const batch = kvstore.batch();
	const count_aa_triggers = await markMcIndexStable(conn, batch, mci);
	await util.promisify(batch.write.bind(batch))({ sync: true });
	await conn.query("COMMIT");
	conn.release();
	if (count_aa_triggers > 0) {
		console.log(`executing ${count_aa_triggers} AA triggers after stabilizing MCI ${mci}`);
		// every trigger takes its own db connection
		const aa_composer = require("./aa_composer.js");
		await aa_composer.handleAATriggers();
	}
	if (mci >= constants.v4UpgradeMci) {
		console.log(`updating tps fees after stabilizing MCI ${mci}`);
		// get a new connection to write tps fees
		const conn = await db.takeConnectionFromPool();
		await conn.query("BEGIN");
		await storage.updateTpsFees(conn, [mci]);
		await conn.query("COMMIT");
		conn.release();
	}
}
