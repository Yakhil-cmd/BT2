### Title
Webhook signature verification is keyed to an attacker-controlled `organization`/`repository.owner.login` field that is decoupled from the `repository.full_name` actually acted upon by event handlers, allowing cross-repository/cross-organization forged webhooks - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects *which* GitHub App configuration (and thus which `webhook_secret`) to validate a webhook against using `repository_owner`, a value parsed straight out of the unauthenticated JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`). Every webhook `Handler`, however, determines the actual `Repository`/`Stack` to mutate from a completely different, independently-controlled field in the same payload: `payload.dig('repository','full_name')`. Because the field used to pick the verifying organization is never cross-checked against the field used to select the repository being written to, the equality "organization that authenticated == repository that is written" is not enforced anywhere in the engine.

### Finding Description
`verify_signature` in [1](#0-0)  computes:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where `repository_owner` is derived from the raw, unverified request body: [2](#0-1) .

`Shipit.github(organization:)` looks up a per-organization config (multi-org support is a documented feature, see `github_app_config` and `TOP_LEVEL_GH_KEYS`) at [3](#0-2) , and `GithubApp#verify_webhook_signature` at [4](#0-3)  returns `true` unconditionally whenever that particular organization has no `webhook_secret` configured (`webhook_secret` is documented as optional, see `docs/setup.md`).

Once `verify_signature` passes (either because a valid signature for that org's own secret was supplied, or because that org has no secret at all), `create` dispatches the *entire, unmodified* payload to the registered handlers: [5](#0-4) . Every handler resolves the target repository independently, from `payload.dig('repository','full_name')`, with no reference back to `repository_owner`: [6](#0-5) . This same pattern repeats in `PushHandler` [7](#0-6) , the `PullRequest` handlers (`OpenedHandler`, `LabeledHandler`, `ReopenedHandler`, etc.), and `MembershipHandler` [8](#0-7) , which additionally trusts `params.organization.login` to attach a `Team` to whatever organization string is present in the payload, independent of the field used for signature routing.

The net effect: the value that determines *whose secret authenticates the request* (`repository.owner.login` / `organization.login`) is never required to equal the value that determines *which repository/team/stack is mutated* (`repository.full_name` / `organization.login` used inside handlers). Nothing in `WebhooksController` or `Handler` enforces that binding.

### Impact Explanation
In a multi-organization Shipit deployment (a supported, documented configuration - `config/secrets.development.example.yml` shows multiple `github:` orgs each with independently optional `webhook_secret`), if even one configured organization has no `webhook_secret` set, an outside attacker who knows only that organization's login name (public information) can submit a completely unauthenticated POST to `/webhooks` that trivially passes `verify_signature` (since `verify_webhook_signature` short-circuits to `true`), while embedding an arbitrary `repository.full_name`/`organization.login` belonging to a *different*, properly-secured organization managed by the same Shipit instance. Downstream handlers act on stacks/teams/repositories under that other organization based solely on the payload content, e.g.:
- `PushHandler` can trigger `GithubSyncJob`/resyncs on stacks that belong to the unrelated organization.
- `MembershipHandler` can create/attach `Team` and `Membership` records (`Team.find_or_create_by!`, `team.add_member`) under a forged `organization.login`, which can influence `Shipit.github_teams` mapping and `User#authorized?` at [9](#0-8)  and [10](#0-9) , i.e. escalation into `Shipit.github_teams` authorization gating access to the whole application.
- `PullRequest` handlers can archive/unarchive review stacks belonging to the unrelated repository.

This matches the "escalation into `Shipit.github_teams` authorization" and "cross-repository writes" High/Critical impact classes, achieved with no `webhook_secret`, no `ApiClient` token, and no session - purely by exploiting the decoupling between the authenticating field and the acted-upon field.

### Likelihood Explanation
Medium. It requires: (1) a multi-org Shipit deployment (a documented, supported configuration), and (2) at least one configured organization having no `webhook_secret` (explicitly documented as optional, and a realistic scenario for test/staging orgs or orgs added without immediately setting a secret). Given those common preconditions, exploitation requires nothing more than a single crafted HTTP POST with a known, public organization login and an arbitrary target `repository.full_name`/`organization.login` - no credentials of any kind.

### Recommendation
Bind the field used to select the verifying GitHub App/secret to the field used to resolve the target repository/organization inside every handler. Concretely:
- In `WebhooksController#verify_signature`, additionally assert that `payload.dig('repository','full_name')`'s owner (and any `organization.login` used later) equals `repository_owner`, rejecting the request otherwise.
- In `Handler#repository_name` and `MembershipHandler#find_or_create_team!`, validate that the organization portion of the resolved repository/org matches the organization whose secret was used to authenticate the webhook, rather than trusting it implicitly.
- Consider failing closed (rejecting, not accepting) webhooks for organizations configured without a `webhook_secret` when the deployment has more than one configured organization.

### Proof of Concept
Preconditions: Shipit is configured with multiple GitHub organizations, e.g. `secrets.github = { "trusted-org" => { webhook_secret: "s3cr3t", ... }, "no-secret-org" => { webhook_secret: nil, ... } }`.

1. Attacker sends:
```
POST /webhooks
X-Github-Event: membership
Content-Type: application/json

{
  "action": "added",
  "team": { "id": 999, "name": "evil", "slug": "evil", "url": "https://x" },
  "organization": { "login": "trusted-org" },
  "member": { "login": "attacker-controlled-user" },
  "repository": { "owner": { "login": "no-secret-org" }, "full_name": "no-secret-org/whatever" }
}
```
2. `repository_owner` resolves to `"no-secret-org"` (from `repository.owner.login`), so `Shipit.github(organization: "no-secret-org")` is used for signature verification.
3. Because `no-secret-org` has no `webhook_secret`, `verify_webhook_signature` returns `true` unconditionally - no valid `X-Hub-Signature` is required at all.
4. `MembershipHandler` then processes the payload using `params.organization.login == "trusted-org"`, creating/joining a `Team` scoped to `trusted-org` and adding `attacker-controlled-user` to it, with the request never having been authenticated by `trusted-org`'s secret at all.   def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

module Shipit
  module Webhooks
    module Handlers
      class MembershipHandler < Handler
        params do
          requires :action, String
          requires :team do
            requires :id, Integer
            requires :name, String
            requires :slug, String
            requires :url, String
          end
          requires :organization do
            requires :login, String
          end
          requires :member do
            requires :login, String
          end
        end
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
      end
    end
  end
end
