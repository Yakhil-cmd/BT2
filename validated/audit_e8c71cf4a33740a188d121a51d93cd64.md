### Title
`InitializeWithPermission.creator` accepted as an unconstrained, non-signer account, allowing permanent freezing of pool creator fees - ([File: programs/cp-swap/src/instructions/initialize_with_permission.rs])

### Summary
`initialize_with_permission` accepts a `creator` account that is neither required to be a signer nor constrained to equal the transaction `payer`, and this value is stored on-chain as `pool_state.pool_creator`, the sole address later permitted to withdraw accumulated creator fees.

### Finding Description
In `InitializeWithPermission`, the `creator` field is declared as a bare `UncheckedAccount` with no `Signer` requirement and no `address =` or other ownership constraint tying it to `payer` or any authenticated party: [1](#0-0) 

By contrast, `Initialize`'s `creator` account is a `Signer<'info>`, so it is guaranteed to be a real, key-holding party: [2](#0-1) 

This `creator` value flows into `pool_state.initialize(...)`, which in the sibling `initialize.rs` path persists it as the pool's `pool_creator` field: [3](#0-2) 

That stored `pool_creator` is later used as the sole authorization gate for withdrawing accumulated creator fees: [4](#0-3) 

Because `InitializeWithPermission` never validates that the supplied `creator` account corresponds to a controllable keypair (no signer check, no equality check against `payer` or any other authenticated signer), the `payer` invoking this instruction can pass an arbitrary pubkey — including one with no known private key (e.g. a PDA that will never sign, or an address never intended to hold funds) — as the `creator`. This exactly parallels the reported bug class: an admin/authority-role parameter (`pool_creator`, which gates a privileged fee-collection feature) is accepted without any validity check, so the corresponding "admin feature" (creator-fee collection) can end up permanently non-functional.

### Impact Explanation
All creator fees (`creator_fees_token_0` / `creator_fees_token_1`) that accrue to that pool over its lifetime become permanently unrecoverable, since `collect_creator_fee` strictly requires a signer matching `pool_state.pool_creator`, and no instruction exists to change `pool_creator` after pool creation. This is a permanent freezing of protocol/creator fee funds tied to that pool.

### Likelihood Explanation
`initialize_with_permission` is reachable by any account holding the `Permission` PDA (a normal, non-privileged "permissioned pool creator" role explicitly in scope), and the flaw is triggered by a single crafted transaction supplying an uncontrolled `creator` pubkey — no special conditions or races are required, only the choice of account passed into the instruction.

### Recommendation
Constrain `creator` in `InitializeWithPermission` the same way as in `Initialize` — require it to be a `Signer`, or at minimum add an explicit `address = payer` (or otherwise cryptographically verified) constraint — so `pool_creator` can never be set to an unwitnessed/unauthenticated address.

### Proof of Concept
1. Attacker (or any account holding a valid `Permission` PDA) calls `initialize_with_permission`, supplying `payer` as their own signer but setting the `creator` account field to an arbitrary pubkey they do not control (e.g., a random keypair's public key with no known private key, or an unrelated PDA of another program).
2. The instruction succeeds because `creator` has no signer or ownership constraint: [1](#0-0) 
3. `pool_state.pool_creator` is permanently set to that address.
4. Over time, swaps accrue `creator_fees_token_0`/`creator_fees_token_1` in the pool state.
5. Because `collect_creator_fee` requires `creator: Signer` with `address = pool_state.load()?.pool_creator` [4](#0-3) , and no one holds the private key for the stored `pool_creator`, the accumulated creator fees can never be withdrawn — permanently frozen in the pool vaults.
