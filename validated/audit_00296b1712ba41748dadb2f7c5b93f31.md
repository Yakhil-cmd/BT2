### Title
Unguarded `onERC721Received` / `onERC20Received` Callbacks Allow Fraudulent Cross-Chain Transfer Requests Without Asset Deposit — (`contracts/service_chain/bridge/BridgeTransferERC721.sol`, `contracts/service_chain/bridge/BridgeTransferERC20.sol`)

---

### Summary

`BridgeTransferERC721.onERC721Received()` and `BridgeTransferERC20.onERC20Received()` are `public` functions that emit a cross-chain transfer request event and increment `requestNonce` based solely on `msg.sender` being a registered token address. Neither function verifies that the bridge contract actually received the corresponding asset before emitting the request. A registered token contract that calls the bridge callback without first executing the asset transfer — whether due to a bug in the token contract or deliberate malice — causes bridge operators to process a fraudulent transfer on the counterpart chain, minting or releasing assets that were never deposited.

---

### Finding Description

The 1-step deposit flow is implemented in `ERC721ServiceChain.requestValueTransfer`:

```solidity
// contracts/testing/sc_erc721/ERC721ServiceChain.sol:43-47
function requestValueTransfer(uint256 _uid, address _to, bytes calldata _extraData) external {
    transferFrom(msg.sender, bridge, _uid);
    IERC721BridgeReceiver(bridge).onERC721Received(msg.sender, _uid, _to, _extraData);
}
```

The token contract is expected to transfer the asset first, then call the bridge callback. The bridge's callback is:

```solidity
// contracts/service_chain/bridge/BridgeTransferERC721.sol:109-118
function onERC721Received(
    address _from,
    uint256 _tokenId,
    address _to,
    bytes memory _extraData
)
    public
{
    _requestERC721Transfer(msg.sender, _from, _to, _tokenId, _extraData);
}
```

The only guard inside `_requestERC721Transfer` is:

```solidity
// contracts/service_chain/bridge/BridgeTransferERC721.sol:82-83
onlyRegisteredToken(_tokenAddress)
onlyUnlockedToken(_tokenAddress)
```

which checks:

```solidity
// contracts/service_chain/bridge/BridgeTokens.sol:32-35
modifier onlyRegisteredToken(address _token) {
    require(registeredTokens[_token] != address(0), "not allowed token");
    _;
}
```

There is **no check** that the bridge's actual ERC721 balance for `_tokenId` increased, and no check that `ownerOf(_tokenId) == address(this)` after the call. In `modeMintBurn = false` (lock/unlock) mode, `_requestERC721Transfer` simply emits `RequestValueTransferEncoded` and increments `requestNonce` without any custody verification:

```solidity
// contracts/service_chain/bridge/BridgeTransferERC721.sol:93-105
emit RequestValueTransferEncoded(
    TokenType.ERC721,
    _from,
    _to,
    _tokenAddress,
    _tokenId,
    requestNonce,
    0,
    _extraData,
    2,
    abi.encode(string(uri))
);
requestNonce++;
```

The identical pattern exists for ERC20:

```solidity
// contracts/service_chain/bridge/BridgeTransferERC20.sol:111-121
function onERC20Received(
    address _from,
    address _to,
    uint256 _value,
    uint256 _feeLimit,
    bytes memory _extraData
)
    public
{
    _requestERC20Transfer(msg.sender, _from, _to, _value, _feeLimit, _extraData);
}
```

In `modeMintBurn = false` mode with `_feeLimit = 0`, `_requestERC20Transfer` emits `RequestValueTransfer` and increments `requestNonce` without verifying the bridge received any tokens.

---

### Impact Explanation

Bridge operators watch for `RequestValueTransferEncoded` / `RequestValueTransfer` events on the source chain and call `handleERC721Transfer` / `handleERC20Transfer` on the counterpart bridge:

```solidity
// contracts/service_chain/bridge/BridgeTransferERC721.sol:66-70
if (modeMintBurn) {
    require(ERC721MetadataMintable(_tokenAddress).mintWithTokenURI(_to, _tokenId, _tokenURI), "mint failed");
} else {
    IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId);
}
```

A fraudulent `RequestValueTransferEncoded` event causes the counterpart bridge to either **mint a new NFT** (mintBurn mode) or **release a locked NFT** (lock/unlock mode) to the attacker's chosen `_to` address — with no corresponding deposit on the source chain. This is an unauthorized mint or unauthorized transfer of a bridged asset.

For ERC20, the counterpart bridge mints or releases tokens of value `_value` to `_to` without any deposit.

---

### Likelihood Explanation

The trigger requires `msg.sender` to be a registered token contract address. Token registration is `onlyOwner`. However:

- Any registered token contract whose code contains a function that calls `bridge.onERC721Received(...)` without first executing `transferFrom` is exploitable by any user of that token contract.
- A token contract deployer who later turns adversarial can add such a function via an upgradeable proxy pattern.
- The reference implementation (`ERC721ServiceChain`) is safe, but the bridge imposes no constraint on what code a registered token contract runs — it only checks that the address is registered.
- The `onERC721Received` and `onERC20Received` functions are `public` with no `msg.sender` whitelist beyond the registered-token check, making the attack surface as wide as the set of registered token contracts and their callers.

---

### Recommendation

Add a custody check inside `onERC721Received` before processing the request. Verify that the bridge is the current owner of the claimed token ID:

```solidity
function onERC721Received(
    address _from,
    uint256 _tokenId,
    address _to,
    bytes memory _extraData
)
    public
{
    require(
        IERC721(msg.sender).ownerOf(_tokenId) == address(this),
        "Bridge: NFT not received"
    );
    _requestERC721Transfer(msg.sender, _from, _to, _tokenId, _extraData);
}
```

For ERC20, verify the bridge balance increased by at least `_value + _feeLimit` compared to a pre-call snapshot, or use a balance-delta pattern. Alternatively, restrict `onERC721Received` / `onERC20Received` to only be callable from within a `safeTransferFrom` / `transferFrom` execution context by checking that the token contract is the immediate caller and that the transfer has already settled.

---

### Proof of Concept

**Setup:** Bridge deployed in `modeMintBurn = false` (lock/unlock) mode. `MaliciousNFT` is registered as a token by the bridge owner. `MaliciousNFT` contains:

```solidity
contract MaliciousNFT is ERC721 {
    address public bridge;

    // Called by attacker — no transferFrom, no actual deposit
    function fakeDeposit(uint256 tokenId, address victim) external {
        // Does NOT transfer any NFT to bridge
        IBridgeERC721(bridge).onERC721Received(
            msg.sender,   // _from (attacker)
            tokenId,      // _tokenId (any ID held by bridge on counterpart)
            victim,       // _to (attacker's counterpart address)
            ""
        );
    }
}
```

**Steps:**
1. Attacker calls `MaliciousNFT.fakeDeposit(tokenId, attackerCounterpartAddr)`.
2. `MaliciousNFT` calls `bridge.onERC721Received(attacker, tokenId, attackerCounterpartAddr, "")`.
3. `msg.sender == address(MaliciousNFT)` passes `onlyRegisteredToken`.
4. `_requestERC721Transfer` emits `RequestValueTransferEncoded` with `requestNonce = N` and increments `requestNonce` to `N+1`. No NFT is transferred to the bridge.
5. Bridge operators observe the event and call `handleERC721Transfer` on the counterpart bridge.
6. Counterpart bridge mints (mintBurn) or releases (lock/unlock) `tokenId` to `attackerCounterpartAddr`.
7. Attacker receives an NFT on the counterpart chain without depositing anything on the source chain.

**Corrupted value:** `requestNonce` is incremented for a non-existent deposit; the counterpart bridge's NFT custody or mint authority is consumed for a fraudulent request.
