Found it. This is a case where the entity used to select which organization's webhook secret verifies a signature is decoupled from the entity that the event handler actually mutates — exactly the "organization authenticated versus repository written" binding named in the rules.

### Title
Webhook Signature Verified Against Payload's `repository.owner.login`, But Handlers Act on an Independent `repository.full_name` — Cross-Organization Event Injection - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification from `params.dig('repository','owner','login')` (falling back to `organization.login`), but every event handler (`Handler#repository_name`, used by `PushHandler`, `StatusHandler`, `CheckSuiteHandler`) resolves the actual target `Repository`/`Stack` from a separate, unchecked field, `payload.dig('repository', 'full_name')`. These two fields are never cross-validated against each other.

### Finding Description
`verify_signature` computes the signing organization from one payload field: [1](#0-0) [2](#0-1) 

Signature verification itself trivially succeeds whenever the resolved organization has no `webhook_secret` configured: [3](#0-2) 

This is a documented, common configuration state — the sample config ships with `webhook_secret: # nil` for every org: [4](#0-3) 

Meanwhile, once verification passes and `create` dispatches to handlers, the actual repository/stack that gets mutated is resolved from a *different, independently-controlled* field of the same attacker-supplied JSON body: [5](#0-4) 
used by `PushHandler#process` (triggers `stack.sync_github`) and `StatusHandler#process` (writes commit statuses): [6](#0-5) [7](#0-6) 

The equality that should hold but doesn't:
`organization authenticated by verify_signature (repository.owner.login)` == `organization/repository actually written by the handler (repository.full_name)`.

Because nothing enforces this equality, an attacker who can produce (or benefit from) a valid/trivial signature for **any one** configured organization — most easily one whose `webhook_secret` is blank/unset, satisfying `return true unless webhook_secret` — can set `repository.owner.login` to that unsecured org while setting `repository.full_name` to point at a completely unrelated repository/stack managed under a different, properly-secured organization. The push/status/check_suite handlers will happily act on that unrelated stack (e.g., forcing `sync_github`, injecting fabricated commit statuses that influence deploy gating), with no code path checking that the two identifiers refer to the same organization.

### Impact Explanation
This crosses a cross-repository/cross-organization boundary using only an unauthenticated (or weakly authenticated) webhook request, matching the "cross-repository writes" High/Critical impact criterion. Concretely: injecting fabricated `status` events can flip a commit's CI/deployable state (`create_status_from_github!`) for a stack the attacker does not control, which can unlock or block deploys on that stack; injecting `push` events can force `sync_github` on stacks under a different organization than the one whose (absent) secret was checked.

### Likelihood Explanation
Requires only that at least one organization configured in `Shipit.github` has no `webhook_secret` set (explicitly supported/shown in the shipped sample config) or that the attacker otherwise controls a valid signature for any one org — no repository write access, no session, and no `ApiClient` token are needed. The mismatch is triggered purely by crafting divergent `repository.owner.login` vs `repository.full_name` values in the JSON body.

### Recommendation
After signature verification, require that the organization used to select the verifying `github_app` matches the owner/org of `repository.full_name` (or any other identifier a handler will use to resolve `Repository`/`Stack`) before dispatching to handlers, and reject the request otherwise. Alternatively, resolve the target repository/stack first, derive the verifying organization from that same resolved repository, and verify strictly against it — never allow two independent payload fields to select "who verifies" versus "what gets written."

### Proof of Concept
1. Configure two orgs in `Shipit.github`: `org-a` (no `webhook_secret`) and `org-b` (a repo/stack tracked under it, with a strong secret).
2. POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/tracked-repo" },
  "sha": "<commit sha belonging to org-b/tracked-repo stack>",
  "state": "success",
  "branches": [{"name": "main"}]
}
```
No/garbage `X-Hub-Signature` header, or any value — `verify_signature` resolves `Shipit.github(organization: "org-a")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally.
3. `create` dispatches to `StatusHandler`, which resolves target commits via `Commit.where(sha: params.sha)` independent of `org-a`, and writes a fabricated `success` status for the `org-b`-owned commit, potentially unblocking a deploy gated on CI status — despite the request never being authenticated for `org-b`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
