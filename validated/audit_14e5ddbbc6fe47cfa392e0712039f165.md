### Title
Cross-organization membership webhook forgery removes a user's authorization Membership - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`MembershipHandler#process` looks up the `Team` solely by `params.team.id` (GitHub team id) without verifying that the requesting organization (the org whose `webhook_secret` was used in `verify_signature`) actually owns that team. An attacker who controls any org onboarded to the same multi-tenant Shipit instance can sign a `membership`/`removed` webhook with their own `webhook_secret` but claim an arbitrary `team.id` that matches a different org's team listed in `Shipit.github_teams`, causing Shipit to delete a legitimate operator's `Membership` row.

### Finding Description
The intended binding is: `organization whose webhook_secret validated the request signature == organization whose team membership is mutated`. Tracing the code shows this binding is never enforced.

`WebhooksController#verify_signature` resolves the GitHub App config using `repository_owner`, which falls back to `params.dig('organization', 'login')` [1](#0-0) . For a `membership` event there is no `repository` key, so this is exactly the attacker-supplied `organization.login`, i.e., the attacker's own org, and the HMAC is verified using the attacker's own `webhook_secret` — this step succeeds legitimately for the attacker's own org, not for the victim org.

`MembershipHandler#find_or_create_team!` then does:
```ruby
Team.find_or_create_by!(github_id: params.team.id) do |team|
  team.github_team = params.team
  team.organization = params.organization.login
end
``` [2](#0-1) 
This lookup is keyed only on `github_id`, with no scoping to the organization that was actually authenticated. If a `Team` row with that `github_id` already exists (e.g., a real Shipit-configured team from `Shipit.github_teams`), `find_or_create_by!` returns that existing row regardless of which org authenticated the request.

`process` then executes:
```ruby
case params.action
when 'removed'
  team.members.delete(member)
``` [3](#0-2) 
`member` is resolved via `User.find_or_create_by_login!(params.member.login)` [4](#0-3) , which is looked up purely by GitHub `login` — again attacker-controlled, arbitrary text in the payload with no cross-check that this user is actually a member of the attacker's org. Because `params.team.id` and `params.member.login` are just JSON fields chosen by whoever crafts the payload (validated only for type/presence by `ExplicitParameters`, not by any GitHub-side truth), an attacker can name any real Shipit-known `github_id` and any real operator login.

This directly deletes the `Membership` row backing `User#authorized?`, which computes:
```ruby
@authorized ||= Shipit.github_teams.empty? || teams.where(id: Shipit.github_teams.map(&:id)).exists?
``` [5](#0-4) 
Removing the `Membership` can flip a currently-authorized operator to unauthorized without any actual change on GitHub.

None of the existing guards catch this: `verify_signature` only proves "this payload was sent using organization X's secret," not "team.id belongs to organization X" [6](#0-5) ; `drop_unhandled_event` and `check_if_ping` are unrelated dispatch guards [7](#0-6) ; the `ExplicitParameters` schema in `MembershipHandler` only validates types/presence, not ownership [8](#0-7) ; and `Team` has no validation tying `github_id` to `organization` at write time [9](#0-8) .

### Impact Explanation
A single forged webhook lets a tenant with any legitimately-configured `webhook_secret` on the shared Shipit instance deauthorize an arbitrary operator of a different, unrelated tenant/org by deleting their `Membership` to a `Shipit.github_teams` team, without ever compromising GitHub or Shipit secrets belonging to the victim org. This is a cross-tenant write: a payload signed for org A mutates state (`Membership`) that governs authorization for org B's `Shipit.github_teams`. It is repeatable against any operator whose login and team `github_id` the attacker can discover (both are public/observable information — GitHub logins and numeric team IDs are not secret). This matches the "escalation into `Shipit.github_teams` authorization" / cross-tenant mutation category described as in-scope Critical/High impact.

### Likelihood Explanation
Preconditions: the attacker must operate/control at least one organization that is itself validly onboarded to the shared Shipit instance (has its own `webhook_secret` configured under `Shipit.github`), which is a normal, low-privilege state for any tenant on a multi-tenant Shipit deployment. Beyond that, the attack requires only knowledge of (a) the victim's `Shipit::Team#github_id` (derived from a real GitHub team id, discoverable via GitHub's team API/URLs) and (b) the victim operator's GitHub login (public). No GitHub secrets, session, or API client token of the victim org are needed. The attacker crafts and POSTs a JSON body to `/webhooks` with the `X-Github-Event: membership` header and a valid `X-Hub-Signature` computed with their own `webhook_secret`. This is inexpensive and repeatable.

### Recommendation
Scope the `Team` lookup and the delete/add operation to the organization that authenticated the request. Concretely:
- In `MembershipHandler#find_or_create_team!`, look up by both `github_id` AND `organization: params.organization.login` (or better, pass down the org that `verify_signature` actually resolved from `repository_owner`, and compare it against `params.organization.login`/`params.team`'s real owning org before mutating).
- Reject the event (204/422, no-op) if the team found by `github_id` belongs to a different `organization` than the one that authenticated the webhook.
- Consider validating team ownership against GitHub (e.g., refetch team info via the authenticated org's API) rather than trusting payload fields for identity-establishing lookups.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` style, using existing fixtures):
1. Seed two orgs in `Shipit.github` config-equivalent test doubles: `victim-org` (with its real webhook_secret) and `attacker-org` (with attacker's own webhook_secret), both resolvable via `Shipit.github(organization:)`.
2. Seed `Shipit::Team` with `github_id: 999`, `organization: 'victim-org'`, included in `Shipit.github_teams`.
3. Seed `Shipit::User` `login: 'victim-operator'` and `Shipit::Membership` linking that user to the seeded team (asserting `victim_operator.authorized?` is `true` before the request, i.e. `victim_team.members.include?(victim_operator) == true`).
4. Build a `membership`/`removed` JSON payload with `organization.login = 'attacker-org'`, `team.id = 999`, `team.name/slug/url` arbitrary, `member.login = 'victim-operator'`.
5. Sign the raw JSON with `attacker-org`'s `webhook_secret` and POST to `/webhooks` with headers `X-Github-Event: membership` and correct `X-Hub-Signature`.
6. Assert response is `200 OK` (not `422`), and assert `victim_team.members.reload.include?(victim_operator) == false` and `victim_operator.reload.authorized?` becomes `false` — proving the attacker-signed payload (bound to `attacker-org`) mutated `victim-org`'s team membership, i.e. the equality "authenticating org == mutated org" is violated (`attacker-org` != `victim-org` but the write succeeded).

# frozen_string_literal: true

module Shipit
  class Team < Record
    REQUIRED_HOOKS = %i[membership].freeze

    has_many :memberships
    has_many :members, class_name: :User, through: :memberships, source: :user

    has_many :github_hooks,
             -> { where(event: REQUIRED_HOOKS) },
             foreign_key: :organization,
             primary_key: :organization,
             class_name: 'GithubHook::Organization',
             inverse_of: false

    class << self
      def find_or_create_by_handle(handle)
        organization, slug = handle.split('/').map(&:downcase)
        find_by(organization:, slug:) || fetch_and_create_from_github(organization, slug)
      end

      def fetch_and_create_from_github(organization, slug)
        return unless github_team = find_team_on_github(organization, slug)

        create!(github_team:, organization:)
      end

      def find_team_on_github(organization, slug)
        gh_api = Shipit.github(organization:).api
        teams = Shipit::OctokitIterator.new(github_api: gh_api) { gh_api.org_teams(organization, per_page: 100) }
        teams.find { |t| t.slug == slug }
      rescue Octokit::NotFound
      end
    end

    def handle
      "#{organization}/#{slug}"
    end

    def add_member(member)
      members.append(member) unless members.include?(member)
    end

    def refresh_members!
      github_api = Shipit.github(organization:).api
      github_members = Shipit::OctokitIterator.new(github_api.get(api_url).rels[:members])
      members = github_members.map { |u| User.find_or_create_from_github(u) }
      self.members = members
      save!
    end

    def github_team=(github_team)
      self.name = github_team.name
      self.slug = github_team.slug
      self.api_url = github_team.url
      self.github_id = github_team.id
    end
  end
