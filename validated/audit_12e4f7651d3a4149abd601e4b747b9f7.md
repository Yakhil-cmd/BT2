### Title
Cross-organization CI status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and thus which HMAC webhook secret) to validate a webhook against based solely on the `repository.owner.login` field of the payload, but the handler that processes `status` events resolves the target `Commit` purely by SHA, with no re-validation that the SHA belongs to a repository owned by the authenticated organization.

### Finding Description
`WebhooksController#verify_signature` picks the `github_app` used to verify the HMAC signature using `repository_owner`, which is read directly from the untrusted payload (`params.dig('repository', 'owner', 'login')`): [1](#0-0) [2](#0-1) 

This binds "which organization's secret verifies the signature" to a payload field the attacker fully controls (as long as it names an organization configured on this Shipit instance, e.g. in a multi-org deployment per `docs/setup.md`'s "Using Multiple Github Applications" section). The signature only proves the sender knows *that org's* webhook secret — it says nothing about which repository the rest of the payload actually targets.

`StatusHandler#process`, however, never checks the `repository` field of the payload at all. It looks up commits globally by SHA and mutates their status directly: [3](#0-2) 

Compare this to the base `Handler` class, which *does* scope lookups by `repository.full_name` for other handlers (`stacks` helper), but `StatusHandler` bypasses that helper entirely and instead does `Commit.where(sha: params.sha)` unconditionally across the whole `commits` table: [4](#0-3) 

`Commit#create_status_from_github!` then directly records a status against that commit and its owning `stack` (which may belong to an entirely different, unrelated organization/repository than the one whose secret was used to authenticate the request): [5](#0-4) 

**The broken binding, as an equality:**
`organization whose webhook secret authenticated the request` ≠ `organization/repository whose commit status is actually written`, because `StatusHandler` never checks that `stack.repository.owner == repository_owner` used in `verify_signature`.

### Impact Explanation
`Commit#deployable?` and `Commit#blocked?` depend directly on commit `status`/CI state: [6](#0-5) 

By forging a `status` webhook — signed with the webhook secret of an organization the attacker controls/has installed the App for on this Shipit instance — an attacker can inject a fake `success` status onto any commit SHA in the database, including commits belonging to stacks/repositories owned by a *different* organization they have no access to. If that SHA collision/knowledge exists (SHAs are often public via commit history, PRs, CI logs, etc.), this can flip `deployable?` to true for a commit that never actually passed CI in its real repository, enabling an **unauthorized deploy** of unvetted code — one of the explicitly accepted high-impact outcomes (unauthorized deploy). It can also be used to mark a legitimately blocking commit as passing to bypass `blocked?` safety gating.

### Likelihood Explanation
This requires the attacker to control (or have compromised) at least one GitHub organization/App that this specific Shipit instance is configured to trust (i.e., is present in `Shipit.github` app configuration) — a realistic scenario in the documented multi-org configuration (`docs/setup.md`), where different organizations may have separately created and independently-secreted GitHub Apps pointed at the same shared Shipit instance. No repository write access, API token, or session is needed — only the ability to send an HTTP POST to `/webhooks` with a body signed by an org-scoped webhook secret the attacker legitimately possesses for their own org. The attacker additionally needs to know or guess a target commit SHA in the victim stack, which is commonly public (e.g., visible on GitHub, in PR links, CI dashboards).

### Recommendation
In `StatusHandler` (and any other handler that resolves records purely by content fields like `sha`), scope the lookup through the `stacks`/`repository_name` helper already used by the base `Handler` class, e.g. restrict to `stacks.commits.where(sha: params.sha)` or otherwise verify `commit.stack.repository.owner == repository_owner` (the same value used in `verify_signature`) before calling `create_status_from_github!`. More generally, `verify_signature` should also enforce that the resolved `github_app`'s configured organization matches every repository referenced later in the payload actually processed by handlers, closing the gap between "which secret authenticated this request" and "which repository/commit this request is allowed to mutate."

### Proof of Concept
1. Shipit is configured (per `docs/setup.md`) with two GitHub App entries: `org-attacker` (attacker's own org, webhook secret known to attacker) and `org-victim` (unrelated org, tracked stack `victim/repo`, with a real commit `abc123...` that has not passed CI).
2. Attacker crafts a `status` webhook payload:
   ```json
   {
     "sha": "abc123...",
     "state": "success",
     "context": "ci/attacker-forged",
     "repository": { "owner": { "login": "org-attacker" } }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=<hmac(org-attacker secret, body)>` and sets `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"org-attacker"`, fetches that org's `github_app`, and the signature verifies successfully (`app/controllers/shipit/webhooks_controller.rb:24-30,59-62`).
5. `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler#process`, which runs `Commit.where(sha: 'abc123...')` — matching the victim's commit in `org-victim`'s stack regardless of which org authenticated the request — and calls `create_status_from_github!`, recording a fabricated `success` status (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`, `app/models/shipit/commit.rb:165-169`).
6. The victim commit is now `deployable?` and can be picked up for an unauthorized deploy, even though the attacker has no relationship to `org-victim`/`victim/repo`.
