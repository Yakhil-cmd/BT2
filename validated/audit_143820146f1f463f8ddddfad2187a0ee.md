### Title
`handleDuplicateAddressDefinition` always rejects legitimate re-submission of an already-registered address definition instead of accepting it - (File: `validation.js`)

### Summary
`validation.js`'s `handleDuplicateAddressDefinition()` is supposed to tolerate an author re-attaching the same (already recorded) address definition to a unit — the trailing comment explicitly says *"let it be for now"* — but the guard that enables this tolerant path is commented out, so the function now **unconditionally rejects the unit** with `"duplicate definition of address..."` even when the resent definition is byte-for-byte identical to the one already stored for that address.

### Finding Description
`validateAuthor()` calls `validateDefinition()` whenever an author explicitly attaches a `"definition"` field to a unit [1](#0-0) . If the address already has a definition on record, `storage.readDefinitionByAddress` invokes the `ifFound` callback, which forwards to `handleDuplicateAddressDefinition` [2](#0-1) .

Inside `handleDuplicateAddressDefinition`, the intended logic was to only reject when the address is *not* eligible for a "harmless resend" (guarded by `bNonserial` / forked-path checks), and otherwise fall through to compare hashes and accept the unit if the resent definition matches the stored one:
```
function handleDuplicateAddressDefinition(arrAddressDefinition){
//	if (!bNonserial || objValidationState.arrAddressesWithForkedPath.indexOf(objAuthor.address) === -1)
		return callback("duplicate definition of address "+objAuthor.address+", bNonserial="+bNonserial);
	...
	callback(); // let it be for now. Eventually, at most one of the balls will be declared good
}
``` [3](#0-2) 

Because the `if` line is commented out, the `return callback("duplicate definition...")` on the next line executes unconditionally for every call, regardless of `bNonserial` or whether the definitions actually match. The hash-comparison code and the final `callback()` that would accept the resend are now dead code, unreachable in all cases.

This mirrors the reported bug class exactly: an operation whose semantics require returning success / accepting the already-existing deterministic result (matching definition already bound to the address) instead reverts/rejects, because the collision-handling branch was disabled rather than fixed.

### Impact Explanation
Any unit where an author attaches an explicit `"definition"` for an address that has already been used (i.e., its `definition_chash` is already on record) will be declared invalid, **even when the attached definition is the exact same one already active for that address**. This can:
- Permanently break address definition resend flows referenced in the code's own comment ("the attacker changes his definition then quickly sends a new ball with the old definition"), which was the exact scenario this function was designed to reconcile without forking nodes.
- Cause wallets/services that defensively re-attach a known definition (e.g., during nonserial/fork resolution, multi-device wallets, or backup/redundant broadcasting) to have every such unit rejected, freezing that address's ability to transact through this path and wasting posted fees.
- Since the rejection is deterministic and identical on every full node (all nodes run the same validation code), this does not cause inter-node disagreement, but it does cause a **network-wide inability to confirm units that legitimately resend a matching address definition**, i.e., an availability/freezing bug for the affected address.

### Likelihood Explanation
The path is reached anytime an author includes an explicit `"definition"` object in a unit for an address that already has a `definition_chash` bound to it — a condition that is trivial to trigger (any second unit that re-attaches the definition instead of omitting it) and is explicitly anticipated by the existing (now dead) code and its comments as a legitimate, expected scenario rather than an edge case.

### Recommendation
Restore (or properly re-derive) the intended guard so `handleDuplicateAddressDefinition` only rejects when appropriate, and otherwise falls through to the hash-comparison/accept logic:
```javascript
function handleDuplicateAddressDefinition(arrAddressDefinition){
	if (!bNonserial || objValidationState.arrAddressesWithForkedPath.indexOf(objAuthor.address) === -1)
		return callback("duplicate definition of address "+objAuthor.address+", bNonserial="+bNonserial);
	try {
		if (objectHash.getChash160(arrAddressDefinition) !== objectHash.getChash160(objAuthor.definition))
			return callback("unit definition doesn't match the stored definition");
	}
	catch (e) {
		return callback("handleDuplicateAddressDefinition definition hash failed: " + e.toString());
	}
	callback(); // accept: the resent definition matches what's on record
}
```

### Proof of Concept
1. Address `A` first uses definition `D1`; `definition_chash` for `A` is recorded as `hash(D1)` via `validateDefinition`'s `ifDefinitionNotFound` branch.
2. Author of `A` posts a subsequent unit that again explicitly includes `"definition": D1` in the author object (a legitimate resend, e.g. during a nonserial/fork-resolution scenario as described in the code's own comment).
3. `validateDefinition()` finds an existing definition (`ifFound`) and calls `handleDuplicateAddressDefinition(D1)` [2](#0-1) .
4. Because the guarding `if` is commented out, the function immediately executes `return callback("duplicate definition of address ...")` [4](#0-3) , rejecting the unit as invalid even though `D1 === D1`.
5. The hash-comparison/accept code below, including the `callback()` that should have validated and accepted the resend, is never reached.
