### Title
Cross-Repository Status Forgery via Unscoped `StatusHandler` — Authenticated-Organization vs. Written-Repository Binding Break (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates a webhook only against the GitHub App/organization derived from the payload's `repository.owner.login` (or `organization.login`), but `StatusHandler#process` then mutates commit-status state using a completely unscoped, global `Commit.where(sha: params.sha)` lookup that ignores `repository.full_name` entirely. The binding "organization whose webhook secret verified the payload" == "repository/stack whose commit status is written" is never enforced, letting a payload signed for one repository/organization overwrite CI status for a commit belonging to an unrelated stack.

### Finding Description
`WebhooksController#verify_signature` picks the `GitHubApp`/`webhook_secret` to validate against based solely on `repository_owner`, itself read straight out of the untrusted JSON body: [1](#0-0) [2](#0-1) 

This only proves the request carries a valid HMAC for *that organization's* configured secret (per-organization secrets are a supported configuration, see `Shipit.github_app_config`): [3](#0-2) 

Signature validity says nothing about which specific repository (or stack) the rest of the payload's fields are allowed to affect — a GitHub App installed on an organization emits the same webhook secret for every repository in that org, and any push/status event to any repo in the org (including ones the attacker fully controls) will produce a validly-signed payload.

Once verified, `StatusHandler#process` uses only `params.sha` to look up commits, with **no scoping by `payload['repository']['full_name']`** even though the base `Handler` class already defines a `repository_name`/`stacks` scoping helper that other handlers use: [4](#0-3) [5](#0-4) 

Compare with `CheckSuiteHandler`, which correctly scopes to `stacks.where(branch: ...)` (i.e., repository-bound) before touching commits: [6](#0-5) 

So the equality that should hold — `organization_that_authenticated(payload) == repository_whose_commit_is_written(params.sha)` — is broken: authentication is organization/repository-keyed, but the actual write (`commit.create_status_from_github!(params)`) is keyed purely by a global SHA match across every stack/repository/organization tracked by the Shipit instance.

### Impact Explanation
An attacker who can generate one validly-signed `status` webhook (e.g., by pushing a commit and CI status to any repository they control that is tracked in *any* organization installation known to this Shipit instance) can supply a `sha` belonging to a commit tracked under a completely different, unrelated stack/repository (git SHAs are not secrets — they are visible via the GitHub UI/API for any repo the attacker can view) and forge an arbitrary CI status (`state: success`, fabricated `context`, `target_url`, `description`) onto that unrelated commit. Because `deploy_spec.rb`'s CI gating (`ci.require`/`required_statuses`, `Commit#deployable?`) depends on stored `Status` rows, this can be used to satisfy a target stack's required-CI-status gate and enable an unauthorized deploy of a commit that never actually passed CI on the correct repository — this reaches the Critical bucket ("an unauthorized deploy").

### Likelihood Explanation
The primary barrier is the ability to obtain one valid webhook signature, which is realistically achievable by any GitHub user who can push to and receive a `status` event on any repository tracked by an org/app installation known to the Shipit instance (this is unprivileged relative to the target stack — the attacker needs no access whatsoever to the target repository). Multi-organization installations with distinct webhook secrets are an explicitly supported and tested configuration (`test/dummy/config/secrets_double_github_app.yml`), making cross-organization forgery directly reachable; even single-organization deployments are affected cross-repository, since one org-level GitHub App secret typically covers many repositories.

### Recommendation
Scope `StatusHandler#process` (and any other handler that doesn't already do so) to the payload's declared repository, mirroring `Handler#stacks`/`repository_name`, e.g. restrict the `Commit.where(sha: params.sha)` lookup to commits belonging to `stacks` derived from `payload.dig('repository', 'full_name')` before calling `create_status_from_github!`.

### Proof of Concept
1. Attacker creates/owns `attacker/toy-repo`, tracked as a Shipit stack under organization `OrgA` (which has its own `webhook_secret` configured under `secrets.github.orga`).
2. Attacker looks up (public/visible) commit SHA `deadbeef...` belonging to `victim-org/critical-app`'s stack, which requires CI context `"ci/tests"` to be `success` before deploy (`ci.require` in `shipit.yml`).
3. Attacker pushes a commit and status update to `attacker/toy-repo`; GitHub sends a `status` webhook signed with OrgA's `webhook_secret`, but the attacker intercepts/replays and edits the JSON body's `sha` field to `deadbeef...` (the victim commit) and `context`/`state` to `"ci/tests"`/`"success"`, recomputing the HMAC with the OrgA secret they legitimately possess.
4. `WebhooksController#verify_signature` resolves `repository_owner` to `attacker`'s org (`OrgA`) from `repository.owner.login`, verifies successfully against OrgA's secret.
5. `StatusHandler#process` runs `Commit.where(sha: 'deadbeef...')` — since no repository filter exists, it finds and updates the actual `victim-org/critical-app` commit, marking `"ci/tests"` as `success`, satisfying `required_statuses` and allowing an unauthorized deploy trigger.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
