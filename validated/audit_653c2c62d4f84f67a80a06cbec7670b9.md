This confirms the multi-organization GitHub App design is a documented, first-class configuration in this engine (`Shipit.github_app_config` / `Shipit.github_organizations`, sample multi-org secrets in `config/secrets.development.example.yml`), and `Shipit.github(organization:)` selects a distinct `webhook_secret` per organization [1](#0-0) . The webhook signature check and the repository-resolution logic used by handlers key off two different, independently-attacker-controlled JSON fields in the same unsigned-until-verified raw body.

### Title
Webhook signature verified against `repository.owner.login`'s org secret while handlers act on the independent `repository.full_name` field, enabling cross-organization stack writes - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
In multi-organization deployments, `WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate the HMAC signature against using `repository_owner` (`repository.owner.login` or `organization.login`) [2](#0-1) . Once the signature is accepted, `Handler#repository_name` (and every handler's own `repository` lookup) independently reads `repository.full_name` from the same JSON body to decide which `Repository`/`Stack` to mutate [3](#0-2) . Nothing enforces that `repository.owner.login` and `repository.full_name` refer to the same repository/organization. An attacker who legitimately controls a GitHub App/organization mounted on this Shipit instance (and therefore knows that org's `webhook_secret`) can forge the entire raw JSON body, since the signature is just an HMAC over attacker-supplied bytes.

### Finding Description
The equality this code is supposed to enforce is:
`organization whose webhook_secret authenticated the request == organization that owns the repository the handler mutates`

`verify_signature` computes:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
using `repository_owner = params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [4](#0-3) .

After the signature check passes, `WebhooksController#create` dispatches the raw parsed JSON to handlers untouched: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [5](#0-4) . Handlers such as `PushHandler` resolve the target `Stack` via `Handler#stacks`, which calls `Repository.from_github_repo_name(repository_name)` where `repository_name = payload.dig('repository', 'full_name')` [3](#0-2) [6](#0-5) . `Repository.from_github_repo_name` simply splits `owner/name` from that string and does a DB lookup, with no relation whatsoever to `repository.owner.login` used earlier for signing [7](#0-6) .

Since `Shipit.github(organization:)` looks up a distinct `webhook_secret` per configured GitHub organization (as documented in the multi-org secrets schema) [1](#0-0) , an attacker who is an admin of, or has installed, their own GitHub App/organization ("attacker-org") on this Shipit instance knows `attacker-org`'s `webhook_secret`. They can then POST an arbitrary raw JSON body to `/webhooks` where:
- `repository.owner.login` = `"attacker-org"` (drives which secret is used to verify — the attacker's own known secret)
- `repository.full_name` = `"victim-org/victim-repo"` (drives which real `Stack` the handler mutates)

`verify_signature` will succeed (attacker signed with their own known secret), and `PushHandler#process` will then run `stack.sync_github(expected_head_sha: params.after)` against the victim's stack — a stack the attacker has no GitHub-side access to and never proved control over.

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" binding explicitly called out in scope. The practical consequence is an unauthorized cross-organization write: the attacker can force `GithubSyncJob` to run against a victim's `Stack`, injecting an `expected_head_sha` and triggering commit/status ingestion for a repository they don't control, similarly to how other handlers (`StatusHandler`, `MembershipHandler`, PR handlers) can be pointed at victim stacks/teams by the same technique. This is a cross-repository write triggered purely by possessing valid credentials for an unrelated, attacker-owned organization — satisfying the Critical "cross-repository writes" bar, though the severity is scoped to whatever webhook handlers can do (sync commits/statuses, membership changes, PR-driven stack archive/unarchive) rather than direct code execution.

### Likelihood Explanation
Exploitability requires the host application to be configured with the documented multi-organization GitHub App schema and requires the attacker to control (or be an admin of) at least one of the configured organizations — a scenario the engine explicitly documents and supports (`config/secrets.development.example.yml` multi-org example, `Shipit.github_organizations`) [8](#0-7) . No GitHub App private key, no Shipit session, and no privileged Shipit account are needed — only knowledge of one legitimately-configured organization's `webhook_secret`, which by design that organization's admins already possess. This makes the attack realistic in any multi-tenant/multi-org Shipit deployment.

### Recommendation
Bind the signature-verification organization to the same field used for repository resolution: derive `repository_owner` from the same `full_name`/owner path that `Repository.from_github_repo_name` uses, or better, after resolving the target `Stack`/`Repository` from `full_name`, re-verify that `repository.owner.login` (or `organization.login`) matches `repository.owner` on that record before invoking handlers. Reject the webhook if the two do not match.

### Proof of Concept
Given a Shipit instance configured with two organizations, `attacker-org` (webhook_secret `S_A`, known to the attacker) and `victim-org` (hosting a real `Stack` for `victim-org/victim-repo`):

1. Attacker crafts JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
2. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(S_A, body)>` using `S_A`, which they legitimately know.
3. POST to `/webhooks` with header `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner = "attacker-org"`, loads `S_A`, verifies successfully [9](#0-8) .
5. `PushHandler` resolves stacks via `full_name = "victim-org/victim-repo"` [10](#0-9)  and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim's real stack, without the attacker ever having GitHub access to `victim-org/victim-repo`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
