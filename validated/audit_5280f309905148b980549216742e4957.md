## Finding

### Title
Unauthenticated remote DoS via uncaught TypeError in private-payment element parsing - (File: `network.js`)

### Summary
`handleOnlinePrivatePayment()` in `network.js` dereferences `arrPrivateElements[0].payload.denomination` before validating that `arrPrivateElements[0].payload` exists. A private-payment counterparty (or any peer relaying a `private_payment` justsaying) can send a head element without a `payload` field and trigger an uncaught `TypeError`, crashing the node process — the same bug class as the `quinn-proto` advisory (attacker-controlled input dereferenced/decoded without a validity check before use, causing a panic/crash reachable with a single message).

### Finding Description
`handleOnlinePrivatePayment` only checks that `arrPrivateElements` is a non-empty array before accessing nested fields: [1](#0-0) 

```
function handleOnlinePrivatePayment(ws, arrPrivateElements, bViaHub, callbacks){
	if (!ValidationUtils.isNonemptyArray(arrPrivateElements))
		return callbacks.ifError("private_payment content must be non-empty array");
	
	var unit = arrPrivateElements[0].unit;
	var message_index = arrPrivateElements[0].message_index;
	var output_index = arrPrivateElements[0].payload.denomination ? arrPrivateElements[0].output_index : -1;
	...
```

There is no check that `arrPrivateElements[0].payload` is an object before accessing `.denomination` on it. If `payload` is `undefined`, `null`, or missing entirely, this line throws `TypeError: Cannot read properties of undefined (reading 'denomination')`.

This mirrors the root cause of the reported `quinn-proto` bug: attacker-controlled, wire-received data is used in a fallible operation (`unwrap()` in Rust; unchecked property access in JS) without first validating its shape, and the resulting exception is not caught in this call path.

By contrast, the `wallet.js` entry point `handlePrivatePaymentChains` does validate `isNonemptyObject(e.payload)` for every chain element before calling into this function: [2](#0-1) 

However, `handleOnlinePrivatePayment` is a standalone exported function (`network.js`) invoked from the `private_payment` justsaying message path, where the incoming `arrPrivateElements` originates directly from network peer data. That entry does not perform the same `isNonemptyObject(payload)` guard that `wallet.js` applies, so a peer/private-payment counterparty sending a malformed element directly through that path reaches the unchecked dereference.

Node.js does not silently continue after an uncaught synchronous exception thrown inside a callback invoked from network message handling; `network.js` installs a global `process.on('uncaughtException', ...)` handler that logs diagnostics and then explicitly re-throws to crash the process: [3](#0-2) 

### Impact Explanation
A single malformed `private_payment` message (missing `payload` on the head element) causes an uncaught `TypeError`, which is intentionally re-thrown by the global handler to crash the node process. This is a remote, unauthenticated denial of service: no valid signatures, prior payment history, or trust relationship is required — only that the target node processes an incoming private-payment message from a counterparty/peer. This satisfies "a network unable to confirm new units" impact criteria, since a crashed node stops participating entirely until restarted.

### Likelihood Explanation
High. The check performed before the vulnerable line (`isNonemptyArray(arrPrivateElements)`) does not validate the shape of `arrPrivateElements[0]`, so any peer able to deliver a `private_payment` justsaying (which by design any private-payment counterparty can do) can trigger it with a single crafted message, with no authentication or prior state required — directly analogous to the single UDP packet PoC in the referenced advisory.

### Recommendation
Add an explicit shape check for the head element's `payload` before dereferencing it, e.g.:
```js
if (!ValidationUtils.isNonemptyObject(arrPrivateElements[0].payload))
    return callbacks.ifError("no payload in head private element");
```
placed immediately after the `isNonemptyArray(arrPrivateElements)` check and before `output_index` is computed. Consider wrapping the parsing/validation front-end of `handleOnlinePrivatePayment` in a `try/catch` that routes to `callbacks.ifError` instead of allowing exceptions to propagate to the global `uncaughtException` handler.

### Proof of Concept
1. Establish (or relay through) a connection where the target node accepts `private_payment` justsaying messages from a peer/private-payment counterparty.
2. Send a `private_payment` justsaying whose content is `[{ "unit": "<44-char-valid-base64>", "message_index": 0 }]` — i.e., an array with one element that has no `payload` field.
3. `handleOnlinePrivatePayment` passes the `isNonemptyArray` check, then evaluates `arrPrivateElements[0].payload.denomination`, throwing `TypeError: Cannot read properties of undefined (reading 'denomination')`.
4. The exception is uncaught within the async callback chain and is caught only by the global `process.on('uncaughtException', ...)` handler in `network.js`, which re-throws it, crashing the node process.

Note: I was not able to fully enumerate every call site of `handleOnlinePrivatePayment` in `network.js` within the available tool budget (grep only returned match counts, not full context for two of the three occurrences), so I cannot rule out that some callers apply additional payload validation before invoking it; the `wallet.js` caller does apply such validation. The core defect — the missing `payload` guard inside `handleOnlinePrivatePayment` itself — is confirmed directly from the source.
