### Title
`MembershipHandler#process` writes team authorization state directly from unverified webhook payload fields, with no GitHub-side corroboration - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`MembershipHandler#process` trusts `params.member.login` and `params.action` verbatim to add or remove a `User` from a `Team`, without ever calling back into the GitHub API to confirm the claimed membership change actually happened on GitHub's side. Because `Team` membership is the basis of `User#authorized?`, a forged `membership`/`added` payload turns into a real authorization grant into `Shipit.github_teams`.

### Finding Description
The broken binding: `params.member.login` (attacker-controlled JSON field) == the login GitHub itself reports as added to `params.team.slug`/`params.team.id` must hold, but nothing in the code enforces it.

Trace:
- `MembershipHandler#process` at [1](#0-0)  does: `team = find_or_create_team!` (built from `params.team`/`params.organization`, again payload-only fields), `member = User.find_or_create_by_login!(params.member.login)`, then on `action == 'added'` calls `team.add_member(member)`.
- `Team#add_member` at [2](#0-1)  unconditionally appends the member to `members` if not already present - no Octokit call, no `team_members`/`org_teams` confirmation.
- The only network-derived data used is `User.find_or_create_by_login!`, which calls `Shipit.github.api.user(login)` at [3](#0-2)  merely to resolve/create a profile for whatever login string is in the payload - this confirms the *login exists on GitHub*, not that it is actually a member of the team named in the payload. There is no call analogous to `gh_api.team_members` (used elsewhere only in `Team.find_team_on_github` / `refresh_members!` at [4](#0-3)  and [5](#0-4) ) inside the webhook handler path.
- This membership record is directly consumed by `User#authorized?` at [6](#0-5) : `Shipit.github_teams.empty? || teams.where(id: Shipit.github_teams.map(&:id)).exists?`. Any user added to a `Team` whose id is in `Shipit.github_teams` becomes `authorized?`.
- Reaching the handler still requires the same signature-bypass precondition noted in the referenced webhook_secret finding: `verify_webhook_signature` returns `true` unconditionally when `webhook_secret` is unset for the target organization's `GitHubApp` config, at [7](#0-6) , and `WebhooksController#verify_signature` (`before_action`) only calls that check, at [8](#0-7) . `drop_unhandled_event` ( [9](#0-8) ) does not block `membership` since a handler exists for it. The `ExplicitParameters` `params do` block in `MembershipHandler` ( [10](#0-9) ) only validates JSON shape/types, not authenticity of the claim.

Given the (already-established) precondition that signature verification can be bypassed when `webhook_secret` is unset for the org, an attacker can POST a `membership`/`added` event with `member.login` set to their own GitHub login and a real, existing `team`/`organization` object (values can be copied from any legitimately-observed event or guessed team `id`/`slug`/`organization.login`), and the handler will add that attacker-controlled `User` row to the `Team` row - with no server-side check against GitHub that the claimed team actually gained that member.

### Impact Explanation
If the targeted `Team` is one of the teams configured in `Shipit.github_teams` (the mechanism gating `User#authorized?`), this grants the attacker's Shipit `User` record `authorized?` status without ever actually being a member of that GitHub team - an authorization-bypass/escalation into `Shipit.github_teams` privilege, matching the "High" impact category ("escalation into `Shipit.github_teams` authorization"). This is repeatable against any team the attacker can name (team id/slug/org login are all just JSON fields), and is independent per organization/team combination.

### Likelihood Explanation
Full exploitation requires the previously-identified precondition that the target organization's `GitHubApp` config has no `webhook_secret` set (so `verify_webhook_signature` short-circuits to `true`). Given that precondition, the attacker needs no Shipit session, API token, or GitHub team membership - only network access to `POST /webhooks` with a crafted JSON body and a valid `X-Github-Event: membership` header. All team/org/member fields are attacker-supplied plaintext with no verification step in this handler, making exploitation deterministic and repeatable.

### Recommendation
In `MembershipHandler#process`, before mutating `Team` membership, call back into the GitHub API (e.g., `Shipit.github(organization: params.organization.login).api.team_membership(params.team.id, params.member.login)` or equivalent `team_members` check) to confirm the claimed action against GitHub's own state, rather than trusting the webhook body directly. This should be layered on top of (not instead of) fixing the `webhook_secret` enforcement gap.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/membership_handler_test.rb
test "process does not corroborate membership with GitHub before mutating Team" do
  team = shipit_teams(:some_team) # or Team.create!(...)
  payload = {
    'action' => 'added',
    'team' => { 'id' => team.github_id, 'name' => team.name, 'slug' => team.slug, 'url' => team.api_url },
    'organization' => { 'login' => team.organization },
    'member' => { 'login' => 'attacker-login' }
  }

  # Stub only the profile lookup used to create the User record
  Shipit.github.api.expects(:user).with('attacker-login').returns(stub(id: 999, login: 'attacker-login', name: nil, email: nil, avatar_url: nil, url: nil))

  # Assert no call is ever made to confirm team membership on GitHub's side
  Shipit.github.api.expects(:team_members).never
  Shipit.github.api.expects(:team_membership).never

  Shipit::Webhooks::Handlers::MembershipHandler.call(payload)

  attacker = Shipit::User.find_by(login: 'attacker-login')
  assert team.members.include?(attacker), "attacker was added to team without any GitHub-side corroboration"
end
```
This demonstrates the equality `params.member.login == GitHub-reported team member` is never checked: the handler's side effect (`team.add_member`) occurs purely from payload content, with `team_members`/`team_membership` never invoked.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
