**Analysis summary:**

The premise — that `size_u32_as_uleb128` is used to *estimate* transaction size in mempool while the VM computes a different *actual* serialized size, creating a desync exploitable at ULEB128 width-transition boundaries — does not hold up.

1. `size_u32_as_uleb128` (re-exported from `move_binary_format::file_format_common`) is a low-level helper used for Move binary-format/BCS length-prefix size computations (e.g. `bcs_size_of_byte_array`, gas-metered value-size estimation), not for mempool's admission size accounting. [1](#0-0) 

2. The existing unit tests already verify `size_u32_as_uleb128` against `bcs::serialized_size` across all documented boundaries (0/127, 127/128, 128²-1/128²), confirming the helper's correctness at exactly the transition points the question hypothesizes as exploitable. [2](#0-1) 

3. Mempool's admission-relevant size accounting (`get_batch`, `read_timeline`, `test_estimated_bytes`/`get_estimated_bytes`) all operate on `txn.txn_bytes_len()` / `txn.raw_txn_bytes_len()` — the actual serialized byte length of the received transaction — not an independently computed ULEB128 estimate. [3](#0-2) [4](#0-3) 

4. The VM's `check_gas` prologue check (which enforces `EXCEEDED_MAX_TRANSACTION_SIZE`) also uses `txn_metadata.transaction_size`, which `TransactionMetadata::new` derives directly from `txn.txn_bytes_len()` or `txn.raw_txn_bytes_len()` on the actual `SignedTransaction` — the same real serialized length used elsewhere, not a separate estimate. [5](#0-4) [6](#0-5) 

Because mempool, consensus/quorum-store, and the VM's size-based prologue check all consistently use the actual serialized byte length of the transaction (not a ULEB128-based estimate that could desync at an encoding-width boundary), there is no admission path by which crafting a vector length at a uleb128 width transition could desynchronize a size estimate from the VM's real check and admit an oversized transaction.
