### Title
stSTXbtc collateral is priced as a 1:1 STX peg with no live exchange-rate feed, unlike every other yield-bearing asset in the oracle - (File: `mainnet/contracts/utility/v0-1-data.clar`, `mainnet/contracts/market/v0-4-market.clar`)

### Summary
The oracle pricing logic used across Zest values every yield-bearing wrapper asset by combining a base price with a *live* conversion ratio that reflects the asset's current redemption value — except `stSTXbtc`. For `stSTX` the code explicitly fetches `get-ststx-ratio` and multiplies it into the STX price before use, but for `stSTXbtc` ("Liquid Staked STX (BTC yield)") the code simply returns the raw STX Pyth price with **no ratio call at all**, even though the surrounding comment claims a "BTC price" transformation is applied. [1](#0-0) [2](#0-1) 

### Finding Description
`get-asset-price` resolves the USD price for every registered asset ID. For `stSTX`, the function fetches the STX price and multiplies it by `get-ststx-ratio()`, a live on-chain call that reflects the current staking exchange rate between stSTX and STX: [1](#0-0) 

For `stSTXbtc`, by contrast, the price is computed as `(default-to u0 (get-pyth-price PYTH-STX))` — a direct pass-through of the STX price with zero adjustment — despite the inline comment describing it as a "BTC price" transformation, which is not actually performed anywhere in this branch: [3](#0-2) 

The same static-mapping pattern exists in the market's own callcode resolver, where `CALLCODE-ZSTSTXBTC` only applies the vault's liquidity index on top of the raw price `p`, never a stSTXbtc/STX or stSTXbtc/BTC exchange ratio: [4](#0-3) 

This is structurally identical to the Napier bug class: an asset whose true redemption value diverges from a reference asset over time (via accrued yield) is priced using a hard-coded 1:1 relationship instead of a live, queryable exchange rate — exactly as the Napier AMM treated Curve's Base LP Token as a static "3x PT" instead of using `get_virtual_price`. Here, `stSTXbtc`'s true STX/BTC-denominated redemption value can drift from the STX spot price (the underlying `ststxbtc-token-v2` accrues yield the same way `ststx-token` does, per `convert-to-assets`/`convert-to-shares` share-math seen in the vault contract), yet the market's price oracle for this collateral asset never reflects that drift. [5](#0-4) 

### Impact Explanation
Because `get-asset-price(stSTXbtc)` and the `zstSTXbtc` callcode both feed directly into collateral valuation (`sum-collateral-usd`) and health-factor/liquidation math used for *all* borrowers, a divergence between the assumed 1:1 STX price and stSTXbtc's real redemption value has pool-wide effects, not just self-harm to the depositor: [6](#0-5) 
- If stSTXbtc's real value falls below the assumed STX-pegged price, borrowers holding stSTXbtc/zstSTXbtc collateral are treated as more solvent than they are, allowing them to borrow against other suppliers' funds (STX, sBTC, USDC, etc.) beyond their real collateral's worth. When positions are later liquidated, the liquidation collects real (lower-value) stSTXbtc but the debt drawn against other vaults was sized off the inflated price — the shortfall is socialized across all suppliers of the borrowed assets.
- If stSTXbtc's real value rises above the assumed price, liquidators or counterparties can seize/receive undervalued stSTXbtc relative to its true worth, extracting value at the expense of the position holder or the vault's other depositors.

This lands on the in-scope **temporary/permanent freezing of funds** and **socialized bad-debt** impact category, since it is other suppliers' locked capital, not just the position owner's, that absorbs the mispricing.

### Likelihood Explanation
Likelihood depends on whether `ststxbtc-token-v2`'s real STX/BTC exchange rate actually drifts from 1:1 over time (i.e., whether BTC yield is reflected in the token's redemption ratio the same way `ststx-token`'s STX yield is reflected in `get-ststx-ratio`). I could not fully verify this off-chain economic behavior of `ststxbtc-token-v2` within available context, so this should be validated against the actual `ststxbtc-token-v2` mechanics before treating it as confirmed-exploitable; but the code path itself is unambiguously missing the ratio adjustment that every structurally similar asset (`stSTX`) receives, and the stale inline comment ("BTC price") is inconsistent with the actual implementation, indicating an incomplete or regressed pricing function.

### Recommendation
Add a live exchange-rate/ratio call for `stSTXbtc` (analogous to `get-ststx-ratio` for `stSTX`) and apply it in `get-asset-price` and in the market's `resolve-callcode`/`CALLCODE-ZSTSTXBTC` path before using the raw STX price, rather than assuming a static 1:1 relationship between stSTXbtc and STX.

### Proof of Concept
1. Assume `ststxbtc-token-v2`'s real redemption rate diverges from 1 STX (either up or down) due to accrued yield, as is the case for `ststx-token`.
2. A user deposits `stSTXbtc` as collateral (directly, or via `v0-vault-ststxbtc` to receive `zstSTXbtc`).
3. `market.clar`/`v0-4-market.clar` calls `resolve-callcode`/`get-asset-price` for `stSTXbtc`, which returns the raw STX Pyth price with no ratio applied. [7](#0-6) 
4. If the real value is lower than the STX price used, the user's health factor is overstated, letting them borrow more of other suppliers' assets (STX, sBTC, USDC, USDH) than their true collateral supports.
5. On liquidation, the seized stSTXbtc is worth less than the debt it was allowed to back, and the deficit is absorbed by the vault(s) that supplied the borrowed asset — a loss socialized across unrelated depositors who never interacted with the mispriced position.

(define-private (resolve-ststx (p uint))
  (let ((ratio (unwrap! (call-ststx-ratio) ERR-ORACLE-CALLCODE)))
    (ok (mul-div-down p ratio STSTX-RATIO-DECIMALS))))

(define-private (resolve-ztoken (p uint) (aid uint))
  (let ((cached (unwrap! (get-cached-indexes aid) ERR-ORACLE-CALLCODE))
        (cached-lindex (get lindex cached))
        (scaled (* p cached-lindex)))
    (ok (div-down scaled INDEX-PRECISION))))

(define-private (resolve-callcode (p uint) (callcode (optional (buff 1))))
  (let ((cc (unwrap! callcode (ok p))))
    (if (is-eq cc CALLCODE-STSTX) (resolve-ststx p)
    (if (is-eq cc CALLCODE-ZSTX) (resolve-ztoken p STX)
    (if (is-eq cc CALLCODE-ZSBTC) (resolve-ztoken p sBTC)
    (if (is-eq cc CALLCODE-ZSTSTX) (resolve-ztoken (try! (resolve-ststx p)) stSTX)
    (if (is-eq cc CALLCODE-ZUSDC) (resolve-ztoken p USDC)
    (if (is-eq cc CALLCODE-ZUSDH) (resolve-ztoken p USDH)
    (if (is-eq cc CALLCODE-ZSTSTXBTC) (resolve-ztoken p stSTXbtc)
    ERR-ORACLE-CALLCODE)))))))))
