### Title
Vault `system-repay` splits principal/interest using a pool-wide average ratio instead of the repaying borrower's own ratio, corrupting `total-borrowed` and mispricing zToken shares for LPs - (File: `mainnet/contracts/vault/v0-vault-usdc.clar` and sibling vault contracts)

### Summary
Every asset vault (`v0-vault-usdc.clar`, `v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`) tracks aggregate borrower debt with an index-based rebase model that is mathematically identical to the BigBang `part`/`elastic` pattern described in the report: a global `index` grows over time, each borrow mints "scaled" shares against the pool, and `total-debt = principal-scaled * index`. When any individual borrower repays, `system-repay` decides how much of that specific payment is "principal" versus "interest" using the *pool-wide* ratio `total-borrowed / total-debt`, not that borrower's own principal-to-debt ratio. [1](#0-0) 

### Finding Description
`system-repay` computes:
```
(principal-repaid (mul-div-down capped-amount total-borrowed-amount debt))
(interest-paid (- capped-amount principal-repaid))
``` [2](#0-1) 

`total-borrowed-amount` and `debt` are pool-wide aggregates summed across every borrower who has ever borrowed this asset, at any index. `capped-amount` is a single caller's repayment. Because different borrowers entered at different values of `index`, each has a different true principal-to-current-debt ratio (early borrowers, having accrued more interest, have a lower ratio than borrowers who just opened a position). Applying the *average* ratio to one specific borrower's payment - exactly the flaw identified in the referenced BigBang report where `part` (a pool-share concept) was used as a stand-in for that user's real original debt - misattributes principal vs. interest for that repayment.

The consequence is not confined to the repaying caller: `total-borrowed` is a single shared state variable consumed by every other participant. The resulting `total-borrowed-new` is under- or over-decremented relative to the truth, and this corrupted value directly feeds:
```
(define-private (total-assets)
  (let ((current-assets (var-get assets))
        (debt (total-debt))
        (borrowed (var-get total-borrowed))
        (interest (if (> debt borrowed) (- debt borrowed) u0)))
    (+ current-assets interest)))
``` [3](#0-2) 

`total-assets`/`total-assets-preview` are the denominators used to price zToken shares on every deposit and redemption:
```
(define-private (convert-to-shares-preview (amount uint))
  (let ((ta (total-assets-preview)) (ts (total-supply-preview))) ...))
(define-private (convert-to-assets-preview (amount uint))
  (let ((ta (total-assets-preview)) (ts (total-supply-preview))) ...))
``` [4](#0-3) 

So one borrower's `repay` transaction (Borrower A, the attacker/unwitting cause) mutates a shared `total-borrowed` value that is subsequently consumed by unrelated LPs depositing/withdrawing (the victims) at a mispriced share rate, and it also mutates the ratio used by the *next* borrower's repay (Borrower B), because `total-borrowed`/`debt` are read again on their turn - an ordering dependence between two unprivileged parties through shared pool state, exactly the shared-index/cache pattern called out as in-scope in the validation rules.

### Impact Explanation
This is not intended risk-sharing (like `socialize-debt`, which is an explicit, bounded, admin/liquidation-triggered loss allocation) - it is a plain accounting bug in the principal/interest split formula that silently and continuously drifts `total-borrowed` away from the true sum of outstanding principal across all borrowers, every time any borrower partially repays. Because `total-assets` (and hence the zToken share price used for every `deposit`/`redeem`) is computed from `total-debt - total-borrowed`, the drift directly misprices LP shares: LPs depositing while `total-borrowed` is inflated get too few shares (their funds are undervalued and effectively transferred to existing/exiting LPs), while LPs depositing while it is deflated get too many shares (diluting other LPs' claims on `assets`). This is a temporary/permanent freezing or mispricing of LP yield depending on drift direction and timing - i.e., theft or freezing of unclaimed yield among LPs caused by ordinary borrower repay activity, which matches the in-scope High impact class (temporary freezing of unclaimed yield, or theft of unclaimed yield via mispriced shares).

### Likelihood Explanation
The bug triggers on every partial repay by any borrower once the vault has multiple borrowers who entered at different index values (a normal, expected operating condition, not a contrived edge case). No privileged action or oracle manipulation is required; any two unprivileged borrowers repaying at different points in the index's growth is sufficient to produce drift, and drift compounds with usage over the life of the vault.

### Recommendation
Do not derive `principal-repaid`/`interest-paid` from the pool-wide `total-borrowed`/`total-debt` ratio applied to an individual's payment. Either (a) eliminate the separate `total-borrowed` nominal-principal tracking entirely and compute `assets`/`total-assets` purely from index-based debt deltas already captured in `accrue` (`debt-delta`), the same way the treasury-fee logic already does, or (b) track each borrower's original principal at the market layer (as the BigBang report's own recommended mitigation suggests: store `debtAsked + openingFee`) and pass the borrower-specific principal down to `system-repay` so the split reflects that borrower's true ratio rather than a pool average.

### Proof of Concept
1. Vault starts empty; Borrower A borrows `1000` at `index = I0`, so `scaled_A = 1000`, `total-borrowed = 1000`, `principal-scaled = 1000`.
2. Time passes, index grows to `I1` such that `total-debt = 1100` (100 accrued interest, all attributable to A).
3. Borrower B borrows `1000` at `index = I1`: `scaled_B = 1000 * I0/I1` (fewer scaled shares for the same nominal amount); `total-borrowed = 2000`; `total-debt = 2100`.
4. Time passes further, index grows again so `total-debt = 2310` (210 more interest: ~190.9 attributable to A's larger balance, ~19.1 to B - proportional to each one's own current debt, not the aggregate).
5. Borrower B repays `capped-amount = 1000` (less than B's true owed debt). `system-repay` computes:
   `principal-repaid = 1000 * total-borrowed(2000) / debt(2310) ≈ 865.8`
   `interest-paid = 1000 - 865.8 ≈ 134.2`
   but B's individual true accrued interest at this point is only ~`19.1` of the ~`1019.1` they owe so far - the formula attributes roughly `134.2` as "interest" for B's payment when B has not actually generated that much interest, using instead the blended average dominated by A's larger accrued interest.
6. `total-borrowed` is decremented by only `865.8` instead of the ~`980.9` that reflects B's true remaining principal, permanently skewing `total-borrowed` relative to the real aggregate principal still owed by A and B combined.
7. Any LP calling `deposit`/`redeem` immediately after step 5 receives a share price computed from the now-skewed `total-assets = assets + (debt - total-borrowed)`, which no longer reflects the true backing value of the pool, causing that LP to receive an incorrect number of zTokens relative to LPs who transacted before or after the drift-inducing repay - a value transfer between two unprivileged LPs mediated purely by Borrower B's repay ordering.
