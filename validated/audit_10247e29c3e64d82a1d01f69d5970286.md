### Title
Webhook signature verification is keyed by attacker-controlled `repository.owner.login` while the acted-upon repository is selected by a separately attacker-controlled `repository.full_name`, allowing cross-tenant forged pushes to trigger `sync_github` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` resolves which GitHub App/organization config (and thus which `webhook_secret`) to check the HMAC signature against using `repository_owner` (`params.dig('repository','owner','login')`), a value taken verbatim from the unauthenticated JSON body. `Handler#stacks` (used by `PushHandler#process`) independently resolves the target `Repository`/`Stack` using `payload.dig('repository','full_name')`, also taken verbatim from the same body. Because these two fields are never checked for consistency, an attacker who controls an organization/app config with no `webhook_secret` set (or who simply owns any configured org) can set `repository.owner.login` to that org while setting `repository.full_name` to a victim org/repo, causing `verify_webhook_signature` to pass trivially against the attacker's own (secret-less) config while the handler acts on the victim's stack.

### Finding Description
The broken binding, stated as an equality that must hold but does not: `repository_owner (used to select verification config)` must equal `owner_of(repository.full_name) (used to select the acted-upon Repository/Stack)`. In this codebase they are two independent reads of the same untrusted JSON payload with no cross-check.

Code path:
- `WebhooksController#create` parses the raw body once (`JSON.parse(request.raw_post)`) and hands it to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` — [1](#0-0) .
- Before `create` runs, `verify_signature` computes `github_app = Shipit.github(organization: repository_owner)` and calls `github_app.verify_webhook_signature(...)`, where `repository_owner` is `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` — [2](#0-1) [3](#0-2) .
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally if that organization's `webhook_secret` is blank: `return true unless webhook_secret` — [4](#0-3) .
- `Shipit.github(organization:)` looks up the config purely by the `organization` argument passed in (i.e., the attacker-supplied `repository_owner`), via `github_app_config(organization)` — [5](#0-4) [6](#0-5) .
- Independently, `Handler#stacks` resolves the affected repository/stacks using `repository_name = payload.dig('repository', 'full_name')`, a different field from the same payload — [7](#0-6) .
- `PushHandler#process` calls `stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }` — [8](#0-7) .

Exploit flow: attacker sends `POST /webhooks` with header `X-Github-Event: push`, body `repository.owner.login = "attacker-org"` (an org either configured in Shipit with no `webhook_secret`, or any org the attacker can get onboarded as an organization in the multi-tenant `github` config with a blank secret), and `repository.full_name = "victim-org/victim-repo"`, `ref = "refs/heads/production"`, `after = "0"*40`. `verify_signature` calls `Shipit.github(organization: "attacker-org")`, which finds attacker-org's config (secret-less) and returns `true` immediately from `verify_webhook_signature` without ever computing/comparing an HMAC. `check_if_ping` and `drop_unhandled_event` both pass since event is `push` and a `PushHandler` exists. `PushHandler#process` then resolves `stacks` via `victim-org/victim-repo` and calls `sync_github(expected_head_sha:)` on the victim's `production` stack.

Why existing guards fail: `drop_unhandled_event`/`check_if_ping` only gate on event type, not repository identity. `verify_signature` authenticates only that *some* organization's secret matches (or that organization has no secret at all) — it never authenticates that the acting organization equals the owner of the repository the handler subsequently touches. `ExplicitParameters` schemas (`requires :ref; requires :after` in `PushHandler`) validate shape, not provenance/authorization. There is no model validation or controller check tying `repository.owner.login` to `repository.full_name`'s owner segment.

### Impact Explanation
This lets an attacker who controls (or can register/onboard) any organization in Shipit's multi-tenant `github` secrets config with a blank `webhook_secret` forge push events that are accepted as validly-signed for *any other tenant's repository*, purely by changing `repository.full_name` in the JSON body. If the targeted victim stack has `continuous_deployment` enabled, this can drive `Stack#sync_github` (and downstream fetch/deploy machinery) for the victim's branch/stack without ever presenting the victim's actual `webhook_secret`. This is a cross-tenant repository/stack action triggered by an unauthenticated-for-that-tenant request — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team" and, contingent on the victim's deploy pipeline configuration, potentially an unauthorized deploy. The blast radius spans every repository/stack configured under any organization whose `webhook_secret` is unset, and is repeatable per request with different `full_name`/`ref`/`after` values.

### Likelihood Explanation
This requires Shipit to be configured in the multi-tenant `github` mode (organization-keyed secrets) with at least one organization entry that has no `webhook_secret` set, and requires the attacker to be able to name that organization as `repository.owner.login` in their POST (no possession of any real secret needed) — I could not fully confirm from the available code how organizations are provisioned/added to this config or whether operators are expected to always set a `webhook_secret` per org; that provisioning/admin path was outside what I could trace here. If a single-tenant (top-level `github` key) config is used instead, `github_default_organization` is `nil`, and `Shipit.github(organization: repository_owner)` still resolves to the single (default) `secrets.github` config regardless of `organization`, so `repository_owner` doesn't select a config at all in that mode — meaning this specific divergence is most exploitable in multi-tenant mode with a secret-less org entry. Attacker cost is a single unauthenticated HTTP POST; the technique is repeatable against arbitrary victim stacks by varying `full_name`.

### Recommendation
Cross-validate that `repository.owner.login` (used to select the verifying GitHub App/secret) matches the owner segment of `repository.full_name` (used by handlers to select the target `Repository`), rejecting the webhook (422) on mismatch. Additionally, do not allow `verify_webhook_signature` to short-circuit to `true` for organizations lacking a `webhook_secret` unless that is an explicit, intentional opt-out documented and restricted to non-multi-tenant deployments.

### Proof of Concept
minitest plan (`test/controllers/webhooks_controller_test.rb`-style, no live GitHub):
1. Configure `Shipit.stubs(:secrets)` (or equivalent credential stub) with a multi-tenant `github` config containing `attacker_org: { app_id:, installation_id:, private_key: ... }` (no `webhook_secret` key) and `victim_org: { webhook_secret: 'realsecret', ... }`.
2. Create a victim `Stack` with `repository` `full_name = "victim_org/victim_repo"`, `branch = "production"`, `continuous_deployment` enabled (or stub `Stack#sync_github` to assert it is called with `expected_head_sha: "0"*40`).
3. POST to `/webhooks` with header `X-Github-Event: push`, no `X-Hub-Signature` (or an arbitrary bogus one), and JSON body: `{"repository": {"owner": {"login": "attacker_org"}, "full_name": "victim_org/victim_repo"}, "ref": "refs/heads/production", "after": "0"*40}`.
4. Assert response is `200 OK` (not `422`), proving `verify_signature` passed via `attacker_org`'s config.
5. Assert `Stack#sync_github` was invoked on the victim stack instance with `expected_head_sha: "0"*40` — i.e., assert equality failure between `repository_owner ("attacker_org")` and the owner segment of `repository.full_name` ("victim_org") did NOT block execution, demonstrating the binding is broken.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end
```
