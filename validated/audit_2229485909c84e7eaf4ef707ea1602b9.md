### Title
`ReopenedHandler#unarchive?` reuses the same `&&`/`||` precedence flaw as `OpenedHandler#provision?`, letting `review_stacks_enabled=false` repositories be re-provisioned on PR reopen - ([File: app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb])

### Summary
`ReopenedHandler#unarchive?` (the reopen-event analogue of `OpenedHandler#provision?`) uses the identical unparenthesized boolean expression, so Ruby's `&&`-before-`||` precedence detaches `repository.review_stacks_enabled` from the `allow_with_label` and `prevent_with_label` branches. A repository owner who has explicitly disabled review stacks (`review_stacks_enabled = false`) but left `provisioning_behavior = allow_with_label` still gets a review stack created/unarchived whenever an unprivileged contributor labels and reopens a PR.

### Finding Description
The intended binding is: `unarchive_allowed == (review_stacks_enabled && <behavior-specific gate>)`. The actual code is: [1](#0-0) 

```ruby
def unarchive?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

Because `&&` binds tighter than `||`, this parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`. `review_stacks_enabled` only gates the `allow_all` branch; it is never consulted for the `allow_with_label` or `prevent_with_label` branches. This is the exact same defect already present in `OpenedHandler#provision?`: [2](#0-1) 

**Path**: An attacker who owns a fork/branch of a repository configured with `provisioning_behavior = allow_with_label` and `review_stacks_enabled = false` opens a PR, applies the provisioning label (self-service, no privilege needed) to a PR, closes it, then reopens it. `process` calls `respond_to_pull_request_reopened?` → `unarchive?`, which evaluates true despite `review_stacks_enabled == false`, and calls `stack.unarchive!`: [3](#0-2) 

`ReviewStackAdapter#unarchive!` either creates a brand-new `ReviewStack` (`create!`, which calls `Shipit::ReviewStackProvisioningQueue.add(stack)`) if none exists, or re-enqueues an existing archived stack for provisioning: [4](#0-3) 

The provisioning queue's worker then invokes the repository/stack's `ProvisioningHandler`, which drives real infrastructure actions: [5](#0-4) 

No existing guard intercepts this: `respond_to_pull_request_reopened?` only checks `params.action == "reopened"`, webhook signature verification and param schema validation only confirm the payload shape/origin of GitHub events, not the semantics of `review_stacks_enabled`; none of those layers re-derive or clamp the `unarchive?`/`provision?` decision.

### Impact Explanation
Any GitHub user capable of opening/labeling/closing/reopening a PR against a targeted repository can force review-stack provisioning (creation of a `ReviewStack`, `enqueue_for_provisioning`, and eventual `provisioner.provision`) on a repository whose administrator explicitly disabled review-stack provisioning (`review_stacks_enabled = false`). This is an unauthorized-provisioning/deploy-adjacent action performed against a repository's declared configuration, repeatable indefinitely per PR (close/reopen cycle) and across every PR opened against that repository — the blast radius is scoped to repositories using `allow_with_label`/`prevent_with_label` with `review_stacks_enabled` disabled, but is fully repeatable within that scope, matching the "unauthorized deploy" class of impact once provisioning executes attacker-influenced branch/environment configuration.

### Likelihood Explanation
Preconditions: target repository must set `provisioning_behavior` to `allow_with_label` (or `prevent_with_label`) while `review_stacks_enabled = false` — a plausible misconfiguration/transition state (e.g., an operator disabling the feature flag without also reverting `provisioning_behavior`). Attacker cost is trivial: open a PR, add the configured label, close, reopen — all self-service GitHub actions requiring no Shipit credentials. The bug is deterministic and 100% reproducible whenever the precondition config holds.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates every branch:
```ruby
def unarchive?
  repository.review_stacks_enabled && (
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
  )
end
```
Apply the same fix to `OpenedHandler#provision?`, and audit other handlers (`labeled_handler.rb`, `unlabeled_handler.rb`, `closed_handler.rb`) for the identical pattern.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/pull_request/reopened_handler_test.rb`):
```ruby
test "does not unarchive/create a review stack when review_stacks_enabled is false, even with allow_with_label + label" do
  repository = shipit_repositories(:shipit)
  repository.update!(
    review_stacks_enabled: false,
    provisioning_behavior: :allow_with_label,
    provisioning_label_name: "pull-requests-label"
  )

  payload = payload_parsed(:pull_request_reopened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  # Binding under test: repository.review_stacks_enabled(false) == effective_gate
  assert_equal false, repository.review_stacks_enabled

  assert_no_difference -> { Shipit::ReviewStack.count } do
    ReopenedHandler.new(payload).process
  end
end
```
This test currently fails against the shown `unarchive?` implementation (a `ReviewStack` gets created/enqueued despite `review_stacks_enabled == false`), demonstrating the broken binding.
