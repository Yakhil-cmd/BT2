### Title
Status webhook is matched by `sha` alone with no repository binding, letting an attacker's own repo trigger `Hook.emit(:commit_status, ...)` and `schedule_continuous_delivery` on an unrelated victim stack - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)`, which has no filter on the webhook's `repository.full_name`, unlike every other handler that scopes work through `Handler#stacks` (`Repository.from_github_repo_name(repository_name)`). Because commit shas are shared across forks/shared history, an attacker who owns a repository registered under an org Shipit trusts can send a signed `status` webhook whose `sha` happens to match a `Commit` row belonging to a completely different, victim-owned stack, causing `Commit#add_status` to run and `Hook.emit(:commit_status, victim_stack, ...)` / `Commit#schedule_continuous_delivery` to fire for that victim stack.

### Finding Description
Binding that should hold: `payload['repository']['full_name'] == stack.repository.full_name` for every `Commit` mutated by a `status` webhook. In code, this binding is enforced in most handlers via [1](#0-0) , which derives `stacks` strictly from the payload's own `repository.full_name`. `StatusHandler`, however, bypasses this entirely: [2](#0-1) 

`Commit.where(sha: params.sha)` matches every `Commit` row in the entire `commits` table sharing that sha, regardless of which stack/repository it belongs to. Each matched commit then runs `create_status_from_github!` → `add_status`, where the `already_deployed` gate is computed from that specific commit/stack pair, correctly reflecting deploy state of the *matched* stack - [3](#0-2) . The gate itself is not broken in isolation, but it operates on a `Commit`/`stack` pair that was never authenticated as belonging to the requesting repository. `schedule_continuous_delivery` is invoked from `Status#schedule_continuous_delivery` via an `after_commit` callback on `Status` creation - [4](#0-3) [5](#0-4)  - and `Commit#schedule_continuous_delivery` reads `stack.continuous_deployment?`/`stack.deployable?` of that matched stack - [6](#0-5) .

Exploit flow:
1. Attacker controls/pushes to `attacker/repoA`, a repository belonging to a GitHub organization already integrated with Shipit (so `Shipit.github(organization: repository_owner)` resolves and `verify_webhook_signature` passes for their own repo's legitimately signed event) - [7](#0-6) .
2. Attacker forks or otherwise shares git history with `victim/repoB` (fork commit shas are identical to upstream shas), or otherwise causes a `Commit` row with the shared sha to exist for `victim/repoB`'s stack.
3. Attacker sends (or GitHub sends on their behalf) a `status` webhook for `attacker/repoA` referencing that shared `sha`.
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, which returns the `victim/repoB` `Commit` too, and calls `create_status_from_github!` on it, emitting `Hook.emit(:commit_status, victim_stack, ...)` and scheduling `ContinuousDeliveryJob` for `victim_stack`.

Existing guards do not catch this: `verify_signature` only checks the signature belongs to the *sender's own* org, not that the payload's repository matches the target commit's stack; `drop_unhandled_event` only checks the event type is handled; the `ExplicitParameters` schema for `StatusHandler` never declares/uses `repository` at all - [8](#0-7)  - so there is no per-repository scoping opportunity even if one wanted to add it downstream.

### Impact Explanation
A payload signed for one repository (`attacker/repoA`) causes a database write (`Status` creation) and side effects (`Hook.emit`, `ContinuousDeliveryJob` scheduling) against a different repository's stack (`victim/repoB`) that never authenticated the request. This matches the Critical category "a payload for one repository mutating another's stack, commit, task or team" and can lead to unauthorized/premature continuous deployment being scheduled for a victim stack. It is repeatable against any stack that shares commit shas with an attacker-controlled repository (most straightforwardly via forks), and generalizes across any two repos/stacks with overlapping commit history.

### Likelihood Explanation
Preconditions: attacker needs a repository under a GitHub org already configured in Shipit (so webhook signature validation succeeds), continuous_deployment enabled on the victim stack, and a shared commit sha between attacker's repo and the victim's tracked commit (trivially achieved by forking the victim's repository, which is a normal unprivileged GitHub action). No Shipit session, API token, or secrets are required beyond what an ordinary GitHub webhook sender already has for their own repo. This is realistically exploitable and repeatable per shared-sha commit.

### Recommendation
Scope `StatusHandler#process` (and any other sha-keyed handler) to only touch commits belonging to stacks resolved from the payload's own `repository.full_name`, mirroring `Handler#stacks`: e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or filter `Commit.where(sha: params.sha)` by `stack_id: stacks.select(:id)` before calling `create_status_from_github!`.

### Proof of Concept
Minitest plan (in `test/models/shipit/webhooks/handlers/status_handler_test.rb` or controller test):
1. Create `victim_stack` with `continuous_deployment: true` and a `Commit` `victim_commit` with `sha: SHARED_SHA`, undeployed (`victim_stack.last_deployed_commit.id < victim_commit.id`).
2. Create a second stack `attacker_stack` tied to repository `attacker/repoA`, with its own `Commit` also having `sha: SHARED_SHA` (simulating shared fork history), or directly stub `Commit.where(sha: SHARED_SHA)` to return both commits to demonstrate the lack of scoping.
3. Send a `status` event payload with `repository: { full_name: 'attacker/repoA' }` and `sha: SHARED_SHA`.
4. Assert: `Hook.expects(:emit).with(:commit_status, victim_stack, ...)` fires (binding check: assert the emitted stack's repository is NOT `attacker/repoA`), and `assert_enqueued_with(job: ContinuousDeliveryJob, args: [victim_stack])`.
5. Compare both sides of the binding explicitly: `payload['repository']['full_name']` (`'attacker/repoA'`) vs. `victim_stack.repository.full_name` (`'victim/repoB'`) — assert they differ while the hook/job still fired for `victim_stack`, proving the divergence.
