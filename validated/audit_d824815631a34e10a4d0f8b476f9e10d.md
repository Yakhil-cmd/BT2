### Title
Grindable pseudo-randomness in oscript `number_from_seed()` allows AA trigger senders to bias lottery/game outcomes - ([File: formula/evaluation.js])

### Summary
The oscript function `number_from_seed()` derives a "random" value deterministically from a `sha256` of an author-supplied seed [1](#0-0) . AA developers commonly use trigger-controlled values (e.g. `trigger.unit`, `trigger.data`, or a combination) as this seed to build gambling/lottery/game-of-chance AAs, exactly as illustrated by the `51_attack_game.oscript` and `fundraising_proxy.oscript` samples that make probabilistic/threshold decisions from trigger-supplied inputs [2](#0-1) . Because `trigger.unit` is the hash of the very unit the caller is about to post, and `trigger.data` is fully attacker-chosen, an unprivileged AA trigger sender can compute the resulting "random" outcome locally before broadcasting, and simply discard/regenerate the candidate unit (by varying a nonce field in `trigger.data`, timestamp, or parent selection) until the derived seed yields a favorable result, then only ever post the favorable one.

### Finding Description
`number_from_seed` is implemented as `sha256(seed) -> Decimal in [0,1) or [min,max]` with no on-chain commit-reveal, VRF, or external unpredictable entropy requirement [3](#0-2) . The formula validator only restricts argument count/types (`formula/validation.js` `case 'number_from_seed'`) but does not forbid or warn against using attacker-known values such as `trigger.unit` or `trigger.data` as the seed [4](#0-3) . `trigger.unit` and `trigger.data` are both directly derived from the unit the caller composes and signs themselves [5](#0-4) , and `getTrigger()` in `aa_composer.js` populates them straight from the posted unit's `unit` field and `data` message with no server-side randomization [6](#0-5) . Since the unit content (and therefore its hash) is fully known to the composer before it is broadcast, the sender can locally simulate the AA formula for many candidate units (cheaply, off-chain) and only submit the one unit whose derived "random" number favors them, exactly mirroring the reported YOLOv2 pattern where an attacker computes/observes conditions before committing to the action that determines the "winning" outcome.

### Impact Explanation
Any AA that implements a lottery, dice game, raffle, or randomized payout using `number_from_seed()` seeded (directly or indirectly) by trigger-controlled data can be gamed by any unprivileged caller who grinds candidate units off-chain and only posts the favorable one, guaranteeing a "win" or biasing payout distribution in their favor. This causes AA fund loss for the AA's balance/other participants and breaks the fairness guarantee of any on-chain game built this way — a direct financial loss vector for AAs, analogous in class (though not code) to the underlying report's economic exploitation of a probabilistic mechanism via cheap pre-computation/selective commitment.

### Likelihood Explanation
Any AA author who follows the documented `number_from_seed` pattern with trigger-derived seeds is exposed, and grinding candidate units locally costs nothing but computation time (fees are only paid on the unit that is actually broadcast). This is a design footgun inherent to the oscript randomness primitive rather than a rare edge case, and it is directly reachable by any unprivileged AA trigger sender, matching the "unprivileged unit poster / AA trigger sender" reachability required.

### Recommendation
- Do not allow (or strongly discourage via linting/validation) using purely trigger-controlled values (`trigger.unit`, `trigger.data`) as the sole seed to `number_from_seed()`. 
- Provide/encourage a commit-reveal or externally-supplied unpredictable entropy source (e.g., a future stable unit hash unknown at trigger-composition time, or an oracle-provided value) for randomness, mirroring the recommendation in the source report to raise the cost of gaming the outcome rather than relying on attacker-controllable inputs.
- Add documentation/warnings in `formula/validation.js` for `number_from_seed` flagging seeds that are fully derived from `trigger.*` fields as unsafe for adversarial contexts.

### Proof of Concept
1. Deploy an AA that pays out based on `number_from_seed(trigger.unit)` or `number_from_seed(trigger.data.nonce)` exceeding some threshold (as in typical lottery AA patterns).
2. Attacker composes a batch of candidate trigger units locally, varying `trigger.data.nonce` (or timestamp/parents affecting `trigger.unit`), without broadcasting.
3. For each candidate, attacker computes `sha256(seed)` exactly as `formula/evaluation.js` `case 'number_from_seed'` does [3](#0-2)  to predict the AA's decision/payout.
4. Attacker signs and broadcasts only the candidate unit whose predicted outcome is favorable, guaranteeing a win/large payout while other participants' outcomes remain genuinely random.

function getTrigger(objUnit, receiving_address) {
	var trigger = { address: objUnit.authors[0].address, unit: objUnit.unit, outputs: {} };
	if ("max_aa_responses" in objUnit)
		trigger.max_aa_responses = objUnit.max_aa_responses;
	objUnit.messages.forEach(function (message) {
		if (message.app === 'data' && !trigger.data) // use the first data message, ignore the subsequent ones
			trigger.data = message.payload;
		else if (message.app === 'payment' && message.payload) {
			var payload = message.payload;
			var asset = payload.asset || 'base';
			payload.outputs.forEach(function (output) {
				if (output.address === receiving_address) {
					if (!trigger.outputs[asset])
						trigger.outputs[asset] = 0;
					trigger.outputs[asset] += output.amount; // in case there are several outputs
				}
			});
		}
	});
	if (Object.keys(trigger.outputs).length === 0)
		throw Error("no outputs to " + receiving_address);
	return trigger;
}
