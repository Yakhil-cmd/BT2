### Title
Webhook signature is verified against the organization derived from `repository.owner.login`, but events are applied to the repository named in `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's webhook secret to validate the HMAC signature against by reading `repository.owner.login` (falling back to `organization.login`) out of the untrusted JSON payload. Once the signature check passes, every event `Handler` locates the `Stack`/`Repository` to mutate using a *different* field from the same payload: `repository.full_name`. Because these two fields are never cross-checked, a payload can be crafted so that the signature validates against Organization A's secret while the actual side effects (push sync, CI status, PR/merge-queue transitions) are applied to a completely different repository "B".

### Finding Description
`verify_signature` computes the signing organization purely from payload content: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
```

with [2](#0-1) 

```ruby
def repository_owner
  # Fallback to the organization sub-object if repository isn't included in the payload
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

Every event handler, however, resolves the target `Stack` using an entirely independent field of the very same payload: [3](#0-2) 

```ruby
private

def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

There is no code path enforcing `repository.owner.login == repository.full_name.split('/').first`. The equality the security model relies on - "the organization whose secret authenticated the request" == "the organization that owns the repository being written to" - is never asserted.

Since `Shipit.github(organization:)` resolves per-organization webhook secrets, and an attacker who administers *any* GitHub organization onboarded to the same Shipit instance necessarily knows (or configured) that organization's own webhook secret, they can produce a validly-signed payload for their own org while placing an arbitrary victim `owner/repo` in `repository.full_name`.

### Impact Explanation
Any handler that mutates state based on `repository.full_name` becomes forgeable for repositories the attacker does not control, once they have valid signing credentials for *any* onboarded organization:
- `PushHandler`/`StatusHandler`/`CheckSuiteHandler` can inject forged commit statuses / CI results for the victim stack's commits, which feed directly into `Shipit::Status::Group` and `MergeRequest#any_status_checks_failed?` / `all_status_checks_passed?` used to gate the merge queue and deploy readiness [4](#0-3) .
- Forged "success" statuses can clear required CI checks and unblock an unauthorized merge (`MergeRequest#merge!`) or deploy for a repository the attacker never had write access to.

This crosses the "unauthorized deploy/merge" boundary described as Critical impact, because the attacker is spoofing another organization's trusted GitHub event stream using credentials scoped to their own organization only.

### Likelihood Explanation
Likelihood is constrained by the precondition that the attacker must already be an authenticated party for *some* organization/repo hooked into the same Shipit instance (i.e., know that org's `webhook_secret`, which they would if they are an admin who configured the GitHub App/webhook themselves). Given that precondition, forging the payload requires no further privilege - it is a simple JSON field substitution, and no code anywhere cross-validates the two repository references.

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler`), assert that the organization used to select the webhook secret matches the owner of `repository.full_name` before dispatching to handlers, e.g.:

```ruby
def verify_signature
  owner_from_repo = params.dig('repository', 'full_name')&.split('/', 2)&.first
  head(422) and return if owner_from_repo && owner_from_repo != repository_owner
  ...
end
```

or have `Handler#stacks` reject any repository whose owner does not match the organization that was used to validate the signature.

### Proof of Concept
1. Attacker administers `attacker-org/some-repo`, which is legitimately registered with this Shipit instance, and therefore knows `attacker-org`'s configured `webhook_secret`.
2. Attacker crafts a `status` (or `push`) webhook payload:
   ```json
   {
     "organization": { "login": "attacker-org" },
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
     "sha": "<victim commit sha>",
     "state": "success",
     "context": "ci/circleci"
   }
   ```
3. Attacker computes `X-Hub-Signature` using `attacker-org`'s webhook secret and `POST`s it to `/webhooks`.
4. `verify_signature` calls `Shipit.github(organization: 'attacker-org')` and validates the signature successfully (`app/controllers/shipit/webhooks_controller.rb:24-30`).
5. `Shipit::Webhooks.for_event('status')` dispatches to the status handler, which uses `payload.dig('repository', 'full_name')` = `"victim-org/victim-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`) to locate the victim's `Stack` and records a forged successful CI status for the victim's commit, satisfying `required_statuses` and unblocking merge/deploy for a repository the attacker never had access to.
