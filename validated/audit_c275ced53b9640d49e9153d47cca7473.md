### Title
Attacker-controlled swap routes can steal unrelated wallet tokens through the caller's authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
Controller strategy entrypoints accept attacker-supplied opaque route bytes and pass them directly into the configured router during `swap_collateral`, `swap_debt`, `multiply`, and `repay_debt_with_collateral` flows. [1](#0-0)  A malicious route venue can execute token transfers from the transaction signer to an attacker while still returning valid swap output. [2](#0-1)  The controller validates only its own input spend, output receipt, and final account risk, so it does not bound unrelated transfers recorded under the caller's authorization tree. [3](#0-2) 

### Finding Description
`swap_tokens` requires only that `swap` is non-empty before forwarding the bytes to `router.execute_strategy`. [1](#0-0)  The controller protects its own input by authorizing one exact transfer to the router, but that authorization does not prevent route-selected code from invoking an unrelated token transfer that requires the user's authorization. [4](#0-3) 

The repository's threat model explicitly documents that route venues are not allowlisted and that code reached through the route can place a malicious token transfer beneath the caller's authorization entry. [2](#0-1)  A dedicated harness test models a route through an attacker-controlled pool whose `swap` implementation transfers an unrelated wallet token from the victim to the attacker. [5](#0-4) 

### Impact Explanation
A victim who submits an attacker-crafted route and signs the generated authorization tree can lose assets unrelated to the lending transaction, up to the victim's balance in any token contract reachable by the malicious venue. [6](#0-5)  The malicious route can still return valid output, so the lending operation succeeds while the unrelated token is drained. [7](#0-6) 

This is theft of user funds rather than a route-quality issue because the loss is not limited to the swap input and is not caused by slippage or an unfavorable exchange rate. [2](#0-1) 

### Likelihood Explanation
Exploitation requires the victim to use a malicious route payload and sign the simulation-generated authorization tree containing the rogue transfer. [8](#0-7)  Route bytes are opaque to ordinary users, and an honest-looking transaction can satisfy all controller settlement checks while including the extra signed child invocation. [3](#0-2)  The precondition is therefore user interaction rather than privileged access, making the issue reachable by any unprivileged attacker who can supply a route to a user. [9](#0-8) 

### Recommendation
Restrict route execution to governance-approved venue contracts instead of allowing payload-selected pool addresses. [10](#0-9)  Until venue allowlisting is deployed, transaction builders and wallets should decode the complete authorization tree and reject any child invocation other than the expected input-token transfer or router-authorized calls. [11](#0-10)  Clients should also decode the route payload itself and compare every venue address against trusted pool metadata before signing. [12](#0-11) 

### Proof of Concept
An attacker deploys a contract that implements the selected venue's expected swap ABI but additionally calls `token.transfer(victim, attacker, amount)` during the route execution. [13](#0-12)  The attacker supplies route bytes naming that contract as a hop pool, while configuring the route to return sufficient legitimate output for the victim's `swap_collateral` call. [14](#0-13) 

During simulation, the rogue transfer is recorded as a child invocation beneath the victim's controller authorization. [15](#0-14)  If the victim signs that tree, the unrelated wallet token moves to the attacker while the victim still receives the expected swap collateral. [8](#0-7)

## Authorization model

The only signature is the sender's. `execute_strategy` calls `sender.require_auth()`, and the sender's auth entry must cover the nested `token_in.transfer(sender, router, total_in)`; simulation produces that tree (`transaction.simulated = true` envelopes already carry it — `attach_simulated_transaction` copies the simulator's `auth` into the op — and `simulateTransaction` produces it for a locally built one). Do **not** `transfer` or `approve` tokens to the router beforehand: the router pulls the input itself, and tokens sent ahead of time are not credited.

Every venue call is self-authorized by the router with invoker-contract auth (`venues/auth.rs::authorize_as_current` → `env.authorize_as_current_contract`): Phoenix and Sushi (`HopContext::authorize_pool_pull`) and Aquarius (`aquarius/pool.rs::invoke_pool_swap`) register `token_in.transfer(router, pool, amount_in)` before the pool pulls; Comet registers `token_in.approve(router, pool, amount_in, expiry)`, then `swap_exact_amount_in` with a nested entry for the pool's `transfer_from`, then clears the allowance; Soroswap transfers from the router to the pool directly. None of these appear in the sender's auth tree.

A contract calling the router (the lending controller in `contracts/controller/src/strategies/swap.rs`, or your own) is the `sender`: it runs `authorize_transfer_as_current(token_in, self, router, amount_in)` (`common/src/token.rs`) immediately before `execute_strategy(self, amount_in, swap)` and measures its own balance deltas afterward (`RouterOverspend = 501`, `NoSwapOutput = 502` in `common/src/errors.rs`). Details in [composition.md](composition.md).
