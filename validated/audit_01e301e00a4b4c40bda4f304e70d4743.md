### Title
Service-Chain Bridge Sends Stale Genesis KIP71 Config Instead of Live Governance Values, Causing Wrong Gas Price on Bridge Transactions — (`File: node/sc/main_bridge_handler.go`)

### Summary

`handleServiceChainParentChainInfoRequestMsg` in the main bridge handler reads KIP71 fee parameters directly from the static genesis `ChainConfig` instead of the live governance module. Because KIP71 parameters (`LowerBoundBaseFee`, `UpperBoundBaseFee`, `GasTarget`, `MaxBlockGasUsedForBaseFee`, `BaseFeeDenominator`) are mutable governance parameters that can be changed via on-chain votes, the child chain receives and permanently caches stale values, causing it to compute wrong gas prices for all bridge operator transactions on the parent chain.

### Finding Description

In `node/sc/main_bridge_handler.go`, `handleServiceChainParentChainInfoRequestMsg` responds to the child chain's info request by building a `parentChainInfo` struct:

```go
chainCfg := mbh.mainbridge.blockchain.Config()   // ← genesis-time, never updated
pcInfo := parentChainInfo{
    nonce,
    mbh.mainbridge.txPool.GasPrice().Uint64(),
    params.KIP71Config{
        LowerBoundBaseFee:         chainCfg.Governance.KIP71.LowerBoundBaseFee,
        UpperBoundBaseFee:         chainCfg.Governance.KIP71.UpperBoundBaseFee,
        GasTarget:                 chainCfg.Governance.KIP71.GasTarget,
        MaxBlockGasUsedForBaseFee: chainCfg.Governance.KIP71.MaxBlockGasUsedForBaseFee,
        BaseFeeDenominator:        chainCfg.Governance.KIP71.BaseFeeDenominator,
    },
    ...
}
``` [1](#0-0) 

`blockchain.Config()` returns the `ChainConfig` that was committed at genesis and is never updated by governance votes. The authoritative, live source for KIP71 parameters is the governance module's `GetParamSet(blockNum)`, which is used correctly everywhere else in the codebase (e.g., `node/cn/gasprice/feehistory.go`, `node/cn/gasprice/gasprice.go`). [2](#0-1) 

KIP71 parameters are explicitly mutable governance parameters. They are registered in the governance parameter registry and can be changed by governance votes at any time: [3](#0-2) 

The child chain receives this stale `parentChainInfo` and in `setRemoteChainValues` immediately sets its bridge operator gas price to the stale `UpperBoundBaseFee`:

```go
if pcInfo.IsMagmaEnabled {
    sbh.remoteGasPrice = pcInfo.KIP71Config.UpperBoundBaseFee  // stale genesis value
    sbh.subbridge.bridgeAccounts.SetParentKIP71Config(pcInfo.KIP71Config)
``` [4](#0-3) 

This stale `KIP71Config` is then stored in `BridgeAccounts.pAccount.kip71Config` and used for all subsequent parent-chain gas price calculations by the bridge operator. [5](#0-4) 

### Impact Explanation

After any governance vote changes a KIP71 parameter on the parent chain:

1. **If `UpperBoundBaseFee` is lowered by governance** (e.g., from 750 Gkei to 100 Gkei): the child chain continues to use 750 Gkei as its bridge operator gas price, overpaying by up to 7.5× on every bridge transaction. This drains KAIA from the bridge operator account at an accelerated rate.

2. **If `UpperBoundBaseFee` is raised by governance** (e.g., from 750 Gkei to 1500 Gkei) and the actual parent-chain baseFee rises above the stale 750 Gkei: the child chain sets its gas price below the minimum required baseFee, causing all bridge operator transactions to be rejected by the parent chain's txpool. This halts the bridge entirely — no value transfers, no anchoring.

3. **If `LowerBoundBaseFee`, `GasTarget`, `MaxBlockGasUsedForBaseFee`, or `BaseFeeDenominator` are changed**: the child chain's internal base-fee prediction for parent-chain transactions diverges from reality, compounding the gas price miscalculation.

The corrupted value is `sbh.remoteGasPrice` and `pAccount.kip71Config`, which directly control the gas price attached to every bridge operator transaction that moves bridged assets between chains.

### Likelihood Explanation

The trigger is any governance vote that changes a KIP71 parameter on the parent chain — a normal, permissioned operation available to the governing node. The child chain's `SyncNonceAndGasPrice` is called periodically (every `SyncRequestInterval = 10` blocks) and each time re-reads from the stale genesis config, so the error persists indefinitely after a governance change. No attacker capability is required beyond the governing node exercising its normal governance rights. [6](#0-5) 

### Recommendation

Replace the direct `chainCfg.Governance.KIP71` field access with a call to the governance module's `GetParamSet` at the current block number, mirroring the pattern used in `feehistory.go`:

```go
// Instead of:
chainCfg := mbh.mainbridge.blockchain.Config()
kip71 := chainCfg.Governance.KIP71

// Use:
currentNum := mbh.mainbridge.blockchain.CurrentBlock().NumberU64()
pset := mbh.mainbridge.govModule.GetParamSet(currentNum)
kip71 := pset.ToKip71Config()
```

This requires injecting the governance module into `MainBridge`, consistent with how it is already injected into the gas price oracle. [7](#0-6) 

### Proof of Concept

1. Deploy a parent chain with Magma enabled and default KIP71 config (`UpperBoundBaseFee = 750_000_000_000`).
2. Connect a service chain (child chain) via the bridge. The child chain syncs and sets `remoteGasPrice = 750_000_000_000`.
3. On the parent chain, the governing node votes to lower `kip71.upperboundbasefee` to `100_000_000_000`. The vote is ratified at the next epoch block. The parent chain's live `GetParamSet()` now returns `UpperBoundBaseFee = 100_000_000_000`.
4. The child chain calls `SyncNonceAndGasPrice`, which triggers `handleServiceChainParentChainInfoRequestMsg` on the parent. The parent reads `chainCfg.Governance.KIP71.UpperBoundBaseFee` — still `750_000_000_000` (genesis value) — and sends it to the child.
5. The child chain sets `remoteGasPrice = 750_000_000_000` and submits bridge operator transactions with this gas price, overpaying by 7.5× per transaction. Every bridge value transfer and anchoring transaction drains the bridge operator account at 7.5× the correct rate. [1](#0-0) [4](#0-3)
