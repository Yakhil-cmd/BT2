### Title
Missing cross-check between `repository_owner` (used for HMAC verification) and `organization.login` (used to stamp `Team#organization`) allows cross-org `Team` record forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` picks the org whose secret to verify a webhook against using `repository_owner`, which reads `params.dig('repository','owner','login')` first. `Shipit::Webhooks::Handlers::MembershipHandler#find_or_create_team!` independently trusts `params.organization.login` to set `team.organization` on `Team` creation. These two payload fields are never cross-checked, so a request signed with one organization's secret can create/mutate a `Team` row stamped with a different organization's name.

### Finding Description
The broken binding, stated as an equality that the code implicitly assumes but never enforces:
`repository_owner` (i.e. `params.dig('repository','owner','login')`, the value used to select `Shipit.github(organization: repository_owner)` for HMAC verification) `== params.dig('organization','login')` (the value later trusted by `MembershipHandler` to set `team.organization`).

Code path:
- `before_action :check_if_ping, :drop_unhandled_event, :verify_signature` runs before `create`. `verify_signature` calls `Shipit.github(organization: repository_owner)` and verifies `X-Hub-Signature` against `request.raw_post` using that org's `webhook_secret`. [1](#0-0) 
- `repository_owner` prefers `repository.owner.login` over `organization.login`: [2](#0-1) 
- Once verified, `create` dispatches the raw parsed JSON to registered handlers for the event, unmodified: [3](#0-2) 
- For `membership` events, `MembershipHandler` is invoked, whose `ExplicitParameters` schema only requires `action`, `team`, `organization.login`, `member.login` — it says nothing about `repository`, so an attacker-supplied top-level `repository` key coexists freely with `organization`: [4](#0-3) 
- `find_or_create_team!` looks the `Team` up by `github_id` (an attacker-controlled integer in the payload) and, on creation, stamps `team.organization = params.organization.login` with no comparison to the org that verified the signature: [5](#0-4) 

Attacker request: a multi-tenant Shipit instance configured with per-org secrets in `secrets.github` (confirmed by `Shipit.github(organization:)` supporting multiple orgs, e.g. `test/dummy/config/secrets_double_github_app.yml`) [6](#0-5) . The attacker, who administers `attacker-org`'s GitHub App installation and therefore knows `attacker-org`'s `webhook_secret`, POSTs to `/webhooks` with `X-Github-Event: membership` and a JSON body containing `repository.owner.login = "attacker-org"`, `organization.login = "victim-org"`, an attacker-chosen `team.id`/`slug`/`name`, and `member.login`, signed with `attacker-org`'s secret. `verify_signature` resolves `repository_owner` to `"attacker-org"`, verifies successfully against the attacker's own known secret, and `MembershipHandler` then creates a `Team` with `organization: "victim-org"` and an attacker-chosen `github_id`/`slug`, adding the attacker-controlled `member` to it.

Existing guards do not close this gap: `verify_signature` only authenticates the HMAC against whichever org string appears in `repository.owner.login` (or falls back to `organization.login` only if `repository` is absent) — it never asserts that this org equals `organization.login` used downstream by the handler. `drop_unhandled_event` and `check_if_ping` are unrelated to this check. `ExplicitParameters` on `MembershipHandler` validates the shape of `organization`, `team`, and `member` but does not touch `repository`, so both keys can coexist in one payload without conflict. No model validation on `Team` restricts `organization` to a value tied to the verifying secret.

### Impact Explanation
An unprivileged attacker who only controls their own org's webhook secret can create arbitrary `Team` rows stamped with any `organization` name and add arbitrary members to them, without ever presenting the victim org's secret. If the forged `organization`/`slug` combination happens to match (or is later matched by) an org/team configured in `Shipit.github_teams` (`github.oauth.teams`), the attacker's forged `Team`/`Membership` can be leveraged by `Team.find_or_create_by_handle` (`find_by(organization:, slug:)`) or by future legitimate `github_id`-keyed membership webhooks to affect authorization state, since `User#authorized?` checks membership in `Shipit.github_teams` [7](#0-6)  and `Shipit.github_teams` resolves teams by organization/slug handle [8](#0-7) . At minimum this is a cross-tenant write: a payload authenticated by one organization's secret mutates state (`Team#organization`) attributed to another organization that never authenticated the request — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." The attack is repeatable against any organization name the attacker chooses to put in `organization.login`, for every request signed with the attacker's own secret.

### Likelihood Explanation
Requires a Shipit deployment hosting multiple GitHub organizations with distinct per-org `webhook_secret`s (explicitly a supported, documented configuration via `secrets.github` multi-org maps) and the attacker administering the GitHub App/webhook installation for at least one of those orgs (so they legitimately know that org's `webhook_secret`). No Shipit session, API token, or victim-org secret is needed. The cost is a single crafted HTTP POST with a valid HMAC computed from the attacker's own known secret — trivially repeatable and scriptable.

### Recommendation
In `WebhooksController#verify_signature` (or in each handler), require that `params.dig('organization','login')` (when present) equals `repository_owner`/the org used to select the verifying secret, and reject (422) on mismatch. Additionally, `MembershipHandler#find_or_create_team!` should not trust `params.organization.login` blindly — it should cross-check it against the request's verified organization context (e.g., pass the verified org from the controller into the handler and compare) before stamping `team.organization`.

### Proof of Concept
Minitest plan (add to `test/controllers/webhooks_controller_test.rb`, using the same `Shipit.github(organization: ...).expects(:verify_webhook_signature)` stubbing pattern already used in that file):

1. Configure two orgs with distinct secrets (reuse `test/dummy/config/secrets_double_github_app.yml` pattern or stub `Shipit.secrets` similarly to `test/unit/shipit_test.rb`).
2. Build payload:
   ```ruby
   payload = {
     action: 'added',
     team: { id: 9999, name: 'Forged', slug: 'forged', url: 'https://example.com' },
     organization: { login: 'victim-org' },
     member: { login: 'attacker' },
     repository: { owner: { login: 'attacker-org' } }
   }.to_json
   ```
3. Assert equality-before: `repository_owner` == `'attacker-org'` (the org whose secret verifies) while `params.dig('organization','login')` == `'victim-org'` (the org used to stamp `team.organization`) — i.e. assert they differ, establishing the broken binding.
4. Stub `Shipit.github(organization: 'attacker-org').verify_webhook_signature` to return `true` (simulating attacker's own secret verifying successfully); do NOT stub/allow `Shipit.github(organization: 'victim-org')` to be used for verification at all.
5. `post :create, body: payload, as: :json, headers: { 'X-Github-Event' => 'membership' }`.
6. Assert `response` is `:ok` and:
   ```ruby
   team = Team.find_by(github_id: 9999)
   assert team.present?
   assert_equal 'victim-org', team.organization
   ```
   proving a `Team` was created with `organization == 'victim-org'` even though only `attacker-org`'s secret ever verified the request — confirming the equality check from step 3 still holds broken after the request (repository_owner ≠ organization.login, and no rejection occurred).
