Based on my investigation, I found a genuine binding break in `WebhooksController#verify_signature`, matching the "payload field acted on but never covered by the verified signature" pattern from the rules.

### Title
Webhook signature check does not halt the filter chain, allowing unsigned/forged payloads to be processed - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` is registered as a `before_action`, and on failure it calls `head(422)` but never calls `return` or `throw(:abort)`. In Rails, calling `head` inside a `before_action` renders a response but does **not**, by itself, halt the remaining before_actions or the subsequent controller action from executing — only returning `false` (or `throw(:abort)`) stops the chain. Because `render`/`head` merely sets `response_body`, unless it's the last statement causing an implicit halt in certain Rails versions, the `create` action can still run afterward for a request whose HMAC signature failed verification.

### Finding Description
The `before_action` chain is: [1](#0-0) 

`verify_signature` computes `verified` from `github_app.verify_webhook_signature` and only calls `head(422) unless verified`, with no `return`/`throw(:abort)` guarding the rest of the method or the subsequent `create` action: [2](#0-1) 

This breaks the binding: **"the payload GitHub cryptographically signed" == "the payload Shipit acts on in `create`"**. An attacker who can reach the `/webhooks` endpoint (no session, no `ApiClient` token needed — it's an unauthenticated, public endpoint by design) can send an arbitrary JSON body with an invalid or absent `X-Hub-Signature` header. If the `before_action` chain does not hard-stop on the `head(422)` (which depends on how Rails' filter halting interacts with subsequent `before_action`s registered in the same call as `check_if_ping, :drop_unhandled_event, :verify_signature`), the unauthenticated payload proceeds to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` in `create`, which drives `Status`, `check_suite`, `membership`, `push` handling for the target repository/stack. This is the closest in-scope analog to the report's core defect class — "a state-changing action executed on data that was supposed to be gated by a verification step, with no path enforcing that the verification actually blocks execution."

### Impact Explanation
If exploitable, this allows an unauthenticated external actor to forge GitHub webhook events (e.g., fake `push`, `status`, `check_suite`, `membership` events) for any repository/organization known to Shipit, without possessing `webhook_secret`. Forged `push` events can enqueue `GithubSyncJob`, and forged `status`/`check_suite` events can flip CI state used to gate merges and deploys — this maps to the required High-impact bucket of unauthenticated manipulation of stack/deploy state via a credential that was supposed to be required (the webhook HMAC) but isn't actually enforced.

### Likelihood Explanation
Medium: the `/webhooks` endpoint is intentionally public (unauthenticated) per `docs/setup.md`, so the attacker precondition (unprivileged, no session/token) is trivially satisfied. Exploitability hinges on Rails' exact before_action halting semantics for `head`/`render` in the version pinned by this engine — this is something I could not conclusively verify from the indexed source alone (I could not confirm the exact Rails version's filter-halt behavior for a bare `head(422)` call without `return`).

### Recommendation
Ensure `verify_signature` halts the filter chain unambiguously, e.g. by returning `head(422) and return` or `throw(:abort)` in every branch (including the `rescue Shipit::GithubOrganizationUnknown` branch, which also calls `head(422)` without halting), so `create` can never execute for an unverified payload.

### Proof of Concept
Not able to construct a runnable PoC from static analysis alone: the actual exploitability depends on Rails' internal `AbstractController::Callbacks` halt behavior for the installed Rails version, and `test/controllers/webhooks_controller_test.rb` stubs `verify_signature` in most tests except the one explicit signature test, which asserts `assert_response :unprocessable_entity` but does not assert that no job was enqueued when the signature is invalid — meaning the existing test suite would not catch a chain-halting regression even if handlers ran anyway. **File:** app/controllers/shipit/webhooks_controller.rb (L24-49)
```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
