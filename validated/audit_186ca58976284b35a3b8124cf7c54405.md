### Title
Cross-tenant `check_suite` forgery via organization-fallback signature verification vs. `repository.full_name` handler selection - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`, `app/models/shipit/webhooks/handlers/handler.rb`, `app/models/shipit/webhooks/handlers/check_suite_handler.rb`)

### Summary
`WebhooksController#repository_owner` selects the verifying `GitHubApp` using `params.dig('repository','owner','login') || params.dig('organization','login')`, while `CheckSuiteHandler` (via the shared `Handler#stacks`/`#repository_name`) resolves the target stacks from `payload.dig('repository','full_name')`. These are two independently attacker-set fields in the same JSON body, so an attacker can pass signature verification against one (lenient/known-secret) organization while directing the handler's effects at a completely different, victim repository/stack — including one configured as `production`.

### Finding Description
The broken binding is: **the organization used to verify `X-Hub-Signature` must equal the organization owning the repository whose stacks are mutated.** Concretely:

- `WebhooksController#repository_owner` (`app/controllers/shipit/webhooks_controller.rb:59-62`) reads `repository.owner.login`, falling back to `organization.login` only if `repository.owner.login` is absent.
- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) calls `Shipit.github(organization: repository_owner)` and verifies the HMAC using that organization's `webhook_secret`. Critically, `GitHubApp#verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`) returns `true` unconditionally `unless webhook_secret` — i.e., if the selected organization has no configured secret, verification is a no-op.
- `Handler#stacks`/`#repository_name` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) independently reads `payload.dig('repository','full_name')` — not `params` validated by `CheckSuiteHandler`'s schema (which only requires `check_suite.head_sha`/`head_branch`, `app/models/shipit/webhooks/handlers/check_suite_handler.rb:7-12`) — to resolve `Repository.from_github_repo_name(...)` and thus the `stacks` scope.

Because a JSON body can independently contain `organization.login = "attacker-org"` (or omit `repository.owner.login`) and `repository.full_name = "victim-org/victim-repo"`, the org used for signature verification and the repo used for the handler's DB lookup diverge. If `attacker-org` is a Shipit-configured organization with no `webhook_secret` set (or one the attacker knows), `verify_signature` passes trivially, and `CheckSuiteHandler#process` then executes:
```ruby
stacks.where(branch: params.check_suite.head_branch).each do |stack|
  stack.commits.where(sha: params.check_suite.head_sha).each(&:schedule_refresh_check_runs!)
end
```
against the victim repository's stacks — regardless of the victim's own webhook secret, and regardless of whether that stack is `production`. `drop_unhandled_event`, `ExplicitParameters` schema, and `force_github_authentication`/`User#authorized?` do not intervene, since this is an unauthenticated webhook path with no session/user checks; none of them validate that `repository_owner` (verification selector) equals `repository.full_name`'s owner (handler selector).

### Impact Explanation
The demonstrated effect of `CheckSuiteHandler` is limited: `Commit#schedule_refresh_check_runs!` (`app/models/shipit/commit.rb:152-154`) only enqueues `RefreshCheckRunsJob`, which calls the stack's `github_api.check_runs` (a read-only GitHub API call) and persists the *actual* check-run data pulled from GitHub into `CheckRun` records (`app/jobs/shipit/refresh_check_runs_job.rb`, `app/models/shipit/commit.rb:186-196`). This does not merge, deploy, or roll back anything by itself — it forces a resync of the target commit's real CI status from GitHub. This is a genuine cross-tenant confused-deputy bug (a request authenticated for org A causes DB writes tied to org B's repository), but the concrete impact of the `check_suite` handler alone is an unauthorized/forced check-run refresh, not a direct unauthorized deploy/rollback/merge. Whether "production environment" amplifies this beyond a forced data refresh depends on downstream logic (e.g., continuous-delivery triggers keyed off check-run success) that was not confirmed as reachable purely from `check_suite` in the traced code.

### Likelihood Explanation
This requires: (1) Shipit configured with multi-organization GitHub App support (`Shipit.github_organizations`/`github_app_config`, `lib/shipit.rb:170-200`) where at least one configured organization has a blank/no `webhook_secret`, or the attacker independently knows some organization's secret; and (2) a victim repository/stack already registered in Shipit with a matching `branch` and existing `Commit` rows for the attacker-chosen `head_sha`. Given those preconditions, the attack is a single unauthenticated `POST /webhooks` and is repeatable at will against any repository/branch/commit combination already known to Shipit.

### Recommendation
Verify the webhook signature using the same repository field the handlers use to select the affected stacks (`payload.dig('repository','full_name')`'s owner), not an independently-controlled `organization.login` fallback. Additionally, `Handler#repository_name` should require and validate against the same, single source of truth used during signature verification, and reject payloads where `repository.owner.login`/`organization.login` disagree with `repository.full_name`'s owner segment.

### Proof of Concept
```ruby
# test/controllers/shipit/webhooks_controller_test.rb (conceptual, under existing test infra)
test "check_suite forged via organization fallback affects a different repository's production stack" do
  victim_stack = shipit_stacks(:shipit) # environment: 'production', repository full_name known
  commit = victim_stack.commits.create!(sha: 'deadbeef', branch: victim_stack.branch, ...)

  payload = {
    'organization' => { 'login' => 'attacker-org' }, # org with blank webhook_secret in test secrets
    'repository' => { 'full_name' => victim_stack.repository.full_name }, # no owner.login key
    'check_suite' => { 'head_sha' => commit.sha, 'head_branch' => victim_stack.branch }
  }.to_json

  assert_enqueued_with(job: Shipit::RefreshCheckRunsJob, args: [commit_id: commit.id]) do
    post shipit.webhooks_path, params: payload,
      headers: { 'X-Github-Event' => 'check_suite', 'X-Hub-Signature' => 'sha1=irrelevant', 'CONTENT_TYPE' => 'application/json' }
  end
  assert_response :ok
end
```
Assert both sides of the equality: `repository_owner` (derived from `organization.login`) ≠ owner segment of `params.dig('repository','full_name')` used by `Handler#stacks`, yet the job is enqueued against the victim's commit — proving the divergence is exploitable.
