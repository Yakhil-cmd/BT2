### Title
Cross-repository Status injection via unscoped SHA lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits with a global `Commit.where(sha: params.sha)` query instead of using the `Handler#stacks` helper that scopes lookups to the repository named in the verified webhook payload. Any verified `status` webhook (signed only by the sending organization/app installation) can therefore write a `Status` row onto a `Commit` belonging to a completely different, unrelated stack if the shas happen to collide, flipping `Commit#deployable?` for that unrelated stack.

### Finding Description
The claimed binding is: `payload.dig('repository','full_name')` (the repository the signature was verified for) `== commit.stack.repository.full_name` (the repository whose `Commit#deployable?` gets re-evaluated). This binding is never enforced.

- `Shipit::WebhooksController#verify_signature` only checks that the HMAC signature matches the secret configured for `repository_owner` (`params.dig('repository','owner','login')`) [1](#0-0) . This proves the payload originated from GitHub for *that* organization/app installation — it says nothing about which `Commit`/`Stack` the payload's `sha` is allowed to touch.
- `Shipit::Webhooks::Handlers::Handler` provides a `stacks` helper explicitly meant to scope handler logic to `Repository.from_github_repo_name(repository_name)` [2](#0-1) , but `StatusHandler#process` does not use it. Instead it does:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 
This query is global across every `Stack`/`Repository` in the Shipit instance — it is keyed only on `sha`, not on `repository_name`/`repository.full_name`.
- `Commit#create_status_from_github!` → `Status.replicate_from_github!(stack_id, github_status)` creates a `Status` row bound to `commit.stack_id` (the victim's stack), using `state`, `description`, etc. taken straight from attacker-controlled `params` [4](#0-3) [5](#0-4) .
- `Commit#deployable?` (`!locked? && (stack.ignore_ci? || (success? && !blocked?))`) is re-evaluated purely from the commit's status aggregate, with no reference to which repository produced that status [6](#0-5) .
- `Commit#schedule_continuous_delivery`, invoked from `add_status` via the `after_commit` chain, checks `deployable? && stack.continuous_deployment? && stack.deployable?` and enqueues `ContinuousDeliveryJob` for `stack` — i.e., the victim's stack — if the sha collision occurs [7](#0-6) .

Exploit flow: attacker owns `attacker/evil`, installs/configures GitHub to send status webhooks for it (this is their own repo, so they legitimately control the signature for `repository_owner: attacker`). If the attacker can produce a commit sha that also exists as a pending `Commit` row in `victim/prod` (the scenario stipulates this precondition is met), a genuine GitHub status webhook from `attacker/evil` for that sha — signed correctly for the `attacker` org — is routed by `StatusHandler#process` to **every** `Commit` in the database sharing that sha, including the one belonging to `victim/prod`. No code path compares `payload['repository']['full_name']` against `commit.stack`'s repository before writing the `Status` or acting on `deployable?`.

### Impact Explanation
A payload correctly authenticated for `attacker/evil` mutates state (`Status` row) and triggers derived authorization (`Commit#deployable?`, `schedule_continuous_delivery`) for `victim/prod`, a stack the attacker does not control. If `victim/prod` has `continuous_deployment: true` in its cached deploy spec, this results in an `ContinuousDeliveryJob` being scheduled — an unauthorized deploy trigger for a repository/stack the attacker never authenticated against. This matches the Critical impact category "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy." Blast radius is bounded by the attacker's ability to produce sha collisions across arbitrary undeployed commits in any tenant's stack, but the code-level authorization gap applies uniformly to every stack in the instance.

### Likelihood Explanation
The code-level gap (missing repository binding check in `StatusHandler#process`) is real and unconditional — it exists for every status webhook regardless of preconditions. However, exploitation requires the attacker to produce a commit whose SHA-1 matches a specific, already-existing, undeployed commit sha in a target victim stack. Git commit shas are SHA-1 over the full commit object (tree, parents, author/committer identities and timestamps, message); producing an exact match to an arbitrary pre-existing sha is a second-preimage problem, not something feasible with a simple "empty-tree commit," despite the scenario's phrasing. So while the missing-binding bug is confirmed in the code, the described end-to-end attack additionally depends on an infeasible SHA collision precondition that is outside this engine's code and not demonstrated as achievable.

### Recommendation
Scope `StatusHandler#process` to the repository named in the verified payload, mirroring the `stacks` helper already provided by the base `Handler` class, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This enforces `payload['repository']['full_name'] == commit.stack.repository.full_name` before any `Status` row is created or `deployable?`/continuous-delivery logic is triggered.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual)
test "status webhook for repo A must not affect commit in repo B sharing the same sha" do
  victim_stack = shipit_stacks(:shipit)              # repository: victim/prod
  attacker_repo_name = 'attacker/evil'
  shared_sha = 'deadbeef' * 5

  commit = victim_stack.commits.create!(sha: shared_sha, message: 'pending commit')
  refute commit.deployable?

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'ci',
    'repository' => { 'full_name' => attacker_repo_name, 'owner' => { 'login' => 'attacker' } }
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  commit.reload
  # EXPECTED (secure): commit untouched because payload's repository != victim/prod
  assert_equal 0, commit.statuses.count
  refute commit.deployable?
end
```
Given current code, `Commit.where(sha: params.sha)` in `StatusHandler#process` matches `commit` regardless of `payload['repository']['full_name']`, so this assertion fails today, demonstrating `deployable?` flips independent of repository binding.
