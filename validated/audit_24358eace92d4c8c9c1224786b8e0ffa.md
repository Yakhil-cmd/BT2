## Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler` — ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
The `WebhooksController` authenticates an inbound webhook by resolving the GitHub App/webhook secret for a single organization derived from the payload (`repository.owner.login`), but the `status` event handler that actually **writes** data does not re-scope its write to that same organization's repositories. It looks up the target `Commit` purely by `sha`, globally across every stack/repository tracked by the Shipit instance. This breaks the equality "organization that authenticated == repository that is written," letting any organization with its own valid (and possibly low-privileged) GitHub App installation forge a commit status for a commit belonging to a completely unrelated tracked repository/organization.

### Finding Description
`WebhooksController#verify_signature` selects the `GitHubApp` (and therefore the `webhook_secret` used to validate `X-Hub-Signature`) strictly from the `repository_owner` embedded in the same payload being verified: [1](#0-0) [2](#0-1) 

This means the signature only proves the request originated from *some* organization's installed GitHub App (in a multi-org configuration, per `lib/shipit.rb`'s `github_app_config`), not that the write it performs is confined to that organization's repositories.

For most event handlers, the actual data mutation is properly re-scoped to stacks belonging to `repository.full_name` via `Handler#stacks`: [3](#0-2) 

For example `PushHandler` and `CheckSuiteHandler` both filter through `stacks`: [4](#0-3) 

However, `StatusHandler#process` bypasses `stacks` entirely and queries the global `Commit` table by `sha` alone: [5](#0-4) 

`Commit.where(sha: params.sha)` is not joined or filtered by `repository`/`stack` at all, so any commit in the entire Shipit database sharing that SHA — regardless of which organization or repository it belongs to — gets a new status attached via `create_status_from_github!`: [6](#0-5) 

Since a 40-character git SHA is often publicly known (visible in Shipit's own UI, GitHub's public API/commits pages, or CI logs), an attacker who controls a legitimate GitHub organization/app installation with its own `webhook_secret` (a valid, low-privilege binding) can sign and send a `status` webhook naming an arbitrary SHA that belongs to a stack owned by a different organization tracked by the same Shipit instance, injecting a forged status (e.g., `success`) for it.

### Impact Explanation
Commit status directly feeds into deploy-gating and merge-queue logic: [7](#0-6) [8](#0-7) 

By forging a `success` status for a target commit in a repository the attacker's organization has no legitimate relationship to, the attacker can satisfy CI-required-status checks used to gate continuous deployment (`Stack.schedule_continuous_delivery`) or PR auto-merge (`MergeRequest#any_status_checks_failed?`/`#reject_unless_mergeable!`), causing an unauthorized deploy or an unauthorized merge on a repository/organization the attacker's webhook credentials were never meant to touch. This crosses the "unauthorized deploy, rollback or merge" Critical bar and is a genuine cross-repository write.

### Likelihood Explanation
Requires the attacker to control (or compromise) a GitHub organization that has a legitimate Shipit GitHub App installation with its own webhook secret — an unprivileged-attacker-obtainable position in any multi-tenant/multi-org Shipit deployment (`docs/setup.md`'s "Using Multiple Github Applications" section, `lib/shipit.rb#github_app_config`). No `ApiClient` token, GitHub App private key, or Shipit session is needed; only the ability to have GitHub deliver (or be spoofed into signing, via the attacker's own org secret) a `status` webhook with an attacker-chosen `sha`. The target SHA needs to be known, which is generally true for any tracked, non-private-hash commit.

### Recommendation
Scope `StatusHandler#process` (and any other handler bypassing `Handler#stacks`) to only mutate commits belonging to stacks resolved from the authenticated `repository.full_name`/`repository_owner`, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)`, mirroring the pattern already used by `PushHandler` and `CheckSuiteHandler`.

### Proof of Concept
1. Attacker controls org `EvilCorp`, which has a legitimate Shipit GitHub App installation with webhook secret `S_evil` (multi-org config).
2. Attacker discovers (via GitHub's public commit API or the Shipit UI) the SHA of a commit `abc123...` belonging to stack `victim-org/critical-service`, currently pending/failing CI.
3. Attacker crafts a `status` webhook payload: `{"sha": "abc123...", "state": "success", "context": "ci/required-check", "repository": {"owner": {"login": "EvilCorp"}, "full_name": "EvilCorp/some-repo"}}` and signs it with `S_evil`.
4. `WebhooksController#verify_signature` resolves `Shipit.github(organization: 'EvilCorp')` and validates successfully since the signature matches `S_evil`.
5. `StatusHandler#process` runs `Commit.where(sha: 'abc123...')`, finds the commit belonging to `victim-org/critical-service`, and attaches the forged `success` status via `create_status_from_github!`, regardless of the fact that the authenticated organization (`EvilCorp`) has no relationship to that stack.
