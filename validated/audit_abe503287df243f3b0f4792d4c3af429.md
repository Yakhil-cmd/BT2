### Title
Inconsistent locking between private and public double-spend acceptance allows a private-asset double-spend race - (File: validation.js)

### Summary
`validation.js`'s double-spend acceptance logic uses two different synchronization strategies depending on whether the conflicting asset is private or public. For public assets the "un-uniquing" SQL (`UPDATE inputs SET is_unique=NULL ...`) is deferred into `objValidationState.arrAdditionalQueries` and executed later by `writer.saveJoint()` while holding the global `["write"]` mutex, which serializes it against every other unit's commit. For private assets, the identical mutation is instead executed immediately, inside the validation transaction, guarded only by a separate, narrower `["private_write"]` mutex that is never taken by the writer's commit path. This mirrors the CVE-2023-52903 pattern, where one execution mode (IOPOLL|SQPOLL) mutated the CQ overflow list without the lock normally required for that data structure, opening a race window.

### Finding Description
`checkInputDoubleSpend()`'s `acceptDoublespends` callback decides how to relax the uniqueness constraint on a conflicting, still-unstable `inputs` row once a new unit is accepted as a non-conflicting competitor: [1](#0-0) 

For public assets the SQL is queued and only applied later, under the `["write"]` lock taken by the writer: [2](#0-1) [3](#0-2) 

For private assets, the same relaxation is executed directly on the validating connection, protected only by `mutex.lock(["private_write"], ...)`, a lock key that is not used anywhere else on the write/commit path: [4](#0-3) 

Crucially, `validation.validate()` itself is only serialized per-author, via `mutex.lock(arrAuthorAddresses, ...)`: [5](#0-4) 

Two units authored by *different* addresses that both spend the same private-asset output can therefore validate fully concurrently. Each one's `checkForDoublespends()` decision to accept the other as a non-conflicting predecessor (based on `graph.determineIfIncludedOrEqual` and the conflicting row's current `is_stable`/`sequence`) is made without holding the `["write"]` lock that the rest of the system relies on to serialize such decisions against actual unit commits: [6](#0-5) 

Because the `["private_write"]` lock only brackets the single UPDATE statement and is disconnected from the `["write"]` lock used for the final commit of competing units in `writer.js`, the acceptance decision and the corresponding commit for two racing private-asset spenders are not mutually exclusive with each other in the way the public-asset path guarantees (there, the mutation is deferred until the writer's own `["write"]`-protected commit, so it can never race a concurrent commit).

### Impact Explanation
If two units from different author addresses concurrently spend the same private-asset output, the locking gap can let both validations independently decide the other is an acceptable (non-conflicting) predecessor and clear `is_unique`, letting both proceed to be written and committed. This produces a genuine double-spend of a private-asset output — one of the concrete high-impact outcomes in scope (unauthorized spending / double-spend), since the transfer/issue amount for the same coin would be recognized as valid in two different units.

### Likelihood Explanation
Triggering the race requires only posting two ordinary private-asset payment units (or AA/asset messages) from two different author addresses that spend the same private output at roughly the same time — something any unprivileged user of a private asset (via the composer/private_payment.js path, or by directly sending crafted joints) can attempt. No special network position, hub, or node privilege is required; only timing to line up the two validations inside the unlocked window.

### Recommendation
Route the private-asset `is_unique=NULL` un-uniquing update through the same `["write"]`-guarded, deferred (`arrAdditionalQueries`) mechanism used for public assets, or otherwise make `checkForDoublespends`'s acceptance decision and its corresponding uniqueness mutation atomic with the eventual `writer.saveJoint()` commit for both units under a single, shared lock, instead of using an independent `["private_write"]` key.

### Proof of Concept
1. Create a private, divisible or indivisible asset and issue a spendable private output `O` to address `A` (accessible/known to two different author addresses via a shared address or attacker-controlled multi-device setup).
2. Author two units, `U1` (author `A1`) and `U2` (author `A2`), each spending private output `O` in a payload for the private asset, and submit/post them to the node at nearly the same time so their `validation.validate()` calls run concurrently (they use different `arrAuthorAddresses` locks and thus are not serialized against each other).
3. In each validation, `checkForDoublespends()` for the other unit's still-unstable `inputs` row sees `bIncluded=false` (since neither is yet included in the other's parents) and enters `acceptDoublespends`, taking only the `["private_write"]` lock, momentarily clearing `is_unique` on the other unit's row.
4. Both `U1` and `U2` proceed through `writer.saveJoint()` (each independently acquiring `["write"]` only for its own commit), resulting in both being committed as valid units — a private double-spend of output `O`.

function checkForDoublespends(conn, type, sql, arrSqlArgs, objUnit, objValidationState, onAcceptedDoublespends, cb){
	conn.query(
		sql, 
		arrSqlArgs,
		function(rows){
			if (rows.length === 0)
				return cb();
			var arrAuthorAddresses = objUnit.authors.map(function(author) { return author.address; } );
			async.eachSeries(
				rows,
				function(objConflictingRecord, cb2){
					if (arrAuthorAddresses.indexOf(objConflictingRecord.address) === -1)
						throw Error("conflicting "+type+" spent from another address?");
					if (conf.bLight) // we can't use graph in light wallet, the private payment can be resent and revalidated when stable
						return cb2(objUnit.unit+": conflicting "+type);
					graph.determineIfIncludedOrEqual(conn, objConflictingRecord.unit, objUnit.parent_units, function(bIncluded){
						if (bIncluded){
							var error = objUnit.unit+": conflicting "+type+" in inner unit "+objConflictingRecord.unit;

							// too young (serial or nonserial)
							if (objConflictingRecord.main_chain_index > objValidationState.last_ball_mci || objConflictingRecord.main_chain_index === null)
								return cb2(error);

							// in good sequence (final state); final-bad is excluded by the query and treated as non-existent
							if (objConflictingRecord.sequence === 'good')
								return cb2(error);

							throw Error("unreachable code, conflicting "+type+" in unit "+objConflictingRecord.unit);
						}
						else{ // arrAddressesWithForkedPath is not set when validating private payments
							if (objValidationState.arrAddressesWithForkedPath && objValidationState.arrAddressesWithForkedPath.indexOf(objConflictingRecord.address) === -1)
								throw Error("double spending "+type+" without double spending address?");
							cb2();
						}
					});
				},
				function(err){
					if (err)
						return cb(err);
					onAcceptedDoublespends(cb);
				}
			);
		}
	);
}
