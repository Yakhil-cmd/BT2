### Title
Unvalidated asset display name allows homograph/lookalike spoofing of legitimate assets - ([File: wallet.js])

### Summary
CVE-2019-13715 describes Chrome's Omnibox failing to properly validate IDN homograph characters, letting an attacker register a domain that visually spoofs a trusted domain. The analogous weakness in ocore is in `fetchAssetMetadata()` in `wallet.js`, where an asset's user-facing display `name` (fetched from a `data` message published by an asset's *registry* address) is accepted and cached with no charset/format restriction beyond a truthiness check, allowing any registry to register a name that is visually indistinguishable (via Unicode confusables/homographs) from a trusted asset's name.

### Finding Description
When a wallet needs to show a friendly name for an asset, it calls `fetchAssetMetadata()`, which fetches metadata from the hub and then reads the metadata unit's `data` message: [1](#0-0) 
The only checks applied to `payload.name` are that it exists (`!payload.name`) — there is no restriction on character set, length normalization, or exclusion of confusable/lookalike Unicode code points before the value is persisted into `asset_metadata.name` and returned to callers for display: [2](#0-1) 

The `asset_metadata` table only enforces uniqueness of `(name, registry_address)`, meaning distinct registries can freely register the exact same display string, or strings that render identically to a well-known asset name/ticker via homoglyphs (e.g. Cyrillic "а" vs Latin "a", or other Unicode confusables), without any collision detection or normalization: [3](#0-2) 

Because any address can act as a registry and publish a `data` message naming any asset it controls, an attacker can publish a metadata unit for their own malicious asset using a name that is visually identical (via homograph characters) to a popular/trusted asset's name. Wallets displaying this attacker-chosen `name` string to a user (e.g. in payment confirmation, asset pickers) have no way to distinguish it from the legitimate asset's name, since normalization/confusable-detection is entirely absent — directly analogous to the CVE's IDN homograph spoofing of domain names in an address/name display surface that users trust to identify what they are interacting with.

### Impact Explanation
A user who is shown the spoofed asset name may believe they are sending/receiving a well-known, valuable asset when in fact they are interacting with an attacker's worthless or malicious asset, or vice versa — mistaking a malicious asset for the legitimate one when authorizing a payment. This can lead to unauthorized/mistaken spending of funds toward the attacker-controlled asset/registry, satisfying the "concrete unauthorized spending" impact bar, since the wallet's own trust-establishing UI text (asset name) is the attack surface, not a third-party or network actor.

### Likelihood Explanation
Any address can act as an asset registry and publish a `data` message with an arbitrary `payload.name` for any asset it defines — no privileged relationship with the real registry or the spoofed asset is required. The only friction is registering an asset and posting a single `data` unit, both of which are default flows any unprivileged unit poster can perform. This makes the attack straightforward and reachable without extra prerequisites.

### Recommendation
Apply Unicode confusable-skeleton normalization (or restrict `asset_metadata.name` to a constrained character set, e.g. ASCII alphanumerics) before accepting and persisting `payload.name` in `fetchAssetMetadata()`, and enforce global name uniqueness/confusable-collision checks across registries rather than only per-registry uniqueness, so wallets cannot be shown two visually indistinguishable names for different assets.

### Proof of Concept
1. Attacker controls address `R` and defines an asset `A` via a normal `asset` message.
2. Attacker publishes a `data` message from `R` with `payload = { asset: A, name: "Byteba11" }` (or any string using Unicode homoglyphs that renders identically to a trusted asset's registered name, e.g. mixed-script lookalikes).
3. A victim wallet calls `fetchAssetMetadata(A)`, which accepts and stores this name with no confusable/format validation (`wallet.js:1464-1483`), then displays "Byteba11"/lookalike name to the user during a payment flow.
4. The victim, trusting the displayed name, sends payment believing they are dealing with the legitimate, well-known asset, when in fact it is the attacker's unrelated asset `A`.
