### Title
Cross-repository/cross-organization Status forgery via webhook authentication/write binding mismatch enabling unauthorized deploy - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate a request against using an attacker-controlled field of the *unverified* JSON body (`repository.owner.login`, falling back to `organization.login`), not from anything cryptographically bound to the actual data acted on. Downstream, `StatusHandler#process` looks up the commit to mutate purely by `Commit.where(sha: params.sha)` with **no scoping to the repository/organization that was used for signature verification at all**. This breaks the binding: `organization authenticated == repository/commit written`.

### Finding Description
`Shipit::WebhooksController#verify_signature` picks the GitHub App config to verify against like this: [1](#0-0) [2](#0-1) 

`repository_owner` comes straight from the raw, unauthenticated request body — the same body the signature is supposed to protect. `Shipit.github(organization: repository_owner)` then resolves a *per-organization* config (Shipit explicitly supports multiple GitHub Apps/organizations sharing one instance, each with its own `webhook_secret`, per `docs/setup.md` "Using Multiple Github Applications" and `test/dummy/config/secrets_double_github_app.yml`). `GithubApp#verify_webhook_signature` only proves the request was signed with *that organization's* secret: [3](#0-2) 

Note also line 77: if that organization's `webhook_secret` is unset (documented as **optional** in `docs/setup.md` under "Creating the GitHub App"), verification unconditionally returns `true` regardless of the signature header content.

Once "verified", `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the *entire* raw JSON body to handlers — including `repository.full_name`, which is never checked against `repository_owner`: [4](#0-3) 

For most handlers (`push`, `pull_request/*`), the target repository is at least re-derived from `repository.full_name` via `Repository.from_github_repo_name`, but that value is *still* never cross-checked against the org whose secret validated the request: [5](#0-4) 

`StatusHandler` is worse: it does not scope by repository at all, only by raw commit SHA across the entire installation's `commits` table: [6](#0-5) 

`Commit#create_status_from_github!` then recomputes the commit's aggregate status and, if it becomes `success`, `stack.continuous_deployment?` and `stack.deployable?`, schedules an actual deploy: [7](#0-6) [8](#0-7) [9](#0-8) 

**Equality broken:** `organization authenticated (repository_owner used to pick the verifying secret)` != `repository/commit whose state is actually mutated (Commit.where(sha:), unscoped by repository)`. The signature only proves "this request came from the org I looked up by an unauthenticated field"; it proves nothing about which commit/repository the payload subsequently claims to modify.

### Impact Explanation
On a Shipit instance configured for multiple GitHub organizations (an explicitly documented, supported configuration), an attacker who can get any single tracked organization's webhook accepted — including one whose `webhook_secret` was left blank, which `docs/setup.md` explicitly calls "optional" — can forge a `status` event claiming `repository.owner.login` = that weakly-protected org while `sha` = the SHA of a commit that actually belongs to a *different*, better-protected organization's stack. Because `StatusHandler` never checks that the SHA belongs to a repository under the authenticated organization, the attacker can mark an arbitrary commit as CI-`success`, and if that stack has continuous deployment enabled, `Commit#schedule_continuous_delivery` triggers `ContinuousDeliveryJob`, resulting in an **unauthorized deploy** of that commit. This matches the report's "Critical/High" bar: unauthorized deploy through an authentication binding that doesn't cover the field actually acted on, directly analogous to `Swap.sol` trusting `msg.sender`/`feeRecipient` transfer semantics without accounting for the actual receiving contract's behavior — here, trusting "signature verified for org X" without verifying "data mutated belongs to org X".

### Likelihood Explanation
Requires: (1) a Shipit deployment configured with more than one GitHub organization (documented feature) where at least one organization has no `webhook_secret` configured (documented as optional) or is otherwise weaker, and (2) a target stack with continuous deployment enabled and a known/guessable commit SHA (SHAs of public repos are trivially discoverable). No `ApiClient` token, `webhook_secret` of the target org, GitHub App private key, or repository write access is required — only a webhook delivery accepted under a weaker/unrelated organization's identity. Likelihood is moderate: it depends on multi-org/blank-secret configuration, but that configuration is explicitly documented and supported by the engine itself, not a deviation from documented mounting.

### Recommendation
- After `verify_signature` succeeds, propagate the verified `repository_owner`/organization identity into the handler dispatch and have every handler (especially `StatusHandler`) reject or scope out records whose `stack.repository`'s organization does not match the organization that authenticated the request.
- In `StatusHandler#process`, scope `Commit.where(sha: params.sha)` to `stacks` (as `Handler#stacks` already does for other handlers) derived from `payload.dig('repository', 'full_name')`, and additionally verify that repository's owner equals `repository_owner`.
- Do not silently `return true` from `verify_webhook_signature` when `webhook_secret` is blank; either require a webhook secret for every configured organization or explicitly document/enforce that unsigned orgs cannot mutate cross-organization state.

### Proof of Concept
1. Configure Shipit with two GitHub orgs sharing one instance: `OrgWeak` (no `webhook_secret`, i.e., blank per `docs/setup.md`) and `OrgTarget` (has a stack `OrgTarget/app` with `continuous_deployment` enabled and commit `abc123...` currently pending CI).
2. POST to `/webhooks` with header `X-Github-Event: status` and no valid `X-Hub-Signature` (or any garbage value), body:
   ```json
   {"sha":"abc123...","state":"success","repository":{"owner":{"login":"OrgWeak"}}}
   ```
3. `verify_signature` resolves `Shipit.github(organization: 'OrgWeak')`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb:77`).
4. `StatusHandler#process` runs `Commit.where(sha: 'abc123...')` — finds the commit belonging to `OrgTarget/app`'s stack regardless of the fact the request was "authenticated" as `OrgWeak` — and calls `create_status_from_github!`, marking it `success`.
5. `Commit#schedule_continuous_delivery` sees `deployable? && stack.continuous_deployment? && stack.deployable?` and enqueues `ContinuousDeliveryJob`, deploying the commit to `OrgTarget/app` without any legitimate CI signal or credential belonging to `OrgTarget`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
