No vulnerability found for this question.

**Rationale:** The described attack — supplying an authentication function proof that doesn't correspond to the sender's registered dispatchable-authenticator module — is exactly the case the framework already rejects.

- At the VM boundary, `validate_signed_transaction` in `aptos-move/aptos-vm/src/aptos_vm.rs` takes the `AuthenticationProof::Abstract { function_info, auth_data }` extracted from the `AccountAuthenticator::Abstract` and calls `dispatchable_authenticate`, gated by `is_account_abstraction_enabled()` / `is_derivable_account_abstraction_enabled()`. [1](#0-0) 
- The actual binding check happens in the Move framework's `authenticate` function: for non-derivable AA it looks up the *sender's own* registered function map via `dispatchable_authenticator_internal(master_signer_addr)` and asserts `func_infos.contains(&func_info)` (aborting with `EFUNCTION_INFO_EXISTENCE` otherwise); for derivable AA it additionally asserts `master_signer_addr == derive_account_address(func_info, ...)`. [2](#0-1) 
- After the dispatched authenticator function runs, the code asserts the returned signer's address equals the original `master_signer_addr`, which is the invariant that prevents any address/signer confusion: "Returned signer MUST represent the same account address. Otherwise, it may break the invariant of Aptos blockchain!" [3](#0-2) 
- Separately, at the authenticator-verification layer, `AccountAuthenticator::verify` for the `Abstract` variant ties the `signing_message_digest` to the actual transaction message *and* the specific `function_info` via `AASigningData::signing_message_digest`, so a proof generated for one function/message pair cannot be reused for another. [4](#0-3) 

Because the sender-address-to-registered-function binding is enforced on-chain (not just client-side), an attacker cannot make a `SingleSender`/`Abstract` authenticator with a mismatched `function_info` pass validation — it aborts with `EFUNCTION_INFO_EXISTENCE` or `EINCONSISTENT_SIGNER_ADDRESS` in the Move module before any state-changing effect occurs. There is no path here where an unprivileged input causes wrong signing material to be accepted as valid for a sender's account.

Additionally, the file cited in the question, `types/src/epoch_change.rs`, is unrelated to transaction/account authenticator logic — it implements `EpochChangeProof` verification for validator-set/ledger-info transitions used in state sync, not account abstraction authentication. [5](#0-4)  This mismatch between the cited file and the described vulnerability further indicates the finding as stated does not correspond to real code behavior in this location.

#[derive(Clone, Debug, Deserialize, Eq, PartialEq, Serialize)]
/// A vector of LedgerInfo with contiguous increasing epoch numbers to prove a sequence of
/// epoch changes from the first LedgerInfo's epoch.
pub struct EpochChangeProof {
    pub ledger_info_with_sigs: Vec<LedgerInfoWithSignatures>,
    pub more: bool,
}
impl EpochChangeProof {
    pub fn new(ledger_info_with_sigs: Vec<LedgerInfoWithSignatures>, more: bool) -> Self {
        Self {
            ledger_info_with_sigs,
            more,
        }
    }

    /// The first/lowest epoch of the proof to indicate which epoch this proof is helping with
    pub fn epoch(&self) -> Result<u64> {
        self.ledger_info_with_sigs
            .first()
            .map(|li| li.ledger_info().epoch())
            .ok_or_else(|| format_err!("Empty EpochChangeProof"))
    }

    /// Verify the proof is correctly chained with known epoch and validator
    /// verifier and return the [`LedgerInfoWithSignatures`] to start target epoch.
    ///
    /// In case a waypoint is present, it's going to be used for verifying the
    /// very first epoch change (it's the responsibility of the caller to not
    /// pass a waypoint in case it's not needed).
    ///
    /// We will also skip any stale ledger info's in the [`EpochChangeProof`].
    pub fn verify(&self, verifier: &dyn Verifier) -> Result<&LedgerInfoWithSignatures> {
        ensure!(
            !self.ledger_info_with_sigs.is_empty(),
            "The EpochChangeProof is empty"
        );
        ensure!(
            !verifier
                .is_ledger_info_stale(self.ledger_info_with_sigs.last().unwrap().ledger_info()),
            "The EpochChangeProof is stale as our verifier is already ahead \
             of the entire EpochChangeProof"
        );
        let mut verifier_ref = verifier;

        for ledger_info_with_sigs in self
            .ledger_info_with_sigs
            .iter()
            // Skip any stale ledger infos in the proof prefix. Note that with
            // the assertion above, we are guaranteed there is at least one
            // non-stale ledger info in the proof.
            //
            // It's useful to skip these stale ledger infos to better allow for
            // concurrent client requests.
            //
            // For example, suppose the following:
            //
            // 1. My current trusted state is at epoch 5.
            // 2. I make two concurrent requests to two validators A and B, who
            //    live at epochs 9 and 11 respectively.
            //
            // If A's response returns first, I will ratchet my trusted state
            // to epoch 9. When B's response returns, I will still be able to
            // ratchet forward to 11 even though B's EpochChangeProof
            // includes a bunch of stale ledger infos (for epochs 5, 6, 7, 8).
            //
            // Of course, if B's response returns first, we will reject A's
            // response as it's completely stale.
            .skip_while(|&ledger_info_with_sigs| {
                verifier.is_ledger_info_stale(ledger_info_with_sigs.ledger_info())
            })
        {
            // Try to verify each (epoch -> epoch + 1) jump in the EpochChangeProof.
            verifier_ref.verify(ledger_info_with_sigs)?;
            // While the original verification could've been via waypoints,
            // all the next epoch changes are verified using the (already
            // trusted) validator sets.
            verifier_ref = ledger_info_with_sigs
                .ledger_info()
                .next_epoch_state()
                .ok_or_else(|| format_err!("LedgerInfo doesn't carry a ValidatorSet"))?;
        }

        Ok(self.ledger_info_with_sigs.last().unwrap())
    }
