### Title
Predictable/grindable pseudo-randomness via `number_from_seed` allows a trigger sender to bias AA outcomes - (File: `formula/evaluation.js`)

### Summary
`number_from_seed` is an oscript function AA authors use to derive "randomness" for probabilistic logic (lotteries, games, fee/roll distribution, etc.). Its implementation is a pure, deterministic hash of the caller-supplied seed(s): `sha256(seed)` truncated and mapped into a range [1](#0-0) . There is no protocol-level requirement or mechanism ensuring the seed contains any value unknown to, or uncontrollable by, the unprivileged party who constructs the triggering unit. This mirrors the reported bug class: a contract computing "randomness" from an input the party who benefits from the outcome fully controls, instead of a properly committed, unpredictable value combined from multiple parties.

### Finding Description
`number_from_seed(seed[, min[, max]])` evaluates its seed expression(s), hashes them with SHA-256, and derives a decimal from the hash [2](#0-1) . Validation only checks the number/type of arguments, not the origin or entropy quality of the seed [3](#0-2) . Nothing in the oscript language or AA trigger-handling code (`aa_composer.js`, `getTrigger`) forces the seed to include data unknown to the unit's author at the time of composing the triggering unit — an AA can be written to call `number_from_seed(trigger.data.something)`, `number_from_seed(trigger.unit)`, or any other value that is fully determined by the same person who posts the trigger, because `trigger.data`/`trigger.unit` are populated straight from the posted unit's own content [4](#0-3) .

Because the trigger sender chooses the entire content of the unit before broadcasting it (including `data` payload fields, and indirectly the resulting `unit` hash once other fields are fixed), and because unit composition/signing can be iterated locally without any network interaction or cost until the unit is actually broadcast, an attacker can offline-compute `number_from_seed(...)` for many candidate trigger payloads and only broadcast the one unit whose seed yields their desired ("random") outcome. This is the same structural flaw described in the report: the final "random" value is derived solely from data controlled by a single, unprivileged party, with no independent, un-manipulable input (equivalent to the missing `userRandomNumber`/provider-committed value in the Entropy protocol), so whichever party can grind inputs before commitment fully controls the outcome.

### Impact Explanation
Any AA that uses `number_from_seed` seeded (directly or transitively, e.g. hashed together with other attacker-known values) from trigger-controlled data to decide payouts, winners, discounts, asset issuance amounts, or other fund-moving logic can be drained or manipulated by a trigger sender who simply grinds candidate triggers offline until they find one that satisfies the winning condition, then submits only that unit. This results in unauthorized/unintended asset transfer out of the AA (AA fund loss) whenever the AA's economic logic assumes the seed is unpredictable to the trigger sender.

### Likelihood Explanation
Likelihood is High for any AA template that naively follows the documented pattern of using `number_from_seed` with trigger-supplied data as the sole entropy source (a very natural and commonly suggested pattern for on-chain "randomness" in oscript, given no other native randomness primitive is highlighted for this purpose besides `vrf_verify`, which requires the AA to independently verify an oracle-provided proof rather than trusting trigger data). No special network position, race condition, or protocol violation is needed — pure local computation and one broadcast, which is exactly the mechanism available to any unprivileged unit poster/AA trigger sender.

### Recommendation
- Document explicitly (and, where feasible, enforce) that `number_from_seed` must not be seeded solely from data supplied by the same party who triggers the AA and benefits from the resulting outcome; any AA-level "randomness" needs at least one input that is fixed independently of, and prior to, the trigger sender's ability to observe or choose it (e.g., a future MC unit hash unknown at trigger time, or a value contributed by a second, disinterested party via a commit-reveal scheme across multiple triggers).
- Consider providing a language-level primitive or MC-based unpredictable value (e.g., a hash of a future stable unit not yet known at trigger submission time) that cannot be grinded by the trigger sender, so AA authors are not tempted to feed `number_from_seed` with self-chosen trigger data.
- Add validation/lint tooling or documentation warnings when an AA definition passes `trigger.data`, `trigger.unit`, or other trigger-sender-controlled fields directly into `number_from_seed` without external unpredictable material.

### Proof of Concept
1. Deploy an AA whose response logic reads: `$r = number_from_seed(trigger.data.seed, 1, 100); if ($r > 50) { pay 2x } else { pay 0 }` (a common "coin-flip" pattern using trigger data as the seed, exactly as demonstrated by `test('number_from_seed', ...)` [5](#0-4) ).
2. Locally iterate over candidate `data.seed` values (any string/number the attacker can freely choose when composing their triggering unit), computing `sha256(seed)` off-chain exactly as `evaluation.js` does [2](#0-1) , until one is found whose derived number exceeds 50.
3. Compose and broadcast only that winning unit as the AA trigger; the AA is deterministic and will pay out the "win" branch every time, since the "randomness" was fully known to the attacker before submission.
4. Repeat to drain AA balance, since there is no mechanism forcing the seed to include any value unknown to the trigger sender at broadcast time.

function getTrigger(objUnit, receiving_address) {
	var trigger = { address: objUnit.authors[0].address, unit: objUnit.unit, outputs: {} };
	if ("max_aa_responses" in objUnit)
		trigger.max_aa_responses = objUnit.max_aa_responses;
	objUnit.messages.forEach(function (message) {
		if (message.app === 'data' && !trigger.data) // use the first data message, ignore the subsequent ones
			trigger.data = message.payload;
		else if (message.app === 'payment' && message.payload) {
			var payload = message.payload;
			var asset = payload.asset || 'base';
			payload.outputs.forEach(function (output) {
				if (output.address === receiving_address) {
					if (!trigger.outputs[asset])
						trigger.outputs[asset] = 0;
					trigger.outputs[asset] += output.amount; // in case there are several outputs
				}
			});
		}
	});
	if (Object.keys(trigger.outputs).length === 0)
		throw Error("no outputs to " + receiving_address);
	return trigger;
}
