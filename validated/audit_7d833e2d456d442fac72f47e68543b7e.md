### Title
`deregisterOperator` Does Not Clear Outstanding Votes, Allowing Stale Deregistered-Operator Votes to Execute Bridge Value Transfers — (`contracts/service_chain/bridge/BridgeOperator.sol`)

---

### Summary

`BridgeOperator.deregisterOperator` removes an operator from `operators` and `operatorList` but leaves the operator's accumulated vote weight intact in the `votes` mapping. A deregistered operator's prior vote can still satisfy the threshold check when a subsequent legitimate operator votes, causing an unauthorized bridge value transfer to execute even after the owner explicitly revoked the operator's authority.

---

### Finding Description

`deregisterOperator` only clears two state variables:

```solidity
delete operators[_operator];   // operators mapping
operatorList[i] = operatorList[operatorList.length-1];
operatorList.length--;         // operatorList array
``` [1](#0-0) 

The `votes` mapping — `mapping(uint8 => mapping(uint64 => VotesData))` — is never touched. `VotesData` holds:

- `voted[operator]` — the `voteKey` the operator committed to for a given nonce
- `voteCounts[voteKey]` — the running tally that is compared against `operatorThresholds` [2](#0-1) 

When a subsequent active operator votes on the same nonce, `_voteCommon` increments `voteCounts[voteKey]`, which now includes the deregistered operator's stale contribution. The threshold check fires on the combined count:

```solidity
if (vote.voteCounts[_voteKey] >= operatorThresholds[uint8(_voteType)]) {
    return true;
}
``` [3](#0-2) 

The contract itself acknowledges this in a comment but frames it as an operator-management concern rather than a security invariant:

> *"Note that outstanding votes by the deregistered operator are not revoked … The Owner shall recognize this issue and expect that operator deregistration takes some time to be fully effective."* [4](#0-3) 

The stale vote does **not** expire — it persists indefinitely in contract storage. There is no time-bound or automatic cleanup.

---

### Impact Explanation

`_voteValueTransfer` calls `_voteCommon` and, on threshold satisfaction, sets `closedValueTransferVotes[_requestNonce] = true` and returns `true`, causing the caller (`handleKLAYTransfer`, `handleERC20Transfer`, `handleERC721Transfer`) to execute the asset transfer out of the bridge. [5](#0-4) 

A deregistered operator's stale vote can be the deciding vote that crosses the threshold, resulting in an unauthorized transfer of KAIA or bridged ERC-20/ERC-721 tokens from the bridge contract — directly within the Kaia Allowed Impact Gate ("Unauthorized transfer … affecting KAIA, bridged assets, or system-managed funds").

---

### Likelihood Explanation

The attack requires:
1. Operator A votes on request nonce N (e.g., a large KAIA withdrawal).
2. The bridge owner discovers A is compromised and calls `deregisterOperator(A)`, believing A's vote is revoked.
3. Any remaining legitimate operator B votes on nonce N.
4. `voteCounts[voteKey]` = A's stale count (1) + B's count (1) = 2 ≥ threshold (2) → transfer executes.

The owner's remediation action (deregistration) is silently ineffective. This is a realistic operational scenario whenever an operator key is suspected compromised mid-vote.

---

### Recommendation

In `deregisterOperator`, iterate over all open (non-closed) nonces for which the deregistered operator has a recorded vote and decrement the corresponding `voteCounts` entry:

```solidity
function deregisterOperator(address _operator) external onlyOwner {
    require(operators[_operator]);
    delete operators[_operator];
    // ... remove from operatorList ...

    // Revoke outstanding votes for all open value-transfer nonces
    for (uint64 nonce = lowerHandleNonce; nonce <= upperHandleNonce; nonce++) {
        if (closedValueTransferVotes[nonce]) continue;
        VotesData storage vd = votes[uint8(VoteType.ValueTransfer)][nonce];
        bytes32 key = vd.voted[_operator];
        if (key != bytes32(0)) {
            vd.voteCounts[key]--;
            delete vd.voted[_operator];
        }
    }
    // Repeat for VoteType.Configuration at configurationNonce
    emit OperatorDeregistered(_operator);
}
```

Alternatively, add a `lastVoteRevocationBlock` per operator and reject stale votes in `_voteCommon` if the voter was deregistered after the vote was cast.

---

### Proof of Concept

Setup: bridge with operators `[A, B]`, `operatorThresholds[ValueTransfer] = 2`.

1. Operator A calls `handleKLAYTransfer(txhash, from, to, 1000 KAIA, nonce=5, blockNum, "")` → `voteCounts[voteKey] = 1`, threshold not met.
2. Owner calls `deregisterOperator(A)` → `operators[A] = false`, `operatorList = [B]`. `votes[0][5].voted[A]` and `votes[0][5].voteCounts[voteKey]` are **unchanged** (still 1).
3. Operator B calls `handleKLAYTransfer(txhash, from, to, 1000 KAIA, nonce=5, blockNum, "")` → `voteCounts[voteKey]` becomes 2 ≥ threshold 2 → `closedValueTransferVotes[5] = true` → 1000 KAIA transferred to `to`.

The owner's intent to block the transfer by deregistering A is defeated by the stale vote state that `deregisterOperator` never clears. [6](#0-5)

    function _voteCommon(VoteType _voteType, uint64 _nonce, bytes32 _voteKey)
        private
        returns(bool)
    {
        VotesData storage vote = votes[uint8(_voteType)][_nonce];

        // If the same voter voted again, revoke previous vote.
        bytes32 oldVoteKeyOfVoter = vote.voted[msg.sender];
        if (oldVoteKeyOfVoter == bytes32(0)) {
            vote.voters.push(msg.sender);
        } else {
            vote.voteCounts[oldVoteKeyOfVoter]--;
        }

        // Either the current voter has voted before or not, update the vote data.
        vote.voted[msg.sender] = _voteKey;

        if (vote.voteCounts[_voteKey] == 0) {
            vote.voteKeys.push(_voteKey);
        }
        vote.voteCounts[_voteKey]++;

        if (vote.voteCounts[_voteKey] >= operatorThresholds[uint8(_voteType)]) {
            return true;
        }
        return false;
    }
```
