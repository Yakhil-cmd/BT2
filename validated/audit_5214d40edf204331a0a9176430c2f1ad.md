### Title
Webhook Signature Verification Selects Trust Based on `organization`/`repository.owner` but Handlers Act on an Unverified `repository.full_name` Field - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
Analogous to the smart-contract bug where the function trusted a value (`msg.value`) that was never actually the value used for the transfer logic, Shipit's webhook pipeline picks *which organization's secret* to verify a signature with using one payload field (`repository.owner.login` / `organization.login`), but then dispatches all mutating logic (which `Stack`/`Repository` gets synced, updated, archived, etc.) using a **different** payload field (`repository.full_name`) that is never cross-checked against the field used for authentication. If any organization configured in a multi-org Shipit deployment has no `webhook_secret` set, verification is a no-op for payloads claiming to be from that organization, letting an attacker forge a webhook that authenticates as the "unsecured" org while writing to a stack that belongs to a completely different, secured org/repository.

### Finding Description
`WebhooksController#verify_signature` resolves the `GitHubApp` instance (and hence the HMAC secret used to validate the signature) purely from the payload's declared owner: [1](#0-0) [2](#0-1) 

The actual HMAC check is performed in `GitHubApp#verify_webhook_signature`: [3](#0-2) 

Note line 77: `return true unless webhook_secret`. Per the setup documentation, `webhook_secret` is explicitly optional per-organization in a multi-app configuration: [4](#0-3) [5](#0-4) 

Once `verify_signature` passes (trivially, for any org lacking a `webhook_secret`), the raw JSON body is dispatched unchanged to the relevant `Handler`, which resolves the target `Repository`/`Stack` using an entirely different field of the same attacker-controlled body — `repository.full_name` — with no relation to `repository.owner.login`/`organization.login` used for authentication: [6](#0-5) [7](#0-6) 

The binding that should hold is: **organization authenticated (via HMAC secret keyed by `repository_owner`) == owner of the repository being written (`repository.full_name`)**. Nothing in `WebhooksController`, `GitHubApp#verify_webhook_signature`, or `Handler#stacks`/`#repository_name` enforces this equality. Because `webhook_secret` presence is decided per-organization and can legitimately be blank, an attacker who knows (or is told) the name of any organization configured in Shipit without a `webhook_secret` can send a completely unsigned/forged POST to `/webhooks`, set `organization.login` (or `repository.owner.login`) to that unsecured org so `verify_webhook_signature` short-circuits to `true`, and set `repository.full_name` to any other repository tracked by Shipit — including ones belonging to a fully-secured organization — causing handlers to act on that unrelated stack.

### Impact Explanation
This breaks the "organization authenticated versus the repository that is written" trust binding called out as in-scope. Depending on which webhook event/handler is invoked, this allows an unauthenticated actor to force actions on stacks they have no relationship to: e.g. `PushHandler` will enqueue `GithubSyncJob` for arbitrary stacks matching a forged branch/SHA (potentially causing the sync/deploy pipeline to pick up a forged `expected_head_sha`), and pull-request handlers can archive/unarchive review stacks or update `PullRequest`/`Commit` state for arbitrary repositories, all without possessing that organization's real webhook secret. Where continuous deployment is enabled on a targeted stack, forged push/status events reaching `GithubSyncJob`/`Stack#sync_github` can influence what gets treated as the "undeployed" head and be picked up by CD, which lines up with the "unauthorized deploy" impact bucket.

### Likelihood Explanation
Requires: (1) a multi-organization Shipit deployment (explicitly documented and supported), and (2) at least one configured organization without a `webhook_secret` — an explicitly optional field per the setup docs. No GitHub App private key, `ApiClient` token, or session is needed; the attacker only needs to know the org name that is misconfigured (which may be discoverable, e.g. via error messages, org listings, or trial and error), then POST directly to the public `/webhooks` endpoint.

### Recommendation
Enforce that the organization used to select/verify the webhook secret matches the owner encoded in every payload field the handler subsequently trusts (i.e., derive `Repository`/`Stack` resolution from the same, already-authenticated `repository_owner`, or explicitly assert `repository.full_name`'s owner segment equals `repository_owner` before dispatch). Additionally, do not treat a missing `webhook_secret` as an implicit "verification passes" case — either require a `webhook_secret` for every configured organization or explicitly reject webhooks when a secret is not configured while still allowing signature bypass to be an opt-in, clearly-audited configuration switch, not the default fallback of `verify_webhook_signature`.

### Proof of Concept
Given a multi-org Shipit config such as:
```yml
production:
  github:
    unsecured-org:
      app_id: 1
      installation_id: 1
      # no webhook_secret set
    secured-org:
      app_id: 2
      installation_id: 2
      webhook_secret: real-secret
```
and a Shipit `Stack` tracking `secured-org/some-repo`, an attacker (no secret knowledge) sends:
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=anything-or-empty

{
  "ref": "refs/heads/master",
  "after": "attacker_controlled_sha",
  "repository": {
    "full_name": "secured-org/some-repo",
    "owner": { "login": "unsecured-org" }
  }
}
```
`repository_owner` resolves to `unsecured-org`, `Shipit.github(organization: "unsecured-org")` returns the app config with no `webhook_secret`, so `verify_webhook_signature` returns `true` regardless of the (invalid) `X-Hub-Signature`. `PushHandler` then resolves stacks via `repository.full_name` = `secured-org/some-repo` and enqueues `GithubSyncJob` for that stack with the attacker-supplied `expected_head_sha`, even though the request was never authenticated by `secured-org`'s real webhook secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.
