### Title
Missing non-default validation on `creator` allows pool creation with `pool_creator = Pubkey::default()`, permanently freezing accrued creator fees - (File: `programs/cp-swap/src/instructions/initialize_with_permission.rs`)

### Summary
The external report's bug class is: a value that a downstream "only-owner"-style check requires to be non-zero is never validated/initialized when a caller-controlled path is taken, causing the dependent function to be permanently unusable. The same root cause pattern — an address field that is stored unchecked and later relied upon as an exclusive signer/authority — exists in the `initialize_with_permission` instruction of this program.

### Finding Description
`InitializeWithPermission` accepts `creator` as a bare `UncheckedAccount<'info>` with no constraint requiring it be non-default or match the transaction payer/signer: [1](#0-0) 

This attacker-supplied `creator` key is passed directly into `pool_state.initialize(...)` and persisted as `pool_creator` with no sanity check: [2](#0-1) 

The stored `pool_creator` is later relied upon as the sole authorized signer for `collect_creator_fee`, whose `creator` account is a `Signer` constrained to equal `pool_state.pool_creator`: [3](#0-2) 

If a caller supplies `creator = Pubkey::default()` (or any account nobody controls the private key for) when calling `initialize_with_permission`, the pool is created successfully, trades accumulate `creator_fees_token_0`/`creator_fees_token_1` in `pool_state` via the swap paths, but `collect_creator_fee` can never be invoked because no one can produce a valid signature for `Pubkey::default()`. This mirrors the RFPSimpleStrategy bug class: a critical address is accepted without a non-default/reachability check, permanently breaking downstream logic that depends on it.

### Impact Explanation
Since `initialize_with_permission` is reachable by any payer who holds a valid `Permission` PDA (an unprivileged, non-admin path relative to fund custody — the payer only proves they're permitted to create a pool, not that `creator` is meaningful), an attacker or even a careless integrator can set `creator` to the default/burn pubkey. This permanently locks all accrued creator fees for that pool in the vaults, since `collect_creator_fee` (the only signer-gated path) can never succeed and `collect_creator_fee_permissionless` would create an ATA for the zero address's ownership and transfer funds there, i.e., an address that no one can ever move tokens out of. This constitutes a permanent freezing of protocol/LP fee funds accrued to the creator fee bucket.

### Likelihood Explanation
The `creator` account is fully attacker-controlled input to a permission-gated but not fund-owner-gated instruction; there is no code path enforcing `creator != Pubkey::default()` or that `creator` corresponds to a signer. Any pool created this way (accidentally or intentionally) permanently locks its future creator fees, making this straightforward to trigger with a single crafted transaction.

### Recommendation
Add an explicit non-default check on `creator` (and ideally require it to be a `Signer` or otherwise prove key ownership, consistent with `initialize.rs` where `creator` is a `Signer`) in `InitializeWithPermission`, e.g. `require_keys_neq!(ctx.accounts.creator.key(), Pubkey::default())`, before persisting it as `pool_creator`.

### Proof of Concept
1. Attacker (or any permitted payer) obtains a valid `Permission` PDA and calls `initialize_with_permission` with the `creator` account set to `Pubkey::default()` (or any keypair-less address) — no constraint rejects this.
2. Pool is created normally; `pool_state.pool_creator = Pubkey::default()`.
3. Users swap through the pool; `creator_fees_token_0`/`creator_fees_token_1` accumulate in `pool_state` per the fee-split logic in `swap_base_input.rs`/`swap_base_output.rs`.
4. `collect_creator_fee` can never be called successfully because its `creator: Signer<'info>` account must equal `pool_state.pool_creator` (`Pubkey::default()`), which has no corresponding private key — the accrued creator fees are permanently stranded in the pool vaults.
