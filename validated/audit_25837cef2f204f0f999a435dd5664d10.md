### Title
Front-running an AA's self-issuance of a capped asset permanently bounces the AA and freezes its funds — (File: `aa_composer.js`)

### Summary
`aa_composer.js`'s `issueAsset()` helper lets an Autonomous Agent (AA) auto-issue the capped asset it previously defined via an `asset` message, whenever the AA needs to pay out that asset but hasn't issued it yet. The uniqueness of the one-time issuance is enforced by a bare SQL check `SELECT 1 FROM inputs WHERE type='issue' AND asset=?` with no address filter, and the code comment assumes "only our AA can issue." That assumption is false unless the asset was defined with `issued_by_definer_only: true`. If it wasn't, any unprivileged user can post an ordinary unit issuing the full cap of that asset before the AA's trigger stabilizes, which consumes the one-shot issuance slot and causes every subsequent AA response depending on `issueAsset()` to bounce with `'already issued'`.

### Finding Description
`aa_composer.js` builds a payment message for an AA and calls `issueAsset()` when the AA's balance of `asset` is insufficient to cover the payload: [1](#0-0) 

For a capped asset, the check that guards the one-time issuance is:
```
if (objAsset.cap) { // only our AA can issue, no unstable consensus-breaking issues possible
    conn.query("SELECT 1 FROM inputs WHERE type='issue' AND asset=?", [asset], function(rows){
        if (rows.length > 0) // already issued
            return cb2('already issued');
        addIssueInput(1);
    });
}
``` [2](#0-1) 

This mirrors the `emitForWeek()` pattern in the audited report: a globally-idempotent, "first caller wins" gate (`emissionForWeek[week] > 0` there vs. `SELECT 1 FROM inputs WHERE type='issue' AND asset=?` here) that, once consumed by *anyone*, causes the economically meaningful caller (`newEpoch()` there, the AA's own `issueAsset()` here) to get a degenerate/failing result instead of the expected real value.

The only real protection against an outside party consuming this slot is `objAsset.issued_by_definer_only`, checked earlier in the same function:
```
if (objAsset.issued_by_definer_only && address !== objAsset.definer_address)
    return cb2("not a definer");
``` [3](#0-2) 

But this flag guards *the AA's own attempt*, not who else may issue. If the asset was defined with `issued_by_definer_only: false` (a pattern that appears in shipped sample AAs, e.g. team/shares assets with a cap that are meant to be freely tradable and are not restricted to definer-only issuance) — [4](#0-3)  — any address can construct and post a normal unit with an `issue` input for that asset (validated generically in `validation.js`, which only enforces double-issue uniqueness via a DB constraint, not "definer-only"): [5](#0-4) 

Because the capped-asset uniqueness check in `aa_composer.js` at line 1196 queries `inputs` globally by `asset` only (no `address` filter, unlike the non-capped branch at line 1204 which does filter by `address`), an attacker's unit — even one that issues to themselves and never reaches the AA — permanently satisfies "already issued" for that asset.

### Impact Explanation
Once the attacker's issue unit becomes stable, every future AA response path that depends on `issueAsset()` for this capped asset will unconditionally hit `cb2('already issued')` and bounce (all AA output/state changes for that trigger are rolled back). This is a permanent denial of the AA's intended token distribution logic for that asset — not a delay like the original report, but an irrecoverable freeze, since the "issued" flag can never be reset. Any bytes/assets sent to the AA in the bounced trigger are refunded minus bounce fees, but the AA's designed payout logic (e.g., distributing capped shares/rewards to users) is permanently broken for that asset, constituting AA fund/functionality freezing.

### Likelihood Explanation
The precondition (capped asset without `issued_by_definer_only: true`) is not exotic — it appears in ocore's own shipped sample AAs (e.g., the 51%-attack-game team-share asset). Any unprivileged user can trivially compose and broadcast a standard unit with an `issue` input for such an asset — no special privileges, timing precision beyond "before the AA's trigger stabilizes," or coordination with witnesses is required. The attack is cheap (one issue transaction) and deterministic.

### Recommendation
In `aa_composer.js`'s `issueAsset()`, do not treat "asset has any issue input from anyone" as equivalent to "our AA has issued it." Either:
1. Require `issued_by_definer_only: true` with `definer_address === address` as a hard precondition before an AA relies on self-issuing a capped asset (fail AA validation/definition otherwise), or
2. Change the uniqueness check to be scoped to issuances *by the AA's own address* (`... AND address=?`), and separately track/report to the AA author that a third party has already exhausted the cap so the AA can branch its logic (e.g., bounce gracefully with a state var flag rather than repeatedly failing silently), or
3. At AA-validation time (`aa_validation.js`), forbid defining a `cap`-based asset intended for AA self-issuance unless `issued_by_definer_only` is also set to true for that asset.

### Proof of Concept
1. Deploy an AA that, in one trigger, defines an asset with `cap: N` and `issued_by_definer_only: false` (mirroring `test/samples/51_attack_game.oscript`), and in a later trigger attempts to pay out `N` units of that asset via `issueAsset()` in `aa_composer.js` (as exercised in `test/aa_composer.test.js` "recently defined asset"/"issue recently defined asset").
2. After the asset-definition unit is stable, an attacker (unprivileged) composes and posts an ordinary unit with a single `issue` input for that asset (`type: "issue", amount: N, serial_number: 1`), self-addressed. `validation.js` accepts it because `issued_by_definer_only` is false.
3. Once that unit stabilizes, the AA's later trigger that relies on `issueAsset()` reaches:
   ```
   conn.query("SELECT 1 FROM inputs WHERE type='issue' AND asset=?", [asset], ...)
   ```
   which now returns a row, causing `cb2('already issued')` and bouncing the AA response permanently — reproducing the same "idempotent gate consumed by a third party" failure mode described in the original `emitForWeek()`/`newEpoch()` report, but with the AA and its downstream users being the ones permanently locked out.
