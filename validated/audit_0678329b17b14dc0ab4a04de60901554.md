### Title
Webhook signature verification is keyed on an attacker-controlled `repository.owner.login`/`organization.login` field while all webhook handlers act on the unrelated `repository.full_name` field, breaking the binding "organization that authenticated == repository that is written" - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App config (and therefore which HMAC `webhook_secret`) to validate the request against using `repository_owner`, a value read straight out of the unauthenticated JSON body. `PushHandler` (and every other handler, via the shared `Handler#stacks`/`#repository_name`) instead selects the `Stack`/`Repository` to mutate using `repository.full_name`, a second, independently-controlled field from the same body. Nothing ties these two fields together, so a valid signature for organization A's secret does not guarantee the payload is actually about a repository owned by organization A.

### Finding Description
`verify_signature` resolves the app/secret purely from attacker-supplied JSON: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` trivially returns `true` whenever no `webhook_secret` is configured for that organization: [3](#0-2) 

`Shipit.github_app_config` looks up the org config by the same attacker-controlled key with no additional constraint: [4](#0-3) 

Meanwhile, every webhook handler (e.g. `PushHandler`) resolves the actual `Stack`/`Repository` to operate on from a *different* field of the same payload, `repository.full_name`, which is never checked against `repository_owner`: [5](#0-4) [6](#0-5) 

Shipit explicitly supports multi-organization configuration where `webhook_secret` is documented as optional per organization: [7](#0-6) [8](#0-7) 

**Binding broken (equality that should hold but doesn't):**
`organization whose secret validated the HMAC signature == organization that owns the repository the handlers actually mutate`

Before the attacker's request: the signature check and the "which repository gets mutated" logic appear coupled because in the common single-org deployment they resolve to the same org.
After the attacker's request: an attacker who controls (or who targets) an organization entry in `secrets.github` that has no `webhook_secret` set (or whose secret they otherwise know) can send a webhook body where `repository.owner.login`/`organization.login` names that unsecured/known org (so `verify_webhook_signature` passes or is trivially satisfied) while `repository.full_name` names a completely different, sensitive repository/stack tracked under a properly-secured organization. `verify_signature` never inspects `repository.full_name`, and the handlers never inspect `repository.owner.login`, so the forged event is accepted and dispatched against the victim stack.

### Impact Explanation
Because handlers key exclusively on `repository.full_name`, a forged (or trivially-passing, secret-less) webhook can inject unauthenticated `push`, `status`, or `check_suite` events against any `Stack` tracked by the Shipit instance, regardless of which organization's secret actually validated. This lets an unprivileged attacker: enqueue `GithubSyncJob` for a stack they don't own/control, and forge commit `Status`/check-run state for commits that legitimate automation (e.g. merge-queue safety checks) consumes to decide whether it is safe to auto-merge or deploy. This crosses the repository-write trust boundary described by the rules ("an organization that authenticated versus the repository that is written") and can feed into unauthorized deploy/merge decisions downstream of falsified CI/status state.

### Likelihood Explanation
Exploitability depends on deployment configuration: it requires the Shipit instance to be configured with multiple GitHub organizations (a documented, first-class feature) where at least one configured organization has no `webhook_secret` set (explicitly called out as "(optional)" in `docs/setup.md`) or whose secret the attacker can otherwise obtain, while other organizations host the actual sensitive stacks. Given the feature is officially supported and the secret is optional by design, this is a realistic misconfiguration rather than a purely theoretical one, but it is not guaranteed to be present in every deployment.

### Recommendation
Bind webhook signature verification to the same repository identity the handlers use for `Stack`/`Repository` resolution: verify the signature using the secret associated with `repository.full_name`'s owning organization (or verify the payload's `repository.full_name` belongs to the same organization used for signature selection) before dispatching to any handler. Also consider making `webhook_secret` mandatory (reject webhooks for any organization without one configured) rather than silently trusting unsigned payloads.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.github`: `victim-org` (has stacks, has `webhook_secret` set) and `attacker-org` (no `webhook_secret` configured, or one the attacker knows).
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and `verify_webhook_signature` returns `true` immediately because `attacker-org` has no `webhook_secret` (or because the attacker supplies a signature valid for a secret they know) — see `app/controllers/shipit/webhooks_controller.rb:24-30` and `lib/shipit/github_app.rb:76-83`.
4. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")` — see `app/models/shipit/webhooks/handlers/handler.rb:32-38` — and enqueues `GithubSyncJob`/`sync_github` for the victim stack, despite the signature having nothing to do with `victim-org`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
