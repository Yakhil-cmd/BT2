### Title
Webhook signature verification is keyed to the payload's declared organization, not the repository being written to, allowing signature bypass via a second unauthenticated org - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App config (and therefore which `webhook_secret`) to verify the HMAC signature against using a field taken from the same unauthenticated payload (`repository.owner.login`, falling back to `organization.login`). The record that is actually mutated by the handler (`Repository.from_github_repo_name(payload.dig('repository', 'full_name'))`) is resolved independently from a different payload field. In a multi-organization Shipit installation, these two values are never checked for consistency, so an attacker can pick an organization whose app config has no `webhook_secret` configured to trivially pass signature verification, while pointing `repository.full_name` at a stack belonging to a different, properly-secured organization.

### Finding Description
Signature verification: [1](#0-0) 

```ruby

  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end
...
def repository_owner
  # Fallback to the organization sub-object if repository isn't included in the payload
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization:)` loads the app config for whichever org name is asserted in `repository_owner`: [2](#0-1) 

`GitHubApp#verify_webhook_signature` unconditionally trusts the request if that org has no `webhook_secret` configured: [3](#0-2) 

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```

Once verification passes, event handlers resolve the target `Repository`/`Stack` from a **different** field of the same untrusted payload — `repository.full_name` — with no cross-check against `repository_owner`: [4](#0-3) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

Shipit explicitly supports multi-organization deployments where each org has its own independently configured `webhook_secret`, `app_id`, `installation_id`, etc., as shown in the reference multi-org secrets file: [5](#0-4) 

The binding that should hold is: **organization authenticated by `verify_signature` == organization owning the repository/stack actually written to by the handler**. Because `repository_owner` (used only to pick the verification secret) and `repository.full_name` (used to pick the record to mutate) are both attacker-controlled fields inside the same JSON body, an attacker can decouple them: set `repository.owner.login`/`organization.login` to an organization configured with `webhook_secret: nil`, and set `repository.full_name` to `VictimOrg/some-repo`, where `VictimOrg` has a real, unknown secret configured. `verify_signature` will authenticate against the unsecured org (trivially succeeding since `webhook_secret` is blank) while the handler processes the forged event against the victim's repository/stack.

### Impact Explanation
This breaks the deployment-trust binding "organization authenticated vs. repository that is written," matching the required analog class. Concretely:
- A forged `status` event (handled by `StatusHandler`, which creates `Status` records) can mark a victim commit's CI state as `success` even though no legitimate CI ever ran, which is read by the merge queue and can lead to an **unauthorized merge**.
- A forged `push` event (`PushHandler`) can trigger `stack.sync_github` on the victim's stack.

Both land in the Critical bucket ("cross-repository writes, or an unauthorized deploy, rollback or merge") since the attacker never needed the victim organization's `webhook_secret`, an `ApiClient` token, or repository write access — only knowledge that a second, less-secured organization is registered in the same Shipit installation.

### Likelihood Explanation
Requires a Shipit installation configured with more than one GitHub organization (an explicitly documented and supported configuration), and at least one of those organizations left with `webhook_secret` unset — a plausible misconfiguration, especially for a newly onboarded org during setup, since `verify_webhook_signature` silently no-ops instead of failing closed when the secret is blank.

### Recommendation
Do not select the verification secret from attacker-controlled payload fields. Verify the signature against the organization that actually owns `repository.full_name` (i.e., resolve the target `Repository`/organization first, then use *that* organization's configured app to verify), and make `verify_webhook_signature` fail closed (return `false`) when no `webhook_secret` is configured rather than trivially returning `true`, so misconfigured/unsecured orgs cannot be used to bypass verification for other repositories.

### Proof of Concept
1. Deploy Shipit with two GitHub Apps configured, e.g. `OrgUnsecured` (no `webhook_secret`) and `OrgVictim` (real `webhook_secret`, has a stack tracking `OrgVictim/app`).
2. Send a webhook POST to `/webhooks` with header `X-Github-Event: status` and no valid `X-Hub-Signature` (or any garbage value), and a JSON body:
```json
{
  "sha": "<victim-commit-sha>",
  "state": "success",
  "context": "ci/tests",
  "repository": {
    "full_name": "OrgVictim/app",
    "owner": { "login": "OrgUnsecured" }
  }
}
```
3. `repository_owner` resolves to `OrgUnsecured`, so `Shipit.github(organization: "OrgUnsecured")` loads a config with `webhook_secret: nil`, and `verify_webhook_signature` returns `true` unconditionally — the request passes verification.
4. `StatusHandler` (via `Handler#repository_name` → `payload.dig('repository','full_name')`) resolves `OrgVictim/app` and records the forged `success` status against the victim's commit, independent of the organization used for authentication.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
