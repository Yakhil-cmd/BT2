### Title
Webhook signature scoped to `repository.owner.login` while Stack resolution keys on `repository.full_name` allows one onboarded GitHub organization to forge state-changing events for another organization's stacks - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In Shipit's multi-organization configuration (documented in `docs/setup.md` "Using Multiple GitHub Applications" and exercised in `test/dummy/config/secrets_double_github_app.yml`), each onboarded GitHub organization gets its own `webhook_secret`. The HMAC signature check picks which organization's secret to verify against using `repository.owner.login` (or the `organization.login` fallback), but every webhook handler resolves the target `Stack`/`Repository` using a completely different field, `repository.full_name`, with no cross-check that the two agree.

### Finding Description
`WebhooksController#verify_signature` selects the verifying `GitHubApp`/secret via: [1](#0-0) [2](#0-1) 

using `repository_owner = payload.dig('repository', 'owner', 'login') || payload.dig('organization', 'login')`.

`Shipit.github(organization:)` maps that string to a distinct `GitHubApp` (and distinct `webhook_secret`) per the multi-org schema: [3](#0-2) 

Once the signature is accepted, every default handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc.) resolves the affected `Stack` via `Handler#repository_name`, which reads a *different* JSON field: [4](#0-3) 

Nothing re-derives or validates that `repository.full_name`'s owner segment equals the `repository_owner` value that selected the verifying secret. The two fields sit side by side in the same attacker-supplied JSON body and are never bound together.

The equality that should hold but doesn't:
`organization whose webhook_secret authenticated the request == organization that owns the repository the handler writes to`

Before the attacker's request: in a legitimate GitHub-relayed webhook, `repository.owner.login` and `repository.full_name`'s prefix are always consistent because GitHub generates both fields from the same underlying repository object.

After the attacker's request: if the request is crafted directly against `/webhooks` (bypassing GitHub) and signed with a secret the attacker legitimately possesses for *their own* onboarded organization (e.g., because they administered that org's GitHub App per `docs/setup.md`), they can set `repository.owner.login`/`organization.login` to their own org (so `verify_signature` picks their own valid secret) while setting `repository.full_name` to `"OtherOrg/tracked-repo"`. The signature check passes, and the handler then mutates state for `OtherOrg/tracked-repo`'s `Stack` — a repository whose real organization never authenticated this event.

### Impact Explanation
This breaks organization isolation in a documented multi-tenant deployment. Concretely reachable actions once signature verification is satisfied with the wrong org's data:
- `StatusHandler#process` calls `Commit#create_status_from_github!`, letting the attacker inject fabricated CI status entries against commits belonging to another organization's stack — these feed into `required_statuses`/`deployable?` checks that gate whether a commit can be shipped.
- `PushHandler#process` calls `stack.sync_github`, and `CheckSuiteHandler#process` schedules check-run refreshes, both operating on the victim organization's `Stack`/`Commit` records.

Because commit deployability gates (CI status) can be forged this way, this can escalate into an unauthorized deploy of another organization's stack — matching the "Critical: unauthorized deploy" impact bucket in scope. It requires no Shipit session, `ApiClient` token, or access to the victim organization's own webhook secret — only a valid secret for *some* onboarded organization plus knowledge of the target's `full_name`.

### Likelihood Explanation
This requires a multi-organization Shipit deployment (explicitly documented as supported) and an attacker who legitimately controls one onboarded organization's webhook secret while attempting to affect a *different* onboarded organization's stack. This is a plausible tenant-isolation failure in any Shipit installation onboarding several distinct/mutually-untrusted GitHub organizations, which is exactly the scenario the multi-org feature (`test/dummy/config/secrets_double_github_app.yml`, `docs/setup.md`) is built for.

### Recommendation
In `Handler#repository_name` (or in `WebhooksController`), verify that the resolved repository's owner matches the organization used to authenticate the request (i.e., compare `repository.full_name.split('/').first` against `repository_owner` used in `verify_signature`), rejecting the webhook if they diverge. Alternatively, pass the authenticated organization down into the handler layer and have `Repository.from_github_repo_name` scope its lookup by that authenticated organization instead of trusting the raw `full_name` field alone.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret`, per `docs/setup.md`'s multi-app schema (as in `test/dummy/config/secrets_double_github_app.yml`). `OrgB` has a Shipit-tracked stack for `OrgB/prod-app`.
2. As someone who legitimately knows `OrgA`'s `webhook_secret` (e.g., the person who set up `OrgA`'s GitHub App), craft a `status` webhook payload:
```json
{
  "sha": "<commit sha in OrgB/prod-app>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "full_name": "OrgB/prod-app", "owner": { "login": "OrgA" } }
}
```
3. Compute `X-Hub-Signature: sha1=HMAC-SHA1(OrgA_webhook_secret, raw_body)` and POST to `/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#repository_owner` reads `"OrgA"`, `verify_signature` validates successfully against `OrgA`'s secret.
5. `StatusHandler#process` uses `payload.dig('repository','full_name')` = `"OrgB/prod-app"` to locate the real `OrgB` commit and calls `create_status_from_github!`, injecting a forged "success" status that can satisfy deploy-gating checks for `OrgB`'s stack — despite `OrgB` never having authenticated this event.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
