### Title
`flash_position` strands undeclared callback tokens on the controller forever — no sweep or refund path exists - (File: contracts/controller/src/strategies/flash_position.rs)

### Summary
`Starklane::depositTokens` accepts any `msg.value` with no minimum-fee check, so a wrong payment leaves user assets locked. The same class exists in `Controller::flash_position`: tokens transferred to the controller during the receiver callback are only handled if they appear in `collaterals` (deposited) or `refund_assets` (refunded). Any token pushed to the controller that is in neither list — including the debt token itself when it is not refund-listed — is neither credited nor returned, and the controller exposes no endpoint to recover it. The funds are permanently frozen.

### Finding Description
`flash_position` mints debt, forwards the measured receipt to a caller-chosen `receiver`, and invokes `execute_flash_position` (`flash_position.rs:131-141`). After the callback the controller reconciles balances in exactly two ways:

1. `collect_collateral_deposits` measures the controller's balance delta for each asset declared in `collaterals` and deposits positive deltas as supply (`flash_position.rs:145-146`).
2. `refund_listed_assets` returns positive deltas only for addresses listed in `refund_assets` (`flash_position.rs:148`).

Everything else is ignored: pre-existing controller balances are explicitly excluded as baselines (`flash_position.rs:124-130`), and any asset that arrives during the callback but is absent from both lists stays on the controller balance with no bookkeeping entry and no outbound transfer. The debt asset is a concrete case: `mint_and_forward` sends the full borrowed `measured` amount to the receiver (`flash_position.rs:285-292`), and if the receiver returns some of it (e.g., an over-purchase refund leg) while the caller did not list the debt asset in `refund_assets`, the returned tokens sit on the controller uncredited — and crucially do not reduce the minted debt. The protocol docs confirm there is no recovery path: "Undeclared callback assets receive neither credit nor refunds. There is no controller sweep endpoint" (`docs/reference/endpoints.md:86`).

### Impact Explanation
Permanent freezing of funds: any token transferred to the controller during the callback that is not declared as collateral or listed for refund becomes unrecoverable protocol dust. A common reachable case is a receiver that swaps the borrowed tokens, buys collateral, and pushes both the collateral and the leftover debt tokens back to the controller — a natural callback shape — while the caller only declared the collateral. The leftover debt tokens are stuck forever; the user still owes the full minted debt and loses the returned principal. Unlike `repay` and `recapitalize`, which refund overpayment/excess, this path has no fallback refund and no admin or permissionless sweep exists to rescue the balance.

### Likelihood Explanation
Medium. Reaching it requires only an unprivileged caller with an account (or account_id 0) calling `flash_position` with a receiver contract whose callback transfers tokens to the controller, plus a collateral/refund declaration that omits one pushed asset. Callbacks that return residual debt tokens or multiple assets are a realistic integration pattern (the SDK docs themselves show receivers pushing tokens via plain `transfer`). It is user-configurable misuse rather than an always-on bug, which caps severity, but the loss is permanent and borne entirely by the user.

### Recommendation
Treat callback-delivered tokens defensively:

- Auto-refund any positive balance delta on the controller for assets not declared in `collaterals` (or at minimum, default the debt asset into the refund set so returned debt principal goes back to the caller).
- Alternatively/additionally, add a permissionless sweep that forwards non-bookkept controller balances above the bookkeeping-required reserve for each listed asset, so stranded tokens are recoverable rather than burned in place.

### Proof of Concept
Reachable call shape for an unprivileged user:

```rust
// Alice owns a strategy-mode account; receiver is her deployed contract.
controller.flash_position(
    &alice,                       // caller
    &0,                           // account_id = create
    &spoke_id,
    &PositionMode::Multiply,
    &HubAssetKey { hub_id, asset: usdc },   // debt
    &10_000_000,                  // amount
    &receiver,                    // Wasm receiver (not controller/pool)
    &data,
    &vec![(HubAssetKey { hub_id, asset: xlm }, 1)], // collaterals: XLM only
    &Vec::new(&env),              // refund_assets: EMPTY — USDC not listed
);
```

Inside `execute_flash_position`, the receiver swaps part of the 10 USDC into XLM and pushes both tokens to the controller:

```rust
token::Client::new(&env, &xlm).transfer(&self_addr, &controller, &collateral_out);
token::Client::new(&env, &usdc).transfer(&self_addr, &controller, &leftover_usdc);
```

Result per `flash_position.rs:145-148`: XLM delta is deposited as supply; the USDC delta is not in `refund_assets`, so `refund_listed_assets` skips it. The USDC sits on the controller permanently — uncredited, unrefunded, and the minted debt is unaffected ("Refunding unused debt tokens does not repay the minted debt", `skills/xoxno-lending-contracts/flash-loans.md:135`; "no controller sweep endpoint", `endpoints.md:86`).
