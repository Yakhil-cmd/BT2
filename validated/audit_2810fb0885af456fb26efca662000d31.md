### Title
Cross-organization commit-status forgery bypasses per-repository webhook trust binding - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
The `M-24` report's root cause is a broken invariant: a value used to *gate* a security-relevant decision (`block.chainid == CHAIN_ID_MAINNET`) is decoupled from the actual deployment context (Arbitrum), so the gate is always false and the real environment is silently ignored. The equivalent trust binding in Shipit's webhook pipeline is: `organization whose webhook signature was verified == repository/commit that gets written`. `WebhooksController#verify_signature` picks the signing organization from `params.dig('repository','owner','login')` and validates the HMAC against that organization's own `webhook_secret` [1](#0-0) , but `Shipit::Webhooks::Handlers::StatusHandler#process` never re-checks which repository/organization the event actually targets — it looks up commits **globally by SHA** and writes a GitHub status onto them [2](#0-1) .

### Finding Description
`verify_signature` derives the signing organization solely from the `repository.owner.login` (or `organization.login`) field of the attacker-supplied JSON body, and fetches that organization's `Shipit.github` app to validate `X-Hub-Signature` [1](#0-0) . Any organization onboarded to a multi-tenant Shipit instance necessarily has a `webhook_secret` that its own admins configure on GitHub's side and therefore know/control.

Once the signature check passes, `WebhooksController#create` dispatches the parsed JSON straight to the registered handlers with no further ownership check: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [3](#0-2) .

`StatusHandler` only requires `sha`, `state`, and cosmetic fields — it does **not** require or validate a `repository` object at all [4](#0-3) . Its `process` method resolves target commits with an unscoped, instance-wide query:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [2](#0-1) 
This contrasts with other handlers in the same `Handlers::Handler` base class, which do scope work through `Repository.from_github_repo_name(repository_name)` before touching data [5](#0-4) . `StatusHandler` bypasses that base-class scoping mechanism entirely, since it doesn't use `stacks`/`repository_name` at all.

Equality that should hold but doesn't:
`organization authenticated by verify_signature (repository.owner.login in the payload) == organization/repository whose commit status is mutated (Commit.where(sha: params.sha), unscoped)`

Because `Commit.sha` is not guaranteed unique per repository in general (and regardless of collisions, the query has zero repository/org predicate), any organization that is a legitimate, onboarded Shipit tenant can sign a `status` webhook event using its own `webhook_secret`, set `repository.owner.login` to its own org (to pass `verify_signature`), and set `sha` to a commit SHA belonging to a **different** organization's stack tracked by the same Shipit instance. `StatusHandler` will happily create/overwrite a `Status` on that foreign commit.

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" binding called out as an in-scope analog pattern, and it maps to the "cross-repository writes" / "unauthorized deploy" outcomes that Sherlock and this scan treat as Critical/High:

- Commit statuses gate CI (`ci.require`, `ci.blocking`) checks that Shipit uses to decide whether a commit is deployable. A tenant with no access to a victim repository can forge a passing status (`state: "success"`) for a specific commit SHA in the victim's repository, potentially making an otherwise CI-failing/blocked commit appear deployable, or forge a failing status to sabotage the victim's deploy pipeline (denial of legitimate merges/deploys is out of scope per rules, but enabling an **unauthorized deploy** by faking a green CI status is in-scope).
- No credential belonging to the victim organization is required — only knowledge of the attacker's own (unprivileged, low-trust) org's webhook secret, which is exactly the kind of unprivileged-attacker path the rules ask to consider.

### Likelihood Explanation
Any organization that is a legitimate Shipit tenant (multi-tenant install with several `Shipit.github` org configs) can trigger this at will, at low cost: craft a JSON body with an arbitrary `sha`, sign it with their own webhook secret, and POST it to `/webhooks`. Guessing a victim's exact commit SHA is the only real precondition; SHAs are frequently public (in the target's own public GitHub repo, PRs, CI logs, Shipit's own UI if it exposes recent SHAs) so this is easily satisfiable rather than requiring brute force.

### Recommendation
`StatusHandler` (and any other handler that mutates data) must scope its lookup to the repository verified by `verify_signature`/present in the same trusted payload, e.g. join `Commit` through `Stack -> Repository` and filter by the repository resolved via `Repository.from_github_repo_name(payload.dig('repository','full_name'))`, mirroring what `Handler#stacks`/`#repository_name` already does for other handlers, and reject/ignore statuses whose payload repository does not match the organization used in `verify_signature`.

### Proof of Concept
1. Onboard (or control) GitHub organization `attacker-org` in the Shipit instance, with a valid `webhook_secret` known to the attacker (as is normal for any tenant admin).
2. Obtain the SHA of a commit belonging to `victim-org/victim-repo`, a stack tracked by the same Shipit instance (e.g., public commit SHA).
3. Build a `status` event payload:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" }
}
```
4. Sign the raw JSON body with `attacker-org`'s known `webhook_secret` using HMAC-SHA1 and set `X-Hub-Signature`; set `X-Github-Event: status`.
5. POST to `Shipit::Engine`'s `/webhooks` route.
6. `verify_signature` succeeds because it only checks `attacker-org`'s secret against `repository.owner.login = attacker-org` [1](#0-0) .
7. `StatusHandler#process` finds the victim's commit via the unscoped `Commit.where(sha: params.sha)` and writes the forged status onto it [2](#0-1) , even though the attacker has no relationship to `victim-org/victim-repo`.
