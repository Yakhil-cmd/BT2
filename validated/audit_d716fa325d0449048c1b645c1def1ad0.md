### Title
Missing cosigner-authorization check lets any paired device request signing on a locally-held wallet address - ([File: wallet.js])

### Summary
`wallet.js`'s `handleMessageFromHub` processes the `"sign"` message from *any* paired device and, when the target address is hosted locally (`ifLocal`), immediately proceeds to build/emit a `signing_request` without verifying that the sending device is actually a registered cosigner of that address. The equivalent check *is* implemented for the `ifRemote` branch (`other_device_addresses.includes(from_address)`), showing the check was intentionally designed but is missing/commented-out for local addresses. [1](#0-0) [2](#0-1) 

### Finding Description
The `"sign"` case validates the shape of the address, signing path and unsigned unit, but the authorization step that should confirm "is `from_address` actually one of the co-signing devices for `body.address`" is explicitly commented out:
```
ifLocal: function(objAddress){
    // the commented check would make multilateral signing impossible
    //db.query("SELECT 1 FROM extended_pubkeys WHERE wallet=? AND device_address=?", [row.wallet, from_address], function(sender_rows){
    //    if (sender_rows.length !== 1)
    //        return callbacks.ifError("sender is not cosigner of this address");
        callbacks.ifOk();
        ...
        eventBus.emit("signing_request", objAddress, body.address, objUnit, assocPrivatePayloads, from_address, body.signing_path);
``` [3](#0-2) 

Compare this with the `ifRemote` branch, which enforces exactly the missing invariant before forwarding/proxying a signing request:
```
ifRemote: function(device_address, other_device_addresses){
    if (device_address === from_address)
        return callbacks.ifError(...);
    if (!other_device_addresses.includes(from_address))
        return callbacks.ifError("you are not listed as a cosigner for this address "+body.address);
``` [2](#0-1) 

Root cause: the authorization boundary ("is the requesting device permitted to ask this wallet to sign for address X") is enforced asymmetrically — present for remote/proxy delegation but absent for the local case, which is the actual signing endpoint. As a direct consequence, any device that is merely paired/correspondent with the victim wallet (not necessarily an actual cosigner of the shared/multisig address in question) can name **any** locally-known address (`body.address`) plus a `signing_path`, supply a fully-formed unit (potentially spending the victim's own single- or multi-sig funds), and cause the wallet to fire the `signing_request` event carrying that unit, its outputs, and any decrypted private payloads — all without the library first checking that the sender is entitled to request a signature for that address. [4](#0-3) 

This directly parallels the CVE-2024-7062 bug class: a component that performs a privileged/sensitive operation (constructing and dispatching a signing request that can lead to fund movement) fails to validate that the caller is authorized to invoke it for the specific target resource (the address), even though the code base clearly implements this exact authorization check elsewhere for a symmetric code path.

### Impact Explanation
`signing_request` is the hand-off point at which a signature over a spending unit is produced (interactively via UI confirmation in end-user wallets, or automatically in unattended/headless signer setups that are commonly used for exchange hot wallets, service multisig cosigners, and automated bots built on top of this library). Because the authorization check that limits who may trigger this hand-off is missing on the local path, any paired device — including one that is not a legitimate cosigner of the address — can solicit a signature for an attacker-chosen unit against a wallet address it does not co-own. In deployments where signing is automated/unattended (a supported and common configuration for `ocore`-based wallets), this enables unauthorized spending of funds from the targeted address. Even in interactive deployments, it weakens/undermines the intended cosigner authorization model that the code explicitly implements on the sibling `ifRemote` path, and can be leveraged to trick users into signing arbitrary attacker-crafted transactions under the guise of a legitimate co-signing flow.

### Likelihood Explanation
Any device that has an established pairing (a normal, low-privilege relationship, not necessarily a designated cosigner) can send this message; the code performs solid syntactic validation but no cosigner authorization for `ifLocal`, so the path is trivially reachable by a correspondent as described in scope ("paired device" is a permitted attacker entity). No cryptographic break, race condition, or privileged access is required — only being paired as a device.

### Recommendation
Restore/implement the analogous check in the `ifLocal` branch of the `"sign"` handler: before emitting `signing_request`, verify `from_address` is among the registered cosigning devices for `body.address` (e.g., query `extended_pubkeys`/shared-address cosigner tables, mirroring the check used in `ifRemote`). Reject with `callbacks.ifError("sender is not cosigner of this address")` when the check fails, consistent with the equivalent enforcement already present for the remote/proxy case.

### Proof of Concept
1. Attacker device pairs with the victim wallet (a normal, unprivileged pairing operation).
2. Attacker sends a `"sign"` message to the victim's device via the hub:
   - `body.address` = any address the victim wallet locally hosts (single-sig or shared/multisig), even though the attacker's device is not listed as a cosigner for it.
   - `body.signing_path` = `"r"` (or a valid nested path).
   - `body.unsigned_unit` = a fully formed unit spending the victim's funds to an attacker-controlled output, with placeholder authentifiers.
3. `handleMessageFromHub` → case `"sign"` passes all structural checks (valid address, valid path, well-formed unit, valid payload hashes) and calls `findAddress`, which resolves to `ifLocal` since the address is hosted locally.
4. Because the cosigner check is commented out, the code immediately proceeds to `callbacks.ifOk()` and emits `eventBus.emit("signing_request", ...)` for the attacker-supplied unit — without ever confirming the attacker's device had any right to request a signature on that address.
5. In any deployment where a listener on `signing_request` automatically signs (headless/unattended wallet configurations commonly built on this library), the victim's funds are signed and spent to the attacker-chosen output with no further authorization check.

*Note:* The consumer of the `signing_request` event (e.g., a headless-wallet auto-signer) lives outside this repository and could not be inspected here; the finding is scoped strictly to the missing authorization check inside `ocore`'s `wallet.js`, which is the root cause reachable from an unprivileged paired device.
