### Title
`StatusHandler#process` writes GitHub statuses to any commit matching `params.sha`, ignoring both `params.branches` and the originating repository - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler` accepts a `branches` parameter but never reads it, and `Commit.where(sha: params.sha)` is not scoped to the stack/repository that the incoming webhook claims to originate from. Any webhook whose signature validates for *some* repository can therefore mutate the `Status` history of a commit belonging to a completely different stack, as long as the two repositories ever share an identical commit SHA (a routine occurrence with forks/shared history), regardless of the `branches` array sent in the payload.

### Finding Description
The claimed binding — "branches named in payload == branches of the stack whose commit is mutated" — is false on both sides of the check: `params.branches` is declared in the `params do ... end` schema but is never referenced inside `process`: [1](#0-0) 

The only binding actually enforced is `sha == sha`, applied globally via `Commit.where(sha: params.sha)`, with **no** `stack_id`/repository filter: [2](#0-1) 

`Commit#create_status_from_github!` also performs no repository check — it just records the status against whatever stack owns that `Commit` row: [3](#0-2) 

The existing test named `":state in an untracked branche bails out"` does **not** actually test branch filtering — it uses a nonexistent `sha` (`'notarealcommit'`), so the 200 OK response is caused by `Commit.where(sha:)` returning no rows, not by any branch check: [4](#0-3) 

Exploit path: An attacker who owns/administers any GitHub repository that has the Shipit GitHub App installed (a routine, unprivileged action available to any repo owner) can create a commit object identical in content to a commit already tracked by a *different*, unrelated Shipit stack (e.g., by replaying a shared/forked commit into their own repo — Git SHA-1s are content-derived and identical across repos for identical commit content). The attacker then calls GitHub's Statuses API against their own repo for that SHA with an arbitrary `state`/`description`/`target_url`. GitHub delivers this as a `status` webhook, correctly signed for the attacker's own repository/installation. `WebhooksController` → `StatusHandler#process` looks up `Commit.where(sha: ...)` with no regard for which repository sent the webhook, finds the commit under the victim's unrelated stack, and calls `create_status_from_github!`, writing a forged `Status` row to that victim stack.

Existing guards do not stop this: `verify_signature`/`GitHubApp#verify_webhook_signature` only prove the payload was signed by *some* legitimate GitHub App installation (the attacker's own), not that the `sha` inside the payload belongs to that installation's repository. The `ExplicitParameters` schema validates types/shape only, not ownership. There is no `require_permission!`/`stacks` scope check anywhere in this handler tying the mutated `Commit`/`Stack` back to the webhook's `repository` field.

### Impact Explanation
A forged `status` webhook from an attacker-controlled repository can write a `Status` row onto a commit belonging to an unrelated, victim-owned stack whenever the two repos share a commit SHA. Since commit statuses feed `Commit#deployable?`/`blocked?`/continuous delivery scheduling (`stack.schedule_merges`, `ContinuousDeliveryJob`), this can push a victim's commit toward "success"/deployable state or otherwise pollute their CI status history — "a payload for one repository mutating another's stack[/]commit" — matching the Critical impact category. It is repeatable against any stack/commit for which a SHA collision (shared commit content) can be arranged, e.g. forks, vendored/shared code, or upstream-cherry-picked commits.

### Likelihood Explanation
Requires: (1) attacker has any repository with the Shipit GitHub App installed — a normal, unprivileged repo-owner action, not requiring any Shipit credentials; (2) attacker needs a commit whose SHA matches one tracked by the victim stack — achievable deterministically by pushing an identical commit (same tree/parent/author/timestamp/message) into their own repo, which is realistic for forked or shared-history repositories. No Shipit secrets, sessions, or API tokens are needed. This is entry-level GitHub usage plus normal use of the Statuses API on the attacker's own repo, making it low-cost and repeatable.

### Recommendation
Scope `StatusHandler#process` to only update commits belonging to the stack that owns the webhook's `repository`/`installation`, e.g. `commit.stack.github_repo_name == payload.repository.full_name` (and organization/installation match) before calling `create_status_from_github!`. Additionally, either remove the unused `branches` parameter or use it to skip processing for branches not tracked by the target stack, per its apparent original intent.

### Proof of Concept
```ruby
test ":state from repository A must not create a Status on a commit owned by unrelated stack B" do
  request.headers['X-Github-Event'] = 'status'

  stack_b = shipit_stacks(:shipit2) # a different repository/stack fixture
  colliding_sha = 'deadbeef' * 5
  commit_b = shipit_commits(:first) # tracked under stack_b, sha = colliding_sha (set up in fixtures)

  # payload claims to originate from a *different* repository than stack_b's
  body = {
    'sha' => colliding_sha,
    'state' => 'success',
    'branches' => [], # branches is empty/unrelated -- proves it has no gating effect
    'repository' => { 'full_name' => 'attacker/unrelated-repo', 'owner' => { 'login' => 'attacker' } }
  }.to_json

  assert_no_difference -> { commit_b.statuses.count }, 'status must not be written for an unrelated repo' do
    post :create, body:, as: :json
  end
end
```
Before the fix, this assertion fails: `commit_b.statuses.count` increases by 1 even though `branches` is empty and the payload's `repository` does not match `stack_b`'s repository, demonstrating that neither `branches` nor repository identity gate `create_status_from_github!`.
