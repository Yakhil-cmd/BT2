### Title
Cross-Organization Commit Status Forgery via Unscoped `sha` Lookup in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates an incoming webhook only against the GitHub organization named by `repository.owner.login` (or the `organization.login` fallback) in the payload [1](#0-0) . Once that check passes, `StatusHandler#process` writes a CI status to **every** `Commit` row that matches the raw `sha` field from the same payload, with no scoping to the repository/organization that was actually authenticated [2](#0-1) . This breaks the equality "organization that authenticated == repository that is written": the org whose `webhook_secret` validated the request is not the org whose commit ends up receiving the status write.

### Finding Description
`Shipit.github(organization: repository_owner)` selects the webhook secret to verify against based on `repository_owner`, itself taken directly from the untrusted JSON body [3](#0-2) . Signature verification therefore only proves "this request was signed by the org named X in this payload" — it says nothing about which repository/commit the handler logic is permitted to mutate.

The base `Handler` class exposes `repository_name` (derived from `payload.dig('repository','full_name')`) and uses it to scope most handlers to `Repository.from_github_repo_name(repository_name)` [4](#0-3) . `StatusHandler`, however, does not use this scoping at all. It looks up commits with a bare, global query:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [2](#0-1) 

`Commit.sha` is not unique per repository/organization across the whole Shipit installation — any stack tracking a commit with that SHA (e.g., a shared/forked/vendored history, or simply a colliding SHA prefix match across independently-hosted repos tracked by different stacks) will receive the forged status, regardless of which organization the request was signed for.

**Binding broken:** `organization that authenticated the webhook (via webhook_secret keyed on payload.repository.owner.login)` != `repository/commit that is actually written (Commit rows selected purely by payload.sha, with zero repository/org scoping)`.

### Impact Explanation
CI statuses recorded via `create_status_from_github!` feed directly into Shipit's `ci.require` deploy-gating logic (referenced throughout `app/models/shipit/stack.rb` and `app/models/shipit/commit.rb`, and documented in the README's CI section). An attacker who controls (or has configured) any GitHub organization that Shipit trusts — including one they legitimately administer, with their own known `webhook_secret` — can pass `verify_signature` for their own org, then send a `status` event containing a `sha` that matches a commit tracked by a **different, higher-trust** stack. Because the write path has no cross-check that the commit belongs to the authenticated organization, this can inject a fabricated "success" CI status onto a commit in a repository/stack the attacker never had access to, potentially satisfying `ci.require` and unblocking an otherwise-gated automatic or continuous deploy — an unauthorized deploy enablement, without ever holding credentials, session, or write access for the victim repository.

### Likelihood Explanation
Exploitation requires only that the attacker control any GitHub organization/App entry configured in `Shipit.github` (a normal, low-privilege tenant in a multi-org Shipit deployment as documented in `config/secrets.development.shopify.yml`), plus knowledge of a `sha` that also exists in the target stack's commit history (plausible for forks, vendored/shared code, or monorepo mirrors). No access to the victim's GitHub org, Shipit session, or API token is needed — only a correctly HMAC-signed POST to `/webhooks` using the attacker's own webhook secret.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to the repository indicated by the authenticated organization, mirroring the pattern used by `Handler#stacks`/`repository_name` (i.e., join through `stacks: :repository` and filter by `Repository.from_github_repo_name(repository_name)`) instead of a bare `Commit.where(sha: ...)`. More generally, `WebhooksController#verify_signature` should ensure the organization used to select the webhook secret matches the organization embedded in `repository.full_name`, and every handler that mutates records keyed by attacker-suppliable fields (`sha`, `full_name`, etc.) should re-derive and check the owning repository/organization rather than trusting an unscoped field.

### Proof of Concept
1. Shipit is configured with (at least) two GitHub orgs/Apps: `attacker-org` (attacker-controlled, webhook secret known to attacker) and `victim-org` (hosts a Stack with `ci.require` configured, tracking commit `abc123...`).
2. Attacker crafts a `status` webhook payload:
   ```json
   {
     "sha": "abc123...",
     "state": "success",
     "context": "required-ci-check",
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" }
   }
   ```
3. Attacker signs the payload with `attacker-org`'s known `webhook_secret` and sends it to `/webhooks` with `X-Github-Event: status`.
4. `verify_signature` resolves `repository_owner` = `attacker-org`, fetches `attacker-org`'s webhook secret, and the signature verifies successfully [1](#0-0) .
5. `StatusHandler#process` runs `Commit.where(sha: "abc123...")`, finds the commit belonging to `victim-org`'s stack, and calls `create_status_from_github!`, recording a forged "success" status for `required-ci-check` on a commit the attacker never had access to [2](#0-1) .
6. If this was the last missing required status, `victim-org`'s stack may now be eligible for continuous/automatic deploy despite the attacker having no access to `victim-org`.
