### Title
Webhook Signature Is Verified Against An Organization Chosen From Unauthenticated Payload Fields, While Handlers Act On Unrelated Payload Fields - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification based on values read directly out of the *unauthenticated* JSON body (`repository.owner.login` or `organization.login`), before the signature has been checked. The event handlers then act on other, independent fields of that same unauthenticated body (e.g. `sha`, `repository.full_name`) to decide what to write. Nothing binds "the organization whose secret validated the signature" to "the data the handler consumes," so a payload can pick a low/no-security organization for the signature check while asserting facts about a completely different, sensitive repository/commit.

### Finding Description
`verify_signature` computes the organization used for verification purely from attacker-controlled JSON, before trust has been established: [1](#0-0) [2](#0-1) 

The resolved `github_app` for that organization is used to verify the HMAC: [3](#0-2) 

Critically, `verify_webhook_signature` returns `true` **unconditionally when no `webhook_secret` is configured** for that organization (`return true unless webhook_secret`), and `webhook_secret` is documented as *optional* per organization: [4](#0-3) [5](#0-4) 

Once the `Repository owner`/`organization` field is used only to pick which secret gates the request, the actual handlers ignore that same binding and act on independent fields of the identical, forgeable JSON body:

- `StatusHandler` looks up commits **globally by `sha`, with no scoping to the organization/repository that authenticated the request**: [6](#0-5) 

- `PushHandler`/base `Handler` resolve the target repository from `repository.full_name`, a field distinct from `repository.owner.login` used for signature selection: [7](#0-6) [8](#0-7) 

This is the same trust-binding break as the reported bug class: the field the app uses to select/authenticate ("taker"/organization secret) is never checked against the field the app actually acts on ("order execution"/commit or repository). Concretely: `organization_that_authenticated == repository_owner_field` (attacker-chosen, and possibly unsecured), while `repository_actually_written == full_name / sha field` (also attacker-chosen), and the two are never asserted equal to a *verified* identity. Any organization configured on the Shipit instance without a `webhook_secret` (an explicitly supported, documented configuration) can be used as a "free pass" identity to forge webhook events whose payload content targets commits/stacks belonging to a totally different, secured organization/repository tracked by the same Shipit instance.

### Impact Explanation
Using an unsecured (no-`webhook_secret`) organization as the "authenticating" identity, an attacker can send a forged `status` event whose `sha` matches a commit belonging to an unrelated, security-conscious organization's stack, injecting a fabricated `success` `CommitStatus` via `Commit#create_status_from_github!`. Since deploy gating (`ci.require`) relies on `CommitStatus` records associated by `sha` without re-validating org/repo provenance at write time, this can satisfy CI requirements and enable an **unauthorized deploy** on a stack the attacker has no legitimate access to — meeting the "unauthorized deploy" impact bar defined in scope.

### Likelihood Explanation
Requires: (1) at least one GitHub organization configured on the Shipit instance without a `webhook_secret` (a documented, optional, and thus realistic configuration — Shipit ships example configs with `webhook_secret: # nil`), and (2) knowledge of another organization's/repo's commit `sha` (routinely public via GitHub, PRs, CI logs). No authentication, API token, or GitHub write access is required — only the ability to POST to the public `/webhooks` endpoint, which by design accepts unauthenticated GitHub-originated traffic.

### Recommendation
Do not let the organization used to select/verify the webhook secret be derived independently from the field(s) the handler subsequently trusts. Concretely:
- Reject webhooks for organizations with no `webhook_secret` configured (fail closed instead of `return true unless webhook_secret`), or require an explicit secret for every configured organization at boot.
- After signature verification, re-derive and enforce that the `repository`/`organization` identity used for verification is the *same* identity referenced by the data the handler consumes (e.g., `StatusHandler` should scope `Commit` lookups to stacks belonging to the verified repository, not search all commits globally by `sha`).

### Proof of Concept
1. Operator configures Shipit with two orgs: `secured-org` (has a `webhook_secret`) and `open-org` (leaves `webhook_secret` blank, per documented optional setting).
2. Attacker finds a commit `sha` belonging to a `secured-org` repository's Shipit stack (public commit history/PR).
3. Attacker POSTs to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "open-org" }, "full_name": "open-org/whatever" },
  "sha": "<secured-org commit sha>",
  "state": "success",
  "context": "ci/required-check"
}
```
4. `WebhooksController#repository_owner` resolves to `open-org`; `Shipit.github(organization: 'open-org').verify_webhook_signature` returns `true` because no secret is configured (`lib/shipit/github_app.rb` line 77), regardless of the `X-Hub-Signature` header.
5. `StatusHandler#process` executes `Commit.where(sha: params.sha)` — matching the `secured-org` commit — and calls `create_status_from_github!`, injecting a forged `success` status that can satisfy `ci.require` gating for a deploy on `secured-org`'s stack.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
