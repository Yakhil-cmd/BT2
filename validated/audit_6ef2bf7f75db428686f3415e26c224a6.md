Based on my investigation, I found a genuine analog in `pallet-assets` ERC20 precompile within `pallet-revive`, but I cannot fully confirm exploitability within this ask-only session, since I lack the ability to run a reproduction. Here's what I found and its limits.

### Title
Potential loss of native value (msg.value analog) sent alongside `pallet-assets` ERC20 precompile `transfer`/`transferFrom`/`approve` calls - (File: substrate/frame/assets/precompiles/src/lib.rs)

### Summary
The `ERC20` precompile in `substrate/frame/assets/precompiles/src/lib.rs` implements Solidity `IERC20::transfer`, `transferFrom`, and `approve`. None of these handler functions inspect or reject a non-zero native `value` (the EVM/PVM analog of `msg.value`) attached to the call. In genuine Solidity ERC-20 tokens these functions are `non-payable`; sending value alongside such a call reverts at the EVM/language level. In `pallet-revive`, a `CALL` opcode/host-call to any address (including a precompile) with `value > 0` unconditionally triggers a currency transfer of that value to the destination account before the precompile body runs (`transfer_from_origin` invoked in `substrate/frame/revive/src/exec.rs`, around lines 1451-1463), regardless of whether the callee is "payable".

### Finding Description
`Precompile::call()` implementations for `ERC20` (`substrate/frame/assets/precompiles/src/lib.rs:163-207`) dispatch to `Self::transfer`, `Self::approve`, `Self::transfer_from`, none of which read `env.value_transferred()`. Meanwhile the calling convention in `substrate/frame/revive/src/exec.rs` (`fn run`, and the surrounding `if frame.delegate.is_none() { Self::transfer_from_origin(...) }` block around lines 1451-1463) transfers `frame.value_transferred` unconditionally for every non-delegate call/frame, including precompile frames. This is the same root cause pattern as the reported Solidity bug: a private/internal helper (`_transferAmount`) or dispatcher does not `require(msg.value == 0)` before executing a token-only transfer path, so any native currency sent along with the call is not returned to the caller and is not incorporated into the intended (asset) transfer amount.

Key uncertainty: `ERC20` precompiles set `const HAS_CONTRACT_INFO: bool = false;` [1](#0-0) , which per its own documentation means "No account or any other state will be created for the address." I could not fully trace whether `transfer_from_origin`/the balance-transfer path for precompiles without contract info actually succeeds in moving funds to (and stranding them at) that address, gracefully fails (e.g., dust/ED issues since no account exists), or is bypassed altogether for `HAS_CONTRACT_INFO = false` precompiles. This determines whether the value is genuinely lost/stranded (High confidence bug) or the transaction simply reverts (no loss, safe by construction). [2](#0-1) [3](#0-2) [4](#0-3) 

### Impact Explanation
If native value sent to the ERC20 precompile address during a `transfer`/`transferFrom`/`approve` call is not refunded and not incorporated into any accounting, a caller invoking the precompile with non-zero `value` (e.g., by mistake, or via a wallet/contract that always attaches value) would have that value permanently stuck at an address that (per `HAS_CONTRACT_INFO = false`) is documented to hold no state and have no owner able to withdraw it. This would constitute a loss-of-funds bug matching the Medium severity of the referenced report. However, without confirming the actual balance-transfer mechanics for `HAS_CONTRACT_INFO = false` precompiles, I cannot assert the funds are irrecoverably stuck versus the call reverting/failing safely.

### Likelihood Explanation
Likelihood requires only a normal, unprivileged EOA or contract caller issuing an EVM/PVM `CALL` with non-zero `value` to the well-known ERC20 precompile address — no privileged role, governance, or malicious peer is needed. This matches the "real user entry point" requirement (arbitrary user-initiated contract call). The likelihood of triggering is plausibly non-trivial (front-ends/wallets sometimes attach value unconditionally, or a composing contract might forward `msg.value`), but is a user-side mistake, similar to the original report.

### Recommendation
If the transfer-of-native-value-to-address-without-contract-info path can succeed and result in stranded funds, add an explicit check in `ERC20::transfer`, `transfer_from`, and `approve` in `substrate/frame/assets/precompiles/src/lib.rs` that rejects execution when `env.value_transferred()` (or the equivalent accessor) is non-zero, mirroring the state-mutability enforcement already noted in `prdoc/stable2512/pr_10080.prdoc` ("precompiles: Enforce state mutability") for read-only vs. mutating calls — but for payability. Alternatively, ensure the native currency transfer step in `substrate/frame/revive/src/exec.rs` refunds/rejects non-zero value for calls into precompiles with `HAS_CONTRACT_INFO = false` when the target precompile does not implement a payable interface.

### Proof of Concept
I was not able to execute a concrete reproduction in this session (no filesystem/terminal access, ask-only mode, and no more tool budget to trace the exact `transfer_from_origin`/dust-handling behavior for accountless precompiles). This report should be treated as a plausible analog requiring verification, not a confirmed, reproduced vulnerability. A background engineering session with repo access would need to:
1. Write a `pallet-revive` integration test invoking `bare_call` with a non-zero `value` and `IERC20::transferCall` payload to an ERC20 precompile address with `HAS_CONTRACT_INFO = false`.
2. Assert whether the call succeeds, whether native balance moves, and whether it is subsequently recoverable by any account.
3. If funds are shown to be stranded, this confirms the Medium-severity analog; if the call reverts or the value is refunded, the finding is not exploitable and this report should be discarded.
