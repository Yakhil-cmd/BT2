### Title
Webhook signature is verified against the organization named in the payload while the target repository is taken from a different payload field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization config (and therefore which `webhook_secret`) to validate a webhook against using `repository_owner`, which is read straight out of the attacker-supplied JSON body (`repository.owner.login` or `organization.login`). The event handlers that actually mutate state (enqueue sync jobs, write commit statuses, refresh check runs, create/delete team memberships, etc.) instead resolve the target `Repository`/`Stack` from a *different* payload field, `repository.full_name`. Because these two fields are never checked against each other, and because `webhook_secret` is an optional per-organization setting, a payload can claim to be "from" an organization that has no `webhook_secret` configured (so signature verification is skipped) while pointing its `repository.full_name` at a repository belonging to a completely different, secured organization.

### Finding Description
- `verify_signature` picks the app/config to verify against using data taken from the unauthenticated request body: [1](#0-0) [2](#0-1) 

- `GitHubApp#verify_webhook_signature` unconditionally returns `true` when the resolved organization has no `webhook_secret` configured — a state explicitly documented as optional/omittable: [3](#0-2) [4](#0-3) 

- Once the request passes `verify_signature`, `create` dispatches the *entire, still attacker-controlled* payload to every registered handler for the event, without re-validating any relationship between the org used to authenticate and the repository the handler will act on: [5](#0-4) 

- Every handler resolves the repository/stack to act on using a separate field, `repository.full_name`, taken from the same untrusted payload: [6](#0-5) [7](#0-6) 

- `PushHandler`, for example, will locate stacks for whatever `repository.full_name` says and immediately trigger a GitHub sync (which updates the stack's known commits/branch state) for the SHA supplied in the same forged payload: [8](#0-7) 

The equality the code is supposed to enforce is: `organization authenticated by verify_signature == owner(repository acted on by the handler)`. Nothing in the controller or in `Handler#repository_name` enforces `payload['repository']['owner']['login'] == payload['repository']['full_name'].split('/').first`, so the two can be made to diverge.

### Impact Explanation
If any organization configured in this Shipit deployment omits `webhook_secret` (a supported, documented configuration), an unauthenticated attacker can submit a webhook claiming `organization`/`repository.owner.login` equal to that secret-less org (verification short-circuits to `true`) while setting `repository.full_name` to any other, secured repository tracked by the instance. This lets the attacker forge `push` events to force `GithubSyncJob`/`sync_github` on arbitrary stacks, forge `status`/`check_suite` events to fabricate CI state that gates deploys, and forge `membership` events to add/remove arbitrary `Team`/`Membership` records for other organizations — all without ever holding a valid signature for the targeted organization. Depending on which handlers are installed, this can influence deployability checks and team membership, i.e., escalate into `Shipit.github_teams` authorization and unauthorized state changes on stacks the attacker does not control.

### Likelihood Explanation
Requires only that the Shipit operator has configured at least one GitHub organization without a `webhook_secret` (explicitly presented as optional in `docs/setup.md`) alongside at least one other organization/repository that is meant to be protected. No repository write access, session, or API token is required — only network access to `POST /webhooks` (or wherever `WebhooksController` is mounted) and knowledge of a tracked repository's `owner/name`.

### Recommendation
Bind the two payload-derived identities together before dispatching: require that the organization/owner used to select and verify the webhook secret in `verify_signature` matches the owner encoded in `repository.full_name` (or, better, resolve the target `Repository` first and always verify against that repository's own organization secret, never a value chosen solely by the unverified payload). Additionally, consider requiring `webhook_secret` to be present for every configured organization rather than allowing verification to be silently skipped.

### Proof of Concept
1. Configure two organizations in Shipit: `open-org` (no `webhook_secret` set) and `secure-org` (with `webhook_secret` set, owning a tracked repository `secure-org/prod-app`).
2. As an unauthenticated attacker, `POST` to the webhooks endpoint with header `X-Github-Event: push` and a JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "open-org" },
    "full_name": "secure-org/prod-app"
  }
}
```
3. `verify_signature` computes `repository_owner = "open-org"`, looks up `Shipit.github(organization: "open-org")`, finds no `webhook_secret`, and `verify_webhook_signature` returns `true` regardless of the (even absent) `X-Hub-Signature` header.
4. `Shipit::Webhooks.for_event('push')` runs `PushHandler` on the payload, which resolves `Repository.from_github_repo_name("secure-org/prod-app")` and calls `sync_github(expected_head_sha: ...)` on its stacks — a write against `secure-org`'s stack achieved without ever satisfying `secure-org`'s webhook secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
