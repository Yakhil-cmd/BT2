### Title
Webhook signature validated against secret keyed by `repository.owner.login`, but the acted-upon stack is looked up by the unrelated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to use for HMAC verification based on `repository.owner.login` (or `organization.login`) parsed from the untrusted request body, while the downstream event handlers (e.g. `PushHandler`) resolve the target `Stack`/`Repository` using the independent `repository.full_name` field from the same payload. Nothing binds these two fields together, so the "organization that authenticated" the request is not guaranteed to equal the "repository that is written."

### Finding Description
`verify_signature` computes:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [1](#0-0) 
where
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

`GithubApp#verify_webhook_signature` checks the HMAC using the secret configured for that specific organization, and critically:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [3](#0-2) 
Since a webhook secret is documented as **optional** per-organization (`docs/setup.md` explicitly calls it "optional"), any organization configured without a `webhook_secret` causes verification to be skipped entirely (`return true unless webhook_secret`) for any payload that names that organization in `repository.owner.login`.

Once "verified" (or trivially bypassed because that org has no secret), `create` re-parses the same raw body and dispatches to handlers:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [4](#0-3) 

The handlers, however, do not use `repository.owner.login` to find the target stack. `PushHandler` (and the base `Handler` class) look up the affected `Repository`/`Stack` using a completely different payload field, `repository.full_name`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [5](#0-4) 
```ruby
def process
  stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [6](#0-5) 

`Repository.from_github_repo_name` splits `owner/name` straight out of `full_name`, independent of `repository.owner.login`:
```ruby
def self.from_github_repo_name(github_repo_name)
  repo_owner, repo_name = github_repo_name.downcase.split('/')
  find_by(owner: repo_owner, name: repo_name)
end
``` [7](#0-6) 

The equality that should be enforced is: `organization used to select the verification secret` == `organization that owns the repository being acted on`. In this instance-mounting mode (documented "Multiple Github Applications" setup, `docs/setup.md:182-209`), where different organizations can have different (or no) webhook secrets, that equality is never checked. An attacker can craft a webhook body where `repository.owner.login` names an organization configured with no `webhook_secret` (or a leaked/weak one), while `repository.full_name` names a stack that belongs to an entirely different, security-sensitive organization. `verify_signature` passes (trivially, since the named org has no secret), and `PushHandler` then triggers `stack.sync_github` for the *other* organization's stack based on attacker-controlled `after` (head SHA) and `ref`, driving unauthorized deploy/sync activity for a repository the attacker's chosen "authenticating organization" never owned.

### Impact Explanation
This breaks the deployment-trust binding between "the GitHub organization that authenticated the webhook" and "the repository being written to/synced," which the task rubric flags explicitly as an analog category. Forged push events can trigger `GithubSyncJob`/`stack.sync_github` for stacks belonging to organizations other than the one whose (weak/absent) secret was used to pass verification, which is a form of unauthorized deploy-pipeline trigger crossing organizational boundaries — this maps to the "unauthorized deploy" High/Critical impact bucket, since it lets an attacker who only controls one poorly-configured organization's webhook influence sync/deploy state of stacks under a different, unrelated organization.

### Likelihood Explanation
Requires only that the instance operator has configured multiple GitHub organizations under `config/secrets.yml`'s multi-org `github:` block (an explicitly documented, supported configuration, `docs/setup.md:182-209`) where at least one organization omits the (optional) `webhook_secret`. No repository write access, `ApiClient` token, or privileged account is needed — it's a plain unauthenticated HTTP POST to `/webhooks`. Given the setup guide explicitly marks the webhook secret as "optional," this is a realistic misconfiguration rather than a purely theoretical one.

### Recommendation
Bind the field used to select the verification secret to the field used to resolve the target stack: after signature verification, re-derive the organization from `repository.full_name`'s owner segment (or from the resolved `Repository`/`Stack`'s actual organization) and reject the request if it doesn't match the organization whose secret was used (`repository_owner`). Alternatively, require `webhook_secret` to be present for every configured organization (fail closed instead of `return true unless webhook_secret`), and validate that `repository.owner.login`/`organization.login` equals the owner segment of `repository.full_name` before dispatching to handlers.

### Proof of Concept
1. Instance is configured with two organizations in `config/secrets.yml`: `trusted-org` (has a real, security-sensitive stack, secret configured) and `open-org` (configured with app credentials but no `webhook_secret`, per the documented "optional" setting).
2. Attacker sends `POST /webhooks` with header `X-Github-Event: push` and no valid `X-Hub-Signature` (or an arbitrary one), and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "open-org" }, "full_name": "trusted-org/sensitive-repo" }
}
```
3. `verify_signature` calls `Shipit.github(organization: "open-org")`; since `open-org` has no `webhook_secret`, `verify_webhook_signature` returns `true` unconditionally, so the request passes verification. [8](#0-7) 
4. `create` dispatches to `PushHandler`, which resolves the stack via `repository.full_name` = `"trusted-org/sensitive-repo"`, entirely ignoring `open-org`, and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` for the trusted-org stack. [6](#0-5) [5](#0-4)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
