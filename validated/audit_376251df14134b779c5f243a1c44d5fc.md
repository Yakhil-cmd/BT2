## Title
Cross-Organization / Cross-Repository Webhook Confusion — Signature Verified Against `repository.owner.login`, Data Acted On From `repository.full_name`/Global `sha` Lookup — ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate a webhook against using `repository.owner.login` (or `organization.login`) from the *attacker-controlled JSON body itself*, while the actual write path — `Shipit::Webhooks::Handlers::Handler#repository_name` and, more critically, `StatusHandler#process` — trusts other independent fields of that same body (`repository.full_name`, or nothing at all for status) to decide which `Stack`/`Commit` records to mutate. The field that is authenticated (which org's secret validated the signature) and the field that is acted upon (which repository/commit gets written) are never checked for equality. This is the same "hub" bug class as the ITS `TokenBalance`/`TokenManager` report: authentication is scoped to one identity, but the write path is scoped to a different, unverified identity carried in the same payload.

### Finding Description
`WebhooksController#verify_signature` picks the `GithubApp` (and thus the webhook secret) to verify against like this: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight out of the untrusted JSON body (`params.dig('repository','owner','login')`). Shipit explicitly supports configuring **multiple GitHub Apps for multiple organizations**, each with its own `webhook_secret`, as documented: [3](#0-2) 

Once the signature is accepted, every registered handler is invoked with the raw JSON `params`: [4](#0-3) 

The base `Handler` class resolves the target repository/stacks for a webhook using a *different* field of the same body: [5](#0-4) 

Nothing anywhere ties `repository.full_name` back to the `repository.owner.login`/`organization.login` value that was used to select the verifying secret. An operator of Organization A (who legitimately knows Organization A's `webhook_secret` because they installed/administer the GitHub App for their own org) can therefore sign an arbitrary JSON body with their own secret while setting `repository.full_name` to `"OrgB/victim-repo"` — a completely different, unrelated tenant repository tracked by the same Shipit instance. `verify_signature` succeeds (Org A's secret matches Org A's `repository.owner.login`), and `PushHandler`/`PullRequest` handlers then act on `OrgB/victim-repo`'s stacks via `Handler#stacks`/`Repository.from_github_repo_name`.

Even worse, `StatusHandler` doesn't consult the repository field at all: [6](#0-5) 

It looks up `Commit.where(sha: params.sha)` **globally across every repository tracked by the Shipit instance** and writes a forged commit status (`state`, `context`, `target_url`, `description`) via `commit.create_status_from_github!`. Any org whose webhook secret is configured in Shipit — however untrusted — can forge a valid signature and inject an arbitrary CI status (e.g. `state: "success"`, `context: "ci/required"`) onto any commit SHA in any other tenant's repository, as long as they can guess/know that SHA (trivial for public repositories, or for SHAs visible via Shipit's own public timeline/API).

This exactly mirrors the reported bug class: the binding that should hold — `organization authenticated == organization/repository written` — is broken because one JSON field is covered by the HMAC check while a sibling field drives the write.

### Impact Explanation
Commit statuses gate Shipit's merge-queue and deploy eligibility logic (`Commit`/`Status::Group`/`MergeRequest` consult commit statuses to decide mergeability and deployability). A tenant organization with only their own valid webhook secret can forge a `success` status on a victim organization's commit, subverting the required-status checks that are supposed to gate `merge`/`deploy` for that other tenant's stack — this reaches the "unauthorized merge/deploy" impact bar via a credential (webhook signature) that authenticates one identity being reused to write another identity's protected state. Because the escalation crosses the multi-tenant organization boundary that Shipit is explicitly documented and designed to support, this is a genuine authentication/authorization-binding break, not merely a same-org data-integrity nuance.

### Likelihood Explanation
Requires Shipit to be configured with more than one GitHub organization (a documented, supported configuration), and requires the attacker to control (or have legitimately been granted) the webhook secret for at least one of those organizations — which is inherent to being a tenant in that setup, not requiring compromise of Shipit itself, a Shipit session, or an `ApiClient` token. The attacker only needs to know a target commit SHA (trivially available for public repositories, or observable through Shipit's own UI/webhooks for private ones they don't own but that share the instance). This is analogous to the report's "compromised chain" scenario — a lower-trust participant abusing a boundary that's supposed to isolate tenants.

### Recommendation
In `WebhooksController#verify_signature`, after verifying the signature, additionally verify that `repository.owner.login`/`organization.login` used for secret selection matches the owner encoded in `repository.full_name` (and reject if not). In `Handler#stacks`/`repository_name`, use the already-authenticated organization instead of blindly trusting `repository.full_name`. In `StatusHandler#process`, scope the `Commit` lookup to commits belonging to stacks/repositories under the authenticated organization instead of a global `Commit.where(sha:)` lookup across all tenants.

### Proof of Concept
1. Configure Shipit with two GitHub orgs per `docs/setup.md`'s multi-app format: `OrgA` (attacker-controlled, webhook secret known to attacker) and `OrgB` (victim, tracked stack `orgb/victim-repo`, has a public commit with SHA `deadbeef...`).
2. Attacker crafts a `status` webhook JSON body:
   ```json
   { "repository": {"owner": {"login": "orga"}, "full_name": "orga/attacker-repo"},
     "sha": "deadbeef...", "state": "success", "context": "ci/required" }
   ```
3. Attacker signs the raw body with `OrgA`'s known `webhook_secret` and sets `X-Hub-Signature`, `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"orga"`, fetches `Shipit.github(organization: 'orga')`, and successfully verifies the signature — the request is accepted (`app/controllers/shipit/webhooks_controller.rb:24-30`).
5. `StatusHandler#process` runs `Commit.where(sha: 'deadbeef...')` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`), matches `OrgB`'s commit, and calls `create_status_from_github!`, forging a `success` status on a commit the attacker does not own — without ever needing `OrgB`'s webhook secret.

If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently.
