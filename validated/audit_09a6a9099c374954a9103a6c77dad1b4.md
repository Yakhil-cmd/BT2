### Title
Unbounded RAY debt valuation permanently freezes an oversized market - ([File: common/src/rates/index.rs](common/src/rates/index.rs))

### Summary

A sufficiently large borrowed position can make `borrowed * borrow_index` overflow `i128` before `borrow_index` reaches `MAX_BORROW_INDEX_RAY`. Because every market operation synchronizes interest before executing, the first overflow permanently blocks `update_indexes`, `withdraw`, `repay`, `borrow`, `liquidate`, and `clean_bad_debt` for that market.

### Finding Description

`Controller::supply`, `borrow`, `withdraw`, `repay`, `liquidate`, and `clean_bad_debt` are reachable without privileged roles, subject to account authorization and token funding. Pool mutations load the market and call `interest::global_sync`, which invokes `accrue_step` and eventually `calculate_supplier_rewards`.

In `common/src/rates/index.rs`, `calculate_supplier_rewards` computes:

```rust
let old_total_debt = borrowed.mul(env, old_borrow_index);
let new_total_debt = borrowed.mul(env, new_borrow_index);
```

Both products use checked RAY arithmetic and panic on overflow. `update_borrow_index` caps the index at `MAX_BORROW_INDEX_RAY`, but there is no equivalent cap on `borrowed * borrow_index`. Therefore a market can cross the finite RAY-value ceiling before the index cap is reached.

The repository's own regression test demonstrates this condition: a `1e18`-decimal market with one billion whole tokens at 98% utilization eventually causes `update_indexes` to fail with `MathOverflow`; subsequent one-unit `withdraw` and `repay` calls fail identically because both accrue first.

### Impact Explanation

Permanent freezing of user funds and protocol insolvency risk. Once the overflow boundary is crossed:

- suppliers cannot withdraw the affected asset;
- borrowers cannot repay the affected debt;
- liquidators cannot liquidate positions through the frozen market;
- permissionless bad-debt cleanup cannot progress;
- `update_indexes` can never commit a later timestamp, so subsequent calls repeat the same failing calculation;
- `update_params` also accrues first, preventing a rate-model change from repairing the market.

This is not merely a caller-supplied transaction exceeding the Soroban resource budget: the deterministic checked multiplication exceeds the `i128` domain and reverts on every future attempt.

### Likelihood Explanation

Exploitation requires a very large market and sustained borrowing so the borrow index grows enough for the scaled debt product to overflow. A single unprivileged whale can supply the liquidity and borrow it against its own collateral using `Controller::supply` and `Controller::borrow`, then let time pass and trigger or encounter the failure through `update_indexes` or any market operation.

Likelihood depends on deployed decimals, caps, collateral prices, utilization limits, and interest-rate parameters. Those limits do not intrinsically prevent the bug: the code permits values up to the asset-domain cap, while the later value multiplication can still exceed `i128`. The checked-in test constructs such a market with lifted caps and demonstrates the reachable permanent-freeze state.

### Recommendation

Bound debt valuation before multiplying scaled debt by the index. In particular:

1. In `calculate_supplier_rewards`, compute accrued interest in a way that cannot require materializing `borrowed * index` as a single `i128`, or explicitly clamp/check the product before accrual.
2. Enforce a market-level scaled-debt cap such that `borrowed * MAX_BORROW_INDEX_RAY <= i128::MAX` for every listed decimal configuration.
3. Recompute caps after every borrow-index update and reject new exposure before the market approaches the valuation ceiling.
4. Add a recovery path that can mark the market accrued or disable further interest without performing the overflowing multiplication, allowing repayment, withdrawal, liquidation, and cleanup to continue.

### Proof of Concept

Conceptual transaction sequence against an admitted high-decimal market `debt_key` and collateral market `collateral_key`:

```rust
// Attacker controls all addresses/accounts and supplies all required tokens.

let debt_account = controller.supply(
    attacker,
    0,
    spoke_id,
    vec![(debt_key, huge_liquidity_amount)],
);

let collateral_account = controller.supply(
    attacker,
    0,
    spoke_id,
    vec![(collateral_key, huge_collateral_amount)],
);

controller.borrow(
    attacker,
    collateral_account,
    vec![(debt_key, high_utilization_borrow_amount)],
    Some(attacker),
);

// Advance ledger time until debt-key RAY value approaches i128::MAX.
controller.update_indexes(attacker, vec![debt_key]);
// Panics with GenericError::MathOverflow inside calculate_supplier_rewards.

// Permanent afterward:
controller.update_indexes(attacker, vec![debt_key]); // same panic
controller.repay(attacker, collateral_account, vec![(debt_key, 1)]); // accrues first, same panic
controller.withdraw(attacker, debt_account, vec![(debt_key, 1)], None); // same panic
controller.liquidate(attacker, victim_or_self, debt_payments, seize_mode); // same panic
controller.clean_bad_debt(attacker, collateral_account); // same market sync, same panic
```

The repository test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` demonstrates this sequence and asserts `MathOverflow` for `update_indexes`, `withdraw`, and `repay` after the overflow boundary is reached.
