### Title
Webhook signature is verified against `repository.owner.login`, but handlers act on the unrelated `repository.full_name` field, allowing cross-organization event forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and thus which `webhook_secret`) to validate the HMAC signature with, using only `repository_owner`, extracted from `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`). Once the signature check passes, the entire raw JSON payload is handed unmodified to the event handlers via `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. Those handlers independently re-read the repository to operate on from `payload.dig('repository', 'full_name')` in `Handlers::Handler#repository_name`. Nothing ties the field used to select the verifying secret to the field used to select the repository/stack that is mutated. In a multi-organization Shipit deployment (`config/secrets.yml` supports a per-organization `github:` hash, each with its own `webhook_secret`), an attacker who legitimately controls one configured organization/app (and therefore knows that organization's `webhook_secret`) can craft a payload whose `repository.owner.login`/`organization.login` names their own org (so the HMAC check succeeds) while `repository.full_name` names a stack that belongs to a completely different, victim organization.

### Finding Description
The equality that should hold, but doesn't, is:
`organization used to verify the signature (repository.owner.login / organization.login)` == `repository whose stacks are mutated (repository.full_name)`.

- `verify_signature` in `app/controllers/shipit/webhooks_controller.rb` picks the GitHub App/secret with `Shipit.github(organization: repository_owner)` and validates via `github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)`. [1](#0-0) 
- `repository_owner` is read from the same untrusted JSON body being signed, specifically `repository.owner.login` (or `organization.login`). [2](#0-1) 
- After the signature passes, `create` dispatches the full parsed body to handlers: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. [3](#0-2) 
- The base `Handler` resolves the target stacks purely from `payload.dig('repository', 'full_name')` via `Repository.from_github_repo_name(repository_name)`, a field that is never cross-checked against `repository_owner`. [4](#0-3) 
- Concrete handlers such as `PushHandler` then trigger `stack.sync_github(expected_head_sha: params.after)` for every non-archived stack on that (attacker-chosen) repository/branch, and `StatusHandler` creates a commit status from attacker-supplied `state`/`target_url` for any commit matching `sha`. [5](#0-4) [6](#0-5) 

Because HMAC signing covers the raw request body as a whole (correctly, per `verify_webhook_signature` in `lib/shipit/github_app.rb`), the signature itself cannot be forged without the correct secret. [7](#0-6)  But the vulnerability is not in the crypto — it's that the *identity used to select which secret is correct* (`repository_owner`) is decoupled from the *identity used to decide what gets acted on* (`repository.full_name`). An operator of a legitimately configured but low-privileged organization (owner of a real, registered GitHub App/organization in `Shipit.github`) can send a webhook whose `repository.owner.login` matches their own org while `repository.full_name` names a stack belonging to an unrelated organization also hosted on the same Shipit instance. The signature check passes because it's validated against the attacker's own known secret, yet the handler acts on the victim organization's repository.

### Impact Explanation
This crosses the "an organization that authenticated versus the repository that is written" boundary explicitly called out in scope. Concretely:
- `push` events let the attacker trigger `stack.sync_github` (kicking off `GithubSyncJob`) against any stack in the victim's repository/branch, which can affect deploy state tracking for a repo the attacker does not own.
- `status` events let the attacker inject arbitrary commit statuses (`state`, `target_url`, `description`, `context`) for any commit SHA in the victim's stacks via `commit.create_status_from_github!`, without owning that repository.
- `check_suite` and `membership` handlers are reachable the same way, since none of them re-validate `repository_owner` against `repository.full_name`.

This is a cross-repository/cross-organization write performed with an unauthorized organizational identity, matching the "cross-repository writes" / "unauthorized deploy" impact categories, since forged commit statuses and sync triggers directly influence deployability and Shipit's decision-making for a repository the attacker does not control.

### Likelihood Explanation
Exploitability requires only that the Shipit instance is configured for multiple GitHub organizations (documented, supported configuration per `config/secrets.development.example.yml`), and that the attacker legitimately controls one of those configured, lower-trust organizations (i.e., knows its `webhook_secret`, which by design they are entitled to as that org's App owner). No access to the victim org, no GitHub App private key, and no Shipit session/API token is needed — only the ability to send a crafted webhook to the shared `/webhooks` endpoint. This is a realistic misconfiguration-independent scenario for any Shipit install serving more than one GitHub organization.

### Recommendation
After signature verification, re-derive `repository_owner` from `repository.full_name` (or otherwise cross-check that `repository.owner.login`/`organization.login` matches the owner segment of `repository.full_name`) and reject the webhook if they diverge. Alternatively, pass the verified `repository_owner` into the handler context and have `Handlers::Handler#repository_name`/`stacks` scope lookups to repositories owned by that verified organization only, rather than trusting the unererified `full_name` field independently.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` and `victim-org`, each with distinct `webhook_secret`s (supported multi-org config shown in `config/secrets.development.example.yml`).
2. As the owner of `attacker-org`'s GitHub App, compute a valid HMAC-SHA1 signature over a JSON body using `attacker-org`'s known `webhook_secret`:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org" }
  }
}
```
3. POST this body to `/webhooks` with header `X-Github-Event: push` and `X-Hub-Signature: sha1=<computed>`.
4. `verify_signature` calls `Shipit.github(organization: 'attacker-org')` (from `repository.owner.login`) and validates successfully because the signature was computed with `attacker-org`'s real secret. [1](#0-0) 
5. `PushHandler#stacks` resolves `Repository.from_github_repo_name('victim-org/victim-repo')` from `repository.full_name` and calls `stack.sync_github(expected_head_sha: 'deadbeef')` on victim-org's stacks — despite the request never being signed by `victim-org`'s secret. [4](#0-3) [5](#0-4)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
