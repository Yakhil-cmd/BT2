## Analysis

CVE-2017-10984 is a length-validation bug in FreeRADIUS's WiMAX attribute parser (`data2vp_wimax()`): a variable-length field is copied without checking that the declared/derived length matches an expected fixed size, causing a buffer write past the allocated region and a daemon crash.

The closest reachable analog in `ocore--004` is in the c-hash (chash) decoding/verification pipeline in `chash.js`, which is invoked whenever address chashes are verified — including from unit/AA-reachable code paths such as address definition validation.

### Root cause

`chash.js` `isChashValid()` decodes an attacker-supplied encoded string and then feeds the *decoded byte length* into helpers that assume the length is **exactly** 160 or 288 bits: [1](#0-0) 

- Only the `base32.decode` / `Buffer.from(encoded, 'base64')` call is wrapped in `try/catch` [2](#0-1) .
- The very next call, `buffer2bin(chash)` followed by `separateIntoCleanDataAndChecksum(binChash)`, is **not** protected: [3](#0-2) .
- `separateIntoCleanDataAndChecksum()` explicitly `throw`s an uncaught `Error` if the bit length is not exactly 160 or 288: [4](#0-3) .

For the 32-character (base32/160-bit) path used by `isValidAddress()`, the `thirty-two` decoder always yields a fixed 20-byte (160-bit) buffer for a 32-character alphabet-conformant string, so the length invariant holds and no crash occurs: [5](#0-4) .

However, `isChashValid()` is also reachable with `len=48` (base64/288-bit chash, used e.g. for "definition template" hash matching in `definition.js`). `Buffer.from(str, 'base64')` in Node.js is lenient: malformed/truncated base64 input silently decodes to a buffer whose length can differ from the expected 36 bytes (288 bits) without throwing. That mismatched length then reaches the un-guarded `separateIntoCleanDataAndChecksum()` call and throws synchronously — crashing whatever process is validating the unit, since this call sits deep inside the synchronous portion of unit/definition validation, not inside any surrounding `try/catch` at the call sites in `validation_utils.js`/`definition.js`.

This mirrors the FreeRADIUS bug class: an attacker supplies a variable-length blob, downstream code assumes it always matches one of a fixed set of expected sizes, and no bounds/length check is enforced before the fixed-size logic runs, leading to a crash from untrusted, unprivileged input (any unit author can construct an address definition or definition-template reference containing an arbitrary base64 chash string).

### Assessment

- Reachable by: any unprivileged unit poster who includes an address definition (or "definition template" reference using the 288-bit/48-character chash form) in a unit.
- Root cause: `chash.js:45-53` unconditional `throw` combined with `chash.js:152-171` failing to validate/catch the decoded length before calling into fixed-length-assuming helpers.
- Impact: uncaught exception thrown during unit validation causes the validating node (hub, witness, full node) to crash — a denial-of-service that can prevent the node from continuing to validate/confirm new units, which matches the "network unable to confirm new units" impact class in scope.

### Limitations / what I could not fully verify

I was unable to directly inspect, in this session, the exact `definition.js` call site that invokes `ValidationUtils.isValidChash(x, 48)` (the "definition template" op) to confirm with 100% certainty that the 48-character/base64 code path is reachable from ordinary unit content without additional guarding try/catch further up the call stack. My tool budget was exhausted before I could pull that specific snippet. The 32-character/address path is confirmed safe (fixed-length base32 decode), but the 48-character path's reachability and exception-handling context in `definition.js`/`aa_validation.js` should be verified directly before treating this as a confirmed, exploitable crash.

### Recommendation (conceptual, not a plan since this is ask-only mode)

`chash.js`'s `isChashValid()` should validate that the decoded buffer's bit-length is exactly 160 or 288 *before* calling `buffer2bin`/`separateIntoCleanDataAndChecksum`, returning `false` instead of letting `separateIntoCleanDataAndChecksum` throw an uncaught exception. This closes the gap regardless of which call sites exercise the 48-character path.
