### Title
Webhook signature is verified against `repository.owner.login` while all event handlers act on the independent `repository.full_name` field, allowing an org whose secret is known to forge webhooks against a different organization's repositories - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which `GitHubApp`/`webhook_secret` to validate the HMAC against using `repository.owner.login` (falling back to `organization.login`), but every webhook handler (`PushHandler`, the `PullRequest::*Handler`s, `ReviewStackAdapter`) resolves the *actual repository/stack to act on* from the sibling field `repository.full_name`. Nothing in the codebase asserts that `repository.owner.login` is the owner segment of `repository.full_name`. On a multi-tenant Shipit install (the documented "Using Multiple Github Applications" mode where each GitHub org has its own `webhook_secret`), a party who knows one org's webhook secret can forge a raw POST body whose `owner.login` matches their own org (so the correct, weaker secret is selected and the HMAC verifies) while `full_name` points at a repository belonging to a *different* tenant/org configured on the same instance.

### Finding Description
- `verify_signature` selects the verification key like this: [1](#0-0) [2](#0-1) 

- `GitHubApp#verify_webhook_signature` performs a straightforward HMAC-SHA1 comparison over the raw body using the secret selected above — it has no knowledge of, or opinion on, which repository the payload claims to target: [3](#0-2) 

- Shipit explicitly supports per-organization webhook secrets for multi-tenant installs: [4](#0-3) [5](#0-4) 

- Every handler, however, determines the repository to act on from a *different* field of the same JSON payload — `repository.full_name` — completely independent of `repository.owner.login`: [6](#0-5) [7](#0-6) [8](#0-7) [9](#0-8) 

Because the entire raw body is HMAC'd, an attacker cannot alter a *legitimate* GitHub-originated payload without breaking the signature. But nothing prevents an attacker who directly controls (or knows) the webhook secret configured for one org ("OrgA" in a multi-org `secrets.yml`) from crafting an entirely new POST body from scratch where:
- `repository.owner.login` = `"OrgA"` (so `verify_signature` picks OrgA's weaker/known secret and the HMAC computed with that secret checks out), and
- `repository.full_name` = `"OrgB/victim-repo"` (a repository belonging to a completely different, unrelated org/tenant hosted on the same Shipit instance).

The signature check only proves "the sender knows OrgA's secret" — it says nothing about which repository is legitimately covered by that secret, because the field it keys off (`owner.login`) is never cross-checked against the field the business logic actually consumes (`full_name`). This is exactly the "verified vs acted-upon field" binding failure: `signature-authenticated organization == organization derived from repository.owner.login` while `repository actually written to == organization derived from repository.full_name`, and these two need not be equal.

### Impact Explanation
Once the forged webhook reaches a handler, effects reachable for `OrgB/victim-repo` include:
- `PushHandler` enqueues `GithubSyncJob` for any matching stack, causing Shipit to re-fetch commits and mark the victim stack accessible/inaccessible, an unauthenticated trigger of internal job processing against a repository the forger has no legitimate relationship to.
- `PullRequest::OpenedHandler` → `ReviewStackAdapter#find_or_create!` will *create a new `ReviewStack` record* for the victim repository, populated from wholly attacker-controlled `pull_request` data (branch/ref/sha/labels), and immediately enqueue it onto `ReviewStackProvisioningQueue`, which leads to an actual provisioning/deploy attempt of attacker-chosen branch content for a repository owned by a different tenant.
- `Labeled/Unlabeled/Closed/Reopened` handlers can archive/unarchive/deprovision review stacks belonging to the victim org.

This crosses the "cross-repository writes" / "unauthorized deploy" bar (Critical) because it lets one tenant's known/compromised secret trigger provisioning and deploy-queue actions against a different tenant's repository/stack on a shared Shipit instance, entirely bypassing per-organization isolation that the multi-org `webhook_secret` feature is meant to provide.

### Likelihood Explanation
This requires a genuinely multi-tenant Shipit deployment (multiple GitHub orgs configured with distinct `webhook_secret`s, as documented) and requires the attacker to know/hold the webhook secret configured for at least one of the tenants — e.g., an admin of "OrgA"'s installed GitHub App (who is authorized to configure OrgA's own webhook secret, but not OrgB's). That party is an "unprivileged attacker" with respect to OrgB, satisfying the rules' "unprivileged-attacker analog." Likelihood is Medium: it depends on the host actually running the multi-org configuration and on one tenant being willing/able to abuse their own legitimate credential, but no exploit of GitHub itself, no `ApiClient` token, and no repository write access to the victim repo is required.

### Recommendation
In `WebhooksController#verify_signature` / the `Handler` base class, enforce that the organization used to select the verification secret (`repository.owner.login` / `organization.login`) matches the owner segment parsed from `repository.full_name` before any handler runs; reject the request (422) on mismatch. More robustly, resolve the target `Repository`/`Stack` first (from `full_name`), then verify the signature specifically against the `webhook_secret` belonging to that repository's configured organization, and refuse to process the event if that organization does not equal the one implied by `owner.login`.

### Proof of Concept
1. Deploy Shipit configured with the documented multi-org scheme: `github.OrgA.webhook_secret = "secretA"`, `github.OrgB.webhook_secret = "secretB"` (see `docs/setup.md` §"Using Multiple Github Applications").
2. An actor who administers OrgA's GitHub App (and therefore knows `secretA`) crafts:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(secretA, raw_body)>` and POST it to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` = `"OrgA"`, loads OrgA's `GitHubApp`, and the HMAC matches `secretA` → request is accepted (`app/controllers/shipit/webhooks_controller.rb:24-30`).
5. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("OrgB/victim-repo")` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) and enqueues `GithubSyncJob`/triggers review-stack provisioning for a repository that belongs to OrgB, not OrgA — despite the request only ever having been authenticated as originating from OrgA's secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
