### Title
Cross-tenant CI status forgery via unscoped SHA lookup in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits to update purely by `sha`, with no constraint that the commit's own `stack`/repository matches the repository that the webhook signature was verified against. Any Shipit-onboarded repository (including one the attacker legitimately owns, e.g. a public fork of the victim's repo) can therefore emit a validly-signed `status` webhook that writes a forged `success` `Status` row against a commit belonging to an unrelated victim stack, corrupting `Commit#deployable?` and, downstream, `Deploy#ignored_safeties` computed in `Stack#build_deploy`.

### Finding Description
The binding that should hold is: `commit.deployable? == (commit's status was computed exclusively from Status/CheckRun rows whose provenance is the webhook signed by that same commit's own stack/organization)`. This binding is broken.

Path:
- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) resolves `Shipit.github(organization: repository_owner)` where `repository_owner` is read straight out of the attacker-supplied JSON body (`params.dig('repository','owner','login')`, line 61), and verifies the HMAC signature against *that* org's configured webhook secret. This only proves the payload was signed by *some* legitimately configured org/app on the Shipit instance — the attacker's own org, if their own repository is separately onboarded as a Shipit stack — not that it was signed by the victim's org. [1](#0-0) [2](#0-1) 

- Once signature verification passes, `WebhooksController#create` dispatches to `StatusHandler.call(params)` (`app/models/shipit/webhooks.rb:19`), whose `process` method does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
This query is **global across all stacks** — it is not filtered by `repository_owner`, `repository.full_name`, or any stack/org identity tied to the verified signature. [3](#0-2) 

- `Commit#create_status_from_github!` writes the status using the *commit's own* `stack_id` (i.e. the victim stack's id, not the attacker's), via `statuses.replicate_from_github!(stack_id, github_status)`: [4](#0-3) [5](#0-4) 

- `Commit#deployable?` is purely a function of the `Status`/`CheckRun` rows attached to the commit, regardless of which webhook (and which org's signature) produced them: [6](#0-5) 

- `Stack#build_deploy` then derives `ignored_safeties: force || !until_commit.deployable?`, so once the forged status flips `deployable?` to `true`, a non-forced deploy is recorded as `ignored_safeties: false` — i.e. marked as CI-validated: [7](#0-6) 

Exploit flow: since Git commit SHAs are content-addressed, any commit shared between the victim's upstream repository and an attacker's fork (i.e. every commit up to the fork point, which is virtually always true for the commits a maintainer is about to deploy) has an identical SHA in both repositories. The attacker, who legitimately owns a Shipit-onboarded fork/repository (their own stack, their own registered webhook secret), sets a `success` commit status on their fork for that shared SHA via the normal GitHub Statuses API (something any repo owner can do without any Shipit secret). GitHub delivers a `status` webhook to Shipit, signed with the attacker's own org's webhook secret — this passes `verify_signature` because verification only checks "signed by a configured org", not "signed by the org that owns this commit's stack". `StatusHandler#process` then matches the shared SHA against the victim's `Commit` record and writes a `success` `Status` scoped to the victim's `stack_id`.

None of the listed guards prevent this: `verify_signature`/`verify_webhook_signature` only authenticates that *some* onboarded org signed the payload, not that it's the correct org for the target commit; `drop_unhandled_event` and `ExplicitParameters` (`StatusHandler`'s `params do ... end` schema) only validate the shape of `sha`/`state`, not repository provenance; there is no `force_github_authentication`, `require_permission!`, or repository-membership check anywhere in this path because webhooks are unauthenticated-by-user by design.

### Impact Explanation
A `Status` record with `state: success` is written for the victim's stack/commit without any authentication that it originated from the victim's own CI/org — this is exactly the "a payload for one repository mutating another's stack, commit, task or task" Critical category. Concretely: `Commit#deployable?` becomes `true` for a commit whose real CI status may be `pending`/`failure`/absent, `Stack#next_commit_to_deploy`/continuous-deployment logic can auto-select and deploy it, and any subsequent human-triggered non-forced deploy through `Api::DeploysController#create` is recorded with `ignored_safeties: false`, misrepresenting an un-vetted deploy as CI-validated. This is repeatable against any commit SHA the attacker can get a forged status onto (trivial via forks sharing history) and against any Shipit stack tracking that SHA, i.e. it generalizes across every tenant on a shared Shipit instance.

### Likelihood Explanation
Preconditions: the Shipit instance must host more than one independently-configured org/repository (a normal multi-tenant deployment), the attacker must control at least one such onboarded repository/fork (trivial, self-service in most Shipit deployments, or simply being any user permitted to add their own fork as a stack), and the victim commit's SHA must be known/shared (trivially true for any commit that predates a public fork). No Shipit secrets, sessions, or API tokens are required. Cost to the attacker is a single `status` webhook (or a real GitHub commit status set via their own token) per target commit, fully repeatable.

### Recommendation
Scope the `StatusHandler` (and `CheckSuiteHandler`/similar handlers) commit lookup to the stack/repository that was actually authenticated by `verify_signature`, e.g. filter `Commit.where(sha: params.sha)` by `stack.repository == payload_repository` (matching `repository_owner`/`repository.full_name` from the webhook against the commit's own stack's repository) before calling `create_status_from_github!`, rejecting or ignoring commits that don't belong to the authenticated repository.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb (conceptual)
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossRepoTest < ActiveSupport::TestCase
        test "a status signed for org B must not mark org A's commit deployable" do
          victim_stack = shipit_stacks(:shipit) # belongs to org "shopify"
          attacker_stack = shipit_stacks(:some_other_org_stack) # belongs to org "attacker-org"

          shared_sha = "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef"
          victim_commit = victim_stack.commits.create!(sha: shared_sha, ...)

          # Simulate a validly-signed webhook for attacker-org claiming success on shared_sha
          params = { 'sha' => shared_sha, 'state' => 'success', 'context' => 'ci/attacker',
                     'repository' => { 'owner' => { 'login' => 'attacker-org' } } }

          refute victim_commit.reload.deployable?

          StatusHandler.new.call(params) # equivalent to what verify_signature-passed webhook triggers

          # BROKEN BINDING: victim's commit becomes deployable from a foreign org's signed payload
          assert victim_commit.reload.deployable?

          deploy = victim_stack.build_deploy(victim_commit, shipit_users(:walrus), force: false)
          assert_equal false, deploy.ignored_safeties # should be true/blocked, but is false
        end
      end
    end
  end
end
```
This asserts both sides of the binding explicitly: `victim_commit.deployable?` before (`false`) and after (`true`) an attacker-signed, cross-org `status` payload, and shows `Deploy#ignored_safeties` incorrectly ending up `false` for a non-forced deploy whose CI signal never came from the victim's own org.
