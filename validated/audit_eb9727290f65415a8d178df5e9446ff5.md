### Title
Fee-on-Transfer ERC20 Tokens Cause Counterpart Bridge Reserve Drain via Inflated `RequestValueTransfer` Event — (File: `contracts/service_chain/bridge/BridgeTransferERC20.sol`)

---

### Summary

`BridgeTransferERC20.requestERC20Transfer` and `onERC20Received` assume that `safeTransferFrom` delivers exactly `_value + _feeLimit` tokens to the bridge. If the registered ERC20 token charges a fee on transfer, the bridge receives fewer tokens than it records in the `RequestValueTransfer` event. The counterpart bridge then releases the full nominal `_value` to the recipient, draining its reserves by the fee-on-transfer shortfall on every crossing.

---

### Finding Description

In `requestERC20Transfer`:

```solidity
IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
_requestERC20Transfer(_tokenAddress, msg.sender, _to, _value, _feeLimit, _extraData);
``` [1](#0-0) 

The bridge pulls `_value + _feeLimit` from the caller. For a fee-on-transfer token with rate `r`, the bridge actually receives `(_value + _feeLimit) × (1 − r)`. No balance-before/after check is performed.

`_requestERC20Transfer` then calls `_payERC20FeeAndRefundChange`, which issues two additional `safeTransfer` calls — one to `feeReceiver` for `fee` and one back to the user for `_feeLimit − fee`:

```solidity
IERC20(_token).safeTransfer(feeReceiver, fee);
...
IERC20(_token).safeTransfer(from, feeRefund);
``` [2](#0-1) 

Each of these transfers also deducts a fee from the bridge's balance. After all outflows, the bridge retains approximately `(_value + _feeLimit)(1 − r) − _feeLimit` tokens — strictly less than `_value`.

Despite this shortfall, `_requestERC20Transfer` emits:

```solidity
emit RequestValueTransfer(
    TokenType.ERC20, _from, _to, _tokenAddress,
    _value,          // ← nominal amount, not actual received
    requestNonce, fee, _extraData
);
``` [3](#0-2) 

The counterpart bridge's operators observe this event and call `handleERC20Transfer` with the full `_value`, releasing that amount to the recipient:

```solidity
IERC20(_tokenAddress).safeTransfer(_to, _value);
``` [4](#0-3) 

The same flaw exists in the 1-step path `onERC20Received`, which passes the caller-supplied `_value` directly to `_requestERC20Transfer` without verifying what the bridge actually received: [5](#0-4) 

---

### Impact Explanation

**Unauthorized drain of counterpart bridge ERC20 reserves.**

Per transfer the counterpart bridge over-releases by `(_value + _feeLimit) × r` tokens (where `r` is the token's transfer-fee rate). An attacker can repeatedly bridge a fee-on-transfer token to systematically empty the counterpart bridge's liquidity pool. In lock/unlock mode (`modeMintBurn = false`) this directly steals real tokens held by the counterpart bridge. In mint/burn mode the minted supply on the destination chain permanently exceeds the burned supply on the source chain, breaking the 1:1 peg.

---

### Likelihood Explanation

The Kaia service-chain bridge explicitly supports arbitrary registered ERC20 tokens (WBTC, WETH, USDC, LINK, etc.). USDT already has fee-on-transfer logic deployed on Ethereum (fee currently set to 0, but changeable by the issuer). Any future token registration with a non-zero transfer fee, or any issuer activating a dormant fee, immediately triggers this condition. No special privilege is required — any user can call `requestERC20Transfer` or use the 1-step `requestValueTransfer` path on the token contract.

---

### Recommendation

Use the balance-before/balance-after pattern to determine the actual amount received, and use that value in the event and for downstream accounting:

```solidity
function requestERC20Transfer(...) public {
    uint256 balBefore = IERC20(_tokenAddress).balanceOf(address(this));
    IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
    uint256 actualReceived = IERC20(_tokenAddress).balanceOf(address(this)).sub(balBefore);
    // derive actual _value and _feeLimit from actualReceived, then proceed
    _requestERC20Transfer(_tokenAddress, msg.sender, _to, actualValue, actualFeeLimit, _extraData);
}
```

Apply the same pattern inside `_payERC20FeeAndRefundChange` for the fee and refund transfers, or restrict bridge registration to tokens that are known not to charge transfer fees.

---

### Proof of Concept

**Setup:** Deploy a fee-on-transfer ERC20 (1% fee) and register it on both the source and counterpart bridges in lock/unlock mode.

**Steps:**

1. Alice calls `requestERC20Transfer(feeToken, Bob, 1000e18, 0, "")` on the source bridge.
2. Source bridge calls `safeTransferFrom(Alice, bridge, 1000e18)`. Due to 1% fee, bridge receives **990e18**.
3. No bridge-side fee is configured (`feeOfERC20 = 0`), so `_payERC20FeeAndRefundChange` is a no-op.
4. Source bridge emits `RequestValueTransfer(..., valueOrTokenId=1000e18, ...)`.
5. Operators observe the event and call `handleERC20Transfer(..., _value=1000e18, ...)` on the counterpart bridge.
6. Counterpart bridge calls `safeTransfer(Bob, 1000e18)`, releasing **1000e18** from its reserves.

**Result:** Source bridge locked **990e18**; counterpart bridge released **1000e18**. Net loss to counterpart bridge: **10e18 per transfer**. Repeated N times, the counterpart bridge is drained of `N × 10e18` tokens with no attacker cost beyond gas.
