### Title
Tokens sent directly to the pool or controller are permanently locked — the contracts accept any token balance but only ever release amounts tracked in `cash` or a measured per-call delta, with no recovery path - ([File: contracts/pool/src/cache/cash.rs])

### Summary
The OpenQ report describes a bounty contract that accepts funding in any token but can only pay out one token, stranding the rest until expiry. The XOXNO Lending analog is stronger: the pool and the controller custody token balances that no accounting leg ever reaches. The pool's only outbound transfers are `Cache::transfer_out` calls sized by the `cash` book or a refund bounded by a declared inbound amount, and the controller only ever refunds the *measured delta* of a single call. Any token balance not created inside one of those flows — a direct SAC transfer to either contract, in a listed or non-listed token — is permanently frozen. Unlike OpenQ, there is not even a delayed refund path: no sweep, rescue, or claim entrypoint exists on either contract (`sweep_balance`/`claim_admin_fees` exist only on the out-of-scope swap-aggregator).

### Finding Description
The pool is a hub/spoke design: multiple `(hub_id, asset)` markets share one physical token balance per contract, and every outbound leg (`borrow`, `withdraw`, `repay` overpayment, `recapitalize` excess, `claim_revenue`, `flash_loan`) is sized from bookkeeping, never from `token.balance(pool)`:

- `Cache::transfer_out` moves at most what the caller-computed `cash` accounting dictates (`contracts/pool/src/cache/cash.rs:46-53`).
- `require_reserves` and `debit_cash` cap payouts at `cash`, so custody above `cash` is unreachable (`cash.rs:15-41`).
- `recapitalize` refunds only `amount - applied` of *this call's* prefunded tokens (`contracts/pool/src/ops/recapitalize.rs:52-58`); a pre-existing excess balance is never touched.
- `flash_loan`'s three `require_balance` equality checks are deltas around the live balance, so donated balances neither break nor get swept by flash loans (`contracts/pool/src/ops/flash.rs:60-67, 179-188`).

The test suite itself pins the behavior: `pool_all_money_paths_preserve_books_and_shared_token_custody` sends `7 * UNIT` directly to the pool and then asserts `token.balance(pool) == cash + other.cash + 7 * UNIT` forever — "an unsolicited donation belongs to no market's cash book" (`tests/test-harness/tests/pool_money_flow_audit.rs:86-96`).

On the controller side, `refund_controller_balance_delta` deliberately preserves the pre-existing balance and refunds only `balance_delta_since(balance_before)` (`contracts/controller/src/payments.rs:41-51`), and `flash_position` keeps callback-pushed tokens that are declared in neither `collaterals` nor `refunds` "uncredited" at the controller (`docs/reference/invariants.md`, INV-STRAT-04). The integration test intentionally seeds the controller with donations and asserts they never move (`tests/integration/flows/flash_position.sh:349-372`, "controller baselines must contain donated funds").

There is no `receiveFunds`-style gate either: nothing in `token.transfer` to a contract can be rejected, and neither contract exposes an owner sweep, so the stranded state is permanent rather than "wait for expiry" as in OpenQ.

### Impact Explanation
Permanent freezing of user funds — within the accepted impact list. Any user or integrating contract that transfers a token directly to the pool (the documented "transferring repayment directly to the pool is a donation" case in `skills/xoxno-lending-liquidations/SKILL.md:76-79`), sends a wrong/non-listed token, or pushes an undeclared asset in a `flash_position` callback loses it with no recovery mechanism whatsoever. The loss scales with the amount sent; there is no expiry-unlock as in the OpenQ original.

### Likelihood Explanation
Reachable by a single unprivileged address via an explicitly permitted action (direct token transfer to pool/controller). The mistaken-funding path is realistic: the liquidations skill has to warn integrators not to fund the pool directly, and the SDK skill warns against setting `to` = pool/controller on withdraw precisely because it strands tokens (`skills/evals/.../07-unwind-repay-withdraw-all.json`). However, the loss requires the sender's own error — no third party can force or profit from it — which keeps this at Medium rather than higher. Note a partial caveat: where a document explicitly calls the behavior out (e.g., INV-STRAT-04's "remains uncredited if in neither list"), a judge may treat that sub-case as a documented design choice; the pool-side custody gap has no equivalent documented recovery rationale.

### Recommendation
Add a recovery path for excess custody. Options consistent with the codebase's structure:
- A controller-owner-only `sweep(asset, to, amount)` on the pool and controller that computes `token.balance(contract) - total_owed` and refuses to touch amounts owed to `cash`/positions — the pool would need the excess computed as `balance - sum(cash over all markets sharing the asset)`, which the current per-market `cash` book does not directly expose, so an aggregate `custody_floor` per asset may need tracking.
- Alternatively, a permissionless `donate(asset)`/skim-style entrypoint that credits unsolicited balance increases of a listed asset to that asset's `cash` (making them withdrawable liquidity) and reverts for non-listed assets, eliminating the permanently-stuck class without adding privileged authority.

```
token_admin.mint(&payer, &amount);
token.transfer(&payer, &pool, &amount);          // or any non-listed token
// There is no entrypoint that can release this balance:
//   - borrow/withdraw are capped by `cash` (Cache::require_reserves)
//   - repay/recapitalize refunds only refund this-call prefunding deltas
//   - claim_revenue is bounded by revenue shares
//   - flash_loan balances are measured as deltas, never skimming excess
// token.balance(pool) - sum_of_cash stays > 0 permanently.
```

For the controller leg, `tests/integration/flows/flash_position.sh:349-372` already demonstrates seeded controller balances that no operation touches; for the pool leg, `pool_money_flow_audit.rs` asserts the donation persists through borrow/repay/withdraw flows.
