### Title
Insufficient commit-completion verification lets `security-guidance`'s LLM security review be silently skipped on legitimate commits - (File: `plugins/security-guidance/hooks/security_reminder_hook.py`)

### Summary
The `security-guidance` plugin's `PostToolUse[Bash]` hook decides whether a `git commit` actually happened using a narrow heuristic — a regex match on stdout/stderr for a `[branch sha]` line plus a git diffstat marker, with a reflog fallback — before running its LLM-based commit-review. This mirrors the ZetaChain bug pattern: a verification check is too narrow to reliably confirm a legitimate event occurred, so the event (here, a real commit containing attacker/model-introduced vulnerable code) is silently missed rather than analyzed.

### Finding Description
`handle_commit_review_posttooluse` requires `commit_succeeded` to be true before it will review anything: [1](#0-0) 
`commit_succeeded` is derived only from `_COMMIT_SHA_RE` matching a `[branch sha]`-style line and `_COMMIT_DIFFSTAT_PATTERNS` matching diffstat text in the captured stdout/stderr: [2](#0-1) 
If neither pattern matches, the code falls back to a reflog-based heuristic (`_git_reflog_recent_commits`) which itself only succeeds under specific freshness/staleness windows: [3](#0-2) 
When both the output-pattern check and the reflog fallback fail to positively identify the commit, the hook exits without ever building a diff or invoking the LLM reviewer: [4](#0-3) 

Because these are pattern/heuristic checks rather than an authoritative confirmation (e.g., comparing pre/post `HEAD` unconditionally), any commit whose output doesn't match the expected shape — `git commit -q`/`--quiet`, output redirected/piped through `2>&1 | something`, a custom `commit.template`/hook wrapper that changes git's printed format, or output arriving outside the freshness window the reflog fallback checks — is treated as "commit did not succeed" (`skip_reason=21`) even though a real commit landed in the repository. This is the same root cause as the ZetaChain report: the verifier checks a specific expected shape of a legitimate event instead of the underlying ground truth, so valid events that don't match the expected shape are dropped.

### Impact Explanation
The `security-guidance` plugin exists specifically to catch security vulnerabilities that Claude (the agent, potentially prompt-injected or simply mistaken) introduces into committed code, per its own hook description ("pattern-based warnings on edits, git-diff-based LLM review on stop"). Its `hooks.json` wires this same handler to fire on `Bash(git commit:*)`: [5](#0-4) 
If the commit-completion check fails open (mis-detects a successful commit as failed), the LLM security review that is supposed to gate that commit never runs, and the security finding never surfaces to the developer. The Stop-hook review is a secondary, opportunistic path and not a guaranteed replacement, since it operates on session-level diffs and heuristics of its own. A user/agent action that legitimately produces quiet or non-standard git output (no malice required) silently defeats the plugin's core security-review guarantee — this is a hook-bypass of a security control the plugin advertises as providing, analogous to ZetaChain's tracker silently dropping legitimate inbound transactions whose shape didn't match the narrow verifier.

### Likelihood Explanation
This requires no privileged access — any user or agent session running `git commit -q`, or any git wrapper/alias/hook that changes the printed commit line or diffstat format, or output piped/redirected such that the exact `[branch sha]` regex or diffstat regex doesn't match, triggers this path. The reflog fallback narrows but does not eliminate the gap (it depends on freshness windows and dedup state). This is a realistic, easily-triggered condition rather than an exotic edge case.

### Recommendation
Replace the output-pattern detection with an authoritative check: compare `git rev-parse HEAD` (or `HEAD@{0}`) captured before and after the Bash tool call runs, independent of what the command printed. If it changed, a commit happened and should be reviewed, regardless of `-q`/piping/custom hook output. Keep the current regex/reflog heuristics only as a secondary hint (e.g., to disambiguate multiple commits in a single compound command), not as the sole gate for deciding whether to run the review at all.

### Proof of Concept
1. In a repo with the `security-guidance` plugin enabled, have Claude run `git add -A && git commit -q -m "add feature"` where the diff contains a clear vulnerability (e.g., a hardcoded secret or command injection).
2. `git commit -q` suppresses the `[branch sha] subject` line and the diffstat output that `_COMMIT_SHA_RE` / `_COMMIT_DIFFSTAT_PATTERNS` look for.
3. `commit_succeeded` evaluates false; the reflog fallback may also miss it depending on timing/dedup state (`sg-reviewed-shas`).
4. `handle_commit_review_posttooluse` exits at `skip_reason=21` without ever calling `git show`/`analyze_code_security`/`agentic_review`.
5. The vulnerable commit is never flagged by the commit-review path, even though a real commit with real vulnerable code was made.

_COMMIT_DIFFSTAT_PATTERNS = [
    re.compile(r'\b\d+ files? changed'),
    re.compile(r'^ create mode ', re.MULTILINE),
    re.compile(r'^ delete mode ', re.MULTILINE),
    re.compile(r'^ rename ', re.MULTILINE),
]

# Capture-group form of the [branch sha] pattern. Mirrors Claude Code's own
# commit-id parsing, but tolerates spaces before the
# sha (covers `[detached HEAD abc1234]`). 7–40 hex chars: git's abbrev floor
# through full sha; the abbrev resolves fine with `git show`. Anchored to
# line-start so a `[hex]` in the commit subject (`[main abc] Revert [e38]`)
# or trailing hook output isn't picked up and fed to `git show`.
_COMMIT_SHA_RE = re.compile(r'^\[[^\]]*?\b([0-9a-f]{7,40})\]', re.MULTILINE)

# Regex matching `git commit` commands. Mirrors Claude Code's own commit
# detection — it does NOT tolerate `git -c k=v commit` global options, which
# keeps this hook aligned with CC's commit attribution on what counts as a
# commit.
_GIT_COMMIT_RE = re.compile(r'\bgit\s+commit(?:\s|$)')
