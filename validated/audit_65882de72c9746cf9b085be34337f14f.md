### Title
Unguarded post-callback settlement lets a listed transfer-hook token reenter controller entrypoints while `flash_position` holds stale in-memory positions - (File: contracts/controller/src/strategies/flash_position.rs)

### Summary
`process_flash_position` wraps only the debt mint, forwarding, and receiver callback in `storage::with_flash_guard` (lines 120-143). Every settlement step after the callback — measuring collateral deltas, depositing them via the pool, and transferring declared `refund_assets` back to the caller — runs with the flash guard already cleared. A listed token contract with a `transfer` hook can therefore reenter monetary controller entrypoints (`withdraw`, `borrow`, `repay`, `liquidate`, `flash_loan`, strategies) mid-settlement, while the outer flow continues to hold and later persist an `Account` loaded before the reentrant mutation. The reentrant write is then clobbered by the outer stale write, while the reentrantly-moved tokens stay moved — the same shape as CVE-2017-15951's unsynchronized "find negative vs. update" race, mapped onto Soroban's single-transaction execution as a stale-load vs. nested-update desynchronization.

### Finding Description
- The guarded window is limited to `mint_and_forward`, the baseline `snapshot_balances` calls, and `invoke_receiver` (`with_flash_guard`, flash_position.rs:120-143).
- The test suite itself documents the gap: "The refund `balance` and `transfer` calls run after `with_flash_guard` closes" (tests/test-harness/tests/strategy/flash_position_adversarial.rs:170-172). The skill documentation confirms the ordering: after the callback returns the controller measures deltas, deposits collateral, refunds listed assets, and only then enforces "debt and collateral remain open" plus LTV/HF/min-borrow gates (skills/xoxno-lending-contracts/flash-loans.md:124-133).
- All reentrancy coverage targets the guarded window only (FlashPositionMode::Reenter* tests, `flow_flash_position_malicious` in tests/integration/flows/flash_position.sh:906-961). Nothing tests a token hook firing during the deposit or refund legs.
- `refund_assets` must be listed (validated via `validate_refund_assets` → `AssetNotInSpoke`), but listing does not exclude hook-bearing token contracts — the codebase explicitly supports them (`with_transfer_hook_market` fixture in flash_position_adversarial.rs:149-168).
- Account positions are loaded once into `Account` (`load_or_create_account`, flash_position.rs:93-101) and persisted at finalization (`finalize_position_flow`). A reentrant `withdraw`/`repay` on the same `account_id` (or on `Credit`-mode share movement) loads the *stored* positions — which still reflect the pre-settlement state for any leg the outer flow has not yet written — mutates them, moves real tokens, and commits. The outer flow then persists its stale in-memory `supply_positions`/`borrow_positions`, restoring shares that were already paid out, while the risk gates pass on the stale snapshot.

### Impact Explanation
An attacker who controls a listed hook token and an existing account with collateral can: trigger `flash_position` with the hook token in `refund_assets` (or as a deposited collateral leg), have the hook reenter `withdraw` on the same account to pull real pool tokens, then let the outer flow overwrite the storage record with the stale, larger share balances. The account ends with its full collateral shares intact *and* the attacker holding the withdrawn tokens — a direct double-spend of pool reserves, repeatable to drain a market. This is theft of user funds reachable by a single unprivileged address through `flash_position` (allowed: "own flash receiver or swap route") plus one listed hook token, mirroring the CVE's class: an update committed concurrently with a consumer that still holds the pre-update view.

### Likelihood Explanation
Reachable by any unprivileged caller whenever a listed asset implements transfer-time code execution — the codebase's own test harness treats such tokens as a supported market type (`with_transfer_hook_market`, `weird_token`). Cost is one `flash_position` call plus a dust balance of the hook token pre-seeded to the controller so its refund delta is positive. The attacker's account must exist beforehand (an existing `Multiply`/`Long`/`Short` account with collateral is the natural target). Uncertainty: the exploit's final profitability depends on the exact persistence order inside `finalize_position_flow` — if every position write occurs eagerly inside the guarded/deposit phase before the first post-guard token call, the reentrant gate may instead fail on already-updated state; the refund leg, however, is confirmed by tests to run after the guard closes, so at minimum refund-leg hooks are unguarded. No privileged action, leaked key, or off-chain component is required once a hook token is listed.

### Recommendation
Extend `storage::with_flash_guard` to cover the entire settlement phase of `process_flash_position` — collateral deposit, refund transfers, position persistence, and the final risk gates — not just mint/forward/callback. Alternatively, restructure settlement to complete all position writes and risk gates before any post-callback token transfer (checks-effects-interactions), or block refund/collateral assets whose token contract is not a known-callback-free interface. Add adversarial tests that fire a token hook during the refund and deposit legs, asserting nested `withdraw`/`borrow`/`repay`/`flash_loan` calls revert.

### Proof of Concept
1. Assume a listed asset `H` (a token contract whose `transfer` runs attacker code, as modeled by `with_transfer_hook_market`/`weird_token`) and an attacker account `A` holding collateral `C` and eligible for `flash_position` on debt asset `D` with `is_flashloanable`.
2. Attacker pre-transfers dust of `H` to the controller so its refund delta is positive, and supplies `C` collateral on `A`.
3. Attacker calls `controller.flash_position(caller=A, account_id=A, mode=Long, debt=D, amount=x, receiver=R, collaterals=[(C_listed, min)], refund_assets=[H])`.
4. The guard wraps mint/forward/callback; `R` returns the required collateral; the guard clears.
5. Settlement deposits collateral deltas and then calls `H.transfer(controller → caller, delta)`. `H`'s hook reenters `controller.withdraw(caller=A, account_id=A, assets=[(C, full)])` — `require_not_flash_loaning` passes because the guard is cleared; the stored `supply_positions` still show the pre-settlement balance for any leg not yet persisted, so the withdrawal's HF/usage gates evaluate against stale state and the pool pays out `C` tokens.
6. The outer flow resumes and `finalize_position_flow` persists the in-memory `Account` loaded at step 3, restoring `A`'s `C` supply shares. Net: attacker holds the withdrawn `C` tokens and retains the shares; protocol backing is reduced by the withdrawn amount — insolvency/theft of supplier funds.
