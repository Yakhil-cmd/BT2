### Title
Liveness endpoint never reflects post-initial sync failures, masking persistent sync denial - (File: main.go)

### Summary
The `MagicLpAggregator` finding is about a status-returning function (`latestRoundData`) whose metadata fields are hardcoded and never reflect the real state of the underlying data, causing integrators who trust that metadata to make incorrect freshness/liveness decisions. The analogous defect in `git-sync` is the `/` HTTP liveness handler registered in `main()`, which is likewise a one-way, "dumb" status signal: once the repo is marked ready it can never become un-ready again, regardless of how badly or how long subsequent sync attempts fail.

### Finding Description
`git-sync` exposes an HTTP endpoint intended for Kubernetes startup/liveness probes: [1](#0-0) 

The comment itself acknowledges the limitation: "This is a dumb liveliness check endpoint. Currently this checks nothing and will always return 200 if the process is live." The only state it consults is the package-level `repoReady` boolean, guarded by `getRepoReady()`/`setRepoReady()`: [2](#0-1) 

`setRepoReady()` is called unconditionally on every successful pass through the sync loop, and critically there is **no corresponding call that resets `repoReady` to `false`** anywhere in the codebase — `setRepoReady`/`repoReady` occur only in the six locations tied to this initialization and the loop's success branch. Once the first successful sync happens, the handler will return HTTP 200 forever, even if every subsequent sync attempt fails.

The sync loop's failure branch only affects `failCount` and, depending on `--max-failures`/`--init-max-failures`, may call `os.Exit(1)`: [3](#0-2) [4](#0-3) 

By default `--max-failures` is `0`, so any failure after the initial sync causes the process to exit — but this flag is explicitly documented as configurable to a negative value to "retry forever": [5](#0-4) 

When an operator sets `--max-failures=-1` (a supported, documented configuration for long-running sidecars that should tolerate transient network/auth issues), `getMaxFailures()` returns `-1`, the `maxFails >= 0` guard in the loop is never true, and the process never exits on failure — it just keeps retrying indefinitely while `repoReady` stays permanently `true` from the one earlier success. The HTTP `/` endpoint keeps returning 200 the entire time, no matter how long or how completely sync has been broken (auth failure, unreachable remote, corrupted ref, malicious commit that breaks fetch/checkout, etc.).

### Impact Explanation
This falls into the "publishing wrong or partial content" / "persistent sync denial" impact category: Kubernetes readiness/liveness probes (the analogous "integrator" to the oracle-consuming DeFi protocol in the source report) rely on this endpoint's status code exactly as the report's example relies on `updatedAt`. Because the endpoint carries no notion of "last successful sync time" or "currently failing," an orchestrator will never restart or evict a pod whose git content has gone stale for an extended period, and any downstream service relying on `--link` will keep serving outdated files while infrastructure believes it is "live." This is a real, if narrower-than-execution, integrity/availability defect: it silently defeats the entire purpose of the liveness probe once retry-forever mode is combined with an unrecoverable sync failure caused by attacker-controlled or corrupted remote content.

### Likelihood Explanation
Requires the deployment to be configured with `--max-failures` (or `--init-max-failures`) set to a negative value — a documented, legitimate, non-malicious configuration choice for tolerating transient errors — combined with any sync-breaking condition (which can originate from attacker-controlled repo content, e.g., a malformed submodule, an unreachable/renamed ref, or a commit that breaks checkout). Given the default is `0` (fail-fast), the bug is latent unless this specific flag combination is chosen, which lowers likelihood but does not eliminate it, since "retry forever" is an explicitly advertised feature for exactly this endpoint's consumers (Kubernetes probes).

### Recommendation
Make the liveness handler reflect actual current health rather than a monotonic "ever succeeded" flag: track the timestamp of the last successful sync and the current consecutive failure count, and have the `/` handler return a non-200 status (or a `/readyz`-style richer response) once failures exceed a staleness/failure threshold, mirroring the report's recommendation to surface real `updatedAt`-equivalent state instead of a hardcoded/one-shot value.

### Proof of Concept
1. Start `git-sync` with `--max-failures=-1 --http-bind=:1234 --repo=<repo>`.
2. Let the initial sync succeed once; confirm `curl localhost:1234` returns `200`.
3. Make the remote repo unreachable/broken (simulate attacker-controlled content that breaks fetch/checkout, or just block network to the remote).
4. Observe `git.SyncRepo` failing repeatedly in the loop at [6](#0-5)  — `failCount` increments but `maxFails=-1` never triggers `os.Exit`.
5. `curl localhost:1234` continues to return `200` indefinitely because `repoReady` was set once and is never reset, even though the synced content under `--link` is now arbitrarily stale.

```go
// repoReady indicates that the repo has been synced.
var readyLock sync.Mutex
var repoReady = false

func getRepoReady() bool {
	readyLock.Lock()
	defer readyLock.Unlock()
	return repoReady
}

func setRepoReady() {
	readyLock.Lock()
	defer readyLock.Unlock()
	repoReady = true
}
```
