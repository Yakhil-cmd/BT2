### Title
CCMenu API client created without stack scope grants cross-stack read access to deploy/build status - ([File: app/controllers/shipit/ccmenu_url_controller.rb])

### Summary
`CCMenuUrlController#fetch` mints a reusable `ApiClient` with the blanket `read:stack` permission but never binds it to the specific `Stack` the URL is generated for. The `Api::CCMenuController` then authorizes requests solely by checking that `read:stack` is present in the token's permission list, never checking that the token's `stack.id` matches the requested `stack_id`. This breaks the intended binding "stack a token authorizes" == "stack a token touches," letting a CCMenu token minted for one stack read the build/deploy status of *any* stack in the installation.

### Finding Description
The normal API authorization flow scopes a token to a single stack via the `ApiClient#stack` association, and `Api::BaseController#stacks`/`#stack` enforce that scope: [1](#0-0) 

`ApiClient#check_permissions!` only checks that the operation/scope string (e.g. `"read:stack"`) is present in the serialized `permissions` array — it never consults `stack_id`: [2](#0-1) 

`CCMenuUrlController#fetch`, reachable by any authenticated Shipit UI user for any stack they can view, creates the CCMenu `ApiClient` scoped only by `creator` and `name`, **not** by `stack`: [3](#0-2) 

`Api::CCMenuController` then overrides the inherited scoped `stack` accessor with an unscoped lookup driven entirely by the request parameter, and authorizes solely on the generic permission check (`require_permission :read, :stack`) inherited from `BaseController`: [4](#0-3) 

Because the token carries no `stack_id`, `current_api_client.stack_id?` is false, and `stacks` falls back to `Stack.all` — but this is moot anyway because `CCMenuController#stack` bypasses `stacks` entirely and does `Stack.from_param!(params[:stack_id])` directly. As a result, a "CCMenu URL" minted for Stack A's build-status widget (a link designed to be embedded/shared with third-party status-monitor tools, i.e. treated as a low-trust, single-project credential) is in fact valid to query the build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `activity`, `webUrl`) of **any** stack in the Shipit instance simply by changing the `stack_id` query parameter, regardless of which stack the token was originally generated for.

The mismatch mirrors the Gearbox report's root cause: a check is performed (`read:stack` permission present) but the value it is supposed to gate — which specific stack — is never re-verified against the actual object being acted upon (`Stack.from_param!(params[:stack_id])`), so the boundary intended by the token's creation (single-stack CCMenu widget) silently does not hold.

### Impact Explanation
This yields unauthenticated (holder of a shared/leaked CCMenu URL, which is explicitly meant to be embedded in third-party desktop CI-status apps) read of stack state and deploy output for stacks the token was never meant to expose — matching the in-scope High-impact category "unauthenticated read of stack state, task streams or deploy output." In multi-team/multi-repository Shipit deployments this discloses deploy status/labels/timing of unrelated, potentially confidential stacks to anyone who obtains a single CCMenu link.

### Likelihood Explanation
Any authenticated Shipit user can generate a CCMenu URL for any stack they have UI access to. Because the resulting token is a bare bearer token embedded in a URL query string (`?token=...`) designed for third-party polling tools, it is commonly shared, bookmarked, or embedded in less-trusted environments (CI dashboards, status-bar apps). Exploitation requires no privilege beyond having previously generated (or intercepted) any single CCMenu link — just changing the `stack_id` parameter reveals other stacks' data.

### Recommendation
- Persist the target `Stack` on the `ApiClient` created in `CCMenuUrlController#fetch` (`ApiClient.create_with(permissions: %w[read:stack], stack:)`), scoping one token per stack rather than sharing one client per user across all stacks.
- Remove the `stack` override in `Api::CCMenuController` and rely on the inherited, scoped `Api::BaseController#stack`/`#stacks` methods so requests are constrained to `current_api_client.stack_id` when present.
- Add a regression test asserting that a CCMenu token generated for Stack A returns 403/404 when queried with a different `stack_id`.

### Proof of Concept
1. As an authenticated Shipit user, call `GET /stacks/:stack_a_id/ccmenu_url` (via `CCMenuUrlController#fetch`) to obtain a CCMenu URL for Stack A, e.g. `.../api/stacks/A/ccmenu.xml?token=T`.
2. Share/leak this URL (as intended by the CCMenu feature) to a third party or a public status-monitor tool.
3. That third party requests `.../api/stacks/B/ccmenu.xml?token=T`, substituting an arbitrary other stack `B`'s id/slug.
4. `Api::CCMenuController#authenticate_api_client` accepts token `T` (`ApiClient.authenticate(params[:token])` succeeds), `require_permission :read, :stack` passes because `T` has `read:stack` in its permissions list, and `stack` resolves to `Stack.from_param!("B")` — unrelated to `T`'s intended scope — returning Stack B's build/deploy status in the XML response.

# frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
  end
end
