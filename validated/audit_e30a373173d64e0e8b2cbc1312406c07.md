Found a concrete analog. The `StatusHandler` and `CheckSuiteHandler` webhook handlers resolve target commits/stacks purely by `sha` (and for `CheckSuiteHandler`, by `branch` name too), with no scoping to the repository whose owner's webhook secret produced a valid HMAC signature.

### Title
Cross-repository commit-status/check-run writes via SHA-only matching in webhook handlers, unscoped from the signature-verified repository - ([File: app/models/shipit/webhooks/handlers/status_handler.rb], [File: app/models/shipit/webhooks/handlers/check_suite_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates a webhook against the `GitHubApp` selected by `repository_owner` (`params.dig('repository','owner','login')`), i.e. it binds trust to "the organization/repository that signed this payload." [1](#0-0) [2](#0-1)  But `StatusHandler#process` and `CheckSuiteHandler#process` never re-check that binding when deciding which `Commit`/`Stack` rows to mutate — they match purely on `sha` (and branch name for check suites) across the entire `Commit`/`Stack` tables, not scoped to `Repository.from_github_repo_name(repository_name)` the way `PushHandler` does via `Handler#stacks`. [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) 

### Finding Description
The binding that should hold is: `repository verified by webhook signature == repository whose Commit/Stack rows are mutated`. `verify_webhook_signature` in `lib/shipit/github_app.rb` only proves that the raw payload bytes were signed with the secret belonging to `repository_owner`'s GitHub App/organization. [7](#0-6)  The signature does not scope which `Commit` rows may be updated — that scoping decision is made independently inside each handler.

`StatusHandler#process` looks up `Commit.where(sha: params.sha)` with no repository filter at all, then calls `commit.create_status_from_github!(params)` on every matching commit, regardless of which stack/repository owns it. [3](#0-2) 

`CheckSuiteHandler#process` is scoped only by `stacks.where(branch: params.check_suite.head_branch)` and then further by `sha`, but `stacks` here is `Handler#stacks`, which is derived from `repository_name = payload.dig('repository', 'full_name')` — a payload field that is itself covered by the signature, so this handler is actually correctly scoped. [4](#0-3) [6](#0-5) 

The real gap is `StatusHandler`, which does not call `stacks` or use `repository_name` at all — it is the only handler among push/check_suite/status that skips repository scoping entirely, despite `Commit` SHAs not being globally unique across repositories (two unrelated repos can share the same commit SHA by coincidence, or via a fork/rebase). Since verification only proves "this org/repo owner signed this specific payload," and `StatusHandler` acts on `sha` matches system-wide, an organization `OrgA` that is a legitimate, verified webhook sender (i.e., has a real Shipit-configured GitHub App/webhook secret for its own repository) can send a `status` webhook event whose `sha` value collides with a commit tracked under a *different*, unrelated `OrgB` repository/stack, and have that commit's CI status mutated — an operation OrgA's signature never authorized for OrgB's repository.

### Impact Explanation
Commit statuses (`create_status_from_github!`) are consumed by Shipit to compute mergeability/deployability (`Commit#state`, review gating), so an attacker who controls one legitimately configured, signature-verified repository/organization in a multi-tenant Shipit deployment (see `test/dummy/config/secrets_double_github_app.yml`, which documents multiple orgs sharing one Shipit instance) can inject fabricated "success"/"failure" statuses onto commits belonging to a different tenant's stack whenever a SHA collision (accidental, or engineered via a crafted commit with attacker-chosen tree/message to brute a 40-hex prefix, or more practically an intra-organization repo with a shared history/fork) exists. This crosses the "organization that authenticated versus the repository that is written" boundary and can influence which commit becomes eligible to ship — an unauthorized state change on a repository the sender was never verified against.

### Likelihood Explanation
Exploitation requires: (1) control of at least one repository/organization already configured with a valid Shipit webhook secret (a legitimate but unprivileged-relative-to-the-victim-repo tenant), and (2) a `sha` value that also exists as a `Commit` row for the victim's stack — realistically forks, mirrors, or shared upstream branches across differently-owned repositories tracked by the same Shipit instance, which is a documented supported deployment mode (multiple GitHub Apps/orgs in one instance).

### Recommendation
Scope `StatusHandler#process` to `stacks` (i.e., `Repository.from_github_repo_name(repository_name)`) exactly as `PushHandler` and `CheckSuiteHandler` do, before filtering by `sha`, so that a status update can never be applied to a commit outside the repository whose signature was actually verified.

### Proof of Concept
1. Configure Shipit with two organizations/GitHub Apps, `OrgA` and `OrgB`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. `OrgB` has a stack tracking a commit with `sha = X` (e.g., inherited from a shared upstream/fork with `OrgA`).
3. Attacker, who legitimately controls `OrgA`'s repository and can trigger real GitHub webhooks for it (e.g., by pushing a status via the GitHub API on their own repo, or by any process producing a validly HMAC-signed `status` event for `OrgA`), causes GitHub to deliver a `status` webhook whose payload has `repository.owner.login = OrgA` (correctly signed with `OrgA`'s secret) but `sha = X`.
4. `WebhooksController#verify_signature` verifies the payload against `OrgA`'s webhook secret and succeeds. [8](#0-7) 
5. `StatusHandler#process` runs `Commit.where(sha: X)`, matches the `OrgB` commit, and calls `create_status_from_github!` on it — updating `OrgB`'s commit status using a payload that was only ever authorized/signed for `OrgA`. [3](#0-2)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
