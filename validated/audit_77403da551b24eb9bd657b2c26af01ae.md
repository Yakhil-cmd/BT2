### Title
`DeploySpec::FileSystem#build_config` follows an unsanitized `inherit_from` path outside the checkout, allowing arbitrary local file read merged into the executed deploy spec - (File: `app/models/shipit/deploy_spec/file_system.rb`)

### Summary
`DeploySpec::FileSystem#build_config` resolves `inherit_from` via `path.dirname.join(config_obj.delete(SHIPIT_CONFIG_INHERIT_FROM_KEY))` with no containment check against the checkout root, and recurses. An attacker who controls a `shipit.yml` in a checked-out commit (e.g., an `EphemeralCommitChecks`/review-stack build of a fork PR's head sha) can set `inherit_from` to an absolute path or a `../`-traversal string to read and deep-merge arbitrary host files into the effective deploy spec.

### Finding Description
The broken binding: "the file `shipit.yml` an authorized party approved/owns == the file bytes deep-merged into the effective `deploy_spec`" is violated because `build_config` in `app/models/shipit/deploy_spec/file_system.rb:149-160` computes:

```ruby
inherits_from_path = path.dirname.join(config_obj.delete(SHIPIT_CONFIG_INHERIT_FROM_KEY))
if inherits_from_path.exist?
  inherits_config_obj = read_config(inherits_from_path)
  config_obj = inherits_config_obj.deep_merge(config_obj)
  ...
``` [1](#0-0) 

There is no `realpath`/prefix check that `inherits_from_path` remains inside `@app_dir`. Ruby's `Pathname#join` semantics mean: (a) a relative value containing `..` segments is not blocked and is resolved by the OS when `.exist?`/`.read` are called, and (b) an absolute-path argument to `Pathname#join` discards the receiver entirely (`Pathname.new('/checkout').join('/etc/passwd') == Pathname.new('/etc/passwd')`). So `inherit_from: /etc/passwd` or `inherit_from: ../../../../etc/passwd` bypasses the checkout directory boundary. The resulting file's parsed YAML is deep-merged into `config_obj`, which becomes `config`, which feeds `machine_env`, `dependencies_steps`, `review_checks`, `deploy_steps`, etc. via `cacheable_config` [2](#0-1) .

Reachable path: `EphemeralCommitChecks#run` checks out an untrusted commit into a temporary working directory and instantiates `DeploySpec::FileSystem.new(directory, stack)` directly from that untrusted tree, then executes `deploy_spec.dependencies_steps` and `deploy_spec.review_checks` as shell `Command`s [3](#0-2) . Similarly, `TaskCommands#deploy_spec` builds `DeploySpec::FileSystem.new(@task.working_directory, @stack)` from the checked-out commit and its `env` method merges `deploy_spec.machine_env` into the environment ultimately passed to `Command#start`'s `PTY.spawn` [4](#0-3) .

No existing guard (webhook signature verification, `ExplicitParameters`, `User#authorized?`, model validations) constrains the *contents* of a checked-out `shipit.yml`/`inherit_from` value — those guards protect API/webhook authenticity, not file-path safety inside the repository checkout. The test suite (`test/models/shipit/deploy_spec/file_system_test.rb`) exercises `inherit_from` for the happy path and the "missing file" path, but never asserts that the resolved path is confined to the checkout directory (`assert loaded_config["deploy"]["override"].include?("test 11")` etc.) [5](#0-4) .

### Impact Explanation
An attacker who can get a commit checked out by Shipit (fork PR triggering merge-queue/ephemeral commit checks, or any commit reachable by a review stack) can cause the Shipit host process to read arbitrary local files readable by the Shipit worker user (e.g., `/etc/passwd`, credentials files mounted on the host, other checked-out repos' files) and have their parsed YAML content deep-merged into the deploy spec. Depending on the target file's content/parseability as YAML, this can inject or overwrite `machine.environment`, `dependencies`, `review.checks`, or `deploy`/`rollback` command arrays that are subsequently executed as shell commands via `Command#start` → `PTY.spawn`, i.e., local file disclosure escalating to influence over commands executed in the deploy/review environment. This matches the Critical category (arbitrary local file read feeding command construction / environment reaching `PTY.spawn`).

### Likelihood Explanation
Preconditions: the attacker only needs to open a PR from a fork with a crafted `shipit.yml`/`shipit.<env>.yml` containing `inherit_from: /absolute/path` or a `../` traversal string, and have Shipit run ephemeral commit checks or provision a review stack against that commit (both are triggered by ordinary, unprivileged PR activity per the repository's configured merge-queue/review-stack features). No secrets, tokens, or team membership are required — this is directly reachable by "any GitHub user who can open a pull request." The main variable is whether the target Shipit deployment has review stacks or merge-queue-triggered ephemeral checks enabled and whether the traversal reaches a file useful to the attacker, but the code-level flaw (missing path containment) is present and reachable regardless.

### Recommendation
In `build_config`, resolve `inherits_from_path` via `path.dirname.join(...).cleanpath` (or `.realpath`, guarded against non-existence) and verify it is still a descendant of `@app_dir` (e.g., `inherits_from_path.to_s.start_with?(@app_dir.realpath.to_s + File::SEPARATOR)`) before calling `.exist?`/reading it; reject and treat as "not found" otherwise. Apply the same containment check to `config_file_path`/`file` if any other input can influence the base filename.

### Proof of Concept
Add to `test/models/shipit/deploy_spec/file_system_test.rb`:
```ruby
test '#load_config refuses inherit_from paths that escape the checkout directory' do
  Shipit.expects(:respect_bare_shipit_file?).returns(true).at_least_once
  stack = shipit_stacks(:shipit)
  Dir.mktmpdir do |checkout_dir|
    Dir.mktmpdir do |outside_dir|
      secret_path = File.join(outside_dir, 'evil.yml')
      File.write(secret_path, { 'deploy' => { 'override' => ['cat /etc/shadow'] } }.to_yaml)

      shipit_yml = File.join(checkout_dir, 'shipit.yml')
      File.write(shipit_yml, { 'inherit_from' => secret_path }.to_yaml) # absolute path traversal

      deploy_spec = Shipit::DeploySpec::FileSystem.new(checkout_dir, stack)
      loaded_config = deploy_spec.send(:load_config)

      # Binding under test: bytes merged into deploy_spec must come only from files under checkout_dir
      refute loaded_config.dig('deploy', 'override')&.include?('cat /etc/shadow'),
        "inherit_from escaped the checkout directory and merged external file content"
    end
  end
end
```
This constructs a `shipit.yml` inside a fresh checkout directory whose `inherit_from` points to a file outside that directory (simulating the fork-controlled file), and asserts the loader does not merge that external file's content into the effective config — currently this assertion fails, demonstrating the vulnerability.

      SHIPIT_CONFIG_INHERIT_FROM_KEY = "inherit_from"
      def build_config(path, config_obj)
        return config_obj if config_obj.blank? || !config_obj.key?(SHIPIT_CONFIG_INHERIT_FROM_KEY)

        inherits_from_path = path.dirname.join(config_obj.delete(SHIPIT_CONFIG_INHERIT_FROM_KEY))
        if inherits_from_path.exist?
          inherits_config_obj = read_config(inherits_from_path)
          config_obj = inherits_config_obj.deep_merge(config_obj)
          path = inherits_from_path
        end

        build_config(path, config_obj)
      end
