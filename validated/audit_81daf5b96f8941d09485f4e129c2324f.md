Based on my investigation, I found a concrete binding mismatch in the webhook signature verification path that matches the required class ("an organization that authenticated versus the repository that is written").

### Title
Webhook signature is verified against `repository.owner.login`/`organization.login` while handlers act on the unrelated `repository.full_name` field, allowing a valid signer for one GitHub organization to forge events for stacks belonging to a different organization - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate against using `repository.owner.login` (falling back to `organization.login`), but every event handler (`PushHandler`, the `PullRequest::*` handlers, `Handler#stacks`) resolves the target repository/stack using the separate `repository.full_name` field, never checking it is consistent with the org used for signature verification.

### Finding Description
`verify_signature` computes the trust anchor as: [1](#0-0) 
It then fetches the GitHub App config/secret for that org and HMAC-verifies the raw body against it: [2](#0-1) 

Shipit supports multiple independently-configured GitHub organizations in `secrets.github`, each with its own `webhook_secret` set by that organization's own admin: [3](#0-2) 

Once the signature check passes, `WebhooksController#create` dispatches the entire raw payload to handlers unmodified: [4](#0-3) 

Every handler, however, determines which repository/stack to mutate using a **different** field of the same payload, `repository.full_name`, with no cross-check against `repository.owner.login`: [5](#0-4) [6](#0-5) [7](#0-6) 

Because the whole request body is attacker-controlled JSON (not derived server-side from the signature), an org admin who legitimately knows their **own** org's `webhook_secret` (they configured/installed the GitHub App themselves) can:
1. Set `repository.owner.login` (or `organization.login`) to their own org, so `Shipit.github(organization: repository_owner)` picks their own app config, and compute a valid HMAC over the whole crafted body with their own known secret.
2. Independently set `repository.full_name` to `"victim-org/some-repo"`, which is what the handlers actually use to look up the `Repository`/`Stack` (`Repository.from_github_repo_name`) and to act (sync, archive/unarchive review stacks, apply labels, create commit statuses, etc.).

The equality that should hold but doesn't: **binding used to verify the signature** (`repository.owner.login` / `organization.login`) **≠ binding used to select the mutated resource** (`repository.full_name`). In legitimate GitHub-originated payloads these two are always consistent, but nothing in this engine enforces that invariant on the untrusted payload it receives, so a same-body, cross-field attack is possible for anyone who is a trusted signer for at least one configured organization.

### Impact Explanation
An attacker who administers (or has been granted) one organization's GitHub App/webhook config in a multi-org Shipit deployment can issue authenticated-looking webhook calls that trigger actions against stacks/repositories belonging to a completely different, victim organization they do not control: forcing `GithubSyncJob`/`stack.sync_github` on arbitrary victim stacks with attacker-chosen `expected_head_sha`, creating/archiving/unarchiving `ReviewStack`s, injecting `Status` records affecting deployability/merge decisions on victim commits (`StatusHandler`), and mutating pull-request metadata on repos they don't own. This crosses a repository/organization boundary that the signature was supposed to enforce, which corresponds to unauthorized cross-repository writes / triggering unauthorized deploy-adjacent state changes.

### Likelihood Explanation
Requires the attacker to be a legitimate webhook signer for at least one org configured in the Shipit deployment (i.e., control of that org's GitHub App/webhook secret) - a realistic scenario in the intended multi-tenant deployment model where several independent organizations share one Shipit instance, each managing its own GitHub App installation and secret. No access to the victim org's credentials, no Shipit session, and no `ApiClient` token are required.

### Recommendation
After signature verification, re-derive the organization from the exact same field used for the repository/stack lookup (`repository.full_name`'s owner segment) and assert it equals the `repository_owner`/`organization.login` value that selected the verifying secret, rejecting the request if they diverge. Alternatively, bind verification to the specific `Repository` record's configured organization rather than a raw payload field.

### Proof of Concept
1. Deploy Shipit configured with two orgs, `org-a` and `org-b`, each with a distinct GitHub App and `webhook_secret` (as in `secrets.development.shopify.yml`).
2. Attacker administers `org-a`'s GitHub App and therefore knows `org-a`'s `webhook_secret`.
3. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "attacker-chosen-sha",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/victim-repo"
  }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<hmac(org-a's webhook_secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `"org-a"`, fetches `org-a`'s app/secret, and the signature verifies successfully.
6. `PushHandler#process` resolves the target repo via `payload.dig('repository','full_name')` = `"org-b/victim-repo"` and calls `stack.sync_github(expected_head_sha: "attacker-chosen-sha")` on `org-b`'s stack, even though the signature only proves control over `org-a`.
