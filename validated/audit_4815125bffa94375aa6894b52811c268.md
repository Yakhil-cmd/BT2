Based on my investigation, I found a strong analog to the reported bug class in the webhook signature verification logic.

### Title
Cross-organization webhook forgery via attacker-controlled `repository_owner` used to select the verification key - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The Sherlock finding shows an attacker controlling an unverified input (`msg.value`/contract token balance) that is fed into a calculation (`convertToShares`) whose correctness the protocol relies on for authorization of minted shares. The shipit-engine analog is `WebhooksController#verify_signature`, where the *organization used to select the HMAC verification secret* is itself taken from the same untrusted, unverified JSON body that the signature is supposed to protect.

### Finding Description
`WebhooksController#verify_signature` computes `repository_owner` from the raw request body and uses it to pick which GitHub App/organization config (and thus which `webhook_secret`) to verify the signature against: [1](#0-0) [2](#0-1) 

`repository_owner` is derived purely from `params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')` — fields inside the attacker-supplied payload, not covered or fixed by any prior authentication. This value determines `Shipit.github(organization: repository_owner)`, i.e. which organization's `webhook_secret` is used as the HMAC key in `verify_webhook_signature`: [3](#0-2) 

Critically, `verify_webhook_signature` **unconditionally returns `true` when the selected organization's `webhook_secret` is blank/unset** (`return true unless webhook_secret`). The engine explicitly supports multi-organization configuration where each org can have its own (optional) `webhook_secret`: [4](#0-3) [5](#0-4) 

This mirrors the reported bug: the field that determines the *key/parameters used in the security calculation* (here: which secret validates the signature) is drawn from the very payload being validated, without itself being cryptographically bound to anything. If any configured organization lacks a `webhook_secret` (which the shipping example configs explicitly show as a valid/nil default — `test/dummy/config/secrets_double_github_app.yml`, `config/secrets.development.example.yml`), an attacker can craft a payload whose `repository.owner.login`/`organization.login` names that secret-less organization to force `verify_webhook_signature` to short-circuit to `true`, while the payload's `repository.full_name`, branches, statuses, etc. can reference **any other stack/repository** tracked by the Shipit instance — because `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` processes the full body without re-checking that the organization actually matches the repository the handler acts on: [6](#0-5) 

### Impact Explanation
This breaks the binding "organization that authenticated versus the repository that is written": signature verification is scoped to organization A (selected from the untrusted payload, possibly configured without a secret), but the handlers act on whatever repository/branch/commit fields are present in the same payload, which can belong to organization B (a properly-secured, victim organization/stack). Depending on handler (e.g. `push_handler.rb` triggering `GithubSyncJob`, status handlers creating commit statuses, membership handlers creating/removing team memberships), this can lead to unauthorized state changes on stacks the attacker does not control — matching the High-severity impact criteria ("escalation into `Shipit.github_teams` authorization" via forged `membership` events, or unauthenticated manipulation of stack/task state via forged `push`/`status` events).

### Likelihood Explanation
Requires the deployment to be configured with multiple GitHub organizations where at least one has no `webhook_secret` set — this is an explicitly documented and shipped default configuration pattern (all example/dummy configs in this repo show `webhook_secret: # nil` as acceptable), not a misconfiguration outside the engine's own documented usage. No credentials, tokens, or prior access are required — this is reachable by any unauthenticated internet client hitting the public webhooks endpoint.

### Recommendation
Do not select the verification secret using data taken from the unverified request body. Either: (1) require a `webhook_secret` for every configured organization and refuse verification (fail closed) rather than defaulting to `true` when absent, and/or (2) verify the payload's signature against all configured organizations' secrets (or a single global secret) and only then trust the payload's self-reported `repository`/`organization` fields, and (3) after verification, assert that the repository referenced in the payload actually belongs to the organization whose secret validated the signature before dispatching to handlers.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.yml`: `OrgA` (no `webhook_secret` set) and `OrgB` (a real stack, `webhook_secret` set and properly protected).
2. Attacker sends `POST /github/webhooks` with header `X-Github-Event: push` and a JSON body where `repository.owner.login = "OrgA"` but `repository.full_name`/`ref`/`after` reference a stack under `OrgB`, with an arbitrary/garbage `X-Hub-Signature`.
3. `verify_signature` calls `Shipit.github(organization: "OrgA")`, whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` regardless of the (invalid) signature.
4. `create` re-parses the same body and dispatches it to `Shipit::Webhooks.for_event('push')`, which processes the forged `OrgB` repository data (`push_handler.rb`), triggering `sync_github`/`GithubSyncJob` for `OrgB`'s stack without the request ever being validated by `OrgB`'s actual secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.
