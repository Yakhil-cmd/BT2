### Title
Peer's permanent pairing secret is disclosed to unrelated wallet cosigners via `arbiter_contract_shared` - (File: arbiter_contract.js)

### Summary
When an arbiter contract is offered, the offeror's permanent device-pairing code (`device_pubkey@hub#pairing_secret`) is embedded in the contract object and sent to the peer. Once the peer accepts, the full contract record — including the offeror's `peer_pairing_code` (their own permanent pairing secret) — is forwarded verbatim to every cosigner of the peer's `my_address` wallet via `arbiter_contract_shared`, even though those cosigners are not parties to the peer relationship and have no legitimate need for that credential.

### Finding Description
In `createAndSend`, the offeror's permanent pairing info is generated and attached to the outgoing contract without being stripped before sending to the peer: [1](#0-0) 

Only `cosigners` is deleted from the copy sent to the peer — `my_pairing_code` (the offeror's permanent pairing secret) is left in the payload that reaches the peer's device: [2](#0-1) 

On the peer side, this value is persisted as `peer_pairing_code`, and when the peer accepts the contract, `respond()` calls `shareContractToCosigners(hash)`: [3](#0-2) 

`shareContractToCosigners` fetches the full contract row (via `getByHash`, which does not redact `my_pairing_code`/`peer_pairing_code`) and sends it as-is to **every** cosigning device on the peer's own wallet address (`getAllMyCosigners`), not just to the direct counterparty: [4](#0-3) [5](#0-4) 

A "permanent" pairing secret is long-lived by design (valid until 2038, reusable by multiple correspondents), as shown by `getOrGeneratePermanentPairingInfo`/`startWaitingForPairing`: [6](#0-5) 

Anyone possessing `device_pubkey@hub#pairing_secret` can pair with the offeror's device as a trusted correspondent — pairing itself is explicitly allowed even from unknown correspondents (`arrSubjectsAllowedFromNoncorrespondents` includes `"pairing"`): [7](#0-6) [8](#0-7) 

This is the structural analog of BIT-gitlab-2020-13264: a sensitive access credential intended only for a specific counterparty ("group maintainer" analog = the peer) leaks to other members of a related trust group (the peer's own wallet cosigners) who were never authorized to hold it, purely because the sharing logic broadcasts the entire contract record without redacting party-specific secrets.

### Impact Explanation
Once a cosigner of the peer's wallet obtains the offeror's permanent pairing secret, that cosigner can independently pair with the offeror's device (pairing from unknown correspondents is explicitly permitted) and thereafter act as a trusted correspondent. From this trusted position they can attempt to be added to shared/multisig wallets, receive forwarded private-payment chains (see `forwardPrivateChainsToOtherMembersOfSharedAddresses`/`OfWallets` in `wallet.js`), or socially engineer the offeror into signing malicious shared-address definitions or payments — creating a path toward AA/fund loss or unauthorized spending against the offeror's addresses. This is a medium-severity confidentiality/authorization break that expands the offeror's trust boundary to an unintended, unbounded set of devices (all present and future cosigners of the peer's wallet).

### Likelihood Explanation
No attacker-controlled input or malicious node is required — this fires automatically for every accepted arbiter contract as soon as the peer's wallet has one or more cosigners (i.e., peer uses a shared/multisig wallet), which is a normal, commonly supported ocore wallet configuration. The disclosure is deterministic and requires no race condition or unusual timing.

### Recommendation
Strip `my_pairing_code`/`peer_pairing_code` (and other party-specific secrets not needed by cosigners) from the contract object before calling `shareContractToCosigners`/`shareUpdateToCosigners`, mirroring the existing `delete objContractForPeer.cosigners` pattern used when sending to the peer. Cosigners only need enough contract data to display/approve signing requests, not the counterparty's permanent pairing credential.

### Proof of Concept
1. Alice creates an arbiter contract offer to Bob: `createAndSend` attaches Alice's permanent pairing code (`my_pairing_code`) to the contract and sends it to Bob (`arbiter_contract_offer`), per [9](#0-8) .
2. Bob's wallet stores Alice's pairing code as `peer_pairing_code` on the contract record.
3. Bob's wallet is a multisig wallet with cosigner Carol. Bob accepts the contract: `respond(hash, "accepted", ...)` is invoked, which calls `shareContractToCosigners(hash)` after updating status, per [10](#0-9) .
4. `shareContractToCosigners` sends the full `objContract` (including `peer_pairing_code` = Alice's permanent pairing secret) to Carol via `device.sendMessageToDevice(..., "arbiter_contract_shared", objContract)`, per [4](#0-3) .
5. Carol, who was never a party to the Alice-Bob agreement, now holds Alice's permanent pairing secret and can pair with Alice's device directly, impersonating a legitimate correspondent.

Note: I was unable to fully trace the client-side handler for the `arbiter_contract_shared` message (likely in a GUI wallet layer outside `ocore`), so I could not confirm whether any UI-level redaction happens after receipt; based on the `ocore` core library code reviewed, no redaction occurs before the message is sent.

function respond(hash, status, signedMessageBase64, signer, cb) {
	cb = cb || function(){};
	getByHash(hash, function(objContract){
		if (objContract.status !== "pending" && objContract.status !== "accepted")
			return cb("contract is in non-applicable status");
		var send = function(authors, pairing_code) {
			var response = {hash: objContract.hash, status: status, signed_message: signedMessageBase64, my_contact_info: objContract.my_contact_info};
			if (authors) {
				response.authors = authors;
			}
			if (pairing_code) {
				response.my_pairing_code = pairing_code;
			}
			device.sendMessageToDevice(objContract.peer_device_address, "arbiter_contract_response", response);

			setField(objContract.hash, "status", status, function(objContract) {
				if (status === "accepted") {
					shareContractToCosigners(objContract.hash);
				};
				cb(null, objContract);
			});
		};
		if (status === "accepted") {
			device.getOrGeneratePermanentPairingInfo(function(pairingInfo){
				var pairing_code = pairingInfo.device_pubkey + "@" + pairingInfo.hub + "#" + pairingInfo.pairing_secret;
				setField(objContract.hash, "my_pairing_code", pairing_code);
				composer.composeAuthorsAndMciForAddresses(db, [objContract.my_address], signer, function(err, authors) {
					if (err) {
						return cb(err);
					}
					send(authors, pairing_code);
				});
			});
		} else {
			send();
		}
	});
}

function getAllMyCosigners(hash, cb) {
	db.query("SELECT device_address FROM wallet_signing_paths \n\
		JOIN my_addresses AS ma USING(wallet)\n\
		JOIN wallet_arbiter_contracts AS wac ON wac.my_address=ma.address\n\
		WHERE wac.hash=?", [hash], function(rows) {
			var cosigners = [];
			rows.forEach(function(row) {
				if (row.device_address !== device.getMyDeviceAddress())
					cosigners.push(row.device_address);
			});
			cb(cosigners);
		});
}

// {pairing_secret: "random string", device_name: "Bob's MacBook Pro", reverse_pairing_secret: "random string"}
function handlePairingMessage(json, device_pubkey, callbacks){
	var body = json.body;
	var from_address = objectHash.getDeviceAddress(device_pubkey);
	if (!ValidationUtils.isNonemptyString(body.pairing_secret))
		return callbacks.ifError("correspondent not known and no pairing secret");
	if (!ValidationUtils.isNonemptyString(json.device_hub)) // home hub of the sender
		return callbacks.ifError("no device_hub when pairing");
	if (json.device_hub.length > 200)
		return callbacks.ifError("device_hub too long");
	if (!network.isValidWsUrl(conf.WS_PROTOCOL + json.device_hub))
		return callbacks.ifError("invalid device_hub URL");
	if (!ValidationUtils.isNonemptyString(body.device_name))
		return callbacks.ifError("no device_name when pairing");
	if (body.device_name.length > 100)
		return callbacks.ifError("device_name too long");
	if ("reverse_pairing_secret" in body && !ValidationUtils.isNonemptyString(body.reverse_pairing_secret))
		return callbacks.ifError("bad reverse pairing secret");
	eventBus.emit("pairing_attempt", from_address, body.pairing_secret);
	db.query(
		"SELECT is_permanent FROM pairing_secrets WHERE pairing_secret IN(?,'*') AND expiry_date>"+db.getNow()+" ORDER BY (pairing_secret=?) DESC LIMIT 1", 
		[body.pairing_secret, body.pairing_secret], 
		function(pairing_rows){
			if (pairing_rows.length === 0)
				return callbacks.ifError("pairing secret not found or expired");
			// add new correspondent and delete pending pairing
			var safe_device_name = body.device_name.replace(/<[^>]*>?/g, '');
			db.query(
				"INSERT "+db.getIgnore()+" INTO correspondent_devices (device_address, pubkey, hub, name, is_confirmed) VALUES (?,?,?,?,1)", 
				[from_address, device_pubkey, json.device_hub, safe_device_name],
				function(){
					db.query( // don't update name if already confirmed
						"UPDATE correspondent_devices SET is_confirmed=1, name=? WHERE device_address=? AND is_confirmed=0", 
						[safe_device_name, from_address],
						function(){
							db.query("UPDATE correspondent_devices SET is_blackhole=0 WHERE device_address=?", [from_address], function(){
								eventBus.emit("paired", from_address, body.pairing_secret);
								if (pairing_rows[0].is_permanent === 0){ // multiple peers can pair through permanent secret
									db.query("DELETE FROM pairing_secrets WHERE pairing_secret=?", [body.pairing_secret], function(){});
									eventBus.emit('paired_by_secret-'+body.pairing_secret, from_address);
								}
								if (body.reverse_pairing_secret)
									sendPairingMessage(json.device_hub, device_pubkey, body.reverse_pairing_secret, null);
								callbacks.ifOk();
							});
						}
					);
				}
			);
		}
	);
}
