### Title
Accrual computes `borrowed * borrow_index` before the index cap, so a saturated RAY value panics every accrual and permanently freezes the market - (File: common/src/rates/simulate.rs)

### Summary
The advisory class is a crash (segfault in `FT_Request_Size`) reachable on attacker-influenced input, producing denial of service. The analog in XOXNO Lending is an arithmetic-overflow panic inside the interest-accrual step: `accrue_step` unscales the full debt (`scaled_to_original(borrowed, borrow_index)`) *before* `update_borrow_index` applies `MAX_BORROW_INDEX_RAY`, so once `borrowed * borrow_index` exceeds `i128::MAX` the accrual panics with `MathOverflow` and the index cap can never engage. Because every pool verb accrues first, the market is permanently frozen — no repay, withdraw, supply, or liquidation ever succeeds again.

### Finding Description
In `common/src/rates/simulate.rs`, `accrue_step` first computes `borrowed_original = scaled_to_original(env, borrowed, borrow_index)`, which performs `borrowed * borrow_index / RAY` via `Ray::mul` → `mul_div_half_up` → panic on `i128` overflow. Only afterwards does it call `update_borrow_index`, which would clamp the index at `MAX_BORROW_INDEX_RAY` (`common/src/rates/index.rs` `update_borrow_index` lines 13-19). The clamp therefore arrives too late: the panic fires while *reading* the current index, so stored state is never rewritten and every subsequent accrual hits the same cliff. The chunked loop in `simulate_update_indexes_body` (lines 158-175) and the pool's mutating `interest::global_sync` share this exact `accrue_step` implementation, so the panic is identical in read and write paths. The in-repo regression test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` in `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-360` demonstrates precisely this: at ~98% utilization on the XLM curve, `update_indexes`, `withdraw`, and `repay` all revert with `MathOverflow` while `borrow_index < MAX_BORROW_INDEX_RAY`.

### Impact Explanation
Permanent freezing of funds. Once the RAY-value product overflows, no transaction touching that market can complete, because accrual runs first in every entrypoint (`supply`, `borrow`, `withdraw`, `repay`, `liquidate`, `clean_bad_debt`, `claim_revenue`, `update_indexes`). All supplier cash and all collateral backing borrows in that market are locked forever; liquidation is also impossible, so the position set cannot be unwound or socialized. This is a direct analog of the report's crash→DoS class, with the DoS upgraded to a permanent freeze by the protocol's accrue-first design.

### Likelihood Explanation
An unprivileged attacker only needs to create the precondition: a very large deposit plus a borrow near maximum utilization on a high-decimals asset (e.g., 18 decimals, where realistic token supplies approach `i128::MAX / RAY_per_unit` scale). The required supply (~10^9 whole tokens at 18 decimals in the test) is large but within the supply domain the cap system permits — `calculate_scaled_cap` explicitly saturates rather than blocking the size (`common/src/rates/scaling.rs:26-33`). After that, ordinary passage of ledger time at high utilization grows `borrow_index` until `borrowed * borrow_index` overflows; the attacker (or anyone) then triggers the freeze via the permissionless `update_indexes`. No privilege, oracle manipulation, or governance action is required. Likelihood is moderate: it requires whale-scale capital and sustained high utilization, but the freeze is irreversible once reached.

### Recommendation
Order the cap before the value computation, or compute utilization on capped/saturating values:
- In `accrue_step`, apply `update_borrow_index` to a copy of `borrow_index` first and compute `borrowed_original` against `min(borrow_index, MAX_BORROW_INDEX_RAY)`, or
- use a saturating `scaled_to_original` for the utilization inputs so an over-ceiling product yields a saturated utilization (100%+) instead of panicking, letting the index clamp proceed and persist, or
- enforce `borrowed * MAX_BORROW_INDEX_RAY <= i128::MAX` at borrow/cap-validation time (`require_cap_within_asset_domain`) so the product can never overflow for any reachable debt.

### Proof of Concept
1. Attacker calls controller `supply` on an 18-decimal market with `principal ≈ 10^9 * 10^18` units (caps permit this scale), then `borrow` ~98% of it.
2. Ledger time advances; utilization stays near max and `borrow_index` compounds via the chunked `accrue_step` loop.
3. When `borrowed * borrow_index > i128::MAX`, `scaled_to_original` at `simulate.rs:60` panics with `GenericError::MathOverflow` before `update_borrow_index`'s `MAX_BORROW_INDEX_RAY` clamp (`index.rs:15-17`) can store a capped index.
4. Anyone calling `update_indexes` (permissionless) realizes the freeze; thereafter `repay`, `withdraw`, and `liquidate` all revert in the same accrual, as demonstrated by the existing test at `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:343-356`.

/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
