### Title
Team membership webhook trusts only `team.id` for lookup, allowing an attacker's own verified organization webhook to add members to another organization's `Team` row - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`MembershipHandler#find_or_create_team!` looks up a `Team` solely by `github_id: params.team.id` via `Team.find_or_create_by!`, and never compares the existing record's `organization` column against `params.organization.login`. If the attacker's own organization signs a membership webhook (which it legitimately can, since `verify_signature` is scoped per `repository_owner`/`organization.login` and the attacker owns that org's app secret), but sets `team.id` to a value that already belongs to a `Team` row for a *different* organization, `team.add_member(member)` mutates that other organization's team/membership records.

### Finding Description
The broken binding is: `team.organization == params.organization.login` for the `Team` record that `find_or_create_team!` returns. This is never asserted.

Code path:
- `Shipit::WebhooksController#verify_signature` selects `Shipit.github(organization: repository_owner)` and verifies the HMAC signature using that specific organization's `webhook_secret` [1](#0-0) . In a multi-org deployment (`docs/setup.md` "Using Multiple Github Applications"), each org has its own `webhook_secret`, so an attacker who legitimately owns/administers their own GitHub org and has installed the configured GitHub App there can generate a *validly signed* membership webhook for arbitrary payload content — because they know their own org's secret.
- `MembershipHandler#process` calls `find_or_create_team!`, then unconditionally `team.add_member(member)` for the `added` action [2](#0-1) .
- `find_or_create_team!` does `Team.find_or_create_by!(github_id: params.team.id) { |team| team.organization = params.organization.login }` [3](#0-2) . The block only runs when a **new** record is created. If a `Team` with that `github_id` already exists (created earlier by org A's legitimate membership webhook), the block is skipped, the existing row (with `organization == "orgA"`) is returned unchanged, and no comparison against the current payload's `params.organization.login` ("orgB") is performed.
- `team.add_member(member)` then appends the attacker-supplied/created `User` (from `User.find_or_create_by_login!(params.member.login)`, itself unauthenticated) to org A's `Team.members` — a cross-tenant `Membership` write triggered by org B's traffic.

Existing guards do not stop this: `verify_signature` only proves the payload came from the org whose secret matches, it says nothing about which `team.id` the org is allowed to reference; `ExplicitParameters` only validates types/presence, not cross-object ownership; there is no `require_permission!`/`Team.find_or_create_by!` scoping by `organization`.

### Impact Explanation
The attacker (controlling only their own GitHub organization) can cause an unauthorized write to another tenant's `Team`/`Membership` records — adding an arbitrary user (which they also control the identity string for) as a member of a team belonging to a different organization. Since `User#authorized?` checks `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [4](#0-3) , and `Shipit.github_teams` is configured from specific `Team` records, this can escalate an attacker-controlled `User` into `Shipit.github_teams` membership if the guessed `github_id` corresponds to one of those authorization-relevant teams — directly matching the "escalation into `Shipit.github_teams` authorization" impact category, and more broadly is a cross-tenant `Team`/`Membership` mutation. Repeatable against any `github_id` value the attacker can guess or observe.

### Likelihood Explanation
Requires: (1) a multi-organization Shipit deployment (or any deployment lacking a webhook_secret for the target scenario), (2) the attacker to own/administer a GitHub organization with the Shipit GitHub App installed (satisfies "attacker owns a repository/org they control", within scope), and (3) knowledge/guessing of a numeric `team.id` belonging to a different org's `Team` row — sequential/small IDs or GitHub's public team-listing API make this feasible for public teams. No Shipit secrets, sessions, or maintainer status are required beyond the attacker's own org's webhook secret, which they legitimately possess for their own org.

### Recommendation
In `find_or_create_team!`, scope the lookup by both `github_id` and `organization`, and reject (or re-parent only via an authorized reconciliation path) if a `Team` with that `github_id` already exists under a different `organization`:
```ruby
def find_or_create_team!
  team = Team.find_by(github_id: params.team.id)
  if team && team.organization != params.organization.login
    raise ArgumentError, "team #{params.team.id} does not belong to organization #{params.organization.login}"
  end
  Team.find_or_create_by!(github_id: params.team.id) do |t|
    t.github_team = params.team
    t.organization = params.organization.login
  end
end
```

### Proof of Concept
```ruby
test "membership webhook cannot mutate a team belonging to another organization" do
  team_a = Shipit::Team.create!(github_id: 999, organization: "org-a", name: "A", slug: "a", api_url: "https://x")

  request.headers['X-Github-Event'] = 'membership'
  # signature verified successfully for org-b (attacker's own org)
  GithubHook.any_instance.stubs(:verify_signature).returns(true)

  payload = {
    action: 'added',
    team: { id: 999, name: 'A', slug: 'a', url: 'https://x' },
    organization: { login: 'org-b' },
    member: { login: 'attacker-user' }
  }.to_json

  assert_no_difference -> { Shipit::Team.count } do
    post :create, body: payload, as: :json
  end

  team_a.reload
  assert_equal "org-a", team_a.organization
  refute team_a.members.exists?(login: 'attacker-user')
end
```
