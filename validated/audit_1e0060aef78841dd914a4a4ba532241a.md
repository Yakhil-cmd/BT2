## Analysis



### Title
Missing `return` after `getBase64Hash` exception causes double invocation of `async.each` completion callback in `handleSavedPrivatePayments` - (File: network.js)

### Summary
In `network.js`, the inner `validateAndSave` function used by `handleSavedPrivatePayments` computes a hash of an attacker/peer-controlled private-payment payload inside a `try/catch` block. When the hash computation throws, the `catch` branch calls `deleteHandledPrivateChain(..., cb)` — consuming the `async.each` iteratee callback `cb` — but does **not** `return`. Execution falls through to the subsequent code, which unconditionally calls `privatePayment.validateAndSavePrivatePaymentChain(...)`, whose `ifOk`/`ifError`/`ifWaitingForChain` callbacks each also eventually invoke `cb` (via `deleteHandledPrivateChain` or directly). This causes `cb` to be invoked twice for a single iteration, analogous to the kernel bug where a buffer is freed by a callee without preventing a second free by the caller.

### Finding Description
`handleSavedPrivatePayments` processes rows from `unhandled_private_payments`, a table populated from private-payment chains received from peers/paired devices (via `handleOnlinePrivatePayment` / `handlePrivatePaymentChains`), i.e. content controlled by an untrusted private-payment counterparty. [1](#0-0) 

Inside the per-row iteratee, `validateAndSave` computes `json_payload_hash` from `objHeadPrivateElement.payload` — a JSON-parsed, attacker-supplied structure — inside a `try` block: [2](#0-1) 

If `objectHash.getBase64Hash` throws (e.g., due to a malformed/unexpected value type in the peer-supplied payload, such as a non-integer number or invalid structure that the hashing routine rejects but that passed the earlier loose validation in `handleOnlinePrivatePayment`), the `catch` block calls `deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb)`, which itself will eventually invoke `cb`. Critically, there is no `return` statement after this call, so control flow continues past the `try/catch` to line 2478 and then into the call to `privatePayment.validateAndSavePrivatePaymentChain(...)` at line 2479, whose callbacks (`ifOk`, `ifError`, `ifWaitingForChain`) each also invoke `cb` a second time: [3](#0-2) 

This double invocation of the `async.each` iteratee callback is structurally the same class of bug as `nr_route_frame()`'s double-free: a helper path releases/consumes a shared resource (the `cb` completion token) without setting a guard/returning, so a second, unrelated code path also releases/consumes it.

### Impact Explanation
`async.each`'s internal completion tracking is corrupted when the same iteratee callback fires twice: the final callback of `handleSavedPrivatePayments` — which calls `unlock()` on the `"saved_private"` mutex and emits `"new_my_transactions"` — can fire prematurely relative to the true completion of all rows still in flight. [4](#0-3) 

A premature `unlock()` of the `"saved_private"` mutex allows a subsequent call to `handleSavedPrivatePayments` (e.g., triggered again by `handleOnlinePrivatePayment`/`rerequestLostJointsOfPrivatePayments`) to start processing the very same still-unprocessed or partially-processed rows concurrently, since the corresponding `unhandled_private_payments` row deletion via `deleteHandledPrivateChain` and the actual chain validation/save in `privatePayment.validateAndSavePrivatePaymentChain` (which performs DB writes such as marking outputs spent/received) are not atomically coupled to the callback bookkeeping. This creates a race window in which the same private payment chain can be concurrently re-validated/re-saved, risking duplicate crediting of a private output to the wallet or inconsistent internal accounting state for private assets — falling under "AA/wallet fund loss or freezing" / "node disagreement on validity" territory referenced in the rules, since private payment processing directly affects the local ledger's view of spendable private outputs.

### Likelihood Explanation
The trigger requires only that a private-payment counterparty (an unprivileged peer or paired device) send a private payment chain whose head element's `payload` causes `objectHash.getBase64Hash` to throw. The payload only needs to satisfy the loose structural checks performed earlier in `handleOnlinePrivatePayment`/`handlePrivatePaymentChains` (non-empty object/array checks) before reaching `validateAndSave`, so a moderately crafted payload (e.g., unsupported number formats) is sufficient. No special privileges, hub/node compromise, or network-level positioning is required — this is reachable purely from application-level messages sent by a private-payment counterparty.

### Recommendation
Add a `return` (or restructure with an `if/else`) after the `deleteHandledPrivateChain(...)` call inside the `catch` block of `validateAndSave` so that execution does not fall through to `privatePayment.validateAndSavePrivatePaymentChain(...)` when hash computation has already failed and already consumed `cb`:
```js
catch (e) {
    console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
    if (ws)
        sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
    return deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
}
```

### Proof of Concept
1. As a private-payment counterparty/paired device, send a `private_payment` chain (via `handlePrivatePaymentChains` → `network.handleOnlinePrivatePayment`) whose head element's `payload` passes the loose non-empty-object/array checks in `handleOnlinePrivatePayment` but contains a value that causes `objectHash.getBase64Hash` to throw (e.g., a malformed numeric field not accepted by the hashing/serialization routine).
2. The chain is queued into `unhandled_private_payments` and picked up by `handleSavedPrivatePayments`.
3. In `validateAndSave`, `getBase64Hash` throws; `deleteHandledPrivateChain(..., cb)` runs and will call `cb`, but execution falls through (no `return`) to `privatePayment.validateAndSavePrivatePaymentChain(...)`, which also eventually calls `cb` again for the same row.
4. `cb` is invoked twice for one `async.each` iteration, corrupting the completion tracking of `handleSavedPrivatePayments` and allowing the `"saved_private"` mutex to be released early while other rows are still being processed, opening a race window for duplicate processing of private payment chains.

**Note:** I was unable to inspect the exact throw conditions inside `objectHash.getBase64Hash` (its implementation was not returned by search), so the precise malformed-payload trigger for the exception is inferred rather than directly confirmed; a Devin session with full repo access would be needed to pinpoint an exact PoC payload.
