### Title
`Shipit::Team#add_member` grants team membership without checking that the webhook-verifying organization matches the team's actual organization - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb], [File: app/models/shipit/team.rb], [File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which organization's `webhook_secret` to verify a request against based on attacker-controlled payload fields (`repository.owner.login` or `organization.login`), not based on the team the event claims to modify. `MembershipHandler#process` then looks up the target `Team` solely by the attacker-supplied `team.id` (`github_id`) and calls `team.add_member(member)`, which never checks that the organization which verified the request equals `team.organization`.

### Finding Description
The broken binding is: `verifying_organization (used to select webhook_secret) == team.organization (the Team record actually being mutated)`. This equality is never enforced anywhere on the `'membership' added` path.

Trace:
1. `WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-49) computes `repository_owner` from `params.dig('repository','owner','login') || params.dig('organization','login')` (line 59-62) and does `Shipit.github(organization: repository_owner)` to pick the `webhook_secret`/app credentials used to verify `X-Hub-Signature`. Both `repository` and `organization` are attacker-supplied JSON body fields.
2. `membership` events have no `repository` key, so `repository_owner` resolves purely to attacker-supplied `params['organization']['login']`.
3. An attacker who owns/administers an org that Shipit is configured to talk to (e.g. their own org, which may be weakly configured, or any org present in `github_hooks`) knows that org's `webhook_secret` and can therefore produce a request that passes `verify_signature` while claiming `organization.login = <attacker's own org>`.
4. `MembershipHandler#process` (app/models/shipit/webhooks/handlers/membership_handler.rb:22-43) calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id)`. `params.team.id` is fully attacker-controlled and is only used as a lookup key — if a `Team` with that `github_id` already exists (e.g. the protected `shopify/developers` team, whose `github_id` is not secret data), the `find_or_create_by!` block (which sets `team.organization = params.organization.login`) is **not** executed, since the record isn't new. The pre-existing `team.organization` value (e.g. `"shopify"`) is left untouched in the DB, but this field is never actually consulted before mutating the team.
5. `team.add_member(member)` (app/models/shipit/team.rb:41-43) is `members.append(member) unless members.include?(member)` — it performs no equality check between `self.organization` and the organization that verified the current request. It simply trusts that whoever called it already validated the request.
6. As a result, an attacker can send `POST /webhooks` with `X-Github-Event: membership`, `action: added`, `team: {id: <victim_team_github_id>, ...}`, `organization: {login: "<attacker-own-org>"}`, `member: {login: "<attacker-github-login>"}`, signed with the attacker's own org's `webhook_secret`. The signature check passes (it only verifies against the attacker's own org), yet the `Membership` row is created for the **victim** `Team` (e.g., `shopify/developers`).

Why existing guards fail: `verify_signature` only proves "this request was sent by someone who knows org X's secret," never "org X is authorized to modify team Y." `ExplicitParameters` schema in `MembershipHandler` only validates types/presence, not any cross-field relationship. No model validation or callback on `Membership`/`Team` re-derives or checks `team.organization` against the verifying organization at write time.

### Impact Explanation
This is a direct authorization-boundary break: an attacker who controls any org onboarded into Shipit's `github_hooks`/`Shipit.github(organization:)` config (including a throwaway/weakly-secured org they created themselves, if Shipit is configured to accept webhooks from it) can add themselves — or any arbitrary GitHub login — as a member of a completely different, protected Shipit `Team`, provided they can guess or learn that team's numeric `github_id`. Since `Shipit.github_teams` (lib/shipit.rb:256-258) is built from `Team.find_or_create_by_handle`, and `Authentication#force_github_authentication` (app/controllers/concerns/shipit/authentication.rb:20-34) gates access on `current_user.authorized?` against membership in those teams, this is a path to escalate an unprivileged GitHub identity into a Shipit-authorized team, matching the "escalation into `Shipit.github_teams` authorization" High-severity category. It is repeatable against any team whose `github_id` the attacker can learn (GitHub team IDs are exposed via the GitHub API/UI to team members and are not treated as secrets), and the write always lands on the victim's pre-existing `Team` row regardless of which org's secret verified the request.

### Likelihood Explanation
Preconditions: (a) the attacker's own organization must already be configured/onboarded in Shipit (present in `github_hooks`/reachable via `Shipit.github(organization:)`) so a valid signature can be produced with a secret the attacker controls; (b) the attacker must know the numeric `github_id` of the target `Team` they want to join, which is discoverable via GitHub's API for any team the attacker or a collaborator can see, or by brute-forcing small sequential IDs. No Shipit session, API token, or GitHub App private key is needed — only the attacker's own org's webhook secret, which they control by definition. This is a low-cost, fully repeatable attack once the onboarding precondition is met.

### Recommendation
In `MembershipHandler#process`/`find_or_create_team!`, verify that the organization that authenticated the current webhook request (the one used in `verify_signature`) equals `team.organization` before allowing `add_member`/`members.delete` to proceed; reject (422/log) events where they differ. Alternatively, scope `Team.find_or_create_by!` lookups by `(github_id, organization)` together rather than `github_id` alone, and treat the webhook-verifying organization as the sole source of truth for which `Team.organization` a membership event is allowed to mutate.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
