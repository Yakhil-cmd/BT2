This confirms the divergence. `PushHandler#process` correctly scopes through `stacks` (which filters `Repository.from_github_repo_name(repository_name)`), but `StatusHandler#process` bypasses this entirely and queries `Commit.where(sha: params.sha)` globally with no repository/stack filter at all.### Title
Cross-repository `status` webhook flips `Commit#deployable?` via unscoped `Commit.where(sha:)` lookup - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits purely by `sha`, without restricting to the stacks/repository named in the webhook payload, unlike every other handler in the same module. A webhook whose `payload['repository']['full_name']` names an attacker-controlled/foreign repository can therefore write a `success` `Status` row onto a `Commit` belonging to a victim `Stack`, flipping `Commit#deployable?` from `false` to `true` for CI the victim's own repository never ran.

### Finding Description
The broken binding, stated as an equality that the code fails to enforce: for the `Status` written by a `status` webhook, `payload['repository']['full_name']` must equal `commit.stack.repository.full_name` before that webhook is allowed to affect `commit`. This is not checked.

`Shipit::Webhooks::Handlers::Handler` provides a `stacks` helper that correctly scopes work to `Repository.from_github_repo_name(repository_name)&.stacks` [1](#0-0) , and `PushHandler#process` uses exactly that scoping (`stacks.not_archived.where(branch:)...`) [2](#0-1) .

`StatusHandler#process`, however, bypasses `stacks` entirely:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 

`Commit.where(sha: params.sha)` is a global, cross-stack, cross-repository query with no `repository_name`/`stack_id` filter. Any `Commit` row anywhere in the Shipit instance sharing that `sha` receives the status. `commit.create_status_from_github!` unconditionally creates a `Status` (`state: 'success'`, etc.) tied to `commit.stack_id` [4](#0-3) , and `Commit#success?` is delegated straight to that `status` [5](#0-4) , which feeds directly into:
```ruby
def deployable?
  !locked? && (stack.ignore_ci? || (success? && !blocked?))
end
``` [6](#0-5) 

Exploit path: git SHA-1 identifiers are content-addressed and identical across forks/mirrors that share history. An attacker forks or otherwise obtains a repository that shares one or more commits (by sha) with a victim's tracked `Stack` (a very common situation for forks, cherry-picks, or shared upstream history). The attacker then sends (or has their own repo emit, since GitHub Apps use one shared webhook secret per app installation, not per-repo) a `status` event with `payload['repository']['full_name']` = attacker's own repo and `sha` = the shared commit, `state: 'success'`. `verify_signature` only checks that the payload can be validly signed for `repository_owner` derived from the payload itself [7](#0-6) ; it says nothing about whether that repository is the one the affected `Commit` actually belongs to, so a legitimately-signed webhook from the attacker's own onboarded/attacker-controlled repository passes signature verification while still writing into an unrelated `Stack`'s `Commit`.

`drop_unhandled_event` and the `ExplicitParameters` schema in `StatusHandler` (`requires :sha`, `requires :state`, etc.) only validate the shape of the payload, not the repository binding [8](#0-7) , so none of the existing guards catch this. This is a genuine authorization gap: the `stacks` scoping mechanism exists in the codebase precisely to enforce this binding, and every other handler except `StatusHandler` uses it.

### Impact Explanation
A payload authenticated for repository A can write a `Status` (and thus flip `success?`/`deployable?`) on a `Commit` belonging to Stack B, tracking a completely different `Repository`. This is a "payload for one repository mutating another's stack/commit" — directly meeting the Critical bar in scope. Once `deployable?` is `true`, downstream automatic/continuous-delivery logic (`schedule_continuous_delivery`, merge-queue processing via `ProcessMergeRequestsJob`) can act on a commit whose CI never actually passed for that stack, potentially triggering an unauthorized deploy or merge. The attack is repeatable against any commit sha shared between an attacker-accessible repository and any tracked stack (forks are the common case), and is not limited to a single victim — it can be replayed against any stack whose commits share sha values with a repository the attacker can emit status events for.

### Likelihood Explanation
Preconditions: the attacker needs a repository (their own, or any public fork) that (a) has the Shipit GitHub App/webhook configured so it can produce a validly-signed webhook, and (b) shares at least one commit sha with a victim `Stack`'s tracked history — trivially true for forks, cherry-picks, or rebased/duplicated commits. No Shipit session, API token, or team membership is required. The attacker only needs to control content of a `status` webhook for a repository they legitimately operate, which is well within an "unprivileged GitHub user" as defined in scope. This is straightforward and repeatable, not merely theoretical, given how common shared-sha situations are between forks and upstreams.

### Recommendation
Scope `StatusHandler#process` the same way `PushHandler` does: resolve `stacks` from `repository_name` first, and only apply the status to commits belonging to those stacks, e.g. `stacks.joins(:commits).merge(Commit.where(sha: params.sha)).find_each { |stack| ... }`, or filter `Commit.where(sha: params.sha, stack_id: stacks.select(:id))` before creating the status. This closes the gap between `payload['repository']['full_name']` and `commit.stack.repository.full_name`.

### Proof of Concept
Under `test/models/webhooks/handlers/status_handler_test.rb` (or extend `test/controllers/webhooks_controller_test.rb`):

```ruby
test "status webhook from a foreign repository must not flip deployable? on a victim stack's commit" do
  victim_stack = shipit_stacks(:shipit) # repository full_name e.g. "shopify/shipit-engine"
  commit = victim_stack.commits.create!(sha: "deadbeef" * 5, ...) # no prior successful status

  refute commit.locked?
  refute victim_stack.ignore_ci?
  assert_equal false, commit.deployable?

  forged_payload = {
    'sha' => commit.sha,
    'state' => 'success',
    'repository' => { 'full_name' => 'attacker/unrelated-repo' } # != victim_stack.repository.full_name
  }

  Shipit::Webhooks::Handlers::StatusHandler.new(forged_payload).process

  commit.reload
  assert_equal true, commit.success?
  assert_equal true, commit.deployable?, "commit became deployable via a status from an unrelated repository"
  refute_equal forged_payload['repository']['full_name'], victim_stack.repository.full_name
end
```
This asserts the binding `payload['repository']['full_name'] == commit.stack.repository.full_name` is false, yet `deployable?` still flips `false → true`, proving the vulnerability.
