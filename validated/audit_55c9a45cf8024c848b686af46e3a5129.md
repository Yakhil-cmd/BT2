### Title
Pre-permissionless `verifySeals` accepts blocks with a single committed seal when `n < 4`, diverging from the consensus-core quorum — (`blockchain/block_validator.go`)

### Summary
`verifySeals` uses `2*sealer.F()+1` as the committed-seal threshold for pre-permissionless blocks. For any committee of size `n ≤ 3`, `F` returns 0 and the threshold collapses to 1. The consensus core uses `calcQuorumSize`, which returns `n` (not `ceil(2n/3)`) for `n < 4`. A single malicious validator can craft a block carrying only its own committed seal, broadcast it over P2P, and have every honest sync/import node accept it via `verifySeals`, while the consensus core would never have committed such a block.

### Finding Description
`IstanbulSealer.F` computes `ceil(n/3) - 1`:

```go
// consensus/istanbul/sealer.go:304-309
func (m *IstanbulSealer) F(_ uint64, qualifiedLen, committeeSize int) int {
    if qualifiedLen > int(committeeSize) {
        return int(math.Ceil(float64(committeeSize)/3)) - 1
    }
    return int(math.Ceil(float64(qualifiedLen)/3)) - 1
}
```

For `n ≤ 3`, `ceil(n/3) = 1`, so `F = 0`. The pre-permissionless branch of `verifySeals` then requires:

```go
// blockchain/block_validator.go:314
if validSeal < 2*v.sealer.F(blockNum, qualifiedLen, committeeSize)+1 {
```

`2*0+1 = 1` — a single valid committed seal satisfies the check.

The consensus core uses:

```go
// consensus/istanbul/core/core.go:81-87
func calcQuorumSize(qualifiedLen int, committeeSize uint64) int {
    size := min(qualifiedLen, int(committeeSize))
    if size < 4 {
        return size   // returns n, not 1
    }
    return int(math.Ceil(float64(2*size) / 3))
}
```

`calcQuorumSize(2,2) = 2`, `calcQuorumSize(3,3) = 3`. The `Quorum` method on `IstanbulSealer` was already corrected to match `calcQuorumSize` (returns `n` for `n<4`), but the pre-permissionless path in `verifySeals` bypasses `Quorum` and calls `2*F+1` directly, preserving the broken formula.

The comment at line 312–313 acknowledges the intentional bypass ("compute 2f+1 explicitly to preserve historical header validity"), but does not account for the fact that `2f+1 = 1 < n` for `n < 4`, making the threshold weaker than what the consensus core ever enforced.

### Impact Explanation
A sync or fast-import node calling `validateHeader → verifySeals` will accept a block whose `CommittedSeal` array contains exactly one valid signature from any council member, provided `qualifiedLen ≤ 3`. The consensus core would never have committed such a block (it requires all `n` validators to commit when `n < 4`). This produces a **chain split**: consensus-participating nodes hold the legitimately committed chain tip; sync nodes that received the crafted block hold a divergent tip with a different state root, enabling invalid balance/state acceptance on those nodes.

### Likelihood Explanation
The condition `qualifiedLen ≤ 3` is required. Kaia's mainnet council is larger, but testnets, private deployments, and newly bootstrapped chains routinely operate with 2–3 validators. The attacker needs one validator private key (their own, if they are a council member) — no key compromise or majority collusion is required. The crafted block is indistinguishable from a legitimate block to any node that only runs `verifySeals`.

### Recommendation
Replace the `2*sealer.F()+1` expression in the pre-permissionless branch with `sealer.Quorum()`, which already implements the correct `n`-for-`n<4` logic and matches `calcQuorumSize`:

```go
// blockchain/block_validator.go
if validSeal < v.sealer.Quorum(blockNum, qualifiedLen, committeeSize) {
    return istanbul.ErrInvalidCommittedSeals
}
```

This unifies the threshold across both the block-validator and the consensus core for all committee sizes, including the degenerate `n < 4` case.
