### Title
Cross-repository commit status forgery via organization/repository binding mismatch in webhook handling - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate an inbound webhook against using the payload's `repository.owner.login` (or `organization.login`) field, then verifies the HMAC over the raw body with that org's secret. Once verified, `StatusHandler` (unlike `PushHandler`/`CheckSuiteHandler`) never re-derives or checks the repository from the signed payload — it updates `Commit` rows matched purely by `sha`, with no scoping to the organization/repository whose secret produced the valid signature. This breaks the binding `verified_organization == written_repository`, letting a webhook signed with org A's secret write commit-status data belonging to any repository/stack tracked by the shared Shipit instance, including those of unrelated organizations.

### Finding Description
`WebhooksController#repository_owner` extracts the organization used to pick the verifying `GitHubApp`/secret directly from attacker-controlled JSON: [1](#0-0) [2](#0-1) 

Because the attacker fully controls the raw JSON body, they can craft any payload and, provided they know the webhook secret configured for *one* organization on the (potentially multi-tenant) Shipit instance — as documented in `config/secrets.development.shopify.yml` where multiple GitHub orgs each have their own `webhook_secret` — compute a signature that `verify_webhook_signature` will accept for that org: [3](#0-2) 

Most handlers (`PushHandler`, `CheckSuiteHandler`) then re-derive the target repository from the same signed payload's `repository.full_name` via `Handler#stacks`/`#repository_name`, scoping writes to stacks belonging to that repository: [4](#0-3) 

`StatusHandler`, however, does not use this scoping mechanism at all. It updates commits found solely by `sha`, independent of any repository/organization field: [5](#0-4) 

Since `Commit` rows are shared across the whole Shipit instance (all stacks/repositories, potentially across multiple organizations configured under `github:` in `config/secrets.yml`), and nothing ties the `sha` field back to the `repository.owner.login`/`repository.full_name` that was used to select the verifying secret, an attacker who legitimately controls the webhook secret for organization A can forge a `status` event naming `repository.owner.login: "orgA"` (to pass `verify_signature`) while setting `sha` to a commit that actually belongs to organization B's repository, and an arbitrary `state`/`context`/`description`/`target_url`.

### Impact Explanation
Commit statuses in Shipit gate whether a commit is considered deployable/mergeable (reflected by the dedicated `deployable_status` / `merge_status` events in `Hook::EVENTS`): [6](#0-5) 
By forging a passing status (`state: "success"`) on a commit belonging to a completely different, unrelated repository/organization hosted on the same Shipit instance, an attacker with no access to that organization's repository or GitHub App can make an otherwise-blocked commit appear CI-green, enabling it to become eligible for deploy or auto-merge — an unauthorized deploy/merge and a cross-repository/cross-organization write, matching the Critical impact bar ("cross-repository writes, or an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Exploitation requires only knowledge of a webhook secret for *any one* organization configured on the shared Shipit instance (a routine, low-privilege capability for a customer/org admin onboarded onto a multi-tenant Shipit deployment, as the shipped `config/secrets.*.yml` templates demonstrate multiple orgs sharing one instance) plus the target commit's SHA, which is frequently public (visible via GitHub UI, PR links, CI logs). No access to the victim organization's repository, GitHub App, or Shipit session is needed, satisfying the "unprivileged attacker breaking a deployment-trust binding" requirement.

### Recommendation
In `StatusHandler#process` (and any other handler that does not already do so), require that the commit's owning repository match the repository/organization identified via `verify_signature`'s `repository_owner`/`repository.full_name`, e.g. filter through `stacks` (as `PushHandler`/`CheckSuiteHandler` already do) or explicitly assert `commit.stack.repository.owner == repository_owner` before applying the status update. More generally, enforce that every webhook handler validates the payload's repository/organization claim against the actual entity being mutated, not just against the field used to select the verifying secret.

### Proof of Concept
1. Deploy Shipit configured for two organizations, `orgA` and `orgB`, each with its own `webhook_secret` (per `config/secrets.*.yml` multi-org schema).
2. Attacker (a legitimate org admin of `orgA`, with no access to `orgB`) knows `orgA`'s `webhook_secret`.
3. Attacker crafts a `status` event JSON body:
```json
{
  "sha": "<sha of a commit belonging to orgB/some-repo>",
  "state": "success",
  "context": "ci/forged",
  "repository": {"owner": {"login": "orga"}},
  "branches": [{"name": "master"}]
}
```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(orgA_webhook_secret, raw_body)>` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `"orga"`, loads `orgA`'s `GitHubApp`, and the HMAC matches → request is accepted (`app/controllers/shipit/webhooks_controller.rb:24-30`).
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the commit in `orgB`'s repository — and calls `create_status_from_github!`, marking it as passing CI, despite the attacker having no relationship to `orgB` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`).

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
