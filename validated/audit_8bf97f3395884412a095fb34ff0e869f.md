### Title
`machine_env` from attacker-controlled `shipit.yml` overrides `GIT_COMMITTER_NAME`/`GIT_COMMITTER_EMAIL`/`GITHUB_REPO_OWNER` in `TaskCommands#env` - ([File: lib/shipit/task_commands.rb])

### Summary
`TaskCommands#env` merges `deploy_spec.machine_env` (sourced from the checked-out branch's `shipit.yml`, via `DeploySpec::FileSystem`) after the hardcoded `GIT_COMMITTER_NAME`/`GIT_COMMITTER_EMAIL` hash and after `@stack.env` (which sets `GITHUB_REPO_OWNER`), and only `@task.env` is merged afterward. This lets a `shipit.yml` author set arbitrary values for these identity keys, which are then passed to the `git`/deploy commands run under the Shipit host's credentials, unless the deploying task's own `env` happens to redefine the same key.

### Finding Description
The binding that should hold is: for every key `k` in `{GIT_COMMITTER_NAME, GIT_COMMITTER_EMAIL, GITHUB_REPO_OWNER}`, `final_env[k] == authorized_value(k)` where `authorized_value` is derived strictly from `@task.user`/`Shipit.committer_*` (for committer identity) or `@stack.repository.owner` (for repo owner) — never from `deploy_spec.machine_env`.

Tracing `TaskCommands#env`:
```
lib/shipit/task_commands.rb:33-48
def env
  super
    .merge(@stack.env)                # sets GITHUB_REPO_OWNER, GITHUB_REPO_NAME, ...
    .merge(
      ...
      'GIT_COMMITTER_NAME' => @task.user&.name || Shipit.committer_name,
      'GIT_COMMITTER_EMAIL' => @task.user&.email || Shipit.committer_email
    )
    .merge(deploy_spec.machine_env)    # <-- attacker-controlled shipit.yml keys, LAST-but-one
    .merge(@task.env)                  # only this can still override machine_env
end
``` [1](#0-0) 

`deploy_spec.machine_env` is a pass-through of the `machine.environment` block of the checked-out `shipit.yml`, with no key filtering at all:
```
app/models/shipit/deploy_spec.rb:69-71
def machine_env
  config('machine', 'environment') || {}
end
``` [2](#0-1) 

`DeploySpec::FileSystem#config` reads this from the checked-out working directory (the commit under deploy), so a `shipit.yml` revision controlled by whoever authored that commit (e.g. an accepted PR, or any commit that ends up deployed) determines `machine_env`'s keys, without restriction to a safe subset — contrast this with `deploy_variables`/`filter_deploy_envs`, which explicitly whitelist deploy-time variables via `EnvironmentVariables#permit` (`app/models/shipit/deploy_spec.rb:174-176`), but `machine_env` has no equivalent filter.

Because `merge` on the right always wins, setting `machine.environment.GIT_COMMITTER_NAME` (or `_EMAIL`, or `GITHUB_REPO_OWNER`) in `shipit.yml` overrides the hardcoded/`@stack.env` values in the resulting hash, unless `@task.env` (the task-level env, set at trigger time from `Stack#build_deploy`/`Stack#trigger_task`, filtered through `deploy_spec.filter_deploy_envs`/`filter_task_envs` against `deploy_variables`, not `machine_env`) happens to also define the same key — which it normally does not, since deploy/task env is a separate, whitelisted mechanism unrelated to `machine_env`.

This computed `env` hash is what `Command.new(command_line, env:, chdir: steps_directory)` receives for deploy/rollback steps (`lib/shipit/task_commands.rb:17-27`), and it also underlies `git(*args)` in `Commands#git`, which is used by `DeployCommands#push`/checkout/clone-style commands, meaning attacker-controlled `GIT_COMMITTER_NAME`/`EMAIL` values reach the actual `git` invocations executed via `Command#start`/`PTY.spawn` under the Shipit host's git identity and credentials.

### Impact Explanation
An attacker who can get a `shipit.yml` revision run by a deploy (their own fork/PR branch in review-stack scenarios, or any commit merged and later deployed before being reverted) can force the `git commit`/`push` commands that run under the Shipit host's authenticated git identity (using `GITHUB_TOKEN`) to record an arbitrary committer name/email, and can spoof `GITHUB_REPO_OWNER` used elsewhere in scripts/env interpolation (e.g. `Stack#links` interpolation, deploy scripts referencing `$GITHUB_REPO_OWNER`). This is a cross-repository/identity spoofing issue: the value written to git history and downstream tooling is attributable to a record (`@task.user`, `@stack.repository`) that did not actually authorize it. This matches the "authorization/identity spoofing via env" pattern described as Critical in the rules, though it does not directly leak `GITHUB_TOKEN` or grant unauthorized deploys by itself — its blast radius is limited to falsifying committer metadata and any script logic that trusts these env vars, scoped to the stack whose `shipit.yml` is being executed.

### Likelihood Explanation
Preconditions: an unprivileged GitHub user needs a deploy or review-stack build to actually execute a revision of `shipit.yml` they control (e.g. a review-stack deploy of their own PR, which is a supported and common Shipit feature — no operator/maintainer approval is required for review stacks in many setups). No Shipit secrets, session, or API token are needed; the attacker only needs to author `shipit.yml`'s `machine.environment` block in a branch that gets deployed. This is directly reproducible and repeatable for any repository configured with review stacks, or any deploy pipeline that runs untrusted branches.

### Recommendation
In `TaskCommands#env` (and/or `Commands#base_env`), reserve `GIT_COMMITTER_NAME`, `GIT_COMMITTER_EMAIL`, `GITHUB_REPO_OWNER`, `GITHUB_REPO_NAME`, `GITHUB_TOKEN`, `GITHUB_DOMAIN` as non-overridable keys: merge `deploy_spec.machine_env` first (or filter it to strip these reserved keys) before merging the hardcoded identity/`@stack.env` hash, so the authoritative values always win regardless of merge order changes. E.g. change order to `.merge(deploy_spec.machine_env).merge(@stack.env).merge(committer_hash).merge(@task.env)`, or explicitly `deploy_spec.machine_env.except(*RESERVED_ENV_KEYS)`.

### Proof of Concept
```ruby
# test/unit/task_commands_test.rb (or deploy_commands_test.rb)
test "machine_env cannot override GIT_COMMITTER_NAME/EMAIL or GITHUB_REPO_OWNER" do
  @deploy_spec.stubs(:machine_env).returns(
    'GIT_COMMITTER_NAME' => 'attacker',
    'GIT_COMMITTER_EMAIL' => 'attacker@evil.com',
    'GITHUB_REPO_OWNER' => 'attacker-org'
  )

  env = @commands.env

  refute_equal 'attacker', env['GIT_COMMITTER_NAME']
  refute_equal 'attacker@evil.com', env['GIT_COMMITTER_EMAIL']
  refute_equal 'attacker-org', env['GITHUB_REPO_OWNER']
  assert_equal 'Shipit', env['GIT_COMMITTER_NAME']
  assert_equal 'shipit@shipit.com', env['GIT_COMMITTER_EMAIL']
  assert_equal @stack.repository.owner, env['GITHUB_REPO_OWNER']
end
```
Given the current merge order in `TaskCommands#env` (`lib/shipit/task_commands.rb:33-48`), this test fails today: `env['GIT_COMMITTER_NAME']` equals `'attacker'` and `env['GITHUB_REPO_OWNER']` equals `'attacker-org'`, confirming the override. [1](#0-0) [2](#0-1) [3](#0-2)
