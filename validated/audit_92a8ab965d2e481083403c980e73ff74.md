### Title
Webhook signature validated against `repository.owner.login`, but stacks resolved from `repository.full_name` — cross-organization webhook forgery ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate a webhook using `repository.owner.login` (or `organization.login`) from the JSON payload, but every `Webhooks::Handlers::Handler` subclass resolves the `Stack`/`Repository` it will act on using the independent `repository.full_name` field of the same payload. Because these two fields are never cross-checked, an entity that legitimately controls the GitHub App/webhook secret for one organization configured in Shipit can forge a signed webhook that is validated as belonging to that organization, while its payload content (`repository.full_name`) targets a stack/repository belonging to a *different* organization on the same Shipit instance.

### Finding Description
`verify_signature` computes `repository_owner` from `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` and uses it to pick the per-organization `webhook_secret` via `Shipit.github(organization: repository_owner)`: [1](#0-0) [2](#0-1) 

The signature check itself is a straight HMAC-SHA1 comparison over the raw JSON body using that organization's configured secret: [3](#0-2) 

Shipit explicitly supports configuring a distinct GitHub App (and therefore a distinct `webhook_secret`) per organization on the same instance, as documented in "Using Multiple Github Applications": [4](#0-3) 

Once the signature passes, `WebhooksController#create` dispatches the raw parsed payload to every registered handler for the event, unmodified: [5](#0-4) 

Every handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc.) inherits `stacks`/`repository_name` from the base `Handler` class, which looks up the affected repository/stack using a **different** payload field — `repository.full_name` — with no reference back to `repository.owner.login`: [6](#0-5) 

So the binding the engine implicitly relies on is:
`organization authenticated (repository.owner.login, checked against a per-org webhook_secret)` == `repository written (repository.full_name, used to resolve the Stack that gets commits/statuses/check-runs written to)`

This equality is never enforced. An attacker who is a legitimate administrator of Organization A (and therefore knows/controls Org A's `webhook_secret`, since they configured Org A's GitHub App integration with this Shipit instance) can sign a POST to `/webhooks` where `repository.owner.login = "org-a"` (passes signature check against Org A's secret) but `repository.full_name = "org-b/victim-repo"` (so the handler resolves and mutates Org B's `Stack`/`Repository`, e.g. via `GithubSyncJob`, `Commit#create_status!`, `RefreshCheckRunsJob`, etc., as exercised in `test/controllers/webhooks_controller_test.rb`).

### Impact Explanation
This is a cross-repository write: an entity with no legitimate relationship to Organization B can inject fabricated `push`, `status`, or `check_suite` events into Organization B's stacks. Depending on stack configuration this can:
- Fabricate passing CI/commit statuses on arbitrary victim commits (`StatusHandler`), which can satisfy `ci.require` gating and enable merges/deploys of that commit through the merge queue or continuous delivery.
- Trigger `GithubSyncJob`/`RefreshCheckRunsJob` for a victim stack based on attacker-controlled payload content.
This maps to "cross-repository writes" and potentially an "unauthorized deploy" if `continuous_deployment` is enabled on the victim stack, both of which are in the accepted High/Critical impact set.

### Likelihood Explanation
Requires the attacker to be a legitimate operator of at least one organization configured on the shared Shipit instance (i.e., they know that organization's `webhook_secret` because they set up its GitHub App integration), but have no access to Organization B. This is a realistic scenario for any Shipit deployment following the documented multi-organization setup. No GitHub write access to the victim repo, no Shipit `ApiClient` token, and no privileged Shipit account are required — only the ability to send an HTTP POST with a valid signature for the attacker's own organization.

### Recommendation
Cross-validate `repository.full_name`'s owner against the authenticated `repository_owner`/organization used for signature verification before dispatching to handlers (e.g., reject the webhook if `repository.full_name.split('/').first` doesn't match the organization whose secret validated the signature), or resolve the webhook secret/organization strictly from the repository actually referenced in the event payload rather than a separate owner field.

### Proof of Concept
1. Shipit is configured (per `docs/setup.md`, "Using Multiple Github Applications") with two organizations, `org-a` and `org-b`, each with its own GitHub App and `webhook_secret`.
2. Attacker administers `org-a`'s GitHub App integration and therefore knows `webhook_secret_a`.
3. Attacker crafts a `push` (or `status`/`check_suite`) webhook JSON body:
   ```json
   {
     "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" },
     ...
   }
   ```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(webhook_secret_a, raw_body)` and POSTs to `/webhooks` with `X-Github-Event`.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `"org-a"`, fetches `Shipit.github(organization: "org-a")`, and the HMAC check passes.
6. `Webhooks::Handlers::Handler#stacks`/`#repository_name` resolves `Repository.from_github_repo_name("org-b/victim-repo")`, and the handler acts on `org-b`'s stack (e.g., enqueues `GithubSyncJob`, creates a `Status`, or triggers `RefreshCheckRunsJob`) — all driven by attacker-supplied content the attacker was never authorized to write for `org-b`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
