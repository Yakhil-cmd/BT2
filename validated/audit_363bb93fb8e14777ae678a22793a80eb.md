## Title
Webhook signature is bound to the payload's `repository.owner.login`/`organization.login`, not to the `repository.full_name` the handlers act on, allowing cross-organization status/commit forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

## Summary
`WebhooksController#verify_signature` selects which GitHub App/organization config (and thus which `webhook_secret`) to use for HMAC verification based on `repository.owner.login` (or `organization.login`) in the JSON body, then hands the *entire, unmodified* payload to the event handlers. The handlers, however, resolve which `Stack`/`Repository`/`Commit` to act on using a *different* field of the same payload: `repository.full_name` (`Handler#repository_name`) or a bare `sha` lookup (`StatusHandler`). Because Shipit is explicitly designed to be multi-tenant — `Shipit.github(organization:)` is configured per-organization in `secrets.yml`, each with its own `webhook_secret` — a party who legitimately controls the webhook secret for *one* configured organization can forge a payload whose `repository.owner.login` matches their own org (so their known secret verifies) while `repository.full_name` (or `sha`) refers to a resource belonging to a *completely different* organization/stack hosted on the same Shipit instance.

## Finding Description
- `WebhooksController#verify_signature` picks the app config using only `repository_owner`: [1](#0-0) [2](#0-1) 

- It then dispatches the raw parsed body to every registered handler for the event, unmodified: [3](#0-2) 

- The base `Handler` class resolves the target `Stack`s using `repository.full_name`, a field the signature-selection logic never inspected: [4](#0-3) 

- `PushHandler` uses that mismatched-lookup `stacks` scope to trigger a live GitHub resync (`stack.sync_github`) on whatever stack `full_name` resolves to: [5](#0-4) 

- `StatusHandler` is even more directly exploitable: it looks up commits purely by `sha` (no repository/org binding check at all) and writes a CI status onto them straight from attacker-controlled `state`/`description`/`context` fields: [6](#0-5) 

- Shipit is explicitly multi-tenant: each organization has its own `webhook_secret`, `app_id`, `private_key`, etc., configured independently in `secrets.yml`: [7](#0-6) [8](#0-7) 

**Binding broken (equality that should hold but doesn't):**
`organization whose webhook_secret authenticated the request` == `organization/repository the handler code actually writes state for`.

Concretely: `repository_owner` (used in `verify_signature`) is derived from `repository.owner.login` / `organization.login`, while the actual mutation target is derived from `repository.full_name` (`Handler#repository_name`) or from a global `sha` lookup (`StatusHandler`). Nothing enforces that these two values agree. An attacker who is a legitimate administrator/holder of Org A's GitHub App webhook secret (a valid, low-privilege actor with respect to Org B) can compute a correct `X-Hub-Signature` for an arbitrary payload of their own construction, set `repository.owner.login` to `"OrgA"` to pass `verify_signature`, but set `repository.full_name` (or a known commit `sha`) to point at Org B's stack/commit — something outside their authorization scope. `Shipit::GithubOrganizationUnknown` handling confirms `Shipit.github(organization: repository_owner)` is a per-organization keyed lookup with no cross-check against the resource being mutated: [9](#0-8) 

## Impact Explanation
This crosses the "an organization that authenticated versus the repository that is written" trust boundary explicitly called out as in-scope. Concretely reachable outcomes with only knowledge of one organization's webhook secret:
- **Forged CI status on a different organization's commit** via `StatusHandler`, which is looked up solely by commit `sha` with no repository/owner check at all — an attacker can inject a fabricated `success` status for a known SHA belonging to another tenant's stack. If that stack has `ci.require` gating and/or `continuous_deployment` enabled, this can unblock or trigger an **unauthorized deploy** of that commit — matching the High-severity criterion "escalation into … unauthorized deploy" territory, and depending on downstream automation could reach the Critical bar (unauthorized deploy).
- **Forced resync (`PushHandler` → `stack.sync_github`)** of an arbitrary cross-tenant stack, letting the attacker trigger GitHub API calls and commit ingestion timing for a stack they don't own, and interfere with another tenant's deploy pipeline/state (denial of accurate state, race conditions with legitimate syncs).

## Likelihood Explanation
Likelihood depends on the deployment being multi-organization (multiple GitHub orgs configured under one Shipit instance, each with its own `webhook_secret`), which is an explicitly supported and documented configuration. Within that model, no cross-repository/App-level assumption is required beyond knowing one org's `webhook_secret` — a credential that many people at that org (anyone able to view/rotate the GitHub App's webhook settings) may hold, which is a materially different (and typically much larger) population than "someone with write access to the specific target repository/stack" that the deploy/task/API-permission model is built to gate.

## Recommendation
Bind webhook signature verification to the *same* repository/organization identifier that handlers subsequently use to select the mutation target:
- Verify the signature using the organization derived from `repository.full_name`'s owner segment (or otherwise reject payloads where `repository.owner.login`/`organization.login` disagrees with `repository.full_name`'s owner).
- In `Handler#repository_name` / `StatusHandler#process`, cross-check that the resolved `Stack`/`Commit`'s repository owner matches the organization whose secret verified the request before mutating any state.
- Consider having each `GithubHook`/organization webhook use a per-organization scoped secret lookup keyed by `full_name`'s owner exclusively, removing the `organization.login` fallback path entirely, and reject the request if the two disagree.

## Proof of Concept
1. Deploy Shipit configured for two organizations, `org-a` and `org-b`, each with distinct `webhook_secret`s (per `config/secrets.*.yml` structure) — a supported and documented multi-tenant setup.
2. As a person who knows/administers `org-a`'s GitHub App and thus its `webhook_secret`, craft a `status` event payload:
   ```json
   {
     "sha": "<known sha of a commit belonging to org-b's stack>",
     "state": "success",
     "context": "ci/required-check",
     "repository": { "owner": { "login": "org-a" }, "full_name": "org-a/some-repo" }
   }
   ```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(org-a webhook_secret, raw_body)>`.
4. POST to `/webhooks` with `X-Github-Event: status`.
5. `WebhooksController#verify_signature` resolves `repository_owner => "org-a"`, fetches `org-a`'s `github_app`, and the signature verifies successfully (attacker legitimately knows this secret). [1](#0-0) 
6. `StatusHandler#process` looks up `Commit.where(sha: params.sha)` — matching the org-b commit purely by SHA, with no cross-check against `org-a`/`org-b` — and calls `commit.create_status_from_github!(params)`, writing an attacker-controlled `success` status onto org-b's commit. [6](#0-5) 
7. If org-b's stack has continuous deployment enabled and gates on this CI status, the forged status can trigger an unauthorized deploy of that commit.
