### Title
Webhook signature is verified against an attacker-chosen organization while `StatusHandler` writes commit status with no repository/organization binding at all - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
The report's bug class is a broken equality between the field a signature actually protects and the field the code acts on. In this engine, `WebhooksController#verify_signature` selects *which* GitHub organization's `webhook_secret` to check the HMAC against using a value taken straight from the untrusted JSON body, while `StatusHandler#process` never checks organization/repository ownership at all before mutating commit status — it matches purely on `sha` across the whole installation.

### Finding Description
`WebhooksController#verify_signature` picks the signing key like this: [1](#0-0) 

and the organization used to select that key comes directly from the request body: [2](#0-1) 

`GitHubApp#verify_webhook_signature` additionally treats a blank `webhook_secret` as automatically verified: [3](#0-2) 

This is officially a supported, documented configuration (multiple GitHub orgs each with their own optional `webhook_secret`): [4](#0-3) [5](#0-4) 

Once the request passes `verify_signature`, the payload is dispatched to handlers, and `StatusHandler` writes a commit status using **only the commit sha**, with no check that the sha's commit belongs to the organization that supposedly signed the request: [6](#0-5) 

Compare this to every other handler, which correctly scopes to a `Repository`/`Stack` derived from `repository.full_name`, e.g.: [7](#0-6) [8](#0-7) 

The equality that should hold is:
`organization_that_signed(payload) == organization_owning(commit_identified_by(params.sha))`

**Before the attack:** a commit's status can only be updated by a webhook whose HMAC is valid for the GitHub App/org that actually owns the repository containing that commit.

**After the attack:** an attacker who legitimately administers (or knows the `webhook_secret` of) OrgA — or any org in the multi-org config that was left with `webhook_secret: nil`, which the docs explicitly mark "(optional)" — can send a forged `status` event where `repository.owner.login` (or `organization.login`) names OrgA, but `sha` names a commit that actually belongs to a stack tracked under OrgB, a repository the attacker has no relationship to. `verify_signature` accepts the request (valid HMAC for OrgA, or unconditionally accepted if OrgA's secret is blank), and `StatusHandler` blindly sets the status ("success"/"failure") for OrgB's commit because it never checks which repository the sha belongs to.

### Impact Explanation
Shipit's merge queue and deploy pipeline treat GitHub commit statuses as ground truth for mergeability/CI gating. Being able to forge a "success" status on an arbitrary commit belonging to a repository/organization the attacker does not control lets them defeat CI gating for that repository, enabling an unauthorized merge or deploy of a commit they never had access to — a cross-repository/cross-organization write that crosses a genuine authorization boundary (one org's credentials used to write another org's state), matching the "unauthorized deploy, rollback, or merge" / "cross-repository writes" impact tier.

### Likelihood Explanation
Exploitability requires the attacker to be a legitimate administrator of at least one GitHub App/organization configured in the same multi-tenant Shipit instance (a documented, supported deployment topology), or to target an org whose optional `webhook_secret` was left unset. Both scenarios are realistic in a shared, multi-org Shipit deployment as explicitly documented in `docs/setup.md`, without requiring any Shipit session, API token, or the target org's own credentials.

### Recommendation
- Make `StatusHandler` (and any other handler that doesn't already do so) resolve and scope to the specific `Repository`/`Stack` derived from the webhook's `repository.full_name`/`organization.login`, and reject/ignore statuses for commits that don't belong to that repository.
- Bind the organization that verified the signature to the organization the payload is allowed to act on, instead of trusting an attacker-controlled field to select the verification key and a separate, unchecked field to select the mutated resource.
- Stop treating a blank `webhook_secret` as automatically-verified in multi-org configurations; require every organization in a multi-org config to have a secret, or explicitly disable that org's webhook processing if unset.

### Proof of Concept
1. Shipit is configured with two orgs, `OrgA` (attacker has push access / created the GitHub App and knows its `webhook_secret`, or `OrgA` has `webhook_secret: nil` per the documented optional setting) and `OrgB` (victim org, unrelated to attacker).
2. Attacker looks up (via the public Shipit UI) a commit sha `S` currently tracked by a stack under `OrgB`.
3. Attacker sends `POST /webhooks` with header `X-Github-Event: status`, and JSON body:
   ```json
   { "repository": {"owner": {"login": "OrgA"}}, "sha": "S", "state": "success", ... }
   ```
   signed (or left unsigned if `OrgA.webhook_secret` is blank) so that `WebhooksController#verify_signature` — using `Shipit.github(organization: "OrgA")` — accepts it.
4. `StatusHandler#process` runs `Commit.where(sha: "S").each { |c| c.create_status_from_github!(params) }`, setting a "success" status on `OrgB`'s commit `S` even though the request was never signed by anything related to `OrgB`.
5. Shipit's merge/deploy gating for `OrgB`'s stack now observes a spoofed "success" status for commit `S`, allowing an unauthorized merge/deploy of that commit.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
