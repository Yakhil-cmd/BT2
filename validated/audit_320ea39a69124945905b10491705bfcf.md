### Title
Webhook signature is verified against `repository.owner.login`'s GitHub App secret while stack lookup uses the unauthenticated `repository.full_name`, allowing cross-organization webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret used to authenticate an inbound GitHub webhook based on `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). All downstream handlers, however, resolve the target `Repository`/`Stack` from a *different* field of the same JSON body: `payload.dig('repository', 'full_name')`. Because the signature only proves that the payload was signed with the secret of the organization named in `repository.owner.login`, but the actual repository acted upon is determined by the independent `repository.full_name` field, an attacker who legitimately controls a GitHub App/webhook installation on one organization (and therefore knows that organization's `webhook_secret`) can craft a payload whose `repository.owner.login` matches their own org (so it passes signature verification) while `repository.full_name` points at a completely different, victim-owned repository/stack tracked by the same Shipit instance.

### Finding Description
`verify_signature` looks up the app/secret exclusively via the owner login field: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

The signature is a plain HMAC-SHA1 over the raw request body, keyed by the `webhook_secret` configured for `repository_owner`'s organization: [3](#0-2) 

`Shipit` supports multiple GitHub organizations, each configured with its own independent `webhook_secret`, exactly as documented/exemplified: [4](#0-3) [5](#0-4) 

Once the signature check passes, every event handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, `MembershipHandler`, pull-request handlers) is dispatched with the raw, unverified-for-consistency `params` hash: [6](#0-5) 

The base `Handler` class resolves the target stacks purely from `repository.full_name`, a field that is never cross-checked against `repository.owner.login`: [7](#0-6) 

`Repository.from_github_repo_name` then does a case-insensitive DB lookup by `owner`/`name` split out of that `full_name`, with no relation at all to which organization's secret validated the request: [8](#0-7) 

`PushHandler#process`, for example, uses only the resolved `stacks` (derived from `full_name`) and the attacker-controlled `ref`/`after` fields to trigger a sync against arbitrary commits: [9](#0-8) 

`StatusHandler` similarly writes a commit status to any `Commit` matching an attacker-supplied `sha`, independent of which org's secret validated the payload: [10](#0-9) 

**The broken binding, stated as an equality that the code assumes but never enforces:**

`organization authenticated by verify_signature (repository.owner.login)` == `repository/stack actually written by the handler (repository.full_name)`

In a single-organization deployment this equality trivially holds because there is only one secret. In a **multi-organization deployment** (the documented `github: { orgA: {...}, orgB: {...} }` schema), the equality is never checked. An attacker who is a legitimate, unprivileged GitHub App installer/webhook sender for `orgA` (i.e., they know `orgA`'s `webhook_secret` because they configured or observed their own org's App/webhook, not because they compromised Shipit) can:
1. Take any organization Shipit tracks stacks for, e.g. `victim-org/target-repo`.
2. Build a JSON payload with `repository.owner.login = "orgA"` (so `Shipit.github(organization: "orgA")` picks orgA's secret) but `repository.full_name = "victim-org/target-repo"`.
3. Sign it with `orgA`'s `webhook_secret` and POST to `/webhooks`.
4. `verify_signature` succeeds because the signature is valid for the secret it looked up (orgA's).
5. `PushHandler`/`StatusHandler`/etc. resolve stacks using `repository.full_name = "victim-org/target-repo"`, and act on that repository's stacks/commits — an organization the attacker's key was never associated with.

### Impact Explanation
This breaks the trust boundary between "which organization's webhook secret authenticated this request" and "which repository's stacks/commits/state get mutated." Concretely, `PushHandler` will call `stack.sync_github(expected_head_sha:)` for a victim repository/branch using an attacker-chosen `after` SHA, and `StatusHandler` will attach fabricated CI statuses to arbitrary commits by SHA, both of which are used by Shipit to decide whether commits are safe to deploy/merge. This can enable **cross-repository writes and an unauthorized deploy/merge decision** on a stack the attacker's GitHub identity has no legitimate relationship with, matching the High/Critical impact categories in scope (cross-repository writes / unauthorized deploy).

### Likelihood Explanation
This requires a Shipit deployment configured with more than one GitHub organization (the supported and documented multi-org schema) and requires the attacker to control/know the `webhook_secret` of at least one of those configured organizations (e.g., by being a legitimate admin of their own org's GitHub App installation that Shipit trusts). No Shipit session, `ApiClient` token, or GitHub write access to the victim repository is required — only knowledge of one configured org's `webhook_secret`, which is a credential boundary distinct from write access to the target repository. Given multi-org Shipit installations are an explicit supported configuration, likelihood is moderate to high in that deployment shape.

### Recommendation
After signature verification succeeds, cross-check that the organization/owner used to select the webhook secret (`repository_owner`) matches the owner embedded in `repository.full_name` (and any `organization.login` field) before dispatching to handlers; reject the request (422) on mismatch. Alternatively, resolve the target `Repository` first, derive the verification key strictly from that repository's own owner, and refuse to process if `repository.owner.login` disagrees with the resolved repository's owner.

### Proof of Concept
1. Configure Shipit with two organizations, `orgA` and `orgB`, each with its own `webhook_secret`, per [4](#0-3) , and track a stack for `orgB/victim-repo`.
2. As an attacker who administers `orgA`'s GitHub App (legitimately knows `orgA`'s `webhook_secret`), build a `push` event JSON body:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen-sha>",
     "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" }
   }
   ```
3. Compute `X-Hub-Signature: sha1=HMAC_SHA1(orgA_webhook_secret, raw_body)` per [3](#0-2) .
4. POST to `/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` computes `Shipit.github(organization: "orgA")` and validates successfully [1](#0-0) .
6. `PushHandler#process` resolves stacks via `payload.dig('repository', 'full_name')` = `"orgB/victim-repo"` [7](#0-6)  and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on `orgB`'s stack [9](#0-8) , despite the request never having been signed by anything associated with `orgB`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
