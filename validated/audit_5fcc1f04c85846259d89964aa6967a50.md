### Title
Cross-organization webhook confusion: signature verified against the payload's `repository.owner.login`, but write actions dispatch on `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
This is the direct analog of the "division-before-multiplication" precision bug: a value that gets used to derive a *guard* (the org used to select the signing secret) diverges from the value that gets used for the actual *write path* (the repository the handler mutates), even though both come from the same unverified JSON body. In the C4 report, `feePct` was computed and used before the true, precise, final quantity was known; here, `repository_owner` is used to pick which organization's HMAC secret validates the request, but the handlers (`PushHandler`, `StatusHandler`, `MembershipHandler`, PR handlers) key their side effects off a *different* field, `repository.full_name` / `organization.login`, taken from that same unauthenticated JSON, without ever checking it is consistent with the org whose secret validated the signature.

### Finding Description
`Shipit::WebhooksController#verify_signature` picks which GitHub App/organization's `webhook_secret` to check the signature against using a value read straight out of the still-unverified JSON body: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` resolves that organization name to a distinct, independently-configured `GitHubApp` instance with its own `webhook_secret`, confirming Shipit is explicitly designed for multi-tenant use (multiple orgs, each with its own app/secret): [3](#0-2) [4](#0-3) 

The HMAC check itself is scoped to whichever org config was selected: [5](#0-4) 

Once the signature validates, `Webhooks.for_event` handlers run and do their own lookups against `payload.dig('repository', 'full_name')` — a separate field from `repository.owner.login` used for org selection — with no re-check that the two agree: [6](#0-5) [7](#0-6) [8](#0-7) 

The binding that should hold is:
`organization whose secret validated the HMAC` == `organization that owns the repository the handler writes to`

Because the two are read from different JSON keys of the same attacker-controlled body, an attacker who legitimately controls org A (with a valid, configured `webhook_secret` in this multi-tenant Shipit install) can craft a raw payload where `repository.owner.login = "org-A"` (so `verify_signature` picks org A's secret, which the attacker can compute a valid HMAC for) but `repository.full_name = "org-B/victim-repo"`. The signature check passes because it only validates that org A signed *some* body — it says nothing about which repository that body may reference. The handler then acts on `org-B/victim-repo` using `Repository.from_github_repo_name(payload.dig('repository','full_name'))`, exactly as the equality above shows it should not.

### Impact Explanation
`Handlers::StatusHandler` writes an arbitrary commit status straight from the forged payload: [9](#0-8) 
and that status directly feeds `Commit#deployable?` / `blocked?`, which gate whether a commit can be deployed and whether it blocks other commits in the queue: [10](#0-9) [11](#0-10) 

By forging a `success` status (or clearing a `blocking` one) for a victim org's commit while only holding credentials for their own, unrelated org's webhook secret, an attacker can make an otherwise CI-failing/blocked commit `deployable?`, enabling an **unauthorized deploy** through the normal deploy UI/API once a legitimate user (or automated continuous-deployment) triggers it. `PushHandler` and `MembershipHandler` are similarly reachable cross-tenant and can trigger unwanted syncs or team/membership mutations for the victim's stack.

This satisfies the required High/Critical bar ("escalation... or an unauthorized deploy, rollback, or merge") because it lets an attacker manipulate the deploy-gating state of a repository/org they do not otherwise control, using only their own (legitimately obtained) webhook secret for a different tenant.

### Likelihood Explanation
Requires: (1) the Shipit install serves more than one GitHub organization/app (explicitly supported and documented, see `config/secrets.development.shopify.yml` and `Shipit.github_organizations`), and (2) the attacker controls/administers at least one of those configured organizations (i.e., can see or set that org's `webhook_secret` in its GitHub App settings) but not the victim org's secret. No GitHub token, Shipit session, or API client credential for the victim org is needed — only knowledge of one's own tenant's webhook secret, which is a much weaker requirement than the excluded preconditions (no `ApiClient` token, `webhook_secret` of the *victim*, private key, etc. is needed). This is a realistic scenario for any shared/multi-tenant Shipit deployment.

### Recommendation
After `verify_signature` succeeds, re-derive the repository/stack strictly from the same organization that was used to validate the signature (e.g., assert `payload.dig('repository','full_name')&.split('/')&.first == repository_owner`, case-insensitively) before dispatching to handlers, and reject (422) on mismatch. More robustly, `Handler#stacks`/`repository_name` should be scoped by the verified organization rather than trusting the raw payload's `full_name` independently of the field used for signature selection.

### Proof of Concept
1. Configure Shipit with two orgs, `org-a` and `org-b`, each with its own `webhook_secret` (as in `config/secrets.development.shopify.yml`).
2. As an attacker who administers `org-a`'s GitHub App (and thus knows `org-a`'s `webhook_secret`), craft a `status` webhook JSON body:
```json
{
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check"
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(org-a's webhook_secret, raw_body)>` and POST to `/github/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "org-a")`, verifies successfully against `org-a`'s secret.
5. `Handlers::StatusHandler#process` looks up `Commit.where(sha: ...)` for the victim commit (found via `payload.dig('repository','full_name') == "org-b/victim-repo"`) and calls `create_status_from_github!`, marking the required check `success` for `org-b`'s commit despite the attacker never having `org-b`'s webhook secret.
6. The victim commit is now `deployable?` per `Commit#deployable?`, and a subsequent (legitimate or CD-triggered) deploy proceeds on a commit whose CI status was forged by an unrelated tenant.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
