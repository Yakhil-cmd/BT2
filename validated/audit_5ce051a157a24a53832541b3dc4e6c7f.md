### Title
Webhook secret authenticates only the sending organization, not the repository the payload writes to, enabling cross-organization stack writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In multi-organization Shipit deployments (`config.github.<OrgOne>`, `config.github.<OrgTwo>`, each with its own `webhook_secret`), `WebhooksController#verify_signature` selects which organization's secret to verify the payload with based on `repository.owner.login` pulled from the *same unverified* JSON body that later determines which repository/stack is written to. The signature only proves "the sender knows OrgOne's webhook secret" — it never constrains which repository the payload is allowed to reference. An attacker who legitimately controls OrgOne's GitHub App (and thus its webhook secret) can forge a payload whose `repository.owner.login` is `OrgOne` (to pick the correct secret for verification) while `repository.full_name` names a repository belonging to `OrgTwo`, causing writes against OrgTwo's stacks.

### Finding Description
`WebhooksController#verify_signature` computes the verifying organization strictly from the incoming payload: [1](#0-0) [2](#0-1) 

`repository_owner` is read via `params.dig('repository', 'owner', 'login')` (or `organization.login`) and used only to pick the `GitHubApp` instance (and therefore the `webhook_secret`) to verify the HMAC signature against (`Shipit.github(organization: repository_owner)` → `lib/shipit.rb#github` / `#github_app_config`) [3](#0-2) . This lookup mechanism, and the fact that multiple orgs can each have distinct secrets, is documented and tested directly in `test/dummy/config/secrets_double_github_app.yml`.

Once the signature check passes, the actual event handlers determine *which repository/stack to act on* using a **different** field from the same body: `repository.full_name`, via `Handler#repository_name` / `Handler#stacks`: [4](#0-3) 

`PushHandler#process` then triggers `stack.sync_github(expected_head_sha: ...)` on every non-archived stack matching that repository/branch [5](#0-4) . `PullRequest::OpenedHandler` similarly resolves `Shipit::Repository.from_github_repo_name(params.repository.full_name)` independently and can auto-provision a review-stack deploy for it [6](#0-5) .

Because HMAC-SHA1 signing only proves "the possessor of the *chosen* org's secret signed this exact byte stream" and does not itself bind `repository.owner.login` to `repository.full_name`'s owner, the engine never checks that the org whose secret validated the signature actually matches the ownership of the repository the handlers subsequently act on. This is the analog to the reported bug class: a value used to compute one binding (`withdrawnRewards`/here: verifying org) is never validated for consistency against the value used to enact the effect (`cumulativeRewardsOf`/here: `repository.full_name`), breaking the equality `organization-that-authenticated == owner(repository-that-is-written)`.

### Impact Explanation
An operator/administrator of one GitHub organization configured on a shared multi-tenant Shipit install (a legitimate, low-privilege position with respect to *other* tenants' repositories) can forge webhook payloads signed with their own org's secret but referencing another tenant's `repository.full_name`. This can trigger `GithubSyncJob`/`sync_github` and auto-provisioning of review stacks (`OpenedHandler`) for repositories/stacks belonging to a completely different organization they have no legitimate access to — an unauthorized cross-organization write/deploy trigger, satisfying the "cross-repository writes" / "unauthorized deploy" Critical impact criterion.

### Likelihood Explanation
Requires: (1) a Shipit instance configured with more than one GitHub organization/app (each with its own `webhook_secret`, a documented and supported configuration — see `test/dummy/config/secrets_double_github_app.yml`), and (2) the attacker controlling one of those orgs' GitHub Apps (a normal, unprivileged position relative to the *other* org). No Shipit session, `ApiClient` token, or GitHub write access to the victim repository is required — only the ability to send an arbitrary HTTP POST with a validly-signed-for-their-own-org body to the shared `/webhooks` endpoint.

### Recommendation
After selecting the organization used for signature verification, re-derive `repository.owner.login` from the same payload and assert it matches the organization whose secret validated the signature (or otherwise validate that `repository.full_name`'s owner segment equals `repository_owner`) before dispatching to any handler. Reject the webhook if there's a mismatch.

### Proof of Concept
1. Configure Shipit with two orgs, `OrgOne` and `OrgTwo`, each with a distinct `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. As an administrator of `OrgOne`'s GitHub App, craft a `push` webhook JSON body:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-controlled-sha>",
     "repository": { "owner": { "login": "OrgOne" }, "full_name": "OrgTwo/victim-repo" }
   }
   ```
3. Compute `X-Hub-Signature: sha1=HMAC-SHA1(OrgOne_webhook_secret, body)`.
4. POST to `/webhooks` with header `X-Github-Event: push`.
5. `WebhooksController#verify_signature` resolves `repository_owner = "OrgOne"`, fetches OrgOne's secret, and the signature verifies successfully [7](#0-6) .
6. `PushHandler#process` resolves stacks via `repository.full_name = "OrgTwo/victim-repo"` and enqueues `sync_github` for OrgTwo's stack [4](#0-3) [5](#0-4)  — a write triggered against `OrgTwo` using only `OrgOne`'s credentials.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
```
