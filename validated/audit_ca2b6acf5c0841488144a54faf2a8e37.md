Found the analog. The critical binding break is in `WebhooksController#verify_signature` versus what `Repository.from_github_repo_name` resolves to when processing the handlers.

### Title
Webhook signature verification key is selected from an unauthenticated payload field, allowing a cross-organization signature substitution to spoof push/status/membership events - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` chooses which GitHub App/organization's `webhook_secret` to verify the `X-Hub-Signature` against by reading `repository.owner.login` (or `organization.login`) directly out of the **unverified** JSON body, before any signature has been checked. [1](#0-0) [2](#0-1) 

### Finding Description
The equality the engine is supposed to enforce is: `organization whose webhook_secret authenticated the request == organization that owns the repository the handlers act on`. Instead, the org used to pick the secret is read from the same untrusted payload that is later used by handlers via `Repository.from_github_repo_name(payload.dig('repository','full_name'))`. [3](#0-2) 

Since Shipit supports multiple GitHub organizations, each configured with its own `webhook_secret` (`Shipit.github(organization: ...)`), an attacker who legitimately controls a webhook secret for **Org A** (e.g., because they administer a GitHub App installed on their own low-trust org that is also configured in this Shipit instance) can craft a payload whose `X-Hub-Signature` is a valid HMAC computed with Org A's secret, while the JSON body's `repository.owner.login` is set to Org A (satisfying `verify_signature`), but the handler-level `repository.full_name` used deeper in the payload for repository resolution can be inconsistent depending on how each handler's parameter schema reads the repository object. Handlers such as `PushHandler`, `StatusHandler`, `MembershipHandler`, and the `PullRequest` handlers all resolve the target `Stack`/`Repository`/`Team` purely by string-matching whatever `full_name`/`login` values appear in the JSON body — there is no re-verification that the resolved repository actually belongs to the organization whose secret was used to authenticate the request. [4](#0-3) [5](#0-4) 

Concretely, this is structurally identical to the Redeemer.sol bug class: an authorization check is performed against one identifier (the organization derived from `repository.owner.login`/`organization.login`), while the actual state-changing action (writes to a `Stack`/`Repository` looked up by `full_name`) is keyed off a different, independently-attacker-controlled field in the same unverified payload. Nothing cryptographically binds "the org whose secret signed this request" to "the specific repository full_name string the handler will act on" other than the attacker's own claim in the JSON body.

### Impact Explanation
If an attacker controls (or compromises) the webhook secret for any one organization/GitHub App configured in `Shipit.github_apps`/`config/secrets.yml`, they can forge webhook deliveries whose signature validates for that org, yet whose payload content (`repository.full_name`, `sha`, `ref`, `after`, team/member data for `membership` events) targets a `Stack`/`Repository`/`Team`/`User` belonging to a *different* organization also configured in the same Shipit instance. This enables cross-repository state writes: triggering `GithubSyncJob`, creating spurious commit statuses, or creating/deleting team memberships for a repository/org the attacker does not control. This matches the "cross-repository writes" Critical impact category from the rules.

### Likelihood Explanation
Requires the attacker to already possess a valid `webhook_secret` for at least one org configured in the multi-tenant Shipit deployment (this is a credential an "unprivileged" GitHub org owner could hold if they were invited to configure their own org's webhook for the same Shipit instance, without any special Shipit privilege). This is plausible in the documented multi-org configuration pattern shown in `test/dummy/config/secrets_double_github_app.yml`, where multiple orgs each have their own independent `webhook_secret`. [6](#0-5) 

### Recommendation
After `verify_signature` succeeds for organization O, handlers must re-verify that `payload.dig('repository','owner','login')` (or `organization.login`) equals O before resolving/mutating any `Stack`/`Repository`/`Team` records, rather than trusting `repository.full_name` independently.

### Proof of Concept
1. Attacker configures/administers a GitHub App on `org-attacker`, which is also registered in this Shipit deployment's `github:` config with its own `webhook_secret`.
2. Attacker computes `sha1=HMAC(webhook_secret_org_attacker, body)` for a `push` payload where `repository.owner.login = "org-attacker"` (so `verify_signature` looks up and validates against `org-attacker`'s secret) but `repository.full_name = "org-victim/some-repo"`.
3. `WebhooksController#verify_signature` passes because the HMAC matches `org-attacker`'s secret. [1](#0-0) 
4. `PushHandler#stacks` resolves `Repository.from_github_repo_name("org-victim/some-repo")` and enqueues `sync_github` for that victim stack, purely based on the unverified `full_name` field. [7](#0-6) 

**Note:** I could not fully verify from the index whether the deployed configuration commonly grants distinct, independently-controlled webhook secrets to mutually-untrusted organizations in practice (this depends on operator configuration in `config/secrets.yml`, not code in scope), so likelihood depends on deployment posture. A Devin session with repo access could confirm this by reviewing all handler classes under `app/models/shipit/webhooks/handlers/**` for cross-checks against the verified organization.
