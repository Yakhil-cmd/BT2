### Title
`StatusHandler#process` writes commit statuses by bare SHA with no repository/stack scoping, letting a status from one repository flip CI state for a commit belonging to another stack - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` and calls `commit.create_status_from_github!(params)` on every match, with no filter on `repository_name`/`stack`. By contrast, sibling handlers (`CheckSuiteHandler`, `PushHandler`) explicitly scope through the base `Handler#stacks` helper, which resolves `Repository.from_github_repo_name(repository_name)` before touching any records. This asymmetry is a genuine binding violation: the invariant "a status for `ci/kubernetes` only affects the repository that authenticated it" does not hold for `StatusHandler`.

### Finding Description
The broken binding: `params.sha (from repository R1's authenticated webhook) == commit.sha` should imply `commit.stack.repository == R1`, but the code enforces no such equality.

- `WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-49) validates the HMAC signature using `Shipit.github(organization: repository_owner)`, i.e., it proves the payload was signed by the GitHub App/webhook secret belonging to the organization named in the payload's own `repository.owner.login`. It does **not** prove, nor is it designed to prove, that the `sha` inside the payload belongs only to that repository - SHAs are content-addressed and can be shared across repositories/forks/stacks.
- `Handler#stacks` (app/models/shipit/webhooks/handlers/handler.rb:32-38) is the sanctioned pattern for scoping any DB read/write to the authenticated repository: `Repository.from_github_repo_name(repository_name)&.stacks`.
- `CheckSuiteHandler#process` (app/models/shipit/webhooks/handlers/check_suite_handler.rb:14-16) and `PushHandler#process` (app/models/shipit/webhooks/handlers/push_handler.rb:13-16) both go through `stacks` before touching commits.
- `StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24) instead does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
This is a raw, unscoped `Commit` lookup across the entire `commits` table, spanning every stack/repository tracked by the Shipit instance.

Exploit flow: an attacker who can legitimately produce a validly-signed `status` webhook for a repository they control (e.g., their own fork/org onto which the app is installed, or a commit whose SHA is shared with a victim stack because of shared git ancestry between a fork and the base repo) sends `context: ci/kubernetes`, an arbitrary `state`, and a `sha` that also exists as a `Commit` row belonging to an unrelated victim stack. `Commit.where(sha: ...)` matches both rows and `create_status_from_github!` is invoked on the victim's commit too, via `add_status` (app/models/shipit/commit.rb:366-386), which can trigger `stack.schedule_merges` and affects `deployable?`/`blocked?` checks used for shipping/merging. If the victim stack has `review_stacks_enabled: true` with `allow_all`, externally-provisioned review stacks execute `shipit.yml` for that stack, so a forced-success status can push the stack toward an unauthorized deploy/merge, or a forced-failure can block it.

Existing guards do not prevent this: `verify_signature` only authenticates which organization signed the payload, not which commits the payload is entitled to mutate; there is no `ExplicitParameters` or model validation constraining `Commit.where(sha:)` to a particular repository; `Repository`/`Stack` validations don't apply here since the query bypasses the `Repository`/`stacks` scoping path entirely.

### Impact Explanation
A payload correctly authenticated for one repository can mutate `Status`/CI state for a `Commit` record belonging to a different, unrelated stack - matching the "payload for one repository mutating another's stack/commit" Critical category. Downstream, `Commit#add_status` can trigger `stack.schedule_merges`, and `deployable?`/`blocked?` feed directly into automatic deploy/merge decisions, so in combination with `review_stacks_enabled: true, allow_all` (which auto-provisions and runs `shipit.yml` for externally-sourced PRs), this can result in an unauthorized ship or block on the victim's stack. The blast radius is bounded by SHA collisions actually existing across stacks (most realistically via shared git ancestry between forks and their upstream, or multiple stacks tracking overlapping repositories/mirrors), so it is not an arbitrary "any repo, any commit" primitive, but it is a real, repeatable cross-tenant write whenever such SHA overlap exists.

### Likelihood Explanation
Requires: (1) attacker access to send a validly-signed `status` webhook for *some* repository tracked by Shipit (achievable per the threat model via forks/PRs on a tracked repo, or CI systems posting statuses on PR head commits), and (2) a `sha` collision between that authenticated repository's commit and a `Commit` row in the target stack - realistic for forked repositories sharing ancestor history, monorepo splits, or repositories that were imported/copied. No secrets, no privileged role, and no signature forgery are needed beyond what a legitimate contributor can already trigger. This is repeatable per matching SHA.

### Recommendation
Scope `StatusHandler#process` the same way as the other handlers: resolve the authenticated repository via `stacks` (i.e., `Repository.from_github_repo_name(repository_name)`) and restrict the commit lookup to `stack.commits.where(sha: params.sha)` (or equivalent join), rejecting/ignoring statuses for commits outside the authenticated repository's own stacks.

### Proof of Concept
Minitest plan (no live GitHub):
1. Create two stacks/repositories, `victim/repo` and `attacker/repo`, each with a `Commit` row sharing the identical `sha` value (simulating shared ancestry).
2. Configure `victim/repo`'s stack with `review_stacks_enabled: true`, `allow_all`, and a required status context `ci/kubernetes`.
3. Build a `status` webhook payload with `repository.full_name = "attacker/repo"`, `sha = <shared sha>`, `context = "ci/kubernetes"`, `state = "success"`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly (bypassing signature verification, as it would already pass for `attacker/repo`).
5. Assert the binding as an explicit equality before/after:
   - Before: `victim_commit.statuses.where(context: 'ci/kubernetes').exists? == false`
   - After: assert this is STILL `false` (i.e., `victim_commit.reload.statuses.pluck(:context)` must not include `ci/kubernetes`) to prove the invariant holds; the current code fails this assertion because `victim_commit.statuses.exists?(context: 'ci/kubernetes')` becomes `true` after step 4, and `victim_commit.stack.reload` shows scheduled merge/deploy behavior it should not have.
