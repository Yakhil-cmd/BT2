### Title
Unbounded decompression during `gh run download` artifact extraction enables zip-bomb disk-exhaustion DoS - ([File: pkg/cmd/run/download/http.go])

### Summary
`downloadArtifact` streams an artifact ZIP response body to disk and then extracts it via `ghzip.ExtractZip`/`extractZipFile` with no cap on the compressed download size, the number of entries, or the decompressed output size per file or in total. An attacker who can get a victim to download an artifact they control (e.g. via a workflow run artifact in a repo, fork, or PR) can craft a highly compressed zip that expands to a very large amount of data on disk, exhausting disk space during `gh run download`.

### Finding Description
The call chain is: `downloadArtifact` ( [1](#0-0) ) reads `resp.Body` into a temp file via `io.Copy(tmpfile, resp.Body)` with no size limit ( [2](#0-1) ), then opens it with `zip.NewReader` and calls `ghzip.ExtractZip(zipfile, destDir)` ( [3](#0-2) ).

`ExtractZip` iterates every entry in the archive and calls `extractZipFile` for each ( [4](#0-3) ). While `destDir.Join(zf.Name)` correctly blocks path-traversal ("Files that would result in path traversal are silently skipped"), there is no check on `zf.UncompressedSize64`, no limit on total bytes written, and no cap on the number of files extracted. The actual write is an unbounded `io.Copy(df, f)` per file ( [5](#0-4) ), where `f` is the decompressing reader from `zf.Open()`. A DEFLATE-compressed file can achieve compression ratios well over 1000:1, so a small downloaded artifact (tens of MB, plausible for a GitHub Actions artifact) can expand to gigabytes or more on disk, or many small files can exhaust an entire filesystem/inode table.

No code in this path (or in `pkg/cmd/run/shared/artifacts.go` where artifacts are listed) enforces a decompressed-size or entry-count budget before or during extraction — the only search hits for size-limiting patterns (`SizeInBytes`, `MaxBytes`, `LimitReader`) are unrelated to this download/extract path (cache list/shared code), confirming no existing mitigation.

### Impact Explanation
This is a disk-exhaustion Denial of Service against the victim's machine when running `gh run download` against an attacker-controlled or attacker-triggered workflow artifact. It does not grant code execution, credential exfiltration, or path traversal (that specific check is present), but it matches the "resource exhaustion via unbounded decompression / zip bomb" DoS class: an unprivileged party (anyone who can trigger a workflow run producing an artifact, e.g. via a PR in a public repo with Actions enabled, or a repo they own that the victim is instructed to download from) can cause the `gh` process to fill the victim's disk.

### Likelihood Explanation
Feasible and repeatable: any GitHub Actions run can upload an artifact (a zip file), and workflow artifacts from forks/PRs on public repos are downloadable by others running `gh run download`. Constructing a highly compressible zip (e.g., a single very large file of repeated bytes) is trivial and deterministic — the DoS is reliably reproduced every time the victim downloads that specific artifact.

### Recommendation
Enforce bounds in the extraction path:
- In `downloadArtifact`, cap the response body size read into the temp file (e.g., via `io.LimitReader` combined with a check that the copy did not hit the limit / reject if `Content-Length` or actual bytes exceed a configurable max).
- In `internal/zip/zip.go`'s `ExtractZip`/`extractZipFile`, validate `zf.UncompressedSize64` against a per-file and cumulative maximum before extraction, and use `io.CopyN`/`io.LimitReader` on the decompressing reader to abort if actual decompressed bytes exceed the declared/allowed size, returning an error and cleaning up partial output.
- Consider also limiting the number of entries extracted.

### Proof of Concept
```go
// internal/zip/zip_bomb_test.go
package zip_test

import (
    "archive/zip"
    "bytes"
    "os"
    "testing"

    ghzip "github.com/cli/cli/v2/internal/zip"
    "github.com/cli/cli/v2/internal/safepaths"
)

func TestExtractZip_NoSizeLimit_AllowsBomb(t *testing.T) {
    var buf bytes.Buffer
    zw := zip.NewWriter(&buf)
    f, _ := zw.CreateHeader(&zip.FileHeader{Name: "bomb.txt", Method: zip.Deflate})
    // Write a highly compressible payload (e.g. 500MB of zero bytes) that compresses to a few KB.
    zero := make([]byte, 1<<20) // 1MB chunk of zeros
    for i := 0; i < 500; i++ {
        f.Write(zero)
    }
    zw.Close()

    zr, err := zip.NewReader(bytes.NewReader(buf.Bytes()), int64(buf.Len()))
    if err != nil {
        t.Fatal(err)
    }

    destDir := t.TempDir()
    abs, _ := safepaths.AbsoluteFromCwd(destDir)

    err = ghzip.ExtractZip(zr, abs)
    // Expect this to succeed today with no error and produce a 500MB file
    // from a payload that was only a few KB on the wire -- demonstrating
    // the lack of any decompressed-size limit.
    if err != nil {
        t.Fatalf("unexpected error: %v", err)
    }

    fi, _ := os.Stat(destDir + "/bomb.txt")
    if fi.Size() < 500*1<<20 {
        t.Fatalf("expected zip bomb to expand fully, got size %d", fi.Size())
    }
}
```
This test (and an equivalent httpmock-based integration test around `downloadArtifact` serving the crafted zip as the artifact response body) demonstrates that the current code path performs no bound-checking and will fully expand an arbitrarily compressed archive to disk.

func ExtractZip(zr *zip.Reader, destDir safepaths.Absolute) error {
	for _, zf := range zr.File {
		fpath, err := destDir.Join(zf.Name)
		if err != nil {
			var pathTraversalError safepaths.PathTraversalError

				continue
			}
			return err
		}

		if err := extractZipFile(zf, fpath); err != nil {

		}
	}
	return nil
}
