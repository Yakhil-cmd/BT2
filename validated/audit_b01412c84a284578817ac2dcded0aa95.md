### Title
Stale relay-chain proxy proof remains usable for up to `MaxStorageRootsToKeep` blocks after revocation - ([File: pallets/remote-proxy/src/lib.rs])

### Summary
`do_remote_proxy` verifies a `RemoteProxyProof::RelayChain` only against membership in `BlockToRoot` (i.e. "is this storage root still retained"), not against whether the proxy is still active at the current time. Because `BlockToRoot` retains up to `MaxStorageRootsToKeep` past storage roots, a delegate whose proxy was already revoked on the relay chain can submit an old proof anchored to a pre-revocation block and still successfully execute `remote_proxy`/`remote_proxy_with_registered_proof`.

### Finding Description
`do_remote_proxy` looks up the caller-supplied `block` in `BlockToRoot` via `roots.binary_search_by(|(b, _)| b.cmp(&block))` [1](#0-0) . If found, it uses the corresponding stored `storage_root` (from when the proxy still existed) to verify a trie proof of the `Proxy::Proxies` entry for `real_remote`, decodes the `ProxyDefinition`s, and matches one where `x.delegate == who` [2](#0-1) . It then only checks `def.delay.is_zero()` before dispatching the wrapped call as `real` [3](#0-2) . There is no check against the *current* relay-chain proxy state — only against whatever root is still retained in `BlockToRoot`, which holds entries going back `MaxStorageRootsToKeep` blocks [4](#0-3) [5](#0-4) . Consequently, if `real` calls `remove_proxy` on the relay chain, the delegate can still submit a proof anchored to any block still present in `BlockToRoot` (pre-revocation) and the extrinsic succeeds.

This is not an unknown oversight in the implementation — it is explicitly documented as an accepted design tradeoff in the pallet's own module docs: "when deleting a proxy at the remote location at X, it will take `MaxStorageRootsToKeep` time until the proxy can not be used anymore... the caller will be able to provide an old proof at which the proxy was still available" [6](#0-5) .

### Impact Explanation
A revoked remote-proxy delegate can continue to dispatch calls as `real` (subject to the proxy's `InstanceFilter`/`proxy_type`) for up to `MaxStorageRootsToKeep` blocks after the relay-chain `remove_proxy` call is observed and applied. Depending on `T::ProxyType`, this can include asset transfers or other privileged actions on behalf of `real`, i.e. unauthorized dispatched calls under a stale/forged-freshness origin. The impact is bounded in time by `MaxStorageRootsToKeep` and bounded in scope by the proxy's configured `ProxyType`/`InstanceFilter`.

### Likelihood Explanation
Preconditions are realistic and require no privileged access: the attacker only needs to have been a legitimate remote-proxy delegate once, and to act within `MaxStorageRootsToKeep` blocks of the real account's `remove_proxy` call. No race condition or timing precision beyond "before the retention window rolls over" is required, so this is fully repeatable within that window on any deployment that enables this pallet. However, the retention window is a chain-configured constant chosen by the runtime maintainers with this known tradeoff in mind, so exploitability is entirely a function of how the operator sets `MaxStorageRootsToKeep` (documented as intentional risk, not concealed).

### Recommendation
Since the fundamental mechanism (verifying against a historical, retained storage root) cannot itself detect a later revocation without an additional signal, mitigations include:
- Reduce `MaxStorageRootsToKeep` to the minimum operationally acceptable value to shrink the exploitation window (as the docs already recommend).
- If feasible, extend `RemoteProxyInterface`/relay-chain state proofs to also carry/verify a "not-revoked" or nonce/generation marker so a subsequently revoked proxy invalidates old proofs immediately rather than waiting out the retention window.
- Consider an explicit revocation-broadcast/relay mechanism (e.g. XCM message or relay-chain event relay) that proactively invalidates cached proofs for a `(real, delegate)` pair once a `remove_proxy` is observed, rather than relying purely on root expiry.

### Proof of Concept
Rust unit test in `pallets/remote-proxy/src/tests.rs`:
1. Set up a relay-chain proxy from `real` to `delegate` and advance parachain blocks so `BlockToRoot` captures a storage root `R0` at block `B0` that includes the proxy definition.
2. On the (mock) relay chain, call `remove_proxy` for `real -> delegate`, then advance blocks so the parachain captures a new storage root `R1` at block `B1` (post-revocation) without yet evicting `R0` from `BlockToRoot` (i.e. `B1 - B0 < MaxStorageRootsToKeep`).
3. Call `Pallet::remote_proxy(delegate_origin, real, None, some_call, RemoteProxyProof::RelayChain { proof: proof_for_B0, block: B0 })`.
4. Assert the call **succeeds** and dispatches `some_call` as `real` — demonstrating the revoked delegate can still act, confirming the documented but exploitable window.
5. Additionally fuzz `MaxStorageRootsToKeep` boundary values and the gap between `B0` and eviction to characterize exactly how long the stale-proof window remains open.

			// Update the block to root mappings.
			BlockToRoot::<T, I>::mutate(|roots| {
				let delete_up_to =
					block.clone().saturating_sub(T::MaxStorageRootsToKeep::get().into());

				while roots.first().is_some_and(|f| f.0 <= delete_up_to) {
					roots.remove(0);
				}

				// We always remove all the old items before, thus there should always be space in
				// the vector.
				let _res = roots.try_push((block, hash));
				debug_assert!(_res.is_ok());
			});
