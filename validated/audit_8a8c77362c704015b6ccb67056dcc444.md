### Title
Unremovable/unfilterable stale delayed receipt causes chunk-processing panic and chain stall - (File: `runtime/runtime/src/congestion_control.rs`)

### Summary
The bug class in the SafEth report is: a fixed, unprivileged-iterated collection (derivatives) contains no mechanism to skip/remove a single malfunctioning member, so one bad entry causes the entire loop (`unstake`) to revert and DoS all users. The closest reachable analog in nearcore is the `DelayedReceiptQueueWrapper::pop`/`receipt_filter_fn` path in chunk `apply`, where a single stale/unmappable delayed receipt in the trie-backed queue is processed via `.unwrap()` calls with no fallback, and — unlike the rest of the receipt pipeline — cannot be skipped, removed, or delayed further. Any account can trigger this by submitting ordinary transactions (global contract deployment + chunk-saturating calls) across a dynamic resharding boundary.

### Finding Description
`DelayedReceiptQueueWrapper::pop` (called every time receipts are processed from the persistent delayed-receipt queue during `Runtime::apply`, reachable from any submitted transaction/chunk) filters delayed receipts by shard using `receipt_filter_fn`: [1](#0-0) 

```rust
fn receipt_filter_fn(&self, receipt: &ReceiptOrStateStoredReceipt) -> bool {
    let shard_layout = self.epoch_info_provider.shard_layout(&self.epoch_id).unwrap();
    let receipt_shard_id = receipt.get_receipt().receiver_shard_id(&shard_layout).unwrap();
    receipt_shard_id == self.shard_id
}
```

This function is called from `pop`, which pops delayed receipts one-by-one from the trie queue during ordinary chunk processing: [2](#0-1) 

The queue is a normal trie-persisted structure populated by any user transaction whose receipts exceed the per-chunk gas/compute limit (see `process_delayed_receipts` in `runtime/runtime/src/lib.rs`), so unprivileged transactions can put arbitrary receipts (including `GlobalContractDistribution` receipts with an embedded `target_shard`) into this queue: [3](#0-2) 

If the receipt's `target_shard`/`receiver_shard_id` cannot be remapped into the *current* shard layout — which the codebase's own regression test explicitly documents can happen "after two resharding generations" — `receiver_shard_id(&shard_layout).unwrap()` panics instead of returning an error. Unlike `SafEth.unstake`, where the fix was to add an enable/disable mechanism per derivative, there is no equivalent "skip and re-delay" or "remove" path for an unmappable delayed receipt here: it is popped, gas/bytes accounting is updated, and then the unwrap panics with no way to leave it in the queue or discard it gracefully.

This exact scenario is anticipated in the repository's own test: [4](#0-3) 

The test comment states directly: "If the vulnerability exists, processing the stale GlobalContractDistribution receipt will panic in `receipt_filter_fn()` when `receiver_shard_id()` fails to remap the old target_shard after two resharding generations," and the test drives exactly this condition (deploy a global contract, saturate the target shard's compute budget so the distribution receipt is pushed into the delayed queue, force two sequential resharding splits of that shard, then let the delayed queue drain) using only ordinary, unprivileged transactions (`tx_deploy_global_contract`, `tx_call` to burn gas).

### Impact Explanation
A panic inside `Runtime::apply` (invoked by every validator during chunk production/chunk application) is not a recoverable `Result` error — it aborts the node process attempting to apply that chunk. If the stale receipt is reached deterministically by all validators applying the same shard, this can cause a chain stall (no chunk producer can successfully apply the chunk containing/following the stale delayed receipt), which matches the "chain stall" acceptance criterion for this analysis. This is reachable purely through user-submitted transactions and a resharding event, with no privileged/validator misbehavior required to trigger it (the resharding event itself is an ordinary protocol-scheduled event once a dynamic-resharding condition, such as force-split configuration or memory thresholds, is met).

### Likelihood Explanation
Reaching this bug requires: (1) dynamic resharding enabled with at least two sequential splits of the same shard, (2) a receipt with an embedded target/receiver shard id (e.g. `GlobalContractDistribution`) being pushed into the delayed-receipt queue and staying there across both resharding boundaries. The repository's own dedicated regression test constructs this exact scenario using only unprivileged transactions and configured dynamic-resharding thresholds, indicating the developers consider this a realistic, previously-unhandled edge case tied to `ReshardingV3`/dynamic resharding, rather than a purely theoretical one. Likelihood depends on whether dynamic resharding (with multiple splits of the same shard in quick succession) is enabled on a live network and whether a fix has already landed for `receiver_shard_id` remapping across multiple resharding generations — this could not be fully confirmed from the available index since `receiver_shard_id`'s implementation in `core/primitives/src/receipt.rs` could not be retrieved (file appears larger than what the index exposes).

### Recommendation
Make `receipt_filter_fn` and its callers (`pop`, `peek_iter`) tolerant of receipts whose target/receiver shard cannot be resolved in the current shard layout: treat unmappable receipts analogous to the SafEth mitigation (an explicit disable/skip mechanism) rather than unwrapping. Concretely, `receiver_shard_id` should return a `Result`, and `receipt_filter_fn`/`pop` should either re-delay the receipt for a later, more-resolved epoch, or route it through a defined fallback shard, instead of panicking. Add explicit unit/integration coverage (beyond the existing test-loop test) asserting that `Runtime::apply` never panics on any delayed receipt regardless of how many resharding generations have elapsed since it was enqueued.

### Proof of Concept
The existing test `test_stale_global_contract_distribution_after_double_resharding` in `test-loop-tests/src/tests/global_contracts_distribution.rs` is a ready-made PoC:
1. Deploy a contract on `user0` (shard `S_A`).
2. Deploy a global contract from `user0`, creating a `GlobalContractDistribution` receipt targeting `S_A`.
3. Continuously submit `burn_gas_raw` calls on `user0`'s shard to saturate its compute budget every block, forcing the distribution receipt into the delayed-receipt queue.
4. Configure dynamic resharding to force-split `S_A` and then force-split it again in a subsequent epoch, so two resharding generations occur while the receipt is still delayed.
5. Stop saturating and let the delayed queue drain; observe whether `Runtime::apply` panics in `receipt_filter_fn` (chain stalls, `head_height < drain_end`) versus the receipt being safely remapped/skipped. [5](#0-4)

    pub(crate) fn pop(
        &mut self,
        trie_update: &mut TrieUpdate,
        config: &RuntimeConfig,
    ) -> Result<Option<ReceiptOrStateStoredReceipt<'_>>, RuntimeError> {
        // While processing receipts, we need to keep track of the gas and bytes
        // even for receipts that may be filtered out due to a resharding event
        loop {
            // Check proof size limit before each receipt is popped.
            if trie_update.trie.check_proof_size_limit_exceed() {
                break;
            }
            let Some(receipt) = self.queue.pop_front(trie_update)? else {
                break;
            };
            let delayed_gas = receipt_congestion_gas(&receipt, &config)?;
            let delayed_bytes = receipt_size(&receipt)? as u64;
            self.removed_delayed_gas =
                self.removed_delayed_gas.checked_add(delayed_gas).ok_or(IntegerOverflowError)?;
            self.removed_delayed_bytes = self
                .removed_delayed_bytes
                .checked_add(delayed_bytes)
                .ok_or(IntegerOverflowError)?;

            // Track gas and bytes for receipt above and return only receipt that belong to the shard.
            if self.receipt_filter_fn(&receipt) {
                return Ok(Some(receipt));
            }
        }
        Ok(None)
    }

#[test]
#[cfg_attr(feature = "protocol_feature_spice", ignore)]
fn test_stale_global_contract_distribution_after_double_resharding() {
    init_test_logger();

    // The fix only works with V3 shard layouts (dynamic resharding).
    // With static resharding, the shard layout doesn't maintain a full split history.
    if !ProtocolFeature::DynamicResharding.enabled(PROTOCOL_VERSION) {
        return;
    }

    let epoch_length: BlockHeightDelta = 10;
    let base_boundary_accounts = create_account_ids(["user2", "user3"]).to_vec();
    let base_shard_layout = ShardLayout::multi_shard_custom(base_boundary_accounts, 3);
    let deploy_user: AccountId = create_account_id("user0");
    let users = create_account_ids(["user0", "user1", "user2", "user3", "user4", "user5"]).to_vec();
    let validators_spec = create_validators_spec(1, 0);
    let clients = validators_spec_clients(&validators_spec);
    let chunk_producer = clients[0].clone();
    let gas_limit = Gas::from_teragas(300);
    let base_pv = PROTOCOL_VERSION - 1;

    // Configure dynamic resharding to force-split two shards sequentially.
    // The first split targets the shard containing deploy_user (user0), so the
    // GlobalContractDistribution receipt becomes stale after two layout transitions.
    let first_split_shard = base_shard_layout.account_id_to_shard_id(&deploy_user);
    let second_split_shard = base_shard_layout.account_id_to_shard_id(&create_account_id("user4"));
    assert_ne!(first_split_shard, second_split_shard);

    let dynamic_config = DynamicReshardingConfig {
        memory_usage_threshold: u64::MAX,
        min_child_memory_usage: u64::MAX,
        max_number_of_shards: 100,
        min_epochs_between_resharding: 1.try_into().unwrap(),
        force_split_shards: vec![first_split_shard, second_split_shard],
        block_split_shards: vec![],
    };

    let genesis = TestLoopBuilder::new_genesis_builder()
        .protocol_version(base_pv)
        .validators_spec(validators_spec)
        .shard_layout(base_shard_layout.clone())
        .epoch_length(epoch_length)
        .gas_limit(gas_limit)
        .add_user_accounts_simple(&users, Balance::from_near(1_000_000))
        .build();
    let base_epoch_config = TestEpochConfigBuilder::from_genesis(&genesis).build();

    let mut dynamic_epoch_config = base_epoch_config.clone();
    dynamic_epoch_config.shard_layout_config =
        ShardLayoutConfig::Dynamic { dynamic_resharding_config: dynamic_config };

    let epoch_config_store = EpochConfigStore::test(BTreeMap::from([
        (base_pv, Arc::new(base_epoch_config)),
        (base_pv + 1, Arc::new(dynamic_epoch_config)),
    ]));

    let mut env = TestLoopBuilder::new()
        .genesis(genesis)
        .clients(clients)
        .epoch_config_store(epoch_config_store)
        .gc_num_epochs_to_keep(5)
        .build();

    // Step 1: Deploy the test contract on user0's account so we can call burn_gas_raw.
    {
        let node = env.node_for_account(&chunk_producer);
        let tx = node.tx_deploy_test_contract(&deploy_user);
        node.submit_tx(tx);
    }
    env.runner_for_account(&chunk_producer).run_for_number_of_blocks(2);

    // Step 2: Deploy a global contract from user0. This creates a
    // GlobalContractDistribution receipt with target_shard = user0's shard (S_A),
    // which is the shard that will be split in the first resharding.
    {
        let node = env.node_for_account(&chunk_producer);
        let code = ContractCode::new(near_test_contracts::rs_contract().to_vec(), None);
        let tx = node.tx_deploy_global_contract(
            &deploy_user,
            code.code().to_vec(),
            GlobalContractDeployMode::CodeHash,
        );
        node.submit_tx(tx);
    }

    // Step 3: Saturate compute on user0's shard every block so that the
    // GlobalContractDistribution receipt (arriving as incoming) gets pushed to
    // the delayed queue and stays there through both resharding events.
    //
    // Each burn_gas_raw call burns slightly more than half the gas limit, so
    // two local receipts exhaust the chunk's compute budget. We submit 3 per
    // block to ensure at least 2 are processed as local receipts.
    let gas_to_burn = gas_limit.checked_div(2).unwrap().checked_add(Gas::from_gas(1)).unwrap();
    let initial_num_shards = base_shard_layout.num_shards();
    let target_num_shards = initial_num_shards + 2; // after two splits

    let start_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };

    // Keep saturating until both resharding events complete. Dynamic resharding has a
    // 2-epoch proposal-to-activation pipeline, so we need enough epochs for both splits.
    let max_saturation_height = start_height + epoch_length * 12;
    let mut both_splits_done = false;
    for target_height in (start_height + 1)..=max_saturation_height {
        // Submit 3 heavy transactions to saturate this block's compute budget.
        {
            let node = env.node_for_account(&chunk_producer);
            for _ in 0..3 {
                let tx = node.tx_call(
                    &deploy_user,
                    &deploy_user,
                    "burn_gas_raw",
                    gas_to_burn.as_gas().to_le_bytes().to_vec(),
                    Balance::ZERO,
                    gas_limit,
                );
                node.submit_tx(tx);
            }
        }
        env.runner_for_account(&chunk_producer).run_until_head_height(target_height);

        // Check if both resharding events have completed.
        let node = env.node_for_account(&chunk_producer);
        let epoch_id = node.client().chain.chain_store().head().unwrap().epoch_id;
        let current_layout = node.client().epoch_manager.get_shard_layout(&epoch_id).unwrap();
        if current_layout.num_shards() >= target_num_shards {
            both_splits_done = true;
            break;
        }
    }
    assert!(both_splits_done, "both shard splits did not complete within the allotted blocks");

    // Step 4: Stop saturating. Let the delayed queue drain.
    // If the vulnerability exists, processing the stale GlobalContractDistribution
    // receipt will panic in receipt_filter_fn() when receiver_shard_id() fails
    // to remap the old target_shard after two resharding generations.
    let current_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };
    let drain_end = current_height + epoch_length * 2;
    env.runner_for_account(&chunk_producer).run_until_head_height(drain_end);

    let head_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };
    assert!(
        head_height >= drain_end,
        "chain stalled at height {}; expected >= {} (likely panicked processing stale receipt)",
        head_height,
        drain_end
    );
}
