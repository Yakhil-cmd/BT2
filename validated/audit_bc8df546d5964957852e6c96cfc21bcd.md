### Title
oscript `is_valid_sig`/`vrf_verify` accept cryptographically weak PEM key curves (secp112r1/r2, secp128r1/r2, sect113r1/r2), enabling forgeable AA authorization - ([File: signature.js])

### Summary
The external report is about phpMyFAQ accepting weak passwords (no minimum strength requirement), which lets an attacker brute-force credentials. The analogous weakness in ocore is that the `validateAndFormatPemPubKey()` function used by the oscript functions `is_valid_sig` and `vrf_verify` accepts a large whitelist of PEM public-key types, including extremely weak elliptic-curve algorithms such as `secp112r1`, `secp112r2`, `secp128r1`, `secp128r2`, and `sect113r1`/`sect113r2` (56–64-bit security levels, breakable by brute force with commodity hardware) as valid "authentication requirements" for AA-based fund release, unless the newer `bPostPemCurvesFix` restriction path is taken.

### Finding Description
`validateAndFormatPemPubKey(pem_key, algo, handle, bPostPemCurvesFix)` in [1](#0-0)  decodes the DER-encoded PEM public key and looks up its OID in `objSupportedPemTypes`, which lists dozens of curves with key sizes as low as 56 hex chars (`secp112r1`/`secp112r2`, 112-bit curve ≈ 56-bit real-world security) and 60/64 hex chars for `sect113r1/r2`, `secp128r1/r2` [2](#0-1) . These weak curves are only rejected when `bPostPemCurvesFix` is true and the type is not in the `objSafePemTypes` allow-list [3](#0-2) [4](#0-3) . Any AA author (or oscript/ojson definition author) can accept a PEM key of these weak curves as an authorization condition via `is_valid_sig(message, pem_key, signature)` or `vrf_verify(seed, proof, pem_key)`, which are directly reachable from AA triggers/formulas as shown in `formula/evaluation.js` [5](#0-4) , and are proven functional in the test suite for weak curves such as secp112r2/secp128r1/secp128r2 [6](#0-5) .

If an AA's payout logic relies on `is_valid_sig`/`vrf_verify` with such a weak curve as the sole authorization gate (e.g., "release funds to whoever submits a valid signature under this PEM public key"), the private key corresponding to a 56–64-bit curve is realistically recoverable by an attacker via brute-force/ECDLP attacks feasible with modern compute resources, allowing them to forge signatures and satisfy the AA's condition without ever holding the legitimate key.

### Impact Explanation
An attacker who breaks a weak-curve key used in such a definition/AA condition can forge a valid signature/proof and satisfy `is_valid_sig`/`vrf_verify`, resulting in unauthorized release of AA-held or address-held funds — directly matching the "concrete unauthorized spending" / "AA fund loss" impact bar. This is a Medium/High-severity cryptographic-strength issue analogous to the weak-password-requirements CWE-521 class: the library permits an inherently insecure authentication credential to be treated as if it were strong.

### Likelihood Explanation
Likelihood depends on AA/definition authors actually choosing to use one of the weak curves (most likely by mistake, copy-paste, or via templates/third-party tools generating keys with the wrong curve), and `bPostPemCurvesFix` not yet protecting old/pre-fix units. Given the large number of weak curves silently accepted and the fact this is an opt-in “fix” gated on `bPostPemCurvesFix`/mci rather than a blanket rejection, the likelihood is moderate — it's a footgun rather than a directly attacker-triggerable bug against arbitrary honest users, but any AA relying on one of these curves is deterministically exploitable once discovered.

### Recommendation
Remove all EC curves with security strength below a safe modern threshold (e.g., under 224-bit, aligning with `objSafePemTypes`) from `objSupportedPemTypes` entirely rather than gating them behind `bPostPemCurvesFix`, or make the `bPostPemCurvesFix` restriction unconditional (not MCI-gated) for `is_valid_sig`/`vrf_verify` so pre-fix units cannot resurrect weak-curve acceptance. Also emit a hard validation error at AA-definition time when a definition references one of the disallowed curves, rather than only at signature-verification time.

### Proof of Concept
1. An AA author writes an oscript condition: `is_valid_sig(trigger.data.message, "<PEM public key using secp112r2>", trigger.data.signature)` and grants a payout when this returns `true`.
2. An attacker who does not hold the corresponding private key runs an ECDLP attack against the 112-bit curve (computationally feasible with today's resources) to recover the private key.
3. The attacker signs an arbitrary `message`/`trigger.data` combination with the recovered key and submits a trigger unit to the AA.
4. `formula/evaluation.js`'s `is_valid_sig` case calls `signature.validateAndFormatPemPubKey` (which accepts the secp112r2 curve, as demonstrated for the equivalent `secp112r2`/`secp128r1` cases in `test/pem_sig.test.js`) and then `verifyMessageWithPemPubKey`, both returning `true`, causing the AA to release funds to the attacker without ever having possessed the legitimate signing key.

function validateAndFormatPemPubKey(pem_key, algo, handle, bPostPemCurvesFix) {

	if (!ValidationUtils.isNonemptyString(pem_key))
		return handle("pem key should be a non empty string");

	//we remove header and footer if present
	var contentAloneB64 = pem_key.replace("-----BEGIN PUBLIC KEY-----", "").replace("-----END PUBLIC KEY-----", ""); 
	
	//we remove space, tab space or carriage returns
	contentAloneB64 = contentAloneB64.replace(/\s/g, "");

	if (contentAloneB64.length > 736) // largest is RSA 4096 bits
		return handle("pem content is too large");

	if (!ValidationUtils.isValidBase64(contentAloneB64))
		return handle("not valid base64 encoding" + contentAloneB64);

	var contentAloneBuffer = Buffer.from(contentAloneB64, 'base64');

	if (contentAloneBuffer[0] != 0x30)
		return handle("pem key doesn't start with a sequence");

//we determine start and length of algo/curve identifiers
	if (contentAloneBuffer[1] <= 0x7F){
		if (contentAloneBuffer[2] != 0x30)
			return handle("pem key doesn't have a second sequence");
		var identifiersStart = 4;
		var identifiersLength = contentAloneBuffer[3];
	} else if (contentAloneBuffer[1] == 0x81){
		if (contentAloneBuffer[3] != 0x30) 
			return handle("pem key doesn't have a second sequence");
		var identifiersStart = 5;
		var identifiersLength = contentAloneBuffer[4];
	} else if (contentAloneBuffer[1] == 0x82){
		if (contentAloneBuffer[4] != 0x30) 
			return handle("pem key doesn't have a second sequence");
		var identifiersStart = 6;
		var identifiersLength = contentAloneBuffer[5];
	} else {
		return handle("wrong length tag");
	}

	//we decode the length of identifiers
	if (identifiersLength != 13 && identifiersLength != 16 && identifiersLength != 19 && identifiersLength != 20)
		return handle("wrong identifiers length" + identifiersLength);

	//we isolate the identifiers
	var contentAloneHex = contentAloneBuffer.toString('hex')
	var typeIdentifiersHex = contentAloneHex.slice(identifiersStart * 2, identifiersStart *2 + identifiersLength *2);

	if (!objSupportedPemTypes[typeIdentifiersHex])
		return handle("unsupported algo or curve in pem key");

	if (bPostPemCurvesFix && !objSafePemTypes.has(typeIdentifiersHex))
		return handle("unsupported curve after pem curves fix MCI");

	if (algo != "any"){
		if (algo == "ECDSA" && objSupportedPemTypes[typeIdentifiersHex].algo != "ECDSA")
			return handle("PEM key is not ECDSA type");
		if (algo == "RSA" && objSupportedPemTypes[typeIdentifiersHex].algo != "RSA")
			return handle("PEM key is not RSA type");
	}

	if (objSupportedPemTypes[typeIdentifiersHex].algo == "ECDSA" && objSupportedPemTypes[typeIdentifiersHex].hex_pub_key_length != (contentAloneHex.length - identifiersStart * 2 - identifiersLength *2 - 8))
		return handle("wrong key length");

	//we add back header and footer
	pem_key =	"-----BEGIN PUBLIC KEY-----" + "\n";
	pem_key += contentAloneB64+"\n";
	pem_key += "-----END PUBLIC KEY-----";
	return handle(null,pem_key);
}
