Confirmed: `StatusHandler#process` [1](#0-0)  never calls `stacks` or `repository_name`. It queries `Commit.where(sha: params.sha)` directly across the entire `Commit` table with no repository scoping, and calls `commit.create_status_from_github!(params)` on every match, regardless of which repository the `status` webhook payload claims to be for.

### Title
StatusHandler#process ignores repository binding entirely, mutating any repo's Commit/Status via sha collision from an unrelated/unknown repository's webhook - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits solely by `sha` with a global `Commit.where(sha: params.sha)` query and never scopes to the `repository` named in the payload, unlike other handlers that use `Handler#stacks` (`Repository.from_github_repo_name(repository_name)&.stacks`) to restrict results to the correct repository's stacks. This means a `status` webhook whose `repository.full_name` does not correspond to any known `Repository` still writes a `Status` row onto whatever `Commit` in the database happens to share that sha, including commits belonging to a completely different, registered repository.

### Finding Description
The binding the handler should enforce is: `repository resolved from payload.repository.full_name == repository owning the Commit that gets mutated`. Tracing `StatusHandler#process` shows this binding is never established: it only does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`, with `params` validated only for `sha`, `state`, `description`, `target_url`, `context`, `created_at`, `branches` — none of which is the repository. The `repository_name`/`stacks` helpers on the base `Handler` class exist and are used by other handlers, but `StatusHandler` overrides `process` and does not call them at all, so `Repository.from_github_repo_name` is never invoked and its `nil` result (for an unknown org) has zero effect on the query. The webhook dispatch path (`verify_signature` / `GitHubApp#verify_webhook_signature`, `drop_unhandled_event`) authenticates that the payload came from a GitHub App installation, but that only proves *a* valid GitHub source sent it — it does not tie the payload's claimed `repository.full_name` to the commit rows being mutated, since `Commit.sha` is not guaranteed unique across repositories/stacks (short SHAs or even coincidental full-sha reuse across unrelated forks/mirrors can collide, and nothing in the schema or handler enforces repository-scoped sha lookup). An attacker who owns any repository can trigger a `status` event (e.g., via GitHub Actions or any integration producing a status callback) with an arbitrary/fabricated `repository.full_name` and a `sha` matching a commit hash they know exists in a targeted Shipit-registered stack, and Shipit will attach a fabricated status/state to that unrelated stack's commit.

### Impact Explanation
This lets an attacker write arbitrary `Status` rows (state, description, `target_url`, context) onto `Commit` records belonging to a repository/stack they do not control and that never authorized the payload's originating repository. Since Shipit's deploy pipeline gates merges/deploys on commit statuses (`Commit#create_status_from_github!` feeds into `Commit#state`, used for merge/deploy readiness checks), this is a payload-for-one-repository mutating another repository's commit/stack record — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." It's repeatable against any known sha in any registered stack and is not limited to a single tenant.

### Likelihood Explanation
The only precondition is that the attacker's own GitHub-connected integration can emit a `status` webhook event to the shared Shipit `/webhooks` endpoint (signed by whatever GitHub App/installation the attacker's own repo uses, since `verify_signature` only checks the payload came from *a* legitimate GitHub source, not that the claimed `repository.full_name` matches the signing installation/repo). The attacker needs to know a target sha (commits are public in open-source stacks or guessable/observable), but no Shipit credentials, session, or team membership are required. This is a low-cost, fully repeatable attack.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup through `stacks` (or otherwise validate that the resolved `Repository` for `payload.repository.full_name` matches the commit's stack) instead of a bare `Commit.where(sha: params.sha)`, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or joining `Commit` to `Stack`/`Repository` and filtering by the resolved repository, so an unregistered or mismatched repository name cannot affect another repository's commits.

### Proof of Concept
Minitest under `test/` (out of scope per rules to author, but conceptually):
1. Create a known `Stack`/`Repository` (e.g. `rails/rails`) with a `Commit` of sha `"abc123..."`.
2. Send a `status` webhook payload with `repository.full_name = "totally/unregistered-org-nobody-knows"` and `sha = "abc123..."`, `state = "success"`.
3. Assert `Repository.from_github_repo_name("totally/unregistered-org-nobody-knows")` is `nil` (left side of the binding is empty).
4. Assert `Commit.find_by(sha: "abc123...").statuses.count` increased and its `state` reflects the payload — mutating the known repo's commit despite the unregistered `repository.full_name`, proving the binding never held.
