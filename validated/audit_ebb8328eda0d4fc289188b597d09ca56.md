### Title
Webhook signature is verified against the payload's `repository.owner.login` while stack-mutating handlers act on the independently-controlled `repository.full_name`, letting any onboarded GitHub organization forge webhooks for other tracked repositories - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to check the HMAC against using `repository.owner.login` (or `organization.login`) taken straight out of the untrusted, attacker-supplied JSON body. Once the signature is accepted, the full raw `params` hash — including a *different*, unrelated `repository.full_name` field — is dispatched unmodified to event handlers, which resolve the target `Stack`/`Repository` solely from `repository.full_name`. Nothing ties the field used to pick the signing secret to the field used to pick the object that gets mutated.

### Finding Description
`verify_signature` computes `repository_owner` from the JSON body itself, then fetches the GitHub App/secret for that organization and verifies the signature with it: [1](#0-0) [2](#0-1) 

The signature check itself just HMAC-compares the raw body against the resolved organization's own `webhook_secret`: [3](#0-2) 

Once `verified` is true, the entire (attacker-controlled) `params` payload is forwarded unmodified to the registered handlers: [4](#0-3) 

Every stack-mutating handler resolves the target repository/stacks from `repository.full_name`, not from `repository.owner.login`: [5](#0-4) [6](#0-5) [7](#0-6) 

The trust binding that should hold is:
`organization whose secret authenticated the request == organization that owns the repository the handler mutates`

Because `repository.owner.login` (used for signature selection) and `repository.full_name` (used for resolving the stack to mutate) are two independent, attacker-controlled JSON keys with no cross-validation, an attacker who legitimately controls a Shipit-onboarded GitHub organization — and therefore knows that org's own `webhook_secret` — can set `repository.owner.login` to their own org (so the signature check passes) while setting `repository.full_name` to `victim-org/victim-repo` (any other repository tracked by the same Shipit instance). The request is accepted as authentic and dispatched with the victim's `full_name`, so the handler acts on the victim's stacks.

This is the direct analog of the reported bug: the field validated by the cheap/authoritative check (`repository.owner.login`, signature) is not the same field the expensive/impactful operation actually acts on (`repository.full_name`, stack lookup) — exactly like `_commit`'s cheap check operating on a different quantity than what `mineGolds` later mints.

### Impact Explanation
This crosses a repository-authorization boundary without any GitHub App private key, GitHub App installation, ApiClient token, or Shipit session: it only requires knowledge of a webhook secret for *any* organization already using this shared Shipit instance (which such an organization inherently possesses since Shipit generates/stores it for them). Using it, the attacker can force `push`, `pull_request`, `check_suite`, and `status`/commit-status webhook processing against arbitrary victim stacks tracked by the instance:
- `PushHandler` enqueues `GithubSyncJob` for a victim stack/branch, which fetches commits from GitHub and appends them to the victim stack, and can also trigger `CacheDeploySpecJob` and lock-on-revert logic — a genuine cross-repository write into another tenant's stack data.
- `PullRequest` handlers can create/unarchive/archive review stacks for a repository the attacker does not control.
- If the victim stack has continuous deployment enabled, forged/manipulated commit/CI state ingested this way can influence which commits are considered deployable, feeding into `ProcessMergeRequestsJob`/continuous delivery.

This is a cross-tenant write achieved purely by exploiting a mismatch between the field checked for authentication and the field used to select the mutated resource, satisfying the "cross-repository writes" impact bar.

### Likelihood Explanation
Any organization legitimately onboarded to a shared/multi-tenant Shipit instance (a routine, unprivileged-relative-to-other-tenants scenario since Shipit is commonly deployed to serve many orgs/repos behind one webhook endpoint) already holds a valid `webhook_secret` for itself. Forging the JSON body's `repository.full_name` while keeping `repository.owner.login` set to their own org requires no special access beyond POSTing to the public `/webhooks` endpoint with a correctly-signed body — something the org can already do legitimately for its own repos. This makes exploitation straightforward for any tenant wishing to attack a co-tenant's stack.

### Recommendation
Bind the verified organization to the resource actually mutated: after `verify_signature` resolves `repository_owner`, require that every handler validate that `payload.dig('repository', 'full_name')` belongs to that same verified organization (e.g., assert `repository.full_name.split('/').first.casecmp(repository_owner) == 0`) before doing any lookup/mutation, and reject the webhook (422) otherwise. Alternatively, look up the `Repository`/`Stack` first, derive the expected owner/org from that resolved repository, and use only that trusted value to select the verification secret — never trust a client-supplied `owner.login` used only for authentication purposes while a different field drives the write path.

### Proof of Concept
1. Attacker owns/administers GitHub org `attacker-org`, which is a legitimate tenant on the shared Shipit instance and therefore knows its own `webhook_secret` (`S_attacker`).
2. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org" }
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC_SHA1(S_attacker, raw_body)` and sends `POST /webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` computes `repository_owner = "attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and successfully verifies the signature using `S_attacker`. [8](#0-7) 
5. `Shipit::Webhooks.for_event('push')` dispatches `params` (with `repository.full_name = "victim-org/victim-repo"`) to `PushHandler`, which resolves `stacks` for `victim-org/victim-repo` and calls `sync_github` on them — mutating a stack the attacker does not own, despite having authenticated only as `attacker-org`.     def verify_webhook_signature(signature, message)
```ruby
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
