### Title
Uncaught null-pointer dereference in `arbiter_dispute_request` handler crashes wallet process - (File: wallet.js)

### Summary
`handleMessageFromHub`'s `arbiter_dispute_request` case reads an arbitrary attacker-specified unit and dereferences its `data` message payload without checking whether the payload field is present. Because this code runs inside an `async` arrow function that is never awaited or `.catch()`-guarded, a thrown `TypeError` becomes an unhandled promise rejection outside of the surrounding synchronous `try/catch` in `doHandle()`, which in default Node.js configurations (unhandled rejections terminate the process since Node 15) crashes the wallet process — the same "malicious message → null-pointer dereference → process crash" bug class as GHSA-8f4f-v9x5-cg6j.

### Finding Description
`handleMessageFromHub` wraps the synchronous execution of `doHandle()` in a `try/catch`: [1](#0-0) 

However, the `arbiter_dispute_request` case dispatches an `async` function via `requestUnit`, which for non-light nodes simply invokes the async callback synchronously and ignores its returned promise: [2](#0-1) 

Inside that async function, after fetching an attacker-chosen `body.unit` from the ledger and locating its `data` message, the code destructures `payload` from `dataMessage` and immediately dereferences a property on it without verifying `payload` is defined: [3](#0-2) 

A `data`-app message can legitimately have `payload_location` other than `"inline"` (e.g. `"none"` for encrypted/private messages, or a message whose payload was pruned), in which case `objUnit.messages` will contain the message object with `payload_hash` but no `payload` field — `dataMessage.payload` is `undefined`. `payload.contacts_hash` then throws `TypeError: Cannot read properties of undefined (reading 'contacts_hash')`.

Because this throw happens asynchronously, inside an unhandled/uncaught promise returned by the arrow function passed to `requestUnit`, it does **not** get caught by the `try { doHandle(); } catch(e) { ... }` wrapper in `handleMessageFromHub` (that catch only covers synchronous exceptions during the initial, synchronous portion of `doHandle()`). The rejection is unhandled, and under default Node.js `--unhandled-rejections` behavior (`throw`, the default since Node 15), an unhandled rejection terminates the process.

### Impact Explanation
Any paired device (a device the wallet already trusts as a correspondent — pairing is required because `arbiter_dispute_request` is not in the list of subjects allowed from non-correspondents in `device.js`) can crash the target wallet/desktop-node/headless-wallet process by:
1. Choosing (or crafting, if it already has one visible on-chain) any unit that contains a `data`-app message whose payload is not inline/present (`payload_location: "none"` or `"uri"`).
2. Sending an `arbiter_dispute_request` message referencing that unit as `body.unit`.

This results in denial of service against the node process handling wallet/hub messages — matching "a network unable to confirm new units" if the crashed process is a full/light node performing other duties, or at minimum loss of wallet availability for the victim. This is the same crash-triggering class described in the external report (CWE-476, uncaught null dereference from an authenticated/paired peer causing a service crash).

### Likelihood Explanation
Likelihood is high for any attacker who is already paired with the victim device (a normal, low-barrier state achieved via pairing codes/QR that arbiters, arbstores, and counterparties routinely exchange). No special privileges beyond being a correspondent device are needed, and the crafted `data` message with `payload_location != "inline"` is trivial to construct or find on-chain.

### Recommendation
Add a guard immediately after destructuring `payload` from `dataMessage`:
```js
const { payload } = dataMessage;
if (!payload)
    return callbacks.ifError("data message has no inline payload");
```
Additionally, wrap the entire `async () => { ... }` callback body in `try/catch` (or attach `.catch()` to the promise returned by `requestUnit`'s callback invocation) so any future unexpected exception inside this asynchronous code path is converted into `callbacks.ifError(...)` instead of an unhandled rejection that can crash the process.

### Proof of Concept
1. Attacker device A pairs with victim wallet device V (standard pairing flow).
2. Attacker publishes (or finds) any accepted unit `U` containing a `data`-app message with `payload_location: "none"` (payload withheld/not inline) — this is valid per unit validation rules and requires no special privilege.
3. Attacker sends V a hub-delivered device message with `subject: "arbiter_contract_offer"`-style pairing not required beyond being a correspondent, `subject: "arbiter_dispute_request"`, and `body.unit = U`, along with other syntactically valid-looking fields (`contract_hash`, `my_address`, `peer_address`, `arbiter_address`, `my_pairing_code`, `peer_pairing_code`, `encrypted_contract`, `amount`, `asset`, `service_fee_asset`, `shared_address`) sufficient to pass the earlier synchronous validation checks up through the decrypted-contract-content check.
4. `storage.readUnit(U)` resolves; `dataMessage` is found; `payload` is `undefined`; `payload.contacts_hash` throws inside the un-awaited async callback.
5. The unhandled promise rejection propagates outside `handleMessageFromHub`'s `try/catch`, crashing the Node.js process running the victim's wallet/node.
