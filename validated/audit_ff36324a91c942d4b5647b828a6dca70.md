### Title
Null pointer dereference in AA primary-trigger processing when the trigger unit's cache entry is invalidated mid-flight - ([File: aa_composer.js])

### Summary
`handleTrigger()` in `aa_composer.js` dereferences `storage.assocStableUnits[trigger.unit].count_aa_responses` without checking whether the lookup returned an object. The same in-memory cache entry can be deleted by `resetMemory()`/`resetStableUnits()` (triggered by a rollback elsewhere) or by `shrinkCache()` while an asynchronous, multi-step trigger-processing pipeline is still using it, mirroring the CVE-2026-5590 pattern where a torn-down/removed connection object is looked up and dereferenced without a null check.

### Finding Description
`handlePrimaryAATrigger()` reads AA triggers from the `aa_triggers` table and, for each one, calls `handleTrigger()`, an asynchronous pipeline (`readUnit` → `updateInitialAABalances` → `evaluateAA` → `sendUnit` → `handleSecondaryTriggers`, etc.) built out of nested callbacks and `async.eachSeries` chains: [1](#0-0) 

Inside `handleTrigger()`, right before formula evaluation, the code checks whether the trigger's own unit already produced an earlier primary response by directly indexing the in-memory cache and reading a property off the result, with no null/undefined guard: [2](#0-1) 

`storage.assocStableUnits[trigger.unit]` is populated when the unit stabilizes and is expected to stay resident while the corresponding trigger is being processed. However, this cache is mutated elsewhere, independent of any particular in-flight `handleTrigger()` call:
- `resetMemory()` (called from `writer.saveJoint()` whenever a write in the *same* AA-processing chain fails, e.g. from a secondary trigger's `validateAndSaveUnit` or a later step) wipes and reinitializes both `assocUnstableUnits` and `assocStableUnits` synchronously: [3](#0-2) [4](#0-3) 
- `shrinkCache()` runs on a periodic `setInterval` and deletes entries from `assocStableUnits` for units whose `main_chain_index` is older than a computed threshold, entirely independent of whether an AA trigger tied to that unit is currently mid-processing: [5](#0-4) 

Because `handleTrigger()`/`handlePrimaryAATrigger()` span multiple DB round-trips, formula evaluation, and nested secondary-trigger dispatch across several event-loop turns, a re-init of `assocStableUnits` (via `resetMemory`) or its shrink-cache eviction can occur between the initial reads that established `trigger.unit` as stable and the deferred, unguarded read at line 1861. When that happens, `storage.assocStableUnits[trigger.unit]` evaluates to `undefined`, and `.count_aa_responses` throws `TypeError: Cannot read properties of undefined`, crashing the node process — analogous to `tcp_backlog_is_full()` dereferencing a NULL pointer derived from stale context after the connection object was torn down.

This is distinct from the defensively-guarded lookup a few lines earlier in the same file, which explicitly throws a descriptive error instead of crashing on an unchecked property access: [6](#0-5) 

### Impact Explanation
A crash in this code path halts AA-trigger processing entirely for the node (it's invoked from `writer.saveJoint()`'s stabilization flow, guarded by the process-wide `handleJoint`/`write` locks), preventing the node from continuing to process new units and stabilize the chain — i.e., "a network unable to confirm new units" if triggered on enough nodes, since AA triggers must be processed before further stabilization can proceed in `writer.js`'s advance-stability loop. This qualifies as Medium severity per the scan rules (node disagreement/inability-to-confirm class), reachable purely by posting an ordinary AA trigger unit (an allowed actor per the rules).

### Likelihood Explanation
Triggering this requires a specific interleaving: an in-flight primary AA trigger whose `trigger.unit` cache entry gets evicted by `resetMemory()` (fired by an unrelated failed AA-chain write within the same trigger's secondary-trigger cascade) or by the periodic `shrinkCache()` sweep while the trigger's own multi-step, asynchronous pipeline is still executing. This is a genuine race but requires specific timing (a concurrent write failure elsewhere in the same trigger chain, or the 5-minute `shrinkCache` interval firing during a slow/queued trigger), making it plausible but not trivially reproducible on demand — consistent with the "AC:H" (high attack complexity) characterization in the source CVE.

### Recommendation
Guard the lookup at `aa_composer.js:1861` the same way `handlePrimaryAATrigger()` already does at line 104-106: fetch `storage.assocStableUnits[trigger.unit]` into a local variable first, and if it is falsy, either re-fetch the unit's props via `storage.readUnitProps()`/`storage.readUnit()` (falling back to the DB) or throw a descriptive error instead of letting the property access throw a raw `TypeError`. More generally, ensure `resetMemory()` and `shrinkCache()` cannot mutate caches for units that have AA triggers currently in flight (e.g., by taking the same mutex/lock that guards `handleAATriggers()`), so cache entries referenced by an active trigger pipeline remain stable for the duration of that pipeline.

### Proof of Concept
1. Post a normal AA trigger unit `U1` to a primary AA `X` such that `X`'s response chain includes at least one secondary AA call that will eventually fail a write (e.g., a secondary AA constructs an invalid unit causing `validateAndSaveUnit` to bubble an error that surfaces through `writer.saveJoint()`'s error branch), which invokes `storage.resetMemory(conn)`: [7](#0-6) 
2. While `handlePrimaryAATrigger(mci, U1, address, ...)` for `X` is still executing subsequent async steps in `handleTrigger()` (e.g., a slow `evaluateAA` call for a large formula, or queued secondary triggers), have `resetMemory()` fire from the failed secondary write (or wait for the periodic `shrinkCache()` at line 2296 of `storage.js` to run if `U1`'s mci is old enough due to processing backlog).
3. Once `assocStableUnits[U1]` is deleted/reinitialized, the still-in-flight call reaches line 1861 in `aa_composer.js` and throws `TypeError: Cannot read properties of undefined (reading 'count_aa_responses')`, crashing the process — the node then fails to complete AA-trigger processing and stabilization for that MCI.
