### Title
`light/execute_getter` previews AA getter values using the unstable chain tip instead of the last stable MC unit, diverging from what the same getter will return during real AA execution - (File: formula/evaluation.js, network.js)

### Summary
The reported bug class is: a read-only "view" function computes state using a different reference point than the write path that actually commits state, so the value shown to callers preparing a real transaction does not match what will actually be used/enforced when the real operation executes. In ocore, the analogous read-only preview path is the `light/execute_getter` network command, which lets *any* unprivileged light client or AA author preview an AA getter's result (e.g. to decide how to construct a trigger unit) without actually posting a trigger.

### Finding Description
AA getters are evaluated by `callGetter()`/`exports.evaluate()`, which derives the MCI used for all `data_feed[[...]]`/`in_data_feed[[...]]` lookups from `objValidationState.last_ball_mci`: [1](#0-0) 

During a real AA trigger (`handleTrigger` via `dryRunPrimaryAATrigger`/`estimatePrimaryAATrigger`), `objValidationState.last_ball_mci` is derived from the trigger unit's actual `last_ball_unit`, i.e., a *stable* main-chain point that necessarily lags behind the current unstable tip: [2](#0-1) 

However, `network.js`'s `light/execute_getter` handler calls `formulaEvaluation.executeGetter`, which in turn calls `executeGetterInState`: [3](#0-2) 

`executeGetterInState` builds its own `objValidationState.last_ball_mci` not from a last-*stable* unit, but from the single most-recent row in the `units` table ordered by `main_chain_index DESC`, which can be an *unstable* unit still subject to reordering/rollback: [4](#0-3) 

Because `callGetter` also passes `stateVars`/`objValidationState` straight into `data_feed`/`in_data_feed` evaluation with `bAA` semantics for including unstable data-feed messages, a getter invoked through `light/execute_getter` can see a materially different (newer, and possibly not-yet-final) `mci` cutoff than the one that will actually be in effect when a real AA response reads the same `data_feed[[...]]` expression at trigger time. This is the direct analog of `viewPrice` reporting the raw feed price instead of the dampened value that `getPrice` would actually apply/commit: the preview function and the "real" execution function share the same formula but diverge in the state snapshot/MCI baseline they operate on.

### Impact Explanation
Any unprivileged caller (AA author, unit poster, or a counter-party constructing a trigger) using `light/execute_getter` to decide a withdrawal amount, a swap threshold, a liquidation-eligible amount, or any other value gated by `data_feed`/`in_data_feed`/state-var reads can be given a value that will not actually hold when the corresponding real AA trigger is posted and processed at its true `last_ball_mci`. This can cause:
- Triggers built around a stale/optimistic preview to bounce (loss of the bounce fee, and DoS-like unusable AA interactions), or
- Triggers that assume a getter-reported price/threshold/eligible amount that no longer matches by the time the trigger becomes primary and executes, causing miscalculated fund transfers, wrong swap ratios, or incorrect liquidation/eligibility computations enforced by the AA's actual bytecode.

This matches the report's core impact category: view functions used to "get on-chain state and prepare values for write calls" returning values inconsistent with what the write path will actually use, causing wrong withdrawal/liquidation amounts or reverts (bounces) in Obyte's analog.

### Likelihood Explanation
`light/execute_getter` is reachable by any peer over the standard network protocol with no authentication or fee, and getters are a first-class, publicly documented AA feature specifically intended to let external actors preview values before submission. Because `readLastStableMcUnit` (stable) vs. "latest unit by mci" (possibly unstable) is a persistent structural difference — not a rare race — the discrepancy is expected to occur routinely whenever the chain tip has advanced past the last stable MCI, which is essentially always during normal operation.

### Recommendation
Make `executeGetterInState` use the same stable-MCI reference as real AA execution, e.g. `storage.readLastStableMcUnitProps`/`readLastStableMcUnit`, instead of "SELECT * FROM units ORDER BY main_chain_index DESC LIMIT 1". This should mirror the behavior in `dryRunPrimaryAATrigger`/`estimatePrimaryAATrigger`, which already correctly derive `mci`/`objMcUnit` from the last *stable* MC unit, ensuring that `light/execute_getter` returns values consistent with what an actual AA trigger execution would compute at the same point in time.

### Proof of Concept
1. Deploy an AA with a getter such as:
```
{
  getters: `
    $get_price = () => {
      data_feed[[oracles='ORACLE_ADDRESS', feed_name='PRICE']]
    };
  `
}
```
2. Have the oracle post a new `data_feed` unit with an updated `PRICE` value; this unit becomes part of `assocUnstableUnits`/`assocUnstableMessages` before it stabilizes.
3. Call `light/execute_getter` for `$get_price()` — because `executeGetterInState` uses the latest unit's mci (`SELECT * FROM units ORDER BY main_chain_index DESC LIMIT 1`) rather than the last *stable* mci, and `bAA`/unstable-inclusion semantics let it read the still-unstable data feed, the preview reflects the brand-new price.
4. Post a real trigger unit that relies on this same `$get_price()` getter inside the AA's `messages`/`bounce` logic. Because the real trigger's `last_ball_mci` lags the tip (it references an earlier stable point), the actual AA execution reads the *old* stable price via `data_feed[[...]]`, not the new one seen in step 3.
5. Observe: the value used to compute the transferred/withdrawn amount (or the bounce condition) in the real execution differs from what `light/execute_getter` reported, exactly mirroring the `viewPrice`-vs-`getPrice` divergence in the original report. [5](#0-4) [6](#0-5) [3](#0-2)

function executeGetterInState(conn, aa_address, getter, args, stateVars, assocBalances, cb) {
	if (!cb)
		return new Promise((resolve, reject) => {
			executeGetterInState(conn, aa_address, getter, args, stateVars, assocBalances, (err, res) => {
				err ? reject(err) : resolve(res);
			});
		});
	conn.query("SELECT * FROM units ORDER BY main_chain_index DESC LIMIT 1", rows => {
		var props = rows[0];
		if (!props) {
			if (!conf.bLight)
				throw Error("no last unit");
			props = {
				main_chain_index: 1e9,
				unit: 'dummyforgetter',
			};
		}
		let objValidationState = {
			last_ball_mci: props.main_chain_index,
			last_ball_timestamp: Math.round(Date.now() / 1000),
			mc_unit: props.unit, // must not be used
			assocBalances: assocBalances,
			number_of_responses: 0, // must not be used
			arrPreviousAAResponses: [],
		};
		// remove the trailing null/undefined as these types don't exist in oscript
		while (args.length && (args[args.length - 1] === null || args[args.length - 1] === undefined))
			args.length--;
		args = args.map(replaceNulls);
		args = args.map(toOscriptType);
		callGetter(conn, aa_address, getter, args, stateVars, objValidationState, [], '', undefined, (err, res) => {
			if (err)
				return cb(err);
			cb(null, toJsType(res));
		});
	});
}

function executeGetter(conn, aa_address, getter, args, cb) {
