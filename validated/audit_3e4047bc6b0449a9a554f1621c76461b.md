### Title
Cross-organization commit-status forgery via webhook signature scoped to payload's own `repository`/`organization` field, not to the actual `Commit`/`Stack` acted on - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to verify a webhook using an organization value read from the same untrusted request payload (`repository.owner.login`, falling back to `organization.login`), and only proves that *some* configured GitHub App/organization's secret matches. `Shipit::Webhooks::Handlers::StatusHandler`, which the `status` event dispatches to, never re-checks that the commit being mutated (`Commit.where(sha: params.sha)`) actually belongs to a stack whose repository's owner is that same authenticated organization. The equality that should hold — `organization whose secret verified the payload == organization owning the repository/commit written to` — is never enforced.

### Finding Description
`verify_signature` computes `repository_owner` from the JSON body itself and uses it purely to pick which configured GitHub App's `webhook_secret` to check the signature against: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the per-organization app config (each configured org can have its own `webhook_secret`, as shown in the multi-org example config): [3](#0-2) 

Signature verification itself only checks the HMAC of the raw payload against that org's secret — it says nothing about which repository/commit the payload's other fields describe: [4](#0-3) 

Once verification passes, `WebhooksController#create` dispatches the entire attacker-controlled JSON body to the registered handler for the event, with no additional scoping: [5](#0-4) 

For `status` events, the handler is `StatusHandler`, whose `process` looks up commits **only by `sha`**, globally across the whole Shipit installation, with no relation to `repository`/`organization` at all: [6](#0-5) 

Contrast this with the base `Handler` class, which *does* provide a `stacks`/`repository_name` scoping helper used by other handlers (e.g. `PushHandler`, `PullRequest::EditedHandler`), but `StatusHandler` does not use it: [7](#0-6) [8](#0-7) 

`Commit#create_status_from_github!` writes the forged status and, critically, feeds directly into deploy-gating logic: `deployable?` and `blocked?` both key off the commit's `status`, and a passing status can trigger `schedule_continuous_delivery`, which schedules an actual continuous-deployment job for the stack: [9](#0-8) [10](#0-9) [11](#0-10) 

**Before the attack (equality that should hold):** `organization authenticated by webhook signature == organization owning the stack/commit written by the handler`.

**After the attack:** An attacker who controls (or has compromised) the GitHub App/webhook secret for *any one* organization configured in this Shipit instance (Org A) can send a `status` webhook with `repository.owner.login = "org-a"` (so `verify_signature` passes using Org A's secret) but `sha` set to a commit SHA belonging to a completely unrelated stack/repository owned by Org B, also hosted on the same Shipit instance. `StatusHandler` will happily attach a forged `success` status to Org B's commit, because it never checks that the commit's `stack.repository.owner` matches the organization that authenticated the request.

### Impact Explanation
This breaks the repository/organization trust boundary explicitly called out in the rules ("an organization that authenticated versus the repository that is written"). Forging a passing CI status for a commit in a repository/organization the attacker does not control can: (a) unblock `deployable?`/`blocked?` checks used by manual deploys, and (b) trigger `schedule_continuous_delivery` for continuous-deployment-enabled stacks, causing an unauthorized deploy of that other organization's code. This maps to the "Critical - unauthorized deploy" impact tier, since it requires no repository write access, no Shipit session, and no privileged account — only possession of a webhook secret for any one org configured on the shared Shipit instance, which is a materially weaker credential than access to the target org.

### Likelihood Explanation
This is a Shipit-instance-hosts-multiple-organizations scenario, which is an explicitly documented and supported configuration (`config/secrets.development.example.yml` shows the multi-org schema). Any organization's Shipit GitHub App webhook secret is a moderately-privileged secret (used only to sign webhook deliveries), and it is plausible for it to leak or be misconfigured independently of the target organization's own GitHub credentials. Exploitation requires only crafting a JSON POST with a valid HMAC using the known secret — no other authentication, TLS interception, or social engineering.

### Recommendation
In `StatusHandler#process` (and any other handler that queries global tables like `Commit` purely by attacker-supplied identifiers such as `sha`), scope the lookup through the repository/organization that was actually used to verify the signature — e.g., join through `stack.repository` and assert `stack.repository.owner == repository_owner` (or pass the verified organization down from the controller and filter `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { owner: verified_organization })`). More generally, every webhook handler that mutates state should re-derive its target `Stack`/`Repository` from the same organization value that `verify_signature` used, rather than trusting unrelated payload fields (like bare `sha`) to select records without an organization check.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` and `org-b`, each with its own `webhook_secret` (per the multi-org schema in `config/secrets.development.example.yml`).
2. Attacker obtains/knows `org-a`'s `webhook_secret` (e.g., a low-security or externally-facing app for org-a) but has no access to `org-b`.
3. Attacker identifies a pending/failing commit SHA on a stack belonging to `org-b` (SHAs are often public, e.g., visible on GitHub or leaked via logs).
4. Attacker crafts a `status` event JSON payload:
   ```json
   {
     "sha": "<org-b-commit-sha>",
     "state": "success",
     "context": "ci/forged",
     "repository": { "owner": { "login": "org-a" } }
   }
   ```
5. Attacker computes `X-Hub-Signature: sha1=<hmac>` over the raw body using `org-a`'s `webhook_secret` and POSTs to `/webhooks` with `X-Github-Event: status`.
6. `verify_signature` calls `Shipit.github(organization: "org-a")` and successfully verifies the signature against `org-a`'s secret. [12](#0-11) 
7. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and finds the `org-b` commit purely by SHA, then calls `create_status_from_github!`, marking it successful — with no verification that `org-b`'s commit had anything to do with `org-a`'s authenticated webhook. [6](#0-5) 
8. If `org-b`'s stack has `continuous_deployment?` enabled, `schedule_continuous_delivery` fires and an unauthorized deploy of `org-b`'s code is triggered.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
