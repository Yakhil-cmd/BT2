### Title
Webhook organization-selection field is decoupled from the repository field acted on by event handlers, breaking the "authenticated organization = written repository" binding - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects the GitHub App/webhook secret used to validate `X-Hub-Signature` based on `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (or `organization.login`) — a value taken from the *payload itself* [1](#0-0) [2](#0-1) . In multi-organization deployments, each organization has its own `webhook_secret` looked up via `Shipit.github_app_config(organization)` [3](#0-2) . Once signature verification passes for the organization implied by `repository.owner.login`, the full unvalidated `params` hash is handed to every registered handler, and handlers such as the pull-request handlers resolve the actual target `Repository`/`Stack` from a *different* field, `params.repository.full_name` [4](#0-3) [5](#0-4) .

### Finding Description
The binding that should hold is: **organization whose secret validated the signature == owner of the repository the handler mutates**. Concretely:

1. `verify_signature` computes `repository_owner` from the JSON body (`repository.owner.login`, falling back to `organization.login`) and uses it to pick which `GitHubApp`/`webhook_secret` to verify the HMAC against [6](#0-5) .
2. After verification succeeds, `create` dispatches the **entire raw payload** to all registered handlers for the event [7](#0-6) .
3. Handlers (e.g. `OpenedHandler`, `ClosedHandler`, `EditedHandler`, `LabelCapturingHandler`, `AssignedHandler`, `ReopenedHandler`, `UnlabeledHandler`) resolve the repository to act on using `params.repository.full_name` via `Shipit::Repository.from_github_repo_name` [8](#0-7)  — a field that is never cross-checked against `repository_owner`.

This means the field that gates which secret is used to authenticate the payload (`repository.owner.login`) is not the same field that determines which repository's `Stack`/`PullRequest`/review-stack records get archived, unarchived, updated, or provisioned (`repository.full_name`). Since the two fields live in the same attacker-influenced JSON body and are never cross-validated, an entity that legitimately controls a webhook secret for **one** configured GitHub organization (e.g. an org admin who installed their own Shipit-compatible GitHub App per `secrets_double_github_app.yml`) can craft a payload where `repository.owner.login` matches their own org (so their own known secret produces a valid `X-Hub-Signature`), while `repository.full_name` names a repository belonging to a **different configured organization**. The signature check passes because it was computed against the attacker's own org's secret, but the handler acts on a repository the attacker does not control.

### Impact Explanation
If exploited, this allows an attacker who administers Webhook delivery for one configured GitHub organization to trigger state changes (archiving/unarchiving review stacks, updating pull-request metadata, provisioning review stacks) against `Stack`/`Repository`/`PullRequest` records belonging to a different organization's repositories hosted on the same Shipit instance, without ever possessing that organization's `webhook_secret`. This is a cross-repository write crossing an authentication boundary — a signature meant to authorize actions on repositories under organization A is reused to authorize actions on organization B's repositories, which matches the "cross-repository writes" Critical-impact category defined in scope.

### Likelihood Explanation
This is only exploitable in the multi-organization GitHub App configuration schema (`secrets.github.<org>.webhook_secret`, as documented and tested via `test/dummy/config/secrets_double_github_app.yml`) [9](#0-8) . It requires the attacker to already control a legitimate webhook secret for at least one configured organization (e.g. because they administer their own GitHub App installation pointed at the shared Shipit instance) — this is a lower bar than "requires a Shipit session" or "requires the target's secret," since Shipit is explicitly designed to host multiple independent organizations behind one webhook endpoint, and the org that authenticates is never the org whose repository is asserted to be modified.

### Recommendation
After `verify_signature` succeeds, cross-check that `repository_owner` (the value used to select the verifying secret) matches the owner segment of every repository reference subsequently consumed by handlers (e.g., `params.repository.full_name`'s owner component, or `params.organization.login`). Reject or drop events where these do not match, rather than trusting `repository.full_name` unconditionally in `Repository.from_github_repo_name`.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgOne` and `OrgTwo`, each with its own GitHub App and `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. As an entity that owns/administers `OrgOne`'s GitHub App (and thus knows `OrgOne`'s `webhook_secret`), craft a `pull_request` webhook JSON body where:
   - `repository.owner.login = "OrgOne"` (so `Shipit.github(organization: "OrgOne")` is selected, and the HMAC signed with `OrgOne`'s secret validates).
   - `repository.full_name = "OrgTwo/target-repo"`, `action = "closed"`, and a valid `pull_request.number` matching an existing review stack for `OrgTwo/target-repo`.
3. Send this payload to `POST /webhooks` with `X-Hub-Signature` computed via `OrgOne`'s webhook secret.
4. `verify_signature` passes (organization resolved as `OrgOne`), and `ClosedHandler#process` resolves `repository` via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` → `OrgTwo/target-repo`, then calls `review_stack.archive!` [10](#0-9) , archiving/mutating a stack that belongs to `OrgTwo`, despite the attacker never having `OrgTwo`'s webhook secret.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

**File:** lib/shipit.rb (L170-200)
```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
