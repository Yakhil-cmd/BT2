### Title
Stack-scoped ApiClient tokens can read any stack's CCMenu status, bypassing per-token stack authorization - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController#stack` resolves the target stack from the request path using `Stack.from_param!(params[:stack_id])`, ignoring the `current_api_client.stack_id` scoping that `Shipit::Api::BaseController#stack`/`#stacks` enforces for every other API resource [2](#0-1) [4](#0-3) . As a result, a valid `ApiClient` token that was deliberately created scoped to a single stack (e.g. fixture `here_come_the_walrus`, tested to only see one stack via `/api/stacks`) can be replayed against `/api/stacks/*stack_id/ccmenu` for a completely different stack and will pass permission checks, since `check_permissions!` only verifies the `read:stack` string, not which stack the token is bound to [5](#0-4) .

### Finding Description
This is the same class of bug as the MixinRefunds report: a value that is supposed to gate an action (the price paid / here, the specific `stack_id` an ApiClient token authorizes) is checked at issuance time but a different, attacker-supplied value (the updated key price / here, an arbitrary `params[:stack_id]`) is used at execution time. The binding that should hold is: `stack the token authorizes == stack the controller acts on`. `BaseController#stacks` establishes this invariant for the entire API surface (`stacks_controller.rb`, `tasks_controller.rb`, `deploys_controller.rb`, `hooks_controller.rb`, etc., all inherit `stack` from `BaseController`) [2](#0-1) . `Api::CCMenuController` breaks that invariant by redefining `stack` to bypass the `stacks` scope entirely [4](#0-3) , and its `authenticate_api_client` override only replaces the credential source (URL `token` param instead of Basic Auth) without restoring the stack check [6](#0-5) .

### Impact Explanation
This grants **unauthenticated read of stack state**, matching the High-severity impact category defined by the rules ("unauthenticated read of stack state, task streams or deploy output"). Any holder of a legitimately-issued but narrowly-scoped `ApiClient` token can enumerate CCMenu build status (`lastBuildStatus`, `lastBuildLabel`, `activity`, `webUrl`, lock state) for any stack in the Shipit installation, not just the one the token owner was authorized to see — an unprivileged information-disclosure escalation across stack/tenant boundaries.

### Likelihood Explanation
Exploitation requires only possession of any valid `ApiClient` token with the generic `read:stack` permission (no need for the specific stack's token) and knowledge/guessing of another stack's `stack_id` path parameter (`owner/repo/environment`), which is not itself secret. The `token` query-string parameter is also more exposure-prone (logged in web server / proxy access logs) than the Basic-Auth header used elsewhere in the API.

### Recommendation
Make `Api::CCMenuController#stack` reuse the scoped `stacks` collection instead of calling `Stack.from_param!` directly, e.g. `stacks.from_param!(params[:stack_id])`, so a stack-scoped token cannot resolve any stack outside its own `stack_id`.

### Proof of Concept
1. As an admin, create an `ApiClient` restricted to stack A (`stack_id` set to A, permission `read:stack`) — analogous to fixture `here_come_the_walrus`, which is asserted elsewhere to only see its own stack [7](#0-6) .
2. Using that client's `authentication_token`, call `GET /api/stacks/<owner>/<other-repo>/<env>/ccmenu?token=<token>` for stack B, which the client was never granted.
3. `authenticate_api_client` accepts the token via `ApiClient.authenticate(params[:token])` [6](#0-5) , `require_permission :read, :stack` passes because the client has `read:stack` permission generically [5](#0-4) , and `stack` resolves stack B directly via `Stack.from_param!` [8](#0-7) , returning stack B's CCMenu XML despite the token only being authorized for stack A.
