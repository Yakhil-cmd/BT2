### Title
RAY-denominated position valuation can exceed `i128::MAX` before index caps engage, permanently freezing a market - (File: common/src/rates/scaling.rs)

### Summary
The LXT2 report’s bug class is an integer overflow during size/value calculation. XOXNO Lending has an analogous overflow boundary in its RAY-scaled accounting: `scaled_to_original` computes `scaled_shares * index / RAY` and returns the result as `i128`. A sufficiently large market can reach a state where this product represents more than `i128::MAX`, even though the stored borrow index remains below `MAX_BORROW_INDEX_RAY`. Once that happens, interest accrual panics, and because market entrypoints accrue before mutating, users can no longer withdraw, repay, liquidate, or synchronize the market.

### Finding Description
`accrue_step` converts scaled borrowed and supplied share balances back to their original RAY values before calculating utilization and interest. It calls `scaled_to_original` for both balances at `common/src/rates/simulate.rs:60-61`. `scaled_to_original` is implemented as `scaled.mul(env, index)` at `common/src/rates/scaling.rs:14-15`, and `Ray::mul` delegates to `mul_div_half_up` at `common/src/math/fp.rs:50-52`. `mul_div_half_up` returns `MathOverflow` when the exact quotient cannot fit in `i128` at `common/src/math/fp_core.rs:122-143`.

The borrow-index cap does not prevent this condition. `update_borrow_index` caps the index at `MAX_BORROW_INDEX_RAY`, but only after multiplying the old index by the interest factor at `common/src/rates/index.rs:13-18`. `MAX_BORROW_INDEX_RAY` is `1e36` raw units at `common/src/constants/pool.rs:18-23`, while `i128::MAX` is approximately `1.70e38`. Therefore a market holding around `1e36` scaled shares can overflow the value calculation once the index exceeds roughly `170 * RAY`, long before the `1e9 * RAY` index ceiling.

The production accrual path is `global_sync`, which invokes `accrue_step` for each elapsed chunk at `contracts/pool/src/interest.rs:20-33` and `contracts/pool/src/interest.rs:39-53`. An unprivileged caller can trigger the same calculation through controller `update_indexes(caller, assets)`, which authorizes the caller and forwards the requested `HubAssetKey` list to the pool at `contracts/controller/src/markets.rs:118-125`. The project’s long-horizon harness demonstrates that after this state is reached, `update_indexes`, `withdraw`, and `repay` all fail with `MATH_OVERFLOW` at `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:315-356`.

### Impact Explanation
This is permanent freezing of user funds in the affected `(hub_id, asset)` market. Once `borrowed * borrow_index / RAY` or `supplied * supply_index / RAY` no longer fits in `i128`, every path that first runs `global_sync` reverts. Suppliers cannot withdraw their principal or yield, borrowers cannot repay, liquidators cannot liquidate, and subsequent `update_indexes` calls cannot advance the market. The state does not self-heal because the stored scaled balances remain large and the next accrual repeats the same overflowing valuation.

### Likelihood Explanation
The condition requires an extremely large market balance and sustained debt accrual. The in-repository stress scenario uses a one-billion-token, 18-decimal market with approximately 98% utilization and a steep configured rate curve; the test reports that the value ceiling is reached within the tested horizon while the borrow index is still below its cap at `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-356`. The likelihood is therefore constrained by actual token supply, market caps, collateral availability, and configured rate parameters, but it is not dependent on privileged intervention once such a book exists. Any user can call `update_indexes` for the market, and normal user actions such as `supply`, `borrow`, `withdraw`, `repay`, or `liquidate` encounter the same accrual boundary.

### Recommendation
Represent intermediate market valuations in a wider type or clamp them before conversion to `i128`. In particular, `accrue_step` should avoid requiring `scaled_to_original` to return an `i128` when computing utilization and debt growth. The utilization calculation can use an `I256` ratio or compare scaled quantities directly where mathematically equivalent. Debt and supply valuation should either saturate at the protocol’s explicit accounting ceiling or be decomposed so the index cap is enforced before the unrepresentable value is materialized. Add a regression test based on the existing cliff scenario asserting that `update_indexes`, `repay`, and `withdraw` continue to function when the borrow index approaches `MAX_BORROW_INDEX_RAY`.

### Proof of Concept
The repository already contains a deterministic proof in `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` at `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-360`:

1. Configure an 18-decimal market using the steep `xlm_curve` parameters defined at `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:26-39`.
2. Supply `BILLION * 10^18` base units.
3. Supply sufficient separate collateral and borrow approximately 98% of the large market.
4. Advance ledger time in one-year increments and invoke `update_indexes` until it returns `MATH_OVERFLOW`.
5. Observe that the stored borrow index remains below `MAX_BORROW_INDEX_RAY`, while `withdraw` and `repay` also return `MATH_OVERFLOW`.

The failing operation is the conversion in `accrue_step`: `scaled_to_original(borrowed, borrow_index)` overflows before `update_borrow_index` can clamp the index.
