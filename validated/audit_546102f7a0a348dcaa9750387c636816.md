### Title
Stack-scoped API token authorization bypass in CCMenu endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` helper from `Shipit::Api::BaseController` to look up the target stack directly from the global `Stack` model instead of using the token-scoped `stacks` collection, breaking the binding between "the stack a token authorizes" and "the stack it actually reads."

### Finding Description
`Shipit::Api::BaseController` establishes the authorization boundary for scoped API tokens: a token created with a `stack_id` is restricted to only that stack via the `stacks` helper, and `stack` is derived from that restricted collection: [1](#0-0) 

This means, for every other API controller, `ApiClient#stack_id` (if set) is treated as an equality constraint: `token.stack_id == requested_stack.id`, otherwise the lookup returns `nil`/404.

`Shipit::Api::CCMenuController`, however, re-defines `stack` to bypass this scoping entirely: [2](#0-1) 

It calls `Stack.from_param!(params[:stack_id])` — the unscoped `Stack` model — rather than `stacks.from_param!(params[:stack_id])`. The `require_permission :read, :stack` before-action only checks that the token carries the `read:stack` permission string; `ApiClient#check_permissions!` has no notion of *which* stack the permission applies to: [3](#0-2) 

Stack-scoped, read-only tokens are specifically minted by `CcmenuUrlController` for embedding in third-party CI dashboard tools (CCMenu clients), and the fixture data confirms scoped tokens exist with only `read:stack` and a `stack_id` set (e.g. `here_come_the_walrus` scoped to the `shipit` stack): [4](#0-3) [5](#0-4) 

Because `CCMenuController#stack` ignores `current_api_client.stack_id`, any holder of such a scoped token — intended to be embedded/exposed for exactly one stack's CI-dashboard integration — can simply change the `stack_id` request parameter to read the CCMenu XML (build status, last build label/time, activity, lock state) of **any** stack in the Shipit instance, not just the one it was issued for.

### Impact Explanation
This is an authorization-boundary break: `token.stack_id` (what the token is authorized to touch) diverges from `params[:stack_id]` (what is actually served) because the lookup uses the unscoped `Stack` model. This grants **unauthenticated/underauthorized read of stack state** for stacks the token was never authorized to see — exactly the "High" impact category of "unauthenticated read of stack state, task streams or deploy output" callable by anyone in possession of a narrowly-scoped, low-privilege CCMenu token (which is deliberately embeddable/exposed, e.g. in dashboards or query strings, per `CcmenuUrlController` design and `ccmenu_controller_test.rb`'s "can authenticate with query string token" test).

### Likelihood Explanation
High likelihood: no privileged access, no signature forgery, and no session is required — only possession of any valid scoped CCMenu token (which is explicitly designed to be shared/exposed as a URL/query-string token for embedding). Exploitation is a single parameter change (`stack_id`) on an otherwise normal, authenticated API request.

### Recommendation
Change `CCMenuController#stack` to use the scoped `stacks` collection from `BaseController` (i.e., `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so that stack-scoped tokens cannot read data belonging to stacks outside their `stack_id` binding.

### Proof of Concept
1. Create a stack-scoped, read-only API token for `stack_A` via the normal CCMenu URL flow (`CcmenuUrlController#fetch`), yielding an `authentication_token` bound to `stack_A.id`.
2. Send `GET /api/stacks/:stack_id/ccmenu.xml` (or equivalent route mapped to `Api::CCMenuController#show`) with `Authorization` using that token's basic-auth credentials (or `?token=...`), but set `stack_id` to `stack_B`'s id/param instead of `stack_A`.
3. `authenticate_api_client` succeeds (token is valid) and `require_permission :read, :stack` succeeds (token has `read:stack`).
4. `stack` resolves via `Stack.from_param!(params[:stack_id])` → returns `stack_B` regardless of `current_api_client.stack_id == stack_A.id`.
5. Response renders `stack_B`'s CCMenu project XML (build status, last build time/label, activity) — data the token was never authorized to access.
