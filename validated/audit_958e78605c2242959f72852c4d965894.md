### Title
Unicode Homoglyph Spoofing of Asset Display Names via Registry `data` Messages Enables Asset Impersonation - ([File: wallet.js])

### Summary
The asset metadata registration/lookup path in `wallet.js` (`fetchAssetMetadata`/`readAssetMetadata`) accepts an arbitrary `payload.name` string from any address acting as a self-declared "registry" and stores/displays it as the human-readable name of an asset, with no restriction on which Unicode code points are allowed and no confusable-character normalization or detection, analogous to the Chrome Omnibox confusable-character spoofing bug (CVE-2019-5776) where a crafted string visually impersonates a trusted identifier.

### Finding Description
Any address can author a `data` app message declaring itself the metadata "registry" for an asset it also authors, supplying `payload.name` (and optional `payload.suffix`) as the asset's display name. The only checks performed are on `metadata_unit` length, `registry_address` validity, and `decimals`: [1](#0-0) 
`payload.name` itself is only checked for existence (`!payload.name`), never for character set, normalization form, or confusable/homoglyph content, before being written into `asset_metadata.name` and later surfaced to users through `readAssetMetadata`, where it is directly concatenated with `suffix` to build the name shown to the user: [2](#0-1) 
Uniqueness in the `asset_metadata` table is enforced only on the exact byte sequence of `(name, registry_address)`: [3](#0-2) 
This means an attacker can register their own asset under a different `registry_address` using a name built from Unicode homoglyphs (e.g. Cyrillic "Т"/"А" mixed with Latin letters) that renders identically or near-identically to a well-known asset's registered name (e.g. a stablecoin or GBYTE-pegged token name). Because the uniqueness constraint and the hub lookup (`hub/get_asset_metadata`) operate on the raw byte string, two visually indistinguishable names can coexist for two different `asset` hashes, with the `suffix` field being the only disambiguator — and the suffix is not guaranteed to be shown prominently in all UI contexts.

### Impact Explanation
A user relying on the displayed asset name (e.g., in a wallet's asset picker, payment confirmation, or textcoin claim flow) to decide where to route funds or which asset to trust can be deceived into sending real value to, or accepting, an attacker's spoofed asset instead of the legitimate one they intended. This can result in real, unauthorized loss of funds by the deceived party — conceptually identical to the browser user being deceived by a spoofed Omnibox URL into trusting a malicious site.

### Likelihood Explanation
Likelihood is moderate: no special privilege is required — any address can issue an asset and self-declare as its metadata registry with an arbitrary `name`, and Unicode confusables suitable for many Latin-alphabet brand names are widely available and easy to construct, but the attack still requires a human to be shown and to misread the spoofed name in the specific asset-selection/confirmation UI built on top of `readAssetMetadata`.

### Recommendation
Restrict `payload.name`/`suffix` to a constrained, normalized character set (e.g., NFC-normalized ASCII or a vetted allow-list), reject names containing mixed-script confusable characters relative to already-registered names, and enforce name uniqueness using a normalized/confusable-folded comparison instead of raw byte equality when writing to and reading from `asset_metadata`.

### Proof of Concept
1. Attacker issues asset `X` via a normal `asset` definition message, then authors a `data` message (as in `fetchAssetMetadata`, `wallet.js:1458-1473`) with `payload = {asset: X, name: "USDТ"}` where the third character is Cyrillic "Т" (U+0422), visually identical to Latin "T".
2. Because `registry_address` differs from the legitimate USDT registry's address, the `UNIQUE(name, registry_address)` constraint in `asset_metadata` does not block insertion, and no character validation rejects it (`wallet.js:1464-1473`).
3. Victims calling `readAssetMetadata`/`fetchAssetMetadata` for asset `X` see the name rendered as "USDТ" indistinguishable from "USDT" in most fonts, and may select/pay this asset believing it is the legitimate one. [4](#0-3)
