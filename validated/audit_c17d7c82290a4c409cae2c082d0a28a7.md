### Title
Attestor-list update can retroactively freeze already-attested addresses' asset outputs - (File: validation.js)

### Summary
For `spender_attested` assets, spendability of an owner's existing output is not fixed at the time the output was created/attested — it is re-evaluated against the *current* attestor list every time a spend is attempted, analogous to the Arcadia bug where two different risk-parameter snapshots (`minUsdValue`) produce different valuations of the same collateral without any re-validation/health-check being performed at the point of change.

### Finding Description
When validating a payment that spends an output of an asset with `spender_attested = true`, the code checks that the current owner address is present in the asset's current attestor set: [1](#0-0) 
The attestor list itself can be updated by the asset definer via an `attestor_list` message, checked in `validateAttestorListUpdate`, which only requires that the sender be the asset definer and that the new list be well-formed — there is no requirement that addresses currently holding attested balances remain attested, nor any check of whether removing an address would strand existing funds: [2](#0-1) 
The attestor set used at spend-validation time is read fresh via `storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, ...)`, i.e. it reflects the attestor list as of the *current* transaction's `last_ball_mci`, not as of the time the output was created or last attested. Consequently, a definer can post an `attestor_list` update at any later MCI that removes an address which legitimately holds (and was correctly attested to hold) asset units. That address's existing, previously valid output then fails the `arrAttestedAddresses.indexOf(owner_address) === -1` check on any future spend attempt, exactly the same failure mode described in the report: a state (collateral value / spendability) that was valid under one "registry" (attestor list version A) becomes invalid under a later version B, without any check at the point of the parameter change to protect holders of the pre-existing state.

### Impact Explanation
Funds already legitimately owned under a `spender_attested` asset become permanently unspendable (frozen) the moment the definer updates the attestor list to exclude that address, even though the address never did anything wrong and the funds were validly received earlier. This is a direct AA/asset-holder fund-freezing bug reachable by any two counterparties of a private/attested asset plus the asset's definer issuing a routine attestor-list update — no special privilege beyond being the asset definer (a normal, expected on-chain action) is required to trigger the freeze for other addresses.

### Likelihood Explanation
`attestor_list` updates are a normal, documented feature of `spender_attested` assets (used, e.g., for KYC/whitelist-style assets) and can be sent by the definer at any time. Any real-world attested asset whose whitelist changes over time (removals, rotations) will trigger this condition for holders removed from the list, so this is very likely to occur in practice rather than being a purely theoretical edge case.

### Recommendation
Either (a) snapshot/pin the attestor status of an output at the time it is created (store an "attested-at-issuance" flag with the output) rather than re-checking against the live attestor list on every future spend, or (b) require attestor-list updates to not remove addresses that currently hold outstanding balances of the asset, or (c) provide an explicit grace/migration mechanism so holders can move funds before an attestor is removed, mirroring the report's suggested fix of adding a health/validity check at the point where the risk parameters (here, the attestor list) change.

### Proof of Concept
1. Definer issues asset `X` with `spender_attested = true` and attestor list `[A, B]`.
2. Address `A` receives a valid transfer of asset `X` (output recorded, `A` is currently in `arrAttestedAddresses`).
3. Definer later posts an `attestor_list` update (validated only per `validateAttestorListUpdate`) removing `A`, leaving `[B]`.
4. `A` now tries to spend its previously received, legitimately owned output of asset `X`.
5. `validatePaymentInputsAndOutputs` re-reads the asset's current attestor list at `objValidationState.last_ball_mci` and rejects the spend with "owner address is not attested" [3](#0-2) , even though the output was valid and correctly owned by `A` when created — `A`'s funds are now permanently frozen.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
