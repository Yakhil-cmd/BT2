### Title
No exploitable bypass of max-actions-per-receipt / max-receipt-size via `append_action_function_call_weight` - (File: runtime/runtime/src/ext.rs)

### Summary
The reported attack requires that receipts built by repeatedly calling `promise_batch_action_function_call_weight` (which forwards to `RuntimeExt::append_action_function_call_weight` -> `ReceiptManager::append_action_function_call_weight`) escape action-count and receipt-size limits. In this codebase, every newly created receipt — including those built entirely inside `ReceiptManager` from host-function calls — is run through `validate_receipt`/`validate_actions_with_mode`, which enforces `max_actions_per_receipt` and `max_receipt_size` before the receipt is merged into results or forwarded, so the described bypass path is closed.

### Finding Description
`ReceiptManager::append_action_function_call_weight` itself performs no bound checking; it just pushes a `FunctionCallAction` and records a gas-weight entry [1](#0-0) . However, after a `FunctionCall` action finishes executing and its `ReceiptManager` is drained into concrete `Receipt`s [2](#0-1) , the runtime's action-execution loop validates every newly produced receipt with `validate_receipt(..., ValidateReceiptMode::NewReceipt)` before merging results [3](#0-2) . `validate_receipt` checks the receipt's serialized `max_receipt_size` in `NewReceipt` mode [4](#0-3)  and, via `validate_action_receipt` -> `validate_actions_with_mode`, rejects any receipt whose action count exceeds `limit_config.max_actions_per_receipt` [5](#0-4) [6](#0-5) . If this validation fails, the whole action is turned into an `ActionErrorKind::NewReceiptValidationError`, so no oversized receipt is ever forwarded to `receipt_sink`/cross-shard delivery. Additionally, `distribute_gas`'s weighted split uses `u128` intermediate arithmetic and `checked_add`/`ok_or(IntegerOverflowError)` rather than raw addition, so it returns an error instead of panicking on overflow [7](#0-6) . Consequently, an attacker cannot grow a single receipt's action list past `max_actions_per_receipt` (100 in current configs) or past `max_receipt_size`, and gas-weight distribution over that bounded action count cannot panic from unbounded growth.

### Impact Explanation
Not applicable — the invariant the question worries about (bounded action count / receipt size before forwarding or gas-weight distribution) is already enforced by `validate_receipt`/`validate_actions_with_mode`, so there is no chunk-halting panic, OOM, or forwarding-path compromise achievable through this call sequence.

### Likelihood Explanation
Not applicable — the described precondition ("the receipt/action count itself may not be separately bounded in ext.rs") is true only for `ext.rs`/`ReceiptManager` in isolation; the bound is enforced one layer up in `runtime/runtime/src/lib.rs`'s per-action result validation, which runs unconditionally for every new receipt regardless of how many host calls produced it.

### Recommendation
No fix needed for this specific path. If defense-in-depth is desired, an early check inside `ReceiptManager::append_action_function_call_weight` (or `append_action`) comparing the current action count against `limit_config.max_actions_per_receipt` before appending could avoid wasted work on invalid receipts, but this is an optimization, not a security fix, since the existing post-hoc validation already prevents the invariant violation from taking effect.

### Proof of Concept
Not applicable (no vulnerability). For confirmation, an integration test could call `promise_batch_action_function_call_weight` more than `max_actions_per_receipt` times in a single contract execution and assert that the produced `ActionResult` contains `ActionErrorKind::NewReceiptValidationError(ReceiptValidationError::ActionsValidation(ActionsValidationError::TotalNumberOfActionsExceeded { .. }))`, confirming the receipt is rejected rather than forwarded, using the existing test scaffolding in `runtime/runtime/src/action_validation.rs::test_validate_actions_num_actions` [8](#0-7)  as a template applied at the receipt level.
