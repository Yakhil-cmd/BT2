## Title
AA state-update formula executes independently of payment output computation, allowing debt/balance accounting to diverge from the matched asset transfer — ([File: aa_composer.js])

### Summary
The reported Zentra Finance bug was an accounting split in `repayWithATokens`, where the debt-reduction path could complete while the paired token-burn path was independently reduced to zero, letting an attacker record a "repayment" without actually returning value. Autonomous Agents (AAs) in ocore have a structurally analogous split: the `state` message (which updates persistent `state vars`, e.g. a debt/balance ledger) is evaluated and committed by `executeStateUpdateFormula` completely independently from the `payment` messages that carry the real asset outputs. If the two formulas (state-var update vs. output amount) are not kept perfectly in sync by the AA author — e.g. because an amount formula rounds/filters to zero while the paired state formula still decrements a "debt" or increments a "repaid" variable — the AA's internal accounting and its real balance diverge, exactly like the debt-vs-burn mismatch in the reported incident.

### Finding Description
When a trigger is processed, `handleTrigger` evaluates the AA template and then filters the resulting `messages` array, dropping any payment message whose outputs became empty: [1](#0-0) 

Critically, the comment on line 1873 states the intended (but dangerous) behavior explicitly: *"eat the received coins and send no response, state changes are still performed"* — i.e., `handleSuccessfulEmptyResponseUnit` is invoked, and the previously-parsed `state` formula (`objStateUpdate`) is executed via `executeStateUpdateFormula` regardless of whether any real payment output survived filtering: [2](#0-1) 

The same "outputs can vanish independently of state" pattern also happens later in the pipeline: zero-amount outputs are filtered out a second time after amount formulas are evaluated (rounding, `balance[...]` lookups, `trigger.output[[...]]` matching, etc.), and if that empties all messages, the unit is still sent as a state-only response with the recorded state changes intact: [3](#0-2) [4](#0-3) 

Because oscript amount expressions typically use `round()`, division, or conditional `if` clauses on `trigger.output[[...]]`/`balance[...]` (as in the shipped `uniswap_like_market_maker.oscript` sample), an attacker who controls the trigger (amount, timing, or a crafted small/edge-case payment) can force the *output* branch to evaluate to zero or to be filtered out, while the *state* branch — which is evaluated by a separate formula and not required to reference the same intermediate values — still executes and updates the ledger (e.g., `var['mm_asset_outstanding'] -= trigger.output[[asset=$mm_asset]]`, or an equivalent "debt reduced"/"shares burned" variable) exactly as if the real transfer had happened: [5](#0-4) 

This is the same root-cause shape as `repayWithATokens`: two logically-paired effects (a value-transfer effect and an accounting effect) are computed and validated by separate code paths, and the system's design explicitly tolerates the value-transfer path collapsing to zero/empty while still committing the accounting path.

### Impact Explanation
Any lending/vault/AMM-style AA (reachable by an unprivileged trigger sender simply by posting a unit that pays the AA) that keeps a debt, share, or collateral counter in a `state` var separate from the `amount` formula on its `payment` outputs is exposed to permanent desynchronization between recorded state and actual AA balance. This can be exploited to record debt repayment/share burn without delivering the corresponding asset, or to have the AA "eat" received coins while updating internal state as though a transfer occurred — leading to AA fund loss or freezing (funds become unspendable relative to accounting, or an attacker can drain real balance while the ledger shows it should not be possible). This matches the required "AA fund loss or freezing" impact category.

### Likelihood Explanation
This does not require any special privilege — any trigger sender can shape `trigger.output[[...]]`/`trigger.data` amounts to hit rounding/filtering edge cases (e.g., causing `round()` to yield 0, or a `send-all` output to vanish after balance recalculation), and the vulnerable pattern (separate `state` formula vs. `payment.outputs` amount formula) is a normal, documented, and even sample-shipped way of writing AAs (see `uniswap_like_market_maker.oscript`), making the class broadly reachable whenever an AA author's formulas aren't perfectly cross-referenced.

### Recommendation
- Ensure any AA-level "debt reduction" / "shares burned" state update is derived from, or gated on, the *actual* amount that survives output filtering/rounding — not from the same input expression evaluated a second, independent time.
- Consider having `aa_composer.js` expose the post-filter, post-rounding output amounts to the state-update formula context (or re-validate that a state update referencing `trigger.output[...]` matches a message that was not dropped), rather than allowing `executeStateUpdateFormula` (aa_composer.js:1431) to run unconditionally when `messages.length === 0` (aa_composer.js:1873, 1351-1355).
- Document more prominently for AA authors that `state` messages are unconditionally executed even when all payment messages are filtered out, and provide oscript-level guard idioms/tests to catch such divergence.

### Proof of Concept
1. Deploy an AA modeled on `test/samples/uniswap_like_market_maker.oscript`'s "divest MM shares" branch, where the payment `amount` is `round($investor_share * balance[$asset])` and the state update independently does `var['mm_asset_outstanding'] -= trigger.output[[asset=$mm_asset]]`.
2. Send a trigger with a very small `$mm_asset` amount such that `round($investor_share * balance[$asset])` evaluates to `0` for the base-asset/asset output message, causing that message's outputs to be filtered per aa_composer.js:1278/1281.
3. If this empties all payment messages (aa_composer.js:1282-1286) or leaves only messages with 0 outputs after asset resolution (aa_composer.js:1350-1355), the AA still calls `executeStateUpdateFormula` (aa_composer.js:1405/1431), decrementing `mm_asset_outstanding` as though shares were redeemed and assets paid out — while the AA never actually sent out the corresponding value, permanently under/over-crediting the ledger relative to the AA's real coin balance.
