### Title
Cross-repository Status forgery via unscoped `Commit.where(sha:)` in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits by SHA alone, across the entire `commits` table, and writes a `Status` to every match, without ever consulting the `repository` field of the verified payload. Unlike sibling handlers (`PullRequest::OpenedHandler`, etc.) which resolve `Repository.from_github_repo_name(params.repository.full_name)` before acting, `StatusHandler` never calls `Handler#stacks` / `Handler#repository_name`, so a webhook whose signature is only proven valid for repository B can mutate a `Commit`/`Status` row that actually belongs to repository A.

### Finding Description
The binding that must hold is: `repository_name(verified payload) == repository_owner(Commit row mutated)`, i.e. `params.dig('repository','full_name') == commit.stack.repository.full_name`.

`WebhooksController#verify_signature` only proves the HMAC matches the `webhook_secret` configured for `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight from the attacker-controlled JSON body (`params.dig('repository','owner','login')`, see [1](#0-0) ). It proves only "this request was signed with the secret for organization X's GitHub App installation" — it says nothing about which specific repository's data may be touched. Since a GitHub App is normally installed at the organization/app level, every repository in that installation (including a low-value throwaway repo B that the attacker owns) shares the same `webhook_secret`, so the attacker can produce a validly-signed `status` event naming `attacker/B` in the `repository` field while its `sha` matches a commit that also exists (with identical SHA) in tenant repository A.

`StatusHandler#process` then does:
```
Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }
``` [2](#0-1) 

This query is **not scoped by repository/stack at all** — it matches every `Commit` row in the database with that SHA, regardless of which `Stack`/`Repository` owns it, and calls `Commit#create_status_from_github!` (which persists a `Status` via `statuses.replicate_from_github!`, see [3](#0-2)  and [4](#0-3) ) on each of them. Contrast this with the base `Handler` class which explicitly supports repository-scoped lookups via `stacks`/`repository_name`: [5](#0-4) 
and with `PullRequest::OpenedHandler`, which resolves `Repository.from_github_repo_name(params.repository.full_name)` before doing anything: [6](#0-5) 

`StatusHandler` never performs this resolution or filtering step, so the equality above is broken after processing: the payload's verified `repository.full_name` is `attacker/B`, but the `Commit`/`Status` rows actually mutated can belong to `A`'s stack.

Exploit flow: attacker owns repository B (in the same GitHub App installation/organization as the target repo A, or in any org whose webhook_secret they can otherwise obtain by legitimately owning a repo there), triggers/crafts a GitHub `status` webhook body `{sha: <SHA shared with A>, state: 'success', repository: {full_name: 'attacker/B', owner: {login: '<org>'}}}`, signs it with the shared webhook_secret, and POSTs it to `/webhooks`. `verify_signature` passes because the signature is valid for that organization. `StatusHandler#process` then writes a `success` `Status` onto A's `Commit` row.

### Impact Explanation
The attacker can write arbitrary `Status` records (state `success`/`failure`/`error`/`pending`, with attacker-chosen `context`, `description`, `target_url`) onto a commit belonging to a tenant repository/stack they do not own or control, as long as a commit with the same SHA also exists in their own repo. `Status` creation can enable CI on the stack (`enable_ci_on_stack`, [7](#0-6) ), flip a commit's aggregate `status`, and (per `commits_test.rb`) trigger `ProcessMergeRequestsJob`/continuous-delivery scheduling when a commit transitions into `success`, i.e. it can influence auto-merge or deploy-eligibility logic for a repository the attacker never authenticated for. This is a payload for one repository (B) mutating another tenant's commit/status data (A), matching the "Critical" category explicitly listed in the rules ("a payload for one repository mutating another's stack, commit, task or team").

### Likelihood Explanation
Preconditions: (1) attacker owns/controls a repository whose webhook deliveries to the Shipit `/webhooks` endpoint are signed with the same `webhook_secret` as the victim repository — realistic whenever a single GitHub App/organization installation covers multiple repositories, which is the documented multi-org/multi-repo Shipit deployment model (see `docs/setup.md`); (2) a commit with an identical SHA exists in both repo B and repo A's tracked history — plausible for forks/mirrors sharing git history, cherry-picks that preserve tree+metadata, or shared merge-base commits. No Shipit session, API token, or GitHub App private key is needed; the attacker only needs to be able to make a legitimately signed webhook fire (or replicate the signing computation using the shared secret they can observe via their own repo's deliveries) and send/replay a crafted POST to `/webhooks`. This is repeatable against any commit whose SHA collides across tenants.

### Recommendation
In `StatusHandler#process`, resolve the repository from the verified payload the same way other handlers do (`Repository.from_github_repo_name(payload.dig('repository','full_name'))`) and constrain the `Commit` lookup to that repository's stacks (e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or an equivalent scoped query joining through `Stack`/`Repository`), rather than querying `Commit` globally by `sha` alone.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test ":status payload scoped to repo B must not mutate repo A's commit with the same sha" do
  shared_sha = "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"

  repo_a = Shipit::Repository.create!(owner: "tenant", name: "a")
  stack_a = Shipit::Stack.create!(repository: repo_a, environment: "production")
  commit_a = stack_a.commits.create!(sha: shared_sha, message: "shared history", authored_at: Time.now, committed_at: Time.now)

  repo_b = Shipit::Repository.create!(owner: "attacker", name: "b")
  stack_b = Shipit::Stack.create!(repository: repo_b, environment: "production")
  stack_b.commits.create!(sha: shared_sha, message: "shared history", authored_at: Time.now, committed_at: Time.now)

  request.headers['X-Github-Event'] = 'status'
  body = {
    sha: shared_sha,
    state: 'success',
    repository: { full_name: 'attacker/b', owner: { login: 'attacker' } }
  }.to_json

  post :create, body: body, as: :json

  # Binding under test: repository named in verified payload ('attacker/b')
  # must equal the repository owning the mutated Commit row.
  assert_equal 'unknown', commit_a.reload.state,
    "repo A's commit should NOT receive a status from a payload scoped to repo B"
end
```
This test is expected to **fail** against the current `StatusHandler#process`, demonstrating that `commit_a.state` becomes `'success'` even though the verified payload's `repository.full_name` is `attacker/b`, confirming the cross-tenant write.
