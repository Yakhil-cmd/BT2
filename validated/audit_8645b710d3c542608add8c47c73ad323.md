### Title
Permanent market freeze from unchecked accrued-debt multiplication overflow - ([File: common/src/rates/index.rs](common/src/rates/index.rs))

### Summary
A market with very large scaled debt can reach an `i128` value ceiling while calculating accrued interest before the borrow-index cap can protect it. Because every pool mutation calls `interest::global_sync` first, the first overflow permanently blocks repayment, withdrawal, liquidation, bad-debt cleanup, and index synchronization for that market. This is an analog of CVE-2018-11102’s input-triggered denial of service: a reachable arithmetic path traps on a state created through ordinary unprivileged lending operations.

### Finding Description
`update_indexes` loads each requested market and calls `interest::global_sync`, and every normal pool mutation also calls `ops::synced_market`, which performs the same accrual before applying the operation [1](#0-0) [2](#0-1) .

Inside accrual, `calculate_supplier_rewards` computes:

```rust
let old_total_debt = borrowed.mul(env, old_borrow_index);
let new_total_debt = borrowed.mul(env, new_borrow_index);
let accrued_interest = new_total_debt.checked_sub(env, old_total_debt);
``` [3](#0-2) 

`Ray::mul` uses `mul_div_half_up`, which returns `MathOverflow` when the resulting RAY-denominated value does not fit in `i128` [4](#0-3) [5](#0-4) .

Although `update_borrow_index` caps the index at `MAX_BORROW_INDEX_RAY`, that check happens only after multiplying the old index by the new interest factor [6](#0-5) . More importantly, the cap does not prevent `borrowed * index` itself from exceeding `i128`. The in-repository long-horizon test demonstrates that this value overflow occurs while the borrow index is still below `MAX_BORROW_INDEX_RAY`, and that subsequent withdrawal and repayment attempts fail with the same `MATH_OVERFLOW` [7](#0-6) .

The reachable path is:

1. A user supplies collateral through `Controller::supply`.
2. A borrower takes a very large position through `Controller::borrow`.
3. Time elapses while utilization is high.
4. Any caller invokes `Controller::update_indexes`, or any user attempts `repay`, `withdraw`, `liquidate`, or `clean_bad_debt`.
5. `global_sync` reaches `calculate_supplier_rewards` and panics before committing the accrual.
6. Every later operation repeats the same overflowing accrual before it can reduce debt or withdraw collateral.

### Impact Explanation
This permanently freezes all funds in the affected market. Suppliers cannot withdraw, borrowers cannot repay, liquidators cannot liquidate, and bad debt cannot be cleaned because each path synchronizes interest before performing the requested mutation [8](#0-7) .

The impact extends beyond the overgrown borrower: every supplier to that market loses access to the corresponding collateral and yield. Once the state crosses the overflow threshold, there is no ordinary unprivileged escape path because even repayment must first calculate the accrued debt that overflows. The repository’s regression test explicitly verifies that both withdrawal and repayment fail after the condition is reached [9](#0-8) .

### Likelihood Explanation
Likelihood is low under ordinary market sizes because the scaled `borrowed * borrow_index` value must approach `i128::MAX`. However, no malformed host input, privileged call, oracle manipulation, or leaked key is required once a sufficiently large market and sustained borrow position exist. A user can build the state through `supply` and `borrow`, and any unprivileged caller can trigger the terminal accrual through `update_indexes` after enough time has passed [10](#0-9) .

The repository demonstrates the issue at an 18-decimal market with approximately one billion whole tokens, 98% utilization, and sustained high-rate accrual; the test reports failure in fewer than 40 years and shows that the configured index cap does not engage [11](#0-10) . For realistic assets, the required notional size makes exploitation difficult, but the failure is deterministic once the market state enters the unsafe range.

### Recommendation
Prevent accrued-value calculations from panicking before debt can be reduced:

- Bound market supply and debt not only by token count but by the maximum RAY-denominated value representable at the configured index ceiling.
- Compute `borrowed * index` through a saturating or wide-result helper that can distinguish “debt exceeds representable bound” from arithmetic failure.
- Cap `new_borrow_index` early enough that `borrowed * capped_index` remains representable for the stored `borrowed` value.
- Alternatively, store or calculate accrued debt with reduced precision where exact RAY output would exceed `i128`, while preserving conservative rounding.
- Add a market-level invariant asserting `borrowed.mul_ceil(MAX_BORROW_INDEX_RAY)` remains representable, and reject supply, borrow, or parameter changes that would violate it.

### Proof of Concept
The repository already contains a reproduction in `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs`:

```rust
let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);
let debt = principal / 100 * 98;
t.borrow_raw(ALICE, "BIG18", debt);
```

The test advances ledger time and calls `try_update_indexes_for(&["BIG18"])` until accrual returns `MATH_OVERFLOW`. It then verifies:

```rust
assert!(last.borrow_index < MAX_BORROW_INDEX_RAY);
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
``` [12](#0-11) 

This confirms that the index cap is not the operative guard and that the same overflow blocks both supplier exit and borrower repayment.

pub fn mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> i128 {
    // The zero check runs first so debug and release builds agree on a zero
    // divisor: both surface `DivisionByZero` rather than tripping the assert.
    require_nonzero_divisor(env, d);
    debug_assert!(
        x >= 0 && y >= 0 && d > 0,
        "mul_div_half_up: non-negative x, y and positive d"
    );
    try_mul_div_half_up(env, x, y, d)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow))
}

fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {

        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);

    t.supply_raw(BOB, "BIG18", principal);
