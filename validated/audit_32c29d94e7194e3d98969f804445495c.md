### Title
Webhook signing-organization is not bound to the target repository, allowing cross-organization status/push forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / webhook secret to verify a payload against using `repository.owner.login` (or `organization.login`), while every webhook `Handler` (`Shipit::Webhooks::Handlers::Handler#repository_name`) resolves the target `Stack`/`Repository` using a *different* JSON field, `repository.full_name`. Nothing enforces that `repository.full_name` actually belongs to the organization whose secret was used to verify the request. This mirrors the reported bug class: two values that are supposed to be checked together (the authenticating organization and the repository actually acted upon) are validated independently, so a payload can pass verification for org A while writing to a stack that belongs to org B.

### Finding Description
`verify_signature` picks the GitHub App config used for HMAC verification purely from the attacker-supplied payload: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up the per-organization config (each organization can have its own, independently-optional `webhook_secret`, as documented in `docs/setup.md` and shown in `config/secrets.development.shopify.yml`): [3](#0-2) 

`GitHubApp#verify_webhook_signature` explicitly treats a missing secret as "always verified": [4](#0-3) 

Once the signature check passes (or is skipped because the selected organization has no secret configured — an explicitly supported, documented configuration), every handler determines *which repository/stack to act on* using a completely separate field from the same JSON body: [5](#0-4) 

For example `PushHandler` calls `stacks` (i.e. `Repository.from_github_repo_name(payload['repository']['full_name'])`) and immediately triggers a real sync against that repository's GitHub App/token: [6](#0-5) 

`StatusHandler` similarly writes an attacker-controlled CI status (`state`, `context`, `target_url`, `description`) onto any `Commit` matching the attacker-supplied `sha`, without any tie-back to `repository.owner.login`: [7](#0-6) 

The break: **the equality "organization whose secret verified the request == organization that owns the repository being mutated" is never checked.** The verification code only checks `repository.owner.login`/`organization.login`, and the mutation code only checks `repository.full_name` — these are two independent, attacker-supplied strings in the same JSON body, and no code path compares them.

### Impact Explanation
In a multi-organization Shipit deployment (the documented "Using Multiple GitHub Applications" setup in `docs/setup.md`, exemplified by `test/dummy/config/secrets_double_github_app.yml`), if **any single configured organization** has no `webhook_secret` set (explicitly marked optional in every example secrets file: `config/secrets.development.example.yml`, `config/secrets.development.shopify.yml`, `test/dummy/config/secrets_double_github_app.yml`), an attacker can send an unauthenticated POST to `/webhooks` with:
- `repository.owner.login` (or `organization.login`) set to that unsecured org, so `verify_webhook_signature` returns `true` unconditionally, and
- `repository.full_name` set to any *other* tracked repository (belonging to any other, properly-secured organization).

This lets the attacker:
- Trigger `GithubSyncJob`/status/check-suite processing against a stack they have no access to, using Shipit's own privileged GitHub App credentials for the victim repository (`stack.github_app` is derived from the real `Repository#owner` record, not from the forged payload) — a cross-organization/cross-repository write.
- Inject fabricated CI `Status` records (`state: "success"`, arbitrary `context`) onto real commits of the victim repository via `StatusHandler`. Since Shipit's merge queue / deploy gating relies on these `Status` records (`Shipit::StatusChecker`, `MergeRequest#any_status_checks_failed?`), this can be used to make an otherwise-failing or unreviewed change appear CI-green, contributing to an unauthorized merge/deploy decision for a repository the attacker does not otherwise control.

This satisfies the "authentication bypass" / "cross-repository writes" / "unauthorized merge" impact bar, driven by an unprivileged, unauthenticated network request to the public `/webhooks` endpoint.

### Likelihood Explanation
Likelihood is Medium-High in any multi-org deployment: the vulnerable configuration (`webhook_secret` unset for at least one org) is explicitly presented as a supported, optional setting in the shipped documentation and example config files, not an unusual misconfiguration. No credentials, session, or repository access are required to exploit it — only knowledge that the target Shipit instance tracks multiple organizations and the name/owner of one org with no configured secret (discoverable, e.g., from public GitHub App installation pages or trial-and-error).

### Recommendation
- Require that the `repository.owner.login` (and any `organization.login`) used to select the verifying webhook secret is identical to the organization segment of `repository.full_name` before dispatching to handlers, i.e. add an explicit AND-style check binding "verified organization" to "organization actually written to," rejecting the request (422) if they differ.
- Resolve the target `Stack`/`Repository` for GitHub-App-mode installs by cross-checking the repository's stored `owner` against the organization whose secret verified the signature, not solely by `full_name` lookup.
- Consider making `webhook_secret` mandatory (or at least warn loudly / disable multi-org processing) when any configured organization lacks one, since a single unsecured org currently undermines verification guarantees for all other organizations sharing the same `/webhooks` endpoint.
- Add regression tests asserting that a payload verified under organization A cannot cause writes/status updates against a repository whose `full_name` belongs to organization B.

### Proof of Concept
Assume a Shipit instance configured per `docs/setup.md`'s "Using Multiple GitHub Applications" with two orgs: `OrgOne` (no `webhook_secret` set — a documented supported option) and `victim-org` (has a real repo/stack tracked, its own webhook_secret set).

1. Attacker sends, without any `X-Hub-Signature` header:
```
POST /webhooks
X-Github-Event: status

{
  "repository": {
    "owner": { "login": "OrgOne" },
    "full_name": "victim-org/private-repo"
  },
  "sha": "<real sha of an open PR's head commit in victim-org/private-repo>",
  "state": "success",
  "context": "ci/required-check"
}
```
2. `verify_signature` calls `Shipit.github(organization: "OrgOne")`, whose `verify_webhook_signature` returns `true` unconditionally because `webhook_secret` is nil for `OrgOne` (`lib/shipit/github_app.rb:76-77`).
3. Request passes to `StatusHandler#process`, which looks up `Commit.where(sha: params.sha)` — commits belonging to `victim-org/private-repo`'s stacks (resolved independently via `repository.full_name`, `app/models/shipit/webhooks/handlers/handler.rb:36-38`) — and creates a fabricated `success` status on that commit, despite the request never having been verified against `victim-org`'s actual webhook secret.
4. Repeating with `X-Github-Event: push` and a crafted `repository.full_name` pointing at `victim-org`'s repo similarly triggers `GithubSyncJob` for that stack using Shipit's real GitHub App credentials for `victim-org`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
