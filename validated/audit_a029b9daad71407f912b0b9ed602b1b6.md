### Title
Unprivileged senders can permanently bloat an AA's `aa_balances` table, increasing DB/compute cost of every future trigger to that AA - (File: `aa_composer.js`)

### Summary
`updateInitialAABalances()` in `aa_composer.js` inserts a new row into `aa_balances` for every distinct asset an AA has ever received, and never removes rows once created, even when the balance returns to zero. Any unprivileged unit poster can issue arbitrary numbers of distinct assets and send them to a victim AA in tiny amounts, forcing that AA's balance-row set to grow without bound. Because the full row set is read on *every* subsequent trigger, this permanently raises the DB and evaluation cost paid to process any future trigger sent to that AA, mirroring the ParaSpace report's pattern where an unprivileged transfer forces the receiver into a permanently more expensive state.

### Finding Description
When any unit triggers an AA, `handleTrigger()` calls `updateInitialAABalances()`, which loads the AA's balances with: [1](#0-0) 


Any asset that appears in `trigger.outputs` (i.e., any payment output addressed to the AA) and that is not already tracked for that address causes a brand-new row to be inserted into `aa_balances`, exactly analogous to the ParaSpace bug where a transfer to a zero-balance receiver silently flips a persistent flag for them. There is no mechanism in `updateFinalAABalances()` (or elsewhere) that deletes a row once its balance goes back to zero: [2](#0-1) 

Anyone can create a new asset definition cheaply (posting an `asset` message costs only the standard unit fee) and can then send an arbitrarily small, even dust, amount of that asset to any AA address as a payment output. Since `getTrigger()` records any payment output addressed to the AA regardless of amount or the AA's own logic accepting it: [3](#0-2) 

the `SELECT asset, balance FROM aa_balances WHERE address=?` query executed on *every subsequent trigger* to that AA (including one sent by the legitimate AA owner or by any other party) has to scan and return a linearly-growing number of rows as the adversary keeps sending new distinct assets. This directly increases per-trigger DB read cost and downstream processing (building `objValidationState.assocBalances[address]`), for the lifetime of the AA, without any cap on the number of distinct assets that can be forced onto an address.

### Impact Explanation
This does not itself change ledger balances or steal funds, but it degrades the ability of a target AA to process triggers economically. As more attacker-created assets accumulate, the read of `aa_balances` and construction of `assocBalances[address]` grows unbounded, raising the validation cost every node must pay to process every future trigger unit sent to the targeted AA. There is no mechanism to garbage collect zero-balance rows, so the cost is monotonically non-decreasing and can be driven arbitrarily high by a low-cost repeated attack (issue asset + tiny payment), fitting the "growing gas/DoS on the AA itself and on the network validating triggers to it" class described in the source report.

### Likelihood Explanation
High. No special privilege, cosigning, or definition control over the target address is required — any address can post a payment unit with an `asset` issuance message plus a payment output to any AA, and this is a normal, always-valid operation. The cost to the attacker (asset issuance + dust payment fees) is fixed and small per attack unit, while the cost imposed on the network/target AA compounds indefinitely since rows are never pruned.

### Recommendation
- Cap the number of distinct assets that can be tracked in `aa_balances` per address, or reject/ignore payment outputs of an asset the AA has not been previously funded/whitelisted for (require an opt-in via the AA's own definition/state rather than auto-registering any incoming asset).
- Add cleanup logic in `updateFinalAABalances()` (or a periodic housekeeping pass) to delete rows once their balance returns to zero, so idle "dust" assets do not permanently inflate the per-address dataset.
- Consider charging a proportional storage/registration fee for the first time a new asset balance row is created for an address, similar to bounce-fee mechanics, to make the attack economically costly rather than nearly free.

### Proof of Concept
1. Attacker repeatedly posts unit A_i containing an `asset` message defining new asset `X_i` (cheap, standard unit fee) followed by a payment message sending 1 unit of `X_i` to victim AA address `V`.
2. For each unit, `getTrigger()` records `trigger.outputs[X_i] = 1` for `V` (`aa_composer.js:375-397`).
3. `updateInitialAABalances()` finds `X_i` is not an existing asset for `V` and inserts a new row into `aa_balances` (`aa_composer.js:516-524`).
4. No code path ever deletes this row even though its balance stays at `1` (or is later spent to `0`) — see `updateFinalAABalances()` (`aa_composer.js:543-587`), which only updates/upserts, never deletes.
5. Repeating steps 1-3 for N distinct assets causes the `SELECT asset, balance FROM aa_balances WHERE address=?` query in step 3 to return N rows on every future trigger sent to `V`, permanently increasing the DB and evaluation cost paid to process any trigger addressed to `V`, for as long as the AA exists.

```javascript
function getTrigger(objUnit, receiving_address) {
	var trigger = { address: objUnit.authors[0].address, unit: objUnit.unit, outputs: {} };
	if ("max_aa_responses" in objUnit)
		trigger.max_aa_responses = objUnit.max_aa_responses;
	objUnit.messages.forEach(function (message) {
		if (message.app === 'data' && !trigger.data) // use the first data message, ignore the subsequent ones
			trigger.data = message.payload;
		else if (message.app === 'payment' && message.payload) {
			var payload = message.payload;

				if (output.address === receiving_address) {
					if (!trigger.outputs[asset])

					trigger.outputs[asset] += output.amount; // in case there are several outputs
				}
			});
		}
	});
	if (Object.keys(trigger.outputs).length === 0)

}
```

```javascript
			if (!assocDeltas[output.asset])

			// this might happen if there is another pending invocation of our AA that created the outputs we are spending now
			if (!objValidationState.assocBalances[address][output.asset])
				arrNewAssets.push(output.asset);

			if (message.app !== 'payment')

				if (output.address !== address)
```
