### Title
Webhook signature is verified against the organization embedded in `repository.owner.login`, but events are applied to whatever repository is named in `repository.full_name` — a cross-organization webhook forgery ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App / webhook secret to validate the HMAC signature using `repository_owner`, which is read straight from the untrusted JSON body (`repository.owner.login`, falling back to `organization.login`). Every event handler, however, resolves the target `Repository`/`Stack` using a *different* payload field, `repository.full_name`, via `Handler#repository_name`. Because these two fields are never cross-checked against each other, an attacker who legitimately controls a GitHub App/webhook on their own organization can forge a payload whose `repository.owner.login` names their own org (so the signature validates against a secret they know) while `repository.full_name` names an arbitrary victim repository tracked by this Shipit instance.

### Finding Description
- Signature verification: `Shipit.github(organization: repository_owner)` looks up the per-organization webhook secret using `params.dig('repository','owner','login') || params.dig('organization','login')`. [1](#0-0) [2](#0-1) 

- Target resolution: every handler subclasses `Handler`, which resolves the acted-upon `Repository`/`Stack` using an entirely separate field, `repository.full_name`, with no check that its owner matches the `repository.owner.login` used for signature verification. [3](#0-2) 

- Concretely, `PushHandler` finds stacks via `stacks` (which calls `Repository.from_github_repo_name(repository_name)`) and immediately queues a sync against a specific commit SHA, and `StatusHandler` writes a CI status onto any `Commit` matching the given `sha`, both driven purely by `repository.full_name`/`sha`, not by the org used for signature verification. [4](#0-3) [5](#0-4) 

This is the same class of bug as the `keep-tecdsa` report: the property that is verified (the authenticated organization, analogous to the "locked" bond) is not the same property that is subsequently acted on (the repository actually written to, analogous to the bond that gets freed). The equality the code implicitly assumes — `repository.owner.login == owner(repository.full_name)` — is never enforced, so it can be broken by a payload crafted with mismatched fields, exactly as the keep contract assumed `lockedBonds[bondID] > 0` would still hold for every member.

### Impact Explanation
Any party who can stand up their own GitHub organization/App and register it against this Shipit instance's webhook endpoint (which is the standard, low-privilege onboarding flow for any org listed in `Shipit.github` config, or one they compromise) obtains a webhook secret for *that* organization. Using it, they can send a validly-signed webhook whose `repository.full_name` names an unrelated tracked repository/stack. Depending on handler:
- `push` events can trigger `GithubSyncJob`/`sync_github` against victim stacks with attacker-chosen `expected_head_sha`.
- `status` events can write forged CI statuses (`create_status_from_github!`) onto victim commits, which Shipit's merge queue and safety checks rely on to decide whether a commit is deployable/mergeable — directly threatening an unauthorized deploy/merge decision.
- `check_suite`/`membership`/`pull_request` handlers are similarly reachable for the org named in `full_name` despite the signature belonging to a different org.

This matches the "High"/"Critical" bar of escalating into stack state and safety decisions without any legitimate access to the victim repository or its GitHub App installation, since it can push a stack toward an unauthorized deploy/merge/rollback decision.

### Likelihood Explanation
Reachability is high: the request goes straight through the public `WebhooksController#create` unauthenticated endpoint, requires no Shipit session, `ApiClient` token, or repository write access — only that the attacker owns/controls a GitHub organization/App configured to hit this Shipit instance's webhook URL (a normal, expected, unprivileged multi-tenant scenario if this instance serves multiple orgs, or achievable by anyone who can add a webhook pointing here from their own repo). The only work required is crafting a JSON payload with `repository.owner.login` set to the attacker's own org and `repository.full_name` set to the victim's `owner/repo`.

### Recommendation
Derive the organization used for signature verification from the *same* field used to resolve the target repository (`repository.full_name`'s owner segment), or explicitly assert `repository.owner.login == full_name.split('/').first` before dispatching to handlers. Alternatively, verify the signature using a secret bound to the resolved `Repository`/`Stack` record rather than a raw, attacker-supplied field.

### Proof of Concept
1. Attacker owns/operates GitHub org `attacker-org`, which is configured (legitimately) in this Shipit instance's `Shipit.github` config with its own `webhook_secret`.
2. Attacker crafts a `push` payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker signs the raw body with `attacker-org`'s known `webhook_secret` and sends `X-Hub-Signature: sha1=...` plus `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: 'attacker-org')` (from `repository.owner.login`) and validates successfully because the attacker used the correct secret for that org. [1](#0-0) 
5. `PushHandler#process` resolves `stacks` via `repository.full_name` = `victim-org/victim-repo`, and triggers `stack.sync_github(expected_head_sha: params.after)` on the victim stack — a stack the attacker never authenticated against. [6](#0-5) [4](#0-3)
