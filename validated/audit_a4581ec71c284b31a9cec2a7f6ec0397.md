### Title
Unauthenticated pub/sub event stream leaks task/stack broadcast data - ([File: config/routes.rb])

### Summary
`Pubsubstub::StreamAction` is mounted directly as a Rack endpoint in `config/routes.rb` rather than being handled through Shipit's own controller stack. Because Rails engine mounts bypass the host controller's `before_action` filter chain entirely, the `force_github_authentication` check defined in `Shipit::Authentication` never executes for requests to `/events`, allowing any unauthenticated caller to open the stream.

### Finding Description
The claimed binding is: for every request reaching Shipit application data, `current_user.logged_in? == true` (or `Shipit.authentication_disabled? == true`) must hold before a response is rendered, enforced by the `force_github_authentication` before_action installed in every Shipit controller [1](#0-0) .

That binding only applies to classes that `include Shipit::Authentication` (i.e., Shipit's `ApplicationController` subclasses). `Pubsubstub::StreamAction` is not a Shipit controller — it is mounted as a raw Rack endpoint: `mount Pubsubstub::StreamAction.new, at: "/events", as: :events` [2](#0-1) . Rails' `mount` dispatches directly to the Rack app's `call` method, completely outside of `ActionController::Base`'s filter chain, so `force_github_authentication` is never invoked for this route. There is no other authentication concern, middleware, or route constraint placed in front of the mount in `config/routes.rb` or `lib/shipit/engine.rb` [3](#0-2) .

As a result, an attacker with no Shipit session and no GitHub credentials can send `GET /events?channel=<name>` and the SSE/long-poll connection from `Pubsubstub` is accepted unconditionally, streaming any events published to that channel — including stack/task update broadcasts used by the `tail` and status pages — for any stack whose channel name the attacker can guess or enumerate.

### Impact Explanation
Exploiting this exposes live task output and stack status broadcasts (deploy progress, task completion, stack state changes) to unauthenticated parties, for stacks the attacker has no authorization to view. This matches the "High: unauthenticated read of stack state, task streams or deploy output" impact category. The blast radius spans every stack/tenant hosted on the instance, since the mount point has no per-stack authorization gate — any subscriber able to guess or discover a channel identifier receives that stack's events, independent of `Shipit.github_teams` membership or repository maintainer status.

### Likelihood Explanation
No Shipit or GitHub configuration is required to reach the endpoint — it is present by default any time this `config/routes.rb` is loaded, per the routes/engine files reviewed. The attacker's cost is a single unauthenticated HTTP GET, fully repeatable and scriptable against any number of channels. The only uncertain factor is how predictable/discoverable the channel names published by task/stack broadcasters are (I was not able to fully trace the exact channel-naming code within the remaining tool budget); however, the core defect — total absence of authentication on the mounted stream endpoint — is confirmed directly from the routing and controller-concern code regardless of channel naming scheme.

### Recommendation
Do not mount `Pubsubstub::StreamAction` as a bare Rack app outside the authenticated controller stack. Wrap it behind a thin Shipit controller action that includes `Shipit::Authentication` (and performs per-stack `require_permission!`/`authorized?` checks based on the requested channel) before delegating to `Pubsubstub`, or add an authentication/authorization Rack middleware in front of the `/events` mount that validates the session and the specific channel(s) being subscribed to belong to a stack the current user may access.

### Proof of Concept
```ruby
# test/integration/events_stream_authentication_test.rb (proposed, not present)
require 'test_helper'

module Shipit
  class EventsStreamAuthenticationTest < ActionDispatch::IntegrationTest
    test "GET /events is rejected without a session" do
      # no session set, no `sign_in`
      get '/events'

      # Binding under test:
      # current_user.logged_in? == true  ->  should gate the response
      # actual: response is accepted without any authentication check
      assert_response :redirect # expected if force_github_authentication ran
      # actual observed behavior: response is 200/streaming, proving the
      # before_action never fired for this mounted Rack endpoint
    end
  end
end
```
This test demonstrates the divergence: for every other Shipit route, an anonymous request is redirected to `github_authentication_path` by `force_github_authentication` [4](#0-3) , but the `/events` mount, defined outside the controller hierarchy [2](#0-1) , returns the stream response instead.
