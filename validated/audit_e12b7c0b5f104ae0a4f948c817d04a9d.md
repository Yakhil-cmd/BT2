## Title
CCMenu API allows an API token scoped to one stack to read CI status of any other stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

## Summary
`Shipit::Api::CCMenuController` inherits the `read:stack` permission check from `Shipit::Api::BaseController`, but overrides `#stack` to resolve the target stack from *all* stacks rather than from the API client's authorized stack scope, breaking the binding between "the stack a token authorizes" and "the stack it actually touches."

## Finding Description
`Shipit::Api::BaseController` scopes stack lookups to the calling `ApiClient`'s authorized stack: [1](#0-0) 
```
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
An `ApiClient` can be created with a `stack_id`, restricting it to operate only on that one stack (see fixture `here_come_the_walrus` scoped to `stack: shipit` with only `read:stack`) [2](#0-1) , and this scoping is enforced everywhere `BaseController#stack`/`#stacks` is used, e.g. in `StacksController#index` filtering results down to the scoped stack.

However, `Shipit::Api::CCMenuController` overrides `#stack` directly: [3](#0-2) 
```
private

def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end

def authenticate_api_client
  @current_api_client = ApiClient.authenticate(params[:token])
  super unless @current_api_client
end
```
This bypasses the `stacks` scoping helper entirely and resolves `params[:stack_id]` against `Stack.from_param!` (i.e. all stacks in the instance), while the only authorization gate applied is `require_permission :read, :stack` at the class level: [4](#0-3) 
```
class CCMenuController < BaseController
  require_permission :read, :stack
  ...
  def show
    latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
    render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
  end
```
`require_permission!` only checks that the `permissions` array on the `ApiClient` model includes `"read:stack"` — it never checks `stack_id` against the requested stack: [5](#0-4) 
```
def check_permissions!(operation, scope)
  required_permission = "#{operation}:#{scope}"
  unless permissions.include?(required_permission)
    raise InsufficientPermission, "This operation requires the `#{required_permission}` permission"
  end
  true
end
```

**The binding being broken:** *the stack a token authorizes* (`ApiClient#stack_id`) *≠ the stack the CCMenu endpoint touches* (`params[:stack_id]`, resolved unscoped). The equivalence the rest of the API enforces — `stacks.from_param!(params[:stack_id])` where `stacks` is filtered by `current_api_client.stack_id?` — is dropped specifically in `CCMenuController`.

## Impact Explanation
An attacker who possesses (or is issued, e.g. via `CCMenuUrlController#fetch` which auto-creates a `read:stack`-scoped client for the *current* stack) a `CCMenu`-style API token scoped to Stack A can substitute any other `stack_id` in the request path and read that stack's CI/deploy state (`deploys_and_rollbacks.last`, build status, last build label, etc.) for any stack in the Shipit instance — including stacks belonging to different repositories/orgs the token holder has no authorization for. This satisfies the "High" impact bucket: *unauthenticated/unauthorized read of stack state or deploy output* across stack boundaries, using only a token that was meant to be scoped to a single stack.

## Likelihood Explanation
Likelihood is high for any deployment where CCMenu-style tokens are distributed (the engine ships a dedicated `CCMenuUrlController` that mints such scoped tokens on demand for logged-in users) [6](#0-5) . Any holder of such a token — which is designed to be safely embeddable in third-party CI dashboard tools — can trivially change the `stack_id` URL segment to enumerate/read other stacks' data; no additional credentials, GitHub access, or privilege escalation is required beyond having one legitimately-scoped `read:stack` token.

## Recommendation
Have `CCMenuController#stack` reuse the inherited, scoped `stacks` relation instead of querying `Stack.from_param!` directly, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
so that a client scoped via `ApiClient#stack_id` cannot resolve any stack other than the one it was issued for, restoring parity with `BaseController#stack`.

## Proof of Concept
1. As a logged-in user with access to Stack A only, visit `CCMenuUrlController#fetch` for Stack A; the engine creates (or reuses) an `ApiClient` with `permissions: ["read:stack"]` and `stack_id: A.id`, and returns a URL `.../api/stacks/:A_id/ccmenu.xml?token=<token>` [7](#0-6) .
2. Take the returned `token` and issue a request to `GET /api/stacks/:B_id/ccmenu.xml?token=<token>` where `B` is an arbitrary stack the token was never scoped to.
3. `CCMenuController#authenticate_api_client` authenticates the token successfully (the token itself is valid) and `require_permission :read, :stack` passes because `permissions` includes `read:stack`.
4. `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` — unscoped — and returns Stack B, letting the response leak Stack B's last deploy status/build label/activity despite the token only authorizing Stack A. This differs from every other API endpoint (e.g. `Api::StacksController#show`), which would 404/empty-scope on Stack B because they use the inherited scoped `stack`/`stacks` helpers.
