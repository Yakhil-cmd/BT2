### Title
Reward-distribution block count is clamped independently of stake-account count, allowing unbounded per-block work at the epoch boundary - (File: `runtime/src/bank/partitioned_epoch_rewards/mod.rs`)

### Summary
The external report's bug class is: a consensus-critical threshold is computed as a function of an unbounded, attacker-influenceable count (active validators), while the actual number of participants allowed into the round is capped at a fixed value, making the threshold unreachable. The closest reachable analog in agave is in the partitioned epoch-rewards distribution mechanism, where the *number of blocks* used to spread out stake-account reward stores is clamped to at most 10% of the epoch's slots, independent of how many stake accounts (i.e., how much per-block work) actually need to be processed [1](#0-0) .

### Finding Description
`get_reward_distribution_num_blocks` computes the number of blocks needed to distribute rewards by dividing the total number of stake accounts with rewards by `partitioned_rewards_stake_account_stores_per_block()`, then clamps the result to at most `slots_per_epoch / MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH` (10% of the epoch): [1](#0-0) 

This `num_partitions` value is fixed at the epoch-boundary block via `create_epoch_rewards_sysvar` and later used, unchanged, to bucket every deferred stake reward into exactly that many partitions using `hash_rewards_into_partitions`, which assigns each stake account's reward to a partition purely by hashing its pubkey against the parent blockhash — with no per-partition size limit: [2](#0-1) 

Each partition is processed entirely within a single block by `distribute_epoch_rewards_in_partition` / `store_stake_accounts_in_partition`, which iterates every stake account assigned to that partition and mutates its account state, updates capitalization, and updates reward history — all synchronously within that one block's production/replay: [3](#0-2) 

The clamp is analogous to the report's fixed `CORE_VALIDATOR_SET_SIZE`: the number of "slots" (rounds) available to spread the work is capped at a fixed fraction of the epoch regardless of how large the workload (total stake accounts) is. Since `stake_account_stores_per_block` is a fixed baseline (`MAX_PARTITIONED_REWARDS_PER_BLOCK = 4096`, scaled by slot-time target) [4](#0-3) , once `total_stake_accounts / stake_account_stores_per_block` exceeds `slots_per_epoch / 10`, the number of computed blocks is clamped down, meaning each of those blocks must now absorb proportionally more work than the intended per-block baseline — potentially many multiples of 4096 stake-account reward stores in a single 400ms slot, with no upper bound other than the total delegator count.

An unprivileged user can trivially inflate the total number of stake accounts with non-zero delegation by splitting SOL across many `CreateAccount` + `stake::instruction::initialize` + `delegate_stake` calls (a normal, permissionless stake-program operation), each stake account requiring only the rent-exempt minimum. There is no fee-market-based nor protocol-level limit tying `total_stake_accounts` to `slots_per_epoch`; the clamp in `get_reward_distribution_num_blocks` was designed to bound *distribution duration*, but as a side effect it also bounds the number of "slots" over which the fixed baseline throughput can be amortized, without bounding the per-block workload itself.

### Impact Explanation
If the total number of active stake accounts grows large enough that the naturally required number of distribution blocks would exceed 10% of the epoch's slots, the clamp forces all that reward-distribution work into fewer blocks than the sizing model assumes. This concentrates massively increased account-store, capitalization-update, and reward-history-update work into single blocks at the epoch boundary. Because every validator must replay this same deterministic partitioning and distribution work to stay in consensus (it's part of bank freeze/replay, not fee-metered instruction execution), an attacker who inflates the number of low-value stake accounts can cause an outsized, non-fee-bounded amount of mandatory work per block at every epoch boundary — a potential epoch-boundary liveness/halt risk if block production/replay time is exceeded, which the report's "consensus becomes unachievable" impact category most closely maps to.

### Likelihood Explanation
Creating many stake accounts is a fully permissionless, low-cost operation (rent-exempt minimum per account, no privileged role required), so the preconditions are within reach of any unprivileged user with a large enough number of accounts/lamports to split. However, actually reaching the threshold where the clamp forces meaningfully outsized per-block work requires accumulating a very large absolute number of active stake accounts relative to `slots_per_epoch / 10` (hundreds of thousands to millions, given the current 4096/block baseline and standard mainnet epoch length), which raises the cost of the attack substantially and is a scaling/DoS-class concern rather than a straightforward, low-cost trigger.

### Recommendation
- **Short term:** Bound the per-block workload directly (i.e., cap the number of stake accounts distributed per block at the configured `stake_account_stores_per_block`, allowing the total number of distribution blocks to grow instead of being clamped to 10% of the epoch), or alternatively bound the maximum number of active stake accounts eligible for a single epoch's distribution cycle, ensuring per-block work never exceeds the sizing assumptions baked into `MAX_PARTITIONED_REWARDS_PER_BLOCK`.
- **Long term:** Perform a dedicated capacity/threat-modeling review of all epoch-boundary and reward-distribution code paths whose per-block cost scales with an attacker-influenceable count (e.g., total stake accounts, total vote accounts) to ensure no fixed clamp on the number of processing rounds can be exploited to concentrate unbounded work into a bounded number of blocks.

### Proof of Concept
Not independently verified beyond static code review: the exact number of stake accounts and epoch length required to trigger the clamp on production `slots_per_epoch` (432,000) and `MAX_PARTITIONED_REWARDS_PER_BLOCK` (4096) would need to be computed and would likely require constructing an accounts-db/bank test harness (as in `test_get_reward_distribution_num_blocks_cap` at `runtime/src/bank/partitioned_epoch_rewards/mod.rs:732-794`) with a stake-account count exceeding `(slots_per_epoch/10) * stake_account_stores_per_block` to empirically measure the resulting per-block processing time increase.

    /// Calculate the number of blocks required to distribute rewards to all stake accounts.
    pub(super) fn get_reward_distribution_num_blocks(
        &self,
        rewards: &PartitionedStakeRewards,
    ) -> u64 {
        let total_stake_accounts = rewards.num_rewards();
        if self.epoch_schedule.warmup && self.epoch < self.first_normal_epoch() {
            1
        } else {
            const MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH: u64 = 10;
            let num_chunks = total_stake_accounts
                .div_ceil(self.partitioned_rewards_stake_account_stores_per_block() as usize)
                as u64;

            // Limit the reward credit interval to 10% of the total number of slots in a epoch
            num_chunks.clamp(
                1,
                (self.epoch_schedule.slots_per_epoch / MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH).max(1),
            )
        }
    }

pub(in crate::bank::partitioned_epoch_rewards) fn hash_rewards_into_partitions(
    stake_rewards: &PartitionedStakeRewards,
    parent_blockhash: &Hash,
    num_partitions: usize,
) -> Vec<Vec<usize>> {
    let hasher = EpochRewardsHasher::new(num_partitions, parent_blockhash);
    let mut indices = vec![vec![]; num_partitions];

    for (i, reward) in stake_rewards.enumerated_rewards_iter() {
        // clone here so the hasher's state is reused on each call to `hash_address_to_partition`.
        // This prevents us from re-hashing the seed each time.
        // The clone is explicit (as opposed to an implicit copy) so it is clear this is intended.
        let partition_index = hasher
            .clone()
            .hash_address_to_partition(&reward.stake_pubkey);
        indices[partition_index].push(i);
    }
    indices
}

    fn distribute_epoch_rewards_in_partition(
        &self,
        partition_rewards: &StartBlockHeightAndPartitionedRewards,
        partition_index: u64,
    ) {
        let pre_capitalization = self.capitalization();
        let (
            DistributionResults {
                stake_reward_lamports_minted,
                stake_reward_lamports_burned,
                block_reward_lamports_distributed,
                block_reward_lamports_burned,
                updated_stake_rewards,
            },
            store_stake_accounts_us,
        ) = measure_us!(self.store_stake_accounts_in_partition(partition_rewards, partition_index));

        // increase total capitalization by the distributed rewards
        self.capitalization
            .fetch_add(stake_reward_lamports_minted, Relaxed);

        // decrease total capitalization by burned block rewards
        self.capitalization
            .fetch_sub(block_reward_lamports_burned, Relaxed);

        // decrease distributed capital from epoch rewards sysvar
        self.update_epoch_rewards_sysvar(
            stake_reward_lamports_minted + stake_reward_lamports_burned,
            block_reward_lamports_distributed + block_reward_lamports_burned,
        );

        // update reward history for this partitioned distribution
        self.update_reward_history_in_partition(&updated_stake_rewards);

        let metrics = RewardsStoreMetrics {
            pre_capitalization,
            post_capitalization: self.capitalization(),
            total_stake_accounts_count: partition_rewards.all_stake_rewards.num_rewards(),
            total_num_partitions: partition_rewards.partition_indices.len(),
            partition_index,
            store_stake_accounts_us,
            store_stake_accounts_count: updated_stake_rewards.len(),
            distributed_rewards: stake_reward_lamports_minted,
            burned_rewards: stake_reward_lamports_burned,
            distributed_block_rewards: block_reward_lamports_distributed,
            burned_block_rewards: block_reward_lamports_burned,
        };

        report_partitioned_reward_metrics(self, metrics);
