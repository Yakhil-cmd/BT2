### Title
Cross-organization webhook forgery via unauthenticated org bypass in `verify_webhook_signature` - ([File: lib/shipit/github_app.rb])

### Summary
`WebhooksController#verify_signature` picks *which* GitHub organization's secret to check a webhook against using an untrusted field of the same JSON body (`repository.owner.login` / `organization.login`), then hands the *entire* raw body to event handlers that separately trust another untrusted field (`repository.full_name`) to decide which `Stack`/`Repository` to mutate. These two fields are never cross-checked against each other, and `GithubApp#verify_webhook_signature` treats an organization with no configured `webhook_secret` as automatically "verified." In a multi-org Shipit deployment this lets an attacker impersonate any repository tracked by the app.

### Finding Description
`WebhooksController#verify_signature` resolves the org purely from the payload: [1](#0-0) 

The org lookup uses `repository_owner`, itself taken straight from the unauthenticated payload: [2](#0-1) 

`GithubApp#verify_webhook_signature` short-circuits to `true` whenever the resolved organization has no `webhook_secret` configured: [3](#0-2) 

This "no secret configured" state is an explicitly supported/documented configuration, shown as `webhook_secret: # nil` in shipped config templates: [4](#0-3) [5](#0-4) 

Once the controller accepts the request, `params = JSON.parse(request.raw_post)` is dispatched to the registered handler, which resolves the target `Stack`/`Repository` using a *different* field — `repository.full_name` — with no relationship enforced back to `repository_owner`/`organization.login` used during verification: [6](#0-5) 

Concrete handlers act on that repository/stack directly, e.g. push triggers a sync against the found stacks: [7](#0-6) 

and status events create arbitrary commit statuses (which gate CI-required deploys/merges) for any commit whose `sha` matches, regardless of repository: [8](#0-7) 

**The broken binding (as an equality that must hold but doesn't):**
`organization authenticated by verify_signature (payload.repository.owner.login / payload.organization.login, checked only against that org's webhook_secret)` ≠ `organization/repository actually written by the handler (payload.repository.full_name)`.

Before the attacker's request: for every legitimate webhook, both fields naturally refer to the same GitHub repository, so this equality silently held and was never enforced explicitly.
After the attacker's request: the attacker sets `repository.owner.login`/`organization.login` to an org that has `webhook_secret` unset (a supported "no verification" configuration) so `verify_signature` passes unconditionally, while setting `repository.full_name` (and/or `sha`, `ref`, etc.) to point at a *different* org/repository/stack that Shipit manages — one that may have a strong `webhook_secret` the attacker doesn't know. The handler then acts on that unrelated repository's stack with no cross-check.

### Impact Explanation
Because `Repository.from_github_repo_name(repository_name)` and `Commit.where(sha: params.sha)` are looked up globally (not scoped to the organization used for signature verification), this enables an unauthenticated attacker to:
- Forge `push` events for any repository tracked by the Shipit install to trigger `stack.sync_github`, and forge `status` events (`state: "success"`) for arbitrary commit SHAs across repositories, which can flip `Commit#deployable?`/CI-required gates used by continuous delivery and the merge queue — leading to an unauthorized deploy or merge.
- Forge `membership` events to add arbitrary GitHub users to `Shipit.github_teams`-backed `Team`s, which is the exact authorization mechanism `Authentication#force_github_authentication`/`User#authorized?` relies on to grant access to the Shipit UI/API — an escalation into `Shipit.github_teams` authorization.

This matches the report's High-severity classification ("write access into cross-organization state" / unauthorized deploy or merge / authorization escalation).

### Likelihood Explanation
Exploitability depends entirely on the deployment having at least one configured GitHub organization with no `webhook_secret` set — a state the project's own templates (`config/secrets.development.shopify.yml`, `template.rb`) present as valid/normal, and multi-org support is a first-class, documented feature (`test/dummy/config/secrets_double_github_app.yml`). Any operator who onboards a second org "for testing" or forgets to set a webhook secret on one org exposes every other org's repositories to forgeable webhooks — no credential, session, or GitHub write access is required by the attacker.

### Recommendation
- Require `webhook_secret` to be present for every configured organization in production (fail closed instead of `return true unless webhook_secret`).
- After signature verification, enforce that the organization used to select the webhook secret matches the organization embedded in `repository.full_name` (or `organization.login`) actually processed by the handler, rejecting mismatches.
- Consider scoping `Handler#stacks`/`Repository.from_github_repo_name` lookups to the verified organization rather than trusting `repository.full_name` unconditionally.

### Proof of Concept
1. Deploy Shipit with two configured orgs, e.g. `OrgA` (has `webhook_secret` set) and `OrgB` (`webhook_secret:` left blank), mirroring the shipped `secrets_double_github_app.yml`/`secrets.development.shopify.yml` templates.
2. Attacker (no credentials) sends `POST /webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "OrgB" }, "full_name": "OrgA/secret-repo" }
}
```
   No `X-Hub-Signature` needed, or any arbitrary value.
3. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgB").verify_webhook_signature(...)`, which returns `true` immediately since `OrgB` has no `webhook_secret` (`lib/shipit/github_app.rb:76-83`).
4. `PushHandler` resolves `stacks` via `Repository.from_github_repo_name("OrgA/secret-repo")` (`handler.rb:32-38`) and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on `OrgA`'s stack — a repository the attacker never had permission for and whose webhook secret they never had to break.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
