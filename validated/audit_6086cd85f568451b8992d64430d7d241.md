## Analog Found: Permissionless dust-donation DoS on `pallet-asset-conversion` first liquidity provisioning

### Title
DoS of `pallet-asset-conversion` pools via pre-funding the deterministic pool account with dust before first `add_liquidity` - (File: `substrate/frame/asset-conversion/src/lib.rs`)

### Summary
The Curve report describes a DoS where sending 1 wei of a token directly to an empty StableSwap pool corrupts the `D` invariant calculation and blocks `add_liquidity()`. The Polkadot SDK analog exists in `pallet-asset-conversion`: any unprivileged account can transfer dust tokens directly to a pool's deterministically-derived `pool_account` before the first real `add_liquidity` call, corrupting the reserve-detection logic in `do_add_liquidity` and permanently preventing legitimate liquidity provisioning for that asset pair, since pools cannot be re-created once their `PoolId` exists in storage.

### Finding Description
`pallet-asset-conversion` derives each pool's `AccountId` deterministically and publicly from the asset pair, with no dependency on any pool having been created or funded: [1](#0-0) 

This means any observer can compute a not-yet-existing (or freshly-created) pool's account off-chain and send an ordinary, permissionless `transfer` of an arbitrary token to it — no `create_pool` or `add_liquidity` call is required to fund this address, since the balance-carrying "account" is simply the target of a normal token transfer.

In `do_add_liquidity`, the reserve amounts used to decide which liquidity-provisioning branch to take are read directly from the pool account's live balances, *before* the caller's own desired transfer is applied: [2](#0-1) 

If both `reserve1` and `reserve2` are non-zero (because an attacker pre-funded the pool account with dust of both assets in an extreme, skewed ratio), the code skips the "empty pool" branch (lines 818–820) and instead computes `amount2_optimal`/`amount1_optimal` via `quote()`, which is a straight ratio derived from the attacker-controlled dust reserves: [3](#0-2) 

Because the attacker controls the dust ratio arbitrarily (e.g., `reserve1 = 1`, `reserve2 = huge_number`), any legitimate depositor's desired amounts will produce a wildly skewed `amount1_optimal`/`amount2_optimal` that fails the `amount1_min`/`amount2_min` slippage checks (`Error::AssetOneDepositDidNotMeetMinimum` / `AssetTwoDepositDidNotMeetMinimum` / `OptimalAmountLessThanDesired`), since `total_supply` of the LP token is still zero at this point (no liquidity has ever actually been added) — the `calc_lp_amount_for_zero_supply` path is only reached if the quote branch itself doesn't first fail: [4](#0-3) 

Because `create_pool` refuses to run twice for the same asset pair (`ensure!(!Pools::<T>::contains_key(&pool_id), Error::<T>::PoolExists)`), and because there is no code path to burn/expunge the attacker's donated dust from the pool account, the pool becomes **permanently unable to accept its first liquidity provision** for any depositor whose desired ratio does not exactly match the attacker's poisoned ratio: [5](#0-4) 

This mirrors the root cause of the Curve report precisely: reserve/invariant math that assumes "reserves == 0" implies "no liquidity has been contributed yet" is defeated by direct token transfers bypassing the pool's accounting entry points.

### Impact Explanation
The affected asset pair's conversion pool becomes permanently unusable: `add_liquidity` will revert for essentially any real depositor because their desired ratio cannot match an attacker-chosen extreme ratio, and the pool's `PoolId` can never be recreated. This is a deterministic, irreversible denial of service against a specific pool/asset-pair — matching the "irreversible freezing" / "deterministic chain failure" class called out as preferred severity in the scan criteria, though the value directly at risk is limited to the usability of that asset-pair pool (no funds are stolen and dust cost is trivial to inflict).

### Likelihood Explanation
The attack requires only:
1. An ordinary signed account with dust balance of the two target assets (attacker cost ~ existential deposit / dust amounts).
2. A standard, permissionless transfer to the deterministically-computable `pool_account` address (`AccountIdConverter::try_convert` off `blake2_256(Seed, PoolId)`), requiring no special role, no governance, and no interaction with the asset-conversion pallet's own extrinsics.
3. Timing before, or racing, the first legitimate `add_liquidity` call for that asset pair.

This is trivially executable by any user and does not require privileged access, matching the "no privileged prerequisites" and "real entry point" requirements.

### Recommendation
`do_add_liquidity` should not infer "pool is empty" solely from `reserve1.is_zero() || reserve2.is_zero()`. Instead it should key the "first liquidity" branch off `T::PoolAssets::total_issuance(pool.lp_token) == 0` (the same signal already used a few lines later at line 858/861) rather than raw balances, so that pre-donated dust tokens sitting in the pool account cannot corrupt the optimal-amount computation. Any pre-existing dust reserves should either be swept into the first LP's minted share or explicitly accounted for in `calc_lp_amount_for_zero_supply`.

### Proof of Concept
No PoC was executed against a live network or test harness in this analysis; this is a static-analysis-derived, code-verified analog based on direct reading of `do_add_liquidity`, `quote`, `calc_lp_amount_for_zero_supply`, and `PoolLocator::address`/`AccountIdConverter` in `substrate/frame/asset-conversion/src/lib.rs` and `substrate/frame/asset-conversion/src/types.rs`. Constructing an executable integration test would require: (1) computing the deterministic pool account for an asset pair before pool creation, (2) transferring skewed dust amounts of both assets to it, (3) calling `create_pool`, then `add_liquidity` with realistic amounts/min-bounds, and (4) asserting the extrinsic errors with `AssetOneDepositDidNotMeetMinimum`/`AssetTwoDepositDidNotMeetMinimum` for all reasonable slippage settings, confirming pool. That reproduction step was not run in this session.

		pub(super) fn calc_lp_amount_for_zero_supply(
			amount1: &T::Balance,
			amount2: &T::Balance,
		) -> Result<T::Balance, Error<T>> {
			let amount1 = T::HigherPrecisionBalance::from(*amount1);
			let amount2 = T::HigherPrecisionBalance::from(*amount2);

			let result = amount1
				.checked_mul(&amount2)
				.ok_or(Error::<T>::Overflow)?
				.integer_sqrt()
				.checked_sub(&T::MintMinLiquidity::get().into())
				.ok_or(Error::<T>::InsufficientLiquidityMinted)?;

			result.try_into().map_err(|_| Error::<T>::Overflow)
		}
