### Title
Operator-precedence bug lets `ReopenedHandler#unarchive?` ignore `review_stacks_enabled: false` for label-based provisioning behaviors - (File: app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb)

### Summary
`ReopenedHandler#unarchive?` mirrors `OpenedHandler#provision?` and uses the same unparenthesized `&&`/`||` chain, so `repository.review_stacks_enabled` is only ANDed with the `allow_all?` branch and is never applied to the `allow_with_label?`/`prevent_with_label?` branches. A repository configured with `review_stacks_enabled: false` but a leftover `provisioning_behavior: :allow_with_label` (+ label) will still unarchive/create and re-provision review stacks on PR reopen, in direct contradiction of the disabled toggle.

### Finding Description
Intended binding: `unarchive? == review_stacks_enabled && (allow_all? || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?))` — i.e. `review_stacks_enabled` should gate every behavior.

Actual code in `unarchive?`: [1](#0-0) 

Ruby operator precedence makes `&&` bind tighter than `||`, so this evaluates as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`.

When `review_stacks_enabled` is `false` and `provisioning_behavior` is `:allow_with_label` with the label present, the second disjunct alone (`allow_with_label? && has_label?`) evaluates to `true`, making the whole expression `true` regardless of `review_stacks_enabled`. `respond_to_pull_request_reopened?` then returns true, and `process` calls `stack.unarchive!`, which (via `ReviewStackAdapter#unarchive!`) creates the stack if missing or enqueues it via `Shipit::ReviewStackProvisioningQueue.add(stack)`: [2](#0-1) 

The identical flaw exists in `OpenedHandler#provision?`: [3](#0-2) 

Root cause: missing parentheses grouping `review_stacks_enabled &&` around the entire `||` chain instead of just the first disjunct.

Attacker's exact action: on a repository where an operator previously used `allow_with_label` (with a provisioning label configured) and later unchecked "review_stacks_enabled" via the settings UI (`app/views/shipit/repositories/settings.html.erb`) without clearing the behavior/label fields, an unprivileged user who can label and reopen their own PR causes the review stack to be (re)provisioned despite the explicit disablement.

Existing guards do not catch this: `ExplicitParameters` schema validation only checks payload shape, not business logic; there is no test in `reopened_handler_test.rb`/`opened_handler_test.rb` that combines `provisioning_enabled: false` with `allow_with_label`/`prevent_with_label` — all such tests keep the default `provisioning_enabled: true`, so the divergence is untested and unnoticed.

### Impact Explanation
Reopening a labeled PR causes `Shipit::ReviewStackProvisioningQueue.add(stack)` to run and the stack's provisioning handler (`up`) and subsequent deploy/task execution to proceed for a repository whose operator explicitly disabled review-stack provisioning. This is a policy/authorization bypass: provisioning that should require `review_stacks_enabled: true` executes anyway. The blast radius is confined to repositories with this specific config drift (label-based behavior configured while the toggle is off), and it is repeatable on every reopen. It does not, by itself, cross tenant boundaries (repository/stack scoping via `repository.review_stacks` is otherwise intact) and default `ProvisioningHandler::Base` is a no-op, so command execution severity depends on the host application's registered `ProvisioningHandler` and/or subsequent deploy tasks using `Command`/`PTY.spawn`.

### Likelihood Explanation
Requires a specific, plausible-but-non-default repository configuration: `review_stacks_enabled: false` together with `provisioning_behavior: :allow_with_label` (or `:prevent_with_label`) and a configured label — a state easily reached by toggling the checkbox off without resetting the other fields, since the settings form doesn't clear them. The attacker needs no Shipit credentials, only the ability to label and reopen their own PR (or push commits triggering the PR lifecycle), which matches the stated threat model.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates the entire disjunction in both `ReopenedHandler#unarchive?` and `OpenedHandler#provision?` (and any other duplicated copies, e.g. `LabelCapturingHandler`/`ClosedHandler` if they share this pattern):
```ruby
def unarchive?
  repository.review_stacks_enabled && (
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
  )
end
```

### Proof of Concept
Add to `test/models/shipit/webhooks/handlers/pull_request/reopened_handler_test.rb`:
```ruby
test "does not unarchive stacks when review_stacks_enabled is false, even with allow_with_label + matching label" do
  stack = create_archived_stack
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :allow_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_reopened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  Shipit::Webhooks::Handlers::PullRequest::ReopenedHandler.new(payload).process

  assert stack.reload.archived?, "Expected stack to remain archived because review_stacks_enabled is false"
end
```
Before the fix this assertion fails (the stack is unarchived and re-queued for provisioning); after adding the parentheses in `unarchive?`, the assertion passes, confirming `review_stacks_enabled == false` correctly disables provisioning for the `allow_with_label` behavior.
