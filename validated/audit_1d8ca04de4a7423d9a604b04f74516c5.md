### Title
Webhook signature verification selects the trust key from an unverified payload field, letting an unsigned event for one org mutate state for a completely different repository - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which `GitHubApp`/`webhook_secret` to validate a webhook against using a value taken directly from the *unverified* JSON body, then dispatches the *entire* unverified body (including a different, unrelated field that actually identifies the target repository/stack) to the event handlers. If the organization picked for verification has no `webhook_secret` configured, signature checking is silently skipped, but the payload's `repository.full_name` used to locate the target `Stack` is never re-validated against that org. This breaks the equality "organization that authenticated == repository that is written."

### Finding Description
`verify_signature` computes the verification target purely from attacker-supplied JSON, before any cryptographic check has occurred: [1](#0-0) [2](#0-1) 

`repository_owner` is read from `params.dig('repository', 'owner', 'login')` (or `organization.login`) — a field fully controlled by whoever sends the POST body, not by GitHub's HMAC signature. This value is used only to select *which* configured GitHub App's secret to check against (`Shipit.github(organization: repository_owner)`), via `GitHubApp#verify_webhook_signature`: [3](#0-2) 

Critically, `verify_webhook_signature` returns `true` unconditionally whenever the selected organization's `webhook_secret` is blank (`return true unless webhook_secret`). Shipit explicitly supports multiple GitHub organizations, each with its own independently configured `webhook_secret`, as documented in `docs/setup.md` and demonstrated by template/example configs that ship with `webhook_secret: null` (i.e., unset) as a normal state: [4](#0-3) [5](#0-4) 

Once `verify_signature` passes (either because a secret truly matches, or because the selected org has none configured), `WebhooksController#create` parses the raw body a second time and forwards the *full, unverified* payload to the registered handlers for the event type: [6](#0-5) 

Nothing re-checks that `repository.full_name` (which handlers use to resolve the actual `Stack`/`Repository` being acted on) belongs to the same organization (`repository.owner.login`) that was used to select the verification secret. The value used to authenticate ("which org's key do I trust") and the value used to act ("which repository do I mutate") are two independent, both attacker-controlled fields inside the same JSON body — the exact class of bug described in the referenced report, where the value that is checked (`d_reward`/transfer condition) is not the value the subsequent accounting update is bound to.

### Impact Explanation
An attacker who can reach the public `/webhooks` endpoint and knows (or can guess) the name of *any* GitHub organization configured in Shipit that currently has no `webhook_secret` set (a state the project's own example/template secrets files show as normal/default) can craft a JSON body where:
- `repository.owner.login` / `organization.login` = the org with no secret (bypasses HMAC entirely), and
- `repository.full_name` = a repository belonging to a *different*, fully-protected organization/stack.

Because signature verification is bypassed for the first org while the handler acts on the second org's stack, the attacker can inject forged events — `push` (enqueues `GithubSyncJob` for the target stack), `status`/`check_suite` (creates/overwrites `Status` rows used by `Commit#deployable?`, `MergeRequest#reject_unless_mergeable!`, and CI-gating logic), or `membership` (creates/removes `Team`/`Membership` records that back `User#authorized?` and `Shipit.github_teams`) — for a stack they should have no ability to influence. This can escalate into forging a passing CI status that unblocks an otherwise-blocked deploy, or manipulating team membership used for authorization, both of which map to the defined High/Critical impact categories (unauthorized deploy, escalation into `Shipit.github_teams` authorization).

### Likelihood Explanation
Exploitability depends on at least one configured organization lacking a `webhook_secret`. This is not a hypothetical edge case — it is the literal default shown in the shipped example/template secrets files (`webhook_secret: # nil`), and multi-org support is a first-class, documented feature, so partially-configured or newly-onboarded organizations are a realistic operational state. No privileged credential (session, `ApiClient` token, GitHub App private key, or actual `webhook_secret`) is required by the attacker — only knowledge of an organization name with a missing secret and the target repository's `full_name`, both discoverable/public information.

### Recommendation
Bind the value used for authentication to the value used for the mutation:
- After computing `repository_owner`, and after signature verification succeeds, additionally require that any repository identifiers in the payload (`repository.full_name`, `repository.owner.login`) resolve to a `Stack`/`Repository` actually owned by that same `repository_owner`/organization before dispatching to handlers.
- Never treat a missing/blank `webhook_secret` as an implicit "verified" bypass in production; require explicit opt-in (e.g., a distinct `insecure: true` flag) for organizations that intentionally skip signature verification, and log/alert loudly when this path is taken.
- Prefer deriving the trust boundary strictly from the verified HMAC (i.e., only ever act on the org whose secret actually matched), rather than trusting an unauthenticated `repository_owner` field to select the check.

### Proof of Concept
1. Configure Shipit with two organizations, `org-open` (no `webhook_secret` set) and `org-protected` (secret configured), per the multi-org format in `docs/setup.md`.
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": {
    "owner": { "login": "org-open" },
    "full_name": "org-protected/protected-repo"
  },
  "after": "<attacker-chosen sha>"
}
```
3. `verify_signature` resolves `Shipit.github(organization: "org-open")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of any (or no) `X-Hub-Signature` header.
4. `create` then dispatches the full payload — including `repository.full_name = "org-protected/protected-repo"` — to the `push` handler, which enqueues `GithubSyncJob` for the `org-protected` stack, an organization the attacker never authenticated against. [7](#0-6) [3](#0-2) 

**Note on uncertainty**: I could not retrieve the full contents of `app/models/shipit/webhooks/handlers/push_handler.rb` (a tool-call error prevented reading it directly), so the exact field(s) that handler uses to resolve the target `Stack`/`Repository` (`repository.full_name` vs. another identifier) are inferred from the surrounding test fixtures (`test/controllers/webhooks_controller_test.rb`) and general handler patterns (e.g., `pull_request` handlers, which do use `repository.full_name`-style dig calls) rather than confirmed line-by-line in that specific file. The core vulnerability — that `repository_owner` used for signature-key selection is independent from whatever field(s) handlers use to identify the acted-upon repository — is confirmed directly in `app/controllers/shipit/webhooks_controller.rb` and `lib/shipit/github_app.rb`.

# frozen_string_literal: true

module Shipit
  class WebhooksController < ActionController::Base
    skip_before_action :verify_authenticity_token, raise: false
    before_action :check_if_ping, :drop_unhandled_event, :verify_signature

    respond_to :json

    def create
      params = JSON.parse(request.raw_post)
      Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }

      head(:ok)
    end

    private

    def drop_unhandled_event
      # Acknowledge, but do nothing
      head(204) unless Shipit::Webhooks.for_event(event).present?
    end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
  end
end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
