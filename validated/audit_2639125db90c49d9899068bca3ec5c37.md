### Title
Caller-supplied stale-but-valid price feed poisons the shared `last-update`/Pyth price cache, degrading price freshness guarantees for other users' positions - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`liquidate`, `borrow`, `collateral-add/remove`, etc. accept an optional `price-feeds` parameter that any unprivileged caller can supply [1](#0-0) . These feeds are written via `write-feed`/`write-feeds` directly into the shared, global Pyth storage contract before any other price/health logic runs [2](#0-1) . The resulting price is then read by `price-resolve`, which also updates a market-wide `last-update` cache keyed only by `{type, ident}` (not by caller/account), and only enforces monotonicity (`>= ts prev`) and a per-asset `max-staleness` window, not tightness to "now" [3](#0-2) . Because this cache is shared across all users and asset consumers (borrow, collateral valuation, liquidation health checks) for the remainder of the freshness window, one caller's chosen feed (which is only required to satisfy `<= delta max-staleness`, not be the most current available price) determines the price every other unrelated user's transaction will use until a fresher update supersedes it.

### Finding Description
The root cause is the combination of (1) permissionless `price-feeds` write access shared globally, and (2) a `last-update` map that is not scoped per-transaction or per-caller but keyed only by `{type, ident}` [4](#0-3) . Any account can call `borrow`/`collateral-add`/`liquidate` with a `price-feeds` list containing an old-but-still-"fresh-enough" (within `max-staleness`) signed Pyth update instead of the newest available one, and that becomes the cached reference price for every other account's health/LTV/liquidation computations that read the same asset in the same or nearby block, since `price-resolve` only refreshes `last-update` when the supplied timestamp is strictly newer than what's stored [5](#0-4) . This matches the report's bug class: unsanitized/unchecked caller-supplied input (a self-chosen historical, valid feed) mutates a piece of shared state that other unprivileged parties subsequently rely on for correctness, letting one caller effectively delay how quickly the "true" price the whole market sees advances.

### Impact Explanation
If an attacker deliberately submits a favorable stale feed (e.g., one that keeps a borrower's collateral price artificially high, just inside the staleness window) before their own borrow/collateral-add transaction, that stale price also becomes the price other unrelated users' concurrent liquidations/health checks resolve against, potentially delaying a legitimate liquidation of a different borrower or allowing an unhealthy position to look healthy for other market participants' calculations in that window. This can result in temporary freezing/incorrect valuation of other users' positions (a liquidator's liquidation reverting under `ERR-HEALTHY` due to the stale cached price) — a "temporary freezing of funds" impact class.

### Likelihood Explanation
Requires the attacker to have a validly-signed but older Pyth feed sitting within the `max-staleness` window (default oracle freshness checks such as `read-price-with-staleness-check` in `pyth-storage-v4.clar` still allow this) [6](#0-5) , and to time a transaction ahead of a victim's liquidation/borrow in the same freshness window. This is opportunistic and needs favorable market timing, making likelihood moderate/low rather than trivial, and I was not able to fully verify within the available context whether upstream Pyth relayers/keepers would race to overwrite it quickly in practice.

### Recommendation
Consider requiring `price-resolve` to compare the supplied feed's timestamp not just against the previously cached `last-update` but against a maximum allowed lag from `stacks-block-time` tightened close to real-time, and/or scoping "used" price staleness checks to the transaction's own price data rather than relying on a globally shared, caller-writable cache that persists across unrelated transactions.

### Proof of Concept
1. Attacker holds a validly signed Pyth feed for asset X with `publish-time = T`, where `T` is within `max-staleness` of current `stacks-block-time` but older than the latest available price.
2. Attacker calls `borrow`/`collateral-add` with `price-feeds = [feed_T]`, causing `write-feed` to push it into `pyth-storage-v4` and `price-resolve` to set `last-update` for `{TYPE-PYTH, ident}` to `T` [3](#0-2) .
3. A victim's liquidator calls `liquidate` on an unrelated borrower without supplying fresher `price-feeds`; `resolve-pyth`/`price-resolve` reads the same stale cached price `T`, computing an LTV that fails the `ERR-HEALTHY` check even though the true current price would have made the position liquidatable [7](#0-6) .

I was not able to fully confirm from the indexed context whether other independent actors (e.g. keeper bots) reliably overwrite this cache with fresher data before it matters in practice, which affects the real-world likelihood of exploitation; a full Devin session with terminal/test access would be needed to simulate timing and confirm exploitability empirically.

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
