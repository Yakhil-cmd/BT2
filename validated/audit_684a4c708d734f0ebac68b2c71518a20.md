### Title
Cross-organization forgery of GitHub webhooks via mismatched `repository.owner.login` and `repository.full_name` — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate an incoming webhook against using `params.dig('repository','owner','login')`, but the event handlers invoked immediately afterwards resolve the *target* repository/stack using a completely different field, `params.dig('repository','full_name')`. Because these two fields live in the same attacker-controlled JSON body and are never cross-checked, an actor who legitimately controls the webhook secret for *their own* onboarded GitHub organization can forge a signed payload that is authenticated as belonging to their org, while directing all side effects (sync, status updates, review-stack lifecycle) at a repository belonging to a different, victim organization.

### Finding Description
The signature check in the webhook controller is: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization: repository_owner)` looks up that organization's configured `webhook_secret` and HMAC-verifies the *raw, unparsed* request body against it [2](#0-1) . This only proves the requester knows the secret for the organization named in `repository.owner.login` — nothing more.

Once verification passes, `create` dispatches the *entire raw JSON payload* to every registered handler for the event, unmodified: [3](#0-2) 

Every handler, however, resolves which `Repository`/`Stack` to act on using a *different* key, `repository.full_name`, via the shared base class: [4](#0-3) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

This same pattern is repeated across `PushHandler` [5](#0-4) , and every pull-request handler (`OpenedHandler`, `ClosedHandler`, `ReopenedHandler`, `LabeledHandler`, `UnlabeledHandler`, `EditedHandler`), all of which call `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [6](#0-5) .

Nothing in the controller or in `Handler#stacks`/`Handler#repository_name` re-checks that `repository.full_name`'s owner segment equals `repository.owner.login` (the value used to select the verifying secret). The JSON body is a single attacker-supplied document, so both fields can be set independently while keeping the HMAC valid, because the HMAC covers the raw bytes as a whole — it proves *who signed*, not *which sub-fields are internally consistent*.

**Binding broken:** `organization authenticated (repository.owner.login → webhook_secret lookup) == organization/repository the handlers act on (repository.full_name)`. Before the attack these two fields always coincide for genuine GitHub-originated payloads. After a forged request, `repository.owner.login = "AttackerOrg"` (whose secret the attacker knows/controls) while `repository.full_name = "VictimOrg/victim-repo"`, breaking the equality and causing the app to authenticate as one org but write state belonging to another.

### Impact Explanation
This is a cross-repository write achieved without any credential belonging to the victim organization: an attacker who is a legitimate administrator of just one onboarded organization (and therefore knows/controls that org's Shipit `webhook_secret`, a routine, low-privilege GitHub org/repo webhook configuration capability) can:
- Force `PushHandler` to invoke `stack.sync_github(expected_head_sha:)` for a victim org's stacks, using an `after` SHA of the attacker's choosing, corrupting deployed/undeployed commit tracking used to gate deploys.
- Forge `commit_status` events (`StatusHandler`) to mark victim commits with arbitrary CI state/context, which stacks rely on to decide whether a commit is deployable/mergeable — directly enabling an unauthorized deploy decision downstream.
- Create, archive, unarchive, or relabel `ReviewStack`s tied to the victim repository's pull requests via the `pull_request` handlers.

This matches the "cross-repository writes" / "unauthorized deploy" criteria for Critical severity, since it lets an org with no authorization over the victim repository mutate that repository's state within Shipit.

### Likelihood Explanation
Likelihood is rated Low-to-Medium: it requires the attacker to already administer at least one organization/repository that is onboarded into the same Shipit instance (so they know that org's configured `webhook_secret`), which is a realistic scenario in any multi-tenant Shipit deployment serving several independent GitHub organizations. No repository write access, session, or `ApiClient` token for the victim org is needed — only the ability to craft an arbitrary HTTP POST with a valid HMAC for their own org.

### Recommendation
- In `Handler#repository_name` (and every handler that reads `repository.full_name`), require that the owner segment of `repository.full_name` matches `repository.owner.login`/`organization.login` used during signature verification, rejecting the payload if they diverge.
- Alternatively, pass the already-authenticated `repository_owner` from the controller into `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params, authenticated_owner: repository_owner) }` and have `Handler#stacks` scope `Repository.from_github_repo_name` lookups to repositories owned by `authenticated_owner`.
- Add a regression test asserting that a webhook signed for `OrgA` but containing `repository.full_name = "OrgB/repo"` is rejected (422) rather than processed.

### Proof of Concept
1. Attacker administers `AttackerOrg`, which is already onboarded to this Shipit instance with a known `webhook_secret` (`S`).
2. Attacker builds a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "AttackerOrg" },
    "full_name": "VictimOrg/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(S, raw_body)>` using their own known secret `S` for `AttackerOrg`, and sends the POST to `/webhooks` with header `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "AttackerOrg")`, verifies the HMAC against `S`, and passes (per [7](#0-6) ).
5. `create` dispatches the full payload to `PushHandler`, which resolves stacks via `Repository.from_github_repo_name("VictimOrg/victim-repo")` (per [4](#0-3)  and [8](#0-7) ) and calls `stack.sync_github(expected_head_sha: "deadbeef...")` on every matching stack in `VictimOrg`, despite the attacker never having authenticated against `VictimOrg`'s secret or having any authorization over that repository.

*Note: `Repository.from_github_repo_name`'s definition was not located in the indexed portions of the repo; its exact matching logic (e.g., case sensitivity, exact `owner/name` parsing) could not be directly verified, though its usage pattern across all handlers is consistent and confirmed above.*

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
