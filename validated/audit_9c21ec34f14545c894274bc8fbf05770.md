### Title
Forged `pull_request` `closed` webhook, verified under a secretless org, archives and deprovisions a victim's `ReviewStack` - (File: app/models/shipit/webhooks/handlers/pull_request/closed_handler.rb)

### Summary
`ClosedHandler#process` resolves the target repository solely from the attacker-controlled `params.repository.full_name` field and then calls `review_stack.archive!`, which deprovisions and archives whatever `Stack` matches that name/PR-environment pair. Because repository resolution and the `Stack` lookup never re-verify that the org whose secret validated the webhook signature is the same org named in `params.repository.full_name`, the same cross-org binding break already present in `OpenedHandler`/`LabeledHandler` lets an attacker who controls a secretless org spoof a `closed` event naming any victim repository and tear down (archive/deprovision) its real review stack.

### Finding Description
Binding claimed: `org_verifying_signature == org_owning(params.repository.full_name)`. Trace shows this binding is never asserted in the handler:

- `repository` is derived purely from the payload: `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [1](#0-0) 
- `process` unconditionally calls `review_stack.archive!` once `params.action == "closed"`, with no re-check of which org/secret authenticated the request [2](#0-1) 
- `ReviewStackAdapter#archive!` looks up the `Stack` by `environment` within the given `scope` (`repository.review_stacks`) and, if found and not already archived, calls `stack.remove_from_provisioning_queue`, `stack.deprovision`, and `stack.archive!(user, ...)` — real state-mutating/tear-down operations [3](#0-2) 

This mirrors the exact same pattern used by `OpenedHandler` (`repository.review_stacks` scope derived from payload `full_name`, no org/secret cross-check) [4](#0-3)  and `LabeledHandler` (`repository.review_stacks` scope similarly derived) [5](#0-4) . If the webhook-signature-verification layer that dispatches to these handlers validates a payload against a secret belonging to a different ("secretless"/misconfigured) org than the org actually named in `params.repository.full_name`, the handler faithfully archives whatever repository/PR-environment the attacker names in the payload, since the resolution logic itself performs no additional ownership check.

The root cause is identical to the already-established `OpenedHandler`/`LabeledHandler` finding: the handler trusts `params.repository.full_name` as the sole authority for which `Stack` to mutate, with the actual authentication binding enforced (or not enforced) entirely outside this file, in the webhook signature/dispatch layer.

### Impact Explanation
A successful forged `closed` event causes `stack.deprovision` and `stack.archive!` to run against a real victim `Stack` — removing it from the provisioning queue, deprovisioning infrastructure, and marking it archived. This is a real, repeatable, unauthorized lifecycle mutation of another tenant's resource ("a payload for one repository mutating another's stack"), matching the Critical impact category. The attacker can repeat this against any repository name they choose as long as the verifying org lacks (or has a mismatched) secret, giving broad blast radius across all repositories/orgs onboarded to the same Shipit instance.

### Likelihood Explanation
Exploitability depends entirely on the webhook-signature-verification/dispatch layer (outside this file) actually permitting a payload naming repository A to be accepted under credentials belonging to org B ("secretless" org). If that layer correctly binds the verified org to `params.repository.full_name` before dispatch, this handler's behavior is safe by construction, since `Repository.from_github_repo_name` and `repository.review_stacks` would resolve consistently to the same org. I was not able to fully inspect `app/controllers/shipit/webhooks_controller.rb` and `lib/shipit/github_app.rb` before running out of tool iterations, so I cannot independently confirm whether the cross-org binding is actually broken at the verification layer for this deployment. Given the premise stated in the question, and the identical vulnerable pattern already established for `OpenedHandler`/`LabeledHandler`, `ClosedHandler` shares the same exposure.

### Recommendation
Enforce the binding at (or before) the handler layer: after signature verification succeeds, assert that the org/repository whose secret verified the signature exactly matches `params.repository.full_name` before resolving `repository` or invoking `review_stack.archive!`. Reject the event (`drop_unhandled_event` or equivalent) if the two diverge, and apply this check uniformly across `OpenedHandler`, `LabeledHandler`, and `ClosedHandler`.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/pull_request/closed_handler_test.rb`):
1. Create `victim_repo` (org "victim-org") with a configured webhook secret, and an active `Stack`/`ReviewStack` for PR `#42` (`environment: "pr42"`), asserting `victim_stack.archived? == false` beforehand.
2. Create `attacker_org` repository configured as secretless (no `webhook_secret` set), simulating the verification path that accepts unsigned/attacker-forged payloads for that org.
3. Send a `pull_request` `closed` webhook whose signature is verified using the attacker/secretless org's (non-)secret, but whose JSON body sets `repository.full_name = "victim-org/victim_repo"` and `number: 42`.
4. Assert that `ClosedHandler.new(...).process` (or the full controller dispatch) results in `victim_stack.reload.archived? == true`, proving the org that verified the signature (`attacker_org`/secretless) differs from the org owning the torn-down stack (`victim-org`), i.e., `org_verifying != org_owning(stack)`, confirming the broken binding.
