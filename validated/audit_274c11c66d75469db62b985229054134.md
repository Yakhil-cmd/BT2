### Title
Attacker-controlled `X-Shipit-User` header lets an unauthenticated caller forge `merge_requested_by`, permanently misattributing a GitHub merge commit and poisoning Shipit's own authorship database - (File: `app/controllers/shipit/api/base_controller.rb`, `app/models/shipit/merge_request.rb`, `app/models/shipit/user.rb`)

### Summary
`Api::BaseController#identify_user` sets `current_user` from the raw, unverified `X-Shipit-User` request header, with no correlation to any authenticated identity. When `Shipit.disable_api_authentication` is enabled, this header is the *only* identity check on the entire API request, so `Api::MergeRequestsController#update` passes an attacker-chosen `current_user` straight into `MergeRequest.request_merge!`, whose `merge_requested_by` field is later written verbatim into the real GitHub commit message and then re-parsed as ground truth by `User.find_or_create_author_from_github_commit`.

### Finding Description
The broken binding: `merge_requested_by.login` (written into `merge_message` and pushed to GitHub) must equal the GitHub identity that actually authenticated the merge-queue request. Concretely, it must hold that `current_user == <the identity that authenticated the HTTP request>`. This equality is violated.

Path:
1. `Api::BaseController#authenticate_api_client` (app/controllers/shipit/api/base_controller.rb:48-56) accepts any request when `Shipit.disable_api_authentication` is true, assigning `UnlimitedApiClient.new` with no credential check at all.
2. `Api::BaseController#identify_user` (app/controllers/shipit/api/base_controller.rb:69-72) sets `current_user` purely from `request.headers['X-Shipit-User']`, looked up case-insensitively by `login` with zero signature or session verification: [1](#0-0) .
3. `Api::MergeRequestsController#update` (app/controllers/shipit/api/merge_requests_controller.rb:17-18) calls `MergeRequest.request_merge!(stack, params[:id], current_user)` with that forged `current_user`: [2](#0-1) .
4. `MergeRequest.request_merge!` (app/models/shipit/merge_request.rb:126-143) stores the forged user as `merge_requested_by` unconditionally: [3](#0-2) .
5. `MergeRequest#merge!` (app/models/shipit/merge_request.rb:164-176) calls `stack.github_api.merge_pull_request(..., merge_message, ...)`, writing `merge_message` to the real GitHub PR: [4](#0-3) .
6. `MergeRequest#merge_message` (app/models/shipit/merge_request.rb:262-266) embeds `merge_requested_by.login` as `"Merge-Requested-By: <login>"` in the commit message written to GitHub: [5](#0-4) .
7. On the subsequent push webhook, `Commit.from_github` (app/models/shipit/commit.rb:105-108) calls `User.find_or_create_author_from_github_commit`, which re-parses that same `Merge-Requested-By:` field out of the commit message and treats it as ground truth for authorship, `find_or_create_by_login!`-ing (and potentially creating) a `User` record for the forged login: [6](#0-5) .

No component in this chain re-validates that the login embedded in step 6 corresponds to whoever actually authenticated the HTTP request in step 1-2. `require_permission :deploy, :stack, only: %i[update destroy]` (app/controllers/shipit/api/merge_requests_controller.rb:7) is checked against `current_api_client`, which is `UnlimitedApiClient` (always authorized) under `disable_api_authentication` — it does not constrain `current_user`. `MergeRequest#refresh!` (app/models/shipit/merge_request.rb:239-245) only refreshes PR metadata (state, mergeable, sha, etc.) and never touches or re-validates `merge_requested_by`.

### Impact Explanation
An attacker (unauthenticated, once `disable_api_authentication` is enabled — a config-dependent precondition shared with the prior header-trust finding) can cause a real, permanent, GitHub-visible commit message to falsely state `Merge-Requested-By: <victim-login>` for an actual production merge, and that same forged identity is written back into Shipit's own `users`/`commits` authorship tables via `find_or_create_author_from_github_commit`, potentially creating a `Shipit::User` record for a login that never interacted with Shipit. This is repeatable against any stack reachable from the unauthenticated `Api::MergeRequestsController#update` endpoint (no per-stack scoping is enforced beyond `stack_id` routing, which is itself attacker-supplied). This matches the Critical category "an unauthorized ... merge" combined with false attribution that corrupts the audit trail Shipit relies on for authorship (`identify_merge_request`, app/models/shipit/commit.rb:316-328, assigns `commit.author` from `merge_request.merge_requested_by`).

### Likelihood Explanation
Requires `Shipit.disable_api_authentication` to be true (or another header-trust identity gap allowing an attacker-chosen `X-Shipit-User`), a merge queue enabled stack, and an open, mergeable pull request. Given that precondition, the attack requires no credentials, no valid `ApiClient` token, and no GitHub secrets — a single crafted HTTP `PATCH` to `/api/stacks/:id/merge_requests/:number` with an `X-Shipit-User` header set to any registered (or creatable) login is sufficient, and is fully repeatable.

### Recommendation
Never derive `current_user` for write/mutating API actions from an unauthenticated header. Either remove `identify_user`'s header-based identity entirely for privileged operations, or require it to be cryptographically bound to the authenticated `ApiClient` (e.g., only trusted for API clients explicitly configured with a specific, pre-registered user identity, never client-supplied). At minimum, `MergeRequest.request_merge!`/`merge_message` should record and use only identities established through the OAuth/session flow (`Authentication#current_user`), not the API's freeform header lookup, when `disable_api_authentication` is active.

### Proof of Concept
In a minitest test (not included here per scope rules, but described): 
1. Stub `Shipit.disable_api_authentication = true`.
2. Issue a `PATCH` to `Shipit::Engine.routes.url_helpers.api_stack_merge_request_path(...)` with header `X-Shipit-User: victim` where `victim` is an existing `Shipit::User` unrelated to the request.
3. Assert `MergeRequest.find_by(...).merge_requested_by.login == "victim"`.
4. Stub `stack.github_api` and call `merge_request.merge!`; capture the `merge_message` argument passed to `merge_pull_request` and assert it contains `"Merge-Requested-By: victim"`.
5. Build a synthetic Sawyer commit resource whose `commit.message` is that captured merge message, call `User.find_or_create_author_from_github_commit(synthetic_commit)`, and assert the returned user's `login == "victim"` rather than any real authenticated actor — proving the round-trip misattribution.
