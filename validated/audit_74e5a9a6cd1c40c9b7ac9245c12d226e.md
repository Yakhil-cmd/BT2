### Title
Force-sent KAIA via `selfdestruct` inflates staking-contract native balance, corrupting `StakingInfo.StakingAmounts` and causing incorrect block-reward distribution — (`kaiax/staking/impl/getter.go`)

---

### Summary

The Kaia staking module derives each validator's staking amount directly from the **native KAIA balance** of its registered staking-contract address. Because the EVM allows any account to force-send native tokens to an arbitrary address via `selfdestruct`, an attacker can inflate a staking contract's apparent balance without going through the staking contract's own deposit logic. The inflated balance is then read by the `MultiCallContract` and stored in `StakingInfo.StakingAmounts`, causing the reward module to over-allocate staking rewards to the manipulated validator for every block that uses the corrupted `StakingInfo`.

---

### Finding Description

**How staking amounts are read**

`StakingModule.getFromState` injects the production `MultiCallContract` bytecode into a copy of the state and calls `multiCallStakingInfo()` (permissioned path) or `multiCallStakingInfoPermissionless()` (permissionless path). The returned `stakingAmounts` array is the raw native-token balance of each staking-contract address, as confirmed by:

1. The module README: *"StakingInfo summarizes the current AddressBook contract state, and all the staking contracts registered in the AddressBook, and **their native token balances**."*
2. The unit test in `kaiax/staking/impl/getter_test.go` which sets only `Balance` (no `Code`) on staking-contract addresses and expects the matching `StakingAmounts`:

```go
// staking1 address has only a native balance, no contract code
common.HexToAddress("0x0000000000000000000000000000000000000F01"): {
    Balance: new(big.Int).Mul(big.NewInt(42_000_000), big.NewInt(params.KAIA)),
},
// Expected result
StakingAmounts: []uint64{42_000_000, 99_000_000},
``` [1](#0-0) 

The amounts are then divided by `params.KAIA` and stored as `uint64` KAIA units:

```go
stakingAmounts[i] = big.NewInt(0).Div(a, big.NewInt(params.KAIA)).Uint64()
``` [2](#0-1) 

**How `selfdestruct` corrupts the balance**

The EVM `SELFDESTRUCT` opcode transfers the selfdestructing contract's entire balance to a beneficiary address and bypasses any `receive`/`fallback` logic on the target. An attacker can:

1. Deploy a contract pre-funded with `X` KAIA.
2. Call `selfdestruct(stakingContractAddress)` targeting a specific validator's staking contract.
3. The staking contract's native balance increases by `X` KAIA with no corresponding internal accounting update.

This is the same force-send primitive as the GenesisGroup bug. The `opSelfdestruct` implementation confirms the balance is added unconditionally:

```go
balance := interpreter.evm.StateDB.GetBalance(scope.Contract.Address())
interpreter.evm.StateDB.AddBalance(beneficiary.Bytes20(), balance)
interpreter.evm.StateDB.SelfDestruct(scope.Contract.Address())
``` [3](#0-2) 

**How the corrupted amount propagates to reward distribution**

`StakingInfo.StakingAmounts` feeds directly into `assignStakingRewards` (pre-Prague) and `assignStakingRewardsFlex` (post-Prague). Both functions compute each validator's share of the stakers' reward budget proportionally to their staking amount minus the minimum stake threshold:

```go
excess := new(big.Int).SetUint64(cnTotalStakingAmount - minStake)
reward := new(big.Int).Div(new(big.Int).Mul(excess, stakersReward), totalExcess)
``` [4](#0-3) 

Inflating one validator's staking amount increases its `excess`, increases `totalExcess`, and shifts the proportional allocation in its favour — reducing every other eligible validator's share. The corrupted `StakingInfo` is then used by `FinalizeState` to call `state.AddBalance` for each recipient:

```go
for addr, amount := range spec.Rewards {
    state.AddBalance(addr, amount)
}
``` [5](#0-4) 

**Caching and persistence**

Before the Kaia hardfork, `StakingInfo` is persisted to the database every `StakingInterval` blocks and cached in memory. A single `selfdestruct` executed in the source block window corrupts the cached/persisted entry and affects reward distribution for the entire subsequent staking interval (up to `StakingInterval` blocks). [6](#0-5) 

After the Kaia hardfork, `StakingInfo` is read from the previous block's state on every block, so the corruption lasts only one block per `selfdestruct` — but the attack is repeatable at negligible marginal cost once the initial KAIA is sacrificed.

---

### Impact Explanation

**Corrupted value**: `StakingInfo.StakingAmounts[i]` for the targeted validator, inflated by `floor(X / params.KAIA)` KAIA units where `X` is the force-sent amount.

**Protected-state impact**: Unauthorized reward distribution — the targeted validator's reward address receives more KAIA staking rewards than it is entitled to, and all other eligible validators receive proportionally less. The total staking-reward budget is fixed per block, so the redistribution is zero-sum among validators but constitutes an unauthorized transfer of KAIA rewards.

**Scope**: Affects the `kaiax/reward` and `kaiax/staking` modules on mainnet and Kairos testnet (both use `DeferredTxFee = true`, meaning `FinalizeState` distributes rewards using `StakingInfo`).

---

### Likelihood Explanation

- **Trigger**: Any account can deploy a contract, fund it, and call `selfdestruct` targeting a staking contract address. No special privilege is required.
- **Cost**: The attacker sacrifices the force-sent KAIA (pure self-inflicted loss), but a competing validator could rationally do this to increase its own reward share at the expense of rivals.
- **Detectability**: The native balance of the staking contract increases visibly on-chain, but there is no on-chain guard or alert.
- **Magnitude**: With a minimum stake of 5,000,000 KAIA, force-sending even 1,000,000 KAIA (20% of minimum stake) to a validator already at minimum stake doubles its `excess` and significantly shifts reward allocation.

---

### Recommendation

Replace the native-balance read in the `MultiCallContract` with a call to the staking contract's own tracked internal variable (e.g., `CnStakingV4.staking()` which should return an internal accounting variable, not `address(this).balance`). This mirrors the fix suggested in the GenesisGroup report: use a supply/deposit tracker that cannot be manipulated by force-sends.

If `CnStakingV4.staking()` itself returns `address(this).balance`, it must be refactored to maintain an internal `_staking` storage variable that is incremented only on legitimate deposits and decremented only on legitimate withdrawals, making it immune to `selfdestruct`-based inflation.

---

### Proof of Concept

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.0;

contract ForceStakeInflator {
    // Fund this contract with X KAIA before calling attack()
    constructor() payable {}

    function attack(address payable targetStakingContract) external {
        // Force-sends all KAIA to the staking contract's address,
        // bypassing any receive() logic and inflating its native balance.
        selfdestruct(targetStakingContract);
    }
}
```

**Steps**:
1. Identify a target validator's staking contract address from the AddressBook.
2. Deploy `ForceStakeInflator` with `X` KAIA (e.g., 1,000,000 KAIA).
3. Call `attack(targetStakingContract)`.
4. In the next block (post-Kaia HF) or next staking interval (pre-Kaia HF), `GetStakingInfo` reads the inflated native balance.
5. `assignStakingRewards` allocates a larger share of the staking-reward budget to the target validator's reward address.
6. `FinalizeState` calls `state.AddBalance(targetRewardAddr, inflatedAmount)`, crediting excess KAIA rewards.

The attacker (or a colluding validator) receives more KAIA block rewards than entitled, at the expense of all other staking validators, for every block in the affected staking window.

func (s *StakingModule) GetStakingInfo(num uint64) (*staking.StakingInfo, error) {
	isKaia := s.ChainConfig.IsKaiaForkEnabled(new(big.Int).SetUint64(num))
	sourceNum := sourceBlockNum(num, isKaia, s.stakingInterval)

	// Try cache first
	if si, ok := s.stakingInfoCache.Get(sourceNum); ok {
		return si.(*staking.StakingInfo), nil
	}

	// Only before Kaia, try the database
	if !isKaia {
		if si := ReadStakingInfo(s.ChainKv, sourceNum); si != nil {
			s.stakingInfoCache.Add(sourceNum, si)
			return si, nil
		}
	}

	// Read from the state
	si, err := s.getFromStateByNumber(sourceNum)
	if err != nil {
		return nil, err
	}

	// Only before Kaia, write to database
	if !isKaia {
		WriteStakingInfo(s.ChainKv, sourceNum, si)
	}

	// Cache it
	s.stakingInfoCache.Add(sourceNum, si)
	return si, nil
}

```go
func opSelfdestruct(pc *uint64, interpreter *EVMInterpreter, scope *ScopeContext) ([]byte, error) {
	if interpreter.readOnly {
		return nil, ErrWriteProtection
	}
	beneficiary := scope.Stack.pop()
	balance := interpreter.evm.StateDB.GetBalance(scope.Contract.Address())
	interpreter.evm.StateDB.AddBalance(beneficiary.Bytes20(), balance)
	interpreter.evm.StateDB.SelfDestruct(scope.Contract.Address())
	if tracer := interpreter.evm.Config.Tracer; tracer != nil {
		tracer.CaptureEnter(SELFDESTRUCT, scope.Contract.Address(), beneficiary.Bytes20(), []byte{}, 0, balance)
		tracer.CaptureExit([]byte{}, 0, nil)
	}
	return nil, errStopToken
}
