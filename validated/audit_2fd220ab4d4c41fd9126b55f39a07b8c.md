## Finding: Valid

### Title
`allow_missing_txn_authentication_key` grants missing-auth-key bypass based only on a global feature flag, not on whether the sender was actually derived via the AA scheme - (File: `aptos-move/framework/aptos-framework/sources/transaction_validation.move`)

### Summary
`allow_missing_txn_authentication_key` is supposed to permit a transaction to omit an authentication key only when the sender's on-chain authentication is actually handled by account abstraction (AA). For the *non-derivable* AA case, this is correctly scoped per-account via `account_abstraction::using_dispatchable_authenticator(transaction_sender)`. For the *derivable* AA case, however, the function short-circuits on the bare global feature flag `features::is_derivable_account_abstraction_enabled()` with no check that the specific `transaction_sender` was ever produced by the derivable-AA derivation scheme, and no check that this particular authenticator's on-chain authentication actually ran. [1](#0-0) 

### Finding Description
`prologue_common` only reaches `allow_missing_txn_authentication_key` when `txn_authentication_key` (derived from `AccountAuthenticator::authentication_proof()`/`authentication_key()`) is `None`: [2](#0-1) 

`authentication_key()` returns `None` in exactly two cases: (1) an `Abstract` authenticator whose `AbstractAuthenticationData` is the non-derivable `V1` variant (no public key attached), and (2) `AccountAuthenticator::NoAccountAuthenticator`: [3](#0-2) 

For a legitimate `DerivableV1` authenticator, `authentication_key()` instead returns `Some(AuthenticationKey::domain_abstraction_address(...))`, so the missing-key branch (and hence `allow_missing_txn_authentication_key`) is *not even exercised* by real derivable-AA transactions — the normal `Some(...)` comparison against `account::get_authentication_key(sender_address)` runs instead. This means the `is_derivable_account_abstraction_enabled()` disjunct in `allow_missing_txn_authentication_key` only fires for the *other* branch that yields `None` — i.e. `NoAccountAuthenticator` (or non-derivable `V1 Abstract`, which is separately protected on the VM side).

Unlike the sibling clause `features::is_account_abstraction_enabled() && account_abstraction::using_dispatchable_authenticator(transaction_sender)`, which validates that *this specific* `transaction_sender` address has actually opted into a dispatchable authenticator, the derivable-AA clause performs **no per-account or per-authenticator validation at all** — it is satisfied purely because the global feature is on, for any `transaction_sender` address.

Correspondingly, on the Move-VM side, `validate_signed_transaction` in `aptos_vm.rs` only invokes `dispatchable_authenticate` (the actual cryptographic AA authentication) when the sender's `AuthenticationProof` is `Abstract`. Any other proof kind — including whatever proof a `NoAccountAuthenticator` account authenticator serializes to — falls into the wildcard arm that simply builds a signer for the address without any authentication call: [4](#0-3) 

Put together, if a transaction's sender authenticator produces a `None` authentication key/proof (via `NoAccountAuthenticator`) for an address that was **never** derived through the AA derivation scheme, the prologue's auth-key check is satisfied solely because `is_derivable_account_abstraction_enabled()` is on network-wide, and the VM performs no compensating cryptographic check for that sender, since it isn't an `Abstract` proof.

### Impact Explanation
If this path is reachable (i.e., if `NoAccountAuthenticator` — or any other authenticator producing a `None` authentication proof — is accepted by upstream signature/transaction-format validation as a valid *sender* authenticator, not just for the fee-payer slot), an unprivileged attacker could submit a transaction naming an arbitrary victim address as sender with no real signature at all, and the prologue would accept it as long as `DERIVABLE_ACCOUNT_ABSTRACTION` is enabled — breaking the sender/signer authentication binding invariant that the framework explicitly documents ("Returned signer MUST represent the same account address... may break the invariant of Aptos blockchain") for the AA authenticate path, but here bypassing that check entirely because no authenticate call happens.

### Likelihood Explanation
I could not fully confirm, within the available search budget, whether `AccountAuthenticator::NoAccountAuthenticator` (or any other authenticator that yields a `None` authentication proof) is actually accepted as the **primary sender's** authenticator by the pre-VM signature/format verification (`SignedTransaction`/`AccountAuthenticator::verify`) — I only found a comment noting `NoAccountAuthenticator` is used for the **fee-payer** slot (`fee_payer_authentication_proof: Some([])` if fee payer's authenticator is `NoAccountAuthenticator`), which suggests this variant may be intentionally restricted to non-sender roles. That restriction, if it exists, would neutralize the exploit for the sender position, but the `allow_missing_txn_authentication_key` code itself is still logically unsound: it grants a blanket bypass tied only to a global feature flag rather than to proof that this transaction's sender was actually authenticated via AA. I was unable to locate and inspect `AccountAuthenticator::verify()`/`SignedTransaction::verify_signature()` in the time available to close this gap.

### Recommendation
- Require `allow_missing_txn_authentication_key` to also validate, in the derivable-AA branch, that the sender's `AuthenticationProof` for this transaction is actually `Abstract` with `DerivableV1` data (mirroring the explicit `using_dispatchable_authenticator` check done for the non-derivable branch), rather than relying solely on the global `is_derivable_account_abstraction_enabled()` flag.
- Independently confirm (via code review of `AccountAuthenticator::verify`/`SignedTransaction` signature-checking) that `NoAccountAuthenticator` can never be supplied as a sender's (or secondary signer's) authenticator, only as fee-payer, and add an explicit, tested invariant/assertion enforcing this at transaction-format validation time.
- Add a unit/property test asserting that a transaction from a plain (non-AA-derived) account address, using a `None`-authentication-proof authenticator, is rejected by `prologue_common` even when `DERIVABLE_ACCOUNT_ABSTRACTION` is globally enabled.

### Proof of Concept
Not fully constructible from static review alone, because it hinges on whether pre-VM signature verification accepts `NoAccountAuthenticator` as a sender authenticator (unresolved — see Likelihood). The proof idea matches the exploit question:
1. Enable `DERIVABLE_ACCOUNT_ABSTRACTION` feature only.
2. Craft a `SignedTransaction` whose sender address is a plain account never derived via `ethereum_derivable_account`/`sui_derivable_account`/etc., with a `TransactionAuthenticator::SingleSender { sender: AccountAuthenticator::NoAccountAuthenticator }` (or any authenticator yielding `AuthenticationProof::None`).
3. Run `prologue_common`/`versioned_prologue` and assert it is rejected with `PROLOGUE_EINVALID_ACCOUNT_AUTH_KEY`. Under current code (`allow_missing_txn_authentication_key` line 114-118), it instead returns `true` and the check passes.

    /// (V1 Abstract, NoAccountAuthenticator).
    pub fn authentication_key(&self) -> Option<AuthenticationKey> {
        match self {
            Self::Ed25519 { .. }
            | Self::MultiEd25519 { .. }
            | Self::SingleKey { .. }
            | Self::MultiKey { .. } => Some(AuthenticationKey::from_preimage(
                self.public_key_bytes(),
                self.scheme(),
            )),
            Self::Abstract { authenticator } => {
                match authenticator.auth_data().abstract_public_key() {
                    Some(abstract_public_key) => {
                        // DerivableV1: derive auth key from function_info + abstract_public_key
                        let func_info_bytes = bcs::to_bytes(authenticator.function_info())
                            .expect("FunctionInfo serialization should not fail");
                        Some(AuthenticationKey::domain_abstraction_address(
                            func_info_bytes,
                            abstract_public_key,
                        ))
                    },
                    None => None, // V1 Abstract: no public key available
                }
            },
            Self::NoAccountAuthenticator => None,
        }
    }
