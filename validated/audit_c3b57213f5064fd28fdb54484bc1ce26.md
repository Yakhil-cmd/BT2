### Title
Webhook signature verification binds to `repository.owner.login`, but handlers act on the independently-controlled `repository.full_name` field, allowing cross-organization/cross-repository webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which HMAC `webhook_secret`) to verify a webhook against based on `repository.owner.login` extracted from the JSON body. Once the signature check passes, every registered handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc.) resolves the actual `Repository`/`Stack` to mutate using a *different* field of the same payload: `repository.full_name`, via `Shipit::Webhooks::Handlers::Handler#repository_name`/`#stacks`. Nothing ties `repository.full_name`'s owner back to the `repository.owner.login` that was actually authenticated, so a party that legitimately controls the webhook secret for one configured GitHub organization can forge a payload that is "signed" for their own org but names a repository belonging to a completely different, unrelated organization tracked by the same Shipit instance.

`Shipit.github(organization:)` and `github_app_config` look up a distinct `webhook_secret`/app config per organization (see the multi-org config example in `docs/setup.md` and `test/dummy/config/secrets_double_github_app.yml`): [4](#0-3) 

Once `verified` is true, `create` dispatches the *entire* parsed payload to handlers: [5](#0-4) 

Handlers determine which `Stack`/`Repository` to act on using a different key of the same payload — `repository.full_name` — with no cross-check against `repository.owner.login`: [6](#0-5) 

For example, `PushHandler` triggers `stack.sync_github` for whatever stack matches `repository.full_name`: [7](#0-6) 

and `StatusHandler` writes commit statuses for any commit matching `params.sha`, again scoped only by what handler-level lookups derive from `full_name`/`sha`, not by the verified `repository_owner`: [8](#0-7) 

**Root cause (binding broken):** the equality the code implicitly assumes is:

`organization authenticated (repository.owner.login, used to pick the HMAC secret)` == `repository actually written (repository.full_name, used by handlers to pick the Stack/Repository)`

But since both fields live in the same attacker-controlled JSON body and are read independently, an attacker who legitimately administers the GitHub App installation (and thus knows the `webhook_secret`) for **Organization A** can compute a valid HMAC over a payload where `repository.owner.login = "OrgA"` (so `verify_signature` succeeds using OrgA's secret) while `repository.full_name = "OrgB/target-repo"` (a repository/stack belonging to an unrelated organization also configured on the same Shipit instance, per the documented multi-org setup).

### Impact Explanation
This breaks the deployment-trust boundary between organizations sharing a single Shipit instance with multiple GitHub App configs (a first-class, documented deployment mode — see `docs/setup.md` "Using Multiple Github Applications"). An attacker who is only entitled to send webhooks for OrgA can forge events that are processed as if they came from OrgB's repository, causing:
- `push` events to enqueue `GithubSyncJob`/`sync_github` for OrgB's stack, forcing Shipit to resync arbitrary refs it wasn't told about by OrgB.
- `status` events to write fabricated CI statuses (`commit.create_status_from_github!`) onto commits belonging to OrgB's repository, which can unblock the merge queue or make otherwise-undeployable commits appear deployable — enabling an unauthorized deploy.
- `check_suite`/`membership`/`pull_request` handlers similarly acting on cross-organization data.

This is a cross-repository/cross-organization write achieved without ever holding OrgB's webhook secret, satisfying the "cross-repository writes" / "unauthorized deploy" impact bar.

### Likelihood Explanation
Exploitability requires only that the Shipit deployment tracks more than one GitHub organization (the officially documented multi-org configuration) and that the attacker controls (or can trigger a webhook delivery from) at least one of those organizations' GitHub App installations — a routine, unprivileged-relative-to-the-other-org capability, not requiring any Shipit session, API token, or the target org's secret. Because `verify_signature` and the handlers each read the payload independently with no consistency check, the attack is a straightforward crafted JSON body plus a correctly computed HMAC using a secret the attacker legitimately possesses.

### Recommendation
After `verify_signature` succeeds, re-derive `repository_owner` (and validate it) using the *same* trust anchor consistently, and additionally verify that any repository/organization referenced by the handlers (`repository.full_name`, `organization.login`, etc.) matches the organization whose secret validated the signature before dispatching to handlers. Concretely, pass the verified `repository_owner` (or the resolved `GitHubApp`/organization) into `Shipit::Webhooks.for_event(event)` handlers and have `Handler#stacks`/`#repository_name` assert that the resolved `Repository#owner` equals the verified organization, rejecting the event (422) otherwise.

### Proof of Concept
1. Configure Shipit with two organizations per `docs/setup.md`'s multi-app example: `OrgA` (attacker-administered, webhook secret known to attacker) and `OrgB` (victim, tracked stacks in the same Shipit instance).
2. Attacker crafts a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<victim-relevant-sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/target-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, raw_body)>` using OrgA's known secret.
4. POST to `/webhooks` with header `X-Github-Event: push`.
5. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgA")` and successfully verifies the signature against OrgA's secret.
6. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("OrgB/target-repo")` (independent of the verified `OrgA` organization) and triggers `stack.sync_github(expected_head_sha: ...)` for OrgB's stack — a write the attacker was never authorized to perform, despite never possessing OrgB's webhook secret.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
