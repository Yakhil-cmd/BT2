### Title
CCMenu API token is created without `stack_id` scope, granting `read:stack` on every stack instead of the one requested - ([File: app/controllers/shipit/ccmenu_url_controller.rb])

### Summary
`CCMenuUrlController#client` mints an `ApiClient` with `permissions: ['read:stack']` but never binds it to the `stack` the user asked for, breaking the equality: **stack a token authorises == stack it touches**. The resulting token authorises `read:stack` for every stack in the installation (`Stack.all`), not just the one the CCMenu URL was generated for.

### Finding Description
`fetch` builds a CCMenu URL and signs it with a token obtained from `client`: [1](#0-0) [2](#0-1) 

`client` does:
```ruby
def client
  @client ||= ApiClient.create_with(permissions: %w[read:stack])
                       .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
end
```
Note that neither `create_with` nor the `find_or_create_by!` conditions ever set `stack:`/`stack_id:`. `ApiClient#stack` is `belongs_to :stack, optional: true`, so the created (or found) client's `stack_id` stays `nil` for its entire lifetime [3](#0-2) .

Every API controller derives the set of stacks a client may operate on from `stack_id?`:
```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end
``` [4](#0-3) 

Because `stack_id` is `nil`, `stacks` resolves to `Stack.all` — i.e. the token is treated as an unscoped, instance-wide `read:stack` client, even though the UI flow that produced it (`fetch`, requested for one specific `stack`) implies the token should only ever "touch" that single stack: [5](#0-4) 

The token is a normal, permanent `ApiClient` authentication token (HMAC-signed id) usable anywhere Basic-Auth API tokens are accepted: [6](#0-5) [7](#0-6) 

`read:stack` is enforced identically on multiple endpoints that expose sensitive stack/task data, including deploy/task output: [8](#0-7) 
and stack listing/details: [9](#0-8) 

So a CCMenu token minted from viewing one stack's settings page can be replayed against `/api/stacks/:other_stack_id`, `/api/stacks/:other_stack_id/tasks/:task_id/output`, etc., for stacks the token was never meant to authorise.

### Impact Explanation
This breaks the binding "a stack a token authorises versus a stack it touches," explicitly called out as an accepted analog class. Any authenticated Shipit user (subject only to org-wide `Shipit.github_teams` gating, not per-stack authorization — see `Shipit::Authentication#force_github_authentication`) who triggers the CCMenu integration for one stack obtains a token that can read task streams, deploy output, and stack metadata for every stack hosted by that Shipit instance, including stacks/repositories that user has no legitimate reason to view. This matches the "High" bucket: unauthenticated/unauthorized read of stack state, task streams, or deploy output beyond the intended authorization boundary.

### Likelihood Explanation
High. No special privilege is required beyond being able to reach the CCMenu settings action for any single stack (`GET /:stack_id/ccmenu_url`, wired in `config/routes.rb`), which any team member can do. The unscoped token is created deterministically the first time a user fetches a CCMenu URL and persists indefinitely (`find_or_create_by!`), so the same token keeps working against arbitrary stacks going forward.

### Recommendation
Bind the CCMenu `ApiClient` to the specific stack it was generated for, e.g.:
```ruby
def client
  @client ||= ApiClient.create_with(permissions: %w[read:stack])
                       .find_or_create_by!(creator: current_user, stack: stack, name: 'CCMenu Client')
end
```
and add a uniqueness/lookup key including `stack_id` so existing unscoped clients are migrated or invalidated. Additionally, back-fill/expire any previously-created "CCMenu Client" records that have `stack_id: nil`.

### Proof of Concept
1. User A has access to Stack `alpha` and visits its settings page, which calls `GET /alpha/ccmenu_url`.
2. `CCMenuUrlController#client` creates `ApiClient(creator: A, name: 'CCMenu Client', permissions: ['read:stack'], stack_id: nil)` and returns its `authentication_token`.
3. User A takes that token and issues `GET /api/stacks/<beta-stack-id>/tasks/<id>/output` (or `/api/stacks/<beta-stack-id>`) with `Authorization: Basic base64(token)`, for a stack `beta` they were never granted CCMenu access to.
4. `authenticate_api_client` succeeds; `require_permission :read, :stack` passes because `check_permissions!` only checks the permissions array, not stack scope; `stacks` resolves via `Stack.all` since `current_api_client.stack_id?` is false — the request returns `beta`'s deploy output/state, confirming the unauthorized cross-stack read.
