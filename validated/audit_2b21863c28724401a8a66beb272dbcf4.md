The claim doesn't hold up against the actual code. `BandwidthScheduler::update_scheduler_state` completely rebuilds `state.link_allowances` from scratch on every call — it does not append to or merge with the previous vector. It iterates only `self.iter_links()`, which is derived from the *current* `shard_layout`'s shard indexes, and produces exactly one entry per (sender, receiver) pair in that current layout. [1](#0-0) 

Additionally, when loading the previous state at the start of `BandwidthScheduler::run`, any `LinkAllowance` entries referring to shard ids that don't exist in the current `shard_layout` (e.g., stale entries from before a resharding) are explicitly dropped via the `match (sender_index_opt, receiver_index_opt)` check, not carried forward. [2](#0-1) 

So after every single call to `BandwidthScheduler::run`, `link_allowances.len()` is bounded exactly by `num_shards^2` of the shard layout used in that call — there is no mechanism for stale entries to accumulate across resharding events since the vector is fully regenerated (not merged/appended) each time. The `iter_links` helper confirms the iteration bound is `num_shards * num_shards` of the current layout. [3](#0-2) 

The one place with a real (but out-of-scope) rough edge is `tools/fork-network/src/storage_mutator.rs`'s `write_bandwidth_scheduler_state`, an offline fork-network/operator tool used during manual resharding of forked state, which is not part of the on-chain protocol path and not reachable by an unprivileged attacker submitting transactions. [4](#0-3) 

Since the described growth mechanism (stale entries accumulating in `update_scheduler_state`) does not exist in the actual implementation, there is no exploitable unbounded storage growth path reachable by an ordinary transaction-submitting attacker.

    /// Iterate over all links from senders to receivers without borrowing &self.
    /// Allows to modify other fields of the struct while iterating over links.
    fn iter_links(&self) -> impl Iterator<Item = ShardLink> + 'static {
        let num_indexes: usize =
            self.shard_layout.num_shards().try_into().expect("num_shards doesn't fit into usize!");
        (0..num_indexes)
            .map(move |sender_idx| {
                (0..num_indexes).map(move |receiver_idx| ShardLink::new(sender_idx, receiver_idx))
            })
            .flatten()
    }

    /// Update the persistent scheduler state after running the scheduler algorithm.
    /// This state is persisted in the trie between runs.
    fn update_scheduler_state(&self, state: &mut BandwidthSchedulerStateV1) {
        let mut new_state_allowances: Vec<LinkAllowance> = Vec::new();

        for link in self.iter_links() {
            if let Some(link_allowance) = self.link_allowances.get(&link) {
                new_state_allowances.push(LinkAllowance {
                    sender: self.shard_layout.get_shard_id(link.sender).unwrap(),
                    receiver: self.shard_layout.get_shard_id(link.receiver).unwrap(),
                    allowance: *link_allowance,
                });
            }
        }

        state.link_allowances = new_state_allowances;
    }

    // TODO: maybe do something other than this
