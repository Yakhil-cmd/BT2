## Title
Operator-precedence bug in `provision?` bypasses `review_stacks_enabled` for label-gated behaviors - (File: `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb`)

### Summary
`OpenedHandler#provision?` combines `repository.review_stacks_enabled` with three OR'd behavior clauses using Ruby's default operator precedence, where `&&` binds tighter than `||`. As a result, `review_stacks_enabled` is only ANDed into the `allow_all?` clause — it is never consulted for `allow_with_label?` or `prevent_with_label?`. `LabeledHandler#respond_to_label_change?` correctly ANDs `review_stacks_enabled` across the whole expression, so the two handlers diverge on the same repository record.

### Finding Description
The claimed binding — `review_stacks_enabled` value consulted by `OpenedHandler#provision?` == the value consulted by `LabeledHandler#respond_to_label_change?` for the same repository — is broken by operator precedence.

`OpenedHandler#provision?`: [1](#0-0) 

Ruby parses this as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`, so when `review_stacks_enabled == false` and `provisioning_behavior == "allow_with_label"`, the second disjunct alone (`allow_with_label? && has_label?`) can make `provision?` return `true`, independent of `review_stacks_enabled`.

`LabeledHandler#respond_to_label_change?`, by contrast, ANDs `review_stacks_enabled` into the entire predicate: [2](#0-1) 

`process` gates directly on this predicate: [3](#0-2) [4](#0-3) 

Attacker's exact request: an unprivileged GitHub user who can open a PR against a repository configured with `review_stacks_enabled = false` and `provisioning_behavior = allow_with_label` opens the PR with the provisioning label already attached (GitHub allows setting labels at PR-open time for one's own PR/fork, no special permission required beyond opening the PR). This triggers a `pull_request` `opened` webhook (`POST /webhooks`) that Shipit processes via `OpenedHandler`. Because of the precedence bug, `provision?` returns `true` and `ReviewStackAdapter#find_or_create!` creates (and queues for provisioning) a `ReviewStack` despite the repository owner having explicitly disabled review stacks. Sending a subsequent `labeled` event does not undo this: `LabeledHandler#respond_to_label_change?` correctly short-circuits on `review_stacks_enabled == false` and no-ops, so the improperly-created stack is never archived and remains queued/provisionable.

Existing guards do not catch this: `ExplicitParameters` schema validation only enforces payload shape, not business logic; `verify_signature`/webhook auth is irrelevant here since the flow does not require a forged signature — a repository owner with a legitimate GitHub App installation naturally emits this webhook when any contributor opens a labeled PR. No model validation exists to prevent stack creation when `review_stacks_enabled` is false; that enforcement is entirely the responsibility of the handler predicate, which is broken by precedence.

### Impact Explanation
A `Shipit::ReviewStack` record is created and queued for provisioning (`awaiting_provision: true`) for a repository whose owner explicitly disabled the review-stacks feature (`review_stacks_enabled = false`), bypassing that repository-level authorization control. Once queued, `ReviewStackProvisioningQueue` will call the registered `ProvisioningHandler#up` for the stack [5](#0-4) , which in host applications can provision real infrastructure (e.g., Kubernetes namespaces) — i.e., an unauthorized deploy-adjacent action performed against a repository's explicit configuration. This is repeatable against any repository configured with `review_stacks_enabled = false` + `allow_with_label`, by any user able to open a PR with the label attached, and does not require any Shipit credential.

### Likelihood Explanation
Preconditions are narrow but plausible and match real deployments: the repository must have `review_stacks_enabled = false` and `provisioning_behavior = "allow_with_label"` (or `prevent_with_label`, similarly affected — need `has_label?` false, trivially satisfied by omitting the label). Attacker cost is trivial — opening a PR and applying a label they control on their own fork/PR requires no special GitHub permission and no Shipit secret. The bug is deterministic (pure boolean-logic defect), not a race condition, and reproducible on every PR-open against a misconfigured-in-this-specific-way repository.

### Recommendation
Add explicit parentheses in `OpenedHandler#provision?` (and mirror in `ReopenedHandler#unarchive?`, which has the identical pattern) so `review_stacks_enabled` gates the entire disjunction:
```ruby
def provision?
  repository.review_stacks_enabled && (
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
  )
end
```

### Proof of Concept
Minitest in `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` (or a cross-handler regression test):
1. Configure `repository.review_stacks_enabled = false`, `provisioning_behavior = :allow_with_label`, `provisioning_label_name = "pull-requests-label"`.
2. Build `payload = payload_parsed(:pull_request_opened)`; append `{"name" => "pull-requests-label"}` to `payload["pull_request"]["labels"]`.
3. Assert `assert_difference -> { Shipit::Stack.count }, 1 do OpenedHandler.new(payload).process end` — demonstrates `provision?` wrongly returns true despite `review_stacks_enabled == false`.
4. Immediately call `LabeledHandler.new(payload_parsed(:pull_request_labeled)_with_same_label).process` on the same repo/PR and assert `assert_no_difference -> { Shipit::Stack.count }` and that the stack created in step 3 is not archived — demonstrating `respond_to_label_change?` correctly no-ops (`review_stacks_enabled == false`), proving the two predicates disagree on the identical `repository.review_stacks_enabled` value for the same repository.
