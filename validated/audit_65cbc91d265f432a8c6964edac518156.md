## Analysis

I found a valid analog. The bug-class here (an authorization check bound to the wrong field/identity) maps to a real trust-boundary break in Shipit's multi-organization webhook signature verification.

### Title
GitHub webhook signature is verified against the organization named in the payload, not the organization owning the repository the handler actually acts on - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
Shipit supports multiple GitHub organizations, each with its own `GitHubApp` config (including an optional per-org `webhook_secret`) selected via `Shipit.github(organization:)`. The webhook signature check picks which org's secret to verify against using the attacker-controlled `repository.owner.login` (or `organization.login`) field of the request body, while the event handlers that actually mutate state (sync a stack, create a commit status, etc.) key off a *different* attacker-controlled field: `repository.full_name` (or, for `status` events, no repository field at all).

### Finding Description
`WebhooksController#verify_signature` resolves the GitHub App/secret to check the signature against purely from the payload itself: [1](#0-0) [2](#0-1) 

`repository_owner` is read from `params.dig('repository', 'owner', 'login')`, i.e., attacker-controlled JSON body content, not anything cryptographically tied to which org the request truly came from.

`Shipit.github(organization:)` looks up that org's config case-insensitively and instantiates a `GitHubApp` scoped to whatever `webhook_secret` (possibly blank) is configured for it: [3](#0-2) 

If that org has no `webhook_secret` configured (shown as a supported, documented configuration in `config/secrets.development.shopify.yml:9,18` and `docs/setup.md`), `verify_webhook_signature` short-circuits to `true` unconditionally: [4](#0-3) 

Meanwhile, the actual event handlers never look at `repository.owner.login` at all. `Handler#repository_name` (used to resolve the target `Repository`/`Stack`) reads `repository.full_name`: [5](#0-4) 

And `PushHandler#process` acts on whatever stacks that repository resolves to, triggering a GitHub sync of the target branch: [6](#0-5) 

`StatusHandler` is even less scoped — it doesn't reference the repository at all, matching purely by commit SHA across the entire installation: [7](#0-6) 

**Binding broken (equality that should hold but doesn't):**
`organization authenticated via repository.owner.login` (used to pick the signature-verification secret) `== organization/repository actually written` (`repository.full_name`, or nothing at all for `status`).

Before the attack: signature verification is intended to prove "this request genuinely originates from GitHub for organization X," and handlers assume the payload's repository fields describe a repository that org X is entitled to notify about.

After the attacker's crafted request: an attacker sends a webhook POST with `repository.owner.login` (or `organization.login`) set to an org that is either (a) configured on the same Shipit instance without a `webhook_secret`, or (b) an org whose secret the attacker otherwise knows/controls (e.g. their own onboarded org/app), while setting `repository.full_name` to an unrelated victim repository already tracked by Shipit under a different org. `verify_signature` passes (trivially in case (a), or with a correctly computed HMAC in case (b)), yet the dispatched handler performs its action against the victim repository/stack/commit, which the "authenticated" organization never had any relationship to.

### Impact Explanation
This breaks the intended per-organization trust boundary between GitHub Apps configured for different orgs on one Shipit instance. Concretely:
- `push` events can force a `GithubSyncJob`/`sync_github` on any stack whose repository full_name is guessable, regardless of which org's credentials were used to authenticate the request.
- `status` events (`StatusHandler`) let the attacker inject a fabricated `commit_status` for **any commit SHA tracked anywhere on the instance**, with no repository binding check at all; forged "success" statuses can satisfy deploy/merge conditions elsewhere in the engine, leading to an unauthorized deploy — this lands squarely in the "unauthorized deploy" Critical-impact category defined in scope.

### Likelihood Explanation
Exploitability depends on Shipit being configured with more than one GitHub org (a supported, documented feature — `docs/setup.md`, `config/secrets.development.shopify.yml`) where at least one org has no `webhook_secret`, or on the attacker controlling/knowing any one org's secret (e.g., by installing their own GitHub App on their own repo pointed at the same Shipit instance, which is an unprivileged, self-service action). No repository write access, session, or `ApiClient` token is required — only the ability to send an unauthenticated HTTP POST to the public `/webhooks` endpoint.

### Recommendation
Bind signature verification to the same repository/organization identity the handler will act on: after selecting the `GitHubApp` for verification, re-derive the org from `repository.full_name` (or reject payloads where `repository.owner.login` and the owner segment of `repository.full_name` disagree) before dispatching to handlers. Additionally, `StatusHandler` should scope its `Commit` lookup to the repository named in the payload rather than matching by SHA alone across the whole installation.

### Proof of Concept
1. On a Shipit instance configured with two orgs in `secrets.github`, e.g. `attacker-org` (no `webhook_secret` configured) and `victim-org` (repo `victim-org/app` already tracked as a Shipit stack).
2. POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/app" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check"
}
```
3. `verify_signature` calls `Shipit.github(organization: "attacker-org")`; since `attacker-org` has no `webhook_secret`, `verify_webhook_signature` returns `true` regardless of the (even absent/garbage) `X-Hub-Signature` header.
4. `StatusHandler.call` runs, and `Commit.where(sha: params.sha)` finds the victim's commit and calls `create_status_from_github!`, creating a forged passing status that can unblock deploy conditions on `victim-org/app` — all without ever presenting valid credentials for `victim-org`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
