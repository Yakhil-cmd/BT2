### Title
Webhook signature check keys off an attacker-controlled `repository.owner.login` field while the actual event target is a different, unsigned `repository.full_name` field, allowing forged GitHub events for any tracked stack whenever any configured GitHub App has no `webhook_secret` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and thus which `webhook_secret`) to verify a webhook against by reading `repository.owner.login` out of the *unauthenticated* request body itself, then that app's `verify_webhook_signature` short-circuits to `true` whenever no `webhook_secret` is configured for that organization. The event handlers, however, resolve the actual `Stack`/`Repository` to act on using a *different* field from the same payload: `repository.full_name`. An attacker who knows any one configured organization has no `webhook_secret` (an explicitly documented, supported configuration) can post an arbitrary JSON payload naming that organization in `repository.owner.login` (to sail through the no-op signature check) while naming any other tracked repository in `repository.full_name`, forging `push`, `status`, `check_suite`, `pull_request`, or `membership` events for stacks belonging to organizations that *do* have a secret configured.

### Finding Description
`verify_signature` picks the signing key from a payload field before verifying anything: [1](#0-0) [2](#0-1) 

The verification itself is a no-op when no secret is set for the selected organization: [3](#0-2) 

`webhook_secret` is documented as optional and defaults to `nil`: [4](#0-3) [5](#0-4) 

Meanwhile, every webhook handler resolves the *target* stack from a **different** payload field, `repository.full_name`, not `repository.owner.login`: [6](#0-5) 

This is the broken binding: the organization whose key "authenticated" the request (`repository.owner.login`) is not the repository that the handler actually writes to (`repository.full_name`). Because the whole raw body is HMAC-signed as a unit, an attacker cannot forge a signature for an org that *does* have a secret — but they don't need to: they only need to make the `owner.login` field point at any org configured with no secret (a supported, documented setup), while making `full_name` point at any other tracked repository, secured or not. `verify_webhook_signature` returns `true` immediately for that org regardless of the signature header, and the event is then dispatched against the attacker-chosen target repository.

Concrete exploitable handler: `MembershipHandler` trusts the forged payload to create/find a `Team` by the payload's `team.id`/`organization.login` and add an arbitrary `member.login` to it: [7](#0-6) 

Team membership is exactly the authorization gate checked by `Shipit::Authentication`/`User#authorized?`: [8](#0-7) [9](#0-8) 

`PushHandler`/`StatusHandler`-style handlers similarly act on whichever stack `Repository.from_github_repo_name(repository_name)` resolves to, unconditionally trusting `full_name`: [10](#0-9) 

### Impact Explanation
- If an attacker can construct a payload where `repository.owner.login` names any GitHub App/org configured in `Shipit.github` with a blank `webhook_secret`, the signature gate is fully bypassed for that request regardless of what `repository.full_name` (or `team`/`member`/`organization` for the `membership` event) contains.
- Via `membership` events, this escalates into `Shipit.github_teams` authorization by adding an arbitrary GitHub login to a Shipit-recognized team, granting that account access to the application (High impact per the stated criteria).
- Via `push`/`status`/`check_suite` events, this lets the attacker forge sync/CI-state signals against any stack tracked by the instance, independent of the organization the stack actually belongs to, undermining the trust boundary between "which org's secret validated this webhook" and "which repository's data will be acted upon."
- This requires no Shipit session, API token, or GitHub credentials — only knowledge that some configured org in the instance has no `webhook_secret`, which is the documented default/optional state.

### Likelihood Explanation
The webhooks endpoint is deliberately unauthenticated (`skip_before_action :verify_authenticity_token`) and public by design, so any internet client can POST to it. `webhook_secret` being left unset is explicitly presented as an "(optional)" field in `docs/setup.md` and the example secrets files ship it as `nil`, making this a realistic, supported operator configuration rather than a misconfiguration outside the engine's documented behavior. The only precondition is that the multi-org (or even single-org) deployment has at least one configured GitHub App without a webhook secret — a condition the attacker can discover by simply omitting/guessing a signature and observing a 200 response for events scoped to that org.

### Recommendation
- Never let a value taken from the unauthenticated payload determine which secret is used to authenticate that same payload; instead the signature verification should not special-case "no secret configured" as automatic success, or that special case should only apply when the organization is the sole configured one and cannot be spoofed to redirect verification for a request that targets another organization's repositories.
- After signature verification succeeds, cross-check that the organization that verified the signature (`repository_owner`) matches the owner implied by `repository.full_name` before dispatching to handlers; reject mismatches.
- Consider requiring a non-blank `webhook_secret` for every configured GitHub App when running in multi-org mode, and log/alert when a webhook is accepted purely because no secret was configured.

### Proof of Concept
Assume the instance's `config/secrets.yml` configures two orgs: `open-org` (no `webhook_secret`, e.g. per `docs/setup.md` "optional") and `secure-org` (has `webhook_secret`), and Shipit tracks a stack for `secure-org/target-repo`.

```
POST /webhooks HTTP/1.1
X-Github-Event: membership
Content-Type: application/json
(no X-Hub-Signature header, or any garbage value)

{
  "action": "added",
  "repository": { "owner": { "login": "open-org" }, "full_name": "secure-org/target-repo" },
  "organization": { "login": "secure-org" },
  "team": { "id": 999, "name": "Shipit Deployers", "slug": "shipit-deployers", "url": "https://api.github.com/teams/999" },
  "member": { "login": "attacker-account" }
}
```

1. `WebhooksController#verify_signature` computes `repository_owner` as `"open-org"` and calls `Shipit.github(organization: "open-org").verify_webhook_signature(...)`.
2. Because `open-org` has no `webhook_secret`, `verify_webhook_signature` returns `true` immediately — the request passes with no valid signature at all.
3. `MembershipHandler#process` runs with the full attacker-supplied payload, creates/finds the `team` (id `999`, org `secure-org`) and adds user `attacker-account` as a member.
4. If `Shipit.github_teams` includes `secure-org/shipit-deployers`, `attacker-account` (once it authenticates via GitHub OAuth) now passes `User#authorized?` and gains access to the Shipit instance for `secure-org`, despite never having a legitimate signed webhook from `secure-org`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
