### Title
Front-running the permissionless `initialize` instruction lets an attacker set an arbitrary initial pool price - ([File: programs/cp-swap/src/instructions/initialize.rs])

### Summary
The `initialize` instruction that creates a new constant-product pool is callable by anyone and derives the pool's initial exchange rate solely from the `init_amount_0`/`init_amount_1` amounts actually deposited by whoever submits the transaction first, with no reservation of the pool for its intended creator. This is the same root cause as the referenced Algebra `initialize` finding: an unprivileged actor observing a pending pool-creation transaction can race it and set the initial price of the pool to whatever ratio benefits them, since the deterministic `pool_state` PDA belongs to whoever lands first.

### Finding Description
`Initialize::creator` is documented as "Address paying to create the pool. Can be anyone" [1](#0-0) . The `pool_state` account is a deterministic PDA derived only from `amm_config`, `token_0_mint`, and `token_1_mint` (unless the caller opts into a random keypair) [2](#0-1) , so the address that a legitimate pool creator will use is fully predictable in advance from public mint addresses.

Inside `initialize`, the pool's starting invariant/price is derived from the actual token balances transferred into the vaults, not from any pre-committed or access-controlled value: [3](#0-2) 

Because the PDA-derivation is public and creation is permissionless, an attacker who observes a legitimate creator's pending `initialize` transaction (same technique described in the report — watching for the instruction targeting a known mint pair before it lands) can submit their own `initialize` transaction for the same `token_0_mint`/`token_1_mint`/`amm_config` triple first, using a tiny, heavily skewed `init_amount_0`/`init_amount_1` ratio of their own choosing. Since Solana account initialization is first-come-first-served on the deterministic PDA, the attacker's transaction succeeds, mints themselves the LP supply computed as `sqrt(amount_0 * amount_1)` minus the fixed `lock_lp_amount = 100` [4](#0-3) , and becomes the pool's initial LP holder — at whatever price ratio they picked. `CurveCalculator::validate_supply` only checks that both amounts are non-zero; it does not validate or bound the ratio in any way [5](#0-4) .

The legitimate creator's original `initialize` transaction then fails (the PDA is already initialized), so their large intended deposit either reverts entirely, or — if instead reissued as a subsequent `deposit` call at the now-attacker-controlled price — the creator is forced to deposit at the manipulated ratio, transferring value to the attacker via the constant-product curve. The `initialize_with_permission` path is not vulnerable to the exact same "anyone can call it" surface as it requires an authorized `permission` PDA, but it is still susceptible to key- and amount-based ratio manipulation by the account listed as `payer` [6](#0-5) , though that path is gated behind a permission check and is less directly comparable to the original unpermissioned report.

### Impact Explanation
An attacker with minimal capital can seize the first-mover position on a soon-to-launch pool, forcing the legitimate liquidity provider to either lose their transaction (denial of pool creation at the intended terms) or deposit/swap into a pool whose price is arbitrarily skewed in the attacker's favor, enabling the attacker to extract value once the legitimate large deposit or subsequent swaps interact with the mispriced pool. This matches the "Medium" classification of the original report: it does not directly steal already-escrowed funds, but it does let an unprivileged actor impose an unauthorized, favorable initial price/ownership state on the pool that legitimate participants did not agree to.

### Likelihood Explanation
Exploitation requires only observing a pending `initialize` transaction for a specific mint pair (public mempool/gossip visibility) and submitting a competing transaction with a higher priority fee for the same deterministic PDA — a single transaction, no elevated privileges, and no dependency on any non-default feature. This is directly analogous to, and at least as practical as, the original Algebra mempool-frontrunning scenario, since Solana's PDA derivation makes the target account address public and precomputable well before the legitimate creator's transaction lands.

### Recommendation
- Require pool creation to go through the permissioned path (`initialize_with_permission`) for pools where price integrity at launch matters, or add a creator-authorization check (e.g., only allow the transaction signer to match a pre-registered "intended creator" for that PDA).
- Alternatively, split pool creation into two steps: first reserve/allocate the `pool_state` PDA (locking out competitors), then have only the reserving account supply `init_amount_0`/`init_amount_1` in a follow-up instruction.
- Document prominently (as the original report's judges concluded) that on-chain pricing of freshly created/low-liquidity pools should not be trusted, and consider enforcing a minimum liquidity/maximum initial ratio-deviation check in `CurveCalculator::validate_supply`.

### Proof of Concept
1. Legitimate creator Alice builds and broadcasts an `initialize` transaction for `token_0_mint`/`token_1_mint` under a known `amm_config`, depositing a fair-value `init_amount_0`/`init_amount_1` ratio.
2. Attacker Bob observes the pending transaction (same mint pair, same `initialize` discriminator) and computes the same deterministic `pool_state`, `token_0_vault`, `token_1_vault`, `lp_mint` PDAs via `Pubkey::find_program_address` using the public seeds shown in `create_pool` [2](#0-1) .
3. Bob submits his own `initialize` instruction for the same mint pair with a higher priority fee and a heavily skewed `init_amount_0`/`init_amount_1` ratio, using only capital he controls.
4. Bob's transaction lands first, creating the `pool_state` PDA at the manipulated price and minting the LP supply to Bob per the liquidity formula at lines 294-316.
5. Alice's original transaction fails (PDA already initialized) or, if resubmitted as a `deposit`, executes against Bob's mispriced pool, allowing Bob to profit by swapping/withdrawing against Alice's subsequent liquidity contribution.
