### Title
`Api::CCMenuController#show` bypasses stack scoping by overriding `stack` with unscoped `Stack.from_param!` - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::CCMenuController` defines its own private `stack` method that resolves the target stack via `Stack.from_param!(params[:stack_id])` directly, instead of using the inherited scoped `stacks.from_param!` from `Api::BaseController`. This means the invariant "an `ApiClient` token bound to `stack_id` can only resolve stacks within that scope" is violated for the ccmenu endpoint: any valid `ApiClient` token with `read:stack` permission (including a stack-scoped one, or a leaked ccmenu `?token=` URL) can fetch ccmenu XML for **any** stack in **any** repository by supplying a different `stack_id` in the path.

### Finding Description
The invariant claimed by the base controller is:
`stacks == current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`, and `stack == stacks.from_param!(params[:stack_id])` [1](#0-0) .

However, `Api::CCMenuController` overrides `stack` to bypass this scoping entirely:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [2](#0-1) 

So the actual binding used by `show` is `stack == Stack.from_param!(params[:stack_id])` — unscoped by `current_api_client.stack_id`, unlike every other resource under `Api::BaseController` (e.g. `Api::StacksController`, which reuses the inherited `stack`/`stacks` from the base controller) [3](#0-2) .

The only gate on the action is `require_permission :read, :stack`, which calls `current_api_client.check_permissions!(:read, :stack)` [4](#0-3) [5](#0-4) . `check_permissions!` only checks the `permissions` array (e.g. `read:stack`) and never checks `stack_id` [6](#0-5) . The `ApiClient` created by `CCMenuUrlController#client` for the "CCMenu Client" feature is exactly such a token: it is created with `permissions: %w[read:stack]` and no `stack_id` restriction is enforced at check time, and is delivered embedded in a `?token=` query string URL meant for one specific stack [7](#0-6) .

Authentication for this controller is also overridden to accept the token from `params[:token]` (URL query string) instead of only Basic Auth headers [8](#0-7) , which is by design for the ccmenu.xml integration, but combined with the unscoped `stack` lookup, means the leaked/observed token (present in plaintext in browser history, CI logs, referrer headers, etc., or brute-forced since the format is a signed integer ID) is redeemable against **every** stack in the Shipit instance, not just the one it was minted for.

**Exploit flow**: Attacker obtains any `ApiClient` token with `read:stack` permission — for example, by observing/leaking a ccmenu URL generated for stack A (`GET /api/stacks/:stack_id/ccmenu?token=...`). The attacker then sends `GET /api/stacks/<stack_id_of_B>/ccmenu?token=<leaked_token>` where B is an unrelated stack/repository. Because `stack` resolves via unscoped `Stack.from_param!`, the request succeeds and returns stack B's latest deploy/rollback XML status (`app/views/shipit/ccmenu/project`), disclosing deploy state for a repository the token was never authorized against.

Existing guards fail to prevent this: `require_permission!`/`check_permissions!` only validate the permission bitset, not stack scope; the `stacks` scoping method in `BaseController` exists precisely to enforce this scoping but is never called because `CCMenuController` shadows `stack` with its own unscoped implementation.

### Impact Explanation
An attacker holding any `read:stack`-permissioned `ApiClient` token — including one legitimately scoped to a single stack via the CCMenu URL feature — can read deploy/task status for arbitrary stacks across arbitrary repositories on the Shipit instance. This is unauthenticated (relative to the target repository) disclosure of stack state and deploy output for tenants the token holder has no relationship with, matching the "High — unauthenticated read of stack state, task streams or deploy output" category. It is fully repeatable against any stack ID on the instance, one request per stack, no rate limiting observed. Blast radius is instance-wide: every repository/stack hosted by the same Shipit deployment is exposed to any holder of any `read:stack` token.

### Likelihood Explanation
Preconditions: attacker needs a single valid `ApiClient` token with `read:stack` permission for any stack — a ccmenu URL from any legitimate CCMenu widget setup (e.g. observed on a colleague's screen, in a CI dashboard, in browser history, in a proxy log, or via a leaked link) suffices, since the token itself is not stack-restricted at check time. No GitHub credentials, no session, no webhook secret, no operator role required. Cost is minimal (one HTTP GET per target stack) and fully automatable/repeatable.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the inherited scoped resolution instead of overriding it with an unscoped lookup, i.e. remove the private `stack` override and rely on `Api::BaseController#stack` (`stacks.from_param!(params[:stack_id])`), so the ccmenu action honors `current_api_client.stack_id` scoping identically to every other `Api::BaseController` subclass.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb
module Shipit
  module Api
    class CCMenuControllerTest < ActionController::TestCase
      test "scoped token cannot fetch ccmenu for a stack in another repository" do
        stack_a = shipit_stacks(:shipit)
        stack_b = shipit_stacks(:cyclimse) # a different repository/stack

        scoped_client = ApiClient.create!(
          creator: shipit_users(:walrus),
          name: "Scoped CCMenu client",
          permissions: %w[read:stack],
          stack: stack_a
        )

        # Binding under test: stack resolved by ccmenu#show must equal
        # stacks.from_param!(params[:stack_id]) where stacks is scoped to
        # current_api_client.stack_id (stack_a), NOT Stack.from_param! unscoped.
        get :show, params: { stack_id: stack_b.to_param, token: scoped_client.authentication_token }

        assert_response :not_found # or :forbidden -- must NOT be :ok / 200
        refute_equal stack_b, assigns(:stack)
      end
    end
  end
end
```
Before the fix, this request returns `200 OK` with stack B's ccmenu XML (violating the invariant); after routing `stack` through the scoped `stacks` collection, it returns `404`/`403`, matching the stated invariant.
