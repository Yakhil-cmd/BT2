### Title
Any secondary-AA bounce reverts the entire primary AA response chain, allowing attacker-controlled "receiver" AAs to griefing/DoS legitimate AA logic - (File: `aa_composer.js`)

### Summary
`aa_composer.js` automatically re-triggers any address that receives a payment from an AA response, if that address happens to have an AA definition (`handleSecondaryTriggers`). If that secondary AA "bounces" (fails), the failure is propagated all the way up and the **entire chain of AA responses stemming from the primary trigger is discarded** via `revert()` — not just the failed branch. This means anyone can deploy a trivial "always-bounce" AA and use its address as the destination of a payment made by another AA (e.g. a refund/payout/outbid-refund target chosen by the attacker), permanently forcing that AA's legitimate operation to fail whenever it must pay the attacker-controlled address, mirroring the NFTX pattern where a malicious "receiver" can halt a shared distribution routine for everyone.

### Finding Description
When a primary AA trigger produces a response unit, `sendUnit()`/`handleSecondaryTriggers()` looks at every output address of that unit and, if the address is itself an AA, invokes `handleTrigger()` recursively as a secondary trigger: [1](#0-0) 

If any of these secondary (or nested) triggers bounces, the error is bubbled up: an intermediate secondary AA simply re-bounces itself (`if (bSecondary) return bounce(err);`), and at the top (primary, non-secondary) level the whole chain is unwound with `revert()`: [2](#0-1) 

`revert()` rolls back **all** previously accumulated responses/state/balances for the entire trigger chain (`revertResponsesInCaches`, `ROLLBACK TO SAVEPOINT`, `arrResponses.splice(0, arrResponses.length)`), then calls `bounce()` on the primary trigger: [3](#0-2) 

Any address can trivially be made to "always bounce": if an AA definition has no `messages` field, `handleTrigger` unconditionally bounces every trigger sent to it: [4](#0-3) 

Because AA addresses are simply the hash of their definition (`objectHash.getChash160`), an attacker can freely mint an "always-bounce" AA address (analogous to `X55IW...` addresses used in the test fixtures) and get it used as an output destination of *any other* AA — e.g. as a refund address, an outbid-refund target in an auction-style AA, a beneficiary/oracle address supplied via `trigger.data`, or simply `trigger.address` when the attacker is the one sending the trigger. Whenever the victim AA subsequently tries to pay that address (a normal, expected code path, e.g. `outputs: [{address: "{trigger.address}", amount: ...}]` seen throughout the test suite), the payment automatically re-triggers the attacker's AA, which bounces and forces `revert()` to discard the *entire* primary trigger's work — exactly analogous to the NFTX `_sendForReceiver` bug where a single malicious receiver could abort the whole `distribute()` loop for all other legitimate receivers.

### Impact Explanation
This is not merely wasted gas: `revert()` discards *all* state variables and responses computed by the primary AA and any already-processed sibling secondary AAs in the same chain, and then treats the whole primary trigger as bounced. Any AA design that must pay out to an address influenced by an untrusted party (auction outbid refunds, marketplace payouts, referral/beneficiary addresses, arbitrary payout addresses supplied in `trigger.data`, or simply returning change/refunds to `trigger.address`) can be permanently blocked by an attacker who registers such an address as an always-bouncing AA. This satisfies "AA fund loss or freezing": legitimate funds sent to the vulnerable AA get bounced back (minus bounce fees) every time, and the AA's core business logic (e.g., accepting a higher bid, completing a payout) can never successfully execute as long as the attacker keeps the poisoned address as a required payee, effectively locking/DoSing that AA's operation.

### Likelihood Explanation
High likelihood: defining a new AA (and thus a new address with attacker-chosen bounce behavior) requires no special privilege — any unit poster can post an AA definition and any AA trigger sender can subsequently interact with other AAs using that address as `trigger.address` or by influencing output-address fields (e.g. via `trigger.data`). Many idiomatic AA patterns (returning refunds/change to `trigger.address`, forwarding to a caller-provided destination, auction-style "refund previous highest bidder") are directly reachable by an ordinary trigger sender, matching the exact reachable-actor classes required (AA trigger sender / AA author).

### Recommendation
Do not let a failure of one secondary AA revert the entire chain of already-successful AA responses. Isolate the effects of a bounced secondary trigger to its own branch (e.g., treat the failed leg the same way a normal output payment failure to a non-AA address would be treated — the payment stands, only the secondary AA's own state change is skipped/bounced) instead of calling `revert()` on the whole primary response. At minimum, cap/limit unconditional propagation of secondary bounce failures so a single uncooperative recipient AA cannot invalidate previously computed, unrelated AA state changes and payments in the same chain.

### Proof of Concept
1. Attacker defines and posts a minimal AA with no `messages` field (or logic that unconditionally bounces), e.g. `['autonomous agent', {}]`; its address is `evilAddr` (computed via `chash160`).
2. Attacker posts a trigger unit authored by `evilAddr` to a victim AA `V` that (as is common) sends a refund/change/bid-refund payment back to `trigger.address` (see the pattern used throughout `test/aa_composer.test.js`, e.g. `outputs: [{address: "{trigger.initial_address}", amount: ...}]`).
3. `V`'s response unit contains an output to `evilAddr`; `handleSecondaryTriggers` (aa_composer.js:1702) detects `evilAddr` is an AA and invokes `handleTrigger` on it as `bSecondary=true`.
4. The secondary trigger immediately bounces (`return bounce('no messages')`, aa_composer.js:1868-1870), causing `handleSecondaryTriggers`'s `async.eachSeries` callback to receive an error (aa_composer.js:1743).
5. Since the failing call chain originates from the primary (non-secondary) trigger, `revert({message: "one of secondary AAs bounced with error: ", ...})` is invoked (aa_composer.js:1749), discarding all of `V`'s state changes/responses and bouncing the original trigger — reproducing the "malicious receiver DoSes the shared distribution routine" pattern described in the report.
