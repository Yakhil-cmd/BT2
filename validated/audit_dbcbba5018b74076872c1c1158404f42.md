### Title
Annotated tag peeled by `rev-parse FETCH_HEAD^{}` to a non-commit object (tree/blob) causes permanent sync stall in `repoSync.SyncRepo` - ([File: main.go])

### Summary
`git-sync` resolves the fetched ref with `git rev-parse FETCH_HEAD^{}` [1](#0-0)  and feeds the result directly to `git reset --soft <remoteHash> --` [2](#0-1) . Git's `^{}` peel operator only guarantees dereferencing through a chain of tag objects to the first non-tag object — it does **not** guarantee a commit. An attacker with push access who creates an annotated tag pointing at a tree or blob (or a chain of tags terminating in one) can make `remoteHash` a non-commit object id, which `git reset --soft` then rejects every sync cycle, permanently stalling `SyncRepo`.

### Finding Description
In `SyncRepo`, after `git.fetch` retrieves the ref, the code assumes peeling an annotated tag always yields a commit: "The ^{} syntax 'peels' annotated tags to their underlying commit hashes" [3](#0-2) . This is incorrect: per gitrevisions semantics, `<rev>^{}` dereferences tag objects recursively until a non-tag object is reached — that object can be a tree or a blob just as easily as a commit, if that is what the tag object points to.

If an attacker pushes such a tag as (or matching) the ref git-sync is configured to track, `rev-parse FETCH_HEAD^{}` succeeds and returns the tree/blob object id as `remoteHash` [4](#0-3) . Because this differs from `currentHash`, the "update required" branch executes and calls `git reset --soft <remoteHash> --` [5](#0-4) . `git reset --soft` requires a commit-ish; passing a raw tree/blob object id (not a tag, so no further peeling is attempted by `reset` itself) causes git to fail with a non-zero exit, and `git.Run` returns an error that `SyncRepo` propagates immediately, before `createWorktree` is ever invoked [6](#0-5) .

Because the failure occurs at the `reset --soft` step (before `createWorktree`/worktree naming), the worktree-naming/symlink half of the described exploit ("a worktree whose leaf name is not a commit hash") is not reachable in this code path — reset fails and aborts the sync attempt first. What *is* reachable is a persistent failure: as long as the malicious tag remains the tip of the tracked ref, every subsequent `SyncRepo` cycle re-fetches the same non-commit object and re-fails at `reset --soft`, producing a permanent inability to advance (sync wedge), since nothing in `fetch`, `isShallow`, or `rev-parse` rejects non-commit peel targets before they reach `reset`.

### Impact Explanation
This is a denial-of-service against the sync pipeline: an unprivileged repo contributor who can push refs/tags to the tracked ref can make git-sync permanently fail to converge, without ever needing elevated flags, secrets, or operator/node compromise. This matches the Kubernetes bug-bounty "persistent stall / sync wedge" impact class. It does not achieve the symlink/worktree-naming corruption also described in the question, since the offending value is rejected by `reset --soft` before any worktree is created or a symlink is published.

### Likelihood Explanation
Requires only that the attacker can push an annotated tag pointing at a tree or blob to the ref git-sync is configured to sync (`--ref`), which matches the stated threat model (unprivileged push access to the synced repo, no flags/env control needed). Depth (`--depth=1`) is irrelevant to the vulnerability — it reproduces regardless of shallow/full clone, since `FETCH_HEAD^{}` peeling is agnostic to depth. This is fully repeatable: as long as the tag/ref exists, every sync period fails identically.

### Recommendation
After computing `remoteHash` via `rev-parse FETCH_HEAD^{}`, verify the result is actually a commit object (e.g., `git cat-file -t <remoteHash>` equals `commit`, or use `rev-parse --verify FETCH_HEAD^{commit}` which fails cleanly if the peeled target is not a commit) and surface a clear, actionable error/log distinguishing "ref does not point to a commit" from generic reset failures, rather than looping indefinitely on the same fetch/reset failure.

### Proof of Concept
```bash
# Set up bare repo
git init --bare /tmp/upstream.git
git clone /tmp/upstream.git /tmp/work
cd /tmp/work
echo hello > file
git add file && git commit -m init
git push origin main

# Attacker pushes an annotated tag pointing at a tree (not a commit)
TREE=$(git rev-parse HEAD^{tree})
git tag -a badtag -m "malicious" "$TREE"
git push origin badtag

# Run git-sync tracking the tag
git-sync --repo=file:///tmp/upstream.git --ref=badtag --root=/tmp/root --link=link --period=2s --one-time=false

# Expected (buggy) behavior: every cycle logs an error from
# `git reset --soft <tree-sha> --` ("fatal: Cannot do soft reset ..." /
# "not a valid commit name"), METRIC_FETCH_COUNT increments but
# METRIC_GOOD_SYNC_COUNT never advances, and /tmp/root/link is never created —
# permanent sync stall.
```
