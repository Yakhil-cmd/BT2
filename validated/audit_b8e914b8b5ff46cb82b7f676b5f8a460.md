### Title
Membership webhook signature verified against attacker's own trusted org while `MembershipHandler` writes to a victim org's `Team` — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` resolves the `Shipit.github` app (and thus the HMAC secret) using `params.dig('repository','owner','login') || params.dig('organization','login')`, preferring the `repository` sub-object when present. `Shipit::Webhooks::Handlers::MembershipHandler`, however, ignores `repository` entirely and uses only `params.organization.login` to set/select the `Team`, and looks the team up by `params.team.id` (`github_id`) with no organization scoping in the finder. An attacker who controls any GitHub App/org pair independently trusted by this Shipit instance can add a synthetic `repository.owner.login` pointing at their own org to force signature verification down their own (known) secret, while `organization.login` and `team.id` in the same payload target a victim org's existing `Team`.

### Finding Description
Binding claimed and broken: `repository_owner` used in `Shipit.github(organization: repository_owner)` for HMAC verification (`app/controllers/shipit/webhooks_controller.rb:24-25,59-61`) must equal `organization.login` used by `MembershipHandler#find_or_create_team!` (`app/models/shipit/webhooks/handlers/membership_handler.rb:38-42`) to select/write the `Team` row. They are not the same read: `repository_owner` prefers `params['repository']['owner']['login']` if that key exists at all, only falling back to `params['organization']['login']` when `repository` is absent:

```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`MembershipHandler` never reads `repository` at all — it reads `organization.login` and `team.id` directly:
```ruby
def find_or_create_team!
  Team.find_or_create_by!(github_id: params.team.id) do |team|
    team.github_team = params.team
    team.organization = params.organization.login
  end
end
``` [2](#0-1) 

`MembershipHandler`'s `ExplicitParameters` schema requires `action`, `team.id/name/slug/url`, `organization.login`, `member.login`, but does not forbid or validate an extraneous `repository` key [3](#0-2) , so the attacker is free to add a `repository` object purely to steer `verify_signature`.

Attacker's exact request: POST `/webhooks` with `X-Github-Event: membership`, body:
```json
{
  "action": "added",
  "repository": {"owner": {"login": "attacker-org"}},
  "organization": {"login": "victim-org"},
  "team": {"id": <victim_team_github_id>, "name": "x", "slug": "x", "url": "http://x"},
  "member": {"login": "attacker-login"}
}
```
signed with `X-Hub-Signature` computed using `attacker-org`'s own webhook secret (an org the attacker legitimately administers and which this multi-tenant Shipit instance also trusts).

Exploit flow: `drop_unhandled_event` passes because `'membership'` is a default handler [4](#0-3) . `verify_signature` computes `repository_owner = 'attacker-org'` (repository key wins over organization), fetches `Shipit.github(organization: 'attacker-org')`, and successfully verifies the signature with the attacker's own known secret [5](#0-4) . `Shipit::Webhooks.for_event('membership')` then dispatches to `MembershipHandler`, which finds the pre-existing victim `Team` by `github_id` (unscoped by organization) and calls `team.add_member(User.find_or_create_by_login!('attacker-login'))` [6](#0-5) , creating a cross-tenant `Membership` row.

Existing guards fail to prevent this: `verify_signature`'s field-selection logic is intended for repo-scoped hooks (push/status) where `repository.owner.login` legitimately identifies the signing org, but it is reused unmodified for org-scoped events (membership) where the handler's authoritative org field is `organization.login`, not `repository.owner.login`. No code cross-checks that the two resolve to the same organization, and `Team.find_or_create_by!(github_id: ...)` performs no organization-scoping check either.

### Impact Explanation
A successful request grants the attacker (or any `member.login` they choose) membership in an existing victim-org `Shipit::Team` without ever possessing victim-org's webhook secret. Since `Shipit.github_teams` / `User#authorized?` gate stack access based on team membership, this is a cross-tenant authorization escalation — an unprivileged external attacker administering an unrelated, Shipit-trusted GitHub App/org can add themselves to a privileged team backing another tenant's stacks. It is repeatable against any victim `Team` whose `github_id` is discoverable (GitHub team IDs for public/known orgs), and against any organization pair trusted by the same multi-org Shipit instance. This matches the Critical category: escalation into `Shipit.github_teams` authorization / a payload for one organization mutating another's `Team`/`Membership` state.

### Likelihood Explanation
Requires: (1) a multi-org `Shipit.github` configuration where the attacker legitimately controls one registered GitHub App/org (a realistic precondition for any Shipit instance serving multiple orgs/customers); (2) knowledge of the victim `Team`'s `github_id` (retrievable via GitHub's public team/org APIs or leaked elsewhere); no Shipit session, API token, or victim secret is needed. The attacker cost is a single crafted HTTP POST signed with their own known secret. This is fully repeatable and scriptable.

### Recommendation
In `WebhooksController#repository_owner`, do not silently prefer `repository.owner.login` over `organization.login`; instead select the org field based on the actual event type (or require both fields, when present, to match) so that `verify_signature`'s organization always matches the organization field the corresponding handler will act upon. Additionally, `MembershipHandler#find_or_create_team!` should scope `find_or_create_by!` by both `github_id` and `organization` (matching `params.organization.login`), and should reject/raise if an existing `Team` with that `github_id` belongs to a different organization than `params.organization.login`.

### Proof of Concept
```ruby
test ":membership webhook cannot use org A's secret to write org B's Team" do
  # Stub two distinct GitHubApp instances with distinct webhook secrets, one per org
  org_a_app = Shipit::GitHubApp.new('attacker-org', webhook_secret: 'secret-a')
  org_b_app = Shipit::GitHubApp.new('victim-org', webhook_secret: 'secret-b')
  Shipit.stubs(:github).with(organization: 'attacker-org').returns(org_a_app)
  Shipit.stubs(:github).with(organization: 'victim-org').returns(org_b_app)

  victim_team = shipit_teams(:shopify_developers) # existing team with known github_id

  body = {
    action: 'added',
    repository: { owner: { login: 'attacker-org' } },
    organization: { login: 'victim-org' },
    team: { id: victim_team.github_id, name: victim_team.name, slug: victim_team.slug, url: victim_team.api_url },
    member: { login: 'attacker-login' }
  }.to_json

  signature = "sha1=#{OpenSSL::HMAC.hexdigest('sha1', 'secret-a', body)}"
  @request.headers['X-Github-Event'] = 'membership'
  @request.headers['X-Hub-Signature'] = signature

  assert_no_difference -> { victim_team.memberships.count } do
    post :create, body: body, as: :json
  end
end
```
Before the fix: `repository_owner` resolves to `'attacker-org'`, verification passes using `secret-a`, and a `Membership` row is created linking `attacker-login` to `victim_team` — the assertion fails, proving the vulnerability. After the recommended fix (org-field consistency check / scoped `find_or_create_by!`), the request is rejected or the team lookup no-ops, and the assertion passes.
