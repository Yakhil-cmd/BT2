### Title
StatusHandler#process mutates commits across all repositories matching a SHA, not just the authenticated repository - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` queries `Commit.where(sha: params.sha)` with no repository/stack scoping, unlike every other handler in the same directory (`PushHandler`, the `PullRequest::*` handlers, `CheckSuiteHandler`) which all restrict their side effects via the `stacks` helper (`Repository.from_github_repo_name(repository_name)&.stacks`). Webhook signature verification only proves the payload came from the GitHub org owning the repo named in the payload, not that the mutation is confined to that repo's commits.

### Finding Description
The binding that should hold is: `repository_owner-authenticated-by(signature) == repository that owns every Commit row mutated by this payload`. Tracing the code:

- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) validates the HMAC signature using `Shipit.github(organization: repository_owner)`, where `repository_owner = params.dig('repository', 'owner', 'login')`. This only proves the payload was signed by the app installed for that GitHub org/repository — it says nothing about which `Commit` rows may be touched.
- `WebhooksController#create` then dispatches to `Shipit::Webhooks.for_event('status') => [Handlers::StatusHandler]` and calls `handler.call(params)` → `StatusHandler.new(params).process` (`app/models/shipit/webhooks/handlers/handler.rb:15-24`).
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`):
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This ignores the `repository` field in the payload entirely and never calls the `stacks` helper that `Handler` provides (`Handler#stacks`, `app/models/shipit/webhooks/handlers/handler.rb:32-34`), which scopes to `Repository.from_github_repo_name(repository_name)&.stacks`. Every other handler in the codebase (`PushHandler#process`, `app/models/shipit/webhooks/handlers/push_handler.rb:12-17`, and the `PullRequest::*` / `CheckSuiteHandler` handlers) uses that scoping helper before mutating anything — `StatusHandler` is the outlier.
- `Commit.by_sha`/`by_sha!` do enforce short-SHA ambiguity checks, but `StatusHandler` uses the plain `Commit.where(sha:)` scope, not `by_sha`, and it iterates **all** matching rows regardless of stack.

Attacker flow: an unprivileged attacker who owns/administers *any* one GitHub repository connected to Shipit (a low bar — they only need a repo whose org is registered in Shipit, e.g. their own fork under an org with GitHub App installed, or any tracked repo where they can trigger a `status` event, such as via a CI integration under their control) can push a commit and craft its SHA (or exploit a naturally colliding SHA — e.g. an empty initial commit, a common merge-base, or a cherry-picked commit shared across forks/stacks) so it exists as a `Commit` row in another, unrelated stack. They then send/trigger a legitimately-signed `status` webhook for their own repository with that SHA and `state: success`. Because signature verification only checks organization identity, not per-commit repository ownership, the payload is accepted, and `StatusHandler#process` updates the `Status` for **every** commit row across **every** stack sharing that SHA — including stacks/tenants the attacker never authenticated for. This can flip `Commit#deployable?` for a foreign stack's commit, enabling downstream effects such as auto-merge (`ProcessMergeRequestsJob`, referenced in `test/models/commits_test.rb:763-777`) or continuous-deployment triggers gated on commit status becoming `success`.

None of the existing guards prevent this: `verify_signature` authenticates the org of the *sender*, not the target commit's stack; `drop_unhandled_event` only checks the event type is registered; the `ExplicitParameters` schema only validates payload shape (`sha`, `state`, etc.), not repository binding; there is no `require_permission!`/`User#authorized?` check on this unauthenticated webhook path at all (by design, webhooks are validated via signature only), and the `stacks` scoping helper that would fix this is defined but simply unused by `StatusHandler`.

### Impact Explanation
A single valid webhook signed for repository A can write `Status` rows and flip `deployable?`/CD-triggering state for commits belonging to unrelated repositories/stacks B, C, ... N that happen to share the reported SHA. This is a cross-tenant write caused by a payload that only authenticated one repository, matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team"). The blast radius scales with however many stacks/tenants contain a commit with the colliding SHA, and is repeatable on every `status` webhook delivery.

### Likelihood Explanation
Requires the attacker to control (or trigger status webhooks for) at least one Shipit-tracked repository, and for a target stack to contain a `Commit` row with the same SHA. This is plausible for: empty/root commits (many repos initialized identically), shared cherry-picked/rebased commits across forks that are all tracked by Shipit, or template/scaffold-generated initial commits. No secrets, sessions, or elevated GitHub permissions are needed beyond controlling one legitimately webhook-emitting repository — the attacker cost is low and the exploit is fully repeatable per matching SHA.

### Recommendation
Scope the query in `StatusHandler#process` to the repository asserted in the payload, mirroring the `stacks` pattern used by other handlers, e.g.:
```ruby
def process
  Commit.where(sha: params.sha, stack_id: stacks.select(:id)).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
or restrict via `commit.stack.repository == Repository.from_github_repo_name(repository_name)` before calling `create_status_from_github!`.

### Proof of Concept
Minitest plan (e.g. in `test/controllers/webhooks_controller_test.rb` style, or `test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Create two stacks/repositories, `stack_a` (repository `owner/repo-a`) and `stack_b` (repository `owner-b/repo-b`), each with a `Commit` row sharing the same `sha` value (e.g. `"deadbeef" * 5`).
2. Assert baseline: `commit_a.statuses.count == 0` and `commit_b.statuses.count == 0`; `commit_a.deployable? == false` and `commit_b.deployable? == false` (both sides of the binding equal/false).
3. POST a signed `status` webhook payload for `owner/repo-a` only, with `sha: shared_sha, state: 'success'`, using `GithubHook.any_instance.stubs(:verify_signature).returns(true)` as in existing tests.
4. Assert `commit_a.statuses.count == 1` (expected, same repo) AND `commit_b.statuses.count == 1` (this should be `0` if the binding held — demonstrating the violation), and that `commit_b.reload.deployable?` flipped to `true` despite the payload never asserting ownership of `repo-b`.
