### Title
Missing parenthesization in `OpenedHandler#provision?` lets `provisioning_behavior_allow_with_label?`/`prevent_with_label?` branches provision stacks even when `review_stacks_enabled` is `false` - (File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb)

### Summary
`OpenedHandler#provision?` ANDs `repository.review_stacks_enabled` only with the first disjunct (`provisioning_behavior_allow_all?`) due to Ruby `&&`/`||` precedence, unlike `LabeledHandler#respond_to_label_change?`, which correctly wraps `review_stacks_enabled && (archive? || unarchive?)` around the whole label-driven decision. As a result, a repository configured with `review_stacks_enabled: false` and `provisioning_behavior: allow_with_label` or `prevent_with_label` will still provision a review stack on `pull_request.opened`, even though the sibling label handlers correctly refuse to act on the same repository/config.

### Finding Description
Binding claimed: `repository.review_stacks_enabled == true` must gate every branch of stack-provisioning logic reachable from a PR webhook, for both `LabeledHandler` and `OpenedHandler`.

In `LabeledHandler`: [1](#0-0) 
`review_stacks_enabled` is explicitly parenthesized to gate `(archive? || unarchive?)` as a whole - if `review_stacks_enabled` is `false`, the method returns `false` unconditionally regardless of `provisioning_behavior`.

In `OpenedHandler`: [2](#0-1) 
Ruby operator precedence (`&&` binds tighter than `||`) parses this as:
`(repository.review_stacks_enabled && repository.provisioning_behavior_allow_all?) || (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) || (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)`

`review_stacks_enabled` only gates the `allow_all` branch. The `allow_with_label` and `prevent_with_label` branches evaluate independently of `review_stacks_enabled`.

Concretely, for a repository with `review_stacks_enabled: false, provisioning_behavior: :prevent_with_label`:
- `LabeledHandler#respond_to_label_change?` on a `labeled` event returns `false` (blocked by `review_stacks_enabled`).
- `OpenedHandler#provision?` on an `opened` event with no matching label present evaluates `(false && false) || (false && ...) || (true && true) == true`, so `process` calls `ReviewStackAdapter#find_or_create!`, creating a `Shipit::Stack`/`Shipit::PullRequest` for a repository that was never opted into review-stack provisioning.

The attacker's exact action: open a pull request (no label manipulation needed for `prevent_with_label`; for `allow_with_label` the attacker needs the PR to carry the configured label, which on many repos a PR author can self-apply or which may already be present via automation) against a Shipit-tracked repository whose owner configured `provisioning_behavior` to `allow_with_label`/`prevent_with_label` but left "Dynamically provision stacks for Pull Requests?" (`review_stacks_enabled`) unchecked - a plausible, even likely, misconfiguration since the settings form exposes `provisioning_behavior` and `review_stacks_enabled` as independent, uncoupled fields. [3](#0-2) 

None of the existing guards catch this: `verify_signature`/webhook auth is orthogonal (this is a logic bug, not an auth bypass on the webhook itself), `params` schema validation only checks payload shape, and the reviewed test suite's `configure_provisioning_behavior` helper defaults `provisioning_enabled: true`, so no existing test exercises `review_stacks_enabled: false` combined with `allow_with_label`/`prevent_with_label`. [4](#0-3) [5](#0-4) 

### Impact Explanation
For any repository where an operator sets `provisioning_behavior` to `allow_with_label` or `prevent_with_label` while `review_stacks_enabled` remains `false` (the column default), an unprivileged PR author can force creation of a `Shipit::Stack`/`Shipit::PullRequest` record and queue it for provisioning (`awaiting_provision`), bypassing the repository's explicit opt-out of dynamic review-stack provisioning - a write for that repository that the repository's own configuration did not authorize. This is repeatable per repository matching this configuration and doesn't require the label handlers' path at all, since it's reached solely via `pull_request.opened`. It does not directly leak credentials or grant cross-repository writes (scope is limited to the affected repository's own `review_stacks`), but it is an unauthorized stack-provisioning action inconsistent with the repository's declared trust boundary, matching the "unauthorized deploy"/provisioning category described in the prompt's Critical bucket, contingent on what happens next in the provisioning/deploy pipeline (out of scope to trace further here).

### Likelihood Explanation
Requires no attacker secrets - only the ability to open a PR against a Shipit-tracked repository. Preconditions are a specific but plausible repository configuration: `review_stacks_enabled: false` with `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` (both non-default, but reachable via the settings UI independently of the `review_stacks_enabled` checkbox). For `prevent_with_label`, no label manipulation is needed at all - a bare, unlabeled PR triggers it. For `allow_with_label`, the attacker needs the qualifying label present, which depends on repository label permissions.

### Recommendation
Parenthesize `provision?` to match `LabeledHandler`'s pattern, gating all three branches uniformly:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Apply the same fix to `ReopenedHandler#unarchive?`, which has an identical precedence bug: [6](#0-5) 

### Proof of Concept
Minitest plan (add to `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`, mirroring the existing `configure_provisioning_behavior` helper):

```ruby
test "does NOT provision stacks when review_stacks_enabled is false, even for prevent_with_label" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,      # review_stacks_enabled = false
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = []   # no label -> prevent_with_label would provision

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```

Corresponding sibling assertion demonstrating the divergence with `LabeledHandler` under the same config (`review_stacks_enabled: false`, `prevent_with_label`):
```ruby
test "LabeledHandler correctly refuses to act when review_stacks_enabled is false" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_labeled)
  payload["pull_request"]["labels"] = []

  assert_no_difference -> { Shipit::Stack.count } do
    LabeledHandler.new(payload).process
  end
end
```
Before the fix, the first test fails (`Stack.count` increases by 1), demonstrating `OpenedHandler` provisions a stack that `LabeledHandler` would refuse to touch under identical `review_stacks_enabled: false` configuration.
