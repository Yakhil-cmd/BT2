Based on my investigation of `pox-5.clar`, I found a strong analog to the report's bug class: an on-chain check that fails to validate that a claimed asset (here, a Bitcoin lockup output) genuinely and *exclusively* backs the value being credited — allowing reuse of the same collateral to mint credit twice, analogous to the oToken forgery bypassing "is this really backed" checks.

### Title
Same Bitcoin L1 lockup outpoint can be replayed across multiple `register-for-bond` calls to double-count sats credit — ([File: stackslib/src/chainstate/stacks/boot/pox-5.clar])

### Summary
`register-for-bond`'s L1 path (`verify-l1-lockups` / `validate-l1-lockup`) verifies that a caller-supplied Bitcoin transaction output is a real, on-chain, correctly-scripted timelock output for the staker, and sums the sats across the list of outputs supplied in a *single* call. However, the "already used" check (`seen-outpoints`) is only a local accumulator scoped to the current call's fold — it is never persisted to contract state. Nothing prevents the exact same outpoint (txid + output-index) from being submitted again in a later `register-for-bond` (or `update-bond-registration`/rollover) call and being credited again as `sats-total`, without any new BTC ever being locked.

### Finding Description
`validate-l1-lockup` (`stackslib/src/chainstate/stacks/boot/pox-5.clar:2031-2113`) folds over the caller-supplied `outputs` list, and for each entry verifies:
- the output's script matches the expected P2WSH timelock script for `staker` [1](#0-0) 
- the amount matches [2](#0-1) 
- the outpoint is not a duplicate *within this same call* via `seen-outpoints`, which starts empty on every invocation of `verify-l1-lockups` [3](#0-2) 
- the block header and merkle proof are valid, proving the transaction is really on Bitcoin [4](#0-3) 

Critically, `seen-outpoints` is a transient value threaded through the fold's accumulator record — it is never written to a persistent `define-map` that would span across calls. I searched `pox-5.clar` for any map tracking used outpoints (`define-map`, `outpoint`, `ERR_DUPLICATE_LOCKUP_OUTPOINT` usage outside the fold) and found none — the only occurrence of outpoint tracking is the local `seen-outpoints` list capped at 10 entries, reset every call.

Consequently, a staker who locked, say, 1 BTC on L1 in a single valid timelock output can:
1. Call `register-for-bond` citing that output, get bond membership credited with `sats-total` sats and the corresponding `amount-ustx` from `min-ustx-for-sats-amount`.
2. Later, roll over/unregister (or simply have that bond conclude), and call `register-for-bond` again (or via `update-bond-registration`/staking flows that re-invoke `verify-l1-lockups`) citing the *same* physical BTC output — which still satisfies `verify-block-header`, `verify-merkle-proof`, script-match, and amount-match, since Bitcoin state doesn't change and the "already spent" state of the collateral is never recorded on the Stacks side.
3. This lets the staker be credited with `sats-total` sats of collateral for two (or more) different, possibly-concurrent bonds — even though only one physical BTC lockup exists.

This breaks the equality the bond system depends on: *sats credited toward reward/allowance calculations == sats actually locked on Bitcoin (once)*. Bond reward allocation (`get-total-shares-staked-for-cycle`, `protocol-bonds-total-staked`) and allowance checks (`sats-total <= allowance`) at `stackslib/src/chainstate/stacks/boot/pox-5.clar:744` all rely on `sats-total` being an honest, non-replayable measure of collateral, and per-staker reward shares scale off `amount-sats`.

### Impact Explanation
This double-counts a Bitcoin collateral commitment across multiple bond memberships, which inflates the staker's proportional share of sBTC reward payouts (or allows exceeding `allowance`/`min-ustx-for-sats-amount` bounds meant to cap exposure), without any additional BTC ever being locked. Per the rules, this matches "double-counting a commitment or reward" (Critical) since it affects reward distribution derived from `total-sbtc-staked`/`get-rewards` and per-cycle share accounting, effectively letting an attacker claim reward weight backed by nonexistent collateral.

### Likelihood Explanation
The replay requires only: (a) a single valid Bitcoin timelock lockup transaction, (b) the ability to call `register-for-bond` more than once referencing it — which is naturally possible once the first bond concludes (staker becomes eligible again via the rollover/re-registration paths already implemented), or via distinct un-related bond periods if the allowlist admits the staker into two different bond indices. No signer key, admin, or miner privilege is required — it is fully reachable by any allowlisted staker.

### Recommendation
Persist consumed L1 outpoints in a durable `define-map` (e.g., `used-l1-lockup-outpoints { txid, output-index } -> bool` or a bond-index/global scoped map) and assert non-membership before crediting `sats-total`, inserting the outpoint upon successful validation — mirroring `ERR_DUPLICATE_LOCKUP_OUTPOINT`'s intent but across calls, not just within a single call's list.

### Proof of Concept
1. Staker locks `S` sats in a single valid P2WSH timelock output on Bitcoin, addressed per `construct-lockup-output-script(staker, unlock_burn_height, staker_unlock_bytes, early_unlock_bytes)`.
2. Staker calls `register-for-bond(bond-index=0, ...)` with `btc-lockup = (ok { outputs: [that output], staker-unlock-bytes })`. `verify-l1-lockups` validates the header/merkle-proof/script/amount and returns `sats-total = S`; bond 0 membership is created with `amount-sats: S`.
3. After bond 0's non-overlap window opens (or by being allow-listed on a second, non-overlapping bond-index), staker calls `register-for-bond(bond-index=1, ...)` again citing the exact same `tx`/`output-index`/`header` for the same on-chain output. All checks in `validate-l1-lockup` pass identically (the BTC output still exists on-chain and hasn't moved), because no contract-side record marks it consumed. Bond 1 membership is now created with `amount-sats: S` as well.
4. The staker now has `S` sats credited to two separate bonds' `protocol-bonds-total-staked` and per-cycle share totals, doubling their proportional reward claim relative to the single real BTC lockup backing it. [5](#0-4)
