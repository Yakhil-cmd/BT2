### Title
Fee-on-Transfer Token Causes Bridge Reserve Insolvency via Overstated `RequestValueTransfer` Amount — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

---

### Summary

`BridgeTransferERC20.requestERC20Transfer()` pulls `_value + _feeLimit` from the caller via `safeTransferFrom`, but when the ERC20 token charges a transfer fee the bridge receives fewer tokens than requested. The function then emits `RequestValueTransfer` with the original user-supplied `_value`, not the actual amount received. The off-chain relayer reads that event and instructs the counterpart bridge to release the full `_value` to the recipient. In lock/unlock mode this drains the counterpart bridge's reserves faster than the source bridge accumulates them, eventually making the counterpart bridge insolvent.

---

### Finding Description

**Source-chain deposit path (`requestERC20Transfer`, 2-step):**

```solidity
// BridgeTransferERC20.sol line 133
IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
_requestERC20Transfer(_tokenAddress, msg.sender, _to, _value, _feeLimit, _extraData);
```

For a fee-on-transfer token with rate `f`, the bridge receives `(1 − f) × (_value + _feeLimit)` tokens, not `_value + _feeLimit`.

**Event emission inside `_requestERC20Transfer`:**

```solidity
// BridgeTransferERC20.sol lines 97-106
emit RequestValueTransfer(
    TokenType.ERC20,
    _from, _to, _tokenAddress,
    _value,          // ← user-supplied, not actual received amount
    requestNonce, fee, _extraData
);
```

`_value` is never adjusted to reflect the fee-on-transfer shortfall.

**Off-chain relayer (`bridge_manager.go` line 339):**

```go
handleTx, err = bi.bridge.HandleERC20Transfer(
    auth, txHash, from, to, ctpartTokenAddr,
    valueOrTokenId,   // ← taken verbatim from the event
    requestNonce, blkNumber, extraData)
```

`valueOrTokenId` equals the unadjusted `_value` from the event.

**Counterpart bridge release (`handleERC20Transfer` line 71):**

```solidity
IERC20(_tokenAddress).safeTransfer(_to, _value);   // releases full _value
```

In lock/unlock mode the counterpart bridge transfers the full `_value` to the recipient, even though the source bridge only locked `(1 − f) × _value` (approximately) worth of tokens.

The same flaw exists in the 1-step path (`onERC20Received` → `_requestERC20Transfer`): the ERC20 token's own `requestValueTransfer` calls `safeTransferFrom` to the bridge before calling `onERC20Received`, so the bridge again receives less than `_value + _feeLimit` but the event still carries `_value`.

---

### Impact Explanation

In **lock/unlock mode** every cross-chain transfer of a fee-on-transfer token causes the counterpart bridge to release `_value` tokens while the source bridge only accumulated `(1 − f) × _value` tokens. The deficit per transfer is `f × _value`. After `N` transfers the counterpart bridge is short by `N × f × _value` tokens. Eventually `safeTransfer` in `handleERC20Transfer` reverts because the counterpart bridge has insufficient balance, permanently blocking all further withdrawals for that token — an unauthorized drain of bridge-managed funds matching the "unauthorized transfer … affecting … bridged assets" impact gate.

---

### Likelihood Explanation

Any user can call `requestERC20Transfer` with a registered fee-on-transfer ERC20 token. No special privilege is required. The bridge contracts explicitly support arbitrary ERC20 tokens. The trigger is a normal, valid user action on the production bridge.

---

### Recommendation

In `requestERC20Transfer`, snapshot the bridge's token balance before and after `safeTransferFrom` and pass the delta (actual received amount) to `_requestERC20Transfer` instead of the user-supplied `_value`:

```solidity
function requestERC20Transfer(
    address _tokenAddress,
    address _to,
    uint256 _value,
    uint256 _feeLimit,
    bytes memory _extraData
) public {
    uint256 balanceBefore = IERC20(_tokenAddress).balanceOf(address(this));
    IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
    uint256 actualReceived = IERC20(_tokenAddress).balanceOf(address(this)).sub(balanceBefore);
    // Derive actual value after fee, keeping feeLimit portion separate
    uint256 actualValue = actualReceived >= _feeLimit ? actualReceived.sub(_feeLimit) : 0;
    _requestERC20Transfer(_tokenAddress, msg.sender, _to, actualValue, _feeLimit, _extraData);
}
```

Apply the same pattern to `onERC20Received` (1-step path).

---

### Proof of Concept

1. Deploy bridge in lock/unlock mode with a fee-on-transfer ERC20 (1% fee) registered on both chains.
2. User approves bridge for `110` tokens and calls `requestERC20Transfer(token, recipient, 100, 10, "0x")`.
3. Bridge pulls `110` tokens but receives `108.9` (1% fee deducted by token).
4. `RequestValueTransfer` event is emitted with `valueOrTokenId = 100`.
5. Relayer calls `handleERC20Transfer(..., 100, ...)` on counterpart bridge.
6. Counterpart bridge transfers `100` tokens to recipient.
7. Net: source bridge locked `~99` tokens (after bridge-fee transfers also incur fee), counterpart bridge released `100` tokens — deficit of `~1` token per transfer.
8. After 1000 such transfers the counterpart bridge is short `~1000` tokens; subsequent `handleERC20Transfer` calls revert, freezing all withdrawals.
