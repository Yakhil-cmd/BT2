### Title
Permanent freezing of stable outputs whose only spending unit becomes `final-bad` — `is_spent` flag is never reset (Analog of "burn() doesn't call ERC721 _burn()") - (File: main_chain.js)

### Summary
`main_chain.js`'s `markMcIndexStable()`/`propagateFinalBad()` demote a competing unit's `sequence` to `'final-bad'` and null out `inputs.is_unique` so the unit's claims are treated as void everywhere else in the codebase, but it never reverses the `UPDATE outputs SET is_spent=1` (or the equivalent `headers_commission_outputs`/`witnessing_outputs` updates) that was applied when that unit was originally written by `writer.js`. This is the same class of bug as the reported ERC721 `burn()` that forgets to call `_burn()`: the "close/void" operation is supposed to fully reverse the effects of the earlier "open/spend" operation, but one necessary state-reset step is omitted, leaving stale state that represents a claim that no longer exists.

### Finding Description
When a unit is written, `writer.js` marks every output it consumes as spent: [1](#0-0) 

If that same unit later turns out to conflict with another and is demoted to `sequence='final-bad'` during main-chain stabilization, `handleNonserialUnits()`/`propagateFinalBad()` in `main_chain.js` correctly nulls `inputs.is_unique` (so `checkForDoublespends()` in `validation.js` and the write path treat the final-bad unit's inputs as "non-existent competitors"), but it does **not** issue any `UPDATE outputs SET is_spent=0` for the outputs that this now-void unit had marked as spent: [2](#0-1) [3](#0-2) 

Compare this to the equivalent, correctly-implemented reversal used when a unit is *voided/archived* (e.g. during catchup rollback or light-wallet reorg handling), which explicitly un-spends every output the removed unit had spent: [4](#0-3) 

`propagateFinalBad` does the "declare invalid" half of the operation (nulling `is_unique`, cascading `final-bad` status to downstream spenders) but skips the "undo the spend" half — the exact same asymmetry as `CollateralizedDebt.burn()` performing the balance-clearing logic but never calling `_burn()` to retire the token.

The repository's own tooling documents this exact symptom: outputs are permanently left with `is_spent=1` even though "no good unit claims" them, because the only spender was propagated to `final-bad`: [5](#0-4) 

A parallel fix was applied specifically to `countVotes()` (using a `NOT EXISTS` join instead of trusting `is_spent`), with an explicit comment acknowledging the root defect: [6](#0-5) 

However, this workaround is local to vote counting. The vast majority of balance/coin-selection code paths still trust the `is_spent` flag directly, e.g. divisible/indivisible coin selection in `inputs.js` (`is_spent=0` filters) and `pickIndivisibleCoinsForAmount` in `indivisible_asset.js`: [7](#0-6) 

### Impact Explanation
Any address whose stable, good output is spent by a unit that is later found to conflict with another unit and is demoted to `sequence='final-bad'` on stabilization will have that output stuck at `is_spent=1` forever, because nothing in `propagateFinalBad`/`handleNonserialUnits` resets it. Since `final-bad` units' claims are treated as non-existent everywhere else (double-spend checks, `is_unique=NULL`), the honest owner's funds are legitimately still theirs to spend — but every wallet/coin-selection code path that filters on `outputs.is_spent=0` (light and full wallets, `pickDivisibleCoinsForAmount`, `pickIndivisibleCoinsForAmount`) will never surface this output as spendable. This is a fund-freezing bug: the coins are unspendable through the normal wallet/AA-funding code paths even though the network considers them un-spent by any valid unit. This satisfies the "AA fund loss or freezing" / inability-to-spend acceptance criteria in the same way the referenced ERC721 report demonstrates a lingering, incorrectly-retained token state after the underlying value was already released.

### Likelihood Explanation
This requires only an ordinary double-spend/non-serial resolution event during normal main-chain stabilization — no malicious peer, hub, or network-level behavior is needed, and it can happen to any user whose output is spent by two competing units where the loser is decided in favor of a different unit. This is a routine occurrence in the DAG's conflict-resolution process (temporary forks are expected and are exactly what `sequence='final-bad'` exists to resolve), so the trigger condition is common, not a rare edge case.

### Recommendation
In `main_chain.js`, wherever a unit's `sequence` is set to `'final-bad'` (both in `handleNonserialUnits()` and in `propagateFinalBad()`), also generate and execute the same "unspend" queries used by `archiving.generateQueriesToUnspendOutputsSpentInArchivedUnit()` (reusable from `archiving.js`) for that unit's `transfer`, `headers_commission`, and `witnessing` inputs, so `outputs.is_spent` (and the commission/witnessing tables) are reset to `0` in lock-step with `inputs.is_unique` being nulled. Alternatively, migrate every remaining `is_spent=0`-based balance/coin-selection query (in `inputs.js`, `indivisible_asset.js`, wallet balance queries, and any light-wallet equivalents) to the `NOT EXISTS`-based approach already adopted in `countVotes()`.

### Proof of Concept
1. Unit `A` (stable, good) is spent by two competing units `B` and `C` referencing the same `(unit, message_index, output_index)` (a legitimate temporary fork).
2. `writer.js` marks `A`'s output `is_spent=1` when `B` (say) is first written/becomes serial.
3. On main-chain stabilization, `findStableConflictingUnits`/`propagateFinalBad` in `main_chain.js` determines `B` loses and sets `B.sequence='final-bad'`, running `UPDATE inputs SET is_unique=NULL WHERE unit=B` — but never `UPDATE outputs SET is_spent=0` for `A`'s output.
4. `C`, if it exists and is good, would set `is_spent=1` again (harmless, same value); but if `C` does not exist (i.e., `B` was simply invalidated with no consuming successor), `A`'s output remains at `is_spent=1` permanently, with no `good` unit claiming it.
5. Any wallet or asset library call using `outputs.is_spent=0` filters (`inputs.js`, `indivisible_asset.js`) will never again offer `A`'s output as spendable, even though `checkForDoublespends`/`is_unique=NULL` treat `B` as if it never existed — the owner's funds are effectively frozen, exactly as demonstrated by the discrepancy documented in `tools/compare_vote_balances.js`.

function generateQueriesToUnspendTransferOutputsSpentInArchivedUnit(conn, unit, arrQueries, cb){
	conn.query(
		"SELECT src_unit, src_message_index, src_output_index \n\
		FROM inputs \n\
		WHERE inputs.unit=? \n\
			AND inputs.type='transfer' \n\
			AND NOT EXISTS ( \n\
				SELECT 1 FROM inputs AS alt_inputs \n\
				WHERE inputs.src_unit=alt_inputs.src_unit \n\
					AND inputs.src_message_index=alt_inputs.src_message_index \n\
					AND inputs.src_output_index=alt_inputs.src_output_index \n\
					AND alt_inputs.type='transfer' \n\
					AND inputs.unit!=alt_inputs.unit \n\
			)",
		[unit],
		function(rows){
			rows.forEach(function(row){
				conn.addQuery(
					arrQueries, 
					"UPDATE outputs SET is_spent=0 WHERE unit=? AND message_index=? AND output_index=?", 
					[row.src_unit, row.src_message_index, row.src_output_index]
				);
			});
			cb();
		}
	);
}
