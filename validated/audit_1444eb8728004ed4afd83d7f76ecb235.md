The CCMenu API endpoint is the one worth digging into further. Let me confirm the exact scoping mechanism in the base controller.### Title
Cross-stack authorization bypass in `Api::CCMenuController` breaks the ApiClient stack-scope binding - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Api::CCMenuController#stack` resolves the target stack directly from `params[:stack_id]` against the unscoped `Stack` relation instead of using the stack-scoped lookup used everywhere else in the API. This breaks the intended binding "the stack a token authorizes == the stack it touches": a narrowly stack-scoped `ApiClient` token can be replayed with a different `stack_id` to read another stack's build/deploy status.

### Finding Description
`Shipit::Api::BaseController` scopes stack access to the token's authorized stack whenever the `ApiClient` is bound to one: [1](#0-0) 

`Api::StacksController` (and other API resources) consistently go through this scoped `stacks` helper (`stacks.from_param!(params[:id])`), so a stack-bound token cannot enumerate or read other stacks: [2](#0-1) 

`Api::CCMenuController`, however, overrides `stack` to bypass this scoping entirely, resolving straight from the global `Stack` collection using the client-supplied `stack_id`, and only enforces the generic `read:stack` permission string (not the token's `stack_id` binding): [3](#0-2) [4](#0-3) 

The token authenticated here is commonly a purpose-built, narrowly-scoped one: `CCMenuUrlController#client` creates an `ApiClient` bound to a single stack with only `read:stack` permission, intended to be embedded in URLs handed out to CI-status widgets/tools: [5](#0-4) 

`ApiClient#check_permissions!` only checks the permission string, not the stack binding; the stack binding is only enforced via the `stacks` scoping method in `BaseController`, which `CCMenuController` never calls: [6](#0-5) 

Before the report's fix: `equality(token.stack_id, requested.stack_id)` is enforced by `BaseController#stacks`/`#stack` for every other API resource. After going through `CCMenuController#stack`, that equality is never checked — `requested.stack_id` is taken verbatim from `params[:stack_id]`, breaking the binding "stack a token authorizes == stack it touches."

### Impact Explanation
Any valid `ApiClient` authentication token — even one deliberately minted for a single, low-sensitivity stack via the CCMenu URL feature — can be used to read the CCMenu XML status (stack name, last build/deploy status, activity, lock state) of any stack in the Shipit instance by simply changing `stack_id` in the request. This is an authorization-scope escalation: a credential explicitly restricted to one stack is used to read state for stacks the credential holder was never authorized to see, matching the High-impact category of escalation into stack-state read access outside the granted authorization scope.

### Likelihood Explanation
CCMenu tokens are handed out via URLs (`ccmenu_url`) intended for embedding in external dashboards/tools, which are more likely to leak than a full user session or a general-purpose API client secret. Exploitation requires only possession of any one such token plus knowledge/enumeration of another stack's `to_param` (owner/repo/environment/branch), all of which are non-secret identifiers. No GitHub credentials, session, or elevated permissions are needed beyond the leaked CCMenu token.

### Recommendation
Have `Api::CCMenuController#stack` resolve through the same scoped lookup as the rest of the API (`stacks.from_param!(params[:stack_id])`, i.e., inherit `BaseController#stacks`) so that a stack-bound `ApiClient` token can only ever resolve to its own authorized `stack_id`, restoring parity between `current_api_client.stack_id` and the stack actually served.

### Proof of Concept
1. As a legitimate user, visit a stack page; `CCMenuUrlController#fetch` mints an `ApiClient` scoped to `stack_id = A` with `permissions: ['read:stack']` and returns a URL containing `token=T`.
2. An attacker who obtains `T` (e.g., from a shared CI dashboard) issues:
   `GET /api/stacks/<other-stack-B>/ccmenu.xml?token=T`
3. `Api::CCMenuController#authenticate_api_client` (app/controllers/shipit/api/ccmenu_controller.rb:33-36) authenticates `T` successfully via `ApiClient.authenticate`.
4. `Api::CCMenuController#stack` (app/controllers/shipit/api/ccmenu_controller.rb:29-31) resolves stack `B` directly from `Stack.from_param!`, ignoring that `T` was only authorized for stack `A`.
5. The response renders stack `B`'s build/deploy status XML, even though `T`'s `ApiClient` record has `stack_id = A`.
