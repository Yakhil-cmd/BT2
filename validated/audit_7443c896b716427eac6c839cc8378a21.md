### Title
Cross-organization webhook forgery via unbound `repository.owner.login` vs `repository.full_name` fields - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the GitHub App (and thus the HMAC secret) used to validate an inbound webhook based on `repository.owner.login` (or `organization.login`), but every downstream `Webhooks::Handlers::Handler` resolves the `Repository`/`Stack` it actually acts on using the **separate**, unverified `repository.full_name` field from the same JSON body. These two fields are never cross-checked against each other.

### Finding Description
`verify_signature` computes the signing organization from the payload and asks `Shipit.github(organization: repository_owner)` for that org's `GitHubApp`, then verifies the signature with that org's secret: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` explicitly treats an unconfigured `webhook_secret` as automatically verified: [3](#0-2) 

`webhook_secret` is a **documented optional** setting — the setup guide and shipped example secrets files show it can legitimately be left blank/`nil` for a given organization in a multi-org deployment: [4](#0-3) [5](#0-4) 

Once the request passes `verify_signature`, `WebhooksController#create` dispatches to handlers with the raw, now-"trusted" params: [6](#0-5) 

Every handler, however, determines which `Repository`/`Stack` to mutate using `repository.full_name`, a field completely independent of `repository.owner.login`: [7](#0-6) 

`PushHandler` (and the pull_request handlers such as `LabeledHandler`, `UnlabeledHandler`, `OpenedHandler`, `ClosedHandler`) act on `stacks`/`repository` resolved this way: [8](#0-7) [9](#0-8) 

**Binding that should hold:** `organization_used_for_signature_verification == organization_owning_the_repository_the_handler_mutates`.
**Binding that actually holds:** the verification key is chosen from `repository.owner.login`/`organization.login`, while the mutated repository is chosen from `repository.full_name` — an attacker fully controls both fields independently in the same JSON body.

### Impact Explanation
In any multi-org Shipit deployment (`docs/setup.md` "Using Multiple Github Applications"), if a single organization is configured with no `webhook_secret` (an explicitly supported/documented configuration), an attacker can send an unsigned or arbitrarily-signed webhook with `repository.owner.login` set to that unsecured org (so `verify_webhook_signature` short-circuits to `true`) while setting `repository.full_name` to a repository belonging to a **different, properly-secured** organization. Because handlers never re-validate that the verified organization matches the repository being acted upon, this lets an unauthenticated attacker:
- Force `GithubSyncJob`/`sync_github` on any stack tied to the victim repository via `PushHandler` (repository/branch state manipulation), and
- Drive pull-request lifecycle side effects (archive/unarchive review stacks, capture labels) on victim repositories via the `PullRequest::*` handlers,

entirely bypassing the webhook authentication boundary meant to scope each org to its own secret. This crosses the "cross-repository writes"/"unauthorized deploy" impact bar since stack synchronization and review-stack archival directly influence deploy eligibility and state for repositories the attacker was never authorized to touch.

### Likelihood Explanation
Likelihood is moderate-to-high in real-world multi-org deployments: the vulnerable configuration (an org with no `webhook_secret`) is explicitly shown as a supported pattern in the project's own docs and shipped example config, so operators following the documented setup for secondary/low-risk orgs unintentionally create a skeleton key that reaches every other org's repositories, since no code path binds the verified organization to the repository actually processed.

### Recommendation
In `WebhooksController#verify_signature` (or in `Webhooks::Handlers::Handler`), assert that the `repository.owner.login` (or `organization.login`) used to select the verifying `GitHubApp` matches the owner segment of `repository.full_name` before dispatching to handlers, e.g. reject the request if `repository_owner.casecmp?(payload.dig('repository', 'full_name')&.split('/')&.first)` is false. Additionally, consider making `webhook_secret` mandatory per organization to remove the automatic-pass branch in `GitHubApp#verify_webhook_signature`.

### Proof of Concept
1. Deploy Shipit with two orgs configured per `docs/setup.md`'s multi-org example: `OrgA` (attacker-observable/no `webhook_secret`) and `OrgB` (victim, has a strong `webhook_secret`), both installed against the same Shipit instance (`Shipit.github_organizations`).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker chosen sha>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
No `X-Hub-Signature` header is required, or any arbitrary value works, because `repository_owner` resolves to `OrgA`, whose `GitHubApp#verify_webhook_signature` returns `true` unconditionally (per `lib/shipit/github_app.rb` line 77).
3. `WebhooksController#create` proceeds and dispatches to `PushHandler`, which resolves `stacks` via `Repository.from_github_repo_name("OrgB/victim-repo")` (per `handler.rb` line 37) and triggers `stack.sync_github(expected_head_sha: params.after)` on the victim's stack — an action the attacker was never authorized to trigger against `OrgB`.

*Note:* I was unable to retrieve the full contents of `app/models/shipit/webhooks/handlers/status_handler.rb` and `check_suite_handler.rb` in this session (tool calls for those files failed on the final iteration), so I could not confirm whether the same binding gap additionally allows forging commit-status/check-suite events that spoof CI results used by `Commit#deployable?`/`required_statuses` gating in `app/models/shipit/stack.rb` and `app/models/shipit/deploy_spec.rb`. Given the shared `Handler#repository_name` base class, this is likely but should be verified directly against those files, since a full index of their contents wasn't available to me here.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
```
