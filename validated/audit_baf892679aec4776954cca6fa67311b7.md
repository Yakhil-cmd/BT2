### Title
Uncaught exception in address-hash validation via malformed base32/base64 c-hash - (File: chash.js)

### Summary
`chash.js` decodes an address's checksum-hash (`c-hash`) representation with only a string-length check before decoding, mirroring the hivex bug class of "insufficient bounds/format validation before processing attacker-supplied binary data leads to a crash."

### Finding Description
`isChashValid()` only validates the *string* length of the encoded address (32 for chash160 / 48 for chash288) before decoding it: [1](#0-0) 

For the 32-char case it calls `base32.decode(encoded)` (via the `thirty-two` package) and for the 48-char case it calls `Buffer.from(encoded, 'base64')`. Neither Node's lenient `base64` decoder nor the `thirty-two` base32 decoder guarantee that the decoded byte buffer will be exactly 20 bytes (160 bits) or 36 bytes (288 bits) when the input string contains characters outside the expected alphabet — decoding can silently truncate or otherwise yield a buffer of unexpected length instead of throwing.

That malformed-length buffer is then fed into `buffer2bin()` and `separateIntoCleanDataAndChecksum()`: [2](#0-1) 
`separateIntoCleanDataAndChecksum` explicitly `throw`s `Error("bad length=...")` when the bit-length isn't exactly 160 or 288 — but this call happens **after** the `try/catch` in `isChashValid` has already completed (the `try` only wraps the decode step), so this throw is not caught by `isChashValid` and propagates as an uncaught exception out to whatever called `isValidChash`/`isValidAddress`.

`isValidAddress`/`isValidChash` in `validation_utils.js` are the standard address-format check used throughout unit/AA/definition validation: [3](#0-2) 
and are invoked from `validation.js` (unit author/definition-change/output address checks), `definition.js` (address-in-definition checks such as `sig`, multisig, `in data feed`, etc.), and `aa_validation.js` — all paths reachable by an unprivileged unit poster or AA-trigger sender supplying an address-like string as part of a posted unit, address definition, or AA trigger/definition.

### Impact Explanation
An uncaught exception thrown deep inside validation code that a hostile unit author or AA trigger can trigger is a denial-of-service against the validating node: depending on where in the async validation chain the throw surfaces, it can crash the Node.js process (unhandled exception) or leave the validation mutex/lock in an inconsistent state, preventing the node from confirming new units — directly matching the impact class of CVE-2021-3504 ("cause the program to crash," availability impact). This is reachable purely from attacker-controlled unit/AA content, not requiring any privileged, peer, or node-operator position.

### Likelihood Explanation
Medium. Constructing an address-length string (32 base32 chars or 48 base64 chars) that decodes to an unexpected byte length requires only crafting a string with a stray character outside the respective alphabet while keeping the same string length — a low-effort input to produce. However, exploitability depends on exact decoder behavior of the `thirty-two` package and Node's `Buffer.from(str, 'base64')` for malformed inputs (whether they throw, truncate, or pad), which could not be fully confirmed from the available source (the `thirty-two` module source was not present in the indexed codebase). This uncertainty affects confidence but the missing bounds/format validation itself (relying solely on encoded string length without validating decoded buffer length) is confirmed in `chash.js`.

### Recommendation
In `isChashValid`, after decoding, explicitly verify `chash.length === encoded_len === 32 ? 20 : 36` (i.e., check the decoded buffer's byte length matches the expected chash length) and return `false` gracefully if not, rather than relying on the downstream `throw` in `separateIntoCleanDataAndChecksum`. Additionally, wrap the entire validation body (including the `separateIntoCleanDataAndChecksum`/`bin2buffer` calls) in the same `try/catch` that already surrounds the decode step, so any parsing anomaly returns `false` instead of throwing.

### Proof of Concept
1. Construct a 48-character string that is otherwise valid standard base64 alphabet-wise but decodes (due to Node's lenient base64 parsing of certain byte sequences/padding placement) to a buffer whose length is not exactly 36 bytes.
2. Call `ValidationUtils.isValidAddress(craftedString)` (e.g., by posting a unit whose author `address` field, or an AA trigger `address`/definition field, is set to the crafted string) — reachable via `validation.js` author/address checks.
3. `chash.isChashValid` decodes the string, and the subsequent `separateIntoCleanDataAndChecksum(binChash)` call throws `Error("bad length=...")` outside of the enclosing `try/catch`, propagating an uncaught exception through the validation call stack.

Note: Full confirmation that `Buffer.from(str,'base64')` or the `thirty-two` `base32.decode` can actually be induced to return a non-canonical-length buffer for a same-length input string could not be completed within available tooling/index coverage; a Devin session with runtime access would be needed to empirically verify the exact malformed input and decoder behavior.
