### Title
Session fixation on GitHub OAuth callback: session is bound to the authenticated GitHub identity without rotating the session ID - ([File: app/controllers/shipit/github_authentication_controller.rb])

### Summary
`GithubAuthenticationController#callback` writes the authenticated user's ID directly into the *existing* session (`session[:user_id] = sign_in_github(auth)`) without ever calling `reset_session`. [1](#0-0)  This breaks the binding `session_id == the GitHub identity currently authorized to act through it`: an attacker who gets a victim's browser to carry an attacker-chosen (or otherwise known) session cookie before the victim completes GitHub OAuth ends up sharing full Shipit authentication with the victim once the victim logs in, because the session identifier itself is never rotated at the authentication boundary.

### Finding Description
The engine's authentication flow is:
1. `Authentication#force_github_authentication` redirects unauthenticated users to `github_authentication_path`. [2](#0-1) 
2. `GithubAuthenticationController#callback` receives the OmniAuth result and finalizes login purely by writing to the session:
```ruby
def callback
  return_url = request.env['omniauth.origin'] || root_path
  auth = request.env['omniauth.auth']
  return render('failed', layout: false) if auth.blank?
  session[:user_id] = sign_in_github(auth)
  session[:authenticated] = true
  redirect_to(return_url)
end
``` [1](#0-0) 

Nowhere in this method — nor anywhere else in the login path — is `reset_session` invoked. The only place `reset_session` is called is in `force_github_authentication`, and only in the unrelated "stale token" branch (when a *currently logged-in* user's token needs refreshing), not on initial sign-in. [3](#0-2) 

Because the session ID is not rotated at the point where privilege is granted, whatever session identifier the browser held before OAuth completed continues to be valid and now maps to the newly authenticated `User`. This is the textbook session-fixation pattern: the equality that should hold — "the session id was generated *for* this authenticated identity" — instead becomes "any session id that happened to be present *before* the user authenticated is thereafter treated as *authenticated as that user*." If an attacker can get their own (or a known/guessable) session cookie planted in the victim's browser prior to the OAuth callback (e.g., cookie tossing across a shared parent domain, a non-`HttpOnly`/insecure cookie write from a lower-trust origin, or simply capturing a session cookie value issued to the victim pre-login and replaying it themselves after the victim logs in), the attacker inherits the victim's Shipit session — including access to `stacks`, ability to trigger deploys/tasks, manage `api_clients`, etc. — all gated by `current_user` derived solely from `session[:user_id]`. [4](#0-3) 

The `GithubAuthenticationController` also does not include Shipit's session/CSRF hardening: it extends `ActionController::Base` directly (not `ShipitController`) and performs no `protect_from_forgery`/authenticity-token verification of its own, relying entirely on the OmniAuth gem's own state-parameter CSRF protections for the OAuth handshake itself — but that protects against forced authorization-code injection, not against session-ID fixation, which is orthogonal and unaddressed here.

### Impact Explanation
This matches the "High" bullet in the accepted impact list: session fixation / forced OAuth completion leading to escalation into `Shipit.github_teams` authorization without the attacker ever presenting valid GitHub credentials. An attacker who successfully fixes a victim's session inherits:
- Full `current_user` identity of the victim for all `Shipit::Authentication`-protected engine controllers (stacks, tasks, deploys, hooks, api_clients). [5](#0-4) 
- The ability to create `ApiClient` records "as" the victim (`creator_id: current_user.id`), and to trigger deploys/tasks that execute `shipit.yml` steps on the deploy host under the victim's authorization. [6](#0-5) 

This is not equivalent to stealing `github_access_token` directly, but it is an authentication-boundary crossing: the attacker never authenticated as the victim, yet the application treats the pre-existing session as if it had.

### Likelihood Explanation
Medium. Exploitation requires the attacker to plant a session cookie in the victim's browser before the victim completes the GitHub OAuth login flow (e.g., via a sibling subdomain the attacker controls, a network position that can write cookies without `Secure`/`HttpOnly` enforcement, or convincing the victim to open an attacker-supplied session/link and then complete login). This is a well-known, GitHub-CVE-documented class of bug (missing session ID rotation on login), and the absence of any `reset_session` call in the login path is a concrete, verifiable root cause in this codebase rather than a theoretical gap.

### Recommendation
Call `reset_session` (or otherwise rotate the session ID) in `GithubAuthenticationController#callback` immediately before establishing the new authenticated session, mirroring the pattern already used for stale-token re-authentication in `Authentication#force_github_authentication`:
```ruby
def callback
  return_url = request.env['omniauth.origin'] || root_path
  auth = request.env['omniauth.auth']
  return render('failed', layout: false) if auth.blank?

  user_id = sign_in_github(auth)
  reset_session
  session[:user_id] = user_id
  session[:authenticated] = true

  redirect_to(return_url)
end
```
Ensure `return_url`/`omniauth.origin` is captured before the reset, and that any state needed post-redirect is preserved outside the session being rotated.

### Proof of Concept
1. Attacker visits the Shipit instance anonymously and notes/sets the resulting (unauthenticated) session cookie value `S` in the victim's browser (e.g., via a cookie-tossing vector on a shared parent domain, or by directly sharing/forcing cookie `S` through any client-side write the attacker controls).
2. Victim, using the browser that now carries cookie `S`, navigates to Shipit and completes the legitimate GitHub OAuth login.
3. `GithubAuthenticationController#callback` executes `session[:user_id] = sign_in_github(auth)` against the *existing* session tied to cookie `S`, without rotating it. [7](#0-6) 
4. Attacker, presenting the same cookie `S`, is now recognized by `Authentication#current_user` as the victim (`session[:user_id]` resolves to the victim's `User` record), and can access/trigger any engine action available to that account. [4](#0-3) 

**Uncertainty note:** I could not verify from the indexed files whether the host application's Rails session store configuration (cookie `Secure`/`HttpOnly`/`SameSite` flags, session ID entropy/rotation defaults) mitigates the fixation vector at the framework level, since `config/initializers/session_store.rb` is only present under `test/dummy/` (a test fixture) and real deployments configure this themselves outside engine scope. The root-cause gap — no `reset_session` in the OAuth login path — is confirmed directly in the engine code cited above.
