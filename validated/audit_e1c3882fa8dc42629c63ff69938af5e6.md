### Title
Missing existence check on `base_aa` in parameterized AA definitions causes an unhandled exception (node crash) on trigger - (File: aa_validation.js)

### Summary
`validateAADefinition()` in `aa_validation.js` accepts a "parameterized AA" definition (`{base_aa: <address>, params: {...}}`) as long as `base_aa` is *syntactically* a valid address — it never checks that the referenced base AA actually exists. Later, when the resulting AA is triggered, `storage.readBaseAADefinitionAndParams()` unconditionally assumes the base AA exists and `throw`s inside an asynchronous DB callback if it doesn't, which is an unhandled/uncatchable exception that crashes the node process. This is the same bug class as the reported yasm issue: a reference/field that "should" be present is dereferenced without validating it was actually resolved, leading to a hard crash triggered by attacker-controlled input.

### Finding Description
When validating a new AA definition, the parameterized-AA branch only validates the syntax of `base_aa`, never its existence: [1](#0-0) 

Any unprivileged unit poster can therefore post and stabilize an AA definition such as:
```json
["autonomous agent", { "base_aa": "SOME_VALID_LOOKING_ADDRESS_THAT_IS_NOT_AN_AA", "params": { "x": 1 } }]
```
This passes `validateAADefinition` and gets inserted via `storage.insertAADefinitions` (`storage.js:904`), becoming a permanently defined AA address that anyone can send funds/triggers to.

When any user (the same poster or anyone else) later sends a trigger unit to this AA address, the network processing that trigger resolves the base definition via `readBaseAADefinitionAndParams`: [2](#0-1) 

Because the base AA was never checked to exist at validation time, `arrBaseDefinition` is `null`/`undefined`, and the code executes `throw Error("base AA not found: " + base_aa)` inside the asynchronous `readAADefinition` callback. This callback is invoked from a DB query completion handler, so the thrown error is not inside any enclosing try/catch that could recover — it propagates as an uncaught exception. This code path is reached both from getter calls (`callGetter`, which also calls `readBaseAADefinitionAndParams`): [3](#0-2) 

and from primary AA trigger handling, since every full node deterministically evaluates every trigger sent to a defined AA address.

The root cause mirrors the reported analog: a field/reference (`base_aa`, analogous to a directive argument in `do_directive()`) is accepted without verifying the object it is expected to resolve to actually exists, and is later dereferenced/assumed valid, causing a NULL/undefined-driven crash instead of a graceful validation error.

### Impact Explanation
Because every full node (and any node maintaining `aa_addresses`/`storage`) processes triggers to defined AAs deterministically as part of unit/DAG validation and AA response computation, sending a single payment/trigger to such a malformed parameterized-AA address will cause the uncaught exception on every full node that processes it, crashing the node process. Since this is deterministic and identical across all nodes, it can be used to repeatedly crash all processing full nodes each time they restart and re-encounter the trigger (or a fresh one), producing a denial-of-service that stalls stabilization of new units — satisfying the "network unable to confirm new units" impact bar.

### Likelihood Explanation
Likelihood is high: any unprivileged user can post an AA definition unit (`{base_aa: <valid-looking but non-existent address>, params:{...}}`), which requires no privileges, no collusion, and passes all existing validation (`isValidAddress` only checks format, not existence). Triggering the crash then only requires sending a normal payment/trigger unit to that address, again something any unprivileged unit poster can do.

### Recommendation
In `aa_validation.js`, when validating the parameterized-AA branch (`template.base_aa`), resolve `base_aa` against `storage.readAADefinition` (or equivalent) at validation time and reject the definition with a normal validation error (e.g., `callback("base_aa not found")`) if it does not correspond to an existing AA, mirroring the pattern used for `definition template` validation elsewhere in `definition.js`. Additionally, in `storage.readBaseAADefinitionAndParams` (`storage.js:822-825`), replace the `throw Error("base AA not found: " + base_aa)` with a graceful error/bounce path so that even a definition that somehow slips past validation cannot crash the node.

### Proof of Concept
1. Attacker posts a unit defining a new AA:
```json
["autonomous agent", {
  "base_aa": "BASE32_ADDRESS_THAT_IS_SYNTACTICALLY_VALID_BUT_NEVER_DEFINED",
  "params": { "x": 1 }
}]
```
This passes `validateAADefinition` (`aa_validation.js:734-743`, only `isValidAddress` is checked) and is stabilized/stored via `storage.insertAADefinitions`.
2. Attacker (or anyone) sends a normal payment/trigger unit to the resulting AA address.
3. Every full node processing the trigger calls `storage.readBaseAADefinitionAndParams` (`storage.js:813-828`), finds `arrBaseDefinition` falsy, and executes `throw Error("base AA not found: " + base_aa)` inside an async DB callback, crashing the node process with an uncaught exception.
