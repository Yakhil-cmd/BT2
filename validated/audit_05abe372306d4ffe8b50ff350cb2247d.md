### Title
CCMenu API token minted for one stack authorizes read access to every stack in the install - ([File: app/controllers/shipit/ccmenu_url_controller.rb])

### Summary
`CCMenuUrlController#client` mints (or reuses) a single `ApiClient` per Shipit user for the "CCMenu Client" name, but never binds it to the `stack` the URL was generated for. When that token is later presented to `Api::CCMenuController`, the generic stack-scoping logic in `Api::BaseController` treats an unscoped `ApiClient` as authorized for `Stack.all`, so a token minted in the context of one stack ends up touching every stack.

### Finding Description
The binding that should hold is: `stack the token was authorized for == stack the token can touch`.

`CCMenuUrlController#fetch` builds a stack-specific CCMenu URL and attaches a token from `client`: [1](#0-0) 

```ruby
def fetch
  uri = URI(api_stack_ccmenu_url(stack_id: stack.to_param))
  uri.query = { 'token' => client.authentication_token }.to_query
  render(json: { ccmenu_url: uri.to_s })
end
...
def client
  @client ||= ApiClient.create_with(permissions: %w[read:stack])
                       .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
end

def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
```

`client` is looked up/created solely by `creator:` and `name:`, with no `stack:` attribute, so the very same `ApiClient` record (with `stack_id` = `nil`) is returned regardless of which `stack` the URL is being generated for.

`ApiClient` supports optional stack scoping: [2](#0-1) 

When that token is later used against the API, `Api::BaseController` decides which stacks the client may touch purely from `stack_id?`: [3](#0-2) 

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

Because the "CCMenu Client" has `stack_id == nil`, `stacks` resolves to `Stack.all` for it. `Api::CCMenuController` only checks the `read:stack` permission bit, not which stack: [4](#0-3) 

The route confirms `stack_id` is a free path parameter on the `ccmenu` endpoint, independent of the token: [5](#0-4) 

So the equality that should hold — "stack the token authorizes == stack it can read" — is broken: **before** the attacker's request, the token is only ever handed out attached to a URL for stack A; **after**, the same bearer token, when replayed against `/api/stacks/B/ccmenu` for any other stack B, is accepted because the underlying `ApiClient` carries no stack restriction at all.

### Impact Explanation
Any Shipit user who is trusted to view one stack's CCMenu URL (a feature explicitly designed to be embedded in third-party CI dashboard tools such as CCTray, i.e., handled with much weaker secrecy expectations than a session cookie) obtains a bearer token that, when replayed, grants `read:stack` access to **every** stack in the deployment via `Api::CCMenuController#show`, regardless of team/repository ownership. This is an authorization escalation matching the High-impact bucket "unauthenticated read of stack state" — because the token, once exposed via an embedded/external CCMenu widget, functions as ambient/unauthenticated read access far beyond the single stack it was ostensibly generated for.

### Likelihood Explanation
Any authenticated Shipit user (no special privilege required) can trigger `CCMenuUrlController#fetch` for a stack they have visibility into, obtain the shared "CCMenu Client" token, and immediately reuse that same token against any other stack ID in the install. No race, no timing window, and no additional secret is required — the missing `stack:` attribute on `find_or_create_by!` makes this deterministic and repeatable for every user with read access to at least one stack.

### Recommendation
Scope the `ApiClient` created in `CCMenuUrlController#client` to the requested `stack`, both in the lookup and creation attributes (e.g. `ApiClient.create_with(permissions: %w[read:stack], stack:).find_or_create_by!(creator: current_user, stack:, name: 'CCMenu Client')`), so `stack_id?` is always true for CCMenu tokens and `Api::BaseController#stacks` correctly restricts them to `Stack.where(id: current_api_client.stack_id)`.

### Proof of Concept
1. User Alice, who can view Stack A, visits `GET /ccmenu/A` → `CCMenuUrlController#fetch` returns a URL containing token `T` (backing `ApiClient` has `stack_id: nil`).
2. Alice (or anyone who obtains `T`, e.g. from an embedded CI badge) calls `GET /api/stacks/B/ccmenu?token=T` for a completely unrelated Stack B that Alice was never granted visibility into.
3. `Api::CCMenuController#authenticate_api_client` accepts `T` via `ApiClient.authenticate(params[:token])`; `require_permission :read, :stack` passes because `T`'s permissions include `read:stack`; `stack` resolves via `Stack.from_param!(params[:stack_id])` directly (bypassing the base `stacks` scoping in this specific controller override) — confirming the token is fully unscoped and works for any stack ID supplied.
4. Stack B's build status/activity/last deploy info is returned, even though the token was only ever minted in the context of Stack A.

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end
