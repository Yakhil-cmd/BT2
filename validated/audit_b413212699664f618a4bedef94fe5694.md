### Title
Attacker-controlled route payload can smuggle unauthorized user-wallet transfers through a signed controller swap - (File: `contracts/controller/src/strategies/swap.rs`)

### Summary
The controller accepts opaque serialized route data and executes it through the configured swap router while the account owner’s authorization is active. Because route venues and pool addresses are not bound to a trusted registry at the controller boundary, a malicious route can invoke attacker-deployed contract code that performs an unrelated `token.transfer(victim, attacker, amount)` under the victim’s signed authorization tree. The controller’s post-swap balance checks can still pass if the malicious venue returns sufficient output, so the attack can steal wallet assets unrelated to the lending position.

### Finding Description
`swap_tokens` accepts the caller-supplied `StrategySwap`, snapshots only the input and output token balances, authorizes the exact input transfer to the configured router, and invokes `router.execute_strategy` inside the flash guard. [1](#0-0)  The subsequent checks bound only the router’s spend of the declared input token and require a positive increase in the declared output token; they do not inspect or restrict other token movements performed by route-selected code. [2](#0-1)  `swap_collateral`, `multiply`, `swap_debt`, and `repay_debt_with_collateral` all expose this opaque `Bytes` route argument through public authenticated entrypoints. [3](#0-2) 

The serialized payload is therefore analogous to unsafe deserialization: it is not merely quote metadata, but an executable route program whose asset indices can name arbitrary pool contracts. During router execution, a malicious pool implementation can make an additional token call naming the swap caller as `from`. Soroban records that call beneath the caller’s authorization tree, and if the generated tree is signed, the host accepts it. The repository’s regression test demonstrates a rogue hop pool draining an unrelated wallet token while the swap still deposits a fair output. [4](#0-3) [5](#0-4) 

### Impact Explanation
A victim can lose arbitrary spendable wallet tokens, including assets that were never supplied to, listed by, or otherwise entrusted to the lending protocol. In the pinned scenario, the malicious route moves Alice’s entire unrelated `WALLET_BALANCE` to the attacker while still producing the expected collateral output. [6](#0-5)  This is theft of user funds, not merely poor execution quality: the stolen token is outside the declared swap input and is not bounded by the controller’s input or output measurements.

The same mechanism applies to any account operation that embeds a route, including `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, and `multiply`, because they all reach `swap_tokens` with caller-controlled route bytes. [7](#0-6) [8](#0-7) 

### Likelihood Explanation
An unprivileged attacker can deploy the malicious venue, encode it in a route, and submit or induce submission of a lending strategy transaction that uses that route. The normal defense is that the unauthorized token transfer appears as an additional child invocation in the simulation/auth tree and fails if the victim signs only an honest tree. [9](#0-8)  However, standard transaction simulation records the extra transfer beneath the caller’s root invocation, and signing that returned tree makes the theft execute. [10](#0-9) 

This requires the victim to sign a poisoned authorization tree, commonly produced by a malicious quote, frontend, or opaque route payload, so it is less likely than a purely permissionless exploit. The impact remains high because the route can target any token balance for which the victim’s account authorization is valid.

### Recommendation
Do not allow serialized routes to select arbitrary executable pool addresses beneath the account owner’s authorization. Maintain an on-chain registry of governance-approved venue/pool addresses and reject any decoded route whose pool is absent, or replace free-form pool addresses with immutable venue identifiers that resolve only to audited adapter contracts. At minimum, constrain route execution so no venue call can add arbitrary sub-invocations under the user’s authorization, and require clients to reject every child authorization other than the single declared input transfer. The controller should also reject non-empty routes unless the router interface provides an enforceable venue allowlist guarantee.

### Proof of Concept
1. Alice owns a lending account with USDC collateral and holds `WALLET_TOKEN` outside the protocol.
2. The attacker deploys `RogueHopPool`; its `swap` function calls `WALLET_TOKEN.transfer(alice, attacker, balance)`.
3. The attacker constructs a route whose pool field resolves to `RogueHopPool` and whose declared output token still receives a valid amount.
4. Alice invokes `swap_collateral(alice, account_id, usdc_key, SWAP_IN_USDC, eth_key, malicious_route)`.
5. The controller authenticates Alice, withdraws the declared collateral, authorizes the exact router input transfer, and passes the opaque route to the router. [11](#0-10) 
6. Inside the route, `RogueHopPool.swap` executes the unrelated wallet-token transfer under Alice’s recorded authorization tree. [5](#0-4) 
7. The route still returns ETH output, so the controller’s positive-output check succeeds and the position update finalizes.
8. If Alice signs the simulation-produced tree containing the extra transfer, enforcing mode accepts it; Alice’s wallet token balance becomes zero and the attacker receives the full balance. [10](#0-9)

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}
