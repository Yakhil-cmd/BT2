### Title
Insertion of Sensitive Device-Message Content into Log File via `decryptPackage` - ([File: device.js])

### Summary
`device.js`'s `decryptPackage()` writes the fully decrypted plaintext of every incoming device message to the process log via `console.log`, before the message is validated or its subject is even checked. Because any paired correspondent (or the hub relaying messages on their behalf) can cause this function to run simply by sending a normal encrypted device message, sensitive payload data that legitimately flows over the device-message channel — private payment chain elements (addresses, amounts, blinding factors), textcoin mnemonics forwarded between a user's own devices, wallet/shared-address definitions, and chat content — ends up persisted in plaintext in the node's/wallet's log output. [1](#0-0) 

### Finding Description
`decryptPackage(objEncryptedPackage, depth)` decrypts an incoming device-message envelope with AES-128-GCM and then immediately logs the entire decrypted plaintext:

```
var decrypted_message = decrypted_message_buf.toString("utf8");
console.log("decrypted: "+decrypted_message);
``` [1](#0-0) 

This happens for every successfully decrypted message, unconditionally, before `handleMessageFromHub`/message-subject dispatch performs any content-specific handling or authorization. The device-message channel is explicitly the transport used for:
- forwarding private (indivisible/divisible) asset payment chains between wallet counterparts, whose payloads include addresses, amounts and blinding factors (`wallet.js` `handlePrivatePaymentChains`, `network.js` `handleSavedPrivatePayments`), [2](#0-1) 
- forwarding textcoin mnemonics between a user's own devices/wallets (`sendPrivatePayments`/`forwardPrivateChainsToOtherMembersOf...` paths that ultimately transmit `mnemonic` fields), [3](#0-2) 
- wallet/shared-address pairing and definition exchange, and free-text chat.

Since `decryptPackage` logs the plaintext regardless of subject, any of this sensitive data that a legitimate correspondent (or the hub acting as relay) sends is written to the node's console/log output. This is a direct analog of CVE-2007-0902 / CWE-532: sensitive runtime information (here, decrypted application payloads containing spendable secrets and private-payment details) is inserted into a log file as a side effect of normal request handling, with no redaction of the message content.

Related, narrower instances of the same bug class also exist in the private-payment validation path, which is directly reachable by a private-payment counterparty:
- `indivisible_asset.js` logs the full spend-proof preimage — including `address`, `amount`, and the output `blinding` factor used to hide the payment amount — for every incoming private-payment input during validation: [4](#0-3) 
- `indivisible_asset.js` `validateAndSavePrivatePaymentChain` logs the entire private-element chain (`JSON.stringify(arrPrivateElements)`) and each output being inserted, again including blinding factors and amounts: [5](#0-4) [6](#0-5) 

### Impact Explanation
The blinding factor of a private/indivisible-asset output is the secret that keeps the payment amount confidential; once logged, anyone who can read the node's log (log aggregation/monitoring services, crash reporters, shared hosts, or a subsequently compromised/backed-up log file) can de-anonymize the amount and correlate the private payment, defeating the privacy guarantee that `is_private` assets are designed to provide. More severely, the `decryptPackage` logging can capture forwarded textcoin `mnemonic` values — which are themselves spending keys for pre-funded outputs — allowing anyone with log access to claim those funds, i.e., unauthorized spending of the affected textcoin balance. This satisfies the "concrete unauthorized spending" / "AA/private-payment fund loss" bar, assuming any downstream log exposure (a realistic and common failure mode for CWE-532-class bugs, as in the original MoinMoin advisory).

### Likelihood Explanation
No special privilege is required to trigger the logging: any paired correspondent device (or the hub relaying on the correspondent's behalf) merely has to send a normal, valid device message (e.g. a private-payment chain, a textcoin mnemonic forward, or any chat message) for `decryptPackage` to log its full plaintext. Likewise, any private-payment counterparty need only send a private-payment chain to a recipient/cosigner to have their blinding factors and amounts written to that node's log during validation/saving. The actual severity depends on whether/how the resulting log file is ever exposed off-device, which is an operational factor outside ocore's control — but the vulnerability itself (writing secrets to logs) is triggered with high likelihood in ordinary use of the wallet/private-payment/textcoin features.

### Recommendation
- Remove or redact the `console.log("decrypted: "+decrypted_message)` statement in `device.js`'s `decryptPackage`, or at minimum strip/replace fields known to carry secrets (mnemonics, blinding factors, private payloads) before logging, and gate any diagnostic logging behind an explicit debug flag that defaults to off.
- In `indivisible_asset.js`, stop logging full spend-proof preimages and private-element chains (`console.log("validation spend proof: ...")`, `console.log("saving private chain "+JSON.stringify(...))`, `console.log("inserting output "+JSON.stringify(output))`); log only non-sensitive identifiers (unit, message_index, output_index) needed for debugging.
- Audit other `console.log` sites that stringify full payloads containing `mnemonic`, `blinding`, or private-payment data (e.g., `wallet.js` `claimBackOldTextcoins`/`eraseTextcoin` paths that log `row.mnemonic`) and apply the same redaction.
- Route all logging through a central logger that supports level-based suppression and field redaction, rather than raw `console.log`, so sensitive fields can be centrally filtered in production.

### Proof of Concept
1. Pair device B with device A (or have B relay through the shared hub) as a normal correspondent.
2. From B, send A a legitimate encrypted device message whose JSON payload contains a `private_payment` chain with an `outputs[]` entry carrying `blinding` and `amount`, or a textcoin-forwarding message containing `mnemonic`.
3. On A's node, `handleMessageFromHub` → `decryptPackage` runs, decrypts the AES-GCM payload, and executes `console.log("decrypted: "+decrypted_message)`, writing the full JSON — including the `blinding` factor / `mnemonic` — to stdout/log. [1](#0-0) 
4. Separately, if the message is a private-payment chain, `indivisible_asset.js`'s validation/save path additionally logs the spend-proof preimage and full private-element chain, again exposing `address`, `amount`, and `blinding`. [4](#0-3) [5](#0-4) 
5. Any process/service with read access to A's log output (log shipping, crash reporting, hosting provider, etc.) can now recover the private payment's amount/blinding (breaking privacy) or the textcoin mnemonic (enabling theft of the associated funds).
