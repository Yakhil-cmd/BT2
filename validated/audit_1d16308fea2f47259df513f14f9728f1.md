### Title
JSON-RPC server disables DNS-rebinding `Host` header protection whenever CORS is set permissive (`--dev` mode / `--rpc-cors all`), while unsafe methods remain enabled on loopback - ([File: substrate/client/rpc-servers/src/utils.rs])

### Summary
Substrate/Polkadot node's JSON-RPC server implements a `HostFilterLayer` specifically to defend against DNS-rebinding attacks against the loopback-bound RPC endpoint, but the filter is only constructed when CORS is *not* permissive. When an operator runs with `--dev` (or explicitly passes `--rpc-cors all`), CORS is turned into `Cors::All`, which is converted to `None` and directly disables the anti-DNS-rebinding host filter as well, even though the socket still only listens on `127.0.0.1`/`[::1]`. Combined with the fact that "unsafe" RPC methods (`author_insertKey`, `author_rotateKeys`, `author_removeExtrinsic`, etc.) are allowed by default on loopback (`RpcMethods::Auto`), this reproduces the exact bug class described in the Rojo advisory: a supposedly loopback-only, developer-workflow HTTP/WS service with no `Host`/`Origin` validation, reachable from an attacker-controlled webpage via DNS rebinding.

### Finding Description
The RPC server binds a `HostFilterLayer` only when CORS is configured (`self.cors.is_some()`): [1](#0-0) [2](#0-1) 

`try_into_cors` shows that when `cors` is `None` the CORS layer becomes fully permissive (`CorsLayer::permissive()`): [3](#0-2) 

The CLI's `Cors` enum collapses `"all"`/`"*"` into `Cors::All`, which is converted to `None`: [4](#0-3) 

And `RpcParams::rpc_cors` explicitly sets CORS to `Cors::All` (i.e. disables both CORS *and*, as a side effect, host filtering) whenever the node is run with `--dev`: [5](#0-4) 

Meanwhile the socket itself still only binds to loopback in this configuration (`rpc_interface` only switches to `UNSPECIFIED` when `--rpc-external`/`--unsafe-rpc-external` is passed, which `--dev` does not imply): [6](#0-5) 

And "unsafe" RPC methods are enabled by default for any loopback connection regardless of CORS settings: [7](#0-6) 

Those unsafe methods gate sensitive keystore/pool operations behind `check_if_safe`, e.g. `author_insertKey`, `author_rotateKeys`, `author_removeExtrinsic`: [8](#0-7) 

Put together: with `--dev` (a routine, undocumented-as-dangerous developer workflow, analogous to `rojo serve`), the node:
1. Listens only on `127.0.0.1`/`[::1]` (developer assumes this means "only my machine can reach it").
2. Serves fully-permissive CORS (`Access-Control-Allow-Origin: *`), because dev mode disables CORS "for convenience."
3. As a direct consequence of (2), also disables the dedicated `Host` header check that exists specifically to stop DNS rebinding (`host_filtering` is gated on `cors.is_some()`).
4. Allows "unsafe" methods on loopback by default, including keystore mutation (`author_insertKey`), transaction-pool censorship (`author_removeExtrinsic`), and other unsafe modules (e.g. offchain local storage, system peer management) wired the same way.

This is structurally the same flaw the Rojo PR #1270 fixed: `Host`/`Origin` validation must not be conditioned on whether CORS is permissive — CORS is a browser-side, `Origin`-based check that DNS rebinding is specifically designed to defeat, while `Host` validation is a server-side check that must remain independent to stop rebinding. Here, disabling CORS also silently disables the only defense that would have caught a DNS-rebound request.

### Impact Explanation
A developer running a node with `--dev` (extremely common for local chain development/testing, exactly analogous to a Roblox developer running `rojo serve`) who visits an attacker-controlled webpage in any browser on the same machine can be targeted via DNS rebinding. Once rebound to `127.0.0.1:9944`, the attacker's page can issue same-origin-appearing `fetch()`/WebSocket requests that:
- Read chain/node state via safe RPC methods (info disclosure).
- Call unsafe methods without any additional check because `check_if_safe` only inspects the `DenyUnsafe` extension derived from `(loopback, RpcMethods::Auto)`, which is `No` here — e.g. `author_insertKey` (poison the node's keystore with attacker-chosen key material under an arbitrary key type), `author_rotateKeys`/`author_removeExtrinsic` (disrupt block authoring / censor transactions), and other unsafe-gated modules exposed the same way (e.g. offchain local storage, peer management).

This does not require any privileged role, governance action, or stolen keys — only that the victim keeps `rojo`-equivalent dev server (`--dev` node) running and browses the web, matching the report's "no further user interaction" pattern once the initial page is visited.

### Likelihood Explanation
Likelihood is real but narrower than the Rojo case: `--dev` mode is a very common workflow for local Substrate/Polkadot chain development (parachain templates, tutorials, CI dev-chain spin-ups), so the vulnerable configuration is reached without any unusual operator choice. The same disabling of `host_filter` also occurs whenever an operator explicitly passes `--rpc-cors all` on a loopback-bound endpoint (seen used together with `--unsafe-rpc-external` in the repo's own `docker/dockerfiles/polkadot/docker-compose.yml`, though that combination is already externally exposed and out of scope for the loopback-trust argument). For the plain `--dev` case, the developer's threat model is "only I can reach 127.0.0.1", which DNS rebinding specifically defeats, and the code has no compensating control once CORS permissiveness is chosen.

### Recommendation
Decouple the `HostFilterLayer` construction from the CORS configuration: always enforce a `Host` allow-list of `localhost`/`127.0.0.1`/`[::1]` (plus the configured port) for any endpoint bound to a loopback address, independent of whether CORS is permissive. Only skip host filtering for endpoints intentionally bound to non-loopback addresses (which already require `--rpc-external`/`--unsafe-rpc-external`). Additionally, emit a clear operator-facing warning when `--dev` or `--rpc-cors all` disables the host filter on a loopback socket, mirroring the warning already present for `--unsafe-rpc-external`.

### Proof of Concept
Not executed against a running node in this session — no filesystem/terminal access was available to spin up a `--dev` node and browser harness in this ask-only investigation. The finding is based on static code tracing showing:
- `host_filtering(self.cors.is_some(), local_addr)` unconditionally disables the `HostFilterLayer` whenever `cors` is `None` (i.e., permissive/"all"), at `substrate/client/rpc-servers/src/utils.rs:146,199-213`.
- `RpcParams::rpc_cors` sets `Cors::All` → `None` specifically for `--dev`, at `substrate/client/cli/src/params/rpc_params.rs:195-214`.
- The socket still binds only to loopback in this mode (`rpc_interface`, `substrate/client/cli/src/params/rpc_params.rs:300-327`), and `deny_unsafe` grants unsafe access by default on loopback (`substrate/client/rpc-servers/src/utils.rs:288-294`), with unsafe methods such as `author_insertKey` gated only by `check_if_safe` (`substrate/client/rpc/src/author/mod.rs:138-152`).

A concrete browser-based DNS-rebinding PoC (rebind an attacker domain to `127.0.0.1`, then issue `fetch('http://attacker-domain.example:9944', {method:'POST', body: JSON.stringify({jsonrpc:"2.0",method:"author_insertKey",params:[...],id:1})})`) was not executed; this should be validated with an actual local integration test (spin up `sc-rpc-server` with `cors=None`, connect with a request whose `Host` header is an arbitrary rebound domain, and confirm the request is *not* rejected, contrasted with the case where `cors=Some([...])` correctly rejects it via `HostFilterLayer`) before treating this as bounty-eligible, since I could not run that harness in this environment.

pub(crate) fn host_filtering(enabled: bool, addr: SocketAddr) -> Option<HostFilterLayer> {
	if enabled {
		// NOTE: The listening addresses are whitelisted by default.

		let hosts = [
			format!("localhost:{}", addr.port()),
			format!("127.0.0.1:{}", addr.port()),
			format!("[::1]:{}", addr.port()),
		];

		Some(HostFilterLayer::new(hosts).expect("Valid hosts; qed"))
	} else {
		None
	}
}

pub(crate) fn try_into_cors(
	maybe_cors: Option<Vec<String>>,
) -> Result<CorsLayer, Box<dyn StdError + Send + Sync>> {
	if let Some(cors) = maybe_cors {
		let mut list = Vec::new();

		for origin in cors {
			list.push(HeaderValue::from_str(&origin)?)
		}

		Ok(CorsLayer::new().allow_origin(AllowOrigin::list(list)))
	} else {
		// allow all cors
		Ok(CorsLayer::permissive())
	}
}

/// Get the `deny_unsafe` setting based on the address and the RPC methods exposed by the interface.
pub fn deny_unsafe(addr: &SocketAddr, methods: &RpcMethods) -> DenyUnsafe {
	match (addr.ip().is_loopback(), methods) {
		(_, RpcMethods::Unsafe) | (true, RpcMethods::Auto) => DenyUnsafe::No,
		_ => DenyUnsafe::Yes,
	}
}

fn rpc_interface(
	is_external: bool,
	is_unsafe_external: bool,
	rpc_methods: RpcMethods,
	is_validator: bool,
) -> crate::Result<(Ipv4Addr, Ipv6Addr)> {
	if is_external && is_validator && rpc_methods != RpcMethods::Unsafe {
		return Err(crate::Error::Input(
			"--rpc-external option shouldn't be used if the node is running as \
			 a validator. Use `--unsafe-rpc-external` or `--rpc-methods=unsafe` if you understand \
			 the risks. See the options description for more information."
				.to_owned(),
		));
	}

	if is_external || is_unsafe_external {
		if rpc_methods == RpcMethods::Unsafe {
			eprintln!(
				"It isn't safe to expose RPC publicly without a proxy server that filters \
				 available set of RPC methods."
			);
		}

		Ok((Ipv4Addr::UNSPECIFIED, Ipv6Addr::UNSPECIFIED))
	} else {
		Ok((Ipv4Addr::LOCALHOST, Ipv6Addr::LOCALHOST))
	}
}

			.into_iter()

			.pool
			.report_invalid(None, hashes)
			.await
			.into_iter()
			.map(|tx| tx.hash().clone())
			.collect())
