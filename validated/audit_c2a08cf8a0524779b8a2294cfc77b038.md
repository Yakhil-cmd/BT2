### Title
Webhook signature verification keys off `repository.owner.login` while all downstream processing keys off `repository.full_name`, allowing a different organization's secret to authorize writes to another org's stack - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects which `GitHubApp`/webhook secret to use for HMAC verification based on `repository.owner.login` (or `organization.login`) pulled from the **unverified** JSON body, but the actual data written by handlers (which stack/repository gets updated) is derived from a **different** field in the same unverified body: `repository.full_name`. This breaks the intended binding "organization that authenticated the webhook == repository being written."

### Finding Description
`verify_signature` computes `repository_owner` from the raw, not-yet-verified payload and uses it to select the per-organization `GitHubApp` (and thus the per-org `webhook_secret`) used to validate the HMAC signature: [1](#0-0) [2](#0-1) 

Multi-organization configuration is supported: `Shipit.github(organization:)` looks up a distinct config (and distinct `webhook_secret`) per organization key: [3](#0-2) 

Meanwhile, every webhook `Handler` resolves the target `Stack`/`Repository` using a completely different payload field, `repository.full_name`, not `repository.owner.login`: [4](#0-3) 

Because HMAC verification covers the raw request body as a whole but the *decision of which secret to check it against* is made from an attacker-controlled field (`repository.owner.login`) that is independent of the field actually used to route the payload (`repository.full_name`), an attacker who knows (or controls) the webhook secret for **one** organization configured in Shipit can forge a payload where:
- `repository.owner.login` = `orgA` (the org whose secret the attacker knows/controls, e.g. their own org's webhook secret they can read from their own repo settings or because they administer that org on GitHub), and
- `repository.full_name` = `orgB/target-repo` (a different, victim organization's repository tracked as a Stack in the same Shipit instance).

The signature is computed and verified using `orgA`'s secret, which the attacker knows, so `verify_signature` passes. The `create` action then dispatches the same payload to the event handler, which resolves the affected `Stack` via `repository.full_name` = `orgB/target-repo`, i.e. a repository outside the org whose secret actually authenticated the request: [5](#0-4) 

This is the structural analog of the reported bug class: a value is trusted/acted upon (`repository.full_name`, driving the write) while a *different* field (`repository.owner.login`) is the one actually covered by the security check (secret selection), and the contract's binding invariant — "the org whose credential validated the payload is the org being written to" — is silently broken, exactly as `originalAllocation` was reset without the corresponding reward-accrual state (`rewardPerToken`/`lastRewardPerTokenUsed`) being brought in sync first.

### Impact Explanation
Depending on which webhook events are supported for cross-org injection (e.g. `push`, `status`, `check_suite`, `pull_request`, `membership`), this could let an attacker with control of one configured organization's GitHub webhook secret inject forged events (commit statuses, check-run results, PR label/merge events, deploy-relevant state) against a Stack belonging to an unrelated organization/repository tracked by the same Shipit instance. Depending on the specific handler, this can influence which commits are marked deployable, alter merge/PR status caching, or affect review-stack lifecycle — i.e., cross-repository state corruption steered by an org that has no legitimate relationship to the targeted repository. This matches the "cross-repository writes" Critical-impact criterion when the affected handler leads to state changes that gate an unauthorized deploy/merge/rollback decision.

### Likelihood Explanation
This requires the operator to run a **multi-organization** Shipit configuration (a supported, documented mode via `Shipit.github(organization:)`/`github_app_config`), and for the attacker to know a valid `webhook_secret` for *some* org configured in that instance (which is plausible if the attacker administers or previously had access to any one of the multiple orgs onboarded to the shared Shipit deployment — no privileged Shipit account, `ApiClient` token, or GitHub App private key is needed, only knowledge of one org's own webhook secret, which is not gated by Shipit itself). The mismatch between `repository_owner` (verification) and `repository_name`/`full_name` (routing) is a straightforward, always-present code path, not a corner case.

### Recommendation
Verify that the organization used to select the webhook secret is the same organization implied by the field(s) used for routing/handling (`repository.full_name`'s owner segment, or `organization.login` for org-level events), rejecting payloads where they diverge, e.g.:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end

def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  ...
  full_name_owner = params.dig('repository', 'full_name')&.split('/')&.first
  head(422) and return if full_name_owner && full_name_owner.casecmp(repository_owner).nonzero?
  ...
end
```
Alternatively, resolve the target `Stack`/`Repository` strictly from the same org value that was used to authenticate the signature, rather than trusting `repository.full_name` independently in `Handler#repository_name`.

### Proof of Concept
1. Configure Shipit with two organizations, `orgA` and `orgB`, each with its own `webhook_secret` (per `github_app_config`).
2. Attacker knows `orgA`'s webhook secret (e.g., they administer `orgA` on GitHub and can view/set its webhook secret).
3. Attacker crafts a JSON body for a supported event (e.g. `status`) with:
   ```json
   { "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/target-repo" }, "sha": "...", "state": "success", ... }
   ```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(orgA_secret, body)` and POSTs to `/github/webhooks`.
5. `verify_signature` resolves `Shipit.github(organization: "orgA")` and validates successfully using the known secret.
6. `Shipit::Webhooks.for_event('status')` handlers execute, resolving the target repository via `payload.dig('repository', 'full_name')` = `orgB/target-repo`, applying the forged status to a stack the attacker does not control and whose organization never authenticated this request.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
