Found the binding break: signature verification is keyed on `repository.owner.login`, but every webhook handler resolves the actual `Repository`/`Stack` to write to using `repository.full_name` — a separate field in the same JSON body that is never independently checked against `repository.owner.login`.

### Title
Webhook signature verified against `repository.owner.login` while handlers act on the unchecked `repository.full_name` field, allowing cross-repository writes from an organization with a valid webhook secret - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to verify the HMAC signature against using `repository_owner`, computed as `params.dig('repository', 'owner', 'login')`. [1](#0-0) [2](#0-1) 
The HMAC covers the raw request body, so the value of `repository.owner.login` and `repository.full_name` inside that body are both technically "signed" as bytes — but only `repository.owner.login` is used to pick *which* secret is the correct one to check against, while the actual object mutated by the handler is chosen from `repository.full_name` via `Handler#repository_name`/`Repository.from_github_repo_name`. [3](#0-2) [4](#0-3) 

### Finding Description
The equality the engine implicitly relies on is:

`organization that authenticated the signature (repository.owner.login)` == `repository that is written (repository.full_name)`

This equality is never enforced in code. An organization admin who legitimately controls a GitHub App installation/webhook secret for org `A` (e.g. `evil-org`) can craft a webhook payload where `repository.owner.login` is `evil-org` (so `Shipit.github(organization: 'evil-org')` is selected and the signature computed with `evil-org`'s `webhook_secret` verifies successfully) while `repository.full_name` is set to `victim-org/some-repo`. `PullRequest::OpenedHandler` (and the sibling `Closed/Labeled/Reopened/...Handler`s) resolve the target `Repository`/`ReviewStack` purely from `params.repository.full_name`, with no check that this matches the signing organization. [5](#0-4) 

Because `verify_webhook_signature` only proves the byte string was signed by *some* known secret, not that the secret's owner matches the object being mutated, an attacker with a valid webhook secret for their own org can forge events (`pull_request`, `status`, `push`, `check_suite`, etc.) that name any other repository already registered in the Shipit instance, and the corresponding handler will act on it.

### Impact Explanation
This crosses a repository-write trust boundary: an organization that is only authorized to sign/deliver webhooks for its own repositories can cause writes on `Repository`/`Stack`/`ReviewStack` records belonging to a completely different, victim organization (e.g., auto-provisioning a review stack, closing/merging status effects, or triggering merge/commit-status side effects tied to `victim-org/some-repo`). This matches the "Critical — cross-repository writes" impact category.

### Likelihood Explanation
Exploitability requires the attacker to already control a valid `webhook_secret` for at least one organization configured in the Shipit instance (a realistic scenario in multi-tenant Shipit deployments where many orgs each configure their own GitHub App/webhook secret), and for the target repository to already exist as a `Shipit::Repository` record. No `ApiClient` token, session, or GitHub write access to the victim repo is needed — only knowledge of one's own legitimate webhook secret and the target's `owner/name`, both of which are discoverable.

### Recommendation
In `WebhooksController#verify_signature` / `Handler`, after resolving the target `Repository` from `repository.full_name`, assert that its `owner` equals `repository_owner` (the value used to select the signing secret) before allowing any handler to mutate state. Reject the request (e.g. `head(422)`) if the owner used for signature verification does not match the owner encoded in `repository.full_name`.

### Proof of Concept
1. Attacker's org `evil-org` has a Shipit GitHub App integration with a known `webhook_secret`.
2. Attacker crafts a `pull_request` webhook JSON body:
```json
{
  "action": "opened",
  "repository": { "owner": { "login": "evil-org" }, "full_name": "victim-org/victim-repo" },
  "pull_request": { ... }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(evil-org_webhook_secret, raw_body)` and POSTs to `/webhooks`.
4. `repository_owner` resolves to `evil-org` [2](#0-1) , `Shipit.github(organization: 'evil-org')` verifies the signature successfully using `evil-org`'s secret.
5. `PullRequest::OpenedHandler` resolves `repository` from `params.repository.full_name` = `"victim-org/victim-repo"` [6](#0-5)  and, if provisioning is enabled, creates/mutates a `ReviewStack` for `victim-org/victim-repo` — a write on a repository the attacker never proved control over.
