## Finding

### Title
`initialize_with_permission` inconsistently establishes `pool_creator` compared to `initialize`, allowing an unvalidated, unsignable address to be recorded as the perpetual creator-fee beneficiary - (File: programs/cp-swap/src/instructions/initialize_with_permission.rs)

### Summary
`initialize` and `initialize_with_permission` both create a pool and record a `pool_creator` field that permanently controls the right to withdraw `creator_fees_token_0/1` via `collect_creator_fee`. The two entry points handle "who is the creator" inconsistently: in the permissionless path the recorded creator is guaranteed to be the same `Signer` who pays and funds the pool, while in the permissioned path the recorded creator is an entirely unconstrained, non-signing `UncheckedAccount` chosen freely by the caller.

### Finding Description
In `programs/cp-swap/src/instructions/initialize.rs`, the `creator` account is a `Signer<'info>` that both pays for pool creation and supplies the initial liquidity: [1](#0-0) [2](#0-1) 
`pool_state.initialize(...)` records `ctx.accounts.creator.key()` as `pool_creator` - a pubkey that is provably capable of signing (it just signed this transaction).

In `programs/cp-swap/src/instructions/initialize_with_permission.rs`, the account that actually pays and funds the pool is `payer` (`Signer`), while a *separate* `creator` field is declared with no signer requirement, no ownership check, and no relationship constraint to `payer`: [3](#0-2) 
That same unconstrained `creator` is then written into `pool_state` as the permanent `pool_creator`: [4](#0-3) 

The only gate on calling `initialize_with_permission` is that `payer` holds a `permission` PDA created by the protocol admin: [5](#0-4) 
This PDA is keyed on `payer`, not on `creator`, so it does nothing to constrain what value the (otherwise fully attacker-controlled, since `payer` chooses all instruction accounts) `creator` field can take.

`pool_creator` subsequently gates who can call `collect_creator_fee` (`address = pool_state.load()?.pool_creator`, requiring `creator` to be a `Signer`): [6](#0-5) 
and determines the ATA destination used by `collect_creator_fee_permissionless`: [7](#0-6) 

Because `creator` in `initialize_with_permission` is never validated to be a genuine, signable wallet (e.g., it can be set to a PDA of another program, the System Program ID, the Token Program ID, or any other address for which no private key is ever obtainable), the pool's accumulated `creator_fees_token_0`/`creator_fees_token_1` can become permanently unclaimable: `collect_creator_fee` will always fail (no one can produce that signature) and `collect_creator_fee_permissionless` will only push funds into an ATA that is likewise inaccessible.

### Impact Explanation
This results in permanent freezing of the creator-fee portion of swap fees accrued in the pool's vaults, since those funds can never be withdrawn once `pool_creator` is fixed to an unsignable address at pool initialization; there is no instruction to change `pool_state.pool_creator` after the fact.

### Likelihood Explanation
Any account holding a valid `Permission` PDA (an already-permitted, non-privileged caller in the sense that it's just a whitelisted integrator/launchpad, not the protocol admin) can call `initialize_with_permission` with an attacker-chosen `creator` account in a single transaction, since the field has no constraint at all beyond existing in the account list. No additional privilege or race condition is required.

### Recommendation
Constrain `creator` in `InitializeWithPermission` similarly to how `creator`/`payer` are handled in `Initialize` — e.g., require it to be a `Signer` (so it is provably capable of later signing `collect_creator_fee`), or otherwise validate that the chosen address is not a program ID / PDA with no associated signer, before recording it as `pool_state.pool_creator`.

### Proof of Concept
1. Protocol admin grants a `Permission` PDA to `payer` via `create_permission_pda`.
2. `payer` calls `initialize_with_permission`, supplying `creator = <arbitrary/unsignable pubkey, e.g. a foreign-program PDA>`.
3. `pool_state.initialize(...)` stores this pubkey as `pool_creator`.
4. Swaps occur and `creator_fees_token_0/1` accumulate in the pool's vaults.
5. No entity can ever call `collect_creator_fee` (fails the `address = pool_state.load()?.pool_creator` signer constraint) nor meaningfully spend from the ATA credited by `collect_creator_fee_permissionless`, permanently locking those accrued creator fees inside the pool's vaults/ATA.
