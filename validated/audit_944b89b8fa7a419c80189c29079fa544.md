## Analog Found

### Title
Precision-loss overflow in the `sum` definition operator bypasses spending-limit authentifier conditions - (File: `definition.js`)

### Summary
The Conflux fix hardens two places that accumulate untrusted per-item values into a fixed-width integer without an overflow-safe check, only validating the *final* total. `ocore` has the same accumulation pattern in the `sum` oscript operator used inside address definitions/authentifiers, and its overflow guard (`isFinite`) does not actually detect the practical overflow condition (loss of integer precision above `Number.MAX_SAFE_INTEGER`), unlike a `checked_add`.

### Finding Description
The `sum` case in `evaluate()`/`validateAuthentifiers` accumulates `arrFoundObjects[i].amount` into a plain JS number with a bare `+=` in a loop, then only checks `isFinite(sum)` before comparing against the definition's `at_least`/`at_most`/`equals` bound: [1](#0-0) 

Unlike Rust's `U256` (which panics/aborts on overflow — the exact failure mode the Conflux patch defends against), JavaScript numbers do not panic when they exceed `Number.MAX_SAFE_INTEGER` (`2^53-1`, i.e. `9007199254740991`) — they silently lose integer precision while remaining a finite `Number`. So `isFinite(sum)` never triggers for this class of overflow; it would only catch a true `Infinity`/`NaN`, which double-precision addition of positive integers essentially never produces here. This mirrors the report's root cause: a bound-check gate that is bypassed because the accumulation itself is unchecked before the gate runs.

The amounts being summed are transaction outputs/inputs, each individually bounded only by `constants.MAX_CAP = 9e15`: [2](#0-1) 
which is very close to `Number.MAX_SAFE_INTEGER` (`9007199254740991 ≈ 9.007e15`). For uncapped, non-fixed-denomination assets, the issuer can perform multiple separate issuances of up to `MAX_CAP` each (no aggregate limit on total issued for an uncapped asset), and a single unit may carry up to `MAX_INPUTS_PER_PAYMENT_MESSAGE`/`MAX_OUTPUTS_PER_PAYMENT_MESSAGE` (128) such amounts across up to `MAX_MESSAGES_PER_UNIT` (128) payment messages: [3](#0-2) 
This makes it feasible to construct a small number of same-asset outputs/inputs whose individual values are each within the per-item `MAX_CAP` limit but whose floating-point sum crosses the `2^53` precision boundary, silently rounding the computed `sum` away from its true mathematical value.

### Impact Explanation
The `sum` operator is intended to let an address definition enforce spending/limit conditions (e.g. a shared or restricted address that only permits a party to spend "at most X of asset Y", or requires "exactly X" as an authorization gate) — this is exactly the kind of authentifier condition covered by the allowed "address definitions and authentifiers" attack surface. Because the accumulation can silently lose precision instead of being rejected, a party constrained by such a `sum`-based condition can craft a unit whose true total exceeds (or falls short of) the intended threshold while the computed `sum` rounds to a value that still satisfies `at_most`/`at_least`/`equals`, letting them **spend beyond an authorized limit** enforced by the address's own definition — a concrete unauthorized-spending outcome from a single posted unit, without needing to compromise any key.

### Likelihood Explanation
Exploitation requires: (1) an address definition/oscript condition using `sum` with a bound (`at_least`/`at_most`/`equals`) over a filterable asset, and (2) the attacker being able to accumulate qualifying inputs/outputs whose true sum straddles `2^53` while each individual amount stays under `MAX_CAP`. This is achievable within existing per-message/per-unit structural limits for uncapped assets (no protocol-level cap prevents an issuer from creating several `MAX_CAP`-sized amounts). It does require the target address definition to actually use a `sum` bound as an authorization gate, which somewhat narrows likelihood versus a universally-reachable path, but no privileged, peer-level, or node-operator access is needed — an ordinary unit poster is sufficient.

### Recommendation
Replace the raw `+=` accumulation in the `sum` case with an accumulator that rejects (or is bounded before) crossing `Number.MAX_SAFE_INTEGER`, e.g. check `arrFoundObjects[i].amount` against `Number.MAX_SAFE_INTEGER - sum` before each add and fail the evaluation (return `cb2(false)` / throw a validation error) instead of relying on `isFinite(sum)`, which cannot detect precision-loss overflow. Consider using `BigInt` or `Decimal`-based summation for this operator to make the result exact regardless of the number of terms.

### Proof of Concept
1. Definer creates an uncapped, non-fixed-denomination custom asset and issues it twice, each issuance amount close to `4.6e15` (each ≤ `MAX_CAP = 9e15`), to a shared/restricted address whose definition includes a condition such as `['sum', {filter: {what: 'input', asset: '<asset>'}, at_most: 5000000000000000}]`.
2. The constrained party crafts a single unit spending both inputs together in one payment message referencing that asset; `total_input` for these two inputs is `~9.2e15`, which exceeds `Number.MAX_SAFE_INTEGER`.
3. During authentifier evaluation, `definition.js`'s `sum` case adds the two `arrFoundObjects[i].amount` values with `sum += ...`; due to IEEE-754 double rounding above `2^53`, the resulting `sum` can round down below the `at_most: 5e15` bound (or otherwise diverge from the true total) while remaining finite, so `isFinite(sum)` never trips and the `at_most` check incorrectly passes.
4. The unit is accepted as satisfying the spending-limit condition even though the true summed amount exceeds the intended limit, letting the party the condition was meant to restrict spend more than authorized.
