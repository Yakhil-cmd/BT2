### Title
Membership webhooks trust the GitHub `team.id` without binding it to the authenticated organization, allowing cross-organization `Shipit.github_teams` privilege escalation - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to verify a webhook against using an organization name taken directly from the unverified request body, and `GithubApp#verify_webhook_signature` treats an org with no configured `webhook_secret` as automatically verified. `MembershipHandler` then looks up the `Team` to mutate using only the GitHub `team.id` field from that same payload, with no check that the team actually belongs to the organization that was (nominally) authenticated. This breaks the binding "organization that authenticated == team/organization actually written," letting an attacker who only needs to know an existing `Shipit.github_teams` team's numeric GitHub id add an arbitrary GitHub login (including their own) to that authorization-granting team.

### Finding Description
`WebhooksController#verify_signature` derives the organization used for signature verification from the untrusted payload itself: [1](#0-0) [2](#0-1) 

For a `membership` event there is no `repository` key, so `repository_owner` falls back to `organization.login`, which is fully attacker-controlled. `GithubApp#verify_webhook_signature` short-circuits to `true` whenever the selected organization has no `webhook_secret` configured: [3](#0-2) 

An unconfigured/blank `webhook_secret` per organization is a documented, ordinary configuration state (not a leaked credential): [4](#0-3) 

Once past this org-scoped signature gate, `MembershipHandler#process` resolves and mutates the `Team` record using only the numeric GitHub `team.id` supplied in the same payload, without any check that this team belongs to the organization that was used for the signature check: [5](#0-4) 

`Team.find_or_create_by!(github_id: params.team.id)` matches purely on `github_id`; if a `Team` row with that id already exists (created by legitimate sync of a different, secured organization), it is fetched and mutated with no organization equality check: [6](#0-5) 

The `member.login` field is resolved via `User.find_or_create_by_login!`, which fetches a real GitHub identity by login through the API and creates/finds a `User` bound to that GitHub account's `github_id`: [7](#0-6) 

This `github_id` is exactly what later binds a normal, legitimate OAuth login session to the same `User` row, and `User#authorized?` checks membership in `Shipit.github_teams` by id: [8](#0-7) 

The binding that should hold is: **organization whose signature was verified == organization owning the `team.id` acted upon**. Before the attack, `Team#github_id` → `Team#organization` is only ever set by legitimate GitHub events from the real owning org. After the attacker's forged `membership` webhook (verified only against an unrelated, secret-less organization), an arbitrary attacker-chosen GitHub login is added as a member of a `Team` belonging to a different, secured organization — with no re-verification that the forged event actually originated from that team's organization.

### Impact Explanation
This escalates into `Shipit.github_teams` authorization, one of the explicitly listed High-impact outcomes. `Shipit`'s entire access-control model for the web UI/API relies on: OAuth login (which anyone with a GitHub account can complete, since Shipit's OAuth app has no install-time allowlist beyond team membership) plus membership in one of `Shipit.github_teams`. Forging a `membership` webhook to add a chosen GitHub login to a required team, and then completing the ordinary OAuth flow with that GitHub account, grants an otherwise-unprivileged GitHub user full authorized access to Shipit (deploys, rollbacks, stack configuration, API client management, etc.), because `User#authorized?` merely checks team membership rows that the attacker can now forge.

### Likelihood Explanation
Likelihood is moderate-to-high in any multi-organization Shipit deployment (explicitly documented as a supported configuration) where at least one configured GitHub organization has no `webhook_secret` set — a state shown as the default/example in the repo's own secrets templates. No credentials, tokens, or privileged access are required: only knowledge of (a) any org name configured in Shipit without a webhook secret, and (b) the numeric GitHub `team.id` of the team referenced by `Shipit.github_teams` (discoverable via the public GitHub API for any team the attacker can view, or via GitHub UI/API metadata).

### Recommendation
Scope `Team` lookups/mutations in `MembershipHandler` (and any other handler resolving records solely by a GitHub-provided numeric id) by the organization that was actually authenticated for that request, e.g. `Team.find_or_create_by!(github_id: params.team.id, organization: repository_owner)` and reject/ignore membership events where an existing team's `organization` does not match the authenticated organization. Additionally, require and enforce a non-blank `webhook_secret` for every configured GitHub organization (treat a missing secret as a hard configuration error rather than an automatic-pass condition) so that no organization can be used as a "free" signature bypass.

### Proof of Concept
1. Configure (or target a deployment that already has) two GitHub orgs in `config/secrets.yml`: `orgX` with `webhook_secret` left blank, and `orgY` which is a real, secured org whose team `id=4242` is listed in `Shipit.github_teams`.
2. Send an unsigned/any-signature POST to the webhooks endpoint:
```
X-Github-Event: membership

{
  "action": "added",
  "team": { "id": 4242, "name": "Developers", "slug": "developers", "url": "http://x" },
  "organization": { "login": "orgX" },
  "member": { "login": "attacker-github-login" }
}
```
3. `verify_signature` resolves `repository_owner` = `"orgX"` (no `repository` key), calls `Shipit.github(organization: "orgX")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the signature header.
4. `MembershipHandler#process` finds the existing `Team` with `github_id: 4242` (belonging to `orgY`) and adds `User` for `attacker-github-login` (fetched from GitHub's real API by login) to it.
5. Attacker completes normal GitHub OAuth login into Shipit as `attacker-github-login`; `User#authorized?` now returns `true` because the forged membership row satisfies `Shipit.github_teams` membership, granting the attacker full Shipit access without ever possessing `orgY`'s webhook secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    class << self
      def find_or_create_by_handle(handle)
        organization, slug = handle.split('/').map(&:downcase)
        find_by(organization:, slug:) || fetch_and_create_from_github(organization, slug)
      end

      def fetch_and_create_from_github(organization, slug)
        return unless github_team = find_team_on_github(organization, slug)

        create!(github_team:, organization:)
      end

      def find_team_on_github(organization, slug)
        gh_api = Shipit.github(organization:).api
        teams = Shipit::OctokitIterator.new(github_api: gh_api) { gh_api.org_teams(organization, per_page: 100) }
        teams.find { |t| t.slug == slug }
      rescue Octokit::NotFound
      end
    end
