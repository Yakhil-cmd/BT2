### Title
`StatusHandler#process` updates `Commit` rows across all stacks by SHA alone, letting a cross-tenant forged status defeat `require_ci` in `Api::DeploysController#create` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)`, with no scoping to the repository/stack that actually sent the webhook. Any commit sha that is shared across repositories (e.g. a fork sharing git history with its upstream) will have its status updated for **every** `Commit` row that matches, including one belonging to a completely unrelated victim stack, which then satisfies `Commit#deployable?` and the `require_ci` gate in `Api::DeploysController#create`.

### Finding Description
The claimed binding is: `webhook.repository == commit.stack.repository`. Tracing the code shows this binding is never enforced.

- `StatusHandler#process` only matches on `sha`, never on repository/stack: [1](#0-0) 

- `Commit#create_status_from_github!` writes the status without any repository check: [2](#0-1) 

- `Commit#deployable?` becomes true purely from the status/statuses relation state: [3](#0-2) 

- `Api::DeploysController#create` looks up the commit scoped to the victim's own stack (`stack.commits.by_sha`), but trusts `commit.deployable?`, whose truthiness was set by the unscoped `StatusHandler`: [4](#0-3) [5](#0-4) 

Exploit flow: an attacker forks a victim's public repository being tracked by a Shipit stack (a normal unprivileged GitHub action). The fork shares identical git commit objects (and therefore identical SHA-1 hashes) with the upstream repository for their common history. If the attacker's fork/webhook path is itself wired into Shipit's `/webhooks` endpoint (e.g. their own onboarded stack, or any repository for which the app delivers events), the attacker can set an arbitrary commit status via the standard GitHub Statuses API on their own fork's commit — a fully legitimate action on a repository they own, requiring no forged signature, no secrets, and no Shipit privileges. GitHub then delivers a correctly-signed `status` webhook to Shipit. `StatusHandler#process` updates every `Commit` row across the whole install matching that sha — including the victim stack's row for the same shared historical commit — flipping `deployable?` to true. A subsequent `POST /api/stacks/:id/deploys` with `require_ci: true` against that sha (issued by a legitimate victim-side actor/token) now passes the `require_ci` gate despite the victim's own CI never running on that commit.

None of the existing guards catch this: `verify_signature`/`GitHubApp#verify_webhook_signature` only validate that the payload really came from GitHub for *some* repo the app is installed on — they don't bind the payload's repository to the specific `Commit`/`stack` being updated. `ExplicitParameters` on `StatusHandler` only validates presence/type of `sha`, `state`, etc., not repository identity. `stack.commits.by_sha` in the controller correctly scopes the *lookup* to the victim's stack, but that scoping happens after the underlying `Commit` row has already been mutated by the unscoped webhook handler, so it does not protect against this.

### Impact Explanation
A cross-tenant status write lets an attacker who controls only their own repository/fork flip the `deployable?` state of a commit belonging to a victim's stack, defeating the `require_ci` safety check on `Api::DeploysController#create` and enabling an unauthorized deploy of code that never passed the victim's real CI. This matches the Critical category: "a payload for one repository mutating another's stack, commit, task" and enabling "an unauthorized deploy." Blast radius spans any stacks that share commit history (forks/mirrors) with a repository the attacker controls, and is repeatable for every shared sha the attacker can reach.

### Likelihood Explanation
Requires: (1) a victim stack tracking a public (or otherwise forkable) repository whose commit history overlaps with a repository the attacker controls, (2) that attacker-controlled repository's status events actually reaching Shipit's webhook endpoint (i.e. the GitHub App/webhook is installed against that repo — this piece could not be fully confirmed from the available code, as `Handler`'s dispatch/installation-scoping logic was not fully inspected within the available iterations), and (3) a legitimate caller subsequently issuing a `require_ci: true` deploy request for the shared sha. Given those preconditions (which the prompt states as given), attacker cost is very low: forking a repo and calling the standard GitHub Statuses API is unprivileged and requires no Shipit secrets.

### Recommendation
Scope `StatusHandler#process` (and analogous handlers like check-run handlers) to only update `Commit` rows belonging to the stack(s) whose `github_repo_name`/repository matches the webhook payload's `repository.full_name`, e.g. joining through `Stack` and filtering `Commit.joins(:stack).where(sha: params.sha, shipit_stacks: { repository_id: repository_id_from_payload })` instead of a bare `Commit.where(sha: params.sha)`.

### Proof of Concept
Minitest integration test plan under `test/` (not shown here per audit scope, but described): create two stacks, `victim_stack` and `attacker_stack`, each with a `Commit` row sharing the same `sha` value. Simulate the incoming webhook payload with `repository.full_name` set to the attacker's repo and post it to the webhooks endpoint (or invoke `StatusHandler.new(...).process` directly with those params). Assert before: `victim_stack.commits.by_sha(sha).deployable? == false`. After processing the attacker-repo-sourced status payload, assert `victim_stack.commits.by_sha(sha).deployable? == true`, then issue `POST /api/stacks/:victim_stack_id/deploys` with `sha:`, `require_ci: true` and assert a `202 Accepted` response rather than the expected `422` rejection — demonstrating the `require_ci` bypass caused by the unscoped `StatusHandler` write.
