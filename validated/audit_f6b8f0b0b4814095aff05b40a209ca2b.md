### Title
Cross-org PR data injection via `repository.owner.login` / `repository.full_name` field confusion in webhook signature verification - ([File: app/models/shipit/webhooks/handlers/pull_request/edited_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate the HMAC signature against using `params.dig('repository','owner','login')`, while `EditedHandler` (and its siblings) resolve the target `Repository`/`Stack`/`PullRequest` to mutate using the completely independent `repository.full_name` field from the same attacker-controlled JSON body. No code anywhere cross-checks that these two fields refer to the same repository/org.

### Finding Description
Binding claimed: verifying org (derived from `repository.owner.login`) == owning org of the `PullRequest`/`Stack` row updated (derived from `repository.full_name`). This does not hold.

- `WebhooksController#verify_signature` computes `repository_owner = params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`. <cite repo="Camomtat/shipit-engine--021" path="app/controllers/shipit/webhooks_controller.rb" start="24-30" end="59-62" />
- `GitHubApp#verify_webhook_signature` short-circuits: `return true unless webhook_secret` — if the org resolved from `repository.owner.login` has no configured `webhook_secret` (documented as "optional" in `docs/setup.md`), signature verification is bypassed entirely, regardless of the signature header. [1](#0-0) 
- `EditedHandler#repository` and `EditedHandler#pull_request` resolve the row to mutate purely from `params.repository.full_name` via `Shipit::Repository.from_github_repo_name`, with no reference to `repository.owner.login` or to whichever org's secret was used (or skipped) during verification. [2](#0-1) 
- `Shipit::Repository.from_github_repo_name` splits `full_name` on `/` and looks the record up by `owner`/`name` columns, with no linkage back to the verifying org. [3](#0-2) 

Exploit flow: an attacker forges a `pull_request` `edited` webhook where `repository.owner.login` = an org configured in Shipit with no `webhook_secret` (or an org whose secret the attacker otherwise controls), while `repository.full_name` = `"victim-org/victim-repo"` and `pull_request.title`/`pull_request.body`... etc. contain arbitrary attacker-chosen text (including shell metacharacters). `verify_signature` passes (either trivially, via the no-secret bypass, or with a signature computed against a secret the attacker actually knows for their own org), and `EditedHandler#process` calls `pull_request.update(github_pull_request: params.pull_request)` on the `PullRequest` row belonging to `victim-org/victim-repo`, mutating data for a repository/org that never authenticated this request. [4](#0-3) 

Existing guards do not prevent this: `drop_unhandled_event` only checks the event type exists a handler; `verify_signature` never validates that `full_name`'s owner segment matches `repository.owner.login`; the `ExplicitParameters` schema only requires `full_name` be a `String`, it does not constrain it to match the org used for verification; and `Repository`/`Stack` model validations only constrain the format of `owner`/`name` columns already stored, not the incoming webhook's cross-field consistency.

### Impact Explanation
This is a payload for one repository/org mutating another org's stored `PullRequest` record — explicitly listed as a Critical-severity impact category ("a payload for one repository mutating another's stack, commit, task or team"). The attacker can overwrite `title`, `body`, `labels`, `assignees`, etc. stored in `github_pull_request` for any tracked repository across the entire multi-tenant Shipit installation, as long as they can name any org configured without a `webhook_secret` (or one whose secret they know) in the `repository.owner.login` field. If that injected title/body is later interpolated unescaped into any `Command` argument (e.g., deploy note generation), this becomes an RCE feeder, but I could not locate, within the available index, a concrete `Command#start`/`Command.new` call site that consumes `PullRequest#title` or `#body` directly — this downstream chain is not confirmed in the code I reviewed and should be traced further (e.g., in deploy/release-note generation tasks) before treating the RCE escalation as proven.

### Likelihood Explanation
Feasibility depends entirely on Shipit's deployment configuration: the "no-secret org" bypass requires at least one org entry in `secrets.github` lacking `webhook_secret` (documented as optional, so plausible in real deployments), and even without that, an attacker who legitimately controls a GitHub org/App that Shipit is configured to trust (and therefore knows that org's `webhook_secret`) can still forge `repository.full_name` for a different, unrelated org's repo. No Shipit session, API token, or GitHub App private key is needed in the no-secret-org case. This is repeatable against any tracked repository in the installation, for every `pull_request` webhook handler that resolves its target via `full_name` (`EditedHandler`, `ClosedHandler`, `OpenedHandler`, `LabeledHandler`, `ReopenedHandler`, etc.), not just `EditedHandler`.

### Recommendation
Bind signature verification to the same identity used for record resolution: require that `repository.owner.login` (or `organization.login`) used to select the webhook secret matches the owner segment of `repository.full_name` before dispatching to any handler, and reject (422) on mismatch. Additionally, treat a missing `webhook_secret` as a misconfiguration to warn/alert on rather than a silent bypass, or require `webhook_secret` to be mandatory for all configured orgs.

### Proof of Concept
Add to `test/controllers/webhooks_controller_test.rb`:
```ruby
test "cross-org pull_request edited payload mutates unrelated repository's PullRequest" do
  # Arrange: victim stack/PR belongs to org "shopify" (has a configured webhook_secret)
  victim_repo = shipit_repositories(:shipit) # owner: "shopify"
  victim_stack = @stack
  pr = victim_stack.pull_requests.create!(number: 42, github_pull_request: { "title" => "original" })

  # Attacker forges payload naming an org with NO webhook_secret configured
  # (e.g. add such an org fixture to test/dummy/config/secrets.test.json)
  payload = {
    action: "edited",
    number: 42,
    pull_request: {
      id: 1, number: 42, url: "http://x", title: "INJECTED $(rm -rf /)",
      state: "open", additions: 0, deletions: 0,
      head: { sha: "a" * 40, ref: "feature" },
      user: { login: "attacker" }, assignees: [], labels: []
    },
    repository: { full_name: victim_repo.full_name, owner: { login: "no-secret-org" } },
    sender: { login: "attacker" }
  }.to_json

  request.headers['X-Github-Event'] = 'pull_request'
  request.headers['X-Hub-Signature'] = 'sha1=deadbeef' # arbitrary/invalid signature

  post :create, body: payload, as: :json

  assert_response :ok
  assert_equal "INJECTED $(rm -rf /)", pr.reload.github_pull_request["title"]
  # Equality check: verifying org ("no-secret-org") != owning org of PullRequest mutated ("shopify")
  refute_equal "no-secret-org", victim_repo.owner
end
```
This demonstrates the broken binding: the org used for `verify_signature` (`no-secret-org`) differs from the org owning the `PullRequest` row that was actually mutated (`shopify`), and the mutation succeeds despite an invalid/arbitrary signature.

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
