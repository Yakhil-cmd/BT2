### Title
Webhook signature is verified against the payload's `repository.owner`/`organization` while the mutated repository/stack is resolved from `repository.full_name`, allowing cross-organization webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to use for HMAC verification based on `repository.owner.login` (or `organization.login`) taken from the untrusted, attacker-supplied JSON body. All webhook handlers, however, resolve the actual `Repository`/`Stack` to act on from a *different* field of the same body: `repository.full_name`. Nothing ties these two fields together, so a signature that is valid for organization A can be attached to a payload whose `repository.full_name` names a repository belonging to organization B, and the event handlers will happily act on organization B's stack.

### Finding Description
`verify_signature` computes the signing organization purely from payload content: [1](#0-0) [2](#0-1) 

```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

It uses this value to pick the `GitHubApp` (and its `webhook_secret`) with `Shipit.github(organization: repository_owner)`, then verifies the HMAC over the raw body with that app's secret.

Every webhook `Handler`, however, determines the repository/stack to operate on from a *different* JSON key that is never cross-checked against `repository_owner`: [3](#0-2) 

```
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`Repository.from_github_repo_name` splits `full_name` on `/` and looks the repo up purely by that string, independent of `repository.owner.login`: [4](#0-3) 

Shipit natively supports multiple GitHub organizations each with their own App ID/`webhook_secret`, as documented and shown in the multi-org secrets template (`somegithuborg`, `someothergithuborg`), each entry carrying an independent `webhook_secret`: [5](#0-4) 

**Binding that should hold:** `signing_org(payload) == owner(repository.full_name)` — i.e., the organization whose secret validated the HMAC must be the same organization whose repository is mutated.

**Binding that is actually enforced:** `signing_org(payload) == repository.owner.login` (verification side) while `target_repo = repository.full_name` (mutation side), with no equality check between the two. An attacker who legitimately administers one GitHub App/organization onboarded to this Shipit instance (`attacker-org`, with its own known `webhook_secret`) can craft a payload with:
- `repository.owner.login = "attacker-org"` (so `verify_signature` selects `attacker-org`'s secret, which the attacker can correctly sign),
- `repository.full_name = "victim-org/victim-repo"` (so the handler resolves and mutates `victim-org`'s stack).

Since the HMAC covers the full raw JSON body, the attacker still produces a technically-valid signature (using their own known secret) over a body that references a completely different organization's repository.

### Impact Explanation
This breaks the trust boundary between "organization authenticated" and "repository being written," which the task rules identify as a critical binding. Concretely, once the mismatched payload passes verification:
- A forged `push` event lets the attacker enqueue `GithubSyncJob` for a victim stack with an attacker-chosen `expected_head_sha`, and forged `status`/`check_suite` events let the attacker write `Status`/`CheckRun` records against a victim repository's commits. Because Shipit's deploy-readiness/continuous-deployment gating reads these locally-stored statuses (not live GitHub state) before allowing a deploy, an attacker who administers an unrelated onboarded organization can inject a fabricated "success" status on a victim commit and enable an otherwise-blocked deploy — an unauthorized deploy triggered via cross-repository writes, matching the report's "value only correctly set after a later, uncorrelated event" bug class, transplanted onto Shipit's organization-vs-repository trust binding.
- This requires no possession of the victim organization's webhook secret, `GITHUB_TOKEN`, or any privileged Shipit account — only administration of some other organization already onboarded to the same multi-tenant Shipit instance, which is an explicitly supported and documented configuration.

### Likelihood Explanation
Any Shipit deployment serving more than one GitHub organization (a first-class, documented configuration in `docs/setup.md` and `config/secrets.development.shopify.yml`) is exposed. An attacker only needs administrative control of their own onboarded organization's GitHub App (to know its `webhook_secret`) and the ability to send an HTTP POST to the public `/webhooks` endpoint with a crafted body/signature — no GitHub push is even required, since the webhook body is fully attacker-authored.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler#repository_name`), assert that the organization whose secret validated the signature matches the owner encoded in `repository.full_name` before dispatching to handlers, e.g.:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  # ...
  full_name_owner = params.dig('repository', 'full_name')&.split('/')&.first
  head(422) and return if full_name_owner && full_name_owner.casecmp(repository_owner).nonzero?
  # ... existing verification
end
```
Alternatively, derive `repository_owner` exclusively from `repository.full_name` so the same field is used both to select the verifying secret and to resolve the mutated repository, eliminating the two-field split entirely.

### Proof of Concept
1. Onboard/administer `attacker-org` on the shared Shipit instance (multi-org config, e.g. per `config/secrets.development.shopify.yml`), obtaining its `webhook_secret`.
2. Craft a `push` event JSON body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "after": "<attacker-controlled-sha>",
  "ref": "refs/heads/master"
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org webhook_secret, raw_body)>` and POST to `/webhooks` with header `X-Github-Event: push`.
4. `WebhooksController#verify_signature` resolves `repository_owner` → `"attacker-org"`, fetches `attacker-org`'s app, and the signature verifies successfully.
5. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, which (via `Handler#repository_name`) resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and enqueues `GithubSyncJob` for `victim-org`'s stack with the attacker-supplied `after` sha — despite the signature never having been validated against `victim-org`'s webhook secret.
