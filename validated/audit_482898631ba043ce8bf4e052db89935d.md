### Title
Cross-organization webhook forgery via mismatched authentication/action fields in `WebhooksController` - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` authenticates an inbound webhook against the GitHub App config of whichever organization is named in `repository.owner.login` (or `organization.login`), but every event `Handler` then acts on `repository.full_name`, a separate, independently-attacker-controlled field in the same JSON body. Because Shipit supports multiple GitHub App/organization configurations (`Shipit.github(organization:)` / `github_app_config`), the identity used to validate the HMAC signature is not the same identity used to select the `Stack`/`Repository` the payload is applied to.

### Finding Description
The equality that should hold is: **organization whose webhook secret signed the request == organization that owns the repository being mutated**. This binding is broken:

- `verify_signature` computes the signing organization purely from the payload: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` and looks up that org's app/secret via `Shipit.github(organization: repository_owner)` [1](#0-0) , then compares `X-Hub-Signature` against that org's `webhook_secret` [2](#0-1) .
- Every `Handler` subclass, however, resolves the target repository from a different field: `payload.dig('repository', 'full_name')` [3](#0-2) , used e.g. by `PushHandler#process` to run `stack.sync_github` [4](#0-3)  or by `StatusHandler#process` to write `commit.create_status_from_github!` for any commit matching `sha` [5](#0-4) .
- Nowhere is it verified that `repository.owner.login` (the field used for authentication) is consistent with `repository.full_name` (the field used for action). Shipit explicitly supports multiple organizations sharing one deployment, each with its own `webhook_secret`, as shown by the multi-org fixture `secrets_double_github_app.yml` (`OrgOne`, `OrgTwo`) and `Shipit.github_app_config` [6](#0-5)  and `github_organizations` [7](#0-6) .

An attacker who administers *any* one of the configured organizations (e.g. `OrgTwo`, a legitimate but low-trust tenant onboarded onto the same Shipit instance) knows `OrgTwo`'s `webhook_secret` (it is a value they themselves configured when installing the app) and can freely POST directly to `/webhooks` (this endpoint is otherwise unauthenticated — no session, no `ApiClient` token required) with:
- `X-Hub-Signature` = HMAC-SHA1 computed with `OrgTwo`'s secret over the raw body,
- `repository.owner.login` = `"OrgTwo"` (so `verify_signature` succeeds using `OrgTwo`'s secret),
- `repository.full_name` = `"OrgOne/victim-repo"` (a repo belonging to an org the attacker has no access to).

`verify_signature` passes because the signature genuinely matches `OrgTwo`'s secret over the payload the attacker crafted, but the `Handler` then acts against `OrgOne/victim-repo`.

### Impact Explanation
This breaks the "organization authenticated versus the repository that is written" binding described as an in-scope class of finding. Concretely:
- Via the `status` event, `StatusHandler` writes a fabricated `CommitStatus` for any `Commit` whose `sha` is guessed/known to exist in `OrgOne`'s stacks [5](#0-4) , which can satisfy CI/merge-gating checks the merge queue relies on to authorize merges.
- Via the `push` event, `PushHandler` forces `GithubSyncJob` for `OrgOne`'s stacks, which can affect deploy-readiness state [4](#0-3) .
- Via `check_suite`/`pull_request` handlers similarly keyed off `repository.full_name`, the same cross-tenant write is possible, potentially culminating in an unauthorized deploy or merge for a repository/organization the attacker was never authorized to interact with.

This matches the "unauthorized deploy, rollback or merge" / "cross-repository writes" Critical impact bar.

### Likelihood Explanation
Requires: (1) the Shipit instance to be configured with more than one GitHub organization (a documented, supported configuration — see `secrets_double_github_app.yml`, `Shipit.github_organizations`), and (2) the attacker to control (or be an admin of) at least one of those onboarded organizations. Given that, no session, `ApiClient` token, or GitHub App private key access is required — only knowledge of one's own org's webhook secret and the ability to POST to the public `/webhooks` endpoint. This is a real, low-effort attack path in any multi-tenant Shipit deployment.

### Recommendation
In `Handler#repository_name` (and anywhere handlers key off `repository.full_name`), cross-check that the organization used to select/verify the webhook secret (`repository.owner.login` / `organization.login`) matches the owner segment of `repository.full_name`, rejecting the request (422) on mismatch. Alternatively, pass the authenticated organization from `WebhooksController#verify_signature` explicitly into each handler and have handlers scope their `Stack`/`Repository` lookups by that authenticated organization rather than trusting `full_name` verbatim.

### Proof of Concept
```
POST /webhooks HTTP/1.1
X-Github-Event: status
X-Hub-Signature: sha1=<HMAC-SHA1(OrgTwo_webhook_secret, body)>
Content-Type: application/json

{
  "sha": "<known sha of a commit in OrgOne/victim-repo>",
  "state": "success",
  "context": "ci/required-check",
  "repository": {
    "full_name": "OrgOne/victim-repo",
    "owner": { "login": "OrgTwo" }
  }
}
```
`verify_signature` resolves `repository_owner` = `"OrgTwo"`, fetches `Shipit.github(organization: "OrgTwo")`, and the signature validates because it was legitimately computed with `OrgTwo`'s own secret [1](#0-0) . `StatusHandler#process` then creates a `success` status on the targeted commit belonging to `OrgOne/victim-repo` [5](#0-4) , even though the attacker has no relationship with `OrgOne`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
