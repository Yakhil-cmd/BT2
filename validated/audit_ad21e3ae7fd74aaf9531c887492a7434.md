### Title
Unhandled TypeError from missing `assocStableUnits[trigger.unit]` cache entry crashes the full node when processing an AA trigger - (File: aa_composer.js)

### Summary
`handleTrigger()` in `aa_composer.js` dereferences `storage.assocStableUnits[trigger.unit].count_aa_responses` without checking whether the cache entry exists. If the trigger unit is not present in the `assocStableUnits` in-memory cache, this throws a synchronous `TypeError: Cannot read properties of undefined`, which is not caught anywhere in the async AA-processing chain and propagates to the process-wide `uncaughtException` handler, which explicitly re-throws to crash the process.

### Finding Description
In `handleTrigger`, the "second primary trigger from same unit" guard reads: [1](#0-0) 
```js
// skip this check for dry-run which uses genesis unit as trigger unit
if (trigger.unit !== constants.GENESIS_UNIT && !trigger_opts.bAir && storage.assocStableUnits[trigger.unit].count_aa_responses && mci >= constants.pemCurvesFixMci)
    return bounce('a second primary trigger from the same unit is not allowed');
```
This directly indexes `storage.assocStableUnits[trigger.unit]` and immediately accesses `.count_aa_responses` on the result, with no null/undefined guard. `assocStableUnits` is a bounded in-memory cache of stable unit properties that is actively evicted by `shrinkCache()` (`storage.js:2250-2295`) and reset via `resetStableUnits`/`resetMemory` (`storage.js:2510-2529`), and entries are only ever inserted for units with `sequence === 'good'` (`storage.js:1536-1537`, `2361-2373`). This mirrors the underlying bug class in CVE-2019-12436: a network-facing/attacker-influenced code path dereferences a data structure entry that can legitimately be absent (analogous to Samba's paged-search NULL pointer), producing an unhandled crash rather than a graceful error.

The path is reached for every primary AA trigger, i.e., whenever *any* unpriviledged unit poster sends a payment (with or without a `data` message) to an AA address and that unit later becomes stable; `handlePrimaryAATrigger` invokes `handleTrigger` for such triggers (`aa_composer.js:91-101`), and this specific line executes for every non-secondary, non-air-estimate, non-genesis trigger once `mci >= constants.pemCurvesFixMci`.

Any uncaught synchronous exception thrown deep in the async callback chain used by `handleTrigger`/`updateInitialAABalances` is not passed to a `.catch`/error callback — it propagates up the call stack until it reaches Node's `process.on('uncaughtException')` handler in `network.js`, which logs, dumps diagnostic data, and then explicitly re-throws to crash the process: [2](#0-1) 

### Impact Explanation
If `storage.assocStableUnits[trigger.unit]` is `undefined` at the moment this line executes (e.g., because the unit's cache entry was evicted by `shrinkCache()`, was never repopulated after a memory reset, or is a non-'good'-sequence unit that is intentionally never cached), the resulting `TypeError` is uncaught within the AA-trigger processing pipeline and crashes the full node process via the global `uncaughtException` handler. Because AA-trigger processing runs for every unit sent to an AA address network-wide, this is a network-reachable, unit-poster-triggerable full node crash — a Denial of Service that can be repeatedly re-triggered on restart, matching the "node unable to confirm new units" impact class.

### Likelihood Explanation
Exploitation requires only sending a normal payment (plus, optionally, a `data` message) to any AA address from an unprivileged wallet — the same action any legitimate user performs to interact with an AA. The attacker does not need special privileges; they only need the trigger unit to reach stabilization while its `assocStableUnits` cache entry is absent (e.g., timed around a `shrinkCache()` sweep, cache reset, or specific reindex/estimation flows). Confirming the precise timing window that reliably reproduces a missing cache entry requires deeper runtime tracing of `shrinkCache()`/`resetMemory()` interleaving with `handlePrimaryAATrigger`, which was not fully verifiable through static code review alone.

### Recommendation
Add a defensive existence check before dereferencing the cache entry, e.g.:
```js
const objTriggerUnitProps = storage.assocStableUnits[trigger.unit];
if (trigger.unit !== constants.GENESIS_UNIT && !trigger_opts.bAir && objTriggerUnitProps && objTriggerUnitProps.count_aa_responses && mci >= constants.pemCurvesFixMci)
    return bounce('a second primary trigger from the same unit is not allowed');
```
If the entry is genuinely expected to always exist at this point, fall back to a DB read (`storage.readUnitProps`) instead of assuming cache presence, and ensure any resulting error is fed into the `bounce()`/`onDone()` error path rather than being allowed to propagate as an uncaught exception.

### Proof of Concept
Static PoC (not runtime-verified due to tool limitations):
1. Deploy an AA on the network (any minimal AA definition with a `messages` block).
2. From an unprivileged wallet, send a payment (any amount sufficient to cover bounce fees) to the AA address, forming a primary trigger unit `U`.
3. Ensure, at the moment `U` stabilizes and `handlePrimaryAATrigger` runs `handleTrigger`, that `storage.assocStableUnits[U]` is not populated — this can occur after `shrinkCache()` (`storage.js:2250`, runs every 300s via `setInterval(shrinkCache, 300*1000)`) evicts old cache entries, or after a `resetMemory`/`resetStableUnits` cycle that has not yet been repopulated for `U`, or if `U`'s sequence is not `'good'` (never cached per `storage.js:1536`).
4. When `handleTrigger` reaches line 1861 in `aa_composer.js`, `storage.assocStableUnits[U]` evaluates to `undefined`, and `.count_aa_responses` throws `TypeError: Cannot read properties of undefined (reading 'count_aa_responses')`.
5. This exception is uncaught in the AA processing callback chain and is caught only by `process.on('uncaughtException')` in `network.js:4530`, which re-throws and crashes the full node (`network.js:4542`).
