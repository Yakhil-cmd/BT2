## Title
Webhook signature verification keys off `repository.owner.login`, but every event handler acts on the independent, unauthenticated `repository.full_name` field — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/org secret to validate an inbound webhook against using `repository_owner`, computed from `params.dig('repository','owner','login')` (falling back to `params.dig('organization','login')`). [1](#0-0) [2](#0-1) 

The signature check itself is a no-op whenever the selected org has no `webhook_secret` configured: [3](#0-2) 

Yet the field actually used by every `Webhooks::Handlers::*` class to decide *which repository/stack the event acts on* is the independent `repository.full_name` field, taken from the same raw, attacker-supplied JSON body: [4](#0-3) [5](#0-4) 

Nothing enforces that `repository.owner.login` (the field that picks the verification key) is actually the owner prefix of `repository.full_name` (the field that picks the target stack). This is the same bug class as the report: a value is used to select a "type"/authorization context (which org's secret governs the request) while a differently-typed/independently-controlled value (arbitrary repo full name) is what gets dereferenced and acted upon, with no check that the two agree.

### Finding Description
`before_action :verify_signature` runs before `create`, and picks the GitHub App config purely from `repository.owner.login`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [6](#0-5) 

`verify_webhook_signature` treats an org with no configured secret as automatically verified:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [3](#0-2) 

If the Shipit multi-tenant configuration includes *any* GitHub organization without a `webhook_secret` (a supported, documented configuration state — see the sample config where `webhook_secret:` is left blank/nil for multiple orgs), then any request claiming `repository.owner.login` equal to that org's name passes signature verification unconditionally, with no signature required at all: [7](#0-6) 

Once past `verify_signature`, `create` parses the full attacker body and dispatches it to handlers keyed only by `X-Github-Event`:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [8](#0-7) 

Every handler resolves its target `Repository`/`Stack` from `repository.full_name`, a completely separate field from the one used for verification:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

`PushHandler` uses this to enqueue a sync against arbitrary matching stacks using an attacker-supplied `after` SHA:
```ruby
def process
  stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [5](#0-4) 

An attacker with no Shipit credentials can therefore craft a payload where `repository.owner.login` = `"an-org-with-no-webhook-secret"` (bypassing the signature check entirely) while `repository.full_name` = `"victim-org/victim-repo"` (the actual real, protected repository tracked by Shipit). The `verify_signature` before_action authenticates against the wrong org/field, and the handler acts on a repository that was never part of that authentication decision — an equality (`repository.owner.login == repository.full_name`'s owner) that the code assumes but never checks.

This directly breaks the binding: *"an organization that authenticated versus the repository that is written."*

### Impact Explanation
By forging `push`, `status`, `check_suite`, `pull_request`, or `membership` webhooks against any Repository/Stack tracked by the Shipit instance (as long as one configured GitHub org lacks a webhook secret), an unprivileged, unauthenticated external attacker can:
- Force `GithubSyncJob`/`stack.sync_github` to run for arbitrary stacks with an attacker-chosen `expected_head_sha`, which on stacks with `continuous_deployment` enabled can drive an unauthorized deploy of a specific (attacker-chosen, pre-existing) commit.
- Forge `status`/`check_suite` events to fabricate passing CI status for a commit, which the merge queue (`MergeRequest#all_status_checks_passed?`) and deploy safety gates rely on, potentially enabling an unauthorized merge or deploy of a commit that never actually passed CI.
- Forge `membership` events to add/remove arbitrary GitHub users to/from `Shipit.github_teams`-backed teams, escalating into `Shipit.github_teams` authorization used by `User#authorized?`.

This satisfies the required High/Critical impact classes: escalation into `Shipit.github_teams` authorization, and a path toward an unauthorized deploy/merge via forged CI status and continuous deployment.

### Likelihood Explanation
The precondition — at least one configured GitHub organization without a `webhook_secret` — is an explicitly supported and documented configuration (the reference secrets file ships two orgs with `webhook_secret: # nil`), not a hypothetical misuse. Any Shipit deployment tracking multiple GitHub orgs where even one is left without a webhook secret (e.g., during setup, for an internal/test org, or an org where webhooks aren't otherwise sensitive) exposes every other org's repositories to forged events, because the verification-key selection and the acted-upon-repository selection are structurally decoupled fields in the same untrusted JSON body. No credentials, session, or GitHub access are required — only knowledge of a target repo's `full_name` and the name of any no-secret org configured in the instance.

### Recommendation
- Require `repository.owner.login` (or `organization.login`) to exactly match the owner segment of `repository.full_name` before selecting a verification key or resolving handlers acting on that repository.
- Treat a missing `webhook_secret` as "reject all webhooks for this org" (fail closed) rather than "skip verification," or require every configured org to have a non-blank secret at boot.
- After selecting `github_app`/org context for verification, thread that verified org identity into `Webhooks::Handlers::Handler` and have `stacks`/`repository_name` cross-check it against `repository.full_name`'s owner, rejecting mismatches.

### Proof of Concept
Preconditions: Shipit instance configured with orgs `no-secret-org` (no `webhook_secret`) and `victim-org` (has `webhook_secret`), and a Stack tracking `victim-org/victim-repo` with `continuous_deployment: true`.

```
POST /github/webhooks
X-Github-Event: push
X-Hub-Signature: sha1=anything-or-omitted
Content-Type: application/json

{
  "ref": "refs/heads/main",
  "after": "<some real, pre-existing commit sha in victim-org/victim-repo>",
  "repository": {
    "owner": { "login": "no-secret-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
- `repository_owner` resolves to `"no-secret-org"` → `Shipit.github(organization: "no-secret-org")` → `verify_webhook_signature` returns `true` unconditionally (`webhook_secret` blank) — no valid signature required. [1](#0-0) [3](#0-2) 
- `PushHandler` then resolves the target stack from `repository.full_name = "victim-org/victim-repo"` and enqueues `sync_github(expected_head_sha: ...)` for it, entirely independent of the org used above for "authentication." [4](#0-3) [5](#0-4) 

I could not fully trace whether `sync_github` on a `continuous_deployment`-enabled stack always results in an immediate, fully-automatic deploy without further gating (e.g. CI-status requirements) in this codebase snapshot — I was unable to load `app/jobs/shipit/continuous_delivery_job.rb` and `Stack#sync_github`/`allows_merges?` bodies within the available tool budget, so the "unauthorized deploy" portion of impact should be verified by a follow-up session with full file access before treating it as fully proven; the authentication-bypass-to-arbitrary-repository binding itself, however, is confirmed directly from the cited code.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
