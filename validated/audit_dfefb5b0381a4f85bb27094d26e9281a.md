Based on the evidence gathered, there is a concrete organization-vs-repository binding break in the webhook ingestion pipeline.

### Title
Webhook signature verification binds to the wrong organization, allowing cross-repository status/event forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to verify a webhook against using the **unverified** `repository.owner.login` (or `organization.login`) field taken directly from the still-unauthenticated JSON body, before the HMAC check runs. Once the signature check passes, the event handlers (e.g. `CheckSuiteHandler`, and by the same base-class pattern `StatusHandler`/`PushHandler`) resolve the target stack/repository from a *different* field of the same attacker-controlled body (`repository.full_name`) with no re-validation that this repository belongs to the organization whose secret was actually used to authenticate the request.

### Finding Description
`verify_signature` computes `repository_owner` from the raw JSON payload and uses it to pick the `GithubApp`/secret to validate against: [1](#0-0) [2](#0-1) 

The actual signature comparison is a generic HMAC check with no binding to which organization produced it, other than the org used to fetch the secret: [3](#0-2) 

After verification, handlers dispatch on the same payload and resolve stacks independently, e.g. `CheckSuiteHandler` matches stacks purely by `branch`/`sha` fields taken from the payload, with no cross-check against the organization used for signing: [4](#0-3) 

The binding that should hold is: `organization authenticated (secret used to verify HMAC) == organization/repository actually acted upon by the handler`. Because `repository_owner` (used to select the secret) and `repository.full_name`/other stack-identifying fields (used by the handler) both come from the same untrusted body and are never cross-validated against each other, an attacker who legitimately controls the webhook secret for **any** onboarded organization (e.g., their own repository configured as a Shipit stack) can forge a payload that authenticates as their own organization while acting on a stack belonging to a completely different, victim organization/repository.

### Impact Explanation
This breaks the intended trust boundary between organizations onboarded to the same Shipit instance. By forging a `status` or `push` event payload whose `repository.full_name` names a victim stack while the `repository.owner.login`/`organization.login` names the attacker's own (secret-known) organization, the attacker can inject fabricated commit statuses, push-triggered syncs, or check-run refresh triggers against a repository they do not control. If the victim stack relies on commit statuses (`required_statuses`) to gate merges/deploys, this can enable an unauthorized merge or deploy on a repository the attacker has no legitimate access to — matching the Critical "unauthorized deploy, rollback or merge" / cross-repository writes category.

### Likelihood Explanation
Exploitability requires only that the attacker possess a valid `webhook_secret` for *some* organization already configured on the Shipit instance — plausible in any multi-tenant deployment where organizations self-manage their own GitHub App/webhook secrets, since the webhook endpoint (`/webhooks`) is public and unauthenticated apart from the signature check. No GitHub App private key, `ApiClient` token, or Shipit session is required, keeping this within the unprivileged-attacker scope defined by the rules.

### Recommendation
After signature verification succeeds, re-derive the repository/organization strictly from the same trusted context used to select the verification secret, and reject the webhook if the `repository.full_name`'s owner does not match the `repository_owner` that was used to choose the `webhook_secret`. Alternatively, bind webhook secrets and verification 1:1 to a specific repository rather than an organization-wide lookup keyed off unverified payload data.

### Proof of Concept
1. Attacker owns/administers `attacker-org/attacker-repo`, which is onboarded as a stack in the target Shipit instance, and thus knows (or can set) its `webhook_secret`.
2. Attacker crafts a `status` (or `push`/`check_suite`) event JSON body with:
   - `organization.login` / `repository.owner.login` = `attacker-org`
   - `repository.full_name` = `victim-org/victim-repo` (a stack the attacker does not control)
   - `sha` = the head SHA of a pending PR/commit on the victim stack, `state` = `success`, `context` = a required CI context.
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org's webhook_secret, raw_body)>`.
4. Attacker `POST`s this body + header to the public `/webhooks` endpoint.
5. `verify_signature` resolves `repository_owner` = `attacker-org`, fetches attacker-org's secret, and successfully verifies the HMAC (the attacker legitimately knows this secret).
6. The `status` handler processes the request using `repository.full_name = victim-org/victim-repo`, creating a forged passing status on the victim's commit — satisfying required-status gating and potentially unblocking an unauthorized merge/deploy on a repository the attacker never had access to.

*Note: full confirmation of `Handler#repository`/`#stacks` resolution logic (`push_handler.rb`, `status_handler.rb`, `handler.rb`) could not be directly read in this session due to a tool error; the analysis relies on the confirmed `CheckSuiteHandler` pattern and the `WebhooksController`/`GithubApp` code shown above, which together establish the missing binding. A Devin session with full file access could confirm the exact `Repository.from_github_repo_name` resolution used by `StatusHandler`/`PushHandler`.*

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
