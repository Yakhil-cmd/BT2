### Title
Unvalidated authentifier input causes uncaught exception in merkle proof deserialization - (File: merkle.js)

### Summary
The Wireshark CVE involves a dissector reading a length-prefixed field without validating that the declared/expected length matches the actual buffer, causing an over-read and crash. The closest reachable analog in ocore is `deserializeMerkleProof` in [1](#0-0) , which blindly `.split("-")`s and indexes into the attacker-supplied `serialized_proof` string without validating its structure, used in the `"in merkle"` authentifier evaluation path in [2](#0-1) .

### Finding Description
`deserializeMerkleProof` assumes `serialized_proof` is a string with a specific `index-siblings...-root` shape and calls `.split("-")`, `.pop()`, `.shift()` on it directly [1](#0-0) . This is invoked from the `"in merkle"` authentifier definition type, where `serialized_proof = assocAuthentifiers[path]` is taken directly from the unit's `author.authentifiers` map — data fully controlled by the unit poster [3](#0-2) . I was not able to confirm, within the available context, whether `validateAuthentifiers`/upstream unit validation in `validation.js` enforces that every authentifier value is a string before this function is called. If a non-string value (object, number, array, null) can reach this path, `serialized_proof.split` would throw a `TypeError`, an uncaught exception distinct from the `try/catch` in `verifyMerkleProof` (which only wraps the *verification* step, not deserialization) [4](#0-3) .

### Impact Explanation
If reachable with malformed/non-string authentifier data, an uncaught `TypeError` thrown during unit validation (a hot path executed by every full node processing every unit containing an address definition with an `"in merkle"` clause) could crash the validating node process, mirroring the wireshark bug's "crash on malformed field" pattern. This is a "network unable to confirm new units" — class impact if it propagates to consensus-critical validation code paths without being caught.

### Likelihood Explanation
Low-to-uncertain: I could not verify in this session whether the authentifier value type is already constrained to strings earlier in `validation.js`'s author/authentifier checks. If it is (which is common in defensively-coded validation layers), this path is not reachable and the finding does not hold.

### Recommendation
Confirm in `validation.js` (author/authentifier field validation) whether authentifier values are strictly type-checked as strings before evaluation. If not enforced, add explicit type/format validation for `serialized_proof` (must be string, must contain expected `index-root` or `index-siblings-root` structure) before calling `deserializeMerkleProof`, and wrap the deserialization call itself in a `try/catch` in `definition.js`'s `"in merkle"` case, treating parse failures as authentication failure (`cb2(false)`) rather than letting exceptions propagate.

function deserializeMerkleProof(serialized_proof){
	var arr = serialized_proof.split("-");
	var proof = {};
	proof.root = arr.pop();
	proof.index = arr.shift();
	proof.siblings = arr;
	return proof;
}

function verifyMerkleProof(element, proof){
	// Node-as-Leaf issue might matter in some cases
	try {
		var index = proof.index;
		var the_other_sibling = hash(element);
		for (var i = 0; i < proof.siblings.length; i++) {
			// this also works for duplicated trailing nodes
			if (index % 2 === 0)
				the_other_sibling = hash(the_other_sibling + proof.siblings[i]);
			else
				the_other_sibling = hash(proof.siblings[i] + the_other_sibling);
			index = Math.floor(index / 2);
		}
		return (the_other_sibling === proof.root);
	}
	catch (e){
		return false;
	}
