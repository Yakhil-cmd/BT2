## Title
Cross-organization webhook forgery via `repository.owner.login` vs `repository.full_name` mismatch in multi-app config - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and therefore the webhook secret) used to validate an incoming webhook based on `repository_owner`, a value read directly from the still-unverified JSON payload. The webhook handlers that actually act on the payload (e.g. `PushHandler`) look up the target `Repository`/`Stack` using a different field from the same payload, `repository.full_name`. When Shipit is configured with the documented multi-organization GitHub App schema, these two fields are never bound together by the signature, so an attacker can pick which organization's secret gets used to "authenticate" the request while the payload still targets a repository belonging to another organization.

### Finding Description
`verify_signature` computes the signing organization purely from payload content, before any cryptographic check: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization:)` resolves the app/secret map keyed by this attacker-supplied organization string, using case-insensitive lookup: [3](#0-2) 

The docs explicitly describe this multi-org schema (`docs/setup.md`, "Using Multiple Github Applications"), and `test/dummy/config/secrets_double_github_app.yml` shows it used with per-org `webhook_secret` values (any of which can be `nil`/unset).

Once verification passes (or is trivially satisfied because the chosen org's `webhook_secret` is blank — `verify_webhook_signature` returns `true` when `webhook_secret` is unset), the controller re-parses the same raw body and dispatches to handlers keyed only on the GitHub event type: [4](#0-3) 

Handlers such as `PushHandler` resolve the actual target `Stack`/`Repository` using a *different* field of the payload, `repository.full_name`, with no cross-check against `repository.owner.login`: [5](#0-4) [6](#0-5) 

This breaks the intended equality: `organization authenticated (repository.owner.login used to pick the secret)` == `repository whose stacks are actually written (repository.full_name used by the handler)`. In a deployment with multiple configured GitHub orgs, an attacker who knows (or is allowed to trigger via a legitimately-installed org they control, e.g. an org with `webhook_secret` left blank per the example config) can send a forged payload where `repository.owner.login` names an org whose secret is unset/known/guessable, while `repository.full_name` names a real tracked repository belonging to a different, protected organization. The signature check passes against the attacker-controlled org, but the handler acts on the victim repository's stacks, triggering `stack.sync_github` (and, depending on stack configuration/events, other handler-driven side effects) without ever validating a signature scoped to the victim org.

### Impact Explanation
This allows a party without any legitimate credential for the victim GitHub organization to make Shipit believe it received an authentic webhook for that organization's repository, causing `GithubSyncJob`-driven state changes (`sync_github`) and other event-handler behaviors to be triggered against real tracked `Stack`s. This is an authentication-boundary break: `Shipit.github(organization: repository_owner)` (deployment-trust binding: organization authenticated) is decoupled from `repository.full_name` (repository actually written to). Depending on which handlers are subscribed and what side effects they trigger for the targeted stack (sync, potentially downstream deploy-eligibility state), this can affect unauthorized state changes on a stack the attacker does not own.

### Likelihood Explanation
Requires the deployment to use the multi-organization GitHub App configuration (explicitly documented and supported) with at least one organization's `webhook_secret` unset, guessable, or otherwise available to the attacker, while a *different*, protected organization's repository is tracked as a `Stack`. This is a realistic operational configuration per `docs/setup.md`, but is conditional on that multi-org setup and on the attacker being able to determine/obtain a usable secret (or exploit a blank one) for some configured org.

### Recommendation
Bind the webhook signature verification to the same repository identity the handlers act upon: derive the verifying organization from `repository.full_name`'s owner segment consistently with `Handler#repository_name`, or independently verify that `repository.owner.login` matches the owner of `repository.full_name` before dispatching. Additionally, disallow (or warn strongly against) leaving `webhook_secret` blank for any configured organization in the multi-app schema, since `GitHubApp#verify_webhook_signature` treats a blank secret as automatically verified.

### Proof of Concept
1. Configure Shipit with two GitHub orgs per `docs/setup.md`: `victim-org` (tracked `Stack`, `webhook_secret` set) and `attacker-org` (`webhook_secret` left blank, as shown as a valid config in `config/secrets.development.example.yml`).
2. POST to `/github/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
No `X-Hub-Signature` needed since `attacker-org` has no `webhook_secret`, so `verify_webhook_signature` returns `true`.
3. `verify_signature` resolves `Shipit.github(organization: "attacker-org")`, passes verification trivially.
4. `create` re-parses the payload and dispatches to `PushHandler`, which looks up stacks via `repository.full_name == "victim-org/victim-repo"` and calls `stack.sync_github(...)` on the victim's real stack — despite the "authenticated" organization being `attacker-org`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
