### Title
Push webhook handler trusts `payload['repository']['full_name']` independently of the org verified for the signature, letting a payload signed for one org sync a Stack under a different Repository - (File: app/models/shipit/webhooks/handlers/push_handler.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret to validate the HMAC using `repository_owner`, which is read from `params.dig('repository','owner','login')`. Once the signature check passes, the same raw JSON body is handed to `PushHandler`, whose `stacks` lookup (inherited from `Handler#stacks`) uses `payload.dig('repository','full_name')` — a different field of the very same attacker-controlled JSON — to locate the `Repository`/`Stack` to mutate via `stack.sync_github(expected_head_sha:)`. Nothing ties `full_name` back to the org that was actually verified, so an attacker who owns (or targets an unconfigured) org can forge a body whose `owner.login` matches their own signing key while `full_name` names a victim repository/stack.

### Finding Description
The broken binding, stated as an equality that the code assumes but never enforces:

`repository_owner (params.dig('repository','owner','login'), used in WebhooksController#verify_signature)` == `org-part-of(payload.dig('repository','full_name'), used in Handler#repository_name / Handler#stacks)`

Trace:
- `app/controllers/shipit/webhooks_controller.rb:24-30` (`verify_signature`) computes `repository_owner` from the JSON body and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`. This selects which secret is used to validate the HMAC over `request.raw_post`. It does not look at `repository.full_name` at all. [1](#0-0) [2](#0-1) 
- Once signature verification passes, `create` dispatches the parsed body unchanged to every registered handler: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. [3](#0-2) 
- `Handler#stacks`/`Handler#repository_name` derive the target `Repository` purely from `payload.dig('repository', 'full_name')`, a field independent from `repository_owner`. [4](#0-3) 
- `PushHandler#process` scopes `stacks` by the attacker-supplied `branch` (derived from `params.ref`) and calls `stack.sync_github(expected_head_sha: params.after)` on every matching, non-archived stack of whatever `Repository` `full_name` resolved to. [5](#0-4) 
- `PushHandler`'s `ExplicitParameters` schema only requires `:ref` and `:after`; it places no constraint linking `repository.owner.login` to `repository.full_name`. [6](#0-5) 

Root cause: the signature-verification org (`repository_owner`) and the stack-resolution org embedded in `repository.full_name` are two independent reads of the same attacker-controlled JSON body. GitHub's real webhooks always keep these consistent, but this engine never asserts that consistency itself, and the raw body/signature pair is fully attacker-constructed (they compute the HMAC themselves using their own org's secret, or exploit an org with no secret configured), so there is no cryptographic tie between the two fields.

Exploit flow: attacker owns `attacker-org` (with a known secret, or an org configured with no secret at all). They craft a `push` event JSON body with:
- `repository.owner.login = "attacker-org"` (or omit and set `organization.login` accordingly) so `verify_signature` picks the key/secret they control (or no secret at all).
- `repository.full_name = "victim-org/victim-repo"` — the real full name of a `Repository` that hosts a target `Stack`.
- `ref = "refs/heads/<victim-stack-branch>"` matching the victim stack's branch.
- `after = "<attacker-chosen-sha>"`.

They sign the raw body with `attacker-org`'s secret (or send it unsigned if no secret is configured for that org) and POST to `/webhooks` with `X-Github-Event: push`. `verify_signature` succeeds because it only validates the HMAC against `attacker-org`'s key, not against `victim-org`. `PushHandler#process` then resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and invokes `sync_github(expected_head_sha: params.after)` on the victim's stack — a repository the attacker never authenticated for.

None of the existing guards stop this: `drop_unhandled_event` only checks the event type is registered; the `ExplicitParameters` schema for `PushHandler` only requires `ref`/`after` and never cross-checks repository identity; `verify_signature` checks the signature against the org derived from the same forged body, not against the `full_name` the handler will actually act on; `force_github_authentication`/`User#authorized?`/`require_permission!` are irrelevant to unauthenticated webhook ingestion; and `Repository`/`Stack` model validations do not constrain cross-field consistency between `owner.login` and `full_name` inside an inbound webhook payload.

### Impact Explanation
An attacker fully controlling a webhook payload for their own (or any unconfigured) GitHub org can force `PushHandler` to call `sync_github(expected_head_sha:)` on any `Stack` belonging to a completely different, victim `Repository`, i.e., a payload authenticated for one repository/org mutates another tenant's stack state. This is a cross-tenant authorization bypass: the `REPOSITORY_SCOPE` boundary that is supposed to keep one repo's webhooks confined to its own stacks is broken. Repeatable per request against any repository/stack whose branch name and full name the attacker can guess or discover (both are typically public information on GitHub). This matches the Critical category: "a payload for one repository mutating another's stack, commit, task or team."

### Likelihood Explanation
Preconditions: the attacker needs an org they control that either has a Shipit-configured webhook secret (which they know because it's their own org) or is an org for which Shipit has no secret configured at all (per the question's stated environment). They need to know/guess the victim's `full_name` and a branch name that has a Stack (both are ordinary public GitHub metadata, easily discoverable for public repos or a repo the attacker can view). No Shipit session, API token, or GitHub App private key is required — cost is a single crafted HTTP POST to `/webhooks`. This is straightforward and repeatable.

### Recommendation
In `Handler#stacks`/`Handler#repository_name` (or centrally in `WebhooksController`), require that the `Repository` resolved for handler processing matches the same organization/owner that was used to select and validate the webhook signature — e.g., compare `repository.full_name.split('/').first` (or `repository.owner.login`) against the verified `repository_owner` before proceeding, and reject/no-op the event if they diverge. Alternatively, bind webhook verification per-repository rather than per-organization so the signing secret itself is scoped to the exact repository being mutated.

### Proof of Concept
Minitest plan (no live GitHub, mocking at controller/handler boundary as the question specifies):

```ruby
test "PushHandler syncs a victim stack when payload owner differs from repository full_name org" do
  victim_repository = shipit_repositories(:shipit) # full_name e.g. "victim-org/victim-repo"
  victim_stack = shipit_stacks(:shipit) # branch matches ref below, belongs to victim_repository

  forged_payload = {
    'repository' => {
      'owner' => { 'login' => 'attacker-org' },
      'full_name' => victim_repository.full_name,
    },
    'ref' => "refs/heads/#{victim_stack.branch}",
    'after' => 'deadbeef' * 5,
  }

  # Equality under test (should hold for a correctly-scoped implementation, but does not):
  assert_equal(
    'attacker-org',
    forged_payload.dig('repository', 'owner', 'login')
  )
  refute_equal(
    forged_payload.dig('repository', 'owner', 'login'),
    forged_payload.dig('repository', 'full_name').split('/').first
  )

  Shipit::Stack.any_instance.expects(:sync_github).with(expected_head_sha: forged_payload['after'])

  Shipit::Webhooks::Handlers::PushHandler.call(forged_payload)
end
```

This demonstrates that `PushHandler.call` invokes `sync_github` on `victim_stack` purely based on `repository.full_name`, regardless of the mismatched `repository.owner.login` that the controller would have used for signature verification — proving the `REPOSITORY_SCOPE` divergence.
