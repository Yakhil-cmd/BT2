### Title
Unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` lets a status webhook from one repository write a `Status` (and trigger merge/deploy scheduling) onto commits belonging to any other stack that happens to share the same SHA - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves the target commit(s) purely by `sha`, with no filter on `repository`/`stack`, so a legitimately-signed `status` webhook from repository A can create a `Status` on a `Commit` row belonging to a completely different stack/repository B whenever the two share a commit SHA (forks, mirrors, monorepo splits, shared upstream history). `Commit#add_status` then schedules merges/continuous delivery based on that status, so a `success` on `ci/coverage`/any required context can flip deployability for the victim stack. The `review_stacks_enabled`/`provision?` precedence bug in `OpenedHandler`/`LabeledHandler`/`ReopenedHandler` is a separate, unrelated code path that is never invoked from `StatusHandler#process`, so it does not participate in this chain; `review_stacks_enabled` has no bearing on status processing.

### Finding Description
The invariant claimed by the question is: `status.stack_id == webhook.authenticated_repository.stack_id` for every `Status` created from a `status` webhook. Tracing the code shows this does not hold.

`Shipit::WebhooksController#verify_signature` authenticates the webhook only against the GitHub organization derived from `params.dig('repository','owner','login')` [1](#0-0) [2](#0-1) . It never validates that the `sha` in the body belongs to that same `repository`. `StatusHandler#process` then does:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 

`Commit.where(sha:)` is a global, cross-stack query with no `stack_id`/`repository` scoping, so any `Commit` row anywhere in the database with that SHA receives the status, regardless of which repository's webhook secret produced the request. `commit.create_status_from_github!` calls `statuses.replicate_from_github!(stack_id, github_status)` [4](#0-3) , which is likewise unscoped by repository - only by `stack_id`, the stack of whichever `Commit` matched. `Commit#add_status` compares previous/new `Status::Group` state and, on a state change to `success`, calls `stack.schedule_merges` [5](#0-4) , and `Commit#schedule_continuous_delivery` fires `ContinuousDeliveryJob` when the commit becomes `deployable?` [6](#0-5) . `deployable?` is driven by `success? && !blocked?` off the aggregated `status` [7](#0-6) .

The exploit precondition is that a `Commit` row with the same SHA exists in a different stack than the one that authenticated the webhook - e.g. a fork's shared pre-fork commits, mirrored repositories, or any case where two `Stack`s/`Repository`s in the same Shipit instance track overlapping git history. An attacker who owns/controls a repository onboarded to the same Shipit instance can cause GitHub to emit a real, correctly-signed `status` event (e.g., via the Statuses API against a SHA reachable in their own repo that is also present in the victim's commit history) with `context: ci/coverage`, `state: success`. `verify_signature` passes because the signature is valid for the attacker's own organization/repo; `StatusHandler#process` then writes the status onto the victim's `Commit`, mutating a stack that never authenticated the payload.

The `review_stacks_enabled`/`provision?` precedence bug that the question references (`repository.review_stacks_enabled && repository.provisioning_behavior_allow_all? || (allow_with_label && label) || (prevent_with_label && !label)`) does exist in `OpenedHandler#provision?`, `ReopenedHandler#unarchive?`, and `LabeledHandler#archive?/unarchive?` [8](#0-7) [9](#0-8) , but it is only reachable from `pull_request` webhook events, never from `StatusHandler#process`. It has no causal role in the cross-stack status-write chain described above, and `review_stacks_enabled` has no effect on whether a status write or `schedule_merges`/`ContinuousDeliveryJob` fires.

### Impact Explanation
An attacker's webhook, authenticated only for their own repository, can force a `Status` (and downstream merge/deploy scheduling) onto a `Commit` belonging to an unrelated stack/repository whenever a SHA collision exists between the two - "a payload for one repository mutating another's stack," matching the Critical impact category. Because `schedule_continuous_delivery` and `stack.schedule_merges` are triggered off the resulting aggregated state, a spoofed `success` can push a victim stack's commit into `deployable?` state, potentially triggering an unauthorized deploy/merge sequence on the victim's stack. The blast radius is limited to stacks/repositories that share commit SHAs with an attacker-controlled repository (forks, mirrors, monorepo splits) - it is not a general "any repo can hit any repo" primitive, since SHA collision across unrelated content is not feasible.

### Likelihood Explanation
Requires: (1) attacker has write access sufficient to trigger a signed `status` webhook for a repository already onboarded to the target Shipit instance (their own repo/fork under an org with the GitHub App/webhook installed), and (2) a `Commit` row with the identical SHA already exists in the victim's stack (realistic for forks/mirrors/monorepo splits sharing history, not realistic for arbitrary unrelated repositories). Given precondition (2), the attack is cheap and repeatable for every shared SHA. The `review_stacks_enabled` framing in the question is not a precondition for this bug - the exploit works identically regardless of that flag.

### Recommendation
Scope `StatusHandler#process` (and `Commit.by_sha`/`by_sha!` call sites used from webhook handlers) to the `Stack`/`Repository` identified by the webhook payload's `repository.full_name`, e.g. `Commit.where(sha: params.sha, stack_id: repository.stacks.select(:id))`, so a status can only be applied to commits belonging to the repository that authenticated the webhook. Apply the same repository-scoping to `Status.replicate_from_github!` and `CheckRun` equivalents if they have the same unscoped lookup pattern. Separately (unrelated to this finding), fix the `&&`/`||` operator precedence in `provision?`/`unarchive?`/`archive?` by parenthesizing `review_stacks_enabled && (...)` around all three provisioning-behavior branches.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status webhook only affects commits belonging to the authenticating repository" do
  victim_stack = shipit_stacks(:shipit) # repository X
  attacker_stack = shipit_stacks(:cyclimse) # repository Y, unrelated
  shared_sha = "deadbeef" * 5 # 40 hex chars

  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: "shared history", author: shipit_users(:shipit), committer: shipit_users(:shipit), authored_at: Time.now, committed_at: Time.now)
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, message: "shared history", author: shipit_users(:shipit), committer: shipit_users(:shipit), authored_at: Time.now, committed_at: Time.now)

  # Binding under test: a status authenticated for attacker_stack's repository
  # must not create a Status on victim_commit.
  assert_equal victim_stack.id, victim_commit.stack_id
  assert_equal attacker_stack.id, attacker_commit.stack_id

  params = Shipit::Webhooks::Handlers::StatusHandler.new(
    OpenStruct.new(sha: shared_sha, state: "success", context: "ci/coverage")
  )
  # simulate authenticated attacker repo webhook
  Shipit::Webhooks::Handlers::StatusHandler.new(params.instance_variable_get(:@params)).process

  victim_commit.reload
  # FAILS today: victim_commit gains a Status even though the webhook only
  # authenticated attacker_stack's repository.
  assert_empty victim_commit.statuses.where(context: "ci/coverage"),
    "victim commit's status should not change from a webhook authenticated for a different repository"
end
```

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
