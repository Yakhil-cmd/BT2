### Title
`Api::CCMenuController#show` leaks any stack's deploy/commit metadata regardless of the authenticated token's `stack_id` scope - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Api::CCMenuController` overrides the `stack` accessor to use `Stack.from_param!(params[:stack_id])` directly instead of the base controller's scoped `stacks.from_param!(params[:stack_id])`, which is the mechanism that restricts lookups to `current_api_client.stack_id` when the token is scoped. As a result, a token scoped to one (e.g. public) stack can request `cc.xml` for any other stack, including private ones, and receive that stack's build status, last deploy id, and timing data.

### Finding Description
Binding claimed: stack whose deploy data is rendered == a stack ∈ `current_api_client.stack_id`'s authorized set.

In `Shipit::Api::BaseController`, the scoping is implemented as: [1](#0-0) 
`stacks` filters to `Stack.where(id: current_api_client.stack_id)` only when `current_api_client.stack_id?` is true, and `stack` resolves via `stacks.from_param!`. This is the intended enforcement point for scoped tokens (tokens created with a specific `stack_id`, e.g. via `CCMenuUrlController#client`, which creates a read-only `ApiClient` — see `app/controllers/shipit/ccmenu_url_controller.rb:15-18`).

However, `Api::CCMenuController` redefines `stack` and bypasses this scoping entirely: [2](#0-1) 
`stack` calls `Stack.from_param!(params[:stack_id])` directly on the `Stack` class, not through the `stacks` scope. `require_permission :read, :stack` only checks `current_api_client.check_permissions!('read', 'stack')` (`app/models/shipit/api_client.rb:38-45`), which validates the permission list (`read:stack`), not which stack IDs the token is bound to. `authenticate_api_client` is also overridden to accept `params[:token]` (query-string auth) in addition to falling back to Basic Auth via `super`, but this only affects *how* the token is verified, not scope enforcement.

Attacker flow: obtain (or already legitimately hold, per the question's framing) an `ApiClient` token issued/scoped for public Stack A (`stack_id == A.id`). Send `GET /stacks/<owner>/<repo-B>/<env-B>/ccmenu?token=<tokenA>` where B is a private/internal stack. `authenticate_api_client` verifies the token successfully via `ApiClient.authenticate`. `require_permission!(:read, :stack)` passes because the token has `read:stack` in its permission list (independent of which stack it's bound to). `stack` resolves `Stack.from_param!(params[:stack_id])` against the **unscoped** `Stack` relation, returning stack B regardless of `current_api_client.stack_id`. `show` then renders `stack.deploys_and_rollbacks.last` into `shipit/ccmenu/project.xml.builder`, exposing `lastBuildStatus`, `lastBuildLabel` (deploy id), `lastBuildTime`, `activity`, and `webUrl` for stack B.

None of the listed guards prevent this: `require_permission!` checks operation+scope name only, not the stack instance; the `stacks` scope method exists but is never invoked by this controller since `stack` is overridden; there is no `ExplicitParameters` schema or model validation tying the request's `stack_id` param to `current_api_client.stack_id`.

### Impact Explanation
A holder of any valid `read:stack`-scoped `ApiClient` token — even one deliberately restricted to a single low-sensitivity stack — can enumerate and read build/deploy status metadata (last deploy id, build time, activity, lock/failure status, and the `webUrl` pointing to the private stack's page) for **any** stack in the Shipit instance by simply changing the `stack_id` in the URL. This is repeatable against arbitrary stacks without rate limiting, matching "unauthenticated read of stack state" for a stack the presented credential is not authorized for (the credential is valid for authentication, but not for that resource) — High severity per the given impact categories (escalation beyond the token's intended scope, unauthorized read of stack state).

### Likelihood Explanation
Preconditions: the attacker must possess a valid `ApiClient` token with `read:stack` permission (e.g., one legitimately issued to them for a public/low-sensitivity stack via the CCMenu UI feature, `CCMenuUrlController`). No GitHub secrets, session, or admin role is needed. The exploit is a single unauthenticated-w.r.t.-target-stack HTTP GET with a known/guessable stack path segment (`owner/repo/environment`), which is low-cost and fully repeatable.

### Recommendation
In `app/controllers/shipit/api/ccmenu_controller.rb`, remove the overridden `stack` method (or reimplement it using the inherited scoped lookup) so that it resolves via `stacks.from_param!(params[:stack_id])` instead of `Stack.from_param!(params[:stack_id])`, restoring enforcement of `current_api_client.stack_id`.

### Proof of Concept
Minitest plan (in `test/controllers/api/ccmenu_controller_test.rb` style):
```ruby
test "a token scoped to a public stack cannot read another stack's ccmenu data" do
  public_stack = shipit_stacks(:shipit) # stack A
  private_stack = Stack.create!(repository: Repository.new(owner: "acme", name: "private-repo"), branch: "main", environment: "production")
  Deploy.create!(stack: private_stack, until_commit: private_stack.commits.create!(sha: "a" * 40), since_commit: private_stack.commits.create!(sha: "b" * 40), status: "success")

  scoped_client = ApiClient.create!(creator: @user, name: "scoped", permissions: %w[read:stack], stack: public_stack)

  get :show, params: { stack_id: private_stack.to_param, token: scoped_client.authentication_token }

  assert_response :ok
  project = Hash.from_xml(response.body)['Projects']['Project']
  # Binding check: stack whose data is rendered (private_stack) must NOT be in scoped_client's authorized set ({public_stack.id})
  refute_equal scoped_client.stack_id, private_stack.id
  assert_equal private_stack.to_param, project['name'] # leak confirmed: private stack data served
end
```
This demonstrates that despite `scoped_client.stack_id == public_stack.id` (the authorized set is `{public_stack.id}`), the response body contains `private_stack`'s name/build data, proving the binding is violated.
