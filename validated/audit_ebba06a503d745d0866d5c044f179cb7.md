### Title
`TaskCommands#env` merges attacker-controlled `@task.env` after computed audit fields, allowing `deploy.variables` in `shipit.yml` to spoof `SHIPIT_USER`/`GIT_COMMITTER_*` - ([File: lib/shipit/task_commands.rb])

### Summary
`Shipit::TaskCommands#env` computes `SHIPIT_USER`, `GIT_COMMITTER_NAME`, `GIT_COMMITTER_EMAIL`, `TASK_ID`, `EMAIL` and `SHIPIT_LINK` from the task/author, but then merges `@task.env` on top of them without excluding these reserved keys. Because `@task.env` is populated from `Stack#build_deploy`'s `filter_deploy_envs(env.to_h)`, which only checks that a key's *name* is declared in the repo's own `shipit.yml` `deploy.variables` (`Shipit::EnvironmentVariables#permit`), a repository (or fork) that declares a `deploy.variables` entry literally named `SHIPIT_USER` (or `GIT_COMMITTER_NAME`/`GIT_COMMITTER_EMAIL`/`TASK_ID`) can have that value silently overwrite the computed audit identity for every deploy that uses the variable's default (or an explicitly supplied value).

### Finding Description
The binding that should hold is:
`TaskCommands#env['SHIPIT_USER'] == "#{@task.author.login} (#{normalized_author_name}) via Shipit"` for every task, regardless of `@task.env`.

Code path:
- `Shipit::DeploySpec#deploy_variables` / `#default_deploy_env` build `{name => default}` straight from the repo-controlled `shipit.yml`: [1](#0-0) 
- `Shipit::EnvironmentVariables#permit` only whitelists by *name*, not by "is this a reserved/internal key": [2](#0-1) 
- `Shipit::DeploySpec#filter_deploy_envs` wires that whitelist into deploy creation: [3](#0-2) 
- `Shipit::Stack#build_deploy` stores the filtered env on the `Deploy`/`Task` record as-is: [4](#0-3) 
- `Shipit::TaskCommands#env` computes the audit fields, then merges `deploy_spec.machine_env` and finally `@task.env` **last**, so any attacker-declared variable with a colliding name wins: [5](#0-4) 

Root cause: the merge order in `TaskCommands#env` treats `@task.env` (whose *keyspace* is entirely defined by the target repository's own `shipit.yml`) as higher priority than Shipit's own computed audit identity, and `EnvironmentVariables#permit` has no concept of reserved/internal names to reject.

Reachable triggers that populate `@task.env` with a default (no explicit override needed):
- `Stack#trigger_continuous_delivery` uses `cached_deploy_spec.default_deploy_env` directly when `continuous_deployment` is enabled for the stack: [6](#0-5) 
- `Stack.run_deploy_in_foreground` (CLI) also uses `default_deploy_env`: [7](#0-6) 
- The deploy `:new` UI form pre-selects the declared default value for each `deploy.variables` entry (`test/controllers/deploys_controller_test.rb:49-57`), so an operator submitting the form "as-is" also carries the attacker's default through unchanged.

For review stacks, the `shipit.yml` that supplies `deploy.variables` is read from the attacker's own fork/PR branch (the review stack deploys the PR head), so the attacker fully controls the variable name/default with no repository-maintainer involvement in choosing that name.

Existing guards do not prevent this: `EnvironmentVariables#permit` only enforces whitelisting-by-declared-name (which the attacker controls), not reservation of internal keys; there is no code anywhere that strips `SHIPIT_USER`/`GIT_COMMITTER_*`/`TASK_ID` out of `@task.env` before the final merge in `TaskCommands#env`.

### Impact Explanation
Whichever value the attacker places under the colliding variable name becomes the value seen by `PTY.spawn` for `SHIPIT_USER`, `GIT_COMMITTER_NAME`, `GIT_COMMITTER_EMAIL`, `EMAIL`, `TASK_ID`, `SHIPIT_LINK`, or `IGNORED_SAFETIES` during that repository's own deploy/rollback steps. Because `GIT_COMMITTER_NAME`/`GIT_COMMITTER_EMAIL` are consumed by git operations that Shipit performs as part of deploy/rollback (`Commands#git`, `StackCommands`), and `SHIPIT_USER` is the value surfaced in task output/audit logs for "who ran this," this allows an attacker to forge the recorded actor identity for tasks run against their own stack/fork. This is scoped to the attacker's own repository/stack (the malicious `shipit.yml` only affects deploys of that repo/branch); it does not cross tenant boundaries and does not by itself achieve command injection, secret exfiltration, or authorization bypass into another repository's stack.

### Likelihood Explanation
- Preconditions: the target stack must run a task (deploy/rollback) using the attacker's `shipit.yml` with a `deploy.variables` entry whose `name` collides with one of `TaskCommands#env`'s computed keys, and that variable's value must reach `@task.env` — either via `default_deploy_env` (continuous delivery must be enabled on the stack, or the CLI `run_deploy_in_foreground` path is used) or via an operator submitting the deploy form with the pre-filled default.
- For a fully unauthenticated/unprivileged attacker (no Shipit session, not a maintainer), reaching this purely through PR/webhook actions (as literally described in the prompt: fork + label + no explicit override) requires `continuous_deployment` already being enabled on that specific review stack by a legitimate maintainer — a setting the attacker cannot set themselves. Absent that, the poisoned default is only exercised when an authenticated maintainer manually triggers a deploy and accepts the pre-filled default in the UI, which is a low-cost but real everyday workflow (test/controllers/deploys_controller_test.rb:49-57 shows defaults are pre-selected in the form).
- Cost to the attacker is low (a one-line `shipit.yml` change in their own fork) and the effect is repeatable on every subsequent deploy/rollback of that stack until the field is renamed or filtered.

### Recommendation
In `Shipit::TaskCommands#env`, reserve the internally-computed keys (`SHIPIT_USER`, `EMAIL`, `SHIPIT_LINK`, `TASK_ID`, `IGNORED_SAFETIES`, `GIT_COMMITTER_NAME`, `GIT_COMMITTER_EMAIL`) and strip them from `@task.env` (and from `deploy_spec.machine_env`) before merging, or reorder the merges so these computed values are applied last and cannot be overridden. Additionally, `Shipit::EnvironmentVariables#permit` (or `DeploySpec#deploy_variables`) should reject variable definitions whose `name` collides with this reserved keyset when parsing `shipit.yml`, so the misconfiguration is caught at spec-load time rather than at task-run time.

### Proof of Concept
Add a minitest to `test/lib/shipit/task_commands_test.rb` asserting the binding directly:

```ruby
test "#env computed audit keys cannot be overridden by @task.env" do
  stack = shipit_stacks(:review_stack)
  task = shipit_tasks(:shipit_restart)
  task.stack = stack
  task.env = {
    'SHIPIT_USER' => 'attacker (forged) via Shipit',
    'GIT_COMMITTER_NAME' => 'Forged Committer',
    'GIT_COMMITTER_EMAIL' => 'forged@evil.example',
    'TASK_ID' => '999999999'
  }

  env = Shipit::TaskCommands.new(task).env

  expected_user = "#{task.author.login} (#{ActiveSupport::Inflector.transliterate(task.author.name)}) via Shipit"
  assert_equal expected_user, env['SHIPIT_USER']
  assert_equal task.user&.name || Shipit.committer_name, env['GIT_COMMITTER_NAME']
  assert_equal task.user&.email || Shipit.committer_email, env['GIT_COMMITTER_EMAIL']
  assert_equal task.id.to_s, env['TASK_ID']
end
```

This test currently fails against `lib/shipit/task_commands.rb:33-48` because `.merge(@task.env)` is applied last, proving the audit fields can be overwritten by attacker-supplied `deploy.variables` values that flow into `@task.env` via `Stack#build_deploy` → `filter_deploy_envs`.
