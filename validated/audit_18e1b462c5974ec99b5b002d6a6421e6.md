### Title
Congestion-control receipt-buffer accounting can desynchronize `size` and `gas` counters, triggering a hard invariant-violation panic during chunk application - (File: `core/store/src/trie/outgoing_metadata.rs`)

### Summary
The `ReceiptGroupsQueue`/`ReceiptGroup` structures that back NEAR's congestion-control outgoing receipt buffer maintain two independently-updated aggregate counters per group — `size` (bytes) and `gas` — and assert that when `size` reaches `0` (i.e. the group is considered empty) `gas` must also be exactly `0`. This is the same invariant class as the reported LatentSwapLEX bug: two correlated supply-like counters (`baseTokenSupply` and Synth token supply) are expected to hit zero together, but because they are tracked/decremented through independent code paths, dust/rounding can decouple them, and the resulting "impossible" state is handled by an unconditional revert/assert rather than gracefully. In nearcore, the `gas` component of a buffered receipt is *not* a fixed value like its byte size — it is recomputed from the current `RuntimeConfig` fee schedule (`compute_receipt_congestion_gas`) whenever it is added to or removed from the buffer, whereas `size` is a fixed, receipt-inherent quantity. If the fee schedule used at buffer-time differs from the fee schedule used at forward/pop-time (e.g. because of a protocol-version/RuntimeConfig change while the receipt sat in the buffer across the boundary), the `gas` subtracted at pop time will not match the `gas` added at push time, while `size` will always balance out exactly. This desynchronizes the two counters and can hit `size == 0` while `gas != 0`, violating the hard-coded invariant.

### Finding Description
`ReceiptGroup::is_empty()` treats `size() == 0` as proof that a group is empty and asserts that `gas()` is also `0`: [1](#0-0) 

This invariant is exercised on every buffered-receipt removal via `ReceiptGroupsQueue::update_on_receipt_popped`, which independently subtracts the caller-supplied `receipt_size` and `receipt_gas` from the group's running totals and then calls `is_empty()`: [2](#0-1) 

The values fed into this accounting come from `receipt_congestion_gas`, which — for a plain (non state-stored) `Receipt` — recomputes gas via `compute_receipt_congestion_gas`, itself dependent on the currently active `RuntimeConfig` fee table (`config.fees.fee(...)`): [3](#0-2) 

Byte `size`, by contrast, is a deterministic property of the serialized receipt and never changes. Because `apply_state.config` is the config of the chunk currently being applied (which can differ from the config active when the receipt was originally buffered, across a protocol upgrade that changes fee parameters), the `gas` value used when the receipt is later popped/forwarded can diverge from the value that was added when it was pushed, while `size` by construction always nets to exactly zero once every receipt in the group has been removed. This produces exactly the "size zero but gas non-zero" state the assertion is meant to prevent.

A closely related, broader instance of the same assumption exists at the `CongestionInfo`/`ReceiptSinkV2WithInfo` level, where emptiness of the outgoing buffer as a whole is asserted to imply `buffered_receipts_gas() == 0`: [4](#0-3) [5](#0-4) 

All of these are plain `assert_eq!`/`assert!` calls (not `debug_assert!`), so they execute — and can panic — in production/release builds during ordinary chunk application, which is directly reachable from normal transaction/receipt traffic that populates the congestion-control outgoing buffer.

### Impact Explanation
An `assert_eq!` panic inside `apply()`'s receipt-forwarding path (`update_on_receipt_popped` → `is_empty()`, or `forward_from_buffer`) crashes the node process while applying a chunk. Because chunk application is deterministic and run by every validator/node tracking that shard, a single desynchronizing event would cause every node applying that chunk to panic identically, halting chunk production/progress for that shard — a chain-stall-class impact, which maps to the "node panic / chain stall" acceptance criteria.

### Likelihood Explanation
Triggering requires (a) buffering an action receipt subject to congestion control, and (b) the fee schedule (`RuntimeConfig.fees`) changing between the chunk where the receipt is buffered and the chunk where it is forwarded/popped — something that happens whenever validators roll out a protocol upgrade that adjusts fee parameters while receipts are congested/buffered. This is a normal, unprivileged occurrence (congestion happens under ordinary heavy transaction load) combined with a protocol-version transition that is entirely outside attacker/validator control requirements, making it a low-to-moderate likelihood but high-impact latent bug, consistent with the "High impact / Low likelihood" rating of the referenced report.

### Recommendation
Do not recompute `gas` for buffered receipts from the live `RuntimeConfig` at pop/forward time. Persist the `gas` (and `size`) that were computed at buffer time as part of the receipt's stored metadata (as is already done for `StateStoredReceipt` via `StateStoredReceiptMetadata`), and always use `use_state_stored_receipt = true` semantics for the accounting path, or otherwise pin the fee config used for buffered-receipt accounting to the value used at insertion. Additionally, replace the hard `assert_eq!`/`assert!` invariant checks in `ReceiptGroup::is_empty()`, `update_on_receipt_popped`, `forward_from_buffer`, and `get_child_congestion_info_not_finalized` with recoverable error handling (`RuntimeError`) so a desync degrades gracefully instead of crashing the node.

### Proof of Concept
Conceptual reproduction path (mirrors the structure of the reported PoC):
1. Submit transactions that create action receipts destined for a congested shard so they are buffered via `ReceiptSinkV2::buffer_receipt`, which calls `own_congestion_info.add_buffered_receipt_gas(gas)` and `outgoing_metadatas.update_on_receipt_pushed(shard, size, gas, ...)` using `gas` computed from the currently active `RuntimeConfig` fee schedule.
2. Have a protocol upgrade activate (changing `RuntimeConfig.fees`) while these receipts remain in the outgoing buffer (achievable simply by keeping the shard congested across an epoch boundary that carries a fee-parameter change).
3. When the buffer subsequently drains and `forward_from_buffer_to_shard`/`update_on_receipt_popped` recomputes `gas` for the same receipts using the new `RuntimeConfig`, the subtracted `gas` no longer matches the originally added `gas`, while `size` (fixed) balances to exactly `0`.
4. `ReceiptGroup::is_empty()` observes `size() == 0` and asserts `gas() == 0`, which fails, panicking the runtime during `apply()` and crashing every node applying that chunk.

/// Get the receipt gas from the receipt that was retrieved from the state.
/// If it is a [Receipt], the gas will be computed.
/// If it s the [StateStoredReceipt], the size will be read from the metadata.
pub(crate) fn receipt_congestion_gas(
    receipt: &ReceiptOrStateStoredReceipt,
    config: &RuntimeConfig,
) -> Result<Gas, IntegerOverflowError> {
    match receipt {
        ReceiptOrStateStoredReceipt::Receipt(receipt) => {
            compute_receipt_congestion_gas(receipt, config)
        }
        ReceiptOrStateStoredReceipt::StateStoredReceipt(receipt) => {
            Ok(receipt.metadata().congestion_gas)
        }
    }
}

/// Calculate the gas of a receipt before it is pushed into a state queue or
/// buffer. Please note that this method should only be used when storing
/// receipts into state. It should not be used for retrieving receipts from the
/// state.
///
/// The calculation is part of protocol and should only be modified with a
/// protocol upgrade.
pub(crate) fn compute_receipt_congestion_gas(
    receipt: &Receipt,
    config: &RuntimeConfig,
) -> Result<Gas, IntegerOverflowError> {
    match receipt.versioned_receipt() {
        VersionedReceiptEnum::Action(action_receipt) => {
            // account for gas guaranteed to be used for executing the receipts
            action_receipt_congestion_gas(receipt, config, action_receipt.into())
        }
        VersionedReceiptEnum::Data(_data_receipt) => {
            // Data receipts themselves don't cost gas to execute, their cost is
            // burnt at creation. What we should count, is the gas of the
            // postponed action receipt. But looking that up would require
            // reading the postponed receipt from the trie.
            // Thus, the congestion control MVP does not account for data
            // receipts or postponed receipts.
            Ok(Gas::ZERO)
        }
        VersionedReceiptEnum::PromiseYield(_) => {
            // The congestion control MVP does not account for yielding a
            // promise. Yielded promises are confined to a single account, hence
            // they never cross the shard boundaries. This makes it irrelevant
            // for the congestion MVP, which only counts gas in the outgoing
            // buffers and delayed receipts queue.
            Ok(Gas::ZERO)
        }
        VersionedReceiptEnum::PromiseResume(_) => {
            // The congestion control MVP does not account for resuming a promise.
            // Unlike `PromiseYield`, it is possible that a promise-resume ends
            // up in the delayed receipts queue.
            // But similar to a data receipt, it would be difficult to find the cost
            // of it without expensive state lookups.
            Ok(Gas::ZERO)
        }
        VersionedReceiptEnum::GlobalContractDistribution(_) => Ok(Gas::ZERO),
    }
}

fn action_receipt_congestion_gas(
    receipt: &Receipt,
    config: &RuntimeConfig,
    action_receipt: VersionedActionReceipt,
) -> Result<Gas, IntegerOverflowError> {
    let prepaid_exec_gas =
        total_prepaid_exec_fees(config, &action_receipt.actions(), receipt.receiver_id())?
            .gas
            .checked_add(config.fees.fee(ActionCosts::new_action_receipt).exec_fee().gas)
            .ok_or(IntegerOverflowError)?;
    // account for gas guaranteed to be used for creating new receipts
    let prepaid_send_cost = total_prepaid_send_fees(config, &action_receipt.actions())?;
    let prepaid_gas = prepaid_exec_gas.checked_add_result(prepaid_send_cost.gas)?;

    // account for gas potentially used for dynamic execution
    let gas_attached_to_fns = total_prepaid_gas(&action_receipt.actions())?;
    let gas = gas_attached_to_fns.checked_add_result(prepaid_gas)?;

    Ok(gas)
}
