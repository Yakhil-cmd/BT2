### Title
Webhook signature verification selects the GitHub App / secret using an unauthenticated field of the payload itself, letting an attacker bypass verification for one organization while writing to another organization's Stack - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which `GitHubApp` (and therefore which webhook secret) to validate the request against by reading `repository_owner` straight out of the *unauthenticated* JSON body, before the signature has been checked. If that self-declared organization has no `webhook_secret` configured, `GitHubApp#verify_webhook_signature` unconditionally returns `true`, so the request is accepted with no cryptographic check at all. Downstream handlers (e.g. `PushHandler`) then resolve and mutate `Stack`/`Repository` records using other payload fields describing the actual repository, which are never re-checked against the organization that was used to "authenticate" the request. This breaks the binding: *organization that authenticated == repository that is written*.

### Finding Description
`repository_owner` is derived entirely from attacker-controlled JSON, with no relation to any previously authenticated context: [1](#0-0) 

It is used to select the `GitHubApp` instance whose secret will (or will not) be checked: [2](#0-1) 

`GitHubApp#verify_webhook_signature` short-circuits to `true` whenever no `webhook_secret` is configured for that organization: [3](#0-2) 

Shipit explicitly supports multi-organization configuration where `webhook_secret` is optional per organization: [4](#0-3) 

Once `verify_signature` passes, the raw JSON body is handed unmodified to the registered handlers: [5](#0-4) 

`PushHandler` (and other handlers) then act on other payload fields — `ref`/`after` and the stack's matching repository — to select and mutate `Stack` records via `sync_github`, with no re-validation that the target repository's owner matches the organization whose (missing) secret was used during verification: [6](#0-5) 

Repositories are resolved purely by the `owner`/`name` strings present in the payload, independent of any authenticated identity: [7](#0-6) 

**Root cause:** the "authenticating organization" is self-selected by the unauthenticated payload (via `repository_owner`), and its presence/absence of a `webhook_secret` gates the entire request's trust — but nothing ties that selected organization to the actual repository/stack that downstream handlers subsequently write to. In an installation managing multiple GitHub organizations (as the shipped `secrets.yml` template explicitly supports), if any one organization is configured without a `webhook_secret` (documented as "optional"), an unauthenticated attacker can craft a payload that is accepted with zero cryptographic verification, while other payload fields point at a different, secret-protected organization's stack.

### Impact Explanation
This allows an unauthenticated party to forge webhook events (`push`, `status`, `check_suite`, `membership`, `pull_request`, etc.) that are processed as if legitimately delivered by GitHub, causing state-changing side effects (queuing `GithubSyncJob`, creating/removing `Membership`/`Team` records, updating commit statuses, refreshing check runs) against Stacks belonging to an organization that never should have been reachable without a valid signature. This satisfies the High-impact criteria: escalation into authorization state and unauthenticated write/mutation of stack state, and depending on which handler fires, can influence merge/deploy eligibility signals (e.g., forged `status`/`check_suite` events feeding into CI-gated deploy logic).

### Likelihood Explanation
Exploitability depends on a specific but realistic and *documented* deployment shape: a Shipit instance configured for more than one GitHub organization where at least one organization has no `webhook_secret` set (explicitly called out as "optional" in `docs/setup.md` and the shipped secrets templates). Given that shape, the bypass requires no credentials, no session, and no GitHub App access — only knowledge (or a guess) of which organization lacks a secret, which is discoverable by simply sending a probe payload and observing the response code.

### Recommendation
Do not let the organization used for signature verification be inferred solely from the unauthenticated request body. Instead:
- Require every configured organization to have a non-blank `webhook_secret` before webhooks are accepted (fail closed rather than `return true unless webhook_secret`).
- After signature verification succeeds, re-derive the "authenticated organization" only from the verified body, and enforce that every repository/stack subsequently mutated by handlers belongs to that same organization; reject or ignore events whose target repository owner does not match.

### Proof of Concept
1. Deploy Shipit configured for two organizations, e.g. `orgA` (has `webhook_secret` set) and `orgB` (no `webhook_secret` configured), each with existing Stacks.
2. As an unauthenticated attacker, POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "orgB" }, "full_name": "orgA/target-repo" }
}
```
No `X-Hub-Signature` header (or an arbitrary one) is needed.
3. `repository_owner` resolves to `"orgB"` [1](#0-0) ; `Shipit.github(organization: 'orgB')` has no `webhook_secret`, so `verify_webhook_signature` returns `true` unconditionally [3](#0-2) , regardless of the signature supplied.
4. The request is accepted and `PushHandler` runs against Stacks matching branch `main` for repository `orgA/target-repo`, invoking `stack.sync_github(expected_head_sha: params.after)` with an attacker-chosen SHA [8](#0-7) , even though `orgA`'s webhook secret was never checked.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
