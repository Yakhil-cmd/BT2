### Title
Webhook signature verification selects the trust anchor (org secret) from an unverified payload field that is disjoint from the field(s) handlers use to decide what gets written - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App/organization webhook secret to HMAC-verify against using a field read straight out of the still-unverified JSON body (`repository.owner.login` or `organization.login`). Once that check passes, the entire raw body — including different fields such as `repository.full_name` and, in the case of `status` events, no repository field at all — is handed unmodified to the event handlers, which use those *other* fields to decide which `Stack`/`Commit` to mutate. In a multi-organization Shipit deployment (`config/secrets.yml` supports one `webhook_secret` per organization, see `lib/shipit.rb`), this breaks the equality "organization that authenticated == repository that is written": a party that legitimately controls one tenant organization's webhook secret can forge a payload whose authentication field points at their own org while its action field points at a repository/commit belonging to a different tenant.

### Finding Description
`Shipit.github(organization:)` and `github_app_config` (`lib/shipit.rb:170-200`) support a per-organization webhook secret, and `WebhooksController#verify_signature` derives the org used for verification purely from body content: [1](#0-0) [2](#0-1) 

The signature check is only "the HMAC of the raw body matches secret for `repository_owner`" — it never checks that `repository_owner` corresponds to the repository actually referenced elsewhere in the same body: [3](#0-2) 

Once this passes, the full, attacker-authored body is dispatched to all handlers for the event: [4](#0-3) 

Handlers pick the target `Stack`/`Repository` from a *different* field of the same body: [5](#0-4) 

`StatusHandler` is the worst case: it does not scope by repository at all, it globally matches on `sha`: [6](#0-5) 

`MembershipHandler` similarly trusts `organization.login` from the body to tag a `Team` without cross-checking it against the field used to select the verification secret: [7](#0-6) 

Because `repository_owner`/`organization.login` (the authentication-selecting field) and `repository.full_name`/`sha` (the write-target field) live in the same unauthenticated JSON blob whose HMAC is computed over the *entire* body with *one* organization's secret, anyone who legitimately knows one organization's `webhook_secret` (e.g., because they are an admin of that org's own installed GitHub App, which is how per-org secrets are normally obtained/rotated in this multi-tenant configuration) can construct a byte string where the "authenticating" sub-object names their own org while the "acted-upon" sub-object names an arbitrary other tracked repository or an arbitrary commit `sha` belonging to a different org's stack. `verify_signature` only proves "the sender knows *some* configured org's secret and this exact byte string," not "the org named in the acted-upon field authorized this content."

### Impact Explanation
This lets an attacker who controls a single tenant organization's webhook secret inject forged GitHub `status` payloads for commits belonging to *any other* organization/stack tracked by the same Shipit instance (bypassing the `repository_owner` gate entirely, since `StatusHandler` never checks the repository). A forged `state: "success"` status with a `context` matching a stack's `ci.require` list can satisfy CI gating used by `Stack#trigger_continuous_delivery` / merge-queue logic, producing an **unauthorized deploy** on a repository the attacker does not control — this lands in the Critical bucket ("unauthorized deploy, rollback or merge"). The `MembershipHandler` variant additionally lets the attacker tag an arbitrary GitHub team as belonging to a different organization and add arbitrary members to it, which can escalate into `Shipit.github_teams` authorization if that team is used for access control (High bucket).

### Likelihood Explanation
Requires only that the attacker is a legitimate holder of one org's `webhook_secret` in a multi-organization Shipit deployment (a normal, unprivileged position relative to *other* tenants on the same instance — they never touch the target org's secret, `GITHUB_TOKEN`, an `ApiClient` token, or a Shipit session). No cooperation from GitHub or the victim organization is needed; the attacker directly POSTs a crafted body to `/webhooks` with a correctly computed HMAC using their own secret.

### Recommendation
Bind the field used to select the verification secret to the field(s) handlers use to act. Concretely: after selecting `github_app` by `repository_owner`, re-derive/validate that every repository reference inside the payload (`repository.full_name`, and for `status`/`check_suite` events, that the matched `Commit`'s stack repository) belongs to that same verified organization before dispatching to handlers, and have `StatusHandler` scope `Commit.where(sha:)` by the verified repository/organization rather than matching globally by `sha`.

### Proof of Concept
1. Configure Shipit with two organizations, `orgA` and `orgB`, each with its own `webhook_secret` (per `config/secrets.*.yml` multi-org schema).
2. As an administrator of `orgA`'s GitHub App (a normal, unprivileged position with respect to `orgB`), read/know `orgA`'s `webhook_secret`.
3. Find a commit `sha` belonging to a stack under `orgB` whose `shipit.yml` requires a CI context, e.g. `ci/tests`.
4. Craft a `status` webhook body:
```json
{
  "sha": "<orgB-stack-commit-sha>",
  "state": "success",
  "context": "ci/tests",
  "repository": {"owner": {"login": "orgA"}}
}
```
5. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(orgA_webhook_secret, body)>` and POST to `/webhooks` with header `X-Github-Event: status`.
6. `verify_signature` resolves `repository_owner` to `orgA`, verifies successfully with `orgA`'s secret, and `create` dispatches the same body to `StatusHandler`, which finds `Commit.where(sha: params.sha)` — the `orgB` commit — and creates a fabricated success status on it, independent of `orgB`'s real CI, potentially unblocking an unauthorized deploy for `orgB`'s stack.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
