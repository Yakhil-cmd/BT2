### Title
Webhook signature is verified against the organization named in `repository.owner.login`, but the write target is selected independently from `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which multi-tenant GitHub App config (and therefore which `webhook_secret`) to verify the HMAC signature against based on `repository_owner`, a field read straight out of the untrusted JSON body. Every downstream `Handler` then locates the `Stack`/`Repository` to act on using a *different* field from the same body, `repository.full_name`. Nothing in the code enforces that these two fields refer to the same organization/repository, breaking the binding: `organization authenticated == repository written`.

### Finding Description
`verify_signature` resolves the GitHub App/secret to use for HMAC verification purely from the payload itself: [1](#0-0) [2](#0-1) 

`repository_owner` is derived from `params.dig('repository', 'owner', 'login')`. `Shipit.github(organization: repository_owner)` looks up the per-organization config (including `webhook_secret`) for exactly that string: [3](#0-2) 

Once signature verification succeeds, `create` dispatches to handlers with the raw parsed body: [4](#0-3) 

Every handler resolves the actual `Repository`/`Stack` to act on from an entirely separate field of the same attacker-controlled payload, `repository.full_name`, via `Handler#repository_name` / `Repository.from_github_repo_name`: [5](#0-4) [6](#0-5) 

Because the HMAC covers the whole raw body, an attacker who legitimately controls (or has been issued) the `webhook_secret` for one configured GitHub organization ("orgA") can craft and correctly sign an arbitrary JSON payload where `repository.owner.login == "orgA"` (satisfying `verify_signature`) while `repository.full_name == "orgB/some-repo"` (satisfying the handler's stack lookup for a repository belonging to an entirely different, unrelated organization "orgB" configured in the same multi-tenant Shipit instance). The code performs no cross-check that `full_name`'s owner segment matches `repository.owner.login`/`repository_owner`.

This is a direct analog of the referenced report's root cause: a value used to satisfy an authorization/verification check (`initialStartTime`/duration check in the Solidity code, here the org used for signature verification) is decoupled from the value that actually drives the state-changing action (minipool recreation there, repository/stack write here), letting an entity that is valid for one target act on a different one.

### Impact Explanation
Handlers such as `PushHandler` trigger `stack.sync_github(expected_head_sha:)` [7](#0-6)  and PR handlers such as `OpenedHandler`/`LabeledHandler` can archive/unarchive stacks or provision review stacks based on repository/PR data resolved solely from `full_name` and the review-stack scope [8](#0-7) . This means a holder of one organization's webhook secret in a multi-org Shipit deployment can spoof events (pushes, PR opened/labeled/reopened/unlabeled) attributed to any repository configured under a *different* organization, causing cross-repository/cross-organization state writes (sync jobs, stack archive/unarchive, review-stack provisioning) that should require that other organization's own credentials. This matches the "cross-repository writes" Critical impact bucket, since it lets an unprivileged-for-org-B attacker (privileged only for org A) cause writes against org B's stacks.

### Likelihood Explanation
Requires the deployment to be configured with `Shipit.github` for multiple organizations (the multi-tenant config path in `github_app_config`) and requires the attacker to know/control one org's `webhook_secret` — which is a realistic scenario for a compromised or malicious GitHub App integration on one tenant org in a shared Shipit instance, since nothing in `verify_signature` or the handler chain cross-validates `repository.owner.login` against `repository.full_name`'s owner. It does not require any Shipit session, `ApiClient` token, or GitHub write access to the target org's repository.

### Recommendation
After successful signature verification, re-derive the acted-upon repository/organization strictly from the same trusted field used for verification (`repository_owner`), or explicitly assert that `repository.full_name.split('/').first == repository_owner` (case-insensitively) before dispatching to handlers, rejecting the webhook otherwise.

### Proof of Concept
1. Configure Shipit with two organizations, `orgA` and `orgB`, each with its own `webhook_secret`, per `docs/setup.md`'s multi-org schema.
2. As an entity that knows `orgA`'s `webhook_secret` (e.g., a compromised GitHub App installation for orgA), craft a `push` event JSON body with:
   - `repository.owner.login = "orgA"`
   - `repository.full_name = "orgB/target-repo"`
   - `ref` matching a tracked branch of a stack that exists under `orgB/target-repo`
3. Sign the raw body with `orgA`'s `webhook_secret` using the same HMAC-SHA1 scheme as `Hook::DeliverySigner`/`verify_webhook_signature` and send it to `POST /webhooks` with header `X-Hub-Signature`.
4. `verify_signature` calls `Shipit.github(organization: "orgA")` and successfully verifies the signature against the attacker-controlled, orgA-signed payload.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("orgB/target-repo")` and calls `stack.sync_github(expected_head_sha: params.after)` on orgB's stack — a state-changing action against orgB despite the attacker only possessing orgA's credentials.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
