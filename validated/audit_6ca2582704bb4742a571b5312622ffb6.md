### Title
Webhook signature verified against the org derived from `repository.owner.login`/`organization.login`, but the Stack that is written is derived from `repository.full_name` in the same untrusted payload, with no check that both name the same organization - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App config (and therefore which HMAC `webhook_secret`) validates an inbound webhook by reading `repository.owner.login` (falling back to `organization.login`) out of the JSON body itself, then calls `Shipit.github(organization: repository_owner)` to fetch that organization's secret. Every downstream `Webhooks::Handlers::Handler` subclass instead resolves the target `Stack`/`Repository` using a *different* field of the same payload, `repository.full_name` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`). Nothing enforces that the organization used to pick the verification secret and the organization embedded in `repository.full_name` are the same. In a multi-org Shipit deployment (the supported configuration, see `config/secrets.development.shopify.yml`), anyone who legitimately administers one configured GitHub organization's App installation (and thus knows that org's own `webhook_secret`) can sign a payload whose `repository.owner.login`/`organization.login` names their own org, while `repository.full_name` names a repository belonging to a *different* configured organization on the same Shipit instance. The signature check passes (it only proves "signed with Org A's secret"), yet the handler acts on Org B's repository/stack.

### Finding Description
- `verify_signature` picks the app/secret purely from attacker-controlled JSON, before the signature is checked: [1](#0-0) [2](#0-1) 

- `Shipit.github(organization:)` maps that string to one of several independently configured `GitHubApp` instances, each with its own `webhook_secret`: [3](#0-2) 

- `verify_webhook_signature` only proves the raw body was HMAC-signed with *the secret belonging to the organization named in the payload's own owner/organization field* — it says nothing about which organization the rest of the payload's content (e.g. `repository.full_name`) actually refers to: [4](#0-3) 

- Every handler that mutates state (push → `GithubSyncJob`, status, check_suite → `RefreshCheckRunsJob`, membership, pull_request, etc.) resolves the acted-upon repository/stack from `repository.full_name`, a completely different key of the same payload than the one used for signature routing: [5](#0-4) 

Because the field used to select the verification secret (`repository.owner.login` / `organization.login`) and the field used to select the object that gets written (`repository.full_name`) are independent, uncorrelated fields of the same signed body, an entity that legitimately controls one organization's webhook secret can produce a validly-signed payload that targets another organization's stack. This is the same class of defect as the referenced report: a trust decision (there: cached balance amount; here: "this payload is authentic for organization X") is bound to one piece of state, while the operation that is actually executed is driven by a different, unchecked piece of state that can diverge from it.

### Impact Explanation
This crosses the "cross-repository writes" bar explicitly listed as Critical impact. On a Shipit instance configured with multiple GitHub organizations (a first-class supported configuration, see `config/secrets.development.shopify.yml`), a party who administers/owns one configured organization's GitHub App installation (and thus its `webhook_secret`, which they themselves generated when installing the app — not a Shipit secret, `GITHUB_TOKEN`, or `api_clients_secret`) can forge webhook events that Shipit will process as if they originated from a *different* organization's repository. Depending on which event type is abused this can: enqueue `GithubSyncJob`/`CacheDeploySpecJob` against another org's stack, inject fabricated commit statuses (`status` event) that feed CI-gating logic used by `MergeRequest#all_status_checks_passed?`/merge automation, or drive `check_suite`/`membership` handlers to mutate `Team`/`Membership` records tied to another organization — all without ever touching the victim organization's own secret, repo write access, or a Shipit API/session credential.

### Likelihood Explanation
Requires only that the Shipit instance be configured for more than one GitHub organization and that the attacker administers (or otherwise possesses the webhook secret of) at least one of them — a realistic operating model for shared internal deploy tools serving several orgs. No repository write access to the *target* org, no `ApiClient`, no Shipit session and no leaked `GITHUB_TOKEN`/`api_clients_secret` are needed, satisfying the "unprivileged relative to the target" requirement in the rules. Single-organization deployments (the default/simple config) are not affected, since `repository_owner` then has no effect on secret selection.

### Recommendation
After signature verification, cross-check that the organization used to select the verifying secret matches the organization embedded in `repository.full_name` (and `organization.login` when present), rejecting the webhook (422) on mismatch. Alternatively, verify the signature against every configured organization's secret rather than one selected from unauthenticated payload content, and only proceed if the org that actually verifies also matches the repository the payload claims to describe.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` and `org-b`, each with its own `webhook_secret` (as in `config/secrets.development.shopify.yml`).
2. As an administrator of `org-a`'s GitHub App, know `org-a`'s `webhook_secret`.
3. Craft a JSON body for a `push` (or `status`/`check_suite`/`membership`) event where `repository.owner.login` = `"org-a"` (or `organization.login` = `"org-a"`) but `repository.full_name` = `"org-b/some-target-repo"`.
4. Compute `X-Hub-Signature` as `sha1=HMAC-SHA1(org-a webhook_secret, raw_body)` and POST to `/webhooks` with `X-Github-Event` set accordingly.
5. `WebhooksController#verify_signature` calls `Shipit.github(organization: "org-a")` and the signature validates successfully. [6](#0-5) 
6. `Shipit::Webhooks.for_event(event)` handlers run and resolve the target via `repository.full_name`, i.e. `org-b/some-target-repo`, mutating that stack's state (sync jobs, statuses, memberships) despite the payload only ever having been authenticated for `org-a`. [5](#0-4)

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
