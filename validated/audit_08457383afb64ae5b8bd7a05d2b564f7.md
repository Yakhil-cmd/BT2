## Analog Found

### Title
Webhook signature verification is keyed on an unsigned `repository.owner.login`/`organization.login` field, letting a valid signature from one GitHub organization authorize handler actions against a completely different organization's stacks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App (and therefore which `webhook_secret`) to validate the HMAC signature against using `repository_owner`, a value read directly out of the untrusted, not-yet-verified JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`). Once the HMAC check passes, `create` hands the **entire raw payload** to `Shipit::Webhooks::Handlers::Handler`, which independently determines the target repository/stack from a *different* payload field, `payload.dig('repository','full_name')`. Nothing binds these two fields together, so a signature that is valid for organization A can be paired with a `repository.full_name` pointing at organization B's repository.

### Finding Description
In multi-organization Shipit deployments (`docs/setup.md` "Using Multiple Github Applications"), each GitHub organization has its own `webhook_secret`: [1](#0-0) 

The webhook signature is verified like this: [2](#0-1) 

`repository_owner` — the value that selects *which org's secret* is used to verify the signature — comes straight from the unauthenticated request body: [3](#0-2) 

After the signature check passes, the full `params` (the same untrusted JSON) is dispatched to handlers: [4](#0-3) 

Handlers, however, resolve the actual target repository/stack from a **different** field of the same payload, `repository.full_name`, with no cross-check against `repository.owner.login`: [5](#0-4) [6](#0-5) 

The equality that should hold but doesn't:
`organization whose webhook_secret produced a valid signature (repository.owner.login / organization.login) == organization whose repository is actually acted upon (repository.full_name)`

Since GitHub places `owner.login` and `full_name`'s owner-segment in the same JSON object under attacker/organization-admin control when composing a payload for signing, an entity that legitimately controls one Shipit-configured organization's GitHub App (and thus knows/produces valid signatures for that org's `webhook_secret`) can produce a request whose `repository.owner.login` is their own org (satisfying `verify_signature`) while `repository.full_name` names a repository belonging to a *different* configured organization tracked by the same Shipit instance. The signature check passes, and handlers act on the victim organization's stack using the field that was never covered by the signature-selection logic.

Concretely, `PushHandler#process` (via `Handler#stacks`/`#repository_name`) will enqueue `stack.sync_github(expected_head_sha: ...)` for the victim stack: [7](#0-6) 

This runs `GithubSyncJob`, which fetches commits **using Shipit's own legitimate GitHub App credentials for the victim organization** (not the attacker's): [8](#0-7) 

Newly appended commits automatically schedule continuous delivery if the victim stack has `continuous_deployment` enabled: [9](#0-8) 

### Impact Explanation
This crosses the exact trust boundary called out by the rules: "an organization that authenticated versus the repository that is written." An attacker who legitimately controls one org configured in Shipit's multi-org `github` secrets section (and therefore possesses/derives valid webhook signatures scoped to that org) can forge webhook deliveries (push/status/check_suite/pull_request/membership events) that are cryptographically validated against their own org's secret but are processed as if they originated for an unrelated victim organization's repository, because the handler layer trusts `repository.full_name` unconditionally. This can:
- Force `GithubSyncJob` to run against a victim's stack, and if `continuous_deployment` is enabled, trigger `ContinuousDeliveryJob`, causing an **unauthorized deploy** of the victim's actual GitHub `HEAD` commit — matching the report's Critical impact category ("unauthorized deploy, rollback, or merge").
- Inject forged commit statuses (`StatusHandler`), influence merge-queue/PR handlers (`labeled_handler.rb`, `assigned_handler.rb`, etc.) for repositories the attacker does not control, all validated by a signature that has nothing to do with that repository.

This is a direct analog of the Rio report's root cause: a downstream consumer (Shipit's handler dispatch) trusts a payload field (`repository.full_name`) that was never actually covered/bound by the verification step (`verify_signature`'s `repository_owner` lookup), just as `RioLRTOperatorDelegator`'s `receive()` forwarded funds without the recipient contract's logic being covered by the gas budget granted upstream.

### Likelihood Explanation
Requires only that the attacker be an admin/owner of *any* GitHub organization/app configured in the same multi-tenant Shipit instance's `secrets.yml` `github` section — no privileged Shipit account, `ApiClient` token, or `webhook_secret` of the *victim* org is needed. This is a realistic deployment pattern explicitly documented in `docs/setup.md`. The attack requires no interaction with Shipit's UI/API, only crafting a raw webhook POST with mismatched `owner.login` vs `full_name`.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler#repository_name`/`#stacks`), enforce that the organization used to select the `webhook_secret` (`repository.owner.login` / `organization.login`) matches the owner segment of `repository.full_name` before any handler is invoked; reject the request (422) on mismatch.

### Proof of Concept
1. Shipit is configured with two GitHub orgs, `attacker-org` and `victim-org`, each with its own `webhook_secret` (per `docs/setup.md` multi-app setup), and both have repositories/stacks tracked by the same Shipit instance.
2. Attacker, who administers `attacker-org`'s GitHub App, knows `attacker-org`'s `webhook_secret` (they created it) and crafts a `push` payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<victim-latest-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/private-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org-secret, body)` and POSTs to `/webhooks`.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")` (from `repository.owner.login`) and the signature validates successfully.
5. `create` dispatches `params` to `PushHandler`, whose `Handler#repository_name` reads `payload.dig('repository','full_name')` → `"victim-org/private-repo"`, resolving `victim-org`'s real stack and enqueuing `GithubSyncJob`/potential `ContinuousDeliveryJob` against it, using Shipit's legitimate credentials for `victim-org` — despite the request never being signed with `victim-org`'s secret.

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
