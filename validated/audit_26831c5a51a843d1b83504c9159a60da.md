### Title
Cross-tenant Commit status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` only proves that the request body was signed with the `webhook_secret` of the organization named in the payload's own `repository.owner.login`/`organization.login` field [1](#0-0) [2](#0-1) . `StatusHandler#process`, invoked next, resolves affected rows purely by `Commit.where(sha: params.sha)` with no filter tying the commit's `Stack`/`Repository` back to the organization that signed the request [3](#0-2) . This lets an attacker who owns any repository under any GitHub organization send a validly-signed `status` webhook whose `sha` collides with a commit belonging to a completely different tenant's stack, mutating that victim commit's CI status.

### Finding Description
The broken binding is: `organization_that_signed(repository_owner from payload) == organization_owning(Commit rows mutated by sha)`. This is never enforced.

Code path:
1. Attacker POSTs to `/webhooks` with `X-Github-Event: status`, a body whose `repository.owner.login` is the attacker's own org (call it `evil-org`), and computes `X-Hub-Signature` using `evil-org`'s real `webhook_secret` (which the attacker legitimately possesses, since it's their own GitHub App/org integration).
2. `verify_signature` calls `Shipit.github(organization: repository_owner)` where `repository_owner` is read straight from the attacker-controlled payload, then verifies the signature against that same organization's secret [1](#0-0) . Because the attacker used their own valid secret for their own org, this check passes — correctly, in isolation.
3. `create` parses the body and dispatches to handlers for the `status` event: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [4](#0-3) .
4. `StatusHandler.call(params)` builds an `ExplicitParameters` struct requiring only `sha`, `state`, and optional fields — no `repository` field is required or validated [5](#0-4) .
5. `process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a global, cross-tenant lookup by SHA with no scoping to any `Repository` or `Stack` [3](#0-2) .

Notably, the base `Handler` class already has a `stacks` helper that scopes by `Repository.from_github_repo_name(repository_name)` derived from `payload.dig('repository', 'full_name')` [6](#0-5) , but `StatusHandler#process` never calls or uses it — it queries `Commit` directly and unconditionally. Because git SHA-1 is a 40-hex-char identifier and many public open-source projects/forks share identical commit SHAs (forks, cherry-picks, vendored histories, mirrored repos), or an attacker can simply learn a victim's commit SHA from any public source (Shipit's own public dashboard, GitHub, CI logs) and craft a payload — no secret of the victim's is needed to target their commit rows, since only the *sha string* is compared, not repository identity.

None of the listed guards prevent this: `verify_signature` only binds signature-to-organization, not organization-to-commit; `drop_unhandled_event` only checks event type exists; the `ExplicitParameters` schema for `StatusHandler` doesn't require/validate `repository`; there is no `force_github_authentication`, `User#authorized?`, or `require_permission!` involved since `WebhooksController` is unauthenticated by design (webhooks come from GitHub, not a logged-in user).

### Impact Explanation
An attacker who owns/controls an arbitrary GitHub repository/organization (trivial — anyone can create one) can send a validly-signed webhook that writes a `Status` row against a `Commit` belonging to any other tenant's `Stack`, as long as they know or guess that commit's SHA. This directly matches the Critical impact category: "a payload for one repository mutating another's stack, commit, task or team." The blast radius is every tenant using this shared Shipit instance — an attacker can flip CI status (`success`/`failure`/`pending`) on victim commits, which can gate or unblock deploys depending on stack configuration (e.g., required status checks before deploy). The attack is fully repeatable against any known SHA and requires no interaction with the victim.

### Likelihood Explanation
Preconditions are minimal: the attacker needs their own GitHub organization/repository configured as a Shipit-integrated org (or any org already known to `Shipit.github_teams`/`Shipit.github` config) so that `Shipit.github(organization: repository_owner)` resolves to a `GithubApp` with a `webhook_secret` the attacker can compute a valid signature with (i.e., their own installation's webhook secret, which they legitimately have access to as the repo/org owner). The only additional information needed is a target commit SHA, which is often public (GitHub commit pages, PR pages, CI dashboards, or Shipit's own stack UI which lists commit SHAs). Attacker cost is a single HTTP POST; the exploit is trivially repeatable and scriptable against any number of guessed/known SHAs.

### Recommendation
In `StatusHandler#process` (and any other handler that queries `Commit`/`Stack` by attacker-supplied identifiers), scope the lookup to the repository asserted by the payload and verified via `verify_signature`, e.g., use the base `Handler#stacks` helper to restrict to commits under stacks belonging to `Repository.from_github_repo_name(payload.dig('repository','full_name'))`, and reject/no-op if the resolved repository's owner doesn't match `repository_owner`/the organization that authenticated the signature. Concretely: `stacks.flat_map(&:commits).where(sha: params.sha)` instead of the global `Commit.where(sha: params.sha)`.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test "status webhook from attacker org cannot mutate victim's commit status" do
  attacker_secret = 'attacker-org-secret'
  Shipit.stubs(:github).with(organization: 'evil-org').returns(
    stub(verify_webhook_signature: true) # simulate a genuinely valid signature computed with attacker_secret
  )

  victim_stack = shipit_stacks(:shipit)
  victim_commit = victim_stack.commits.last
  refute_predicate victim_commit.statuses, :any?

  payload = {
    'repository' => { 'owner' => { 'login' => 'evil-org' }, 'full_name' => 'evil-org/evil-repo' },
    'sha' => victim_commit.sha,
    'state' => 'failure',
    'context' => 'forged-check'
  }.to_json

  signature = 'sha1=' + OpenSSL::HMAC.hexdigest('sha1', attacker_secret, payload)

  post '/webhooks', params: payload,
       headers: { 'X-Github-Event' => 'status', 'X-Hub-Signature' => signature, 'CONTENT_TYPE' => 'application/json' }

  assert_response :ok
  # BEFORE: attacker's org != victim's org (attacker owns evil-org, victim commit belongs to Repository X)
  # AFTER : victim_commit now has a Status row created by a payload signed only by evil-org's secret
  assert victim_commit.statuses.reload.exists?(context: 'forged-check', state: 'failure'),
         "victim commit status was mutated by an unrelated, attacker-controlled organization's webhook"
end
```
This demonstrates the equality `repository_owner (evil-org)` vs `owning organization of Commit#sha` diverging both before (different orgs) and after (still different orgs, yet the write succeeded) the request — confirming the vulnerability.
