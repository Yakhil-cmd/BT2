### Title
Unilateral asset attestor list replacement instantly and permanently freezes existing holders' funds with no grace period - (File: validation.js, storage.js)

### Summary
For a `spender_attested` asset, the asset definer (a normal, unprivileged application actor — the "asset issuer" — including an AA acting as its own asset's definer) can publish an `asset_attestors` message that completely replaces the trusted attestor list at any time. `storage.readAsset`'s `addAttestorsIfNecessary` always uses only the single, latest attestor-list unit for the asset, with no transition window, versioning, or delay before the new list takes effect for payment validation.

### Finding Description
When an asset has `spender_attested = true`, every payment (issue, transfer) involving that asset requires that at least one author/owner address be attested by one of the asset's current attestors, checked via `storage.filterAttestedAddresses` and enforced in `validatePayment`/`validatePaymentInputsAndOutputs`. [3](#0-2) [4](#0-3) 

The attestor list itself is not append-only or versioned per-address: `readAsset` looks up only the single most recent `asset_attestors` unit for the asset (`ORDER BY level DESC LIMIT 1`) and uses that unit's entire attestor set as the current, authoritative list, discarding the previous list wholesale. [5](#0-4) 

`validateAttestorListUpdate` only checks that the sender is the asset's definer and that the new list is well-formed (sorted, valid addresses, under the max count) — it imposes no cooldown, no overlap period with the old list, and no mechanism letting holders who were attested only by a now-removed attestor to move/redeem their coins before the change takes effect. [2](#0-1) [6](#0-5) 

Because the check is evaluated against `objValidationState.last_ball_mci` at spend time using whatever the *current* stable attestor list is, a holder whose only attestation came from a removed attestor becomes immediately and irreversibly unable to spend, transfer, or redeem outputs they already hold — even outputs that existed and were validly attested before the list changed. This mirrors the JOJO report's root cause: a state transition (delisting/attestor-list swap) controlled by a single privileged-but-reachable party takes effect instantly with zero warning or transition window, converting previously "good standing" holders into permanently stuck holders, with no on-chain path to exit gracefully.

### Impact Explanation
Any holder of a `spender_attested` asset whose attestation comes from an attestor that gets dropped from the list loses the ability to spend their existing coins the moment the new `asset_attestors` unit becomes stable — there is no fallback, no delay, and no alternate path to move the funds (the coins are not burned, but they become permanently unspendable/frozen under the current attestor set, since attestations themselves aren't retroactively revocable/reissuable by the holder). This is a fund-freezing bug directly analogous to the "instant liquidation with no chance to withdraw" pattern: the asset issuer's routine, expected administrative action (updating the attestor set, e.g., to rotate a KYC/compliance provider) causes an uncommunicated, block-instant loss of access for existing token holders in previously good standing, with no protocol-level grace period.

### Likelihood Explanation
Any asset issuer (including an AA that defines its own `spender_attested` asset and later emits `asset_attestors`) can trigger this at will by simply posting one `asset_attestors` message; no special network position or timing attack is needed. This is a routine, permitted operation (rotating attestors is explicitly part of the asset's designed lifecycle), so it will occur in normal operation of such assets, not merely as a rare edge case.

### Recommendation
Introduce a grace/overlap period when replacing an asset's attestor list: honor the previous attestor list for a defined number of MCIs (or units) after a new `asset_attestors` unit becomes stable, so that addresses attested under the old list can still spend previously-held outputs during the transition. Alternatively, validate spend-time attestation against the attestor list that was current when the output was created (or any list valid at any point since), rather than exclusively the single latest list, to avoid retroactively freezing existing balances.

### Proof of Concept
1. Definer issues asset A with `spender_attested: true` and initial `attestors: [X]`.
2. Attestor X attests address H (holder). H receives a payment output in asset A — validated fine since H is attested by X (`filterAttestedAddresses`).
3. Definer posts an `asset_attestors` message for asset A with `attestors: [Y]` (dropping X). This passes `validateAttestorListUpdate` since only definer-authorship and list well-formedness are checked. [7](#0-6) 
4. Once this unit is stable, `readAsset`'s `addAttestorsIfNecessary` returns `arrAttestorAddresses = [Y]` as the sole current list. [8](#0-7) 
5. H attempts to spend the previously received output. `filterAttestedAddresses` now finds no row for H (since only X, not Y, ever attested H), so `arrAttestedAddresses` excludes H, and `validatePayment` rejects the transaction with "none of the authors is attested" — H's coins are permanently stuck with no recourse, despite H having done nothing wrong and having held the coins in good standing before the list change. [9](#0-8)

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}

function checkAttestorList(arrAttestors){
	if (!isNonemptyArray(arrAttestors))
		return "attestors not defined";
	if (arrAttestors.length > constants.MAX_ATTESTORS_PER_ASSET)
		return "too many attestors";
	var prev="";
	for (var i=0; i<arrAttestors.length; i++){
		if (!isValidAddress(arrAttestors[i]))
			return "invalid attestor address: "+JSON.stringify(arrAttestors[i]);
		if (arrAttestors[i] <= prev)
			return "attestors not sorted";
		prev = arrAttestors[i];
	}
	return null;
}
