## Title
Malicious asset definer can permanently freeze all holders' funds by bricking the `cosigned_by_definer` address - (File: `validation.js`)

### Summary
An asset can be defined with the `cosigned_by_definer` flag, which forces every future transfer of that asset to include the asset's `definer_address` as a co-signing author. Because address definitions in ocore are mutable and are always evaluated **live** (against the current, most-recently-disclosed definition, not the one active at asset-creation time), the definer — an ordinary, unprivileged asset issuer — can redefine their own address to an unsatisfiable condition at any time. Once that happens, no future unit can ever produce valid authentifiers for the definer, so `cosigned_by_definer` can never be satisfied again, and every other honest holder of the asset loses the ability to transfer their balance forever. This mirrors the reported bug class: an untrusted party (the counterpart other users must rely on) unilaterally destroys/invalidates a resource (their own signable identity) that other unprivileged users' fund recovery depends on, causing an irreversible DoS/freeze with no on-chain remediation path.

### Finding Description
When a payment message spends a `cosigned_by_definer` asset, `validatePayment` requires the definer address to be among the unit's authors: [1](#0-0) 

This check only ensures the definer's address is present as an author; the actual cryptographic validity of that author's signature is checked later by resolving the definer address's **current** definition via `storage.readDefinitionByAddress`, which reads whatever definition is stable as of `last_ball_mci` at the time of validation — not the definition that existed when the asset (or any given holder's coins) was created: [2](#0-1) [3](#0-2) 

Ocore's address model allows any address owner to redefine their own address's spending condition at will (a standard `address_definition_change`), subject only to signing the change with the previously-valid definition: [4](#0-3) [5](#0-4) 

Nothing prevents the definer from changing their address's definition to a condition that can never be satisfied again (e.g., referencing a `hash` secret nobody knows, an `in data feed` condition that will never match, or a definition requiring a key that was never generated/was discarded). Because `validateAuthentifiers`/`validateDefinition` always re-evaluate the *current* definition of every author on every subsequent unit (as documented directly in the code, "we need to re-validate the definition every time... in case a referenced address was redefined"): [6](#0-5) 

once the definer's address becomes permanently unsatisfiable, `cosigned_by_definer` can never again be satisfied by any unit, for any holder, forever. There is no fallback, emergency path, or way for other holders to move their balances of that asset — the freeze is total and irreversible, exactly like the reported case where burning the NFT permanently prevented `underlyingPositionManager` calls from succeeding for any counterparty.

### Impact Explanation
- Every honest holder of a `cosigned_by_definer` asset loses the ability to transfer or otherwise spend their balance of that asset, permanently.
- This is not limited to the malicious definer's own funds — it freezes funds held by any third party who legitimately received or holds the asset, with no mechanism to bypass the broken co-signature requirement.
- The attack is fully reachable by an ordinary, unprivileged actor (the asset's own definer/issuer) using only standard, already-permitted operations (issuing an asset, later changing their own address definition) — no special network, hub, or protocol-level privilege is required.
- Given ocore explicitly lists "asset issuance and transfer conditions" as an in-scope reachable path for unprivileged actors, and the impact is a concrete, unrecoverable freeze of other users' funds, this qualifies as High severity.

### Likelihood Explanation
Any asset issuer choosing `cosigned_by_definer: true` (a documented, supported asset flag) can trigger this at any later time simply by posting a valid `address_definition_change` for their own address to an unsatisfiable definition. This requires no coordination with other parties, no race condition, and no unusual network state — it is a deterministic, always-available action by the definer.

### Recommendation
- Consider pinning `cosigned_by_definer` validation to the definer's definition as it existed when the asset was defined (or as of the relevant "safe" MCI), rather than always re-resolving the live/current definition, to avoid single-party griefing of all other holders.
- Alternatively, provide an escape hatch (e.g., allow governance/majority-of-holders override, or disallow definer redefinition once `cosigned_by_definer` assets with nonzero circulating supply exist) so a malicious or careless definer cannot unilaterally and irreversibly freeze funds belonging to other users.
- At minimum, document this risk prominently for anyone building on `cosigned_by_definer`/`spender_attested` assets, since the same "live re-evaluation of a third party's mutable definition" pattern also affects `spender_attested` attestor lists.

### Proof of Concept
1. Alice issues asset X with `cosigned_by_definer: true`, `definer_address = D` (an address Alice controls).
2. Bob and other users legitimately acquire units of asset X (each such transfer already included D as a co-signing author, satisfying the check at that time).
3. Alice posts a valid `address_definition_change` unit that redefines address D's spending condition to something permanently unsatisfiable (e.g., `["hash", {hash: <unknown-secret-hash>}]`), and this change becomes stable.
4. Bob (or anyone) now attempts to spend their asset X balance. `validatePayment` still requires D as an author (`validation.js:2112-2113`), but `validateAuthentifiers`/`validateDefinition` re-resolve D's live definition (`storage.readDefinitionByAddress`) and it can never be satisfied — the unit is permanently rejected.
5. Every future attempt by any holder to spend asset X fails identically; there is no valid unit D can ever author again, so the freeze is permanent.
