### Title
Race between `dryRunPrimaryAATrigger` and real AA trigger execution leads to stale/corrupted unit caches (`assocUnstableUnits`) — analogous UAF-style stale-reference bug - ([File: aa_composer.js])

### Summary
`dryRunPrimaryAATrigger` (aa_composer.js:272-306) is reachable by an unprivileged remote peer via the `light/dry_run_aa` network command [1](#0-0)  and is also invoked automatically for every unit that triggers an AA, right before the real commit, when `conf.bDryRunNewTriggers` is enabled [2](#0-1) . Unlike the real trigger-processing path, which is always serialized behind the `['aa_triggers']` mutex [3](#0-2) , `dryRunPrimaryAATrigger` takes no such lock — it only opens its own DB connection and later issues `ROLLBACK` [4](#0-3) . However, `handleTrigger` still mutates the shared, process-global in-memory caches in `storage.js` (`assocUnstableUnits`, `assocBestChildren`, etc.) as a side effect of composing/“posting” the dry-run response unit, and `revertResponsesInCaches` is expected to undo this by looking the unit back up and calling `storage.forgetUnit` [5](#0-4) .

### Finding Description
`revertResponsesInCaches` reads a shared cache entry and immediately dereferences it without checking that it still exists:
```
var objFirstUnit = storage.assocUnstableUnits[first_unit];
var parent_units = objFirstUnit.parent_units;
arrResponseUnits.forEach(storage.forgetUnit);
``` [6](#0-5) 

`storage.forgetUnit` itself unconditionally dereferences `assocUnstableUnits[unit].parent_units`:
```
function forgetUnit(unit){
	console.log('forgetting unit '+unit);
	if (!conf.bLight){
		console.log('parents', assocUnstableUnits[unit].parent_units);
``` [7](#0-6) 

Because `dryRunPrimaryAATrigger` does not hold the `['aa_triggers']` or `['write']` mutex that every other mutator of these caches holds (`handleAATriggers`/`handlePrimaryAATrigger` [8](#0-7) , `markMcIndexStable` which moves/deletes entries from `assocUnstableUnits` as units stabilize [9](#0-8) , and `writer.saveJoint`’s cache updates [10](#0-9) ), an unprivileged remote party can trigger a dry run whose fake response-unit entry in `assocUnstableUnits`/`assocBestChildren` is concurrently deleted or reshuffled by one of these locked, legitimately-running operations (unit stabilization, purge/forget of another unit, or the real AA trigger for the same unit). When `revertResponsesInCaches` (or `forgetUnit`) then runs on the stale/freed key, it dereferences `undefined`, causing an unhandled exception in a hot code path shared by every full node that processes AA triggers or serves `light/dry_run_aa`, and — more importantly — leaving the in-memory unit-graph caches (`assocUnstableUnits`, `assocBestChildren`, `assocStableUnits`) in a partially-reverted, inconsistent state relative to the SQL data, since the cache mutations from the dry run are not confined to the rolled-back SQL transaction. These caches are authoritative inputs to main-chain construction (`main_chain.js`) and inclusion/ancestry checks (`graph.js`), i.e., to stability determination.

This is the closest structural analog in ocore to CVE‑2022‑0460 (Chrome's Window Dialogue UAF): a transient object (the dry-run fake unit props) is referenced from a shared structure, gets torn down by another concurrently-running, differently-synchronized code path, and is then used/dereferenced afterward.

### Impact Explanation
If the stale-reference access does not simply throw (e.g., in code paths that use `if (assocUnstableUnits[x])` guards elsewhere but not here), the desynchronization between the SQL-backed unit state and the reverted-but-not-fully-cleaned in-memory caches can make different nodes disagree about which units are free/stable, or crash the process handling `light/dry_run_aa` or automatic pre-commit dry runs — both of which map to “node disagreement on validity or stability” or “a network unable to confirm new units” per the accepted impact categories. Because `light/dry_run_aa` is served to any connected light client and the pre-commit dry run runs for every unit sent to any AA address, the trigger surface is broad and requires no special privilege.

### Likelihood Explanation
Triggering requires only: (1) sending a `light/dry_run_aa` request (or a normal payment/trigger to any AA address while `conf.bDryRunNewTriggers` is enabled) targeting an AA address, timed so that it races with the address’s real AA-trigger execution (`handleAATriggers`) or with MC stabilization deleting the referenced unit from `assocUnstableUnits`. Both of these events happen routinely and repeatedly (every stabilized MCI runs `handleAATriggers`; dry runs happen on essentially every unit sent to an AA). An attacker fully controls the timing of their own `light/dry_run_aa` requests and can flood them to increase race-window hits, making exploitation with moderate reliability plausible, though winning the exact race window against the internal single-threaded event loop’s interleavings has some non-determinism.

### Recommendation
- Have `revertResponsesInCaches` (and `storage.forgetUnit`) defensively check `if (!objFirstUnit) return;` / `if (!assocUnstableUnits[unit]) return;` before dereferencing, instead of assuming existence.
- Serialize `dryRunPrimaryAATrigger` (and `estimatePrimaryAATrigger`) behind the same `['aa_triggers']`/`['write']` mutex used by the real trigger-execution and stabilization code paths, so dry-run cache mutation/reversion cannot interleave with concurrent real mutation of `assocUnstableUnits`/`assocBestChildren`.
- Alternatively, make dry-run cache mutations fully local (e.g., operate on a cloned/shadow cache) rather than mutating the shared global `storage` caches at all, eliminating the need for revert logic entirely.

### Proof of Concept
1. Deploy an AA address `A` on a full node that also serves light clients (`light/dry_run_aa` enabled) and has `conf.bDryRunNewTriggers = true`.
2. From a light client, continuously send `light/dry_run_aa` requests targeting `A` in a tight loop (no cost to the attacker, since it never commits) — see handler at [1](#0-0) .
3. Concurrently, as an ordinary unprivileged unit poster, repeatedly send small payments to `A` so that `A` receives frequent real AA triggers, causing `handleAATriggers`/`handlePrimaryAATrigger` to run frequently under the `['aa_triggers']` mutex [8](#0-7) , and so that MC stabilization frequently calls `markMcIndexStable`, deleting entries from `storage.assocUnstableUnits` [9](#0-8) .
4. Because `dryRunPrimaryAATrigger` never acquires these locks, some of its `revertResponsesInCaches` calls will read `storage.assocUnstableUnits[first_unit]` after the corresponding key has already been removed/replaced by the concurrently-running, mutex-protected real path, producing an unhandled `TypeError` (dereferencing `undefined.parent_units`) or leaving `assocBestChildren`/`assocUnstableUnits` inconsistent with the SQL-backed unit graph.
5. Repeat under load to reliably reproduce the race and observe process crash or cache corruption reflected in subsequent stability/inclusion computations (`graph.js` / `main_chain.js`).

Note: I was not able to fully inspect `sendUnit`'s exact cache-mutation code inside `aa_composer.js` (the grep for `assocUnstableUnits[`/`assocBestChildren[` assignments inside that file returned only 2 matches that I could not expand further before the tool budget ran out), so the precise mechanism by which the dry-run path inserts entries into `storage.assocUnstableUnits`/`assocBestChildren` is inferred from `revertResponsesInCaches`’s need to call `storage.forgetUnit` on the fake response units, rather than directly confirmed by reading the insertion code. A Devin session with full file access should verify this insertion point before treating the PoC as fully validated.
