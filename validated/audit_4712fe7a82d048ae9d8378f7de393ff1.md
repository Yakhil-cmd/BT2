### Title
Stack-scoped ApiClient token can read *any* stack's deploy status via CCMenu endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides the stack-resolution helper inherited from `Shipit::Api::BaseController` in a way that removes the scope enforcement that binds an `ApiClient` token to a single `Stack`. This breaks the trust binding: `stack a token authorises == stack it touches`.

### Finding Description
`Shipit::ApiClient` supports being scoped to a single stack (`belongs_to :stack, optional: true`), and `Shipit::Api::BaseController` enforces this scope everywhere stacks are resolved: [1](#0-0) 

`stacks` restricts the queryable set to `current_api_client.stack_id` when the authenticated client is scoped to a stack, and `stack` (the singular helper used by resource controllers) is derived from that already-scoped `stacks` relation. This is exactly how the intended scoping is verified in the test suite ("an api client scoped to a stack will only see that one stack").

`Shipit::Api::CCMenuController`, however, defines its **own** `stack` method that bypasses `stacks` entirely and resolves the stack directly from the unscoped `Stack` model: [2](#0-1) 

`authenticate_api_client` here only verifies the `token` param cryptographically via `ApiClient.authenticate`, and the class-level `require_permission :read, :stack` only checks that `"read:stack"` is present in `current_api_client.permissions` — it never checks that the requested `stack_id` matches `current_api_client.stack_id`. So the only place stack-scoping could be enforced (the `stack` helper) is the exact method that was overridden to skip the scoping.

Before vs. after the equality that should hold:
- Before (intended): `current_api_client.stack_id == stack.id` for every read served to that client.
- After (actual in `CCMenuController#show`): `stack = Stack.from_param!(params[:stack_id])`, independent of `current_api_client.stack_id`.

A holder of any stack-scoped, `read:stack`-permitted `ApiClient` token (e.g., the `here_come_the_walrus` type client, or any CCMenu-style client an admin restricts to one stack) can supply a different `stack_id` in the request path and read that other stack's latest deploy/rollback status, defeating the per-stack scoping that is otherwise enforced uniformly by `BaseController`.

### Impact Explanation
This escalates an authorization boundary: a low-privilege, single-stack-scoped API credential gains unauthenticated-for-that-resource read access to deploy/build state of every other stack in the Shipit instance (stack name, environment, last deploy status/timestamp, running state) via `Shipit::Api::CCMenuController#show`. This matches the in-scope "High" category: escalation of a token's authorized stack scope to read stack state/deploy output it was never granted.

### Likelihood Explanation
Any party in possession of a valid, stack-restricted `ApiClient` token (a routine, low-privilege credential intentionally scoped by administrators to limit blast radius) can trivially trigger this by changing the `stack_id` path parameter on the CCMenu XML endpoint — no other secret, session, or elevated permission is required beyond the token itself.

### Recommendation
Remove the custom `stack` override in `Shipit::Api::CCMenuController` (or reimplement it using the inherited, scope-aware `stacks` relation, e.g. `stacks.from_param!(params[:stack_id])`) so that stack resolution is always constrained by `current_api_client.stack_id`, consistent with `Shipit::Api::BaseController`.

### Proof of Concept
1. Admin creates (or the system creates, e.g. via `CCMenuUrlController`/console) an `ApiClient` with `permissions: ['read:stack']` and `stack_id` set to Stack A only.
2. Attacker/holder of that token issues:
   `GET /api/stacks/<STACK_B_ID>/ccmenu.xml?token=<TOKEN>`
3. `authenticate_api_client` succeeds (token is valid), `require_permission :read, :stack` succeeds (`read:stack` present), and `stack` resolves to Stack B via `Stack.from_param!(params[:stack_id])`, bypassing the `stacks` scope check.
4. Response renders Stack B's latest deploy/rollback status even though the token was only authorized for Stack A.
