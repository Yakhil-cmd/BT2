This confirms the mismatch: the webhook signature-selection organization (`repository_owner`, derived from `params.dig('repository','owner','login') || params.dig('organization','login')`) is decoupled from the repository the handlers actually act on (`payload.dig('repository','full_name')` in `Handler#repository_name`, used by `PushHandler`, `ClosedHandler`, `LabeledHandler`, `OpenedHandler`, etc.). Both fields live in the same signed JSON body, but nothing cross-checks that the `repository.owner.login` used to pick the webhook secret matches the `repository.full_name` whose Stack gets written to.

### Title
Webhook signature is verified against the payload's claimed organization, not the repository actually mutated, enabling cross-organization writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to validate the HMAC signature against using `repository_owner`, which is read from the same untrusted JSON body it is about to validate (`params.dig('repository','owner','login') || params.dig('organization','login')`). Handlers such as `PushHandler`, `ClosedHandler`, `LabeledHandler`, `OpenedHandler`, and `ReopenedHandler` locate the `Stack`/`Repository` to mutate using a *different* field of the very same payload: `payload.dig('repository', 'full_name')` (via `Handler#repository_name`/`#stacks`) [1](#0-0) . Nothing enforces that `repository.owner.login` and `repository.full_name` belong to the same organization.

### Finding Description
`verify_signature` picks the app config to check against based on `repository_owner`: [2](#0-1) [3](#0-2) 

Because Shipit supports multiple GitHub App configs keyed by organization (`Shipit.github(organization:)`), each org's App has its own independently known `webhook_secret` [4](#0-3) [5](#0-4) . If Shipit is configured for multiple organizations, whoever administers the GitHub App for org "A" knows (or can retrieve/reset) org A's `webhook_secret` and can therefore compute a valid `X-Hub-Signature` for **any** JSON body, as long as `repository.owner.login` in that body says "A" (so `verify_signature` selects A's secret and the HMAC matches).

Once the signature check passes, `WebhooksController#create` dispatches the same raw payload to handlers, none of which re-check the organization used for signing. Instead they resolve the target `Repository`/`Stack` purely from `repository.full_name`: [6](#0-5) [7](#0-6) [8](#0-7) 

An attacker who controls org A's GitHub App (registered legitimately in Shipit's multi-org config) can therefore forge a signed webhook claiming `"repository": {"owner": {"login": "A"}, "full_name": "VictimOrg/victim-repo"}`, `"ref": "refs/heads/main"`, `"after": "<attacker-chosen-sha>"`. `verify_signature` succeeds (org A's secret matches), and `PushHandler` will call `stack.sync_github(expected_head_sha: params.after)` on any `Stack` backed by `VictimOrg/victim-repo`, driving a `GithubSyncJob` against the victim repository under the attacker's control — a cross-organization write into a stack the attacker was never granted access to.

### Impact Explanation
This breaks the binding "organization that authenticated == repository that is written": signature verification authenticates one organization, while the payload's `repository.full_name` field determines which (potentially unrelated) repository/stack is mutated. The impact matches the specified High/Critical bar of cross-repository writes and effectively an unauthorized deploy pipeline trigger (via `sync_github`/`GithubSyncJob`, which can cascade into commit/status ingestion and merge-queue processing for the victim stack).

### Likelihood Explanation
Requires Shipit to be configured with more than one GitHub organization (`config/secrets*.yml` supports this natively, as shown by the shipped multi-org example) and requires the attacker to control (create/administer) one of those configured GitHub Apps — a low bar for a party who is legitimately allowed to register an org with the shared Shipit instance, but who is an "unprivileged attacker" with respect to the victim organization/repository. No Shipit session, `ApiClient` token, or repository write access on GitHub is needed for the victim repo; only knowledge of one configured org's `webhook_secret`.

### Recommendation
Verify that the organization whose secret validated the signature actually matches (or is authorized for) the `repository.full_name`/`organization.login` fields the handlers act upon, e.g. re-derive `repository_owner` strictly from `repository.full_name`'s owner segment and require it be identical to the owner used to select the webhook secret, rejecting the request otherwise (422) before dispatching to handlers.

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.yml`: `VictimOrg` (has a real stack for `VictimOrg/victim-repo`) and `AttackerOrg` (attacker creates/administers this GitHub App and therefore knows its `webhook_secret`).
2. Attacker crafts JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": { "owner": { "login": "AttackerOrg" }, "full_name": "VictimOrg/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(AttackerOrg_webhook_secret, body)>` and sets `X-Github-Event: push`.
4. POST to `/webhooks`. `verify_signature` resolves `repository_owner` = `"AttackerOrg"`, fetches `Shipit.github(organization: "AttackerOrg")`, and the signature validates successfully [9](#0-8) .
5. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("VictimOrg/victim-repo")` and calls `stack.sync_github(expected_head_sha: "deadbeef...")` on the victim's stack [7](#0-6) , even though the request was never signed by `VictimOrg`.
