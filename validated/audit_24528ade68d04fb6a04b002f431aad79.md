Based on the code, this claim does not hold up.

**Capitalization accounting is correct for the burn path.** In `distribute_epoch_rewards_in_partition`, capitalization is only ever *increased* by `stake_reward_lamports_minted` (the amount actually credited to surviving stake accounts) — never by `stake_reward_lamports_burned`. Since burned inflation rewards were never minted into any account in the first place (the `account.checked_add_lamports()` call in `build_updated_stake_reward` operates on a local clone that is discarded on the `Err` branch and never passed to `store_accounts`), there is nothing to "subtract" — capitalization simply never receives that phantom credit. [1](#0-0) 

The `Err` branch in `store_stake_accounts_in_partition` only increments local burn counters, it never touches capitalization or credits any account: `stake_reward_lamports_burned += stake_reward_amount` — this lamport amount is simply forfeited, not minted anywhere. [2](#0-1) 

The `block_reward_lamports_burned` case is different in kind — block rewards are *pre-existing* lamports already resident in the `EpochRewards` sysvar account (added via `checked_add_lamports` in `create_epoch_rewards_sysvar` without touching capitalization). [3](#0-2) 

So when block rewards are burned instead of distributed, those already-counted lamports need to be removed from both the sysvar account and capitalization — which is exactly what the `fetch_sub(block_reward_lamports_burned, ...)` does, matched by `update_epoch_rewards_sysvar` debiting `debit_block_reward_lamports = block_reward_lamports_distributed + block_reward_lamports_burned` from the sysvar account.
