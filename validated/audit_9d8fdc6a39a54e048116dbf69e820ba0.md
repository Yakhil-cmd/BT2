### Title
Signature verification keys on `repository.owner.login`/`organization.login` while every handler resolves its write target from the independent `repository.full_name` field, letting a valid signer for one configured GitHub organization forge webhook events against a stack belonging to a different organization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `GithubApp` (and therefore which `webhook_secret`) to validate the HMAC signature against using `repository_owner`, computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. [1](#0-0) [2](#0-1)  Every event handler, however, resolves the actual `Stack`/`Repository` to act on from a completely different JSON field, `repository.full_name`, via `Handler#repository_name` and `Repository.from_github_repo_name`. [3](#0-2) [4](#0-3)  Because the signature covers the raw request body but nothing in the controller or handlers cross-checks that `repository.owner.login` and the owner portion of `repository.full_name` refer to the same organization, the field used for *authentication* is disjoint from the field used to select *the repository that is written*.

### Finding Description
Shipit supports multiple GitHub organizations, each with its own `app_id`/`webhook_secret` configured under `config/secrets.yml`. [5](#0-4)  `WebhooksController#verify_signature` fetches the `GithubApp` for `repository_owner` and calls `verify_webhook_signature`, which HMACs the raw payload against that organization's `webhook_secret`: [6](#0-5) 

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  algorithm, signature = signature.split("=", 2)
  return false unless algorithm == 'sha1'
  SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
end
```

If the signature validates, `create` dispatches the entire raw JSON body to every registered handler for the event, unmodified: [7](#0-6) 

Each handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, `MembershipHandler`, the `pull_request/*` handlers) inherits `stacks`/`repository_name` from `Handler`, which looks up the target purely from `payload.dig('repository', 'full_name')`: [3](#0-2) 

`Repository.from_github_repo_name` splits that string on `/` and does a straight `find_by(owner:, name:)` lookup, with no relation to the organization whose secret was used to authenticate the request: [4](#0-3) 

The equality that the design implicitly assumes but never enforces is:
`organization authenticated by verify_signature (repository.owner.login) == organization owning the repository actually written (repository.full_name)`

Before the report class of bug: this equality holds in practice because GitHub itself always emits internally-consistent payloads (the `owner.login` and `full_name` always describe the same repo). After considering a party who can freely construct the raw POST body and sign it with a `webhook_secret` they legitimately hold for **their own configured organization** (`OrgA`), the binding breaks: they can set `repository.owner.login` (or `organization.login`) to `"OrgA"` so `verify_signature` selects `OrgA`'s secret and the HMAC matches, while independently setting `repository.full_name` to `"OrgB/victim-repo"` — any other organization/repo that happens to have a `Stack` configured in this Shipit instance. The controller only checks that the signature matches *some* configured organization's secret; it never checks that this organization is the one whose repository is subsequently mutated.

### Impact Explanation
Once the forged, validly-signed request passes `verify_signature`, the handler for the declared `X-Github-Event` operates on `OrgB`'s stack using attacker-supplied data:
- `PushHandler` calls `stack.sync_github(expected_head_sha: params.after)` on every non-archived `OrgB` stack matching the branch, letting the attacker drive `GithubSyncJob` with an arbitrary `after` SHA of their choosing. [8](#0-7) 
- `StatusHandler`/`CheckSuiteHandler`/pull-request handlers similarly write commit statuses, check-suite results, and PR/label state for `OrgB`'s repositories/stacks, which downstream code uses to decide whether commits are "safe" to deploy or merge.

This crosses the exact boundary this scan is scoped to catch: cross-repository/cross-organization writes triggered without ever having legitimate credentials or a GitHub App installation on the victim organization — an unauthorized deploy/ship pathway driven purely by a mismatch between the field checked for authentication and the field used to select the write target.

### Likelihood Explanation
The only prerequisite is that the attacker administers (or has webhook-secret-level control of) at least one organization that this Shipit instance is configured to serve, which is a normal, unprivileged position in a multi-tenant Shipit deployment as documented in `docs/setup.md`. [5](#0-4)  No access to `OrgB`'s secret, GitHub App private key, or any Shipit session/API token is required — only the ability to compute a valid HMAC over an arbitrary self-crafted body, which is exactly what owning `OrgA`'s `webhook_secret` grants. The webhook endpoint is unauthenticated aside from this signature check, and `WebhooksController` performs no additional binding between the authenticated organization and the resolved repository. [9](#0-8) 

### Recommendation
After signature verification succeeds for `repository_owner`, the controller (or `Handler#repository_name`) must verify that the owner segment of `repository.full_name` (and `organization.login`, if present) matches the `repository_owner`/organization that produced a valid signature, rejecting the request (422) on mismatch. Alternatively, resolve the target repository directly from the same field used for authentication (`repository.owner.login`) rather than trusting a separate, unauthenticated-relative `full_name` field.

### Proof of Concept
1. Attacker legitimately configures `OrgA` in a multi-org Shipit deployment and knows `OrgA`'s `webhook_secret` (as its own GitHub App owner). [10](#0-9) 
2. Attacker crafts a `push` event JSON body:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen sha>",
     "repository": {
       "owner": { "login": "OrgA" },
       "full_name": "OrgB/victim-repo"
     }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(OrgA_webhook_secret, raw_body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` computes `repository_owner = "OrgA"`, fetches `OrgA`'s `GithubApp`, and the signature matches — request passes. [1](#0-0) 
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("orgb/victim-repo")`, finds `OrgB`'s stacks, and calls `stack.sync_github(expected_head_sha: <attacker sha>)` on a repository the attacker never had legitimate access to. [8](#0-7)

```ruby
# frozen_string_literal: true

module Shipit
  class WebhooksController < ActionController::Base
    skip_before_action :verify_authenticity_token, raise: false
    before_action :check_if_ping, :drop_unhandled_event, :verify_signature

    respond_to :json

    def create
      params = JSON.parse(request.raw_post)
      Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }

      head(:ok)
    end

    private

    def drop_unhandled_event
      # Acknowledge, but do nothing
      head(204) unless Shipit::Webhooks.for_event(event).present?
    end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
  end
```

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

      private_key:

        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
