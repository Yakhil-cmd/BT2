### Title
Self-referential `MintType::HolderOf` mint gate lets a single actor drain an entire "holder-gated" NFT collection with only one externally-held token - (File: substrate/frame/nfts/src/lib.rs)

### Summary
`pallet-nfts` implements a "token-gated" mint mode, `MintType::HolderOf(collection_id)`, which only allows an account to mint an item in collection `C` if it owns (and has not previously used) an item from `collection_id`. The pallet does track per-item, per-target usage via a `PalletAttributes::UsedToClaim` attribute to stop the *same* witness item being reused against the *same* target collection twice. However, neither `do_update_mint_settings` nor collection creation validates that `collection_id != C` (the collection being gated) or that a chain of mutually-gating collections cannot be assembled. This is structurally the same missing check that the ERC721SeaDrop report flagged as "Scenario 1" (self-registration of an allowed token as its own gate) and generalizes to "Scenario 2" (mutually gating collections).

### Finding Description
`MintType::HolderOf(CollectionId)` lets the collection issuer restrict minting to holders of items from another collection [1](#0-0) . The `update_mint_settings`/`do_update_mint_settings` path that sets this type performs only a permission check (`CollectionRole::Issuer`) and never validates the referenced `collection_id` against the collection being configured [2](#0-1) , and the dispatchable wrapper adds no further validation [3](#0-2) .

When actually minting, the `mint` extrinsic's `HolderOf(collection_id)` branch: checks the caller owns `owned_item` in `collection_id`, checks a `PalletAttributes::UsedToClaim(collection)` attribute has not already been set for `(collection_id, owned_item)`, and then sets that attribute [4](#0-3) . This anti-replay check only prevents the *same specific item* from being reused as a witness against the *same target collection* — it does not prevent an attacker from continuously minting brand‑new items in `C` and immediately re‑using each freshly minted item as the witness for the next mint, when `collection_id == C` (self-referential) or when two collections `N1`/`N2` are configured to mutually gate each other.

Concretely, with `collection_id == collection == C` (self-referential gate):
1. Attacker owns one item `t0` in an unrelated collection `A`, and uses it as witness to mint item `i0` in `C` (marks `(A, t0) -> UsedToClaim(C)`).
2. Attacker now owns `i0` in `C` and uses **`i0` itself** as the witness to mint `i1` in `C`, since `HolderOf(C)` only requires ownership of *some* item in `C`. The `AlreadyClaimed` check keys on `(C, i0, UsedToClaim(C))`, which was never set (only `(A, t0, UsedToClaim(C))` was set), so it passes, and `i0` is now marked `(C, i0) -> UsedToClaim(C)`.
3. Repeat using `i1`, `i2`, … until `collection_details.items == max_supply`, exhausting the entire "holder-gated" collection allocation from a single starting external token.

The same pattern with two collaboratively-gating collections (`N1` gates on `N2` and vice versa) lets a single holder of one item alternate mints between the two, draining both up to `max_supply`, mirroring "Scenario 2" of the report.

### Impact Explanation
The intended design goal of `MintType::HolderOf` — restricting minting to a *broad set* of distinct external holders — is defeated: one actor, starting from a single externally-held item, can mint out the *entire* `max_supply` of a self- or mutually-gated collection alone. This is a fairness/design-integrity break of the gating mechanism (analogous to the Medium-severity ERC721SeaDrop finding), not a funds-theft or unbacked-issuance bug: each mint still reserves the configured `ItemDeposit` [5](#0-4)  and pays any configured `price` [6](#0-5) , so there is no free minting or accounting corruption — the loss is that other intended participants are excluded from the "holder-gated" allocation, and the collection issuer's distribution design is subverted.

### Likelihood Explanation
Likelihood is moderate: it requires an issuer to configure `MintType::HolderOf(collection_id)` where `collection_id` equals the collection itself, or to set up two collections that mutually gate each other — both configurations are permitted today with no validation, and the exploit itself requires only ordinary signed `mint` calls (no privileged role, no governance).

### Recommendation
Add a validation step in `do_update_mint_settings` (and any collection-creation path that sets `mint_settings` directly) rejecting `MintType::HolderOf(collection_id)` where `collection_id == collection`. Document the residual risk of mutually-gating collection chains (as OpenSea/Spearbit did for the analogous SeaDrop case) since a fully general cycle-detection check across independently configured collections is impractical to enforce on-chain.

### Proof of Concept
No local integration test was executed; this is a static-analysis-based structural analog derived from reading `substrate/frame/nfts/src/lib.rs` (mint dispatchable, lines 826-938 and 1713-1727) and `substrate/frame/nfts/src/features/settings.rs` (lines 84-114), confirming the absence of a self-reference/no-cycle check. A concrete Rust reproduction would: (1) `force_create` collection `A` (public mint) and mint item `t0` to attacker; (2) `force_create` collection `C` with `update_mint_settings` set to `MintType::HolderOf(C)` (self-referential, passes today since no rejection exists); (3) `mint` item `i0` in `C` using witness `(A, t0)`; (4) repeatedly `mint` further items in `C` using the immediately-preceding minted item in `C` itself as witness, verifying `AlreadyClaimed` never fires and the loop runs until `MaxSupplyReached`, all from the single external item `t0`.
