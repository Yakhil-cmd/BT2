### Title
`StatusHandler#process` writes `Status` records by `sha` alone, allowing commits in one repository's stacks to be mutated via a webhook payload naming a different `repository.full_name` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` queries `Commit.where(sha: params.sha)` across the entire `commits` table and calls `commit.create_status_from_github!(params)` on every match, without ever calling the inherited `Handler#stacks`/`repository_name` methods to scope the lookup to the payload's own repository. Any commit sha that happens to exist under a different, unrelated stack (e.g. via shared ancestry between a fork and its upstream) receives a `Status` write attributed to that unrelated repository's commit.

### Finding Description
Binding that should hold: `Handler#stacks` (i.e. `Repository.from_github_repo_name(payload['repository']['full_name'])&.stacks`) should equal, or at minimum bound, the set of stacks whose commits get mutated by the handler. In code: [1](#0-0) 

is defined on the base `Handler` class specifically to scope work to the repository named in the payload, and is used by sibling handlers. `StatusHandler#process`, however, never references `stacks` or `repository_name` at all: [2](#0-1) 

`Commit.where(sha: params.sha)` is a global, cross-tenant query - `sha` has no uniqueness constraint scoping it to a repository/stack, and `Commit#create_status_from_github!` performs the mutation directly through `stack_id` derived from whatever `Commit` row matched, not from the payload's repository: [3](#0-2) 

The only gate before this code runs is `WebhooksController#verify_signature`, which validates the HMAC signature against `Shipit.github(organization: repository_owner)`, where `repository_owner` is taken from the payload's own `repository.owner.login`: [4](#0-3) [5](#0-4) 

This check authenticates that the payload genuinely came from GitHub for the repository named in the payload - it does **not** bind the `sha` field to any repository/stack ownership. So a webhook that is 100% legitimately signed for repository A (e.g. an attacker's own fork) can carry a `sha` that also exists in repository B's commit history (identical git objects are common between a fork and its upstream prior to divergence). Since `StatusHandler` never intersects the `sha` lookup with `stacks` for repository A, a `Status` gets attached to repository B's `Commit` row - a real cross-repository mutation.

Existing guards checked and found insufficient for this specific issue: `verify_signature`/`drop_unhandled_event` authenticate *that a repository sent a webhook*, not *that the sha belongs to that repository*; `ExplicitParameters` only validates payload shape (`sha` as `String`), not ownership; there is no `stacks`/`repository_name` call anywhere in `status_handler.rb` to close this gap.

### Impact Explanation
An attacker who owns/controls a repository that is able to successfully pass `verify_signature` (i.e., its owner/org is recognized by Shipit's configured GitHub App/organization) can cause `Status` rows to be created against commits belonging to a *different* tracked stack, purely by sha coincidence with shared git history (fork scenario). This is a cross-repository data-integrity/authorization bypass: a `Status` write (which feeds into `Commit#deployable?`, CI gating, and can unblock `ContinuousDeliveryJob`/merges for the victim's stack) is attributed to a repository that never authenticated ownership of that commit. This matches the "payload for one repository mutating another's stack/commit" Critical category. Repeatable for every shared/inherited commit sha between the attacker's repo and any victim stack tracked by the same Shipit instance.

### Likelihood Explanation
Requires: (1) the attacker's own repository/org must already be recognized by `Shipit.github(organization: ...)` (i.e., onboarded to the same GitHub App/org configuration as the victim stack) so `verify_signature` succeeds - this is the main precondition and was not fully re-verified in this session (the internals of `Shipit.github`/`GithubApp#verify_webhook_signature` were not traced to confirm whether the webhook secret is global to the App or scoped per organization); (2) a real sha collision, most realistically achieved by forking a public repository tracked by Shipit and posting a GitHub commit status on an inherited/shared-ancestry commit in the fork, which any GitHub user can do on their own fork with no special privilege. Given these preconditions, the exploit is cheap and repeatable per shared commit.

### Recommendation
In `StatusHandler#process`, intersect the `Commit` lookup with the payload's own stacks, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalently `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, mirroring the scoping pattern already established by `Handler#stacks`/`repository_name`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual)
test "process does not mutate commits outside the payload's repository" do
  victim_stack = shipit_stacks(:shipit)
  victim_commit = victim_stack.commits.create!(sha: 'a' * 40, message: 'victim commit')

  attacker_repo_payload = {
    'repository' => { 'full_name' => 'attacker/unrelated-repo' },
    'sha' => victim_commit.sha,
    'state' => 'success',
    'context' => 'ci/attacker'
  }

  assert_no_difference -> { victim_commit.statuses.count } do
    Shipit::Webhooks::Handlers::StatusHandler.new(attacker_repo_payload).process
  end
end
```
Running this against the current implementation fails: `victim_commit.statuses.count` increases by 1, proving `Commit.where(sha: params.sha)` matched and mutated a commit belonging to a stack never referenced by `attacker/unrelated-repo`.

      ].join(' '))
