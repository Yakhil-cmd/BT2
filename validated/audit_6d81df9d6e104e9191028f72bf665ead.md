### Title
Webhook signature verification is scoped to the wrong payload field, allowing cross-organization/cross-repository webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and thus which `webhook_secret`) to validate a webhook against using `repository_owner`, derived from `params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`. But the handler that actually performs the write — `Shipit::Webhooks::Handlers::Handler#repository_name` — resolves the target repository from an entirely different, unrelated payload field: `payload.dig('repository', 'full_name')`. Nothing ties these two fields together or re-verifies that the "owner" used for signature selection matches the "full_name" used to select the stacks that get mutated.

### Finding Description
`verify_signature` picks the GitHub App/organization config to check the HMAC against: [1](#0-0) [2](#0-1) 

Critically, `verify_webhook_signature` treats an organization with no configured `webhook_secret` as always-valid: [3](#0-2) 

Meanwhile, every webhook handler (push, status, check_suite, …) resolves which `Stack`/`Repository` to act on using a completely different payload key — `repository.full_name` — with no cross-check against the organization/owner used for signature verification: [4](#0-3) [5](#0-4) 

This breaks the required binding: **the organization that authenticated the request ≠ the repository that is written**. An attacker can craft a JSON body where `repository.owner.login` (used only for signature-org selection) points at any organization that has `webhook_secret` unset/nil in the host app's config — this is a documented/common configuration, as shown in the shipped example config (`webhook_secret: # nil`): [6](#0-5) 

while `repository.full_name` in the same payload is set to a *different*, fully-configured organization/repository with real stacks. Because `verify_webhook_signature` returns `true` unconditionally when that first organization has no secret, the request passes verification with **no valid signature at all**, and the handler then acts on the second (attacker-chosen) `full_name` target.

### Impact Explanation
This is an authentication bypass on the webhook ingress path leading to unauthorized cross-repository writes: an unauthenticated attacker can trigger `GithubSyncJob` (push handler), mutate commit `Status` rows, trigger `RefreshCheckRunsJob` (check_suite handler), or create/delete `Membership`/`Team` records (membership handler) for a stack/repository/org that is *not* the one whose (missing) secret was used to pass verification. Because these actions influence what Shipit believes is deployable/synced, and CI/status data feeds directly into deploy-gating decisions, this can be leveraged toward unauthorized deploy behavior without ever possessing any organization's real `webhook_secret`.

### Likelihood Explanation
Requires only that the deployment configures at least one GitHub organization/App without a `webhook_secret` — a state the engine's own example configuration explicitly shows as a valid, supported setup (`webhook_secret: # nil`). No credentials, tokens, or repository access are needed; the attacker only needs to POST to the public `/webhooks` endpoint with a crafted `X-Github-Event` header and JSON body.

### Recommendation
Bind signature verification to the same identity that is used to resolve write targets: verify using the organization/owner embedded in `repository.full_name` (or otherwise require both `repository.owner.login` and the owner segment of `repository.full_name` to match) before any handler is invoked. Additionally, do not default `verify_webhook_signature` to `true` when `webhook_secret` is blank for an organization that isn't the one being targeted by the payload — at minimum, reject payloads whose `repository_owner` used for verification does not match the owner encoded in `repository.full_name`.

### Proof of Concept
1. Host app has two orgs configured: `orgA` (no `webhook_secret`) and `orgB` (has a real stack, `webhook_secret` set, no attacker knowledge of it).
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "orgB/real-repo"
  }
}
```
No `X-Hub-Signature` header, or any arbitrary value, is required.
3. `WebhooksController#repository_owner` resolves to `orgA`; `Shipit.github(organization: 'orgA').verify_webhook_signature` returns `true` because `orgA` has no `webhook_secret` [7](#0-6) .
4. `PushHandler` is invoked and resolves target stacks via `repository.full_name` = `orgB/real-repo`, enqueuing `GithubSyncJob` for `orgB`'s real stack — despite the request never being validated against `orgB`'s webhook secret [4](#0-3) .

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
