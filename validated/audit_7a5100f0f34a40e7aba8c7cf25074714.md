### Title
Membership webhook mutates arbitrary `Team` records by `github_id` with no cross-check against the signing organization - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#find_or_create_team!` looks up `Team` solely by the numeric `params.team.id` (`github_id`), and `process` then calls `team.add_member(member)` for `'added'` events without ever verifying that `params.organization.login` (the org whose secret signed the webhook) matches the `organization` already stored on that `Team` row. Any tenant/organization configured in Shipit with its own valid `webhook_secret` can sign a legitimate membership-`added` webhook naming a different org's team `github_id` and an arbitrary `member.login`, causing that member to be added to a `Team` that belongs to a different, unrelated GitHub organization.

### Finding Description
The broken binding: the code treats `signing_org(params.organization.login) == team.organization` as true, but this equality is never checked. In reality `find_or_create_team!` only enforces `Team.github_id == params.team.id`: [1](#0-0) 

`team.organization`/`slug`/`name` are assigned only inside the `find_or_create_by!` block, i.e. only on first creation; on every subsequent webhook for an already-existing `github_id`, none of these fields — nor the payload's `organization.login` — are re-checked against the found record: [2](#0-1) 

Signature verification (`WebhooksController#verify_signature`) selects the GitHub App/secret to verify against using `repository_owner`, which for a membership event (no `repository` key) falls back to `params.organization.login`: [3](#0-2) 

So the signature check only proves "this payload was signed with organization `params.organization.login`'s webhook secret" — it says nothing about `params.team.id` actually belonging to that organization. `GitHubApp#verify_webhook_signature` performs a pure HMAC comparison keyed to that org's configured secret: [4](#0-3) 

Exploit flow: In a multi-tenant Shipit deployment (`Shipit.github(organization:)` supports per-organization configs, see `github_app_config`), an attacker who legitimately administers/controls Organization A's GitHub App/webhook config (and thus knows Org A's `webhook_secret`) can:
1. Learn or guess the numeric `github_id` of a `Team` belonging to victim Organization B that is already present in `Shipit.github_teams` (this Team was created earlier from a real Org B `membership` event).
2. POST to `/webhooks` with `X-Github-Event: membership`, a body `{"action":"added","team":{"id":<victim_team_github_id>,"slug":"totally-unrelated","name":"Nonsense","url":"http://x"},"organization":{"login":"orgA"},"member":{"login":"attacker-controlled-login"}}`, signed with Org A's real `webhook_secret`.
3. `verify_signature` passes because the signature legitimately matches Org A's secret.
4. `find_or_create_team!` finds the pre-existing `Team` row by `github_id` alone (owned by Org B), ignoring that the signing org is Org A and that slug/name/url don't match.
5. `team.add_member(member)` adds the attacker-chosen user to that Org-B-authorized Team's `members`.

Existing guards fail to close this because they check *authenticity of the sender* (signature) but not *authorization to mutate this specific resource* (team-organization binding). `drop_unhandled_event`/`check_if_ping`/`ExplicitParameters` schema only validate presence/type of fields, not cross-field consistency; `Team` has no validation tying `github_id` to `organization`; `find_or_create_by!` performs no re-sync or ownership check on the found path.

### Impact Explanation
A member is added to a `Team` object (`Shipit::Team`) that gates `Shipit.github_teams`, i.e. `User#authorized?`, which is checked by `force_github_authentication` to permit access to the entire Shipit application (deploys, rollbacks, stack management): [5](#0-4) [6](#0-5) 
This lets a party controlling one tenant's webhook secret grant an arbitrary GitHub login membership/authorization in a completely different tenant's authorized team, i.e. cross-tenant privilege escalation into `Shipit.github_teams` — matching the "escalation into `Shipit.github_teams` authorization" High-severity category (and arguably crosses into Critical territory as it can enable that user to then perform unauthorized deploys/rollbacks once authorized). It is repeatable against any `Team` row whose `github_id` is known/guessable, and the write is fully attacker-controlled (arbitrary `member.login`).

### Likelihood Explanation
This requires a genuinely multi-tenant Shipit deployment where more than one organization's GitHub App/webhook secret is configured (`secrets.github` with multiple org keys) and the attacker legitimately controls one of those organizations' webhook configuration (a plausible position for a "self-signed organization" tenant admin, not a fully external anonymous user). It further requires knowledge of the victim team's numeric `github_id`, which is a small integer, often discoverable via GitHub's public API (`GET /orgs/{org}/teams`) or previously observed webhook traffic — feasible, not purely theoretical. Given those preconditions, the attack is trivial to script and fully repeatable.

### Recommendation
In `MembershipHandler#find_or_create_team!`, verify that `params.organization.login` matches the `organization` on any pre-existing `Team` found by `github_id` before mutating membership (reject/log mismatch), and re-sync `name`/`slug`/`api_url` from the payload only when the organization matches. Additionally, `WebhooksController#verify_signature` should ensure the verified signing organization is consistent with every organization-scoped identifier used later in the handler (not just used to pick the secret).

```ruby
# test/models/shipit/webhooks/handlers/membership_handler_test.rb (conceptual)
test "membership 'added' event does not mutate a team belonging to a different organization" do
  victim_team = Shipit::Team.create!(
    github_id: 555,
    organization: 'org-b',
    slug: 'real-slug',
    name: 'Real Team',
    api_url: 'https://api.github.com/teams/555'
  )

  payload = {
    'action' => 'added',
    'team' => { 'id' => 555, 'slug' => 'totally-unrelated', 'name' => 'Nonsense', 'url' => 'http://x' },
    'organization' => { 'login' => 'org-a' }, # attacker-controlled org, signed with org-a's real secret
    'member' => { 'login' => 'attacker-controlled-login' }
  }

  Shipit::Webhooks::Handlers::MembershipHandler.new(payload).call

  victim_team.reload
  assert_equal 'real-slug', victim_team.slug          # unchanged (expected, currently true)
  assert_equal 'Real Team', victim_team.name           # unchanged (expected, currently true)
  refute victim_team.members.exists?(login: 'attacker-controlled-login')
  # currently FAILS: membership is added despite organization mismatch
end
```
This demonstrates the binding `signing_org == team.organization` is never checked, and the membership mutation succeeds against a team owned by a different organization than the one that signed the request.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
