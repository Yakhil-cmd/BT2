### Title
No global replay protection on L1 BTC lockup outpoints allows the same locked Bitcoin output to be reused across multiple `register-for-bond` calls, double-counting sats collateral - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
`register-for-bond`'s L1 path verifies BTC lockup proofs through `verify-l1-lockups` → `validate-l1-lockup`, which only deduplicates outpoints *within a single call's* `seen-outpoints` accumulator. There is no contract-level map that records previously-consumed lockup outpoints across separate transactions, so the same on-chain BTC lock (one real timelocked UTXO) can be presented as proof in more than one `register-for-bond` call, crediting `sats-total` (and therefore bond reward share / STX unlock terms) more than once for a single underlying Bitcoin commitment.

### Finding Description
In `stackslib/src/chainstate/stacks/boot/pox-5.clar`, `validate-l1-lockup` folds over the caller-supplied list of BTC outputs and rejects duplicates only via the in-call `seen-outpoints` list: [1](#0-0) 

This list is initialized fresh on every call to `verify-l1-lockups`: [2](#0-1) 

Nothing else in the contract records that a given `(txid, output-index)` has already been consumed by a prior `register-for-bond` call. The only "global" state produced by a successful registration is `protocol-bond-memberships`, keyed by `staker` (a Stacks principal), not by BTC outpoint: [3](#0-2) 

Since the timelock script commits to the staker's principal (via `construct-lockup-output-script`), the legitimate owner of a single BTC UTXO can:
1. Register for bond A using the lockup proof, locking STX and getting bond-A sats credit.
2. Wait for the existing membership to roll over or unstack (or use a second Stacks account that is separately allow-listed with the same staker-committed script logic, if the lockup script allows any staker key committed via hash), and submit the *same* BTC proof again to a different bond period or after `announce-l1-early-exit`/rollover flows, crediting `sats-total` again for BTC that was never separately re-locked.

The core equality broken: "sats credited by an L1 proof" should equal "sats actually and currently locked on Bitcoin, once." Because outpoint consumption is not tracked globally, the same locked BTC can back more than one bond's `sats-total`, inflating reward-share computations (`min-ustx-for-sats-amount`, `get-total-sbtc-staked`-style totals used in `calculate-rewards`) without a corresponding second BTC lock.

### Impact Explanation
If the same UTXO can be replayed across bond registrations, the staker's sats stake used to compute `min-ustx-for-sats-amount` and bond reward shares (`bond-distributions` / `calculate-bond-rewards` in `calculate-rewards`) is double-counted, letting an attacker claim more sBTC bond rewards than their real, currently-locked BTC collateral entitles them to. Per the scope's impact table, this is a double-counted commitment/reward, which is rated **Critical** (unbacked minting of sBTC rewards / double-counting a commitment).

### Likelihood Explanation
Likelihood is low-to-moderate: exploitation requires the attacker to control the underlying BTC UTXO and structure at least two separate `register-for-bond` calls (e.g., across different bond periods, or via rollover paths) that both accept the identical lockup proof without the intervening consumption being recorded. The `is-l1-lock`/rollover code paths (`verify-bond-rollover-window`, `bond-overlaps-new-position?`) were not fully inspected here for whether they incidentally prevent a stale/rolled-over membership from being reused with the same outpoint — this is an area of uncertainty that would need further code review (I was not able to fully trace `announce-l1-early-exit` interactions given the exploration budget).

### Recommendation
Add a durable contract map (e.g., `used-l1-lockup-outpoints`, keyed by `{txid, output-index}`) that is checked and permanently inserted in `validate-l1-lockup` (or in `register-for-bond` after a successful `verify-l1-lockups`), independent of the per-call `seen-outpoints` accumulator, so that once a specific Bitcoin output has been credited to any bond, it cannot be presented again in any future `register-for-bond` call from any account.

### Proof of Concept
Not fully constructible without confirming the rollover/early-exit state machine's exact gating; the concrete reachable sequence is:
1. Staker locks BTC into the P2WSH computed by `construct-lockup-output-script` for `staker = alice`.
2. Alice calls `register-for-bond(bondIndex=0, ..., btc-lockup=ok({outputs:[lockupProof], ...}))`, which passes `validate-l1-lockup`, credits `sats-total`, and creates `protocol-bond-memberships[alice]`.
3. After the bond-0 membership naturally rolls off (per `bond-overlaps-new-position?`/`verify-bond-rollover-window` conditions) or is exited via `announce-l1-early-exit`, Alice calls `register-for-bond` again for a later bond index, submitting the exact same `lockupProof` (same `tx`, `output-index`, `header`) — since `seen-outpoints` is re-initialized per call and there is no persistent outpoint map, `validate-l1-lockup` re-accepts it and credits `sats-total` a second time for BTC that was only ever locked once.

This flow is consistent with the existing dedup test that only asserts *intra-call* duplicate rejection: [4](#0-3) 

which explicitly documents the dedup as "per-output dedup inside `validate-l1-lockup`" — confirming no cross-call/global outpoint tracking exists.
