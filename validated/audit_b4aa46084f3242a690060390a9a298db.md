### Title
Sending native value together with an ERC20-precompile `transfer`/`transferFrom` call in `pallet-revive` permanently burns the native currency - ([File: substrate/frame/revive/src/lib.rs])

### Summary
`pallet_revive::Pallet::call` is the FRAME analog of Solidity's implicit "payable" call: a caller can attach an arbitrary native `value` to *any* destination address, including the fixed, deterministic addresses of the `pallet-assets` ERC20 precompiles. The ERC20 precompile's `transfer`/`transferFrom` handlers move the ERC20-style asset balance but never inspect or reject the attached native `value`. Because the precompile address is not backed by any real key-holder, native currency sent alongside such a call is transferred into that address's mapped account and becomes permanently unspendable - the exact bug class described in the original report (a function that logically deals with an ERC20 token but is also payable, with no guard against an accidentally attached native-currency payment).

### Finding Description
`Pallet::call` in `pallet-revive` takes an explicit `value: BalanceOf<T>` parameter that is transferred from the caller to `dest` regardless of what `dest` is: [1](#0-0) 

Inside the execution stack, the transfer of `frame.value_transferred` to the destination account happens unconditionally for every non-delegate frame, *before* the callee (executable or precompile) is invoked: [2](#0-1) 

Only precompiles that opt in with `HAS_CONTRACT_INFO = true` get special account bootstrap/consumer-increment handling to protect their balance from being reaped by accident: [3](#0-2) 

The `pallet-assets` ERC20 precompile explicitly declares `HAS_CONTRACT_INFO = false`: [4](#0-3) 

Its `transfer` and `transferFrom` handlers only move the `pallet-assets` balance via `do_transfer`/`do_transfer_approved`; they never call `Ext::value_transferred()` to check that no native currency was attached to the call: [5](#0-4) [6](#0-5) 

The precompile's address is a fixed, deterministically-matched `H160` (e.g. `AddressMatcher::Prefix`), not derived from any real signing key, and the account it maps to via `AddressMapper` has no code and no owner who can sign an outgoing transfer. This mirrors exactly the pattern in the original report: a function operates on an ERC20-style token but is reachable through a "payable" style call, and the code has no `require(value_transferred == 0)`-equivalent guard, so an honest user mistake (attaching native value while intending only to move the ERC20/pallet-assets balance) results in native currency being deposited into an address nobody controls.

### Impact Explanation
Native currency (the runtime's `Balances`/native token) sent together with an ERC20 precompile call is transferred to a deterministic precompile-address account that has no controlling private key and no contract logic to withdraw it. This funds is permanently unspendable/frozen - an irreversible freezing/loss of the caller's own funds, analogous to and possibly worse than the original OpenQ report's "stuck in BountyCore.sol forever," since polkadot-sdk chains generally have no owner/emergency-recovery mechanism for such addresses.

### Likelihood Explanation
The precondition is only a normal, unprivileged, signed `pallet_revive::call` extrinsic against a well-known precompile address executing a standard `transfer`/`transferFrom` selector while also specifying a non-zero `value`. No special role, governance, or malicious actor is required - only a user mistake (or a wallet/dApp bug that fills in a non-zero `value` field by default, which is common in EVM tooling where `value` and calldata are independent form fields). This closely tracks the "Medium - user could lose funds by mistake" classification of the original report.

### Recommendation
In the ERC20 precompile's state-changing handlers (`transfer`, `transferFrom`, `approve`, `permit`), reject the call if `env.value_transferred()` is non-zero (mirroring the suggested fix in the original report: `require(msg.value == 0)` before proceeding with the ERC20-style transfer). Alternatively/additionally, refund or bounce back any attached native value for precompiles that are not designed to receive it.

### Proof of Concept
I was not able to complete an executable Rust/FRAME integration test within the available iterations; this is a source-level analysis, not a verified/ran reproduction. What I confirmed by reading the code:
- `pallet_revive::Pallet::call` accepts and unconditionally forwards a native `value` to `dest` before invoking the precompile handler: [2](#0-1) .
- The ERC20 precompile's `transfer`/`transferFrom` do not check or reject `value_transferred()`: [5](#0-4) .
- ERC20 precompiles are `HAS_CONTRACT_INFO = false`, so they do not get the automatic minimum-balance/consumer-protection bootstrap applied to "real" contracts: [4](#0-3) .

What remains unverified (explicitly uncertain):
- I did not trace the full body of `Self::transfer_from_origin` (only its call site) to double-check there is no separate, existing guard elsewhere in the stack that rejects non-zero value to non-contract/precompile destinations - I ran out of tool iterations before confirming this function's internals.
- I did not execute a test (e.g., via `pallet_revive::Pallet::bare_call` in the existing `substrate/frame/assets/precompiles/src/tests.rs` harness) to empirically confirm the native balance lands at the precompile's mapped account and cannot subsequently be withdrawn by any party; this should be validated with a concrete test before treating the finding as fully proven.

Given these unverified gaps, this should be treated as a plausible, code-supported analog requiring a runtime integration test to confirm exploitability end-to-end, rather than a fully proven Critical/High finding.

	fn transfer(
		asset_id: <Runtime as Config<Instance>>::AssetId,
		call: &IERC20::transferCall,
		env: &mut impl Ext<T = Runtime>,
	) -> Result<Vec<u8>, Error> {
		env.charge(<Runtime as Config<Instance>>::WeightInfo::transfer())?;

		let from = Self::caller(env)?;
		let dest = <Runtime as pallet_revive::Config>::AddressMapper::to_account_id(
			&call.to.into_array().into(),
		);

		let f = TransferFlags { keep_alive: false, best_effort: false, burn_dust: false };
		pallet_assets::Pallet::<Runtime, Instance>::do_transfer(
			asset_id,
			&<Runtime as pallet_revive::Config>::AddressMapper::to_account_id(&from),
			&dest,
			Self::to_balance(call.value)?,
			None,
			f,
		)?;

		Self::deposit_event(
			env,
			IERC20Events::Transfer(IERC20::Transfer {
				from: from.0.into(),
				to: call.to,
				value: call.value,
			}),
		)?;

		Ok(IERC20::transferCall::abi_encode_returns(&true))
	}
