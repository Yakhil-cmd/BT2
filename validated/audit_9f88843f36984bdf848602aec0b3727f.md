### Title
Webhook signature verification is keyed off a different payload field than the one used to select the target repository, allowing spoofed events to be accepted for another organization's stack in multi-app deployments - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks which GitHub App (and thus which `webhook_secret`) to validate a webhook against using `repository.owner.login`, while the actual event handlers resolve the `Stack`/`Repository` to mutate using the separate, independently attacker-controlled `repository.full_name` field. In the documented multi-organization configuration, each organization has its own `webhook_secret`, and `GitHubApp#verify_webhook_signature` trivially returns `true` when that organization's secret is unset. An attacker can therefore choose `repository.owner.login` to point at a configured GitHub App whose `webhook_secret` is blank (an explicitly documented, valid configuration) while setting `repository.full_name` to a *different* organization's real repository, bypassing verification entirely for writes/events targeting that other org's stack.

### Finding Description
The controller determines which app config governs signature verification from one field: [1](#0-0) [2](#0-1) 

```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization: repository_owner)` looks up the app config keyed by that value in multi-app deployments: [3](#0-2) 

Signature verification for the selected app then short-circuits to `true` whenever that app's `webhook_secret` is blank: [4](#0-3) 

Meanwhile, every event handler resolves the `Stack` to act on using an entirely different field of the same JSON body: [5](#0-4) 

```
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

Because `verify_signature` binds trust to `repository.owner.login` but `Handler#stacks` binds the actual write/action to `repository.full_name`, these two fields are never checked for equality, and both are attacker-controlled in the raw JSON body of an unauthenticated POST to `/webhooks`. `PushHandler` (triggers `GithubSyncJob`), `StatusHandler` (writes commit statuses), and `MembershipHandler` (creates/removes Team memberships) all rely on this `Handler#stacks`/`repository_name` resolution: [6](#0-5) [7](#0-6) 

Multi-organization configuration, where each org has its own (optionally unset) `webhook_secret`, is an explicitly documented and supported feature, not a misconfiguration: [8](#0-7) [9](#0-8) 

The equality that should hold but doesn't: `organization_used_to_select_and_verify_signature (repository.owner.login)` == `organization_whose_repository_the_handler_acts_on (repository.full_name)`.

### Impact Explanation
In a multi-GitHub-App deployment where at least one configured organization has no `webhook_secret` set (a state explicitly shown as valid in the docs and dummy config), an unauthenticated attacker can submit a forged webhook body claiming `repository.owner.login` = that secret-less org while setting `repository.full_name` = any other tracked repository belonging to a different, properly-secured org. `verify_webhook_signature` returns `true` unconditionally (no secret to check against), and the handler then acts on the *target* repository's `Stack`, e.g. enqueuing `GithubSyncJob`, writing commit statuses via `StatusHandler`, or mutating `Team`/`Membership` records via `MembershipHandler` — all without possessing the target organization's actual webhook secret. This is an authentication-bypass style write into stack state that the attacker has no legitimate credential for, satisfying the "unauthenticated ... cross-repository writes" impact bar.

### Likelihood Explanation
Requires: (1) the deployment uses the documented multi-org `github:` config schema, and (2) at least one configured organization has a blank/unset `webhook_secret` — both are states the shipped documentation and dummy fixtures present as normal/expected (webhook secret is described as "optional"). No credentials, GitHub App private key, or `ApiClient` token are needed; the attacker only needs the public `/webhooks` endpoint and knowledge of one org's login name that lacks a webhook secret (organization logins are public on GitHub).

### Recommendation
Bind the signature-verification organization to the exact same field used by handlers to resolve the target repository (`repository.full_name`'s owner segment), and refuse to treat a request as verified if the selected app config exists but is for an org that doesn't match the acted-upon repository's owner. Additionally, consider not treating a missing `webhook_secret` as an automatic pass in multi-app configurations — require every org used in a multi-app setup to define a `webhook_secret`, or at minimum log/alert when signature verification is skipped for a payload whose acted-upon repository belongs to a different org than the one selected for verification.

### Proof of Concept
1. Configure Shipit with the documented multi-org schema: `OrgA` (has a `webhook_secret`) tracks a private stack; `OrgB` is configured with `webhook_secret` left blank (as shown in `test/dummy/config/secrets_double_github_app.yml` and `docs/setup.md`).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": { "owner": { "login": "OrgB" }, "full_name": "OrgA/private-stack" },
  "ref": "refs/heads/main",
  "after": "deadbeef..."
}
```
3. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgB")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` without checking any `X-Hub-Signature` header (attacker can omit it or send garbage).
4. `PushHandler#process` resolves `Repository.from_github_repo_name("OrgA/private-stack")` via `payload.dig('repository', 'full_name')` and enqueues `GithubSyncJob` for `OrgA`'s stack — an unauthenticated write triggered under `OrgB`'s (secret-less) identity.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml
production:
  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
```
