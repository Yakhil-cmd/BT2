### Title
CCMenuController leaks any stack's build status by ignoring the API token's stack scope - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` (mounted at `api_stack_ccmenu_url`) overrides the stack-lookup helper inherited from `Shipit::Api::BaseController` to query `Stack.from_param!` directly, instead of the scoped `stacks` collection that every other API controller uses. This breaks the equality that an `ApiClient` token scoped to a single stack should only ever "touch" that stack.

### Finding Description
`Shipit::Api::BaseController` restricts the set of stacks an authenticated `ApiClient` can operate on: [1](#0-0) 
`stacks` is scoped to `current_api_client.stack_id` when the client has one, and `stack` (used by `StacksController`, `TasksController`, etc.) is derived from that scoped relation, so a token created for Stack A cannot resolve Stack B via `params[:stack_id]`.

`CCMenuController`, however, redefines `stack` to bypass this scoping entirely: [2](#0-1) 
It also overrides `authenticate_api_client` to authenticate via a `params[:token]` query parameter (as generated by `CCMenuUrlController`) rather than HTTP basic auth, but still relies on the class-level `require_permission :read, :stack` declaration, which only checks that the token carries the `read:stack` permission string — it never verifies that the requested `stack_id` matches `current_api_client.stack_id`.

The intended trust binding is: `current_api_client.stack_id == stack.id` (the stack a token authorizes to read). `CCMenuController#stack` instead resolves `Stack.from_param!(params[:stack_id])` against *all* stacks, so the binding actually enforced is `current_api_client.permissions.include?("read:stack")` regardless of which stack is requested. Any token with `read:stack` permission — even one legitimately minted and scoped to a single stack via `CCMenuUrlController#client` (`ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(...)`) — can be replayed against `/api/*any_other_stack*/cc.xml` to read that other stack's latest deploy/rollback status. [3](#0-2) 

### Impact Explanation
This is an unauthenticated-scope-escape read of stack state (deploy status, running/success/failure, timestamps) for stacks the token holder was never granted access to. It matches the "High" impact category of escalation past a stack-scoped credential into unauthorized read of stack state/deploy output, without needing a privileged account, session, or secret beyond the narrowly-scoped CCMenu token itself (which is meant to be embedded in third-party CI dashboard tools and is not treated as a high-trust secret).

### Likelihood Explanation
Any holder of a legitimately-issued CCMenu URL/token (these are designed to be shared with build-monitoring tools, embedded in URLs, and are not treated as highly sensitive) can trivially swap `stack_id` in the request path to enumerate/read other stacks' status. No privilege escalation, brute force, or additional secrets are required beyond having any valid CCMenu token — likelihood is high given the token is designed for lightweight/external consumption.

### Recommendation
Make `CCMenuController#stack` use the scoped `stacks` collection from `BaseController` (i.e., `stacks.from_param!(params[:stack_id])`) instead of the unscoped `Stack.from_param!`, so a stack-scoped token cannot resolve any stack outside `current_api_client.stack_id`.

### Proof of Concept
1. As an authenticated user, call `GET /:stack_id/ccmenu_url` for Stack A. `CCMenuUrlController#client` mints (or reuses) an `ApiClient` with `permissions: ['read:stack']` and no `stack_id` restriction unless explicitly configured with one; obtain `client.authentication_token`.
2. Assume/construct instead a token that *is* scoped to Stack A only (`ApiClient.create!(stack: stack_a, permissions: ['read:stack'], ...)`), as is the documented intended use of stack-scoped tokens (see `here_come_the_walrus` fixture: `stack: shipit, permissions: ['read:stack']`). [4](#0-3) 
3. Send `GET /api/<stack_b_owner>/<stack_b_repo>/<stack_b_env>/cc.xml?token=<stack_a_scoped_token>` for an unrelated Stack B.
4. `authenticate_api_client` in `CCMenuController` accepts the token (valid signature via `ApiClient.authenticate`), `require_permission :read, :stack` passes because the token has `read:stack`, and `stack` resolves Stack B via `Stack.from_param!` (unscoped) — returning Stack B's deploy status XML, even though the token was only authorized to read Stack A.
