### Title
Forged `push` webhook via `organization.login` fallback bypasses per-repo signature verification and lets one org's payload sync another org's stacks - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/handler.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret to verify the HMAC signature using `repository_owner`, which falls back to `params.dig('organization', 'login')` whenever `repository.owner.login` is absent from the payload. [1](#0-0)  Meanwhile `Shipit::Webhooks::Handlers::Handler#repository_name`, used by every handler including `PushHandler`, independently reads `payload.dig('repository', 'full_name')` to select which `Repository`/stacks to mutate. [2](#0-1)  These two fields are attacker-controlled independently, so an attacker who owns/controls one organization's webhook secret can forge a payload whose `organization.login` matches their own org (for signature verification) while `repository.full_name` names a victim org's repository (for the handler's target selection).

### Finding Description
The invariant that should hold is: `organization-that-signed-the-request == organization-that-owns-the-repository-being-mutated`. Concretely: the org used in `Shipit.github(organization: repository_owner)` for signature verification must equal the org that owns `Repository.from_github_repo_name(repository_name)`.

- `repository_owner` is computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. [1](#0-0)  This is used to fetch the correct `GithubApp`/webhook secret via `Shipit.github(organization: repository_owner)` and verify `X-Hub-Signature`. [3](#0-2) 
- `Handler#repository_name` reads `payload.dig('repository', 'full_name')` directly, with no cross-check against `repository_owner` or `organization.login`. [2](#0-1) 
- `PushHandler#process` uses `stacks` (built from that `repository_name`) filtered by `branch` (from `params.ref`) and calls `stack.sync_github(expected_head_sha: params.after)` for every matching non-archived stack. [4](#0-3) 

Exploit request: attacker sends `POST /webhooks` with `X-Github-Event: push` and a body of the form:
```json
{
  "organization": { "login": "attacker-org" },
  "repository": { "full_name": "victim-org/victim-repo" },
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>"
}
```
Note `repository` deliberately omits the `owner.login` sub-key, so `repository_owner` falls back to `"attacker-org"`. The attacker signs this body with `attacker-org`'s legitimate `webhook_secret` (which they control since it's their own org's Shipit-connected GitHub App/org). `verify_signature` succeeds because it only checks the signature against `attacker-org`'s secret, which is valid for the raw body the attacker crafted. [5](#0-4)  The request then reaches `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`, which dispatches to `PushHandler`, resolves stacks via `victim-org/victim-repo`, and calls `sync_github(expected_head_sha: ...)` on the victim's stacks — with no relation to `attacker-org` at all. [6](#0-5) 

Existing guards do not stop this: `verify_signature` only validates that the raw bytes match some org's secret, not that the org matches the repository referenced elsewhere in the payload; `drop_unhandled_event` only filters by event type, not payload consistency; `ExplicitParameters` schema for `PushHandler` only requires `ref` and `after`, it does not require or validate `repository`. [7](#0-6) 

### Impact Explanation
An attacker who controls any single organization onboarded to this Shipit instance (i.e., knows that org's `webhook_secret`, which is normal for a repo/org owner setting up their own webhook) can forge push events that are attributed to their own org for signature purposes but target an arbitrary other org's repository/stacks by full_name. This drives `Stack#sync_github`, which fetches commits and can queue deploy-relevant syncs for a repository the attacker does not own or administer — a cross-tenant "payload for one repository mutating another's stack/commit" scenario, matching the Critical impact category defined in the rules. This is repeatable against any repository name the attacker can guess or discover (repository full names are generally public/discoverable via GitHub), for any number of pushes.

### Likelihood Explanation
Preconditions: the Shipit instance must be configured with GitHub Apps/secrets per-organization such that at least one organization onboarded to Shipit is one the attacker legitimately controls (owns a GitHub org integrated with this Shipit instance, or otherwise knows/can obtain that org's webhook secret through normal, unprivileged setup of their own org's webhook). Given that, the attack costs a single crafted HTTP POST with a valid HMAC computed from a secret the attacker legitimately possesses for their own org — no Shipit session, API token, or GitHub push access to the victim repo is required. This is fully repeatable and low-cost.

### Recommendation
Enforce a single, unambiguous, cross-checked repository/organization derivation for both signature verification and handler dispatch: require `repository.full_name` (and derive `repository.owner.login` from it, not from a separately-trusted `organization.login`) for signature verification, and reject any payload where `repository.owner.login` (or the org derived from `repository.full_name`) does not match the `organization.login` used, when both are present. Additionally, `Handler#repository_name`/`repository_owner` should be derived from the exact same trusted field, and payloads lacking `repository.owner.login` should not silently fall back to a differently-scoped `organization.login`.

### Proof of Concept
minitest (ActionDispatch::IntegrationTest) plan under `test/controllers/webhooks_controller_test.rb`:
1. Configure two orgs in test secrets: `attacker-org` with a known `webhook_secret`, and `victim-org` (owning `victim-org/victim-repo`, which has a Shipit `Stack` with `branch: "master"`).
2. Build payload: `{"organization": {"login": "attacker-org"}, "repository": {"full_name": "victim-org/victim-repo"}, "ref": "refs/heads/master", "after": "<sha>"}` (no `repository.owner.login`).
3. Compute `X-Hub-Signature` using `attacker-org`'s `webhook_secret` over the raw JSON body.
4. `POST /webhooks` with headers `X-Github-Event: push`, `X-Hub-Signature: <computed>`.
5. Assert response is `200 OK` (not `422`), proving `verify_signature` accepted a request signed by `attacker-org`'s secret while targeting `victim-org`'s repository — i.e., assert `repository_owner_used_for_verification ("attacker-org") != organization_owning_target_repo ("victim-org")` yet the request was accepted.
6. Assert `Stack#sync_github` (or a resulting job/side effect, e.g. `GithubSyncJob.jobs` or a stubbed `sync_github` expectation) was invoked on the `victim-org/victim-repo` stack, proving cross-tenant mutation occurred without `victim-org`'s secret ever being used.
