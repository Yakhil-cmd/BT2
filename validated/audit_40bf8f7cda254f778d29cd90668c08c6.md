### Title
Webhook signature verified against `repository.owner.login` while stack provisioning trusts an independent `repository.full_name` field, letting a payload for one org's repo create a review stack under another org's repo - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and thus the HMAC secret) used to authenticate a webhook based on `params.dig('repository','owner','login')`, while `PullRequest::OpenedHandler#repository` (used by `ReviewStackAdapter#find_or_create!`) resolves the target `Shipit::Repository` from the completely independent `params.repository.full_name` field [1](#0-0) . Nothing cross-checks that these two fields describe the same repository/organization, so a payload can be "authenticated" as belonging to an org with no `webhook_secret` while mutating a different org's repository state.

### Finding Description
Broken binding: `organization used to verify HMAC (params['repository']['owner']['login'])` should equal `organization owning the repository whose review_stacks are provisioned (derived from params['repository']['full_name'])`. These are two independent JSON fields, and the code never asserts they agree.

- `verify_signature` picks the app config via `Shipit.github(organization: repository_owner)`, where `repository_owner` reads `params.dig('repository', 'owner', 'login')` [2](#0-1) .
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when `webhook_secret` is blank for that org: `return true unless webhook_secret` [3](#0-2) .
- In `Shipit.github`, when the deployment uses the single-org config schema (`github_default_organization` returns `nil`), `config = secrets.github` is used regardless of the `organization` argument passed in - so the `organization:` parameter passed by `verify_signature` may not even matter to which secret is checked [4](#0-3) . In multi-org mode, an org key with no configured `webhook_secret` (shown as valid/expected config in `config/secrets.development.shopify.yml` and `docs/setup.md`) similarly causes verification to always pass for that org.
- Once the request passes `verify_signature`, `PullRequest::OpenedHandler#process` runs `Shipit::Webhooks::Handlers::PullRequest::ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!`, where `repository` is resolved via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [5](#0-4) , and `from_github_repo_name` simply splits `"owner/name"` and looks up the DB row [6](#0-5) .
- `ReviewStackAdapter#create!` then creates a `ReviewStack` (`scope.create!(stack_attributes)`) with `branch: params.pull_request.head.ref` fully attacker-controlled, attaches a `PullRequest` record, and enqueues provisioning via `ReviewStackProvisioningQueue.add(stack)` [7](#0-6) .

Attacker's exact request: `POST /webhooks` with header `X-Github-Event: pull_request`, body:
```json
{
  "action": "opened",
  "number": 9999,
  "pull_request": { "id": 1, "number": 9999, "url": "...", "title": "x", "state": "open",
                     "additions": 1, "deletions": 0,
                     "head": { "sha": "deadbeef", "ref": "attacker-branch" },
                     "user": { "login": "attacker" }, "assignees": [], "labels": [] },
  "repository": { "full_name": "victim-org/victim-repo", "owner": { "login": "attacker-org" } },
  "sender": { "login": "attacker" }
}
```
where `attacker-org` is a Shipit-configured org (or the sole configured org in single-org mode) whose `webhook_secret` is unset - exactly the documented default in `config/secrets.development.example.yml` and `config/secrets.development.shopify.yml`. `verify_signature` looks up `attacker-org`'s app, finds no secret, returns `true` for any/no signature. The handler then resolves and mutates `victim-org/victim-repo`'s `ReviewStack` scope, unrelated to the org that "authenticated" the request.

Existing guards checked and found insufficient: `drop_unhandled_event` only filters by event type, not by repo/org consistency; `verify_signature`'s `GithubOrganizationUnknown` rescue only fires if the org key is *unrecognized*, not if it's recognized-but-secret-less or simply mismatched from `full_name`; the `ExplicitParameters` schema in `OpenedHandler` (`params do ... end`) only validates field presence/types, not cross-field consistency between `repository.owner.login` and `repository.full_name`; `Repository` model validations only constrain `owner`/`name` character sets, not that a webhook's claimed owner matches the repo being targeted.

### Impact Explanation
A forged webhook "authenticated" under one (secret-less) organization's identity causes creation of a `Shipit::ReviewStack`/`Shipit::Stack` and an associated `Shipit::PullRequest` row scoped to a different organization's `Shipit::Repository`, with an attacker-fully-controlled `branch`/`environment`/PR metadata. This directly matches the rules' explicitly-listed Critical impact: "a payload for one repository mutating another's stack, commit, task or team." The stack is queued for provisioning (`ReviewStackProvisioningQueue.add(stack)`), which downstream would attempt to fetch/checkout the attacker-specified ref against the victim's real repository using the victim's real GitHub App credentials - if the attacker can get any ref/sha to exist in the victim repo (e.g., via a legitimately opened PR from a fork, then simply relaying a forged additional webhook with a different declared org), this becomes an unauthorized deploy path. Even absent a resolvable ref, this is still unauthorized persistent state creation (rows, provisioning-queue entries, User/PullRequest records) against a tenant that never authorized or triggered the action, and is repeatable against any victim repository with `review_stacks_enabled` + `provisioning_behavior_allow_all`, for any organization key configured with a blank `webhook_secret` (a documented, shipped default configuration).

### Likelihood Explanation
Preconditions: Shipit must have at least one configured GitHub org/app entry with a blank `webhook_secret` (the example/shipped configs literally default to `webhook_secret: # nil`), and a victim repository that has `review_stacks_enabled` with `provisioning_behavior_allow_all`. No Shipit session, API token, or GitHub secret is required by the attacker - only the ability to POST arbitrary JSON to `/webhooks`, which the rules state is in-scope for an unprivileged attacker. The attack is trivially repeatable (any number, any branch name, any target `full_name`) and costs nothing beyond crafting an HTTP request. The only real barrier is operational: at least one configured org must lack a webhook secret, which is a common misconfiguration actively encouraged by this repo's own example secrets files.

### Recommendation
Bind the two identities together before trusting the payload: after `verify_signature` succeeds, require that `params.dig('repository','full_name')&.split('/')&.first&.downcase == repository_owner&.downcase` (or equivalently, derive the target `Repository`/org strictly from the same field used for signature verification), and reject (422) on mismatch. Additionally, treat a missing/blank `webhook_secret` for a configured org as a hard configuration error in production (refuse to boot or refuse all webhooks for that org) rather than silently authenticating any payload, since `verify_webhook_signature`'s `return true unless webhook_secret` amounts to an implicit "trust everything" fallback.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (new test)
test "pull_request opened for org A (no webhook_secret) cannot provision review stack for org B's repository" do
  victim_repo = shipit_repositories(:shipit) # owner: 'shopify', review_stacks_enabled: true, provisioning_behavior: allow_all
  victim_repo.update!(review_stacks_enabled: true, provisioning_behavior: :allow_all)

  # attacker-org configured with no webhook_secret -> verify_webhook_signature returns true unconditionally
  Shipit.stubs(:github).with(organization: 'attacker-org').returns(
    Shipit::GitHubApp.new('attacker-org', { webhook_secret: nil })
  )

  forged_payload = {
    action: 'opened', number: 9999,
    pull_request: {
      id: 1, number: 9999, url: 'x', title: 'x', state: 'open', additions: 1, deletions: 0,
      head: { sha: 'deadbeef', ref: 'attacker-branch' },
      user: { login: 'attacker' }, assignees: [], labels: []
    },
    repository: { full_name: "#{victim_repo.owner}/#{victim_repo.name}", owner: { login: 'attacker-org' } },
    sender: { login: 'attacker' }
  }.to_json

  # Binding check BEFORE: verifying org ('attacker-org') != owning org of repository.full_name ('shopify')
  assert_not_equal 'attacker-org', victim_repo.owner

  @request.headers['X-Github-Event'] = 'pull_request'
  @request.headers['X-Hub-Signature'] = 'sha1=deadbeef' # arbitrary, irrelevant since secret is nil

  assert_difference -> { Shipit::ReviewStack.where(repository_id: victim_repo.id).count }, 1 do
    post :create, body: forged_payload, as: :json
  end
  assert_response :ok

  # Binding check AFTER: a review stack now exists under victim_repo despite the request being
  # "verified" only for a wholly unrelated, secret-less organization.
  created = Shipit::ReviewStack.where(repository_id: victim_repo.id).last
  assert_equal 'pr9999', created.environment
  assert_equal 'attacker-branch', created.branch
end
```
Expected outcome on the current code: the test passes, demonstrating the write to `victim_repo`'s `review_stacks` despite the webhook only ever being verified against `attacker-org`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
