## Analysis

The Rubicon `setBonusToken` bug is a **duplicate-entry-in-array** bug class: pushing the same logical entity into an array that is later iterated as if entries were independent/unique, letting one entry's effect be counted multiple times at the expense of correctness for others.

The closest reachable analog in `ocore--001` is in the `"r of set"` and `"weighted and"` operators of address definitions, evaluated in `definition.js`'s `validateAuthentifiers`. Both operators iterate over `args.set` and increment a `count`/`weight` for each member that evaluates true, with **no requirement that the members of the set be distinct**: [1](#0-0) [2](#0-1) 

Because each set member gets its own signing path (`path+'.'+index`), a member can legitimately reuse the exact same `["sig", {pubkey: X}]` sub-definition at two different indices in the `set`. Since a `secp256k1` signature over `unit_hash_to_sign` only depends on the key, not on the path, the holder of a single private key can submit the *same signature bytes* twice — once at `r.0`, once at `r.1` — and satisfy `required: 2` alone: [3](#0-2) 

This is directly analogous to the Rubicon issue: an array (`bonusTokens` there, `set` here) that is supposed to represent distinct contributors/approvers is allowed to contain duplicates, letting one entry's weight be double- (or N-times-) counted, defeating the intended threshold semantics.

The practically dangerous path is shared multi-device/multi-owner addresses created via `wallet_defined_by_addresses.js`. `handleNewSharedAddress`/`validateAddressDefinitionTemplate` validate that signer addresses match the definition's extracted paths and that a definition path exists for every declared signer, but they never check that the members inside an `"r of set"`/`"weighted and"` are mutually distinct (different keys/addresses): [4](#0-3) [5](#0-4) [6](#0-5) 

A malicious co-signer who proposes the shared-address definition (e.g. via `createNewSharedAddress`/`sendOfferToCreateNewWallet`) can craft an `"r of set", {required: N, set:[...]}` structure where two or more "member" slots secretly resolve to the *same* pubkey/address under their sole control, while the other slots point to genuinely independent cosigners. The other cosigners see a definition that *looks* like an `N`-of-`M` multisig requiring cooperation, but the attacker alone can already reach `required` by re-submitting one signature at multiple paths, spending funds from the shared address without any of the intended independent approvals.

### Title
Duplicate members inside `"r of set"` / `"weighted and"` address-definition constructs let one signer meet a multisig threshold alone - (File: `definition.js`)

### Summary
`definition.js`'s authentifier evaluator counts each element of an `"r of set"` or `"weighted and"` set independently, without verifying that set members are distinct definitions/keys, mirroring the reported class of bug where duplicate array entries let one party's contribution be counted multiple times.

### Finding Description
`evaluate()` for `'r of set'` increments `count` for every array element in `args.set` that verifies true and accepts the definition once `count >= args.required`; `'weighted and'` behaves the same way with weights. Nothing in this evaluation, nor in the structural checks of `validateDefinition`, nor in the shared-address helpers of `wallet_defined_by_addresses.js`, enforces that the members of `set` reference distinct keys/addresses. Because each member gets a separate signing path but the underlying `sig` verification only checks the signature against `unit_hash_to_sign` and the member's `pubkey`, a single private key controlling two (or more) `set` entries can supply the identical signature at each of its assigned paths, satisfying an arbitrary `required`/`weight` threshold on its own. [7](#0-6) 

### Impact Explanation
If a shared/multi-owner address (or any address whose definition a user did not fully audit) is created with a `"r of set"`/`"weighted and"` definition containing hidden duplicate key entries, the party who crafted the definition can unilaterally reach the signing threshold and spend all funds from the address, even though other cosigners believe their independent approval is required. This is unauthorized spending from what is presented as a cooperative multisig — analogous to the "early withdrawer gets multiples of bonus" impact, except here it manifests as one signer gaining multiples of intended signing weight.

### Likelihood Explanation
Exploitation requires the attacker to be the one proposing/crafting the shared address definition (a role reachable by any wallet user via `handleNewSharedAddress`/`createNewSharedAddress`), and requires the other cosigners not to notice the duplicate sub-definitions when reviewing the offered definition. This is plausible since the definition is a nested JSON structure that isn't rendered as a simple "which addresses are members" list checked for uniqueness anywhere in the codebase.

### Recommendation
When validating `"r of set"` and `"weighted and"` (both in `Definition.validateDefinition`'s structural pass and/or in `wallet_defined_by_addresses.js`'s shared-address creation flow), reject definitions whose `set` contains duplicate sub-definitions (compare by `objectHash.getChash160` of each member, or reject duplicate pubkeys/addresses across members of the same set) to guarantee that `required` truly corresponds to that many independent approvers.

### Proof of Concept
1. Attacker device proposes a shared address with definition `["r of set", {required: 2, set: [["sig",{pubkey:A}], ["sig",{pubkey:A}], ["sig",{pubkey:B}]]}]` to cosigner B, framing it as "2-of-3, requires B's cooperation."
2. B approves, believing 2 signatures from independent parties are needed.
3. Attacker (holding only key `A`) signs the spending unit once; the same signature bytes are placed at authentifier paths `r.0` and `r.1`.
4. `evaluate()` for `'r of set'` calls `evaluate` on both `r.0` and `r.1`, both succeed via the `'sig'` case verifying the same signature against the same pubkey `A`, giving `count = 2 >= required`, and the unit is accepted without any input from B. [1](#0-0) [3](#0-2)

function getMemberDeviceAddressesBySigningPaths(arrAddressDefinitionTemplate){
	function evaluate(arr, path){
		var op = arr[0];
		var args = arr[1];
		if (!args)
			return;
		switch (op){
			case 'or':
			case 'and':
				for (var i=0; i<args.length; i++)
					evaluate(args[i], path + '.' + i);
				break;
			case 'r of set':
				if (!ValidationUtils.isNonemptyArray(args.set))
					return;
				for (var i=0; i<args.set.length; i++)
					evaluate(args.set[i], path + '.' + i);
				break;
			case 'weighted and':
				if (!ValidationUtils.isNonemptyArray(args.set))
					return;
				for (var i=0; i<args.set.length; i++)
					evaluate(args.set[i].value, path + '.' + i);
				break;
			case 'address':
				var address = args;
				var prefix = '$address@';
				if (!ValidationUtils.isNonemptyString(address) || address.substr(0, prefix.length) !== prefix)
					return;
				var device_address = address.substr(prefix.length);
				assocMemberDeviceAddressesBySigningPaths[path] = device_address;
				break;
			case 'definition template':
				throw Error(op+" not supported yet");
			// all other ops cannot reference device address
		}
	}
	var assocMemberDeviceAddressesBySigningPaths = {};
	evaluate(arrAddressDefinitionTemplate, 'r');
	return assocMemberDeviceAddressesBySigningPaths;
}
