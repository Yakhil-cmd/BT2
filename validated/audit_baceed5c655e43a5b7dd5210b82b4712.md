### Title
Quadratic-time input/output key lookups in payment validation, with the size cap bypassed for AA-generated payments - (File: validation.js)

### Summary
`validatePaymentInputsAndOutputs()` in `validation.js` checks every input and output for duplicates by calling `Array.prototype.indexOf()` on ever-growing accumulator arrays (`arrInputKeys`, `arrOutputAddresses`, `arrInputAddresses`) once per element, giving O(n²) behavior for n inputs/outputs — the same algorithmic-complexity bug class as the reported `archive/zip` super-linear name-indexing CVE (repeated linear scans instead of a hash-based lookup). Critically, the size cap that normally bounds `n` is explicitly skipped when the payment is generated by an Autonomous Agent (`objValidationState.bAA`), letting an attacker who merely triggers an AA drive `n` far above the normal per-unit limits.

### Finding Description

Each of these `objValidationState.arrInputKeys.indexOf(input_key)` calls scans the entire array built so far before pushing a new element, making the whole loop quadratic in the number of inputs. The same pattern applies to output addresses: [4](#0-3) 
and owner addresses: [5](#0-4) 

Normally the number of inputs/outputs per payment message is capped: [6](#0-5) 

However, the input-count cap is explicitly **not enforced** when the message belongs to an AA (`!objValidationState.bAA`), meaning payment messages produced by AA bounce/response logic can carry an arbitrarily large `payload.inputs` array (limited only by AA response/state constraints elsewhere, not by `MAX_INPUTS_PER_PAYMENT_MESSAGE`). An AA author can write an autonomous agent whose response payment iterates a large, attacker-influenced data structure (e.g., built from `trigger.data` via `oscript`/formula evaluation) to produce many synthetic inputs; any user can then trigger that AA. This causes `checkInputDoubleSpend`'s enclosing loop, together with the repeated `indexOf` scans, to run in quadratic time relative to attacker-controlled input, similar to the "super-linear indexing algorithm" described in the archive/zip advisory.

### Impact Explanation
Every full node that validates the resulting AA-response unit (or every full node/hub validating the AA trigger and subsequent bounce processing) pays the quadratic CPU cost, since unit/AA validation is mandatory consensus-critical work performed by all nodes, not just the submitter. A sufficiently large attacker-crafted input count can turn a single AA trigger into a multi-second-to-minutes CPU burn across the network, potentially stalling validation of other units and impairing timely stabilization of the DAG — a node-disagreement/availability risk consistent with "network unable to confirm new units in a timely manner," rather than merely a local inconvenience.

### Likelihood Explanation
Likelihood is moderate-to-high: no privileged access is needed — any user can post an AA trigger unit, and any user can also author and deploy an AA definition containing oscript logic that fans out many payment inputs from trigger data. The bypass of `MAX_INPUTS_PER_PAYMENT_MESSAGE` for `bAA` payments is an explicit code branch, not a subtle edge case, so the constraint that would normally cap `n` (and thus the quadratic blow-up) is removed specifically for the AA path that is externally triggerable.

### Recommendation
- Replace the linear `arrInputKeys`/`arrOutputAddresses`/`arrInputAddresses` `Array.indexOf` duplicate checks with `Set`/`Map`-backed O(1) lookups in `validatePaymentInputsAndOutputs()` (and equivalent checks in `validateMessage()`'s `spend_proofs` handling at `validation.js:1577-1579`).
- Re-apply (or introduce an AA-specific but still finite) bound on `payload.inputs.length` / `payload.outputs.length` for AA-generated payments instead of unconditionally exempting `bAA` from `MAX_INPUTS_PER_PAYMENT_MESSAGE`, or ensure AA response composition itself enforces a strict, low cap on generated inputs before this validation is reached.

### Proof of Concept
Conceptual outline (cannot be executed without a live node/AA environment):
1. Deploy an AA whose response logic builds a `payment` message with `inputs` derived from a large `data` array supplied by the trigger unit (e.g., iterating `trigger.data.items` to synthesize/split coin inputs), so that `payload.inputs.length` can reach several thousand elements uncapped because `objValidationState.bAA` disables the `MAX_INPUTS_PER_PAYMENT_MESSAGE` check [7](#0-6) .
2. Send a trigger unit to this AA that causes it to emit such a large-input payment in its response.
3. When full nodes validate the AA response unit, `validatePaymentInputsAndOutputs()` executes `arrInputKeys.indexOf(input_key)` for each of the thousands of inputs against a growing array [2](#0-1) , producing O(n²) comparisons and measurably elevated CPU/validation time proportional to the square of the attacker-chosen input count.
