### Title
Webhook signature verification keys on `repository.owner.login`/`organization.login` while event handlers act on the independent `repository.full_name` field, letting one authenticated GitHub org forge webhook events against any other org's stack - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App config (and thus which `webhook_secret`) is used to validate the `X-Hub-Signature` HMAC based solely on `repository.owner.login` (falling back to `organization.login`) extracted from the untrusted JSON body. But every event handler (`PushHandler`, `StatusHandler`, the `PullRequest::*Handler` family) resolves the actual `Stack`/`Repository`/`Commit` to mutate using the independent `repository.full_name` field from the same body. These two fields are never cross-checked, so in a multi-org deployment an org that legitimately authenticates its own webhook can supply a `repository.full_name` pointing at a completely different (victim) org's stack.

### Finding Description
`verify_signature` picks the app/secret via: [1](#0-0) [2](#0-1) 

This is the "organization that authenticated" side of the binding: `Shipit.github(organization: repository_owner)` looks up the per-org config declared in `secrets.yml` (`Using Multiple Github Applications` schema documented in `docs/setup.md`), and `verify_webhook_signature` HMACs the raw body with that org's `webhook_secret`: [3](#0-2) 

Once the signature check passes, `WebhooksController#create` dispatches the *entire* parsed body to handlers without re-deriving or re-checking the org: [4](#0-3) 

Handlers then resolve the target stack from `repository.full_name`, a field completely independent of `repository.owner.login`: [5](#0-4) [6](#0-5) 

Concrete write-affecting handlers using this unguarded field:
- `PushHandler` triggers a GitHub sync job for any stack under the attacker-chosen repo: [7](#0-6) 
- `StatusHandler` creates a `Commit::Status` for **any** commit `sha` present in the datastore, entirely from attacker-controlled `state`/`description`/`target_url`/`context`, with no repository scoping check at all: [8](#0-7) 
- The `PullRequest::*Handler` classes (`OpenedHandler`, `LabeledHandler`, `ClosedHandler`, `ReopenedHandler`, etc.) all resolve `repository` via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` and then archive/unarchive/create Review Stacks or update pull-request state on that resolved repo, again independent of which org's secret verified the signature: [9](#0-8) 

The GitHub App's own webhook signing guarantees only that the *raw JSON body byte-for-byte* was produced by GitHub for the org that installed the app with that specific `webhook_secret` — it says nothing about internal consistency between `repository.owner.login` and `repository.full_name` inside a body. When Shipit is configured with multiple GitHub App configs (as documented under "Using Multiple Github Applications"), each org administers its own app installation and therefore knows/controls its own `webhook_secret` (or it may legitimately be blank, in which case `verify_webhook_signature` returns `true` unconditionally). Nothing stops that org's owner from using their own installation/webhook redelivery tooling (or a custom endpoint that simply resends a crafted JSON body, HMAC-signed with their own known secret) to submit an event whose `repository.full_name` names a repository/stack belonging to a different org onboarded to the same Shipit instance.

The security-relevant equality the code should enforce but does not is:
```
organization_verifying_signature(repository_owner) == organization_owning(repository.full_name)
```
Today the left side is derived from `repository.owner.login` and the right side is derived independently from `repository.full_name`; they are never compared.

### Impact Explanation
This crosses the "escalation into authorization" / "cross-repository writes" boundary called out in scope: a party who only administers Org A's GitHub App installation (an unprivileged party with respect to Org B's Shipit stacks) can forge webhook events that mutate Org B's data — creating fabricated commit `Status` records (which can gate/allow deploy safety checks depending on stack configuration), forcing spurious GitHub syncs, or archiving/creating/mutating Org B's Review Stacks and pull-request state — without ever needing Org B's webhook secret, an `ApiClient` token, or a Shipit session. This is a cross-organization/cross-repository write achieved purely by exploiting the mismatch between the field used for authentication routing and the field used for the actual write target.

### Likelihood Explanation
This only manifests when a Shipit instance is configured for multiple GitHub organizations (the documented "Using Multiple Github Applications" setup, i.e. `secrets.yml`'s `github:` keyed by org name) — a realistic and explicitly documented/supported configuration for shared/hosted Shipit deployments serving several orgs. Any org onboarded to such a shared instance is, by construction, "unprivileged" with respect to every other onboarded org's stacks, yet can trivially craft a JSON payload with a `repository.full_name` differing from `repository.owner.login`/`organization.login`, since GitHub's signature only certifies the bytes were signed with a given secret, not any semantic relationship between fields inside the JSON.

### Recommendation
After signature verification succeeds, re-derive the acting organization for every handler from the same trust anchor used for verification (`repository_owner`/`organization.login`), and require it to match the owner segment of `repository.full_name` before resolving/mutating any `Stack`/`Repository`/`Commit`. Concretely, pass the verified `repository_owner` into `Shipit::Webhooks::Handlers::Handler#initialize`/`stacks`/`repository_name` and reject (or scope) any event where `repository.full_name.split('/').first` does not case-insensitively equal the org whose `webhook_secret` verified the request.

### Proof of Concept
1. Configure a shared Shipit instance with two GitHub App orgs, `attacker-org` and `victim-org`, per the documented multi-org `secrets.yml` schema (each org's admin knows their own `webhook_secret`).
2. As the administrator of `attacker-org`'s GitHub App, craft a `status` (or `push`, `pull_request`) webhook JSON body where:
   - `organization.login` / `repository.owner.login` = `"attacker-org"` (so `verify_signature` selects `attacker-org`'s config and secret).
   - `repository.full_name` = `"victim-org/victim-repo"`, and `sha` = the SHA of a commit currently pending in `victim-org/victim-repo`'s stack.
3. Sign the raw body with `attacker-org`'s known `webhook_secret` and POST it to `/webhooks` with header `X-Github-Event: status`.
4. `verify_signature` succeeds (attacker-org's own secret matches). `StatusHandler#process` then runs `Commit.where(sha: params.sha).each { |c| c.create_status_from_github!(params) }`, creating an attacker-controlled `success`/`failure` status on the victim commit — despite the attacker never possessing `victim-org`'s webhook secret, an `ApiClient` token, or any Shipit credential for `victim-org`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
