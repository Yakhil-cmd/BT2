### Title
Webhook signature is verified against the organization named in `repository.owner.login`, but the repository actually acted upon is taken from a different, unverified field (`repository.full_name`) - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and therefore which `webhook_secret`) is used to authenticate an incoming webhook based on `repository.owner.login` from the raw JSON body. Once "verified," every registered `Webhooks::Handlers::Handler` resolves the `Stack`/`Repository` to act on using a *different* payload field, `repository.full_name` [1](#0-0) . Nothing binds these two fields together. In a multi-tenant Shipit installation where at least one onboarded organization has no `webhook_secret` configured (explicitly documented as optional), `GitHubApp#verify_webhook_signature` returns `true` unconditionally for that organization [2](#0-1) , so an attacker can send an unsigned/arbitrary webhook whose `repository.owner.login` matches that unsecured organization while `repository.full_name` names any other stack's repository, and have the handler act on that unrelated repository.

### Finding Description
`verify_signature` derives the verifying organization purely from the untrusted body, before any cryptographic check has occurred: [3](#0-2) [4](#0-3) 

`GitHubApp#verify_webhook_signature` treats a blank `webhook_secret` as "always verified": [2](#0-1) 

The docs explicitly document `webhook_secret` as optional per organization, and the multi-organization test fixture shows a realistic configuration where one org (`OrgTwo`) has no secret while another does: [5](#0-4) [6](#0-5) 

Once `head(422)` is skipped, `create` hands the *entire unverified payload* to every registered handler for the event [7](#0-6) . Every handler picks its target `Stack` via `Repository.from_github_repo_name(repository_name)`, where `repository_name` is `payload.dig('repository', 'full_name')` — a field completely independent from `repository.owner.login` used earlier for organization selection: [1](#0-0) 

Concretely, `PushHandler` will call `stack.sync_github(expected_head_sha:)` for whatever repository `full_name` names [8](#0-7) , and other handlers (`status`, `check_suite`, `pull_request`, `membership`) act on their respective payload data for that same mismatched target, none of it constrained to the organization that "verified" the request.

**The broken binding, stated as an equality that fails to hold:**
`organization used to select webhook_secret for signature verification (repository.owner.login)` ≠ `repository whose Stack/commits/statuses are mutated (repository.full_name)`

Before the attacker's request: only requests signed with a given org's real secret (or requests targeting an org with no secret configured, if one exists) can reach handlers, and in the documented/intended design that org's own repositories are the only ones expected to be affected.
After the attacker's request: by setting `repository.owner.login` to the unsecured org and `repository.full_name` to any other onboarded repository, the handler mutates state for a repository entirely unrelated to the (non-)verification that was performed.

### Impact Explanation
This breaks the deployment-trust boundary between "the organization whose credential authorized this webhook" and "the repository being written to." Depending on which handler fires, an attacker can:
- Force `PushHandler` to trigger `GithubSyncJob`/`sync_github` for an arbitrary victim stack.
- Force `StatusHandler`/`CheckSuiteHandler` to inject fabricated commit statuses/check runs for an arbitrary victim stack's commits, which can flip a commit's `deployable?`/CI-required-status state and enable an otherwise-blocked deploy — an unauthorized deploy triggered by an unprivileged, unauthenticated party.
This qualifies as Critical impact ("an unauthorized deploy") because it lets an outside party manipulate the deploy-gating signals of a repository they have no relationship with, purely by exploiting the mismatch between the field used for authentication and the field used for authorization of the write target.

### Likelihood Explanation
Likelihood is **High** in any multi-organization Shipit deployment where at least one onboarded organization was configured without a `webhook_secret` (an explicitly supported, documented configuration, not a compromise of any credential). No authentication, session, or secret is required by the attacker; only knowledge of the target stack's repository `full_name` and the name of any unsecured org onboarded to the same Shipit instance, both of which are typically public.

### Recommendation
Bind webhook authentication to the exact repository being acted upon rather than to an org name pulled from an independent field:
- Verify the signature using the config that matches `repository.full_name`'s owner (or reject if they diverge from `repository.owner.login`).
- Reject/short-circuit any event whose `repository.owner.login` does not match the owner segment of `repository.full_name`.
- Do not allow `verify_webhook_signature` to silently return `true` for organizations lacking a secret; either require a secret for all onboarded orgs or scope such an organization's trust so it cannot be used to authorize writes to other organizations' repositories.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `OrgA` (no `webhook_secret`) and `VictimOrg` (has a stack `VictimOrg/prod-app`), mirroring `test/dummy/config/secrets_double_github_app.yml`.
2. POST to `/webhooks` with header `X-Github-Event: push` and no `X-Hub-Signature` header, body:
```json
{
  "repository": { "owner": { "login": "OrgA" }, "full_name": "VictimOrg/prod-app" },
  "ref": "refs/heads/main",
  "after": "<any sha already known to Shipit>"
}
```
3. `verify_signature` resolves `repository_owner` → `"OrgA"`; `Shipit.github(organization: "OrgA").verify_webhook_signature` returns `true` unconditionally because `OrgA` has no `webhook_secret` [9](#0-8) .
4. `create` dispatches the payload to `PushHandler`, which resolves the target stack via `repository.full_name` = `"VictimOrg/prod-app"` [10](#0-9)  and triggers `sync_github` for `VictimOrg`'s stack, despite the request never being authenticated against `VictimOrg`'s secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
