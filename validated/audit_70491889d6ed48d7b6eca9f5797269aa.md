### Title
`StatusHandler#process` mutates commits belonging to any stack regardless of the webhook's originating repository - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits solely by `Commit.where(sha: params.sha)` and never restricts the result to `self.stacks` (the stacks belonging to `Repository.from_github_repo_name(payload.dig('repository','full_name'))`). Any commit anywhere in the Shipit database that happens to share a SHA with the webhook's `sha` field gets `create_status_from_github!` invoked on it, writing attacker-supplied CI state (`state`, `description`, `target_url`, `context`) onto a commit that belongs to a stack/repository the attacker does not control.

### Finding Description
The binding that should hold is: for every `Commit` mutated in `#process`, `commit.stack` must be a member of `self.stacks`, where `self.stacks = Repository.from_github_repo_name(payload.dig('repository','full_name'))&.stacks`.

`StatusHandler#process` violates this: [1](#0-0) 

Compare with `CheckSuiteHandler#process`, which correctly scopes through `stacks`: [2](#0-1) 

`stacks`/`repository_name` are defined on the base `Handler` but `StatusHandler` never references them: [3](#0-2) 

`create_status_from_github!` writes the status using the commit's own real `stack_id` (not attacker-supplied), so this is not merely a data-confusion bug — it is a legitimate write into the correct victim stack's commit history, using attacker-controlled status fields: [4](#0-3) 
`add_status` further triggers `stack.schedule_merges` when the forged status is `pending` or `success`, and emits `commit_status`/`deployable_status` hooks: [5](#0-4) 

**Why existing guards fail:** `verify_signature` in `WebhooksController` only validates that the request is authentically signed by the GitHub organization named in `payload.dig('repository','owner','login')` — i.e., it authenticates *which org sent this webhook*, not *which commit/stack the SHA may legitimately belong to*: [6](#0-5) 
An attacker who owns/administers any GitHub repository (including a fork of the victim's repository, which shares the victim's git history and therefore commit SHAs) can generate a validly-signed `status` webhook for their own repository. `ExplicitParameters` only validates the shape of `sha`/`state`/etc., not repository ownership of the commit. No other check (`Repository` validators, `Stack` validators) ties `params.sha` back to `payload['repository']['full_name']`.

**Attacker's exact request:** POST `/webhooks` with header `X-Github-Event: status`, a valid `X-Hub-Signature` computed with the webhook secret of a GitHub organization/repo the attacker controls (e.g. a fork of the victim project), and body:
```json
{
  "repository": {"full_name": "attacker/fork-of-victim", "owner": {"login": "attacker"}},
  "sha": "<sha of a commit shared with the victim's upstream history>",
  "state": "success",
  "context": "ci/forged"
}
```
Since forks share commit history with upstream, this SHA also exists as a `Commit` row belonging to the victim's Shipit stack. `StatusHandler` finds and mutates it.

### Impact Explanation
The attacker can inject an arbitrary, forged CI status (including `success`) onto a commit belonging to a stack/repository they do not own or administer. Because a forged `success` status can satisfy `Commit#deployable?`/`blocked?` checks and triggers `stack.schedule_merges`, this can enable an unauthorized merge/deploy pipeline advancement on the victim stack, or conversely inject forged `failure`/`error` to block legitimate deploys. This is a cross-repository/cross-tenant mutation of CI state and stack behavior — matching the Critical category "a payload for one repository mutating another's ... commit ... or an unauthorized deploy."

### Likelihood Explanation
Preconditions: the attacker needs (1) a GitHub repository they administer whose git history overlaps with the victim's tracked repository (most realistically a fork of the victim project, which is trivially creatable by any GitHub user with no special privileges — this satisfies the "attacker who can push to a fork they own" threat model), and (2) knowledge of a victim commit SHA, which is public information in the shared git history. No Shipit secrets, sessions, or API tokens are required — only the GitHub-issued webhook secret for the attacker's own fork, which GitHub provides automatically when the attacker configures a webhook on a repo they control. This is fully repeatable against any stack whose tracked repository has attacker-accessible forks/mirrors.

### Recommendation
In `StatusHandler#process`, scope the commit lookup to `self.stacks` (as `CheckSuiteHandler` does), e.g. `Commit.where(sha: params.sha, stack: stacks)` or `stacks.flat_map { |s| s.commits.where(sha: params.sha) }`, ensuring only commits belonging to the webhook's own repository's stacks can be mutated.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, outside index scope but illustrative):
1. Create `Repository`/`Stack` `victim_stack` for `github_repo_name: "owner/victim"`, and a `Commit` `victim_commit` with `sha: "a" * 40` under `victim_stack`.
2. Create a separate `Repository` `attacker_repo` for `github_repo_name: "attacker/fork"` (no shared stacks with victim).
3. Build a payload: `{"repository" => {"full_name" => "attacker/fork"}, "sha" => "a"*40, "state" => "success"}`.
4. Assert the binding is broken: stub/mock `Shipit::Webhooks::Handlers::Handler#stacks` and `#repository_name` with `Mocha` `.expects(:stacks).never` and `.expects(:repository_name).never` on the `StatusHandler` instance, then call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` and confirm it does not raise (i.e., neither method is invoked).
5. Assert the impact: reload `victim_commit` and assert `victim_commit.status.state == "success"` (or that `victim_commit.statuses.count` increased), proving a payload claiming to be from `attacker/fork` mutated a commit belonging to `owner/victim`'s stack — i.e. `commit.stack != Repository.from_github_repo_name(payload['repository']['full_name'])&.stacks`.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
