### Title
Mutable attestor list for `spender_attested` assets can permanently freeze a private-payment counterparty's already-received funds - (File: `storage.js`, `validation.js`)

### Summary
For assets defined with `spender_attested: true`, ocore does not lock in the attestor list that applied when a recipient received funds. Instead, every later validation dynamically pulls whatever attestor list is *latest* at validation time. Because the asset definer (an allowed "asset issuer" actor) can replace this list at any moment with a single self-authored `asset_attestors` message, a spender who was validly attested when they received private/public asset units can be silently de-attested afterward, permanently blocking their ability to spend the units they already legitimately hold — the same "mutable external dependency changes value/availability of already-deposited funds" pattern as the reported `InsuranceFund#syncDeps()` bug.

### Finding Description
`storage.readAsset()` resolves the attestor list for a `spender_attested` asset by querying for the *latest* `asset_attestors` unit stable as of the currently validating unit's `last_ball_mci`, not as of when the spender's coins were received: [1](#0-0) 

This attestor list is what gets used to validate any owner address trying to spend/output the asset, both for public divisible payments and for private fixed-denomination payments: [2](#0-1) [3](#0-2) 
and for output addresses of a payment: [4](#0-3) 

The attestor list itself can be updated at will by the definer through a single-authored `asset_attestors` message. Validation of this update only checks that the sender is the asset's definer and that the new list is well-formed — it performs no check on outstanding balances, in-flight private payments, or previously-attested holders: [5](#0-4) 

This is structurally the same defect class as the reported bug: a single privileged party can change a value (`vusd` address / attestor list) that other users' already-received funds depend on, and the change is applied retroactively to funds that were acquired under the old value, with no reconciliation or grandfathering logic — exactly the missing `balance()` check the report recommends adding to `syncDeps()`.

### Impact Explanation
A user (a private-payment counterparty, or any holder of a `spender_attested` asset) can legitimately receive private or public units of the asset while attested. Before that user gets a chance to spend or move those units, the asset definer publishes a new `asset_attestors` unit that removes the user's attestor status (or attests a completely different set of addresses). From that point on, any attempt by the user to spend those previously valid coins fails validation (`"owner address is not attested"` in `validatePaymentInputsAndOutputs`), because `readAsset()` always fetches the *current* attestor list rather than the one that was current when the coins were received. The user's coins become permanently frozen/unspendable with no path to recover them, even though the funds were validly acquired. This matches the allowed "AA fund loss or freezing" / private-payment counterparty impact category.

### Likelihood Explanation
The trigger requires only the asset definer to publish one additional message (`asset_attestors`), which is a normal, permitted operation for any `spender_attested` asset and needs no special network privilege — it is directly reachable by the "asset issuer" actor explicitly allowed in scope. Any asset that uses `spender_attested` (e.g., compliance/KYC-gated tokens, common in Obyte-based DeFi/token issuances) is exposed. The race window (received while attested, then de-attested before spending) is realistic for any token with periodic attestor-list rotation.

### Recommendation
Anchor the attestor-eligibility check to the time the payer's/payee's coin was created (or to the moment the coins were received) rather than to the "latest" attestor list at spend-validation time, or provide a grace period / migration path so previously-attested holders can move already-received funds before a new attestor list revokes their status. Alternatively, require attestor-list changes to explicitly account for currently outstanding balances of previously attested addresses, analogous to the suggested `syncDeps()` fix of checking `balance()` before and after the dependency swap.

### Proof of Concept
1. Definer creates asset `A` with `spender_attested: true` and attestor list `[X]`.
2. Attestor attests address `Bob` (`Bob` is now in `arrAttestedAddresses` per `filterAttestedAddresses`).
3. Alice sends Bob a private payment of asset `A` while `Bob` is attested; the payment validates successfully per `validatePaymentInputsAndOutputs` (`validation.js:2630-2641`).
4. Before Bob spends the received coins, the definer publishes an `asset_attestors` message for asset `A` with a new list that excludes `Bob` (`validation.js:2829-2848` allows this unconditionally).
5. Bob now tries to spend his previously-received coins. `storage.readAsset()` fetches the new (latest) attestor list (`storage.js:1917-1946`), `Bob` is no longer in `arrAttestedAddresses`, and his spend fails at `"owner address is not attested"` (`validation.js:2432` / `2506`).
6. Bob's funds are permanently stuck — there is no mechanism to spend coins received before the list changed.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
