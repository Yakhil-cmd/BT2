Confirmed root-cause binding: `WebhooksController#verify_signature` selects which GitHub App/organization secret to check against using `repository_owner`, which is read straight from the unauthenticated JSON body (`params.dig('repository', 'owner', 'login')` or `organization.login`), i.e. the field used to pick the trust anchor (`Shipit.github(organization: repository_owner)`) is not itself covered by that anchor's signature check — it's just trusted attacker-controlled JSON. The event handlers, however, resolve the actual `Repository`/`Stack` to mutate using a *different* field of the same payload: `payload.dig('repository', 'full_name')` (see `Handler#repository_name`, `PushHandler#process`, `OpenedHandler#repository`, etc.). This creates exactly the "organization authenticated vs. repository written" binding class from the prompt.

### Title
Webhook organization used to select verification secret is disjoint from the repository the handler writes to — cross-tenant status/state injection - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` derives the GitHub App/secret used for HMAC verification from `repository.owner.login` (or `organization.login`) in the *unverified* request body, then the actual mutation performed by the handler (`Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`) resolves its target `Stack`/`Repository` using `repository.full_name`, a separate field of that same unverified body.

### Finding Description
`verify_signature` in [1](#0-0)  computes:
```
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
`repository_owner` comes straight from the JSON body [2](#0-1) , before any signature has been checked. `verify_webhook_signature` itself just HMACs the raw body against whichever org's `webhook_secret` was picked by that field [3](#0-2) .

Once verification passes, `create` dispatches the entire parsed payload to handlers [4](#0-3) . Handlers such as `PushHandler` and the `PullRequest` handlers resolve their target stack not from `repository.owner.login`, but from `repository.full_name` via `Repository.from_github_repo_name` [5](#0-4) [6](#0-5) .

Equality that should hold but doesn't: `verified_secret(payload.repository.owner.login) == secret_covering(payload.repository.full_name)`. Because Shipit supports multiple GitHub Apps/orgs each with an independently configured `webhook_secret` [7](#0-6) , an operator/attacker who legitimately controls (or has compromised) the `webhook_secret` for organization A can forge a request where `repository.owner.login = "A"` (so their own valid signature verifies) while `repository.full_name = "B/some-repo"` for a completely different, unrelated organization/repository whose stack is tracked by this same Shipit instance.

### Impact Explanation
This lets a party with only organization A's webhook secret inject fabricated `push`, `status`, `check_suite`, or `pull_request` events against organization B's stacks — forcing `stack.sync_github(expected_head_sha: ...)`, fabricating commit `Status` records, or firing pull-request label/archive logic on someone else's repository, all validated against a secret that has nothing to do with that repository. Whether this rises to write access on the target stack's deploy pipeline depends on what those handlers subsequently trigger (e.g., forged CI `status` can be required/blocking status data consumed by the merge queue's `all_status_checks_passed?` / `StatusChecker`, potentially unblocking automated merges for an unrelated stack). This is a cross-repository/cross-tenant write achieved without holding the correct organization's credential.

### Likelihood Explanation
Requires the attacker to hold a valid `webhook_secret` for *any one* organization configured in the multi-tenant `secrets.github` map — this is a legitimate, low-privilege credential compared to `GITHUB_TOKEN`, an `ApiClient` token, or a GitHub App private key, and is explicitly a scenario this engine's own docs anticipate (multiple GitHub Apps configured via `Shipit.github(organization:)`, see `test/unit/shipit_test.rb`). No repository write access, session, or GitHub App key is needed for org A's holder to affect org B's data — only crafting a JSON body with mismatched `repository.owner.login` vs `repository.full_name`.

### Recommendation
Verify the signature using the same repository identity the handlers act on (`repository.full_name`), and ensure the resolved `Repository`/`Stack`'s configured owner matches the organization whose secret validated the signature before dispatching to handlers — i.e. re-derive/require `repository.owner.login` to equal the owner segment of `repository.full_name`, or bind webhook secrets per-repository/per-stack rather than trusting an unauthenticated field to select the verifying secret.

### Proof of Concept
1. Shipit is configured with two GitHub Apps: org `A` (attacker-controlled, secret `SECRET_A`) and org `B` (victim, secret `SECRET_B`), each tracked as stacks in the same Shipit instance — mirroring the multi-org config demonstrated in [8](#0-7) .
2. Attacker (who legitimately owns org `A`'s GitHub App/secret) crafts a `push` payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "A" }, "full_name": "B/victim-repo" }
}
```
3. Attacker signs the raw body with `SECRET_A` and sets `X-Hub-Signature`.
4. `verify_signature` computes `repository_owner == "A"`, loads `Shipit.github(organization: "A")`, and the HMAC checks out against `SECRET_A` [1](#0-0) .
5. `create` dispatches the same payload to `PushHandler`, which resolves the stack via `repository.full_name = "B/victim-repo"` [5](#0-4)  and triggers `stack.sync_github(expected_head_sha: params.after)` on org B's stack — despite the signature never having been checked against `SECRET_B`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
