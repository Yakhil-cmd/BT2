### Title
Cross-organization webhook forgery via decoupled signature-organization and payload-repository fields - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and thus which `webhook_secret`) to validate the HMAC signature against by reading `repository.owner.login` (or `organization.login`) straight out of the *unauthenticated* JSON body. [1](#0-0)  Once the signature check passes, every registered handler locates the `Repository`/`Stack` to act on using a *different* field of the same payload: `repository.full_name`. [2](#0-1)  Nothing enforces that `repository.full_name` is owned by `repository.owner.login`/`organization.login`. In a Shipit instance configured with multiple GitHub organizations (a documented, supported deployment shape, e.g. `config/secrets.development.shopify.yml`), an attacker who legitimately owns a webhook integration for *their own* onboarded organization (Org A) can forge a payload whose `owner.login` is Org A (so the signature verifies with Org A's `webhook_secret`, which the attacker legitimately knows) but whose `repository.full_name` names a repository belonging to a different, unrelated organization (Org B) also hosted on the same Shipit instance. This breaks the equality: `organization that authenticated (owner.login used for HMAC selection) == repository that is written (full_name used by the handler)`.

### Finding Description
`verify_signature` derives the org used to pick the verifying `webhook_secret` this way:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [3](#0-2) 

`Shipit.github(organization:)` looks up the per-organization app config (each with its own `webhook_secret`), as shown by the multi-org secrets layout. [4](#0-3) 

After the signature is accepted, event processing dispatches to handlers built on `Handlers::Handler`, whose `stacks`/`repository_name` helper reads a completely different payload key:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [2](#0-1) 

`Repository.from_github_repo_name` splits this attacker-controlled string on `/` and resolves it to whatever `Repository` row matches, with no relation back to the verified `repository_owner`. [5](#0-4) 

So the HMAC only proves "this request was signed by the holder of Org A's `webhook_secret`" — it says nothing about which repository the payload's `full_name` actually refers to. Any organization configured in Shipit's `github` secrets can therefore forge webhook events that are attributed to any other organization's repositories/stacks in the same Shipit instance.

### Impact Explanation
Handlers act on the state of the target repo's `Stack`/`Commit` records once `stacks`/`repository_name` resolves. For example, the `status` event handler creates a `Status` for an arbitrary `sha` on the resolved stack/commit (see the analogous unsigned-field acceptance demonstrated in `test/controllers/webhooks_controller_test.rb`, `":state create a Status for the specific commit"`). [6](#0-5)  Because CI gating (`ci.require`) and merge/continuous-deployment automation in Shipit rely on `Status` rows attached to commits, an attacker with only their own onboarded organization's webhook credential can inject fabricated "success" statuses (or push/sync events) against a victim organization's stack that they have no authorization over, and thereby unblock/trigger an unauthorized deploy of that unrelated repository. This lands squarely in the "High" bucket defined by the rules: escalation that leads to an unauthenticated write/unauthorized deploy on state the attacker was never granted, crossing the trust boundary between "organization whose secret authenticated the request" and "repository the request is allowed to mutate."

### Likelihood Explanation
Exploitation requires the attacker to control a legitimately-configured GitHub organization/App entry already present in the multi-tenant Shipit deployment (i.e., their own repos are hooked up to the same Shipit instance) — this is an ordinary, unprivileged position for any org onboarded to a shared Shipit deployment, not an insider/admin of Shipit itself, and does not require possession of the victim's `webhook_secret`, `api_clients_secret`, or a Shipit session/GitHub App key. The only "privilege" the attacker needs is the same one an ordinary webhook subscriber already has for their own repo, making this a realistic, low-effort forgery once multiple orgs share one Shipit instance.

### Recommendation
After signature verification succeeds, validate that the resolved verifying organization equals the owner encoded in `repository.full_name` (and `organization.login` where relevant) before dispatching to handlers, e.g. reject the request if `repository_owner != payload.dig('repository', 'full_name')&.split('/')&.first`. Alternatively, bind handlers' repository resolution to the same trusted `repository_owner` value used for signature verification rather than re-reading an independent, unauthenticated payload field.

### Proof of Concept
1. Shipit is configured with two organizations, `orgA` and `orgB`, each with its own `webhook_secret` (as supported by `config/secrets.development.shopify.yml`).
2. Attacker owns/administers a GitHub App installation for `orgA`, and thus knows/can compute a valid `X-Hub-Signature` using `orgA`'s `webhook_secret`.
3. Attacker sends a `status` (or `push`) webhook to `WebhooksController#create` with body:
   ```json
   {
     "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" },
     "sha": "<victim commit sha>",
     "state": "success",
     "context": "ci/required-check",
     "target_url": "https://attacker.example.com"
   }
   ```
   signed with `orgA`'s secret.
4. `verify_signature` computes `repository_owner` = `"orgA"`, fetches `orgA`'s `github_app`, and the signature validates successfully. [7](#0-6) 
5. The `status` handler then resolves `repository_name` = `"orgB/victim-repo"` via `payload.dig('repository', 'full_name')` and writes a fabricated `Status` on `orgB`'s commit — an organization the attacker never authenticated as and has no relationship with. [2](#0-1)
