### Title
Attacker-controlled recursive submodule structure causes excessive execution time / persistent sync denial - (File: `main.go`, function `configureWorktree`)

### Summary
`git-sync` syncs an operator-specified `--repo`, but the content of that repository — including its `.gitmodules` file, submodule tree, and submodule commit graph — is attacker-controlled if the upstream repo/ref is writable by an untrusted party (e.g., a CI bot pushing to a branch that git-sync tracks, or a webhook-triggered ref update). When `--submodules=recursive` (the default), `configureWorktree` unconditionally runs `git submodule update --init --recursive` with no bound on submodule nesting depth, submodule count, or per-submodule size.

### Finding Description
On every successful fetch of a new hash, `git-sync` calls `configureWorktree`, which builds and runs a recursive submodule update: [1](#0-0) 

The submodule mode defaults to `"recursive"`: [2](#0-1) 

There is no limit on the number of submodules, the recursion depth, or the total number of objects/blobs that `git submodule update --recursive` will process — this is entirely determined by the content of the tracked repository (which, transitively through submodule pointers, can reference an attacker-controlled chain of repos, each adding its own `.gitmodules` with further submodules). A malicious or compromised upstream content owner can construct a repository whose submodule graph is deep or wide enough (e.g., many levels of nested submodules, or a submodule fan-out) that a single `git submodule update --recursive` invocation takes a very long time or effectively hangs doing many sequential clone/checkout operations, analogous to the recursive `CALL`/`SELFDESTRUCT` gas-accounting flaw in the EVM report where deep, cheap recursion produced disproportionate execution cost relative to the resource accounting model.

Because `--sync-timeout` bounds only one *sync attempt* (via a `context.Context` passed down to `git.Run`), an oversized submodule tree causes that attempt to be killed on timeout, but the process will retry on the next `--period` tick and repeat the same expensive recursive submodule walk indefinitely, since nothing caches partial progress across attempts and nothing bounds recursion independent of wall-clock time.

### Impact Explanation
This matches the "persistent sync denial" impact category: a git-sync sidecar pointed at a repository containing (or later updated to contain, by an attacker with push/merge access to the tracked ref) a deeply/widely nested submodule graph will never complete a sync, repeatedly consuming CPU, memory, disk I/O, and network bandwidth on every period without ever publishing a new (or first) revision via the `--link` symlink. In `--one-time` bootstrap use, this permanently prevents the application container from starting. This is a resource-exhaustion / availability issue, not a memory-safety or credential-disclosure issue.

### Likelihood Explanation
Likelihood is limited to scenarios where the tracked repository content itself is attacker-influenced (e.g., an untrusted contributor's branch/PR-merge-target is synced, or a compromised upstream/dependency repo is used as a submodule source) — consistent with the "unprivileged, attacker-pushed-content" scope. `--submodules=recursive` is the default, so no special flag is required to be exposed; an operator only needs to configure git-sync against an untrusted or externally-influenced ref.

### Recommendation
- Document and/or enforce a configurable cap on submodule recursion depth / total submodule count before invoking `git submodule update --recursive` (e.g., pre-scan `.gitmodules` recursively via `git config -f` parsing and abort with a clear error if limits are exceeded).
- Consider defaulting `--submodules` to `shallow` or `off` for untrusted-content deployments, and calling out the DoS risk of `recursive` in the `--submodules` flag documentation.
- Ensure `--sync-timeout` failures from an oversized submodule tree are surfaced distinctly (e.g., a dedicated metric/log) so operators can detect "stuck on submodules" versus generic network failures.

### Proof of Concept
1. Attacker (with push access to the branch/ref that git-sync tracks) commits a `.gitmodules` referencing a submodule repo, and that submodule repo itself references another nested submodule, repeated to a large depth (or fans out to many submodules at one level) — analogous to the e2e nested-submodule test setup already present in the codebase: [3](#0-2) 
2. Run `git-sync --repo=<attacker-controlled-repo> --root=... --link=link` with default `--submodules=recursive`.
3. `configureWorktree` invokes `git submodule update --init --recursive`: [4](#0-3) 
4. With a sufficiently deep/wide submodule graph, the command exceeds `--sync-timeout` (default 120s), the sync attempt fails, and it is retried every `--period`, never publishing content and continuously consuming resources.
