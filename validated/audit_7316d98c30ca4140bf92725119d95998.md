### Title
Webhook signature verification keys off attacker-controlled `repository.owner.login` while status/CI handlers act on a globally-scoped, cross-repository `sha` — forged CI status can be attributed to any stack's commit - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
The reported bug class is a "commitment"/binding check that compares the wrong two quantities, so it can never actually reject the attacker's forged input. In this engine, the same class of defect exists in the webhook pipeline: the code that decides *which organization's secret* to verify a webhook against is chosen from an attacker-controlled JSON field (`repository.owner.login`), and none of the downstream handlers re-derive or re-check that the *acted-upon* data (commit `sha`, and thus the `Stack`/repository ultimately affected) belongs to that same organization/repository. The binding "verified organization == organization whose data is written" is never enforced.

### Finding Description
`WebhooksController#verify_signature` selects the `GitHubApp` (and therefore the `webhook_secret` used for HMAC verification) using a value taken straight from the untrusted JSON body, before the signature has been checked: [1](#0-0) [2](#0-1) 

Once the signature is confirmed to match *some* organization's own webhook secret (an org the attacker legitimately controls and has a GitHub App installed for — installing a GitHub App on your own org/repo requires no privilege over anyone else's data), `WebhooksController#create` hands the entire attacker-controlled `params` hash to the registered handlers unmodified: [3](#0-2) 

`StatusHandler#process`, however, does not scope its effect to the repository/organization that was authenticated at all — it looks up commits **globally by `sha`** and writes a GitHub-status onto every matching `Commit` row in the entire Shipit database, regardless of which stack/repository owns it: [4](#0-3) 

Note it doesn't even use the `Handler#repository_name`/`stacks` helper that other handlers use: [5](#0-4) 

So the binding that should hold — *"the organization whose webhook secret verified this request" == "the repository/stack whose commit gets a new status"* — is broken: verification is keyed on `repository.owner.login`, but the actual write is keyed only on `sha`, a field the sender fully controls and which is never cross-checked against `repository.full_name`/owner.

`create_status_from_github!` feeds directly into `Commit#add_status` via `after_commit` hooks (`schedule_continuous_delivery`, `ProcessMergeRequestsJob` scheduling on success), so a forged "success" status on a victim stack's commit can unblock continuous deployment / the merge queue for a repository the attacker has no access to: [6](#0-5) [7](#0-6) 

### Impact Explanation
An attacker who legitimately controls their own GitHub organization/repository (with a Shipit-managed GitHub App installed, satisfying only their own tenant's requirements — no credentials or access to the victim organization are needed) can:
1. Sign an arbitrary webhook payload with their own org's `webhook_secret` (obtained trivially by owning the GitHub App installation for their own org).
2. Send an `X-Github-Event: status` webhook whose `sha` is a real commit SHA belonging to a *different*, unrelated stack/repository tracked by the same Shipit instance (commit SHAs are public information visible on GitHub).
3. Because `StatusHandler` matches `Commit.where(sha: params.sha)` with no repository/stack scoping, and `verify_signature` never re-confirms that the payload's `repository.full_name` matches the org whose secret validated the signature, the forged `state: success` status is attached to the victim's commit.
4. This can bypass required CI checks (`deployable?`), unblock the merge queue (`ProcessMergeRequestsJob`), and trigger an unauthorized/automatic deploy of a commit that never actually passed CI — a cross-repository write and an unauthorized deploy, matching the Critical bar in the rules ("cross-repository writes, or an unauthorized deploy").

### Likelihood Explanation
Any Shipit installation that manages more than one GitHub organization/repository (as explicitly supported and documented, e.g. `config/secrets.development.shopify.yml` showing multiple org configs, each with its own `webhook_secret`) is exposed. The attacker needs no privileges over the victim repository at all — only a legitimately-installed GitHub App for their own tenant, which is a normal, low-friction onboarding action in a multi-tenant Shipit deployment. This is a realistic, unprivileged, cross-tenant attack surface, not a theoretical one.

### Recommendation
- In `WebhooksController`, after verifying the signature, re-derive the organization/repository from the verified webhook source (or additionally verify that `params.dig('repository','full_name')`'s owner matches `repository_owner` used for signature selection) before dispatching to handlers.
- In `StatusHandler#process` (and any other handler that resolves records purely by `sha`), scope the lookup by the stack(s) belonging to `payload.dig('repository', 'full_name')` (as `Handler#stacks` already does for other handlers), instead of a global, cross-tenant `Commit.where(sha: ...)`.
- Add a regression test asserting that a validly-signed webhook for organization A cannot mutate commit/status state belonging to a stack under organization B.

### Proof of Concept
1. Attacker owns GitHub org `attacker-org`, installs the Shipit GitHub App on it, and Shipit is configured (per `docs/setup.md`) with a `webhook_secret` for `attacker-org`.
2. Attacker finds a public commit SHA `<victim_sha>` belonging to a stack tracked under `victim-org/victim-repo` in the same Shipit instance.
3. Attacker crafts and correctly HMAC-signs (using `attacker-org`'s own webhook secret) a `status` event body:
```json
{
  "sha": "<victim_sha>",
  "state": "success",
  "context": "ci/travis",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/attacker-repo" }
}
```
4. `WebhooksController#verify_signature` looks up `Shipit.github(organization: "attacker-org")` (derived from `repository.owner.login`) and successfully verifies the signature against the attacker's own secret.
5. `StatusHandler#process` runs `Commit.where(sha: "<victim_sha>")` — matching the victim's commit regardless of the `repository.full_name` field in the same payload — and creates a `success` status on it, potentially unblocking deploy/merge for the victim stack.
