### Title
Missing cross-transaction replay protection for L1 Bitcoin lockup outpoints in `verify-l1-lockups` allows double-counting a single BTC lock into multiple pox-5 stake credits - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
`pox-5.clar`'s L1 lockup verification path (`verify-l1-lockups` / `validate-l1-lockup`) only deduplicates Bitcoin outpoints *within a single call's list of proofs*, via a `seen-outpoints` accumulator that is reinitialized to `(list)` on every invocation. There is no persistent on-chain record of previously-credited outpoints, so the same real Bitcoin lockup UTXO can be re-submitted (with a fresh, still-valid merkle/header proof for the same, already-used transaction) across separate `register-for-bond`/rollover calls and be credited again.

### Finding Description
`verify-l1-lockups` folds over the caller-supplied list of `lockups.outputs` via `validate-l1-lockup`, starting the accumulator with `seen-outpoints: (list)`: [1](#0-0) 

`validate-l1-lockup` checks the unlock height, the script, the amount, and rejects duplicates only against this same, per-call `seen-outpoints` list: [2](#0-1) 

Crucially, the checks performed (block header validity, merkle inclusion, script match, amount match, unlock-height bound) all validate that a *given Bitcoin transaction output exists and locks BTC to the staker's timelock script* — but none of them assert that this specific `(txid, output-index)` pair has never been credited before, in any prior transaction. The dedup list `seen-outpoints` is local to the current `fold`/call and is discarded once the call returns; it is not persisted in any map (no `used-l1-outpoints`/similar map exists in the contract). Consequently, a staker can submit the *same* previously-valid BTC lockup proof again in a later transaction — e.g., a subsequent `register-for-bond` call for a different `bond-index`, or a repeat/rollover registration — and `validate-l1-lockup` will accept it exactly as before, crediting `sum` (and hence stake shares / signing weight for the reward cycle) a second time, without any additional BTC ever being locked.

This is directly analogous to the WEBrick request-smuggling bug class: one validation layer (the per-call fold) enforces an invariant ("no duplicate outpoint") only locally/transiently, while the broader system (the persistent staking/reward state across multiple transactions) has no matching, durable enforcement of that same invariant — letting a single underlying artifact (a Bitcoin lockup output) be "smuggled" through the pipeline more than once and interpreted as two distinct commitments.

### Impact Explanation
This breaks the equality "sats credited to a staker's L1-backed bond shares == sats actually locked once on Bitcoin." Re-submitting the same lockup lets an unprivileged staker double-count (or n-times count) a single BTC lock across multiple `bond-index` registrations, inflating `total-shares-staked-for-cycle` / `signer-shares-staked-for-cycle` / `staker-shares-staked-for-cycle` and the staker's proportional reward and signing-weight entitlement without backing it with additional locked BTC. Per the rules, double-counting a commitment maps to Critical severity; at minimum it grants stake/signing weight exceeding the value actually locked (High).

### Likelihood Explanation
The attack requires no special privileges — any staker who legitimately locked BTC once for `register-for-bond` can simply resubmit the identical proof (same header, tx, merkle path, output-index) in a fresh transaction targeting a different (or the same, if permitted) bond registration. No signer, admin, or oracle cooperation is needed; the proof data itself is public once the original lockup transaction is confirmed.

### Recommendation
Persist a durable map (e.g., `used-l1-outpoints: { txid: (buff 32), output-index: uint } -> bool`) and check/insert into it inside `validate-l1-lockup` (or immediately after `verify-l1-lockups` returns) so that once an outpoint has been credited to any staker/bond, subsequent attempts to credit it again are rejected with a dedicated error (e.g., `ERR_DUPLICATE_LOCKUP_OUTPOINT` reused for the persistent case). This closes the gap between the transient per-call dedup and the durable cross-transaction state.

### Proof of Concept
1. Staker locks BTC into the timelock script for `bond-index = 0`, producing a valid Bitcoin output `(txid T, output-index N)`.
2. Staker calls `register-for-bond` (bond 0) with a lockup proof for `(T, N)`. `verify-l1-lockups`/`validate-l1-lockup` accept it and credit `sum` sats to bond 0's shares.
3. A second bond (`bond-index = 1`) is set up (or the staker later re-registers). The staker calls `register-for-bond` again, submitting the *same* proof for `(T, N)` (still perfectly valid: same header, same merkle path, same script/amount).
4. Because `seen-outpoints` was re-initialized to `(list)` for this new call, and no persistent map records that `(T, N)` was already used, `validate-l1-lockup` accepts it again, crediting the same sats a second time — doubling the staker's effective stake/signing weight without locking any additional BTC.
