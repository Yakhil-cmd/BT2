### Title
Unbounded per-account position maps let an attacker build an unliquidatable account, trapping bad debt and freezing funds - (File: contracts/controller/src/risk/totals.rs)

### Summary
The libexpat CVE is a resource-consumption DoS: one large input forces many full reparsings, so cost grows super-linearly with attacker-controlled size. The on-chain analog is an attacker-inflated position book: `supply_positions`/`borrow_positions` are `Map`s with no cardinality bound, and every risk, liquidation, and bad-debt path iterates them in full inside a single Soroban invocation whose budget is fixed. An account with one position per listed hub asset can push `calculate_account_risk_totals` past the transaction resource limit, making `liquidate` and `clean_bad_debt` permanently unexecutable for that account.

### Finding Description
Every liquidation begins with `build_liquidation_plan`, which calls `risk::calculate_account_risk_totals` over the full supply and borrow maps in `contracts/controller/src/positions/liquidation/plan.rs:34-39`. That function iterates every supply position (price fetch, index fetch, three valuations per entry) at `contracts/controller/src/risk/totals.rs:171-199` and every debt position at `contracts/controller/src/risk/totals.rs:48-60`, and additionally loads each hub market via `cache.load_markets(&portfolio_hub_keys(...))` at `totals.rs:163-166`, which is itself linear in the number of distinct positions. The seizure side then iterates all collateral legs again at `plan.rs:73-89`, and `execute_bad_debt_cleanup` re-iterates both books at `contracts/controller/src/positions/liquidation/bad_debt.rs:22-47`.

No code path caps `account.supply_positions.len()` or `account.borrow_positions.len()`; a `supply` call with any hub asset adds a map entry. There is no partial liquidation that targets a subset of collateral books — the plan is always computed over the whole account. Like the libexpat bug, a single attacker-controlled dimension (number of positions ≈ number of listed hub assets, expandable across spokes) forces repeated full-map scans, each far more expensive than the marginal cost of opening a dust position.

### Impact Explanation
An account that cannot be liquidated cannot be saved once its health factor falls below 1: `liquidate` fails on budget exhaustion before reaching `build_liquidation_plan`, and `clean_bad_debt` fails in `execute_bad_debt_cleanup` for the same reason. The debt position then accrues interest unbounded while collateral stays locked, so the account drifts into deep insolvency that the protocol can neither seize nor socialize — bad debt that `apply_bad_debt_to_supply_index` in `contracts/pool/src/interest.rs:73-89` was designed to absorb is never reached, and suppliers' funds are effectively frozen/lost pro-rata. This is permanent freezing of funds plus protocol insolvency, not a transient fail-closed DoS: no sequence of transactions can recover the account because every recovery entrypoint shares the same unbounded iteration.

### Likelihood Explanation
Reachable by any unprivileged address through `supply`. The attacker opens one account, supplies a minimal amount into every listed hub asset (and can multiply entries across hubs/spokes since keys are `(hub, token)`), borrows against the book, and waits for or engineers HF < 1. Cost is dust per market; there is no penalty for holding many positions. The only mitigating factor is that the market list is governance-controlled and bounded, so feasibility depends on how many `(hub, token)` markets exist; each additional listed market monotonically increases liquidation cost with no compensating bound.

### Recommendation
Enforce a protocol-side cap on total positions per account (checked at every verb that inserts into `supply_positions`/`borrow_positions`), sized so the worst-case liquidation stays comfortably within the Soroban budget; alternatively, support partial liquidation that plans over a caller-specified subset of collateral legs so a large book can be unwound in multiple transactions.

### Proof of Concept
1. Attacker calls `controller.supply(caller, 0, spoke_id, legs)` once per listed hub asset with dust amounts, filling `supply_positions` to N entries.
2. Attacker calls `borrow` to take on debt; price movement pushes HF < 1 WAD.
3. Any liquidator calling `liquidate(payments)` hits `calculate_account_risk_totals` (`totals.rs:157-216`), which performs ~3 price/index lookups and multiplications per position plus `load_markets`; the invocation exceeds the Soroban CPU/memory budget and aborts before seizure.
4. `clean_bad_debt` aborts the same way inside `execute_bad_debt_cleanup`'s full-book loops (`bad_debt.rs:22-47`), so the bad debt can never be written down against the supply index — the insolvency is permanent.
