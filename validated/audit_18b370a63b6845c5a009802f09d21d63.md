## Analysis

In a multi-organization Shipit deployment (`config/secrets.yml` supporting the `github: {org1: {...}, org2: {...}}` schema per `lib/shipit.rb#github_app_config`), `WebhooksController#verify_signature` selects which organization's `webhook_secret` to verify against using a field read from the **unverified** JSON payload itself: [1](#0-0) [2](#0-1) 

Meanwhile, the actual handler that decides *which repository/stack gets written to* (e.g. `PushHandler`) resolves the target repository from a **different** field of the same payload — `repository.full_name` — via `Repository.from_github_repo_name`: [3](#0-2) [4](#0-3) [5](#0-4) 

`repository_owner` (used to pick `webhook_secret`) and `repository.full_name` (used to pick the `Stack`/`Repository` that gets written) come from the **same untrusted JSON body** and are logically supposed to refer to the same repository, but nothing enforces that they match. However, to actually forge a valid signature, an attacker still needs the correct `webhook_secret` for *some* configured organization — which they'd only have if they control a repo under that org's GitHub App installation. In that scenario they could sign a payload with their own org's secret (`repository.owner.login` = their org) but set `repository.full_name` to a victim repository/stack belonging to a *different* configured organization in the same Shipit instance, and `verify_signature` would happily validate it because it only checked the secret for the attacker's own (correctly identified) org, while the handler acts on the victim's repository name embedded in the same payload.

This satisfies the "organization that authenticated versus the repository that is written" binding: verification proves "the sender knows org A's secret," but the handler applies effects to whatever `repository.full_name` says, which could reference org B's repository/stack — allowing an attacker who has legitimate GitHub App access to one configured organization to trigger `GithubSyncJob`, deploy status changes, pull-request/review-stack provisioning, or check-run refreshes against a stack belonging to an entirely different organization/repository configured on the same Shipit instance.

### Title
Webhook signature verification authenticates the payload's claimed organization but handlers act on an unbound repository field, enabling cross-organization webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the `webhook_secret` to validate against based on `repository_owner`, itself read from the unverified payload (`params.dig('repository','owner','login')` or `organization.login`). Once a valid HMAC is found for *that* organization, the entire raw payload is dispatched to handlers, which independently derive the affected repository from `payload.dig('repository','full_name')` (`Handler#repository_name`) with no re-check that it matches the organization whose secret validated the signature.

### Finding Description
In multi-org configurations (`lib/shipit.rb#github_app_config`, keyed by organization), each org has its own `webhook_secret`. `verify_signature` picks the app/secret via `repository_owner`, extracted straight from the payload body, then calls `github_app.verify_webhook_signature(signature, raw_post)` over the *entire* raw payload. The signature check is really "was this raw body signed with org X's secret" — it does not restrict which `repository.full_name` may appear inside that body. Handlers such as `PushHandler`, `PullRequest::OpenedHandler/ClosedHandler/ReopenedHandler`, and others use `repository.full_name` (a sibling field of `repository.owner.login`) to look up `Repository.from_github_repo_name` and act on its `stacks`/`review_stacks`. An attacker who legitimately controls (or has app access to) one configured GitHub organization/repo in the same Shipit instance can craft a payload where `repository.owner.login` matches their own org (so the signature check picks their own, correct, `webhook_secret`) while `repository.full_name` names a repository belonging to a different configured organization, since nothing binds these two fields together during verification.

### Impact Explanation
This crosses a repository-write boundary: a party authorized only for organization A's webhooks can trigger organization B's stack sync, review-stack provisioning/archival, or check-run refresh jobs — effectively cross-repository writes/actions not authorized by B, satisfying the "cross-repository writes" Critical impact category.

### Likelihood Explanation
Requires the attacker to have legitimate webhook-signing capability for at least one organization configured in the same multi-org Shipit deployment (i.e., control of a GitHub App installation's webhook secret for org A), which is a real but non-trivial precondition; single-organization deployments (the common case, `github_default_organization` returns `nil`) are not affected since there's only one secret to check.

### Recommendation
Bind organization identity into the resolution used by handlers: after verifying the signature for `repository_owner`, re-derive/require that `payload.dig('repository','full_name')` split by `/` yields the same owner (`repository_owner`) before dispatching to handlers, rejecting the webhook otherwise.

### Proof of Concept
1. Configure Shipit with two organizations, `orgA` and `orgB`, each with its own `webhook_secret`, both defined under `secrets.github`.
2. Attacker controls a GitHub App/webhook secret for `orgA` (e.g., is an admin of an `orgA` repo/installation).
3. Attacker crafts a `push` payload: `repository.owner.login = "orgA"`, `repository.full_name = "orgB/victim-repo"`, `ref = "refs/heads/main"`, `after = "<attacker-chosen sha>"`.
4. Attacker signs the raw body with `orgA`'s `webhook_secret` and sets `X-Hub-Signature` accordingly.
5. `WebhooksController#verify_signature` looks up `repository_owner` = `"orgA"`, fetches `Shipit.github(organization: "orgA")`, and validates successfully.
6. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("orgB/victim-repo")` and triggers `stack.sync_github(expected_head_sha: params.after)` on `orgB`'s stack, despite the request never being authenticated by `orgB`'s secret.
