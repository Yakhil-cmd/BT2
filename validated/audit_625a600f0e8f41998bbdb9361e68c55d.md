### Title
Webhook signature is verified against the payload's self-declared `repository.owner.login`, but handlers act on the independently-controlled `repository.full_name` field — allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate an inbound webhook against using a field taken directly from the unauthenticated JSON body. The handlers that actually mutate state (e.g. `PushHandler`, `StatusHandler`) then resolve the target `Stack`/`Repository` from a *different*, independently-forgeable field in the same body. Because these two fields are never cross-checked, an attacker who controls (and therefore knows) the webhook secret for one organization/repository configured in the shared Shipit instance can forge a signed payload that authenticates as "their" organization while directing the write at a completely different, victim repository.

### Finding Description
`verify_signature` computes the org used for HMAC verification straight from the raw, unauthenticated body: [1](#0-0) [2](#0-1) 

`repository_owner` is `params.dig('repository', 'owner', 'login')` — a JSON field fully controlled by whoever is sending the HTTP request, evaluated *before* any signature has been validated. This value only determines whose webhook secret is used to check the HMAC (`Shipit.github(organization: repository_owner).verify_webhook_signature`).

Once the signature "passes" (because it was correctly computed with the secret belonging to the organization named in `repository.owner.login`), the raw parsed body is handed unmodified to the registered handlers: [3](#0-2) 

Handlers, however, resolve the actual `Repository`/`Stack` to act on from a *different* JSON field, `repository.full_name`, with no correlation back to `repository.owner.login`: [4](#0-3) [5](#0-4) 

Because `repository.owner.login` (the field bound by the signature check) and `repository.full_name` (the field the write is performed against) are two independent, attacker-supplied strings in the same JSON body, nothing stops them from disagreeing. An attacker who legitimately controls organization `orgA` in this shared Shipit deployment (and therefore knows `orgA`'s configured webhook secret) can send:

```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" }
}
```
HMAC-signed with `orgA`'s secret. `verify_signature` validates fine (it only ever looks at `orgA`), yet `PushHandler#stacks` resolves and acts on `orgB/victim-repo`.

### Impact Explanation
This breaks the trust binding "organization that authenticated == repository that is written," letting an attacker who is a legitimate, valid webhook sender for one org/repo forge state changes against any *other* repository/stack configured in the same Shipit instance — without ever having access to that victim repository. Concretely:
- `PushHandler` enqueues `GithubSyncJob` with an attacker-chosen `expected_head_sha` for the victim stack [6](#0-5) , forcing the victim stack's sync/deploy pipeline to react to a forged commit reference chosen by the attacker.
- Other handlers keyed the same way (status, check_suite) can inject forged commit statuses/check-run refreshes onto a victim's commits.

This is a cross-repository write triggered without any credential belonging to the victim organization — matching the "cross-repository writes" / "unauthorized deploy" Critical impact category.

### Likelihood Explanation
Requires only that the attacker legitimately administers (or has push/webhook-config access to) any one organization/repository already onboarded into the same Shipit instance — no privileged Shipit account, API token, or session is needed, since the whole exploit lives inside the unauthenticated `WebhooksController#create` endpoint. In any multi-tenant Shipit deployment (multiple orgs/repos configured, as the `GithubOrganizationUnknown`/`Shipit.github(organization:)` machinery implies), this is directly reachable.

### Recommendation
After computing `repository_owner` and verifying the signature, re-derive the repository/organization the handler is about to act on and assert it matches the authenticated organization (e.g., require `repository.full_name.split('/').first == repository_owner`, or better, resolve the `Stack`/`Repository` scoped to the verified organization only) before dispatching to handlers.

### Proof of Concept
1. Attacker legitimately controls org `orgA`, which is registered in the shared Shipit instance, and therefore knows/controls `orgA`'s GitHub App/webhook secret.
2. Attacker crafts a `push` event JSON body where `repository.owner.login = "orgA"` but `repository.full_name = "orgB/victim-repo"` (a real stack belonging to a different, victim organization `orgB` on the same Shipit instance), and sets `after` to an arbitrary SHA.
3. Attacker computes `X-Hub-Signature` using `orgA`'s webhook secret over this exact raw body and POSTs it to `/github/webhooks`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "orgA")` and the signature checks out, so the request is accepted [1](#0-0) .
5. `PushHandler.call(params)` runs, resolves `stacks` via `repository.full_name = "orgB/victim-repo"` [7](#0-6) , and enqueues `stack.sync_github(expected_head_sha: <attacker sha>)` for `orgB`'s stack — a write the attacker was never authorized to trigger.

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end
