## Title
Market-maker share-price manipulation via re-triggerable "initial deposit" branch mints shares disproportionate to contribution - (File: test/samples/uniswap_like_market_maker.oscript)

### Summary
The `uniswap_like_market_maker.oscript` sample AA that ships with ocore issues its `$mm_asset` liquidity-share token using a two-branch formula in the "invest in MM" case. The first branch, meant only for the very first deposit into an empty pool, is re-triggerable any time either reserve balance is driven to exactly zero, and it mints shares equal to the AA's entire current bytes balance rather than an amount proportional to the depositor's actual contribution and the outstanding share supply.

### Finding Description
In the "invest in MM" case, share issuance is computed as: [1](#0-0) 

```
$asset_balance = balance[$asset] - trigger.output[[asset=$asset]];
$bytes_balance = balance[base] - trigger.output[[asset=base]];
if ($asset_balance == 0 OR $bytes_balance == 0){ // initial deposit
    $issue_amount = balance[base];
    return;
}
...
$issue_amount = round($investor_share_of_prev_balance * var['mm_asset_outstanding']);
```

The `$asset_balance == 0 OR $bytes_balance == 0` branch is intended to fire only once, for the very first liquidity provider when the pool is empty. However, `$asset_balance` (the pool's pre-trigger asset reserve) can also become exactly `0` later in the pool's life through the normal "exchange bytes to asset" swap path, which lets any trigger sender drain the asset reserve toward zero via the constant-product formula: [2](#0-1) 

Because pool balances and swap amounts are `round()`-ed integers, a sufficiently large or repeated swap can push `$asset_balance` to exactly `0` without reverting. Once that happens, the very next "invest" call re-enters the "initial deposit" branch instead of the proportional-issuance branch, and mints `$issue_amount = balance[base]` — the AA's *entire current bytes balance* (which includes all bytes previously deposited by earlier liquidity providers) — to the new depositor, regardless of how small their actual deposit was, as long as it clears the `1e5` bytes / `>0` asset thresholds.

This mirrors the reported vault bug class: the share-minting formula has an edge case where the price/ratio check that normally protects other depositors (`$current_ratio`/`$expected_asset_amount` proportional-issuance branch) is bypassed, letting one participant mint a share amount disconnected from their real contribution relative to `var['mm_asset_outstanding']` and the pool's actual reserves.

### Impact Explanation
An attacker who can trigger the AA (any unprivileged AA trigger sender) can:
1. Drain `$asset` reserve to zero via repeated/large "exchange bytes to asset" swaps.
2. Immediately follow with a minimal "invest" deposit that re-enters the flawed "initial deposit" branch, minting `$mm_asset` equal to the pool's full bytes balance instead of a proportional share.
3. Immediately "divest" those shares, since divestment is proportional to `var['mm_asset_outstanding']`: [3](#0-2) 

This allows the attacker to redeem a disproportionately large fraction of `balance[base]` and `balance[$asset]` that rightfully belongs to earlier liquidity providers, resulting in fund loss for other depositors and permanent corruption of the `mm_asset_outstanding`/reserve accounting invariant — a direct AA fund-loss condition.

### Likelihood Explanation
Reachable by any address able to send a trigger unit to the AA (no privileged role required). It requires only ordinary payment/exchange messages already supported by the AA's own cases, so no special network condition, mempool timing, or validator collusion is needed — only sequencing two ordinary triggers (a swap followed by an invest) from the same or coordinated addresses.

### Recommendation
Guard the "initial deposit" branch so it can only apply when `var['mm_asset_outstanding']` is unset/zero (i.e., truly the first ever deposit), not merely when one reserve balance happens to be zero at call time, e.g. change the condition to check `!var['mm_asset_outstanding']` instead of `$asset_balance == 0 OR $bytes_balance == 0`. Additionally, consider requiring a minimum non-zero reserve floor (never letting a swap drive a reserve to exactly zero) to avoid this branch being reachable mid-life of the pool.

### Proof of Concept
1. Pool is live with liquidity providers holding shares proportional to `var['mm_asset_outstanding']`.
2. Attacker repeatedly calls the "exchange bytes to asset" case with large `base` amounts until `$asset_balance` (pool's asset reserve pre-trigger) rounds down to `0`.
3. Attacker sends an "invest in MM" trigger with `trigger.output[[asset=base]] > 1e5` and `trigger.output[[asset=$asset]] > 0` (minimal amount, e.g., a few units of `$asset` acquired earlier).
4. Because `$asset_balance == 0`, the AA executes `$issue_amount = balance[base]`, minting the attacker `$mm_asset` equal to the *entire* pool bytes balance rather than a small proportional amount.
5. Attacker immediately sends the received `$mm_asset` back in a "divest" trigger, redeeming a disproportionate share of `balance[$asset]` and `balance[base]`, extracting value contributed by earlier depositors.
