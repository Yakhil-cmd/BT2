CVE-2021-21382 describes a network relay service (TURN/restund) that, given attacker-controlled `XOR-PEER-ADDRESS`, would open a relay to loopback/internal addresses because it lacked address-class validation, exposing an unauthenticated administrative interface. Searching for the closest structural analog in this codebase — features where an untrusted actor supplies a network address/URL that the node then dials or relays to — turns up only:

- The offchain worker HTTP API (`sp_runtime::offchain::http`, `substrate/client/offchain/src/api/http.rs`), which is driven by the node's own runtime code and only active if the node operator explicitly enables offchain workers and HTTP capability; it is not reachable by an unprivileged external caller supplying arbitrary URLs. [1](#0-0) [2](#0-1) 
- `sc-network`/`cumulus` discovery and bootnode-advertisement code, which explicitly filters loopback and non-global addresses before dialing or advertising them (`is_global`/`is_loopback` checks), and multiple prdocs show this class of issue (loopback address leakage/dialing) has already been proactively hardened rather than left exploitable. [3](#0-2) [4](#0-3) 
- The RPC server's host filtering and `deny_unsafe` logic, which is specifically designed around loopback trust boundaries (`substrate/client/rpc-servers/src/utils.rs`), and is node-operator-configured, not attacker-reachable without a privileged/administrative RPC client role. [5](#0-4) 

None of these constitute a real user entry point (signed extrinsic, enabled contract call, or permitted XCM message) that lets an unprivileged attacker instruct the node to relay/connect to an arbitrary or loopback address to reach an otherwise-private administrative interface, which is the core invariant violated in the CVE. FRAME's pallet-contracts chain extension mechanism (`substrate/frame/contracts/src/chain_extension.rs`) is a chain-author-defined, non-networked host-function dispatch and is explicitly documented as the chain author's own security responsibility, not a network relay. No comparable open-relay/SSRF pattern with unauthenticated attacker-controlled destination addressing was found in FRAME, XCM, or contracts/revive production code.

impl HttpApi {
	/// Mimics the corresponding method in the offchain API.
	pub fn request_start(&mut self, method: &str, uri: &str) -> Result<HttpRequestId, ()> {
		// Start by building the prototype of the request.
		// We do this first so that we don't touch anything in `self` if building the prototype
		// fails.
		let (body_sender, receiver) = mpsc::channel(0);
		let body = StreamBody::new(receiver);
		let body = BoxBody::new(body);
		let mut request = hyper::Request::new(body);
		*request.method_mut() = hyper::Method::from_bytes(method.as_bytes()).map_err(|_| ())?;
		*request.uri_mut() = hyper::Uri::from_maybe_shared(uri.to_owned()).map_err(|_| ())?;

		let new_id = self.next_id;
		debug_assert!(!self.requests.contains_key(&new_id));
		match self.next_id.0.checked_add(1) {
			Some(new_id) => self.next_id.0 = new_id,
			None => {
				tracing::error!(
					target: LOG_TARGET,
					"Overflow in offchain worker HTTP request ID assignment"
				);
				return Err(());
			},
		};
		self.requests
			.insert(new_id, HttpApiRequest::NotDispatched(request, body_sender));

		tracing::trace!(
			target: LOG_TARGET,
			id = %new_id.0,
			%method,
			%uri,
			"Requested started",
		);

		Ok(new_id)
	}
