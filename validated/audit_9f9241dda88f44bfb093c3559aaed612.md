### Title
Attacker-chosen `creator` in `initialize_with_permission` allows creator fees to be permanently frozen in an unowned/unsignable token account - ([File: programs/cp-swap/src/instructions/initialize_with_permission.rs])

### Summary
The reported Footium bug is a class of "beneficiary-identity mismatch": prizes are earmarked for an address, but no signer capable of controlling that address exists (a club escrow) that can invoke the claim path, so funds cannot actually be spent/claimed by their intended owner and are effectively stuck. The Raydium `cp-swap` program has an analogous pattern: `initialize_with_permission` lets an allow-listed `payer` set an arbitrary, unvalidated `creator` account (`pub creator: UncheckedAccount<'info>` at [1](#0-0) ), which is stored directly into `pool_state.pool_creator` ( [2](#0-1) ) without requiring it to be a signer or verifying it corresponds to a key with a known private key.

### Finding Description
`collect_creator_fee` requires `creator` to be a `Signer` whose key matches `pool_state.pool_creator` ( [3](#0-2) ). If `pool_creator` was set (via `initialize_with_permission`) to a value that nobody can produce a valid signature for — e.g. a Program Derived Address belonging to another program, a burn-style vanity pubkey, or simply an address whose keypair the payer never generated/kept — then `collect_creator_fee` can never be called for that pool: it is structurally unreachable, exactly like the Footium `claimERC20Prize`/`claimERC20AllPrize` functions being unreachable for a club escrow that cannot itself act as `msg.sender`.

The permissionless fallback `collect_creator_fee_permissionless` looks like a mitigation because *anyone* can trigger it ( [4](#0-3) ), and it does not require `creator` to sign. But it still routes accumulated fees into an Associated Token Account whose `authority` is that same unreachable `creator` pubkey ( [5](#0-4) ). Moving funds out of `pool_state`'s vaults into this ATA does not solve the underlying problem — if `creator` cannot sign, nobody can subsequently spend from that ATA either, so the tokens are permanently frozen there, unreachable by any real owner. This mirrors the root cause identified in the Footium report: recording a beneficiary as a bare public key with no linked signing capability defeats a "claim" design intended to let the beneficiary actually retrieve funds.

Unlike `initialize` (permissionless creation) where `creator` is forced to equal the transaction `Signer` ( [6](#0-5) ), `initialize_with_permission` decouples `payer` (the signer, who must hold a `Permission` PDA) from `creator` (an arbitrary `UncheckedAccount`), with no constraint forcing `creator` to be a signer, an ATA-owning wallet, or otherwise capable of later signing.

### Impact Explanation
Once a pool is initialized this way, all future creator fees accrued from swaps (`creator_fees_token_0`/`creator_fees_token_1` in `PoolState`, see [7](#0-6) ) become permanently unclaimable by any real actor: they are either stuck (unreachable `collect_creator_fee`) or transferred into a token account whose authority can never sign a further transfer (after `collect_creator_fee_permissionless`). This is a permanent freezing of protocol-designated creator fee funds — a concrete loss for whoever was supposed to be the pool's creator/fee beneficiary.

### Likelihood Explanation
Triggering this requires `initialize_with_permission` to be called with a `creator` value that has no discoverable private key and is not itself under program control (e.g. supplying a random pubkey, or a PDA from an unrelated/nonexistent program). This account creation path is gated by the `Permission` PDA check on `payer` ( [8](#0-7) ), meaning only allow-listed payers can create such pools — this reduces likelihood versus a fully permissionless entry point, but does not require any privileged Raydium admin action; it only requires being on the "permissioned" pool-creation allow-list and choosing an arbitrary `creator` argument, which the instruction does not prevent.

### Recommendation
Require `creator` in `InitializeWithPermission` to either (a) be a `Signer`, or (b) be constrained to equal `payer`, or (c) require an explicit acknowledgment/second-signature step establishing that `creator` can control an ATA. At minimum, `collect_creator_fee_permissionless` should not be treated as a full mitigation for an unreachable `creator` since it only relocates — not resolves — the freezing problem.

### Proof of Concept
1. An allow-listed `payer` (holding a `Permission` PDA) calls `initialize_with_permission`, supplying a `creator` account that is a random `Pubkey` with no known private key (or a PDA belonging to some other/nonexistent program) — `programs/cp-swap/src/instructions/initialize_with_permission.rs` lines 26-27, 357-371.
2. `pool_state.pool_creator` is now permanently set to this unsignable key.
3. Swaps occur, accruing `creator_fees_token_0`/`creator_fees_token_1` in `PoolState`.
4. `collect_creator_fee` can never succeed because no one can produce `creator`'s signature (`collect_creator_fee.rs` lines 10-13).
5. Anyone calls `collect_creator_fee_permissionless`, which succeeds and transfers the fees into an ATA owned by the unreachable `creator` key (`collect_creator_fee_permissionless.rs` lines 61-79) — funds are now sitting in a token account that nobody can ever move again, permanently frozen.
