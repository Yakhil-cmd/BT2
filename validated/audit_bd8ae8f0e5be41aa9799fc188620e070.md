### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits by bare `sha` with no repository or stack scoping, and `WebhooksController#verify_signature` only authenticates a webhook against the GitHub organization derived from `repository.owner.login`, not the specific repository. Any repository within the same GitHub organization/App installation as a victim stack can therefore emit a genuinely GitHub-signed `status` event whose SHA collides with a commit tracked by an unrelated stack (including a production stack), flipping that commit's CI status.

### Finding Description
The broken binding: the code implicitly assumes `status.repository == commit.stack.repository`, but nothing enforces `params.dig('repository','full_name') == commit.stack.repository.full_name`.

Path: `POST /webhooks` → `WebhooksController#create` → `verify_signature` computes `github_app = Shipit.github(organization: repository_owner)` and calls `github_app.verify_webhook_signature(signature, raw_post)` [1](#0-0)  — this authenticates the payload against the **org-level** `webhook_secret` [2](#0-1) , not against the specific repository that owns the SHA. It never inspects `params.dig('repository','full_name')` for the `status` event.

Once past that gate, `StatusHandler#process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [3](#0-2)  — this is a global lookup across **all** commits/stacks in the installation, with no `repository`/`stack_id` filter. `Commit#create_status_from_github!` writes into `statuses` and recomputes `status` [4](#0-3) , and `deployable?`/`blocked?` are derived directly from that status [5](#0-4) .

Exploit flow: within a GitHub organization/App installation that hosts multiple repositories tracked by Shipit (a normal multi-repo setup, since the App is installed org-wide per `docs/setup.md`), an attacker who is an unprivileged contributor on **any one** of those repositories can trigger a genuine, GitHub-signed `status` webhook (e.g. via their own CI integration or a workflow they control on a repo they can push to) for a commit SHA that happens to also exist in a victim's production stack's commit table (e.g. a shared ancestor commit, a monorepo mirror, or two stacks tracking the same underlying repository under different names/environments). Because `verify_signature` only checks "this came from GitHub for org X" and `StatusHandler` only checks "this SHA exists somewhere," the forged/foreign `ci/test: failure` status is written onto the victim commit, and — since the affected stack is production — this flips `deployable?`/`blocked?` on that stack.

Existing guards fail because: `verify_signature` is scoped to organization, not repository [6](#0-5) ; there is no `ExplicitParameters` field or model validation tying `params.dig('repository','full_name')` to `commit.stack.repository.full_name` in `status_handler.rb`; and `Commit` has no `repository_id`/`full_name` column to filter on directly (only `stack_id`, reached via `belongs_to :stack`).

### Impact Explanation
A payload authenticated for one repository can mutate the commit/status state of a **different** stack (potentially production), satisfying the "payload for one repository mutating another's stack, commit" Critical category. This can force a production stack's commit to become `failure`/`blocked` (denial of legitimate deploy) or, in the case where the forged status is a `success` for a `ci/test` context that the victim stack requires, force it into a deployable state prematurely — either direction is a real deploy-flow integrity break. Blast radius is bounded to stacks within the same GitHub organization/App installation whose commit tables happen to contain a colliding SHA; it is not a fully unscoped cross-tenant primitive across arbitrary organizations, since the org-level webhook secret does still block completely unrelated organizations.

### Likelihood Explanation
Preconditions are narrow but realistic: (1) the org's GitHub App installation covers multiple repositories, (2) the attacker has legitimate push/CI-trigger ability on at least one of those repositories (unprivileged but "in the org's install footprint"), and (3) a SHA collision exists between the attacker-controlled repo's commit history and the victim stack's commit table — which happens naturally with forks/mirrors/shared-history repos rather than requiring a cryptographic hash collision. This is a materially narrower precondition than "any unauthenticated internet user against any stack," so likelihood is moderate rather than trivial, but it is fully repeatable once the SHA-sharing condition holds, since no per-request secret or session is needed beyond the org's own signature (which is not attacker-held but is satisfied by GitHub's genuine delivery).

### Recommendation
Scope `StatusHandler#process` (and the analogous `CheckRunHandler`, if present) to the repository that authenticated the webhook: filter `Commit.where(sha: params.sha)` further by joining `stack.repository` and comparing against `params.dig('repository', 'full_name')` (or `id`), discarding statuses whose payload repository does not match the commit's own stack repository, before calling `create_status_from_github!`.

### Proof of Concept
```ruby
test "status webhook does not mutate a commit belonging to a different repository" do
  victim_stack = shipit_stacks(:shipit)
  victim_stack.update!(environment: 'production')
  victim_commit = victim_stack.commits.last
  victim_commit.statuses.create!(state: 'success', context: 'ci/test', stack: victim_stack)

  other_repo_commit_sha = victim_commit.sha # simulate SHA collision from another repo in same org

  before = victim_commit.reload.deployable?

  # Signed for a *different* repository within the same org (repository_owner authenticated,
  # but repository.full_name does not match victim_stack.repository.full_name)
  post_status_webhook(
    sha: other_repo_commit_sha,
    state: 'failure',
    context: 'ci/test',
    repository_full_name: 'someorg/unrelated-repo'
  )

  after = victim_commit.reload.deployable?

  assert_equal before, after, "a status authenticated for a foreign repository must not change the victim stack's commit deployability"
end
```
Both sides of the equality (`before == after`) must hold; today they diverge because `StatusHandler` and `Commit.where(sha:)` never check `repository.full_name`.
