### Title
CCMenu API token authorized for one stack can read build/deploy status of any stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Api::CCMenuController` overrides the stack-scoping method inherited from `Api::BaseController`, replacing the token-scoped lookup with an unscoped one. This breaks the binding between "the stack a token authorizes" and "the stack the endpoint actually touches", allowing any valid API token with `read:stack` permission — even one created and scoped to a single stack — to read the CI/deploy status (`lastBuildStatus`, `lastBuildLabel`, `activity`, `webUrl`, lock state, etc.) of any other stack in the installation, by simply changing the `stack_id` request param.

### Finding Description
`Api::BaseController` defines the canonical, token-scoped stack resolution: [1](#0-0) 

`stacks` restricts the visible set to `current_api_client.stack_id` when the token was created scoped to a specific stack; `stack` then does `stacks.from_param!(...)`, so a scoped token can never resolve a stack outside the one it was issued for.

`Api::CCMenuController`, however, redefines `stack` to bypass this scoping entirely: [2](#0-1) 

It calls `Stack.from_param!(params[:stack_id])` directly instead of `stacks.from_param!(params[:stack_id])`, and separately overrides `authenticate_api_client` to also accept the token via a `params[:token]` query string. Permission enforcement is still delegated to `require_permission :read, :stack`, which only calls `ApiClient#check_permissions!`: [3](#0-2) 

This method checks only whether `"read:stack"` is present in the token's `permissions` array — it never checks `current_api_client.stack_id` against the requested stack. The stack-scoping is entirely delegated to (and expected to be enforced by) the `stack`/`stacks` helper in `BaseController`, which `CCMenuController` does not use.

The equality that should hold is:
`token.stack_id (if present) == requested stack_id` for every stack-scoped read, enforced via `BaseController#stacks`.
`CCMenuController#stack` breaks this by resolving `params[:stack_id]` against the global `Stack` scope instead of the token-restricted `stacks` scope.

### Impact Explanation
This is an unauthenticated-for-that-resource read of stack state: a legitimately-issued, stack-scoped API token (e.g. the one automatically created by `CCMenuUrlController` for CCTray/CI-status-widget integrations, see `app/controllers/shipit/ccmenu_url_controller.rb` lines 15-18, which is created with only `permissions: %w[read:stack]` and handed out per stack) can be replayed against `/api/<other-stack>/cctray.xml` to disclose that other stack's deploy/build status, lock state, and last build metadata, even though the token was never authorized for that stack. This matches the "unauthenticated read of stack state ... deploy output" High-impact category, since it discloses cross-stack deployment state to a party who only holds credentials for a single, unrelated stack.

### Likelihood Explanation
Likelihood is high for any deployment that uses the CCMenu/CCTray integration feature (`CCMenuUrlController`), since those tokens are handed out to users/widgets per stack and are expected by design to be stack-scoped. Any holder of such a token — which is treated as low-sensitivity, widely distributed (embedded in CI status widget URLs) — can trivially enumerate other stacks by changing the `stack_id` path/query parameter, no additional privilege needed.

### Recommendation
Change `Api::CCMenuController#stack` to use the token-scoped resolution consistent with the rest of the API:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
i.e., remove the override entirely so it inherits `Api::BaseController#stack`, ensuring `current_api_client.stack_id` scoping is honored.

### Proof of Concept
1. An operator uses the CCMenu integration for `stack A`; `CCMenuUrlController#client` creates (or reuses) an `ApiClient` with `permissions: %w[read:stack]` and no `stack_id` restriction by default unless explicitly scoped — but for a token that *is* scoped to `stack A` (e.g., created via the API with `stack_id` set to A's id, as supported by `ApiClient belongs_to :stack, optional: true`), the following holds:
   - Calling `GET /api/A/cctray.xml?token=<A's token>` succeeds (expected).
   - Calling `GET /api/B/cctray.xml?token=<A's token>` (where token is scoped only to stack A) also succeeds and returns stack B's build/deploy status, because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` unscoped, ignoring `current_api_client.stack_id`.
2. Confirmed by contrasting with `Api::BaseController#stack`/`#stacks` (lines 74-80), which is the only place `current_api_client.stack_id` scoping is applied, and which `CCMenuController` explicitly bypasses at lines 29-31.
