### Title
Webhook signature verification is keyed off an unverified `repository.owner.login`/`organization.login` field, decoupled from the `repository.full_name` field actually used to select which Stack/Commit is mutated - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and thus which `webhook_secret`) to validate a webhook payload against using `repository_owner`, a value read directly out of the *unauthenticated* JSON body (`params.dig('repository', 'owner', 'login')` or the `organization.login` fallback). [1](#0-0) [2](#0-1) 

Every event handler, however, resolves the record(s) to write to using a *different, independently-attacker-controlled* field of the same body: `repository.full_name`, via `Shipit::Webhooks::Handlers::Handler#repository_name`. [3](#0-2) 

Nothing cross-validates that `repository.full_name` actually belongs to the organization named in `repository.owner.login`/`organization.login`. This is exactly the report's bug class: a field that is used to authenticate/authorize a request (here: which org's secret backs the signature) is different from the field that is actually acted upon (here: which repository/stack gets written).

### Finding Description
`Shipit.github(organization: repository_owner)` picks a per-organization `GitHubApp` config, and `verify_webhook_signature` HMACs `request.raw_post` against that organization's `webhook_secret`: [4](#0-3) 

Critically, `webhook_secret` is explicitly documented as *optional* per GitHub App/organization: [5](#0-4) 

and the engine ships with multi-organization configuration examples where a `webhook_secret` may legitimately be left unset (`nil`) for one org while set for another: [6](#0-5) 

When `webhook_secret` is blank, `verify_webhook_signature` unconditionally returns `true` - i.e., signature verification is a no-op for that organization: [7](#0-6) 

Because `repository_owner` (used only to pick which secret bypass/validate against) and `repository.full_name` (used to resolve the actual `Repository`/`Stack` to mutate) are two unrelated, attacker-supplied JSON fields in the same POST body, an unprivileged attacker who knows (or can guess) the name of *any* organization configured in `Shipit.github` without a `webhook_secret` can:
1. Set `repository.owner.login` (or `organization.login`) to that unsecured org, so `verify_signature` trivially passes.
2. Set `repository.full_name` (and any other event-specific fields) to point at a completely different, victim organization/repository/commit that Shipit actually tracks.

Every handler trusts `repository.full_name` at face value to resolve `Stack`s: [8](#0-7) 

and `StatusHandler` writes a `Status` onto *any* `Commit` matching an attacker-chosen `sha`, with attacker-chosen `state`/`context`, regardless of which repository it belongs to: [9](#0-8) 

`MembershipHandler` similarly trusts `organization.login`, `team.id` (GitHub team ID) and `member.login` wholesale to add arbitrary GitHub logins to a `Team`: [10](#0-9) [11](#0-10) 

If that team's primary-key id is one of the ids returned by `Shipit.github_teams`, this directly grants the attacker's GitHub identity `User#authorized?` privileges inside Shipit without ever touching GitHub's real membership API: [12](#0-11) [13](#0-12) 

### Impact Explanation
This breaks the deployment-trust binding: "the organization whose secret authenticated the request" ≠ "the repository/commit/team that the request's handler actually writes to". Concretely:
- **Forged CI statuses on arbitrary commits** via `StatusHandler`, which can satisfy `ci.require`/blocking-status checks and enable continuous deployment or merge-queue validation on commits the attacker does not control → unauthorized deploy/merge (Critical).
- **Forced sync/push events** via `PushHandler` for any tracked stack whose owning org has no `webhook_secret` configured, letting the attacker drive `sync_github` with an arbitrary `expected_head_sha`.
- **Escalation into `Shipit.github_teams` authorization** via `MembershipHandler`, letting an attacker's own GitHub login be enrolled as a member of an authorization-gating `Team` (High, matches the explicitly listed impact "escalation into `Shipit.github_teams` authorization").

None of this requires a Shipit session, an `ApiClient` token, TLS interception, or any privileged account - only knowledge that some organization in Shipit's multi-org GitHub config has no `webhook_secret` (an explicitly documented, supported configuration), plus the target repository's `full_name`/commit sha/team id.

### Likelihood Explanation
Likelihood is conditioned on at least one configured GitHub organization lacking a `webhook_secret` - a state the project's own docs and shipped example config present as normal/optional, not a misconfiguration outside the documented deployment model. Given that condition, the exploit requires no secrets: only a crafted, unsigned-effectively JSON POST to `/webhooks` with mismatched `repository.owner.login` vs `repository.full_name`/`team.id`/`member.login` fields.

### Recommendation
- Verify the webhook signature using the secret associated with the actual repository/entity being mutated, not a value read from the same unauthenticated payload used only to pick that secret.
- Do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is blank; either require a secret for every configured organization or explicitly reject/flag unsigned deliveries instead of treating them as verified.
- In each handler, assert that `repository.owner.login`/`organization.login` (the field driving secret selection) matches the organization portion of `repository.full_name` (and, for membership events, `organization.login`) before performing any writes.

### Proof of Concept
1. Configure Shipit (per documented multi-org setup) with two orgs: `orgA` (no `webhook_secret`) and `orgB` (tracked victim repos/teams, `webhook_secret` set).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "orgB/victim-repo"
  },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>"
}
```
`verify_signature` resolves `Shipit.github(organization: "orgA")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of signature header/content.
3. `PushHandler` then resolves stacks via `repository.full_name` = `"orgB/victim-repo"`, driving a sync on the victim stack.
4. Repeat with `X-Github-Event: status` and a `sha` belonging to a commit in `orgB`'s stack, or `X-Github-Event: membership` with a known `team.id` from `Shipit.github_teams`, to forge CI status / gain team membership respectively.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
