### Title
Divide-before-multiply precision loss in `min-ustx-for-sats-amount` understates the required STX collateral for a sBTC bond - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
`min-ustx-for-sats-amount` in `pox-5.clar` computes the minimum amount of uSTX that must be locked for a given sBTC bond, based on a "sats-amount", "stx-value-ratio" and "min-ustx-ratio" (a basis-points minimum collateralization ratio). The function performs an intermediate division before the final multiplication, which is exactly the bug class described in the external report: dividing before multiplying causes truncation/precision loss that produces a result lower than the mathematically correct one.

### Finding Description
The function is defined as: [1](#0-0) 

```clarity
(define-read-only (min-ustx-for-sats-amount
        (sats-amount uint)
        (stx-value-ratio uint)
        (min-ustx-ratio uint)
    )
    (/ (* (/ (* stx-value-ratio sats-amount) u100) min-ustx-ratio) u10000)
)
```

The correct order of operations to avoid precision loss would multiply all three quantities together first and only then divide by the combined denominator (`u100 * u10000 = u1000000`):
`(/ (* stx-value-ratio sats-amount min-ustx-ratio) u1000000)`

Instead, the contract first computes `(/ (* stx-value-ratio sats-amount) u100)` — an intermediate division that truncates any remainder — and only afterward multiplies by `min-ustx-ratio` and divides by `u10000`. Because Clarity integer division floors, the intermediate `(/ ... u100)` step discards up to 99/100 of a unit of precision *before* it gets scaled by `min-ustx-ratio`, so the final result is systematically lower than (or, in the worst case, up to ~1% lower than) the value produced by multiplying first. This is the identical bug pattern to the `FiveFiftyRule::_updateEntityAllowance` report: `(DENOM / X) * amount` instead of `(DENOM * amount) / X`.

The function's docstring states it computes "the minimum amount of STX needed to hit `min-ustx-ratio`" relative to a given `sats-amount` — i.e., it is a collateralization-floor check. The naming of related test artifacts (`RegisterForBondErrInsufficientStx.ts`) indicates this calculation gates whether a staker's committed STX is sufficient to back a protocol bond denominated in sBTC/sats.

### Impact Explanation
If `min-ustx-for-sats-amount` is used as the floor that a staker's locked STX must meet or exceed when registering for (or maintaining) a protocol bond, the truncation causes the computed minimum to be lower than the true minimum ratio the protocol intends to enforce. A staker can register a bond backed by more `sats-amount` (sBTC exposure) than their locked STX collateral actually justifies under the intended `min-ustx-ratio`. This breaks the equality between locked STX and the sBTC/sats commitment the bond is supposed to be collateralizing — i.e., it lets a bond be committed with insufficient locked STX relative to its sats exposure, which is a form of "signing weight or reward slots exceeding locked value" (an under-collateralized stacking commitment being accepted as valid).

### Likelihood Explanation
This triggers on the normal, unprivileged bond-registration code path anytime `min-ustx-for-sats-amount` is invoked to validate a staker's STX amount against a sats commitment — no special privileges are required, only submitting a bond registration with an amount just below the mathematically correct floor but above the (incorrectly) truncated floor computed by the contract.

### Recommendation
Reorder the arithmetic to multiply all terms before dividing, matching the combined denominator:
```clarity
(/ (* stx-value-ratio sats-amount min-ustx-ratio) u1000000)
```
This avoids the intermediate truncation and matches the recommended fix pattern from the external report (multiply fully before dividing).

### Proof of Concept
Given `stx-value-ratio = 1`, `sats-amount = 199`, `min-ustx-ratio = 10000` (i.e. 100% in basis points):
- Correct calculation: `(1 * 199 * 10000) / 1000000 = 1990000/1000000 = 1` (floor).
- Contract's calculation: `(/ (* 1 199) u100) = (/ 199 u100) = 1`; then `(/ (* 1 10000) u10000) = 1`. In this specific example the results coincide, but for values such as `stx-value-ratio = 1`, `sats-amount = 150`, `min-ustx-ratio = 6600`:
  - Correct: `(1*150*6600)/1000000 = 990000/1000000 = 0` (floor) — actually both floor to 0 here too.
  
  A clearer discrepancy: `stx-value-ratio = 3`, `sats-amount = 33`, `min-ustx-ratio = 10000`:
  - Correct: `(3*33*10000)/1000000 = 990000/1000000 = 0`.
  - Contract: `(/ (* 3 33) u100) = (/ 99 u100) = 0`; `(/ (* 0 10000) u10000) = 0`. Same again for tiny numbers since correct answer also floors to 0, but for larger `sats-amount` where the intermediate division discards a fractional unit that would have mattered after the final multiply (e.g., `stx-value-ratio=1, sats-amount=199, min-ustx-ratio=15000`):
  - Correct: `(1*199*15000)/1000000 = 2985000/1000000 = 2`.
  - Contract: `(/ (* 1 199) u100) = 1` (truncated from 1.99); `(* 1 15000)=15000`; `(/ 15000 u10000) = 1`.
  - Result: contract returns `1` uSTX minimum instead of the correct `2` uSTX minimum — a 50% understatement of the required collateral for this input, letting a staker register a bond with less STX locked than the protocol's stated minimum ratio requires. [2](#0-1)
