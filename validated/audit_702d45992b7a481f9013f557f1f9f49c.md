### Title
Webhook signature verification binds only the claimed organization, not the repository/commit actually acted upon - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and therefore which `webhook_secret`) is used to validate an inbound webhook based on an attacker-controlled field inside the unauthenticated JSON body (`repository.owner.login` / `organization.login`), while the handlers that actually mutate state key off different, independently-controlled fields of the same body (`repository.full_name`, or in the `StatusHandler` case, only `sha` with **no repository check at all**). When an organization is configured without a `webhook_secret` (an explicitly documented, supported configuration), `GitHubApp#verify_webhook_signature` accepts the request unconditionally, so the "verified organization" side of the equality is empty while the "repository/commit acted on" side is fully attacker-chosen.

### Finding Description
`repository_owner` is read straight out of the untrusted payload before any cryptographic check occurs: [1](#0-0) [2](#0-1) 

That value is used only to pick which `GitHubApp`/secret to validate against: [3](#0-2) 

Note the `return true unless webhook_secret` short-circuit — an org configured without a secret (documented as a valid, default configuration, e.g. `config/secrets.development.example.yml` and `template.rb` both ship `webhook_secret:` with no value) makes verification a no-op for any payload claiming that org.

Once "verified," the actual side effects are driven by unrelated fields of the same attacker-controlled JSON body:
- `Handler#repository_name` (base class used by push/pull_request handlers) reads `payload.dig('repository', 'full_name')`, decoupled from the `repository.owner.login` used for signature-app selection: [4](#0-3) 
- `StatusHandler#process` does not check the repository at all — it matches purely on `sha` across the entire instance: [5](#0-4) 
- `PushHandler#process` triggers a GitHub sync for any stack under the `full_name`-resolved repository: [6](#0-5) 

The binding that should hold is: `organization authenticated by verify_signature == organization owning the repository/commit that handlers act on`. Because `verify_signature` only authenticates the `repository_owner`/`organization.login` string (and can be trivially satisfied when that org has no secret), while `StatusHandler`/`PushHandler`/PR handlers act on independently-supplied `sha`/`full_name` fields, this equality is not enforced anywhere in the request path.

### Impact Explanation
An unauthenticated, unprivileged internet requester who knows (a) the name of any Shipit-configured GitHub organization that has no `webhook_secret` set, and (b) the `sha` of a commit or `full_name` of a repository belonging to a *different*, sensitive stack, can:
- Inject a forged `status` event via `StatusHandler`, calling `commit.create_status_from_github!` on an arbitrary commit in any stack, since `StatusHandler` never checks which repository the commit belongs to. This can be used to fabricate CI/deploy-gating statuses.
- Trigger `stack.sync_github` (`PushHandler`) or PR/label state transitions (`archive!`/`unarchive!`) against stacks in an unrelated, "protected" organization by setting `repository.full_name` to that org's repo while satisfying signature verification under the no-secret org's identity.

This can escalate to influencing which commits appear "deployable"/pass status gates, contributing to an unauthorized deploy path, which matches the in-scope Critical/High impact category ("unauthorized deploy" / escalation via forged status).

### Likelihood Explanation
Requires only: (1) a Shipit instance with at least one GitHub organization configured without a `webhook_secret` (a documented, valid setup shown in the shipped example secrets files), and (2) knowledge of a target commit `sha` or repository `full_name`, both of which are often publicly discoverable (public repos, PR pages, commit hashes). No token, session, or GitHub credential of any kind is required — the webhook endpoint is unauthenticated by design and only gated by the (bypassable) HMAC check.

### Recommendation
- Require `verify_signature` to also assert that the organization used for signature selection matches the actual `repository.full_name`'s owner (or `organization.login`) present in every handler's scope, i.e., re-derive and compare both fields before dispatching to handlers.
- Do not treat a missing `webhook_secret` as an automatic pass; if any organization in a multi-org Shipit install is configured without a secret, either require a secret universally when multiple orgs are configured, or scope acceptance strictly to that org's own repositories.
- Fix `StatusHandler` to scope commits by repository (`stacks`/`repository_name`) rather than matching bare `sha` across the whole instance.

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.yml`: `orgA` (no `webhook_secret`) and `orgB` (has `webhook_secret`, owns a sensitive stack).
2. POST to the webhook endpoint with header `X-Github-Event: status`, no valid `X-Hub-Signature` (or any junk value), and body:
```json
{
  "sha": "<sha of a commit belonging to orgB's stack>",
  "state": "success",
  "repository": { "owner": { "login": "orgA" } }
}
```
3. `verify_signature` calls `Shipit.github(organization: "orgA")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the (invalid) signature header: [7](#0-6) 
4. `StatusHandler#process` runs unconditionally against `Commit.where(sha: params.sha)`, creating a forged "success" status on orgB's commit with zero relation checked to `orgA`: [5](#0-4)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
