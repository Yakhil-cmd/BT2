## Title
Liquidator-supplied price feeds populate a global oracle cache that unfavorably prices an unrelated borrower's collateral within the same block - (File: mainnet/contracts/market/v0-4-market.clar)

### Summary
`liquidate()` accepts an optional `price-feeds` parameter and calls `write-feeds`/`price-resolve` *before* any authorization or position-specific check. `price-resolve` writes the resolved price's timestamp into the **global** `last-update` map keyed only by `{type, ident}` (i.e., per price feed, not per borrower or per caller), and `accrue-and-cache` writes into the **global** `index-cache` map keyed by `{timestamp, aid}`. Both are consumed by every other position evaluation (borrow, withdraw, other liquidations) that resolves the same asset in the same block. Any unprivileged liquidator can therefore "prime" these shared caches with a self-selected, still-technically-fresh Pyth update (any publish time inside the staleness window and monotonically ≥ the previously recorded timestamp) before their own liquidation call, and that same cached price/index is then reused — without re-validation — against a completely different borrower's position later in the same block.

### Finding Description
`price-resolve` in `mainnet/contracts/market/v0-4-market.clar` validates freshness only via: [1](#0-0) 

```
(oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (<= delta max-staleness) (>= ts prev)
...
(if (> timestamp last-update-time) (map-set last-update key timestamp) false)
```

`last-update` is a single global map keyed by `{type, ident}` — not scoped to a caller or to a specific borrower's position: [2](#0-1) 

`liquidate()` invokes `write-feeds price-feeds` unconditionally at the very start of the function, before the borrower is even resolved: [3](#0-2) 

Any account (an unprivileged liquidator) can therefore push a Pyth update whose `publish-time` sits anywhere in the allowed staleness window (bounded independently by `pyth-storage-v4`'s own `stale-price-threshold` and this contract's per-asset `max-staleness`), as long as it is ≥ the last recorded timestamp for that feed. Because the underlying Pyth price history contains many valid signed prices across that window, the caller can choose the value in that window that is least favorable to a target borrower (e.g., the lowest historical BTC price within the freshness window) and submit it as their own `price-feeds` argument while liquidating an *unrelated* victim's position. `resolve-ztoken`/`get-cached-indexes` for zTokens similarly read from the block-shared `index-cache`, which whichever caller "primes" first in the block supplies to everyone else: [4](#0-3) [5](#0-4) 

The victim borrower has no ability to prevent or override this: their own `liquidate`/health-check call in the same block that doesn't supply fresher `price-feeds` will simply hit the cache the attacker already primed, since `price-resolve` treats any cached/oracle-stored value satisfying the monotonic+staleness bound as valid regardless of who submitted it.

### Impact Explanation
This lets an attacker manufacture a temporarily depressed (or inflated, for debt-asset) valid price and apply it to a borrower whose position is healthy at the true current price, pushing `current-ltv` above `ltv-liq-partial`/`ltv-liq-full` and triggering an unwarranted liquidation — direct theft of the victim's collateral via the liquidation penalty (`liq-penalty`), which is "theft of user funds at rest... other than unclaimed yield" (Critical) since the collateral seized never should have been eligible for seizure at the honest current price.

### Likelihood Explanation
Requires only a public, unprivileged `liquidate` call with attacker-chosen `price-feeds`; no special permission, DAO action, or flashloan is needed (a flashloan could be used purely as capital, which the rules permit). It depends on the staleness/monotonicity window being wide enough to contain an unfavorable historical price and the victim's position sitting close enough to the liquidation threshold that the price differential within that window is sufficient to cross it — a realistic condition given `max-staleness` values described as up to 300 seconds for stable assets and 60+ seconds even for volatile ones.

### Recommendation
Scope oracle price/timestamp caches and index caches by transaction/caller instead of relying solely on a block-global map, or require that `liquidate()` use only the single most recent price already recorded (reject any submitted feed whose timestamp is not strictly the newest available at call time). Additionally, tie liquidation eligibility to a price that cannot be chosen by the liquidator for a borrower who did not submit that price themselves (e.g., require the borrower's own last update or use only prices already resolved earlier in the block, not liquidator-supplied ones).

### Proof of Concept
1. Borrower B holds a position with `current-ltv` slightly below `ltv-liq-partial`, healthy at true current BTC price $P_now$.
2. Within the staleness window (`max-staleness` seconds) there exists a valid, still-fresh, monotonically-acceptable Pyth-signed BTC price $P_low < P_now$ (e.g., published 50 seconds ago in a volatile market).
3. Attacker (any unprivileged account) calls `market.liquidate(borrower=B, ..., price-feeds=(some [P_low VAA]))`.
4. `write-feeds` verifies and stores $P_low$ in `pyth-storage-v4`; `price-resolve` accepts it (`oracle-timestamp-fresh` passes) and records it in the global `last-update` map for that feed.
5. `get-notional-evaluation` for B's collateral now uses $P_low$, pushing `current-ltv` above `ltv-liq-partial`, and the liquidation executes against B despite B's position being healthy at $P_now$.

**Note:** I was unable to fully verify the exact bounds of `stale-price-threshold` in `pyth-storage-v4` and each asset's configured `max-staleness` value from the indexed context, which determine how wide the exploitable price-selection window actually is in practice; a full session with file access would be needed to confirm concrete numeric feasibility for this attack.

(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
