### Title
Unliquidatable accounts permanently keep a stale liquidation threshold when governance tightens market risk params - (File: contracts/controller/src/risk/params.rs)

### Summary
The Kirby advisory's bug class is an "is this local?" trust decision that silently uses stale environment assumptions (.dev TLD, proxy-hidden origin). The analog here is the controller's treatment of each supply position's *cached* liquidation tuple as authoritative: once a position's snapshot favors the borrower, the `update_account_threshold` gate structurally refuses to restamp it, so the stale snapshot keeps deciding liquidation and solvency forever, even though the market's listed parameters have moved on.

### Finding Description
Each `AccountPosition` stores a snapshot of `liquidation_threshold`, `liquidation_bonus`, and `liquidation_fees` taken when the position was opened. The only permissionless way to refresh it is `update_account_threshold(caller, has_risks=true, account_ids)`, which reaches `sync_account_thresholds` → `apply_gated_liquidation_params` (contracts/controller/src/risk/params.rs:68-93).

That function first asks whether the new listed config "favors the liquidator" — a lower `liquidation_threshold`, a higher `liquidation_bonus`, or lower `liquidation_fees` (`favors_liquidator`, lines 96-100). If it does, the change is only applied when the position still clears `HF >= 1.05` under the *new* threshold (`clears_min_hf`, lines 102-119); otherwise the position is silently skipped (`return` at line 87), keeping the old, more favorable snapshot.

Concretely, when governance lowers a market's `liquidation_threshold`:

- Any account whose health factor under the *new* threshold falls below 1.05 (including below 1.0) can never have that position restamped. `clears_min_hf` fails, the snapshot is skipped, and — if the position is unhealthy enough — the final `hf >= 1.05` assertion at lines 221-234 reverts the whole call anyway.
- `liquidate`, `borrow`, and every solvency check read the *stored* per-position `liquidation_threshold` via `calculate_account_risk_totals` — not the listed market config. So an account that is insolvent under current listed parameters still reports `HF >= 1` to `liquidate`, which rejects the liquidation, and the keeper path that could fix the snapshot is the exact path the gate blocks.

There is no fallback: `update_account_threshold` is the only mutator that restamps the tuple on an existing position, and the gate has no bypass for accounts that are already unhealthy. The check designed to protect borrowers from being pushed into liquidation doubles as a permanent shield for accounts that governance has already decided are too risky.

### Impact Explanation
Permanent freezing of liquidation and continued borrowing on effectively insolvent accounts → protocol insolvency / theft of pool funds. An attacker holding a leveraged position in a market whose `liquidation_threshold` is lowered can keep the stale higher threshold indefinitely, remain unliquidatable under the cached HF, and continue borrowing (post-borrow solvency is also measured with the stale snapshot) until real backing is exhausted. Bad debt accrues to suppliers; `clean_bad_debt`/`seize_positions` can only socialize the loss afterward.

### Likelihood Explanation
Requires a governance operation that lowers `liquidation_threshold` (or otherwise favors liquidators) while some account sits in the HF band that is healthy under the old tuple but below 1.05 under the new one — a routine risk-tightening scenario. No privileged access or leaked keys needed: the attacker only needs an existing open position, and all paths (`liquidate`, `update_account_threshold`, `borrow`) are permissionless or owner-gated for the attacker's own account. Severity: Medium.

### Recommendation
Decouple the borrower-protection gate from threshold *updates* that reduce risk terms: when `favors_liquidator` is true and `clears_min_hf` fails, either (a) clamp the stored threshold to the lower of old/new rather than skipping, or (b) compute liquidation HF against `min(stored_threshold, listed_threshold)` at read time so a stale snapshot can never make an undercollateralized account appear healthy. At minimum, allow `FullTuple` restamping of unhealthy accounts when the update strictly tightens terms, since keeping the stale value is strictly worse for the protocol.

### Proof of Concept
1. Governance lists asset X with `liquidation_threshold = 0.80`; attacker supplies X and borrows so that HF ≈ 1.02 under 0.80.
2. Governance executes a ready operation lowering X's `liquidation_threshold` to 0.60. Attacker's true HF under listed params is now < 1.
3. Any liquidator calls `liquidate`: `calculate_account_risk_totals` uses the stored 0.80 → HF 1.02 → reverts.
4. Any keeper calls `update_account_threshold(caller, true, [account_id])`: `favors_liquidator` is true and `clears_min_hf(.., 0.60)` fails → position skipped (or whole call reverts on the final HF assert). Stale 0.80 persists.
5. Attacker calls `borrow` again; solvency is evaluated with stored 0.80 → succeeds → drains additional pool liquidity while remaining unliquidatable.
