### Title
Authorization scope bypass in CCMenu endpoint lets a stack-restricted API token read any stack's build/deploy state - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the base controller's stack lookup to resolve the target stack directly from the URL parameter instead of going through the stack-scoping collection used everywhere else in the API. This breaks the binding "the stack a token authorises == the stack the request touches," letting an `ApiClient` token that is restricted to one stack read CI/deploy status for any other stack.

### Finding Description
`ApiClient` supports an optional `stack_id` scope (`belongs_to :stack, optional: true`) [1](#0-0) . The base API controller enforces this scope for every resource lookup: it restricts the visible `Stack` collection to `current_api_client.stack_id` when set, and all per-stack controllers resolve the target stack through this scoped collection: [2](#0-1) 

Every other stack-scoped API controller (e.g. `TasksController#task`/`#trigger`, which calls `stack.tasks...`) relies on this scoped `stack` helper [3](#0-2) .

`CCMenuController`, however, redefines `stack` to bypass this scoping and fetch the stack straight from the raw `Stack` model using only the URL parameter: [4](#0-3) 

`require_permission :read, :stack` only checks that the token carries the `read:stack` permission string; it never checks that the requested stack matches `current_api_client.stack_id` [5](#0-4) . The fixture-backed test suite confirms stack-scoped tokens are a supported, real access-control mechanism ("an api client scoped to a stack will only see that one stack") [6](#0-5) , and `CCMenuController` additionally accepts the token via a plain query-string parameter [7](#0-6) , which is exactly how CCMenu URLs are distributed by `CCMenuUrlController#fetch` [8](#0-7) .

This is structurally the same class of bug as the AAVE report: an authorization/consistency check is anchored to one entity (the permission label, checked against the client) while the operation is actually performed against a different, attacker-supplied entity (an arbitrary `stack_id`) that was never re-validated against the token's declared scope — analogous to approving an allowance on the Lending Pool Core while operations act on the Lending Pool.

### Impact Explanation
Any holder of a legitimately-issued, stack-scoped API token (with only `read:stack` permission, intended to be confined to one stack) can enumerate `stack_id` values and read `lastBuildStatus`, `lastBuildLabel`, `activity`, and `webUrl` for stacks they are not authorized to access. This is an unauthorized read of stack/deploy state across authorization boundaries — matching the "High: escalation into `Shipit.github_teams` authorization... unauthenticated read of stack state, task streams or deploy output" impact class.

### Likelihood Explanation
Exploitation requires only a valid, already-issued `ApiClient` token scoped to a single stack (a normal, documented deployment configuration, e.g. distributed via `CCMenuUrlController`) and knowledge or guessing of another stack's numeric/slug identifier — no elevated privileges, no signature forgery, and no additional credentials are needed. This is directly reachable through the public CCMenu XML endpoint.

### Recommendation
Make `CCMenuController#stack` resolve through the same scoped collection as the rest of the API (`stacks.from_param!(params[:stack_id])` from `BaseController`) instead of `Stack.from_param!(params[:stack_id])`, so the `current_api_client.stack_id` restriction is enforced consistently for the CCMenu endpoint as it is everywhere else.

### Proof of Concept
1. Obtain (or have a CI system generate) an `ApiClient` token scoped to `stack_id = A` with permission `read:stack` (as fetched via `CCMenuUrlController#fetch` for stack A) [9](#0-8) .
2. Send `GET /api/stacks/<stack_B_id>/ccmenu.xml?token=<tokenScopedToA>` where stack B is a different, unauthorized stack.
3. Because `CCMenuController#stack` ignores `current_api_client.stack_id` and looks up `params[:stack_id]` directly [10](#0-9) , and `require_permission :read, :stack` only checks the permission label, not stack ownership [5](#0-4) , the request returns HTTP 200 with stack B's CI/deploy status, despite the token being scoped only to stack A.
