### Title
Unvalidated swap-route venues can steal unrelated caller tokens through the caller’s authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
Medium-severity authorization-boundary vulnerability. Controller strategies accept caller-supplied opaque route bytes and execute them through the configured aggregator without restricting the route’s venue/pool addresses; the aggregator then invokes whichever pool address the payload names. [1](#0-0) [2](#0-1) 

Because the strategy requires the account owner’s authorization, a malicious pool can insert an unrelated `token.transfer(victim, attacker, amount)` beneath the signed invocation tree. [3](#0-2) [4](#0-3) 

### Finding Description
`swap_collateral` accepts caller-controlled `swap` bytes, authenticates the account owner or delegate, withdraws the selected collateral, and forwards the route to `swap_tokens`. [5](#0-4) [6](#0-5) 

`swap_tokens` authorizes only the controller’s exact input transfer to the configured router, but it does not decode the route or constrain which contracts the route invokes. [1](#0-0) [7](#0-6) 

The router resolves a hop’s `pool`, `token_in`, and `token_out` directly from the payload’s attacker-controlled address registry and dispatches to a venue adapter. [2](#0-1) [8](#0-7) 

There is no venue/pool allowlist in this path: the dispatcher chooses only the adapter type and calls the supplied pool address. [9](#0-8) 

A malicious contract can implement the expected venue ABI, fund itself with the output token so the router’s measured-output checks pass, and additionally call `transfer` from the strategy caller to the attacker. [10](#0-9) [11](#0-10) 

Soroban simulation records that malicious token transfer as a child of the caller’s `swap_collateral` authorization; if the caller signs the returned tree, the unrelated transfer executes even though the user intended to authorize only a collateral swap. [12](#0-11) [13](#0-12) 

### Impact Explanation
An attacker can steal tokens held directly by the victim that are unrelated to the routed input, borrowed asset, collateral, or account position. [13](#0-12) 

The theft is not bounded by `amount`, the route’s minimum output, or the final account health check because the malicious venue transfers a separate victim-held token under the victim’s signed authorization tree. [14](#0-13) [15](#0-14) 

### Likelihood Explanation
The attacker must cause the victim to use a malicious route and sign the simulated authorization containing the extra transfer, so this is not a fully signature-free theft. [16](#0-15) 

The attack is nevertheless practical because route bytes are opaque protocol input supplied with `swap_collateral`, and the malicious venue can return a valid output while hiding the additional wallet transfer deep in the invocation tree. [5](#0-4) [17](#0-16) 

### Recommendation
Do not allow route payloads to name arbitrary executable pool addresses. Replace raw addresses with governance-registered venue/pool identifiers, or verify every executable address against a governance-managed allowlist before dispatch. [2](#0-1) 

Additionally, controller-facing clients should enforce that strategies such as `swap_collateral`, which do not pull caller tokens, produce no caller-side authorization children; this should remain a defense-in-depth check rather than the primary contract fix. [15](#0-14) 

### Proof of Concept
1. The victim owns a normal lending account with USDC collateral and also holds an unrelated wallet token that is not part of the lending strategy. [18](#0-17) 
2. The attacker deploys a venue-compatible contract whose swap method calls `wallet_token.transfer(victim, attacker, victim_balance)` and then returns enough destination token for the router’s measured-output checks. [11](#0-10) 
3. The attacker supplies a `swap` payload for `Controller::swap_collateral(caller=victim, account_id, current=USDC key, amount=small_amount, new=ETH key, swap=payload)` whose hop `pool` index resolves to that malicious contract. [5](#0-4) [2](#0-1) 
4. Simulation records the unrelated wallet-token transfer as a child of the victim’s `swap_collateral` authorization. [12](#0-11) 
5. When the victim signs that authorization tree, the swap still completes and deposits the measured ETH output, while the victim’s entire unrelated wallet-token balance is moved to the attacker. [13](#0-12)

/// Authorizes, on behalf of the current contract, one `transfer(from, to, amount)`
/// call on `token_addr` made deeper in the next contract call (for example by
/// the pool). The entry allows no further sub-invocations.
pub fn authorize_transfer_as_current(
    env: &Env,
    token_addr: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
) {
    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);
}

pub(crate) fn dispatch_hop(
    env: &Env,
    router: &Address,
    hop: &SwapHop,
    amount_in: i128,
    tokens_cache: &mut Map<Address, Vec<Address>>,

    let ctx = HopContext::new(env, router, hop, amount_in);

        SwapVenue::Aquarius => aquarius::swap(&ctx, tokens_cache),
        SwapVenue::Phoenix => phoenix::swap(&ctx),
        SwapVenue::Sushi => sushi::swap(&ctx),
        SwapVenue::CometDex => comet::swap(&ctx),
    };

**File:** docs/explanation/threat-model.md (L154-165)
```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
user.
```
