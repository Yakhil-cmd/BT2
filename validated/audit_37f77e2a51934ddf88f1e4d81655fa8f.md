### Title
Skill preview writes unsanitized remote file bytes directly to the external pager - (File: pkg/cmd/skills/preview/preview.go)

### Summary
`renderAllFiles` and `renderInteractive` in `pkg/cmd/skills/preview/preview.go` fetch arbitrary skill-repository files via `discovery.FetchBlob` and write their raw contents straight to `opts.IO.Out` while a pager (`less`, or whatever `PAGER`/`GH_PAGER` resolves to) is active, with no escape-sequence stripping performed anywhere in the codebase. Because the pager is a separate program that interprets terminal control sequences independently of gh, an attacker who publishes a skill can embed escape sequences that are inert to gh's own writer but active once handed to the pager.

### Finding Description
In `previewRun`, `renderAllFiles`, and `renderInteractive` ( [1](#0-0) , [2](#0-1) ), skill file bytes obtained from `discovery.FetchBlob` (an attacker-controlled skill archive/repo entry) are passed through `fmt.Fprint(out, sanitized)` / `fmt.Fprint(opts.IO.Out, content)`. Despite the local variable name `sanitized`, no sanitization function is ever applied to it — a repo-wide search found no `SanitizeText`, `StripANSI`, or equivalent escape-stripping utility anywhere in this codebase. Non-markdown extra files (scripts, text files, etc.) are written completely raw; markdown files go through `renderMarkdownPreview` → `markdown.Render` → `glamour`'s renderer, which is designed to render markdown to ANSI for display but is not a security sanitizer against arbitrary embedded raw escape/OSC bytes in the source text.

All of this output happens while `opts.IO.StartPager()` is active ( [3](#0-2) , [4](#0-3) ), meaning the bytes are piped to an external program (the user's configured pager) rather than interpreted by gh's own terminal-writer/theme-aware renderer. External pagers implement their own (sometimes different or more permissive) escape-sequence handling, so content that gh's own code paths might treat safely can still reach the pager unmodified and be interpreted there — e.g., cursor repositioning, screen clearing, OSC 8 hyperlink or OSC 52 clipboard sequences, or title-bar manipulation used for terminal/prompt spoofing.

The attacker-controlled input chain is: a published skill repository → `SKILL.md` and any additional file in the skill directory → `discovery.FetchBlob` fetches raw blob content from the GitHub API → written unmodified to the pager.

### Impact Explanation
This matches the "Terminal output/prompt spoofing" impact class described in the question. An attacker who publishes a skill can craft file content with terminal escape/OSC sequences that render misleading text, hide/alter previously-displayed content, or manipulate terminal state (e.g., faking a confirmation prompt or clearing evidence of malicious content) when the victim runs `gh skill preview`. Depending on the pager and terminal emulator in use, this could extend to clipboard injection (OSC 52) or other terminal-emulator-specific behaviors that gh itself does not exercise or test against.

### Likelihood Explanation
Fully reachable by an unprivileged attacker: publishing a public GitHub repository with a skill directory (containing `SKILL.md` and/or any additional file) is sufficient. No special repo permissions are needed, and the victim only needs to run `gh skill preview <attacker-repo>` — a normal command flow encouraged by the feature. The default flow (`!canPrompt || len(extraFiles) == 0`) or the interactive per-file viewer both hit the unsanitized write path.

### Recommendation
Before writing any fetched blob content to `opts.IO.Out`/the pager (both the `SKILL.md` rendered output and the raw "extra files" loop), strip or neutralize ANSI/OSC control sequences that are not part of gh's own rendering output (e.g., filter out ESC-prefixed control sequences except the specific, allow-listed ones gh itself emits via `iostreams`/`colorScheme`). This sanitization should be applied uniformly regardless of whether the content is going to `opts.IO.Out` directly or to the interactive pager path, so the invariant "sanitize before leaving gh, regardless of sink" holds.

### Proof of Concept
```go
// pkg/cmd/skills/preview/preview_sanitize_test.go
func TestRenderAllFiles_StripsRawEscapeSequences(t *testing.T) {
    ios, _, out, _ := iostreams.Test()
    ios.SetStdoutTTY(true) // enable pager path
    opts := &PreviewOptions{IO: ios, RenderFile: func(_, c string) string { return c }}

    maliciousContent := "\x1b]0;PWNED\x07\x1b[2Jsafe text" // OSC title-set + clear-screen
    files := []discovery.SkillFile{{Path: "notes.txt", SHA: "sha1", Size: len(maliciousContent)}}

    apiClient := stubClientReturning(maliciousContent) // httpmock returning blob content

    renderAllFiles(opts, ios.ColorScheme(), discovery.Skill{}, files, "", files, apiClient, "github.com", "owner", "repo")

    got := out.String()
    require.NotContains(t, got, "\x1b]0;")   // OSC sequence must be stripped
    require.NotContains(t, got, "\x1b[2J")   // clear-screen escape must be stripped
    require.Contains(t, got, "safe text")
}
```
Expected result today: the test fails because `renderAllFiles` writes `maliciousContent` unmodified (the raw OSC/CSI bytes pass through `fmt.Fprint(out, sanitized)`), confirming the lack of sanitization before bytes reach the pager sink.
