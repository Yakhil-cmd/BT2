The reported bug class—an attacker cheaply spamming zero-value entries into a request queue to overwhelm a bounded off-chain processor's resources—maps to the "flooding / generic resource-exhaustion" category that the scan's own rejection rules (rule 5) explicitly exclude from consideration. It's also not a valid analog in polkadot-sdk because:

- Every signed extrinsic in FRAME pays weight/length-based transaction fees via `pallet-transaction-payment` regardless of the "amount" argument, so there is no free/cheap way to push unlimited zero-value entries into on-chain storage the way an EVM tx with only gas cost can.
- Where polkadot-sdk does have analogous "bid"/"request" queues, they already enforce minimum-amount and bounded-capacity checks, e.g. `pallet-nis`'s `place_bid` requires `amount >= T::MinBid::get()` and bounds queue length with `MaxQueueLen`/`try_insert` [1](#0-0) , and `asset-conversion`'s `do_remove_liquidity` rejects zero-amount withdrawals via `ensure!(!amount1.is_zero() ...)` [2](#0-1) .
- At the network layer, analogous "off-chain processor drowned by cheap spam" scenarios are explicitly guarded against with bounded per-peer queues and rate limiting/flooding detection, e.g. dispute-distribution's `PeerQueues::push_req` drops requests once a peer's queue reaches `PEER_QUEUE_CAPACITY` [3](#0-2) , and the statement-store network protocol implements token-bucket rate limiting with explicit flooding detection and peer disconnection [4](#0-3) .

No exact file:line evidence of an unprotected, fee-free, unbounded zero-value request queue reachable by an unprivileged signed extrinsic was found, and the bug class itself falls under the excluded "flooding/resource-exhaustion" category per the scan's own criteria.
