### Title
Protocol fee minted on gross interest before bad-debt write-down leaves suppliers permanently short - (File: `mainnet/contracts/vault/v0-vault-stx.clar` and equivalent vault contracts)

### Summary
Each vault's `accrue()` mints a protocol reserve fee to `dao-treasury` based on the full interest delta (`debt-delta`) accrued on the *entire* pool of borrowers, before any determination that part of that accrued interest belongs to a position that will subsequently default and be written off via `socialize-debt`. This mirrors the Overlay finding: a fee is recorded on the full/gross notional before the "health" of the underlying position(s) generating that notional is resolved, and the fee is never corrected afterward when a shortfall (bad debt) materializes.

### Finding Description
In every vault contract (`vault-stx.clar`, `vault-sbtc.clar`, `vault-usdc.clar`, `vault-usdh.clar`, `vault-ststx.clar`, `vault-ststxbtc.clar`, and their `mainnet` `v0-*` equivalents), `accrue()` works as follows: [1](#0-0) 

```
(let ((next (next-index))
      (scaled-principal (var-get principal-scaled))
      (old-debt (mul-div-down scaled-principal idx INDEX-PRECISION))
      (new-debt (mul-div-down scaled-principal next INDEX-PRECISION))
      (debt-delta (if (> new-debt old-debt) (- new-debt old-debt) u0))
      (reserve-inc (mul-div-down debt-delta (var-get fee-reserve) BPS))
      (treasury-lp (if (> reserve-inc u0) (mul-div-down reserve-inc (total-supply) (- (total-assets-preview) reserve-inc)) u0)))
  ...
  (if (> treasury-lp u0)
      (try! (ft-mint? zft treasury-lp .dao-treasury))
      false)
  ...)
```

`debt-delta` is the growth of the entire outstanding scaled-debt principal over the elapsed period at the borrow index rate — it includes interest accruing on every borrower's position, including those that are already underwater or about to be liquidated with a shortfall. `reserve-inc` (the protocol's cut) is computed and `treasury-lp` shares are minted to `dao-treasury` *unconditionally*, purely from index growth, with no visibility into whether the underlying debt generating that growth is actually collectible.

Later, when an underwater position is liquidated and collateral is insufficient to cover the debt, `market.clar`'s `liquidate` function calls the vault's `socialize-debt`: [2](#0-1) 

```
(define-public (socialize-debt (scaled-amount uint))
  (let (...
        (debt-reduction (mul-div-down scaled-amount idx INDEX-PRECISION))
        ...
        (new-lindex (if (and (> old-total-assets u0) (> old-total-assets debt-reduction))
                       (mul-div-down current-lindex (- old-total-assets debt-reduction) old-total-assets)
                       u0)))
    ...
    (var-set lindex new-lindex)
    (var-set principal-scaled ...)
    (var-set total-borrowed ...)
    (var-set assets ...)
    ...))
```

This write-down reduces `lindex`, the exchange-rate index that converts zToken shares into underlying value for *every* shareholder, including the `dao-treasury` shares that were just minted moments earlier in the same block (via `accrue-and-cache` calls performed at the top of `liquidate`, see `mainnet/contracts/market/v0-4-market.clar` lines 1405-1407) from interest that was, in the same transaction, revealed to be uncollectible.

Because the treasury shares are minted from the pre-write-down asset/supply ratio (`total-assets-preview` before the bad debt is recognized), and the vault has no mechanism to claw those shares back or to exclude the doomed borrower's accrued-but-uncollectible interest from `reserve-inc`, the treasury's cut effectively includes a slice of interest that never existed as real value. Since `lindex` write-down is applied to the *whole* share pool (treasury included) proportionally to the loss, but the treasury's share count was inflated an instant earlier by exactly the phantom interest, the net effect is that honest suppliers absorb a bad-debt write-down that is partially attributable to fee shares that should never have been minted in the first place — the fee is "double counted": once as newly minted treasury value, and again as part of the loss base that gets socialized across all remaining (non-treasury) value.

This is the direct structural analog of the Overlay bug: `_feeAmount` (here, `reserve-inc`/`treasury-lp`) is computed and materialized (minted) from gross notional (`debt-delta`) *before* the position-level shortfall/health outcome (bad-debt socialization) is known, and there is no adjustment mechanism afterward — exactly the pattern the report calls out and recommends fixing by only accruing fee on the "remaining part of position that is available after taking debt into account."

### Impact Explanation
This is a temporary/permanent freezing-of-funds-class impact on the supplier side: unprivileged depositors of the affected vault (e.g., USDC, sBTC suppliers) bear a socialized loss that is inflated by fee shares minted on interest that was never actually realized. Every liquidation event that ends in bad-debt socialization permanently shifts value from ordinary suppliers to `dao-treasury`'s zToken share balance beyond what actually accrued as real yield, since the fee-mint step is not reversed or adjusted when the corresponding debt is subsequently written off in the very same transaction. Over repeated liquidations with shortfalls, this compounds, degrading the redemption value available to depositors relative to what they should be entitled to.

### Likelihood Explanation
Likelihood is moderate: it requires (a) interest accruing on a position between the last accrual and the liquidation transaction, and (b) that liquidation ending in insufficient collateral to fully repay debt (triggering `socialize-debt`) — both of which are routine, expected outcomes of the protocol's liquidation and bad-debt-socialization design (visible in `market.clar`'s dedicated `no-collateral-left` / `bad-debt-socialized` handling). No attacker action beyond normal borrowing/price-drop dynamics is required, and it happens automatically on every liquidation that results in a shortfall.

### Recommendation
Do not mint the treasury's reserve share unconditionally from `debt-delta` in `accrue()`. Instead, defer or net out the fee/reserve amount that corresponds to any interest that is later found to be part of a socialized shortfall — e.g., by tracking uncollectible interest at liquidation time (as computed in `market.clar`'s bad-debt-socialization path) and burning/clawing back a proportional amount of the just-minted `treasury-lp` shares before applying `socialize-debt`'s write-down, mirroring the report's suggested fix of adjusting the fee to only the "remaining part... available after taking debt into account."

### Proof of Concept
1. Vault (e.g., `v0-vault-usdc.clar`) has active borrowers; index grows normally each block via `accrue()`, minting `dao-treasury` a `reserve-inc`-based share of `debt-delta` including interest accrued on a borrower B whose collateral (in `v0-4-market.clar`) has already dropped in USD value below `LTV-LIQ-PARTIAL`.
2. A liquidator calls `market.liquidate(borrower=B, ...)`. Inside, `accrue-user-debts` triggers `vault-accrue` → `accrue()` runs, computing `debt-delta` including B's just-added interest, and mints `treasury-lp` shares to `dao-treasury` based on the pre-loss `total-assets-preview`/`total-supply` ratio: [3](#0-2) 
3. Liquidation proceeds; because B's collateral is insufficient (`coll-removed` == 0 / `no-collateral-left` true), `market.clar` invokes bad-debt socialization, calling the vault's `socialize-debt(scaled-amount)` for B's remaining unpaid scaled debt: [4](#0-3) 
4. `socialize-debt` writes down `lindex` for the whole vault based on `old-total-assets` and `debt-reduction`, diluting all zToken holders' redemption value — including the `dao-treasury` shares minted one step earlier from interest that was, by this same step, proven uncollectible.
5. Net result: suppliers' aggregate redeemable value is lower than it would be had the treasury not been minted shares for interest that was simultaneously discovered to be unrecoverable — the fee was "recorded" (minted) before the position's shortfall was resolved, with no subsequent correction, exactly matching the Overlay double-counting pattern.

Note: I was not able to fully trace `total-assets`, `total-assets-preview`, `total-supply`, and `next-index` implementations (the file read for these was truncated in this session) to derive an exact numeric worked example; the causal ordering (mint-before-write-down, no clawback) is confirmed from the cited `accrue()`, `socialize-debt()`, and `market.clar` liquidation code, but a precise quantitative bound on the leaked amount would need those helper definitions, which should be verified in a follow-up session with full file access.
