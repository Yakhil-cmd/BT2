### Title
Duplicate leaves in an `r of set` address definition let one signer's single signature satisfy multiple threshold slots - ([File: definition.js])

### Summary
In `ocore`, multisig-style spending conditions are expressed with the `r of set` operator inside an address definition (analogous to the `UserOpMultiSigVerifier` owners array / threshold check in the report). `validateDefinition()` checks only that `required <= set.length` and recurses into each set element, but never checks that the elements of `set` are distinct (e.g. two `['sig', {pubkey: X}]` leaves with the same pubkey, or two `['address', A]` leaves pointing at the same address). `validateAuthentifiers()` then evaluates each set element independently at its own path (`path+'.'+index`) and simply counts how many elements evaluate true, requiring `count >= args.required`. [1](#0-0) [2](#0-1) 

### Finding Description
Because `ecdsaSig.verify()` for a `sig` leaf only checks that the supplied signature matches the given pubkey against the shared `unit_hash_to_sign`, and does not depend on which authentifier path it was submitted under, the exact same signature bytes can legally be placed at two different authentifier paths (e.g. `r.0` and `r.1`) if the definition contains the same pubkey twice in the `set`: [3](#0-2) 

`validateDefinition` never rejects a `set` containing duplicate sub-definitions (duplicate `sig` pubkeys or duplicate `address` references): [4](#0-3) 

and `validateAuthentifiers`'s `r of set` handler just tallies how many of the (possibly duplicated) sub-definitions independently returned true, with no de-duplication of the underlying signer identity: [2](#0-1) 

This mirrors the reported `UserOpMultiSigVerifier` bug exactly: the "index"/"path" uniqueness is enforced (each set element is evaluated at a distinct sub-path, so the same authentifier slot cannot be reused twice), but nothing enforces that the *signer identity* (pubkey/address) referenced by two different slots is unique. A malicious co-signer who proposes (or is one of the founders of) a shared/multisig address defined with `r of set` can plant their own pubkey/address at two (or more) positions in `set`. When it comes time to spend, that single co-signer contributes one signature that is copied to both paths, occupying two of the `required` slots by themselves, effectively lowering the number of *distinct* parties needed to authorize a spend below what the other cosigners believe the threshold to be. The `wallet_defined_by_addresses.js` shared-address creation flow only records signers by signing path and forwards/broadcasts the definition to cosigners; it does not check that all leaf pubkeys/addresses in the `set` are unique: [5](#0-4) [6](#0-5) 

### Impact Explanation
This breaks the core security guarantee of an `M of N` `r of set` multisig/shared address: co-signers who agree to and fund a shared address believing that `required` *distinct* parties must cooperate to spend can instead have their funds spent by a smaller, colluding subset (as few as `required - duplicates_planted` distinct signers, potentially just one signer if enough duplicate slots are planted), because one signer's single signature can be legally replicated across multiple `set` slots. This is a fund-loss/unauthorized-spending vulnerability for any address using `r of set` (directly, or via the shared-address wallet feature) with duplicated leaves.

### Likelihood Explanation
Exploitability requires the attacker to control (or convince a victim to accept) an address definition where the `set` array of an `r of set` node contains a repeated `sig` pubkey or repeated `address` reference — something entirely under the control of whoever proposes the shared-address definition, and something the current validation code does not detect or reject at definition-validation time (`validateDefinition`) or at spend time (`validateAuthentifiers`). Since address definitions are attacker-supplied data reachable from an ordinary unit author (no special privilege needed), and the shared-address creation flow in `wallet_defined_by_addresses.js` does not perform a uniqueness check on the definition it accepts/forwards, this is realistically reachable by any participant proposing a multi-party address.

### Recommendation
In `validateDefinition`'s `r of set` (and `weighted and`) handling, reject definitions whose `set` contains structurally duplicate sub-definitions that resolve to the same underlying signer identity — at minimum, reject duplicate `['sig', {pubkey}]` leaves with the same pubkey and duplicate `['address', addr]` leaves with the same address within the same `set`/`weighted and` block (and recursively through nested `or`/`and`/`address` references where feasible). As a stronger, path-independent fix, `validateAuthentifiers` could additionally track the set of already-counted signer identities (pubkeys/addresses) satisfied within an `r of set`/`weighted and` node and only count a given identity once, mirroring the report's recommendation to track used signer identities instead of just slot/path uniqueness.

### Proof of Concept
1. Attacker (co-signer #1) proposes a shared address whose definition is:
```json
["r of set", {
  "required": 2,
  "set": [
    ["sig", {"pubkey": "<attacker_pubkey>"}],
    ["sig", {"pubkey": "<attacker_pubkey>"}],
    ["sig", {"pubkey": "<honest_cosigner_pubkey>"}]
  ]
}]
```
`validateDefinition` accepts this because `required (2) <= set.length (3)` and each `sig` leaf is independently well-formed — no duplicate check exists. [4](#0-3) 
2. Other cosigners see a nominal "2 of 3" address and fund it, believing 2 distinct parties must cooperate to spend.
3. When spending, the attacker signs the message once with their own key and submits the identical signature value under both `r.0` and `r.1` in `assocAuthentifiers`.
4. `validateAuthentifiers` evaluates `r.0` and `r.1` independently; both pass `ecdsaSig.verify` against the same `unit_hash_to_sign` and pubkey, `count` reaches 2, satisfying `required`, without any input from the honest cosigner. [7](#0-6)

// Returns a map of signing_path -> address for every ["address", ...] leaf in the definition
function extractAddressPathsFromDefinition(arrDefinition) {
	var result = {};
	function traverse(arr, path) {
		if (!Array.isArray(arr) || arr.length < 2) return;
		var op = arr[0];
		var args = arr[1];
		switch (op) {
			case 'or':
			case 'and':
				if (Array.isArray(args))
					for (var i = 0; i < args.length; i++)
						traverse(args[i], path + '.' + i);
				break;
			case 'r of set':
				if (args && Array.isArray(args.set))
					for (var i = 0; i < args.set.length; i++)
						traverse(args.set[i], path + '.' + i);
				break;
			case 'weighted and':
				if (args && Array.isArray(args.set))
					for (var i = 0; i < args.set.length; i++)
						traverse(args.set[i].value, path + '.' + i);
				break;
			case 'address':
				result[path] = args;
				break;
			case 'hash':
				result[path] = 'secret';
				break;
			case 'in merkle':
				result[path] = ''; // empty address
				break;
		}
	}
	traverse(arrDefinition, 'r');
	return result;
}
