### Title
Webhook signature verification keys on `repository.owner.login`/`organization.login`, but every handler acts on the unauthenticated `repository.full_name` field — cross-organization/cross-repository status and sync spoofing ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate the HMAC signature against using `repository_owner`, computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0) . Once the signature check passes, the full raw payload is dispatched to handlers, all of which resolve the target `Repository`/`Stack` from a *different* field: `payload.dig('repository', 'full_name')` [2](#0-1) . Because the field used to pick the verification secret (`repository.owner.login`) and the field used to select the acted-upon repository (`repository.full_name`) are independent, attacker-controlled JSON keys in the same payload, an operator who legitimately controls one onboarded GitHub organization (and therefore knows that organization's `webhook_secret`) can forge a payload whose `repository.owner.login` matches their own org (so it passes HMAC verification) while `repository.full_name` names a stack belonging to a completely different, unrelated organization/repository onboarded to the same Shipit instance.

### Finding Description
This is the same "verified field vs. acted-upon field" mismatch as the `StakingVault.acceptPositionManagerRewards()` report: there, `transferFrom` used an attacker-supplied `from` instead of `msg.sender`, breaking the binding between "who approved" and "whose tokens move." Here, Shipit breaks the binding between "which organization's secret authenticated this webhook" and "which repository/stack the webhook payload is applied to":

- Verification binds to `repository.owner.login` (or `organization.login`): `Shipit.github(organization: repository_owner)` then `github_app.verify_webhook_signature(signature, raw_post)` [3](#0-2) .
- Every action taken by handlers binds to `repository.full_name` via `Repository.from_github_repo_name(repository_name)` and `Stack`s scoped to that repository [2](#0-1) , e.g. `PushHandler#process` triggers `stack.sync_github` for every non-archived stack on the matching branch [4](#0-3) , and `StatusHandler#process` creates a GitHub-sourced commit status for any `Commit` matching the attacker-supplied `sha` regardless of which repository/org it belongs to [5](#0-4) .

Because `Shipit.github_app_config(organization)` looks up per-organization `webhook_secret` values independently per org in a multi-org deployment [6](#0-5) , and the controller derives that org purely from the unauthenticated payload body rather than from a channel the attacker cannot control, the equality the engine needs to hold — `organization whose secret signed the request == organization owning the repository the handler mutates` — does not hold. An attacker with legitimate access to Org A's webhook secret (any GitHub org admin who onboards their org to the shared Shipit instance) can sign a payload with `repository.owner.login = "org-a"` while setting `repository.full_name = "org-b/victim-repo"`, and the HMAC check passes because it only ever looks at `org-a`'s secret and the raw body — it never checks that `repository.full_name` actually belongs to `org-a`.

### Impact Explanation
On a Shipit instance shared across multiple GitHub organizations (the documented multi-org configuration in `docs/setup.md`), this allows a party who only controls one onboarded organization to forge webhook events attributed to any other onboarded organization's repositories:
- `StatusHandler` lets the attacker inject arbitrary CI/CD status payloads (`state`, `context`, `target_url`, `description`) against any commit `sha` they can guess/know in a victim's stack, which Shipit's status-gating logic in `Commit` uses to determine deployability [5](#0-4) . This can be used to mark a victim's commit as passing CI even though it never did, enabling an unauthorized/unreviewed deploy to proceed.
- `PushHandler`/`GithubSyncJob` lets the attacker trigger sync jobs on stacks belonging to a repository/org they don't own [4](#0-3) .

This matches the "unauthorized deploy" and "cross-repository writes" impact classes.

### Likelihood Explanation
Requires only that the attacker be an admin of any single GitHub organization that has been onboarded to the shared Shipit instance and has installed the GitHub App there (which grants them access to that org's own `webhook_secret`, a routine, expected capability for organization owners in a multi-tenant Shipit deployment). No access to the victim organization's secret, a Shipit session, or an `ApiClient` token is needed — this is a pure webhook-payload forgery against the public `/webhooks` endpoint.

### Recommendation
Bind the field used for signature verification to the same field used to determine the acted-upon repository/stack. Concretely, after verifying the signature with the org derived from the payload, re-derive `repository.full_name`'s owning organization and require it to equal `repository_owner`/`organization.login` before invoking handlers (or better, always resolve the target stack's expected organization from `Repository`/`Stack` records and require the *verified* organization to match).

### Proof of Concept
1. Attacker legitimately controls GitHub org `attacker-org`, which is onboarded to a shared Shipit instance and has its own `webhook_secret` in `config/secrets.yml` under `github.attacker-org.webhook_secret`.
2. Attacker crafts a `status` event payload:
```json
{
  "sha": "<victim-commit-sha>",
  "state": "success",
  "context": "ci/tests",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. Attacker signs the raw body with `attacker-org`'s known `webhook_secret` and sets `X-Hub-Signature` accordingly, then POSTs to `/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: 'attacker-org')` and successfully verifies the signature against `attacker-org`'s secret [3](#0-2) .
5. `StatusHandler.call(params)` is invoked with the full payload and creates a spoofed passing status on the victim's commit belonging to `victim-org/victim-repo`, because it only looks at `repository.full_name`/`sha` and never re-checks the owner used for verification [5](#0-4) .

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event

    end

    def repository_owner

    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
