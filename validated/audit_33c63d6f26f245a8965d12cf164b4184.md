### Title
Missing newline (`\n`) sanitization for formula-computed data-feed names/values allows delimiter-injection into the newline-delimited kvstore keys - (File: `aa_validation.js`, `validation.js`, `main_chain.js`)

### Summary
Data feeds are persisted in the key-value store using `\n` as an internal field delimiter (`'df\n'+address+'\n'+feed_name+'\n'+type+'\n'+value+'\n'+mci`), exactly the kind of "line-based" data structure that CVE-2017-6200 abused (Sandstorm's `findFilesToZip` treated `\n` as a record separator without filtering it out of attacker-controlled directory names). ocore is aware of this class of bug and explicitly rejects literal `feed_name`/`value` strings containing `\n` in both unit validation and AA-definition validation — but only for the *static* (non-formula) case. The check is skipped whenever the field is a formula, and the formula's evaluated result is never re-checked for embedded `\n` before being written into the `data_feed` payload and ultimately persisted as a kvstore key.

### Finding Description
In `validation.js`, `validateInlinePayload` filters plain `data_feed` payload fields for `\n`: [1](#0-0) 

In `aa_validation.js`, the AA-definition validator applies the identical `\n` check, but the guard is wrapped in `if (feed_name_formula === null)` / `if (value_formula === null)` — i.e. it is only enforced when the feed name/value is a literal string, not a formula: [2](#0-1) 

When the AA actually executes (in `aa_composer.js`), formula-keyed/valued object fields are computed and substituted back into the message payload via `replace()`, with checks only for “duplicate key” and “looks like a formula again” — there is no re-validation that the computed string is free of `\n`: [3](#0-2) [4](#0-3) 

The resulting `data_feed` message (with an attacker/AA-author-controlled string that may contain an embedded `\n`) is then written into the kvstore using raw `\n`-joined keys during stabilization: [5](#0-4) 

and looked up the same way in `data_feeds.js`: [6](#0-5) [7](#0-6) 

Because the address/feed_name/type/value/mci fields are concatenated with `\n` and parsed back with `key.split('\n')` (see `string_utils.getValueFromDataFeedKey`, which asserts exactly 6 parts), an embedded `\n` inside a formula-computed `feed_name` or `value` breaks the assumed 1:1 mapping between logical fields and physical key segments: [8](#0-7) 

This is structurally the same root cause as CVE-2017-6200: a sanitization routine exists for the delimiter character, but it is applied inconsistently, leaving a code path (here: formula-derived strings) where the delimiter can still reach the sensitive string-splitting logic.

### Impact Explanation
An AA author can craft a `data_feed` message whose `feed_name` or `value` is a formula (bypassing the static `\n` filter) that evaluates, at trigger time, to a string containing an embedded `\n`. Depending on how the resulting `\n`-delimited key is later parsed by `data_feed()`/`in_data_feed()` oracle lookups (used pervasively by other AAs to make funds-releasing decisions, e.g. price oracles, existence checks with `min_mci`/`ifseveral`), a maliciously crafted feed_name/value could:
- Inject extra pseudo-fields into the `df\n...` key so that `getValueFromDataFeedKey`/prefix range queries in `dataFeedByAddressExists`/`readDataFeedByAddress` associate an attacker-chosen value with a different `feed_name`/`type`/`mci` boundary than intended, corrupting oracle lookups relied on by other AAs for asset issuance, payment release, or supply-affecting logic.
- Cause disagreement between nodes if any downstream consumer parses the key differently, risking stability/validity divergence for the affected data feed reads.

This can translate into fund loss/freezing or wrong payouts in AAs that gate spending on `data_feed()`/`in_data_feed()` results, satisfying the required "AA fund loss or freezing" / "node disagreement" bar.

### Likelihood Explanation
Likelihood is moderate: it requires (a) an oscript/ojson mechanism to produce a runtime string containing an actual `\n` byte without a literal newline appearing in the AA source (which the `formula/parse_ojson.js`'s `searchNewlineRecursive` blocks only at parse time for literal source text), and (b) a downstream data-feed consumer whose logic depends on exact key boundaries. Since the codebase explicitly hardened the *literal* path against this exact bug class but left the *formula* path unguarded, this looks like an incomplete fix rather than a hypothetical gap, closely mirroring the Sandstorm root cause (filter applied to only one code path that produces the sensitive value).

### Recommendation
Re-apply the same `\n` (and length) checks against the *evaluated* `feed_name`/`value` strings at the point they are substituted into the `data_feed` payload in `aa_composer.js`'s `replace()` (both the key-substitution branch and the value-substitution branch), not just at AA-definition-validation time for literal strings. Equivalently, add a final sanitization/rejection step in `validateInlinePayload`'s `data_feed` case and in `main_chain.js`'s `addDataFeeds`/`data_feeds.js` before constructing the `\n`-joined kvstore key, bouncing the AA response if `\n` is present in any computed feed name or value, matching the existing static-string behavior in `validation.js` lines 1936/1942 and `aa_validation.js` lines 100/109.

### Proof of Concept
Conceptual outline (exact formula syntax capable of yielding a byte `\n` without a literal newline in AA source needs confirmation from a live oscript grammar/escape review, which is outside what can be validated via static code search alone):
1. Define an AA with a `data_feed` message whose `feed_name` (or `value`) is a formula, e.g. `"{some_expr_producing_newline}": "{val}"`.
2. `aa_validation.js`'s `data_feed` case skips the `\n` check because `getFormula(feed_name) !== null` (lines 96-101).
3. At trigger time, `aa_composer.js`'s `replace()` evaluates the formula to a string containing an embedded `\n` and assigns it into the payload without any `\n` check (lines 639-654 / 682-695).
4. On stabilization, `main_chain.js`'s `addDataFeeds` writes `'df\n'+address+'\n'+feed_name+'\n...'` into kvstore, where `feed_name` itself now contains an extra `\n`, shifting field boundaries relative to what `getValueFromDataFeedKey`/`getMciFromDataFeedKey` expect.
5. A separate AA relying on `data_feed()`/`in_data_feed()` against that oracle address may retrieve or match against a corrupted/attacker-influenced value or existence result.

Note: I was not able to confirm within the indexed code whether the oscript formula language exposes a primitive that yields a literal `\n` character at evaluation time (e.g., a `char()`/codepoint function) without violating `parse_ojson.js`'s `searchNewlineRecursive` literal-source check; this should be verified in a live Devin session against the full `formula/grammars/oscript.ne` and `formula/evaluation.js` for any codepoint-to-char, `\u000A`-escape, or string-concatenation path that can synthesize `\n` at runtime.

function getMciFromDataFeedKey(key){
	var arrParts = key.split('\n');
	var strReversedMci = arrParts[arrParts.length-1];
	var reversed_mci = parseInt(strReversedMci, 16);
	var mci = 0xFFFFFFFF - reversed_mci;
	return mci;
}

// df:address:feed_name:type:value:strReversedMci
function getValueFromDataFeedKey(key){
	var m = key.split('\n');
	if (m.length !== 6)
		throw Error("wrong number of elements in data feed "+key);
	var type = m[3];
	var value = m[4];
	return (type === 's') ? value : decodeLexicographicToDouble(value);
}
