### Title
`in_data_feed()` reports unstable AA data feeds as existing without the sequence/finality check that `data_feed()` performs, causing a state-existence oracle mismatch - ([File: data_feeds.js])

### Summary
`data_feeds.js` implements two parallel lookup paths for oscript's `data_feed[[...]]` and `in_data_feed[[...]]` functions: `readDataFeedValue()` and `dataFeedExists()`. Both scan `storage.assocUnstableMessages` to let AA logic see fresh, not-yet-stable data-feed messages posted by other AAs before MC stabilization. `readDataFeedValue()` explicitly discards candidate units whose `sequence` is not `'good'` (i.e., units that are provisionally judged non-serial/"final-bad" and destined to be voided), but `dataFeedExists()`'s equivalent scan has no such filter.

### Finding Description [1](#0-0) 
`readDataFeedValue()`'s unstable-message scan explicitly requires `objUnit.sequence !== 'good'` to `continue` (skip) a candidate unit, ensuring only units that are provisionally valid ("good" sequence) are used to answer a `data_feed` query. [2](#0-1) 
`dataFeedExists()`'s analogous unstable-message scan (used for `in_data_feed`) filters only by `objUnit.bAA`, address, and MCI range - it never checks `objUnit.sequence`. This means a unit that has been provisionally marked non-serial ("final-bad", i.e. a unit that will be voided once its conflicting sibling wins the double-spend race and content stripped) can still cause `in_data_feed` to report `true` for a data-feed value that `data_feed` would correctly treat as "not found" for the same query.

This mirrors the MyBB bug class exactly: two code paths perform semantically the "same" existence check over the same underlying dataset, but only one of them validates the record's true/final visibility state (`sequence`/`visible` analog) before answering, creating a boolean oracle inconsistency between the two.

### Impact Explanation
AA definitions commonly gate control flow and fund release using `in_data_feed[[...]]` as a lightweight existence test before optionally reading the actual value with `data_feed[[...]]`. If an attacker can arrange for a conflicting/soon-to-be-voided AA-authored unit to exist transiently in the unstable DAG (`sequence` not yet `'good'`, on track to become `final-bad`), `in_data_feed` can answer `true` based on data that `data_feed` would never honor and that will disappear once the network reaches stability. An AA that branches its logic (e.g., releasing funds or unlocking a state transition) on `in_data_feed` alone could act on data that is never authoritative, leading to AA fund loss/incorrect payouts or state divergence between what full nodes eventually agree is canonical and what the AA already acted upon.

### Likelihood Explanation
Exploitability depends on whether AA-authored ("bAA") units can practically enter a non-`'good'` sequence state (i.e., become subject to a double-spend/non-serial race before finality) in ways an attacker can trigger deterministically. I was unable to fully verify this precondition within the available investigation budget — I could not trace `main_chain.js`'s sequence-assignment logic and `writer.js`'s handling of `bAA` units far enough to confirm whether AA response units can realistically become non-serial through attacker-controlled means, or whether this is purely a defensive/theoretical gap in the code that in practice never diverges from `readDataFeedValue()`'s outcome (e.g., because AA balances/response generation are deterministic and never actually race). This should be validated further (e.g., attempting a double-spend race that touches an AA-authored data-feed message, or auditing `main_chain.js` sequence determination) before treating this as a confirmed, immediately-exploitable bug.

### Recommendation
Add the same `objUnit.sequence !== 'good'` filter to the unstable-message scan inside `dataFeedExists()` (data_feeds.js, lines 34-44) that `readDataFeedValue()` already applies, so that `in_data_feed` and `data_feed` agree on which unstable AA-authored messages are eligible to be treated as existing.

### Proof of Concept
Not fully constructible without confirming the sequence-assignment precondition noted above. Conceptually: an attacker/AA author defines two AAs (or an AA and a conflicting unit) such that an AA-authored unit carrying a `data_feed` message is temporarily included in `storage.assocUnstableMessages` with `sequence` not yet `'good'`, and a downstream AA queries `in_data_feed[[oracles=..., feed_name=..., feed_value=...]]` referencing that message before stabilization completes, while a parallel `data_feed[[...]]` call on the identical parameters returns "not found." This observable divergence, if reachable, is the exploitable analog of the reported CVE's "internal query succeeds while the authoritative query says no result" bug class.
