### Title
`StatusHandler#process` writes forged statuses onto any `Commit` row matching a SHA, unscoped by repository/stack - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits purely by SHA across the entire database — `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github! }` — with no filter tying the lookup to the repository named in the webhook payload. Every other handler (e.g. `PushHandler`) scopes its side effects through `stacks`, which resolves `Repository.from_github_repo_name(repository_name)` before touching any `Stack`; `StatusHandler` does not. As a result, a genuinely signed `status` webhook from repository A can write a `Status` onto a `Commit` belonging to an unrelated `Stack`/repository B whenever both happen to have a `Commit` row with the same `sha`, which is the normal case for forks that share upstream git history.

### Finding Description
The broken binding is: for a `Status` created by `StatusHandler#process`, `status.commit.stack.repository` should equal the repository that the verified webhook payload named (`payload.dig('repository','full_name')`), i.e. `commit.stack.repository == Repository.from_github_repo_name(payload['repository']['full_name'])`. This does not hold.

Code path:
- `WebhooksController#create` verifies the HMAC signature using the *organization derived from the payload's own `repository.owner.login`* via `verify_signature` [1](#0-0) . This only proves the request was signed with the secret configured for that organization's hook — it says nothing about which `Commit`/`Stack` rows may be mutated.
- `StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [2](#0-1) 
This query has no `stack_id`/repository filter at all, unlike `PushHandler#process`, which resolves the affected stacks strictly through `stacks.not_archived.where(branch:)`, where `stacks` is `Repository.from_github_repo_name(repository_name)&.stacks` [3](#0-2) [4](#0-3) .
- `Commit` rows are uniquely keyed on `(sha, stack_id)`, not globally unique on `sha` [5](#0-4) , so the same SHA legitimately exists as separate rows under different stacks/repositories whenever two `Repository` records share git ancestry (a fork of a public/tracked project, a repo re-added under a second `Repository`/`Stack`, etc.). `create_status_from_github!` → `add_status` writes the forged status, recomputes `commit.status`, fires `deployable_status`/`commit_status` hooks, and schedules continuous delivery for whichever stack owns that row [6](#0-5) [7](#0-6) .
- `Commit#blocked?` and `#deployable?` then read exactly that row: `stack.commits.reachable.newer_than(stack.last_deployed_commit).older_than(self).any?(&:blocking?)` [8](#0-7) , and `blocking?` is driven by the freshest status per `Status::Common#blocking?` (`!success? && commit.blocking_statuses.include?(context)`) [9](#0-8) .

Attacker action: attacker owns (or forks) a GitHub repository that Shipit already tracks as its own `Stack`/`Repository` (a legitimate, unprivileged onboarding — they only need *a* tracked repo, not the victim's). That repository shares an ancestor commit SHA with the victim's tracked repository (trivial via forking a public upstream project). The attacker sets a commit status (success/anything non-blocking, using a `context` string matching the victim's `blocking_statuses` configuration) on that shared SHA via the normal GitHub API on their own repo. GitHub fires a genuinely signed `status` webhook for the attacker's repository. `verify_signature` passes because the signature is real for that organization. `StatusHandler#process` then matches and mutates *every* `Commit` row in the database with that SHA, including the victim's, flipping `blocking?` to false on the victim's commit and thus `blocked?`/`deployable?` on the victim's head commit — enabling an unauthorized deploy on a stack the attacker never authenticated against.

Existing guards do not stop this: `verify_signature` only authenticates "this event was for organization X"; it never constrains which `Commit`/`Stack` rows the handler is allowed to touch, and `StatusHandler` (unlike `PushHandler`) omits the `stacks`/`Repository.from_github_repo_name` scoping that would have prevented cross-repository writes.

### Impact Explanation
A payload correctly authenticated for repository/organization A causes a `Status` record to be written against a `Commit`/`Stack` belonging to unrelated repository/organization B, flipping `Commit#blocking?`, `#blocked?`, and `#deployable?` for B's deploy queue and triggering `schedule_continuous_delivery`/`ProcessMergeRequestsJob` for B. This is a cross-tenant write causing an unauthorized deploy decision on a stack the attacker never authenticated against — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team" / "an unauthorized deploy". It is repeatable against any victim stack that shares commit ancestry (fork lineage) with any repository the attacker controls and that Shipit already tracks.

### Likelihood Explanation
Preconditions: (1) the attacker must control at least one GitHub repository already onboarded into this Shipit instance as a `Stack` (this is a normal, low-privilege onboarding action, not a secret-holding privilege); (2) that repository must share a commit SHA with the victim stack's undeployed commit range — trivially true for forks of the same upstream project, and increasingly likely the more forks/mirrors are tracked; (3) the victim stack must have `blocking_statuses` configured and a currently-blocking status on that shared commit. No GitHub App private key, `webhook_secret`, `api_clients_secret`, or session is needed — the attacker uses only their own legitimately signed webhook traffic. This is feasible without any cryptographic collision attack, contrary to the question's SHA-collision framing; the shared-ancestry fork scenario is the practical, low-cost path.

### Recommendation
Scope `StatusHandler#process` to the stacks that match the payload's own `repository.full_name`, mirroring `PushHandler`: resolve `stacks` via `Repository.from_github_repo_name(repository_name)&.stacks` and restrict the `Commit` lookup to `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalently `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, so a verified webhook can only mutate commits belonging to the repository/stacks it was actually signed for.

### Proof of Concept
Minitest under `test/models/webhooks/handlers/status_handler_test.rb` (or extend `test/controllers/webhooks_controller_test.rb`):
1. Create two `Stack`s backed by two different `Repository` rows (`victim/repo`, `attacker/repo`), each with its own `GithubHook::Repo` secret (mirrors fixtures like `shipit_status`/`cyclimse_push`).
2. Create a `Commit` with the same `sha` under both stacks (simulating shared fork ancestry): `victim_commit = victim_stack.commits.create!(sha: shared_sha, ...)`, `attacker_commit = attacker_stack.commits.create!(sha: shared_sha, ...)`.
3. Configure `victim_stack.cached_deploy_spec` (or equivalent) with `blocking_statuses` including a context, and give `victim_commit` a blocking (non-success) `Status` with that context so `victim_commit.blocking?` is true and the victim head commit's `blocked?`/`deployable?` reflect that.
4. Assert baseline: `assert victim_head_commit.blocked?` and `refute victim_head_commit.deployable?`.
5. POST to `/webhooks` with `X-Github-Event: status`, a payload whose `repository.full_name` is `attacker/repo` and `sha` equal to `shared_sha`, `state: 'success'`, matching `context`, signed with `attacker` hook's real secret (stub `verify_webhook_signature` to return true for the attacker org only, as existing tests do).
6. Assert the binding: `victim_commit.reload.statuses` gained no new attacker-authored row tied to `victim_stack`'s CI gate state — i.e. `assert_no_difference -> { victim_commit.reload.statuses.count }` should hold if fixed, but on current code `assert_difference` shows a status row lands on `victim_commit`, and `victim_head_commit.blocked?`/`deployable?` change (`refute victim_head_commit.blocked?`, `assert victim_head_commit.deployable?`) even though the request was only ever signed for `attacker/repo`.
