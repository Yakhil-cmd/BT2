### Title
`StatusHandler#process` writes GitHub status updates to commits in any stack sharing a SHA, regardless of the webhook's originating repository - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits with `Commit.where(sha: params.sha).each`, a global query with no repository scoping, then calls `commit.create_status_from_github!(params)` on every match. Unlike the pattern intended by the `Handler` base class (`stacks` scoped via `Repository.from_github_repo_name(repository_name)`), `StatusHandler` never restricts the lookup to commits belonging to stacks of the repository that the verified webhook signature actually covers, so a validly-signed status webhook for an attacker-owned repository can create a `Status` on a same-SHA commit belonging to an unrelated victim stack.

### Finding Description
The broken binding: for a `status` webhook signed for `attacker_owner/attacker_repo`, the only stacks that should have `Status` rows created must satisfy `stack.repository == Repository.from_github_repo_name(payload.repository.full_name)` (i.e., `victim_stack == attacker_stack`). In `StatusHandler#process`: [1](#0-0) 
the code queries `Commit.where(sha: params.sha)` with no join/filter on `stack.repository`, so `victim_stack != attacker_stack` yet the victim's commit is still processed.

`WebhooksController#verify_signature` only proves the payload was genuinely signed by GitHub for the org named in the payload (`repository_owner`): [2](#0-1) 
It says nothing about which *stacks* the handler is permitted to mutate — that scoping is left entirely to each handler. The `Handler` base class explicitly provides the correct primitive for this, `stacks`, built from `payload.dig('repository', 'full_name')`: [3](#0-2) 
but `StatusHandler#process` never calls or filters through `stacks`; it hits the global `Commit` table directly by SHA.

From there, `Commit#create_status_from_github!` calls `Status.replicate_from_github!(stack_id, github_status)` using `self.stack_id` (the victim commit's own stack_id, not anything derived from the webhook payload): [4](#0-3) [5](#0-4) 
Creating this `Status` triggers `after_commit :schedule_continuous_delivery` on `Status`, which calls `commit.schedule_continuous_delivery`: [6](#0-5) 
and `Commit#schedule_continuous_delivery` re-evaluates `deployable?` (`!locked? && (stack.ignore_ci? || (success? && !blocked?))`) and, if true together with `stack.continuous_deployment?` and `stack.deployable?`, enqueues `ContinuousDeliveryJob` for the **victim** stack: [7](#0-6) [8](#0-7) 

Exploit flow, given the stated SHA-collision precondition (a commit with identical SHA exists in both `attacker/repo`'s stack and `victim-org/victim-repo`'s stack — this is the given precondition, not something demonstrated here):
1. Attacker pushes/commits to their own repo, then triggers (or GitHub sends) a `status` webhook for `attacker/repo` with `state: success` for that colliding SHA.
2. `verify_signature` legitimately succeeds because the webhook really is signed for `attacker`'s org — no forgery of secrets required.
3. `StatusHandler#process` queries `Commit.where(sha: ...)` globally, finds **both** the attacker's commit and the victim's commit (same SHA, different stacks), and calls `create_status_from_github!` on each.
4. The victim commit gets a `Status` row created attributed to `victim_stack.id` even though the verified webhook was never for `victim-org/victim-repo`.
5. If `victim_stack.continuous_deployment?` is enabled, this can flip `deployable?` and enqueue `ContinuousDeliveryJob` for the victim stack.

No existing guard prevents this: `verify_signature` authenticates the org, not the stack scope of the DB write; `drop_unhandled_event` and `ExplicitParameters` only validate webhook shape/event type; there is no `stacks`/`Repository.from_github_repo_name` filter applied in `StatusHandler#process` as there is meant to be per the `Handler` base class design.

### Impact Explanation
An attacker who fully controls one repository (their own fork/org) can, via a legitimately-signed webhook for that repository, cause a `Status` record to be written into a completely different, victim-owned stack, and — when continuous deployment is enabled — cause `ContinuousDeliveryJob` to be enqueued for that victim stack. This is "a payload for one repository mutating another's stack/commit," matching the Critical impact category (cross-tenant stack mutation / potential unauthorized deploy trigger). Blast radius: any stack whose commit table contains a commit with the same SHA as one in the attacker's repository is affected, across tenants sharing the same Shipit deployment.

### Likelihood Explanation
This finding is entirely conditioned on the stated SHA-collision precondition being satisfied (the same 40-hex SHA existing as a `Commit` row in both the attacker's stack and the victim's stack) — the prompt explicitly directs treating that as a given precondition rather than something to be independently proven, since finding a genuine SHA-1 collision is not feasible. Given that precondition, the rest of the exploit requires no privileged access: attacker only needs a repository they own to receive a legitimately GitHub-signed `status` webhook. `victim_stack.continuous_deployment?` must be enabled for the deploy-job impact.

### Recommendation
Scope `StatusHandler#process` to the repository named in the verified webhook payload, mirroring the `stacks` helper already provided by `Handler`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This ensures `Status` rows (and any consequent `schedule_continuous_delivery`) are only created for commits belonging to the repository/stacks that the verified webhook signature actually authenticates.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, or equivalent - not to be created here, just outlined):
```ruby
test "status webhook for attacker repo does not create Status on victim stack's colliding-sha commit" do
  victim_stack = shipit_stacks(:shipit)
  victim_stack.update!(continuous_deployment: true)
  victim_commit = victim_stack.commits.create!(sha: "a" * 40, message: "victim commit")

  attacker_stack = Shipit::Stack.create!(repository: shipit_repositories(:some_other_repo))
  attacker_commit = attacker_stack.commits.create!(sha: "a" * 40, message: "attacker commit")

  payload = {
    "sha" => "a" * 40,
    "state" => "success",
    "context" => "ci/attacker",
    "repository" => { "full_name" => attacker_stack.repository.full_name, "owner" => { "login" => attacker_stack.repository.owner } }
  }

  assert_no_difference -> { victim_commit.statuses.count } do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end

  assert_no_enqueued_jobs(only: Shipit::ContinuousDeliveryJob) do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end
end
```
Binding assertion: `victim_stack (owner of victim_commit) != Repository.from_github_repo_name(payload['repository']['full_name']).stacks` — before the fix this test fails (a `Status` is created on `victim_commit` and, with `continuous_deployment` enabled, `ContinuousDeliveryJob` is enqueued with `[victim_stack]`); after applying the recommended `stacks`-scoped fix, both assertions pass.
