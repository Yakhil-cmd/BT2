## Title
Webhook signature is verified against the organization named in `repository.owner.login`, but the repository acted upon is looked up from the unrelated `repository.full_name` field — ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification based on `repository_owner`, a value read directly out of the untrusted JSON payload (`params.dig('repository','owner','login')`, falling back to `params.dig('organization','login')`). Once that organization's secret validates the signature, the *entire* raw payload is handed to the registered handlers unmodified. Those handlers (`Shipit::Webhooks::Handlers::Handler#repository_name`, used by `PushHandler`, `PullRequest::OpenedHandler`, etc.) independently pull the repository to operate on from `payload.dig('repository','full_name')` — a different field that is never cross-checked against the organization whose secret authenticated the request.

### Finding Description
The controller's authentication step is: [1](#0-0) [2](#0-1) 

`repository_owner` is derived purely from attacker-supplied JSON, and is used only to pick which configured org's `webhook_secret` (`Shipit.github(organization: repository_owner)`) is used to check the signature: [3](#0-2) 

Shipit is explicitly designed to host multiple independent GitHub organizations side by side, each with its own App/secret, as shown in the sample multi-org secrets file: [4](#0-3) 

Once `verify_signature` passes, `create` dispatches the *raw parsed payload* to every registered handler for the event: [5](#0-4) 

Handlers determine which `Stack`/`Repository` to act on from a completely separate payload field, `repository.full_name`, with no re-validation that this repository belongs to the same organization that supplied a valid signature: [6](#0-5) 

`PushHandler` then queries and mutates stacks scoped only by that `repository_name` lookup: [7](#0-6) 

`Repository.from_github_repo_name` performs a pure string split/lookup with no ownership binding back to the authenticating org: [8](#0-7) 

This is the exact "organization that authenticated versus the repository that is written" binding described in scope: the org whose `webhook_secret` validated the HMAC (`repository.owner.login`) is never required to equal, or even be checked against, the org/repo encoded in `repository.full_name` that the handler actually acts on. A GitHub App owner for organization A (who legitimately possesses A's `webhook_secret` because they administer A's own GitHub App integration with this Shipit instance) can send a payload where `repository.owner.login = "orgA"` (so the signature check passes using A's secret) while setting `repository.full_name = "orgB/victim-repo"` for a stack belonging to a completely unrelated organization B that is also configured on the same Shipit instance. `PushHandler` will happily call `stack.sync_github(expected_head_sha: ...)` on org B's stacks, and `PullRequest::OpenedHandler` will create/provision review stacks under org B's `Repository` using org A's forged, but signature-valid, request.

### Impact Explanation
This breaks cross-tenant isolation between GitHub organizations hosted on the same Shipit instance. An attacker who legitimately controls a webhook secret for one organization (a normal, unprivileged relationship from Shipit's perspective — they are not a privileged Shipit user, GitHub team member, or `ApiClient`) can forge events attributed to a different organization's repositories: trigger `sync_github` (updating "last deployed"/HEAD tracking and potentially forcing out-of-band commit fetch/deploy eligibility state) on victim stacks, or open/close/label PRs, provisioning or tearing down review stacks for repositories they do not own. This is a cross-repository/cross-organization write achieved purely by crafting payload fields that are not covered by the signature-selection binding, satisfying the "cross-repository writes" impact category.

### Likelihood Explanation
Any Shipit deployment that onboards more than one GitHub organization (a documented, supported configuration per `config/secrets.development.shopify.yml`) is affected. The only prerequisite is administering a legitimate GitHub App/webhook integration for *any one* of the hosted organizations — no Shipit account, `ApiClient` token, or access to the victim org is required. The mismatch is a structural design flaw (signature-selection field ≠ processing-target field), not a rare edge case, so it is reliably exploitable whenever multi-tenant hosting is used.

### Recommendation
After signature verification succeeds, re-derive (or cross-check) the repository/organization the handlers will operate on strictly from the same field(s) used to select the verifying secret (or vice-versa), and reject the webhook if `repository.full_name`'s owner segment does not match `repository_owner`/the org whose secret validated the signature. Alternatively, thread the authenticated organization through to `Handler#stacks`/`#repository_name` and require an equality check against it before any stack lookup or mutation.

### Proof of Concept
1. Configure Shipit with two organizations, `orgA` and `orgB`, each with its own GitHub App and `webhook_secret` (as in `config/secrets.development.shopify.yml`), both hosting stacks.
2. As the administrator of `orgA`'s GitHub App (a normal, unprivileged capability relative to Shipit itself — no Shipit account needed), craft a `push` event JSON body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen sha>",
     "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" }
   }
   ```
3. Compute `X-Hub-Signature: sha1=<hmac using orgA's known webhook_secret over the raw body>`.
4. POST to `/webhooks` with `X-Github-Event: push`. `verify_signature` resolves `repository_owner` to `"orgA"`, fetches `orgA`'s app, and validates successfully (`app/controllers/shipit/webhooks_controller.rb:24-30`, `lib/shipit/github_app.rb:76-83`).
5. `create` dispatches to `PushHandler`, whose `stacks` helper resolves `Repository.from_github_repo_name("orgB/victim-repo")` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`, `app/models/shipit/repository.rb:53-56`) and calls `stack.sync_github(expected_head_sha: params.after)` on `orgB`'s stack (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) — despite the request never being authenticated by, or on behalf of, `orgB`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
