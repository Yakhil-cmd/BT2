### Title
Membership webhook with unverified signature lets an attacker link an arbitrary existing `User` to an arbitrary `Team` via `find_or_create_by_login!`/`add_member` - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`Shipit::GitHubApp#verify_webhook_signature` unconditionally returns `true` when no `webhook_secret` is configured for the resolved organization, so any org lacking a configured secret accepts unsigned/forged webhooks. `MembershipHandler#process` then resolves `params.member.login` via `User.find_or_create_by_login!`, which matches an already-existing `Shipit::User` row by login instead of any authenticated identity, and calls `team.add_member(member)` on a `Team` resolved purely from the attacker-supplied `params.team.id`. This lets an attacker create a `Membership` linking a pre-existing (possibly privileged) user to a team the attacker chose, including a team already counted in `Shipit.github_teams`.

### Finding Description
The broken binding: `Membership.user_id` should equal `User.find_by(login: X).id` **only when X == the GitHub identity that actually consented to join `Team#github_id == params.team.id`**, i.e. `team.add_member(member).team_id == the team that GitHub actually invited member.login to`. In this code path that equality is never checked.

Code path:
- `Shipit::WebhooksController#verify_signature` resolves the app via `Shipit.github(organization: repository_owner)` and calls `github_app.verify_webhook_signature(...)`. [1](#0-0) 
- `GitHubApp#verify_webhook_signature` explicitly bypasses verification when the org's `webhook_secret` is blank: `return true unless webhook_secret`. [2](#0-1) 
- Once the (unsigned) payload passes, `MembershipHandler#process` resolves the team purely by attacker-controlled `params.team.id` via `find_or_create_team!` (`Team.find_or_create_by!(github_id: params.team.id)`), and resolves the member purely by attacker-controlled `params.member.login` via `User.find_or_create_by_login!`. [3](#0-2) 
- `User.find_or_create_by_login!` does a `find_or_create_by!(login:)` — if a `User` with that login already exists (e.g., an operator who previously logged in, or a bot account), that existing row is returned unchanged rather than any new/attacker-controlled row being created. [4](#0-3) 
- `Team#add_member` simply appends the resolved `User` to `members` if not already present, with no verification against GitHub. [5](#0-4) 
- Team membership directly feeds authorization: `User#authorized?` checks `teams.where(id: Shipit.github_teams.map(&:id)).exists?`. [6](#0-5) 

Attacker's request: a raw `POST /webhooks` with header `X-Github-Event: membership`, `X-Hub-Signature` arbitrary/absent, and JSON body:
```json
{"action":"added","team":{"id":<github_id of an existing privileged Team>,"name":"x","slug":"x","url":"x"},"organization":{"login":"<org with nil webhook_secret>"},"member":{"login":"<login of existing privileged User>"}}
```
As long as `Shipit.github(organization: repository_owner)` resolves to a `GitHubApp` instance whose `webhook_secret` is blank, `verify_webhook_signature` returns `true` and the forged payload is processed exactly as a legitimate GitHub-originated membership event. None of `drop_unhandled_event`, `check_if_ping`, the `ExplicitParameters` schema, or `require_permission!`-style checks validate that the named `member.login`/`team.id` correspond to a real GitHub action — the schema only enforces types/presence, not provenance.

### Impact Explanation
The attacker can attach an arbitrary pre-existing `Shipit::User` (bot account or a real operator who has ever authenticated to Shipit) to an arbitrary `Team` row identified only by numeric `github_id`, without that user's consent and without GitHub ever performing the corresponding org/team action. If the chosen team's `id` is one enumerated in `Shipit.github_teams`, this directly flips `User#authorized?` to `true` for that account, i.e., unauthorized escalation into `Shipit.github_teams` authorization — matching the "High" impact category ("escalation into `Shipit.github_teams` authorization"). This is repeatable against any org configured without a `webhook_secret`, and against any existing `User`/`Team` pair known to the attacker (logins and numeric team ids are often discoverable via GitHub's public API).

### Likelihood Explanation
Preconditions: (1) at least one organization configured in Shipit without a `webhook_secret` (a real, documented-as-optional configuration state, not a hypothetical), and (2) a target `User` login and a target privileged `Team`'s numeric `github_id` known to the attacker (both are generally discoverable from public GitHub data). Given those, the attacker needs no Shipit session, API token, or GitHub secret — just an HTTP POST to `/webhooks` with a crafted JSON body and a `X-Github-Event: membership` header. This is fully repeatable and requires no interaction from GitHub or the victim account.

### Recommendation
- Do not bypass signature verification when `webhook_secret` is unset; fail closed (reject the webhook) instead of `return true unless webhook_secret` in `GitHubApp#verify_webhook_signature`.
- In `MembershipHandler`, verify that `params.team.organization.login` matches the resolved `repository_owner`/verified org before mutating team membership, and consider re-fetching the true membership state from the GitHub API rather than trusting the payload for identity-linking mutations.

### Proof of Concept
```ruby
# test/models/webhooks/membership_handler_test.rb (conceptual)
test "cannot attach pre-existing privileged user to attacker-chosen team via forged membership webhook" do
  privileged_user = Shipit::User.create!(login: 'known-operator', name: 'Known Operator')
  privileged_team = Shipit::Team.create!(github_id: 4242, organization: 'real-org', slug: 'privileged-team', name: 'Privileged')

  # Simulate GitHubApp with nil webhook_secret for the target org
  Shipit.stubs(:github).returns(Shipit::GitHubApp.new('forged-org', { webhook_secret: nil }))

  payload = {
    'action' => 'added',
    'team' => { 'id' => privileged_team.github_id, 'name' => 'x', 'slug' => 'x', 'url' => 'x' },
    'organization' => { 'login' => 'forged-org' },
    'member' => { 'login' => privileged_user.login }
  }

  assert_no_difference -> { Shipit::User.count } do
    assert_difference -> { Shipit::Membership.count }, 1 do
      Shipit::Webhooks::Handlers::MembershipHandler.new.call(payload)
    end
  end

  # Broken binding assertion: user was linked to a team it never consented to join
  assert privileged_team.members.reload.include?(privileged_user)
  assert privileged_user.reload.authorized? # if privileged_team.id is in Shipit.github_teams
end
```
The assertion `privileged_team.members.include?(privileged_user)` succeeding, produced entirely from attacker-supplied `member.login` and `team.id` with no valid webhook signature, demonstrates the broken binding.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
