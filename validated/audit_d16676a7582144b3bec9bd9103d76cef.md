### Title
`StatusHandler#process` resolves commits by raw SHA with no repository scope, letting a genuine webhook for one repository write `Status` rows onto commits of unrelated stacks — ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits with `Commit.where(sha: params.sha).each` across the entire `commits` table and calls `create_status_from_github!` on every match, with no join or filter tying the lookup to the `repository` named in the webhook payload. Every other comparable handler (`PushHandler`, `CheckSuiteHandler`) restricts its effect to `stacks`, which is derived from `Repository.from_github_repo_name(payload.dig('repository','full_name'))`; `StatusHandler` skips this scoping entirely.

### Finding Description
The binding that should hold is: `authorized_repos_for_this_webhook (1, the repository named in payload['repository']['full_name']) == repos_actually_mutated_by_process`.

Trace:
- `WebhooksController#verify_signature` verifies the HMAC using `Shipit.github(organization: repository_owner)` — this authenticates that the payload came from a legitimate webhook for that *organization*, nothing more. [1](#0-0) 
- `Handler#stacks` is the mechanism other handlers use to scope effects to the repository named in the payload: [2](#0-1) 
- `PushHandler#process` and `CheckSuiteHandler#process` both use `stacks` (or `stack.commits`) to restrict their side effects to the repository the webhook is for: [3](#0-2) [4](#0-3) 
- `StatusHandler#process`, however, never calls `stacks` or reads `payload['repository']`. It queries `Commit` (the global table, spanning every stack/repository tracked by this Shipit instance) purely by `sha`: [5](#0-4) 

`create_status_from_github!` then creates a `Status` scoped to each matched commit's own `stack_id` via the `commit.statuses` association (`replicate_from_github!` runs inside `commit.statuses`, which is `has_many` scoped, so `commit_id`/`stack_id` are implicit — the uniqueness-key framing in the prompt is not itself the amplification vector): [6](#0-5) [7](#0-6) 

The actual root cause is that the *set of commits mutated* is not restricted to the repository whose signature was verified. Git commit SHAs are content-addressed and stable across clones/forks: any two stacks tracked by the same Shipit instance that share history (a fork and its upstream, or two repos bootstrapped from the same template with an identical initial commit) will contain `Commit` rows with identical `sha` but different `stack_id`. An attacker who owns/administers one such repository (and therefore can legitimately trigger a real, correctly-signed GitHub `status` event for that repository — e.g., by pushing a commit to their own fork whose SHA is shared with the upstream history, and having any CI/service they control post a status for it) causes `StatusHandler` to write a `Status` row not only for their own stack's commit but for every other tracked stack's commit sharing that SHA, regardless of organization or webhook secret ownership. No forged signature is required — the request is a genuine, correctly-signed webhook for the attacker's own repository; the vulnerability is that its effect is not confined to that repository.

None of `verify_signature`, `drop_unhandled_event`, or the `ExplicitParameters` schema mitigate this, because they only validate that the request came from a real GitHub event for the named organization/repository — they say nothing about which commits the handler is allowed to touch, and `StatusHandler` is the one handler that ignores the `repository` field entirely.

### Impact Explanation
A single legitimately-signed webhook for repository A can create `Status` rows on commits belonging to stacks in unrelated repositories B, C, … whenever those stacks share a commit SHA with A (fork/upstream pairs, or repos seeded from a common template are common in practice). Created `Status` rows affect deployability signals (`Commit#state`, CI gating) and can trigger downstream side effects — `enable_ci_on_stack`, `schedule_continuous_delivery`, `ProcessMergeRequestsJob` enqueuing — on a stack the attacker never authenticated for. This matches the "a payload for one repository mutating another's stack, commit... " Critical category, since it is an unauthorized cross-tenant write triggered purely by a repository the attacker legitimately controls.

### Likelihood Explanation
Requires: (1) the attacker administers/pushes to at least one GitHub repository tracked as a Shipit stack (unprivileged, self-service condition satisfiable by anyone who can get their repo onboarded, or by contributing a commit whose SHA is shared with a tracked upstream/fork pair), and (2) another Shipit-tracked stack contains a commit with an identical SHA — realistic for fork/upstream pairs or template-seeded repositories, both common Shipit usage patterns. No secrets or privileged roles are required beyond normal GitHub write access to one's own repository, and the attack is trivially repeatable for every shared SHA.

### Recommendation
Scope `StatusHandler#process` to the repository named in the payload, mirroring `PushHandler`/`CheckSuiteHandler`: resolve `stacks` from `Repository.from_github_repo_name(payload.dig('repository','full_name'))` and restrict the commit lookup to `stacks.flat_map(&:commits).where(sha: params.sha)` (or an equivalent `Commit.joins(:stack).merge(stacks).where(sha: params.sha)`), rather than querying the global `Commit` table unscoped.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossRepoTest < ActiveSupport::TestCase
        test "a status webhook for repo A must not create a Status on repo B's commit sharing the same sha" do
          shared_sha = "a" * 40

          stack_a = shipit_stacks(:shipit) # repository "shopify/shipit-engine"
          stack_b = shipit_stacks(:cyclimse) # unrelated repository/org

          commit_a = stack_a.commits.create!(sha: shared_sha, message: "shared", author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now)
          commit_b = stack_b.commits.create!(sha: shared_sha, message: "shared", author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now)

          payload = {
            "sha" => shared_sha,
            "state" => "success",
            "description" => "Build passed",
            "context" => "ci/example",
            "target_url" => "https://ci.example.com/1",
            "created_at" => Time.now.iso8601,
            "repository" => { "full_name" => stack_a.repository.full_name, "owner" => { "login" => stack_a.repository.owner } }
          }

          # authorized_repos_for_this_webhook == 1 (stack_a only)
          assert_equal 1, [stack_a.repository.full_name].size

          assert_no_difference -> { commit_b.reload.statuses.count } do
            StatusHandler.call(payload)
          end

          # Binding check: repos actually mutated must equal 1 (stack_a), not 2
          mutated_stacks = [commit_a, commit_b].select { |c| c.reload.statuses.any? }.map(&:stack_id).uniq
          assert_equal [stack_a.id], mutated_stacks
        end
      end
    end
  end
end
```
This test currently fails against `StatusHandler#process` as written, because `Commit.where(sha: params.sha)` matches `commit_b` in `stack_b` even though the payload's `repository` field names only `stack_a`.
