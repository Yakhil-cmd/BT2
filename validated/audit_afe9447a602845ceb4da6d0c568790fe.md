### Title
Webhook signature verification is scoped to the wrong organization, allowing cross-tenant forgery of commit statuses and repository events - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
In a multi-tenant Shipit deployment (multiple GitHub organizations configured under `secrets.github`), the webhook signature is verified using the `webhook_secret` of the organization named in the payload's `repository.owner.login` (or `organization.login`) field, while the actual data written by the handlers (which `Commit`/`Stack` is mutated) is derived from separate payload fields (`repository.full_name`, or — in the case of `StatusHandler` — nothing at all, just the raw `sha`). An attacker who legitimately controls (and thus knows) the `webhook_secret` for their *own* onboarded organization can therefore forge a signed webhook that is verified against their own org's secret but whose effects land on a completely different organization's stacks/commits.

### Finding Description
`Shipit.github(organization:)` supports per-organization GitHub App configuration, each with its own `webhook_secret` [1](#0-0) , as documented for "Using Multiple Github Applications" [2](#0-1) .

`WebhooksController#verify_signature` selects which org's app/secret to verify against purely from the attacker-controlled JSON body: [3](#0-2) [4](#0-3) 

`GitHubApp#verify_webhook_signature` just HMACs the raw body with that org's configured secret [5](#0-4) . Since the HMAC covers the whole body, an attacker who legitimately knows their *own* org's `webhook_secret` (e.g. they configured the GitHub App webhook delivery for their own onboarded org) can construct **any** payload content and sign it correctly — including a payload whose `repository.owner.login` is their own org (so verification passes) but whose other repository-identifying fields point at a different, unrelated org/stack.

The generic `Handler` base class resolves the target stacks from `repository.full_name`, a field completely independent from the one used for signature-org-selection [6](#0-5) .

Worse, `StatusHandler` doesn't even scope by repository at all — it matches commits globally by `sha` across the entire Shipit database and writes a GitHub status onto them: [7](#0-6) 

This means the binding: `organization authenticated by verify_signature == repository/commit actually mutated by the handler` does not hold. Before the attack: only GitHub, holding the real per-repo webhook secret, can write statuses/push events for a given repo. After the attack: any tenant admin who knows their own org's secret can write forged commit statuses (and push/check-suite events) against commits belonging to *any* other tenant's stack hosted on the same Shipit instance, as long as they know (or guess) the target commit SHA — which is public on GitHub.

### Impact Explanation
Commit statuses gate `ci.require` checks in `shipit.yml`, which control whether a deploy is permitted. A forged "success" status injected via `StatusHandler` on a target org's commit can satisfy CI requirements and enable an **unauthorized deploy** on a stack the attacker has no legitimate access to — a cross-repository/cross-tenant write with deploy authorization impact. `PushHandler` and `CheckSuiteHandler` are similarly reachable across repositories because the "org that signed" and "repository that is written" are decoupled, though those are at least scoped by `repository.full_name`; `StatusHandler` has no repository scoping whatsoever, making it the most direct path to impact.

### Likelihood Explanation
Requires only that Shipit is configured for multiple GitHub organizations (a documented, supported configuration) and that the attacker has legitimate control over the webhook secret of at least one onboarded org (which is the normal level of access any onboarded tenant/org owner has, since they configure their own App's webhook delivery). No token, GitHub App private key, or repository write access to the *victim* org is needed — only knowledge of the target commit's SHA, which is public.

### Recommendation
Bind signature verification to the same repository identity used by the handlers: verify the webhook using the organization/App derived from `repository.full_name` (or an authoritative, pre-registered mapping of repo → GitHub App/secret) rather than the attacker-suppliable `repository.owner.login`/`organization.login`. Additionally, `StatusHandler` should scope `Commit` lookups by the repository resolved from the verified webhook context (`stacks`) rather than a global `sha` match across all stacks.

### Proof of Concept
1. Shipit is configured with two orgs, `OrgOne` and `OrgTwo`, each with its own `webhook_secret` (per `docs/setup.md` multi-org setup).
2. Attacker legitimately administers `OrgOne`'s GitHub App webhook config and thus knows `OrgOne`'s `webhook_secret`.
3. Attacker crafts a `status` event body:
```json
{
  "sha": "<victim-commit-sha-in-OrgTwo-repo>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "OrgOne" }, "full_name": "OrgOne/irrelevant-repo" }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(OrgOne_secret, body)` and POSTs to `/webhooks`.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgOne"`, fetches `Shipit.github(organization: "OrgOne")`, and the signature validates successfully [3](#0-2) .
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)` globally and writes a "success" status onto the victim commit belonging to `OrgTwo`'s stack [7](#0-6) , potentially satisfying that stack's `ci.require` gate and enabling an unauthorized deploy.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
