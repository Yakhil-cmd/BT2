### Title
Cross-organization status/webhook forgery via signature-organization mismatch enables unauthorized deploys - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
In a multi-tenant Shipit deployment (multiple GitHub organizations configured under `github:` in secrets, as documented in `docs/setup.md`), the webhook controller selects *which* organization's `webhook_secret` to verify a signature against using one payload field (`repository.owner.login` / `organization.login`), while the handlers that actually mutate state act on a completely different, unrelated scope: `StatusHandler` matches `Commit.where(sha: params.sha)` with no repository/organization scoping at all. An admin of Organization A's GitHub App — who legitimately possesses OrgA's `webhook_secret` — can forge a signed `status` webhook whose signature is verified against OrgA's secret but whose `sha` matches a commit belonging to Organization B's stack, causing a forged `success` status to be applied to OrgB's commit. If OrgB's stack has continuous deployment enabled, this directly triggers an unauthorized deploy of OrgB's stack.

### Finding Description
`WebhooksController#verify_signature` picks the `GitHubApp` (and therefore the `webhook_secret` used for HMAC verification) from the payload field `repository.owner.login` (falling back to `organization.login`): [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` resolves to a distinct `GitHubApp` instance per organization, each with its own independently-configured `webhook_secret`, as documented for multi-org setups: [3](#0-2) 

Once the signature check passes (using OrgA's secret, because `repository.owner.login == "OrgA"` in the forged payload), the *entire raw request body* — including any other fields — is treated as trusted, and dispatched to the registered handlers: [4](#0-3) 

For the `status` event, `StatusHandler#process` does not scope its side effect to any repository, organization, or stack at all — it looks up `Commit` records purely by `sha` across the **entire** Shipit instance, and applies the attacker-supplied `state`/`description`/`context` to any matching commit: [5](#0-4) 

This breaks the equality that should hold: `organization authenticated by verify_signature == organization/repository whose data is written by the handler`. Instead, the authenticated organization is OrgA (whose secret matched), but the entity written is any commit in the datastore with a matching sha — regardless of which organization or repository it belongs to.

`Commit#create_status_from_github!` (invoked by `StatusHandler`) creates a `Status` record, which schedules continuous delivery if the stack has continuous deployment enabled: [6](#0-5) 

This is confirmed by existing tests showing that a `success` status on a commit, when `continuous_deployment: true`, creates a `Deploy` and enqueues `ContinuousDeliveryJob`: [7](#0-6) 

### Impact Explanation
An attacker who is an administrator of one tenant organization's GitHub App (OrgA) on a shared Shipit instance — with zero privileges on a different tenant's stack (OrgB) — can forge a `status` webhook signed with OrgA's `webhook_secret` that targets a commit sha belonging to OrgB. If OrgB's stack has `continuous_deployment` enabled (a common configuration), this forged `success` status directly causes `trigger_continuous_delivery` to build and run a `Deploy` for OrgB — an unauthorized deploy triggered without any legitimate CI signal or credential belonging to OrgB. This matches the Critical impact category "an unauthorized deploy" and constitutes a cross-organization/cross-repository write, since the boundary the code should enforce (organization that authenticated == repository/stack acted upon) is not checked anywhere in `StatusHandler` or the base `Handler#stacks`/`repository_name` helper (which other handlers use, but `StatusHandler` bypasses entirely).

### Likelihood Explanation
Likelihood is Medium: it requires (1) the target Shipit instance to be configured for multiple GitHub organizations (an explicitly documented and supported feature), (2) the attacker to control/administer at least one tenant org's GitHub App (thus legitimately knowing its `webhook_secret`), and (3) the attacker to know or guess a commit sha belonging to the victim organization's tracked stack (commit shas are often publicly visible on GitHub for public repos, or discoverable via the Shipit UI). No `ApiClient` token, `GITHUB_TOKEN`, or Shipit session is required — only the ability to POST to the public `/github/webhooks` endpoint with a validly-signed payload for one's own tenant.

### Recommendation
`StatusHandler` (and any other handler relying on shared, un-scoped lookups) must verify that the commit/stack it is about to mutate actually belongs to the same repository/organization that was authenticated in `verify_signature`. Concretely:
- Scope `StatusHandler#process` to commits whose `stack.repository` matches `payload.dig('repository', 'full_name')`, consistent with how other handlers use `Handler#stacks`/`repository_name`.
- In `WebhooksController`, after selecting the `GitHubApp` via `repository_owner`, re-verify that `repository.owner.login` (or `organization.login`) actually matches the owner encoded in `repository.full_name`, rejecting the webhook if they diverge.
- More generally, ensure every handler enforces "the organization whose secret verified this payload" as an intrinsic scoping constraint for any database write, rather than trusting unscoped fields (like bare `sha`) taken from the request body.

### Proof of Concept
1. Shipit is configured with two tenant organizations, `OrgA` and `OrgB`, each with its own GitHub App and `webhook_secret` (per `docs/setup.md` "Using Multiple Github Applications").
2. `OrgB` has a stack with `continuous_deployment: true` and a pending commit with sha `abcd1234...` known to the attacker (e.g., visible on GitHub or via Shipit's UI/API for that stack).
3. Attacker, who administers `OrgA`'s GitHub App and therefore knows `OrgA`'s `webhook_secret`, crafts:
   ```json
   {
     "sha": "abcd1234...",
     "state": "success",
     "context": "attacker/forged",
     "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgA/some-other-repo" }
   }
   ```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, raw_body)>` and POSTs to `/github/webhooks` with `X-Github-Event: status`.
5. `WebhooksController#verify_signature` resolves `repository_owner` to `"OrgA"`, fetches OrgA's `GitHubApp`, and the signature verifies successfully.
6. `StatusHandler#process` runs `Commit.where(sha: "abcd1234...")`, finds OrgB's commit (unrelated to OrgA), and calls `create_status_from_github!`, creating a `success` `Status`.
7. Because OrgB's stack has continuous deployment enabled, `Status#schedule_continuous_delivery` → `ContinuousDeliveryJob` → `Stack#trigger_continuous_delivery` fires, creating and running an unauthorized `Deploy` on OrgB's stack — entirely triggered by an attacker with no legitimate access to OrgB.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
