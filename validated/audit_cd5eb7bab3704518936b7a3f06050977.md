### Title
AA balance overflow check bounces trigger *after* balance already committed to `aa_balances`, permanently corrupting the AA's tracked balance and blocking future deposits - (File: aa_composer.js)

### Summary
This is the same bug class as the f(x) `PoolManager` report: a hard capacity/limit check (`MAX_BALANCE`, analogous to the pool's capacity) is evaluated *after* the credit has already been applied to the tracked quantity, so the limit can be breached by legitimate, unprivileged activity (any user paying an AA), and once breached the AA is effectively unable to process further deposits of that asset.

### Finding Description
`updateInitialAABalances()` in `handleTrigger` adds the coins received in the trigger to the AA's cached balance before checking whether the result overflows `MAX_BALANCE`: [1](#0-0) 
For the real (non-`bAir`) path, the `UPDATE aa_balances SET balance=balance+?` query is queued into `arrQueries` and executed via `async.series(arrQueries, ...)` *before* the overflow flag is inspected: [2](#0-1) 
Only after these queries have run does the code call back with `bOverflow ? "balance overflow" : null`, which propagates to `bounce(err)`: [3](#0-2) 

`bounce()` only restores balances for the `bAir` (dry-run) simulation path; for a real trigger it does **not** roll back the `aa_balances` row that was just incremented: [4](#0-3) 
`bounce()` then only manages to return funds to the sender if the trigger's `base` output covers `bounce_fees.base` and each individual asset amount covers its own bounce fee; otherwise it silently keeps the coins with `finish(null)` and issues no response: [5](#0-4) 

This mirrors the reported pattern precisely: a hard cap (`MAX_BALANCE` here, pool `capacity` there) is checked against a sum that already includes the "extra" contribution (bonus-from-reserve there, trigger-received coins here) rather than being checked before the addition, so the operation that would put the tracked quantity over the cap fails/bounces, yet the side effect (crediting the DB balance / adding reserve funds) already happened or the received coins are consumed without a corresponding balance decrement.

### Impact Explanation
- Once an asset's tracked balance for an AA is at or near `MAX_BALANCE`, any further posted payment of that asset to the AA (something *any* unprivileged unit poster can trigger simply by sending a payment to the AA) will overflow the check and force a bounce.
- On bounce, the received coins are not necessarily returned to the sender: if the specific asset's received amount doesn't exceed its `bounce_fees` entry (assets other than `base` have no bounce-fee requirement enforced up front), the loop `for (var asset in trigger.outputs) ... if (fee === amount) continue;` skips creating a refund message for that asset entirely, meaning the sender's asset payment is consumed by the AA (added to its UTXO set) with no compensating message and, worse, the row previously written in `aa_balances` already reflects the overflowed value.
- This can permanently and irreversibly disable the AA from accepting further deposits of the affected asset (denial of service / freezing of funds for the AA and its users), and can also desynchronize the cached `aa_balances` figure used by AA formulas (`balance[asset]`) from the AA's actual spendable coin set, since state changes are discarded on bounce but the balance UPDATE already executed outside of the formula-evaluation rollback path.

### Likelihood Explanation
Reaching `MAX_BALANCE` requires accumulating a very large balance in a single asset for a single AA address, which is possible for high-cap/high-volume assets or for `base` bytes given enough legitimate/attacker-funded deposits over time; it does not require any privileged role - any address can post a payment message targeting the AA. The condition is comparable in "low likelihood, edge case" character to the reported f(x) issue, but is reachable purely through normal unprivileged usage (sending payments/triggers), matching the required threat model of an unprivileged unit poster.

### Recommendation
Perform the `MAX_BALANCE` (and any other balance-cap) check *before* committing the `UPDATE aa_balances` query, or make the check advisory-and-atomic: compute the prospective new balance, verify it does not exceed `MAX_BALANCE`, and only then queue the SQL update; if it would overflow, bounce (or reject) before any DB write occurs. Additionally, ensure `bounce()` always returns all received asset amounts to the sender (or otherwise reverts any balance mutation) rather than silently absorbing them when the corresponding bounce fee isn't met, so a capacity violation can never result in coins being retained by the AA without a matching accounting update.

2. Post successive payment triggers of a given asset (or `base`) to the AA's address until `trigger_opts.assocBalances[address][asset]` (real-path: `aa_balances.balance`) approaches `MAX_BALANCE`.
3. Post one more trigger whose asset output amount does not exceed `bounce_fees[asset]` (for non-base assets there's no required minimum), pushing the cached balance over `MAX_BALANCE`.
