### Title
Webhook signature verification is keyed to `repository.owner.login`/`organization.login`, but handlers act on the unverified `repository.full_name` field, allowing cross-organization webhook forgery when any configured GitHub App lacks a `webhook_secret` - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App config (and therefore which `webhook_secret`) to validate the incoming signature against based on `repository_owner`, a value read directly from the untrusted JSON body. The handler that subsequently processes the same body does not re-derive or re-check that binding — it resolves the target `Repository`/`Stack` purely from `repository.full_name`, a separate field in the same unverified payload.

### Finding Description
`verify_signature` picks the GitHub App used for HMAC verification from the payload itself: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` unconditionally trusts the request if the selected app has no `webhook_secret` configured: [3](#0-2) 

Shipit supports multiple GitHub Apps, one per organization, configured independently, each with its own optional `webhook_secret`: [4](#0-3) 

After signature verification passes (or is trivially skipped), the actual event handler resolves which `Repository`/`Stack` to mutate using a *different* field of the same JSON body — `repository.full_name` — with no cross-check against the organization that was used to select the webhook secret: [5](#0-4) [6](#0-5) 

The equality the code implicitly assumes is:
`organization authenticated by signature (repository_owner) == organization that owns the repository actually written (repository.full_name)`

This holds only as long as every configured organization's `webhook_secret` is set and only that organization can produce a validly-signed payload naming its own repositories. If any org in a multi-org deployment is configured without a `webhook_secret` (a supported, documented configuration — see `docs/setup.md` and `config/secrets.development.example.yml`), the binding breaks: an unprivileged, unauthenticated attacker can POST a forged JSON body to `/webhooks` with `repository.owner.login` (or `organization.login`) set to the org lacking a secret, while setting `repository.full_name` to any repository/stack tracked under a *different*, fully-secured organization. `verify_signature` passes trivially (`return true unless webhook_secret`), and the handler (e.g. `PushHandler`, `StatusHandler`, `CheckSuiteHandler`) then acts on the attacker-chosen `full_name`, e.g. triggering `stack.sync_github(expected_head_sha: params.after)` for a target stack the attacker never had access to.

### Impact Explanation
This crosses a repository/authentication boundary: an attacker with no Shipit session, no `ApiClient` token, and no knowledge of the target organization's `webhook_secret` can inject GitHub events (push/status/check_suite/membership, etc.) for stacks belonging to organizations they have no relationship with, as long as any other configured org lacks a webhook secret. Depending on which handler is triggered, this can force spurious syncs, statuses, or check-run refreshes on unrelated stacks (a cross-repository write), matching the "organization authenticated versus the repository that is written" pattern called out in scope.

### Likelihood Explanation
Requires a multi-org Shipit deployment where at least one configured GitHub App has no `webhook_secret` set — a state the codebase and documentation explicitly allow and even ship example configs for (`config/secrets.development.example.yml`, `test/dummy/config/secrets_double_github_app.yml`). No credentials, sessions, or repository access are needed to exploit it once that precondition holds.

### Recommendation
After selecting the app/organization for signature verification, re-validate that `repository.owner.login` (used for signature selection) matches the organization owning the `repository.full_name` that handlers subsequently act upon, or require `webhook_secret` to be mandatory for every configured organization so an unsigned/uncovered org cannot be used as a bypass vector for forging events about repositories belonging to other organizations.

### Proof of Concept
1. Deploy Shipit with two orgs configured as in `test/dummy/config/secrets_double_github_app.yml`: `OrgOne` (has `webhook_secret` set) and `OrgTwo` (leave `webhook_secret` blank/nil).
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: push` and a JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef",
  "repository": { "full_name": "OrgOne/some-secured-repo", "owner": { "login": "OrgTwo" } }
}
```
3. `verify_signature` calls `Shipit.github(organization: 'OrgTwo')`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally (`app/controllers/shipit/webhooks_controller.rb:24-30`, `lib/shipit/github_app.rb:76-83`) regardless of the (missing/garbage) `X-Hub-Signature` header.
4. `PushHandler#process` resolves the target via `Repository.from_github_repo_name('OrgOne/some-secured-repo')` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) and enqueues `stack.sync_github` for a stack under `OrgOne`, an organization whose webhook secret the attacker never had.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
