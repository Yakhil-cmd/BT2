### Title
Cross-organization commit-status forgery bypasses CI gating and enables unauthorized deploys - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates an inbound GitHub webhook against the `GitHubApp` (and its `webhook_secret`) selected by `repository_owner`, a value read directly out of the attacker-supplied JSON body (`repository.owner.login`) [1](#0-0) . Signature verification therefore only proves that the sender knows the webhook secret belonging to that one organization [2](#0-1) . However, once the signature is accepted, the full unvalidated JSON `params` are dispatched to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [3](#0-2) , and `StatusHandler#process` looks up the target record with **no repository/organization scoping at all**:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [4](#0-3) 

This breaks the binding **"organization that authenticated == repository whose data is written."** Every other handler resolves the target via `payload.dig('repository', 'full_name')` through `Handler#stacks`/`#repository_name` [5](#0-4) , but `StatusHandler` is the outlier: it matches purely on a global `sha` column that is shared across every `Stack`/`Repository` hosted by the same Shipit instance.

### Finding Description
In a multi-org Shipit deployment (explicitly supported and documented via `config/secrets.yml`'s per-organization `github:` sections, e.g. `test/dummy/config/secrets_double_github_app.yml`) [6](#0-5) , each organization has its own GitHub App / `webhook_secret`. `Shipit.github(organization: repository_owner)` picks the app whose secret is used purely based on the attacker-controlled `repository.owner.login` field of the payload [1](#0-0) .

An attacker who legitimately controls organization **OrgA** (and thus knows OrgA's `webhook_secret`) can send a `status` event correctly signed for OrgA, but set `sha` to the SHA of a commit that actually belongs to a Stack under a completely different, unrelated organization **OrgB** hosted on the same Shipit instance. Because `StatusHandler#process` filters only `Commit.where(sha: params.sha)` with no repository check, the forged, cross-org-signed payload creates/overwrites a commit status on OrgB's commit.

Commit statuses directly drive Shipit's deploy gating logic: `Commit#deployable?` is `!locked? && (stack.ignore_ci? || (success? && !blocked?))`, and `success?`/`state` are computed from the object's `statuses` [7](#0-6) . By injecting a fabricated `success` status for a required CI context on an OrgB commit, an attacker with only OrgA-level credentials can flip an OrgB commit to `deployable?`, and it can then be shipped via the normal deploy API/flow (`stack.trigger_deploy`) [8](#0-7) , or unblock merge queues via `Stack#allows_merges?`/blocking-status logic that also derives from the same globally-writable `statuses` table [9](#0-8) .

### Impact Explanation
This is a real authentication-scope-crossing bug: the webhook signature check authenticates "this request was signed by OrgA," while the actual write ("set the CI status of this commit") is applied to a resource (a commit belonging to an arbitrary Stack/Repository owned by any other org configured on the same instance) that was never covered by that authentication. Forging a required-status "success" to make a commit `deployable?` directly enables an **unauthorized deploy** of a commit that never actually passed CI/required checks in its own org — matching the High-impact class "escalation ... unauthorized deploy" in this engine's threat model. It also risks unblocking merge queues cross-tenant.

### Likelihood Explanation
Exploitation requires only that the attacker legitimately control (or have compromised) one organization/repository already onboarded to the same shared Shipit instance — no privileged Shipit account, `ApiClient` token, or `webhook_secret` for the *victim* org is required, since the attacker signs with their own org's secret. Any Shipit deployment serving more than one GitHub organization (a documented, supported configuration) is exposed. The only variable is knowing/guessing a target `sha` of a commit tracked by another stack, which is often discoverable (e.g. public repos, CI logs, PR pages).

### Recommendation
Scope `StatusHandler#process` (and any other handler resolving records purely by attacker-controlled cross-cutting keys like `sha`) to the repository actually authenticated for the request. Concretely, resolve the target `Stack`/`Repository` from `payload.dig('repository', 'full_name')` (as `Handler#stacks` already does) and restrict `Commit.where(sha: params.sha)` to `stacks.commits` for that repository, rejecting or ignoring commits that don't belong to the org/repo the signature was verified against.

### Proof of Concept
1. Attacker registers/owns GitHub org `OrgA` which is configured in this Shipit instance's `config/secrets.yml` (with its own `webhook_secret`), alongside unrelated victim org `OrgB` also hosted on the same instance.
2. Attacker discovers a `sha` belonging to a commit tracked under an `OrgB` `Stack` (e.g. from a public repository or PR page) that requires a CI context such as `ci/required`.
3. Attacker crafts a GitHub `status` webhook JSON body:
   ```json
   {
     "sha": "<OrgB commit sha>",
     "state": "success",
     "context": "ci/required",
     "repository": { "owner": { "login": "OrgA" } }
   }
   ```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(OrgA_webhook_secret, body)` — this is valid because they know `OrgA`'s secret.
5. `WebhooksController#verify_signature` selects `Shipit.github(organization: "OrgA")` (from the payload's `repository.owner.login`), verifies successfully, and the request proceeds [1](#0-0) .
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the OrgB commit purely by `sha` (no org/repo check), and calls `create_status_from_github!`, marking it `success` [4](#0-3) .
7. The OrgB commit is now `deployable?` (or unblocks its stack's merge queue) despite never having been authorized by anyone with `OrgB`'s credentials [10](#0-9) .
