### Title
Cross-organization Team/Membership forgery via `organization`/`repository.owner` divergence in `membership` webhooks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the signing organization using `params.dig('repository','owner','login') || params.dig('organization','login')`, while `MembershipHandler#find_or_create_team!` scopes the created `Team` using `params.organization.login` independently. An attacker who legitimately controls one configured GitHub organization (org A) can forge a webhook body containing a `repository.owner.login` of `orgA` (so the signature check passes with a secret they know) but an `organization.login` of `orgB`, causing Shipit to create/mutate `Team`/`Membership` rows attributed to `orgB` without ever proving control of `orgB`.

### Finding Description
The binding that should hold is:
`organization_verified_by_signature (repository_owner) == organization_scoping_the_written_Team (params.organization.login)`

Tracing the code:
- `repository_owner` in `app/controllers/shipit/webhooks_controller.rb` is computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0) , and `verify_signature` uses this value to pick which org's `webhook_secret` verifies the HMAC: `github_app = Shipit.github(organization: repository_owner)` [2](#0-1) .
- `MembershipHandler#find_or_create_team!`, however, reads a completely separate field, `params.organization.login`, to set `team.organization` on the created/found `Team` record: `Team.find_or_create_by!(github_id: params.team.id) { |team| team.github_team = params.team; team.organization = params.organization.login }` [3](#0-2) , then adds/removes the attacker-controlled `member.login` from that team [4](#0-3) .
- Nothing in `verify_signature`, `drop_unhandled_event`, or the `ExplicitParameters` schema in `MembershipHandler` cross-checks that `repository.owner.login` (used for the signature) equals `organization.login` (used to scope the write). The existing test suite always sets both to the same value (`'shopify'`), so this divergence is untested: `membership_params` merges `organization: { login: 'shopify' }` with `repository_params` = `{ repository: { owner: { login: 'shopify' } } }` [5](#0-4) .

Exploit flow, assuming a legitimately multi-org-configured Shipit instance where the attacker administers org A (knows org A's `webhook_secret`, as is standard for org-scoped webhook secrets) but is not a member of `Shipit.github_teams` and does not control org B:
1. Attacker crafts a raw JSON body for a `membership` event:
   ```json
   {
     "action": "added",
     "team": {"id": 999999, "name": "fake", "slug": "developers", "url": "https://example.com"},
     "organization": {"login": "orgB"},
     "member": {"login": "attacker"},
     "repository": {"owner": {"login": "orgA"}}
   }
   ```
2. Attacker computes `sha1=HMAC(orgA_webhook_secret, body)` and POSTs directly to `/webhooks` with `X-Github-Event: membership` and that signature.
3. `verify_signature` resolves `repository_owner` to `"orgA"` (because `repository.owner.login` is present and takes priority), looks up org A's `GitHubApp`, and the signature verifies successfully because the attacker legitimately knows org A's secret.
4. `MembershipHandler.process` runs unaware of which org actually authenticated the request; it creates a new `Team` row with `organization: "orgB"`, `slug: "developers"` (matching an org-B team handle that may be referenced by `Shipit.github_teams` config, i.e. `oauth_teams` containing `"orgB/developers"`), and immediately adds the attacker as a member via `team.add_member(member)`.
5. If the legitimate org-B `developers` team has not yet been synced into Shipit's DB, `Shipit.github_teams` (computed via `Team.find_or_create_by_handle`, which does `find_by(organization:, slug:)`, not by `github_id`) will resolve to the attacker's forged row the first time it is evaluated [6](#0-5) [7](#0-6) . Because the attacker is already a member of that forged team, `User#authorized?` (`teams.where(id: Shipit.github_teams.map(&:id)).exists?`) [8](#0-7)  returns `true` for the attacker's own Shipit user — granting authorization for org B without ever being vetted by org B's GitHub org or webhook secret.

Even absent that race, the minimal guaranteed impact is that an attacker who controls only org A can create/manipulate `Team` and `Membership` rows labeled as belonging to org B, entirely under attacker-chosen `team.id`/`slug`/`name` and `member.login`, which no part of the existing code path (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema) prevents, since none of them tie the verified organization to the organization value used for the database write.

### Impact Explanation
The attack lets a party that owns/administers one configured GitHub organization write `Team`/`Membership` records attributed to a different organization they do not control, with attacker-chosen team ids, slugs and member logins. When the targeted org-B team handle coincides with an entry in `Shipit.github_teams` (the `oauth_teams` allow-list used for authorization), this becomes an authorization-escalation path: the attacker's own Shipit account (or any account they name) can be granted membership in the team that gates `User#authorized?`, bypassing the intended requirement of real GitHub org/team membership in org B. This matches the "High – escalation into `Shipit.github_teams` authorization" category. It is repeatable against any org-B team handle referenced in Shipit's configuration and requires no compromise of org B's secrets.

### Likelihood Explanation
Preconditions: a multi-org `github:` configuration (more than one organization section, each with its own `webhook_secret`), and the attacker legitimately controlling at least one configured organization (org A) — a scenario explicitly enabled by Shipit's multi-tenant webhook design. The attacker needs no privileged Shipit role, no session, and no knowledge of org B's secret — only knowledge of org A's own secret, which they possess as its administrator. Crafting and POSTing an arbitrary JSON body with mismatched `repository.owner.login` / `organization.login` fields is trivial and fully repeatable.

### Recommendation
In `MembershipHandler` (and any other org-scoped webhook handler), derive the organization used to scope writes from the same value verified by `WebhooksController#verify_signature` (i.e., pass/compare `repository_owner` into the handler) rather than trusting `params.organization.login` independently. Reject the webhook (or refuse to update/create records) if `params.organization.login` does not match the organization whose secret verified the request.

### Proof of Concept
Minitest plan (in `test/controllers/webhooks_controller_test.rb`, using a dummy multi-org secrets fixture like `test/dummy/config/secrets_double_github_app.yml` which already configures two organizations with distinct `webhook_secret`s):

```ruby
test ":membership signed by org A but claiming org B does not write org B's Team" do
  # Two orgs configured: 'org-a' (attacker controls, secret known) and 'org-b' (victim org)
  body = {
    action: 'added',
    team: { id: 555, name: 'Fake', slug: 'developers', url: 'https://example.com' },
    organization: { login: 'org-b' },          # target org (write side)
    member: { login: 'attacker' },
    repository: { owner: { login: 'org-a' } }  # org whose secret signs the request (auth side)
  }.to_json

  signature = "sha1=#{OpenSSL::HMAC.hexdigest('sha1', ORG_A_WEBHOOK_SECRET, body)}"

  @request.headers['X-Github-Event'] = 'membership'
  @request.headers['X-Hub-Signature'] = signature

  # Equality under test: organization verified by signature ('org-a')
  # must equal organization used to scope the Team write ('org-b's payload claims)
  assert_no_difference -> { Team.where(organization: 'org-b').count } do
    post :create, body:, as: :json
  end

  assert_response :ok # currently passes verify_signature because repository_owner == 'org-a'
  refute Team.exists?(organization: 'org-b', slug: 'developers'),
    "Team scoped to org-b was created/modified by a request only signed by org-a's secret"
end
```
This asserts that a request whose signature is verified against org A's secret must not be able to create or modify a `Team`/`Membership` scoped to org B; under the current implementation this assertion fails, demonstrating the vulnerability.
