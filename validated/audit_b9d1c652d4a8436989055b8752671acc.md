### Title
Webhook organization used for signature verification is decoupled from the repository the payload actually targets - cross-organization writes in multi-org deployments (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to check the HMAC signature against using the *unverified* JSON body field `repository.owner.login` (or `organization.login`). Once the signature check passes, the entire raw payload (including a separately-read `repository.full_name` field) is handed to the event handlers, which use `repository.full_name` to look up the target `Repository`/`Stack` and perform writes. Nothing ties the field used to choose the verification secret to the field used to choose the affected repository, so in a multi-organization Shipit deployment, whoever controls one organization's webhook secret can forge a payload that authenticates as their own org but writes to a stack belonging to a different organization.

### Finding Description
In a multi-tenant Shipit instance, `Shipit.github(organization:)` maps an organization name to its own `GitHubApp` config (`app_id`, `webhook_secret`, etc.), keyed by the org name in `secrets.github`. [1](#0-0) 

`WebhooksController#verify_signature` derives the organization purely from the attacker-supplied payload and validates the HMAC signature against *that organization's* secret: [2](#0-1) [3](#0-2) 

After the signature is accepted, `#create` dispatches the raw, parsed params to handlers unchanged: [4](#0-3) 

Every `Handler` subclass resolves the target `Stack`s using a *different* field of the same payload, `repository.full_name`, via `Repository.from_github_repo_name`: [5](#0-4) [6](#0-5) 

`repository_owner` (used for verification) and `repository.full_name` (used for the actual write) are two independent, attacker-controlled strings in the same forged request body — nothing links them. The equality the code implicitly assumes is:

`organization whose secret authenticated the request == owner segment of the repository actually written to`

This equality is never enforced. An attacker who legitimately controls the webhook secret for org `A` (e.g. because they administer their own GitHub organization/App that is also onboarded to this same shared Shipit instance) can:
1. Set `repository.owner.login` (or `organization.login`) = `"A"` so `verify_signature` selects org A's `webhook_secret`.
2. Set `repository.full_name` = `"B/some-repo"` for a stack belonging to org `B`.
3. Sign the raw body with org A's known secret — `verify_webhook_signature` succeeds because it only checks the byte-for-byte HMAC of whatever body was sent, using org A's secret.
4. The handler (e.g. `PushHandler`) resolves the stack via `repository.full_name` = `"B/some-repo"` and acts on org B's stack, e.g. enqueuing `stack.sync_github` for org B's stacks: [7](#0-6) 

This mirrors the BakerFi analog exactly: the value that is cryptographically bound/verified (the organization/secret) is not the same value that is actually acted upon (the repository/owner written), just as `_deploy()`/`_undeploy()` returned share amounts while the vault's accounting assumed asset amounts.

### Impact Explanation
This allows cross-organization writes: a party who legitimately controls one org's webhook secret in a shared/multi-tenant Shipit deployment can trigger `GithubSyncJob`s, commit status updates, membership/team changes, merge-status changes, or pull-request-driven review-stack provisioning against a *different* organization's repository/stack, without any credentials for that second organization. This falls under the "cross-repository writes" Critical impact category, since it lets an outside org forge writes into another org's deploy pipeline state (sync commits, statuses, PR-derived merge behavior, team/membership records) despite never being authorized for that org.

### Likelihood Explanation
Requires: (a) the Shipit instance is configured for multiple GitHub organizations (`secrets.github` keyed by org, i.e. `github_default_organization` is non-nil), and (b) the attacker legitimately possesses one organization's `webhook_secret` (which is intentionally distributed to that org's GitHub App/webhook config — not a Shipit-internal secret). Given that, forging the request is trivial (just crafting JSON + HMAC over it, no other privilege needed). Likelihood is Medium: it is fully unprivileged with respect to the *victim* organization, but conditioned on the "multi-org" deployment topology, which the engine explicitly supports (`github_organizations`, `github_app_config`).

### Recommendation
Bind the field used for signature-secret selection to the field used for locating the target repository/stack. Concretely, in `WebhooksController#verify_signature` (or in `Handler#stacks`), reject the payload if `repository.owner.login`/`organization.login` does not match the owner segment of `repository.full_name`, or better: derive the organization used to pick the webhook secret from the *same* `full_name` field the handlers use, so there is a single unambiguous binding between "who authenticated" and "which repository is written."

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.github`: `A` (attacker-controlled, webhook secret known to attacker) and `B` (victim, unrelated secret), both onboarded to the same Shipit instance.
2. Attacker crafts a `push` event JSON body:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "deadbeef",
     "repository": {
       "owner": { "login": "A" },
       "full_name": "B/victim-repo"
     }
   }
   ```
3. Attacker computes `sha1=HMAC(webhook_secret_of_A, body)` and sends it as `X-Hub-Signature`, with header `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `repository_owner` → `"A"`, fetches `Shipit.github(organization: "A")`, and successfully verifies the signature against `A`'s secret. [8](#0-7) 
5. `Shipit::Webhooks.for_event('push')` handlers run with the full params; `PushHandler#stacks` resolves `Repository.from_github_repo_name("B/victim-repo")` and enqueues `sync_github` for org `B`'s stack, without the attacker ever holding org `B`'s webhook secret or any credential for org `B`. [5](#0-4) [7](#0-6) 

Note: I could not fully trace every downstream handler (e.g., `membership_handler.rb`, `status_handler.rb`) to enumerate every possible write side effect within the tool-call budget available; the `PushHandler` case above is sufficient to demonstrate the cross-organization write, but a fuller audit of all handlers listed in `Hook::EVENTS`/`Shipit::Webhooks::DEFAULT_HANDLERS` would be needed to catalog the complete blast radius.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
