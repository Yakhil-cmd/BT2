### Title
`StatusHandler#process` matches commits by SHA across all repositories/stacks, mutating tenants outside the webhook's own repository - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with no scoping to the repository named in the webhook payload. Unlike `PushHandler` and `CheckSuiteHandler`, which both use the `Handler#stacks` helper (scoped via `Repository.from_github_repo_name(repository_name)`) before touching commits, `StatusHandler` queries the global `commits` table by `sha` alone, so any `Commit` row in any `Stack`/`Repository` sharing that SHA gets a `Status` written.

### Finding Description
The claimed binding is: `distinct_repositories_touched_by(webhook) == 1` (the repository named in `payload['repository']['full_name']`). Tracing the code:

- `Handler#initialize` parses `payload` into `params` via `ExplicitParameters`, and separately exposes `repository_name` / `stacks` derived from `payload.dig('repository', 'full_name')` [1](#0-0) .
- `CheckSuiteHandler` and `PushHandler` correctly restrict their DB operations to `stacks` (i.e., the repository in the payload) before acting on commits [2](#0-1) [3](#0-2) .
- `StatusHandler#process`, however, never calls `stacks` or filters by `repository_name`; it queries `Commit.where(sha: params.sha)` directly on the unscoped model and iterates every match, calling `commit.create_status_from_github!(params)` on each [4](#0-3) .
- The database only enforces uniqueness of `sha` combined with `stack_id`, not `sha` alone: `add_index :commits, %i(sha stack_id), unique: true` [5](#0-4) . This means the same commit SHA can legitimately exist as separate `Commit` rows under multiple distinct `Stack`/`Repository` records simultaneously — e.g., an upstream repo and any fork tracked as a separate Shipit stack share identical commit history and thus identical SHA-1 hashes for shared commits.
- `verify_signature` / `GitHubApp#verify_webhook_signature` authenticate that the payload came from *some* registered GitHub organization/app installation, but they do not constrain which `Commit` rows the handler is allowed to mutate once inside `process`; that authorization gap is `StatusHandler`'s own responsibility, and it is absent.

Attack: An attacker who owns or forks a public repository that Shipit also tracks as another tenant's stack (a common real-world topology: upstream + fork, or a monorepo mirrored to multiple deploy targets) pushes commits, then triggers (or waits for GitHub to deliver, or crafts) a `status` webhook naming their own repository with a `sha` that also exists as a `Commit` row in another tenant's `Stack`. Because `StatusHandler` never checks that the returned `Commit` rows belong to a stack whose repository matches the payload's `repository.full_name`, `create_status_from_github!` fires for every matching commit across all such stacks, writing a `Status` and triggering `commit_status`/`deployable_status` hooks and `ProcessMergeRequestsJob` for repositories the attacker does not own [6](#0-5) .

### Impact Explanation
A forged/attacker-controlled `status` webhook can write `Status` rows and trigger `commit_status`/`deployable_status` hooks and merge-request processing jobs against `Commit`s belonging to stacks/repositories the attacker does not control, as long as a SHA collision exists (trivially achievable via shared git history between a repo and any fork/mirror also tracked by the same Shipit instance). This is a cross-tenant data-mutation vulnerability: "a payload for one repository mutating another's stack, commit ... " — matching the Critical impact category. Since commit statuses gate deploy readiness (`deployable_status`, `required_statuses`), this can influence whether unrelated stacks' commits appear deployable, and is repeatable against any SHA the attacker can also produce in their own tracked repository/fork.

### Likelihood Explanation
Preconditions: the attacker needs a GitHub repository that Shipit tracks as a `Stack` (attacker-owned, e.g. a fork), and another Shipit-tracked stack must contain a `Commit` row with an identical SHA (a natural consequence of git history sharing between forks/mirrors — no secret or privileged access needed). The webhook must still pass `verify_signature`, which only proves the payload came from a legitimate GitHub org/app for the attacker's own repository — it does not, and cannot, prove exclusive ownership of the SHA. This makes the attack low-cost and repeatable for any organization using Shipit to manage multiple stacks/forks of overlapping codebases.

### Recommendation
Scope `StatusHandler#process` the same way `PushHandler`/`CheckSuiteHandler` are scoped: restrict the `Commit` lookup to commits belonging to `stacks` (i.e., `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalently `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`) so only commits in stacks whose repository matches `payload['repository']['full_name']` are mutated.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "process only updates commits belonging to the payload's repository" do
  shared_sha = "deadbeef" * 5

  stack_a = shipit_stacks(:shipit)                     # attacker's own tracked repo/stack
  stack_b = Shipit::Stack.create!(repository: shipit_repositories(:cyclimse), environment: "other")

  commit_a = stack_a.commits.create!(sha: shared_sha, author: Shipit::AnonymousUser.new,
                                      committer: Shipit::AnonymousUser.new, authored_at: Time.now, committed_at: Time.now)
  commit_b = stack_b.commits.create!(sha: shared_sha, author: Shipit::AnonymousUser.new,
                                      committer: Shipit::AnonymousUser.new, authored_at: Time.now, committed_at: Time.now)

  payload = {
    "sha" => shared_sha, "state" => "success",
    "repository" => { "full_name" => stack_a.repository.full_name }
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  # Binding under test: only stack_a's commit should receive the status.
  assert_equal 1, Shipit::Status.where(commit_id: [commit_a.id, commit_b.id]).count
  assert_predicate commit_a.reload, :statuses?
  refute_predicate commit_b.reload, :statuses?
end
```
Running this against current `StatusHandler#process` fails: both `commit_a` and `commit_b` receive a `Status`, demonstrating `Status.where(...).count == 2` instead of `1`, i.e. the webhook for `stack_a`'s repository mutates `stack_b`, a repository/tenant not present in the webhook payload.
