### Title
Webhook signature verification keys off an attacker-controlled `repository_owner` field decoupled from the `repository.full_name` actually acted upon, allowing cross-organization webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to verify the HMAC signature against by reading `repository_owner` straight out of the untrusted JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`). Every webhook `Handler` then independently resolves the *actual* repository/stack to mutate from a different field in the same untrusted body: `payload.dig('repository','full_name')`. Nothing enforces that these two attacker-supplied fields refer to the same organization/repository. In this engine's supported multi-organization configuration (multiple `github:` entries, each with its own optional `webhook_secret`), an attacker can pick an organization whose `webhook_secret` is unset (a documented, legitimate configuration state) to trivially pass signature verification, while pointing `repository.full_name` at a completely different, victim organization's stack.

### Finding Description
Signature verification: [1](#0-0) [2](#0-1) 

`repository_owner` is derived purely from the request body the attacker controls, and used to look up which `Shipit::GithubApp` (and thus which `webhook_secret`) is used to validate `X-Hub-Signature`. The verification itself: [3](#0-2) 

Critically, `return true unless webhook_secret` — if the selected organization's `webhook_secret` is blank (explicitly documented as optional, and shown as `# nil` in every shipped secrets template, e.g. `config/secrets.development.example.yml`, `config/secrets.development.shopify.yml`, `test/dummy/config/secrets_double_github_app.yml`), verification is bypassed unconditionally for any payload whose `repository.owner.login`/`organization.login` resolves to that org.

Once verification passes, the event is dispatched to handlers via `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` in `WebhooksController#create`: [4](#0-3) 

Every handler resolves the target repository/stack from a *different*, uncorrelated field of the same body: [5](#0-4) 

For example `PushHandler` triggers a real sync against whatever stack `repository.full_name` names, using an attacker-chosen `after` SHA: [6](#0-5) 

The equality that should hold — `organization that authenticated the request == organization that owns the repository being written to` — is broken because both sides are independently read from the same attacker-controlled JSON body with no cross-check that `repository.owner.login` is actually the owner segment of `repository.full_name`.

### Impact Explanation
An unauthenticated attacker who knows (or exploits the absence of) one configured organization's `webhook_secret` can forge `push`, `status`, `check_suite`, or `membership` events targeting **any other** organization/repository/stack configured in the same Shipit instance, bypassing the per-organization webhook authentication boundary entirely. This can enqueue `GithubSyncJob` with an attacker-chosen `expected_head_sha` for a victim stack; if `continuous_deployment` is enabled on that stack, this results in an unauthorized deploy of an attacker-selected (but pre-existing) commit — meeting the "unauthorized deploy" / "authentication bypass" Critical impact bar. Even without continuous deployment, it is a full authentication bypass of the webhook ingestion boundary for arbitrary configured repositories.

### Likelihood Explanation
Feasible whenever the deployment uses the engine's documented multi-organization GitHub App feature and at least one configured organization has no `webhook_secret` set — a state the shipped templates present as the default/optional configuration. No credentials, GitHub App private key, or repository write access are required; the attacker only crafts an HTTP POST to the public `/webhooks` endpoint.

### Recommendation
Do not select the verification key from attacker-controlled payload fields that are also (separately) trusted for target-repository resolution. Cross-validate that `repository.owner.login` matches the owner segment of `repository.full_name` (or better, verify the signature against every configured `webhook_secret` and require at least one non-blank secret configured, refusing verification success when the secret is unset) before dispatching to handlers. Alternatively, resolve the acting organization/app strictly from `repository.full_name`, not from a separate `owner`/`organization` field.

### Proof of Concept
Assume a Shipit instance configured per `test/dummy/config/secrets_double_github_app.yml`-style multi-org setup where `OrgA.webhook_secret` is blank and `OrgB` (victim, hosting stack `OrgB/victim-repo` with `continuous_deployment: true`) has a secret set.

```
POST /webhooks HTTP/1.1
X-Github-Event: push
Content-Type: application/json

{
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  },
  "ref": "refs/heads/main",
  "after": "<existing legit commit sha in OrgB/victim-repo>"
}
```
`repository_owner` resolves to `"OrgA"`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of any `X-Hub-Signature` header (`lib/shipit/github_app.rb#L76-L83`). `PushHandler#process` then resolves `repository_name` as `"OrgB/victim-repo"` (`handler.rb#L36-L38`) and calls `stack.sync_github(expected_head_sha: "<attacker chosen sha>")`, syncing/deploying that stack without ever presenting a valid `OrgB` webhook signature.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
