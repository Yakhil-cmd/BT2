### Title
Webhook signature verified against org derived from an unbound payload field, while a different org's Stack is written - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
### Finding Description
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate the incoming request against based on `repository_owner`, which is read straight out of the *unverified* request body: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. Only after this per-organization secret check passes does `create` dispatch the same raw payload to the handler classes. [1](#0-0) 

Shipit explicitly supports hosting multiple GitHub organizations from one instance, each with its own `webhook_secret`, keyed by organization name in `secrets.yml` (`docs/setup.md`, "Using Multiple GitHub Applications", and `Shipit.github(organization:)` / `github_app_config`). [2](#0-1) 

The handlers that actually mutate state never re-derive or re-check the organization used for signing; they independently read `repository.full_name` (a sibling field of `repository.owner.login`, not cryptographically tied to it beyond both living in the same signed HTTP body) to look up the `Repository`/`Stack` to act on: [3](#0-2) [4](#0-3) 

The binding that is broken: **the organization whose secret authenticated the request** must equal **the organization/repository whose Stack is written**. Before the attacker's payload: `repository_owner (used for HMAC secret selection) == repository.full_name's owner (used for Stack lookup)`, because both come from a single legitimate GitHub webhook for one repo. After a crafted payload: an entity that legitimately owns/administers *any* one organization configured in this Shipit instance (and therefore legitimately knows that organization's `webhook_secret`, which GitHub itself exposes to that org's App admin) can sign a webhook body in which `repository.owner.login`/`organization.login` names their own org (so `verify_signature` picks and validates against their own known secret) while `repository.full_name` names a repository belonging to a *different* configured organization/stack. Nothing in `verify_signature` or in the handlers cross-checks that the two fields agree.

### Impact Explanation
Because the two fields are decoupled, a party who only controls one tenant/organization onboarded to this multi-org Shipit deployment can forge webhook events that are processed as if they originated from a different organization's repository:
- `push` events route to `PushHandler`, which calls `stack.sync_github(expected_head_sha:)`, enqueuing `GithubSyncJob` for the target stack of *another* organization, pulling attacker-influenced commit metadata (`sha`) into that stack's commit history/deploy pipeline. [5](#0-4) [6](#0-5) 
- `status` events forge CI/commit statuses on arbitrary commits of another org's stack. [7](#0-6) 
- `membership` events can create/delete `Team`/`Membership` records tied to a different org, which feeds directly into `Shipit.github_teams` access control (`User#authorized?`), i.e. escalation into `Shipit.github_teams` authorization. [8](#0-7) [9](#0-8) 

This matches the rules' accepted "High" impact category of escalation into `Shipit.github_teams` authorization, and can influence deploy pipelines (commits/statuses feeding into merge/deploy decisions) for stacks belonging to organizations the caller does not control.

### Likelihood Explanation
Exploitability requires the attacker to be an onboarded organization admin for *some* org configured in the multi-org Shipit deployment (a legitimate, unprivileged-relative-to-other-tenants position, since they only need control of their own org's GitHub App/webhook settings, not the victim org's). This is a realistic and documented deployment topology (`docs/setup.md`), not a theoretical one; the discovered code path shows no cross-check between the field used for authentication and the field used for the write target, so likelihood is limited only by whether the deployment actually enables multiple organizations (a supported, documented configuration).

### Recommendation
In `WebhooksController#verify_signature`/`#create`, after verifying the signature for the resolved `repository_owner`, re-validate that every entity the payload references (e.g., `repository.full_name`'s owner segment, `organization.login`) matches the exact organization whose secret was used to verify the signature, and reject the webhook otherwise. Alternatively, have each `Handler` receive the authenticated organization and assert it matches the repository/organization it is about to mutate before performing any writes.

### Proof of Concept
1. Deploy Shipit with the documented multi-org config (`docs/setup.md`, "Using Multiple GitHub Applications") hosting `OrgA` (attacker-administered) and `OrgB` (victim), each with a distinct `webhook_secret`.
2. As the admin of `OrgA`, obtain `OrgA`'s `webhook_secret` from the GitHub App settings (legitimate access to your own org's App).
3. Craft a `push` webhook JSON body: `{"ref": "refs/heads/main", "after": "<attacker-chosen sha>", "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgB/victim-repo"}}`.
4. Compute `X-Hub-Signature` as `sha1=` HMAC-SHA1 of the raw body using `OrgA`'s `webhook_secret`.
5. POST to `/webhooks` with header `X-Github-Event: push`.
6. `verify_signature` resolves `repository_owner` = `"OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and the signature validates successfully.
7. `Shipit::Webhooks.for_event('push')` invokes `PushHandler`, whose `repository_name` reads `payload.dig('repository','full_name')` = `"OrgB/victim-repo"`, locating and enqueuing a sync job against `OrgB`'s stack — despite the request never being authenticated by `OrgB`'s secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
