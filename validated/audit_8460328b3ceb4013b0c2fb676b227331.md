### Title
Users stuck in `Queue` cannot `deregister` (and thus never unreserve their `Deposit`) once `pallet-fast-unstake` internally halts itself - ([File: substrate/frame/fast-unstake/src/lib.rs])

### Summary
`pallet-fast-unstake` gates both `register_fast_unstake` and, critically, `deregister` on the same "enabled" flag, `ErasToCheckPerBlock`. This flag can be forced to `0` either by governance (`control`) or automatically by the pallet itself via `Self::halt(...)` whenever an internal invariant is violated (e.g. an unexpected `unreserve` shortfall while unstaking/slashing a batch). Once halted, users who are already sitting in `Queue<T>` with funds reserved via `T::Deposit` lose the only exit path (`deregister`) that would return their reserved deposit, exactly mirroring the amAMM finding where disabling the feature blocks `claimRefund`/`cancelNextBid`/`withdrawFromNextBid`.

### Finding Description
`register_fast_unstake` reserves a `Config::Deposit` amount and inserts the caller into `Queue<T>`: [1](#0-0) 

The only way to leave the queue and get the deposit back before being picked up by `on_idle` is `deregister`: [2](#0-1) 

Both `register_fast_unstake` and `deregister` are gated by the *same* liveness check, `ErasToCheckPerBlock::<T>::get() != 0`: [3](#0-2) [4](#0-3) 

`ErasToCheckPerBlock` can be set to `0` by `ControlOrigin` via the `control` extrinsic: [5](#0-4) 

More importantly, the pallet can **self-disable** without any governance action: `Self::halt` sets `ErasToCheckPerBlock` to `0` automatically whenever the pallet detects an unexpected state during `on_idle` processing (e.g., "not enough balance to unreserve" when unstaking or de-registering internally): [6](#0-5) 

This same `halt` is invoked from the `on_idle` batch-processing closures for both the slashing and unstaking paths: [7](#0-6) 

and from `deregister` itself if an `unreserve` doesn't fully clear: [8](#0-7) 

Once `ErasToCheckPerBlock` becomes `0` (whether by governance intervention or by this automatic, permissionless-triggered halt), `do_on_idle` becomes a no-op: [9](#0-8) 

At that point, any stash still sitting in `Queue<T>` with its `Deposit` reserved (confirmed by the existing test `deregister_disabled_fails`) can no longer call `deregister` to reclaim it, and it will never be processed by `on_idle` either: [10](#0-9) 

This is the exact structural analog of the amAMM bug: an "enabled/disabled" flag is checked identically for both the "join"/bid path and the "exit"/refund path, so disabling it (here, partly through an internally-triggered, non-privileged halt path) locks funds that users already committed, with no permissionless recovery mechanism (only `ControlOrigin` via `control` can re-enable it — a privileged, ungoverned-by-the-user action, and normal deregistration remains impossible in the meantime).

### Impact Explanation
Stashes with a reserved `Deposit` in `Queue<T>` become unable to `deregister` and reclaim their reserved balance while the pallet is halted, and `Head`/`Queue` items are never advanced (`do_on_idle` short-circuits). Funds remain reserved (not lost outright since `ControlOrigin` can restore `ErasToCheckPerBlock`), but this is an irreversible-by-the-user freeze of funds for an indeterminate period, matching the "funds can get locked" characterization of the referenced report. The `Deposit` amount is generally small/bounded (not proportional to total stake), which caps the blast radius, but the loss of a self-service exit path for as long as the pallet is halted is a genuine availability/funds-locking issue.

### Likelihood Explanation
Low-to-moderate. The halt is triggered either by deliberate governance action (`control(0)`) — a low-likelihood, intentional maintenance action — or by an internal-error branch guarded with `defensive!` that is only supposed to trigger on an accounting bug (unreserve shortfall), which the pallet authors already flag as unexpected ("not enough balance to unreserve"). This is analogous to the report's own "Low" likelihood rating for the amAMM disablement path — it requires an unusual/administrative event, not a routine user-triggered condition.

### Recommendation
Decouple the queue-exit path from the enabled/disabled flag: `deregister` should not require `ErasToCheckPerBlock != 0`. A user who is only in `Queue` (not `Head`) and wants to leave should always be able to call `deregister` and unreserve their deposit regardless of whether the pallet is currently processing (`ErasToCheckPerBlock == 0`), analogous to the amAMM recommendation to always let managers reclaim deposits once bidding/managing is disabled. Only `register_fast_unstake` (entering the system) should be gated by the enabled check.

### Proof of Concept
Not independently re-executed here; the failing guard is directly evidenced by the existing repository test `deregister_disabled_fails`, which asserts `deregister` returns `Error::<T>::CallNotAllowed` once `ErasToCheckPerBlock` is `0`: [10](#0-9) 

Combined with the automatic halt path in `deregister`'s own `unreserve` branch and in the `on_idle` unstake/slash closures (`Self::halt("not enough balance to unreserve")`), this demonstrates that a user queued for fast-unstake can be left with a reserved `Deposit` and no dispatchable path to reclaim it as soon as `ErasToCheckPerBlock` reaches `0`, whether via governance `control(0)` or via the pallet's own internal-error halt. A full local FRAME integration reproduction (e.g., driving `on_idle` into the `not enough balance to unreserve` defensive branch to trigger a genuine self-halt rather than a governance-forced one) was not executed in this pass; this would require constructing a scenario where the reserved deposit balance is reduced below what `unreserve` expects (e.g., through another hold/lock on the same account) — this is left as follow-up verification.

		pub fn register_fast_unstake(origin: OriginFor<T>) -> DispatchResult {
			let ctrl = ensure_signed(origin)?;

			ensure!(ErasToCheckPerBlock::<T>::get() != 0, Error::<T>::CallNotAllowed);
			let stash_account =
				T::Staking::stash_by_ctrl(&ctrl).map_err(|_| Error::<T>::NotController)?;
			ensure!(!Queue::<T>::contains_key(&stash_account), Error::<T>::AlreadyQueued);
			ensure!(!Self::is_head(&stash_account), Error::<T>::AlreadyHead);
			ensure!(!T::Staking::is_unbonding(&stash_account)?, Error::<T>::NotFullyBonded);

			// chill and fully unstake.
			T::Staking::chill(&stash_account)?;
			T::Staking::fully_unbond(&stash_account)?;

			T::Currency::reserve(&stash_account, T::Deposit::get())?;

			// enqueue them.
			Queue::<T>::insert(stash_account, T::Deposit::get());
			Ok(())
		}

		#[pallet::weight(<T as Config>::WeightInfo::deregister())]
		pub fn deregister(origin: OriginFor<T>) -> DispatchResult {
			let ctrl = ensure_signed(origin)?;

			ensure!(ErasToCheckPerBlock::<T>::get() != 0, Error::<T>::CallNotAllowed);

			let stash_account =
				T::Staking::stash_by_ctrl(&ctrl).map_err(|_| Error::<T>::NotController)?;
			ensure!(Queue::<T>::contains_key(&stash_account), Error::<T>::NotQueued);
			ensure!(!Self::is_head(&stash_account), Error::<T>::AlreadyHead);
			let deposit = Queue::<T>::take(stash_account.clone());

			if let Some(deposit) = deposit.defensive() {
				let remaining = T::Currency::unreserve(&stash_account, deposit);
				if !remaining.is_zero() {
					Self::halt("not enough balance to unreserve");
				}
			}

			Ok(())
		}
