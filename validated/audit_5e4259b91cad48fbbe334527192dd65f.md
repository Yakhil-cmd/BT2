### Title
Cross-stack status forgery via unscoped `Commit.where(sha:)` lookup in `security/scan` amplified by `merge_queue_enabled` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` writes a `Status` to **every** `Commit` record that shares the reported SHA, regardless of which stack/repository authenticated the webhook. Because Git commit SHAs are content-addressed, an attacker who forks/mirrors a victim's public repository can reproduce identical commit SHAs, then send a validly signed webhook for their own repository that also flips CI state (e.g. `security/scan`) on the victim's identical commit, ultimately biasing `MergeRequest#merge!` / deploy gating on the victim's `merge_queue_enabled` stack.

### Finding Description
The broken binding is: `status.commit.stack_id` should equal `webhook.repository.stack_id` — i.e. a status webhook should only ever attach to commits belonging to the repository/stack that authenticated the request. In code:

- `StatusHandler#process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — no filter by `stack_id`, `repository`, or the payload's `repository.full_name`. [1](#0-0) 

- `Commit` has no unique index tying `sha` to a single stack — `sha` is only unique per row via `(sha, stack_id)`-style usage elsewhere (`Commit.by_sha` operates on `stack.commits`), but `StatusHandler` bypasses that scoping entirely and queries the global `Commit` table. [2](#0-1) 

- `WebhooksController#verify_signature` authenticates the webhook only against the GitHub **organization** login extracted from the payload (`Shipit.github(organization: repository_owner)`), not against the specific repository or stack, and it does not cross-check that `params['repository']['full_name']` matches any stack that actually owns the SHA. [3](#0-2) [4](#0-3) 
`GitHubApp#verify_webhook_signature` only checks the HMAC against the configured per-organization `webhook_secret`. [5](#0-4) 

**Exploit flow:** An attacker who owns/administers any repository under a GitHub organization that Shipit trusts (i.e. they can legitimately register a webhook and obtain that org's `webhook_secret` for their own repo) forks a victim's public repository, which reproduces byte-identical commit objects and therefore identical SHAs for existing history. The attacker then sends a correctly-signed `status` event (`POST /webhooks`, `X-Github-Event: status`) referencing that shared SHA with `context: security/scan` and `state: success` (or `failure`). `StatusHandler#process` matches the victim's `Commit` row purely by `sha` and calls `commit.create_status_from_github!(params)`, creating a `Status` for the **victim's stack** that the attacker never authenticated for. [6](#0-5) 

`create_status_from_github!` triggers `add_status`, which schedules merges (`stack.schedule_merges`) whenever the new status is `pending` or `success`. [7](#0-6) 

If the victim stack has `merge_queue_enabled: true`, `MergeRequest.schedule_merges` iterates enabled stacks and evaluates `MergeRequest#merge!`, which gates on `StatusChecker` built from `head.statuses_and_check_runs` — the exact list the attacker just polluted via the forged `Status` row. [8](#0-7) [9](#0-8) 

None of the existing guards prevent this: `verify_signature` authenticates the org, not the repo/stack relationship to the SHA; `drop_unhandled_event` only checks the event type is registered; the `ExplicitParameters` schema on `StatusHandler` only validates `sha`/`state`/`context` types, not ownership; there is no `require_permission!` or stack-scoping check anywhere in this path.

### Impact Explanation
A payload from one attacker-controlled repository can write a `Status` record — and therefore flip effective CI/merge-gating state — on a completely different stack/repository's commit that the attacker never authenticated for, provided the commit SHA is shared (trivially achievable for any public repo via fork/mirror). Combined with `merge_queue_enabled: true`, this can force `merge!` to proceed (unauthorized merge) or block a legitimate merge (denial of a legitimate ship) on the victim's stack — matching "a payload for one repository mutating another's stack, commit, task" / "unauthorized deploy, rollback or merge" (Critical). The attack is repeatable against any stack whose repository shares history (i.e. any public fork target) with an attacker-accessible repository under a trusted GitHub org.

### Likelihood Explanation
Preconditions: the attacker must control (or register a webhook for) some repository under a GitHub organization already configured/trusted in Shipit's `github_apps`/`webhook_secret` config (needed to pass `verify_signature`), and the victim stack must track `security/scan` as a required/blocking status with `merge_queue_enabled: true`. Forking a public repo to obtain identical commit SHAs is trivial and free. Cost is low and the primitive is repeatable per shared SHA per webhook delivery.

### Recommendation
Scope `StatusHandler#process` (and analogously `CheckSuiteHandler`) to only touch commits belonging to stacks whose `repository.full_name`/`owner` match the authenticated webhook's `params['repository']`, e.g. join through `Stack`/`Repository` instead of a bare `Commit.where(sha:)`. Additionally, `verify_signature` should bind the verified organization/repository to the specific stack(s) being mutated in `process`, not just to organization-level signature validity.

### Proof of Concept
minitest outline (`test/controllers/webhooks_controller_test.rb` or `test/models/status_test.rb`):
1. Create `stack_a` (attacker's, org `evilcorp`) and `stack_b` (victim's, org `victimcorp`, `merge_queue_enabled: true`, deploy spec requiring `security/scan`).
2. Create a `Commit` with the same `sha` (e.g. `"deadbeef" * 5`) under both `stack_a` and `stack_b`, and an open `MergeRequest` on `stack_b` with `head` pointing to that commit, `merge_status: 'pending'`.
3. Stub `Shipit.github(organization: 'evilcorp').verify_webhook_signature` to return `true` (simulating attacker's legitimately-signed request for their own org).
4. POST to `/webhooks` with `X-Github-Event: status`, body `{ sha: <shared_sha>, state: 'success', context: 'security/scan', repository: { owner: { login: 'evilcorp' } } }`.
5. Assert equality that should hold but doesn't: `stack_b.commits.find_by(sha: shared_sha).statuses.where(context: 'security/scan').count == 0` before the request, and after the request this is `> 0` — i.e. `victim_commit.statuses.count` changed as a result of a request that only authenticated `stack_a`'s organization, proving `params['repository']` (attacker's) ≠ `commit.stack.repository` (victim's) yet the write succeeded.
6. Additionally assert `MergeRequest#any_status_checks_failed?`/`missing?` flips accordingly and, with `merge_queue_enabled: true`, that `MergeRequest.schedule_merges` / `merge!` behavior changes for `stack_b`.

      raise AmbiguousRevision, "Short SHA1 #{sha} is ambiguous (too short)" if sha.to_s.size < 6

      raise AmbiguousRevision, "Short SHA1 #{sha} is ambiguous (matches multiple commits)" if commits.size > 1

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
