### Title
Missing default handler in oscript definition/authentifier evaluator causes unhandled-op hang/crash - (File: definition.js)

### Summary
`validateAuthentifiers()`'s inner `evaluate()` function in [1](#0-0)  dispatches on the address/asset-definition opcode `op` via a `switch(op)` statement, but the switch has **no `default` case** [2](#0-1) . This mirrors the CVE-2019-10894 bug class: a dispatcher (Wireshark's GSS-API sub-dissector table) that is invoked without first ensuring a valid handler exists for the given type, leading to abnormal termination/hang instead of controlled error handling.

### Finding Description
Address and asset-spending conditions in Obyte are represented as nested `[op, args]` arrays. Two independent evaluators walk this same structure:

1. `validateDefinition()`'s `evaluate()` — validates the *shape* of the definition and has a proper `default: return cb("unknown op: "+op);` [3](#0-2) .
2. `validateAuthentifiers()`'s `evaluate()` — actually *executes*/evaluates the condition against the unit's authentifiers when checking authors/signatures, and has **no `default` branch at all**, closing the `switch` directly after the `'formula'` case [2](#0-1) .

`validateAuthentifiers()` is called only after `validateDefinition()` has approved the definition [4](#0-3) , so under normal conditions the op passed to the second evaluator should already be whitelisted by the first. However, this creates a fragile "shadow whitelist" pattern: any op accepted by `validateDefinition()`'s switch that is not handled (or handled differently) by `validateAuthentifiers()`'s switch will fall through silently with **`cb2` never invoked**, because there is no default branch to report an error. Since these evaluators are invoked inside `async.eachSeries` continuation-passing chains, failing to call the callback halts the recursive walk without throwing or returning — the calling `async.eachSeries`/`evaluate()` invocation simply never completes.

This is the JavaScript analogue of the Wireshark bug: instead of validating that a "sub-dissector" (here, an opcode handler) exists before dispatching to it, the code assumes the whitelist enforced in a *different, decoupled* function is exactly in sync. Any accidental mismatch between the two switch statements (e.g. via future maintenance adding a case to one but not the other, or a version/mci-gated op recognized by one and not the other) is unguarded and will silently stall unit validation rather than reporting a validation error.

I was not able to fully diff every parenthesis/branch of both switches under all `mci`/upgrade-flag combinations from the excerpts examined (some code paths are version-gated, e.g. `weighted and`, `formula`, `attested`), so I cannot conclusively prove today's whitelist content is out of sync — but the code path itself is structurally unguarded, which is the exact same root cause pattern as the reported CVE (dispatch without validating the target handler exists).

### Impact Explanation
If a mismatch between the two whitelists is ever introduced (which is easy given they are maintained as two independent, hand-written switch statements 900+ lines apart with different case sets and different mci-gating conditions), a unit could be crafted that:
- Passes `validateDefinition()`'s structural check (since that op is listed there), but
- Falls through `validateAuthentifiers()`'s switch with no default case, silently never calling `cb2`.

This stalls the mutex-protected unit validation path for that unit (validation.js's `mutex.lock(['write'], ...)` chain never proceeds to `unlock()`), effectively freezing further validation of new units for the node — a "network unable to confirm new units" condition reachable by any unpaired attacker posting a single crafted unit with a valid-looking address definition.

### Likelihood Explanation
Currently, based on the cases reviewed, the two switches for the "core" set of ops (`or`, `and`, `r of set`, `weighted and`, `sig`, `hash`, `address`, `definition template`, `seen address`, `seen definition change`, `attested`, `cosigned by`, `not`, `in data feed`, `in merkle`, `mci`/`age`/`timestamp`, `has`/`has one`, `sum`, `has definition change`, `formula`) appear to line up, so exploitation today would require finding one that is missing or gated differently. I could not verify with full certainty that no such op-vs-mci mismatch exists across all upgrade flags (`pemCurvesFixMci`, `formulaUpgradeMci`, `attestedInDefinitionUpgradeMci`, `anyDefinitionChangeUpgradeMci`, `aa2UpgradeMci`, etc.) since the interacting mci-gates in `validateDefinition()` and the un-gated cases in `validateAuthentifiers()` are not identical in structure. This uncertainty is the reason likelihood is rated medium rather than high — the code is defensively weak (matching the CVE bug class) but I cannot confirm active exploitability with the information reviewed.

### Recommendation
Add an explicit `default:` case to the `switch(op)` in `validateAuthentifiers()`'s `evaluate()` (definition.js, ending around line 1232) that calls `cb2(false)` (or surfaces a fatal error) for any unrecognized op, exactly as `validateDefinition()` already does. This ensures that any future divergence between the two whitelists fails safely (rejecting the unit) instead of silently hanging the validation pipeline — directly closing the CVE-2019-10894-style "dispatch without validating the target handler" gap.

### Proof of Concept
Not able to construct a concrete PoC unit with the information available: doing so would require identifying (or introducing via a future code change) an op that `validateDefinition()`'s whitelist accepts but that is absent from `validateAuthentifiers()`'s switch, or an op that is valid at one `mci` boundary in one function but not gated identically in the other. I was unable to confirm such a live mismatch exists in the current codebase from the sections read, so I cannot provide a working exploit unit; the finding is reported as a structural robustness/defense-in-depth gap analogous to the CVE, not a proven exploitable path today.
