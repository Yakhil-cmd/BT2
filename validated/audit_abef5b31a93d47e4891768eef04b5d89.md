### Title
Null-byte injection in paired device name allows sender identity spoofing in correspondent display - ([File: device.js])

### Summary
`handlePairingMessage()` in `device.js` sanitizes the incoming `device_name` field only by stripping HTML tags, but never rejects or strips embedded NUL (`\x00`) bytes before persisting the value as the correspondent's displayed name. This mirrors the root cause of CVE-2017-7829 (Thunderbird sender spoofing via a NUL byte in the display string): a value containing an embedded NUL byte is stored/rendered by downstream consumers that treat `\x00` as a string terminator, letting an attacker present a different (spoofed) identity than the one actually stored.

### Finding Description
When a device (paired or unpaired, as long as it knows a valid pairing secret) sends a `pairing` message, `handlePairingMessage` validates `device_name` only for non-emptiness and a 100-character length cap, then "sanitizes" it by stripping HTML-like tags: [1](#0-0) 

```
if (!ValidationUtils.isNonemptyString(body.device_name))
    return callbacks.ifError("no device_name when pairing");
if (body.device_name.length > 100)
    return callbacks.ifError("device_name too long");
...
var safe_device_name = body.device_name.replace(/<[^>]*>?/g, '');
db.query(
    "INSERT ... INTO correspondent_devices (device_address, pubkey, hub, name, is_confirmed) VALUES (?,?,?,?,1)",
    [from_address, device_pubkey, json.device_hub, safe_device_name], ...
```

No check for `\x00` is performed here, even though `ocore` clearly recognizes this class of attack elsewhere and explicitly rejects NUL bytes in other user-supplied strings, e.g. in `validation.js`: [2](#0-1) 

and in `string_utils.js`'s `getSourceString`, which throws on embedded `\x00`: [3](#0-2) 

The unsanitized `safe_device_name` (still containing the raw NUL byte) is written verbatim into the `name` column of `correspondent_devices`:



e.g. `name VARCHAR(100) BINARY NOT NULL` in the MySQL/RocksDB schema, which preserves the raw bytes exactly as supplied by the remote device. [4](#0-3) 

This name is later read back and shown to the wallet user through `readCorrespondents`/`readCorrespondent`, which return the `name` field unmodified for UI display: [5](#0-4) 

Any GUI/wallet layer built on `ocore` (mobile/desktop wallet apps, chat UI, correspondent lists) that renders this string using a NUL-terminated string API (common in native components — Objective‑C `NSString` from a C buffer, certain Android/JNI paths, or any library relying on C-string semantics) will display only the substring preceding the injected `\x00`, while the actual persisted `name` (used internally for matching, logs, exports, etc.) contains the full attacker-controlled string. An attacker can therefore craft `device_name = "Trusted Contact\x00 - fake-note-or-hidden-suffix"`, or conversely embed a legitimate-looking name after the NUL so that any downstream tooling that strips at the first NUL displays a benign prefix while the stored record differs from what's shown — exactly the "sender spoofing via NUL byte in display string" pattern from CVE-2017-7829.

### Impact Explanation
The correspondent `name` is the primary human-readable identity marker used to decide whether to trust a device for chat, private-payment chain delivery (`handlePrivatePaymentChains`), and payment notifications processed in `handleMessageFromHub`. If the displayed name can be spoofed via a hidden/truncated NUL suffix, a user can be tricked into believing they are interacting with (and subsequently sending private payment chain data, or making private/public payments to) an already-trusted correspondent, when in fact the record was created/renamed by an unrelated attacker device. This enables social-engineering-driven fund loss/misdirected payments consistent with "unauthorized spending" via a trusted-identity spoof, analogous to the phishing risk the original CVE addresses.

### Likelihood Explanation
Exploitation requires only sending a `pairing` device message with an attacker-chosen `device_name`, which is reachable by any device holding a (possibly widely shared, e.g. bot/public) pairing secret — no special privilege beyond being a paired/pairing device is needed. The lack of NUL-byte filtering is a straightforward, deterministic bug (unlike guessing hashes or timing races), making likelihood moderate-to-high for any hub/GUI stack whose rendering layer honors C-string NUL termination.

### Recommendation
Reject or strip NUL bytes (`\x00`) from `device_name` (and other user-controlled display strings, e.g. `correspondent.name` in `updateCorrespondentProps`) in `device.js`, mirroring the existing check used for `payload_uri` in `validation.js`:
```
if (body.device_name.includes("\x00"))
    return callbacks.ifError("device_name contains null byte");
```
Apply the same check to `updateCorrespondentProps` and any other path that writes to `correspondent_devices.name`.

### Proof of Concept
1. Attacker device obtains/knows a valid pairing secret (own generated one, or a leaked/public bot pairing code).
2. Attacker sends a `pairing` device message with body:
```
{
  "pairing_secret": "<valid secret>",
  "device_name": "Trusted Friend\u0000 (attacker real identity/hidden note)"
}
```
3. `handlePairingMessage` in `device.js` accepts the name (length ≤ 100, no NUL check), strips HTML tags (none present), and stores the raw string (with embedded NUL) into `correspondent_devices.name`.
4. Any wallet UI that renders this field with NUL-terminated string semantics displays only `"Trusted Friend"` to the user, while the actual record and any raw-string processing elsewhere retains the full attacker-controlled value — spoofing the displayed identity of the correspondent, exactly as in CVE-2017-7829's sender-spoofing scenario.
