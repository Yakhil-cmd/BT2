### Title
Delimiter-less concatenation in prosaic contract hashing allows content-boundary smuggling between `title` and `text` fields - ([File: prosaic_contract.js])

### Summary
`prosaic_contract.js` computes the commitment hash of a prosaic contract by naively concatenating `contract.title + contract.text + contract.creation_date` with no separator, both in `getHash()` and `getHashV1()`. This is the same class of bug as the reported CVE: a parser/serializer that does not strictly delimit adjacent fields, so two different peers (or two different points in the protocol) can end up interpreting the same byte stream as different logical structures — exactly like an HTTP intermediary and origin server disagreeing on where one message ends and the next begins.

### Finding Description [1](#0-0) 

```js
function getHash(contract) {
	return crypto.createHash("sha256").update(contract.title + contract.text + contract.creation_date, "utf8").digest("base64");
}

function getHashV1(contract) {
	return objectHash.getBase64Hash(contract.title + contract.text + contract.creation_date);
}
```

There is no delimiter between `title`, `text` and `creation_date`. Because string concatenation of `title + text` is not injective, an attacker who controls both fields (the offeror of a "prosaic contract", an operation reachable by any paired device via the `prosaic_contract_offer` device message) can pick two different `(title, text)` pairs that concatenate to the identical byte sequence, e.g.:
- `title = "Pay 100 bytes"`, `text = " to Alice"` 
- `title = "Pay 100 bytes "`, `text = "to Alice"`

These serialize to the same string and thus the same `getHash`/`getHashV1` value. Compare this with `arbiter_contract.js`, which does the equivalent job correctly by using an explicit `exports.DELIMITER` when joining fields [2](#0-1) , showing the codebase is aware that unseparated concatenation of variable-length fields is unsafe, yet `prosaic_contract.js` doesn't apply the same fix.

This hash is used as the on-chain commitment for the contract: when the shared-address unit carrying the "data" message is later found, the code checks that the message's `payload.contract_text_hash` matches the locally stored `contract.hash` [3](#0-2) . Because the hash function has boundary collisions, this on-chain commitment does not uniquely determine the contract's `title`/`text` split, and it is reachable purely through the device-message-driven contract offer/response flow that a paired device can initiate.

### Impact Explanation
This is a data-integrity/commitment-forgery bug reachable from a paired device counterparty: the sha256 commitment stored on-chain (`contract_text_hash`) and used to prove what a signer agreed to is not a faithful, collision-resistant binding of the two separate fields. A malicious counterparty could craft an offer/response pair such that the locally displayed and locally stored `(title, text)` differs between two victims (or between what was displayed to a signer and what is later presented to an arbiter) while sharing the same hash, undermining the contract's non-repudiation guarantee. This does not directly cause double-spend or supply inflation, but it does allow a form of "message smuggling" across the two fields that a party relying on `contract.hash` for content authentication cannot detect.

### Likelihood Explanation
Exploitation requires only that a malicious paired device craft `title`/`text` strings whose concatenation is ambiguous (trivial to construct, since any character(s) can be shifted across the boundary between `title` and `text`), and send it via the ordinary `prosaic_contract_offer` / response device-message flow. No privileged access, hub compromise, or network position is needed — only the private-payment/paired-device messaging channel that ordinary users already use for these contracts.

### Recommendation
Use a length-prefixed or explicitly delimited encoding (as already done in `arbiter_contract.js` via `exports.DELIMITER`, or by using `objectHash.getSourceString`/`getJsonSourceString` on a structured object `{title, text, creation_date}` rather than raw string concatenation) in both `getHash` and `getHashV1` of `prosaic_contract.js`, so that field boundaries cannot be shifted while preserving the resulting hash.

### Proof of Concept
1. Craft contract A: `title = "Pay 100 bytes"`, `text = " to Alice"`, `creation_date = "2024-01-01"`.
2. Craft contract B: `title = "Pay 100 bytes "`, `text = "to Alice"`, `creation_date = "2024-01-01"`.
3. Compute `getHash(A)` and `getHash(B)` — both equal `sha256("Pay 100 bytes to Alice2024-01-01")`, i.e. identical hashes for different logical (title,text) content.
4. An offeror sends contract A to a signer for review/signature, and later claims/presents contract B (or a third-party arbiter sees B) as the agreed contract — the shared `contract.hash`/`contract_text_hash` commitment cannot distinguish the two.

Note: I could not fully trace every downstream `wallet.js` usage (7 matches were found for `prosaic_contract_offer`/`prosaic_contract_response`/`contract_text_hash`, but I did not have remaining tool calls to inspect each one in detail); a Devin session with full repository access should confirm the exact UI/display and dispute-resolution code paths that consume `contract.hash` to fully scope real-world exploitability.
