### Title
`StatusHandler#process` writes GitHub status webhooks onto *any* `Commit` row sharing the reported sha, regardless of which repository sent the webhook, enabling cross-repository merge-queue forgery - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the target `Commit` records purely by `sha`, with no filter on the reporting repository, while `WebhooksController#verify_signature` only proves that the *payload's own repository owner* signed the request — it does not prove the sha actually belongs to that repository. An attacker who controls a repository sharing commit history with a victim stack (e.g. a fork, or any repo containing an identical commit) can send a legitimately signed status webhook from their own repo and have it applied to the victim's queued `MergeRequest#head` commit, flipping `all_status_checks_passed?` to true and causing `Shipit::ProcessMergeRequestsJob` to call `merge_request.merge!` → `stack.github_api.merge_pull_request`.

### Finding Description
The broken binding, stated as an equality that must hold but does not:
`Commit.where(sha: params.sha).first.stack.repository.full_name == payload.dig('repository', 'full_name')`

Code path:
1. `Shipit::WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) verifies the HMAC signature using `Shipit.github(organization: repository_owner)`, where `repository_owner` is taken from the *attacker's own payload* (`params.dig('repository','owner','login')`). Since the attacker owns/controls that repository and its GitHub App/webhook configuration for their own org/repo, this signature check passes legitimately — it authenticates "this request came from repo X," not "sha S belongs to repo X."
2. `Shipit::Webhooks::Handlers::StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`):
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This query is global across the entire `commits` table — it is not scoped to `stacks` belonging to `repository_name` (contrast with `Handler#stacks`, defined at `app/models/shipit/webhooks/handlers/handler.rb:32-34`, which *is* available but unused here). Any `Commit` row in any stack, in any repository, whose `sha` column matches the attacker-supplied value receives a new `Status` row via `Shipit::Status.replicate_from_github!` (`app/models/shipit/status.rb:24-33`).
3. `Commit#create_status_from_github!` → `#add_status` (`app/models/shipit/commit.rb:165-169`, `366-386`) recomputes `status` (a `Status::Group`) and, on a state change to success/pending, calls `stack.schedule_merges`, queuing `ProcessMergeRequestsJob` for the **victim's** stack.
4. `Shipit::ProcessMergeRequestsJob#perform` (`app/jobs/shipit/process_merge_requests_job.rb:21-23`) calls `merge_request.refresh!` (re-fetches PR metadata/statuses from GitHub but only *appends* new `Status` rows, it does not delete the forged one) then `merge_request.all_status_checks_passed?` (`app/models/shipit/merge_request.rb:193-197`), which builds `StatusChecker.new(head, head.statuses_and_check_runs, stack.cached_deploy_spec)` over the accumulated statuses, including the forged one. If `Status::Group` selects the most recent status per context, the attacker's forged `success` status (with a matching `context`) can satisfy the missing/failing required context.
5. `all_status_checks_passed?` returns `true`, so `merge_request.merge!` (`app/models/shipit/merge_request.rb:164-191`) runs and calls `stack.github_api.merge_pull_request(...)`, merging the victim's PR using the victim's own installation credentials, even though the victim repository's real CI never produced that passing status for that context.

Why existing guards fail: `verify_signature` authenticates the sender's repository ownership but is checked against the wrong scope — it never re-validates that the `sha` in the payload is actually a commit that belongs to the sending repository. `ExplicitParameters` only validates the shape of the payload (`sha`, `state`, `context`, etc.), not repository ownership of the sha. `drop_unhandled_event` and `force_github_authentication` are unrelated to this path (`WebhooksController` is a raw signed-webhook endpoint, not a session/API-token endpoint).

### Impact Explanation
A payload for one repository (the attacker's) mutates and ultimately triggers an authoritative action (merge) for a completely different, unrelated repository/stack's queued pull request. This is an unauthorized merge — code is shipped for the victim repository without the victim repository's real CI having passed the required context. This matches the Critical impact category "a payload for one repository mutating another's stack, commit, task or team" and "an unauthorized deploy, rollback or merge." The blast radius spans any Shipit installation hosting multiple stacks where commit history/shas can collide (forks of the same upstream, shared base commits, empty/no-op commits, or intentionally crafted commits with identical content+parents+timestamps to force a sha collision) — repeatable per victim commit sha the attacker can reproduce.

### Likelihood Explanation
Preconditions: victim stack must have a pending `MergeRequest` in the merge queue whose `head` commit is currently failing/missing the required status context; attacker needs a repository they control that is already integrated with the same Shipit instance (so a valid `X-Hub-Signature` can be produced for their own repo) and the ability to produce/name a commit whose sha matches (or is later reused for) the victim's queued head sha — most practically via a shared/forked history, cherry-picked/rebased identical commits, or targeting the case where the victim's head commit itself is reachable/pushed into the attacker's own repo (e.g., attacker forked the victim repo, so many shas are trivially identical). Attacker cost is a single crafted signed HTTP POST to `/webhooks`; no secrets, sessions, or team membership are required. This is feasible and repeatable for any attacker who can get commit-sha overlap with a target stack's queue, which is a realistic condition for open-source forks feeding a shared merge queue.

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` (and equivalently in any other sha-keyed handler, e.g. check-run handlers) to the stacks belonging to the reporting repository, mirroring `Handler#stacks`:
```ruby
def process
  stacks.flat_map { |stack| stack.commits.where(sha: params.sha) }.each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This enforces that a status webhook can only ever affect commits under the repository that actually sent (and signed) it, closing the cross-repository sha-collision vector.

### Proof of Concept
Minitest plan (no live GitHub calls):
```ruby
test "cross-repo status webhook cannot flip an unrelated stack's merge request to mergeable" do
  victim_stack = shipit_stacks(:shipit)
  attacker_stack = create_stack(repository: create_repository(owner: 'attacker', name: 'evil-fork'))

  shared_sha = 'a' * 40
  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: 'victim commit')
  attacker_stack.commits.create!(sha: shared_sha, message: 'attacker commit') # sha collision

  merge_request = victim_stack.merge_requests.create!(number: 42, head: victim_commit, merge_status: 'pending')

  # Binding under test, BEFORE:
  assert_equal false, merge_request.all_status_checks_passed?

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => victim_stack.cached_deploy_spec.merge_request_required_statuses.first, # required context
    'repository' => { 'full_name' => 'attacker/evil-fork', 'owner' => { 'login' => 'attacker' } }
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(payload) # simulates the attacker's signed webhook

  # Binding under test, AFTER — must remain false; currently flips to true (the bug):
  assert_equal false, merge_request.reload.all_status_checks_passed?

  Shipit::Stack.any_instance.expects(:github_api).never # merge_pull_request must not be reachable
  Shipit::ProcessMergeRequestsJob.perform_now(victim_stack)
end
```
This demonstrates that `Commit.where(sha: params.sha)` in `StatusHandler#process` matches the victim's `Commit` row despite the webhook payload naming `attacker/evil-fork`, and that the resulting forged `Status` is what flips `all_status_checks_passed?` and would drive `merge_request.merge!` → `stack.github_api.merge_pull_request` for the victim's repository.     def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?
      end

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end
    end
  end
