## Title
Missing newline (`\n`) validation of `feed_name`/`value` in `in data feed` / `data_feed` oscript conditions allows delimiter-injection bypass of oracle attestation checks - ([File: definition.js])

## Summary
Ocore's data-feed storage uses a line-based key protocol in `kvstore`, delimiting `address`, `feed_name`, `type`, `value` and `mci` with literal `'\n'` characters. When an actual `data_feed` message is *posted*, the validator strictly rejects any `feed_name` or string `value` containing `\n` (`validation.js`, `aa_validation.js`). However, when a `feed_name`/`value` is used on the *reading* side — inside an address/AA definition's `in data feed` condition, or an oscript/AA formula's `data_feed`/`data_feed_exists` operator — no such `\n` check is performed. This asymmetry is the same class of bug as CVE-2024-52006: a delimiter-based protocol is protected against newline injection on one side (the writer) but not the other (the reader/query builder), letting an attacker-controlled string blur the field boundaries and match unintended keys.

## Finding Description
Data feeds are persisted with `\n`-delimited composite keys:
```
'df\n'+address+'\n'+feed_name+'\ns\n'+strValue+'\n'+strMci   // or n\n... for numeric
``` [1](#0-0) 

Writing enforces that `feed_name` and `value` cannot contain `\n` for actually-posted `data_feed` messages: [2](#0-1) 
and the equivalent check exists for AA `data_feed` messages in `aa_validation.js`: [3](#0-2) 

But the *query side* — where an address (or AA) definition specifies an `in data feed` condition that will later be checked against the kvstore via `dataFeeds.dataFeedExists`/`dataFeedByAddressExists` — never rejects `\n` in `feed_name` or `value`: [4](#0-3) 

The same gap exists in the oscript/AA-formula validators for the `data_feed` and `data_feed_exists` operators, which only check `value.trim() === ''`, never `\n`: [5](#0-4) 

At evaluation/spend time, the attacker-controlled `feed_name`/`value` from the definition/formula is concatenated verbatim into the `\n`-delimited kvstore key/range used to look up a *real* oracle-posted record: [6](#0-5) 

Because real posted keys never contain an embedded `\n` inside the `feed_name` segment (that's enforced only on the write side), but the reader's `feed_name` can, an attacker can embed the delimiter plus a crafted `type`/`value` suffix directly inside their own `feed_name` argument. This shifts the effective field boundaries of the constructed `key_prefix`/range (`gte`/`lte`/`gt`/`lt`), so the range query no longer represents "oracle posted `feed_name`=`X` with `value` related to `Y`" but instead can be widened/shifted to match a *different*, unrelated, already-existing record from the same oracle address — decoupling the "in data feed" check from its intended semantic meaning (a specific future oracle attestation).

## Impact Explanation
An `in data feed` (or AA `data_feed`/`data_feed_exists`) condition is the standard oscript primitive used to gate spending on an oracle's future attestation (e.g. escrow: "payer can reclaim funds only if oracle posts `delivery_failed`=`yes`", or asset/AA logic gated on price feeds). By exploiting the missing `\n` validation on the condition-defining side, the address/AA definer (who is also typically the party trying to satisfy the condition prematurely) can construct a `feed_name`/`value` pair that causes the lookup to match an unrelated, already-existing data-feed record from the named oracle address instead of requiring the oracle to actually post the intended attestation. This directly enables unauthorized spending of funds protected by such a condition (the "wait for oracle to confirm X" guarantee is bypassed), and can similarly corrupt AA logic that treats `data_feed`/`data_feed_exists` results as trusted external input, leading to fund loss/freezing in AAs that gate payouts on oracle data.

## Likelihood Explanation
The condition (`feed_name`, `value`, `relation`) inside an `in data feed` clause, and the arguments to the `data_feed`/`data_feed_exists` oscript operators, are fully attacker-controlled at definition time — no privileged role is required. Any user can post a unit defining such an address/AA and then trigger a spend attempting to satisfy the condition using a crafted key. This is reachable purely from posting units/AA triggers, matching the "unprivileged unit poster / AA author / AA trigger sender" reachability bar.

## Recommendation
Add the same `\n`-rejection check that already exists for posted `data_feed` message payloads (`validation.js`/`aa_validation.js`) to:
- `definition.js`'s `evaluate()` handling of `'in data feed'` (reject `feed_name`/string `value` containing `\n`), and
- `formula/validation.js`'s `validateDataFeed`/`validateDataFeedExists` (reject `feed_name`/`feed_value` string containing `\n`).

Additionally, harden `data_feeds.js` key-construction functions (`dataFeedByAddressExists`, `readDataFeedByAddress`) to defensively reject/escape `\n` in the `feed_name`/`value` inputs regardless of caller, so the kvstore key structure can never be manipulated via field-boundary confusion.

## Proof of Concept
1. Oracle address `ORACLE` posts, at some point in the past, an unrelated data feed message `{"unrelated_feed": "some_value"}`, creating kvstore key `df\nORACLE\nunrelated_feed\ns\nsome_value\n<strMci1>`. [1](#0-0) 
2. Attacker defines an address (or AA) with condition:
   `["in data feed", [["ORACLE"], "unrelated_feed\ns\nsome_value", ">=", "", 0]]`
   This passes `definition.js` validation because there is no `\n` rejection for `feed_name`, only a length check. [7](#0-6) 
3. At spend time, `dataFeeds.dataFeedByAddressExists('ORACLE', "unrelated_feed\ns\nsome_value", '>=', "", ...)` builds `key_prefix = 'df\nORACLE\nunrelated_feed\ns\nsome_value\n'+prefixed_value` and issues a `gte`/`lt` range query against kvstore. [8](#0-7) 
4. Because the attacker's `feed_name` already reproduces the real `feed_name`, `type`, and `value` segments of the unrelated, already-existing key, the constructed range matches the pre-existing `unrelated_feed` record, satisfying the condition — even though the oracle never posted anything semantically related to the attacker's intended condition, letting the attacker spend funds meant to be gated on a distinct future oracle attestation.

function validateDataFeed(params) {
	var complexity = 1;
	if (params.oracles && params.feed_name) {
		for (var name in params) {
			var operator = params[name].operator;
			var value = params[name].value;
			if (Decimal.isDecimal(value)){
				if (!isFiniteDecimal(value))
					return {error: 'not finite', complexity};
				value = toDoubleRange(value).toString();
			}
			if (operator !== '=') return {error: 'not =', complexity};
			if (['oracles', 'feed_name', 'min_mci', 'feed_value', 'ifseveral', 'ifnone', 'what', 'type'].indexOf(name) === -1)
				return {error: 'unknown df param: ' + name, complexity};
			if (typeof value !== 'string')
				continue;
			switch (name) {
				case 'oracles':
					if (value.trim() === '') return {error: 'empty oracle', complexity};
					var addresses = value.split(':');
					if (addresses.length === 0) return {error: 'empty oracle list', complexity};
				//	complexity += addresses.length;
					if (!addresses.every(ValidationUtils.isValidAddress)) return {error: 'oracle address not valid', complexity};
					break;

				case 'feed_name':
					if (value.trim() === '') return {error: 'empty feed name', complexity};
					break;

				case 'min_mci':
					if (!(/^\d+$/.test(value) && ValidationUtils.isNonnegativeInteger(parseInt(value)))) return {
						error: 'bad min_mci',
						complexity
					};
					break;

				case 'feed_value':
					break;
				case 'ifseveral':
					if (!(value === 'last' || value === 'abort')) return {error: 'bad ifseveral: ' + value, complexity};
					break;
				case 'ifnone':
					break;
				case 'what':
					if (!(value === 'value' || value === 'unit')) return {error: 'bad what: ' + value, complexity};
					break;
				case 'type':
					if (!(value === 'string' || value === 'auto')) return {error: 'bad df type: ' + value, complexity};
					break;
				default:
					throw Error("unrecognized name after checking: "+name);
			}
		}
		return {error: false, complexity};
	} else {
		return {error: 'no oracles or feed name', complexity};
	}
}
