### Title
`StatusHandler#process` writes GitHub commit statuses without repository scoping, allowing cross-repository status forgery - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits by `sha` alone (`Commit.where(sha: params.sha)`) with no repository/stack filter, unlike `PushHandler` which scopes through `stacks` (derived from the webhook payload's `repository.full_name`). Because git commit SHAs are frequently shared across repositories (forks, mirrors, cherry-picks of the same tree), a correctly-signed `status` webhook from an attacker-owned repository can write a forged `success`/`failure` status onto a `Commit` row belonging to a completely unrelated victim `Stack`.

### Finding Description
Broken binding: `commit.stack_id == repository_that_authenticated_this_webhook.stack_id` is assumed but never checked in `StatusHandler#process`.

- `WebhooksController#verify_signature` validates the HMAC signature against `Shipit.github(organization: repository_owner)`, i.e. it only proves the request originated from GitHub for the *attacker's own* org/repo — it says nothing about which `Commit` rows the payload is allowed to touch. [1](#0-0) 
- `Handler` base class exposes a repo-scoped `stacks` helper (`Repository.from_github_repo_name(repository_name)&.stacks`) that other handlers such as `PushHandler` correctly use to scope their side effects to the stacks belonging to the reporting repository. [2](#0-1) [3](#0-2) 
- `StatusHandler#process` ignores this helper entirely and instead runs a global, unscoped lookup: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`. [4](#0-3) 
- `create_status_from_github!` writes a new `Status` row for every matching `Commit`, regardless of which repository's stack it belongs to. [5](#0-4) 

Exploit flow: an attacker forks (or otherwise obtains a repository containing) a commit whose SHA is already present in a victim `Stack`'s commit history (trivial via GitHub fork, since forking preserves SHAs). The attacker's own repo has a legitimate GitHub App/webhook installation (they own it), so GitHub itself computes a valid signature for a `status` event the attacker triggers on their own repo/commit (e.g., via the Statuses API on their fork, or a CI run against the shared SHA) with `state: success`. This event passes `verify_signature` (correctly, since it truly came from GitHub for the attacker's org) and reaches `StatusHandler#process`, which then writes a `success` status onto the victim's `Commit` record sharing that SHA — a write the victim's repository never authenticated.

Correction to the deploy-trigger mechanism named in the question: `Commit#schedule_continuous_delivery` is wired as `after_commit ..., on: :create` [6](#0-5) , meaning it fires only once, at the moment the `Commit` row is created (via push/sync), never when a later `status` webhook mutates an existing commit's statuses. `StatusHandler#process` only calls `create_status_from_github!`, which never creates a `Commit`, so this specific callback is **not** re-triggered by repeated status-webhook exploitation. The claimed direct chain "`StatusHandler#process` → `Commit#schedule_continuous_delivery` → `ContinuousDeliveryJob`" does not fire as described.

There is, however, a real (different) path to the same impact: the periodic cron task `Stack.schedule_continuous_delivery`, run every minute independent of any commit event, enqueues `ContinuousDeliveryJob.perform_later(stack)` for every `not_archived` stack with `continuous_deployment: true` [7](#0-6) [8](#0-7) . `ContinuousDeliveryJob#perform` then calls `stack.trigger_continuous_delivery`, which selects `next_commit_to_deploy` via `deployable_commits`, which calls `Commit#deployable?` (`!locked? && (stack.ignore_ci? || (success? && !blocked?))`) [9](#0-8) . If the victim's most recent undeployed commit was forged to `success` by the cross-repo write above, this cron-driven path can pick it up on its own schedule and call `trigger_deploy`, running a real `Deploy` task for the victim stack. This is gated by `stack.continuous_deployment?` being enabled on the victim (a pre-existing, attacker-uncontrolled but publicly discoverable config, per the question's own framing) and by no other blocking condition (`deployed_too_recently?`, `checks?`, `commit.deploy_failed?`, etc. in `should_resume_continuous_delivery?`/`should_delay_continuous_delivery?`).

### Impact Explanation
The confirmed vulnerability is: an unauthenticated write of a `Status` row onto a victim `Commit`/`Stack` from a payload the victim repository never authenticated — matching "a payload for one repository mutating another's stack, commit, task or team" (Critical). This can silently mark backlog commits `success`, unblock branch-protection-style gating logic (`Commit#blocked?`, `Stack#branch_status`, `Stack#merge_status`) and, when combined with the independently-running `Stack.schedule_continuous_delivery` cron and `continuous_deployment` being enabled on the victim, can cause the victim's stack to deploy a commit whose CI never actually passed on the victim's own repository — an unauthorized deploy trigger. This is repeatable against any stack whose commits share a SHA reachable by the attacker (trivially satisfied via forking any public repo tracked by Shipit), and scales to "an arbitrary number of victim Stacks" whose commits share SHAs with attacker-controlled repositories.

The specific mechanism named in the question — direct enqueue of `ContinuousDeliveryJob` from `Commit#schedule_continuous_delivery` as a consequence of a status webhook — does **not** occur, because that callback is `on: :create` only and is not re-invoked by subsequent status mutations.

### Likelihood Explanation
Preconditions: (1) a `Commit` in some victim `Stack` shares a SHA with a repository the attacker controls (satisfied for essentially any fork relationship, which requires no privilege); (2) the attacker's own repository has the Shipit GitHub App/webhook installed so GitHub signs the event — since GitHub itself computes the signature per the app's real secret, the attacker never needs to know the secret. Cost to the attacker is minimal: fork a tracked repo, or push a status via GitHub's own API on a repo they own for a shared SHA. For the deploy-escalation portion, the victim must additionally have `continuous_deployment: true`, which the question states is discoverable on public Shipit stack pages, and the cron path runs unconditionally every minute.

### Recommendation
Scope `StatusHandler#process` (and any similar handler) to only the commits belonging to the stacks of the repository that authenticated the webhook, mirroring `PushHandler`'s use of the `stacks` helper, e.g. `stacks.commits.where(sha: params.sha)` instead of the global `Commit.where(sha: params.sha)`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "process does not update commits belonging to a different repository sharing the same sha" do
  victim_repo  = create(:repository, owner: 'victim-org', name: 'victim-repo')
  victim_stack = create(:stack, repository: victim_repo, continuous_deployment: true)
  shared_sha   = 'a' * 40
  victim_commit = create(:commit, stack: victim_stack, sha: shared_sha)

  attacker_repo = create(:repository, owner: 'attacker-org', name: 'attacker-fork')

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'ci',
    'repository' => { 'full_name' => attacker_repo.github_repo_name }
  }

  assert_no_difference -> { victim_commit.statuses.count } do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end
end
```
Given the current implementation of `StatusHandler#process` (`Commit.where(sha: params.sha)`), this assertion fails, demonstrating the cross-repository write. A corollary test (not asserting the exact `Commit#schedule_continuous_delivery` path, which is confirmed unreachable) would instead assert `Shipit::ContinuousDeliveryJob` is not queued directly as a side-effect of `StatusHandler.call`, which currently passes — confirming the question's specific claimed mechanism does not fire, while the underlying cross-repo status-write vulnerability is real and separately reportable.
