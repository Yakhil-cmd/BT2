### Title
Webhook signature verification is keyed by attacker-controlled `repository.owner.login`, decoupling the authenticated GitHub organization from the repository actually acted upon - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp`/`webhook_secret` to validate the request against using `repository_owner`, a value read straight out of the unverified JSON body, while the downstream handlers act on a separate field, `repository.full_name`, taken from the same unverified body. [1](#0-0) [2](#0-1) [3](#0-2)  In a multi-organization deployment, an organization entry with no `webhook_secret` configured causes signature verification to be unconditionally bypassed for that org selector, per `GitHubApp#verify_webhook_signature`'s `return true unless webhook_secret` short-circuit. [4](#0-3) 

### Finding Description
This is the analog of the "partial trading" bug class: the report's `Lien.sol` used `sqrtPriceLimitX96` as a loose, "partial" bound while the strict guarantee (`amountOutMinimum`) was left at 0, letting an attacker satisfy the weak check while the actually-executed trade diverged from what the user believed was protected. Here the equivalent binding is: `organization used to select webhook_secret == organization that owns the repository actually mutated`. That equality is never enforced.

`WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` — a field read out of the raw, attacker-suppliable JSON body before any cryptographic check has succeeded — and uses it purely to pick which configured `GitHubApp` (and thus which `webhook_secret`) to validate the `X-Hub-Signature` against:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
``` [5](#0-4) 

The handlers that actually execute the event, however, resolve the target `Stack`/`Repository` from a *different* JSON field, `repository.full_name`:

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

Both `repository.owner.login` and `repository.full_name` come from the same unsigned-until-verified body, so nothing enforces that they name the same organization. `Shipit.github_app_config` looks up the org config by the `organization` argument passed to `Shipit.github`, in a case-insensitive, per-key manner: [6](#0-5)  and `GitHubApp#verify_webhook_signature` returns `true` without any cryptographic check whenever that org's `webhook_secret` is blank/nil: [4](#0-3) 

Concretely, the documented multi-org configuration schema explicitly allows per-organization `webhook_secret` entries, and it is entirely plausible (and shown blank in the shipped example) for one org to be left with `webhook_secret: nil` while another org in the same install has a real secret configured: [7](#0-6)  If a Shipit instance is configured for multiple organizations and any one of them has no `webhook_secret` set, an attacker who knows only that unconfigured org's name can craft a POST to `/webhooks` with:
- `X-Github-Event: push`
- `repository.owner.login = "<org-with-blank-secret>"` (selects the org whose secret check is a no-op)
- `repository.full_name = "<victim-org>/<victim-repo>"` (the actual target acted upon downstream)
- No valid `X-Hub-Signature` needed at all, since `verify_webhook_signature` short-circuits to `true`.

`verify_signature` passes unconditionally, `PushHandler` resolves `stacks` via `Repository.from_github_repo_name("<victim-org>/<victim-repo>")`, matched purely by the `owner`/`name` columns in the DB with no relation back to which GitHub App/organization actually authenticated the request: [8](#0-7)  and enqueues a `GithubSyncJob` that fetches commits/pushes state for that stack using `stack.github_api`, ultimately calling GitHub with the *victim* organization's own app credentials (since `Repository#github_app` is derived from `owner`, not from the value used at the webhook boundary): [9](#0-8) [10](#0-9) 

The root cause is exactly analogous to the reported bug class: a strict, cryptographically-verified check (`amountOutMinimum` / here, per-org `webhook_secret` HMAC) is bound to one field (`sqrtPriceLimitX96` / here, `repository.owner.login`), while the actually-executed side effect operates on a different, unchecked field (partial trade outcome / here, `repository.full_name`), letting an attacker satisfy the weak/absent bound while diverging the executed action from what was nominally protected.

### Impact Explanation
This breaks the equality "organization whose webhook_secret authenticated the request == repository written to by the resulting handler." An unprivileged, unauthenticated network attacker can forge push/status/check_suite/pull_request events for any repository belonging to a *victim* organization configured in the same Shipit instance, as long as at least one *other* configured organization in that instance has no `webhook_secret` set. This can trigger `GithubSyncJob` fetches, commit deployment status writes, and other webhook-driven side effects (e.g., pull request label handlers, membership/team creation via the `membership` event) against a repository/organization the attacker does not control and did not sign for — a cross-organization write triggered without valid authentication for the target org. This maps to the report's "Critical: cross-repository writes/unauthorized deploy" tier, since deploy-triggering GitHub sync and commit/state mutation for the victim stack can be forced by an attacker who never possessed the victim's `webhook_secret`.

### Likelihood Explanation
Requires: (1) a Shipit deployment configured for multiple GitHub organizations (the documented, supported multi-org schema), and (2) at least one configured organization with a blank/unset `webhook_secret`. The setup docs and shipped example configs literally template `webhook_secret: # nil` for each org, making an accidentally- or intentionally-unset secret on one org in a multi-org install plausible. [11](#0-10) [12](#0-11)  No credentials, session, or write access to GitHub are required; only knowledge of the weakly-configured organization's name and the victim's repository full name.

### Recommendation
- Derive the organization used for signature verification from configuration/routing that cannot be spoofed by the request body alone, or verify the signature against *every* configured organization's secret and require a match, rather than trusting `repository.owner.login`/`organization.login` from the payload to select the verifying secret.
- After signature verification succeeds, assert that the authenticated organization matches the owner embedded in `repository.full_name` before dispatching to handlers (i.e., enforce `repository_owner == repository.full_name.split('/').first`).
- Do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is blank in a multi-organization configuration; require every organization entry to define a secret, or refuse to process events for organizations without one.

### Proof of Concept
1. Configure Shipit with two organizations: `victim-org` (has a real `webhook_secret`) and `attacker-org` (leaves `webhook_secret` unset/nil), per the documented multi-org schema. [7](#0-6) 
2. Send `POST /webhooks` with header `X-Github-Event: push` and no valid `X-Hub-Signature`, body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and `verify_webhook_signature` returns `true` immediately because that org's `webhook_secret` is blank. [1](#0-0) [4](#0-3) 
4. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github(expected_head_sha:)`, enqueueing `GithubSyncJob` against the victim's stack using the victim organization's own GitHub App credentials, without ever presenting a valid signature for `victim-org`. [13](#0-12) [8](#0-7)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

      handle_github_errors do

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS

        end

            append_commit(gh_commit)
          end
