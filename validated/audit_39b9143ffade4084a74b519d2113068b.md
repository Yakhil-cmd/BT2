### Title
Asset attestor list can be changed by the definer after issuance, freezing already-issued spender_attested tokens - (File: validation.js, storage.js)

### Summary
For assets defined with `spender_attested: true`, the definer publishes an `asset_attestors` message listing which addresses are trusted attestors. Unlike `issue_condition`/`transfer_condition`, which are fixed forever inside the `asset` message itself, the attestor list is a separate, freely-resettable message that the definer can post at any time, with no restriction requiring it be set only once, and with eligibility always evaluated against the *latest* list rather than the list in force when the coins were issued/received.

### Finding Description
`validateAttestorListUpdate` in [1](#0-0)  only checks that the message is single-authored, well-formed, that the asset actually requires attestors, and that the sender is the asset's `definer_address`. It contains no check preventing the definer from replacing the attestor list arbitrarily many times, and no linkage to a specific point in time or to addresses already holding the asset.

When any subsequent payment of that asset is validated, `storage.readAsset` fetches attestors via `addAttestorsIfNecessary`, which explicitly picks the **most recent** `asset_attestors` unit before the current last ball, not the list that was active when a given holder acquired their coins: [2](#0-1) . The attested status is then re-checked live for both issuers and every input/output owner in `validatePayment` and `validatePaymentInputsAndOutputs`: [3](#0-2) [4](#0-3) [5](#0-4) .

Because this check re-evaluates against whatever the *current* attestor list is, a definer can:
1. Issue a `spender_attested` asset with an initial, permissive attestor list, attracting holders/counterparties who verify they satisfy the condition at receipt time.
2. Once value has flowed to those holders, post a new `asset_attestors` message that removes those addresses (or narrows attestation to addresses only the definer controls).
3. From that point on, none of the existing holders can pass the `attested` check as an input owner, and — for divisible assets — outputs must also go to currently-attested addresses (`filterAttestedAddresses`), so previously legitimate holders can no longer move or receive the asset at all.

This is the direct analog of the reported Solidity issue: a parameter that governs eligibility/conditions of an ongoing financial arrangement (there: Dutch-auction pricing; here: which addresses may hold/transfer the asset) is left mutable indefinitely by a privileged party, and is checked against its *current* value rather than being locked in at the time counterparties committed funds. Just as the auction owner could retroactively manipulate price after buyers had already committed, the asset definer can retroactively manipulate spending eligibility after holders have already received/committed the asset.

### Impact Explanation
An asset definer (a role reachable by any ordinary user who defines an asset — no special "operator" privilege) can weaponize the mutable attestor list to freeze already-issued coins belonging to unprivileged private-payment counterparties/asset holders at will, at any point after issuance, with no limitation on frequency or timing. This is effectively unrecoverable fund freezing for holders who relied on the attestor state that existed when they accepted the asset, since checks are always re-evaluated against the newest list rather than any list committed to at transfer time. For `is_private && fixed_denominations` "coin"-style assets in particular, the recipient has no on-chain way to know that a subsequent `asset_attestors` unit will retroactively invalidate their holdings.

### Likelihood Explanation
Likelihood is high: any account can freely become an asset definer, define a `spender_attested` asset (a normal, documented asset type), and later broadcast a single `asset_attestors` unit signed by the definer's own key to swap out the attestor list. No collusion, governance vote, race condition, or additional privilege is required — only a signed unit from the address that is already, by design, allowed to update this field, and the update logic itself imposes no cooldown or one-time-set constraint (contrast with `checkAttestorList`, which only validates array shape/sorting/length, not update frequency): [6](#0-5) .

### Recommendation
Bind attestation eligibility for a given payment to the attestor list that was current at the time the spent output was created (or require attestation to be re-verified/opt-in by the counterparty at receipt time and cached with the output), rather than always re-resolving to the latest `asset_attestors` unit at spend time. At minimum, disclose/lock the attestor list's mutability window (e.g., require a minimum stability delay or a maximum number of updates), and consider requiring that any address removed from the attestor list retain a grace period or an escape hatch (e.g., ability to redeem/exchange to the definer or convert to an unattested state) so that value already transferred under a prior attestor list cannot be unilaterally frozen.

### Proof of Concept
1. Definer `D` issues asset `A` with `spender_attested: true`, `is_private: true`, `fixed_denominations: true`, and initially posts `asset_attestors` listing attestor `X`.
2. `D` transacts with counterparty `C`; `C` is attested by `X` at the time and receives coins of asset `A`, believing the coins are freely spendable per the current attestor list — see the live-checked `spender_attested` gate in `validatePayment`: [3](#0-2) .
3. After `C` holds the coins, `D` posts a new `asset_attestors` message removing `X` (or listing only an attestor controlled by `D`), which passes `validateAttestorListUpdate` unconditionally since there is no "set once" restriction: [1](#0-0) .
4. `storage.readAsset`/`addAttestorsIfNecessary` now resolves the "latest" attestor list to the new one for any future validation: [2](#0-1) .
5. Any subsequent attempt by `C` to spend the coins fails validation because `arrAttestedAddresses` no longer contains `C` (`filterAttestedAddresses` / `owner address is not attested`): [5](#0-4) [4](#0-3) , permanently freezing `C`'s coins even though `C` acquired them legitimately under the attestor list in force at the time.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}

function checkAttestorList(arrAttestors){
	if (!isNonemptyArray(arrAttestors))
		return "attestors not defined";
	if (arrAttestors.length > constants.MAX_ATTESTORS_PER_ASSET)
		return "too many attestors";
	var prev="";
	for (var i=0; i<arrAttestors.length; i++){
		if (!isValidAddress(arrAttestors[i]))
			return "invalid attestor address: "+JSON.stringify(arrAttestors[i]);
		if (arrAttestors[i] <= prev)
			return "attestors not sorted";
		prev = arrAttestors[i];
	}
	return null;
}
