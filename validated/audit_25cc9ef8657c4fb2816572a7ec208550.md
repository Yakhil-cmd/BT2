### Title
Webhook signature verification keys off `repository.owner.login`/`organization.login` while event handlers act on the unrelated `repository.full_name` field, allowing cross-organization forged webhooks in multi-app deployments - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In multi-GitHub-App deployments, `WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate the HMAC signature against using a field taken from the *same untrusted request body* (`repository.owner.login`, falling back to `organization.login`). The actual repository/stack acted upon by every event handler is derived from a *different* field of that same body, `repository.full_name`. Nothing ties these two fields together, so an attacker who legitimately controls one configured GitHub organization (and therefore knows/controls that organization's `webhook_secret`) can forge a signed payload whose `repository.owner.login` matches their own org (to pass signature verification) but whose `repository.full_name` points at a stack belonging to a completely different, victim organization tracked by the same Shipit instance.

### Finding Description
`verify_signature` picks the verification key using attacker-controlled data: [1](#0-0) [2](#0-1) 

```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization:)` looks up a **per-organization** `webhook_secret` when Shipit is configured for multiple GitHub Apps (documented in `docs/setup.md`, "Using Multiple Github Applications"): [3](#0-2) 

Once the signature check passes, the raw body is re-parsed and dispatched to handlers, all of which resolve the target repository/stack via `repository.full_name`, not `repository.owner.login`: [4](#0-3) [5](#0-4) 

Because HMAC validation only proves "this body was signed with organization X's secret," and `repository.owner.login` and `repository.full_name` are independent, attacker-controlled JSON keys in the very same unverified-until-checked body, nothing prevents an attacker from setting `repository.owner.login = "attacker-org"` (to select their own known secret) while setting `repository.full_name = "victim-org/some-repo"` (to target another tenant's Stack). This is the "organization that authenticated versus the repository that is written" binding break: the equality `authenticated_org == acted_upon_repo.owner` is never enforced.

Concretely reachable handlers that write state keyed off `full_name`/branch:
- `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` for any stack under the victim's branch: [6](#0-5) 
- `StatusHandler#process` calls `commit.create_status_from_github!(params)` for any commit matching a forged `sha`, across all stacks in the DB (not even scoped by repository, only by `Commit.where(sha:)`): [7](#0-6) 
- `CheckSuiteHandler#process` reschedules check-run refresh for arbitrary stacks: [8](#0-7) 

### Impact Explanation
The `status` handler is the most severe path: it lets an attacker fabricate a green/success commit status for a commit belonging to a stack in a *different, unrelated organization*. `StatusHandler` looks up commits solely by `sha` with no repository scoping at all, so this crosses repository/organization boundaries entirely. Where a stack uses `status.context`/`release_status` gating combined with continuous delivery (`deploy.interval`, continuous deployment schedules), a forged "success" status can be used to unblock or trigger an unauthorized deploy of a victim's stack. This matches the required "cross-repository writes" / "unauthorized deploy" impact bar, achieved purely by an attacker's legitimate possession of their own org's webhook secret in a multi-tenant Shipit deployment — no privileged Shipit credential, `ApiClient` token, or GitHub App private key is required.

### Likelihood Explanation
This requires a Shipit deployment configured with multiple GitHub Apps/organizations (explicitly documented and supported: `docs/setup.md` lines 182-209), where at least one of those organizations is controlled by, or has compromised credentials known to, an attacker who is not authorized to interact with other tenants' repositories on the same instance. Given that this is a documented, supported multi-tenant configuration mode, and forging the payload requires only computing an HMAC-SHA1 over an arbitrary JSON body with a secret the attacker legitimately possesses, likelihood is moderate-to-high in any deployment that actually uses the multi-org feature.

### Recommendation
After signature verification succeeds, cross-check that the `repository_owner` (or `organization.login`) used to select the verifying secret matches the owner segment of `repository.full_name` (and any other repository identifiers used by handlers) before dispatching to handlers; reject the webhook (422) on mismatch. More robustly, resolve the target `Stack`/`Repository` first from `repository.full_name`, derive the organization to verify against from that resolved repository's own `owner` column (trusted, already-stored state) rather than from the unverified request body, and only then validate the signature.

### Proof of Concept
Preconditions: Shipit configured with `config/secrets.yml` `github:` block using the multi-organization schema, with at least `attacker-org` (secret known to the attacker, e.g. because they administer that GitHub App/org) and `victim-org` (tracked stack `victim-org/some-repo` with branch `main`).

1. Attacker crafts a `push` payload:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/some-repo"
  }
}
```
2. Attacker computes `sha1=HMAC(webhook_secret_of_attacker_org, raw_body)` and sends:
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=<computed>
<raw_body>
```
3. `verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `attacker-org`'s `webhook_secret`, and the signature validates successfully. [1](#0-0) 
4. `create` re-parses the body and dispatches to `PushHandler`, which resolves `repository_name = "victim-org/some-repo"` and enqueues a sync/deploy-affecting action for the victim's stack: [4](#0-3) [6](#0-5) 

The same technique with `X-Github-Event: status` and a known victim commit `sha` forges a fabricated CI status for the victim repository's commit, independent of any repository scoping. [7](#0-6)

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
