### Title
Webhook signature is verified against the organization named in the payload while the affected repository/stack is looked up from a separate, unbound payload field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the `X-Hub-Signature` HMAC against by reading `repository.owner.login` (or `organization.login`) directly out of the untrusted, not-yet-verified request body. Once the HMAC check passes, the event handlers (`Handler#stacks`, used by `PushHandler`, `CheckSuiteHandler`, etc.) resolve the actual `Stack`/`Repository` to act on from a *different* payload field, `repository.full_name`, with no re-check that this repository actually belongs to the organization whose secret validated the signature.

### Finding Description
In a multi-organization Shipit deployment (documented in `docs/setup.md` under "Using Multiple Github Applications"), each GitHub organization has its own `webhook_secret`. Verification is implemented as: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight from the JSON body via `params.dig('repository', 'owner', 'login')`, and `Shipit.github(organization: repository_owner)` picks the corresponding `GitHubApp` (and thus `webhook_secret`) to validate the raw body signature: [3](#0-2) [4](#0-3) 

After signature verification succeeds, the event is dispatched to handlers, which independently resolve which `Stack`s to act on using a *different* field of the same payload — `repository.full_name` — with no cross-check against the organization used for signature verification: [5](#0-4) [6](#0-5) [7](#0-6) 

The binding that should hold is: **organization whose secret authenticated the request == organization owning the repository whose stacks are mutated**. Because the two fields (`repository.owner.login` used for auth, `repository.full_name` used for the actual write/action) are read independently from the same attacker-controlled JSON body, and the signature only proves "some raw body was signed with Org A's secret," an attacker who legitimately possesses (or controls) a valid webhook secret for **their own** organization "Org A" (e.g., they installed their own GitHub App instance, which is explicitly a supported, low-privilege configuration in this multi-org design) can craft a payload where `repository.owner.login = "OrgA"` but `repository.full_name = "OrgB/target-repo"` — a repository/stack that belongs to a completely different organization "Org B" that they have no access to. The signature computed with Org A's secret over that crafted body will validate successfully, and the handler will then act on Org B's stack.

This is directly analogous to the reported Move bug class: a check is performed against one identity (organization owning the signature) while the actual state-changing action is applied to a different identity (the repository/stack named elsewhere in the same object), letting a "soft" boundary (owning your own org's webhook secret) be used to reach objects that should require a different, stronger credential (owning/controlling Org B).

### Impact Explanation
`PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` on any stack matched by `repository.full_name`, which can trigger a GitHub sync job for a stack that belongs to a wholly unrelated organization the attacker doesn't control. `CheckSuiteHandler` similarly schedules `RefreshCheckRunsJob` for that stack's commits. If `continuous_deployment` is enabled on the targeted stack, forcing an out-of-band sync can precipitate an unscheduled/unauthorized deploy trigger for that stack, and more generally allows an attacker to force read/refresh operations (repository state, CI status refresh) on stacks outside their authorization boundary — this satisfies the "unauthorized deploy" / "unauthenticated read of stack state" impact bar defined in scope, achieved purely by owning a webhook secret for an unrelated, attacker-controlled organization.

### Likelihood Explanation
Likelihood is Medium: it requires the multi-organization GitHub Apps configuration to be in use (a documented, supported deployment mode) and requires the attacker to control (or successfully register) at least one organization's GitHub App/webhook secret pointing at the shared Shipit instance — which is a comparatively low bar compared to compromising the target organization directly, since Shipit's webhook endpoint is shared across all configured organizations at a single `/webhooks` URL.

### Recommendation
After signature verification, re-derive/require that `repository.owner.login` (the field used to select the verifying secret) matches the organization portion of `repository.full_name` before dispatching to handlers, or better, bind the handler's `Repository.from_github_repo_name` lookup to the same verified organization used in `verify_signature`, rejecting the event if they diverge.

### Proof of Concept
1. Configure Shipit with two organizations in `config/secrets.yml`: `orgA` (attacker-controlled, e.g. attacker installs their own GitHub App and knows its `webhook_secret`) and `orgB` (victim, has a `Stack` for `orgB/target-repo`).
2. Attacker crafts a JSON push payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<any_sha>",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/target-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(orgA_webhook_secret, raw_body)` and POSTs to `/webhooks` with header `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "orgA")`, validates successfully against `orgA`'s secret [8](#0-7) .
5. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("orgB/target-repo")` [5](#0-4)  and invokes `stack.sync_github` on `orgB`'s stack, despite the attacker having no credentials for `orgB`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end
```
