### Title
Missing cosigner authorization check in device "sign" handler lets any paired (correspondent) device request signing of a local wallet's own addresses - ([File: wallet.js])

### Summary
CVE-2018-16883 is an sssd access-control failure where the `infopipe` D-Bus interface did not honor the `allowed_uids` restriction, letting local callers reach functionality that should have been limited to an approved set of principals. The structural analog in `ocore--005` is in `wallet.js`'s device-message handler for the `sign` subject: the check that verifies the requesting device is actually an authorized cosigner of the target address has been deliberately commented out, so the intended "allowed set" (cosigners only) is not enforced, and any paired correspondent device can invoke the local signing workflow for the user's own addresses.

### Finding Description
`wallet.js` processes device messages received via the hub in `handleMessageFromHub` / `doHandle`. The `case "sign":` branch [1](#0-0)  accepts a `{address, signing_path, unsigned_unit}` payload from `from_address` (any device that is a correspondent, not necessarily a cosigner of the target wallet), validates unit structure and payload hashes, and then calls `findAddress(body.address, body.signing_path, {...})`.

When the target address is one that the local device itself controls (`ifLocal`), the code was originally meant to verify that `from_address` is a legitimate cosigner of that wallet by querying `extended_pubkeys`, but this check is commented out: [2](#0-1) 

Without this check, `callbacks.ifOk()` is invoked unconditionally for ANY correspondent device sending a well-formed `sign` request naming any of the local wallet's `my_addresses` — even single-key addresses that are not shared/multisig at all, since `findAddress`'s `ifLocal` branch is reached for any row matched in `my_addresses`/`wallet_signing_paths` regardless of whether the wallet is genuinely a multi-device wallet [3](#0-2) . The handler then proceeds to compute the unit hash and either emits a `signing_request` event (for the wallet UI to display a signing/confirmation dialog) or runs the attacker-supplied unit through `network.handleOnlineJoint` before emitting `signing_request` on successful validation [4](#0-3) .

By contrast, the sibling `ifRemote` branch of the same handler does still enforce a correspondent allow-list, verifying `from_address` is present in `other_device_addresses` before proxying the signing request [5](#0-4) . This asymmetry confirms that an authorization check ("allowed cosigners") was intentionally present in the design for one code path but is not enforced in the `ifLocal` path — mirroring the CVE's root cause of an access-restriction parameter that exists conceptually but is not actually applied on one interface.

### Impact Explanation
Any device merely paired (a "correspondent") with the victim's wallet — not necessarily a genuine cosigner of any shared/multisig address — can push a `sign` device message naming one of the victim's own addresses and an attacker-crafted `unsigned_unit`/`private_payloads` describing a payment that spends the victim's coins to an address of the attacker's choosing. Because the authorization check for cosigner membership is disabled, this reaches the same code path as legitimate multi-device signing coordination and can drive the wallet UI into a "confirm and sign" workflow for a transaction the victim never initiated. If confirmed (a normal, expected user action for legitimate multi-device signing scenarios that this bug abuses), this results in unauthorized spending of the victim's funds — matching the "concrete unauthorized spending" impact bar. Even absent user confirmation, this exposes wallet address membership/behavior to unauthorized correspondents and lets them repeatedly trigger this workflow with attacker-chosen content, undermining the intended cosigner-only trust boundary.

### Likelihood Explanation
Any existing paired device (e.g., an old contact, a previously-approved chat correspondent, or one leg of an arbiter/prosaic contract) can trigger this without ever having been added as a wallet cosigner, since the code only checks that the device is a known correspondent at the hub-message layer, not that it is an authorized signer for the specific address. The comment in the source ("the commented check would make multilateral signing impossible") shows this was a conscious trade-off, but it broadens the trust boundary from "cosigners of this specific wallet" to "any correspondent of the device," which is a materially larger, attacker-influenced set.

### Recommendation
Reinstate an authorization check in the `ifLocal` branch of the `sign` handler that verifies `from_address` is listed as a legitimate device for the specific `wallet` associated with `body.address` (e.g., via `extended_pubkeys`/`wallet_signing_paths`) before calling `callbacks.ifOk()` and emitting `signing_request` or invoking `network.handleOnlineJoint`. If multilateral/dumb-contract signing genuinely requires accepting requests from non-cosigner correspondents, that use case should be distinguished explicitly (e.g., a dedicated flag/subject) rather than universally disabling the cosigner check for all local addresses, including single-key wallet addresses that have no legitimate reason to accept remote signing requests at all.

### Proof of Concept
1. Attacker device A pairs with victim device V (ordinary correspondent pairing, no special permissions).
2. V has a wallet with local address `ADDR` in `my_addresses` (single-key or as one branch of a shared address), and `signing_path` known/guessable (`r` or `r.N` patterns are predictable/enumerable).
3. A crafts an `unsigned_unit` whose `messages` include a `payment` app message with `outputs` sending V's balance to an attacker-controlled address, sets `authors: [{address: ADDR, authentifiers: {...}}]`, and computes matching `payload_hash`(es).
4. A sends a device message to V with `subject: "sign"`, `body: {address: ADDR, signing_path: "r", unsigned_unit: <crafted unit>}`.
5. On V, `handleMessageFromHub` reaches `case "sign"`, passes structural validation, calls `findAddress(ADDR, "r", ...)`, hits `ifLocal` (since V is the address' own device), and — because the cosigner check is commented out — calls `callbacks.ifOk()` and emits `signing_request` for V's UI to display a "confirm signing" dialog for the attacker's transaction, despite A never having been authorized as a cosigner of `ADDR`.

*Note: full exploitation to the point of broadcasting a signed unit still depends on the victim's UI confirming the request; this is inherent to any signing-request analysis in `ocore` and could not be independently exercised further here (e.g., I could not confirm from the available index whether any bot/headless wallet configuration auto-approves `signing_request` events, which would remove the user-confirmation dependency entirely).*
