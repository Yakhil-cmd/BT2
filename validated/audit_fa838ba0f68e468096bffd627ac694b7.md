### Title
Webhook signature verification selects the GitHub-org secret from an unverified `repository.owner.login`/`organization.login` field, letting a signature valid for one org authorize writes against a different org's repository/commit - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks which GitHub App config (and therefore which HMAC `webhook_secret`) to verify the request against using `repository_owner`, a value read straight out of the untrusted, not-yet-verified JSON body [1](#0-0) [2](#0-1) . Once the signature check passes, the actual event handlers (`PushHandler`, `StatusHandler`, `PullRequest::OpenedHandler`, `CheckSuiteHandler`) act on a *different* field of the same body — `repository.full_name` or a bare `sha` lookup with no owner scoping at all [3](#0-2) [4](#0-3) . Nothing cross-checks that the org whose secret validated the signature is the same org/repository the handler subsequently mutates.

### Finding Description
The binding that should hold is: **organization authenticated by `verify_signature` == repository/organization actually written by the handler**. This binding is broken:

- `verify_signature` resolves `Shipit.github(organization: repository_owner)` and calls `verify_webhook_signature` with that org's config [1](#0-0) .
- `repository_owner` is computed from the raw, unverified body: `params.dig('repository','owner','login') || params.dig('organization','login')` [2](#0-1) .
- `verify_webhook_signature` in `lib/shipit/github_app.rb` has a documented escape hatch: `return true unless webhook_secret` [5](#0-4) . A per-org `webhook_secret` of `nil` is an explicitly supported configuration value, shown in the shipped template `config/secrets.development.shopify.yml` (`webhook_secret: # nil`).
- The `create` action then dispatches the entire raw body to handlers keyed only by event type, with no re-validation that the handler's target repository matches `repository_owner` [6](#0-5) .
- `PushHandler`/`PullRequest` handlers resolve the target repository via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` — a separate JSON key from the one used to pick the verifying secret [4](#0-3) .
- `StatusHandler` is even weaker: it looks up `Commit.where(sha: params.sha)` globally, with no repository/org scoping whatsoever [3](#0-2) .

Consequently, an attacker who can get `repository_owner` to resolve to any org whose `webhook_secret` is blank (a supported, non-privileged configuration state — no secret, no session, no `ApiClient` token is required) trivially satisfies `verify_signature` for *that* org, then supplies a payload whose `repository.full_name` (push/pull_request/check_suite) or bare `sha` (status) targets a completely unrelated, protected organization/repository/commit tracked by the same Shipit instance. The signature only proves the request "belongs" to the org selected for verification; it proves nothing about the repository the handler subsequently mutates.

### Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" boundary explicitly called out as in-scope. Concretely:
- Forging a `status` event lets the attacker attach an arbitrary/fabricated commit status (e.g. `success`) to any commit SHA tracked by any stack in the instance, with no org/repo scoping check at all — this can be used to make a commit appear CI-green to satisfy Shipit's deploy-safety gating, contributing to an unauthorized deploy of a real commit.
- Forging `push`/`pull_request`/`check_suite` events lets the attacker cause Shipit to enqueue sync/refresh jobs (`GithubSyncJob`, `RefreshCheckRunsJob`) or run review-stack provisioning logic against a repository the attacker doesn't control, using the org's real, unrelated GitHub App credentials for the resulting API calls.

This is High severity: unauthenticated (no session, no `ApiClient` token, no knowledge of any org's real `webhook_secret`) cross-repository/cross-organization write into stack/commit state, contingent only on the deployment having at least one org configured without a `webhook_secret` — a state the code itself treats as valid (`return true unless webhook_secret`) rather than as a misconfiguration to reject.

### Likelihood Explanation
Likely in any multi-tenant Shipit deployment (multiple GitHub orgs configured in `secrets.yml`, as the engine explicitly supports via `Shipit.github(organization:)`) where at least one org's webhook integration was set up without a secret — exactly the state depicted in the shipped `config/secrets.development.shopify.yml` template. No credential, session, or privileged access is needed to exploit it once that precondition holds; the attacker just needs to know the name of the secret-less org and the target repository's `full_name` or a target commit SHA (both public GitHub information).

### Recommendation
Bind signature verification to the same identifier the handler will act on: verify the signature using the org/repository actually resolved by the handler (or, at minimum, require every configured GitHub App/org to have a non-blank `webhook_secret` and refuse to process events whose `repository.owner.login`/`organization.login` doesn't match the `repository.full_name`/derived owner used later). Remove or gate the `return true unless webhook_secret` bypass in `Shipit::GithubApp#verify_webhook_signature` so a missing secret fails closed instead of open.

### Proof of Concept
1. Deploy Shipit multi-tenant with two orgs configured: `no-secret-org` (webhook_secret left blank, as in the shipped template) and `victim-org` (with `victim-org/protected-repo` tracked as a stack).
2. POST to `/github_webhooks` (or configured mount) with header `X-Github-Event: status` and body:
   ```json
   { "sha": "<known-sha-of-a-commit-in-victim-org/protected-repo>",
     "state": "success",
     "repository": { "owner": { "login": "no-secret-org" } } }
   ```
   Any (or no) `X-Hub-Signature` value is accepted because `Shipit.github(organization: "no-secret-org")` has `webhook_secret` blank, making `verify_webhook_signature` return `true` unconditionally [5](#0-4) .
3. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and calls `create_status_from_github!`, writing a forged `success` status onto the victim commit with no relation to `no-secret-org` checked anywhere [3](#0-2) .

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
