## Finding

### Title
Fork PR label names inject arbitrary `PYTHONSTARTUP`/env vars into `dependencies.override` command execution via `ReviewStack#env` - ([File: lib/shipit/task_commands.rb])

### Summary
`ReviewStack#env` merges every PR label name (uppercased) into the environment hash with no allowlist, and `Command#install_dependencies` (in `TaskCommands`) passes the full, unfiltered `env` (including this label-derived hash) straight to `Command.new`, which is then merged onto `Command#unbundled_env` and passed to `PTY.spawn`. Since `Command#env` only casts values to strings but performs no key filtering, and `EnvironmentVariables.permit` (the only allowlist mechanism in this codebase) is never invoked in the `install_dependencies`/`dependencies.override` path, an attacker-controlled label such as `pythonstartup` becomes `PYTHONSTARTUP=true` in the child process environment for any python invoked by a `dependencies.override` step.

### Finding Description
The broken binding: `TaskCommands#install_dependencies` env passed to `Command.new` == `TaskCommands#env` (unfiltered), whereas the codebase's only sanitization primitive, `EnvironmentVariables.permit(variable_definitions)` [1](#0-0) , is applied only via `deploy_spec.filter_deploy_envs`/`filter_rollback_envs` for `deploy`/`rollback` variables [2](#0-1) , never for the dependencies phase.

Trace:
1. `ReviewStack#env` merges `pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" }` onto `super` with no key allowlist [3](#0-2) .
2. `LabelCapturingHandler#capture_labels` persists `params.pull_request.labels.map(&:name)` directly from the webhook payload with no sanitization of label text [4](#0-3) .
3. `TaskCommands#env` merges `@stack.env` (the ReviewStack's label-derived env) into the task environment [5](#0-4) .
4. `TaskCommands#install_dependencies` builds the dependencies-phase commands using this same unfiltered `env:` and `deploy_spec.dependencies_steps!` (which is `config('dependencies', 'override')`, i.e., the fork's `shipit.yml`) [6](#0-5) [7](#0-6) .
5. `Command#start` calls `PTY.spawn(unbundled_env, *interpolated_arguments, ...)` where `unbundled_env` merges `BASE_ENV` (derived from `Bundler.unbundled_env`/`ENV`) with `Shipit.shell_paths`/`PATH` and finally `@env.stringify_keys` — i.e., the attacker-supplied label-derived keys win on merge [8](#0-7) [9](#0-8) .

The exploit is: an unprivileged fork user opens a PR against a repository with `provisioning_behavior=allow_all` and `review_stacks_enabled`, adds a label named `pythonstartup` (case-insensitive, becomes `PYTHONSTARTUP`), and the fork's `shipit.yml` defines a `dependencies.override` step invoking `python`/`python3` (or any tool honoring `PYTHONSTARTUP`). When the deploy runs the dependencies phase, the interpreter reads `PYTHONSTARTUP` and executes the named file at startup.

Existing tests confirm the unfiltered label-merge behavior end-to-end: `TaskCommandsTest#env includes a ReviewStack's pull request labels` [10](#0-9)  and `DeployCommandsTest#env includes the stack's pull request labels` [11](#0-10) , and `ReviewStackTest#env includes the stack's pull request labels` [12](#0-11) , none of which exercise any allowlist because none exists on this path.

Why existing guards fail: `EnvironmentVariables.permit` exists and is exercised for `deploy`/`rollback`/`task` variable definitions [1](#0-0) , but `install_dependencies` never calls `filter_deploy_envs`/`filter_rollback_envs`/`permit` on the env before constructing `Command.new` [6](#0-5) . `Command#env=` only does `transform_values { |v| v&.to_s }` — no key filtering [13](#0-12) . Webhook signature verification, `respond_to_pull_request_opened?`/`allow_all` gating, and `Repository` validations govern *whether* a review stack is created/labeled, not *what characters or names* are allowed in a label — none of them constrain label content, and `allow_all` is a documented, common, supported configuration (the docs literally recommend it: "most likely Allow All") [14](#0-13) .

### Impact Explanation
This allows any unprivileged fork contributor to inject arbitrary environment variable names (uppercased) into the process environment of every command Shipit runs for that review stack's task/deploy, including the `dependencies.override` step defined by the fork's own `shipit.yml`. Combined with a `dependencies.override` step that invokes `python`, this yields execution of an attacker-named startup file at Python interpreter initialization — Remote Code Execution on the Shipit deploy host, matching the Critical impact category (`Command`/`PTY.spawn` RCE). The blast radius is scoped to the repository owning the review stack (its checkout, its `GITHUB_TOKEN` scope, and whatever host resources the deploy process can reach), but is fully repeatable per-PR/per-label-add on any repository configured with `allow_all` + review stacks enabled.

### Likelihood Explanation
Preconditions: repository has `review_stacks_enabled=true` and `provisioning_behavior=allow_all` (a supported, documented, and recommended configuration) [15](#0-14) , and the repository's `shipit.yml` `dependencies.override` (or discovered dependency steps) invoke an interpreter sensitive to an env var of the attacker's choosing (e.g., `python`). Attacker cost is trivial: open a PR from a fork and add a label with the target variable name (GitHub label names are attacker-controlled since the attacker owns the fork/PR). No secrets, sessions, or privileged roles are required. This is fully repeatable against any repository with this common configuration.

### Recommendation
Apply an explicit allowlist to the environment merged into `dependencies.override` (and any other phase) commands, analogous to `filter_deploy_envs`/`filter_rollback_envs`, so that `ReviewStack#env`'s label-derived keys go through `EnvironmentVariables.permit` against a defined variable list before reaching `Command.new`. Additionally, consider not merging raw, uppercased PR label names directly as env var names at all, or restricting them to a safe, non-shadowing prefix (e.g., `LABEL_<NAME>`) so they can never collide with sensitive interpreter/tooling variables like `PYTHONSTARTUP`, `LD_PRELOAD`, `BUNDLE_GEMFILE`, etc.

### Proof of Concept
```ruby
# test/lib/shipit/task_commands_test.rb (or a new test file)
test "#install_dependencies inherits attacker-controlled PYTHONSTARTUP from a PR label" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["pythonstartup"]
  task = shipit_tasks(:shipit_restart)
  task.stack = stack

  commands = Shipit::TaskCommands.new(task)
  commands.stubs(deploy_spec: stub(
    dependencies_steps!: ['python3 -c "pass"'],
    machine_env: {},
  ))

  dependency_command = commands.install_dependencies.first

  assert_equal "true", dependency_command.env["PYTHONSTARTUP"]
  # And, tracing into Command#unbundled_env, confirm it reaches the spawned process env:
  assert_equal "true", dependency_command.unbundled_env["PYTHONSTARTUP"]
end
```
This demonstrates the equality `dependency_command.env["PYTHONSTARTUP"] == "true"` and `dependency_command.unbundled_env["PYTHONSTARTUP"] == "true"`, proving the fork-controlled label reaches the env passed to `PTY.spawn` for the `dependencies.override` step, with no allowlist rejecting it.

    def start(&block)
      return if @started

      @control_block = block
      @out = @pid = nil
      FileUtils.mkdir_p(@chdir)
      begin
        @out, child_in, @pid = PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)
        child_in.close
      rescue Errno::ENOENT
        raise NotFound, "#{Shellwords.split(interpolated_arguments.first).first}: command not found"
      rescue Errno::EACCES
        raise Denied, "#{Shellwords.split(interpolated_arguments.first).first}: Permission denied"
      end
      @started = true
      self
    end
