### Title
Irregular indentation in `conditions:` block causes silent field-loss in `extract_frontmatter`, turning targeted secret-detection conditions into overly-broad (or, in edge cases, empty) matches - ([File: plugins/hookify/core/config_loader.py])

### Summary
`extract_frontmatter()`'s hand-rolled state machine only treats a continuation line as belonging to the current dict item when `indent > 2` [1](#0-0) . If a rule author (or an attacker crafting a `.local.md` rule file merged into the repo) writes `operator:`/`pattern:` continuation lines at an indent of ≤2 spaces (e.g., aligned flush with the leading `-`), those lines match none of the parser's branches and are silently discarded — no exception, no warning. The resulting `Condition` keeps only the `field` key, and `Condition.from_dict` fills `operator`/`pattern` with defaults (`'regex_match'`/`''`) [2](#0-1) .

### Finding Description
Trace: `load_rule_file` → `extract_frontmatter` → `Rule.from_dict` → `RuleEngine._rule_matches` [3](#0-2) [4](#0-3) .

For a conditions block such as:
```
conditions:
  - field: file_path
  operator: regex_match
  pattern: "\.env"
```
- `"  - field: file_path"` (indent=2) is recognized as a new list item, setting `in_dict_item=True`, `current_dict={'field':'file_path'}` [5](#0-4) .
- `"  operator: regex_match"` and `"  pattern: ..."` also have indent=2 (a very plausible mistake — aligning fields with the dash rather than with the text after it). Neither the top-level branch (`indent==0`) nor the list-item branch (`stripped.startswith('-')`) nor the continuation branch (`indent > 2`) matches at indent=2, so these lines fall through the entire `if/elif` chain and are silently dropped with no error [6](#0-5) .
- The final `Condition` becomes `{field: 'file_path', operator: 'regex_match' (default), pattern: '' (default)}`.

A regex pattern of `''` matches (`re.compile('').search(text)`) any non-`None` string, and `'' in text` is always `True` for the `contains` operator. So rather than the rule *never* firing (the specific false-negative the question hypothesizes), the more consistently reproducible outcome is that the condition becomes trivially always-true, and the rule fires on every event for that field (turning a targeted `.env`/`credentials` detector into a rule that blocks/warns on all matching-event operations). I was also able to trace a related, more severe variant: a stray zero-indent continuation line inside the conditions block (e.g. a dedented `pattern:` line) is misclassified by the `indent == 0` top-level-key branch, which both (a) prematurely closes the `conditions` list (setting `in_list = False`) and (b) silently drops *all subsequent* condition items in the block without any warning, since after `in_list` is cleared none of the remaining `- ...` lines match any branch. Depending on exactly where that stray line lands relative to the accumulated dict, this can produce an empty `conditions` list, which via `_rule_matches`'s explicit guard (`if not rule.conditions: return False`) makes the rule permanently inert. However, constructing a case where **every** condition dict ends up fully empty (rather than partially populated with defaulted `operator`/`pattern`) requires a more specific line arrangement, and I could not fully verify from the indexed code alone that this exact "all-conditions-empty" outcome is reliably reproducible for a *legitimate-looking* multi-condition secret-detection rule versus the more directly demonstrable "condition becomes always-true" outcome above.

### Impact Explanation
Both failure modes are security-relevant but in different directions:
- Field-loss producing a default empty pattern → condition matches everything → over-broad blocking/warning noise (potential DoS on legitimate operations, not secret disclosure).
- Premature list termination → some/all conditions dropped, `rule.conditions` empty → `_rule_matches` returns `False` unconditionally → the specific `.env`/`credentials` detection rule silently never fires, allowing secrets to be written/read without triggering the intended `warn`/`block` action, even though the `.local.md` file appears correctly configured.

The scoped impact described in the question (a sensitive-file/secret rule silently never triggering) is real for the second failure mode, but it depends on the exact placement of a mis-indented line, and is not guaranteed for arbitrary "2 vs 4 space" mistakes — the more directly reproducible consequence of simple 2-space vs 4-space continuation errors is the always-true condition, not condition loss. This is a genuine parser correctness/differential bug in `extract_frontmatter`, not a bypass of any explicit trust boundary, authentication, or approval mechanism — it is a logic bug in a custom mini-YAML parser that a repo-included rule author (or attacker who can merge rule files) can trigger, silently and without any diagnostic output.

### Likelihood Explanation
Precondition: an attacker (or careless rule author) needs to get a `.claude/hookify.*.local.md` file merged into the repo with a `conditions:` block using non-4-space-exceeding indentation for continuation lines — this is a very easy and plausible authoring mistake (no special tooling needed), and nothing in `load_rules`/`load_rule_file` validates that parsed conditions retain the fields the author intended; the file loads successfully with degraded/incorrect conditions and no error is surfaced to the user reviewing the merged rule file.

### Recommendation
Replace the custom nested-list-of-dict parser with a real YAML parser (e.g. `PyYAML`'s `yaml.safe_load`) for the frontmatter block, or, if a custom parser must be retained, make indentation width explicit and validated (e.g., record the indent of the first line after `- ` as the "reference" indent for that item and require exact/greater match, rejecting/erroring on any line that doesn't structurally fit rather than silently ignoring it). Additionally, `Rule.from_dict`/`Condition.from_dict` should reject/raise on conditions missing required keys (`field`, `operator`, `pattern`) instead of silently defaulting `pattern` to `''`, since an empty pattern turns `regex_match`/`contains` into an always-true condition.

### Proof of Concept
Unit test in `plugins/hookify/core/config_loader.py`'s test area (or a new pytest file) comparing `extract_frontmatter` against `yaml.safe_load` on a fuzzed set of indentation variants of the same logical `conditions:` block:

```python
import yaml
from hookify.core.config_loader import extract_frontmatter

RULE_TEMPLATE = """---
name: secret-scanner
enabled: true
event: file
action: block
conditions:
{conditions_block}
---
Blocked: possible secret file write
"""

VARIANTS = [
    # correct 4-space continuation (baseline)
    '  - field: file_path\n    operator: regex_match\n    pattern: "\\.env"\n',
    # 2-space continuation (aligned with dash) - buggy
    '  - field: file_path\n  operator: regex_match\n  pattern: "\\.env"\n',
    # stray zero-indent continuation line - buggy
    '  - field: file_path\n    operator: regex_match\npattern: "\\.env"\n',
]

for block in VARIANTS:
    content = RULE_TEMPLATE.format(conditions_block=block)
    fm, _ = extract_frontmatter(content)
    ref = yaml.safe_load(content.split('---')[1])
    parsed_conditions = fm.get('conditions', [])
    ref_conditions = ref.get('conditions', [])
    # Assert parser output matches reference YAML semantics,
    # or that malformed conditions are rejected loudly (raise), not silently dropped/degraded.
    assert parsed_conditions == ref_conditions, (
        f"Parser differential: got {parsed_conditions}, expected {ref_conditions}"
    )
```

Expected result: the baseline variant passes; the 2-space and stray-zero-indent variants fail the assertion, demonstrating that `extract_frontmatter` silently produces a condition list that differs from the semantically-intended one (missing `operator`/`pattern`, or missing subsequent conditions entirely) without raising any error, confirming the parser differential.

def load_rule_file(file_path: str) -> Optional[Rule]:
    """Load a single rule file.

    Returns:
        Rule object or None if file is invalid.
    """
    try:
        with open(file_path, 'r') as f:
            content = f.read()

        frontmatter, message = extract_frontmatter(content)

        if not frontmatter:
            print(f"Warning: {file_path} missing YAML frontmatter (must start with ---)", file=sys.stderr)

    def _rule_matches(self, rule: Rule, input_data: Dict[str, Any]) -> bool:
        """Check if rule matches input data.

        Args:
            rule: Rule to evaluate
            input_data: Hook input data

        Returns:
            True if rule matches, False otherwise
        """
        # Extract tool information
        tool_name = input_data.get('tool_name', '')
        tool_input = input_data.get('tool_input', {})

        # Check tool matcher if specified
        if rule.tool_matcher:
            if not self._matches_tool(rule.tool_matcher, tool_name):
                return False

        # If no conditions, don't match
        # (Rules must have at least one condition to be valid)
        if not rule.conditions:
            return False

        # All conditions must match
        for condition in rule.conditions:
            if not self._check_condition(condition, tool_name, tool_input, input_data):
                return False

        return True
