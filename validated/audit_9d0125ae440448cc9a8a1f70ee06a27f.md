### Title
Approved git credentials remain cached and are not revoked/scoped after sync, allowing reuse by other repos/submodules on the same host - (File: main.go)

### Summary
`git-sync`'s credential handling mirrors the `Visor.transferERC721` bug class: an authorization ("approval") is granted for one purpose and is never revoked or narrowly scoped, so it can be reused later by an unintended party. In `git-sync`, credentials supplied via `--username`/`--password(-file)`, `--credential`, `--askpass-url`, or the GitHub App token flow are persisted with `git credential approve` into a process-wide credential cache (`credential.helper = "cache --timeout 3600"`), and are never explicitly revoked (`git credential reject`) once the sync that needed them completes.

### Finding Description
`StoreCredentials` calls `git credential approve` to register a username/password for a URL [1](#0-0) . The global git config sets `credential.helper` to `cache --timeout 3600`, meaning any approved credential is cached in memory for up to one hour and returned to any git process that asks for credentials matching the same protocol/host [2](#0-1) . `refreshCreds` calls `StoreCredentials` for every entry in `--credential` on every sync loop iteration (used explicitly for submodule authentication per the README), for `--askpass-url` responses, and for GitHub App tokens [3](#0-2) . Because git's default credential matching (absent `credential.useHttpPath`) is scoped to protocol+host, not full path, a credential approved for one repository URL becomes available to *any* other repository/submodule fetch against the same host during the cache window - there is no corresponding `git credential reject` call anywhere in the codebase to revoke a credential once its specific sync/fetch has completed. This is functionally analogous to the reported NFT bug: an "approval" is granted for a single operation but is never cleared afterward, so it can be reused for an unintended subsequent operation (here, a different repo/submodule path on the same host, or a later untrusted submodule introduced by an attacker-controlled commit).

### Impact Explanation
If an attacker can introduce or modify a submodule URL (e.g., via a malicious commit merged into the tracked branch, as `git-sync` fetches whatever ref is configured) pointing to a different path on the same host as a previously-authenticated `--credential` entry, git's credential lookup can silently supply the previously approved username/password to authenticate the attacker-controlled fetch, without git-sync deliberately intending to authorize that repo. This can lead to unintended credential disclosure to a third-party service that shares the host (e.g., a shared git hosting provider) or unauthorized access to sibling repositories, persisting for the `cache --timeout 3600` window (1 hour) after being approved.

### Likelihood Explanation
Requires: (1) `--credential` (or other credential-supplying flags) to be configured, (2) the credential cache helper's default host-level scoping to remain in effect (no `credential.useHttpPath=true` is set anywhere in the codebase), and (3) an attacker able to introduce a submodule/reference pointing at another path on the same host within the 1-hour cache window. This is a plausible but conditional path — it depends on host-sharing between the legitimate repo and the untrusted content, and on git-sync's submodule support being enabled, so likelihood is moderate rather than trivially exploitable.

### Recommendation
- After each sync/fetch that used a specific credential, call `git credential reject` for that URL to remove it from the cache, mirroring "reset approval after transfer."
- Set `credential.useHttpPath=true` globally so cached credentials are scoped to the full URL path (not just protocol+host), preventing cross-repo/submodule credential reuse on shared hosts.
- Reduce or make configurable the `cache --timeout` value, and avoid pre-approving credentials for submodule URLs that aren't yet known to be trusted.

### Proof of Concept
1. Configure `git-sync` with `--credential='{"url":"https://git.example.com/legit-repo","username":"user","password":"secret"}'` for a legitimate repo hosted at `git.example.com`.
2. `git-sync` calls `StoreCredentials` → `git credential approve`, caching `user:secret` for host `git.example.com` for 3600s (no `useHttpPath`) [2](#0-1) .
3. An attacker who controls content merged into the synced ref adds/updates a submodule pointing to `https://git.example.com/attacker-repo`.
4. During submodule update, git's credential subsystem matches the cached credential by host and transparently supplies `user:secret` to authenticate against `attacker-repo`, without any code path in `git-sync` calling `git credential reject` to have prevented it [1](#0-0) .

// StoreCredentials stores a username and password for later use.
func (git *repoSync) StoreCredentials(ctx context.Context, url, username, password string) error {
	git.log.V(1).Info("storing git credential", "url", redactURL(url))
	git.log.V(9).Info("md5 of credential", "url", url, "username", md5sum(username), "password", md5sum(password))

	creds := fmt.Sprintf("url=%v\nusername=%v\npassword=%v\n", url, username, password)
	_, _, err := git.RunWithStdin(ctx, "", creds, "credential", "approve")
	if err != nil {
		return fmt.Errorf("can't configure git credentials: %w", err)
	}

	return nil
}
