### Title
Crafted payment input referencing a stable "temp-bad" output crashes validating nodes via uncaught `throw` - ([File: validation.js])

### Summary
The CVE describes an "unexpected interaction" that trips an internal `ASSERT` in Apple's software, crashing the process on attacker-influenced input. `ocore`'s unit-validation code contains an analogous pattern: instead of gracefully rejecting a malformed/unexpected payment input via the normal `cb(errorString)` path, several branches use a hard `throw Error(...)` that is not caught by the surrounding `async`/DB-callback control flow, which will crash the node process when hit by data supplied in an untrusted, unprivileged unit.

### Finding Description
`validatePaymentInputsAndOutputs` processes `"transfer"` type payment inputs for every unit an unprivileged author posts. After looking up the source output of the referenced input, the code checks whether that output belongs to a unit that is stable in the DAG and has `sequence === 'temp-bad'`: [1](#0-0) 

Unlike the adjacent `'final-bad'` case, which is handled with a normal validation rejection (`return cb(...)`), the `'temp-bad'` case is treated as an internal invariant violation and does a hard, synchronous `throw Error("spending a stable temp-bad output " + input.unit)` from inside a `conn.query` result callback: [2](#0-1) 

This throw happens deep inside nested asynchronous callbacks (`conn.query` → row-processing callback), not inside a `try/catch` guarded by the `async.series`/`async.eachSeries` control flow that wraps the rest of unit validation. There is no code path that converts this exception into an `ifUnitError`/`ifJointError` callback the way other validation failures are surfaced; the call stack for `validation.validate` (see `validate(objJoint, callbacks, external_conn)`) only translates structured error-code objects thrown/returned through the async pipeline, not synchronous exceptions raised from a DB callback: [3](#0-2) 

A "temp-bad" unit is not an implausible or purely-internal state — it is the normal transient status assigned to the loser of a double-spend race while its ancestor units are still stable and it awaits final resolution to `final-bad`. An attacker who controls or observes such a race can construct a unit whose payment input spends an output of that temp-bad-but-stable unit and post it to the network like any other unit. Because this reaches the `throw` before the code can decide it's "final-bad" (i.e., during the window while the conflict is only "temp-bad"), any full node that receives and attempts to validate this crafted unit executes the `throw`.

This mirrors the CVE's bug class precisely: a normally-unreachable internal assumption (an "ASSERT"/hard invariant) is violated by attacker-controlled input during ordinary processing, and the resulting failure is not handled gracefully but crashes execution.

### Impact Explanation
If this uncaught exception propagates past Node.js's event loop without a global handler that keeps the process alive, the full node process crashes while validating a single attacker-crafted unit. Because every full node applies the same deterministic validation logic to every unit it receives, a unit posted to the network that triggers this state could be independently processed (and independently crash) by every full node that receives it, which prevents the network from continuing to confirm/validate new units until operators identify and patch the code — this matches the "network unable to confirm new units" impact class permitted by the report rules.

### Likelihood Explanation
Reaching the `'temp-bad'`-and-stable state requires the existence of a genuine double-spend conflict in the DAG where the loser is already stable but not yet marked `'final-bad'`, and then crafting a subsequent unit whose payment input references the loser's output. This requires precise timing/knowledge of the DAG state (a double-spend has occurred and is stable but not fully resolved) but does not require any special privilege — any regular unit poster could attempt it, e.g., by racing their own double-spend and then immediately building a spending unit on the losing branch. It's a narrow, timing-dependent path.

### Recommendation
Replace the `throw Error("spending a stable temp-bad output " + input.unit)` at `validation.js:2458` (and the similar unconditional `throw` statements nearby, e.g. `"more than 1 src output"` at `validation.js:2451`, and the `no src_coin`/`no src_output`/`no denomination`/`no src coin amount` throws at `validation.js:2417-2424`) with a normal `return cb("...")` validation-error path, consistent with how the `'final-bad'` sibling case is handled, so that unexpected-but-attacker-reachable states are surfaced as ordinary unit-validation failures instead of crashing the process. Additionally, ensure `validation.validate`'s wrapping call sites (`network.js`, `composer.js`, `aa_composer.js`) don't rely on synchronous throws from deep async DB callbacks for control flow, and add defensive `try/catch` around DB-result callbacks in the validation pipeline.

### Proof of Concept
1. Attacker crafts and broadcasts unit `A`, which is later followed by a second unit `B` from the attacker's own address spending the same source output (a double-spend), such that one of the two ends up with `sequence = 'temp-bad'` while being stable in the DAG (main_chain_index ≤ last_ball_mci) — reachable via the normal double-spend/nonserial resolution logic tracked in `main_chain.js`/`writer.js`.
2. Attacker crafts unit `C` with a `"transfer"` payment input pointing to `{unit: A.unit, message_index, output_index}` (the temp-bad output).
3. Attacker posts `C` to the network.
4. Any full node validating `C` executes `validatePaymentInputsAndOutputs`, reaches the `conn.query` callback at `validation.js:2443`, finds `src_output.sequence === 'temp-bad'` and `bStableInParents === true`, and executes `throw Error("spending a stable temp-bad output " + input.unit)` at line 2458, crashing (or otherwise destabilizing) the validating process instead of cleanly rejecting unit `C`.

Note: I could not fully confirm within the available index whether a global `process.on('uncaughtException', ...)` handler in `network.js` prevents an actual process crash (I found two matches for `uncaughtException` in `network.js` but ran out of iterations to inspect their implementation) — this should be verified before treating the crash impact as certain; if the handler swallows the exception without crashing, the practical impact would be reduced to a stuck/incorrect validation state for that unit rather than a full process crash.
