### Permissionless third-party supply can force-restamp a foreign account’s LTV and temporarily lock its collateral - (File: contracts/controller/src/risk/params.rs)

### Summary

`update_account_threshold` is permissionless and refreshes every listed supply position’s stored `loan_to_value` from the current spoke configuration. The stronger issue is that third-party `supply` also refreshes the target supply leg’s risk parameters while crediting the deposit. An unprivileged caller can therefore force a foreign account to adopt a newly reduced LTV before the account owner acts.

This gives an attacker a state-changing “breakpoint” primitive analogous to the referenced bug class: a user-reachable control path rewrites risk state that later borrowing and withdrawal paths trust. If the listed LTV is reduced while the account has debt, the victim may be unable to withdraw collateral until the debt is repaid or risk parameters become favorable again.

### Finding Description

The permissionless maintenance entrypoint calls `sync_account_thresholds` for arbitrary `account_ids`; in `LtvOnly` mode, no debt positions are loaded and no final health-factor check is applied. [1](#0-0) 

`restamp_listed_supply_ltv` iterates all supply positions and overwrites `position.loan_to_value` with the current listed configuration when the values differ. [2](#0-1) 

The standalone refresh writes the changed supply positions without requiring the final health-factor floor unless `has_risks == true`. [3](#0-2) 

The same force-restamp is exercised through third-party supply: the repository’s regression test has an unrelated caller top up an existing leg after governance lowers LTV, then shows that the account’s stored LTV immediately changes and a borrow that would have worked is rejected with `INSUFFICIENT_COLLATERAL`. [4](#0-3) 

The API documentation confirms that any caller may top up only an existing supply leg of a foreign account, which prevents opening new risk but does not prevent mutation of the existing leg’s stored risk snapshot. [5](#0-4) 

### Impact Explanation

A victim’s collateral can become temporarily immobilized because `withdraw` must pass post-operation collateral coverage and health checks while debt remains. The attacker does not need authority over the victim account: supplying a token amount into a leg the victim already holds causes that leg to use the current, lower LTV.

The attack can be timed immediately after a legitimate risk-parameter reduction but before the victim voluntarily restamps or adjusts their position. The attacker’s deposit is credited to the victim, so the cost is primarily the temporarily deposited asset rather than a protocol fee. The victim retains ownership of the deposited collateral, but its lower effective LTV can be enough to push an already-levered account below the borrow/withdrawal boundary.

This is not permanent protocol insolvency: the victim can repay debt, receive a later favorable LTV, or potentially unwind through liquidation. The affected funds are nonetheless temporarily frozen and the victim’s planned risk-management operations can be prevented by a third party.

### Likelihood Explanation

Likelihood is conditional but plausible:

- Any authenticated address may call `update_account_threshold` on arbitrary account IDs.
- Any authenticated address may top up a market already present in another account.
- Risk parameter reductions are governance-visible and therefore can be anticipated.
- The attacker only needs a positive deposit into an existing victim collateral leg.
- Accounts near their LTV boundary are the most exposed; strongly overcollateralized accounts are unaffected.

The issue requires an LTV tightening and an account whose remaining LTV headroom is smaller than the attacker’s forced restamp effect. It does not directly create liquidation because `has_risks = false` does not restamp liquidation threshold and the health factor does not read LTV. The resulting restriction is therefore a targeted withdrawal/borrow availability denial rather than immediate theft.

### Recommendation

Do not let a third-party supply mutate stored risk parameters on a foreign account. In particular:

1. Preserve the existing `loan_to_value` when the caller is neither the NFT owner nor an active delegate.
2. Make `supply` refresh LTV only for accounts controlled by the caller, or only when the refresh cannot reduce the stored value.
3. Alternatively, stop storing per-position LTV on supply positions and always read the current listing at risk-evaluation time.
4. If permissionless maintenance remains necessary, split risk-state updates into a privileged/keeper-only path or require owner authorization whenever the update would reduce borrowing capacity.
5. Add a regression test where a third-party top-up follows an LTV reduction and the victim’s subsequent withdrawal/borrow result remains unchanged.

``` [4](#0-3) 

A withdrawal variant is conceptually:

```text
1. Alice opens an account, supplies collateral, and borrows near the old LTV boundary.
2. Governance reduces the listed collateral LTV.
3. Attacker calls:
   supply(
     caller = attacker,
     account_id = alice_account,
     spoke_id = alice_spoke,
     assets = [(existing_collateral_hub_asset, 1)]
   )
4. The victim’s stored supply LTV is force-restamped to the reduced value.
5. Alice calls:
   withdraw(
     caller = alice,
     account_id = alice_account,
     withdrawals = [(collateral, amount_that_was_previously_safe)],
     to = None
   )
6. The post-operation risk gate rejects the withdrawal while debt remains.
```

The account can recover by repaying debt or waiting for a later favorable parameter state, so the validated impact is temporary freezing of collateral rather than permanent loss.

/// Refreshes stored LTV snapshots in memory for listed supply assets, skipping
/// unlisted assets. Returns whether any position changed.
pub(crate) fn restamp_listed_supply_ltv(cache: &mut Context, account: &mut Account) -> bool {
    let mut changed = false;
    let keys = account.supply_positions.keys();
    for hub_asset in keys.iter() {
        let Some(listed) = cache.cached_spoke_asset(account.spoke_id, &hub_asset) else {
            continue;
        };
        let config: AssetConfig = (&listed).into();
        let Some(raw) = account.supply_positions.get(hub_asset.clone()) else {
            continue;
        };
        let mut position = AccountPosition::from(&raw);
        if position.loan_to_value.raw() == config.loan_to_value.raw() {
            continue;
        }
        position.loan_to_value = config.loan_to_value;
        update_or_remove_supply_position(account, &hub_asset, &position);
        changed = true;
    }
    changed

/// Allows any authenticated caller to refresh listed supply LTV snapshots.
/// `has_risks` also refreshes gated liquidation tuples and enforces health
/// factor >= 1.05. Rejects execution during a flash loan.
pub(crate) fn update_account_threshold(
    env: &Env,
    caller: Address,
    has_risks: bool,
    account_ids: Vec<u64>,
) {
    validation::require_authorized_caller(env, &caller);

    let scope = if has_risks {
        RiskRefreshScope::FullTuple
    } else {
        RiskRefreshScope::LtvOnly
    };

    let mut cache = Context::new(env);

    for account_id in account_ids {
        cache.reset_spoke_context();
        sync_account_thresholds(env, account_id, scope, &mut cache);
    }
