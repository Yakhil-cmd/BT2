### Title
`StatusHandler#process` mutates `Commit`/`Status` rows across tenants via unscoped `Commit.where(sha:)` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits purely by `sha` with no scoping to the repository that sent the webhook, so a status/commit-state webhook signed for repository R1 will mutate any `Commit` row in the database that happens to share that sha — including commits belonging to stack S2 of a completely different repository (R2), even if R2's `Repository` record has since been deleted or renamed.

### Finding Description
The binding that should hold is: `commit.stack.repository.full_name == payload.dig('repository', 'full_name')` for every `Commit` mutated by a webhook. In `StatusHandler#process`: [1](#0-0) 

the code does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — no join or filter through `Repository`/`stack.repository` at all. The base `Handler` class does define a `stacks` helper that scopes by `Repository.from_github_repo_name(repository_name)`: [2](#0-1) 

but `StatusHandler` never calls it — `process` is overridden to query `Commit` globally instead. `Commit#create_status_from_github!` then writes a `Status` row and triggers `Hook.emit(:commit_status, ...)`/`Hook.emit(:deployable_status, ...)` and can schedule merges (`stack.schedule_merges`) using S2's `stack`, all driven by attacker-controlled `state`/`description`/`target_url` from R1's payload: [3](#0-2) [4](#0-3) 

Any commit sha collision across the `commits` table — whether from a legitimately shared commit (cherry-pick, common ancestor, monorepo split, fork history) or an attacker crafting a commit with a colliding/attacker-chosen sha in their own repo — causes cross-tenant writes, independent of whether S2's `Repository` record still exists. The webhook signature check in `WebhooksController`/`GitHubApp` only proves the payload came from GitHub for the *sending* repository (R1); it says nothing about which `sha`s that payload is allowed to touch, so it does not prevent this divergence. Since the query is `Commit.where(sha:)` with zero repository predicate, the repository lifecycle (deleted, renamed, transferred) of the *victim* stack is irrelevant — the vulnerability is present for any existing S2 commit row regardless of whether S2's `Repository` record is intact, renamed, or gone.

### Impact Explanation
An attacker who controls or can push to any repository configured as a Shipit stack (R1) can send a `status` webhook (or trigger a real GitHub status event) referencing a `sha` that also exists as a `Commit` row under a victim stack S2. This creates a forged `Status` row on S2's commit, can flip CI/deployability state (`deployable?`), and can trigger `stack.schedule_merges` — i.e., "a payload for one repository mutating another's stack, commit, task" — matching the Critical impact category. This is repeatable against any sha collision and is not limited by S2's `Repository` record's existence, so it also persists after repository transfer/deletion as claimed.

### Likelihood Explanation
Precondition is a `sha` collision between a commit the attacker controls (via R1) and a `Commit` row already ingested for S2 — this can occur legitimately (shared git history, cherry-picks, monorepo splits) without requiring any secret, privileged role, or bypass of signature verification. The attacker only needs an active/valid Shipit stack for R1 that they can push to or open PRs against, which is within the stated unprivileged threat model.

### Recommendation
Scope `StatusHandler#process` (and any other sha-keyed handler) to only mutate commits belonging to stacks under the repository that signed the webhook, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or `Commit.joins(stack: :repository).merge(Repository.from_github_repo_name(repository_name)).where(sha: params.sha)`, mirroring the `stacks` helper already defined in `Handler`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual)
test "status webhook from R1 does not mutate commits of unrelated stack S2, even if S2's repository was renamed/deleted" do
  repo1 = shipit_repositories(:shipit) # attacker-controlled repo
  stack1 = create_stack(repository: repo1)
  stack2 = shipit_stacks(:shipit) # victim stack S2
  victim_commit = stack2.commits.create!(sha: 'deadbeef' * 5, message: 'victim commit')

  # simulate S2's Repository being renamed/deleted
  stack2.repository.update!(owner: 'renamed-owner', name: 'renamed-repo')

  payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'repository' => { 'full_name' => repo1.full_name }
  }

  assert_no_difference -> { victim_commit.statuses.count } do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end
end
```
Both sides of the binding (`commit.stack.repository.full_name` vs `payload.dig('repository','full_name')`) should be asserted unequal yet the status is still created, proving the missing scope; the test currently would fail (status is created), confirming the vulnerability. [1](#0-0)
