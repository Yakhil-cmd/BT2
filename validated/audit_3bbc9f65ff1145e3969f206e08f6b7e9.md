Based on my investigation, I found a genuine equality-breaking analog in `pox-5.clar`'s L1 lockup verification path, though I was cut off before I could fully confirm whether there's a persistent used-outpoint registry elsewhere in the contract that would prevent replay across separate `register-for-bond` calls.

### Title
Reused Bitcoin L1 lockup outpoint can be credited to multiple bond registrations, double-counting sats never re-locked - (File: `stackslib/src/chainstate/stacks/boot/pox-5.clar`)

### Summary
`validate-l1-lockup` / `verify-l1-lockups` in `pox-5.clar` deduplicate lockup outpoints only *within a single call*, via a freshly-initialized `seen-outpoints` list [1](#0-0) . Each fold call starts `seen-outpoints: (list)` from scratch [2](#0-1) , and the per-lockup dedup check only asserts against that call-scoped list [3](#0-2) . I was not able to locate, within the code I retrieved, a persistent contract-level map (e.g. `used-outpoints`/`claimed-outpoints`) that records which Bitcoin outpoints have already been consumed across separate transactions/calls.

### Finding Description
The contract equality that must hold is: *sats credited to a staker's bond position via L1 proof == sats actually locked (once) on Bitcoin*. `validate-l1-lockup` proves an L1 UTXO exists, matches the expected timelock script for the staker/bond, and hasn't unlocked yet [4](#0-3) , then adds `(get amount output)` to the running `sum` [5](#0-4) . If the only anti-replay mechanism is the transient `seen-outpoints` list (capped at 10, reset every call), the same Bitcoin outpoint could be submitted in two separate `register-for-bond`-style calls (e.g., once directly, and again bundled with a different set of lockups, or reused after the first call's list is exhausted), each producing a validated `sum` that increments `staker-shares-staked-for-cycle` / `total-shares-staked-for-cycle` and mints reward-earning stake without any second BTC ever being locked.

### Impact Explanation
If outpoint reuse across calls is truly unguarded, this breaks "sats credited by an L1 proof that were never locked on Bitcoin" — the staker's `stacked_amt`/sats used in `pox_5_make_signer_set` weight allocation [6](#0-5)  and bond reward calculations in `calculate-bond-rewards` [7](#0-6)  would be inflated relative to actually-locked BTC, letting a staker claim signer weight and sBTC rewards disproportionate to real collateral — a Critical-class double-counting of a locked commitment.

### Likelihood Explanation
This is uncertain without full confirmation. The tool budget was exhausted before I could verify (a) whether a persistent `used-outpoints`/similar map exists elsewhere in `pox-5.clar` or in the accompanying Rust dispatch (`pox_5.rs`) that rejects previously-claimed outpoints, or (b) how `register-for-bond`'s surrounding logic (bond membership, rollover checks) might independently prevent reuse. Given the amount of unread contract code (`pox-5.clar` is >2300 lines and I only reviewed the L1-lockup section plus reward math), I cannot assert this is exploitable with full confidence.

### Recommendation
A background engineer should:
1. Search all of `pox-5.clar` for any map keyed by `(txid, output-index)` that persists across transactions (not just the per-call `seen-outpoints` fold accumulator), and confirm whether `register-for-bond` (or whatever the L1-crediting entry point is named) checks against it before calling `verify-l1-lockups`.
2. If no such persistent check exists, add a `define-map used-l1-outpoints { txid: (buff 32), output-index: uint } bool` (or similar), and have `validate-l1-lockup` assert-and-insert against it, so an outpoint can only ever be credited once contract-wide, not merely once per call.

### Proof of Concept
Not constructed — this requires confirming the absence of a persistent outpoint registry across the full `pox-5.clar` file and the bond-registration entry point, which I could not complete within the available tool calls. A concrete PoC would call the L1-crediting function twice with the same Bitcoin outpoint/merkle proof (either in the same block or across blocks) and show `total-shares-staked-for-cycle` increases twice for one real BTC lock.
