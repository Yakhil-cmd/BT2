### Title
Webhook signature verification is keyed off `repository.owner.login`, but the acted-upon repository is resolved from a different field in the same unauthenticated-until-verified JSON body - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App/organization's `webhook_secret` to verify the HMAC signature against by reading `repository.owner.login` (falling back to `organization.login`) out of the still‑unverified JSON body. Once the signature check passes, the event handlers (e.g. `PushHandler`) locate the `Stack`/`Repository` to act on using a *different* value taken from the same body (the repository name used to look up `Repository.from_github_repo_name`/`Stack`). Both values live inside the same attacker-crafted payload, so nothing forces them to refer to the same repository.

### Finding Description
`verify_signature` in `WebhooksController` does: [1](#0-0) 
selecting the GitHub App/org config via: [2](#0-1) 

`Shipit.github(organization: repository_owner)` returns a `GithubApp` instance whose `webhook_secret` is specific to that organization (Shipit supports multiple GitHub Apps, one per org, each with its own `webhook_secret`), as documented in `docs/setup.md` ("Using Multiple Github Applications") and configured via `config/secrets.yml`'s per-org `github` hash. The HMAC signature is verified with `GithubApp#verify_webhook_signature`, which simply HMACs the raw JSON body with that organization's secret: [3](#0-2) 

This only proves the sender knows *some* configured organization's webhook secret; it does not bind the verified request to any specific repository. Once verification passes, downstream handlers such as `PushHandler` act on stacks matched by branch/repository fields taken from the same JSON body: [4](#0-3) 

and repositories/stacks are looked up by owner/name pairs independently parsed from the body, e.g. `Repository.from_github_repo_name`: [5](#0-4) 

Because the attacker fully controls the raw JSON body (they only need to know one organization's `webhook_secret` to produce a valid signature over an arbitrary body), they can set `repository.owner.login` (used to pick the verifying secret) to an organization whose secret they know, while setting the repository name fields used by the handler (e.g. the branch/stack lookup path) to point at a completely different organization/repository's stack. The signature only proves "signed by someone who knows Org‑A's secret," not "this payload legitimately describes an Org‑A repository," yet Shipit trusts the payload's repository identity for all subsequent actions (triggering `Stack#sync_github`, creating commits/statuses, etc.) once that unrelated signature check passes.

This is exactly the class of binding break called out in the rules: *"an organization that authenticated versus the repository that is written."*

### Impact Explanation
An attacker who has legitimate control of a webhook secret for **any one** GitHub organization where the Shipit GitHub App is installed (a normal, low-privilege scenario in any multi-tenant/multi-org Shipit deployment — they only need admin rights on their own, unrelated org) can forge webhook deliveries that are accepted as authentic for **other** organizations' stacks. Depending on the handler reached, this can force `Stack#sync_github` to run for a stack the attacker does not own, which can trigger continuous deployment / merge processing for that stack — an unauthorized deploy performed against a repository the attacker has no legitimate relationship with. This satisfies the "unauthorized deploy" Critical impact criterion.

### Likelihood Explanation
Requires Shipit to be configured with more than one GitHub organization (the documented "Using Multiple Github Applications" setup) and requires the attacker to know one org's `webhook_secret` — attainable simply by being an admin of any org that has the Shipit GitHub App installed, without any Shipit session, API token, or access to the victim org/repository. Given that webhook secrets are configured per-org and the controller trades on an implicit assumption that `repository.owner.login` and the repository name used by handlers always match (true for genuine GitHub-issued payloads, false for attacker-crafted ones), likelihood is moderate but concrete.

### Recommendation
After verifying the HMAC, cross-check that the organization whose secret validated the signature actually matches the owner/organization of the repository object used by the event handler for every field the handler will act on (not just the field chosen for secret lookup). Alternatively, verify the signature using every configured secret and only accept the request if the resolved organization's secret matches the repository actually referenced by the payload's `repository.full_name` (i.e., derive the verifying secret from the same field the handlers use to resolve the target repository), and reject the request otherwise.

### Proof of Concept
1. Deploy Shipit configured for two GitHub orgs, `orgA` (attacker is org admin, knows `webhook_secret_A`) and `orgB` (victim org, has a Shipit stack, e.g. `orgB/app` on branch `main`).
2. Attacker crafts a `push` event JSON body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen sha, must exist on orgB/app as a reachable commit>",
     "repository": {
       "owner": { "login": "orgA" },
       "full_name": "orgB/app"
     }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(webhook_secret_A, body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` = `"orgA"`, fetches `Shipit.github(organization: "orgA")`, and the signature verifies successfully (attacker-known secret, attacker-crafted body).
5. `PushHandler#process` resolves stacks using the repository name embedded elsewhere in the payload processing chain (`orgB/app`) and calls `stack.sync_github(expected_head_sha: ...)` for the victim's stack, forcing a sync/deploy trigger the attacker was never authorized to invoke on `orgB`.

*(Exact confirmation of which internal `Handler` base-class method resolves `stacks`/`repository` from the payload was not fully traced beyond `PushHandler` and `Repository.from_github_repo_name`; a Devin session with full repo access should verify the precise field used by `Handler#stacks`/`Handler#repository` to confirm the exact mismatched field pairing before remediation.)*

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
