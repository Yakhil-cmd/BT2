### Title
Webhook signature verification is keyed to an attacker-controlled organization field, decoupled from the repository the payload actually acts on - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and its `webhook_secret`) to verify the incoming HMAC signature against, based purely on an unauthenticated field taken from the JSON body (`repository.owner.login` / `organization.login`). The event handlers, however, resolve the `Stack`/`Repository` to act on using a *different* field of the same unauthenticated body — `repository.full_name`. Nothing binds "the organization whose secret validated this request" to "the repository the request is allowed to mutate," breaking the equality `verified_organization == acted_upon_repository.owner` that the signature check is supposed to enforce.

### Finding Description
`verify_signature` looks up the GitHub App/secret to use for HMAC verification from `repository_owner`, itself parsed straight out of the untrusted request body: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` resolves per-org config in multi-tenant installs (a fully documented and tested deployment mode): [3](#0-2) 

and `GitHubApp#verify_webhook_signature` **returns `true` unconditionally when that org's `webhook_secret` is blank**: [4](#0-3) 

Multi-org configuration is a first-class, documented feature (`docs/setup.md`, "Using Multiple Github Applications") and blank `webhook_secret` is shown as a valid example value in both the example and test dummy secrets files: [5](#0-4) 

Once `verify_signature` passes (either because it validated against a *different* org's secret than the one whose repository will actually be touched, or because that org's secret is blank), `create` dispatches the raw, unauthenticated payload to the event handlers: [6](#0-5) 

Every handler resolves its target `Stack`/`Repository` from `repository.full_name` in that same payload — a field the signature check never inspects or binds to the organization it used for verification: [7](#0-6) [8](#0-7) 

So an attacker who can produce (or does not even need to forge, if the secret is blank) a validly "signed" webhook for Organization A can set `repository.full_name` to a repository belonging to Organization B (a completely different, protected tenant on the same Shipit instance) and have the `push`, `pull_request`, `status`, `check_suite`, or `membership` handlers act on Organization B's stacks.

### Impact Explanation
This breaks the exact trust binding called out as in-scope: *"an organization that authenticated versus the repository that is written."* Concretely:
- `PushHandler#process` calls `stack.sync_github(expected_head_sha:)` on a stack chosen purely from the forged `full_name`, letting an attacker trigger GitHub sync / undeployed-commit tracking on a repository they don't own, using another tenant's (or no) signature validation. Depending on continuous-delivery configuration this can advance a stack toward deploy eligibility.
- `PullRequest::OpenedHandler` / `LabeledHandler` / `ReopenedHandler` can archive/unarchive review stacks or trigger provisioning logic for a repository outside the authenticating organization.
- The `MembershipHandler` path (exercised in `test/controllers/webhooks_controller_test.rb`) creates/removes `Team`/`Membership`/`User` records server-side based on unauthenticated payload content once the (unrelated) org's signature check passes.

Because the org used to select the verifying secret is never the same org whose data gets mutated, this is a cross-tenant/cross-repository write that a fully unprivileged external actor can trigger without any Shipit session, API token, or the target organization's actual webhook secret — satisfying the "cross-repository writes / unauthorized deploy" Critical bucket, or at minimum unauthenticated manipulation of stack state (High).

### Likelihood Explanation
Requires only that the Shipit instance be configured with multiple GitHub Apps (a documented, supported configuration) and that at least one configured organization either has a blank `webhook_secret` (shown as an accepted example value) or whose secret the attacker can otherwise obtain (e.g., they administer that organization's own GitHub App settings). No Shipit credentials, GitHub OAuth session, or API token are needed — only the ability to send an HTTP POST to the public `/webhooks` endpoint with a crafted JSON body and, optionally, the `X-Hub-Signature` computed from the (weakly-protected or blank-secret) organization's secret.

### Recommendation
Bind signature verification to the same organization/repository the handlers will act on: derive the verifying `webhook_secret` from `repository.full_name` (or an equivalent trusted identifier) rather than from `repository.owner.login`/`organization.login`, and reject the payload if the resolved repository's actual owning organization does not match the organization whose secret validated the signature. Additionally, treat a blank/absent `webhook_secret` for any configured organization as a hard misconfiguration (reject the webhook) rather than an implicit signature-bypass, since `verify_webhook_signature` returning `true` for blank secrets removes signature protection entirely for that tenant.

### Proof of Concept
Given a Shipit instance configured with two GitHub Apps, `OrgOne` (attacker-influenced / blank `webhook_secret`) and `OrgTwo` (victim tenant, properly secured), as in `test/dummy/config/secrets_double_github_app.yml`:

1. Attacker sends:
```
POST /webhooks
X-Github-Event: push
Content-Type: application/json

{
  "ref": "refs/heads/master",
  "after": "<attacker chosen sha>",
  "repository": {
    "full_name": "OrgTwo/victim-repo",
    "owner": { "login": "OrgOne" }
  }
}
```
2. `repository_owner` resolves to `"OrgOne"` [2](#0-1) , so `Shipit.github(organization: "OrgOne")` is used for verification [9](#0-8) .
3. Because `OrgOne`'s `webhook_secret` is blank, `verify_webhook_signature` returns `true` regardless of any (or no) signature header [10](#0-9) .
4. `create` dispatches the raw payload to `PushHandler`, which resolves the target stack from `repository.full_name = "OrgTwo/victim-repo"` [11](#0-10)  and calls `stack.sync_github(expected_head_sha: params.after)` on `OrgTwo`'s stack [8](#0-7)  — despite the signature having been verified against `OrgOne`, not `OrgTwo`.

I was not able to fully trace whether `sync_github` alone is sufficient to trigger an actual deploy without further conditions (e.g., continuous delivery enabled) — that would require deeper review of `Stack#sync_github` and `GithubSyncJob`, whose full bodies were not returned by search; the underlying cross-organization authentication/authorization decoupling in `WebhooksController`, however, is directly confirmed by the cited source.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
