In `WebhooksController#verify_signature`, the GitHub App (and thus the HMAC secret) used to authenticate the request is selected using `repository_owner`, which is read straight out of the *unverified* JSON body: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0) [2](#0-1) . But once the signature check passes, the actual stack that gets mutated is resolved from a *different* field of the same payload — `payload.dig('repository', 'full_name')` — via `Repository.from_github_repo_name` [3](#0-2) [4](#0-3) . The HMAC itself is computed over the entire `raw_post`, but in multi-org configurations (`Shipit.github_app_config`) each org has its own `webhook_secret` selected via `github_app_config(organization)` [5](#0-4) , and that org lookup is derived purely from attacker-supplied JSON, not from anything cryptographically bound to which secret is checked.

This mirrors the report's bug class: the verifier's "challenge"/binding (which secret to check the signature against) is derived from a value the prover (attacker) fully controls and that is not itself pinned to the payload's execution semantics, exactly the "organization that authenticated versus the repository that is written" binding called out in the rules.

However, after evaluating exploitability: a valid HMAC signature can only be produced by someone who knows the correct `webhook_secret`, and the secret used is chosen based on the payload's declared `repository.owner.login`/`organization.login`. If the attacker controls org A (and thus knows org A's `webhook_secret`, e.g. because they administer their own GitHub App installation on a distinct organization configured in the same Shipit instance) and crafts a payload with `repository.owner.login = "orgA"` but `repository.full_name = "orgB/victim-repo"`, `verify_signature` would select org A's secret, correctly validate the signature (since attacker signs with the secret they legitimately know), and the request would pass. The handler would then act on `orgB/victim-repo` because `repository_name` comes from `full_name`, not `owner.login`. This would let an attacker with legitimate control of one configured GitHub organization forge push/status/pull_request events against a stack under a completely different organization also configured on the same instance, e.g. triggering `GithubSyncJob`, fabricating commit `Status`, or affecting merge queue behavior for a repository they don't own — a cross-repository write across the org boundary Shipit is supposed to enforce.

This requires the multi-organization webhook configuration (`Shipit.github_organizations` with more than one org, each with a `webhook_secret`) and requires the attacker to legitimately control at least one of those configured organizations/installations. That is a real, low-privilege-but-not-zero-privilege precondition (owning/administering *a* GitHub App installation on the same Shipit instance, not the victim's), which is a plausible unprivileged-attacker scenario relative to the victim org, matching the rules' organization-vs-repository binding example.

### Title
Webhook signature verification selects the HMAC secret from an unauthenticated payload field, allowing cross-organization webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Finding Description
`WebhooksController#verify_signature` picks the `GitHubApp` (and therefore the `webhook_secret` used to validate `X-Hub-Signature`) using `repository_owner`, computed from `params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')` — both taken from the raw, unauthenticated JSON body before any signature check occurs [6](#0-5) . `Shipit.github(organization:)` then loads that organization's specific config/secret via `github_app_config` [5](#0-4) . Once the signature verifies, the event is dispatched to handlers whose `stacks` lookup uses a separate field, `repository.full_name`, resolved through `Repository.from_github_repo_name` [3](#0-2) [4](#0-3) . Nothing binds the "owner" used to pick the verification secret to the "full_name" used to pick the acted-upon repository — a body signed with organization A's secret can declare `repository.full_name` belonging to organization B.

### Impact Explanation
An attacker who legitimately controls a GitHub App installation for one organization configured on a multi-org Shipit instance can forge webhook payloads (signed with their own known secret) that claim to originate from, and target, a different organization's repository. This can trigger `GithubSyncJob` [7](#0-6) , fabricate `commit_status`/`push` events, or manipulate merge/review-stack workflows for a repository the attacker does not control, constituting a cross-repository/cross-organization write that Shipit's per-org secret model is meant to prevent.

### Likelihood Explanation
Requires a multi-organization Shipit deployment where the attacker legitimately administers at least one configured GitHub App/organization (and thus knows its `webhook_secret`) distinct from the victim organization also hosted on the same instance. This is a realistic setup for shared/multi-tenant Shipit deployments serving several GitHub orgs.

### Recommendation
Bind the organization used to select the verification secret to the same field used to resolve the target repository (e.g., derive both from `repository.full_name`'s owner segment, or verify the signature against the config for the repository actually being acted on, not a separately-read `organization`/`repository.owner.login` field). Reject payloads where these two do not match.

### Proof of Concept
1. Configure two organizations in `secrets.github` (multi-org mode), each with its own `webhook_secret`.
2. Attacker controls org `attacker-org` and knows its `webhook_secret`.
3. Attacker crafts a JSON body: `{"repository": {"owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo"}, "ref": "refs/heads/master", "after": "<sha>"}`.
4. Attacker computes `X-Hub-Signature: sha1=<hmac with attacker-org secret>` over that raw body.
5. `verify_signature` resolves `repository_owner` = `"attacker-org"`, loads `attacker-org`'s secret, and the HMAC validates successfully [1](#0-0) .
6. `PushHandler`/other handlers resolve `stacks` via `repository.full_name = "victim-org/victim-repo"` [3](#0-2) , acting on the victim's stack despite the signature only proving control of `attacker-org`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
