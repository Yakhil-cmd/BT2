### Title
Unhandled "second call of onEnd" exception in `dataFeedByAddressExists` crashes the node when an oracle posts multiple matching data-feed values - ([File: data_feeds.js])

### Summary
`dataFeedByAddressExists()` (used to evaluate `in_data_feed()` in oscript/AA formulas) manually short-circuits its LevelDB/RocksDB key-stream by calling `stream.destroy()` followed by a synchronous call to `onEnd()` as soon as a matching record is found. `onEnd()` is a "run-once" guard that `throw`s if it is invoked a second time. Because `stream.destroy()` does not synchronously suppress the stream's own `'end'`/`'close'` event, the same stream can also fire the `'end'` handler afterwards, causing `onEnd()` to run twice and `throw Error("second call of onEnd")`. This is an uncaught exception on a callback-style code path with no surrounding try/catch, and in Node.js an uncaught exception thrown from an event-emitter callback crashes the process.

### Finding Description
`dataFeedByAddressExists` in [1](#0-0)  implements a "stop stream early" optimization:

```js
var bOnEndCalled = false;
function onEnd(){
    if (bOnEndCalled)
        throw Error("second call of onEnd");
    bOnEndCalled = true;
    ...
    handleResult(bFound);
}
var stream = kvstore.createKeyStream(options);
stream.on('data', handleData)
.on('end', onEnd)
.on('error', function(error){ throw Error('error from data stream: '+error); });
```

For relational comparisons (`>`, `>=`, `<`, `<=`), the `data` handler calls `stream.destroy()` and then `onEnd()` directly the moment a matching record inside the `[min_mci, max_mci]` window is found: [2](#0-1) . `kvstore.createKeyStream` is a thin passthrough to the underlying RocksDB LevelUP stream implementation with no guarantee that destroying the stream cancels a pending `'end'` (or `'close'`) event that may already be queued/emitted by the underlying store: [3](#0-2) . If the stream also emits `'end'` after the manual `onEnd()` call (e.g., because multiple qualifying rows were already buffered/read when the first match triggers `destroy()`), `onEnd()` runs a second time and throws.

This function is reached from `dataFeedExists`, which is invoked from the `in_data_feed` oscript operator evaluated when validating/executing any AA trigger: [4](#0-3) [5](#0-4) . An oracle (any address, no special privilege) simply needs to post two or more `data_feed` messages for the same `feed_name` whose stabilized MCIs both fall in the `[min_mci, max_mci]` window a trigger's `in_data_feed(...)` call queries with a relational operator (`>`, `>=`, `<`, `<=`). Any user (or the oracle itself) then posts a unit that triggers an AA whose oscript calls `in_data_feed` with that oracle/feed/relation — this is the "2 announcements a short time apart" pattern from the CVE, mapped onto duplicate/ordered `data_feed` records instead of duplicate mDNS CNAME records.

### Impact Explanation
An uncaught `throw` inside a database stream event handler is not caught by any surrounding `try/catch` in the call chain (`dataFeedExists` → `dataFeedByAddressExists` is fired directly off `stream.on('end', ...)`, an async event callback). In Node.js, an exception thrown from inside an event-emitter's event handler that has no listener for `'error'` (or that is thrown synchronously in a handler without a domain/try-catch wrapper) propagates as an uncaught exception, crashing the full-node process (`process.exit` via default uncaughtException behavior). Any single full node — witness, hub, or ordinary full node — that evaluates the affected AA trigger would crash, which can be triggered repeatedly and reliably from any oracle willing to post two `data_feed` values and any counter-party willing to fire the corresponding AA trigger, i.e., an unauthenticated remote crash of arbitrary nodes on the network, matching the "network unable to confirm new units" / node-crash class of impact.

### Likelihood Explanation
Likelihood is high given the low bar to trigger: posting a `data_feed` message is a normal, unprivileged operation (see the `data_feed` message validation in [6](#0-5) ), and calling `in_data_feed()` from an AA is a documented, commonly used oscript feature. The bug depends only on the underlying stream implementation emitting `'end'`/`'close'` asynchronously after `destroy()` is called mid-stream, a well-known race in Node.js streams/leveldb-family stores, so it is plausible though not certain to reproduce deterministically on every hit — the exact timing depends on RocksDB/LevelUP's internal buffering, which could not be independently verified in this environment.

### Recommendation
- Make `onEnd()` idempotent instead of throwing: guard with the `bOnEndCalled` flag and simply `return` on a repeat call instead of throwing.
- Remove the listeners (`stream.removeAllListeners('data')`, `.removeAllListeners('end')`) before calling `stream.destroy()`, or listen for the stream's `'close'` event (fired once destroy completes) rather than relying on `'end'` racing with manual short-circuit logic.
- Wrap the `data`/`end`/`error` handlers so that any unexpected double-invocation degrades gracefully (log and ignore) rather than crashing the process, consistent with defense-in-depth for other `kvstore` stream consumers (e.g., `readDataFeedByAddress` in the same file has an analogous but unguarded pattern and should be reviewed too: [7](#0-6) ).

### Proof of Concept
1. As oracle address `O`, post a `data_feed` message `{"price": 100}` in unit `U1`; let it stabilize at MCI `m1`.
2. Post a second `data_feed` message `{"price": 200}` in unit `U2` shortly after; let it stabilize at MCI `m2 > m1`.
3. Deploy/trigger any AA whose oscript evaluates `in_data_feed({oracles: 'O', feed_name: 'price', feed_value: '>50', min_mci: m1})` (or any relational operator) with `max_mci` covering both `m1` and `m2`, so that `dataFeedByAddressExists` reads at least two matching keys from the `df\nO\nprice\n...` range before/around the point where the early-exit `destroy()`/`onEnd()` fires.
4. If the underlying RocksDB read stream emits `'end'` after `destroy()` (racing with the manual `onEnd()` call already executed inside `handleData`), the second `onEnd()` invocation throws `Error("second call of onEnd")`, which is uncaught and crashes the node process evaluating the trigger.

Note: I was unable to execute the RocksDB/LevelUP stream to empirically confirm the exact timing of `'end'` firing after `stream.destroy()` in this environment (no runtime access), so the reproducibility of the race is based on code inspection of `data_feeds.js` and `kvstore.js` rather than an observed crash; this should be verified experimentally against the exact `level-rocksdb` version in use.
