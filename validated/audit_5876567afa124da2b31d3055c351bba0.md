### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup - (`app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits by `sha` alone, with no scoping to the webhook's `repository.full_name`, while `PushHandler#process` and the base `Handler` class provide exactly this scoping via `stacks`/`repository_name`. An attacker who owns/controls any GitHub repository can send a legitimately-signed `status` webhook for that repository whose `sha` happens to match a commit belonging to an unrelated `Stack`, and the handler will write a forged `Status` record onto that unrelated stack's commit.

### Finding Description
The broken binding, stated as an equality that should hold but does not:
`payload.dig('repository','full_name')` (the webhook's authenticated origin repo, available via `Handler#repository_name`, `app/models/shipit/webhooks/handlers/handler.rb:36-38`) MUST equal `commit.stack.repository` (the repository owning every `Commit` row mutated by the handler).

`StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
This queries `Commit` globally by `sha` with no `stack_id`/repository filter, never calling `stacks` or `repository_name`, which are otherwise the standard scoping mechanism defined on the base `Handler` class (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) and used correctly by `PushHandler#process` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`, which does `stacks.not_archived.where(branch:)`).

Signature verification in `Shipit::WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) only confirms the payload came from GitHub for the *organization* named in `repository.owner.login` — it says nothing about which specific repository's stacks/commits the handler is permitted to mutate. It provides no protection against an attacker-controlled repository (which the attacker legitimately owns, so the signature verifies) supplying an unrelated repo's commit `sha`.

Exploit flow:
1. Attacker owns/controls GitHub repository `attacker/evil-repo`, configured with a valid webhook secret for Shipit (this is normal, since they own the repo).
2. Attacker discovers or brute-forces a `sha` known to exist as a `Commit` row under some other `Stack` (e.g., via publicly visible commit history of the target's GitHub repo, or in the case of duplicate commits/cherry-picks/forks sharing SHAs, which is common in monorepo/fork workflows).
3. Attacker POSTs a `status` event to `/webhooks` with `repository.full_name = "attacker/evil-repo"` and `sha` = target's commit sha. Signature is valid because it's signed with the attacker's own repo's secret.
4. `StatusHandler#process` finds `Commit` rows in the DB with that `sha` — including the row belonging to the *victim* stack — and calls `commit.create_status_from_github!(params)` on it, injecting a forged status (arbitrary `state`, `description`, `target_url`, `context`) onto the victim's commit.
5. This can flip `Status::Group` state on the victim's commit (e.g., forge a `success` state for a required CI check), directly influencing `Commit#deployable?` and continuous deployment eligibility (`app/models/shipit/commit.rb:227-229`, `:281-287`) for a stack the attacker has no relationship to.

### Impact Explanation
A payload from one repository (`attacker/evil-repo`) mutates state (`Status` records) belonging to a completely different repository/stack, which matches the specified Critical impact category ("a payload for one repository mutating another's stack, commit, task or team"). Concretely, the attacker can forge required-status-check results (e.g., "CI passed") on a victim commit they don't own, potentially unblocking `deployable?`/continuous deployment for that victim stack. This is repeatable against any known/guessable sha collision and is not limited to a single victim — any stack whose commits share a sha with an attacker-controlled repo's commits is affected.

### Likelihood Explanation
Preconditions: the attacker needs (a) any GitHub repository they control that can be registered to send `status` webhooks to the Shipit host's `/webhooks` endpoint with a valid signature (trivial — attacker owns the repo, sets up the webhook themselves, no privileged Shipit role needed), and (b) a `sha` value that also exists as a `Commit` row under a target `Stack`. SHA collisions across repos are not cryptographically improbable coincidences the attacker must engineer from scratch — they occur naturally via forks, cherry-picks, squash workflows, subtree merges, or shared upstream history, and an attacker can directly increase likelihood by cherry-picking/rebasing a target's public commit into their own controlled repo, thereby giving that exact sha a `Commit` row scheduled for creation in their own stack while it also exists in the victim stack (Shipit creates `Commit` rows from GitHub push/PR activity it observes). This makes the attack practically achievable at low cost and fully repeatable.

### Recommendation
Scope `StatusHandler#process` to the requesting repository, mirroring `PushHandler`, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
using the existing `stacks`/`repository_name` helpers from `Handler`, so that only commits belonging to the stacks associated with `payload['repository']['full_name']` can be mutated.

### Proof of Concept
Minitest plan (no live GitHub required):
```ruby
test "StatusHandler does not mutate commits belonging to a different repository" do
  repo_x = shipit_stacks(:shipit).repository # or create a Repository for "attacker/evil-repo"
  repo_y_stack = shipit_stacks(:cross_repo_stack) # belongs to a different Repository "victim/app"
  victim_commit = repo_y_stack.commits.create!(sha: "deadbeef" * 5, message: "victim commit")

  payload = {
    'repository' => { 'full_name' => 'attacker/evil-repo' },
    'sha' => victim_commit.sha,
    'state' => 'success',
    'context' => 'forged-ci'
  }

  assert_no_difference -> { victim_commit.statuses.count } do
    Shipit::Webhooks::Handlers::StatusHandler.new(payload).process
  end
end
```
Currently this assertion FAILS (i.e., `victim_commit.statuses.count` increases by 1) because `StatusHandler#process` matches on `sha` alone across all repositories, demonstrating the cross-repository mutation. After applying the recommended fix (scoping via `stacks`), the assertion passes.
