### Title
Unauthenticated webhook forgery when `webhook_secret` is unset causes cross-repository status/CI forgery and unauthorized `Shipit.github_teams` membership escalation - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::GitHubApp#verify_webhook_signature` treats an unconfigured `webhook_secret` as an implicit pass, returning `true` unconditionally rather than rejecting the request. Because `webhook_secret` is explicitly documented as *optional* and defaults to `nil` in every shipped secrets template, any Shipit deployment that follows the setup docs but does not set a webhook secret will process **arbitrary, unsigned** `POST /webhooks` payloads as if they were verified GitHub events — including `status` and `membership` events that directly control commit deployability and `Shipit.github_teams` authorization.

### Finding Description
`WebhooksController#verify_signature` selects a `GitHubApp` using an attacker-controlled field (`repository_owner`, taken straight from the unauthenticated JSON body) and delegates trust entirely to `verify_webhook_signature`: [1](#0-0) 

That method contains a fail-open branch: [2](#0-1) 

`return true unless webhook_secret` means the binding "payload accepted == payload cryptographically signed by GitHub" only holds when an operator has explicitly configured `webhook_secret`. The setup documentation and every shipped secrets template list it as optional/nil: [3](#0-2) [4](#0-3) 

Once the signature check is bypassed, `WebhooksController#create` dispatches the fully attacker-controlled body to registered handlers with no further authentication: [5](#0-4) 

Two handlers turn this into concrete privilege/state violations:

1. `StatusHandler` writes a `Status` for any commit matching an attacker-supplied `sha`, with no linkage back to a signed CI provider: [6](#0-5) 
This status feeds directly into `Commit#deployable?` and the merge-queue's `all_status_checks_passed?` gate, and can schedule merges via `ProcessMergeRequestsJob`: [7](#0-6) 

2. `MembershipHandler` creates/looks up a `Team` and adds a `member` to it based purely on payload content: [8](#0-7) 
Since `User#authorized?` is driven by `teams.where(id: Shipit.github_teams.map(&:id)).exists?`, forging a `membership` event that adds an arbitrary existing `User` to a `Shipit.github_teams` team grants that user full application access: [9](#0-8) 

The equality that should hold — "webhook payload processed == payload verified by GitHub's HMAC" — is broken whenever `webhook_secret` is absent, which is a supported, documented configuration rather than a misuse of the engine.

### Impact Explanation
This crosses the "escalation into `Shipit.github_teams` authorization" (High) and "unauthorized deploy/rollback/merge" (Critical) impact classes named in scope: an unauthenticated attacker who can reach `/webhooks` on any deployment without a configured `webhook_secret` can (a) forge a `membership` webhook to add themselves (or any known GitHub login) to a team listed in `Shipit.github_teams`, gaining authenticated access to the whole Shipit UI/API, and (b) forge `status` webhooks to mark arbitrary commits as CI-passing, unblocking deploys and the merge queue for repositories they do not control.

### Likelihood Explanation
Any organization that follows the documented setup ("Webhook secret (optional)") and skips this optional field is exposed with zero attacker prerequisites — no session, no `ApiClient` token, no GitHub credentials. The `/webhooks` endpoint is meant to be internet-reachable by design (it receives GitHub's webhooks), so it is exposed on any standard Shipit deployment.

### Recommendation
Reject webhook requests instead of accepting them when `webhook_secret` is not configured for the resolved organization (fail closed, not fail open), and require the header signature to always be validated against a configured secret; log/alert if an organization is registered without one. Additionally, `repository_owner`/`organization` extracted from the still-unverified body should not be used to select the verification key without a secondary corroboration.

### Proof of Concept
Given a Shipit instance configured per `docs/setup.md` without `github.webhook_secret` (or for the specific org handling the target repo), an attacker sends:
```
POST /webhooks
X-Github-Event: membership
Content-Type: application/json

{
  "action": "added",
  "team": {"id": 999, "name": "Deployers", "slug": "deployers", "url": "https://example.com"},
  "organization": {"login": "victim-org"},
  "member": {"login": "attacker-controlled-existing-user"}
}
```
No `X-Hub-Signature` header is required because `verify_webhook_signature` short-circuits to `true`. This causes `MembershipHandler#process` to create/find the `Team` and call `team.add_member(member)`, granting the specified user membership in a team that `Shipit.github_teams` recognizes for authorization — as shown functionally equivalent in the existing (signature-stubbed) test: [10](#0-9) 
Similarly, a forged `status` event with an arbitrary `sha`/`state: "success"` is processed identically to `test/controllers/webhooks_controller_test.rb:42-59`, creating a `Status` record that can mark any tracked commit deployable.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
