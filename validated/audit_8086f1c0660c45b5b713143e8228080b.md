### Title
Webhook signature is verified against the organization named in the payload while handlers act on an unrelated repository named in the same payload - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to check the HMAC signature against using `repository.owner.login` (or `organization.login`) from the **request body itself**, while every webhook handler locates the `Repository`/`Stack` to mutate using `repository.full_name` from that same, otherwise unauthenticated JSON body. Because these two fields are never checked for consistency, an attacker who legitimately knows the webhook secret for *any one* organization configured in a multi-org Shipit deployment can forge a payload whose `repository.owner.login` matches their own org (so signature verification passes) but whose `repository.full_name` names a completely different, victim organization's repository (so the handler acts on it).

### Finding Description
Signature verification:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

Shipit explicitly supports configuring multiple independent GitHub Apps, one per organization, each with its own `webhook_secret`, precisely so different orgs' webhooks can be verified with different keys: [2](#0-1) [3](#0-2) 

Every handler, however, resolves the target repository from a different field of the same attacker-controlled payload, with no cross-check against the organization that was used to authenticate the request:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

`StatusHandler` is worse still: it doesn't even scope to `stacks`, it queries **all** commits globally by SHA:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [5](#0-4) 

`PushHandler` and `CheckSuiteHandler` do use `stacks` (derived from `repository.full_name`), so they are affected by the owner/full_name mismatch: [6](#0-5) [7](#0-6) 

**The broken equality**: verification binds `HMAC_secret(repository_owner)` to the request, but the mutation binds to `repository_name` (full_name), and nothing enforces `repository_owner == owner(repository_name)`. In a single-app deployment this is latent (the same secret is used for any claimed owner, so an outsider without the shared secret gains nothing new). In the officially documented **multi-org** deployment, this becomes a real cross-tenant authentication bypass: knowledge of Org A's webhook secret is sufficient to forge events that Shipit will process as if they came from Org B's repository, because the org name is only used to pick the verification key, never to constrain which repository the handler is allowed to touch.

### Impact Explanation
An attacker who administers a GitHub App for one organization onboarded into a shared Shipit instance (and therefore legitimately possesses that org's `webhook_secret`) can:
- Forge `status` events (`StatusHandler`) to attach a fabricated `success` CI status to an arbitrary commit SHA belonging to a completely unrelated repository/organization, bypassing `ci.require` checks that gate deploys, potentially enabling an **unauthorized deploy**.
- Forge `push` events (`PushHandler`) causing `stack.sync_github` to run against a victim stack using a spoofed `expected_head_sha`.
- Forge `check_suite` events to trigger check-run refresh logic against a victim stack's commits.

This is a cross-repository/cross-organization write triggered purely by a signed-but-misattributed webhook payload, matching the "cross-repository writes" / "unauthorized deploy" impact tier.

### Likelihood Explanation
Requires the target Shipit instance to be configured with multiple GitHub App organizations (a documented, supported configuration) and requires the attacker to control (be an admin of) at least one of the onboarded orgs — a much lower bar than compromising the victim org, requiring no Shipit session, API token, or victim repository access. Given multi-org setups are an explicit, documented feature, this is a realistic deployment shape.

### Recommendation
After verifying the signature, re-derive `repository_owner` from `repository.full_name` (not from the possibly-independent `repository.owner.login`/`organization.login` fields) and reject the payload if it doesn't match the organization whose secret validated the signature. Alternatively, bind the `github_app` used for verification to the specific `Repository` record being targeted and confirm the app/org used to sign the request actually owns that repository before invoking any handler.

### Proof of Concept
1. Shipit is configured (per `docs/setup.md`, "Using Multiple Github Applications") with `OrgA` and `OrgVictim`, each with distinct `webhook_secret`s.
2. Attacker is an admin of the GitHub App for `OrgA` and thus knows `OrgA`'s `webhook_secret`.
3. Attacker crafts a JSON body:
```json
{
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgVictim/victim-repo" },
  "sha": "<victim commit sha>",
  "state": "success",
  "branches": [{"name": "master"}]
}
```
4. Attacker computes `X-Hub-Signature` using `OrgA`'s known `webhook_secret` and POSTs to `/webhooks` with header `X-Github-Event: status`.
5. `verify_signature` calls `Shipit.github(organization: "OrgA")` and the signature matches, so the request passes.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — since it never checks `repository.full_name`/owner at all, it applies the forged `success` status to the victim's commit in `OrgVictim/victim-repo`, regardless of which org authenticated the request.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
