### Title
`OpenedHandler#provision?` ignores `review_stacks_enabled` for `allow_with_label`/`prevent_with_label` behaviors, allowing review-stack creation while review stacks are disabled - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`Repository.review_stacks_enabled` is only consulted in the `allow_all` branch of `provision?` due to Ruby operator precedence (`&&` binds tighter than `||`), leaving the `allow_with_label` and `prevent_with_label` branches unconditioned on it. An attacker who can label their own PR (or trigger auto-labeling via PR body) can trigger review-stack creation and provisioning even when an operator has explicitly set `review_stacks_enabled = false`.

### Finding Description
The claimed binding is: `repository.review_stacks_enabled (false) == the value provision? consults for the allow_with_label branch`. Tracing `provision?`: [1](#0-0) 

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

Due to Ruby's operator precedence, this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`

So when `provisioning_behavior == 'allow_with_label'` and the PR carries the configured label, `provision?` returns `true` regardless of `review_stacks_enabled`. The value the code actually consults for that branch is not `repository.review_stacks_enabled` at all — it never appears in the disjunct — confirming the two sides of the binding diverge (`false != (value used)` because the latter is never evaluated).

Call path: `process` → `respond_to_pull_request_opened?` → `provision?` (true) → `ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!` → `create!` [2](#0-1)  → `scope.create!(stack_attributes)` and `Shipit::ReviewStackProvisioningQueue.add(stack)` [3](#0-2) , which calls `stack.enqueue_for_provisioning` [4](#0-3) .

Attacker request: open a pull request on a repository where the operator has configured `review_stacks_enabled: false` and `provisioning_behavior: allow_with_label`, and apply/have applied the configured `provisioning_label_name` label to that PR (labels can be self-applied by PR authors in many GitHub configurations, or auto-applied via a labeler bot triggered by PR body). No Shipit credentials are needed beyond the ability to open a PR and add a label to it — the webhook itself is verified upstream by signature checks that are unaffected by this logic bug.

No existing guard intercepts this: webhook signature verification only authenticates that GitHub sent the payload, not that the payload's content should trigger provisioning; `ExplicitParameters` only validates types/shape, not business logic; there is no separate `review_stacks_enabled` check downstream in `ReviewStackAdapter#create!` or `ReviewStackProvisioningQueue`.

### Impact Explanation
An attacker-controlled label on the attacker's own PR causes Shipit to create a `ReviewStack` record and enqueue it for provisioning, even though the repository operator explicitly disabled review stacks (`review_stacks_enabled = false`). Provisioning ultimately executes the repository's `shipit.yml`/provisioning tasks (per the review-stacks provisioning pipeline), giving the attacker a path to run their own provisioning configuration on the Shipit host despite the feature being turned off — a control the operator relied on as a safety switch. This matches "an unauthorized deploy" / cross-boundary resource creation for a repository whose operator did not authorize this behavior, and can lead toward RCE via attacker-supplied `shipit.yml` once provisioning tasks run.

### Likelihood Explanation
Preconditions: repository has `provisioning_behavior = 'allow_with_label'` (or `'prevent_with_label'`, inverted) and `review_stacks_enabled = false` — a plausible transitional/misconfigured but legitimate operator state (e.g., disabling review stacks broadly while leaving behavior set for later use). Attacker cost is trivial: open a PR, add a label to it. No secrets, no privileged role, fully repeatable per PR/per repository matching this configuration.

### Recommendation
Add parentheses to make `review_stacks_enabled` a mandatory gate for every branch:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`-style minitest:
1. Create a `Repository` fixture/record with `review_stacks_enabled: false`, `provisioning_behavior: 'allow_with_label'`, `provisioning_label_name: 'x'`.
2. Build `params` for an "opened" PR event whose `pull_request.labels` includes `{ name: 'x' }`.
3. Assert before: `repository.review_stacks_enabled == false`.
4. Invoke `OpenedHandler.new(...).process` (or call `provision?` via `send`).
5. Assert `provision?` (via `send`) returns `true` despite `review_stacks_enabled == false`.
6. Assert a `Shipit::ReviewStack` was created and `stack.awaiting_provision?` is `true`, demonstrating that `repository.review_stacks_enabled == false` did not prevent stack creation/enqueue — the two sides of the binding diverge.
