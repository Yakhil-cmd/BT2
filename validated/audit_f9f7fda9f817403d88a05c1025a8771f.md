### Title
Opaque swap routes can execute attacker-controlled code under the caller’s authorization and steal unrelated wallet funds - (File: contracts/controller/src/strategies/swap.rs)

### Summary
`swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, and `multiply` forward caller-controlled opaque `swap` bytes to the configured router while the caller’s authorization remains active for the invocation tree. [1](#0-0)  If the route reaches an attacker-controlled venue, that code can add unrelated `token.transfer(caller, attacker, amount)` calls to the authorization tree produced by simulation and steal any token the victim signs for. [2](#0-1) 

### Finding Description
`swap_tokens` accepts `swap` as opaque `StrategySwap` bytes, requires only that it is non-empty, and passes it unchanged to `router.execute_strategy`. [3](#0-2)  The controller only constrains its own contract authorization to one exact input-token transfer, but it does not constrain what contracts the router subsequently invokes or what those contracts place under the caller’s authorization tree. [4](#0-3) [1](#0-0) 

The strongest unprivileged entrypoint is `swap_collateral(caller, account_id, current, amount, new, swap)`: the victim supplies or is induced to sign a transaction whose `swap` bytes route through an attacker-controlled venue. [5](#0-4)  During simulation, that venue can perform a token transfer from the victim to the attacker; the host records that transfer as an authorization child beneath the user’s controller call. [6](#0-5)  If the victim signs the returned tree, the hidden transfer is authorized even though it is unrelated to the lending swap. [7](#0-6) 

The controller’s measured-input, overspend, refund, and positive-output checks do not detect the unrelated wallet transfer because they inspect only `token_in` and `token_out` balances held by the controller. [8](#0-7) [9](#0-8) 

### Impact Explanation
An attacker can steal arbitrary unrelated tokens directly from a victim’s wallet while still returning enough `token_out` for the protocol strategy to pass. [9](#0-8)  The stolen amount is not bounded by `amount_in`, the routed collateral, position health, or protocol liquidity; it is bounded by the victim’s wallet balance and signed authorization tree. [10](#0-9)  This is direct theft of user funds and does not require privileged protocol access. [2](#0-1) 

### Likelihood Explanation
Any unprivileged user can submit the `swap` bytes through `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, or `multiply`. [11](#0-10) [12](#0-11)  Exploitation requires a victim to sign the expanded authorization tree produced for a malicious route, which is realistic when users rely on route construction and simulation output rather than manually auditing every nested authorization. [1](#0-0)  The protocol’s output measurement permits the route to remain economically successful while the unauthorized side transfer also succeeds. [13](#0-12) 

### Recommendation
Do not allow opaque routes to invoke unallowlisted contracts while the caller’s authorization is on the call stack. Decode and validate routes in the router or controller, and restrict every venue, pool, token, and callback address to governance-approved contracts. [14](#0-13)  If arbitrary venues are required, execute them through an isolation contract that cannot consume the original caller’s authorization and preserve the existing exact controller-input authorization and measured-output checks. [4](#0-3)  Clients should additionally reject any simulated authorization child other than the expected swap input transfer, but contract-side venue restrictions are needed because wallet UX alone is not a reliable security boundary. [1](#0-0) 

### Proof of Concept
1. The victim holds `USDC` collateral in a solvent account and also holds an unrelated `ATTACK_TOKEN` in their wallet.
2. The attacker deploys a `RogueVenue` contract whose route function calls `ATTACK_TOKEN.transfer(victim, attacker, victim_balance)` before returning normally.
3. The attacker constructs `swap` bytes that consume the swap input, invoke `RogueVenue`, and still return a positive `token_out`.
4. The victim calls `swap_collateral(victim, account_id, current=usdc_market, amount, new=eth_market, swap=malicious_route)`. [2](#0-1) 
5. `swap_tokens` authorizes only the controller’s exact `USDC` input transfer, then invokes the router with the malicious route. [15](#0-14) 
6. During simulation, `RogueVenue` causes `ATTACK_TOKEN.transfer(victim, attacker, victim_balance)` to be recorded as a nested authorization under the victim’s controller call.
7. The victim signs the returned authorization tree; the rogue transfer succeeds, the router returns positive output, the controller accepts the swap, and the attacker receives the victim’s unrelated `ATTACK_TOKEN`. [8](#0-7) [9](#0-8)

pub(crate) fn swap_tokens_or_passthrough(

    refund_to: &Address,
    token_in: &Address,
    amount_in: i128,
    token_out: &Address,
    swap: &StrategySwap,
) -> i128 {
    if token_in == token_out {
        assert_with_error!(env, swap.is_empty(), GenericError::InvalidPayments);

    } else {

/// Authorizes, on behalf of the current contract, one `transfer(from, to, amount)`
/// call on `token_addr` made deeper in the next contract call (for example by
/// the pool). The entry allows no further sub-invocations.
pub fn authorize_transfer_as_current(
    env: &Env,
    token_addr: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
) {
    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);
