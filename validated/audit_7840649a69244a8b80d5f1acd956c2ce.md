### Title
Slowloris DoS via Missing Timeout Configuration on git-sync HTTP Endpoint - (File: main.go)

### Summary
The git-sync `--http-bind` HTTP endpoint (serving liveness `/`, `--http-metrics` `/metrics`, and `--http-pprof` `/debug/pprof/`) is started with the bare `http.Serve(ln, mux)` call, which uses `http.Server` zero-value defaults. No `ReadHeaderTimeout`, `ReadTimeout`, `WriteTimeout`, or `IdleTimeout` is configured, exactly matching the bug class in the referenced report (missing `ReadHeaderTimeout` enabling Slowloris).

### Finding Description
When `--http-bind` (`$GITSYNC_HTTP_BIND`) is set, `main.go` binds a TCP listener and serves an `http.ServeMux` using the package-level `http.Serve` helper: [1](#0-0) 

`http.Serve(ln, mux)` internally constructs an `&http.Server{Handler: mux}` with all timeout fields left at their zero values. Go's `net/http` does not apply any default timeout in this case — a client that opens a TCP connection and sends headers byte-by-byte (or not at all) will keep the connection, and the goroutine handling it, alive indefinitely. Because this handler is reachable from the network (any client that can reach the `--http-bind` address, e.g. other pods in the cluster, or externally if exposed), it satisfies "reachable from untrusted... HTTP request to git-sync."

This is a direct structural analog to the original go-spacemesh finding: an `http.Server`/`http.Serve` invocation lacking `ReadHeaderTimeout` (and here, also lacking `ReadTimeout`/`WriteTimeout`/`IdleTimeout`).

### Impact Explanation
An attacker capable of opening TCP connections to the `--http-bind` port can hold many slow/partial-header connections open simultaneously, exhausting file descriptors and/or goroutines on the git-sync sidecar. Since this same process performs the git sync loop, resource exhaustion (goroutine/FD starvation) can degrade or halt the sync loop, causing **persistent sync denial** — the sidecar's core function (keeping `--root`/`--link` up to date) stops making progress, and the liveness/readiness endpoint itself may also become unresponsive, potentially triggering pod restarts under Kubernetes probes. This maps to the "persistent sync denial" impact category accepted for this analysis.

### Likelihood Explanation
Likelihood is dependent on network reachability of `--http-bind`. Because `--http-bind` is a common flag used specifically to expose Kubernetes startup/liveness probes, it is very often listening on a pod IP reachable at minimum from other pods/namespaces within the cluster (kubelet probes reach it directly), and depending on the deployment's Service/NetworkPolicy configuration may be reachable more broadly. No authentication is required to open a connection to this listener, so any reachable actor can attempt the attack; no special flags beyond `--http-bind` are required to expose the vulnerable code path.

### Recommendation
Replace the bare `http.Serve(ln, mux)` call with an explicit `&http.Server{}` configured with sane timeouts, e.g.:

```go
srv := &http.Server{
    Handler:           mux,
    ReadHeaderTimeout: 5 * time.Second,
    ReadTimeout:       10 * time.Second,
    WriteTimeout:      10 * time.Second,
    IdleTimeout:       60 * time.Second,
}
go func() {
    err := srv.Serve(ln)
    log.Error(err, "HTTP server terminated")
    os.Exit(1)
}()
```

### Proof of Concept
1. Start git-sync with `--http-bind=:8080` (as used in `e2e::expose_http` test, `test_e2e.sh:2895-2935`, which curls `http://localhost:$HTTP_PORT`). [2](#0-1) 
2. From an attacker-reachable network position, open many TCP connections to `:8080` and send partial HTTP request headers very slowly (e.g., one byte every few seconds, never completing the header), or open connections and send nothing at all.
3. Because `http.Serve` applies no `ReadHeaderTimeout`/`ReadTimeout`, these connections are never closed by the server, and each holds a goroutine and file descriptor open indefinitely.
4. Repeating this exhausts available file descriptors/goroutines in the git-sync process, degrading or stopping the health endpoint and the sync loop it shares a process with. [1](#0-0)
