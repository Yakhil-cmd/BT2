### Title
Unhandled exception in `definition template` authentifier evaluation crashes node validation — ([File: definition.js])

### Summary
`validateAuthentifiers()` in `definition.js` evaluates the `definition template` operator inside an asynchronous `conn.query()` callback and, unlike its sibling `validateDefinition()`, does not turn a bad row-count result into a validation error — it unconditionally `throw`s a plain `Error`. Because this throw happens inside a DB-callback (not inside the synchronous call stack that any surrounding `try/catch` covers), it becomes a genuinely uncaught exception that reaches `network.js`'s global `process.on('uncaughtException', ...)` handler, which explicitly re-`throw`s to crash the process.

### Finding Description
`definition.js` implements the `definition template` opcode twice:

- In `validateDefinition()` (used to statically validate the shape of an address/asset definition), the same query is checked gracefully: [1](#0-0) 
returns `cb("template not found or too many")` when the referenced unit doesn't have exactly one `definition_template` message.

- In `validateAuthentifiers()` (used every time a unit's signatures/authentifiers, or an asset's issue/transfer condition, are actually checked against a definition), the equivalent code path is: [2](#0-1) 
`if (rows.length !== 1) throw Error("not 1 template");` — this exception is raised from inside the `db.query` result callback (asynchronous), so it cannot be caught by any synchronous `try/catch` wrapping the call to `evaluate()`/`validateAuthentifiers()`. It propagates as an uncaught exception.

`network.js` installs a global handler that turns any uncaught exception into a full process crash: [3](#0-2) 

`validateAuthentifiers` is also invoked directly for asset issue/transfer spending conditions via `evaluateAssetCondition`, which does not go through `validateDefinition`'s row-count check at all: [4](#0-3) 
So for asset conditions, the only place this row-count is checked is the vulnerable, throwing branch inside `validateAuthentifiers`.

Even for ordinary address definitions where `validateDefinition` runs first and appears to "pre-check" the template, the check and the later re-evaluation are two separate, non-atomic SQL queries executed at different points in time against `main_chain_index<=? AND +sequence='good' AND is_stable=1`. Any state change between the two checks (e.g., the referenced unit becoming non-serial / losing "good" sequence, or stability bookkeeping changing) can make the counts diverge, hitting the throwing branch during authentifier evaluation.

### Impact Explanation
Because the thrown error is not something callers can catch, it crashes the entire ocore process on every full node that validates the offending unit (this is deterministic given consistent DB state across full nodes, since validation is DB-driven and content-driven, not peer-specific). A unit or asset-condition triggering the throw can therefore render the network unable to validate/confirm new units built on top of it, and since asset transfer/issue conditions reach the same vulnerable code, an attacker-crafted asset definition can crash any node attempting to validate a transfer using that asset — potentially freezing funds denominated in that asset (nodes can't process further payments/AA triggers touching it) until the code is patched. This matches the required impact class: "node disagreement on validity or stability" / "a network unable to confirm new units" and AA/asset fund freezing.

### Likelihood Explanation
The `definition template` opcode is a normal, documented address/asset-definition construct reachable by any unprivileged unit poster or asset issuer — no special privileges are required. Triggering the bug only requires constructing (or waiting for) a state where the referenced `definition_template` unit does not resolve to exactly one qualifying row (e.g., referencing a unit with no `definition_template` message, or one that isn't yet stable at the queried `last_ball_mci`, or one where sequence status changed between the two evaluation passes). This is a low-complexity, self-contained data condition, not a p2p/timing race with other peers, making it a Medium-severity, single-poster analog of the GitLab job-log parsing bug (unhandled exception on attacker-influenced parsing state).

### Recommendation
- In `validateAuthentifiers()`'s `definition template` branch, replace `throw Error("not 1 template")` with a graceful failure path (`return cb2(false)` / `fatal_error = ...`) mirroring `validateDefinition()`'s `cb("template not found or too many")`.
- Wrap all `definition template` handling (including `JSON.parse(template)` and `replaceInTemplate`) in `try/catch` and route failures through the callback rather than throwing.
- Consider making the row-count check idempotent/consistent between `validateDefinition` and `validateAuthentifiers` (e.g., compute and cache the resolved template once) to avoid TOCTOU divergence.
- Audit other `throw Error(...)` calls made from inside asynchronous `conn.query` callbacks elsewhere in `definition.js` (e.g., `"seen address"`, `"address"` branches) for the same uncaught-exception pattern.

### Proof of Concept
1. Issue/witness a normal unit `T` that legitimately carries **no** `definition_template` message (or two of them for the same target).
2. Post a new unit `U` authored by (or defining) an address whose definition is:
   `["definition template", [T, {"param1":"value1"}]]`
   satisfying the shape checks in `validateDefinition` at the moment of authoring, but ensure that a later authentifier-evaluation pass over the same definition (during actual signature validation, or by using it as an asset issue/transfer condition via `evaluateAssetCondition`, which never runs `validateDefinition`'s check at all) hits the query `SELECT payload FROM messages JOIN units USING(unit) WHERE unit=T AND app='definition_template' AND main_chain_index<=? AND +sequence='good' AND is_stable=1` returning `0` or `>1` rows.
3. Any full node that validates `U` (or a transfer/issue of the asset using this condition) executes `definition.js`'s `validateAuthentifiers` → `throw Error("not 1 template")` inside the `conn.query` callback.
4. The exception is uncaught, reaches `process.on('uncaughtException', ...)` in `network.js`, and the process crashes (`throw err;`), halting that node's ability to validate/confirm subsequent units.
