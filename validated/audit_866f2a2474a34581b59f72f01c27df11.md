### Title
Restart-triggered `recalculate_stake_rewards` uses live `StakesCache` instead of the epoch-boundary snapshot, letting an attacker's own `Split`/`Deactivate` desync recalculated stake rewards from the original `all_stake_rewards`, causing per-account state divergence between restarted and non-restarted validators - ([File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs])

### Summary
`Bank::recalculate_stake_rewards` (invoked only through `initialize_after_snapshot_restore` -> `recalculate_partitioned_rewards_if_active` after a validator restart mid-distribution) rebuilds the pending `StakeRewards` for undistributed partitions from `self.stakes_cache.stakes()`, i.e. the *current* live delegation state of the restored bank, rather than the delegation snapshot that was frozen at the epoch boundary and used by the original, non-restarted computation in `calculate_stake_rewards_and_commissions`/`calculate_rewards_for_partitioning`. A stake owner (attacker acting only on their own stake account) can submit a `Split` instruction—whose effect on `Delegation::stake` is applied immediately, unlike `Deactivate`, which is gated by warmup/cooldown and `stake_history`—between the epoch-boundary calculation and a validator restart that falls inside the still-active distribution window. This can make the recalculated `PartitionedStakeReward.inflation.stake`/`stake_reward` for that account diverge from the value already baked into other validators' original `all_stake_rewards`, and `build_updated_stake_reward` unconditionally overwrites the account's `StakeStateV2::Stake` delegation with whatever `inflation.stake` value is stored in the (possibly stale-vs.-recalculated) reward record at distribution time.

### Finding Description
- Reward calculation at the epoch boundary is performed once, synchronously, via `calculate_rewards_for_partitioning`/`calculate_stake_rewards_and_commissions`, reading `stake_delegations` from `self.stakes_cache.stakes()` at that exact deterministic slot [1](#0-0) . This result (`all_stake_rewards`) is cached only in the in-memory `Bank::epoch_reward_status` and is **not** part of bank-hash-covered account state, and is also not preserved across a snapshot save/restore.
- After a snapshot restore, `initialize_after_snapshot_restore` calls `recalculate_partitioned_rewards_if_active`, which calls `recalculate_stake_rewards` to rebuild the pending reward list for any partitions not yet distributed [2](#0-1) [3](#0-2) .
- `recalculate_stake_rewards` explicitly sources `stake_delegations` from `self.stakes_cache.stakes()` — the bank's **live/current** delegation state at the (later) restart slot, not a frozen snapshot from the rewarded epoch boundary [4](#0-3) . `point_value` itself is fixed (read from the `EpochRewards` sysvar, which *is* covered by the bank hash), so `point_value`/`total_rewards` cannot diverge — but the **individual per-account** stake amount and resulting `inflation.stake_reward`/`inflation.stake` fed into `redeem_delegation_rewards` can, because they are derived from the live, mutable `Delegation::stake` field.
- `Split` (`solana-stake-program`) immediately mutates the source account's `Delegation::stake` (unlike `Deactivate`, which only sets `deactivation_epoch` and is gated through `delegation_effective_stake`/`stake_history` for the fixed `rewarded_epoch`, so a plain Deactivate mid-distribution does not retroactively change the reward computed for the already-completed `rewarded_epoch`). If an attacker performs `Split` on their own stake account between the epoch-boundary calculation and a validator's restart (while distribution is still active), the restarted validator's recalculation will compute a stake reward for that pubkey using the post-Split (reduced) `Delegation::stake`, while validators that did not restart still hold the pre-Split `all_stake_rewards` value computed at the epoch boundary.
- At distribution time, `build_updated_stake_reward` takes whichever calculation's `inflation.stake` is present in `partition_rewards.all_stake_rewards` and unconditionally overwrites the account's `StakeStateV2::Stake(meta, new_stake, flags)` with it [5](#0-4) , so the resulting on-chain delegation/lamports for that stake account differ between the restarted and non-restarted validator sets for the same slot/partition — a bank-hash-affecting divergence.
- Existing tests (`test_recalculate_stake_rewards`, `test_recalculate_partitioned_rewards`, `test_recalculate_alpenglow_rewards_after_partial_distribution_uses_original_denominator`) only validate the no-intervening-stake-mutation case, or the specific already-fixed Alpenglow vote-account denominator race; none of them cover an attacker-initiated `Split` (or other immediate delegation-mutating instruction) occurring between the epoch-boundary calculation and a restart-triggered recalculation [6](#0-5) [7](#0-6) .

### Impact Explanation
This is a cross-node state/consensus divergence: validators that restart mid-distribution recompute a different stake-reward amount/delegation for an attacker-influenced stake account than validators that never restarted, both of which then apply their (different) `inflation.stake`/`stake_reward` values to the *same* on-chain account via `store_stake_accounts_in_partition`/`build_updated_stake_reward` at the same slot/partition. That produces differing account state and therefore differing bank hashes for the same slot between otherwise-honest nodes — the exact "deterministic-state" violation category in scope (consensus/hash divergence).

### Likelihood Explanation
Preconditions: (1) partitioned rewards distribution must be active across more than one block (multi-partition distribution, which is common on large validator sets), (2) at least one validator must restart from a snapshot while distribution is still in progress (an operationally common event — process crash/restart, not attacker-controlled), and (3) the attacker must submit a normal, permissionless `Split` instruction on their own stake account between the epoch boundary and that restart. All three attacker-controlled/observable conditions are trivially reachable by an unprivileged user; only the restart timing is outside attacker control, but the attacker does not need to control it — they only need to race their `Split` against whatever restarts happen to occur, which is repeatable by simply submitting the instruction on every epoch boundary and waiting.

### Recommendation
`recalculate_stake_rewards` should not read live `stakes_cache` delegation amounts for accounts already reflected in the frozen epoch-boundary reward set. Either (a) persist/snapshot the original `all_stake_rewards`/`epoch_reward_status` across restarts so no recomputation from live state is ever needed, or (b) if recomputation must occur, source `stake_delegations` from a delegation snapshot taken/pinned at the rewarded-epoch boundary (e.g., stored alongside `EpochStakes`) rather than from `self.stakes_cache.stakes()` at the restart slot, so recalculated rewards are invariant to any stake-mutating instructions executed after the epoch boundary.

### Proof of Concept
Rust integration test in `runtime/src/bank/partitioned_epoch_rewards/calculation.rs` test module:
1. Build a `RewardBank` with several delegations and `num_rewards_per_block` small enough to force multiple distribution partitions (as in `test_recalculate_stake_rewards`).
2. Advance to the epoch boundary; capture `all_stake_rewards` from `EpochRewardPhase::Calculation` (the "non-restart" baseline path A, which never recalculates).
3. Fork/clone the same bank into path B. Before crossing into the distribution phase, submit a `Split` transaction on an attacker-controlled stake account included in an as-yet-undistributed partition, moving part of its lamports/stake to a new account (a normal, unprivileged instruction).
4. Advance path B to a distribution block, then simulate restart: reset `feature_set` and call `bank.initialize_after_snapshot_restore(...)` (as in `test_initialize_after_snapshot_restore`), forcing `recalculate_stake_rewards` to run against the post-`Split` `StakesCache`.
5. Continue distributing all remaining partitions on both path A (never restarted) and path B (restarted-after-Split) to completion.
6. Assert divergence: `path_A.get_account(&attacker_stake_pubkey)` vs `path_B.get_account(&attacker_stake_pubkey)` differ in `lamports()`/`delegation().stake`, and/or `path_A.hash() != path_B.hash()` for the corresponding slot, and `total_stake_rewards_lamports` distributed for that pubkey differs between the two paths — demonstrating that identical starting reward intent produced non-identical final state solely due to restart timing plus the attacker's own `Split`.

    /// updates Bank::epoch_reward_status. This method assumes that reward
    /// commissions have already been calculated and delivered, and *only*
    /// recalculates stake rewards
    pub(in crate::bank) fn recalculate_partitioned_rewards_if_active<F, TP>(

    ) where
        F: FnOnce() -> TP,
        TP: std::borrow::Borrow<ThreadPool>,
    {
        let epoch_rewards_sysvar = self.get_epoch_rewards_sysvar();
        if epoch_rewards_sysvar.active {
            let thread_pool = thread_pool_builder();
            let (stake_rewards, partition_indices) =
                self.recalculate_stake_rewards(&epoch_rewards_sysvar, thread_pool.borrow());
            self.set_epoch_reward_status_distribution(
                epoch_rewards_sysvar.distribution_starting_block_height,
                stake_rewards,
                partition_indices,
            );
        }
    }
