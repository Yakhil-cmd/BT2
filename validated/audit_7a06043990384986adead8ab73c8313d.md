## Title
Unhandled Exception During AA Trigger/Formula Evaluation Crashes the Node Process (Network-Wide DoS) - (File: `network.js`, `aa_composer.js`, `formula/evaluation.js`)

### Summary
An unprivileged user can post a normal payment unit to an Autonomous Agent (AA) address with crafted `data`/messages that cause the deterministic AA trigger execution engine (`aa_composer.handleTrigger` → `formula/evaluation.js`) to throw a raw, unhandled JavaScript exception rather than a controlled formula/bounce error. Because ocore installs a global `process.on('uncaughtException')` handler that deliberately re-throws to crash the process "to avoid ending up in an inconsistent state," any such exception kills the node. Since every full node in the network must deterministically execute the same AA trigger to reach consensus on the resulting state, the same crafted unit will crash every full node that processes it — a network-wide denial of service. This mirrors CVE-2018-1050, where insufficiently sanitized RPC input to a spooler service crashed the daemon; here, insufficiently constrained AA trigger input crashes the ocore full-node process itself.

### Finding Description
The code explicitly acknowledges that AA trigger evaluation "would crash": when a submitted unit contains an output to an AA address and `conf.bDryRunNewTriggers` is set, ocore proactively dry-runs the trigger and comments "if it would crash, let it crash now, not when we execute the trigger for real": [1](#0-0) 

This dry run (and, more importantly, the real trigger execution during `writer.saveJoint`/`main_chain` stabilization for every full node) calls into `aa_composer.dryRunPrimaryAATrigger` → `handleTrigger` → `evaluateAA`/`replace`, which feeds attacker-controlled `trigger.data` and AA definition formulas into the oscript evaluator: [2](#0-1) [3](#0-2) 

`aa_validation.js` bounds many structural aspects of trigger `data` (size ≤ 10 KB via `isTooBigObj`, string length limits, etc.), but this is a best-effort allow-list rather than a complete guarantee that every downstream code path in `formula/evaluation.js` handles all attacker-controlled shapes/types safely: [4](#0-3) 

The formula evaluator itself contains numerous "should never happen" assumptions expressed as bare `throw Error(...)` (not passed through the `cb`/bounce error-handling machinery), for example in `evaluate()`'s entrypoint sanity checks and various case handlers throughout `formula/evaluation.js`: [5](#0-4) 

If attacker-supplied `trigger.data` (or interactions between `data`, `params`, and the targeted AA's own definition) can reach one of these "impossible" branches — a class of bug the CVE report calls "missing input sanitization checks on some of the input parameters" — the resulting exception is not caught by the formula evaluator's controlled error path. It propagates up through the async callback chain and becomes an uncaught exception at the top of the event loop, hitting the global handler: [6](#0-5) 

That handler explicitly re-throws (`throw err`) specifically to crash the process rather than continue in a possibly inconsistent state, which is the deliberate DoS trigger point.

### Impact Explanation
Because AA execution must be deterministic and identical across all full nodes to reach consensus (the same trigger unit is executed by every full node when it becomes the relevant MC unit), a single maliciously crafted unit sent to any AA address can crash every full node in the network simultaneously once it is processed/stabilized. This satisfies "a network unable to confirm new units": with all full nodes down or continuously crash-looping on the same poisoned unit (since the unit is already saved/known and would be re-processed on node restart), the network cannot make progress. This is a more severe outcome than the underlying CVE (which crashed only an auxiliary print-spooler daemon per host); here the core validation/consensus process itself is affected across the whole node population.

### Likelihood Explanation
The attack surface is directly reachable by any unprivileged actor who can post a signed unit (a standard payment with `data`, as used to trigger AAs) — no special privileges, peer/hub trust, or node-operator access are required. The `light/dry_run_aa` network command additionally allows any connected (even light) client to directly invoke `dryRunPrimaryAATrigger` with a hand-crafted trigger object without ever posting a real unit, giving attackers a cheap oracle to search for crash-inducing inputs before broadcasting a real malicious unit. The comment in `network.js` ("if it would crash, let it crash now") shows the developers are aware that crashes are possible from trigger evaluation, indicating the underlying input-sanitization gaps are a recognized but not fully closed risk class — precisely analogous to the CVE's "missing input sanitization checks on some of the input parameters."

### Recommendation
- Wrap all AA trigger/formula evaluation (`handleTrigger`, `evaluateAA`, `formula/evaluation.js` `evaluate()`) in an outer `try/catch` boundary that converts any unexpected exception into a formula/bounce error instead of letting it escape as an uncaught exception.
- Audit `formula/evaluation.js` and `aa_composer.js` for every `throw Error(...)` that is reachable with attacker-controlled data (as opposed to true internal invariants) and replace them with graceful `cb(error)`/bounce paths.
- Consider making the `light/dry_run_aa` handler run trigger evaluation in an isolated context (e.g., a worker/child process or with a hardened try/catch + resource limits) so that malformed triggers submitted purely for probing cannot destabilize the serving full node.
- Add fuzz testing of AA `data`/`params`/formula inputs (deeply nested objects, prototype-polluting keys, extreme numeric values, mismatched types) against `dryRunPrimaryAATrigger` to find and fix additional un-caught throw sites before they can be exploited on mainnet.

### Proof of Concept
1. Identify or deploy an AA whose definition performs an operation on `trigger.data` in a way that is only "usually" safe due to upstream structural checks (e.g., relies on `trigger.data.x` being of an expected type/shape that `aa_validation.js`'s allow-list does not fully pin down for nested structures).
2. As an unprivileged wallet, either:
   - a) Connect as a light client and repeatedly send `light/dry_run_aa` requests with varied malformed `trigger.data` payloads to probe for a JS-level uncaught exception (bypassing bounce/error handling) without spending any funds, or
   - b) Post a real payment unit to the AA's address with the crafted `data` payload once a crash-inducing shape is found.
3. When the crafted trigger reaches a code path in `formula/evaluation.js` that performs an operation not defensively guarded (rather than returning a controlled formula error), the exception propagates uncaught to `process.on('uncaughtException')` in `network.js`, which re-throws and terminates the node process.
4. Because trigger execution for a stabilized unit must be replayed identically by every full node reaching that MCI, all full nodes that receive/process the unit crash in the same way, halting network-wide confirmation of new units.
