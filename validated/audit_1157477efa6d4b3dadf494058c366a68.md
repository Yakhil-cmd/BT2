### Title
Unguarded `onERC721Received` / `onERC20Received` Callbacks Allow Registered Token Contracts to Spoof Bridge Deposit Requests Without Actual Asset Transfer — (`contracts/service_chain/bridge/BridgeTransferERC721.sol`, `contracts/service_chain/bridge/BridgeTransferERC20.sol`)

---

### Summary

`BridgeTransferERC721.onERC721Received` and `BridgeTransferERC20.onERC20Received` are `public` functions with no check that an actual token transfer to the bridge occurred. Any registered token contract can call them directly, causing the bridge to emit a `RequestValueTransferEncoded` / `RequestValueTransfer` event and increment `requestNonce` without holding the corresponding asset. The bridge operator on the counterpart chain will faithfully process the spoofed event, resulting in unauthorized minting or transfer of bridged assets.

---

### Finding Description

The 1-step deposit flow is implemented in `ERC721ServiceChain.requestValueTransfer`:

```solidity
// contracts/testing/sc_erc721/ERC721ServiceChain.sol:43-47
function requestValueTransfer(uint256 _uid, address _to, bytes calldata _extraData) external {
    transferFrom(msg.sender, bridge, _uid);   // ← actual transfer
    IERC721BridgeReceiver(bridge).onERC721Received(msg.sender, _uid, _to, _extraData);
}
```

The bridge's callback is:

```solidity
// contracts/service_chain/bridge/BridgeTransferERC721.sol:109-118
function onERC721Received(
    address _from,
    uint256 _tokenId,
    address _to,
    bytes memory _extraData
)
    public          // ← no access control beyond onlyRegisteredToken(msg.sender)
{
    _requestERC721Transfer(msg.sender, _from, _to, _tokenId, _extraData);
}
```

`_requestERC721Transfer` checks `onlyRegisteredToken(msg.sender)` and `onlyUnlockedToken(msg.sender)`, but **never verifies that the token was actually transferred to the bridge**:

```solidity
// contracts/service_chain/bridge/BridgeTransferERC721.sol:74-106
function _requestERC721Transfer(...) internal
    onlyRegisteredToken(_tokenAddress)
    onlyUnlockedToken(_tokenAddress)
{
    require(isRunning, "stopped bridge");
    // ... tokenURI call (non-reverting) ...
    if (modeMintBurn) {
        ERC721Burnable(_tokenAddress).burn(_tokenId);  // ← only guard in mintBurn mode
    }
    emit RequestValueTransferEncoded(...);
    requestNonce++;   // ← state mutated unconditionally in lock/unlock mode
}
```

In **lock/unlock mode** (`modeMintBurn = false`), the burn call is skipped entirely. The function emits the event and increments `requestNonce` with no proof of custody.

The identical pattern exists for ERC20:

```solidity
// contracts/service_chain/bridge/BridgeTransferERC20.sol:111-121
function onERC20Received(...) public {
    _requestERC20Transfer(msg.sender, _from, _to, _value, _feeLimit, _extraData);
}
```

where `_requestERC20Transfer` in lock/unlock mode also emits `RequestValueTransfer` and increments `requestNonce` without verifying the bridge received the tokens (the `_payERC20FeeAndRefundChange` call only processes fee accounting from the bridge's existing balance, and is a no-op when `feeReceiver == address(0)` or `fee == 0`).

---

### Impact Explanation

The bridge operator's Go relay (`node/sc/bridge_manager.go:handleRequestValueTransferEvent`) processes every `RequestValueTransferEncoded` / `RequestValueTransfer` event it observes on-chain and calls `handleERC721Transfer` / `handleERC20Transfer` on the counterpart bridge:

```go
// node/sc/bridge_manager.go:344-350
case ERC721:
    uri := GetURI(ev)
    handleTx, err = bi.bridge.HandleERC721Transfer(auth, txHash, from, to,
        ctpartTokenAddr, valueOrTokenId, requestNonce, blkNumber, uri, extraData)
```

On the counterpart bridge in **mint/burn mode**:

```solidity
// contracts/service_chain/bridge/BridgeTransferERC721.sol:66-67
if (modeMintBurn) {
    require(ERC721MetadataMintable(_tokenAddress).mintWithTokenURI(_to, _tokenId, _tokenURI), "mint failed");
```

This mints a new NFT to the attacker-controlled `_to` address with no corresponding deposit on the source chain — **unauthorized mint of a bridged asset**.

In lock/unlock mode on the counterpart chain, `IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId)` is called; this reverts if the bridge doesn't hold that token ID, limiting the impact to nonce corruption and DoS in that configuration.

Additionally, `requestNonce` is permanently incremented on the source bridge, creating a gap in the nonce sequence that the VT-recovery mechanism will attempt to re-process, potentially causing further state divergence.

---

### Likelihood Explanation

The prerequisite is that `msg.sender` must be a registered token contract (`onlyRegisteredToken`). Token registration is owner-only. However:

1. A token contract registered by the bridge owner may itself contain a function that calls `bridge.onERC721Received` without first calling `transferFrom` (e.g., a misconfigured or malicious token).
2. A supply-chain-compromised token contract upgrade could introduce this call path post-registration.
3. The `onERC721Received` function selector (`0xcf0da290`) is publicly callable by any EOA or contract; if the attacker can make a registered token contract execute arbitrary calls (e.g., via a callback or reentrancy), the attack succeeds.

The standard `ERC721ServiceChain` always calls `transferFrom` before the callback, so it is not directly exploitable. The risk is from non-standard or malicious registered tokens.

---

### Recommendation

Add an explicit custody check inside `onERC721Received` and `onERC721Received` to verify the bridge actually received the token before processing the request:

```solidity
function onERC721Received(
    address _from,
    uint256 _tokenId,
    address _to,
    bytes memory _extraData
)
    public
{
    // Verify the token is now owned by this bridge contract
    require(
        IERC721(msg.sender).ownerOf(_tokenId) == address(this),
        "token not transferred to bridge"
    );
    _requestERC721Transfer(msg.sender, _from, _to, _tokenId, _extraData);
}
```

For ERC20, verify the bridge's balance increased by at least `_value + _feeLimit` since the last call (or use a snapshot approach). Alternatively, restrict `onERC721Received` / `onERC20Received` to only be callable from the registered token contract's known `requestValueTransfer` entry point by checking `msg.sender` against a whitelist of known-safe token implementations.

### Proof of Concept

**Setup:** Bridge deployed in lock/unlock mode on source chain; counterpart bridge deployed in mint/burn mode.

**Attacker contract (registered as a token):**
```solidity
contract MaliciousToken is ERC721, Ownable {
    address public bridge;
    constructor(address _bridge) { bridge = _bridge; }

    // Called by attacker to spoof a deposit of tokenId=999 to attacker's address
    function spoofDeposit(address attacker) external {
        // No transferFrom — token 999 is never transferred to the bridge
        IERC721BridgeReceiver(bridge).onERC721Received(
            attacker,   // _from (spoofed)
            999,        // _tokenId (never deposited)
            attacker,   // _to (attacker receives on counterpart)
            ""
        );
    }
}
```

**Steps:**
1. Bridge owner registers `MaliciousToken` as a token pair.
2. Attacker calls `MaliciousToken.spoofDeposit(attacker)`.
3. Source bridge emits `RequestValueTransferEncoded(ERC721, attacker, attacker, maliciousToken, 999, nonce=0, ...)` and sets `requestNonce = 1`.
4. Bridge operator relay picks up the event and calls `counterpartBridge.handleERC721Transfer(txHash, attacker, attacker, counterpartToken, 999, 0, blockNum, "", "")`.
5. Counterpart bridge (mint/burn mode) calls `counterpartToken.mintWithTokenURI(attacker, 999, "")`.
6. Attacker now holds token ID 999 on the counterpart chain without ever depositing anything on the source chain.

**Corrupted value:** `requestNonce` on source bridge is incremented to 1 with no corresponding asset held; counterpart bridge mints token 999 to attacker with no backing deposit. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) [8](#0-7)
