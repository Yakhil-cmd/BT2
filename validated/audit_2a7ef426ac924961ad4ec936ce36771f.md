This confirms the vulnerability. The base `Handler` class provides a `stacks` helper that scopes lookups to `Repository.from_github_repo_name(repository_name)&.stacks`, derived from `payload.dig('repository', 'full_name')` [1](#0-0) . Other handlers (`pull_request/*`) use this scoping, but `StatusHandler#process` bypasses it entirely and queries `Commit.where(sha: params.sha)` globally with no repository/stack filter [2](#0-1) .

### Title
Cross-repository status webhook mutates arbitrary stacks' commits via unscoped SHA lookup - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits by bare SHA across the entire `commits` table, with no filter on the repository that authenticated the webhook, then writes a `Status` row using each matched commit's own `stack_id`. Combined with `Commit#blocked?`/`Status::Common#blocking?`, which key off `stack.blocking_statuses` and `context`, a status event authenticated for one repository can flip `blocked?`/`deployable?` for a stack belonging to a completely different repository, as long as a `Commit` row with the same SHA exists in both.

### Finding Description
The broken binding: the invariant claims `status.stack_id == stack_of(repository_that_authenticated(request))`. In code, this equality does not hold. `WebhooksController#verify_signature` only checks that the signature matches the GitHub App/organization secret associated with `repository_owner` from the payload [3](#0-2)  — it never ties the verified payload to a specific `stack_id`. `StatusHandler#process` then does:

```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [2](#0-1) 

This iterates over **every** `Commit` row in the database matching that SHA, regardless of which `stack`/repository it belongs to — unlike every other handler (e.g. `pull_request/*`), which uses the base `Handler#stacks` helper that scopes by `Repository.from_github_repo_name(payload.dig('repository','full_name'))` [1](#0-0) .

For each matched commit, `create_status_from_github!` calls `statuses.replicate_from_github!(stack_id, github_status)`, creating a `Status` bound to that commit's own `stack_id` [4](#0-3) . `Status::Common#blocking?` then evaluates `commit.blocking_statuses.include?(context)` (delegated to `stack.blocking_statuses`) [5](#0-4) , and `Commit#blocked?` scans `stack.commits.reachable...any?(&:blocking?)` to gate `deployable?` [6](#0-5) .

Exploit flow: an attacker who administers their own GitHub repository (in any organization configured on the Shipit instance) can, via GitHub's real Status API, post a status with `context: "shipit/checks"` on a commit SHA in their own repo. If that same SHA also exists as a `Commit` row tracked under a victim's stack (trivially achievable since git SHAs are content-addressed — e.g., via a fork sharing history, or a cherry-picked/identical commit), GitHub delivers a legitimately-signed webhook (signed with the attacker's own org's secret) to Shipit. `verify_signature` passes correctly (it is a real GitHub webhook), but `StatusHandler#process` then writes a `Status` against the *victim's* stack's commit — because the lookup is by bare SHA with no repository binding.

None of the existing guards catch this: `verify_signature` validates provenance of the org, not the target stack; `ExplicitParameters` only validates payload shape (`sha`, `state`, `context`, etc.) [7](#0-6) ; there is no `stacks`/repository-scoping check as used by the other handlers.

### Impact Explanation
A status forced onto `shipit/checks` (or any context in a victim stack's `blocking_statuses`) can flip `Commit#blocking?` and therefore `Commit#blocked?`, which gates `deployable?` and continuous delivery scheduling (`schedule_continuous_delivery`) [6](#0-5) . This lets an attacker who authenticated only for their own repository force a block or unblock condition, and trigger merge/deploy scheduling (`stack.schedule_merges`, `ContinuousDeliveryJob`) [8](#0-7) , on a stack belonging to a different repository/tenant. This is a cross-tenant state write: "a payload for one repository mutating another's stack/commit," matching the Critical category in the rules.

### Likelihood Explanation
Preconditions: the victim stack must have `blocking_statuses` configured for the forced context, and a `Commit` record with an identical SHA must exist under both the attacker's authenticated repository and the victim's stack. This is feasible without any privileged access — an attacker only needs to own/administer a public (or forked) repository with shared git history/content with the target, and use their own valid GitHub credentials to set a status via the real GitHub API; GitHub itself signs and delivers the resulting webhook. No Shipit secrets, sessions, or team membership are required. The attack is repeatable against any stack sharing a commit SHA with an attacker-controlled repo.

### Recommendation
Scope `StatusHandler#process` (and `Commit.where(sha: ...)`) to only the commits belonging to stacks associated with `payload.dig('repository', 'full_name')`, mirroring the `Handler#stacks` pattern used by other handlers, e.g. `stacks.flat_map { |stack| stack.commits.where(sha: params.sha) }`, instead of an unscoped `Commit.where(sha:)` query.

### Proof of Concept
minitest plan (`test/models/webhooks/status_handler_test.rb`, illustrative — not present in repo, must be added):
```ruby
test "status for one repo must not affect a commit belonging to another repo's stack" do
  attacker_repo = create_repository(full_name: "attacker/evil")
  victim_stack = shipit_stacks(:shipit) # tied to repository "shopify/shipit-engine" e.g.
  shared_sha = "deadbeef" * 5
  victim_commit = victim_stack.commits.create!(sha: shared_sha, ...)
  victim_stack.update!(blocking_statuses: ['shipit/checks'])

  assert_equal false, victim_commit.reload.blocked?

  payload = {
    'sha' => shared_sha,
    'state' => 'failure',
    'context' => 'shipit/checks',
    'repository' => { 'full_name' => attacker_repo.full_name }
  }
  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  assert_equal true, victim_commit.reload.blocked?,
    "status authenticated for attacker/evil must not block victim stack's commit"
end
```
Both sides of the equality (`status.stack_id` vs. `stack_of(repository_that_authenticated_request)`) should be asserted explicitly before/after; currently they diverge because `StatusHandler#process` has no repository/stack scoping [2](#0-1) .
