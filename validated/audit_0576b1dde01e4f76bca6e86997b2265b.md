### Title
A crafted `swap_collateral` route can poison the caller’s signed authorization tree and steal unrelated wallet tokens - (File: `contracts/controller/src/strategies/swap.rs`)

### Summary
`swap_collateral` accepts attacker-influenced route bytes and invokes the configured router while the account owner’s authorization is active. [1](#0-0)  A route venue can invoke a token transfer from the caller; Soroban records that transfer as a child of the caller’s `swap_collateral` authorization, and it executes when the victim signs the simulated tree. [2](#0-1) 

### Finding Description
`swap_collateral(caller, account_id, current, amount, new, swap)` authenticates `caller` and requires ownership or delegation before routing the withdrawn collateral through `swap`. [3](#0-2)  `swap_tokens` passes the caller-supplied `swap` bytes to `router.execute_strategy`; the controller only bounds its own input spend and requires a positive measured output. [4](#0-3)  The route payload can name an arbitrary pool address, and that pool executes below the caller’s authorization boundary. [5](#0-4)  If malicious venue code calls `token.transfer(victim, attacker, amount)`, simulation records it as a child authorization beneath `swap_collateral`, and signing that tree authorizes the unrelated wallet transfer. [6](#0-5) 

### Impact Explanation
An attacker can steal any token balance held by the victim’s wallet, including assets that were never supplied to or listed by the lending protocol. [7](#0-6)  The swap itself can still produce its advertised output and pass all controller risk checks, so the transaction appears successful while the separate wallet transfer is executed. [8](#0-7)  This is theft of user funds, not a bounded loss of the routed collateral input. [9](#0-8) 

### Likelihood Explanation
Exploitation requires the victim to sign a crafted transaction containing a malicious authorization child, so it is not freely exploitable without user interaction. [10](#0-9)  The attacker only needs to deploy or identify a venue that performs the extra `victim -> attacker` transfer and deliver the crafted route to the victim. [11](#0-10)  Because the authorization tree is generated during transaction simulation and may be presented through a link or wallet flow, a user can miss the unrelated child transfer while approving an otherwise successful collateral swap. [12](#0-11) 

### Recommendation
Constrain strategy routes to governance-reviewed venue contracts or add route-level venue allowlisting before dispatch. [13](#0-12)  At minimum, make every client fail closed when the simulated caller authorization tree contains anything other than the expected operation-specific children, and display every child contract, function, token, recipient, and amount before signing. [14](#0-13)  Protocol documentation should prominently warn that `swap` bytes can introduce arbitrary downstream code under the caller’s authorization. [15](#0-14) 

### Proof of Concept
The repository’s regression test constructs a router route whose named hop pool calls `token.transfer(alice, attacker, WALLET_BALANCE)` during `swap_collateral`. [11](#0-10)  Simulation records the malicious wallet transfer as a sub-invocation of Alice’s `swap_collateral` authorization. [16](#0-15)  With an honest tree lacking that child, the host rejects the transfer and rolls back; after signing the simulated poisoned tree, Alice’s wallet balance becomes zero and the attacker receives `WALLET_BALANCE`. [10](#0-9)

```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
user.
```
