### Title
Attacker-selected multi-org GitHub App config lets forged webhooks bypass signature verification - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` config (and therefore which `webhook_secret`) to validate a webhook against based on an **unauthenticated field taken from the raw request body itself** (`repository.owner.login` / `organization.login`), before the signature has been checked. `GitHubApp#verify_webhook_signature` unconditionally returns `true` when the selected config has no `webhook_secret` set. In a multi-organization Shipit deployment, an attacker who knows (or guesses) the name of any configured organization that has a blank/unset `webhook_secret` can forge the `repository.owner.login`/`organization.login` field to select that organization's config, causing the signature check to be bypassed entirely and the forged payload processed as a legitimate GitHub event for whatever `repository.full_name` the attacker also puts in the payload.

### Finding Description
This mirrors the C4 report's bug class: a verification/limit check is computed on a value that does not correspond to the value actually used afterwards. In `M-05`, `maxCap` is checked against the pre-fee mint amount while the post-fee amount is what's actually minted. Here, the *organization used to select the trust anchor* (which `webhook_secret` to verify against) is taken from the same unverified payload that the signature is supposed to protect — creating an equality that should hold (`verified_org == secret_used_for_verification`) but is actually attacker-controlled before any verification occurs:

```ruby
# app/controllers/shipit/webhooks_controller.rb
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end

`Shipit.github(organization:)` looks up the per-organization config from `secrets.github` using this attacker-supplied string as the key:
```ruby
def github(organization: github_default_organization)
  ...
  config = github_app_config(organization)
  raise GithubOrganizationUnknown, organization if config.nil?
  @github[organization] ||= GitHubApp.new(organization, config)
end
``` [3](#0-2) 

And `GitHubApp#verify_webhook_signature` trivially passes if that org's config has no secret configured:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [4](#0-3) 

The test fixture `secrets_double_github_app.yml` demonstrates that multiple orgs can be configured, and at least one (`OrgTwo`) can have `webhook_secret: # nil`: [5](#0-4) 

Since the org used for signature selection (`repository_owner`) and the repository that is ultimately acted on (`params.dig('repository', 'full_name')`, used deeper in the webhook handlers) are independently attacker-controlled fields in the same unauthenticated JSON body, an attacker can set `repository.owner.login` to the no-secret org while setting `repository.full_name` to any tracked repository/stack, causing `create` to dispatch the forged event (e.g. `push`, `status`, `check_suite`) to `Shipit::Webhooks.for_event(event)` handlers as if it were a genuine, signed GitHub webhook for that repository.

### Impact Explanation
This breaks the binding "the organization whose secret authenticated the webhook == the organization/repository the event is applied to." A forged `push` event can enqueue `GithubSyncJob` for an arbitrary tracked stack, and forged `status`/`check_suite` events can fabricate commit statuses/check runs, which downstream deploy-safety logic (CI/status gating before deploy) may rely on. This can lead to bypassing deploy safety checks and enabling an unauthorized deploy — matching the "unauthorized deploy" High-impact category — without any GitHub credentials, session, or API token.

### Likelihood Explanation
Exploitability requires the operator to run a multi-organization Shipit configuration (`secrets.github` keyed by org, per `github_app_config`) where at least one configured organization omits `webhook_secret` (shown as a supported/documented configuration shape in the fixtures). Given documentation explicitly treats `webhook_secret` as "optional" per app, this is a plausible real-world misconfiguration, not a purely theoretical one, and the request requires no authentication of any kind — just an HTTP POST to `/webhooks` with attacker-chosen JSON.

### Recommendation
Do not let the unauthenticated request body select the verification key. Instead:
- Require `webhook_secret` to be present for every configured organization/app (fail closed instead of `return true unless webhook_secret`).
- Alternatively, verify the signature against every configured app's secret (or a global secret) rather than looking one up keyed by an attacker-controlled payload field, and only then use the verified event to determine which organization/repository it pertains to.
- Reject webhooks where the verified organization does not match the `repository.owner.login` used later by handlers to resolve the `Stack`/`Repository`.

### Proof of Concept
1. Deploy Shipit with a multi-org `secrets.github` config where `OrgWithSecret` has a strong `webhook_secret` and `OrgNoSecret` has no `webhook_secret` set (as in `test/dummy/config/secrets_double_github_app.yml`'s `OrgTwo`).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": { "owner": { "login": "OrgNoSecret" }, "full_name": "OrgWithSecret/victim-repo" },
  "after": "<attacker-chosen-sha>"
}
```
No `X-Hub-Signature` header (or any bogus value) is required.
3. `repository_owner` resolves to `"OrgNoSecret"`, `Shipit.github(organization: "OrgNoSecret")` returns a `GitHubApp` with `webhook_secret == nil`, so `verify_webhook_signature` returns `true` unconditionally per [6](#0-5) , and the forged `push` event is processed for `OrgWithSecret/victim-repo`, enqueuing a `GithubSyncJob` for that stack despite never presenting a valid signature for `OrgWithSecret`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
