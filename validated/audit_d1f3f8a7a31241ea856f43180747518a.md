### Title
Unvalidated route hop addresses let attacker-supplied contracts execute under the caller's authorization tree and drain the caller's wallet - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The HashBrown analog is CWE-20: unvalidated user input reaching a dangerous execution sink. In XOXNO Lending, every routed strategy (`swap_collateral`, `swap_debt`, `multiply`, `repay_debt_with_collateral`, and direct `Router::execute_strategy`) accepts a caller-supplied `swap_xdr` whose `assets` registry names arbitrary token and pool addresses. The controller and router place no allowlist on those addresses, so the router invokes any contract the payload names — and Soroban attributes every sub-invocation to the caller's signed authorization tree, giving the rogue hop code the caller's authority for arbitrary token transfers.

### Finding Description
`swap_tokens` in `contracts/controller/src/strategies/swap.rs:13-55` snapshots balances, grants the router exactly one `authorize_transfer_as_current` for the input, then calls `router.execute_strategy(&controller, &amount_in, swap)` inside the flash guard (`swap.rs:34-38`). The `swap` payload (`StrategySwap` XDR) is never inspected: the controller validates only measured input spend (`in_after <= in_before`, `actual_spent <= amount_in` at `swap.rs:41-48`) and positive measured output (`verify_router_output`, `swap.rs:75-84`). The router, per its README and threat model, calls "the pool and token addresses its payload names and keeps no allowlist of them" (`docs/explanation/threat-model.md:154-165`); adapters such as `venues/sushi.rs:20-50` and `venues/aquarius/swap.rs:11-24` invoke `token0`/`token1`/`get_oracle_hints`/`swap` on whatever address the hop encodes.

Because those hop calls sit below the caller's `require_auth` on the strategy entrypoint, any `token.transfer(caller, attacker, x)` a rogue hop contract issues is recorded as a child of the caller's authorization entry and executes if the caller signs that tree — exactly what simulation produces. The harness test `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs:194-227` proves this end-to-end through `swap_collateral`: a route through an attacker-deployed `RogueHopPool` transfers Alice's entire balance of an unlisted wallet token to the attacker while the swap itself settles fairly (`assert_eq!(s.wallet(&s.alice), 0)`, `assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE)` at lines 224-225).

### Impact Explanation
Theft of user funds beyond the routed amount. The victim loses arbitrary balances of any token held in their wallet — the loss is "the caller's wallet, not the routed amount, and neither the payload minimum nor the final risk gate bounds it" (`threat-model.md:159-161`). All of the controller's measured-flow protections (`RouterOverspend`, `NoSwapOutput`, final HF/collateral gates) pass because the swap leg itself behaves honestly; the theft rides the authorization tree, not the accounting.

### Likelihood Explanation
Reachable by a single unprivileged address via `swap_collateral`, `swap_debt`, `multiply`, `repay_debt_with_collateral`, `flash_position`-composed routes, or direct `Router::execute_strategy` — all accept attacker-craftable `swap_xdr`. Exploitation requires the victim to sign an authorization tree containing the rogue transfer; the threat model notes honest clients must "decode the route it signs and refuse an authorization tree with any other child," but nothing in the contracts enforces this, and wallet/Soroban-RPC simulation surfaces make the poisoned child easy to miss for a user who requested a legitimate-looking quote. Rated High rather than Critical only because it needs the victim's signature on the augmented tree.

### Recommendation
Enforce a venue/pool allowlist in the router (governance-managed set of pool and token addresses the dispatcher may invoke), or constrain hop targets to a registry keyed by `(venue, pool)` validated at `execute_strategy` entry. As a defense-in-depth, have the router reject payloads whose `assets` registry contains addresses not referenced by a known venue adapter signature, and emit the full invocation plan so clients can diff it against the signed auth tree.

### Proof of Concept
See `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`:

1. Attacker deploys `RogueHopPool`, a contract whose `swap()` calls `token::Client::transfer(victim, attacker, WALLET_BALANCE)` on an unrelated token the victim holds (lines 62-72).
2. A `RoutedSwap` XDR payload names `RogueHopPool` as `hop_pool` (lines 111-125) and is passed as `route` to `controller.swap_collateral(alice, account_id, usdc, 5_000 USDC, eth, route)` (lines 134-157).
3. In recording mode, the simulated auth tree attaches the rogue `transfer(alice, attacker, WALLET_BALANCE)` as a child of Alice's `swap_collateral` entry (lines 206-222); once signed, the transaction succeeds — Alice's wallet token balance is 0, the attacker holds `WALLET_BALANCE`, and Alice still receives her fair `ETH` supply (lines 224-226).
