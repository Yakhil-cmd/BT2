Asset Definer Can Rewrite the Attestor Whitelist for `spender_attested` Assets at Any Time With No Timing/Versioning Guard, Causing Payments to Be Judged Against Different Attestor Sets Depending on When They Are Sent - (File: validation.js, storage.js)

### Summary
For any asset created with `spender_attested: true`, the asset's **definer** can post a new `asset_attestors` message at will, at any moment, to replace the whole trusted-attestor list. Every future payment's validity (who is allowed to send/receive this asset) is decided by whichever attestor list happens to be the *latest one before the payer/receiver's `last_ball_mci`* at the moment the payment unit is composed — there is no round/epoch boundary, cooldown, or "effective starting next period" mechanism. This is structurally the same bug class as the reported Solidity issue: a privileged party (asset definer ≈ admin) can change a rule that governs value transfer mid-flight, so two users transacting the same asset within a short time window can be validated against materially different attestor sets, purely based on timing of unit propagation — unlike ocore's own `system_vars` mechanism (used for protocol-wide fee/threshold parameters), which correctly implements an "effective after next MCI" pattern (`vote_count_mci`) specifically to avoid this class of bug.

### Finding Description
When an asset is defined with `spender_attested: true`, only addresses in the attestor-approved list may send/receive it [1](#0-0) . The attestor list itself is fully mutable post-issuance via the `asset_attestors` message, which can be sent by the asset definer at any time with no restriction on frequency or timing: [2](#0-1) .

When a payment referencing this asset is validated, `readAsset` resolves the "latest" attestor list purely by picking whichever `asset_attestors` unit has the highest MC index (or level, for unstable/AA-visible cases) at or before the payer's `last_ball_mci`, with no minimum-age or "next round" delay: [3](#0-2) . `filterAttestedAddresses` then checks each output/input address against whatever that snapshot happens to be: [4](#0-3) .

There is no mechanism analogous to `system_vars.vote_count_mci` ("applies since the next mci", see [5](#0-4) ) protecting the attestor list from being changed and immediately taking effect. A single asset definer can therefore add/remove attestors as often as desired, and different concurrently-composed units built with different `last_ball` snapshots will be validated against different attestor whitelists for the same asset — exactly analogous to `commissionPercent`/`baseStake` being editable mid-round in the reported Solidity contract.

### Impact Explanation
- A malicious or compromised asset definer can front-run legitimate spender_attested asset transfers: remove an attestor (or add a colluding one) right after luring counterparties into initiating a transfer, then swap the list back, so that units composed with slightly different `last_ball_mci` snapshots see inconsistent attestor sets.
- Two users sending the same asset in the same short window can have their payments validated against different attestor lists purely due to which unit happened to be their `last_ball`, producing consensus disagreement risk if nodes race to different stable states, and enabling denial-of-service against legitimate spenders/issuers (their payment becomes invalid retroactively depending on ball inclusion) or, conversely, enabling a temporarily-added illegitimate attestor to validate a fraudulent transfer before being removed.
- This falls under "node disagreement on validity" and "AA/asset fund loss or freezing" categories in scope, since AAs and normal wallets alike rely on `spender_attested` assets' consistent validation rules for private and public payments.

### Likelihood Explanation
Reaching this requires only that the attacker be the definer of an existing `spender_attested` asset — no witness, operator, or node-level privilege is required. Sending an `asset_attestors` message is a normal, unprivileged unit-posting action available to any wallet. The precondition is common: `spender_attested` is a standard, supported asset feature (KYC/whitelisted tokens), and any asset issuer choosing that flag is, by design, this "admin" role — so the likelihood of at least some deployed assets being susceptible is realistic, though the practical severity depends on the definer already being semi-trusted (this is a "your issuer can rug you" scenario rather than an outside attacker scenario, similar in spirit to the Revolver report where the abuse comes from the already-privileged admin role).

### Recommendation
- Apply the same "effective after next MCI/round" pattern that `system_vars` already uses (`vote_count_mci`, "applies since the next mci") to `asset_attestors` updates: require attestor-list changes to only take effect starting some number of MCIs (or a fixed grace period) after being posted and stabilized, not immediately upon becoming the latest stable unit.
- Alternatively, snapshot and pin the attestor list referenced by a payment to a specific `asset_attestors` unit hash inside the payment message itself, so that both parties explicitly agree on which attestor-list version governs their transfer, rather than implicitly relying on "whatever is latest as of my last_ball."
- Document and consider warning users/wallets that `spender_attested` assets carry this mid-flight-change risk inherent to the definer role.

### Proof of Concept
1. Attacker issues an asset `A` with `spender_attested: true` and an initial attestor list `[X]` (validated per [6](#0-5) ).
2. Address `X` attests address `V` (victim) as trustworthy; `V` and a counterparty `C` begin composing a payment of asset `A` from `V` to `C`.
3. Before `V`'s payment unit stabilizes, the attacker (asset definer) posts a new `asset_attestors` message removing `X` and adding a colluding attestor `Y`, per [2](#0-1) .
4. Depending on which unit each validating node/peer uses as `last_ball_mci` when calling `readAsset`/`filterAttestedAddresses` ( [3](#0-2) , [4](#0-3) ), `V`'s payment may be accepted by nodes that saw the old list but rejected by nodes that already see the new list (or vice versa), producing inconsistent validation results for the same unit, or letting the attacker retroactively invalidate a payment that was valid at composition time — all without any round boundary or delay protecting against this manipulation.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
