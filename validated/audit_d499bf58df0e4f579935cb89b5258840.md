### Title
`ProxyType::NonTransfer` fails open on Asset Hub Rococo, permitting proxy-executed value-moving calls (PolkadotXcm, Vesting::vested_transfer, Indices::transfer) - ([File: cumulus/parachains/runtimes/assets/asset-hub-rococo/src/lib.rs])

### Summary
`ProxyType::NonTransfer::filter` on Asset Hub Rococo is documented as "can execute any call that does not transfer funds or assets" [1](#0-0) , but it is implemented as a deny-list that only excludes `Balances`, `Assets`, `NftFractionalization`, `Nfts`, and `Uniques` [2](#0-1) . This is exactly the same "fail-open list" root cause that Eclipse Mosquitto's ACL bug (CVE-2018-12550) exhibits: an incomplete restriction list is silently treated as "allow everything not listed," rather than the intended restrictive policy.

### Finding Description
The invariant violated is: a `NonTransfer` proxy should never be able to move the delegator's funds or assets. `pallet_proxy::Pallet::do_proxy` enforces authorization purely through `T::ProxyType::filter(c)` (plus `is_superset` gating for `add_proxy`/`remove_proxy`) [3](#0-2) . Because `NonTransfer::filter` is a deny-list, any pallet/call not explicitly named passes the filter and is dispatched under the real account's signed origin.

Asset Hub Westend had the identical bug (tracked as paritytech/polkadot-sdk#12466) and was patched to explicitly deny `ForeignAssets`, `PoolAssets`, `AssetConversion`, `Psm`, `PolkadotXcm`, `Revive`, `Vesting::vested_transfer`, and `Indices::transfer`/`force_transfer` [4](#0-3)  (see prdoc `pr_12771.prdoc` and the regression test `non_transfer_proxy_rejects_value_moving_calls`) [5](#0-4) . The `staking-async` parachain runtime received an analogous partial fix for `ForeignAssets`/`PoolAssets` in `pr_12922.prdoc` [6](#0-5) .

Asset Hub Rococo runs the same pallets — `PolkadotXcm`, `Vesting`, and `Indices` are configured in its runtime (confirmed via `pallet_xcm::Config`, `pallet_vesting::Config`, `pallet_indices::Config` impls) — but its `NonTransfer` deny-list was never updated to match Westend's fix. Concretely:
- `PolkadotXcm::transfer_assets`/`teleport_assets`/`send`/`execute` are not denied, letting a `NonTransfer` proxy move the delegator's assets off-chain via XCM.
- `Vesting::vested_transfer`/`force_vested_transfer` are not denied, letting a `NonTransfer` proxy transfer the delegator's vested balance.
- `Indices::transfer`/`force_transfer` are not denied, letting a `NonTransfer` proxy repatriate the delegator's reserved index deposit to a new owner.

### Impact Explanation
An attacker who is granted (or self-authorizes via `announce`/accepts a delegation as) a `NonTransfer` proxy — a role explicitly documented and marketed as safe for "any call that does not transfer funds or assets" — can drain the delegator's balance/assets through `PolkadotXcm` transfers/teleports, `Vesting::vested_transfer`, or `Indices::transfer`. This breaks the proxy pallet's core authorization guarantee and directly causes theft of delegator funds, which is High/Critical impact.

### Likelihood Explanation
Likelihood is High: `NonTransfer` proxies are a standard, commonly-granted low-trust proxy type (e.g. for bots/apps that should never move funds). No privileged role or governance action is needed — any delegator who grants a `NonTransfer` proxy to a counterparty is exposed, and the counterparty (the proxy account) can unilaterally dispatch the denied-in-spirit-but-not-in-code calls.

### Recommendation
Mirror the fix already applied to Asset Hub Westend (`pr_12771`) in Asset Hub Rococo's `ProxyType::NonTransfer::filter`: explicitly deny `PolkadotXcm`, `Vesting::vested_transfer`/`force_vested_transfer`, `Indices::transfer`/`force_transfer`, and any other pallets present in the Rococo runtime capable of moving the delegator's funds/assets (re-audit against the full pallet list, since deny-lists silently fail open whenever a new pallet is added).

### Proof of Concept
I was not able to execute a live integration test in this session (ask-only mode, no code-execution tools available). The logical reproduction is:
1. Delegator `A` grants `ProxyType::NonTransfer` proxy to account `B` via `pallet_proxy::add_proxy`.
2. `B` calls `pallet_proxy::proxy(real = A, force_proxy_type = None, call = RuntimeCall::PolkadotXcm(Call::transfer_assets { ... }))` (or `Vesting::vested_transfer`, or `Indices::transfer`).
3. `ProxyType::NonTransfer::filter` returns `true` for this call because none of `PolkadotXcm`, `Vesting`, or `Indices::transfer` are matched in the deny-list at `cumulus/parachains/runtimes/assets/asset-hub-rococo/src/lib.rs:608-615`, so `do_proxy` dispatches it under `A`'s origin, moving `A`'s funds/assets without `A`'s direct consent.

This mirrors the already-fixed and already-tested scenario for Asset Hub Westend (`non_transfer_proxy_rejects_value_moving_calls`) [7](#0-6) ; an equivalent test written against `asset_hub_rococo_runtime::ProxyType` would fail today because the deny-list was never extended to cover Rococo's `PolkadotXcm`/`Vesting`/`Indices` calls. I recommend a Devin/engineer session run that exact adapted test against the `asset-hub-rococo` runtime crate to confirm and then apply the same fix pattern as `pr_12771`.

/// Regression test for <https://github.com/paritytech/polkadot-sdk/issues/12466>.
///
/// `ProxyType::NonTransfer` is documented as permitting "any call that does not transfer funds or
/// assets", but it is implemented as a deny-list and so fails open. `ForeignAssets` and
/// `PoolAssets` transfers were reachable, as were swaps, XCM transfers, contract calls carrying a
/// value, and index transfers (which repatriate the reserved deposit).
#[test]
fn non_transfer_proxy_rejects_value_moving_calls() {
	use asset_hub_westend_runtime::ProxyType;
	use frame_support::traits::InstanceFilter;

	// Collected rather than asserted one by one, so a regression reports every call that slipped
	// through instead of only the first.
	let mut leaked = Vec::new();
	for (name, call) in value_moving_calls() {
		if ProxyType::NonTransfer.filter(&call) {
			leaked.push(name);
		}
		// The call is otherwise well-formed and reachable by a fully permissioned proxy.
		assert!(ProxyType::Any.filter(&call), "Any must permit {name}");
	}

	assert!(
		leaked.is_empty(),
		"NonTransfer must reject calls that move funds or assets, but permitted: {leaked:?}",
	);
}
