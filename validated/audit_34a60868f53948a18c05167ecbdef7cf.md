### Title
Vault `transfer` authorizes moves of a vault's zft shares using `tx-sender` (transaction signer), letting any contract in the caller's transaction drain the signer's share balance without approval - ([File: mainnet/contracts/vault/v0-vault-usdc.clar])

### Summary
Every tokenized vault (`v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`) implements `transfer` for its `zft` share token with an authorization check that accepts either `contract-caller` (the direct caller, analogous to Solidity `msg.sender`) or `tx-sender` (the address that signed the top-level transaction, analogous to Solidity `tx.origin`) as proof of ownership: [1](#0-0) 
```
(define-public (transfer (amount uint) (from principal) (to principal) (memo (optional (buff 34))))
  (begin
    (try! (accrue))
    (asserts! (or (is-eq tx-sender from) (is-eq contract-caller from)) (err u4))
    (asserts! (not (is-eq current-contract to)) ERR-TOKENIZED-VAULT-PRECONDITIONS)
    (try! (ft-transfer? zft amount from to))
    (match memo to-print (print to-print) 0x)
    (ok true)))
```
This mirrors exactly the `transferTo`/`tx.origin` bug class from the external report: because `tx-sender` in Clarity stays fixed to the original transaction signer across the entire chain of nested `contract-call?`s (it does not change per hop, the way `contract-caller` does), any arbitrary contract that a victim's transaction happens to call into — even one totally unrelated to the vault — can call the vault's public `transfer` function directly, pass `from = tx-sender` (the victim) and `to = attacker`, and pass the `is-eq tx-sender from` branch of the `or` check with no approval from the victim.

### Finding Description
- Attacker: deploys any malicious contract (e.g., a fake token, fake DEX/aggregator "helper" contract) that a victim is lured into calling as part of an ordinary-looking transaction (airdropped token swap, "claim" contract, block-explorer "Write Contract" interaction, etc.).
- Victim: any holder of zft vault shares (e.g., `zUSDC` from `v0-vault-usdc.clar`, or equivalents from the other vaults) who signs a transaction that invokes the attacker's contract.
- Shared state: the victim's `zft` balance tracked by `ft-get-balance`/`ft-transfer?` inside the vault contract (`mainnet/contracts/vault/v0-vault-usdc.clar` and siblings) [2](#0-1) .
- Root cause: the transfer authorization uses `tx-sender`, which is fixed for the whole transaction regardless of how many contracts are called in between, as an implicit "owner approved this transfer" signal. Because the victim never directly calls `transfer` themselves in the attack — the attacker's contract does, on the victim's behalf, deep in the call stack — `contract-caller` at the point of the `transfer` call is the attacker's contract, not the victim, yet the check still succeeds via the `tx-sender` branch.
- With attack: victim signs `(contract-call? .attacker-contract do-something)`; inside `do-something`, attacker's contract issues `(contract-call? .v0-vault-usdc transfer victim-balance victim attacker-address none)`. Since `tx-sender` is still the victim (the original signer), `(is-eq tx-sender from)` is true, the vault moves the victim's entire `zft` balance to the attacker, with zero approval step.
- Without attack: the victim's balance is untouched unless the victim explicitly calls `transfer` themselves (`contract-caller` == `from`) or grants some proper allowance mechanism — which does not even exist here since this check bypasses any allowance/approval concept entirely.

### Impact Explanation
This is a direct, unconditional theft of user funds at rest: the entire `zft` share balance of any vault (`v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`) can be moved out from under a victim to an attacker-controlled address the moment the victim's signed transaction touches any attacker-controlled contract, with no interaction with or approval on the vault itself. This lands squarely in the Critical impact category — direct theft of user funds at rest.

### Likelihood Explanation
Likelihood is non-trivial but requires the victim to interact with an attacker-supplied contract in the same transaction (e.g., a spoofed/airdropped token or a malicious "helper"/router contract), matching precisely the attack path described and acknowledged in the source report (airdrop bait, fake liquidity pool, deceptive swap UI). This is a standard, well-documented social-engineering vector on both EVM and non-EVM chains, and does not require any privileged access, oracle manipulation, or DAO compromise — only that the victim signs one transaction that reaches attacker code.

### Recommendation
Remove the `tx-sender` branch from the authorization check in `transfer` in all six vault contracts; require only `(is-eq contract-caller from)` (i.e., the immediate caller must be the token owner), matching the report's core mitigation recommendation of relying on direct authorization rather than transaction-signer identity. If delegated transfers are needed, implement an explicit allowance/`approve`+`transfer-from` pattern instead of trusting `tx-sender`.

### Proof of Concept
1. Victim holds `zft` shares in `v0-vault-usdc.clar` (`zUSDC`).
2. Attacker deploys `attacker-contract` with a public function `drain (victim principal)` that calls `(contract-call? 'SP...v0-vault-usdc transfer (ft-get-balance zft victim) victim attacker-address none)`.
3. Attacker gets the victim to sign a transaction that calls `attacker-contract.drain(victim)` (via airdropped token swap UI, fake "claim rewards" page, etc.).
4. Inside the call, `tx-sender` is still the victim (the transaction signer), so `(is-eq tx-sender from)` in `v0-vault-usdc.clar`'s `transfer` function [3](#0-2)  evaluates true even though `contract-caller` is `attacker-contract`, not the victim.
5. `ft-transfer?` executes, moving the victim's entire `zUSDC` balance to `attacker-address`, with no prior approval and no direct call by the victim to the vault.
