### Title
Unauthenticated webhook signature bypass leads to forged GitHub events and `Shipit.github_teams` authorization escalation - (File: `lib/shipit/github_app.rb`, `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
The Gondi bug is a TOCTOU/binding-break where a value used for a later trust check (`_loans[loanId]`) can be mutated between verification and use, letting an attacker desynchronize "what was checked" from "what is acted on." The same class of binding break exists in `WebhooksController`: the HMAC signature check is supposed to prove "GitHub sent this payload," but `verify_webhook_signature` unconditionally treats an unset `webhook_secret` as "verified," so the binding `signature verified == GitHub authored this request` collapses to always-true for any organization configured without a secret. Because `webhook_secret` is documented as *optional* and shipped as `nil` in the example/template configs, this is not a hypothetical misconfiguration outside the engine's own guidance — it's the documented default path.

### Finding Description
`WebhooksController#verify_signature` picks the `GitHubApp` instance to validate against using an attacker-supplied field from the very payload it is about to validate: [1](#0-0) [2](#0-1) 

The actual verification, however, is short-circuited when no secret is configured for that organization: [3](#0-2) 

`return true unless webhook_secret` means: for any organization whose `github.<org>.webhook_secret` is blank/nil, **any unauthenticated POST to `/webhooks`** is treated as a verified GitHub event, with zero cryptographic proof of origin. This is exactly the documented "optional" state: [4](#0-3) [5](#0-4) [6](#0-5) 

Once past `verify_signature`, `WebhooksController#create` dispatches the fully attacker-controlled JSON body to registered handlers with no further authentication: [7](#0-6) 

One of the default handlers is `MembershipHandler`, which mutates `Team`/`Membership` records straight from payload fields (`team.id`, `organization.login`, `member.login`) with no cross-check against the org that was supposedly authenticated: [8](#0-7) 

`Shipit.github_teams` (the authorization gate for the whole app) is a fixed set of `Team` records pre-populated from `github.oauth.teams` config, resolved to their real GitHub `github_id` via the API: [9](#0-8) [10](#0-9) 

And `User#authorized?` is a simple membership existence check against those teams: [11](#0-10) 

Because `MembershipHandler#find_or_create_team!` looks the team up (or creates it) purely by `params.team.id` matching the real `github_id`, a forged `membership`/`action: 'added'` event that references the authoritative team's `github_id` and the attacker's own GitHub login will insert a `Membership` row binding the attacker's `User` to that team — satisfying `authorized?` without ever going through the GitHub OAuth flow or GitHub's actual team membership.

The binding broken, stated as an equality that fails to hold:
`signature_verified(payload) == payload_originated_from_GitHub(org)`
is false whenever `webhook_secret` is unset for the org derived from the attacker's own payload, exactly mirroring how `_loans[_loanId] == loan.hash()` was assumed stable but was mutable by an unprivileged actor in the Gondi report.

### Impact Explanation
This crosses into "escalation into `Shipit.github_teams` authorization," an explicitly in-scope High-severity impact. An attacker who is not a GitHub App-authenticated caller, holds no `ApiClient` token, and has no repository write access can:
- Forge arbitrary webhook events (`push`, `status`, `check_suite`, `pull_request`, `membership`) for any organization whose Shipit config lacks a `webhook_secret`.
- Use the `membership` event specifically to add themselves to a `Team` that gates access via `Shipit.github_teams`, bypassing the GitHub OAuth-based authorization entirely and gaining full authenticated access to the Shipit instance (deploy, rollback, lock/unlock stacks, etc., once logged in through the normal OAuth flow as themselves, since `authorized?` is the only gate after login).

### Likelihood Explanation
Likelihood is elevated by the fact that `webhook_secret` is explicitly documented as optional and ships blank in the example/dev/template configs, so unconfigured-secret deployments are foreseeable, not a violation of documented setup. The remaining requirement — knowing the target team's real `github_id` — is a moderate but realistic bar (discoverable via GitHub's team APIs for teams the attacker or a colluding member can see, or via previously observed legitimate webhook traffic/logs, since the controller logs `repository_owner` but not the team id — still, id enumeration on a small integer space is feasible for a motivated attacker, similar to how the Gondi judge accepted "too many limitations but still likely" reasoning for High severity).

### Recommendation
- Require `webhook_secret` to be present for every configured organization; refuse to start (or reject all webhooks) if it is blank, rather than defaulting to `verified = true`.
- Never derive the *verification key* from unverified request content; if multiple orgs must share the endpoint, verify against all configured secrets (constant-time) rather than selecting one secret using attacker-controlled JSON fields.
- In `MembershipHandler`, cross-validate that the `organization.login` in the payload matches the organization actually authenticated for this webhook_secret before mutating `Team`/`Membership`, and consider treating `Shipit.github_teams` membership changes as requiring re-validation against the live GitHub API rather than trusting webhook payload data directly for authorization-relevant state.

### Proof of Concept
1. Deploy Shipit with `github.someorg.webhook_secret` left blank (as shown in `config/secrets.development.example.yml` / `template.rb`), which is the documented default.
2. As an unauthenticated actor, `POST /webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "team": { "id": <real_github_team_id_of_a_Shipit.github_teams_team>, "name": "x", "slug": "x", "url": "https://example.com" },
  "organization": { "login": "someorg" },
  "member": { "login": "<attacker_github_login>" },
  "repository": { "owner": { "login": "someorg" } }
}
```
3. `verify_signature` selects `Shipit.github(organization: 'someorg')`; since its `webhook_secret` is blank, `verify_webhook_signature` returns `true` unconditionally regardless of the (absent/garbage) `X-Hub-Signature` header — see `lib/shipit/github_app.rb:76-83`.
4. `MembershipHandler#process` runs, creating a `Membership` row linking the attacker's `User` to the authoritative `Team` — see `app/models/shipit/webhooks/handlers/membership_handler.rb:22-34`.
5. Attacker logs in via the normal GitHub OAuth flow (`GithubAuthenticationController`); `User#authorized?` now returns `true` because of the forged membership, granting full app access.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
