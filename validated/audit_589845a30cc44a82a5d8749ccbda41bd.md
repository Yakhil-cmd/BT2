### Title
Cross-organization webhook forgery via authenticated-organization / acted-upon-repository binding mismatch - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the GitHub App (and therefore the HMAC `webhook_secret`) used to authenticate an inbound webhook based on `repository.owner.login` (or `organization.login`) taken from the still-unverified JSON body. Once the signature check passes, the entire raw payload — including a completely different `repository.full_name`, `organization.login`, `team`, or `sha` field — is handed unmodified to `Shipit::Webhooks::Handlers::Handler` subclasses, which look up the target `Repository`/`Stack`/`Team`/`Commit` from those same untrusted fields. Nothing ties the organization whose secret validated the signature to the organization/repository the handler actually mutates.

### Finding Description
`verify_signature` picks the signing organization straight from the payload: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` resolves to a per-organization config entry (each with its own `webhook_secret`), as shown by the multi-org secrets layout: [3](#0-2) 

`verify_webhook_signature` only checks that the raw body HMACs correctly under *that one organization's* secret: [4](#0-3) 

After the check passes, `create` dispatches the full parsed JSON body to handlers: [5](#0-4) 

But every handler resolves its target repository from a *different* payload field, `repository.full_name`, with no relation to `repository.owner.login` used for signing: [6](#0-5) 

Because a valid signature only proves "the body was signed with organization X's secret," and organization X's admin legitimately knows X's own `webhook_secret` (they configured it when installing their GitHub App), nothing stops that admin from crafting a body where `repository.owner.login == "orgX"` (so it verifies against X's secret) while `repository.full_name == "orgY/private-repo"`, `organization.login == "orgY"`, or an arbitrary `sha`/`team` value belonging to an unrelated, Shipit-tracked organization/repository. The binding the rules describe — "an organization that authenticated versus the repository that is written" — is broken here: **authenticated org (X) ≠ acted-upon repository/org (Y)**.

Concretely reachable handlers that trust these unrelated fields:
- `PushHandler` looks up stacks via `stacks` (i.e. `Repository.from_github_repo_name(repository_name)`) and triggers `stack.sync_github(...)`, which can queue syncs/deploy flows for a repository the attacker does not control: [7](#0-6) 
- `StatusHandler` writes CI statuses for arbitrary commits (`sha`) with an attacker-chosen `state`/`context`, which can flip a "required" CI status to green for an unrelated stack's commit and unblock a deploy/merge gate: [8](#0-7) 
- `MembershipHandler` creates/updates a `Team` keyed only by `team.id` supplied in the payload and adds an arbitrary `member.login` to it: [9](#0-8) . If the forged `team.id` matches an existing team referenced in `Shipit.github_teams`, the attacker (or any user login they name) is added as a member of that team, and `User#authorized?` grants access to Shipit based purely on `teams.where(id: Shipit.github_teams.map(&:id)).exists?`: [10](#0-9) . This is a direct escalation into `Shipit.github_teams` authorization, matching the High-impact criterion in scope.

### Impact Explanation
An attacker who administers one Shipit-linked GitHub App/organization (and therefore legitimately knows that org's `webhook_secret`, without needing any Shipit account, `ApiClient` token, or GitHub App private key) can forge signed webhook deliveries whose payload content targets any *other* organization/repository tracked by the same Shipit instance. Depending on handler chosen, this yields:
- Unauthorized triggering of GitHub syncs / deploy-adjacent flows for repositories the attacker doesn't own (`PushHandler`).
- Forged CI status on arbitrary commits, defeating `ci.require` gates used to authorize merges/deploys (`StatusHandler`).
- Membership escalation into any `Team` (including ones in `Shipit.github_teams`), granting `current_user.authorized?` access to the whole Shipit instance for an attacker-chosen `User` (`MembershipHandler`).

This matches the "High - escalation into `Shipit.github_teams` authorization" impact bucket defined in scope.

### Likelihood Explanation
Requires the attacker to control at least one organization that is configured in Shipit's `github:` secrets with its own GitHub App/webhook secret (a realistic scenario for any multi-tenant/multi-org Shipit deployment, and explicitly supported by the engine's config format). No privileged Shipit credentials, `ApiClient` token, or GitHub App private key are needed — only ownership of one legitimately-configured organization out of possibly many the Shipit instance serves.

### Recommendation
Bind the field used to select the verification secret to the field(s) used by handlers to resolve the affected resource. Concretely: after verifying the signature, re-derive `repository_owner`/`organization.login` from the payload and compare it against `payload.dig('repository', 'full_name')`'s owner segment (and `team.organization`, etc., in relevant handlers), rejecting the request if they diverge. Alternatively, verify the signature using every configured organization's secret and only accept the request if the specific organization whose secret matched is the same organization that owns the repository/team/commit the handler is about to mutate.

### Proof of Concept
1. Attacker legitimately installs/administers a Shipit-configured GitHub App for `org-attacker`, and thus knows `Shipit.github(organization: 'org-attacker').webhook_secret`.
2. Attacker crafts a JSON body:
```json
{
  "repository": { "owner": { "login": "org-attacker" }, "full_name": "org-victim/private-repo" },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>"
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac(org-attacker secret, body)>` and sends it with `X-Github-Event: push` to `POST /webhooks`.
4. `WebhooksController#verify_signature` resolves `repository_owner = "org-attacker"`, fetches `org-attacker`'s secret, and the HMAC verifies successfully (`app/controllers/shipit/webhooks_controller.rb:24-30`).
5. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, which resolves the target via `payload.dig('repository', 'full_name')` = `"org-victim/private-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`) and calls `stack.sync_github(...)` for a stack the attacker never had access to (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`).
6. The same technique applied to the `membership` event (with a guessed/observed `team.id` used by `Shipit.github_teams`) adds an attacker-controlled `User` login to that team, satisfying `User#authorized?` and granting full Shipit application access.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
