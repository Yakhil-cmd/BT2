## Title
Asset definer can change the `spender_attested` attestor list at any time, freezing already-held units of a `spender_attested` asset for holders who fall off the new list - (File: `validation.js`, `storage.js`)

### Summary
For assets defined with `spender_attested: true`, the asset definer can post an `asset_attestors` message at any time to replace the entire trusted-attestor list, exactly analogous to `PaymentSettler::setStablecoin` being callable at any time without regard to outstanding balances. Because attestation is checked against the *current, latest* attestor list at the moment a holder tries to spend, rather than the list that was in force when the holder received the asset, a definer's routine or malicious list rotation can retroactively strand funds that were validly received under the old list.

### Finding Description
When an asset is defined with `spender_attested: true`, only the asset's `definer_address` is authorized to update the attestor list, and this can be done unconditionally, at any main-chain index, regardless of the asset's outstanding circulating supply: [1](#0-0) 

The check enforced on every subsequent transfer of the asset does not pin the attestor list to the one in effect when the sender received the funds. Instead, `readAsset` always looks up the single, most-recently-published attestor list before `last_ball_mci`: [2](#0-1) 

`filterAttestedAddresses` and `loadAssetWithListOfAttestedAuthors` then check the payment's author addresses against that same, always-current list: [3](#0-2) 

`validatePayment` bounces/rejects any transfer whose author isn't in `objAsset.arrAttestedAddresses`: [4](#0-3) 

So the sequence of events mirrors the reported bug class exactly:
1. Definer issues/enables a `spender_attested` asset with attestor set A.
2. A holder receives (and is validly attested for) units of the asset while set A is in force — this posted unit is fully valid at the time.
3. The definer (an "asset issuer" in ocore terms, reachable by anyone who defines such an asset) later posts a single `asset_attestors` unit replacing the attestor list with set B, which does not include the holder's attestor.
4. The holder can no longer produce a valid `payment` message for that asset — `validatePayment` will reject the unit with "none of the authors is attested" / "issuer is not attested" — even though the funds were legitimately received.

There is no mechanism to pin the attestor set used at receipt time to future transfers, no timelock, and no restriction preventing the definer from rotating the list while there is outstanding, unspent balance of the asset in other addresses. This is the same root cause as the reported issue: a single-sided, unrestricted admin/definer action mutates a parameter that other parties' already-issued funds depend on for spendability, with no way to reconcile the two states.

### Impact Explanation
Holders of a `spender_attested` asset can have their previously and validly received funds become permanently unspendable the moment the definer updates the attestor list, with no recourse (no migration path, no grace window, no escrow of an old list). This is a fund-freezing bug directly reachable by any account holding such an asset: their own posted payment unit will be rejected by every node, so the funds are stuck — an availability/freezing issue equivalent in class to the reported medium-severity finding (funds trapped, inability of holders to claim/spend). Because `spender_attested` is a first-class, documented asset feature (not a bespoke user AA script), this is squarely within `validation.js`/`storage.js` core-protocol logic.

### Likelihood Explanation
Likelihood is Medium: it requires the asset definer to actively post an `asset_attestors` message, which is a routine/expected administrative action for real-world regulated or KYC-gated assets (attestor lists are explicitly documented as needing periodic updates: "must subsequently publish and update the list of trusted attestors" per the `assets` table schema comment). Definers rotating compliance providers/attestors, revoking a compromised attestor, or simply making an operational mistake are realistic, non-adversarial triggers — comparable to the stablecoin de-peg scenario in the original report where an "admin" action taken for legitimate reasons produces the freeze.

### Recommendation
Either (a) record, at the time each output/UTXO of a `spender_attested` asset is created, which attestor-list version (unit) was in force, and require attestation checks on spend to use that historical list rather than always the latest one; or (b) require that attestor-list changes take effect only after a delay long enough for holders to migrate, and/or provide a fallback so that an address attested under any list that was valid since the address received its balance remains eligible to spend it. At minimum, document/guard so that removing an attestor does not retroactively invalidate the spendability of funds already held by addresses attested at receipt time.

### Proof of Concept
Conceptual reproduction using existing validation code paths:
1. Definer D creates asset `X` with `spender_attested: true` and initial `attestors: [A1]` via the `asset` message (`writer.js:218-235` records `asset_attestors` for the definer's initial unit): [5](#0-4) 
2. Attestor `A1` attests address `H` (attestation message). D sends `X` to `H`. `validatePayment` passes because `H` is in `arrAttestedAddresses` computed from the (only) attestor list `[A1]`.
3. D posts a single `asset_attestors` unit for asset `X` with a new list `[A2]` (validated only by `validateAttestorListUpdate`, which only checks `objUnit.authors[0].address === objAsset.definer_address`): [1](#0-0) 
4. `H` (who is not attested by `A2`) attempts to spend/transfer their existing balance of `X`. `readAsset`'s `addAttestorsIfNecessary` fetches only the newest attestor-list unit (`[A2]`) as of `last_ball_mci`: [6](#0-5) , `filterAttestedAddresses` finds `H` is not attested under `[A2]`, and `validatePayment` rejects the unit with "none of the authors is attested": [4](#0-3) 
5. `H`'s validly received balance of `X` is now permanently stuck — no code path allows reverting to the historical attestor list valid at receipt time.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}

function filterAttestedAddresses(conn, objAsset, last_ball_mci, arrAddresses, handleAttestedAddresses){
	conn.query(
		"SELECT DISTINCT address FROM attestations CROSS JOIN units USING(unit) \n\
		WHERE attestor_address IN(?) AND address IN(?) AND main_chain_index<=? AND is_stable=1 AND sequence='good' \n\
			AND main_chain_index>IFNULL( \n\
				(SELECT main_chain_index FROM address_definition_changes JOIN units USING(unit) \n\
				WHERE address_definition_changes.address=attestations.address AND main_chain_index<=? AND is_stable=1 AND sequence='good' ORDER BY main_chain_index DESC LIMIT 1), \n\
			0)",
		[objAsset.arrAttestorAddresses, arrAddresses, last_ball_mci, last_ball_mci],
		function(addr_rows){
			var arrAttestedAddresses = addr_rows.map(function(addr_row){ return addr_row.address; });
			handleAttestedAddresses(arrAttestedAddresses);
		}
	);
}

function loadAssetWithListOfAttestedAuthors(conn, asset, last_ball_mci, arrAuthorAddresses, bAcceptUnconfirmedAA, handleAsset){
	if (arguments.length === 5) {
		handleAsset = bAcceptUnconfirmedAA;
		bAcceptUnconfirmedAA = false;

		if (err)
			return handleAsset(err);
		if (!objAsset.spender_attested)

		filterAttestedAddresses(conn, objAsset, last_ball_mci, arrAuthorAddresses, function(arrAttestedAddresses){

			handleAsset(null, objAsset);
		});
	});
