### Title
Signature-verification org (`repository.owner.login`) decoupled from mutation-target org (`organization.login`) lets an attacker forge `membership` webhooks that grant themselves access to any team - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`, `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects the `GitHubApp` used for HMAC verification solely from `params.dig('repository','owner','login')` (falling back to `params.dig('organization','login')` only when `repository` is absent), while `MembershipHandler` mutates state using an entirely separate, attacker-controlled `params.organization.login` field. Because these two fields are never required to match, an attacker can point signature verification at any organization configured without a `webhook_secret` while directing the actual team/membership mutation at a different, victim organization.

### Finding Description
The broken binding, stated as an equality that the code assumes but never enforces:
`repository_owner` (used to select `Shipit.github(organization: repository_owner)` for signature verification) `== params.organization.login` (used by `MembershipHandler#find_or_create_team!` to set/match the mutated `Team`'s organization).

Trace:
- `Shipit::WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0)  and uses it to fetch the `GitHubApp` instance to verify against [2](#0-1) .
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when the selected org has no `webhook_secret` configured: `return true unless webhook_secret` [3](#0-2) .
- `MembershipHandler`'s schema separately requires and reads `params.organization.login` and `params.team.id` to find-or-create a `Team`, and `params.member.login` to find-or-create a `User`, then adds/removes membership rows [4](#0-3) . Note the handler never reads `params.repository` at all.
- `User#authorized?` reads exactly those membership rows: `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [5](#0-4) .
- `Team.find_or_create_by!(github_id: params.team.id)` matches purely by `github_id`; if a `Team` row for that `github_id` already exists (e.g., a legitimate, previously-synced authorized team), the `organization` field in the attacker's payload is irrelevant to which row gets mutated — the attacker only needs to know/guess the numeric GitHub team id, which is discoverable via GitHub's public API for many orgs/teams [6](#0-5) .

Exploit request: an unprivileged attacker sends `POST /webhooks` with header `X-Github-Event: membership` and a JSON body they fully construct:
```json
{
  "action": "added",
  "team": {"id": <victim_team_github_id>, "name": "x", "slug": "x", "url": "x"},
  "organization": {"login": "victim-org"},
  "member": {"login": "attacker-login"},
  "repository": {"owner": {"login": "org-without-secret"}}
}
```
`repository_owner` resolves to `"org-without-secret"`, so `Shipit.github(organization: "org-without-secret").verify_webhook_signature` returns `true` regardless of the (even garbage/missing) `X-Hub-Signature` header, because that org's `webhook_secret` is blank. `drop_unhandled_event`/`check_if_ping` do not filter `membership` events. The handler then finds/creates the victim `Team` (by `github_id`) and the attacker's own `User` (by `login`), and calls `team.add_member(member)`, inserting a `Membership` row.

No existing guard prevents this: `verify_signature` never cross-checks `repository_owner` against `params.organization.login`; `ExplicitParameters`/the handler's `params do ... end` schema only validates presence/types, not cross-field consistency or that the org matches the one used for authentication; there is no `force_github_authentication`, `require_permission!`, or model validation tying `Membership`/`Team` creation to the webhook's authenticated origin.

### Impact Explanation
If the victim org's team (matched by `github_id`) is one of the teams enumerated in `Shipit.github_teams`, the attacker's forged membership grants their own `User` row membership in that team, making `User#authorized?` return `true` for their account — a full authentication/authorization bypass that elevates an unprivileged internet attacker into `Shipit.github_teams`-gated access (deploy/rollback/merge capability), matching the "Critical: escalation into `Shipit.github_teams` authorization" / "payload for one repository (org) mutating another's stack/team" category. The attack is repeatable against any org/team as long as at least one org in the Shipit instance's configuration lacks a `webhook_secret`, and requires no secrets, sessions, or GitHub App credentials from the attacker.

### Likelihood Explanation
Preconditions: (1) at least one org configured in the Shipit instance without a `webhook_secret` (explicitly the scenario given), and (2) the attacker knows or can discover a target team's numeric GitHub `id` (obtainable via GitHub's public teams API for many orgs, or simply create their own team/org and let it collide if IDs aren't globally scoped — GitHub team IDs are global and enumerable). No Shipit credentials, GitHub App keys, or webhook secrets are needed. The request is a single unauthenticated `POST /webhooks` with a forged JSON body — trivially repeatable and inexpensive.

### Recommendation
In `WebhooksController#verify_signature`, require that the org used to select the signing secret matches the org(s) referenced by the payload actually consumed by the handler (e.g., validate `params.dig('organization','login')` and `params.dig('repository','owner','login')` are consistent, and prefer the field the specific handler will use). More robustly, `MembershipHandler` (and other handlers) should assert that `params.organization.login == repository_owner` (the value used for signature verification) before performing any mutation, rejecting the event otherwise. Additionally, consider treating "no `webhook_secret` configured" as a hard misconfiguration to reject/alert on rather than silently trusting all signatures for that org.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`-style, no live GitHub):
1. Configure two orgs in `Shipit.app.github.apps` (or equivalent test config): `"open-org"` with no `webhook_secret`, and `"victim-org"` with a `webhook_secret` set.
2. Create a `Shipit::Team` fixture with `github_id: 4242`, `organization: "victim-org"`, and add it to `Shipit.github_teams` (or stub `Shipit.github_teams` to include it).
3. POST to `/webhooks` with header `X-Github-Event: membership`, no/garbage `X-Hub-Signature`, and body:
   ```json
   { "action": "added", "team": {"id":4242,"name":"x","slug":"x","url":"x"},
     "organization": {"login":"victim-org"}, "member": {"login":"attacker"},
     "repository": {"owner": {"login": "open-org"}} }
   ```
4. Assert response is `200 OK` (not `422`), i.e. `assert_response :ok`.
5. Assert `Shipit::User.find_by(login: "attacker").teams.exists?(github_id: 4242)` is `true`.
6. Assert `Shipit::User.find_by(login: "attacker").authorized?` is `true` — proving the equality `repository_owner == params.organization.login` was violated and the attacker gained unauthorized `Shipit.github_teams` membership using only `open-org`'s missing secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
