## Title
Cross-organization Team hijack via `MembershipHandler`'s unscoped `github_id` lookup - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
This is a structural analog of the reported "mutable caps" bug: the KinTokenSale issue is that a privileged actor can rewrite an unprivileged participant's tier/cap binding at will, with no immutability guard tying the record to its original approval context. In shipit-engine, `Shipit::Webhooks::Handlers::MembershipHandler` performs the equivalent unsafe rebind: it looks up (or lazily creates) a `Team` record purely by the GitHub-supplied `team.id`, with no check that this team belongs to the organization whose webhook secret verified the request. This breaks the binding "organization that authenticated the webhook" == "organization whose team membership is written."

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to verify against based on the organization derived from the payload itself: [1](#0-0) 

For `membership` events (no `repository` key), this organization is `params.dig('organization', 'login')`. In a multi-org Shipit deployment (explicitly supported, see `test/dummy/config/secrets_double_github_app.yml`, defining independent `webhook_secret`s per organization), this means the signature only proves "this payload was sent by *an* org configured in secrets.yml with a valid HMAC for *that org's* secret" — it says nothing about which `Team` record the payload is allowed to mutate.

`MembershipHandler#process` then acts on attacker-supplied `team.id`, `organization.login`, and `member.login` fields without re-validating that `params.organization.login` actually owns `params.team.id`: [2](#0-1) 

Critically, `Team.find_or_create_by!(github_id: params.team.id)` is scoped **only** by the global `github_id` column (see `app/models/shipit/team.rb`, lines 41-58 `add_member`/`github_team=`), not by organization. GitHub team IDs are global integers, not namespaced per organization. If a `Team` row with that `github_id` already exists (e.g., created earlier for legitimate org "OrgOne" and used in `Shipit.github_teams` for authorization), `find_or_create_by!` finds the existing record and the creation block (which sets `team.organization`) never runs — the existing team's `organization` is left untouched. The handler then calls `team.add_member(member)` where `member` is `User.find_or_create_by_login!(params.member.login)`, an attacker-chosen GitHub login.

This means an administrator of **any** org configured in Shipit's multi-tenant `secrets.yml` (a party with zero privilege in the *target* org, and no Shipit account) can send a validly-signed `membership` webhook from *their own org* referencing a `team.id` belonging to a *different* org, and add an arbitrary GitHub identity as a member of that team.

`current_user.authorized?` (used by `force_github_authentication` to gate all of Shipit) is: [3](#0-2) 

If the hijacked `Team` is one of the configured `Shipit.github_teams`, the attacker has just granted an arbitrary account authorization to the entire Shipit instance — bypassing the org-scoped access control the multi-org feature exists to enforce.

### Impact Explanation
This escalates into `Shipit.github_teams` authorization, which the rules list as a High-severity outcome. An attacker who controls (or briefly compromises) any org onboarded to a shared, multi-tenant Shipit deployment can grant arbitrary GitHub logins access to stacks/deploys belonging to organizations they have no legitimate relationship with, purely by guessing/enumerating a numeric team ID and firing a legitimately-signed webhook from their own org.

### Likelihood Explanation
Requires: (1) a multi-org Shipit deployment (explicitly supported and documented, see `test/dummy/config/secrets_double_github_app.yml`), (2) the attacker controls at least one onboarded, lower-trust org and can trigger `membership` events for it (any org owner can add/remove team members), and (3) knowledge of a target `github_id` for a team belonging to another org (GitHub team IDs are small sequential integers and are frequently observable via API responses, CODEOWNERS, or other public artifacts). No repository write access, no Shipit session, and no privileged Shipit account are required — only administrative control of one's own onboarded organization, which is the baseline "unprivileged" capability in a multi-tenant setup.

### Recommendation
Scope the `Team` lookup by both `github_id` and `organization` (i.e., `find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`), and reject/log the event if a `Team` already exists with that `github_id` under a different organization. More generally, cross-check that the organization used to select/verify the webhook secret matches every organization-scoped resource acted upon by the handler.

### Proof of Concept
1. Shipit is configured with two GitHub Apps for `OrgOne` and `OrgTwo` (as in `secrets_double_github_app.yml`), and `Shipit.github_teams` includes `OrgOne/leads` (github_id = 100), which is already persisted as `Team(github_id: 100, organization: "OrgOne")`.
2. Attacker administers `OrgTwo` (legitimately onboarded, low trust) and knows/guesses `github_id: 100` (e.g., observed via a prior public API call or leaked webhook).
3. Attacker creates/renames a team in `OrgTwo`, triggering GitHub to send a `membership` webhook, "added" action, with `organization.login = "OrgTwo"`, `team.id = 100`, `member.login = "attacker"`. GitHub signs this with `OrgTwo`'s real webhook secret.
4. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "OrgTwo")` and successfully verifies the HMAC — signature check passes because it's genuinely from OrgTwo.
5. `MembershipHandler#process` runs `Team.find_or_create_by!(github_id: 100)` — finds the existing `OrgOne/leads` team (organization field untouched) and adds `User("attacker")` as a member via `team.add_member(member)`.
6. `attacker`'s Shipit session now passes `current_user.authorized?` (member of `Shipit.github_teams`), granting full access to stacks owned by `OrgOne`, despite the attacker never having any relationship with `OrgOne`.

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

        "status=#{status}"
      ].join(' '))
    end

        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
