### Title
Unprivileged `DepositDelegatorRewards` lets anyone permanently block a vote account from being closed - ([File: programs/vote/src/vote_state/mod.rs])

### Summary
The report's bug class is: an attacker-controlled, permissionless input (an arbitrary ERC20 implementation) becomes embedded in escrow state and can be weaponized to permanently block a legitimate state transition (offer finalization) for a counterparty who has no way to route around it. The Agave analog is `VoteInstruction::DepositDelegatorRewards` (SIMD-0123), implemented in `deposit_delegator_rewards` [1](#0-0) . This instruction lets *any* signer of the source account push lamports into *any* vote account's `pending_delegator_rewards` field, and the vote program's `withdraw` path then refuses to fully close a vote account while `pending_delegator_rewards > 0` [2](#0-1) .

### Finding Description
`deposit_delegator_rewards` only requires the *source* account to sign the transfer; it performs no check that the caller is the vote account's authorized withdrawer/voter, or has any relationship to the vote account at all: [3](#0-2) 

After the CPI transfer, it unconditionally increments the target vote account's `pending_delegator_rewards`: [4](#0-3) [5](#0-4) 

The vote program's `withdraw` instruction explicitly uses this field to gate account closure: if the withdraw would zero the account's balance, it now requires `pending_delegator_rewards == 0`; otherwise it enforces a higher minimum remaining balance (`rent_exempt + pending_delegator_rewards`): [6](#0-5) 

The only mechanism that reduces `pending_delegator_rewards` is `calculate_block_reward`, invoked during epoch reward distribution, which pays it out proportionally to a vote account's *currently delegated, active* stake: [7](#0-6) 

Critically, if a vote account has **no active delegated stake** for the rewarded epoch (`total_active_stake == 0`), `calculate_block_reward` returns `0` — i.e. `pending_delegator_rewards` is never drawn down, no matter how many epochs pass: [8](#0-7) 

This creates the same structural flaw as the ERC20 report: an unprivileged, adversarial party can inject state into someone else's account (here, a nonzero `pending_delegator_rewards`) that the honest party cannot clear on their own, and that permanently blocks a specific legitimate operation (fully closing/withdrawing the vote account) for the account owner — exactly analogous to Bob's malicious ERC20 blocking Alice's `paySeller` finalization.

### Impact Explanation
An attacker can call `DepositDelegatorRewards` with a trivial deposit (as small as 1 lamport, subject to arithmetic-overflow checks) against any vote account that currently has zero active delegated stake (e.g., a validator that has fully deactivated its stake in preparation to shut down, or a freshly created/undelegated vote account). This permanently prevents the vote account's authorized withdrawer from fully closing/withdrawing the account via `Withdraw`, since:
- Full closure is unconditionally rejected while `pending_delegator_rewards > 0` [9](#0-8) .
- With zero active stake for that vote account, the epoch-reward mechanism that would otherwise pay down `pending_delegator_rewards` never fires [8](#0-7) .

This meets the "permanently frozen accounts" impact bar: legitimate lamports belonging to the vote account owner become permanently unwithdrawable (locked at minimum `rent_exempt_balance + pending_delegator_rewards`), and the account can never be deinitialized/closed, regardless of the owner's cooperation, unless a delegator later re-delegates active stake to that specific vote account (an event outside the victim's control and that the attacker can counteract by repeating the deposit).

### Likelihood Explanation
The attack requires only a signed, permissionless transaction from any funded keypair — no special privileges, no validator/operator role, and no cooperation from the vote account owner is needed. The preconditions (target vote account with zero currently-active delegated stake) are common: newly created vote accounts before stake delegates to them, or vote accounts whose delegators have fully deactivated stake. This is a low-cost, repeatable, unprivileged griefing vector, making likelihood moderate-to-high wherever such vote accounts exist and someone wants to prevent their closure/withdrawal.

### Recommendation
- **Short term:** Restrict `DepositDelegatorRewards` so that only the vote account's authorized withdrawer (or another explicitly authorized party) can increase `pending_delegator_rewards`, or require the deposited amount to be immediately attributable/refundable, so an unrelated third party cannot unilaterally encumber someone else's vote account.
- **Long term:** Decouple the `Withdraw` closure gate from `pending_delegator_rewards` accumulation that has no active stake to consume it — e.g., allow the vote account owner to reclaim/self-distribute (or the runtime to auto-forfeit/refund) `pending_delegator_rewards` when there is no active delegated stake for that vote account, so the reward isn't permanently stranded and the account isn't permanently unclosable.

### Proof of Concept
1. Attacker identifies (or a validator naturally reaches) a vote account `V` with `total_active_stake == 0` for the current/relevant epoch (e.g., all delegators have deactivated).
2. Attacker submits `VoteInstruction::DepositDelegatorRewards { deposit: 1 }` with their own funded keypair as the source account and `V` as the target — no signature from `V`'s authorities is required (`verify_authorized_signer(&source_address, signers)` only checks the source) [10](#0-9) .
3. `V.pending_delegator_rewards` becomes `1` and stays `1` indefinitely, since `calculate_block_reward` returns `0` when `total_active_stake == 0` [8](#0-7) .
4. `V`'s authorized withdrawer attempts `Withdraw(all_lamports)` to close the account; the instruction returns `InstructionError::InsufficientFunds` because `pending_delegator_rewards > 0` blocks full closure [9](#0-8) , matching the existing test pattern for this exact guard [11](#0-10) .
5. The vote account remains permanently unclosable (and its full balance unwithdrawable) as long as no active stake is delegated to it to trigger `calculate_block_reward` payout — a condition fully controllable/re-triggerable by the attacker.

pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}

/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }
}
