### Title
Accrual-time RAY value overflow can permanently freeze a large market - (File: common/src/rates/simulate.rs)

### Summary
The pool accrues interest before every market mutation, and `accrue_step` evaluates `borrowed * borrow_index` and `supplied * supply_index` in RAY using checked `i128` arithmetic. A sufficiently large, high-utilization market can therefore reach a state where the indexes remain below their configured ceilings but their scaled underlying value no longer fits in `i128`. The next `update_indexes`, `withdraw`, `repay`, `borrow`, liquidation, or other market mutation panics during accrual, leaving the market unable to process exits or repayments. [1](#0-0) [2](#0-1) 

### Finding Description
`accrue_step` begins by unscaling both aggregate scaled balances with `scaled_to_original`, which performs `scaled.mul(index)` under checked RAY arithmetic. [3](#0-2) [4](#0-3)  The multiplication calls `fp_core::mul_div_half_up` and panics with `MathOverflow` when the resulting RAY-denominated value cannot fit in `i128`. [5](#0-4) [6](#0-5) 

The borrow-index cap does not prevent this condition because `accrue_step` computes total underlying debt before calculating the next index, and the index ceiling only limits the index itself. [7](#0-6) [8](#0-7)  Every pool mutation first calls `global_sync` through `synced_market`, so once aggregate debt or supply value crosses the representable boundary, each subsequent operation repeats the same overflow before it can reduce debt or shares. [9](#0-8) [10](#0-9) 

The reachable user-facing setup is `Controller::supply` followed by `Controller::borrow`; `Controller::update_indexes` invokes the pool accrual directly, while `withdraw`, `repay`, and `liquidate` reach the same pool accrual through their respective owner-mediated pool calls. [11](#0-10) [12](#0-11) [13](#0-12) 

### Impact Explanation
The affected market becomes permanently unavailable for all state-changing operations that accrue it. Suppliers cannot withdraw, borrowers cannot repay, liquidators cannot repay or seize debt, and keepers cannot advance indexes; the transaction aborts before any corrective balance reduction executes. [2](#0-1) [14](#0-13) 

The repository’s regression test demonstrates that a large 18-decimal market at 98% utilization crosses the RAY-value ceiling while `borrow_index < MAX_BORROW_INDEX_RAY`, after which both one-unit withdrawal and repayment fail with `MATH_OVERFLOW`. [15](#0-14) 

### Likelihood Explanation
Triggering this state requires a market whose governance-admitted caps, asset decimals, available token supply, collateral, utilization, and elapsed time permit aggregate RAY value to exceed `i128::MAX`. The stored proof uses an exceptionally large 18-decimal market and sustained 98% utilization, so this is not a small-balance attack. [16](#0-15) 

Nevertheless, the path uses ordinary `supply`, `borrow`, and `update_indexes` semantics once such a market configuration exists, and no privileged runtime action or corrupted storage is needed at the moment of failure. The condition is also a recognized numeric boundary in the protocol documentation: valid caps do not guarantee that later accrued totals remain representable, and value overflow can occur before the index ceiling. [17](#0-16) 

### Recommendation
Prevent accrual from panicking on aggregate-value overflow by restructuring `accrue_step` and downstream reward calculations to use saturating or widened arithmetic at the aggregate-value layer, or derive utilization and interest without materializing `borrowed * index` and `supplied * index` in `i128`. If overflow is unavoidable, provide a recovery path that can clamp debt/index accounting or socialize the excess without first evaluating the overflowing product.

Add a market-level invariant before committing accrual that detects unrepresentable aggregate values while the transaction still has a recovery option. Index ceilings alone are insufficient; enforce a conservative scaled-share ceiling proportional to `i128::MAX / MAX_BORROW_INDEX_RAY`, accounting for asset decimals and future index growth.

### Proof of Concept
The checked-in test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` constructs a very large `BIG18` market, supplies `BILLION * 10^18`, borrows 98% of it, advances ledger time yearly, and calls `update_indexes` until accrual fails. [18](#0-17) 

At failure, the test verifies `MATH_OVERFLOW`, verifies `borrow_index < MAX_BORROW_INDEX_RAY`, and confirms that subsequent `withdraw` and `repay` calls fail with the same error. [19](#0-18)

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();

fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);

| Deposit conversion at the supply-index floor | About 170.14 million whole tokens before scaled-share overflow |

The token-to-RAY maximum is also the admitted cap maximum. Accrued position
values and market totals must independently fit the RAY domain; valid caps and
bounded indexes do not guarantee that future accrual fits. Value overflow can
occur before the index ceiling and block repayment/withdrawal because those
operations accrue first. At the borrow-index ceiling, further accrual produces
