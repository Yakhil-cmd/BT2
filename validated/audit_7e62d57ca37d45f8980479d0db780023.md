## Analysis

Confirmed: this Shipit instance supports a **multi-organization GitHub App configuration** — `Shipit.github_app_config(organization)` looks up a webhook secret keyed by organization from `secrets.github`, and each organization can have its own `webhook_secret` [1](#0-0) . Multiple orgs sharing one Shipit deployment is an explicit, tested configuration (`secrets_double_github_app.yml`, `OrgOne`/`OrgTwo`) [2](#0-1) .

`WebhooksController#verify_signature` selects **which** organization's `webhook_secret` to check the HMAC signature against using `repository_owner`, derived from `params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`: [3](#0-2) [4](#0-3) 

However, once the signature is deemed valid, the entire raw JSON body (`params`) is dispatched unmodified to event handlers. Handlers determine the actual repository/stack to act on using a **different, independently-controlled field**: `payload.dig('repository', 'full_name')`: [5](#0-4) 

`PushHandler#process`, for instance, resolves `stacks` from that `full_name` and calls `stack.sync_github(expected_head_sha: params.after)` — a `full_name` value never covered by, or bound to, the field used for signature-key selection: [6](#0-5) 

`Repository.from_github_repo_name` splits `full_name` on `/` to find owner+name independently of the `repository.owner.login` field used for verification: [7](#0-6) 

## Binding broken

The equality that should hold but doesn't:

`organization used to select webhook_secret for signature verification (repository.owner.login / organization.login)` == `organization actually written to (repository.full_name)`

Before the attack: for legitimate GitHub-originated webhooks these two fields always agree, because GitHub populates both from the same repository object.

After the attack: an attacker who administers **any** GitHub App installation configured in this Shipit instance (e.g., their own org `attacker-org`, onboarded as one of several installations sharing this Shipit deployment) knows `attacker-org`'s `webhook_secret` (it's visible to them as the app owner, or leaked/weak). They craft a raw POST body where:
- `repository.owner.login` = `attacker-org` (and/or top-level `organization.login` = `attacker-org`) → causes `verify_signature` to fetch `Shipit.github(organization: "attacker-org")` and validate the HMAC using `attacker-org`'s secret, which the attacker controls, so the signature check passes.
- `repository.full_name` = `"victim-org/victim-repo"` → causes `PushHandler` (or `PullRequest` handlers, `StatusHandler`, etc.) to resolve `Repository.from_github_repo_name` against the victim org's repository/stack and act on it (e.g., trigger `stack.sync_github`, forcing a sync to an attacker-chosen `expected_head_sha`/ref, or manipulate commit status/PR label state on the victim's stacks).

This is a cross-repository/cross-organization write: the HMAC signature legitimately proves knowledge of `attacker-org`'s secret, but the payload is executed against `victim-org`'s stack, which was never covered by that signature.

## Impact

This matches the "Critical - cross-repository writes / unauthorized deploy" bar: an attacker with legitimate control of one tenant's GitHub App installation in this multi-org Shipit deployment can force Shipit to sync, deploy-relevant commit status changes, or PR-state changes against a **different** organization's stacks that they do not control, entirely bypassing the intent of per-organization webhook signature isolation.

### Title
Webhook signature is verified against the org derived from `repository.owner.login`, but handlers act on the org in `repository.full_name` — cross-tenant repository writes ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App / webhook secret to validate against using `repository.owner.login` (or `organization.login`), while `Shipit::Webhooks::Handlers::Handler#repository_name` (used by all event handlers) resolves the target `Stack`/`Repository` using the independent `repository.full_name` field of the same JSON body. In a multi-organization Shipit deployment, these two fields are never cross-checked, so a valid signature from one tenant's app installation authorizes handler-side mutation of another tenant's stacks.

### Finding Description
- `verify_signature` fetches `Shipit.github(organization: repository_owner)` and calls `verify_webhook_signature` using that org's `webhook_secret` [3](#0-2) .
- `repository_owner` comes from `params.dig('repository','owner','login') || params.dig('organization','login')` [4](#0-3) .
- After verification, the raw parsed body is passed unchanged to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [8](#0-7) .
- Handlers derive the operative repository from `payload.dig('repository', 'full_name')`, not from `repository.owner.login` [5](#0-4) .
- `Repository.from_github_repo_name` looks up the DB record purely from that `full_name` [7](#0-6) .
- Nothing enforces that the repository resolved by `full_name` belongs to the organization used for signature verification.

### Impact Explanation
This breaks the trust boundary between tenants in a shared Shipit deployment: possession of a valid signature for organization A's GitHub App is sufficient to trigger writes (git sync, PR/commit-status state changes, stack archive/unarchive) against organization B's stacks. This is a cross-repository write / unauthorized deploy-adjacent action, matching the Critical impact bar.

### Likelihood Explanation
Requires the attacker to control (or know the webhook secret of) at least one GitHub App installation configured on the shared Shipit instance — a realistic scenario for any Shipit deployment onboarding multiple organizations/customers, each of whom is an "unprivileged attacker" relative to other tenants' repositories. No Shipit session, API token, or GitHub write access to the victim org is needed.

### Recommendation
After signature verification, assert that `repository.owner.login` (the org whose secret validated the signature) matches the owner segment of `repository.full_name` before dispatching to handlers; reject the webhook otherwise.

### Proof of Concept
1. Deploy Shipit with two orgs configured, `attacker-org` and `victim-org`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`) [9](#0-8) .
2. Attacker builds a `push` event JSON body: `{"repository": {"owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo"}, "ref": "refs/heads/main", "after": "<attacker-chosen-sha>"}`.
3. Attacker signs the raw body with `attacker-org`'s known `webhook_secret` and sets `X-Hub-Signature`.
4. POST to `/webhooks` with `X-Github-Event: push`. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and the signature validates.
5. `PushHandler` resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")`, acting on `victim-org`'s stack despite the signature only proving control of `attacker-org`'s secret [6](#0-5) .
