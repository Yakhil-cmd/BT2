### Title
Webhook `status` handler writes commit statuses without validating them against the authenticated organization/repository - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::WebhooksController#verify_signature` authenticates an inbound webhook only against the *organization* named in the payload (`repository.owner.login`, falling back to `organization.login`), and looks up that organization's `webhook_secret` to check the HMAC. `Shipit::Webhooks::Handlers::StatusHandler`, which is invoked immediately afterward for `status` events, never re-checks that the commit it is about to mutate actually belongs to that same organization/repository — it looks the target commit up globally by SHA. This breaks the binding "organization that authenticated == repository that is written."

### Finding Description
The webhook signature check is performed once, at the controller level, scoped to a single organization derived purely from attacker-controlled payload fields: [1](#0-0) [2](#0-1) 

`verify_webhook_signature` is a no-op (`return true unless webhook_secret`) when the target organization has no `webhook_secret` configured: [3](#0-2) 

Configuring an organization without a `webhook_secret` is an explicitly supported, "optional" setup documented in `docs/setup.md` ("Webhook secret (optional)"), and shipped as the default template value (`webhook_secret: # nil`) in the sample secrets files. In a multi-organization Shipit install (the `github:` config supports multiple orgs, each with its own `webhook_secret`), any org without a configured secret becomes a completely unauthenticated entry point into `/webhooks`, because signature verification always returns `true` for it.

Most webhook handlers scope the data they touch to the repository named in the same payload via `Handler#stacks`, which resolves `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))`: [4](#0-3) 

`StatusHandler`, however, does not use this scoping mechanism at all. It resolves the target purely by commit SHA, globally, across every stack/repository/organization tracked by the whole Shipit instance: [5](#0-4) 

So the equality that should hold — "the organization whose secret authenticated this request" == "the repository/commit that gets written" — is never enforced. The org used to pick the `webhook_secret` (and thus pass/fail signature verification) can be any org configured in Shipit (including one with a `nil` secret, i.e. no verification at all), while the record mutated (`Commit#create_status_from_github!`) is chosen solely by an attacker-supplied SHA, with zero repository/org filtering.

### Impact Explanation
An unprivileged attacker who needs no Shipit session, API token, or GitHub credentials for the target repository can:
1. Identify (or brute force/observe, since SHAs are not secrets) a commit SHA belonging to a *different*, sensitive stack/repository tracked by the same Shipit instance.
2. POST a forged `status` event to `/webhooks` with `repository.owner.login` set to any organization configured with no (or a known/leaked) `webhook_secret`.
3. Have `StatusHandler` create an arbitrary `CommitStatus` (state, context, description, target_url) on the unrelated commit belonging to the sensitive repository.

Because commit statuses feed directly into Shipit's CI gating (`ci.require` contexts), `deployable?`/continuous-deployment checks, and merge-queue validation described in the README, an attacker can forge a passing CI status for a required context on a commit they do not control, potentially unblocking an unauthorized deploy or merge on a stack belonging to an organization/repository they have no legitimate access to. This is a cross-repository write achieved purely by exploiting the org/repository binding gap in webhook processing — qualifying as Critical impact ("cross-repository writes" / "an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Likelihood is high in any multi-organization Shipit deployment where at least one configured organization has no `webhook_secret` set (an explicitly supported/documented configuration) or where a `webhook_secret` for any one org has leaked. No GitHub App private key, Shipit session, or `ApiClient` token is required — only a raw HTTP POST to the public `/webhooks` endpoint with a crafted JSON body and the correct `X-Github-Event: status` header, plus knowledge of a target commit SHA.

### Recommendation
`StatusHandler` (and any other handler that does not go through `Handler#stacks`) must scope its lookup to the repository named in the (independently-signed) `repository.full_name` field, e.g. `Repository.from_github_repo_name(repository_name)&.stacks&.joins(:commits)&.where(shipit_commits: { sha: params.sha })`, and the controller should verify that the organization used to authenticate the signature actually owns the repository named in `repository.full_name`, rejecting mismatches. Additionally, treat organizations with a blank/`nil` `webhook_secret` as unverifiable and reject their webhooks by default rather than treating them as automatically verified.

### Proof of Concept
Assume a Shipit instance configured with two GitHub orgs: `trusted-org` (has a `webhook_secret`, hosts `trusted-org/sensitive-repo` with commit SHA `abcd1234…` gating a deploy on CI context `ci/tests`) and `attacker-org` (any org registered in Shipit's `github:` config with `webhook_secret` left blank, per the documented optional setting).

```
POST /webhooks HTTP/1.1
X-Github-Event: status
Content-Type: application/json

{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" },
  "sha": "abcd1234...",           // commit that actually belongs to trusted-org/sensitive-repo
  "state": "success",
  "context": "ci/tests",
  "target_url": "https://example.com"
}
```

`verify_signature` resolves `repository_owner = "attacker-org"`, and since `attacker-org.webhook_secret` is `nil`, `verify_webhook_signature` short-circuits to `true` — no signature is actually checked. `StatusHandler#process` then runs `Commit.where(sha: "abcd1234...")`, finds the commit under `trusted-org/sensitive-repo`, and calls `create_status_from_github!`, writing a forged `success` status for `ci/tests` onto a commit the attacker never had access to, potentially unblocking a deploy gated on that context.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
