### Title
Webhook signature is verified against the organization derived from `repository.owner.login`/`organization.login`, but handlers act on the unrelated `repository.full_name` field, letting a valid sender for one configured GitHub org spoof events for another org's repositories - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In a multi-organization Shipit deployment, `WebhooksController#verify_signature` selects which org's `webhook_secret` to validate the HMAC against using `repository_owner`, computed from `params.dig('repository','owner','login')` (falling back to `organization.login`). Once that check passes, every event handler determines *which repository/stack to mutate* using a completely different field, `payload.dig('repository','full_name')` (`app/models/shipit/webhooks/handlers/handler.rb`, `repository_name`/`stacks`). Nothing cross-validates that the `full_name` repository actually belongs to the same organization that was used to select and verify the webhook secret.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
This picks the `GitHubApp` config (and thus the `webhook_secret` used for HMAC verification, see `lib/shipit/github_app.rb#verify_webhook_signature`) purely from `repository.owner.login`/`organization.login` in the untrusted JSON body.

`app/models/shipit/webhooks/handlers/handler.rb`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```
All handlers (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, `PullRequest::*Handler`, `MembershipHandler`, etc.) resolve the target `Repository`/`Stack` from `repository.full_name`, not from `repository.owner.login`.

Because Shipit supports configuring multiple GitHub organizations (`config/secrets.development.shopify.yml`, `test/dummy/config/secrets_double_github_app.yml`), each with its own `webhook_secret`, an attacker who legitimately administers (or otherwise knows the webhook secret of) *OrgA* can build a JSON payload where:
- `repository.owner.login` = `"OrgA"` (so `verify_signature` looks up and verifies against OrgA's secret - which the attacker controls/knows),
- `repository.full_name` = `"OrgB/victim-repo"` (a stack belonging to a different, unrelated organization onboarded on the same Shipit instance).

Since the HMAC is only checked for validity under OrgA's secret and the body is entirely attacker-controlled, this passes `verify_signature`, and the dispatched handler then acts on `OrgB/victim-repo` using attacker-supplied data (fake commit SHAs/statuses, fake push `after` SHA, fake check-suite results, fake PR events, membership/team creation, etc.) despite the attacker never having any authorized relationship with OrgB or its webhook secret.

This is the analog of the `MAX_SHORTFALL_WITHDRAW` bug class: a guard is enforced against one value (the 50% cap / the org used for signature check) while the actually consequential state mutation is driven by a different, uncovered value (repeated calls bypassing the cap / a different repository field bypassing the org binding).

### Impact Explanation
This breaks the binding "organization that authenticated == repository that is written." A sender authenticated only for OrgA can cause writes against OrgB's stacks: injecting forged commit statuses (`StatusHandler`/`Commit#create_status_from_github!`) that could satisfy `ci.require` checks and enable an unauthorized deploy, forcing `GithubSyncJob` syncs with attacker-chosen `expected_head_sha` (`PushHandler`), forging check-suite/PR state, or fabricating team memberships (`MembershipHandler`) that affect `Shipit.github_teams` authorization for a repository outside the attacker's own organization. This falls in the "cross-repository writes" / potential "unauthorized deploy" impact category.

### Likelihood Explanation
Requires a Shipit instance configured with more than one GitHub organization (a documented, supported configuration) and requires the attacker to be a legitimate webhook sender for at least one of those orgs (e.g., an org admin who can view/rotate that org's own webhook secret, or anyone who can guess/leak it, but not a privileged Shipit account). Given the multiple test fixtures and docs dedicated to multi-org setups, this is a realistic deployment pattern, though it does not affect single-org deployments (where `repository_owner` always resolves to the one configured org and the binding is trivially satisfied).

### Recommendation
After signature verification succeeds using the org derived from `repository_owner`, re-derive the organization from `repository.full_name` (the field handlers actually act on) and reject the request (422) if it does not match `repository_owner`/the org used for verification. Alternatively, always verify the signature against *every* configured org's secret and only accept if the same org's secret both verifies the signature and matches the repository actually referenced in `full_name`.

### Proof of Concept
1. Configure Shipit with two orgs, `OrgA` and `OrgB`, each with a distinct `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker (who administers OrgA's GitHub App/webhook and thus possesses OrgA's `webhook_secret`) builds a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` computes `repository_owner == "OrgA"`, loads `Shipit.github(organization: "OrgA")`, and successfully verifies the signature against OrgA's secret.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("OrgB/victim-repo")` and calls `stack.sync_github(expected_head_sha: params.after)` on a stack the attacker has no legitimate relationship with, using attacker-controlled parameters — despite never possessing OrgB's webhook secret.     def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
