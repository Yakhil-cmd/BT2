### Title
Webhook signature verification keys off `repository.owner.login`/`organization.login` while handlers act on the independently-attacker-controlled `repository.full_name` field, letting an org's own webhook secret forge events for a different org's stacks - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate the HMAC signature against using `repository_owner`, computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. The `create` action then hands the *entire, unfiltered* JSON payload to the event handlers, which independently resolve the target `Repository`/`Stack` via `payload.dig('repository', 'full_name')` (e.g. `Handler#repository_name`, used by `PushHandler`, `StatusHandler` via `Commit.where(sha:)`, `CheckSuiteHandler`, and all `PullRequest::*Handler`s through `Repository.from_github_repo_name`). Since `repository.owner.login` and `repository.full_name` are two independent fields inside the same attacker-supplied JSON object, nothing enforces they agree. ### Finding Description
Shipit supports multiple independently configured GitHub organizations, each with its own `webhook_secret` (`Shipit.github_app_config`, `docs/setup.md` "Using Multiple Github Applications"). Anyone who administers a GitHub App installation for their *own* organization (`org-attacker`) legitimately knows that org's `webhook_secret` — this is a normal, unprivileged configuration credential scoped only to their own org. [5](#0-4) [6](#0-5) 

The binding that should hold is: **organization that authenticated the signature == repository that gets written to by the handler**. In `verify_signature`, the organization used to pick the secret is `repository.owner.login` (or `organization.login`). But the handlers never re-check that owner against the org whose secret validated the request; instead they trust `repository.full_name` verbatim to look up `Repository`/`Stack` (`Repository.from_github_repo_name`, `Commit.where(sha:)`) with no ownership cross-check. [7](#0-6) [8](#0-7) [9](#0-8) 

An attacker who legitimately controls `org-attacker`'s webhook secret can therefore sign an arbitrary JSON body — computing HMAC-SHA1 with their own secret — that sets `repository.owner.login = "org-attacker"` (so `verify_signature` fetches and validates against `org-attacker`'s secret, which succeeds) while setting `repository.full_name = "victim-org/victim-repo"` (an arbitrary victim stack tracked by Shipit under a different, unrelated GitHub App/organization). The mismatch is never checked before dispatch to handlers.

### Impact Explanation
This breaks the trust boundary between GitHub organizations that Shipit's multi-org webhook design is meant to enforce: a signature valid only for `org-attacker` is accepted as authorization to mutate state belonging to `victim-org`'s stacks. Concretely:
- Forging a `status` event with `state: "success"` for an arbitrary `sha` lets the attacker create a fabricated commit status on a victim stack's commit (`Commit#create_status_from_github!`), which can satisfy `continuous_deployment` gating and trigger an unauthorized deploy of that commit.
- Forging a `push` event with `repository.full_name` set to the victim stack causes `stack.sync_github(expected_head_sha:)` to run against the victim stack, forcing a resync from an attacker-chosen SHA claim.
- Forging `pull_request`/`check_suite` events similarly manipulates victim `ReviewStack`s (archive/unarchive, check-run refresh) despite the request only being authenticated for a different, unrelated org.

This matches the "Critical: unauthorized deploy" / cross-organization write-boundary violation class, since it results in a deploy (or state mutation) of a repository the requester's authenticated org has no relationship to.

### Likelihood Explanation
Medium-High: exploitation requires only that Shipit be configured with more than one GitHub organization (explicitly documented and supported: `docs/setup.md` "Using Multiple Github Applications", `test/dummy/config/secrets_double_github_app.yml`) and that the attacker controls at least one of those organizations' webhook secret — a normal, unprivileged position for any org onboarded onto a shared Shipit instance. No GitHub write access, `ApiClient` token, or Shipit session is required; only crafting a raw HTTP POST with a valid HMAC-SHA1 signature computed from the attacker's own known secret.

### Recommendation
After successfully verifying the HMAC signature against the organization derived from the payload, re-derive the "authenticated organization" and cross-check it against every repository the handler will act upon (compare `repository.owner.login` to the *actual* owner of `Repository.from_github_repo_name(repository.full_name)`, or simply require `repository.full_name.split('/').first == authenticated_organization` before invoking handlers) and reject the request (422) on mismatch.

### Proof of Concept
1. Configure Shipit with two GitHub orgs, `org-attacker` and `victim-org`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. Victim has an existing tracked `Stack` for `victim-org/victim-repo` with `continuous_deployment: true`.
3. Attacker (who administers the `org-attacker` GitHub App / knows its `webhook_secret`) crafts a `status` webhook payload:
```json
{
  "sha": "<victim-commit-sha>",
  "state": "success",
  "context": "ci/attacker-forged",
  "repository": { "owner": { "login": "org-attacker" }, "full_name": "victim-org/victim-repo" }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(org-attacker's webhook_secret, raw_body)>` and POSTs to `/github/webhooks`.
5. `verify_signature` resolves `repository_owner` to `"org-attacker"`, fetches `org-attacker`'s `GitHubApp`, and successfully verifies the signature against the attacker's own secret.
6. `create` dispatches the full payload to `StatusHandler`, which does `Commit.where(sha: params.sha)` — matching the victim's commit regardless of the signing org — and calls `commit.create_status_from_github!(params)`, injecting a forged "success" status that can trigger an unauthorized deploy of `victim-org/victim-repo`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
