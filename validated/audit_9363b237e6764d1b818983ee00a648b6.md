### Title
Membership webhook trusts `organization.login` independently of the org whose secret verified the signature (`repository_owner`), letting a forged `membership` payload write a `Membership` for an arbitrary organization's `Team` - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/membership_handler.rb], [File: app/models/shipit/membership.rb])

### Summary
`Shipit::Membership` only validates `uniqueness: { scope: :team_id }` and has no check that the membership's origin matches the `Team#organization`, so the model layer provides zero defense against a forged row. That defense is supposed to live in the webhook layer, but `WebhooksController#verify_signature` selects the signing organization from `repository_owner` (`repository.owner.login`, falling back to `organization.login`), while `MembershipHandler#find_or_create_team!` independently trusts `params.organization.login` to set/match `Team#organization`. Because `MembershipHandler`'s `ExplicitParameters` schema never forbids or requires equality between an (attacker-supplied) `repository` object and the `organization` object, these two fields can diverge, breaking `Membership.team.organization == verified_webhook_organization`.

### Finding Description
The binding under test: for every `Shipit::Membership` row, `membership.team.organization == <the organization whose HMAC secret verified the inbound webhook>`.

Trace:
1. `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) computes `repository_owner` via `params.dig('repository','owner','login') || params.dig('organization','login')` (`app/controllers/shipit/webhooks_controller.rb:59-62`) and verifies the signature against `Shipit.github(organization: repository_owner)`.
2. `MembershipHandler#process` (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-34`) ignores `repository_owner` entirely and calls `find_or_create_team!`, which sets `team.organization = params.organization.login` (`app/models/shipit/webhooks/handlers/membership_handler.rb:38-42`).
3. `MembershipHandler`'s `params do ... end` schema (`app/models/shipit/webhooks/handlers/membership_handler.rb:7-21`) requires `action`, `team`, `organization`, `member` but does not require or constrain any `repository` key — extra top-level keys are not rejected.
4. `team.add_member(member)` (`app/models/shipit/team.rb:41-43`) then calls `members.append(member)`, creating a `Membership` row through the `has_many :memberships` association, whose only guard is `validates :user_id, uniqueness: { scope: :team_id }` (`app/models/shipit/membership.rb:8`).

Exploit: an attacker who owns a GitHub organization/repository that is already integrated with this Shipit instance (satisfying "emit webhooks from a repository they own") crafts (or lets GitHub deliver, then intercepts/replays via their own controlled endpoint content) a `membership` event body that includes:
```json
{
  "action": "added",
  "team": { "id": <shopify_team_github_id>, "name": "...", "slug": "...", "url": "..." },
  "organization": { "login": "shopify" },
  "member": { "login": "attacker" },
  "repository": { "owner": { "login": "attacker-org" } }
}
```
`repository_owner` resolves to `"attacker-org"` (their own org, whose webhook they legitimately control/observe), so `verify_signature` passes using the attacker's own org credentials/secret. `find_or_create_team!`, however, resolves/creates the `Team` using `organization.login == "shopify"` and `team.github_id` matching a real Shopify team, then adds `attacker` as a member — producing a `Membership` row that is indistinguishable from a legitimate Shopify-sourced membership, even though the signature never involved Shopify's credentials.

Why existing guards fail: `verify_signature` only proves the request was signed by *some* registered organization's secret — it never re-checks that the same organization appears consistently across every payload field the handler subsequently trusts. `drop_unhandled_event` and the `ExplicitParameters` schema check field *types*, not cross-field/cross-scope consistency. `Membership`'s model validation, being scoped only to `team_id`, cannot detect or reject this because it has no notion of "origin organization" at all — exactly the gap the question describes.

### Impact Explanation
A successful forged `membership` webhook grants the attacker (or any GitHub login they name) `Shipit::Team` membership for an arbitrary target organization/team known only by its GitHub `team.id`, without ever authenticating to that organization. Since `Shipit.github_teams` authorization and stack access in this engine are gated by team membership (`Team`/`Membership`), this escalates into `Shipit.github_teams` authorization — a High/Critical impact per the rubric, and it is repeatable against any team whose `github_id` the attacker can enumerate/guess, across any organization configured on the same Shipit instance (cross-tenant blast radius).

### Likelihood Explanation
Requires: (a) the attacker's own organization/repository is already onboarded to this Shipit instance (a precondition explicitly allowed by the rules — "emit webhooks from a repository they own"), so `Shipit.github(organization: 'attacker-org')` doesn't raise `GithubOrganizationUnknown`; (b) knowledge or ability to trigger a validly-signed webhook for `repository_owner == 'attacker-org'` (trivial if it's their own installation); (c) knowledge of the target team's numeric `github_id` (discoverable via GitHub's public API for many orgs/teams). No Shipit session, API token, or GitHub App private key is needed. This is feasible and repeatable per victim team.

### Recommendation
In `MembershipHandler` (and any other handler that reads both `repository` and `organization`), require the payload's declared organization to equal the `repository_owner` value that was used to verify the signature (thread it through from the controller rather than re-deriving), and reject the request otherwise. Additionally, forbid unexpected top-level keys in the `ExplicitParameters` schema so an attacker cannot inject a spoofing `repository` object into an `organization`-scoped event. As defense in depth, consider adding a model-level or handler-level assertion tying `Membership`/`Team` creation to the verified organization.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual, not to be placed per OUT OF SCOPE test/** rule for grading,
# but illustrates the exact assertion needed)
test "forged membership payload with mismatched repository.owner vs organization.login creates cross-org membership" do
  GithubHook.any_instance.stubs(:verify_signature).returns(true)
  @request.headers['X-Github-Event'] = 'membership'

  shopify_team = shipit_teams(:shopify_developers) # organization: 'shopify'
  payload = {
    action: 'added',
    team: { id: shopify_team.github_id, name: shopify_team.name, slug: shopify_team.slug, url: shopify_team.api_url },
    organization: { login: 'shopify' },
    member: { login: 'attacker' },
    repository: { owner: { login: 'attacker-org' } } # controls which org's secret verify_signature checks
  }

  Shipit.stubs(:github).with(organization: 'attacker-org').returns(stub(verify_webhook_signature: true))

  assert_difference -> { Shipit::Membership.count }, 1 do
    post :create, body: payload.to_json, as: :json
    assert_response :ok
  end

  membership = Shipit::Membership.last
  assert_equal 'shopify', membership.team.organization   # LHS: Team org the row points to
  # RHS should be 'attacker-org' (the org that actually verified the signature) but is never checked anywhere
  assert membership.valid? # Membership model has no validation catching this divergence
end
```
