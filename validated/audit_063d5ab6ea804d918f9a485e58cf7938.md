### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the target commit purely by SHA (`Commit.where(sha: params.sha)`) with no repository/stack scoping, unlike the `stacks`/`repository_name` helpers the base `Handler` class exposes for exactly this purpose. Any webhook whose GitHub-App signature validates for the sender's own org/repo can therefore write a status onto a `Commit` row belonging to a completely different stack, as long as the SHA values coincide (e.g. shared git history from a fork). On a stack with `merge_queue_enabled: true`, this forged status is consumed by `Commit#add_status`, which reevaluates `deployable?`/`blocked?` and calls `stack.schedule_merges`, directly influencing that victim stack's merge/ship decisions.

### Finding Description
The broken binding is: `commit.stack_id` (the row `StatusHandler` mutates) should equal `Repository.from_github_repo_name(payload.repository.full_name).stack_id` (the stack that authenticated the webhook). It does not.

Path:
1. `Shipit::WebhooksController#create` parses the JSON body and dispatches to handlers after `verify_signature`, which only checks that the HMAC matches the GitHub App secret for `repository_owner` derived from the payload — it never restricts *which stack's commits* the handler is allowed to touch. [1](#0-0) 
2. The base `Handler` class provides `stacks`/`repository_name` helpers specifically to scope handler logic to the repository that sent the payload. [2](#0-1) 
3. `StatusHandler#process` ignores that scoping entirely and looks up commits by bare SHA across the whole `commits` table: [3](#0-2) 
4. `Commit#create_status_from_github!` → `add_status` records the new status, recomputes `status`/`deployable?`, and — critically — calls `stack.schedule_merges` when the simple state transitions to pending or success, and separately affects `blocked?`/`deployable?` used by the merge queue on every state change: [4](#0-3) [5](#0-4) 

Exploit flow: an attacker who owns/controls a repository under an org for which the Shipit GitHub App is installed (satisfying `verify_signature`) forks or otherwise obtains a commit whose SHA is identical to a commit already tracked by a victim stack with `merge_queue_enabled: true` (git SHA1 is a hash of tree+parents+message, so identical content — e.g. a forked branch that hasn't diverged — produces an identical SHA in both repos). The attacker sends a `status` webhook from their own, legitimately-signed repository with `context: ci/build`, `state: failure` (or `success`) for that shared SHA. `StatusHandler#process` finds the *victim's* `Commit` row (same SHA, different `stack_id`) and writes the forged status onto it, flipping `deployable?`/`blocked?` for the victim stack and triggering `schedule_merges`.

Existing guards do not prevent this: `verify_signature` authenticates only the sender's own org/repo, not the target commit's ownership; the `ExplicitParameters` schema for `StatusHandler` only validates types (`sha`, `state`, `context`, etc.), not repository identity; and `StatusHandler`, unlike other handlers that use `stacks`/`repository_name`, performs no repository-based filtering at all.

### Impact Explanation
A forged `ci/build` status can be written onto a stack the attacker never authenticated for, altering `Commit#deployable?`/`blocked?` state and triggering `Stack#schedule_merges` on a `merge_queue_enabled` stack. This is a payload from one repository mutating another repository's stack/commit state, matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team" / "unauthorized deploy, rollback or merge"). Blast radius spans any two stacks/repos that ever share a commit SHA (forks of the same repo, cherry-picked/rebase-preserved commits, monorepo mirrors), and is repeatable for every shared SHA the attacker can produce.

### Likelihood Explanation
Preconditions: the attacker must control a repository whose org has the Shipit GitHub App installed (so `verify_signature` passes), and a SHA must be shared between that repository and the victim's tracked stack (realistic when an attacker forks the victim repo before it diverges, or reuses/cherry-picks a commit with identical tree/parents/message). No Shipit session, API token, or GitHub secret is required beyond a legitimate GitHub webhook signature for the attacker's own repo — a capability explicitly granted to unprivileged attackers under this threat model ("emit webhooks from a repository they own"). This makes the attack low-cost and repeatable.

### Recommendation
Scope `StatusHandler#process` to the stacks that authenticated the webhook, mirroring the `stacks`/`repository_name` pattern already defined on `Handler`: resolve commits via `stacks.flat_map(&:commits).where(sha: params.sha)` (or join `Commit` to `Repository` through `Stack` and filter by `repository_name`) instead of the global `Commit.where(sha: params.sha)`.

### Proof of Concept
Minitest plan (no live GitHub):
1. Create two `Repository`/`Stack` fixtures, `repo_a` (attacker's) and `repo_b` (victim), with `repo_b.merge_queue_enabled = true` and `required_statuses`/`blocking_statuses` including `ci/build`.
2. Create a `Commit` row under `repo_b`'s stack with a fixed `sha` (e.g. `"deadbeef" * 5`) and an existing passing `ci/build` status, asserting `commit_b.deployable?` is `true` (or previous merge-queue state is known) before the attack — this is the "before" side of the equality `commit.stack_id == repo_a.stack.id` (false) vs `commit.stack_id == repo_b.stack.id` (true).
3. Build a `status` webhook payload with `repository.full_name = repo_a.github_repo_name`, `sha` equal to the same value, `context: "ci/build"`, `state: "failure"`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly (bypassing signature verification, per the fast-validation note).
5. Assert `commit_b.reload.deployable?` flipped to `false` / `blocked?` became `true` / `stack_b.schedule_merges` was invoked (e.g. via `Stack.any_instance.expects(:schedule_merges)` or checking merge queue side effects), even though the payload's `repository.full_name` was `repo_a`, never `repo_b`. This demonstrates the equality `commit.stack_id == stack_for(payload.repository.full_name)` is violated.
