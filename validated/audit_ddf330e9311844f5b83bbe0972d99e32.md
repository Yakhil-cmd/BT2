### Title
Spendable textcoin mnemonic (equivalent to a private key) is written in plaintext to application logs - ([File: wallet.js])

### Summary
`claimBackOldTextcoins()` in `wallet.js` logs the full textcoin `mnemonic` value in plaintext via `console.log` whenever a claim-back attempt succeeds or fails. The `mnemonic` is not a label or metadata field — it is the literal seed phrase from which the spending key for the textcoin's one-time address is derived, functionally identical to a password/private key. This mirrors CVE-2022-3697 (GHSA-cpx3-93w7-457x), where Ansible's `tower_callback` handling caused a secret credential to be written to logs, enabling anyone with log access to obtain it and act with the victim's privileges.

### Finding Description
When a user sends a "textcoin" payment, `sendMultiPayment()` generates a fresh BIP39 `mnemonic`, derives an address/definition from it (`m/44'/0'/0'/0/0`), and persists the mnemonic in the `sent_mnemonics` table so it can later be emailed/shared with the recipient or reclaimed by the sender. [4](#0-3) [5](#0-4) 

`expandMnemonic()` shows that the mnemonic alone is sufficient to reconstruct the full HD private key (`addrInfo.xPrivKey`), public key, definition, and address: [1](#0-0) 

`receiveTextCoin()` then uses `addrInfo.xPrivKey.privateKey` directly to sign and spend the unit at that address: [2](#0-1) 

`claimBackOldTextcoins()`, invoked when a sent textcoin has gone unclaimed past a configured expiry, reads unclaimed mnemonics from `sent_mnemonics` and, for every row, logs the raw mnemonic string directly to console/log output on both the success and failure paths: [6](#0-5) 

Any log aggregation system, log file, crash reporter, or process supervisor that captures stdout — which is exactly the class of exposure the referenced Ansible advisory (CWE-233, sensitive parameter leaked to logs) is about — will now contain the raw spending seed for that textcoin address. Unlike the wallet's raw private keys (which are typically encrypted at rest and never intentionally logged), this codepath deliberately serializes the plaintext mnemonic into the log stream.

### Impact Explanation
Whoever gains read access to the node's logs obtains the same mnemonic that `expandMnemonic()` uses to derive the private key for the associated address. Since the textcoin's whole design is "possession of the mnemonic = ability to spend the funds," log exposure directly enables unauthorized spending of the underlying bytes/asset — either by racing the legitimate claim-back transaction or by claiming the funds before the sender's automatic reclaim job runs (the same address is not marked reclaimed until an actual unit lands, per `eraseTextcoin()`/`unit_authors` check in the query used by `claimBackOldTextcoins`). This is a concrete unauthorized-spending scenario, not merely an information disclosure.

### Likelihood Explanation
This code path executes automatically whenever `claimBackOldTextcoins()` runs (typically on a periodic timer configured by the wallet operator to reclaim stale textcoins), for every unclaimed mnemonic that has aged past the configured number of days — no attacker interaction or malicious peer is required. Any component with log/stdout visibility (log shipping agents, crash/monitoring integrations, misconfigured verbose logging retained on disk) is sufficient to harvest the secret; this is a normal, everyday operational codepath rather than an edge case.

### Recommendation
Never log the raw `mnemonic` value. In `claimBackOldTextcoins()` (and anywhere else a mnemonic is logged, e.g. `getPrivateProfileFromJsonBase64`-style debug prints), log only non-sensitive identifiers such as the derived `addrInfo.address`, the `unit`, or a truncated/hashed representation of the mnemonic. Audit other `console.log` sites that print `mnemonic`, `xPrivKey`, or other key material (e.g., `decryptPackage`'s commented-out private key logs in `device.js`) to ensure none of them are enabled in production logging configurations.

### Proof of Concept
1. Configure a wallet/node that periodically calls `claimBackOldTextcoins(to_address, days)` (or trigger it directly) with `sent_mnemonics` containing at least one row where `unit_authors.address IS NULL` and `creation_date` is older than `days`.
2. Ensure the node writes stdout to a log file or forwards it to a log aggregator (a standard deployment practice).
3. Observe the log line `"claimed back mnemonic "+row.mnemonic+", unit "+unit+", asset "+asset` (or the failure variant) printed with the full plaintext mnemonic. [7](#0-6) 
4. Any party with read access to that log (log-shipping infra, support tooling, misconfigured public log endpoint, etc.) can feed the captured mnemonic into `expandMnemonic()` to derive the private key and immediately submit a spending transaction from the corresponding address, front-running the legitimate reclaim/claim flow.

function expandMnemonic(mnemonic) {
	var addrInfo = {};
	mnemonic = mnemonic.toLowerCase().split('-').join(' ');
	if ((mnemonic.split(' ').length % 3 !== 0) || !Mnemonic.isValid(mnemonic)) {
		throw new Error("invalid mnemonic: "+mnemonic);
	}
	mnemonic = new Mnemonic(mnemonic);
	addrInfo.xPrivKey = mnemonic.toHDPrivateKey().derive("m/44'/0'/0'/0/0");
	addrInfo.pubkey = addrInfo.xPrivKey.publicKey.toBuffer().toString("base64");
	addrInfo.definition = ["sig", {"pubkey": addrInfo.pubkey}];
	addrInfo.address = objectHash.getChash160(addrInfo.definition);
	return addrInfo;
}

function claimBackOldTextcoins(to_address, days){
	if (typeof days !== 'number')

	db.query(
		"SELECT mnemonic FROM sent_mnemonics LEFT JOIN unit_authors USING(address) \n\
		WHERE mnemonic!='' AND unit_authors.address IS NULL AND creation_date<"+db.addTime("-"+days+" DAY"),
		function(rows){
			async.eachSeries(

					receiveTextCoin(row.mnemonic, to_address, function(err, unit, asset){

						else
							console.log("claimed back mnemonic "+row.mnemonic+", unit "+unit+", asset "+asset);
						cb();
					});
				}
			);
		}
	);
}
