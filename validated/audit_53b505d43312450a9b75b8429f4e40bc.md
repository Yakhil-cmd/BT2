### Title
Regular Expression Denial of Service (ReDoS) in `isValidEmail` via vulnerable email regex - (File: validation_utils.js)

### Summary
`validation_utils.js` contains an `isValidEmail()` helper whose regular expression is structurally identical to the `email_regex` in `flask-restx` that was assigned CVE-2021-32838 / GHSA-3q6g-vf58-7m4g for catastrophic backtracking. The same nested-quantifier construction is present verbatim in ocore, and this helper is reachable from wallet/device-facing URI parsing.

### Finding Description
`isValidEmail` uses the pattern: [1](#0-0) 

```
/^(([^<>()\[\]\\.,;:\s@"]+(\.[^<>()\[\]\\.,;:\s@"]+)*)|(".+"))@((\[[0-9]{1,3}\.[0-9]{1,3}\.[0-9]{1,3}\.[0-9]{1,3}\])|(([a-zA-Z\-0-9]+\.)+[a-zA-Z]{2,}))$/
```

Both the local part `([^<>()\[\]\\.,;:\s@"]+(\.[^<>()\[\]\\.,;:\s@"]+)*)` and the domain part `(([a-zA-Z\-0-9]+\.)+[a-zA-Z]{2,})` contain a quantified group nested inside another quantifier (`(...+)*` and `(...+)+`). This is the exact backtracking pattern flagged in the flask-restx advisory: when the overall match ultimately fails (e.g., no valid TLD or malformed trailing character), the regex engine tries an exponential number of ways to partition the repeated segments before giving up, causing the single-threaded Node.js event loop to hang.

This helper is invoked from `parseUri()` when classifying a URI's "address" component: [2](#0-1) 

`parseUri` is the wallet-side entry point for `byteball:`/`obyte:` deep links, which are commonly populated from data received from an untrusted counterparty (e.g. pasted/scanned payment links, or links embedded in chat/device messages processed by the wallet). An attacker who can get a victim's wallet to parse such a URI (e.g. a paired device or chat correspondent sending a "payment request" link) controls the `address` string that reaches `isValidEmail`.

### Impact Explanation
Triggering the exponential backtracking blocks the Node.js event loop of the process running the wallet/node. Since ocore/wallet processes are single-threaded, this stalls all concurrent operations in that process — including unit validation, network message handling, and UI responsiveness — for as long as the regex engine is stuck (which grows exponentially with crafted input length, easily reaching an unresponsive state with a modestly sized string). This matches the "node unable to process/confirm new units" impact class for the affected process.

### Likelihood Explanation
The vulnerable code path is reached purely through string parsing with no privileged capability required — any correspondent able to send the victim a `byteball:`/`obyte:` link (as text, via chat, QR code content, or clipboard) can trigger it. No cryptographic material or special permission is needed, only convincing a wallet to call `parseUri` on attacker-supplied text, which is a normal wallet operation (e.g., processing pasted/scanned payment requests).

### Recommendation
Replace the vulnerable email regex with a non-backtracking validator (e.g. use an atomic/possessive-quantifier-safe pattern, or an actual RFC 5322-lite validator implemented without nested quantifiers), or bound the input length before matching and use a safe regex library (e.g. `re2`) for `isValidEmail`. Additionally, enforce a reasonable maximum length on the `address` string in `parseUri` before applying any regex checks.

### Proof of Concept
```js
const ValidationUtils = require('./validation_utils.js');
const evil = "a@" + "a.".repeat(40000) + "!"; // fails to match; forces backtracking
console.time('redos');
ValidationUtils.isValidEmail(evil);
console.timeEnd('redos'); // grows exponentially with the repeat count, effectively hangs the process
```
Feeding a URI such as `byteball:` + `evil` into `parseUri()` (uri.js line 159) reproduces the same hang through the wallet's normal URI-parsing path.
