### Title
Arbitrary route contracts can inject unauthorized wallet transfers into a signed strategy - (File: `contracts/controller/src/strategies/swap.rs`)

### Summary
A caller-supplied strategy can name an arbitrary contract as a swap pool, and that contract is invoked during `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, or `multiply`. Malicious pool code can then request a token transfer from the caller to an attacker; Soroban records that transfer as a child of the caller’s strategy authorization, so signing the simulated tree authorizes theft of unrelated wallet tokens. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`swap_collateral(caller, account_id, current, amount, new, swap)` accepts the serialized `swap` route and forwards it after only owner-or-delegate authorization and market checks. [4](#0-3) [5](#0-4) 

`swap_tokens` authorizes only the controller-to-router input transfer, but it passes the caller-controlled route to `execute_strategy`; the route’s asset registry supplies the pool address for each hop. [1](#0-0) [6](#0-5) 

The route decoder validates indices, opcode values, token chaining, and split weights, but it does not constrain a hop’s `pool` address to a deployed or allowlisted venue contract. [7](#0-6) 

The venue dispatcher then invokes the supplied pool address, while balance-delta checks constrain only the router’s input spend and output receipt. [8](#0-7) 

The repository’s dedicated authorization test shows a rogue hop pool calling `token.transfer(victim, attacker, amount)` from inside `swap`, and shows the transfer becoming a child of the caller’s `swap_collateral` authorization and executing when that tree is signed. [9](#0-8) [10](#0-9) [11](#0-10) 

### Impact Explanation
An attacker can steal arbitrary balances from a user who submits or authorizes a malicious route, including assets unrelated to the supplied collateral or debt markets. [12](#0-11) [13](#0-12) 

The loss is not bounded by `amount`, minimum output, or the account’s final health because those checks measure only the strategy tokens and position state. [14](#0-13) [15](#0-14) 

This is theft of user funds and can be critical when the victim holds substantial token balances. [16](#0-15) [17](#0-16) 

### Likelihood Explanation
The attacker only needs to deploy a contract that implements the called pool functions and deliver a route whose asset registry points a hop at that contract. [18](#0-17) [19](#0-18) 

Execution requires the victim to sign the authorization tree containing the malicious child transfer, such as after receiving a poisoned route from a quoting interface or router provider. [20](#0-19) [15](#0-14) 

Because simulation records the injected transfer under the user-facing strategy call, wallet interfaces that display only the root call or expected input transfer can make the authorization appear consistent with the requested strategy. [21](#0-20) 

### Recommendation
Do not allow arbitrary route-selected contracts to execute below a user authorization. Maintain an on-chain allowlist of venue pool factories or exact pool contracts, validate each decoded pool address before `execute_strategy`, and ensure user-facing strategy authorization cannot be extended by untrusted route code. [6](#0-5) [22](#0-21) 

If arbitrary pools remain supported, require an explicit per-hop venue approval registry and reject routes containing unapproved `assets[idx_a]` pool addresses before any external invocation. [7](#0-6) 

Clients should additionally simulate every strategy transaction and reject any authorization tree containing children beyond the expected token transfers; this mitigates signing risk but does not replace contract-level venue validation. [15](#0-14) 

### Proof of Concept
1. Deploy a malicious pool that implements the venue’s `get_reserves` and `swap` interface; preload it with the strategy output token.
2. In `swap`, transfer the injected wallet asset with `token::Client::transfer(victim, attacker, victim_balance)`, then pay a positive output amount to the router so the measured-output checks pass. [9](#0-8) 
3. Give the victim a valid `StrategyPayload` whose `assets` registry contains the malicious pool as a hop’s `idx_a` address and whose opcode selects a swap venue. [23](#0-22) [6](#0-5) 
4. Have the victim invoke `swap_collateral(victim, account_id, usdc_asset, amount, eth_asset, swap)` or another route-taking strategy and sign the authorization tree returned by simulation. [4](#0-3) 
5. Simulation records the malicious wallet-token transfer as a child of the caller’s `swap_collateral` authorization, and the signed tree executes it while the strategy still supplies the expected output to the position. [3](#0-2) 
6. The harness demonstrates the concrete result: the victim’s unrelated wallet balance moves to the attacker while the new collateral receives the expected output. [13](#0-12) [17](#0-16)

    /// Validates every instruction's opcode, mode, and indices before execution begins,
    /// including the `Prev` chain, same-token swaps, and split-weight bounds.
    fn validate(&self, env: &Env, assets_len: u32, amounts_len: u32, weight_count: u32) {
        for i in 0..self.op_count {
            let record = self.raw(i);
            let Some(opcode) = Opcode::from_u8(record[field::OPCODE]) else {
                panic_with_error!(env, Error::InvalidRouteXdr);
            };
            let mode = Mode::from_u8(record[field::MODE]);
            let (idx_a, idx_b, idx_c) = (
                record[field::POOL] as u32,
                record[field::TOKEN_IN] as u32,
                record[field::TOKEN_OUT] as u32,
            );

            // `Prev` is a purely structural link: the predecessor must exist,
            // must have a single output, and that output must be this
            // instruction's input.
            if mode == Mode::Prev {
                if i == 0 {
                    panic_with_error!(env, Error::BrokenTokenChain);
                }
                let previous = self.raw(i - 1);
                let produced = match Opcode::from_u8(previous[field::OPCODE]) {
                    // A swap produces its `token_out`, a mint its share token.
                    Some(Opcode::Swap(_)) => previous[field::TOKEN_OUT],
                    Some(Opcode::Mint) => previous[field::TOKEN_IN],
                    // A burn releases every constituent at once.
                    _ => panic_with_error!(env, Error::BrokenTokenChain),
                };
                if idx_b != produced as u32 {
                    panic_with_error!(env, Error::BrokenTokenChain);
                }
            }
            match mode {
                Mode::Fixed(idx) if idx as u32 >= amounts_len => {
                    panic_with_error!(env, Error::InvalidRouteXdr)
                }
                Mode::Ppm(idx) if idx as u32 >= weight_count => {
                    panic_with_error!(env, Error::InvalidRouteXdr)
                }
                _ => {}
            }

            if idx_a >= assets_len || idx_b >= assets_len {
                panic_with_error!(env, Error::InvalidRouteXdr);
            }
            match opcode {
                Opcode::Swap(_) => {
                    if idx_c >= assets_len {
                        panic_with_error!(env, Error::InvalidRouteXdr);
                    }
                    if idx_b == idx_c {
                        panic_with_error!(env, Error::SameToken);
                    }
                }
                // Liquidity legs spend the full vault balance, so only `Mode::All` is valid.
                Opcode::Burn | Opcode::Mint => {
                    if mode != Mode::All {
                        panic_with_error!(env, Error::InvalidRouteXdr);
                    }
                    if idx_c >= amounts_len {
                        panic_with_error!(env, Error::InvalidRouteXdr);
                    }
                }
            }
        }

That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
