### Title
Webhook organization used for signature verification differs from the repository the payload's handler acts on, allowing an unauthorized action against an unrelated stack - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to verify the request's HMAC signature with, based on `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). [1](#0-0) [2](#0-1) 

However, the event handlers that actually act on the payload resolve the target `Repository`/`Stack` using a **different** field of the same JSON body: `payload.dig('repository', 'full_name')`. [3](#0-2) 

Because the entire raw POST body is what GitHub's HMAC signature covers, and Shipit is multi-tenant (multiple organizations each configured with their own `webhook_secret` in `Shipit.github`), an attacker who legitimately administers **any one** onboarded GitHub organization (and therefore legitimately knows that organization's own `webhook_secret`, which they configured themselves) can craft a JSON body where `repository.owner.login` names their own org (so the signature is checked against a secret they know) while `repository.full_name` names an entirely different, victim organization/repository tracked by the same Shipit instance.

### Finding Description
The binding that should hold is:
`organization authenticated by verify_signature (repository.owner.login / organization.login)` == `repository the handler writes to (repository.full_name)`

This binding is never enforced anywhere in the code:
- `verify_signature` fetches `Shipit.github(organization: repository_owner)` and validates the signature purely to prove "this body was sent by someone who knows organization X's webhook secret" — it says nothing about which repository inside the body is legitimate to act on. [4](#0-3) 
- After that check passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` hands the **entire attacker-controlled** `params` hash to the handler. [5](#0-4) 
- `Handler#stacks` / `Handler#repository_name` then resolves the `Repository` (and its `Stack`s) using `payload.dig('repository', 'full_name')` — a field that was never cross-checked against the field used to pick the verifying secret. [3](#0-2) 
- `PushHandler#process` then calls `stack.sync_github(expected_head_sha: params.after)` for every non-archived stack of that resolved repository whose branch matches, letting the attacker pick an arbitrary `ref`/`after` sha to force-sync a victim stack's tracked branch head. [6](#0-5) 
- `StatusHandler#process` is even less scoped: it looks up `Commit.where(sha: params.sha)` with **no repository/organization filter at all**, so a validly-signed webhook (signed with any onboarded org's own secret) can inject a fabricated commit status onto a commit belonging to any other stack in the whole Shipit installation. [7](#0-6) 

This is the direct analog of the reported bug class: just as the Solidity report flagged sensitive state changes (`take`) happening without the expected safeguard (event emission) so downstream observers couldn't verify what happened, here a sensitive state change (writing to a `Stack`/`Commit` belonging to organization B) is authorized based on a check that was actually performed against organization A's credential — the two are never bound together.

### Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" trust boundary explicitly called out as in-scope. Concretely:
- Via `PushHandler`, an attacker who controls one onboarded organization's legitimate GitHub App/webhook secret can force `stack.sync_github` to run for a victim organization's stack with an attacker-chosen `after` sha, which can advance the tracked branch/commit state used to gate deploys — this maps to the "unauthorized deploy" impact category.
- Via `StatusHandler`, the attacker can write arbitrary CI status entries (`state`, `context`, `target_url`, `description`) onto any commit in any stack across the whole installation, without any relation to the organization whose secret validated the request. Since commit statuses are commonly used to gate/allow deploys and merges (`Status::Group`, `Commit#create_status_from_github!`), this can be leveraged to make an otherwise-blocked commit appear "green"/deployable in a victim stack, again mapping to "unauthorized deploy" territory.

This requires the attacker to be a legitimate administrator of at least one organization already onboarded to the same multi-tenant Shipit installation — no `ApiClient` token, session, or GitHub write access to the victim repository is needed.

### Likelihood Explanation
Exploitability depends on Shipit being deployed multi-tenant (multiple `Shipit.github` orgs configured, as shown in `config/secrets.development.shopify.yml`), which is a documented, supported configuration, not a misconfiguration. Any org onboarded this way inherently knows its own webhook secret (it's the org's own credential), so no secret theft is required — only crafting a webhook body whose `repository.owner.login`/`organization.login` and `repository.full_name` refer to different repositories.

### Recommendation
Enforce the trust binding explicitly: after selecting `repository_owner` for signature verification, validate that `payload.dig('repository', 'full_name')` (and any `organization.login` used by handlers such as `MembershipHandler`) is actually owned by the same organization/owner that was used to verify the signature, before dispatching to handlers. Reject (422) any webhook where these fields disagree. Additionally, scope `StatusHandler`'s `Commit.where(sha: params.sha)` lookup to commits belonging to stacks of the verified repository/organization rather than searching all stacks globally.

### Proof of Concept
1. Shipit instance configured multi-tenant with (at least) `Shipit.github(organization: 'attacker-org')` and `Shipit.github(organization: 'victim-org')`, each with distinct `webhook_secret`s — the attacker legitimately administers `attacker-org` and therefore knows its `webhook_secret`.
2. Attacker crafts a `status` (or `push`) event JSON body:
   ```json
   {
     "sha": "<victim commit sha tracked by victim-org/some-repo>",
     "state": "success",
     "context": "ci/tests",
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/some-repo" }
   }
   ```
3. Attacker computes `X-Hub-Signature` using `attacker-org`'s own `webhook_secret` over the exact raw body, and sends it to `POST /github/webhooks` with `X-Github-Event: status`.
4. `verify_signature` computes `repository_owner = "attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and the HMAC check passes because the attacker legitimately knows that secret. [1](#0-0) 
5. `StatusHandler#process` then executes `Commit.where(sha: params.sha)` — matching the victim commit in `victim-org/some-repo` — and calls `create_status_from_github!`, injecting a fabricated "success" status on a commit the attacker never had access to. [7](#0-6) 

Note: I was not able to fully trace, within the available iterations, the exact downstream code path that consumes commit statuses to gate an actual `Deploy`/merge action (e.g., `Status::Group`, `Commit#create_status_from_github!`), so the "unauthorized deploy" consequence of the status-injection path is inferred from the naming/purpose of these models rather than a fully traced call chain; a Devin session with broader read access would be needed to confirm the exact deploy-gating logic that consumes these injected statuses.
