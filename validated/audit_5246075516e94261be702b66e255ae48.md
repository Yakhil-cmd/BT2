### Title
Stale/discarded Address Lookup Table resolution in `Bank::resanitize_transaction_minimally` allows a transaction to execute against ALT addresses that no longer match the current bank state - ([File: runtime/src/bank.rs])

### Summary
`Bank::resanitize_transaction_minimally` is the analog of Jetty's missing HTTP/2/HTTP/3 authority/Host consistency check: it has two representations of the "loaded ALT addresses" identity for a transaction — the addresses cached on the transaction from its original resolution, and the addresses that a fresh resolution against the *current* bank state would produce — and it never compares them. Just like Jetty accepted requests that carried two silently-diverging host values, this function accepts (and lets `Bank` continue processing) transactions whose cached loaded addresses can silently diverge from what the current on-chain `AddressLookupTable` state would resolve to.

### Finding Description
`RuntimeTransaction`/`ResolvedTransactionView` caches resolved ALT addresses once, at initial sanitization time (`runtime-transaction/src/runtime_transaction/transaction_view.rs`, `core/src/banking_stage/transaction_scheduler/receive_and_buffer.rs:439-454`, `translate_to_runtime_view`). When a buffered transaction is revalidated later (near/at its `alt_invalidation_slot`), `Bank::resanitize_transaction_minimally` is invoked: [1](#0-0) 

The comment explicitly documents the intended semantics: *"If the addresses still resolve here, then the transaction is still valid... If they do not, then the ATL has expired and the transaction can be dropped."* The function calls `load_addresses_from_ref` — which performs a full, fresh resolution against the *current* bank's ALT accounts (`runtime/src/bank/address_lookup_table.rs:41-68`) — but binds the result to `_addresses`/`_deactivation_slot`, i.e., it is computed and then thrown away: [2](#0-1) 

The check only asks "does resolution still succeed" (`AddressLoaderError` propagated via `?`), not "does resolution still produce the *same* addresses that are already cached on `transaction`". The transaction is then handed to `prepare_sanitized_batch`/execution still carrying its **original** cached `account_keys()`/loaded addresses (`transaction.account_keys()` as used throughout `RuntimeTransaction`, e.g. `runtime-transaction/src/runtime_transaction/transaction_view.rs:204-266`), not the freshly-resolved ones.

Because an Address Lookup Table account is a PDA derived from `(authority, recent_slot)`, its authority can deactivate it, wait out the deactivation window, close it, and recreate a lookup table at the *same address* with a *different* address list (reusing a `recent_slot` value that is still present in `SlotHashes`). A transaction referencing that table by index, sanitized/cached before the swap and only "minimally" resanitized after the swap, will pass `resanitize_transaction_minimally` (because the new table still resolves those indices without error) while still executing with the stale, pre-swap addresses cached in its `RuntimeTransaction`. This is exactly the Jetty pattern: one code path (`load_addresses_from_ref` at fresh-resolution time) computes a correct, current identity, while another path (whatever originally cached the transaction, e.g. banking-stage buffering) continues to be trusted downstream, and the two are never cross-checked for equality — only the "success/failure" property of the fresh path is checked.

### Impact Explanation
If different validators (or the same validator across different scheduling paths — full resanitize versus this "minimal" resanitize) end up using different loaded-address sets for the *same* wire transaction depending on exactly when they resolved it relative to an ALT close/recreate cycle, the executed instruction's account set (and therefore the resulting account states, lamport movements, and transaction result) can diverge between validators processing the same slot. This is a state-transition/consensus-determinism risk category (bank commit determinism / account loading conservation), since Solana's safety model requires that the loaded account set for a given transaction message be a pure, reproducible function of the bank state at the slot of inclusion — this code path breaks that invariant by allowing a stale cached resolution to survive a "resolves-but-was-discarded" recheck.

### Likelihood Explanation
Exploitation requires: (1) an attacker who fully controls an ALT they authored, (2) careful timing of deactivate → wait deactivation window → close → recreate at the same PDA with different content, and (3) getting a victim transaction referencing that table buffered by banking stage long enough to cross the `alt_invalidation_slot` boundary that triggers this "minimal" resanitize path rather than a full resolution. All of these are things an unprivileged transaction sender (as ALT owner) can arrange on their own without needing a malicious leader/validator/network position, but the timing window is narrow and depends on internal scheduler buffering behavior, so likelihood is moderate rather than high.

### Recommendation
In `Bank::resanitize_transaction_minimally` (`runtime/src/bank.rs:3794-3804`), do not discard the freshly resolved `LoadedAddresses`. Compare them against the transaction's currently cached loaded addresses (or refuse to reuse cached data at all and force a full re-sanitize/re-resolution) and return `TransactionError::SanitizeFailure` (or equivalent) if the fresh resolution differs from what is cached, mirroring how Jetty's fix is to explicitly compare `:authority` vs `Host` and reject on mismatch rather than silently keeping two diverging values alive.

### Proof of Concept
Note: I was not able to fully trace the exact call site in `core/src/banking_stage/consumer.rs` that invokes `resanitize_transaction_minimally` within the remaining investigation time (grep only returned a match count, not the surrounding logic), so the precise scheduling window (how long a transaction can sit buffered before this path triggers, and whether other checks upstream would already catch a stale cache) is not fully confirmed and should be verified directly in the source before treating this as a proven, end-to-end exploit. Conceptual PoC:
1. Create ALT `T` at PDA `P` derived from `(authority, recent_slot=S)` containing addresses `[A, B]`.
2. Submit transaction `tx` referencing `T` by index; it is sanitized/cached by a validator with `[A, B]` and given `alt_invalidation_slot` based on `T`'s (non-)deactivation.
3. While `tx` is buffered, deactivate `T`, wait out the deactivation window, close `T`, then recreate a lookup table at the same PDA `P` (same authority, same `recent_slot=S`, still present in `SlotHashes`) with addresses `[C, D]`.
4. Once the bank slot passes `tx`'s `alt_invalidation_slot`, `resanitize_transaction_minimally` re-resolves indices against `T` (now `[C, D]`), succeeds (no `AddressLoaderError`), discards the result, and returns `Ok(())`.
5. `tx` is executed still carrying its originally cached `[A, B]` addresses, which no longer correspond to any current, freshly-resolvable state of `T` — demonstrating the same "two diverging identity views, only one checked" bug class as the Jetty advisory.

impl Bank {
    /// Load addresses from an iterator of `SVMMessageAddressTableLookup`,
    /// additionally returning the minimum deactivation slot across all referenced ALTs
    pub fn load_addresses_from_ref<'a>(
        &self,
        address_table_lookups: impl Iterator<Item = SVMMessageAddressTableLookup<'a>>,
    ) -> Result<(LoadedAddresses, Slot), AddressLoaderError> {
        let slot_hashes = self
            .transaction_processor
            .sysvar_cache()
            .get_slot_hashes()
            .map_err(|_| AddressLoaderError::SlotHashesSysvarNotFound)?;

        let mut deactivation_slot = u64::MAX;
        let mut loaded_addresses = LoadedAddresses::default();
        for address_table_lookup in address_table_lookups {
            deactivation_slot = deactivation_slot.min(
                self.rc
                    .accounts
                    .load_lookup_table_addresses_into(
                        &self.ancestors,
                        address_table_lookup,
                        &slot_hashes,
                        &mut loaded_addresses,
                    )
                    .map_err(into_address_loader_error)?,
            );
        }

        Ok((loaded_addresses, deactivation_slot))
    }
