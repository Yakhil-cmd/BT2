### Title
AA payments to multiple recipients of an attested/conditioned asset are merged into one payment message, so a single non‑compliant recipient can block and revert payouts owed to all other, legitimate recipients - (File: `aa_composer.js`, `validation.js`)

### Summary
When an Autonomous Agent (AA) sends a payment response with several `payment` messages that use the same asset (e.g. one output refunding the trigger author and another output paying a counterparty), the AA composer silently merges them into a single `payment` message with combined outputs. If that asset has `spender_attested` or a `transfer_condition`, the network validates the condition once for the *whole* set of output addresses in the message. If any single output address fails the check (e.g., it was removed from the attestor list, or fails a custom `transfer_condition`), the entire unit is rejected, the AA bounces, and **all** state changes for that trigger — including the entitlement bookkeeping for the unaffected party — are rolled back. This mirrors the Nouns `Stream.sol` root cause: one party's inability to receive funds blocks funds legitimately owed to another party in the same atomic operation.

This merge is applied automatically whenever the mci is past `pemCurvesFixMci`, regardless of the AA author's intent to keep the payouts logically independent: [2](#0-1) 

The resulting combined message is validated as a single unit. For any asset with `spender_attested` or a `transfer_condition`, the check is evaluated against the *entire* set of output addresses of that message, not per-output: [3](#0-2) 

`filterAttestedAddresses` requires that every address in `arrOutputAddresses` be attested; if even one address fails, the whole payment (and therefore the whole unit) is rejected with `"some output addresses are not attested"` or `"transfer or issue condition not satisfied"`.

Back in `aa_composer.js`, if unit validation/save fails, the AA calls `bounce()`, and if this happens after state vars were already modified, `revert()` rolls back **all** balance and state-variable changes for the trigger to the initial savepoint: [4](#0-3) 

`bounce()` only returns whatever was received in the triggering unit back to `trigger.address`; it does not and cannot pay out the AA's own accumulated balance that was destined for the legitimate party, since that whole state update was rolled back: [5](#0-4) 

Consequently, an AA design that (a) uses a `spender_attested` or condition-restricted asset, and (b) in a single trigger response pays multiple addresses in that asset (e.g., a stream/vesting/escrow-style AA settling both the payer's leftover balance and the recipient's entitlement) is vulnerable: if the counterparty's address is removed from the attestor list (or otherwise fails the `transfer_condition`) — which can be done deliberately by whoever controls the attestor logic, or simply happen due to the attestor's independent decision — every subsequent attempt to run that payout logic bounces, and the funds owed to the *other*, compliant party are never released, because the entire operation (including the bookkeeping marking the payout as done) is reverted every time.

### Impact Explanation
This causes irrecoverable/indefinite freezing of AA balance funds legitimately owed to a compliant party, purely because of the compliance status of an unrelated address bundled into the same merged payment message. Since AA balances and state variables are the only place tracking entitlements, and `revert()` unconditionally rolls back the entire state change on any failure, there is no partial-success path — the funds remain stuck in the AA indefinitely as long as the non‑compliant address remains part of any payout attempt that also carries the merged asset outputs.

### Likelihood Explanation
Reaching this requires an AA design (writable by any unprivileged oscript author) that batches multiple addresses' payouts of the same attested/conditioned asset within one trigger's response — a common pattern for streaming/vesting/settlement AAs analogous to the Nouns `Stream` contract. The merge behavior in `mergeMessagesAndOutputs` is automatic and not opt-out, so the author does not even need to intentionally combine the outputs; the composer does it for them once mci passes `pemCurvesFixMci`. An adversarial designated recipient (or a party who controls the attestor/condition logic) can trigger the block deliberately, similar to a USDC address self-blacklisting in the original report.

### Recommendation
- Avoid merging payment outputs across different logical payout intents for assets that carry `spender_attested` or `transfer_condition`, or expose an option for AA authors to opt out of `mergeMessagesAndOutputs` per message/asset.
- For AAs handling entitlements to multiple parties, encourage/require separate payout units per recipient (pull-based withdrawal) instead of bundling several recipients into a single payment message, so that one recipient's condition failure cannot block or roll back an unrelated recipient's payout.
- Consider surfacing which specific output address failed the attestation/condition check so oscript logic could, in principle, retry payouts excluding the failing address rather than reverting the whole state update.

### Proof of Concept
1. Asset `X` is created with `spender_attested: true` and an attestor list maintained by an oracle AA/attestor.
2. An AA implements a "stream"-like payout that, in a single trigger response, sends `payment` messages in asset `X`: one output refunding the payer/trigger-address and one output paying the recipient's accrued amount, both referencing the trigger's asset `X` — these get merged by `mergeMessagesAndOutputs` (`aa_composer.js:1010-1041`, invoked at `aa_composer.js:1287-1288`) into a single `payment` message with two outputs.
3. The recipient's address is removed from asset `X`'s attestor list (or otherwise made to fail its `transfer_condition`).
4. Any subsequent trigger that attempts to run the settlement logic causes `completePaymentPayload`/unit validation to fail at `validation.js:2634-2638` ("some output addresses are not attested"), the AA calls `bounce()` (`aa_composer.js:910-945`), and if state vars were already touched, `revert()` (`aa_composer.js:1759-1783`) rolls back all balance/state changes.
5. The payer's portion of the payout, which would have succeeded independently, is never sent and the entitlement bookkeeping is never updated — the funds remain stuck in the AA's balance as long as the recipient's address stays non-compliant.

	function mergeMessagesAndOutputs(messages) {
		const arrMergedMessages = [];
		const assocMergedMessagesByAsset = Object.create(null);
		for (let message of messages) {
			if (message.app !== 'payment') {
				arrMergedMessages.push(message);
				continue;
			}
			const payload = message.payload;
			const asset = payload.asset || 'base';
			let objMergedMessage = assocMergedMessagesByAsset[asset];
			if (!objMergedMessage) {
				objMergedMessage = { app: 'payment', payload: { outputs: [] } };
				if (payload.asset)
					objMergedMessage.payload.asset = payload.asset;
				assocMergedMessagesByAsset[asset] = objMergedMessage;
				arrMergedMessages.push(objMergedMessage);
			}
			for (let output of payload.outputs) {
				if (output.amount === undefined) { // send-all output, don't merge with anything
					objMergedMessage.payload.outputs.push(output);
					continue;
				}
				const existing_output = objMergedMessage.payload.outputs.find(o => o.address === output.address && o.amount !== undefined);
				if (existing_output)
					existing_output.amount += output.amount;
				else
					objMergedMessage.payload.outputs.push(output);
			}
		}
		return arrMergedMessages;
	}
