Rails >= 8.1.1 is required here, and since Rails 5 the `before_action` callback chain is only halted by `throw(:abort)` — calling `head`/`render` inside a callback no longer implicitly stops the chain (`config.action_controller.halt_callback_chains_on_return_false` era is long gone; Rails 5+ callbacks require an explicit halt). `Shipit::WebhooksController#verify_signature` calls `head(422) unless verified` but never returns/halts, so the callback chain (and then `create`) keeps executing even when the signature check fails.

### Title
Unauthenticated GitHub webhook processing due to non-halting signature-verification callback - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` is registered as a `before_action` that is supposed to gate `create` on a valid `X-Hub-Signature` HMAC. On failure it calls `head(422)` but does not `throw(:abort)`/`return`, so under Rails' modern callback semantics the chain is not halted and `create` still runs the event handlers with attacker-controlled JSON.

### Finding Description
`before_action :check_if_ping, :drop_unhandled_event, :verify_signature` runs before `create` [1](#0-0) . `verify_signature` computes `verified` from `github_app.verify_webhook_signature` and, if it is false, only calls `head(422)`, with no `throw(:abort)` and no `return` [2](#0-1) . `create` then unconditionally parses `request.raw_post` and dispatches to every handler registered for the event: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` before calling `head(:ok)` [3](#0-2) . Because Rails callback chains since Rails 5 only halt on `throw(:abort)`, and this gem now requires Rails `>= 8.1.1` [4](#0-3) , the earlier implicit-halt-on-render behavior no longer applies, so the handler side effects (e.g. enqueuing `GithubSyncJob`, creating `Status`, creating `Team`/`Membership`/`User` records as exercised in `test/controllers/webhooks_controller_test.rb`) execute even though the signature check failed and a 422 was queued. This breaks the trust binding: "GitHub organization whose webhook secret authenticated the request" versus "the handler mutations actually performed on the repository/stack state," analogous to the Astaria bug where a caller could act on the vault (`ERC4626Cloned`) bypassing the intended gate (`afterDeposit`) that was supposed to restrict who could mutate state.

### Impact Explanation
An unauthenticated attacker who can reach the public `/webhooks` endpoint (no GitHub App private key, no `ApiClient` token, and no session required — the whole point of this endpoint is to accept unauthenticated internet traffic gated only by the HMAC signature) can submit a forged payload for any handled event (`push`, `status`, `membership`, `check_suite`, etc.) and have Shipit execute the corresponding side effects: queuing sync/build-status jobs, creating or deleting `Membership`/`Team`/`User` records, or updating commit `Status`. This is an authentication bypass of the mechanism that is supposed to be the sole gate protecting the webhook ingestion path, and depending on the handler it can lead to unauthorized state changes (e.g., forged CI/check-run status manipulation feeding into deploy safety checks, or forged membership changes affecting `Shipit.github_teams` authorization used elsewhere in the app).

### Likelihood Explanation
High if the described callback semantics hold on the Rails version this gem is pinned to (`>= 8.1.1`) — no privileged token, session, or repository access is required; the attacker only needs network access to the public webhook route registered in `config/routes.rb`, and can omit/forge the `X-Hub-Signature` header entirely. I was not able to execute the code in this environment to confirm at runtime whether some other Rails default (e.g. `raise_on_missing_callback_actions` or an engine-level `ActionController::Base` default not visible in the indexed files) forces a halt; this should be confirmed by writing a request spec that sends an intentionally-invalid `X-Hub-Signature` and asserting that the handler's side effect (e.g., `GithubSyncJob` enqueued) did NOT occur, in addition to asserting the 422 response.

### Recommendation
In `app/controllers/shipit/webhooks_controller.rb`, make `verify_signature` explicitly halt the callback chain on failure, e.g. `head(422) and throw(:abort) unless verified` (or restructure to `render(...)` and `return` before any handler dispatch), and add a regression test asserting that webhook handlers are never invoked when the signature check fails.

### Proof of Concept
1. POST to the mounted webhook endpoint (e.g. `/webhooks`) with header `X-Github-Event: push`, an intentionally invalid/absent `X-Hub-Signature`, and a JSON body shaped like the `push` fixture used in `test/controllers/webhooks_controller_test.rb` (`payload(:push_master)`), targeting an existing stack's branch.
2. Because `verify_signature` only calls `head(422)` without halting [2](#0-1) , the `create` action still runs `Shipit::Webhooks.for_event('push').each { |handler| handler.call(params) }` [3](#0-2) , enqueuing `GithubSyncJob` for the target stack exactly as in the legitimate, signature-verified test case at `test/controllers/webhooks_controller_test.rb` lines 23-32 [5](#0-4) .
3. Confirm the response is a 422 (from the queued `head(422)`) or a `DoubleRenderError`, while `assert_enqueued_with(job: GithubSyncJob, ...)` still passes — demonstrating the mutation occurred despite failed authentication.
