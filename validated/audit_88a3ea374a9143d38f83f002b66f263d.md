### Title
PR label named `PATH` overrides Shipit's constructed `PATH` env var, enabling RCE via bare command hijacking - ([File: lib/shipit/command.rb])

### Summary
`ReviewStack#env` merges every pull-request label into the environment hash as `LABEL.upcase => "true"`, with no key blocklist. `Command#unbundled_env` builds the authoritative `PATH` from `Shipit.shell_paths` and `ENV['PATH']`, but then merges the task-supplied `@env` on top, so a label literally named `path`/`PATH` overwrites it with the string `"true"`. Since `PTY.spawn` is chdir'd into the attacker's checked-out branch, a relative `PATH=true` causes any bare command name in that task's steps (e.g. `git`) to resolve against a directory named `true` in the attacker's own checkout.

### Finding Description
Broken binding: `Command#unbundled_env['PATH']` should always equal `Shipit.shell_paths.join(':') + ':' + ENV['PATH']`, but instead:
```ruby
# lib/shipit/command.rb:103-105
def unbundled_env
  BASE_ENV.merge('PATH' => "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}").merge(@env.stringify_keys)
end
``` [1](#0-0) 
the final `.merge(@env.stringify_keys)` lets any key in `@env` — including `PATH` — clobber the carefully constructed value.

`@env` is populated from `TaskCommands#env`, which merges in `@stack.env`:
```ruby
# lib/shipit/task_commands.rb:33-48
def env
  super.merge(@stack.env).merge(...).merge(deploy_spec.machine_env).merge(@task.env)
end
``` [2](#0-1) 

`ReviewStack#env` (used when `@stack` is a review stack) folds every GitHub PR label into this hash with no filtering of the key name:
```ruby
# app/models/shipit/review_stack.rb:84-93
def env
  return super unless pull_request.present?

  super.merge(
    pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" }
  )
end
``` [3](#0-2) 

Exploit flow: attacker owns/controls a repository with Review Stacks enabled (`allow_all` or opts in via label). They open a PR from their own branch, add the label `path` (case-insensitive, becomes `PATH`), and commit a directory literally named `true` at the branch root containing an executable file named `git` (or any command used in the deploy steps, e.g. `bundle`, `npm`). When Shipit runs `TaskCommands#perform`/`clone`/`checkout` (`git(...)` helper) or the deploy steps, `Command.new(command_line, env:, chdir: steps_directory)` is constructed with the poisoned `env`, and `PTY.spawn(unbundled_env, ...)` executes with `PATH=true` while `chdir` points into the attacker's own checkout — `execvp`'s bare-name resolution finds the attacker's `true/git` binary instead of the real `git`. This lets the attacker's code run on the shared Shipit deploy host with whatever privileges the task runner has (potentially exposing `GITHUB_TOKEN`, other stacks' secrets, or writing to unrelated repos/stacks on the same host).

None of the existing guards stop this: `EnvironmentVariables#permit`/interpolation only governs variable *interpolation* in command arguments, not the raw env hash passed to `PTY.spawn`; there is no allowlist/blocklist on label names in `ReviewStack#env`; and `Command#unbundled_env`'s merge order structurally guarantees `@env` wins over the computed `PATH`.

### Impact Explanation
Critical — arbitrary code execution on the shared Shipit deploy host, achieved purely by controlling PR labels and repository content on a repo with Review Stacks enabled. Because the deploy host is shared across stacks/tenants, this can be used to exfiltrate `GITHUB_TOKEN`, other stacks' secrets, or interfere with concurrent tasks, matching the Critical RCE category.

### Likelihood Explanation
Requires the target repository to have Review Stacks enabled (an explicit opt-in by a repository/Shipit operator) and the attacker to be able to add a label to their own PR in that repository — both plausible for an attacker who owns the repository or is a collaborator able to label PRs. No Shipit secrets, sessions, or webhook signatures need to be forged; the attack goes through legitimate GitHub actions (push branch, open PR, add label) that Shipit's webhook processing already trusts for that repository. Cost is low and the attack is fully repeatable against any review-stack-enabled repository the attacker controls.

### Recommendation
In `ReviewStack#env`, reject/blocklist label names that collide with reserved/security-sensitive variables (at minimum `PATH`, `LD_PRELOAD`, `LD_LIBRARY_PATH`, `IFS`, `BASH_ENV`), or namespace label-derived variables (e.g. prefix with `LABEL_`) instead of writing them directly by upcased label name. Additionally, harden `Command#unbundled_env` to always force `PATH` to the Shipit-computed value regardless of `@env` (i.e., merge `@env` first, then overwrite `PATH` last), so no caller-supplied environment can ever override it.

### Proof of Concept
```ruby
# test/unit/command_test.rb (proof of the broken binding)
test "#unbundled_env allows @env to override the computed PATH" do
  Shipit.stubs(:shell_paths).returns(['/shipit/bin'])
  command = Shipit::Command.new('git status', env: { 'PATH' => 'true' }, chdir: Dir.mktmpdir)

  expected_path = "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}"
  refute_equal expected_path, command.unbundled_env['PATH']
  assert_equal 'true', command.unbundled_env['PATH']
end
```
```ruby
# test/models/shipit/review_stack_test.rb (proof of label -> PATH override)
test "a PR labeled 'path' overrides the stack env's PATH" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["path"]

  assert_equal "true", stack.env["PATH"]
end
```
Both assertions demonstrate that the last-applied source (`@env`, ultimately derived from an attacker-controlled PR label) — not `Shipit.shell_paths`/`ENV['PATH']` — determines the final `PATH` used by `PTY.spawn`, confirming the binding violation described in the question.
