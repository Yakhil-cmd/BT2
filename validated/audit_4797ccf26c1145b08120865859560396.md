### Title
Insecure Default File Permissions When Exporting Private Textcoin Payload - (File: wallet.js)

### Summary
`storePrivateAssetPayload()` in `wallet.js` persists a ZIP file to disk containing the plaintext mnemonic and the full private-payment chain (inputs/outputs/blinding factors) of a textcoin sent to an offline recipient. The file is written with Node's `fs.writeFile()` without specifying a `mode`, so it inherits Node's default file mode `0o666`, modified only by the process umask. On systems with a standard umask this leaves the file world-readable; in environments with a permissive umask (e.g., many container images) it is also world-writable.

### Finding Description
When a wallet sends a private, indivisible/divisible asset to a "textcoin" recipient (an address not directly reachable by device message, e.g. paying to a mnemonic-derived address), the private payment chain and the mnemonic used to redeem it are serialized into a ZIP archive and written to a caller-provided path via `storePrivateAssetPayload`: [1](#0-0) 
This is invoked from the `preCommitCb` of `sendMultiPayment` for private assets whenever a textcoin is being paid, i.e. as a normal, unprivileged sender action reachable by any wallet/asset-issuer flow that pays a private asset to an off-device recipient: [2](#0-1) 
Unlike other sensitive local state in the codebase — which is explicitly created with restrictive `0o700` directory modes (e.g. the RocksDB data directory and sqlite parent directories) — this file write path specifies no mode at all, so it silently falls back to Node's insecure default: [3](#0-2) [4](#0-3) 

The mnemonic + chain data stored in this file are effectively bearer credentials for the private asset amount: possession of the mnemonic and chain is sufficient to claim the textcoin (see `receiveTextCoin`/`handlePrivatePaymentFile`, which reconstruct and redeem the payment purely from the ZIP's `mnemonic`/`chains` fields).

### Impact Explanation
Because the exported ZIP is world-readable by default, any other unprivileged local user or process on the same host/container (a common deployment pattern for wallet backends, kiosks, or shared servers) can read the file before it is delivered to the intended recipient and redeem the private asset payment itself. This results in theft/unauthorized spending of the private-asset textcoin funds — the legitimate recipient can no longer claim the asset because the attacker with local read access races to redeem it first.

### Likelihood Explanation
Exploitation only requires unprivileged local file read access at the time the wallet exports a private textcoin payload — a routine operation for any wallet issuing private-asset textcoins to off-device recipients (e.g. paper wallets, USB export, gift codes). No special privileges, network position, or malicious peer/hub interaction are required, making this readily reachable by design for any host with multiple local users or a permissive umask.

### Recommendation
Explicitly set a restrictive mode (e.g. `0o600`) when creating the private-payload file in `storePrivateAssetPayload`, consistent with the `0o700` pattern already used for other sensitive local storage (`kvstore.js`, `sqlite_pool.js`), for example: `fs.writeFile(fullPath, zipFile, { mode: 0o600 }, cb)`.

### Proof of Concept
1. A wallet issues a private asset payment to a textcoin recipient (mnemonic-based address not on a paired device), triggering `sendMultiPayment` → `preCommitCb` → `storePrivateAssetPayload(fullPath, ...)`.
2. `storePrivateAssetPayload` calls `fs.writeFile(fullPath, zipFile, cb)` with no explicit mode, so the resulting file is created with mode `0o666 & ~umask`.
3. A second unprivileged local account on the same host (or container with a permissive umask) reads the file at `fullPath` before it is handed off to the intended recipient, extracts `mnemonic` and `chains` from the ZIP's `private_textcoin` entry, and calls `receiveTextCoin`/`handlePrivatePaymentFile` to redeem the asset itself, resulting in loss of funds for the intended recipient.
