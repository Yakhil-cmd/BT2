### Title
Webhook signature verification keys off an attacker-controlled `repository.owner.login` field, letting a valid webhook signer for one configured GitHub org forge events for a *different* org's repositories/stacks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `webhook_secret` to HMAC-verify the payload against by reading `repository.owner.login` (or `organization.login`) out of the **same unauthenticated JSON body** it is trying to authenticate, then hands the *entire* raw payload — including `repository.full_name` — to event handlers that resolve the target `Stack`/`Repository` from `repository.full_name`. Nothing binds "the org whose secret validated this signature" to "the repository the handler actually acts on."

### Finding Description
`verify_signature` computes `repository_owner` from attacker-supplied JSON and uses it purely to pick which per-org `webhook_secret` to check the signature against: [1](#0-0) 

`Shipit.github(organization: repository_owner)` looks up a distinct `GithubApp` config (with its own `webhook_secret`) per org, as configured in `config/secrets.*.yml` for multi-org installs: [2](#0-1) 

Signature check itself is a straightforward HMAC over the raw body with that org's secret: [3](#0-2) 

Once `verified` is true, the full, attacker-influenced `params` hash is dispatched unchanged to every handler for the event type: [4](#0-3) 

Handlers such as `PushHandler` derive the target stacks from `repository.full_name` in that same payload, not from `repository_owner`: [5](#0-4) [6](#0-5) 

`Repository.from_github_repo_name` splits `full_name` on `/` and looks the repo up purely by owner+name string, with no re-check against the org that supplied the verified signature: [7](#0-6) 

The equality that is supposed to hold is:
`org_whose_secret_signed(payload) == owner(payload.repository.full_name)`

But since both sides are read from the same untrusted body, an attacker who legitimately controls the webhook secret for `OrgA` (e.g. they administer a GitHub App/organization that has a Shipit webhook configured, a scenario the engine explicitly supports for multi-org setups) can:
1. Set `repository.owner.login` = `OrgA` (or `organization.login` = `OrgA`) so `verify_signature` selects and validates against `OrgA`'s secret, which the attacker knows and can sign with.
2. Set `repository.full_name` = `OrgB/some-repo` (an org they do **not** control) inside the same signed body.

The signature is valid (it's computed over the full raw body using `OrgA`'s secret, which the attacker legitimately possesses), so `verify_signature` passes, and the handler layer then acts on `OrgB/some-repo` because it reads `full_name`, not `repository_owner`.

### Impact Explanation
This breaks the org-authentication-to-repository-write binding described in scope: the org whose credential authenticated the webhook is not the org whose repository/stack the code subsequently operates on. Depending on which handler fires, this can be leveraged to:
- `PushHandler`: force `stack.sync_github(expected_head_sha: ...)` on an arbitrary victim stack belonging to a different, unrelated organization that the attacker has no legitimate relationship with, effectively triggering unauthorized sync/refresh actions on another org's deploy pipeline using only a secret the attacker holds for their own, unrelated org.
- `PullRequest::*Handler`s and `MembershipHandler`/`Team` handlers similarly resolve target objects from attacker-supplied payload fields once "verified," so team membership and review-stack provisioning logic keyed off cross-org repository/team data could likewise be manipulated.

This matches the "unauthenticated read of stack state" / "authorization escalation" bar for High severity, since it is effectively an authentication-bypass-by-confusion for the org boundary (an attacker with a secret for Org A obtains write/state-changing capability against Org B's stacks without ever being granted access to Org B).

### Likelihood Explanation
This requires the attacker to legitimately control the webhook secret for *some* configured org on the Shipit instance (i.e., they run their own GitHub App/org that is deliberately configured to send webhooks to this Shipit deployment — a normal, low-privilege scenario for any org onboarded onto a shared multi-org Shipit instance) but not the target org. This is a realistic scenario for shared/hosted Shipit deployments serving multiple organizations, which is exactly the multi-org config the engine ships support for (`config/secrets.*.yml` with multiple org blocks). No GitHub App private key, `api_clients_secret`, or session is required — only knowledge of one org's `webhook_secret`, which by design many parties (any org onboarded to the shared instance) legitimately hold.

### Recommendation
After signature verification, re-derive the repository owner strictly from `repository.full_name`/`repository.owner.login` used by the handlers, and reject the request (or re-verify against the *same* value) if the org used to select the `webhook_secret` does not match the owner of the repository the payload claims to act on. Concretely, `verify_signature` and `Handler#repository_name` must be forced to agree on a single canonical field, and the controller should confirm `repository_owner == payload.dig('repository','full_name').split('/').first` before dispatching to handlers, rejecting mismatches with 422.

### Proof of Concept
1. Configure Shipit with two orgs, `orga` and `orgb`, each with its own `webhook_secret` (as in `config/secrets.development.shopify.yml`).
2. As an attacker who administers `orga` (and thus legitimately knows `orga`'s `webhook_secret` because they configured/received it when onboarding their own org's webhook), craft a `push` event JSON body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen sha>",
     "repository": {
       "owner": { "login": "orga" },
       "full_name": "orgb/victim-repo"
     }
   }
   ```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(orga_webhook_secret, raw_body)>` and POST to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "orga")` (from `repository.owner.login`), verifies successfully with `orga`'s secret [8](#0-7) .
5. `PushHandler#stacks` resolves `Repository.from_github_repo_name("orgb/victim-repo")` [5](#0-4)  and calls `stack.sync_github(expected_head_sha: ...)` on `orgb`'s stack [6](#0-5) , an org the attacker never authenticated against.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
