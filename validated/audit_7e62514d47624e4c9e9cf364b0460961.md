### Title
Membership webhook forged via an org lacking a `webhook_secret` allows cross-tenant `Team` mutation, independent of `ignore_ci` - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which organization's secret to check against by reading `params.dig('organization','login')` from the attacker-supplied JSON body itself, and `GitHubApp#verify_webhook_signature` trivially returns `true` whenever that organization has no `webhook_secret` configured. Because `MembershipHandler` uses `params.team.id` (an arbitrary integer) to find-or-create a `Team`, and never checks that the `team.id` actually belongs to the `organization.login` that was used to authenticate, this only lets an attacker create/mutate `Team`/`Membership` rows scoped to `Team.github_id` — it does not touch any specific `Stack`, and `ignore_ci` on a stack has no bearing on this handler at all.

### Finding Description
The binding that should hold is: *the organization whose secret authenticated the request* == *the organization whose `Team`/membership data is mutated*. Trace:

- `verify_signature` computes `repository_owner` from the payload (`params.dig('organization','login')` for a `membership` event) and calls `Shipit.github(organization: repository_owner)` — i.e., the attacker's own JSON body picks which org's `GitHubApp`/secret is used. [1](#0-0) [2](#0-1) 
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when `webhook_secret` is blank for that org, and otherwise only accepts a `sha1=` prefixed signature (rejecting `sha256=`) before comparing an HMAC computed with that org's secret. [3](#0-2) 
- `MembershipHandler#process` derives `team` purely from `params.team.id` (an attacker-supplied integer) and `member` from `params.member.login`, then adds/removes the membership row based on `params.action`. Nothing ties `team.github_id`/`params.team.id` back to the `organization.login` that was used for signature verification. [4](#0-3) 

Exploit flow: the attacker picks any organization the Shipit instance knows about that has **no `webhook_secret` configured** (a legitimate, attacker-discoverable condition since many low-security orgs may be onboarded without a secret), sets `organization.login` to that org's name in the JSON body, and sends `POST /webhooks` with `X-Github-Event: membership` and any/garbage `X-Hub-Signature` header. `verify_signature` passes trivially. The body's `team.id` can then be set to any GitHub team id — including one already tracked as a `Team` record belonging to a *different*, secret-protected organization — with `action: "removed"` or `"added"`, mutating that `Team`'s `memberships` table entries.

Existing guards fail because: `verify_signature` is scoped by attacker-chosen `organization.login`, not by any value independently authenticated; `MembershipHandler`'s `ExplicitParameters` schema (`requires :team.id, Integer` etc.) only validates shape, not provenance; and there is no cross-check between the authenticating org and the team/org referenced in the payload.

However, the `ignore_ci`/`Commit#deployable?` part of the question's framing does not connect to this handler at all — `MembershipHandler` never touches `Stack`, `Commit`, or CI status; `Commit#deployable?` (`!locked? && (stack.ignore_ci? || (success? && !blocked?))`) is a separate, unrelated code path triggered only by push/status/check_run webhooks. [5](#0-4) 

### Impact Explanation
If the forged `team.id` corresponds to a `Team` whose `id` is listed in `Shipit.github_teams`, then adding a `User` (attacker-controlled `member.login`) to that team makes `User#authorized?` return true globally (`Shipit.github_teams.empty? || teams.where(id: Shipit.github_teams.map(&:id)).exists?`), [6](#0-5)  which is the "escalation into `Shipit.github_teams` authorization" category (High). This is a cross-tenant write: a request that only authenticated against org A's (secret-less) config is able to mutate `Team`/`Membership` state associated with org B's `github_id`. It does not, by itself, grant "Critical — unauthorized deploy" because `authorized?` alone does not create a Shipit session/login for the attacker; actual deploy/rollback still requires the attacker to separately obtain a Shipit session (OAuth) as that GitHub login. The `ignore_ci` and `Commit#deployable?` elements asserted in the question are not exercised by this handler and add no additional impact here.

### Likelihood Explanation
Requires (a) at least one organization configured in `Shipit.github(organization: ...)` without a `webhook_secret` (a real but instance-specific configuration state, not a universal default), and (b) the attacker being able to guess/know a target `team.id` (GitHub's numeric team id) for a team referenced by another org's `Shipit.github_teams` — knowable since team ids are visible via GitHub's API/UI to anyone with read access to the team, or via prior legitimate webhook traffic. No GitHub App private key, `webhook_secret`, or Shipit session is needed. This is repeatable per request and does not require live GitHub. The "legacy sha1 header" / sha256-rejection detail is not itself the bypass — an attacker who doesn't know a valid secret cannot forge a valid `sha1=` HMAC either; the actual bypass is exclusively the `return true unless webhook_secret` no-secret fallback combined with attacker-controlled `organization.login` selection.

### Recommendation
Do not let the request body select which organization's secret verifies it — resolve the org/config from a value not fully controlled in the same unauthenticated payload the signature is meant to protect (e.g. require secrets configured for every onboarded org and reject verification with no secret rather than treating it as `true`). Additionally, `MembershipHandler` should validate that the `team.id`/`organization.login` pairing is internally consistent, and ideally scope `Team` records to the authenticated organization rather than trusting `params.organization.login` verbatim.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (illustrative)
test "membership webhook forged against secret-less org mutates team from another org" do
  no_secret_org_config # Shipit.github(organization: 'attacker-org') with webhook_secret: nil
  victim_team = Shipit::Team.create!(github_id: 999, organization: 'victim-org')

  payload = {
    action: 'removed',
    team: { id: 999, name: 'x', slug: 'x', url: 'http://x' },
    organization: { login: 'attacker-org' }, # picks the no-secret config for verify_signature
    member: { login: 'victim-admin' }
  }.to_json

  post '/webhooks', params: payload, headers: {
    'X-Github-Event' => 'membership',
    'X-Hub-Signature' => 'sha1=deadbeef', # garbage, irrelevant because webhook_secret is nil
    'CONTENT_TYPE' => 'application/json'
  }

  assert_response :ok
  refute victim_team.members.exists?(login: 'victim-admin')
  # assert equality broken: authenticating org ('attacker-org') != mutated team's org ('victim-org')
end
```
This demonstrates the cross-tenant `Team` mutation gap. The `ignore_ci`/`Commit#deployable?` portion of the original question is not corroborated — no code path in `MembershipHandler` or the webhook verification flow interacts with `Stack#ignore_ci` or `Commit#deployable?`, so no test can bind those together with this handler.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'

          end
        end
```
