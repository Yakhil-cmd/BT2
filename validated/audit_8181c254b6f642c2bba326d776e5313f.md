## Finding: WebhooksController verifies signature against `repository.owner.login`, but handlers act on the independent `repository.full_name` field — no binding between the two

### Title
Webhook signature verification is bound to `repository.owner.login`, but event handlers act on an independent `repository.full_name` field, allowing cross-organization/cross-repository forged webhooks - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate the HMAC signature against using `repository_owner`, derived from `params.dig('repository', 'owner', 'login')`. But the actual event processing in `Shipit::Webhooks::Handlers::Handler#repository_name` independently reads `payload.dig('repository', 'full_name')` to find the target `Repository`/`Stack`. Nothing enforces that these two fields agree, so a signature valid for organization "A" can carry a payload whose `repository.full_name` points at a repository belonging to organization "B".

### Finding Description
In `app/controllers/shipit/webhooks_controller.rb`: [1](#0-0) 
selects the `github_app` (and therefore the `webhook_secret` used to verify `X-Hub-Signature`) via: [2](#0-1) 

Separately, every handler in `app/models/shipit/webhooks/handlers/handler.rb` resolves the target repository/stack via a *different* field of the same JSON body: [3](#0-2) 

For example `PushHandler` triggers `stack.sync_github` based on that repository lookup: [4](#0-3) 

and PR handlers archive/unarchive review stacks or cancel merge requests based on the same disconnected `repository.full_name`: [5](#0-4) 

The docs confirm that in multi-tenant deployments each organization has its own GitHub App and its own `webhook_secret`, configured independently per org: [6](#0-5) 

Because `repository_owner` (used to pick the secret) and `repository.full_name` (used to pick the target `Stack`/`Repository`) are read independently from the same untrusted JSON body and never cross-checked, a party who legitimately knows the `webhook_secret` for *one* configured organization (e.g., they set up their own GitHub App per the multi-org instructions) can craft a POST to the single shared `/webhooks` endpoint with `repository.owner.login` set to their own org (so signature verification passes with the secret they know) while setting `repository.full_name` to `victim-org/victim-repo` — a completely different, unrelated organization/repository also hosted on the same Shipit instance.

### Impact Explanation
This breaks the intended binding "organization that authenticated" == "repository that is written," which is explicitly one of the trust bindings this engine relies on for webhook security. An attacker controlling a known webhook secret for any one configured organization can:
- Force `PushHandler` to call `stack.sync_github(expected_head_sha:)` on a victim's stack, driving unauthorized sync/deploy triggering behavior for a repository they don't own.
- Force `PullRequest::ClosedHandler`/`ReopenedHandler` to archive/unarchive victim review stacks.
- Forge `status`/`check_suite` events for victim commits (`StatusHandler`, `CheckSuiteHandler`), which can affect CI-gated deploy/merge decisions on unrelated repositories.
- Cancel/merge victim merge requests through the merge queue's reaction to forged pull_request events.

This matches the "unauthorized deploy, rollback or merge" / cross-repository writes impact bar, since a webhook credential scoped to one org can act on a stack belonging to a completely different org.

### Likelihood Explanation
Requires the attacker to legitimately possess a `webhook_secret` for at least one organization configured in the same multi-tenant Shipit instance (achievable if they self-service-created their own GitHub App per the documented multi-org setup) and knowledge that a target stack exists on the same instance. This is a realistic scenario for any shared/multi-tenant Shipit deployment as explicitly documented in `docs/setup.md`.

### Recommendation
After successfully verifying the signature for a given `repository_owner`, validate that `payload.dig('repository', 'full_name')` (and any `organization.login` used by org-scoped handlers, e.g. `MembershipHandler`) belongs to that same verified organization before dispatching to handlers. Reject the request (422) if the two do not match.

### Proof of Concept
1. Configure Shipit with two organizations in `config/secrets.yml`, `OrgA` (attacker-controlled, secret known to attacker) and `OrgB` (victim, has a `Stack` tracking `OrgB/victim-repo`).
2. Attacker computes `X-Hub-Signature` using `OrgA`'s known `webhook_secret` over a crafted JSON body where:
   - `repository.owner.login = "OrgA"`
   - `repository.full_name = "OrgB/victim-repo"`
   - `ref = "refs/heads/<victim-branch>"`, `after = "<attacker-chosen-sha>"`
3. POST this body with header `X-Github-Event: push` and the computed signature to `/webhooks`.
4. `verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) selects `Shipit.github(organization: "OrgA")` and successfully verifies the signature (attacker knows this secret) — request passes.
5. `create` dispatches to `PushHandler`, which resolves `stacks` via `payload.dig('repository', 'full_name')` = `"OrgB/victim-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`), and calls `stack.sync_github(expected_head_sha: params.after)` on the victim's stack — an action never authorized by `OrgB`.
