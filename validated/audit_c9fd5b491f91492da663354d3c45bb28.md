### Title
Cross-repository Status poisoning via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits by SHA alone (`Commit.where(sha: params.sha)`), with no filter on the repository that sent the webhook, unlike the base `Handler` class's `stacks` helper which scopes by `Repository.from_github_repo_name(repository_name)`. A validly-signed status webhook from repository A can therefore write a `Status` row onto every stack in every repository (B, C, …) that happens to have a commit with the same SHA, even though `verify_signature` only proves the event came from repository A's organization.

### Finding Description
The binding that should hold is: **stacks_updated_by_event(payload) == stacks_of(Repository.from_github_repo_name(payload.repository.full_name))**, i.e., a webhook event for repository R should only mutate state belonging to stacks whose repository is R.

Trace:
1. `Shipit::WebhooksController#create` (app/controllers/shipit/webhooks_controller.rb:10-15) parses the payload and dispatches to handlers via `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. Before this, `verify_signature` (lines 24-49) validates the HMAC signature using `Shipit.github(organization: repository_owner)`, which only proves the payload was signed for that org's webhook secret — it says nothing about which commit SHAs may be referenced inside the payload body.
2. `Handler#initialize`/`Handler.call` (app/models/shipit/webhooks/handlers/handler.rb:15-24) merely parses params; the base class exposes a `stacks` helper (lines 32-34) that correctly scopes to `Repository.from_github_repo_name(repository_name)&.stacks`, but this helper is opt-in per handler.
3. `StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24) does NOT use the `stacks` helper. It runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a global lookup across the entire `commits` table, regardless of which stack/repository the commit belongs to.
4. `Commit#create_status_from_github!` (app/models/shipit/commit.rb:165-169) calls `statuses.replicate_from_github!(stack_id, github_status)`, and `Status.replicate_from_github!` (app/models/shipit/status.rb:24-33) does correctly stamp each created `Status` row with the `commit`'s own `stack_id` via `find_or_create_by!(stack_id:, ...)`.

So the per-row `stack_id` scoping described in the question is indeed correct — each `Status` is written with the right `stack_id` for the commit it's attached to. The vulnerability is one level up: the *set of commits mutated* is not restricted to the webhook's own repository. An attacker who owns/controls repository A can create a commit (e.g. via a PR, push, or cherry-pick) whose SHA collides with (or is deliberately copied from) a commit that already exists in another repository/stack B tracked by the same Shipit instance (fork chains, vendored branches, mono-to-poly repo migrations, or repos who share commit history via `git subtree`/mirrors commonly produce identical SHAs across "different" Repository records in Shipit). The attacker then triggers (or GitHub sends, since it's a real signed event for repo A) a `status` webhook for that SHA with a forged `state`/`description`/`target_url`. `verify_signature` passes because the event genuinely came from A. `StatusHandler` then finds all `Commit` rows with that SHA — including the one in stack B — and writes a poisoned `Status` for stack B too, propagating to `Commit#blocked?`/`deployable?` on stack B and corrupting `stack.commits.reachable.newer_than(...).older_than(...)` results there, since `blocking?`/CI state on stack B is now driven by an event repository B never sent.

### Impact Explanation
A single valid signed webhook from an attacker-controlled repository can flip CI/status state (`success`/`failure`/`error`/`pending`, with arbitrary `description`/`target_url`) on commits belonging to unrelated stacks/repositories that merely share a commit SHA. Since `Commit#deployable?` and `Commit#blocked?` depend on `Status`/`CommitChecks` state, this can force `success?` to true on a commit in a victim stack, enabling `schedule_continuous_delivery` to trigger, or block/unblock deploys — a payload for one repository mutating another's stack/commit state, matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy/rollback"). Blast radius scales with N — every stack across every repository sharing that SHA gets a forged, incorrectly-scoped write from one event.

### Likelihood Explanation
Requires: (a) a Shipit instance tracking two or more repositories/stacks (b) that end up sharing an identical commit SHA (achievable deliberately by the attacker forcing a specific commit — since SHA is a hash of tree+parents+metadata, an attacker who controls repository A's history can engineer a commit whose content, parent, author/committer identity and timestamps exactly match a commit visible in repository B, e.g. by mirroring/forking public history) and (c) GitHub delivering (or the attacker's owned repo sending) a `status` event for that SHA. No secrets, sessions, or elevated privileges are needed — the attacker only needs write access to a repository they control and the ability to create commits with a chosen SHA (feasible when B's history is public/forkable, which is common for OSS or internally mirrored repos). This is exploitable per-SHA and repeatable.

### Recommendation
Scope `StatusHandler#process` to the webhook's own repository, mirroring the base `Handler#stacks` helper, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This ensures only commits belonging to stacks of the repository that actually emitted the webhook are updated, restoring the "one event, one repository's stacks" invariant. The same scoping check should be audited for other handlers that query by SHA/commit without going through `stacks`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual addition)
test "status webhook is scoped to the sending repository's stacks, not global sha" do
  repo_a = shipit_repositories(:shipit)
  stack_a = shipit_stacks(:shipit)
  stack_b = create_stack!(repository: create_repository!(full_name: "attacker/victim-mirror"))
  stack_c = create_stack!(repository: create_repository!(full_name: "someone/other-mirror"))

  shared_sha = "a" * 40
  commit_a = stack_a.commits.create!(sha: shared_sha, ...)
  commit_b = stack_b.commits.create!(sha: shared_sha, ...)
  commit_c = stack_c.commits.create!(sha: shared_sha, ...)

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'attacker-ci',
    'repository' => { 'full_name' => repo_a.full_name, 'owner' => { 'login' => repo_a.owner } }
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  # EXPECTED (fixed) binding: only stack_a gets a Status row for this event.
  assert_equal [stack_a.id], Shipit::Status.where(sha_commit_id: [commit_a.id, commit_b.id, commit_c.id]).pluck(:stack_id).uniq

  # CURRENT (vulnerable) behavior demonstrates the break:
  # Shipit::Status.where(stack_id: [stack_a.id, stack_b.id, stack_c.id]).count == 3
end
```
Note: exact fixture/model setup should follow existing conventions in `test/models/shipit/webhooks/handlers/`, which is out of scope to author here per the rules, but the assertion `Status.where(stack_id: [stack_a.id, stack_b.id, stack_c.id]).count == 3` after a single `StatusHandler.call` for repo A's payload is the reproducible demonstration of the break.
