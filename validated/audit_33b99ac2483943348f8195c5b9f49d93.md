### Title
Header/Witnessing Commission Income to AA Addresses Is Untracked by `aa_balances` and Unspendable by AA Payment Logic, Permanently Freezing AA Funds - (File: aa_composer.js, headers_commission.js, paid_witnessing.js)

### Summary
Like the RAAC/FeeCollector bug — where tokens physically arrive at an address but never update the accounting ledger the recipient's distribution logic relies on — ocore has an analogous split-ledger problem for Autonomous Agents. Coins can be credited to an AA's address as headers commission (and analogously as witnessing income) through `headers_commission_outputs`/`witnessing_outputs`, completely bypassing the `aa_balances` table that is the sole accounting system AAs use to know and spend their funds. Because the AA response payment composer only ever draws inputs from the `outputs` table, this income becomes permanently unspendable by the AA.

### Finding Description
AA balance accounting is centralized in the `aa_balances` table. It is populated only via two paths:
1. `updateInitialAABalances`, which credits an AA's balance strictly from `trigger.outputs`, i.e. amounts found in `payment` messages of the *triggering unit* addressed to the AA [1](#0-0) .
2. `updateFinalAABalances`, which adjusts the AA's balance only by consumed/created rows in the `outputs` table when the AA sends its own response payment [2](#0-1) .

Separately, the protocol has an entirely independent commission-crediting mechanism: `calcHeadersCommissions()` in `headers_commission.js` pays out headers commission directly into the `headers_commission_outputs` table to the *author address* of the winning child unit (or its `earned_headers_commission_recipients`) [3](#0-2) , and an analogous `witnessing_outputs` table exists for witnessing income. These tables are **not** part of the `outputs` table and are **never referenced** by any AA balance-update code path (`aa_balances` is only touched by the code cited above and by `insertAADefinitions`'s initial backfill, which itself only sums the `outputs` table [4](#0-3) ).

An AA response unit is authored by the AA's own address (`authors: [{address: address}]` — see `sendUnit`), so if that response unit is later chosen as the "best child" of a parent unit for header-commission purposes, the AA address becomes eligible to receive headers commission that lands only in `headers_commission_outputs`.

The AA's own payment-composition logic (used whenever oscript emits a `payment` message) only ever selects spendable inputs from the `outputs` table via `iterateUnspentOutputs`/`completePaymentPayload` [5](#0-4) ; it has no code path to consume `headers_commission_outputs` or `witnessing_outputs`. Regular wallets can spend such commission income through dedicated wallet-composer flows, but AAs cannot express that operation in oscript — an AA can only issue `payment` messages, which the AA composer resolves solely against `outputs`.

Finally, the protocol's own consistency check, `checkBalances()`, only reconciles `aa_balances` against the `outputs` table (`sql_fill_temp`/`sql_balances_to_outputs`) [6](#0-5) ; it does not include `headers_commission_outputs` or `witnessing_outputs` in the comparison (note the fully commented-out `sql_base`/witnessing-aware queries in the same function, indicating this class of income was deliberately or accidentally left out of the invariant check) [7](#0-6) . This mirrors the RAACToken pattern exactly: value is credited to an address through a side channel that the address's internal accounting/spend-tracking system does not observe, and the discrepancy is invisible to the system's own sanity check.

### Impact Explanation
Any bytes credited to an AA address via headers commission (or witnessing commission, if reachable) become permanently frozen: they are real, spendable-by-protocol-rules bytes sitting in `headers_commission_outputs`/`witnessing_outputs`, but the AA's oscript cannot construct a payment referencing them (no `balance[]` visibility, no input-selection path), and no external actor holds the AA's private key to spend them manually the way a normal wallet address would. This is a concrete AA fund-loss/freezing condition, matching the accepted "AA fund loss or freezing" impact category — funds are unrecoverable by the AA logic that is supposed to control them, and the discrepancy is not caught by `checkBalances()`, so it would go undetected in production monitoring.

### Likelihood Explanation
Triggering an AA response unit to become the "best child" of a commission-paying parent does not require any special privilege — it depends only on normal DAG parent/child selection dynamics (best-parent selection by hash tie-break in `getWinnerInfo`), which any unit poster indirectly influences by choosing parents when composing units that reference an AA response unit. Because AA response units are routinely selected as parents by subsequent activity (this is normal DAG growth, not adversarial), this condition is expected to occur naturally over time for active AAs, not merely as a contrived edge case.

### Recommendation
Either (a) extend `aa_balances` accounting to also ingest `headers_commission_outputs`/`witnessing_outputs` credited to AA addresses (updating balances in `headers_commission.js`/`paid_witnessing.js` when the recipient is an AA), and give AAs an oscript-level ability to spend such commission balances, or (b) prevent AA addresses from ever becoming eligible headers/witnessing commission recipients (e.g., exclude `aa_addresses` from `earned_headers_commission_recipients` eligibility and from the best-child headers-commission algorithm), and additionally extend `checkBalances()` to include these tables in its invariant so any future regression of this kind is caught automatically.

### Proof of Concept
Conceptual reproduction path (cannot be executed here without a running ocore devnet, but the mechanism is directly traceable in code):
1. Deploy an AA whose response unit(s) are frequently used as parents by other units (i.e., an active, widely-referenced AA).
2. Post units on top of the AA's response unit so that, per `calcHeadersCommissions()`'s best-child selection (`getWinnerInfo`, SHA1 tie-break), the AA response unit is selected as the "best child" of some parent unit and headers commission accrues to the AA address in `headers_commission_outputs` [3](#0-2) .
3. Query `aa_balances` for the AA address — it does not reflect the accrued headers commission (confirmed by code inspection: no write path from `headers_commission.js` into `aa_balances`).
4. Attempt to have the AA emit a `payment` message spending this balance from oscript — the AA composer's `completePaymentPayload`/`iterateUnspentOutputs` only reads unspent rows from the `outputs` table [8](#0-7)  and will never find or spend the `headers_commission_outputs` row, leaving the bytes permanently stuck at the AA address.

Note: I was unable to fully verify within available tool calls (a) the exact regular-wallet composer code path that normally spends `headers_commission_outputs` (to contrast it explicitly against the AA composer), and (b) whether an AA response unit being selected as a headers-commission "best child" has ever been explicitly tested/exercised in the test suite. These would need direct confirmation in a live/dev environment or through a Devin session with broader file access, since the codebase index used here may not include every relevant file in full.
