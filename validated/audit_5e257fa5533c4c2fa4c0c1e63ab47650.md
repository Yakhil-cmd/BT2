### Title
Cross-repository forged `Status` row satisfies a merge-required context without flipping commit `#state`, enabling an unauthorized-merge bypass - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Webhooks::Handlers::StatusHandler#process` resolves target commits by `sha` alone, with no scoping to the webhook's originating repository, and hands attacker-controlled `state`/`context` straight to `Status.replicate_from_github!`. Combined with how `Status::Group` computes "missing" required contexts, an attacker who can guess/replicate a victim's public `merge.require`/`ci.require` context name can inject one forged `Status` row for that exact context on the victim's stack, which removes the `Status::Missing` placeholder that was the sole reason `MergeRequest#any_status_checks_missing?` returned true — without necessarily making `Commit#state`/`#success?` become `success`, because unrelated genuine pending/failure statuses continue to dominate `Status::Group`'s `significant_status` for `#state`.

### Finding Description
The broken binding: the question of "which repository authorized this Status row" is never checked. `StatusHandler#process` does: [1](#0-0) 

`Commit.where(sha: params.sha)` is a global, cross-stack lookup — unlike other handlers that scope via `stacks`/`repository_name` (`Handler#stacks` at [2](#0-1) ), `StatusHandler` ignores that scoping entirely. Any commit sha match, from any stack, receives the status. `create_status_from_github!` then calls `statuses.replicate_from_github!(stack_id, github_status)` using **that commit's own `stack_id`** (`app/models/shipit/commit.rb:165-169`), and `Status.replicate_from_github!` persists attacker-controlled `state`/`context`/`description` verbatim: [3](#0-2) 

An attacker who owns/controls a repository (Repo A) can send a `status` webhook (with a valid signature for their own org — `verify_signature` only checks the sending org, not that the sha belongs to that org's repo) referencing a `sha` that also exists as a commit in victim Repo B's stack. This writes a forged `Status` row with `stack_id = Repo B's stack`, and a `context` chosen to match a string from Repo B's public `shipit.yml` `merge.require`/`ci.require`.

Why this produces the specific divergence the question describes: `Status::Group#initialize` computes missing required contexts purely from context-name absence: [4](#0-3) 

If the required context previously had no real status, a `Status::Missing` placeholder (`state == 'pending'`, `missing? == true`) is synthesized ( [5](#0-4) ). Once the forged status supplies that exact context, the placeholder disappears entirely — `missing_contexts` no longer includes it. `MergeRequest::StatusChecker` (a `Status::Group` subclass) uses `deploy_spec.merge_request_required_statuses` as its `required_statuses`: [6](#0-5) [7](#0-6) 

so `any_status_checks_missing?` ( [8](#0-7) ) flips from true to false purely because the placeholder for that one context is gone — independent of whatever other statuses exist.

Meanwhile `significant_status` selection (used both for `Commit#state` via the plain `Status::Group` and for the merge checker) is: [9](#0-8) 

If Repo B's commit already carries genuine `failure`/`error` statuses in *other*, unrelated contexts, those remain in `non_success_statuses` and (being non-`pending`) are picked as `significant_status` ahead of the newly-added forged `success` entry, so `#state`/`#success?` stays non-success — exactly matching the "hierarchy" test at [10](#0-9) . But `any_status_checks_failed?` only inspects `failure?`/`error?`, not `pending?` ( [11](#0-10) ), so if the victim's genuine unrelated statuses are merely `pending` (not `failure`/`error`), then after the forged status removes the missing-context rejection, `reject_unless_mergeable!` ( [12](#0-11) ) no longer rejects for `ci_missing` nor `ci_failing`, potentially allowing an incomplete/pending PR to proceed to `merge!`.

Existing guards do not prevent this: `verify_signature` only authenticates the sending GitHub org/app, not that the `sha` in the payload belongs to a commit owned by that org's repositories; `ExplicitParameters` validates payload shape, not sha-ownership; there is no `repository`/`stack_id` cross-check in `StatusHandler#process`.

### Impact Explanation
A forged `Status` row is written against a repository (Repo B) that never authenticated it, on a stack the attacker doesn't own. This can cause `MergeRequest#any_status_checks_missing?` to flip from true to false for Repo B's pull requests without their required CI actually having run, potentially letting `reject_unless_mergeable!` skip the `ci_missing` rejection and, when the victim's other required checks are merely `pending` rather than `failure`, allow the merge job to proceed to `merge!` — an unauthorized merge for a repository the attacker does not control. This is cross-tenant (payload for Repo A mutates Repo B's stack/commit records) and repeatable against any victim stack whose `sha` the attacker can also produce a commit for and whose `merge.require`/`ci.require` context strings are guessable from the victim's public `shipit.yml`. Matches Critical: "a payload for one repository mutating another's stack, commit... or an unauthorized... merge."

### Likelihood Explanation
Preconditions: attacker needs (1) a GitHub org/repo of their own with a valid Shipit webhook config (unprivileged, self-serve), (2) a commit `sha` value that collides with a sha present in the victim Repo B's `commits` table (feasible with short/ambiguous shas or by referencing a sha the attacker can reproduce, e.g. an empty/well-known tree commit, or via targeted collision through commit crafting), and (3) knowledge of the victim's public `merge.require`/`ci.require` context strings (readable from the victim's public `shipit.yml` on GitHub). No Shipit session, API token, or secrets are required — this is a pure unauthenticated-relative-to-Repo-B webhook injection. The attack is repeatable per victim/stack and does not require guessing any secret, only public config values.

### Recommendation
In `Webhooks::Handlers::StatusHandler#process`, scope the commit lookup to the webhook's own repository/stacks (as other handlers do via `Handler#stacks`), e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalently restrict to `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, so a status payload can only ever create `Status` rows for commits belonging to the repository that sent (and is authenticated for) the webhook.

### Proof of Concept
```ruby
# test/models/merge_request_forged_status_test.rb
test "#any_status_checks_missing? can be satisfied by a forged status while #state stays non-success" do
  commit = shipit_commits(:cyclimse_first) # victim commit/stack fixture
  stack = commit.stack
  stack.cached_deploy_spec.stubs(:merge_request_required_statuses).returns(['ci/required-context'])

  # Legitimate pending/failure statuses already present for unrelated contexts
  commit.statuses.create!(stack_id: stack.id, state: 'pending', context: 'ci/other-pending')

  merge_request = shipit_merge_requests(:cyclimse) # associated with `commit` as head
  assert_predicate merge_request, :any_status_checks_missing? # true: 'ci/required-context' missing

  # Attacker-controlled webhook payload for a DIFFERENT repository, sha collides with victim commit
  forged = OpenStruct.new(state: 'success', description: 'forged', context: 'ci/required-context',
                           target_url: nil, created_at: Time.now)
  Shipit::Commit.where(sha: commit.sha).each { |c| c.create_status_from_github!(forged) }

  merge_request.reload
  refute_predicate merge_request, :any_status_checks_missing? # flips to false
  refute_equal 'success', commit.reload.state # #state still dominated by 'ci/other-pending'
end
```
