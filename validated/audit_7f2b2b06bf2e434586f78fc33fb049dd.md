### Title
API client stack-scope bypass in `Api::CCMenuController#stack` — ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::BaseController` enforces stack authorization by restricting the queryable stack set to the ones an `ApiClient` is scoped to (`current_api_client.stack_id`). `Api::CCMenuController` overrides the `stack` accessor and looks the stack up directly from `Stack.from_param!(params[:stack_id])`, completely bypassing that scoping. This breaks the binding "the stack a token authorizes == the stack the endpoint touches": a token scoped to one stack can read the CCMenu status of any other stack.

### Finding Description
`Api::BaseController` defines the canonical, scope-enforcing accessor: [1](#0-0) 

`stacks` restricts to `Stack.where(id: current_api_client.stack_id)` when the client is scoped, and `stack` resolves the requested `params[:stack_id]` only within that restricted set — this is the equality the engine intends to hold: `token.stack_id == stack.id` (or `token.stack_id.nil?` for unscoped/admin clients).

`Api::CCMenuController` inherits from `BaseController` and declares `require_permission :read, :stack`, but it redefines `stack` to bypass the scoped `stacks` collection entirely: [2](#0-1) 

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
```

`require_permission` only checks that the token *has* the `read:stack` permission string — it never checks *which* stack the permission applies to (`app/models/shipit/api_client.rb#check_permissions!` merely checks `permissions.include?("read:stack")`). The actual per-stack restriction is supposed to come exclusively from the `stacks`/`stack` scoping in `BaseController`, which `CCMenuController` discards.

Root cause file/method: `app/controllers/shipit/api/ccmenu_controller.rb`, private method `stack` (line ~29-31), which calls `Stack.from_param!(params[:stack_id])` instead of the inherited `stacks.from_param!(params[:stack_id])`.

Before the trust-breaking path: `ApiClient#stack_id` scopes what stacks a `read:stack`-permissioned token may see, enforced uniformly via `BaseController#stacks`/`#stack` (used correctly by `Api::StacksController#stack`, see `app/controllers/shipit/api/stacks_controller.rb` lines 87-89, which does use `stacks.from_param!`).

After: `Api::CCMenuController#stack` ignores `current_api_client.stack_id` and resolves any `stack_id` supplied in the URL against the entire `Stack` table.

### Impact Explanation
This is a High-severity authorization escalation: unauthenticated-read-boundary violation of `Shipit.github_teams`/stack scoping. Any holder of an `ApiClient` token whose intended privilege is `read:stack` limited to a single stack (a common least-privilege pattern, e.g. a CCMenu/CI-status widget deployed to a specific team) can enumerate and read the deploy/build status (`lastBuildStatus`, `lastBuildLabel`, `webUrl`, lock state) of every other stack managed by the Shipit instance, including stacks belonging to unrelated repositories/teams that the token owner was never granted access to. This is exactly the "stack a token authorizes vs. stack it touches" binding called out as in-scope, and constitutes unauthorized read of stack state across authorization boundaries.

### Likelihood Explanation
High likelihood for anyone who already holds a stack-scoped, `read:stack`-only `ApiClient` credential: exploitation requires nothing but changing the `stack_id` segment of the CCMenu URL (`/api/stacks/*stack_id/ccmenu`) to a different, unauthorized stack identifier. No additional secrets, signatures, or elevated permissions are needed — the attacker's own legitimately-issued, narrowly-scoped token is sufficient.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the inherited scoped lookup instead of querying `Stack` directly, e.g. remove the override and rely on `BaseController#stack` (`stacks.from_param!(params[:stack_id])`), so CCMenu status is only resolvable for stacks the authenticated `ApiClient` is actually scoped to.

### Proof of Concept
1. Create (or use an existing) `ApiClient` scoped to `stack_id = A` with permission `read:stack` (e.g. fixture `here_come_the_walrus`, scoped to stack `shipit`, as seen in `test/fixtures/shipit/api_clients.yml`).
2. Using this token's `authentication_token` as HTTP Basic credentials, issue:
   `GET /api/stacks/<other-owner>/<other-repo>/<other-env>/ccmenu`
   where `other-owner/other-repo/other-env` identifies a stack `B` the client is *not* scoped to.
3. Observe the request succeeds with HTTP 200 and returns stack `B`'s CCMenu XML (`lastBuildStatus`, `lastBuildLabel`, `webUrl`, etc.), even though `BaseController#stacks` would have restricted the client to only stack `A` had `CCMenuController` used the inherited `stack` method (contrast with `test/controllers/api/stacks_controller_test.rb` lines 217-223, "an api client scoped to a stack will only see that one stack", which passes only because `Api::StacksController` correctly uses the scoped `stacks.from_param!`).

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
  end
end
