## Title
`is_valid_signed_package`/`validateSignedMessage` provide no monotonic counter or single-use binding, allowing replay of stale-but-validly-signed packages against AAs - (File: signed_message.js, formula/evaluation.js)

### Summary
The core primitive AAs use to accept off-chain signed data (`is_valid_signed_package` in oscript, backed by `signed_message.validateSignedMessage`) only verifies (a) the ECDSA signature over the canonical package content and (b) that an optional `last_ball_unit` is a stable, non-future unit. It never binds the package to a single use or to a monotonically increasing counter. Exactly like the ClearanceKit bug, "freshness" is asserted only by ordering against a coarse reference point (there: row content + no counter; here: `last_ball_unit`/mci), not by an enforced, ever-increasing sequence number checked by the verifier itself. Any previously broadcast, still cryptographically valid signed package can be resubmitted by an unprivileged AA-trigger sender at any later time (as long as its `last_ball_unit` is still stable and ≤ current mci, which is essentially always true), and the AA-level protection against this is entirely optional and left to the oscript author.

### Finding Description
`validateSignedMessage` computes the hash to verify from `getSignedPackageHashToSign`, which hashes only `signed_message`, `authors` (without authentifiers), `last_ball_unit`, and `version` — no nonce or counter field is mandated: [1](#0-0) 

`validateSignedMessage` itself only checks structural validity, sorted/valid authors, that the definition hashes match, and — if `last_ball_unit` is present — that it refers to a stable unit whose `main_chain_index` is not later than the caller-supplied `mci`: [2](#0-1) 

There is no check anywhere in this function, nor in the AA-facing `is_valid_signed_package` formula op, that the package has not already been used, nor that its `last_ball_unit` is "recent" rather than merely "not in the future": [3](#0-2) [4](#0-3) 

Because the verifier gives no built-in freshness/replay guarantee, the ocore-shipped reference patterns for using signed packages must reinvent one themselves, and only do so imperfectly:
- `payment_channels.oscript` manually compares a `period` field inside the signed message against a state variable to prevent replaying an old channel-state signature: [5](#0-4) 
- `order_book_exchange.oscript` derives a dedup id by hashing order fields together with `last_ball_unit` and checks a `var['executed_'||$id]` flag: [6](#0-5) 

Both patterns are AA-author-supplied workarounds, not something enforced by `signed_message.js`/`formula/evaluation.js`. Any AA that consumes `is_valid_signed_package` for oracle prices, order signatures, off-chain balance attestations, etc. without independently embedding and checking a strictly increasing counter is exposed: an old, still-valid signature (e.g., an out-of-date price quote, an old channel balance split, a previously executed order) remains permanently acceptable to `is_valid_signed_package`, mirroring the ClearanceKit issue where an old signed snapshot is replayed because the verifier lacks a monotonic freshness counter.

### Impact Explanation
Any AA that relies on this primitive for financial decisions (price oracles, payment-channel state, order matching, attestation-gated payouts) without independently implementing a counter can be tricked by an unprivileged trigger sender into re-accepting stale signed data. Depending on the AA logic, this enables reuse of a stale, more favorable price/exchange rate, replay of an already-settled channel balance, or double-execution of a signed order — i.e., concrete AA fund loss/inflation of AA-held balances at the expense of counterparties, without needing to compromise any key.

### Likelihood Explanation
Exploitation requires only sending an AA trigger containing a signed package the attacker legitimately received earlier (e.g. from a price feed, a counterparty in a payment channel, or their own prior order) — no privileged access, hub/node compromise, or key theft is needed. The barrier is entirely on the AA author correctly implementing manual anti-replay logic (as the shipped samples show is easy to omit or get wrong, e.g. binding to `last_ball_unit` rather than a true incrementing counter). Given `is_valid_signed_package` is a documented, encouraged building block for off-chain signed data in AAs, likelihood of at least one deployed AA missing correct replay protection is non-trivial.

### Recommendation
Add first-class replay protection to the primitive itself rather than leaving it entirely to AA authors: support/require an explicit, strictly increasing `counter`/`nonce` field validated by `validateSignedMessage`/`is_valid_signed_package` against AA-tracked state, or provide an oscript-level helper that atomically checks-and-updates a "last used counter" for a given signer/context so that stale packages are rejected by the platform instead of by convention. At minimum, document and lint/warn when `is_valid_signed_package` is used without a monotonic counter check in the surrounding oscript logic.

### Proof of Concept
1. Deploy an AA that accepts a price quote via `is_valid_signed_package(trigger.data.quote, oracle_address)` and uses `trigger.data.quote.signed_message.price` to compute a payout, without checking a counter field against state (a simplified version of the order/channel patterns above minus the manual dedup key).
2. Oracle signs and publishes a favorable quote at time T0; a user trigger consumes it once.
3. Later, market price has moved unfavorably for the AA, but the old quote's `last_ball_unit` is still a stable unit with `main_chain_index <= current mci` (always true for any past stable unit).
4. Attacker resubmits the identical `trigger.data.quote` from step 2 in a new trigger. `is_valid_signed_package` (`formula/evaluation.js:1653-1701`, `signed_message.js:117-303`) validates it as fully valid again since no consumption/counter state is checked by the core verifier.
5. The AA pays out using the stale price again, repeatable indefinitely until the AA author adds their own manual dedup/counter logic (as `order_book_exchange.oscript`/`payment_channels.oscript` had to do by hand).

function getSignedPackageHashToSign(signedPackage) {
	var unsignedPackage = _.cloneDeep(signedPackage);
	for (var i=0; i<unsignedPackage.authors.length; i++)
		delete unsignedPackage.authors[i].authentifiers;
	var sourceString = (typeof signedPackage.version === 'undefined' || signedPackage.version === constants.versionWithoutTimestamp) ? getSourceString(unsignedPackage) : getJsonSourceString(unsignedPackage);
	return crypto.createHash("sha256").update(sourceString, "utf8").digest();
}
