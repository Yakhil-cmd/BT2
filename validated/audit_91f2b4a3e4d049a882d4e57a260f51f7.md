### Title
Attacker-controlled linked-branch names starting with `-` are passed as unsanitized positional arguments into `git pull`/`git checkout`, enabling git flag injection (e.g. `--upload-pack`) - ([File: pkg/cmd/issue/develop/develop.go])

### Summary
`checkoutBranch` in `pkg/cmd/issue/develop/develop.go` takes `LinkedBranch.BranchName`, an attacker-controllable value returned by `api.CreateLinkedBranch`/`api.ListLinkedBranches`, and passes it directly as a bare positional argument to `gc.CheckoutBranch`, `gc.CheckoutNewBranch`, and — most critically — `gc.Pull`. None of these `git.Client` methods insert a `--` separator before the branch name, so a name beginning with `-` can be parsed by git as an option rather than a ref name.

### Finding Description
`checkoutBranch` receives `checkoutBranch` (the branch name) from `developRunCreate`, which sets `branchName` from `api.CreateLinkedBranch(...)` (or from an existing `api.ListLinkedBranches` entry via `findExistingLinkedBranchName`) with no validation that the value doesn't start with `-` [1](#0-0) .

That value flows into:
- `gc.Fetch(ctx, baseRemote.Name, fmt.Sprintf("+refs/heads/%[1]s:refs/remotes/%[2]s/%[1]s", checkoutBranch, baseRemote.Name))` — safe, because the branch name is embedded in the middle of a refspec string that always begins with `+refs/heads/`, so the resulting argument can never start with `-` [2](#0-1) .
- `gc.CheckoutBranch(ctx, checkoutBranch)` at line 406, which builds `args := []string{"checkout", branch}` in `git/client.go` — the branch name is passed as a bare positional token [3](#0-2) [4](#0-3) .
- `gc.Pull(ctx, baseRemote.Name, checkoutBranch)` at lines 398 and 410, which builds `args := []string{"pull", "--ff-only"}` then `args = append(args, remote, branch)` — the branch name again becomes a bare positional token passed to a network-triggering `git pull` invocation [5](#0-4) [6](#0-5) .
- `gc.CheckoutNewBranch(ctx, baseRemote.Name, checkoutBranch)` at line 414, which builds `args := []string{"checkout", "-b", branch, "--track", track}` in `git/client.go` [7](#0-6) [8](#0-7) .

None of these `Command`/`AuthenticatedCommand` call sites prepend a `--` end-of-options marker before the branch name (contrast with other methods in the same file such as `ShowRefs`, `WorktreeRemove`, `RemoteURL`, `IsIgnored`, which do use `"--"`) [9](#0-8) [10](#0-9) . This means `git.Client` has no general protection against branch names that look like options, and `checkoutBranch` in `develop.go` relies entirely on the git client to do so, which it does not for `Pull`, `CheckoutBranch`, or `CheckoutNewBranch`.

The most exploitable sink is `gc.Pull`: `git pull` forwards fetch-related options (including `--upload-pack=<command>`) to the underlying `git fetch`/`fetch-pack` invocation when contacting the remote. If `checkoutBranch` (the branch name) is a string like `--upload-pack=touch /tmp/pwned`, the resulting invocation is effectively `git pull --ff-only <remote> --upload-pack=touch /tmp/pwned`, which git's option parser will interpret as an option (git's `parse-options` machinery accepts options interleaved with positional arguments unless a literal `--` has already been seen) and can invoke the specified program as the "upload-pack" helper during the fetch phase — the same class of primitive abused in CVE-2017-1000117 for `git clone`.

### Impact Explanation
This allows local command execution on the victim's machine when they run `gh issue develop <n> --checkout` (or with `--branch-repo`) against an issue whose linked branch was created (or echoed back) with an attacker-chosen name of the attacker's own repository. This matches the "arbitrary command/code execution on the client via a malicious repository" bounty class. It also creates a smaller-impact path via `checkout -b`/`checkout` option confusion for repository state corruption (e.g., forcing unexpected checkout modes), though the `Pull` path is the most severe because `--upload-pack` is a documented remote-command-execution vector.

### Likelihood Explanation
Preconditions: the victim must run `gh issue develop <n> --checkout` (or supply `--branch-repo`) pointed at a repository/issue controlled by the attacker, and a local git remote matching that repo must already exist (`remotes.FindByRepo` must succeed) for `checkoutBranch` to reach the `Fetch`/`Pull`/`Checkout*` calls at all [11](#0-10) . The attacker fully controls the repository they own and can call the `createLinkedBranch` GraphQl mutation (or otherwise influence the branch name returned by the API) to set an arbitrary `BranchName` value, satisfying the "attacker controls linkedBranches on a repository they own" precondition stated in the question. This is a normal, low-effort action for anyone who owns a repo and is not blocked by any host allowlisting or ghrepo/ghinstance validation, since those only validate hostnames/repo identifiers, not branch-name content.

### Recommendation
- In `git/client.go`, insert `"--"` before user/API-derived ref or branch names in `CheckoutBranch`, `CheckoutNewBranch`, `Pull`, and `Fetch` (where applicable) so git cannot interpret them as options, e.g. `args := []string{"checkout", "--", branch}`, `args = append(args, "--", remote, branch)` for `Pull` (git pull's `--` separates options from `<repository> <refspec>`).
- Additionally/alternatively, validate `LinkedBranch.BranchName` (and any other API-derived ref name) in `pkg/cmd/issue/develop/develop.go` before use, rejecting or quoting names that start with `-`.
