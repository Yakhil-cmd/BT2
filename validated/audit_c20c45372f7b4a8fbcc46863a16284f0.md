### Title
CCMenu token created without `stack` scoping grants read access to all stacks - (File: app/controllers/shipit/ccmenu_url_controller.rb)

### Summary
`CCMenuUrlController#client` mints an `ApiClient` via `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')` without ever assigning `stack:`, so the resulting token's `stack_id` is `nil`. Any holder of a ccmenu URL minted for one stack can use its embedded token against `Api::StacksController` to read the state of every stack in the installation, not just the one the URL's path implies.

### Finding Description
Binding that should hold: `current_api_client.stack_id == stack_A.id` for a token minted from `GET /stacks/:stack_id/ccmenu_url` for stack A, so that `Api::BaseController#stacks` resolves to `Stack.where(id: stack_A.id)`.

Actual code: [1](#0-0) 
`create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')` never sets `stack:`, so `ApiClient#stack_id` is `nil` for every token this endpoint issues, regardless of which stack the request was for.

`Api::BaseController#stacks` treats an absent `stack_id` as "unrestricted": [2](#0-1) 
`current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` — since `stack_id` is `nil`, `stack_id?` is `false`, so `stacks == Stack.all`.

`Api::StacksController#show`/`#index` only enforces the `read:stack` permission via `require_permission`, and then resolves the record through `stacks.from_param!(params[:id])`: [3](#0-2) [4](#0-3) 
Because `stacks` resolves to `Stack.all`, this check does not restrict the token to the stack it was issued for.

Additionally, the `find_or_create_by!` lookup key is `creator + name` only, not `creator + name + stack`, so the *same* `ApiClient` record (and thus the same `authentication_token`) is reused across every stack for which that user requests a ccmenu URL — compounding the missing `stack_id` binding: even a naive fix that adds `stack: stack` to `create_with` would not fix already-existing unscoped records, and would not stop the found record (created for stack A) from being returned unchanged when the user later requests the URL for stack B.

Exploit flow: a user (any Shipit session holder, not necessarily an operator/maintainer) visits `GET /stacks/repoA-stack/ccmenu_url`. This mints/reuses an `ApiClient` with `permissions: ["read:stack"]` and `stack_id: nil`, and returns a URL containing `?token=<token>`. That token, embedded in a URL intended only for CCTray/CCMenu polling of stack A's build status, is fully valid HTTP Basic Auth credential for the whole `Api::BaseController` surface gated by `read:stack` (e.g. `Api::StacksController#show`, `#index`), and resolves to `Stack.all` — i.e. it can read any stack B's state, not just stack A's.

None of the existing guards catch this: `authenticate_api_client` only checks the signature is valid, `require_permission!` only checks the `read:stack` scope string is present (which it is), and the `stacks` scope explicitly treats `stack_id.nil?` as "no restriction" rather than "deny."

### Impact Explanation
A ccmenu token — meant to be a narrowly-scoped, low-trust credential embedded in a URL for CI status polling of one specific stack — instead grants unauthenticated (from the target repo's perspective) read access to every stack managed by the Shipit instance: stack configuration, environment, branch, deploy history, task state, etc. This is a cross-tenant read exposure: whoever obtains repo A's ccmenu URL (which is explicitly designed to be embedded in external tooling, dashboards, or CI badges — a lower-trust surface than a full session) gains read access to all other repositories' stacks, matching the "unauthenticated read of stack state" High-impact category. It is trivially repeatable against arbitrary stacks with the same single token.

### Likelihood Explanation
Preconditions are minimal: any user with a Shipit session (not necessarily an operator) can hit `GET /stacks/:stack_id/ccmenu_url` for a stack they have UI access to, which is the intended normal use of this feature. No GitHub secrets, webhook secrets, or `api_clients_secret` are needed — the token is handed out by the feature itself. The only "attacker" action needed is obtaining a ccmenu URL that was generated for stack A (these URLs are meant to be shared/embedded in monitoring tools by design), then replaying its token against a different stack's API endpoint. This requires no privilege escalation beyond what the feature already grants by design, only exploiting the missing scoping.

### Recommendation
Set `stack: stack` on `create_with` in `CCMenuUrlController#client`, and include `stack` in the `find_or_create_by!` lookup key (e.g. `find_or_create_by!(creator: current_user, name: 'CCMenu Client', stack: stack)`) so a distinct, stack-scoped `ApiClient` is created per stack. Additionally, migrate/patch any existing `ApiClient` rows created by this endpoint with `stack_id: nil` to bind them to a stack or revoke them, since the current bug has already been minting unscoped tokens.

### Proof of Concept
Minitest plan (added to `test/controllers/ccmenu_controller_test.rb` and `test/controllers/api/stacks_controller_test.rb` style):

```ruby
test ":fetch mints a client scoped to the requested stack, and it must not authorize a different stack" do
  stack_a = shipit_stacks(:shipit)
  stack_b = shipit_stacks(:shipit2) # another stack in fixtures

  get :fetch, params: { stack_id: stack_a.to_param }
  data = JSON.parse(response.body)
  token = Rack::Utils.parse_nested_query(URI(data['ccmenu_url']).query)['token']
  client = ApiClient.last

  # Binding that should hold:
  assert_equal stack_a.id, client.stack_id, "token minted for stack A must be bound to stack A"

  # Demonstrate the break: using the token against stack B succeeds when it should 404/403
  @request.env['HTTP_AUTHORIZATION'] =
    ActionController::HttpAuthentication::Basic.encode_credentials(token, '')
  get :show, params: { id: stack_b.to_param }, controller: 'shipit/api/stacks' # via Api::StacksController
  assert_response :not_found # currently fails: responds 200, exposing stack B's data
end
```

This test fails today because `client.stack_id` is `nil` (breaking the first assertion) and the token successfully reads stack B (breaking the second), proving `stacks == Stack.all` instead of `Stack.where(id: stack_a.id)`.
