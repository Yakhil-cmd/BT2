### Title
Webhook signature verified against `repository.owner.login`'s org while handlers act on `repository.full_name`'s org, allowing cross-org stack/commit writes - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#repository_owner` selects the org used to look up the `webhook_secret` for HMAC verification from `params.dig('repository','owner','login')`, but every event handler (`StatusHandler`, `PushHandler`, `PullRequest::*Handler`, `Handler#repository_name`) independently resolves the target `Repository`/`Stack` from `params.dig('repository','full_name')`. These are two separate, independently attacker-controlled JSON fields in the same request body, and nothing in the engine checks that they name the same organization.

### Finding Description
The broken binding: the code assumes `organization_used_for_HMAC == organization(repository.full_name)`. In reality:
- `repository_owner` (used for signature verification) reads `repository.owner.login` first, only falling back to `organization.login` if `repository` is absent: [1](#0-0) 
- `verify_signature` fetches the `GitHubApp` (and its `webhook_secret`) for that org and HMAC-verifies the raw body against it: [2](#0-1) 
- Once verified, `create` dispatches the raw, still-untouched `params` hash to every registered handler for the event: [3](#0-2) 
- The base `Handler#repository_name`/`#stacks`, used by `StatusHandler` (via `Commit.where(sha:)` — actually `StatusHandler` keys off `sha` alone, see below) and `PushHandler`, resolve the acted-upon `Repository` from `payload.dig('repository', 'full_name')`: [4](#0-3) 
- `PushHandler#process` uses that `stacks` scope (derived from `full_name`) to call `stack.sync_github`: [5](#0-4) 
- All `PullRequest::*` handlers (`OpenedHandler`, `ClosedHandler`, `ReopenedHandler`, `LabeledHandler`, `UnlabeledHandler`, `LabelCapturingHandler`, `EditedHandler`) independently resolve `repository` via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` and then archive/unarchive/create/update review stacks and pull requests on it, e.g. `ClosedHandler#process` calling `review_stack.archive!`: [6](#0-5) 

Attack: an attacker who administers their own GitHub org/repo (and therefore legitimately knows their own org's `webhook_secret` configured in Shipit) sends `POST /webhooks` with a body such as:
```json
{
  "repository": { "owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo" },
  "pull_request": { ... },
  "action": "closed",
  ...
}
```
signed with `X-Hub-Signature` computed using `attacker-org`'s `webhook_secret`. `repository_owner` returns `"attacker-org"`, `Shipit.github(organization: "attacker-org")` is fetched, and `verify_webhook_signature` succeeds because the attacker legitimately controls that secret. The request passes `check_if_ping`/`drop_unhandled_event`/`verify_signature` cleanly, and `create` then hands the *same* payload (with `full_name: "victim-org/victim-repo"`) to the matching handler, which resolves and mutates the victim's `Repository`/`Stack`/`PullRequest`/review-stack records — actions the attacker never authenticated for.

No existing guard closes this gap: `verify_signature` never re-checks that the org implied by `full_name` matches `repository_owner`; the `ExplicitParameters` schemas in each handler validate types/presence of fields but not cross-field consistency with the org used for authentication; `Repository.from_github_repo_name` performs no ownership/secret check, it purely does a DB lookup by name.

### Impact Explanation
Any handler that trusts `repository.full_name` (or `payload.dig('repository','full_name')`) to locate a `Stack`/`Repository`/`PullRequest` can be pointed at an arbitrary victim org/repo while the request is authenticated using the attacker's own org's `webhook_secret`. Demonstrated impact via `PullRequest::ClosedHandler` (archives a victim `ReviewStack`), `PushHandler` (triggers `sync_github` against a victim stack), and other `PullRequest::*Handler`s (create/unarchive/label-driven archive of victim review stacks, update of victim `PullRequest` records). This is a cross-repository write performed by an unauthenticated (with respect to the victim org) party, matching the Critical "payload for one repository mutating another's stack/commit/task" category. The attack is trivially repeatable against any victim repo name, for every event type routed through handlers keyed on `full_name` instead of the owner used for authentication.

### Likelihood Explanation
Preconditions: multi-org GitHub config with per-org `webhook_secret` (explicitly stated as the setup); attacker only needs to register/administer their own GitHub org (or any org configured in Shipit with a known secret to them) and know a victim's `full_name` (public information: `org/repo`). Attacker cost is a single crafted HTTP POST with a correctly computed HMAC using their own legitimately-known secret — no privileged access, no Shipit session, no victim secret needed. This is highly feasible and fully repeatable.

### Recommendation
In `WebhooksController#verify_signature` (or in `create`), after determining `repository_owner`, also derive the organization implied by `params.dig('repository','full_name')` (or by resolving `Repository.from_github_repo_name(full_name).owner`/organization) and require it to match `repository_owner` before dispatching to handlers; reject (422) on mismatch. Alternatively, have each handler validate that the resolved `Repository`'s owner/org equals the `repository_owner` used for signature verification (passed down from the controller) before performing any mutation.

### Proof of Concept
Minitest under `test/controllers/webhooks_controller_test.rb` (or `test/models/shipit/webhooks/handlers/pull_request/closed_handler_test.rb`):
1. Configure two orgs in `Shipit.github_config`-equivalent test config: `attacker-org` with `webhook_secret: "attacker-secret"`, and `victim-org` with `webhook_secret: "victim-secret"`.
2. Create `shipit_stacks(:other_org_stack)` (or a `ReviewStack`) under repository `victim-org/victim-repo`, active/unarchived.
3. Build a `pull_request` "closed" payload body:
```ruby
body = {
  action: "closed",
  number: pr.number,
  pull_request: { ... head: { sha:, ref: }, user: { login: "attacker" }, ... },
  repository: { owner: { login: "attacker-org" }, full_name: "victim-org/victim-repo" },
  sender: { login: "attacker" }
}.to_json
signature = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", "attacker-secret", body)
```
4. `post shipit.webhooks_path, params: body, headers: { "X-Github-Event" => "pull_request", "X-Hub-Signature" => signature, "Content-Type" => "application/json" }`
5. Assert both sides of the binding:
   - `assert_equal "attacker-org", @controller.send(:repository_owner)` (or assert response is `200`, proving signature verification passed using `attacker-secret`).
   - `assert shipit_stacks(:other_org_stack).reload.archived?` — proving the victim stack (under `victim-org`, authenticated via `attacker-org`'s secret) was mutated despite `repository_owner ("attacker-org") != organization_of(repository.full_name) ("victim-org")`.

If the fix is applied (cross-check `repository_owner` against the org of `full_name`), step 4 should instead return `422` and the victim stack should remain unarchived.
