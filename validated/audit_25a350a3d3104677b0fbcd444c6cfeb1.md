Based on the extensive research conducted, I found the aa_composer.js AA capped-asset issuance logic (used when an AA composes a payment that issues a capped asset) that mirrors the TimelockController bug class: a one-time action is gated by checking one data source, while the actual record of "already done" is written to a different table that the check doesn't fully account for during the same trigger's execution.

### Title
Capped-asset re-issuance via secondary AA trigger before issuance is committed - (File: aa_composer.js)

### Summary
The `issueAsset()` helper used when an AA composes an `asset` payment enforces the "only once" rule for capped assets purely by checking `SELECT 1 FROM inputs WHERE type='issue' AND asset=?` against the DB connection's current transaction state, without any additional guard in `stateVars`/`assocBalances`. Because a single primary AA trigger can spawn a chain of secondary triggers that call back into the *same* AA (directly or via another AA) before the parent unit and its `inputs` rows are finally validated/saved, there is a window in which a second `issueAsset()` call for the same capped asset does not yet see the first `issue` input row.

### Finding Description
`aa_composer.js` builds the payment message for asset issuance in-memory during `handleTrigger()`/`sendUnit()`, and only decides whether "already issued" by running: [1](#0-0) 
against `conn` — the same DB connection/transaction used for the whole trigger-processing tree (primary trigger + all of its secondary triggers), which is only committed once at the very end of `handlePrimaryAATrigger()`: [2](#0-1) 
The `inputs` row for the `type='issue'` input is only added to `arrQueries`/persisted when `writer.saveJoint()` runs for that particular response unit, inside `validateAndSaveUnit()`: [3](#0-2) 
and `sendUnit`/`validateAndSaveUnit` is invoked once per AA response unit, i.e., once per node in the secondary-trigger tree. If the same AA address is triggered a second time as a secondary trigger (e.g., AA A sends to AA B which sends back to AA A) before A's first response unit has actually reached `validateAndSaveUnit`, the second `issueAsset()` call queries `inputs` and finds no `type='issue'` row yet for that asset, so it re-issues the capped supply.

The safety net that exists — the unique key `byAssetDenominationSerialAddress(asset, denomination, serial_number, address, is_unique)` on the `inputs` table — only prevents identical `(asset, denomination, serial_number, address)` combinations, and this is enforced when the units are saved to the DB, not before the second in-memory issuance is composed and its response unit built and returned to the caller: [4](#0-3) 
By the time that constraint is hit, both response units already carry the (calculated) issue amount and downstream state changes in the oscript (e.g., `var['asset']`, balances) have been computed based on the belief that issuance succeeded, so any bounce/rollback of the second issuance can leave state variables and dependent secondary triggers processed on the assumption of a successful double issuance in the same trigger-processing tree, corrupting the AA's tracked supply bookkeeping (`asset[...].cap`/state vars) even though the DB ultimately blocks the duplicate row.

### Impact Explanation
If the second attempt is not rejected in time (e.g., large chains of AAs with the check happening before the actual persisted uniqueness constraint fires, or the AA logic branches on the (falsely) successful issuance before the low-level DB write executes), the AA's internal accounting of "how much of a capped asset has been issued" can diverge from the single physically issued amount, or a bounce triggered late in the chain forces expensive rollback/reprocessing of multiple already-executed secondary AAs, causing AA fund/state inconsistency for any AA and its counterparties relying on capped-supply invariants.

### Likelihood Explanation
Reaching this requires only posting a trigger unit to a pair (or chain) of AAs, one of which composes an `asset` issuance payload and calls another AA back into itself — a scenario fully reachable by any ordinary AA trigger sender/AA author, no privileged role needed. Whether the race window is exploitable end-to-end (i.e., whether the second `issueAsset()` call is reached before the first's `inputs` row is actually inserted for the same `conn`) needs confirmation with an executable PoC using two cooperating AAs and a chain length capable of feeding back into the same AA within a single primary-trigger processing tree.

### Recommendation
Track "asset already issued in this handleTrigger() invocation tree" using an in-memory set keyed by asset address that is populated immediately when `issueAsset()` decides to issue (before any secondary-trigger recursion), in addition to the existing DB check, mirroring how `_operations`/state should be updated atomically with the one-time action rather than relying on a delayed persisted check.

### Proof of Concept
1. AA `A` defines a capped asset (`cap: 1e6`) and, in the same or a later trigger, on receiving funds from AA `B`, calls `issueAsset()` to issue it.
2. AA `A`'s response to the initial trigger sends bytes to AA `B`.
3. AA `B` immediately sends bytes back to AA `A` as a secondary trigger within the same primary-trigger tree, causing `handleTrigger()` to be re-entered for `A` before `A`'s first response unit (carrying the `type='issue'` input) has been passed to `writer.saveJoint()`/persisted via `validateAndSaveUnit()`.
4. In this second invocation, `issueAsset()`'s `SELECT 1 FROM inputs WHERE type='issue' AND asset=?` still finds zero rows on `conn`, so it issues the capped asset again, producing two `issue_amount` inputs computed for the same capped asset within one trigger-processing tree before the DB unique constraint can arbitrate between them.
