### Title
Single reverting KLAY delivery permanently freezes `lowerHandleNonce` and DoSes the VT recovery system — (File: `contracts/service_chain/bridge/BridgeTransferKLAY.sol`, `node/sc/bridge_manager.go`)

---

### Summary

`handleKLAYTransfer` in `BridgeTransferKLAY.sol` performs all state mutations (nonce recording, `lowerHandleNonce` advancement, event emission) before the actual KLAY delivery to `_to`. If `_to` is a non-payable contract, the low-level call returns `ok = false`, `require(ok)` reverts the entire transaction, and every state mutation is rolled back. Because `lowerHandleNonce` advances only through a contiguous sequence of recorded nonces, a single permanently-failing nonce N freezes `lowerHandleNonce` at N forever. The VT recovery system (`vt_recovery.go`) uses `recoveryBlockNumber` — which is derived from `lowerHandleNonce` — as its scan start, so it enters an infinite retry loop re-submitting the always-reverting nonce N. Simultaneously, the relay loop in `bridge_manager.go` has strict head-of-line blocking: any Go-level submission error on nonce N causes all subsequent nonces to be re-queued and halted.

---

### Finding Description

**Root cause 1 — `handleKLAYTransfer` (BridgeTransferKLAY.sol lines 81–99)**

State is mutated before the external call:

```solidity
_setHandledRequestTxHash(_requestTxHash);          // line 81
handleNoncesToBlockNums[_requestedNonce] = _requestedBlockNumber; // line 83
_updateHandleNonce(_requestedNonce);               // line 84
emit HandleValueTransfer(...);                     // lines 86-96

(bool ok, ) = _to.call.value(_value)("");          // line 98
require(ok, "handleKLAYTransfer: transfer failed"); // line 99
```

If `_to` is a contract without a payable fallback, `ok` is `false`. `require(ok)` reverts the entire transaction, rolling back lines 81–96. `handleNoncesToBlockNums[N]` is never written (stays 0). [1](#0-0) 

**Root cause 2 — `_updateHandleNonce` (BridgeTransfer.sol lines 149–155)**

`lowerHandleNonce` advances only while `handleNoncesToBlockNums[i] > 0` for every `i` in the contiguous window:

```solidity
for (i = lowerHandleNonce; i <= limit && handleNoncesToBlockNums[i] > 0; i++) {
    recoveryBlockNumber = handleNoncesToBlockNums[i];
    ...
}
lowerHandleNonce = i;
```

Because nonce N's entry is never written (tx reverted), the loop stops at `i = N`. `lowerHandleNonce` is permanently stuck at N. All `handleNoncesToBlockNums` entries for nonces > N accumulate and are never cleaned up (unbounded storage growth). [2](#0-1) 

**Root cause 3 — relay head-of-line blocking (`bridge_manager.go` lines 254–258)**

```go
if err := bi.handleRequestValueTransferEvent(ev); err != nil {
    bi.AddRequestValueTransferEvents(ReadyEvent[idx:])
    logger.Error("Failed handle request value transfer event", ...)
    return
}
```

On any Go-level submission error for nonce N (e.g., account nonce mismatch after a dropped tx, RPC error), the relay re-queues `ReadyEvent[idx:]` — starting at N — and returns. Nonces N+1, N+2, … are never processed until nonce N succeeds. [3](#0-2) 

**Root cause 4 — VT recovery infinite loop (`vt_recovery.go` lines 211, 224)**

The recovery hint uses `to.bridge.RecoveryBlockNumber(nil)` as the scan start and `to.bridge.LowerHandleNonce(nil)` as the handle nonce. Both are frozen at the pre-N state. Every recovery cycle re-discovers nonce N as pending, re-submits `handleKLAYTransfer` for it, and the on-chain tx reverts again. The loop never terminates. [4](#0-3) 

---

### Impact Explanation

- **`lowerHandleNonce` permanently frozen at N**: `handleNoncesToBlockNums` entries for all nonces > N are never deleted, causing unbounded on-chain storage growth.
- **`recoveryBlockNumber` frozen**: The recovery system scans from an old block forever, wasting RPC bandwidth and gas on always-reverting transactions.
- **Relay head-of-line blocking**: A Go-level submission failure on nonce N halts all subsequent bridge transfers until manual operator intervention.
- **KAIA bridge transfers delayed indefinitely**: Users whose transfers have nonces > N cannot receive their assets via the automated relay; they require manual operator action to bypass the stuck nonce.

This matches the allowed impact gate: unauthorized delay/blocking of KAIA bridge asset delivery and persistent corruption of bridge accounting state (`lowerHandleNonce`, `recoveryBlockNumber`, `handleNoncesToBlockNums`).

---

### Likelihood Explanation

Any user can trigger this by calling `requestKLAYTransfer` with `_to` set to a contract address that lacks a payable fallback (e.g., a multisig, a DAO treasury, or any ERC20 token contract). This is a normal user action — the user may not know the destination rejects KLAY. A malicious actor can do it deliberately as a griefing attack with only the cost of the request-side gas. No privileged access is required.

---

### Recommendation

1. **Pull-payment pattern**: Instead of pushing KLAY to `_to` inside `handleKLAYTransfer`, record the claimable amount in a mapping and let `_to` pull it. This eliminates the revert-on-delivery path entirely.

2. **Skip/quarantine on delivery failure**: If the low-level call returns `ok = false`, do not revert; instead move the nonce into a "failed" mapping, advance `lowerHandleNonce` normally, and emit a `HandleValueTransferFailed` event. Provide a separate function for the recipient to update their address and retry.

3. **Separate state commit from delivery**: Commit `handleNoncesToBlockNums[N]` and advance `lowerHandleNonce` unconditionally before the external call, so the nonce is always consumed regardless of delivery outcome.

---

### Proof of Concept

1. Deploy the bridge on a test network with sufficient KLAY liquidity.
2. Deploy a non-payable contract `Blocker` (no `receive`/`fallback`).
3. Call `requestKLAYTransfer(blockerAddress, 1 ether, "")` from any EOA on the source chain. This emits `RequestValueTransfer` with nonce N.
4. The bridge relay picks up the event and calls `handleKLAYTransfer(..., blockerAddress, 1 ether, N, ...)` on the destination bridge.
5. On-chain: `_to.call.value(1 ether)("")` returns `(false, "")` because `Blocker` has no payable fallback. `require(ok)` reverts. `handleNoncesToBlockNums[N]` remains 0.
6. Observe: `lowerHandleNonce` is stuck at N. `recoveryBlockNumber` does not advance.
7. Submit `handleKLAYTransfer` for nonce N+1 (a valid EOA recipient). It succeeds on-chain, but `_updateHandleNonce(N+1)` loops from `lowerHandleNonce = N`, hits `handleNoncesToBlockNums[N] == 0`, and stops. `lowerHandleNonce` remains N.
8. The VT recovery goroutine fires every `VTRecoveryInterval` seconds, re-discovers nonce N as pending (since `lowerHandleNonce == N`), re-submits, and reverts again — indefinitely.
9. The relay's `processingPendingRequestEvents` loop, on any Go-level error for nonce N, re-queues `ReadyEvent[idx:]` and returns, blocking nonces N+1, N+2, … from being relayed.
