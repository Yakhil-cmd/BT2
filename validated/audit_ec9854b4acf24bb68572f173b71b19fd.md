### Title
Stack-scoped ApiClient can read the deploy status of any stack via `/api/stacks/:stack_id/ccmenu` - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Api::CCMenuController` overrides the base controller's stack-scoping logic and resolves the requested stack directly from the URL parameter, bypassing the `ApiClient#stack_id` restriction that every other stack-scoped API endpoint enforces.

### Finding Description
Every other stack-scoped API controller resolves the target stack via `Api::BaseController#stack`, which is built on `stacks`, and that method binds the token to a *specific* stack when `current_api_client.stack_id?` is true: [1](#0-0) 

For example `Api::StacksController#stack` uses this scoped `stacks` relation: [2](#0-1) 

`Api::CCMenuController`, however, defines its own private `stack` method that queries `Stack.from_param!(params[:stack_id])` directly, never going through `stacks`/`current_api_client.stack_id`: [3](#0-2) 

The permission check only verifies the coarse-grained `read:stack` permission flag on the token, not that the specific stack being accessed matches the token's bound `stack_id`: [4](#0-3) [5](#0-4) 

This is exactly the "a stack a token authorises versus a stack it touches" binding: `ApiClient.stack_id` is the stack the token is supposed to be scoped to, but `CCMenuController#stack` lets the request determine which stack is actually touched, with no intersection check between the two.

The route confirms `stack_id` is attacker-controlled and not otherwise constrained to the token's own stack: [6](#0-5) 

### Impact Explanation
An `ApiClient` token that was deliberately scoped to a single stack (e.g. `stack_id` set, with only `read:stack` permission — the common "least privilege" configuration described in `docs`/README and exercised by fixtures such as `here_come_the_walrus`) can be used to read the CCMenu status (`lastBuildStatus`, `lastBuildLabel`, `webUrl`, activity, lock status, etc.) of **any** stack in the installation, not just the one it was issued for. This is cross-repository/cross-stack information disclosure of deploy/build state and lock state via an under-privileged, narrowly-scoped credential — matching the "unauthorized read of stack state" High-impact category.

### Likelihood Explanation
Likelihood is high for any deployment that issues stack-scoped `ApiClient` tokens (a documented, intended use case per `ApiClient.belongs_to :stack, optional: true` and the `stacks` scoping logic in `BaseController`). Any holder of such a token — which by design is meant to be handed to lower-trust integrations/CI systems for a single stack — can simply substitute a different `stack_id` in the URL; no additional privileges or secrets are needed. The route pattern accepts any stack identifier without server-side scoping.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the scoped `stacks` relation from `BaseController` instead of calling `Stack.from_param!` directly, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
This removes the need for a controller-specific override and ensures `ApiClient.stack_id` scoping is enforced consistently everywhere a stack is resolved from client input.

### Proof of Concept
1. Create two stacks, `stack-A` and `stack-B`.
2. Create an `ApiClient` scoped to `stack-A` only (`stack: stack-A`, `permissions: ['read:stack']`) — analogous to the `here_come_the_walrus` fixture: [7](#0-6) 
3. Authenticate with that token and request:
   ```
   GET /api/stacks/<stack-B-owner>/<stack-B-repo>/<stack-B-env>/ccmenu
   Authorization: Basic <base64(token)>
   ```
4. `CCMenuController#authenticate_api_client` accepts the token and `require_permission :read, :stack` passes because the token does have `read:stack` (just not for `stack-B`).
5. `CCMenuController#stack` resolves `stack-B` directly via `Stack.from_param!`, ignoring the token's `stack_id` restriction, and returns `stack-B`'s CCMenu XML (build status, last deploy, lock state) even though the token was only meant to see `stack-A`.
