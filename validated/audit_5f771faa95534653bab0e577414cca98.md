### Title
Webhook Signature Key Is Selected by `repository.owner.login`/`organization.login` While Every Handler Resolves the Target Repository by `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App/organization's `webhook_secret` to validate the HMAC signature against by reading `repository.owner.login` (or `organization.login`) straight out of the unauthenticated JSON body. Every event handler, however, resolves the actual `Shipit::Repository`/`Stack` to act on using a completely different field of the same body: `repository.full_name`. Because these two fields are never cross-checked, a valid signature computed with organization A's `webhook_secret` can carry a `repository.full_name` pointing at organization B's repository, and Shipit will write to B's stacks using a signature that only proves knowledge of A's secret.

### Finding Description
`verify_signature` derives the signing organization purely from payload content: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the per-organization config (`webhook_secret`, etc.) that was configured under the "Multiple GitHub Applications" feature, where each organization owner independently creates their own GitHub App and sets their own webhook secret: [3](#0-2) [4](#0-3) 

Once the HMAC check passes, control passes to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` with the raw, unmodified JSON body. Every handler built on the base `Handler` class resolves its target `Repository`/`Stack` using a *different* field — `repository.full_name` — not the `repository.owner.login`/`organization.login` value that gated the signature check: [5](#0-4) 

The same disjoint pattern repeats in every pull-request handler (`OpenedHandler`, `ClosedHandler`, `ReopenedHandler`, `LabeledHandler`, `UnlabeledHandler`, `AssignedHandler`, `EditedHandler`, `LabelCapturingHandler`), all of which call `Shipit::Repository.from_github_repo_name(params.repository.full_name)` to find the repository they will mutate: [6](#0-5) 

Nowhere in the request lifecycle is `repository.full_name` compared to `repository.owner.login`/`organization.login`. The binding the code implicitly assumes — "the organization whose secret authenticated this request" == "the organization that owns the repository the handler writes to" — is never enforced.

### Impact Explanation
In a multi-tenant Shipit deployment (the officially documented "Multiple GitHub Applications" setup), each onboarded organization's administrator creates and controls their own GitHub App, including its `webhook_secret`, and supplies it to the Shipit operator to be placed under their own key in `secrets.yml`. That administrator therefore legitimately knows the exact secret Shipit uses to authenticate traffic attributed to their org (`repository.owner.login == their-org`). Because handlers key off `repository.full_name` instead, that administrator can POST a hand-crafted JSON body directly to `/webhooks` with:
- `repository.owner.login` (or `organization.login`) = their own organization (so `verify_signature` selects and validates against a secret they know), and
- `repository.full_name` = `"victim-org/victim-repo"` (so the handler resolves and mutates a stack that belongs to a different tenant).

Depending on the event chosen, this yields unauthorized cross-tenant writes: `PushHandler` can force-sync a victim stack to an attacker-chosen `expected_head_sha` (`sync_github`), and the PR handlers can archive/unarchive review stacks, mutate pull-request state, or create arbitrary `Shipit::User`/`Membership` records tied to the victim's repositories/organizations — all without ever holding credentials for the victim organization. This is a cross-repository/cross-tenant write achieved purely by exploiting the mismatch between the authentication key selection and the resource the request is allowed to act on.

### Likelihood Explanation
This requires the Shipit instance to be configured for multiple GitHub organizations (`Shipit.github_default_organization` present, i.e. the multi-org secrets schema documented in `docs/setup.md`), and requires the attacker to be a legitimate administrator of at least one onboarded (but otherwise unprivileged with respect to other tenants') organization who knows their own org's `webhook_secret` — a scenario the multi-tenant feature explicitly enables by design. No `ApiClient` token, GitHub App private key, or victim credentials are needed; only the attacker's own org's webhook secret, which they set themselves when creating their GitHub App.

### Recommendation
Bind the two identities together explicitly: after `verify_signature` succeeds for a given `repository_owner`, require that `Handler#repository_name`'s owner segment matches the authenticated `repository_owner`/organization before any handler is permitted to act, e.g. compare `payload.dig('repository','full_name')&.split('/')&.first` (or the equivalent org login) against the `repository_owner` used to select the HMAC key, and reject the request (422) on mismatch.

### Proof of Concept
1. Deploy Shipit with the multi-org `github:` secrets schema, onboarding organizations `attacker-org` and `victim-org`, each with their own `webhook_secret` (per `docs/setup.md`, "Using Multiple Github Applications").
2. As the administrator of `attacker-org` (who legitimately knows `attacker-org`'s `webhook_secret` because they created that GitHub App), craft a `push` event JSON body:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen-sha>",
     "repository": {
       "full_name": "victim-org/victim-repo",
       "owner": { "login": "attacker-org" }
     }
   }
   ```
3. Compute `X-Hub-Signature: sha1=HMAC-SHA1(attacker-org-webhook-secret, body)` and POST it to `/webhooks` with header `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")`, finds the signature valid, and lets the request through.
5. `Shipit::Webhooks::Handlers::PushHandler#stacks` resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github(expected_head_sha: params.after)` on `victim-org`'s stacks — a write triggered on a repository the requester never authenticated for.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
