### Title
RAY value overflow during interest accrual permanently freezes an oversized market - (File: common/src/rates/scaling.rs)

### Summary
An unprivileged user can create an admissible whale market by supplying and borrowing very large balances; as the borrow index grows, `borrowed * borrow_index / RAY` or `supplied * supply_index / RAY` exceeds `i128` and accrual reverts before it can commit. [1](#0-0)  Every pool money operation loads the market through `synced_market`, which invokes `global_sync` before processing the requested operation. [2](#0-1)  The result is a permanent freeze of that market, including withdrawals, repayments, and liquidations. [3](#0-2) 

### Finding Description
The accrual step converts scaled debt and supply into RAY values via `scaled_to_original`. [4](#0-3)  `scaled_to_original` delegates to `Ray::mul`, which returns an overflowing `MathOverflow` rather than bounding the resulting value. [5](#0-4)  Interest is accrued in chunks and committed only after all chunks complete, so once any required chunk overflows, `last_timestamp` cannot advance and later calls repeat the same failing calculation. [6](#0-5) 

A valid configuration can admit balances whose RAY value initially fits but later exceeds `i128::MAX` before either index reaches its protocol ceiling. [7](#0-6)  The repository’s test creates a one-billion-whole-token, 18-decimal market at 98% utilization, advances accrual, observes `MATH_OVERFLOW`, and confirms that withdrawal and repayment subsequently fail. [8](#0-7) 

### Impact Explanation
All suppliers’ funds and unclaimed yield in the affected market become permanently inaccessible because withdrawals load and accrue the market before debiting cash or transferring tokens. [9](#0-8)  Borrowers cannot repay or close positions, and liquidators cannot reduce risk, because those paths perform the same accrual first. [10](#0-9)  This affects one `(hub_id, asset)` book, but the freeze is permanent rather than a transient failed transaction.

### Likelihood Explanation
Exploitation requires a very large token balance and sufficient collateral: the demonstrated setup supplies `1_000_000_000 * 10^18` units and borrows 98% of it. [11](#0-10)  It also requires an admitted market with caps and a rate curve that can drive the index beyond the representable market-value threshold; the tested curve is within the protocol’s documented parameter domain and uses a 175% maximum borrow rate. [12](#0-11)  Once such exposure exists, the attacker only needs to let time pass and call the permissionless controller `update_indexes` path for the market. [13](#0-12) 

### Recommendation
Enforce a market-value ceiling during accrual instead of allowing `scaled * index` to overflow, or constrain admitted scaled totals and index ceilings so every valid market remains representable throughout its lifetime. [14](#0-13)  Add a conservative recovery path that can stop interest and permit withdrawals/repayments after saturation, because the current “accrue before every mutation” design provides no route around the overflow. [2](#0-1)  The effective bound should account for future index growth rather than only validating that the initial deposit conversion fits `i128`. [15](#0-14) 

### Proof of Concept
The existing harness demonstrates the issue with a large 18-decimal market and a separate collateral market. [16](#0-15) 

```rust
// Market BIG18 has the tested 175%-maximum XLM curve and lifted caps.
let principal = 1_000_000_000i128 * 10i128.pow(18);
supply(alice, account_id, spoke_id, vec![(BIG18_key, principal)]);
supply(alice, account_id, spoke_id, vec![(COL_key, 3_000_000_000 * 10_000_000)]);
borrow(
    alice,
    account_id,
    vec![(BIG18_key, principal / 100 * 98)],
    None,
);

// Advance ledger time, then repeatedly call:
update_indexes(vec![BIG18_key]);

// Once borrowed * borrow_index / RAY exceeds i128::MAX:
//   update_indexes(...) -> MathOverflow
//   withdraw(..., 1)    -> MathOverflow
//   repay(..., amount)  -> MathOverflow
//   liquidate(...)      -> MathOverflow
```

The test verifies that the borrow index remains below `MAX_BORROW_INDEX_RAY`, proving that the unchecked RAY value product overflows before the explicit index ceiling can protect the market. [17](#0-16)

fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();

| Borrow APR maximum 2 RAY | 200% annual rate; not a bound on balance growth alone |
| Token-to-RAY input maximum `i128::MAX / 10^(27-d)` | About 170.14 billion whole tokens, before other limits |
| Deposit conversion at the supply-index floor | About 170.14 million whole tokens before scaled-share overflow |

The token-to-RAY maximum is also the admitted cap maximum. Accrued position
values and market totals must independently fit the RAY domain; valid caps and
bounded indexes do not guarantee that future accrual fits. Value overflow can
occur before the index ceiling and block repayment/withdrawal because those
operations accrue first. At the borrow-index ceiling, further accrual produces
no borrower interest. No dedicated ceiling alarm is emitted.

pub fn update_supply_index(env: &Env, supplied: Ray, old_index: Ray, rewards_increase: Ray) -> Ray {
    if supplied == Ray::ZERO || rewards_increase == Ray::ZERO {
        return old_index;
    }

    let total_supplied_value = supplied.mul(env, old_index);

    if total_supplied_value == Ray::ZERO {
        return old_index;
    }

    let new_value = total_supplied_value.checked_add(env, rewards_increase);
    let grown = fp_core::mul_div_floor_saturating(env, new_value.raw(), RAY, supplied.raw());

    let bounded_old = old_index.raw().min(MAX_SUPPLY_INDEX_RAY);
    Ray::from(grown.min(MAX_SUPPLY_INDEX_RAY).max(bounded_old))
