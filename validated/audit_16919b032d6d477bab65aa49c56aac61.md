### Title
ERC20 asset transactor trusts nominal transfer `amount` instead of measured balance delta, allowing fee-on-transfer/rebasing tokens to desynchronize `AssetsInHolding` credit from actual holdings - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `ERC20Transactor::deposit_asset_with_surplus` implement the XCM `TransactAsset` trait for ERC20-style tokens deployed as `pallet-revive` smart contracts [1](#0-0) . Both functions call the token contract's `transfer()` function with the nominal `amount` extracted from the XCM `Asset`, and on a `true` boolean return value they unconditionally treat `amount` as the amount actually moved — exactly the "rebase/FoT tokens are not supported" pattern from the reported Blueberry bug, where `amount` transferred is assumed to equal `amount` requested without checking the real balance delta of the receiving account.

### Finding Description
In `withdraw_asset_with_surplus`, the transactor calls `IERC20::transferCall{ to: checking_address, value: amount }` on the caller's declared ERC20 contract (`asset_id`) [2](#0-1) . If the call does not revert and the ABI-decoded return value is `true`, the code immediately mints an `Erc20Credit(amount)` into the returned `AssetsInHolding`, without ever reading the checking account's actual token balance before/after the call [3](#0-2) .

Symmetrically, `deposit_asset_with_surplus` calls `transfer()` from the checking account to the beneficiary for the nominal `amount`, and on `true` simply reports success — again without verifying the beneficiary actually received `amount` [4](#0-3) .

Because the "ERC20" contract at `asset_id`/`asset_contract_id` is arbitrary bytecode deployed via `pallet_revive::Pallet::<T>::bare_call` (i.e., any contract a user has deployed, not a pallet-native asset with guaranteed 1:1 ledger semantics like `pallet_assets`), nothing in this code path prevents the contract from implementing:
- a fee-on-transfer `transfer()` that moves less than `value` to `to` but still returns `true`,
- a rebasing balance model where the checking/beneficiary account's realized balance differs from `value`.

`ERC20Transactor` is wired into the real runtime as the `TransactAsset` handler for ERC20 tokens in `cumulus/parachains/runtimes/assets/asset-hub-westend/src/xcm_config.rs` (confirmed via reference to `ERC20Transactor` there), so this is production runtime code reachable through ordinary XCM `WithdrawAsset`/`DepositAsset` execution (e.g. via `pallet_xcm::execute` or incoming XCM programs), not test/mock-only code.

The comment on `Erc20Credit` explicitly acknowledges the design assumption that is violated here: *"the actual balance constraints are enforced by the ERC20 smart contract itself rather than the runtime"* [5](#0-4)  — i.e., the runtime's `AssetsInHolding` bookkeeping (`amount`) can silently diverge from what the ERC20 contract actually moved, exactly analogous to `BlueBerryBank.lend` crediting `pos.underlyingAmount` with the nominal `amount` instead of the measured `uBalanceAfter - uBalanceBefore` delta that `SoftVault`/`HardVault` correctly compute.

### Impact Explanation
If the underlying ERC20 contract behind `asset_id` moves less value than requested during `withdraw_asset_with_surplus` (fee-on-transfer) while still returning `true`, the XCM executor's in-memory `AssetsInHolding` will hold a credit larger than what is actually sitting in the checking account. Subsequent XCM instructions in the same program (e.g. `DepositAsset`, `InitiateTransfer`) that consume this holding can then attempt to move/credit more tokens than physically exist in the checking account, producing an accounting break between the runtime's XCM holding register and the ERC20 contract's real balances. This is a token-accounting integrity issue rather than a straightforward drain, and its severity depends on whether such a mismatched credit can be laundered into a double-spend (e.g., depositing the inflated credit to a beneficiary while the checking account's real balance is short), which would constitute unbacked issuance.

### Likelihood Explanation
Likelihood depends entirely on whether the `Matcher: MatchesFungibles<H160, u128>` configured for `ERC20Transactor` in `asset-hub-westend/src/xcm_config.rs` permits arbitrary user-deployed contract addresses as valid "asset ids," or whether it is restricted to a governance-curated allowlist of trusted/audited ERC20 contracts. I was not able to inspect that Matcher configuration before running out of tool budget, so I cannot confirm whether an attacker (with no privileged role) can register/target an arbitrary self-deployed fee-on-transfer contract as the `asset_id` for this transactor. If the Matcher is unrestricted (any deployed contract address matches), likelihood is high, since `pallet_revive` contract deployment is a normal permissionless user entry point. If the Matcher enforces an allowlist, this finding would not be practically exploitable without a privileged asset-registration step.

### Recommendation
In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, read the checking/beneficiary account's ERC20 balance immediately before and after the `transfer()` call (the same pattern already used correctly for native-token deposits in `substrate/frame/revive/src/exec.rs`'s dust-aware transfer logic, and analogous to `SoftVault.deposit`'s `uBalanceBefore`/`uBalanceAfter` delta), and use that measured delta — not the requested `amount` — when constructing `Erc20Credit` in `AssetsInHolding` or when reporting success for a deposit.

### Proof of Concept
No executable PoC was run. Reachability could not be fully confirmed within the available tool budget: I located and read the vulnerable trust-boundary code in `erc20_transactor.rs` and confirmed `ERC20Transactor` is instantiated in the live `asset-hub-westend` XCM configuration, but I was unable to inspect the concrete `Matcher` type used there to determine whether arbitrary user-deployed `pallet_revive` contracts (attacker-controlled bytecode, no privileged role required) can be registered/matched as the `asset_id`/`asset_contract_id` for this transactor. Without confirming that the Matcher accepts attacker-chosen contract addresses, this should be treated as a credible analog with an open verification item (Matcher restrictiveness), not a fully proven exploit chain.

/// A minimal imbalance tracking type that holds an ERC20 token amount.
///
/// This type implements the necessary imbalance accounting traits but does not perform
/// runtime-level balance enforcement. It's used to track ERC20 token amounts within XCM
/// asset holdings, where the actual balance constraints are enforced by the ERC20 smart
/// contract itself rather than the runtime.
struct Erc20Credit(u128);
impl UnsafeConstructorDestructor<u128> for Erc20Credit {
	fn unsafe_clone(&self) -> Box<dyn ImbalanceAccounting<u128>> {
		Box::new(Erc20Credit(self.0))
	}
	fn forget_imbalance(&mut self) -> u128 {
		let amount = self.0;
		self.0 = 0;
		amount
	}
}
