### Title
Webhook signature verification is bound to `repository.owner.login`, while every event handler acts on `repository.full_name` — allowing cross-organization forged webhooks and unauthorized syncs/deploys - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate a payload against using the attacker-controlled JSON field `repository.owner.login` (or `organization.login`), while every `Handler` (e.g. `PushHandler`) resolves the actual `Stack`/`Repository` to act on using a *different* attacker-controlled field, `repository.full_name`. In a multi-organization Shipit deployment (supported natively, see `config/secrets.development.shopify.yml`), these two fields are never checked for consistency, so a payload can be validly signed with org A's secret while acting on org B's repository.

### Finding Description
`verify_signature` picks the GitHub App config to validate against like this: [1](#0-0) 

`repository_owner` is derived purely from the JSON body: [2](#0-1) 

`Shipit.github(organization: repository_owner)` returns an org-specific `GithubApp` instance carrying that org's own `webhook_secret` (multiple orgs, each with independent secrets, is an explicitly supported configuration): [3](#0-2) [4](#0-3) 

Once the signature check passes, `create` dispatches the *raw, attacker-supplied* `params` to every registered handler for the event, with no re-validation: [5](#0-4) 

But handlers resolve the actual repository/stack to operate on via a **different** field, `repository.full_name`, not `repository.owner.login`: [6](#0-5) 

`PushHandler`, for example, uses that mismatched-field-derived `stacks` collection to trigger a real GitHub sync against whatever stack matches `full_name`: [7](#0-6) 

**The broken equality:** "organization whose `webhook_secret` cryptographically authenticated the payload" (`repository.owner.login`) should equal "organization/repository the payload's effects are applied to" (`repository.full_name`). Nothing in `WebhooksController` or `Handler` enforces this. An operator of any one organization configured on the shared Shipit instance (i.e., whoever created/administers that org's GitHub App and therefore knows its `webhook_secret`) can craft an arbitrary JSON body where:
- `repository.owner.login` = their own org (so `verify_signature` selects and validates against a secret they legitimately know), and
- `repository.full_name` = `victim-org/victim-repo` (any other repo tracked by this Shipit instance).

Because the HMAC only proves "signed with *some* org's secret", and the controller lets the payload itself choose *which* org's secret is checked, the signature provides no binding between the authenticated identity and the resource being mutated.

### Impact Explanation
This crosses the "an organization that authenticated versus the repository that is written" boundary explicitly called out as in-scope. Concretely, an attacker who controls one tenant org's GitHub App secret can forge `push`, `pull_request`, `status`, `check_suite`, or `membership` events against **any other organization's repository/stack** hosted on the same Shipit instance:
- `push` → forces `stack.sync_github` on a victim stack; if the victim stack has continuous deployment enabled and the attacker references a real existing commit SHA on the victim repo (public info via GitHub), this can trigger an **unauthorized deploy** of that stack.
- `pull_request`/`membership`/`status` handlers can similarly manipulate merge status, team memberships, or CI state for a repository the attacker does not own — a **cross-repository write**.

This qualifies as Critical/High under the listed impact categories (cross-repository writes, unauthorized deploy).

### Likelihood Explanation
Requires the deployment to configure more than one GitHub organization (a documented, supported configuration pattern in this engine — see `config/secrets.development.shopify.yml` and `docs/setup.md`), and requires the attacker to be a legitimate administrator of at least one of those configured orgs' GitHub Apps (i.e., they know that org's own `webhook_secret`). No Shipit session, `ApiClient` token, or repository write access on the victim repo is needed — only knowledge of one's own org's webhook secret, which is the normal level of access an onboarded tenant org has.

### Recommendation
`verify_signature` must not let the payload dictate which secret validates itself independent of what the payload will actually be used to act upon. Concretely:
- Bind webhook handling to a single, out-of-band-verified identity: derive the organization for secret selection from the same field (`repository.full_name`'s owner segment) that `Handler#repository_name` actually uses, not from a separately-trusted `repository.owner.login`/`organization.login` field.
- Optionally, after verifying the signature, re-validate that the resolved `Repository`/`Stack.repository.owner` matches the `repository_owner` that selected the signing secret, and reject on mismatch.

### Proof of Concept
1. Configure two orgs, `attacker-org` and `victim-org`, each with its own GitHub App/`webhook_secret` on the same Shipit instance (per `config/secrets.development.shopify.yml` pattern). Assume `victim-org/victim-repo` already has a Shipit `Stack` with continuous deployment enabled.
2. Attacker, who legitimately administers `attacker-org`'s GitHub App, knows `attacker-org`'s `webhook_secret`.
3. Attacker crafts a `push` event JSON body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<a real existing commit sha on victim-org/victim-repo>",
     "repository": {
       "owner": { "login": "attacker-org" },
       "full_name": "victim-org/victim-repo"
     }
   }
   ```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org_webhook_secret, body)>` and POSTs to `/github/webhooks` (`WebhooksController#create`) with `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: 'attacker-org')` (from `repository.owner.login`) and the HMAC matches — verification succeeds.
6. `PushHandler#process` resolves `stacks` via `repository.full_name` = `victim-org/victim-repo`, and calls `stack.sync_github(expected_head_sha: ...)` on the victim's stack — triggering an unauthorized sync/deploy of a repository the attacker does not own or control.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
