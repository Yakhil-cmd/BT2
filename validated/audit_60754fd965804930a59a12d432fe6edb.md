### Title
Indirect Correspondent Scope-Gate Is Disabled, Allowing an Untrusted Multi-Device Cosigner to Send Arbitrary Wallet-Protocol Messages - ([File: wallet.js])

### Summary
`addIndirectCorrespondents()` in `device.js` auto-registers "other cosigners" of a shared/multisig address as full correspondent devices (`is_indirect=1`) without any pairing-secret handshake performed by the local user. `handleMessageFromHub()` in `wallet.js` is supposed to gate what such indirectly-added, unvetted devices are allowed to request — but that gate is commented out, so every device-protocol `subject` (create/approve shared address, `sign`, `private_payments`, `arbiter_dispute_request`, etc.) is processed exactly as if it came from an explicitly, manually paired device.

### Finding Description
`addIndirectCorrespondents` inserts a correspondent row with `is_indirect=1` for every "other cosigner" address supplied when a multi-device shared address is being negotiated: [1](#0-0) 

This path is reachable without the local user ever scanning/exchanging a pairing QR code with the new correspondent — the pubkey/hub/name are taken from data supplied during shared-address setup (`create_new_shared_address` / `new_shared_address` messages), i.e., effectively attacker-controlled once any single hop of trust exists.

`handleMessageFromHub` receives `bIndirectCorrespondent` (derived from `correspondent_devices.is_indirect`, see `device.js:204-211`) and was designed to restrict what an indirectly-known device can make the local node do. That restriction, however, is disabled: [2](#0-1) 

Because the check is commented out, an indirect correspondent can send *any* subject that a fully-vetted correspondent could send, including:
- `sign` — requesting the local wallet to co-sign an arbitrary unit/shared-address transaction, including one bearing private payment payloads [3](#0-2) 
- `create_new_shared_address` / `approve_new_shared_address` / `new_shared_address` — creating shared addresses whose signing paths are attributed to the local device [4](#0-3) 
- `private_payments` and `arbiter_dispute_request` handling, which decrypt and process attacker-supplied encrypted content and unit data [5](#0-4) [6](#0-5) 

This is a direct structural analog of the OpenClaw advisory: a "device-paired" (here, indirectly/auto-paired) peer is meant to be confined by a scope gate limited to a narrow whitelist of subjects, but the gate enforcement was disabled, so the paired-but-unvetted peer gets the same trust level as a fully authenticated correspondent and can drive the node's signing/wallet logic.

### Impact Explanation
An indirect correspondent that should only be trusted for shared-address bootstrap messages can instead trigger the full device-message surface, including requesting the local wallet to sign transactions (`sign`), manipulate shared/multisig address negotiation, and process crafted `private_payments`/`arbiter_dispute_request` content. In multi-device or multisig wallet setups this can lead to unauthorized signing requests being surfaced to the user under misleading pretenses, corruption of shared-address bookkeping, or being tricked into approving attacker-controlled shared addresses/private payment chains — i.e., a path toward unauthorized spending or fund loss for cosigned wallets. This matches the "unauthorized spending" / "AA-fund-loss"-class impact required by the scan rules, reached purely through a paired-device message path (no p2p/hub-only attack, no leaked keys required).

### Likelihood Explanation
Reaching this requires the victim to already have some multi-device/multisig wallet relationship (so that `addIndirectCorrespondents` is invoked for the attacker's device address), which is a normal, expected workflow (Obyte multisig/shared wallets, arbiter contracts). No manual pairing-code exchange with the attacker is needed — the indirect correspondent is added automatically as a side effect of shared-address setup messages. Given the commented-out check is the *only* mechanism meant to constrain such indirect correspondents, likelihood is high once any shared-address relationship involving the attacker's device exists.

### Recommendation
Re-enable and correctly scope the indirect-correspondent restriction in `handleMessageFromHub` (currently commented out at `wallet.js:92-93`): explicitly whitelist only the subjects strictly required for shared-address bootstrap (e.g. `cancel_new_wallet`, `my_xpubkey`, `new_wallet_address`, and the minimal shared-address negotiation subjects) for any correspondent with `is_indirect=1`, and reject/ignore all other subjects (`sign`, `private_payments`, `arbiter_dispute_request`, `signature`, etc.) from such correspondents until the user performs an explicit trust-elevating action (e.g., direct pairing or explicit approval).

### Proof of Concept
1. Attacker becomes an "other cosigner" in a multi-device shared-address setup with the victim (e.g., is listed in `address_definition_template` during `create_new_shared_address`/`new_shared_address` flow), causing `device.addIndirectCorrespondents` to insert the attacker's device as `correspondent_devices` with `is_indirect=1` — no manual pairing performed by the victim.
2. Attacker's device (now a known, if indirect, correspondent) sends a `hub/message` with `subject: "sign"` and a `body.unsigned_unit` designed to make the victim's wallet sign a transaction favorable to the attacker (e.g., spending shared funds), or sends `subject: "private_payments"` with crafted private payload chains.
3. In `handleMessageFromHub` (`wallet.js`), since the disabling comment means `bIndirectCorrespondent` is never checked, the message is processed identically to a message from a manually, fully-paired correspondent, invoking `findAddress`/signing-request flow and surfacing a signing dialog or otherwise processing the attacker payload as trusted correspondent content.
