## Title
Unhandled exception during AA trigger processing permanently jams the shared `aa_triggers` FIFO queue, halting all AA execution network-wide - ([File: aa_composer.js])

## Summary
`handleAATriggers()` processes every pending AA trigger from the global `aa_triggers` table in one deterministic, ordered `async.eachSeries` loop, deleting a row only after its trigger has been fully and successfully processed. Multiple code paths reachable while composing an ordinary (non-error) AA response contain bare `throw Error(...)` statements instead of routing the failure through the existing `bounce()`/error-callback mechanism. If any one of those paths is hit for a given trigger, the exception is not caught anywhere in the callback chain, the row is never deleted from `aa_triggers`, and because the same DAG state is processed identically by every full node, the very next call to `handleAATriggers()` (on this or any other node, or after a restart) re-encounters the same trigger and fails again — permanently blocking the processing of that trigger and, because it sits in a strict ordering, of every subsequently queued trigger for every AA on the network. This mirrors the reported OpenZeppelin ERC1155 callback-DOS pattern (single unprocessable queue item blocking an entire relayer FIFO queue), but with a much larger blast radius: instead of freezing one vault's deposit queue, it can freeze the entire network's ability to execute AA responses (and, since `handleAATriggers` is awaited synchronously inside `writer.saveJoint`'s MC-stabilization flow, potentially block further unit confirmation as well).

## Finding Description
`handleAATriggers()` reads all pending rows from `aa_triggers`, ordered deterministically, and feeds them one at a time into `handlePrimaryAATrigger()` via `async.eachSeries`: [1](#0-0) 

A row is deleted from `aa_triggers` only after `handleTrigger()` finishes and calls back into `handlePrimaryAATrigger`'s success path: [2](#0-1) 

Inside `handleTrigger()` and its helper functions, several invariant checks are enforced with a bare `throw Error(...)` rather than being routed to `bounce()`/`cb(err)`, even though they sit on paths exercised while normally composing an AA's response unit — for example:

- `pickParents()`, called whenever an AA needs to post a non-bounce response unit: [3](#0-2) 
- `validateAndSaveUnit()`, which validates and saves the AA's freshly composed response unit and throws on several conditions instead of failing gracefully: [4](#0-3) 
- `updateInitialAABalances()`'s storage-size lookup: [5](#0-4) 

None of these throws are wrapped in try/catch anywhere in the call chain, and they occur inside asynchronous DB-driver callbacks (`conn.query(..., function(rows){ ... throw ... })`), so the exception propagates out of the Node.js event loop as an unhandled exception rather than being caught by `handleAATriggers`'s `async.eachSeries` error handler.

Because trigger processing is fully deterministic given identical DAG state, every node that reaches the same stabilized MCI will hit the same throw. And because the offending `aa_triggers` row is never deleted (the DELETE only runs after successful completion), the *same* row is re-selected by the very next `ORDER BY aa_triggers.mci, level, aa_triggers.unit, address` query and causes the identical crash/hang again — including after a process restart, since the trigger persists in the DB.

Crucially, `handleAATriggers()` is invoked synchronously as part of `writer.saveJoint()`'s MC-stabilization sequence: [6](#0-5) 

so a stuck trigger can also stall further stabilization/unit-writing flow on the node, not merely AA execution.

## Impact Explanation
This is the direct structural analog of the reported bug: a single unprocessable item in a strictly-ordered processing queue blocks the entire queue with no way to skip or recover it (there is no `try/catch` around trigger processing and no side-channel withdrawal for a stuck trigger). The impact here is broader than the original report because:
- `aa_triggers` is a single shared, network-wide, strictly-ordered queue (not one queue per vault), so one bad trigger for AA-A blocks all pending/future responses for every other AA as well.
- The failure is deterministic and reproducible by every full node, so it is not merely a local liveness bug — it can stop AA processing (and potentially further unit confirmation) network-wide, matching the "network unable to confirm new units" / "AA fund loss or freezing" impact classes.
- Persisting the trigger row means the fault survives node restarts, requiring a manual DB intervention/hotfix to clear.

## Likelihood Explanation
Reaching one of these invariant-violation throws requires an attacker to construct a unit/trigger whose processing lands on one of the un-bounced `throw` branches (e.g., forcing `validateAndSaveUnit`'s `ifNeedParentUnits`/`nonserial AA`/`ifJointError` paths, or a DAG parent-selection edge case hit by `pickParents`). These are deliberately marked in the code as conditions that "should never happen" in normal operation, which indicates they are edge-case invariants rather than hardened, user-input-validated branches — precisely the kind of edge case a determined attacker crafting AA trigger units/parents can attempt to surface. The architectural weakness itself (no isolation between individual trigger failures and the shared FIFO queue) is unconditionally present regardless of which specific throw is used to trigger it.

## Recommendation
- Wrap the body of `handlePrimaryAATrigger`/`handleTrigger` execution in a top-level `try/catch` (or attach `process.on('uncaughtException')`-safe guards) so that any unexpected error converts into a graceful bounce or a safely-skippable failure state, instead of an unhandled exception.
- Persist a retry/failure counter per `aa_triggers` row, and provide a mechanism (e.g., after N failed attempts) to move the failing trigger out of the main FIFO path (dead-letter handling) so it cannot indefinitely block all other pending triggers, mirroring the fix recommended in the original report (dirty try/catch + separate failed-queue handling).
- Replace bare `throw Error(...)` invariant checks reachable from trigger execution (`pickParents`, `validateAndSaveUnit`, `updateInitialAABalances`, etc.) with calls into the existing `bounce()`/`revert()` error paths wherever the condition can plausibly be influenced by attacker-controlled unit/trigger content.

## Proof of Concept
1. Craft a unit that sends a payment to an AA address such that, during composition of that AA's response, one of the un-bounced invariant checks in `aa_composer.js` (e.g. `pickParents`'s `"limci of last AA > mci"`, or one of `validateAndSaveUnit`'s `ifJointError`/`ifNeedParentUnits`/`nonserial AA` branches) is triggered instead of hitting `bounce()`.
2. The unit becomes stable; `writer.saveJoint()` inserts the corresponding row into `aa_triggers` and calls `aa_composer.handleAATriggers()` [6](#0-5) .
3. `handleAATriggers()`'s `async.eachSeries` reaches this row, `handleTrigger()` throws inside a DB callback, and the exception is unhandled — the row is never `DELETE`d from `aa_triggers` [2](#0-1) .
4. Every subsequent call to `handleAATriggers()` (triggered by any later unit stabilization on any node) re-selects the same stuck row first (per the `ORDER BY` clause) [7](#0-6) , and fails identically, permanently starving all other queued and future AA triggers across the network.
