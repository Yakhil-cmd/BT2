### Title
Missing `return` after error path causes double invocation of the async callback and use of an uninitialized `json_payload_hash` in private-payment validation - ([File: network.js])

### Summary
In `handleSavedPrivatePayments()`, the inner `validateAndSave()` function computes `json_payload_hash` inside a `try` block. If `objectHash.getBase64Hash()` throws, the `catch` block logs the error, notifies the peer, and calls `deleteHandledPrivateChain(..., cb)` — but does **not** `return`. Execution falls through to the code below the try/catch, which builds `key` using the now-`undefined` `json_payload_hash`, and then unconditionally calls `privatePayment.validateAndSavePrivatePaymentChain(...)`, whose `ifOk`/`ifError`/`ifWaitingForChain` callbacks each also invoke `cb` (via `deleteHandledPrivateChain` or directly). This is analogous to the reported bug class (CWE-824/access-before-init): a value that should only be used after successful initialization is instead used (and the completion callback is invoked twice) once initialization fails.

### Finding Description [1](#0-0) 

The relevant code:
```js
var validateAndSave = function(){
    var objHeadPrivateElement = arrPrivateElements[0];
    try {
        var json_payload_hash = objectHash.getBase64Hash(objHeadPrivateElement.payload, true);
    }
    catch (e) {
        console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
        if (ws)
            sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
        deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
    }
    var key = 'private_payment_validated-'+objHeadPrivateElement.unit+'-'+json_payload_hash+'-'+row.output_index;
    privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {
        ifOk: function(){ ... deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb); ... },
        ifError: function(error){ ... deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb); ... },
        ifWaitingForChain: function(){ ... cb(); }
    });
};
```

`json_payload_hash` is declared with `var` inside the `try` block (function-scoped, so it exists as `undefined` after a thrown exception). Because the `catch` clause omits `return`, control flow continues to the statement building `key` (using the `undefined` hash value) and then to `privatePayment.validateAndSavePrivatePaymentChain(...)`. Since `deleteHandledPrivateChain(..., cb)` was already invoked once in the `catch` block, and one of `ifOk`/`ifError`/`ifWaitingForChain` will invoke `cb` (directly or via `deleteHandledPrivateChain`) again, `cb` — the `async.each` iteration callback — is called twice for the same row.

This is directly reachable by any device that can send a private payment chain over the wallet/hub messaging protocol (`private_payment` messages saved into `unhandled_private_payments`), i.e. a private-payment counterparty, without requiring any special network position.

### Impact Explanation
Calling the `async.each` iteratee callback `cb` more than once is undefined behavior for the `async` library and typically causes the final callback (`function(){ unlock(); ... }`) to fire prematurely and/or multiple times. Because this code path runs under `mutex.lock(["saved_private"], ...)`, an early/duplicate unlock can release the mutex while other rows in the same `async.each` batch are still being processed, breaking the mutual-exclusion guarantee that protects the private-payment validation/save state. In addition, `validateAndSavePrivatePaymentChain` is invoked on an object that was already handed to `deleteHandledPrivateChain` (i.e., the DB row was already deleted) yet the private chain is validated and potentially saved a second time and events (`new_direct_private_chains`, `new_my_transactions`, `emit(key, ...)`) are emitted using a corrupted `key` (containing the literal string `"undefined"` instead of the real payload hash), which can desynchronize any code waiting on `eventBus.once(key, ...)` for a specific payload hash. This can plausibly cause inconsistent local processing/acceptance state of private payments (double processing of a payment chain, and unlock races that let a not-yet-fully-validated chain be treated as processed) — a form of node-local disagreement on validity of the private payment being handled, and a source of confusion/duplication for private payment chains.

### Likelihood Explanation
The trigger condition — `objectHash.getBase64Hash()` throwing — occurs whenever `objHeadPrivateElement.payload` cannot be canonically stringified/hashed (e.g., a payload containing values that make `getJsonSourceString`/hashing throw, such as non-well-formed strings or structures rejected by the hashing routine). Since `arrPrivateElements` originates from `JSON.parse(row.json)`, where `row.json` was persisted from data received from a peer/hub (private payment forwarded to the wallet), an unprivileged private-payment counterparty controls the shape of `objHeadPrivateElement.payload` and can craft a payload that reliably triggers the hashing exception, making this deterministically reachable.

### Recommendation
Add a `return` (or otherwise short-circuit) in the `catch` block after calling `deleteHandledPrivateChain(..., cb)` so the fallthrough code (`key` construction and the call to `validateAndSavePrivatePaymentChain`) never executes when the hash computation failed:
```js
catch (e) {
    console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
    if (ws)
        sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
    return deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
}
```
Additionally, consider declaring `json_payload_hash` outside the try/catch with an explicit sentinel value and asserting it is defined before use, to make the invariant explicit and avoid similar silent fallthrough issues in future refactors.

### Proof of Concept
1. As a device/peer, send a `private_payment` message whose first private element (`objHeadPrivateElement`) has a `payload` that causes `objectHash.getBase64Hash(payload, true)` to throw (e.g., a payload object containing a string value that is not well-formed Unicode, which `string_utils.getJsonSourceString` — used internally by hashing — rejects).
2. The wallet stores this into `unhandled_private_payments` and later `handleSavedPrivatePayments()` picks it up.
3. Inside `validateAndSave()`, `objectHash.getBase64Hash` throws; the `catch` block runs `deleteHandledPrivateChain(row.unit, ..., cb)` (first `cb()` invocation) without returning.
4. Execution falls through: `key` is built with `json_payload_hash === undefined`, and `privatePayment.validateAndSavePrivatePaymentChain(...)` is called on the already-deleted row; whichever callback (`ifOk`/`ifError`/`ifWaitingForChain`) fires calls `cb` a second time.
5. Observe `async.each`'s completion callback (`unlock(); ...`) firing early/twice relative to the outstanding rows still being processed under the `"saved_private"` mutex lock, and observe `eventBus.emit(key, ...)` firing with `key` containing the literal substring `"-undefined-"` instead of the real payload hash.

(Direct dynamic verification of the exact hashing failure path was not performed within this session; the control-flow defect — the missing `return` in the `catch` block leading to use of the uninitialized `json_payload_hash` and a double `cb` invocation — is confirmed by static reading of `network.js` lines 2467-2504.)
