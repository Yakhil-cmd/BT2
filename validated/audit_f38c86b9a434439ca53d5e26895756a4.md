The reported issue is about a Solidity contract (`FundingRateArbitrage.sol`) calling `IERC20.approve()` with `type(uint256).max` without first resetting the allowance to 0, which breaks on tokens like USDT that revert on a non-zero→non-zero allowance change. This is an EVM/Solidity implementation pattern issue.

Searching the polkadot-sdk codebase, the closest related code is the `pallet-assets` ERC-20 precompile's `approve` function, which already implements set semantics correctly. The precompile explicitly reads the current allowance and calls `do_cancel_approval` before `do_approve_transfer` whenever overwriting a non-zero allowance with another non-zero value, which is precisely the fix pattern (cancel-then-set) that would avoid the USDT-style approval race/lock issue described in the report: [1](#0-0) 

This was intentionally fixed via [2](#0-1)  to match ERC-20 "set" semantics instead of the additive semantics of the underlying `pallet_assets::do_approve_transfer`, and the code even explicitly notes the front-running caveat without regressing into the accumulation bug: [3](#0-2) 

Tests confirm non-zero-to-non-zero approvals correctly use cancel+re-approve rather than accumulating, and that reserved deposits are handled correctly through the cycle: [4](#0-3) 

The underlying `pallet_assets::approve_transfer` extrinsic itself is additive by design (`amount` tops up the existing approval) and is a FRAME dispatchable, not an ERC-20-style external call subject to the USDT quirk of reverting on non-zero-to-non-zero `approve`: [5](#0-4) 

There is no code path in this repository where a FRAME pallet or precompile calls an external `approve`-style function on a token that could impose a USDT-style "must reset to zero first" restriction causing a functional lock — the pattern that exists (precompile `approve`) already avoids the issue by cancelling first. No entry point, attacker-controlled input, or missing check analogous to the reported EVM approve-race issue was found in FRAME/XCM/bridge code.

/// Directly overwriting a non-zero allowance with a different non-zero value must use set
/// semantics (cancel + re-approve). The allowance must equal the new value — not the sum of
/// old and new — and only a single deposit should be reserved.
#[test_case(PRECOMPILE_ADDRESS_PREFIX)]
#[test_case(PRECOMPILE_ADDRESS_PREFIX_FOREIGN)]
fn approve_nonzero_to_nonzero(asset_index: u16) {
	use frame_support::traits::fungibles::approvals::Inspect;

	new_test_ext().execute_with(|| {
		let asset_id = 0u32;
		let asset_addr = H160::from(set_prefix_in_address(asset_index));

		let owner = 123456789u64;
		let spender = 987654321u64;

		Balances::make_free_balance_be(&owner, 100);
		Balances::make_free_balance_be(&spender, 100);

		let spender_addr = <Test as pallet_revive::Config>::AddressMapper::to_address(&spender);

		setup_asset_for_prefix(asset_id, asset_index);
		assert_ok!(Assets::force_create(RuntimeOrigin::root(), asset_id, owner, true, 1));
		assert_ok!(Assets::mint(RuntimeOrigin::signed(owner), asset_id, owner, 100));

		let deposit: u128 = <Test as pallet_assets::Config>::ApprovalDeposit::get();

		// Approve 100 (0 → 100).
		call_approve(owner, asset_addr, spender_addr, U256::from(100));
		assert_eq!(Assets::allowance(asset_id, &owner, &spender), 100);
		assert_eq!(Balances::reserved_balance(&owner), deposit);

		// Overwrite with 50 directly (100 → 50), no zeroing in between.
		call_approve(owner, asset_addr, spender_addr, U256::from(50));
		assert_eq!(Assets::allowance(asset_id, &owner, &spender), 50);
		// Deposit reserved exactly once — cancel unreserved the old one, approve re-reserved.
		assert_eq!(Balances::reserved_balance(&owner), deposit);

		// Overwrite upward (50 → 200) to confirm it works in both directions.
		call_approve(owner, asset_addr, spender_addr, U256::from(200));
		assert_eq!(Assets::allowance(asset_id, &owner, &spender), 200);
		assert_eq!(Balances::reserved_balance(&owner), deposit);
	});
}
