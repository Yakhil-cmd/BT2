### Title
Webhook signature verification is bound to an attacker-controlled JSON field, not to the repository the event handler actually writes to - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App/organization secret to validate a webhook signature against by reading `repository.owner.login` (or `organization.login`) straight out of the unauthenticated request body. Once "verified", `Shipit::Webhooks::Handlers::Handler` resolves the `Stack`/`Repository` to mutate using a *different* field from that same attacker-controlled body (`repository.full_name`). Nothing binds these two fields together, so the organization that "authenticates" the request is not necessarily the organization/repository that gets written to. Combined with the fact that a webhook secret is optional per organization (`verify_webhook_signature` returns `true` unconditionally when no secret is configured), this lets an unauthenticated caller impersonate webhook events for any tracked stack as long as at least one configured GitHub organization on the instance has no `webhook_secret` set - a documented, supported configuration.

### Finding Description
- `verify_signature` derives the org used to fetch a secret solely from the JSON payload: [1](#0-0) [2](#0-1) 

- If that organization has no `webhook_secret` configured (an explicitly optional setting per the setup docs), `verify_webhook_signature` short-circuits to `true` with **no cryptographic check at all**: [3](#0-2) [4](#0-3) 

- After "verification", the actual event handler resolves the target repository/stack using a sibling field of the same attacker-supplied JSON, `repository.full_name`, with no cross-check against the org used for verification: [5](#0-4) 

- Worse, `StatusHandler` doesn't even scope by repository at all - it matches purely on commit SHA across the entire install: [6](#0-5) 

The equality that should hold is: `organization that signed/authenticated the webhook == organization owning the repository/stack the handler mutates`. Instead, the code enforces: `organization named in payload.repository.owner.login (attacker-chosen, verified only if that org happens to have a secret) != repository actually resolved via payload.repository.full_name / commit sha (unconstrained)`.

### Impact Explanation
An attacker who submits a raw HTTP request to the public `/webhooks` endpoint - with **no credentials, no session, no API token** - can:
- Set `repository.owner.login`/`organization.login` to any GitHub organization configured on the Shipit instance that has no `webhook_secret` set (a supported/documented "optional" state), making `verify_webhook_signature` pass unconditionally.
- Set `repository.full_name` (or, for `status` events, just a known commit `sha`) to point at a completely different, unrelated tracked stack/repository.
- Trigger handler side effects against that unrelated stack: e.g. a forged `push` event enqueues `GithubSyncJob` for another org's stack, and a forged `status` event calls `Commit#create_status_from_github!` to fabricate a CI status (e.g. `success`) on arbitrary commits, which can be used to satisfy commit-status-based deploy safety gating and produce an unauthorized deploy.

This crosses the "organization authenticated vs. repository written" trust boundary and can result in an unauthorized deploy, matching the report's High/Critical impact bar.

### Likelihood Explanation
Requires only: (a) the target Shipit instance to have at least one configured GitHub organization without a `webhook_secret` (explicitly documented as optional), and (b) knowledge of a target stack's `repository.full_name` or a commit SHA (both are public/discoverable GitHub metadata). No credentials, tokens, or privileged access are required, matching the "unprivileged attacker" constraint.

### Recommendation
Bind the verified organization to the resolved repository/stack before any handler runs: after determining the org whose secret verified (or bypassed, if `nil`) the signature, require that the resolved `Repository`'s `owner` match that verified organization, and reject (422) otherwise. Additionally, `StatusHandler` should filter matched commits to those belonging to a stack whose repository owner matches the verified organization, rather than matching bare SHA across the whole installation. Consider also making `webhook_secret` mandatory (or at minimum warn loudly / disable unauthenticated fallback) rather than silently trusting unsigned payloads when unset.

### Proof of Concept
1. Configure (or identify) a Shipit instance with two GitHub orgs: `OrgA` (no `webhook_secret` set) and `OrgB` (target, has a tracked stack `OrgB/victim-repo`).
2. Send, unauthenticated, to `POST /webhooks` with header `X-Github-Event: status`:
```json
{
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgA/whatever" },
  "sha": "<known sha of a commit in OrgB/victim-repo>",
  "state": "success",
  "context": "ci/required-check"
}
```
3. `verify_signature` resolves `Shipit.github(organization: "OrgA")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` without checking `X-Hub-Signature` at all.
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the commit belonging to `OrgB/victim-repo`, and calls `create_status_from_github!`, injecting a forged "success" status for that commit with no relation to the verified (or unverified) `OrgA` context.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
