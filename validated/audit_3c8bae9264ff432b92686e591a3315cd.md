### Title
Hookify "file" event block rules never match on `Write` tool operations because `new_text` field extraction ignores the `content` key - (File: `plugins/hookify/core/rule_engine.py`)

### Summary
`RuleEngine._check_condition` (via `RuleEngine._extract_field`) resolves the `new_text` field for `Write`/`Edit` tools by reading only `tool_input.get('new_string', '')`, which is the key used exclusively by the `Edit` tool. The `Write` tool supplies its payload under the `content` key, so any hookify rule authored with the documented "file" event + simple `pattern:` shorthand (which config_loader infers `field='new_text'`) silently receives an empty string for every `Write` invocation and can never match, even when the written content contains the exact dangerous pattern the rule was meant to block.

### Finding Description
In `plugins/hookify/core/config_loader.py` (`Rule.from_dict`), a rule declared with `event: file` and a simple `pattern:` (the primary documented workflow in `plugins/hookify/skills/writing-rules/SKILL.md` and `plugins/hookify/commands/hookify.md`) is converted into a condition with `field='new_text'`: [1](#0-0) 

When this rule is evaluated, `RuleEngine._rule_matches` calls `_check_condition`, which calls `_extract_field(condition.field, tool_name, tool_input, input_data)`: [2](#0-1) 

Inside `_extract_field`, the `Write`/`Edit` branch handles `new_text`/`new_string` by reading only `tool_input.get('new_string', '')`, with no fallback to `content`: [3](#0-2) 

The `Write` tool's `tool_input` never contains a `new_string` key — it uses `content` (as shown in the sample hook payload in `plugins/plugin-dev/skills/hook-development/scripts/test-hook.sh`, `tool_input: {"file_path": ..., "content": ...}`). As a result, `_extract_field` returns `''` (empty string, not `None`) for every `Write` call when `field == 'new_text'`. Since the value is not `None`, `_check_condition` proceeds to evaluate the operator (`regex_match`, `contains`, etc.) against an empty string, which never matches a real dangerous pattern, so the condition returns `False` and the rule silently fails to fire.

Both `plugins/hookify/hooks/pretooluse.py` and `plugins/hookify/hooks/posttooluse.py` route `Write`, `Edit`, and `MultiEdit` tool calls into the same `event='file'` rule set: [4](#0-3) 
so users are led to believe a single "file" rule protects all three tools, but in practice `Write` calls bypass it entirely due to the field-extraction gap. An attacker does not need any elevated privilege — ordinary repository content or a prompt-injected instruction that causes the agent to create a new file via `Write` (instead of editing an existing one via `Edit`) with the exact same dangerous payload (e.g., `eval(`, a hardcoded secret, or a malicious script body) evades the block rule that a maintainer configured specifically to stop it.

### Impact Explanation
This breaks the core invariant that a matching hookify `block` rule reliably denies the protected operation. A maintainer relying on the documented "file" event pattern shorthand to block dangerous content (e.g., secrets, `eval()`, malicious code) believes all `Write`/`Edit`/`MultiEdit` operations are covered, but `Write` operations pass through unchecked. Since `PreToolUse` hookify rules are one of the enforcement layers users rely on to gate tool execution/content writes, this allows unauthorized file creation containing content that should have been denied — matching the "Unauthorized local command execution / bypasses Claude Code approval or deny controls" impact category, scoped specifically to file-write content that a block rule was supposed to stop.

### Likelihood Explanation
Highly likely and trivially repeatable: any hookify rule created via the primary documented workflow (`pattern:` frontmatter + `event: file`) is affected, with no special configuration needed. The bypass triggers automatically whenever the `Write` tool (rather than `Edit`) is used to introduce the flagged content — a completely ordinary and common occurrence, not an edge case requiring social engineering or credentials.

### Recommendation
In `RuleEngine._extract_field`, make the `new_text`/`new_string` branch fall back to `content` for the `Write` tool, mirroring the existing `content` branch's fallback logic:
```python
elif field == 'new_text' or field == 'new_string':
    return tool_input.get('new_string') or tool_input.get('content', '')
```
Additionally, consider unifying field resolution so `new_text` and `content` are treated as aliases across `Write`/`Edit`/`MultiEdit`, and add regression tests asserting that a `file`-event block rule with a simple `pattern:` matches dangerous content supplied via `Write`'s `content` key, not just `Edit`'s `new_string` key.

### Proof of Concept
Unit test to add to a hookify test suite (e.g. `plugins/hookify/tests/test_rule_engine.py`):
```python
from hookify.core.config_loader import Rule
from hookify.core.rule_engine import RuleEngine

def test_write_tool_bypasses_file_event_block_rule():
    rule = Rule.from_dict(
        {"name": "block-eval", "enabled": True, "event": "file",
         "action": "block", "pattern": r"eval\("},
        "Dangerous eval() detected!"
    )
    engine = RuleEngine()

    # Same dangerous payload, via Edit -> correctly blocked
    edit_input = {"tool_name": "Edit",
                  "tool_input": {"file_path": "app.js", "new_string": "eval(userInput)"}}
    assert engine.evaluate_rules([rule], edit_input).get("hookSpecificOutput", {}).get("permissionDecision") == "deny"

    # Same dangerous payload, via Write -> incorrectly NOT blocked (bug)
    write_input = {"tool_name": "Write",
                   "tool_input": {"file_path": "app.js", "content": "eval(userInput)"}}
    result = engine.evaluate_rules([rule], write_input)
    assert result == {}  # demonstrates the block rule fails to fire for Write
```
Expected (fixed) behavior: both `Edit` and `Write` invocations with the same dangerous content should produce `{"hookSpecificOutput": {"hookEventName": "PreToolUse", "permissionDecision": "deny"}, ...}`.
