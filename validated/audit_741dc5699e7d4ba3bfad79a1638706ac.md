### Title
Rounding of `earned_headers_commission_share` splits in headers-commission distribution can inflate the total bytes credited to recipients - ([File: headers_commission.js])

### Summary
Headers commissions won by a unit are split among `earned_headers_commission_recipients` by independently rounding each recipient's share of the full amount with `Math.round()`. Because each recipient's cut is rounded separately rather than being derived from a running remainder, the sum of the individually-rounded amounts can exceed the `full_amount` that was actually paid by the payer unit, crediting recipients with more bytes than were actually collected — the same "rounding gives out more than was deposited" root cause as the referenced Solidity report.

### Finding Description
Any unprivileged unit poster can author a unit with multiple authors and specify a custom `earned_headers_commission_recipients` list, as long as the shares sum to exactly 100, which is the only invariant enforced at validation time: [1](#0-0) 

When this unit later wins a headers commission (`calcHeadersCommissions`), the payer's `full_amount` (the fixed `headers_commission` field of the payer unit) is split among the recipients by calling `Math.round(full_amount * share / 100.0)` independently for each recipient, both in the in-RAM code path and in the SQL/DB code path: [2](#0-1) [3](#0-2) 

There is no adjustment of the last recipient's amount to absorb the rounding remainder (unlike patterns that give the remainder to one designated party). Since each `Math.round()` call is performed on the full, unreduced `full_amount`, an attacker who crafts a recipient list with many small percentage shares whose individual roundings each tip upward (e.g., several 3% shares of an amount where `3% * full_amount` rounds up half a unit each time) can make the sum of all recipients' rounded amounts exceed `full_amount` for that payer unit. These amounts are inserted into `headers_commission_contributions`, which directly credit each recipient's address balance, so any extra bytes generated this way are new, uncollateralized coin credited to attacker-controlled addresses.

### Impact Explanation
This is a supply-inflation bug in the base-currency ledger: bytes are credited to recipients from `headers_commission_contributions` in amounts that in aggregate can exceed what the payer unit actually paid as `headers_commission`. Because base-currency (bytes) supply is fixed and every byte is supposed to be traceable to the genesis issuance, any mechanism that can create extra spendable bytes constitutes unauthorized token supply inflation, which the validation rules explicitly call out as a critical impact category (asset issuance/transfer, and payment inputs/outputs and commissions are both listed as in-scope reachable surfaces). The magnitude per unit is bounded by rounding error (at most ~0.5 units per recipient), but an attacker controlling many author addresses per unit, and repeating this over many units, can accumulate real value over time at no cost beyond posting units.

### Likelihood Explanation
Reaching this path requires only posting an ordinary multi-authored unit with a self-chosen `earned_headers_commission_recipients` list summing to 100% — something any unprivileged unit poster can do; no special permissions, races, or hub/witness collusion are required. The unit merely needs to be selected as the "winning child" for headers commission by the existing (permissionless) selection algorithm, which happens naturally in the normal course of DAG growth. This makes the bug realistically triggerable, though the per-transaction gain is small (dust-level), matching the "Medium" characterization in the original report.

### Recommendation
Change the distribution algorithm so that recipient amounts are computed from a running remainder rather than independently from the full amount, e.g. accumulate `assigned_so_far`, compute each recipient's amount as `Math.round(full_amount * cumulative_share/100) - assigned_so_far`, and give the last recipient `full_amount - assigned_so_far` explicitly, guaranteeing that the sum of distributed amounts always equals `full_amount` exactly. Apply the same fix to both the in-RAM path (`headers_commission.js:179-188`) and the SQL/rows path (`headers_commission.js:192-210`) to keep the two computations (used for cross-checking) synchronized.

### Proof of Concept
1. Attacker creates two addresses `A` and `B` under their control and posts a unit authored by both, with `earned_headers_commission_recipients = [{address: A, earned_headers_commission_share: 50}, {address: B, earned_headers_commission_share: 50}]` — this passes validation because the shares sum to 100 (`validation.js:1122`).
2. Suppose this unit wins a headers commission with `full_amount` such that `full_amount * 0.5` is exactly `x.5` (e.g., `full_amount = 71`, so `71*0.5 = 35.5`).
3. In `headers_commission.js`, `Math.round(35.5)` is computed independently for both A and B: `Math.round(71*50/100.0) = 36` for A and `Math.round(71*50/100.0) = 36` for B.
4. Total credited = `36 + 36 = 72`, one byte more than the `full_amount = 71` that was actually paid by the payer unit — an extra byte created from rounding, credited to the attacker's own addresses.
5. Repeating this pattern across many won headers commissions (each unit posting costs only the minimal spam-prevention fee) accumulates real, uncollateralized byte balance over time.

function validateHeadersCommissionRecipients(objUnit, cb){
	if (objUnit.authors.length > 1 && typeof objUnit.earned_headers_commission_recipients !== "object")
		return cb("must specify earned_headers_commission_recipients when more than 1 author");
	if ("earned_headers_commission_recipients" in objUnit){
		if (!isNonemptyArray(objUnit.earned_headers_commission_recipients))
			return cb("empty earned_headers_commission_recipients array");
		var total_earned_headers_commission_share = 0;
		var prev_address = "";
		for (var i=0; i<objUnit.earned_headers_commission_recipients.length; i++){
			var recipient = objUnit.earned_headers_commission_recipients[i];
			if (!isPositiveInteger(recipient.earned_headers_commission_share))
				return cb("earned_headers_commission_share must be positive integer");
			if (hasFieldsExcept(recipient, ["address", "earned_headers_commission_share"]))
				return cb("unknown fields in recipient");
			if (!isValidAddress(recipient.address))
				return cb("invalid recipient address checksum");
			if (recipient.address <= prev_address)
				return cb("recipient list must be sorted by address");
			total_earned_headers_commission_share += recipient.earned_headers_commission_share;
			prev_address = recipient.address;
		}
		if (total_earned_headers_commission_share !== 100)
			return cb("sum of earned_headers_commission_share is not 100");
	}
	cb();
}
