### Title
Unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` lets a status from one repository/organization flip required-context state for a commit belonging to a different repository's stack - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target commit purely by SHA, with no constraint on the repository/organization that authenticated the webhook, then calls `commit.create_status_from_github!` which mutates that commit's status regardless of which repo it "belongs" to. Because SHAs are git object hashes shared identically between a repository and any of its forks (or between any two repos containing the same commit, e.g. via a fork of a production repo), an attacker who owns a forked/second repository wired into the same Shipit host (satisfying `Shipit.github(organization: repository_owner)` and its `webhook_secret`) can send a valid, self-authenticated `status` webhook whose `sha` matches a commit that also exists in a victim's production stack, forging `context: review/approved`, `state: failure` for that shared commit.

### Finding Description
The broken binding: the code implicitly assumes `commit.stack.repository == payload.repository`, i.e. `Commit.where(sha: params.sha).first.stack.repository_owner/name == request.params['repository']`. This equality is **never checked**.

Trace:
- `Shipit::WebhooksController#create` (`app/controllers/shipit/webhooks_controller.rb:10-15`) dispatches to `Shipit::Webhooks.for_event(event)` handlers after `verify_signature`, which only checks `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` — this validates that the payload was signed by *some* configured GitHub App/org's `webhook_secret`, not that the `sha`/commit inside the payload belongs to the repository named in that payload. [1](#0-0) 
- `StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
No `stack_id`, `repository`, or organization filter is applied — any commit row across *any* stack in the Shipit instance whose `sha` column matches is updated. [2](#0-1) 
- `Commit#create_status_from_github!` → `add_status` recomputes `status`, and if the `simple_state` changes, emits `deployable_status` hooks and calls `stack.schedule_merges`. [3](#0-2) [4](#0-3) 
- `Commit#blocked?`/`#deployable?` consult `stack.blocking_statuses`/`stack.required_statuses` (deploy-spec driven), so a forged `failure` status on a `review/approved`-style required context can flip `blocked?`/`deployable?` for the victim's stack, and `schedule_merges`/`ContinuousDeliveryJob` react to state transitions. [5](#0-4) [6](#0-5) 

Exploit flow: attacker forks (or otherwise controls) a repository registered as a Shipit App installation whose organization webhook secret they can trigger legitimately (i.e., they push commits and GitHub emits real `status`/webhook events signed with that org's `webhook_secret` for their own repo). Any commit SHA shared between the attacker's repo and the victim's production stack (e.g., commits that predate the fork, or a rebase producing an identical SHA, or the two repos being mirrors) will have its `Commit` row in the victim stack updated by the attacker's status payload, because the lookup is a bare `sha` match with no repository scoping.

Why existing guards fail: `verify_signature` authenticates *which organization's secret signed the payload*, not *which commit/stack the payload is permitted to affect*; `drop_unhandled_event` and the `ExplicitParameters` schema only validate the shape of `context/state/sha`, not ownership; there is no `stack.repository`/`params.dig('repository')` cross-check anywhere in `StatusHandler`.

### Impact Explanation
A payload authenticated for one repository can write a `Status` record (and cascade into `deployable_status`/merge-scheduling hooks) for a commit belonging to a different stack/repository/tenant — this is exactly the "payload for one repository mutating another's stack/commit" category. If the affected stack requires `review/approved` as a blocking/required status and is the production environment, a forged `failure` can force `Commit#blocked?`/`#deployable?` to flip, which can block a legitimate deploy or, depending on deploy-spec configuration, unblock/ship a different commit by altering CI gating. This is repeatable for every shared SHA and against any stack on the same Shipit instance whose commits share history with an attacker-reachable repository.

### Likelihood Explanation
Preconditions: the attacker needs a repository wired to a Shipit-recognized GitHub organization/app (own repo or fork) so `verify_signature` accepts their webhook, and a commit SHA that is present both in that repository's git history and in the victim stack's `commits` table (trivial via forking, since fork history shares SHAs identically, or possible via targeted rebase/cherry-pick to reproduce an identical SHA against a known parent+tree). Attacker cost is a single `git push`/webhook trigger from their own controlled repo — no Shipit credentials, sessions, or secrets are required. This is feasible without brute-forcing SHA1 collisions when a fork relationship or shared history exists, which is a common real-world scenario for actively-developed repos.

### Recommendation
Scope the lookup by both `sha` and the repository identified in the payload: resolve the target `Stack`(s) via `Repository` matched to `params.dig('repository', 'full_name')` / `repository_owner` before querying `Commit`, e.g. `Commit.joins(:stack).where(sha: params.sha, stack: { repository_id: repository.id })`, and reject/no-op when the webhook's repository does not match any commit's owning repository. Apply the same fix pattern to any other unscoped `Commit.where(sha: ...)`/`by_sha` usages reachable from webhook handlers (e.g. `CheckRunHandler` if it exists) to eliminate cross-tenant writes.

### Proof of Concept
Minitest plan (`test/models/webhooks/handlers/status_handler_test.rb`-style, no live GitHub):
1. Create `repository_a` (attacker-controlled) and `repository_b` (victim, production environment, deploy-spec requiring `review/approved` as a blocking/required status).
2. Create `stack_b` for `repository_b` and a `commit` with `sha = "abc123..."` belonging to `stack_b`, with an existing passing `review/approved` status so `commit.blocked?` is `false` and `commit.deployable?` is `true`.
3. Assert the binding before: `commit.reload.blocked? == false` and the commit's owning repository (`stack_b.repository`) is **not** `repository_a`.
4. Build a `status` webhook payload with `sha: "abc123..."`, `context: "review/approved"`, `state: "failure"`, and `repository: repository_a`'s attributes (simulating the payload came from `repository_a`).
5. Call `Shipit::Webhooks::Handlers::StatusHandler.new.call(payload)` (or the equivalent invocation used by existing handler tests) directly, bypassing the controller layer to isolate the model-level bug (or go through `WebhooksController#create` stubbing `verify_signature` to pass for `repository_a`'s org).
6. Assert the binding after: `commit.reload.status.state == "failure"` and `commit.blocked?` has flipped to `true` (or `deployable?` flipped to `false`), even though the authenticating payload's `repository` was `repository_a`, not `repository_b`/`stack_b.repository`.
7. The assertion `commit.stack.repository_id == repository_b.id` while the payload's repository was `repository_a.id` demonstrates the cross-repository write, proving `StatusHandler#process`'s unscoped `Commit.where(sha:)` allows one repository's authenticated webhook to mutate another repository's stack state.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
