### Title
Webhook signature verified against payload's `repository.owner`/`organization.login` while write actions key off the unrelated `repository.full_name` field, allowing cross-organization stack manipulation - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub organization's `webhook_secret` to validate the HMAC signature against using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (or `organization.login`). But once the signature check passes, every `Shipit::Webhooks::Handlers::Handler` subclass (used for `push`, `status`, `check_suite`, `pull_request`, etc.) resolves the target `Repository`/`Stack` purely from `payload.dig('repository', 'full_name')` (or `params.repository.full_name`) via `Repository.from_github_repo_name`. These two fields are never cross-checked against each other. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
In a multi-organization Shipit deployment (the documented config format supports several GitHub orgs, each with its own `webhook_secret`, as shown in `config/secrets.development.shopify.yml`), the trust binding that should hold is:

`organization whose secret authenticated the request == organization owning the repository that gets mutated`

The controller breaks this binding:
1. `verify_signature` derives `repository_owner` from the payload body itself (`params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`) and looks up `Shipit.github(organization: repository_owner)` to find the secret to check the HMAC against. [2](#0-1) 
2. The HMAC itself covers the entire raw JSON body, but nothing ties the *verified* org identity to any other field consumed downstream — the handler layer never re-reads `repository.owner.login`, it reads a completely separate JSON key, `repository.full_name`. [4](#0-3) 
3. `Repository.from_github_repo_name` splits `full_name` on `/` and looks up any `Repository` record by owner/name, regardless of which org's secret validated the request. [5](#0-4) 

Because an attacker only needs to know (or possess) the `webhook_secret` configured for **any one** org tracked by the Shipit instance to produce a valid `X-Hub-Signature`, they can craft a JSON body where `repository.owner.login` (and/or `organization.login`) matches that known-secret org — satisfying `verify_signature` — while `repository.full_name` names a repository belonging to an entirely different, unrelated org also tracked by the same Shipit instance. Handlers such as `PushHandler` then act on stacks under that unrelated org's repository: [6](#0-5) 

`CheckSuiteHandler`, `StatusHandler`, and the `PullRequest` handlers exhibit the same pattern — they all resolve `repository`/`stacks` from `params.repository.full_name` independent of the verified owner: [7](#0-6) [8](#0-7) 

This is directly analogous to the linked gnark fix's bug class: a value used for one purpose (limb-count bound check) computed via a path that could diverge from the value actually acted upon (the real overflow), i.e., a mismatch between the checked quantity and the used quantity. Here the checked quantity is "which org's secret verified this request" and the used quantity is "which repository the handler writes to" — and they are never reconciled.

### Impact Explanation
`PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` on every non-archived stack matching the branch derived from the forged `ref`, for a repository the attacker does not control. This can force git ref synchronization state changes, trigger `RefreshCheckRunsJob` (`CheckSuiteHandler`), spoof commit statuses used for deploy gating (`StatusHandler` calls `commit.create_status_from_github!`), and manipulate review-stack lifecycle (archive/unarchive/provision) for pull requests belonging to a victim org's repository (`OpenedHandler`, `LabeledHandler`, `ClosedHandler`, etc.) — all while only possessing the `webhook_secret` of an unrelated, possibly less-trusted, org configured in the same Shipit instance. Spoofed commit statuses feeding into deploy safety checks and forced ref-sync on a stack the attacker doesn't own constitute cross-repository writes and potential unauthorized-deploy preconditions, matching the "Critical: cross-repository writes / unauthorized deploy" bar.

### Likelihood Explanation
Exploitation strictly requires the attacker to already know a `webhook_secret` valid for *some* organization onboarded to the Shipit instance (e.g., because they administer that org's GitHub App/webhook settings, or the secret leaked). This is a real precondition, but it is not equivalent to "repository write access" on the *victim* org, nor does it require a Shipit session, `ApiClient` token, or GitHub App private key — it is exactly the "unprivileged relative to the target org" scenario the rules ask to keep in scope, since knowledge of one org's low-value webhook secret should never authorize writes to a different org's stacks. In single-org deployments (the default/simple config) this issue is not reachable, since there is only one possible secret and the mismatch is moot; likelihood is meaningfully non-trivial only for multi-org installs, which the engine explicitly documents and supports.

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler`), after verifying the HMAC, re-derive and enforce that `payload.dig('repository', 'full_name')`'s owner segment matches the `repository_owner` value that selected the verifying secret (or, better, verify the signature using the secret owned by the org that actually owns the resolved `Repository`, and reject if they diverge). Add a test asserting a webhook whose `repository.owner.login` differs from `repository.full_name`'s owner is rejected even when signed with a valid (but wrong-org) secret.

### Proof of Concept
1. Shipit is configured for two orgs, `org-a` (attacker-known `webhook_secret_a`) and `org-b` (victim, tracked stacks under `org-b/victim-repo`), per the multi-org config format in `config/secrets.development.shopify.yml`.
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": { "full_name": "org-b/victim-repo", "owner": { "login": "org-a" } }
}
```
3. Attacker computes `X-Hub-Signature` as `sha1=HMAC-SHA1(webhook_secret_a, body)`.
4. `verify_signature` calls `Shipit.github(organization: "org-a")` (from `repository_owner`, matching the `owner.login` in the crafted body) and successfully verifies the signature against `webhook_secret_a`.
5. `PushHandler#process` is invoked; `Handler#repository_name` reads `full_name` = `"org-b/victim-repo"`, resolving `org-b`'s real stacks and invoking `stack.sync_github(expected_head_sha: ...)` on them — without ever having proven possession of `org-b`'s webhook secret.
