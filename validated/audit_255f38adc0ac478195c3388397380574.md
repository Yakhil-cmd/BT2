### Title
Api::CCMenuController leaks other stacks' CI/deploy status to a stack-scoped ApiClient token - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides the base controller's stack-scoping logic and looks up the requested stack directly from the unscoped `Stack` model, ignoring the restriction that an `ApiClient` token may be limited to a single stack. This breaks the binding "the stack a token authorizes == the stack the request touches."

### Finding Description
`Api::BaseController` scopes any stack lookup through `stacks`, which restricts results to the stack the current `ApiClient` is bound to when `stack_id` is set: [1](#0-0) 

This is the mechanism that makes the `authenticate!(:here_come_the_walrus)` test assert "an api client scoped to a stack will only see that one stack": [2](#0-1) 

However, `Api::CCMenuController` redefines its own private `stack` method that bypasses this scoping entirely, resolving the stack directly from `params[:stack_id]` against the global `Stack` relation: [3](#0-2) 

The controller only checks the permission name (`read:stack`) via `require_permission :read, :stack`, which calls `ApiClient#check_permissions!` — a check that only inspects the `permissions` array, never the `stack_id` binding: [4](#0-3) 

So any token that carries the `read:stack` permission — including one deliberately scoped by its creator to a single stack via `ApiClient.stack_id` — can be replayed against `/api/1/stacks/:stack_id/cc.xml` for any other stack in the installation, because `CCMenuController#stack` never consults `current_api_client.stack_id?`.

### Impact Explanation
This is an unauthenticated-read escalation of exactly the class flagged in the external report (a permission granted for one object being usable for a different, unauthorized object — there, pool weights when swap was disabled; here, one stack's data when the token authorizes only another stack). Concretely, a token minted for CI status badge/CCMenu display of Stack A (as done by `CCMenuUrlController#client`, which mints a `read:stack`-only client) — or any other `read:stack`-scoped token — can be used to enumerate build status, last build label/time, and activity state of any other stack, including stacks the token holder has no legitimate access to. This meets the "unauthenticated read of stack state" High-impact bucket because the request is authenticated only by a bearer-style token, not by any check that the token's owner may see the target stack.

### Likelihood Explanation
The exploit requires nothing beyond a single valid `read:stack`-scoped `ApiClient` token (the intended low-trust credential type for CCMenu integrations, as generated automatically and unauthenticated by `CCMenuUrlController`) and knowledge/guessing of another stack's `stack_id` (repo owner/name/env), which are not secrets and are visible throughout the UI/API. No signature bypass, session, or elevated account is needed beyond the token itself, making this straightforward to exploit once any such token exists.

### Recommendation
Remove the `stack` override in `Api::CCMenuController`, or reimplement it using the same scoped `stacks` helper from `BaseController` (i.e., `stacks.from_param!(params[:stack_id])`) so that a stack-scoped `ApiClient` cannot access stacks outside its `stack_id` binding.

### Proof of Concept
1. Create (or reuse) an `ApiClient` with `permissions: ['read:stack']` and `stack_id` set to Stack A's id (e.g., via `CCMenuUrlController#client`, which is exactly how the CCMenu URL feature provisions a token from `app/controllers/shipit/ccmenu_url_controller.rb`).
2. Using that token, call `GET /api/1/stacks/:stack_a_id/cc.xml?token=<token>` — succeeds as expected.
3. Call `GET /api/1/stacks/:stack_b_id/cc.xml?token=<token>` for a different stack B that the token was never scoped to.
4. Observe that the request succeeds and returns Stack B's build status/activity, because `Api::CCMenuController#stack` (app/controllers/shipit/api/ccmenu_controller.rb:29-31) resolves `Stack.from_param!` unscoped instead of using `current_api_client.stack_id`-filtered `stacks` from `Api::BaseController#stacks`/`#stack` (app/controllers/shipit/api/base_controller.rb:74-80).
