Confirmed: `StatusHandler#process` iterates `Commit.where(sha: params.sha)` with **no repository or stack filter** at all, then calls `commit.create_status_from_github!(params)` on every matching row across the entire installation.### Title
Cross-repo status webhook forgery updates commit statuses for any stack sharing the same commit sha, unblocking deploys - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits purely by `sha` with no repository/stack scoping, so a `status` webhook that legitimately passes signature verification for repository R2 will create a `Status` on any `Commit` row in the database with a matching sha — including commits belonging to stack S1 tracked from a different repository R1. Since `Commit#blocked?` (`app/models/shipit/commit.rb:231-237`) and `Status::Common#blocking?` (`app/models/shipit/status/common.rb:46-48`) only look at `Status` rows attached to the commit without checking which repository/stack produced them, this allows an attacker who controls R2 (e.g. a fork of R1 sharing pre-fork commit history) to flip the blocking state of a shared commit sha and unblock S1's deploy queue.

### Finding Description
Binding claimed: the blocking status resolved for a commit range in S1 == statuses genuinely produced by R1's CI, not R2's.

Trace:
- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) verifies the signature using `Shipit.github(organization: repository_owner)`, where `repository_owner` is read from the payload's `repository.owner.login` (`app/controllers/shipit/webhooks_controller.rb:59-62`). This validates that the payload was signed with **the organization's** webhook secret — it does NOT validate that the sha in the payload belongs to the named repository, nor does it constrain which `Commit` rows the handler may touch.
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`):
  ```ruby
  def process
    Commit.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
  ```
  This queries `Commit` globally by `sha`, with **no filter on `repository_name`/`stacks`** even though the base `Handler` class already provides a `stacks` helper scoped by `payload.dig('repository', 'full_name')` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) that other handlers (e.g. `PushHandler`) use but `StatusHandler` does not.
- `Commit#create_status_from_github!` (`app/models/shipit/commit.rb:165-169`) creates a `Status` scoped to `stack_id` (the commit's own stack), so the forged status lands attached to whichever stack the sha-matching commit belongs to — even if that's R1's stack S1, not R2's.
- `Commit#blocked?` (`app/models/shipit/commit.rb:231-237`) and `Status::Common#blocking?` (`app/models/shipit/status/common.rb:46-48`) then evaluate blocking purely from `commit.blocking_statuses` and `Status` rows on that commit, with no notion of which repository/webhook produced them.

Attack: If R2 is a fork of R1 (or any repository sharing git history/commit shas with R1) and both are tracked as separate Shipit stacks, any commit that predates the fork point has an identical sha in both repos. An attacker with push access to R2 (their own fork, tracked by Shipit) can set a commit status via the GitHub Status API on that shared sha in R2. GitHub fires a legitimate, correctly-signed `status` webhook for R2's org. `StatusHandler#process` finds the same-sha `Commit` row belonging to R1's stack S1 and creates a `Status` on it, because the lookup ignores repository origin entirely. If that status is `success` for a required blocking context, it can flip an otherwise-failing/missing blocking commit in S1 to `success?`; `Commit#blocking?` becomes false for that earlier commit, and `Commit#blocked?` for a later, legitimate commit in S1 evaluates `stack.commits.reachable.newer_than(...).older_than(self).any?(&:blocking?)` as false, unblocking the whole downstream range for deployment.

Existing guards that fail to prevent this: `verify_signature` only checks the HMAC against the organization derived from the payload, not the target commit's actual owning repository; `drop_unhandled_event` and `ExplicitParameters` (`params` schema for `StatusHandler`) only validate the shape of the payload (`sha`, `state`, etc.), not repository/commit ownership; there is no `Repository.from_github_repo_name(repository_name)` check gating which `Commit`s can be touched, unlike `PushHandler`/other handlers that use `stacks`.

### Impact Explanation
A forged/legitimate-but-cross-repo status write causes a `Status` record to be attached to a commit in a *different* repository's stack than the one that actually authenticated the webhook, which matches the listed Critical impact category "a payload for one repository mutating another's stack, commit, task or team" and can directly cause "an unauthorized deploy." Concretely, it can flip `Commit#blocking?`/`Commit#blocked?` for arbitrary later commits in R1's stack, unblocking (or, in the opposite direction, blocking/DoS-ing, though DoS is out of scope) an entire queue of otherwise-gated deploys in a repository the attacker does not control. This is repeatable against any pair of stacks that happen to share a commit sha (most realistically: forks/mirrors of the same upstream tracked as separate Shipit stacks), and scales to any number of such sha collisions the attacker can produce or find.

### Likelihood Explanation
Preconditions: (1) two Shipit-tracked stacks/repositories S1 (victim) and S2 (attacker-controlled, e.g. a fork) that share at least one commit sha in S1's undeployed/blocking range, and (2) attacker has push/status-write access to S2 (trivial if S2 is their own fork with a configured Shipit webhook, or any repo in the org they can write commit statuses to). The attacker needs no Shipit credentials, no `api_clients_secret`, and no elevated GitHub permissions beyond "repo:status" write on their own repository — well within the stated unprivileged attacker capabilities. The main constraint is finding/arranging a shared sha in S1's blocking range, which is straightforward for forks (pre-fork history is identical) or for any workflow where commits are cherry-picked/rebased identically across tracked repos. Given forks-of-tracked-repos are a common real-world Shipit setup, likelihood is realistic, not merely theoretical.

### Recommendation
Scope `StatusHandler#process` to the repository that authenticated the webhook, mirroring the pattern already used by `Handler#stacks`/`PushHandler`: restrict the `Commit.where(sha: params.sha)` lookup to `stacks` (i.e., commits belonging to stacks under `Repository.from_github_repo_name(payload.dig('repository','full_name'))`), for example:
```ruby
def process
  stacks.flat_map(&:commits).select { |c| c.sha == params.sha }.each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
or equivalently `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`.

### Proof of Concept
Minitest plan (place under `test/models/webhooks/handlers/status_handler_test.rb`, no live GitHub required):

```ruby
test "status webhook from repository R2 must not create a Status on a same-sha commit belonging to repository R1's stack" do
  # Arrange: two repositories/stacks sharing a commit sha (simulating a fork sharing pre-fork history)
  repo1 = shipit_repositories(:r1) # owner/repo1, has stack s1
  repo2 = shipit_repositories(:r2) # owner/repo2 (fork), has stack s2
  shared_sha = 'deadbeef' * 5

  blocking_commit_s1 = repo1.stacks.first.commits.create!(sha: shared_sha, ...)
  repo2.stacks.first.commits.create!(sha: shared_sha, ...)

  repo1.stacks.first.stubs(:blocking_statuses).returns(['ci/blocking'])
  blocking_commit_s1.statuses.create!(stack: repo1.stacks.first, state: 'failure', context: 'ci/blocking')

  later_commit_s1 = repo1.stacks.first.commits.create!(sha: 'cafebabe' * 5, ...)

  assert_predicate blocking_commit_s1, :blocking?
  assert_predicate later_commit_s1, :blocked?

  # Act: forge/replay a status webhook that legitimately authenticates as repo2's org,
  # for the shared sha, marking CI success.
  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'ci/blocking',
    'repository' => { 'full_name' => repo2.github_repo_name, 'owner' => { 'login' => repo2.owner } }
  }
  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  # Assert: the binding is broken — R2's status was applied to R1's commit.
  blocking_commit_s1.reload
  assert_predicate blocking_commit_s1, :success?   # forged from R2
  refute_predicate blocking_commit_s1, :blocking?
  refute_predicate later_commit_s1.reload, :blocked?  # deploy queue incorrectly unblocked
end
