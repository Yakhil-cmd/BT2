### Title
`StatusHandler#process` ignores repository scoping and mutates commits belonging to any stack whose SHA collides with the attacker's payload - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::Handler` exposes a `stacks` helper that correctly scopes results to the repository named in the webhook payload via `repository_name` (`payload.dig('repository', 'full_name')`), but `StatusHandler#process` never uses it. Instead it calls `Commit.where(sha: params.sha)` unscoped, across the entire `commits` table, so a correctly-signed webhook for one repository can create/mutate commit statuses for commits belonging to a completely different stack whose SHA happens to match.

### Finding Description
The intended binding is: `StatusHandler#process`'s effective scope of commits should equal `stacks.joins(:commits)`/`stacks` filtered set (i.e. commits belonging to `Repository.from_github_repo_name(repository_name).stacks`). Instead the actual binding is `Commit.where(sha: params.sha)` with no `stack`/`repository` predicate at all: [1](#0-0) 

The base class already computes the correct scope and makes it available to every subclass via `stacks`, which internally resolves `repository_name` from the payload and looks up only that repository's stacks: [2](#0-1) 

`StatusHandler` inherits `stacks`/`repository_name` but never calls `stacks` in `process`, so the repository named in the payload has no bearing on which commits get mutated — only the raw `sha` string does.

Attack path: `WebhooksController#create` parses the raw JSON body and dispatches to registered handlers for the event type without any correlation between the payload's `repository` and the commits it is allowed to touch: [3](#0-2) 

Signature verification only proves the request originated from the GitHub org named in the payload (`repository_owner`), via a per-organization signing secret: [4](#0-3) 

It does **not** prove that the SHA referenced inside the payload actually belongs to a commit under that organization's own repository/stack. An attacker who owns any GitHub repository that is registered with Shipit (a legitimate, unprivileged precondition — they only need their own repo hooked up, which is the normal operating mode of this engine) can send a genuinely, correctly-signed `status` event whose `sha` field is copied from a commit belonging to an entirely different stack. `StatusHandler#process` will find and mutate that commit via `Commit.where(sha: params.sha)` regardless of which repository it actually belongs to, because the repository-scoping (`stacks`) that the base class already provides is simply never applied.

`Commit#create_status_from_github!` → `add_status` then emits `Hook.emit(:commit_status, ...)`/`:deployable_status`, and can trigger `stack.schedule_merges`, i.e., cause a victim stack's commit to be marked "success" and become deployable/mergeable — a genuine cross-tenant mutation.

None of the existing guards close this gap:
- `verify_signature` only authenticates the org referenced in the payload, not the sha-to-repository binding.
- `ExplicitParameters` schema only validates the parameter types (`sha`, `state`, etc.), not ownership.
- `drop_unhandled_event` just filters unregistered event types.
- No model validation ties `Commit#sha` uniqueness or ownership checks into this codepath.

### Impact Explanation
An attacker who controls any onboarded repository can forge a `status` webhook (with a valid signature for their own org) referencing a `sha` that belongs to a commit on a stack of a completely unrelated repository/tenant, and inject a fabricated status (e.g., `success`) for it. This can make an unrelated stack's commit appear deployable, trigger `stack.schedule_merges`, and fire `Hook.emit(:deployable_status, ...)`, i.e., "a payload for one repository mutating another's stack/commit" — squarely Critical severity as defined. It is repeatable against any commit sha the attacker can guess/observe (commit SHAs are often public via GitHub), across arbitrary stacks in the same Shipit instance.

### Likelihood Explanation
Preconditions: the attacker needs at least one repository already registered/onboarded with Shipit (a normal, unprivileged state — any repo owner can be onboarded) so that `verify_signature` succeeds for their own org's secret. They need to know or guess a target SHA (commit hashes are frequently public). No Shipit session, API token, or cross-org secret is required. Cost is a single crafted HTTP POST to `/webhooks` with a valid `status` event and correct signature for their own organization. This is easily repeatable and requires no interaction from the victim.

### Recommendation
Scope `StatusHandler#process` to only commits within the repository named in the payload, using the inherited `stacks` helper, e.g.:
```ruby
def process
  Commit.where(sha: params.sha, stack: stacks).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual; illustrates the missing binding)
test "stacks resolves correctly from payload but process ignores it" do
  victim_stack = shipit_stacks(:shipit)
  victim_commit = victim_stack.commits.create!(sha: 'deadbeef' * 5, message: 'victim commit')

  forged_payload = {
    'repository' => { 'full_name' => 'attacker-org/attacker-repo' },
    'sha' => victim_commit.sha,
    'state' => 'success'
  }

  handler = Shipit::Webhooks::Handlers::StatusHandler.new(forged_payload)

  attacker_stack_ids = handler.send(:stacks).pluck(:id)
  assert_not_includes attacker_stack_ids, victim_stack.id # proves `stacks` correctly resolves to attacker's own (irrelevant) scope

  assert_difference -> { victim_commit.reload.statuses.count }, 1 do
    handler.process # mutates victim's commit despite zero overlap with handler.stacks
  end
end
```
This demonstrates: `handler.send(:stacks)` (inherited, repository-scoped) contains none of the victim's stacks, yet `handler.process` still mutates the victim commit — confirming the fix (`Commit.where(sha:, stack: stacks)`) is a same-class, already-available equality check that is currently skipped.
