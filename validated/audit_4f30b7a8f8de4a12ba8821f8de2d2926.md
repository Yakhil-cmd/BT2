### Title
Third-party dust top-ups keep an insolvent account above the $5 bad-debt gate, DoS-ing permissionless `clean_bad_debt` - (File: contracts/controller/src/positions/liquidation/mod.rs)

### Summary
`clean_bad_debt` is permissionless but gated by `is_socializable_bad_debt`: cleanup is only admitted when `total_debt > total_collateral && total_collateral <= BAD_DEBT_USD_THRESHOLD` ($5 WAD USD) (`contracts/controller/src/positions/liquidation/curve.rs:25-27`, `contracts/controller/src/positions/liquidation/mod.rs:229-235`). At the same time, `supply` deliberately lets any unauthenticated third party top up a collateral leg an account already holds — `require_third_party_existing_supply` only blocks opening *new* asset slots on foreign accounts, and `process_supply`/`process_deposit` run no solvency or health check on the target (`contracts/controller/src/positions/supply.rs:61-97`, `docs/reference/invariants.md:43-48` INV-AUTH-03). An attacker can therefore grief the dust-gated cleanup path: every time collateral approaches the $5 ceiling, a small top-up of an existing leg pushes `total_collateral` above the threshold and `clean_bad_debt` reverts with `CannotCleanBadDebt`.

### Finding Description
The Megapot bug class is "cheap occupancy of a gated resource at near-zero cost to disable a protocol function." Here the gated resource is the permissionless bad-debt socialization window:

- `socialize_bad_debt` admits a `DustCapped` cleanup only when `is_socializable_bad_debt` holds (`mod.rs:212-243`).
- `supply(caller, account_id, spoke_id, assets)` with a nonzero `account_id` belonging to someone else succeeds as long as every leg names a hub asset the account already supplies (`supply.rs:78-97`).
- Nothing in `process_supply` checks that the target account is insolvent, liquidatable, or awaiting cleanup; deposits only ever improve the account's collateral total.
- The bad-debt account necessarily holds a supply leg (its residual collateral), so there is always at least one leg the attacker is allowed to top up.

Each top-up must move `total_collateral` strictly above $5, so one blocking deposit costs roughly >$5 of token value that is donated into the victim's account (the attacker cannot withdraw it — `withdraw` requires owner/delegate auth). The attacker repeats the top-up whenever liquidation or accrual drags collateral back under the cap.

### Impact Explanation
**Medium.** While the griefing persists, permissionless `clean_bad_debt` cannot execute, so residual bad debt is not socialized and keeps accruing interest inside the borrow book; supplier indexes cannot be written down and spoke usage stays locked (`docs/reference/invariants.md:463-479` INV-LIQ-04). The debt is only removed when (a) liquidators fully repay it — the topped-up collateral is seizable, so each >$5 blocking deposit is progressively consumed by liquidators — or (b) governance executes the owner-gated `force_socialize_bad_debt` runbook (`mod.rs:246-249`, `docs/reference/runbooks/force-socialize-bad-debt.md:43-46`). The analog to the Megapot report's effect — a protocol function disabled at bounded attacker cost — holds; the loss is bounded by the collateral donations and the existence of the governed fallback keeps it below High.

### Likelihood Explanation
**Low-Medium.** The attacker gains nothing directly and donates >$5 per blocking round, mirroring the report's own "Low" rationale. Execution is trivial: a single `supply` call per round against a known insolvent `account_id`, no timing constraints. The attack is self-limiting because each donated top-up is claimable by liquidators and eventually retires the debt outright, and governance can force-socialize at any collateral size.

### Recommendation
Restrict third-party `supply` top-ups on accounts that are insolvent (`total_debt > total_collateral`) or liquidatable (HF < 1), so griefers cannot re-inflate the collateral total that the dust gate reads. Alternatively, have `clean_bad_debt` evaluate eligibility on a snapshot taken before any same-transaction top-up, or net same-market supply/debt pairs before applying the dust threshold — the docs already note cleanup does not net such pairs (`docs/explanation/threat-model.md:302-308`).

### Proof of Concept
1. A borrower account goes insolvent after a price crash: e.g., $3 of USDC collateral vs $10 of debt (the state built by `policy_zero_threshold_account_is_still_socializable_as_bad_debt`, `contracts/controller/tests/positions/liquidation_zero_threshold.rs:477-494`). `clean_bad_debt` is callable by anyone.
2. Attacker calls `supply` with `caller = attacker`, `account_id = victim`, one leg of the victim's existing collateral asset worth $5.01. `require_third_party_existing_supply` passes because the leg already exists (`supply.rs:86-96`).
3. `total_collateral` is now > `BAD_DEBT_USD_THRESHOLD`; `clean_bad_debt` reverts `CannotCleanBadDebt` (`mod.rs:229-235`). `force_socialize_bad_debt` is owner-gated and requires a governance delay.
4. If a liquidator seizes the donated collateral, the attacker repeats step 2 — each round costs just over $5 — keeping the permissionless cleanup path closed for as long as the attacker funds it.
