### Title
Cross-repository forgery of commit statuses via unscoped SHA lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates a webhook by deriving the signing organization solely from `params.dig('repository','owner','login')` (falling back to `params.dig('organization','login')`), and validates the HMAC using that organization's `webhook_secret`. [1](#0-0) [2](#0-1)  This authenticates the *organization/repository claiming to send the event*, but `StatusHandler#process` never re-checks that the commit being mutated actually belongs to that repository — it looks up commits globally by SHA across the entire `commits` table.

### Finding Description
The base `Handler` class exposes a `repository_name`/`stacks` helper that scopes lookups to the repository named in the payload [3](#0-2) , and most handlers (e.g. `PushHandler`) use it to constrain writes to stacks belonging to the authenticated repository [4](#0-3) . `StatusHandler`, however, bypasses this scoping entirely:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [5](#0-4) 

This means the binding that should hold — *"the organization whose signature was verified" == "the repository/stack whose commit status is mutated"* — is broken. The signature check authenticates organization `A` (derived from `repository.owner.login`), but the actual write (`create_status_from_github!`, which creates a `Status` record and can trigger `Hook.emit(:commit_status, ...)`/`:deployable_status` and `stack.schedule_merges`) applies to **every** `Commit` row across **all** stacks/repositories/organizations whose `sha` column matches the attacker-supplied `params.sha`, regardless of which org or stack that commit actually belongs to.

An attacker who controls (or has push/CI access to) any single repository that Shipit is configured to receive webhooks for can send a legitimately-signed `status` event for their own repository, but populate the `sha` field with a commit SHA that they know (or brute/guess) exists in a different, victim stack. Because Git SHAs are frequently shared across forks, mirrors, cherry-picked commits, or repositories seeded from a common template/initial commit, this is a realistic collision vector, and nothing in `StatusHandler` prevents it even when SHAs don't collide by chance — the handler simply never checks `repository_name` at all.

### Impact Explanation
This breaks the "organization authenticated" vs "repository written" trust binding described in the audit's Pool analogy: just as `reallocate()` acted on the wrong balance target, `StatusHandler` mutates commit-status state for a stack it never validated ownership of. Consequences include:
- Injecting fake success/failure/pending commit statuses on a victim's commits, which can flip `Commit#deployable?` and influence `stack.schedule_merges` / continuous deployment gating (`Commit#schedule_continuous_delivery`) on a stack the attacker does not control. [6](#0-5) [7](#0-6) 
- This can enable an unauthorized deploy/merge decision on the victim stack by forging a passing CI status, without ever holding credentials for the victim's organization or repository.

This matches the "unauthorized deploy, rollback or merge" Critical-tier impact bucket, contingent on the attacker being able to produce or predict a colliding SHA in the target stack.

### Likelihood Explanation
Medium. It requires the attacker to control at least one repository/organization already configured in Shipit (so they can get a validly-signed webhook), and to know or engineer a SHA collision with a commit tracked in the victim stack. This is not a "just send any request" bug — it needs an in-scope, unprivileged-but-legitimate webhook sender plus a SHA that also exists in the target stack's `commits` table (achievable via forks/mirrors/shared history, or by waiting for the target's known public commit SHA and replaying it before/without owning that repo, since GitHub commit statuses accept arbitrary `sha` values that need not exist in the sender's own repo to be technically well-formed and signed).

### Recommendation
Scope `StatusHandler#process` to the repository from which the event was authenticated, mirroring `PushHandler`'s use of the `stacks` helper, e.g. only update commits belonging to `stacks` (or `Repository.from_github_repo_name(repository_name)`) instead of a bare `Commit.where(sha: params.sha)` across the whole table.

### Proof of Concept
1. Attacker has push/webhook-trigger rights on `attacker-org/attacker-repo`, which is registered in Shipit's multi-org GitHub config (see `docs/setup.md` "Using Multiple GitHub Applications"). [8](#0-7) 
2. Victim stack `victim-org/victim-repo` has a tracked commit with SHA `deadbeef...` (obtainable publicly or via a forked/mirrored history that shares commits with `attacker-repo`).
3. Attacker sends (or triggers, e.g. via their own CI hitting the Status API for their repo but for a SHA that also matches victim's commit row) a `status` webhook event with `repository.owner.login = attacker-org` and `sha = deadbeef...`, `state = success`.
4. `WebhooksController#verify_signature` verifies the signature using `attacker-org`'s legitimate webhook secret and passes. [1](#0-0) 
5. `StatusHandler#process` runs `Commit.where(sha: 'deadbeef...')`, which returns the victim's `Commit` row too, and calls `create_status_from_github!` on it — forging a status on `victim-repo`'s commit despite the signature only proving control of `attacker-org`. [5](#0-4)
