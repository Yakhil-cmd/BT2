### Title
Route-selected contract can execute unauthorized wallet transfers under the caller’s signed authorization tree - (File: `contracts/controller/src/strategies/swap.rs`)

### Summary
`swap_collateral`, `multiply`, `swap_debt`, and `repay_debt_with_collateral` accept caller-controlled route bytes and execute them through the configured swap router while the caller’s authorization is active. Because route venues are not allowlisted, a malicious pool can invoke an unrelated token’s `transfer(caller, attacker, amount)`; Soroban simulation records that call as a child of the caller’s strategy authorization, and signing the poisoned tree makes the transfer succeed. [1](#0-0) [2](#0-1) 

### Finding Description
`process_swap_collateral` authenticates the caller and account owner, then forwards the attacker-controllable `swap` payload into `withdraw_and_swap_from_supply`. [3](#0-2)  `swap_tokens` grants only an exact controller-to-router input transfer, but it does not constrain what code the router executes beneath the still-active caller authorization. [4](#0-3)  The project’s own authorization test demonstrates that a rogue hop pool can call `token.transfer(alice, attacker, balance)` and have that operation join Alice’s `swap_collateral` authorization tree. [5](#0-4) 

### Impact Explanation
A malicious route can steal arbitrary spendable tokens directly from the caller’s wallet, including assets unrelated to the lending position and exceeding the swap input amount. [6](#0-5)  The token transfer is authorized by the victim’s signed simulation tree, while the legitimate collateral swap can still complete, making the theft appear to be part of a valid strategy execution. [7](#0-6)  This is theft of user funds and rates High: the loss can equal the victim’s full balance in targeted tokens, although exploitation requires the victim to sign the poisoned authorization tree.

### Likelihood Explanation
Any unprivileged route producer can reference an unallowlisted malicious pool contract and induce a user to execute the resulting strategy. [8](#0-7)  The controller and router measurements only bound routed input and output; they do not prevent an additional token movement authorized as a child invocation. [9](#0-8)  The repository’s threat model explicitly identifies this signed-tree exposure and relies on external clients to decode and reject unexpected child authorizations. [10](#0-9) 

### Recommendation
Do not allow arbitrary route-selected contracts to execute while the end user’s authorization can satisfy nested `require_auth` calls. Ideally, isolate route execution behind an intermediate contract whose calls cannot consume the user’s root authorization, or constrain `StrategySwap` to a protocol-verified venue allowlist. At minimum, require wallets and simulation clients to reject any authorization tree containing calls other than the intended strategy’s explicit input transfer, and surface unexpected child invocations as blocking errors rather than signing them. [11](#0-10) [10](#0-9) 

### Proof of Concept
1. Create a malicious pool contract whose swap entrypoint calls `token::Client::new(wallet_token).transfer(victim, attacker, wallet_balance)`. [12](#0-11) 
2. Build a `swap_collateral` route that pays a fair output through that pool and call `swap_collateral(caller, account_id, current, from_amount, new, route)`. [13](#0-12) 
3. During simulation, the rogue wallet transfer is recorded as a child invocation beneath the caller’s `swap_collateral` authorization. [5](#0-4) 
4. If the caller signs the simulated tree unchanged, the same transaction transfers the full unrelated wallet-token balance to the attacker while crediting the expected swap output to the lending account. [6](#0-5)

fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {

    let route = s.route_through_pool_stealing(WALLET_BALANCE);

/// Authorizes, on behalf of the current contract, one `transfer(from, to, amount)`
/// call on `token_addr` made deeper in the next contract call (for example by
/// the pool). The entry allows no further sub-invocations.
pub fn authorize_transfer_as_current(
    env: &Env,
    token_addr: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
) {
    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);
