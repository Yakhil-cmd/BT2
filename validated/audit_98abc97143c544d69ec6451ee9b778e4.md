### Title
Webhook organization used for signature verification is decoupled from the repository the payload writes to - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to verify the HMAC signature against using `repository_owner`, taken from `params.dig('repository','owner','login')`. [2](#0-1) [3](#0-2) 
Every event handler, however, resolves the target `Repository`/`Stack` from a *separate* field, `params.dig('repository','full_name')`, via `Handler#repository_name` and `Repository.from_github_repo_name`. [4](#0-3) [1](#0-0) 
Because the HMAC signature is validated using the secret belonging to `repository.owner.login`, while the actual write target is picked from the independent `repository.full_name` field, the two values are never required to agree.

### Finding Description
The binding that should hold is: `organization whose secret authenticated the request == organization that owns the repository being written to`. Nothing in the code enforces this equality.

In a multi-org deployment (the documented "Using Multiple GitHub Applications" configuration, see `docs/setup.md` and `test/dummy/config/secrets_double_github_app.yml`), each org may configure a `webhook_secret`, but it is explicitly documented as optional (`webhook_secret: # nil`) in the setup docs and example secrets files. [5](#0-4) 
`GitHubApp#verify_webhook_signature` short-circuits to `true` whenever no secret is configured for the resolved organization: [6](#0-5) 

An attacker who knows (or guesses) that org `orgA` is configured without a `webhook_secret` can send a forged webhook to `/webhooks` with:
- `repository.owner.login = "orgA"` (or `organization.login`, used as fallback) → selects `orgA`'s `GitHubApp`, whose `verify_webhook_signature` auto-passes because `webhook_secret` is blank.
- `repository.full_name = "orgB/secured-repo"` → the event handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, pull-request handlers, etc.) all derive the target `Repository`/`Stack` from this field, completely ignoring `repository.owner.login`. [7](#0-6) 

The signature is computed over the full raw JSON body, so it is not that the field is "outside" the signed payload as in the original StRSR bug — rather, the value that gates *which* secret is used to check the signature (`repository.owner.login`) is not the same value later used to decide *what gets written* (`repository.full_name`). This is exactly the class of binding break called out in the rules ("an organization that authenticated versus the repository that is written").

### Impact Explanation
This lets an attacker who only needs to know one organization's repo-owner name (which is public information, and often the low-security/no-secret org in a multi-org setup) forge webhook events that are accepted as if delivered by GitHub, and then act on any other stack/repository hosted by the same Shipit instance, including ones belonging to organizations that *do* have a secret configured. Concretely, `StatusHandler`/`CheckSuiteHandler` create `Status`/`CheckRun` records for a targeted commit purely from payload content, and these statuses feed directly into `Commit#deployable?` and the merge-queue's CI gating logic (`ci.require`, `merge.require` in `shipit.yml`) — i.e., forging a "success" status for a commit on a repo you don't control can make Shipit consider it deployable/mergeable when it should not be, an unauthorized deploy/merge condition, which matches the Critical/High impact bar defined in the rules ("an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Requires: (1) Shipit configured with more than one GitHub organization (documented, supported feature), (2) at least one configured organization without a `webhook_secret` (explicitly shown as the default/example configuration), and (3) attacker knowledge of that organization's login name and the target repository's `owner/name`. No GitHub credentials, session, or API token are required — only the ability to POST to the public `/webhooks` endpoint, matching the "unprivileged attacker" scope of this analog.

### Recommendation
In `WebhooksController#verify_signature`, require that `params.dig('repository','owner','login')` (the value used to select the verifying `GitHubApp`) is identical to the owner portion of `params.dig('repository','full_name')` before allowing further processing (or better, have every handler resolve the repository via the same organization value that was used to validate the signature, not via an independently-parsed `full_name`). Additionally, treat a missing `webhook_secret` in multi-org configurations as a hard configuration error rather than an implicit signature bypass.

### Proof of Concept
1. Configure Shipit with two orgs: `orgA` (`webhook_secret: nil`) and `orgB` (`webhook_secret: "s3cret"`), each with an existing `Stack` for `orgA/repo-x` and `orgB/repo-y` respectively.
2. POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/repo-y" },
  "sha": "<commit sha in orgB/repo-y>",
  "state": "success",
  "context": "ci/required-check"
}
```
3. `verify_signature` resolves `Shipit.github(organization: "orgA")`, whose `webhook_secret` is `nil`, so `verify_webhook_signature` returns `true` unconditionally regardless of the (missing/incorrect) `X-Hub-Signature` header. [6](#0-5) 
4. `StatusHandler`/`Handler#stacks` resolves the target using `full_name = "orgB/repo-y"`, unrelated to `orgA`, and creates a forged success `Status` on `orgB`'s protected repository/commit. [4](#0-3)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
