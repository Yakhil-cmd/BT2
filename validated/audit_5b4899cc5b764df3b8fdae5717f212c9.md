### Title
Attacker-controlled PR labels injected into deploy env override BASE_ENV safety stripping via `Command#unbundled_env`, enabling arbitrary `RUBYOPT`/env-var injection into spawned deploy commands - (File: `app/models/shipit/review_stack.rb`)

### Summary
`ReviewStack#env` merges every GitHub PR label name (upcased, value `"true"`) directly into the environment hash used to run deploy/task commands, with no allowlist or filtering. `TaskCommands#env` merges `@stack.env` (which includes these labels) *before* `deploy_spec.machine_env` and `@task.env`, so a label such as `RUBYOPT` is not overwritten unless the deploy spec explicitly redefines that exact key. The resulting hash reaches `Command#unbundled_env`, which merges `@env` over `BASE_ENV`/`PATH`, and is passed straight into `PTY.spawn`, so an attacker who labels their own PR can inject `RUBYOPT` (or other Ruby/Bundler-sensitive variables) into the ruby/bundler processes that run on the deploy host.

### Finding Description
The binding assumed safe is: `keys(Command#unbundled_env.@env) == keys(deploy_spec's declared VariableDefinitions ∪ Shipit hardcoded vars)`. This is false — `ReviewStack#env` injects unconstrained keys derived from `pull_request.labels`: [1](#0-0) 

`pull_request.labels` is populated verbatim from the webhook payload's label names with no format or allowlist validation: [2](#0-1) 

`TaskCommands#env` builds the final environment by merging, in order: `super` (base `Commands#env`), then `@stack.env` (includes the label-derived keys via `ReviewStack#env`), then hardcoded Shipit vars, then `deploy_spec.machine_env`, then `@task.env`: [3](#0-2) 

None of the later merges (`deploy_spec.machine_env`, `@task.env`) remove or reset keys they don't explicitly define — Ruby hash merge is additive per-key, so an attacker-chosen label key such as `RUBYOPT` survives untouched into the final env hash, since deploy specs never declare `RUBYOPT` as a machine env var or task var.

This hash is passed to `Command.new(..., env:, ...)`, stored as `@env`, and then combined in `Command#unbundled_env`: [4](#0-3) 

`BASE_ENV` is derived from `Bundler.unbundled_env`/`Bundler.clean_env`, which is specifically designed to strip Bundler/Ruby-poisoning variables like `RUBYOPT`, `RUBYLIB`, `BUNDLE_GEMFILE`, etc., from the spawned environment: [5](#0-4) 

But `unbundled_env` re-merges `@env` (attacker-controlled) *on top* of that sanitized `BASE_ENV`, re-introducing exactly the variable Bundler intentionally cleaned. The final hash is handed to `PTY.spawn`: [6](#0-5) 

**Attack**: An attacker who owns/controls a repository with an active Shipit `ReviewStack` (opened PR) adds a label literally named `RUBYOPT` (case-insensitive, upcased by the code) via the GitHub UI/API on their own PR, which triggers a `labeled` webhook, processed by `LabelCapturingHandler#capture_labels`, updating `pull_request.labels`. On the next `install_dependencies` or `deploy` task run for that review stack, `TaskCommands#env` includes `'RUBYOPT' => 'true'`, and this value (or any other value if a more useful trick label could be used, e.g. label names allowing `-r` style injection are constrained by upcasing but the mechanism generalizes to any unfiltered env var name) is passed into the `ruby`/`bundle`/`rake` invocations of the deploy steps on the deploy host.

Existing guards do not stop this: `filter_deploy_envs`/`filter_task_envs` (`EnvironmentVariables#permit` against `VariableDefinition`s) are only applied to explicit `@task.env` supplied at deploy trigger time — not to `@stack.env`, which is where the label injection occurs. The webhook `params` schema (`LabelCapturingHandler`) validates types/presence but not label *content*, and only permits string label names, not the semantic use of upcased label names as env var keys.

### Impact Explanation
Injecting arbitrary environment variable names/values (constrained only by GitHub's label-name character set and the code's `.upcase` transform) into commands executed by `PTY.spawn` on the deploy host is a Critical-severity RCE primitive per this engine's own env-merge and command-execution code (`Command#unbundled_env`, `PTY.spawn`). `RUBYOPT` demonstrates the class of bug (Ruby/Bundler behavior-altering env vars bypassing Bundler's clean-env protection); other labels could similarly inject variables like `BUNDLE_GEMFILE`, `GIT_SSH_COMMAND`, `LD_PRELOAD`-adjacent hooks depending on what the deploy steps invoke, extending impact toward arbitrary code execution in the spawned processes. This is repeatable by any unprivileged GitHub user who can label their own PR against any repository with an active review stack, with no operator or maintainer approval gating the label webhook.

### Likelihood Explanation
Preconditions: the target repository must have Shipit's review-stack feature configured and an active (non-archived) `ReviewStack`/PR for the attacker to label — a standard, commonly-enabled configuration, not a privileged one. The attacker needs no Shipit credentials, session, or API token; they only need to label a PR they control (or, if review stacks activate on `opened`, simply open+label a PR) in their own fork/branch, which is within the described unprivileged attacker capability set. Cost is minimal (one GitHub label), and the attack is fully repeatable across any review-stack-enabled repository the attacker can open PRs against.

### Recommendation
Do not use PR label names as raw environment variable keys. In `ReviewStack#env`, restrict merged label-derived keys to an explicit allowlist (e.g. only labels declared via `deploy_spec` review variables), or namespace them (e.g. `LABEL_<name>`) so they cannot collide with sensitive interpreter/bundler env vars. Additionally, apply `EnvironmentVariables#permit`/`VariableDefinition`-based filtering to the merged `@stack.env` in `TaskCommands#env`, and explicitly blocklist dangerous variable names (`RUBYOPT`, `RUBYLIB`, `BUNDLE_GEMFILE`, `LD_PRELOAD`, `GIT_SSH_COMMAND`, etc.) from ever being settable via label-derived or otherwise unauthenticated inputs before they reach `Command#unbundled_env`.

### Proof of Concept
```ruby
# test/unit/task_commands_env_test.rb (conceptual; place under test/ per repo conventions)
class TaskCommandsEnvTest < ActiveSupport::TestCase
  test "PR label RUBYOPT survives into TaskCommands#env and Command#unbundled_env" do
    stack = shipit_review_stacks(:review_stack) # active ReviewStack fixture
    stack.pull_request.update!(labels: ['RUBYOPT'])

    task = shipit_tasks(:deploy_for_review_stack) # or create a Deploy on stack
    commands = Shipit::TaskCommands.new(task)

    env = commands.env
    assert_equal 'true', env['RUBYOPT'], "label-derived RUBYOPT should be absent but is present"

    command = Shipit::Command.new('true', env:, chdir: Dir.tmpdir)
    final_env = command.unbundled_env
    assert_equal 'true', final_env['RUBYOPT'],
      "Bundler.unbundled_env strips RUBYOPT but attacker-controlled @env re-injects it, binding violated"
  end
end
```
Both sides of the binding — `Command#unbundled_env` keys vs. deploy-spec-declared `machine_env`/`VariableDefinition` names — diverge: `RUBYOPT` is present in the spawned env despite not being declared anywhere in the deploy spec, confirming the vulnerability.
