### Title
Webhook signature is verified against the payload's `repository.owner`/`organization` login, but the event is applied to whatever `repository.full_name` the payload names, allowing cross-organization event forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App (and thus the webhook secret) used to validate `X-Hub-Signature` based on `repository_owner`, computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. [1](#0-0)  However, the actual side effects performed by the event handlers (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc.) resolve the target repository/stack using `payload.dig('repository', 'full_name')` via `Handler#repository_name`/`#stacks`, which is a *separate* field from the one used for signature-org selection. [2](#0-1)  Nothing in `WebhooksController#create` re-checks that the org whose secret validated the signature actually owns the repository being mutated. [3](#0-2) 

### Finding Description
This is a real instance of the "organization authenticated vs. repository written" binding failing to hold as an equality.

- **What should hold:** `organization_that_signed(payload) == organization_that_owns(repository_acted_on(payload))`.
- **What actually happens:** `verify_signature` picks the GitHub App/webhook secret using `repository_owner` (from `repository.owner.login`, or falling back to `organization.login`). [4](#0-3)  The handler dispatch (`create`) then hands the **entire raw JSON payload** to `Shipit::Webhooks.for_event(event)` handlers with no re-validation of which repo it targets. [3](#0-2)  Each handler independently derives the target repository from `payload.dig('repository', 'full_name')`. [2](#0-1) 

Because a Shipit instance can be configured with **multiple GitHub Apps for multiple organizations** (documented explicitly in `docs/setup.md`, "Using Multiple Github Applications"), each organization's operator/admin knows their own app's `webhook_secret`. Nothing forces `repository.owner.login`/`organization.login` (used to pick the secret) to match `repository.full_name`'s owner (used to find the `Repository`/`Stack` to mutate). An attacker who legitimately controls one configured organization's webhook secret can craft a payload where:
- `repository.owner.login` = their own org (so `verify_signature` picks their own valid secret and signs successfully), and
- `repository.full_name` = `victim-org/victim-repo` (a repository tracked by Shipit under a different, unrelated organization).

`StatusHandler#process` will then look up `Commit.where(sha: params.sha)` — note this is **global across all repositories**, not scoped by owner at all — and call `commit.create_status_from_github!(params)`, letting the attacker forge a passing (`state: "success"`) CI status for any commit SHA already known to Shipit, regardless of which org's secret signed the request. [5](#0-4)  `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name(repository_name)` (again taken from the attacker-controlled `repository.full_name`) and calls `stack.sync_github(expected_head_sha: params.after)` on any matching, non-archived stack. [6](#0-5)  `Repository.from_github_repo_name` performs no ownership cross-check against the org that authenticated the webhook. [7](#0-6) 

### Impact Explanation
This breaks a deployment-trust binding at High/Critical severity: an attacker who only controls the webhook secret for *one* GitHub organization configured on a shared Shipit instance can forge `status` (and `push`/`check_suite`) events targeting repositories/commits owned by a completely different organization also hosted on that instance. Forging a green CI status (`state: success`) for an arbitrary commit SHA can cause Shipit's merge-queue/deploy-safety logic to treat unreviewed or malicious code as CI-passing, enabling an unauthorized deploy/merge of that commit — i.e., escalation into cross-repository writes / unauthorized deploy, matching the report's "High"/"Critical" impact categories. It exploits exactly the same trust-binding root cause as the AURA bug (a check performed against one identity, an effect applied to a different, unbound target), just here it's org-owns-secret vs. repo-owns-webhook-authority.

### Likelihood Explanation
Requires the Shipit instance to be configured for multiple GitHub organizations (a documented, supported configuration) and requires the attacker to know or control the webhook secret of at least one of those orgs (e.g., because they administer that org's GitHub App) plus knowledge of a target commit SHA/repo full_name in another org tracked by the same instance (both are public/discoverable, e.g. via git history or the Shipit UI itself). This is a realistic multi-tenant misconfiguration scenario explicitly supported by the codebase's own documentation, not a purely theoretical one.

### Recommendation
In `WebhooksController`, after verifying the signature, re-derive the repository owner strictly from `repository.full_name`/`repository.owner.login` and reject (422) the request if it doesn't match the organization whose secret validated the signature. Additionally, scope `StatusHandler#process`'s `Commit.where(sha: params.sha)` lookup to commits belonging to the verified repository/organization rather than searching globally, and have `Handler#stacks`/`Repository.from_github_repo_name` verify that the resolved repository's `owner` equals the organization that authenticated the webhook before performing any writes.

### Proof of Concept
1. Configure Shipit (per `docs/setup.md`'s multi-org example) with two GitHub Apps: one for `attacker-org` (secret known to the attacker, who administers that org's GitHub App) and one for `victim-org` (tracking a Stack for `victim-org/victim-repo`).
2. Attacker builds a `status` webhook payload:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature` using `attacker-org`'s webhook secret over this exact payload (valid, since they control that secret).
4. POST to `/github/webhooks` with `X-Github-Event: status`.
5. `verify_signature` resolves `repository_owner` = `"attacker-org"` from `repository.owner.login`, fetches `Shipit.github(organization: "attacker-org")`, and successfully verifies the signature against the attacker's own secret. [8](#0-7) 
6. `create` dispatches to `StatusHandler`, which finds the victim's commit by SHA (global lookup, no owner check) and records a forged "success" status on it. [5](#0-4) 
7. The victim commit now shows a fabricated passing CI status it never actually received, potentially unblocking merge/deploy gating that depends on that status.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
```
