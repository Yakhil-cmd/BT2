## MembershipHandler abuses cross-organization team authorization via webhook org/repository binding mismatch - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and thus which `webhook_secret`) to validate an inbound webhook against by reading `repository.owner.login` (falling back to `organization.login`) straight out of the *unverified* JSON body [1](#0-0) . The `membership` event handler, however, trusts a *separate* field of the same unverified body — `params.organization.login` — to decide which `Team#organization` a synced GitHub team is filed under, and that `organization` attribute is exactly what `User#authorized?` checks against `Shipit.github_teams` to grant application access [2](#0-1) [3](#0-2) . Because signature validation is keyed by one field and the write is keyed by a different, independently-controlled field of the same body, an attacker who can get any signature check to pass (e.g. by targeting a configured GitHub organization that has no `webhook_secret` set, which `verify_webhook_signature` explicitly treats as "always verified" [4](#0-3) ) can create/repopulate a `Team` record tagged with an **arbitrary** `organization` value of their choosing, including the name of `Shipit.github_teams`'s protected org/team, and add arbitrary GitHub logins as members of it.

### Finding Description
The binding that should hold is: *the organization whose webhook secret authenticated this request* == *the organization the resulting `Team`/membership write is attributed to*. This engine breaks that equality:

- `WebhooksController#repository_owner` (used to pick the verifying `GitHub App`/secret) reads `params.dig('repository','owner','login') || params.dig('organization','login')` [5](#0-4) .
- `MembershipHandler#find_or_create_team!` independently reads `params.organization.login` from the same raw JSON to set `team.organization` [6](#0-5) .
- Both values come from the same attacker-controlled JSON body and are never cross-checked against each other.
- `verify_webhook_signature` returns `true` unconditionally when the resolved app's `webhook_secret` is blank [4](#0-3) , which is a normal, documented configuration state for a Shipit installation (the example/multi-org config templates ship with `webhook_secret: # nil`) [7](#0-6) .
- `Shipit.github(organization:)` requires `repository_owner` to match a configured org key, but does not require it to equal `params.organization.login` [8](#0-7) .

So an attacker who knows (or is allowed to interact with) any configured organization that has no `webhook_secret` configured can send a `membership` event where `repository.owner.login`/`organization.login` (top level, used only for signature routing) names that unsecured org, while the payload's `organization.login` used by the handler is fabricated arbitrarily. This lets them create a `Team` claiming to belong to any organization string, and add any GitHub login (real or fabricated) to it via `team.add_member(member)`.

### Impact Explanation
`User#authorized?` gates the entire application behind membership: `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [3](#0-2) , and `Shipit.github_teams` is derived from the configured `oauth.teams` handles matched against `Team#organization`/`slug` [9](#0-8) . By forging a `membership` webhook that is signature-validated against an unsecured org but whose `team`/`organization`/`member` fields target the *protected* org's team slug, an attacker can add an arbitrary GitHub `login` as a member of a `Team` row that subsequently satisfies `Shipit.github_teams` matching, escalating an untrusted GitHub identity into `authorized?` status — bypassing the org/team authorization gate that is supposed to restrict access to the whole Shipit instance. This maps to the "High" impact bucket ("escalation into `Shipit.github_teams` authorization").

### Likelihood Explanation
Exploitability depends on the deployment having at least one configured GitHub organization/app without a `webhook_secret` — a state the shipped example configs explicitly show as valid (`webhook_secret: # nil`), and multi-org Shipit installs are a documented, supported configuration [10](#0-9) . No session, `ApiClient` token, or the actual secret of the *targeted* organization is required — only that some configured org key lacks a secret, and knowledge of that org's name (often discoverable from `config/secrets.*.yml` filenames/docs or trial-and-error against the public `/webhooks` endpoint, since a wrong org returns a distinguishable `422 GithubOrganizationUnknown`).

### Recommendation
- In `WebhooksController`, derive the organization used for signature verification and the organization used by each handler from the *same*, single source of truth, and reject the request if `repository.owner.login`/`organization.login` used for verification does not match the `organization.login` acted upon by the handler.
- Do not allow `verify_webhook_signature` to silently pass (`return true unless webhook_secret`) for organizations that are used to authorize security-sensitive events like `membership`; require a webhook secret for any org whose teams are referenced in `Shipit.github_teams`.
- In `MembershipHandler#find_or_create_team!`, validate that `params.organization.login` matches the `repository_owner`/verified organization for the request rather than trusting it independently.

### Proof of Concept
1. Deploy Shipit configured for two GitHub organizations, e.g. `secured-org` (has `oauth.teams: ['secured-org/admins']` and a real `webhook_secret`) and `unsecured-org` (webhook_secret left blank, as shown in the shipped example config).
2. As an anonymous attacker, POST to `/webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "team": { "id": 999, "name": "admins", "slug": "admins", "url": "https://example.com" },
  "organization": { "login": "secured-org" },
  "member": { "login": "attacker-account" },
  "repository": { "owner": { "login": "unsecured-org" } }
}
```
No `X-Hub-Signature` header (or any value) is required, since `unsecured-org`'s app has no `webhook_secret`, so `verify_webhook_signature` returns `true` unconditionally.
3. `WebhooksController#repository_owner` resolves to `"unsecured-org"` and passes signature verification trivially; `Shipit::Webhooks.for_event('membership')` then invokes `MembershipHandler`, which reads `params.organization.login == "secured-org"` and creates/updates `Team(organization: "secured-org", slug: "admins")`, adding `attacker-account` as a member.
4. If `attacker-account`'s GitHub login later authenticates via OAuth (`GithubAuthenticationController#callback` / `User.find_or_create_from_github`), `User#authorized?` finds the forged `Team` membership and grants access, bypassing the intended `secured-org/admins` restriction.
