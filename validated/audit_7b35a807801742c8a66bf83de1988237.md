### Title
Tokens delivered to the controller outside the declared collateral/refund lists are permanently locked — there is no sweep or recovery path - (File: contracts/controller/src/strategies/flash_position.rs)

### Summary
Analogous to the OpenQ bounty report (issuer accepts multiple ERC20 deposits but only ever pays out one token, stranding the rest), the XOXNO Lending controller can end up holding token balances that no code path can ever return. There is no sweep endpoint on the controller, and every balance-sensitive flow measures only *deltas* against pre-call baselines. Any token amount sitting on the controller — a direct user transfer, or a `flash_position` callback delivery of an asset that is neither in `collaterals` nor `refund_assets` — is locked forever, benefiting nobody.

### Finding Description
`flash_position` measures collateral deposits and refunds strictly as positive balance deltas over baselines snapshotted *before* the receiver callback:

- `snapshot_balances` baselines are taken for declared collateral assets and `refund_assets` only (`flash_position.rs:120-143`).
- `collect_collateral_deposits` credits only declared collaterals' positive deltas; `refund_listed_assets` returns only refund-listed assets' positive deltas (`flash_position.rs:145-148`, `372-384`).

Anything else delivered to the controller is "neither deposited nor refunded" — confirmed by the protocol's own docs: "Undeclared callback assets receive neither credit nor refunds. There is no controller sweep endpoint" (`docs/reference/endpoints.md:86`) and "Returned debt is never auto-repaid: it can become declared collateral, be refunded when refund-listed, or remain uncredited" (`docs/explanation/decisions.md:258-259`, ADR-0020).

The codebase itself acknowledges that controller-held funds are unrecoverable: the `borrow`/`withdraw` recipient check exists precisely because "the controller holds funds no balance-delta measurement can ever claim" (`tests/test-harness/tests/controller/recipient_is_protocol_contract.rs:1-4`). That guard blocks borrow/withdraw payouts to the controller or pool, but no equivalent protection exists for tokens *pushed* to the controller — via `flash_position` callback deliveries of undeclared assets, leftover debt tokens returned but not refund-listed, or plain `token.transfer` donations to the controller or pool.

The same shape exists on the pool: "Direct donations do not rewrite those books" (`docs/explanation/threat-model.md:129-130`). Pool custody above the `cash` book belongs to no market, and no entrypoint (supply/withdraw/repay/recapitalize/claim_revenue/flash_loan) ever pays out unbooked balance — `cash` accounting ignores it entirely.

### Impact Explanation
Permanent freezing of funds. Tokens stranded on the controller or as unbooked pool balance are locked for the lifetime of the contract. In the `flash_position` variant the loss is compounded: leftover debt tokens returned to the controller without being refund-listed are locked *and* the account still owes the full minted debt, since "refunding it does not repay the minted debt" (`endpoints.md:84`).

### Likelihood Explanation
Reachable by a single unprivileged address:

- `token.transfer(user -> controller/pool, amount)` — any holder can do this; there is no recovery.
- `flash_position(caller, account_id, spoke_id, mode, debt, amount, receiver, data, collaterals, refund_assets)` — the caller's own receiver contract can push an asset not present in either list, or return residual debt tokens while omitting the debt asset from `refund_assets`. Validation only enforces list uniqueness, listing, and disjointness (`flash_position.rs:174-214`); it cannot force the caller to declare everything the callback will send. The integration suite even seeds nonzero controller donations to prove baselines exclude them (`tests/integration/flows/flash_position.sh:349-372`).

Likelihood is moderate because stranding one's own funds requires a misconfigured `refund_assets` list or an erroneous direct transfer — same self-inflicted-but-protocol-accepted profile as the original report (users "needlessly locking up their funds… with no benefit to anybody").

### Recommendation
Add a permissionless sweep entrypoint on the controller (and equivalently let the pool release balance above `cash`), sending unbooked balances to a designated address or back via a claim mechanism. Alternatively, for `flash_position`, auto-repay residual debt-token deltas and/or treat undeclared positive deltas as implicit refunds to the caller rather than leaving them stranded.

### Proof of Concept
1. Alice calls `flash_position` with `collaterals = [(USDC, min)]`, `refund_assets = []`, and a receiver that buys USDC plus pushes `X` extra ETH (or leftover debt tokens) to the controller.
2. After the callback, `collateral_before`/`refund_before` deltas for the undeclared ETH are never measured (`flash_position.rs:125-130`); ETH is neither deposited nor refunded.
3. The call succeeds (minima met, account solvent). The ETH now sits on the controller with no entrypoint capable of moving it — `borrow`/`withdraw` to the controller are rejected by `INVALID_FLASHLOAN_RECEIVER`, refunds only cover listed assets, and no sweep exists (`endpoints.md:86`).
4. Equivalently, a plain `token.transfer(alice, pool, X)` creates pool custody above `cash` that no market book ever references — permanently locked.
