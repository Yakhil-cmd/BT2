### Title
Webhook signature verification key is chosen from an unauthenticated `repository.owner.login` field that is decoupled from the `repository.full_name` used to select the target stack, allowing cross-organization webhook forgery when any configured GitHub App has no `webhook_secret` - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization config (and therefore which `webhook_secret`) to verify the HMAC against based on an attacker-controlled JSON field, `repository.owner.login` (falling back to `organization.login`), while the actual event handlers that execute after verification (e.g. `PushHandler`) resolve the target `Stack`/`Repository` using a *different* attacker-controlled field in the same payload: `repository.full_name`. These two fields are never checked for consistency, so the "organization whose secret authenticated the request" is not bound to "the repository that is actually acted upon."

### Finding Description
`verify_signature` picks the app config to verify against like this: [1](#0-0) 

```

  ...

Shipit explicitly supports and documents multi-organization deployments where each org has its own, independently-optional `webhook_secret`: [7](#0-6) [8](#0-7) 

In this documented topology, if **any one** configured organization has `webhook_secret: nil` (an explicitly supported value, shown in the example configs), the equality the app implicitly assumes — `organization whose secret verified the request == organization/repository the payload acts on` — is broken: an unauthenticated attacker can set `repository.owner.login` to the org with no secret (so `verify_webhook_signature` short-circuits to `true`), while setting `repository.full_name` to a repository belonging to a *different*, secret-protected organization that has a Stack configured in this Shipit instance. `check_if_ping`/`drop_unhandled_event` do not filter this, and `create` will invoke `PushHandler` (or other handlers keyed by `X-Github-Event`) against the victim organization's stack.

### Impact Explanation
This lets a fully unauthenticated network attacker trigger `Stack#sync_github` (and other event handlers such as `status`, `commit_status`, `deployable_status`, `check_suite`, `pull_request`, `membership`) against any stack/repository tracked by the Shipit instance, without possessing that repository's own webhook secret, GitHub App credentials, or any Shipit session/API token. Because CI/commit-status webhooks feed into Shipit's deployability gating and merge-queue/lock logic, an attacker who only needs one org in the fleet to be configured without a secret can forge status/push events for a *different, protected* org's repository — e.g., injecting a fabricated passing status or forcing a resync with an attacker-chosen `after` SHA — undermining the deploy-gating trust boundary the CI-status binding is meant to enforce, and can lead to unauthorized deploy/merge actions on a repository the attacker has no legitimate relationship to. This satisfies the "unauthorized deploy/merge/rollback" Critical-impact bucket.

### Likelihood Explanation
Requires no credentials of any kind for the target repository. It only requires that the Shipit instance is configured for multiple GitHub organizations and that at least one of those organizations (which need not be the victim) has `webhook_secret` unset — a state the project's own setup docs and example secrets files show as valid/expected ("(optional)"). Given that many real deployments track several orgs and treat `webhook_secret` as optional convenience, this is a realistic misconfiguration surface built into a documented, supported feature rather than a hypothetical one.

### Recommendation
Bind the verified identity to the acted-upon resource: after choosing `github_app` by `repository_owner`, verify that `repository.full_name`'s owner segment matches `repository_owner` before processing, and/or require `webhook_secret` to be present for every configured organization (reject requests, or refuse to boot with an org missing a secret when other orgs exist). At minimum, `Handler#repository_name`/`#stacks` should cross-check that the resolved `Repository`'s org matches the org that produced a valid signature.

### Proof of Concept
Assume `config/secrets.yml` configures multiple orgs (per docs/setup.md "Using Multiple Github Applications"), where `orgNoSecret` has `webhook_secret: nil` and `orgProtected/private-repo` is a tracked Shipit stack with `webhook_secret` set.

```
POST /webhooks
X-Github-Event: push
Content-Type: application/json

{
  "ref": "refs/heads/master",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "orgNoSecret" },
    "full_name": "orgProtected/private-repo"
  }
}
```

`repository_owner` resolves to `orgNoSecret`, whose `GithubApp#verify_webhook_signature` short-circuits `true` because `webhook_secret` is blank. `PushHandler` then resolves `repository_name` = `"orgProtected/private-repo"` and calls `stack.sync_github(expected_head_sha: "deadbeef...")` on the protected stack, entirely bypassing `orgProtected`'s own webhook secret. No test in `test/controllers/webhooks_controller_test.rb` exercises a mismatch between `repository.owner.login` and `repository.full_name`, confirming this cross-field trust binding is unchecked.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
