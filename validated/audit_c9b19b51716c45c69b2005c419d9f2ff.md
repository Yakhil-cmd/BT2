### Title
Failed beneficiary/curator payout in `child-bounties::claim_child_bounty` silently proceeds and permanently strands child-bounty funds — ([File: substrate/frame/child-bounties/src/lib.rs])

### Summary
The Gitcoin report shows funds becoming permanently locked in a Round contract because a required-but-unset fee address causes the payout transfer to revert, while the surrounding state transition (marking the round as paid out) is not gated on that transfer succeeding, and no recovery path exists afterward. The equivalent FRAME pattern exists in `pallet-child-bounties::claim_child_bounty`: the final payout `transfer` to `beneficiary` (and the curator-fee transfer) is dispatched, but its result is only checked with `debug_assert!`, not propagated as a `DispatchResult`. In a release-mode runtime this check compiles to nothing, so if the transfer fails (e.g., the destination account does not exist and the payout is below the Existential Deposit, or the account is otherwise unable to accept the currency), the extrinsic still deletes the child-bounty entry from storage and emits the `Claimed` event as if payment succeeded, leaving the funds stuck in the un-reachable `child_bounty_account_id` sub-account with no further code path to reclaim them.

### Finding Description
`claim_child_bounty` computes `payout` and dispatches two currency transfers from the child-bounty sub-account: [1](#0-0) 

Both results are checked only via `debug_assert!`, and the code comments state "Should not fail" without any protocol-level guarantee backing that assumption. Regardless of the transfer outcome, execution continues to unconditionally finalize state: [2](#0-1) 

This mirrors the audited Gitcoin bug precisely: a payout path assumes a downstream transfer cannot fail, does not gate irreversible state mutation on that transfer's success, and provides no fallback withdraw/reclaim mechanism if it does fail. `pallet-balances::transfer` with `AllowDeath` still requires the *receiver* to end up with at least the Existential Deposit if the receiver account does not already exist; a `payout` value below ED to a non-existent `beneficiary` account fails with `ExistentialDeposit`/`DeadAccount`-class errors. Since `award_child_bounty` lets the curator (a bounty-role account, not a privileged network/governance key) freely choose any `beneficiary` and the child-bounty `value`/`fee` split can yield an arbitrarily small `payout`, this failure condition is reachable through ordinary, permitted extrinsics (`propose_curator`/accept flow → `award_child_bounty` → `claim_child_bounty`), with no forged inherent, no stolen keys, and no privileged role required.

Critically, Parity has already recognized this exact bug class for the *parent* `pallet-bounties` pallet: PR #11045 added a permissionless `reclaim_bounty_funds` extrinsic specifically to sweep funds "stranded in a closed bounty's account" after such failures: [3](#0-2) [4](#0-3) 
That fix bumped only `pallet-bounties`, not `pallet-child-bounties`, and no equivalent `reclaim_child_bounty_funds` (or similar) function exists in `child-bounties/src/lib.rs`. The child-bounty sub-account (`child_bounty_account_id(parent_bounty_id, child_bounty_id)`) is a deterministic derived account with no owner able to sign a withdrawal, so once the `ChildBounties` storage entry is removed, the parent bounty/treasury/curator has no code path left to recover the stranded balance — an irreversible freeze, exactly analogous to the reported Solidity issue.

### Impact Explanation
Funds sent to fund a child-bounty (native currency held in a PVM/FRAME-derived sub-account) can become permanently unrecoverable whenever the final payout transfer to the beneficiary (or curator-fee transfer) fails for any reason not anticipated by the "should not fail" assumption — most concretely, a payout amount below the Existential Deposit paid to a not-yet-existing beneficiary account. This is a irreversible freezing of funds, matching the High-severity classification of the original report (funds locked with no recovery path), and directly parallels the bug class Parity itself patched for the sibling `pallet-bounties` pallet via `reclaim_bounty_funds`.

### Likelihood Explanation
Likelihood is moderate-to-high given ordinary permitted governance-free extrinsic flow: any curator (a normal signed account, not a privileged/root role) can `award_child_bounty` to an arbitrary `beneficiary`, and the resulting `payout = value - curator_fee` can easily fall below the runtime's Existential Deposit when a small child-bounty value is combined with a curator fee near that value, or when the beneficiary account is simply a fresh, never-before-used address. No malicious node/collator/validator, no forged inherent, and no stolen keys are needed — only a normal curator interaction with a chosen beneficiary account, which is entirely within the intended, permissionless usage of the pallet.

### Recommendation
Propagate the result of both `T::Currency::transfer` calls in `claim_child_bounty` as real `DispatchResult` errors instead of `debug_assert!`, so a failed payout aborts the extrinsic and the child-bounty remains in `PendingPayout` (retryable) rather than being deleted with funds stranded. Additionally, add a permissionless "reclaim" extrinsic for child-bounty sub-accounts, mirroring `pallet-bounties::reclaim_bounty_funds`, to sweep any residual balance back to the parent bounty/treasury account if a payout has already failed and the entry was removed under the current logic.

### Proof of Concept
No live/dynamic PoC was executed against a running node — this is a static-analysis-based analog derived strictly from the audited report's bug class (unchecked/assumed-infallible payout transfer + irreversible state finalization + missing recovery function), cross-referenced against the exact source lines cited above and against Parity's own acknowledgment of this bug class via the `reclaim_bounty_funds` fix (`prdoc/pr_11045.prdoc`) that was applied to `pallet-bounties` but not to `pallet-child-bounties`. A full local FRAME integration reproduction (constructing a child-bounty with `value`/`fee` combination that yields a sub-ED `payout` to a fresh beneficiary account, then calling `claim_child_bounty` and asserting the sub-account balance remains non-zero and unrecoverable afterward) was not run in this pass; confirming the exact ED/`transfer` failure semantics against the configured `Test`/production `Balances` config and asserting the stranded balance is required before treating this as fully proven.
