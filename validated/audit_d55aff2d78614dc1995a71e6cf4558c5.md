### Title
Webhook signature is verified against an attacker-chosen organization while payload writes target an unrelated repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate the `X-Hub-Signature` against using an **attacker-controlled JSON field** (`repository.owner.login`, falling back to `organization.login`), while every downstream `Webhooks::Handlers::Handler` subclass resolves the repository/stack to actually write to using a **different field** (`repository.full_name`) that is never cross-checked against the field used for signature verification.

### Finding Description
`repository_owner` is read straight from the untrusted JSON body and used to pick the org-scoped webhook secret to verify against: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: ...)` returns the `GithubApp` configured for that organization name and `verify_webhook_signature` only checks the HMAC against that org's `webhook_secret`: [3](#0-2) 

Once the signature check passes, `WebhooksController#create` dispatches the *entire* raw payload to the registered handler for the event, with no further binding of "the org whose secret validated the request" to "the repository the handler is about to mutate": [4](#0-3) 

Every handler base class then resolves the target repository/stack from a **separate** field, `repository.full_name`, which is completely independent of `repository.owner.login`: [5](#0-4) 

Concrete handlers use that lookup to perform writes with no additional owner/org validation, e.g.:
- `PushHandler` triggers `stack.sync_github(expected_head_sha:)` for stacks matched by `repository_name`/branch: [6](#0-5) 
- `StatusHandler` writes a commit status for **any commit matching the SHA anywhere in the Shipit instance**, with no repository check at all: [7](#0-6) 
- `MembershipHandler` creates/updates `Team` records keyed by `params.team.id`, again independent of the field used for signature verification: [8](#0-7) 

**The broken binding, stated as an equality that the code fails to enforce:**
`organization used to verify signature (payload["repository"]["owner"]["login"] or payload["organization"]["login"])` **==** `repository/commit actually written by the handler (payload["repository"]["full_name"] or bare params.sha)`

Any principal who legitimately controls a GitHub App/organization already configured in this Shipit instance's `secrets.yml` (and therefore knows that organization's `webhook_secret` — a routine thing for whoever set up that org's integration) can sign an arbitrary payload with their own org's secret while setting `repository.full_name` (or, for `status`, just `sha`) to point at a stack/commit belonging to an entirely different, unauthorized organization tracked by the same Shipit instance.

### Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" trust boundary called out explicitly in scope. Concrete exploitable outcomes:
- **Cross-repository/cross-org writes**: `StatusHandler` lets a caller who only owns Org A's webhook secret inject fabricated commit statuses (`state`, `context`, `target_url`) onto commits belonging to Org B's stacks, because the lookup is `Commit.where(sha: params.sha)` with no ownership check.
- **Unauthorized deploy enablement**: Forged passing statuses can satisfy a stack's `ci.require` gating (`DeploySpec`/`ci.require`), and combined with `continuous_deployment`, can trigger an **unauthorized deploy** of a repository the attacker does not control.
- `PushHandler`/`MembershipHandler` similarly act on data resolved from fields never bound to the verified signing organization, allowing state corruption (fake sync, forged team membership) across organizations.

This satisfies the required Critical/High impact bar (cross-repository writes / unauthorized deploy) without requiring a Shipit session, API token, or repository write access on the *victim* repo — only knowledge of a webhook secret for *some* organization already configured on the instance.

### Likelihood Explanation
Multi-org Shipit deployments are explicitly supported (`config/secrets.development.shopify.yml` shows a `github:` map keyed by multiple organizations, each with its own `webhook_secret`). In such deployments, each organization's own GitHub App owner is expected to know their org's `webhook_secret`, but nothing in the engine prevents that same principal from using it to forge writes against every other organization/stack hosted on the same Shipit instance. No special privilege beyond "administers one org's GitHub App on a shared Shipit instance" is required, making this a realistic, low-effort attack path.

### Recommendation
Never let signature verification and repository resolution use independent, attacker-controlled fields. Bind the two: after `verify_webhook_signature` succeeds for organization `O`, require `payload.dig('repository','owner','login') == payload.dig('repository','full_name').split('/').first` (or equivalently derive the "verified organization" once and pass it down to `Handler#stacks`/`StatusHandler#process`, rejecting/scoping any lookup whose resolved repository owner does not equal `O`).

### Proof of Concept
Given a Shipit instance configured with two orgs in `secrets.yml`, `org-a` (attacker-administered, secret known to attacker) and `org-b` (victim, has a tracked stack with commit `deadbeef` and `ci.require: [ci/tests]`):

```
POST /github/webhooks
X-Github-Event: status
X-Hub-Signature: sha1=<HMAC-SHA1(body, org-a's webhook_secret)>
Content-Type: application/json

{
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" },
  "sha": "deadbeef",
  "state": "success",
  "context": "ci/tests",
  "target_url": "https://fake",
  "created_at": "2026-09-01T00:00:00Z"
}
```

`verify_signature` resolves `repository_owner` = `"org-a"`, verifies the HMAC against `org-a`'s secret (known to the attacker) and succeeds. `StatusHandler#process` then looks up `Commit.where(sha: "deadbeef")` — matching the victim's commit in `org-b` — and calls `create_status_from_github!`, injecting a forged passing CI status that can satisfy `ci.require` and enable deployment of `org-b`'s stack, despite the attacker never being authorized on `org-b`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
