### Title
Cross-tenant webhook forgery via `repository_owner` organization fallback lets an attacker mutate/archive any repository's review stack on an `ignore_ci: true` stack - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`, `app/models/shipit/webhooks/handlers/pull_request/labeled_handler.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects which `GitHubApp` (and thus which webhook secret) authenticates a request using `repository_owner`, which falls back from `repository.owner.login` to `organization.login` when the former is absent. `LabeledHandler` and its base `Handler` independently resolve the target repository from `params.dig('repository', 'full_name')`. Because these two fields are set independently by the attacker in the same JSON body, an attacker who legitimately controls (and can produce a valid signature for, or who targets an org configured with no `webhook_secret`) one organization can pick that organization for signature verification while naming an unrelated victim repository in `repository.full_name`, causing `LabeledHandler` to archive/unarchive the victim's review stack.

### Finding Description
The broken binding, stated as an equality that must hold but does not:
`repository_owner used to select the verifying GitHubApp == organization/owner that actually owns repository.full_name used by the handler`.

Path:
1. `Shipit::WebhooksController#repository_owner` (`app/controllers/shipit/webhooks_controller.rb:59-62`) computes `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`.
2. `verify_signature` (`webhooks_controller.rb:24-30`) calls `Shipit.github(organization: repository_owner)` and then `github_app.verify_webhook_signature(header, raw_post)`.
3. `GitHubApp#verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`) returns `true` unconditionally `unless webhook_secret` is configured for that organization — i.e., if the attacker names an organization that has no configured secret (or one the attacker legitimately administers with a known secret), the check is trivially satisfied.
4. Once past `verify_signature`, `create` re-parses the raw body and dispatches to `LabeledHandler`, whose `ExplicitParameters` schema only requires `repository.full_name` (`labeled_handler.rb:33-35`) — it does **not** require `repository.owner.login`, and never cross-checks it against `repository_owner`.
5. `LabeledHandler#repository` resolves `Shipit::Repository.from_github_repo_name(params.repository.full_name)` (`labeled_handler.rb:65-67`), independent of whatever organization authenticated the webhook.
6. `handle` (`labeled_handler.rb:49-57`) calls `stack.archive!` or `stack.unarchive!` via `ReviewStackAdapter`, mutating the victim repository's review stack based solely on the attacker-chosen `repository.full_name`, `pull_request.labels`, and `pull_request.state`.

Attacker request: JSON body with `action: "labeled"`, `pull_request.state: "open"`, `pull_request.labels` chosen to trigger `archive?`/`unarchive?`, `repository: { full_name: "victim-org/victim-repo" }` (no `owner.login`), `organization: { login: "attacker-org" }`, and `X-Hub-Signature` computed with `attacker-org`'s own webhook secret (or omitted entirely if `attacker-org` has none configured). `X-Github-Event: pull_request` header selects the handler.

No existing guard closes this gap: `drop_unhandled_event` only checks the event type, `ExplicitParameters` never requires `repository.owner.login` nor compares it to `organization.login`, and there is no post-verification check that the authenticated organization matches the organization owning `repository.full_name`.

### Impact Explanation
An attacker who controls (or targets a lenient/unsecured tenant) organization onboarded to a shared Shipit instance can, without any credential belonging to the victim organization, forge a `pull_request`/`labeled` webhook that archives or unarchives a victim's `ReviewStack`. On a victim stack configured with `ignore_ci: true`, `Commit#deployable?` (`app/models/shipit/commit.rb:227-229`) short-circuits CI gating (`stack.ignore_ci? || (success? && !blocked?)`), so unarchiving/creating a review stack via this forged webhook lets an attacker-influenced commit become immediately deployable, i.e., a payload authenticated for one repository/organization mutates another organization's stack — matching the Critical category "a payload for one repository mutating another's stack" / unauthorized deploy path.

### Likelihood Explanation
Requires a multi-tenant Shipit deployment (multiple `github_apps`/organizations configured) where the attacker legitimately controls at least one onboarded organization (or one configured without a `webhook_secret`), and the victim stack has `review_stacks_enabled` and `ignore_ci: true`. Attacker cost is a single crafted HTTP POST to `/webhooks`; no GitHub secrets, session, or API token are needed. The attack is fully repeatable against any repository/stack whose `full_name` the attacker can guess or know, as long as any laxly-configured organization exists in the same Shipit instance.

### Recommendation
After parsing the webhook body, verify that the organization/owner used to select the signing `GitHubApp` (`repository_owner`) matches the owner of `repository.full_name` that the handler will act on, and reject the request if they diverge. Additionally, require `repository.owner.login` in `LabeledHandler`'s (and other handlers') `ExplicitParameters` schema rather than tolerating its absence, and disallow the `organization.login` fallback for repository-scoped events. Also treat a missing `webhook_secret` for a configured organization as a strict deny rather than an implicit-pass.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
