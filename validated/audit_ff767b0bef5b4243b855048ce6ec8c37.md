### Title
Webhook signature is verified against an organization taken from the request body, not against the repository the event actually mutates - allowing forged GitHub events for any tracked repository - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate the `X-Hub-Signature` against by reading `repository.owner.login` (or `organization.login`) out of the **same untrusted JSON body** being verified, then routes the event to a `Stack`/`Commit`/`Repository` using a *different* field of that body (`repository.full_name`, `sha`, etc.) which is never cross-checked against the verified organization. An attacker who controls a webhook secret for one organization tracked by this Shipit instance can therefore forge signed events that are applied to any other tracked repository/organization.

### Finding Description
The controller resolves which secret to use for HMAC verification from attacker-supplied data: [1](#0-0) [2](#0-1) 

`repository_owner` is `params.dig('repository', 'owner', 'login')` (fallback `organization.login`) — both fields live inside the same raw POST body whose integrity the signature is supposed to guarantee. `Shipit.github(organization: repository_owner)` looks up the `GitHubApp` instance (and its `webhook_secret`) for that organization name, and `verify_webhook_signature` HMACs the *entire* raw body against that org's secret: [3](#0-2) 

Crucially, the handlers that actually act on the event use a **different** field of the same payload to decide which repository/stack/commit to mutate, and never verify it matches the organization used for signature selection: [4](#0-3) 

`repository_name` is `payload.dig('repository', 'full_name')` — an independent key from `repository.owner.login`. So a crafted JSON body can present one org (`repository.owner.login`, `organization.login`) for signature-secret selection and a *different* org/repo (`repository.full_name`) for actual routing (push sync, status creation, PR merge, membership sync, etc.): [5](#0-4) [6](#0-5) 

This is precisely the binding class called out in scope: "an organization that authenticated versus the repository that is written." The `webhooks_controller` verifies "organization named in payload field A signed this body," but the effect is "mutate the repository named in payload field B," with no equality enforced between A and B.

Shipit explicitly supports multiple independently-configured GitHub Apps/organizations, each with its own `webhook_secret`, all served by the same public, unauthenticated `/github/webhooks` endpoint: [7](#0-6) 

The webhook endpoint requires no session, API token, or other credential — only a valid HMAC for *some* configured organization: [8](#0-7) 

### Impact Explanation
Any party who legitimately controls (or can install a GitHub App for) one organization tracked by a multi-org Shipit instance — and therefore knows that org's `webhook_secret` — can compute a valid signature for a hand-crafted payload whose `repository.owner.login`/`organization.login` names *their* org, but whose `repository.full_name`, `sha`, PR `number`, etc. name a victim repository/stack tracked under a *different, unrelated* organization on the same instance. This breaks the deployment-trust boundary between organizations that the per-org `webhook_secret` design is meant to enforce:
- `StatusHandler` lets the attacker forge a `success` commit status on an arbitrary commit SHA in the victim repo, which can satisfy `ci.require`/`merge.require` checks and enable an unauthorized deploy or merge queue merge.
- `PushHandler` lets the attacker trigger `stack.sync_github` for a victim stack, forcing a GitHub sync to an attacker-chosen `expected_head_sha`.
- `MembershipHandler`/`pull_request` handlers similarly act on attacker-controlled `full_name`/PR data outside the org actually authenticated.

This satisfies the Critical/High bar: it is a cross-repository/cross-organization write and can lead to an unauthorized deploy/merge, achieved purely by crafting an HTTP request to a public endpoint with a secret the attacker legitimately possesses for their own tenant.

### Likelihood Explanation
Requires the instance to be configured with more than one GitHub organization (documented and supported feature, see `secrets_double_github_app.yml`), and requires the attacker to know/possess a valid `webhook_secret` for at least one of those organizations (e.g., because they are the admin who installed the GitHub App for their own org on this Shipit instance). No other privilege (no Shipit session, no `ApiClient` token, no repository write access to the victim repo) is needed. This is a realistic setup for any Shipit deployment shared across independent teams/orgs.

### Recommendation
Cross-check that the organization used to select the verifying `webhook_secret` (`repository.owner.login`/`organization.login`) equals the organization portion of the field the handler will actually act upon (`repository.full_name`'s owner segment) before dispatching to any handler, rejecting the request (422) on mismatch. Alternatively, verify the signature using a global default and derive stack/repository lookups strictly from the same, already-authenticated organization context rather than trusting an independent body field.

### Proof of Concept
1. Configure Shipit with two orgs, `OrgOne` and `OrgTwo`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`), and track a stack for `OrgTwo/victim-repo`.
2. As an attacker who administers `OrgOne` (and thus knows `OrgOne`'s `webhook_secret`), build a JSON body for a `status` event:
   ```json
   {
     "repository": { "owner": { "login": "OrgOne" }, "full_name": "OrgTwo/victim-repo" },
     "sha": "<victim commit sha>",
     "state": "success"
   }
   ```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgOne_webhook_secret, body)>` and POST it to `WebhooksController#create` with `X-Github-Event: status`.
4. `verify_signature` looks up `Shipit.github(organization: "OrgOne")` (from `repository.owner.login`) and verification succeeds because the attacker signed with the correct `OrgOne` secret — see `app/controllers/shipit/webhooks_controller.rb:24-30`.
5. `StatusHandler#process` then looks up commits solely by `sha` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) and creates a `success` status for the victim commit belonging to `OrgTwo/victim-repo`, even though the signature only proves knowledge of `OrgOne`'s secret, not any control over `OrgTwo`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

    someothergithuborg:
