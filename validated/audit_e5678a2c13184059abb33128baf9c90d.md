## Title
Cross-organization webhook forgery via unscoped signature verification lets any onboarded org's webhook secret set commit statuses (and trigger syncs) for repositories belonging to any other organization on the same Shipit instance - (File: `app/controllers/shipit/webhooks_controller.rb`)

## Summary
Shipit supports multiple GitHub Apps/organizations on a single instance, each with its own `webhook_secret` [1](#0-0) . `WebhooksController#verify_signature` picks which organization's secret to verify against by reading `repository.owner.login` (or `organization.login`) out of the **unverified** JSON body, then verifies the HMAC using that org's secret [2](#0-1) . Once the signature check passes, event handlers use other, independently-controlled fields of the same payload to decide what to write - e.g. `StatusHandler` uses only `params.sha`, globally, with no repository/org scoping at all [3](#0-2)  and `Handler#repository_name`/`PushHandler` key off `repository.full_name`, a field distinct from the `owner.login` used for authentication [4](#0-3) . This breaks the binding `organization authenticated == repository/commit written`.

## Finding Description
The verified equality should be: *the organization whose secret validated the signature == the organization/repository the event handler mutates*. In this codebase that equality does not hold:

1. `verify_signature` derives `repository_owner` from the raw JSON body itself (not from any authenticated source) and looks up `Shipit.github(organization: repository_owner)` to get that org's `webhook_secret` [5](#0-4) .
2. Because HMAC verification only proves "whoever crafted this exact byte stream knows Org X's secret," and an administrator of any org onboarded to the same Shipit instance legitimately knows their own org's `webhook_secret` (set at GitHub App install time, per `docs/setup.md`'s multi-org config) [1](#0-0) , that administrator can craft an arbitrary JSON body, set `repository.owner.login`/`organization.login` = their own org (so verification passes against their own secret), while filling all *other* fields of the payload - `sha`, `repository.full_name`, `after`, etc. - with values referring to a completely different, unrelated organization's repository/commits tracked by the same Shipit instance.
3. `StatusHandler` never checks any repository/org scoping - it simply does `Commit.where(sha: params.sha).each { |c| c.create_status_from_github!(params) }` across the entire instance [6](#0-5) . So a `sha` collision (or just knowing another org's public commit SHAs) lets the attacker set status/state/`target_url`/`description` for a commit that lives in a stack owned by a completely different organization.
4. `PushHandler`/`Handler#repository_name` resolve the target purely from `repository.full_name` in the same forged payload [4](#0-3) [7](#0-6) , again independent of the org whose secret was actually verified.

This satisfies the required binding-break pattern: "an organization that authenticated versus the repository that is written."

## Impact Explanation
The forged status write directly feeds `Commit#deployable?` and the continuous-delivery/merge scheduling path: `add_status` re-evaluates `status`, and if the new status is `success`, it calls `stack.schedule_merges` and can trigger `ContinuousDeliveryJob` via `schedule_continuous_delivery` [8](#0-7) [9](#0-8) [10](#0-9) . An attacker who only administers their own onboarded org (Org A) can forge a `status` webhook, signed with Org A's own webhook secret, claiming success for a commit belonging to Org B's stack, causing Shipit to treat that commit as CI-green and enqueue it for continuous deployment/merge - an unauthorized deploy of code the attacker does not control the CI result for. This matches the "unauthorized deploy" Critical criterion, and is a cross-organization/cross-repository write.

## Likelihood Explanation
This requires the attacker to control at least one legitimate org onboarded to the same shared Shipit instance (a supported, documented multi-org configuration in `docs/setup.md`), and to know or guess a commit SHA belonging to another tracked org's stack (commit SHAs are typically public GitHub data, and repository/branch names are discoverable through Shipit's own UI/API for that instance). No GITHUB_TOKEN, `api_clients_secret`, or session is needed - only the ability to send an HTTP POST to `/webhooks` with a crafted body and a correctly computed HMAC signature using a legitimately-known org secret. This is a realistic, unprivileged (with respect to the victim org) exploitation path in any Shipit deployment hosting more than one organization.

## Recommendation
Bind webhook signature verification to the fixed org config the handler is about to act on, not to attacker-controlled payload fields chosen after the fact, and re-validate that every entity the handler mutates (commit's stack, repository) belongs to the same org whose secret validated the request. For single-tenant deployments this is moot, but for the documented multi-org configuration, scope handlers (especially `StatusHandler`) to the verified organization, and reject events whose payload-derived repository/org does not match records already known to belong to that verified org.

## Proof of Concept
1. Operator onboards two organizations to one Shipit instance: `OrgA` (attacker-controlled, `webhook_secret = secretA`) and `OrgB` (victim, unrelated `webhook_secret = secretB`), per the documented multi-app config [1](#0-0) .
2. Attacker (admin of OrgA, knows `secretA`) learns/guesses a commit SHA `deadbeef` that belongs to a commit in an OrgB-tracked stack (e.g. from OrgB's public GitHub repo or Shipit's public stack pages).
3. Attacker builds JSON body:
```json
{"sha":"deadbeef","state":"success","context":"ci/tests","repository":{"owner":{"login":"OrgA"}}}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(secretA, body)` and POSTs to `/webhooks` with header `X-Github-Event: status`.
5. `verify_signature` resolves `repository_owner` = `"OrgA"`, fetches OrgA's app, verifies the HMAC successfully [5](#0-4) .
6. `StatusHandler#process` runs unconditionally against `Commit.where(sha: "deadbeef")` regardless of which org that commit belongs to [6](#0-5) , marking OrgB's commit as `success`, which can trigger `stack.schedule_merges`/continuous delivery for OrgB's stack [11](#0-10) .

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
  end
