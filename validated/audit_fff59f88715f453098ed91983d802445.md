### Title
Unfunded overpayment refund in `repay` (and `recapitalize`) drains pool custody - (File: contracts/pool/src/ops/repay.rs)

### Summary
The Allo report's bug class is "the contract computes an excess over what is owed and pays/refunds based on the declared amount, not on what was actually received." XOXNO Lending has the same shape, but with the sign flipped into a critical loss: the pool's `repay` op computes `overpayment = amount - debt` purely from the **declared** `action.amount`, credits only the net repay to `cash`, and then unconditionally transfers the full declared overpayment back out of the pool's real token balance — without ever verifying that `amount` was actually transferred in. `recapitalize` has the identical pattern (`refund = amount - applied_shortfall`). An unprivileged caller can therefore declare a huge repay against a market with zero or small debt and receive the entire declared "excess" as a refund paid from suppliers' custody.

### Finding Description
`ops::repay::accounting` resolves the repay via `cache.resolve_repay(amount, position)` which calls `resolve_repay` in `common/src/rates/scaling.rs:171-192`: if `amount >= current_debt_ceil`, it returns `overpayment = amount - current_debt_ceil`. The function then credits only `net_repay = amount - overpayment` to the cash book (`cache.credit_cash(net_repay)`, repay.rs:57) and `apply` executes `outcome.cache.transfer_out(payer, outcome.overpayment)` (repay.rs:32) — a real token transfer out of the pool's balance.

The doc comments state "The controller transfers the repay amount into the pool before this call" (repay.rs:3), but the refund path itself performs no balance-delta check: there is no equivalent of `refund_controller_balance_delta` (contracts/controller/src/payments.rs:41-52, which does measure an actual balance increase before refunding). The refund is derived from the declared `amount`, not measured receipts.

The codebase's own test proves it: `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` (contracts/pool/tests/flows.rs:3590-3611) calls `repay` on a market with zero debt, transfers nothing in, and asserts the entire declared amount (`custody_before`) is paid out of the pool's custody, leaving the cash book untouched — i.e., book and custody are driven permanently out of sync.

`ops::recapitalize::accounting` (contracts/pool/src/ops/recapitalize.rs:52-55) has the identical flaw: `refund = amount - applied` where `applied = min(amount, backing_shortfall)`, and `apply` transfers the refund out unconditionally. With no backing shortfall, `applied = 0` and the full declared `amount` is refunded from custody.

### Impact Explanation
Theft of user funds / protocol insolvency. Each call moves `overpayment`/`refund` tokens out of the physical pool balance while `cash` (the book suppliers are owed) is unchanged. Repeating it — or one call sized to the pool balance — transfers the entire real token balance to the attacker while suppliers' supply shares still claim the full `cash` amount. Withdrawals then fail or are paid from other suppliers' funds: direct, unprivileged draining of the pool's custody.

### Likelihood Explanation
A single unprivileged address submits `pool.repay(payer, actions)` with `actions = [PoolAction { position scaled_amount: anything, amount: pool_balance }]` on any market with no outstanding debt for that position (debt 0 → `current_debt_ceil == 0` → entire `amount` is overpayment). No collateral, no position, no prior deposit, and no inbound transfer is needed. Equivalently, `recapitalize(hub_asset, payer, amount)` on a market with zero backing shortfall refunds the full declared `amount`. The attack is a single transaction and is deterministic — demonstrated by the existing regression test.

### Recommendation
Measure the refund from actual receipts, not from the declared amount, mirroring `refund_controller_balance_delta`:
- Snapshot `token.balance(pool)` at entry to `repay`/`recapitalize` (or `apply`), and cap `overpayment`/`refund` at `min(declared_excess, balance_after_inbound - balance_before)`; alternatively assert the inbound delta covers `net_repay` and only refund `delta - net_repay`.
- Or enforce that `repay`/`recapitalize` can only be invoked by the controller, which has already pulled the funds (require controller auth on these entrypoints).
- Same fix applies to `ops::recapitalize::accounting`/`apply`.

### Proof of Concept
```rust
// contracts/pool/tests/flows.rs::test_unfunded_repay_overpayment_refund_also_pays_out_of_custody
// Market with zero debt; attacker transfers nothing in.
let custody_before = token.balance(&t.pool);   // e.g. 50_000_000_000
let credited = t.client()
    .repay(&payer, &t.ract(0, custody_before)) // declared amount = full pool balance
    .get_unchecked(0)
    .actual_amount;
assert_eq!(credited, 0);                        // no debt retired, cash untouched
// payer's token balance increases by custody_before: the "overpayment"
// refund was paid entirely out of supplier custody.
```
The same sequence via `client.recapitalize(&hub_asset, &payer, &custody_before)` on a market with no backing shortfall yields `applied == 0` and `refund == custody_before` paid out of custody (recapitalize.rs:52-55, 34).

Note: I could not fully confirm within the iteration budget whether `pool.repay`/`recapitalize` enforce caller authorization in `contracts/pool/src/lib.rs`; if they are controller-only, the finding reduces to the controller's repayment path never reconciling pulled amounts — but the existing test invokes `repay` directly with no funding and the refund pays out regardless, so the custody drain stands on the code path as written.
