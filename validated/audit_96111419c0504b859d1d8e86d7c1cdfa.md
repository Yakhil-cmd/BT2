### Title
Cross-organization commit-status / review-stack forgery via mismatched webhook signature scope vs. acted-upon repository - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App secret to verify the incoming `X-Hub-Signature` against using a value taken from the **same attacker-controlled JSON body** (`repository.owner.login`, or `organization.login`), while every event `Handler` (e.g. `PushHandler`, `StatusHandler`, `PullRequest::ClosedHandler`) resolves the `Stack`/`Repository` to act on from an **independent field of the same body**, `repository.full_name`. Nothing binds these two fields together, so the organization whose secret authenticated the request is not provably the organization whose repository is written to.

### Finding Description
`verify_signature` computes:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`repository_owner` is read directly from the untrusted JSON payload. Meanwhile every handler resolves the acted-upon repository from a *different*, independently-controlled field of the same payload:
```ruby
def repository_name
  payload.dig('repository', 'full_name')
end
``` [2](#0-1) 

Since `repository.owner.login` and `repository.full_name` are two separate keys in one JSON body, an attacker able to produce a validly-signed request for *any* org configured in Shipit can set `repository.owner.login` to that org (so the correct, known secret is used for `verify_webhook_signature`) while setting `repository.full_name` to `"OtherOrg/other-repo"` for a completely different, unrelated stack tracked by the same Shipit instance. `HMAC` signature verification only proves the raw body was signed by *some* configured GitHub App secret — it says nothing about which repository fields inside that body are trustworthy.

This is compounded by `GitHubApp#verify_webhook_signature`:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [3](#0-2) 
If any configured organization (including the default/only org in a single-GitHub-App deployment, which the setup docs show as optional, e.g. `webhook_secret: # nil` in `config/secrets.development.example.yml`) has no `webhook_secret` configured, `verify_webhook_signature` unconditionally returns `true` regardless of the actual signature header — meaning *any* unauthenticated party can produce a "verified" request for that organization's identity, then point `repository.full_name` at any other repository/stack the Shipit instance tracks, including ones belonging to organizations that *do* have a secret configured. [4](#0-3) 

The binding broken is exactly: *the organization that authenticated the webhook* ≠ *the repository that is actually written to* by the handler.

### Impact Explanation
Handlers acting on `repository.full_name`-resolved stacks perform state-changing operations without further verification of ownership:
- `StatusHandler` creates commit statuses on any `Commit` matching the forged `sha` [5](#0-4) 
- `PullRequest::ClosedHandler` archives a review stack it looked up via the forged `full_name` [6](#0-5) 
- `PullRequest::LabeledHandler`/`ReopenedHandler` can archive/unarchive review stacks the same way [7](#0-6) 
- `PushHandler` triggers a `sync_github` job against any tracked stack matching the forged repo/branch [8](#0-7) 

These allow an attacker to manipulate commit statuses (which gate CI-required deploys), archive/unarchive review stacks, and force resynchronization of arbitrary tracked stacks — all cross-organization/cross-tenant, without any repository write access or Shipit session. This does not reach the "Critical: unauthorized deploy" bar directly for every handler, but commit-status forgery on a stack that requires specific CI contexts before deploy (`ci.require` in `shipit.yml`) can be used to unblock/trigger deploy eligibility on a victim stack the attacker has no access to, which is a credible path toward an unauthorized deploy — matching the "unauthorized deploy" / "cross-repository writes" impact bar.

### Likelihood Explanation
Exploitability depends on the attacker being able to produce a request that passes `verify_signature` for *some* organization known to Shipit. This is straightforward whenever any configured GitHub App organization has no `webhook_secret` set (an explicitly supported, documented configuration state — `webhook_secret: # nil` — not a misconfiguration outside the engine's own code), because `verify_webhook_signature` then accepts unconditionally. In that state, no credentials, GitHub App installation, or repository access are required at all — the endpoint is public (`app/controllers/shipit/webhooks_controller.rb` mounts with no session/API-client auth), so the attacker is a fully unprivileged, unauthenticated actor.

### Recommendation
Do not select the verification secret from the same payload whose fields are later trusted for repository resolution. Bind the verified organization to the acted-upon repository by deriving both from a single, GitHub-signed source (or by validating that `repository.owner.login` matches the owner segment of `repository.full_name`, and matches the config keyed for that request) before dispatching to handlers. Additionally, require `webhook_secret` to be present for every configured organization (fail closed rather than defaulting to `true` when absent).

### Proof of Concept
Assume Shipit is configured with organization `attacker-org` (webhook secret known/absent) and separately tracks a stack for `victim-org/victim-repo`.

```
POST /webhooks HTTP/1.1
X-Github-Event: status
X-Hub-Signature: sha1=<valid signature for attacker-org's secret, or arbitrary if attacker-org has no secret configured>
Content-Type: application/json

{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check",
  "description": "forged",
  "created_at": "2026-09-01T00:00:00Z"
}
```
`verify_signature` resolves `github_app = Shipit.github(organization: "attacker-org")` and validates against attacker-org's secret (or unconditionally if unset) — passes. `StatusHandler` then looks up `Commit.where(sha: ...)`, which belongs to `victim-org/victim-repo`, and creates a forged CI status on it, independent of `attacker-org`'s identity or permissions on `victim-org`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
