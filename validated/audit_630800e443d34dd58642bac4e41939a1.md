### Title
Webhook signing-organization is not bound to the target repository, allowing cross-organization webhook spoofing - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and thus which `webhook_secret`) is used to validate the HMAC signature based on `repository_owner`, a field read directly out of the untrusted, unsigned-at-selection-time JSON body. Once the signature is validated against that organization's secret, the payload is dispatched to handlers that identify the target `Stack`/`Repository` using a *different* field, `repository.full_name` [1](#0-0) . In a multi-organization Shipit deployment (explicitly supported and documented) [2](#0-1) , this breaks the intended binding: "the organization whose secret authenticated the request" must equal "the repository the request is allowed to write to."

### Finding Description
`verify_signature` computes `repository_owner` from the payload itself, then loads the matching GitHub App config to verify the signature: [3](#0-2) 

The signature is a valid HMAC-SHA1 over the entire raw request body, but it is computed with the secret belonging to whichever organization the attacker names in `repository.owner.login` (or `organization.login`) — a value the attacker fully controls when crafting the JSON body. In a multi-tenant configuration each organization has its own `app_id`/`installation_id`/`webhook_secret` [4](#0-3) , and each organization's admin necessarily knows their own webhook secret (they configured it when creating their GitHub App). Nothing prevents an attacker who owns/administers `attacker-org` (and thus knows `attacker-org`'s `webhook_secret`) from POSTing to `/webhooks` a JSON body where:
- `repository.owner.login` = `attacker-org` (so `verify_signature` picks `attacker-org`'s secret and the HMAC validates), and
- `repository.full_name` = `victim-org/victim-repo` (used later by `Handler#repository_name` to resolve the actual target).

Every webhook handler resolves its target purely from `repository.full_name`: [5](#0-4) 

For example, `PushHandler` uses this to find `Stack`s and call `sync_github`, and `StatusHandler` uses the (separately supplied, also attacker-controlled) `sha` to set a commit's CI status regardless of which org's key signed the request: [6](#0-5) [7](#0-6) 

This is the exact class of bug described in the report: a signature (analogous to the yNEAR-funded call) is verified using one identity/authority (the "payer"/signing org), while the state actually mutated (the "recipient"/target repository) is taken from an unrelated, unverified field. Just as `nft_resolve_payout_ft` trusted `ft_transfer` to succeed for a caller-controlled `account`/`amount` without tying it back to the entity that funded the call, `verify_signature` trusts the payload's `repository.full_name` to route the webhook without tying it back to the organization that actually signed it.

### Impact Explanation
Any attacker who controls (or has ever controlled) a GitHub organization/App configured in a shared, multi-organization Shipit instance can forge signed-looking webhook events targeting any *other* tenant repository configured on that instance. Depending on handler, this permits:
- Injecting fake `status` events to mark arbitrary commits on a victim stack as CI-passing, which — combined with `continuous_deployment`/merge-queue features — can lead to an unauthorized deploy or merge of unreviewed code.
- Forcing `push`-triggered `sync_github` on a victim's stack.
- Forging `pull_request`/`membership`/`check_suite` events for repositories the attacker does not own.

This crosses the "organization that authenticated versus the repository that is written" trust boundary explicitly called out as in-scope, and the CI-status/merge-queue path can escalate to an unauthorized deploy or merge, matching the High/Critical impact bar.

### Likelihood Explanation
Requires a multi-organization Shipit deployment (a supported, documented configuration) where the attacker administers at least one of the configured GitHub organizations/Apps — a lower bar than compromising the target organization itself, and no `ApiClient` token, session, or GitHub write access to the victim repo is needed. This is a realistic scenario for any Shipit instance shared across multiple business units or customers.

### Recommendation
After selecting the GitHub App by `repository_owner` and verifying the signature, cross-check that `payload.dig('repository', 'full_name')` (and `organization.login`) actually belongs to the same organization used to select/verify the signature before dispatching to handlers; reject the webhook otherwise. Handlers should not trust `repository.full_name` independently of the organization that was cryptographically verified.

### Proof of Concept
1. Configure Shipit with two GitHub Apps/orgs, `attacker-org` (secret known to attacker) and `victim-org` (hosts the target stack), per the documented multi-org setup [2](#0-1) .
2. Attacker crafts a `status` webhook body:
   ```json
   {
     "sha": "<victim commit sha>",
     "state": "success",
     "context": "ci/tests",
     "repository": {"full_name": "victim-org/victim-repo", "owner": {"login": "attacker-org"}}
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org secret, body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `verify_signature` resolves `repository_owner` = `attacker-org`, fetches `attacker-org`'s app, verifies the signature successfully [8](#0-7) .
5. `StatusHandler#process` uses `sha` to update the status of a commit belonging to `victim-org/victim-repo`, regardless of the signing org [9](#0-8) , potentially unblocking a deploy/merge that depends on that CI context.

**File:** app/controllers/shipit/webhooks_controller.rb (L24-49)
```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
