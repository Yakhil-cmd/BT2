### Title
Non-stack-scoped `ApiClient` token issued by CCMenu URL grants cross-stack read access - ([File: app/controllers/shipit/ccmenu_url_controller.rb])

### Summary
`CCMenuUrlController#client` looks up (or creates) an `ApiClient` keyed only on `creator: current_user, name: 'CCMenu Client'`, with no `stack` attribute ever set. Because the token is `message_verifier.generate(id)` and `id` is the row's primary key, the same token is issued regardless of which stack's CCMenu URL is being requested, and that token authenticates for every stack, not just the one in the URL.

### Finding Description
Binding claimed broken: `token(stack_a) == token(stack_b)` for the same user — TRUE.

Trace:
- `app/controllers/shipit/ccmenu_url_controller.rb:15-18` — `client` does `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')`. The lookup/creation criteria (`creator`, `name`) never include `stack`, so for a given `current_user` this always resolves to the identical `ApiClient` row on every call, irrespective of `params[:stack_id]`. [1](#0-0) 
- `app/models/shipit/api_client.rb:34-36` — `authentication_token` is `self.class.message_verifier.generate(id)`, a pure function of the row's `id`. Same row → same token, every time, for every stack. [2](#0-1) 
- Consequently `ccmenu_url_path(stack_id: stack_a)` and `ccmenu_url_path(stack_id: stack_b)` for the same session user return byte-identical `token` values in the JSON body.

This is not just a theoretical duplication — it has a concrete cross-tenant read consequence. `Api::BaseController#stacks` normally restricts stack lookups to `current_api_client.stack_id` when set: [3](#0-2) 
but `Api::CCMenuController` overrides `stack` to bypass that scope entirely and resolve directly from `params[:stack_id]` against all stacks: [4](#0-3) 
Since the `ApiClient` created by `CCMenuUrlController` never has `stack_id` set, `current_api_client.stack_id?` is always false, so even the base-controller scope would not have restricted it — but the override in `CCMenuController#stack` makes this explicit and unconditional: any valid `read:stack`-permissioned token (this one included) can fetch `GET /stacks/:any_other_stack/ccmenu.xml?token=...` for arbitrary stacks, not just the one it was minted for.

No existing guard catches this: `require_permission :read, :stack` only checks the permission list on the client, not which stack it targets; there is no per-stack authorization check anywhere in `Api::CCMenuController`. [5](#0-4) 

### Impact Explanation
Anyone who obtains a single leaked CCMenu URL (these URLs are designed to be pasted into unauthenticated CI-status widgets/badges, so leakage via referrer headers, public dashboards, or shared documents is realistic) can substitute an arbitrary `stack_id` in the URL and read that other stack's deploy/build status via `Api::CCMenuController#show`, even though the token was only ever displayed for one specific stack. This is unauthorized cross-stack disclosure of deploy state, matching the High-severity category "unauthenticated read of stack state ... deploy output" for any stack reachable via `Stack.from_param!` — i.e., every stack in the installation, not just ones belonging to the token's creator.

### Likelihood Explanation
No special Shipit configuration is required. The only precondition is that a legitimate operator has ever generated one CCMenu URL (a standard, documented feature) and that URL/token leaks through any normal channel (browser history, referrer, shared CI dashboard, screenshot, log). No secrets, sessions, or privileged roles are needed by the attacker once the token string is known; the cost is a single GET request with a substituted `stack_id`, and it is fully repeatable against every stack on the instance.

### Recommendation
Bind the `ApiClient` to the specific stack when it's created (`stack: stack`, and include `stack_id` in the `find_or_create_by!` lookup), and have `Api::CCMenuController#stack` honor `current_api_client.stack_id` (reuse the base `stacks` scope) instead of resolving unscoped `Stack.from_param!` directly, so a CCMenu token only ever authorizes reads of the stack it was issued for.

### Proof of Concept
```ruby
test "ccmenu token is identical across stacks and authorizes arbitrary stacks" do
  user = shipit_users(:walrus)
  stack_a = shipit_stacks(:shipit)
  stack_b = shipit_stacks(:cocaine)

  session_login_as(user) # sign in as the same user for both requests

  get ccmenu_url_path(stack_id: stack_a.to_param)
  token_a = URI(JSON.parse(response.body)['ccmenu_url']).query.then { |q| Rack::Utils.parse_query(q)['token'] }

  get ccmenu_url_path(stack_id: stack_b.to_param)
  token_b = URI(JSON.parse(response.body)['ccmenu_url']).query.then { |q| Rack::Utils.parse_query(q)['token'] }

  assert_equal token_a, token_b # binding broken: identical credential for two stacks

  # cross-stack read: token minted while viewing stack_a's URL reads stack_b's CI status
  get api_stack_ccmenu_url(stack_id: stack_b.to_param, token: token_a)
  assert_response :success
end
```
