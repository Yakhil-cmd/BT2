### Title
Cross-repository status injection via unscoped SHA lookup enables unauthorized merge of a victim's queued pull request - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target `Commit` purely by `Commit.where(sha: params.sha)`, with no filter on the repository/stack that the webhook signature actually authenticated. Since Git SHAs are content-addressed and shared across forks (an ancestor commit reused as a PR head has the identical SHA in every fork containing it), an attacker who owns any repository serviced by Shipit's GitHub App can emit a legitimately-signed `status` webhook for a SHA that also happens to be the `head.sha` of an unrelated victim's pending `MergeRequest`, causing the victim's `Commit` statuses to be updated and the merge queue to proceed to `MergeRequest#merge!`.

### Finding Description
The binding that should hold is: `repository_owner_authenticated_by(webhook_signature) == repository_owner_of(stack_that_owns(matched_commit))`. Tracing the code shows this is never enforced.

- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) only proves that the payload's `repository.owner.login` matches a GitHub App/org that Shipit trusts — it authenticates *who sent this specific status event*, not which `Commit`/`Stack` may be mutated. [1](#0-0) 
- `StatusHandler#process` then looks up commits globally by SHA with no repository/stack scoping at all: [2](#0-1) 
- `Commit#create_status_from_github!` → `add_status` mutates the matched commit's `statuses` and, on a state transition to pending/success, calls `stack.schedule_merges`, regardless of whose webhook triggered it: [3](#0-2) [4](#0-3) 

Root cause: the `sha` column is not a tenant-scoped identifier — it's globally unique only per Git object, and identical content (e.g., an ancestor commit shared between a victim's base branch history and an attacker's fork) produces the identical SHA in both repositories. Because `Commit.where(sha:)` searches the entire `commits` table across all stacks/repositories, any signed webhook the attacker can legitimately produce (by owning a repository where Shipit's GitHub App is installed) can update a `Commit` belonging to a completely different stack, as long as that commit's SHA happens to coincide with one already recorded for the victim's stack (e.g., the `head` commit of a queued `MergeRequest`).

None of the existing guards catch this: `verify_signature` validates sender authenticity for the attacker's own repo (which legitimately succeeds), `ExplicitParameters` only validates the shape of `sha`/`state`/etc., and there is no model-level or handler-level check tying the resolved `Commit#stack_id` back to the repository identified in the webhook payload.

### Impact Explanation
An attacker with no relationship to the victim's stack can cause a specific queued pull request in the victim's repository to be merged (`MergeRequest#merge!` → `stack.github_api.merge_pull_request`), purely by emitting a webhook scoped to their own repository. This is a payload for one repository mutating another's commit/stack state, directly enabling an unauthorized merge — matching the Critical impact category. The blast radius is any Shipit-monitored stack whose queued `MergeRequest#head.sha` is (or can be arranged to be) an ancestor commit reachable from a repository the attacker controls.

### Likelihood Explanation
Exploitation requires: (1) Shipit's GitHub App/webhook trust to be installed on a repository the attacker controls (feasible for public GitHub Apps that can be installed on personal accounts), (2) a victim stack with a `MergeRequest` in `pending` merge_status whose `head` commit SHA is reachable/reproducible in the attacker's own repository history (a known and reproducible git property — forks sharing base history retain identical SHAs for shared ancestor commits, and a PR head can be pointed at any existing commit), and (3) the required status `context` for the victim's stack must go green from the forged event. None of these preconditions require any Shipit secret, session, or elevated GitHub permission — only ordinary unprivileged GitHub actions (fork, branch, open PR, POST status against own repo). This makes the attack fully repeatable against any stack whose merge-queue head SHA can be predicted or engineered by an attacker with git history knowledge of the shared upstream.

### Recommendation
Scope the commit lookup in `StatusHandler#process` (and the equivalent `CheckRunHandler`, if present) to the repository/stack actually authenticated by the webhook, e.g. resolve `Stack`/`Repository` from `params.dig('repository', 'full_name')` (already used for signature verification) and restrict `Commit.where(sha: params.sha, stack: matching_stacks)` instead of a bare global SHA match, so a status event can only affect commits belonging to the stack(s) tied to the repository that produced the signed payload.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual)
test "status event for attacker's own repo cannot mutate a commit belonging to a different stack" do
  victim_stack = shipit_stacks(:shipit)
  colliding_sha = "a" * 40
  victim_commit = victim_stack.commits.create!(sha: colliding_sha, message: "shared ancestor")
  merge_request = create_merge_request(stack: victim_stack, head_sha: colliding_sha, status: "pending")

  attacker_payload = {
    sha: colliding_sha,
    state: "success",
    context: merge_request_required_context,
    repository: { full_name: "attacker/own-repo", owner: { login: "attacker-org" } },
  }

  # signature computed with attacker-org's legitimately-owned webhook secret
  post "/webhooks", params: attacker_payload.to_json,
       headers: { "X-Github-Event" => "status", "X-Hub-Signature" => attacker_signature }

  victim_commit.reload
  assert victim_commit.success?, "victim commit was mutated by an unrelated repository's webhook"

  # assert merge queue was advanced for a stack the attacker never authenticated against
  assert_enqueued_with(job: Shipit::ProcessMergeRequestsJob, args: [{ stack_id: victim_stack.id }])
end
```
Assertion pair to validate the broken binding: `attacker_payload[:repository][:full_name] != victim_stack.repository.full_name` while `victim_commit.reload.success? == true` and `Shipit::ProcessMergeRequestsJob` is enqueued for `victim_stack.id` — proving a webhook authenticated for one repository mutated another repository's commit/stack state.

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))

      end
      new_status
    end
