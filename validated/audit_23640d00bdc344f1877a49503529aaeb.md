### Title
Cross-repository `Status` write via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves the target commit purely by `sha`, with no check that the commit belongs to the repository that authenticated the webhook. This lets a validly-signed `status` webhook from any repository write a `Status` row (and therefore mutate `state`/`redeploy_state`) on a commit that belongs to a different stack/repository, silently, even when the target commit is already `deployed?`.

### Finding Description
The claimed binding is:
`payload.dig('repository','full_name')` (the repo whose org secret produced a valid `X-Hub-Signature`) `== commit.stack.repository.full_name` (the repo whose historical CI record is being amended).

Tracing the code shows this binding is never enforced for the `status` event:

- `WebhooksController#verify_signature` only checks that the HMAC signature matches the secret configured for the *organization* named in the payload (`Shipit.github(organization: repository_owner)`), via `GitHubApp#verify_webhook_signature`. [1](#0-0)  This authenticates "some repo under org X sent this", not "this repo owns this commit".
- `StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [2](#0-1) 
This is a *global* lookup across all stacks/repositories in the Shipit install, unscoped by `payload['repository']`. Contrast this with `CheckSuiteHandler`, which correctly scopes through `stacks` (derived from `Repository.from_github_repo_name(repository_name)`) before touching commits: [3](#0-2)  and the base `Handler#stacks`/`#repository_name` helpers that exist precisely to perform that scoping but are not used by `StatusHandler`. [4](#0-3) 

- `Commit#create_status_from_github!` unconditionally persists the row via `add_status`/`Status.replicate_from_github!`, regardless of the commit's `deployed?` state; only the *webhook emission* (`deployable_status`) is suppressed for already-deployed commits, per the existing test suite, while the underlying `Status` row and `state` are still written. [5](#0-4) [6](#0-5) [7](#0-6) 

Root cause: `StatusHandler` trusts `params.sha` as sufficient to locate the target commit, without verifying `payload['repository']['full_name']` matches the stack/repository that owns that commit. Because Shipit deployments commonly configure a single GitHub App/webhook secret shared across every repository in an organization (the default, non-multi-org config path in `Shipit.github`), any repository under that org can produce a validly-signed `status` payload naming an arbitrary `sha` string belonging to a commit tracked under a *different* repository/stack in the same Shipit instance (e.g. forked/mirrored/subtree-split repositories that share git history and therefore identical commit SHAs). None of the existing guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema in `StatusHandler.params`) check this repository-to-commit binding; the schema only validates types/presence of `sha`, `state`, etc., not repo ownership. [8](#0-7) 

### Impact Explanation
An attacker who legitimately owns/controls a repository under the same org (or under a fork sharing commit history with the victim's repo) can write a `Status` record — and thereby flip `state`/`redeploy_state`/`pending?`/`success?`/`failure?`/`error?` — for a commit belonging to a `victim` stack they do not own, including commits already deployed, without triggering the `deployable_status` hook (silent write). This falsifies the historical CI/audit trail Shipit's UI and API expose for that commit, satisfying the "payload for one repository mutating another's stack, commit" category. The blast radius spans every stack/repository sharing a Shipit installation and (in single-secret configs) every repository under the authenticated org; repeatable per request, at will, with no elevated privileges.

### Likelihood Explanation
Preconditions: the attacker must be able to produce a validly-signed `status` webhook naming a `sha` belonging to a commit tracked by a different stack. This is realistic wherever (a) Shipit is configured with a single GitHub App/secret shared org-wide (the documented default), or (b) two Shipit-tracked repositories share commit history (forks, mirrors, monorepo splits) — both common, low-cost setups. No secrets, sessions, or maintainer privileges are required, consistent with the "attacker action" and "preconditions" stated in the question.

### Recommendation
In `StatusHandler#process`, scope the commit lookup to the repository that authenticated the webhook, mirroring `CheckSuiteHandler`'s pattern: resolve `stacks` via `Repository.from_github_repo_name(repository_name)` and restrict `Commit.where(sha: params.sha)` to commits belonging to those stacks before calling `create_status_from_github!`.

### Proof of Concept
```ruby
test "status webhook cannot write a Status for a commit from another repository/stack" do
  victim_commit = shipit_commits(:second) # belongs to stack `shipit`/`cyclimse` etc.
  assert_predicate victim_commit, :deployed?
  before_state = victim_commit.state

  attacker_payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'context' => 'ci/travis',
    'created_at' => 1.day.ago.to_formatted_s(:db),
    'repository' => { 'full_name' => 'attacker-org/attacker-repo', 'owner' => { 'login' => 'attacker-org' } }
  }.to_json

  # signature legitimately produced by attacker-org's own (org-shared) webhook secret
  GithubHook.any_instance.stubs(:verify_signature).returns(true)

  expect_no_hook(:deployable_status) do
    post :create, body: attacker_payload, as: :json
  end

  victim_commit.reload
  assert_equal before_state, victim_commit.state # should NOT have changed via a foreign repo's webhook
end
```
Given the current `StatusHandler#process` implementation (`Commit.where(sha: params.sha)`), this assertion fails: `victim_commit.state` changes to `success` despite the webhook being authenticated only for `attacker-org`, demonstrating the cross-tenant write.
