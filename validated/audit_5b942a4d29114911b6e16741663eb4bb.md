### Title
Cross-organization webhook forgery triggers sync/deploy on arbitrary victim stacks - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret used to authenticate an inbound webhook from the `repository.owner.login` (or `organization.login`) field of the JSON payload, while the handlers that actually mutate state (e.g. `PushHandler`) look up the target `Stack`/`Repository` using the separate `repository.full_name` field of the very same payload. Both fields sit inside the same HMAC-signed body, so an attacker who legitimately controls a GitHub App/organization registered in Shipit (and thus knows its `webhook_secret`) can forge a raw payload where `repository.owner.login` names their own organization (so the signature check passes against their own secret) while `repository.full_name` names a victim repository/stack that they do not control. This breaks the binding "organization that authenticated == repository that is written."

### Finding Description
`verify_signature` derives the signing organization purely from payload content: [1](#0-0) [2](#0-1) 

It fetches `Shipit.github(organization: repository_owner)` and checks the `X-Hub-Signature` against *that organization's* `webhook_secret`. If the signature verifies, the whole raw body — including the independent `repository.full_name` field — is treated as trusted and handed to event handlers.

Every handler resolves its target `Stack` from `repository.full_name`, not from the `repository.owner.login`/`organization.login` field that was used to select the secret: [3](#0-2) 

`PushHandler` uses this repository lookup to enqueue a sync (and, for stacks with continuous deployment enabled, downstream deploy activity) using an attacker-supplied `after` SHA: [4](#0-3) 

`CheckSuiteHandler` similarly acts on whatever `Stack`/`Commit` matches `repository.full_name`: [5](#0-4) 

Because Shipit supports multiple GitHub organizations, each with its own `webhook_secret` configured under `Shipit.github(organization:)`, an operator/administrator of *any one* of these configured organizations (a legitimate but unprivileged-w.r.t.-other-orgs actor) can compute a valid `X-Hub-Signature` for a payload whose `repository.owner.login` names their own org (satisfying `verify_signature`), yet whose `repository.full_name` names a `Stack` belonging to a *different* configured organization. The signature only proves "this body was signed with organization A's secret" — it does not prove "this body concerns a repository owned by organization A," yet the handler trusts the embedded `full_name` to select the repository being acted upon.

This is structurally identical to the referenced bug class: a value (`triggerFee`) is acted upon without being tied to the payer whose signed intent was actually verified; here, a value (`repository.full_name`) is acted upon without being tied to the organization whose signature was actually verified.

### Impact Explanation
An attacker with legitimate control over one configured GitHub organization's app secret can force Shipit to enqueue sync jobs (`Stack#sync_github`) and check-run refreshes against a `Stack` that belongs to a different, victim organization, without ever needing that victim's `webhook_secret`, GitHub repository access, or Shipit session/API-client credentials. On stacks configured for continuous deployment, a forged, attacker-chosen `after` SHA fed into `sync_github` can cause an unsolicited deploy pipeline to run for a repository the attacker does not control — an unauthorized deploy trigger across an organization boundary the engine is supposed to keep separate. This matches the High-severity impact category "escalation... unauthorized deploy" listed in scope.

### Likelihood Explanation
Requires the attacker to control at least one of the several GitHub organizations/apps configured in Shipit's multi-org `github:` secrets (a normal, expected multi-tenant configuration per `config/secrets.development.example.yml` and `config/secrets.development.shopify.yml`), and knowledge of `full_name`/branch of a victim stack (both are public, non-secret GitHub metadata). No access to the victim's webhook secret, GitHub token, or Shipit session is needed, so this is reachable by an unprivileged-relative-to-victim attacker in any multi-organization Shipit deployment.

### Recommendation
Bind the two fields together before trusting either: after `verify_signature` succeeds, re-derive/require that `repository.owner.login` (the field used to select the verifying secret) equals the owner portion of `repository.full_name` (the field handlers use to resolve the `Stack`), and reject the webhook (422) on mismatch. Alternatively, resolve the target `Repository`/`Stack` using the *same* authenticated organization value used for signature verification rather than re-parsing `full_name` independently in `Handler#repository_name`.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` (secret `S_A`, attacker-controlled) and `victim-org` (secret unknown to attacker), each backed by a `Stack` for `victim-org/prod` with continuous deployment enabled.
2. Attacker crafts payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/prod"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(S_A, body)` (they know `S_A`) and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `attacker-org`'s app, verifies the signature successfully against `S_A`. [6](#0-5) 
5. `PushHandler#process` resolves stacks via `repository.full_name` = `"victim-org/prod"` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on the victim's stack, entirely outside the authenticated organization's scope. [4](#0-3)

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
