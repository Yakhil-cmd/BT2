### Title
Webhook signature verification selects the HMAC secret using an unsigned field, letting a payload's `repository.full_name` be acted on without ever being covered by a valid signature - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which GitHub App configuration (and therefore which `webhook_secret`) to use for HMAC validation based on `repository_owner`, a value read directly out of the *unverified* request body. The event handlers that actually act on the payload (e.g. `PushHandler`) instead resolve the target `Stack`/`Repository` from a *different* unverified field, `repository.full_name`. In a multi-GitHub-App deployment where at least one configured organization has no `webhook_secret` set (documented as optional), an attacker can pick that organization's login for `repository.owner.login`/`organization.login` while pointing `repository.full_name` at a completely different, "protected" repository. The signature check trivially passes because `verify_webhook_signature` returns `true` when the selected app has no `webhook_secret`, yet the event is processed against the unrelated target repository named in `full_name`.

### Finding Description
`verify_signature` derives the app used for verification purely from attacker-controlled JSON, before any signature has been validated: [1](#0-0) [2](#0-1) 

`verify_webhook_signature` short-circuits to `true` whenever the selected app's `webhook_secret` is blank: [3](#0-2) 

Multiple GitHub Apps (one per organization) are an explicitly documented, supported configuration, and `webhook_secret` is documented as optional per organization: [4](#0-3) [5](#0-4) 

After signature "verification" passes, the controller dispatches to event handlers using the raw, unverified JSON: [6](#0-5) 

Handlers resolve the target `Stack` from `repository.full_name` — a field never checked against `repository_owner`: [7](#0-6) [8](#0-7) 

This breaks the intended binding `organization that authenticated == repository that is written`: the "authenticated organization" is whatever `repository.owner.login`/`organization.login` names (used only to pick a possibly-secretless app config), while the "repository written" is whatever `repository.full_name` names (used by the handler to find the real `Stack`). Because both values live in the same unsigned JSON body and are never cross-checked, an attacker who has zero credentials can forge a "verified" webhook for any stack as long as any configured organization in `Shipit.github` lacks a `webhook_secret`.

### Impact Explanation
An unauthenticated attacker can forge webhook events (`push`, `status`, `check_suite`, `membership`, etc.) that Shipit treats as GitHub-authenticated for an arbitrary target stack/repository, provided the deployment uses multiple GitHub App configs and at least one lacks a `webhook_secret`. Concrete consequences include:
- Forged `push` events triggering `GithubSyncJob` for an unrelated stack, causing unexpected `Commit` ingestion.
- Forged `status`/`check_suite` events writing fake commit statuses/check runs, which factor into deploy/merge safety gating (`ignore_ci`, status checks), potentially enabling an unauthorized deploy or merge.
- Forged `membership` events creating/deleting `Team`/`Membership` rows, potentially escalating into `Shipit.github_teams` authorization used by `Authentication#force_github_authentication`.

This matches the High/Critical impact categories: escalation into `Shipit.github_teams` authorization, or an unauthorized deploy/merge triggered via forged status checks.

### Likelihood Explanation
Exploitability depends on a specific, but documented and supported, configuration: multiple GitHub Apps configured (one per org) with at least one organization's `webhook_secret` left blank (explicitly shown as optional in setup docs and the example secrets templates, e.g. `config/secrets.development.shopify.yml` and `test/dummy/config/secrets_double_github_app.yml`, both showing `webhook_secret: # nil`). Given the docs present this as a normal setup path rather than a discouraged one, likelihood is moderate — operators following the documented multi-org guide without setting a secret on every org are exposed. No credentials, tokens, or privileged access of any kind are required by the attacker; only network reachability to `/webhooks`.

### Recommendation
Do not let any unverified payload field select the verification key. Bind webhook signature verification to a fixed, statically-configured secret per deployment (or per repository, resolved via an authoritative source such as the installation ID/registered repository, not the payload), and reject the request if the field used to pick that secret does not match the field(s) the handlers use to resolve the target repository/stack (`repository.full_name`). At minimum, require `webhook_secret` to be mandatory for every configured organization and cross-validate `repository.owner.login` against `repository.full_name`'s owner before dispatching to handlers.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `OrgOne` (has `webhook_secret` set, owns the sensitive `OrgOne/target-repo` stack) and `OrgTwo` (no `webhook_secret` configured), as shown in `test/dummy/config/secrets_double_github_app.yml`.
2. Send `POST /webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef",
  "repository": {
    "full_name": "OrgOne/target-repo",
    "owner": { "login": "OrgTwo" }
  }
}
```
No `X-Hub-Signature` header (or any arbitrary value) is required.
3. `verify_signature` computes `repository_owner` = `"OrgTwo"`, calls `Shipit.github(organization: "OrgTwo")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally per `lib/shipit/github_app.rb:76-77`.
4. `create` dispatches the payload to `PushHandler`, which resolves the stack via `repository.full_name` = `"OrgOne/target-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) and enqueues `GithubSyncJob` for `OrgOne`'s protected stack — despite the request never being signed by `OrgOne`'s (or anyone's) real secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.
