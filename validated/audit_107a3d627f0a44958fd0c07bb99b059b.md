### Title
Cross-repository commit status forgery via unscoped SHA lookup in StatusHandler#process - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)` across the entire database, without ever restricting to the repository named in the payload or verified by the signature. An attacker who owns any registered app/repo can send a validly-signed `status` webhook naming their own repository but referencing a SHA that also exists as a `Commit` row in a victim stack (e.g., the well-known empty-tree SHA, or any SHA shared by chance/force/cherry-pick), causing the victim's `Commit#status` to be mutated.

### Finding Description
The broken binding: `params.repository['full_name']` (the repository whose `webhook_secret` verified the request, e.g. `attacker/fork`) must equal `commit.stack.repository.full_name` for the write to be authorized, but the code never checks this equality.

Path: `WebhooksController#verify_signature` verifies the HMAC signature using `Shipit.github(organization: repository_owner)`, where `repository_owner` is taken from the attacker-controlled `params.dig('repository','owner','login')` [4](#0-3) . This only proves the request was signed by *some* registered app that the attacker legitimately owns — it says nothing about which `Commit` rows may be touched. `WebhooksController#create` then dispatches to `StatusHandler.call(params)` [5](#0-4) .

`Handler` provides a `stacks` helper that correctly scopes to `Repository.from_github_repo_name(repository_name)` derived from the verified payload [2](#0-1) , but `StatusHandler#process` does not use it at all — it queries `Commit.where(sha: params.sha)` globally and calls `commit.create_status_from_github!(params)` for every match regardless of which stack/repository owns that commit [1](#0-0) . `create_status_from_github!` mutates the commit's status history and triggers `Hook.emit(:commit_status, ...)`/`schedule_merges` side effects [6](#0-5) [7](#0-6) .

Exploit: Attacker registers/owns `attacker/fork` in Shipit with a real `webhook_secret`. Attacker discovers or engineers a SHA collision with a victim commit (empty-tree SHA `4b825dc642cb6eb9a060e54bf8d69288fbee4904` is trivially shared across any repo with an empty commit, or attacker cherry-picks/copies a victim commit into their own history to get an identical SHA). Attacker POSTs to `/webhooks` with `X-Github-Event: status`, a signature computed with their own `webhook_secret`, and body `{action:'status', sha:'<shared-sha>', state:'success', repository:{full_name:'attacker/fork', owner:{login:'attacker'}}}`. Signature verification passes because it only checks against the attacker's own app. `StatusHandler#process` finds the victim's `Commit` row (same SHA, different stack) and flips its status to `success`, potentially unblocking `deployable?`/triggering continuous delivery on the victim stack.

Existing guards do not prevent this: `verify_signature` only authenticates *which app* signed the request, not *which commits* the payload may affect; `drop_unhandled_event` and `ExplicitParameters` schema only validate presence/shape of fields, not repository ownership of the target records.

### Impact Explanation
A single unprivileged webhook POST from an attacker's own registered app can flip CI status on an arbitrary victim commit merely by SHA collision, which is a payload for one repository mutating another's commit/stack — matching the Critical impact category explicitly listed in scope. Consequences include marking a victim's pending/failed commit as `success`, which can unblock deploy gating (`deployable?`) and trigger `ContinuousDeliveryJob`, i.e., influence an unauthorized deploy decision on a repository the attacker never authenticated for. The attack is repeatable against any victim commit whose SHA the attacker can predict or reproduce (trivially the empty-tree SHA, or any commit they can cherry-pick byte-for-byte into their own fork).

### Likelihood Explanation
Preconditions are low-cost and fully within attacker capability: register any repo/app with Shipit (a normal onboarding action), then send a signed `status` webhook for it. No victim secrets, no Shipit session, and no special SHA collision technique are required for the empty-tree case — it's a well-known constant SHA present in essentially any git history with an empty commit. For targeted victim commits, the attacker simply needs to reproduce the exact same tree/parent/author/committer/message/timestamp to get an identical SHA (feasible for public commits, e.g. copying a PR commit into their fork). This is directly reachable from an internet-facing, unauthenticated endpoint (`POST /webhooks`) using only the attacker's own credentials.

### Recommendation
In `StatusHandler#process`, scope the commit lookup to the repository named/verified in the payload, mirroring `Handler#stacks`, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or explicitly join `commits` to `stacks` filtered by `Repository.from_github_repo_name(repository_name)`, before calling `create_status_from_github!`. Apply the same audit to other handlers (e.g. check-run handler) that key off `sha` without going through `stacks`.

### Proof of Concept
```ruby
test "status webhook for repo A cannot mutate commit status belonging to stack B" do
  stack_a = shipit_stacks(:shipit) # backed by repo A, app secret S_A
  stack_b = create_stack(repository: create_repository(owner: 'victim', name: 'repo')) # repo B

  shared_sha = '4b825dc642cb6eb9a060e54bf8d69288fbee4904'
  commit_a = stack_a.commits.create!(sha: shared_sha, message: 'a')
  commit_b = stack_b.commits.create!(sha: shared_sha, message: 'b')

  assert_predicate commit_b.status, :pending?

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'repository' => { 'full_name' => stack_a.repository.full_name, 'owner' => { 'login' => stack_a.repository.owner } },
  }

  post shipit.webhooks_path, params: payload.to_json,
       headers: signed_headers_for(stack_a.repository, payload, event: 'status')

  commit_b.reload
  refute_equal 'success', commit_b.status.state,
    "Commit belonging to stack B (repository #{stack_b.repository.full_name}) must not be mutated " \
    "by a webhook signed for stack A (repository #{stack_a.repository.full_name})"
end
```
This asserts the equality `params.repository['full_name'] == commit_b.stack.repository.full_name` does not hold, yet the write still occurred — demonstrating the violation.
