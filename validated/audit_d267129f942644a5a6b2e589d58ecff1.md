### Title
Uncaught exception during AA trigger processing permanently bricks node and prevents unit confirmation - (File: aa_composer.js)

### Summary
The Salty `DAO._executeApproval` bug is a synchronous external call whose revert is not caught, which permanently blocks state finalization for one user. In ocore, `handlePrimaryAATrigger` processes a stable AA trigger inside an open DB transaction and only deletes the row from `aa_triggers` and commits after `handleTrigger`'s `onDone` callback fires successfully. If any code path invoked from `handleTrigger`/formula evaluation throws a JS exception instead of routing the error through the `bounce()`/`revert()` callback machinery, the exception is uncaught, and `network.js`'s global `uncaughtException` handler deliberately re-throws it to crash the whole node process "to avoid ending up in an inconsistent state."

### Finding Description
`handlePrimaryAATrigger` in `aa_composer.js` begins a DB transaction and only removes the trigger row and commits after the trigger has been fully (and successfully) handled: [1](#0-0) 

All expected AA errors (bad definition, insufficient bounce fees, formula failures, etc.) are designed to be routed through `bounce(error)` or `revert(error)`, which properly finish processing, allow committing the transaction, and delete the trigger row — this is the ocore analog of a `try/catch`: [2](#0-1) [3](#0-2) 

However, several code paths reachable from arbitrary, attacker/AA-author-controlled trigger data or AA definition content use `throw Error(...)` directly instead of funneling into `bounce`/`revert`. Examples include the message-template composer: [4](#0-3) 

and the formula evaluator's `ifelse` test handling: [5](#0-4) 

These `throw Error` calls are not caught anywhere in the synchronous call chain of `handleTrigger`. Because Node.js treats an uncaught exception as fatal, and `network.js` explicitly re-throws inside its global handler to force a crash: [6](#0-5) 

the node process dies mid-transaction. Since the DB transaction was never committed and `DELETE FROM aa_triggers ...` was never reached, the pending trigger row for that unit/address remains in the `aa_triggers` table. On node restart, `handleAATriggers()` will reselect and reprocess the exact same trigger: [7](#0-6) 

Because AA/trigger execution is meant to be fully deterministic (same unit content, same AA definition, same prior state), reprocessing hits the identical `throw Error`, and the node crashes again — indefinitely. This is structurally the same bug class as the Salty `DAO._executeApproval` finding: an unhandled failure from processing a single (attacker- or AA-author-influenced) unit/trigger becomes a *persistent*, unrecoverable failure instead of a contained, bounded one.

### Impact Explanation
Unlike the Solidity case where only one user's ballot gets stuck, in ocore this crashes the *entire node process* every time it tries to process that specific stable trigger. Because trigger processing happens deterministically from already-stable, already-final DAG data (the trigger's originating unit is already stable), every node that reaches that MCI and attempts to run AA triggers will hit the identical crash on catch-up/restart, i.e., a network-wide "unable to confirm new units" condition if enough/most full nodes execute AAs (which is required for AA-based DAG state), matching the accepted Medium/High impact category "a network unable to confirm new units."

### Likelihood Explanation
The trigger for this crash class is any unit sent to an AA address whose messages/definition, combined with the specific formula evaluation path, hits one of the un-bounced `throw Error(...)` statements (e.g., an `ifelse` test unexpectedly evaluating to a raw JS object, or a message template value falling outside the handled `replace()` cases). Such units can be posted by any unprivileged user targeting any AA, and an AA author (deliberately or via an edge case) can construct a definition that makes this reachable through ordinary/permitted formula constructs, since `formula/validation.js` validates formula syntax/complexity but does not guarantee that every runtime evaluation branch is funneled through `setFatalError` rather than `throw`. Given the breadth of the formula/evaluation.js switch statement, several of these `throw Error` branches appear only reachable through edge-case runtime states rather than through static validation, making exploitation plausible but requiring careful crafting; likelihood is assessed as Medium given the difficulty of confirming a concrete unauthenticated trigger without executing the code.

### Recommendation
Wrap the top-level entry point of `handleTrigger` invoked by `handlePrimaryAATrigger` (and any other primary AA-trigger invocation site) in a catch boundary that converts any uncaught synchronous exception into a `bounce()`-style failure (or, at minimum, into a safely committed no-op response) rather than letting it propagate to the process-level `uncaughtException` handler. Additionally, audit all `throw Error` sites inside `aa_composer.js`'s `replace()`/message-composition logic and inside `formula/evaluation.js`'s `evaluate()` switch that are reachable from trigger/AA-definition-controlled data, and convert them to `setFatalError`/`cb(err)` style error propagation (consistent with the rest of the formula evaluator) so that malformed or unexpected runtime states result in a normal bounce rather than a fatal, non-recoverable, deterministically-repeating process crash.

### Proof of Concept
A definitive PoC requires actually driving the formula evaluator/`replace()` composer into one of the identified `throw Error` branches with a concrete AA definition and trigger unit (e.g., constructing a message template whose replaced value is neither string, array, nonempty object, nor otherwise handled type at `aa_composer.js:871-872`, or constructing an `ifelse` test expression whose evaluated result is a raw JS object rather than `wrappedObject`/`Decimal`/`string`/`boolean` at `formula/evaluation.js:1471-1472`). Reaching these branches requires runtime experimentation against the oscript grammar/evaluator, which is not verifiable from static code reading alone. The report should be understood as identifying a class of unhandled-throw-inside-AA-trigger-processing bugs whose mechanism (deterministic reprocessing of an un-deleted `aa_triggers` row after a crash) is fully confirmed in code, while the exact triggering payload for a specific `throw Error` site remains unconfirmed and would need to be validated with a running test harness (e.g., `test/aa_composer.test.js`, `test/aa.test.js`).
