## Title
Cross-organization webhook authentication bypass in `WebhooksController#verify_signature` allows forging `membership` events that grant unauthorized `Shipit.github_teams` access — ([File: app/controllers/shipit/webhooks_controller.rb])

## Summary
`WebhooksController` selects which GitHub App/`webhook_secret` to verify a webhook's HMAC signature against using `repository_owner`, extracted from `params.dig('repository','owner','login')`, falling back to `params.dig('organization','login')`. But every event handler that actually mutates state (`MembershipHandler`, `PushHandler`, `PullRequest::*Handler`) reads its own, independently-controlled field from the *same attacker-supplied JSON body* (`params.organization.login`, `params.repository.full_name`) to decide what `Team`/`Stack`/`Repository` to act on. Because the entire raw body is attacker-authored, an attacker who legitimately controls one onboarded GitHub organization's `webhook_secret` (a supported, documented multi-tenant configuration — "Using Multiple GitHub Applications", `docs/setup.md`) can sign a payload whose "verification" fields point to their own org while its "target" fields point to a victim org/team, breaking the intended binding between *the organization whose secret authenticated the request* and *the organization/team/repository actually written to*.

## Finding Description
The signature-selection logic and the action-target logic use different, independently attacker-controllable JSON paths:

- Signature verification org selector: `params.dig('repository','owner','login') || params.dig('organization','login')` in `repository_owner` [1](#0-0) , used to select the app/secret with `Shipit.github(organization: repository_owner)` before calling `verify_webhook_signature(signature, request.raw_post)` [2](#0-1) .
- `verify_webhook_signature` only proves the caller knows the secret configured for that *selected* organization; it says nothing about the payload's semantic content, since the whole `raw_post` (including the org/team/repo fields) is written by the caller: `SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))` [3](#0-2) .
- `MembershipHandler#process` independently trusts `params.organization.login` (used to create/attribute a `Team`) and `params.member.login`, and directly mutates team membership: `team.add_member(member)` / `team.members.delete(member)` [4](#0-3) .
- `Shipit.github_teams` (which gates `User#authorized?` and hence access to the whole application) is derived from `Team` membership: `@authorized ||= Shipit.github_teams.empty? || teams.where(id: Shipit.github_teams.map(&:id)).exists?` [5](#0-4) , and `Shipit.github_teams` is `github.oauth_teams.map { |t| Team.find_or_create_by_handle(t) }` [6](#0-5) .
- The engine explicitly documents and supports multiple independently-configured GitHub Apps/webhook secrets, one per organization, in a single Shipit instance — i.e., different tenants each know only their own secret: `docs/setup.md` "Using Multiple Github Applications" [7](#0-6) .

**Binding broken (equality that should hold but doesn't):**
`organization_whose_secret_signed_request (repository_owner) == organization/team the handler actually writes to (params.organization.login used by MembershipHandler)`

These two values are read from the same untrusted JSON body via different keys/paths, so an attacker who owns and controls their own onboarded org ("attacker-org", with its own legitimately-known `webhook_secret`) can set `repository.owner.login = "attacker-org"` (satisfies signature check) while setting the `membership` event's `organization.login = "shopify"` (the victim org whose team gates access) — the handler never checks that the two match.

## Impact Explanation
This directly maps to the specified High-impact category "escalation into `Shipit.github_teams` authorization": an attacker owning a `webhook_secret` for any onboarded org in a multi-org Shipit deployment can forge a `membership` webhook naming the *victim* org's team (e.g. the org referenced by `Shipit.github_teams`) and add an arbitrary GitHub login (including one they control) as a member, via `team.add_member(member)`. Since `User#authorized?` grants full application access based on membership in any configured `Shipit.github_teams` team [5](#0-4) , this is a path to unauthorized access to the whole Shipit instance (deploys, rollbacks, stack management) for an identity that was never actually a member of the authorized GitHub team/org.

## Likelihood Explanation
Requires only: (1) a Shipit instance configured for multiple GitHub organizations (a documented, supported configuration), and (2) the attacker legitimately controlling/administering one onboarded org (hence knowing its own `webhook_secret`, which they themselves provide when creating their GitHub App). No GITHUB_TOKEN, `api_clients_secret`, or Shipit session/ApiClient token is required — only an HTTP POST to the public `/webhooks` endpoint with a correctly-HMAC'd body using the attacker's own known secret.

## Recommendation
In `MembershipHandler` (and any other handler using an org/repo field to select the write target), require that the field used to pick the write target equals the `repository_owner`/organization value that was used to select the verifying `webhook_secret`, and reject the event otherwise. More generally, `WebhooksController` should pass the *verified* organization down to handlers and have each handler assert equality against every organization/repository field it acts upon, rather than letting handlers independently re-derive trust from unauthenticated-relative-to-target payload fields.

## Proof of Concept
1. Configure Shipit with two orgs per `docs/setup.md` "Using Multiple GitHub Applications": `attacker-org` (attacker's own GitHub App, secret known to attacker) and `shopify` (victim org, whose team gates `Shipit.github_teams`).
2. Attacker crafts a `membership` event body:
```json
{
  "action": "added",
  "team": {"id": 48, "name": "Developers", "slug": "developers", "url": "https://example.com"},
  "organization": {"login": "shopify"},
  "member": {"login": "attacker-controlled-login"},
  "repository": {"owner": {"login": "attacker-org"}}
}
```
3. Attacker signs this body with `attacker-org`'s known `webhook_secret` and sends `POST /webhooks` with `X-Github-Event: membership` and `X-Hub-Signature: sha1=<hmac>`.
4. `verify_signature` computes `repository_owner` = `"attacker-org"` [1](#0-0) , loads `attacker-org`'s app, and the signature validates successfully since the attacker knows that secret.
5. `MembershipHandler#process` reads `params.organization.login = "shopify"` and `params.member.login`, and calls `team.add_member(member)` [4](#0-3) , granting the attacker-controlled login membership in the `shopify/developers` team — which, if listed in `Shipit.github_teams`, grants `authorized?` access to the whole Shipit instance.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
