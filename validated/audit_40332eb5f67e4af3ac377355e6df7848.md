Let me pull the actual router-strategy authorization code to ground a finding.### Title
Unallowlisted route venues let third-party code execute token transfers under the caller's authorization tree - (File: contracts/swap-aggregator/src/execute/mod.rs, contracts/controller/src/strategies/swap.rs)

### Summary
CVE-2016-2781 is a confinement-escape class: `chroot --userspec` let a sandboxed process push `TIOCSTI` input into the *parent* session's input buffer, so operations meant to be confined executed in the outer, more privileged context. The analog in XOXNO Lending is the router-strategy boundary: a swap is meant to be confined to "spend `amount_in`, return output", but the swap aggregator executes arbitrary payload-named venue contracts with no allowlist, so attacker-controlled code runs on the call stack *beneath* the caller's `require_auth` entry — like TIOCSTI bytes landing in the parent's input queue.

### Finding Description
The controller confines its own side correctly: `swap_tokens` in `contracts/controller/src/strategies/swap.rs:34` calls `authorize_transfer_as_current` granting exactly one `token_in.transfer(controller, router, amount_in)` invocation with no sub-invocations, and it rejects input-balance growth and overspend at lines 41-52 [1](#0-0) . That guard binds only the *controller's* authorization.

The user's side is not confined. To execute a router strategy (`swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`, or a direct `execute_strategy` on the aggregator), the account owner signs a `require_auth` tree containing the router invocation. The route payload — supplied by the caller — names the venue contracts the router will invoke, and the router keeps no allowlist of pool/venue addresses [2](#0-1) . A route can therefore name an attacker-deployed "venue" contract which, while on the stack under the router call, issues `token.transfer(victim, attacker, X)` on any token; an honest host simulation records that transfer as a child of the *caller's* authorization entry, and it executes if the caller signs the resulting tree. The injected transfer escapes the swap's economic boundary: it is not bounded by `amount_in`, by the router's payload minimum, or by the controller's measured-output and final-risk gates, because those gates only observe the routed `token_in`/`token_out` deltas [3](#0-2) .

### Impact Explanation
Theft of user funds. The malicious venue can drain every token the victim holds for which a child transfer appears in the signed auth tree — the loss is "the caller's wallet, not the routed amount," per the threat model itself [2](#0-1) . A user intending to swap a bounded `amount_in` can lose unrelated token balances, mirroring how a confined chroot process could inject commands into the unrestricted parent shell.

### Likelihood Explanation
Exploitation requires the victim to sign an authorization tree that contains the extra child entry — i.e., a front-end or wallet that submits routes without diffing the simulated auth tree. The threat model explicitly assigns that duty to the client ("a client must decode the route it signs"), so this is a documented boundary rather than a hidden flaw; likelihood is gated on user/client behavior, which is why Medium rather than High is appropriate. The unprivileged path itself (`execute_strategy` / controller swap verbs with a caller-supplied route) is fully on-chain and reachable.

### Recommendation
- Introduce a venue allowlist in the swap aggregator (set at deployment/governance): `execute_strategy` should reject any route leg whose `contract` address is not a registered venue, so payload-named third-party code can never sit under the caller's auth.
- Alternatively/additionally, have the router invoke venues through a fixed adapter interface and refuse arbitrary `(contract, fn, args)` triples.
- Keep documenting client-side auth-tree verification as defense-in-depth, not as the sole mitigation.

### Proof of Concept
1. Attacker deploys contract `EVIL` exposing `fn swap(...)` which internally calls `token::Client(usdc).transfer(victim, attacker, victim_full_balance)` — a `require_auth`-able transfer recorded as a sub-invocation of the caller's entry.
2. Attacker's front end offers victim a "swap XLM→USDC" on `swap_collateral`/`execute_strategy` with a route whose leg names `EVIL` as the venue.
3. Wallet simulates; the auth tree shows `caller → router.execute_strategy → … → usdc.transfer(victim, attacker, …)`. A non-decoding client signs it.
4. Router executes `EVIL.swap`; the injected transfer pulls the victim's USDC. Controller checks pass: `actual_spent <= amount_in`, output measured positive, final HF fine — none of them see the unrelated transfer, exactly as TIOCSTI bytes bypassed the chroot boundary into the parent session.

Note on scope: the router contract (`contracts/swap-aggregator`) is listed in the prompt's rejection list for *internals*, and the threat model documents the client-side check, so this may be classified as a known accepted risk rather than a new finding. It is the closest on-code analog to the CVE's "confined context escapes into privileged parent" class; all other candidate mappings (shared pool custody across hubs — ADR-0002, stranger restamp gating — `risk/params.rs`, flash callback re-entry — `with_flash_guard` + host `InvalidAction`) are either documented design or already defended.

Distinct-token swaps require positive measured controller output. The current
