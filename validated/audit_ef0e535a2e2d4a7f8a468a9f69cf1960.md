### Title
Withdraw is fully gated by admin-controlled `PoolStatusBitIndex::Withdraw` with no emergency-exit path, permanently freezing LP funds if the bit is disabled - (File: programs/cp-swap/src/instructions/withdraw.rs)

### Summary
The `withdraw` instruction is the only way for a liquidity provider to redeem LP tokens for underlying `token_0`/`token_1`. It unconditionally reverts with `ErrorCode::NotApproved` whenever the pool's `Withdraw` status bit is disabled, and the program provides no alternative or emergency withdrawal path that bypasses this check, mirroring the reported `BLVaultLido` issue where `withdraw` only works `onlyWhileActive`.

### Finding Description
`withdraw()` loads the `PoolState` and immediately gates on the status bitmap:
```rust
if !pool_state.get_status_by_bit(PoolStatusBitIndex::Withdraw) {
    return err!(ErrorCode::NotApproved);
}
``` [1](#0-0) 

This bit is controlled exclusively via `update_pool_status`, which sets the raw `u8` status field on `PoolState`:
```rust
pub fn update_pool_status(ctx: Context<UpdatePoolStatus>, status: u8) -> Result<()> {
    require_gte!(255, status);
    let mut pool_state = ctx.accounts.pool_state.load_mut()?;
    pool_state.set_status(status);
    ...
}
``` [2](#0-1) 

The status field packs three independent bits (Deposit/Withdraw/Swap) per `pool.rs`, and `get_status_by_bit` simply masks the byte to determine if a given operation is currently allowed:
```rust
pub enum PoolStatusBitIndex {
    Deposit,
    Withdraw,
    Swap,
}
...
pub fn get_status_by_bit(&self, bit: PoolStatusBitIndex) -> bool {
    let status = u8::from(1) << (bit as u8);
    self.status.bitand(status) == 0
}
``` [3](#0-2) [4](#0-3) 

Once the `Withdraw` bit is set (disabled), *every* LP in the pool — not just future depositors — is permanently blocked from `withdraw()`, since there is no separate "emergency withdraw" instruction that lets an LP burn their LP tokens and redeem principal while bypassing the status gate. Searching the instruction set confirms the `Withdraw` bit check exists only in `withdraw.rs`, with no companion bypass route. [5](#0-4) 

### Impact Explanation
If the `Withdraw` status bit is ever disabled (whether intentionally, by mistake, or as a stuck/incorrectly-set value), all liquidity providers' principal becomes permanently locked in the pool's vaults with no on-chain recourse, since `withdraw` is the sole redemption path and it hard-fails on the status check. This is a direct, permanent freezing-of-funds risk for every LP holding LP tokens against that pool.

### Likelihood Explanation
The status bit is a normal, expected operational lever exposed by the program itself (`update_pool_status`), not a hypothetical external condition — so this isn't a rare edge case but a directly reachable program state. Any time the `Withdraw` bit is left/set disabled (by design, misconfiguration, or a stuck emergency pause with no unwind mechanism), LPs are locked out indefinitely, since the vault/design provides no fallback.

### Recommendation
Introduce an emergency/forced-withdraw path (or separate the "new withdrawal disabled" semantics from "pro-rata redemption of existing LP tokens") so that LPs can always redeem their principal (potentially without protocol/creator fee accounting or reward distribution) even when normal `Withdraw` status is disabled, analogous to the recommended `emergencyWithdraw` in the referenced report.

### Proof of Concept
1. Admin (or misconfiguration) calls `update_pool_status` with a `status` byte that sets bit 1 (Withdraw disabled), e.g. `status = 2`. [2](#0-1) 
2. Any LP calls `withdraw` with a valid `lp_token_amount` they own.
3. The check `if !pool_state.get_status_by_bit(PoolStatusBitIndex::Withdraw) { return err!(ErrorCode::NotApproved); }` reverts the transaction unconditionally. [1](#0-0) 
4. There is no other instruction in the program that allows the LP to burn LP tokens and redeem `token_0`/`token_1`, so their funds remain locked in the pool vaults for as long as the bit stays set, with no on-chain way to force an exit.
