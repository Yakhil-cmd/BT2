### Title
Bridge Operator Can Front-Run User's Fallback KAIA Transfer to Silently Drain Bridged Value — (`File: contracts/service_chain/bridge/BridgeTransferKLAY.sol`, `contracts/service_chain/bridge/BridgeFee.sol`)

---

### Summary

The `BridgeTransferKLAY` fallback function reads `feeOfKLAY` at execution time and passes it as both the fee limit and the effective fee, with no user-controlled slippage guard. A bridge operator can call `setKLAYFee()` in the same block (or a block immediately before) a user's fallback transaction, silently redirecting a portion of the user's bridged KAIA to the fee receiver instead of the destination chain.

---

### Finding Description

`BridgeTransferKLAY.sol` exposes two paths for KAIA bridge requests:

**Path 1 — `requestKLAYTransfer` (protected):** [1](#0-0) 

The user explicitly sets `feeLimit = msg.value - _value`. If `feeOfKLAY` has been raised above `feeLimit`, `_payKLAYFeeAndRefundChange` reverts with `"insufficient feeLimit"`. The user is protected.

**Path 2 — Fallback (vulnerable):** [2](#0-1) 

The fallback passes `feeOfKLAY` as `_feeLimit`. Inside `_requestKLAYTransfer`, the bridged value is computed as:

```
value_transferred = msg.value - _feeLimit = msg.value - feeOfKLAY
``` [3](#0-2) 

The fee is then deducted from `_feeLimit` in `_payKLAYFeeAndRefundChange`: [4](#0-3) 

Because `_feeLimit == feeOfKLAY` at call time, `feeRefund = 0` — the entire `feeOfKLAY` is consumed as fee. If an operator raises `feeOfKLAY` between when the user observes the fee and when the transaction executes, the user's `msg.value` is split differently: more goes to the fee receiver, less is bridged.

The operator fee-change path: [5](#0-4) 

`setKLAYFee` requires only `onlyOperators` and uses `_voteConfiguration`. With the default threshold of `1`, a single operator can change the fee in one transaction with no time-lock or waiting period: [6](#0-5) [7](#0-6) 

---

### Impact Explanation

**Corrupted value:** `(new_feeOfKLAY − old_feeOfKLAY)` KAIA is silently redirected from the bridged amount to the fee receiver. The `RequestValueTransfer` event emits the reduced `valueOrTokenId`, so the counterpart bridge operator will only release the smaller amount on the destination chain. The user suffers a permanent, unrecoverable loss of bridged KAIA with no on-chain indication that the fee changed.

This matches the allowed impact gate: *"unauthorized fee charge … affecting KAIA, bridged assets."*

---

### Likelihood Explanation

- The default `operatorThresholds[Configuration] = 1`, so a single operator can execute `setKLAYFee` atomically.
- There is **no time-lock or waiting period** on bridge fee changes (unlike the Kaia header-governance system, which enforces a full epoch ≥ 604 800 blocks before any parameter takes effect).
- The fallback function is the documented "simple send" path for KAIA bridge transfers and is exercised in production tests.
- An operator who controls transaction ordering (e.g., the bridge node itself) can place `setKLAYFee` in the same block before the user's fallback call.

---

### Recommendation

1. **Add a `maxFee` parameter to the fallback or a dedicated `requestKLAYTransferWithMaxFee` function** so users can specify the maximum fee they accept; revert if `feeOfKLAY > maxFee`.
2. **Alternatively, deprecate the parameterless fallback** for bridge transfers and require users to call `requestKLAYTransfer`, which already provides slippage protection via the explicit `feeLimit`.
3. **Enforce a time-lock on `setKLAYFee` / `setERC20Fee`** analogous to the epoch-based delay used by Kaia header governance, so fee changes cannot be applied within the same block as pending user transfers.

---

### Proof of Concept

```
State before:
  feeOfKLAY = 0.1 KAIA
  feeReceiver = operator_wallet

User submits (pending):
  bridge.fallback{value: 1.1 KAIA}()
  // expects: 1.0 KAIA bridged, 0.1 KAIA fee

Operator front-runs (same block, earlier tx):
  bridge.setKLAYFee(0.6 KAIA, configurationNonce)
  // threshold=1, executes immediately

User's fallback executes:
  _feeLimit = feeOfKLAY = 0.6 KAIA
  require(1.1 > 0.6)  ✓ passes
  fee paid = 0.6 KAIA → feeReceiver
  value bridged = 1.1 - 0.6 = 0.5 KAIA  ← user expected 1.0 KAIA

Loss: 0.5 KAIA silently redirected to fee receiver
```

    function _payKLAYFeeAndRefundChange(uint256 _feeLimit) internal returns(uint256) {
        uint256 fee = feeOfKLAY;

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            (bool ok, ) = feeReceiver.call.value(fee)("");
            require(ok, "transfer fee failed");

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                (bool ok, ) = msg.sender.call.value(feeRefund)("");
                require(ok, "refund fee failed");
            }

            return fee;
        }

        if (_feeLimit > 0) {
            (bool ok, ) = msg.sender.call.value(_feeLimit)("");
            require(ok, "refund fee failed");
        }
        return 0;
    }
```
