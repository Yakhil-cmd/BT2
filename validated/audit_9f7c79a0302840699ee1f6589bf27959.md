### Title
AAs Cannot Send Out Fixed-Denomination (Indivisible) Assets They Receive, Causing Permanent Fund Freezing - (File: `aa_composer.js`)

### Summary
The external report describes forwarder/withdrawal-helper contracts that can accept and route tokens but silently fail to handle native ETH because they lack a `receive` function, leading to bridged/wrapped funds becoming permanently stuck. The structural analog in `ocore` is `aa_composer.js`'s unit-composition logic for Autonomous Agent (AA) response units: an AA can receive *any* asset sent to it (recorded via `getTrigger`), but when it tries to compose an outgoing `payment` message for an asset that is `fixed_denominations` (an indivisible/textcoin-style asset), that message is silently dropped before being sent, exactly like ETH being bounced off a contract with no `receive()`.

### Finding Description
`getTrigger()` collects outputs of *any* asset sent to an AA address without restriction: [1](#0-0) 

`updateInitialAABalances()` then credits the AA's internal balance (`aa_balances`) for that asset unconditionally, regardless of whether it is divisible or fixed-denomination: [2](#0-1) 

However, when the AA's own definition tries to emit an outgoing `payment` message that carries that same fixed-denomination asset in `sendUnit()`, the composition path explicitly skips completing the payload for such assets and defers a decision ("will skip it later"): [3](#0-2) 

The payment message is then unconditionally filtered out later, regardless of what the AA's oscript intended to send: [4](#0-3) 

This is because indivisible/fixed-denomination assets require a fundamentally different payload structure (`denomination`, single-input coin picking by serial number, `is_private` proof logic implemented in `indivisible_asset.js`'s `pickIndivisibleCoinsForAmount`/`composeIndivisibleAssetPaymentJoint`) that the generic AA payment-composition code path in `aa_composer.js` never implements. There is no `aaApps` capability or oscript primitive that lets an AA construct this special payload; the aaApps list only supports the generic completion logic shown above: [5](#0-4) 

Consequently, any AA that is designed to forward, exchange, escrow, or refund whatever it receives (a very common oscript pattern, e.g. the "silently accept coins" branches in `test/samples/a_bank_without_percent.oscript` and `test/samples/sell_asset_for_bytes.oscript`, or a dedicated forwarder such as `test/samples/forwarder_of_bytes.oscript`) will accept and credit a fixed-denomination asset into its balance, but any oscript-authored attempt to pay that same asset back out is silently discarded by `sendUnit`. If that removal empties the whole outgoing unit, the AA falls back to `handleSuccessfulEmptyResponseUnit`, eating the coins with no response and no refund: [4](#0-3) 

### Impact Explanation
This is a genuine, unrecoverable AA fund-freezing bug class analogous to the ETH-stuck-in-bridge issue. Once a fixed-denomination asset is sent to an AA address, the AA's `aa_balances` row is credited, but there is no working code path (in oscript or in the generic message composer) that allows the AA to move that balance back out via a `payment` message — the message is filtered out at both the per-message stage and the final stage, and there is no alternate withdrawal mechanism available to AAs (unlike EOAs, which use `indivisible_asset.js`'s specialized picker/prover). The funds become permanently inaccessible, matching the "AA fund loss or freezing" acceptance criterion. Any asset issuer or user who mistakenly (or deliberately, to test/exploit a forwarder-style AA) sends an indivisible asset to a "generic forwarder"/"accept-and-relay" AA effectively burns those coins into an address that can never move them again.

### Likelihood Explanation
Likelihood is moderate-to-high: an unprivileged asset issuer can create a fixed-denomination asset at will (`asset` message with `fixed_denominations: true`), and an unprivileged unit poster can then send that asset to any AA, including widely deployed general-purpose "accept any asset and route it" AAs shown in the codebase's own sample scripts (bank/forwarder/exchange patterns). No special privilege, timing, or race condition is required — a single crafted unit triggers the freeze.

### Recommendation
Either (a) reject triggers that deliver fixed-denomination assets to an AA at the validation/trigger stage (bounce immediately with a clear error, so senders don't lose funds silently), or (b) implement full indivisible-asset payload composition support (denomination-aware coin selection, serial numbers, and private-proof generation) inside `aa_composer.js`'s `sendUnit` so that AAs can actually forward or refund such assets, mirroring what `indivisible_asset.js` already does for regular wallets.

### Proof of Concept
1. Issue a `fixed_denominations` asset `X` (any user can do this via a normal `asset` message).
2. Deploy (or use an existing) forwarder-style AA, e.g. the pattern in `test/samples/forwarder_of_bytes.oscript` / `test/samples/a_bank_without_percent.oscript`, whose "accept coins" branch composes a `payment` message intending to route or refund whatever asset was received in `trigger.output`.
3. Send a unit that pays asset `X` to the AA address as the trigger.
4. Observe in `handleTrigger`/`sendUnit` (`aa_composer.js` lines 1323-1330 and 1356-1361) that: `updateInitialAABalances` credits the AA's `aa_balances` for asset `X`, but the `payment` message referencing asset `X` is filtered out because `assetInfos[asset].fixed_denominations` is true, resulting in `handleSuccessfulEmptyResponseUnit` — the AA keeps the balance internally forever with no way to spend it back out.
