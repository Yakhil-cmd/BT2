### Title
`nominate()` in `pallet-staking` silently accepts non-existent (unregistered) validators as targets - ([File: substrate/frame/staking/src/pallet/mod.rs])

### Summary
The `Kryptonite` report concerns `execute_redelegate_proxy` allowing redelegation to non-active validators because the check for "is this validator active" is missing, leaving the caller in a state that requires a costly cooldown to correct. The closest demonstrable analog in the Polkadot SDK is in the classic `pallet-staking::nominate` extrinsic: it checks whether a nomination target is *blocked*, but never checks whether the target is a *registered validator at all*. A signed, unprivileged nominator can therefore submit a "nomination" to an account that never called `validate()`, and the call succeeds silently instead of being rejected.

### Finding Description
In `pallet::mod.rs`'s `nominate` dispatchable (call index 5), each target is validated with: [1](#0-0) 

```rust
let old = Nominators::<T>::get(stash).map_or_else(Vec::new, |x| x.targets.into_inner());

let targets: BoundedVec<_, _> = targets
    .into_iter()
    .map(|t| T::Lookup::lookup(t).map_err(DispatchError::from))
    .map(|n| {
        n.and_then(|n| {
            if old.contains(&n) || !Validators::<T>::get(&n).blocked {
                Ok(n)
            } else {
                Err(Error::<T>::BadTarget.into())
            }
        })
    })
    .collect::<Result<Vec<_>, _>>()?
    .try_into()
    .map_err(|_| Error::<T>::TooManyNominators)?;
```

`Validators::<T>::get(&n)` returns the *default* `ValidatorPrefs` (`blocked: false`) for any account that never registered as a validator, so `!Validators::<T>::get(&n).blocked` evaluates to `true` even when `n` was never a validator. The intended check — that `n` must actually exist in `Validators` — is missing; only the `blocked` flag is checked.

This is the exact bug class that Parity's own engineers already identified and fixed in the sibling crate `pallet-staking-async`, per the changelog: [2](#0-1) , and the fixed logic in `pallet-staking-async` explicitly adds the missing containment check: [3](#0-2) 

```rust
let targets: BoundedVec<_, _> = targets
    .into_iter()
    .map(|n| {
        if old.contains(&n) ||
            (Validators::<T>::contains_key(&n) && !Validators::<T>::get(&n).blocked)
        {
            Ok(n)
        } else {
            Err(Error::<T>::BadTarget.into())
        }
    })
    .collect::<Result<Vec<_>, DispatchError>>()?
```

The classic `pallet-staking` crate (used by Polkadot, Kusama, and their parachains today) was **not** patched with this same `contains_key` check, while `pallet-staking-async` (the newer, in-development staking pallet) was. This is a real, unprivileged entry-point (`Staking::nominate`, a signed extrinsic) reachable by any bonded account meeting `MinNominatorBond` — [4](#0-3) .

### Impact Explanation
A nominator can end up with a `Nominations` entry pointing at accounts that are not (and never were) validators. Because election-provider target snapshots are built from `Validators::<T>::iter()` (not from arbitrary nominator targets), stake directed at a phantom target contributes nothing to any validator's exposure and earns no era reward — the nominator's bonded stake is effectively wasted for as long as the mistake persists, mirroring the "unexpected situation" theme of the original report (a staking-target error that a user is stuck with).

Unlike the original CosmWasm report, `pallet-staking::nominate` has **no cooldown** between calls, so a nominator can immediately re-nominate to fix the mistake — this materially reduces the severity relative to the original 5.0 BVSS finding, where a forced redelegation cooldown made correction costly. The measurable loss here is limited to missed rewards for the affected era(s), not a locked/irreversible state. I therefore classify this as Low severity, not Medium/High.

### Likelihood Explanation
Likelihood is Low: the bug is only triggered by mistake (fat-fingering a target, or nominating a validator that has since been fully removed/rotated out of `Validators` storage — though `chill`/`validate` removal actually clears the whole entry, so this is mainly a "never was a validator" typo scenario), not by a profitable exploit path for a third party against another user's funds. There is no attacker-victim relationship; the "victim" is the caller themselves.

### Recommendation
Backport the containment check from `pallet-staking-async` to `pallet-staking`'s `nominate` dispatchable:

```rust
if old.contains(&n) || (Validators::<T>::contains_key(&n) && !Validators::<T>::get(&n).blocked) {
    Ok(n)
} else {
    Err(Error::<T>::BadTarget.into())
}
```

### Proof of Concept
- Failed guard: `Validators::<T>::get(&n).blocked` check in `substrate/frame/staking/src/pallet/mod.rs:1411` does not verify `Validators::<T>::contains_key(&n)`.
- Deployment evidence: `pallet-staking` is the staking pallet compiled into live Polkadot/Kusama-style runtimes; `nominate` is dispatchable by any signed account satisfying `MinNominatorBond`, i.e., no privileged role is required [5](#0-4) .
- Minimal reproduction (conceptual, using the existing mock/test harness in `substrate/frame/staking/src/tests.rs` and `ExtBuilder`): bond a fresh account, then call `Staking::nominate(RuntimeOrigin::signed(controller), vec![account_that_never_called_validate])` and assert `Ok(())` plus that `Nominators::<Test>::get(stash).unwrap().targets` contains the non-validator account. **I did not execute this test** — no execution tool was available in this session, so this is a described-but-unexecuted repro, not a claimed passing/failing run. Confidence in the code-level defect itself is high (directly read from the two pallet implementations), but the "silently succeeds" behavior at runtime should be confirmed by actually running the described test before filing.
- Note: I was unable to fully inspect the single `BadTarget`-referencing test in `substrate/frame/staking/src/tests.rs` (only its existence, not its body, was confirmed by grep) due to running out of tool iterations; it's possible that test already exercises a related-but-different scenario (e.g., nominating a currently-blocked validator) rather than a never-registered one. This should be verified before treating the PoC as conclusive.

```rust
		pub fn nominate(
			origin: OriginFor<T>,
			targets: Vec<AccountIdLookupOf<T>>,
		) -> DispatchResult {
			let controller = ensure_signed(origin)?;

			let ledger = Self::ledger(StakingAccount::Controller(controller.clone()))?;

			ensure!(ledger.active >= MinNominatorBond::<T>::get(), Error::<T>::InsufficientBond);
			let stash = &ledger.stash;

			// Only check limits if they are not already a nominator.
			if !Nominators::<T>::contains_key(stash) {
				// If this error is reached, we need to adjust the `MinNominatorBond` and start
				// calling `chill_other`. Until then, we explicitly block new nominators to protect
				// the runtime.
				if let Some(max_nominators) = MaxNominatorsCount::<T>::get() {
					ensure!(
						Nominators::<T>::count() < max_nominators,
						Error::<T>::TooManyNominators
					);
				}
			}

			ensure!(!targets.is_empty(), Error::<T>::EmptyTargets);
			ensure!(
				targets.len() <= T::NominationsQuota::get_quota(ledger.active) as usize,
				Error::<T>::TooManyTargets
			);
```
