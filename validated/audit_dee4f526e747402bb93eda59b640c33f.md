### Title
Webhook signature is bound to `repository.owner.login`/`organization.login`, but every event handler acts on the independently-attacker-controlled `repository.full_name` field, allowing cross-organization stack manipulation in multi-tenant Shipit installs - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret to validate the HMAC signature using `repository_owner`, which is parsed from `params.dig('repository','owner','login')` (or `params.dig('organization','login')` as fallback). [1](#0-0) [2](#0-1)  Every webhook `Handler`, however, resolves the repository/stack it actually acts on from a *different* field of the same attacker-supplied JSON body: `payload.dig('repository', 'full_name')`. [3](#0-2)  Because `owner.login` and `full_name` are two independent strings inside a single JSON payload that the requester fully controls, nothing forces them to refer to the same repository.

### Finding Description
Shipit supports multi-tenant configurations where multiple GitHub organizations, each with its own `webhook_secret`, are configured under `Shipit.github(organization: ...)` (see `test/dummy/config/secrets_double_github_app.yml`, which configures `OrgOne`/`OrgTwo` each with distinct `webhook_secret`s). [4](#0-3)  The webhook endpoint is a single shared endpoint for the whole install. [5](#0-4) 

`verify_signature` computes/verifies the HMAC using only the secret belonging to `repository_owner` (derived from `repository.owner.login`), and does nothing to ensure that `repository.full_name`'s owner segment matches that same value:
```
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [6](#0-5) 

All handlers (`PushHandler`, `PullRequest::ClosedHandler`, `PullRequest::OpenedHandler`, `PullRequest::ReopenedHandler`, `PullRequest::LabeledHandler`, `PullRequest::LabelCapturingHandler`, etc.) instead resolve the target `Repository`/`Stack` via `Repository.from_github_repo_name(payload.dig('repository','full_name'))`, which splits on `/` and does a database lookup unrelated to which secret authenticated the request. [3](#0-2) [7](#0-6)  For example, `PullRequest::ClosedHandler#process` calls `review_stack.archive!` and `PullRequest::ReopenedHandler#process` calls `stack.unarchive!` purely based on the repository resolved from `full_name`. [8](#0-7) [9](#0-8) 

Since the JSON body is fully attacker-controlled (it's the raw `request.raw_post`, only origin-authenticated via HMAC, never schema-bound to require `owner.login` be a substring of `full_name`), an actor who legitimately administers *their own* GitHub organization's App/webhook (and therefore knows that org's `webhook_secret`, as configured per-org in `secrets.yml`) can craft a payload where:
- `repository.owner.login` = their own org (used only to select which secret verifies the signature), and
- `repository.full_name` = `"victim-org/victim-repo"` (used to select the actual `Stack`/`Repository` acted upon).

This breaks the deployment-trust binding: `organization authenticated == repository acted upon` no longer holds.

### Impact Explanation
Depending on the handler triggered, this allows an attacker who controls only their own tenant's webhook secret to trigger state changes against a completely unrelated organization's stacks: archiving/unarchiving review stacks (`ClosedHandler`, `ReopenedHandler`), triggering `sync_github` (`PushHandler`), or updating PR/label state used for provisioning decisions (`OpenedHandler`, `LabeledHandler`, `LabelCapturingHandler`). This is an authorization-boundary crossing between tenants (organizations) hosted on the same Shipit instance, matching the "organization that authenticated versus the repository that is written" binding break called out as in-scope. This can reach the "cross-repository writes" Critical bucket for handlers that mutate a victim org's stack/review-stack records (archive/unarchive, PR label capture) without the victim's GitHub App ever having sent that event.

### Likelihood Explanation
This only applies to multi-tenant Shipit deployments with more than one configured GitHub organization (each with a distinct `webhook_secret`), as demonstrated by the `secrets_double_github_app.yml` fixture. [10](#0-9)  The attacker needs only to be a legitimate administrator of one tenant's GitHub App/organization (which is an unprivileged actor from the perspective of *other* tenants on the same Shipit instance) — no compromise of the victim org, no Shipit account, and no `ApiClient` token is required, satisfying the "unprivileged attacker" requirement.

### Recommendation
In `WebhooksController#verify_signature` and in `Handler#repository_name`/`stacks`, enforce that the organization used to select the verifying secret is the same organization embedded in `repository.full_name` (i.e., derive the owner strictly from one canonical field and validate consistency), rejecting payloads where `repository.owner.login` does not match the owner segment of `repository.full_name`.

### Proof of Concept
1. Shipit is configured with two orgs, `OrgOne` and `OrgTwo`, each with its own `webhook_secret` (as in `secrets_double_github_app.yml`).
2. Attacker administers `OrgTwo`'s GitHub App and knows `OrgTwo`'s `webhook_secret`.
3. Attacker crafts a `pull_request` "closed" webhook JSON payload:
```json
{
  "action": "closed",
  "number": 42,
  "pull_request": { ... },
  "repository": { "owner": { "login": "OrgTwo" }, "full_name": "OrgOne/victim-repo" },
  "sender": { "login": "attacker" }
}
```
4. Attacker computes `X-Hub-Signature` using `OrgTwo`'s known `webhook_secret` over the raw body and POSTs it to the shared `/github/webhooks` endpoint with header `X-Github-Event: pull_request`.
5. `verify_signature` looks up `Shipit.github(organization: "OrgTwo")` (from `repository.owner.login`) and the signature verifies successfully. [1](#0-0) 
6. `PullRequest::ClosedHandler#repository` resolves `Repository.from_github_repo_name("OrgOne/victim-repo")` and `process` calls `review_stack.archive!` on `OrgOne`'s review stack, despite the request never being authenticated by `OrgOne`'s GitHub App. [8](#0-7)

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
