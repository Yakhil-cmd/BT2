## Title
Single global TPS-fee curve applied to both plain units and AA-trigger units causes disproportionate fee escalation and unconfirmable AA triggers during congestion - (File: storage.js)

### Summary
The reported PoolTogether issue is that a single dutch-auction decay curve is shared across auctions with very different value ranges (prize tiers), so lower/higher-value tiers ramp up to their tier-specific fee caps at very different, uncalibrated rates — leading to inefficient/unclaimable outcomes for some tiers. `ocore`'s v4 TPS-fee mechanism has the same root-cause shape: a single global exponential fee curve (`base_tps_fee`, `tps_interval`, `tps_fee_multiplier`) is applied uniformly to two structurally different "tiers" of unit — plain payment units (`count_units = 1`) and AA-trigger units (`count_units = 1 + count_primary_aa_triggers * max_aa_responses`, up to `1 + MAX_RESPONSES_PER_PRIMARY_TRIGGER`) — with `count_units` used both as a fee multiplier and as additional simulated load fed back into the same shared TPS counter.

### Finding Description
`storage.getLocalTpsFee()` computes the fee per unit from a single shared curve: [1](#0-0) 

and `getCountUnitsPayingTpsFee()` inflates `count_units` for any unit that triggers an AA, using either the declared `max_aa_responses` or the network-wide cap `MAX_RESPONSES_PER_PRIMARY_TRIGGER` as a fallback: [2](#0-1) 

This same `count_units` value is fed recursively into `getLocalTps()` when computing the TPS load contributed by ancestor units, so an AA-triggering unit is charged `count_units × tps_fee_per_unit`, where `tps_fee_per_unit` itself grows exponentially with the *same* global `tps`/`tps_interval` term used for plain single-output payments: [3](#0-2) 

Because `count_units` for an AA-trigger unit can be as large as `1 + MAX_RESPONSES_PER_PRIMARY_TRIGGER` while a plain payment always has `count_units = 1`, the *effective* price curve experienced by AA-triggering senders is the plain exponential curve multiplied by up to `MAX_RESPONSES_PER_PRIMARY_TRIGGER`, i.e. AA triggers ride a much steeper, uncalibrated auction relative to ordinary payments — exactly the "shared decay parameter applied to tiers of very different scale" pattern flagged in the report. At composition time (`estimateTpsFee`, `composer.js`) and at validation time (`validateTpsFee`, `validation.js`), this same shared curve is used to decide whether a unit's declared `tps_fee` is acceptable: [4](#0-3) [5](#0-4) 

At stabilization, however, the *actual* charged fee `getFinalTpsFee()` is derived from `getFinalTps()`, which counts real `count_aa_responses` (the observed number of AA responses, capped by execution, not the declared `max_aa_responses`): [6](#0-5) 

so the "auction speed" experienced when composing/validating a unit (driven by the declared cap) and the one used to true-up its balance at stabilization (driven by actual execution) are calibrated completely differently, and both ride the same global exponential rather than each type of traffic having its own curve — this is explicitly acknowledged as a known gap in the code itself: [7](#0-6) 

### Impact Explanation
During periods of elevated TPS, ordinary single-output payments and AA-triggering units are forced through the identical exponential curve, but AA triggers are charged `count_units` times as much per the same curve and also inflate the observed `tps` for everyone downstream (since `count_units` is added into `getLocalTps()`/`getCurrentTps()` for subsequent units). This means AA-trigger senders can be priced out of confirmation (rejected by `validateTpsFee` as underpaying, or soft-rejected via `min_acceptable_tps_fee`) far sooner than plain-payment senders under the same network conditions, even though both are competing for the same underlying DAG throughput. This can result in legitimate AA-directed payments (i.e., funds intended for an Autonomous Agent) being unable to get included/confirmed during congestion, effectively freezing fund flow to AAs while plain payments continue to clear normally — a tier-specific denial of confirmability caused entirely by a shared, uncalibrated pricing curve, matching the "auctions run at significantly different speeds for different tiers" bug class from the report.

### Likelihood Explanation
This requires only ordinary network congestion (elevated recent TPS) plus normal AA-directed payment traffic — no malicious peer, hub, or privileged actor is needed. Any unprivileged unit poster sending to an AA address is affected purely as a side effect of `getCountUnitsPayingTpsFee()`/`getLocalTpsFee()` being on the hot path of unit composition and validation for every unit since the `v4UpgradeMci` upgrade.

### Recommendation
Introduce separate TPS accounting/pricing streams (or per-type multipliers on the decay/interval parameters) for plain units versus AA-trigger units, rather than folding `count_units` into a single shared exponential curve and shared global TPS counter. Alternatively, calibrate `tps_interval`/`base_tps_fee` as a function of the unit's `count_units` so that the marginal cost curve for high-`count_units` AA triggers scales consistently with the curve for `count_units = 1` payments, and reconcile the declared-cap-based estimate (`max_aa_responses`) with the actual-usage-based final fee (`count_aa_responses`) more tightly to avoid divergence between admission-time and settlement-time pricing.

### Proof of Concept
1. Network reaches a recent TPS level such that `storage.getCurrentTps()`/`getRecentTps()` yields a moderately high `tps` (see `getMinAcceptableTpsFeeMultiplier()` threshold of `tps > 15`): [8](#0-7) 
2. Regular payment unit composes with `count_units = 1`; its `tps_fee_per_unit` is `base_tps_fee * (exp(tps/tps_interval) - 1)`, a moderate value.
3. An AA-triggering unit composes at the same moment with `max_aa_responses` defaulting toward `constants.MAX_RESPONSES_PER_PRIMARY_TRIGGER` (as used by `estimateTpsFee`): [9](#0-8)  — its required fee is `count_units * tps_fee_per_unit`, i.e. up to `MAX_RESPONSES_PER_PRIMARY_TRIGGER` times larger, and it also raises the effective `tps` seen by subsequent units in `getLocalTps()`/`getCurrentTps()` because `count_units` is added to the running count.
4. As `tps` climbs, `min_acceptable_tps_fee` (based on `getMinAcceptableTpsFeeMultiplier()` at `getCurrentTps`) rejects underpaying AA-trigger units with a transient error before it rejects plain payments, because the AA-trigger unit's required multiple (`count_units`) compounds on the same exponential term: [10](#0-9)  — AA-directed payments stall while ordinary payments continue to confirm.
