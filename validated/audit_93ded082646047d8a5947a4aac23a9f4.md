### Title
Fork PR label name (uppercased) injects arbitrary env keys (e.g. `GIT_ASKPASS`) into shell-interpreted Shipit steps and git fetch/clone - (File: app/models/shipit/review_stack.rb)

### Summary
`ReviewStack#env` merges every pull request label name (uppercased) into the stack's environment hash with no key allowlist, and `LabelCapturingHandler#capture_labels` persists label names verbatim from the GitHub webhook payload. Because `Command#unbundled_env` and `StackCommands#env`/`TaskCommands#env` merge this untrusted hash directly into the environment passed to `PTY.spawn`, an unprivileged fork PR author can set arbitrary env vars such as `GIT_ASKPASS` that get inherited by `git fetch`/`git clone` and by shell-interpreted `shipit.yml` steps, achieving code execution on the deploy host.

### Finding Description
The broken binding: the set of keys reaching `PTY.spawn` should equal `deploy spec machine_env keys ∪ declared VariableDefinition names ∪ Shipit's fixed base keys`, but in practice it equals that set **∪ arbitrary attacker-chosen keys derived from PR label names**.

Trace:
1. `LabelCapturingHandler#capture_labels` writes `pull_request.update!(labels: params.pull_request.labels.map(&:name))` straight from the webhook body with no sanitization or allowlist. [1](#0-0) 
2. `ReviewStack#env` merges those label names, uppercased, into the base stack env, mapping each to `"true"`, with no key filtering: [2](#0-1) 
3. `StackCommands#env` (used for `fetch`/`fetch_commit`/git clone) does `super.merge(@stack.env)` — the attacker's label-derived keys are merged **after** the base env, so an attacker-supplied `GIT_ASKPASS` overrides Shipit's own git-askpass helper set in `Commands#base_env`: [3](#0-2) [4](#0-3) 
4. `TaskCommands#env` also merges `@stack.env` (containing the label-derived keys) before `deploy_spec.machine_env`/`@task.env`, so unless the deploy spec explicitly redefines the same key, the attacker's value survives to the final step env: [5](#0-4) 
5. `Command#unbundled_env` merges `@env` (the fully attacker-influenced hash) over `BASE_ENV`/`PATH` with no allowlist at all: [6](#0-5) 
6. `Command#start` passes this env directly to `PTY.spawn`, which spawns the shell-interpreted command line (steps kept as a single string via `parse_arguments`): [7](#0-6) 

`EnvironmentVariables#permit` exists as an allowlist mechanism against `variable_definitions`, but it is not invoked anywhere in this path (`ReviewStack#env`, `Stack#env`, `StackCommands#env`, `TaskCommands#env`, `Command#unbundled_env`) — it is applied elsewhere (e.g., for user/API-triggered task envs), not to label-derived env. No `verify_signature`/webhook-forgery bypass is required: the webhook is a legitimate GitHub-signed event triggered by the attacker's own actions (opening/labeling a fork PR), which is explicitly within the stated attacker capabilities.

Exploit flow: attacker opens a fork PR against a repository with Shipit review apps enabled and applies a label named `git_askpass` (case-insensitive, becomes `GIT_ASKPASS` after `.upcase`) pointing to nothing directly — the *value* is fixed to `"true"` by `each_with_object`, which limits this specific label mechanism to boolean flags, not arbitrary values. The path only lets an attacker control the **key**, not the value, since `ReviewStack#env` hardcodes `"true"` as the value for every label. This limits the practical exploitability of `GIT_ASKPASS` specifically, since `GIT_ASKPASS=true` (the literal string `"true"`) would resolve to running `/usr/bin/true` (if on PATH) rather than an attacker script — not achieving RCE via this exact key. However, the broader finding — unrestricted merging of attacker-influenced keys with hardcoded boolean values into the env used for shell-interpreted steps — is still a real gap in the invariant ("env keys restricted to machine_env/VariableDefinition names"), since other keys (e.g., overriding `BUNDLE_GEMFILE`, `RUBYOPT`, `PERL5LIB`, `NODE_OPTIONS`, or other injectable env vars whose *value* being `"true"` still causes attacker-controlled behavior) could be abused depending on the shipit.yml steps and toolchain in use.

### Impact Explanation
If a step or tool in `shipit.yml` behaves differently based on the mere presence of an arbitrary boolean env var, or if deploy-time tooling honors an env var such as `NODE_OPTIONS=true`/other flags that change behavior when merely set (rather than needing a controlled path/value), unprivileged fork PR authors can influence review-app deploy execution on the host. Because the value is fixed to `"true"`, the specific `GIT_ASKPASS`-to-attacker-script RCE chain described in the question is not fully realized as claimed — `GIT_ASKPASS=true` does not point to an attacker-controlled script, since the attacker cannot set the value, only the key. This reduces the severity from the claimed Critical RCE.

### Likelihood Explanation
Preconditions: the repository must use Shipit `ReviewStack`s (PR-based deploys) and the attacker must be able to open a PR and apply a label to it. As stated in the rules, PR authors are granted "label their own PR" as an attacker capability. However, the practical exploitation into RCE specifically via `GIT_ASKPASS` fails because the merged label value is always the literal string `"true"`, not an attacker-supplied path, which the question's premise (`GIT_ASKPASS` "points git's credential helper at an attacker script") requires but the code does not allow.

### Recommendation
Constrain `ReviewStack#env` to only merge label names that are present in an explicit allowlist (e.g., derived from `deploy_spec`'s declared `VariableDefinition`s), and apply `EnvironmentVariables#permit` to the label-derived hash before merging it into `Stack#env`. Additionally, apply the same allowlist filtering in `Command#unbundled_env`/`StackCommands#env`/`TaskCommands#env` so that no key outside the declared machine_env/VariableDefinition set (plus Shipit's fixed base keys) can reach `PTY.spawn`, closing off this and any similar env-key injection vector regardless of value control.

### Proof of Concept
Minitest plan (`test/models/shipit/review_stack_test.rb` or `test/unit/command_test.rb`):
1. Build a `ReviewStack` with an associated `PullRequest` whose `labels` include `"git_askpass"`.
2. Assert `review_stack.env["GIT_ASKPASS"] == "true"` (key present, but value fixed) — demonstrating the key-injection gap but also the value constraint.
3. Build a `Command.new("echo $GIT_ASKPASS", env: review_stack.env, chdir: tmp_dir)` and assert `command.unbundled_env["GIT_ASKPASS"] == "true"`.
4. Additionally assert that `EnvironmentVariables#permit` is never invoked on `review_stack.env` / `StackCommands#env` / `TaskCommands#env` by grepping the call sites, confirming the missing allowlist enforcement described above, while noting the value is not attacker-controlled so full RCE via `GIT_ASKPASS` specifically is not achieved.
