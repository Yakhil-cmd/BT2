### Title
Webhook Authentication Bypass via Organization/Repository Mismatch — Cross-Organization Forged GitHub Events - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the GitHub App (and therefore the `webhook_secret` used for HMAC verification) using `repository_owner`, which is parsed from the attacker-controlled JSON body (`params.dig('repository', 'owner', 'login')` or the `organization.login` fallback). The event handlers that actually act on the payload (`Shipit::Webhooks::Handlers::Handler#repository_name`, used by e.g. `PushHandler`) resolve the target repository from a *different* field of the same body: `payload.dig('repository', 'full_name')`. Nothing binds these two fields together, so the organization whose secret is used to authenticate the request is not necessarily the organization that owns the repository actually mutated. [1](#0-0) [2](#0-1) 

### Finding Description
Shipit supports hosting multiple GitHub organizations in a single deployment (`docs/setup.md`), each with its own `app_id`, `private_key`, and optional `webhook_secret`. `GitHubApp#verify_webhook_signature` explicitly treats a missing/blank `webhook_secret` as "always verified": [3](#0-2) 

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```

`WebhooksController#verify_signature` picks which org's `webhook_secret` to check against using `repository_owner`, itself taken straight out of the untrusted request body: [4](#0-3) [5](#0-4) 

Meanwhile, `Handler#stacks`/`#repository_name` resolves the repository (and thus the `Stack` that gets mutated — synced, given a commit status, etc.) from a completely separate field of the body, `repository.full_name`: [6](#0-5) 

Because `verify_signature` and `repository_name` independently `dig` into attacker-supplied JSON, an attacker can construct a single payload where:
- `repository.owner.login` (or `organization.login`) = an organization configured in `Shipit.github` **without** a `webhook_secret` set (a state the docs mark as valid/optional, see `docs/setup.md` "Webhook secret (optional)"), so `verify_webhook_signature` short-circuits to `true` with zero knowledge of any secret;
- `repository.full_name` = a *different*, secured organization's repository that Shipit tracks with real stacks.

This breaks the binding `organization authenticated == repository that is written`: the signature check authenticates against org A (unsecured), but the event handler acts on org B's repository/stack.

### Impact Explanation
An unauthenticated, unprivileged network attacker can forge GitHub webhook events (`push`, `status`, `check_suite`, `membership`, etc.) targeting any stack tracked by Shipit, as long as at least one configured GitHub organization in the deployment lacks a `webhook_secret` (an explicitly optional and documented configuration). Concretely:
- Forged `status` events let an attacker mark arbitrary commits on a victim stack as CI-`success`, which Shipit's deployability/merge-queue logic consumes to gate merges and deploys — enabling an unauthorized merge or deploy of unreviewed code.
- Forged `push` events trigger `GithubSyncJob`/`stack.sync_github`, letting an attacker force re-sync of arbitrary stacks.
- Forged `membership` events can create/attach arbitrary GitHub users/teams into Shipit's authorization model.

This meets the High/Critical bar: escalation into deploy/merge gating and cross-repository writes performed without possessing the secured organization's credentials.

### Likelihood Explanation
Likelihood is Medium-to-High in multi-organization Shipit deployments where at least one configured GitHub org omits `webhook_secret` (explicitly permitted, and the single-org example in `config/secrets.development.example.yml` even ships with `webhook_secret: # nil`). No authentication, session, or API token is required — only knowledge of the public `/webhooks` endpoint and the target repository's `full_name`, both public information.

### Recommendation
Bind webhook verification to the same repository identity used by the handlers: verify the signature using the secret belonging to the organization that owns `repository.full_name` (not a separately-dug `repository.owner.login`/`organization.login`), and reject events for organizations that cannot be unambiguously resolved to a single, consistent owner across the whole payload. Consider also requiring a non-blank `webhook_secret` for every configured organization, or refusing unauthenticated events for any org share where another configured org enforces signatures, to eliminate the "unsecured org" bypass path entirely.

### Proof of Concept
1. Deploy Shipit configured with two organizations: `org-open` (no `webhook_secret`) and `org-secured` (has `webhook_secret`, and owns a tracked repository/stack, e.g. `org-secured/prod-app`).
2. POST to `/webhooks` with header `X-Github-Event: status` and no/invalid `X-Hub-Signature`, body:
```json
{
  "repository": { "owner": { "login": "org-open" }, "full_name": "org-secured/prod-app" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/tests",
  "branches": [{"name": "master"}]
}
```
3. `verify_signature` calls `Shipit.github(organization: "org-open")`, whose `verify_webhook_signature` returns `true` unconditionally (`webhook_secret` blank) — request passes with `head(:ok)`.
4. The `status` handler resolves `repository.full_name` = `org-secured/prod-app`, finds the real tracked stack, and records the forged `success` status for the given commit, influencing deploy/merge decisions for `org-secured` without any credential belonging to `org-secured`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
