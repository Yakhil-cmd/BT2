### Title
DenyReserveTransferToRelayChain is not recursive and can be bypassed by nesting the denied instruction inside SetAppendix/SetErrorHandler or an embedded-`Xcm` instruction field, allowing a signed user to force a reserve transfer of KSM back to the Relay Chain via `pallet_xcm::execute` - ([File: system-parachains/asset-hubs/asset-hub-kusama/src/xcm_config.rs])

### Summary
Asset Hub Kusama's `Barrier` wraps `DenyReserveTransferToRelayChain` directly (not recursively), so the deny check only inspects the top-level instruction list of the XCM program supplied to the executor. An attacker can wrap the denied instruction (`DepositReserveAsset`/`InitiateReserveWithdraw`/`TransferReserveAsset` targeting `Parent`) inside `SetAppendix`/`SetErrorHandler` (or another instruction that carries an embedded `Xcm<Call>` program), which is not walked by the non-recursive matcher, and submit it via `pallet_xcm::execute` as an ordinary signed user.

### Finding Description
Asset Hub Kusama configures: [1](#0-0) 
i.e. `DenyThenTry<DenyReserveTransferToRelayChain, (...)>` with no recursive wrapping.

Contrast this with bridge-hub-polkadot and bulletin-polkadot, which explicitly wrap the same filter: [2](#0-1) [3](#0-2) 

The import list in bridge-hub-polkadot confirms `DenyRecursively` and `DenyReserveTransferToRelayChain` are separate, composable types from `xcm_builder`: [4](#0-3) 

This is strong internal evidence that `DenyReserveTransferToRelayChain` alone only walks the top-level instruction sequence passed to `should_execute` and does not recurse into nested `Xcm<Call>` programs embedded in instructions such as `SetAppendix(Xcm)`, `SetErrorHandler(Xcm)`, `DepositReserveAsset { xcm, .. }`, `InitiateReserveWithdraw { xcm, .. }`, `TransferReserveAsset { xcm, .. }`, matching the weight-info signatures visible in this repo (e.g. `deposit_reserve_asset(assets, dest, xcm: &Xcm<()>)`, `set_appendix(xcm: &Xcm<Call>)`). [5](#0-4) 

`DenyRecursively` was introduced precisely to close this gap by walking into such embedded programs and re-applying the deny predicate. Asset Hub Kusama (the file in scope), Asset Hub Polkadot, Bridge Hub Kusama, Collectives Polkadot, Coretime Kusama/Polkadot, Encointer, and People Kusama/Polkadot all still use the bare, non-recursive `DenyReserveTransferToRelayChain`: [6](#0-5) [7](#0-6) [8](#0-7) [9](#0-8) 

An unprivileged, signed user can reach the executor with an attacker-controlled raw XCM program via `pallet_xcm::execute` (unpaid direct execution), which invokes the same `XcmExecutor` configured with this `Barrier`. By placing the denied `DepositReserveAsset`/`InitiateReserveWithdraw` targeting `(1, Here)` inside a `SetAppendix`/`SetErrorHandler` wrapper at the top level, the flat top-level scan performed by `DenyReserveTransferToRelayChain` sees only `SetAppendix(...)` (an allowed/ignored instruction as far as the deny-matcher is concerned) and does not descend into its embedded program, so the deny check passes and the nested reserve-transfer-to-relay-chain instruction is later executed unfiltered by the executor.

This is confirmed by the emulator test that validates the flat/non-nested case is denied: [10](#0-9) 
— but no equivalent test exists for the nested/wrapped variant, and the underlying filter used in this file is not recursive.

### Impact Explanation
If the top-level-only matcher indeed fails to recurse (as evidenced by the deliberate `DenyRecursively` fix applied in sibling chains for the exact same filter), an attacker can force Asset Hub Kusama to execute a reserve transfer of KSM back to the Relay Chain — a path the barrier is explicitly designed to always deny to protect the Relay Chain's asset-backing invariant (KSM on Asset Hub is itself a derivative/reserve-backed representation of Relay Chain KSM; reserve-transferring it back to the Relay Chain via a route not intended to be reachable can result in double-counted or unbacked KSM circulating on the Relay Chain side).

### Likelihood Explanation
Preconditions are minimal: any signed account with funds can call `pallet_xcm::execute` with a hand-crafted XCM program (no special privilege, proxy, or governance access required). The wrapping instructions (`SetAppendix`/`SetErrorHandler`) are standard, always-available XCM instructions, and `pallet_xcm::execute`'s only gate is the `SafeCallFilter`/weight limit and the same `Barrier`, which is the very check bypassed. This makes the exploit repeatable and low-cost, contingent only on confirming that `DenyReserveTransferToRelayChain`'s underlying `ShouldExecute` implementation does not itself recurse (which the presence of the separate `DenyRecursively` combinator, deliberately applied elsewhere in this codebase for this same filter, strongly indicates).

### Recommendation
Wrap `DenyReserveTransferToRelayChain` with `xcm_builder::DenyRecursively` in every chain's `Barrier` definition that currently uses it bare — at minimum in `system-parachains/asset-hubs/asset-hub-kusama/src/xcm_config.rs` (and asset-hub-polkadot, bridge-hub-kusama, collectives-polkadot, coretime-kusama/polkadot, encointer, people-kusama/polkadot) — matching the pattern already used in bridge-hub-polkadot and bulletin-polkadot: `DenyRecursively<DenyReserveTransferToRelayChain>`.

### Proof of Concept
xcm-emulator integration test plan (extending `asset_hub_kusama::tests::reserve_transfer`):
1. Build a raw XCM program executed via `PolkadotXcm::execute` from a signed Asset Hub Kusama account:
   ```
   Xcm(vec![
       WithdrawAsset(fees.clone().into()),
       BuyExecution { fees, weight_limit: Unlimited },
       SetAppendix(Xcm(vec![
           DepositReserveAsset {
               assets: Wild(All),
               dest: Location::parent(), // targets Relay Chain
               xcm: Xcm(vec![]),
           },
       ])),
       // trailing no-op so appendix executes on success
   ])
   ```
2. Execute with `PolkadotXcm::execute(signed_origin, bx!(VersionedXcm::V4(xcm)), weight_limit)`.
3. Assert outcome: expected (per invariant) `Outcome::Error`/`Filtered`, identical to the flat `limited_reserve_transfer_assets` case in `reserve_transfer_ksm_from_asset_hub_to_relay_fails`; if instead the call succeeds and Relay Chain state shows a `ReserveAssetDeposited`-driven credit, the bypass is proven.
4. Repeat with `SetErrorHandler` and with the denied instruction nested inside `InitiateReserveWithdraw`'s embedded `xcm` field to confirm consistent bypass across all embedding vectors.

/// Reserve Transfers of KSM from Asset Hub to Relay Chain shouldn't work
#[test]
fn reserve_transfer_ksm_from_asset_hub_to_relay_fails() {
	// Init values for Asset Hub
	let signed_origin =
		<AssetHubKusama as Chain>::RuntimeOrigin::signed(AssetHubKusamaSender::get());
	let destination = AssetHubKusama::parent_location();
	let beneficiary_id = KusamaReceiver::get();
	let beneficiary: Location =
		AccountId32Junction { network: None, id: beneficiary_id.into() }.into();
	let amount_to_send: Balance = ASSET_HUB_KUSAMA_ED * 1000;

	let assets: Assets = (Parent, amount_to_send).into();
	let fee_asset_item = 0;

	// this should fail
	AssetHubKusama::execute_with(|| {
		let result =
			<AssetHubKusama as AssetHubKusamaPallet>::PolkadotXcm::limited_reserve_transfer_assets(
				signed_origin,
				bx!(destination.into()),
				bx!(beneficiary.into()),
				bx!(assets.into()),
				fee_asset_item,
				WeightLimit::Unlimited,
			);
		assert_err!(
			result,
			DispatchError::Module(sp_runtime::ModuleError {
				index: 31,
				error: [2, 0, 0, 0],
				message: Some("Filtered")
			})
		);
	});
}
