### Title
Unbounded in-memory buffering of git subprocess stdout/stderr driven by untrusted upstream repo content - (File: pkg/cmd/cmd.go)

### Summary
`git-sync`'s command runner captures the entire stdout/stderr of every invoked `git` subcommand into unbounded `bytes.Buffer` objects before returning it as a string, with no size cap and no backpressure mechanism. Because git-sync repeatedly executes commands whose output size is a function of attacker-influenced remote content (refs, tags, commit history, config, log output), a remote repository crafted to produce very large command output can force the git-sync process to buffer that entire output in memory, analogous to the reported Yamux issue where a peer-influenced production of data was accumulated in an unbounded in-memory structure with no cap and no backpressure.

### Finding Description
`runWithStdin` in [1](#0-0)  allocates `outbuf := bytes.NewBuffer(nil)` and `errbuf := bytes.NewBuffer(nil)`, wires them as `cmd.Stdout` / `cmd.Stderr`, and then calls `cmd.Run()`, which blocks until the whole subprocess output has been written into these buffers [2](#0-1) . There is no maximum size enforced on `outbuf`/`errbuf`, and no streaming/discard path — every byte the git subprocess writes to stdout/stderr is retained in memory until the command exits.

This `Runner.Run`/`RunWithStdin` API is the single code path used throughout `main.go` to invoke every `git` operation in the sync loop (fetch, ls-remote, log, show-ref, config list, submodule, worktree operations, etc.) — 26 call sites in `main.go` reference this runner. Several of these operations produce output whose size is directly controlled by the content of the remote repository that git-sync is configured to pull from (e.g., `git log`, `git config list -z`, `git show-ref`, `git ls-remote`), as seen for example at [3](#0-2)  where `cmdRunner.Run(ctx, "", nil, *flGitCmd, "config", "list", "-z")` output is captured in full and then processed. An attacker able to influence the content of the synced repository (a large number of refs, an oversized/verbose config, or contrived object/ref structures that make `git` commands emit large volumes of output) can inflate the size of a single command's captured output arbitrarily, since the buffer grows without bound.

This differs from the Yamux report's specific mechanic (a *queue* of pending frames growing because the network write side gets backpressured by the peer's flow control), but it shares the same underlying bug class: attacker-influenced data is placed into an in-memory structure that has no maximum size and no bounded/streaming alternative, so the amount of memory consumed is proportional to attacker-controlled input rather than to a fixed, safe limit.

### Impact Explanation
If reachable with a sufficiently malicious upstream repository, this could allow a remote party who controls (or can influence, e.g. via a compromised or hostile `--repo` target, or a repository the sidecar is configured to mirror) the synced git repository to cause the git-sync process to allocate very large amounts of memory during a single `git` command invocation, potentially exhausting available memory and crashing the container/pod — a persistent sync denial condition, consistent with the "Reject... no-impact analogs" bar met by memory exhaustion / DoS.

### Likelihood Explanation
Likelihood is moderate-to-low in git-sync's typical unprivileged threat model: the `--repo` value and its content are operator-configured, so the attacker generally needs some level of ability to push to or otherwise control the content of the *configured* remote repository (e.g., a public repo git-sync is pointed at, or an org member/CI system with push access) — this is not a general "any git server" remote attacker scenario, and command outputs like `git config list` are local-config-driven rather than purely attacker-supplied over the wire. This makes it a real but narrower analog compared to the original Yamux bug, which is triggerable by any network peer merely by opening a connection.

### Recommendation
- Cap the size of `outbuf`/`errbuf` in [4](#0-3)  (e.g., wrap with an `io.LimitedWriter`/custom bounded writer) and fail the command (or truncate with a clear marker) once the limit is exceeded.
- For commands whose output can scale with repository size/content (log, config list, ls-remote, show-ref), prefer streaming/line-based processing over full-buffer capture where possible.
- Add resource limits (e.g., container memory limits, which Kubernetes deployments already typically set) as defense-in-depth, and consider structured logging that avoids ever quoting unbounded stdout/stderr strings into single log lines.

### Proof of Concept
Not independently verified against a live target — this is a static-analysis-based structural analog derived from `pkg/cmd/cmd.go`. A concrete PoC would require configuring `--repo` to point at a repository (or a `--git-config` string) engineered to make one of the git-sync-invoked commands (e.g., `git config list -z`, `git log`, `git ls-remote`) emit output on the order of available memory, then observing process RSS growth via `cmd.Run()` in [1](#0-0)  until OOM.

func runWithStdin(ctx context.Context, log logintf, cwd string, env []string, stdin, command string, args ...string) (string, string, error) {
	cmdStr := cmdForLog(command, args...)
	log.V(5).Info("running command", "cwd", cwd, "cmd", cmdStr)

	cmd := exec.CommandContext(ctx, command, args...)
	if cwd != "" {
		cmd.Dir = cwd
	}
	if len(env) != 0 {
		cmd.Env = env
	}
	outbuf := bytes.NewBuffer(nil)
	errbuf := bytes.NewBuffer(nil)
	cmd.Stdout = outbuf
	cmd.Stderr = errbuf
	cmd.Stdin = bytes.NewBufferString(stdin)

	start := time.Now()
	err := cmd.Run()
	wallTime := time.Since(start)
	stdout := strings.TrimSpace(outbuf.String())
	stderr := strings.TrimSpace(errbuf.String())
	if ctx.Err() == context.DeadlineExceeded {
		return stdout, stderr, fmt.Errorf("Run(%s): %w: { stdout: %q, stderr: %q }", cmdStr, ctx.Err(), stdout, stderr)
	}
	if err != nil {
		return stdout, stderr, fmt.Errorf("Run(%s): %w: { stdout: %q, stderr: %q }", cmdStr, err, stdout, stderr)
	}
	log.V(6).Info("command result", "stdout", stdout, "stderr", stderr, "time", wallTime)

	return stdout, stderr, nil
