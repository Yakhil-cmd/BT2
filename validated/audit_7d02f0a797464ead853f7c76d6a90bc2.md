### Title
Cross-repository CI-status corruption via SHA-only commit matching in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha).each`, matching every `Commit` row in the entire database that shares that SHA regardless of which repository/stack it belongs to. Since `verify_signature` in `WebhooksController` only authenticates that the request came from *some* known GitHub organization (`repository_owner`), not that the payload's SHA is scoped to that organization's own commit, a legitimate, correctly-signed `status` webhook from an attacker-owned repository can write a `Status` onto a `Commit` belonging to a completely different (e.g., private) repository whenever the two commits share a SHA.

### Finding Description
The broken binding is: `webhook.repository.full_name == commit.stack.repository.full_name` for every `Commit` row that `create_status_from_github!` is applied to. In reality, only `webhook.payload.sha == commit.sha` is checked: [1](#0-0) 

`Commit.where(sha: params.sha)` performs a global, unscoped lookup across all stacks/repositories — there is no `stack_id`, `repository_id`, or `github_repo_name` filter tying the match back to the webhook's originating repository.

`WebhooksController#verify_signature` only validates that the HMAC signature corresponds to the GitHub App/organization identified by `params.dig('repository','owner','login')`: [2](#0-1) 

This check authenticates *which organization* sent the webhook, but does nothing to bind the payload's `sha` to commits that actually belong to that organization/repository. An attacker who legitimately owns/administers any repository onboarded to the same Shipit instance (or under an org Shipit trusts) can:
1. Create a commit whose SHA collides with a commit already present on a victim's private/internal stack (trivial via the well-known empty-tree SHA `4b825dc642cb6eb9a060e54bf8d69288fbee4904`, which is identical for every empty tree in every repository, or via any deliberately duplicated tree/commit object).
2. Trigger a real `status` event on that commit in their own repository (e.g., via GitHub Actions setting a commit status, or the Statuses API, which they have full rights to on their own repo).
3. GitHub signs and delivers this webhook correctly for the attacker's organization; `verify_signature` passes because it is checking the attacker's own, legitimately-owned organization/app secret.
4. `StatusHandler#process` then matches and mutates the `Commit` row(s) in the victim's private/internal repository that happen to share that SHA, writing an attacker-controlled `state`, `description`, `target_url`, and `context` via `commit.create_status_from_github!(params)` → `Commit#create_status_from_github!` → `statuses.replicate_from_github!`.

None of the existing guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema on `StatusHandler`) validate that the SHA belongs to the requesting repository — they only validate transport-level authenticity of the sender's organization and payload shape, not object ownership.

### Impact Explanation
The attacker can write arbitrary `Status` records (any `state`: `success`, `failure`, `error`, `pending`, with attacker-chosen `description`/`target_url`/`context`) onto commits belonging to a repository/stack they have no permission on, as long as the SHA collides. `Commit#add_status` re-evaluates `deployable?`, can trigger `Hook.emit(:deployable_status, ...)`, and can call `stack.schedule_merges` — meaning a forged "success" status can unblock/trigger continuous delivery (`schedule_continuous_delivery` → `ContinuousDeliveryJob`) on a victim stack, i.e., a payload for one repository mutating another's stack/commit and potentially triggering an unauthorized deploy path. This matches the "Critical" impact category (payload for one repository mutating another's stack/commit, or triggering an unauthorized deploy/merge).

### Likelihood Explanation
Preconditions: attacker needs (a) some repository legitimately onboarded to the same Shipit instance/GitHub App installation (a low bar — Shipit is often self-served for onboarding), and (b) the ability to produce a commit sharing a SHA with a target commit. The well-known empty-tree SHA is deterministic and identical across all repositories, so any Shipit stack that has ever synced an empty/initial commit is a candidate victim with zero attacker effort to "guess" — no brute force needed. Cost is a single legitimate webhook delivery from the attacker's own repo. The attack is fully repeatable against any stack containing a colliding SHA and does not require any GitHub token, session, or Shipit credential beyond the attacker's own repository admin rights.

### Recommendation
Scope the commit lookup in `StatusHandler#process` (and analogously `CheckSuiteHandler`/other SHA-keyed handlers) to commits belonging to stacks whose repository matches the webhook's `repository.full_name`/`repository_owner`, e.g. join through `Stack` and filter by `github_repo_name`, rather than a bare global `Commit.where(sha: params.sha)`.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Create two `Stack`s, `public_stack` (public repo) and `private_stack` (private/internal repo).
2. Create a `Commit` on each stack with `sha: '4b825dc642cb6eb9a060e54bf8d69288fbee4904'`.
3. Build a `status` webhook payload with `sha: '4b825dc642cb6eb9a060e54bf8d69288fbee4904'`, `state: 'success'`, `context: 'attacker'`, and a `repository` block pointing at `public_stack`'s repo/org.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.new(payload).call` (or drive through the controller with a valid signature for the public org).
5. Assert `public_commit.reload.statuses.last.state == 'success'` (expected, same-repo write).
6. Assert `private_commit.reload.statuses.last.state == 'success'` as well — demonstrating the private stack's commit was mutated by a webhook that authenticated only for the public repository's organization, proving `webhook.repository.full_name == commit.stack.repository.full_name` does **not** hold while the status write still succeeded.
