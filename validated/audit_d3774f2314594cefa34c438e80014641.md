### Title
Cross-tenant webhook binding confusion in `MembershipHandler#process`/`#find_or_create_team!` allows org-a's webhook secret to mutate shopify's team membership - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates a webhook request solely against the GitHub organization derived from `repository.owner.login` (falling back to `organization.login` only if `repository` is absent), but `MembershipHandler#find_or_create_team!`/`#process` trust the *payload's* `organization.login` and `team.id` fields to create/attribute a `Team` and add a member to it. Because these two fields are never cross-checked, a webhook signed with org-a's `webhook_secret` can claim `organization.login = 'shopify'` and `team.id = <shopify team github_id>`, causing Shipit to add an attacker-controlled user to the real `shopify` team.

### Finding Description
The broken binding, stated as an equality that must hold but doesn't:

`repository_owner` (used for authentication in `WebhooksController#verify_signature`) == `params.organization.login` (used for authorization/attribution in `MembershipHandler#find_or_create_team!`)

Code path:
- `WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository','owner','login')` and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(signature, raw_body)`. [1](#0-0) [2](#0-1) 
- This only proves the request was signed with the `webhook_secret` configured for the organization named in `repository.owner.login`; it says nothing about the separate `organization.login`/`team` fields inside the same JSON body.
- `MembershipHandler#process` and `#find_or_create_team!` then use `params.team.id` and `params.organization.login` directly, with no re-derivation of, or comparison against, `repository_owner`: [3](#0-2) 
- `Team.find_or_create_by!(github_id: params.team.id)` looks up by `github_id` globally (not scoped by organization), so if a `Team` row already exists for the real shopify team (which it will, since `Shipit.github_teams` includes it per the precondition), the attacker's payload finds and mutates that exact record, then `team.add_member(member)` persists a `Membership` linking the attacker's `User` to it. [4](#0-3) 
- `User.find_or_create_by_login!` creates/attaches a `User` record for the attacker-supplied `member.login`, with no relationship to the authenticated organization either.

Attacker request: `POST /webhooks` with `X-Github-Event: membership`, `X-Hub-Signature` = HMAC-SHA1 over the raw body computed using org-a's `webhook_secret` (known to the attacker because they administer org-a and configured its webhook against this Shipit instance), and JSON body:
```json
{
  "action": "added",
  "repository": {"owner": {"login": "org-a"}},
  "organization": {"login": "shopify"},
  "team": {"id": <shopify_team_github_id>, "name": "...", "slug": "...", "url": "..."},
  "member": {"login": "<attacker-login>"}
}
```

Existing guards do not prevent this:
- `drop_unhandled_event` only checks that a handler exists for the event type, not payload consistency.
- `verify_signature` only verifies the byte-for-byte signature against org-a's secret; it never inspects or validates `organization.login` against `repository_owner`.
- `ExplicitParameters` schema in `MembershipHandler` only validates types/presence, not cross-field consistency with the authenticated org.
- `User#authorized?` checks membership in `Shipit.github_teams`, but that check happens later, at *login* time, using the (now-poisoned) `Membership` table — it does not prevent the poisoning itself. [5](#0-4) 

### Impact Explanation
A single crafted webhook lets an attacker who controls any tenant organization configured in Shipit (org-a) grant an arbitrary GitHub-attacker-controlled `User` account membership in any other tenant's `Team` referenced by `Shipit.github_teams`, since `Team.find_or_create_by!` is keyed only by `github_id`, not by the authenticated organization. Because `User#authorized?` and `force_github_authentication` gate access to the whole Shipit UI/API on `Shipit.github_teams` membership, this is a direct escalation into `Shipit.github_teams` authorization — matching the "High" severity category for escalation into `Shipit.github_teams` authorization. It is repeatable against any team whose `github_id` and organization login the attacker knows (both are typically public/discoverable via GitHub's API), and against any Shipit multi-tenant deployment where the attacker legitimately controls at least one configured tenant org.

### Likelihood Explanation
Preconditions required: (1) Shipit configured multi-tenant (`secrets.github` has multiple org keys), (2) attacker administers at least one configured org (org-a) and therefore knows/controls its `webhook_secret` (set when they configured the webhook pointing at the Shipit instance), (3) `Shipit.github_teams` includes a team from another tenant (e.g. shopify) that the attacker wants to join. Given these, the attack is a single unauthenticated HTTP POST with a correctly computed HMAC using a secret the attacker legitimately possesses — no privileged Shipit credentials are required. This is realistic in any Shipit installation supporting multiple independent GitHub orgs as tenants.

### Recommendation
In `WebhooksController#verify_signature` or in `MembershipHandler`, enforce that the organization used for signature verification matches the organization referenced by the event payload (e.g., require `params.organization.login.casecmp?(repository_owner)` before processing), and additionally scope `Team.find_or_create_by!` lookups by `organization` (e.g., `find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`) so a `github_id` collision alone cannot bind cross-tenant records. Reject/drop the webhook (422) when the two fields disagree.

### Proof of Concept
Add to `test/controllers/webhooks_controller_test.rb`:
```ruby
test ":membership from org-a cannot add a member to shopify's team" do
  @request.headers['X-Github-Event'] = 'membership'
  shopify_team = shipit_teams(:shopify_developers)

  payload = {
    action: 'added',
    repository: { owner: { login: 'org-a' } },       # signed org
    organization: { login: 'shopify' },               # claimed org (mismatch)
    team: { id: shopify_team.github_id, name: shopify_team.name, slug: shopify_team.slug, url: shopify_team.api_url },
    member: { login: 'attacker' }
  }.to_json

  Shipit.stubs(:github).with(organization: 'org-a').returns(stub(verify_webhook_signature: true))

  assert_no_difference -> { Membership.count } do
    post :create, body: payload, as: :json
    assert_response :unprocessable_entity # or :ok only if fix rejects mismatched org
  end
end
```
Before the fix, this test fails because a `Membership` row linking `User(login: 'attacker')` to `shopify_team` is created despite the request only ever being authenticated against `org-a`'s `webhook_secret`; after applying the recommended organization cross-check, the request is rejected and no `Membership` is created.
