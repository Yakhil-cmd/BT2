### Title
Cross-account index cache written by one user's transaction is silently reused for another user's health/liquidation calculation - (File: `mainnet/contracts/market/v0-4-market.clar`, `docs/oracle.md`)

### Summary
`market.clar`/`v0-4-market.clar` maintains a block-scoped, protocol-wide cache `index-cache-` keyed only by `{ timestamp, aid }` (not by account), populated via `accrue-and-cache` [1](#0-0) . Any user's transaction that touches a given vault asset within a block writes/primes this shared entry, and every other user's transaction that resolves a ztoken price for that asset in the same block reads the cached value instead of re-accruing, as seen in `collateral-add`'s `cache-primed` step [2](#0-1) .

### Finding Description
`accrue-and-cache` checks `map-get? index-cache-` for `{timestamp: stacks-block-time, aid}`; if present it returns the existing (possibly stale-relative-to-the-caller) value, otherwise it calls `vault-accrue` and stores the fresh result for that timestamp/asset pair [3](#0-2) . This cache is not scoped per-account or per-transaction: whichever account's transaction happens to execute first in a block for a given `aid` determines the `{index, lindex}` values that every subsequent unrelated account's health, capacity, and liquidation checks in that same block will consume, via `resolve-ztoken`'s `get-cached-indexes` lookup [4](#0-3) . Analogous to the `changeDAO` one-step-write finding, there is no isolation/confirmation step ensuring the value one principal wrote is validated before another principal's critical calculation consumes it—the write and the (unrelated) read are entangled through global shared state (`index-cache-`) keyed only by block-time and asset id, not by caller.

### Impact Explanation
Because collateral/debt capacity checks (`ERR-UNHEALTHY` in `collateral-add`) and liquidation eligibility rely on the notional valuation derived from this shared cached index [5](#0-4) , a victim's position can be evaluated against an index that was primed by an attacker's earlier same-block transaction rather than the victim's own fresh accrual. If the attacker can influence the timing/content of the first accrual in a block (e.g., by triggering `vault-accrue` via a cheap unrelated call before the victim's borrow/liquidation transaction lands), the victim's capacity/health check or a liquidator's threshold check could be computed against an index that doesn't reflect the victim's actual up-to-date state, causing the victim to be pushed into/out of a health boundary they did not create. This can enable unwarranted liquidation (temporary/permanent freezing or seizure of the victim's collateral) or block a legitimate liquidation, an unprivileged-principal-harms-another-unprivileged-principal scenario matching the rules' allowed analog category (shared cache primed by one caller, consumed by another).

### Likelihood Explanation
Likelihood is constrained by the fact that `vault-accrue` is generally monotonic (interest indexes only increase within reasonable bounds) and the cache is invalidated every new block via `stacks-block-time`, so the practical window is a single block and the divergence per block is typically small [6](#0-5) . However, on chains/rollups where multiple transactions can be sequenced within one block/timestamp (or where an attacker can force an early cheap transaction touching the same vault), the ordering dependency is real and requires no privileged access—only two unprivileged transactions landing in the same block, which mirrors the "ordering dependence between two users in one block" category explicitly permitted by the rules.

### Recommendation
Either (a) scope health/liquidation evaluations to always force a fresh `vault-accrue` per affected account/transaction rather than reusing a globally shared cache keyed only by `{timestamp, aid}`, or (b) key the cache additionally by a per-transaction nonce/account so that stale cross-account reuse cannot occur, or (c) bound the acceptable divergence between the cached index and a freshly computed one with an explicit tolerance check before using it in a capacity/health/liquidation decision.

### Proof of Concept
1. Block N begins. User A submits a transaction (e.g., a small `collateral-add` on the USDC vault) that is the first to touch `aid = USDC` in this block; `accrue-and-cache` computes and stores `{index, lindex}` at `stacks-block-time = T` [3](#0-2) .
2. Still within block N, victim User B submits a `collateral-add`/borrow transaction that also resolves the price of a zUSDC-denominated asset; `resolve-ztoken` calls `get-cached-indexes(aid)` which returns User A's cached `{index, lindex}` for timestamp `T` instead of re-deriving from B's own transaction context [4](#0-3) .
3. If A's priming transaction was crafted/timed to leave a slightly different index in place (e.g., by triggering accrual right at a moment that produces a marginally different value than what B would have computed independently), B's `ERR-UNHEALTHY` capacity check in `collateral-add` [7](#0-6)  evaluates against A's cached index rather than a value reflecting B's exact transaction, potentially failing a check that should have passed (or passing one that should have failed), demonstrating the cross-account consume-what-another-wrote dependency.
