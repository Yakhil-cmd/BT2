### Title
Webhook secret is selected by an attacker-controlled `repository.owner.login`/`organization.login` field, while handlers act on a different, unverified `repository.full_name`/`sha` field, allowing cross-organization forgery of commit statuses and other webhook-driven actions - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to verify the HMAC signature against using `repository_owner`, computed from the untrusted JSON body itself (`params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`). [1](#0-0) [2](#0-1)  Once the signature is validated against that organization's secret, the raw params are dispatched unchanged to event handlers, which act on a *different* field of the same payload - `repository.full_name` (for `Handler#stacks`) or a bare `sha` (for `StatusHandler`) - with no re-check that this field corresponds to the organization whose secret validated the request. [3](#0-2) [4](#0-3) 

### Finding Description
Shipit supports multiple GitHub Apps/organizations, each with its own `webhook_secret`, configured under `github.<org>.webhook_secret`. [5](#0-4)  `verify_webhook_signature` simply HMACs the raw request body with whichever secret matches the resolved organization: [6](#0-5) 

The binding the engine relies on is: *the organization whose secret authenticated the request* == *the repository/commit that the handler subsequently writes to*. This binding is never enforced. `repository_owner` is read straight out of the same body the attacker crafts, so an attacker who legitimately controls (or has been granted) **any** organization tracked by this Shipit instance - and therefore knows that organization's `webhook_secret` (e.g. their own installed GitHub App) - can:

1. Build an arbitrary JSON payload where `repository.owner.login` (or `organization.login`) is set to *their own* organization (so the correct, attacker-known secret is selected and the HMAC passes verification).
2. Populate the rest of the payload - notably `repository.full_name`, or in the case of the `status` event just `sha` - with data belonging to a **victim** stack/repository tracked by the very same Shipit instance under a different GitHub App/organization.
3. Sign the full body with their own valid secret and POST it to `/webhooks`.

`verify_signature` only checks that the HMAC matches the secret for the org named inside the payload - it never confirms that the events being enacted (`repository.full_name` in `Handler#stacks`, or `sha` in `StatusHandler`) actually belong to that same organization.

The clearest concrete impact is `StatusHandler`, which looks up commits **globally**, with zero repository/stack scoping:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [4](#0-3) 
`params.sha` and `params.state`/`context` are entirely attacker-controlled and unrelated to `repository_owner`. If the attacker knows (or brute-forces/observes) the SHA of a commit in a victim stack that belongs to a *different* organization on the same Shipit instance, they can inject a fabricated `success` status with the exact `context` value required by that victim stack's `ci.require` configuration. [7](#0-6)  This directly feeds `Commit#deployable?`, which trusts stored statuses:
```ruby
def deployable?
  !locked? && (stack.ignore_ci? || (success? && !blocked?))
end
``` [8](#0-7) 
and can also trigger `schedule_continuous_delivery`, which enqueues a `ContinuousDeliveryJob` if the commit becomes deployable and the stack has continuous deployment enabled: [9](#0-8) 

Other handlers (`PushHandler`, `CheckSuiteHandler`, `PullRequest*Handler`) similarly resolve their target via `repository.full_name`, a field that is never cross-checked against the org used for signature verification: [10](#0-9) [3](#0-2) 

### Impact Explanation
This satisfies the "authorization escalation into `Shipit.github_teams`" / "cross-repository writes" class: an attacker who is only trusted (has a valid webhook secret) for **their own** organization's repositories can forge webhook events that write state (commit statuses, sync jobs, check-run refresh triggers) for **another organization's** stacks tracked by the same Shipit instance. Concretely with `StatusHandler`, this can fake a passing CI status on an arbitrary victim commit, defeating the `ci.require` safety gate used to control whether a commit is `deployable?`, and can trigger an unintended continuous-deployment run of that commit. This is a cross-organization/cross-repository trust-boundary break that does not require the attacker to compromise the victim org's webhook secret, GitHub App, or any Shipit credentials — only a legitimate, unprivileged webhook-signing capability for an unrelated organization on the same multi-tenant Shipit deployment.

### Likelihood Explanation
Requires: (a) a multi-organization Shipit deployment (explicitly documented and supported: `docs/setup.md` "Using Multiple Github Applications"), and (b) the attacker holding a legitimate GitHub App/webhook_secret for at least one of the organizations configured on that instance (e.g., they operate their own org that is also tracked). Given that document explicitly recommends multi-org configuration for shared Shipit instances, and that the SHA of a target commit is often discoverable (it is displayed publicly in the Shipit UI, GitHub commit history, PR pages, etc.), this is a realistically reachable, moderate-likelihood scenario for anyone administering their own org's GitHub App on a shared Shipit deployment.

### Recommendation
Bind the signature-verification identity to the same field the handler will act on. At minimum:
- After signature verification, re-derive the target repository/stack from `repository.full_name` and require that its configured GitHub organization equals `repository_owner` used to select the `webhook_secret`; reject the webhook otherwise.
- In `StatusHandler`, scope the `Commit.where(sha: ...)` lookup to `stacks` (i.e., commits belonging to repositories under the verified organization), instead of a global, unscoped lookup, mirroring the scoping already used by `Handler#stacks`.
- Consider signing organization identity as part of the trusted context (e.g., verifying with all configured secrets and confirming exactly one org matches AND that its name equals `repository.owner.login`/`repository.full_name`'s owner) rather than trusting the payload field to select which secret to verify against.

### Proof of Concept
Given a Shipit instance configured with two organizations, `attacker-org` (attacker's own installed GitHub App, secret `S_attacker`, known to the attacker) and `victim-org` (tracked stack unrelated to the attacker), and a victim commit `deadbeef...` belonging to a `victim-org` stack requiring CI context `"ci/tests"`:

```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=<HMAC-SHA1(S_attacker, body)>

body = {
  "repository": { "owner": { "login": "attacker-org" } },
  "sha": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "state": "success",
  "context": "ci/tests",
  "created_at": "2026-09-02T00:00:00Z"
}
```

1. `WebhooksController#verify_signature` computes `repository_owner == "attacker-org"`, fetches `attacker-org`'s `webhook_secret` (`S_attacker`), and the HMAC matches because the attacker signed the body with their own known secret. [1](#0-0) 
2. `create` dispatches the parsed body to `StatusHandler.call(params)`. [11](#0-10) 
3. `StatusHandler#process` finds the victim's commit purely by `sha` (no org/repo scoping) and calls `create_status_from_github!`, injecting a forged `success` status for `ci/tests` on the victim's commit. [4](#0-3) 
4. `Commit#deployable?` and `schedule_continuous_delivery` now treat the victim commit as passing CI, potentially auto-deploying it if `continuous_deployment?` is enabled on that stack. [12](#0-11) 

I was unable to fully verify a specific instance where this leads to a fully "unauthorized deploy" (that also depends on `stack.continuous_deployment?` and safety checks not covered in this scan), so the strongest concretely confirmed impact is unauthenticated cross-organization tampering with commit CI status records, with a plausible escalation path to an unintended deploy trigger via `schedule_continuous_delivery`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
