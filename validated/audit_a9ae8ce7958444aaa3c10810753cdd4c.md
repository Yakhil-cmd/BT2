This confirms the schema only requires `labels[].name` to be a `String` with no format restriction — an attacker can name a label `ld_library_path` (or any other env-like key) via the webhook payload, and `LabelCapturingHandler#capture_labels` persists it verbatim [1](#0-0) [2](#0-1) . `PullRequest#labels` is a plain serialized array with no validation [3](#0-2) .

### Title
Attacker-controlled PR label name (e.g. `LD_LIBRARY_PATH`) is merged unfiltered into the `git` subprocess environment via `ReviewStack#env` → `StackCommands#fetch`/`#git_clone` → `Command#start` - (File: app/models/shipit/review_stack.rb, lib/shipit/stack_commands.rb, lib/shipit/command.rb)

### Summary
`ReviewStack#env` merges every pull request label name, uppercased, straight into the stack's environment hash with no key allowlist. This hash flows unfiltered through `StackCommands#env`/`#fetch`/`#git_clone` into `Command#start`, which merges it directly into the environment passed to `PTY.spawn`, so a PR label literally named `ld_library_path` becomes `LD_LIBRARY_PATH=true` in the `git` subprocess's environment.

### Finding Description
The broken binding: the set of environment variable **keys** reaching `PTY.spawn` for a `git` invocation should equal the set of keys defined by Shipit's own code/config (`Stack#env`, `Shipit.env`, `deploy_spec.machine_env`, whitelisted `deploy_variables`/`task_definitions`), **not** an attacker-chosen set derived from PR label text. That equality is violated here.

Path:
1. Any unprivileged GitHub user opens a PR against a repo with `review_stacks_enabled` and `provisioning_behavior: allow_all`, and adds a label whose name, uppercased, is `LD_LIBRARY_PATH` (or `GIT_ASKPASS`, `LD_PRELOAD`, etc.).
2. The `labeled`/`opened` webhook is processed by `LabelCapturingHandler`, whose params schema only requires `labels[].name` to be a `String` [1](#0-0) . `capture_labels` persists `pull_request.labels.map(&:name)` verbatim with no allowlist [2](#0-1) .
3. `ReviewStack#env` merges `pull_request.labels.each_with_object({}) { |n,h| h[n.upcase]='true' }` into the stack env with zero filtering: [4](#0-3) .
4. `StackCommands#env` merges this into the base env (`Shipit.env` + `GITHUB_TOKEN`/`GITHUB_DOMAIN`) [5](#0-4) , and `#fetch`/`#git_clone` pass this `env:` straight to `git(...)`, which only defaults (does not override) `kwargs[:env]` [6](#0-5) .
5. `Command#start` calls `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)`, where `unbundled_env` merges `@env.stringify_keys` directly on top of the process's base env with no key restriction [7](#0-6) , so `LD_LIBRARY_PATH=true` reaches the spawned `git` process (and any dynamic linker resolving shared libraries for it).

This differs from the deploy/rollback/task-trigger paths where user-supplied `env` params ARE filtered through `EnvironmentVariables#permit` against a per-stack/task whitelist (`deploy_variables`/`rollback_variables`/`task_definitions` variables) [8](#0-7)  — that guard exists only for explicit controller params, not for the label-derived keys injected automatically by `ReviewStack#env`. No allowlist, format validation, or reserved-name blocklist exists in `ReviewStack#env`, `PullRequest#labels`, or `LabelCapturingHandler`.

### Impact Explanation
An attacker who can merely open/label a PR on a repository configured with `provisioning_behavior: allow_all` (or `allow_with_label`/`prevent_with_label`, since labels are captured regardless once a review stack exists) can set arbitrary environment variable keys — including `LD_LIBRARY_PATH`, `LD_PRELOAD`, `GIT_ASKPASS`, `PATH`-adjacent variables — into the `git fetch`/`git clone` subprocess environment on the Shipit deploy host. Combined with control over the attacker's own fork/branch content (also reachable via this same PR), this enables loading of attacker-supplied shared objects or scripts during the `git` invocation, i.e., Remote Code Execution on the deploy host. This is repeatable against any repository with review stacks enabled, and since it happens at every `fetch`/`clone`/`checkout` for that stack, it is fully repeatable per-PR.

### Likelihood Explanation
Preconditions are minimal and attacker-only: the target repository must have `review_stacks_enabled` and some non-`prevent` provisioning behavior (a common configuration for review-app workflows), and the attacker needs only the ability to open a PR and add a label — actions any GitHub user with a fork can perform. No Shipit secrets, session, or maintainer privileges are required. This is a low-cost, highly repeatable attack path.

### Recommendation
Do not derive raw environment variable keys from user-controlled data. `ReviewStack#env` should either drop the label-to-env-var feature entirely, or run the derived hash through an explicit allowlist/prefix scheme (e.g. only permit keys prefixed `SHIPIT_LABEL_` or defined via `deploy_variables`), and reject/skip any label name that collides with security-sensitive variable names (`LD_*`, `GIT_*`, `PATH`, `BUNDLE_*`, etc.) before merging into the command environment used for `git`/`PTY.spawn`.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_test.rb (or lib/shipit/stack_commands_test.rb)
test "PR label names inject arbitrary env keys into git subprocess env (allow_all)" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["ld_library_path"]

  env = stack.env
  assert_equal "true", env["LD_LIBRARY_PATH"]

  commands = Shipit::StackCommands.new(stack)
  commands.stubs(:valid_git_repository?).returns(true)
  command = commands.fetch

  assert_equal "true", command.env["LD_LIBRARY_PATH"],
    "attacker-controlled PR label reached the git fetch subprocess env"
end
```
This demonstrates the equality `command.env.keys ⊆ Shipit-defined keys` is violated: `LD_LIBRARY_PATH`, derived purely from an attacker-chosen PR label name, is present in the exact env hash passed to the `git` invocation in `StackCommands#fetch`.
