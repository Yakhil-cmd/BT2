### Title
Webhook organization used for signature verification is not bound to the repository the event handlers actually mutate - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The external report describes a class of bug where an attacker-controlled, "typed" value is trusted and acted upon without being covered by the security check that is supposed to protect it. The equivalent binding in this engine is: **the GitHub organization that `verify_signature` authenticates the request against** must equal **the repository/organization whose data the webhook handlers actually write to Shipit's database**. `WebhooksController` breaks this equality: the organization used to pick a signing secret is read from the same untrusted JSON body that the handlers later use to identify the affected repository, and no code ties the two together.

### Finding Description
`WebhooksController#verify_signature` derives the organization used for verification purely from the unauthenticated request body: [1](#0-0) [2](#0-1) 

```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

That value is used to fetch the corresponding `GithubApp` config and check the signature: [3](#0-2) 

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  algorithm, signature = signature.split("=", 2)
  return false unless algorithm == 'sha1'
  SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
end
```

Critically, `return true unless webhook_secret` means that for **any organization entry configured without a `webhook_secret`** (a state the engine's own sample config explicitly shows as valid, `webhook_secret: # nil`), signature verification is a no-op regardless of the actual `X-Hub-Signature` header: [4](#0-3) 

Once `verify_signature` passes (because the org named in `repository.owner.login`/`organization.login` happens to have no secret configured), the full, attacker-controlled JSON body is handed to the registered handlers unmodified: [5](#0-4) 

Nothing re-derives the "authenticated organization" and compares it against the repository/stack identifiers (`repository.full_name`, `repository.owner.login` used elsewhere in the payload, `organization.login`, etc.) that the handlers use to locate and mutate `Stack`/`Commit`/`Membership` records. The field used to *select the trust boundary* (`repository_owner`) and the fields used to *perform the write* are both taken from the same unverified payload, so an attacker can set them independently.

### Impact Explanation
An unprivileged, unauthenticated attacker who is aware of (or can guess/enumerate) any organization entry in Shipit's multi-tenant `github:` config that has no `webhook_secret` set can send a POST to `/webhooks` with:
- `repository.owner.login` / `organization.login` set to that unsecured organization (to make `verify_webhook_signature` return `true` unconditionally), and
- the rest of the payload (`repository.full_name`, commit SHA, state, etc.) forged to target a completely different, legitimately protected stack/repository tracked by Shipit.

This lets the attacker forge `push`, `status`, `check_suite`, or `membership` events for repositories they have no relationship to, e.g.:
- Fabricate passing CI/`commit_status` events, making otherwise-undeployed commits appear deployable and triggering continuous delivery — an unauthorized deploy.
- Trigger `GithubSyncJob` for arbitrary tracked repositories.
- Forge `membership` events to add/remove team memberships, potentially escalating into `Shipit.github_teams` authorization.

This satisfies the Critical/High impact bar ("unauthorized deploy" / "escalation into `Shipit.github_teams` authorization") without requiring any Shipit session, API token, or webhook secret from the attacker.

### Likelihood Explanation
Exploitability depends entirely on operator configuration: it requires at least one organization entry in the `github:` config with a blank `webhook_secret` while other organizations/stacks are actively tracked and protected. The engine ships a documented sample (`config/secrets.development.shopify.yml`) showing `webhook_secret: # nil` as an accepted configuration shape, and nothing in the engine enforces that every configured organization must have a secret, so this is a realistic operational state (e.g., an org added for review-app support before secrets were provisioned) rather than a purely theoretical one. I could not fully trace every downstream handler (e.g., `push_handler.rb`, `status` handler) to confirm each one resolves its target `Stack`/`Repository` from a payload field independent of `repository_owner`; this should be verified directly, as it determines exactly how far the confusion can be pushed for each event type.

### Recommendation
Bind the verified organization to the entity being mutated: after `verify_webhook_signature` succeeds, re-validate that the repository/organization actually referenced by the payload for record lookups matches the organization whose secret validated the request. Additionally, treat a missing `webhook_secret` as "reject the webhook" rather than "skip verification," or require webhook secrets to be mandatory for all configured organizations.

### Proof of Concept
1. Configure two GitHub orgs in Shipit: `unsecured-org` (no `webhook_secret`) and `victim-org` (tracked stack with a secret).
2. POST to `/webhooks` with header `X-Github-Event: push`, no valid `X-Hub-Signature`, and body:
```json
{
  "repository": { "owner": { "login": "unsecured-org" }, "full_name": "victim-org/protected-repo" },
  "after": "<attacker-chosen sha>",
  "ref": "refs/heads/main"
}
```
3. `repository_owner` resolves to `unsecured-org`; `Shipit.github(organization: "unsecured-org").verify_webhook_signature` returns `true` unconditionally.
4. The `push` handler processes the request using `repository.full_name` = `victim-org/protected-repo`, acting on the victim's stack despite the request never being authenticated for `victim-org`.
