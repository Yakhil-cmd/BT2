### Title
Cross-Organization Webhook Forgery via Owner/Full-Name Binding Mismatch Can Trigger Unauthorized Deploys - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/`webhook_secret` used to validate an incoming webhook's HMAC signature based on `repository.owner.login` (or `organization.login`) — a value read directly out of the *untrusted, unverified* JSON body. Every webhook handler (`PushHandler`, `StatusHandler`, etc.), however, resolves which `Stack`/`Commit` to act on using a **different** field of that same payload: `repository.full_name`. Because the signature check only proves "this payload was signed with the secret belonging to the organization named in `repository.owner.login`," and never checks that `repository.full_name` actually belongs to that same organization, an attacker who legitimately controls the webhook secret for one configured GitHub organization can forge a payload that authenticates as that organization while acting on any other organization's repository/stack.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`repository_owner` is used only to pick which GitHub App config (and thus which `webhook_secret`) is used for `verify_webhook_signature`. Signature validity therefore proves only that the request body was HMAC-signed with `Shipit.github(organization: repository_owner).webhook_secret` — i.e. it authenticates the *organization named in that one field*.

Every handler, though, resolves the actual object of the action from a completely different, unchecked field:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [2](#0-1) 

`PushHandler` uses this to trigger a GitHub sync for the matched stack: [3](#0-2) 

`StatusHandler` uses the (org-independent) `sha` field to look up commits by any repository and injects a fabricated CI status: [4](#0-3) 

`Repository.from_github_repo_name` splits `full_name` on `/` and does a plain DB lookup with no relation back to `repository_owner`: [5](#0-4) 

This is the same class of bug as the referenced report: a value that is authenticated/verified (`msg.value` vs `sellOrder.price` in the analog; here `repository.owner.login`, checked against a specific org's `webhook_secret`) is different from the value actually acted upon (`sellOrder.maker` transfer amount in the analog; here `repository.full_name`, used to locate the `Stack`/`Commit` to mutate). The binding `organization authenticated == repository written` is never enforced.

### Impact Explanation
An attacker who is a legitimate admin/webhook operator for **any one** GitHub organization configured in Shipit's multi-org `github:` config (a routine, low-privilege position relative to Shipit itself — they need no Shipit account, no `ApiClient` token, and no access to the *target* organization) can:
1. Craft a `push` event with `repository.owner.login` = their own org (so signature check passes using their own known secret) and `repository.full_name` = `victim-org/victim-repo`, forcing `PushHandler` to call `sync_github` / enqueue `GithubSyncJob` for a stack they do not control.
2. Craft a `status` event the same way, injecting arbitrary CI status ("success"/"failure") for a commit belonging to a foreign stack via `Commit#create_status_from_github!`. If that stack has continuous deployment enabled and is otherwise waiting on CI status, this can push it toward an automatic, unauthorized deploy — matching the "unauthorized deploy" high-impact category. It can equally be used to falsely mark a legitimate deploy as blocked (spoofed failing status) as a denial-of-legitimate-deploy vector, or to desynchronize the victim stack's known commit list.

This is a cross-organization write achieved purely by forging one JSON field while satisfying signature verification with a *different* organization's secret — a genuine authentication-boundary break, not merely a data-quality bug.

### Likelihood Explanation
Requires the attacker to control (or know) the `webhook_secret` of at least one GitHub organization that the Shipit instance is configured to serve (a realistic scenario for multi-tenant Shipit deployments serving many orgs, as explicitly supported by `config/secrets.development.example.yml`'s multi-org schema). No Shipit credentials, sessions, or GitHub write access to the *victim* repository are needed — only the ability to POST an HTTP request to `/webhooks` with a correctly HMAC-signed body using their own org's secret.

### Recommendation
After signature verification, additionally verify that `repository.owner.login` (or `organization.login`) matches the owner segment of `repository.full_name` before dispatching to any handler; reject the webhook (422) on mismatch. Handlers should also independently confirm the resolved `Repository`'s `owner` equals the authenticated `repository_owner` rather than trusting `full_name` alone.

### Proof of Concept
1. Configure Shipit with two orgs, `attacker-org` (secret known to the attacker) and `victim-org` (any Shipit-tracked stack e.g. `victim-org/victim-repo`).
2. Attacker builds a `push` payload:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef...",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC_SHA1(attacker-org_webhook_secret, body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")`, verifies successfully against `attacker-org`'s secret.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")`, which is unrelated to `attacker-org`, and enqueues `GithubSyncJob`/status update for the victim's stack — demonstrating the authenticated-organization vs. written-repository binding is broken. # frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
