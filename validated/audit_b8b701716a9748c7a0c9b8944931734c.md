### Title
Webhook signature verification authenticates the `repository.owner.login` organization while the event handlers act on the unvalidated `repository.full_name` field, allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
This is the analog of the "EVM channel task terminates early" bug class translated to a trust-binding break rather than an availability break: the report's root cause is that a security-relevant equality between two related but independently-consumed fields is never enforced, so error paths (or in this case, forgeable payload fields) let one component diverge from the invariant the other depends on. In `shipit-engine` the equivalent binding is: the **organization used to authenticate** the webhook signature must equal **the organization that owns the repository the handler writes to**. This binding is never checked.

### Finding Description
`Shipit::WebhooksController#verify_signature` selects which GitHub App/organization config (and therefore which `webhook_secret`) to validate the incoming signature against using: [1](#0-0) [2](#0-1) 

```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

This picks `repository.owner.login` (or falls back to `organization.login`) purely from the raw JSON body, and calls `Shipit.github(organization: repository_owner)` to fetch the matching webhook secret for HMAC verification.

Once signature verification passes, `create` dispatches the same raw `params` to the registered handlers: [3](#0-2) 

Every handler resolves the target `Stack`/`Repository` via a **different** field from the same payload: [4](#0-3) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`repository.owner.login` (used for authentication) and `repository.full_name` (used to select which repository/stack is written to) are two independent leaf values inside the same untrusted, attacker-suppliable `repository` object. Nothing enforces that `full_name` starts with `owner.login`. Since Shipit supports multiple configured GitHub organizations/apps, each with its own `webhook_secret`, `Shipit.github(organization: ...)` looks up a secret keyed purely by the `repository_owner` string extracted from the same payload the attacker controls.

Consequently, an attacker who legitimately knows (or controls) the `webhook_secret` for **any one** organization configured in the Shipit instance (e.g., an org they administer and self-serve) can craft a payload where `repository.owner.login` is set to their own organization (to select their own known secret and pass `verify_signature`), while `repository.full_name` is set to an arbitrary **victim** organization/repository. They sign the raw body with their own known secret, and `verify_signature` succeeds because it only checks that the signature matches the secret for the org named in `repository.owner.login` — it never checks that this org matches the repository the handler will actually act on.

### Impact Explanation
This breaks the exact binding class the rules call out: "an organization that authenticated versus the repository that is written." A successfully forged webhook can trigger `GithubSyncJob` (via the `push` handler) or other handlers for the victim stack, e.g., causing the engine to record fabricated commits/statuses or otherwise drive stack state for a repository the attacker does not own — an unauthorized write against another organization's stack, satisfying the Critical/High bar of "cross-repository writes" without requiring a Shipit session, API token, or the victim's own webhook secret.

### Likelihood Explanation
Exploitability depends on the attacker possessing (or being able to obtain) a valid `webhook_secret` for at least one organization configured in the Shipit instance — a scenario the deployment model can allow when an instance manages multiple orgs/installations. Given that secret, forging the cross-repository payload is trivial (a normal HMAC-SHA1 computation over an attacker-crafted JSON body), no other credential (session, API client token, GitHub token) is required, and the `WebhooksController` is a public unauthenticated endpoint by design.

### Recommendation
In `WebhooksController#verify_signature`, validate that the organization used to select the webhook secret is the same organization implied by `repository.full_name` (and any handler-relevant repository fields) before dispatching to handlers — e.g., derive `repository_owner` strictly from `repository.full_name.split('/').first` (or validate equality between `repository.owner.login` and the owner segment of `full_name`) rather than trusting a separate, independently-controllable JSON key.

### Proof of Concept
1. Attacker has (or self-registers) organization `attacker-org` in the Shipit multi-org config with a known `webhook_secret`.
2. Attacker crafts a `push` event body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "after": "<attacker-chosen-sha>"
}
```
3. Attacker computes `sha1=HMAC(attacker-org secret, body)` and sends it as `X-Hub-Signature`, with `X-Github-Event: push`.
4. `verify_signature` computes `Shipit.github(organization: "attacker-org")` and successfully verifies the signature [5](#0-4) .
5. `create` dispatches to the push handler, which resolves `Repository.from_github_repo_name("victim-org/victim-repo")` [4](#0-3)  and enqueues `GithubSyncJob` for the victim's stack with the attacker-chosen `expected_head_sha`, without any credential belonging to `victim-org`.
