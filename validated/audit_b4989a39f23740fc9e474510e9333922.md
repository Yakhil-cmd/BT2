### Title
Webhook signature verification keys off `repository.owner.login`, while the repository actually acted upon is taken from the unverified `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb], [File: lib/shipit/github_app.rb])

### Summary
`_validateRange` in the Sherlock report checks a `baseKey` only for cosmetic/error-message purposes but never enforces the value against the pre-set boundary it claims to validate. The same "checked-for-one-purpose, not-for-the-purpose-that-matters" pattern exists in Shipit's webhook path: the field used to select which GitHub App/`webhook_secret` to verify the signature against (`repository.owner.login`) is never bound to the field that actually determines which repository/stack the event mutates (`repository.full_name`). Both fields come from the same unauthenticated, attacker-controlled JSON body.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App config to validate the HMAC signature against using `repository_owner`, which is read straight out of the untrusted JSON payload: [1](#0-0) [2](#0-1) 

That app's `webhook_secret` is then used in `GitHubApp#verify_webhook_signature`, which — crucially — treats a blank/`nil` `webhook_secret` as "verification passes": [3](#0-2) 

Every documented multi-organization example ships with `webhook_secret: # nil` for each org (this is the shown default, not a rare misconfiguration): [4](#0-3) [5](#0-4) 

Meanwhile, once the request passes `verify_signature`, the event handlers determine *which repository/stack to mutate* using a completely different field of the same JSON body — `repository.full_name` — via `Handler#repository_name`: [6](#0-5) 

There is no code anywhere that cross-checks `repository.owner.login` (used to pick the signing key) against `repository.full_name`'s owner segment (used to pick the actually-affected `Stack`). This is exactly the M-36 pattern: a value is consulted for one narrow purpose (key selection / error text) while the value that drives the real state change is a sibling field in the same untrusted structure, never covered by the check.

### Impact Explanation
In any Shipit installation configured with the documented multi-org schema (`Shipit.github_organizations`, `Shipit.github_app_config`) where at least one configured organization is left with its default blank `webhook_secret` (the example/default configuration shown in every setup doc and fixture), an unprivileged external attacker can:
1. Craft a webhook POST to `/webhooks` with `X-Github-Event` set to `push`/`status`/`check_suite`/`pull_request`.
2. Set `repository.owner.login` to the organization that has no `webhook_secret` configured — `verify_signature` will select that org's `GitHubApp`, and `verify_webhook_signature` returns `true` unconditionally, regardless of the (garbage or absent) `X-Hub-Signature` header.
3. Set `repository.full_name` to `<secured-org>/<tracked-repo>` — the actual org that does have a real Shipit stack and a properly configured `webhook_secret`.

Because `Handler#repository_name` reads `full_name`, not `repository.owner.login`, the forged event is processed against the secured organization's real `Stack`, causing e.g. `GithubSyncJob` enqueuing, spurious `Status` records, or `RefreshCheckRunsJob` enqueuing — all without ever presenting a signature the secured org's real webhook secret would validate. This is an authentication-bypass on the webhook trust boundary: the attacker authenticates as "having a valid signature for org A" but writes state belonging to "org B."

### Likelihood Explanation
Likelihood depends entirely on deployment configuration: it requires the multi-org GitHub App schema with at least one org left at the documented default of no `webhook_secret`. This is a realistic and encouraged default in the shipped docs/examples, but I could not verify from the indexed code whether any deployment-time validation forces a non-blank `webhook_secret` for every configured organization — this remains unconfirmed. If all configured orgs have non-blank secrets, this specific path is not exploitable, though the field-mismatch itself (owner used for key-selection vs. full_name used for the state change) remains present as a latent trust-boundary defect regardless.

### Recommendation
- Do not allow signature verification to silently pass when `webhook_secret` is blank in a multi-org configuration; require and validate a secret per organization, or refuse to process events for orgs with no secret configured.
- After signature verification succeeds, assert that the organization/owner used to select the verifying key equals the owner segment of `repository.full_name` (and `organization.login` for org-scoped events) before dispatching to any handler, so the value that authorized the request is provably the same value that is acted upon.

### Proof of Concept
1. Deploy Shipit with the documented multi-org config, leaving `OrgA.webhook_secret` blank and configuring `OrgB.webhook_secret` with a real secret; track a repo `OrgB/app` in Shipit.
2. POST to `/webhooks` with header `X-Github-Event: push` and no valid `X-Hub-Signature` (or any garbage value), and JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/app" }
}
```
3. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "OrgA")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` per [7](#0-6) , regardless of the header supplied.
4. `PushHandler#process` (via `Handler#repository_name`, [6](#0-5) ) resolves the repository from `full_name` = `OrgB/app` and enqueues `GithubSyncJob` for `OrgB`'s real stack — despite the request never being validated against `OrgB`'s actual webhook secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
