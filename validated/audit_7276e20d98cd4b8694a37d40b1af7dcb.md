### Title
Uncaught `throw Error` in AA Trigger Execution Path (`handleTrigger`/`replace`) Causes Node Process Crash - (File: aa_composer.js)

### Summary
Analogous to CVE-2023-46673, where a malformed script processed during Elasticsearch's Simulate Pipeline caused an uncaught exception that crashed the node, `ocore`'s AA (Autonomous Agent) trigger-execution engine in `aa_composer.js` contains multiple `throw Error(...)` statements reachable from processing an AA's `messages` template against attacker-controlled `trigger` data. These throws occur inside asynchronous callback chains (`handleTrigger`'s internal `replace` function and `validateAndSaveUnit`), so they are not caught by any surrounding `try/catch` and are not routed through the normal `cb(err)`/bounce error-handling path. Because `handleAATriggers` processes triggers synchronously in the main event loop as part of stabilizing the DAG, an uncaught exception here becomes a process-level uncaught exception, crashing the full/hub node during trigger processing of a stabilized unit.

### Finding Description
`aa_composer.js`'s `handleTrigger` builds the AA's response by walking its `messages` template with the function `replace(obj, name, path, locals, xpath, cb)`. This function recursively evaluates formulas and structural values found in the AA template combined with trigger data: [1](#0-0) 

If a resulting `value` doesn't match any of the expected recognized shapes (string, cases, if/init object, array, non-empty object), the function falls through to an unconditional `throw`: [2](#0-1) 

Similarly, `validateAndSaveUnit`, called at the end of `handleTrigger` to persist the AA's response unit, wraps `validation.validate` callbacks with `throw Error(...)` for supposedly "impossible" states such as `ifJointError`, `ifTransientError`, `ifNeedHashTree`, `ifNeedParentUnits`, and `ifOkUnsigned`: [3](#0-2) 

These are executed deep inside `async`/callback-based control flow triggered from `handlePrimaryAATrigger`, itself invoked from `handleAATriggers`, which runs as part of normal main-chain stabilization/writer logic (not inside a `try/catch` that would gracefully degrade): [4](#0-3) [5](#0-4) 

Because the AA `messages` template's `if`/`init`/`state` values are formula strings evaluated by `formula/evaluation.js`'s `evaluate` function, and that evaluator handles a wide variety of return types (`Decimal`, `wrappedObject`, string, boolean, and explicit fatal-error paths via `setFatalError`), there is a real possibility that certain formula constructs, edge-case return values, or unusual AA definition shapes that pass static `aa_validation.js` checks at deployment time nonetheless produce a template value at execution time that `replace()` does not recognize — triggering the unconditional `throw` at line 872, or one of the "impossible" `throw Error` guards in `validateAndSaveUnit`. This mirrors the Elasticsearch bug class (CWE-755): a difference between what is validated up front (script/pipeline syntax, or here, static AA-definition validation) and what is actually encountered at execution time (simulate pipeline invocation, or here, real trigger execution against attacker-supplied `trigger.data`/`params`) results in an unhandled exceptional condition that crashes the service process rather than being handled as a recoverable/bounce error.

### Impact Explanation
An uncaught exception thrown inside the AA trigger-processing pipeline propagates up through the `async`/callback chain until it becomes an unhandled exception in the Node.js process. Since `handleAATriggers` runs on every full/hub node as part of normal stabilization of the DAG (processing all AAs that received a stabilized trigger), this halts main-chain/database processing on that node, preventing it from continuing to validate/write new units and confirm the network — satisfying the "network unable to confirm new units" / node-crash criterion. Any address, once controlling a deployed AA (which any user can do without special privilege) or any user who can send a payment to an existing AA with crafted `trigger.data`/`params`, can attempt to trigger the mismatched-type/edge condition, causing every full node that processes that stabilized trigger to crash identically (since AA execution is deterministic and re-executed by every node) — this is a Medium/High severity, unprivileged, network-wide crash vector, not merely a local validation failure.

### Likelihood Explanation
Exploitability is not proven with a concrete formula/trigger payload here — the exact combination of AA definition constructs and trigger inputs needed to reach the unrecognized-value branch in `replace()` (or one of the "impossible" branches in `validateAndSaveUnit`) is not confirmed by direct testing in this analysis; multiple layers of static validation in `aa_validation.js` (`validateAADefinition`, `validateFormula`) are designed to prevent most malformed templates from being deployed. However, the code comment "// if it would crash, let it crash now, not when we execute the trigger for real" found elsewhere in the codebase (`network.js`, around dry-run trigger handling) is itself an explicit acknowledgment by the developers that AA trigger execution can crash the process on certain inputs, which corroborates that this is a recognized, real risk class rather than a purely theoretical one. Because deployment of an AA and sending it a trigger require no special privilege, and every node re-executes AAs deterministically and identically, likelihood should be assessed as at least Medium.

### Recommendation
- Wrap the entire `evaluate`/`replace` template-processing pipeline in `handleTrigger`, and the `validateAndSaveUnit` callback handlers, with defensive `try/catch` that converts any unexpected condition into a bounce (`bounce(err)`) rather than an unconditional `throw`, mirroring how the rest of AA execution already treats formula errors as recoverable (`err.formattedError`).
- Audit all `throw Error(...)` statements inside `aa_composer.js` that are reachable from processing attacker-controlled trigger data or state to determine whether they represent conditions genuinely impossible after validation, or reachable edge cases; convert reachable ones into `bounce()` calls.
- Add fuzz/property-based testing feeding a wide variety of validated-but-edge-case AA definitions and trigger payloads into `handleTrigger` to find inputs that reach these `throw` statements, similar to how Elasticsearch added defensive handling for malformed ingest pipeline scripts in the Simulate Pipeline API.
- Consider isolating AA trigger execution in a recoverable execution context (e.g., a `process.on('uncaughtException')`-guarded microtask or worker) so that if such a condition does occur, the node can log the specific AA/trigger and safely skip/bounce it rather than crashing the entire node, restoring network-wide liveness.

### Proof of Concept
A concrete reproduction payload (a specific AA definition plus trigger `data`/`params` combination that survives `aa_validation.validateAADefinition` but produces an unrecognized template value in `replace()`, or drives `validation.validate`'s callback into one of the "impossible" `ifJointError`/`ifTransientError`/`ifNeedHashTree` branches during `validateAndSaveUnit`) was not constructed or executed in this analysis. Confirming exploitability would require crafting and testing such an AA/trigger pair against a running `ocore` node to observe the process crash directly.
