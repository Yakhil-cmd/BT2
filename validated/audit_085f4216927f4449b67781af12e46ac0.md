### Title
Webhook signature verification is keyed on `repository.owner.login` while event routing is keyed on `repository.full_name`, allowing cross-organization webhook forgery when any configured GitHub App has no `webhook_secret` - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to validate a webhook against using `repository_owner`, a value read straight out of the unauthenticated JSON body (`repository.owner.login` or `organization.login`). Every webhook handler, however, resolves the target `Repository`/`Stack` using a *different* field from the same body: `repository.full_name`. Because `GithubApp#verify_webhook_signature` short-circuits to `true` whenever that organization's `webhook_secret` is blank (a state explicitly shown as the default in this repo's own sample secrets files), any org configured without a webhook secret turns the entire `/webhooks` endpoint into an open, unauthenticated relay that can target **any** repository/stack on the whole Shipit instance by simply setting `repository.full_name` to a different org's repo.

### Finding Description
The binding that should hold is:
`organization that authenticated the webhook (repository.owner.login used to pick the app/secret) == repository that is written/acted upon (repository.full_name used to route the event to a Stack)`

In `verify_signature`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`verify_webhook_signature` bypasses HMAC checking entirely when the app has no configured secret:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [2](#0-1) 

Meanwhile, every `Handler` (e.g. `PushHandler`) resolves the stacks to act on using a *different, independent* field of the same unauthenticated JSON body:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

```ruby
class PushHandler < Handler
  def process
    stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
  end
end
``` [4](#0-3) 

Multiple independent GitHub App configs (one per org) are an explicitly supported and documented feature, each with its own, separately-set `webhook_secret`: [5](#0-4) [6](#0-5) 

and the setup docs describe the secret as merely "optional": [7](#0-6) 

Because `repository_owner` (used to pick the app/secret) and `repository.full_name` (used to pick the stack that is actually mutated) are two unrelated, independently attacker-controlled JSON fields, an attacker who can get any single configured org's webhook secret to be blank (the shown default) can send an arbitrary, unsigned/self-crafted payload where `repository.owner.login` names that no-secret org (so `verify_signature` trivially passes) while `repository.full_name` names a completely different org's repository, whose `Stack`/`Repository` records then get manipulated by the handler layer.

### Impact Explanation
This lets an unauthenticated network attacker forge GitHub events against **any repository/stack configured on the Shipit instance**, not just the one belonging to the org with the missing secret:
- `push` events force `GithubSyncJob`/`stack.sync_github` to run for an arbitrary target stack with an attacker-chosen `expected_head_sha`.
- `status` events fabricate CI statuses on arbitrary commits (`StatusHandler`), which Shipit's merge queue and deploy gating logic (`ci.require`/`hidden_statuses`/`soft_failing_statuses` in `DeploySpec`) rely on [8](#0-7) , potentially unblocking merges/deploys that should have been gated on real CI.
- `membership` events create/attach `Team`/`Membership` records on the fly (per `test/controllers/webhooks_controller_test.rb`'s `:membership` tests), which feed directly into `User#authorized?`'s check against `Shipit.github_teams` [9](#0-8) , so team-membership state that gates access to the whole app can be manipulated remotely.
- `pull_request` events drive review-stack creation/archival/merge flows across arbitrary repositories via `ReviewStackAdapter`.

This satisfies the "High" bar in the rules (escalation into `Shipit.github_teams` authorization, and forged task-triggering webhooks affecting cross-repository state) without requiring a Shipit session, API token, or the target org's own secret — only requires that some org on the same Shipit instance is configured with a blank `webhook_secret`, a state the project's own sample configs default to.

### Likelihood Explanation
Medium-High. It requires no credentials of any kind against the target org; it only requires that at least one org configured on the multi-tenant Shipit instance has `webhook_secret` left unset — a state explicitly shown as the default/example across this codebase's own secrets samples (`webhook_secret: # nil`) and described in `docs/setup.md` as merely "optional." Given Shipit is designed to host many organizations on one instance (as evidenced by `secrets_double_github_app.yml`), it is plausible that not every onboarded org sets a secret, and the vulnerability is exploitable without waiting for/needing a real GitHub event.

### Recommendation
Do not let a per-organization "no secret configured" bypass apply globally. Specifically:
1. Cross-check that the `repository.full_name`'s owner matches the same `repository_owner`/org that was used to select the webhook app/secret before dispatching to any handler; reject the event if they differ.
2. Do not silently `return true` from `verify_webhook_signature` when `webhook_secret` is blank; instead require every configured GitHub App to have a non-blank webhook secret (fail closed / raise a configuration error at boot), or restrict a no-secret app to only process events for its own declared organization/repositories.
3. Make `Handler#repository_name`/`stacks` resolution organization-scoped, deriving the allowed organization from the same webhook verification step, rather than trusting an independent, unauthenticated field from the same payload.

### Proof of Concept
Preconditions: Shipit instance hosts ≥2 orgs, e.g. `OrgNoSecret` (configured with `webhook_secret: nil`, as shown by this repo's own sample configs) and `VictimOrg/victim-repo` (a real, tracked stack).

```
POST /webhooks HTTP/1.1
X-Github-Event: push
Content-Type: application/json

{
  "ref": "refs/heads/master",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "OrgNoSecret" },
    "full_name": "VictimOrg/victim-repo"
  }
}
```
- `verify_signature` computes `repository_owner = "OrgNoSecret"` [10](#0-9) , loads `OrgNoSecret`'s `GithubApp`, and `verify_webhook_signature` returns `true` unconditionally because `webhook_secret` is blank [11](#0-10) , with no `X-Hub-Signature` header needed at all.
- `PushHandler#process` then resolves `stacks` via `payload.dig('repository', 'full_name')` = `"VictimOrg/victim-repo"` [12](#0-11)  and enqueues `sync_github` against `VictimOrg`'s real stack, despite the request never being authenticated for `VictimOrg`.

Note: I could not fully trace the deploy-gating/merge-queue consumption of forged `status` events or the exact `Team`/`github_teams` mapping mechanics within the remaining exploration budget; those secondary escalation paths (CI-status spoofing affecting merges, membership-driven `Shipit.github_teams` authorization) are inferred from the handler and model code cited above but were not traced end-to-end into the merge-queue scheduler.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
