### Title
Webhook signature verification keys off `repository.owner.login`/`organization.login` while stack/commit writes key off the independent `repository.full_name` field, allowing cross-organization forgery of push/status/check-suite events - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/`webhook_secret` used to validate `X-Hub-Signature` based on `repository_owner`, computed from `params.dig('repository', 'owner', 'login')` (or `organization.login`) in the untrusted JSON body itself. `Handlers::Handler#stacks`/`#repository_name`, used by `PushHandler`, `StatusHandler`, and `CheckSuiteHandler` to decide which `Stack`/`Commit` records to mutate, instead reads `payload.dig('repository', 'full_name')`. These are two independently attacker-controlled fields inside the same signed JSON body, and nothing cross-checks that `full_name`'s owner segment matches `owner.login`.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` does: [1](#0-0) [2](#0-1) 

It fetches `Shipit.github(organization: repository_owner)` and verifies the HMAC using that organization's `webhook_secret`. `repository_owner` is taken directly from the JSON payload (`repository.owner.login`, falling back to `organization.login`).

Once verified, `Handler#stacks` picks the target repository/stacks using a *different* field from the same payload: [3](#0-2) 

`Repository.from_github_repo_name` splits this `full_name` on `/` to find `owner`/`name` and locate the `Repository`/`Stack`: [4](#0-3) 

`PushHandler`, `StatusHandler`, and `CheckSuiteHandler` all act on the stacks/commits resolved this way: [5](#0-4) [6](#0-5) [7](#0-6) 

Because `repository.owner.login` (used to pick the verifying secret) and `repository.full_name` (used to pick which repository's stacks/commits are written to) are separate JSON keys under attacker control before signature verification, an attacker who legitimately controls a GitHub organization/App instance configured in Shipit (org "A", with its own `webhook_secret`) can send a correctly-HMAC-signed webhook where `repository.owner.login` = `"A"` (so it passes `verify_signature`) but `repository.full_name` = `"B/some-target-repo"` — a stack belonging to an unrelated organization "B" tracked by the same Shipit instance. This breaks the intended binding: `organization authenticated == organization whose repository state is written`.

This mirrors the reported bug class: an initializer/binding accepts a value about *who is calling* while the effect is applied to a *different, unchecked target parameter* supplied in the same call.

### Impact Explanation
With a forged `repository.full_name`, the attacker can:
- Force `PushHandler` to invoke `stack.sync_github(expected_head_sha:)` on stacks belonging to organization B, using a forged `after` SHA under attacker control, based on org A's legitimately signed webhook.
- Forge `StatusHandler`/`check_suite` payloads to write fake commit statuses / trigger `RefreshCheckRunsJob` against commits under org B's stacks (`Commit.create_status_from_github!`, `schedule_refresh_check_runs!`), which can be used to make org B's CI/status checks appear green, unblocking deploys/merges for org B stacks that the attacker does not control.

This is a cross-organization/cross-repository write achieved purely by controlling the payload of a webhook that is genuinely signed for a different, attacker-controlled organization — matching the "cross-repository writes" / "unauthorized deploy" Critical impact bucket, since fabricated passing statuses can enable an unauthorized deploy on a stack the attacker has no legitimate access to.

### Likelihood Explanation
Exploitability requires the attacker to control (or be an authorized member/webhook sender of) at least one GitHub organization/App that is configured in this Shipit instance's `config/secrets.yml` — a realistic scenario in the documented "Using Multiple GitHub Applications" multi-tenant setup, where a single Shipit deployment serves several unrelated organizations. Any such tenant can trivially craft an HTTP POST to `/hooks` (no session, no `ApiClient` token needed) with a legitimately-signed body and an inconsistent `repository.full_name`, since nothing in `WebhooksController` or `Handler` cross-validates the two fields.

### Recommendation
- In `Handler#repository_name`/`#stacks`, derive the target repository from `payload.dig('repository', 'owner', 'login')` + `payload.dig('repository', 'name')` — i.e., the same field used for signature verification — instead of trusting the independent `full_name` string.
- Alternatively, in `WebhooksController#verify_signature`, after resolving `repository_owner`, assert that `payload.dig('repository', 'full_name')` actually starts with `"#{repository_owner}/"` and reject (422) otherwise, before dispatching to handlers.

### Proof of Concept
1. Deploy Shipit with two configured organizations in `config/secrets.yml`: `orgA` (attacker-controlled, with its own `webhook_secret`) and `orgB` (victim, with a tracked stack `orgB/victim-repo`).
2. Attacker computes `sha1=HMAC(orgA.webhook_secret, body)` for a payload:
   ```json
   {
     "sha": "<attacker-chosen-sha>",
     "state": "success",
     "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" }
   }
   ```
3. POST to `/hooks` with header `X-Github-Event: status` and `X-Hub-Signature: sha1=<computed>`.
4. `WebhooksController#verify_signature` resolves `repository_owner == "orgA"`, verifies against `orgA`'s secret, and passes.
5. `StatusHandler#process` looks up `Commit.where(sha: params.sha)` scoped by whichever commits share that SHA across the instance (or via `stacks`/`Repository.from_github_repo_name("orgB/victim-repo")` for `PushHandler`/`CheckSuiteHandler`), and writes a fabricated status/check result against organization B's stack — despite the attacker never having proven control of `orgB`.
