## Analog Found: ERC20 Asset Transactor trusts an arbitrary contract's boolean return value instead of verifying the actual balance delta

The reported bug class (recording the *intended* transfer amount instead of the *actually received* amount for a token with non-standard transfer semantics) has a demonstrable analog in `ERC20Transactor`, the XCM `TransactAsset` implementation used to let any local ERC20 contract (deployed via `pallet-revive`) act as an XCM-transactable asset on Asset Hub.

### Title
ERC20 XCM Transactor credits/moves the requested amount based solely on a boolean return value, never checking actual balance deltas, allowing a malicious or non-standard ERC20 contract to spoof asset holdings inside `pallet_xcm::execute` - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `::deposit_asset_with_surplus` move ERC20 balances by calling the token contract's Solidity `transfer()` function and then unconditionally trust the boolean return value to decide whether `amount` units were moved [1](#0-0) . There is no `balanceOf` check before/after the call, so the XCM holding register (`AssetsInHolding`, backed by `Erc20Credit(amount)`) is populated with the *nominal* transfer amount rather than the *actual* change in the checking account's/beneficiary's balance [2](#0-1) . Any address matching the `AccountKey20` location pattern is accepted as a valid "asset" by the matcher with no allow-list/registration requirement [3](#0-2) , so a fully permissionless, attacker-deployed contract can supply a `transfer()` that returns `true` while moving less (fee-on-transfer/deflationary) or none of the claimed value.

### Finding Description
The entry point is fully user-reachable and unprivileged: any signed account can deploy an arbitrary Solidity contract via `pallet-revive`, then call `PolkadotXcm::execute` with a program that references that contract's `H160` address as an XCM `Location` (`AccountKey20`). This is precisely how the existing test `withdraw_and_deposit_erc20s` operates, using `WithdrawAsset`/`DepositAsset` against a user-deployed ERC20 [4](#0-3) .

`ERC20Matcher` (`MatchedConvertedConcreteId` over `IsLocalAccountKey20`/`AccountKey20ToH160`) accepts *any* `(0, [AccountKey20{..}])` location as a valid fungible asset id — there is no registration, allow-list, or metadata check comparable to `pallet-assets`' `ForeignAssets`/`Assets` registration flow [3](#0-2) . `ERC20Transactor` is wired into `AssetTransactors` on Asset Hub Westend (and analogously Rococo) [5](#0-4) .

On `withdraw_asset_with_surplus`, the transactor calls `IERC20::transferCall{ to: checking_address, value: amount }` against the *user-supplied* contract address, decodes only the boolean success value, and on `true` credits an `AssetsInHolding` register with `Erc20Credit(amount)` — the amount *requested*, not the amount that the checking account's balance actually increased by [1](#0-0) . Symmetrically, `deposit_asset_with_surplus` calls `transfer()` from the (shared, persistent) checking account to the beneficiary for `amount`, again trusting only the boolean result [6](#0-5) . The `Erc20Credit` imbalance type itself is explicitly documented as *not* performing runtime-level balance enforcement, "where the actual balance constraints are enforced by the ERC20 smart contract itself" [7](#0-6)  — i.e., the runtime fully outsources bookkeeping correctness to an untrusted, attacker-controlled contract.

This is the structural analog of the Kairos bug: the recorded amount (`toRepay`/`toPay` in the original report, `Erc20Credit(amount)` here) is set from the *intended* transfer value rather than a verified pre/post balance delta, for an asset whose transfer semantics are not guaranteed to move exactly that amount (fee-on-transfer, deflationary, or outright fake/"honeypot" tokens that always return `true`).

### Impact Explanation
Within a single `pallet_xcm::execute` program, this lets an attacker fabricate an `AssetsInHolding` credit that does not correspond to any real value movement (their own contract can return `true` unconditionally while transferring 0 or a reduced amount). Any subsequent instruction in the same XCM program that treats this credit as real value (e.g. `ExchangeAsset` against a liquidity pool, or `DepositAsset` drawing down the shared `ERC20TransfersCheckingAccount`) will operate on incorrect accounting. Because the checking account is a single, persistent, shared account across all users of the transactor (not reset per program), any residual mismatch between "credited-but-not-received" and "debited-but-partially-received" amounts accumulates in a shared, cross-user account, and non-standard tokens (fee-on-transfer, deflationary, or fake-success contracts) can cause deposits to a beneficiary to fail, funds to be trapped (`AssetsTrapped`), or (where the fake credit is later exchanged against a real-asset pool) enable extraction of real backing assets for a worthless/fabricated ERC20. This mirrors the report's Medium-severity "claim()/repay() breaks due to fee-on-transfer accounting" pattern, but here the check is entirely absent rather than merely imprecise, and the "token with fees" is fully attacker-deployable and permissionless (no registration).

### Likelihood Explanation
High reachability, no privilege required: deploying a contract via `pallet-revive` and calling `PolkadotXcm::execute(...)` are both ordinary, permissionless user actions already exercised in-repo by `withdraw_and_deposit_erc20s` [8](#0-7) . The `IsLocalAccountKey20` matcher imposes no allow-list, so any freshly deployed contract is immediately eligible [9](#0-8) . The only constraint reducing severity is that the *initial* damage is confined to the attacker's own fabricated asset unless combined with a downstream instruction (e.g. `ExchangeAsset`) that converts the fabricated credit into real value — the plumbing for such downstream use (arbitrary XCM instruction composition in a single `execute` call) already exists.

### Recommendation
Verify actual balance deltas rather than trusting the boolean `transfer()` return value: read `balanceOf(checking_account)` (or beneficiary) immediately before and after the `bare_call`, and use `min(amount, actual_delta)` (or reject on mismatch) when constructing/consuming the `Erc20Credit`, mirroring the "check balance before/after" pattern recommended in the original report. Additionally consider requiring explicit registration/allow-listing of ERC20 contracts eligible for `ERC20Matcher`, consistent with how `pallet-assets`/`ForeignAssets` require explicit creation before being XCM-transactable.

### Proof of Concept
- Reachable code path is exercised by the existing integration test `withdraw_and_deposit_erc20s`, which deploys a user contract and drives it through `PolkadotXcm::execute` with `withdraw_asset`/`deposit_asset` against the `AccountKey20` location of the deployed contract [10](#0-9) .
- The missing check is at `withdraw_asset_with_surplus`/`deposit_asset_with_surplus`, where `is_success` (the ABI-decoded boolean) is the sole gate for crediting/consuming `amount`, with no `balanceOf` comparison [11](#0-10) .
- A full end-to-end PoC (deploying a fee-on-transfer/fake-success Solidity contract, wiring it through `pallet_xcm::execute`, and demonstrating a beneficiary receiving less than credited, or a checking-account balance underflow/failure) was not executed in this environment — no test harness run was performed; this analysis is based on static code review of the transactor and its existing test coverage. A Devin session with Rust/Substrate toolchain access would be needed to compile a malicious Solidity fixture and run the emulated integration test to obtain concrete before/after balance assertions.

/// A minimal imbalance tracking type that holds an ERC20 token amount.
///
/// This type implements the necessary imbalance accounting traits but does not perform
/// runtime-level balance enforcement. It's used to track ERC20 token amounts within XCM
/// asset holdings, where the actual balance constraints are enforced by the ERC20 smart
/// contract itself rather than the runtime.
struct Erc20Credit(u128);
impl UnsafeConstructorDestructor<u128> for Erc20Credit {
	fn unsafe_clone(&self) -> Box<dyn ImbalanceAccounting<u128>> {
		Box::new(Erc20Credit(self.0))
	}
	fn forget_imbalance(&mut self) -> u128 {
		let amount = self.0;
		self.0 = 0;
		amount
	}
}

impl UnsafeManualAccounting<u128> for Erc20Credit {
	fn saturating_subsume(&mut self, mut other: Box<dyn ImbalanceAccounting<u128>>) {
		let amount = other.forget_imbalance();
		self.0 = self.0.saturating_add(amount);
	}
}

impl ImbalanceAccounting<u128> for Erc20Credit {
	fn amount(&self) -> u128 {
		self.0
	}
	fn saturating_take(&mut self, amount: u128) -> Box<dyn ImbalanceAccounting<u128>> {
		let new = self.0.min(amount);
		self.0 = self.0 - new;
		Box::new(Erc20Credit(new))
	}
}

/// `Contains<Location>` implementation that matches locations with no parents,
/// a `PalletInstance` and an `AccountKey20` junction.
pub struct IsLocalAccountKey20;
impl Contains<Location> for IsLocalAccountKey20 {
	fn contains(location: &Location) -> bool {
		matches!(location.unpack(), (0, [AccountKey20 { .. }]))
	}
}

/// Fallible converter from a location to a `H160` that matches any location ending with
/// an `AccountKey20` junction.
pub struct AccountKey20ToH160;
impl MaybeEquivalence<Location, H160> for AccountKey20ToH160 {
	fn convert(location: &Location) -> Option<H160> {
		match location.unpack() {
			(0, [AccountKey20 { key, .. }]) => Some((*key).into()),
			_ => None,
		}
	}

	fn convert_back(key: &H160) -> Option<Location> {
		Some(Location::new(0, [AccountKey20 { key: (*key).into(), network: None }]))
	}
}

/// [`xcm_executor::traits::MatchesFungibles`] implementation that matches
/// ERC20 tokens.
pub type ERC20Matcher =
	MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>;

#[test]
fn withdraw_and_deposit_erc20s() {
	let sender: AccountId = ALICE.into();
	let beneficiary: AccountId = BOB.into();
	let revive_account = pallet_revive::Pallet::<Runtime>::account_id();
	let checking_account =
		asset_hub_westend_runtime::xcm_config::ERC20TransfersCheckingAccount::get();
	let initial_wnd_amount = 100_000_000_000_000_000u128;
	sp_tracing::init_for_tests();

	ExtBuilder::<Runtime>::default().build().execute_with(|| {
		// Bring the revive account to life.
		assert_ok!(Balances::mint_into(&revive_account, initial_wnd_amount));
		// Fund all accounts involved.
		assert_ok!(Balances::mint_into(&sender, initial_wnd_amount));
		assert_ok!(Balances::mint_into(&beneficiary, initial_wnd_amount));
		assert_ok!(Balances::mint_into(&checking_account, initial_wnd_amount));

		let code = compile_module_with_type("MyToken", FixtureType::Resolc)
			.expect("compile ERC20")
			.0;

		let initial_amount_u256 = U256::from(1_000_000_000_000u128);
		let constructor_data = sol_data::Uint::<256>::abi_encode(&initial_amount_u256);
		let Contract { addr: erc20_address, .. } = bare_instantiate(&sender, code)
			.transaction_limits(TransactionLimits::WeightAndDeposit {
				weight_limit: Weight::from_parts(500_000_000_000, 10 * 1024 * 1024),
				deposit_limit: Balance::MAX,
			})
			.data(constructor_data)
			.build_and_unwrap_contract();

		let sender_balance_before = <Balances as fungible::Inspect<_>>::balance(&sender);

		let erc20_transfer_amount = 100u128;
		let wnd_amount_for_fees = 10_000_000_000_000u128;
		// Actual XCM to execute locally.
		let message = Xcm::<RuntimeCall>::builder()
			.withdraw_asset((Parent, wnd_amount_for_fees))
			.pay_fees((Parent, wnd_amount_for_fees))
			.withdraw_asset((
				AccountKey20 { key: erc20_address.into(), network: None },
				erc20_transfer_amount,
			))
			.deposit_asset(AllCounted(1), beneficiary.clone())
			.refund_surplus()
			.deposit_asset(AllCounted(1), sender.clone())
			.build();
		assert_ok!(PolkadotXcm::execute(
			RuntimeOrigin::signed(sender.clone()),
			Box::new(VersionedXcm::V5(message)),
			Weight::from_parts(600_000_000_000, 15 * 1024 * 1024),
		));

		// Revive is not taking any fees.
		let sender_balance_after = <Balances as fungible::Inspect<_>>::balance(&sender);
		// Balance after is larger than the difference between balance before and transferred
		// amount because of the refund.
		assert!(sender_balance_after > sender_balance_before - wnd_amount_for_fees);

		// Beneficiary receives the ERC20.
		let beneficiary_amount =
			<Revive as fungibles::Inspect<_>>::balance(erc20_address, &beneficiary);
		assert_eq!(beneficiary_amount, erc20_transfer_amount);
	});
