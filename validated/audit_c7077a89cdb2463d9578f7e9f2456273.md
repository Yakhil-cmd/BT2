### Title
`OpenedHandler#provision?` operator-precedence bug lets `prevent_with_label`/`allow_with_label` repos auto-provision review stacks even with `review_stacks_enabled: false` - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`OpenedHandler#provision?` is written with `&&`/`||` operators such that `repository.review_stacks_enabled` is only ANDed into the `allow_all` branch of the boolean expression, not the `allow_with_label`/`prevent_with_label` branches. As a result, a repository configured with `review_stacks_enabled: false, provisioning_behavior: :prevent_with_label` will still auto-create and auto-provision a review stack whenever an unprivileged contributor opens a PR without the provisioning label, running that PR's `shipit.yml` steps on the deploy host via `Command#start` / `PTY.spawn`.

### Finding Description
The broken binding is: `repository.review_stacks_enabled == true` should be a necessary condition for `provision?` to return `true`, for every provisioning behavior. That equality does not hold for the `prevent_with_label` and `allow_with_label` branches. [1](#0-0) 

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

Because Ruby's `&&` binds tighter than `||`, this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`

For a repository with `review_stacks_enabled: false, provisioning_behavior: :prevent_with_label`: the first term is `false`, the second is `false` (behavior isn't `allow_with_label`), but the third term is `prevent_with_label? (true) && !has_label? (true when the attacker adds no label)` = `true`. `provision?` therefore returns `true` purely from a genuine, unforged GitHub webhook that any external contributor can trigger by opening a PR without adding any label — no signature bypass or privilege is needed.

By contrast, `LabeledHandler#respond_to_label_change?` correctly ANDs `review_stacks_enabled` across the entire behavior check: [2](#0-1) 

showing the intended semantic that was lost in `OpenedHandler#provision?` (and equivalently in `ReopenedHandler#unarchive?`, which has the identical broken expression).

Downstream, `process` calls `ReviewStackAdapter#find_or_create!`, which creates a `ReviewStack` whose `branch` is taken directly from the PR's `head.ref`: [3](#0-2) 

and enqueues it via `Shipit::ReviewStackProvisioningQueue.add(stack)`. The cron-driven queue then provisions it: [4](#0-3) 

Once provisioned, a `Task` is created and run using `TaskCommands`, whose `steps` come straight from `@task.definition.steps` (parsed out of the checked-out `shipit.yml`) and whose `perform` builds a `Command` per step: [5](#0-4) 

`DeploySpec::FileSystem` reads that `shipit.yml`/task definitions straight off the working directory that was checked out to the attacker-controlled `stack.branch`: [6](#0-5) 

Finally, `Command#start` executes each interpolated argument via `PTY.spawn` using the merged environment: [7](#0-6) 

Existing guards do not catch this: there is no separate `review_stacks_enabled` check in `respond_to_pull_request_opened?` outside of `provision?`; webhook signature verification only ensures the event is a genuine GitHub delivery (which it is, since the attacker's real PR generates a real, correctly-signed webhook) and does not validate authorization semantics inside the handler; and there is no test in `opened_handler_test.rb` covering `provisioning_enabled: false` combined with `prevent_with_label` or `allow_with_label` (only the `allow_all` case is tested), which is why this asymmetry with `LabeledHandler` went unnoticed.

### Impact Explanation
Any unprivileged GitHub user able to open a pull request against a repository that has review stacks nominally disabled (`review_stacks_enabled: false`) but configured with `provisioning_behavior: :prevent_with_label` (or `:allow_with_label` if they can add their own label) can get their PR's `shipit.yml` steps executed as shell commands on the Shipit deploy host with the host's deploy credentials/environment (`GITHUB_TOKEN`, `deploy_spec.machine_env`, etc., merged into `Command#env` and passed to `PTY.spawn`). This is Critical — RCE on the deploy host — and is repeatable for every PR opened against any repository sharing this configuration, and the review stack persists (re-provisionable) as long as the label is not added.

### Likelihood Explanation
Preconditions: a repository must exist in Shipit with `review_stacks_enabled: false` and `provisioning_behavior` set to `prevent_with_label` (or `allow_with_label` combined with the attacker being able to add the provisioning label themselves). No secrets, tokens, or elevated GitHub permissions are required by the attacker — only the ability to open a PR against the target repository (or a repo that accepts PRs from forks), which is the baseline capability assumed for the attacker in scope. This is a plain logic/precedence bug in first-party code, reachable through the documented webhook flow, and is fully repeatable.

### Recommendation
Fix the operator precedence in `OpenedHandler#provision?` and `ReopenedHandler#unarchive?` so `repository.review_stacks_enabled` gates every branch, matching `LabeledHandler`'s pattern, e.g.:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Apply the same fix to `unarchive?` in `reopened_handler.rb`, and add regression tests exercising `provisioning_enabled: false` combined with `allow_with_label` and `prevent_with_label`.

### Proof of Concept
minitest plan (add to `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`):
```ruby
test "does not create/provision stacks for prevent_with_label repos when review_stacks_enabled is false" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = []

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Assert both sides of the binding before/after the fix:
- Before fix: `repository.review_stacks_enabled == false` while `OpenedHandler.new(payload).send(:provision?) == true` — the equality "provision? implies review_stacks_enabled" is broken; `Shipit::Stack.count` increases and a `ReviewStack` with `branch == payload["pull_request"]["head"]["ref"]` is created and enqueued (`ReviewStackProvisioningQueue.add`).
- End-to-end extension: after `Shipit::ReviewStackProvisioningQueue.work` provisions the stack and a `Task` runs, assert `Shipit::TaskCommands.new(task).perform.first.args == [attacker's shipit.yml step]` and that `Shipit::Command#start` would invoke `PTY.spawn` with those attacker-controlled arguments — confirming code from a PR on a review-stacks-disabled repository reaches command execution.
- After the fix: `provision? == false`, no `Stack` is created, `assert_no_difference` passes.

    def start(&block)
      return if @started

      @control_block = block
      @out = @pid = nil
      FileUtils.mkdir_p(@chdir)
      begin
        @out, child_in, @pid = PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)
        child_in.close
      rescue Errno::ENOENT
        raise NotFound, "#{Shellwords.split(interpolated_arguments.first).first}: command not found"
      rescue Errno::EACCES
        raise Denied, "#{Shellwords.split(interpolated_arguments.first).first}: Permission denied"
      end
      @started = true
      self
    end
