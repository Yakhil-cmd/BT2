### Title
Unauthorized shared-address cosigner registration in `handleNewSharedAddress` leaks private payment data to attacker-controlled device (IDOR analog) - ([File: wallet_defined_by_addresses.js])

### Summary
The Weblate advisory describes an IDOR where scoped-permission objects (teams/projects) were accepted without validating that the caller was actually authorized for the referenced scope, letting an attacker gain read access to private projects. The `wallet_defined_by_addresses.js` message handler `handleNewSharedAddress` has an analogous authorization gap: it accepts an attacker-supplied address *definition* and *signers* map from any paired correspondent device, and treats the local user as a legitimate "member" of the resulting shared address as long as **any** address named in the definition happens to belong to the local wallet — without verifying that the local user (or any other referenced party) actually agreed to be part of that specific shared-address arrangement. Because that record subsequently drives who receives forwarded private-payment chains, an attacker can insert themselves as an unauthorized "cosigner" object reference and thereby be forwarded private financial data for outputs sent to that address.

### Finding Description
`handleNewSharedAddress` [1](#0-0)  performs only structural checks on an incoming `new_shared_address` message from a correspondent device:
- that `body.address` equals `chash(body.definition)`,
- that `signers[path].address` fields are syntactically valid and match `"address"` leaves extracted from the definition,
- and that every `"address"` leaf in the definition has a corresponding signer entry.

None of these checks verify that the *other* parties referenced by `"address"` leaves in the definition (or the local user in particular) consented to be bound into this new shared-address scope. Authorization is delegated entirely to `determineIfIncludesMeAndRewriteDeviceAddress` [2](#0-1) , which only checks whether **any** address named as a member in the definition is already one of `my_addresses` or a known `shared_addresses` entry: [3](#0-2) 

If a match is found, the message is accepted and `addNewSharedAddress` persists the attacker's device/address as a signer of this shared address [4](#0-3) , without any step requiring the referenced own-address owner to explicitly approve this specific composite definition (the legitimate multi-party flow, `createNewSharedAddressByTemplate`/`approvePendingSharedAddress`, exists but `handleNewSharedAddress` does not require it).

A malicious correspondent can craft a definition such as `["or", [["address", victim_address], ["sig", {pubkey: attacker_pubkey}]]]` where `victim_address` is any address the attacker knows belongs to the victim (e.g., learned from prior public units). This deterministically yields a new address `X = chash(definition)` unrelated to any address the victim has used, and the attacker fills in `signers` accordingly (no proof of collaboration is required for the `sig` leaf, since it is the attacker's own key). Upon receiving this message, the victim's wallet passes all structural checks, finds `victim_address` in `my_addresses`, concludes "I am not a member... " check succeeds, and calls `addNewSharedAddress`, inserting a `shared_address_signing_paths` row that binds the attacker's device_address as a legitimate cosigner of `X`.

This record is later consumed by the private-payment forwarding logic. When any private payment (divisible or indivisible asset) is later received with an output to `X`, `forwardPrivateChainsToOtherMembersOfOutputAddresses`/`forwardPrivateChainsToOtherMembersOfAddresses` look up `shared_address_signing_paths` for `X` and forward the **entire private payment chain** (amounts, blinding factors, and preceding chain elements) to every device_address recorded there [5](#0-4) , including the attacker's device that was never legitimately authorized by the victim for that specific shared address: [6](#0-5) 

This mirrors the CWE-639 pattern in the Weblate advisory: an object (an address/scope) is bound into a new authorization context based on the caller-supplied definition, and the check for "is the local principal a member" is insufficiently scoped, allowing the attacker to smuggle themselves in as an authorized party for private data they should have no access to.

### Impact Explanation
Successful exploitation discloses private-payment details (amounts, blinding factors, and full private-payment chain history for a divisible/indivisible private asset) to an unauthorized party — a confidentiality breach analogous to the "unauthorized read access to private project" impact in the original advisory (CVSS C:H). No funds can be stolen through this path alone (spending still requires the victim's or attacker's genuine private key per their own definition branch), but private financial data belonging to the victim (or forwarded through them as an intermediate hop) can be leaked to a device that was never authorized to see it. This is a High-severity information disclosure impacting private asset confidentiality guarantees that ocore explicitly aims to protect.

### Likelihood Explanation
The attack only requires being an established correspondent (paired device) of the victim — a normal, low-privilege relationship in ocore's wallet chat/device-pairing model, requiring no special network position, hub compromise, or leaked keys. Crafting a definition with an "or" branch containing the victim's known address plus the attacker's own `sig` leaf is straightforward and passes all existing validation in `handleNewSharedAddress`. The victim's wallet processes such unsolicited messages automatically (no explicit UI-level approval step is enforced by this code path), making exploitation practical for any paired correspondent.

### Recommendation
- Require positive, out-of-band or explicit-approval confirmation (mirroring the existing `pending_shared_addresses`/`approvePendingSharedAddress` flow) before persisting any `new_shared_address` message that includes one of the local user's own addresses as a member, rather than silently accepting any correspondent-initiated definition referencing an owned address.
- In `determineIfIncludesMeAndRewriteDeviceAddress`, additionally verify that the specific composite definition was solicited/expected (e.g., match against a locally-initiated template or require a matching pending-approval record) instead of accepting any definition that happens to reference an owned address.
- Audit all consumers of `shared_address_signing_paths` (e.g., `forwardPrivateChainsToOtherMembersOfAddresses`, `readAllControlAddresses`) to ensure they only forward private payment data to device_addresses that were affirmatively established through a bilateral/multilateral agreement, not through unilateral attacker-supplied registration.

### Proof of Concept
1. Attacker device `D_a` pairs as a normal correspondent with victim device `D_v` (standard, low-privilege ocore wallet correspondence).
2. Attacker learns `victim_address` (any address `D_v` controls, e.g., seen in a public unit).
3. Attacker builds `arrDefinition = ["or", [["address", victim_address], ["sig", {pubkey: attacker_pubkey}]]]`, computes `X = objectHash.getChash160(arrDefinition)`.
4. Attacker sends a `new_shared_address` message to `D_v`: `{address: X, definition: arrDefinition, signers: {"r.0": {address: victim_address}, "r.1": {device_address: D_a}}}`.
5. `handleNewSharedAddress` on `D_v` passes structural checks, `determineIfIncludesMeAndRewriteDeviceAddress` finds `victim_address` in `my_addresses`, and `addNewSharedAddress` persists `shared_address_signing_paths` binding `D_a` as cosigner of `X`.
6. Attacker (or anyone told to pay `X`) sends a private (divisible or indivisible) asset payment to `X`.
7. When `D_v` (or any other legitimate party in the forwarding chain) processes/forwards this private payment, `forwardPrivateChainsToOtherMembersOfAddresses` queries `shared_address_signing_paths` for `X`, finds `D_a`, and forwards the full private payment chain (amounts/blinding factors/history) to the attacker's device — data the attacker was never authorized to receive.

function determineIfIncludesMeAndRewriteDeviceAddress(assocSignersByPath, handleResult){
	var assocMemberAddresses = {};
	var bHasMyDeviceAddress = false;
	for (var signing_path in assocSignersByPath){
		var signerInfo = assocSignersByPath[signing_path];
		if (signerInfo.device_address === device.getMyDeviceAddress())
			bHasMyDeviceAddress = true;
		if (signerInfo.address)
			assocMemberAddresses[signerInfo.address] = true;
	}
	var arrMemberAddresses = Object.keys(assocMemberAddresses);
	if (arrMemberAddresses.length === 0)
		return handleResult("no member addresses?");
	db.query(
		"SELECT address, 'my' AS type FROM my_addresses WHERE address IN(?) \n\
		UNION \n\
		SELECT shared_address AS address, 'shared' AS type FROM shared_addresses WHERE shared_address IN(?)", 
		[arrMemberAddresses, arrMemberAddresses],
		function(rows){
		//	handleResult(rows.length === arrMyMemberAddresses.length ? null : "Some of my member addresses not found");
			if (rows.length === 0)
				return handleResult("I am not a member of this shared address");
			var arrMyMemberAddresses = rows.filter(function(row){ return (row.type === 'my'); }).map(function(row){ return row.address; });
			// rewrite device address for my addresses
			if (!bHasMyDeviceAddress){
				for (var signing_path in assocSignersByPath){
					var signerInfo = assocSignersByPath[signing_path];
					if (signerInfo.address && arrMyMemberAddresses.indexOf(signerInfo.address) >= 0)
						signerInfo.device_address = device.getMyDeviceAddress();
				}
			}
			handleResult();
		}
	);
}

function handleNewSharedAddress(body, callbacks){
	if (!ValidationUtils.isArrayOfLength(body.definition, 2))
		return callbacks.ifError("invalid definition");
	if (typeof body.signers !== "object" || Object.keys(body.signers).length === 0)
		return callbacks.ifError("invalid signers");
	try {
		var addr = objectHash.getChash160(body.definition);
	}
	catch (e) {
		return callbacks.ifError("invalid definition: " + e);
	}
	if (body.address !== addr)
		return callbacks.ifError("definition doesn't match its c-hash");
	for (var signing_path in body.signers){
		var signerInfo = body.signers[signing_path];
		if (signerInfo.address && signerInfo.address !== 'secret' && !ValidationUtils.isValidAddress(signerInfo.address))
			return callbacks.ifError("invalid member address: " + JSON.stringify(signerInfo.address));
	}
	const assocDefinitionAddresses = extractAddressPathsFromDefinition(body.definition);
	for (let signing_path in body.signers) {
		const signerInfo = body.signers[signing_path];
		if (assocDefinitionAddresses[signing_path] !== signerInfo.address)
			return callbacks.ifError("signer address at path " + signing_path + " doesn't match definition");
	}
	for (let def_path in assocDefinitionAddresses) {
		if (!body.signers[def_path])
			return callbacks.ifError("no signer for definition address at path " + def_path);
	}
	determineIfIncludesMeAndRewriteDeviceAddress(body.signers, function(err){
		if (err)
			return callbacks.ifError(err);
		validateAddressDefinition(body.definition, function(err){
			if (err)
				return callbacks.ifError(err);
			addNewSharedAddress(body.address, body.definition, body.signers, body.forwarded, callbacks.ifOk);
		});
	});
}
