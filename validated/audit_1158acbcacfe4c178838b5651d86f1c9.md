## Analysis

The reported issue is about a one-step, unchecked ownership transfer: `OwnableImpl.transferOwnership()` lets the current owner set a new owner in a single, irreversible step, with no verification that the new owner value is valid/reachable, risking permanent loss of control.

The `ocore` analog is the `address_definition_change` message, which lets an address's current signer replace the address's definition (i.e., transfer control of the address to a new key/definition) in one irreversible step, based purely on a hash (`definition_chash`) supplied by the composer — with no validation that a definition matching that hash actually exists or can ever be revealed.

### Root cause
`composeDefinitionChangeJoint()` builds the message directly from a caller-supplied `definition_chash` with no sanity check on it: [1](#0-0) 

On-chain validation of the message only checks that `definition_chash` is syntactically a valid base32 address-like hash — it never checks that the hash corresponds to any known/derivable definition, nor that it differs from a "dead" or unreachable value: [2](#0-1) 

The change takes effect as soon as the unit is stable — there is no two-step "propose new definition, then confirm from the new definition" flow. Once `address_definition_changes` records the new `definition_chash` for the address, all subsequent authorizations for that address require disclosing a definition array whose hash equals it: [3](#0-2) [4](#0-3) 

If nobody knows a definition array that hashes to the new `definition_chash` (e.g., due to a bug in the composing wallet/hardware device, a corrupted/incomplete definition template exchange for a shared/multisig address, or a malicious cosigner substituting an unrecoverable hash during a shared-address definition-change negotiation), the address becomes permanently unusable: `checkSerialAddressUse` → `checkNoPendingChangeOfDefinitionChash` → `validateDefinition` will forever reject any future unit from that address because the disclosed definition can never hash to the recorded `definition_chash`: [5](#0-4) 

This mirrors the reported bug class precisely: a single unprivileged actor (the address's own signer, or a cosigner in a shared/multisig address flow) can trigger an irreversible "ownership"(definition) change with no on-protocol sanity check and no two-step reveal/confirmation, permanently freezing any current and future funds at that address.

### Title
Single-step, unchecked `address_definition_change` can permanently freeze an address's funds - (File: validation.js, composer.js)

### Summary
The `address_definition_change` message changes which key/definition controls an address in one irreversible step, validated only for base32 well-formedness of the new `definition_chash`. There is no check that a definition matching the new hash is known/derivable, and no two-step propose/confirm mechanism, analogous to the reported `OwnableImpl.transferOwnership()` weakness.

### Finding Description
`composeDefinitionChangeJoint(from_address, definition_chash, signer, callbacks)` accepts an arbitrary `definition_chash` from the caller with no validation [1](#0-0) . When posted, `validateInlinePayload` for `"address_definition_change"` only checks that `payload.definition_chash` is a syntactically valid address/hash and that only one change per address exists in the unit [2](#0-1) . It never verifies that this hash corresponds to any actual, known definition array. Once stable, `writer.js` persists the new hash as the address's current controlling definition [3](#0-2) , and future validation of any unit signed by that address requires the signer to disclose a definition array whose `objectHash.getChash160()` equals this recorded hash, or the unit is rejected [5](#0-4) . If the chosen hash cannot ever be matched by a real definition (e.g., composer/wallet bug, corrupted shared-address negotiation, or a malicious cosigner in a multi-signature address supplying a bogus commitment during a change-of-definition round), the address is permanently bricked — the change is one-directional and there is no "pending"/"proposed" state that requires acceptance by anyone holding the new keys before it takes effect.

### Impact Explanation
Any bytes, assets, or AA-controlled funds held at (or later sent to) the affected address become permanently unspendable, since no future unit from that address can ever validate. This is a direct fund-freezing outcome equivalent in severity to the referenced report's "ownership lost forever," reachable by an ordinary address owner or a cosigner in a shared-address definition-change flow — no privileged network role is required.

### Likelihood Explanation
Triggering requires only posting a normally-authorized `address_definition_change` message from an address the attacker/mistaken user already controls (or co-controls in a multisig/shared address). This is a standard, frequently-used feature (key rotation) with no built-in sanity check or reveal/confirm step, making accidental or adversarial (in multisig cosigner disputes) triggering plausible.

### Recommendation
Require the `address_definition_change` payload to include (or be immediately followed, atomically in the same unit, by) the actual new definition array so its hash can be verified against `definition_chash` at validation time, rather than deferring hash verification until the address is later used. Alternatively, introduce a two-step process: record the change as "pending," and only finalize/activate it once a unit signed with the new definition (proving it is known and satisfiable) is seen, mirroring `Ownable2Step`'s accept-by-new-owner pattern.

### Proof of Concept
1. Wallet/user calls `composer.composeDefinitionChangeJoint(from_address, definition_chash, signer, callbacks)` with a `definition_chash` value that does not correspond to any definition array actually known to any party (e.g., due to a bug, or a cosigner substituting a bad hash during a shared-address key-rotation negotiation).
2. The unit passes `validateInlinePayload` since `definition_chash` is a well-formed base32 hash [6](#0-5) .
3. Once stable, `writer.js` records this hash as the address's controlling definition [3](#0-2) .
4. Any future unit from `from_address` must supply a `definition` whose chash equals the recorded value or be rejected by `validateDefinition`/`handleDuplicateAddressDefinition` [5](#0-4) ; since no definition hashing to that value exists, the address can never again be validly used, permanently freezing all funds held there.

function readDefinitionChashByAddress(conn, address, max_mci, handle){
	if (!handle)

	if (max_mci == null || max_mci == undefined)
		max_mci = MAX_INT32;

	conn.query(
		"SELECT definition_chash FROM address_definition_changes CROSS JOIN units USING(unit) \n\
		WHERE address=? AND is_stable=1 AND sequence='good' AND main_chain_index<=? ORDER BY main_chain_index DESC, level DESC LIMIT 1", 
		[address, max_mci], 
		function(rows){
			var definition_chash = (rows.length > 0) ? rows[0].definition_chash : address;
			handle(definition_chash);
	});
