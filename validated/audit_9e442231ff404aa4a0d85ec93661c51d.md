### Title
Webhook signature verification keys off `repository.owner.login` while event routing keys off the independent `repository.full_name` field, allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to validate an inbound webhook against using `repository_owner`, read from `params.dig('repository', 'owner', 'login')`. Once the signature check passes, the actual event routing and the repository/stack that gets acted upon is derived from a *different*, uncorrelated JSON field: `payload.dig('repository', 'full_name')` in `Shipit::Webhooks::Handlers::Handler#repository_name`. Nothing ties these two fields together, so the organization whose key authenticated the request is never proven to be the organization whose repository is actually written to. [1](#0-0) [2](#0-1) 

### Finding Description
Shipit supports hosting multiple GitHub organizations, each configured with its own `webhook_secret` under `Shipit.github`: [3](#0-2) 

`GitHubApp#verify_webhook_signature` explicitly treats a blank/unconfigured `webhook_secret` as "always valid": [4](#0-3) 

`WebhooksController#verify_signature` picks the `GitHubApp` instance to check the signature with solely from `repository_owner`, itself parsed straight out of the untrusted request body before any verification occurs: [5](#0-4) 

Once verification "succeeds" (which it trivially does for any organization configured with a blank `webhook_secret`, e.g. during onboarding as shown in the shipped example secrets templates), `WebhooksController#create` hands the entire attacker-controlled JSON body to `Shipit::Webhooks.for_event(event)` handlers unchanged: [6](#0-5) 

Every handler then resolves the target `Stack`/`Repository` using `repository.full_name`, a field that is never cross-checked against the `repository.owner.login` used for signature selection: [2](#0-1) 

This breaks the trust binding: `organization that authenticated == organization whose repository is written`. Concretely, if the Shipit installation hosts an organization `A` whose `webhook_secret` is left blank (a state the code path explicitly supports and the shipped config templates depict as valid), an unauthenticated attacker can:
1. Set `repository.owner.login = "A"` so `verify_signature` resolves `Shipit.github(organization: "A")`, whose `verify_webhook_signature` short-circuits to `true` because `webhook_secret` is blank.
2. Set `repository.full_name = "victim-org/victim-repo"` — a different, fully secured organization already tracked by Shipit — so that `PushHandler`, `StatusHandler`, `MembershipHandler`, or the `pull_request` handlers act on the victim's `Stack`/`Repository`.

No `webhook_secret`, `ApiClient` token, or session of any kind is required to reach this bypass — the endpoint is public by design so GitHub can deliver events.

### Impact Explanation
Depending on which event type is chosen, this cross-organization confusion allows an unauthenticated party to:
- Forge `push` events to enqueue `GithubSyncJob` and inject attacker-chosen commit SHAs into a victim stack's undeployed commit list.
- Forge `status`/`check_suite` events to mark arbitrary commits on the victim repository as passing CI, undermining the review/CI gates that a deploy or merge decision relies on.
- Forge `membership` events to create `Team`/`Membership` records, directly manipulating the `Shipit.github_teams`-based authorization model.

Combined with existing deploy/merge automation, this can lead to an unauthorized deploy or an escalation into the team-based authorization system — matching the High/Critical impact classes defined for this engine (unauthorized deploy, escalation into `Shipit.github_teams` authorization).

### Likelihood Explanation
Exploitability only requires that *any one* organization hosted by the Shipit instance has an unset `webhook_secret` — an onboarding state the code explicitly tolerates (`return true unless webhook_secret`) and that the project's own example/secrets templates show as a normal, non-error configuration. No secrets, tokens, or sessions are needed by the attacker; the webhook endpoint is intentionally public.

### Recommendation
Bind the authenticating organization to the repository actually acted upon: after `verify_signature` succeeds, require that `repository.full_name`'s owner segment matches the `repository_owner` used to select the signing key, and reject the request otherwise. Additionally, treat a blank `webhook_secret` as a hard misconfiguration that disables event processing (or at minimum restricts the "always verified" fallback to organizations that have no repositories/stacks registered), rather than silently accepting any payload.

### Proof of Concept
1. Configure Shipit with two organizations in `Shipit.github`: `unsecured-org` (no `webhook_secret`) and `secured-org` (with `webhook_secret`, and hosting `secured-org/victim-repo` as a tracked `Stack`).
2. As an unauthenticated attacker, POST to the webhook endpoint (`config/routes.rb` mounts `WebhooksController#create`) with:
   - Header `X-Github-Event: push`
   - Header `X-Hub-Signature: sha1=0000000000000000000000000000000000000000` (or any value)
   - Body:
     ```json
     {
       "repository": { "owner": { "login": "unsecured-org" }, "full_name": "secured-org/victim-repo" },
       "after": "<attacker-chosen-sha>",
       "ref": "refs/heads/master"
     }
     ```
3. `verify_signature` calls `Shipit.github(organization: "unsecured-org").verify_webhook_signature(...)`, which returns `true` unconditionally per `lib/shipit/github_app.rb:76-77`, regardless of the bogus `X-Hub-Signature`.
4. `create` dispatches the parsed body to `PushHandler`, which resolves the target stack via `payload.dig('repository', 'full_name')` = `"secured-org/victim-repo"`, enqueuing sync/processing against the victim's real, properly-secured stack — despite the attacker never possessing `secured-org`'s `webhook_secret`.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
