### Title
Bridge `handleKLAYTransfer` / `handleERC20Transfer` Bypass `isRunning` Stop — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`, `contracts/service_chain/bridge/BridgeTransferERC20.sol`)

---

### Summary

The Kaia service-chain bridge exposes an asymmetric protection gap that is structurally identical to the Ion Protocol "safe-pause" liquidation bypass. The `isRunning` flag is intended to halt all asset movement when the bridge owner calls `setRunningStatus(false)` or `start(false)`. The outbound request functions (`_requestKLAYTransfer`, `_requestERC20Transfer`) correctly enforce this guard. The inbound completion functions (`handleKLAYTransfer`, `handleERC20Transfer`) do not. Bridge operators can therefore drain KLAY and ERC-20 tokens from a stopped bridge, defeating the emergency-stop invariant.

---

### Finding Description

`BridgeTransfer.sol` declares `isRunning = true` and exposes `setRunningStatus(bool)` (owner-only) as an emergency stop: [1](#0-0) 

The outbound path enforces the guard:

```solidity
// _requestKLAYTransfer (BridgeTransferKLAY.sol:108)
require(isRunning, "stopped bridge");
``` [2](#0-1) 

```solidity
// _requestERC20Transfer (BridgeTransferERC20.sol:88)
require(isRunning, "stopped bridge");
``` [3](#0-2) 

The inbound completion path has **no such check**:

```solidity
function handleKLAYTransfer(...) public onlyOperators nonReentrant {
    _lowerHandleNonceCheck(_requestedNonce);
    if (!_voteValueTransfer(_requestedNonce)) { return; }   // early-return analog
    // ... proceeds to transfer KLAY regardless of isRunning
    (bool ok, ) = _to.call.value(_value)("");
    require(ok, "handleKLAYTransfer: transfer failed");
}
``` [4](#0-3) 

```solidity
function handleERC20Transfer(...) public onlyOperators {
    _lowerHandleNonceCheck(_requestedNonce);
    if (!_voteValueTransfer(_requestedNonce)) { return; }   // early-return analog
    // ... proceeds to mint or transfer ERC-20 regardless of isRunning
    if (modeMintBurn) { ERC20Mintable(_tokenAddress).mint(_to, _value); }
    else { IERC20(_tokenAddress).safeTransfer(_to, _value); }
}
``` [5](#0-4) 

The structural parallel to the Ion Protocol bug is exact:

| | Ion Protocol | Kaia Bridge |
|---|---|---|
| Protected state | `safePause` | `isRunning = false` |
| Blocked path | Normal liquidation → `repayBadDebt` reverts | `_requestKLAYTransfer` → `require(isRunning)` reverts |
| Bypassing path | Protocol liquidation returns early before `repayBadDebt` | `handleKLAYTransfer` has no `isRunning` check at all |
| Early-return mechanism | `return` before the failing call | `if (!_voteValueTransfer) { return; }` before the transfer |
| Asset impact | Unfair liquidation of user collateral | Unauthorized KLAY/ERC-20 drain from stopped bridge |

---

### Impact Explanation

When the bridge owner stops the bridge (e.g., in response to a security incident, a compromised operator key, or an exploit on the counterpart chain), they expect **all** asset movement to halt. Because `handleKLAYTransfer` and `handleERC20Transfer` ignore `isRunning`, any registered operator can still:

1. Call `handleKLAYTransfer` with a fabricated or replayed `_requestTxHash` and `_requestedNonce` to transfer arbitrary KLAY to an arbitrary `_to` address.
2. Call `handleERC20Transfer` to mint (in `modeMintBurn` mode) or transfer registered ERC-20 tokens to an arbitrary address.

The nonce window (`lowerHandleNonce` / `upperHandleNonce`) limits replay of already-handled nonces, but any unhandled nonce within the window is exploitable. In `modeMintBurn` mode the bridge can mint unbounded tokens on the child chain even with zero liquidity.

---

### Likelihood Explanation

The trigger requires a registered bridge operator — a semi-trusted role granted by the owner. The scenario is realistic: the owner stops the bridge precisely because an operator key is suspected compromised, yet the compromised operator can still drain the bridge through the unguarded handle path. The owner's only recourse is to also call `deregisterOperator` for every operator before the attacker acts, which is a race condition under incident conditions.

---

### Recommendation

Add an `isRunning` guard to both handle functions, mirroring the request-side protection:

```solidity
function handleKLAYTransfer(...) public onlyOperators nonReentrant {
    require(isRunning, "stopped bridge");   // add this
    _lowerHandleNonceCheck(_requestedNonce);
    ...
}

function handleERC20Transfer(...) public onlyOperators {
    require(isRunning, "stopped bridge");   // add this
    _lowerHandleNonceCheck(_requestedNonce);
    ...
}
```

Alternatively, place the guard in `BridgeTransfer._voteValueTransfer` so all handle paths inherit it uniformly.

---

### Proof of Concept

1. Owner deploys bridge, registers two operators `op1` and `op2` (threshold = 2), charges it with 1000 KLAY.
2. A security incident occurs; owner calls `bridge.start(false)` → `isRunning = false`.
3. `op1` calls `handleKLAYTransfer(fakeTxHash, attacker, attacker, 500 ether, 0, blockNum, "0x")` — first vote, no transfer yet.
4. `op2` calls `handleKLAYTransfer(fakeTxHash, attacker, attacker, 500 ether, 0, blockNum, "0x")` — threshold met, `_voteValueTransfer` returns `true`, the early-return is **not** taken, and 500 KLAY is transferred to `attacker` despite `isRunning == false`.
5. Repeat for remaining nonces to drain the bridge.

The test fixture at `contracts/test/Bridge/bridge.test.ts` line 770–788 confirms that `handleKLAYTransfer` succeeds with two operator votes and transfers KLAY; no test covers the `isRunning = false` case for handle functions, confirming the gap is untested. [6](#0-5)
