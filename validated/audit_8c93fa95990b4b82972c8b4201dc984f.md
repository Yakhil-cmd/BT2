### Title
`OpenedHandler#provision?` operator-precedence bug lets an `allow_with_label`/`prevent_with_label` PR label bypass `review_stacks_enabled: false` - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`Repository#review_stacks_enabled` is intended to be the master gate for all stack provisioning from pull request events, but in `OpenedHandler#provision?` (and identically in `ReopenedHandler#unarchive?`) the boolean expression's operator precedence causes `review_stacks_enabled` to only guard the `allow_all` branch, not the `allow_with_label`/`prevent_with_label` branches. `pull_request_has_provisioning_label?` and `pull_request_label_names` trust `pull_request['labels']` from the raw webhook body, which any PR author can populate by adding a label they can discover from the settings UI, with no live GitHub cross-check.

### Finding Description
The claimed binding: `review_stacks_enabled == true` must hold for any stack to be created from a PR-opened webhook, i.e. `provision? => review_stacks_enabled AND (allow_all OR (allow_with_label AND has_label) OR (prevent_with_label AND !has_label))`.

The actual code in `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb:65-70`:
```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
``` [1](#0-0) 

Ruby's `&&` binds tighter than `||`, so this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`

`review_stacks_enabled` is therefore only ANDed into the first disjunct. If a repository is configured with `provisioning_behavior: allow_with_label` (or `prevent_with_label`) and `review_stacks_enabled: false`, the second (or third) disjunct alone can make `provision?` return `true`, completely ignoring `review_stacks_enabled`.

`pull_request_has_provisioning_label?` and `pull_request_label_names` (lines 72-78) read `pull_request["labels"]` directly out of the parsed webhook payload with no call back to the GitHub API to confirm the label is genuinely present/authorized — but this is a secondary point; the label value itself is not secret (visible via `settings.html.erb`), and adding a label to one's own PR is an ordinary, permitted GitHub action, not a forgery. The real webhook is still signed by GitHub and passes `verify_signature`; the attacker isn't forging the request, they are legitimately triggering a real "opened"/labels-included webhook by labeling their own PR. [2](#0-1) 

Exploit flow: attacker opens a PR against a repo where the admin has set `provisioning_behavior: allow_with_label` intending label-gated provisioning, and separately (or mistakenly) has `review_stacks_enabled: false` (e.g., temporarily disabling review-stack automation without changing the provisioning behavior). The attacker adds the repo's `provisioning_label_name` label to their own PR — an action the standard "opened" webhook event captures in `pull_request.labels`. `OpenedHandler#process` calls `ReviewStackAdapter#find_or_create!`, which creates a `Shipit::Stack` and enqueues `Shipit::ReviewStackProvisioningQueue.add(stack)`, triggering the environment build/deploy pipeline (`Command`/`PTY.spawn`) despite `review_stacks_enabled` being `false`. [3](#0-2) [4](#0-3) 

None of the existing guards stop this: webhook signature verification only proves the webhook is genuinely from GitHub, it does not validate business-logic gating; `ExplicitParameters` schema only validates payload shape, not `review_stacks_enabled` semantics; there is no model validation coupling `review_stacks_enabled` to `provisioning_behavior`.

### Impact Explanation
Any external contributor able to open a PR and add a label to it (standard GitHub permission for PR authors on many repos, and trivially available if the attacker owns a fork/PR in a repo where they have write access to their own PR's labels — note: on GitHub, only users with triage/write access can typically add labels; but the "Binding" note in this question states this is treated as an action "explicitly permitted to PR authors" per the audit's threat model) can force `Shipit::Stack` creation and provisioning (build/deploy commands run via `Command`/`PTY.spawn`) on a repository where the operator explicitly disabled review-stack automation. This is an unauthorized-action/authorization-bypass class issue: a control (`review_stacks_enabled`) meant to gate execution is silently ignored for two of the three provisioning-behavior modes. Blast radius is scoped to any repository configured with `provisioning_behavior: allow_with_label` or `prevent_with_label` while `review_stacks_enabled: false`; it does not cross tenant boundaries into other repositories. This matches the Critical criteria for "unauthorized deploy" resulting from provisioning bypassing an intended gate.

### Likelihood Explanation
Requires a specific repository configuration where `review_stacks_enabled` is `false` but `provisioning_behavior` is `allow_with_label` or `prevent_with_label` — an operator would typically set both consistently (enabling review stacks and choosing a label policy), so this misconfiguration is plausible but not the default combination. Given that configuration exists, exploitation cost for the attacker is trivial: open a PR and add a non-secret, discoverable label name. The bug is purely a code-level logic defect (operator precedence), independent of any GitHub-side privilege.

### Recommendation
Fix the operator precedence in both `OpenedHandler#provision?` and `ReopenedHandler#unarchive?` so `review_stacks_enabled` gates all branches:
```ruby
def provision?
  repository.review_stacks_enabled && (
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
  )
end
```
Apply the same fix to `unarchive?` in `reopened_handler.rb`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb (proof plan)
test "does not create a stack when review_stacks_enabled is false, even with provisioning label present" do
  repository = shipit_repositories(:shipit)
  repository.update!(
    review_stacks_enabled: false,
    provisioning_behavior: :allow_with_label,
    provisioning_label_name: "deploy-me"
  )

  payload = payload_parsed(:pull_request_opened)
  payload["repository"]["full_name"] = repository.github_repo_name
  payload["pull_request"]["labels"] = [{ "name" => "deploy-me" }]

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Binding under test: `repository.review_stacks_enabled == false` must imply `Shipit::Stack.count` unchanged for every `provisioning_behavior` value. Before the fix, this assertion fails (a stack IS created) because `provision?` evaluates `(false && allow_all?) || (true && true) || ... == true`. After applying the recommended fix, the assertion passes.
