Based on my investigation, I found a genuine analog to the reported bug class.

### Title
Webhook Signature Verified Against `repository.owner.login` But Event Processing Trusts `repository.full_name` Unchecked - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In multi-organization Shipit deployments, `WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate the HMAC signature against using `repository_owner`, derived from `params.dig('repository', 'owner', 'login')`. Once the signature validates, the raw, attacker-supplied JSON body is handed unmodified to the event handlers, which resolve the target `Stack`/`Repository` using a *different* field, `payload.dig('repository', 'full_name')`. These two fields are never cross-checked against each other.

### Finding Description
`Shipit.github(organization:)` looks up the `GitHubApp` (and its `webhook_secret`) keyed by the organization derived from the *inbound, unauthenticated* payload [1](#0-0) . The signature is verified using that org's secret against the raw body [2](#0-1) . `Shipit.github` supports a multi-org secrets schema where each organization has its own independent `webhook_secret` [3](#0-2) .

After the signature check passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` is invoked with the full parsed JSON [4](#0-3) . Every handler resolves the target repository/stack via `payload.dig('repository', 'full_name')`, not `repository.owner.login` [5](#0-4) , then looks it up with `Repository.from_github_repo_name`, which just splits the string on `/` [6](#0-5) .

Because JSON payloads are entirely attacker-controlled (only the raw body's HMAC is checked, not any specific field's consistency), an attacker who legitimately controls a GitHub App installation on **their own** organization/repository (and therefore legitimately knows that org's `webhook_secret`, e.g. by owning that org in a multi-tenant Shipit install) can compute a valid signature for a forged JSON body where `repository.owner.login` = their own org (to pass signature selection) but `repository.full_name` = `victim-org/victim-repo` (to target someone else's stack). The equality the code implicitly assumes — `repository.owner.login used to select/verify secret == repository.full_name used to select the acted-upon Stack` — is never enforced.

### Impact Explanation
This breaks the binding between "the organization whose webhook secret authenticated the request" and "the repository/stack the event handlers act upon." Depending on the handler, this enables cross-repository/cross-organization writes: e.g. the `push` handler can enqueue a `GithubSyncJob` against a victim's stack [7](#0-6) , or `status`/`check_suite` handlers can mark arbitrary commits' CI state, or `pull_request`/`membership` handlers can manipulate state (labels, review stacks, team membership) on a repository the attacker does not own. This matches the "cross-repository writes" Critical impact bucket, since it lets an org that legitimately authenticated (owns a webhook secret) write to a repository it was never authorized to touch.

### Likelihood Explanation
This only manifests in the multi-organization `secrets.github` configuration schema, which is a documented and supported configuration (`github_app_config`/`github_organizations` in `lib/shipit.rb`) [8](#0-7) . Any tenant/org onboarded into such a shared Shipit instance holds a valid webhook secret for their own org and can freely craft the JSON body sent to `/webhooks`, since only the raw-body HMAC — not field consistency — is checked. This requires the host to run a multi-org configuration and requires the attacker to already be a legitimate org owner in that shared instance (no GitHub org membership on the victim side, no Shipit session, no API token is needed).

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler#repository_name`), assert that `params.dig('repository', 'owner', 'login')` matches the owner segment of `params.dig('repository', 'full_name')` before dispatching to handlers, and reject the request (422) on mismatch.

### Proof of Concept
1. Shipit configured with `secrets.github` containing two orgs, `attacker-org` and `victim-org`, each with distinct `webhook_secret`s.
2. Attacker, who legitimately owns `attacker-org`'s GitHub App and thus its `webhook_secret`, crafts a `push` event JSON body:
   ```json
   {
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
     "after": "<sha>"
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org_webhook_secret, body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` → `attacker-org`, fetches `attacker-org`'s secret, and the signature validates.
5. `Shipit::Webhooks.for_event('push')` handler runs using `repository.full_name` = `victim-org/victim-repo`, resolving and acting on the victim's `Stack` (e.g., enqueuing `GithubSyncJob` for that stack) despite the attacker never having any relationship to `victim-org`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
