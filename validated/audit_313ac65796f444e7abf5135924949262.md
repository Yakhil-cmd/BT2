### Title
Attacker-crafted swap route injects arbitrary contract calls that drain the caller's wallet under their own `swap_collateral` authorization — ([File: contracts/controller/src/strategies/swap_collateral.rs](contracts/controller/src/strategies/swap_collateral.rs))

### Summary
The Keycloak bug class — a crafted document whose placeholder/referenced content is substituted and processed during a routine operation — maps onto XOXNO Lending's `swap` route bytes. The controller strategies (`swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`) pass caller-supplied `StrategySwap`/`swap_xdr` bytes to the configured router, which invokes whatever pool/token addresses the payload names, with no venue allowlist. A rogue venue contract executed inside the victim's `require_auth` tree can call `token.transfer(victim, attacker, x)` on any token the victim holds; that child invocation is recorded under the victim's authorization entry and executes if the victim signs the simulated tree.

### Finding Description
`process_swap_collateral` in `contracts/controller/src/strategies/swap_collateral.rs:27-77` calls `caller.require_auth()` (via `require_authorized_caller`, line 40) and then forwards the caller-provided `swap` bytes into `withdraw_and_swap_from_supply` → `execute_strategy`. The router calls the pool address the payload names and keeps no allowlist of venues; the threat model confirms: "a route can put third-party code on the call stack below the caller's authorization" and any `transfer` such code makes "executes if the caller signs that tree" (docs/explanation/threat-model.md:154-165). There is no on-chain enforcement that the signed auth tree contains only the single input-transfer child the strategy legitimately needs.

The harness test `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` proves the path end-to-end: `UnlistedPoolRouter::execute_strategy` invokes the route-named `hop_pool` (lines 39-47); `RogueHopPool::swap` performs `wallet_token.transfer(victim → attacker)` (lines 62-71); simulation records the stolen transfer as a child of Alice's `swap_collateral` entry and drains her entire wallet token balance while still crediting her a fair ETH output (lines 194-227); enforcement mode moves the funds exactly when the simulated (poisoned) tree is signed (lines 229-269).

### Impact Explanation
Theft of user funds unbounded by the swap size. The victim's `swap_collateral` executes correctly at fair output, so the position-level checks (`RouterOverspend` = 501, `NoSwapOutput` = 502, final account risk per `INV-STRAT-02`, docs/reference/invariants.md:642-660) all pass — none of them bound a child `transfer` of an unrelated wallet token. The attacker steals every token balance of the signing account, demonstrated by `assert_eq!(s.wallet(&s.alice), 0)` and `assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE)` in the test (lines 224-226).

### Likelihood Explanation
Requires the victim to sign a route that names an attacker-controlled venue — typically delivered through a malicious or compromised quote source / frontend supplying `routeXdr` for `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`, or direct `execute_strategy`. The craft costs nothing (a registered contract plus payload bytes), and honest simulation legitimately produces the poisoned tree for signing, so wallets/clients that sign the simulated auth tree without decoding it are exposed. This matches a Medium severity: user action required, but total wallet loss on success.

### Recommendation
Enforce the authorization-tree shape rather than documenting it away. Options: (a) have the controller whitelist venue addresses reachable from router payloads (governance-approved pool registry), or (b) ship and enforce client-side verification — decode `swap_xdr`/`routeXdr` before signing and reject any authorization tree whose `swap_collateral`/`execute_strategy` entry carries children other than the single `token_in.transfer(sender → router, amount_in)`; the reference implementation already exists in `verifyRouteBytes`/`verifyRoutePayload` (skills/xoxno-swap-aggregator/payload.md:154-291) and should be a mandatory step, not optional guidance.

### Proof of Concept
See `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`. Concretely:

1. Attacker deploys `RogueHopPool` configured with `(victim, wallet_token, attacker, amount)` and crafts `routeXdr` naming that pool as a hop, with a fair `min_out`.
2. Victim requests a collateral swap and receives the crafted route; calls `controller.swap_collateral(alice, account_id, USDC_key, amount, ETH_key, route)` — reachable by any account owner per `controller::swap_collateral` in `scripts/permissionless_entrypoints.txt:54`.
3. `simulateTransaction` records `wallet_token.transfer(alice → attacker, WALLET_BALANCE)` as a child of Alice's `swap_collateral` auth entry (test lines 194-227).
4. Victim signs the simulated tree; the rogue transfer executes; Alice's unrelated wallet token balance goes to zero and the attacker receives it (test lines 265-268), while her `swap_collateral` still settles with fair output so no protocol check fires.
