### Title
Webhook signature verification is bound to `repository.owner.login` while all handlers act on the unrelated `repository.full_name` field, allowing cross-organization stack writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App (and thus the HMAC secret) to validate a webhook against using `repository.owner.login` (or `organization.login`) taken from the unverified request body. Once the signature check passes for that org, the exact same untrusted payload is handed to `Shipit::Webhooks::Handlers::Handler` subclasses, which resolve the `Stack`/`Repository` to mutate using `repository.full_name` — a separate field with no enforced relationship to `repository.owner.login`.

### Finding Description
`verify_signature` reads `repository_owner` from `params` (Rails auto-parses the JSON body before any HMAC check runs) and uses it to fetch `Shipit.github(organization: repository_owner)`, then verifies `X-Hub-Signature` against that organization's `webhook_secret`: [1](#0-0) 

The lookup of `repository_owner` itself: [2](#0-1) 

After the signature is accepted, `create` forwards the raw parsed `params` unchanged to the matching handlers: [3](#0-2) 

Every handler's `stacks`/`repository` resolution uses `repository.full_name`, not `repository.owner.login`: [4](#0-3) [5](#0-4) 

`Repository.from_github_repo_name` simply splits `full_name` on `/`, imposing no constraint that its owner segment matches the organization used to select the verifying secret: [6](#0-5) 

Deployments using the documented multi-organization GitHub App configuration (`github: { OrgOne: {...webhook_secret...}, OrgTwo: {...webhook_secret...} }`) are the concrete case where this equality is meant to hold but is never checked: [7](#0-6) 

Because the check binds only "does this signature match OrgOne's secret" while the mutation binds "act on whatever `full_name` says," a party who legitimately holds one organization's `webhook_secret` (e.g., an admin of one onboarded repo under OrgOne) can craft a payload where `repository.owner.login = "OrgOne"` (to pass verification) but `repository.full_name = "OrgTwo/some-other-repo"` (to target a stack under a different, unrelated organization/app they were never granted access to).

### Impact Explanation
This breaks the equality `organization that authenticated == repository that is written`. It allows cross-organization/cross-repository state writes — e.g., forging a `push` event that triggers `stack.sync_github` for a `Stack` belonging to a repository/organization the attacker does not control, or forging `status`/`check_suite`/`pull_request` events that manipulate commit statuses, review-stack archiving/unarchiving, or merges for stacks outside the org whose secret was actually used. This matches the "cross-repository writes" / "unauthorized deploy, rollback or merge" Critical impact criteria, since sync/status manipulation can influence which commits are considered deployable and can drive automated merges/deploys.

### Likelihood Explanation
Exploitation requires possession of a valid `webhook_secret` for at least one organization/app configured in Shipit — the same bar GitHub itself expects for legitimate webhook delivery, so this is not a fully unauthenticated attack. However, in any multi-organization Shipit deployment (the documented and supported configuration), the party with legitimate access to configure/deliver a webhook for one org is not expected to be trusted for other onboarded organizations, yet the controller never checks that the two identity fields agree, so the boundary is real and concretely reachable via a crafted HTTP POST with no need for a Shipit session, API token, or repository write access.

### Recommendation
After signature verification, re-derive `repository_owner` (or `organization`) strictly from the same field used to resolve the target repository (`repository.full_name`'s owner segment), and reject the request if they disagree. Equivalently, verify the signature using the app resolved from `repository.full_name`'s owner rather than a separately-read `repository.owner.login`/`organization.login`, so the value that authorizes the request and the value the request acts on are provably the same field.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgOne` and `OrgTwo`, each with its own `webhook_secret`, per the documented multi-app setup.
2. Onboard a repository `OrgOne/repo-a` (attacker has legitimate access here and thus knows `OrgOne`'s `webhook_secret`) and a target stack under `OrgTwo/repo-b`.
3. Craft a `push` payload where `repository.owner.login = "OrgOne"` but `repository.full_name = "OrgTwo/repo-b"`, with `ref`/`after` pointing at attacker-chosen values.
4. Compute `X-Hub-Signature` using `OrgOne`'s known `webhook_secret` over the raw JSON body.
5. POST to `/webhooks` with `X-Github-Event: push`. `verify_signature` looks up `Shipit.github(organization: "OrgOne")`, verifies successfully, and `PushHandler` resolves stacks via `Repository.from_github_repo_name("OrgTwo/repo-b")`, invoking `stack.sync_github(expected_head_sha: ...)` on the `OrgTwo` stack despite the signature never being checked against `OrgTwo`'s secret.
