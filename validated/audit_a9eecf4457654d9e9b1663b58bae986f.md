### Title
Stack-scoped API token can read the status of *any* stack via `CCMenuController` - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::BaseController` enforces a binding between an `ApiClient` token and the stacks it is allowed to touch: `stacks = current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` [1](#0-0) . `CCMenuController`, however, overrides both authentication and the `stack` finder and never consults that scoping, so a token minted for one stack can be used to read the CI status of a different stack.

### Finding Description
`BaseController#stack` is the standard resource lookup and is scoped through `stacks`, which restricts lookups to `current_api_client.stack_id` when the client is stack-scoped: [1](#0-0) 

`CCMenuController` bypasses this entirely. It authenticates via a raw query-string `token` (`ApiClient.authenticate(params[:token])`) and resolves the stack directly from the unscoped `Stack` model, ignoring which stack (if any) the authenticated `ApiClient` is bound to: [2](#0-1) 

The only authorization check performed is `require_permission :read, :stack`, which only validates the `read:stack` permission string on the client via `ApiClient#check_permissions!` — it does not check that `params[:stack_id]` matches `current_api_client.stack_id`: [3](#0-2) 

The equality that should hold is:
`stack(s) authorised by the token (current_api_client.stack_id)` == `stack the request actually touches (params[:stack_id] resolved via Stack.from_param!)`

Before the request: a caller only holds a token scoped to stack A (`current_api_client.stack_id == A.id`).
After the request: by supplying `stack_id=B` in the URL, `CCMenuController#stack` resolves and serves stack B's data — a stack the token was never authorized for.

This exact "stack-scoped" client pattern is corroborated by tests in `test/controllers/api/stacks_controller_test.rb` ("an api client scoped to a stack will only see that one stack") which validates the scoping is a real security boundary elsewhere in the API, but `CCMenuController` does not enforce it.

### Impact Explanation
An attacker in possession of a legitimately-issued, stack-scoped `ApiClient` token (e.g., a CCMenu URL generated for one stack, see `CCMenuUrlController#client`, which mints `read:stack`-permissioned clients: [4](#0-3) ) can enumerate `stack_id` values and read the build/deploy status (last build label, status, activity, web URL) of any stack in the Shipit instance, not just the one the token was created for. This is an unauthenticated-scope-boundary escalation resulting in unauthorized read of stack state, matching the in-scope "High" impact category (unauthenticated read of stack state / deploy output).

### Likelihood Explanation
Any holder of a valid, narrowly-scoped `read:stack` token (which is routinely distributed to third-party CI dashboards/CCMenu clients since it is embedded in a plain query-string URL) can trivially perform this by changing the `stack_id` path parameter. No special privileges beyond holding one such token are required.

### Recommendation
`CCMenuController#stack` should resolve through the scoped `stacks` collection (as `BaseController#stack` does) rather than calling `Stack.from_param!` directly, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
so that stack-scoped tokens can never resolve a stack outside `current_api_client.stack_id`.

### Proof of Concept
1. Stack A's owner visits the CCMenu URL page and obtains a token via `CCMenuUrlController#fetch`, scoped (in the intended design) to Stack A.
2. Using that same token value, issue: `GET /api/stacks/<stack-B-id>/ccmenu.xml?token=<tokenForStackA>`.
3. `CCMenuController#authenticate_api_client` accepts the token (it only validates the HMAC signature and existence of the `ApiClient`, not stack ownership).
4. `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` — resolving Stack B directly, with no scoping check against the token — and returns Stack B's build/deploy status in the XML response, even though the token was never authorized for Stack B.
