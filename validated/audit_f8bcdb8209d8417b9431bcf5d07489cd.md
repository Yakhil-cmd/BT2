The CVE describes a path-traversal/directory-listing flaw in a web admin panel driven by an HTTP `path` parameter — a class of bug tied to a filesystem-serving web application with unauthenticated/low-privilege HTTP requests. I searched for analogous attacker-controlled path construction reachable through Polkadot SDK's actual user-facing entry points (signed extrinsics, contract calls, XCM execution) and found none. All path-handling and directory-listing code identified is either:

- Node/CLI configuration and local operator tooling (base path, keystore path, workers path resolution) that is set by the node operator, not by any remote/unsigned/signed transaction sender [1](#0-0) [2](#0-1) [3](#0-2) 
- PVF worker sandboxing/artifact-cache path handling operating on validator-local, non-externally-supplied paths, with a `chroot`/`pivot_root` sandbox specifically hardening against path escape rather than exposing one [4](#0-3) [5](#0-4) 
- Build/benchmark/test tooling (fixtures `build.rs`, benchmarking-cli writers, subsystem-bench utils) that runs offline/at compile time, never exposed to on-chain input [6](#0-5) [7](#0-6) 

None of these paths are derived from a signed extrinsic parameter, a contract call argument, or an XCM instruction — there is no FRAME pallet call, precompile, or XCM transactor that takes a string and uses it to build a filesystem path exposed to the caller, so the "attacker-controlled path segment causing directory traversal/listing" invariant from CVE-2018-16820 has no reachable analog in the runtime/consensus-critical code paths.

		};
