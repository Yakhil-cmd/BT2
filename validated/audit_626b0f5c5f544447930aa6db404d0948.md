Based on the code trace, this vulnerability is confirmed to exist. Here is the analysis.

**The equality claimed to be broken:** `sum over stakers(get-earned-staker-rewards(signer, cycle, bond-index, staker))` should equal `get-earned(signer, cycle, bond-index)` (the signer's own total accrued, which bounds what was actually pulled into the contract via `claim-rewards`).

The divergence occurs because `settle-rewards` maintains **two separate snapshots** with different update conditions:
- `signer-rewards-per-token-settled-for-cycle` — used for the **signer's own** `get-earned`/`compute-earned-rewards`. Updated **unconditionally** every call.
- `signer-rewards-per-token-for-cycle` — used by **stakers'** `get-earned-staker-rewards`/`get-signer-rewards-per-token-for-cycle`. Updated **only inside `(if (> shares u0) ...)`**. [1](#0-0) 

When a signer's aggregate delegation drops below `SIGNER_SET_MIN_USTX`, `signer-shares-staked-for-cycle` is zeroed even though an individual staker's own `staker-shares-staked-for-cycle` entry is left untouched: [2](#0-1) 

While shares are zero, the global `rewards-per-token-for-cycle` continues to advance from *other* signers' contributions, and `settle-rewards`'s guard correctly prevents `signer-rewards-per-token-for-cycle` from moving during this window — but it also prevents it from moving on the very call that re-crosses the threshold, because `settle-rewards` reads shares *before* the calling function's own mutation: [3](#0-2) 

The frozen snapshot only catches up on some *later* settle call once shares are already nonzero, at which point it jumps directly from the stale pre-gap value to the current global value — retroactively crediting the entire gap (including the period the signer contributed zero shares) to whichever stakers currently hold `staker-shares-staked-for-cycle`. Meanwhile the signer's own `get-earned` (via the unconditionally-updated settled map) correctly earned nothing for that gap, since `compute-earned-rewards` multiplies by shares=0 during it: [4](#0-3) 

So `get-earned-staker-rewards` for a persisting staker computes `shares * (rpt_current_global_after_jump - staker_settled_before_gap)`, over-crediting them relative to what `get-earned`/`claim-rewards` actually pulled in for the signer over that same span: [5](#0-4) 

The repo already has a regression test for the closely related "always-zero-shares" case (no regain), which confirms the maintainers are aware of this bug class: [6](#0-5) 

But that test never exercises the "regain shares mid-cycle while an existing staker's share record was never zeroed" path, which is the exact scenario the question describes and which the guard does **not** protect against.

### Title
Signer-facing `signer-rewards-per-token-for-cycle` snapshot freezes during a below-threshold gap and retroactively over-credits stakers on regain, breaking `sum(staker earned) == signer earned` - (File: `stackslib/src/chainstate/stacks/boot/pox-5.clar`)

### Summary
`settle-rewards` only advances the staker-facing `signer-rewards-per-token-for-cycle` snapshot when the signer currently has nonzero shares, while the signer's own `signer-rewards-per-token-settled-for-cycle` snapshot advances unconditionally. When a signer's aggregate delegation dips below `SIGNER_SET_MIN_USTX` for part of a cycle (zeroing `signer-shares-staked-for-cycle`) and later regains it while an existing staker's individual `staker-shares-staked-for-cycle` entry was never zeroed, the staker-facing snapshot jumps straight from its pre-gap value to the post-gap global value on the next settle, retroactively crediting the staker for a period the signer contributed zero shares.

### Finding Description
`settle-rewards` (`stackslib/src/chainstate/stacks/boot/pox-5.clar:2530-2574`) computes the signer's own earned via `signer-rewards-per-token-settled-for-cycle`, updated unconditionally, but only writes `signer-rewards-per-token-for-cycle` — the value stakers read through `get-earned-staker-rewards` → `get-signer-rewards-per-token-for-cycle` — when `shares > u0`. `remove-staker-from-signer-for-cycle` zeroes `signer-shares-staked-for-cycle` for the signer when aggregate delegation drops below `SIGNER_SET_MIN_USTX`, without touching the remaining/other individual staker's `staker-shares-staked-for-cycle`. During the ensuing zero-shares window, the global `rewards-per-token-for-cycle` keeps advancing from other signers' contributions (correctly excluding this signer from `total-shares-staked-for-cycle`). When the signer regains shares (e.g. a new staker registration or bond claim pushes delegation back over threshold), `add-staker-to-signer-for-cycle`/`update-claimable-rewards` calls `settle-rewards` while shares are still (momentarily) zero, so the guard again skips the update. Only on a later call, once shares are nonzero, does `signer-rewards-per-token-for-cycle` jump directly to the then-current global value — retroactively crediting the entire gap to whatever `staker-shares-staked-for-cycle` currently exists, including a staker who never left and whose shares should not have earned during the zero-contribution gap. This is reachable purely by an unprivileged attacker orchestrating their own stake/registration timing to straddle the threshold boundary within a single cycle; no privileged role is required. No existing guard (`verify-not-prepare-phase`, `validate-no-reentrancy`, `check-pox-lock-period`, etc.) inspects this snapshot divergence.

### Impact Explanation
The identity `sum(staker earned for signer,cycle) == signer's total-rewards claimed for that cycle` is broken: a staker can be over-credited sBTC that the signer never actually pulled into the contract for that window, while the signer's own `get-earned`/`claim-rewards` correctly reflects zero for the gap. This produces either stranded sBTC with no owner (if the signer under-collects relative to what other, uninvolved signers' stakers should have gotten) or double-assignment of the same reward pool slice to two different stakers' claims, matching the Critical impact category (double-counting a reward / unbacked claim against pooled sBTC).

### Likelihood Explanation
Requires: a signer whose aggregate delegation crosses below `SIGNER_SET_MIN_USTX` and then back above it within the same reward cycle, with at least one staker whose individual share record persists across that dip (i.e., they are not the staker who caused the dip). This is fully attacker-controllable via ordinary `stake`/`register-for-bond`/`claim-rewards` calls timed within a cycle, at the cost of only the attacker's own STX/sBTC, and is repeatable every cycle in which the threshold-crossing pattern can be engineered.

### Recommendation
Decouple the two snapshots' semantics or make `signer-rewards-per-token-for-cycle` track the global rpt at the exact moment the signer's shares transition, rather than gating the write on the *current* shares value alone. Concretely, `settle-rewards` should record the rpt increment attributable only to the interval the signer actually held nonzero shares (e.g. maintain a running `earned` accumulator independent of the shares check, and expose per-staker "earned since" via that accumulator rather than a frozen `rpt` snapshot that can silently skip a settlement point), so a staker's earned computation can never span a gap during which the signer contributed zero shares to the global pool.

### Proof of Concept
Integration test plan (Clarity/vitest style, extending `contrib/core-contract-tests/tests/pox-5/pox-5.test.ts`):
1. Register signer S with two STX-only stakers: staker Y at an amount that alone is below `SIGNER_SET_MIN_USTX`, and staker Bob whose addition pushes S over threshold.
2. Call `calculate-rewards` mid-cycle so global `rewards-per-token-for-cycle` for `none` bond-index advances to `R1`, and assert `getSignerRewardsPerTokenForCycle(S, cycle, none) == R1`.
3. Unstake/remove Bob so S's aggregate delegation drops below threshold; assert `getSignerSharesStakedForCycle(S, cycle, none) == 0` while `getStakerSharesStakedForCycle(Y, cycle, none, S) > 0`.
4. Fund more sBTC and call `calculate-rewards` again so global rpt advances to `R2` (attributable to other signers only).
5. Add a new staker Z to S, pushing delegation back over threshold; then trigger another settle (e.g. `claim-rewards` by S).
6. Assert on both sides of the equality:
   - `signerClaimedTotal = sum of FtTransferEvent amounts from S's claim-rewards / claim-staker-rewards flow attributable to cycle`
   - `stakerEarnedSum = getEarnedStakerRewards(Y, cycle, none) + getEarnedStakerRewards(Z, cycle, none)`
   - Assert `stakerEarnedSum == signerClaimedTotal` (should fail on unfixed code, with `stakerEarnedSum` including Y's spurious `shares_Y * (R2 - R1)` credit that S never earned).
