## Title
Cross-tenant stack lookup: HMAC-verified org login never checked against `repository.full_name` used for the `Stack` lookup - (File: app/models/shipit/webhooks/handlers/handler.rb)

## Summary
`Webhooks::Handlers::Handler#stacks`/`#repository_name` resolve the target `Stack` purely from the attacker-controlled `repository.full_name` JSON field, while `WebhooksController#verify_signature` selects which `GitHubApp` secret to check the HMAC against using a *different*, independently attacker-controlled field, `repository.owner.login`. Because the two fields are never cross-checked, an operator of any GitHub App configured in this Shipit instance (e.g. `attacker-org`) can sign an arbitrary payload with their own known webhook secret while setting `repository.full_name` to `victim-org/victim-repo`, causing any `Handler` subclass to operate on the victim's `Stack`/`Commit` records.

## Finding Description
The broken binding, stated as an equality that the code implicitly assumes but never enforces:

`params.dig('repository', 'owner', 'login')` (used in `WebhooksController#repository_owner`, `app/controllers/shipit/webhooks_controller.rb:59-62`, to select `Shipit.github(organization: repository_owner)` for HMAC verification) **==** the owner segment of `payload.dig('repository', 'full_name')` (used in `Handler#repository_name`, `app/models/shipit/webhooks/handlers/handler.rb:36-38`, to do `Repository.from_github_repo_name(repository_name)`).

These are two separate, independently attacker-settable JSON keys in the same POST body. `verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) only proves that the raw body was HMAC-signed with the secret configured for whichever org name appears in `repository.owner.login`/`organization.login`. It does **not** re-derive or validate that value against `repository.full_name`. `Handler#stacks` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) then does a raw DB lookup:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end
def repository_name
  payload.dig('repository', 'full_name')
end
```
with zero reference to `repository_owner` or the org that was actually verified.

Exploit flow:
1. Attacker legitimately owns/operates a GitHub App configured in this Shipit instance's `secrets.yml` under `attacker-org` (per `docs/setup.md` multi-app setup, `test/dummy/config/secrets_double_github_app.yml`), and therefore knows that app's `webhook_secret`.
2. Attacker POSTs to `/webhooks` with `X-Github-Event: push` (or `check_suite`, or any `pull_request` action), body containing `repository.owner.login = "attacker-org"` and `repository.full_name = "victim-org/victim-repo"`, and computes `X-Hub-Signature` correctly using the `attacker-org` webhook secret they legitimately possess.
3. `verify_signature` picks `Shipit.github(organization: "attacker-org")`, verifies the HMAC against the attacker's own known secret, succeeds.
4. The handler (e.g. `PushHandler`, `app/models/shipit/webhooks/handlers/push_handler.rb`) is invoked; `stacks` resolves via `Repository.from_github_repo_name("victim-org/victim-repo")`, hitting the victim's real `Stack`, and calls `stack.sync_github(expected_head_sha: params.after)`, or `CheckSuiteHandler` schedules `schedule_refresh_check_runs!` on victim commits, or PullRequest handlers (`OpenedHandler`, `LabeledHandler`, `ClosedHandler`, etc.) archive/unarchive/create review stacks belonging to the victim.

Existing guards do not close the gap: `verify_signature` only authenticates *which org's secret signed the bytes*, not *which repository the payload logically describes*; `drop_unhandled_event` only checks the event type exists; `ExplicitParameters` schemas only validate types/presence of `repository.full_name`, not its relationship to `repository.owner.login`; and `Repository.from_github_repo_name` (`app/models/shipit/repository.rb:53-56`) is a pure `owner/name` string lookup with no tenant check.

## Impact Explanation
Any org onboarded as a legitimate GitHub App tenant of a shared Shipit instance can, with a single crafted POST, cause writes against another tenant's `Stack`/`Commit`/`ReviewStack` records: forcing `GithubSyncJob` runs against a victim stack (`Stack#sync_github` in `app/models/shipit/stack.rb`), archiving/unarchiving a victim's review stack (`LabeledHandler#handle`, `ClosedHandler#process`), or triggering check-run refresh cycles on victim commits (`CheckSuiteHandler#process`). This is a cross-tenant data-integrity/authorization violation: a payload "for" the attacker's org mutates records that belong to a different, unrelated tenant's repository, matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team"). It is fully repeatable against any repository name present in the shared Shipit database, and the primitive is inherited by every `Handler` subclass (`PushHandler`, `CheckSuiteHandler`, all `PullRequest::*Handler` classes) — a single root cause with broad blast radius across all tenants sharing the instance.

## Likelihood Explanation
Requires the Shipit instance to be configured for multiple GitHub organizations (documented and supported feature, `docs/setup.md` "Using Multiple Github Applications"), and requires the attacker to control at least one of those onboarded orgs/apps (i.e., know its own `webhook_secret`, which app owners set themselves in GitHub App settings). It also requires the victim's repository/stack to exist in the shared instance. Given those realistic preconditions, the attack costs a single crafted HTTP POST with a correctly-computed HMAC over an otherwise arbitrary JSON body — no other secret, session, or privileged role is needed, and it is trivially repeatable against any `owner/name` string.

## Recommendation
In `Handler#stacks`/`#repository_name` (or centrally in `WebhooksController#create`), require that the org used to verify the webhook signature equals the owner segment of `repository.full_name` before doing the `Stack`/`Repository` lookup — e.g., pass the verified `repository_owner` into each `Handler.call` and assert `repository_name.split('/').first.casecmp?(verified_owner)`, rejecting (422/404) otherwise. Equivalently, verify by looking up the `GitHubApp` from `repository.full_name`'s owner segment instead of trusting a separately supplied `repository.owner.login`.

## Proof of Concept
Minitest, no live GitHub:
```ruby
# test/models/shipit/webhooks/handlers/handler_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class HandlerCrossTenantTest < ActiveSupport::TestCase
        test "PushHandler resolves stacks purely from repository.full_name, ignoring verifying org" do
          victim_repo = shipit_repositories(:shipit) # owner/name != "attacker-org"
          victim_stack = victim_repo.stacks.first

          payload = {
            "ref" => "refs/heads/#{victim_stack.branch}",
            "after" => "deadbeef",
            "repository" => {
              "full_name" => victim_repo.github_repo_name, # e.g. "victim-org/victim-repo"
              "owner" => { "login" => "attacker-org" }      # verifying org != owner segment above
            }
          }

          # Equality under test (should hold for the binding to be safe, but does not):
          verifying_org = payload.dig("repository", "owner", "login")
          owner_segment = payload.dig("repository", "full_name").split("/").first
          refute_equal verifying_org, owner_segment # demonstrates divergence attacker controls

          handler = PushHandler.new(payload)

          Stack.any_instance.expects(:sync_github).with(expected_head_sha: "deadbeef")
          handler.process # succeeds and mutates the victim stack despite verifying_org mismatch
        end
      end
    end
  end
end
```
This demonstrates `Handler#stacks`/`#repository_name` never receive or check the verifying org, and that a payload whose `repository.owner.login` diverges from the owner segment of `repository.full_name` still resolves and mutates the victim `Stack`.
