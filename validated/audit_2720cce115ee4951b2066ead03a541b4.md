### Title
Bounced/refunded AA funds are misdirected to the alphabetically-first author instead of the actual coin owner in multi-authored triggers - ([File: aa_composer.js])

### Summary
`getTrigger()` in `aa_composer.js` hard-codes the "owner" of an AA trigger to `objUnit.authors[0].address`, i.e. the address that happens to sort first among the unit's authors. Both the framework-level `bounce()` function and every AA template that refunds via `trigger.address` (as intended and documented by ocore itself, e.g. `just_a_bouncer.oscript`, `bouncer_infinite_cycle.oscript`) send the refunded/bounced coins exclusively to this single address. Because `validatePaymentInputsAndOutputs` allows the payment's input coins to be owned by *any* of the unit's multiple authors (not just `authors[0]`), a multi-authored trigger unit whose inputs actually belong to a different co-author can have its bounce refund sent to the wrong person entirely.

### Finding Description
`getTrigger(objUnit, receiving_address)` builds the AA trigger object as: [1](#0-0) 

`trigger.address = objUnit.authors[0].address` — this is simply the first author in the unit, and `validateAuthors` requires that `arrAuthors` be sorted lexicographically by address: [2](#0-1) 

Nothing in `validateAATrigger` restricts the number of authors of a triggering unit — it only limits the number of AA addresses targeted and the number of outputs per asset to a given AA: [3](#0-2) 

Meanwhile, the payment-input ownership check in `validatePaymentInputsAndOutputs` only requires that the spent output's owner be *among* the unit's authors, not that it be `authors[0]`: [4](#0-3) 

This means a single unit can be co-authored/co-signed by two (or more) unrelated addresses, e.g. address `A` (which sorts first) and address `B` (which actually owns/spends the coins that fund the payment output sent to an AA). When the AA subsequently reverts the trigger, the framework's built-in bounce logic sends the refund to `trigger.address`, i.e. to `A`, not to `B` who actually supplied the funds: [5](#0-4) 

The same problem occurs for AA-authored refund logic that explicitly uses `trigger.address`, which is a documented and expected pattern throughout the AA ecosystem (bouncer templates, ICO refund templates, marketplace change outputs, etc.): [6](#0-5) [7](#0-6) 

In all of these cases, the code implicitly assumes that the single address recorded as `trigger.address` is "the" economic owner of the funds sent with the trigger — exactly the same class of assumption flagged in the external report, where the receiver address on the destination chain was assumed to be controlled by the same party who supplied the funds on the source chain. Here, the assumption fails whenever a payment to an AA is funded via a multi-authored unit where the actual coin owner is not the lexicographically-first author.

### Impact Explanation
Any AA-based service on Obyte that refunds or bounces funds based on `trigger.address` (which is the standard, framework-recommended and framework-default pattern used both by the built-in `bounce()` and virtually all AA templates) will send the money to the wrong, unrelated address if the triggering payment is composed as a multi-authored unit whose actual paying address differs from `authors[0]`. This causes a real, unrecoverable loss of funds to the true payer, who never receives their bounced/refunded coins, while a completely different co-author (who may not even control any of the spent coins) receives them instead. Because base-layer wallets can freely construct multi-authored, multi-source payment units to any AA address, an attacker (or simply a legitimate co-signing setup) reaching the exact same result described in the analog report — misdirected user funds during a fallback/refund flow — is possible without any privileged access, purely from a single crafted trigger unit.

### Likelihood Explanation
Exploitability requires only the ability to post a normal, valid multi-authored unit to the network with a payment to an AA address, and to trigger a bounce/refund condition in that AA (either a native protocol-level bounce for insufficient balance/invalid trigger, or any AA template logic that intentionally refunds unspent/erroneous payments to `trigger.address`, which is an extremely common and idiomatic AA pattern). No special privileges, hub/witness cooperation, or protocol bugs beyond normal usage are needed — an ordinary user (or attacker) fully controls unit composition and can choose which address sorts first among authors while still spending coins owned by a different author.

### Recommendation
Do not collapse a multi-authored trigger's identity into `authors[0].address`. Track, per asset/payment, which specific author address(es) actually supplied the input coins that fund the output being credited to the AA, and use that information (or reject multi-authored trigger units outright, forcing a single-authored/shared-address model) when computing refund/bounce destinations in `getTrigger()` and `bounce()`. At minimum, disallow multi-authored units from directly triggering AAs (mirroring the restriction already imposed for AA response units, `arrAuthors.length !== 1`), so `trigger.address` is guaranteed to correspond to the sole economic owner of the funds.

### Proof of Concept
1. Construct a valid multi-authored unit with two authors, `A` (address that sorts alphabetically before `B`) and `B`.
2. Have the payment message's base-asset input(s) be owned solely by `B` (allowed per `validatePaymentInputsAndOutputs`, since ownership only needs to be "among" the authors), with the payment output directed to an AA address.
3. `getTrigger()` sets `trigger.address = A` (author[0]), even though `B` supplied all the funds.
4. Cause the AA to bounce (e.g., trigger an unmet condition or invalid data so that `bounce()` executes, or trigger a template with an explicit `{address: "{trigger.address}", ...}` refund message).
5. The refunded bytes/asset are sent entirely to `A`, while `B`, the actual owner of the spent funds, receives nothing — resulting in a permanent loss of `B`'s funds to an unrelated co-author address.

function getTrigger(objUnit, receiving_address) {
	var trigger = { address: objUnit.authors[0].address, unit: objUnit.unit, outputs: {} };
	if ("max_aa_responses" in objUnit)
		trigger.max_aa_responses = objUnit.max_aa_responses;
	objUnit.messages.forEach(function (message) {
		if (message.app === 'data' && !trigger.data) // use the first data message, ignore the subsequent ones
			trigger.data = message.payload;
		else if (message.app === 'payment' && message.payload) {
			var payload = message.payload;
			var asset = payload.asset || 'base';
			payload.outputs.forEach(function (output) {
				if (output.address === receiving_address) {
					if (!trigger.outputs[asset])
						trigger.outputs[asset] = 0;
					trigger.outputs[asset] += output.amount; // in case there are several outputs
				}
			});
		}
	});
	if (Object.keys(trigger.outputs).length === 0)
		throw Error("no outputs to " + receiving_address);
	return trigger;
}
