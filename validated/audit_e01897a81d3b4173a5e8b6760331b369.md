## Finding [1](#0-0) [2](#0-1) 

### Title
Stack-scoped API token can read CI/build status of any stack via `CCMenuController` - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::BaseController` restricts which stacks an `ApiClient` may access through the `stacks` helper, which returns only the stack the client is bound to when `current_api_client.stack_id?` is true. [3](#0-2)  `CCMenuController`, however, overrides the `stack` accessor to resolve `Stack.from_param!(params[:stack_id])` directly, completely bypassing that scoping. [4](#0-3) 

### Finding Description
This is the same class of bug as the referenced report: a security invariant (the giant pool's ETH accounting/receive-capability binding, or here, the binding of "the stack a token authorizes" to "the stack the endpoint actually touches") is enforced in one code path but silently dropped in a sibling path.

`ApiClient#check_permissions!` only verifies that the requested `operation:scope` string (e.g. `read:stack`) is present in the client's `permissions` array — it never checks *which* stack is being accessed. [5](#0-4)  The actual per-stack restriction is implemented separately, only inside `BaseController#stacks`/`#stack`. [1](#0-0)  `CCMenuController` is a subclass of `BaseController` and uses `require_permission :read, :stack`, but it defines its own `stack` method that ignores `current_api_client.stack_id` entirely and just looks up `params[:stack_id]` globally. [6](#0-5) 

Equality that should hold but doesn't:
`stack accessible via CCMenuController#show` == `stacks scoped to current_api_client.stack_id` (when the client is stack-scoped)

Before the request: an `ApiClient` record exists with `stack_id` set to stack A and `permissions` containing `read:stack` (this is the documented intended pattern — see test "an api client scoped to a stack will only see that one stack" for `StacksController`). [7](#0-6) 

After the request: that same token, presented to `GET /api/stacks/:stack_id/ccmenu` with `stack_id` = stack B (any other stack), passes `require_permission :read, :stack` (since that check is permission-list only) and then resolves `stack` to stack B directly via `Stack.from_param!`, rendering stack B's deploy/build status.

### Impact Explanation
This breaks the "stack a token authorizes versus a stack it touches" binding explicitly called out as in-scope. An API client deliberately scoped to a single stack — the mechanism used to limit third-party integrations (e.g. CI dashboards, status badges) to one stack's data — can read the CI/build status (`lastBuildStatus`, `lastBuildLabel`, `activity`, lock status, etc., see the `CCMenu` view) of every other stack in the Shipit instance. This is an unauthorized cross-stack read of stack state, matching the High-severity criterion "escalation into authorization... unauthenticated read of stack state, task streams or deploy output" (here, escalation past the intended per-stack authorization scope).

### Likelihood Explanation
Any holder of a legitimately-issued, stack-scoped `ApiClient` token (a routine credential meant to be handed to low-trust integrations/consumers, exactly the kind of credential that is supposed to be constrained to one stack) can trigger this with a single unauthenticated-scope-widening HTTP GET, changing only the `stack_id` path parameter. No special privilege beyond holding an ordinary scoped token is required, and the flaw is a simple, always-reachable method override.

### Recommendation
Remove the `stack` override in `CCMenuController`, or make it delegate to the scoped `stacks` collection from `BaseController` (i.e. `stacks.from_param!(params[:stack_id])`) so stack-scoped clients cannot resolve stacks outside their `stack_id`.

### Proof of Concept
1. Create `ApiClient` A with `stack_id: <stack_1.id>` and `permissions: ['read:stack']`.
2. Using A's `authentication_token`, call:
   `GET /api/stacks/<stack_2.to_param>/ccmenu` (any other, unrelated stack)
3. Observe `require_permission :read, :stack` passes (permission list only) and the response renders `stack_2`'s CCMenu XML (build status, activity, etc.), even though the token is only supposed to have visibility into `stack_1`.
