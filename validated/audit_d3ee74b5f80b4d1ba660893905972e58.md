### Title
Cross-repository `Commit` status forgery via unscoped SHA lookup in `StatusHandler#process` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits solely by `sha` with `Commit.where(sha: params.sha)` and never restricts the result to the stacks/repository named in the verified webhook payload, unlike the base `Handler` class's `stacks`/`repository_name` helpers which exist for exactly this purpose. A webhook that is validly signed for one GitHub organization/repository can therefore write a fabricated commit status onto `Commit` rows belonging to a completely unrelated stack, as long as the SHAs collide.

### Finding Description
The binding that should hold is: `repository_name` derived from the verified webhook payload (`payload.dig('repository','full_name')`, exposed via `Handler#repository_name`/`Handler#stacks`) == the repository owning every `Commit` row mutated by the handler. `Shipit::Webhooks::Handlers::StatusHandler#process` breaks this binding: [1](#0-0) 

It calls `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with no reference to `stacks` or `repository_name`, even though the base class provides exactly this scoping mechanism: [2](#0-1) 

`WebhooksController#verify_signature` authenticates the payload only at the GitHub **organization** level — it resolves `Shipit.github(organization: repository_owner)` and checks the HMAC signature against that organization's single `webhook_secret`: [3](#0-2) [4](#0-3) 

This confirms the request genuinely came from GitHub for *some* repository in that organization, but it does not bind the payload to the specific repository/stack whose commits are mutated. Because `StatusHandler` never re-derives and filters by `repository_name`/`stacks`, any repository within the same organization (one that shares the app installation and thus the org-wide `webhook_secret`) can emit a `status` event whose `sha` collides with a commit tracked under a different stack in that same org, and `Commit#create_status_from_github!` will be invoked on that victim commit: [5](#0-4) 

None of the existing guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema) check repository/stack ownership of the target `Commit`; they only validate the schema and the organization-level signature. The gap is specific to `StatusHandler` — the base `Handler` class's `stacks`/`repository_name` pattern (used by other handlers in this module) is simply not invoked here.

### Impact Explanation
Within a Shipit deployment where a single GitHub App/organization is shared across multiple repositories/stacks (the common multi-stack setup this engine supports), an attacker who can trigger a `status` webhook for *any* repository in that org (e.g., a repo they have push/CI access to) can inject arbitrary CI state (`success`, target URL, description, context) onto commits of a *different* stack/repository in the same org, provided a SHA collision (shared history via fork, cherry-pick, or empty-tree/rebase collisions) exists. Since `deployable?` and blocking-status logic on `Commit` consult these injected statuses, this can influence deploy-gating decisions for a repository the attacker does not own — a cross-tenant write matching the "payload for one repository mutating another's stack/commit" Critical category.

### Likelihood Explanation
Exploitability requires: (1) a Shipit deployment where multiple repositories/stacks are served by the same GitHub App/organization config (common for orgs adopting Shipit across teams), (2) the attacker being able to trigger `status` webhooks from a repository within that same org (e.g., pushing code with CI hooked up, or a fork/rebase producing a SHA collision with the victim's tracked commit), and (3) a genuine SHA match between the two repositories' commit histories. SHA collisions across genuinely unrelated repositories require shared git history (forks, cherry-picks, common base commits) rather than arbitrary attacker choice, which somewhat limits but does not eliminate the practical exploitation surface (e.g., forks of the same upstream tracked as separate Shipit stacks are a realistic scenario).

### Recommendation
Scope `StatusHandler#process` to the repository/stacks referenced in the payload, mirroring the pattern already provided by `Handler#stacks`, e.g. restrict the query to `Commit.where(sha: params.sha, stack_id: stacks.select(:id))` (or filter per-commit via `commit.stack.repository == expected repository`) before calling `create_status_from_github!`.

### Proof of Concept
Minitest plan (integration, no live GitHub):
1. Create two stacks/repositories `stack_a` (victim) and `stack_b` (attacker-owned), each with distinct `github_hooks` fixtures pointing at the *same* GitHub organization/app config (shared `webhook_secret`).
2. Create `Commit` rows in both stacks sharing the identical `sha` value.
3. Stub `GithubHook.any_instance.stubs(:verify_signature).returns(true)` (or mock `Shipit.github(organization:).verify_webhook_signature` to return true), simulating a validly-signed webhook originating from repository B.
4. POST a `status` event to `/webhooks` with `repository.full_name` set to stack B's repo and `sha` equal to the shared SHA, `state: 'success'`.
5. Assert `stack_a`'s `Commit#statuses` changed (`assert_difference 'stack_a_commit.statuses.count', 1`) even though the payload's `repository.full_name` never named stack A — demonstrating the missing binding between `repository_name` (payload) and the stack whose `Commit` was mutated.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
