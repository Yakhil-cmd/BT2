### Title
Cross-organization webhook forgery via organization-scoped signature routing with optional `webhook_secret` - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController` selects *which* GitHub App configuration (and therefore which `webhook_secret`) is used to verify an inbound webhook's signature based on a field taken from the **unauthenticated** request body itself, then dispatches handlers using the **entire** unauthenticated body, including fields that identify a different repository/stack than the one used to pick the signing secret.

### Finding Description
`verify_signature` computes `repository_owner` and uses it to look up the GitHub App/organization config *before* the signature has been validated: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight from the attacker-supplied JSON body (`params.dig('repository', 'owner', 'login')` or `organization.login`), with no relation yet established to any verified identity. `Shipit.github(organization: repository_owner)` then returns the `GitHubApp` instance for that org, and its `webhook_secret` is used for HMAC verification: [3](#0-2) 

Critically, when an org's `webhook_secret` is blank/unset — an explicitly supported configuration, shown in both the shipped documentation and test fixtures (`webhook_secret: # nil`) — `verify_webhook_signature` returns `true` unconditionally: [4](#0-3) [5](#0-4) [6](#0-5) 

Once `verify_signature` passes, `create` parses and dispatches the *entire raw body* to the registered handlers for the event, without re-checking that the repository/stack targeted by the payload actually belongs to the organization whose secret authorized the request: [7](#0-6) 

This breaks the binding: **the organization that authenticated the webhook (via `repository_owner` → selected `webhook_secret`) ≠ the repository/stack that the handler subsequently acts on** (identified independently via `repository.full_name`, `sha`, etc., in the same untrusted payload). In a multi-org Shipit deployment (documented and tested as a first-class configuration in `docs/setup.md` "Using Multiple Github Applications" and `test/dummy/config/secrets_double_github_app.yml`), if even one configured organization has no `webhook_secret` set, an unprivileged network attacker can:
1. Set `X-Github-Event` and craft a JSON body where `repository.owner.login` (or `organization.login`) equals the org with the blank secret — trivially passing `verify_signature`.
2. Populate the rest of the payload (`repository.full_name`, `sha`, `state`, etc.) to target a stack belonging to a *different, properly secured* organization.
3. Handlers such as the push/status handlers act on this forged, "verified" payload for a repository outside the org that was actually authenticated.

### Impact Explanation
This allows forging events (push, commit status, deployable/merge status, membership, pull_request) attributed to a fully-secured GitHub organization, without ever presenting a valid signature for that organization. Depending on the handler, this can trigger `GithubSyncJob` enqueuing, inject fabricated commit statuses that gate deploy/merge eligibility, or manipulate team/user membership records — i.e., an unauthorized deploy/merge path driven by forged status data, which falls under the "unauthorized deploy, rollback or merge" Critical-tier impact.

### Likelihood Explanation
Requires no credentials, no repository write access, and no privileged account — only that the deployment is configured with more than one GitHub organization and that at least one has no `webhook_secret` set (both are documented, supported, and tested configurations in this engine, not a hypothetical misuse). Given `webhook_secret` is explicitly marked optional throughout the setup docs and fixtures, this is a realistic operational state, not an edge case requiring host misconfiguration outside documented use.

### Recommendation
- Do not use attacker-supplied payload fields to select the verification secret before the signature is verified.
- Require `webhook_secret` to be present for every configured organization (fail closed rather than `return true unless webhook_secret`), or bind the verified organization identity to the specific repository/stack acted upon downstream, rejecting payloads where `repository.full_name`'s owner doesn't match the org used for signature verification.

### Proof of Concept
1. Configure Shipit with two organizations per `docs/setup.md`'s multi-app example: `OrgA` (has `webhook_secret` set) and `OrgB` (no `webhook_secret`, i.e., `nil`).
2. Send `POST /webhooks` with `X-Github-Event: push`, no valid `X-Hub-Signature` for `OrgA`, and body:
```json
{
  "repository": { "owner": { "login": "OrgB" }, "full_name": "OrgA/protected-repo" },
  "after": "<attacker-chosen-sha>",
  "ref": "refs/heads/master"
}
```
3. `repository_owner` resolves to `OrgB`; `Shipit.github(organization: "OrgB").verify_webhook_signature` returns `true` (blank secret) regardless of the (missing/garbage) signature header.
4. `create` dispatches the full payload to the push handler, which resolves the stack via `repository.full_name = "OrgA/protected-repo"`, enqueuing `GithubSyncJob` for `OrgA`'s protected repository — despite the request never having been signed by `OrgA`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
