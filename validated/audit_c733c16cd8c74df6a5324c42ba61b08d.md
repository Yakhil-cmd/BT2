### Title
Cross-organization status forgery via multi-app webhook signing lets one authorized GitHub org set CI status/`deployable?` for any other org's commits - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
Shipit supports mounting multiple independent GitHub Apps, one per organization, each with its own `webhook_secret` [1](#0-0) . `WebhooksController#verify_signature` picks which org's secret to validate the HMAC against using `repository_owner`, itself read from the attacker-controlled JSON body (`repository.owner.login`, falling back to `organization.login`) [2](#0-1) [3](#0-2) . Once the signature check passes, `StatusHandler#process` looks up commits solely by `sha` — with **no scoping to the authenticated organization or its repositories at all** — and writes a GitHub-status record to whatever `Commit` matches that sha anywhere in the Shipit instance: [4](#0-3) .

### Finding Description
This is the same class of bug as the referenced report: a one-shot authorization check ("this payload was signed by org X's secret") is trusted for an operation whose actual target ("which repository/commit gets mutated") is taken from a different, unverified part of the same payload, breaking the required invariant `authenticated_org == repo_owner_of(target_commit)`.

Concretely:
- `verify_signature` derives the signing organization from `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` and verifies the raw HMAC using `Shipit.github(organization: repository_owner).verify_webhook_signature` [5](#0-4) . Because the entire JSON body is attacker-supplied, `repository.owner.login` and any other field in the same body are independent and not cross-checked against each other.
- Other handlers (`PushHandler`, `CheckSuiteHandler`) correctly re-derive the target from `payload.dig('repository', 'full_name')` via `Handler#stacks`, which scopes to `Repository.from_github_repo_name(repository_name)&.stacks` [6](#0-5) [7](#0-6) [8](#0-7) .
- `StatusHandler`, however, does not use `stacks`/`repository_name` at all: it queries `Commit.where(sha: params.sha)` globally across the entire Shipit database and calls `commit.create_status_from_github!(params)` for every match [4](#0-3) .

So in a multi-org deployment (`docs/setup.md`'s "Using Multiple Github Applications" section, exercised in `test/dummy/config/secrets_double_github_app.yml`) [9](#0-8) , an attacker who legitimately controls the GitHub App installation for Organization A (and therefore knows Org A's `webhook_secret`) can:
1. Craft a raw `status` event body with `repository.owner.login` (or `organization.login`) = `"OrgA"` so it authenticates against Org A's `webhook_secret`.
2. Set `sha` to a commit belonging to a stack/repository owned by Organization B (a sha which is not secret — visible on public PR pages, commit URLs, CI badges, etc.).
3. Sign the whole raw body with Org A's `webhook_secret` and POST it to `/webhooks`.

`verify_signature` succeeds (Org A's secret matches Org A's own signed content), but `StatusHandler#process` writes the forged `state`/`description`/`target_url`/`context` as a new status onto Org B's commit, with no check that Org B ever authorized Org A's app.

### Impact Explanation
Commit status directly gates `Commit#deployable?` (`success? && !blocked?`) [10](#0-9) , and `add_status` triggers `stack.schedule_merges` when the new status is `pending` or `success` [11](#0-10) , and can trigger continuous deployment via `schedule_continuous_delivery` on later related commits [12](#0-11) . An attacker who only administers their own unrelated GitHub org's App installation can forge a "success" CI status on another organization's commit that they do not control, potentially unblocking that commit for merge-queue processing or continuous deployment — an unauthorized deploy/merge influenced by a party with no access to the victim repository. This satisfies the Critical/High bar of "an unauthorized deploy, rollback or merge."

### Likelihood Explanation
Requires only that the target Shipit instance is configured with the documented multi-organization GitHub App scheme and that the attacker administers (or has compromised) one of those orgs' App installations — a legitimate, unprivileged-relative-to-the-victim-org capability explicitly supported by this engine. The attacker needs no access to the victim's repository, GitHub App, or Shipit credentials, only the target commit sha (routinely public) and the ability to send a signed HTTP POST to `/webhooks`.

### Recommendation
`StatusHandler` (and any other handler using bare `params.sha`/global lookups) must scope its `Commit` lookup to the repository named in the authenticated payload, mirroring `Handler#stacks`/`repository_name`, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or joining through `Repository.from_github_repo_name(repository_name)`. More generally, `WebhooksController#verify_signature` should ensure the organization used to select the webhook secret is provably tied to the same repository entity subsequently used by every handler to select which `Stack`/`Commit` records get mutated, not merely to a same-named field elsewhere in an unauthenticated-until-verified payload.

### Proof of Concept
1. Configure Shipit with two orgs, `OrgA` and `OrgB`, each with a distinct `webhook_secret` (per `docs/setup.md`).
2. As an attacker who administers `OrgA`'s GitHub App (and thus its `webhook_secret`), build a JSON body:
```json
{
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgA/attacker-repo" },
  "sha": "<victim commit sha in OrgB/stack>",
  "state": "success",
  "context": "ci/forged"
}
```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(OrgA_webhook_secret, body)>`.
4. POST to `/webhooks` with `X-Github-Event: status`. `verify_signature` passes because it validates against `OrgA`'s secret using `repository_owner == "OrgA"` [13](#0-12) .
5. `StatusHandler#process` finds the commit in `OrgB`'s stack purely by `sha` and records the forged "success" status on it [4](#0-3) , potentially making that commit `deployable?` in `OrgB`'s stack.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
