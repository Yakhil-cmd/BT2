### Title
Uncaught `throw Error` on attacker-controlled amount in private (fixed-denomination) payment chain crashes the node - ([File: validation.js])

### Summary
A private-payment counterparty (any device that can send a private_payment/chat private-asset chain to a wallet) can craft a private payment chain for a private, fixed-denomination ("blackbyte"-style) asset in which a *previous* chain element's hidden output `amount` is not a valid positive integer. When the receiving node parses the chain, this attacker-controlled value is copied into `objValidationState.src_coin.amount` without being validated, and is later checked with an unconditional `throw Error(...)` (not routed through the normal `callbacks.ifError` path) inside `validatePaymentInputsAndOutputs`. Because this throw happens deep inside nested asynchronous callbacks with no surrounding `try/catch`, it becomes an uncaught exception that reaches Node's global `uncaughtException` handler, which deliberately re-throws to crash the process. This is directly analogous to CVE‑2015‑8739 (Wireshark IPMI dissector crashing the whole application via an assertion failure caused by improperly-validated remote data): unvalidated, attacker-supplied field data reaches a hard assertion/throw that aborts the entire application rather than being handled as a validation error.

### Finding Description
In `indivisible_asset.js`, `validatePrivatePayment()` builds the transfer input's `src_coin` directly from the *previous* private chain element supplied by the sender, without validating that the referenced hidden output's `amount` field is a valid positive integer: [1](#0-0) 

Specifically:
- `prev_hidden_output = objPrevPrivateElement.payload.outputs[input.output_index]` is only checked for existence ("no prev hidden output"), not for the validity of its `amount`.
- `objValidationState.src_coin = { src_output, denomination: payload.denomination, amount: prev_hidden_output.amount }` copies this unvalidated `amount` straight from attacker-controlled JSON.

This chain is processed element-by-element in `parsePrivatePaymentChain()`, where `prevElement = arrPrivateElements[i+1]` is taken from the *entire attacker-supplied array* before that later element is itself independently validated: [2](#0-1) 

The `src_coin` is then consumed in `validation.js`'s `validatePaymentInputsAndOutputs()`, which enforces integrity with **unconditional `throw Error(...)`** statements rather than routing failures through the `callback(...)` error convention used everywhere else in that function: [3](#0-2) 

Because `src_coin.amount` was never checked to be a positive integer before this point, a malicious/malformed value (e.g. a string, `0`, negative number, or float) makes `isPositiveInteger(src_coin.amount)` fail and triggers `throw Error("no src coin amount")`. This call happens many levels deep inside nested `async`/DB-query callbacks (`network.handleOnlinePrivatePayment` → `privatePayment.validateAndSavePrivatePaymentChain` → `indivisibleAsset.validateAndSavePrivatePaymentChain` → `parsePrivatePaymentChain` → `validatePrivatePayment` → `validation.validatePayment` → `validatePaymentInputsAndOutputs`), none of which wrap this call in a `try/catch`.

The reachable entry point for an untrusted private-payment counterparty is `wallet.handlePrivatePaymentChains`, which forwards attacker-supplied `arrChains` to `network.handleOnlinePrivatePayment`: [4](#0-3) 

Any uncaught exception anywhere in the process is handled globally, and the handler intentionally re-throws to terminate the process: [5](#0-4) 

This mirrors the root cause pattern of CVE‑2015‑8739: a dissector/validator trusts a remotely supplied field without adequately validating it, and hits a hard assertion/abort that kills the whole process instead of failing gracefully.

### Impact Explanation
Any device capable of sending a private-payment (blackbyte/fixed-denomination private asset) chain to a node/wallet — i.e. an ordinary private-payment counterparty, not a privileged operator or hub — can remotely crash that node's process. Repeated delivery of such malformed chains provides a reliable, low-cost denial-of-service against any wallet/node that processes incoming private payments for private fixed-denomination assets, disrupting normal operation (inability to process transactions, node restart required) and potentially destabilizing coordinated network operation if targeted broadly. This satisfies the required "network unable to confirm new units / node crash" impact bar for a Medium-severity finding.

### Likelihood Explanation
The path is reachable by any private-payment counterparty without special privileges, keys, or timing — it only requires constructing a private payment chain JSON with an invalid `amount` in the second-from-head element's hidden output for a private, fixed-denomination asset, then sending it to the victim via the standard private-payment/chat delivery mechanism (`wallet.handlePrivatePaymentChains` → `network.handleOnlinePrivatePayment`). No cryptographic proof forgery is required for this particular field because the flaw is in field type/range validation, not spend-proof or signature verification. This makes the bug straightforward and repeatable to trigger, similar in ease to the original Wireshark issue (any crafted packet reaching the dissector).

### Recommendation
- Validate `prev_hidden_output.amount` (and any other numeric fields taken from `objPrevPrivateElement`) with `ValidationUtils.isPositiveInteger` immediately when building `objValidationState.src_coin` in `indivisible_asset.js`, and return `callbacks.ifError(...)` on failure instead of allowing an unchecked value to propagate.
- In `validation.js`'s `validatePaymentInputsAndOutputs`, convert the defensive `throw Error("no src_coin")`, `"no src_output"`, `"no denomination in src coin"`, and `"no src coin amount"` checks into normal `callback(...)` validation errors (or wrap the whole private-asset validation call chain in a top-level `try/catch` that converts unexpected exceptions into validation errors) so that malformed/attacker-controlled private payment data can never crash the process.
- Audit other `throw Error(...)` statements reachable from privately/externally supplied unit or payment data (e.g. within `buildPrivateElementsChain`, `validatePaymentInputsAndOutputs`) for the same "should be a recoverable validation failure but is implemented as a hard throw" pattern.

### Proof of Concept
1. Attacker (private-payment counterparty) prepares a private, fixed-denomination asset payment chain `arrPrivateElements` consisting of at least two chain elements, where:
   - Element `i` is a `transfer` input referencing element `i+1` (`input.unit`, `input.message_index`, `input.output_index`) as its source, matching required linkage checks.
   - Element `i+1`'s `payload.outputs[input.output_index].amount` is set to an invalid value, e.g. `"NaN"`, `-1`, or `0`, instead of a positive integer.
2. Attacker sends this chain to the victim wallet via the normal private-payment delivery mechanism (chat/device message → `wallet.handlePrivatePaymentChains` → `network.handleOnlinePrivatePayment`).
3. The victim node parses the chain: `parsePrivatePaymentChain` processes element `i` before fully re-validating element `i+1`'s own `amount` field, copies the malicious `amount` into `objValidationState.src_coin.amount`, and calls `validation.validatePayment` → `validatePaymentInputsAndOutputs`.
4. `isPositiveInteger(src_coin.amount)` fails, `throw Error("no src coin amount")` executes with no enclosing `try/catch`, the exception is uncaught, `process.on('uncaughtException')` logs it and re-throws, and the victim's node process crashes.
