### Title
Cross-Repository Status Injection via Organization/Repository Binding Mismatch in Webhook Signature Verification - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate an inbound GitHub webhook using the organization derived from the request body itself (`repository.owner.login`, falling back to `organization.login`), but the handlers that act on the payload (e.g. `StatusHandler`) locate the target record using an entirely different, independently attacker-controlled field (`sha`, with no repository scoping at all). This breaks the intended binding "the organization whose secret authenticated this request" == "the repository/commit that gets written," letting anyone who owns a legitimate webhook secret for **one** repository forge writes against commits belonging to **any other** repository/stack hosted on the same Shipit instance.

### Finding Description
`WebhooksController#verify_signature` resolves the signing organization purely from body content: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` fetches a `GitHubApp` scoped to that organization's own `webhook_secret`, and `verify_webhook_signature` HMAC-validates the raw body against that secret only: [3](#0-2) 

Signature validity therefore only proves that *the request body as a whole* was signed by the secret belonging to whatever organization the `repository.owner.login`/`organization.login` field claims — it says nothing about which specific record the handler will mutate. Handlers use unrelated fields to pick their target. `StatusHandler`, in particular, resolves the target commit **globally by SHA, with no repository/organization scoping whatsoever**: [4](#0-3) 

Since a Shipit instance commonly hosts many repositories/organizations (as shown by the multi-org config support in `Shipit.github_app_config`/`github_organizations` and the `secrets_double_github_app.yml` fixture), an attacker who legitimately controls (or has been granted webhook access to) **Repository A** under **Org A** can compute a valid `X-Hub-Signature` using Org A's `webhook_secret`, while setting the payload's `sha` to a commit SHA that belongs to an unrelated **Stack B** (a different repository/org entirely — the attacker only needs to know a target SHA, which is public GitHub data). `verify_signature` passes because Org A's secret matches the body; `StatusHandler#process` then finds and mutates `Commit` rows in Stack B, injecting an arbitrary `state`/`description`/`target_url` status: [5](#0-4) 

The consequence is not cosmetic. `Commit#add_status` recomputes the commit's status and, if it becomes `success`, calls `schedule_continuous_delivery`, which — if the target stack has Continuous Delivery enabled — enqueues an automatic deploy of that commit: [6](#0-5) [7](#0-6) 

So a webhook-authenticated principal for one repository can forge a passing CI status on a commit in a completely different repository/stack it has no legitimate relationship to, and — if that stack has CD enabled and the commit is otherwise eligible (unlocked, not blocked) — cause Shipit to automatically deploy it. This is an "organization that authenticated versus the repository that is written" binding violation exactly analogous to the reported `remainShares`/`marketOnly` bug: the code computes/acts on state (`remainShares` / the target `Commit`) derived from a code path that was never covered by the verification actually performed (verifying `marketOnly`==false / verifying the org owns the acted-upon SHA).

### Impact Explanation
This crosses the "unauthorized deploy" bar explicitly listed as Critical impact: a party with webhook access to Repository A can, without any relationship to Repository B, cause an unauthorized deploy to be triggered on Repository B's stack by forging its commit-status webhook payload. Even short of triggering CD, it allows unauthenticated-with-respect-to-target writes of arbitrary commit statuses (`state`, `description`, `target_url`) into any tracked stack, corrupting deploy-gating signals (`deployable?`, `blocked?`) instance-wide.

### Likelihood Explanation
Exploitation requires the attacker to (a) control or have compromised webhook delivery/secret access for at least one repository configured on the Shipit instance (a realistic scenario for any multi-tenant/multi-org Shipit deployment, which the codebase explicitly supports), and (b) know a target commit SHA in a different tracked repository (trivially obtainable from public GitHub history). No privileged Shipit session, API token, or the target org's secret is required — only knowledge of *any one* configured webhook secret and a public commit SHA belonging to another tracked repo. Likelihood is moderate-to-high in any environment with more than one onboarded repository/organization.

### Recommendation
Scope the `Commit` (and analogous) lookups by the organization/repository that was actually authenticated, not by attacker-supplied identifiers alone. Concretely: in `StatusHandler#process` (and any other handler resolving records without going through `Handler#stacks`), join through `Repository`/`Stack` using `payload.dig('repository', 'full_name')` — the same field bound to the verified organization/secret — and require it to match `repository_owner`, rejecting statuses whose `repository.owner.login` doesn't correspond to the stack's actual GitHub repository owner. More generally, `verify_signature` should ensure the organization used to select the secret is the same organization that owns the actual resource(s) the handler subsequently touches, not merely a claim in the same unauthenticated JSON blob.

### Proof of Concept
1. Onboard/repository-A is configured under Org A with webhook secret `SECRET_A`; Org B (unrelated) has its own stack/repository, Stack B, with continuous delivery enabled and a known commit `SHA_TARGET` currently pending/failing.
2. Attacker (who has `SECRET_A`, e.g. as the legitimate owner of repo A's webhook) crafts a `status` event JSON body:
   ```json
   {
     "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgA/repo-a" },
     "sha": "<SHA_TARGET belonging to Stack B in OrgB>",
     "state": "success",
     "context": "ci/forged"
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(SECRET_A, body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgA"`, fetches Org A's `GitHubApp`, and validates the signature against `SECRET_A` — it passes.
5. `Shipit::Webhooks::Handlers::StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the commit belonging to Stack B (no org/repo filter applied), and calls `create_status_from_github!`, marking it `success`.
6. `Commit#add_status` → `schedule_continuous_delivery` fires; if Stack B is `continuous_deployment?` and the commit is `deployable?`, `ContinuousDeliveryJob` deploys the forged-as-passing commit in OrgB's stack — an unauthorized deploy triggered entirely from Org A's credentials.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
