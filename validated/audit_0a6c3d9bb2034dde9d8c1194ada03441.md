### Title
Webhook signature verification is bound to `repository.owner.login`/`organization.login` but event handlers act on the unauthenticated `repository.full_name` field, enabling cross-repository/cross-organization forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the `GithubApp` (and its `webhook_secret`) using `repository_owner`, computed from `params.dig('repository','owner','login')` or `params.dig('organization','login')`. Once the signature check passes, the *entire raw payload* is dispatched unmodified to the event handlers [1](#0-0) . Those handlers, however, resolve which `Stack`/`Repository`/`Commit` to mutate using a *different* field of the same payload — `payload.dig('repository', 'full_name')` in the base `Handler` class, or a bare `sha` lookup with no repository scoping at all in `StatusHandler` [2](#0-1) [3](#0-2) . Nothing ties `repository.owner.login` (the field the signature is verified against) to `repository.full_name` (the field the write path trusts), so the two can be set to different values inside a single, legitimately-signed payload.

### Finding Description
The binding that should hold is:

`organization authenticated by verify_signature == organization/repository written by the handler`

but the engine actually verifies:

`Shipit.github(organization: repository_owner)` against `signature`

while it *acts* on:

`Repository.from_github_repo_name(payload.dig('repository', 'full_name'))` (PushHandler/most handlers) or `Commit.where(sha: params.sha)` with no owner filter at all (StatusHandler).

Because a GitHub webhook JSON body is attacker-controlled at the field level (an attacker who owns any repository configured in `Shipit.github_teams`/`Shipit.github` — or any org whose entry has `webhook_secret: nil`, as shown in the shipped `config/secrets.development.shopify.yml` template — can trigger real webhook deliveries for their own repo and GitHub will HMAC-sign exactly the bytes GitHub sent, which are whatever repo/org fields GitHub filled in). The attacker cannot change what GitHub itself puts in `repository.full_name` for their *own* delivery, but the check that matters — `verify_webhook_signature` — only binds the org whose secret was used, not the specific repository name inside the body:

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [4](#0-3) 

If a configured GitHub organization has no `webhook_secret` set (nil is an explicitly supported and templated configuration value), `verify_webhook_signature` unconditionally returns `true` for **any** payload claiming to belong to that organization, regardless of signature contents [5](#0-4) . Combined with `repository_owner` being derived from the attacker-controllable JSON body itself [6](#0-5) , an attacker can pick `repository.owner.login`/`organization.login` to be an org that has no `webhook_secret`, set `repository.full_name` to point at a completely different, victim-owned repository tracked by the same Shipit instance, and the request sails through `verify_signature` with no valid HMAC required at all. `Handler#stacks`/`Handler#repository_name` then trust `repository.full_name` unconditionally [2](#0-1) .

`StatusHandler` is worse: it doesn't even use `repository.full_name` — it looks up `Commit.where(sha: params.sha)` globally across the entire Shipit instance and calls `commit.create_status_from_github!(params)` [3](#0-2) , so any commit sha in any stack in the whole deployment can have a forged CI status attached once *any* configured org's (unsigned/no-secret) webhook check passes.

### Impact Explanation
Commit statuses gate `deployable?`/`deployment_checks_passed?` on a `Stack`, which in turn gates continuous deployment and manual deploy eligibility [7](#0-6) . Forging a `success` CI status on an arbitrary commit sha via `StatusHandler`, or forging `push`/`sync_github` events via `PushHandler` against a victim repository whose owning org has a permissive (`nil`) `webhook_secret`, lets an unprivileged external attacker mark unreviewed/malicious commits as deployable and, on stacks with continuous deployment enabled, trigger an unauthorized deploy of that commit — without any Shipit session, API token, or GitHub repository write access. This matches the "unauthorized deploy" Critical-impact category.

### Likelihood Explanation
Exploitability depends on at least one organization in `Shipit.github` (or `Shipit.github_teams`, since Shipit is explicitly designed as a multi-tenant, multi-organization engine) being configured with no `webhook_secret` — a state the project's own sample configuration templates (`config/secrets.development.shopify.yml`, `test/dummy/config/secrets_double_github_app.yml`) show as an accepted, undocumented-as-dangerous default [8](#0-7) . In such a deployment, any external actor who can send an HTTP POST to `/webhooks` (no auth required, this is the public GitHub webhook endpoint) can exploit this immediately with a hand-crafted JSON body; no signature-forgery skill is even needed because `webhook_secret` being blank short-circuits verification entirely.

### Recommendation
Bind the field the handler acts on to the field the signature was verified against: after `verify_signature` resolves `repository_owner`/the `GithubApp`, re-derive and enforce that `payload.dig('repository', 'owner', 'login')` (and thus the effective org used to load/write `Stack`/`Repository`/`Commit` records) is identical to the org whose secret validated the signature, for every handler — not just at the controller level. `StatusHandler` additionally needs to scope its `Commit` lookup by the verified repository (e.g., via the commit's stack's repository), not by bare `sha` across the whole instance. Treat a missing/blank `webhook_secret` for a configured organization as a hard misconfiguration (refuse to boot, or log/alert loudly) rather than a silently-permissive default.

### Proof of Concept
1. Shipit instance tracks `victim-org/victim-repo` (a `Stack` with continuous deployment enabled) and is also configured with GitHub App entry `attacker-org` that has `webhook_secret: nil` (matches the shipped template default).
2. Attacker creates/owns a real GitHub repository under `attacker-org`, installs the Shipit GitHub App there so GitHub will deliver real, "validly formed" webhook events to Shipit's `/webhooks` endpoint.
3. Attacker crafts (or replays/edits, since delivery is just an HTTP POST that GitHub does not further validate against Shipit) a `status` event payload where:
   - `repository.owner.login` = `attacker-org` (or simply omits repository and sets `organization.login` = `attacker-org`)
   - `sha` = the sha of a malicious/unreviewed commit sitting on `victim-org/victim-repo`
   - `state` = `success`
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: 'attacker-org').verify_webhook_signature(...)`, which returns `true` immediately because `attacker-org`'s `webhook_secret` is blank [5](#0-4) .
5. `StatusHandler#process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [3](#0-2) , marking the victim's commit as CI-green regardless of which org actually owns it.
6. If `victim-org/victim-repo`'s stack has continuous deployment enabled, the newly "green" commit becomes the `next_commit_to_deploy` and is auto-deployed — an unauthorized deploy triggered purely by a forged webhook from an unrelated organization.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
