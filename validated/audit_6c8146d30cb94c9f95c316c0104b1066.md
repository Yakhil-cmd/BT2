### Title
Unauthenticated Bridge Peer Can Inject Arbitrary JSON-RPC Calls into Main Bridge's Internal RPC Server via `ServiceChainCall` P2P Messages — (File: `node/sc/main_bridge_handler.go`)

---

### Summary

The `MainBridge` P2P server accepts connections from any node that knows the public `NetworkId` and `ProtocolVersion`. Once connected, a peer can send `ServiceChainCall` (0x06) P2P messages whose raw bytes are written **without any validation or authorization check** directly into the main bridge's internal RPC server pipe. The internal RPC server has all public `kaia`/`klay` namespace APIs registered, including `kaia_sendRawTransaction`. A secondary bug in `SendRPCResponseData` causes RPC responses to be delivered to only the first peer in the set, allowing an attacker to steal responses intended for the legitimate sub-bridge and block bridge value transfers.

---

### Finding Description

**Step 1 — Unauthenticated peer connection**

The main bridge starts a P2P server that listens on `MainBridgePort`:

```go
serverConfig.ListenAddr = mb.config.MainBridgePort
serverConfig.NoDiscovery = true
serverConfig.NoDial = true
``` [1](#0-0) 

Any node that reaches this port can initiate a connection. The handshake (`readStatus`) only checks `NetworkId` and `ProtocolVersion` — both are public, unauthenticated values:

```go
if status.NetworkId != network {
    return errResp(ErrNetworkIdMismatch, ...)
}
if int(status.ProtocolVersion) != p.version {
    return errResp(ErrProtocolVersionMismatch, ...)
}
``` [2](#0-1) 

No cryptographic proof of identity is required. There is no allowlist of authorized sub-bridge keys.

**Step 2 — `ServiceChainCall` written directly to internal RPC pipe**

Once connected, any peer can send a `ServiceChainCall` (0x06) message. `HandleSubMsg` dispatches it to `handleCallMsg`:

```go
case ServiceChainCall:
    if err := mbh.handleCallMsg(p, msg); err != nil {
        return err
    }
``` [3](#0-2) 

`handleCallMsg` decodes the raw bytes and writes them **directly** to the internal RPC server pipe with no content validation, no sender authentication, and no message-type filtering:

```go
func (mbh *MainBridgeHandler) handleCallMsg(p BridgePeer, msg p2p.Msg) error {
    data := make([]byte, msg.Size)
    err := msg.Decode(&data)
    ...
    _, err = mbh.mainbridge.rpcConn.Write(data)
    ...
}
``` [4](#0-3) 

**Step 3 — Internal RPC server has full `kaia`/`klay` API surface**

The internal RPC server is set up via `net.Pipe()` and has all public `kaia`/`klay` APIs registered:

```go
mb.rpcServer = rpc.NewServer()
p1, p2 := net.Pipe()
mb.rpcConn = p1
go mb.rpcServer.ServeCodec(rpc.NewCodec(p2), 0)
``` [5](#0-4) 

```go
if api.Public && (api.Namespace == "klay" || api.Namespace == "kaia") {
    mb.rpcServer.RegisterName("klay", api.Service)
    mb.rpcServer.RegisterName("kaia", api.Service)
}
``` [6](#0-5) 

This includes `kaia_sendRawTransaction`, `kaia_sendTransaction`, and every other public `kaia`/`klay` method backed by the main chain's `blockchain` and `txPool`.

**Step 4 — Response-stealing secondary bug**

After the internal RPC server processes a call, the response is forwarded via `SendRPCResponseData`, which iterates peers but **returns after the first one**:

```go
func (mb *MainBridge) SendRPCResponseData(data []byte) error {
    peers := mb.BridgePeerSet().peers
    for _, peer := range peers {
        err := peer.SendResponseRPC(data)
        ...
        return err   // ← exits after first peer
    }
    return nil
}
``` [7](#0-6) 

If the attacker's peer appears first in the map, it receives all RPC responses. The legitimate sub-bridge's pending RPC calls (nonce sync, gas price sync, receipt queries) never receive their responses, stalling bridge value-transfer operations.

---

### Impact Explanation

| Impact | Mechanism |
|---|---|
| Arbitrary JSON-RPC injection into main bridge's internal server | Attacker sends crafted `ServiceChainCall` P2P message |
| Transaction submission to main chain tx pool | Attacker calls `kaia_sendRawTransaction` via injected RPC call |
| Bridge value-transfer stall (KAIA/ERC20/ERC721) | Attacker steals RPC responses via `SendRPCResponseData` early-return bug, blocking sub-bridge nonce sync |

The bridge value-transfer stall is the highest-severity impact: the sub-bridge's `handleParentChainInfoResponseMsg` sets `nonceSynced = true` only after receiving a valid `ServiceChainParentChainInfoResponseMsg`. If the sub-bridge's RPC channel is starved, `getParentOperatorNonceSynced()` returns `false`, and `LocalChainHeadEvent` skips all bridge transaction broadcasting and anchoring indefinitely. [8](#0-7) 

---

### Likelihood Explanation

- The main bridge P2P port is network-accessible (it listens on a configurable TCP port).
- The only barrier is knowing `NetworkId` and `ProtocolVersion`, both of which are public constants in `node/sc/protocol.go`.
- No key material, no operator credential, and no privileged network position is required.
- The attacker only needs to open a TCP connection and complete a trivial handshake. [9](#0-8) 

---

### Recommendation

1. **Authenticate bridge peers**: Require the connecting peer to prove ownership of a pre-configured sub-bridge public key (e.g., sign a challenge with the node key and verify against an allowlist). Reject `ServiceChainCall` messages from peers whose identity is not in the allowlist.
2. **Filter `ServiceChainCall` by sender**: In `HandleSubMsg`, check that the sending peer is the registered, authenticated sub-bridge before forwarding to the RPC pipe.
3. **Fix `SendRPCResponseData`**: Remove the early `return err` inside the loop so that all connected peers receive the response, or track which peer originated each RPC call and route the response only to that peer.

### Proof of Concept

```python
# Attacker connects to the main bridge P2P port and sends a ServiceChainCall
# containing a JSON-RPC request for kaia_sendRawTransaction.
# NetworkId and ProtocolVersion are public constants.

import socket, rlp

MAIN_BRIDGE_HOST = "target-main-bridge-ip"
MAIN_BRIDGE_PORT = 50505  # default MainBridgePort

# 1. Perform P2P handshake (StatusMsg = 0x00)
#    Send: ProtocolVersion=2, NetworkId=<public>, TD=0, CurrentBlock=<zero hash>, ChainID=<public>
# 2. Send ServiceChainCall (0x06) with RLP-encoded JSON-RPC payload:
rpc_payload = b'{"jsonrpc":"2.0","method":"kaia_sendRawTransaction","params":["0x...signed_tx..."],"id":1}'
msg_code = 0x06
encoded = rlp.encode([rpc_payload])
# 3. Frame and send via P2P wire protocol
# The main bridge writes this to its internal RPC server pipe and processes it.
# The response (kaia_sendRawTransaction result) is sent back via ServiceChainResponse (0x07).
# If the attacker is the first peer in the peer map, it also receives responses
# to the legitimate sub-bridge's pending RPC calls, starving the sub-bridge.
```

The `handleCallMsg` function at `node/sc/main_bridge_handler.go:86` performs no sender verification before writing to `mb.mainbridge.rpcConn`, confirming the injection path is reachable with no privilege. [4](#0-3)

		return errResp(ErrNetworkIdMismatch, "%d (!= %d)", status.NetworkId, network)
	}
	if int(status.ProtocolVersion) != p.version {
		return errResp(ErrProtocolVersionMismatch, "%d (!= %d)", status.ProtocolVersion, p.version)
	}
	return nil
}

func (mbh *MainBridgeHandler) handleCallMsg(p BridgePeer, msg p2p.Msg) error {
	logger.Trace("mainbridge writes the rpc call message to rpc server", "msg.Size", msg.Size, "msg", msg)
	data := make([]byte, msg.Size)
	err := msg.Decode(&data)
	if err != nil {
		logger.Error("error in mainbridge message handler", "err", err)
		return err
	}

	// Write to RPC server pipe
	_, err = mbh.mainbridge.rpcConn.Write(data)
	if err != nil {
		logger.Error("failed to write to the rpc server pipe", "err", err)
		return err
	}
	return nil
}
