### Title
AA `data_feed`/`in_data_feed` Formulas Accept Zero-Confirmation Oracle Values, an Overly-Short "Lookback" That Enables Data-Feed Manipulation - ([File: data_feeds.js])

### Summary
The Maverick report flags a 30-second TWAP lookback that is too short and lets an attacker feed unstable/manipulable prices into `createTokenManager()`. The equivalent weakness in ocore is that when an Autonomous Agent (AA) evaluates the `data_feed[[...]]` / `in_data_feed[[...]]` oscript operators, the "confirmation window" required before an oracle-posted value is trusted can be **zero** — the code deliberately also accepts values from units that are still completely unstable (not yet part of any stabilized ball), i.e. the effective "lookback" for freshness/confirmation is as short as "just posted, not even 1 MC confirmation."

### Finding Description
`data_feed`/`in_data_feed` formula evaluation in AAs calls `dataFeeds.readDataFeedValue(...)` / `dataFeeds.dataFeedExists(...)` with `unstable_opts = bAA` (true inside AA execution): [1](#0-0) [2](#0-1) 

Inside `readDataFeedValue`, when `bIncludeUnstableAAs` is set, the function scans `storage.assocUnstableMessages` — messages belonging to units that have **not stabilized yet** — for a matching `data_feed` payload from the oracle address(es), and if found, returns that value directly to the AA without requiring any confirmation depth: [3](#0-2) 

The only tunable "window" parameter, `min_mci`, defaults to `0` and is validated merely as a non-negative integer — it does not require the read value to be *stable*, only that its `latest_included_mc_index` be `>= min_mci`, which an unstable unit can already satisfy immediately after being posted: [4](#0-3) [5](#0-4) 

The same zero-confirmation path exists for `dataFeedExists` used by `in data_feed` used in address-definition authentifiers as well: [6](#0-5) 

This is the direct structural analog of the reported bug class: instead of a 30-second TWAP window that is "too short" to resist manipulation, ocore's AA data-feed reader has an effective lookback/confirmation requirement of **zero units of stability**, so a value that has not gone through the DAG's stabilization/witnessing process (which is exactly what gives ocore's "TWAP-equivalent" data feeds their manipulation resistance) can still drive AA logic such as price bands, exchange rates, or blackswan triggers, as seen in the shipped `futures_contract.oscript` sample which reads `data_feed[[oracles=..., feed_name='GBYTE_USD_MA']]` to gate fund payouts: [7](#0-6) 

### Impact Explanation
Because AAs execute deterministically as soon as their triggering unit stabilizes, but the oracle value they read can still come from a unit that has **not** stabilized, an oracle (or anyone colluding with/impersonating one before stabilization) can post a value, have it consumed by an AA response that immediately moves/locks funds (`payment` messages, `var[]` state), and then have the underlying data-feed unit end up non-final, get reordered relative to other candidate data-feed posts (`ifseveral:'last'` re-sorts by `latest_included_mc_index`/`level`, which is not guaranteed identical to the final stabilized DAG ordering), or simply differ across nodes that saw different unstable DAG states at evaluation time. This can cause AA fund loss/incorrect payout, or different nodes disagreeing on the AA's execution result if their transient unstable views differed when the trigger stabilized.

### Likelihood Explanation
This is fully reachable by an unprivileged AA trigger sender interacting with any AA that uses `data_feed`/`in_data_feed`, combined with the oracle address (which many AA templates allow the AA author/trigger data to name, or which may simply be a normal wallet address anyone can author units from). No special privileges, leaked keys, or node/peer compromise are required — only ordinary unit posting from the oracle address in the narrow pre-stabilization window, which is a normal, always-available race condition in ocore's DAG.

### Recommendation
Require oracle data feeds consumed by AA/definition formulas to come from **stable** units by default (or require an explicit, sufficiently large `min_mci`/confirmation depth measured in actually-stabilized MC indexes, not merely `latest_included_mc_index`), removing or tightly restricting `bIncludeUnstableAAs`/`all_unstable` short-circuits so that financial decisions in AAs cannot be based on data that has not passed through DAG stabilization.

### Proof of Concept
1. Deploy an AA (e.g. modeled on `test/samples/futures_contract.oscript`) whose `messages.cases[].if`/`state` reads `data_feed[[oracles='ORACLE_ADDR', feed_name='PRICE']]` to compute a payout.
2. From `ORACLE_ADDR`, post a `data_feed` unit with a favorable `PRICE` value, and immediately (in the same unstable window, before the data-feed unit is included in a stable ball) send the AA trigger unit.
3. Because `readDataFeedValue` is called with `unstable_opts = bAA = true` (`formula/evaluation.js:646`), the AA reads the just-posted, not-yet-stable value from `storage.assocUnstableMessages` (`data_feeds.js:211-249`) as soon as the trigger unit stabilizes, and executes the payout based on it — even though the data-feed unit itself may later end up on a different final branch/ordering, or never actually be "confirmed" in the sense the AA author intended.

function readDataFeedValue(arrAddresses, feed_name, value, min_mci, max_mci, unstable_opts, ifseveral, timestamp, handleResult){
	var bLimitedPrecision = (max_mci < constants.aa2UpgradeMci);
	var start_time = Date.now();
	var objResult = { bAbortedBecauseOfSeveral: false, value: undefined, unit: undefined, mci: undefined };
	var bIncludeUnstableAAs = !!unstable_opts;
	var bIncludeAllUnstable = (unstable_opts === 'all_unstable');
	if (bIncludeUnstableAAs) {
		var arrCandidates = [];
		for (var unit in storage.assocUnstableMessages) {
			var objUnit = storage.assocUnstableUnits[unit] || storage.assocStableUnits[unit];
			if (!objUnit)
				throw Error("unstable unit " + unit + " not in assoc");
			if (!objUnit.bAA && !bIncludeAllUnstable)
				continue;
			if (objUnit.sequence !== 'good')
				continue;
			if (objUnit.latest_included_mc_index < min_mci || objUnit.latest_included_mc_index > max_mci)
				continue;
			if (_.intersection(arrAddresses, objUnit.author_addresses).length === 0)
				continue;
			storage.assocUnstableMessages[unit].forEach(function (message) {
				if (message.app !== 'data_feed')
					return;
				var payload = message.payload;
				if (!ValidationUtils.hasOwnProperty(payload, feed_name))
					return;
				var feed_value = payload[feed_name];
				if (value === null || value === feed_value || value.toString() === feed_value.toString())
					arrCandidates.push({
						value: string_utils.getFeedValue(feed_value, bLimitedPrecision),
						latest_included_mc_index: objUnit.latest_included_mc_index,
						level: objUnit.level,
						unit: objUnit.unit,
						mci: max_mci // it doesn't matter
					});
			});
		}
		if (arrCandidates.length === 1) {
			var feed = arrCandidates[0];
			objResult.value = feed.value;
			objResult.unit = feed.unit;
			objResult.mci = feed.mci;
			if (ifseveral === 'last')
				return handleResult(objResult);
		}
