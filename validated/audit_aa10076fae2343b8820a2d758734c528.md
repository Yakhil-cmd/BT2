### Title
Cross-organization webhook forgery via `owner`/`full_name` divergence lets an unauthenticated attacker mutate another org's `PullRequest` record and reach the merge queue - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`, `app/models/shipit/webhooks/handlers/pull_request/assigned_handler.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects the GitHub App/secret to validate a webhook against using `repository.owner.login`, while every handler (including `AssignedHandler`) resolves the actual `Repository`/`Stack` to mutate using the independent `repository.full_name` field. `GitHubApp#verify_webhook_signature` additionally returns `true` unconditionally when no `webhook_secret` is configured for the selected organization. An attacker can therefore pick a Shipit-known organization with no configured `webhook_secret` for `repository.owner.login` (bypassing signature verification for free) while setting `repository.full_name` to a victim organization's repository that the attacker does not control, causing `AssignedHandler` to write to that victim's `PullRequest` record.

### Finding Description
The broken binding: the code implicitly assumes `params.dig('repository','owner','login') == params.dig('repository','full_name').split('/').first`, i.e., that the organization used to authenticate the webhook is the same organization whose repository is mutated. Nothing enforces this equality.

Path:
1. `Shipit::WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository', 'owner', 'login')` (falls back to `params.dig('organization','login')`), and calls `Shipit.github(organization: repository_owner)` to fetch the `GitHubApp` config for that org, then calls `verify_webhook_signature`. [1](#0-0) [2](#0-1) 
2. `GitHubApp#verify_webhook_signature` returns `true` unconditionally if that org has no `webhook_secret` configured: `return true unless webhook_secret`. [3](#0-2) 
3. Once verified (or trivially passed), `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the raw JSON payload to handlers — with no re-check that the payload's target repository matches the org that was used to authenticate it. [4](#0-3) 
4. `AssignedHandler` resolves the repository purely from `params.repository.full_name` (completely separate from `repository.owner.login` used in step 1), looks up the matching `Shipit::PullRequest` by number/repository id, and calls `pull_request.update(github_pull_request: params.pull_request)`. [5](#0-4) 
5. `PullRequest#github_pull_request=` writes attacker-controlled fields (`title`, `state`, `additions`, `deletions`, `user`, `assignees`, `labels`, `head` sha lookup) directly onto the persisted record belonging to the victim's stack. [6](#0-5) 

Exploit request: attacker sends `POST /webhooks` with header `X-Github-Event: pull_request`, a valid or absent `X-Hub-Signature` (irrelevant if the chosen owner org has no secret), and JSON body:
```json
{
  "action": "assigned",
  "number": <victim PR number>,
  "pull_request": { ... "head": {"sha": "<attacker-controlled sha in victim repo>"} ... },
  "repository": { "owner": {"login": "no-secret-org"}, "full_name": "victim-org/victim-repo" },
  "sender": {"login": "attacker"}
}
```
Because `no-secret-org` has no `webhook_secret` configured in `Shipit.github`, `verify_signature` passes trivially, and `AssignedHandler` then updates the victim's `PullRequest` row using `full_name` pointing at `victim-org/victim-repo`.

Existing guards do not prevent this: `drop_unhandled_event` only checks the event type exists, `verify_signature` never cross-checks `owner.login` against `full_name`'s owner segment, and `ExplicitParameters` schema only validates types/presence, not cross-field consistency. `Repository.from_github_repo_name` used by the handler blindly trusts `full_name`.

### Impact Explanation
This is a payload for one repository/organization mutating another organization's stack record ("a payload for one repository mutating another's stack, commit, task or team" — Critical category). Concretely, `AssignedHandler` overwrites the victim `PullRequest`'s `title`, `state`, `additions`, `deletions`, `assignees`, `labels`, and `head` commit — the `head` field feeds `find_or_create_commit_from_github_by_sha!`, which will fetch/create a `Commit` for the given sha via `stack.github_api.commit`. On a stack with `merge_queue_enabled: true`, downstream jobs (`ProcessMergeRequestsJob`) act on `MergeRequest`/`Commit` state that can be influenced by this write path, and a subsequently green head can drive `MergeRequest#merge!`, which calls `stack.github_api.merge_pull_request` — an unauthorized merge action taken on behalf of the victim's stack using Shipit's own GitHub App credentials for that org. [7](#0-6) 
This is repeatable against any repository configured in the same Shipit instance as long as at least one organization known to `Shipit.github` has no `webhook_secret` set, and the attacker knows or guesses a victim `full_name` and PR `number`.

### Likelihood Explanation
Preconditions: (a) the Shipit instance must have at least one organization/app entry configured with no `webhook_secret` (a realistic misconfiguration, e.g., during onboarding or for orgs relying solely on GitHub App auth without HMAC), (b) the attacker must know the victim's `repository.full_name` and an existing PR `number` on a stack that already has a persisted `Shipit::PullRequest` record, (c) merge-queue amplification additionally requires `merge_queue_enabled: true` and a pending `MergeRequest` for that PR. Attacker cost is a single unauthenticated HTTP POST; no credentials, no GitHub App key, no session are required. The core forgery (steps 1-5) is fully repeatable and requires no live GitHub interaction to demonstrate in a request-spec test — this satisfies the "Fast validation" criterion in the question. The merge-queue `merge!` amplification is a secondary, config-dependent escalation of the same core bug.

### Recommendation
In `Shipit::WebhooksController#verify_signature` (or before handler dispatch), derive the authenticating organization and the target-repository organization from the same field and require they match — e.g., verify the signature using the organization derived from `repository.full_name.split('/').first` rather than (or in addition to, with an equality check against) `repository.owner.login`. Additionally, make `GitHubApp#verify_webhook_signature` fail closed (return `false`, not `true`) when no `webhook_secret` is configured for an organization that owns registered stacks, or require every organization with configured stacks to have a mandatory `webhook_secret`.

### Proof of Concept
minitest plan (`test/controllers/webhooks_controller_test.rb` style, request spec against `POST /webhooks`, no live GitHub):
1. Configure `Shipit.github_apps`/config with two orgs: `"no-secret-org"` (no `webhook_secret`) and `"victim-org"` (has a `webhook_secret`, unknown to the test/attacker).
2. Create a `victim-org/victim-repo` `Repository`, a `Stack` with `merge_queue_enabled: true`, and a persisted `Shipit::PullRequest` with `number: 42`, `title: "original"`.
3. Assert the intended binding before firing the request: `repository.owner.login` used for auth (`"no-secret-org"`) should equal the org segment of `repository.full_name` (`"victim-org"`) for the event to be legitimately scoped — assert they are NOT equal in the crafted payload (`"no-secret-org" != "victim-org"`).
4. POST to `/webhooks` with header `X-Github-Event: pull_request`, no/garbage `X-Hub-Signature`, and body `{"action":"assigned","number":42,"pull_request":{...,"title":"pwned",...},"repository":{"owner":{"login":"no-secret-org"},"full_name":"victim-org/victim-repo"},"sender":{"login":"attacker"}}`.
5. Assert response is `200 OK` (not `422`), proving signature verification was bypassed.
6. Reload the `PullRequest` fixture and assert `title == "pwned"` (or whichever mutated field), proving a payload authenticated against `no-secret-org` mutated `victim-org`'s stack data — i.e., the equality `authenticating_org == mutated_repo_org` is violated while the write still occurred.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
