### Title
Missing Cross-Connection Locking Around Private-Asset Duplicate/Double-Spend Check Enables TOCTOU Race in Private Payment Chains - (File: private_payment.js)

### Summary
`private_payment.js`'s `validateAndSavePrivatePaymentChain()` performs a classic check-then-act sequence — it opens a brand-new DB connection, runs a `SELECT` to detect a duplicate output, and only if no duplicate is found proceeds to validate and insert the private payment chain — but it does this without acquiring any mutex that would serialize concurrent calls for the same private output/asset. Each invocation takes its own independent connection via `db.takeConnectionFromPool`, so two concurrent private-payment deliveries (e.g., from a private-payment counterparty resending, or two units of the same conflicting chain arriving via different code paths) can each pass the duplicate/validation check before either has committed its `INSERT`.

### Finding Description
The relevant flow is in `private_payment.js`: [1](#0-0) 

Each call to `validateAndSavePrivatePaymentChain()` calls `db.takeConnectionFromPool` and starts its own `BEGIN`/`COMMIT` transaction, with **no `mutex.lock()` guarding the whole check-and-insert sequence** for a given asset/output/unit key. Compare this to the general unit-validation path in `validation.js`, which explicitly locks on `arrAuthorAddresses` for the entire validate+commit window: [2](#0-1) 

and to the public-payment double-spend path, which explicitly wraps the “ununique” conflict resolution in a dedicated `mutex.lock(["private_write"], ...)` critical section precisely because it recognizes private-asset writes need serialization against races: [3](#0-2) 

No equivalent lock exists around `private_payment.js`’s duplicate check + save. The duplicate check reads: [4](#0-3) 

If two overlapping calls for the same head element/output arrive close together (each on its own connection/transaction), both connections can see `rows.length === 0` (or fail to find a match) before either commits, and both proceed to `assetModule.validateAndSavePrivatePaymentChain(conn, arrPrivateElements, transaction_callbacks)`, which performs raw `INSERT` statements into `outputs`/`inputs`: [5](#0-4) 

Critically, for private, unstable inputs, `is_unique` is explicitly set to `NULL` (`var is_unique = bStable ? 1 : null;`), and SQL `UNIQUE` constraints treat `NULL` values as distinct — so the `bySrcOutput` unique index on `inputs(src_unit, src_message_index, src_output_index, is_unique)` does **not** prevent two `NULL`-is_unique rows referencing the same source output from both being inserted. This is exactly the invariant that the `private_write` mutex in `validation.js` was introduced to protect for the public-unit validation path, but that protection was not extended to the `private_payment.js` entry point, which is reachable directly by a private-payment counterparty delivering a (possibly resent or maliciously duplicated) private chain.

### Impact Explanation
If both concurrent inserts succeed, the same private-asset source output can be recorded as spent twice (two `inputs` rows referencing the same `src_unit`/`src_message_index`/`src_output_index`, both with `is_unique=NULL`), and two conflicting `outputs` rows can be created for a single spend. Since private assets settle out-of-band (wallet-to-wallet) and this table state feeds subsequent balance/spendability calculations and stability determination, this can lead to double-crediting of the private-asset recipient (spending the same coin/output value twice) — a direct double-spend of a private-asset output, i.e., unauthorized creation of spendable value / loss of asset supply integrity for that asset. This satisfies the "concrete double-spend" and "AA/asset fund loss" bar required by the report criteria.

### Likelihood Explanation
The race window requires two conflicting private-payment deliveries to be processed with overlapping timing on two different DB connections. This is plausible in real deployments: a private-payment counterparty (or a script controlled by one) can deliberately resend a payload (e.g., via `network.js` "private_payment" message handling) multiple times in quick succession, or send two conflicting private chains for the same source output nearly simultaneously, since there is no lock preventing overlapping execution of `validateAndSavePrivatePaymentChain`. Because this requires precise timing and is not deterministic on a single call, likelihood is Medium, but it is achievable by an unprivileged actor with control over payload delivery timing (no elevated/network/hub privileges are needed — a normal private-payment counterparty suffices), consistent with the CVE's "authorized attacker, race condition" bug class.

### Recommendation
Wrap the duplicate-check-and-save sequence in `private_payment.js`’s `validateAndSavePrivatePaymentChain()` with a `mutex.lock()` keyed on a stable identifier for the target output (e.g., `asset + head unit + message_index [+ output_index]`), matching the pattern already used in `validation.js` (`mutex.lock(["private_write"], ...)`) for the analogous public/double-spend path. This ensures the check-then-insert is atomic with respect to other concurrent private-payment processing for the same source output.

### Proof of Concept
1. Attacker (a private-payment counterparty) obtains/derives two payloads that both spend the same private-asset source output (`src_unit`/`src_message_index`/`src_output_index`) — e.g., replaying the legitimate chain payload to the recipient wallet twice in quick succession via two parallel network deliveries, or via two independent calls that each invoke `private_payment.validateAndSavePrivatePaymentChain`.
2. Both calls execute concurrently; each opens its own connection (`db.takeConnectionFromPool` in `private_payment.js:45`), and both run the duplicate-check `SELECT` in `private_payment.js:62-73` before either transaction commits, so both see no duplicate.
3. Both proceed into `divisibleAsset.validateAndSaveDivisiblePrivatePayment`, each independently inserting `outputs`/`inputs` rows on their own connection (`divisible_asset.js:32-72`), with `is_unique=NULL` for the input row since it's unstable — bypassing the `bySrcOutput` unique-index protection due to NULL semantics.
4. Both transactions `COMMIT` successfully, resulting in two independent unspent/duplicated output records tied to a single original source output — a double-spend/double-credit of the private asset.
