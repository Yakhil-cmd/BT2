### Title
Webhook signature verification is keyed on `repository.owner.login` while the acted-upon repository is resolved from `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The bug class in the report is a discrepancy between the value used for authoritative accounting (the field a security check validates) and the value actually used to perform the underlying operation. In `WebhooksController`, `verify_signature` selects the `GitHubApp`/secret used to validate the HMAC signature based on `repository.owner.login`, but the handler that actually resolves and mutates state (`Handler#stacks`) uses `repository.full_name`, a separate, independently-controlled JSON field in the same untrusted payload. There is no enforcement that the organization used to select the verifying secret is the owner encoded in `full_name`.

### Finding Description
`WebhooksController#verify_signature` picks the `GitHubApp` config using: [1](#0-0) 

`repository_owner` is read straight from the JSON body: [2](#0-1) 

`verify_webhook_signature` trivially returns `true` when the selected organization has no `webhook_secret` configured (documented as optional in setup): [3](#0-2) [4](#0-3) 

Once the signature check passes (or is bypassed because that org has no secret), `create` hands the entire raw JSON payload to the handlers unchanged: [5](#0-4) 

The handler that actually resolves *which* `Repository`/`Stack` records get mutated uses a **different** field, `repository.full_name`, with no cross-check against `repository.owner.login`: [6](#0-5) 

`PushHandler#process` then acts on the resolved stacks using an attacker-supplied `after` SHA: [7](#0-6) 

In a multi-organization deployment (`config/secrets.yml` keyed by GitHub org, as documented), each org has its own `GitHubApp` and optionally its own `webhook_secret`: [8](#0-7) [9](#0-8) 

The binding that should hold is: `organization authenticated by verify_signature == owner(full_name) used by Handler#stacks`. Nothing in the code enforces this equality — `repository_owner` and `repository_name` are read from independent JSON keys that an attacker fully controls in the raw POST body.

### Impact Explanation
If any organization configured in `secrets.yml` has `webhook_secret` left blank/nil (an explicitly supported, documented configuration - "Webhook secret (optional)"), then:
- An unauthenticated caller can POST to `/webhooks` with `X-Github-Event`, `repository.owner.login` set to that unsecured organization, and `repository.full_name` set to `victim-org/victim-repo` belonging to a fully secured organization with real stacks.
- `verify_signature` will select the unsecured org's `GitHubApp`, whose `verify_webhook_signature` short-circuits to `true` regardless of the `X-Hub-Signature` header, since `return true unless webhook_secret` .
- The request is accepted, and `PushHandler` (or `StatusHandler`/`CheckSuiteHandler`/`MembershipHandler`) resolves stacks via `Repository.from_github_repo_name("victim-org/victim-repo")`, which are wired to the secured org, and executes with attacker-controlled `after`/state values — e.g. calling `stack.sync_github(expected_head_sha: <attacker sha>)` for a repository the attacker has no relationship to.

This is a spoofed cross-repository/cross-organization webhook: an org boundary intended to gate write access to a stack's sync/status/membership state is bypassed because the authenticating field and the acted-upon field are not the same, and are not cross-validated. This is the same shape of bug as the reported `USDMPegRecovery` finding: a value trusted for authorization/accounting purposes (owner used to pick the verifying secret / stored balance) diverges from the value actually operated on (full_name used to resolve the target / real LP balance), letting state be manipulated inconsistently with the intended trust boundary.

### Likelihood Explanation
Exploitability is entirely conditional on operational configuration: it requires at least one configured GitHub organization in a multi-org Shipit deployment to have no `webhook_secret` set. This is explicitly documented as optional, so it is a plausible (not purely theoretical) misconfiguration, especially during onboarding of a new org before its secret is generated. Once that precondition holds, the exploit itself requires no credentials, no repository write access, and no session — an anonymous POST to `/webhooks` is sufficient, matching the "unprivileged attacker" scope of this engagement. I was not able to fully verify every downstream handler's blast radius (e.g., exact effects of `StatusHandler`/`MembershipHandler`/`CheckSuiteHandler` under this same cross-field mismatch) within available tool calls, so the most concrete confirmed path is `PushHandler` triggering `Stack#sync_github` with an attacker-chosen `expected_head_sha` against a stack that belongs to an organization other than the one whose (missing) secret was checked.

### Recommendation
Bind the two fields together: after selecting the `GitHubApp` via `repository_owner`, verify that `payload.dig('repository', 'full_name')`'s owner segment matches `repository_owner` before dispatching to handlers, and reject the request (422) on mismatch. Additionally, treat organizations with no configured `webhook_secret` as unable to authorize writes to any other organization's repositories — e.g., require `webhook_secret` to be present for every organization in a multi-org config, or scope `Handler#stacks` lookups to repositories owned by the verified `repository_owner`.

### Proof of Concept
1. Deploy Shipit with a multi-org `secrets.yml`: `org-empty` (no `webhook_secret`) and `victim-org` (has a real stack, real `webhook_secret`).
2. Send `POST /webhooks` with header `X-Github-Event: push` and any/garbage `X-Hub-Signature`, and JSON body:
```json
{
  "repository": { "owner": { "login": "org-empty" }, "full_name": "victim-org/victim-repo" },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>"
}
```
3. `verify_signature` calls `Shipit.github(organization: "org-empty")`, whose `verify_webhook_signature` returns `true` unconditionally (no secret configured), so the request passes. [10](#0-9) 
4. `PushHandler` resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on `victim-org`'s real stacks, despite the request never being authenticated for `victim-org`. [7](#0-6)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
