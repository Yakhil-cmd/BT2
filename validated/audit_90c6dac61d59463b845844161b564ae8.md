## Finding: Valid — Cross-tenant team membership escalation via unscoped `github_id` lookup

### Title
`MembershipHandler#find_or_create_team!` matches teams by `github_id` alone, letting any configured organization's webhook forge membership into another organization's `Team` - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#process` finds the target `Team` solely via `Team.find_or_create_by!(github_id: params.team.id)`, without validating that the webhook's verified organization (`Shipit.github(organization: repository_owner)`, matched by the org's own `webhook_secret`) actually owns that team. In a multi-app `github:` install, an attacker who legitimately controls one org's registered `webhook_secret` can sign a `membership` webhook, set `team.id` to a victim org's known/guessed `github_id`, and set `organization.login` to their own org (so signature verification passes), causing `team.add_member` to inject an arbitrary GitHub identity into the victim `Team`'s membership set.

### Finding Description
The broken binding: `Team#members` for a given `Team` (identified by `github_id` X, `organization` = "victim-org") should equal the set of users GitHub reports as members of team X under "victim-org". After the attack it instead becomes the union of memberships asserted by any org whose webhook_secret the attacker controls, because the lookup key ignores `organization` entirely.

Code path:
- `WebhooksController#verify_signature` resolves the signing org via `Shipit.github(organization: repository_owner)`, where `repository_owner` falls back to `params.dig('organization', 'login')` for membership events. [1](#0-0) . This only proves the payload was signed by *some* configured org's secret — the org named inside the attacker's own payload, which the attacker fully controls.
- `MembershipHandler#find_or_create_team!` does `Team.find_or_create_by!(github_id: params.team.id) do |team| team.organization = params.organization.login ... end`. The `organization` assignment only executes in the creation block, i.e. only when no existing row matches `github_id`. If a `Team` row with that `github_id` already exists (e.g. the victim's), the block is skipped and the existing (victim) row is returned untouched. [2](#0-1) 
- `process` then calls `team.add_member(member)` unconditionally on whatever `Team` was matched. [3](#0-2) 
- `Team#add_member` simply appends the member with no organization check. [4](#0-3) 

Attacker request: a `membership` webhook, `action: 'added'`, `team: { id: <victim_team.github_id>, name, slug, url }`, `organization: { login: 'attacker-org' }`, `member: { login: 'attacker-controlled-login' }`, signed with `attacker-org`'s own legitimately-known `webhook_secret`. `verify_signature` succeeds because it only checks that `attacker-org`'s secret matches — it never checks whether `attacker-org` is the org that owns `team.id`. `find_or_create_team!` then resolves to the victim `Team` purely by its numeric `github_id`, and the attacker's chosen member is appended to it.

Existing guards do not stop this: `verify_signature` authenticates the org, not the specific team; `ExplicitParameters` schema only validates types/presence, not ownership; there is no model validation tying `Team#organization` to the `organization` claimed in a membership payload once the row exists.

### Impact Explanation
Any user added this way becomes a `Membership` row on the victim `Team`. If that `Team` is part of `Shipit.github_teams` (configured via `github.oauth.teams`), the injected identity satisfies `User#authorized?` (`teams.where(id: Shipit.github_teams.map(&:id)).exists?`) [5](#0-4) , granting login/authorization to Shipit for an identity that GitHub never actually put on that team. This is repeatable per victim team for every attacker-controlled `member.login`, and reachable by anyone who owns webhook credentials for any one of the configured multi-tenant orgs — a blast radius spanning all tenants sharing the Shipit instance. This matches the documented High-severity category "escalation into `Shipit.github_teams` authorization."

### Likelihood Explanation
Requires a multi-tenant Shipit install with more than one org under `github:` (documented multi-app config [6](#0-5) ), and the attacker must legitimately operate one such org (own its `webhook_secret`) while knowing/guessing a victim `Team`'s numeric `github_id` (GitHub team IDs are small sequential integers, easily discoverable via the GitHub API or brute force). Attacker cost is low — a single crafted HTTP POST to `/webhooks` — and the attack is fully repeatable and automatable.

### Recommendation
Scope the lookup in `MembershipHandler#find_or_create_team!` by both `github_id` and `organization` (e.g. `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`), and additionally verify that `params.organization.login` matches the webhook-verified `repository_owner`/signing org before allowing `add_member`/`delete` to mutate that team's membership.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/membership_handler_test.rb` or extending `test/controllers/webhooks_controller_test.rb`):
1. Fixtures: `shipit_teams(:shopify_developers)` with `github_id: 1`, `organization: 'shopify'`. Add a second `GithubHook::Organization` fixture for `organization: 'attacker-org'` with its own distinct `secret`.
2. Build payload: `{ action: 'added', team: { id: 1, name: 'Developers', slug: 'developers', url: '...' }, organization: { login: 'attacker-org' }, member: { login: 'mallory' } }`.
3. Sign with `attacker-org`'s own secret (legitimately known to attacker) and set `X-Github-Event: membership`, `X-Hub-Signature` accordingly.
4. Before: assert `Shipit::Team.find(shopify_developers.id).members.map(&:login)` does not include `'mallory'`.
5. POST to `/webhooks` with that payload/signature; assert `response` is `:ok` (signature verification succeeds because it only checks `attacker-org`'s secret).
6. After: assert `Shipit::Team.find(shopify_developers.id).members.map(&:login)` now includes `'mallory'`, and that `Shipit::Team.where(organization: 'attacker-org').count` did not increase (proving the existing `shopify` team row, not a new attacker-org team, was mutated).
7. Optionally stub `Shipit.github_teams` to include `shopify_developers` and assert `mallory_user.authorized?` is now `true`, demonstrating the authorization escalation.

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

    someothergithuborg:
