Confirmed: the route `GET /api/stacks/*stack_id/ccmenu` is mounted under `Shipit::Api::CCMenuController#show`, which authenticates via a plain `ApiClient.authenticate(params[:token])` and only checks the coarse `read:stack` permission, but resolves the target stack independently of the client's `stack_id` scope.### Title
Stack-scoped API tokens can read the CCMenu build status of any other stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` resolves the target stack independently of the `ApiClient`'s stack scope, while `require_permission :read, :stack` only checks that the token has the `read:stack` permission flag, never that the permission applies to the requested stack. This lets a token that is authorized (`stack_id`-scoped) for stack A read the CCMenu build status of any other stack B.

### Finding Description
`Shipit::Api::BaseController` implements the intended binding between an `ApiClient` token and the stack(s) it may act on: [1](#0-0) 

`stacks` is scoped to `current_api_client.stack_id` when the client has one, and `stack` is derived from that scoped relation (`stacks.from_param!`). `ApiClient#check_permissions!` only checks whether the client's coarse `permissions` array contains `read:stack`/`write:stack` etc. — it has no notion of *which* stack: [2](#0-1) 

So the actual per-request authorization boundary is enforced entirely by the `stack`/`stacks` helper in `BaseController`, not by `check_permissions!`.

`CCMenuController` overrides `stack` to bypass this scoped helper entirely, resolving the stack directly from the request parameter: [3](#0-2) 

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
```

This is mounted at `GET /api/stacks/*stack_id/ccmenu`: [4](#0-3) 

The `before_action` still calls `require_permission :read, :stack`, which only calls `check_permissions!(:read, :stack)` — a permission-name check unrelated to `stack_id`: [5](#0-4) 

The binding that should hold is: `stack a token authorizes == stack the request touches`. Before the request: an `ApiClient` with `stack_id = A` and `permissions = ['read:stack']` is authorized only for stack A (per the fixture `here_come_the_walrus`, which is `stack: shipit`, `permissions: ['read:stack']`, as seen in the fixtures). After the request: `CCMenuController#show` calls `stack.deploys_and_rollbacks.last`, where `stack` was loaded from `Stack.from_param!(params[:stack_id])` for an arbitrary `stack_id` supplied in the URL — completely independent of `current_api_client.stack_id`. The check (`require_permission :read, :stack`) passes because it only validates permission *name*, and the object actually acted upon (`stack`) was never checked against the client's authorized stack. This exactly mirrors the H-1 pattern: the guard checks one value (`permissions` list) while a different, unguarded value (the concrete `stack` object resolved from `params[:stack_id]`) is the one actually used.

### Impact Explanation
A holder of a stack-scoped `read:stack` API token (e.g. a CCMenu integration token deliberately scoped to a single stack per the intended design — see `CCMenuUrlController`) can enumerate and read the deploy status (`lastBuildStatus`, `lastBuildLabel`, lock status, etc., rendered by the `shipit/ccmenu/project` view) of **any** stack in the Shipit instance, not just the one the token was issued for. This is a cross-tenant read of stack state/deploy output that the token was never authorized to access, matching the "unauthenticated/unauthorized read of stack state ... deploy output" High-impact category — the scoping mechanism that is supposed to bind the token to one stack is completely bypassed for this endpoint.

### Likelihood Explanation
High. No secret/webhook knowledge is required beyond possessing any valid, stack-scoped API token (which is routinely handed out, e.g. via `CCMenuUrlController#fetch`, to third-party CI dashboards). The attacker only needs to change the `stack_id` segment of the URL to an arbitrary stack identifier; no other privilege escalation step is needed.

### Recommendation
Have `CCMenuController#stack` resolve the stack through the same scoped `stacks` relation used by `BaseController` (i.e. `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so that a client scoped to `stack_id` cannot resolve stacks outside that scope, consistent with every other API controller.

### Proof of Concept
1. Fixture `here_come_the_walrus` is an `ApiClient` scoped to `stack: shipit` with `permissions: ['read:stack']` (`test/fixtures/shipit/api_clients.yml`).
2. Obtain its `authentication_token` (e.g. via the app's normal issuance flow, such as `CCMenuUrlController#fetch`, or `ApiClient#authentication_token` if already known).
3. Send `GET /api/stacks/<other-stack-full-name>/ccmenu?token=<here_come_the_walrus token>` for a stack that is *not* `shipit` (e.g. `soc` or `cyclimse` fixture stacks).
4. `CCMenuController#authenticate_api_client` authenticates the token; `require_permission :read, :stack` passes because the token has `read:stack` in its `permissions` list; `stack` resolves the *other* stack directly via `Stack.from_param!`, bypassing the client's `stack_id` scope.
5. The response returns build/deploy status XML for the unauthorized stack, confirming the token escapes its intended single-stack scope.

```ruby
# frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
```
