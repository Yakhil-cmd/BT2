### Title
CCMenu status endpoint bypasses `ApiClient` stack-scoping, letting a stack-restricted token read any stack's build state - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` resolver used elsewhere in the API namespace, replacing the scoped lookup with an unscoped `Stack.from_param!`. This drops the binding that restricts a stack-scoped `ApiClient` token to the single stack it was issued for, letting that token read the build/deploy status of any other stack in the installation.

### Finding Description
`Shipit::Api::BaseController` defines the canonical, scope-respecting stack resolver: [1](#0-0) 
`stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` whenever the authenticated `ApiClient` is bound to a specific stack (`stack_id?`), and `stack` uses that scoped relation to resolve `params[:stack_id]`. This is exactly the mechanism intended to enforce "a stack a token authorises" == "a stack it touches" for every other API resource (`Api::StacksController`, etc.), and it's covered by tests confirming a scoped client only sees its own stack (e.g. `test "an api client scoped to a stack will only see that one stack"`).

`Shipit::Api::CCMenuController`, however, redefines `stack` to bypass this scoping entirely: [2](#0-1) 
It calls `Stack.from_param!(params[:stack_id])` directly — the unscoped, global lookup used by unauthenticated/other-controller contexts — instead of inheriting `stacks.from_param!`. The controller still runs `require_permission :read, :stack` [3](#0-2)  before every action, but `check_permissions!` only checks the operation/scope permission string (`"read:stack"`) and never the specific stack the token is bound to: [4](#0-3) 

So the equality that should hold — `current_api_client.stack_id` (the stack the token authorizes) == `@stack.id` (the stack the request actually touches) — is enforced in `Api::BaseController#stack` but is broken specifically in `CCMenuController#stack`.

### Impact Explanation
Any holder of a stack-scoped `read:stack` `ApiClient` token (e.g., a CI badge/CCMenu token deliberately scoped to one repository/stack, as created in `CCMenuUrlController`) can supply an arbitrary `stack_id` to `GET /api/1/stacks/:stack_id/ccmenu` and receive that other stack's build status: `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`, lock state, etc. (rendered via `shipit/ccmenu/project`). This is an authorization-boundary violation — unauthenticated-for-that-resource read of another stack's deploy/build state — matching the "unauthorized read of stack state" class of impact, achievable by any party holding a legitimately-issued but narrowly-scoped read token, without needing write access, a GitHub identity, or session cookies.

### Likelihood Explanation
Exploitation only requires possession of any valid, stack-scoped `ApiClient` credential with `read:stack` permission (these are routinely distributed for CI badges/dashboards per `CCMenuUrlController`) and knowledge or guessing of another stack's `to_param` (owner/repo/environment slug, which is often public/predictable). No additional privilege, write access, or user interaction is needed, making this straightforward to exploit once such a token is obtained.

### Recommendation
Remove the `stack` override in `Shipit::Api::CCMenuController` and rely on the inherited, scope-respecting `stacks.from_param!` resolver from `Api::BaseController`, so a stack-restricted `ApiClient` can never resolve a `stack_id` outside its own `stack_id`.

### Proof of Concept
1. Create (or use) an `ApiClient` scoped to `stack_a` only, with `permissions: ['read:stack']` (mirrors the `here_come_the_walrus` fixture pattern: `stack: shipit`, `permissions: ['read:stack']`) [5](#0-4) .
2. Authenticate as that client and request a different stack's CCMenu status:
   `GET /api/1/stacks/<stack_b_owner>/<stack_b_repo>/<stack_b_env>/ccmenu` using the `stack_a`-scoped token's Basic-Auth credentials.
3. Because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` unscoped rather than `stacks.from_param!`, the request succeeds (HTTP 200) and returns `stack_b`'s `lastBuildStatus`/`lastBuildLabel`/lock info, even though the token is only authorized (`stack_id`) for `stack_a`. Compare against `Api::StacksController#show` with the same scoped token and `stack_b`'s id, which correctly 404s due to `stacks.from_param!`.
