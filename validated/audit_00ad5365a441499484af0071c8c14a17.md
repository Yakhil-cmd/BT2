### Title
Webhook signature validated against `repository.owner.login`, but handlers act on the unrelated `repository.full_name` field - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App secret to check the HMAC against using `repository_owner`, computed from `params.dig('repository','owner','login')` (falling back to `organization.login`). The HMAC (`verify_webhook_signature`) is computed over the *entire* raw body, so in isolation this is fine for a single-org install. But `Shipit::Webhooks::Handlers::Handler#repository_name` — used by every handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc.) to locate the `Stack`/`Repository` to act on — reads a **different** JSON field: `repository.full_name`.

### Finding Description
In a multi-organization Shipit deployment (`secrets.github` keyed by organization, see `Shipit.github_app_config`), each org has its own `webhook_secret`. A GitHub App installed on OrgA can only send webhooks whose payload naturally has `repository.owner.login == "OrgA"` and `repository.full_name == "OrgA/whatever"` — these two fields are consistent because GitHub itself constructs the payload for events GitHub sends.

The vulnerability requires the equality `verified-signing-organization == acted-upon-repository-owner` to hold, but the code never enforces it directly — it trusts that `repository.owner.login` and `repository.full_name`'s prefix will always agree. Nothing in `verify_signature` or in `Handler#repository_name` cross-checks that the owner used for signature verification is the same as the owner encoded in `full_name`. An attacker who legitimately controls a repository in OrgA (and can therefore make OrgA's GitHub App emit a validly-signed webhook by pushing/commenting there, or who otherwise obtains OrgA's `webhook_secret`) can submit a request whose signature is computed with OrgA's secret but whose `repository.full_name` is set to `OrgB/some-other-tracked-repo`. Because `verify_webhook_signature` only checks that the HMAC matches the raw body against OrgA's secret (which it will, since the attacker/legit OrgA sender is the one signing it), and the handler never checks that `full_name`'s owner matches `repository_owner`, the push/status/check_suite event will be dispatched against Stacks belonging to `OrgB/some-other-tracked-repo`.

This breaks the equality that should hold: **organization whose secret authenticated the payload == repository whose Stacks are written to**. `PushHandler#process` will call `stack.sync_github(expected_head_sha: params.after)` for a repository the sending organization does not own, potentially syncing a spoofed head SHA and desynchronizing/locking an unrelated stack. `StatusHandler`/`CheckSuiteHandler` allow spoofing CI status/check-run state for another org's stack, which is a component of Shipit's deploy safety checks.

### Impact Explanation
This is a cross-organization write in a multi-org Shipit install: a party in control of (or possessing) one organization's webhook secret can inject fabricated commit/CI status events into a completely different organization's stack, corrupting deploy safety-gating state (statuses/check runs) that Shipit's merge/deploy logic depends on. This does not by itself achieve RCE or direct unauthorized deploy, but it undermines the trust boundary between tenants and can be leveraged to force incorrect CI/status state that gates deploys (`StatusHandler`, `CheckSuiteHandler`), which is a cross-repository/cross-tenant write of state the engine treats as trusted GitHub-origin data.

### Likelihood Explanation
Requires a multi-org Shipit configuration with more than one `github.<org>` entry, and requires the attacker to be able to trigger a signed webhook from an org they control (they always can, by pushing/commenting on their own repo which is wired to that org's GitHub App), while crafting the `repository.full_name` field to reference another tenant's repository. Whether GitHub itself would ever produce such a payload is not something this engine controls — an attacker capable of proxying/replaying (as in the referenced external report) or crafting a raw POST directly to the webhook endpoint (which does not require TLS interception, session, or app credentials, only network reachability to the public webhook endpoint and knowledge of one org's already-authorized webhook secret) could exploit this.

### Recommendation
In `WebhooksController#verify_signature` / `Shipit::Webhooks::Handlers::Handler`, enforce that the organization used to select/verify the webhook secret matches the owner encoded in `repository.full_name` (and `organization.login` if present) before dispatching to handlers. Reject the webhook if these two owner values disagree.

### Proof of Concept
1. Multi-org Shipit config with `OrgA` (webhook_secret `SECRET_A`, tracks `OrgA/repo1`) and `OrgB` (tracks `OrgB/repo2`).
2. Attacker controls `OrgA/repo1` and can trigger genuine, correctly-signed webhooks from OrgA's App (e.g., pushing a commit).
3. Attacker crafts (or replays/proxies, per the external report's methodology) a POST to `/github_hook` with `X-Hub-Signature` computed by OrgA's App over a body where `repository.owner.login = "OrgA"` (so `verify_signature` resolves `Shipit.github(organization: "OrgA")` and the HMAC matches) but `repository.full_name = "OrgB/repo2"`.
4. `verify_signature` passes because the signature validly matches OrgA's secret and the raw body.
5. `Shipit::Webhooks.for_event('push').each { |handler| handler.call(params) }` → `PushHandler#process` resolves `Repository.from_github_repo_name("OrgB/repo2")` via `Handler#repository_name`, and calls `sync_github` on OrgB's stacks — a write against a repository never authenticated by the signing organization.
