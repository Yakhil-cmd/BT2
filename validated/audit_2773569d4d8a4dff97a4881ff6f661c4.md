### Title
Attestor-list scope check is skipped for AA-issued assets, allowing unattested addresses to pass `spender_attested` checks - (File: storage.js)

### Summary
The Moodle bug (MDL-80504) let a forum export bypass Separate-Groups scoping and reveal data to users who should have been filtered out, because the code path that should apply the group-scope filter (`is_stable`/`main_chain_index` boundary in Moodle's case) was conditionally skipped. The analogous pattern in `ocore` is `readAsset()`'s inner helper `addAttestorsIfNecessary()` in `storage.js`, which determines the current attestor list for an asset with `spender_attested=true`.

### Finding Description
`addAttestorsIfNecessary(byAA)` builds the SQL condition used to pick the "current" attestor list: [1](#0-0) 

```
function addAttestorsIfNecessary(byAA = false){
    if (!objAsset.spender_attested)
        return handleAsset(null, objAsset);
    const before_last_ball_cond = byAA ? "" : `AND main_chain_index<=${+last_ball_mci} AND is_stable=1`;
    ...
}
```

When `byAA` is `false` (the normal, non-AA path), the query only considers attestor-list units that are already stable and at or before `last_ball_mci` — i.e., it is scoped to what every node deterministically agrees was confirmed as of the last ball, exactly like a group/visibility filter that limits data to an authorized, agreed-upon scope. When `byAA` is `true` (used when the asset is defined by an AA and `bAcceptUnconfirmedAA` allows reading it before confirmation, see the caller `readAsset(conn, asset, last_ball_mci, bAcceptUnconfirmedAA, handleAsset)`), the `before_last_ball_cond` scoping filter is dropped entirely — the query becomes unrestricted by stability or MCI, and simply grabs whichever `asset_attestors` unit has the highest `level`/`rowid`.

This mirrors the reported bug class precisely: a scope/visibility restriction that should always be enforced (only use confirmed, agreed-upon data before the reference point) is conditionally bypassed for one code path, letting a different attestor list "leak into" the computation. Because `spender_attested` transfer/issue validation (`validation.js`, `validatePaymentInputsAndOutputs`) trusts `objAsset.arrAttestedAddresses` derived from this attestor list to gate who may hold/spend the asset: [2](#0-1) 

if the attestor list picked up via the unscoped AA path differs from what other nodes (who use the properly-scoped, pre-last-ball list) would pick, different nodes can disagree about whether a given output owner is "attested" — the exact analog of forum content being exported to accounts that shouldn't have had access, because the scope check was skipped.

### Impact Explanation
If the attestor list used to validate `spender_attested` transfers can diverge between nodes (or between the AA-triggering unit's execution and later main-chain validation) because the stability/MCI boundary is not applied, an address that is not really attested as of the agreed last ball could be treated as attested when the asset is defined/updated by an AA. This can let unattested addresses spend or receive units of the asset, directly enabling unauthorized transfer of a spender-restricted asset, or it can cause a stable output to be considered valid on one node and invalid on another — a validity/stability disagreement between nodes, one of the explicitly accepted impact classes.

### Likelihood Explanation
The condition is reached only for assets defined by AAs where `bAcceptUnconfirmedAA` is set and `spender_attested` is used together with an `asset_attestors` update — a narrow but reachable path (an AA author/asset issuer controls the AA's asset definition and, if the AA itself updates the attestor list post-issuance, controls the ordering/level of the relevant units). Because `addAttestorsIfNecessary(true)` is only invoked from the AA branch of `readAsset` (confirmed by the code reading `readAADefinition` immediately above the `addAttestorsIfNecessary(true)` call), exploitation requires deploying/using an AA-defined `spender_attested` asset and racing an attestor-list update — a real but non-trivial scenario for a single AA author/asset issuer, matching a Medium severity.

### Recommendation
Apply the same stability/MCI scoping in the `byAA` branch as in the non-AA branch, or otherwise ensure the attestor list used for `spender_attested` decisions is deterministically derived the same way regardless of whether the asset/AA response is confirmed, so that all nodes agree on which attestor list applies at a given last ball.

### Proof of Concept
Not independently reproduced; based on static analysis of the divergent SQL condition (`before_last_ball_cond`) in `storage.js`'s `addAttestorsIfNecessary`, contrasted with the strict scoping used in `filterAttestedAddresses` (`storage.js` lines 1960-1974) and in `validatePaymentInputsAndOutputs` (`validation.js` lines 2630-2641). Full exploit construction (deploying an AA that both defines a `spender_attested` asset and posts a conflicting `asset_attestors` update, then demonstrating divergent validation outcomes across nodes) was not completed within this analysis; a live/interactive session against the codebase would be needed to confirm exploitability end-to-end.

			if (!objAsset.spender_attested)
				return handleAsset(null, objAsset);

			// find latest list of attestors
			const before_last_ball_cond = byAA ? "" : `AND main_chain_index<=${+last_ball_mci} AND is_stable=1`;
			conn.query(
				"SELECT unit FROM asset_attestors CROSS JOIN units USING(unit) \n\
				WHERE asset=? " + before_last_ball_cond + " AND sequence='good' ORDER BY "+ (conf.bLight ? "units.rowid" : "level") + " DESC LIMIT 1",
				[asset],
				function (latest_rows) {
					if (latest_rows.length === 0)
						throw Error("no latest attestor list");
					var latest_attestor_list_unit = latest_rows[0].unit;

					// read the list
					conn.query(
						"SELECT attestor_address FROM asset_attestors CROSS JOIN units USING(unit) \n\
						WHERE asset=? AND unit=? " + before_last_ball_cond + " AND sequence='good'",
						[asset, latest_attestor_list_unit],
						function (att_rows) {
							if (att_rows.length === 0)
								throw Error("no attestors?");
							objAsset.arrAttestorAddresses = att_rows.map(function (att_row) { return att_row.attestor_address; });
							handleAsset(null, objAsset);
						}
					);
				}
			);
		}
