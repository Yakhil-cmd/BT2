### Title
Team-authorization webhook trust binding: `Shipit.github_teams` membership can be granted by anyone when `webhook_secret` is unset - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#create` dispatches any JSON body whose `X-Github-Event` header matches a registered handler, gated only by `verify_signature` [4](#0-3) . The binding this endpoint is supposed to enforce is: *the organization named in the payload* == *the organization whose secret validated the payload*. But `GitHubApp#verify_webhook_signature` returns `true` unconditionally whenever `webhook_secret` is blank for that org [3](#0-2) , which is a supported, documented configuration (`webhook_secret: # nil` is the default in every secrets template in this repo, e.g. `config/secrets.development.example.yml`) [5](#0-4) . In that state, the "verified" payload is not actually signed by anything — the equality the code is supposed to enforce (`organization that authenticated == organization the handler acts on`) never holds, and the handler acts purely on attacker-supplied JSON.

### Finding Description
`MembershipHandler#process` trusts the `organization`, `team`, and `member.login` fields straight from the webhook body to create/find a `Team` and add/remove a `User` from it [6](#0-5) . `Team#add_member` appends the resolved user to `team.members` with no additional check [7](#0-6) . Application-wide authorization is then decided purely by team membership: `User#authorized?` returns true if the user belongs to any team in `Shipit.github_teams` [1](#0-0) , and `force_github_authentication` blocks/allows access to the entire Shipit UI based on that single boolean [8](#0-7) .

Thus the equality that should hold — *the entity that authenticated the webhook == the GitHub organization whose team roster is being mutated* — is broken whenever the operator relies on the documented-optional `webhook_secret` field being unset for an org. An attacker who already has a `login` on the Shipit instance's GitHub OAuth (i.e., can log in and reach the "requires fresh login"/"forbidden" gate, but is not yet a member of any `Shipit.github_teams` team) can `POST /webhooks` with `X-Github-Event: membership`, `action: added`, `organization.login` set to any org configured in `Shipit.github`, and `member.login` set to their own GitHub login. `MembershipHandler` will `find_or_create_by_login!` their user and add it to the target team, since there is no signature actually protecting that org's webhook traffic.

### Impact Explanation
This directly maps to the explicit High-severity criterion "escalation into `Shipit.github_teams` authorization" [9](#0-8) . Once added to a permitted team, the attacker passes `force_github_authentication` and gains full authenticated access to the Shipit web UI: they can view stacks, trigger deploys/rollbacks/tasks, lock/unlock stacks, and manage merge queues as an authorized user, none of which they could otherwise reach.

### Likelihood Explanation
Requires only: (1) the target Shipit instance not to configure `webhook_secret` for at least one GitHub organization it manages (a state directly enabled and shown as the default in this repo's own secrets templates, not a misconfiguration outside the documented setup [5](#0-4) ), and (2) the attacker be able to authenticate via the instance's GitHub OAuth app (any GitHub account, since OAuth login itself does not require org membership — that check happens only after login, via `authorized?`). No Shipit session privilege, `ApiClient` token, `webhook_secret`, `api_clients_secret`, or GitHub App private key is needed to reach the vulnerable endpoint itself.

### Recommendation
Require `webhook_secret` to be present and enforce signature verification unconditionally (fail closed instead of `return true unless webhook_secret`), or bind `MembershipHandler` mutations to server-side knowledge (e.g., re-verify org/team membership via the GitHub API using the app's own installation token) rather than trusting the raw webhook body fields for authorization-relevant state changes.

### Proof of Concept
1. Deploy Shipit with `Shipit.github` configured for organization `acme` but leave `webhook_secret` blank, matching the shipped example config [5](#0-4) .
2. Attacker logs into the Shipit instance via GitHub OAuth with an account that is a member of `acme` on GitHub but not of any `Shipit.github_teams` team — they see the "You must be a member of ..." forbidden page [10](#0-9) .
3. Attacker sends:
```
POST /webhooks
X-Github-Event: membership
{
  "action": "added",
  "team": {"id": <id_of_a_Shipit.github_teams_team>, "name": "...", "slug": "...", "url": "..."},
  "organization": {"login": "acme"},
  "member": {"login": "attacker-github-login"}
}
```
4. `WebhooksController#verify_signature` calls `verify_webhook_signature(nil, raw_body)`, which returns `true` because `webhook_secret` is blank for `acme` [3](#0-2) .
5. `MembershipHandler#process` creates/finds the `Team` and calls `team.add_member(User.find_or_create_by_login!('attacker-github-login'))` [2](#0-1) .
6. Attacker reloads the Shipit UI; `authorized?` now returns true and they have full authenticated access.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
