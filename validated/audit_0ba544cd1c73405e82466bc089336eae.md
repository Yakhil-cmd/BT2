### Title
Webhook event handlers write to repositories never bound to the verified webhook organization - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks the HMAC secret to validate a webhook against solely from `params.dig('repository', 'owner', 'login')` (or `organization.login`), but none of the event handlers that subsequently mutate state re-check that the *target* repository/stack they act on belongs to that same, verified organization. [1](#0-0) 

### Finding Description
The controller resolves which `GitHubApp`/`webhook_secret` to verify the signature with using `repository_owner`: [2](#0-1) 

Once the signature check passes, the raw JSON `params` are handed unmodified to every registered handler for the event: [3](#0-2) 

The base `Handler` class, and every handler built on it, resolve the *actual* repository/stack to mutate from a **different** field of the same payload, `repository.full_name`, with no comparison back to the org that was authenticated: [4](#0-3) 

`StatusHandler` goes further and doesn't even use repository scoping — it matches by bare commit SHA across the entire `commits` table, i.e. across every stack of every onboarded organization: [5](#0-4) 

`CheckSuiteHandler` and `PushHandler` use `Handler#stacks`, which resolves via `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))` — again independent of `repository_owner` used for signature selection: [6](#0-5) [7](#0-6) 

Shipit is explicitly designed to host multiple GitHub organizations behind a single instance, each with its own (optional) `webhook_secret`: [8](#0-7) [9](#0-8) 

`verify_webhook_signature` trivially returns `true` when no secret is configured for the resolved organization, and otherwise only checks the signature against the *whole raw body*, not against any cross-field binding between `repository.owner.login` and `repository.full_name`: [10](#0-9) 

**The binding that is broken:** *"an organization that authenticated versus the repository that is written."* The organization whose secret validated the request (`repository.owner.login`) is never the same value used to decide which repository/stack/commit is mutated (`repository.full_name` or a bare `sha` lookup). Anyone who legitimately controls the webhook delivery for **any one** organization onboarded to a shared Shipit instance (i.e., a GitHub org admin who configured their own org's webhook pointing at the shared `/webhooks` endpoint, or an org with no `webhook_secret` set at all, which the setup docs list as optional) can send a signed (or unsigned, if that org has no secret) request that sets `repository.owner.login`/`organization.login` to their own org while setting `repository.full_name` (or a raw `sha`) to a target belonging to a completely different, unrelated organization tracked by the same instance.

### Impact Explanation
This is a cross-repository/cross-tenant write that the acting party has no authorization over:
- `StatusHandler` lets the attacker create arbitrary commit statuses (`state`, `context`, etc.) on **any commit of any stack in the instance**, purely by SHA match, with zero repository scoping. Flipping a required CI context to `success` can unblock Shipit's merge queue or continuous-deployment gating for a repository the attacker does not control — an unauthorized deploy/merge path.
- `CheckSuiteHandler`/`PushHandler` can trigger `RefreshCheckRunsJob`/`GithubSyncJob` against arbitrary stacks belonging to other organizations.
- `MembershipHandler` similarly trusts `params.organization.login`/`params.team`/`params.member` without validating them against `repository_owner`, letting an attacker who only controls one org's webhook mutate team membership records tied to `params.organization.login`.

This satisfies the "cross-repository writes" / "unauthorized deploy" bar defined in the engine's Critical impact bucket, because the verified organization and the mutated repository/stack are never bound together.

### Likelihood Explanation
Likelihood is moderate-to-high on any multi-organization Shipit deployment (a documented, supported configuration), or on any deployment where at least one onboarded organization has no `webhook_secret` set (the setup guide marks the secret as "optional"). No repository write access, `ApiClient` token, or session is required — only control over the webhook delivery for one (any) onboarded org, or exploitation of an org with no secret configured, both of which are within the documented deployment model of this engine rather than a misconfiguration outside it.

### Recommendation
Bind the two identities together before any handler mutates state: after resolving `repository_owner` and verifying the signature, re-derive the target repository from `repository.full_name` (or `sha`'s owning stack) and reject the request (422) unless that repository's `owner` matches `repository_owner`. For `StatusHandler` specifically, scope the `Commit.where(sha:)` lookup to stacks whose repository owner equals the verified `repository_owner`, rather than matching globally by SHA.

### Proof of Concept
1. Shipit instance hosts two organizations, `OrgA` and `OrgB`, each with its own GitHub App/webhook config (`Shipit.github_organizations` returns `[OrgA, OrgB]`); `OrgA` was set up per the documented, optional `webhook_secret` field, but left blank (or the attacker is `OrgA`'s own admin and knows its secret).
2. Attacker (an org admin/webhook operator of `OrgA` only, with no rights on `OrgB`) POSTs to `/webhooks` with header `X-Github-Event: status` and body:
   ```json
   { "sha": "<sha of a commit belonging to OrgB/critical-repo>", "state": "success", "context": "ci/required", "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgA/whatever"} }
   ```
3. `verify_signature` resolves `repository_owner = "OrgA"`, verifies against `OrgA`'s (blank/known) secret — passes.
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)` (see `app/models/shipit/webhooks/handlers/status_handler.rb:20-24`), finds the `OrgB` commit purely by SHA, and calls `create_status_from_github!`, flipping its CI status to `success` for a repository the attacker has no authorization over — potentially unblocking `OrgB`'s merge queue or deploy gating.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",

      ].join(' '))
    end

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
