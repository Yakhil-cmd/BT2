### Title
Unrestricted, timelock-free control by asset `definer_address` over `spender_attested` attestor list enables freezing/gating of user funds - (File: `validation.js`)

### Summary
The reported bug class describes a single privileged actor (`handler` in Vester/VesteNPL) able to unilaterally change a security-critical parameter that controls other users' funds (who can claim/deposit rewards), without any timelock. In ocore, the analogous centralized-entity pattern exists for `spender_attested` assets: the asset's `definer_address` can post an `asset_attestors` message at any time, with no delay, quorum, or restriction, to completely replace the list of addresses whose attestations are required to spend the asset — directly gating fund transferability for every holder of that asset.

### Finding Description
When an asset is defined with `spender_attested: true`, spending it requires the sender/issuer to be attested by one of the addresses in the asset's current "trusted attestor list" [1](#0-0) . This list is not fixed at asset creation; it can be rewritten at any time by a single-authored `asset_attestors` message, validated solely by checking that the message author equals `objAsset.definer_address`: [2](#0-1) 

`checkAttestorList` only validates array format/sorting/length — it imposes no cooldown, no timelock, no multi-sig requirement, and no limitation on how the list is used going forward [3](#0-2) . Once the definer posts a new list, it fully replaces the set of attestors used to authorize any subsequent spend of that asset (`storage.readAsset` always reads the *latest* attestor list unit) [4](#0-3) , and spend validation checks `arrAttestedAddresses` derived from that same latest list [5](#0-4) .

This mirrors the GMX report's `setHandler` bug class exactly: a single centralized entity (here, the asset definer — reachable by any unprivileged unit poster who defines an asset) holds standing, uncontrolled authority over a mechanism (attestor whitelist) that gates other addresses' ability to move already-issued/held funds of that asset, with no protocol-enforced delay for holders to react.

### Impact Explanation
Any holder of a `spender_attested` asset is exposed to the definer's unilateral control: the definer can remove all previously trusted attestors (freezing every holder who is not immediately re-attested by a new trusted attestor) or insert themselves/a colluding address as the sole attestor and then attest arbitrary addresses to grant them spending rights, effectively deciding at will who may transact in the asset. This constitutes AA/asset fund freezing and enables the definer to selectively lock out legitimate holders — matching the "excessive privileged-actor impact on protocol/holders" impact class in the original report (Medium severity, since the affected surface is scoped to a single asset chosen by users who opted into its `spender_attested` model, but the change is instantaneous and irreversible for held funds).

### Likelihood Explanation
Any unprivileged unit poster can create a `spender_attested` asset (part of standard `asset` definition) and reach the vulnerable path with a single subsequent `asset_attestors` message; no special network privilege, timing, or other actors are required — only the definer's own signature. This is entirely self-serve and always reachable whenever a `spender_attested` asset exists.

### Recommendation
Introduce a mandatory delay (timelock) between posting an `asset_attestors` update and it taking effect for spend validation, giving holders time to react (e.g., withdraw/exchange) before a definer's list change can affect their outstanding holdings. Alternatively, allow the asset definer to add attestors immediately but require the delay only for *removals*, or cap how drastically/frequently the attestor set can change.

### Proof of Concept
1. Attacker (as an unprivileged unit poster) defines an asset `A` with `spender_attested: true` and an initial attestor list `[X]` [6](#0-5) .
2. Users acquire/hold `A`, relying on attestor `X` to remain trusted so they can later transfer/spend it.
3. Attacker (definer of `A`) posts an `asset_attestors` message removing `X` and setting the list to `[Y]` where `Y` is controlled by the attacker [2](#0-1) ; this is accepted instantly with no delay.
4. All holders whose attestation came from `X` immediately fail the `spender_attested` check on their next spend attempt (`"none of the authors is attested"` / `"issuer is not attested"`) [1](#0-0) , freezing their funds unless they can somehow obtain a fresh attestation from `Y` — which the attacker fully controls.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}

function checkAttestorList(arrAttestors){
	if (!isNonemptyArray(arrAttestors))
		return "attestors not defined";
	if (arrAttestors.length > constants.MAX_ATTESTORS_PER_ASSET)
		return "too many attestors";
	var prev="";
	for (var i=0; i<arrAttestors.length; i++){
		if (!isValidAddress(arrAttestors[i]))
			return "invalid attestor address: "+JSON.stringify(arrAttestors[i]);
		if (arrAttestors[i] <= prev)
			return "attestors not sorted";
		prev = arrAttestors[i];
	}
	return null;
}
