### Title
`OpenedHandler#provision?` operator-precedence bug lets `prevent_with_label` PRs bypass `review_stacks_enabled=false` - (File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb)

### Summary
`OpenedHandler#provision?` intends `repository.review_stacks_enabled` to gate *every* provisioning path, but Ruby operator precedence only applies it to the `allow_all?` branch. When `provisioning_behavior == :prevent_with_label` and the PR carries no label, `provision?` returns `true` regardless of `review_stacks_enabled`, so an attacker's unlabeled PR causes a `ReviewStack` to be created and queued for provisioning on a repository whose admin explicitly disabled review stacks.

### Finding Description
Broken binding: the code's intended invariant is `enqueue_for_provisioning ⟹ repository.review_stacks_enabled == true`. The actual code is: [1](#0-0) 

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

Due to `&&` binding tighter than `||`, this parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`. The last two disjuncts never reference `review_stacks_enabled`, so `review_stacks_enabled == false` no longer prevents provisioning when `provisioning_behavior` is `allow_with_label` or `prevent_with_label`.

Path: attacker opens a PR without the provisioning label against a repository configured with `review_stacks_enabled=false` and `provisioning_behavior=:prevent_with_label` [2](#0-1) . `respond_to_pull_request_opened?` returns true, `ReviewStackAdapter#find_or_create!` creates the `ReviewStack` and immediately calls `ReviewStackProvisioningQueue.add(stack)` [3](#0-2) , which sets `awaiting_provision = true` [4](#0-3) .

On the next `ReviewStackProvisioningQueue.work` run, `provision(stack)` checks `stack.provisioner.provision?` and, if true, calls `stack.provision` [5](#0-4) . I traced the binding the question assumes ("`provisioner.provision?` is an explicit authorized-user check independent of the buggy expression") and it does **not** hold: the default `ProvisioningHandler::Base#provision?` unconditionally returns `true` with no re-check of `review_stacks_enabled` or any authorization state [6](#0-5) . So there is no independent second gate in this engine's shipped code — the precedence bug in `OpenedHandler#provision?` is the only real guard, and it is broken for the `prevent_with_label`/no-label case.

What actually executes at this point, however, is bounded by what this engine ships: `stack.provision` triggers the state machine's `after_transition deprovisioned: :provisioning` callback, which calls `stack.provisioner.up` [7](#0-6) . In this engine `up` is a no-op on `Base` [8](#0-7)  or, for an unregistered handler name, immediately locks the stack and halts the transition [9](#0-8) . I could not find code in this engine (excluding `lib/shipit/deploy_commands.rb`'s normal `Task`/`Deploy` pipeline, which is a separate, unrelated trigger path) that connects `ReviewStack#provision`/`ProvisioningHandler#up` directly to `TaskCommands#perform`/`Command#start`/`PTY.spawn`. That link only exists if a host application registers a custom `ProvisioningHandler` subclass that itself runs commands — which is an out-of-engine extension point, not a bug in this engine's own code.

### Impact Explanation
Confirmed, in-engine impact: the `review_stacks_enabled=false` control is bypassed for repositories using `provisioning_behavior: prevent_with_label`, causing an unauthorized `ReviewStack` + `PullRequest` record to be created and the stack to be marked `awaiting_provision: true`/transitioned to `provisioning` — state written for the repository that its admin did not authorize via the disabled flag. This is confined to the same repository (not cross-tenant) and only manifests for repos that combine `review_stacks_enabled=false` with a non-`allow_all` provisioning behavior. Whether this escalates to actual `Command`/`PTY.spawn` execution (Critical, per the question's RCE framing) depends entirely on a host-supplied `ProvisioningHandler#up` implementation that is outside this engine's shipped code; the engine's own `Base`/`UnregisteredProvisioningHandler` do not execute commands.

### Likelihood Explanation
Requires a specific, somewhat unusual repository configuration (`review_stacks_enabled=false` combined with `provisioning_behavior=:prevent_with_label`), set by that repository's own admin — no schema or model validation prevents this combination [10](#0-9) . Given that configuration exists, any unprivileged GitHub user able to open a PR without the provisioning label against the repo triggers the bug at zero cost, and it is fully repeatable per PR.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates the entire expression:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Additionally, make `ReviewStackProvisioningQueue#provision` (or `ProvisioningHandler::Base#provision?`) independently re-check `stack.stack.repository.review_stacks_enabled` before calling `stack.provision`, so a single control failure at the webhook handler cannot silently bypass the feature flag.

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` (existing suite already exercises `provisioning_behavior_prevent_with_label?`):
```ruby
test "#process does NOT create/enqueue a ReviewStack when review_stacks_enabled is false, even with prevent_with_label and no label" do
  repository = shipit_repositories(:shipit)
  repository.update!(review_stacks_enabled: false, provisioning_behavior: "prevent_with_label")

  params = default_params(labels: []) # no provisioning label
  handler = Shipit::Webhooks::Handlers::PullRequest::OpenedHandler.new(params)

  assert_no_difference -> { Shipit::ReviewStack.count } do
    handler.process
  end
end
```
Before the fix this assertion fails: a `ReviewStack` is created and `ReviewStackProvisioningQueue.add` sets `awaiting_provision: true` [11](#0-10) , demonstrating `repository.review_stacks_enabled == false` yet `stack.awaiting_provision == true`, violating the intended binding. Complementary assertion in `review_stack_provisioning_queue_test.rb`: with the default `ProvisioningHandler::Base`, `queue.work` transitions such a stack from `deprovisioned` to `provisioning` despite `review_stacks_enabled == false`, confirming no second independent gate exists in this engine's shipped code.
