## Finding

Webhook authenticity is verified against one JSON field (`repository.owner.login` / `organization.login`), while every event handler that actually mutates state selects the target `Repository`/`Stack`/`Commit` using a completely different field (`repository.full_name`, or no repository field at all). Nothing ties these two together, so the "organization whose signature was checked" and "the repository that gets written to" are not the same equality the design assumes.

### Title
Webhook signature verification is bound to `repository.owner.login`, but event handlers act on `repository.full_name` (or nothing at all) - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp`/`webhook_secret` to validate a webhook against using `repository_owner`, derived from `params.dig('repository','owner','login')` (falling back to `organization.login`) [1](#0-0) [2](#0-1) . Once the request passes that check, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the *whole raw payload* to handlers [3](#0-2) . Every handler that needs to resolve a `Repository`/`Stack` uses `Handler#repository_name`, which reads `payload.dig('repository', 'full_name')` - a sibling field of `owner.login`, never covered by the signature-selection logic - to look up the `Repository` and its `Stack`s: `Repository.from_github_repo_name(repository_name)&.stacks` [4](#0-3) . `StatusHandler` goes further and does not use the repository at all, matching purely by commit SHA across the entire installation: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [5](#0-4) .

### Finding Description
`Shipit.github(organization:)` resolves a per-organization `GitHubApp` config (secrets, `webhook_secret`, etc.) in multi-org deployments [6](#0-5) , a feature the docs explicitly document ("Using Multiple Github Applications") [7](#0-6) , and which is exercised by fixtures that deliberately configure one organization with `webhook_secret: # nil` [8](#0-7) . `GitHubApp#verify_webhook_signature` short-circuits to `true` whenever that organization's `webhook_secret` is blank: `return true unless webhook_secret` [9](#0-8) .

Because `verify_signature` only inspects `repository.owner.login`/`organization.login` to pick which org's secret to check [1](#0-0) , and the handlers only ever look at `repository.full_name` (or the raw commit `sha`, unscoped by repository) to decide what to mutate, an attacker can submit a POST to `/webhooks` where:
- `repository.owner.login` (and/or `organization.login`) is set to an organization configured on this Shipit instance with an unset/blank `webhook_secret` - satisfying `verify_signature` with **zero credentials**, and
- `repository.full_name` (used by `PushHandler`, `PullRequest::*Handler`s) or `sha` (used by `StatusHandler`) references an entirely different, security-sensitive organization/repository/commit tracked by the same Shipit instance.

`PushHandler` will then call `stack.sync_github(expected_head_sha: params.after)` on stacks belonging to the *other* organization's repository [10](#0-9) , and `StatusHandler` will attach an attacker-chosen CI status (`state`, `context`, `description`, `target_url`) to any commit in the database matching the SHA, independent of which repository/organization it belongs to [5](#0-4) .

Before the attacker's request: an org lacking a `webhook_secret` is (by the documented design) only supposed to be able to affect its own repositories' Shipit state - i.e., `verified_organization == repository_written_to.organization`. After the crafted request: `verified_organization` (the unsecured org named in `owner.login`) is decoupled from `repository_written_to` (whatever `full_name`/`sha` says), breaking that equality entirely.

### Impact Explanation
This lets an unauthenticated, credential-less party inject forged `push`, `status`, and `pull_request` events that are attributed to and act on repositories/stacks belonging to a different, "secured" organization than the one whose (absent) secret satisfied verification. Concretely: forging a `status` event can mark an arbitrary commit "success" for any CI context Shipit's merge/deploy checklist relies on (`ci.require` in `shipit.yml`), and forging a `push` event triggers a GitHub sync for another org's stack with an attacker-chosen `expected_head_sha`. Both can contribute to an unauthorized deploy/merge decision on a stack the attacker has no legitimate relationship to, which maps to the "unauthorized deploy or merge" High/Critical impact category.

### Likelihood Explanation
Exploitability depends entirely on at least one organization configured on the Shipit instance having a blank/unset `webhook_secret` - an explicitly documented, supported, and test-fixture-demonstrated configuration state (`webhook_secret: # nil` in the multi-org fixture, and blank by default in `template.rb`). In that state, no credential, session, or repository access of any kind is required to reach `PushHandler`/`StatusHandler`/`PullRequest` handlers with attacker-controlled `full_name`/`sha` values, because `verify_webhook_signature` returns `true` unconditionally for that organization.

### Recommendation
Cross-validate that the organization used to select/verify the webhook signature is the same organization implied by `repository.full_name` (and by extension every `Repository`/`Stack`/`Commit` the handler subsequently touches) before dispatching to handlers - reject the request if they disagree. Additionally, `StatusHandler` should scope its `Commit` lookup by the repository present in the payload rather than matching by `sha` alone across the entire database.

### Proof of Concept
1. On a multi-org Shipit deployment, configure (or observe an existing) organization `OrgWeak` with no `webhook_secret` (a documented, supported configuration).
2. POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<sha of a commit tracked under OrgStrong/critical-repo>",
  "state": "success",
  "context": "ci/required-check",
  "organization": { "login": "OrgWeak" },
  "repository": { "owner": { "login": "OrgWeak" }, "full_name": "OrgWeak/whatever" }
}
```
3. `verify_signature` resolves `Shipit.github(organization: "OrgWeak")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` with no signature header needed.
4. `StatusHandler#process` executes `Commit.where(sha: params.sha)` and calls `create_status_from_github!`, setting the forged "success" status on the `OrgStrong/critical-repo` commit despite the attacker having no relationship to `OrgStrong`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
