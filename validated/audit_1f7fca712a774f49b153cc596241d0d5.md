### Title
Session Fixation on GitHub OAuth Callback — `session[:user_id]` Set Without Session Rotation ([File: app/controllers/shipit/github_authentication_controller.rb])

### Summary
The `GithubAuthenticationController#callback` action binds a newly authenticated GitHub identity to whatever session already exists in the browser, without first calling `reset_session`. This breaks the equality that should hold after every privilege-elevation event: `session.id (before login) == session.id (after login)` should be false — i.e., the session container itself must be rotated whenever the anonymous-to-authenticated transition happens. Here it is not, which is the classic session-fixation pattern.

### Finding Description
`callback` is the terminal step of the OmniAuth GitHub flow: [1](#0-0) 

It writes `session[:user_id] = sign_in_github(auth)` and `session[:authenticated] = true` directly into the current session hash. It never calls `reset_session` before doing so. Contrast this with `logout`, a few lines below, which explicitly calls `reset_session` to destroy the session container: [2](#0-1) 

`Shipit::Authentication#force_github_authentication` — the concern that gates every authenticated controller — only calls `reset_session` in the narrow case where an *already logged-in* user's token is stale (`requires_fresh_login?`); it performs no rotation for the anonymous → authenticated transition, which is instead handled solely by the OAuth `callback` above: [3](#0-2) 

Because the session identifier is never rotated on login, an attacker who can plant/know a session id in a victim's browser before the victim authenticates (session fixation — e.g. via a Shipit session cookie set from a sibling subdomain, a permissive cookie scope, or any mechanism that lets the attacker pre-establish/know the session cookie value) will find that, once the victim completes their own legitimate GitHub OAuth login through that same fixated session, `session[:user_id]` and `session[:authenticated]` now resolve to the victim's `User` under the attacker-controlled session id. `find_current_user` in the `Authentication` concern trusts `session[:user_id]` unconditionally to resolve `current_user`: [4](#0-3) 

This is structurally analogous to the reported reentrancy bug: in both cases, an action the attacker is fully entitled to perform (a token transfer with a hook / their own legitimate OAuth completion) is allowed to execute against a piece of state (the `count` accounting variable / the session container) that was never invalidated or re-derived for that specific interaction, letting the attacker's pre-existing artifact (the reentrant call / the fixated session id) capture privileges that were meant to be scoped to a fresh interaction.

### Impact Explanation
If session fixation is achievable against this deployment (e.g., cookie scope misconfiguration, a subdomain under attacker control, or any cookie-setting primitive), the attacker ends up in possession of a session id that is bound to the victim's `Shipit::User`, i.e. `session[:authenticated] == true` and `current_user` resolves to the victim. This grants the attacker the victim's full authorization level inside Shipit — including `Shipit.github_teams` gated access, deploy/rollback/merge triggering rights, and stack management — without ever needing the victim's GitHub credentials or `github_access_token`. This matches the explicitly listed High-impact category: "session fixation / forced OAuth completion."

### Likelihood Explanation
Exploitation requires an external prerequisite (a way to plant or force a specific session cookie value into the victim's browser before they log in — e.g. cookie tossing from a less-trusted sibling subdomain, or lack of a `secure`/host-only cookie scope). This external requirement is exactly analogous to the "external requirements" caveat that caused the original finding to be scored Medium rather than High/Critical. No GitHub credentials, `webhook_secret`, `api_clients_secret`, or repository write access are required — only a session-fixation primitive against the login flow, and the victim performing a normal legitimate login.

### Recommendation
Call `reset_session` at the start of `GithubAuthenticationController#callback`, before writing `session[:user_id]` / `session[:authenticated]`, so that every anonymous → authenticated transition rotates the session container the same way `logout` already does. This severs the binding an attacker would otherwise rely on between a pre-existing (attacker-known) session id and the post-login authenticated identity.

### Proof of Concept
1. Attacker obtains/plants a session cookie value `S` for the victim's browser on the Shipit host (via any cookie-scope primitive, e.g. a sibling subdomain writing a cookie for the parent domain, or a session id accepted from a non-HttpOnly/non-secure context).
2. Victim, using session `S`, visits Shipit and completes the GitHub OAuth login flow normally.
3. `GithubAuthenticationController#callback` executes: `session[:user_id] = victim.id; session[:authenticated] = true` — writing into session `S` without rotating it.
4. Attacker, who already possesses session id `S`, now presents it and is treated by `Authentication#find_current_user` as the victim, gaining the victim's full Shipit authorization. [1](#0-0) [4](#0-3)

```ruby
    def callback
      return_url = request.env['omniauth.origin'] || root_path
      auth = request.env['omniauth.auth']

      return render('failed', layout: false) if auth.blank?

      session[:user_id] = sign_in_github(auth)

      # We need to set this so that the /events and /sidekiq endpoint
      # which leverage `UserRequiredMiddleware` will recognize the user
      # is authenticated.
      session[:authenticated] = true

      redirect_to(return_url)
    end
```

```ruby
    def force_github_authentication
      if current_user.logged_in? && current_user.requires_fresh_login?
        Rails.logger.warn("User #{current_user.id} requires a fresh login, logging out...")
        reset_session
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      elsif Shipit.authentication_disabled? || current_user.logged_in?
        unless current_user.authorized?
          team_handles = Shipit.github_teams.map(&:handle)
          team_list = team_handles.to_sentence(two_words_connector: ' or ', last_word_connector: ', or ')
          render(plain: "You must be a member of #{team_list} to access this application.", status: :forbidden)
        end
      else
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      end
    end
```
