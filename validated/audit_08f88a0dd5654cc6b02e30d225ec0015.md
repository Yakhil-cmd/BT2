Based on my investigation, I found a strong structural analog to the kernel bug's core defect pattern — **a key/field mismatch that silently defeats a cleanup/invalidation path, leaving stale cached state referenced after the underlying data was rolled back** — in `aa_composer.js`'s `revertResponsesInCaches()`.

### Title
Stale AA unit references left in `storage.assocUnstableUnits`/`assocBestChildren` caches after bounce/dry-run rollback due to field-name mismatch in `revertResponsesInCaches` - (File: `aa_composer.js`)

### Summary
`revertResponsesInCaches()` is the cache-cleanup routine invoked whenever an AA trigger evaluation is rolled back — either because a secondary AA bounced (`revert()`) or because a dry run finished (`dryRunPrimaryAATrigger`). Its job mirrors the kernel's cancellation logic: undo any response-unit bookkeeping that was speculatively added to the in-memory unit caches before the corresponding DB transaction is rolled back with `ROLLBACK TO SAVEPOINT` / `ROLLBACK`. [1](#0-0) 

### Finding Description
`revertResponsesInCaches` filters `arrResponses` by testing `objAAResponse.response_unit`:
```
arrResponses.forEach(function (objAAResponse) {
    if (objAAResponse.response_unit)
        arrResponseUnits.push(objAAResponse.response_unit);
});
``` [2](#0-1) 

Everywhere else in the same file (and in the test suite) the emitted response unit is stored under a **different** property name, `objResponseUnit` — e.g. in `handlePrimaryAATrigger`: `if (objAAResponse.objResponseUnit) arrPostedUnits.push(objAAResponse.objResponseUnit);` and the tests assert `arrResponses[0].objResponseUnit...`. [3](#0-2) 

This is the exact same class of defect as the kernel CVE: a cleanup/cancellation routine keys its lookup on a field (`data=NULL` in the kernel case, `response_unit` here) that does not match the key actually used to populate the corresponding record (`conn` in the kernel case, `objResponseUnit` here). As a result, the `if (objAAResponse.response_unit)` guard never fires, `arrResponseUnits` stays empty, and `storage.forgetUnit()` / `storage.fixIsFreeAfterForgettingUnit()` are never called for the units that were spun up (and cached into `storage.assocUnstableUnits`, `assocBestChildren`, `assocUnstableMessages`, etc.) during the trigger evaluation that is about to be discarded via `ROLLBACK`/`ROLLBACK TO SAVEPOINT`. [4](#0-3) [5](#0-4) 

This is invoked on two reachable paths that any AA trigger sender/AA author can drive:
1. Bounce of a secondary AA call chain (`revert()` inside `handleTrigger`), which any unprivileged unit poster can trigger by sending a payment to an AA whose secondary call bounces. [6](#0-5) 
2. Dry-run trigger estimation (`dryRunPrimaryAATrigger`), used for AA response estimation. [7](#0-6) 

### Impact Explanation
If the caches are not purged, `storage.assocUnstableUnits`/`assocBestChildren`/`assocUnstableMessages` retain entries for units that were never actually committed to the DB (they were rolled back). Later code paths — including main-chain/stability computation (`main_chain.js`, which iterates `storage.assocUnstableUnits` to compute best parents, MC index, and stability) and `fixIsFreeAfterForgettingUnit`/`readUnitProps` consistency checks (which `throw Error` on any divergence between the DB and the in-memory props) — rely on this cache being exactly consistent with DB state. [8](#0-7) [9](#0-8) 

A divergence between the in-memory unstable-unit graph and the actual DB content can cause the node to compute stability/best-parent/main-chain differently from peers that reconstructed their caches purely from DB rows, i.e. **node disagreement on validity or stability** — one of the explicitly accepted high-impact outcomes. It can also manifest as `throw Error("different props of ...")` crash loops (denial of ability to process further units) once the stale cache entry is later re-read via `readUnitProps`, i.e., a node becoming unable to confirm new units. [10](#0-9) 

### Likelihood Explanation
This is reachable by any address that triggers or is called by an Autonomous Agent whose evaluation ends up being rolled back (secondary-AA bounce) — a common, easily engineered condition (any unprivileged unit poster can craft a trigger unit that causes a secondary AA to fail on purpose, or where dry-run estimation is used, e.g. wallet UIs previewing AA behavior via `dryRunPrimaryAATrigger`). No special privileges, hub/peer position, or race timing is required beyond composing an ordinary unit.

### Recommendation
Fix the field-name mismatch in `revertResponsesInCaches` so the check matches the actual property populated on `objAAResponse` (`objResponseUnit.unit` or equivalent), ensuring `storage.forgetUnit`/`fixIsFreeAfterForgettingUnit` are always invoked for every response unit that is rolled back. Add a regression test (extending the existing `test/aa_composer.test.js` cache-equality assertions) that specifically exercises the bounce/dry-run revert path and asserts that `storage.assocUnstableUnits`, `assocBestChildren`, and `assocUnstableMessages` return to their pre-trigger state.

### Proof of Concept
1. Deploy a primary AA `A` that calls a secondary AA `B` via a payment message.
2. Make `B`'s script bounce deterministically (e.g., `bounce("fail")`), forcing `handleTrigger`'s secondary-trigger error path to call `revert()` on the primary trigger. [11](#0-10) 
3. Inside `revert()`, `revertResponsesInCaches(arrResponses)` is called; because each `objAAResponse` object carries `objResponseUnit` (an object) rather than `response_unit`, the `if (objAAResponse.response_unit)` check is always false, so `arrResponseUnits` remains empty and `storage.forgetUnit`/`fixIsFreeAfterForgettingUnit` are skipped. [1](#0-0) 
4. The DB transaction is rolled back via `ROLLBACK TO SAVEPOINT initial_balances`, but the in-memory `storage.assocUnstableUnits` cache still contains entries for the now-nonexistent response units. [12](#0-11) 
5. Subsequent calls to `storage.readUnitProps` for a unit sharing a parent with the phantom cached unit, or main-chain calculations iterating `storage.assocUnstableUnits`, observe a state that is inconsistent with the DB, producing either a stability/graph divergence from other nodes or a `throw Error("different props ...")` crash.

**Note on confidence**: I was not able to fully confirm—due to running out of tool-call budget—whether `response_unit` is ever set as a valid property elsewhere in the codebase outside `aa_composer.js` (e.g., possibly set transiently by some other module before `revertResponsesInCaches` runs). The finding is based on strong, but not 100%-exhaustively-verified, evidence: every other read/write of the AA response's unit reference in `aa_composer.js` and its test suite uses `objResponseUnit`, never `response_unit`. If a Devin session confirms `response_unit` is genuinely never set, this finding stands as a real cache-desync bug; if it turns out to be set through some code path I didn't inspect, the severity should be reassessed downward.

function revertResponsesInCaches(arrResponses) {
	// remove the rolled back units from caches and correct is_free of their parents if necessary
	console.log('will revert responses ' + JSON.stringify(arrResponses, null, '\t'));
	var arrResponseUnits = [];
	arrResponses.forEach(function (objAAResponse) {
		if (objAAResponse.response_unit)
			arrResponseUnits.push(objAAResponse.response_unit);
	});
	console.log('will revert response units ' + arrResponseUnits.join(', '));
	if (arrResponseUnits.length > 0) {
		var first_unit = arrResponseUnits[0];
		var objFirstUnit = storage.assocUnstableUnits[first_unit];
		var parent_units = objFirstUnit.parent_units;
		arrResponseUnits.forEach(storage.forgetUnit);
		storage.fixIsFreeAfterForgettingUnit(parent_units);
	}
}
