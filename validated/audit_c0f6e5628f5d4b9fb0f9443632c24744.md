### Title
Cross-repository commit status forgery via unscoped `Commit.where(sha:)` lookup - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` only proves that a `status` webhook body was HMAC-signed for the GitHub organization named in that same body's `repository`/`organization` field; it does not, and cannot, prove that the `sha` inside the body actually belongs to a commit under that organization. `StatusHandler#process` then performs a global `Commit.where(sha: params.sha)` lookup with no repository/stack scoping, so a validly-signed event for an attacker-owned repo can write a status onto any commit record in the entire Shipit installation whose sha the attacker knows, including commits belonging to a completely different tenant's stack.

### Finding Description
The binding the design implicitly assumes is: `authenticated_organization(payload) == owner_of(Commit.where(sha: payload.sha))`. This does not hold.

- `verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) derives the signing org solely from `repository_owner`, i.e. `params.dig('repository','owner','login') || params.dig('organization','login')` (`app/controllers/shipit/webhooks_controller.rb:59-62`), and checks the HMAC against that org's `webhook_secret` via `Shipit.github(organization: repository_owner).verify_webhook_signature`.
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) never reads `params.repository` at all; it does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`, a query with no stack/repository filter (`app/models/shipit/commit.rb` has no such scoping applied here).

Exploit flow: an attacker who owns/administers a repository under org X (with the Shipit GitHub App installed, so X has a legitimate `webhook_secret`) can use GitHub's real commit-status API (`POST /repos/X/repo/statuses/{sha}`) to create a status for **any 40-character sha string**, even one that does not exist as a commit in their own repository — GitHub does not require the sha to belong to the target repo. GitHub then emits a genuine `status` webhook, signed with org X's real secret, whose `repository` field correctly says `X/repo` but whose `sha` is the attacker-chosen value (e.g., a sha copied from a public commit in victim org Y's repository/stack). `verify_signature` validates this signature successfully because it only checks org X's secret against org X's own payload — this is legitimate GitHub traffic, not a forged signature. `StatusHandler#process` then finds the `Commit` record with that sha regardless of which stack/org it belongs to, and calls `commit.create_status_from_github!(params)`, injecting an attacker-controlled `state`/`description`/`target_url`/`context` onto org Y's commit.

This write is not inert: `Commit#add_status` (`app/models/shipit/commit.rb:366-386`) reacts to status changes by calling `stack.schedule_merges` when the new status is `pending` or `success`, and `Commit#schedule_continuous_delivery` (invoked on create, but status changes recompute `deployable?`) can lead to `ContinuousDeliveryJob` being scheduled once `deployable?` becomes true (`!locked? && (stack.ignore_ci? || (success? && !blocked?))`). An attacker who can guess/observe a target's pending commit sha (shas are public in git history, PRs, GitHub UI) can force that commit's CI status to `success`, potentially triggering continuous deployment or unblocking merges for a stack/org they never authenticated against.

None of the existing guards catch this: `verify_signature` authenticates the org named in the payload (X), not the org that owns the target commit (Y); `drop_unhandled_event`/`check_if_ping` are irrelevant; the `ExplicitParameters` schema for `StatusHandler` only validates types/presence of `sha`, `state`, etc., never repository identity; there is no `Stack`/`Repository` scoping check between `verify_signature` and `Commit.where(sha:)`.

### Impact Explanation
A payload legitimately signed for organization X mutates a `Commit`/`Status` record belonging to organization Y's stack — this is exactly the "payload for one repository mutating another's stack, commit, task or team" Critical category. Depending on stack configuration (`continuous_deployment?`, `ignore_ci?`, blocking statuses), the forged success status can unblock merges or trigger an unauthorized deploy for a stack the attacker has no access to. The attack is repeatable against any known commit sha in the installation and is not limited to one victim commit — the attacker can iterate over shas.

### Likelihood Explanation
Preconditions: attacker must control (or have push access to) any repository under some org X that has the Shipit GitHub App installed (a low bar — many installs are org-wide or per-repo self-service), and must know a target sha belonging to victim org Y's stack (shas are routinely public via GitHub UI, PRs, CI logs, git clones). No Shipit secrets, sessions, or API tokens are required; the attacker only uses GitHub's own API against their own repository. This is inexpensive and fully repeatable.

### Recommendation
Scope the commit lookup in `StatusHandler#process` to the repository that authenticated the webhook: filter `Commit` by its `stack`'s `repository` (or `github_repo_name`) matching `params.dig('repository','full_name')`/`repository_owner` from the verified payload, rather than a bare `Commit.where(sha:)` across all stacks. More generally, have `verify_signature` (or a shared concern) attach the authenticated repository/org to the request, and have every handler (`StatusHandler`, `CheckRunHandler`, etc.) enforce that the target `Commit`/`Stack` belongs to that authenticated repository before mutating it.

### Proof of Concept
Minitest integration test plan (no live GitHub):
1. Create `stack_x` under org `X` (with `repository` `X/repo`) and `stack_y` under org `Y` (with `repository` `Y/repo`), each with a `Commit` record; give the `Y` commit a distinct `sha_y`.
2. Stub `Shipit.github(organization: 'X').verify_webhook_signature` to return `true` (simulating a correctly-signed body from GitHub for org X), matching how `verify_signature` derives org solely from payload.
3. POST to `/webhooks` with header `X-Github-Event: status` and a JSON body: `{ "repository": {"owner": {"login": "X"}, "full_name": "X/repo"}, "sha": "<sha_y>", "state": "success", "context": "ci/attacker" }`.
4. Assert response is `200`.
5. Assert `Shipit::Commit.find_by(sha: sha_y).stack_id == stack_y.id` (equality check: `authenticated_organization == 'X'` while `owner_of(commit_with(sha_y)) == 'Y'` — they differ) and that a new `Status` row with `context: "ci/attacker", state: "success"` now exists on `stack_y`'s commit, proving org X's signed payload mutated org Y's data. module Shipit
  module Webhooks

        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
    end
