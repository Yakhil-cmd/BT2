### Title
Untrusted `.gitmodules` submodule URLs let an attacker-pushed commit exfiltrate git-sync's cached HTTP(S) credentials to a same-host repository - (File: main.go)

### Summary
`git-sync` stores repository credentials (username/password, PAT, or askpass-URL response) with `git credential approve` and configures `credential.helper` as `cache --timeout 3600` globally [1](#0-0) , then unconditionally recurses into submodules declared by the *synced repo's own content* via `git submodule update --init --recursive` [2](#0-1) . Because git's credential subsystem matches cached credentials by protocol+host (ignoring path) unless `credential.useHttpPath` is enabled — which git-sync never sets — any attacker who can push a commit that edits `.gitmodules` in the synced repo/branch can point a submodule at a different repository path on the *same host* and have git-sync automatically replay its cached token/password to that attacker-controlled repository path during the next sync.

### Finding Description
This mirrors the ZetaChain M-15 pattern: a component trusts content supplied by an untrusted party (there: unverified `MsgAddToInTxTracker`/`MsgAddToOutTxTracker` entries; here: unverified `.gitmodules` entries in the synced repo) and acts on it without any additional validation, letting the attacker redirect a privileged operation.

In `git-sync`:
1. `StoreCredentials` calls `git credential approve` with the full `--repo` URL (including path) for the main repository and for every `--credential` entry [3](#0-2) .
2. `SetupDefaultGitConfigs` sets `credential.helper` to `cache --timeout 3600` globally, and does not set `credential.useHttpPath=true` [4](#0-3) . Without `useHttpPath`, git's credential matching keys only on `protocol://host[:port]`, not on path — this is standard, well-documented git behavior, not something git-sync opts out of.
3. On every sync, `configureWorktree` unconditionally runs `git submodule update --init --recursive` (or shallow) against whatever `.gitmodules` is present in the checked-out commit [2](#0-1) . The submodule URLs are fully attacker-controlled content of the tracked repository/ref — the exact "untrusted repo content" trust boundary called out in scope.
4. When git fetches a submodule whose URL shares the same host as the main `--repo` (e.g., a different path/repo/org on the same self-hosted GitLab/Gitea/GitHub Enterprise instance), the cached credential for that host is transparently reused by the credential helper, sending the token/password to the attacker-chosen path.

### Impact Explanation
This results in credential/token disclosure: an attacker able to land a commit on the synced ref (a common trust level — e.g., a contributor with branch/PR-merge rights, or anyone able to influence the branch/tag git-sync tracks) can cause git-sync's cached HTTPS Basic-Auth credentials (personal access token, password, or askpass-provided secret) to be sent to a repository/path the attacker controls on the same git host. Depending on host configuration (self-hosted servers where the attacker can view request logs, or where the "repo" is actually an attacker-run endpoint on that host), this discloses the credential outright. Even where full disclosure requires additional host-side conditions, this is a direct, sync-triggered credential-scoping violation stemming purely from processing untrusted repo content (`.gitmodules`) with no separate confirmation step — a clear analog of the "acting on unverified content from an untrusted party" root cause in the reference report.

### Likelihood Explanation
Likelihood is moderate-to-high in realistic deployments: `--submodules` defaults to `recursive` [5](#0-4) , so no special opt-in flag is required. Any workflow where git-sync tracks a branch that accepts external contributions, or where the git host is a shared/self-hosted multi-tenant instance, exposes this path. The credential-URL-path-ignorance behavior is inherent to git and not mitigated anywhere in this codebase (`useHttpPath` is never referenced).

### Recommendation
- Set `credential.useHttpPath=true` (or otherwise scope stored credentials to the exact configured `--repo`/`--credential` URLs including path) so cached tokens are not replayed to other repositories on the same host.
- Provide an option to disable/allowlist submodule URLs (e.g., restrict submodule recursion to explicitly trusted hosts/paths, or require `--submodules=off` by default for untrusted sources), rather than unconditionally trusting `.gitmodules` content from the synced ref.
- Document this credential-scoping caveat prominently, since it is a subtle but security-relevant consequence of combining shared `credential.helper` caching with automatic, content-driven submodule recursion.

### Proof of Concept
1. Deploy `git-sync` against `--repo=https://git.example.com/org/legit-repo` with `--username`/`GITSYNC_PASSWORD` (or `--credential`) supplying a PAT. `StoreCredentials` runs `git credential approve` for that exact URL [3](#0-2) , and `credential.helper=cache` is active globally [6](#0-5) .
2. An attacker with commit rights to the tracked branch (or a merged PR) adds to `legit-repo`'s `.gitmodules`:
   ```
   [submodule "evil"]
       path = evil
       url = https://git.example.com/attacker/evil-repo
   ```
   (same host `git.example.com`, different path/namespace which the attacker controls).
3. On the next periodic sync, `configureWorktree` runs `git submodule update --init --recursive` [2](#0-1) . Git resolves credentials for `https://git.example.com` from the cache (path-agnostic by default) and sends the legit PAT/password as Basic Auth to `https://git.example.com/attacker/evil-repo`.
4. The attacker (who controls that repository/namespace on the shared host, e.g., can inspect server-side access logs or a custom git backend they operate under that path) observes/exfiltrates the credential.

Note: this PoC's final disclosure step depends on host-level visibility the attacker has into requests reaching their own namespace/path (e.g., a self-hosted or custom git server); this condition could not be further verified purely from the `git-sync` source, since it depends on the specific git-hosting backend in a real deployment.

```go
// StoreCredentials stores a username and password for later use.
func (git *repoSync) StoreCredentials(ctx context.Context, url, username, password string) error {
	git.log.V(1).Info("storing git credential", "url", redactURL(url))
	git.log.V(9).Info("md5 of credential", "url", url, "username", md5sum(username), "password", md5sum(password))

	creds := fmt.Sprintf("url=%v\nusername=%v\npassword=%v\n", url, username, password)
	_, _, err := git.RunWithStdin(ctx, "", creds, "credential", "approve")
	if err != nil {
		return fmt.Errorf("can't configure git credentials: %w", err)
	}

	return nil
}
```

```go
// SetupDefaultGitConfigs configures the global git environment with some
// default settings that we need.
func (git *repoSync) SetupDefaultGitConfigs(ctx context.Context) error {
	configs := []keyVal{{
		// Never auto-detach GC runs.
		key: "gc.autoDetach",
		val: "false",
	}, {
		// Fairly aggressive GC.
		key: "gc.pruneExpire",
		val: "now",
	}, {
		// How to manage credentials (for those modes that need it).
		key: "credential.helper",
		val: "cache --timeout 3600",
	}, {
		// Never prompt for a password.
		key: "core.askPass",
		val: "true",
	}}

	for _, kv := range configs {
		if _, _, err := git.Run(ctx, "", "config", "--global", kv.key, kv.val); err != nil {
			return fmt.Errorf("error configuring git %q %q: %w", kv.key, kv.val, err)
		}
	}
	return nil
}
```
