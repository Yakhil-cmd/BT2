This confirms the mechanism: on every swap, `trade_fee` (minus protocol/fund/creator carve-outs) is left in the vault via `new_input_vault_amount` [1](#0-0) , and `deposit`/`withdraw` price LP tokens using `vault_amount_without_fee`, which subtracts only `protocol_fees`, `fund_fees`, and `creator_fees` — not the LP trading fee, which stays commingled in the vault balance [2](#0-1) . This is the classic constant-product AMM design where LP fee accrual is continuous per-swap rather than a discrete batch "distribute" call, unlike the NFTX `distribute`/`xToken` model in the report.

### Title
Just-In-Time Liquidity Sandwiching Lets Well-Funded Depositors Siphon Swap Fees From Long-Term LPs - (File: programs/cp-swap/src/instructions/deposit.rs, programs/cp-swap/src/instructions/withdraw.rs, programs/cp-swap/src/curve/calculator.rs)

### Summary
`deposit` and `withdraw` mint/burn LP tokens based on the pool's *instantaneous* reserve ratio (`vault_amount_without_fee`), and the constant-product swap fee (`trade_fee` net of the protocol/fund/creator cuts) is credited directly and irrevocably into the vault balance the moment a swap executes [3](#0-2) . Because there is no time-weighted accounting, holding-period requirement, or withdrawal delay, an attacker can atomically (or same-slot) deposit a large amount of liquidity immediately before a large pending swap and withdraw immediately after, capturing a share of that swap's LP fee proportional to their (temporary) share of the pool — fees that would otherwise have accrued entirely to the existing, long-term LPs.

### Finding Description
- `deposit` computes `lp_token_amount -> (token_0_amount, token_1_amount)` using the current `pool_state.lp_supply` and `vault_amount_without_fee(vault_0, vault_1)` [4](#0-3) , then mints LP tokens 1:1 with the requested `lp_token_amount` [5](#0-4) .
- `withdraw` performs the symmetric operation, redeeming LP tokens for a proportional share of the *current* vault balances [6](#0-5) .
- `vault_amount_without_fee` only excludes `protocol_fees_*`, `fund_fees_*`, and `creator_fees_*` from the vault totals; the LP-owned `trade_fee` portion of every swap remains inside `token_0_vault`/`token_1_vault` and is therefore immediately reflected in the pool's reserve ratio [2](#0-1) .
- `CurveCalculator::swap_base_input`/`swap_base_output` compute `new_input_vault_amount = input_vault_amount + input_amount_less_fees`, where `input_amount_less_fees` still contains the LP `trade_fee` (only `protocol_fee`/`fund_fee`/`creator_fee` are carved out and separately tracked) [7](#0-6) .
- There is no minimum staking duration, cooldown, or per-block/per-slot restriction between `deposit` and `withdraw` — any signer can call both in sequence, and Anchor/Solana permit multiple instructions (deposit, swap, withdraw) to be composed inside a single atomic transaction or across adjacent same-slot transactions submitted by the same actor (e.g., via a searcher/validator relationship or simple back-to-back submission).

Because LP-token minting/burning is purely a function of instantaneous reserves and total supply — with no mechanism to attribute swap fees only to LPs who were present during the swap — a large depositor can insert themselves into the pool immediately before a fee-generating swap and exit immediately after, capturing fee income they did not economically earn, while diluting the pro-rata claim of pre-existing LPs on both the fee income and (through slippage/impermanent-loss timing) the underlying reserves.

### Impact Explanation
This directly mirrors the core mechanism in the referenced NFTX `deposit`/`distribute` report: value is periodically added to a pooled, share-based accounting structure, and an attacker with access to a single transaction (or an atomic bundle) can transiently inflate their share right before the value-add event and withdraw right after, extracting fees intended for existing depositors. Here, the "distribute" event is any swap, which happens continuously and is fully predictable/observable in the mempool. Repeated JIT extraction reduces the yield captured by genuine, long-duration LPs and effectively transfers protocol swap-fee revenue to capital-rich, opportunistic actors, which is a fee-ledger/accounting fairness impact against LP funds.

### Likelihood Explanation
The attack requires no privileged access — only a `deposit`, the target `swap_base_input`/`swap_base_output`, and a `withdraw`, all of which are permissionless instructions reachable by any signer with sufficient capital [8](#0-7) . On Solana, an attacker can bundle deposit → (wait for / trigger a large swap) → withdraw within the same or adjacent slots, and since deposit/withdraw incur no time lock, no cooldown, and no minimum LP holding period, the capital-at-risk window is minimal (bounded by slippage on the deposit/withdraw legs and normal transaction fees). As with the original NFTX finding, this requires meaningful capital relative to the pool and precise timing, which somewhat limits how often it's profitable against small trades, but it scales with pool size and trade size and needs no special privileges, making it a realistic risk for pools that see large, predictable swaps.

### Recommendation
- Introduce a minimum holding period (measured in slots) between `deposit` and a subsequent `withdraw` of the same LP position, rejecting withdrawals that occur within N slots of the corresponding deposit.
- Alternatively/additionally, track fee accrual with a time-weighted or checkpointed accounting scheme (e.g., snapshotting the "fee-per-share" index at deposit time) so that only LPs present during a swap accrue that swap's fee, similar to Uniswap V3's fee growth checkpoints, rather than allowing pro-rata redemption of instantaneous reserves.
- Consider charging a deposit/withdraw fee (already partially present via transfer fees) sized to offset the expected value of JIT extraction, or requiring `deposit` and `withdraw` in the same slot/transaction to be explicitly disallowed.

### Proof of Concept
1. Attacker observes a large pending `swap_base_input` transaction against `PoolState` P with reserves `(X, Y)` and `lp_supply = S`.
2. Attacker calls `deposit` with `lp_token_amount = L`, minting `L` LP tokens against current reserves (via `vault_amount_without_fee`) [4](#0-3) , bringing supply to `S + L`.
3. The large swap executes; `trade_fee` (net of protocol/fund/creator cuts) is added into the vault balance, increasing the redeemable reserves for all LP holders, including the attacker, per `swap_base_input`'s `pool_state.update_fees` and the underlying `new_input_vault_amount` computation [9](#0-8) .
4. Attacker immediately calls `withdraw` for `L` LP tokens, redeeming a proportional share of the now-larger reserves per `vault_amount_without_fee` [6](#0-5) , capturing `L/(S+L)` of the swap's LP fee despite having provided liquidity only for the duration of the single swap.
5. Pre-existing LPs (holding `S` shares) receive a diluted share of that swap's fee (`S/(S+L)` instead of 100%), repeating this against every observable large swap systematically siphons fee revenue away from long-term liquidity providers.

    pub fn swap_base_input(
        input_amount: u128,
        input_vault_amount: u128,
        output_vault_amount: u128,
        trade_fee_rate: u64,
        creator_fee_rate: u64,
        protocol_fee_rate: u64,
        fund_fee_rate: u64,
        is_creator_fee_on_input: bool,
    ) -> Option<SwapResult> {
        let mut creator_fee = 0;
        let trade_fee: u128;

        let input_amount_less_fees = if is_creator_fee_on_input {
            let total_fee = Fees::trading_fee(input_amount, trade_fee_rate + creator_fee_rate)?;
            creator_fee = Fees::split_creator_fee(total_fee, trade_fee_rate, creator_fee_rate)?;
            trade_fee = total_fee - creator_fee;
            input_amount.checked_sub(total_fee)?
        } else {
            trade_fee = Fees::trading_fee(input_amount, trade_fee_rate)?;
            input_amount.checked_sub(trade_fee)?
        };
        let protocol_fee = Fees::protocol_fee(trade_fee, protocol_fee_rate)?;
        let fund_fee = Fees::fund_fee(trade_fee, fund_fee_rate)?;

        let output_amount_swapped = ConstantProductCurve::swap_base_input_without_fees(
            input_amount_less_fees,
            input_vault_amount,
            output_vault_amount,
        );

        let output_amount = if is_creator_fee_on_input {
            output_amount_swapped
        } else {
            creator_fee = Fees::creator_fee(output_amount_swapped, creator_fee_rate)?;
            output_amount_swapped.checked_sub(creator_fee)?
        };

        Some(SwapResult {
            new_input_vault_amount: input_vault_amount.checked_add(input_amount_less_fees)?,
            new_output_vault_amount: output_vault_amount.checked_sub(output_amount_swapped)?,
            input_amount,
            output_amount,
            trade_fee,
            protocol_fee,
            fund_fee,
            creator_fee,
        })

            .checked_add(self.creator_fees_token_1)

            vault_0
                .checked_sub(fees_token_0)
                .ok_or(ErrorCode::InsufficientVault)?,
            vault_1
