### Title
Zero-valued relayer reward can be silently computed by `calculate_fee` despite passing non-zero `PricingParameters` validation, leaving relayers unpaid for gas spent - ([File: bridges/snowbridge/pallets/outbound-queue/src/lib.rs])

### Summary
The Snowbridge outbound-queue pallet computes the fee that a user pays to have a message relayed to Ethereum, part of which becomes `Message.Reward` — the amount the relayer that submits/executes the message on Ethereum is paid. `PricingParameters::validate()` [1](#0-0)  only checks that the individual governance-set parameters (`exchange_rate`, `fee_per_gas`, `rewards.local`, `rewards.remote`, `multiplier`) are non-zero, but does not check that the final *computed* fee is non-zero. Because `calculate_fee` performs integer/fixed-point division and truncation when converting the remote (ETH) fee into local currency and applying the exchange rate, the final relayer reward embedded in the outbound message can still be computed as `0` even though every individual pricing parameter is valid and non-zero. This is confirmed by the pallet's own test suite. As in the reported Perennial `Kept.sol` issue — where a zero/garbage price from an unchecked oracle silently zeroes out the keeper incentive — here a "valid-looking" set of pricing parameters can still silently zero out the relayer's incentive due to unchecked truncation, with no downstream guard rejecting a zero result.

### Finding Description
Any permitted user of the bridge (sending an XCM/asset transfer through the Snowbridge system that ultimately calls `SendMessage::validate`) triggers `Pallet::<T>::calculate_fee`: [2](#0-1) 

This function:
1. Computes `RemoteFee = fee_per_gas * gas_used_at_most + reward` in `calculate_remote_fee` [3](#0-2) .
2. Converts it to a `u128`, multiplies by `multiplier`, and divides by `exchange_rate` using `FixedU128` fixed-point arithmetic [4](#0-3) .
3. Finally scales by decimals in `convert_from_ether_decimals` [5](#0-4) .

None of these steps assert the final `fee.remote` (or `fee.local`) is non-zero after the arithmetic. The only validation gate is `PricingParameters::validate()`, invoked when governance calls `set_pricing_parameters` in `pallet-system`, and it only guards the *raw inputs*: [1](#0-0) 

This is directly analogous to `Kept.sol`'s `_etherPrice`: the upstream data source check (`answer > 0` missing / `validate()` on parameters) passes, yet the derived value fed into the incentive calculation is truncated/rounded down to zero, and the code has no defensive check on the *derived* fee before it is committed into the message that a relayer will later claim `Message.Reward` for on Ethereum.

### Impact Explanation
If the final computed `fee.remote` is `0`, the message committed to the outbound queue and delivered to the Ethereum gateway contract encodes a `Message.Reward` of `0`. A relayer who observes the message, pays gas to submit the proof/transaction on Ethereum, and executes the message receives `Min(GasPrice, MaxFeePerGas) * GasUsed() + 0` — i.e., only the gas refund component if any at all, with zero net incentive. This is a direct parallel to the "keepers lose funds paid for gas without gaining incentive" impact described in the original report. This is a `Medium`-severity issue: relayers realize a loss on any affected message, but the loss is bounded to the reward-per-message rather than an unbounded/critical asset-theft or unbacked-issuance issue.

### Likelihood Explanation
This does not require any privileged actor, forged data, or malicious relayer — it can occur under entirely legitimate, governance-approved `PricingParameters` combined with small `gas_used_at_most`/`reward` values and normal fixed-point truncation, exactly the scenario the pallet's own test `test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero` exercises and explicitly comments is "invalid... which should be avoided": [6](#0-5) 

The likelihood scales with how governance configures `fee_per_gas`, `rewards.remote`, `multiplier`, and `exchange_rate` relative to `gas_used_at_most`; low-fee/low-reward configurations (which lower user costs) increase the chance of this truncation-to-zero outcome for lightweight messages.

### Recommendation
After computing the final fee in `calculate_fee`, explicitly check that `fee.remote` (and `fee.local`, if relevant to relayer incentive) is non-zero for any user-originated (non-governance) message, and reject/re-price the send if the derived relayer reward would be zero — mirroring the exact "verify the derived value, not just the raw oracle/parameter inputs, is non-zero" recommendation from the referenced report.

### Proof of Concept
The pallet's existing (non-mocked) unit test already reproduces the exact zero-derived-fee condition using only valid, non-zero `PricingParameters` (which pass `validate()`), demonstrating the finding without needing external live-network execution: [6](#0-5) 
Test result per the source comment: `fee.local == 698000000` (non-zero) but `fee.remote == 0`, i.e., the relayer reward channel is zeroed even though `exchange_rate`, `fee_per_gas`, `rewards.local`, `rewards.remote`, and `multiplier` were all set to non-zero, valid values that would pass `PricingParameters::validate()`. This confirms the guard gap: input validation passes, but the derived/relayer-facing value can still be zero, unlike what the current `validate()` implementation guarantees.

Note: I could not fully trace the exact live deployment path of `set_pricing_parameters` (source at `bridges/snowbridge/pallets/system/src/lib.rs`) within the tool budget to confirm whether any additional post-computation guard exists at a higher layer (e.g., in `pallet-system` or the BridgeHub runtime configuration) that might reject a zero-reward message before commitment; this should be verified in a Devin session with full repository access if a definitive confirmation of exploitability in the currently deployed BridgeHub runtimes is required.

		/// Calculate total fee in native currency to cover all costs of delivering a message to the
		/// remote destination. See module-level documentation for more details.
		pub(crate) fn calculate_fee(
			gas_used_at_most: u64,
			params: PricingParameters<T::Balance>,
		) -> Fee<T::Balance> {
			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}

#[test]
fn test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero() {
	new_tester().execute_with(|| {
		let gas_used: u64 = 250000;
		let price_params: PricingParameters<<Test as Config>::Balance> = PricingParameters {
			exchange_rate: FixedU128::from_rational(1, 1),
			fee_per_gas: 1_u32.into(),
			rewards: Rewards { local: 1_u32.into(), remote: 1_u32.into() },
			multiplier: FixedU128::from_rational(1, 1),
		};
		let fee = OutboundQueue::calculate_fee(gas_used, price_params.clone());
		assert_eq!(fee.local, 698000000);
		// Though none zero pricing params the remote fee calculated here is invalid
		// which should be avoided
		assert_eq!(fee.remote, 0);
	});
}
