### Title
Unchecked route-venue addresses let a crafted swap payload execute attacker code beneath the caller's `require_auth`, draining wallet funds beyond the routed amount - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The GeoServer bug class is an *unchecked lookup*: user-supplied input names a target (a JNDI resource) that is resolved and executed without validation, turning the caller's own privileges into arbitrary code execution. XOXNO Lending has the same shape. `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply` and `flash_position` accept a caller-supplied `StrategySwap`/route payload that names arbitrary contract addresses as hop pools/venues. The controller grants only one exact input-transfer authorization and measures balances, but the router invokes whatever addresses the payload names, with no venue allowlist. Any contract the route names runs beneath the caller's `require_auth` tree, so a route crafted by an attacker can add a `token.transfer(victim, attacker, victim_balance)` child to the victim's authorization entry — stealing wallet tokens the protocol never touched.

### Finding Description
`swap_tokens` in `contracts/controller/src/strategies/swap.rs:13-55` does three things: snapshot balances, call `authorize_transfer_as_current` for exactly `amount_in` to `router_addr`, then `router.execute_strategy(&controller, &amount_in, swap)`. Nothing validates the addresses inside `swap`; the comment at line 11 and the threat model at `docs/explanation/threat-model.md:154-165` confirm the router "calls the pool and token addresses its payload names and keeps no allowlist of them, so a route can put third-party code on the call stack below the caller's authorization." The harness test `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` demonstrates it end-to-end: a `RogueHopPool` named in the route calls `token.transfer(alice, attacker, WALLET_BALANCE)`, simulation records it as a child of Alice's `swap_collateral` auth entry, and enforcing mode accepts it if signed — Alice ends with wallet balance 0 while the swap itself pays a fair output and passes every protocol gate.

The protective checks in `swap_tokens` (`RouterOverspend`, `NoSwapOutput`, leftover refund, final health-factor gate) all bound only the *routed* funds; none bounds the auth tree. The uncapped exposure is the caller's whole wallet across every token, recorded under the single `swap_collateral`/`swap_debt`/`multiply` signature — the Soroban equivalent of an unchecked JNDI lookup executing attacker-controlled code with the victim's privileges.

### Impact Explanation
Theft of user funds: an unprivileged attacker deploys a contract like `RogueHopPool`, embeds its address in a swap route delivered to a victim (malicious frontend, compromised quote response, phishing), and when the victim signs the `swap_collateral`/`multiply`/`swap_debt`/`flash_position` invocation the rogue contract transfers arbitrary wallet tokens to the attacker under the victim's own authorization. The loss is unbounded by `amount_in`, slippage, or the risk gates.

### Likelihood Explanation
Requires the victim to sign a poisoned route — the authorization tree displays the extra child transfer, so a wallet that renders sub-invocations, or a client that decodes the route (the SDK's `verifyRouteBytes`/envelope checks in `skills/xoxno-swap-aggregator/payload.md`) would reject it. But nothing in the protocol forces that check, honest-looking output and a passing final health check make the swap appear normal, and the threat model documents that exposure is "the caller's wallet, not the routed amount." Reachable by a single unprivileged address through `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`, and `flash_position`. Medium likelihood, high per-victim impact → High.

### Recommendation
Validate route venues instead of trusting payload-named addresses. Concretely: (a) enforce at the controller/router boundary that the swap execution produces no additional sub-invocations under the caller's auth beyond the single input `transfer` — i.e., have the controller require the router run under the controller's own auth rather than exposing the caller's tree to route-named contracts; (b) alternatively maintain an allowlist of permitted venue contracts (Aquarius/Soroswap pool factory or registered pools) and reject routes naming unregistered addresses; (c) at minimum, document-enforced client-side verification should be codified — reject any signed authorization tree containing children other than the expected single input transfer, as `threat-model.md` prescribes.

### Proof of Concept
See `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`:

1. Attacker registers `RogueHopPool` with plan `(victim=Alice, wallet_token, to=attacker, amount=WALLET_BALANCE)` (lines 54–72).
2. Route `RoutedSwap{ hop_pool: rogue, min_out: FAIR_OUT_ETH, token_in: USDC, token_out: ETH }` is passed to `swap_collateral(alice, account_id, usdc, 50e9, eth, route)` (lines 111–164).
3. The router invokes `hop_pool.swap()`, which calls `token::Client::transfer(&alice, &attacker, &WALLET_BALANCE)` inside the call stack.
4. Simulation records the stolen transfer as a child of Alice's `swap_collateral` authorization entry (lines 206–222); if Alice signs that tree, the transfer executes — asserted by `assert_eq!(s.wallet(&s.alice), 0)` and `assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE)` at lines 224–225, while her ETH supply still lands (`FAIR_OUT_ETH`), so every protocol check passes.

The GeoServer advisory's "unchecked JNDI lookup executes attacker-resolved code under the victim's privileges" maps exactly: the route payload is the unchecked lookup, the hop venue is the resolved class, and the caller's `require_auth` tree is the privilege context.
