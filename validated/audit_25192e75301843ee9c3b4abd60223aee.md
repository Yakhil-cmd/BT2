### Title
Webhook Signature Verification Bound to `repository.owner.login`, Not the `repository.full_name` Handlers Actually Act On - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to verify a webhook using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')`. Every event handler, however, resolves the `Repository`/`Stack` to mutate using a *different* field from the same attacker-controlled JSON body: `payload.dig('repository', 'full_name')`. Nothing ties these two fields together, so a payload can be signed by one organization's webhook secret while pointing at a repository belonging to a completely different organization.

### Finding Description
The controller picks the GitHub App/organization config for signature verification like this: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
```

and `repository_owner` is taken straight from the JSON body: [2](#0-1) 

Once the signature check passes (using *Org B's* secret), the raw JSON is dispatched unmodified to every handler: [3](#0-2) 

Every handler resolves the target `Repository`/`Stack` from `repository.full_name`, a field the verify step never inspects: [4](#0-3) 

Because Shipit explicitly supports hosting several independently-configured GitHub Apps/organizations, each with its own `webhook_secret` (see the multi-org example), the admin/owner of any one onboarded organization already legitimately knows that organization's `webhook_secret` — they set it themselves when they created their own GitHub App: [5](#0-4) 

The equality this breaks is: *"the organization whose secret authenticated the request" == "the repository/stack the request is allowed to act on."* An attacker who legitimately controls Org B can compute a valid `X-Hub-Signature` over any JSON body they like using Org B's secret, but set `repository.owner.login` = `"OrgB"` (to pass `verify_signature`) while setting `repository.full_name` = `"OrgA/victim-repo"` (to drive the handler). Since the signature check only reads `owner.login` and never cross-checks it against `full_name`, the forged payload is accepted and processed against Org A's stack.

Concrete handlers reachable this way:
- `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` for any stack matching the forged `full_name`/branch, using an attacker-chosen `after` SHA: [6](#0-5) 
- `PullRequest::OpenedHandler`, `ClosedHandler`, `ReopenedHandler`, `LabelCapturingHandler` all resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)` and drive Review Stack provisioning/archival for that repository regardless of which org's secret was used to authenticate: [7](#0-6) 
- `MembershipHandler` creates/removes `Shipit::Team`/`Shipit::Membership` records purely from the payload, which gate `Shipit.github_teams` authorization used across the app (`User#authorized?`): [8](#0-7) 

### Impact Explanation
This allows a party who is a legitimate admin of *any one* organization onboarded to a multi-org Shipit instance to forge webhook events that are processed against a *different* organization's stacks, without any credential belonging to that victim organization. Reachable outcomes include triggering unauthorized `GithubSyncJob`/`sync_github` calls against a victim stack with attacker-chosen commit SHAs, and manipulating `membership` events to add/remove team memberships that back `Shipit.github_teams` authorization — an explicit "escalation into `Shipit.github_teams` authorization" (High) impact per the accepted criteria. Depending on how far state diverges (e.g. Review Stack archive/unarchive, forced re-sync), this can also affect what commits/statuses a victim stack considers valid, bordering on unauthorized deploy/rollback triggering via subsequent legitimate UI actions.

### Likelihood Explanation
Requires the attacker to be an onboarded/legitimate organization admin in a multi-organization Shipit deployment (a config pattern the engine explicitly documents and supports), but requires no access whatsoever to the victim organization, no Shipit session, and no API token — only the ability to craft an arbitrary HTTP POST to the shared `/webhooks` endpoint with a signature computed from their own org's secret. The root cause is a straightforward missing cross-field check in `WebhooksController` and `Handler#repository_name`.

### Recommendation
In `WebhooksController#verify_signature`, after determining the organization used for the secret, enforce that `params.dig('repository', 'full_name')` (or `organization.login`, for org-level events) belongs to that same authenticated organization before dispatching to handlers — e.g., reject the request if `repository_owner != repository.full_name.split('/').first` (case-insensitively). Alternatively, resolve the target `Repository`/`Stack` strictly within the verified organization's namespace inside `Shipit::Webhooks::Handlers::Handler#stacks`, rather than trusting an unchecked `full_name` field from the same payload used only for a different field during verification.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own GitHub App and `webhook_secret` (per the documented multi-org config in `config/secrets.development.example.yml`).
2. As the admin of `OrgB` (attacker), craft a JSON push payload:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen-sha>",
     "repository": { "owner": { "login": "OrgB" }, "full_name": "OrgA/victim-repo" }
   }
   ```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgB_webhook_secret, body)>` using the known `OrgB` secret.
4. POST to `/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: "OrgB")`, verifies successfully against `OrgB`'s secret, and the request is dispatched. `PushHandler` then resolves stacks via `Repository.from_github_repo_name("OrgA/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on `OrgA`'s stack — despite the request never having been authenticated against `OrgA`'s secret.
