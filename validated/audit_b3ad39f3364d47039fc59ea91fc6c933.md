### Title
Cross-tenant Status write via unscoped `Commit.where(sha:)` in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by `sha` alone, across the entire `commits` table, and writes a `Status` row to every matching `Commit#stack_id` regardless of which GitHub organization's webhook signature was verified. Because `Commit#sha` has no per-`stack_id` uniqueness constraint or stack-scoping in the query, a webhook signed only with org A's `webhook_secret` can write state visible to org B's stack whenever both stacks contain a `Commit` row with the same sha (e.g., shared history between a public repo and a fork of it).

### Finding Description
The claimed binding is: `org_that_signed(payload) == org_owning(stack_id)` for every `Status` row created by this handler.

Trace:
- `WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-30) resolves `github_app = Shipit.github(organization: repository_owner)` where `repository_owner` (line 59-62) is read straight out of the untrusted payload (`params.dig('repository','owner','login')`), then calls `github_app.verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`), which HMACs the raw body against **that organization's own** `webhook_secret`. This only proves the request was signed by whoever owns `repository_owner` in the payload — the attacker's own org, if the attacker names their own repo. It proves nothing about which `stack_id`s the payload is allowed to affect.
- `StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24) then runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a global lookup with no `stack_id`/repository filter at all.
- `Commit` (app/models/shipit/commit.rb) has `belongs_to :stack` but no `validates :sha, uniqueness: { scope: :stack_id }` or any other constraint preventing the same sha existing under multiple stacks. `Status.replicate_from_github!` (app/models/shipit/status.rb:24-33) writes with `stack_id:` taken from `commit.stack_id`, not from the payload's repository.

Because git commit hashes are content-addressed, a `Commit` row with an identical `sha` legitimately exists in two different stacks whenever one stack tracks a public repository and another stack tracks a fork of it (or any repo sharing history) — no hash collision is required, just shared ancestry. Attacker forks victim's public repo, gets/has their own Shipit `Stack` A configured for the fork (webhook secret = attacker-org's own secret), and their `Commit` table already contains rows for the shared ancestor commits with the same `sha` as rows under the victim's `Stack` B. The attacker then POSTs a `status` webhook event to `/webhooks`, naming `repository.owner.login = attacker-org` (so signature verification passes using the attacker's own secret) and `sha` set to one of the shared-ancestor commit hashes. `StatusHandler#process` finds both `Commit` rows (stack A and stack B) and writes a `Status` to both, even though only stack A's org ever authenticated the request.

No existing guard prevents this: `verify_signature` only checks the payload's own `repository.owner.login` against its own secret; it never checks that the returned `Commit` rows' stacks belong to that same owner. `drop_unhandled_event` and the `ExplicitParameters` schema only validate presence/type of `sha`/`state`, not ownership.

### Impact Explanation
A single, correctly-signed webhook from an attacker's own org can write a `Status` (arbitrary `state`/`description`/`target_url`/`context`) onto a victim stack's commit that the attacker never authenticated for. Because `Commit#deployable?` (app/models/shipit/commit.rb:227-229) and CI-gating logic depend on `success?`/`status`, this can flip a victim commit into "deployable"/CI-green state, potentially triggering `stack.schedule_merges` or continuous delivery (app/models/shipit/commit.rb:379-384) — an unauthorized deploy trigger tied to the impact category "a payload for one repository mutating another's stack, commit, task, or ... an unauthorized deploy." The blast radius is bounded to stacks whose commit history overlaps with a repo the attacker controls (forks/mirrors of the same upstream), but is repeatable for every shared sha and for any victim stack tracking a public/forkable repository.

### Likelihood Explanation
Preconditions: attacker needs (1) a GitHub org/repo they control that is a fork or shares history with the victim's repository, (2) a Shipit `Stack` configured for that repo/org with its own legitimate `webhook_secret` (a normal, low-privilege setup step for any repo the attacker owns, not a Shipit secret), and (3) knowledge of a shared-ancestor commit sha (trivially obtainable via `git log`/GitHub API on the public upstream). No Shipit session, API token, or victim secret is required — only the attacker's own webhook secret, which they legitimately possess for their own stack. This is realistic for any Shipit deployment tracking a public/forkable repository, which is a common case, and is repeatable per shared commit.

### Recommendation
Scope `StatusHandler#process` (and the analogous check-run/other SHA-keyed handlers) to only touch commits belonging to stacks whose repository matches the payload's `repository.full_name`/owner that was actually verified, e.g. `Commit.joins(:stack).where(sha: params.sha, stacks: { repository_owner: ..., repository_name: ... })`, or otherwise scope commit lookups by `stack_id` derived from the verified repository rather than a bare global `sha` match.

### Proof of Concept
Minitest plan (webhooks/status handler test, no live GitHub):
1. Create `stack_a` (repository owned by `attacker-org`) and `stack_b` (repository owned by `victim-org`).
2. Create `Commit.create!(stack: stack_a, sha: "deadbeef" * 5)` and `Commit.create!(stack: stack_b, sha: "deadbeef" * 5)` (identical sha, fixture-equivalent to shared-ancestor-commit scenario).
3. Build a `status` event JSON payload with `repository.owner.login = "attacker-org"`, `sha` = the shared sha, `state = "success"`.
4. Compute `X-Hub-Signature` using **only** `attacker-org`'s configured `webhook_secret` (stub `Shipit.github(organization: 'attacker-org')`).
5. POST to `/webhooks` with `X-Github-Event: status` and the attacker-only signature.
6. Assert: `stack_a.commits.find_by(sha: ...).statuses.count == 1` (expected, attacker's own stack) AND `stack_b.commits.find_by(sha: ...).statuses.count == 1` (this is the violation: `victim-org`'s stack received a `Status` write from a webhook that never verified against `victim-org`'s `webhook_secret`).

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
