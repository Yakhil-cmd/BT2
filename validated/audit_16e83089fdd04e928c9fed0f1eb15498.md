### Title
Fork PR label name (uppercased) is merged unfiltered into the `fetch` step's environment, allowing `SSH_ASKPASS` injection into `PTY.spawn` - (File: app/models/shipit/review_stack.rb, lib/shipit/stack_commands.rb, lib/shipit/command.rb)

### Summary
`ReviewStack#env` merges every pull-request label name (uppercased) into the stack's environment with no allowlist, and `StackCommands#fetch`/`#fetch_commit` pass that unfiltered `env` straight into `Command#start`, which merges it over `BASE_ENV`/`unbundled_env` and hands it to `PTY.spawn`. Unlike `deploy`/`rollback` steps, which are filtered through `DeploySpec#filter_deploy_envs`/`filter_rollback_envs` (an explicit `deploy_variables`/`rollback_variables` allowlist), the git `fetch` path has no such filter, so a label like `ssh_askpass` becomes `SSH_ASKPASS=true` in the environment of the spawned `git fetch`/`git clone` process.

### Finding Description
The broken binding: the invariant should be `fetch_env.keys ⊆ allowlisted_keys` (as is enforced for deploy/rollback via `EnvironmentVariables#permit`), but in fact `fetch_env.keys ⊇ {LABEL_NAME.upcase for every pull_request label}` with no filtering at all.

Path:
- `ReviewStack#env` (`app/models/shipit/review_stack.rb:84-93`) merges `pull_request.labels.each_with_object({}) { |n,h| h[n.upcase] = "true" }` on top of the base stack env, with no key allowlist.
- `pull_request.labels` is populated by `LabelCapturingHandler#capture_labels` (`app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb:98-102`), which stores `params.pull_request.labels.map(&:name)` verbatim from the incoming `pull_request` webhook payload — the schema only requires `name` be a `String` (`label_capturing_handler.rb:29-31`), no charset/format restriction (the handler test even confirms emoji/arbitrary strings are accepted).
- `StackCommands#env` (`lib/shipit/stack_commands.rb:13-15`) is `super.merge(@stack.env)`, and `StackCommands#fetch`/`#fetch_commit` (`stack_commands.rb:17-35`) pass this env directly to `git(...)`/`git_clone` with **no** call to `filter_deploy_envs`/`filter_rollback_envs` (those filters are only applied to `deploy`/`rollback` steps, per `DeploySpec#filter_deploy_envs`/`#filter_rollback_envs`, `app/models/shipit/deploy_spec.rb:174-180`).
- `Command#start` (`lib/shipit/command.rb:85-105`) computes `unbundled_env = BASE_ENV.merge('PATH'=>...).merge(@env.stringify_keys)` — the caller-supplied `@env` (which includes the label-derived `SSH_ASKPASS`) is merged **last**, i.e., it overrides `BASE_ENV`, and is passed directly to `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` (`command.rb:92`).

Exploit flow: An external contributor opens a pull request against a repository configured with `provisioning_behavior: prevent_with_label` (or `allow_with_label`) review-stacks, and applies (or has GitHub apply) a label literally named `ssh_askpass` to their own PR. GitHub sends a legitimately signed `pull_request` webhook (labeled/opened/reopened) to Shipit. `LabelCapturingHandler` stores `"ssh_askpass"` as-is on the stack's `pull_request.labels`. The next time the review stack's `fetch` step runs (triggered automatically whenever Shipit fetches/clones the PR branch), `ReviewStack#env` turns the label into `SSH_ASKPASS => "true"`, `StackCommands#fetch` passes it to `git fetch`/`git clone` unfiltered, and `Command#start` merges it into the child process environment used for `PTY.spawn`. Because git will invoke `$SSH_ASKPASS` whenever it needs to prompt for an SSH credential (e.g., during `ssh` transport, or via `GIT_SSH_COMMAND`/askpass helper invocation on some setups), the attacker names an arbitrary program to be executed on the Shipit deploy host.

Existing guards do not stop this: webhook signature verification only proves the webhook came from GitHub for that repo — it does not restrict label content. `ExplicitParameters` only validates `labels[].name` is a `String`. There is no `EnvironmentVariables#permit`/allowlist call on the `fetch` path (only on `deploy`/`rollback`). `Repository`/`Stack` validations do not touch label-derived env keys.

### Impact Explanation
If SSH-based git transport is used for fetching (or if git otherwise consults `SSH_ASKPASS`/GIT_ASKPASS-adjacent tooling), an attacker-named executable path can be invoked on the Shipit deploy host during the routine, automatic `fetch` step, without any deploy button being pressed. This is a Critical, RCE-class impact via `Command`/`PTY.spawn`, since the label-controlled env variable rides along into every subsequent `git fetch`/`git clone` for that review stack, is repeatable on every fetch cycle, and — because any fork/PR author who can get a label attached to their PR can trigger it — can be repeated against any repository that enables review stacks with `prevent_with_label`/`allow_with_label`.

### Likelihood Explanation
Preconditions: the target repository must have review stacks enabled with a label-based provisioning behavior (`prevent_with_label` or `allow_with_label`), which is a documented, supported Shipit feature, not a misconfiguration. The attacker needs only the ability to open a PR and have a label named `ssh_askpass` attached to it (either because they have label permission themselves, or a maintainer/bot applies labels based on external input) — no Shipit credentials, GitHub App keys, or webhook secrets are required, since the webhook is a normal, correctly-signed GitHub event. Actual RCE also depends on git's transport actually invoking `SSH_ASKPASS` for that stack's remote (e.g., an `ssh://` git remote) — this is an environmental dependency I could not fully verify from the code alone (repo/remote URL scheme config, `Shipit.use_git_askpass?`/`GIT_ASKPASS` interplay in `lib/shipit/commands.rb:37-50`), but the underlying flaw — unfiltered, attacker-controlled env keys reaching `PTY.spawn` for the `fetch` step — is confirmed in code regardless of whether `SSH_ASKPASS` specifically is the exploited variable.

### Recommendation
Apply the same allowlist mechanism used for `deploy`/`rollback` to the `fetch` path: filter `StackCommands#env` (or specifically the env passed into `fetch`/`fetch_commit`) through an explicit allowlist (e.g., a `fetch_variables`/`deploy_variables`-style permit list), and/or strip label-derived environment keys entirely before they reach `Command`. Additionally, `Command#unbundled_env` should not allow caller-supplied `@env` to freely set dangerous keys like `SSH_ASKPASS`/`GIT_ASKPASS`/`LD_PRELOAD`/`GIT_SSH_COMMAND` — a denylist or a strict merge order where trusted `BASE_ENV` values for sensitive keys take precedence over caller-supplied values would close this class of injection.

    def start(&block)
      return if @started

      @control_block = block
      @out = @pid = nil
      FileUtils.mkdir_p(@chdir)
      begin
        @out, child_in, @pid = PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)
        child_in.close
      rescue Errno::ENOENT
        raise NotFound, "#{Shellwords.split(interpolated_arguments.first).first}: command not found"
      rescue Errno::EACCES
        raise Denied, "#{Shellwords.split(interpolated_arguments.first).first}: Permission denied"
      end
      @started = true
      self
    end

    def unbundled_env
      BASE_ENV.merge('PATH' => "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}").merge(@env.stringify_keys)
    end
