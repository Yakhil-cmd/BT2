## Title
CCMenuController#stack bypasses stack-scoping, letting a stack-scoped API token read any stack's build status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
The bug class in the external report is "check the wrong variable": a restriction is validated against one variable but the sensitive operation is performed with a different, unchecked variable. In `Shipit::Api::CCMenuController`, the permission check (`require_permission :read, :stack`) only validates that the authenticated `ApiClient` *has* the `read:stack` permission string; the actual scoping to *which* stack that token is allowed to see is supposed to be enforced by `BaseController#stack`, which resolves the stack through `stacks.from_param!(params[:stack_id])` — and `stacks` filters to `Stack.where(id: current_api_client.stack_id)` when the client is scoped to one stack. `CCMenuController` overrides `#stack` to use `Stack.from_param!(params[:stack_id])` directly, on the full, unscoped `Stack` relation, breaking the binding between "the stack the token authorizes" and "the stack that is actually read."

### Finding Description
`app/controllers/shipit/api/base_controller.rb` defines the intended authorization binding: [1](#0-0) 

`stacks` restricts the queryable set to the client's own `stack_id` when the `ApiClient` is scoped (e.g. the `here_come_the_walrus` fixture, which is created with `stack: shipit`): [2](#0-1) 

`require_permission!` only checks that the permission string (e.g. `read:stack`) is present in the client's `permissions` array — it never checks which stack the client is scoped to: [3](#0-2) 

`CCMenuController` declares `require_permission :read, :stack`, but overrides `#stack` to bypass the scoped `stacks` relation and instead resolve directly against all stacks: [4](#0-3) 

So the "checked" variable is the permission name (`read:stack`) plus the client's identity, while the actually-touched variable is an attacker-supplied `params[:stack_id]` that is never intersected with `current_api_client.stack_id`. This is the direct analog of the "stack a token authorises versus a stack it touches" binding called out in scope: a token minted for stack A (e.g. via `CCMenuUrlController`, which creates a client with `stack: <specific stack>` and a `read:stack`-only permission) can be replayed against any other stack B by simply changing `stack_id` in the URL.

`CCMenuUrlController` shows how such a scoped, low-privilege token is normally generated and handed out (e.g., embedded in CI dashboards, README badges, or CCTray URLs), confirming these tokens are meant to be stack-scoped and are treated as less sensitive than a full API client credential: [5](#0-4) 

### Impact Explanation
Any holder of a legitimate, stack-scoped `read:stack` CCMenu token (which is designed to be shared/embedded, e.g. in build-status widgets) can enumerate `stack_id` values and read the build/deploy status (`stack.deploys_and_rollbacks.last`, `deploy.running?`, `ended_at`, commit/deploy info rendered in `shipit/ccmenu/project`) of **any** stack on the Shipit instance, not just the one it was issued for. This is an authorization-scope bypass leading to unauthenticated-for-that-resource read of stack/deploy state across stacks, matching the in-scope High-severity category "unauthenticated read of stack state, task streams or deploy output" (here, read access exceeding the token's authorized stack scope).

### Likelihood Explanation
High. No secret material, GitHub credentials, or elevated privileges are needed beyond possessing *any* valid `read:stack`-scoped CCMenu token (which by design is meant to be low-sensitivity and widely distributed/embedded, per `CCMenuUrlController`). The attacker only needs to change the `stack_id` query parameter to any other numeric/slug value; the vulnerable code path (`CCMenuController#stack`) is directly reachable via `GET /api/stacks/:stack_id/ccmenu`.

### Recommendation
Remove the `CCMenuController#stack` override so the controller uses `BaseController`'s scoped `stack` method (`stacks.from_param!(params[:stack_id])`), ensuring the `Stack.where(id: current_api_client.stack_id)` restriction is applied identically to every other API controller. If CCMenu needs to resolve stacks by param, it must intersect with `stacks`, not query `Stack` directly.

### Proof of Concept
1. Admin issues a CCMenu token scoped to `stack_id: A` via `CCMenuUrlController#fetch` (`ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(...)`), yielding a token bound to stack A only.
2. Attacker (or anyone who obtains the embedded/shared CCMenu URL for stack A, e.g. from a README badge) sends:
   `GET /api/stacks/B/ccmenu?token=<token-scoped-to-A>`
3. `authenticate_api_client` succeeds (token is valid), `require_permission!(:read, :stack)` succeeds (token has `read:stack`).
4. `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` = stack B directly, ignoring `current_api_client.stack_id == A`.
5. `show` renders stack B's real build/deploy status in the XML response, disclosing stack B's deploy state to a token never authorized for stack B — confirmed by contrasting with `BaseController#stack`, which would have raised `RecordNotFound` via `stacks.from_param!` since `Stack.where(id: A)` does not include B.

```ruby
# frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
```

```ruby
require 'uri'

module Shipit
  class CCMenuUrlController < ShipitController
    def fetch
      uri = URI(api_stack_ccmenu_url(stack_id: stack.to_param))
      uri.query = { 'token' => client.authentication_token }.to_query
      render(json: { ccmenu_url: uri.to_s })
    end

    private

    def client
      @client ||= ApiClient.create_with(permissions: %w[read:stack])
                           .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
    end

    def stack
      @stack ||= Stack.from_param!(params[:stack_id])
    end
  end
end
```
