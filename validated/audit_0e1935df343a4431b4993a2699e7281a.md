### Title
Webhook Signature Verified Against Payload-Chosen Organization While Handlers Act on an Unbound Repository/Team Field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and thus which `webhook_secret`) to validate a webhook's HMAC against based on a value taken from the same untrusted payload it is supposed to authenticate. The field used to select the signing key (`repository_owner`, derived from `repository.owner.login` or `organization.login`) is never bound to the field the downstream handler actually acts on (`repository.full_name` for repo handlers, or `organization.login`/`team.id` for `MembershipHandler`). In a multi-organization Shipit deployment this breaks the equality "organization whose secret authenticated the request == organization/repository the handler writes to."

### Finding Description
`Shipit.github(organization:)` supports per-organization GitHub App configs, each with its own `webhook_secret`, selected via `github_app_config(organization)` [1](#0-0) . The webhooks controller determines which organization's secret to use for signature verification purely from the incoming JSON payload:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

Once the signature check passes for *organization A*, the full raw payload is dispatched unchanged to the registered handler(s), which independently re-read fields from the same payload to decide what to write, e.g. `Handler#repository_name` reads `payload.dig('repository', 'full_name')` [3](#0-2) , and `MembershipHandler#process` / `#find_or_create_team!` reads `params.organization.login` and `params.team.id` to create/find a `Team` and add or remove a `member` from it [4](#0-3) . Nothing re-checks that the organization whose secret produced a valid signature is the same organization named in `repository.full_name` / `organization.login` used by the handler.

Root cause: the signature covers the raw bytes of the payload (so its *contents* can't be tampered with by an outsider), but which *secret* is used to validate those bytes is attacker-influenced via `repository_owner`, and no code enforces `repository_owner == payload.repository.full_name.split('/').first` (or `== payload.organization.login` for membership events).

### Impact Explanation
In a multi-tenant Shipit instance (multiple entries under `secrets.github`, each organization administering its own GitHub App/webhook secret — this is the exact scenario `github_app_config`/`github_organizations` exists to support [5](#0-4) ), the administrator of Organization A knows Organization A's `webhook_secret` (they configured it). Since `Shipit.github(organization:)` is looked up by the payload-controlled `repository_owner`, that administrator can HMAC-sign a payload that names their own org as `repository.owner.login` (satisfying `verify_signature` with their own known secret) while setting the actually-processed fields — `repository.full_name`, or for the `membership` event `organization.login`/`team.id`/`member.login` — to values belonging to a different, victim organization/repository.

For the `membership` event this directly escalates into `Shipit.github_teams` authorization: `MembershipHandler` will `find_or_create_team!` for an arbitrary victim `team.id`/`organization.login` and then `team.add_member(member)`, granting an arbitrary chosen `User` membership in a `Team` the attacker does not administer [6](#0-5) . If that `Team`'s handle is configured in `Shipit.github_teams` (`config.oauth.teams`), this is a path to granting attacker-chosen users deploy/admin authorization without any interaction with GitHub for the victim org — satisfying the High-severity "escalation into `Shipit.github_teams` authorization" criterion.

### Likelihood Explanation
Exploitation requires the attacker to be an administrator/owner of at least one legitimately configured GitHub organization in the same multi-org Shipit deployment (so they possess a valid `webhook_secret` for *some* entry), then send one crafted HTTP request to `/github/webhooks` with a manually computed `X-Hub-Signature`. No GitHub session, `ApiClient` token, or Shipit account is required — only knowledge of one org's own webhook secret, which that org's administrator legitimately possesses. This is realistic in any Shipit deployment that onboards multiple, mutually distrusting GitHub organizations (the exact use case `github_app_config` supports).

### Recommendation
After `verify_signature` succeeds, enforce that the organization used to select the signing secret matches the organization actually referenced by the payload fields the handler will act on (e.g., assert `repository_owner == payload.dig('repository','full_name').to_s.split('/').first` and, for `membership`, assert `repository_owner == payload.dig('organization','login')`), rejecting the request with 422 on mismatch. Alternatively, look up the target `Repository`/`Team`'s configured organization from Shipit's own database (not from the payload) and verify it equals `repository_owner` before invoking any handler.

### Proof of Concept
1. Shipit is configured with two organizations under `secrets.github`: `org-a` (attacker-administered, webhook secret known to attacker) and `org-b` (victim), per the schema handled by `github_app_config` [7](#0-6) .
2. Attacker crafts a `membership` event JSON body:
   ```json
   {
     "action": "added",
     "team": {"id": <victim_team_github_id>, "name": "Deployers", "slug": "deployers", "url": "https://api.github.com/teams/X"},
     "organization": {"login": "org-b"},
     "member": {"login": "attacker-controlled-user"},
     "repository": {"owner": {"login": "org-a"}}
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(org-a's webhook_secret, raw_body)>` and POSTs to the webhooks endpoint with `X-Github-Event: membership`.
4. `verify_signature` calls `Shipit.github(organization: "org-a")` (from `repository.owner.login`), verifies successfully against the attacker's own known secret [8](#0-7) .
5. `MembershipHandler#process` reads `params.organization.login` = `"org-b"` and `params.team.id` = victim team id, creates/finds that `Team`, and adds `attacker-controlled-user` as a member [4](#0-3) , granting cross-organization team membership the attacker never authenticated for.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end

        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
