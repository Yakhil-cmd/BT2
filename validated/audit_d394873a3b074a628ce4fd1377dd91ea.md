### Title
Rounding in headers-commission distribution to multiple earned-commission recipients lets a unit author mint extra bytes (supply inflation) - (File: headers_commission.js)

### Summary
When a payer unit's headers commission is split among several `earned_headers_commission_recipients`, each recipient's share is rounded independently with `Math.round()` and the leftover/deficit is never reconciled against the original `headers_commission` amount. Because rounding is applied per-recipient instead of once with a compensating remainder, the sum of the rounded amounts can exceed the actual commission that was deducted from the payer, letting an attacker who controls the recipient addresses mint bytes that were never actually paid.

### Finding Description
`calcHeadersCommissions` distributes a payer unit's fixed `headers_commission` (an exact, deterministic byte amount computed by `objectLength.getHeadersSize`, enforced in `validation.js`) to the winning child unit's authors. When the child specifies multiple `earned_headers_commission_recipients` (validated only for `sum === 100`, individual shares are unconstrained integers, see [1](#0-0) ), each recipient's cut is computed independently: [2](#0-1) [3](#0-2) 

The code even acknowledges rounding is done "before summing up" without any leftover adjustment: [4](#0-3) . Unlike the MySQL single-recipient path where a full amount is passed through unmodified, the multi-recipient path (`ROUND(punits.headers_commission*earned_headers_commission_share/100.0)`, [5](#0-4) ) and its JS equivalent round every recipient's fraction to the nearest integer independently. Because `Math.round` rounds `.5` up, splitting an odd `headers_commission` value evenly between two attacker-controlled addresses (e.g. 50/50) causes both shares to round up, so the sum paid out (e.g. 22) exceeds the collected commission (e.g. 21).

These per-address sums are inserted into `headers_commission_outputs` (aggregated via `SUM(amount)`, [6](#0-5) ) and later become spendable as `headers_commission`-type payment inputs, whose value is computed purely from this table by `mc_outputs.calcEarnings` and checked in `validatePaymentInputsAndOutputs` ( [7](#0-6) ). There is no cross-check anywhere that the sum of `headers_commission_contributions` for a payer unit equals its declared `headers_commission`, so the extra rounded-up byte(s) become genuinely spendable currency that was never removed from any sender's balance.

### Impact Explanation
Both `earned_headers_commission_recipients` (addresses and integer shares summing to 100) and — since the payer's `headers_commission` is a deterministic function of that unit's own header fields (`objectLength.getHeadersSize`) — the exact commission amount are fully controlled by an ordinary, unprivileged unit poster who authors both the parent and the (sole) winning child unit. By choosing a parent whose `headers_commission` is odd and splitting the commission 50/50 between two addresses they control (or other share combinations that maximize aggregate rounding), the attacker systematically causes the sum of `headers_commission_outputs` to exceed the amount actually deducted as commission. Since this excess becomes spendable base-asset (bytes) that was never paid by anyone, repeating this pattern across many self-authored units constitutes uncapped supply inflation of the network's base currency.

### Likelihood Explanation
The mechanism requires no special privileges, no witnessing majority, and no cooperation from other network participants — only posting ordinary multi-authored units with a crafted `earned_headers_commission_recipients` list, which is explicitly supported and validated functionality (`validateHeadersCommissionRecipients`). The attacker fully controls both the commission amount (via header size) and the split, making the rounding-up outcome deterministic and repeatable at will, bounded only by the cost of unit creation.

### Recommendation
Distribute `headers_commission` (and similarly, `payload_commission` in `paid_witnessing.js`, which has the same per-recipient `Math.round` pattern at [8](#0-7) ) using an allocation method that guarantees the sum of individual shares never exceeds the original amount — e.g., round down for all recipients except the last, and assign the last recipient the remainder (`full_amount - sum of already-rounded shares`), or use a largest-remainder allocation method. Apply the same fix consistently to both the MySQL SQL path and the in-memory/SQLite JS path in `headers_commission.js`.

### Proof of Concept
1. Attacker controls addresses `A1` and `A2`.
2. Attacker posts (or is the sole author/child selected by `getWinnerInfo`) a parent unit `P` whose `headers_commission` is deterministically shaped (by adjusting header content length) to be an odd number, e.g. `21`.
3. Attacker posts the winning child unit `C` of `P` with two authors and:
   ```
   earned_headers_commission_recipients = [
     { address: A1, earned_headers_commission_share: 50 },
     { address: A2, earned_headers_commission_share: 50 }
   ]
   ```
   This passes `validateHeadersCommissionRecipients` since shares sum to 100.
4. When `P` and `C` stabilize, `calcHeadersCommissions` computes for each recipient `Math.round(21 * 50 / 100) = Math.round(10.5) = 11`, giving `A1` and `A2` 11 bytes each — a total of 22, one byte more than the 21 actually collected from `P`.
5. Both `A1` and `A2` can later spend their 11-byte allocation via `headers_commission`-type inputs (`mc_outputs.calcEarnings`/`inputs.js`), meaning 22 bytes become spendable although only 21 were ever removed from a balance.
6. Repeating steps 2–5 across arbitrarily many self-authored unit pairs accumulates unbounded extra bytes, inflating the base-asset supply.

function validateHeadersCommissionRecipients(objUnit, cb){
	if (objUnit.authors.length > 1 && typeof objUnit.earned_headers_commission_recipients !== "object")
		return cb("must specify earned_headers_commission_recipients when more than 1 author");
	if ("earned_headers_commission_recipients" in objUnit){
		if (!isNonemptyArray(objUnit.earned_headers_commission_recipients))
			return cb("empty earned_headers_commission_recipients array");
		var total_earned_headers_commission_share = 0;
		var prev_address = "";
		for (var i=0; i<objUnit.earned_headers_commission_recipients.length; i++){
			var recipient = objUnit.earned_headers_commission_recipients[i];
			if (!isPositiveInteger(recipient.earned_headers_commission_share))
				return cb("earned_headers_commission_share must be positive integer");
			if (hasFieldsExcept(recipient, ["address", "earned_headers_commission_share"]))
				return cb("unknown fields in recipient");
			if (!isValidAddress(recipient.address))
				return cb("invalid recipient address checksum");
			if (recipient.address <= prev_address)
				return cb("recipient list must be sorted by address");
			total_earned_headers_commission_share += recipient.earned_headers_commission_share;
			prev_address = recipient.address;
		}
		if (total_earned_headers_commission_share !== 100)
			return cb("sum of earned_headers_commission_share is not 100");
	}
