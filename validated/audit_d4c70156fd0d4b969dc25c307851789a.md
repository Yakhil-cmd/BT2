### Title
CCMenuController#stack bypasses ApiClient stack scoping even after fallback authentication - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::CCMenuController#stack` resolves the requested stack via `Stack.from_param!(params[:stack_id])` instead of the scoped `stacks.from_param!(params[:stack_id])` used by `BaseController#stack`. This means any authenticated `ApiClient` — including one scoped to a single stack via `stack_id` — can read CCMenu XML for any stack in the system, not just the one it is authorized for, once it passes `authenticate_api_client` by any route (including the Basic-Auth fallback to `super`).

### Finding Description
The binding that should hold is: `stack ∈ current_api_client.stack_id? ? {Stack with id == current_api_client.stack_id} : Stack.all`, i.e. the resolved `stack` must come from `BaseController#stacks` (`app/controllers/shipit/api/base_controller.rb:74-76`), which restricts to `Stack.where(id: current_api_client.stack_id)` when the client is stack-scoped.

`CCMenuController` overrides both `authenticate_api_client` and `stack`:
- `authenticate_api_client` (`app/controllers/shipit/api/ccmenu_controller.rb:33-36`) first tries `ApiClient.authenticate(params[:token])`, and falls back to `super` (Basic-Auth path in `BaseController#authenticate_api_client`, lines 48-61) if the token param fails.
- `stack` (`app/controllers/shipit/api/ccmenu_controller.rb:29-31`) is overridden to `Stack.from_param!(params[:stack_id])`, completely bypassing `stacks` (the scoped relation) regardless of which authentication path set `@current_api_client`.

Attack: attacker holds a legitimate `ApiClient` token for stack C with `read:stack` permission. They send:
`GET /api/stacks/:other_stack_id/ccmenu.xml?token=garbage` with `Authorization: Basic <base64 of stack-C token>`.

Flow: `ApiClient.authenticate('garbage')` returns `nil` (invalid signature caught) → `super` runs → `BasicAuth.authenticate` extracts the valid stack-C credentials → `@current_api_client` is set to the stack-C `ApiClient` → `require_permission!(:read, :stack)` passes because stack-C client has `read:stack` → `CCMenuController#show` calls `stack`, which calls `Stack.from_param!(params[:stack_id])` — an **unscoped** lookup across `Stack.all`, returning the attacker-chosen `:other_stack_id` regardless of `current_api_client.stack_id`.

`check_permissions!` (`app/models/shipit/api_client.rb:38-45`) only checks permission *names* (`read:stack`), not the stack instance itself, so it does not catch this. `stacks` scoping exists precisely to enforce object-level authorization but is never invoked in this controller.

### Impact Explanation
An attacker with a `read:stack` token scoped to a single stack can read CCMenu status/deploy information (branch, last deploy status, timestamps) for **any stack** on the Shipit instance by supplying an arbitrary `stack_id` in the URL, as long as they can pass `authenticate_api_client` via the Basic-Auth fallback path. This is a cross-tenant authorization bypass — unauthenticated-for-that-resource read of stack state — matching the High severity category ("escalation ... unauthenticated read of stack state"). It's fully repeatable against arbitrary stacks with a single valid token, no rate limiting or additional secrets required.

### Likelihood Explanation
Preconditions: attacker must already possess one legitimate, stack-scoped `ApiClient` token (issued through normal, non-privileged means such as being granted `read:stack` for their own stack C). Given the CCMenu endpoint is typically used for CI-status polling and often has looser access expectations, and the query parameter is trivially left invalid/garbage to trigger the fallback, exploitation cost is low: single HTTP GET with a Basic-Auth header and a query param. No GitHub secrets, session, or elevated role needed beyond what's assumed possessed already (a scoped API token) per the ruleset preconditions.

### Recommendation
Change `CCMenuController#stack` to use the scoped `stacks` relation instead of the global `Stack` model:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
This aligns with `BaseController#stack` and ensures the `current_api_client.stack_id` scoping is enforced regardless of which authentication path (token param or Basic-Auth) succeeded.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb
test "ccmenu#show does not leak stacks outside the api client's scope via basic auth fallback" do
  stack_c = shipit_stacks(:shipit)
  other_stack = shipit_stacks(:cocaine) # a different stack fixture

  scoped_client = ApiClient.create!(
    creator: shipit_users(:walrus),
    name: 'scoped-client',
    stack: stack_c,
    permissions: ['read:stack']
  )

  authorization = ActionController::HttpAuthentication::Basic.encode_credentials(
    scoped_client.authentication_token, ''
  )

  get shipit.api_stack_ccmenu_path(other_stack, format: :xml),
      params: { token: 'garbage-invalid-token' },
      headers: { 'Authorization' => authorization }

  # Binding under test: resolved stack must equal a stack within
  # scoped_client's authorized set (stack_c only), never `other_stack`.
  assert_response :success
  refute_includes response.body, other_stack.repo_name
  # This assertion currently FAILS: the response leaks `other_stack`'s
  # CCMenu data because CCMenuController#stack uses Stack.from_param!
  # instead of stacks.from_param!.
end
```
