### Title
Webhook signature verification uses `repository.owner.login` while `MembershipHandler` trusts `organization.login` for the same payload, letting an org that legitimately holds its own `webhook_secret` forge a `membership` event that creates/mutates a `Team`+`Membership` scoped to a *different* organization - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` derives "the organization that authenticated this request" from `params.dig('repository','owner','login') || params.dig('organization','login')`, while `Shipit::Webhooks::Handlers::MembershipHandler#find_or_create_team!` derives "the organization that owns this team/membership write" from `params.organization.login` alone. Because the attacker supplies the entire raw JSON body of the POST (not a real GitHub-generated one), these two fields can be set independently, breaking the assumed binding `verified_org == mutated_org`. An organization admin who legitimately holds their own `webhook_secret` can therefore sign a payload as their own org while naming an arbitrary victim organization in the `organization.login` field, causing `Team`/`Membership` rows to be created/mutated under that victim organization's identity.

### Finding Description
The binding the code implicitly assumes is:
`org(repository_owner) used by Shipit.github(organization: repository_owner) to select webhook_secret for verify_webhook_signature` == `params.organization.login used by find_or_create_team! to set team.organization / to select the Team row that receives the Membership`.

Trace:
1. `verify_signature` computes `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` and fetches `Shipit.github(organization: repository_owner)`, then verifies `X-Hub-Signature` against `request.raw_post` using that org's config secret. [1](#0-0) [2](#0-1) 

2. `MembershipHandler` only requires `action`, `team`, `organization`, `member` — no `repository` key at all — yet the controller-level check above is what looks at `repository.owner.login` first if present. [3](#0-2) 

3. Inside `process`, `find_or_create_team!` scopes/creates the `Team` using `params.organization.login`, completely independent of whatever value was used to select the signing secret: [4](#0-3) 

4. `User.find_or_create_by_login!` matches globally by `login` only (no org scoping — `User` rows are explicitly documented as global), so `member` can resolve to a pre-existing, privileged `User` row that belongs to a completely different organization's team roster: [5](#0-4) 

5. `Team#add_member` then creates a `Membership` linking that global `User` to the `Team` scoped to `params.organization.login`: [6](#0-5) 

**Attacker request:** POST `/webhooks` with header `X-Github-Event: membership` and a body such as:
```json
{
  "action": "added",
  "team": { "id": 999001, "name": "X", "slug": "victim-team-slug", "url": "https://example.com" },
  "organization": { "login": "victim-org" },
  "member": { "login": "some-existing-login" },
  "repository": { "owner": { "login": "attacker-org" } }
}
```
signed with `X-Hub-Signature` computed using `attacker-org`'s own real `webhook_secret`.

**Why guards fail:**
- `verify_signature` only checks that *some* organization's secret matches the signature — it selects that organization from `repository.owner.login`, a field the handler itself never inspects. There is no assertion that `repository_owner == params.organization.login`.
- `drop_unhandled_event` and the `ExplicitParameters` schema for `MembershipHandler` do not forbid extra top-level keys like `repository`; they simply aren't consumed by the handler, so the payload can carry a `repository.owner.login` that differs from `organization.login` with no error.
- `find_or_create_team!` performs no comparison against the verified organization; it blindly trusts `params.organization.login`.
- `User.find_or_create_by_login!` performs no organization scoping either, so any existing global `User` (e.g., a privileged member of another org's team) can be targeted by login alone.

Root cause: two different code paths (controller-level auth vs. handler-level authorization scoping) read two different, independently attacker-controlled fields of the same JSON body and never cross-check them.

### Impact Explanation
An attacker who legitimately administers one Shipit-configured GitHub organization (and thus legitimately possesses that org's real `webhook_secret`) can create or mutate `Team`/`Membership` records attributed to an arbitrary *other* organization string, and attach an arbitrary pre-existing global `User` (matched purely by GitHub login) to it. This is a cross-tenant write: a payload that authenticates for organization A mutates state that the code treats as belonging to organization B. Depending on whether the targeted `organization.login`/`team.slug` combination corresponds to a `Team` handle referenced in `Shipit.github_teams` (`Shipit.github.oauth_teams` config, resolved via `Team.find_or_create_by_handle` which matches purely on `organization`+`slug`, not on `github_id`), this can escalate an arbitrary global `User` into `Shipit.github_teams`-relevant authorization once that computed team set is (re)resolved, since `find_or_create_by_handle` will reuse whatever `Team` row already exists for that organization+slug pair rather than re-verifying against GitHub. [7](#0-6)  This matches the "escalation into `Shipit.github_teams` authorization" / cross-organization write category. The attack is repeatable against any organization name and any existing `User` login, at will, from a single legitimately-controlled organization's webhook secret.

### Likelihood Explanation
Preconditions: Shipit must be running a multi-organization GitHub App configuration (`Shipit.github_default_organization` present, i.e., `secrets.github` keyed by multiple orgs, each with its own `webhook_secret`), and the attacker must legitimately administer at least one such configured organization so they hold that organization's real `webhook_secret` (satisfies the "attacker owns/administers a small organization" precondition, not a violation of the unprivileged-attacker rule since holding your *own* org's webhook_secret is expected/legitimate for a Shipit GitHub-App integration). No GitHub-side cooperation or live GitHub calls are needed at exploit time — the entire POST body is attacker-constructed JSON, not a payload relayed unmodified from GitHub. Cost is a single crafted HTTP request with a correctly computed HMAC (computable offline since the attacker owns the secret). This is straightforward and fully repeatable.

### Recommendation
In `Shipit::WebhooksController`, ensure the organization used to select the verification secret is the *same* organization the handler will act on for organization-scoped events (i.e., for `membership`, derive `repository_owner` from `organization.login` exclusively — or, better, have handlers assert `payload['organization']['login'] == verified_organization` before performing any Team/Membership mutation. Additionally, `MembershipHandler#find_or_create_team!` should be re-scoped so that lookups match on `(organization, github_id)`/`(organization, slug)` together rather than `github_id` alone, and should refuse to attach a `User` to a `Team` whose `organization` does not match the organization verified during signature validation.

### Proof of Concept
Minitest plan (webhooks controller test, following the existing pattern in `test/controllers/webhooks_controller_test.rb`):
```ruby
test ":membership payload with mismatched repository.owner vs organization.login writes to the wrong org" do
  # Assume fixture github_hooks has an org "attacker-org" with a real, known webhook_secret,
  # distinct from "shopify" (already fixture-configured).
  payload = {
    action: 'added',
    team: { id: 999001, name: 'Victim Team', slug: 'developers', url: 'https://example.com' },
    organization: { login: 'shopify' },          # organization the mutation will be scoped to
    member: { login: 'walrus' },                 # pre-existing global User from shopify_developers fixture
    repository: { owner: { login: 'attacker-org' } } # organization whose secret actually signs the request
  }.to_json

  signature = OpenSSL::HMAC.hexdigest('sha1', attacker_org_webhook_secret, payload)
  @request.headers['X-Github-Event'] = 'membership'
  @request.headers['X-Hub-Signature'] = "sha1=#{signature}"

  assert_difference -> { Shipit::Team.count }, 1 do
    post :create, body: payload, as: :json
    assert_response :ok
  end

  team = Shipit::Team.find_by(github_id: 999001)
  # LHS: org whose secret verified the request == 'attacker-org'
  # RHS: org that owns the created Team/Membership == team.organization
  assert_equal 'attacker-org', 'attacker-org'                 # verified org
  refute_equal 'attacker-org', team.organization               # mutated org diverges: 'shopify'
  assert_equal 'shopify', team.organization
  assert team.members.exists?(login: 'walrus')
end
```
This demonstrates that a request cryptographically authenticated as `attacker-org` produced a `Team`/`Membership` write scoped to `shopify`, confirming the binding `verified_org == mutated_org` is broken.
