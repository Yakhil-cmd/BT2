Based on my investigation, the strongest admission-boundary analog to the SAM bug is in the Aptos framework's multisig transaction execution path, specifically the optional/feature-gated payload binding in `multisig_account.move`.

### Title
Multisig transaction execution payload is not bound to the on-chain approved payload when only the full payload (not a hash) is stored, and the binding check is feature-gated - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
`create_transaction` lets an owner store the full transaction payload on-chain (`payload_hash: option::none()`), while `create_transaction_with_hash` stores only a hash (`payload_hash: option::some(hash)`). [1](#0-0)  The VM prologue function `validate_multisig_transaction` is the single place that is supposed to bind "what quorum approved" to "what will actually execute": it hashes the caller-supplied `payload` against `transaction.payload_hash` only `if (transaction.payload_hash.is_some())`, and otherwise only compares the caller-supplied `payload` byte-for-byte against `transaction.payload` `if` a separate feature flag `abort_if_multisig_payload_mismatch_enabled()` is turned on **and** the supplied payload is non-empty. [2](#0-1) 

### Finding Description
For a transaction created via `create_transaction` (the common, gas-cheaper-for-verification-at-approval-time path where the full payload is stored on chain instead of just a hash), the code path that is supposed to enforce "the payload being executed is the one owners voted on" is entirely conditional on the `abort_if_multisig_payload_mismatch_enabled` feature flag. If that flag is not enabled (it is modeled as an incrementally-rolled-out feature, per its name and the surrounding comment "the timelock change added ... as a new abort path" style feature gating seen throughout this module), `validate_multisig_transaction` performs **no comparison at all** between the payload that will actually be executed and the payload that owners approved when they voted. This mirrors the SAM root cause exactly: a privileged-looking admission check (`onlyEditionOwnerOrAdmin`/`onlyBeforeMintConcluded` in SAM, `assert_is_owner` + quorum count here) is satisfied, but the actual state-changing content executed is not the content that was authorized/trusted, because the binding between "who/what was approved" and "what executes" is missing or optional.

Concretely: once `num_approvals >= num_signatures_required` for a given `sequence_number` (which can be satisfied by any k owners approving *some* payload), any owner can call the execution entry point supplying an arbitrary `transaction_payload` (the outer `Multisig.transaction_payload` field in `types/src/transaction/multisig.rs`, which is what actually gets turned into the entry-function/script executable via `as_transaction_executable`). [3](#0-2)  As long as `payload_hash` is `None` (true for every `create_transaction`-created proposal) and the mismatch-check feature is off, this arbitrary payload sails through `validate_multisig_transaction` with zero content verification.

### Impact Explanation
This breaks the fundamental k-of-n security guarantee of the multisig account module: owners who approved transaction #N (e.g., "transfer 1 APT to charity") are not actually approving the entry function that gets executed as the multisig account's signer. Any owner (even a minority, non-quorum owner) who is the one *executing* the transaction can substitute an arbitrary entry function call — including draining coins, rotating auth keys, or adding themselves as a controlling owner via `add_owners` — while the on-chain vote records still show approval for the original, benign payload. This is a critical fund-theft / unauthorized-state-transition primitive scoped to any account using the enhanced multisig standard.

### Likelihood Explanation
Likelihood depends entirely on the default/rollout state of `features::abort_if_multisig_payload_mismatch_enabled`. I was not able to confirm from the code I reviewed whether this flag is enabled by default on mainnet/current releases in this repository snapshot (I ran out of tool budget before locating the feature's default value in `aptos-move/framework/aptos-framework/sources/chain_status.move`/genesis feature list or `types/src/on_chain_config/aptos_features.rs`). If the flag is off (which its being introduced as a gated, incrementally-rolled-out check strongly suggests), then the bypass is trivially and reliably triggerable by any account owner with no special privilege beyond ordinary multisig owner status, requiring no race condition or timing. If it is already enabled everywhere, the exploit is closed for `create_transaction`-created proposals (the hash-based `create_transaction_with_hash` path was never affected).

### Recommendation
Make the payload-matches-what-was-approved check for `create_transaction`-created proposals **unconditional** (not feature-gated), i.e. always require `payload == *transaction.payload.borrow()` when `transaction.payload.is_some()`, regardless of the `abort_if_multisig_payload_mismatch_enabled` flag or whether the supplied `payload` is empty. Additionally, deprecate/disallow empty-payload short-circuiting, since an empty payload argument should never be treated as "skip verification."

### Proof of Concept
1. Owners `A`, `B`, `C` control a 2-of-3 multisig account holding funds.
2. `A` calls `create_transaction(multisig_account, payload_transfer_1_apt_to_charity)` — this stores the full payload on-chain with `payload_hash = None`.
3. `B` calls `approve_transaction(multisig_account, seq)` — quorum (2) is now reached for `seq`.
4. `A` (a legitimate owner acting maliciously) submits the outer `Multisig` transaction with `transaction_payload = Some(EntryFunction(drain_all_funds_to_A))` instead of the approved transfer.
5. If `abort_if_multisig_payload_mismatch_enabled` is disabled, `validate_multisig_transaction` sees `payload_hash.is_none()`, skips the hash check, and (feature disabled) skips the payload-equality check entirely — the prologue passes.
6. The VM executes `drain_all_funds_to_A` as the multisig account's signer, even though nobody voted for it.

**Note on uncertainty:** I could not confirm within the available tool budget (a) the exact current default value of the `abort_if_multisig_payload_mismatch_enabled` feature flag, or (b) the precise Rust-side wiring in `aptos-move/aptos-vm/src/aptos_vm.rs` that serializes `Multisig.transaction_payload` into the `payload: vector<u8>` argument passed to `validate_multisig_transaction`. Both are load-bearing for confirming this is exploitable in the current default configuration versus already mitigated. I recommend a Devin session with full repository/tooling access to verify the feature flag's on-chain default and trace the exact byte-serialization path in `aptos_vm.rs` before treating this as confirmed-exploitable in production.

impl Multisig {
    pub fn as_multisig_payload(&self) -> MultisigPayload {
        MultisigPayload {
            multisig_address: self.multisig_address,
            entry_function_payload: self.transaction_payload.as_ref().and_then(|inner_payload| {
                match inner_payload {
                    MultisigTransactionPayload::EntryFunction(entry) => {
                        Some(entry.as_entry_function_payload())
                    },
                    MultisigTransactionPayload::Script(_) => None,
                }
            }),
        }
    }

    pub fn as_transaction_executable(&self) -> TransactionExecutable {
        match &self.transaction_payload {
            Some(MultisigTransactionPayload::EntryFunction(entry)) => {
                TransactionExecutable::EntryFunction(entry.clone())
            },
            Some(MultisigTransactionPayload::Script(script)) => {
                TransactionExecutable::Script(script.clone())
            },
            None => TransactionExecutable::Empty,
        }
    }
