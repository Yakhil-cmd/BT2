## Finding Confirmed

**Broken binding:** `commit.stack.repository.owner == repository_owner_that_signed_the_request` — this equality is never checked anywhere in the call path.

### Trace

`WebhooksController#verify_signature` only proves the *organization named in `params['repository']['owner']['login']`* signed the raw payload with that organization's `webhook_secret`: [1](#0-0) 

It never binds that verification to which *Stack/Commit rows* the payload is allowed to mutate — that binding is left entirely to the handler.

The base `Handler` class provides exactly the primitive needed to do that binding correctly: a `stacks` helper scoped to `Repository.from_github_repo_name(repository_name)`, derived from the payload's own `repository.full_name`: [2](#0-1) 

But `StatusHandler#process` does **not** use it. It looks up commits globally by SHA alone, with zero repository/stack scoping: [3](#0-2) 

Any `Commit` row anywhere in the database — belonging to any Stack, owned by any organization — whose `sha` column matches `params.sha` gets `create_status_from_github!` called on it, which creates a `Status` and fires: [4](#0-3) [5](#0-4) 

`enable_ci_on_stack` calls `commit.stack.enable_ci!` unconditionally on whatever stack owns the matched `Commit` row — not the stack tied to the webhook's `repository_owner`.

### Why this is real and not just theoretical

Git commit SHAs are content-addressed but **not scoped to a single GitHub repository**. The identical SHA can legitimately exist in two different repositories tracked by two different Shipit stacks — most commonly via forks (a fork initially shares full commit history/SHAs with upstream) or repositories added under different owners that share a common commit history. Since Shipit stores a `Commit` row per stack for every commit it has synced (via `GithubSyncJob`/`Commit.create_from_github!`), if a victim's stack has ever synced a commit whose SHA also exists in an attacker-controlled repo, the attacker can:

1. Own repo `attacker/fork`, verified only under their own org's `webhook_secret`.
2. Send `POST /webhooks` with `X-Github-Event: status`, `repository.full_name = attacker/fork`, `repository.owner.login = attacker-org`, and `sha` equal to a commit SHA that is shared with the victim stack.
3. `verify_signature` passes — it only checks the attacker's own org's secret against the attacker's own payload.
4. `StatusHandler#process` finds **every** `Commit` row with that SHA, including the victim's, and creates a `Status` on it, firing `enable_ci_on_stack` → `commit.stack.enable_ci!` on the victim's `Stack`, regardless of whether that stack has any relation to `attacker/fork`.

This matches the "payload for one repository mutating another's stack" Critical impact category. The same missing-scoping flaw also independently affects `CheckRun#enable_ci_on_stack` via the check_runs path, since check-run creation is similarly keyed by SHA lookups without repository binding.

### Title
Cross-repository Status webhook mutates unrelated Stack's `ci_enabled` state due to unscoped SHA lookup - (`app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves target commits via `Commit.where(sha: params.sha)` with no filter tying the lookup to the repository/organization whose webhook secret was actually verified. An attacker who owns any repository sharing a commit SHA with a victim's tracked stack (e.g., via a fork) can trigger `Status` creation — and thus `Stack#enable_ci!` — on the victim's Stack using only their own, correctly-signed webhook.

### Finding Description
The broken binding, stated explicitly: `commit.stack.repository.owner == repository_owner` (the org verified by `WebhooksController#verify_signature`) is assumed but never enforced. `verify_signature` at [6](#0-5)  authenticates only that the payload was signed by `Shipit.github(organization: repository_owner)`'s secret — it says nothing about which `Commit`/`Stack` rows the payload's `sha` may affect. `StatusHandler#process` at [3](#0-2)  ignores the `stacks` scoping helper provided by the base `Handler` class ( [2](#0-1) ) and instead does a global `Commit.where(sha: params.sha)`, iterating over every matching row across all stacks/tenants. `Status#after_create :enable_ci_on_stack` ( [4](#0-3) [5](#0-4) ) then mutates `commit.stack.ci_enabled` cache for whichever stack owns the matched commit, not the stack belonging to the verified organization.

### Impact Explanation
A `Status` row and a flipped `ci_enabled` cache flag are written to a victim `Stack` that never authenticated the request — a write attributable to one tenant landing on another tenant's record, matching the Critical category "a payload for one repository mutating another's stack". Since `_banners.html.erb` treats `ci_enabled? == false` as "not yet configured for CI, requires a passing build" for `ignore_ci: false` stacks, flipping this flag changes the UI-presented deployability guidance for the victim stack. This is repeatable against any stack whose commit history overlaps (via fork or otherwise) with a repository the attacker controls, and does not require any credential belonging to the victim.

### Likelihood Explanation
Requires only: (1) attacker owns/controls a GitHub repository (no privilege needed), (2) that repository shares at least one commit SHA with a victim Stack Shipit already tracks (trivially achievable by forking the victim's public upstream before or after Shipit syncs it — SHAs are preserved across forks), (3) ability to POST to `/webhooks` (public endpoint). No Shipit secrets, sessions, or GitHub App keys are needed by the attacker. This is straightforward to reproduce and repeat.

### Recommendation
Scope `StatusHandler#process` (and the analogous check-run flow) to the repository that actually signed the webhook: use the base `Handler#stacks` helper (or otherwise join through `Repository.from_github_repo_name(repository_name)`) so only commits belonging to stacks whose repository matches `payload['repository']['full_name']` are updated, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` instead of the global `Commit.where(sha: params.sha)`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status webhook from an unrelated repository cannot flip ci_enabled on a victim stack sharing the same commit sha" do
  victim_stack = shipit_stacks(:shipit) # some existing stack, ignore_ci: false
  Shipit::Status.where(stack_id: victim_stack.id).delete_all
  Shipit::CheckRun.where(stack_id: victim_stack.id).delete_all
  Rails.cache.clear
  assert_not victim_stack.ci_enabled?

  victim_commit = victim_stack.commits.first
  shared_sha = victim_commit.sha

  attacker_repo = Shipit::Repository.create!(owner: 'attacker-org', name: 'fork')
  attacker_stack = Shipit::Stack.create!(repository: attacker_repo, environment: 'production', branch: 'master')
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, message: 'shared', author: shipit_users(:shipit), authored_at: Time.now, committer: shipit_users(:shipit), committed_at: Time.now)

  # Only the attacker's org signature is stubbed as valid; victim's org secret is never involved.
  Shipit.github(organization: 'attacker-org').stubs(:verify_webhook_signature).returns(true)

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'ci/attacker',
    'branches' => [{ 'name' => 'master' }],
    'repository' => { 'full_name' => 'attacker-org/fork', 'owner' => { 'login' => 'attacker-org' } }
  }

  @request.headers['X-Github-Event'] = 'status'
  post :create, body: payload.to_json, as: :json

  assert victim_stack.reload.ci_enabled?, "victim stack ci_enabled flipped by attacker's own webhook, never verified by victim's org"
end
```
