### Title
AA `attestation` formula does not invalidate attestations issued to a previous controller of an address, unlike the core `attested` definition opcode - (File: `formula/evaluation.js`)

### Summary
The core `Definition.validateAuthentifiers` `'attested'` opcode used in address definitions and asset conditions calls `storage.filterAttestedAddresses`, which explicitly excludes any attestation whose unit is older than the address's last `address_definition_change` (i.e. it re-validates that the attestation still applies to the *current* controller of the address). The AA-facing `attestation` formula function (used by oscript/AA definitions via `formula/evaluation.js`) implements the same "is this address attested by X" logic but queries `attestations`/`attested_fields` directly, with no join against `address_definition_changes`, so it never checks whether the address's signing key/definition has changed since the attestation was issued.

### Finding Description
`storage.filterAttestedAddresses` (used by `definition.js` `case 'attested'` at [1](#0-0) ) is intentionally designed so that an attestation is only honored if it is *newer* than the most recent `address_definition_change` for that address: [2](#0-1) 

This is the exact mitigation for the report's bug class: it ensures that if control of an address changes (analogous to an NFT being transferred/burned in the Turnstile report), a stale attestation tied to the previous owner is not honored — the new controller is treated as unattested until re-attested.

However, the `attestation` formula opcode available to Autonomous Agents (`arr[0] === 'attestation'`), which AA developers use in `oscript`/`ojson` conditions (`if:`, `init:`, bounce logic, etc.) to gate fund releases, token issuance, or other AA behavior based on KYC/whitelist attestations, performs the lookup without this safeguard: [3](#0-2) 

Both the "recent unstable" query and the "stable" query select from `attestations`/`attested_fields` joined only to `units`/`unit_authors`/`aa_addresses`, filtered by `attestor_address` and `address` — there is no join to `address_definition_changes` to exclude attestations that predate a change of control over the target address.

### Impact Explanation
Any address that was attested once by a trusted attestor keeps that attestation forever in the eyes of AA logic, even after:
- the address's private key/definition is changed via an `address_definition_change` message (e.g., the original owner sells the address, key is compromised, or address is deliberately handed over to someone else), or
- the address is reused by a different party under a shared/definition-template scheme.

Because AAs commonly use `attestation[[attestors=...]]` to gate high-value actions (e.g., "only KYC'd/whitelisted addresses may withdraw funds", "only attested addresses may mint/redeem an asset"), a new controller of a previously-attested address can pass this check without ever having been vetted by the attestor, and can trigger fund release from an AA (unauthorized spending / AA fund loss) that the AA author and attestor never intended to authorize to this new party. This matches the "unauthorized spending" / "AA fund loss" impact categories.

### Likelihood Explanation
Likelihood is moderate: it requires (a) an AA that relies on the `attestation` formula for access control, and (b) an attested address whose control later changes hands (via `address_definition_change`, key compromise, or resale). Given that attested addresses (KYC/whitelist patterns) are a documented, encouraged AA design pattern in Obyte, and address definition changes are a normal core feature, the preconditions are realistically reachable by any unprivileged AA trigger sender who obtains control of a previously-attested address.

### Recommendation
Make the `attestation` formula function in `formula/evaluation.js` consistent with `storage.filterAttestedAddresses`: join against `address_definition_changes` and require `main_chain_index` (or `latest_included_mc_index`) of the attestation's unit to be greater than the MCI of the last definition change for the attested address, for both the "recent unstable" and "stable" queries, mirroring the logic already implemented at `storage.js:1959-1974`.

### Proof of Concept
1. Address `A` is genuinely KYC'd by attestor `T`, who posts an `attestation` message for `A` (stored in `attestations`/`attested_fields`).
2. An AA `X` is deployed with logic such as `if: "{attestation[[attestors=T]].address == trigger.address}"` (or similar `attestation[[...]]` usage) gating a payout.
3. Later, address `A`'s owner posts an `address_definition_change` (changing signing keys) — control of `A` passes to a new party (e.g., sold, compromised, or handed off).
4. The new controller of `A` sends a trigger unit from address `A` to AA `X`.
5. `formula/evaluation.js`'s `attestation` handler queries `attestations`/`attested_fields` by `address='A'` with no check against `address_definition_changes`, so it returns the old attestation as valid, and AA `X` releases funds/privileges to the new, unvetted controller — whereas the equivalent core `Definition.validateAuthentifiers` `'attested'` check via `filterAttestedAddresses` would have correctly rejected this address, since the attestation's MCI is not newer than the definition-change MCI.
