### Title
Unauthenticated device_address binding in `new_shared_address` handler enables hijack of multisig signing/private-payment routing - (File: wallet_defined_by_addresses.js)

### Summary
The Wekan CVE (CVE-2025-65780) is a mass-assignment/missing-authorization bug: a client can submit an update that touches fields it should not be allowed to control (org/team membership, `loginDisabled`) because the server does not restrict which fields of the target object the caller is permitted to set. The structural analog in ocore is in `handleNewSharedAddress()` in [1](#0-0) : the function validates that the `address` field of each `signers[signing_path]` entry matches the corresponding leaf in the supplied definition, but it never validates or authorizes the `device_address` field that the sender attaches to *other* members' signing paths.

### Finding Description
`new_shared_address` is a device-message subject reachable directly from any paired device via `handleMessageFromHub` in [2](#0-1) , which calls straight into `wallet_defined_by_addresses.handleNewSharedAddress(body, ...)`.

The handler validation logic is: [3](#0-2) 

Only `signerInfo.address` is checked against the addresses extracted from the definition (`extractAddressPathsFromDefinition`). The `device_address` supplied in `body.signers[signing_path]` for every path — including paths that belong to *other* members, not the sending device — is accepted verbatim and persisted unauthenticated via `addNewSharedAddress`: [4](#0-3) 

That `device_address` column in `shared_address_signing_paths` is later used to decide where to forward private-payment chains for the shared address (`forwardPrivateChainsToOtherMembersOfAddresses`): [5](#0-4) 

and (per `wallet.js`/`wallet_general.js` usages of `assocSignersByPath[...].device_address`) to route multisig co-signing requests to the party who is supposed to hold the private key for that path. Because the sender of `new_shared_address` fully controls the `signers` map's `device_address` values for paths it does not own, a malicious cosigner (or malicious correspondent that is one legitimate member of the multisig) can bind an arbitrary/attacker-controlled `device_address` to another member's signing path. This is conceptually the same class of bug as the CVE: the message accepts and persists “extra” privileged fields (routing/ownership metadata) beyond what the sender should be authorized to set for entries that are not its own.

### Impact Explanation
By poisoning `device_address` for a cosigner's signing path, the attacker can cause the victim node to:
- forward outgoing private payment chains for the shared (multisig) address to the attacker's device instead of the legitimate cosigner's device, exposing private payment amounts/addresses to an unauthorized party;
- route future spend/co-signing requests for that shared address to the attacker's device, which can lead to stalled/failed signing (freezing) for the legitimate cosigner, or (depending on downstream signing-request handling) enable the attacker to interfere with fund transfers of a shared multisig address they only partially control.

This matches the "AA/wallet fund loss or freezing" and "private-payment counterparty" categories of impact called out in scope, since it corrupts routing metadata for private multisig payment chains and signing coordination without any check that the sender is authorized to assign device identities to paths belonging to other parties.

### Likelihood Explanation
Reachable by any paired device that can send a `new_shared_address` device message (this includes any correspondent that is nominally one member of the intended multisig group, or — since the address in the `signers` map is checked but the `device_address` is not tied to any registration/pairing proof — potentially any device that knows/guesses the definition and target addresses). No special privilege beyond being a paired correspondent is required to send arbitrary `signers` maps once a shared-address definition hash is known, since `handleNewSharedAddress` is invoked unconditionally for this subject.

### Recommendation
In `handleNewSharedAddress`, cross-check every `device_address` supplied in `body.signers` against a trusted source of truth (e.g., the sending device's own address for its own signing path, and previously-agreed/pending shared-address records — such as `pending_shared_address_signing_paths` — for other members' paths) rather than trusting the value verbatim from the message body. Reject or ignore `device_address` values that were not established through an authenticated pairing/approval flow (`approvePendingSharedAddress`/`create_new_shared_address`) for the given signing path.

### Proof of Concept
1. Device A and Device B (and possibly others) agree via `create_new_shared_address`/`approve_new_shared_address` to form a 2-of-2 (or n-of-n) shared address; suppose signing path `r.1` belongs to Device B's address per the address definition.
2. A malicious Device A, instead of forwarding the legitimately-approved `new_shared_address` message, sends its own crafted `new_shared_address` message to the victim (Device C, another member) with `signers = { "r.0": {address: A_addr, device_address: A_dev}, "r.1": {address: B_addr, device_address: <attacker_device>} }`.
3. `handleNewSharedAddress` in [3](#0-2)  only checks that `B_addr` matches the definition at path `r.1`; it does not verify that `<attacker_device>` is actually Device B.
4. `addNewSharedAddress` stores `<attacker_device>` as the routing device for path `r.1` in `shared_address_signing_paths`.
5. Any future private payment or signing request destined for path `r.1` is now forwarded by Device C to `<attacker_device>` instead of Device B, per `forwardPrivateChainsToOtherMembersOfAddresses` ( [5](#0-4) ) and the general signing-request routing in `wallet.js`/`wallet_general.js`.

function handleNewSharedAddress(body, callbacks){
	if (!ValidationUtils.isArrayOfLength(body.definition, 2))
		return callbacks.ifError("invalid definition");
	if (typeof body.signers !== "object" || Object.keys(body.signers).length === 0)
		return callbacks.ifError("invalid signers");
	try {
		var addr = objectHash.getChash160(body.definition);
	}
	catch (e) {
		return callbacks.ifError("invalid definition: " + e);
	}
	if (body.address !== addr)
		return callbacks.ifError("definition doesn't match its c-hash");
	for (var signing_path in body.signers){
		var signerInfo = body.signers[signing_path];
		if (signerInfo.address && signerInfo.address !== 'secret' && !ValidationUtils.isValidAddress(signerInfo.address))
			return callbacks.ifError("invalid member address: " + JSON.stringify(signerInfo.address));
	}
	const assocDefinitionAddresses = extractAddressPathsFromDefinition(body.definition);
	for (let signing_path in body.signers) {
		const signerInfo = body.signers[signing_path];
		if (assocDefinitionAddresses[signing_path] !== signerInfo.address)
			return callbacks.ifError("signer address at path " + signing_path + " doesn't match definition");
	}
	for (let def_path in assocDefinitionAddresses) {
		if (!body.signers[def_path])
			return callbacks.ifError("no signer for definition address at path " + def_path);
	}
	determineIfIncludesMeAndRewriteDeviceAddress(body.signers, function(err){
		if (err)
			return callbacks.ifError(err);
		validateAddressDefinition(body.definition, function(err){
			if (err)
				return callbacks.ifError(err);
			addNewSharedAddress(body.address, body.definition, body.signers, body.forwarded, callbacks.ifOk);
		});
	});
}
