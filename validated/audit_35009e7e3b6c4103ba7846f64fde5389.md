This is exactly the analog: the BLS12-381 group-operation syscalls call `_unchecked` addition/subtraction functions on caller-supplied points **without any on-curve/subgroup validation**, unlike the Curve25519 path (whose `edwards::add_edwards`/`multiply_edwards` internally validate and return `None` on invalid input, as proven by the test at [1](#0-0) ). This mirrors the reported `ecdh` bug class (CWE-668: accepting a point never checked to be on the curve and using it in cryptographic group arithmetic).

### Title
BLS12-381 group-operation syscalls perform elliptic-curve addition/subtraction on unvalidated (possibly off-curve/off-subgroup) points - (File: syscalls/src/lib.rs)

### Summary
`SyscallCurveGroupOps` handles `BLS12_381_G1`/`BLS12_381_G2` addition and subtraction by calling `solana_bls12_381_syscall::bls12_381_g1_addition_unchecked` / `bls12_381_g2_addition_unchecked` / `..._subtraction_unchecked` directly on the raw, attacker-controlled point bytes translated from VM memory, with no call to a validation routine analogous to `SyscallCurvePointValidation`'s `bls12_381_g1_point_validation`/`bls12_381_g2_point_validation` beforehand. [2](#0-1) [3](#0-2) 

### Finding Description
The point-validation syscall explicitly validates BLS12-381 G1/G2 points via `bls12_381_g1_point_validation`/`bls12_381_g2_point_validation` before returning success/failure: [4](#0-3) 

However, the group-operation syscall for the *same curves* uses functions explicitly named `..._addition_unchecked` / `..._subtraction_unchecked` for add/sub, bypassing that validation entirely: [5](#0-4) [6](#0-5) [7](#0-6) 

By contrast, the Curve25519 Edwards/Ristretto path performs validation internally as part of `add_edwards`/`subtract_edwards`/`multiply_edwards`, demonstrated by the test showing an invalid point causes the group-op syscall to return `1` (failure) rather than silently computing a result: [1](#0-0) 

This is the same bug class as the `ecdh` npm advisory: a cryptographic library/API accepts a caller-supplied elliptic-curve point and performs group arithmetic on it without first checking that the point lies on the curve (or, for pairing-friendly curves, in the correct prime-order subgroup). For BLS12-381 in particular, small-subgroup / invalid-curve points can produce results that leak information about, or otherwise corrupt, values used downstream (e.g., in vote/randomness aggregation schemes that rely on BLS12-381 group operations), since the unchecked path silently returns whatever arithmetic result falls out instead of failing on invalid input.

### Impact Explanation
An unprivileged transaction sender can invoke a BPF program (or ship a purpose-built program) that calls `sol_curve_group_op` with `BLS12_381_G1`/`G2` add or subtract using arbitrary attacker-chosen 48/96-byte point encodings. Because these paths use the `_unchecked` variants, malformed points that are not valid curve points (or not in the correct subgroup) are still processed and yield a "successful" result written back to the caller, rather than being rejected as `Ok(1)`. Any on-chain program logic (present or future) that treats a `SUCCESS` result from `sol_curve_group_op` as proof the inputs were valid group elements would be misled, potentially enabling small-subgroup-style attacks against protocols built on top of this syscall (e.g., forging aggregate signatures, corrupting cryptographic commitments, or bypassing authorization checks that assume validity of curve points used in group operations).

### Likelihood Explanation
High reachability: `sol_curve_group_op` is a permissionless syscall reachable from any BPF program invoked by any submitted transaction once `enable_bls12_381_syscall` is active, requiring no special privileges, and the asymmetry between the validated point-validation syscall and the `_unchecked` group-op path is visible directly in the syscall dispatch code.

### Recommendation
Validate BLS12-381 G1/G2 points (on-curve and correct-subgroup membership) before performing addition/subtraction, either by calling the existing `bls12_381_g1_point_validation`/`bls12_381_g2_point_validation` routines prior to invoking `_unchecked` arithmetic, or by switching to checked addition/subtraction primitives (mirroring how `edwards::add_edwards`/`subtract_edwards` already validate internally), and returning `Ok(1)` for invalid inputs instead of computing over them.

### Proof of Concept
1. Craft a BPF program that invokes `sol_curve_group_op(BLS12_381_G1_LE, ADD, left_addr, right_addr, result_addr)` where `left_addr`/`right_addr` point to 48-byte buffers that are valid field-element encodings but do **not** correspond to points on the BLS12-381 G1 curve (or are on the curve but not in the correct prime-order subgroup) — analogous to the `invalid_bytes` fixtures used for Curve25519 in `syscalls/src/lib.rs:3622-3626`, but for the BLS12-381 encoding.
2. Submit a transaction invoking this program via the syscall interface (`syscalls/src/lib.rs:1457-1576`).
3. Observe that `bls12_381_g1_addition_unchecked` (unlike `edwards::add_edwards`) returns `Some(result_point)` for the invalid input, causing the syscall to report `SUCCESS` and write out an arithmetic result derived from an invalid group element, in contrast to the `Ok(1)` rejection Curve25519 group ops return for invalid points at `syscalls/src/lib.rs:3844`.
