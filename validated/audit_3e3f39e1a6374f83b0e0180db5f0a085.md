### Title
Webhook signature is verified against the organization named in `repository.owner.login`/`organization.login`, while the repository actually acted upon is looked up from the independent `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In multi-tenant Shipit deployments (multiple GitHub organizations, each with its own GitHub App / webhook secret configured via `Shipit.github(organization: ...)`), the webhook controller selects *which* HMAC secret to verify a delivery against using one payload field, but every downstream handler decides *which* repository/stack to mutate using a different, unrelated payload field. These two fields are never cross-checked against each other, breaking the intended binding "organization that authenticated == repository that is written."

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/secret to verify the signature with based on `repository_owner`, which is read straight out of the untrusted JSON body: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` resolves a distinct `GitHubApp` instance (and thus a distinct `webhook_secret`) per organization key found in credentials: [3](#0-2) 

Once `verify_signature` passes (HMAC-SHA1 matches the secret for `repository.owner.login`), `WebhooksController#create` dispatches the *entire* raw payload to handlers: [4](#0-3) 

Every handler, however, determines the target repository/stack from a completely different field, `repository.full_name`, with no re-validation that it is consistent with `repository.owner.login`: [5](#0-4) [6](#0-5) 

Because `owner.login` (used to pick the verifying secret) and `full_name` (used to pick the acted-upon repository) are two independent strings inside the same attacker-supplied JSON body, and GitHub's webhook signature only proves that *some* configured secret produced that body — a tenant who legitimately knows their own organization's webhook secret (because in this per-organization config scheme each org's secret is provisioned independently, see `github_app_config`) can construct a payload whose `repository.owner.login`/`organization.login` is their own org (so it authenticates against their own secret) while `repository.full_name` names a repository belonging to a *different* organization/tenant onboarded to the same Shipit instance. The signature check succeeds, yet the handler acts on the victim tenant's `Repository`/`Stack`.

### Impact Explanation
This breaks the deployment-trust binding "organization that authenticated == repository that is written." Depending on which webhook event/handler is targeted, this can drive cross-tenant/cross-repository effects that are normally gated by knowledge of a specific org's secret: enqueueing `GithubSyncJob` for another org's stack, posting/overwriting commit statuses on another org's commits, or creating/archiving/provisioning review stacks for another org's repository via the `pull_request` handlers. This is a cross-repository write performed with a validly-verified-but-mismatched authentication context, matching the High/Critical "cross-repository writes" impact class.

### Likelihood Explanation
Exploitability requires the attacker to already possess a legitimately-issued webhook secret for *some* organization onboarded to the multi-tenant Shipit instance (i.e., they must be a real, if malicious, tenant with their own configured GitHub App/webhook secret) — this is a low but non-zero privilege bar consistent with the rule's "unprivileged-attacker" framing relative to any *other* tenant's resources, since no access to the victim org's credentials, GitHub App, or Shipit account is required. The multi-organization configuration path (`github_default_organization` non-nil, per-org `secrets.github` entries) must be in use; single-tenant/single-secret deployments are not affected because there is only one secret to authenticate against.

### Recommendation
After signature verification succeeds, cross-check that the organization whose secret matched (`repository_owner`) is consistent with the organization encoded in `repository.full_name` (and any other org identifiers used later in `Handler#repository_name` / `Repository.from_github_repo_name`) before dispatching to handlers; reject the request (422) on mismatch.

### Proof of Concept
1. Deploy Shipit with multi-org config: `secrets.github` contains `orgA: { webhook_secret: "secretA", ... }` and `orgB: { webhook_secret: "secretB", ... }`, and both `orgA/repoA` and `orgB/repoB` are registered as Shipit `Repository`/`Stack` records.
2. Attacker, who administers `orgA` and therefore knows `secretA` (per-org webhook secret they configured when installing/registering their own GitHub App/webhook with this Shipit instance), crafts a `push` (or `pull_request`) JSON body:
   ```json
   {
     "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/repoB" },
     ...
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(secretA, body)>` and POSTs to `/github/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "orgA")`, verifies against `secretA`, and succeeds — see `app/controllers/shipit/webhooks_controller.rb:24-30,59-62`.
5. `Shipit::Webhooks.for_event('push')` handlers run and resolve the target via `payload.dig('repository', 'full_name')` = `"orgB/repoB"` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`), causing the handler to act on `orgB`'s stack (e.g., enqueue a sync job or mutate commit status) despite the signature having been verified with `orgA`'s secret, not `orgB`'s.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
