### Title
`Api::CCMenuController#stack` ignores `current_api_client.stack_id` regardless of whether authentication succeeded via token param or Basic-auth fallback - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Api::CCMenuController#authenticate_api_client` first tries `ApiClient.authenticate(params[:token])` and falls back to `super` (HTTP Basic auth) only when the token param fails, but in both cases `current_api_client` ends up as a stack-restricted `ApiClient`. The controller's own `stack` method (`Stack.from_param!(params[:stack_id])`) never consults `current_api_client.stack_id`, so a client scoped to stack A can request `cc.xml` for stack B and it will be served, independent of which auth branch was taken.

### Finding Description
Binding claimed: `stack` resolved by `CCMenuController#show` should equal a member of `current_api_client`'s authorized stack set, i.e. `stack.id ∈ {current_api_client.stack_id}` when `current_api_client.stack_id?` is true.

Code path:
- `Api::BaseController#stack` correctly scopes lookups: `@stack ||= stacks.from_param!(params[:stack_id])` where `stacks` is `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` [1](#0-0) .
- `Api::CCMenuController` overrides `stack` and drops this scoping entirely: `@stack ||= Stack.from_param!(params[:stack_id])` [2](#0-1) , looking up any stack in the system regardless of `current_api_client.stack_id`.
- `authenticate_api_client` in `CCMenuController` sets `@current_api_client = ApiClient.authenticate(params[:token])` and only calls `super` (the Basic-auth path in `BaseController#authenticate_api_client`) `unless @current_api_client` [3](#0-2) .
- `BaseController#authenticate_api_client` (the `super` path) authenticates via `BasicAuth.authenticate(request)` and also just sets `@current_api_client` to whatever `ApiClient.authenticate(token)` returns, with no stack-scoping check at authentication time [4](#0-3) .
- `require_permission :read, :stack` only calls `current_api_client.check_permissions!('read', 'stack')`, which checks the `permissions` array for the string `"read:stack"` and has no notion of stack IDs at all [5](#0-4) [6](#0-5) .

Because neither `check_permissions!` nor either authentication branch enforces `stack_id`, and because `CCMenuController#stack` bypasses the scoped `stacks` helper entirely, an attacker holding an `ApiClient` restricted to stack A — whether authenticated via the `token` query param or via HTTP Basic auth (`super` fallback) — can request `GET /stacks/:owner/:repo-B/:branch/cc.xml` and have stack B's build status served. This confirms the hole is in `CCMenuController#stack`'s lookup logic itself, not in the choice of authentication mechanism; both the token-param path and the Basic-auth fallback path converge on the same unscoped `stack` method.

### Impact Explanation
An attacker with only a stack-A-scoped API token (Basic-auth-capable or token-param-capable) can read `cc.xml` build/deploy status (latest deploy id, timestamp, running state) for any stack B in the installation, without ever being granted access to stack B. This is an unauthorized cross-tenant read of stack state, matching the High severity category ("escalation ... unauthenticated/unauthorized read of stack state"). It is fully repeatable against arbitrary stacks by varying `params[:stack_id]`, and applies identically whether the attacker authenticates via `?token=` or via `Authorization: Basic`.

### Likelihood Explanation
Precondition: attacker must possess any valid `ApiClient` token restricted to a specific stack (stack A), obtainable if any Shipit operator has issued a scoped token to them (or if leaked). No GitHub secrets, session, or maintainer role are required beyond having a legitimate but narrowly scoped API client. Given that precondition, exploitation cost is a single unauthenticated-in-effect HTTP GET; it is deterministic and repeatable for any stack ID.

### Recommendation
Fix `Api::CCMenuController#stack` to use the same scoped lookup as `BaseController#stack` (i.e., `stacks.from_param!(params[:stack_id])` respecting `current_api_client.stack_id?`), removing the private override or delegating properly, so both the token-param and Basic-auth authentication paths are equally protected.

### Proof of Concept
minitest plan (`test/controllers/api/ccmenu_controller_test.rb`):
1. Create `stack_a` and `stack_b`.
2. Create an `ApiClient` with `stack_id: stack_a.id`, `permissions: ['read:stack']`.
3. Send `GET /stacks/:owner/:repo_b/:branch/cc.xml` with header `Authorization: Basic <base64 of client.authentication_token + ':'>` and an invalid/absent `token` query param (forcing the `super`/Basic-auth branch in `CCMenuController#authenticate_api_client`).
4. Assert response status `200` and that the rendered XML corresponds to `stack_b` (i.e., `current_api_client.stack_id == stack_a.id` but served `stack.id == stack_b.id`), proving `stack.id != current_api_client.stack_id` — the binding is broken via the Basic-auth path exactly as via the token-param path.
5. Repeat with `params[:token] = client.authentication_token` (no Basic header) for stack B to show both branches are equally exploitable.
