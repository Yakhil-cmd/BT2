### Title
Cross-organization team membership injection via `MembershipHandler#find_or_create_team!` ignoring webhook provenance - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#find_or_create_team!` looks up a `Team` solely by `github_id: params.team.id`, without ever verifying that `params.organization.login` (the org that authenticated the webhook via `verify_signature`) matches the `organization` already stored on the existing `Team` record. Because `Team.github_id` is not scoped by the requesting installation, any attacker who controls a valid GitHub App installation for their own org can send a `membership` webhook, correctly signed with their own `webhook_secret`, that references a victim org's existing team by its (guessable/enumerable) numeric `github_id`, causing the attacker's chosen GitHub user to be added as a `Membership` of that victim `Team` row.

### Finding Description
The binding that should hold is: `Team#organization == repository_owner` (the value `WebhooksController#verify_signature` used to select the `webhook_secret` that authenticated the request) for every `Team` row touched by `MembershipHandler`.

Trace:
- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30,59-62`) verifies the payload signature using `Shipit.github(organization: repository_owner)`, where `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')`. This only proves the payload came from *some* org that possesses that org's `webhook_secret` — the attacker's own org, e.g. `attacker-org`.
- `MembershipHandler#process` (lines 22-34) then calls `find_or_create_team!`, which does:
  ```ruby
  Team.find_or_create_by!(github_id: params.team.id) do |team|
    team.github_team = params.team
    team.organization = params.organization.login
  end
  ``` [1](#0-0) 
  The lookup key is `github_id` only. If a `Team` row with that `github_id` already exists (e.g., a victim org's real team, created previously through legitimate config-driven `Team.find_or_create_by_handle`), `find_or_create_by!` returns the **existing** row and the `organization:` assignment block is **never executed** (ActiveRecord only runs the block on creation). No code anywhere checks `team.organization == params.organization.login` before proceeding.
- `process` then does `team.add_member(member)` for `action: 'added'`, appending `member` (a `User` resolved purely from `params.member.login`, itself attacker-controlled) into that pre-existing victim `Team`'s `memberships` association (`app/models/shipit/team.rb:41-43`).

Exploit flow:
1. Attacker registers/owns a GitHub App installation for their own org `attacker-org`, giving them a legitimate `webhook_secret` for that org in Shipit's config.
2. Attacker obtains the numeric `github_id` of a victim team (GitHub team IDs are global integers, discoverable through GitHub's public/team APIs, org events, or prior interactions — not secret, just not "their" team).
3. Attacker crafts a `membership` webhook payload: `{"action":"added","team":{"id": <victim_team_github_id>, "name":..., "slug":..., "url":...}, "organization":{"login":"attacker-org"}, "member":{"login":"attacker_github_login"}}`, signs it with `attacker-org`'s `webhook_secret`, and POSTs to `/webhooks`.
4. `verify_signature` passes (correct secret for `attacker-org`, since `repository_owner` resolves to `attacker-org`).
5. `find_or_create_team!` finds the **victim's existing `Team`** row by `github_id` (ignores `organization.login`), and `team.add_member(User.find_or_create_by_login!('attacker_github_login'))` inserts a `Membership` linking the attacker's user to the victim's team, cross-organization, with no cross-check.

Existing guards do not prevent this: `verify_signature` only authenticates *which org* sent the payload, not *which entities inside the payload* the sender is entitled to reference; the `ExplicitParameters` schema only validates types/presence, not organizational ownership; there is no model validation on `Team` or `Membership` enforcing `organization` consistency on `find_or_create_by!`'s find-path.

### Impact Explanation
An attacker can inject arbitrary `Membership` rows into any `Team` in Shipit's database whose GitHub team ID they know, regardless of which organization the team belongs to. If that team is one of the teams configured in `Shipit.github_teams` (`lib/shipit.rb:256-258`), used by `User#authorized?` (`app/models/shipit/user.rb:80-82`) to gate access, the attacker's own GitHub account gains Shipit authorization it was never granted — a genuine authorization-boundary violation (escalation into `Shipit.github_teams`), and repeatable against any team whose numeric ID is known, across any number of tenants sharing this Shipit instance.

### Likelihood Explanation
Preconditions: attacker needs their own valid GitHub App installation/org configured in Shipit (feasible if Shipit supports multi-org GitHub Apps, i.e., `github_default_organization` is non-nil per `lib/shipit.rb:170-188`), and knowledge of the victim's team's numeric `github_id` (obtainable via GitHub org/team APIs or team-URL metadata, not a secret). No Shipit session, API token, or victim secret is required — only the attacker's own legitimate webhook credential. This is a low-cost, repeatable, unauthenticated-relative-to-victim attack once an attacker has any org onboarded to the same Shipit instance.

### Recommendation
In `MembershipHandler#find_or_create_team!`, cross-check `params.organization.login` against the `organization` of any pre-existing `Team` matched by `github_id`, and reject/no-op (or raise) when they diverge instead of silently reusing/mutating the record; alternatively, scope the lookup by both `github_id` and `organization` (e.g., `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`) and treat an existing `github_id` under a different `organization` as an error condition to be logged and dropped rather than acted upon.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/membership_handler_test.rb`, or similar under `test/`):
```ruby
test "does not add cross-organization member when team.id collides with a different organization's team" do
  victim_team = shipit_teams(:shopify_developers) # organization: 'shopify', github_id: e.g. 1234
  attacker_payload = {
    'action' => 'added',
    'team' => { 'id' => victim_team.github_id, 'name' => victim_team.name, 'slug' => victim_team.slug, 'url' => victim_team.api_url },
    'organization' => { 'login' => 'attacker-org' },
    'member' => { 'login' => 'attacker_user' }
  }

  assert_no_difference -> { Shipit::Membership.count } do
    Shipit::Webhooks::Handlers::MembershipHandler.new(attacker_payload).call
  end

  victim_team.reload
  assert_equal 'shopify', victim_team.organization # binding: organization must remain victim's, unchanged
  refute victim_team.members.exists?(login: 'attacker_user') # attacker must not be added as member
end
```
Assertions on both sides of the binding: before, `Team#organization == 'shopify'` (victim) while the payload authenticates as `'attacker-org'`; after processing, the fix must keep `Team#organization == 'shopify'` and must not create a `Membership` linking `attacker_user` to that team — currently (pre-fix) the second assertion fails because `team.add_member(member)` succeeds unconditionally.
