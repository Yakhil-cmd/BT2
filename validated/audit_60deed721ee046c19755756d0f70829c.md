### Title
Cross-organization webhook confusion allows forging deploy-relevant GitHub events for repositories the attacker does not control - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate an inbound webhook against using an attacker-controlled field (`repository.owner.login` / `organization.login`), while every downstream `Webhooks::Handlers::*` acts on a *different*, independently attacker-controlled field (`repository.full_name`). In a multi-organization Shipit deployment these two fields are never cross-checked, so a payload can be "signed" (or unsigned, if the selected org has no `webhook_secret` configured) against one organization while its `full_name`/`sha` target a stack belonging to a completely different organization.

### Finding Description
`verify_signature` picks the app/secret to verify with like this: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight out of the untrusted JSON body (`params.dig('repository', 'owner', 'login')`), and `Shipit.github(organization: repository_owner)` returns the `GitHubApp` configured for *that* org name, as shown by the multi-org config schema: [3](#0-2) [4](#0-3) 

`verify_webhook_signature` trivially returns `true` when the selected org has no `webhook_secret` configured: [5](#0-4) 

Meanwhile, every handler resolves the *target* repository/stack from a completely separate field of the same attacker-controlled JSON body, `repository.full_name`, with no relation enforced to `repository.owner.login`: [6](#0-5) 

Because the attacker supplies the raw JSON body directly, nothing forces `repository.owner.login` (used for signature selection) to match `repository.full_name`'s owner (used for handler dispatch). An attacker who is a legitimate GitHub user in — or otherwise knows the (possibly blank) webhook secret for — *any* organization onboarded to the same Shipit instance can pick that organization for `owner.login`/`organization.login` to pass `verify_signature`, while setting `repository.full_name` to `victim-org/victim-repo`.

This is compounded by `StatusHandler`, which doesn't even use `repository_name`/`full_name` to scope its effect — it matches purely on commit SHA across the entire installation: [7](#0-6) 

and `PushHandler`, which triggers a GitHub sync (fetching and appending commits, potentially advancing the deploy queue) for any stack whose branch matches: [8](#0-7) [9](#0-8) 

The binding that should hold is: `organization authenticated by signature == organization owning the repository/commit acted upon`. This engine breaks that equality because the field used to select the verification secret and the field used to select the acted-upon repository/commit are independent, both attacker-controlled.

### Impact Explanation
Falls under High/Critical: an attacker onboarded to (or aware of the blank/known secret of) one organization on a shared Shipit instance can forge `push`, `status`, or `check_suite` events attributed to a *different* organization's repositories/stacks without ever knowing that organization's webhook secret. This can inject fabricated commit statuses (`StatusHandler`) that feed into deploy/merge-readiness checks, or trigger `GithubSyncJob` (`PushHandler`) against another organization's stacks — a cross-organization/cross-repository interference with deploy state that the signature check was meant to prevent.

### Likelihood Explanation
Requires the host to run Shipit with multiple GitHub organizations configured (a documented, supported configuration — see `docs/setup.md` "Using Multiple Github Applications"), and requires at least one onboarded organization to have no `webhook_secret` set (also an explicitly supported, `# nil`-documented configuration) or a secret the attacker can otherwise learn. Given multi-org setups are a first-class documented feature and `webhook_secret` is optional per-org, this is plausible in real deployments without needing any privileged Shipit credentials.

### Recommendation
Verify the webhook signature against the organization that actually owns `repository.full_name` (or `organization.login` used consistently), not a value chosen independently by the attacker. Concretely, derive the app/org used for `Shipit.github(organization:)` from the same field the handlers use for repository resolution, and additionally validate in each handler that the authenticated organization matches the owner segment of `repository.full_name` before acting. Also scope `StatusHandler#process` to commits belonging to repositories owned by the verified organization, rather than a global SHA lookup.

### Proof of Concept
1. Configure Shipit with two organizations, `AttackerOrg` (webhook secret unset/blank) and `VictimOrg` (webhook secret set), per `docs/setup.md`'s multi-app schema.
2. As an outside attacker (no Shipit session, no GitHub App key), POST to `/github/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "AttackerOrg" },
    "full_name": "VictimOrg/victim-repo"
  }
}
```
3. `verify_signature` resolves `Shipit.github(organization: "AttackerOrg")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally regardless of the (absent/garbage) `X-Hub-Signature` header.
4. `Handler#repository_name` reads `payload.dig('repository', 'full_name')` == `"VictimOrg/victim-repo"`, and `PushHandler#process` calls `stack.sync_github(expected_head_sha: ...)` on `VictimOrg`'s stack — an action the attacker was never authorized to trigger, without ever supplying `VictimOrg`'s webhook secret.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
