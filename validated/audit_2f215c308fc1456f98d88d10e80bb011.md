This confirms the vulnerability. `Api::CCMenuController#stack` bypasses the stack-scoping that `Api::BaseController#stack` normally enforces.### Title
CCMenu API endpoint ignores an ApiClient's stack scoping, letting a stack-scoped token read CI/build status of any stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
The Sherlock report's root cause is a binding that is enforced on one artifact (signature verifies the payload bytes) but is silently assumed, and never actually checked, to also apply to a second artifact (ownership of the pubkey by the claimed inferer/reputer). The analogous binding in shipit-engine is: *"the `Stack` an `ApiClient` token is scoped to" == "the `Stack` the request actually operates on."* `Api::BaseController` enforces this equality via its `stacks`/`stack` helpers, but `Api::CCMenuController` overrides `stack` in a way that breaks the equality while still relying on the same permission check, so a token scoped to stack A can be used to read data about stack B.

### Finding Description
`Api::BaseController` establishes the general invariant for every API controller: a scoped `ApiClient` (one created with `stack_id` set, e.g. via `CCMenuUrlController#client`) may only touch the stack it was scoped to: [1](#0-0) 

`stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` whenever `stack_id?` is true, and `stack` resolves `params[:stack_id]` **through that restricted relation** (`stacks.from_param!`). This is the mechanism that keeps "the stack a token authorizes" equal to "the stack a token touches."

`Api::CCMenuController`, however, overrides `stack` to bypass this restriction entirely: [2](#0-1) 

It resolves `params[:stack_id]` directly against `Stack.from_param!`, i.e., against *all* stacks, not `current_api_client`'s scoped relation. The only authorization gate left is the class-level `require_permission :read, :stack` declaration, which merely checks that the client's `permissions` array contains `read:stack` — it says nothing about *which* stack: [3](#0-2) 

So the equality the base controller is designed to preserve — `current_api_client.stack_id == stack.id` (when scoped) — is checked by `stacks`/`stack` in `BaseController` but is never checked in `CCMenuController`, exactly mirroring how the pubkey-ownership check was checked for the signature validity but never for identity ownership in the Allora report.

Tokens scoped to a single stack are the norm for this endpoint: `CCMenuUrlController#client` deliberately mints a `read:stack`-scoped `ApiClient` tied to one specific stack precisely so it can be handed out as an unauthenticated-looking CI badge URL: [4](#0-3) 

That token is meant to authorize reads of exactly that one stack. Because `CCMenuController#stack` doesn't consult `current_api_client.stack_id`, the same token, when replayed with a different `stack_id` param, authorizes reads of any stack in the installation.

### Impact Explanation
Any holder of a legitimately-issued, narrowly-scoped `read:stack` CCMenu token (these URLs are routinely shared/embedded in CI dashboards, IRC topics, README badges, etc., under the assumption they only expose one stack's status) can enumerate `stack_id` values and pull build/deploy status (`deploys_and_rollbacks.last`, rendered via the `project.xml` CCMenu view) for every stack in the Shipit instance, including stacks/repositories the token holder has no legitimate access to. This is an authorization-scope bypass: the token holder crosses from "authorized reader of stack A" to "reader of stack state for all stacks," which matches the specified High-impact category of "escalation into ... unauthenticated/under-scoped read of stack state."

### Likelihood Explanation
High. No privileged credentials beyond the already-issued single-stack CCMenu token are required; the attack is a single unauthenticated-looking GET request with a different `stack_id` path/query parameter. `Stack.from_param!` accepts any stack identifier reachable through routing, and no additional check ties the resolved stack back to `current_api_client.stack_id`.

### Recommendation
In `Api::CCMenuController`, resolve `stack` the same way `Api::BaseController` does — through the `stacks` scoping helper (`stacks.from_param!(params[:stack_id])`) — instead of `Stack.from_param!`, so the client's `stack_id` scope (when present) is always enforced, restoring the invariant that a token can only ever touch the stack it was authorized for.

### Proof of Concept
1. As a legitimate but unprivileged user, visit `CCMenuUrlController#fetch` for `stack_id: "org/repoA/production"`. This creates/reuses an `ApiClient` with `permissions: ['read:stack']` and `stack_id` set to `repoA`'s stack, returning a token URL such as:
   `GET /api/stacks/org/repoA/production/ccmenu.xml?token=<TOKEN>`
2. Take the leaked/shared `<TOKEN>` and replay it against a different stack path that the token was never scoped to:
   `GET /api/stacks/org/repoB/production/ccmenu.xml?token=<TOKEN>`
3. `authenticate_api_client` in `CCMenuController` accepts the token via `ApiClient.authenticate(params[:token])` — it authenticates fine because the token itself is valid (it's the same client record). `require_permission :read, :stack` passes because the client has `read:stack`. `stack` then resolves `params[:stack_id]` to `repoB`'s stack directly via `Stack.from_param!`, ignoring that the client's `stack_id` column points at `repoA`.
4. The response renders `repoB`'s latest deploy/rollback status — data the token was never authorized to access — confirming the scope-bypass.
