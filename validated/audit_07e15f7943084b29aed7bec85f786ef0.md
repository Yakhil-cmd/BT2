### Title
Cross-organization commit-status forgery via webhook secret/repository binding mismatch in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates an inbound GitHub webhook by looking up a `GitHubApp` (and its `webhook_secret`) keyed on an organization name read from the payload (`repository.owner.login` or `organization.login`), but the handler that actually mutates state — `Shipit::Webhooks::Handlers::StatusHandler` — never checks that field. It looks up commits **globally by `sha`** with no repository/organization scoping at all. This is the same class of defect as the reported `removeTemplate()` bug: an identity/index used to authorize an operation (`templateIdToIndex` / here, the org used to select the verifying secret) is decoupled from the identity of the object actually written (the template actually deleted / here, the commit and stack actually mutated).

### Finding Description
`WebhooksController#verify_signature` selects which `GitHubApp` (and thus which `webhook_secret`) to verify the signature against using: [1](#0-0) [2](#0-1) 

```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

Shipit explicitly supports **multiple GitHub App configurations, each with its own independent `webhook_secret`**, keyed by organization — this is demonstrated by the test fixture with two distinct orgs/secrets: [3](#0-2)  and the lookup logic in [4](#0-3) .

Once `verify_signature` passes for *whatever* organization the attacker names in `repository.owner.login` (using a secret the attacker legitimately possesses for their own onboarded org), the raw JSON body is dispatched to handlers with no further binding to that verified organization: [5](#0-4) 

`StatusHandler` then does a **global, unscoped** lookup by `sha` across the entire Shipit database (all stacks, all repositories, all organizations) and writes a new commit status: [6](#0-5) 

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

There is no check that the commit's `stack.repository` belongs to the organization/repository that was actually verified. Compare this to `PushHandler`/`CheckSuiteHandler`, which at least filter by `Repository.from_github_repo_name(repository.full_name)` — but even those trust the attacker-supplied `repository.full_name` field, which itself is never cross-validated against `repository.owner.login` (the field the signature check actually used to pick the secret). `StatusHandler` doesn't even do that much — it has no repository/org gate whatsoever.

`create_status_from_github!` creates a real `Status` record from attacker-controlled fields (`state`, `context`, `description`, `target_url`, `created_at`): [7](#0-6) 

This directly feeds `Commit#deployable?` and the continuous-delivery scheduler: [8](#0-7) [9](#0-8) 

### Impact Explanation
On a multi-tenant Shipit install (multiple GitHub Apps/orgs configured, as documented/tested by the engine itself), an attacker who legitimately controls a webhook secret for **their own** onboarded organization can forge a `status` event, sign it with their own secret, set `repository.owner.login` to their own org (so `verify_signature` succeeds), and set `sha` to a real commit SHA belonging to a **victim organization's stack** (SHAs are public on GitHub, not secret). This forges a `success` status on a commit the attacker has no access to. If that stack has `continuous_deployment` enabled, this directly triggers `schedule_continuous_delivery` → `ContinuousDeliveryJob`, producing an **unauthorized deploy** of a commit whose CI/required-status gates were bypassed — matching the Critical impact tier ("unauthorized deploy") explicitly in scope.

### Likelihood Explanation
Exploitation only requires: (1) the Shipit instance to host more than one organization/GitHub App (a documented, supported configuration), and (2) the attacker to be a legitimate but low-privileged tenant with a valid webhook secret for their own org — no access to the victim repository, GitHub org, or Shipit UI is required. The attack is a single crafted HTTP POST with a correctly-computed HMAC using the attacker's own secret; no privileged credentials of the victim are needed.

### Recommendation
In `Handler#stacks`/`StatusHandler#process`, scope all lookups (commits, stacks) to the organization/repository that was actually verified against the webhook secret, and reject the payload if the verified organization does not match the organization implied by the object being mutated (e.g., `commit.stack.repository.owner` must equal the verified `repository_owner`). This should be enforced centrally in `WebhooksController` or in the base `Handler` class so every handler consistently binds the verified identity to the entity being written, analogous to properly deleting/re-indexing `templateIdToIndex` for the exact `id` being removed rather than trusting a stale/uncorrelated index.

### Proof of Concept
Assume a Shipit instance configured with two GitHub Apps/orgs, `OrgAttacker` (secret known to the attacker, who is a legitimate tenant) and `OrgVictim` (unrelated, no access):

1. Attacker finds a real commit SHA on `OrgVictim/repo`'s tracked branch (public on GitHub), e.g. `abcdef123...`, belonging to a Shipit stack with `continuous_deployment: true`.
2. Attacker builds a `status` webhook payload:
```json
{
  "sha": "abcdef123...",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "OrgAttacker" } }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac(OrgAttacker_webhook_secret, body)>` — a signature they can legitimately compute since it's their own secret.
4. POST to `/webhooks` with header `X-Github-Event: status`.
5. `verify_signature` resolves `Shipit.github(organization: "OrgAttacker")` and the signature verifies successfully.
6. `StatusHandler#process` runs `Commit.where(sha: "abcdef123...")` — matching the victim's commit regardless of organization — and creates a forged `success` status.
7. If this satisfies the victim stack's required/blocking statuses, `Commit#schedule_continuous_delivery` fires and an unauthorized deploy is queued for a commit the attacker never had access to.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
