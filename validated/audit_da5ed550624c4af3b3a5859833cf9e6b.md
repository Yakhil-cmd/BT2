### Title
Webhook authenticity is bound to `repository.owner.login`, but the write target is resolved from the unrelated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
This is the same bug class as the BaseTSA report: a mutable, attacker-influenced field is used to decide *whether* a request is authorized, while a *different* field in the same payload decides *what gets written*. In BaseTSA, `sharesReceived` (a derived, resettable value) gated re-processing instead of a fixed per-deposit identifier, letting one deposit's funds be attributed to other users' accounting. In Shipit, `verify_signature` in `WebhooksController` selects which organization's HMAC secret validates the request using `repository.owner.login` (or `organization.login`), while every event `Handler` (e.g. `PushHandler`, `ClosedHandler`) resolves the stack/repository to mutate using the independent `repository.full_name` field via `Repository.from_github_repo_name`.

### Finding Description
`verify_signature` computes the authorizing organization like this: [1](#0-0) [2](#0-1) 

The secret used for HMAC verification is looked up per-organization: [3](#0-2) 

Crucially, `GitHubApp#verify_webhook_signature` unconditionally accepts the request when that organization has no `webhook_secret` configured: [4](#0-3) 

Meanwhile, every handler determines the actually-mutated repository/stack from a **different** JSON field, `repository.full_name`, completely decoupled from `repository.owner.login`: [5](#0-4) [6](#0-5) [7](#0-6) 

The binding that should hold is:
`organization authorizing the request (repository.owner.login → webhook_secret lookup)` == `organization/repository actually mutated (repository.full_name)`

Because these are two independent, attacker-suppliable fields inside one JSON body, and because the verification path can short-circuit to `true` when the resolved organization's `webhook_secret` is unset (a legitimate, documented configuration state for orgs onboarded without a secret, per `Shipit.github_app_config`/multi-org config docs), a request whose `repository.owner.login` maps to an org with no configured secret bypasses signature verification entirely, regardless of the value of `repository.full_name`. The handler then acts on `repository.full_name`, which can point to any other stack/repository tracked by the same Shipit instance.

### Impact Explanation
If any organization in the Shipit installation's multi-org `github` config lacks a `webhook_secret` (a supported and plausible operational state - e.g., an org onboarded before secrets were enforced, or one whose secret was intentionally left blank), `verify_webhook_signature` returns `true` for **any** payload whose `repository.owner.login`/`organization.login` resolves to that org, no matter what signature header is sent or omitted. An attacker who knows (or guesses) the login of such an org can POST an arbitrary, unsigned JSON body to `/webhooks` with `repository.owner.login` set to that org and `repository.full_name` set to a *different*, privileged repository Shipit actually deploys. This reaches handlers such as `PushHandler` (which calls `stack.sync_github(expected_head_sha: ...)`, `Stack#update_deployed_revision`) and `pull_request` handlers (which archive/merge review stacks), producing unauthorized state changes on a repository the attacker never authenticated against - crossing the "unauthorized deploy/rollback/merge" and "cross-repository writes" impact bar without possessing any Shipit session, API token, or the correct repo's webhook secret.

### Likelihood Explanation
This requires the deployment to have at least one organization configured in `Shipit.secrets.github` without a `webhook_secret` (single-org legacy config with a blank `webhook_secret` has the same effect - see `lib/shipit/github_app.rb` line 77, `return true unless webhook_secret`). This is a plausible, silent misconfiguration rather than a default-safe state, since nothing in `WebhooksController` or `GitHubApp` enforces that a secret must be present; the code path is explicitly written to accept unsigned traffic in that case. Given the report's framing (an in-scope, code-level accounting/authorization mismatch, not requiring credentials), this is assessed as a real, reachable analog, though its exploitability in any specific deployment depends on that org-level configuration choice.

### Recommendation
Do not let `repository.owner.login`/`organization.login` (used only to select a verification secret) and `repository.full_name` (used to select the write target) diverge unchecked. Concretely:
1. After signature verification, assert that `repository.full_name`'s owner matches the `repository_owner` used to select the verifying secret; reject on mismatch.
2. Do not silently pass verification when `webhook_secret` is blank for a resolved organization - treat a missing secret as a hard misconfiguration (fail closed) rather than `return true`, per `lib/shipit/github_app.rb` line 77.
3. Prefer binding authorization/scoping directly to the resolved `Repository`/`Stack` record's own configured secret rather than an org-level lookup keyed on a payload field that isn't cryptographically tied to `repository.full_name`.

### Proof of Concept
1. Configure (or find) a Shipit instance with multi-org GitHub app config where org `unsecured-org` has no `webhook_secret` set (`Shipit.github_app_config('unsecured-org')` returns a hash without `webhook_secret`), while org `victim-org` (which owns a real, deployed stack `victim-org/victim-repo`) has a proper secret.
2. POST to `/webhooks` with header `X-Github-Event: push` and a body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "unsecured-org" }, "full_name": "victim-org/victim-repo" }
}
```
No valid `X-Hub-Signature` is required, since `verify_signature` resolves `repository_owner` = `unsecured-org`, `Shipit.github(organization: "unsecured-org").verify_webhook_signature` returns `true` immediately (blank secret) — see `app/controllers/shipit/webhooks_controller.rb` lines 24-30 and `lib/shipit/github_app.rb` lines 76-83.
3. `WebhooksController#create` dispatches to `Shipit::Webhooks::Handlers::PushHandler`, which resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")` (`app/models/shipit/webhooks/handlers/handler.rb` lines 32-38) and calls `stack.sync_github(expected_head_sha: params.after)` on the *victim* stack (`app/models/shipit/webhooks/handlers/push_handler.rb` lines 12-17), causing an unauthorized state change on a repository the request was never authenticated for.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
