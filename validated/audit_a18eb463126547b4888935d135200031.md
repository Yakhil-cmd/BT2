## Title
`MembershipHandler` binds `Team` mutation only by GitHub `team.id`, letting any configured organization hijack another organization's `Team` and inject a member - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

## Summary
`MembershipHandler#find_or_create_team!` looks up `Team` solely by `github_id: params.team.id`, with no check that the found/created team's `organization` matches the webhook's verified `repository_owner`. `WebhooksController#verify_signature` only proves the payload's `X-Hub-Signature` matches *some* configured organization's `webhook_secret`, not that it matches the organization owning the target `Team` row.

## Finding Description
The binding that must hold is: `WebhooksController#repository_owner` (the org whose `webhook_secret` verified the request) `== team.organization` for the `Team` row mutated in `MembershipHandler#process`. It does not.

`WebhooksController#verify_signature` resolves `Shipit.github(organization: repository_owner)` from the payload's own `organization.login`/`repository.owner.login` field [1](#0-0)  and checks the signature against that organization's `webhook_secret` [2](#0-1) . This only proves the request was legitimately sent by *the organization named in the payload* — it says nothing about which `Team` row is targeted.

`MembershipHandler#find_or_create_team!` then does:
```ruby
Team.find_or_create_by!(github_id: params.team.id) do |team|
  team.github_team = params.team
  team.organization = params.organization.login
end
``` [3](#0-2) 
`find_or_create_by!` matches purely on `github_id`. If a `Team` with that `github_id` already exists (created earlier for organization A, e.g. via `Shipit.github_teams`/`Team.find_or_create_by_handle`), the block is **not** executed — `team.organization` is left as whatever it was originally set to (organization A), regardless of what `params.organization.login` (organization B, the attacker's org) says. `MembershipHandler#process` then calls `team.add_member(member)` [4](#0-3) , appending the attacker's `User` (created via `User.find_or_create_by_login!(params.member.login)`) into `Team A`'s `memberships` [5](#0-4) .

**Exploit flow:** An attacker who owns and controls a GitHub organization B, which the Shipit operator has configured as a valid `Shipit.github(organization:)` app (i.e., B has its own `webhook_secret` in `secrets.github`), can craft/send a `membership`/`added` webhook payload with `organization.login = "B"` (satisfies signature verification since it's signed with B's real secret) but `team.id` set to the integer `github_id` of an existing privileged `Team` row belonging to organization A (a member of `Shipit.github_teams`). The attacker fully controls `team.id`, `member.login`, `team.name/slug/url`, and `organization.login` in this payload since the entire body is attacker-authored and only the signature is checked, not field consistency. `find_or_create_by!` finds Team A (matching on `github_id` alone), and `add_member` inserts the attacker's user into Team A's membership, granting them `Shipit.github_teams` authorization via `User#authorized?` [6](#0-5) .

No existing guard prevents this: `verify_signature` only authenticates "org B sent this", `drop_unhandled_event` only filters on event type, and there is no `ExplicitParameters` or model-level check comparing `params.organization.login` to `team.organization` for pre-existing records.

**Precondition/uncertainty:** this requires the Shipit deployment to be configured with `secrets.github` entries for multiple organizations (multi-org GitHub App config, as supported by `Shipit.github_app_config`) and the attacker to control one such org while a target org's `Team#github_id` value is knowable/guessable (GitHub team ids are sequential integers, often enumerable or discoverable). I could not verify from this index alone whether the wiki/production deployment actually enables multi-org configuration in practice — that is an external configuration fact, not code I can confirm further with available tools.

## Impact Explanation
An attacker with no access to Shipit and no `Shipit.github_teams` membership can escalate an arbitrary internet-created GitHub user into a privileged `Team`, gaining `User#authorized?` == true and thus authorization gated by `Shipit.github_teams` (stack access, deploy/rollback permissions, etc., depending on how the host app uses team authorization) — this is a cross-tenant authorization escalation matching the **High** severity category ("escalation into `Shipit.github_teams` authorization"). It is repeatable for any `Team#github_id` the attacker can guess/learn, and only requires one signed webhook per target user added.

## Likelihood Explanation
Requires: (1) the Shipit instance is configured with more than one GitHub organization app (multi-tenant `secrets.github` config) so that an attacker can control a legitimately-configured org's `webhook_secret`; (2) the attacker knows/guesses the numeric GitHub `team.id` (`github_id`) of a target `Team` already present in the `Shipit.github_teams` set. Given these, the attack costs a single crafted HTTP POST to `/webhooks` with a valid HMAC signature computed from the attacker's own `webhook_secret` — fully within reach of an unprivileged attacker controlling their own org's webhook.

## Recommendation
In `MembershipHandler#find_or_create_team!`, require that the existing team's `organization` matches `params.organization.login` before mutating membership; e.g. look up by `github_id` and `organization` together, or explicitly raise/reject if `team.organization != params.organization.login` for a found record before calling `add_member`/`members.delete`.

## Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test "membership webhook from org B cannot add member to org A's team" do
  team_a = shipit_teams(:some_team) # organization: "org-a", github_id: 555

  payload = {
    action: 'added',
    team: { id: team_a.github_id, name: team_a.name, slug: team_a.slug, url: team_a.api_url },
    organization: { login: 'org-b' },
    member: { login: 'attacker' }
  }.to_json

  post shipit.hooks_url,
       params: payload,
       headers: {
         'X-Github-Event' => 'membership',
         'X-Hub-Signature' => webhook_signature_for_org('org-b', payload) # signed with org B's own secret
       }

  assert_response :ok
  team_a.reload
  refute team_a.members.exists?(login: 'attacker'),
    "attacker from org-b must not be added to org-a's team via mismatched organization binding"
end
```
Both sides of the binding to assert: `repository_owner` (derived as `"org-b"` from the payload) must equal `team_a.organization` (`"org-a"`) — they do not, and the test should show the current code fails to reject the mismatch (member gets added), proving the vulnerability.
