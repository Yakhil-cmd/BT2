## Title
Cross-organization stack manipulation via webhook signature/repository binding mismatch - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate a request against using `repository_owner`, derived from `params.dig('repository', 'owner', 'login')` (or the `organization.login` fallback). The signature check only proves the request was signed by *some* configured organization's `webhook_secret`. It never establishes that the *acted-upon* repository — the value used everywhere downstream to select `Stack`/`Repository` records, namely `payload.dig('repository', 'full_name')` in `Shipit::Webhooks::Handlers::Handler#repository_name` — belongs to that same organization.

### Finding Description
`verify_signature` picks the app config by org login and validates the HMAC over the raw body: [1](#0-0) [2](#0-1) 

Every default handler (`PushHandler`, `StatusHandler`, `PullRequest::*Handler`, `CheckSuiteHandler`) resolves the target `Repository`/`Stack` via a *different* field of the same payload — `repository.full_name` — with no cross-check against the `repository.owner.login` used for signature selection: [3](#0-2) [4](#0-3) 

Shipit explicitly documents and supports one GitHub App/`webhook_secret` per organization, all delivered to the same shared `/webhooks` endpoint: [5](#0-4) 

Because the person who configures a GitHub App for their own organization necessarily knows that organization's `webhook_secret` (it is filled in by the org's own installer, per the setup docs), an org onboarded to a shared Shipit instance can compute a valid HMAC-SHA1 signature over an arbitrary payload of their own choosing. Nothing forces `repository.owner.login` (used to select/verify the signing secret) to equal the owner encoded in `repository.full_name` (used to pick the target `Repository`/`Stack`). This is structurally the same class of bug as the Merkle report: a value that is checked/verified (`index` / tree position, here `repository.owner.login`) is decoupled from the value that actually determines the effect that gets applied (`proof` length / leaf position, here `repository.full_name`), because no equality between the two is enforced.

### Impact Explanation
An org that legitimately controls its own GitHub App installation (and therefore its own `webhook_secret`) can forge a signed webhook whose `repository.owner.login` matches its own org (to pass `verify_signature`) while `repository.full_name` names a stack belonging to a *different*, unrelated organization hosted on the same Shipit instance. This lets the low-trust org's operator:
- force `PushHandler` to call `stack.sync_github(expected_head_sha:)` on another org's stacks,
- trigger `PullRequest` handlers that call `stack.archive!` / `stack.unarchive!` or create/destroy `ReviewStack` records via `ReviewStackAdapter.find_or_create!` for another org's repository,
- drive `StatusHandler`/`CheckSuiteHandler` behavior against another org's commits/stacks.

This crosses the "organization that authenticated versus the repository that is written" trust boundary explicitly called out as in-scope, and can result in unauthorized state changes (archiving/unarchiving stacks, creating/destroying review stacks, forcing syncs) on another organization's stack without ever holding a Shipit session, `ApiClient` token, or GitHub write access to that organization/repository.

### Likelihood Explanation
Requires only that the attacking organization be one of the multiple orgs configured on a shared Shipit instance (a documented, supported deployment topology) and be willing to POST a hand-crafted, self-signed payload to the shared `/webhooks` endpoint — no compromise of the victim org's credentials, no session, and no API token is needed.

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler`), enforce that the organization used to select/verify the webhook signature is the same organization encoded in `repository.full_name` (and `organization.login`) before dispatching to handlers — reject the request if they diverge.

### Proof of Concept
Not independently executable from static analysis alone (would require a live multi-org Shipit deployment and knowledge of one org's `webhook_secret`, which the attacker legitimately possesses as that org's own GitHub App owner). Conceptually:
1. Configure Shipit with two orgs, `LowTrustOrg` and `HighTrustOrg`, each with distinct `webhook_secret`s (per `docs/setup.md` "Using Multiple Github Applications").
2. As the administrator of `LowTrustOrg`'s GitHub App (who knows `LowTrustOrg`'s `webhook_secret`), construct a `push` payload with `repository.owner.login = "LowTrustOrg"` and `repository.full_name = "HighTrustOrg/critical-stack"`.
3. Sign the raw body with `LowTrustOrg`'s `webhook_secret` per `Hook::DeliverySigner`/GitHub's HMAC-SHA1 scheme and POST it to `/webhooks` with header `X-Github-Event: push`.
4. `verify_signature` succeeds (uses `LowTrustOrg`'s secret matched against `repository_owner="LowTrustOrg"`), and `PushHandler#stacks` resolves `HighTrustOrg/critical-stack` via `repository.full_name`, triggering `sync_github` on a stack the attacker does not own.
