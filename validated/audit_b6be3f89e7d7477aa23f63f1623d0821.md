### Title
Webhook signature is verified against `repository.owner.login`/`organization.login` but every event handler dispatches on the unchecked `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to check the `X-Hub-Signature` against using `params.dig('repository','owner','login')` (falling back to `params.dig('organization','login')`). Once the signature passes, the same raw payload is handed to the event handlers, which resolve the target `Stack`/`Repository` using a completely different, independently-controlled field: `payload.dig('repository','full_name')`. Nothing ties these two fields together, so the "organization that authenticated" the request is not proven to be the same as the "repository that gets written to."

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb:24-49` picks the HMAC secret to validate against based solely on `repository_owner`:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

This is used only to choose which `Shipit.github(organization:)` app config's `webhook_secret` performs `verify_webhook_signature` [2](#0-1) [3](#0-2) .

Once verification passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the raw, attacker-supplied JSON to handlers [4](#0-3) . Every handler resolves its target repository/stack from a **different** field, `repository.full_name`, via `Handler#repository_name`/`#stacks`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [5](#0-4) 

`PushHandler` uses this to trigger `stack.sync_github` for any non-archived stack matching the branch [6](#0-5) , and `PullRequest::OpenedHandler` independently re-derives the repository from `params.repository.full_name` to auto-provision review stacks [7](#0-6) .

**The broken binding, stated as an equality that the code fails to enforce:**
`organization used to select webhook_secret for signature verification (repository.owner.login / organization.login)` **≠** `organization/repository whose Stack is mutated (repository.full_name)`.

In a Shipit deployment configured for multiple GitHub organizations (explicitly supported — see the multi-org `github:` config block in `config/secrets.development.example.yml:18-38` and `docs/setup.md`), each organization has its own `webhook_secret`. An attacker who legitimately controls (or has push/webhook access to) a repository in Organization A — and therefore can produce a validly-signed webhook payload using Org A's `webhook_secret` — can set `repository.owner.login` (and/or `organization.login`) to `"OrgA"` while setting `repository.full_name` to `"OrgB/tracked-repo"` for any *other* tracked repository already known to this Shipit instance. `verify_signature` will validate the signature against Org A's secret and succeed, then every handler will act on Org B's stack because they never re-check that `full_name`'s owner matches the verified `repository_owner`.

Before the attacker's forged request: Org A's webhook secret only authorizes events for Org A repositories. After the forged request: an Org-A-authenticated payload drives sync/provisioning/status logic for an Org B stack the attacker has no legitimate relationship with — the exact "organization that authenticated versus the repository that is written" trust binding called out as in-scope.

### Impact Explanation
This crosses a genuine authorization boundary between separately-secured GitHub organizations hosted on the same Shipit instance: an entity that only has credentials/webhook access for Organization A can drive state changes (forced re-sync via `PushHandler`, commit `Status` creation via `StatusHandler`, review-stack auto-provisioning via `PullRequest::OpenedHandler`, `check_suite` refresh, `membership`/`Team` mutation) against a completely unrelated Organization B's tracked repository. This matches the "cross-repository writes" / escalation-into-authorization-boundary impact class, since it lets a party authenticated for one org's webhook manipulate state belonging to a different, non-consenting org that only shares the same Shipit deployment.

### Likelihood Explanation
Medium. It requires: (1) a Shipit instance configured with more than one GitHub organization (`github:` multi-org config, explicitly documented as supported), and (2) the attacker to already possess a legitimate GitHub App installation / webhook secret for at least one of those organizations (e.g., they administer or have compromised one org while targeting another org tracked by the same Shipit deployment). This is a realistic multi-tenant scenario for shared Shipit installs, but it does not work against a single-organization deployment where all repos share the same secret.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler`), assert that the organization used to select the `webhook_secret` (`repository.owner.login` / `organization.login`) matches the owner segment of `repository.full_name` before dispatching to any handler. Reject (422) the request if they diverge, so a secret valid for one organization cannot be used to author events against a repository belonging to a different organization.

### Proof of Concept
Given a Shipit instance configured with two organizations, `orgA` (attacker-controlled, secret `SECRET_A`) and `orgB` (victim, tracked stack `orgB/prod-app`):

1. Attacker builds a `push` payload:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef...",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/prod-app" }
}
```
2. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(SECRET_A, payload)` using the legitimately-known `orgA` webhook secret.
3. POST to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` → `"orgA"`, fetches `Shipit.github(organization: "orgA")`, and the signature validates successfully against `SECRET_A` [2](#0-1) .
5. `PushHandler#stacks` resolves the target via `payload.dig('repository','full_name')` → `orgB/prod-app`, and forces `stack.sync_github(expected_head_sha: 'deadbeef...')` on the victim's `orgB` stack [6](#0-5)  — despite the request never being authenticated for `orgB`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
