### Title
`MembershipHandler#find_or_create_team!` reuses an existing `Team` by `github_id` without verifying `organization` matches the payload, allowing cross-org `Membership` injection - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`find_or_create_team!` calls `Team.find_or_create_by!(github_id: params.team.id)` and only sets `team.organization = params.organization.login` inside the `do |team| ... end` block, which Rails executes solely on the **create** branch. When the `github_id` already matches an existing `Team` row, the find branch returns that row untouched, and `process` immediately calls `team.add_member(member)` without ever comparing `team.organization` to `params.organization.login`.

### Finding Description
The broken binding is: `team.organization == params.organization.login` must hold for any `Team` row before `add_member` writes to it, but the code never asserts this on the find path.

Code path: `WebhooksController#create` → `verify_signature` (looks up `Shipit.github(organization: repository_owner)`, where `repository_owner` is read from the *same* untrusted payload via `params.dig('organization', 'login')`) [1](#0-0) [2](#0-1)  → `Shipit::Webhooks.for_event('membership')` → `MembershipHandler#process` → `find_or_create_team!` → `Team.find_or_create_by!(github_id: params.team.id)` (organization only set in the create block) [3](#0-2)  → `team.add_member(member)` [4](#0-3) .

`verify_signature` only proves the request was signed with the webhook secret configured for whatever `organization.login` value appears in the same request body — it does not bind the nested `team.id`/`team` object to that organization. An operator who controls (or is an admin of) any GitHub org onboarded into this Shipit instance knows that org's `webhook_secret` (since they configured the webhook themselves) and can therefore craft and validly sign an arbitrary JSON body, e.g. `organization.login = "attacker-org"` but `team.id` equal to the `github_id` of an already-existing `Team` row belonging to `shopify` (team IDs are discoverable via GitHub's team APIs). `Team.find_or_create_by!` finds the `shopify` team, `find_or_create_team!` returns it as-is, and `team.add_member(member)` inserts a `Membership` linking the attacker-controlled `member` (`User.find_or_create_by_login!(params.member.login)`) into the `shopify` team, while `team.reload.organization` still equals `"shopify"`.

None of the existing guards catch this: `verify_signature` validates *who signed*, not *what the payload's nested fields claim*; the `ExplicitParameters` schema in `params do ... end` only validates types/presence, not cross-field consistency [5](#0-4) ; and `Team` has no uniqueness/consistency validation tying `github_id` to `organization`.

### Impact Explanation
If the collided `Team` is one of `Shipit.github_teams` (teams used for authorization), the injected `Membership` makes `User#authorized?` return `true` for the attacker's controlled `User` record, since it checks `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [6](#0-5) . This is a cross-organization write into `Shipit::Team`/`Shipit::Membership` for a different tenant's team, matching the "escalation into `Shipit.github_teams` authorization" High-severity category. The attack is repeatable against any `Team#github_id` the attacker can discover, from any org onboarded to the Shipit instance.

### Likelihood Explanation
Requires: (1) the target `Team` row to already exist in Shipit's database (created by a legitimate prior membership event from the real org), (2) attacker to control/administer a GitHub org that is itself configured in Shipit with a known `webhook_secret`, and (3) the attacker to know or guess the target team's numeric `github_id`. Given these preconditions (stated explicitly in the prompt), the attack requires only crafting one signed HTTP POST — no GitHub-side event needs to actually occur, since the endpoint accepts direct POSTs with attacker-chosen JSON bodies as long as the HMAC signature matches the org's configured secret.

### Recommendation
In `find_or_create_team!`, after locating/creating the team, explicitly verify `team.organization == params.organization.login` (case-insensitively, matching GitHub's org handling) and raise/reject the event if they differ, before calling `add_member`/`members.delete`. Consider looking up by `organization`+`github_id` (or `organization`+`slug`) together rather than `github_id` alone, and/or updating `team.organization` on find only if changed and validating the change against the actual GitHub API rather than trusting the payload.

### Proof of Concept
Minitest plan (in `test/models/webhooks/handlers/membership_handler_test.rb`):
1. Create `team = Shipit::Team.create!(github_id: 123, organization: 'shopify', slug: 'ops', name: 'Ops')`.
2. Build a membership payload: `{ action: 'added', team: { id: 123, name: 'Ops', slug: 'ops', url: '...' }, organization: { login: 'attacker-org' }, member: { login: 'attacker-user' } }`.
3. Call `Shipit::Webhooks::Handlers::MembershipHandler.new(payload).process` (or invoke via `.call`).
4. Assert `team.reload.organization == 'shopify'` (unchanged) while `Shipit::Membership.exists?(team_id: team.id, user_id: Shipit::User.find_by(login: 'attacker-user').id)` is `true` — proving a cross-organization membership write occurred despite the organization mismatch.
