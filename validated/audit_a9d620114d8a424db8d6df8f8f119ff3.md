### Title
`collect_creator_fee` / `collect_creator_fee_permissionless` bundle both token transfers atomically, so a single stuck/frozen recipient token account permanently freezes all accrued creator fees - ([File: programs/cp-swap/src/instructions/collect_creator_fee.rs])

### Summary
`collect_creator_fee` and `collect_creator_fee_permissionless` each read the full accrued `creator_fees_token_0` / `creator_fees_token_1` balances from `pool_state` and then perform two `transfer_from_pool_vault_to_user` CPIs in the same instruction, zeroing the counters only after both succeed. If either transfer reverts (e.g. because the mint's freeze authority has frozen the creator's associated token account, the mint/token program is paused, or the counterparty token has any other transient/permanent transfer restriction), the whole instruction reverts and the counters are never reset — exactly the same "single transfer failure blocks the whole claim" pattern as the referenced Notional/Aura `claimRewardTokens` finding.

### Finding Description
Both fee-claim instructions collect two tokens' worth of accumulated fees in one atomic call: [1](#0-0) 

and the permissionless variant behaves identically: [2](#0-1) 

Both use `transfer_from_pool_vault_to_user`, which performs a raw `transfer_checked` CPI with no failure isolation between the two calls: [3](#0-2) 

The fee counters `creator_fees_token_0` / `creator_fees_token_1` are only zeroed after both transfers complete successfully. Because Anchor/Solana instructions are atomic, if the token_1 transfer fails for any reason (frozen destination account via the mint's `freeze_authority` — a base SPL/Token-2022 mint field not screened by `is_supported_mint`, a paused token program, or any other CPI-level transfer failure), the entire instruction reverts, including the already-successful token_0 transfer's effect being rolled back and the counters remaining unchanged. There is no per-token try/partial-claim logic, no withdrawal-pattern fallback, and no way to collect the still-healthy token_0 fee independently of the stuck token_1 fee.

Since `collect_creator_fee_permissionless` is callable by anyone but always routes to the fixed ATA owned by `pool_creator` (`associated_token::authority = creator`), the destination accounts are deterministic and cannot be substituted by any caller — if that specific ATA becomes frozen/unusable, every future call (permissioned or permissionless) to collect creator fees for that pool will keep failing, and the accrued balances in `pool_state.creator_fees_token_0/1` become permanently unclaimable.

### Impact Explanation
Creator fees are pool-creator funds that the protocol design promises will accrue and be withdrawable via `collect_creator_fee`/`collect_creator_fee_permissionless`. If the recipient's associated token account for either token side becomes frozen or otherwise transfer-restricted (a realistic condition for many real-world mints with a `freeze_authority`, e.g. regulated stablecoins), the bundled, all-or-nothing transfer logic permanently locks both the token_0 and token_1 accrued creator fees — even the fee for the token side that is still perfectly transferable. This is a permanent freezing of user (pool-creator) funds with no on-chain recovery path, matching the Medium severity of the referenced report.

### Likelihood Explanation
The precondition (a token with a freeze authority freezing the specific recipient ATA, or any other durable transfer failure on the token program side) is plausible and outside the swapper/LP/attacker's control per se, but does not require any privileged action within this program — it only requires reaching `collect_creator_fee_permissionless` (open to any caller) while one side's mint has an active freeze authority, which is common among real-world token deployments (e.g. USDC-style tokens) that raydium-cp-swap explicitly supports pairing with (Token-2022/legacy SPL tokens are both permitted as vault mints). No protocol-admin privilege is needed to trigger the DoS once such a freeze occurs.

### Recommendation
Decouple the two token transfers so that a failure on one side does not block collection of the other:
- Perform each token's transfer and counter reset independently (e.g., wrap each transfer, and only zero/decrement the corresponding counter for the token that actually succeeded), rather than requiring both to succeed atomically.
- Alternatively, adopt a withdrawal/pull pattern per token side, or allow retrying collection of just the token that is currently transferable while leaving the stuck token's balance queued.

### Proof of Concept
1. Create a pool where the base/quote mint has an active `freeze_authority` (this is a base Mint field on both legacy SPL Token and Token-2022 and is not filtered by `is_supported_mint`'s extension checks in `programs/cp-swap/src/utils/token.rs`).
2. Accrue nonzero `creator_fees_token_0` and `creator_fees_token_1` via normal swaps (`swap_base_input`/`swap_base_output`), which call `pool_state.update_fees(...)`.
3. Have the mint's freeze authority freeze the pool creator's associated token account for token_1 (external event, analogous to the USDC-blacklist scenario cited in the original report).
4. Call `collect_creator_fee` or `collect_creator_fee_permissionless`: the token_0 transfer would succeed but the token_1 `transfer_checked` CPI reverts because the destination account is frozen, causing the whole instruction to fail and `creator_fees_token_0/1` to remain unchanged.
5. Every subsequent call fails identically, permanently locking both the frozen token's and the healthy token's accrued creator fees since they are only ever combined in one atomic instruction.

pub fn collect_creator_fee(ctx: Context<CollectCreatorFee>) -> Result<()> {
    let mut pool_state = ctx.accounts.pool_state.load_mut()?;
    let creator_fees_token_0 = pool_state.creator_fees_token_0;
    let creator_fees_token_1 = pool_state.creator_fees_token_1;
    if creator_fees_token_0 == 0 && creator_fees_token_1 == 0 {
        return err!(ErrorCode::NoFeeCollect);
    }

    let signer_seeds: &[&[u8]] = &[crate::AUTH_SEED.as_bytes(), &[ctx.bumps.authority]];

    transfer_from_pool_vault_to_user(
        ctx.accounts.authority.to_account_info(),
        ctx.accounts.token_0_vault.to_account_info(),
        ctx.accounts.creator_token_0.to_account_info(),
        ctx.accounts.vault_0_mint.to_account_info(),
        ctx.accounts.token_0_program.to_account_info(),
        creator_fees_token_0,
        ctx.accounts.vault_0_mint.decimals,
        &[signer_seeds],
    )?;

    transfer_from_pool_vault_to_user(
        ctx.accounts.authority.to_account_info(),
        ctx.accounts.token_1_vault.to_account_info(),
        ctx.accounts.creator_token_1.to_account_info(),
        ctx.accounts.vault_1_mint.to_account_info(),
        ctx.accounts.token_1_program.to_account_info(),
        creator_fees_token_1,
        ctx.accounts.vault_1_mint.decimals,
        &[signer_seeds],
    )?;

pub fn transfer_from_pool_vault_to_user<'a>(
    authority: AccountInfo<'a>,
    from_vault: AccountInfo<'a>,
    to: AccountInfo<'a>,
    mint: AccountInfo<'a>,
    token_program: AccountInfo<'a>,
    amount: u64,
    mint_decimals: u8,
    signer_seeds: &[&[&[u8]]],
) -> Result<()> {
    if amount == 0 {
        return Ok(());
    }
    token_2022::transfer_checked(
        CpiContext::new_with_signer(
            *token_program.key,
            token_2022::TransferChecked {
                from: from_vault,
                to,
                authority,
                mint,
            },
            signer_seeds,
        ),
        amount,
        mint_decimals,
    )
}
