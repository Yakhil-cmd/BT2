### Title
Webhook signature is verified against an organization identity that is independent from the repository the payload actually writes to - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App/organization secret to check the `X-Hub-Signature` against using `repository_owner`, derived from `params.dig('repository','owner','login')` (falling back to `params.dig('organization','login')`). The event handlers, however, resolve the target `Repository`/`Stack` to act on using a *different* field of the same untrusted JSON body: `payload.dig('repository','full_name')` in `Shipit::Webhooks::Handlers::Handler#repository_name`. Because both fields live in the same attacker-supplied POST body and are read independently, the identity that is cryptographically authenticated (`repository.owner.login`) is not bound to the identity that is actually written to (`repository.full_name`).

### Finding Description
- Verification path: `app/controllers/shipit/webhooks_controller.rb` `verify_signature` calls `Shipit.github(organization: repository_owner)` and then `github_app.verify_webhook_signature(...)`, where `repository_owner` is read directly from the unverified JSON body. [1](#0-0) [2](#0-1) 
- `verify_webhook_signature` in `lib/shipit/github_app.rb` returns `true` unconditionally when no `webhook_secret` is configured for that organization: `return true unless webhook_secret`. [3](#0-2) 
- Write path: every handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, PR handlers, etc.) resolves the affected stacks via `Handler#stacks`/`#repository_name`, which reads `payload.dig('repository', 'full_name')` — a completely separate key from the one used for signature-organization selection. [4](#0-3) [5](#0-4) 

Equality that should hold but does not:
`organization used to select/verify signature (repository.owner.login)` ≡ `organization/repository actually mutated by the handler (repository.full_name)`

Before the attacker's request: for a legitimate GitHub webhook these two fields are always consistent (GitHub always sets `repository.owner.login` to match the owner segment of `repository.full_name`), so the binding holds implicitly, never enforced explicitly.

After a crafted request: an attacker who is not a Shipit user, has no `ApiClient` token, and has never seen `webhook_secret` can submit an arbitrary JSON body directly to the public `/webhooks` endpoint (no CSRF token required — `skip_before_action :verify_authenticity_token`) with:
```json
{
  "repository": {
    "owner": { "login": "org-with-no-secret-configured" },
    "full_name": "victim-org/victim-repo"
  },
  ...
}
```
`repository_owner` resolves to `"org-with-no-secret-configured"`. If that Shipit-configured GitHub organization has no `webhook_secret` set (a valid, supported configuration per `Shipit::GithubApp#initialize`, `@webhook_secret = @config[:webhook_secret].presence`), `verify_webhook_signature` returns `true` regardless of signature/header value. The handler then resolves `stacks` using `repository.full_name = "victim-org/victim-repo"`, i.e. a repository entirely unrelated to the organization whose (absent) secret was used to pass verification.

### Impact Explanation
This lets an unauthenticated, unprivileged external party trigger authenticated-looking GitHub webhook side effects against any Shipit-tracked repository/stack, as long as at least one configured GitHub organization in the multi-org Shipit deployment has no `webhook_secret` set (or its secret is otherwise satisfied) — a configuration explicitly supported by `github_app.rb` (`return true unless webhook_secret`, and the test suite even exercises "sends without signature if no secret is configured" for outbound hooks, showing blank secrets are an accepted operational mode). Depending on event type this can:
- Force `GithubSyncJob`/`stack.sync_github` runs against a victim stack via forged `push` payloads.
- Inject forged commit `status`/`check_suite` results that influence deploy-readiness (`deployable?`), potentially enabling an unauthorized deploy on a stack that requires green CI.
- Create/mutate `Team`/`Membership` records via the `membership` handler for an organization the attacker does not control (if `organization.login` can similarly be desynced from the org actually receiving the membership write).

This crosses the "repository/organization authenticated vs. repository/organization written" boundary explicitly called out as in-scope, and can escalate into unauthorized-deploy conditions (falls under the Critical impact category: "an unauthorized deploy").

### Likelihood Explanation
Requires no credentials, no session, and no prior access — only knowledge (or discovery) that Shipit is configured with multiple GitHub organizations and that at least one has no `webhook_secret` configured (a state explicitly supported and tested in this codebase, e.g. `Hook`/webhook tests for "sends without signature if no secret is configured"). In single-organization deployments with a secret always set, this analog does not apply directly, so exploitability is conditioned on a specific, but supported and plausible, multi-tenant configuration. This keeps likelihood Medium rather than trivially universal, but the code path itself contains no check preventing the divergence regardless of configuration.

### Recommendation
In `WebhooksController#verify_signature`, do not select the verification key/app purely from an attacker-controlled field; instead, after verification, re-derive the acting repository/organization from the payload and assert it belongs to the same organization whose secret validated the signature (or verify per-repository rather than per-claimed-owner). At minimum, `Handler#repository_name` should cross-check `payload.dig('repository','owner','login')` equals the owner segment of `payload.dig('repository','full_name')`, and reject events where they diverge, in addition to requiring a `webhook_secret` for every configured GitHub organization (fail closed rather than `return true unless webhook_secret`).

### Proof of Concept
1. Configure Shipit with two GitHub organizations: `org-a` (has `webhook_secret` set) and `org-b` (no `webhook_secret`, i.e. `webhook_secret: null` in `secrets.json`, a supported configuration per `lib/shipit/github_app.rb`).
2. As an anonymous attacker, `POST /webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef...",
  "repository": {
    "owner": { "login": "org-b" },
    "full_name": "org-a/victim-repo"
  }
}
```
No valid `X-Hub-Signature` header is required (any value is accepted).
3. `verify_signature` computes `repository_owner = "org-b"`, calls `Shipit.github(organization: "org-b")`, whose `verify_webhook_signature` short-circuits `true` because `org-b` has no secret. [6](#0-5) 
4. `Shipit::Webhooks.for_event('push')` invokes `PushHandler`, which resolves `stacks` via `payload.dig('repository','full_name') == "org-a/victim-repo"` and calls `stack.sync_github(...)` on stacks belonging to `org-a`, an organization whose secret was never checked. [4](#0-3) [5](#0-4)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
