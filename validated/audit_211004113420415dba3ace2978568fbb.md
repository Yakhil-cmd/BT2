### Title
Missing `onlyRegisteredToken` Guard in `handleERC20Transfer` Allows Bridge Operators to Drain Arbitrary ERC20 Tokens — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

---

### Summary

`BridgeTransferERC20.handleERC20Transfer` accepts an arbitrary `_tokenAddress` parameter from any registered operator and immediately transfers tokens from the bridge contract to any `_to` address, without verifying that `_tokenAddress` is a whitelisted (registered) token. The outbound path (`_requestERC20Transfer`) correctly enforces `onlyRegisteredToken`, but the inbound handle path does not. A malicious or compromised operator (or colluding operators meeting the threshold) can drain any ERC20 token held by the bridge by supplying a fabricated request hash and an unregistered token address.

---

### Finding Description

`_requestERC20Transfer` (the outbound deposit path) applies both `onlyRegisteredToken(_tokenAddress)` and `onlyUnlockedToken(_tokenAddress)` modifiers: [1](#0-0) 

`handleERC20Transfer` (the inbound withdrawal path) applies only `onlyOperators` and then unconditionally calls `IERC20(_tokenAddress).safeTransfer(_to, _value)`: [2](#0-1) 

The `onlyRegisteredToken` modifier in `BridgeTokens` enforces that `registeredTokens[_token] != address(0)`: [3](#0-2) 

Because `handleERC20Transfer` never checks this mapping, an operator can pass any `_tokenAddress` — including tokens that were never registered, or tokens that were subsequently deregistered — and the bridge will transfer them out. The `_requestTxHash` parameter is only stored to prevent replay of the same hash; it is never verified against any on-chain oracle or counterpart chain state. [4](#0-3) 

The same structural defect exists in `handleERC721Transfer`: [5](#0-4) 

The default operator threshold is `1`: [6](#0-5) 

This means a single operator can execute the drain without any co-signer.

---

### Impact Explanation

In non-mintBurn mode the bridge holds ERC20 tokens as liquidity. A single operator (or colluding operators meeting the configured threshold) can call `handleERC20Transfer` with a fabricated `_requestTxHash`, any `_tokenAddress` held by the bridge, `_to` set to an attacker-controlled address, and `_value` equal to the full bridge balance. The bridge will execute `IERC20(_tokenAddress).safeTransfer(_to, _value)` and transfer all bridged assets to the attacker. This is an unauthorized transfer of bridged assets — a direct match to the allowed impact gate.

---

### Likelihood Explanation

Bridge operators are semi-trusted: they are expected to relay legitimate cross-chain events, not to steal funds. The default threshold of 1 means no collusion is required. Even with a higher threshold, colluding operators (e.g., a compromised operator key) can execute the attack. The attack requires no special on-chain state beyond holding the operator role, which is a realistic compromise scenario for a bridge relayer.

---

### Recommendation

Add `onlyRegisteredToken(_tokenAddress)` to `handleERC20Transfer` and `handleERC721Transfer`, mirroring the guard already present on the outbound paths:

```solidity
function handleERC20Transfer(
    bytes32 _requestTxHash,
    address _from,
    address _to,
    address _tokenAddress,
    uint256 _value,
    uint64 _requestedNonce,
    uint64 _requestedBlockNumber,
    bytes memory _extraData
)
    public
    onlyOperators
    onlyRegisteredToken(_tokenAddress)   // ADD THIS
{
    ...
}
```

Apply the same fix to `handleERC721Transfer`.

---

### Proof of Concept

Preconditions: bridge deployed in non-mintBurn mode; `tokenA` registered; bridge holds 1,000,000 `tokenA` as liquidity; `tokenB` (unregistered, also held by bridge) has balance 500,000.

```
// Attacker is a registered operator (threshold = 1)
bridge.handleERC20Transfer(
    bytes32(uint256(1)),   // fabricated _requestTxHash (never seen before)
    attacker,              // _from (irrelevant)
    attacker,              // _to — receives the tokens
    address(tokenB),       // _tokenAddress — NOT registered, but held by bridge
    500_000e18,            // _value — full balance of tokenB in bridge
    999,                   // _requestedNonce — any unused nonce
    block.number,
    ""
);
// Result: bridge transfers 500,000 tokenB to attacker
// tokenA liquidity is equally drainable by substituting tokenA as _tokenAddress
```

The `_voteValueTransfer` call uses `keccak256(msg.data)` as the vote key, so with threshold = 1 the single operator vote immediately passes and the transfer executes. [7](#0-6)
