### Title
Prosaic-contract hash uses unpadded string concatenation, allowing text-substitution collisions - ([File: prosaic_contract.js])

### Summary
`prosaic_contract.js` computes the unique identifier of a prosaic (plain-text) contract by directly concatenating the user-controlled, variable-length `title`, `text`, and `creation_date` fields and hashing the result, instead of hashing them with length-prefixing/delimiters. This is the same class of bug as `abi.encodePacked()` used with dynamic types before `keccak256`: distinct field combinations can produce an identical hash.

### Finding Description
`getHash()` and `getHashV1()` build the source string for hashing by plain string concatenation: [1](#0-0) 

```js
function getHash(contract) {
	return crypto.createHash("sha256").update(contract.title + contract.text + contract.creation_date, "utf8").digest("base64");
}
function getHashV1(contract) {
	return objectHash.getBase64Hash(contract.title + contract.text + contract.creation_date);
}
```

Because `title` and `text` are both attacker/peer-controlled, variable-length strings with no separator or length prefix between them, two different `(title, text)` pairs can produce the same concatenated string and therefore the same hash — e.g. `title="AB", text="C"` and `title="A", text="BC"` (with the same `creation_date`) both concatenate to `"ABC" + creation_date` and hash identically. This is the exact `abi.encodePacked`-style collision the external report describes, ported to this codebase's use of raw string concatenation before `sha256`.

This is in contrast to the codebase's own general-purpose hashing utility, `getSourceString()` in `string_utils.js`, which explicitly type-tags and null-byte-separates each field precisely to prevent this class of collision: [2](#0-1) 

The prosaic-contract hash bypasses that safe utility and reintroduces the vulnerability. The peer/arbiter-adjacent `arbiter_contract.js` shows the codebase authors were aware of this and fixed it for arbiter contracts (introducing a `DELIMITER` and `.join(DELIMITER)` for contracts created after `NEW_HASH_DATE`), but left the pre-existing unsafe `.join("")` path active for backward compatibility and did not apply an equivalent fix to `prosaic_contract.js`: [3](#0-2) 

The resulting `contract.hash` is used as the immutable identifier that a counterparty relies on when accepting/signing the contract (`respond`), and is checked against `payload.contract_text_hash` in an incoming `data` message to confirm the on-chain signing transaction corresponds to the agreed-upon contract text: [4](#0-3) 

### Impact Explanation
An unprivileged private-contract counterparty could craft a contract whose `title`+`text` concatenation collides with a different, previously-agreed `title`+`text` pair sharing the same `creation_date`. Because acceptance/signing flows (`handleReceivedSigningUnit`, hash-based lookups via `getByHash`) treat `contract.hash` as the canonical identity of the agreed contract text, a hash collision lets a malicious party substitute different contractual text/terms after signature exchange while the recorded/verified `contract_text_hash` still matches, i.e. the signed on-chain data message no longer provably corresponds to the exact text the other party believed they signed. This is a private-payment/contract-counterparty integrity issue, not merely a low-severity data-format nit, since it undermines the non-repudiation guarantee the hash is meant to provide.

### Likelihood Explanation
Exploitation requires an attacker able to choose `title` and `text` for a prosaic contract offered to (or received from) a counterparty — a normal, unprivileged capability of any prosaic-contract participant. Constructing a colliding pair is straightforward (move a boundary between `title` and `text`, or manipulate whitespace/character split points) and does not require breaking SHA-256 itself, only exploiting the missing delimiter. Likelihood is therefore Medium-to-High for any two parties who exchange prosaic contracts where such text substitution has practical/financial consequence.

### Recommendation
Use the codebase's existing safe hashing utility (`objectHash.getBase64Hash`/`string_utils.getSourceString`, which type-tags and null-byte-delimits fields) or an explicit delimiter/length-prefix scheme (as already implemented in `arbiter_contract.js` for post-`NEW_HASH_DATE` contracts) for `prosaic_contract.js`'s `getHash`/`getHashV1`, e.g.:
```js
function getHash(contract) {
	return objectHash.getBase64Hash([contract.title, contract.text, contract.creation_date]);
}
```
ensuring `getSourceString`-style tagging (or an unambiguous delimiter not permitted inside `title`/`text`) is used instead of raw concatenation.

### Proof of Concept
1. Party A offers a prosaic contract with `title = "AB"`, `text = "C"`, `creation_date = "2026-01-01 00:00:00"`.
   `hash = sha256("AB" + "C" + "2026-01-01 00:00:00")`.
2. Party A (acting maliciously toward a later dispute, or a MITM app-layer message) instead persists/presents `title = "A"`, `text = "BC"` with the same `creation_date`.
   `hash = sha256("A" + "BC" + "2026-01-01 00:00:00")` — identical to step 1's hash.
3. Both contracts pass the `contract.hash` equality check in `handleReceivedSigningUnit` (`payload.contract_text_hash !== contract.hash`), so a peer relying on `contract.hash` to prove which exact text was signed cannot distinguish between the two different textual agreements.

function getHashSrc(contract) {
	const payer_name = contract.me_is_payer ? contract.my_party_name : contract.peer_party_name;
	const payee_name = contract.me_is_payer ? contract.peer_party_name : contract.my_party_name;
	const payer_address = contract.me_is_payer ? contract.my_address : contract.peer_address;
	const payee_address = contract.me_is_payer ? contract.peer_address : contract.my_address;
	const src = contract.creation_date > exports.NEW_HASH_DATE
		 ? [contract.title, contract.text, contract.creation_date, payer_address, payer_name || '', contract.arbiter_address, payee_address, payee_name || '', contract.amount, contract.asset || 'null'].join(exports.DELIMITER)
		 : [contract.title, contract.text, contract.creation_date, payer_name || '', contract.arbiter_address, payee_name || '', contract.amount, contract.asset || 'null'].join("");
	return src;
}

function getHash(contract) {
	return crypto.createHash("sha256").update(getHashSrc(contract), "utf8").digest("base64");
}
