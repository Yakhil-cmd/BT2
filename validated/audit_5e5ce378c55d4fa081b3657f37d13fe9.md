### Title
Unrestricted Submodule URL/Protocol Handling During `git submodule update --init` - ([File: main.go])

### Summary
`git-sync` blindly trusts data pulled from the untrusted upstream repository content in the same way the reported LST oracle blindly trusted `getRate()` without validation. Here, the equivalent "untrusted external value" is the `.gitmodules` file and submodule configuration contained in the synced commit itself. When submodules are enabled, `git-sync` runs `git submodule update --init` (optionally `--recursive`) against whatever `.gitmodules` content is present in the fetched commit, with no allow-list or protocol restriction placed on submodule URLs.

### Finding Description
`configureWorktree` unconditionally executes submodule initialization based on the `git.submodules` setting, using arguments built only from local flags (`--depth`, `--recursive`), never inspecting or restricting the submodule URLs/protocols that come from the repository content itself: [1](#0-0) 

This mirrors the oracle bug class precisely: `getRate()` is an external, attacker-influenceable data source consumed without bounds-checking; `.gitmodules` is likewise external, attacker-influenceable content (any actor who can push a commit/ref that `git-sync` fetches controls it) consumed by `git submodule update --init` without any restriction on protocol (e.g. `ext::`, `file://`) or destination path. Historically, unrestricted submodule URLs/protocols in git clients have been abused for remote code execution and arbitrary file writes (the class of issues fixed upstream by `protocol.*.allow` allow-lists and submodule path validation in git itself). `git-sync` does not set `GIT_ALLOW_PROTOCOL`, `protocol.ext.allow=never`, or otherwise vet `.gitmodules` before invoking submodule update, so it inherits whatever protocol/path exposure the underlying `git` binary in the container permits.

The `fetch`/`SyncRepo` flow that ultimately leads here fetches exactly the ref/hash requested from `git.repo` and resets/checks out onto that content, so any attacker who can commit to the synced ref controls the `.gitmodules` file processed by `configureWorktree`: [2](#0-1) [3](#0-2) 

### Impact Explanation
If the underlying `git` binary/version in the container does not itself restrict submodule protocols (older `git`, or explicit misconfiguration), an attacker who can push a commit to the tracked ref (a realistic threat model for `git-sync`, which is explicitly designed to sync from a repo an operator does not fully control, e.g. a shared/forkable repo) can smuggle a malicious `.gitmodules` entry (e.g. using the `ext::` transport or a crafted `file://`/relative submodule path) to achieve command execution inside the sync container or write files outside the intended worktree — a "code execution" or "file write outside `--root`" outcome per the accepted impact categories.

### Likelihood Explanation
Likelihood depends on the `git` version bundled in the container image and whether `--submodules` is enabled (it is `submodulesOff` only if explicitly disabled; recursive submodules are opt-in via `git.submodules == submodulesRecursive`). No mitigation exists in `git-sync` itself (no `GIT_ALLOW_PROTOCOL` env var set, no allow-list enforcement, no `.gitmodules` inspection), so the exposure is entirely dependent on upstream `git`'s own defaults, which is a fragile trust boundary — the same fragile-trust pattern the original report flagged for the LST oracle ("fully trusting" an external, single-party-controlled value).

### Recommendation
- Set `protocol.ext.allow=never` (and restrict `protocol.file.allow`) via `git.Run`/config before invoking `git submodule update --init`, or export `GIT_ALLOW_PROTOCOL` with a safe allow-list (e.g. `http,https,ssh`), analogous to placing bounds/guards on an oracle's returned rate.
- Optionally parse/validate `.gitmodules` before allowing submodule update, rejecting unexpected protocols or absolute/`..`-containing paths.
- Document this as a hardening option for `--submodules=recursive` deployments syncing from repos not fully trusted by the operator.

### Proof of Concept
Conceptual PoC (mirrors the reported "unchecked oracle input" pattern, mapped to git-sync's untrusted commit content):
1. Attacker with push access to the ref that `git-sync --repo=<attacker-reachable-repo> --ref=<ref> --submodules=recursive` tracks.
2. Attacker commits a `.gitmodules` file with a submodule URL such as `ext::sh -c "id > /tmp/pwned"` (works on `git` versions lacking `protocol.ext.allow=never` by default, or where the container's global git config does not restrict it).
3. `git-sync`'s next sync cycle calls `configureWorktree`, which runs `git submodule update --init --recursive`, executing the attacker-controlled command: [4](#0-3) 

Note: exploitability is contingent on the `git` binary/version and its default protocol allow-list inside the deployed container image — `git-sync` performs no independent validation regardless of that default, which is the root cause matching the reported bug class.
