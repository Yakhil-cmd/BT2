### Title
Supply inflation via rounding of `earned_headers_commission_share` in headers-commission distribution - (File: `headers_commission.js`)

### Summary
`Allo#fundPool`'s bug class (a percentage fee is rounded per-transaction and the rounding error can be repeatedly exploited) has a direct, more severe analog in ocore's headers-commission distribution logic. Each `earned_headers_commission_recipients` entry's payout is computed by independently rounding `full_amount * share / 100`, with no correction to make the sum of the rounded shares equal the original `full_amount`. An attacker who controls the recipient list of a unit can pick shares/recipient counts that cause the sum of rounded outputs to exceed the amount actually earned, minting extra bytes.

### Finding Description
When headers commissions are distributed, `calcHeadersCommissions()` computes, per recipient, a portion of the parent unit's fixed `headers_commission` (`full_amount`): [1](#0-0) 

```
var full_amount = assocWonAmounts[child_unit][payer_unit];
if (objUnit.assocEarnedHeadersCommissionRecipients) {
    for (var address in objUnit.assocEarnedHeadersCommissionRecipients) {
        var share = objUnit.assocEarnedHeadersCommissionRecipients[address];
        var amount = Math.round(full_amount * share / 100.0);
        arrValuesRAM.push("('"+payer_unit+"', '"+address+"', "+amount+")");
    };
}
```

The MySQL code path performs the same operation in SQL: [2](#0-1) 

Each recipient's amount is independently rounded with `Math.round`, with no adjustment to keep `Σ amount_i == full_amount`. The only protocol-level constraint on the recipient list is that the declared `earned_headers_commission_share` values are positive integers summing to exactly 100: [3](#0-2) 

There is no limit on the *number* of recipients (only that each share is a positive integer and the total is 100), so a unit author can list up to 100 recipients each with `earned_headers_commission_share = 1`. Because `Math.round` rounds `x.5` up, whenever `full_amount * 0.01 >= 0.5` (i.e., `full_amount >= 50`), every one of the 100 recipients receives `round(full_amount*0.01)` bytes, and the total credited across `headers_commission_outputs` can be roughly double (or more, depending on chosen shares) the `full_amount` that the parent unit actually allocated as its `headers_commission`.

Crucially, the cost of adding many recipients (their own unit's `headers_commission`/size grows slightly) is decoupled from the benefit: the inflated amount comes from redistributing a *different* unit's (the parent's) `headers_commission`, which the attacker wins nondeterministically via the hash-based "best child" tournament (`getWinnerInfo`) — see: [4](#0-3) 
Any unit whose child ends up winning a parent's headers commission and carries a crafted `earned_headers_commission_recipients` list will trigger the inflation, so this is systemically exploitable over time, not a one-off.

The resulting excess bytes are inserted into `headers_commission_contributions` and subsequently summed into spendable `headers_commission_outputs`: [5](#0-4) 
These become real spendable balances usable as payment inputs later (validated in `validation.js`), so the extra bytes are genuinely mintable, unbacked value.

### Impact Explanation
This is a direct currency/supply inflation bug: the sum of headers-commission outputs distributed to recipients can exceed the actual `headers_commission` amount recorded on the paying unit. Because headers commission outputs become spendable base-asset (bytes) inputs, this allows minting bytes out of thin air, matching the "supply inflation" impact category.

### Likelihood Explanation
Any unprivileged unit author can set `earned_headers_commission_recipients` on their own unit as long as authors count > 1 (any two-address multi-author unit, which is trivial to construct with two addresses controlled by the same person) — see `validateHeadersCommissionRecipients` which only requires the shares to be positive integers summing to 100, without limiting the number of recipients. Winning the headers-commission "lottery" for at least one parent unit is a normal, frequent occurrence in the DAG (every stable unit's headers commission is won by some child), so an attacker only needs to consistently post units with the crafted recipients list to periodically realize the inflation whenever they win a parent whose `headers_commission >= ~50` (easily arranged, e.g., by controlling which unit sizes they parent from, or simply repeating the attempt across many units).

### Recommendation
When distributing `full_amount` across `earned_headers_commission_recipients`, do not round each recipient's share independently. Instead, use a remainder-preserving allocation (e.g., largest-remainder method, or compute all but the last recipient with `Math.floor` and assign the last recipient `full_amount - sum_of_previous`), guaranteeing `Σ amount_i === full_amount` exactly, matching the pattern the original report recommends ("ensure paid amount reflects the intended value rather than being lost/gained to rounding"). Apply the same fix to both the SQL (`ROUND(...)`) and in-memory JS paths in `headers_commission.js`.

### Proof of Concept
1. Attacker controls two addresses `A` and `B` and posts a 2-author unit `U` (satisfies the `authors.length > 1` requirement for `earned_headers_commission_recipients`).
2. `U.earned_headers_commission_recipients` lists 100 distinct addresses (can be attacker-controlled or arbitrary), each with `earned_headers_commission_share = 1` (sums to 100, passes `validateHeadersCommissionRecipients`, `validation.js:1101-1124`).
3. Over time, `U` (or units built the same way) is chosen as the "winner" child of some parent unit `P` whose `headers_commission >= 50` via the deterministic hash tournament in `getWinnerInfo` (`headers_commission.js:249-259`) — a routine, unavoidable event on the network.
4. `calcHeadersCommissions()` computes, for each of the 100 recipients, `amount = Math.round(P.headers_commission * 1/100)`. For `P.headers_commission = 50`, each recipient gets `Math.round(0.5) = 1`, for a total of `100` bytes credited into `headers_commission_outputs`, double the `50` bytes that `P` actually allocated.
5. These 100 bytes are fully spendable (as `type: "headers_commission"` payment inputs), so `50` bytes have been minted with no corresponding value burned/paid anywhere — a concrete instance of supply inflation.

function getWinnerInfo(arrChildren){
	if (arrChildren.length === 1)
		return arrChildren[0];
	if (arrChildren.length === 0)
		throw Error("no children for hc");
	arrChildren.forEach(function(child){
		child.hash = crypto.createHash("sha1").update(child.child_unit + child.next_mc_unit, "utf8").digest("hex");
	});
	arrChildren.sort(function(a, b){ return ((a.hash < b.hash) ? -1 : 1); });

function validateHeadersCommissionRecipients(objUnit, cb){

		if (!isNonemptyArray(objUnit.earned_headers_commission_recipients))
			return cb("empty earned_headers_commission_recipients array");
		var total_earned_headers_commission_share = 0;
		var prev_address = "";
		for (var i=0; i<objUnit.earned_headers_commission_recipients.length; i++){
			var recipient = objUnit.earned_headers_commission_recipients[i];
			if (!isPositiveInteger(recipient.earned_headers_commission_share))
				return cb("earned_headers_commission_share must be positive integer");
			if (hasFieldsExcept(recipient, ["address", "earned_headers_commission_share"]))
				return cb("unknown fields in recipient");
			if (!isValidAddress(recipient.address))
				return cb("invalid recipient address checksum");
			if (recipient.address <= prev_address)
				return cb("recipient list must be sorted by address");
			total_earned_headers_commission_share += recipient.earned_headers_commission_share;
			prev_address = recipient.address;
		}
		if (total_earned_headers_commission_share !== 100)
			return cb("sum of earned_headers_commission_share is not 100");
	}
