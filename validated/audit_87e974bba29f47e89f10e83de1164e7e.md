### Title
Refund paid from declared (not received) amount drains pool custody in `repay`/`recapitalize` - (File: contracts/pool/src/ops/repay.rs)

### Summary
CVE-2020-25863 is a double-free/crash class: memory is deallocated for an object that was never validly allocated. The lending analog is a **refund released for value that was never deposited**: the pool computes the overpayment refund from the *declared* `action.amount`, then transfers that refund out of real token custody without checking that the corresponding inbound transfer actually arrived and without debiting the cash book.

`ops::repay::apply` resolves `(burned, overpayment)` purely from `action.amount` vs. the position's debt, credits only `net_repay` to cash, then calls `cache.transfer_out(payer, overpayment)` — paying the excess from the pool's physical balance. `ops::recapitalize::apply` does the same with `refund = amount - applied`. The comment in `repay.rs` states "The controller transfers the repay amount into the pool before this call" — the pool *trusts* rather than measures the inbound amount. A test in the repo already demonstrates the drain: `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` shows a `repay` on a market with zero debt refunds the full declared amount "out of real custody with the book untouched."

### Finding Description
In `contracts/pool/src/ops/repay.rs:44-57`, `resolve_repay(amount, position)` clamps the declared `amount` at the outstanding debt and returns the remainder as `overpayment`. `apply` then executes `outcome.cache.transfer_out(payer, outcome.overpayment)` at line 32 — a real token transfer to the caller — while `credit_cash` only accounts for `net_repay`. If the inbound transfer delivered less than `amount` (or nothing), the difference is paid out of supplier/borrower custody while the books remain consistent. The same shape exists in `contracts/pool/src/ops/recapitalize.rs:52-57`, where `refund = amount - applied` is returned unconditionally.

This mirrors the CVE's "deallocation of invalid MIME parts": the contract releases (frees) tokens corresponding to a leg that was never funded. The fix direction is identical to the upstream fix — only release what was actually allocated, i.e., measure the received balance delta and clamp the refund to it.

### Impact Explanation
Theft of user funds / protocol insolvency: each unit refunded in excess of tokens actually received comes directly out of pooled custody backing suppliers' shares and outstanding borrows. Repeating the call drains the pool balance while `cash` accounting stays correct, breaking the cash-vs-custody invariant and leaving suppliers unable to withdraw.

### Likelihood Explanation
Reachability depends on whether the pool gates `repay`/`recapitalize` to the controller. The docstring and flow assume controller-ordered transfers; the in-repo test invokes `client().repay(&payer, &ract(0, custody_before))` directly with no inbound transfer and observes the custody drain, which indicates the pool does not enforce receipt of the declared amount. If pool entrypoints are not controller-restricted (or any controller path passes a declared amount that exceeds the delivered amount, e.g. via a callback or measured-receipt gap), a single unprivileged address can drain custody by declaring `amount = pool balance` against a market with zero debt. I could not fully verify the authorization guard on the pool's `repay`/`recapitalize` entrypoints within the iteration budget; if they are hard-gated to the controller and the controller always transfers exactly `amount` before the call, the residual risk narrows to fee-on-transfer/misbehaving tokens, which the engagement rules exclude.

### Recommendation
Compute the refund against the *received* amount: snapshot the pool's token balance before the operation (or accept an explicit `received` measured by the caller's balance delta) and clamp `overpayment`/`refund` to `min(declared_excess, received_excess)`. Additionally, require `received >= net_repay` before burning debt shares, and gate `repay`/`recapitalize` to the controller address if they are not already.

### Proof of Concept
Directly from `contracts/pool/tests/flows.rs` (`test_unfunded_repay_overpayment_refund_also_pays_out_of_custody`):
1. Market has zero debt; pool holds `custody_before` tokens backing suppliers.
2. Attacker calls `pool.repay(attacker, PoolAction { amount: custody_before, .. })` with no prior transfer.
3. `resolve_repay` sees `current_debt == 0`, so `overpayment = amount`; `net_repay = 0` satisfies the `RepayRoundsToZeroShares` assert via its `net_repay == 0` disjunct.
4. `transfer_out(attacker, custody_before)` sends the full custody to the attacker; the book is untouched, so suppliers' claims now exceed custody — insolvency.
