## Analysis

The Allo.sol issue is a classic "assumed transfer amount ≠ actual transfer amount" accounting bug for fee-on-transfer ERC20 tokens: the contract calls `transfer()`, gets back `true`, and then credits its internal ledger with the *requested* amount rather than the *actually received* amount, creating a permanent discrepancy between the ledger and the real token balance.

I searched for an analogous "trust the requested/return value, not actual balance delta" pattern reachable through a real, unprivileged Polkadot SDK entry point. The polkadot-sdk native asset pallets (`pallet-balances`, `pallet-assets`, `fungible`/`fungibles` traits) consistently use `actual`/`credit` values returned from internal debit/credit computations [1](#0-0) , so they don't reproduce this bug class.

However, `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs` implements an XCM `TransactAsset` for arbitrary ERC20 contracts deployed under `pallet-revive`, and it exhibits exactly this bug class.

### Title
ERC20Transactor credits XCM holdings with the requested amount instead of the amount actually received from `transfer()`, enabling accounting desync for fee-on-transfer/rebasing ERC20 tokens - (File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs)

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` calls the ERC20 `transfer()` function to move tokens from the XCM-origin account to the checking account, then—if the call returns `true`—unconditionally mints an `AssetsInHolding` credit of the *requested* `amount`, not the amount the checking account actually received [2](#0-1) . `ERC20Matcher` matches any local `AccountKey20` location with no allow-list [3](#0-2) , and this transactor is wired into the production `AssetTransactors` tuple on Asset Hub Westend/Rococo [4](#0-3) .

### Finding Description
Any signed account can permissionlessly deploy an arbitrary Solidity contract via `pallet-revive::upload_code`/`instantiate` (no privileged role required), including a fee-on-transfer/deflationary ERC20 that deducts a tax on every `transfer()` while still returning `true`. That contract's address becomes usable in XCM as `Location { parents: 0, interior: [AccountKey20 { key, network }] }`, which `IsLocalAccountKey20`/`ERC20Matcher` accepts unconditionally [5](#0-4) .

When a user executes an XCM `WithdrawAsset` for this asset (e.g. via `pallet_xcm::execute`, reachable by any signed origin, per the pattern shown in `execute_withdraw_to_deposit_works`) [6](#0-5) , `withdraw_asset_with_surplus` performs an ERC20 `transfer(checking_account, amount)` from the user to the shared `TransfersCheckingAccount`, then checks only the boolean return value—not the checking account's actual balance delta—before minting `Erc20Credit(amount)` into the XCM holding [7](#0-6) . If the token deducts a transfer fee, the checking account receives `amount - fee`, but the XCM holding records the full `amount` as backed value.

This virtual over-credit is then spent via `deposit_asset_with_surplus`, which — on any subsequent leg of the same message or a follow-up message — instructs the shared checking account to `transfer(beneficiary, amount)` for that same over-stated `amount` [8](#0-7) . Because `TransfersCheckingAccount` is a single shared pooled account for *all* ERC20 assets processed by this transactor, a deficit created by one fee-on-transfer token silently consumes real balance backing other users' deposits/withdrawals of the same or other ERC20s routed through the same checking account, or simply causes the deposit leg to revert once the shortfall is discovered — depending on timing, either an accounting break (unbacked XCM credit) or a deterministic failure/asset trap for legitimate users sharing the checking account.

This mirrors the reported bug's exact fault pattern: crediting a ledger/holding with the pre-fee amount instead of verifying the actual balance change caused by a fee-taking token transfer.

### Impact Explanation
The `TransfersCheckingAccount` is a single global account for the entire chain's ERC20-via-XCM traffic [9](#0-8) . A fee-on-transfer token deployed by any user causes the transactor's bookkeeping (the `AssetsInHolding`/`Erc20Credit` amount) to diverge from the checking account's true on-chain token balance for that asset. This creates an unbacked-value condition inside the XCM executor's holding register that can propagate to `deposit_asset`, letting a beneficiary receive (or be promised) more of the token than the checking account actually possesses, at the expense of subsequent/other users of the same shared checking account for that asset — a fund-safety/integrity issue, though scoped to the `pallet-revive`-hosted ERC20 asset class rather than native DOT/KSM balances.

### Likelihood Explanation
Deploying a fee-on-transfer ERC20 via `pallet-revive` requires no special privilege — any signed account can do it — and `ERC20Matcher`/`IsLocalAccountKey20` impose no allow-list, so any deployed contract address is automatically eligible for XCM transacting [5](#0-4) . Triggering `withdraw_asset`/`deposit_asset` only requires a standard `pallet_xcm::execute`/`send` call with a `WithdrawAsset`/`DepositAsset` program referencing that token, which is a normal (fee-paying) user action.

### Recommendation
In `withdraw_asset_with_surplus`, read the checking account's ERC20 balance before and after the `transfer()` call and mint `Erc20Credit` with the actual delta rather than the requested `amount`. Symmetrically, in `deposit_asset_with_surplus`, verify the beneficiary's actual balance delta matches (or handle any shortfall) before treating the deposit as fully successful, and consider isolating or disallowing tokens whose transfer semantics cannot guarantee exact-amount delivery (e.g. via an allow-list of vetted ERC20 contracts) rather than accepting any `AccountKey20` address unconditionally.

### Proof of Concept
Program/severity rationale: this is a genuine reachable defect in `assets-common`'s `ERC20Transactor`, wired into `asset-hub-westend`/`asset-hub-rococo` production XCM config, triggered purely by unprivileged actions (permissionless contract deployment + `pallet_xcm::execute`). No guard in `withdraw_asset_with_surplus`/`deposit_asset_with_surplus` compares balances before/after; both only check the boolean ERC20 return value [10](#0-9) .

I was not able to execute a live Rust/FRAME integration test reproducing this end-to-end (deploying a custom fee-on-transfer Solidity contract via `pallet-revive`, wiring it through XCM `execute`, and asserting the checking-account balance vs. `AssetsInHolding` divergence) within this session — no code execution/tooling access is available in this environment. This should be validated with a concrete integration test in `cumulus/parachains/runtimes/assets/asset-hub-westend/tests/` that: (1) deploys a minimal ERC20 with a transfer tax, (2) calls `pallet_xcm::execute` with `WithdrawAsset`/`DepositAsset` for that token, and (3) asserts the checking account's real ERC20 balance is less than the sum of `Erc20Credit` amounts minted, and/or that a later `deposit_asset` for another user fails or under-delivers due to the shortfall.

/// `Contains<Location>` implementation that matches locations with no parents,
/// a `PalletInstance` and an `AccountKey20` junction.
pub struct IsLocalAccountKey20;
impl Contains<Location> for IsLocalAccountKey20 {
	fn contains(location: &Location) -> bool {
		matches!(location.unpack(), (0, [AccountKey20 { .. }]))
	}
}

/// Fallible converter from a location to a `H160` that matches any location ending with
/// an `AccountKey20` junction.
pub struct AccountKey20ToH160;
impl MaybeEquivalence<Location, H160> for AccountKey20ToH160 {
	fn convert(location: &Location) -> Option<H160> {
		match location.unpack() {
			(0, [AccountKey20 { key, .. }]) => Some((*key).into()),
			_ => None,
		}
	}

	fn convert_back(key: &H160) -> Option<Location> {
		Some(Location::new(0, [AccountKey20 { key: (*key).into(), network: None }]))
	}
}

/// [`xcm_executor::traits::MatchesFungibles`] implementation that matches
/// ERC20 tokens.
pub type ERC20Matcher =
	MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>;
