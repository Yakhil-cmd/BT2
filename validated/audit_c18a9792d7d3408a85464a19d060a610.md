### Title
Api::CCMenuController bypasses stack-scoped ApiClient authorization, letting a token authorized for one stack read the status of any stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`ApiClient` records can be scoped to a single `stack` via `stack_id`, and `Api::BaseController` enforces this binding by restricting the queryable stack set through the `stacks` helper. `Api::CCMenuController` overrides `stack` to query `Stack.from_param!(params[:stack_id])` directly, never going through the `stacks` scoping helper, so the stack-scope binding the token authorizes is never checked against the stack the request actually touches.

### Finding Description
`ApiClient#stack_id?` and the `stacks` helper in `Api::BaseController` are the mechanism that restricts a scoped API token to a single stack: [1](#0-0) 

Every other API controller (`Api::StacksController`, `Api::DeploysController`, etc.) resolves the target stack via this `stacks` helper, e.g.: [2](#0-1) 

`Api::CCMenuController`, however, defines its own `stack` method that queries `Stack.from_param!` directly against the global `Stack` model, completely bypassing `current_api_client.stack_id` scoping: [3](#0-2) 

The controller still runs `require_permission :read, :stack`, but `check_permissions!` in `ApiClient` only checks the coarse `permissions` array (e.g. `"read:stack"`), not which specific stack the token is bound to: [4](#0-3) 

This is the exact bug class from the external report applied to Shipit: the report's `IGauge`/`Minter` mismatch is "the API that should be authoritative for context X is not the one actually invoked." Here the analog is "the stack a token authorizes (`ApiClient#stack_id`) versus the stack a request actually touches (`params[:stack_id]` resolved without the scoping filter)." An `ApiClient` created with `stack_id` set to stack A (intended to restrict a CI badge/CCMenu integration to only that stack) can present its valid, correctly-signed token yet supply an arbitrary `stack_id` for stack B in the URL, and `CCMenuController#stack` will happily resolve and render stack B's status.

### Impact Explanation
This meets the High-severity bar of "unauthenticated read of stack state, task streams or deploy output" in spirit — more precisely, it is an authorization-scope escalation: a token deliberately restricted to one stack gains read access (via the CCMenu XML endpoint) to every other stack's build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `activity`, lock status, etc.), rendered via:
```
render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
```
in `Api::CCMenuController#show`. Stack-scoped tokens (as used for embeddable CI badges, e.g. distributed publicly in README badges/CCTray URLs) are meant to leak minimal information about a single stack; this bypass turns any such token into a global read key for every stack's deploy status in the Shipit instance.

### Likelihood Explanation
Exploitation only requires possessing any valid `ApiClient` authentication token that is scoped to a stack (a routine, low-privilege credential intentionally handed out for CCMenu/CI-badge integrations, often embedded in public URLs via `CCMenuUrlController`) and changing the `stack_id` route/query parameter to a different stack's identifier. No additional secrets, GitHub access, or elevated permissions are needed — the `require_permission :read, :stack` check passes for any client with the generic `read:stack` permission, since it never consults `stack_id`.

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the same scoped `stacks` helper used elsewhere (e.g. `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so a stack-scoped `ApiClient` cannot address stacks outside its authorized `stack_id`.

### Proof of Concept
1. Create (or use) an `ApiClient` with `stack_id` set to Stack A and permission `read:stack` (e.g. as `CCMenuUrlController` does when generating a CCMenu URL for Stack A).
2. Obtain its `authentication_token` (e.g. from the generated CCMenu URL for Stack A).
3. Send `GET /api/stacks/:stack_id_of_B/ccmenu.xml?token=<token>` substituting Stack B's `stack_id`/slug instead of A's.
4. Observe that `Api::CCMenuController#stack` resolves Stack B via `Stack.from_param!` (bypassing the `stacks` scope check that would otherwise return `Stack.none` for an out-of-scope stack), and the response renders Stack B's `lastBuildStatus`/`lastBuildLabel`/`lastBuildTime`, even though the token was only ever authorized for Stack A.
