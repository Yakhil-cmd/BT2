### Title
`NonTransfer` proxy can escalate to `Auction` proxy and execute `Registrar::swap`, which it is explicitly designed to deny - ([File: polkadot/runtime/rococo/src/lib.rs])

### Summary
`pallet_proxy` gates `add_proxy`/`remove_proxy` sub-delegation on `ProxyType::is_superset` [1](#0-0) . In the Rococo and Westend relay-chain runtimes (and the identical pattern in `substrate/frame/staking-async/runtimes/rc/src/lib.rs`), `ProxyType::NonTransfer.is_superset()` unconditionally returns `true` for every other proxy type except `Any` [2](#0-1) , while `NonTransfer`'s own `filter()` explicitly **excludes** `paras_registrar::Call::swap` (commented "Specifically omitting Registrar `swap`") but the `Auction` proxy type's `filter()` **admits the entire Registrar pallet unconditionally**, including `swap` [3](#0-2) . This is the exact bug class that was already identified and fixed for `NonTransfer`/`Governance` on Asset Hub Westend (issue #12724, `prdoc/pr_12769.prdoc`), but the analogous `NonTransfer`/`Auction` escalation via `Registrar::swap` was left unpatched on the relay chain runtimes.

### Finding Description
A user who is only granted a `NonTransfer` proxy (a real, first-class governance/permission-delegation feature, not a privileged prerequisite) is supposed to be barred from calling `Registrar::swap`, per the explicit code comment in the `filter()` match arm [4](#0-3) . However, `pallet_proxy::do_proxy` only checks the *delegated* call directly against `filter()` for ordinary calls; for `Proxy::add_proxy`/`Proxy::remove_proxy` calls specifically, it instead checks `def.proxy_type.is_superset(proxy_type)` [5](#0-4) .

Because `NonTransfer::is_superset()` claims to be a superset of every proxy type (`(ProxyType::NonTransfer, _) => true`) [2](#0-1) , a `NonTransfer` delegate can add itself (or a third party) as an `Auction` sub-proxy on the delegator's account, even though `Auction`'s filter admits `RuntimeCall::Registrar { .. }` (the entire pallet, unfiltered) [3](#0-2) . Once that `Auction` sub-proxy exists, the delegate dispatches `Proxy::proxy(origin=delegate, real=delegator, call=Registrar::swap{...})`, and `Auction`'s filter admits it unconditionally, so `swap` executes on behalf of the real account — a call class the `NonTransfer` grant was designed to forbid.

`Registrar::swap` accepts `Root`, the para owner, or the para itself as origin [6](#0-5) ; a delegator that is the manager/owner of a para (e.g. a `NonTransfer` proxy over that account) is a valid caller of `swap`. `swap` mutates on-chain lease, deposit and lifecycle scheduling data between two `ParaId`s via `T::OnSwap::on_swap` and lifecycle downgrade/upgrade scheduling [7](#0-6) , effectively exchanging which `ParaId` holds a lease-holding-parachain slot, its auction deposit, and crowdloan/lease references [8](#0-7) .

This is precisely the same authorization-bypass root cause as the CodeChecker CVE: a permission/authorization function (`is_superset`, analogous to CodeChecker's permission endpoints) is checked with a coarse allow-rule ("NonTransfer is superset of everything") that does not match the actual (finer-grained) call filter, letting an account escalate to functionality its explicit grant denies — without any signature or consent from the real privileged party beyond the original, narrower `NonTransfer` delegation.

### Impact Explanation
An attacker who is only trusted with a `NonTransfer` proxy (a common, non-privileged delegation used for e.g. governance/voting on behalf of a stash) can self-escalate to execute `Registrar::swap` on behalf of the real account. This can rewrite lease-holding/auction-deposit and crowdloan ownership state between `ParaId`s that the real account manages, an operation the `NonTransfer` type was specifically documented and coded to exclude. This is an authorization bypass / unauthorized dispatch of a sensitive extrinsic (CWE-863/CWE-290 analog), matching the "Critical/High: unauthorized dispatch" category called for in this analysis. The prior, structurally identical `NonTransfer`/`Governance` bug on Asset Hub Westend was treated as a genuine, patch-worthy vulnerability by the project (see `prdoc/pr_12769.prdoc`), establishing precedent for severity.

### Likelihood Explanation
High reachability: `add_proxy`, `remove_proxy`, and `proxy` are ordinary signed extrinsics available to any account with a `NonTransfer` proxy grant — a routine, intentionally-supported delegation pattern, not a privileged prerequisite. No governance, root, or validator collusion is required; the attacker only needs to already hold a `NonTransfer` proxy relationship (which the delegator grants believing it excludes `swap`), then perform two ordinary extrinsics (`add_proxy` with `proxy_type: Auction`, then `proxy` wrapping `Registrar::swap`).

### Recommendation
Apply the same fix pattern used for the `NonTransfer`/`Governance` case in `asset-hub-westend` (`prdoc/pr_12769.prdoc`) to the Rococo/Westend relay-chain `ProxyType::is_superset` implementations (and the equivalent `rc`-runtime copy): remove the blanket `(ProxyType::NonTransfer, _) => true` rule and replace it with an explicit, audited list of subsets whose `filter()` calls are fully covered by `NonTransfer`'s `filter()`, or add a lattice-consistency test analogous to `proxy_type_superset_relation_matches_call_filters` in `cumulus/parachains/runtimes/assets/asset-hub-westend/tests/tests.rs` for the relay-chain runtimes to prevent regressions.

		/// Swap a lease holding parachain with another parachain, either on-demand or lease
		/// holding.
		///
		/// The origin must be Root, the `para` owner, or the `para` itself.
		///
		/// The swap will happen only if there is already an opposite swap pending. If there is not,
		/// the swap will be stored in the pending swaps map, ready for a later confirmatory swap.
		///
		/// The `ParaId`s remain mapped to the same head data and code so external code can rely on
		/// `ParaId` to be a long-term identifier of a notional "parachain". However, their
		/// scheduling info (i.e. whether they're an on-demand parachain or lease holding
		/// parachain), auction information and the auction deposit are switched.
		#[pallet::call_index(3)]
		#[pallet::weight(<T as Config>::WeightInfo::swap())]
		pub fn swap(origin: OriginFor<T>, id: ParaId, other: ParaId) -> DispatchResult {
			Self::ensure_root_para_or_owner(origin, id)?;

			// If `id` and `other` is the same id, we treat this as a "clear" function, and exit
			// early, since swapping the same id would otherwise be a noop.
			if id == other {
				PendingSwap::<T>::remove(id);
				return Ok(());
			}

			// Sanity check that `id` is even a para.
			let id_lifecycle =
				paras::Pallet::<T>::lifecycle(id).ok_or(Error::<T>::NotRegistered)?;

			if PendingSwap::<T>::get(other) == Some(id) {
				let other_lifecycle =
					paras::Pallet::<T>::lifecycle(other).ok_or(Error::<T>::NotRegistered)?;
				// identify which is a lease holding parachain and which is a parathread (on-demand
				// parachain)
				if id_lifecycle == ParaLifecycle::Parachain &&
					other_lifecycle == ParaLifecycle::Parathread
				{
					Self::do_thread_and_chain_swap(id, other);
				} else if id_lifecycle == ParaLifecycle::Parathread &&
					other_lifecycle == ParaLifecycle::Parachain
				{
					Self::do_thread_and_chain_swap(other, id);
				} else if id_lifecycle == ParaLifecycle::Parachain &&
					other_lifecycle == ParaLifecycle::Parachain
				{
					// If both chains are currently parachains, there is nothing funny we
					// need to do for their lifecycle management, just swap the underlying
					// data.
					T::OnSwap::on_swap(id, other);
				} else {
					return Err(Error::<T>::CannotSwap.into());
				}
				Self::deposit_event(Event::<T>::Swapped { para_id: id, other_id: other });
				PendingSwap::<T>::remove(other);
			} else {
				PendingSwap::<T>::insert(id, other);
			}

			Ok(())
