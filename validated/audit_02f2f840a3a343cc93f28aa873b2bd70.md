## Title
Merkle proof verification lacks leaf/internal-node domain separation, allowing forged proofs for arbitrary elements — (File: `merkle.js`)

### Summary
`ocore`'s merkle implementation, used both for `'in merkle'` address-definition authentifiers and the oscript `is_valid_merkle_proof()` function, hashes leaves and internal nodes with the exact same function and no domain-separation prefix. This mirrors the root cause of CVE-2023-34459 (ambiguity between leaf and internal-node encoding), letting anyone who has observed any genuine merkle proof over a given root forge a valid proof for an attacker-chosen "element" that was never actually a leaf of the tree.

### Finding Description
`getMerkleRoot`/`getMerkleProof` build the tree by repeatedly applying `hash(x) = sha256(x)`: leaves are hashed as `hash(element)`, and each internal node is `hash(child_left + child_right)` (string concatenation, no tag distinguishing "leaf" vs "internal node") [1](#0-0) . Verification walks up from a claimed element using `verifyMerkleProof`, computing `hash(element)` as the starting value and then repeatedly combining with `proof.siblings[i]` exactly the same way internal nodes were built, with no differentiation of tree depth or node type [2](#0-1) . The authors themselves flag this as a known concern in a code comment: `"// Node-as-Leaf issue might matter in some cases"` [3](#0-2) .

Because leaf-hashing and node-hashing are indistinguishable, if an attacker learns the two raw string values `h_left`/`h_right` of any sibling pair anywhere in the tree (which are legitimately exposed as `proof.siblings` in any genuine proof the oracle/tree-builder ever publishes for a real leaf near that subtree), the attacker can set `element = h_left + h_right`. Then `hash(element)` equals the parent node's hash by construction, and supplying the proof path continuing upward from that parent (a truncated/shifted version of an already-observed sibling list, with adjusted `index`) will pass `verifyMerkleProof` for this **forged, never-inserted** `element` value.

This directly maps to the OpenZeppelin advisory's bug class: proving membership of an arbitrary attacker-chosen value against a legitimately-rooted tree by exploiting ambiguity between leaf and internal-node hashing, rather than the proof mechanism cryptographically binding only to actual, declared leaves.

### Impact Explanation
This verification routine gates two consensus-relevant, permissionless paths:
1. The `'in merkle'` address-definition authentifier, evaluated during unit validation, which checks a self-supplied `serialized_proof` element against a data-feed-posted merkle root and, if valid, grants signing authority for that path [4](#0-3) .
2. The `is_valid_merkle_proof()` oscript function usable inside AA formulas/triggers to check arbitrary attacker- or trigger-supplied `element`/`proof` pairs against a root [5](#0-4) .

Any oracle/data-feed publisher that shares even one legitimate merkle proof over a root (a normal, expected usage pattern for merkle-anchored oracle data) leaks sibling hashes that let anyone forge a proof of membership for an unrelated, attacker-chosen value against the same root. An attacker can then satisfy `'in merkle'` conditions in address definitions (unlocking otherwise-restricted spending authority) or pass `is_valid_merkle_proof()` checks inside AAs that gate fund release/logic on oracle-anchored merkle data — leading to unauthorized spending or AA fund loss under conditions the tree/oracle never actually committed to.

### Likelihood Explanation
Exploitation requires the attacker to have observed at least one legitimate proof (any two sibling values at some level) for the target root — a normal, expected condition since data-feed/merkle-root publishers routinely disclose proofs to consumers. No preimage break of SHA-256 is required; the forged "element" is simply the concatenation of two already-known strings. This is a low-effort, deterministic construction once any single genuine proof for the tree is public, and is directly usable against any AA or address definition relying on `'in merkle'` / `is_valid_merkle_proof` for balanced or partially-known trees.

### Recommendation
Introduce domain separation between leaf and internal-node hashing (e.g., `hash(0x00 + element)` for leaves and `hash(0x01 + left + right)` for internal nodes), matching the approach OpenZeppelin adopted after this CVE. Additionally, encode/commit sibling values with length-prefixing or fixed-size encoding to remove any parsing ambiguity in the concatenation, and consider hashing leaves prior to insertion in all producers (`dataFeeds`, `objectHash`) so raw application values are never used directly as tree leaves.

### Proof of Concept
1. Oracle builds merkle tree over 4+ elements with `merkle.getMerkleRoot`/`getMerkleProof` and publishes root via data feed, later sharing (or an attacker observes via any means) a proof for one leaf, revealing `proof.siblings = [s0, s1, ...]`.
2. Attacker computes `forged_element = s0 + s1` (the exact two children of some internal node revealed in step 1) and builds a new proof object `{ index: <parent index>, siblings: proof.siblings.slice(2), root: proof.root }`.
3. Attacker submits `forged_element` and the truncated proof either as the `'in merkle'` authentifier value in an address definition path, or as arguments to `is_valid_merkle_proof(forged_element, forged_proof)` in an AA formula.
4. `merkle.verifyMerkleProof(forged_element, forged_proof)` returns `true` [6](#0-5)  even though `forged_element` was never a leaf of the original tree, satisfying the condition and unlocking the guarded spending/AA logic.

function hash(str){
	return crypto.createHash("sha256").update(str, "utf8").digest("base64");
}

function getMerkleRoot(arrElements){
	var arrHashes = arrElements.map(hash);
	while (arrHashes.length > 1){
		var arrOverHashes = []; // hashes over hashes
		for (var i=0; i<arrHashes.length; i+=2){
			var hash2_index = (i+1 < arrHashes.length) ? (i+1) : i; // for odd number of hashes
			arrOverHashes.push(hash(arrHashes[i] + arrHashes[hash2_index]));
		}
		arrHashes = arrOverHashes;
	}
	return arrHashes[0];
}

function verifyMerkleProof(element, proof){
	// Node-as-Leaf issue might matter in some cases
	try {
		var index = proof.index;
		var the_other_sibling = hash(element);
		for (var i = 0; i < proof.siblings.length; i++) {
			// this also works for duplicated trailing nodes
			if (index % 2 === 0)
				the_other_sibling = hash(the_other_sibling + proof.siblings[i]);
			else
				the_other_sibling = hash(proof.siblings[i] + the_other_sibling);
			index = Math.floor(index / 2);
		}
		return (the_other_sibling === proof.root);
	}
	catch (e){
		return false;
	}
}
