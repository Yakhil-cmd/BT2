### Title
Webhook signature is verified against a GitHub App keyed by an unauthenticated payload field, while the repository actually acted upon is read from a different unauthenticated payload field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which* HMAC secret to check the `X-Hub-Signature` against by reading `repository.owner.login` (or `organization.login`) straight out of the still-unverified JSON body, then verifies the raw body against that secret. Once verification "succeeds," `create` dispatches the very same body to event handlers that determine which `Repository`/`Stack` to mutate by reading a *different* field, `repository.full_name` (`Handlers::Handler#repository_name`). Nothing ties the organization whose secret validated the signature to the repository/org that the handler subsequently writes to. This mirrors the reported Astaria bug class: a value that is used to authorize an action (there: `maxPotentialDebt`, here: which org's secret is trusted) is not cross-checked against the value that the operation actually acts on (there: the newly appended stack, here: `repository.full_name`).

### Finding Description
`app/controllers/shipit/webhooks_controller.rb`:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end

  ...
  SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
end

The docs explicitly document per-organization webhook secrets as a supported, first-class configuration (`docs/setup.md` "Using Multiple Github Applications"), so any Shipit instance serving more than one GitHub organization is exposed by design, not by misconfiguration: [9](#0-8) 

**The broken equality:** the code implicitly assumes
`organization(repository.owner.login used to select the verifying secret) == organization(repository.full_name used to resolve the Repository/Stack that gets mutated)`.
Nothing enforces this. An attacker who can produce a validly-signed webhook body for Organization A (e.g., because they have legitimate write access to a public/low-value repo under Org A and can trigger real GitHub webhook deliveries carrying attacker-controlled JSON structure via GitHub's replay/redelivery, or because Org A's secret has weaker operational protection) can set `repository.owner.login = "orgA"` (so Org A's secret is selected and the HMAC computed over the raw, fully attacker-controlled body validates) while setting `repository.full_name = "orgB/private-repo"`. `Repository.from_github_repo_name` then resolves Org B's `Repository`/`Stack` and the handler acts on it — an organization crossing that should be architecturally impossible given the "one GitHub App per organization" model documented for multi-org setups.

### Impact Explanation
This breaks the cross-repository/cross-organization isolation that the multi-org GitHub App model is supposed to provide: a webhook cryptographically authenticated for Organization A's App installation can be made to drive state changes (GitHub commit sync, stack archive/unarchive of review stacks via the `pull_request` handlers, commit `Status` creation, `check_suite` refresh) against Organization B's stacks. Per the accepted impact list this qualifies as a cross-repository/cross-organization write triggered through a boundary that should have been enforced by App-to-organization binding, satisfying the "cross-repository writes" bar even though it does not directly leak `GITHUB_TOKEN` or force a deploy by itself; `sync_github` mutating another org's commit graph and detaching commits (`shared_parent&.detach_children!`) is a genuine unauthorized write to a repository's/stack's data outside the boundary the signing key was meant to enforce.

### Likelihood Explanation
Exploitation requires the deployer to run Shipit in the documented multi-organization mode (`docs/setup.md`, "Using Multiple Github Applications") and requires the attacker to be able to produce a body that verifies against *some* org's secret while carrying a different org's `repository.full_name` — this is most directly reachable if any configured organization has no `webhook_secret` set (`return true unless webhook_secret` short-circuits verification entirely for that org) or if an attacker otherwise controls a legitimate signed delivery from one org and can influence body content delivered through GitHub (e.g., a malicious repo name/rename or GitHub's own webhook delivery for events attacker partially controls). This is not the most common day-one configuration, but it is a documented, supported one, and the underlying design flaw (verifying against a value chosen from unauthenticated data, then acting on a different value from the same unauthenticated data) is present regardless of the exact delivery vector.

### Recommendation
Do not select the verification secret from an unauthenticated field of the same payload whose authenticity is being tested. Options:
- Bind webhooks to a specific organization/App via routing (e.g., `/webhooks/:organization`) rather than inferring it from `params`, so the secret used for verification is chosen by trusted configuration, not attacker-controlled JSON.
- After signature verification succeeds, re-derive and enforce that `repository.owner.login` used for verification equals the owner encoded in `repository.full_name` (and equals the resolved `Repository#owner`) before dispatching to handlers, rejecting the event otherwise.
- Iterate over all configured organizations' secrets to find one that validates the signature (defense in depth), and pass the *matched* organization, not the attacker-declared one, into the handler pipeline for authorization decisions.

### Proof of Concept
1. Deploy Shipit configured for two GitHub organizations, `orgA` and `orgB`, each with its own App/`webhook_secret` (per `docs/setup.md` multi-org instructions), both mounted at the shared `/webhooks` endpoint.
2. Attacker crafts a JSON body for a `push` event where `repository.owner.login = "orgA"` (or omits it and relies on `organization.login = "orgA"`) but `repository.full_name = "orgB/private-repo"`.
3. Attacker computes/obtains a valid `X-Hub-Signature` for this exact raw body using `orgA`'s `webhook_secret` (trivial if `orgA`'s secret is known/weak, or if `orgA` has no `webhook_secret` configured at all, in which case `verify_webhook_signature` returns `true` unconditionally per `lib/shipit/github_app.rb#L76-77`).
4. POST to `/webhooks` with `X-Github-Event: push`. `verify_signature` looks up `Shipit.github(organization: "orgA")`, verifies successfully.
5. `create` dispatches the body to `PushHandler`, which resolves `Repository.from_github_repo_name("orgB/private-repo")` and calls `stack.sync_github(...)` on Org B's stack — a write triggered by a signature that was never checked against Org B's own webhook secret. [10](#0-9) [5](#0-4) [6](#0-5)

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end

If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently.
