### Title
Webhook signature verification keys the secret lookup off the attacker-controlled `repository.owner.login` field, which is independent of the `repository.full_name`/`organization.login` fields the handlers actually act on - allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to verify the HMAC signature against by reading `repository.owner.login` out of the *unauthenticated* JSON body itself, then verifies the HMAC over the whole raw body with that secret. [1](#0-0)  Once verification passes, `Shipit::Webhooks::Handlers::Handler` resolves the actual `Stack`/`Repository` to mutate using a *separate* field of the same body, `repository.full_name`, via `Repository.from_github_repo_name(repository_name)`. [2](#0-1) 

Because the signature check only proves "this payload was signed by whichever org's secret matches `repository.owner.login`" and not "this payload legitimately describes a webhook fired by GitHub for `repository.full_name`", any party who knows (or legitimately possesses, as an org admin) the `webhook_secret` for **any one** GitHub organization configured on a shared Shipit instance can forge a signed payload that sets `repository.owner.login` to their own org (so the secret lookup/HMAC succeeds) while setting `repository.full_name` to an arbitrary **other** org/repo's stack. The push/status/check_suite handlers then act on that other stack as if GitHub itself had sent the event.

### Finding Description
Shipit explicitly supports "Using Multiple Github Applications", where each configured GitHub organization has its own `webhook_secret`. [3](#0-2)  The `GitHubApp#verify_webhook_signature` computes an HMAC over the raw request body using the `webhook_secret` belonging to whatever organization was selected. [4](#0-3) 

The organization selection itself comes straight from the payload the caller controls:
```ruby
def repository_owner
  # Fallback to the organization sub-object if repository isn't included in the payload
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [5](#0-4) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
``` [6](#0-5) 

After the signature check, `WebhooksController#create` dispatches the raw parsed body to handlers. [7](#0-6)  Every handler resolves the target `Stack`/`Repository` using `repository.full_name`, a field that is never re-checked against `repository.owner.login`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [2](#0-1) 

For example, `PushHandler#process` finds all matching stacks and calls `stack.sync_github(expected_head_sha: params.after)`, which enqueues `GithubSyncJob` — pulling attacker-influenced commit history into the target stack's tracked commit graph. [8](#0-7) 

**The binding that is broken:** "organization that authenticated" (i.e., whose `webhook_secret` validated the HMAC, derived from `repository.owner.login`) is treated as equal to "repository that is written" (derived independently from `repository.full_name`), but nothing in the code enforces that equality. An attacker who is a legitimate admin of `OrgA` (and thus knows `OrgA`'s `webhook_secret`, e.g. because they set up the GitHub App/webhook for their own repository connected to this shared Shipit instance) can:
1. Craft a JSON payload with `repository.owner.login = "OrgA"` (so `Shipit.github(organization: "OrgA")` resolves and the HMAC validates), and
2. Set `repository.full_name = "OrgB/victim-repo"` (or any other repository/stack tracked by the instance).
3. Sign the entire raw body with `OrgA`'s `webhook_secret`.
4. POST it to the shared `/github/hooks` (or engine-mounted equivalent) endpoint.

`verify_signature` passes because the HMAC matches `OrgA`'s secret over the exact bytes sent. The handler then acts on `OrgB/victim-repo`'s `Stack` using attacker-supplied push/status/check_suite/membership data.

### Impact Explanation
This crosses a repository/organization trust boundary that Shipit's multi-org design is explicitly meant to enforce (each org's webhook only speaks for that org's own repositories). An attacker who legitimately controls webhook configuration for one tenant/org on a shared Shipit instance can forge GitHub events for a completely different org/repository's `Stack`, without ever having write access to that other repository. Depending on handler, this enables: injecting/altering commit status webhooks used in `MergeRequest`/deploy-gating logic, triggering `GithubSyncJob` to pull attacker-chosen commit metadata into another team's stack, or manipulating team/membership records via the `membership` handler for an org the attacker doesn't belong to. This matches the "cross-repository writes"/unauthorized deploy-adjacent impact class, since the forged events feed directly into commit tracking and merge/deploy decision state for a stack outside the attacker's authorized scope.

### Likelihood Explanation
Exploitability requires only that the Shipit deployment configures `github` as a multi-organization map (documented as a supported, non-exotic configuration) and that the attacker has legitimate knowledge of any one of those orgs' `webhook_secret` values (e.g., as the admin/maintainer who configured that org's GitHub App). No access to `GITHUB_TOKEN`, `api_clients_secret`, private keys, or any of the target org's secrets is required. It also does not depend on frontrunning or timing races — a single crafted HTTP request suffices, which is a stronger and more deterministic exploitation vector than the ID-collision report it was scanned against.

### Recommendation
Bind the signature verification to the same identity the handlers act on: derive `repository_owner` (or, better, the full `owner/repo`) used to select the `webhook_secret` from the same trusted field that will be used to resolve the `Stack`, and additionally verify, after locating the `Stack`/`Repository` by `full_name`, that its owner matches the organization whose secret validated the signature (e.g., compare `Repository#owner` to `repository_owner` post-verification and reject on mismatch). Alternatively, do not select secrets per-payload-declared org at all when multiple orgs are configured on one endpoint — segment webhook endpoints per organization/app installation so each has a dedicated URL with its own secret and no attacker-controlled org-selection field is possible in the trust decision.

### Proof of Concept
Given a Shipit instance configured with two organizations, `OrgA` (webhook secret known to attacker, who is `OrgA`'s app admin) and `OrgB` (stack `orgb/victim-repo` tracked by Shipit, secret unknown to attacker):

1. Attacker builds the JSON push payload:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef0000000000000000000000000000cafe",
  "repository": {
    "full_name": "orgb/victim-repo",
    "owner": { "login": "OrgA" }
  }
}
```
2. Attacker computes `sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>` and sets it as `X-Hub-Signature`, with `X-Github-Event: push`.
3. POST to the Shipit webhooks endpoint.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgA")` (derived from `repository.owner.login`), and the HMAC matches because it was signed with `OrgA`'s real secret — verification passes. [6](#0-5) 
5. `PushHandler` resolves `stacks` via `Repository.from_github_repo_name("orgb/victim-repo")` (the `full_name` field, unrelated to `OrgA`) and calls `stack.sync_github(expected_head_sha: "deadbeef...")` on `OrgB`'s stack. [9](#0-8) 
6. `GithubSyncJob` runs against `OrgB`'s stack using the attacker-triggered event, even though the attacker never possessed `OrgB`'s webhook secret or had any access to `orgb/victim-repo`. [10](#0-9)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
