### Title
Cross-organization webhook signature confusion allows spoofed events to be applied to a different organization's stacks - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/handler.rb)

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp`/`webhook_secret` to verify a webhook against based on `params.dig('repository','owner','login')` (falling back to `params.dig('organization','login')`), while every `Shipit::Webhooks::Handlers::Handler` subclass resolves the actual `Repository`/`Stack` to mutate using an independently-read field, `payload.dig('repository','full_name')`. These two fields are never cross-checked against each other, so the organization whose secret authenticated the request is not bound to the repository the handler subsequently writes to.

### Finding Description
`verify_signature` picks the signing key like this: [1](#0-0) [2](#0-1) 

`repository_owner` is only `owner.login` (or `organization.login`) — it never constrains `repository.full_name`. The signature check (`GitHubApp#verify_webhook_signature`) only proves that *some* configured organization's `webhook_secret` was used to sign the raw body: [3](#0-2) 

Once verified, `WebhooksController#create` dispatches the full, attacker-supplied JSON body to every registered handler for the event, unmodified: [4](#0-3) 

Every handler then derives the repository to act on solely from `repository.full_name` inside that same body, with no relation back to which organization's secret validated the request: [5](#0-4) 

This pattern repeats across handlers, e.g. `PushHandler` (`stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(...) }`), and the `PullRequest` handlers (`opened`, `closed`, `labeled`, `unlabeled`, `reopened`, `assigned`) which resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)` independent of `repository_owner`: [6](#0-5) [7](#0-6) 

**The trust boundary broken:** `organization authenticated by signature == organization that actually owns repository.full_name`. Shipit is explicitly designed as multi-tenant: `config/secrets.development.example.yml` shows multiple orgs, each with its own `app_id`/`installation_id`/`webhook_secret`, all handled by the same `/webhooks` endpoint: [8](#0-7) 

An entity that legitimately administers its own onboarded GitHub App on this Shipit instance (and therefore knows its own `webhook_secret`, since GitHub App owners set/see that secret when configuring the webhook on GitHub's side) can forge a raw JSON payload where `repository.owner.login` (or `organization.login`) is set to *its own* org (so `verify_signature` succeeds using its own secret) while `repository.full_name` is set to a *different* onboarded organization's repository (e.g. `"victim-org/victim-repo"`). The signature check passes because it only validates the byte string against the attacker's own known secret; it never checks that the signing org matches the repository named inside the payload.

### Impact Explanation
This breaks the binding "organization authenticated == repository written," enabling cross-repository/cross-tenant writes without any GitHub-side compromise of the victim org:
- `PushHandler` can force `stack.sync_github(expected_head_sha: ...)` against a victim stack, triggering fetch/deploy machinery against attacker-chosen `after` SHAs.
- `PullRequest::LabeledHandler`/`UnlabeledHandler`/`ClosedHandler`/`ReopenedHandler`/`OpenedHandler` can archive, unarchive, or create/destroy review stacks belonging to the victim organization.
- `StatusHandler`/`CheckSuiteHandler` (not fully inspected due to tool budget, but following the same `Handler#stacks`/`repository_name` pattern) could inject fabricated commit statuses/check-suite results for a victim repository's commits — directly influencing Shipit's merge queue, which gates merges/deploys on commit status. That crosses into "cross-repository writes" / "unauthorized merge or deploy," which is the required Critical-tier impact for this analog.

### Likelihood Explanation
Medium-to-High: exploitation requires only that the attacker be a legitimate, unprivileged operator of *any* one organization already onboarded to the shared Shipit instance (a realistic scenario for any Shipit deployment serving more than one GitHub org/team, which the codebase explicitly supports). No GitHub credentials, private keys, or victim secrets are needed — only the attacker's own `webhook_secret`, which they control by design.

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler`), after signature verification succeeds, assert that the repository/organization actually referenced in the payload (`repository.full_name`'s owner, or `organization.login`) matches the `repository_owner` value used to select the verifying `GitHubApp`/secret. Reject the webhook (422) if there's a mismatch, rather than trusting `full_name` in isolation for repository/stack lookups.

### Proof of Concept
1. Attacker onboards/administers organization `attacker-org` on the shared Shipit instance, with its own `webhook_secret` (`S_attacker`) configured in `secrets.yml` per the multi-org schema in `config/secrets.development.example.yml`.
2. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef...",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org" }
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(S_attacker, body)>` using their own known secret.
4. Attacker POSTs this to `/webhooks` with header `X-Github-Event: push`.
5. `repository_owner` resolves to `attacker-org` → `Shipit.github(organization: 'attacker-org')` → signature verifies successfully against `S_attacker`.
6. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name('victim-org/victim-repo')` (per `Handler#repository_name`) and calls `stack.sync_github(expected_head_sha: 'deadbeef...')` on the victim's stack — a write triggered entirely by an org that has no relationship to `victim-org`.

Note: I could not fully inspect `status_handler.rb`/`check_suite_handler.rb`/`membership_handler.rb` contents within the available tool budget to confirm the exact write operations they perform; the analysis of those handlers'  reachability to `Handler#stacks`/`repository_name` is inferred from the shared base class and the pattern seen in `PushHandler` and the `PullRequest` handlers, which were fully read.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
