### Title
AA trigger.address is bound to the alphabetically-first author, not the actual payer, enabling reward/response hijacking in multi-authored triggers - (File: aa_composer.js)

### Summary
`getTrigger()` derives the identity an Autonomous Agent treats as "the sender" solely from `objUnit.authors[0].address`, while the payment amount credited to the AA is summed from *all* payment outputs addressed to the AA in the same unit, with no check that the funding inputs belong to that first author. Because unit authors must be sorted by address (`validateAuthors`), an attacker can co-author a single payment unit together with a victim whose address sorts first, so that funds actually supplied by the victim are attributed to the attacker for all AA-side authorization/refund/reward logic keyed on `trigger.address`. This is the ocore analog of the reported "AllowanceTarget approval drain": a piece of previously-granted authorization/identity (here, "who is `trigger.address`") is exercised by a party other than the one whose funds are actually being moved, resulting in unauthorized diversion of value that the AA legitimately owes.

### Finding Description
`getTrigger()` sets `trigger.address = objUnit.authors[0].address` unconditionally, then loops over **all** `payment` messages in the unit and sums into `trigger.outputs` any output addressed to the receiving AA — regardless of which author's `inputs` funded that output: [1](#0-0) 

This `trigger` object (in particular `trigger.address`) is what all AA oscript logic uses to decide whom to refund, credit, or record ownership for (state vars, issued assets, discounts, "already paid" checks, etc.), as seen throughout the AA sample scripts and tests, e.g. `outputs: [{address: "{trigger.address}", ...}]` and `var[trigger.address]` state bookkeeping: [2](#0-1) [3](#0-2) 

Multi-author units are a first-class, unprivileged feature ("multilateral signing", shared addresses) reachable by any user, and `validateAuthors` only imposes that authors are listed in **ascending address order** — it does not require author[0] to be the address whose inputs fund the AA payment: [4](#0-3) 

Meanwhile, `validatePaymentInputsAndOutputs` only requires that the **owner of a spent input** be among the unit's authors (`arrAuthorAddresses.indexOf(owner_address) === -1` → reject); it does not require that owner to be `authors[0]`: [5](#0-4) 

Putting these together: a unit can be validly composed and cosigned with two authors, A (attacker, address sorts first) and V (victim, address sorts second, e.g. a shared/multisig address V has cosigned for an unrelated reason such as a joint wallet or an arbiter contract), where the payment's inputs are owned by V but the output goes to the target AA. The unit is fully valid per `validateAuthors`/`validatePaymentInputsAndOutputs`. When this unit stabilizes and triggers the AA, `getTrigger()` still reports `trigger.address = A` (author[0]) even though V's coins paid for it. Any AA logic that uses `trigger.address` to gate a benefit ("first N payers get X", "record depositor for later reward", "credit purchased asset/shares to trigger.address", "mark address as having paid invoice") will credit the benefit to A instead of V, letting A capture funds/assets that the AA intended to be paid to V — the payer.

This mirrors the external bug class: the external exploit abused a standing, address-scoped authorization (`ALLOWANCE_TARGET` allowance) via a shared "already-authorized" contract to move a victim's funds to the attacker without the victim's payment intent being honored for its intended beneficiary. Here, the ocore analog is the AA's addressing/authorization primitive (`trigger.address`) being decoupled from the actual source of funds in a multi-author unit, letting a co-signer redirect the AA's fund/state response away from the true payer.

### Impact Explanation
Any AA that uses `trigger.address` (directly or via state vars keyed by it) to determine a beneficiary of payments, issued assets, discounts, or refunds is exposed. In a two-cosigner scenario an attacker can:
- Redirect refunds/change/rewards that should go to the paying co-author to themselves.
- Falsely register themselves as the payer for logic like "first depositor gets bonus asset" or "mark address as attested/paid", stealing that credit from the actual funder.
- In AA-based exchanges/ICOs that key balances/vesting to `trigger.address`, cause fund loss for the real depositor and unauthorized gain for the attacker.

This is a concrete AA fund-loss / unauthorized-crediting vector reachable by any user who can get a counterparty to co-sign a single unit (a routine, unprivileged operation for shared/multisig addresses), so it satisfies "AA fund loss" / "unauthorized spending" criteria at Medium-to-High severity depending on the specific AA's logic.

### Likelihood Explanation
Likelihood depends on the specific AA implementation trusting `trigger.address` as "the payer" in a multi-author unit context, which is a very common oscript pattern (nearly every sample/test AA does `outputs: [{address: "{trigger.address}", ...}]`). It requires a victim to co-sign a unit with the attacker where the victim's own funds are the ones paid to the AA — a plausible scenario in shared-address/joint-wallet setups, or if a victim's automated cosigning service (e.g. an arbiter or a "multilateral signing" contract flow) doesn't inspect whose inputs are being spent versus who else is co-authoring. It is not a purely theoretical construct: the codebase explicitly supports and documents multi-author "multilateral signing... such as a (dumb) contract" (`wallet.js`), confirming this pattern is intentionally exposed to general users.

### Recommendation
- In `getTrigger()`, derive `trigger.address` from the address that actually owns the inputs funding the AA payment, not merely `authors[0]`. When a unit is multi-authored, either (a) require a single, unambiguous payer address for AA-directed payments and reject/clarify otherwise, or (b) expose the true payer address(es) explicitly in the trigger object separate from the (cryptographic) author list, and update documentation/oscript semantics so contract authors do not implicitly conflate "author[0]" with "the payer."
- Add validation that rejects (or explicitly documents and forces AA authors to defend against) AA-directed payments in units where the paying input's owner differs from `authors[0]`.
- Audit official AA samples/patterns (`test/samples/*.oscript`) that rely on `trigger.address` for crediting purposes and add guidance/warnings in the AA docs about this multi-author ambiguity.

### Proof of Concept
1. Attacker A and victim V jointly control (or V is tricked into cosigning) a 2-author unit where V's address is lexically greater than A's, so `authors = [A, V]`.
2. The unit's `payment` message spends **V's** input(s) and sends the output amount to AA address `X`.
3. Both A and V sign the unit (a normal multi-author flow, e.g. via the `sign`/multilateral-signing path in `wallet.js`), and it is broadcast and stabilizes.
4. When `X` becomes a stable AA trigger, `getTrigger(objUnit, X)` computes:
   - `trigger.address = objUnit.authors[0].address` → `A`
   - `trigger.outputs.base` → amount from V's payment [1](#0-0) 
5. Any AA logic such as `{address: "{trigger.address}", amount: ...}` or `var[trigger.address] = ...` (as in the sample AAs) will refund, credit tokens, or record state against `A`, even though `V` supplied the funds — demonstrating that the AA's benefit/refund is diverted from the true payer to the attacker.

Note: this analysis is based on static code review of `aa_composer.js`, `validation.js`, and representative AA samples/tests; I did not execute a live trigger end-to-end in this environment, so the exact bounce/refund behavior of a concrete production AA would need to be confirmed against that AA's specific oscript logic before treating this as an exploit against any deployed contract.

function getTrigger(objUnit, receiving_address) {
	var trigger = { address: objUnit.authors[0].address, unit: objUnit.unit, outputs: {} };
	if ("max_aa_responses" in objUnit)
		trigger.max_aa_responses = objUnit.max_aa_responses;
	objUnit.messages.forEach(function (message) {
		if (message.app === 'data' && !trigger.data) // use the first data message, ignore the subsequent ones
			trigger.data = message.payload;
		else if (message.app === 'payment' && message.payload) {
			var payload = message.payload;
			var asset = payload.asset || 'base';
			payload.outputs.forEach(function (output) {
				if (output.address === receiving_address) {
					if (!trigger.outputs[asset])
						trigger.outputs[asset] = 0;
					trigger.outputs[asset] += output.amount; // in case there are several outputs
				}
			});
		}
	});
	if (Object.keys(trigger.outputs).length === 0)
		throw Error("no outputs to " + receiving_address);
	return trigger;
}
