### Title
Webhook signature verification is keyed off an attacker-controlled `repository.owner.login`/`organization.login` field that is independent of the repository the webhook actually mutates - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects *which* GitHub App config (and thus which `webhook_secret`) is used to validate the HMAC signature by reading `repository.owner.login`/`organization.login` straight out of the still-unverified JSON body. Every webhook handler, however, resolves the repository it actually writes to independently, from `repository.full_name` in the same body. These two lookups are never cross-checked. In a multi-organization Shipit install (a documented, supported configuration), any organization whose `webhook_secret` is left blank causes signature verification to short-circuit to `true` for a payload merely *claiming* to belong to that organization — while the payload's `repository.full_name` can point at a completely different, fully-configured, tracked repository.

### Finding Description
`Shipit::WebhooksController#verify_signature` picks the verifying GitHub App using an org name pulled from the raw, not-yet-authenticated body: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` treats an absent `webhook_secret` as automatic success: [3](#0-2) 

Shipit explicitly supports multiple GitHub organizations, each with its own independently-configurable `webhook_secret`, and the shipped example/dummy configs show `webhook_secret` left blank as a normal, valid state: [4](#0-3) [5](#0-4) [6](#0-5) 

Once "verified", the raw params are dispatched unmodified to every registered handler: [7](#0-6) 

But the handler base class — used by `PushHandler` and all `pull_request`/other handlers — determines the repository/stacks to mutate from a *different* field of the same body, `repository.full_name`, completely decoupled from whatever org was used to select the (possibly secret-less) verifying app: [8](#0-7) [9](#0-8) 

This is exactly the "authenticated organization vs. repository actually written" binding break: the equality that must hold is
`org(secret used to verify signature) == owner(repository actually mutated by the handler)`.
The controller never enforces this — it only uses `repository.owner.login`/`organization.login` to *pick a config*, and separately (in a totally different code path, the `Handler` class) uses `repository.full_name` to *pick the target*. An attacker who knows (or can enumerate) one organization slug in the install that has no `webhook_secret` configured can set `repository.owner.login`/`organization.login` to that slug (causing `verify_webhook_signature` to always return `true`, regardless of the `X-Hub-Signature` header sent) while setting `repository.full_name` to any other tracked, fully-secured repository, and the forged event will be processed for that other repository.

### Impact Explanation
This allows an unauthenticated attacker to forge arbitrary GitHub webhook events (`push`, `status`, `check_suite`, `pull_request`, `membership`, etc.) targeting any repository/stack tracked by the Shipit install, with no valid `webhook_secret` needed at all — bypassing the entire authentication boundary the `WebhooksController` is meant to enforce. Concretely this can:
- Feed attacker-chosen commit SHAs into `stack.sync_github` via a forged `push` event.
- Forge `status`/`check_suite` events marking arbitrary commits "green".
- Combined against a stack with `continuous_deployment: true`, this can drive Shipit into autonomously deploying attacker-influenced commits — an unauthorized deploy — without any GitHub credentials, webhook secret, API client token, or Shipit session, matching the Critical "unauthorized deploy" impact.

### Likelihood Explanation
Requires only that the Shipit install use, or be configurable with, multiple GitHub organizations where at least one has no `webhook_secret` set (a state the project's own example/dummy configs treat as normal/default) and that the attacker can reach the public `/webhooks` endpoint (unauthenticated, no CSRF token needed — `skip_before_action :verify_authenticity_token`). No repository write access, session, or secret material is required.

### Recommendation
Do not use attacker-supplied payload fields to select the verification key. Instead, verify the signature against every configured organization's secret (or against the specific organization the target `Stack`/`Repository` actually belongs to), and reject the request if the resolved repository's owning organization does not match the organization whose secret produced a valid signature. Also disallow `webhook_secret` from being effectively "always valid" when blank in installs that mix secured and unsecured organizations — require explicit opt-in for unauthenticated webhook processing.

### Proof of Concept
1. Configure (or find) a multi-org Shipit install where org `NoSecretOrg` has `webhook_secret` unset and org `RealOrg` (tracked in Shipit as `RealOrg/app`) has a real secret.
2. POST to `/webhooks` with header `X-Github-Event: push`, an arbitrary/garbage `X-Hub-Signature`, and body:
```json
{
  "organization": { "login": "NoSecretOrg" },
  "repository": { "owner": { "login": "NoSecretOrg" }, "full_name": "RealOrg/app" },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>"
}
```
3. `verify_signature` calls `Shipit.github(organization: "NoSecretOrg")`, whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` regardless of the bogus signature.
4. `PushHandler` resolves the target via `payload.dig('repository','full_name')` → `RealOrg/app`, and enqueues `GithubSyncJob` for that stack — despite the request never having been validated against `RealOrg`'s actual webhook secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
