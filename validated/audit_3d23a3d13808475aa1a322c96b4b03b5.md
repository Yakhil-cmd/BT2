### Title
Cross-organization webhook forgery via mismatched signature-verification key and payload target repository - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to use for HMAC verification based on an attacker-controlled field inside the unsigned-at-selection-time JSON payload (`repository.owner.login` / `organization.login`), while the handlers that act on the request (e.g. `StatusHandler`, `PushHandler`) operate on a *different* attacker-controlled field of the same payload (`repository.full_name`, `sha`) that is never cross-checked against the organization whose secret validated the signature.

### Finding Description
`verify_signature` computes the signing organization purely from payload content, not from any authenticated channel: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
end
...
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization:)` looks up a per-organization config/secret when the instance is configured for multiple organizations (`Shipit.github_app_config`), each with its own independent `webhook_secret`: [3](#0-2) 

Once the HMAC check passes (using whichever organization's secret matched the payload's self-declared `repository.owner.login`), the request body is dispatched to handlers that read *other* fields of the same JSON to decide what to act on:

- `StatusHandler` does not check the repository at all — it matches purely on `sha` across the entire commits table and writes a `Status`: [4](#0-3) 

- `PushHandler`/`Handler#stacks` resolve the target repository via `repository.full_name`, a field independent from `repository.owner.login` used for signing: [5](#0-4) [6](#0-5) 

Because the whole raw POST body is attacker-supplied JSON, and the HMAC is computed over that entire body with a key chosen from one field of that same body, an attacker who is a legitimate GitHub App integrator for **their own** onboarded organization (and thus knows that organization's `webhook_secret`) can forge a signature that is valid for a payload whose `repository.full_name`/`sha` target a completely unrelated organization/repository/commit tracked by the same shared Shipit instance. The binding broken is: *organization whose secret authenticated the request* ≠ *repository/commit the handler actually writes to*.

### Impact Explanation
On a Shipit instance shared by multiple organizations (each with its own GitHub App and `webhook_secret`, as explicitly supported by `Shipit.github_app_config`), a low-privileged attacker who administers or controls the webhook secret for one onboarded organization can forge `status` webhooks that inject arbitrary commit statuses (`state`, `description`, `target_url`, `context`) onto **any commit sha already known to Shipit, regardless of which organization/repository it belongs to**, because `StatusHandler` never re-checks the organization. Since Shipit uses commit CI statuses to gate deploy readiness/merge eligibility, this allows an attacker without access to the victim organization or repository to make an unmerged/unsafe commit appear to have passing CI, potentially leading to an unauthorized deploy of another organization's stack — matching the High-impact criterion "escalation... unauthenticated read/write of stack state" via a broken authentication boundary.

### Likelihood Explanation
Requires only that the Shipit instance is configured for more than one organization (a documented, supported configuration in `Shipit.github_app_config`/`TOP_LEVEL_GH_KEYS`) and that the attacker is a legitimate but unprivileged integrator for one of those organizations (knows only their own `webhook_secret`, has no access to the victim org/repo). No `ApiClient` token, GitHub App private key, or repository write access to the victim repository is required — only the ability to know one's own onboarded organization's webhook secret and POST to the shared `/webhooks` endpoint.

### Recommendation
After verifying the HMAC, re-derive the organization from the same trusted value used for verification and require every handler to confirm that the repository/commit it is about to mutate actually belongs to that organization (e.g., compare `Repository#owner` against `repository_owner` before dispatch, and scope `StatusHandler`'s commit lookup by repository, not just `sha`). Alternatively, verify the signature against every configured organization's secret and only accept the match whose organization equals the repository owner declared in the same payload.

### Proof of Concept
1. Shipit is configured with two organizations, `orgA` and `orgB`, each with a distinct GitHub App and `webhook_secret` (per `docs/setup.md` multi-org setup).
2. Attacker controls `orgA`'s GitHub App and therefore knows `orgA`'s `webhook_secret`.
3. Attacker crafts a `status` webhook JSON body with:
   - `repository.owner.login = "orgA"` (or `organization.login = "orgA"`, used only for signature-key selection)
   - `sha` = the SHA of a real commit belonging to `orgB`'s tracked repository
   - `state = "success"`, forged `context`/`description`/`target_url`
4. Attacker computes `X-Hub-Signature` using `orgA`'s `webhook_secret` over the full raw body and POSTs to `/webhooks`.
5. `verify_signature` calls `Shipit.github(organization: "orgA")` and validates successfully with `orgA`'s secret.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching `orgB`'s commit — and calls `commit.create_status_from_github!(params)`, writing a forged "success" status onto `orgB`'s commit despite the attacker having no relationship to `orgB`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
