### Title
Webhook signature is bound to the payload's `repository.owner`/`organization` login, but `StatusHandler` writes commit statuses scoped only by `sha`, letting an authenticated-but-unrelated organization forge CI status for any stack's commit - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App secret to use for HMAC verification based on a field read out of the unauthenticated request body itself (`repository.owner.login` or `organization.login`), then dispatches the parsed body to event handlers. [1](#0-0)  `StatusHandler#process`, however, never checks that the commit it updates belongs to the repository/organization that was actually authenticated - it looks up commits globally by `sha` alone and writes a `Status` record onto whatever it finds. [2](#0-1)  This breaks the intended binding: `authenticated organization == repository/commit being written`.

### Finding Description
Shipit supports multi-organization deployments where each organization has its own GitHub App configuration, including an independently optional `webhook_secret` (documented as optional in the setup guide, and demonstrated by the shipped multi-org config fixture with multiple orgs each carrying their own, potentially blank, secret). [3](#0-2) [4](#0-3) 

`GitHubApp#verify_webhook_signature` short-circuits to `true` whenever no `webhook_secret` is configured for the organization resolved from the request: [5](#0-4) 

`WebhooksController#verify_signature` resolves *which* app/secret to check against purely from attacker-controlled JSON fields (`repository.owner.login`, falling back to `organization.login`) before any signature has been validated: [6](#0-5) [7](#0-6) 

Once verification passes (trivially, for any org lacking a secret, or for a legitimately-signed webhook from an org the attacker is a member/installer of), the raw JSON is dispatched to the registered handlers for the event type: [8](#0-7) [9](#0-8) 

`StatusHandler#process` then updates `Commit` records matched **only by `sha`**, with no scoping to the repository/organization that was authenticated in `verify_signature`: [10](#0-9) 

Git commit SHAs are public information (visible on GitHub for any repository), so an attacker does not need any secret information about the victim stack to reference its commits. The equality that should hold - "the organization/repository whose signature was verified" == "the repository/commit that the handler writes to" - does not hold: signature verification is keyed off one payload field (`repository.owner.login`/`organization.login`), while the actual write (`Commit.where(sha:)`) is keyed off a completely different, unchecked value (`sha`) with no cross-reference back to the authenticated organization or even to `repository.full_name`.

Note: `PushHandler` at least scopes to `stacks` derived from `repository.full_name` via `Handler#stacks`, [11](#0-10)  but this value is itself never cross-checked against the organization used for signature verification (`repository_owner`), so a signature validated for org A (e.g., one with no configured `webhook_secret`) does not guarantee the acted-upon `repository.full_name` genuinely belongs to org A.

### Impact Explanation
This is a cross-repository/cross-organization write: an unprivileged actor who can get *any* payload accepted (either because one configured organization has no `webhook_secret`, which the docs treat as a supported optional setting, or by legitimately triggering a webhook from an organization/repo they control) can forge a "success" `Status` for a commit belonging to a **different, unrelated stack's repository**, purely by referencing that commit's public SHA. Since deploy gating (`Deploy`/`Stack#trigger_task`/CI checks) relies on `Status`/`release_status` records associated with a commit, injecting a forged passing status can help an attacker manufacture green CI on a target repository's commit, undermining the CI-gating trust boundary the deploy pipeline relies on. This matches the "cross-repository writes" / unauthorized-deploy class of impact.

### Likelihood Explanation
Requires: (1) a multi-organization Shipit deployment (an explicitly supported, documented configuration) where at least one configured GitHub App organization has no `webhook_secret` set, or the attacker's own legitimately-owned org/repo webhook triggers a valid signature; and (2) knowledge of a target commit SHA, which is public GitHub data. No Shipit session, `ApiClient` token, or repository write access on the victim repo is required - only reachability of the public `/webhooks` endpoint. Likelihood is moderate: it depends on the multi-org/no-secret configuration existing, but that configuration is explicitly supported and documented rather than a documented misuse.

### Recommendation
Bind the entire trust chain to a single, verified identity end-to-end:
- After computing `repository_owner` for secret selection, re-derive and assert that every downstream identifier used by handlers (`repository.full_name`) is consistent with the same organization used to select the verification secret.
- In `StatusHandler#process` (and any other handler that mutates records), scope the lookup by the authenticated repository (e.g. `stacks.commits.where(sha: params.sha)`) rather than a bare, repository-agnostic `Commit.where(sha:)`.
- Do not treat a missing `webhook_secret` as an automatic bypass; require an explicit, admin-visible acknowledgment (or reject unsigned requests entirely) when multiple organizations are configured.

### Proof of Concept
1. Configure Shipit with two GitHub App organizations, `orgA` (no `webhook_secret`) and `orgB` (has a real stack with a real commit `abc123...`), mirroring `test/dummy/config/secrets_double_github_app.yml`.
2. As an unauthenticated attacker, `POST /webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": {"full_name": "orgA/some-repo", "owner": {"login": "orgA"}},
  "sha": "abc123...",
  "state": "success",
  "context": "ci/required-check",
  "description": "forged"
}
```
3. `verify_signature` resolves `repository_owner` to `orgA`, whose `webhook_secret` is unset, so `verify_webhook_signature` returns `true` unconditionally. [12](#0-11) 
4. `StatusHandler#process` matches `Commit.where(sha: "abc123...")`, which finds the commit belonging to `orgB`'s stack, and creates a `Status` record on it - despite the request never being authenticated for `orgB`. [2](#0-1)

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
