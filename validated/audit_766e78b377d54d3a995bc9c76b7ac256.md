### Title
Webhook signature verification keyed on attacker-chosen `repository.owner.login`, but repository actions performed on attacker-chosen `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification by reading `repository.owner.login` (or `organization.login`) straight out of the *unverified* JSON body, before the signature has been checked. `Shipit::Webhooks::Handlers::Handler#stacks` then separately resolves the target repository from `repository.full_name`, also read from the same unverified body. Nothing enforces that these two attacker-controlled fields agree, so the field used to pick the verification secret and the field used to select which repository gets acted upon are decoupled.

### Finding Description
`verify_signature` computes:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [1](#0-0) 
where `repository_owner` is taken from the raw JSON body:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

In `lib/shipit/github_app.rb`, `verify_webhook_signature` **bypasses verification entirely** when the selected organization's `webhook_secret` is not configured:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [3](#0-2) 

Shipit explicitly supports multi-organization configuration where different orgs can have different (or no) `webhook_secret` values, as shown in the double-app test fixture (`OrgTwo` has `webhook_secret: # nil`), and this is resolved via `Shipit.github_app_config`/`Shipit.github`: [4](#0-3) [5](#0-4) 

After (falsely) passing `verify_signature`, the handler dispatch uses a *different* field of the same body to decide which repository/stacks are affected:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [6](#0-5) 

Because `repository.owner.login` (used to pick the verification secret) and `repository.full_name` (used to pick the acted-upon repository) are two independent keys inside the same unauthenticated JSON body, an attacker can set them inconsistently: `owner.login` pointing at an organization with no `webhook_secret` configured (so `verify_webhook_signature` always returns `true`), while `full_name` points at a completely different, "secured" organization/repository whose stacks actually get mutated.

This is the structural analog of the reported bug class: the value that is checked/agreed upon (the organization whose secret validates the request) is not the value that is acted upon (the repository whose state is mutated) — exactly like the oracle-agreed-vs-oracle-used mismatch in the original report.

### Impact Explanation
Once `verify_signature` is spoofed this way, any of the webhook handlers execute unauthenticated, attacker-controlled writes against a legitimate, protected stack:
- `PushHandler#process` triggers `stack.sync_github(expected_head_sha: params.after)` for the forged branch/SHA on the real target stack [7](#0-6) 
- `StatusHandler#process` writes a forged commit status via `commit.create_status_from_github!(params)` for existing commits [8](#0-7) 
- `CheckSuiteHandler#process` forces `schedule_refresh_check_runs!` on arbitrary stack commits [9](#0-8) 

Forged commit statuses / check-run refresh can flip deployability checks used to gate deploys (`deployable_status`/merge gating), which can lead to an unauthorized deploy being unlocked on a protected repository — this satisfies the Critical "unauthorized deploy" bar, achieved purely by crafting an unauthenticated HTTP POST with no valid signature, no session, and no knowledge of any org's real `webhook_secret`.

### Likelihood Explanation
Requires only that the Shipit instance is configured with more than one GitHub organization/app where at least one configured organization has no `webhook_secret` set (an explicitly supported, documented configuration per `secrets_double_github_app.yml` and the multi-org code path in `Shipit.github`/`Shipit.github_app_config`). Given that, exploitation needs no credentials of any kind — just an HTTP POST to `/webhooks` with a crafted JSON body. Likelihood is high in any deployment that enables the multi-organization configuration with mixed secret settings.

### Recommendation
Verify the webhook signature using the secret associated with the *same* repository/organization that the handlers subsequently act on, not a value independently re-derived from the untrusted payload. Concretely:
- After resolving `repository_name` for handler dispatch, confirm that its owner matches the `repository_owner` value used to select the verifying `github_app`, rejecting the request otherwise.
- Do not allow `verify_webhook_signature` to return `true` unconditionally when `webhook_secret` is blank in a multi-organization setup; require every configured organization to have a non-blank secret, or fail closed instead of open.

### Proof of Concept
1. Configure Shipit with two organizations: `OrgSecure` (has a `webhook_secret`) and `OrgOpen` (no `webhook_secret`, as in the shipped `secrets_double_github_app.yml` fixture).
2. Attacker sends, with no auth/session and no valid `X-Hub-Signature`:
```
POST /webhooks
X-Github-Event: push
{
  "ref": "refs/heads/master",
  "after": "<attacker_chosen_sha>",
  "repository": {
    "owner": { "login": "OrgOpen" },
    "full_name": "OrgSecure/protected-repo"
  }
}
```
3. `repository_owner` resolves to `"OrgOpen"`, so `Shipit.github(organization: "OrgOpen").verify_webhook_signature` returns `true` unconditionally (blank secret) [10](#0-9) .
4. `verify_signature` passes and `PushHandler` is invoked with `payload.dig('repository','full_name') == "OrgSecure/protected-repo"`, causing `stack.sync_github` to run against the real, protected stack in `OrgSecure` — a repository the attacker never authenticated against [6](#0-5) [7](#0-6) .

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
