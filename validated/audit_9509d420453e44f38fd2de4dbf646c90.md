## Analysis

The external report's core invariant is: **a state list must be kept consistent with membership changes — removing an entity must purge its stale associated state, and re-adding must not silently resurrect old state.** The Solidity bug is about `poolArray` never being pruned or deduplicated.

Searching Aptos-native admission-adjacent code for the same class of bug (stale state not cleared on removal, silently resurrected on re-admission) in approval/authenticator contexts, the strongest local analog is in `multisig_account.move`'s owner/vote bookkeeping.

## Title
Stale votes are not purged when a multisig owner is removed, allowing silent resurrection of approval when the same address is re-added - (`File: aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
`MultisigTransaction.votes` is a `simple_map<address, bool>` that records each owner's vote for a pending transaction. When an owner votes, their address is inserted into this map [1](#0-0) . Quorum is computed by intersecting the **current owners list** with this votes map [2](#0-1) . `update_owner_schema`, which backs `add_owner(s)`, `remove_owner(s)`, and `swap_owner(s)`, mutates only the `owners` vector — it never touches any pending `MultisigTransaction.votes` map for any in-flight transaction [3](#0-2) .

### Finding Description
The framework does correctly exclude a removed owner's vote from the quorum count while that address is *not* in the owners list — this is verified by an explicit test, `test_validate_transaction_should_not_consider_removed_owners` [4](#0-3) . However, the exclusion is achieved purely by filtering `owners.for_each_ref` against the votes map — the vote itself is never deleted from `MultisigTransaction.votes`. If the same address is later re-added as an owner (e.g. via `swap_owner`, `add_owner`, or `swap_owners`) while the original transaction is still pending in the queue, `num_approvals_and_rejections_internal` will once again find that address's stale `true`/`false` entry in the votes map and count it toward quorum — with no new vote action performed by that owner [2](#0-1) .

This is the direct multisig analog of the `poolArray` bug: membership removal does not clean up the associated per-entity approval record, and re-admission silently reactivates the old, un-refreshed record instead of requiring a fresh affirmative action.

### Impact Explanation
This breaks the intended admission invariant that "quorum must reflect **current, deliberate** approvals from **current** owners." A concrete abuse scenario:
1. Owner A creates or approves a pending transaction (auto-vote on creation) [1](#0-0) .
2. Owner A is removed via governance (`remove_owner`/`swap_owner`) for any reason (suspected issue, temporary rotation, restructuring) — the pending transaction correctly loses A's vote from the quorum count at that moment.
3. Owner A's address is later re-added to the owner set (e.g., reinstated, or the address is reused as part of an ownership reshuffle) while the original transaction is still queued.
4. A's stale vote reappears in the quorum tally without A ever re-affirming it, potentially pushing an old/stale transaction over the `num_signatures_required` threshold and letting it execute based on approval history that no longer reflects the intent of the currently constituted owner set.

This is an approval-set confusion at the admission boundary of a privileged execution path (`validate_multisig_transaction` gates transaction execution on `can_be_executed`/`can_execute`, which call this same vote-counting logic) [5](#0-4) .

### Likelihood Explanation
Triggering this requires the multisig account itself to perform two governance actions (remove then re-add the same address) while a transaction is left pending in the queue — both are legitimate multisig-governed actions, not requiring any external attacker privilege. Because multisig owner churn (temporary removal/reinstatement, key-rotation-driven reshuffles, restructuring cap tables) is a normal, expected operational pattern, and the framework provides no warning or automatic vote-purge, this can be triggered inadvertently by legitimate administrators without realizing a stale vote will resurrect.

### Recommendation
When `update_owner_schema` removes an owner, iterate all pending `MultisigTransaction` entries in the queue and remove that owner's entry from each `votes` map (or otherwise invalidate it) so that re-adding the same address at a later time cannot resurrect a stale approval. Given the queue is generally small and bounded (`available_transaction_queue_capacity`), this should not introduce a materially different gas/DoS profile than existing owner-schema updates, but the implementation should still guard against unbounded queue sizes as called out in the original report's caution about gas.

### Proof of Concept
Extending the existing test `test_validate_transaction_should_not_consider_removed_owners` [4](#0-3) :
1. Owners `[1, 2, 3]`, 2-of-3 quorum.
2. Owner 1 creates transaction (auto-approves); owner 2 does not approve — quorum not met.
3. `remove_owners(multisig_signer, vector[owner_1_addr])` — quorum count now excludes owner 1 (as shown by the existing test).
4. `add_owner(multisig_signer, owner_1_addr)` (or `swap_owner` reinstating the same address) while the transaction from step 2 is still pending.
5. Call `num_approvals_and_rejections`/`can_be_executed` for that pending sequence number: owner 1's original stale vote is counted again, and if this pushes approvals to 2, the transaction becomes executable without owner 1 taking any new action after being reinstated.

**Note on verification limits:** I was unable to view the exact source lines of `vote`, `approve_transaction`, `reject_transaction`, and the `MultisigTransaction` struct definition in this session (the tool call for that specific range was cut off before results returned). The behavior of vote insertion/counting is confirmed indirectly through `add_transaction` (which inserts into `votes`) and `num_approvals_and_rejections_internal` (which counts by intersecting current owners with `votes`), plus the absence of any vote-map mutation in `update_owner_schema`. A Devin session with full file access would be needed to confirm there is no other cleanup path (e.g., inside `vote()` itself) that purges stale entries before finalizing this as a confirmed, unpatched issue.

    inline fun num_approvals_and_rejections_internal(owners: &vector<address>, transaction: &MultisigTransaction): (u64, u64) {
        let num_approvals = 0;
        let num_rejections = 0;

        let votes = &transaction.votes;
        owners.for_each_ref(|owner| {
            if (simple_map::contains_key(votes, owner)) {
                if (*simple_map::borrow(votes, owner)) {
                    num_approvals += 1;
                } else {
                    num_rejections += 1;
                };
            }
        });

        (num_approvals, num_rejections)
    }

    /// Add new owners, remove owners to remove, update signatures required.
    fun update_owner_schema(
        multisig_address: address,
        new_owners: vector<address>,
        owners_to_remove: vector<address>,
        optional_new_num_signatures_required: Option<u64>,
    ) {
        assert_multisig_account_exists(multisig_address);
        let multisig_account_ref_mut =
            borrow_global_mut<MultisigAccount>(multisig_address);
        // Verify no overlap between new owners and owners to remove.
        new_owners.for_each_ref(|new_owner_ref| {
            assert!(
                !vector::contains(&owners_to_remove, new_owner_ref),
                error::invalid_argument(EOWNERS_TO_REMOVE_NEW_OWNERS_OVERLAP)
            )
        });
        // If new owners provided, try to add them and emit an event.
        if (new_owners.length() > 0) {
            multisig_account_ref_mut.owners.append(new_owners);
            validate_owners(
                &multisig_account_ref_mut.owners,
                multisig_address
            );
            emit(AddOwners { multisig_account: multisig_address, owners_added: new_owners });
        };
        // If owners to remove provided, try to remove them.
        if (owners_to_remove.length() > 0) {
            let owners_ref_mut = &mut multisig_account_ref_mut.owners;
            let owners_removed = vector[];
            owners_to_remove.for_each_ref(|owner_to_remove_ref| {
                let (found, index) =
                    vector::index_of(owners_ref_mut, owner_to_remove_ref);
                if (found) {
                    vector::push_back(
                        &mut owners_removed,
                        vector::swap_remove(owners_ref_mut, index)
                    );
                }
            });
            // Only emit event if owner(s) actually removed.
            if (owners_removed.length() > 0) {
                emit(
                    RemoveOwners { multisig_account: multisig_address, owners_removed }
                );
            }
        };
