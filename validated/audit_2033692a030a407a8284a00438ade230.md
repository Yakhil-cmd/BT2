### Title
Webhook signature is verified against the organization named in `repository.owner.login`, but the event is applied to the repository named in `repository.full_name` — an attacker who controls one GitHub organization's webhook secret can inject fake commits/statuses into any other tracked repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects the `GithubApp` (and therefore the `webhook_secret`) used to validate the HMAC signature based on `repository.owner.login` (with a fallback to `organization.login`) taken from the raw JSON body. `Shipit::Webhooks::Handlers::Handler#stacks`, used by every actual event handler (e.g. `PushHandler`), instead resolves the target `Repository`/`Stack` using a *different* field of the same body: `repository.full_name`. Because the controller never checks that `repository.full_name` actually belongs to the organization whose secret validated the signature, these two fields can be set independently by whoever crafts the POST body.

### Finding Description
The webhooks endpoint is unauthenticated by design (`ActionController::Base`, no session/API-key check) — the sole gate is the HMAC signature: [1](#0-0) 

The organization (and thus which `webhook_secret` is used to compute the expected HMAC) is derived purely from the payload: [2](#0-1) 

`GithubApp#verify_webhook_signature` only proves the raw body was signed by *some* organization's known secret — it says nothing about which repository the body's other fields describe: [3](#0-2) 

Once the signature check passes, `WebhooksController#create` dispatches to handlers based purely on the event type, and each handler resolves its target stacks with `Handler#stacks`, which reads a *different* JSON field, `repository.full_name`, not `repository.owner.login`: [4](#0-3) 

For example `PushHandler` uses this to look up and update stacks/commits for whatever repository `repository.full_name` names: [5](#0-4) 

Because `repository.owner.login` (used to pick the signing secret) and `repository.full_name` (used to pick the write target) are two independent fields of the attacker-supplied JSON body, and only the HMAC of the *entire raw body* is verified — not any semantic binding between these two fields — anyone who knows (or controls) the `webhook_secret` for **any one** GitHub organization configured in Shipit (`config/secrets*.yml` `github.<org>.webhook_secret`) can craft a validly-signed payload where:
- `repository.owner.login` = "OrgA" (their own org, whose secret they know, so the HMAC computed with OrgA's secret verifies)
- `repository.full_name` = "OrgB/some-other-tracked-repo" (a completely unrelated repository/organization tracked by the same Shipit instance)

This breaks the binding: "the organization that authenticated" (OrgA, via its webhook secret) is not equal to "the repository that is written" (OrgB/some-other-repo, via `repository.full_name`).

### Impact Explanation
With a forged but validly-signed payload, an attacker with only one organization's webhook secret can drive `PushHandler`, the `status`/`check_suite` handlers, and pull-request handlers against a completely unrelated stack. This can be used to inject fabricated commits (`stack.sync_github`), fabricate passing CI statuses/check-runs for a commit, or fabricate merged/pull-request state — all of which can feed directly into `continuous_deployment` (`Stack.schedule_continuous_delivery`) or the merge queue (`MergeRequest#all_status_checks_passed?`), resulting in an unauthorized deploy/merge of a repository the attacker does not control. This matches the Critical-severity bucket ("unauthorized deploy, rollback or merge") defined in scope.

### Likelihood Explanation
Exploitation requires only knowledge of one organization's `webhook_secret` configured on the same Shipit instance — not repository write access, not a Shipit session, and not an `ApiClient` token. Any tenant/organization admin who legitimately holds their own org's webhook secret (a routine credential, not a privileged Shipit credential) can attack every other organization/stack tracked by the same Shipit deployment. This is a realistic scenario in any multi-organization Shipit installation, which is the deployment model the engine explicitly supports (`config/secrets*.yml` shows multiple orgs each with independent `webhook_secret`).

### Recommendation
After signature verification succeeds, cross-validate that the organization whose secret validated the signature actually owns the repository being acted upon — e.g. verify that `repository.owner.login` (or `organization.login`) equals the owner segment of `repository.full_name` before dispatching to any handler, and reject the webhook otherwise.

### Proof of Concept
1. Configure Shipit with two organizations, `orga` and `orgb`, each with distinct `webhook_secret`s, both tracking stacks (`config/secrets.yml`).
2. As an attacker who only knows `orga`'s `webhook_secret` (e.g. an org admin of `orga`), craft a JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "orga" },
    "full_name": "orgb/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(orga_webhook_secret, body)>` and POST it to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` = `"orga"`, fetches `orga`'s `GithubApp`, and the signature validates successfully (`app/controllers/shipit/webhooks_controller.rb:24-30,59-62`).
5. `PushHandler#process` runs `stacks` which resolves via `Repository.from_github_repo_name("orgb/victim-repo")` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`, `app/models/shipit/webhooks/handlers/push_handler.rb:12-17`), causing `orgb`'s stack to sync to the attacker-chosen `after` sha — despite the attacker never having proven any relationship to `orgb`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
