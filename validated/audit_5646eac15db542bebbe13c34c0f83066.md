## Title
Unbounded `handleAATriggers` processing during MCI stabilization can block the node's write pipeline as the number of AAs/triggers grows - (File: aa_composer.js, main_chain.js, writer.js)

### Summary
The reported bug class is that a settlement function that iterates over *all* markets in a single call will grow linearly with the number of markets/activity and eventually exceed a hard resource limit (block gas), causing a DoS that prevents anyone from calling it. The analogous unbounded-loop-over-a-growing-set pattern exists in ocore's AA trigger execution pipeline: every time a main-chain index (MCI) stabilizes, `markMcIndexStable()`'s inner `handleAATriggers()` collects **every** AA address that received a payment in that MCI (no batching/paging, no per-call limit) and `aa_composer.handleAATriggers()` then processes all of them synchronously, one after another, **inside the critical unit-write/stabilization pipeline**, before the node can move on to process/accept further units.

### Finding Description
In `main_chain.js`, `markMcIndexStable()` builds the set of AA triggers for a stabilized MCI with a single unbounded query: [1](#0-0) 

This selects *every* distinct `(address, unit)` pair with an output to an AA address in the MCI being stabilized, with no cap on `rows.length`, and inserts them all into `aa_triggers` for later processing.

That processing happens in `aa_composer.js`'s `handleAATriggers()`, which loads **all outstanding** `aa_triggers` rows (not scoped to a single MCI, but potentially accumulated across MCIs if execution ever falls behind) and processes them strictly sequentially via `async.eachSeries`, each one going through `handlePrimaryAATrigger` (its own DB transaction, full formula evaluation, balance updates, batch write, etc.): [2](#0-1) [3](#0-2) 

Critically, this whole sequential pipeline is `await`-ed synchronously inside `writer.js`'s `saveJoint()` commit path, before the write lock is released and the caller is told the unit is done: [4](#0-3) 

and it is also invoked in a `while(true)` loop that keeps trying to stabilize and trigger further MCIs before returning control: [5](#0-4) 

There is no per-call, per-MCI, or per-address cap analogous to a gas limit anywhere in this chain — unlike formula evaluation itself, which is bounded by `MAX_COMPLEXITY`/`MAX_OPS` per single AA invocation (`definition.js` lines 104-111, 621-638), the *number* of AA triggers processed synchronously in one stabilization event is unbounded and grows with the number of active AAs/payments included in a single MCI, exactly mirroring the `settleFunding`/"loop over all markets" pattern from the report (loop count scales with ecosystem growth and activity, each iteration doing non-trivial, DB-bound, formula-evaluation work analogous to `_calcTwap`).

### Impact Explanation
Because `handleAATriggers()` runs synchronously as part of the mainstream unit-write/stabilization critical section (holding the `aa_triggers` mutex and blocking the corresponding `writer.js` write completion/unlock), a large batch of triggers stabilizing in one MCI (e.g., many popular AAs all receiving payments in units that land in the same MCI, which becomes more likely as the number of deployed AAs and network activity grows) can make this synchronous step take a very long time. Since new unit processing/finalization is serialized behind this step, this can starve or significantly delay a node's ability to validate/accept/confirm subsequent units, which is a "network unable to confirm new units" style impact — the DAG-native analog of exceeding a block gas limit.

### Likelihood Explanation
This does not require a malicious actor: it is a direct consequence of ordinary ecosystem growth, exactly as acknowledged in the original report ("It's a known issue that adding many more markets will eventually exceed block gas limit... DAO governance has to be careful"). Any single poster who sends payments to many AA addresses within one unit, or many independent users whose payment units happen to land in the same stabilizing MCI, increases the size of the `aa_triggers` batch that must be processed synchronously and sequentially with no ability to defer, paginate, or parallelize beyond the current DB-connection-per-trigger model.

### Recommendation
- Cap or paginate the number of AA triggers processed per stabilization event, and/or move `aa_composer.handleAATriggers()` off the critical write path (fully asynchronous background processing) so growth in trigger volume cannot block acceptance of new units.
- Consider limiting the number of distinct AA-address triggers a single unit/MCI can create (similar in spirit to `MAX_MESSAGES_PER_UNIT`), and processing triggers in bounded batches with yields back to the event loop / unlocking the write path between batches.

### Proof of Concept
1. Deploy or observe growth in the number of active AAs on the network (or have many users pay AA addresses within units that end up in the same MCI).
2. When that MCI stabilizes, `markMcIndexStable()` (main_chain.js:1691-1723) selects all matching `(unit, address)` pairs with no limit and inserts them into `aa_triggers`.
3. `writer.js` awaits `aa_composer.handleAATriggers()` (writer.js:724-759), which sequentially processes every row via `async.eachSeries` (aa_composer.js:59-89), each doing a full DB transaction + formula evaluation (aa_composer.js:91-150).
4. As the trigger count grows (proportional to AA/network adoption, exactly as markets grew in the referenced report), this synchronous step's duration grows unbounded, delaying the write-path unlock and the node's ability to move on to further units.

function handleAATriggers(onDone) {
	if (!onDone)
		return new Promise(resolve => handleAATriggers(resolve));
	mutex.lock(['aa_triggers'], function (unlock) {
		db.query(
			"SELECT aa_triggers.mci, aa_triggers.unit, address, definition \n\
			FROM aa_triggers \n\
			CROSS JOIN units USING(unit) \n\
			CROSS JOIN aa_addresses USING(address) \n\
			ORDER BY aa_triggers.mci, level, aa_triggers.unit, address",
			function (rows) {
				var arrPostedUnits = [];
				async.eachSeries(
					rows,
					function (row, cb) {
						console.log('handleAATriggers', row.unit, row.mci, row.address);
						var arrDefinition = JSON.parse(row.definition);
						handlePrimaryAATrigger(row.mci, row.unit, row.address, arrDefinition, arrPostedUnits, cb);
					},
					function () {
						arrPostedUnits.forEach(function (objUnit) {
							eventBus.emit('new_aa_unit', objUnit);
						});
						unlock();
						onDone();
					}
				);
			}
		);
	});
}

function handlePrimaryAATrigger(mci, unit, address, arrDefinition, arrPostedUnits, onDone) {
	db.takeConnectionFromPool(function (conn) {
		conn.query("BEGIN", function () {
			var batch = kvstore.batch();
			readMcUnit(conn, mci, function (objMcUnit) {
				readUnit(conn, unit, function (objUnit) {
					var arrResponses = [];
					var trigger = getTrigger(objUnit, address);
					trigger.initial_address = trigger.address;
					trigger.initial_unit = trigger.unit;
					handleTrigger(conn, batch, trigger, {}, {}, arrDefinition, address, mci, objMcUnit, false, arrResponses, function(){
						conn.query("DELETE FROM aa_triggers WHERE mci=? AND unit=? AND address=?", [mci, unit, address], async function(){
							await conn.query("UPDATE units SET count_aa_responses=IFNULL(count_aa_responses, 0)+? WHERE unit=?", [arrResponses.length, unit]);
							let objUnitProps = storage.assocStableUnits[unit];
							if (!objUnitProps)
								throw Error(`handlePrimaryAATrigger: unit ${unit} not found in cache`);
							if (!objUnitProps.count_aa_responses)
								objUnitProps.count_aa_responses = 0;
							objUnitProps.count_aa_responses += arrResponses.length;
							var batch_start_time = Date.now();
							batch.write({ sync: true }, function(err){
								console.log("AA batch write took "+(Date.now()-batch_start_time)+'ms');
								if (err)
									throw Error("AA composer: batch write failed: "+err);
								conn.query("COMMIT", function () {
									conn.release();
									if (arrResponses.length > 1) {
										// copy updatedStateVars to all responses
										if (arrResponses[0].updatedStateVars)
											for (var i = 1; i < arrResponses.length; i++)
												arrResponses[i].updatedStateVars = arrResponses[0].updatedStateVars;
										// merge all changes of balances if the same AA was called more than once
										let assocBalances = {};
										for (let { aa_address, balances } of arrResponses)
											assocBalances[aa_address] = balances; // overwrite if repeated
										for (let r of arrResponses) {
											r.balances = assocBalances[r.aa_address];
											r.allBalances = assocBalances;
										}
									}
									else
										arrResponses[0].allBalances = { [address]: arrResponses[0].balances };
									arrResponses.forEach(function (objAAResponse) {
										if (objAAResponse.objResponseUnit)
											arrPostedUnits.push(objAAResponse.objResponseUnit);
										eventBus.emit('aa_response', objAAResponse);
										eventBus.emit('aa_response_to_unit-'+objAAResponse.trigger_unit, objAAResponse);
										eventBus.emit('aa_response_to_address-'+objAAResponse.trigger_address, objAAResponse);
										eventBus.emit('aa_response_from_aa-'+objAAResponse.aa_address, objAAResponse);
									});
									onDone();
								});
							});
						});
					});
				});
			});
		});
	});
}
