### Title
Unauthenticated cross-tenant CI status forgery via global `Commit.where(sha:)` scan in `StatusHandler#process` unblocks victim deploys - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits solely by `sha` with no scoping to the organization/repository that signed the webhook, so a `status` event validly signed by an attacker-controlled GitHub organization (org A) can flip the `simple_state` and trigger `stack.schedule_merges` for a commit that actually belongs to an unrelated victim stack/org (org B), as long as the two share a commit sha and the attacker guesses/knows a blocking status `context`.

### Finding Description
The broken binding: `verify_signature` proves only that `repository_owner ∈ params['repository']['owner']['login']` (attacker-supplied, from the raw JSON body they crafted) is a Shipit-known org whose `webhook_secret` signed this specific `raw_post` — it says nothing about which `Commit`/`Stack` rows the payload's `sha` is allowed to touch. `StatusHandler#process` should require `commit.stack.repository == request-authenticated repository`, but it does not:

```
app/models/shipit/webhooks/handlers/status_handler.rb:20-24
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

Verification flow: `WebhooksController#verify_signature` derives `repository_owner` from the attacker-controlled payload itself and fetches `Shipit.github(organization: repository_owner)`, then checks `verify_webhook_signature` against that org's `webhook_secret`: [2](#0-1) [3](#0-2) 

`verify_webhook_signature` only checks the HMAC against the org named in the payload — an attacker who registers/controls org A in Shipit (and thus knows org A's own `webhook_secret`, since it's their own GitHub org) can produce a fully valid signature for any JSON body they want, including one whose top-level `sha`/`context`/`state` fields target a completely different (victim) commit: [4](#0-3) 

Because `Handler#call` dispatches to `StatusHandler#process` with `params` parsed only via the `ExplicitParameters` schema (`sha`, `state`, `context`, etc., with no `repository`/`stack` constraint), and `Commit.where(sha:)` is a global, unscoped lookup across every `Stack` in the installation, the forged status is attached to whichever real `Commit` row(s) share that sha — regardless of which org/stack they belong to.

`Commit#create_status_from_github!` → `add_status` then compares `previous_status.simple_state` to `new_status.simple_state`; if the forged `state: success` flips it, `stack.schedule_merges` is invoked for the **victim's** `stack`: [5](#0-4) 

This can also make `commit.deployable?` true (`success? && !blocked?`), which gates `Deploy` creation via `schedule_continuous_delivery`/manual deploy flows: [6](#0-5) 

No other guard intervenes: `drop_unhandled_event` only checks that a handler is registered for the `status` event type, `ExplicitParameters` only validates field types/presence, and there is no `stacks`/repository-ownership filter comparable to what other handlers (e.g. `PushHandler`, `CheckSuiteHandler`) apply via `Handler#stacks`.

### Impact Explanation
An attacker who controls any Shipit-registered GitHub organization (including a throwaway one they register themselves) can forge a `status` webhook that is fully authenticated for their own org, but whose effect lands on an arbitrary victim `Stack`'s `Commit` (matched only by shared `sha`, which is public GitHub data, and a guessable `context` name from the victim's public CI config). This can flip a victim commit's `simple_state`, invoke `stack.schedule_merges`, and make `deployable?` true — an unauthorized-merge/deploy-enablement primitive that crosses tenant boundaries entirely through the attacker's own, unrelated organization's credentials. This matches the "payload for one repository mutating another's stack/commit" and "unauthorized deploy/merge" Critical impact categories. It is repeatable against any stack/commit whose sha and blocking-context name the attacker can determine, and is not limited to a single victim.

### Likelihood Explanation
Preconditions: (1) attacker registers or otherwise controls a GitHub organization known to this Shipit instance (or one whose `webhook_secret` is unset — see the related secret-less-org bypass — either way giving them a valid signature over an arbitrary body); (2) attacker knows a victim commit sha (trivially public on GitHub) and a blocking status `context` string used by the victim's stack (visible in the victim's public CI config/`shipit.yml`). Both are low-cost/no-privilege reconnaissance. Given these, forging the POST is a single unauthenticated HTTP request with a correctly computed HMAC using a secret the attacker legitimately possesses for their own org — fully within the declared unprivileged-attacker capability set. This is feasible and repeatable at will.

### Recommendation
Scope `StatusHandler#process` (and any other sha-keyed handler) to only the commits belonging to stacks whose repository matches the authenticated `repository_owner`/`repository.full_name` from the verified payload — e.g. join through `Stack` and filter `Commit.joins(:stack).merge(Stack.where(repository: ...)).where(sha: params.sha)` — mirroring the `Handler#stacks`-based scoping used by other handlers, rather than a bare global `Commit.where(sha:)`.

### Proof of Concept
Minitest plan (`test/models/webhooks/status_handler_test.rb` or controller-level `test/controllers/webhooks_controller_test.rb`):
1. Create org/stack A with repository `attacker/repo`, a `Commit` with `sha: SHA` (attacker's own, or a duplicate of victim's sha), and register a valid `webhook_secret` for org A.
2. Create org/stack B (victim) with repository `victim/repo`, blocking status context `"ci/travis"`, and a `Commit` with the same `sha: SHA`, initial state pending/unknown.
3. Build a `status` webhook JSON body with `repository.owner.login = "attacker"`, `sha: SHA`, `state: "success"`, `context: "ci/travis"`.
4. Compute `X-Hub-Signature` using org A's real `webhook_secret`.
5. POST to `/webhooks` with `X-Github-Event: status` and that signature.
6. Assert response is `200`/`:ok` (signature accepted for org A).
7. Assert **both** commits (`stack_a`'s and `stack_b`'s, matching `SHA`) now have `status.state == 'success'` — proving `Commit.where(sha:)` matched org B's row despite the request being authenticated only for org A.
8. Assert `stack_b.reload` triggered `schedule_merges` (e.g. assert `ProcessMergeRequestsJob` enqueued for `stack_b`, or that `stack_b`'s merge-eligible commit's `deployable?` becomes `true`), demonstrating cross-tenant unauthorized deploy/merge enablement.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
