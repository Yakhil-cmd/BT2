### Title
Webhook signature verified against `repository.owner.login`'s org while `PushHandler` mutates the stack resolved from `repository.full_name` - cross-tenant forged push (`app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects the `GitHubApp`/secret used to verify a webhook's HMAC using `repository.owner.login`, but `Shipit::Webhooks::Handlers::Handler#stacks` resolves the repository/stack to mutate using the entirely separate `repository.full_name` field of the same payload. Because these two fields are never checked for consistency, an attacker who names an org configured in Shipit without a `webhook_secret` in `repository.owner.login`, while pointing `repository.full_name` at a victim org/repo, can get `verify_signature` to pass trivially and have `PushHandler` sync the victim's real stack. The `review_stacks_enabled`/provisioning-precedence angle in the question does not apply to this path, since `PushHandler` operates on `Repository#stacks` (ordinary stacks), not `review_stacks`, and never reads `review_stacks_enabled`.

### Finding Description
The broken binding: `verify_signature` implicitly assumes
`params.dig('repository','owner','login') == owner(params.dig('repository','full_name'))`,
but this equality is never enforced.

- `WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository','owner','login')` and uses it to pick the signing org/secret: [1](#0-0) [2](#0-1) 
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when that org's config has no `webhook_secret` set: [3](#0-2) 
- Once "verified", `WebhooksController#create` dispatches the *raw, unmodified* JSON payload to the handler: [4](#0-3) 
- `Handler#stacks`/`#repository_name` resolve the target `Repository` from `payload.dig('repository', 'full_name')`, a completely different field than the one used for signature routing: [5](#0-4) 
- `PushHandler#process` then syncs every non-archived stack of that resolved repository matching `branch` and calls `stack.sync_github(expected_head_sha: params.after)`, which appends commits/drives GitHub sync for the deploy pipeline: [6](#0-5) 

Exploit flow: attacker sends `POST /webhooks` with header `X-Github-Event: push`, a garbage/empty `X-Hub-Signature`, and a body where `repository.owner.login` = some org configured in Shipit's multi-org GitHub config but lacking a `webhook_secret` (a legitimate config the app supports, per `docs/setup.md`'s "Using Multiple Github Applications" section), while `repository.full_name` = `victim-org/victim-repo`. `verify_signature` calls `Shipit.github(organization: 'no-secret-org')`, which is a distinct, cached `GitHubApp` instance from the victim org's app; `verify_webhook_signature` short-circuits to `true` since that org has no secret. The request proceeds to `PushHandler`, which resolves the stack via `full_name` and calls `sync_github` on the real victim stack/branch with attacker-chosen `after` SHA.

This is a genuine architectural gap: nothing in `drop_unhandled_event`, `ExplicitParameters` schema (`PushHandler` only requires `ref`/`after`, not repository identity), or `Repository.from_github_repo_name` cross-checks that the signing org matches the resolved repository's owner.

The `review_stacks_enabled false` / "provisioning precedence bug" premise in the question does **not** hold for this handler: `PushHandler` never reads `review_stacks_enabled`, and operates purely on `Repository#stacks` (regular stacks), not `Repository#review_stacks`. [7](#0-6)  That aspect of the combined question is a red herring for this specific handler/entrypoint — it is relevant to `PullRequest::LabeledHandler`/`OpenedHandler`, not `PushHandler`.

### Impact Explanation
An attacker who knows (or can enumerate, since org names appear in URLs) the name of any Shipit-configured GitHub organization that lacks a `webhook_secret` can forge `push` events that are routed and processed as if they came from a completely different organization's repository. This lets an unauthenticated party trigger `Stack#sync_github` on a victim repository's stack with an attacker-chosen `expected_head_sha`, which drives commit ingestion and can seed continuous-delivery pipelines (a payload for one repository mutating another's stack/commit state) — matching the "Critical: a payload for one repository mutating another's stack" category. Repeatable against any repository/stack whose owning org is configured in Shipit, as long as some other configured org lacks a secret.

### Likelihood Explanation
This requires a specific operator misconfiguration precondition: Shipit must be configured with multiple GitHub organizations (per the documented multi-org config) where at least one configured org has no `webhook_secret` set. Given that default single-org Shipit setups typically configure a `webhook_secret`, and this bug is only exploitable in the specific multi-org-with-one-secretless-org configuration, likelihood depends heavily on deployment config rather than being universally exploitable. Where present, attacker cost is a single unauthenticated HTTP POST, fully repeatable.

### Recommendation
In `Handler#stacks`/`#repository_name`, and in `WebhooksController#verify_signature`, enforce that the org used to select/verify the webhook secret is the same org that owns the repository the handler will mutate — e.g., verify signature against `Shipit.github(organization: owner_of(payload.dig('repository','full_name')))` instead of `repository.owner.login`, or reject payloads where these two disagree. Additionally, consider disallowing `webhook_secret`-less org configs, or require explicit opt-in per org.

### Proof of Concept
```ruby
test "push event with mismatched repository.owner.login and repository.full_name syncs victim stack" do
  # no-secret-org has no webhook_secret configured; victim-org/victim-repo does
  Shipit.stubs(:secrets).returns(dummy_secrets_with(
    "no-secret-org" => { app_id: 1, installation_id: 1, private_key: TEST_KEY }, # no webhook_secret
    "victim-org" => { app_id: 2, installation_id: 2, private_key: TEST_KEY, webhook_secret: "victim-secret" }
  ))

  victim_repo = shipit_repositories(:victim) # owner: "victim-org", name: "victim-repo"
  victim_stack = shipit_stacks(:victim_stack) # branch "master", repository: victim_repo

  payload = {
    ref: "refs/heads/master",
    after: "deadbeef" * 5,
    repository: { owner: { login: "no-secret-org" }, full_name: "victim-org/victim-repo" }
  }.to_json

  @request.headers["X-Github-Event"] = "push"
  @request.headers["X-Hub-Signature"] = "sha1=bogus" # attacker doesn't know victim-org's secret

  # equality claimed broken: signing org ("no-secret-org") != owner of full_name ("victim-org")
  assert_not_equal "no-secret-org", "victim-org"

  Stack.any_instance.expects(:sync_github).with(expected_head_sha: "deadbeef" * 5)

  post :create, body: payload, as: :json
  assert_response :ok # signature check passed despite bogus signature and wrong org
end
```
This demonstrates `verify_signature` passing for a repository it was never authorized to speak for, and `PushHandler` mutating the victim stack.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
