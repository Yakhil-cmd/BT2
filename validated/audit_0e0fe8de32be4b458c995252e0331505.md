### Title
Unvalidated Arbstore URL from Hub Used for Outbound HTTP Requests Enables SSRF/Network Pivot - ([File: arbiters.js], [File: arbiter_contract.js])

### Summary
Similar to the java-client `directConnect` issue where a server-supplied host/port was blindly used to redirect all further session traffic, ocore's arbiter-contract subsystem fetches an "arbstore URL" via `device.requestFromHub("hub/get_arbstore_url", ...)` and then immediately performs outbound HTTP(S) requests to that URL with no host/IP validation, allowlist, or denylist.

### Finding Description
In `arbiters.js`, `getInfo()` and `getArbstoreInfo()` request a URL from the hub for a given `arbiter_address` and only check that it is a non-empty string before using it: [1](#0-0) [2](#0-1) 

The URL is then passed straight into `requestInfoFromArbStore()`, which performs an HTTPS GET with no host/IP checks: [3](#0-2) 

In `arbiter_contract.js`, the same pattern repeats for `openDispute()`, `appeal()`, and `getAppealFee()` — each fetches a URL from the hub via `hub/get_arbstore_url`/`hub/get_arbstore_url_by_address` and then POSTs encrypted contract/dispute data to it via `httpRequest()`, which builds the request target directly from the untrusted `host` string with `url.parse(host)` and no validation whatsoever: [4](#0-3) [5](#0-4) [6](#0-5) 

The `arbiter_address` field that drives this lookup originates from the arbiter-contract offer itself (`objContract.arbiter_address`), which is set by whichever party creates/proposes the contract and stored via `createAndSend()`/`store()`: [7](#0-6) [8](#0-7) 

Registering as an arbiter/arbstore with a hub is a normal, unprivileged network feature — any actor can become an "arbiter" and have their claimed arbstore URL served back by the hub for that address. Just as the java-client trusted `directConnectHost`/`directConnectPort` from the NEW_SESSION response without validating the destination, ocore trusts the `url` returned by `hub/get_arbstore_url` without validating the destination host, port, or scheme target (beyond the `https` module always being used). No check exists to block loopback, RFC-1918, or link-local addresses (e.g., `169.254.169.254`).

### Impact Explanation
A counterparty in a private arbiter contract can nominate an arbiter address whose associated arbstore URL points at an internal/loopback address or attacker infrastructure. When the victim wallet later calls `openDispute`, `appeal`, or `getAppealFee` (all normal, user/peer-triggerable actions in the contract lifecycle), the client will silently issue outbound HTTP requests — carrying encrypted contract details and dispute metadata — to that attacker-chosen destination. This is a Server-Side-Request-Forgery-like network pivot from the victim's own client process, potentially reaching internal services, cloud metadata endpoints, or attacker-controlled listeners, and exfiltrating the peer's contact/contract payload once decrypted keys are involved. It does not by itself cause double-spend or unit-validation disagreement, but it does expose sensitive off-chain contract data and internal network reachability triggered purely by an unprivileged private-payment counterparty choosing an arbiter/arbstore registration.

### Likelihood Explanation
Reaching this path only requires becoming a correspondent, proposing/accepting an arbiter contract naming an attacker-controlled or attacker-influenced `arbiter_address`, and having the victim invoke the dispute/appeal flow — all standard, unprivileged wallet operations with no special hub cooperation beyond the hub relaying arbstore registration metadata that anyone can create. No malicious-hub or malicious-node behavior is required; the hub is functioning as designed by returning whatever URL was registered for that address.

### Recommendation
Validate the `url` returned by `hub/get_arbstore_url`/`hub/get_arbstore_url_by_address` before use: enforce an allowlist of known/approved arbstore hosts, or at minimum resolve and reject loopback, RFC-1918, and link-local (including `169.254.169.254`) destinations in `arbiters.js` (`getInfo`, `getArbstoreInfo`, `requestInfoFromArbStore`) and `arbiter_contract.js` (`httpRequest`, `getArbstoreAddresses`, `openDispute`, `appeal`, `getAppealFee`) before issuing any outbound request.

### Proof of Concept
1. Attacker registers as an arbiter with the shared hub and sets their arbstore URL to `https://169.254.169.254/` (or an internal RFC-1918 address) via the standard arbstore registration mechanism reachable through `hub/get_arbstore_url`.
2. Attacker proposes an arbiter contract to victim naming themselves (or a colluding party) as `arbiter_address`, via `arbiter_contract.js:createAndSend` / `store`.
3. Victim accepts the contract and later disputes it: `arbiter_contract.js:openDispute(hash, cb)` calls `device.requestFromHub("hub/get_arbstore_url", objContract.arbiter_address, ...)`, receives the attacker-controlled URL unchecked, and `httpRequest(url, "/api/dispute/new", dataJSON, cb)` sends the victim's encrypted contract payload to that internal/attacker address — reproducing the same "server tells client where to send subsequent traffic, client obeys with no validation" pattern as CVE-2026-43910. 	http.get(url, function(resp){
		var data = '';
		resp.on('data', function(chunk){
			data += chunk;

			try {
				cb(null, JSON.parse(data));

				cb(ex);
			}
		});
	}).on("error", cb);

function httpRequest(host, path, data, cb) {
	var reqParams = Object.assign(url.parse(host),
		{
			path: path,
			method: "POST",
			headers: {
				"Content-Type": "application/json",
				"Content-Length": (new TextEncoder().encode(data)).length
			}
		}
	);
	var req = http.request(
		reqParams,
		function(resp){
			var data = "";
			resp.on("data", function(chunk){
				data += chunk;
			});
			resp.on("end", function(){
				try {
					data = JSON.parse(data);
					if (data.error) {
						return cb(data.error);
					}
					cb(null, data);
				} catch (e) {
					cb(e);
				}
			});
		}).on("error", cb);
	req.write(data);
	req.end();
}
