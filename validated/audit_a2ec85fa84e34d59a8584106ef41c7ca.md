### Title
Cross-tenant webhook forgery: signature verified against attacker's own organization's secret while the handler acts on an unrelated organization's repository/commit - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate a webhook against using an attacker-controlled field from the *same, unauthenticated* JSON body (`repository.owner.login` / `organization.login`), and only after that does it verify the raw body against that self-selected secret. The event handlers that subsequently act on the payload (writing commits, statuses, syncing stacks, matching pull requests) key off a *different*, independently-controlled field of the same body — `repository.full_name` (and even a global, repo-unscoped `sha` lookup in the status handler). In a multi-tenant deployment (explicitly documented and supported via the multi-org `github:` secrets schema, see `docs/setup.md` "Using Multiple Github Applications" and `test/dummy/config/secrets_double_github_app.yml`), an operator/administrator of one tenant organization who legitimately knows their own `webhook_secret` can forge a webhook whose HMAC is valid for their own organization while its `repository.full_name`/`sha` target a *different* tenant's repository or commit.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` does: [1](#0-0) 

`repository_owner` is read straight out of the untrusted request body: [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the per-organization `GitHubApp` (and its dedicated `webhook_secret`) purely from that attacker-supplied string: [3](#0-2) 

Multiple, independently-secreted organizations sharing one Shipit instance is a first-class, documented configuration: [4](#0-3) 

Once `verify_signature` passes (because it was checked against the secret of the organization *named in the payload*, which the attacker controls and, for their own tenant, legitimately knows), `WebhooksController#create` dispatches to handlers using the raw parsed JSON: [5](#0-4) 

Handlers resolve the target `Repository`/`Stack` from `repository.full_name` — a field never cross-checked against `repository_owner`: [6](#0-5) 

`PushHandler` then syncs the resolved stack from the (attacker-controlled) `after` sha: [7](#0-6) 

`StatusHandler` is worse: it doesn't even scope by repository — it matches **any** `Commit` row across the whole installation by `sha` and attaches an attacker-chosen CI status to it: [8](#0-7) 

That status directly feeds `MergeRequest#all_status_checks_passed?`, which is the exact gate `ProcessMergeRequestsJob` uses to decide whether to call `merge_request.merge!` (which invokes `stack.github_api.merge_pull_request`): [9](#0-8) [10](#0-9) 

**Binding that should hold but doesn't:**
`organization whose secret validated the HMAC` == `organization owning the repository/commit the handler writes to`.

Before: GitHub itself only ever produces a signature over a payload whose `repository.owner.login`/`organization.login` and `repository.full_name` are consistent (both describe the same real repository), so the binding holds implicitly.
After the attacker's forged request: the attacker sets `repository.owner.login = "TenantA"` (their own org, whose `webhook_secret` they know because they provisioned/administer TenantA's GitHub App) and signs the body with TenantA's secret, while setting `repository.full_name = "TenantB/critical-repo"` and/or an arbitrary `sha` belonging to TenantB. `verify_signature` succeeds (TenantA's secret matches TenantA's signature), but the handler acts on TenantB's stack/commit. The equality above is broken, and nothing in the code re-establishes it.

### Impact Explanation
This lets an attacker who only controls one tenant in a multi-org Shipit deployment forge webhooks that write into another tenant's stacks:
- Trigger `GithubSyncJob`/`stack.sync_github` and pull-request handlers for a repository they do not own.
- Most critically, inject a forged `success` CI status (`StatusHandler`) onto any commit by `sha` regardless of repository, satisfying `MergeRequest#all_status_checks_passed?` for another tenant's pull request and causing `ProcessMergeRequestsJob` to call `merge_pull_request` on GitHub using that tenant's `GITHUB_TOKEN`/GitHub App credentials — an unauthorized merge into a repository the attacker has no legitimate access to.

This matches the required Critical impact bucket: an unauthorized merge/deploy triggered via cross-repository writes, achieved purely by an unprivileged (from the victim tenant's perspective) attacker who only holds credentials for their own, unrelated tenant.

### Likelihood Explanation
Requires: (1) a Shipit deployment configured for multiple GitHub organizations (an explicitly documented, supported configuration), and (2) the attacker to be an administrator/operator of one of those tenant organizations (i.e., knows their own org's `webhook_secret`, which they configured themselves when setting up their GitHub App). No access to the victim tenant's secret, GitHub App, or Shipit account is needed. This is a realistic multi-tenant SaaS-style deployment threat.

### Recommendation
- After signature verification succeeds, re-derive the organization strictly from the resolved `Repository`/`Stack` record (never from unauthenticated payload fields) and reject the webhook if `repository.owner.login`/`organization.login` does not match the owner of the `Repository` matched by `repository.full_name`.
- Scope `StatusHandler`'s `Commit.where(sha: params.sha)` lookup to commits belonging to stacks under the verified organization only, rather than a global, repo-unscoped lookup.
- Consider binding each `GithubHook`/organization's webhook secret to the specific installation/organization id returned by GitHub (rather than a client-suppliable string) so the same secret cannot be reused to sign payloads referencing arbitrary other tenants' repositories.

### Proof of Concept
```ruby
# Multi-tenant secrets: TenantA and TenantB each have their own webhook_secret
# (see docs/setup.md "Using Multiple Github Applications").
# Attacker administers TenantA and knows TenantA's webhook_secret.

payload = {
  "ref" => "refs/heads/master",
  "after" => "<some sha the attacker wants recorded as pushed on TenantB's stack>",
  "repository" => {
    "full_name" => "TenantB/critical-repo",   # <-- victim tenant's repo
    "owner" => { "login" => "TenantA" }        # <-- used ONLY to pick the verifying secret
  }
}.to_json

signature = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", tenant_a_webhook_secret, payload)

post "/webhooks", body: payload,
     headers: { "X-Github-Event" => "push", "X-Hub-Signature" => signature }
# verify_signature succeeds (TenantA's own secret validates TenantA's own signature)
# but PushHandler#stacks resolves and syncs TenantB/critical-repo, not TenantA's repo.
```
A more severe variant targets `status` events with a `sha` belonging to a pending pull request on `TenantB`'s stack, forging a `success` status to unlock `ProcessMergeRequestsJob#perform` -> `MergeRequest#merge!` on TenantB's repository.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
