### Title
CCMenu API endpoint lets a stack-scoped `ApiClient` token read the build status of any stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
The bug-class in the report is a deployment-trust binding that is set up correctly in one place but silently bypassed in another, so a value the system believes is constrained is actually unconstrained. In this engine, the equivalent binding is: **"the stack an `ApiClient` token is authorised for" == "the stack the endpoint actually returns data for."** `Shipit::Api::CCMenuController` breaks that equality.

### Finding Description
`Shipit::Api::BaseController` enforces stack scoping centrally through the `stacks`/`stack` helpers: [1](#0-0) 

`current_api_client.stack_id?` restricts the queryable set to the one stack the client was created for (see the `here_come_the_walrus` fixture, which has `stack: shipit`), and every other API controller (`StacksController#stack`, `TasksController`, `DeploysController`, etc.) resolves `stack` via this scoped `stacks` relation, e.g.: [2](#0-1) 

`Shipit::Api::CCMenuController`, however, overrides `stack` to bypass this scoping entirely and resolve directly against the full `Stack` table by an attacker-controlled `params[:stack_id]`: [3](#0-2) 

The controller only enforces `require_permission :read, :stack`, which is implemented by `ApiClient#check_permissions!` and checks nothing but the string `"read:stack"` against the client's permission list — it has no notion of which stack the permission applies to: [4](#0-3) 

So the "authorization" side of the equality (`ApiClient.stack_id` — the one stack this token was minted for) is never consulted by `CCMenuController#stack`, while the "touches" side (`params[:stack_id]`, fully attacker-controlled) determines what data is rendered. Any client holding a `read:stack`-permissioned token — including one deliberately scoped to a single, low-sensitivity stack via `Stack#stack_id` (as created by `CCMenuUrlController`, which mints such tokens automatically for any `current_user`) — can pass a different `stack_id` and read another stack's latest build/deploy status, activity, and last build label, which are otherwise gated by per-stack API-client scoping elsewhere in the API.

The counterpart route/controller `Shipit::CcmenuUrlController` (non-API, session-authenticated) generates exactly this style of narrowly-scoped token for any logged-in user: [5](#0-4) 

confirming that stack-scoped tokens are a real, relied-upon security boundary in this codebase — one that `CCMenuController` alone fails to honor.

### Impact Explanation
This is a stack-scope authorization bypass: a credential intentionally restricted to one stack can be used to read build/CI status of any other stack in the Shipit instance, violating the stack-scoping contract that the rest of the API enforces (as demonstrated by the existing test "an api client scoped to a stack will only see that one stack"). This matches the "High: escalation into unauthenticated/under-scoped read of stack state" impact class — the leak is limited to build status metadata (`lastBuildStatus`, `activity`, `lastBuildLabel`, `webUrl`, stack name) rather than task output or credentials, but it does cross a repository/stack authorization boundary that the token was explicitly meant not to cross.

### Likelihood Explanation
Any party holding a legitimately-issued, stack-scoped `ApiClient` token with `read:stack` permission (e.g., a CCMenu URL generated for a specific stack and shared/embedded in a CI dashboard) can exploit this trivially by changing the `stack_id` URL segment — no special privileges beyond possessing that one token are required, and the request is a simple unauthenticated-looking GET with a `token` query parameter.

### Recommendation
Have `CCMenuController#stack` resolve the stack through the same scoped `stacks` helper used everywhere else in `BaseController` (i.e., `stacks.from_param!(params[:stack_id])` instead of `Stack.from_param!(params[:stack_id])`), so that a stack-scoped `ApiClient` cannot query outside of `current_api_client.stack_id`.

### Proof of Concept
1. As a legitimate user, generate a CCMenu URL for `stack-a` via `CCMenuUrlController#fetch`, which creates/reuses an `ApiClient` scoped to `stack-a` (`stack_id` set) with `permissions: ['read:stack']`.
2. Take the returned `token` and issue a request to the CCMenu API endpoint for a different stack: `GET /api/<other-stack>/ccmenu.xml?token=<token-scoped-to-stack-a>`.
3. Because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly rather than `stacks.from_param!(...)`, the request succeeds and returns `<other-stack>`'s build status, even though the token's `ApiClient.stack_id` is `stack-a`.
