### Title
Bad-debt supply-index floor clamp leaves wiped suppliers with phantom claims that drain fresh deposits - (File: contracts/pool/src/interest.rs)

### Summary
The use-after-free analog maps to a dangling-share bug class: value is "freed" (socialized away) while the share objects referencing it survive. When `apply_bad_debt_to_supply_index` socializes a loss that exceeds total supplied value, it clamps `supply_index` up to `SUPPLY_INDEX_FLOOR_RAW` (`RAY/1000`) instead of zeroing out supplier shares. Every pre-wipeout supplier position keeps a small but positive claim against the market. When a new supplier later deposits, those stale shares redeem real tokens first, draining the fresh deposit and leaving the pool unable to cover the new supplier's claim.

### Finding Description
`seize_positions` with `AccountPositionType::Borrow` socializes unpaid debt via `interest::apply_bad_debt_to_supply_index` in `contracts/pool/src/interest.rs:73-89`. The function computes `remaining = total_supplied_value - min(bad_debt, total_supplied_value)`, derives a `reduction_factor`, multiplies it into `supply_index`, then floors the result at `SUPPLY_INDEX_FLOOR_RAW`:

```rust
cache.set_supply_index(new_supply_index.max(Ray::from(SUPPLY_INDEX_FLOOR_RAW)));
```

On a near-total wipeout (`bad_debt >= total_supplied_value`), `remaining` is zero and `new_supply_index` would be zero — but the clamp forces the index back up to `RAY/1000`. Scaled supply shares (`supplied`) are never burned or rebalanced; each supplier's `scaled_amount` remains fully intact on the controller's books. Each share therefore retains a claim of `scaled * RAY/1000`, a phantom balance backed by nothing.

The repository's own test `test_raw_cache_floor_clamp_strands_claim_without_supply_guard` in `contracts/pool/tests/interest.rs:372-427` demonstrates the end-to-end theft: after the clamp, an old scaled position resolves to `stranded > 0` via `unscale_supply_floor`, a fresh deposit of that size is credited, and the stale position's `resolve_withdrawal(i128::MAX, old_scaled)` pays out `gross == fresh_cash`, leaving `cache.cash() < fresh_claim` — the fresh supplier can never be made whole.

Reachability by an unprivileged address: controller `clean_bad_debt` is permissionless (dust-threshold gated, per `scripts/permissionless_entrypoints.txt` line 72) and calls `execute_bad_debt_cleanup` (`contracts/controller/src/positions/liquidation/bad_debt.rs:14-49`), which forwards a `PoolSeizeEntry` with `side: Borrow` to `pool_seize_positions_call`, reaching `ops::seize::apply` (`contracts/pool/src/ops/seize.rs:18-34`) and then the flawed clamp.

### Impact Explanation
Theft of user funds / protocol insolvency. Any supplier who held scaled shares through a wipeout keeps a positive redemption claim that the pool's bookkeeping honors. The first deposits into the market after the wipeout are paid out to the holders of these dead positions instead of backing the new supplier. An attacker can pre-position as the dominant supplier of a market, wait for (or ride) a bad-debt event that consumes total supplied value, then recover `scaled * RAY/1000` of real tokens from subsequent depositors — tokens that were supposed to back the victims' shares. The pool then permanently fails `require_reserves`-style backing checks for the new supplier, a lasting insolvency introduced by the clamp.

### Likelihood Explanation
Triggering requires a bad-debt event large enough to consume essentially all supplied value in one market — i.e., debt accrued beyond total supply claims with residual collateral under the dust threshold, enabling `clean_bad_debt`. This is tail-risk territory (deep underwater, thinly supplied market after long accrual, or a market abandoned after a severe collateral crash), so the frequency is low, but no privileged action, oracle manipulation, or parameter misconfiguration is needed: the cleanup call is permissionless and the clamp executes unconditionally once the wipeout exceeds supply value. The exploit then succeeds deterministically against the next honest depositor. Medium severity.

### Recommendation
Instead of clamping `supply_index` up to `SUPPLY_INDEX_FLOOR_RAW` when `remaining` reaches zero, handle total wipeout explicitly: when `bad_debt >= total_supplied_value`, write the scaled `supplied` (and `revenue`) shares down to zero — or set the index to zero and special-case zero-index unscaling to yield zero claims — so surviving share records cannot redeem. If a nonzero index is required for subsequent `calculate_scaled_supply` divisions, gate the floor to the case where `remaining > 0` and record a "wiped" flag (or reset `supplied`/`revenue` to zero) so old scaled positions unscale to nothing. At minimum, bound the clamp by `new_supply_index.min(old_index)` semantics so a socialization can never *raise* the index relative to the unclamped result.

### Proof of Concept
Encoded in the repository's own test at `contracts/pool/tests/interest.rs:372-427`:

1. Seed a market with `supplied = 1_000 * RAY` scaled shares, `supply_index = RAY`, `cash = 0`.
2. Call `apply_bad_debt_to_supply_index(&mut cache, Ray::from(5_000 * RAY))` — a bad debt 5x total supply, exactly what a `clean_bad_debt` seize of deeply underwater debt produces.
3. Observe `supply_index == SUPPLY_INDEX_FLOOR_RAW` (clamped up, shares untouched).
4. The old position still unscale_withdraws `stranded > 0`.
5. A fresh supplier deposits `fresh_cash = stranded`, minting shares at the floored index.
6. The old position withdraws `gross == fresh_cash`, and `cache.cash() < fresh_claim` — the fresh supplier's claim is unbacked.

Attacker path in production: supply into a thin market → let an underwater account's debt be socialized via permissionless `controller::clean_bad_debt(account_id)` → index clamps to `RAY/1000` while the attacker's scaled supply position survives → wait for (or self-fund) a new deposit → `controller::withdraw` against the phantom claim to extract the new depositor's tokens.
