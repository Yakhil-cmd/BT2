### Title
Webhook signature verification is scoped by `repository.owner.login`/`organization.login` while record mutation is scoped by a separately attacker-controlled `repository.full_name`, enabling cross-repository forgery via any no-secret org - ([File: app/controllers/shipit/webhooks_controller.rb], [File: lib/shipit/github_app.rb], [File: app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb])

### Summary
`Shipit::WebhooksController#verify_signature` picks which organization's `webhook_secret` to check against using `repository_owner`, computed from `params.dig('repository','owner','login')` (or `organization.login`), while `LabelCapturingHandler` (and every other `pull_request` handler) resolves the target `Repository`/`Stack` from a different, independently attacker-controlled field: `params.repository.full_name`. Because these two JSON fields are not required to be consistent, an attacker can pick an organization that has no `webhook_secret` configured to short-circuit verification, while pointing `repository.full_name` at a completely different, victim-configured stack (e.g., one with `blocking_statuses`).

### Finding Description
The binding the code implicitly assumes is: `repository_owner (used to authenticate) == owner(repository.full_name) (used to mutate)`. This is never enforced.

- `verify_signature` in [1](#0-0)  calls `Shipit.github(organization: repository_owner)` and then `github_app.verify_webhook_signature(...)`, where `repository_owner` is defined at [2](#0-1) .
- `verify_webhook_signature` in `GitHubApp` returns `true` unconditionally, without inspecting the signature header at all, when the resolved organization's config has no `webhook_secret`: [3](#0-2) . `@webhook_secret` itself is just `@config[:webhook_secret].presence`, i.e., an optional per-organization setting [4](#0-3) .
- Once verification passes (or is skipped), `WebhooksController#create` dispatches the full, unmodified `params` to every handler for the event with no further ownership check: [5](#0-4) .
- `LabelCapturingHandler#repository` resolves the acted-upon repository from `params.repository.full_name` — a different JSON path than the one used for signature-org selection: [6](#0-5) . It then persists attacker-supplied label names onto that repository's stack's `PullRequest`: [7](#0-6) .

Exploit flow: attacker crafts a `pull_request`/`action=labeled` payload where `repository.owner.login` = `"attacker-org"` (an organization onboarded to this Shipit instance without a configured `webhook_secret`), and `repository.full_name` = `"victim-org/victim-repo"` (a real repository with a review stack that has `blocking_statuses` configured). Because verification resolves `Shipit.github(organization: "attacker-org")`, whose `webhook_secret` is blank, `verify_webhook_signature` returns `true` regardless of the `X-Hub-Signature` header content (malformed or absent) — no HMAC comparison against the victim org's real secret ever occurs. The request passes `verify_signature`, and `LabelCapturingHandler` then looks up and mutates `victim-org/victim-repo`'s stack based on `repository.full_name`, writing attacker-chosen label names into `PullRequest#labels`, which `ReviewStack#env` later uppercases into environment variables that can influence `blocked?`/deploy gating for a stack the attacker never authenticated against.

The "nil/malformed signature split" behavior in `verify_webhook_signature` (returning `false` because a malformed header rarely produces `algorithm == 'sha1'`, or feeding `nil` into `secure_compare` in the edge case where the header is exactly `"sha1"`) is not required to make this exploit work — the decisive bypass is that verification org selection and mutation target selection are decoupled fields in the same attacker-controlled body, and any org with no configured secret nullifies the entire signature check outright.

### Impact Explanation
An unprivileged internet requester (no GitHub session, no repo access, no webhook secret) can write to a `PullRequest`/`Stack` record belonging to a repository/org they do not control, as long as any org on the instance lacks a configured `webhook_secret`. This is a payload-for-one-repository-mutates-another's-stack scenario, matching the Critical impact category. Because label names become uppercased environment variables consumed by `ReviewStack#env`, and label state feeds `blocked?` logic gating deploys on stacks with `blocking_statuses` configured, this can be leveraged to influence deploy gating on a victim stack. The attack is repeatable against any repository/stack whose full name the attacker can guess or discover, as long as one no-secret organization exists on the instance.

### Likelihood Explanation
Requires: (1) the Shipit instance to have at least one organization configured without a `webhook_secret` (a plausible and legitimate multi-tenant configuration, e.g., a sandbox/internal org or one relying solely on network-level trust), and (2) knowledge of the victim's exact `owner/repo` full name (public information for GitHub). No secrets, tokens, or privileged roles are needed. Attacker cost is a single crafted HTTP POST to `/webhooks` with mismatched `repository.owner.login` vs `repository.full_name`.

### Recommendation
Enforce that `repository.owner.login` (or `organization.login`) used for secret selection is derived from — and consistent with — the same `repository.full_name` used by handlers to resolve the target `Repository`/`Stack`; reject the webhook if they diverge. Additionally, do not allow `verify_webhook_signature` to silently return `true` for organizations without a configured secret if any other organization on the instance requires one; require every onboarded organization to have a `webhook_secret`, or reject payloads targeting repositories owned by organizations different from the one that authenticated the request.

### Proof of Concept
Minitest plan (extends `test/controllers/webhooks_controller_test.rb`):
1. Configure two orgs in `Shipit.github_configs`: `"attacker-org"` with no `webhook_secret`, and `"victim-org"` with a `webhook_secret` set (do not use it).
2. Create `Repository.create!(owner: "victim-org", name: "victim-repo")`, a `ReviewStack` under it with `blocking_statuses: ["ci/status"]`, and a `PullRequest` with `number: 42`.
3. Build a `pull_request`/`action=labeled` JSON body with `repository: { owner: { login: "attacker-org" }, full_name: "victim-org/victim-repo" }`, `pull_request.number: 42`, `pull_request.labels: [{name: "SHIPIT_BLOCKED"}]` (or any attacker-chosen label).
4. POST to `/webhooks` with `X-Github-Event: pull_request` and any `X-Hub-Signature` value (malformed or absent).
5. Assert response is `200 OK` (verification bypassed) and assert `PullRequest.find_by(number: 42, stack: victim_stack).labels` now equals `["SHIPIT_BLOCKED"]` — i.e., a repository the request never authenticated against (`victim-org`) had its `PullRequest` mutated by a request authenticated only as `attacker-org`.
6. Before/after equality check: before, `victim_pull_request.labels == []`; after, `victim_pull_request.reload.labels == ["SHIPIT_BLOCKED"]`, proving the divergence between the org used for authentication and the org whose record was mutated.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
