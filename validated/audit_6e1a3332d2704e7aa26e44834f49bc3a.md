### Title
Webhook signature verified against `repository.owner.login`/`organization.login`, but repository-scoped writes use the unrelated `repository.full_name` field (and `StatusHandler` uses no repository scope at all) - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App config (and therefore which `webhook_secret`) is used to validate `X-Hub-Signature` based on `repository_owner`, a value read straight out of the attacker-suppliable JSON body (`repository.owner.login` or `organization.login`). [1](#0-0)  If that organization has no `webhook_secret` configured (documented as optional in `docs/setup.md`), `GithubApp#verify_webhook_signature` returns `true` unconditionally, regardless of the actual signature header. [2](#0-1)  The equality the engine relies on — "the organization that authenticated the request" == "the repository being written to" — is never enforced, because the write path uses a different, unchecked field of the same payload.

### Finding Description
The webhook dispatch pipeline is:
1. `verify_signature` picks the signing organization from `repository.owner.login` (fallback `organization.login`) and validates the raw body against that org's secret. [1](#0-0) 
2. If verification passes (including the "no secret configured → always verified" branch), `WebhooksController#create` parses the entire JSON body and dispatches it, unmodified, to every registered handler for the event. [3](#0-2) 
3. Handlers resolve the target `Repository`/`Stack` using `repository.full_name`, a completely independent JSON field from `repository.owner.login`: [4](#0-3) 
4. `StatusHandler`, used for the `status` event, does not scope by repository at all — it looks up commits globally by SHA across the entire Shipit instance: [5](#0-4) 

Because a multi-tenant Shipit deployment (as shown in `config/secrets.development.shopify.yml` and `docs/setup.md`) can configure several organizations, each with an *optional* `webhook_secret`, [6](#0-5)  an attacker only needs one such configured organization to lack a secret (or to have a leaked/guessable one). They then submit an arbitrary JSON body where `repository.owner.login` equals that low-trust organization (satisfying step 1), while `repository.full_name` (used in step 3) or the commit `sha` (used in step 4, with no repository check whatsoever) refers to a completely different, higher-trust repository/stack tracked by the same Shipit instance. This breaks the binding "organization that authenticated" == "repository that is written" required by the analog rules.

`Commit#create_status_from_github!` writes an attacker-chosen state directly to `Status`, and `Commit#deployable?`/`#blocked?` rely on that state to decide whether CI requirements are satisfied. [7](#0-6) [8](#0-7)  `ci.require`/`ci.blocking` are documented mechanisms specifically meant to gate deploys on commit status context. [9](#0-8)  Forging a `status` webhook that marks a required/blocking context as `success` for a victim stack's commit, using only a foreign (unsecured) organization's identity, therefore bypasses that gate and can unblock/trigger an unauthorized deploy via continuous delivery (`Commit#schedule_continuous_delivery`). [10](#0-9) 

### Impact Explanation
This is an authentication-bypass class issue on the webhook trust boundary: an unprivileged attacker who knows (or can guess) that any one configured GitHub organization in the target's multi-org Shipit deployment lacks a `webhook_secret` can forge signed-looking webhook events for repositories/stacks belonging to *other*, properly secured organizations. Concretely this allows forging CI `status` (globally, with zero repository scoping) or `push`/`check_suite`/`membership` events for stacks and teams unrelated to the "authenticated" organization, enabling bypass of `ci.require`/`ci.blocking` checks that gate deploys — an unauthorized-deploy-enabling condition, and also team/membership tampering across organizations.

### Likelihood Explanation
Requires no session, no API token, and no repository write access — only knowledge that a configured GitHub App organization in the Shipit instance has no webhook secret (a documented "optional" configuration) or a leaked secret for any one org. In multi-organization Shipit deployments this is a realistic, low-effort condition, since Shipit's own setup docs explicitly show the secret as optional per-organization.

### Recommendation
Bind the field used for signature-organization selection to the same field used by every handler for repository/stack resolution (i.e., verify against `repository.full_name`'s owner, not a separately-trusted field), and reject webhooks where these disagree. Additionally, `StatusHandler` (and any handler resolving by SHA/global lookup) must scope its queries by the repository identified in the *verified* payload, never search across all stacks unconditionally. Consider also disallowing/deprecating the "no secret configured" auto-pass behavior in `GithubApp#verify_webhook_signature` for any but explicitly acknowledged trusted setups.

### Proof of Concept
1. Configure Shipit with two organizations: `LowTrustOrg` (no `webhook_secret`) and `HighTrustOrg` (with a strong `webhook_secret`), both with repositories tracked as stacks — mirrors the documented multi-org setup in `config/secrets.development.shopify.yml`.
2. Find a commit SHA of a stack under `HighTrustOrg` that is pending/missing a required CI status.
3. POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<HighTrustOrg-commit-sha>",
  "state": "success",
  "context": "ci/required-context",
  "repository": { "owner": { "login": "LowTrustOrg" }, "full_name": "whatever" }
}
```
No valid `X-Hub-Signature` is required because `LowTrustOrg` has no secret — `verify_webhook_signature` returns `true` at `lib/shipit/github_app.rb:77`.
4. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) finds the commit by SHA with no repository filter and creates a `success` status on it, even though the request was only "authenticated" for `LowTrustOrg`.
5. If this status was a required/blocking context for the `HighTrustOrg` stack, the commit becomes `deployable?` and, with continuous deployment enabled, a deploy is triggered without any legitimate CI signal from `HighTrustOrg`.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
