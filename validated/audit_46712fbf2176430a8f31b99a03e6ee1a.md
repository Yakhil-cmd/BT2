### Title
Cross-organization webhook forgery via mismatched `repository.owner.login` (signature key) vs `repository.full_name` (write target) - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to validate an inbound webhook signature against using `repository_owner`, computed from `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`). Every webhook handler (`PushHandler`, `CheckSuiteHandler`, `StatusHandler`, etc.), however, resolves the `Repository`/`Stack` to act on using a *different* JSON field from the same payload: `payload.dig('repository', 'full_name')` in `Handler#repository_name`. In a multi-organization Shipit deployment (as documented in `config/secrets.development.example.yml` and `docs/setup.md`, where each org has its own `app_id`/`webhook_secret`), these two fields are never cross-checked against each other.

### Finding Description
The verified binding should be: *"the organization whose secret signed this payload" == "the organization whose repository is written to."* This engine breaks that binding.

- `verify_signature` in `app/controllers/shipit/webhooks_controller.rb:24-49` looks up the GitHub App config via `Shipit.github(organization: repository_owner)` and calls `github_app.verify_webhook_signature(signature, raw_post)`.
- `repository_owner` is `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` (`app/controllers/shipit/webhooks_controller.rb:59-62`).
- `verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`) only proves the raw body was HMAC-signed with *that organization's* `webhook_secret`. It says nothing about which repository the body actually describes.
- All handlers derive the actual write target independently, via `Handler#repository_name` = `payload.dig('repository', 'full_name')` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`), then `Repository.from_github_repo_name(repository_name)&.stacks`.

For a legitimate GitHub-generated webhook these two fields always agree (GitHub itself sets `repository.owner.login` and `repository.full_name` consistently). But an attacker who administers their **own** GitHub organization/App installed on this same multi-tenant Shipit instance controls that org's `webhook_secret` (it is configured by the org admin per `docs/setup.md`). Nothing prevents that attacker from POSTing directly to `/webhooks` a JSON body whose `repository.owner.login` is their own org (so the correct secret is selected and the HMAC check passes) but whose `repository.full_name` names an arbitrary *other* org/repo tracked by the same Shipit instance.

### Impact Explanation
By forging `repository.full_name` while keeping `repository.owner.login`/`organization.login` matching their own org's secret, an attacker with no access to the victim repository can drive handlers that operate on victim stacks:
- `PushHandler` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) enqueues `stack.sync_github` on any stack matching the forged branch/full_name, for a repository the attacker doesn't own.
- `StatusHandler` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) creates a fake CI status (`commit.create_status_from_github!`) on the victim's commits by SHA — since CI status gates deploys (per `ci.require` in `shipit.yml`), this can be used to fabricate green CI on a victim commit and unlock deploys that should be blocked, i.e. an unauthorized/deploy-enabling condition.
- `CheckSuiteHandler` similarly triggers `schedule_refresh_check_runs!` against victim stacks/commits by SHA.

This is a cross-tenant/cross-repository write through a trust boundary that is supposed to isolate organizations from each other, matching the "Critical: cross-repository writes / unauthorized deploy" impact bucket.

### Likelihood Explanation
Requires: (1) a Shipit instance configured for multiple GitHub organizations sharing one engine deployment (an explicitly supported and documented configuration in `docs/setup.md`/`config/secrets.development.example.yml`), and (2) attacker control of a legitimate, low-privilege GitHub App/org onboarded to that same instance (no special Shipit privilege — just being one of the multiple tenants). This is a realistic setup for SaaS-style or internal multi-org Shipit deployments and requires no compromise of the victim org's secrets, GitHub credentials, or the Shipit host.

### Recommendation
After signature verification, validate that `repository.owner.login` (or `organization.login`) used to select the signing key is the same organization that owns the repository referenced by `repository.full_name` before dispatching to any handler — i.e., derive the write target's owner strictly from the same trusted, already-signature-verified field used for secret selection, rather than trusting a second independent field from the payload. Concretely, `WebhooksController` should re-derive `repository_name`'s owner and reject (422) if it doesn't match `repository_owner` used for the signature check.

### Proof of Concept
1. Shipit is configured with two orgs in `secrets.yml`: `orgA` (attacker-controlled, webhook secret known to attacker) and `orgB` (victim, has a tracked `Stack` for `orgB/victim-repo`).
2. Attacker crafts a `push` (or `status`) webhook JSON body with:
   - `repository.owner.login = "orgA"`
   - `repository.full_name = "orgB/victim-repo"`
3. Attacker computes `X-Hub-Signature` using `orgA`'s `webhook_secret` (`Hook::DeliverySigner`/HMAC-SHA1 scheme in `lib/shipit/github_app.rb:76-83`).
4. POSTs to `/webhooks` with `X-Github-Event: push`. `verify_signature` selects `Shipit.github(organization: "orgA")`, verifies successfully.
5. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("orgB/victim-repo")`, triggering `sync_github`/status/check-run updates for the victim's stack — despite the attacker having no relationship to `orgB`.       github_app = Shipit.github(organization: repository_owner)

**File:** lib/shipit/github_app.rb (L76-83)
```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
