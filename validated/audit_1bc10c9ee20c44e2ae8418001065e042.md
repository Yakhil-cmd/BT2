### Title
Cross-organization webhook confusion allows forged `push`/`membership` events to trigger unauthorized syncs and role changes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate a request against using an *organization name pulled straight from the unverified JSON body*, while the handlers that actually act on the request use a *different, independently attacker-controlled field* (`repository.full_name`) to decide which `Stack`/`Repository` gets mutated. In a multi-organization Shipit deployment, if any one configured organization has no `webhook_secret` set (an explicitly documented, supported configuration — see `docs/setup.md` "Using Multiple Github Applications" and `config/secrets.development.example.yml` showing `webhook_secret: # nil`), signature verification for that organization is a no-op, but the payload's `repository.full_name` is not constrained to that organization at all.

### Finding Description
The bug-class analog to the Nibbl `_updateTwav()`/`_getTwav()` report is: a check is performed over one piece of state (`cumulativeValuation`) while a *different, unguarded* code path (the difference calculation) is trusted to remain consistent with it. Here, the equivalent broken binding is:

`organization used to authenticate the webhook signature == organization that owns the repository the handlers write to`

This equality is never enforced.

1. `verify_signature` computes `repository_owner` from the **unverified** raw body:
`params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0) 
2. It uses that attacker-supplied string to select a `GitHubApp` config/secret: `Shipit.github(organization: repository_owner)`, then verifies `X-Hub-Signature` against that org's secret [2](#0-1) .
3. `GitHubApp#verify_webhook_signature` **unconditionally returns `true` if no `webhook_secret` is configured** for the selected organization: `return true unless webhook_secret` [3](#0-2) .
4. Once verification passes, the entire raw JSON body (fully attacker-controlled, no further checks tie it back to `repository_owner`) is dispatched to handlers: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [4](#0-3) .
5. Handlers resolve the target `Stack`/`Repository` from `payload.dig('repository', 'full_name')` — a completely independent field from the one used in step 1: `Repository.from_github_repo_name(repository_name)&.stacks` [5](#0-4) .
6. `PushHandler#process` then triggers `stack.sync_github(expected_head_sha: params.after)` for any stack matching that (attacker-chosen) repository/branch [6](#0-5) .

Shipit explicitly supports multiple GitHub Apps keyed by organization, each independently configured (`TOP_LEVEL_GH_KEYS = [:app_id, :installation_id, :webhook_secret, :private_key, :oauth, :domain]`) [7](#0-6) , and the setup docs illustrate this multi-org layout with `webhook_secret:` left blank per-org [8](#0-7) . Because signature validation is scoped per-organization but the payload's repository/stack targeting is not cross-checked against that organization, an attacker who knows (or can enumerate) any configured organization name that has no `webhook_secret` set can forge a request whose `repository.owner.login` equals that weakly-configured org, while `repository.full_name` names *any other, unrelated tracked repository* (belonging to an organization that does enforce a secret).

### Impact Explanation
This breaks the deployment-trust binding "organization authenticated == repository written." A forged `push` event lets an unprivileged attacker specify `ref` and `after` (an arbitrary SHA) for a `Stack` belonging to a repository they do not control, causing `Stack#sync_github` to run against an attacker-chosen SHA. If continuous deployment is enabled on that stack, this can result in an unauthorized deploy of attacker-chosen content — matching the Critical/High impact bar ("unauthorized deploy, rollback, or merge"). A forged `membership` event can similarly add/remove users from `Team`s tracked by Shipit (`Handlers::MembershipHandler`), escalating into `Shipit.github_teams`-style authorization without any legitimate GitHub signature covering the actual target repository/team.

### Likelihood Explanation
This requires: (a) a multi-organization Shipit deployment, and (b) at least one configured organization without a `webhook_secret`. Both conditions are explicitly documented as supported/valid configurations rather than misconfigurations unique to this deployment, so the vulnerability is a design gap in the engine rather than a one-off operator mistake. The attacker needs no credentials, no GitHub App access, and no valid signature — only network access to `/webhooks` and knowledge of one org name lacking a secret and the target repository's `full_name`.

### Recommendation
Bind the two identities together: after selecting the `GitHubApp` used to verify the signature, re-derive and enforce that `payload.dig('repository','full_name')`'s owner matches the organization whose secret validated the request, rejecting the webhook otherwise. Additionally, avoid the `return true unless webhook_secret` short-circuit in `verify_webhook_signature`, or make it configurable per-deployment with an explicit opt-in flag, so organizations without a secret cannot be silently used as an unauthenticated relay for other organizations' repositories/stacks.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.yml`: `orgA` (no `webhook_secret`) and `orgB` (with `webhook_secret: "s3cr3t"`), each with a tracked repository/stack (`orgA/repo-a`, `orgB/repo-b`).
2. Attacker sends `POST /webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "full_name": "orgB/repo-b",
    "owner": { "login": "orgA" }
  }
}
```
No `X-Hub-Signature` header value need be valid, since `Shipit.github(organization: "orgA")` resolves to a `GitHubApp` with no `webhook_secret`, causing `verify_webhook_signature` to return `true` unconditionally [9](#0-8) .
3. `WebhooksController#create` proceeds to dispatch to `PushHandler`, which resolves stacks via `repository.full_name = "orgB/repo-b"` [10](#0-9)  and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on `orgB`'s stack [11](#0-10) , despite the request never being signed by `orgB`'s secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

    someothergithuborg:
