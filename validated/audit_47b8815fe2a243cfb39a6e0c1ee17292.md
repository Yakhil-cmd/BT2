Based on my investigation into transaction admission, multisig approval validation, and prologue logic, I found a concrete gap in the multisig transaction approval-binding check.

### Title
Multisig transaction execution can bypass payload-match verification against the on-chain approved payload when `abort_if_multisig_payload_mismatch_enabled` is disabled - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
`validate_multisig_transaction`, the Move function invoked by the VM prologue for every multisig transaction [1](#0-0) , is supposed to guarantee that the entry function/arguments an executor actually submits for execution is the same one the multisig owners voted to approve. When the full payload (not just its hash) was stored on-chain at proposal time, that binding check is gated entirely behind the `abort_if_multisig_payload_mismatch_enabled` feature flag [2](#0-1) .

### Finding Description
`run_multisig_prologue` in the Rust VM builds a `provided_payload` byte string directly from the `executable` field of the *signed transaction being submitted for execution* (i.e., whatever the executor puts in their transaction) [3](#0-2) , and passes it into `validate_multisig_transaction`. Inside that Move function:

- If `transaction.payload_hash` is set (large-payload mode), the provided payload is always checked against the stored hash unconditionally [4](#0-3) .
- If instead the full `transaction.payload` was stored at proposal time (the normal/small-payload path), the match check is only performed when `features::abort_if_multisig_payload_mismatch_enabled()` returns true [2](#0-1) .

When that feature is not active, none of the quorum/approval logic (`can_execute`, `num_approvals_and_rejections`, `can_execute_with_timelock`) at lines 1335–1359 verifies *what* was approved matches what is about to run — it only verifies that *some* payload received enough votes. The prologue then allows the VM to proceed to actually execute whatever `executable` (entry function + arguments) the submitting owner encoded in their transaction [5](#0-4) , not the payload that was actually voted on by the other owners.

This is the same conceptual bug class as the referenced report: a validation step that should bind two related values (input token vs. output token in the report; approved payload vs. executed payload here) is applied to only one side of the check while the other side is silently unchecked, letting the operation proceed onto unapproved/uncontrolled data.

### Impact Explanation
Any account owner who is entitled to be the final approving executor of a multisig transaction (satisfying quorum/threshold) can submit a completely different entry function call than what was actually approved by the co-owners, as long as `abort_if_multisig_payload_mismatch_enabled` is not turned on. This breaks the core multisig approval-set invariant: execution should occur under exactly the transaction body that the required signer/owner set voted for. It enables unauthorized state transitions under the multisig account's authority (e.g., transferring funds to an address never voted on) even though the on-chain vote count "looks" satisfied.

### Likelihood Explanation
This requires no privileged network state beyond the feature flag being unset. Given that this check is guarded by a distinctly named "fix" feature flag (implying that it did not exist as a mandatory check before this flag was introduced), any deployment/testnet/devnet or period before the flag's activation is exposed. The exploit requires only normal multisig usage (create a multisig, get quorum approvals for tx A, then have the executor submit payload B instead), no leaked keys or admin privileges needed to trigger the mismatch itself.

### Recommendation
Make the payload-match assertion for full-stored payloads unconditional (remove the `features::abort_if_multisig_payload_mismatch_enabled()` gate), matching the mandatory unconditional hash check already applied in the `payload_hash` branch.

### Proof of Concept
Conceptually (cannot fully execute in this read-only session, but the code path is directly traceable):
1. Owner A creates a multisig transaction proposing `EntryFunction(coin::transfer, [victim, 1])`, which is stored fully on-chain via `transaction.payload` (not `payload_hash`).
2. Owners vote and reach quorum for that specific proposal.
3. The executing owner submits a `SignedTransaction` whose `executable` field instead encodes `EntryFunction(coin::transfer, [attacker, 1000000])`.
4. `run_multisig_prologue` builds `provided_payload` from this attacker-controlled executable [6](#0-5)  and calls `validate_multisig_transaction`.
5. Since `abort_if_multisig_payload_mismatch_enabled` is false, the mismatch branch at lines 1375-1384 is skipped entirely; only quorum/timelock checks run and pass.
6. The VM proceeds to execute the attacker's entry function under the multisig account's signer authority.

Note: I was not able to fully verify within tool-call limits whether some other layer (e.g., additional runtime checks in `aptos_vm.rs` execution beyond the prologue) independently re-derives and enforces the stored payload before dispatch; the prologue-level gap is confirmed directly in source, but full end-to-end confirmation of the entry-function dispatch path would benefit from a live Devin session with test execution to close this last link with certainty.

```rust
pub(crate) fn run_multisig_prologue(
    session: &mut SessionExt<impl AptosMoveResolver>,
    module_storage: &impl ModuleStorage,
    txn_data: &TransactionMetadata,
    executable: TransactionExecutableRef,
    multisig_address: AccountAddress,
    features: &Features,
    log_context: &AdapterLogSchema,
    traversal_context: &mut TraversalContext,
) -> Result<(), VMStatus> {
    let unreachable_error = VMStatus::error(StatusCode::UNREACHABLE, None);
    // Note[Orderless]: Earlier the `provided_payload` was being calculated as bcs::to_bytes(MultisigTransactionPayload::EntryFunction(entry_function)).
    // So, converting the executable to this format.
    let provided_payload = match executable {
        TransactionExecutableRef::EntryFunction(entry_function) => bcs::to_bytes(
            &MultisigTransactionPayload::EntryFunction(entry_function.clone()),
        )
        .map_err(|_| unreachable_error.clone())?,
        TransactionExecutableRef::Empty => {
            if features.is_abort_if_multisig_payload_mismatch_enabled() {
                vec![]
            } else {
                bcs::to_bytes::<Vec<u8>>(&vec![]).map_err(|_| unreachable_error.clone())?
            }
        },
        TransactionExecutableRef::Script(script) => {
            if !features.is_multisig_script_enabled() {
                return Err(VMStatus::error(
                    StatusCode::FEATURE_UNDER_GATING,
                    Some("Multisig script payload is not enabled".to_string()),
                ));
            }
            bcs::to_bytes(&MultisigTransactionPayload::Script(script.clone()))
                .map_err(|_| unreachable_error.clone())?
        },
        TransactionExecutableRef::Encrypted => {
            return Err(VMStatus::error(
                StatusCode::FEATURE_UNDER_GATING,
                Some("Encrypted payload not supported for multisig transactions".to_string()),
            ));
        },
    };
```
