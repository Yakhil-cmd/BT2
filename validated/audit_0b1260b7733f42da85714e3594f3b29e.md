### Title
Webhook organization used to select the HMAC signing key is not bound to the repository the event actually mutates - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which GitHub App/organization's `webhook_secret` to verify a webhook against using a value taken straight out of the *unverified* JSON body, then hands that same unverified body to the event handlers. In a multi-organization Shipit deployment, the value that authenticates the request (the org whose secret is checked) and the value that is later acted upon (the repository/stack the handler mutates) are never proven to be the same organization.

### Finding Description
`repository_owner` is computed from `params`, which is simply `JSON.parse(request.raw_post)` — data that has not yet been authenticated: [1](#0-0) 

That value is what selects the `GitHubApp` instance (and therefore the `webhook_secret`) used to verify the signature: [2](#0-1) 

`verify_webhook_signature` only checks the raw body against the secret belonging to whichever organization was selected: [3](#0-2) 

Shipit explicitly supports configuring multiple GitHub organizations, each with its own independent `webhook_secret`: [4](#0-3) [5](#0-4) 

Once the signature is accepted, the entire unverified payload — not just the field used to pick the secret — is dispatched to every registered handler for the event: [6](#0-5) 

Nothing re-checks that the `repository`/`sha`/other identifying fields used by the handlers actually belong to the same organization whose secret was used to authenticate the request. The `status` handler, for example, writes attacker-supplied fields (`state`, `target_url`, `description`, `created_at`) onto whatever commit matches the supplied `sha`, taken verbatim from the body: [7](#0-6) 

**The broken binding:** organization-that-authenticated (chosen via `repository_owner` and validated by `verify_webhook_signature`) ≠ repository/stack-that-is-written (resolved later from the same unverified payload by the handler). Before the attacker's request, an attacker only controls webhooks whose HMAC is signed with the secret of an organization they legitimately administer (their own GitHub App installation). After the request, because `repository_owner` and the fields used inside the handler are independently taken from the same attacker-authored JSON body, the attacker can set `repository.owner.login` to their own org (to select their own known secret) while setting the other identifying fields (`sha`, `repository.full_name`, etc.) to point at a victim stack tracked under a different, unrelated organization also configured on the same Shipit instance.

### Impact Explanation
If exploited against the `status` event, this allows an attacker who only controls their own GitHub App installation/org to forge a commit status (state, description, target_url) on a commit belonging to a completely different organization's stack. Since Shipit stacks can gate deploys on required commit statuses, this can be used to mark a malicious or unreviewed commit as "success" and enable an unauthorized deploy — a Critical impact per the "unauthorized deploy" category. The same confused-deputy pattern applies to any handler that trusts payload fields (`push`, `check_suite`, `membership`, `pull_request`) beyond the single field used to pick the verification secret.

### Likelihood Explanation
Requires a Shipit instance configured with more than one GitHub organization (an explicitly documented and supported configuration) and requires the attacker to control (own) at least one of those organizations/GitHub App installations, giving them a genuine webhook secret to sign with — no Shipit session, `ApiClient` token, or private key theft needed. This is a realistic setup for any Shipit instance serving multiple teams/orgs.

### Recommendation
After verifying the HMAC, re-derive `repository_owner` (and any other org-identifying field used by handlers) from the same trusted context used to select the secret, and reject the webhook if the organization that authenticated the signature does not match the organization owning the `repository`/`stack` referenced elsewhere in the payload. Alternatively, bind the verified GitHub App/organization object to the request and pass it explicitly into every handler instead of re-parsing organization identity from the raw payload downstream.

### Proof of Concept
1. Configure Shipit with two GitHub orgs, `OrgOne` (victim, hosts a tracked stack `OrgOne/victim-repo`) and `OrgTwo` (attacker-controlled, legitimately installed with its own `webhook_secret`), as supported by `test/dummy/config/secrets_double_github_app.yml`.
2. Attacker, who knows `OrgTwo`'s `webhook_secret` (it's their own GitHub App), crafts a `status` event JSON body:
   ```json
   {
     "sha": "<victim commit sha in OrgOne/victim-repo>",
     "state": "success",
     "description": "forged",
     "target_url": "https://attacker.example.com",
     "repository": { "owner": { "login": "OrgTwo" }, "full_name": "OrgOne/victim-repo" }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(OrgTwo_webhook_secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `verify_signature` resolves `repository_owner` = `"OrgTwo"`, fetches `OrgTwo`'s `GitHubApp`, and successfully verifies the signature against `OrgTwo`'s secret [2](#0-1) .
5. `create` then dispatches the full body — including the `sha` referencing `OrgOne/victim-repo` — to the `status` handler, which writes the forged status onto the victim's commit, as demonstrated by the equivalent legitimate-path test [7](#0-6) .

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml
production:
  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
```
