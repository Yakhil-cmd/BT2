### Title
Unattributed `pending_delegator_rewards` block-revenue pool is misdistributed to whichever delegators are staked at the next epoch boundary, penalizing depositors who leave early and rewarding late joiners — ([File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs])

### Summary
The GoGoPool `syncRewards()` bug is a permissionless "sync" call that finalizes a reward cycle only when someone invokes it; anyone interacting with the pool before that call is unfairly excluded, while anyone present at the call gets the pool's full accrued rewards regardless of actual duration staked. Agave's SIMD‑0123 block‑revenue‑sharing mechanism has the same structural shape: `pending_delegator_rewards` on a vote account is a permissionless, ever‑growing pool (anyone can call `DepositDelegatorRewards` at any time) that is only "synced"/distributed once per epoch at the epoch-boundary reward calculation, and distribution is based on a single point‑in‑time stake snapshot rather than on who actually held stake while the pool accrued.

### Finding Description
`DepositDelegatorRewards` lets any signer transfer lamports into a vote account and unconditionally increases `pending_delegator_rewards` via `add_pending_delegator_rewards`, which only ever `checked_add`s the deposit [1](#0-0) . The instruction itself is invoked from `deposit_delegator_rewards`, and nowhere in that path is `pending_delegator_rewards` decremented at deposit time [2](#0-1) .

This pool is only "released" once per epoch, during the epoch‑boundary reward calculation, by `calculate_block_reward`. That function reads the vote account's current `pending_delegator_rewards` and distributes it to each stake delegation in proportion to `stake / total_active_stake`, where `total_active_stake` is the `RewardEpochDelegatedStakes` snapshot taken at the *end* of the rewarded epoch (i.e., a single point in time), not an integral over the period during which the pool accrued [3](#0-2) .

A comprehensive search of `pending_delegator_rewards` usage across the codebase (vote program, handler, vote_state_view, CLI/decoders, and the reward-calculation path) turns up only additions (`add_pending_delegator_rewards`) and reads; there is no code path that decrements/zeroes `pending_delegator_rewards` after `calculate_block_reward` consumes it for distribution. This means the pool keeps compounding epoch over epoch, and whichever proportional share is computed at any given epoch boundary is applied against the *entire accumulated-to-date* pool, not just revenue that accrued while the currently-staked delegators were actually staked.

This reproduces the GoGoPool bug class precisely:
- Deposits into `pending_delegator_rewards` (analogous to reward accrual in the ggAVAX vault) can happen at any time, permissionlessly, and are not tied to a bounded "cycle."
- The "sync" event (the epoch reward calculation) only fires at epoch boundaries, exactly like `syncRewards()` firing only when someone calls it after `rewardsCycleEnd`.
- Any stake delegation that deactivates/undelegates from the vote account before an epoch boundary loses its share of the accumulated pool entirely — the same lamports are then attributed only to whichever delegations are staked at the snapshot instant, i.e., late arrivals capture rewards that accrued from block production performed while they were not staked, while early depositors who leave before the boundary get zero of the block-revenue rewards they should be entitled to. This mirrors "user1 withdraws before syncRewards() and gets 0 rewards; user2 deposits right before and captures the whole cycle's rewards."

### Impact Explanation
Because the distribution formula uses `stake / total_active_stake` evaluated only at the rewarded epoch's snapshot, and the numerator pool (`pending_delegator_rewards`) is a cumulative, never-reset balance, this produces misattributed rewards between delegators: capital that deactivates stake right before an epoch boundary forfeits its true economic share of block revenue to whichever stake is present at that instant. This is a "misattributed or duplicated rewards" class impact — lamports are not stolen or minted incorrectly in aggregate (the block reward total distributed still sums to ≤ `pending_delegator_rewards`), but individual delegator entitlements are computed against the wrong population and the wrong time window, which is a concrete economic unfairness in reward distribution, consistent with the accepted "Medium" severity classification of the original GoGoPool finding.

### Likelihood Explanation
`DepositDelegatorRewards` is unprivileged and can be called by anyone with lamports and a vote-account address at any cadence, and stake activation/deactivation are ordinary, permissionless staker actions. Because the block-revenue pool accumulates continuously while distribution happens only once per epoch based on a single stake snapshot, virtually any staker who deactivates/redelegates around an epoch boundary — or any staker who joins right before one — will experience this misattribution as a matter of normal operation, not a crafted attack. No exceptional configuration or validator/operator privilege is required to trigger it.

### Recommendation
Consider tracking `pending_delegator_rewards` accrual against a continuously-updated stake-weighted accumulator (analogous to a "reward per share" checkpoint updated on stake/vote account changes) rather than a single balance redeemed against an epoch-end snapshot, or explicitly decrement/checkpoint `pending_delegator_rewards` each time it's consumed in `calculate_block_reward` so unresolved (undistributed) amounts don't compound across multiple epochs and get reattributed to a different stake population than the one present while the revenue was earned.

### Proof of Concept
1. Vote account `V` has one delegator, `stakeA`, fully staked, contributing to block production for an entire epoch `E`.
2. Throughout epoch `E`, arbitrary parties call `DepositDelegatorRewards` on `V`, growing `pending_delegator_rewards` to `R` [4](#0-3) .
3. Near the very end of epoch `E` (before the epoch boundary reward calculation), `stakeA` fully deactivates and a new delegator `stakeB` activates and becomes part of `RewardEpochDelegatedStakes` for the epoch.
4. At the epoch boundary, `calculate_block_reward` computes `stakeB`'s share as `pending_delegator_rewards (R) * stake_B / total_active_stake`, crediting `stakeB` for revenue `R` that was earned while `stakeA`, not `stakeB`, was staked and contributing to block production [5](#0-4) .
5. Because `pending_delegator_rewards` is never decremented back to `0` for the amount consumed (no subtraction found anywhere in the codebase), if `R` is only partially distributed at this boundary, any leftover continues to compound, further disconnecting future distributions from the stakers who actually earned it.

/// Deposit delegator rewards into a vote account (SIMD-0123).
pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}

/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }
