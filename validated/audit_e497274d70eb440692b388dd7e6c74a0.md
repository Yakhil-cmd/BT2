### Title
Unpriceable Aquarius LP dust collateral blocks liquidation and bad-debt cleanup - (File: contracts/controller/src/risk/totals.rs)

### Summary

A borrower can add a dust amount of an Aquarius LP token as collateral, then withdraw enough liquidity from that LP’s configured Aquarius pool to push its valuation below `min_pool_value_wad`. Because every valuation-dependent path prices **all** collateral and debt positions through the strict `prices` interface, `liquidate`, `clean_bad_debt`, and `update_account_threshold` revert with `InsufficientAquariusLiquidity`. [1](#0-0) [2](#0-1) 

### Finding Description

`supply` permits the account owner to create a new supply leg and credits the measured deposit; it performs no strict price check on the newly deposited asset. [3](#0-2)  Later, `build_liquidation_plan` computes `calculate_account_risk_totals` over both `supply_positions` and `borrow_positions`. [4](#0-3)  That routine first calls `Context::load_markets` on the union of those position keys. [5](#0-4) 

`load_markets` fetches strict prices for every unique token in the account. [6](#0-5)  The controller invokes the aggregator’s fail-closed `prices` endpoint and panics if any requested result is absent. [7](#0-6)  For an Aquarius LP source, the aggregator reads the live reserves and total shares, computes pool value, and returns `OracleError::InsufficientAquariusLiquidity` when the value is below `lp.min_pool_value_wad`. [8](#0-7) 

The same all-position valuation runs in `socialize_bad_debt`, so the dust LP leg also prevents permissionless cleanup after the account becomes insolvent. [9](#0-8)  An equivalent regression test already demonstrates that adding a dust position whose feed is unusable bricks both `liquidate` and `clean_bad_debt`, then restores them once the leg is priceable. [10](#0-9) 

### Impact Explanation

An unhealthy borrower can temporarily prevent liquidation and bad-debt socialization without any privileged role. While the configured Aquarius pool remains below the liquidity floor, liquidators cannot resolve the account’s health factor or seize collateral, and `clean_bad_debt` cannot socialize the residual debt. [11](#0-10) [12](#0-11) 

The attacker’s debt continues accruing while economically recoverable collateral cannot be liquidated through the intended path. If liquidity is not restored or governance cannot replace the oracle promptly, the position can become deeply insolvent and transfer losses to suppliers through bad debt. This is temporary freezing of liquidation/cleanup and creates protocol-insolvency risk.

### Likelihood Explanation

Likelihood is Medium. The attacker must borrow against an account that includes an Aquarius LP collateral leg and control enough LP liquidity to move the configured pool below `min_pool_value_wad`. That condition is practical where the listed LP market has shallow liquidity or the borrower is a dominant LP. Supplying the dust leg requires no oracle success, and the subsequent liquidity withdrawal is an ordinary unprivileged Aquarius action.

### Recommendation

Do not require every collateral leg to have a currently valid strict price for liquidation and bad-debt cleanup. Options include:

- Value an unpriceable collateral leg conservatively at zero for liquidation/cleanup rather than aborting the entire account.
- Add a liquidation-only degraded mode that excludes an unpriceable collateral leg from both seizure and collateral totals.
- For bad-debt cleanup, carry a stored last-known value solely for the dust gate, while treating an unpriceable residual leg as zero or as protocol revenue.
- Alternatively, explicitly restrict LP collateral to pools whose liquidity is sufficiently deep and widely distributed that one LP cannot cross the configured floor.

### Proof of Concept

1. An attacker opens an account and supplies normal collateral plus one unit, or another dust amount, of a listed Aquarius LP token:

```rust
controller.supply(
    attacker,
    0,
    spoke_id,
    vec![
        (normal_collateral_hub_asset, collateral_amount),
        (aquarius_lp_hub_asset, dust_amount),
    ],
);
```

2. The attacker borrows against the account:

```rust
controller.borrow(
    attacker,
    account_id,
    vec![(debt_hub_asset, borrow_amount)],
    None,
);
```

3. After market movement or interest makes the account unhealthy, the attacker withdraws their liquidity from the Aquarius pool referenced by the LP oracle until its computed pool value is below `min_pool_value_wad`. The LP source then returns `InsufficientAquariusLiquidity`. [1](#0-0) 

4. Any liquidator call reverts before repayment or seizure:

```rust
controller.liquidate(
    liquidator,
    account_id,
    vec![(debt_hub_asset, repayment_amount)],
    SeizeMode::Transfer,
);
```

The revert occurs because liquidation loads a strict price for every supply and borrow asset before checking the health factor. [4](#0-3) [2](#0-1) 

5. Once the account is insolvent, permissionless cleanup reverts on the same valuation before its dust gate can be evaluated:

```rust
controller.clean_bad_debt(caller, account_id);
```

The harness test `audit_liquidate_and_clean_bricked_by_unpriceable_dust_leg` demonstrates the same account-level failure pattern with an unpriceable dust leg: the added supply succeeds, liquidation and cleanup revert, and liquidation succeeds after the leg becomes priceable. [10](#0-9)
