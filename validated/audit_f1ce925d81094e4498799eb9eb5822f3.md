### Title
Cross-organization webhook forgery via mismatched verification identity and repository resolution field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to validate a webhook against using `repository_owner`, taken from `params.dig('repository', 'owner', 'login')` (or `organization.login`). Every webhook handler, however, resolves the actual `Repository`/`Stack` to mutate using a completely different, unchecked field of the same attacker-supplied JSON body: `payload.dig('repository', 'full_name')`. Because Shipit explicitly supports multiple independently-configured GitHub organizations (each with its own, optional `webhook_secret`), these two fields are never cross-checked against each other.

### Finding Description
`verify_signature` computes the signing organization purely from the request body itself, then fetches that org's `GithubApp` config and calls `verify_webhook_signature`: [1](#0-0) [2](#0-1) 

`verify_webhook_signature` trivially returns `true` whenever the selected org has no `webhook_secret` configured, which the documentation shows as a supported, optional value (`webhook_secret: # nil`): [3](#0-2) [4](#0-3) 

Once verification passes, `WebhooksController#create` dispatches the raw, unauthenticated-content payload straight to the event handlers: [5](#0-4) 

Every handler resolves the target `Repository`/`Stack` using `repository.full_name`, not `repository.owner.login`: [6](#0-5) [7](#0-6) 

The binding that should hold is: `organization used to verify signature == organization owning the repository the handler mutates`. It does not — the two are read from two independent, attacker-controlled JSON fields in the same request body, and nothing enforces that `repository.owner.login` is a prefix of `repository.full_name`.

### Impact Explanation
If a Shipit deployment configures multiple GitHub organizations (as documented and supported, see `config/secrets.development.example.yml` and `docs/setup.md` "Using Multiple Github Applications"), and even one of those organizations has no `webhook_secret` set (an explicitly supported, non-privileged configuration state), an attacker can craft a JSON body such as:
```json
{
  "repository": { "owner": {"login": "org-with-no-secret"}, "full_name": "victim-org/victim-repo" },
  ...
}
```
`verify_signature` will authenticate this request for free (no secret required for `org-with-no-secret`), while the dispatched handler acts on `victim-org/victim-repo`, an entirely different, presumably higher-trust organization whose own webhook secret was never checked. This lets an unauthenticated attacker forge `push`, `status`, `check_suite`, `pull_request`, etc. events for any repository tracked by the Shipit instance — e.g., forging commit `status` payloads that gate `deployable_status`, or triggering `GithubSyncJob`/`ReviewStackAdapter` flows — which can lead to unauthorized deploy-gating state changes or spoofed CI signals feeding the deploy pipeline. This directly breaks the "organization authenticated versus the repository that is written" trust binding named in scope.

### Likelihood Explanation
Requires only that the Shipit instance is configured with more than one GitHub App/organization and that at least one configured organization has no `webhook_secret` set — both explicitly documented, supported configurations, not a misconfiguration outside the engine's intended use. No credentials, tokens, or repository access of any kind are required by the attacker; the entire attack is a single unauthenticated POST to `/webhooks` with a self-consistent forged JSON body.

### Recommendation
After signature verification, re-validate that the organization used for signature verification (`repository_owner` / `organization.login`) actually matches the organization component of `repository.full_name` before dispatching to any handler, or resolve the target repository via the verified organization rather than trusting an independent field of the unauthenticated payload body.

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.yml`: `TrustedOrg` (no `webhook_secret`) and `VictimOrg` (with a `webhook_secret`, hosting a real tracked stack, e.g. `VictimOrg/app`).
2. POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<victim-commit-sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": {
    "owner": { "login": "TrustedOrg" },
    "full_name": "VictimOrg/app"
  }
}
```
No `X-Hub-Signature` header, or any arbitrary value, is required, since `TrustedOrg` has no `webhook_secret` (`verify_webhook_signature` returns `true` unconditionally per `lib/shipit/github_app.rb:76-77`).
3. `WebhooksController#verify_signature` passes; `Shipit::Webhooks.for_event('status')` handler resolves the commit via `repository.full_name = "VictimOrg/app"` (per `app/models/shipit/webhooks/handlers/handler.rb:36-38` pattern used across handlers) and records a forged successful status on `VictimOrg`'s commit, despite the attacker never possessing `VictimOrg`'s webhook secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
