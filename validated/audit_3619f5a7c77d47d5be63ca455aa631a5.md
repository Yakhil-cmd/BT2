### Title
Cross-tenant Team membership mutation via global `github_id` lookup in `MembershipHandler#find_or_create_team!` - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`MembershipHandler#find_or_create_team!` looks up an existing `Team` solely by `github_id`, a GitHub-wide numeric ID, with no check that `params.organization.login` matches the found team's `organization`. Because `membership` webhook payloads never include a `repository` key, `WebhooksController#verify_signature` legitimately falls back to `params.dig('organization','login')` to select the signing app - and this is the attacker's *own*, correctly-configured organization. The attacker can therefore send a fully-valid, correctly-signed `membership` webhook naming their own org, but embedding a victim team's `github_id`, causing `team.add_member`/`team.members.delete` to run against the victim's `Team` record.

### Finding Description
The broken binding is the equality that should hold but doesn't: `team.organization == params.organization.login` for every mutation path, not just the create path.

Code path:
- `WebhooksController#create` (app/controllers/shipit/webhooks_controller.rb:10-15) parses the raw JSON and dispatches to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. [1](#0-0) 
- `verify_signature` resolves the signing app via `repository_owner`, which for `membership` events (no `repository` key) falls back to `params.dig('organization', 'login')` - this is the attacker's own org, so signature verification legitimately succeeds using the attacker's own webhook secret. [2](#0-1) 
- `Handler#initialize`/`.call` just parses and dispatches to `MembershipHandler#process` with no repository/organization authorization of its own. [3](#0-2) 
- `MembershipHandler#find_or_create_team!` calls `Team.find_or_create_by!(github_id: params.team.id) { |team| team.organization = params.organization.login }` - the block (which sets `organization`) only executes on the **create** branch of `find_or_create_by!`. On the **find** branch (an existing `Team` row with that `github_id`, e.g. a victim's legitimate team), the block never runs, so `params.organization.login` has zero effect and no comparison against the existing record's `organization` occurs. [4](#0-3) 
- `process` then unconditionally calls `team.add_member(member)` or `team.members.delete(member)` on whatever `Team` was returned. [5](#0-4) 
- `Team#add_member` performs the actual membership mutation with no organization check. [6](#0-5) 

Exploit flow: attacker controls a real, Shipit-configured GitHub organization ("attacker-org") with its own valid webhook secret. Attacker POSTs to `/webhooks` with header `X-Github-Event: membership` and a JSON body containing:
- `action: "added"`
- `team: { id: <victim_team_github_id>, name: ..., slug: ..., url: ... }` (any team name/slug/url - only `id` needs to match the victim's real `github_id`)
- `organization: { login: "attacker-org" }`
- `member: { login: "attacker-controlled-username" }`
- no `repository` key at all (consistent with real `membership` events)

Signed with attacker-org's own valid webhook secret. `verify_signature` resolves `Shipit.github(organization: "attacker-org")`, verifies successfully (it is a legitimately signed request from a real tenant), and the request proceeds. `MembershipHandler` finds the victim's existing `Team` by `github_id` alone and adds the attacker's chosen `member` to it, or removes an existing legitimate member - independent of which organization actually owns that team.

Existing guards do not stop this: `verify_signature` only proves the request came from the named organization, it says nothing about which `Team` rows that organization may mutate; `drop_unhandled_event` and the `ExplicitParameters` schema only validate shape/presence of fields, not cross-tenant ownership; there is no `require_permission!`/`Shipit.github_teams` check anywhere in the webhook handling path.

### Impact Explanation
An attacker who legitimately controls any single Shipit-configured GitHub organization can add arbitrary GitHub users (including themselves) to, or remove legitimate members from, any other tenant's `Team` record, as long as they can guess or discover that team's numeric GitHub `github_id` (obtainable via GitHub's public API, since team IDs are visible to team/org members and often guessable/enumerable). Team membership in Shipit typically governs deploy/merge authorization gates (`Shipit.github_teams`-style checks elsewhere in the app), so this is a cross-tenant escalation into another organization's authorized-team membership - matching the "escalation into `Shipit.github_teams` authorization" / "payload for one repository mutating another's team" impact categories. It is repeatable against any team github_id and requires only one HTTP POST per mutation.

### Likelihood Explanation
Precondition: attacker must operate a real, already-configured Shipit tenant (their own org with a valid GitHub App/webhook secret) - stated as given in the prompt. No Shipit session, API token, or victim secrets are needed. The attacker needs to know or guess the victim team's numeric `github_id`, which is discoverable via GitHub's REST API for teams the attacker can see, or otherwise enumerable. Cost is a single crafted, self-signed HTTP request; fully repeatable and scriptable against many victim team IDs.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup by both `github_id` and `organization` (e.g. `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`), and/or explicitly verify that an existing found `Team#organization` equals `params.organization.login` before performing any membership mutation, rejecting (or no-op'ing) the webhook otherwise.

### Proof of Concept
Minitest plan (webhooks controller/handler test, no live GitHub):
1. Fixture: create `Team` record `victim_team` with `github_id: 555`, `organization: "victim-org"`, with an existing member `victim_user`.
2. Configure two tenants in `Shipit.github_teams`/app config: `attacker-org` (attacker-controlled, with known webhook secret `attacker_secret`) and `victim-org`.
3. Build payload:
   ```json
   {
     "action": "added",
     "team": { "id": 555, "name": "x", "slug": "x", "url": "https://api.github.com/teams/555" },
     "organization": { "login": "attacker-org" },
     "member": { "login": "attacker_user" }
   }
   ```
   with no `repository` key.
4. Compute `X-Hub-Signature` using `attacker_secret` (the attacker's own legitimately-known secret for their own org) over the raw JSON body.
5. POST to `/webhooks` with `X-Github-Event: membership` and the computed signature header.
6. Assert response is `200 OK` (signature verified, not `422`).
7. Assert `victim_team.reload.members` now includes a `User` with login `attacker_user` - i.e., `victim_team.organization` (`"victim-org"`) never equaled `params["organization"]["login"]` (`"attacker-org"`) yet the mutation on `victim_team` still occurred, proving the broken binding.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
