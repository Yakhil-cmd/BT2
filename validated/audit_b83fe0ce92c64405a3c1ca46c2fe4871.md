### Title
Webhook signature is verified against the payload's `repository.owner.login`, but every handler acts on the unrelated `repository.full_name` field — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController` selects which GitHub App / webhook secret to use for HMAC verification based on `repository.owner.login` (or `organization.login`) read out of the *same, attacker-controlled* JSON body, then verifies the raw body against that org's secret. Every event handler, however, resolves the repository/stack to act on using a completely different field — `repository.full_name` — which is never cross-checked against the organization whose secret produced a valid signature. This breaks the intended binding "organization that authenticated" == "repository that is written", exactly one of the documented in-scope trust bindings.

### Finding Description
`WebhooksController#verify_signature` computes `repository_owner` from the untrusted request body and uses it purely to look up which secret to check the signature against: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` resolves the app config for that organization, and `GitHubApp#verify_webhook_signature` explicitly treats an org without a configured `webhook_secret` as always verified: [3](#0-2) 

Meanwhile, every `Shipit::Webhooks::Handlers::Handler` subclass (push, status, pull_request, check_suite, membership, etc.) resolves the target `Stack`/`Repository` using an entirely different payload field, `repository.full_name`, with no re-validation that this repo belongs to the org whose secret was actually checked: [4](#0-3) [5](#0-4) 

`Shipit.github_app_config` performs case-insensitive lookup keyed only by whatever organization string is embedded in the request: [6](#0-5) 

Because Shipit supports multiple GitHub organizations, each with independently optional `webhook_secret` values, and the authenticating field (`repository.owner.login`) is disjoint from the field that drives repository resolution (`repository.full_name`), an attacker who controls (or is a member of) *any one* configured organization that has no `webhook_secret` set can:
1. Send a POST to `/webhooks` with `X-Github-Event: push` (or `status`, `check_suite`, etc.).
2. Set `repository.owner.login` (and/or `organization.login`) to the unsecured org, so `verify_webhook_signature` returns `true` unconditionally (line 77 of `github_app.rb`), with no `X-Hub-Signature` header required.
3. Set `repository.full_name` to `"victim-org/victim-repo"` — any repository actually tracked by Shipit, belonging to a different, properly-secured organization.
4. `Repository.from_github_repo_name` resolves the victim stack by that spoofed `full_name`, and the handler acts on it (`push_handler.rb` calls `stack.sync_github`, `status_handler.rb` creates commit statuses, `check_suite_handler.rb` triggers `RefreshCheckRunsJob`, etc.) as if GitHub itself had sent the event for the victim repository.

This is the "no error handling on an external verification result" bug class from the report, mapped onto Shipit: the signature-verification result is unconditionally trusted for the *entire* payload, while the field that actually drives state changes (`repository.full_name`) is never bound to the organization the signature check was performed against.

### Impact Explanation
This crosses the "unauthorized deploy/rollback or cross-repository writes" bar: an attacker can forge `push` events to trigger `GithubSyncJob`/`stack.sync_github` against arbitrary tracked stacks belonging to organizations they have no relationship with, forge `status` events to fabricate commit statuses that gate merges/deploys, and forge `check_suite` events to trigger `RefreshCheckRunsJob`. All of this requires no `ApiClient` token, no `webhook_secret`, and no repository write access to the victim repo — only that at least one org configured in the same Shipit instance omits `webhook_secret` (an explicitly supported, documented configuration per `docs/setup.md` and `config/secrets.development.example.yml`, which mark `webhook_secret` as `# nil`/optional).

### Likelihood Explanation
Moderate-to-high in any multi-organization Shipit deployment where at least one configured org has not set a `webhook_secret` (an explicitly supported configuration). No credentials, sessions, or GitHub App access are required — only knowledge of a tracked repository's `owner/name` and the target event shape, both of which are effectively public.

### Recommendation
Bind repository resolution to the authenticated organization: after signature verification succeeds, require that `repository.full_name`'s owner segment (or `organization.login`) matches the `repository_owner` value that was actually used to select and verify against a secret. Alternatively, disallow relying on an unauthenticated `repository_owner` to select the verification key at all — instead verify against every configured org's secret (or require `webhook_secret` to be mandatory for all orgs) and reject payloads whose `repository.full_name` owner doesn't match the org that produced a valid signature.

### Proof of Concept
Given a Shipit instance configured with two organizations, `secure-org` (has `webhook_secret` set) and `open-org` (no `webhook_secret`, per the supported optional configuration in `docs/setup.md`), and a tracked stack for `secure-org/victim-repo`:

```
POST /webhooks
X-Github-Event: push
Content-Type: application/json
(no X-Hub-Signature needed)

{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "full_name": "secure-org/victim-repo",
    "owner": { "login": "open-org" }
  }
}
```

- `WebhooksController#repository_owner` returns `"open-org"` [2](#0-1)  — signature check passes unconditionally because `open-org` has no `webhook_secret` [7](#0-6) .
- `PushHandler#stacks` resolves via `Repository.from_github_repo_name("secure-org/victim-repo")` [4](#0-3)  and calls `stack.sync_github(expected_head_sha: params.after)` on the victim stack [5](#0-4) , with zero signature material tied to `secure-org` ever presented.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
