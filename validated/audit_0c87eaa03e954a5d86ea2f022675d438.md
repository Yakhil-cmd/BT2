### Title
Stale in-memory account overwrites reentrant storage mutations during the `flash_position` receiver callback, resurrecting withdrawn collateral — (File: contracts/controller/src/strategies/flash_position.rs)

### Summary
The Waitress bug class — a shared resource is mutated by another actor while an operation holds a stale view of it, so the in-flight operation completes on invalidated state — maps directly onto `process_flash_position`. The controller loads `account` (both position maps) into memory *before* the receiver callback, lets the callback run arbitrary code while the flash guard only blocks `liquidate`, and then writes the stale position maps back to storage afterwards via `process_deposit`/`strategy_finalize`. Any reentrant mutation of that account's positions during the callback is clobbered — a classic lost-update race.

### Finding Description
`process_flash_position` resolves and loads the full `Account` via `account::load_or_create_account` (line 93), then enters `storage::with_flash_guard` (line 121) inside which it mints debt (`mint_and_forward`) and invokes the attacker's `execute_flash_position` callback (line 131). Only after the callback returns does it persist position changes through `process_deposit` (line 146) and `strategy_finalize` (line 153).

The flash guard (`is_flash_loan_ongoing`, `contracts/controller/src/storage/account.rs:285-313`) is only enforced by `require_not_flash_loaning`, which is called exclusively in the liquidation path (`contracts/controller/src/positions/liquidation/mod.rs`). `supply`, `withdraw`, `repay`, `net_settle`, and position-NFT `transfer` are all reachable during the callback.

Position persistence is wholesale-map based: `set_supply_positions`/`set_debt_positions` (`contracts/controller/src/storage/account.rs:75-105`) store entire `Map<HubAssetKey, _>` values, not deltas. The `account` object held across the callback therefore contains a pre-callback snapshot of both maps. When `strategy_finalize` persists it, it overwrites whatever a reentrant call wrote.

Concrete attack: the initiator (an attacker contract holding the account NFT) calls `flash_position`. Inside `execute_flash_position`, the receiver calls `withdraw(account_id, …)` on a pre-existing supply position of the same account. `withdraw` reloads positions from storage, burns the supply shares, pays out tokens, and removes the position from the stored map. Control returns to `flash_position`, whose stale `account` still contains the withdrawn supply entry; `strategy_finalize` writes it back, resurrecting the collateral position while the attacker keeps the withdrawn tokens.

### Impact Explanation
Resurrected supply shares correspond to tokens already paid out — the pool's `cash` book was debited by the reentrant `withdraw`, but the controller ledger still credits the attacker the collateral. The attacker can then `borrow` against the phantom collateral up to the market LTV, extracting real tokens backed by nothing. This is theft of user funds and, if scaled, protocol insolvency.

### Likelihood Explanation
Reachable by a single unprivileged address: the attacker controls both the initiator contract (owns the account NFT, authorizes reentrant calls) and the receiver. No privileged role, no oracle manipulation, no bad parameters — just a normal `flash_position` call plus one reentrant `withdraw`. The only requirement is a market with `is_flashloanable` params and a pre-funded supply position, both cheap to arrange. The residual uncertainty is whether `strategy_finalize` or `process_deposit` narrows the writeback to changed keys only; nothing in the code reviewed suggests per-key merging — the persistence layer stores whole maps — and the debt position minted before the callback is likewise held only in the in-memory `account`, so the same staleness applies symmetrically to reentrant `repay`/`net_settle`.

### Recommendation
Apply `require_not_flash_loaning` (or the existing `with_flash_guard` flag check) to every account-mutating entrypoint — `supply`, `withdraw`, `repay`, `net_settle`, `clean_bad_debt`, `update_account_threshold`, and position-NFT `transfer`/`approve` — not just liquidation. Alternatively, reload position maps from storage after the callback and reconcile, or persist the flash-minted debt before invoking the receiver so reentrant operations observe and update the true state.

### Proof of Concept
1. Attacker deploys contract `A` (initiator + account owner) and contract `R` (flash receiver), or a single contract serving both roles.
2. `A` supplies collateral `C` into market `S`, obtaining supply position `P` on `account_id` `N`.
3. `A` calls `controller.flash_position(account_id=N, spoke_id, mode=Multiply, debt=D, amount=X, receiver=R, collaterals=[(S, 1)], …)`.
4. Inside `R::execute_flash_position`, `A` calls `controller.withdraw(N, …)` burning `P` and transferring `C`'s tokens to `A` (the flash guard does not cover `withdraw`).
5. Callback returns; `flash_position`'s stale `account` still contains `P`. `process_deposit`/`strategy_finalize` persists the stale supply map, restoring `P` in storage.
6. `A` now holds the withdrawn tokens *and* a supply position `P`; it calls `borrow` against `P` and exits with unbacked tokens.
