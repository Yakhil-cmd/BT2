### Title
Cross-stack authorization bypass in CCMenu API - a stack-scoped `ApiClient` token can read the build/deploy status of any other stack - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::CCMenuController` overrides `#stack` to resolve the target `Stack` directly from the request parameter (`Stack.from_param!(params[:stack_id])`) instead of going through the stack-scoping helper (`stacks.from_param!`) that every other API controller inherits from `Shipit::Api::BaseController`. This breaks the binding between "the stack(s) an `ApiClient` token is authorized for" and "the stack whose data is actually returned," which matches the report's `stack a token authorises` vs. `stack it touches` bug class.

### Finding Description
`Shipit::Api::BaseController` implements stack scoping for every API endpoint: [1](#0-0) 

`stacks` restricts the visible set of stacks to `current_api_client.stack_id` when the client was created with a `stack_id` (i.e., a stack-scoped token, as produced e.g. by `CCMenuUrlController#client`), and `stack` resolves `params[:stack_id]` only within that restricted set: [2](#0-1) 

`CCMenuController`, however, redefines `stack` to bypass this scoping entirely: [3](#0-2) 

The only authorization gate left is `require_permission :read, :stack`, which merely checks that the token's `permissions` array contains the string `read:stack` — it never checks *which* stack the token is scoped to: [4](#0-3) 

So the field that is verified (the token's permission list / `stack_id` scope at issuance time) is not the field that is used to select the record acted on (`params[:stack_id]`, taken directly from the request and resolved against `Stack.from_param!` with no scoping). This exactly mirrors the DODO bug class: the balance-check binding (WETH before/after) was decoupled from the actual settlement asset (native ETH); here the authorization binding (`current_api_client.stack_id`) is decoupled from the actual record resolution (`Stack.from_param!(params[:stack_id])`).

### Impact Explanation
Any holder of a valid `ApiClient` token that includes `read:stack` permission - including a token intentionally scoped to a single stack via `stack_id` (e.g. the "CCMenu Client" or any admin-created scoped token, see `test/fixtures/shipit/api_clients.yml`'s `here_come_the_walrus` fixture which is scoped to stack `shipit`) - can call `GET /api/stacks/:stack_id/ccmenu.xml` with any other `stack_id` and receive that unrelated stack's deploy/build status (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, lock state, etc.). This is an unauthenticated-for-that-resource read of stack state across a trust boundary the token issuer intended to enforce, matching the report's High-impact category "unauthorized read of stack state, task streams or deploy output."

### Likelihood Explanation
The attack requires only possession of any valid API token with `read:stack` permission - it does not require a full `Shipit` session, GitHub credentials, or write access to any repository, and the request is a single unauthenticated-relative-to-target GET call with an attacker-controlled `stack_id` path parameter. Given that scoped tokens are a documented/intended mechanism (`ApiClient#stack_id`, `CCMenuUrlController`), this is a straightforward misuse that any token holder can exploit deterministically, not merely theoretical.

### Recommendation
Remove the `stack` override in `Shipit::Api::CCMenuController` and use the inherited scoped resolver (`stacks.from_param!(params[:stack_id])`) so that stack-scoped tokens cannot resolve stacks outside their `stack_id`, consistent with every other endpoint under `Shipit::Api::BaseController`.

### Proof of Concept
1. As an admin, create (or use `CCMenuUrlController#client`, which creates) an `ApiClient` scoped to `stack_id: A` with `permissions: ['read:stack']` (see `here_come_the_walrus` fixture: `stack: shipit`, `permissions: [read:stack]` in `test/fixtures/shipit/api_clients.yml`).
2. Obtain its `authentication_token` (e.g. via the "CCMenu URL" feature at `CCMenuUrlController#fetch`, or from the API client's `show` page).
3. Send `GET /api/stacks/:other_stack_id/ccmenu.xml?token=<token>` where `other_stack_id` is a different stack the token was never scoped to.
4. Observe that `CCMenuController#stack` resolves `other_stack_id` via `Stack.from_param!` (unscoped), and `#show` renders that other stack's build/deploy status - despite the token only being authorized for stack `A`, contrary to the scoping enforced by `BaseController#stack`/`#stacks` for every other API endpoint.
