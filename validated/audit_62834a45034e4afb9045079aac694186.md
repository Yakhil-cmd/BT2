### Title
Unprotected `initializeConfig()` in `BridgeCommittee.sol` allows front-running to install a malicious `BridgeConfig`, enabling vault fund theft via decimal/token manipulation - (File: bridge/evm/contracts/BridgeCommittee.sol)

### Summary
`BridgeCommittee.initializeConfig()` is the exact analog of the reported `initializeV2()` bug: it is a post-deployment "second-phase" initializer that is not called atomically with the main `initialize()` and carries no caller restriction, only a state check (`config == address(0)`). Any address can call it, so it is vulnerable to front-running between proxy deployment and the deployer's own configuration call.

### Finding Description
`BridgeCommittee.sol` uses OpenZeppelin's UUPS pattern. The primary `initialize()` is protected by the `initializer` modifier and is invoked atomically with proxy deployment [1](#0-0) . However, the `config` address is *not* set in `initialize()`. It is set later via a separate, unprotected call:

```solidity
function initializeConfig(address _config) external {
    require(address(config) == address(0), "BridgeCommittee: Config already initialized");
    config = IBridgeConfig(_config);
}
``` [2](#0-1) 

This function has no `onlyOwner`, no `initializer` modifier, and no restriction on `msg.sender` — the only guard is that `config` must still be the zero address, exactly matching the reported pattern of a "second-phase initializer that is not atomic and lacks caller protection."

The deployment script confirms the non-atomic, two-step flow: `BridgeCommittee` is deployed and initialized first, `BridgeConfig` is deployed in a *separate* transaction afterward, and only then is `initializeConfig()` called in yet another transaction:

```solidity
address bridgeCommittee = Upgrades.deployUUPSProxy("BridgeCommittee.sol", ...); // tx 1
address bridgeConfig = Upgrades.deployUUPSProxy("BridgeConfig.sol", ...);       // tx 2
BridgeCommittee(bridgeCommittee).initializeConfig(address(bridgeConfig));       // tx 3 (unprotected)
``` [3](#0-2) 

Between tx 1 and tx 3, `BridgeCommittee.config` sits at `address(0)` and `initializeConfig` is callable by anyone. An attacker monitoring the mempool can front-run tx 3 with their own call, deploying and injecting an attacker-controlled `BridgeConfig` implementation before the legitimate one is set.

`BridgeConfig` itself governs token addresses, per-token Sui-side decimal counts, and supported-chain membership, all of which are trusted downstream without further validation:
```solidity
function initialize(... address[] memory _supportedTokens, ... uint8[] memory _suiDecimals, uint8[] memory _supportedChains) external initializer { ... }
``` [4](#0-3) 

`SuiBridge.transferBridgedTokensWithSignatures` reads `committee.config()` and uses its token address/decimals to compute the payout amount for a committee-signed transfer:
```solidity
IBridgeConfig config = committee.config();
...
uint256 erc20AdjustedAmount = BridgeUtils.convertSuiToERC20Decimal(
    IERC20Metadata(config.tokenAddressOf(tokenTransferPayload.tokenID)).decimals(),
    config.tokenSuiDecimalOf(tokenTransferPayload.tokenID),
    tokenTransferPayload.amount
);
_transferTokensFromVault(..., erc20AdjustedAmount);
``` [5](#0-4) 

Because `config` is fully attacker-controlled if front-run, the attacker can set `tokenSuiDecimalOf` to an artificially low value for a given `tokenID` while `tokenAddressOf` still points at the real vault-held ERC20. Any subsequent legitimately committee-signed token-transfer message (even for a small nominal amount) is then decimal-scaled by `convertSuiToERC20Decimal` into a hugely inflated ERC20 amount, causing `BridgeVault` to pay out far more than the committee authorized — direct theft of vault funds.

### Impact Explanation
This maps to the Critical bucket: "bridge governance or upgrade bypass that enables illegitimate mint or unlock." The attacker does not need committee keys or validator/authority privileges — only the ability to submit an ordinary transaction that lands before the deployer's follow-up `initializeConfig` call. Once the malicious config is installed, every subsequent legitimate, committee-signed token transfer can be manipulated into an outsized withdrawal from `BridgeVault`, directly draining bridged funds.

### Likelihood Explanation
The window of exposure is a normal part of every deployment/re-deployment of `BridgeCommittee` (and any future upgrade that resets `config`): there is an unavoidable gap between the `BridgeCommittee` proxy going live (with `config == 0x0`) and the deployer's separate `initializeConfig` transaction. Front-running an unprotected, publicly-callable state-setting function via mempool monitoring or same-block bundling is a well-understood, low-cost attack technique on EVM chains, making exploitation realistic during any live/mainnet deployment rather than purely theoretical.

### Recommendation
- Restrict `initializeConfig` to the contract owner/deployer (e.g., `onlyOwner`, or bind it to the same `initializer` semantics as `initialize`) rather than gating solely on `config == address(0)`.
- Preferably fold `config` assignment directly into the atomic `initialize()` call (deploy `BridgeConfig` first, then pass its address into `BridgeCommittee.initialize`), eliminating the two-transaction gap entirely.
- If a two-step flow must remain (e.g., for circular dependency reasons), use a multicall/batched deployment script that performs proxy deployment and `initializeConfig` in the same transaction, and additionally add an explicit `onlyOwner` check as defense in depth.

### Proof of Concept
1. Deployer submits tx to deploy the `BridgeCommittee` UUPS proxy and calls `initialize()` (this succeeds and is atomic, `config` remains `address(0)`).
2. Attacker observes the pending/confirmed `BridgeCommittee` proxy address on-chain (public information) and, before the deployer's subsequent `initializeConfig` transaction lands, deploys their own malicious `BridgeConfig`-compatible contract that:
   - Reports the real vault-held ERC20 addresses via `tokenAddressOf`.
   - Reports an artificially low `tokenSuiDecimalOf` value for the target token (e.g., `0` instead of the real `6` or `8`).
   - Reports `isChainSupported` as needed to pass `onlySupportedChain`.
3. Attacker calls `BridgeCommittee(bridgeCommittee).initializeConfig(maliciousConfig)` with higher gas/priority to front-run the deployer's legitimate call; since `config == address(0)` still holds, this succeeds and the deployer's subsequent legitimate call now reverts (`EAlreadyAuthorized`-style check fails), confirming the takeover.
4. Once the real committee later signs a normal, legitimate small-value token transfer message (e.g., depositing 1 unit of `tokenID`), `SuiBridge.transferBridgedTokensWithSignatures` calls `BridgeUtils.convertSuiToERC20Decimal` using the attacker's manipulated `tokenSuiDecimalOf`, producing a vastly inflated `erc20AdjustedAmount`, and `BridgeVault` transfers out far more of the real token than the committee authorized — draining bridge reserves.

Note: full exhaustive review of `BridgeUtils.convertSuiToERC20Decimal`'s exact scaling formula and of `SuiBridge`'s `onlySupportedChain`/`onlySupportedToken` modifiers was not completed due to iteration limits; these should be re-verified by a background agent to confirm the exact numeric blow-up factor and whether any additional check (e.g., a fixed token-address allowlist independent of `config`) mitigates the decimal-manipulation payout path.

    function initialize(
        address _committee,
        uint8 _chainID,
        address[] memory _supportedTokens,
        uint64[] memory _tokenPrices,
        uint8[] memory _tokenIds,
        uint8[] memory _suiDecimals,
        uint8[] memory _supportedChains
    ) external initializer {
        __CommitteeUpgradeable_init(_committee);
        require(
            _supportedTokens.length == _tokenPrices.length, "BridgeConfig: Invalid token prices"
        );
        require(
            _supportedTokens.length == _tokenIds.length, "BridgeConfig: Invalid token IDs"
        );
        require(
            _supportedTokens.length == _suiDecimals.length, "BridgeConfig: Invalid Sui decimals"
        );

        for (uint8 i; i < _tokenIds.length; i++) {
            // `is_native` is hardcoded to `true` because we only support Eth native tokens
            // at the moment. This needs to change when we support tokens native on other chains.
            supportedTokens[_tokenIds[i]] = Token(_supportedTokens[i], _suiDecimals[i], true);
        }

        for (uint8 i; i < _supportedChains.length; i++) {
            require(_supportedChains[i] != _chainID, "BridgeConfig: Cannot support self");
            supportedChains[_supportedChains[i]] = true;
        }

        for (uint8 i; i < _tokenPrices.length; i++) {
            tokenPrices[_tokenIds[i]] = _tokenPrices[i];
        }

        chainID = _chainID;
    }
