### Title
Deregistering Bridge Operators Without Threshold Guard Permanently Locks Bridged Assets — (`contracts/service_chain/bridge/BridgeOperator.sol`)

---

### Summary

`BridgeOperator.deregisterOperator` removes an operator from `operatorList` without verifying that the remaining operator count still satisfies `operatorThresholds`. If the owner deregisters enough operators so that `operatorList.length < operatorThresholds[VoteType.ValueTransfer]`, the vote threshold for value transfers becomes permanently unreachable. Every subsequent `handleKLAYTransfer`, `handleERC20Transfer`, or `handleERC721Transfer` call silently returns without executing, permanently locking all bridged KAIA and tokens in the bridge contract until the owner intervenes.

---

### Finding Description

`setOperatorThreshold` enforces the invariant `operatorList.length >= _threshold` at the time the threshold is set: [1](#0-0) 

However, `deregisterOperator` removes an operator from `operatorList` with no symmetric check: [2](#0-1) 

After deregistration, `operatorList.length` may fall below `operatorThresholds[VoteType.ValueTransfer]`. The vote accumulation in `_voteCommon` can then never satisfy the threshold condition: [3](#0-2) 

`_voteValueTransfer` returns `false`, and every handle function silently returns without transferring assets: [4](#0-3) [5](#0-4) 

The contract's own comment acknowledges that deregistration has subtle timing effects, but only for the opposite scenario (stale votes still counting), not for the threshold-breach scenario: [6](#0-5) 

---

### Impact Explanation

All pending and future cross-chain value transfers (KAIA, ERC20, ERC721) routed through the affected bridge pair are silently dropped. Bridged assets already locked in the bridge contract cannot be released. The `lowerHandleNonce` and `upperHandleNonce` never advance, so the value-transfer recovery mechanism (`valueTransferRecovery`) keeps re-submitting the same events with no effect: [7](#0-6) 

This matches the "bridged assets" impact category: assets are effectively frozen in the bridge contract with no on-chain path to release them until the owner registers new operators or lowers the threshold.

---

### Likelihood Explanation

The trigger requires the bridge owner to call `deregisterOperator` enough times to drop `operatorList.length` below the current threshold. This is a privileged action, but the contract provides no guard or warning when the invariant is about to be broken. The scenario is plausible during operator rotation (e.g., removing compromised operators before adding replacements). The existing comment about deregistration side-effects shows the developers are aware of subtle deregistration hazards, making an accidental breach of the threshold invariant realistic.

---

### Recommendation

Add a threshold-reachability check inside `deregisterOperator`, mirroring the check already present in `setOperatorThreshold`:

```solidity
function deregisterOperator(address _operator) external onlyOwner {
    require(operators[_operator]);
    // Ensure remaining operators can still meet every threshold
    for (uint8 i = 0; i < uint8(VoteType.Max); i++) {
        require(
            operatorList.length - 1 >= operatorThresholds[i],
            "threshold unreachable after deregistration"
        );
    }
    delete operators[_operator];
    // ... existing removal logic ...
    emit OperatorDeregistered(_operator);
}
```

Alternatively, automatically lower the threshold to `operatorList.length - 1` when deregistration would otherwise breach it, and emit a warning event so operators are alerted.

---

### Proof of Concept

1. Bridge is deployed with owner as the sole operator; `operatorThresholds[ValueTransfer] = 1`.
2. Owner registers operators A and B; sets `operatorThresholds[ValueTransfer] = 2`. Check passes: `3 >= 2`.
3. Owner deregisters the original owner-operator. `operatorList = [A, B]`, threshold = 2. Still reachable.
4. Owner deregisters A (e.g., key compromise). `operatorList = [B]`, threshold = 2. **No revert — invariant silently broken.**
5. User on the child chain calls `requestKLAYTransfer`, locking KAIA in the child bridge.
6. Operator B calls `handleKLAYTransfer` on the parent bridge. `_voteValueTransfer` accumulates 1 vote, which is `< threshold 2`, returns `false`. Function returns without transferring KAIA.
7. Value-transfer recovery re-submits the event; same silent failure repeats indefinitely.
8. User's KAIA is permanently locked until the owner registers a second operator or lowers the threshold — an off-chain remediation with no on-chain time guarantee. [2](#0-1) [4](#0-3) [5](#0-4)
