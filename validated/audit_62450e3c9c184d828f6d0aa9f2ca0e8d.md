### Title
Uncaught exception from a single crafted unit crashes the full node — analog of Knot DNS crafted-message crash (CVE-2014-0486) - ([File: validation.js])

### Summary
Knot DNS crashed on a crafted DNS message because an unexpected/edge-case input path threw an unhandled fault that terminated the process. `ocore` has a structurally identical class of bug: several `throw Error(...)` statements sit inside asynchronous `conn.query()`/callback chains deep in unit-validation code (`checkForDoublespends`, parts of `validatePaymentInputsAndOutputs`, `validateDefinition`/`validateAuthentifiers` in `definition.js`), which are **not** wrapped by any `try/catch` in their call stack. Any exception thrown there escapes to Node's top-level `uncaughtException` handler in `network.js`, which explicitly re-throws to crash the whole process — turning a single malformed/edge-case unit posted by any peer or light client into a full node crash.

### Finding Description

These `throw` statements are guarded by comments implying "this should be unreachable," i.e. they are defensive assertions rather than normal validation-error returns (`cb(err)`). Because JS exceptions thrown inside an async DB callback cannot be caught by the caller that invoked `conn.query()` synchronously (the call has already returned), the throw propagates out through the driver's event loop turn straight to the process-level handler: [3](#0-2) 

```
process.on('uncaughtException', (err) => {
	console.log('Uncaught exception:', err);
	...
	throw err; // crash the process to avoid ending up in an inconsistent state
});
```

This is a deliberate "crash rather than continue in an inconsistent state" design, but it means *any* code path that can be driven by attacker-controlled/edge-case data into one of these un-caught `throw`s becomes a remote, unauthenticated DoS: a single posted unit (via `handlePostedJoint` in `network.js`, reachable by any peer/light client, or a self-posted unit from an unprivileged wallet/light client), or a crafted payment/definition/AA trigger, causes the process to abort.

Similar unguarded `throw`s inside async `conn.query` callbacks exist throughout the same validation surface reachable from a single posted unit, e.g.:
- `validatePaymentInputsAndOutputs` transfer-input lookup: `throw Error("more than 1 src output")`, `throw Error("spending a stable temp-bad output ...")`, `throw Error("src output amount is not a number")` [4](#0-3) 
- `definition.js` inner-address / definition-template evaluation: `throw Error("more than 1 address definition")`, `throw Error("not 1 template")` [5](#0-4) 

All of these sit in the exact same unguarded async-callback shape as the DNS-parser crash class described by the CVE: an edge case in message content that the author assumed "can't happen" turns into an unhandled crash instead of a graceful rejection.

### Impact Explanation
Because `process.on('uncaughtException')` deliberately re-throws (`throw err;`) to kill the process, reaching any of these assertions with attacker-supplied unit content crashes the whole ocore node (full node or hub), not just a request handler. Every peer that receives/re-validates the crafted unit (it will be gossiped/broadcast like a normal unit) can be forced to crash simultaneously, which is a network-wide denial of service — "a network unable to confirm new units" if enough validating full nodes crash near-simultaneously on the same broadcast unit. This matches the "High" severity class assigned to the original crash CVE.

### Likelihood Explanation
Reaching most of these specific invariants (e.g. "more than 1 src output for the same unit/message_index/output_index", "more than 1 address definition matching a chash") requires satisfying several independent DB uniqueness assumptions the schema is expected to enforce, so a concrete step-by-step trigger for a *specific* one of them could not be fully confirmed by static review alone — DB schema constraints (`PRIMARY KEY`/`UNIQUE` indexes) may already prevent some of these rows from co-existing. This uncertainty is explicitly noted: without running the code against the real schema/indices, I cannot prove which specific `throw` is reachable with a single crafted, otherwise-passes-basic-checks unit. What is confirmed by code inspection is the general unsafe pattern (assert-via-throw inside unguarded async callbacks feeding straight into a process-crashing `uncaughtException` handler) is pervasive across the core unit-validation and AA/definition-evaluation code that is reachable by any peer posting a single unit.

### Recommendation
- Treat all "should never happen" internal-consistency checks in async DB callbacks (`checkForDoublespends`, `validatePaymentInputsAndOutputs`, `definition.js` evaluate/validateAuthentifiers, `validateAuthor`, etc.) as untrusted-input validation errors, not process-fatal assertions: replace `throw Error(...)` with `return cb(err_string)` / `callbacks.ifUnitError(...)` so they are handled the same way as any other invalid-unit rejection.
- Where these invariants genuinely indicate DB corruption rather than attacker input, wrap the surrounding logic so the exception is caught locally (e.g. `try { ... } catch(e) { return cb("internal error: " + e); }`) instead of letting it bubble to the global `uncaughtException` handler.
- Add fuzz/adversarial unit tests that specifically try to trigger each of these `throw` sites with a single crafted joint via `handlePostedJoint`/`validate()`, to confirm/rule out reachability, since static analysis alone cannot fully validate DB-uniqueness-dependent conditions.
- Consider hardening the top-level `uncaughtException` handler to attempt a controlled, per-connection failure (dropping/banning the offending joint and peer) rather than an unconditional process-wide crash, at least for exceptions raised from within unit-validation code paths.

### Proof of Concept
A concrete, fully-worked minimal reproduction unit could not be constructed with confidence from static analysis alone, because triggering the specific defensive `throw`s (e.g. `"conflicting spend proof spent from another address?"`, `"more than 1 src output"`, `"more than 1 address definition"`) depends on precise database state/uniqueness constraints that would need to be verified dynamically (e.g. in a running Devin/test session with the actual sqlite schema) to confirm which of these asserts is genuinely reachable from a single externally-supplied joint via `network.handlePostedJoint` → `validation.validate`. The mechanism itself — an unguarded `throw` inside an async `conn.query` callback in validation code, propagating to the process-crashing `process.on('uncaughtException')` handler in `network.js:4530-4543` — is directly confirmed by code inspection and is the load-bearing root cause of the analog DoS class.
