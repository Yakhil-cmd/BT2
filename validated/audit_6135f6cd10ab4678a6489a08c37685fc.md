### Title
Private Asset Transaction Details (Address, Amount, Blinding Factor) Are Written to Console/Log on Every Private Payment Validation - ([File: indivisible_asset.js])

### Summary
In `validatePrivatePayment` (indivisible_asset.js), every time a private (indivisible) asset payment element is validated — a routine, unconditional path executed whenever a node receives and processes a private payment chain — the full spend-proof input data is dumped to the console/log via `console.log("validation spend proof: "+JSON.stringify({...}))`. This mirrors the reported APM Server issue (CVE-2024-37286, CWE-532): sensitive payload content that is supposed to stay confidential ends up persisted in application logs as a side effect of normal request/validation handling.

### Finding Description
`validatePrivatePayment` is called for every private asset payment element a hub or wallet processes (e.g. via `network.handleOnlinePrivatePayment` → `privatePayment.validateAndSavePrivatePaymentChain` → `indivisibleAsset.validateAndSavePrivatePaymentChain` → `validatePrivatePayment`). [1](#0-0) 

For the "transfer" input branch, it constructs the spend proof, and immediately logs the underlying private data unconditionally, on the success path (not error handling): [2](#0-1) 

This log line prints `asset`, `unit`, `message_index`, `output_index`, `address`, `amount`, and `blinding` — the exact fields that private assets are designed to keep hidden from third parties (the whole point of the "hidden output"/blinding scheme in indivisible private assets is that `address`, `amount`, and `blinding` are not disclosed except to the parties in the private payment chain). By writing them to `console.log`, this confidential transaction data is duplicated into the node's stdout/log stream.

In typical ocore-based deployments (hubs, wallets run as daemons), stdout is commonly redirected to a persistent log file (via `pm2`, `forever`, `nohup`, or systemd journal capture), so this is not merely a transient console print — it becomes durable, on-disk sensitive data. Any operator, log aggregation pipeline, or third party with read access to that log file (which may have broader access controls than the database itself, e.g. shipped to centralized logging, included in support bug reports, or exposed via misconfigured log rotation/backup) can reconstruct private asset transaction details: which address received how much of a private asset, and the blinding factor that could aid de-anonymization or link outputs.

This is directly reachable by any private-asset sender or by anyone forwarding a private payment chain element to the node, since validation runs on all elements the node receives, not on operator-triggered maintenance actions.

### Impact Explanation
The private asset system's core confidentiality guarantee — that spend amounts, output addresses, and blinding factors are only known to chain participants — is undermined for any node that validates the payment (hubs, cosigner wallets, wallets restoring/handling forwarded chains). Log exposure of `amount`, `address`, and `blinding` allows reconstruction of private transaction graphs and amounts, a confidentiality break (CWE-532 analog) for the private-asset feature, even though the underlying database storage is otherwise protected.

### Likelihood Explanation
This is triggered on every validation of a private payment "transfer" input — an unauthenticated/normal-path event that occurs whenever any user sends or forwards a private asset payment through a hub or a receiving wallet. No special conditions or attacker privilege are required; it happens on the ordinary flow of private payments (network.js `handleOnlinePrivatePayment`, wallet.js `handlePrivatePaymentChains`), making it highly likely to occur in production for any active private-asset usage. [3](#0-2) 

### Recommendation
Remove or gate the `console.log("validation spend proof: "+JSON.stringify({...}))` statement in `indivisible_asset.js` (and audit similar debug logging elsewhere that prints raw private-payment payload fields, e.g. in `divisible_asset.js`/`private_payment.js`) behind an explicit debug flag that defaults to off, and never log `address`, `amount`, or `blinding` fields of private outputs in production logging paths.

### Proof of Concept
1. Configure a hub or wallet node with private-asset support and redirect stdout to a persistent log file (standard deployment practice, e.g. `node start.js >> app.log 2>&1`).
2. Have any user send a private (indivisible) asset payment with a "transfer" input to another user via the node (or forward a private payment chain to it, e.g. via `handlePrivatePaymentChains`/`handleOnlinePrivatePayment`).
3. Observe `app.log`: it contains a line `validation spend proof: {"asset":...,"address":...,"amount":...,"blinding":...}` exposing the recipient address, exact transferred amount, and the output's blinding factor — data meant to remain private to the sender/recipient/cosigners only. [4](#0-3)
