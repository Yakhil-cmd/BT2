### Title
Stack-scoped ApiClient token authorization bypass in CCMenu endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
### Finding Description
`Api::BaseController` defines the authorization invariant that an `ApiClient` scoped to a single stack (`current_api_client.stack_id?`) must only ever be able to resolve stacks from that restricted set: [1](#0-0) 

Every other stack-scoped API controller (`Api::StacksController`, `Api::DeploysController`, `Api::TasksController`, etc.) inherits `stack`, so the equality `stack a token authorises == stack it touches` always holds for them.

`Api::CCMenuController`, however, overrides `stack` and bypasses the scoped `stacks` collection entirely: [2](#0-1) 

It resolves the stack directly with `Stack.from_param!(params[:stack_id])` — a global, unscoped lookup — instead of `stacks.from_param!(params[:stack_id])`. The controller only enforces `require_permission :read, :stack`, which checks that the token's `permissions` array contains the string `read:stack`; it never checks that `params[:stack_id]` matches `current_api_client.stack_id`.

An `ApiClient` can legitimately be created scoped to exactly one stack through the normal, session-authenticated `ApiClientsController` (or the built-in CCMenu URL generator), with the explicit intent of restricting it to that single stack: [3](#0-2) 

Because `Api::CCMenuController#stack` never consults `current_api_client.stack_id`, any holder of such a stack-scoped, `read:stack`-only token can pass an arbitrary `stack_id` param and retrieve CI/deploy status (`deploys_and_rollbacks.last`, running/succeeded state) for **any** stack in the Shipit installation, not just the one the token was issued for.

Before vs. after invariant:
- Before (intended): `stack_id token authorises = {stack A}` ⇒ `stack_id it can read via CCMenu = {stack A}`
- After (actual): `stack_id token authorises = {stack A}` ⇒ `stack_id it can read via CCMenu = {any stack}`

### Impact Explanation
This breaks the "stack a token authorises vs. stack a token touches" binding and results in unauthenticated (relative to the target stack) read access to deploy/task status of stacks the token holder was never granted access to — matching the High-severity impact category "unauthenticated read of stack state, task streams or deploy output." It leaks CI/deploy state (success/failure, running status, last deploy id/time) across stack boundaries to a holder of a narrowly-scoped credential, defeating the purpose of stack-scoped tokens.

### Likelihood Explanation
Likelihood is high for any environment issuing stack-restricted ApiClient tokens (the documented/intended use case for the CCMenu integration is exactly to hand out narrowly-scoped, low-privilege tokens to third-party CI dashboard tools). Exploitation requires no special access beyond possessing one such legitimately-issued, low-privilege token and knowing/guessing another stack's `to_param` (owner/repo/environment), which is not secret information within a Shipit instance.

### Recommendation
Have `Api::CCMenuController#stack` use the inherited, scoped `stacks` collection instead of the raw `Stack` model, e.g.:

```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

so that stack-scoped tokens are constrained to their authorized stack, consistent with every other API controller.

### Proof of Concept
1. As an authorized Shipit user, create a stack-scoped ApiClient token for `stack_A` via `ApiClientsController#create` (or via the CCMenu "get URL" feature on `stack_A`'s page), granting only `read:stack`.
2. Using that token, call:
   `GET /api/stacks/:owner_B/:repo_B/:env_B/ccmenu.xml?token=<stack_A_token>`
   where `owner_B/repo_B/env_B` is any other stack in the instance.
3. Observe that `Api::CCMenuController#show` returns `stack_B`'s deploy/rollback status via `render('shipit/ccmenu/project', ... locals: { stack: stack_B, ... })`, even though the token was authorized only for `stack_A`. Compare this to calling `GET /api/stacks/:owner_B/:repo_B/:env_B` (handled by `Api::StacksController`, which uses the scoped `stacks.from_param!`), which correctly returns a 404 for the same token.
