Confirmed: `WebhooksController#verify_signature` selects which GitHub App config (and thus which HMAC `webhook_secret`) validates the request based on `repository_owner`, which reads `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). But every webhook `Handler` subclass (`app/models/shipit/webhooks/handlers/handler.rb`) resolves the target repository independently via `payload.dig('repository', 'full_name')`, which is then split into `owner/name` and looked up with `Repository.from_github_repo_name` in `app/models/shipit/repository.rb`. In a single-app configuration this is a non-issue since one `webhook_secret` is shared for everything, but in the documented multi-organization configuration (`Using Multiple Github Applications`, `docs/setup.md:182-209`, exercised in `test/dummy/config/secrets_double_github_app.yml`), each organization has its own independent `webhook_secret`.

### Title
Webhook signature verified against `repository.owner.login`'s secret while the actual target repository is taken from an independent `repository.full_name` field - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In a multi-organization Shipit deployment, `WebhooksController#verify_signature` picks the HMAC secret to validate a webhook using `repository.owner.login` (or `organization.login`), but the handlers that actually act on the payload resolve which `Repository`/`Stack` to operate on using the separate `repository.full_name` field. These two fields are never cross-checked against each other, so a payload signed with Organization B's webhook secret can still drive actions against Organization A's stacks if the two JSON fields are set inconsistently.

### Finding Description
`verify_signature` in [1](#0-0)  looks up the `Shipit::GitHubApp` (and its `webhook_secret`) via `repository_owner`: [2](#0-1) 

`Shipit.github(organization:)` resolves per-organization config in `github_app_config` [3](#0-2) , and the docs confirm each org has its own independent `webhook_secret` in the multi-app schema [4](#0-3) , with `test/dummy/config/secrets_double_github_app.yml` showing two distinct organizations each configured with their own (potentially attacker-controlled/leaked) `webhook_secret` [5](#0-4) .

Once signature verification passes, `WebhooksController#create` dispatches the parsed JSON body to handlers [6](#0-5) . Every handler subclass (e.g. `PushHandler`) determines the target repository not from `repository.owner.login` but from the independent `repository.full_name` field via `Handler#repository_name` and `#stacks`: [7](#0-6) 

`Repository.from_github_repo_name` then splits `full_name` on `/` to find the `owner`/`name` row independent of any organization context: [8](#0-7) 

The binding that should hold is: `organization whose secret authenticated the request == owner of the repository the handler acts on`. Because the controller derives the authenticating organization from `repository.owner.login`/`organization.login` while the handler derives the acted-upon repository from the unrelated `repository.full_name`, an attacker who knows or controls the `webhook_secret` for one configured organization (e.g. a low-trust org they administer, or one whose secret leaked) can craft a JSON body where `repository.owner.login` = their org (so verification uses their known secret) but `repository.full_name` = `"other-org/other-repo"` (so `PushHandler`, `StatusHandler`, etc. act on a Stack belonging to a different, higher-trust organization). This breaks the "org authenticated versus repo written" binding called out in scope.

### Impact Explanation
This lets an unprivileged holder of one org's webhook secret drive `GithubSyncJob`/status updates and other webhook side effects against stacks belonging to a completely different GitHub organization/repository configured in the same Shipit install — a cross-repository write through the org boundary the signature is supposed to enforce. Depending on which handler is triggered (`push`, `status`, `check_suite`, `merge_status`, etc.) this can affect merge-queue state, commit status, or synchronization of an unrelated repository's Stack without that repository's own organization ever authenticating the request.

### Likelihood Explanation
This requires operating a multi-organization Shipit deployment (documented, supported configuration) and possessing/controlling the `webhook_secret` of at least one of the configured organizations — plausible for an org admin of a lower-trust tenant org in a shared Shipit instance, or if that org's secret leaks. No GitHub App private key, session, or `ApiClient` token is required; only the ability to send an HTTP POST with a valid HMAC for one org's secret.

### Recommendation
After resolving the GitHub App used for signature verification via `repository.owner.login`, re-validate that `repository.full_name`'s owner segment matches that same organization before dispatching to any `Handler`; reject the webhook (422) on mismatch instead of relying solely on `repository.owner.login` while handlers independently trust `repository.full_name`.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgOne` and `OrgTwo`, each with a distinct `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`), and a Stack for repository `orgone/target-repo`.
2. As an entity that knows `OrgTwo`'s `webhook_secret` (e.g. an admin of `OrgTwo`'s own low-trust repo), craft a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "OrgTwo" }, "full_name": "orgone/target-repo" }
}
```
3. Compute `X-Hub-Signature` as `sha1=HMAC-SHA1(OrgTwo_webhook_secret, body)` and POST to `/github/webhooks`.
4. `verify_signature` resolves `repository_owner` = `"OrgTwo"`, loads `OrgTwo`'s app, and successfully verifies the signature against the attacker-known secret.
5. `PushHandler#stacks` resolves the target via `repository.full_name` = `"orgone/target-repo"`, finds `OrgOne`'s stack, and enqueues `GithubSyncJob`/sync against it — despite the request never having been authenticated by anything belonging to `OrgOne`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
