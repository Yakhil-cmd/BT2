### Title
Unchecked `u64::try_from(...).unwrap()` casts in `deposit`/`withdraw` panic when vault balance is inflated relative to `lp_supply`, permanently freezing deposits and withdrawals - (File: `programs/cp-swap/src/instructions/deposit.rs`, `programs/cp-swap/src/instructions/withdraw.rs`)

### Summary
`deposit` and `withdraw` compute `token_0_amount`/`token_1_amount` as `u128` values via `CurveCalculator::lp_tokens_to_trading_tokens` and then downcast them to `u64` with `u64::try_from(results.token_0_amount).unwrap()` [1](#0-0) [2](#0-1) . This is the same downcast-without-checked-conversion pattern as the referenced Notional finding (`vaultShares.toUint80()`), except here the panic can be triggered not just by an oversized deposit request but by anyone donating tokens directly to the pool's token vault, which inflates the vault balance relative to `lp_supply` and causes the computed trading-token amount to exceed `u64::MAX` for essentially any subsequent deposit or withdrawal.

### Finding Description
The pool tracks reserves purely via the live SPL token balance of `token_0_vault`/`token_1_vault`, read through `vault_amount_without_fee` in `deposit`/`withdraw` [3](#0-2) [4](#0-3) . These vault accounts are ordinary SPL token accounts (owned by the pool's PDA authority) whose address is deterministic and public [5](#0-4) ; any unprivileged actor can perform a normal SPL token transfer directly into these vault accounts without going through `deposit`, inflating the on-chain balance without minting any corresponding LP tokens and without changing `lp_supply`.

`lp_tokens_to_trading_tokens` computes `token_0_amount = lp_token_amount * token_0_vault_amount / lp_token_supply` in `u128` [6](#0-5) . Once the vault balance is inflated relative to `lp_supply` (e.g., by directly donating a very large amount of tokens to the vault), this ratio can grow arbitrarily large, so even a normal/small `lp_token_amount` deposit request yields a `token_0_amount`/`token_1_amount` result that exceeds `u64::MAX`. The subsequent `u64::try_from(results.token_0_amount).unwrap()` then panics instead of returning a graceful error [1](#0-0) [7](#0-6) . The identical pattern exists in `withdraw` [2](#0-1) [8](#0-7) , meaning existing LPs' attempts to redeem their LP tokens for the underlying assets would also panic and revert.

Because the vault balance stays inflated indefinitely (there is no mechanism that reconciles/burns the donated tokens or corrects the ratio), this is not a self-inflicted, one-off failure limited to the attacker's own transaction (as in a plain "large-input reverts" case) — it permanently distorts the deposit/withdraw math for the whole pool going forward, exactly analogous to how the Notional report's low `totalPoolClaim` permanently skewed the vault-share ratio for all future depositors.

### Impact Explanation
Once the vault-to-lp_supply ratio is skewed via a donation, both `deposit` and `withdraw` for that pool will panic and revert for any legitimate participant whose implied `token_0_amount`/`token_1_amount` exceeds `u64::MAX` on either token side. Because `withdraw` uses the same unchecked cast, this can permanently trap existing LPs' funds in the pool (freezing of user/LP funds), not merely block new deposits. This satisfies "permanent freezing of user or LP funds" from an unprivileged, single-transaction donation.

### Likelihood Explanation
The donation-based ratio manipulation requires only a standard SPL token transfer to a publicly-derivable PDA vault address — no special permissions, no protocol interaction, and it can be performed by any account holding (or able to flash-acquire) a sufficiently large amount of one of the pool's tokens. For low-decimal or low-supply/low-liquidity tokens (or freshly created pools with small `lp_supply`, e.g., right after `initialize` where a large fraction of supply is the 100-unit locked minimum), the amount needed to push the ratio past `u64::MAX` thresholds is realistically attainable, making this a practical, not purely theoretical, attack. It also does not depend on any privileged signer, malicious validator, or non-default feature build.

### Recommendation
Replace `u64::try_from(...).unwrap()` in both `deposit.rs` and `withdraw.rs` with a checked conversion that returns a proper program error (e.g., `.map_err(|_| ErrorCode::MathOverflow)?` or via `DownCast::to_u64()` which already exists in `programs/cp-swap/src/utils/math.rs` [9](#0-8) ) instead of panicking. Additionally, consider hardening reserve accounting against direct-transfer donation attacks (e.g., tracking reserves in `PoolState` rather than trusting the live token account balance, or reconciling/sweeping unexpected vault surplus) so a single donation transaction cannot permanently distort the deposit/withdraw exchange rate for the whole pool.

### Proof of Concept
1. A pool is initialized with `token_0_vault`/`token_1_vault` balances and `lp_supply` set at `initialize` time (with 100 LP tokens locked) [10](#0-9) .
2. An attacker performs a plain SPL `Transfer` (not via the `deposit` instruction) sending a very large amount of `token_0` directly to `token_0_vault`'s address, which is a publicly derivable PDA `[POOL_VAULT_SEED, pool_state, token_0_mint]` [11](#0-10) . This does not go through `deposit`, so `lp_supply` is untouched, but `vault_amount_without_fee` will now report the inflated balance [3](#0-2) .
3. Any subsequent user calls `deposit` with even a small `lp_token_amount`. `lp_tokens_to_trading_tokens` computes `token_0_amount = lp_token_amount * inflated_vault_amount / lp_supply`, which now exceeds `u64::MAX` [6](#0-5) .
4. `u64::try_from(results.token_0_amount).unwrap()` panics, reverting the transaction and blocking all further deposits [1](#0-0) .
5. Existing LP holders attempting `withdraw` hit the same panic at `token_0_amount = u64::try_from(results.token_0_amount).unwrap()` in `withdraw.rs`, freezing their previously deposited funds [2](#0-1) .

impl DownCast for u128 {
    fn to_u64(&self) -> Option<u64> {
        if *self > u64::MAX as u128 {
            None
        } else {
            Some(*self as u64)
        }
    }
