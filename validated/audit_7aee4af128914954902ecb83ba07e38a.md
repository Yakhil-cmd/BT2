### Title
Webhook signature is verified against the org derived from `repository.owner.login`/`organization.login`, but event handlers act on unrelated payload fields (`sha`, `repository.full_name`) — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App/organization's `webhook_secret` to validate the request against using a field taken from the same untrusted JSON body (`repository.owner.login`, falling back to `organization.login`), then verifies the raw body HMAC using that org's secret. Once verification passes, the handlers dispatched from the very same body do not re-check that the org used for signing matches the resource actually mutated: `StatusHandler` looks up commits by `sha` across the entire `Commit` table with no repository/organization scoping at all, and other handlers key off `repository.full_name`, a separate field that is never cross-checked against `repository.owner.login`.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb` computes: [1](#0-0) [2](#0-1) 

`repository_owner` is read out of the JSON body and used solely to pick the GitHub App config (`Shipit.github(organization: repository_owner)`), which supplies the `webhook_secret` used in `verify_webhook_signature`: [3](#0-2) 

This design assumes one org = one secret = one set of repositories, which is explicitly supported for Shipit installations serving multiple GitHub orgs (`docs/setup.md`, "Using Multiple Github Applications"). However, nothing binds the *value* used to select the secret (`repository.owner.login`) to the fields the handlers actually operate on. In `StatusHandler`, the mutated record is selected purely by commit SHA, with no repository or owner filter whatsoever: [4](#0-3) 

Other handlers (`PushHandler`, `PullRequest::*Handler`, `CheckSuiteHandler`) resolve the target repository via `Handler#repository_name`, which reads `repository.full_name` — a distinct field from `repository.owner.login`: [5](#0-4) [6](#0-5) 

Because the same attacker-supplied JSON body supplies both fields, and no code compares them, an operator who legitimately controls one configured organization (and therefore legitimately knows that org's `webhook_secret`) can produce a validly-signed payload whose `repository.owner.login`/`organization.login` equals their own org (so it passes `verify_signature` against their own org's secret) while `repository.full_name` — or, for `status` events, the raw `sha` — targets a completely different, victim organization's repository/commit that is configured under a different secret in the same Shipit instance.

The binding that should hold but doesn't:
`organization authenticated by verify_signature == organization owning the repository/commit acted on by the handler`

Concretely for `status` events this is even weaker than a full org check — there is no repository scoping at all, so any org's known secret can forge a CI status for **any** commit SHA present in the database, regardless of which repository/org it belongs to.

### Impact Explanation
This breaks a deployment-trust binding explicitly called out as in-scope: "an organization that authenticated versus the repository that is written." A `status` webhook forged this way calls `Commit#create_status_from_github!`, which updates `Status::Group` state used by `Commit#deployable?` (`success? && !blocked?`) and can trigger `stack.schedule_merges` / `ContinuousDeliveryJob` when the new status is `success`: [7](#0-6) [8](#0-7) [9](#0-8) 

An attacker who is a legitimate, low-privileged administrator of only one of several GitHub organizations hosted by a shared Shipit instance can therefore forge a "success" CI status for a victim organization's commit, unblocking `deployable?` and triggering continuous-delivery/merge flows for a repository they have no access to — i.e., an unauthorized deploy/merge on a cross-organization repository, satisfying the "unauthorized deploy" Critical-impact criterion.

### Likelihood Explanation
Requires (a) a multi-organization Shipit deployment (explicitly documented and supported), and (b) the attacker being a legitimate low-privilege operator/admin of at least one of the configured organizations — not a Shipit user, `ApiClient`, or holder of any victim-org credential. This is a realistic operating model for shared Shipit instances serving multiple teams/orgs, and the crafting of the forged payload requires no more than standard HMAC signing knowledge of the attacker's own already-known secret.

### Recommendation
After `verify_signature` succeeds, re-derive the authorized organization and enforce it in every handler: reject (or scope queries) unless the repository resolved by the handler (via `full_name` or via the commit's `stack.repository.owner`) belongs to the same organization that was used to select the `webhook_secret`. For `StatusHandler` in particular, scope `Commit.where(sha:)` by `stack.repository`/owner matching `repository_owner`/`organization_login` from the verified request context, not merely by global SHA.

### Proof of Concept
1. Configure Shipit with two orgs, `attacker-org` and `victim-org`, each with distinct `webhook_secret`s (per `docs/setup.md` multi-org setup).
2. As the legitimate admin of `attacker-org`'s GitHub App, obtain `attacker-org`'s `webhook_secret` (this is normal, authorized access to your own org's app settings).
3. Craft a `status` event JSON body:
   ```json
   {
     "sha": "<victim commit sha, known/guessable/observed>",
     "state": "success",
     "organization": { "login": "attacker-org" }
   }
   ```
4. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org secret, body)>` and POST to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `attacker-org`'s app, and successfully verifies the signature (`lib/shipit/github_app.rb#verify_webhook_signature`).
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and applies the forged `success` status to the victim's commit, regardless of organization, potentially unblocking deploy/merge flows on `victim-org`'s stack.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
