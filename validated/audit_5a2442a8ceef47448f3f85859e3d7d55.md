### Title
RAY-scaled total value overflows i128 during accrual, permanently freezing all operations on a large market - (File: contracts/pool/src/interest.rs)

### Summary
The pool accrues interest before every operation (`supply`, `borrow`, `withdraw`, `repay`, `liquidate`, `flash_loan`, `update_indexes`). During accrual, `scaled_to_original` multiplies scaled balances (RAY domain) by the borrow/supply index. When `scaled * index` exceeds `i128::MAX`, the fixed-point helper panics with `MathOverflow`. Because the panic happens inside the mandatory accrual step, the market becomes permanently frozen — no repayment, withdrawal, or liquidation can ever execute — even though the borrow index is still far below its configured `MAX_BORROW_INDEX_RAY` ceiling.

### Finding Description
Every pool operation routes through `global_sync` (`contracts/pool/src/interest.rs:20-33`), which calls `accrue_chunk` → `accrue_step` (`interest.rs:39-53`). Accrual values the book by unscaling: `scaled_to_original(env, borrowed, borrow_index)` and `scaled_to_original(env, supplied, supply_index)` (`contracts/pool/src/cache/scale.rs:23-24`), which perform `scaled * index / RAY` with checked `i128` arithmetic (`common/src/math/fp.rs`, `fp_core::mul_div_*`).

The documented numeric limit (`docs/reference/formulas.md:429-437`) confirms: "Value overflow can occur before the index ceiling and block repayment/withdrawal because those operations accrue first." The in-repo harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:315-361`) proves the end state: after the accrual panic at `scaled_to_original`, `try_withdraw_raw` and `try_repay` both fail with `MATH_OVERFLOW`, and `borrow_index < MAX_BORROW_INDEX_RAY` — the index cap that would stop interest growth never engages because the value multiplication overflows first.

An unprivileged address reaches this path by supplying tokens and borrowing to high utilization, then letting time pass — the same flow as any user; `update_indexes` itself is an unprivileged entrypoint and is the first call to trap. Once the panic occurs the state is stored with the accrued-revenue/index progression aborted, but the triggering condition (scaled balances × index > i128::MAX) is monotonic — indexes only grow while debt is outstanding, and debt cannot be repaid because repayment accrues first. There is no admin-free or privileged escape documented; the market is frozen.

### Impact Explanation
Permanent freezing of funds and protocol insolvency on the affected market: suppliers cannot withdraw, borrowers cannot repay, liquidators cannot liquidate underwater positions, and bad-debt cleanup (`clean_bad_debt`/`recapitalize` paths also accrue first) cannot run. All supplied liquidity and collateral accounting in that `(hub, token)` book is bricked while tokens remain locked in the pool.

### Likelihood Explanation
Requires an unusually large market: the RAY value ceiling is `i128::MAX ≈ 170 × 10^36`, i.e. roughly 170 billion whole tokens at index 1, or proportionally less at higher indexes (the test uses 1 billion 18-decimal tokens — `1e36` raw — and needs the borrow index to exceed ~170×, reached in a few years on the steep segment of the XLM-style curve at ~98% utilization). The scenario is realistic for a whale-scale market under sustained high utilization, not something an attacker can force instantly, but it is also reachable through organic growth on any market whose scaled value approaches the ceiling — a real, demonstrated liveness failure, which justifies Medium.

### Recommendation
Widen the total-value computation to the exact `I256` path in `accrue_step`/`scaled_to_original` (the codebase already uses `I256` in `fp_core::mul_div` fallback paths — see `certora/common/spec/rate_index_accounting_rules.rs:366-409` where the widened variant exists specifically because `borrowed * new_index` overflows `i128`), or clamp accrued growth when the unscaled book value approaches `i128::MAX` so accrual degrades gracefully instead of panicking. At minimum, engage the `MAX_BORROW_INDEX_RAY` index cap before the value ceiling can be crossed, or gate accrual so that a saturated index still permits repay/withdraw/liquidate to execute.

### Proof of Concept
From `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-361` (unprivileged `supply`/`borrow`/`update_indexes`/`withdraw`/`repay` calls only):

```rust
let mut t = LendingTest::new()
    .with_market(big("BIG18", 18, xlm_curve()))
    .with_market(col())
    .with_max_utilization_disabled_all_markets()
    .build();
lift_caps(&t, "BIG18", 18);
lift_caps(&t, "COL", 7);
let principal = BILLION * 10i128.pow(18);          // 1e36 raw ray
t.supply_raw(BOB, "BIG18", principal);             // unprivileged supply
let debt = principal / 100 * 98;                   // 98% utilization
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", debt);                // unprivileged borrow

loop {
    t.advance_time(YEAR_SECS);
    if let Err(e) = t.try_update_indexes_for(&["BIG18"]) { break e; }
}
// e == MATH_OVERFLOW raised inside scaled_to_original
// borrow_index < MAX_BORROW_INDEX_RAY — cap never engaged
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```

Every subsequent `withdraw`, `repay`, `liquidate`, `borrow`, `supply`, or `update_indexes` on `BIG18` reverts in the accrual preamble, permanently locking supplier funds and borrower collateral.
