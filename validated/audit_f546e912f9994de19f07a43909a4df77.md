### Title
Silent CL Staking Info Overwrite When Multiple Nodes Share a Reward Address Corrupts Staking Reward Distribution - (`kaiax/staking/staking_info.go`)

---

### Summary

In `consolidateNodes()`, when two validator nodes registered in the AddressBook share the same `RewardAddr` and both have consensus-liquidity (CL) staking registered in the CLRegistry, the second node's `CLStakingInfo` silently overwrites the first. The dropped CL pool receives zero staking rewards, and the surviving CL pool and the CN reward address receive inflated rewards because the missing CL staking amount is absent from the denominator in `Split()`.

---

### Finding Description

`consolidateNodes()` in `kaiax/staking/staking_info.go` first merges all AddressBook entries that share a `RewardAddr` into a single `consolidatedNode`, correctly summing their `StakingAmount` values. It then attaches CLStakingInfos by iterating over `si.CLStakingInfos` and writing directly into the map:

```go
// kaiax/staking/staking_info.go lines 150-160
if len(si.CLStakingInfos) > 0 {
    for _, clsi := range si.CLStakingInfos {
        if r, ok := nToR[clsi.CLNodeId]; ok {
            // One CLStakingInfo per validator is guaranteed by CLRegistry.
            cmap[r].CLStakingInfo = clsi   // ← plain assignment, not accumulation
        }
    }
}
```

The comment "One CLStakingInfo per validator is guaranteed by CLRegistry" is true at the *NodeId* level: the CLRegistry ensures each NodeId has at most one CL pool. However, the AddressBook explicitly supports multiple NodeIds sharing the same `RewardAddr` (the whole purpose of consolidation). When NodeId `n1` and NodeId `n3` both map to `RewardAddr r1` and both have CL pools registered in the CLRegistry, the loop processes them sequentially and the second assignment overwrites the first. The test in `staking_info_test.go` lines 243–271 confirms this behaviour and labels it "not feasible in real" — but that assumption is incorrect: the CLRegistry is keyed by NodeId, not by RewardAddr, so nothing prevents two NodeIds with the same RewardAddr from each registering a CL pool.

After consolidation, `consolidatedNode.Split()` (lines 169–187) uses only the surviving `CLStakingInfo.CLStakingAmount` as the CL portion of the denominator:

```go
cnAmountBig = big.NewInt(int64(c.StakingAmount))                    // a1 + a3 (correct)
clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))    // only clStakingAmount2 (wrong)
totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
clAmount    = clAmountBig * amount / totalAmount
cnAmount    = amount - clAmount
```

`assignStakingRewards` (lines 486–534) and `assignStakingRewardsFlex` (lines 421–484) both call `Split()` and write the result with plain map assignment:

```go
alloc[cn.RewardAddr]              = cnAmount
alloc[cn.CLStakingInfo.CLPoolAddr] = clAmount
```

The dropped CL pool address is never written into `alloc`, so it receives zero KAIA.

---

### Impact Explanation

For a validator operator who runs two nodes (`n1`, `n3`) under the same `RewardAddr r1`, each with its own CL pool (`clPool1`, `clPool2`):

- `clPool1` (the overwritten entry) receives **zero** staking rewards every block.
- `clPool2` and `r1` receive **inflated** rewards because `clStakingAmount1` is absent from the denominator in `Split()`, making the total appear smaller than it is.
- The mismatch is permanent for every block processed while this configuration exists.

This is an unauthorized redistribution of KAIA staking rewards: funds that should flow to `clPool1` are silently redirected to `clPool2` and `r1`.

---

### Likelihood Explanation

The AddressBook has always supported multiple NodeIds sharing a single `RewardAddr` (the consolidation feature exists precisely for this). The CLRegistry (introduced at Prague) allows any registered NodeId to have a CL pool. A validator who operates two nodes under one reward address and registers CL pools for both — a natural operational pattern — triggers this bug automatically. No adversarial action is required; the validator's own valid on-chain configuration is sufficient.

---

### Recommendation

Replace the plain assignment with accumulation. The `consolidatedNode` struct should hold a slice of `CLStakingInfo` entries (one per contributing NodeId), and `Split()` should sum all CL amounts:

```go
// In consolidateNodes:
if r, ok := nToR[clsi.CLNodeId]; ok {
    cmap[r].CLStakingInfos = append(cmap[r].CLStakingInfos, clsi)
}

// In Split():
totalCL := uint64(0)
for _, cl := range c.CLStakingInfos {
    totalCL += cl.CLStakingAmount
}
// distribute proportionally to each CL pool
```

Alternatively, if the protocol intends to support at most one CL pool per consolidated validator, enforce that constraint explicitly (return an error or log a warning and skip the second entry) rather than silently overwriting.

---

### Proof of Concept

**Setup (Prague hardfork active, `reward.kip82ratio = 20/80`):**

| Entity | Role | Staking |
|---|---|---|
| `n1` | NodeId, RewardAddr = `r1` | 6 000 000 KAIA |
| `n3` | NodeId, RewardAddr = `r1` | 4 000 000 KAIA |
| `clPool1` | CL pool for `n1` | 3 000 000 KAIA |
| `clPool2` | CL pool for `n3` | 2 000 000 KAIA |
| `minStake` | | 5 000 000 KAIA |

**Expected behaviour:**
- Combined CN staking = 10 000 000 KAIA; combined CL staking = 5 000 000 KAIA; total = 15 000 000 KAIA.
- `Split(stakersReward)` should yield: CN = 10/15, `clPool1` = 3/15, `clPool2` = 2/15.

**Actual behaviour after `consolidateNodes()`:**
- `cmap[r1].CLStakingInfo` = `{n3, clPool2, 2_000_000}` (n1's entry overwritten).
- `Split(stakersReward)` uses denominator = 10 000 000 + 2 000 000 = 12 000 000.
- CN receives 10/12 of `stakersReward` (inflated).
- `clPool2` receives 2/12 of `stakersReward` (inflated).
- `clPool1` receives **0** (never written to `alloc`).

The 3 000 000 KAIA staked in `clPool1` earns nothing, and the 3/15 share that should have gone to `clPool1` is redistributed to `r1` and `clPool2`. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)

```go
func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
	if c.CLStakingInfo == nil {
		return amount, big.NewInt(0)
	}

	var (
		cnAmountBig = big.NewInt(int64(c.StakingAmount))
		clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
		totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
	)

	clAmount := new(big.Int).Mul(clAmountBig, amount)
	clAmount = clAmount.Div(clAmount, totalAmount)

	// The remaining amount is for the CN.
	cnAmount := big.NewInt(0).Sub(amount, clAmount)

	return cnAmount, clAmount
}
```
