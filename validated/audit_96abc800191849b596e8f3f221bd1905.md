### Title
Webhook signature is verified against the organization named in the payload while the write path trusts an unrelated `repository.full_name`/`sha` from the same untrusted payload - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App (and therefore which `webhook_secret`) to verify the `X-Hub-Signature` against by reading `repository_owner` straight out of the untrusted, attacker-supplied JSON body: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`, then calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`. [1](#0-0) 

Once the signature check passes, `create` dispatches the *entire raw payload* to every registered handler for the event, with no re-binding to the organization that was actually used to authenticate the request: [2](#0-1) 

Downstream handlers then derive the target repository/commit from a *different* field of that same untrusted payload:
- `Handlers::Handler#stacks` resolves the target via `payload.dig('repository', 'full_name')` [3](#0-2) , used unchanged by `PushHandler#process` [4](#0-3)  and by pull-request handlers such as `OpenedHandler#repository` / `ClosedHandler#repository` [5](#0-4) [6](#0-5) .
- `StatusHandler#process` doesn't even use the repository at all — it looks up commits **globally by `sha`**: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [7](#0-6) .

This creates exactly the ambiguous-binding pattern described in the analog report: "the organization that authenticated" (`repository.owner.login`, used only to pick the `webhook_secret`) is never checked to equal "the repository/commit that is written" (`repository.full_name` or bare `sha`, used by the handlers). Nothing in `verify_signature` or `create` asserts `repository.owner.login == repository.full_name.split('/').first`.

In the documented multi-tenant configuration ("Using Multiple Github Applications", `docs/setup.md`), each GitHub organization onboarded onto the same Shipit instance gets its own `webhook_secret` [8](#0-7) . An org administrator who legitimately possesses their own org's `webhook_secret` (a value they set themselves when creating their GitHub App, and which is not considered privileged with respect to *other* tenants) can compute a valid `X-Hub-Signature` for a payload whose `repository.owner.login` is their own org (so `verify_signature` passes), while setting `repository.full_name` (or `sha`) to point at a completely different, victim organization's repository/commit that is also hosted on the same shared Shipit instance.

### Impact Explanation
This breaks the deployment-trust binding "organization authenticated == repository written," enabling cross-tenant/cross-repository writes with only one tenant's webhook secret:
- Via `StatusHandler`, an attacker can forge a passing (or failing) CI status for *any* commit sha tracked by Shipit across all tenants, since the lookup is a bare `Commit.where(sha:)` with no repository/tenant scoping [7](#0-6) . Because `MergeRequest#any_status_checks_failed?` / `#any_status_checks_missing?` gate `merge!`, which calls `stack.github_api.merge_pull_request(...)` with the app's own GitHub token [9](#0-8) , injecting a fake passing status for a victim tenant's PR head commit can help satisfy the merge queue's CI gate and contribute to an unauthorized merge on a repository the attacker never had signature access to.
- Via `PushHandler`/pull-request handlers, an attacker can trigger `sync_github`, archive/create review stacks, or otherwise mutate Shipit's model of a victim tenant's repository [4](#0-3) [10](#0-9) , using only their own tenant's `webhook_secret`.

This matches the "Critical/High" bar in the rules: cross-repository writes and contribution toward an unauthorized merge, achieved purely by crossing the organization/repository trust boundary that the signature check was supposed to enforce.

### Likelihood Explanation
Requires only the ability to sign a webhook payload with a `webhook_secret` for one tenant configured on a shared, multi-organization Shipit instance — a value the tenant's own administrator legitimately controls for their own org, not a secret belonging to the victim. No GitHub App private key, no `ApiClient` token, and no Shipit session are needed; the attacker interacts only with the public `/webhooks` endpoint. The likelihood is bounded by how commonly the "Using Multiple Github Applications" multi-tenant setup is deployed, but the engine explicitly documents and supports this configuration.

### Recommendation
In `WebhooksController#verify_signature`, after signature verification, additionally assert that the organization used to select the `webhook_secret` (`repository_owner`) matches the owner segment of `repository.full_name` (or, for org-scoped events, the `organization.login`) that the dispatched handlers will actually act on, and reject the request (422) on mismatch. Equivalently, pass the authenticated `repository_owner` down into the handler dispatch path and have `Handler#stacks`/`StatusHandler#process` scope their lookups to that authenticated owner instead of trusting `payload['repository']['full_name']` or a bare `sha` independently.

### Proof of Concept
1. Configure Shipit for two tenants in `config/secrets.yml` per `docs/setup.md`'s multi-app section: `orgB` (attacker-administered) and `orgA` (victim), each with a distinct `webhook_secret` [8](#0-7) .
2. As the administrator of `orgB`, compute `X-Hub-Signature: sha1=HMAC(orgB_webhook_secret, body)` for a crafted `status` event body:
```json
{
  "repository": { "owner": { "login": "orgB" }, "full_name": "orgB/some-repo" },
  "sha": "<victim commit sha belonging to orgA/victim-repo, tracked by its stack>",
  "state": "success",
  "context": "ci/required-check"
}
```
3. POST to `/webhooks` with header `X-Github-Event: status`. `verify_signature` resolves `repository_owner = "orgB"`, fetches `orgB`'s `webhook_secret`, and the signature validates successfully [11](#0-10) .
4. `StatusHandler#process` executes `Commit.where(sha: params.sha)`, finds the victim's commit belonging to `orgA/victim-repo` (no ownership check), and records a synthetic passing status on it [7](#0-6) , potentially unblocking `orgA`'s merge queue for that commit despite the attacker never possessing `orgA`'s `webhook_secret`.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently.
