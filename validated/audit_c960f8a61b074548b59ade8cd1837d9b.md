### Title

Medium: RAY-scaled market totals can overflow `i128` and permanently freeze a market - (File: `common/src/rates/index.rs`)

### Summary

The pool stores aggregate supply and debt as `i128` RAY-scaled shares, then converts them to live values by multiplying by the supply or borrow index; a book admitted under the configured cap can therefore become unrepresentable as the index grows. [1](#0-0) [2](#0-1)  The index ceilings bound the index itself, not `scaled_shares * index`, so accrual can panic before either ceiling is reached. [3](#0-2) [4](#0-3)  Because every pool operation synchronizes interest before mutating the market, the first overflowing accrual prevents repayment, withdrawal, liquidation, and later index updates. [5](#0-4) [6](#0-5) 

### Finding Description

`scaled_to_original` delegates to `Ray::mul`, whose underlying `mul_div_*` helpers panic with `MathOverflow` when the exact result does not fit in `i128`. [1](#0-0) [7](#0-6)  During utilization and supply-index updates, the pool calculates `supplied * supply_index`; debt accrual similarly calculates `borrowed * old_borrow_index` and `borrowed * new_borrow_index`. [8](#0-7) [9](#0-8) 

The configured asset cap only proves that the deposit's initial asset-to-RAY conversion fits in `i128`; it does not reserve headroom for future index growth. [10](#0-9) [11](#0-10)  For example, `max_cap_for_decimals(7)` is `1_701_411_834_604_692_317` base units, whose initial RAY value is already close to `i128::MAX`; a very small subsequent increase in the supply index makes `supplied * supply_index` unrepresentable. [12](#0-11) [13](#0-12) 

An unprivileged caller can reach this through `Controller::supply(caller, account_id = 0, spoke_id, assets = [(hub_asset, amount)])`, followed by `Controller::borrow(caller, account_id, borrows = [(hub_asset, borrow_amount)], to = None)` against collateral. [14](#0-13)  After the accrual threshold is crossed, `Controller::update_indexes` with `hub_assets = [hub_asset]`, `repay(caller, account_id, payments = [(hub_asset, 1)])`, `withdraw(caller, account_id, withdrawals = [(hub_asset, 1)], to = None)`, or `liquidate(liquidator, account_id, debt_payments, seize_mode)` all route through a market sync and revert. [15](#0-14) [16](#0-15) 

### Impact Explanation

Once `supplied * supply_index` or `borrowed * borrow_index` exceeds `i128::MAX`, `interest::global_sync` panics before `mark_accrued` or `commit` can execute, so the stale `last_timestamp` remains stored. [6](#0-5) [17](#0-16)  Every subsequent repayment, withdrawal, deposit, liquidation leg, or index update repeats the same overflowing accrual and rolls back. [18](#0-17) [19](#0-18) 

The result is permanent freezing of supplier principal and yield, inability for borrowers to repay, and inability for liquidators to close risky positions in that market absent a privileged contract upgrade. [20](#0-19) [21](#0-20) 

### Likelihood Explanation

The attack requires a market whose configured cap, token liquidity, collateral value, and utilization permit aggregate scaled shares to approach `i128::MAX / index`; it is therefore capital-intensive and market-dependent rather than universally reachable. [22](#0-21) [4](#0-3)  However, the caps currently validate only the initial conversion domain and admit values near `i128::MAX` for lower-decimal assets, while a large borrower can generate the nonzero accrual needed to move an index across the overflow boundary. [23](#0-22) [24](#0-23) 

The repository already contains a regression test in which a 98%-utilized whale market reaches this overflow before the borrow-index ceiling, after which both withdrawal and repayment fail with `MathOverflow`. [25](#0-24) [21](#0-20) 

### Recommendation

Use `I256` for aggregate `scaled_shares * index` calculations, or clamp each market's indexes at a dynamic safe bound such as `i128::MAX / max(total_supply_shares, total_debt_shares)` before unscaling totals. [26](#0-25) [27](#0-26)  Recompute that bound whenever supply, debt, or revenue shares change, including protocol-fee minting and bad-debt socialization. [28](#0-27) [29](#0-28) 

Add a recovery accrual path that can clamp indexes without first calculating an overflowing total, so existing oversized markets can still process withdrawals and repayments. [16](#0-15) [30](#0-29)  Finally, express cap validation in terms of the maximum representable scaled-share/index product rather than only `Ray::from_asset(amount)`. [31](#0-30) [32](#0-31) 

### Proof of Concept

1. Choose a listed seven-decimal market `A = HubAssetKey { hub_id, asset }` whose configured supply cap is at or near `max_cap_for_decimals(7) = 1_701_411_834_604_692_317` base units. [12](#0-11) 
2. Call `Controller::supply(attacker, 0, spoke_id, vec![(A, cap)])`; the resulting `supplied` RAY value fits at index `RAY` but has almost no `i128` headroom. [33](#0-32) [34](#0-33) 
3. Supply sufficient collateral and call `Controller::borrow(attacker, account_id, vec![(A, borrow_amount)], None)`, with `borrow_amount` near the maximum allowed by reserves, utilization, and the 2% liquidation buffer. [35](#0-34) [24](#0-23) 
4. Let interest accrue until either `supplied * supply_index` or `supplied * supply_index + rewards` exceeds `i128::MAX`; for a near-maximum seven-decimal cap, the multiplicative threshold is only slightly above index `1.0`. [27](#0-26) [36](#0-35) 
5. Call `Controller::update_indexes(vec![A])`, or have any user call `repay(caller, borrower_id, vec![(A, 1)])` or `withdraw(supplier, supplier_id, vec![(A, 1)], None)`; each call invokes `synced_market` and reverts inside accrual. [5](#0-4) [16](#0-15) 
6. Repeating the calls cannot clear the condition because neither debt shares nor supply shares can be reduced until after the same overflowing accrual completes. [18](#0-17) [19](#0-18)

```markdown
A cap is in native token units. Entry compares stored scaled usage plus the
new scaled amount with the cap floor-converted at the current index. Zero cap
allows no positive exposure. Exits subtract usage without checking caps;
missing usage rows and zero exit deltas are no-ops. Cap→scaled conversion

open instead of trapping. A saturated scaled cap does not enforce the
configured asset-unit limit. An admitted cap saturates only at an index below
one RAY. Only a bad-debt write-down moves the supply index below one RAY; at
its floor (`RAY / 1000`), a supply cap above 1/1000 of the admitted maximum
saturates. The borrow index never falls below one RAY, so an admitted borrow
cap cannot saturate. Position conversion still rejects overflow.
```

```rust
pub(crate) fn apply_bad_debt_to_supply_index(cache: &mut Cache, bad_debt: Ray) {
    let total_supplied_value = cache.supplied().mul(cache.env(), cache.supply_index());

    if total_supplied_value == Ray::ZERO {
        return;
    }

    let capped = bad_debt.min(total_supplied_value);
    let remaining = total_supplied_value.checked_sub(cache.env(), capped);

    let reduction_factor = remaining.div_floor(cache.env(), total_supplied_value);
    let new_supply_index = cache
        .supply_index()
        .mul_floor(cache.env(), reduction_factor);

    cache.set_supply_index(new_supply_index.max(Ray::from(SUPPLY_INDEX_FLOOR_RAW)));
```

```rust
/// Computes `x * y / d` rounded half up. Requires `x >= 0`, `y >= 0`, and `d > 0`; a
/// `debug_assert` checks this in debug builds. Panics with `GenericError::DivisionByZero` if
/// `d == 0`, and with `GenericError::MathOverflow` if any other precondition is violated or if
/// the result does not fit in `i128`.
pub fn mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> i128 {
    // The zero check runs first so debug and release builds agree on a zero
    // divisor: both surface `DivisionByZero` rather than tripping the assert.
    require_nonzero_divisor(env, d);
    debug_assert!(
        x >= 0 && y >= 0 && d > 0,
        "mul_div_half_up: non-negative x, y and positive d"
    );
    try_mul_div_half_up(env, x, y, d)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow))
}
```

```rust
pub fn mul_div_floor(env: &Env, x: i128, y: i128, d: i128) -> i128 {
    require_nonzero_divisor(env, d);
    if let Some(quotient) = x
        .checked_mul(y)
        .and_then(|product| div_floor_i128(product, d))
    {
        return quotient;
    }
    let (x256, y256, d256) = to_i256_operands(env, x, y, d);
    let nonneg = quotient_is_nonnegative(x, y, d);
    to_i128(env, &div_floor_i256(env, &x256.mul(&y256), &d256, nonneg))
}
```

```rust
/// Returns the largest cap, in asset base units, whose ray-scaled form still
/// fits in `i128`.
///
/// Returns 0 when `asset_decimals > RAY_DECIMALS`, since the ray form is not
/// representable in that case. Enforced by
/// [`require_cap_within_asset_domain`], so stored caps can never overflow the
/// asset→ray rescale.
pub fn max_cap_for_decimals(asset_decimals: u32) -> i128 {
    let Some(exp) = RAY_DECIMALS.checked_sub(asset_decimals) else {
        return 0;
    };
    let upscale = 10i128
        .checked_pow(exp)
        .expect("10^(RAY_DECIMALS - asset_decimals) fits i128 for asset_decimals <= RAY_DECIMALS");
    i128::MAX / upscale
}

/// Panics with `CollateralError::AssetDecimalsTooHigh` if `asset_decimals`
/// exceeds `RAY_DECIMALS`, or with `CollateralError::InvalidBorrowParams` if
/// `cap` exceeds the value returned by `max_cap_for_decimals`.
pub fn require_cap_within_asset_domain(env: &Env, cap: i128, asset_decimals: u32) {
    if RAY_DECIMALS.checked_sub(asset_decimals).is_none() {
        panic_with_error!(env, CollateralError::AssetDecimalsTooHigh);
    }
    assert_with_error!(
        env,
        cap <= max_cap_for_decimals(asset_decimals),
        CollateralError::InvalidBorrowParams
    );
```

```rust
        amount == 0 || minted.raw() > 0,
        GenericError::SupplyRoundsToZeroShares
    );

    position = position.checked_add(env, minted);
    cache.mint_supply(minted);

    cache.credit_cash(amount);
```
