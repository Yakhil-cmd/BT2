## Finding

### Title
Signature verification selects the GitHub App/secret from an attacker-controlled payload field that is never itself cryptographically bound to the field the webhook handlers later act on - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks *which* configured GitHub App (and therefore which `webhook_secret`) is used to validate an incoming webhook by reading `repository.owner.login` (or `organization.login`) directly out of the still‑unverified request body, then verifies the raw body against that App's secret. Every downstream handler (push, status, pull_request, etc.) subsequently acts on other fields of that same body (commit `sha`, `repository.full_name`, branch, etc.) to decide what stack/commit to mutate. Nothing ties "the org whose secret validated this request" to "the repository/commit actually written to." On top of that, `GithubApp#verify_webhook_signature` treats an unset `webhook_secret` as automatic success, and an unset secret is explicitly presented as a normal, optional configuration in the shipped docs/examples.

### Finding Description
`repository_owner` is computed purely from the JSON body before any cryptographic check occurs: [1](#0-0) 

That value is used to select the GitHub App instance whose secret is used to validate the *same* body: [2](#0-1) 

`GithubApp#verify_webhook_signature` unconditionally passes when the selected org has no secret configured: [3](#0-2) 

An unset `webhook_secret` is presented as a normal, supported, optional setting, including in a multi-organization configuration example that is shipped with the engine: [4](#0-3) [5](#0-4) 
and the setup docs call it "optional": [6](#0-5) 

Once verification passes, handlers key their side effects off *different* body fields than the one used to select the signing App. For example, the `status` webhook path was demonstrated in tests to look up an existing `Commit` purely by `sha` and update its CI status, independent of which organization's secret validated the request: [7](#0-6) 
and PR-based handlers resolve the acting `Repository`/`Stack` from `params.repository.full_name`, a field distinct from the `repository.owner.login`/`organization.login` field consulted for signature selection: [8](#0-7) [9](#0-8) 

The equality that should hold but is not enforced is:
`organization whose secret authenticated the request == owner of the repository/commit that the handler subsequently mutates`

Because `repository_owner` (the authentication key) is attacker-controlled body content, and because at least one configured organization can legitimately have no secret at all (per the shipped example configs and docs), an unprivileged internet client can:
1. Send a `POST /webhooks` body where `repository.owner.login` (or `organization.login`) names the no-secret (or attacker-known-secret) organization — satisfying `verify_signature` with no real credential.
2. Populate the event-specific fields (`sha`, `repository.full_name`, `ref`/`after`, etc.) to reference a **completely different, tracked repository/stack/commit** that the attacker has no access to.
3. Have the corresponding handler (`push`, `status`, `pull_request`, `check_suite`, `membership`, ...) execute against that unrelated repository/stack as if GitHub itself had legitimately delivered the event for it.

### Impact Explanation
This breaks the "organization that authenticated vs. repository that is written" binding explicitly called out as in-scope. Concretely reachable impacts observed in the handler set:
- Forcing a `status` event with an arbitrary `sha` sets/overwrites the CI `Status` for any commit tracked by Shipit regardless of the real organization's webhook secret, which can be used to satisfy a stack's `ci.require` gate and let a deploy proceed that should have been blocked — an unauthorized deploy.
- `pull_request` handlers (`opened_handler.rb`, `labeled_handler.rb`, `closed_handler.rb`) auto-provision/archive/unarchive review stacks for any repository resolved via `params.repository.full_name`, letting an attacker create/destroy review-stack state for repositories outside the org whose secret was actually checked — a cross-repository write.
- `push` triggers a `GithubSyncJob` for any stack whose branch matches, causing Shipit to re-fetch/re-cache deploy specs and commit history for a stack the caller has no legitimate relationship to.

These map to the required Critical bucket (unauthorized deploy, cross-repository writes).

### Likelihood Explanation
The precondition — one org in a multi-org Shipit deployment having no `webhook_secret` — is not a hypothetical misconfiguration outside the documented deployment model; it is presented by the engine itself as a valid, optional setting in both the setup guide and the shipped multi-org example config. Any operator running more than one GitHub App/org through a single Shipit instance and choosing to skip the secret on even one of them (e.g., a low-stakes sandbox org) exposes every other org's stacks to forged events, with no GitHub credentials, session, or `ApiClient` token required — only network access to the `/webhooks` endpoint, which is intentionally unauthenticated pre-signature-check.

### Recommendation
- Do not use attacker-supplied body fields to select the verification secret. Route webhooks by a stable, out-of-band identifier (e.g., a per-organization delivery path, or the GitHub `X-GitHub-Hook-Installation-Target-ID` header cross-checked against configuration) rather than `params.dig('repository','owner','login')`.
- After signature verification, re-derive/re-validate that the `repository`/`organization` fields used by the handler match the organization whose secret validated the request; reject mismatches.
- Do not silently treat an absent `webhook_secret` as "verification passed" — require an explicit `insecure_webhooks: true` opt-in (logged prominently) instead of defaulting to open when unset, and update docs/example configs accordingly.

### Proof of Concept
Preconditions: Shipit configured with ≥2 GitHub orgs (as in the shipped `config/secrets.development.shopify.yml` layout), where org `A` has `webhook_secret: nil` and org `B` (target) has undeployed commits.

1. Attacker sends:
```
POST /webhooks
X-Github-Event: status
Content-Type: application/json

{
  "sha": "<sha of a commit belonging to org B's tracked repo>",
  "state": "success",
  "context": "ci/required-check",
  "target_url": "https://attacker.example/fake",
  "repository": { "owner": { "login": "A" } }
}
```
2. `verify_signature` resolves `repository_owner` = `"A"`, loads org `A`'s `GithubApp`, and calls `verify_webhook_signature`, which returns `true` unconditionally because org `A` has no `webhook_secret` (`lib/shipit/github_app.rb:76-77`), regardless of any `X-Hub-Signature` header value.
3. The `status` handler updates/creates a `Status` for the referenced commit belonging to org `B`'s stack (behavior demonstrated by `test/controllers/webhooks_controller_test.rb:42-59`, which shows lookup is by `sha` alone), even though org `B`'s own webhook secret was never checked.
4. If that commit is otherwise ready to deploy and only blocked by the `ci.require` status gate in `shipit.yml`, the forged "success" status can allow a deploy to proceed that a genuine CI system never approved.

Note: I could not directly open `app/models/shipit/webhooks/handlers/handler.rb` or the concrete `status`/`push` handler source files in this session (tool errors), so the exact repository-scoping logic inside the base `Handler#stacks` method is inferred from the `PushHandler`/`PullRequest::*Handler` code shown and from the webhook controller test's behavior rather than directly read; a full session with file access should confirm whether `Handler#stacks`/the status handler impose any additional repository-consistency check before this PoC is treated as fully verified end-to-end.

**File:** lib/shipit/github_app.rb (L76-83)
```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
