### Title
Cross-repository status webhook can reject a victim's legitimate merge request via unscoped `Commit.where(sha:)` lookup - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits solely by `sha`, with no constraint tying the status event's `repository.full_name` to the commit's owning stack/repository. Any correctly-signed `status` webhook (signed by any GitHub App/organization Shipit trusts) that references a SHA which happens to match a `Commit` row belonging to a different, unrelated stack will attach the forged status to that commit, letting `MergeRequest#any_status_checks_failed?` return true and `ProcessMergeRequestsJob` call `reject!('ci_failing')` on a pending merge request whose real CI had already passed.

### Finding Description
The intended binding is: `status.repository.full_name == commit.stack.repository.full_name` for every `Commit` record a `status` event is allowed to mutate. The actual code enforces no such equality: [1](#0-0) 

`Commit.where(sha: params.sha)` is a global, unscoped query across every stack/repository tracked by the Shipit instance; `repository_name`/`stacks` (defined in the base `Handler`) are never consulted by `StatusHandler#process` at all: [2](#0-1) 

`WebhooksController#verify_signature` only proves that the payload was signed by the GitHub App configured for `repository.owner.login` in the payload — it says nothing about which repository's commits may be touched: [3](#0-2) 

Git commit SHAs are content-addressed and repository-independent: the exact same commit object (and therefore SHA) can exist in two different repositories (e.g., a public commit copied/cherry-picked into another repo within the same GitHub organization/App installation). An attacker who owns or has push access to any repository covered by the same trusted GitHub App installation (satisfying signature verification) can:
1. Observe the victim's pending merge request's `head.sha` (PRs are public).
2. Push/import a commit with that identical SHA into their own repository.
3. Call GitHub's Statuses API on their own repo for that SHA with `state=failure`.
4. GitHub emits a validly-signed `status` webhook naming the attacker's repository, but `params.sha` matches the victim commit.

`Commit.create_status_from_github!` is invoked on the victim's `Commit` row purely because the SHA matched: [4](#0-3) 

This flips `head.statuses_and_check_runs`, so `MergeRequest#any_status_checks_failed?` returns true: [5](#0-4) 

and `reject_unless_mergeable!` calls `reject!('ci_failing')` on the victim's otherwise-mergeable pending request: [6](#0-5) 

None of the existing guards catch this: `verify_signature` validates the signer's org, not the target repository; the `ExplicitParameters` schema only validates payload shape; `drop_unhandled_event` only checks the event type exists; there is no `Repository`/`Stack` equality check between the event's `repository.full_name` and the matched `Commit#stack`.

### Impact Explanation
A cross-tenant/cross-repository write occurs: an attacker who controls (or has push access to) one repository under a Shipit-trusted GitHub organization/App can mutate the CI status state — and thereby the merge/rejection state — of a `MergeRequest` belonging to a completely different repository/stack they do not control. This is a business-logic integrity break where "a payload for one repository mutates another's ... task" (an unauthorized rejection of a legitimate merge decision), matching the Critical impact category. It is repeatable against any commit whose SHA the attacker can reproduce in a repository they control, and the attack can be run against arbitrary merge requests as long as the SHA collision precondition is met.

### Likelihood Explanation
Preconditions: the attacker must be able to send a validly-signed `status` webhook, which requires push/write access to at least one repository registered under a GitHub organization/App that Shipit's `verify_signature` accepts (per the org's `webhook_secret`), and the attacker must get a commit with an identical SHA to the victim's PR head into that repository (feasible since git objects are portable and PR heads are public). This is not "any internet user with zero relationship to the org" — it requires at least minimal legitimate access to *some* repo covered by the trusted GitHub App/organization, which is a materially lower bar than being a maintainer of the *victim's specific* repository. Given typical org-wide GitHub App installations, this is a realistic, low-cost, and repeatable attack once the precondition is met.

### Recommendation
Scope the commit lookup in `StatusHandler#process` to the repository named in the webhook payload, e.g., restrict to `stacks.flat_map(&:commits).where(sha: params.sha)` or filter matched commits by `commit.stack.repository.full_name == repository_name`, using the `stacks`/`repository_name` helpers already defined on `Handler`, before calling `create_status_from_github!`.

### Proof of Concept
```ruby
test "cross-repo status forgery rejects victim merge request" do
  victim_stack = shipit_stacks(:shipit) # repo "shopify/shipit-engine"
  attacker_stack = shipit_stacks(:cyclimse) # different repo, e.g. "attacker/other-repo"

  head = victim_stack.commits.create!(sha: 'deadbeef' * 5, ...)
  merge_request = victim_stack.merge_requests.create!(number: 42, head:, merge_status: 'pending', ...)
  # Simulate real CI already passed
  head.statuses.create!(stack: victim_stack, state: 'success', context: 'ci')
  assert_not merge_request.any_status_checks_failed?

  # Attacker forges a validly-signed status webhook naming a different repository,
  # but referencing the victim's head sha
  forged_payload = {
    'sha' => head.sha,
    'state' => 'failure',
    'context' => 'attacker-ci',
    'repository' => { 'full_name' => attacker_stack.repository.full_name, 'owner' => { 'login' => attacker_stack.repository.owner } }
  }
  Shipit::Webhooks::Handlers::StatusHandler.call(forged_payload)

  ProcessMergeRequestsJob.new.perform(victim_stack)

  merge_request.reload
  assert merge_request.rejected?
  assert_equal 'ci_failing', merge_request.rejection_reason
end
```
Both sides of the intended binding (`status.repository.full_name == commit.stack.repository.full_name`) diverge: the status event's repository is the attacker's, but it mutates the victim's commit/merge request state — confirming the vulnerability.
