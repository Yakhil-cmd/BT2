## Title
Generic `signed_message` Signing Scheme Lacks Domain Separation, Enabling Cross-Context Signature Reuse Against AAs and Off-Chain Contracts - (File: `signed_message.js`, `object_hash.js`, `formula/evaluation.js`)

### Summary
The external report's bug class is: a signature scheme with no fixed, context-binding format lets an attacker smuggle a different operation's payload into a field that a victim signs for an unrelated purpose, letting the attacker obtain a signature that is also valid for a more sensitive operation. `ocore`'s generic "signed message" primitive (`signMessage`/`validateSignedMessage` in `signed_message.js`, exposed to oscript via `is_valid_signed_package` in `formula/evaluation.js`) has the same structural weakness: the hash-to-sign is computed over whatever attacker/application-supplied value is placed in the `signed_message` field, with no protocol-level tag identifying which feature/context the signature is meant for.

### Finding Description
`signMessage()` builds `objUnit = {version, signed_message: message, authors}` and signs `objectHash.getSignedPackageHashToSign(objUnit)` [1](#0-0) [2](#0-1) . The only fields that are structurally guaranteed are `signed_message`, `authors`, `last_ball_unit`, `version` [3](#0-2) ; the *content* of `signed_message` itself is completely free-form — it can be a plain string or an arbitrary nested object, and the core validator never binds it to any specific feature, protocol, channel, or AA address.

This generic primitive is exposed directly to oscript through `is_valid_signed_package`, which just calls `signed_message.validateSignedMessage` on whatever object a trigger sender supplies and returns true/false: [4](#0-3) . Because the core check only verifies "this address signed exactly this JSON blob," any additional context binding (which channel, which period, which counterparty, which purpose) must be added manually by every AA author on top of the raw `signed_message` payload. The shipped reference sample (`payment_channels.oscript`) demonstrates this necessity by manually checking `signed_message.channel != this_address` and `signed_message.period != var['period']` before trusting `signed_message.amount_spent` [5](#0-4) . This is exactly the mitigation the external report recommends ("append a predefined string/context to each signature"), but it is opt-in per AA rather than enforced by `ocore` itself.

The same unconstrained-field pattern also appears in the wallet's paired-device contract flows: `prosaic_contract` and `arbiter_contract` responses bind the signature only to `objContract.title`, an arbitrary free-text string chosen by the contract offeror, with `objSignedMessage.signed_message != objContract.title` as the sole context check [6](#0-5) [7](#0-6) . Nothing in `validateSignedMessage` forces `signed_message` to carry any tag identifying "this signature is only valid for accepting a prosaic contract," so if any other feature (a custom AA, a payment-channel implementation, an arbiter dispute flow, etc.) is willing to accept a free-form string or an object subset as its own `signed_message` payload, a signature obtained under the guise of one operation (e.g., "please sign this contract title to accept my offer") can be replayed as a valid authorization in a completely different, more sensitive context that happens to accept the same textual/structural shape.

### Impact Explanation
Because `is_valid_signed_package`/`validateSignedMessage` provide no protocol-enforced domain separation, security of any AA or off-chain-payment feature built on top of it depends entirely on that feature's author remembering to embed and check enough unique, non-guessable context (address, purpose tag, nonce/period) inside `signed_message`. Any AA that omits or under-specifies such binding (unlike the reference `payment_channels.oscript` sample, which needs three separate manual checks to be safe) is exposed to a counterparty obtaining a validly-signed package under an innocuous pretext (e.g., contract acceptance, a differently-scoped state update) and replaying/repurposing it to unlock AA state transitions it was never intended to authorize — leading to AA fund loss/theft between the two off-chain counterparties, which is a concrete impact under the given scope (AA fund loss).

### Likelihood Explanation
Exploitation requires no privileged access: it is reachable by any paired device / private counterparty who can propose a contract, payment-channel message, or AA trigger containing a `signed_message` payload and get the other party's wallet to sign it through the normal accept/respond flow. The likelihood of a concrete exploit depends on a specific AA/feature failing to add its own context-binding fields (as the shipped sample does add), so this is a design-level weakness whose severity is realized whenever a downstream feature relies on the generic primitive without full manual domain separation — which the core library does nothing to prevent or warn about.

### Recommendation
Add a mandatory, protocol-level domain/context tag to the signed-message hash construction (e.g., require and hash a reserved `app`/`purpose` field alongside `signed_message`, distinct per feature and possibly per AA `this_address`), analogous to the fix in the reference report (`f19c8e1`), so that a signature produced for one feature/context cannot be structurally valid input for another. At minimum, document and enforce in `validateSignedMessage`/`is_valid_signed_package` that callers must include a unique, feature-specific literal string in the signed payload, rather than leaving this entirely to each AA author's discretion.

### Proof of Concept
Conceptual sequence (mirrors the external report's city→operation-name substitution):
1. Device A and Device B are counterparties in an off-chain relationship that uses `signed_message` (e.g., a prosaic contract negotiation).
2. Device A crafts a `title`/message payload whose text/structure happens to satisfy the field checks of a different, more sensitive AA or contract flow that also consumes a `signed_message`-shaped object via `is_valid_signed_package` (e.g., an object containing `channel`, `period`, `amount_spent`-like keys disguised as ordinary contract text/fields).
3. Device B signs the "contract acceptance" through the normal `respond`/`processResponse` path [7](#0-6) , unaware the resulting `objSignedMessage` is also a structurally valid signed package for the other context.
4. Device A submits this signed package to the other AA/feature via `is_valid_signed_package` [8](#0-7) , which only verifies the raw signature over the JSON blob and — absent that feature's own extra binding checks — treats it as a legitimate authorization, potentially causing fund loss for Device B in that AA.

function getSignedPackageHashToSign(signedPackage) {
	var unsignedPackage = _.cloneDeep(signedPackage);
	for (var i=0; i<unsignedPackage.authors.length; i++)
		delete unsignedPackage.authors[i].authentifiers;
	var sourceString = (typeof signedPackage.version === 'undefined' || signedPackage.version === constants.versionWithoutTimestamp) ? getSourceString(unsignedPackage) : getJsonSourceString(unsignedPackage);
	return crypto.createHash("sha256").update(sourceString, "utf8").digest();
}
