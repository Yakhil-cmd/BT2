### Title
`pallet-psm::mint` uses stale decimals snapshot with no drift check, allowing mismatched conversion between internal and external assets - (File: substrate/frame/psm/src/lib.rs)

### Summary
`pallet-psm` documents a "runtime drift guard" that should make `mint`/`redeem` return `DecimalsMismatch` if an external or internal asset's live decimals diverge from the snapshot taken at `create_psm`/`add_external_asset` time [1](#0-0) . In practice, `mint` and `redeem` never compare the snapshot decimals (`info.internal_decimals`, `external.decimals`) against the live decimals reported by `T::Fungibles::decimals(..)`; they simply use the stored snapshot values to scale amounts via `external_to_internal`/`internal_to_external` [2](#0-1) [3](#0-2) . This mirrors the ShareMath.sol bug pattern: a conversion function that uses the wrong/stale decimal precision, which silently corrupts share/asset conversion math whenever the two decimal domains diverge.

### Finding Description
`PsmInfo::internal_decimals` and `ExternalAssetInfo::decimals` are captured once when the PSM instance and external asset are registered [4](#0-3) . `mint` reads these two snapshot fields and uses them directly to scale `external_amount` into internal units via `external_to_internal`, and to compute `effective_external` via `internal_to_external` [5](#0-4) . There is no call anywhere in `mint` (nor, on inspection, in `redeem`) that re-reads `T::Fungibles::decimals(...)` and compares it to the stored snapshot, despite the prdoc's claim that "mint/redeem return DecimalsMismatch if live metadata diverges from the registration snapshot" [1](#0-0) . A search for `DecimalsMismatch` across the crate shows it only appears in the README and prdoc description, not as an active check inside `mint`/`redeem` dispatchables.

Any external asset's decimals metadata can be legitimately changed after PSM registration by whoever controls that asset's `set_metadata` call (the asset owner, not a PSM-privileged role) — the pallet's own test suite demonstrates this scenario for `redeem` (`redeem_uses_snapshot_when_asset_decimals_drift`, `redeem_uses_snapshot_when_internal_decimals_drift`) [6](#0-5) [7](#0-6) , but no equivalent guard or test exists confirming `mint` rejects or safely handles drifted decimals. Since `mint` performs `external_to_internal` (scale external amount up/down) and then mints internal-asset tokens to the user based on that scaling [8](#0-7) , if the external asset's live decimals have increased or decreased since registration (e.g. an ERC20-style asset whose metadata is later corrected/updated), the pallet will continue scaling by the stale factor `10^(diff)`, producing an internal mint amount inconsistent with the real value of the external asset actually deposited by the caller.

This is the exact analog of the reported ShareMath.sol bug: a "decimals" input parameter used inside a `checked_mul`/`checked_div` conversion routine is sourced from a stale/incorrect reference (vault decimals instead of asset decimals in the original report; a stale snapshot instead of live metadata here), which desynchronizes value conversion between two different decimal domains and can cause the pallet to systematically over- or under-value an external deposit relative to the internal asset minted.

### Impact Explanation
If the divergence is exploitable in the "scale up" direction (external decimals snapshot lower than the asset's actual current decimals, or internal snapshot mismatched against live), a caller can mint an internal-asset amount larger than the true value of the external tokens deposited, directly diluting/breaking the internal asset's 1:1 backing and creating unbacked issuance — a Critical/High class issue (unbacked issuance) per the program's severity classification. Conversely, in the "scale down" direction it degrades user funds (theft of value from users), and it also breaks `PsmDebt` accounting, since `PsmDebt` is meant to track pUSD-equivalent value consistently across mixed-decimal assets, which the prdoc explicitly calls out as a design requirement [9](#0-8) .

### Likelihood Explanation
Likelihood depends entirely on whether the external (or internal) asset's decimals metadata can actually change after PSM registration in a live deployment, and whether `T::Fungibles::decimals(..)` is dynamically settable by the asset owner (as in `pallet-assets::set_metadata`) without PSM governance involvement — this is exactly what the pallet's own test helpers exercise for `redeem` by calling `Assets::set_metadata` post-registration [10](#0-9) . I could not fully verify from the index whether `mint` is genuinely unguarded in the shipped code (I only reviewed the visible portion of `mint`, lines ~703–768, and did not find a decimals-comparison check there or a call site for `DecimalsMismatch`), or whether such a check exists elsewhere (e.g. a hook called before dispatch, or inside `external_to_internal`/`internal_to_external` themselves, which I also reviewed and found to contain no live-decimals comparison, only scaling by the two decimals arguments passed in) [11](#0-10) .

### Recommendation
Add an explicit `DecimalsMismatch` check in `mint` (and confirm it exists and is enforced in `redeem`) that re-reads `T::Fungibles::decimals(internal_asset)` and `T::Fungibles::decimals(external_asset)` and compares them against `info.internal_decimals` / `external.decimals` before performing any conversion, halting the specific asset pair until governance intervenes, consistent with the documented intent in the prdoc.

### Proof of Concept
I was not able to execute a live reproduction against this codebase (no terminal/execution access in this ask-only session). Based on static analysis:
- `create_psm` snapshots `internal_decimals` from live metadata at creation time [4](#0-3) .
- `mint` uses the snapshot values `ext_decimals`/`internal_decimals` directly in `external_to_internal`/`internal_to_external` without re-validating against current `T::Fungibles::decimals(..)` [5](#0-4) .
- The pallet's own test suite proves live decimals metadata can drift post-registration via `pallet_assets::Pallet::set_metadata` and that `redeem` deliberately (and only) uses the frozen snapshot [12](#0-11) , but there is no equivalent test proving `mint` is protected by a `DecimalsMismatch` guard as the prdoc claims.

A concrete Rust/FRAME integration reproduction would need to: (1) `create_psm` and `add_external_asset` for an asset at decimals D1, (2) call `pallet_assets::set_metadata` to change that asset's decimals to D2 ≠ D1, (3) call `Psm::mint` and assert whether it succeeds (using stale D1) and quantify the value discrepancy between `external_amount` at true decimals D2 and the `internal_to_user` amount minted. This step was not run; the finding is offered as an analog based on static code and test evidence, not a confirmed executed exploit. Given I could not confirm the absence of the guard beyond the visible source and could not execute the PoC, treat this as a **Medium**-confidence finding pending verification of whether `mint`'s drift guard exists elsewhere in the pallet or in an upstream call boundary not indexed here.

		pub(crate) fn external_to_internal(
			amount: BalanceOf<T>,
			ext_decimals: u8,
			internal_decimals: u8,
		) -> Result<BalanceOf<T>, Error<T>> {
			use core::cmp::Ordering::*;
			match ext_decimals.cmp(&internal_decimals) {
				Equal => Ok(amount),
				Less => {
					let diff = (internal_decimals - ext_decimals) as u32;
					let factor = Self::pow10(diff)?;
					amount.checked_mul(&factor).ok_or(Error::<T>::ConversionOverflow)
				},
				Greater => {
					let diff = (ext_decimals - internal_decimals) as u32;
					let factor = Self::pow10(diff)?;
					Ok(amount.checked_div(&factor).unwrap_or_else(BalanceOf::<T>::zero))
				},
			}
		}

			let alice_internal_before = get_asset_balance(INTERNAL_ASSET_ID, ALICE);
