### Title
Hookify's `PreToolUse`/`PostToolUse`/`Stop` guard hooks fail open on any error, silently disabling the security check they exist to enforce - (File: `plugins/hookify/hooks/pretooluse.py`)

### Summary
The Brahma report describes a Safe `Guard` contract that cannot be attached because it does not conform to a required interface (`EIP-165`), so the security control the guard is supposed to provide never gets applied to that Safe. The structural analog in this repository is Claude Code's `hookify` plugin: its hook executors are meant to act as a "guard" that blocks dangerous tool calls (e.g. destructive `rm -rf`), but the executor scripts are written to catch every possible failure and unconditionally allow the operation, meaning any incompatibility between the hook runtime and its dependencies (missing module, malformed rule file, bad `CLAUDE_PLUGIN_ROOT`, Python version mismatch, etc.) silently disables the guard instead of blocking or surfacing the failure.

### Finding Description
`plugins/hookify/hooks/pretooluse.py` wraps its rule-loading/import logic in a `try/except ImportError` that, on failure, prints a diagnostic `systemMessage` and calls `sys.exit(0)` [1](#0-0) . The `main()` function similarly wraps rule evaluation in a blanket `except Exception` that also emits a message and, in the `finally` block, unconditionally exits `0` with the comment "ALWAYS exit 0 - never block operations due to hook errors" [2](#0-1) . The same fail-open pattern is duplicated in `posttooluse.py`, `stop.py`, and `userpromptsubmit.py` [3](#0-2) [4](#0-3) [5](#0-4) .

Because a `PreToolUse` hook's approval/denial is only expressed via its JSON `hookSpecificOutput.permissionDecision` and exit code (documented as `deny` decisions plus non-zero exit to actually block, per `plugins/plugin-dev/skills/hook-development/SKILL.md:144-153`) [6](#0-5) , any code path that exits `0` without emitting a `deny` decision is functionally equivalent to "no guard present" — exactly like a Gnosis Safe whose `setGuard` call reverted because the guard doesn't implement `supportsInterface`. The `config_loader.py` rule loader itself has multiple broad `except Exception` fallbacks that skip malformed or unreadable rule files rather than failing the check [7](#0-6) [8](#0-7) , so a single malformed `.claude/hookify.*.local.md` rule file (or an environment where the plugin's Python package fails to import) silently removes protection for every rule, not just the broken one.

The project's own documentation independently confirms this is a known footgun class ("Hook fails silently" is called out with remediation guidance to check exit codes and validate JSON output) [9](#0-8) , and the CHANGELOG shows the core product has repeatedly had to fix real permission/hook bypasses of this shape (e.g. "Fixed PreToolUse auto-allow hooks bypassing tool restrictions in background agent tasks", "Fixed a permission-check bypass...") [10](#0-9) [11](#0-10) , indicating the fail-open hook pattern is a recurring, exploitable trust-boundary issue rather than a one-off.

### Impact Explanation
Any user who relies on `hookify` (or a similarly-authored fail-open hook) to block dangerous operations (destructive `rm -rf`, writes to sensitive paths, etc.) gets no actual protection whenever the hook errors out — which can be triggered unintentionally (a bad `PLUGIN_ROOT`/`sys.path`, a malformed local rule file, an unhandled exception in regex compilation, an interpreter/version mismatch) or, in an adversarial framing, deliberately by an attacker who can influence rule file content or the plugin's Python environment to force an exception and thereby disable the guard for every subsequent tool call in the session. This directly maps onto the "command approval / hook bypass" trust boundary named in the analog rules: unauthorized shell/file actions proceed without the approval check the user configured.

### Likelihood Explanation
Likelihood is moderate to high: the fail-open behavior is unconditional and by design ("ALWAYS exit 0"), so it will trigger on ordinary error conditions (malformed rule frontmatter, missing dependency, unicode errors) without any attacker action, and can additionally be deliberately induced by anyone who can write to `.claude/hookify.*.local.md` rule files in the project (an unprivileged, in-scope workspace-local action).

### Recommendation
Change the hook executors to fail closed (or at minimum surface a clear, blocking warning) when the guard logic cannot run: on unexpected exceptions or import failures, emit a `deny`/`ask` `permissionDecision` (or a nonzero exit with `decision: "block"`) instead of silently exiting `0`, and validate rule files strictly at load time so a single malformed file cannot silently disable protection for all other rules. This mirrors the Brahma fix of enforcing the interface contract up front rather than allowing operation to proceed when the guard cannot be attached/executed correctly.

### Proof of Concept
1. Create a malformed hookify rule at `.claude/hookify.broken.local.md` (e.g., invalid encoding or a syntax error that raises `UnicodeDecodeError`/`AttributeError` inside `load_rule_file`) alongside a legitimate blocking rule such as the shipped `warn-dangerous-rm` example [12](#0-11) .
2. Trigger a `Bash` tool call containing `rm -rf /important/path`.
3. `pretooluse.py` invokes `load_rules()`, which hits the broken file's exception handler and logs a warning but continues execution [7](#0-6) ; if instead an exception propagates from deeper in `main()` (e.g., an environment where `hookify.core` fails to import due to `sys.path`/`CLAUDE_PLUGIN_ROOT` misconfiguration), the `except ImportError`/`except Exception` handlers fire and the script exits `0` without any `permissionDecision: deny` [13](#0-12) .
4. Claude Code treats exit `0` with no denying `hookSpecificOutput` as approval, so the destructive `rm -rf` command executes even though the user configured a rule specifically to block it — the guard was bypassed exactly as in the Brahma report where the guard could not be attached due to an interface mismatch.

```python
try:
    from hookify.core.config_loader import load_rules
    from hookify.core.rule_engine import RuleEngine
except ImportError as e:
    # If imports fail, allow operation and log error
    error_msg = {"systemMessage": f"Hookify import error: {e}"}
    print(json.dumps(error_msg), file=sys.stdout)
    sys.exit(0)


def main():
    """Main entry point for PreToolUse hook."""
    try:
        # Read input from stdin
        input_data = json.load(sys.stdin)

        # Determine event type for filtering
        # For PreToolUse, we use tool_name to determine "bash" vs "file" event
        tool_name = input_data.get('tool_name', '')

        event = None
        if tool_name == 'Bash':
            event = 'bash'
        elif tool_name in ['Edit', 'Write', 'MultiEdit']:
            event = 'file'

        # Load rules
        rules = load_rules(event=event)

        # Evaluate rules
        engine = RuleEngine()
        result = engine.evaluate_rules(rules, input_data)

        # Always output JSON (even if empty)
        print(json.dumps(result), file=sys.stdout)

    except Exception as e:
        # On any error, allow the operation and log
        error_output = {
            "systemMessage": f"Hookify error: {str(e)}"
        }
        print(json.dumps(error_output), file=sys.stdout)

    finally:
        # ALWAYS exit 0 - never block operations due to hook errors
        sys.exit(0)
```
