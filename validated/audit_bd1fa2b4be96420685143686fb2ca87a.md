### Title
Uncaught exception from malformed c-hash length in address/asset-checksum validation - (File: `chash.js`)

### Summary
CVE-2016-10721 is a heap overflow in `partclone.restore` caused by insufficient validation of a length field in an untrusted image header before it is used to size/index a buffer. The closest reachable analog in this JS codebase is the checksum/"chash" validation logic in `chash.js`, where a length value derived from decoding an attacker-supplied base32/base64-encoded address/checksum string is not fully validated before being used to select array-index maps and slice bit-strings, resulting in an uncaught runtime exception path instead of a graceful validation failure.

### Finding Description
`chash.isChashValid()` [1](#0-0)  only wraps the `base32.decode(encoded)` / `Buffer.from(encoded, 'base64')` call in a `try/catch` [2](#0-1) . It does not validate that the *decoded* buffer has the expected bit-length (160 or 288 bits) before passing it to `buffer2bin()` and then `separateIntoCleanDataAndChecksum()` [3](#0-2) .

`separateIntoCleanDataAndChecksum()` explicitly throws an uncaught `Error("bad length=...")` if the bit-length of the decoded data is anything other than exactly 160 or 288 [4](#0-3) . Because only the *encoded string length* (32 or 48 characters) is checked by the caller `isValidChash()` [5](#0-4)  — not the actual decoded byte length — a decode step that yields a different number of bytes (e.g., due to non-standard base32 characters, padding quirks in the `thirty-two` library, or base64 variability) can slip past the length check performed on the input string and throw inside `isChashValid`, outside of any `try/catch`.

This mirrors the CVE's root cause pattern: a length/size value taken from untrusted input is checked superficially (string length) rather than validated against the actual decoded/parsed structure size before being used deeper in the parsing pipeline.

`isValidChash()` is reachable both through `isValidAddress()` (which additionally enforces a strict `/^[A-Z2-7]{32}$/` regex before calling it) and through `isValidAddressAnyCase()`, which calls `isValidChash(address, 32)` directly with **no charset restriction** [6](#0-5) . Any code path that validates addresses via `isValidAddressAnyCase` (rather than `isValidAddress`) processes attacker-controlled strings without first constraining them to the base32 alphabet, increasing the chance of feeding `chash.isChashValid` a payload whose decode yields a non-160/288-bit result.

### Impact Explanation
If this uncaught exception is thrown synchronously inside a unit/AA-trigger/address validation code path that is not wrapped in an enclosing `try/catch` by the caller (e.g., during processing of a posted unit, AA trigger data, or device/private-payment address field), it would crash the Node.js process handling that message. If exploitable broadly, this could cause nodes across the network to crash when processing the same malicious unit/message, contributing to the "network unable to confirm new units" impact class. I was not able to fully trace, within the remaining tool budget, every call site of `isValidChash` / `isValidAddressAnyCase` to confirm whether all reachable paths are guarded by an outer `try/catch` (e.g., in `validation.js`'s top-level `validate()` wrapper) that would downgrade this from a crash to a mere validation rejection.

### Likelihood Explanation
The trigger only requires supplying a syntactically-plausible 32- or 48-character encoded string (address-like field) that decodes to a byte length other than 20/36 bytes — reachable from any unprivileged unit poster, AA trigger sender, or device-message field that is validated with `isValidAddressAnyCase`/`isValidChash` rather than the stricter `isValidAddress`. Likelihood is Medium because it depends on (a) locating a caller that uses the case-insensitive/looser validator on fully-untrusted input, and (b) whether outer exception handling in that specific call path prevents a hard crash — both of which I could not fully confirm before the iteration budget was exhausted.

### Recommendation
In `chash.js`, validate the decoded buffer's actual bit-length immediately after decoding and return `false` (not throw) if it does not equal 160 or 288, mirroring the existing `try/catch` pattern already used around the decode call:
```js
var binChash = buffer2bin(chash);
if (binChash.length !== 160 && binChash.length !== 288)
    return false;
```
Additionally, audit all call sites of `isValidChash`/`isValidAddressAnyCase` to ensure input length/charset are fully validated before reaching `chash.js`, and confirm that unit/AA/device message validation entry points wrap all such checks in `try/catch` so a malformed field can never crash the process.

### Proof of Concept
Conceptual (not fully verified end-to-end due to tool-call limits): craft a 32-character string using characters accepted by the `thirty-two` package's decoder but which decode to a byte count other than 20 bytes (160 bits), and route it through any validation call that uses `isValidAddressAnyCase`/`isValidChash` directly instead of `isValidAddress`. This should reach `separateIntoCleanDataAndChecksum()` and throw `Error("bad length=...")` uncaught from within `chash.isChashValid`.

**Note on investigation limits:** I was unable to enumerate all production call sites of `isValidAddressAnyCase`/`isValidChash` or confirm the presence/absence of enclosing exception handling in each due to running out of tool-call iterations. This should be verified further (e.g., by starting a full Devin session with complete codebase access) before treating this as a confirmed crash-inducing vulnerability rather than a validation-hardening gap.
