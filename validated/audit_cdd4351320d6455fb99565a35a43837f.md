### Title
Unsanitized `feed_name`/oracle string allows data-feed key-boundary injection in LevelDB lookups - (File: `data_feeds.js`)

### Summary
CVE-2021-3027 is an LDAP injection caused by building a search filter from raw, unescaped user input, letting an attacker craft values that "escape" the intended filter boundary and match unintended records. The ocore analog is in `data_feeds.js`, where `feed_name` (and the colon-delimited oracle address list) — both attacker-controlled from oscript (`data_feed[[...]]` / `in_data_feed[[...]]`) — are concatenated directly, with no escaping of the `\n` delimiter, into LevelDB key prefixes used for range (`gte`/`lte`/`gt`/`lt`) queries.

### Finding Description
`readDataFeedByAddress` and `dataFeedByAddressExists` build key prefixes with plain string concatenation: [1](#0-0) [2](#0-1) 

`feed_name` comes straight from the oscript formula parameters with only an emptiness/type check — there is no restriction on which characters (including the `\n` record delimiter used everywhere as the field separator in these keys) may appear: [3](#0-2) [4](#0-3) 

Because the key format is `'df\n'+address+'\n'+feed_name+'\n'+prefixed_value+'\n'+mci` (or `'dfv\n'+address+'\n'+feed_name'`), and `feed_name` is not sanitized or length-delimited, a value containing embedded `\n` sequences can shift what the `gte/lte` range actually bounds — exactly the "escaping the provided search filter" root cause described in the CVE: input meant to be a single opaque token is instead interpreted as several delimiter-separated key components, letting the constructed prefix drift into a different `type`/`value`/`mci` sub-range or effectively broaden/narrow the intended match. This is reachable by any AA author or, per the test suite, even a plain trigger sender, since both `oracles` and `feed_name` can be built from evaluated formula expressions (including data taken from `trigger.data`/`input`): [5](#0-4) [6](#0-5) 

### Impact Explanation
AAs frequently use `data_feed`/`in_data_feed` results (e.g., price oracles, outcome oracles) to gate fund releases (swaps, prediction markets, insurance-style AAs). If a crafted `feed_name` can cause the LevelDB range query to match a record that does not correspond to the literal feed name the AA author intended (i.e., the filter is "escaped" the same way the LDAP filter is escaped in the CVE), an AA can be tricked into treating a value as satisfying its data-feed condition when the trusted oracle never posted that exact feed under that exact name/relation. That can lead to AA fund loss (paying out based on a spoofed/incorrect condition) or freezing (condition never resolves as intended). This satisfies the required "AA fund loss or freezing" impact bar.

### Likelihood Explanation
No privileged access is needed: an ordinary AA author (who chooses the `feed_name` string embedded in the AA's oscript) or a trigger sender supplying `feed_name`/`oracles` values dynamically from trigger data can attempt to construct delimiter-laden strings, since neither `formula/evaluation.js` nor `formula/validation.js` restrict `feed_name` content against embedded `\n` characters.

### Recommendation
- Reject or escape `\n` (and any other key-structural delimiter) inside `feed_name` and in each oracle address token before using them to build LevelDB key prefixes, or use a length-prefixed encoding for `feed_name` so its boundary cannot be confused with subsequent fields.
- Add explicit character-set/format validation for `feed_name` in `formula/validation.js` and `readDataFeedValueByParams` (analogous to how addresses are validated with `ValidationUtils.isValidAddress`), rejecting any feed name containing control characters.
- Add regression tests that attempt to smuggle `\n`-delimited payloads inside `feed_name` and verify no cross-feed/cross-type/cross-mci match occurs.

### Proof of Concept
1. Oracle O posts a data feed unit with `feed_name = "price"`, value `100` (numeric), creating (conceptually) key `df\nO\nprice\nn\n<enc(100)>\n<mci>`.
2. An AA (or the attacker, via a crafted trigger) evaluates `data_feed[[oracles="O", feed_name="price\nn\n<enc(100)>", ...]]` (or similar payload constructed via string `||` concatenation of trigger-controlled fields, as already demonstrated feasible in `test/formula.test.js:883-888` where the delimiter-laden feed name `'t,e(s)[],\'t'` is accepted without restriction).
3. Because `feed_name` is inserted unescaped into `key_prefix = 'df\n'+address+'\n'+feed_name+'\n'+prefixed_value'`, the extra embedded `\n<type>\n<value>` segments in the crafted `feed_name` shift the effective range boundaries used by `kvstore.createReadStream`/`createKeyStream`, allowing the lookup to match keys that do not correspond to a literal `feed_name="price"` posting — deviating from the oracle's actual, single intended feed record.
4. If the vulnerable AA's payout logic depends on that data-feed value, the attacker's crafted trigger can influence which stored record is matched, potentially forcing payout/withholding decisions the AA author never intended.

(Exact reproduction of a concrete cross-record collision requires constructing keys byte-for-byte in a running node/kvstore, which was not verified end-to-end in this review — the finding is based on direct source inspection of the unescaped concatenation, not a live exploit run.)
