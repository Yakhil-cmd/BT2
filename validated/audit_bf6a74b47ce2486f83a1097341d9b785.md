### Title
Webhook signature verification binds to `repository.owner.login`/`organization.login` from the *verifying* org, while `MembershipHandler` trusts an independently-read `organization.login` for its write, letting an attacker who controls one tracked org's webhook secret forge team membership data for a different org - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#repository_owner` selects the `GitHubApp` (and thus the HMAC secret) used to verify a webhook from `params.dig('repository','owner','login')` with a fallback to `params.dig('organization','login')`. `MembershipHandler` independently re-reads `params.organization.login` to decide which organization's `Team` record to create/mutate, with no check that this value matches the organization whose secret verified the request. Because the request body is fully attacker-controlled, an attacker who owns/controls one Shipit-tracked organization (and therefore legitimately knows that organization's `webhook_secret`) can craft a single POST to `/webhooks` where `repository.owner.login` names their own org (for HMAC key selection) while `organization.login` names an unrelated victim org (for the mutating write), breaking the intended binding between "who was cryptographically verified" and "whose data gets written."

### Finding Description
The broken binding: `repository_owner` (i.e., `params.dig('repository','owner','login') || params.dig('organization','login')`) used in `verify_signature` to pick the `GitHubApp` == `params.organization.login` used by `MembershipHandler#find_or_create_team!` to set `team.organization`. These are read independently and never cross-checked.

- `verify_signature` calls `Shipit.github(organization: repository_owner)` and verifies `X-Hub-Signature` against that org's `webhook_secret`: [1](#0-0) 
- `repository_owner` reads `repository.owner.login` first, falling back to `organization.login`, purely from the raw JSON body the attacker POSTs: [2](#0-1) 
- `MembershipHandler` independently requires and reads `params.organization.login` (schema only enforces presence, not equality to anything) to create the `Team` and set its organization, and to add the attacker-supplied `member.login` to that team: [3](#0-2) 

Exploit flow: attacker legitimately owns/controls an org `secretless-org` that a Shipit operator has configured (with a known `webhook_secret` the attacker set/knows, since they administer that org's GitHub App integration into this Shipit instance). Attacker sends `POST /webhooks` with `X-Github-Event: membership` and body:
```
{
  "action": "added",
  "team": {"id": 1, "name": "n", "slug": "s", "url": "u"},
  "organization": {"login": "victim-org"},
  "member": {"login": "attacker-login"},
  "repository": {"owner": {"login": "secretless-org"}}
}
```
signed with the HMAC secret for `secretless-org`. `verify_signature` resolves `repository_owner` to `secretless-org`, selects that org's `GitHubApp`, and the signature checks out - the request is accepted. `MembershipHandler` then runs `find_or_create_team!`, writing `team.organization = "victim-org"` and adding `attacker-login` to that team, entirely decoupled from the org that was actually cryptographically verified.

None of the existing guards catch this: `drop_unhandled_event` only checks the event type is handled; `ExplicitParameters` schema (`requires :organization do requires :login, String end`) only enforces presence/type, not cross-field consistency with `repository_owner`; `verify_signature`/`GitHubApp#verify_webhook_signature` verify authenticity of the *signing* org only, never that the payload's semantic organization matches it: [4](#0-3) .

### Impact Explanation
A `Team` record can be created/mutated for `victim-org` with an attacker-chosen `github_id`, and an attacker-controlled GitHub login can be added as a member of that team. If any team for `victim-org` is referenced by `Shipit.github_teams` for authorization checks (`User#authorized?`/`require_permission!`), this is a path to escalate into privileged Shipit roles for an organization the attacker never authenticated against - matching the High severity category ("escalation into `Shipit.github_teams` authorization"). It is repeatable against any victim organization name and any team id/slug the attacker chooses, as long as the attacker controls a webhook secret for one Shipit-tracked org used purely as the "signing" identity.

### Likelihood Explanation
Preconditions: the attacker must control (or know the webhook secret of) at least one organization already configured in this Shipit instance's `github_apps`/`Shipit.github` mapping (e.g., their own org added to be tracked). Given that, forging the request costs nothing beyond computing an HMAC-SHA1 signature over an arbitrary JSON body they fully control, and the endpoint `POST /webhooks` is unauthenticated by design (webhook ingress). This is straightforward and repeatable once the attacker has one legitimate tracked org.

### Recommendation
In `MembershipHandler` (and any other handler that reads `organization.login` or `repository.owner.login` for record identity), require that the payload's organization/owner field equals the `repository_owner` value used for signature verification, rejecting (422) the webhook otherwise. Alternatively, pass the verified `repository_owner` into the handler context and use it - not a re-parsed payload field - as the authoritative organization for any write.

### Proof of Concept
Minitest sketch (`test/controllers/shipit/webhooks_controller_test.rb`):
```ruby
test "membership webhook cannot bind team to an organization different from the verified repository_owner" do
  secretless_secret = Shipit.github(organization: 'secretless-org').send(:webhook_secret) # attacker-known secret
  payload = {
    action: 'added',
    team: { id: 999, name: 'n', slug: 's', url: 'u' },
    organization: { login: 'victim-org' },
    member: { login: 'attacker-login' },
    repository: { owner: { login: 'secretless-org' } }
  }.to_json

  signature = 'sha1=' + OpenSSL::HMAC.hexdigest('sha1', secretless_secret, payload)

  post shipit.hooks_path, params: payload,
       headers: { 'X-Github-Event' => 'membership', 'X-Hub-Signature' => signature, 'Content-Type' => 'application/json' }

  assert_response :ok
  team = Team.find_by(github_id: 999)
  # Demonstrates the divergence: verification passed for 'secretless-org' but the write landed on 'victim-org'
  assert_equal 'victim-org', team.organization
end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
