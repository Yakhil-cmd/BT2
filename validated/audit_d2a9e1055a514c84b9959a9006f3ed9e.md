### Title
Address-definition-change race condition allows a compromised co-signer to spend funds after revocation is submitted but before it stabilizes - ([File: definition.js], [File: validation.js], [File: storage.js])

### Summary
Obyte lets an address holder replace the signing definition of an address by posting an `address_definition_change` message, the on-chain analog of `setSignatureValidatorApproval`'s "swap out an approved signer" pattern. Exactly like the WETH9 report, the new definition only takes effect once the change unit becomes stable, so there is a window in which a party who still holds the old (compromised/revoked) signing key can post spending units against the address that will still validate successfully with the old definition.

### Finding Description
When validating who is allowed to sign for an address, `readDefinitionByAddress`/`readDefinitionChashByAddress` resolve the address's *effective* definition by looking at `address_definition_changes` joined with `units`, filtered by `main_chain_index<=last_ball_mci` of the *unit being validated* — not by "the very latest change known to the network": [1](#0-0) 

This means any two units can each pick their own `last_ball_mci` snapshot of the address's DAG history. Any unit built by whoever holds the *old* signing keys, referencing a `last_ball` unit that predates the point at which the definition-change unit becomes stable, still resolves to the old definition and is accepted as valid: [2](#0-1) 

The definition-change message itself only records the new `definition_chash`; the actual new definition can be disclosed later, and until that disclosure/stabilization, both the old signer and (once revealed) the address owner are effectively racing over which snapshot of history ends up in later units' `last_ball_mci`: [3](#0-2) 

This is structurally identical to `setSignatureValidatorApproval`: revocation of an authority (there, `allowedValidators`; here, the address definition/signing keys) is not atomic with respect to the underlying resource (funds at the address). A holder of the outgoing authority can front-run the revocation because unconfirmed/pending units are visible in the network before they are included and stabilized in the MC, and the old definition remains valid for any unit whose `last_ball_mci` precedes stabilization of the change.

### Impact Explanation
If a co-signer key of a multi-authority (or shared/multisig) address is known to be compromised, the legitimate owner posts an `address_definition_change` to remove/replace that key. Because Obyte's validation resolves the applicable definition per-unit `last_ball_mci` rather than "as of the moment the spending unit is received," the compromised key holder can, upon observing the pending revocation unit in the network (before it is stable), immediately author and broadcast a spending unit using the still-valid old definition that references an earlier last-ball. If this malicious unit gets included and its `main_chain_index` ends up ≤ the point required, it is validated as good and funds are stolen/misappropriated before the revocation takes effect — a concrete unauthorized-spending scenario, not merely a theoretical race.

### Likelihood Explanation
Exploitation requires: (1) an address definition using a "sig"/co-signer that has been compromised, (2) the owner detecting the compromise and posting a revocation (`address_definition_change`), and (3) the attacker observing the pending unit before it stabilizes and immediately broadcasting a conflicting spend using the old key. Given Obyte's typical multi-second-to-minutes stabilization latency for units to become final via witnesses, this window is realistic and directly mirrors the external report's exploit scenario (Alice revokes Bob's validator approval; attacker races to use it first).

### Recommendation
- Short term: Document for wallet/shared-address users that revoking a compromised signing key does not immediately invalidate spends authored with the old key; instruct users to move funds to a new address immediately upon suspected compromise rather than relying on `address_definition_change`.
- Long term: Consider tightening `address_definition_change` semantics so that any unit spending from the address must reference a `last_ball_mci` at or after the change's inclusion once the change is broadcast (e.g., treat pending/known-but-unstable definition changes as immediately blocking further spends from the old definition, or require witnesses/algorithm to prioritize the definition-change unit's ordering), and/or monitor `address_definition_changes` events to detect and challenge front-running spends before they stabilize.

### Proof of Concept
1. Address `A` is defined with `["sig", {pubkey: K_old}]` (or an `and`/`or` combination including `K_old` as one signer).
2. Owner discovers `K_old` compromised and broadcasts unit `U_change` containing `address_definition_change` with `definition_chash` of a new definition excluding `K_old`. [2](#0-1) 
3. Attacker holding `K_old` observes `U_change` in the mempool before it stabilizes, and immediately composes/broadcasts unit `U_steal`, signed with `K_old`, spending funds from `A`, with `last_ball_mci` set to a value before `U_change` is stable.
4. During validation of `U_steal`, `readDefinitionByAddress`/`readDefinitionChashByAddress` resolve `A`'s definition using `main_chain_index<=U_steal.last_ball_mci`, which is still the old (compromised) definition because `U_change` has not yet reached that MCI/stability: [1](#0-0) 
5. `U_steal` passes `validateAuthentifiers`/signature checks against the old definition and is accepted as valid, resulting in unauthorized spending from `A` despite the owner's revocation attempt.

function readDefinitionChashByAddress(conn, address, max_mci, handle){
	if (!handle)
		return new Promise(resolve => readDefinitionChashByAddress(conn, address, max_mci, resolve));
	if (max_mci == null || max_mci == undefined)
		max_mci = MAX_INT32;
	// try to find last definition change, otherwise definition_chash=address
	conn.query(
		"SELECT definition_chash FROM address_definition_changes CROSS JOIN units USING(unit) \n\
		WHERE address=? AND is_stable=1 AND sequence='good' AND main_chain_index<=? ORDER BY main_chain_index DESC, level DESC LIMIT 1", 
		[address, max_mci], 
		function(rows){
			var definition_chash = (rows.length > 0) ? rows[0].definition_chash : address;
			handle(definition_chash);
	});
}

CREATE TABLE address_definition_changes (
	unit CHAR(44) NOT NULL,
	message_index TINYINT NOT NULL,
	address CHAR(32) NOT NULL,
	definition_chash CHAR(32) NOT NULL, -- might not be defined in definitions yet (almost always, it is not defined)
	PRIMARY KEY (unit, message_index),
	UNIQUE  (address, unit),
	FOREIGN KEY (unit) REFERENCES units(unit),
	CONSTRAINT addressDefinitionChangesByAddress FOREIGN KEY (address) REFERENCES addresses(address)
);
