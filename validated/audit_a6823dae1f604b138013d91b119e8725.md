### Title
Missing check that `input_vault != output_vault` allows a same-token "swap" - ([File: programs/cp-swap/src/instructions/swap_base_input.rs])

### Summary
The `Swap` accounts struct used by both `swap_base_input` and `swap_base_output` validates `input_vault` and `output_vault` independently, each only requiring that it equals *either* `pool_state.token_0_vault` or `pool_state.token_1_vault`, without ever asserting the two vaults (and therefore the two token mints) are different from each other.

### Finding Description
In `programs/cp-swap/src/instructions/swap_base_input.rs`, the `Swap<'info>` account constraints are: [1](#0-0) 

Both `input_vault` and `output_vault` are checked with an `OR` condition against the pool's two vaults, but there is no constraint that `input_vault.key() != output_vault.key()`. The mints are then derived directly from the vaults via `address = input_vault.mint` / `address = output_vault.mint`: [2](#0-1) 

Because the mint fields are just mirrors of whatever vault account the caller passes in, a caller can pass the **same vault** (e.g. `token_0_vault`) for both `input_vault` and `output_vault`. This satisfies every Anchor constraint (`token_0_vault == token_0_vault` is true for both fields), and `input_token_mint`/`output_token_mint` will resolve to the same mint. `pool_state.get_swap_params(...)` then computes swap parameters using `total_input_token_amount` and `total_output_token_amount` both derived from the same vault balance, and the constant-product math and fee split proceed as if this were a valid two-sided swap: [3](#0-2) 

Finally, the instruction performs a real token transfer *into* the vault (`transfer_from_user_to_pool_vault`) and a real token transfer *out of* the same vault (`transfer_from_pool_vault_to_user`) for the identical mint/vault: [4](#0-3) 

This is the same root cause pattern as the referenced report: the protocol never rejects a degenerate "swap" where the input and output sides refer to the same underlying asset, so a no-op (or self-referential) trade is processed as if it were a genuine two-token exchange, and protocol/fund/creator fees are computed and deducted from vault accounting that has no real counterpart asset movement.

### Impact Explanation
Because the vault balance used as `total_output_token_amount` is read *before* the input transfer lands (the `get_swap_params` call happens prior to the transfers), and the same vault is both credited and debited within the same instruction against curve math that assumes two distinct pools of liquidity, this creates an accounting mismatch on the single real vault: the constant-product invariant check (`constant_after >= constant_before`) is validated against a synthetic `k = balance * balance` rather than `k = token0_balance * token1_balance`, which does not correspond to any real solvency invariant of the pool. This allows fee accounting (protocol_fee/fund_fee/creator_fee state) to be manipulated and can be used to siphon or misstate vault/fee-ledger balances without a genuine two-asset trade, an insolvent/incorrect pool-accounting condition matching the severity bar of "insolvent pool or fee-ledger accounting."

### Likelihood Explanation
Any unprivileged trader can construct a single transaction with `input_vault == output_vault == token_0_vault` (or `token_1_vault`) and matching mint/token accounts, satisfying all existing Anchor constraints, since no distinctness check exists between the two vault/mint fields.

### Recommendation
Add an explicit constraint in the `Swap` accounts struct (and equivalently for the `swap_base_output` path, which reuses the same struct) requiring `input_vault.key() != output_vault.key()` (and/or `input_token_mint.key() != output_token_mint.key()`), rejecting any swap where the input and output resolve to the same pool vault/mint.

### Proof of Concept
1. Attacker creates a pool normally with `token_0`/`token_1`.
2. Attacker calls `swap_base_input` (or `swap_base_output`), passing `input_vault = pool_state.token_0_vault` and `output_vault = pool_state.token_0_vault` (same account), with `input_token_account`/`output_token_account` both being the attacker's own `token_0` ATA.
3. Both the `input_vault` and `output_vault` constraints in `programs/cp-swap/src/instructions/swap_base_input.rs` pass because each is independently checked against `token_0_vault || token_1_vault`.
4. `pool_state.get_swap_params` computes swap parameters treating the single vault balance as both sides of the trade, `CurveCalculator` computes an `input_amount`/`output_amount` and fee split, and the instruction performs a real transfer into and out of the same vault, corrupting the fee-ledger/vault accounting for a degenerate same-asset trade.
