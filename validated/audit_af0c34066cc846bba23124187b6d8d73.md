### Title
API-authenticated client can attribute privileged actions (locks, deploys, merges) to an arbitrary user identity via the `X-Shipit-User` header - ([File: app/controllers/shipit/api/base_controller.rb])

### Summary
The `Api::BaseController` binds `current_user` for API requests to whatever login is supplied in the unauthenticated `X-Shipit-User` request header, with no cryptographic or session tie to that identity. This is structurally the same class of bug as the Ambire finding: a value that drives privileged downstream behavior (there, the recovery nonce/timelock state; here, the acting `User` record) is not bound to the credential that was actually verified (there, the recovery signature; here, the `ApiClient` bearer token).

### Finding Description
`Api::BaseController#authenticate_api_client` verifies only the `ApiClient` bearer token via HTTP Basic auth and `ApiClient.authenticate`: [1](#0-0) 

Separately, `current_user`/`identify_user` derives the acting `User` purely from the client-supplied `X-Shipit-User` header, with no signature, no session, and no relation to the authenticated `ApiClient`: [2](#0-1) 

That `current_user` is then passed straight into privileged, attributed actions across multiple controllers:
- Locking/unlocking a stack: `stack.lock(params.reason, current_user)` [3](#0-2) 
- Triggering/aborting arbitrary tasks: `stack.trigger_task(params[:task_name], current_user, env: params.env)` and `task.abort!(aborted_by: current_user)` [4](#0-3) 
- Triggering deploys: `stack.trigger_deploy(commit, current_user, env: params.env, ...)` [5](#0-4) 
- Triggering rollbacks / aborting active tasks: `active_task.abort!(aborted_by: current_user, ...)` / `deploy.trigger_rollback(current_user, ...)` [6](#0-5) 
- Requesting a merge, which is later embedded in the merge commit message (`Merge-Requested-By`) written back to GitHub: `MergeRequest.request_merge!(stack, params[:id], current_user)` and `merge_message` [7](#0-6) [8](#0-7) 
- Reporting release health/faultiness: `deploy.report_healthy!(user: current_user)` [9](#0-8) 

Authorization is enforced purely at the `ApiClient` level via `require_permission`/`check_permissions!` (a coarse scope like `deploy:stack`), which is orthogonal to `current_user`: [10](#0-9) 

The binding that should hold is: *identity attributed to an action == identity that authenticated the request*. Instead: *identity attributed to an action == attacker-supplied header value*, while only the coarse client-scope credential is verified. This is analogous to the Ambire report's core defect — a value consumed by privileged state transitions (there: nonce/timelock gating recovery replay; here: the `User` record gating attribution and audit trail) is not covered by the verification that actually occurred (there: the recovery signature over the bundle; here: the `ApiClient` token authentication).

### Impact Explanation
Any holder of a valid `ApiClient` token (which may be scoped to a single stack with e.g. only `deploy:stack`) can impersonate any `User` in the Shipit database for the purposes of:
- Merge commit attribution written into the actual GitHub repository history (`Merge-Requested-By: <arbitrary-login>` via `merge!`) — this is a falsified audit trail baked into a cross-repository write.
- Deploy/rollback/task/lock actions being recorded as performed by an arbitrary user, undermining any authorization or audit logic downstream that trusts `current_user` (e.g. `deploy_spec` hooks, notifications, `lock_author` display, `report_healthy!`/`report_faulty!` attribution used to gate rollout status).

This does not, by itself, grant a token new `ApiClient` permissions, but it breaks the identity-verification binding used to attribute and audit privileged GitHub-writing actions, and the merge-message injection results in falsified data written directly into the repository via the app's GitHub credentials.

### Likelihood Explanation
High for any party holding a legitimate `ApiClient` token (a normal, intended usage scenario for CI systems calling the Shipit API) — no additional privilege, secret, or session is required beyond the token they already have; the `X-Shipit-User` header is entirely self-asserted and unauthenticated.

### Recommendation
Do not derive `current_user` for API requests from an unauthenticated header. Either (a) remove the `X-Shipit-User` identity-attribution feature for privileged writes, or (b) bind the asserted user to the authenticated `ApiClient`'s `creator`, or (c) require a signed/verifiable assertion (e.g., a per-user signed token, not a bare login string) so that the identity used for attribution is cryptographically tied to the same credential that was verified in `authenticate_api_client`.

### Proof of Concept
1. Obtain any valid `ApiClient` token scoped to a stack (e.g., `deploy:stack` permission only).
2. Send `PATCH /api/.../merge_requests/:id` (or `POST /api/.../deploys`, `.../locks`, `.../tasks/:name`) with header `Authorization: Basic <valid token>` and `X-Shipit-User: admin-login`.
3. Observe `current_user` resolves to the `User` record for `admin-login` [11](#0-10) , and the resulting merge commit / lock / deploy / task is attributed to `admin-login` even though the requester never authenticated as that user.

        @current_api_client = if Shipit.disable_api_authentication
                                UnlimitedApiClient.new

      def create
        commit = stack.commits.by_sha(params.sha) || param_error!(:sha, 'Unknown revision')
        param_error!(:force, "Can't rollback a locked stack") if !params.force && stack.locked?
        deploy = stack.deploys.find_by(until_commit: commit) || param_error!(:sha, 'Cant find associated deploy')
        rollback_env = stack.filter_rollback_envs(params.env)

        response = nil
        if !params.force && stack.active_task?
          param_error!(:force, "Can't rollback, deploy in progress")
        elsif stack.active_task?
          active_task = stack.active_task
          active_task.abort!(aborted_by: current_user, rollback_once_aborted_to: deploy, rollback_once_aborted: true)
          response = active_task
        else
          response = deploy.trigger_rollback(current_user, env: rollback_env, force: params.force, lock: params.lock)
        end

        render_resource(response, status: :accepted)
      end
