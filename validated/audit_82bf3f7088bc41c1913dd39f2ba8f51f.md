Confirmed. The vulnerable logic is real, and matches exactly what the question describes.### Title
`OpenedHandler#provision?` ignores `review_stacks_enabled` for `allow_with_label` and `prevent_with_label` behaviors due to operator precedence - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`provision?` in `OpenedHandler` uses `&&`/`||` without parentheses grouping the `review_stacks_enabled` gate around all three provisioning behaviors, so the flag only guards `allow_all`. For repositories configured with `allow_with_label` or `prevent_with_label`, review stacks are provisioned even when `review_stacks_enabled` is `false`, letting any user who can open a pull request or apply/omit a label trigger stack creation on a repository the operator believes has review stacks disabled.

### Finding Description
The claimed binding is: for all `provisioning_behavior` values, `repository.review_stacks_enabled == true` must be necessary for `provision? == true`. This currently only holds for `provisioning_behavior_allow_all?`.

The code:
```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
``` [1](#0-0) 

Ruby's `&&` binds tighter than `||`, so this parses as:
```ruby
(repository.review_stacks_enabled && repository.provisioning_behavior_allow_all?) ||
(repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
(repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
```
`review_stacks_enabled` is only ANDed into the first disjunct. For `provisioning_behavior_allow_with_label?` with a matching label, or `provisioning_behavior_prevent_with_label?` with the label absent, `provision?` returns `true` regardless of `review_stacks_enabled`.

Call path: `process` calls `respond_to_pull_request_opened?` which is `params.action == "opened" && provision?`, then calls `ReviewStackAdapter#find_or_create!`, which calls `create!` and inserts a `ReviewStack`/`Stack` row and enqueues it via `Shipit::ReviewStackProvisioningQueue.add(stack)`. [2](#0-1) [3](#0-2) 

No other guard checks `review_stacks_enabled` before this. `respond_to_pull_request_opened?` only checks the action string and `provision?`. Existing tests in `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` cover `allow_all` + disabled (correctly blocked, lines 96-107) and `allow_with_label`/`prevent_with_label` combinations, but every one of those tests uses the default `provisioning_enabled: true` for the label-based behaviors — none test `review_stacks_enabled: false` combined with `allow_with_label` or `prevent_with_label`, so the gap is untested and unnoticed. [4](#0-3) 

Exploit: an attacker who can open a pull request against a repository previously configured with `provisioning_behavior = allow_with_label` (or `prevent_with_label`) — even after the operator sets `review_stacks_enabled = false` to shut off review-stack provisioning entirely — can still create a `ReviewStack` and queue it for provisioning simply by opening a PR with (or without) the configured label, since none of `verify_signature`, `drop_unhandled_event`, or the `ExplicitParameters` schema check `review_stacks_enabled`.

### Impact Explanation
A successful request causes an unauthorized `Stack`/`ReviewStack` row to be created and queued via `Shipit::ReviewStackProvisioningQueue.add(stack)` for a repository whose operator explicitly disabled review-stack auto-provisioning. Downstream provisioning of that queued stack can trigger deploy-time hooks/tasks (`Command`/`PTY.spawn` execution paths used elsewhere in provisioning), i.e., an unauthorized deploy/provisioning action performed against operator intent — matching the Critical category of "unauthorized deploy" triggered without proper authorization. The blast radius is limited to repositories that were ever configured with `allow_with_label` or `prevent_with_label`, but is repeatable for every PR opened/labeled against such a repo.

### Likelihood Explanation
Preconditions: a repository record must have `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` (a historical/lingering configuration state), regardless of the current `review_stacks_enabled` value. No secrets, sessions, or privileged roles are required — only the ability to open a pull request (or control PR labels) against that repository, which is standard unprivileged GitHub user capability. This is low-cost and fully repeatable.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates all three behaviors:
```ruby
def provision?
  repository.review_stacks_enabled && (
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
  )
end
```

### Proof of Concept
Add to `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`, table-driving all three behaviors with `review_stacks_enabled: false`:
```ruby
[:allow_all, :allow_with_label, :prevent_with_label].each do |behavior|
  [true, false].each do |label_present|
    test "review_stacks_enabled=false blocks provisioning for #{behavior} (label_present=#{label_present})" do
      repository = shipit_repositories(:shipit)
      configure_provisioning_behavior(
        repository:,
        provisioning_enabled: false,
        behavior:,
        label: "pull-requests-label"
      )
      payload = payload_parsed(:pull_request_opened)
      payload["pull_request"]["labels"] = label_present ? [{ "name" => "pull-requests-label" }] : []

      assert_no_difference -> { Shipit::Stack.count } do
        OpenedHandler.new(payload).process
      end
    end
  end
end
```
Before the fix, the `allow_with_label`/label_present=true and `prevent_with_label`/label_present=false cases fail (`Shipit::Stack.count` increases despite `review_stacks_enabled == false`); after applying the parenthesization fix, all six combinations pass with no stack created.
