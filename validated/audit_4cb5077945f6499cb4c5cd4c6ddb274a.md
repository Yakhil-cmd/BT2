### Title
Validator Nodekey Exposed via `--private-key` CLI Flag Enables Unauthorized AddressBookV2 State Transitions — (`File: cmd/kcn/abv2.go`)

### Summary

The `kcn valops` production CLI tool accepts the validator's ECDSA private key as a plaintext hex argument via `--private-key`. CLI arguments are globally readable on Linux via `/proc/<pid>/cmdline` and `ps aux`, and are persisted in shell history. An attacker who reads the exposed key can impersonate the validator and submit unauthorized state-transition transactions to the `AddressBookV2` system contract at `0x400`, forcibly removing or pausing the validator from the active consensus set.

### Finding Description

`cmd/kcn/abv2.go` defines `abv2PrivateKeyFlag` as a `cli.StringFlag` named `"private-key"` that accepts a hex-encoded ECDSA private key directly on the command line:

```go
abv2PrivateKeyFlag = &cli.StringFlag{
    Name:  "private-key",
    Usage: "Hex-encoded private key (default: load from " + defaultNodeKeyPath + ")",
}
``` [1](#0-0) 

The `loadKey` function reads this value and converts it to an `*ecdsa.PrivateKey` used to sign all subsequent transactions:

```go
func loadKey(ctx *cli.Context) (*ecdsa.PrivateKey, error) {
    if keyHex := ctx.String("private-key"); keyHex != "" {
        return crypto.HexToECDSA(strings.TrimPrefix(keyHex, "0x"))
    }
    return crypto.LoadECDSA(defaultNodeKeyPath)
}
``` [2](#0-1) 

The README explicitly documents and encourages this usage pattern with examples such as:

```sh
kcn valops suspend-validator --node-id 0xABCD... --private-key 0x1234...
kcn valops ready-validator --private-key 0x1234... --endpoint /tmp/klay.ipc
``` [3](#0-2) 

The key loaded is the validator's **nodekey** — the same key that controls all node-operator state transitions in `AddressBookV2` (`onlyNodeId` guard), as documented:

> `nodekey` | node identity (p2p) + createNode `nodeId`; signs state transitions (onlyNodeId) [4](#0-3) 

This key is used to sign transactions to the `AddressBookV2` system contract at `system.AddressBookAddr` (`0x400`) for all node-operator subcommands: [5](#0-4) 

### Impact Explanation

An attacker who obtains the exposed key (via `ps aux`, `/proc/<pid>/cmdline`, shell history, or CI/CD logs) can submit signed transactions to `AddressBookV2` as the validator node, calling:

- `exit(nodeId)` — removes the validator from the validator set entirely
- `offboard(nodeId)` — offboards the validator
- `pause(nodeId)` — removes the validator from active consensus participation
- `unreadyValidator(nodeId)` / `unreadyCandidate(nodeId)` — transitions the validator out of active states

These are protected state transitions in the `AddressBookV2` system contract that directly alter the on-chain validator set, affecting consensus participation and KAIA block reward distribution. [6](#0-5) [7](#0-6) 

### Likelihood Explanation

The README presents `--private-key 0x...` as a normal, documented usage pattern. Any operator on a shared machine (cloud VM, managed hosting, CI/CD pipeline) who follows the documented examples exposes the key. On Linux, any local user can read `/proc/<pid>/cmdline` for processes they can observe, and shell history files are frequently world-readable or accessible to co-tenants. The trigger requires no special privileges beyond local access or shell history access.

### Recommendation

Remove the `--private-key` flag entirely. The default behavior — loading the key from the file at `defaultNodeKeyPath` — is already secure. For cases where a non-default key path is needed, accept a `--private-key-file <path>` flag pointing to the key file, never the raw hex value. This mirrors the pattern already used by the node itself (`--nodekey <file>` vs. the discouraged `--nodekeyhex`).

### Proof of Concept

1. Operator runs on a shared Linux host:
   ```sh
   kcn valops exit --private-key 0xDEADBEEF...CAFEBABE
   ```
2. A co-tenant or monitoring process reads the process arguments:
   ```sh
   cat /proc/$(pgrep kcn)/cmdline | tr '\0' ' '
   # → kcn valops exit --private-key 0xDEADBEEF...CAFEBABE
   ```
3. Attacker extracts the hex key and constructs a transaction calling `exit(nodeId)` on `AddressBookV2` at `0x400`, signed with the stolen key.
4. The transaction is accepted by the chain (the `onlyNodeId` guard is satisfied by the stolen key), and the validator's state is changed to `ValExiting`, removing it from the active consensus set and halting its reward distribution.
