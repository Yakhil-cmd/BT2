### Title
Cross-tenant Status description injection via unscoped `Commit.where(sha:)` lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits solely by `sha`, with no scoping to the repository/organization that authenticated the webhook, and writes `params.description` verbatim to every matching `Commit` across all stacks. Because webhook signature verification only proves the payload came from the org named in `repository.owner.login`, an attacker who controls a repo/org onboarded to the Shipit instance (e.g. their own fork tracked as a stack) can send a `status` event whose `sha` matches a commit shared by another tenant's stack (common ancestor commit), overwriting that other tenant's `Status#description`.

### Finding Description
The binding the code should enforce is: `verified_org == repository_owner_of(params)` AND `commit.stack.repository.owner == repository_owner_of(params)` for every `Commit` mutated. In reality, `WebhooksController#verify_signature` only checks the first half — `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [1](#0-0)  — and never re-checks that the commits touched downstream actually belong to that same `repository_owner`.

`StatusHandler#process` then does:
```
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [2](#0-1) 

This query is global across the `commits` table with no `stack_id`/repository filter, so it matches every `Commit` row with that `sha`, regardless of which stack/repository it belongs to. `create_status_from_github!` then writes the attacker-supplied `description`, `state`, `target_url`, `context` into a `Status` for each matched commit via `statuses.replicate_from_github!(stack_id, github_status)` [3](#0-2) .

If two stacks (belonging to different tenants/orgs) happen to share a commit `sha` — plausible for shared ancestor commits before a fork diverges, or intentionally crafted by an attacker who mirrors a known upstream sha into their own repo/branch and gets Shipit to record a `Commit` row with that sha (e.g. by pushing/opening a PR referencing that sha in a repo tracked by Shipit) — a `status` webhook signed with the attacker's own org's webhook secret will still update the `Status` of the *victim* stack's `Commit` with the same sha, since the lookup is not scoped to `repository_owner`.

Existing guards do not prevent this: `verify_signature` only authenticates that the payload was signed by the org identified in the payload's own `repository.owner.login` field [1](#0-0) ; nothing in `StatusHandler` cross-checks that field against the `stack`/repository of the `Commit` rows being mutated. The `ExplicitParameters` schema in `StatusHandler` only validates types (`sha`, `state`, `description`, etc.), not ownership [4](#0-3) .

### Impact Explanation
Impact matches "a payload for one repository mutating another's stack, commit, task or team" (Critical). An attacker who controls an org/repo already tracked by the Shipit instance (any onboarded tenant, including a low-trust fork) can inject an arbitrary string into another tenant's `Status#description`, which is displayed on that other tenant's dashboard. The attack is repeatable against any sha collision across tenants and scales to every stack sharing that sha (dozens of stacks in the scenario described), amplifying a single forged webhook into many cross-tenant writes. It does not grant code execution or credential exfiltration, but it is an unauthorized cross-tenant data write triggered by an unauthenticated-relative-to-target party.

### Likelihood Explanation
Preconditions are non-trivial but realistic in the stated threat model: the attacker must (a) control an org/repo that Shipit already tracks (so they have a legitimate webhook secret for their *own* org), and (b) get a `Commit` row with a shared `sha` created under a victim's stack — which happens naturally for monorepo forks/common ancestor commits pulled in via normal GitHub sync, without any attacker action against the victim. Given those preconditions, the exploit costs only a single crafted HTTP POST to `/webhooks` with a valid signature for the attacker's own org and requires no interaction with the victim, GitHub secrets, or elevated Shipit privileges — it is fully repeatable.

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` (and any similar handler doing sha-only lookups) to commits belonging to stacks whose repository matches the authenticated `repository_owner`/`repository.full_name` from the verified payload, e.g. join `Commit` to `Stack`/`Repository` and filter by `owner`/`name` derived from `params.repository`, instead of a bare `Commit.where(sha: params.sha)`.

### Proof of Concept
Minitest plan (webhooks controller / model test, no live GitHub):
1. Fixtures: create two stacks in different "orgs" — `stack_victim` (owner `victim-org/repo`) and `stack_attacker` (owner `attacker-org/repo`), each with a `GithubHook` with distinct secrets.
2. Create `commit_victim` under `stack_victim` and `commit_attacker` under `stack_attacker`, both with the identical `sha` (`shared_sha`).
3. Stub `verify_signature` to succeed only for `attacker-org` (simulate a correctly signed webhook from the attacker's own org).
4. POST to `/webhooks` with `X-Github-Event: status`, body `{ sha: shared_sha, state: 'failure', description: 'PWNED-BY-ATTACKER', repository: { owner: { login: 'attacker-org' } } }`.
5. Assert:
   - `commit_attacker.statuses.last.description == 'PWNED-BY-ATTACKER'` (expected, same-tenant write).
   - `commit_victim.reload.statuses.last.description == 'PWNED-BY-ATTACKER'` — this assertion succeeding demonstrates the vulnerability: a payload authenticated only for `attacker-org` mutated `commit_victim`, which belongs to `victim-org`, violating the intended binding `verified_org == owner_of(mutated_commit.stack)`.
