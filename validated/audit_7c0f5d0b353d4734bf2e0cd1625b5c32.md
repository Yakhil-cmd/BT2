### Title
Webhook signature selection keyed on attacker-controlled `repository.owner.login` allows forging events for any other organization when one configured org has `webhook_secret: nil` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and therefore which `webhook_secret`) to verify the request against using `repository_owner`, which is read straight from the attacker-controlled JSON body [1](#0-0) . Nothing ties that value to the `organization.login`/`team.id`/`member.login` fields that `MembershipHandler#process` actually acts on [2](#0-1) , so if any configured org has a `nil` `webhook_secret`, that org's identity can be used to satisfy signature verification while the payload's `organization`/`team` fields target a completely different, properly-secured org.

### Finding Description
The broken binding is: **organization that authenticated the request** (`repository_owner` used in `Shipit.github(organization: repository_owner)`) **== organization whose Team/Membership is mutated** (`params.organization.login` / `params.team.id` used by `MembershipHandler`).

- `repository_owner` is computed purely from attacker-supplied JSON: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0) .
- `verify_signature` calls `Shipit.github(organization: repository_owner)` and then `github_app.verify_webhook_signature(...)` [3](#0-2) .
- `verify_webhook_signature` returns `true` unconditionally when `webhook_secret` is blank for that org's config: `return true unless webhook_secret` [4](#0-3) .
- After verification passes, `MembershipHandler#process` reads `params.organization.login` and `params.team.id` — entirely independent fields from the same attacker JSON body — to find-or-create a `Team` and add a member to it [2](#0-1) .

So an attacker who crafts a JSON body with `repository.owner.login = 'attacker-org'` (an org configured in Shipit with `webhook_secret` left nil, as the example config schema shows is valid: `webhook_secret: # nil` [5](#0-4) ) but `organization.login = 'shopify'` and `team.id` equal to an existing `shopify` `Team`'s `github_id`, causes `verify_signature` to authenticate against `attacker-org`'s (no-op) secret while the handler mutates `shopify`'s team membership.

Existing guards don't prevent this: `drop_unhandled_event` only checks the event type is registered, not payload consistency; the `ExplicitParameters` schema in `MembershipHandler` validates field *types*, not that `organization.login` matches `repository_owner`; `GithubOrganizationUnknown` only guards against wholly unconfigured orgs, not org-confusion between two configured orgs.

### Impact Explanation
If successful, the attacker's own GitHub user (`member.login = 'attacker'`) is added as a member of an existing `Shipit::Team` belonging to `shopify`, and if that team's `github_id`/handle is in `Shipit.github_teams`, `User#authorized?` becomes `true` for the attacker [6](#0-5) . This is a cross-tenant authorization escalation ("High" per the rubric: escalation into `Shipit.github_teams` authorization) achieved via a payload for one organization (`attacker-org`) mutating another organization's (`shopify`) team/authorization state. It is repeatable for any `team.id` the attacker can enumerate/guess, and for `removed` actions could also be used to deauthorize legitimate members.

### Likelihood Explanation
Requires a Shipit deployment using the **multi-organization** `Shipit.github` config schema (`github_app_config`/`github_organizations`) where at least one configured organization has `webhook_secret` left blank — a real-world plausible misconfiguration explicitly shown as a valid state in the documented example config. No secrets, sessions, or privileged roles are needed by the attacker: they only need to know (a) that such a misconfigured org exists/its slug, and (b) the target team's `github_id`, both of which are often discoverable (org names are public; team ids can be observed via prior legitimate webhook traffic or GitHub API for public orgs). Cost per attempt is a single unauthenticated HTTP POST.

### Recommendation
Derive the verifying organization consistently with the organization the handler will act on — e.g., require `organization.login` (or a validated equivalent) to match the org whose `webhook_secret` was used, and reject events where `repository.owner.login` (used for secret selection) diverges from `organization.login`/other payload org identifiers. Alternatively, verify the signature independently against every configured org's secret only when that org's login matches the payload's own `organization`/`repository.owner` fields consistently, and never accept `webhook_secret: nil` as automatically "verified" for multi-tenant configs — treat a nil secret as a hard misconfiguration error rather than an implicit bypass.

### Proof of Concept
Minitest `ActionDispatch::IntegrationTest` (webhooks_controller / membership handler flow):
1. Configure a stubbed `Shipit.github` multi-org setup: `Shipit.github(organization: 'attacker-org')` returns a `GitHubApp` stub whose `webhook_secret` is `nil` (so `verify_webhook_signature` returns `true` unconditionally); `Shipit.github(organization: 'shopify')` would have a real secret.
2. Create `shopify_team = Shipit::Team.create!(github_id: 555, ...)` and ensure `Shipit.github_teams` includes it (stub `Shipit.github.oauth_teams` to include the team's handle, or directly assert `authorized?` uses that membership).
3. POST `/webhooks` with header `X-Github-Event: membership`, no `X-Hub-Signature`, body:
```json
{
  "action": "added",
  "repository": {"owner": {"login": "attacker-org"}},
  "organization": {"login": "shopify"},
  "team": {"id": 555, "name": "n", "slug": "s", "url": "u"},
  "member": {"login": "attacker"}
}
```
4. Assert response is `200 OK` (not `422`).
5. Assert `Shipit::Membership.exists?(team_id: shopify_team.id, user: Shipit::User.find_by(login: 'attacker'))` is `true`.
6. Assert `Shipit::User.find_by(login: 'attacker').authorized?` is `true`.

Both sides of the claimed binding (`repository_owner` used for authentication vs. `organization.login`/`team.id` used for mutation) diverge (`attacker-org` vs `shopify`) and the test demonstrates the resulting unauthorized write, confirming the vulnerability.
