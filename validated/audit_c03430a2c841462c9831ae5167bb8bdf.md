### Title
Unauthenticated webhook forgery via attacker-chosen organization with no `webhook_secret` configured - ([File: lib/shipit/github_app.rb])

### Summary
`GitHubApp#verify_webhook_signature` contains a vacuous-truth bug analogous to the `isTargetContractAllowed` flaw: when no `webhook_secret` is configured for the resolved organization, the method unconditionally returns `true` instead of rejecting the request, and the organization used to pick that config is read directly from the unauthenticated payload.

### Finding Description
`WebhooksController#verify_signature` selects which `GitHubApp` (and therefore which `webhook_secret`) to validate against using a value taken straight from the untrusted request body: [1](#0-0) [2](#0-1) 

`repository_owner` is `params.dig('repository', 'owner', 'login')` — a field inside the JSON body that is only checked *after* signature verification passes, and is never itself covered by the HMAC comparison against the correct organization. The verification itself is: [3](#0-2) 

`return true unless webhook_secret` means: for any organization entry in `secrets.yml` that omits `github.webhook_secret` (documented as optional — see `docs/setup.md` lines 119-127, where the field is presented without any statement that all orgs must be configured), the signature check is fully bypassed, returning `true` regardless of the `X-Hub-Signature` header contents.

The trust binding broken: the **organization whose credentials authenticated the request** (chosen by an unauthenticated field in the payload) must equal **the organization/repository whose data is written by the handler**. Because the organization used for verification is attacker-controlled (`repository.owner.login`), an attacker can craft a JSON payload claiming to be from any org that is configured in `secrets.yml` without a `webhook_secret`, sending an arbitrary/garbage `X-Hub-Signature` header, and `verify_webhook_signature` will short-circuit `true`. The request then reaches `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` with completely attacker-controlled `params`, feeding models such as `MembershipHandler` (which creates/removes `Team`/`Membership` records used by `User#authorized?` for `Shipit.github_teams` gating) and `PushHandler`/`StatusHandler` (which drive `GithubSyncJob`, commit statuses, etc.) with forged data. [4](#0-3) [5](#0-4) 

### Impact Explanation
If any organization configured under `Shipit.github` lacks a `webhook_secret` (a state the documentation explicitly allows and does not warn against), an unauthenticated attacker can forge webhook deliveries impersonating that organization: fabricating `membership` events to add themselves to a `Team` matching `Shipit.github_teams` (escalating into the `Shipit.github_teams` authorization boundary and gaining access to stack state, task streams, and deploy triggers), or forging `push`/`status`/`check_suite` events to manipulate deploy readiness signals for repositories under that organization. This matches the High-impact class: escalation into `Shipit.github_teams` authorization / unauthenticated read (and mutation) of stack state.

### Likelihood Explanation
Likelihood is Low-to-Medium and configuration-dependent: it requires at least one organization in the deployment's `secrets.yml` to have `github.webhook_secret` unset (a documented-as-optional field, so plausible in real deployments, e.g. staging/test orgs configured alongside production orgs with secrets). No prior credential, session, or repository-write access is needed — only knowledge that such an organization exists (discoverable by trial, since a missing/garbage signature that returns 200/204 instead of 422 reveals the bypass).

### Recommendation
- Change `verify_webhook_signature` to fail closed rather than open when `webhook_secret` is absent, i.e., reject (`return false`) if no secret is configured for that organization rather than treating "no secret" as "always verified."
- Do not select the verification context (`organization`) from unauthenticated payload fields before any cryptographic check has occurred; alternately, require every configured organization to have a `webhook_secret`, enforced at boot (raise if missing) rather than silently allowing bypass.

### Proof of Concept
1. Deploy Shipit configured with two GitHub orgs: `org-a` (has `webhook_secret`) and `org-b` (no `webhook_secret` set, e.g. a staging/test entry left in `secrets.yml`).
2. Attacker POSTs to `/github/webhooks` with header `X-Github-Event: membership`, an arbitrary/garbage `X-Hub-Signature`, and a JSON body: `{"action":"added","team":{...},"organization":{"login":"org-b"},"member":{"login":"attacker"}}`.
3. `verify_signature` calls `Shipit.github(organization: "org-b").verify_webhook_signature(garbage_sig, raw_body)`, which hits `return true unless webhook_secret` in `lib/shipit/github_app.rb` line 77 and returns `true` without ever checking the signature.
4. `MembershipHandler#process` runs with fully attacker-controlled `params`, adding the attacker's `User` to a `Team` — potentially satisfying `Shipit.github_teams` authorization in `app/models/shipit/user.rb` line 81 and granting access to protected stacks.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
