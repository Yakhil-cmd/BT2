### Title
Webhook signature verification is keyed to `repository.owner.login`, not `repository.full_name`, allowing an unverified payload to mutate a different repository's stack - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
In a multi-organization Shipit deployment, `WebhooksController#verify_signature` selects the `GitHubApp` (and thus the `webhook_secret` to check against) using `repository_owner` (`params.dig('repository','owner','login')`), while `Handler#repository_name`/`LabelCapturingHandler#repository` resolve and mutate the actual `Shipit::Repository` using `payload.dig('repository','full_name')`. If any organization known to `Shipit.github_app_config` has no `webhook_secret` configured, `GitHubApp#verify_webhook_signature` returns `true` unconditionally, letting an attacker forge `repository.owner.login` as that org while pointing `repository.full_name` at a real, differently-owned repository tracked by Shipit.

### Finding Description
The broken binding: the organization whose credential verified the request bytes must equal the organization owning the repository the handler mutates, i.e. `org_verified(repository_owner) == org_mutated(repository.full_name.split('/').first)`. This engine breaks that equality when running with per-organization GitHub Apps.

- `Shipit.github(organization: organization)` in `lib/shipit.rb#170-181`: when `github_default_organization` is non-nil (multi-org mode), it looks up `github_app_config(organization)` using the caller-supplied `organization`, i.e. `repository_owner`, and raises `GithubOrganizationUnknown` only if that org key is entirely absent from config — not if it lacks a `webhook_secret`.
- `GitHubApp#verify_webhook_signature` (`lib/shipit/github_app.rb#76-83`): `return true unless webhook_secret` — if the resolved org's config omits `webhook_secret` (e.g., an org configured only for OAuth/team membership, not for repository webhooks), any body/signature combination is treated as verified. [1](#0-0) 
- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb#24-30, #59-62`) picks the app strictly by `repository_owner`, never cross-checking it against `repository.full_name`. [2](#0-1) [3](#0-2) 
- `WebhooksController#create` re-parses `request.raw_post` and dispatches to handlers with the full payload. [4](#0-3) 
- `Handler#repository_name`/`stacks` and `LabelCapturingHandler#repository` resolve the target purely from `payload.dig('repository','full_name')` via `Shipit::Repository.from_github_repo_name`, with no re-validation against `repository_owner`. [5](#0-4) [6](#0-5) 

Attacker request: POST `/webhooks` with `X-Github-Event: pull_request`, no `X-Hub-Signature` (or a garbage one), body containing `"repository": {"owner": {"login": "org-a"}, "full_name": "org-b/real-repo"}` and a valid `pull_request`/`labels` payload shape satisfying `LabelCapturingHandler`'s `ExplicitParameters` schema. If `org-a` is a configured-but-webhook_secret-less organization in `Shipit.github`, `verify_signature` passes; `create` then dispatches to `LabelCapturingHandler`, which resolves `org-b/real-repo` (a genuinely tracked, properly-secured repository) and calls `PullRequest#update!(labels: ...)`.

Existing guards fail to prevent this: `drop_unhandled_event` only filters unknown event types; the `rescue Shipit::GithubOrganizationUnknown` branch only fires when the org key is entirely missing, not when it exists without a secret; there is no check anywhere that `repository.owner.login` matches the owner segment of `repository.full_name`.

### Impact Explanation
An attacker can mutate the labels (and via other handlers — `opened_handler.rb`, `closed_handler.rb`, `labeled_handler.rb`, etc. — potentially the state) of any `PullRequest`/`ReviewStack` belonging to any organization that Shipit tracks, as long as some other configured organization in the same Shipit deployment lacks a `webhook_secret`. This is a genuine authentication-bypass / cross-tenant write: bytes never authenticated by org B's secret are used to write to org B's repository. This is repeatable per request against any repository full_name Shipit tracks, and the blast radius spans all organizations hosted by the same Shipit instance. This matches "Critical: payload for one repository mutating another's stack" — but its applicability is conditioned entirely on a specific operator misconfiguration (an org present in `Shipit.github` config lacking `webhook_secret`).

### Likelihood Explanation
Preconditions are non-trivial: the deployment must use the multi-org GitHub App config schema (`github_default_organization` non-nil) as described in `docs/setup.md`, AND at least one configured organization key must omit `webhook_secret`. In the single-app config schema (the common/default case, `github_default_organization` returns `nil`), `Shipit.github` ignores the passed `organization` argument entirely and always uses `secrets.github` — the one real secret — so `repository_owner` spoofing has no effect there. The vulnerability only manifests for multi-org deployments with an inconsistently configured organization, which is a documented but non-default setup. An attacker also needs to discover/guess a valid configured-but-secretless org name, which is feasible via trial (422 = unknown org, 200 = accepted) since GitHub org names are public identifiers.

### Recommendation
Bind signature verification to the same identity used for mutation: verify the signature using the GitHub App configuration for the *owner segment of `repository.full_name`* (not the separate `repository.owner.login`/`organization.login` field), or explicitly assert `repository.owner.login == repository.full_name.split('/').first` before proceeding. Additionally, change `GitHubApp#verify_webhook_signature` to fail closed (return `false`) when `webhook_secret` is blank instead of trivially returning `true`, and/or require all organizations in multi-org config to declare a `webhook_secret`.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` style, using the existing `test/dummy/config/secrets_double_github_app.yml` multi-org fixture):
1. Configure two orgs in test secrets: `org-a` (no `webhook_secret` key) and `org-b` (real `webhook_secret`), mirroring `secrets_double_github_app.yml`.
2. Create a `Shipit::Repository` owned by `org-b` with an existing `Stack`/`ReviewStack` and `PullRequest` fixture with known `labels`.
3. POST to `/webhooks` with `X-Github-Event: pull_request`, no `X-Hub-Signature` header, and JSON body: `{"action":"labeled","number":1,"pull_request":{...,"head":{...},"user":{"login":"attacker"},"assignees":[],"labels":[{"name":"malicious-label"}]},"repository":{"owner":{"login":"org-a"},"full_name":"org-b/real-repo"},"sender":{"login":"attacker"}}`.
4. Assert response is `200 OK` (bypassing verification for `org-a`).
5. Assert `PullRequest#labels` for the `org-b/real-repo` pull request now equals `["malicious-label"]`, proving org-a's (absent) signature check authorized a write to org-b's data — i.e., `org_verified("org-a") != org_mutated("org-b")` yet the write succeeded.

      return true unless webhook_secret

    end
