Based on my research, I found a concrete instance of this bug class (a value used for a security check being read separately from, and potentially inconsistent with, the value used for the resulting action) in `WebhooksController`.

### Title
Webhook signature verified against `repository.owner.login`/`organization.login` while handlers act on `repository.full_name` from the same unauthenticated payload - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/organization webhook secret to check the HMAC signature against using `repository_owner`, computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0) . The actual repository/stack that handlers act on is derived independently, from `payload.dig('repository', 'full_name')` in `Handler#repository_name` [2](#0-1) .

### Finding Description
In a multi-organization Shipit deployment (`docs/setup.md` documents configuring one GitHub App per organization, each with its own `webhook_secret`) [3](#0-2) , `Shipit.github(organization: repository_owner)` resolves to a `GitHubApp` instance holding that organization's own `webhook_secret`, and `verify_webhook_signature` HMACs the raw request body against it [4](#0-3) , [5](#0-4) .

The binding the engine relies on is: *the organization whose secret authenticated the request* == *the repository the resulting handler writes to*. However, both values are parsed from the same untrusted, attacker-controlled JSON body before any signature check occurs (`params = JSON.parse(request.raw_post)` in `#create`, and `repository_owner` reads from the same parsed body in `verify_signature`) [6](#0-5) [7](#0-6) . Nothing in `PushHandler`/`Handler#stacks` re-derives or cross-checks that the `repository.owner.login` used for authentication matches the `repository.full_name` used for the actual `Repository.from_github_repo_name` lookup that drives `stack.sync_github` [8](#0-7) [2](#0-1) .

Concretely, an attacker who legitimately controls a GitHub organization/repository that has its own installed Shipit GitHub App (and therefore knows/can generate a validly-signed webhook using that org's `webhook_secret`) can send a webhook whose `repository.owner.login` equals their own org (so it authenticates successfully against their own app's secret) but whose `repository.full_name` is set to a **different, victim** org/repo string that also happens to be configured as a Shipit stack. Because `verify_signature` only checks the signature against the attacker's own org's secret and never validates that this matches the `full_name` the handler subsequently acts on, the forged event is accepted and dispatched to the victim stack's `PushHandler`, e.g. triggering `stack.sync_github(expected_head_sha: params.after)` for a repository the attacker does not control and never signed a webhook for [8](#0-7) .

### Impact Explanation
This breaks the binding "the organization that authenticated versus the repository that is written." It allows an attacker who owns a self-installed Shipit GitHub App on one organization to forge signed webhook events (push, pull_request opened/closed/labeled, check_suite, status) targeting stacks belonging to a completely different, victim organization also configured on the same Shipit instance. Depending on which handler runs, this can force an out-of-band `GithubSyncJob`/deploy-triggering re-sync, archive/unarchive review stacks, or fabricate commit statuses for the victim repository — i.e., unauthorized state changes to a stack the attacker has no legitimate access to, without needing an `ApiClient` token or `User` session.

### Likelihood Explanation
Requires the deployment to host multiple organizations with per-organization GitHub Apps (a documented, supported configuration), and requires the attacker to control at least one of those organizations' Shipit GitHub App installation (i.e., they know that org's `webhook_secret`, which they can set themselves when creating their own App). No repository write access, `ApiClient` token, or user session is needed for the victim stack — only knowledge of the victim's `full_name` stack identifier, which is generally not secret. This is a design gap in cross-checking within the shared engine code rather than a misconfiguration of a single deployment.

### Recommendation
After successfully authenticating the webhook with `Shipit.github(organization: repository_owner)`, verify that the organization used for authentication actually matches the organization portion of `repository.full_name` (or `organization.login`) before dispatching to handlers, rejecting (422) any mismatch. Alternatively, resolve the target `Repository`/`Stack` via the authenticated organization rather than trusting the payload's `full_name` independently.

### Proof of Concept
1. Attacker creates their own GitHub App "Attacker App" installed on `attacker-org`, and configures Shipit with `github: { attacker-org: { webhook_secret: "known-secret", ... }, victim-org: { ... } }` (multi-org setup as documented).
2. Attacker crafts a `push` payload:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature` using `attacker-org`'s known `webhook_secret` over the raw body and POSTs to `/webhooks`.
4. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` (from `repository.owner.login`), verifies successfully against the attacker's own secret [7](#0-6) .
5. `PushHandler#stacks` looks up `Repository.from_github_repo_name("victim-org/victim-repo")` via `repository_name` [2](#0-1)  and triggers `stack.sync_github` for the victim's stack [8](#0-7) , despite the signature never having been validated against `victim-org`'s secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
