### Title
Griefing Push-Payment in `handleKLAYTransfer` Permanently Locks KAIA in Service-Chain Bridge — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

---

### Summary

`handleKLAYTransfer` in `BridgeTransferKLAY` pushes KAIA to a user-controlled `_to` address via a low-level `.call.value()`. If `_to` is a contract that reverts on receipt, the hard `require(ok, ...)` causes the entire transaction to revert, rolling back every state mutation. Because no admin escape-hatch or skip mechanism exists, the KAIA deposited on the source chain is permanently locked in the destination bridge with no recovery path.

---

### Finding Description

`handleKLAYTransfer` executes in this order:

1. Nonce guard (`_lowerHandleNonceCheck`) — line 75
2. Operator vote (`_voteValueTransfer`) — line 77; sets `closedValueTransferVotes[nonce] = true` on threshold
3. State writes: `_setHandledRequestTxHash`, `handleNoncesToBlockNums[nonce]`, `_updateHandleNonce` — lines 81–84
4. Event emission — lines 86–96
5. **Push transfer**: `(bool ok, ) = _to.call.value(_value)("");` — line 98
6. **Hard revert**: `require(ok, "handleKLAYTransfer: transfer failed");` — line 99 [1](#0-0) 

Because step 6 is an unconditional `require`, any revert from `_to` rolls back **all** of steps 2–4:

- `closedValueTransferVotes[nonce]` is reset to `false` → operators can re-vote, but every attempt will revert again at step 5.
- `handleNoncesToBlockNums[nonce]` is never written → `_updateHandleNonce`'s sequential scan (`for i = lowerHandleNonce; handleNoncesToBlockNums[i] > 0; i++`) can never advance `lowerHandleNonce` past this nonce.
- `recoveryBlockNumber` never advances → the off-chain VT recovery daemon re-scans from the same stale block forever. [2](#0-1) 

There is no admin function to skip a nonce, redirect funds, or mark a transfer as handled without executing the push. The `setRunningStatus` / `lockKLAY` controls only gate new requests, not stuck handles. [3](#0-2) 

---

### Impact Explanation

- **Unauthorized asset lock (loss of funds)**: KAIA sent by the user on the source chain is burned/locked there. The corresponding KAIA held in the destination bridge can never be delivered and cannot be recovered by any on-chain action. The exact amount lost equals `_value` in the stuck `handleKLAYTransfer` call.
- **`lowerHandleNonce` stagnation**: The `recoveryBlockNumber` never advances past the stuck nonce, causing the off-chain recovery system to re-scan the same block range indefinitely and re-submit the same failing transaction, wasting operator gas.
- **`closedValueTransferVotes` corruption**: The vote is never durably closed, so operators repeatedly re-vote and re-fail, consuming gas with no effect. [4](#0-3) 

---

### Likelihood Explanation

The `_to` address is fully user-controlled: it is supplied by the caller of `requestKLAYTransfer` on the source chain and relayed verbatim to `handleKLAYTransfer` on the destination chain. [5](#0-4) 

A malicious actor needs only to:
1. Deploy a contract with a reverting `receive()` on the destination chain (zero cost beyond gas).
2. Call `requestKLAYTransfer` with that address as `_to` and any non-zero KAIA value.

No privileged access is required. The attack is repeatable for every new request nonce.

---

### Recommendation

1. **Remove the hard `require` on the push transfer.** Instead, record the failed delivery in a claimable mapping (pull-payment pattern):

```solidity
mapping(address => uint256) public pendingWithdrawals;

// In handleKLAYTransfer, replace lines 98-99 with:
(bool ok, ) = _to.call.value(_value)("");
if (!ok) {
    pendingWithdrawals[_to] += _value;
}
```

2. **Add a `withdraw()` function** so recipients can pull their KAIA.
3. Alternatively, allow operators to supply a fallback recipient address when the primary `_to` reverts, so the nonce can always be closed.

---

### Proof of Concept

```solidity
// 1. Deploy on destination chain
contract RevertOnReceive {
    receive() external payable { revert("no KAIA"); }
}

// 2. On source chain — any unprivileged user
sourceBridge.requestKLAYTransfer{value: 1 ether}(
    address(revertOnReceive), // _to
    1 ether,                  // _value
    ""                        // _extraData
);
// Source bridge emits RequestValueTransfer(nonce=N), locks 1 KAIA.

// 3. Operators call handleKLAYTransfer on destination bridge (required by protocol)
destBridge.handleKLAYTransfer(
    requestTxHash, from, address(revertOnReceive),
    1 ether, N, blockNum, ""
);
// _to.call.value(1 ether)("") → revert
// require(ok) → entire tx reverts
// closedValueTransferVotes[N] = false (rolled back)
// handleNoncesToBlockNums[N] = 0 (rolled back)
// lowerHandleNonce never advances past N
// 1 KAIA permanently locked in destBridge, no recovery path
``` [6](#0-5) [7](#0-6)
