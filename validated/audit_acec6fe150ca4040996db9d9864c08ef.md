### Title
Stack-scoped API token can read CI status of any other stack via `CCMenuController#stack` bypassing token scope check - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::ApiClient` can be scoped to a single stack via its `stack_id` column, and `Api::BaseController` enforces this scope by resolving the requested stack only from the set of stacks the token authorizes. `Api::CCMenuController` overrides this scoping and resolves the stack directly from the request parameter, so a token authorized only for stack A can be used to read CI/deploy status for any other stack B.

### Finding Description
`Api::BaseController#stacks` restricts the queryable stacks to the ones the current `ApiClient` is scoped to: [1](#0-0) 
and `#stack` resolves the requested `params[:stack_id]` only within that scoped relation, so `from_param!` will raise/404 if the token's `stack_id` doesn't match the requested stack.

`Api::CCMenuController`, however, defines its own private `stack` method that ignores the scoped `stacks` relation entirely and resolves any stack directly from `Stack.from_param!(params[:stack_id])`: [2](#0-1) 
The controller only checks the generic `read:stack` permission bit, not whether the authenticated `ApiClient.stack_id` matches the requested `params[:stack_id]`: [3](#0-2) 
`ApiClient#check_permissions!` only checks membership in the `permissions` array (e.g. `read:stack`), it never compares `stack_id`: [4](#0-3) 

This is the same class of bug as the `SwapRouter.add_path()` issue: a binding that is supposed to gate access ("the stack a token authorises") is stored/checked in one place (`BaseController#stacks`/`#stack`) but the actual lookup performed by the consumer (`CCMenuController#stack`) uses a different, unguarded path, so the scope check silently doesn't apply in one direction (any token with `read:stack` + any `stack_id` combination can touch any stack through this specific endpoint), even though it is correctly enforced everywhere else (e.g. `CCMenuControllerTest`/other `Api::*Controller`s use `stacks.from_param!`).

Before the analog condition: a stack-scoped `ApiClient` (created with `stack: some_stack`, `permissions: %w[read:stack]`) can only read data for `some_stack` through any endpoint built on `Api::BaseController#stack`.
After: the same token, when hitting `Api::CCMenuController#show` with a different `stack_id` param, is granted the same read access to a stack it was never scoped to, because `#stack` in that controller does not consult `current_api_client.stack_id`.

### Impact Explanation
This breaks the equality "stack authorised by token == stack touched by token" for one controller. Impact is unauthenticated-relative-to-scope read of stack state: build/deploy status, activity, last build label/time and web URL of an arbitrary stack (rendered via the `shipit/ccmenu/project` view), exposed to any holder of a valid but narrowly-scoped API token. This matches the "High - unauthenticated read of stack state" impact category, since the token holder is not authenticated for that particular stack's data yet can retrieve it.

### Likelihood Explanation
Exploitation only requires possession of any valid `ApiClient` token that has `read:stack` permission (which is the default token minted by `Shipit::CCMenuUrlController`) and knowledge/guessing of another stack's `to_param` (repo owner/name/env, which are not secret and are visible throughout the UI). No privileged access, TLS interception, or social engineering is required beyond having one legitimate stack-scoped token — a normal, expected credential in this system.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the scoped lookup from `Api::BaseController` (i.e., remove the private `stack` override and rely on `stacks.from_param!(params[:stack_id])`, or explicitly verify `current_api_client.stack_id.nil? || current_api_client.stack_id == resolved_stack.id`) so the CI-status endpoint is bound by the same "token scope == stack touched" invariant enforced elsewhere in the API.

### Proof of Concept
1. Admin/CI system creates (or a user auto-provisions via `CCMenuUrlController#client`) an `ApiClient` scoped to stack A: `ApiClient.create!(creator: user, name: 'CCMenu Client', permissions: %w[read:stack], stack: stack_a)`.
2. Attacker obtains this token (e.g., it's embedded in a CI dashboard URL, as generated by `CCMenuUrlController#fetch`).
3. Attacker calls `GET /api/stacks/:owner/:repo/:env/ccmenu.xml?token=<token>` but substitutes `stack_id` params for stack B (`shipit_stacks(:some_other_stack).to_param`).
4. `CCMenuController#authenticate_api_client` succeeds (token is valid) and `require_permission :read, :stack` succeeds (`read:stack` is present).
5. `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly (no scoping), returning stack B.
6. `show` renders stack B's `deploys_and_rollbacks.last` status/activity — data the token was never authorized to see — confirming the cross-stack read.
