### Title
Incorrect assumption that `asset[asset].cap` equals actual circulating supply for fixed-denomination capped assets - (File: formula/evaluation.js)

### Summary
The oscript/AA formula field `asset[asset].cap` returns the asset's declared maximum cap, not the amount actually issued into circulation. For ordinary divisible capped assets this distinction is harmless because issuance is atomic and enforced to equal the full cap in one shot. However, for capped assets with `fixed_denominations` (indivisible assets), the protocol explicitly allows the cap to be issued incrementally, coin-by-coin, across many separate units and possibly over a long period of time — so at any given moment the real circulating supply can be far below `cap`. Any AA (bonding-curve, vault, DEX, or price/share calculator) that uses `asset[asset].cap` as a stand-in for "total supply", the same modeling mistake made in the Balancer report with `totalSupply()` vs `getActualSupply()`, will compute wrong per-unit valuations.

### Finding Description
`asset[asset].cap` is resolved in the formula evaluator by directly returning the asset's static `cap` field from its definition: [1](#0-0) 

This value is the maximum authorized issuance recorded at asset-definition time, not a live count of coins actually issued. For normal divisible assets, `validatePaymentInputsAndOutputs` forces the entire cap to be issued as a single input, so once `is_issued` becomes true, `cap` and actual supply coincide: [2](#0-1) 

Note the `!objAsset.fixed_denominations` guard: this "issue must equal cap" enforcement is explicitly skipped for indivisible (fixed-denomination) assets. Indivisible capped assets are instead issued denomination-by-denomination, each denomination tracked independently via `asset_denominations.max_issued_serial_number`, and issuance of a given denomination can happen in any later unit, by any allowed issuer, whenever a wallet needs that denomination: [3](#0-2) 

The `asset_denominations` schema confirms each denomination has its own `count_coins` and `max_issued_serial_number` independent of the others, allowing the total actually-issued supply to remain well below the declared `cap` indefinitely: [4](#0-3) 

Meanwhile `asset[asset].is_issued` only reports whether *any* issue input exists at all for the asset — not whether the full cap has been issued: [5](#0-4) 

So an AA has no reliable, cheap way via `asset[]` fields to learn the true circulating supply of a fixed-denomination capped asset; the only field exposed (`cap`) reflects the maximum, not the actual amount in circulation, exactly mirroring the Balancer `totalSupply()` vs `getActualSupply()` confusion.

### Impact Explanation
Any AA that uses `asset[X].cap` under the (reasonable-looking) assumption that it represents total circulating supply — e.g., to compute a per-share redemption value (`balance[base] / asset[X].cap`), a bonding-curve price, or a pro-rata payout — will systematically overstate the token supply for capped fixed-denomination assets whose issuance is still incomplete. This lets early/insider redeemers extract a disproportionately large share of AA-held funds, or lets a share-token holder mint/redeem at incorrect exchange rates, resulting in AA fund loss for other legitimate participants. This is a direct analog of the reported Balancer issue: using an "authorized/maximum" supply figure instead of the actually-circulating one to price a share of pooled assets.

### Likelihood Explanation
Any unprivileged user or AA can define a capped, `fixed_denominations` asset and issue it incrementally (this is standard, intended behavior, not a bug in itself). The vulnerability is triggered whenever a downstream AA (vault/DEX/bonding-curve style oscript, similar in spirit to the `uniswap_like_market_maker.oscript` / `option_contract.oscript` samples in this repo that key logic off asset-level quantities) is written to rely on `asset[X].cap` as a supply oracle for such an asset. Given that `cap` is the only asset-level "supply-like" field exposed to oscript, and its semantics ("maximum authorized amount") are easy to conflate with "amount in circulation," this is a realistic and likely mistake for AA authors building token-economics contracts on top of indivisible capped assets.

### Recommendation
- Do not expose `cap` as a stand-in for circulating supply; consider exposing a genuine "issued supply" accessor for AAs (e.g., an oscript field or function that reports the actual sum of issued amounts for an asset, analogous to `getActualSupply`), so AA authors have a correct, cheap primitive to query.
- Alternatively, document explicitly (and ideally enforce via the AA-definition linter) that `asset[X].cap` must not be used as a proxy for circulating supply when `fixed_denominations` is true, and recommend AA authors instead track issued/circulating amounts themselves via `balance[]` accounting or explicit state variables.
- Consider tightening the protocol so that fixed-denomination capped assets also require full-cap issuance atomically (as already done for divisible capped assets) if the incremental-issuance flexibility is not essential, removing the cap/actual-supply divergence at the source.

### Proof of Concept
1. Define an asset with `cap: 1000000`, `fixed_denominations: true`, `denominations: [{denomination: 1, count_coins: 500000}, {denomination: 2, count_coins: 250000}]` (sums to the cap).
2. Only the `denomination: 1` group gets issued (500,000 units); the `denomination: 2` group is never issued. Actual circulating supply = 500,000, but `asset[asset].cap` still returns 1,000,000.
3. An AA vault holding `balance[base]` and using `share_value = balance[base] / asset[asset].cap` to price token redemptions will undervalue each unit of the asset by 2x, allowing early depositors/redeemers of the vault's base-asset reserve to extract disproportionate value relative to legitimate holders of the fully-issued portion of the asset, since the AA's math assumes twice as many outstanding tokens as actually exist.
