### Title
Cross-repository commit-status forgery bypasses CI blocking gates via SHA-only matching - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits purely by SHA (`Commit.where(sha: params.sha)`) with no check that the webhook's authenticated repository matches the commit's owning stack/repository. Because git SHAs are shared identically across forks/mirrors of a repository, an attacker who forks `victim/prod` can send a legitimately-signed status webhook from their own fork and have it applied to the victim stack's commit, clearing a `ci.blocking` gate and enabling an unauthorized deploy.

### Finding Description
The claimed binding is: `webhook.repository.full_name == commit.stack.repository.full_name` (the repo that authenticated/signed the webhook must equal the repo owning the commit the status is applied to). This binding is never enforced.

`WebhooksController#verify_signature` only proves that the payload was HMAC-signed with the webhook secret configured for `repository_owner` (`params.dig('repository','owner','login')`), i.e., that the payload genuinely originated from GitHub for *some* org/repo Shipit trusts: [1](#0-0) 

It does not verify that the `repository` in the payload is the same repository that owns the commit referenced by `sha`. The handler then does: [2](#0-1) 

`Commit.where(sha: params.sha)` performs a global, cross-tenant lookup with **no** `stack_id`/repository filter at all, and applies `create_status_from_github!` to every matching commit across every stack in the database: [3](#0-2) 

Since git commit SHAs are content-addressed, a fork of `victim/prod` (or any repo sharing history with it) contains commits with byte-identical SHAs, including the blocking commit `C2`. If the attacker's own repository/org has the Shipit GitHub App installed (a normal, unprivileged action for a repo the attacker owns), GitHub will genuinely sign a `status` webhook for that repo's SHA `C2` and deliver it to Shipit. `verify_signature` passes because it only checks authenticity for the attacker's own org, not that the org owns `C2` in Shipit's data model.

`Commit#blocked?` then re-evaluates blocking status purely from the `Status` rows on `C2`: [4](#0-3) 

Once the forged `success`/`security-scan` status lands on `C2` (belonging to `victim/prod`), `C2` stops being `blocking?`, `C5#blocked?` flips to `false`, and `Stack#next_commit_to_deploy` → `deployable_commits` will include `C5`, which `ContinuousDeliveryJob` deploys.

No existing guard prevents this: `verify_signature` authenticates the webhook's origin, not its target commit's owner; `ExplicitParameters` only validates the shape of `sha`/`state`/`context`, not repository binding; there is no `stack.repository == webhook.repository` check anywhere in `StatusHandler` or `Commit#create_status_from_github!`.

### Impact Explanation
An attacker who owns any repository/fork sharing a SHA with a commit in a victim stack can write arbitrary CI/status data (`success`, `failure`, any `context`) onto that victim commit, without ever authenticating to or being authorized on the victim repository. In the scoped scenario, this clears a `ci.blocking` safety gate (`security-scan`), causing `ContinuousDeliveryJob` to deploy a commit that was deliberately held back — an unauthorized deploy triggered by a payload authenticated for a different repository. This matches the Critical category: "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy." The technique is repeatable against any stack/repository whose commit history (or any historical commit) is forkable/mirrorable by the attacker, which is essentially any public repo tracked by Shipit.

### Likelihood Explanation
Preconditions: the attacker must have (or fork) a repository whose commit history includes the exact SHA of the target blocking commit `C2` (trivial via `git fork`/mirror of a public repo), and that attacker-owned repo must have the Shipit GitHub App/webhook integration enabled for its org (a normal, self-service action for a repo the attacker owns, not requiring any Shipit privilege, team membership, or secret). Given that, the attacker only needs to trigger (or directly emit, if they control CI on their fork) a `status` event with the target `sha`, `state`, and `context` — a single HTTP-triggerable action, fully repeatable and scriptable against any tracked victim commit.

### Recommendation
Scope status application to the commit's own stack/repository: in `StatusHandler#process`, resolve the webhook's `repository` (owner/name) and only apply the status to commits belonging to stacks whose `Repository` matches that `full_name`, e.g. `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { name: ..., owner: ... })`, rejecting/ignoring statuses whose payload repository doesn't match the commit's stack repository.

### Proof of Concept
Minitest plan (`test/models/webhooks/handlers/status_handler_test.rb` or similar, illustrative — actual location may need `test/` additions per engine conventions):
1. Create two stacks/repos in fixtures: `victim/prod` (with `shipit.yml` `ci.blocking: ['security-scan']`) and `attacker/fork`, each with a commit sharing the identical `sha` value (simulate SHA collision/fork by creating two `Commit` records with the same `sha` but different `stack_id`).
2. Seed `victim/prod`'s commit `C2` (shared sha) with no `security-scan` status, and `C5` (a later commit) — assert `C5.blocked?` is `true` (binding LHS: no status authorized by `victim` repo exists for `C2`).
3. Build a `status` webhook payload with `sha` = shared sha, `state: 'success'`, `context: 'security-scan'`, and `repository.owner.login` = attacker's org; call `Shipit::Webhooks::Handlers::StatusHandler.new.call(payload)` (or POST through `WebhooksController` with signature stubbed for the attacker org).
4. Assert a `Status` record was created on **both** `attacker/fork`'s commit *and* `victim/prod`'s `C2` (binding RHS: `webhook.repository != commit.stack.repository`, yet status was written) — this demonstrates the divergence.
5. Assert `C5.reload.blocked?` is now `false`, and that `Stack#next_commit_to_deploy` for `victim/prod` returns `C5` (or later), proving the forged cross-repo status caused an unauthorized deploy candidate to appear.
