### Title
Null-pointer dereference when evaluating address-condition filters (`has`/`has one`/`seen`) against inputs lacking augmented data - (File: definition.js)

### Finding Description
This mirrors the TF `ragged.cross` bug class: code assumes a certain augmented shape/object is always present (a RaggedTensor-like structure) without validating it, and dereferences it unconditionally. Here, `augmented_input` is set to `null` whenever `objValidationState.arrAugmentedMessages` is falsy (which is the normal case for many validation paths — `arrAugmentedMessages` is only populated in specific formula-evaluation contexts, not during standard `validateDefinition`/`validateAuthentifiers` calls). Yet immediately below, if the filter contains an `address` field (`this address`, `other address`, or a normal address) — a fully attacker-controlled part of any address/asset definition using `has`/`has one`/`seen` with an `input` filter — the code does `augmented_input.address`, `augmented_input.amount`, etc., without a null check, analogous to `augmented_input.amount !== filter.amount` at line 1327 and `augmented_input.amount < filter.amount_at_least` at line 1329.

### Impact Explanation
Since `evaluateFilter` is invoked while validating spending-condition definitions (`validateDefinition`) for ordinary addresses signing any unit, and asset conditions, an attacker can craft an address definition containing `["has", {"what":"input", "address":"this address", ...}]` (or `has one`/`seen`) such that, when authentifier verification runs against a posted unit, `objValidationState.arrAugmentedMessages` is not set, causing `augmented_input` to be `null` and the subsequent `augmented_input.address` access to throw an uncaught `TypeError`. If this exception propagates out of the async validation callback chain rather than being funneled through `callback(err)`, it can crash the validating node process (full node / witness / hub) that is trying to validate the maliciously crafted unit — a self-inflicted denial of the ability to confirm units containing this address condition, satisfying "node disagreement on validity" / "network unable to confirm new units" if different nodes end up with divergent behavior (crash vs. graceful reject) depending on whether `arrAugmentedMessages` happens to be populated in their validation context.

### Likelihood Explanation
Medium: reaching this code path requires only posting/using an address whose definition contains a `has`/`has one`/`seen`/`has equal` filter with `what:"input"` and an `address` sub-field, which is a standard, legal oscript definition construct. Whether `arrAugmentedMessages` is populated depends on the calling context (some formula-evaluation paths populate it; the AuthorSignature/definition-validation path generally does not), so the null path is plausible but requires confirming which call sites into `evaluateFilter` never populate `arrAugmentedMessages`.

### Recommendation
Add an explicit guard before dereferencing `augmented_input`:
```js
var augmented_input = (objValidationState.arrAugmentedMessages && objValidationState.arrAugmentedMessages[i]) ? objValidationState.arrAugmentedMessages[i].payload.inputs[j] : null;
if (filter.address && !augmented_input)
    augmented_input = input; // fall back to non-augmented input for address/amount comparison, matching output-filter fallback below
```
or fail closed (`continue`) when `augmented_input` is `null` but `filter.address`/`filter.amount*` fields are requested, so validation errors out cleanly instead of throwing.

### Proof of Concept
1. Register an address whose definition includes: `["has", {"what":"input", "address":"this address"}]`.
2. Post a unit spent by that address, going through a `validateDefinition`/`validateAuthentifiers` call path where `objValidationState.arrAugmentedMessages` is not populated (this is the default for plain unit signature validation, as opposed to formula-based AA-trigger evaluation paths that explicitly set it).
3. During filter evaluation, `augmented_input` resolves to `null`; the check `augmented_input.address !== address` throws a `TypeError`, crashing or erroring the validating node's process for that unit.

*Note: I was not able to fully enumerate every call site of `evaluateFilter`/`validateDefinition` to confirm with certainty that a real-world call path exists where `arrAugmentedMessages` is absent while `filter.address` is set with `what:"input"` — this would need to be verified in a live Devin session by tracing all callers of `validateDefinition`/`validateAuthentifiers` and checking whether `objValidationState.arrAugmentedMessages` is ever left unset in a live-unit-validation context (as opposed to formula unit tests, which do set it).*
