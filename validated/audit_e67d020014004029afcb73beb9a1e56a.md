### Title
Cross-organization team membership forgery via unbound `organization.login` field in webhook signature verification - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's secret to check the HMAC signature against using `repository_owner`, which prefers `repository.owner.login` and only falls back to `organization.login` when `repository` is absent. [1](#0-0) [2](#0-1)  The membership event handler, however, trusts a *different* payload field — `params.organization.login` — to decide which organization's `Team` record to create/modify. [3](#0-2)  Because both fields live in the same unverified JSON body, and `GitHubApp#verify_webhook_signature` returns `true` unconditionally whenever the selected organization has no `webhook_secret` configured, an attacker can select a low-value/no-secret organization for signature verification while pointing the actually-executed side effect (team membership write) at a different, high-value organization.

### Finding Description
The trust binding that should hold is:

`organization whose secret authenticated the request == organization whose state the handler writes to`

`verify_signature` authenticates the request against `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight out of the still-unverified request body (`params.dig('repository','owner','login') || params.dig('organization','login')`). [2](#0-1)  `GitHubApp#verify_webhook_signature` trivially returns `true` when that organization's `webhook_secret` is blank — a supported, non-error configuration state (`@webhook_secret = @config[:webhook_secret].presence`, `return true unless webhook_secret`). [4](#0-3) [5](#0-4)  The test fixtures confirm multi-organization deployments with per-organization, independently-nil `webhook_secret` values are a real, intended configuration shape. [6](#0-5) [7](#0-6) 

Once `verify_signature` passes (because the org picked via `repository.owner.login` has no secret), `WebhooksController#create` dispatches the entire raw JSON `params` to the registered handlers for the event. [8](#0-7)  For the `membership` event, `Shipit::Webhooks::Handlers::MembershipHandler#process` never re-checks that `params.organization.login` matches the organization used for signature verification; it uses `params.organization.login` directly as the `Team#organization` when creating/looking up the team, and `params.team.id` as the lookup key, then adds `params.member.login` as a member. [3](#0-2) 

Consequently, an attacker can craft a body where `repository.owner.login` names an organization configured with no `webhook_secret` (so the HMAC check is skipped), while `organization.login`, `team.id`, and `member.login` reference a *different*, victim organization/team. The handler will faithfully add the attacker-chosen GitHub login to that victim `Team`. Because `User#authorized?` grants access to the Shipit UI/API based on membership in `Shipit.github_teams`, [9](#0-8)  and access is otherwise gated purely on GitHub OAuth login plus team membership, [10](#0-9)  this lets an unprivileged network attacker escalate an arbitrary GitHub identity into `Shipit.github_teams` authorization if the attacker can supply (or guess) the numeric GitHub `team.id` of a team already tracked as authorized (e.g. from a prior legitimate `membership` webhook, from public team pages, or from any organization the attacker legitimately administers and has previously synced with Shipit).

### Impact Explanation
This is a direct analog of the reported class: a field used to satisfy a security check (`repository.owner.login`, used to pick the verifying secret) is disjoint from the field the resulting write actually depends on (`organization.login`/`team.id`, used by `MembershipHandler`). The impact matches the "High" bucket explicitly listed in scope: escalation into `Shipit.github_teams` authorization, i.e., an unprivileged attacker obtaining authenticated access to a Shipit deployment (view stack state, task output, trigger deploys/rollbacks if further `require_permission` checks pass) without ever being a real member of the authorized GitHub team/org.

### Likelihood Explanation
Requires: (1) a multi-organization Shipit deployment where at least one configured organization has no `webhook_secret` (an explicitly supported, non-erroring configuration per `lib/shipit/github_app.rb`), and (2) knowledge of the victim team's numeric GitHub `team.id` (not the slug/name), which is not secret but not trivially public either. Given multi-org support and "optional" webhook secrets are first-class, deliberate features of this engine, likelihood is moderate rather than purely theoretical.

### Recommendation
- In `WebhooksController#verify_signature`, do not let an unauthenticated field select which secret authenticates the request without also proving all organization-identifying fields in the payload are consistent with that same organization.
- In `MembershipHandler#process`, verify that `params.organization.login` equals the organization that was actually used to validate the webhook signature (e.g., pass the authenticated organization through to handlers and assert equality) before creating/mutating any `Team`.
- Do not allow `verify_webhook_signature` to silently return `true` for organizations with a blank `webhook_secret`; require an explicit, logged opt-in for "no verification" instead of treating blank as "always trust."

### Proof of Concept
1. Deploy Shipit configured with two organizations, e.g. `OrgOne` (attacker-controlled, `webhook_secret` left blank) and `OrgTwo` (victim, with a `Team` already synced whose GitHub `team.id` is known/guessed, and which is listed in `Shipit.github_teams`).
2. POST to `/webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "team": { "id": <OrgTwo_real_team_github_id>, "name": "Developers", "slug": "developers", "url": "https://example.com" },
  "organization": { "login": "OrgTwo" },
  "member": { "login": "attacker-github-login" },
  "repository": { "owner": { "login": "OrgOne" } }
}
```
No valid `X-Hub-Signature` is required, since `Shipit.github(organization: "OrgOne")` has a blank `webhook_secret`, so `verify_webhook_signature` returns `true` unconditionally (`app/controllers/shipit/webhooks_controller.rb:24-30`, `lib/shipit/github_app.rb:76-83`).
3. `MembershipHandler#process` runs with `params.organization.login == "OrgTwo"` and adds `attacker-github-login` to the real `OrgTwo` team (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-43`).
4. Attacker signs into Shipit via GitHub OAuth as `attacker-github-login`; `User#authorized?` now returns `true` because the user belongs to a team in `Shipit.github_teams` (`app/models/shipit/user.rb:80-82`), granting full authenticated access.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
