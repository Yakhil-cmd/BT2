### Title
Denial of Service via invalid main-chain stabilization state assumed impossible in `writer.saveJoint` - (File: writer.js)

### Summary
`writer.js`'s post-commit logic assumes that a single call to `main_chain.advanceMcStability()` can stabilize at most one MCI, and defends this assumption with hard `throw Error(...)` invariant checks. However, a second, independent code path — `main_chain.determineIfStableInLaterUnitsAndUpdateStableMcFlag()`, reachable from ordinary unit validation — can advance the stability point by walking through *multiple* MCIs in a loop while holding a different lock (`"handleJoint"`) than the one guarding `writer.saveJoint`'s stabilization loop. If both paths interleave on an attacker-crafted unit graph, the invariant "at most one MCI stabilizes per step" can be violated, triggering the `throw Error(...)` guard and crashing the whole node process — a Denial of Service reachable purely by posting/broadcasting units, analogous to the Envoy CVE-2021-32780 pattern of "invalid state transition when two events are processed in the same pass."

### Finding Description
`writer.saveJoint()` calls `main_chain.advanceMcStability()` and asserts: [2](#0-1) 
right after committing a unit, and again in the follow-up "stabilize more" loop: [3](#0-2) 

The assumption baked into `main_chain.advanceMcStability()` is that it stabilizes exactly one MCI per call ("not trying next any more"): [4](#0-3) 

But a second, independently-triggered stabilization path exists: `determineIfStableInLaterUnitsAndUpdateStableMcFlag()`, invoked from unit validation while checking whether `last_ball` is stable in view of parents: [5](#0-4) 

This function acquires the `"handleJoint"` mutex — a *different* lock than the `write`/DB-transaction serialization used inside `writer.saveJoint`'s stabilization `while(true)` loop — and then walks forward through a *range* of MCIs in a `for` loop, calling `stabilizeMci(mci)` for each one sequentially: [6](#0-5) 

Because this loop and `writer.saveJoint`'s own stabilization loop are not mutually exclusive (they use different mutex keys — `"handleJoint"` vs. the write/db-transaction serialization), it is possible for MC advancement driven by unit validation of one unit (via `determineIfStableInLaterUnitsAndUpdateStableMcFlag`) to race with a concurrent `saveJoint()` commit that also detects and processes stability advancement via `advanceMcStability()`. Since both mechanisms mutate global caches (`storage.assocStableUnits`, `arrStabilizedMcis`) and DB rows for `is_stable`/`main_chain_index` without a shared lock, the "advance by exactly one MCI" invariant relied on by `writer.js`'s guards can be violated when a specially crafted sequence of units (designed to make `last_ball` stability trail multiple MCIs behind the actual free-unit witnessed levels) is posted, causing `writer.js`'s `throw Error("...stabilized more than one MCI...")` guard to fire.

### Impact Explanation
The thrown `Error` occurs inside an `async` function passed as a callback (`commit_fn(... async function(){ ... throw Error ... })`) with no enclosing `try/catch` and no global `unhandledRejection`/`uncaughtException` handler registered in the codebase [7](#0-6) . In default Node.js behavior (Node 15+), an unhandled promise rejection terminates the process. This means a full node crash — network-wide Denial of Service — can be triggered by an unprivileged party who is able to post units that drive the two independent stabilization code paths into disagreement, exactly mirroring the "two independent state-machine events colliding" root cause of CVE-2021-32780.

### Likelihood Explanation
Reaching this requires crafting a unit graph precise enough that `determineIfStableInLaterUnitsAndUpdateStableMcFlag`'s multi-MCI-advance loop and `writer.saveJoint`'s single-MCI-advance path both fire concurrently on overlapping MCIs — this demands deep knowledge of DAG stability rules (witnessed levels, best-parent computation, MC branching) but does not require any special privilege, only the ability to post ordinary units/joints, since `determineIfStableInLaterUnitsAndUpdateStableMcFlag` is invoked from core unit validation (`validateParents`) that runs on every incoming unit.

### Recommendation
Serialize all mutations of stability state behind a single lock (or ensure `determineIfStableInLaterUnitsAndUpdateStableMcFlag`'s stabilization loop and `writer.saveJoint`'s post-commit stabilization loop cannot run concurrently for overlapping MCIs), and replace the hard `throw Error(...)` invariant violations in `writer.js` with graceful recovery/retry logic instead of an unguarded crash, or wrap the async commit callback in a `try/catch` that logs and safely aborts only the affected write rather than the whole process.

### Proof of Concept
Not independently reproducible from static analysis alone: exploitation requires constructing a precise multi-unit DAG (parent/witness/MC topology) that causes `determineIfStableInLaterUnitsAndUpdateStableMcFlag`'s MCI range loop (main_chain.js:1224) to run concurrently with `writer.saveJoint`'s stabilization loop (writer.js:738-753) on overlapping MCIs. This would require dynamic testing against a running node with a controlled witness/DAG setup to confirm the race actually manifests; I could not execute or simulate this interaction with the static tools available.
