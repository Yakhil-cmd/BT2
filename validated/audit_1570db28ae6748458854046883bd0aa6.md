### Title
Membership webhook cross-organization confused deputy: `repository.owner.login` used for signature auth diverges from `organization.login`/`team.id` used to mutate `Team`/`Membership` records - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the `GithubApp` (and hence the HMAC secret) used to authenticate a webhook exclusively from `repository.owner.login` (falling back to `organization.login`), but `MembershipHandler#process` mutates state keyed on the payload's separate `organization.login` and `team.id` fields without cross-checking them against the authenticated `repository_owner`. Any party able to produce a validly-signed webhook for one organization can therefore forge `membership` events that add arbitrary GitHub users to `Team` rows belonging to a completely different organization, escalating that user's `Shipit.github_teams` authorization via `User#authorized?`.

### Finding Description
The broken binding: `organization authenticated by verify_signature (repository_owner)` must equal `organization whose Team/Membership rows are mutated (params.organization.login / team.github_id owner)` — but nothing in the code enforces this.

Trace:
- `WebhooksController#verify_signature` computes `repository_owner` purely from attacker-controlled JSON: `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0)  and uses it to fetch the `GithubApp` config and verify the signature: `github_app = Shipit.github(organization: repository_owner); verified = github_app.verify_webhook_signature(...)` [2](#0-1) .
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when `webhook_secret` is blank for that org's config: `return true unless webhook_secret` [3](#0-2) .
- Once the request passes this org-scoped check, `MembershipHandler#process` never re-validates that `params.organization.login` (or the eventual owner of `params.team.id`) matches `repository_owner`. It does `team = find_or_create_team!` (`Team.find_or_create_by!(github_id: params.team.id)`) and then `team.add_member(User.find_or_create_by_login!(params.member.login))` [4](#0-3) .
- Because `Team.find_or_create_by!` looks up by `github_id` alone, if that ID already belongs to an existing `Team` (e.g., a `shopify` team present in `Shipit.github_teams`), the existing record is found (not created) and `team.add_member` is executed against it directly, regardless of which organization's secret authenticated the request [5](#0-4) .
- `User#authorized?` grants access purely based on membership in `Shipit.github_teams`: `Shipit.github_teams.empty? || teams.where(id: Shipit.github_teams.map(&:id)).exists?` [6](#0-5) , so adding a forged `Membership` row directly flips `authorized?` to true for the attacker's user.

This is a genuine confused-deputy flaw independent of the nil-secret detail: even an attacker who legitimately owns and correctly signs webhooks for their *own* configured organization (`repository.owner.login = attacker-org`, correctly signed) can set `organization.login` and `team.id` in the same JSON body to reference a victim org's team, and the handler will still mutate the victim's `Team`/`Membership` state because no code path binds the two fields together. The nil-`webhook_secret` variant described in the question is simply the degenerate case where no signature at all is required, making exploitation trivially unauthenticated — but it does require that `attacker-org` be a pre-configured entry in `Shipit.github`'s multi-org config (confirmed by the `GithubOrganizationUnknown` guard/test at `app/controllers/shipit/webhooks_controller.rb:39` and `test/controllers/webhooks_controller_test.rb:109-127`), so the operator must have an organization present in config with `webhook_secret` unset/nil (matching the shipped `config/secrets.development.example.yml` pattern) for the unauthenticated instantiation to work.

No existing guard prevents this: `drop_unhandled_event` only checks event type presence, `ExplicitParameters` schema in `MembershipHandler` only validates types/presence of `team.id`, `organization.login`, `member.login` — not their consistency with `repository_owner` — and `force_github_authentication`/`require_permission!` are session/API-token guards irrelevant to the webhook endpoint.

### Impact Explanation
A successful forged `membership` event lets an attacker add an arbitrary GitHub login (which they then also create via `User.find_or_create_by_login!`) to a `Team` row that belongs to a victim organization tracked by Shipit, without any credential belonging to that victim organization. If that `Team` is part of `Shipit.github_teams` (the OAuth-authorization team list), the newly created `Membership` makes `User#authorized?` return `true` for the attacker's account, granting them access equivalent to a legitimate victim-org member across the Shipit instance. This matches the "escalation into `Shipit.github_teams` authorization" High-severity category, and is repeatable for any known/guessable `team.id` (GitHub numeric team IDs), and for any additional attacker-controlled logins per request.

### Likelihood Explanation
Preconditions: Shipit must be configured (by the operator) with multiple GitHub organizations, one of which (`repository_owner`/`organization.login` used for auth) has authentication that the attacker can pass — either because its `webhook_secret` is left `nil`/unset (as illustrated by the shipped dev-example config pattern), or because the attacker legitimately controls that org and can produce a valid HMAC signature with their own known secret. The attacker also needs the numeric `github_id` of the target `Team` row (obtainable from the existing `Team.api_url`/public GitHub team metadata in many cases, or from prior legitimate webhook traffic). Given these, the exploit is a single unauthenticated (or self-signed) HTTP POST to `/webhooks`, fully repeatable and requiring no privileged Shipit role.

### Recommendation
In `MembershipHandler#process` (and any other webhook handler that trusts nested `organization`/`repository` fields), require that the value used to select and verify the webhook signature (`repository_owner`) matches the organization asserted inside the payload (`params.organization.login`) before performing any lookup or mutation, and reject the event otherwise. Additionally, `Team.find_or_create_by!(github_id:)` should also scope by/verify `organization` so an existing team cannot be silently reused by a payload claiming a different `organization.login`. Consider also hardening `GitHubApp#verify_webhook_signature` so that a `nil`/unset `webhook_secret` for a *configured* organization fails closed instead of returning `true`, unless explicitly running in a documented insecure/dev mode.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` style, `ActionDispatch::IntegrationTest` or `ActionController::TestCase`):
```ruby
test ":membership event authenticated as attacker-org mutates shopify's team" do
  shopify_team = shipit_teams(:shopify_developers) # existing Team row, organization: 'shopify'
  Shipit.github_teams # ensure it includes shopify_team

  # Simulate multi-org config: 'attacker-org' has webhook_secret nil (per secrets.development.example.yml pattern)
  Shipit.stubs(:github).with(organization: 'attacker-org').returns(GitHubApp::App.new('attacker-org', {})) # webhook_secret nil -> verify_webhook_signature returns true

  request.headers['X-Github-Event'] = 'membership'
  body = {
    action: 'added',
    team: { id: shopify_team.github_id, name: shopify_team.name, slug: shopify_team.slug, url: shopify_team.api_url },
    organization: { login: 'shopify' },
    member: { login: 'attacker' },
    repository: { owner: { login: 'attacker-org' } } # binding broken here: auth org != mutated org
  }.to_json

  assert_difference -> { Membership.count }, 1 do
    post :create, body:, as: :json
    assert_response :ok
  end

  attacker = User.find_by(login: 'attacker')
  assert Membership.exists?(team_id: shopify_team.id, user: attacker)
  assert attacker.authorized?
end
```
Both sides of the equality — `repository_owner` used by `verify_signature` (`'attacker-org'`) and the organization owning the mutated `Team` (`'shopify'`) — remain unequal after the request completes, while the `Membership` row and `authorized?` flip prove the escalation.

          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

            team.organization = params.organization.login
          end
        end
