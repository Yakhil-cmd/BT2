### Title
Webhook signature verified against the payload's self-declared organization, not the repository the handlers act on - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to verify the HMAC signature against by reading an *unauthenticated* field from the JSON body (`repository.owner.login` or `organization.login`), then verifies the signature using that organization's `webhook_secret`. Once verification passes, the entire raw `params` hash — including a separate, independently-attacker-controlled `repository.full_name` field — is handed unmodified to the event handlers, which use `repository.full_name` alone to resolve the `Repository`/`Stack` to mutate. The field that is cryptographically covered by the signature check (the organization used to pick the secret) is not the same field that authorizes which repository's state gets written.

### Finding Description
`verify_signature` computes the signing organization from the payload itself: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization:)` looks up a per-organization `webhook_secret` from `config/secrets.yml` and `GitHubApp#verify_webhook_signature` does an HMAC compare against that specific secret: [3](#0-2) 

The signature check therefore only proves "this request was signed by whoever holds `webhook_secret` for organization X" — where X is read from the same untrusted JSON body being verified. It does not constrain which repository the request is allowed to mutate.

After verification, `create` dispatches the full, unfiltered `params` to every registered handler: [4](#0-3) 

Handlers resolve the target `Stack`/`Repository` purely from `repository.full_name`, a field never checked against `repository_owner`: [5](#0-4) 

`PushHandler`, for example, uses that repository resolution to trigger `stack.sync_github`: [6](#0-5) 

**Binding broken:** the organization whose secret authenticated the request ≠ the repository whose Stack is written by the handler. Any operator who legitimately controls a GitHub App installation on organization A (and therefore knows/derives A's `webhook_secret`) can sign an arbitrary JSON body where `repository.owner.login`/`organization.login` = "A" (so `verify_signature` picks and passes A's secret) while `repository.full_name` = "victim-org/victim-repo" (a Stack belonging to a completely different, unrelated organization configured on the same Shipit instance). The signature check succeeds, and the handler acts on the victim's Stack using attacker-supplied event data (branch push SHA, commit statuses, check-suite conclusions, PR labels/merge actions, etc., depending on which handler is registered).

### Impact Explanation
This crosses the "an organization that authenticated versus the repository that is written" trust boundary explicitly called out in scope. Concretely, on a multi-organization Shipit deployment (the documented "Using Multiple GitHub Applications" configuration in `docs/setup.md`), an attacker who is a legitimate GitHub App owner for their *own* organization can forge webhook deliveries that are accepted as authentic for a *different* organization's repositories/stacks, e.g.:
- Forcing `GithubSyncJob`/`sync_github` for a victim Stack with attacker-chosen `after` SHA via `PushHandler`.
- Injecting fabricated commit `Status` records for a victim commit via `StatusHandler`.
- Triggering `RefreshCheckRunsJob` or pull-request state transitions (label/merge/close handling) against a victim repository.

This is a cross-repository/cross-organization write achieved without ever holding the victim organization's actual `webhook_secret`, satisfying the "cross-repository writes" Critical-impact criterion.

### Likelihood Explanation
Requires the attacker to control (or be granted) a legitimate GitHub App installation/webhook secret for *any* one organization configured in the multi-org `github:` section of `config/secrets.yml` — a normal, low-privilege scenario for SaaS-style multi-tenant Shipit deployments where different customer orgs each install their own App. No access to the victim's secret, GitHub token, or Shipit session is needed. The only extra step beyond a normal legitimate webhook is substituting the `repository` object's `full_name` while keeping `owner.login`/`organization.login` matching the attacker's own org.

### Recommendation
After selecting `github_app` by `repository_owner`, re-validate that `params.dig('repository', 'full_name')` (and `organization.login` if present) actually belongs to the same organization used for signature verification (e.g., compare `repository.owner.login` case-insensitively against the resolved `repository_owner`, and reject if `Repository.from_github_repo_name` resolves to a Stack whose organization differs from the authenticated one). Alternatively, verify the signature independently per configured organization/secret without trusting the payload to select which secret to check against, or scope one GitHub App/webhook secret strictly to the repositories it is installed on and cross-check installation membership before dispatching to handlers.

### Proof of Concept
1. Attacker legitimately owns/operates a GitHub App installed on organization `attacker-org`, giving them `attacker-org`'s `webhook_secret` (a normal capability for anyone running a Shipit multi-org deployment).
2. Attacker crafts a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org" }
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(attacker-org_webhook_secret, raw_body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: 'attacker-org')`, verifies against `attacker-org`'s secret successfully, and lets the request through. [1](#0-0) 
5. `create` dispatches to `PushHandler`, which resolves `Repository.from_github_repo_name('victim-org/victim-repo')` and calls `stack.sync_github(expected_head_sha: 'attacker-chosen-sha')` on the victim's Stack, even though the request was never signed by `victim-org`'s secret. [6](#0-5) [5](#0-4)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
