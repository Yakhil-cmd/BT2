## Title
Reward misattribution: closing and recreating a stake account between epoch-reward calculation and partitioned distribution lets stale reward data be merged onto an unrelated new delegation - (File: runtime/src/bank/partitioned_epoch_rewards/distribution.rs)

### Summary
`Bank::store_stake_accounts_in_partition` and its helper `Bank::build_updated_stake_reward` look up the stake account to credit purely by `stake_pubkey` in the *live* `stakes_cache` at distribution time, not the snapshot used during reward calculation. If a staker fully withdraws (closing) their stake account after the calculation phase captured its reward, and then recreates a brand-new stake account at the same address before the distribution block for their partition executes, the stale, previously-calculated `PartitionedStakeReward` (old delegation, old voter_pubkey, old `credits_observed`, old stake amount) gets merged into the new account, minting the old reward's lamports into it and overwriting the new delegation's state with the resurrected old one.

### Finding Description
Reward calculation (`calculate_stake_rewards_and_commissions` in `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`) produces an immutable `PartitionedStakeReward` snapshot keyed by pubkey at the epoch boundary [1](#0-0) . This snapshot is stored in `EpochRewardPhase::Distribution` and consumed block-by-block, potentially many blocks later, by `distribute_epoch_rewards_in_partition` → `store_stake_accounts_in_partition` [2](#0-1) .

Crucially, `store_stake_accounts_in_partition` reads `self.stakes_cache.stakes()` at *current* (distribution-time) bank state, not the calculation-time snapshot, and `build_updated_stake_reward` looks the account up solely by pubkey: [3](#0-2) 

It then unconditionally overwrites the account's entire `Stake` state (delegation, voter_pubkey, activation/deactivation epoch, `credits_observed`) with the value computed during the calculation phase, only adjusting the `delegation.stake` amount for rent purposes: [4](#0-3) 

`StakesCache::check_and_store` removes an entry from the cache once an account's lamports reach 0 (full withdrawal/closure), and re-inserts a brand-new entry keyed by the same pubkey once a new stake account is created/delegated there, with no continuity check against the old entry: [5](#0-4) [6](#0-5) 

Exploit flow:
1. Attacker's stake is active during rewarded epoch N and earns a positive reward, captured into the immutable `PartitionedStakeReward` at the epoch-N→N+1 boundary.
2. Attacker requests deactivation during epoch N (before the boundary), so by epoch N+1 the position is fully inactive and eligible for full `Withdraw`.
3. Attacker computes (deterministically, from `hash_rewards_into_partitions` using the parent blockhash, itself derivable once the first distribution block executes) which future block height will process their pubkey's partition.
4. Before that block height, attacker sends `Withdraw` (fully closes the account, removing it from `stakes_cache`) then `CreateAccount` + `InitializeStake` + `DelegateStake` to reopen a brand-new stake account at the *same* pubkey with an arbitrary new delegation.
5. When the targeted partition's block executes, `build_updated_stake_reward` fetches the *new* account from `stakes_cache_accounts`, adds the old `stake_reward` + `block_reward` lamports to it, and overwrites its `Stake` state with the old delegation's voter_pubkey/activation_epoch/deactivation_epoch/`credits_observed` (capped stake amount only, per `adjust_delegation_for_rent`) [7](#0-6) .

No check in this path verifies that the live account at distribution time is "the same" delegation instance that earned the reward (e.g., no epoch/generation nonce, no activation_epoch/voter_pubkey consistency check under the `adjust_delegations_for_rent` branch). The only existing guard, the `assert_eq!` in the non-adjust-rent branch, only checks lamport-consistent stake amount, not identity, and is bypassed entirely when `adjust_delegations_for_rent` (SIMD-0392) is active [8](#0-7) .

### Impact Explanation
This is minted-lamport misattribution: `stake_reward_lamports_minted` is added to `Bank::capitalization` and credited to whatever stake account currently occupies the pubkey, even though the real delegation that earned it has already been closed and cashed out [9](#0-8) . Additionally, the attacker's freshly-created delegation is silently clobbered and replaced by the resurrected old delegation's voter_pubkey/activation_epoch/`credits_observed`, corrupting the intended new stake state. This matches "Critical: reward theft/mis-attribution across unrelated delegations sharing an address" per the scoped bounty category — real lamports get minted onto an address whose current owner already withdrew the underlying stake, violating "each stake account earns rewards for a given epoch exactly once at its own credits."

### Likelihood Explanation
Feasible for any unprivileged staker who controls the keypair of their own stake account: only ordinary `Withdraw`, `CreateAccount`, `InitializeStake`, `DelegateStake` instructions are needed, no elevated privileges. The distribution window spans up to `SLOTS_PER_EPOCH/10` blocks (per `partitioned_rewards_stake_account_stores_per_block` capping logic), giving ample time to time the withdraw/recreate sequence once the partition assignment (deterministic via `hash_rewards_into_partitions` and the known parent blockhash) is known. Timing risk exists (must land before the exact target block), but the attacker can retry every block until their partition's block height is reached, or simply always redo the withdraw/recreate on every block leading up to it.

### Recommendation
Bind the calculation-time `PartitionedStakeReward` to the specific delegation instance it was computed for (e.g., include and verify `voter_pubkey`, `activation_epoch`, and pre-reward `credits_observed`/stake amount against the live `stakes_cache` entry at distribution time), and treat any mismatch as `DistributionError` (burn the reward) rather than unconditionally overwriting the live account's state. Alternatively, snapshot and lock the specific `StakeAccount` state (not just pubkey) at calculation time and require the live account to match that snapshot before crediting.

### Proof of Concept
Rust integration test plan (extending `runtime/src/bank/partitioned_epoch_rewards/distribution.rs` test module):
1. Build a bank; create stake account `S` delegated to vote account `V1` with large stake; advance epoch so that it earns a reward for epoch N (positive `stake_reward`/`credits_observed`).
2. At the epoch boundary, capture the `PartitionedStakeReward` for `S` via `calculate_stake_rewards_and_commissions`, but before calling `store_stake_accounts_in_partition`, simulate: `bank.store_account(&S, &zero_lamport_account)` (full withdraw/close), then `bank.store_account(&S, &new_stake_account_delegated_to(V2, small_stake))` (fresh delegate to a different voter with fresh `credits_observed`=0).
3. Call `Bank::store_stake_accounts_in_partition` with the stale `PartitionedStakeReward`.
4. Assert that the resulting stored account at `S` has `delegation.voter_pubkey == V1` (old) instead of `V2` (new), `credits_observed` equal to the old redeemed value, and `post_balance` includes the old `stake_reward + block_reward` even though `S`'s live delegation was `V2` with zero prior credits — demonstrating reward/state misattribution onto an unrelated new delegation, and that `bank.capitalization()` increased by `stake_reward_lamports_minted` despite the original delegation no longer existing.

fn adjust_delegation_for_rent(
    delegation: &mut Delegation,
    rewarded_epoch: Epoch,
    new_delegation_with_rewards: u64,
    lamports_with_rewards: u64,
    minimum_lamports: u64,
) {
    let new_delegation = std::cmp::min(
        new_delegation_with_rewards,
        lamports_with_rewards.saturating_sub(minimum_lamports),
    );

    if new_delegation != delegation.stake {
        delegation.stake = new_delegation;
        // Deactivate stake if needed. This deactivation is immediate,
        // unlike a requested deactivation which happens at the next epoch
        // boundary
        if new_delegation == 0 {
            delegation.deactivation_epoch = rewarded_epoch;
        }
    }
}

    fn upsert_stake_delegation(
        &mut self,
        stake_pubkey: Pubkey,
        stake_account: StakeAccount,
        new_rate_activation_epoch: Option<Epoch>,
        use_fixed_point_stake_math: bool,
    ) {
        debug_assert_ne!(stake_account.lamports(), 0u64);
        let delegation = stake_account.delegation();
        let voter_pubkey = delegation.voter_pubkey;
        let stake = delegation_effective_stake(
            delegation,
            self.epoch,
            &self.stake_history,
            new_rate_activation_epoch,
            use_fixed_point_stake_math,
        );
        match self.stake_delegations.insert(stake_pubkey, stake_account) {
            None => {
                self.add_delegated_stake(voter_pubkey, stake);
                self.vote_accounts.add_stake(&voter_pubkey, stake);
            }
            Some(old_stake_account) => {
                let old_delegation = old_stake_account.delegation();
                let old_voter_pubkey = old_delegation.voter_pubkey;
                let old_stake = delegation_effective_stake(
                    old_delegation,
                    self.epoch,
                    &self.stake_history,
                    new_rate_activation_epoch,
                    use_fixed_point_stake_math,
                );
                if voter_pubkey != old_voter_pubkey || stake != old_stake {
                    self.sub_delegated_stake(&old_voter_pubkey, old_stake);
                    self.add_delegated_stake(voter_pubkey, stake);
                    self.vote_accounts.sub_stake(&old_voter_pubkey, old_stake);
                    self.vote_accounts.add_stake(&voter_pubkey, stake);
                }
            }
        }
    }
