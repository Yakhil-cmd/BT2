### Title
Cross-tenant webhook forgery: signature verified against `repository.owner.login`'s GitHub App secret but stack resolution keyed on unrelated `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate an inbound webhook against using `repository_owner`, a field read directly out of the untrusted JSON payload (`params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`). Once the signature check passes, `create` dispatches the *entire* payload to every registered handler, and those handlers resolve the target `Stack`/`Repository` using a *different* payload field: `payload.dig('repository', 'full_name')` (see `Shipit::Webhooks::Handlers::Handler#repository_name`). Nothing ties `repository.owner.login` (the field used to pick the authenticating secret) to `repository.full_name` (the field used to decide which repository/stack gets acted upon).

### Finding Description
In multi-organization deployments, Shipit supports one distinct GitHub App/webhook secret per organization: [1](#0-0) . The controller resolves which app/secret to verify against solely from attacker-supplied JSON: [2](#0-1) [3](#0-2) 

`verify_webhook_signature` only proves that the raw body was HMAC-signed with the secret belonging to whatever organization `repository_owner` claims (`Shipit.github(organization: repository_owner)` looks up that org's `webhook_secret` via `github_app_config`) — [4](#0-3) . It never confirms that `repository.owner.login` actually matches the repository the payload claims to be about.

After the signature check passes, the handlers run against the same payload but key off a *different* field, `repository.full_name`, to find the `Repository`/`Stack` to mutate: [5](#0-4) [6](#0-5) 

Both `repository.owner.login` and `repository.full_name` are entirely attacker-controlled since the attacker is the one composing the raw HTTP POST body sent to Shipit's webhook endpoint (Shipit does not re-derive owner/login from GitHub itself — it trusts these two independent fields inside the same JSON blob). This is exactly the "organization authenticated versus the repository that is written" binding break called out by the analog rules: the HMAC only proves *an* org's secret was known to the sender; it does not prove that the sender is authorized for the specific repository named in `full_name`.

Concretely: if Org A is any organization configured on this multi-tenant Shipit instance whose GitHub App webhook secret is known to Org A's own administrators (they created/own that App), an Org A admin/attacker can POST a forged webhook body where:
- `repository.owner.login = "OrgA"` (so `Shipit.github(organization: "OrgA")` is selected and the HMAC computed with `OrgA`'s own known secret validates), and
- `repository.full_name = "victim-org/victim-repo"` (an unrelated repository/stack hosted on the same Shipit instance that Org A has no access to).

`verify_signature` passes because the HMAC is valid for the secret actually used. `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` then runs, e.g., `PushHandler#process`, `Handler#stacks` resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github(expected_head_sha: params.after)` on the victim's stack — a stack the attacker has no `ApiClient`/session/GitHub permission on. The same mechanism lets the attacker forge `status`/`check_suite`/`commit_status` events against victim commits, injecting fabricated CI statuses that feed directly into `Stack#deployable?`/`blocking_statuses`/`required_statuses` gating used by the merge queue and continuous deployment, or forge `membership`/`pull_request` events that mutate `Team`, `Membership`, or `ReviewStack` records tied to the victim repository.

### Impact Explanation
This breaks the isolation boundary between tenants/organizations configured on a single Shipit instance: an entity that only legitimately controls one organization's GitHub App/webhook secret can forge webhook events that mutate/act on a completely different, victim repository's `Stack`/`Repository`/`Commit` state (cross-repository writes), including data that feeds CI-gating logic used to authorize deploys (`required_statuses`, `blocking_statuses`). That satisfies the Critical "cross-repository writes/unauthorized deploy" bar, since spoofed commit statuses can make an otherwise non-deployable commit appear deployable.

### Likelihood Explanation
Exploitability depends on the deployment running the multi-organization `github:` config with per-org webhook secrets and multiple tenants/repos on one instance — the single-app config (`github_default_organization.nil?`) collapses to one shared secret and doesn't provide this specific cross-org signature-to-target mismatch (though it still doesn't cross-check owner vs full_name, it removes the "attacker knows a distinct valid secret for their own org" precondition). Given multi-org support is a documented, first-class feature (`docs/setup.md`, `secrets_double_github_app.yml` fixture), this is a realistic configuration, and the attack requires no Shipit session, ApiClient token, or GitHub write access to the victim repo — only knowledge of one organization's own configured webhook secret, which its own administrators legitimately possess.

### Recommendation
In `WebhooksController#verify_signature` / `Handler`, cross-validate that the organization used to select the verifying secret (`repository.owner.login` / `organization.login`) matches the owner embedded in `repository.full_name` before dispatching to handlers, rejecting (422) any mismatch. More robustly, resolve the target `Repository`/`Stack` first using the trusted `repository.owner.login` (the value used for secret selection) rather than trusting `full_name` independently, so a single payload field determines both authentication scope and the entity acted upon.

### Proof of Concept
1. Configure Shipit with multi-org `github:` secrets for `OrgA` (attacker-administered) and `OrgB` (victim), each with a `webhook_secret` known respectively to each org's own admins, per `docs/setup.md` and `test/dummy/config/secrets_double_github_app.yml`.
2. As an OrgA admin (who legitimately knows `webhook_secret` for OrgA because they configured OrgA's own GitHub App), craft a raw JSON body for a `push` event:
   ```json
   { "ref": "refs/heads/master", "after": "<attacker-chosen-sha>",
     "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" } }
   ```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(webhook_secret_OrgA, body)>`.
4. POST to `/github/webhooks` with `X-Github-Event: push`. `verify_signature` selects `Shipit.github(organization: "OrgA")` (via `repository_owner`), the HMAC validates, and the request is accepted.
5. `PushHandler#process` resolves `Repository.from_github_repo_name("OrgB/victim-repo")` from `repository.full_name` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on OrgB's stack, despite the attacker never having any credential, permission, or GitHub-authenticated relationship with `OrgB/victim-repo`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        "unknown_organization=#{e.message}",

      ].join(' '))
    end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
