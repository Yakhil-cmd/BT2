## Analysis

The `pallet-asset-rewards` in this repo implements the same "staking rewards" accounting pattern as the reported `MultiRewards.sol`, and it reproduces the identical precision-loss root cause: `reward_per_token_stored` is only incremented by an integer division that can truncate to zero while `last_update_block` (the FRAME analog of `lastUpdateTime`) is unconditionally advanced. [1](#0-0) 

The precision buffer used here, `PRECISION_SCALING_FACTOR = 4096`, is drastically smaller than Solidity's `1e18` used in the original report, making the truncation-to-zero condition far easier to satisfy on-chain. [2](#0-1) 

Any signed account can permissionlessly trigger the update path via `stake`, `unstake` (on their own account) or `harvest_rewards` (on their own account, no privilege required), each of which calls `update_pool_and_staker_rewards` → `reward_per_token` → `update_pool_rewards`, persisting `last_update_block = now` regardless of whether `reward_per_token_stored` changed. [3](#0-2) [4](#0-3) [5](#0-4) 

### Title
Precision loss in `reward_per_token` allows griefing that permanently freezes reward accrual for a pool - (File: substrate/frame/asset-rewards/src/lib.rs)

### Summary
`pallet-asset-rewards::reward_per_token` computes the incremental reward-per-token using integer division: `(reward_rate_per_block * blocks_elapsed * PRECISION_SCALING_FACTOR) / total_tokens_staked`. When the numerator is smaller than `total_tokens_staked`, the division truncates to `0`, so `reward_per_token_stored` stays unchanged, while `last_update_block` is still advanced in the same call. Since any staker can permissionlessly trigger this update path on their own account (`stake`, `unstake`, `harvest_rewards`), and `PRECISION_SCALING_FACTOR` is only `4096` (vs. `1e18` in the referenced Solidity contract), an attacker can keep the elapsed-block window small enough on every call to permanently suppress reward accrual for the whole pool, causing zero reward yield for all stakers for the remainder of the pool's life.

### Finding Description
`reward_per_token` is:
```rust
Ok(pool_info.reward_per_token_stored.ensure_add(
    pool_info
        .reward_rate_per_block
        .ensure_mul(rewardable_blocks_elapsed.into())?
        .ensure_mul(PRECISION_SCALING_FACTOR.into())?
        .ensure_div(pool_info.total_tokens_staked)?,
)?)
``` [6](#0-5) 

`update_pool_rewards` unconditionally sets `last_update_block = now` and `reward_per_token_stored = reward_per_token`, even when `reward_per_token` computed the *same* value as before due to truncation: [7](#0-6) 

This mirrors exactly the flaw described in the external report for `MultiRewards.sol`'s `updateReward`/`rewardPerToken`: whenever `blocks_elapsed * reward_rate_per_block * PRECISION_SCALING_FACTOR < total_tokens_staked`, the reward-per-token accumulator does not advance, yet the "last updated" timestamp/block does — permanently losing the reward accrual for that window.

The trigger is fully permissionless: `stake`, `unstake` and `harvest_rewards` are signed extrinsics callable by any account, and when called on the caller's own stake (`staker == caller`), they bypass the `now > pool_info.expiry_block` restriction: [8](#0-7) [9](#0-8) 

An attacker can:
1. Join the pool with `stake` (increasing `total_tokens_staked` to any size they can fund, e.g. via a low-value staked asset), inflating the denominator.
2. Repeatedly call `harvest_rewards`/`unstake` (no-op amounts or on their own position) every N blocks, where N is chosen so `reward_rate_per_block * N * 4096 < total_tokens_staked`.
3. Each call advances `last_update_block` without advancing `reward_per_token_stored`, nullifying reward accrual for that window for every staker in the pool, not just the attacker.

Because `PRECISION_SCALING_FACTOR` is only `4096` (2^12) — far smaller than the `1e18` scaling used in the referenced Solidity contract — the condition for zero accrual is trivially reachable with realistic `total_tokens_staked`/`reward_rate_per_block` combinations, without needing extreme parameters.

### Impact Explanation
All non-attacker stakers in an affected pool can be griefed out of their rewards for the duration the attacker sustains the attack, up to the entire `expiry_block` window, since `reward_per_token_stored` — the sole basis for `derive_rewards`/`pending_rewards` computations — never increases. This is a loss of expected yield for legitimate participants caused solely by a third party's low-cost, permissionless extrinsic calls (transaction fees), matching the Medium severity/likelihood classification of the original report. It also causes a continuous, smaller-scale precision-loss dust accumulation in the pool account on every normal invocation, independent of active griefing.

### Likelihood Explanation
Medium: the attacker needs no elevated privileges — only the ability to submit ordinary signed `stake`/`harvest_rewards`/`unstake` extrinsics for their own account. The 4096 scaling factor (versus the 1e18 factor in the original EVM report) meaningfully lowers the bar for triggering the truncation-to-zero condition, so pools with moderately large `total_tokens_staked` relative to `reward_rate_per_block` are exposed with ordinary staking amounts rather than needing extreme values.

### Recommendation
Track and carry forward the truncated remainder of the division in `reward_per_token` (e.g., store `(reward_rate_per_block * blocks_elapsed * PRECISION_SCALING_FACTOR) % total_tokens_staked` alongside `reward_per_token_stored`) and add it back into the numerator on the next invocation, so reward accrual is never silently lost between updates regardless of how frequently the update path is triggered.

### Proof of Concept
No PoC was executed. This is a code-level derivation from reading `substrate/frame/asset-rewards/src/lib.rs` (`reward_per_token`, `update_pool_rewards`, `stake`, `unstake`, `harvest_rewards`) and comparing it against the mechanism described in the external `MultiRewards.sol` report; a minimal FRAME integration test would call `create_pool`, `stake` with a large `total_tokens_staked` and small `reward_rate_per_block`, then repeatedly call `harvest_rewards` every few blocks while asserting `reward_per_token_stored` remains unchanged and `last_update_block` advances, analogous to the Solidity `test_rewardPerTokenStored` case in the report. Existing test helpers such as `pool_pending_rewards`/`reward_imbalance` in `substrate/frame/nomination-pools/src/mock.rs` (a different but related reward pallet) show the codebase already has precedent for reward-precision regression tests, underscoring this is a testable, reachable condition rather than a theoretical one.

		pub fn harvest_rewards(
			origin: OriginFor<T>,
			pool_id: PoolId,
			staker: Option<T::AccountId>,
		) -> DispatchResult {
			let caller = ensure_signed(origin)?;
			let staker = staker.unwrap_or(caller.clone());

			// Always start by updating the pool and staker rewards.
			let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
			let now = T::BlockNumberProvider::current_block_number();
			ensure!(now > pool_info.expiry_block || caller == staker, BadOrigin);

			let staker_info =
				PoolStakers::<T>::get(pool_id, &staker).ok_or(Error::<T>::NonExistentStaker)?;
			let (pool_info, mut staker_info) =
				Self::update_pool_and_staker_rewards(&pool_info, &staker_info)?;

			// Transfer unclaimed rewards from the pool to the staker.
			T::Assets::transfer(
				pool_info.reward_asset_id,
				&pool_info.account,
				&staker,
				staker_info.rewards,
				// Could kill the account, but only if the pool was already almost empty.
				Preservation::Expendable,
			)?;

			// Emit event.
			Self::deposit_event(Event::RewardsHarvested {
				caller,
				staker: staker.clone(),
				pool_id,
				amount: staker_info.rewards,
			});

			// Reset staker rewards.
			staker_info.rewards = 0u32.into();

			if staker_info.amount.is_zero() {
				PoolStakers::<T>::remove(&pool_id, &staker);
			} else {
				PoolStakers::<T>::insert(&pool_id, &staker, staker_info);
			}

			Ok(())
		}

		/// Derives the current reward per token for this pool.
		pub(super) fn reward_per_token(
			pool_info: &PoolInfoFor<T>,
		) -> Result<T::Balance, DispatchError> {
			if pool_info.total_tokens_staked.is_zero() {
				return Ok(pool_info.reward_per_token_stored);
			}

			let rewardable_blocks_elapsed: u32 =
				match Self::last_block_reward_applicable(pool_info.expiry_block)
					.ensure_sub(pool_info.last_update_block)?
					.try_into()
				{
					Ok(b) => b,
					Err(_) => return Err(Error::<T>::BlockNumberConversionError.into()),
				};

			Ok(pool_info.reward_per_token_stored.ensure_add(
				pool_info
					.reward_rate_per_block
					.ensure_mul(rewardable_blocks_elapsed.into())?
					.ensure_mul(PRECISION_SCALING_FACTOR.into())?
					.ensure_div(pool_info.total_tokens_staked)?,
			)?)
		}
