### Title
Cross-repository commit status forgery via unscoped `StatusHandler#process` sha lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves commits solely by `Commit.where(sha: params.sha)`, without validating that the incoming webhook's `repository.full_name` matches the repository owning that commit's stack. This lets any webhook sender with a validly-signed `status` event for *some* repository/organization tracked by Shipit set a fabricated `success` status on a commit belonging to a completely unrelated stack, defeating `Commit#deployable?` and the `require_ci` deploy gate in `Shipit::Api::DeploysController#create`.

### Finding Description
The broken binding: `status.stack_id == commit_from_payload_repository.stack_id` is assumed but never enforced — instead the code enforces only `status.sha == params.sha`, with no equality check against `payload['repository']['full_name']`.

Path: `WebhooksController#create` dispatches `status` events to `Shipit::Webhooks::Handlers::StatusHandler` [4](#0-3)  after `verify_signature`, which validates the HMAC using `Shipit.github(organization: repository_owner)` derived from the **attacker-controlled** payload's own `repository.owner.login` field [5](#0-4) . `StatusHandler#process` then does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [1](#0-0)  with **no filter by repository/stack** — contrast with `PushHandler`, which correctly scopes via `stacks.not_archived.where(branch:)` derived from `Repository.from_github_repo_name(repository_name)` [2](#0-1) [3](#0-2) . `create_status_from_github!` writes a `Status` row scoped to `commit.stack_id` (the victim's real stack), not the payload's repository [6](#0-5) , and `Commit#deployable?` becomes true once this forged status flips `success?` [7](#0-6) .

Downstream, `Shipit::Api::DeploysController#create`'s `require_ci` guard only checks `commit.deployable?` [8](#0-7) , which is now poisoned.

Attack requires the attacker to be able to produce a webhook event whose signature validates against `Shipit.github(organization: repository_owner)` for *some* organization Shipit tracks, and to know the target victim commit's sha (public GitHub data). Whether an unprivileged attacker (per the strict attacker model in this prompt — no GitHub App installation, no team membership, no repo under a tracked org) can actually produce such a validly-signed request is the key open question and was not fully verified: this requires inspecting `GithubApp#verify_webhook_signature` and how `webhook_secret`/GitHub App secrets are scoped (global app secret vs. per-organization/per-installation secret), which I could not fully confirm from indexed content. If the secret is genuinely per-organization/per-installation and only issued to already-vetted repositories, then the attacker described in the strict "unprivileged internet user" model (no session, no team membership, no maintainer role) cannot forge a valid signature at all, and this bug — while real as an authorization/scoping defect — would not be reachable by the specific attacker class defined in the rules without at least being an existing maintainer of *some* tracked repository (which is a lower bar than being a maintainer of the *victim* repository, but is not "no privileges at all").

### Impact Explanation
If exploitable by the defined attacker class, this is a cross-tenant mutation: a webhook attributable to repository A can write a fabricated success `Status` row against a commit belonging to victim stack/repository B, defeating the `require_ci` deploy gate and CI attestation entirely — "a payload for one repository mutating another's stack, commit" per the Critical bucket. This is repeatable against arbitrary target shas (as long as they are known) and is not limited to a single stack.

### Likelihood Explanation
Requires the attacker to already control at least one repository/organization webhook relationship recognized by Shipit (i.e., be an existing maintainer of *any* tracked repo, not necessarily the victim's), and to know the victim's exact commit sha. Whether "any GitHub user who can push to a fork" satisfies "controls a repository/org that Shipit already trusts for signature verification" is uncertain and depends on `GithubApp`/`Shipit.github` secret scoping, which was not fully confirmed here.

### Recommendation
In `StatusHandler#process`, scope the commit lookup to the webhook's own repository, mirroring `PushHandler`: e.g. `stacks.each { |stack| stack.commits.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) } }`, ensuring a status event can only mutate commits belonging to the repository that sent it.

This finding is valid as a scoping defect in `StatusHandler`, but I could not fully confirm within this session whether it is reachable by the specific "fully unprivileged, no session/token/team/maintainer-role" attacker defined in the rules, due to incomplete visibility into `GithubApp#verify_webhook_signature`'s secret scoping — flagging this as an open verification gap rather than asserting definitive exploitability under the strict attacker model.
