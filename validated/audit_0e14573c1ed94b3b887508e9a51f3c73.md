This finding conflates two unrelated systems: the storage-layer accumulator proof-serving path (`TransactionAccumulatorDb::get_transaction_proof`) and the actual transaction admission stack (mempool, vm-validator, VM prologue). They are not on the same trust boundary.

Key points:

1. `get_transaction_proof` simply computes a Merkle proof from already-committed leaves given a `version` and `ledger_version`; it does not decide whether a transaction was validated or admitted — it only reflects what has already been committed to the ledger. [1](#0-0) 

2. Any proof returned by storage is checked by the verifier against a trusted, validator-signed `LedgerInfo`'s `transaction_accumulator_hash()`, not against a value the storage layer itself asserts. `verify_transaction_info` recomputes the transaction-info hash and validates the accumulator proof cryptographically against that signed root hash. [2](#0-1) 

3. The Merkle-proof verification (`TransactionAccumulatorProof::verify`) recombines sibling hashes bottom-up and only succeeds if the resulting root matches the expected (signed) root hash exactly — it rejects mismatches outright rather than silently accepting them. [3](#0-2) 

4. Even if a client requests a "mismatched" `ledger_version` (e.g., stale or out-of-range), the proof produced would be checked against leaves at that exact `num_leaves = ledger_version + 1` boundary, and any inconsistency (e.g., transaction version newer than the ledger info version) is explicitly rejected before proof verification even runs. [4](#0-3) 

None of this code path touches sender binding, signer sets, sequence numbers, chain-id, gas, or fee-payer authorization — those are enforced entirely in mempool's `vm-validator` and the VM prologue during transaction admission and execution, which are separate from the read-only proof-serving/query path described here. A stale or mismatched `ledger_version` in a proof request can, at most, cause a `NotFound`/inconsistency error or a proof that fails cryptographic verification against the trusted signed root — it cannot cause a transaction whose sender was never validated by the VM prologue to be "admitted," because admission already happened (or didn't) before any transaction info/accumulator entry ever exists to be proven against.

```rust
/// Verifies that a given `transaction_info` exists in the ledger using provided proof.
fn verify_transaction_info(
    ledger_info: &LedgerInfo,
    transaction_version: Version,
    transaction_info: &TransactionInfo,
    ledger_info_to_transaction_info_proof: &TransactionAccumulatorProof,
) -> Result<()> {
    ensure!(
        transaction_version <= ledger_info.version(),
        "Transaction version {} is newer than LedgerInfo version {}.",
        transaction_version,
        ledger_info.version(),
    );

    let transaction_info_hash = transaction_info.hash();
    ledger_info_to_transaction_info_proof.verify(
        ledger_info.transaction_accumulator_hash(),
        transaction_info_hash,
        transaction_version,
    )?;

    Ok(())
}
```
