## Finding

### Title
Full plaintext of decrypted device messages (including private-payment blinding secrets) is written to log files - (File: device.js)

### Summary
`decryptPackage()` in `device.js` decrypts every inbound device message (received from any paired correspondent or relayed through a hub) and immediately writes the **entire decrypted plaintext** to the console/log stream before any content-specific handling occurs. This is the same bug class as CVE-2024-47094 (Checkmk): confidential data that is only supposed to be known to the two communicating parties is unconditionally persisted into local log files that unprivileged local readers of those logs can access.

### Finding Description
When a device message arrives (`hub/message` justsaying or a self-hosted `hub/deliver` request), `device.js` verifies the signature and then calls `decryptPackage()`: [1](#0-0) 

```
	var decrypted_message = decrypted_message_buf.toString("utf8");
	console.log("decrypted: "+decrypted_message);
```

This logs the raw decrypted JSON of *every* message body before `wallet.js`'s `doHandle()` dispatches on `subject`. The decrypted body can carry highly sensitive content depending on `subject`, including:

- `private_payments` chains — full private-element payloads with `blinding` factors, amounts and addresses that are designed to stay hidden from anyone who is not the direct recipient (see the analogous logging in `private_payment.js`/`indivisible_asset.js`, which also dump full private elements: [2](#0-1) ).
- wallet-management secrets such as `my_xpubkey`, signing requests/`assocPrivatePayloads`, and pairing data used to set up shared/multisig wallets (`wallet.js` `doHandle`, e.g. the `signature`/`private_payments` cases at [3](#0-2) ).
- free-form `text`/`object` chat messages, which users routinely use to exchange recovery mnemonics for textcoins (see `sent_mnemonics`/`assocMnemonics` handling in `wallet.js` [4](#0-3) ), and which are themselves separately logged in plaintext in `claimBackOldTextcoins`: [5](#0-4) 

Because `console.log` output in ocore-based node/hub deployments is typically redirected to a persistent log file, any local process or user with read access to that log file (but without access to the wallet's SQLite/MySQL secrets or private keys) obtains the same confidential material a full compromise of the wallet database would provide — mirroring the Checkmk advisory's description of "remote site secrets... written to web log files accessible to local site users."

The trigger requires no special privilege: any correspondent that is already paired with the victim's device (a normal, expected participant class per the reachable-analog rules — "paired device") can send an arbitrary `text`/`object`/`private_payments` message and force its plaintext, including private-payment blinding secrets, into the victim's log file. The hub relaying `hub/deliver` (`network.js`) similarly stores/forwards the still-encrypted envelope, but decryption and full-content logging happens unconditionally at the receiving device.

### Impact Explanation
An unprivileged correspondent (paired device) or a private-payment counterparty can cause confidential material to be durably written into the recipient's plaintext application logs:
- Private-payment `blinding` factors and amounts for indivisible/divisible private assets are exposed to anyone with local log-file read access, even though the entire design goal of `blinding` is to keep hidden-denomination outputs unlinkable/untraceable on the public DAG. Exposure lets a local log reader de-anonymize and link private outputs to specific amounts/addresses (a direct violation of the wallet's private-payment privacy guarantee) and, since `spend_proof` is derived deterministically from `{asset, unit, message_index, output_index, address, amount, blinding}` (see `indivisible_asset.js` construction at [6](#0-5) ), a party who obtains it from the log without being the legitimate holder gains the exact data needed to construct duplicate spend proofs / interfere with input uniqueness for that private output.
- Textcoin mnemonics logged via `claimBackOldTextcoins` are equivalent to private keys controlling live funds; leakage from log files enables unauthorized spending of those funds by a local reader who otherwise has no wallet-database access.

This satisfies "concrete... unauthorized spending... or freezing" and "node disagreement on validity" thresholds indirectly through spend-proof/blinding disclosure, and directly through mnemonic disclosure enabling fund theft.

### Likelihood Explanation
No attacker privilege beyond being an already-paired correspondent (or being the counterparty of a private payment/textcoin) is required — this is one of the explicitly allowed reachable actor classes. The logging is unconditional (`console.log`) on every message decryption and every completed textcoin claim-back cycle, so exploitation only requires the victim's node to have file/stdout logging enabled, which is the default for long-running ocore hub/wallet processes.

### Recommendation
- Remove or gate behind a verbose/debug-only, disabled-by-default flag the `console.log("decrypted: "+decrypted_message)` statement in `device.js`'s `decryptPackage()`, and similarly the raw payload dumps in `private_payment.js` / `indivisible_asset.js` (`console.log("saving private chain "+JSON.stringify(arrPrivateElements))`, spend-proof logging including `blinding`).
- Redact `blinding`, `mnemonic`, and other secret fields before logging (log only unit/message identifiers, not full payloads).
- Remove `row.mnemonic` from the `claimBackOldTextcoins` log lines in `wallet.js`; log only the unit/address.
- Adopt a structured logger with explicit secret-scrubbing/allow-listing instead of ad hoc `console.log` of full objects.

### Proof of Concept
1. Pair device B with victim device A (normal, permitted correspondent relationship).
2. From B, send A a `private_payments` message carrying a private (hidden-denomination) asset chain, or simply a `text` message containing a textcoin recovery mnemonic.
3. On A's node, `device.js` `decryptPackage()` executes `console.log("decrypted: "+decrypted_message)`, writing the full plaintext (including `blinding`, `amount`, `address`, or the mnemonic) to A's process log/log file.
4. Any local user/process on A's host with read access to that log file (but not to A's database or private keys) now has the private-payment blinding secret or the textcoin mnemonic, and can use it to link/attack the private output or spend the textcoin funds. [7](#0-6) [8](#0-7) [2](#0-1)
