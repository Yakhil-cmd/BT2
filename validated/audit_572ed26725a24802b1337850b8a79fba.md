### Title
Stack-Scoped API Client Tokens Can Read Any Stack's Build Status via CCMenu Endpoint — ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Api::CCMenuController` re-implements the `stack` lookup used by every other API controller, but omits the scoping enforced by `Api::BaseController`. As a result, an `ApiClient` token that is scoped to a single stack (`ApiClient#stack_id` set) can be used to read the CCMenu/build-status XML of *any* stack in the installation, not just the one it was authorized for.

### Finding Description
`Api::BaseController` defines the authorization boundary between an `ApiClient` token and the stacks it is allowed to touch: [1](#0-0) 

Every stack-scoped endpoint that inherits from `BaseController` (e.g. `Api::StacksController`) resolves the target stack through `stacks.from_param!`, which is filtered by `current_api_client.stack_id` when the client is scoped: [2](#0-1) 

`Api::CCMenuController`, however, overrides `stack` directly and bypasses `stacks` entirely: [3](#0-2) 

It only requires the generic `read:stack` permission, which every scoped or unscoped token can hold, and resolves `params[:stack_id]` against `Stack.from_param!` with no reference to `current_api_client.stack_id`: [4](#0-3) 

The `ApiClient` model explicitly supports per-stack scoping via `belongs_to :stack, optional: true`, and this scoping is treated elsewhere as a security boundary (see the test asserting a stack-scoped client "will only see that one stack"): [5](#0-4) [6](#0-5) 

This is the exact bug class described in the report: a binding that is supposed to hold everywhere (here, "the stack a token authorizes" == "the stack a token touches") is silently dropped on one specific code path, exactly as the original report's `SocketBridge` event was silently skipped on the early-return path.

The equality broken is:
`stack the ApiClient token authorizes (current_api_client.stack_id)` ≠ `stack the CCMenu endpoint actually serves (params[:stack_id] via Stack.from_param!)`.

Before the attacker's request: a stack-scoped token can only read/act on its own stack across every other API endpoint.
After the attacker's request: the same token, hitting `GET /api/stacks/*stack_id/ccmenu`, returns build/deploy status (running/failed state, last deploy time, links) for an arbitrary, unauthorized stack.

### Impact Explanation
This is an authenticated-but-unauthorized cross-stack read of stack state/deploy status, matching the High-impact category "unauthenticated read of stack state, task streams or deploy output" — here achieved by a token whose grant is supposed to be limited to one stack. Any holder of any scoped read-only token (which can be generated by low-privileged flows such as `CCMenuUrlController`, or issued deliberately as least-privilege by an admin) can enumerate build status of every stack in the Shipit instance.

### Likelihood Explanation
Likelihood is high for anyone in possession of a stack-scoped `read:stack` token (the intended least-privilege credential type for this feature): the CCMenu route is public within the API namespace, requires no special conditions, and the missing scoping check is deterministic and always reachable, not tied to a race condition or rare configuration.

### Recommendation
Have `Api::CCMenuController#stack` reuse the inherited, scope-aware `stacks` lookup (`stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so that stack-scoped `ApiClient` tokens are restricted to their authorized stack, consistent with every other controller under `Api::BaseController`.

### Proof of Concept
1. Create (or obtain) an `ApiClient` with `stack_id` set to Stack A and `permissions: ["read:stack"]` (this is the supported least-privilege client type per `ApiClient#stack`).
2. Using that client's `authentication_token` as Basic Auth credentials, request:
   `GET /api/stacks/<org>/<repo-B>/<env-B>/ccmenu`
   where `repo-B/env-B` identifies Stack B, a stack the token was never scoped to.
3. Because `Api::CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly (bypassing `stacks`/`current_api_client.stack_id` filtering), the request succeeds and returns Stack B's CCMenu XML (build status, last deploy, running/failed state) — data the token was not authorized to access, per the same test pattern used to prove correct scoping in `test/controllers/api/stacks_controller_test.rb:217-223`.

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end
