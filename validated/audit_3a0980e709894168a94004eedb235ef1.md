This confirms the vulnerability. `LabeledHandler#respond_to_label_change?` correctly checks `repository.review_stacks_enabled` as a top-level `&&` gate applied to the whole disjunction of `archive? || unarchive?` [1](#0-0) , but `OpenedHandler#provision?` puts `review_stacks_enabled` inside only the first disjunct due to operator precedence, leaving the `allow_with_label?` and `prevent_with_label?` branches unguarded [2](#0-1) .

### Title
`OpenedHandler#provision?` ignores `review_stacks_enabled` for `allow_with_label`/`prevent_with_label` repositories, allowing unauthorized `ReviewStack` provisioning - (File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb)

### Summary
`provision?` in `OpenedHandler` is written as `repository.review_stacks_enabled && repository.provisioning_behavior_allow_all? || (...) || (...)`, and because `&&` binds tighter than `||`, `review_stacks_enabled` is only ANDed into the first disjunct. Any repository configured with `provisioning_behavior: allow_with_label` (or `prevent_with_label`) will provision a `ReviewStack` from an opened PR even when `review_stacks_enabled` is `false`, contradicting the feature-gate's intent.

### Finding Description
The broken binding: `review_stacks_enabled == false` (actual DB/config value) should equal `the gate enforced before ReviewStack creation` (which the code claims is `true` is required), but for the `allow_with_label`/`prevent_with_label` code paths the gate enforced is unconditionally `true` regardless of `review_stacks_enabled`.

Path: A GitHub webhook `pull_request` `opened` event is routed to `OpenedHandler#process`, which calls `respond_to_pull_request_opened?` → `provision?` [3](#0-2) . `provision?` is:
```
repository.review_stacks_enabled &&
  repository.provisioning_behavior_allow_all? ||
  (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
  (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
``` [2](#0-1) 
Due to Ruby operator precedence, this parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`. If `review_stacks_enabled` is `false` and `provisioning_behavior` is `allow_with_label`, an attacker who opens a PR with the configured provisioning label makes the second disjunct `true`, so `provision?` returns `true` with no check of `review_stacks_enabled` at all.

Once `provision?` is true, `process` calls `ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!` [4](#0-3) , which creates a `ReviewStack` with `branch: params.pull_request.head.ref` (attacker-controlled branch name from their own fork/PR) and `environment: "pr#{params.number}"` [5](#0-4) , then enqueues it via `Shipit::ReviewStackProvisioningQueue.add(stack)` [6](#0-5) . The queued stack eventually transitions `deprovisioned -> provisioning`, triggering `stack.provisioner.up` [7](#0-6) , which runs the repository's provisioning commands.

Existing guards do not stop this: the webhook signature check (`verify_signature`) only validates the request came from GitHub for *some* repository — it does not authorize the specific repository's `review_stacks_enabled` setting, and `LabeledHandler`'s correct pattern proves the intent was to gate all provisioning behaviors on `review_stacks_enabled`, which `OpenedHandler` fails to do. The scoping (`scope: repository.review_stacks`) prevents cross-repo writes but does not prevent this same-repo unauthorized creation.

### Impact Explanation
For any repository misconfigured/left with `review_stacks_enabled: false` and `provisioning_behavior: allow_with_label` (or `prevent_with_label`), an unprivileged PR author can force creation and provisioning of a `ReviewStack` bound to their own branch — a record write and provisioning action for a repository that has explicitly opted out of review stacks. Given the codebase's own framing (provisioner execution reaching `PTY.spawn`), this results in execution of the repository's provisioning/deploy commands against attacker-supplied branch content, which is unauthorized command execution — Critical severity. This is repeatable per PR/per repository configured this way.

### Likelihood Explanation
Requires a repository with `review_stacks_enabled: false` and `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` — a plausible, even likely, misconfiguration since these are two independent settings and nothing in the model prevents this combination [8](#0-7) . The attacker only needs to open a PR (with or without the label depending on which behavior) against such a repository — no privileges, tokens, or secrets required, just a normal webhook delivery from GitHub for their own PR.

### Recommendation
Fix operator precedence to require `review_stacks_enabled` as a top-level gate for every branch, matching `LabeledHandler`'s pattern:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (
      repository.provisioning_behavior_allow_all? ||
      (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
      (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
    )
end
```

minitest plan (in `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` style):

  repository.update!(review_stacks_enabled: false, provisioning_behavior: 'allow_with_label', provisioning_label_name: 'ship-it')
  payload = default_pull_request_opened_payload(labels: [{ name: 'ship-it' }])

    Shipit::Webhooks::Handlers::PullRequest::OpenedHandler.new(payload).process
  end

Assert both sides of the equality: `repository.review_stacks_enabled` is `false` (required to be `true` by design) vs. `Shipit::ReviewStack.count` increases (actual gate enforced allows creation) — before the fix these diverge (count increases despite `false`); after applying the recommended fix, `assert_no_difference` passes.
