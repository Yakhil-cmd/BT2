The Sandclock finding centers on a single trusted key holder being a hard prerequisite for releasing already-deposited user funds, with no recovery path if that key is lost. There's a structurally identical pattern in `ocore`'s asset system: the `cosigned_by_definer` asset flag.

### Title
Assets defined with `cosigned_by_definer: true` permanently freeze all holders' funds if the definer loses access to their key - (File: `validation.js`)

### Summary
An asset issuer (an unprivileged, ordinary unit poster) can define an asset with `cosigned_by_definer: true`. Once set, this flag is immutable for the lifetime of the asset and is enforced at the consensus/validation layer: every single payment of that asset — by any holder, forever — must include the definer's address as a cosigning author. If the definer address's private key is ever lost (or the address becomes otherwise inaccessible), all current and future holders of that asset lose the ability to transfer their balances permanently, with no protocol-level recovery mechanism.

### Finding Description
When an asset is created, `validateAssetDefinition` requires `cosigned_by_definer` to be an explicit boolean and stores it as part of the immutable asset definition unit [1](#0-0) . There is no message type that can later change this flag — the only post-creation update mechanism for assets (`asset_attestors`) only touches the attestor list, not `cosigned_by_definer` [2](#0-1) .

At payment-validation time, every payment of such an asset is rejected unless the definer's address is among the unit's authors: [3](#0-2) 

This same check is enforced client-side by both divisible and indivisible asset composers, which refuse to build a payment unless the definer's address is among the paying/signing addresses: [4](#0-3) [5](#0-4) 

The only place `cosigned_by_definer` is forcibly disabled is when an Autonomous Agent defines the asset (`cosigned_by_definer must be false because AA can't cosign`), which confirms the field is specifically meant for human-controlled definer addresses: [6](#0-5) [7](#0-6) 

Because the definer address is a normal single/multi-sig address chosen at asset-creation time and is never required to be a robust multisig or have a designated successor, an ordinary user acting as an asset issuer can (intentionally or not) create a token whose entire holder base becomes permanently dependent on that one address's key remaining accessible forever.

### Impact Explanation
If the definer's key is lost (device loss, death, corrupted wallet, forgotten seed, etc.), or the address is a light/hot wallet compromised beyond recovery, **every holder of the asset — not just the definer — permanently loses the ability to move their balance**. There is no fallback, timeout, governance mechanism, or emergency exit encoded in the protocol; the `cosigned_by_definer` requirement is enforced unconditionally by both `validation.js` and the wallet-side composers for the lifetime of the DAG. This is a full, irreversible freeze of third-party funds caused by a single point of failure, matching the "AA/asset fund freezing" impact class.

### Likelihood Explanation
Likelihood is driven purely by ordinary key-management risk on the definer's side, which is common in practice (lost seed phrases, device failure, custodial key mismanagement). Any asset issuer can set this flag when defining a token — no special privilege is required beyond normal unit posting — and any user who later acquires that asset via ordinary trading/transfer becomes exposed to this risk without necessarily being aware of it. Because the flag can't be reversed or migrated away from, the risk accumulates and never resolves itself, similar to the "hit by a bus" scenario in the original Sandclock report.

### Recommendation
Consider one or more of the following at the protocol/tooling level:
- Warn wallets/UIs prominently when interacting with `cosigned_by_definer` assets so holders understand the standing centralization/freeze risk tied to the definer's key.
- Allow (via an explicit, attested mechanism) the definer to migrate `cosigned_by_definer` control to a new address (e.g., an `asset_attestors`-like update message restricted to the current definer) so control can be moved to a multisig or rotated before a key is lost.
- Encourage/require that `cosigned_by_definer` assets use a multi-signature definer address by convention, reducing single-key-loss risk, and document this clearly in the asset-creation guidance akin to WP-M1's recommendation in the original report.

### Proof of Concept
1. Asset issuer A defines asset `X` with `is_transferrable: true`, `cosigned_by_definer: true` (a valid, fully-supported asset definition per `validateAssetDefinition`) [8](#0-7) .
2. Asset `X` is distributed/traded to many independent holders over time; each transfer unit must legitimately include A's signature, per `validatePayment`'s enforcement [3](#0-2) .
3. Issuer A loses access to their private key (device destroyed, seed lost, etc.).
4. No holder of asset `X` can ever construct a valid payment unit again: `divisible_asset.js`/`indivisible_asset.js` composers will refuse to compose the payment locally, and even if manually constructed, `validation.js` will reject any unit lacking A's authorship for asset `X` payments.
5. All balances denominated in asset `X`, across the entire holder base, are permanently frozen with no recovery path in the protocol.
