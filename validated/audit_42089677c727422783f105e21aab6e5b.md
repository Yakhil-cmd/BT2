This confirms the vulnerability exactly as described. `check_permissions!` only validates that the client has the `read:stack` permission string — it does **not** check which stack the operation is scoped to. That authorization check is entirely delegated to the `stacks`/`stack` scoping helper in `Shipit::Api::BaseController`, which `CCMenuController` bypasses.

### Title
Cross-tenant CCMenu XML disclosure via unscoped `Stack.from_param!` bypassing `current_api_client.stack_id` - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::CCMenuController#stack` resolves the target stack with `Stack.from_param!(params[:stack_id])` instead of the base controller's tenant-scoped `stacks.from_param!`, so a token issued for stack A can be used to fetch deploy status for any other stack B. `check_permissions!` only validates the `read:stack` permission string, not the stack identity, so it does nothing to stop this.

### Finding Description
The intended binding is: `stack the request may read == current_api_client.stack_id` (when the `ApiClient` is stack-scoped). `Shipit::Api::BaseController` implements this correctly: [1](#0-0) 
`stacks` restricts the resolvable set to `Stack.where(id: current_api_client.stack_id)` when the client is stack-scoped, and `stack` calls `stacks.from_param!`, so `from_param!` raises `ActiveRecord::RecordNotFound` for any stack outside that scope.

`CCMenuController` overrides both `authenticate_api_client` (to accept the token via `params[:token]` instead of Basic Auth) and `stack`: [2](#0-1) 
Here `stack` calls `Stack.from_param!` directly on the unscoped `Stack` model, never intersecting with `current_api_client.stack_id`. `require_permission :read, :stack` only calls `current_api_client.check_permissions!('read', 'stack')`, which checks the client's `permissions` array for the string `"read:stack"` — it has no notion of which stack: [3](#0-2) 

Attacker flow: attacker holds a valid CCMenu token for stack A, e.g. obtained from a legitimately shared CI badge URL for their own project (`ApiClient` with `stack_id` = A, `permissions` including `read:stack`). They send `GET /api/stacks/<stack_B_slug_or_id>/ccmenu.xml?token=<A_token>`. `authenticate_api_client` verifies the token signature and sets `current_api_client` to the stack-A client — this succeeds because the token itself carries no stack binding beyond the `ApiClient` record, and nothing re-checks `current_api_client.stack_id` against `params[:stack_id]`. `require_permission!(:read, :stack)` passes because the client does have `read:stack` in `permissions`. `#stack` then resolves stack B unconditionally via `Stack.from_param!`. `#show` renders `stack.deploys_and_rollbacks.last`, exposing stack B's deploy/rollback state to a party who only authenticated for stack A.

No other guard intervenes: `verify_signature`/webhook checks are irrelevant to this API path, `ExplicitParameters` isn't used here, and the `stacks` scope that would normally enforce this binding is simply never invoked by this controller.

### Impact Explanation
Any holder of a stack-scoped CCMenu token can read deploy/rollback status (latest deploy id, status, timestamps) for an arbitrary other stack across tenants, by only changing the `stack_id` in the URL path. This is an unauthenticated (relative to the target stack) cross-tenant read of stack deploy state, repeatable against any stack id/slug in the system with a single GET request. This matches the "High - unauthenticated read of stack state" impact category.

### Likelihood Explanation
Preconditions are minimal and match realistic deployment: any `ApiClient` scoped to a single stack with `read:stack` permission (a common configuration for CCMenu/CI badge integrations) provides a valid token; CCMenu tokens are commonly embedded in public CI badge URLs, which is exactly the kind of value an attacker with access to their own project's badge could have. The attacker needs no session, no operator role, and only sends one HTTP GET with an attacker-controlled `stack_id` path segment. This is trivially repeatable against any number of target stacks.

### Recommendation
In `Shipit::Api::CCMenuController#stack`, resolve the stack through the tenant-scoped `stacks` helper (i.e., use `stacks.from_param!(params[:stack_id])`, mirroring `Shipit::Api::BaseController#stack`) instead of calling `Stack.from_param!` directly on the unscoped model, so stack resolution honors `current_api_client.stack_id`.

### Proof of Concept
```ruby
# test/controllers/shipit/api/ccmenu_controller_test.rb
test "#show does not leak another stack's deploy state to a token scoped to a different stack" do
  stack_a = shipit_stacks(:shipit)
  stack_b = shipit_stacks(:cocaine) # or any second fixture stack, different repo
  client_a = ApiClient.create!(
    creator: shipit_users(:walrus),
    name: 'ccmenu-a',
    stack: stack_a,
    permissions: ['read:stack'],
  )

  # Binding under test: stack the request may read == current_api_client.stack_id
  assert_equal stack_a.id, client_a.stack_id

  get api_stack_ccmenu_url(stack_b, token: client_a.authentication_token, format: :xml)

  # Expect the scoping to be enforced (stack B is NOT in { current_api_client.stack_id })
  assert_response :not_found
  assert_no_match(/#{Regexp.escape(stack_b.deploys_and_rollbacks.last.to_param.to_s)}/, response.body)
end
```
Before the fix this test fails: the request returns `200 OK` with stack B's `deploys_and_rollbacks.last` rendered, even though `client_a.stack_id != stack_b.id`.
