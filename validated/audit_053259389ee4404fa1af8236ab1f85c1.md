## Title
TOCTOU race in private-payment double-spend check allows double-spending a private (hidden) output before stabilization - ([File: private_payment.js])

## Summary
`ocore` validates and stores incoming private (hidden) asset payment chains via `private_payment.js:validateAndSavePrivatePaymentChain()`, which is called concurrently for different chains by `network.js` (`handleOnlinePrivatePayment` and `handleSavedPrivatePayments`, the latter explicitly using `async.each` to "handle different chains in parallel"). Unlike the equivalent flow for regular (public) unit validation, this function acquires **no mutex** before running its read-then-write sequence. Two chains that reference the *same source private output* and are processed concurrently each open an independent DB transaction, each execute the double-spend check against the `inputs` table before either has committed, see no conflicting row, and both successfully commit an `inputs` row with `is_unique=NULL`. Because SQL `UNIQUE` constraints do not consider `NULL` values equal, the `UNIQUE (src_unit, src_message_index, src_output_index, is_unique)` constraint on `inputs` does not prevent this, permitting a genuine double-spend of the same private output. This mirrors the WinPmem bug class: verification is only performed once at routine start, while a concurrent actor can change/consume the checked state mid-routine before the effect is committed.

## Finding Description
`private_payment.js:23-119` (`validateAndSavePrivatePaymentChain`) takes its own DB connection, begins a transaction, performs a "check if duplicate" query against `outputs`, and then dispatches to `divisibleAsset.validateAndSavePrivatePaymentChain` / `indivisibleAsset.validateAndSavePrivatePaymentChain` — all **without acquiring any mutex** across the address/output being spent: [1](#0-0) [2](#0-1) 

Contrast this with the equivalent flow used when *sending* a divisible/indivisible payment from the wallet's own composer, which correctly serializes validate+save with a global mutex before touching validation state: [3](#0-2) 

For divisible private payments, the actual double-spend detection happens inside `validation.js` `checkInputDoubleSpend` → `checkForDoublespends`, which issues a `SELECT ... FROM inputs ... WHERE src_unit=? AND src_message_index=? AND src_output_index=?` to look for a conflicting row: [4](#0-3) 

Only *after* a conflict is actually found does the code take a `mutex.lock(["private_write"])`, i.e. the lock is used to serialize resolution of an already-detected doublespend, not to make the initial "is there a doublespend" read atomic with the later insert: [5](#0-4) 

The insertion of the competing input row sets `is_unique` to `NULL` whenever the private output is not yet stable ("unstable still have chances to become nonserial therefore nonunique"): [6](#0-5) [7](#0-6) 

Since `NULL` values are not considered equal by SQL `UNIQUE` indexes, the schema's uniqueness guarantee against double-spend explicitly documented as `UNIQUE (src_unit, src_message_index, src_output_index, is_unique), -- UNIQUE guarantees there'll be no double spend for type=transfer` does **not** hold when `is_unique` is `NULL`: [8](#0-7) 

Two callers, each processing a distinct private-payment chain that spends the same hidden source output, can run `validateAndSavePrivatePaymentChain` concurrently — network delivery of private payments is explicitly processed in parallel: [9](#0-8) 

Because each invocation opens its own connection/transaction (`db.takeConnectionFromPool` + `BEGIN`) and the doublespend-detection `SELECT` in one transaction cannot see the uncommitted `INSERT` of the other, both transactions pass validation and both `COMMIT`, resulting in two live inputs referencing the same source output.

## Impact Explanation
An attacker who controls (or can quickly interact with) two recipient wallets/devices for the same private asset output can deliver two overlapping private-payment chains to the victim node at (near) the same time. Both are accepted as valid, both mark the hidden output as spent for two different destinations, and there is no subsequent public-DAG mechanism that reconciles this — private payment records are not attached to the ordinary unit-sequence resolution logic that resolves public double-spends at stabilization. This is a direct double-spend of value in a private asset, i.e. unauthorized duplicate spending of funds, which the ruleset explicitly treats as a Medium/High/Critical, in-scope impact ("concrete unauthorized spending, double-spend of a stable output").

## Likelihood Explanation
The race is triggerable by any two unprivileged private-payment senders (or a single attacker controlling both ends of the private chain, e.g. sending the same private output to two devices they control, or exploiting a natural retry/duplicate-delivery scenario) without any special privileges, node compromise, or malicious-peer/hub behavior. It requires only ordinary use of the private-payment feature (chains built from valid signed transfers) with timing such that two `validateAndSavePrivatePaymentChain` calls overlap — a realistic condition given `async.each` explicitly runs multiple pending private chains in parallel, and given that private payments can be forwarded through multiple channels (`hub`, direct peer, `unhandled_private_payments` retry table).

## Recommendation
Serialize `private_payment.js:validateAndSavePrivatePaymentChain` (and the divisible/indivisible variants it calls) per source-output (or globally, similar to the `mutex.lock('handleJoint')` used for outgoing composed payments) so that the read (`checkForDoublespends`) and the corresponding `INSERT INTO inputs` happen atomically with respect to other concurrent private-payment validations referencing the same `(src_unit, src_message_index, src_output_index)`. Alternatively, use a real DB-level lock/transaction isolation (e.g. `SELECT ... FOR UPDATE` where supported, or a single serialized queue keyed by the source output) instead of relying on the `UNIQUE` constraint that is bypassed by `NULL` values of `is_unique`.

## Proof of Concept
1. Create a private divisible/indivisible asset output `O` owned by address `A`.
2. Build two independent private-payment chains `chain1` and `chain2`, both spending `O` as their sole `transfer` input, sending to two different destination addresses `B` and `C`.
3. Deliver `chain1` and `chain2` to a full node concurrently (e.g., via two simultaneous `handleOnlinePrivatePayment` network deliveries, or by queuing both into `unhandled_private_payments` so `handleSavedPrivatePayments`'s `async.each` processes them together).
4. Because `output_index`/`src_output` referenced by `O` is not yet stable, `is_unique` is inserted as `NULL` for both `inputs` rows in `divisible_asset.js`/`indivisible_asset.js`, and the `checkForDoublespends` SELECT in each transaction runs before the other's INSERT commits, both `validateAndSavePrivatePaymentChain` calls succeed, and the same output `O` is now recorded as spent to both `B` and `C`.
