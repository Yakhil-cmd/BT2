### Title
Hookify PreToolUse hook fails open on any exception, allowing an attacker to bypass configured `block` rules by triggering an internal error (e.g., regex evaluation failure) - ([File: plugins/hookify/hooks/pretooluse.py])

### Summary
The Solidity report describes a caller controlling execution resources (gas) so that a safety mechanism (callback) silently fails while the surrounding transaction still succeeds, breaking the intended atomicity between action and safety check. The structural analog here is the `hookify` plugin's `PreToolUse` hook, which is the mechanism used to `block` dangerous tool calls (e.g., `rm -rf`, writes to `.env` files). Its executor is explicitly designed to always allow the operation whenever rule evaluation throws any exception, regardless of what the (potentially malicious) rule matching logic was trying to block.

### Finding Description
`plugins/hookify/hooks/pretooluse.py` is the single `PreToolUse` gate that evaluates user-defined blocking rules against every `Bash`/`Edit`/`Write`/`MultiEdit` tool call: [1](#0-0) 

The `main()` function wraps rule evaluation in a broad `try/except`, and its `finally` block unconditionally calls `sys.exit(0)`: [2](#0-1) 

`RuleEngine.evaluate_rules` (called from `main()`) compiles and executes user-supplied regex patterns against tool input via `compile_regex`/`re.search` with no bounds on complexity or execution time: [3](#0-2) [4](#0-3) 

Because any exception during evaluation (or the overall command-hook timeout being exceeded and the process killed) results in the same outcome as "no rules matched" — the operation is allowed — an attacker (or an adversarial prompt/tool input) that can influence the `tool_input` (e.g., the exact Bash command string or file content being written) being matched against a `block`-configured rule pattern can craft a specific string that triggers catastrophic backtracking (ReDoS) in the rule's regex, or otherwise raises an exception during evaluation. This causes the hook to fail without ever emitting the `deny`/`permissionDecision` output, and the underlying dangerous tool call (`rm -rf`, writing secrets, etc.) proceeds exactly as if no blocking rule existed.

This mirrors the Sablier bug precisely: the entity that controls the resource budget/input to the "callback"-equivalent (the validation hook) can deliberately starve/crash it, while the outer operation (the tool call) still completes successfully because the surrounding harness treats hook failure as non-fatal.

### Impact Explanation
A user (or content injected into a repository that Claude Code operates on, since `tool_input` can be influenced by file contents Claude reads and echoes back into commands) can defeat security-critical `block` rules configured via `/hookify` (e.g., rules meant to prevent destructive `rm -rf`, credential exfiltration, or edits to sensitive files) simply by causing the rule engine to error out on a crafted match target. This breaks the intended safety guarantee of the `block` action, allowing unauthorized destructive shell commands or file writes to execute unblocked — a direct local workspace compromise via hook bypass, matching the "unauthorized shell/file action" and "hook bypass" categories.

### Likelihood Explanation
Likelihood is moderate: it requires (1) a project with an active `hookify` `block` rule using a regex pattern, and (2) an ability to supply/influence a string matched against that pattern that induces catastrophic backtracking or another runtime exception in `re.search`/`RuleEngine`. Since `hookify` explicitly documents user-defined regex patterns as its rule mechanism (`plugins/hookify/README.md`), and patterns are compiled from arbitrary Markdown frontmatter files without complexity limits, constructing a ReDoS-triggering input against a plausible user pattern (e.g., nested quantifiers combined with attacker-controlled command text) is a known, practical technique.

### Recommendation
- In `plugins/hookify/hooks/pretooluse.py`, do not fail open (`exit 0`) on unexpected exceptions when a `block`-type rule was in scope for the event; instead fail closed (emit a `deny`/`ask` decision) or clearly surface the internal error as a blocking condition so the operation does not silently proceed.
- In `plugins/hookify/core/rule_engine.py`, bound regex evaluation time (e.g., run `re.search` with a timeout via a subprocess/signal-based guard, or use a regex engine with linear-time guarantees) to prevent ReDoS-induced hook timeouts.
- Add regression tests that specifically simulate rule-evaluation exceptions/timeouts under an active `block` rule to confirm the system defaults to deny, not allow.

### Proof of Concept
1. Create `.claude/hookify.dangerous-rm.local.md` with a `block` rule for `event: bash` using a regex vulnerable to catastrophic backtracking, e.g. `pattern: (a+)+b` (per the documented pattern syntax in `plugins/hookify/README.md`).
2. Have Claude issue a `Bash` tool call whose `tool_input.command` contains a long string of `a` characters without a trailing `b` (e.g., `echo "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa!"; rm -rf /tmp/target`).
3. `RuleEngine._rule_matches` invokes `re.search` on the compiled pattern against the command string; the exponential backtracking causes the match to run far longer than the hook's configured timeout (default 60s for command hooks), the process is killed, and/or an exception path is hit.
4. Per `pretooluse.py`'s `finally: sys.exit(0)` (and the harness's presumed non-fatal treatment of hook subprocess failures), the `PreToolUse` hook exits without a `deny` decision, and the `rm -rf` command executes unblocked despite the configured `block` rule.

Note: I was unable to directly verify, within the available index, the exact runtime behavior of the outer Claude Code harness when a *command hook itself* times out (i.e., whether it always fail-opens or sometimes fail-closes) — this determination happens in the CLI's core hook-execution code, which is not part of this plugin repository content, so this aspect carries residual uncertainty. The `pretooluse.py`-level fail-open on caught exceptions, however, is directly confirmed in source.

```python
def main():
    """Main entry point for PreToolUse hook."""
    try:
        # Read input from stdin
        input_data = json.load(sys.stdin)

        # Determine event type for filtering
        # For PreToolUse, we use tool_name to determine "bash" vs "file" event
        tool_name = input_data.get('tool_name', '')

        event = None
        if tool_name == 'Bash':
            event = 'bash'
        elif tool_name in ['Edit', 'Write', 'MultiEdit']:
            event = 'file'

        # Load rules
        rules = load_rules(event=event)

        # Evaluate rules
        engine = RuleEngine()
        result = engine.evaluate_rules(rules, input_data)

        # Always output JSON (even if empty)
        print(json.dumps(result), file=sys.stdout)

    except Exception as e:
        # On any error, allow the operation and log
        error_output = {
            "systemMessage": f"Hookify error: {str(e)}"
        }
        print(json.dumps(error_output), file=sys.stdout)

    finally:
        # ALWAYS exit 0 - never block operations due to hook errors
        sys.exit(0)
```

```python
    Args:
        pattern: Regex pattern string

    Returns:
        Compiled regex pattern
    """
```

```python
    def evaluate_rules(self, rules: List[Rule], input_data: Dict[str, Any]) -> Dict[str, Any]:
        """Evaluate all rules and return combined results.

        Checks all rules and accumulates matches. Blocking rules take priority
        over warning rules. All matching rule messages are combined.

        Args:
            rules: List of Rule objects to evaluate
            input_data: Hook input JSON (tool_name, tool_input, etc.)

        Returns:
            Response dict with systemMessage, hookSpecificOutput, etc.
            Empty dict {} if no rules match.
        """
        hook_event = input_data.get('hook_event_name', '')
        blocking_rules = []
        warning_rules = []

        for rule in rules:
            if self._rule_matches(rule, input_data):
                if rule.action == 'block':
                    blocking_rules.append(rule)
                else:
                    warning_rules.append(rule)
```
