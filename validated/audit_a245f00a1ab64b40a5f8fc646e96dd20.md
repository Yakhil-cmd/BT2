### Title
Webhook signature verification org is decoupled from the repository the handler actually mutates - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and thus which `webhook_secret`) to validate a webhook against using `repository_owner`, which reads `params.dig('repository','owner','login')` and falls back to `params.dig('organization','login')` if that key is absent. [1](#0-0)  The `pull_request.closed` handler, however, resolves the repository/stack to mutate exclusively from `params.repository.full_name`, a field the attacker fully controls and which is never cross-checked against the value used for signature verification. [2](#0-1)  Because `Shipit.github(organization:)` looks up a per-organization config (own `webhook_secret`, own `bot_login`) in multi-tenant deployments, an attacker who legitimately controls one onboarded organization (and thus knows/can compute a valid HMAC with that organization's own `webhook_secret`) can sign a payload whose `repository.full_name` names an entirely different, victim organization/repo. [3](#0-2) 

### Finding Description
The broken binding, stated as an equality that the code implicitly assumes but never enforces:

`organization_used_for_signature_verification (repository_owner) == owner_of(params.repository.full_name)`

This equality is never checked anywhere in the request path. `verify_signature` computes:
```
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [4](#0-3) 
`repository_owner` is derived independently of `repository.full_name`:
```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [5](#0-4) 

`GitHubApp#verify_webhook_signature` validates the HMAC of the *entire raw body* against the `webhook_secret` configured for whichever organization was selected — it has no notion of "this signature is only valid for repository X":
```
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
  SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
end
``` [6](#0-5) 

Downstream, `ClosedHandler` (and its sibling PR handlers) resolve the actually-affected `Repository`/`ReviewStack` purely from `params.repository.full_name`:
```
def repository
  @repository ||=
    Shipit::Repository.from_github_repo_name(params.repository.full_name) ||
    Shipit::NullRepository.new
end
``` [2](#0-1) 

Exploit flow, in a multi-tenant Shipit deployment (evidenced by `secrets_double_github_app.yml` showing multiple org keys under `github:`, each with its own `webhook_secret`, `bot_login`, `app_id`): [7](#0-6) 
1. Attacker legitimately owns/administers `AttackerOrg`, an org onboarded into this Shipit instance, and knows `AttackerOrg`'s `webhook_secret` (they configured it, or it is blank/lenient).
2. Attacker crafts a `pull_request` JSON body with `action: "closed"`, `repository: { full_name: "VictimOrg/victim-repo" }` (satisfying the handler's `ExplicitParameters` schema, which only requires `full_name`, not `owner`), and either `repository.owner.login: "AttackerOrg"` or omits `owner` and sets `organization.login: "AttackerOrg"`.
3. `repository_owner` resolves to `AttackerOrg`; `Shipit.github(organization: "AttackerOrg")` returns the attacker's own tenant's `GitHubApp`, using a secret the attacker knows.
4. `verify_webhook_signature` succeeds using that known secret over the full attacker-crafted body (HMAC covers the raw bytes, not a specific field), so the request passes.
5. `Shipit::Webhooks.for_event('pull_request')` dispatches to `ClosedHandler`, which resolves `Shipit::Repository.from_github_repo_name("VictimOrg/victim-repo")` — an entirely different tenant's repository — and calls `review_stack.archive!` on the `ReviewStack` bound to the attacker-chosen PR number in that victim repo. [8](#0-7) 
6. Because the victim stack has `bot_login` configured (`Shipit.user`), any auto-triggered downstream actions (e.g., re-deploys, merges triggered by other PR handlers reachable via the same signature-laundering path) execute as that configured bot identity against the victim's real GitHub repository.

Existing guards do not close this gap: `verify_signature` only prevents *unsigned/unrecognized* requests from being processed at all — it does not bind the verified signature to the specific repository named in `params.repository.full_name`; `drop_unhandled_event` only filters unknown event types; the `ExplicitParameters` schema for `ClosedHandler` requires `repository.full_name` but not `repository.owner`, so the fallback path is reachable; and there is no code anywhere that asserts `repository_owner == repository.full_name.split('/').first`.

### Impact Explanation
An attacker who is an unprivileged GitHub user with respect to the victim org, but who legitimately administers or has onboarded any organization/tenant on the same multi-tenant Shipit instance, can forge signed `pull_request` webhooks that operate on a completely unrelated victim organization's repository/stack. For the `closed` event this results in an unauthorized `ReviewStack#archive!` against a victim's `ReviewStack`; for other `pull_request` sub-handlers reachable via the identical signature-laundering technique (e.g. `opened`, `labeled`, `reopened`), this generalizes to unauthorized creation, labeling, or state transitions of stacks that trigger auto-deploys running as the victim's configured `Shipit.user`/bot identity — matching "a payload for one repository mutating another's stack, commit, task or team" (Critical). The blast radius spans every tenant/org configured in the same Shipit installation's `secrets.github` map.

### Likelihood Explanation
This requires a multi-organization Shipit deployment (`secrets.github` keyed by multiple org names, as shown in `secrets_double_github_app.yml`) where the attacker controls at least one onboarded org and its `webhook_secret`. Given that, the attack costs a single crafted HTTP POST with a valid HMAC computed from a secret the attacker legitimately possesses — no GitHub session, no privileged Shipit role, and no cross-org secret knowledge is needed. It is fully repeatable against any victim repository name the attacker chooses to put in `repository.full_name`, and works even without relying on the `organization.login` fallback (setting `repository.owner.login` to the attacker's own org name while spoofing `repository.full_name` also works), making the fallback path an aggravating but not the sole vector.

### Recommendation
In `WebhooksController#verify_signature`, after selecting `repository_owner` and successfully verifying the signature, additionally enforce that the organization/owner derived from `params.repository.full_name` (or `params.repository.owner.login`) matches the `repository_owner` used to pick the verifying secret, rejecting the request (422) on mismatch. More robustly, verify the signature against every configured organization's secret whose name textually matches the owner segment of `repository.full_name`, rather than trusting a caller-suppliable `organization.login` fallback field to select the verifying tenant.

### Proof of Concept
minitest plan (`test/controllers/webhooks_controller_test.rb`):
```ruby
test "pull_request closed for a different org's repo verified with attacker's own org secret" do
  attacker_org = 'AttackerOrg'
  victim_full_name = 'VictimOrg/victim-repo'
  # victim_stack has bot_login configured and an open ReviewStack bound to PR #7

  payload = {
    action: 'closed',
    number: 7,
    pull_request: { id: 1, number: 7, url: 'https://x', title: 't', state: 'closed',
                     additions: 1, deletions: 1,
                     head: { sha: 'abc', ref: 'pr-7' },
                     user: { login: 'attacker' }, assignees: [], labels: [] },
    repository: { full_name: victim_full_name }, # note: no owner.login
    organization: { login: attacker_org },        # attacker's own org
    sender: { login: 'attacker' }
  }.to_json

  signature = "sha1=#{OpenSSL::HMAC.hexdigest('sha1', attacker_org_webhook_secret, payload)}"

  assert_equal attacker_org, JSON.parse(payload).dig('organization', 'login')
  refute_equal attacker_org, victim_full_name.split('/').first # binding is broken: verifier org != mutated repo owner

  @request.headers['X-Github-Event'] = 'pull_request'
  @request.headers['X-Hub-Signature'] = signature

  assert_difference -> { victim_review_stack.reload.status }, from: 'open', to: 'archived' do
    post :create, body: payload, as: :json
  end
  assert_response :ok
end
```
This proves the verifying identity (`attacker_org`, via `repository_owner`) diverges from the mutated repository's real owner (`VictimOrg`), yet the request is accepted and the victim's `ReviewStack` is archived.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
