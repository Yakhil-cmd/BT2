## Analog Found: Premature stream destroy + duplicate completion handling in `data_feeds.js`

CVE-2018-12882's root cause is that `exif_read_from_impl` destroys/closes a resource (a stream) that it does not fully own the lifecycle of, leaving a dangling reference that later gets used again, causing a crash. The closest analog in this codebase is in `dataFeedByAddressExists()` in `data_feeds.js`, which destroys a `kvstore` read stream while it may still be delivering buffered `'data'`/`'end'` events, and guards against re-entrant completion by throwing an uncaught `Error`. [1](#0-0) 

### Title
Premature stream destruction in `in_data_feed`/`data_feed` evaluation can trigger an uncaught "second call of onEnd" crash - (File: data_feeds.js)

### Summary
`dataFeedByAddressExists()` opens a `kvstore.createKeyStream()` over the `df\n<address>\n<feed_name>...` key range to answer `data_feed`/`in_data_feed` oscript/AA-formula queries. When a matching record is found for relational operators (`>`, `>=`, `<`, `<=`), the code calls `stream.destroy()` and then synchronously invokes `onEnd()` itself, instead of letting the stream's natural `'end'` event drive completion. `onEnd()` is guarded with `if (bOnEndCalled) throw Error("second call of onEnd")`, indicating the authors anticipated the underlying stream could still emit a completion event after `destroy()` was called. [2](#0-1) 

### Finding Description
The stream is destroyed by code that does not fully control (and cannot synchronously guarantee) the stream's subsequent event emissions — mirroring the PHP EXIF bug's root cause of closing a stream whose closing responsibility/lifecycle isn't fully owned by the caller. If the underlying rocksdb/leveldb key-stream implementation has already buffered/batched multiple key entries and emits them in the same synchronous pass (a common pattern in `abstract-leveldown`/`level-rocksdb` read-stream implementations, which prefetch batches and drain them via `nextTick`/synchronous loops), the manual `stream.destroy(); onEnd();` call can race with an already-scheduled `'end'` event for that batch. When both fire, `onEnd()` is invoked twice, hitting the explicit `throw Error("second call of onEnd")` guard.

This is reachable via `in_data_feed[[...]]` (and `data_feed[[...]]`) oscript expressions, which can appear in:
- address definitions validated via `formula` authentifiers (`definition.js`), reachable by any unit poster whose address uses such a definition,
- AA formulas evaluated on every AA trigger (`formula/evaluation.js`, case `'data_feed'`/`'in_data_feed'`), reachable by any AA trigger sender. [3](#0-2) [4](#0-3) 

An oracle address (which can be any address, including one controlled by the attacker) posts multiple `data_feed` messages for the same `feed_name` that fall inside the queried mci range and satisfy the relational operator, so that the key-range scan for that feed contains 2+ matching entries. A subsequent unit/AA trigger evaluates `in_data_feed[[oracles=..., feed_name=..., feed_value > X, min_mci=...]]` (or `data_feed` with a non-`=` implicit scan path) against that oracle/feed. The internal key-stream drains multiple qualifying keys in one batch; the first match triggers `stream.destroy()` + synchronous `onEnd()`, and if the stream's own `'end'` (or a queued `'data'` leading to a second `onEnd` invocation window) still fires afterward, the guard throws an uncaught `Error`.

### Impact Explanation
An uncaught `Error` thrown from inside the stream's event-handling flow is not caught anywhere up this call chain (the surrounding validation/AA-trigger flow does not wrap formula evaluation in a `try/catch` that survives such throws; the codebase relies on fail-fast throws for invariant violations elsewhere in this same file, e.g. `throw Error('error from data stream: ...')`). Since every full node (including witnesses/hubs) independently validates units and executes AA triggers, and `in_data_feed`/`data_feed` evaluation is a normal, reachable, unprivileged path for any unit author or AA trigger sender, a crafted sequence of data-feed posts plus a triggering unit/AA can crash all full nodes that process that unit — a network-wide denial of validation/consensus availability ("network unable to confirm new units"), which meets the accepted impact bar.

### Likelihood Explanation
Reaching this code path requires only:
1. Posting several `data_feed` messages from one address for the same `feed_name`, spanning multiple values/mcis, which is unprivileged and permitted by protocol.
2. Posting a unit (via a `formula` authentifier) or an AA trigger that evaluates `in_data_feed`/`data_feed` with a relational operator against that oracle/feed with an mci range that matches multiple entries.

The actual race depends on internal batching behavior of the underlying leveldown/rocksdb stream implementation (whether multiple `'data'` events for a batch are drained before a `destroy()` call is honored), which is implementation/version-dependent and not something this analysis can fully confirm without running the exact stream library version. This tempers likelihood from "trivial" to "plausible/version-dependent," but the explicit defensive throw for exactly this scenario strongly suggests the double-completion case is a real, reachable condition.

### Recommendation
- In `dataFeedByAddressExists()`, do not call `onEnd()` synchronously after `stream.destroy()`; instead, let stream teardown be idempotent — e.g., track completion once via a dedicated flag checked at the very top of every event handler (`'data'`, `'end'`, `'close'`, `'error'`) and simply `return` if already completed, rather than throwing.
- Prefer listening for `'close'` after `destroy()` to signal true stream teardown before calling `handleResult`, instead of manually invoking the completion callback while the stream may still be flushing buffered events.
- Replace the `throw Error("second call of onEnd")` guard with a silent no-op guard, since a defensive invariant check should not be allowed to crash unprivileged validation/AA-execution paths driven by attacker-controlled data feeds.

### Proof of Concept
1. From address `A`, post several `data_feed` units for `feed_name = "f"` with increasing numeric values/mcis such that at least two entries fall within a queryable mci window (e.g., values `10` at mci `100` and `20` at mci `101`).
2. From any address (or an AA), post a unit/trigger with an oscript/AA formula such as:
   `in_data_feed[[oracles="A", feed_name="f", feed_value > 5, min_mci=90]]`
3. During validation, `dataFeedExists` → `dataFeedByAddressExists` opens a `kvstore.createKeyStream()` over the matching key range containing both entries.
4. If the underlying stream delivers both matching keys in the same synchronous/batched dispatch before honoring `destroy()`, the first match sets `bFound = true`, calls `stream.destroy()` and `onEnd()`; the stream's own completion event fires afterward, invoking `onEnd()` a second time and hitting `throw Error("second call of onEnd")`, crashing the node process handling this unit's validation/AA execution.
