### Title
`OpenedHandler#provision?` operator-precedence bug lets a PR label bypass `review_stacks_enabled` and auto-provision review stacks - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`Repository#provisioning_behavior_allow_all?`, `#provisioning_behavior_allow_with_label?`, and `#provisioning_behavior_prevent_with_label?` are plain Rails `enum` predicate methods generated from the `provisioning_behavior` column; they read only that column and carry no dependency on `review_stacks_enabled` whatsoever. Because of that orthogonality, `OpenedHandler#provision?`'s `&&`/`||` expression only ANDs `review_stacks_enabled` with the `allow_all?` branch, leaving the `allow_with_label?` and `prevent_with_label?` branches ungated, so a repository with `review_stacks_enabled: false` still auto-provisions a review stack whenever the incoming pull request satisfies the label condition.

### Finding Description
Binding checked: `review_stacks_enabled == true` must be an independent precondition ANDed into every branch of the provisioning decision. Confirmed broken: [1](#0-0) defines `provisioning_behavior` as a Rails `enum`, and its three generated predicates return purely the enum value with no reference to `review_stacks_enabled` [2](#0-1)  (the `NullRepository` stand-in makes the same independence explicit). Therefore any caller must independently AND each predicate with `review_stacks_enabled`.

`OpenedHandler#provision?` fails to do this due to Ruby operator precedence (`&&` binds tighter than `||`): [3](#0-2) 

This parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label) || (prevent_with_label? && !has_label)`. Only the `allow_all?` term is gated by `review_stacks_enabled`; the `allow_with_label?` and `prevent_with_label?` terms are not.

Attack: an unprivileged GitHub user opens a pull request against a repository whose Shipit configuration has `review_stacks_enabled: false` but `provisioning_behavior: allow_with_label` (or `prevent_with_label`) configured from an earlier/legacy setup, and applies (or omits) the matching label on their own PR. `provision?` returns `true` even though review stacks were explicitly disabled for that repository, causing `ReviewStackAdapter#find_or_create!` to create and provision a live review stack for that PR.

No existing guard stops this: `params` schema validation, `drop_unhandled_event`, and webhook signature verification only ensure the payload shape and origin are legitimate — they do not enforce the intended `review_stacks_enabled && behavior` semantics, which is a pure logic bug in the handler's boolean expression.

I also observed `ReopenedHandler#unarchive?` contains the byte-for-byte identical grouping [4](#0-3) , so the same bypass is not strictly isolated to `provision?` as the question's binding assumes — it also affects `ReopenedHandler`. `LabeledHandler`/`UnlabeledHandler` are safe because they factor `repository.review_stacks_enabled` outside as a top-level AND over `(archive? || unarchive?)` in `respond_to_label_change?` [5](#0-4) , rather than embedding it inside one disjunct.

### Impact Explanation
An attacker who can merely open (or reopen) a pull request against any tracked repository can force Shipit to create and provision a review stack for a repository/environment that the operator explicitly disabled review stacks for (`review_stacks_enabled: false`), as long as that repository's `provisioning_behavior` is `allow_with_label` or `prevent_with_label`. Review-stack provisioning runs deployment tasks against that repository's branch, so this is an unauthorized deploy trigger — matching the Critical "unauthorized deploy" category. It is repeatable against any repository matching the misconfiguration precondition below, though not against arbitrary repositories unconditionally.

### Likelihood Explanation
This requires a specific repository configuration precondition: `review_stacks_enabled: false` combined with `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` (rather than the default `allow_all`, which is fully gated). This is a plausible configuration (e.g., an operator temporarily disabling review stacks while leaving the behavior selector at its prior value), but it is not the default state of a freshly created repository. Given the precondition holds, the attacker cost is trivial — opening/labeling a PR requires no privileges beyond standard GitHub PR access to the repository.

### Recommendation
Fix the boolean grouping in `OpenedHandler#provision?` (and identically in `ReopenedHandler#unarchive?`) so `review_stacks_enabled` gates all three branches, e.g.:
```ruby
def provision?
  repository.review_stacks_enabled && (
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
  )
end
```

### Proof of Concept
```ruby
# test/models/shipit/repository_test.rb (conceptual addition)
test "provisioning_behavior_allow_with_label? is independent of review_stacks_enabled" do
  repository = shipit_repositories(:shipit)
  repository.update!(review_stacks_enabled: false, provisioning_behavior: :allow_with_label)

  assert repository.provisioning_behavior_allow_with_label?
  refute repository.review_stacks_enabled
end

# test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb (conceptual addition)
test "bypasses review_stacks_enabled=false when allow_with_label and label present" do
  repository = shipit_repositories(:shipit)
  repository.update!(review_stacks_enabled: false, provisioning_behavior: :allow_with_label, provisioning_label_name: "pull-requests-label")

  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  assert_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
