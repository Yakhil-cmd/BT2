### Title
AA funds are permanently frozen when private-asset payments are sent to an AA address, because private outputs never create an `aa_triggers` entry - (File: `main_chain.js`)

### Summary
`handleAATriggers()` in `main_chain.js` only inserts an `aa_triggers` row for a stable unit's outputs to an AA address when the output's asset is `base` or a *public* asset (`outputs.asset IS NULL OR is_private=0`). Private (indivisible/hidden) asset outputs sent to an AA address are silently excluded from this trigger-creation logic, exactly analogous to the ZetaChain issue where specific code paths that legitimately move value never emit/process the corresponding log/event needed to complete the operation.

### Finding Description
The trigger-selection query in `handleAATriggers()` explicitly restricts eligible outputs with `AND (outputs.asset IS NULL OR is_private=0)` [1](#0-0) . This means that when a regular user posts a unit containing a private-asset payment whose output address is an AA, that unit's stabilization never inserts a corresponding row into `aa_triggers`, and therefore `handleAATriggers()`/`handleTrigger()` (in `aa_composer.js`) is never called for that unit and AA [5](#0-4) . Nonetheless, the private output is a legitimate, spendable output belonging to the AA address once it becomes part of a proven private-payment chain (validated the same way as regular payments via `validatePayment()` in `validation.js`) [6](#0-5) . Because the AA is never triggered, its internal accounting (`aa_balances`) is never credited for that private output — confirmed by the balance-seeding query in `storage.insertAADefinitions()` and the consistency-check query in `aa_composer.checkBalances()`, both of which deliberately exclude private outputs (`AND (is_private=0 OR is_private IS NULL)`) [7](#0-6) [8](#0-7) . Additionally, even if an AA were somehow triggered and tried to forward such funds onward, `sendUnit()` explicitly bounces any attempt to pay out a private asset from an AA with the error `"sending private asset from AA"` [9](#0-8) . The combination means the private output sitting at the AA address is neither reflected in the AA's balance nor forwardable by AA logic — it is permanently stuck, unspendable by anyone (the AA has no private keys and its bytecode cannot spend private assets), and un-refundable to the sender because the AA never even "sees" the trigger to bounce it back.

### Impact Explanation
Any unprivileged unit poster who sends a private-asset payment to an existing AA address permanently loses those funds: the value is transferred out of the sender's control by a validly-stabilized unit, but never becomes usable balance for the destination AA and can never be recovered, since the AA has no private key and its bytecode is barred from re-sending private assets. This constitutes a concrete case of asset loss with no path to recovery — funds are neither spendable by the AA nor returned to the sender, differing from the normal AA flow where insufficient bounce fees or unrecognized messages still trigger the AA and produce a bounce/refund.

### Likelihood Explanation
This requires no attacker cooperation or privileged access — any wallet user can compose and send a private (indivisible) asset payment to an AA address using standard wallet functionality, since nothing in the payment-composition or validation path (`validatePayment`, `divisible_asset.js`/`indivisible_asset.js`) prevents targeting an AA address with a private-asset output. The condition is purely a consequence of normal usage/misconfiguration (mistakenly or intentionally sending a private asset to an AA), making the likelihood of triggering the bug class high, though the impact is confined to whichever assets/amounts are actually sent this way.

### Recommendation
Either (a) reject/bounce private-asset payments destined for AA addresses at validation time (so senders get clear, immediate feedback and the funds are never actually transferred), or (b) extend `handleAATriggers()` to also create `aa_triggers` entries for private-asset outputs once their private-payment chain is proven/stable, and correspondingly update `aa_balances` accounting (`insertAADefinitions`, `checkBalances`) to include such outputs, giving the AA logic (and its bounce mechanism) a chance to actually process and, if necessary, refund the funds.

### Proof of Concept
1. Deploy any autonomous agent AA at address `AA_ADDR`.
2. Issue a private (indivisible) asset and compose a private payment whose sole output sends units of that asset to `AA_ADDR`, following the standard private-payment flow (`indivisible_asset.js` / `private_payment.js`).
3. Post and stabilize the unit; validation succeeds because `validatePayment()` does not special-case AA destinations for private assets [6](#0-5) .
4. Observe that `handleAATriggers()`'s SQL selecting rows for `aa_triggers` excludes this output because `is_private=1`, so no trigger row is inserted and the AA's `handleTrigger()` never runs for this unit [1](#0-0) .
5. Query `aa_balances` for `AA_ADDR`/that asset — it is not credited, matching the exclusion filters used elsewhere (`storage.insertAADefinitions`, `checkBalances`) [3](#0-2) [10](#0-9) .
6. The private-asset units are now permanently stuck at `AA_ADDR`: the AA has no key to spend them directly, and even a manually-triggered AA response attempting to forward that asset is rejected with `"sending private asset from AA"` [4](#0-3) .
