### Title
Unbounded response body reads in `CallAskPassURL` / `RefreshGitHubAppToken` / `Webhook.Do` allow memory-exhaustion DoS of git-sync - (File: main.go, pkg/hook/webhook.go)

### Summary
Like the `eth_getLogs` bug where `FilterCriteria.Addresses` was read and processed without any upper bound, git-sync reads several HTTP response bodies with `io.ReadAll(resp.Body)` and no size limit (`http.MaxBytesReader`/`io.LimitReader`) before parsing them. Any of these HTTP endpoints (`--askpass-url`, GitHub App token endpoint, `--webhook-url`) that is compromised, misconfigured, or spoofed (e.g. via DNS/network-level interception, or a malicious response from a supposedly-trusted internal service) can return an arbitrarily large body, driving unbounded memory allocation on every sync cycle and causing a persistent denial-of-service of the git-sync sidecar.

### Finding Description
`repoSync.CallAskPassURL` performs an HTTP GET to the operator-configured `--askpass-url` / `$GITSYNC_ASKPASS_URL` on every credential refresh (i.e., every sync attempt) and reads the full response body unconditionally: [1](#0-0) 

Both the error path (`resp.StatusCode != http.StatusOK`) and success path call `io.ReadAll(resp.Body)` with no size cap, then the success-path body is converted to a `string` and split line-by-line with `strings.SplitSeq(string(authData), "\n")`. There is no `http.MaxBytesReader`, `io.LimitReader`, or content-length check anywhere in `main.go` (confirmed via search — no `MaxBytesReader`/`LimitReader` usage exists in the file), so a multi-gigabyte response is fully buffered into memory and then duplicated again during the `string()` conversion and `SplitSeq` iteration.

`refreshCreds` is invoked on every sync loop iteration when `--askpass-url` is set: [2](#0-1) 

The same unbounded pattern exists in `RefreshGitHubAppToken`, which reads the GitHub App token-exchange response (error path via `io.ReadAll`, success path via `json.NewDecoder(resp.Body).Decode`, both unbounded): [3](#0-2) 

And in `Webhook.Do`, which reads the webhook response body unbounded after every successful sync: [4](#0-3) 

### Impact Explanation
Because `CallAskPassURL` runs on every sync attempt (default `--period` 10s), and `Webhook.Do` runs after every publish, an attacker who can influence the response from any of these endpoints (compromised askpass service, DNS hijack, on-path attacker for plaintext HTTP as explicitly warned about in `docs/askpass-url.md`, or a malicious/compromised GitHub-compatible endpoint when `--github-base-url` is attacker-influenced) can force git-sync to repeatedly allocate unbounded memory. This can OOM-kill the git-sync sidecar container, causing persistent sync denial for the pod that depends on it — matching the accepted impact class of "persistent sync denial." Unlike the original minievm finding (a public unauthenticated RPC), here the trigger requires control of a response from a git-sync-configured endpoint, which is a lower-privilege bar than a full remote-code-execution vector but still an unprivileged network-response-based DoS given git-sync's own documentation acknowledges these channels can carry attacker-influenced content (e.g. "credentials will pass in plain text").

### Likelihood Explanation
Requires the attacker to control or intercept traffic to the configured `--askpass-url`, GitHub token endpoint, or `--webhook-url`. `docs/askpass-url.md` explicitly warns that the connection must be kept secure because credentials pass in plaintext, implying the threat model already includes network-level attackers on this path. Given periodic (default every 10s) unauthenticated-size GET/POST calls, exploitation is trivial once such a position is achieved, and the failure repeats on every sync cycle without a `--max-failures` limit stopping it (each call fails/succeeds independently of memory pressure until OOM).

### Recommendation
Wrap all external response bodies with a bounded reader before use, e.g. `io.LimitReader(resp.Body, maxAskpassRespBytes)` in `CallAskPassURL`, `io.LimitReader(resp.Body, maxTokenRespBytes)` in `RefreshGitHubAppToken`, and similarly in `Webhook.Do`. Choose small, sane limits (askpass responses are a handful of `key=value` lines; GitHub token responses and webhook acknowledgements are small JSON documents), and treat truncation/overflow as an error rather than silently processing partial data.

### Proof of Concept
1. Configure git-sync with `--askpass-url=http://attacker-controlled/askpass`.
2. Have the attacker-controlled endpoint stream several GB of arbitrary bytes (e.g. `while true; do echo -n a; done` behind a slow-loris style or simple large fixed body) as the HTTP response with status 200.
3. On the next `refreshCreds` cycle, `CallAskPassURL` calls `io.ReadAll(resp.Body)` [5](#0-4)  which will buffer the entire response into memory, repeating every `--period` interval and eventually exhausting the container's memory limit, killing the git-sync process (or the whole pod under a shared cgroup), producing persistent sync denial.
