Based on my research, there's a genuine analog to the described bug class in `near-wallet-contract`, nearcore's Ethereum-emulation wallet contract that is globally deployed for ETH-implicit accounts.

### Title
Hard-coded fixed gas margins for wallet-contract callbacks can permanently brick the wallet (`has_in_flight_tx` never resets) - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
`WalletContract` (the ETH-emulation contract deployed globally for eth-implicit accounts) uses small, hard-coded static gas constants to bound the callback that finalizes every `rlp_execute` transaction. If the callback runs out of that fixed gas budget, the entire receipt is rolled back atomically by the runtime, including the write that clears the `has_in_flight_tx` guard, permanently locking the wallet out of processing any future transaction — an analog of the "hard-coded gas amount forwarded to a call" class of bug described in the report, but with an unrecoverable outcome instead of a retryable one.

### Finding Description
`WalletContract::rlp_execute` sets `self.has_in_flight_tx = true` before returning a promise, and only `address_check_callback`, `nep_141_storage_balance_callback`, and `rlp_execute_callback` ever reset it back to `false`, each doing so as their first statement: [1](#0-0) [2](#0-1) 

These callbacks are attached with fixed, small gas budgets defined as constants: [3](#0-2) 

Notably, `ADDRESS_CHECK_CALLBACK_GAS` and `NEP_141_STORAGE_BALANCE_CALLBACK_GAS` only add a fixed extra 5–10 Tgas margin on top of the user-supplied `action.gas()` to cover the callback's own logic (JSON (de)serialization of the promise result, string formatting, and promise creation): [4](#0-3) 

The `target`/token account for `ERC20Transfer` (and the registrar interaction for `EOABaseTokenTransfer`) is attacker/relayer-influenced input to `rlp_execute`, so the size and cost of the cross-contract call's response (e.g. a `storage_balance_of` or `lookup` JSON payload) is not fully controlled by the wallet owner. If that response is large enough that deserializing it inside the callback (`nep_141_storage_balance_callback` / `address_check_callback`) exceeds the fixed 5–10 Tgas margin, the callback fails with `GasExceeded`.

Crucially, nearcore treats a failed action receipt as fully rolled back: `runtime/runtime/src/lib.rs` commits state changes only when the receipt result is `Ok`, and calls `state_update.rollback()` on any error: [5](#0-4) 

This is also documented as an invariant: "A function call has a fixed gas cost to be initiated. Then the execution itself draws gas from the `attached_gas`... at which point the function call aborts with a `GasExceeded` error. No changes are persisted on chain." [6](#0-5) 

Because the very first line of the callback (`self.has_in_flight_tx = false;`) is rolled back along with everything else when the callback itself runs out of its fixed gas margin, the flag is left permanently `true`. Every subsequent call to `rlp_execute` is then unconditionally rejected: [7](#0-6) 

There is no other code path (grep confirms only these 11 references) that resets `has_in_flight_tx`, so this is unrecoverable by the contract itself — it can only be avoided, not repaired.

### Impact Explanation
This is a state-corruption / permanent unauthorized denial-of-service on a specific account: the wallet is meant to abstract Ethereum transactions into NEAR actions, and getting permanently stuck means all NEAR/NEP-141 assets routed through this wallet interface become inaccessible via `rlp_execute` — directly analogous to "Eth may get stuck in contract" from the original report, except here the lock is permanent rather than merely gas-price-dependent. This maps to an "unauthorized state change" (an unintended, un-reversible and un-recoverable invariant violation of `has_in_flight_tx`) reachable purely from a submitted Ethereum-style transaction routed through a standard unprivileged eth-implicit account.

### Likelihood Explanation
The 5 Tgas fixed margins are a static compile-time budget in the wallet contract's Wasm binary that is globally deployed to every eth-implicit account. Any future protocol-level increase in the cost of the relevant host functions (JSON parsing indirectly via env/storage host fn costs, `promise_batch_create`, string formatting through allocation-heavy costs) — which the CHANGELOG shows happens regularly across protocol versions (e.g. `72.yaml`, `77.yaml`, `84.yaml`, `85.yaml` all adjust gas/compute costs) — could push previously-safe workloads over budget. Additionally, a relayer or the account owner themselves choosing an `ERC20Transfer` `target`/token contract that returns an unusually large `storage_balance_of` response, or an `EOABaseTokenTransfer` where the registrar `lookup` response is large, can trigger this today without any protocol change, since the callback margin does not scale with response size at all.

### Recommendation
- Do not hard-code fixed gas constants as the only safety margin for callback logic whose cost depends on attacker/relayer-influenced response sizes; bound or validate the size of cross-contract responses before deserializing them, or dynamically size the callback gas budget based on worst-case response size.
- More importantly, make the `has_in_flight_tx` guard resilient to callback failure independent of gas exhaustion in the same execution unit — e.g., reset the flag in a separate, minimal-gas, always-succeeding step, or provide a recovery/timeout mechanism so the wallet cannot become permanently unusable.
- Consider using `promise_batch_action_function_call_weight`-style gas weighting instead of a small fixed additive margin, ensuring the callback receives a share of gas proportional to remaining budget rather than an easily exhausted static amount.

### Proof of Concept
1. Deploy `WalletContract` for an eth-implicit account (as done automatically for such accounts).
2. Construct/sign an RLP transaction with `TransactionKind::EthEmulation(EthEmulationKind::ERC20Transfer { .. })` whose `target` token contract is one the caller controls (or any NEP-141-look-alike contract) and which returns an oversized `storage_balance_of` JSON payload.
3. Call `rlp_execute`; the flow goes through `nep_141_storage_balance_callback`, which is only given `NEP_141_STORAGE_BALANCE_CALLBACK_GAS` (fixed ~15 Tgas total: `5 + 5 + 5` Tgas) plus `action.gas()` — see the constant definitions and their usage. [8](#0-7) 
4. If deserializing the oversized response exceeds the fixed margin, the callback aborts with `GasExceeded`, and the runtime rolls back the entire receipt's state changes per `runtime/runtime/src/lib.rs` lines 945-955 above, discarding the `has_in_flight_tx = false` reset.
5. `has_in_flight_tx` remains `true` forever; all future calls to `rlp_execute` are rejected with "transaction already in progress," matching the guard check at lines 97-105 of `lib.rs`, permanently bricking the wallet.
