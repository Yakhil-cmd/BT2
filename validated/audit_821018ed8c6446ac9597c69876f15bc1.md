### Title
Cross-organization webhook forgery via mismatched `repository.owner.login` (used to pick the signing secret) vs `repository.full_name` (used to select the acted-upon repository) — (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` derives *which* GitHub App/organization's `webhook_secret` to verify the incoming payload against from the untrusted payload itself, then every `Shipit::Webhooks::Handlers::Handler` subclass looks up the repository/stack to act on from a *different* field of the same untrusted payload. In a multi-organization Shipit deployment where any one configured organization has no `webhook_secret` set (a state explicitly documented and shown as valid in `docs/setup.md` and `test/dummy/config/secrets_double_github_app.yml`), an unauthenticated attacker can send a payload whose `repository.owner.login` names the unsecured organization (so signature verification trivially passes) while `repository.full_name`/`organization.login` names a completely different, secured organization's tracked repository/stack, causing Shipit to process the forged event as if it came from that other organization.

### Finding Description
`verify_signature` picks the signing secret using an untrusted field before any authentication occurs: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` resolves the per-organization `GitHubApp` config, and `verify_webhook_signature` **unconditionally returns `true` when that organization has no `webhook_secret` configured**: [3](#0-2) 

This "nil webhook_secret" state is a documented, supported configuration, shown both in single-org and multi-org setup examples: [4](#0-3) [5](#0-4) 

Once `verify_signature` passes, `Shipit::Webhooks.for_event(event)` dispatches the *entire* raw payload to handlers, which determine the actually-affected `Repository`/`Stack`/`Team` from other fields of that same payload — `repository.full_name` in nearly all handlers: [6](#0-5) [7](#0-6) [8](#0-7) 

There is no check anywhere in the controller or handlers that the organization used to select/verify the signing secret (`repository_owner`, derived from `repository.owner.login`/`organization.login`) equals the owner embedded in `repository.full_name` that the handler actually acts on. The binding "organization that authenticated == repository that is written" is broken: an attacker only needs one organization in the Shipit installation's `github` config to have no `webhook_secret`, and they can then forge events attributed to *any other* organization/repository the instance tracks.

### Impact Explanation
This is an authentication bypass for the webhook ingestion boundary: an unprivileged, unauthenticated network attacker who can reach the `/webhooks` endpoint can make Shipit act on forged GitHub events for repositories it does not administer, as long as the deployment has at least one configured organization without a `webhook_secret`. Depending on which event/handler is exercised, this can:
- Trigger unauthorized `GithubSyncJob` runs / cache invalidation for arbitrary tracked stacks (`PushHandler`, `CheckSuiteHandler`).
- Provision or unarchive review stacks for arbitrary pull requests on a targeted repository (`PullRequest::OpenedHandler`, `ReopenedHandler`), i.e. trigger unauthorized deploy-like activity.
- Forge commit `Status`/pull-request metadata that downstream deploy-gating logic (`ci.require`, review checklists) relies upon.
- Create/modify `Team`/`Membership` records tied to an arbitrary `organization.login`, which feeds `Shipit.github_teams` authorization.

This satisfies the Critical/High bar of "authentication bypass" / "escalation into `Shipit.github_teams` authorization" / "unauthorized deploy or rollback" depending on the event forged.

### Likelihood Explanation
Requires only that the Shipit instance be configured with multiple GitHub organizations where at least one lacks a `webhook_secret` — a state the project's own documentation and dummy fixtures present as a normal, supported configuration (`webhook_secret: # nil`). No credentials, tokens, or repository write access are needed; the attacker only needs network access to the public webhook endpoint and knowledge (or a guess) of an organization name that Shipit is configured for without a secret.

### Recommendation
Bind signature verification to the same identity used for the write path: after selecting the `GitHubApp` for verification, re-derive and cross-check that the organization implied by `repository.full_name` (and any other identity fields consumed by handlers) matches the organization used to verify the signature; reject the request otherwise. Alternatively, verify the payload against *every* configured organization's secret (if any) rather than only the one named by the untrusted payload, and disallow silent pass-through when a configured organization has no secret in multi-org mode.

### Proof of Concept
1. Configure Shipit with two organizations: `OrgA` (no `webhook_secret`) and `OrgB` (secret set), both mirroring `test/dummy/config/secrets_double_github_app.yml`, with a tracked repository `OrgB/service`.
2. POST to the webhooks endpoint with header `X-Github-Event: pull_request` and no (or garbage) `X-Hub-Signature`, and a body such as:
```json
{
  "action": "opened",
  "number": 42,
  "pull_request": { ... "head": {"sha": "<existing-branch-sha>", "ref": "feature-x"} ... },
  "repository": { "full_name": "OrgB/service", "owner": {"login": "OrgA"} },
  "sender": {"login": "attacker"}
}
```
3. `repository_owner` resolves to `OrgA` → `Shipit.github(organization: "OrgA")` → `verify_webhook_signature` returns `true` unconditionally (no secret configured for `OrgA`).
4. `Shipit::Webhooks::Handlers::PullRequest::OpenedHandler` looks up `Repository.from_github_repo_name("OrgB/service")` and provisions/acts on `OrgB`'s review stack — despite the request never being authenticated against `OrgB`'s secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
