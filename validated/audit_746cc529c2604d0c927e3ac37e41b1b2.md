### Title
Asset definer can revoke previously-attested holders' ability to spend a `spender_attested` asset by publishing a new `asset_attestors` list, permanently freezing their funds - (File: `validation.js`)

### Summary
For assets created with `spender_attested: true`, spending/transferring an output requires the owning address to be attested by an address in the asset's *current* attestor list. The asset definer alone controls this list via the `asset_attestors` message and can update it at any time to remove attestors that previously vouched for a holder's address, or add new attestors that never attested existing holders. Because eligibility is re-evaluated against the *latest* attestor list at validation time (not the list in force when the tokens were issued/received), the definer can retroactively strip a legitimate holder's spending rights, freezing their asset balance forever — the same "owner revokes access" pattern as the MasterChef `onlyDepositor` finding, but here the "owner" is the asset issuer and the "depositor" is any token holder.

### Finding Description
- When defining an asset with `spender_attested: true`, only the definer (single author) is allowed to update the attestor list, enforced in `validateAttestorListUpdate`: [1](#0-0) 
- `checkAttestorList` only validates format/sorting of the list; it does not require the new list to be a superset of the old one or otherwise preserve previously attested addresses: [2](#0-1) 
- `storage.readAsset` computes `objAsset.arrAttestorAddresses` from only the *single latest* `asset_attestors` unit for that asset (`ORDER BY level DESC LIMIT 1`), i.e., older attestor lists are completely discarded once a newer one is stable: [3](#0-2) 
- Spend eligibility (`arrAttestedAddresses`) is derived by joining `attestations` against this current attestor list via `filterAttestedAddresses`, so an address only counts as attested if one of the *current* attestors attested it: [4](#0-3) [5](#0-4) 
- Both issuance and transfer validation reject inputs/outputs whose owner address is not in `arrAttestedAddresses`: [6](#0-5) [7](#0-6) 
- Output-side attestation is likewise enforced before allowing a payment to complete: [8](#0-7) 

Because the definer fully controls the attestor set and there is no restriction preventing removal of attestors that attested existing balance holders, the definer can:
1. Publish an initial attestor list, let attestors attest holder addresses, and let users acquire/hold the asset.
2. Publish a new `asset_attestors` message naming different attestor addresses (which have not attested the existing holders, or which the definer controls to selectively attest).
3. From that point on, the previously-legitimate holders' addresses fail the `arrAttestedAddresses` check and can never again spend or transfer their balance of that asset — their funds are permanently locked in-protocol with no fallback path (there is no `onlyDepositor`-style modifier here, but the analogous "removable authorization gate" is the attestor list).

### Impact Explanation
This lets a malicious or compromised asset issuer freeze arbitrary holders' balances of a `spender_attested` asset at will, post-issuance, with a single ordinary message from their own address. It is a fund-freezing vulnerability contingent on a malicious/compromised privileged party (the asset definer), matching the accepted Medium severity of the referenced MasterChef finding ("valid... but contingent on a malicious owner"). Holders have no recourse: they cannot make themselves attested by attestors they don't control, and the change is immediate once stable.

### Likelihood Explanation
Likelihood is Medium: it requires the asset definer (a privileged single-author key) to act maliciously or be compromised, similar to the original finding's dependency on a malicious/compromised owner. No cooperation from other network participants, witnesses, or consensus is needed — a single valid `asset_attestors` unit from the definer suffices, and normal validation rules fully support it as a documented (not merely bugged) mechanism, making it trivially exploitable once the actor's intent turns malicious.

### Recommendation
- Either make the attestor list immutable after the asset is created (comment in the schema even says "must subsequently publish and update the list of trusted attestors", implying mutability is by design, but this should be re-evaluated), or
- Require attestation checks to consider the attestor list that was in effect at the time the attestation was made (i.e., attestations should remain valid as long as they were made under an attestor set that was current at attestation time), rather than re-validating every attestation against only the single latest list, or
- Add a grace period / one-way-only restriction (e.g., attestors may only be added, not removed, or removal requires holder consent), so a definer cannot retroactively invalidate attestations that existing balances rely on.

### Proof of Concept
1. Definer publishes an `asset` message with `spender_attested: true` and an initial `attestors` list `[A1]`. [9](#0-8) 
2. Attestor `A1` attests Alice's address; Alice receives/holds units of the asset — validated successfully because `A1` is in the current `arrAttestorAddresses` and Alice is in `arrAttestedAddresses`. [10](#0-9) 
3. Definer publishes a new `asset_attestors` message for the same asset with a new list `[A2]` (excluding `A1`). Validation only checks that the sender is the definer and the list is well-formed: [1](#0-0) 
4. `storage.readAsset` now returns `arrAttestorAddresses = [A2]` only, since it reads the single latest attestor-list unit. [3](#0-2) 
5. Alice attempts to spend her previously-received units. `filterAttestedAddresses` finds no attestation from `A2` for Alice's address, so `arrAttestedAddresses` no longer includes her, and `validatePaymentInputsAndOutputs` rejects her spend with "owner address is not attested". [7](#0-6) 
6. Alice's balance is now permanently unspendable unless the definer chooses to have `A2` (or a future attestor) attest her again — entirely at the definer's discretion.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}

function checkAttestorList(arrAttestors){
	if (!isNonemptyArray(arrAttestors))
		return "attestors not defined";
	if (arrAttestors.length > constants.MAX_ATTESTORS_PER_ASSET)
		return "too many attestors";
	var prev="";
	for (var i=0; i<arrAttestors.length; i++){
		if (!isValidAddress(arrAttestors[i]))
			return "invalid attestor address: "+JSON.stringify(arrAttestors[i]);
		if (arrAttestors[i] <= prev)
			return "attestors not sorted";
		prev = arrAttestors[i];
	}
	return null;
}

// filter only those addresses that are attested (doesn't work for light clients)
function filterAttestedAddresses(conn, objAsset, last_ball_mci, arrAddresses, handleAttestedAddresses){
	conn.query(
		"SELECT DISTINCT address FROM attestations CROSS JOIN units USING(unit) \n\
		WHERE attestor_address IN(?) AND address IN(?) AND main_chain_index<=? AND is_stable=1 AND sequence='good' \n\
			AND main_chain_index>IFNULL( \n\
				(SELECT main_chain_index FROM address_definition_changes JOIN units USING(unit) \n\
				WHERE address_definition_changes.address=attestations.address AND main_chain_index<=? AND is_stable=1 AND sequence='good' ORDER BY main_chain_index DESC LIMIT 1), \n\
			0)",
		[objAsset.arrAttestorAddresses, arrAddresses, last_ball_mci, last_ball_mci],
		function(addr_rows){
			var arrAttestedAddresses = addr_rows.map(function(addr_row){ return addr_row.address; });
			handleAttestedAddresses(arrAttestedAddresses);
		}
	);
}
