### Title
Unvalidated Arbstore URL from Attacker-Controlled Arbiter Identity Leads to SSRF - ([File: arbiters.js])

### Summary
`arbiters.js` and `arbiter_contract.js` fetch an "arbstore" URL through the hub for a given `arbiter_address` and then issue an HTTP(S) request directly to that URL with no scheme, host, or address-range validation, mirroring the LocalAI SSRF pattern of feeding an unsanitized, remotely-supplied URL straight into an outbound HTTP client.

### Finding Description
When a wallet resolves arbiter/arbstore information, it calls `device.requestFromHub("hub/get_arbstore_url", address, ...)` and then immediately fetches whatever URL comes back, with only a "non-empty string" check: [1](#0-0) 
That URL is passed unmodified into `requestInfoFromArbStore`, which does a raw `http.get(url, ...)` (module aliased to `https`) and parses the response body as JSON, with no allow-list, no protocol restriction, and no check that the target is not a loopback/private/link-local address: [2](#0-1) 

The same pattern repeats in `arbiter_contract.js`, where `getArbstoreAddresses` and `getAppealFee` fetch the URL via `device.requestFromHub("hub/get_arbstore_url", arbiter_address, ...)` and hand it to `httpRequest`, which builds a raw `http.request` from `url.parse(host)` with no validation of the resulting host/protocol before issuing the request: [3](#0-2) [4](#0-3) 

Critically, `arbiter_address` — the key used to look up the arbstore URL — originates from an `arbiter_contract` object that is fully attacker-controlled: a peer creates and sends the contract offer to the victim over `sendMessageToDevice(objContract.peer_device_address, "arbiter_contract_offer", objContractForPeer)`, with `arbiter_address` set by the sender at creation time: [5](#0-4) 
and the receiving side persists the offer's fields, including `arbiter_address`, via `store()` without independently validating that the identity is a genuine, trusted arbiter: [6](#0-5) 

Because `arbiter_address` (and thus which hub/identity answers `hub/get_arbstore_url`) is chosen by the offering peer, a malicious paired-device counterparty can register/control a hub identity for that address that answers with an arbitrary URL (e.g. `http://127.0.0.1:PORT/...` or an internal-network address). When the victim's wallet subsequently resolves arbiter/arbstore info for that contract (via `arbiters.getInfo`/`getArbstoreInfo` or `arbiter_contract.getAppealFee`/`fillArbstoreAddresses`), it will blindly issue an HTTP(S) request to that attacker-chosen URL, exactly analogous to LocalAI's `POST /models/apply` passing an unsanitized gallery URL straight into `gallery.GetGalleryConfigFromURLWithContext`.

### Impact Explanation
An attacker acting as a private-payment/arbiter-contract counterparty can force the victim's ocore-based wallet to issue outbound HTTP requests to internal/loopback network endpoints under the attacker's chosen target. Response bodies are parsed and, on parse failure or network error, propagated back through `cb(err)`/`console.warn` paths, which can leak partial content or error details about internal services. This does not directly cause double-spend or fund loss, but it is a genuine SSRF impacting confidentiality of the victim's local network (matching the CVSS vector of the source report: `SC:H`, no confidentiality/integrity impact to the app's own accounting).

### Likelihood Explanation
Likelihood is moderate: it requires the victim to accept/interact with an `arbiter_contract_offer` from a paired device and for the wallet UI to subsequently resolve arbiter/arbstore info (a normal step in the arbiter-contract flow, e.g., to show arbiter details or the appeal fee) — no special privileges beyond being a pairing counterparty are needed.

### Recommendation
Validate any URL obtained via `hub/get_arbstore_url` before use: enforce `https://` scheme, resolve and reject loopback/private/link-local/metadata-service IP ranges, and apply an allow-list or the same SSRF-hardening approach later used for `fetchUrl`/`fetchUrl`-like flows in `uri.js`. Add these checks in `arbiters.js` (`getInfo`, `getArbstoreInfo`, `requestInfoFromArbStore`) and `arbiter_contract.js` (`getArbstoreAddresses`, `getAppealFee`, `httpRequest`) before any outbound request is issued.

### Proof of Concept
1. Attacker (peer B) pairs with victim (peer A) and creates an arbiter contract offer with `arbiter_address` set to an identity controlled by attacker's own hub, then calls `createAndSend`, sending `arbiter_contract_offer` to A [5](#0-4) .
2. Victim's wallet stores the offer via `store()` [6](#0-5)  and later resolves arbiter info, calling `arbiters.getInfo(arbiter_address, ...)`.
3. `device.requestFromHub("hub/get_arbstore_url", arbiter_address, ...)` returns to attacker's hub, which responds with `http://169.254.169.254/latest/meta-data/` (or any internal URL) [1](#0-0) .
4. `requestInfoFromArbStore` performs `http.get(url, ...)` against that internal address and parses/returns the response [2](#0-1) , completing the SSRF.

function httpRequest(host, path, data, cb) {
	var reqParams = Object.assign(url.parse(host),
		{
			path: path,
			method: "POST",
			headers: {
				"Content-Type": "application/json",
				"Content-Length": (new TextEncoder().encode(data)).length
			}
		}
	);
	var req = http.request(
		reqParams,
		function(resp){
			var data = "";
			resp.on("data", function(chunk){
				data += chunk;
			});
			resp.on("end", function(){
				try {
					data = JSON.parse(data);
					if (data.error) {
						return cb(data.error);
					}
					cb(null, data);
				} catch (e) {
					cb(e);
				}
			});
		}).on("error", cb);
	req.write(data);
	req.end();
}
