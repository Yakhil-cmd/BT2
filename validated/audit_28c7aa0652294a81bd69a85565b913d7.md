### Title
`unbundled_env` merges task/API-supplied `env` last with no denylist, letting a repository-controlled `shipit.yml` override `GITHUB_TOKEN`/`GIT_ASKPASS`/`PATH` on every command execution - ([File: lib/shipit/command.rb#unbundled_env])

### Summary
`Command#unbundled_env` builds the process environment as `BASE_ENV.merge('PATH' => ...).merge(@env.stringify_keys)`, so any key in the task's `env` hash unconditionally wins, including `GITHUB_TOKEN`, `GIT_ASKPASS`, and `PATH`. Because the whitelist that decides which keys are allowed into `@env` (`deploy.variables` / `task.variables` in `shipit.yml`) is itself read from the commit being deployed, an attacker who controls that commit's `shipit.yml` (e.g. a fork/PR branch behind a review stack) can declare a variable literally named `GIT_ASKPASS` with a default value pointing at a script they committed, causing that attacker-authored script to run with the real deploy-host credentials.

### Finding Description
The claimed binding is: `keys(@env) ∩ {'GITHUB_TOKEN','GIT_ASKPASS','PATH'} == ∅` for any `@env` sourced from an unapproved ref. Nothing in the code enforces this.

- `Command#unbundled_env` merges `@env.stringify_keys` last with no denylist: [1](#0-0) 

- `Commands#base_env` sets the legitimate `GITHUB_TOKEN`/`GIT_ASKPASS` first: [2](#0-1) 

- `TaskCommands#env` merges `@task.env` (the user/task-declared variables) absolutely last, after `super` (which contains `GITHUB_TOKEN`/`GIT_ASKPASS`): [3](#0-2) 

- The only gate on what can land in `@task.env` is `EnvironmentVariables#permit`, which whitelists by *name*, not by disallowing sensitive names such as `GITHUB_TOKEN`/`GIT_ASKPASS`/`PATH`: [4](#0-3) [5](#0-4) 

- The whitelist itself (`deploy_variables`/`rollback_variables`/task `variables`) is parsed from `shipit.yml` on the commit being deployed (`DeploySpec::FileSystem`), i.e. attacker-controlled content on the branch/PR being deployed: [6](#0-5) [7](#0-6) 

- Confirmed test behavior: even with no explicit `env` param, declared variable **defaults** are automatically applied to `Task#env`: [8](#0-7) 

Exploit flow: an attacker opens a PR / pushes a branch whose `shipit.yml` declares `deploy: { variables: [{name: 'GIT_ASKPASS', default: './evil_askpass.sh'}] }` and commits `evil_askpass.sh` (which exfiltrates `$GITHUB_TOKEN`/other env vars to an attacker server and exits 0). When a deploy/task is executed against that commit — which is the normal, intended behavior for review-stack automation that clones and runs the PR's own `shipit.yml` — `TaskCommands#env` merges this attacker-controlled `GIT_ASKPASS` value last, overriding the legitimate one set in `base_env`. `PTY.spawn(unbundled_env, ...)` then runs `git` with `GIT_ASKPASS` pointing at the attacker's script, which git executes on the deploy host, with the real `GITHUB_TOKEN` still present in the process environment (unless the attacker also names `GITHUB_TOKEN` as a variable to overwrite it, or reads it from the untouched real value via the same script). The whitelist mechanism (`EnvironmentVariables#permit`) does not block this because it only checks membership in a declared-name list — that list is authored by the same attacker.

### Impact Explanation
Successful exploitation runs attacker-supplied code on the Shipit deploy host with the real `GITHUB_TOKEN` and other deploy secrets in its environment, satisfying the "RCE on the deploy host via `Command`/`PTY.spawn`" and "exfiltration of `GITHUB_TOKEN`... or deploy-time secrets" Critical categories. Because `GITHUB_TOKEN` is a shared app-level (or org-level) credential used across stacks/repositories, exfiltrating it lets the attacker impersonate Shipit against GitHub for other repositories too, extending blast radius beyond the single attacking repository.

### Likelihood Explanation
Preconditions: the target Shipit deployment must run automated deploys/tasks against attacker-influenced commits (review stacks, PR-triggered tasks, or any workflow where an unprivileged contributor's branch content is checked out and its `shipit.yml` consulted for `deploy.variables`/task `variables`). No Shipit session, API token, or GitHub team membership is required — the attacker only needs push/PR access to a repository configured with Shipit. This matches the "review stack" scenario the question specifically raises. The attack is fully repeatable per push/PR and costs the attacker nothing beyond authoring a commit.

### Recommendation
In `Command#unbundled_env` (or upstream in `Commands#base_env`/`TaskCommands#env`), enforce a denylist so that keys like `GITHUB_TOKEN`, `GIT_ASKPASS`, and `PATH` (and any other credential/execution-control variables) cannot be overridden by `@env`, regardless of merge order — e.g. re-merge the protected keys after `@env` is applied, or strip them from `@env` before merging. Additionally, `EnvironmentVariables#permit`/`VariableDefinition` should reject variable *declarations* that use reserved/sensitive names in `shipit.yml`, since the whitelist itself is attacker-controlled content.

### Proof of Concept
```ruby
# test/unit/command_test.rb (illustrative)
test "unbundled_env does not allow env to override GITHUB_TOKEN" do
  command = Command.new("true", chdir: Dir.tmpdir, env: { 'GITHUB_TOKEN' => 'evil' })
  refute_equal 'evil', command.unbundled_env['GITHUB_TOKEN']
end

test "unbundled_env does not allow env to override GIT_ASKPASS" do
  command = Command.new("true", chdir: Dir.tmpdir, env: { 'GIT_ASKPASS' => '/tmp/evil_askpass.sh' })
  refute_equal '/tmp/evil_askpass.sh', command.unbundled_env['GIT_ASKPASS']
end
```
Both assertions currently fail against `lib/shipit/command.rb#unbundled_env` (line 104), confirming the unguarded override.

    def sanitize_env_vars(variable_definitions)
      allowed_variables = variable_definitions.map(&:name)

      allowed, disallowed = @env.partition { |k, _| allowed_variables.include?(k) }.map(&:to_h)

      error_message = "Variables #{disallowed.keys.to_sentence} have not been whitelisted"
      raise NotPermitted, error_message unless disallowed.empty?

      allowed
    end
