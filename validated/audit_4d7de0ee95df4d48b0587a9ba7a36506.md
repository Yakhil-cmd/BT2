### Title
AA "silently accept coins" fallback pattern permanently strands funds because `aa_balances`/`balance[]` is credited unconditionally while the internal accounting state var is only updated above a threshold - ([File: aa_composer.js])

### Summary
This is the ocore analog of the Allo pool-funding bug: a caller can send funds directly to a contract/pool such that the pool's *real* balance increases but the pool's *internal accounting variable* (the one actually used to authorize withdrawals/distribution) does not, permanently stranding the funds. In ocore, the "pool" is any Autonomous Agent (AA) that tracks depositor balances or pooled funds in a `state var` (e.g. `var[$base_key]`), while the AA's real coin holdings are tracked independently and automatically by the engine in the `aa_balances` table (exposed to oscript as `balance[asset]`).

### Finding Description
Every unit that sends outputs to an AA address updates the AA's real balance unconditionally, before any of the AA's `if`-conditions are even evaluated. This happens in `updateInitialAABalances()`, called at the very start of `handleTrigger()`: [1](#0-0) 
which runs before the `case` matching / `evaluateAA` logic that decides how to react to the trigger: [2](#0-1) 

The real balance is queryable from oscript via `balance[asset]`, which just reads `aa_balances`, completely independent of any AA-defined state variable: [3](#0-2) 

Because of this decoupling, AA authors commonly implement a "silently accept coins" fallback case that only credits an internal tracking variable (e.g. `var[$base_key]`) when the deposited amount exceeds a threshold, as shown in ocore's own shipped sample AAs: [4](#0-3) [5](#0-4) 

If a user sends a payment of `base` (or any tracked asset) at or below the threshold (`<= 10000` in these samples) with no `trigger.data`, the `if: "{!trigger.data...}"` case still matches and runs, but the inner `if (trigger.output[[asset=base]] > 10000)` guard fails, so `var[$base_key]` is never incremented. Meanwhile the AA's real `aa_balances`/`balance[base]` has already been incremented unconditionally by `updateInitialAABalances`. The coins are now permanently inside the AA (they satisfy `checkBalances()`'s reconciliation between `aa_balances` and unspent `outputs` — i.e. this is not detected as a bug by ocore's own invariant checker) but are invisible to the accounting variable that governs withdrawals/distribution, exactly mirroring the reported Allo issue where `poolAmount` fails to increase on direct token transfer even though the contract's real token balance rises.

### Impact Explanation
Funds sent this way become permanently locked in the AA: no depositor's tracked balance reflects them, so no withdrawal path can ever claim them, and any pool-level accounting/distribution logic that relies on the state var (rather than `balance[]`) will be inconsistent with the AA's real holdings. This is a fund-freezing condition reachable by any ordinary AA trigger sender with no special privileges — a direct analog to "stuck of funds in the protocol" from the source report.

### Likelihood Explanation
Any user (or the AA's own author testing it) can trivially trigger this by sending a plain payment of `base` bytes equal to or below the sample's threshold and no `data` object. No privileged role, malicious peer, or race condition is required — a single, otherwise valid unit accepted and stabilized by the network suffices.

### Recommendation
AA authors (and the reference/sample templates ocore ships, which developers copy) should not gate the accounting-variable update on an arbitrary threshold while still accepting/keeping the coins. Either: (1) bounce the trigger (return the funds) whenever the received amount is insufficient to be credited to the tracking variable, so `balance[]` and the state var never diverge, or (2) always credit whatever amount was received into the tracking variable regardless of size, removing the threshold gate entirely.

### Proof of Concept
1. Deploy `test/samples/a_bank_without_percent.oscript` as an AA.
2. From address `A`, send a payment unit consisting only of `5000` bytes to the AA address, with no `data` field on the trigger.
3. `updateInitialAABalances()` credits `aa_balances` for the AA by `5000` bytes immediately (`aa_composer.js:475-541`, invoked at `aa_composer.js:1841`).
4. The `"silently accept coins"` case matches (`!trigger.data.withdraw` is true), but `trigger.output[[asset=base]] > 10000` is false, so `var[$base_key]` is not incremented (`test/samples/a_bank_without_percent.oscript:39-43`).
5. `balance[base]` (real AA balance) now includes the `5000` bytes, but no depositor's `var[$base_key]` reflects it, and there is no code path to ever withdraw it — the funds are permanently stuck, and `checkBalances()` will not flag this as an inconsistency since `aa_balances` still correctly matches the unspent outputs.
