### Title
`unstake-sbtc` and reward payouts permanently freeze a staker's locked sBTC/STX if the sBTC token transfer to the staker reverts - (File: `stackslib/src/chainstate/stacks/boot/pox-5.clar`)

### Summary
`unstake-sbtc` mutates all of the staker's accounting state (bond membership, per-cycle shares, `protocol-bonds-total-staked`, `total-sbtc-staked`) and only afterwards performs the actual sBTC payout via a direct `contract-call?` to the external `sbtc-token` contract, wrapped in `try!`. If that transfer call fails or reverts for any reason tied to the recipient address (e.g., the sBTC token contract refusing to credit that principal), the entire transaction — including all the state mutations — is rolled back, and there is no alternate path for the staker to reclaim their sBTC.

### Finding Description
`unstake-sbtc` (lines 1261-1342) reduces the staker's `amount-sats` in `protocol-bond-memberships`, updates per-cycle share maps via `unstake-sats-from-bond-cycles`, decrements `protocol-bonds-total-staked` and `total-sbtc-staked`, and only then calls: [1](#0-0) 

This transfer is a single, hard dependency `try!`'d directly on the outcome of the external `sbtc-token` contract's `transfer` function. Because the whole function body (including the accounting updates) is atomic in Clarity, any revert in the `transfer` call rolls back the entire `unstake-sbtc` transaction, leaving `amount-sats`, `total-sbtc-staked`, etc. unchanged (i.e., no funds lost from accounting), but leaving the staker's sBTC still fully custodied in the contract with no way for the staker to unstake — the only public entry point that releases this specific sBTC amount is this same `unstake-sbtc` function.

The same pattern (`try!` around a direct `contract-call? sbtc-token transfer ... staker`) recurs in `roll-sbtc`'s decrease branch: [2](#0-1) 
and in `claim-staker-rewards` in the signer-manager contract, which pays the staker's earned sBTC rewards directly: [3](#0-2) 

In each case, a single push-style transfer to the staker/recipient is embedded inside a larger state-mutating transaction with no fallback claim mechanism. This is the direct analog of the reported `Stream.cancel()` bug: a payout-on-cancel/unstake operation that combines state finalization and a mandatory push transfer to a principal whose ability to receive the asset is not guaranteed to always succeed.

Unlike the STX lock (which is released by the node's own lazy-unlock mechanism at `unlock-burn-height`, independent of any contract call — see `pox_unstake_v5` and `unlock_available_tokens_if_any`), the sBTC held in `pox-5` custody has no such node-level fallback. Its only release path is the explicit `transfer` call embedded in `unstake-sbtc`/`roll-sbtc`/reward-claim functions.

### Impact Explanation
If the `sbtc-token` transfer to a specific staker principal can be made to fail (whether via an allow/deny-list on the token, a trait/dispatch failure, or any other condition that makes that specific `transfer` call non-executable for that principal), that staker's locked sBTC becomes permanently stuck in the `pox-5` contract: they can never successfully call `unstake-sbtc` (it always reverts at the final transfer step), and no other function releases that specific bond's custodied sBTC to them. This matches the "permanent freezing of staked... sBTC" Critical impact category, since the staker's collateral becomes unrecoverable while the contract's internal accounting (`total-sbtc-staked`) never actually reflects the release (since the whole transaction reverts, so no partial-state corruption occurs, but the funds are frozen forever for that principal).

### Likelihood Explanation
Likelihood depends entirely on whether the specific `sbtc-token` deployment referenced in `pox-5.clar` (`SM3VDXK3WZZSA84XXFKAFAF15NNZX32CTSG82JFQ4.sbtc-token`) can reject a `transfer` to an arbitrary recipient principal (analogous to USDC's blacklist). This repo does not contain that token contract's source, so I cannot confirm from the indexed code whether such a reject condition exists in the deployed `sbtc-token`. The vulnerability pattern in `pox-5.clar` itself, however, is concretely present and reachable by any staker: the direct, unguarded, all-in-one-transaction push transfer.

### Recommendation
Decouple the accounting state changes from the token transfer in `unstake-sbtc`, `roll-sbtc`, and reward-claim flows: instead of a mandatory `try!`'d push transfer inside the same transaction that finalizes unstake accounting, record a claimable/withdrawable balance for the staker and let the staker (or anyone) pull the funds in a separate transaction. This way, if the transfer to a specific principal is blocked, the staker's unstake/accounting update still succeeds, and the sBTC amount remains claimable (e.g. to a different address the staker controls) rather than being permanently trapped by a failing recipient-specific transfer.

### Proof of Concept
1. Staker registers for a bond and locks sBTC via `register-for-bond`, custodied by `pox-5.clar`.
2. Assume the external `sbtc-token` contract enters a state where `transfer` to the staker's principal fails (analogous to a USDC blacklist entry).
3. Staker calls `unstake-sbtc`, providing a valid `signer-manager` and amount: [4](#0-3) 
4. Execution proceeds through all state mutations (`unstake-sats-from-bond-cycles`, map updates, `total-sbtc-staked` decrement) and then reaches: [1](#0-0) 
5. The inner `contract-call? ... transfer ...` fails, the outer `try!` propagates the error, and the entire transaction (including all the accounting updates) reverts.
6. The staker's sBTC remains locked in `pox-5` with no alternative function to withdraw it — every call to `unstake-sbtc` for this staker will revert identically, permanently freezing their sBTC.
