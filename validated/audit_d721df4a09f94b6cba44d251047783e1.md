This confirms Shipit uses a GitHub App installed org-wide, with a single `webhook_secret` per organization. All repositories in that installed organization share the same webhook secret. This is important: an attacker who owns/controls *any* repository within an organization where the Shipit GitHub App is installed (e.g., an org that allows members to freely create repos) can receive genuinely-signed webhooks for their own repo, since GitHub computes the signature using the org-level app's shared secret, not a per-repo secret. That signed payload is fully valid per `verify_webhook_signature` [1](#0-0) , yet its `payload['repository']['full_name']` names the attacker's own (unrelated) repo.

### Title
StatusHandler mutates Commit records for any organization repo without checking `payload['repository']['full_name']` against the commit's own stack/repository - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits globally by `sha` across the entire `Commit` table and calls `commit.create_status_from_github!` on each match, without ever calling the inherited `repository_name`/`stacks` scoping helpers that every other handler (`PushHandler`, `CheckSuiteHandler`, all `PullRequest::*Handler`s) uses to constrain the query to the repository named in the payload. This means any correctly-signed `status` webhook from any repository sharing a GitHub App installation (org-wide webhook secret) can update statuses on commits belonging to a completely unrelated stack/repository, as long as the SHA happens to match.

### Finding Description
The broken binding, stated as an equality that should hold but doesn't: `repository_name` (i.e., `payload.dig('repository','full_name')`) must equal `commit.stack.repository.full_name` for every `Commit` mutated by the handler. In `StatusHandler#process`:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 

there is no `.joins(:stack, stack: :repository)` and no reference to `repository_name` or `stacks` (the inherited helpers defined in the base `Handler` class) [3](#0-2) . Contrast with `PushHandler#process`, which scopes via `stacks.not_archived.where(branch:)` [4](#0-3) , and `CheckSuiteHandler#process`, which scopes via `stacks.where(branch: ...)` [5](#0-4) . Every `PullRequest::*` handler likewise resolves `repository = Shipit::Repository.from_github_repo_name(params.repository.full_name)` before touching any record.

Root cause: `Commit.where(sha: params.sha)` is a global, unscoped lookup. The `sha` is attacker-controllable-adjacent — while GitHub SHA1s are content-derived and not arbitrarily forgeable, two different repositories can legitimately share identical commit SHAs whenever they share commit history (forks, mirrors, repos split from a common ancestor, or a repo created by the attacker that pulls/cherry-picks a commit object identical to one tracked by Shipit). No cryptographic collision is required — only that the same commit object (same tree, parents, author, message, timestamp) exists in both repositories, which is routine for forks/mirrors within one GitHub organization.

Exploit flow: 1) Attacker creates or controls Repo B inside a GitHub org where Shipit's GitHub App is installed (the org where they have repo-creation rights, or a repo they already own that shares the app installation's webhook secret). 2) Repo B shares a commit (same SHA) with Repo A, which is tracked by an unrelated Shipit stack. 3) Attacker triggers (or crafts) a `status` event on Repo B for that SHA with `state: 'success'`/`'failure'` etc., which GitHub signs with the organization's shared `webhook_secret`. 4) `WebhooksController#verify_signature` calls `Shipit.github(organization: repository_owner)` using `payload.dig('repository','owner','login')` from the attacker's own repo and successfully verifies the signature because it's the same org-wide secret [6](#0-5) . 5) `StatusHandler#process` runs `Commit.where(sha: params.sha)` and matches the commit belonging to Repo A's stack, mutating its status/state with no repository check.

Why existing guards fail: `verify_signature` only proves "some repository in this GitHub org sent this", not "the repository named in the payload owns this commit". `ExplicitParameters` schema in `StatusHandler` only validates types/presence of `sha`, `state`, etc., not repository identity [7](#0-6) . The base `Handler#stacks`/`#repository_name` scoping exists precisely for this purpose but is simply never invoked by `StatusHandler`.

### Impact Explanation
A payload legitimately signed for one repository can mutate `Commit`/`Status` state belonging to a different repository's stack, provided the attacker controls a repo under the same GitHub App installation and can produce (or replay) a status event referencing a shared SHA. `Commit#create_status_from_github!` can affect deployability/CI-gating logic (`deployable_status`, `commit_status` hooks) for the victim stack [8](#0-7) , which can influence whether a commit is treated as green/deployable in an unrelated stack — matching the "payload for one repository mutating another's stack/commit" Critical category, though scoped specifically to commit status state.

### Likelihood Explanation
Requires: (1) attacker has repo-creation or webhook-triggering ability within a GitHub organization that hosts Shipit's App installation (i.e., an org where signups/repo creation isn't restricted, or attacker is an existing member with a legitimate but low-privilege repo), and (2) a shared commit SHA between attacker's repo and the victim stack's repo (realistic via forks/mirrors, not a SHA1 collision). This is plausible in orgs with permissive repo-creation policies but not universal — a fully locked-down org where only trusted repos exist would not be exploitable this way. Attacker cost is low once inside the org; the action is repeatable against any commit whose SHA is known/shared.

### Recommendation
Scope `StatusHandler#process` the same way as other handlers, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }
  end
end
```
or use `Commit.joins(stack: :repository).where(sha: params.sha, shipit_stacks: { repository_id: Repository.from_github_repo_name(repository_name)&.id })`, ensuring `repository_name` (from the verified payload) is checked against `commit.stack.repository.full_name` before mutation.

### Proof of Concept
Minitest plan (`test/models/webhooks/handlers/status_handler_test.rb` conceptually):
```ruby
test "#process does not mutate a commit belonging to a different repository" do
  victim_commit = shipit_commits(:first) # belongs to stack whose repository.full_name == "shopify/shipit-engine"
  attacker_payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'repository' => { 'full_name' => 'attacker-org/unrelated-repo' }
  }
  handler = Shipit::Webhooks::Handlers::StatusHandler.new(attacker_payload)
  handler.expects(:repository_name).never # inherited method is unused
  assert_difference -> { victim_commit.statuses.count }, 1 do
    handler.process
  end
  refute_equal 'attacker-org/unrelated-repo', victim_commit.stack.repository.full_name
end
```
This demonstrates: `repository_name`/`stacks` are never invoked, and a commit is mutated even though `payload.dig('repository','full_name')` ("attacker-org/unrelated-repo") ≠ `commit.stack.repository.full_name` ("shopify/shipit-engine").
