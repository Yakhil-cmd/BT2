### Title
`ReopenedHandler#unarchive?` shares the `review_stacks_enabled` precedence bug, letting attackers force re-provisioning on opt-out repos - ([File: app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb])

### Summary
`ReopenedHandler#unarchive?` uses the exact same operator-precedence-broken boolean expression as `OpenedHandler#provision?`. Because Ruby's `&&` binds tighter than `||`, `repository.review_stacks_enabled` only gates the `allow_all` branch; the `allow_with_label` and `prevent_with_label` branches are evaluated independently of `review_stacks_enabled`, so an attacker can reopen a PR and re-trigger provisioning even when review stacks are disabled for that repository.

### Finding Description
The intended binding is: `unarchive_allowed == repository.review_stacks_enabled && provisioning_behavior_permits?(pull_request)`. The actual code at [1](#0-0)  is:

```ruby
def unarchive?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

Due to Ruby operator precedence, this parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`. The `review_stacks_enabled` flag is only ANDed into the first disjunct. If a repository has `review_stacks_enabled: false` but `provisioning_behavior: allow_with_label` (with a matching label present) or `provisioning_behavior: prevent_with_label` (with the label absent), `unarchive?` still returns `true`.

`process` then calls `stack.unarchive!` [2](#0-1) , which delegates to `ReviewStackAdapter#unarchive!`. That method looks up an existing archived `ReviewStack` (or creates one if missing), adds it to `Shipit::ReviewStackProvisioningQueue`, and calls `stack.unarchive!` [3](#0-2) . Queuing re-triggers the provisioning pipeline (`TaskCommands#perform`) against the PR's `head.ref` branch — attacker-controlled content, including `shipit.yml`.

This is an unmitigated code path: `respond_to_pull_request_reopened?` only checks `params.action == "reopened"` and `unarchive?` [4](#0-3) ; there is no additional guard re-checking `review_stacks_enabled` before calling `unarchive!`. The `NullRepository` fallback used for untracked repos safely returns `false` for all behaviors [5](#0-4) , so the bug is only exploitable against repositories that are actually tracked in Shipit (`Shipit::Repository.from_github_repo_name` match) but have explicitly opted out of review stacks (`review_stacks_enabled: false`) while still configuring a label-based `provisioning_behavior`.

### Impact Explanation
For any tracked repository configured with `review_stacks_enabled: false` and `provisioning_behavior: allow_with_label` or `prevent_with_label`, an unprivileged actor who can open/label/reopen a PR on that repository can force Shipit to unarchive (or create) a `ReviewStack` and enqueue it for provisioning, causing `TaskCommands#perform` to execute the attacker's branch content (e.g., `shipit.yml` steps) on the deploy host. This is repeatable per PR/repository matching the configuration and constitutes RCE via re-provisioning attacker-controlled steps, matching the Critical impact category (arbitrary command execution via `Command`/`PTY.spawn` through the provisioning task pipeline) for repositories that believed they had opted out of review-stack automation.

### Likelihood Explanation
Preconditions: the target repository must be tracked by Shipit and configured with `review_stacks_enabled: false` combined with `provisioning_behavior: allow_with_label` (label present) or `prevent_with_label` (label absent) — a plausible/realistic misconfiguration since operators may believe disabling `review_stacks_enabled` fully disables the feature regardless of `provisioning_behavior`. No secrets, session, or elevated GitHub role are required: the attacker only needs to open a PR (or fork+PR), optionally add a label they control, and reopen it, driving a standard `pull_request_reopened` webhook. This mirrors the already-acknowledged bug in `OpenedHandler#provision?`, indicating the same latent misconfiguration risk applies wherever this expression pattern is duplicated (also `LabeledHandler`/`UnlabeledHandler`, which reuse the identical pattern per the grep results).

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates the entire behavior evaluation:

```ruby
def unarchive?
  repository.review_stacks_enabled &&
    (
      repository.provisioning_behavior_allow_all? ||
      (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
      (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
    )
end
```

Apply the identical fix to `OpenedHandler#provision?`, and audit `LabeledHandler`/`UnlabeledHandler` for the same pattern.

### Proof of Concept
Minitest plan (mirrors `reopened_handler_test.rb`'s `configure_provisioning_behavior` helper):

```ruby
test "does not unarchive stacks when review_stacks_enabled is false, even with prevent_with_label satisfied" do
  stack = create_archived_stack
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_reopened)
  payload["pull_request"]["labels"] = [] # label absent satisfies prevent_with_label

  Shipit::Webhooks::Handlers::PullRequest::ReopenedHandler.new(payload).process

  assert stack.reload.archived?, "Expected stack to remain archived because review_stacks_enabled is false"
end
```

Before the fix, this assertion fails: `unarchive?` evaluates `(false && false) || (false && ...) || (true && true) == true`, `stack.unarchive!` runs, `Shipit::ReviewStackProvisioningQueue.add(stack)` is called, and `assert_pending_provision(stack)` would pass — demonstrating the stack is unarchived and queued for re-provisioning despite `review_stacks_enabled: false`. After applying the parenthesization fix, `unarchive?` correctly evaluates to `false` and the stack stays archived.
