### Title
Caller-selected flash receiver can steal unrelated wallet tokens through the caller's signed authorization tree - (File: contracts/controller/src/strategies/flash_position.rs)

### Summary

High. `flash_position` accepts a caller-selected Wasm receiver, excludes only the controller and pool, and invokes that receiver while the transaction is executing under `caller.require_auth()`. [1](#0-0) [2](#0-1) [3](#0-2) 

A malicious receiver can call `token.transfer(initiator, attacker, amount)` for any unrelated token held by the caller; Soroban simulation records that required authorization as a child of the caller's `flash_position` authorization, and enforcement executes it if the caller signs the poisoned tree. 

### Finding Description

`process_flash_position` authenticates the supplied `caller`, loads or creates the account, mints and forwards debt, then invokes `execute_flash_position` on the arbitrary `receiver` argument supplied in the public call. [4](#0-3) [3](#0-2) 

The only receiver restrictions are that it is a deployed Wasm contract and is neither the controller nor the pool; there is no receiver allowlist, code-hash check, or restriction on additional calls that request `caller` authorization. [5](#0-4) 

The callback receives `initiator`, which is the same authorized `caller`, so malicious receiver code has the victim address needed to request unrelated token transfers. [6](#0-5) 

The flash guard and post-callback collateral/risk checks constrain protocol accounting but do not constrain what other contracts the receiver calls or which additional `caller.require_auth()` invocations are inserted into the authorization tree. [7](#0-6) 

### Impact Explanation

A successful signed transaction can transfer arbitrary unrelated wallet tokens from the caller to an attacker while still satisfying the flash-position collateral requirements, resulting in theft of user funds beyond the flash-borrowed amount or account collateral. [8](#0-7)  

Because the extra token transfers are independent protocol calls, the receiver can drain multiple known token balances from the victim in one signed transaction, subject to authorization-tree and resource limits. 

### Likelihood Explanation

An unprivileged attacker can deploy a compatible receiver and induce or serve a `flash_position` call naming that receiver; the caller must sign the authorization tree containing the extra token-transfer children, so exploitation requires user interaction rather than an on-chain authorization bypass. [9](#0-8)  

The condition is realistic because the receiver and `data` are caller-controlled integration parameters, and the malicious transfer can be combined with callback logic that returns enough declared collateral for the transaction to complete. [10](#0-9) [11](#0-10) 

### Recommendation

Restrict flash-position receivers to governance-approved addresses or immutable code hashes, or remove arbitrary receiver callbacks from the transaction that carries account-owner authorization. [2](#0-1) 

Until receivers are constrained, clients must decode the complete simulated authorization tree and reject any `flash_position` authorization containing children beyond the explicitly expected calls, especially token transfers to addresses other than the pool or controller. 

### Proof of Concept

1. Deploy a malicious Wasm contract implementing `execute_flash_position`.
2. Configure it with the attacker's payout address and an unrelated token held by the expected caller.
3. Have the victim call:

```rust
controller.flash_position(
    victim,
    0,
    spoke_id,
    PositionMode::Multiply,
    debt_asset,
    borrow_amount,
    malicious_receiver,
    Bytes::new(&env),
    vec![&env, (collateral_asset, minimum_collateral)],
    Vec::new(&env),
)
```

The receiver is valid because `require_wasm_receiver` permits arbitrary deployed Wasm contracts and the explicit exclusions cover only the controller and pool. [2](#0-1) 

Inside `execute_flash_position`, the malicious contract executes conceptually:

```rust
let victim_balance = token::Client::new(&env, &unrelated_token).balance(&initiator);
token::Client::new(&env, &unrelated_token)
    .transfer(&initiator, &attacker, &victim_balance);
token::Client::new(&env, &collateral_asset)
    .transfer(&env.current_contract_address(), &controller, &minimum_collateral);
```

The first transfer requests authorization from `initiator`, which is the caller passed by the controller, while the second satisfies the declared collateral receipt expected after callback return. [8](#0-7) 

During simulation, the unrelated `token.transfer(initiator -> attacker, victim_balance)` is recorded as an additional child under the victim's `flash_position` authorization; if the victim signs that tree, the token transfer succeeds and the controller subsequently deposits the supplied collateral and finalizes the flash position. [11](#0-10)
