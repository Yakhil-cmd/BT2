### Title
Cross-repository commit-status forgery via unscoped `Commit.where(sha:)` in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits to update purely by SHA string, with no constraint tying the lookup to the repository that authenticated the incoming webhook. An attacker who controls any repository enrolled under the same GitHub App/organization installation as a victim's production stack can create a `status` (`context: github-actions`, `state: success`) on an arbitrary SHA string belonging to the victim's stack via GitHub's own Statuses API, causing Shipit to attach that status to the victim's commit and flip its deployability.

### Finding Description
The broken binding is:
`payload.repository.owner.login (the org that signed the webhook) == commit.stack.repository (the repository whose commit gets mutated)`

In reality the code enforces only:
`verify_signature` checks `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` (app/controllers/shipit/webhooks_controller.rb:24-38), i.e. it proves the payload genuinely came from GitHub for *some* repository owned by `repository_owner`. It does not constrain which Shipit `Stack`/`Commit` the event is allowed to affect.

`StatusHandler#process` then does: [1](#0-0) 
`Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — this is a global, unscoped lookup across every `Commit` row in the database, regardless of which repository/stack it belongs to.

`create_status_from_github!` then writes the status and recomputes deployability: [2](#0-1) [3](#0-2) 
and `deployable?` becomes true once a `success` status matching the stack's required context is recorded and the commit is not `blocked?`: [4](#0-3) 

Exploit flow: an attacker with push/Actions access to *any* repository enrolled under the same GitHub App installation as the victim's production stack (they need not have any access to the victim repository itself) calls GitHub's `POST /repos/{attacker_repo}/statuses/{sha}` API with `sha` set to the literal SHA of a commit that exists in the victim's production stack, `context: github-actions`, `state: success`. The GitHub Statuses API does not require the SHA to correspond to a real object reachable in the attacker's repository — any 40-hex-character string is accepted. GitHub then delivers a webhook for the attacker's own repository, correctly signed with that organization's app secret. `verify_signature` passes because the signature is genuinely valid for `repository_owner` (attacker's org/repo). `drop_unhandled_event` passes because `status` is a handled event. `StatusHandler#process` then matches the victim's `Commit` row purely by SHA and writes the forged `github-actions success` status onto it, flipping its `deployable?` state and, since the affected stack is a production environment, triggering `Hook.emit(:deployable_status, ...)` and `stack.schedule_merges` for continuous delivery.

No existing guard closes this gap: `verify_signature` authenticates the *sender org*, not the *target stack*; `ExplicitParameters` only validates payload shape (`sha`, `state`, `context` are simple strings); there is no `Repository`/`Stack` scoping anywhere in the query.

### Impact Explanation
A payload authenticated for one repository mutates another repository's stack/commit state — this is squarely the "payload for one repository mutating another's stack/commit" Critical category. Concretely: the attacker forces a required `github-actions` context to `success` on a commit in a victim's **production** stack they do not control, which can flip `deployable?` to true and, with continuous deployment enabled, trigger an unauthorized production deploy of attacker-influenced state, or unblock a merge/rollback decision that depended on that status. This is repeatable against any SHA the attacker can learn (commit SHAs are typically visible via the Shipit UI, GitHub, or PR pages) and against any stack reachable from an org where the attacker controls at least one enrolled repository.

### Likelihood Explanation
Preconditions: the attacker needs write/Actions access to at least one repository whose GitHub App installation/webhook secret is shared with (or organization matches) the victim's Shipit-monitored organization — a common multi-repo/multi-team setup. They need to know the target SHA (readily discoverable). No Shipit credentials, session, or GitHub App private key are required; the entire exploit is executed through GitHub's public Statuses API plus GitHub's normal webhook delivery, with zero interaction with Shipit's admin/API surface. Cost is a single API call; the flaw is deterministic and repeatable against arbitrary target SHAs/stacks.

### Recommendation
Scope the commit lookup in `StatusHandler#process` (and equivalently in the check-run handler) to the repository that authenticated the webhook, e.g. join through `stack: :repository` and filter by `github_repo_name`/`repository.full_name` derived from `params.dig('repository','full_name')`, rejecting or ignoring statuses whose payload repository does not match the commit's owning stack repository.

### Proof of Concept
minitest plan (in `test/models/webhooks/status_handler_test.rb`, no live GitHub required):
1. Create two `Stack`s with different `Repository` records (`repo-a/attacker`, `repo-b/victim`), the victim stack configured with `environment: "production"` and `required_status_contexts` including `github-actions`.
2. Create `Commit` rows with the **same** `sha` value, one belonging to each stack (`commit_attacker.stack == stack_a`, `commit_victim.stack == stack_b`).
3. Assert baseline: `commit_victim.deployable?` is `false` (no successful status yet).
4. Build a `status` payload: `{ sha: <shared_sha>, state: "success", context: "github-actions" }`, and invoke `Shipit::Webhooks::Handlers::StatusHandler.new.process` (or call through the handler as the controller would after signature verification, using `stack_a`'s org for signing context) — i.e., simulate that the webhook was authenticated only for `repo-a/attacker`.
5. Assert `commit_victim.reload.deployable?` is now `true` and `commit_victim.statuses.last.context == "github-actions"` and `.state == "success"`, proving that a status authenticated for `repo-a` mutated `repo-b`'s (production) commit — the binding `payload.repository == commit.stack.repository` fails to hold, confirming the vulnerability.
