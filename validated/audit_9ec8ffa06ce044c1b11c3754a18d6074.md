### Title
Uncaught exception (crash) in c-hash validation on malformed address/asset chash - (File: chash.js)

### Summary
`chash.js`'s `isChashValid()` only wraps the base32/base64 *decoding* step in a `try/catch`. The subsequent bit-length re-partitioning step, `separateIntoCleanDataAndChecksum()`, is called **outside** that try/catch and unconditionally `throw`s an `Error` if the decoded buffer's bit-length is not exactly 160 or 288. This mirrors the root cause of CVE-2017-15019 (LAME): an insufficiently-validated, attacker-supplied length value drives a downstream code path that was never hardened against the "wrong length" case, producing an unhandled crash instead of a graceful rejection.

### Finding Description
`isChashValid()` in [1](#0-0)  performs:
1. length check on the encoded string (32 or 48 chars),
2. `base32.decode()` / `Buffer.from(..., 'base64')` wrapped in `try/catch` — decode failures are caught and return `false`,
3. `buffer2bin(chash)` then `separateIntoCleanDataAndChecksum(binChash)` — **not** wrapped in try/catch.

`separateIntoCleanDataAndChecksum()` [2](#0-1)  throws a bare `Error("bad length=...")` whenever the decoded bit-length isn't exactly 160 or 288. Because the outer `isStringOfLength()` check in `isValidChash()` only constrains the *encoded string* length (32 or 48 characters) [3](#0-2) , it does not guarantee that the *decoded byte length* will be the expected 20 or 36 bytes — that depends entirely on the base32 decoder's behavior for non-canonical inputs (e.g. characters outside the strict `[A-Z2-7]` set, since `isValidAddressAnyCase()` performs no charset regex, unlike `isValidAddress()`) [4](#0-3) . Any mismatch between the assumed and actual decoded length causes an uncaught `Error` to propagate out of `isChashValid()`.

This function is the sole primitive backing address/asset chash validity checks throughout the codebase: `isValidChash`, `isValidAddressAnyCase`, `isValidAddress`, and `isValidDeviceAddress` all funnel through it [5](#0-4) . These are used pervasively during unit validation (author addresses, payment output addresses, definition-address checks, asset issuer/definer addresses, device addresses in pairing/private-payment messages) — all values that are directly attacker-controlled in a posted unit, AA definition, or device message.

### Impact Explanation
An uncaught synchronous exception thrown mid-way through address/chash validation of an incoming unit or message can abort the enclosing validation flow unexpectedly rather than cleanly rejecting the malformed input, since only the outer decode step was defensively coded. Depending on where in the call stack this fires (unit content validation, AA trigger validation, device pairing/private-payment handling), this can manifest as a node crash or an inconsistent validation outcome between differently-patched nodes (some paths may have added try/catch elsewhere, others not), risking node disagreement on unit validity — the class of impact this scan requires. This is reachable by any unprivileged unit poster, AA trigger sender, asset issuer, or paired device, by supplying a crafted 32- or 48-character chash string with non-canonical characters/padding that decodes to a byte length other than 20 or 36 bytes.

### Likelihood Explanation
Likelihood is High for triggering the exception itself (constructing a 32-character string that base32-decodes to something other than 20 bytes is straightforward, especially since `isValidAddressAnyCase` has no character-class restriction). Certainty about the ultimate network-wide impact (crash vs. clean rejection) is Medium, because I could not fully verify from the indexed code whether every call site of `isValidChash`/`isValidAddressAnyCase` is itself wrapped in an outer try/catch that would contain the exception (I was not able to inspect the `thirty-two` package internals or exhaustively trace every caller within the remaining tool budget).

### Recommendation
Wrap the entire body of `isChashValid()` — including `buffer2bin`, `separateIntoCleanDataAndChecksum`, and `getChecksum` calls — in a single `try/catch` that returns `false` on any thrown error, so malformed chash input is always treated as "invalid" rather than propagating an exception. Additionally, add an explicit charset check (`/^[A-Z2-7]+$/`) to `isValidChash`/`isValidAddressAnyCase` before calling `chash.isChashValid`, matching the stricter behavior already present in `isValidAddress`.

function isChashValid(encoded){
	var encoded_len = encoded.length;
	if (encoded_len !== 32 && encoded_len !== 48) // 160/5 = 32, 288/6 = 48
		throw Error("wrong encoded length: "+encoded_len);
	try{
		var chash = (encoded_len === 32) ? base32.decode(encoded) : Buffer.from(encoded, 'base64');
	}
	catch(e){
		console.log(e);
		return false;
	}
	var binChash = buffer2bin(chash);
	var separated = separateIntoCleanDataAndChecksum(binChash);
	var clean_data = bin2buffer(separated.clean_data);
	//console.log("clean data", clean_data);
	var checksum = bin2buffer(separated.checksum);
	//console.log(checksum);
	//console.log(getChecksum(clean_data));
	return checksum.equals(getChecksum(clean_data));
}

function isValidChash(str, len){
	return (isStringOfLength(str, len) && chash.isChashValid(str));
}

function isValidAddressAnyCase(address){
	return isValidChash(address, 32);
}

function isValidAddress(address){
	return (typeof address === "string" && /^[A-Z2-7]{32}$/.test(address) && isValidChash(address, 32));
}

function isValidDeviceAddress(address){
	return ( isStringOfLength(address, 33) && address[0] === '0' && isValidAddress(address.substr(1)) );
