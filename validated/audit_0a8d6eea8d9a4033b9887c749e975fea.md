### Title
Accrued RAY value overflow permanently freezes an oversized market - (File: common/src/rates/simulate.rs)

### Summary
A market whose scaled debt or supply value grows beyond `i128::MAX` cannot be accrued. The permissionless `update_indexes` path, and every subsequent market-mutating operation, panics before updating `last_timestamp`, permanently freezing repayments, withdrawals, liquidation, recapitalization, and revenue processing for that market. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`accrue_step` computes `borrowed * borrow_index` and `supplied * supply_index` through `scaled_to_original`. [4](#0-3)  `scaled_to_original` delegates to `Ray::mul`, which panics with `MathOverflow` when the correctly widened `I256` result cannot be represented as `i128`. [5](#0-4) [6](#0-5) [7](#0-6) 

This check happens before `update_borrow_index` can clamp the index to `MAX_BORROW_INDEX_RAY`. [8](#0-7)  Consequently, valid scaled balances and a bounded index can still overflow the market's accrued value. `global_sync` runs this accrual before every pool mutation and updates `last_timestamp` only after all chunks complete. [2](#0-1)  The overflow therefore reverts without advancing accrual state, so all later calls repeat the same failing calculation.

The reachable path is:

`controller.update_indexes(caller, [hub_asset])` → `pool.update_indexes` → `ops::market::accrue` → `interest::global_sync` → `accrue_step` → `scaled_to_original`.

`controller.update_indexes` requires only caller authorization and no privileged role. [9](#0-8) [10](#0-9) [11](#0-10) [12](#0-11) 

### Impact Explanation
This can permanently freeze all user funds associated with the affected market. Repayment and withdrawal call the shared synced-market path, which accrues before mutation. [13](#0-12)  Liquidation also cannot execute because it repays or withdraws through the same pool paths.

The repository's own regression test demonstrates the terminal state: after accrual reaches the RAY-value ceiling, `update_indexes`, `withdraw`, and `repay` all revert with `MathOverflow`, and `clean_bad_debt`/liquidation remain unavailable because they accrue first. [14](#0-13)  The state cannot recover through ordinary unprivileged calls; changing the rate model also accrues first, leaving only governance/administrative intervention or upgrade as possible recovery paths. [15](#0-14) 

### Likelihood Explanation
The condition requires a very large listed market: approximately 1 billion whole tokens at 18 decimals at high utilization in the demonstrated scenario. Nevertheless, both the token-to-RAY and market-cap domains admit sizes near this scale, and normal interest accrual can move an initially valid market across the boundary without further privileged action. [16](#0-15) [17](#0-16) 

The triggering call itself is permissionless: once the market reaches the boundary, any caller can submit `update_indexes`. The impact is permanent freezing of substantial deposits and debt settlement, but exploitation depends on a large market and sustained accrual conditions, making the severity Medium rather than High.

### Recommendation
Make accrued market totals saturating or wider-domain-aware instead of reverting inside utilization calculation. For example:

- compute utilization from widened `I256` totals and saturate utilization at `RAY`;
- cap `borrowed_original` and `supplied_original` at `i128::MAX` before calling `scaled_to_original`; or
- add a stored “value-scale ceiling reached” state that freezes new interest while still allowing repayment, withdrawal, liquidation, and bad-debt cleanup.

At minimum, cap the debt and supply values used for utilization/rate calculation without preventing position unscaling where possible, and add a regression test proving `update_indexes`, `repay`, `withdraw`, liquidation, and `recapitalize` remain executable after a market crosses the value ceiling.

### Proof of Concept
The existing harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` demonstrates the issue with unprivileged operations:

1. Create an 18-decimal market with a steep rate curve and raised caps.
2. Supply `1_000_000_000 * 10^18` base units.
3. Supply collateral in another market and borrow 98% of the large market.
4. Advance ledger time yearly and repeatedly call:
   ```text
   update_indexes(caller, [HubAssetKey { hub_id, asset: BIG18 }])
   ```
5. Once `borrowed * borrow_index` exceeds `i128::MAX`, `update_indexes` reverts with `MathOverflow`.
6. Subsequent `withdraw` and `repay` calls revert with the same error because they run `global_sync` before applying the operation. [18](#0-17)

```rust
pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
```

```rust
/// Computes `x * y / d` rounded half up. Requires `x >= 0`, `y >= 0`, and `d > 0`; a
/// `debug_assert` checks this in debug builds. Panics with `GenericError::DivisionByZero` if
/// `d == 0`, and with `GenericError::MathOverflow` if any other precondition is violated or if
/// the result does not fit in `i128`.
pub fn mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> i128 {
    // The zero check runs first so debug and release builds agree on a zero
    // divisor: both surface `DivisionByZero` rather than tripping the assert.

    );
    try_mul_div_half_up(env, x, y, d)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow))
}
```

```rust
/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```
