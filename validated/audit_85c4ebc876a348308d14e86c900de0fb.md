No vulnerability found for this question.

**Rationale:** The `signer` type in Move cannot be forged by arbitrary/unprivileged code. The only way to obtain a `signer` for an address is either (1) the VM constructing root/secondary signers strictly from the authenticated transaction sender(s) during prologue execution, or (2) the `create_signer::create_signer` native, which is `public(friend)` and restricted to an explicit allow-list of framework modules (`account`, `aptos_account`, `coin`, `fungible_asset`, `genesis`, `account_abstraction`, `multisig_account`, `object`, `reconfiguration_with_dkg`, `transaction_validation`, `stake`, `init`) [1](#0-0) . There is no entry point reachable by an unprivileged transaction sender that lets them invoke this native with an arbitrary address like `@aptos_framework`, since Move's bytecode verifier enforces `friend`/visibility rules at module load/verification time, not at runtime — an attacker cannot simply "pass a signer" for `@aptos_framework` from a user transaction.

`system_addresses::assert_aptos_framework` itself is a correct, narrow check: it only compares `signer::address_of(account) == @aptos_framework` [2](#0-1) , and its formal spec confirms the abort condition is exactly `signer::address_of(account) != @aptos_framework` [3](#0-2) . Since a caller cannot obtain a genuine `signer` bound to `@aptos_framework` without going through genesis (where the VM constructs it directly) or through the friend-restricted native, there's no way for the check itself to be bypassed by unprivileged input. All call sites relying on `assert_aptos_framework` (e.g. `account::initialize`, `timestamp::set_time_has_started`, `transaction_validation::initialize`, `keyless_account` config setters, `confidential_asset` config setters) are equally protected by this same invariant [4](#0-3) [5](#0-4) [6](#0-5) .

At the native/VM layer, `native_create_signer` in Rust simply wraps the address argument popped off the Move stack into a `Value::master_signer` [7](#0-6) , but this native is only invocable from Move bytecode that has passed the friend-visibility check during verification — it is not exposed to arbitrary transaction payloads, scripts, or entry functions callable by unprivileged senders.

This maps to a well-established Move language security property (signer unforgeability), not a bug in this repository's admission path. There is no unprivileged transaction, REST/BCS input, or authenticator path shown or found that produces a spoofed `@aptos_framework` signer outside genesis/friend-restricted execution, so this does not meet the Admission Impact Gate criteria.

pub(crate) fn native_create_signer(
    context: &mut SafeNativeContext,
    ty_args: &[Type],
    mut arguments: VecDeque<Value>,
) -> SafeNativeResult<SmallVec<[Value; 1]>> {
    debug_assert!(ty_args.is_empty());
    debug_assert!(arguments.len() == 1);

    context.charge(ACCOUNT_CREATE_SIGNER_BASE)?;

    let address = safely_pop_arg!(arguments, AccountAddress);
    Ok(smallvec![Value::master_signer(address)])
}
