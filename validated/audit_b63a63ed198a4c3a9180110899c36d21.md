### Title
Unconstrained path traversal via `inherit_from` in `DeploySpec::FileSystem#build_config` allows reading files outside the repo checkout - ([File: app/models/shipit/deploy_spec/file_system.rb])

### Summary
`build_config` resolves the `inherit_from` value with `path.dirname.join(...)` and only checks `.exist?` before calling `read_config`, without verifying the resulting path stays inside `@app_dir` (the checkout root for that stack/ref). Because `shipit.yml` is fully attacker-controlled content on any branch/PR that becomes a stack checkout, an attacker can supply `inherit_from: '../../../../some/host/path.yml'` and have `SafeYAML.load` read and deep-merge a file located outside the intended checkout directory into the deploy spec.

### Finding Description
The claimed binding is: `inherits_from_path` (`path.dirname.join(config_obj.delete(SHIPIT_CONFIG_INHERIT_FROM_KEY))`) should always satisfy `inherits_from_path.to_s.start_with?(@app_dir.to_s)`. It does not — no such check exists.

Code path: `load_config` (app/models/shipit/deploy_spec/file_system.rb:98-107) reads the primary `shipit.yml` found via `config_file_path` (which is always confined to `@app_dir`/`directory`, `file_system.rb:135-142`), then calls `build_config(config_file_path, config_obj)`. In `build_config` (`file_system.rb:149-160`): [1](#0-0) 
`path.dirname.join(...)` performs pure lexical concatenation (Pathname#join does not strip `..` segments), and `.exist?`/`Pathname#read` are then resolved by the OS, which does honor `..` traversal up past the checkout root. Since `read_config` merely does `SafeYAML.load(path.read) if path.exist?` with no containment check, any `..`-laden value in `inherit_from` that lands on a real, readable file on the Shipit host is loaded and `deep_merge`d into the effective deploy spec (`config_obj = inherits_config_obj.deep_merge(config_obj)`).

Attacker request: push a branch (or open a PR that spawns a review stack) whose `shipit.yml` contains:
```yaml
inherit_from: '../../../../../../etc/some_readable_config.yml'
```
When Shipit builds the deploy spec for that stack/commit (`StackCommands#build_cacheable_deploy_spec`, `TaskCommands#deploy_spec`), `build_config` will attempt to read the traversal target from the actual git checkout on disk.

Existing guards (`verify_signature`, `ExplicitParameters`, `force_github_authentication`, `Repository`/`Stack` validators, `EnvironmentVariables#permit`) are irrelevant here because the trigger is the *content* of a file inside the attacker's own repository checkout, not an HTTP parameter — none of the listed webhook/API guards inspect `shipit.yml` contents, and no path-containment check exists in `build_config`/`read_config`.

### Impact Explanation
Successful traversal lets `SafeYAML.load` parse an arbitrary file on the Shipit worker filesystem that is readable by the app process (e.g., another stack's checkout under a sibling `deploys_path`/`git_path`, or a Rails config file), provided that file happens to parse into a Hash so `deep_merge` succeeds. If that content is a Hash, its keys not overridden by the attacker's own top-level `shipit.yml` bleed through into the effective deploy spec (e.g., `machine.environment`, `deploy.override`, `deploy.variables`), which is subsequently merged into the environment passed to `Command`/`PTY.spawn` (`lib/shipit/task_commands.rb:33-48`) and streamed to task output that the attacker can view for their own stack/review-stack deploy. This is a credential/config exfiltration primitive matching the "deploy-time secrets"/config exfiltration Critical category, scoped to whatever the attacker can craft their own deploy steps to echo from the merged config.

I could not confirm within the available context a concrete, guaranteed-to-be-Hash-shaped secret file at a fixed, predictable path reachable from every checkout (this depends on host directory layout, e.g. `Shipit.checkouts_path`/`deploys_path` structure and permissions), so exploitability against a specific named secret is host-configuration-dependent rather than universally guaranteed. The vulnerable code path itself is confirmed and reproducible without any live GitHub calls.

### Likelihood Explanation
Preconditions: attacker needs a branch/PR that becomes a Shipit stack or review-stack checkout (no Shipit session/token/team membership required, only push/PR ability on a tracked repo). Cost is a single crafted `shipit.yml` commit. The traversal itself (reaching arbitrary readable files) is trivially reproducible; turning that into secret exfiltration additionally requires the target file to be Hash-shaped YAML and knowledge/guessing of its host path, which raises real-world likelihood from "trivial" to "moderate, environment-dependent."

### Recommendation
In `build_config`, after resolving `inherits_from_path`, canonicalize it (`.expand_path` / `.realpath`) and assert it is still a descendant of `@app_dir` (e.g., `inherits_from_path.expand_path.to_s.start_with?("#{@app_dir.expand_path}/")`) before calling `read_config`; otherwise raise/skip inheritance. Apply the same containment check to `config_file_path`/`file` resolution paths for defense in depth.

### Proof of Concept
```ruby
# test/models/shipit/deploy_spec/file_system_test.rb
test '#build_config refuses to inherit from a path outside the checkout root' do
  Dir.mktmpdir do |app_dir|
    stack = shipit_stacks(:shipit)
    deploy_spec = Shipit::DeploySpec::FileSystem.new(app_dir, stack)

    outside_secret = Tempfile.new(['secrets', '.yml'])
    outside_secret.write("deploy:\n  override:\n    - 'cat /etc/shadow'\n")
    outside_secret.flush

    traversal = Pathname.new(app_dir).join('shipit.yml')
    relative_traversal = traversal.dirname.relative_path_from(Pathname.new('/')).to_s
    inherit_value = ('../' * (relative_traversal.split('/').size + 2)) + outside_secret.path.sub(%r{\A/}, '')

    config_obj = { 'inherit_from' => inherit_value }

    result = deploy_spec.send(:build_config, traversal, config_obj)

    # Binding under test: resolved inherits_from_path must stay inside app_dir
    refute result.dig('deploy', 'override')&.include?('cat /etc/shadow'),
      "build_config must not merge content read from outside @app_dir (#{app_dir})"
  end
end
```
This asserts that content from a file resolved outside `@app_dir` via `..` traversal is never merged into the effective deploy spec.

```ruby
      SHIPIT_CONFIG_INHERIT_FROM_KEY = "inherit_from"
      def build_config(path, config_obj)
        return config_obj if config_obj.blank? || !config_obj.key?(SHIPIT_CONFIG_INHERIT_FROM_KEY)

        inherits_from_path = path.dirname.join(config_obj.delete(SHIPIT_CONFIG_INHERIT_FROM_KEY))
        if inherits_from_path.exist?
          inherits_config_obj = read_config(inherits_from_path)
          config_obj = inherits_config_obj.deep_merge(config_obj)
          path = inherits_from_path
        end

        build_config(path, config_obj)
      end

      def read_config(path)
        SafeYAML.load(path.read) if path.exist?
      end
```
