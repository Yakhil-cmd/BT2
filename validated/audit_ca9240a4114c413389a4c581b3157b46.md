### Title
Webhook Signature Verification Bypass via Unauthenticated Organization Selection When `webhook_secret` Is Unset - ([File: `app/controllers/shipit/webhooks_controller.rb`], [File: `lib/shipit/github_app.rb`])

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and therefore which `webhook_secret`) to verify a webhook against by reading an **unauthenticated field from the request body itself** (`repository.owner.login` / `organization.login`), before any cryptographic check has taken place. `GitHubApp#verify_webhook_signature` then unconditionally returns `true` whenever the selected app's `webhook_secret` is blank. Because Shipit explicitly supports multi-organization configuration where each org has an independently optional `webhook_secret` [1](#0-0) , any organization configured without a secret becomes a completely open relay: an unprivileged attacker can POST a forged payload claiming to belong to that organization and have it processed as a genuine GitHub event, with no signature validation performed at all.

### Finding Description
`verify_signature` derives the verification key from data inside the very payload it is about to check: [2](#0-1) [3](#0-2) 

`GitHubApp#verify_webhook_signature` treats an absent secret as automatic success: [4](#0-3) 

The binding that should hold is:
`organization whose GitHub App cryptographically authenticated the request == organization whose repository/stack state is written by the handler`

Because the organization used to *select the verification key* is itself untrusted attacker input, and because `verify_webhook_signature` degrades to `return true unless webhook_secret`, this equality breaks for any org configured without a `webhook_secret`: the "authenticated organization" side becomes vacuously true (no cryptographic check occurred), while the "repository that is written" side is fully attacker-controlled through `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [5](#0-4) .

Before the pull request/config state: a request whose claimed organization has a `webhook_secret` set is rejected unless it carries a valid HMAC (`SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(...))`) [4](#0-3) .

After: for any organization whose `webhook_secret` config key is omitted (a documented, supported, optional setting) [1](#0-0) , `verified` is `true` regardless of the `X-Hub-Signature` header content, and the handler dispatch proceeds unauthenticated [2](#0-1) .

### Impact Explanation
An unauthenticated internet client can forge `membership`, `push`, `status`, and `check_suite` webhook events for any stack belonging to an org with no `webhook_secret` configured. The `membership` handler mutates `Team`/`Membership` records tied to `Shipit.github_teams` authorization [6](#0-5) ; a forged `push` event enqueues `GithubSyncJob` which drives deploy/merge pipeline state [7](#0-6) ; a forged `status` event fabricates commit statuses used to gate merges [8](#0-7) . This reaches the report's required Critical/High bar: escalation into `Shipit.github_teams` authorization and unauthorized deploy/merge state manipulation, achieved without any Shipit session, `ApiClient` token, or GitHub credentials.

### Likelihood Explanation
Requires only that at least one configured GitHub organization omit the optional `webhook_secret` value — an explicitly documented, non-privileged configuration choice, not a deviation from documented mounting/setup. Any attacker who knows (or guesses) that organization's login and a targeted repo name can send unsigned/arbitrary-signed POSTs to the public `/webhooks` endpoint.

### Recommendation
Never let `verify_webhook_signature` short-circuit to `true` when `webhook_secret` is blank — require an operator-set secret for every configured organization, or reject webhooks outright for orgs without one. Additionally, the organization used to select the verification key should not be trusted before the signature check succeeds; consider verifying against all configured secrets or binding the app selection to server-side configuration rather than attacker-supplied payload fields.

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.yml`: `org-a` (has `webhook_secret`) and `org-b` (no `webhook_secret` set) [1](#0-0) .
2. As an unauthenticated attacker, POST to `/webhooks` with header `X-Github-Event: membership` and body:
   ```json
   {"action":"added","team":{"id":<target_team_id>,"slug":"developers","name":"Developers","url":"https://example.com"},
    "organization":{"login":"org-b"},"member":{"login":"attacker-login"},
    "repository":{"owner":{"login":"org-b"}}}
   ```
   with an arbitrary/garbage `X-Hub-Signature` header.
3. `repository_owner` resolves to `org-b`; `Shipit.github(organization: "org-b").verify_webhook_signature` returns `true` immediately because `org-b`'s `webhook_secret` is blank [4](#0-3) .
4. The `membership` handler processes the forged payload and adds `attacker-login` to the `developers` team, as demonstrated by the equivalent legitimate test path [9](#0-8) , granting the attacker whatever authorization `Shipit.github_teams` maps to that team — without ever authenticating to GitHub or Shipit.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
