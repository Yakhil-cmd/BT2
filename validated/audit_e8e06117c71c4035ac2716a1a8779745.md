### Title
Disabled unidirectional-trust check for indirect correspondents in device-message handling — (File: `wallet.js`)

### Summary
`handleMessageFromHub()` in `wallet.js` used to restrict which message `subject`s an "indirect correspondent" (a paired device introduced only indirectly, e.g. through a shared-address/wallet-creation flow, rather than a device that was directly paired by the user) could send. That restriction is now fully commented out, so any subject — including privileged ones such as `sign`, `removed_paired_device`, `create_new_wallet`, `approve_new_shared_address`, `new_shared_address`, `private_payments`, etc. — is now processed from an indirect correspondent exactly as if it came from a directly-trusted device.

### Finding Description
The dropped check is: [1](#0-0) 

`bIndirectCorrespondent` is derived from the `is_indirect` flag stored in `correspondent_devices`, and is passed through from the hub message-receiving path in `device.js`: [2](#0-1) 

Before the fix was reverted/commented, only `["cancel_new_wallet", "my_xpubkey", "new_wallet_address"]` were meant to be trusted from a correspondent that was only indirectly introduced (never explicitly paired/verified by the local user). With the check disabled, every other subject handled in the giant `switch` — including `sign` (co-signing requests for shared/multisig addresses), `removed_paired_device` (which can blackhole/unpair a correspondent), `create_new_wallet`/`new_shared_address`/`approve_new_shared_address` (multi-device wallet and shared-address creation), and `private_payments` — is now reachable from an indirect correspondent with no additional gating: [3](#0-2) [4](#0-3) 

This is structurally the same bug class as CVE-2019-15149: a defense-in-depth trust-boundary check (limiting what an indirectly-reachable peer is allowed to originate) was dropped, silently widening the set of privileged operations reachable from a less-trusted party, even though downstream handlers still perform their own checks.

### Impact Explanation
For multi-device or shared-address (multisig) wallets, this removes the layer meant to prevent an indirectly-introduced device from initiating co-signing requests (`sign`) or shared-address/wallet flows (`create_new_wallet`, `new_shared_address`, `approve_new_shared_address`) that were previously reserved for directly-paired, user-verified correspondents. In setups where a wallet acts as an automated/semi-automated co-signer (e.g. server-side multisig cosigner, bot), this widens the attack surface for tricking that co-signer into processing/approving spend requests it should never have accepted from an unverified device, i.e. a path toward unauthorized spending from shared addresses. It also allows an indirect correspondent to request `removed_paired_device`, undermining the correspondent trust list integrity.

### Likelihood Explanation
Exploitability depends on additional factors — most importantly, whether the specific deployment has an automated component that acts on `sign`/shared-address events without a human confirming via UI (the plain reference-wallet UI still shows a confirmation dialog for `signing_request`). This mirrors the CVE's own dispute note that the underlying bug is "exploitable only in conjunction with hypothetical other factors" — here, an automated or lightly-supervised co-signing/wallet-management setup. On interactive wallets requiring explicit user approval for signing, the immediate risk is lower but the trust-boundary regression is real and applies to every "indirect correspondent" subject, not just `sign`.

### Recommendation
Restore (uncomment) the subject whitelist check for indirect correspondents in `wallet.js`, so that only the originally intended safe subjects (`cancel_new_wallet`, `my_xpubkey`, `new_wallet_address`) — or a properly re-audited list — are accepted from devices marked `is_indirect`. Audit all `switch` cases in `handleMessageFromHub` to confirm each one is safe to receive from an unverified/indirectly-introduced device before re-enabling broader access, particularly `sign`, `removed_paired_device`, and shared-address/wallet creation flows.

### Proof of Concept
1. Device A introduces device C to device B only indirectly (e.g., through a shared-address/group-wallet flow), so `correspondent_devices.is_indirect = 1` for C on B's side, per `device.js` handling of correspondents.
2. Device C sends a `hub/message` (via `network.js` `hub/deliver`) with `subject: "sign"` (or `removed_paired_device`, `create_new_wallet`, etc.) addressed to B.
3. Because the guard at `wallet.js:92-93` is commented out, B's `handleMessageFromHub` processes the message identically to a directly-trusted correspondent, dispatching it to `findAddress(...)`/`eventBus.emit("signing_request", ...)` or other privileged handlers instead of rejecting it with "you're indirect correspondent, cannot trust ...".
4. If B runs any automated co-signing logic (or a user habitually approves signing prompts without verifying the requester), C can obtain B's signature over multisig transactions it should never have been allowed to request.
