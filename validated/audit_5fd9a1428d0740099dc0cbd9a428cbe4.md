### Title
Asset definer can arbitrarily replace `spender_attested` attestor list, permanently freezing holders' funds - (File: `validation.js`)

### Summary
### Finding Description
For assets with `spender_attested: true`, the definer publishes and can later update the list of trusted attestors via an `asset_attestors` message. Payment validation requires that at least one author of the spending unit is attested by the *current* attestor list, otherwise the payment fails with `"none of the authors is attested"` [1](#0-0) . The update itself, `validateAttestorListUpdate()`, only checks that the caller is the asset's definer and that the new list is non-empty, sorted, and made of valid addresses — it never checks whether any currently attested/holding address remains attestable, nor bounds how the list may change: [2](#0-1) .

This mirrors the reported UToton bug class exactly: a privileged, single actor (the `FixedInterestRateModel` owner in the C4 report; the asset *definer* here) can set a parameter (interest rate / attestor list) with no bound or consistency check, which is later consumed by a core validation routine (`accrueInterest`→`borrowRatePerBlock` / `validatePaymentInputsAndOutputs`→`filterAttestedAddresses`) that unconditionally reverts/fails once the parameter takes an "adversarial" value, disabling a fundamental user operation (repay / spend) that the user cannot bypass. Here the definer can publish a new attestor list that excludes every address currently holding units of the asset (including addresses that were previously attested and already received funds), instantly freezing every existing holder's ability to spend, and can later re-attest them (e.g. in exchange for a fee), exactly the adversarial "disable then re-enable for a price" pattern in the report.

### Impact Explanation
Once the definer updates the attestor list to a set that does not include the addresses holding balances of the asset, `filterAttestedAddresses()` returns zero matches, so any subsequent payment message spending that asset fails validation with `"none of the authors is attested"` (public payment `validatePayment`, line 2118) or `"some output addresses are not attested"` (payment attempted to non-attested recipients, line 2637), and this is enforced on every node identically, so it is not a mere soft/local reject — the asset becomes globally unspendable for the affected holders until the definer chooses to re-attest them. This is a deterministic loss of fund access for third-party asset holders caused solely by a single privileged party's action, matching Medium severity per the analog (temporary, reversible-at-will DoS on legitimate value transfer, exploitable adversarially).

### Likelihood Explanation
Any asset with `spender_attested: true` is affected as soon as the definer authors a single `asset_attestors` unit; no cooperation from holders is required and no additional preconditions exist beyond owning/definer authority over the asset, which is expected and common for compliance-style ("attested") assets. The action is a normal, always-available message type (`asset_attestors`), requiring no special mci/upgrade or race condition, so likelihood of a malicious or careless definer triggering it is high whenever such assets are used.

### Recommendation
Add safeguards to `validateAttestorListUpdate()` / `checkAttestorList()` analogous to the bounce-fee bound check pattern already used for `bounce_fees` (`fee > constants.MAX_CAP` check in `aa_validation.js` line 755). Concretely:
- Require attestor-list changes to preserve attestation continuity for addresses that already hold a nonzero balance of the asset (e.g., disallow removing all attestors that currently attest any existing holder in one update, or add a timelock/notice period before a new list takes effect), and/or
- Document explicitly in `IInterestRateModel`-style specs (asset spec docs) that `spender_attested` gives the definer unilateral power to freeze holder funds, so wallets/dApps can warn users before accepting such assets.

### Proof of Concept
1. Definer issues asset `A` with `spender_attested: true` and attestor list `[X]`.
2. Attestor `X` attests holder address `H`; `H` receives/holds units of `A` and can freely spend them (passes the `arrAttestedAddresses` check in `validatePayment`, `validation.js:2115-2121`).
3. Definer submits an `asset_attestors` message replacing the list with `[Y]` (a different attestor who has not attested `H`). This passes `validateAttestorListUpdate` because it only checks non-empty/sorted/valid addresses (`validation.js:2829-2864`).
4. `H` now attempts to spend `A`: `filterAttestedAddresses` finds no match for `H` against the new attestor list, and `validatePayment` returns `"none of the authors is attested"` (`validation.js:2118-2119`), rejecting the unit on every node.
5. `H`'s funds in asset `A` are frozen until the definer chooses to restore/expand the attestor list to re-attest `H` (which the definer could condition on payment or other demands), replicating the "disable-then-monetize" scenario from the original report.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}

function checkAttestorList(arrAttestors){
	if (!isNonemptyArray(arrAttestors))
		return "attestors not defined";
	if (arrAttestors.length > constants.MAX_ATTESTORS_PER_ASSET)
		return "too many attestors";
	var prev="";
	for (var i=0; i<arrAttestors.length; i++){
		if (!isValidAddress(arrAttestors[i]))
			return "invalid attestor address: "+JSON.stringify(arrAttestors[i]);
		if (arrAttestors[i] <= prev)
			return "attestors not sorted";
		prev = arrAttestors[i];
	}
	return null;
}
