### Title
AA can define an `asset` message with `spender_attested=true` but no `attestors`, causing an uncaught `throw Error` (node crash / DoS) when the asset is later spent - ([File: storage.js])

### Summary
`aa_validation.js` validates AA-issued `asset` messages but, unlike the equivalent path for ordinary (non-AA) asset definitions, does not require an `attestors` list when `spender_attested` is `true`. An AA can therefore post (or an AA author/trigger sender can cause an AA to emit) an `asset` message with `spender_attested: true` and no `attestors` field. This passes AA definition/message validation and gets written to the database without any `asset_attestors` row. Any later attempt by any node to validate a payment spending that asset calls `storage.readAsset()` → `addAttestorsIfNecessary()`, which unconditionally `throw`s an uncaught `Error("no latest attestor list")` (or `"no attestors?"`) inside an asynchronous DB-query callback, crashing the node process. This is analogous to CVE-2021-41865: an incomplete specification submitted by an ordinary, authenticated actor (an AA definition/trigger poster) that is accepted by validation but causes an unhandled failure/crash when a downstream feature combination (asset spending) is exercised, resulting in denial of service for every node that processes the spending unit.

### Finding Description
For a regular (non-AA), user-submitted asset definition, `validateAssetDefinition` in `validation.js` enforces that if `spender_attested` is true, an `attestors` list must be supplied: [1](#0-0) 

However, the equivalent validator for AA-defined assets, in `aa_validation.js`'s `case 'asset':`, only checks the *type* of `spender_attested` (boolean or formula), and only validates the format of `attestors` *if the field happens to be present* — it never requires `attestors` to exist when `spender_attested` is (or evaluates to) `true`: [2](#0-1) 

When such an AA definition is triggered and executes an `asset` message with `spender_attested=true` and no `attestors`, `writer.js` writes the asset row but skips inserting any `asset_attestors` rows because `asset.attestors` is undefined: [3](#0-2) 

Later, when any unit (from any user) spends this asset, validation calls `storage.readAsset()`, whose `addAttestorsIfNecessary()` helper assumes that if `spender_attested` is true there must be at least one prior `asset_attestors` list, and `throw`s an uncaught exception otherwise, inside a nested asynchronous DB query callback that has no surrounding `try/catch`: [4](#0-3) 

Because this `throw` occurs inside an async callback chain (`conn.query(...)`), it is not caught by the caller's error-handling logic and will propagate as an unhandled exception, crashing the Node.js process on every full node (and light-serving/hub node) that validates the spending unit — a direct parallel to the Nomad bug where an incomplete job specification for a specific feature combination (Consul mesh gateway + host networking) passed submission-time validation but crashed the node when the feature was actually exercised.

### Impact Explanation
Any full node (and hubs performing full validation) that processes a payment spending the malformed asset will crash with an unhandled exception. Since asset spending units propagate across the network, this can be triggered repeatedly against every full node that receives the unit, amounting to a network-wide denial of service preventing confirmation of new units — one of the explicitly in-scope impacts (a network unable to confirm new units / node disagreement due to crash-vs-processing divergence). This qualifies as Medium/High severity per the same class as CVE-2021-41865 (CVSS 6.5, AV:N/AC:L/PR:L/UI:N/S:U/C:N/I:N/A:H).

### Likelihood Explanation
The attacker only needs the ability that any unprivileged unit poster already has: post a valid AA that emits an `asset` message with `spender_attested: true` and no `attestors` (this passes `aa_validation.js` cleanly since attestors is optional there), get the AA triggered, and then have anyone (including the attacker) submit a `payment` message spending that asset. No special privilege, hub cooperation, or malicious peer/node condition is required — it is purely a self-consistent misuse of already-accepted AA/asset semantics, matching the "incomplete specification submitted by an authorized actor" pattern of the CVE.

### Recommendation
- In `aa_validation.js`, mirror the check already present in `validation.js`'s `validateAssetDefinition`: when validating an AA `asset` message (and `asset_attestors` updates), require a non-empty `attestors` list (or formula) whenever `spender_attested` is `true` (or is a formula that could evaluate to true), for both the immediate value and inside `cases`.
- Defensively harden `storage.js`'s `addAttestorsIfNecessary()` to return a validation error to `handleAsset` callback instead of `throw`ing when no attestor list is found, so a malformed/legacy asset cannot crash the validating node; propagate this as a normal validation failure ("no attestors defined for spender_attested asset") instead of an unhandled exception.

### Proof of Concept
1. Deploy an AA whose `messages` include an `asset` message such as:
```
{
  app: 'asset',
  payload: {
    cap: 1000000,
    is_private: false,
    is_transferrable: true,
    auto_destroy: false,
    fixed_denominations: false,
    issued_by_definer_only: false,
    cosigned_by_definer: false,
    spender_attested: true
    // no "attestors" field
  }
}
```
This passes `aa_validation.js`'s `case 'asset':` checks because `attestors` is only validated `if ("attestors" in payload)`.
2. Trigger the AA so this asset gets defined; `writer.js` inserts the `assets` row but no `asset_attestors` row (since `asset.attestors` is falsy).
3. Have any user post a `payment` unit spending this new asset. Every node that validates this payment calls `storage.readAsset()` → `addAttestorsIfNecessary()`, finds `latest_rows.length === 0`, and executes `throw Error("no latest attestor list")` inside the query callback, crashing the validating node process.
