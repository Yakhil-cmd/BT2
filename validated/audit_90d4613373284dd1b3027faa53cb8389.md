### Title
Stack-scoped API token can read CI/deploy status of any stack via CCMenu endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` bypasses the token-scoping mechanism that every other stack-scoped API endpoint uses, letting an `ApiClient` token that is restricted to a single stack read the deploy/CI status of an arbitrary stack.

### Finding Description
`Shipit::Api::BaseController#stacks` is the intended scoping primitive: it restricts the set of stacks a request can touch to the one authorized for the presenting `ApiClient` when that client has a `stack_id` set: [1](#0-0) 

`Shipit::Api::StacksController#stack` correctly resolves the target stack through this scoped relation (`stacks.from_param!`): [2](#0-1) 

`Shipit::Api::CCMenuController`, however, defines its own `stack` helper that resolves directly against `Stack.from_param!(params[:stack_id])`, completely ignoring `current_api_client.stack_id`: [3](#0-2) 

The controller only enforces `require_permission :read, :stack` — a permission-name check performed by `ApiClient#check_permissions!`, which only checks the `permissions` array, never the `stack_id` scope: [4](#0-3) 

This means the binding "the stack a token is authorized for" (`current_api_client.stack_id`) is not equal to "the stack the CCMenu action actually touches" (`params[:stack_id]` resolved unscoped). Any client holding a scoped token with `read:stack` permission for stack A can query `GET /api/:stack_id/ccmenu.xml?token=...` with `stack_id` set to stack B and receive stack B's build/deploy status, name, and last build label.

### Impact Explanation
This is an authorization-scope bypass: a token deliberately restricted to a specific repository/stack (e.g. tokens minted by `CCMenuUrlController#client`, which creates `ApiClient.create_with(permissions: %w[read:stack])` tied to one stack) can be replayed against any other stack in the Shipit instance to read that stack's deploy status/CI state — an unauthenticated-for-that-resource read of stack state, matching the "High — unauthenticated read of stack state" impact category, achieved purely by crossing the stack-scope authorization boundary that every sibling controller (`StacksController`, `HooksController` via its `stack` delegate) respects.

### Likelihood Explanation
Likelihood is high: any holder of a legitimately-scoped, low-privilege (`read:stack` only) API token — for example a CCMenu URL shared with a CI dashboard — can trivially perform this by changing the `stack_id` path segment of the request. No additional secrets, sessions, or privileged access are required beyond a token that is already meant to be narrowly scoped.

### Recommendation
```diff
- def stack
-   @stack ||= Stack.from_param!(params[:stack_id])
- end
+ def stack
+   @stack ||= stacks.from_param!(params[:stack_id])
+ end
```
This routes `CCMenuController#stack` through `BaseController#stacks`, which already enforces `current_api_client.stack_id?` scoping, consistent with `StacksController`.

### Proof of Concept
1. Create (or obtain) a stack-scoped, `read:stack`-only `ApiClient` for stack A, e.g. via `POST /:stack_a_id/ccmenu_url` which internally calls `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator:, stack: stack_a, name: 'CCMenu Client')` (see `CCMenuUrlController#client`) — yielding `token_A` scoped to `stack_id: stack_a.id`.
2. Send `GET /api/:stack_b_id/ccmenu.xml?token=token_A` where `stack_b` is a different, unrelated stack.
3. `authenticate_api_client` (overridden in `CCMenuController`) authenticates `token_A` successfully via `ApiClient.authenticate`.
4. `require_permission :read, :stack` passes because `token_A` has `read:stack` in its `permissions` list (scope is not checked here).
5. `stack` resolves via `Stack.from_param!(params[:stack_id])` — unscoped — returning `stack_b` regardless of `token_A.stack_id == stack_a.id`.
6. The response renders `stack_b`'s name, activity, and last build status/label, which `token_A` was never authorized to access.
