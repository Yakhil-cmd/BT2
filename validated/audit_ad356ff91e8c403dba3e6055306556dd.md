## Title
Merkle proof verification in `merkle.js` is vulnerable to forgery via unbounded/mismatched proof length and index, analogous to `SSZ.restoreMerkleRoot` (File: `merkle.js`)

### Summary
The `merkle.verifyMerkleProof` function, used both by the `'in merkle'` address-definition operator and by the `is_valid_merkle_proof` oscript/AA function, reconstructs a Merkle root by iterating exactly `proof.siblings.length` times and choosing left/right concatenation order from `proof.index % 2` at each step, where **both `index` and `siblings` (including its length) are fully attacker-controlled**. This is the same class of bug as the reported `SSZ.restoreMerkleRoot` issue: the number of hashing rounds and the traversal direction are dictated by untrusted, unconstrained input rather than by a fixed/verified tree depth tied to a specific leaf position.

### Finding Description
`getMerkleRoot`/`getMerkleProof` build a Merkle tree using a single hash function for both leaves and internal nodes, with no domain separation (no leaf/node tag): [1](#0-0) 

`verifyMerkleProof` reconstructs the root purely from attacker-supplied `proof.index` and `proof.siblings`, looping for `proof.siblings.length` iterations and branching on `index % 2` at every step, with no check that `index` is within `[0, 2^siblings.length)` nor that `siblings.length` matches any real tree height: [2](#0-1) 

This is consumed in two attacker-reachable paths:
1. `'in merkle'` address-definition authentifier, where the proof is deserialized straight from the unit's `assocAuthentifiers[path]` (fully attacker-controlled), and the reconstructed `proof.root` is checked against a stored data feed value: [3](#0-2) 
2. `is_valid_merkle_proof(element, proof)` oscript/AA function, where **both** `element` and `proof` (including `siblings` and `index`) are evaluated from oscript expressions and can come directly from `trigger.data`, i.e. fully attacker-controlled at AA-trigger time. The only guard added is a cap of 50 siblings and a string-nonemptiness check — it does not validate that `index` corresponds to the claimed depth: [4](#0-3) 

Because leaves and internal nodes are hashed identically (`hash(concat(childA, childB))` for internal nodes vs. `hash(element)` for leaves), and because the verifier accepts *any* `index`/`siblings.length` combination without tying it to the real committed tree height, this is the classic "second preimage / variable-length branch" Merkle forgery: if an attacker learns two adjacent hash values from the real tree (e.g. two sibling leaf hashes revealed as part of any legitimate proof, or simply computable if the attacker owns/knows two adjacent leaves), they can submit a forged `element` string equal to the raw concatenation of those two hash values. `hash(element)` then equals exactly the internal node's hash that the real tree would have computed at the next level up. Supplying the correct remaining sibling path from that internal node to the root (which is identical to the genuine path, since it's a real subpath of the real tree) yields a `verifyMerkleProof` call that returns `true` for a value that was **never an actual leaf/element of the committed set**.

This mirrors the root cause described in the external report: the verifier's control flow (number of rounds, branch direction) is driven by untrusted `index`/proof-length rather than being bound to a canonical, checked tree position, letting an attacker present a proof for a fabricated "leaf" that actually corresponds to an internal tree node.

### Impact Explanation
Any AA that stores a Merkle root (e.g., a whitelist/airdrop root, an allowed-address set, an authorized-payment set) and gates fund release or address authorization using `is_valid_merkle_proof(trigger_supplied_element, trigger_supplied_proof)` can be tricked into accepting membership for a value that is not one of the originally committed elements. An attacker who colludes with, or is, the owner of two adjacent tree leaves can derive the corresponding internal-node hash and forge an additional "phantom member" proof, enabling unauthorized withdrawal of AA funds or unauthorized satisfaction of an address's `'in merkle'` authentication condition — a concrete unauthorized fund loss / access-control bypass.

### Likelihood Explanation
Exploitability requires only: (1) knowledge of two adjacent hash values within a real Merkle tree whose root is trusted by the AA/address definition (obtainable from any legitimate proof shared with/by the attacker, or from owning two adjacent leaves), and (2) the ability to submit an AA trigger or unit authentifier with attacker-chosen `element`/`proof` data — both are available to any unprivileged AA trigger sender or unit poster. No cryptographic breaking of SHA-256 is required, only the standard "unbounded/second-preimage" Merkle-proof flaw, making this a realistic Medium/High likelihood issue wherever `is_valid_merkle_proof` or `'in merkle'` is used to protect value.

### Recommendation
- Enforce a strict, canonical relationship between `proof.index` and `proof.siblings.length`: e.g., require `0 <= index < 2^siblings.length` and reject proofs whose length does not correspond to the actual/expected tree depth for the given index.
- Add domain-separated hashing: prefix leaf hashing and internal-node hashing with distinct tags (e.g., `hash(0x00 || element)` for leaves vs. `hash(0x01 || left || right)` for internal nodes) so a leaf hash can never collide with/impersonate an internal node hash.
- For `is_valid_merkle_proof`, validate that the supplied proof's implied tree height is consistent across all uses against the same root (or otherwise bind the proof length to a value that isn't purely attacker-chosen).

### Proof of Concept
1. Oracle/AA builds `arrElements = [e0, e1, e2, e3]` and posts `root = merkle.getMerkleRoot(arrElements)` as a trusted state root (data feed or AA state var) used to gate fund release via `is_valid_merkle_proof`.
2. Attacker, knowing `h0 = hash(e0)` and `h1 = hash(e1)` (e.g., because they legitimately own leaf `e0` and observed `e1`'s hash from any earlier valid proof), computes the internal node value `n01 = hash(h0 + h1)` — this is exactly what `getMerkleRoot` computes internally at level 1, index 0.
3. Attacker crafts a forged `element' = h0 + h1` (raw string concatenation) and a `proof' = { index: 0, siblings: [n23], root }`, where `n23 = hash(hash(e2)+hash(e3))` is the sibling at level 1 (also derivable/known).
4. Calling `merkle.verifyMerkleProof(element', proof')` computes `hash(element') = n01`, then `hash(n01 + n23) = root`, returning `true`, even though `element'` was never one of `arrElements`.
5. Submitting this forged `element'`/`proof'` via `is_valid_merkle_proof` in an AA trigger (or via `'in merkle'` authentifier data) lets the attacker satisfy a membership/authorization check they should not pass, enabling unauthorized fund release or address authentication. function verifyMerkleProof(element, proof){
	// Node-as-Leaf issue might matter in some cases
	try {
		var index = proof.index;
		var the_other_sibling = hash(element);
		for (var i = 0; i < proof.siblings.length; i++) {
			// this also works for duplicated trailing nodes
			if (index % 2 === 0)
				the_other_sibling = hash(the_other_sibling + proof.siblings[i]);
			else
				the_other_sibling = hash(proof.siblings[i] + the_other_sibling);
			index = Math.floor(index / 2);
		}
		return (the_other_sibling === proof.root);
	}
	catch (e){
		return false;
	}
}
