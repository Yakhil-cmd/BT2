### Title
Permanent freezing of creator fees when the pool creator's token account is frozen/blacklisted - (File: programs/cp-swap/src/instructions/collect_creator_fee.rs, programs/cp-swap/src/instructions/collect_creator_fee_permissionless.rs)

### Summary
`collect_creator_fee` and its permissionless counterpart both force a token transfer *to* the pool creator's associated token account before the accumulated `creator_fees_token_0`/`creator_fees_token_1` counters are reset. If the destination account (owned by the pool creator) is frozen — either through the SPL Token freeze-authority mechanism or a Token-2022 mint with a blacklist-style extension/hook — the CPI transfer permanently reverts, mirroring the JOJO `liquidate()` pattern where a forced payout to a blacklisted recipient makes the whole transaction, and therefore the whole class of operation, permanently un-executable.

### Finding Description
Both instructions read the accumulated fee counters and then unconditionally call `transfer_from_pool_vault_to_user` to push tokens into `creator_token_0`/`creator_token_1`, only clearing `pool_state.creator_fees_token_0`/`creator_fees_token_1` after both transfers succeed: [1](#0-0) 

The permissionless variant is reachable by *any* unprivileged caller (`payer`), yet still routes funds to the same creator-owned account, so any account state that makes that destination un-transferable blocks the instruction for everyone who tries to trigger it: [2](#0-1) 

`transfer_from_pool_vault_to_user` (via `utils/token.rs`) uses `transfer_checked`/`TransferChecked`, which the SPL Token / Token-2022 programs reject outright if the destination account is frozen — exactly the same failure mode as a USDC blacklist check reverting a `transfer` call in the original JOJO report: [3](#0-2) 

Since `token_0_mint`/`token_1_mint` are validated only via `is_supported_mint` at `initialize` time (not re-validated for freeze-authority absence at collection time), a pool created with a token that has a freeze authority (e.g. USDC-style stablecoins) can end up with a creator whose ATA is frozen by the token issuer after the pool has already accrued fees.

### Impact Explanation
Because `creator_fees_token_0`/`creator_fees_token_1` are only zeroed after a successful transfer, a frozen/blacklisted creator token account causes the accrued creator fees to become permanently stuck inside `token_0_vault`/`token_1_vault` — neither `collect_creator_fee` nor `collect_creator_fee_permissionless` can ever succeed again for that pool. This is a permanent freezing of LP/creator funds, matching the accepted impact class for this analog.

### Likelihood Explanation
Any pool created with a freeze-capable mint (SPL Token freeze authority or a Token-2022 mint carrying a permanent-delegate/transfer-hook-style extension) is exposed. No privileged action is required beyond the token issuer freezing the creator's account — the on-chain program logic itself has no fallback path (e.g., internal balance crediting or ability to redirect fees to a different account) once that happens.

### Recommendation
Do not perform a direct forced push transfer to a fixed, externally-controlled account as the only path to realize fees. Instead:
- Credit the creator's fee entitlement to an internal, program-tracked balance and let the creator pull funds via a transfer whose destination account they explicitly supply and can update if their default ATA becomes frozen, or
- Wrap the transfer CPI in a way that isolates failure to the creator's own claim without blocking the instruction for other unrelated participants, or
- Allow the creator to specify an alternate un-frozen receiving account for fee collection.

### Proof of Concept
1. Create a pool via `initialize` using a mint that has (or later gains) SPL Token freeze authority, e.g. a USDC-like token, with `creator` as the pool creator.
2. Accumulate creator fees via normal `swap_base_input`/`swap_base_output` calls, incrementing `pool_state.creator_fees_token_0`/`creator_fees_token_1`. [4](#0-3) 
3. Have the token's freeze authority freeze the creator's associated token account for `token_0_mint`/`token_1_mint`.
4. Call `collect_creator_fee` (or the permissionless variant) — the `transfer_from_pool_vault_to_user` CPI (`transfer_checked`) fails because the destination account is frozen, causing the whole instruction to revert. [5](#0-4) 
5. Since the fee counters were never reset, the accrued fees remain locked in the vault permanently with no code path to recover them.

```rust
pub fn collect_creator_fee(ctx: Context<CollectCreatorFee>) -> Result<()> {
    let mut pool_state = ctx.accounts.pool_state.load_mut()?;
    let creator_fees_token_0 = pool_state.creator_fees_token_0;
    let creator_fees_token_1 = pool_state.creator_fees_token_1;
    if creator_fees_token_0 == 0 && creator_fees_token_1 == 0 {
        return err!(ErrorCode::NoFeeCollect);
    }

    let signer_seeds: &[&[u8]] = &[crate::AUTH_SEED.as_bytes(), &[ctx.bumps.authority]];

    transfer_from_pool_vault_to_user(
        ctx.accounts.authority.to_account_info(),
        ctx.accounts.token_0_vault.to_account_info(),
        ctx.accounts.creator_token_0.to_account_info(),
        ctx.accounts.vault_0_mint.to_account_info(),
        ctx.accounts.token_0_program.to_account_info(),
        creator_fees_token_0,
        ctx.accounts.vault_0_mint.decimals,
        &[signer_seeds],
    )?;

    transfer_from_pool_vault_to_user(
        ctx.accounts.authority.to_account_info(),
        ctx.accounts.token_1_vault.to_account_info(),
        ctx.accounts.creator_token_1.to_account_info(),
        ctx.accounts.vault_1_mint.to_account_info(),
        ctx.accounts.token_1_program.to_account_info(),
        creator_fees_token_1,
        ctx.accounts.vault_1_mint.decimals,
        &[signer_seeds],
    )?;

    pool_state.creator_fees_token_0 = 0;
    pool_state.creator_fees_token_1 = 0;
    pool_state.recent_epoch = Clock::get()?.epoch;
```

```rust
pub fn transfer_from_user_to_pool_vault<'a>(
    authority: AccountInfo<'a>,
    from: AccountInfo<'a>,
    to_vault: AccountInfo<'a>,
    mint: AccountInfo<'a>,
    token_program: AccountInfo<'a>,
    amount: u64,
    mint_decimals: u8,
) -> Result<()> {
    if amount == 0 {
        return Ok(());
    }
    token_2022::transfer_checked(
        CpiContext::new(
            *token_program.key,
            token_2022::TransferChecked {
                from,
                to: to_vault,
                authority,
                mint,
            },
        ),
        amount,
        mint_decimals,
    )
}
```
