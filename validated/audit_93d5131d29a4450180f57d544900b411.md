### Title
Webhook signature is verified against `repository.owner.login`, but handlers act on `repository.full_name` / raw commit `sha`, allowing any onboarded GitHub organization to forge events for another organization's stacks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to validate an incoming webhook against using `repository.owner.login` (or `organization.login`) taken from the attacker-controlled JSON body, while the actual event handlers (`PushHandler`, `CheckSuiteHandler`, `StatusHandler`) resolve which `Repository`/`Stack`/`Commit` to mutate using a *different* field of the same body (`repository.full_name`, or in `StatusHandler`'s case, no repository scoping at all). Because the HMAC only proves "this body was signed with organization X's secret", not "the repository referenced inside this body belongs to organization X", an org that legitimately owns/administers its own GitHub App and webhook secret can forge a signed payload whose `repository.owner.login` matches its own org (to pass signature verification) while `repository.full_name` (or `sha`) targets a completely different, unrelated organization's stack.

### Finding Description
`verify_signature` computes the verification target purely from body content: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization:)` looks up a per-organization `webhook_secret` in a multi-tenant configuration schema that the engine explicitly documents and supports: [3](#0-2) 

Each organization's `webhook_secret` is set independently by whoever registers that org's GitHub App with the shared Shipit instance, as documented in `docs/setup.md` and `config/secrets.development.example.yml` (multi-org schema). An org owner therefore legitimately knows their own org's `webhook_secret`.

Downstream, the event handlers never re-check that the field used for signature selection matches the field used for the actual write:

- `PushHandler` and the base `Handler` resolve target stacks via `repository.full_name`, a separate JSON field from `repository.owner.login`: [4](#0-3) [5](#0-4) 

- `CheckSuiteHandler` similarly scopes only via `stacks` (i.e. `repository.full_name`), not `repository.owner.login`: [6](#0-5) 

- `StatusHandler` is worse: it doesn't scope by repository at all, it looks up commits globally by `sha` across the entire instance: [7](#0-6) 

`verify_webhook_signature` is a plain HMAC-SHA1 comparison of the whole raw body against a secret keyed only by the org name pulled out of that same body: [8](#0-7) 

The equality that should hold is: `organization whose secret authenticated the request == organization that owns the repository/stack being written`. Nothing enforces `repository.owner.login == repository.full_name.split('/').first`, and `StatusHandler` doesn't check organization/repository identity at all. An attacker who administers Organization A (and thus knows Org A's `webhook_secret`, entirely legitimately, as the party who configured that GitHub App) can:
1. Craft a JSON body with `repository.owner.login = "orgA"` and `repository.full_name = "orgB/victim-repo"` (or, for `status` events, simply any `sha` value that happens to match a commit belonging to a *different* stack).
2. Sign that raw body with Org A's `webhook_secret` (`HMAC-SHA1`).
3. POST it to `/webhooks` with `X-Github-Event` set to `push`, `check_suite`, or `status`.

`verify_signature` passes because it only checks that the body was signed by whichever org's name is embedded (Org A), then the handler blindly acts on Org B's stack/commit found via `full_name`/`sha`.

### Impact Explanation
This crosses the exact boundary the analog rules flag: "an organization that authenticated versus the repository that is written." Concretely:
- Forging a `push` event lets an attacker call `stack.sync_github(expected_head_sha: <attacker-chosen sha>)` on a stack belonging to an organization they do not own, potentially advancing another tenant's deploy pipeline HEAD to an attacker-chosen commit/sha.
- Forging a `status` event lets an attacker set commit CI status (`create_status_from_github!`) on any commit across the whole instance merely by knowing its SHA, since `StatusHandler` performs no repository ownership check whatsoever - this can flip a commit's CI state to "success" for a stack that gates deploys on CI status, enabling an unauthorized deploy that the real CI never approved.
- Forging a `check_suite` event can trigger `schedule_refresh_check_runs!` against another org's commits.

This matches the "unauthorized deploy" / cross-tenant write impact bucket for High-severity findings.

### Likelihood Explanation
This requires the multi-organization deployment mode that the engine itself documents and ships example config for (`config/secrets.development.example.yml`, `docs/setup.md`). Any organization onboarded to a shared Shipit instance already legitimately possesses its own `webhook_secret` (it is not a privileged Shipit credential, GitHub App private key, or `api_clients_secret`; it's just the HMAC secret for that org's own GitHub App, configured by that org's own admins). No repository write access, `ApiClient` token, or Shipit session is required — only the ability to send an arbitrary HTTP POST to the public `/webhooks` endpoint with a body they've signed with their own known secret. This is a low-effort, unprivileged-from-the-target's-perspective attack.

### Recommendation
Bind the field used to select the verification secret to the same field(s) actually used by handlers to determine what gets written, and re-validate ownership inside every handler:
- After selecting `github_app` by `repository_owner`, additionally verify that `repository.full_name`'s owner segment equals `repository_owner` before dispatching to handlers, rejecting mismatches with `422`.
- In `StatusHandler`, scope commit lookup through `stacks`/`Repository.from_github_repo_name(repository_name)` (consistent with other handlers) instead of a global `Commit.where(sha:)`, and reject if the repository's owner doesn't match the organization that authenticated the webhook.
- More generally, ensure the HMAC-verified organization identity is authoritative for every repository-scoped side effect performed by a handler, not merely one field extracted independently from the same untrusted payload.

### Proof of Concept
1. Shipit is configured for multiple GitHub organizations, each with its own `webhook_secret` (per `config/secrets.development.example.yml`'s multi-org schema), e.g. `orgA` and `orgB` both have Shipit stacks.
2. Attacker administers `orgA`'s GitHub App and therefore knows `orgA`'s `webhook_secret` (a secret they configured themselves; not a Shipit-privileged secret).
3. Attacker builds a JSON body for a `status` event:
```json
{
  "sha": "<sha of a real commit belonging to orgB/victim-repo's stack>",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgA/some-repo" }
}
```
4. Attacker computes `sig = HMAC-SHA1(orgA_webhook_secret, raw_body)` and sends:
```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=<sig>
<raw_body>
```
5. `WebhooksController#verify_signature` calls `Shipit.github(organization: "orgA")` and validates the signature successfully (Org A's own secret matches Org A's own signed body).
6. `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`, which runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — this finds the commit belonging to `orgB`'s stack (looked up purely by `sha`, with no relation to `orgA`) and writes a forged `success` CI status onto it, regardless of the fact that the request was authenticated only as `orgA`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
