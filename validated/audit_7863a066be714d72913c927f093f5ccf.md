### Title
Arbiter contract acceptance is authenticated by a shared, non-unique `title` string instead of the contract-specific hash, enabling cross-contract signature replay - ([File: wallet.js])

### Summary
The reported bug class is that a check authorizes an action using a **coarse/shared identifier** (`allowedDiscriminator1`, "any bridge on the network") instead of the **instance-specific identifier** (`allowedDiscriminator2`, "this exact bridge"), letting a proof meant for one instance be replayed against a different instance sharing the same network. The same class of flaw exists in `arbiter_contract.js`/`wallet.js`: a peer's cryptographic acceptance of a contract is checked against the free-text `title` field rather than the contract's unique `hash`, so an accepted-contract signature can be replayed across different contracts that share the same `title`.

### Finding Description
When a peer accepts an arbiter contract offer, the acceptor signs a message and the initiator validates it in `handleMessageFromHub`: [1](#0-0) 

The only bindings checked are: the signature is valid, `objSignedMessage.authors[0].address === objContract.peer_address`, and `objSignedMessage.signed_message == objContract.title`. There is no check that the signed message is bound to `objContract.hash`, which is the actual unique identifier of the contract (computed in `createAndSend`): [2](#0-1) 

`title` is user-supplied free text (see the `wallet_arbiter_contracts` schema and `respond()`/`store()` functions using `title`/`text` fields) and is not required to be unique per contract: [3](#0-2) [4](#0-3) 

Because the validation compares against the shared/coarse field (`title`) instead of the per-instance discriminator (`hash`), a single acceptance signature obtained from a peer for one contract can be reused to satisfy the acceptance check of a *different* contract with the same peer and the same `title` text (e.g., a default or copy-pasted title), exactly mirroring the reported pattern where the "open" (network-wide) discriminator was accepted in place of the bridge-specific one.

### Impact Explanation
Contract "accepted"/"signed" status gates fund release through the arbiter contract's shared address (`pay()` sends funds to `objContract.shared_address` once the contract is `"signed"`, and payment-received listeners advance status based on this signature-authenticated response): [5](#0-4) 

If acceptance authentication can be satisfied by replaying a title-matching signature from an unrelated contract, an attacker controlling contract creation (same peer, reused/duplicated title) can force premature/incorrect status transitions, potentially causing a party to pay into a shared address they never validly agreed to, or bypassing intended per-contract consent — a fund-loss/authorization-bypass condition analogous to the reported double-spend-across-bridges impact.

### Likelihood Explanation
Exploitation requires a peer relationship where multiple distinct arbiter contracts share the same `peer_address` and an identical `title` string — plausible with default/templated titles or an attacker deliberately reusing wording across simultaneous offers to the same counterparty, similar to how the reported bug required a mass-exit event across bridges on the same network. This is reachable entirely by an unprivileged wallet user initiating/accepting arbiter contracts; no privileged/hub/node role is needed.

### Recommendation
Bind the signed acceptance message to the contract's unique `hash` (not the free-text `title`), e.g., require `objSignedMessage.signed_message === objContract.hash` (or a structured payload including `hash`), so that an acceptance signature cannot be valid for more than one contract instance — mirroring the original recommendation to avoid the "open"/shared identifier and enforce the instance-specific one.

### Proof of Concept
1. Attacker (or a user reusing text) creates two different arbiter contracts, Contract A and Contract B, with the same `peer_address` and identical `title` (e.g., default title "Contract agreement").
2. Peer signs and sends `arbiter_contract_response` accepting Contract A, producing `signed_message = title`.
3. Attacker intercepts/reuses this `signed_message` and resubmits it as the `arbiter_contract_response` for Contract B.
4. In `wallet.js` handling (`wallet.js:932-936`), validation only checks `authors[0].address === peer_address` and `signed_message == title` — both satisfied — so Contract B is incorrectly marked `"accepted"`, even though the peer never agreed to Contract B's specific terms (amount/asset/arbiter may differ). function pay(hash, walletInstance, arrSigningDeviceAddresses, cb) {
	getByHash(hash, function(objContract) {
		if (!objContract.shared_address || objContract.status !== "signed" || !objContract.me_is_payer)
			return cb("contract can't be paid");
		var opts = {
			asset: objContract.asset,
			to_address: objContract.shared_address,
			amount: objContract.amount,
			spend_unconfirmed: walletInstance.spendUnconfirmed ? 'all' : 'own'
		};
		if (arrSigningDeviceAddresses.length)
			opts.arrSigningDeviceAddresses = arrSigningDeviceAddresses;
		walletInstance.sendMultiPayment(opts, function(err, unit){								
			if (err)
				return cb(err);
			setField(objContract.hash, "status", "paid", function(objContract){
				cb(null, objContract, unit);
			});
			// listen for peer announce to withdraw funds
			storage.readAssetInfo(db, objContract.asset, function(assetInfo) {
				if (assetInfo && assetInfo.is_private)
					db.query("INSERT "+db.getIgnore()+" INTO my_watched_addresses (address) VALUES (?)", [objContract.peer_address]);
			});
		});
	});
}
