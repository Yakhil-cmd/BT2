### Title
Unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` allows cross-repository status forgery - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits purely by `sha`, with no repository/stack scoping, unlike sibling handlers (`PushHandler`, `PullRequest::OpenedHandler`) which resolve `Repository.from_github_repo_name(payload.dig('repository','full_name'))` before acting. Any correctly-signed `status` webhook (signed with the secret of *some* GitHub organization/app installation known to Shipit) can attach a fabricated `success` status to a `Commit` row belonging to an entirely different stack/repository, as long as the `sha` in the forged payload matches that commit's SHA.

### Finding Description
The claimed binding is: `require_permission!(:merge, :stack)` on `Api::MergeRequestsController#create`/`#refresh` == the authorization boundary for the merge decision. In reality the actual merge trigger predicate is `MergeRequest#all_status_checks_passed?` [1](#0-0) , evaluated by `ProcessMergeRequestsJob#perform` [2](#0-1) , which is fed by `Commit#status` built from `commit.statuses` [3](#0-2) .

`Status` rows are created by `commit.create_status_from_github!(params)`, invoked from `StatusHandler#process`:
```
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [4](#0-3) 

Unlike `PushHandler`, which resolves the target stacks via `Repository.from_github_repo_name(repository_name)` before acting [5](#0-4)  and the base `Handler#stacks`/`#repository_name` helper that derives scope from `payload.dig('repository', 'full_name')` [6](#0-5) , `StatusHandler` never consults `payload['repository']` at all — it matches on `sha` across the entire `Commit` table, spanning every stack and every repository tracked by the Shipit instance.

The webhook request must still pass `WebhooksController#verify_signature`, which computes `Shipit.github(organization: repository_owner).verify_webhook_signature(signature, raw_post)` [7](#0-6) , using an HMAC keyed by that organization's configured `webhook_secret` [8](#0-7) . This means a genuinely signed `status` event for *any* repository under an organization already onboarded to Shipit (i.e., any repo covered by that org's GitHub App installation, which shares one org-wide secret) is accepted — but the handler that processes it does not verify that the `sha` inside the payload actually belongs to the repository that the signature was issued for. Because git commit SHAs are content-addressed, an attacker who can get a real "status" webhook fired for their own commit (e.g., by pushing to a branch/fork within a repo covered by the same GitHub App installation and letting any status-producing integration report on it) can construct a commit object with byte-identical content/parents/timestamps to a target commit in an unrelated stack, producing the same SHA, and thereby cause `Commit.where(sha:)` to match and poison the *victim's* `Commit` row with a forged `success` status.

### Impact Explanation
A forged `success`/`error` status can be attached to a `Commit` belonging to a different stack than the one that legitimately triggered the webhook, corrupting `MergeRequest#all_status_checks_passed?` for that unrelated stack's queued merge request and causing `ProcessMergeRequestsJob` to call `merge_request.merge!`, which invokes `stack.github_api.merge_pull_request` [9](#0-8) . This is an unauthorized merge triggered for a stack/repository the attacker never authenticated against — matching the "Critical: unauthorized merge" / "payload for one repository mutating another's stack" category.

### Likelihood Explanation
Exploitation strictly requires the attacker to be able to get a *validly signed* `status` webhook delivered to Shipit — i.e., they need some level of legitimate access (push/CI-trigger rights) to at least one repository already covered by an onboarded GitHub App installation whose organization the target stack also belongs to (since `webhook_secret` is per-organization, not per-repository) [10](#0-9) . This is not "zero privilege, zero GitHub relationship" as the question's framing implies (a completely unaffiliated internet user without any account or fork within a Shipit-onboarded organization cannot get `verify_signature` to pass, since they lack the org's `webhook_secret` and cannot make GitHub sign a payload on their behalf for an unrelated org). Within that constraint (any contributor to any repo sharing the org/app installation with the target stack), the attack is straightforward and repeatable: force a duplicate-SHA commit and let any CI/status integration post to it.

### Recommendation
Scope `StatusHandler#process` to the repository named in the webhook payload, mirroring `PushHandler`/`Handler#stacks`, e.g. filter `Commit.where(sha: params.sha)` further by `stack: Repository.from_github_repo_name(payload.dig('repository', 'full_name'))&.stacks`, so a status webhook can only ever affect commits belonging to the stack(s) of the repository the webhook actually names.

### Proof of Concept
minitest plan (`test/models/webhooks/status_handler_test.rb`, hypothetical):
1. Create two stacks/repos, `stack_a` (attacker-accessible) and `stack_b` (victim, unrelated), each with a `Commit` sharing the identical `sha` value (simulating the content-collision precondition).
2. Assert before: `stack_b.commits.find_by(sha: sha).status.state != 'success'` and no `Status` row exists for `stack_b`'s commit.
3. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload_for_repo_a_with_sha_and_state_success)` (correctly "signed" per test setup, i.e., bypassing `WebhooksController` and calling the handler directly as the existing test suite does).
4. Assert after: `stack_b.commits.find_by(sha: sha).reload.status.state == 'success'`, proving the cross-repository write, i.e. that `Api::MergeRequestsController#create`'s `require_permission!(:merge, :stack_b)` boundary was never consulted for this write to `stack_b`.
