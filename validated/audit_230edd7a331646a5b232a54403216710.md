### Title
Webhook signature verified against the payload's claimed organization, not the repository actually acted upon - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController` selects which GitHub App/HMAC secret to use for verifying an inbound webhook based on an organization login taken directly from the *unverified* JSON body, but the event handlers that subsequently act on the payload key off a completely different field — `repository.full_name` — without ever checking that it belongs to the same organization whose secret was used to authenticate the request. In Shipit's supported multi-tenant deployment mode (one Shipit instance serving several GitHub Apps/organizations, each with its own `webhook_secret`), this breaks the binding `organization_authenticated == repository_written`.

### Finding Description
`WebhooksController#verify_signature` derives the organization to authenticate against straight from the request body: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` resolves the per-organization `GithubApp` config (including its `webhook_secret`), and `verify_webhook_signature` HMACs the *entire raw body* with that organization's secret: [3](#0-2) 

This design exists because Shipit can be configured with multiple GitHub Apps, one per organization, each with its own independently-managed secret — see the multi-org fixture: [4](#0-3) 

Once the signature check passes, `create` dispatches the same untrusted body to handlers: [5](#0-4) 

Handlers (push, status, check_suite, pull_request, membership, etc.) locate the `Repository`/`Stack`/`Team` to mutate using `repository.full_name` (or `organization.login` for membership events), a field that is never cross-checked against the `repository_owner`/`organization` value that was actually used to select the HMAC secret. For example, pull-request handlers resolve the target repo from `full_name`: [6](#0-5) 

Because the two fields live in the same attacker-controlled JSON body and only one of them (`repository.owner.login`) is used to pick the verification secret, an attacker who legitimately knows the `webhook_secret` for **their own** organization's GitHub App (a normal, unprivileged tenant in this multi-org setup) can craft a raw payload where `repository.owner.login`/`organization.login` = their own org (so the signature check succeeds using a secret they legitimately possess) while `repository.full_name` = `<victim-org>/<victim-repo>` (so the handler acts on a stack/repository they do not control), and POST it directly to `/webhooks`.

### Impact Explanation
This lets an attacker who administers one tenant organization's GitHub App forge signed-looking webhook events that are processed as if they came from a different organization's repository, without ever holding that organization's secret, an `ApiClient` token, or GitHub write access to the victim repo. Depending on which event is forged this enables:
- Injecting attacker-chosen commit statuses on a victim stack's commits, potentially satisfying `ci.require`/CI gating and enabling an **unauthorized deploy**.
- Forging `push`/`check_suite` events to enqueue sync/merge jobs against a victim `Stack`, influencing which commit is considered head/mergeable.
- Forging `membership` events, which create/delete `Team`/`Membership` records that back `Shipit.github_teams` authorization, an explicit **escalation into `Shipit.github_teams` authorization**.

Both are within the defined Critical/High impact categories (unauthorized deploy; escalation into `Shipit.github_teams` authorization).

### Likelihood Explanation
Requires only that the deployment run multiple GitHub Apps/organizations behind one Shipit instance (an explicitly supported and documented configuration, per `test/dummy/config/secrets_double_github_app.yml`) and that the attacker be a legitimate administrator/owner of one of those tenant organizations — not a Shipit session, `ApiClient` token, or GitHub write access to the victim repository. No special conditions besides crafting a raw HTTP POST with a valid HMAC computed from a secret the attacker legitimately owns.

### Recommendation
After verifying the HMAC signature, re-derive and pin the organization for the remainder of request processing, and reject (or independently re-verify) any event whose `repository.full_name` owner segment (or `organization.login` for org-level events) does not match the `repository_owner` used to select the verification secret. Handlers should never trust `full_name`/`organization.login` from the body as authoritative once a different field from the same body was used to choose the trust anchor.

### Proof of Concept
1. Deploy Shipit with two tenant orgs, `OrgA` and `OrgB`, each with its own GitHub App and `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. As the legitimate operator of `OrgA` (who therefore knows `OrgA`'s `webhook_secret`), craft a raw JSON body for a `push` (or `status`/`membership`) event where:
   - `repository.owner.login` = `"OrgA"` (or `organization.login` = `"OrgA"`)
   - `repository.full_name` = `"OrgB/victim-repo"`
   - other event fields (e.g. `after`, `ref`, `sha`, `state`) crafted to target `OrgB`'s stack.
3. Compute `sha1=HMAC-SHA1(OrgA_webhook_secret, raw_body)` and send:
   `POST /webhooks` with headers `X-Github-Event: push`, `X-Hub-Signature: sha1=<computed>`.
4. `verify_signature` resolves `repository_owner` = `"OrgA"`, fetches `OrgA`'s config, and the HMAC check succeeds (attacker used the correct, legitimately-known secret) — see `app/controllers/shipit/webhooks_controller.rb` lines 24-30.
5. The push handler then processes the event using `repository.full_name` = `"OrgB/victim-repo"`, acting on `OrgB`'s stack even though only `OrgA`'s secret was validated.

Note: I was unable to fully trace every default handler (`app/models/shipit/webhooks/handlers/**`) within the available search budget to confirm the exact downstream side effects (e.g. precise `GithubSyncJob` enqueue path for `push`), so the exact blast radius per event type should be validated by a Devin session with full repo access.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
