### Title
Webhook signature is verified against the organization named in the payload while the repository/stack acted upon is selected from a different, decoupled field of the same untrusted payload - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to use for HMAC verification based on `repository.owner.login` (or `organization.login`) taken directly from the unauthenticated JSON body. Once the signature "passes" (because it was signed with a secret the attacker legitimately controls for *their own* configured organization), the actual event-processing code (`Shipit::Webhooks::Handlers::Handler#repository_name`) resolves the target `Repository`/`Stack` using a *different* field of the same body: `repository.full_name`. Nothing ties `repository.owner.login` to `repository.full_name`, so an attacker who is a legitimate, unprivileged administrator of one GitHub organization/App configured on a multi-tenant Shipit instance can forge webhook payloads whose `full_name` points at a stack belonging to a completely different organization, while signing with their own org's secret.

### Finding Description
The verifying key (the webhook secret) is chosen using: [1](#0-0) [2](#0-1) 

`repository_owner` comes straight from `params.dig('repository', 'owner', 'login')` in the raw JSON body that the request itself provides — it is not otherwise authenticated. `Shipit.github(organization: repository_owner)` looks up the App config (and thus the `webhook_secret`) for that organization, matching the multi-org configuration format shown in `test/dummy/config/secrets_double_github_app.yml`.

Once `verify_signature` passes, `WebhooksController#create` dispatches to handlers via `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. Every handler inherits from `Shipit::Webhooks::Handlers::Handler`, which resolves the actual repository/stack to act on using a **different** field: [3](#0-2) 

`repository.owner.login` (used to pick the verifying secret) and `repository.full_name` (used to pick the affected `Repository`/`Stack`) are two independent JSON fields inside the same attacker-supplied body. GitHub itself keeps these consistent, but the verification logic does not enforce that relationship — it only checks that *some* HMAC signature computed with *some* org's secret matches the raw body. An attacker who legitimately controls a GitHub App/webhook secret for one organization configured on the Shipit instance (an unprivileged actor with respect to any other tracked organization/repository) can set `repository.owner.login` to their own org (so their own secret is selected and the signature check passes) while setting `repository.full_name` to `"other-org/other-repo"` (so the handler acts on a stack that belongs to a different, victim organization).

This is the same class of bug as the reported EIP712 issue: the value bound into the "verifying" computation (the organization used to pick the secret) is not the same value the code ultimately trusts and acts upon (the repository named in `full_name`). The binding `organization used to verify signature == repository actually written to` is broken.

### Impact Explanation
Every webhook handler is reachable through this mismatch since they all inherit `Handler#repository_name`/`stacks`:
- `PushHandler` calls `stack.sync_github(expected_head_sha: params.after)` on stacks belonging to the victim org/repo [4](#0-3) 
- `StatusHandler` writes forged commit statuses (`create_status_from_github!`) onto commits of the victim's stacks [5](#0-4) 
- `CheckSuiteHandler` schedules check-run refreshes for the victim's commits [6](#0-5) 

Forging commit statuses/check-suite state for a stack the attacker does not own is a cross-repository write into Shipit's data model driven entirely by attacker-controlled payload content, using credentials that were only ever supposed to authorize events for the attacker's own organization. Depending on downstream logic (continuous-deployment/merge-queue gating on commit status success, which this report could not fully trace within the remaining budget), this can influence whether Shipit considers a victim commit "deployable" or safe to merge/ship, i.e., it crosses the "cross-repository writes" / "unauthorized deploy" bar for this engine, even though the exact deploy-trigger chain from a forged `success` status was not fully re-verified against `Commit#create_status_from_github!` in this pass.

### Likelihood Explanation
Requires the Shipit instance to be configured with more than one GitHub organization/App (a documented, supported deployment mode per `test/dummy/config/secrets_double_github_app.yml` and `docs/setup.md`), and requires the attacker to be a legitimate (unprivileged, relative to the victim org) administrator of at least one of the configured organizations' GitHub Apps — i.e., they know only their own `webhook_secret`, never any Shipit session, `ApiClient` token, or the victim's secret. No repository write access, no Shipit account, and no interception of TLS/secrets is required; only the ability to send an arbitrary HTTP POST to the shared `/webhooks` endpoint with a fabricated `repository.full_name`.

### Recommendation
Bind the verifying secret to the same value that is subsequently trusted to select the target repository:
- Derive `repository_owner` (used to select the webhook secret) from the same `repository.full_name` field that `Handler#repository_name` uses, or better, cross-check that `repository.owner.login` is a strict prefix of `repository.full_name` before dispatching.
- Alternatively, resolve the `Repository`/`Stack` first, look up which organization it belongs to from Shipit's own trusted records, and use only that organization's secret to verify — never trust an organization value taken from the unauthenticated payload to select the verifying key.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own GitHub App and `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. As the (unprivileged, relative to `OrgB`) administrator of `OrgA`'s GitHub App, craft a `push` webhook body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac using OrgA's known webhook_secret over the raw body>`.
4. POST to `/webhooks` with `X-Github-Event: push`. `verify_signature` resolves `repository_owner` = `"OrgA"`, fetches `OrgA`'s secret, and the HMAC matches (attacker knows this secret) → `verified == true`.
5. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("OrgB/victim-repo")` and calls `sync_github(expected_head_sha: "<attacker-chosen sha>")` on `OrgB`'s stack — an organization the attacker never authenticated as and does not control.
