### Title
Cross-organization webhook signature confusion allows unauthorized commit status forgery and unauthorized merges/deploys - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate the HMAC signature against using `repository_owner`, derived from the JSON payload itself (`repository.owner.login` or `organization.login`), rather than from any pre-established, immutable binding to the target repository/stack. [1](#0-0) 
Once the signature is verified against that (attacker-selected) organization's secret, the raw payload is dispatched to a handler, and `StatusHandler` resolves the target `Commit` purely by `sha` — with **no check that the commit belongs to a repository/stack owned by the organization whose secret was used to validate the signature**. [2](#0-1) 

### Finding Description
This mirrors the GMX oracle bug class: a value that is supposed to be bound together with the field the signature vouches for (`repository_owner` used for choosing the signing key) is not actually tied to the field that is later trusted for the write (`sha`, which is looked up globally across all repositories). The binding that should hold is:

`organization whose webhook_secret authenticated the request == organization that owns the repository/commit being written`

In this codebase, that equality is never enforced.

- Shipit supports multiple GitHub Apps/organizations configured under `github:` in secrets, each with its own `webhook_secret`. [3](#0-2) 
- `verify_signature` picks the app/secret via `repository_owner`, which is read straight out of the untrusted JSON body (`params.dig('repository','owner','login') || params.dig('organization','login')`), before the signature has been validated. [4](#0-3) 
- An attacker who legitimately administers *any* one organization onboarded to this Shipit instance (and therefore knows that organization's own `webhook_secret`, since they created it when registering their GitHub App) can compute a valid HMAC for a payload with `repository.owner.login` set to their own org, while embedding a `sha` value belonging to a commit in a completely different, higher-privileged repository/stack.
- `StatusHandler#process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with no repository/stack scoping at all. [2](#0-1) 
- Commit statuses directly gate merge-queue behaviour: `MergeRequest#all_status_checks_passed?`/`any_status_checks_failed?`/`any_status_checks_missing?` are driven by the `Status`/`Status::Group` built from these very rows, and `ProcessMergeRequestsJob` calls `merge_request.merge!` once `all_status_checks_passed?` is true. [5](#0-4) [6](#0-5) 
- `merge!` calls `stack.github_api.merge_pull_request(...)`, using the *victim* stack's own installation credentials, so the attacker never needs the victim's GitHub token — Shipit performs the merge on their behalf once the forged "success" status satisfies `required_statuses`/`merge_request_required_statuses`. [7](#0-6) 

### Impact Explanation
By forging a `status` webhook signed with an org they legitimately control, an attacker can inject arbitrary CI status rows (e.g., `state: success`) onto commits belonging to an unrelated repository/stack they have no authorization over. If that stack's merge queue is active and the required-status check is satisfied by the injected status, `ProcessMergeRequestsJob` will call `MergeRequest#merge!`, causing Shipit to merge a pull request using its own GitHub App credentials for the victim repository — an unauthorized merge triggered entirely from outside that repository's trust boundary. This matches the "Critical - unauthorized deploy/merge" impact bucket in scope.

### Likelihood Explanation
Requires only that the Shipit instance is configured for more than one GitHub organization (a documented, supported configuration — see `docs/setup.md` and `secrets.development.shopify.yml`), and that the attacker controls one of those organizations' GitHub App webhook secret (a normal, unprivileged capability for the owner of *their own* onboarded org). No access to the victim's GitHub credentials, Shipit session, or `ApiClient` token is needed — only the ability to know the sha of a target commit (visible on the victim's public/private repo via normal GitHub access) and send a raw POST to `/webhooks` with a self-signed payload.

### Recommendation
Bind the verified signer identity to the resource being mutated:
- After signature verification, re-derive `repository_owner` from the authenticated context (not from payload fields) and require that the resolved `Commit`'s `Stack`/`Repository` actually belongs to that same GitHub organization/App before applying `create_status_from_github!`.
- In `Shipit::Webhooks::Handlers::Handler`/`StatusHandler`, scope commit lookup by repository (`payload.dig('repository','full_name')`) validated against the verifying org, in addition to `sha`, mirroring how `PushHandler` scopes through `stacks`.
- Reject webhooks where `repository.owner.login`/`organization.login` do not match the repository actually referenced by `repository.full_name`.

### Proof of Concept
1. Configure Shipit (as documented) with two orgs, `victim-org` (secret `S_v`, hosting `victim-org/critical-repo`) and `attacker-org` (secret `S_a`, controlled by the attacker).
2. Attacker crafts a JSON body:
```json
{
  "repository": {"owner": {"login": "attacker-org"}, "full_name": "attacker-org/whatever"},
  "sha": "<sha of head commit of a pending PR in victim-org/critical-repo>",
  "state": "success",
  "context": "ci/required-check"
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(S_a, body)` — a valid signature since they legitimately own `attacker-org`'s app.
4. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "attacker-org")` from `repository.owner.login`, verifies the signature successfully. [8](#0-7) 
5. `StatusHandler#process` looks up `Commit.where(sha: params.sha)` — matching the victim's commit regardless of the fact the signature came from `attacker-org` — and records a `success` status on it. [2](#0-1) 
6. If this satisfies the victim stack's `merge_request_required_statuses`, `ProcessMergeRequestsJob` merges the PR using the victim stack's own GitHub App credentials on the attacker's behalf. [6](#0-5)

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner

    def merge!
      raise InvalidTransition unless pending?

      raise NotReady if not_mergeable_yet?

      stack.github_api.merge_pull_request(
        stack.github_repo_name,
        number,
        merge_message,
        sha: head.sha,
        commit_message: 'Merged by Shipit',
        merge_method: stack.merge_method
      )
      begin
        if stack.github_api.pull_requests(stack.github_repo_name, base: branch).empty?
          stack.github_api.delete_branch(stack.github_repo_name, branch)
        end
      rescue Octokit::UnprocessableEntity
        # branch was already deleted somehow
      end
      complete!
      true
    rescue Octokit::MethodNotAllowed # merge conflict
      reject!('merge_conflict')
      false
    rescue Octokit::Conflict # shas didn't match, PR was updated.
      raise NotReady
    end

    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?
      end

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end
