### Title
Unauthenticated Pubsubstub `/events` mount allows anonymous subscription to stack update channels - ([File: config/routes.rb])

### Summary
The `mount Pubsubstub::StreamAction.new, at: "/events", as: :events` line in `config/routes.rb` mounts a Rack endpoint directly, bypassing the controller-level `before_action :force_github_authentication` that protects every other Shipit route. Anyone who knows or guesses a channel name of the form `stack.<id>` can subscribe and receive live `update` broadcasts for that stack without any session or credential.

### Finding Description
The binding the question assumes should hold is: `every request path reachable under Shipit::Engine.routes` `⇒` `passes through Shipit::Authentication#force_github_authentication before serving data`. That binding is enforced only via `include Shipit::Authentication` in `Shipit::ShipitController` [1](#0-0)  which wires the `before_action :force_github_authentication` from the concern [2](#0-1) . The `/events` route, however, is `mount`ed as a raw Rack app (`Pubsubstub::StreamAction.new`) rather than routed to any Shipit controller [3](#0-2) , so it never runs through `ApplicationController`/`ShipitController`'s filter chain, and thus never runs `force_github_authentication`. This confirms the binding is broken for this specific route: the mounted endpoint is reachable with zero authentication.

Channel names published to Pubsubstub are low-entropy and derived directly from the stack's numeric primary key, e.g. `Stack#broadcast_update` calls `Pubsubstub.publish("stack.#{id}", { id:, updated_at: }.to_json, name: 'update')` [4](#0-3) , and the same channel naming convention (`stack.#{@stack.id}`) is used by the authenticated views that subscribe to it via the `subscribe` helper, e.g. `app/views/shipit/stacks/show.html.erb` line 1, `app/views/shipit/stacks/all_tasks.html.erb` line 1, and the merge-request views. An attacker can iterate small integers (`channel=stack.1`, `stack.2`, ...) against `GET /events?channel=stack.<id>` and passively receive `update` events whenever a commit/status/deploy touches that stack.

However, tracing what is actually published on these channels shows the payload is minimal: `Stack#broadcast_update` only emits `{ id:, updated_at: }` — no command output, no task logs, no secrets, no branch/environment details beyond the numeric stack id and timestamp. I found no evidence in the reachable code (`Hook#emit`, `Task#emit_hooks`, `Chunk`/output streaming) that live command/task output lines are pushed to Pubsubstub channels reachable via this `/events` mount; `Hook.emit` delivers to registered webhook URLs via `DeliverHookJob`, not through Pubsubstub [5](#0-4) , and task/commit-status broadcast helpers seen in tests (`expect_event` in `status_test.rb`, `deploys_test.rb`, `commits_test.rb`) all assert only on the channel name `stack.#{id}`, not on any content resembling command output. So the premise in the question that "command output lines pushed via Hook/task streaming" are exposed through this channel could not be substantiated with the code available to this index.

### Impact Explanation
An unauthenticated attacker can learn, for a guessed stack id, that a stack was updated and its `updated_at` timestamp — i.e., an unauthenticated read of a very small slice of stack state (existence/activity of a stack). This is a real confidentiality leak (unauthenticated read of stack state) but is narrow: no task output, no deploy logs, no secrets, no `github_access_token`, no ability to trigger or mutate anything. It does not rise to the "unauthenticated read of ... task streams or deploy output" tier described in the rules because that richer data was not found to be published on these channels in this codebase; the demonstrable leak is limited to stack id + update timestamp.

### Likelihood Explanation
No Shipit credentials, GitHub secrets, or privileged role are required — only network access to the host and a guessable/enumerable small integer stack id, which is trivially crawlable since stack ids are sequential primary keys. The attack is repeatable indefinitely and against any stack whose id is known or guessed.

### Recommendation
Wrap the `/events` mount behind authentication and authorization: either replace the raw `mount` with a controller action that includes `Shipit::Authentication` and verifies the requesting user is authorized to view the specific stack(s) named in the `channels` parameter before establishing/allowing the Pubsubstub subscription, or insert Rack middleware in `lib/shipit/engine.rb` that authenticates the `/events` path and validates that `current_user` has access to the requested channel(s) before delegating to `Pubsubstub::StreamAction`.

### Proof of Concept
```ruby
# test/integration/events_stream_test.rb
require 'test_helper'

module Shipit
  class EventsStreamTest < ActionDispatch::IntegrationTest
    test "unauthenticated request can subscribe to a stack's update channel" do
      stack = shipit_stacks(:shipit)

      # No session/user set up at all.
      get "/events", params: { channels: "stack.#{stack.id}" }, headers: { "Accept" => "text/event-stream" }

      # Binding under test: mounted /events should behave like every other
      # Shipit route and be rejected by force_github_authentication.
      # Actual: request is accepted by Pubsubstub::StreamAction directly.
      assert_response :success
      refute_equal 403, response.status
    end
  end
end
```
This demonstrates that `/events` is reachable and establishes a subscription without any `session[:user_id]`, in contrast to any other Shipit controller action which would redirect (302) or return 403 via `force_github_authentication`.
