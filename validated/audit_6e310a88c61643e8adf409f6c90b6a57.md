## Analysis Result

### Title
Cross-organization webhook signature confusion allows forging writes against repositories of *other* GitHub organizations - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to verify a GitHub webhook against using `repository.owner.login` (or `organization.login`), but every event handler dispatches and writes state using the independent `repository.full_name` field from the same JSON body. Nothing ties these two fields together, so a party who legitimately knows the `webhook_secret` configured for *any one* organization in a multi-org Shipit deployment can forge a signature that validates for that organization while pointing `repository.full_name` at a repository belonging to a *different* organization, causing Shipit to act on that other organization's stacks/pull requests/review stacks.

### Finding Description
`verify_signature` computes `repository_owner` purely from the untrusted JSON body and uses it to pick which `GitHubApp`/`webhook_secret` to validate against: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` resolves a distinct `GitHubApp` (and therefore a distinct `webhook_secret`) per organization key when the multi-org config schema is used: [3](#0-2) 

The HMAC check itself only proves that *some* configured secret (the one belonging to `repository_owner`) matches the raw body — it says nothing about which repository the payload's other fields describe: [4](#0-3) 

Every handler, however, resolves the target repository/stacks from a *different* field, `repository.full_name`, with no cross-check against `repository.owner.login`/`organization.login` used earlier for secret selection: [5](#0-4) [6](#0-5) 

Concretely, `PushHandler` triggers a GitHub sync for whatever stack matches `repository.full_name`+branch: [7](#0-6) 

and pull-request handlers write attacker-supplied payload data / archive-unarchive review stacks keyed only off `repository.full_name`: [8](#0-7) [9](#0-8) [10](#0-9) 

**The broken binding, as an equality that no longer holds:**
`organization whose webhook_secret authenticated the request` (derived from `repository.owner.login`/`organization.login`) **≠** `organization/repository whose stack/pull-request/review-stack state is mutated` (derived from `repository.full_name`).

Before the attack: for a legitimately-installed GitHub App, GitHub always sets `repository.owner.login` and `repository.full_name`'s owner segment to the same value, so the two fields happen to agree and the binding holds implicitly.

After the attack: an attacker who administers (or has obtained the `webhook_secret` for) organization *A* in a multi-org Shipit config crafts a raw JSON body where `repository.owner.login` = `"A"` (so `verify_signature` selects *A*'s secret and the HMAC validates) but `repository.full_name` = `"B/victim-repo"` (a repository belonging to a completely different, unrelated organization *B* configured on the same Shipit instance). The HMAC signature is computed over the full raw body with *A*'s secret, so it is valid — the mismatch between `repository.owner.login` and `repository.full_name`'s owner is never checked anywhere in the codebase.

### Impact Explanation
This breaks a repository-write-authorization boundary described by the rules ("an organization that authenticated versus the repository that is written"). Depending on event type, an attacker controlling only org *A*'s webhook secret can:
- Force `PushHandler` to enqueue `GithubSyncJob` / drive deploy pipeline state for org *B*'s stacks.
- Cause `PullRequestEditedHandler`/`AssignedHandler` to overwrite `github_pull_request` attributes of org *B*'s tracked pull requests with attacker-controlled JSON.
- Cause `PullRequestClosedHandler`/`LabeledHandler`/`ReopenedHandler` to archive/unarchive review stacks belonging to org *B*.

This is a cross-repository/cross-organization write achieved without possessing the target organization's own webhook secret — matching the "cross-repository writes" / "unauthorized deploy or rollback" critical-impact criteria.

### Likelihood Explanation
Exploitability depends entirely on multi-organization Shipit deployments (`docs/setup.md` explicitly documents this as a supported configuration where each org gets its own `webhook_secret`). In that configuration, any party who administers one onboarded organization's GitHub App webhook settings (a normal, low-privilege position relative to the *other* tenant organizations on the same Shipit instance) can mount this attack against any other tenant's repositories with a single crafted HTTP POST to `/webhooks`. In a single-organization deployment the attack collapses (there is only one secret/org, so the mismatch is moot), so likelihood is conditioned on multi-tenant setups, which the project explicitly supports and documents.

### Recommendation
In `WebhooksController#verify_signature`/`create`, after verifying the signature, validate that `repository.owner.login` (or `organization.login`) used to select the `webhook_secret` matches the owner segment of `repository.full_name` (and, for `membership`/organization events, that `organization.login` matches). Reject the request (422) if they diverge, ensuring the organization whose secret validated the payload is the same organization whose repository state handlers are permitted to mutate.

### Proof of Concept
1. Configure Shipit with two organizations in `config/secrets.yml`: `A` (attacker-administered app, secret known to attacker) and `B` (victim, unrelated secret).
2. Attacker crafts a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "A" },
    "full_name": "B/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(secret_A, raw_body)` using *A*'s known `webhook_secret`.
4. POST to `/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: "A")` (from `repository.owner.login`) and validates successfully against `secret_A` [1](#0-0) .
6. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("B/victim-repo")` [11](#0-10)  and enqueues a sync/deploy action on organization *B*'s stack, despite the attacker never possessing `B`'s webhook secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
