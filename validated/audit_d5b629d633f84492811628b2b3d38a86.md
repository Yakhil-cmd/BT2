### Title
Unpriviledged spam of `data_feed` units grows `storage.assocUnstableMessages`, forcing an O(n) full-array scan on every AA data-feed read - ([File: data_feeds.js])

### Summary
An attacker can post many minimal-size `data_feed` units (cheap, requires only ordinary network/witnessing fees, no economic value needs to be locked or destroyed) while withholding them from stabilizing (or simply posting faster than stabilization can catch up). Every one of these units is kept in the in-memory map `storage.assocUnstableMessages` until it becomes stable, and this map is fully iterated, unit-by-unit, every single time any AA (Autonomous Agent) reads a data feed value with the "include unstable AA data feeds" option. This mirrors the reported bug class: a low-cost, frequently-repeatable posting action inflates a queue/array that a privileged/automatic downstream process (here, AA trigger execution/data-feed evaluation, analogous to the keeper's `calculateWithdrawShares`) must scan in full on every subsequent operation.

### Finding Description
When a unit is saved, any message with `app` in `['data_feed', 'definition', 'system_vote', 'system_vote_count']` is pushed into `storage.assocUnstableMessages[objUnit.unit]`: [1](#0-0) 

This array entry for a unit is only removed once the unit's MCI becomes stable, inside `saveUnstablePayloads()`, called from `markMcIndexStable`/`addBalls`: [2](#0-1) 

Stabilization of an MCI requires main-chain progression and sufficient witnessing/majority-of-witnesses agreement — it is not instantaneous and can lag, especially under load or during network partitions/parallel branches, as seen in the stabilization logic of `advanceMcStability`/`determineIfStableInLaterUnits`: [3](#0-2) 

Meanwhile, `dataFeedExists()` and `readDataFeedValue()` in `data_feeds.js` — both invoked from AA formula evaluation and from the `in data feed` authentifier — iterate over the **entire** `storage.assocUnstableMessages` object whenever `bAA`/`unstable_opts` (looking at unstable AA-authored data feeds) is requested: [4](#0-3) [5](#0-4) 

These functions are reachable from ordinary formula evaluation (the `data_feed[[...]]` function and `in data feed` operator) used inside every AA definition, and from `definition.js`'s authentifier evaluator: [6](#0-5) 

Because the loop is `for (var unit in storage.assocUnstableMessages)` with only cheap early-exit `continue` checks (address intersection, mci range, `bAA` flag), the cost of a **single** data-feed read scales linearly with the total number of currently-unstable units carrying `data_feed`/`definition`/`system_vote` messages network-wide — not just units relevant to the querying AA. An attacker who is any unprivileged unit poster can:
1. Post a stream of minimal-size units, each containing a single tiny `data_feed` message (e.g., `{x:1}`), from freshly generated addresses.
2. As long as these units remain unstable (which an attacker can help ensure by keeping the DAG wide/forking, or simply by outposting the network's stabilization rate), each unit's entry stays in `assocUnstableMessages`.
3. Every AA in the network that performs a data-feed lookup with the unstable/AA option now pays for an O(n) scan over all of these attacker-inserted entries.

This is directly analogous to the reported Noya finding: a near-zero-cost, frequently-repeatable user action (`withdraw(0, ...)` there; posting a tiny `data_feed` unit here) inflates an array (`withdrawQueue` there; `storage.assocUnstableMessages` here) that a downstream, unavoidable process (`calculateWithdrawShares` there; AA data-feed evaluation here) must scan in full, at cost proportional to attacker-controlled queue length.

### Impact Explanation
Every AA that reads any data feed while considering unstable AA-authored feeds (a common, encouraged oracle pattern) incurs CPU cost proportional to the number of outstanding attacker-inserted unstable `data_feed`/`definition`/`system_vote` messages. Because AA trigger execution occurs synchronously inside `handleAATriggers`/`handleTrigger` while holding the `aa_triggers` mutex and a DB connection/transaction (see `aa_composer.js`), sustained growth of `assocUnstableMessages` slows down AA processing for the whole node, delaying stabilization further (a feedback loop: slower AA processing → slower unit processing → more units remain unstable → array grows further). This can degrade throughput and delay confirmation of AA-related outputs network-wide, which qualifies as a network-availability/DoS-style degradation reachable purely by posting ordinary AA-triggering/data-feed units — no privileged role required.

### Likelihood Explanation
Likelihood is moderate-to-high: creating many tiny `data_feed` units is cheap (bounded only by standard headers/payload commission, no special asset or balance requirements beyond minimal bytes), and any address can author them. The attack does not require any AA cooperation; it simply requires that units remain in the unstable set for a sustained period, which an attacker can influence by fanning out fresh parallel unit chains (increasing the pool of unstable, non-mutually-included units) faster than the network's witnessing/majority process can retire them.

### Recommendation
- Avoid a full-array scan of `storage.assocUnstableMessages` for data-feed lookups. Maintain a secondary index (e.g., `assocUnstableMessagesByAddressAndFeedName` or per-address arrays) so lookups are O(matching entries) rather than O(all outstanding unstable message-bearing units).
- Bound the number of outstanding unstable `data_feed`/`definition`/`system_vote` entries a single address (or a cheap set of addresses) can contribute before further such units are deprioritized/rate-limited during validation.
- Alternatively, cap or fee-adjust the `data_feed` app message so that low-value repeated postings are economically discouraged relative to the CPU cost they impose on the whole network.

### Proof of Concept
1. Attacker generates N fresh addresses.
2. For each address, attacker composes and posts a minimal unit containing a single `data_feed` message with a unique feed name/value, paying only the standard minimal headers/payload commission.
3. Attacker keeps these units (and their ancestors) spread across parallel branches so they are slow to reach majority-of-witnesses stability (or simply posts them continuously, faster than the network naturally stabilizes MCIs).
4. Observe that `storage.assocUnstableMessages` (populated per `writer.js` lines 603-613) grows to size N and is not pruned until each unit stabilizes (`main_chain.js` lines 1550-1584).
5. Any AA in the network invoking a data-feed read with the unstable-AA option (`dataFeedExists`/`readDataFeedValue`, `data_feeds.js` lines 34-97 and 211-241) now performs an O(N) loop over `assocUnstableMessages` for every such call, measurably increasing AA trigger execution latency in `aa_composer.handleTrigger`/`handleAATriggers` proportional to attacker-controlled N.

				if (relation === '=') {

						bFound = true;

				}
				if (relation === '!=') {
					// search only within the same type, otherwise 'abc' != 123 but we don't want to say that they are not equal, because they are incomparable
					if (valueIsNumber()) {
						if (value.toString() !== feed_value.toString())
							bFound = true;
					}
					else {
						if (value !== feed_value)
							bFound = true;
					}
					return;

					if (relationSatisfied(feed_value, value))
						bFound = true;

						bFound = true;
					return;
