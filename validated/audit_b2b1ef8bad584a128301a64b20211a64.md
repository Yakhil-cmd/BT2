### Title
Insufficient escaping in `has_only()` builtin allows regex character-class injection - (File: formula/evaluation.js)

### Summary
The oscript builtin `has_only(str, charset)` builds a dynamic JavaScript `RegExp` character class by splicing the user-supplied `charset` argument directly into the pattern string `"^[" + sub + "]*$"`, only escaping the literal `]` delimiter (and rejecting a trailing lone backslash). This mirrors the Mermaid `classDef` bug class: a value captured with an unrestricted grammar rule is spliced unsanitized into a mini-language whose syntax is richer than "just the closing delimiter," allowing an attacker to change the semantics of the generated construct rather than merely close it early.

### Finding Description
In `formula/evaluation.js`, the `has_only` case evaluates the second argument (`sub_expr`) to a string and constructs a regex character class: [1](#0-0) 

The sanitization only guards against the value literally closing the `[...]` group early (`\]` and a trailing backslash). It does not escape other characters that carry special meaning **inside** a JS regex character class, such as:
- a leading `-`/embedded `-` used to form arbitrary character **ranges** (e.g. `0-\uffff`, effectively matching any character), and
- a leading `^`, which **negates** the whole character class.

Both of these are validated in `formula/validation.js`'s companion `evaluate` walker only for type/arity, not content: [2](#0-1)  — the charset string itself is never restricted to a safe character set before reaching the interpreter.

This is directly analogous to the Mermaid CVE: an "unrestricted" user-controlled string (there, `CLASSDEF_STYLEOPTS`; here, the `has_only` charset argument) is concatenated into a structured mini-language (CSS rule text / JS regex source) with escaping limited to the single delimiter that would prematurely close the construct, while ignoring other syntactically meaningful characters that let the attacker change the meaning of the surrounding construct instead of just escaping it.

### Impact Explanation
`has_only()` is intended for AA authors to whitelist-validate incoming trigger data (e.g., "only digits", "only base32 letters") before proceeding with fund transfers or state changes. If an AA constructs the charset argument from attacker-influenced trigger data (a supported and encouraged oscript pattern for flexible validators, e.g. `has_only(trigger.data.value, trigger.data.allowed_chars)` or charset built by concatenating a fixed prefix with attacker data), an attacker who is simply the trigger sender can:
- Prepend `^` to negate the whole class, flipping an "only allow X" check into "reject only X, allow everything else", or
- Inject a `-` range spanning the full codepoint space, making the "restrictive" whitelist match arbitrary strings.

Either way, a validation gate that the AA logic relies on before releasing funds, updating balances, or authorizing an operation can be silently bypassed, leading to unauthorized fund release / AA fund loss from the affected Autonomous Agent, since `has_only`'s result commonly feeds a `require()`/`bounce` guard.

### Likelihood Explanation
Exploitation requires the target AA to route (even partially) attacker-controlled data into the second argument of `has_only`. Because AA developers are free to compose charset strings from `trigger.data`/`params`, and no documentation or engine-level restriction prevents this, the pattern is plausible in real AAs that implement dynamic/configurable whitelisting rather than hard-coded literal charsets. Any account/unit poster can trigger the target AA with crafted `trigger.data` — no special privilege, node position, or network condition is required, matching the "single posted unit/trigger" reachability required for this analysis.

### Recommendation
Harden `has_only()` in `formula/evaluation.js` to properly escape (or reject) all regex metacharacters that have meaning inside a character class before constructing the `RegExp`, not just `]`. At minimum, escape `\`, `]`, `^`, and `-` (or restrict `sub` to a byte-for-byte literal match using a manually built character set instead of feeding it into `RegExp` source at all), so the resulting character class always matches exactly the literal characters the AA author/attacker string enumerates.

### Proof of Concept
Given an AA that validates trigger data with the pattern:
```
if (!has_only(trigger.data.value, trigger.data.charset))
    bounce("invalid characters");
```
An attacker who wants `trigger.data.value` to pass validation regardless of the AA's intended restriction can post a trigger with:
```
{
  "value": "; DROP everything;",
  "charset": "^"
}
```
This produces the regex `^[^]*$`, i.e. "any character, negated empty class", which matches any input, bypassing the intended whitelist entirely and letting arbitrary `value` content reach the rest of the AA logic (e.g., a downstream `require`, or being stored/echoed into other decisions).
