### Title
Stack-scoped ApiClient tokens can read CI status of arbitrary stacks via `Api::CCMenuController` - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::CCMenuController#stack` resolves the target stack with `Stack.from_param!(params[:stack_id])` instead of the token-scoped `stacks.from_param!` used by every other API controller, so a token that is only authorised for one stack can be used to read the CI status (name, last build status/label, lock state) of any other stack.

### Finding Description
Every other resource controller under `Shipit::Api` inherits `stack` from `Api::BaseController`, which restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` when the authenticated `ApiClient` is bound to a specific stack: [1](#0-0) 
`ApiClient` supports this stack-scoping via its `stack` association and is created that way through `Api::ApiClientsController`/`ApiClientsController` when an operator wants a token limited to a single stack. [4](#0-3) 

`Api::CCMenuController` overrides `stack` to bypass this scoping and hits the unrestricted `Stack` model directly: [5](#0-4) 
Its permission check only verifies the class-level `read:stack` bit, not that the specific `stack_id` in the request matches the token's bound stack: [6](#0-5) [7](#0-6) 

This is the same root-cause shape as the BunniHook report: a binding meant to restrict an operation to a specific authorized unit (there, the swap-received amount; here, the stack a token is scoped to) is dropped, and the code instead operates over the unrestricted global pool (there, the full token balance; here, `Stack.all` via `Stack.from_param!`).

### Impact Explanation
An attacker (or any holder of a stack-scoped `ApiClient` token, e.g. an integration credential intentionally restricted to a single repository/stack by an operator) can query `GET /api/stacks/:stack_id/ccmenu.xml` for any `stack_id`, not just the one the token was authorised for. This discloses stack name, lock status, and last build status/label for stacks outside the token's intended scope — an unauthorised cross-stack read of stack state, matching the High-severity bucket for "escalation into `Shipit.github_teams` authorization" / "unauthenticated read of stack state."

### Likelihood Explanation
High. Any legitimately-issued, single-stack-scoped API token (a normal, supported configuration via `ApiClient#stack`) is affected; no additional privilege is needed beyond possessing that one scoped token, and the request is a simple unauthenticated parameter change (`stack_id` in the URL).

### Recommendation
Change `Api::CCMenuController#stack` to reuse the scoped lookup from `Api::BaseController` (i.e. `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so stack-scoped tokens cannot read data for stacks they are not bound to.

### Proof of Concept
1. Operator creates a stack-scoped `ApiClient` with `stack: stack_a` and permission `read:stack` (supported via `ApiClient` model/`ApiClientsController`).
2. Using that token's `authentication_token`, call `GET /api/stacks/{stack_b.to_param}/ccmenu.xml` (any other stack's identifier).
3. `Api::CCMenuController#stack` resolves via `Stack.from_param!(params[:stack_id])`, ignoring the token's `stack_id` restriction, and returns `stack_b`'s CI status instead of rejecting the request. [8](#0-7)
