### Title
ReDoS via catastrophic-backtracking email regex in `isValidEmail` - (File: validation_utils.js)

### Summary
`validation_utils.js` exposes `isValidEmail()`, which is called from `uri.js` (payment-request/pairing URI parsing) and `wallet.js` (wallet/device message handling) to validate address-like strings. The regex used contains the same class of catastrophic-backtracking construct that GHSA-pjwm-cr36-mwv3 identifies in Giskard's URL-detection regex: a repeated group whose alternatives overlap on the same character class, enabling exponential backtracking on adversarial input.

### Finding Description
`isValidEmail` is defined as: [1](#0-0) 

The core of the regex is:
```
^(([^<>()\[\]\\.,;:\s@"]+(\.[^<>()\[\]\\.,;:\s@"]+)*)|(".+"))@(...)$
```
The subexpression `([^<>()\[\]\\.,;:\s@"]+(\.[^<>()\[\]\\.,;:\s@"]+)*)` repeats a `+`-quantified character class separated by `.`, where the character class itself can also match `.`-adjacent characters in ambiguous ways once the required trailing `@...` anchor fails to match. This is structurally identical to the vulnerable pattern class described in the Giskard advisory (an unanchored/ambiguous repeated group used for link/email detection), which is a textbook CWE-1333 catastrophic-backtracking shape: nested/overlapping quantifiers where many different partitionings of the same input segment are tried before the engine gives up.

This function is invoked to validate the `address` field of a `byteball:`/`obyte:` URI: [2](#0-1) 

and is also referenced 3 times in `wallet.js`, which handles wallet/device message and payment-request processing (paired-device or locally-supplied URIs/strings ultimately reach this validator).

### Impact Explanation
If an attacker (e.g., a paired device sending a crafted payment-request URI, or any code path that funnels an untrusted string, such as a long sequence of non-`@`/non-`.` characters with many trailing dots and no valid `@domain` suffix, into `isValidEmail`) can control the input string, the regex engine can be driven into near-exponential backtracking, freezing the Node.js event loop that runs the wallet/URI-parsing logic. Because Node.js is single-threaded, this can stall wallet message processing, payment-request handling, and other event-loop-bound operations for the duration of the runaway match, i.e., a denial-of-service of the wallet/message-handling component.

### Likelihood Explanation
The regex is reachable through `parseUri()` in `uri.js` whenever an "address" style URI is parsed and the address value is not already a valid on-chain address (`isValidAddress`) — `isValidEmail` is the very next check performed on attacker-suppliable text. Constructing a string that fails all the alternate checks but is long and dot/`@`-ambiguous is trivial for any party that can hand a URI/string to the wallet (e.g., via a pairing/chat message), giving a straightforward trigger path with low complexity.

### Recommendation
Replace the email regex with a non-backtracking, linear-time validator (e.g., use `RegExp` with atomic-group-equivalent alternatives, split-and-check via `String.split('@')` plus simpler bounded character-class checks, or a maintained safe email-validation library), and/or impose a strict maximum length on the input before it is passed to `isValidEmail`, mirroring the upstream Giskard fix which replaced the vulnerable regex with a non-catastrophic pattern.

### Proof of Concept
Calling the vulnerable function directly demonstrates the blow-up:
```js
var ValidationUtils = require('./validation_utils.js');
var payload = 'a'.repeat(30) + '!'; // many repeats of the quantified class, no valid @domain suffix
console.time('email');
ValidationUtils.isValidEmail(payload + '.'.repeat(5) + 'a'.repeat(30));
console.timeEnd('email');
```
Increasing the count of repeated `a.` segments before an invalid terminator causes the match time to grow superlinearly, consistent with catastrophic backtracking in `([^...]+(\.[^...]+)*)`. This can be delivered end-to-end via `parseUri()`'s address branch: [2](#0-1) 
by supplying a `byteball:<crafted-string>` URI where `<crafted-string>` is not a valid ocore address and matches the above pattern.

**Note on completeness:** I was unable to fully trace the three `isValidEmail` call sites inside `wallet.js` (only match counts were retrieved, not the surrounding code), so I cannot confirm with certainty whether all of them are reachable from a fully untrusted paired-device message versus locally-entered wallet UI text. The `uri.js` path, however, is clearly reachable from externally supplied URI strings. If you need the exact `wallet.js` invocation context confirmed, a Devin session with full file access would be needed to inspect `wallet.js` in its entirety.
