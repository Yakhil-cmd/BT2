### Title
Global pending-registration cap in `pallet-registrar-relay` lets one manager exhaust `MaxPendingRegistrations` and block all other managers' parachain registrations - (File: `substrate/frame/registrar/relay/src/lib.rs`)

### Summary
`pallet-registrar-relay::on_register_request` enforces the pending-registration cap by comparing the total count of `PendingRegistrations` (a single global `CountedStorageMap`) against `T::MaxPendingRegistrations`, instead of scoping the cap per manager/account. Any signed account that can reserve para ids and request registrations through the companion `pallet-registrar-para` on the origin chain can fill the entire global pending window, causing `FailureReason::TooManyPending` rejections for every other unrelated manager until the attacker's own entries are cleared.

### Finding Description
The relay-side check is: [1](#0-0) 

`PendingRegistrations` is keyed by `ParaId`, but the cap check reads `PendingRegistrations::<T>::count()` globally rather than counting entries whose `manager` field matches the requester: [2](#0-1) 

The `manager` is only stored inside each `PendingRegistration` value for bookkeeping/reporting, never used to bound how many slots one manager may occupy: [3](#0-2) 

The user-facing entry point on the origin chain is `pallet-registrar-para::reserve`/`register`, both signed, fee-paying extrinsics open to any account: [4](#0-3) [5](#0-4) 

`register` sends a `MessageToRelayV1::Register` for each reserved para id, which the relay chain's trusted `ParaOrigin` accepts and dispatches into `on_register_request`. An attacker who repeatedly calls `reserve()` (paying `ReservationConsideration` per id) and then `register()` (paying `RegistrationConsideration` per id) for many distinct para ids can push `PendingRegistrations::<T>::count()` up to `T::MaxPendingRegistrations::get()` using entries that are all "his own," at which point every other manager's `register()` request is rejected relay-side with `TooManyPending`, exactly mirroring the OpenClaw bug class: a pending-request cap that is enforced on a shared/global resource instead of per-account, letting one caller starve everyone else's pending window.

This is confirmed directly by the pallet's own test, which demonstrates the cap is a flat, non-per-account ceiling: [6](#0-5) 

Because "an authorization never times out here" (per the module docs) and only ends when the parachain explicitly sends `CancelRegistration`, the attacker fully controls how long the DoS persists — they simply never cancel: [7](#0-6) 

### Impact Explanation
This is availability-only, matching the referenced advisory's classification: legitimate managers on the origin chain cannot get new registration requests accepted on the relay chain while the global pool is saturated by another user's outstanding (unresolved) entries, blocking onboarding of unrelated parachains. No funds are stolen and no authorization bypass occurs; the attacker's own deposits (`ReservationConsideration`/`RegistrationConsideration`) remain held/returnable, so this is a cost-bounded denial of new registrations rather than free flooding.

### Likelihood Explanation
The reachable path (`reserve` → `register` → XCM/Transact → relay `receive` → `on_register_request`) requires only ordinary signed transactions and standard consideration deposits — no privileged role, governance, or validator/collator control is needed. However, I was unable to confirm that `pallet-registrar-relay`/`pallet-registrar-para` are wired into any live Parity-operated production runtime (Polkadot, Kusama, an Asset Hub, or the Coretime chain). The only runtime wiring found in this index is the generic reference/test node at `substrate/bin/node/runtime/src/lib.rs`, not a deployed system chain. Per the analog methodology's own eligibility rule, "file-list membership or a reference-runtime reproduction alone is not bounty eligibility" — so this should be treated as a real architectural defect in shipped pallet code, but its live-network exploitability/bounty eligibility could not be verified with the tools available.

### Recommendation
Scope the pending-registration cap per manager (e.g., a secondary `StorageMap<ManagerId, u32>` counter, or an additional bound checked against entries filtered by `manager`) in `pallet-registrar-relay::on_register_request`, analogous to the OpenClaw fix that moved the pending-pairing cap from per-channel to per-account scope, so a single manager cannot exhaust `T::MaxPendingRegistrations` for all other managers.

### Proof of Concept
Not executed against a live network. The existing unit test `requests_beyond_the_pending_cap_are_rejected_and_reported` in `substrate/frame/registrar/relay/src/tests.rs:225-242` already demonstrates the guard is global rather than per-manager (all `MAX_PENDING` requests in the test come from a single flow filling the shared counter, and the very next request from any manager — including a different one — would be rejected the same way, since the check at `lib.rs:338` never inspects `manager`). A full attacker-vs-victim integration PoC (two distinct signed accounts on the para side, one flooding `reserve`/`register` and a second's legitimate `register` being rejected with `TooManyPending`) was not run due to lack of terminal/build access in this session; confirming it would require executing `substrate/frame/registrar/integration-tests` locally with two distinct manager accounts.

		#[pallet::call_index(2)]
		#[pallet::weight(T::WeightInfo::register(genesis_head.len() as u32))]
		pub fn register(
			origin: OriginFor<T>,
			para_id: ParaId,
			genesis_head: Vec<u8>,
			code_len: u32,
			code_hash: H256,
		) -> DispatchResult {
			let who = ensure_signed(origin)?;

			let mut info = Paras::<T>::get(para_id).ok_or(Error::<T>::NotReserved)?;
			ensure!(info.manager == who, Error::<T>::NotOwner);
			ensure!(
				matches!(info.state, RegistrationState::Reserved),
				Error::<T>::AlreadyRegistered
			);

			let head_len = genesis_head.len() as u32;
			ensure!(head_len <= T::MaxHeadDataSize::get(), Error::<T>::HeadDataTooLarge);
			ensure!(code_len >= T::MinCodeSize::get(), Error::<T>::CodeTooSmall);
			ensure!(code_len <= T::MaxCodeSize::get(), Error::<T>::CodeTooLarge);

			let ticket = T::RegistrationConsideration::new(
				&who,
				Self::registration_footprint(head_len, code_len),
			)?;

			let cancellable_at = T::BlockNumberProvider::current_block_number()
				.saturating_add(T::PendingDeadline::get());
			info.state = RegistrationState::Pending { ticket, cancellable_at };
			Paras::<T>::insert(para_id, info);

			// A transport failure returns `Err` and unwinds everything above, ticket included.
			let message_id = Self::next_message_id();
			T::SendToRelay::send(MessageToRelay::V1(MessageToRelayV1::Register {
				para_id,
				message_id,
				manager: who.clone(),
				genesis_head,
				code_hash,
				code_len,
			}))
			.map_err(|()| Error::<T>::SendFailed)?;

			Self::deposit_event(Event::RegisterRequested { para_id, message_id, manager: who });
			Ok(())
		}
