## Title
Reachable Assertion / Full-Node Crash via `throw Error` Invariants in AA Response-Unit Validation - (File: `aa_composer.js`)

### Summary
The Open5GS CVE is a classic "reachable assertion": an SBI request the NRF accepts from a normal peer (deleting its own registry entry) drives an internal state into a condition that trips a hard `assert`, crashing the process and killing the discovery service. The analogous class in `ocore` is a hard-coded invariant expressed as a bare `throw Error(...)` inside the deterministic Autonomous-Agent (AA) execution path that every full node runs when it processes a trigger unit. If any of these invariants can be violated by ordinary, unprivileged input (an AA trigger unit posted by any user), the resulting uncaught exception propagates up through the synchronous callback chain and crashes the Node.js process, exactly like the reachable-assertion pattern in the report.

### Finding Description
`aa_composer.js`'s `handleTrigger()` computes a response unit for an AA trigger and then calls `validateAndSaveUnit()` to validate/save that self-generated unit under the write lock: [1](#0-0) 

Every branch of the `validation.validate()` callbacks used here is a bare `throw Error(...)` rather than a recoverable error path:
- `ifJointError` → `throw Error("AA validation joint error: " + err)`
- `ifTransientError` → `throw Error("AA validation transient error: " + err)`
- `ifNeedHashTree` → `throw Error("AA validation unexpected need hash tree")`
- `ifNeedParentUnits` → `throw Error("AA validation unexpected dependencies: ...")`
- `ifOkUnsigned` → `throw Error("AA validation returned ok unsigned")`
- `ifOk` with `sequence !== 'good'` → `throw Error("nonserial AA")`

These are treated as "can never happen" assertions on the assumption that a unit composed internally by the AA engine is always well-formed, has its parents already known, and never conflicts (double-spends) with anything else. This mirrors the NRF bug: a "should never happen" condition guarded only by an assertion, reachable from ordinary, attacker-influenceable input (the trigger unit and the oscript logic it invokes) rather than from a privileged/internal-only caller.

None of the callers up the stack (`handleTrigger`, `handlePrimaryAATrigger`, `handleAATriggers`, and ultimately `writer.saveJoint`/`network.js` unit processing) wrap this call in a try/catch that gracefully bounces the trigger; the exception is synchronous and uncaught, which is caught only by the top-level `process.on('uncaughtException', …)` handler in `network.js`, which explicitly **re-throws to crash the process**: [2](#0-1) 

Because AA execution is deterministic and mandatory for consensus (every full node must execute the same AA logic to agree on state and stability), a single crafted trigger to a vulnerable AA (or an AA definition composed by an attacker, since AAs may be freely deployed by anyone) that drives one of these invariants to fail will crash **every full node** that processes that trigger — not just one operator's node.

### Impact Explanation
This matches the required "network unable to confirm new units" bar: any full node (attacker-controlled or honest) that reaches the offending trigger in its `aa_triggers` processing queue crashes via the uncaught-exception handler at `network.js:4530-4543`, taking down unit/joint validation, AA processing, and network services on that node. Because AA execution order and content are consensus-relevant, this can be replicated across the network by simply broadcasting the triggering unit, which is exactly the kind of reachable-assertion DoS described in the CVE, but with a more severe blast radius (multiple/most full nodes vs. a single NRF instance).

### Likelihood Explanation
Reachability requires: (1) deploying or using an existing AA whose oscript composes payment/response messages in a way that can produce a genuinely conflicting/malformed response unit (e.g., two response units racing for the same underlying coin/output across concurrent primary/secondary triggers, or a response referencing a parent that isn't yet locally known at validation time), and (2) sending a trigger. Both are available to any unprivileged unit poster/AA trigger sender — no operator, hub, or peer trust is required. Establishing the exact oscript pattern that flips `sequence !== 'good'` or forces `ifNeedParentUnits` for a self-generated unit would need further fuzzing/testing against `handleTrigger`'s parent-selection (`pickParents`) and balance/serialization logic, so likelihood is assessed as moderate rather than trivially certain.

### Recommendation
Replace the `throw Error(...)` assertions in `validateAndSaveUnit()`'s validation callbacks (`aa_composer.js:1800-1837`) with recoverable failure handling: if the AA-generated response unit fails validation for any reason (joint error, transient error, unexpected dependency, nonserial), bounce the trigger (or the specific secondary trigger) with a descriptive error via the existing `bounce()`/`revert()` machinery instead of crashing the process. At minimum, wrap the call in a try/catch that converts these conditions into a bounce path, and audit `pickParents()`/`handleSecondaryTriggers()` for the specific double-spend/parent-selection races that could realistically trip `sequence !== 'good'` or `ifNeedParentUnits` under concurrent AA execution.

### Proof of Concept
A concrete unit-level PoC (an oscript definition and trigger sequence proven to flip `objAAValidationState.sequence !== 'good'` or to make `ifNeedParentUnits` fire for a self-composed unit) could not be fully constructed from static analysis alone; it would require exercising `handleTrigger`/`pickParents` concurrency (e.g., two triggers to the same AA landing in the same MC unit, or a secondary-trigger chain racing for the same balance/output) in a live/test node to confirm which invariant is reachable in practice. The exact reachable code paths and assertions to target are cited above.
