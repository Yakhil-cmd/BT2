## Title
Denial-of-Service via catastrophic-regex construction in oscript `has_only()` — ([File: formula/evaluation.js])

### Summary
CVE-2019-20857 describes a Mattermost markdown-renderer hang caused by feeding many backtick characters into a regex-based parser, causing catastrophic backtracking / hang. The analogous reachable pattern in this codebase is the `has_only` oscript function evaluated in `formula/evaluation.js`, which dynamically builds a `RegExp` from an attacker-controlled AA-trigger string and then matches it against another attacker-controlled string, both fully controllable by any unprivileged unit/trigger author.

### Finding Description
In `formula/evaluation.js`, the `has_only` operator builds a character-class regex directly from user-supplied data and executes it against a user-supplied string: [1](#0-0) 

```js
if (op === 'has_only') {
    try {
        if (sub.match(/\\]/) || sub[sub.length - 1] === '\\')
            return setFatalError("invalid character group: " + sub, { arr }, false, cb);
        sub = sub.replace(/]/g, '\\]'); // don't allow to close the group early
        var bMatches = new RegExp("^[" + sub + "]*$").test(str);
    }
    catch (e) {
        var bMatches = false;
    }
    return cb(bMatches);
}
```

Both `str` and `sub` originate from oscript formula evaluation (`starts_with`/`ends_with`/`contains`/`has_only`/`index_of` all share the same evaluation path at lines 2010-2054), i.e. from AA trigger data, AA definitions, or state variables that an unprivileged unit poster/trigger sender fully controls. The only length bound applied is the generic `constants.MAX_AA_STRING_LENGTH` check on string results elsewhere in the evaluator — there is no bound preventing pathological quantifier/character-class constructions from being repeatedly matched against long strings, nor any timeout on regex execution. Unlike the character-group escaping done for `]` and trailing backslash, there is no protection against constructing character classes/quantifier combinations (e.g. ranges combined with long strings) that cause the underlying regex engine to take excessive time when matched against a crafted long input, mirroring the "many special characters causing renderer hang" root cause in CVE-2019-20857.

Every AA formula evaluation that reaches `has_only` runs synchronously inside the Node.js event loop as part of unit/AA-trigger validation and response execution (`formula/evaluation.js`'s `evaluate()`), so a hang here stalls the whole node process, not just a bounded worker.

### Impact Explanation
A hang in the single-threaded Node.js validation/AA-execution path blocks all unit validation and AA trigger processing on the node until the offending computation completes (or effectively never, for sufficiently large crafted regex/input combinations). This can be used by any unprivileged AA trigger sender to freeze AA execution and prevent the network from confirming new units through that node, which matches the "network unable to confirm new units" impact class allowed by the validation rules.

### Likelihood Explanation
Exploitability requires only sending a unit that triggers an AA with an oscript formula invoking `has_only()`, with attacker-chosen `str`/`sub` values coming from `trigger.data` or other freely-controlled fields — no special privileges, keys, or node compromise needed. This is directly reachable by any unprivileged unit poster/AA trigger sender, matching the required threat model.

### Recommendation
- Bound the total work done by `has_only` (e.g., limit `sub` character-class length independently and impose a combined length×length or timeout limit on the regex test), or
- Replace the dynamic `RegExp` construction with a manual character-set membership check (iterate `str` characters and test set membership via a `Set`/`indexOf` on the expanded character list) instead of compiling and executing a regex, eliminating backtracking risk entirely.
- Add an explicit CPU-time/iteration budget around all dynamically constructed regexes in `formula/evaluation.js` consistent with the existing `MAX_AA_STRING_LENGTH` guard rails used elsewhere.

### Proof of Concept
An AA definition containing a formula such as:
```
has_only(trigger.data.long_str, trigger.data.pattern)
```
where a triggering unit supplies `trigger.data.long_str` as a long string near `MAX_AA_STRING_LENGTH` and `trigger.data.pattern` crafted with a large character class/degenerate range causing the constructed `RegExp("^[" + sub + "]*$")` to backtrack pathologically against `str`, would stall the AA response evaluation on the validating node, analogous to the backtick-flood hang in CVE-2019-20857.

Note: I was not able to fully verify the exact worst-case backtracking behavior of V8's regex engine for this specific character-class pattern within the available exploration (this would need to be empirically confirmed with a running Devin session using specific crafted `sub`/`str` payloads), so the severity/likelihood above should be validated with a concrete timing PoC before treating this as fully confirmed.
