### Title
Cross-organization CI-status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret used to authenticate an inbound webhook purely from the payload's `repository.owner.login` (falling back to `organization.login`), then dispatches the entire, already-parsed JSON body to event handlers. [1](#0-0) [2](#0-1)  For the `status` event, `StatusHandler#process` looks up the target `Commit` **only by `sha`, with no scoping to the repository/organization that was used to authenticate the request**: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`. [3](#0-2) 

### Finding Description
Shipit supports hosting multiple, independently-trusted GitHub organizations from a single instance (`config/secrets.yml` `github:` per-org sections), each with its own `webhook_secret`. [4](#0-3)  The binding that should hold is: **the organization whose secret validated the signature == the repository/commit the handler is permitted to mutate**. Instead:

- Signature verification only checks that the raw body is HMAC-signed with the secret belonging to whatever organization is named in `repository.owner.login` / `organization.login` of the payload itself. [5](#0-4) 
- Once verified, `WebhooksController#create` hands the fully attacker-controlled JSON to `Shipit::Webhooks.for_event(event)` handlers with no further binding of "authenticating org" to "target records". [6](#0-5) 
- Most handlers derive their target via `Handler#stacks`, which resolves `Repository.from_github_repo_name(payload.dig('repository','full_name'))` — a payload field that is never cross-checked against `repository.owner.login`. [7](#0-6) 
- `StatusHandler` goes further and doesn't even scope by repository at all — it matches `Commit.where(sha: params.sha)` globally across every stack in the database. [3](#0-2) 

Because an organization owner/admin who legitimately controls a GitHub App installed for their **own** (low-trust) org knows that org's `webhook_secret`, they can sign an arbitrary JSON body with it. They set `repository.owner.login` (or `organization.login`) to their own org so the signature check passes, while setting `sha` to the SHA of a commit that belongs to a **completely different** stack/repository/organization hosted on the same Shipit instance. `Shipit::Webhooks.for_event('status')` → `StatusHandler#process` will then create a fabricated GitHub commit status (e.g. `state: "success"`, arbitrary `context`) on that unrelated commit, with no verification that the forging org has any relationship to the affected repository. [8](#0-7) 

This directly affects `Commit#deployable?`, which is computed from the fabricated status: `!locked? && (stack.ignore_ci? || (success? && !blocked?))`. [9](#0-8)  `success?` is delegated to `status`, which aggregates the (forged) `statuses` records. [10](#0-9) [11](#0-10)  A forged passing status also triggers `stack.schedule_merges` and continuous-delivery scheduling on the victim stack via `add_status`. [12](#0-11) 

### Impact Explanation
This breaks the "organization authenticated vs. repository written" trust boundary called out in scope: an attacker who only controls one tenant organization's webhook secret can forge required-CI status/deployability state for commits belonging to a completely unrelated organization/stack on the same Shipit instance. Since `ci.require` / deployability gating relies on `Commit#deployable?`/`success?`, this can enable an **unauthorized deploy** (bypassing required CI checks) or trigger unwanted continuous-delivery/merge actions on a victim's stack — matching the in-scope "Critical: unauthorized deploy" / escalation impact criteria.

### Likelihood Explanation
Requires the attacker to control (be an admin of) at least one GitHub organization/App that is configured as a trusted tenant on the same multi-org Shipit deployment — a documented, supported configuration (`docs/setup.md`, "Using Multiple Github Applications"). [13](#0-12)  No Shipit session, API token, or GitHub write access to the victim repository is needed — only the webhook secret of the attacker's own tenant org and knowledge/guess of a target commit SHA (SHAs are often public via GitHub, PRs, CI logs, etc.). This is realistic in any shared/multi-tenant Shipit deployment.

### Recommendation
In `WebhooksController#verify_signature` / `Handler`, cryptographically bind the authenticated organization to the resource being mutated: after verifying the signature for `repository_owner`, reject or ignore payloads whose `repository.full_name` owner does not match `repository_owner`. In `StatusHandler` (and any other handler mutating records by cross-payload lookups), scope `Commit`/status lookups by the repository resolved from the authenticating organization (e.g., `stack.repository.owner == repository_owner`) instead of a bare `sha`/global lookup.

### Proof of Concept
1. Configure Shipit with two orgs, `attacker-org` and `victim-org`, each with its own GitHub App/`webhook_secret` (multi-org config).
2. As an owner of `attacker-org`, note its `webhook_secret`.
3. Identify a commit SHA belonging to a stack under `victim-org` (e.g. from a public PR).
4. POST to `/webhooks` with header `X-Github-Event: status`, body:
```json
{
  "sha": "<victim-org commit sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/some-repo" }
}
```
5. Sign the raw body with `attacker-org`'s `webhook_secret` and set `X-Hub-Signature` accordingly.
6. `verify_signature` passes (uses `attacker-org`'s secret). `StatusHandler#process` finds the commit purely by `sha` and calls `commit.create_status_from_github!`, creating a forged "success" status on the `victim-org` commit, altering its `deployable?` state.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.
