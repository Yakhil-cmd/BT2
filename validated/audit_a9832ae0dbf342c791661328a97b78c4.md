### Title
Unbounded dust-output consumption when an AA composes an asset payment can freeze AA custodial funds - ([File: aa_composer.js])

### Summary
When an AA sends a payment in a custodial (non-`base`) asset, `completePaymentPayload()` queries **all** unspent outputs held by the AA for that asset with no `LIMIT` and no minimum-amount ("dust") filter, then consumes every returned row in `iterateUnspentOutputs()` until the target amount is reached. An unprivileged unit poster can flood the AA's address with a very large number of near-zero-value outputs of that asset, forcing the AA (on its next attempt to pay out in that asset) to build a payment message with an unbounded number of inputs, which can make the response unit too large to compose/broadcast, permanently blocking the AA's ability to pay out that asset.

### Finding Description
In `completePaymentPayload()` (`aa_composer.js`), the query used to find spendable UTXOs at the AA's own address differs for base bytes vs. custodial assets: [1](#0-0) 

For the base asset there is an explicit dust filter (`amount>=FULL_TRANSFER_INPUT_SIZE`), with the accompanying comment stating this exists specifically "to prevent dust attack: spamming the AA with very small outputs so that the AA spends all its money for fees when it tries to respond." **This filter is only applied when `asset` is falsy** (i.e., paying bytes). When `asset` is set (custodial/definer-issued token held by the AA), the `WHERE` clause has no minimum-amount condition and, critically, the SQL has **no `LIMIT`** at all — unlike the wallet's own `pickDivisibleCoinsForAmount()` in `inputs.js`, which explicitly caps additional inputs to `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE-2`: [2](#0-1) 

`iterateUnspentOutputs()` then loops over every row returned and pushes each into `payload.inputs`, continuing until the accumulated `total_amount` reaches `target_amount`: [3](#0-2) 

Normally, `validatePaymentInputsAndOutputs()` rejects payment messages with more than `MAX_INPUTS_PER_PAYMENT_MESSAGE` (128) inputs, but this cap is explicitly waived for AA-generated units: [4](#0-3) 

So AA response units are permitted to carry an arbitrarily large number of inputs. Any unprivileged user can send the AA's address thousands or millions of tiny (e.g., amount=1) outputs of a custodial asset the AA holds (a normal `payment` message any author can post, subject only to per-unit output count limits, so the attacker simply spreads the dust across many units/messages over time). The next time the AA composes a payment in that asset (e.g., forwarding a user's withdrawal), `readStableOutputs`/`readUnstableOutputsSentByAAs` will return all of these dust outputs (ordered deterministically by `main_chain_index, unit, output_index`), and `iterateUnspentOutputs` will consume them one by one because none of them individually helps reach `target_amount` quickly. This inflates `payload.inputs`, `objUnit` size, and processing cost proportionally to the amount of dust the attacker chooses to inject, with no cap analogous to the wallet's `MAX_INPUTS_PER_PAYMENT_MESSAGE-2` limit or the byte-asset dust filter.

### Impact Explanation
If the number of dust inputs required to be included grows large enough, the composed AA response unit can exceed `constants.MAX_UNIT_LENGTH`, or simply become computationally/storage expensive enough to repeatedly fail composition/validation/broadcast (`bounce`/`revert` paths in `handleTrigger`). Because the AA always starts consuming outputs in the same deterministic order and there is no way to skip dust or cap the input count for asset payments, the condition is self-perpetuating: as long as the dust outputs remain unspent at the AA address, every subsequent attempt to pay out that asset re-encounters the same unbounded consumption. This can durably prevent the AA from ever composing a valid payment in that asset, freezing legitimate user funds/withdrawals held in that asset by the AA — a fund-freezing denial-of-service directly analogous to the reported Hubble `VUSD.processWithdrawals` issue (attacker-supplied worthless entries force the honest processor to pay a disproportionate, eventually infeasible cost to reach real entries).

### Likelihood Explanation
Likelihood is high for any AA that custodial-manages a token asset and pays it out based on accumulated address balance (a common pattern, e.g., bridges/exchangers/vaults). Sending dust outputs of an asset to any address, including an AA address, requires no special privilege — it's an ordinary `payment` message any unit author can construct, and the byte cost of doing so is comparatively small relative to the eventual gas/processing cost forced on the AA and the width of the freeze.

### Recommendation
Apply the same anti-dust protections used for base-asset payments to custodial asset payments in `completePaymentPayload()`:
- Add a minimum-amount filter to the `readStableOutputs`/`readUnstableOutputsSentByAAs` queries when `asset` is set (e.g., ignore outputs below some fraction of typical fee/output size for that asset), and/or
- Add an explicit `LIMIT` on the number of additional inputs collected (mirroring `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE - 2` used in `inputs.js`), falling back to `issueAsset`/failure gracefully instead of unboundedly growing `payload.inputs`.
- Consider enforcing `MAX_INPUTS_PER_PAYMENT_MESSAGE` for AA-composed payments as well, or explicitly documenting/handling the "too many small outputs" case so the AA can still make partial progress instead of stalling entirely.

### Proof of Concept
1. Deploy/observe an AA that custodial-holds an issued asset `X` and, upon trigger, sends a payment of asset `X` from its own balance to a recipient (a common bridge/vault AA pattern).
2. As an unprivileged user, repeatedly post ordinary `payment` messages transferring output amount = 1 of asset `X` to the AA's address, across many units, accumulating a very large number (e.g., tens of thousands) of dust outputs at that address.
3. Trigger the AA to make a normal, otherwise-valid payout of asset `X`.
4. Observe that `completePaymentPayload()` (`aa_composer.js:1140-1155`, `1102-1138`) queries and iterates over all unspent `X` outputs (no `LIMIT`, no dust filter) at the AA address, pulling in the attacker's dust entries before/along with legitimate ones, inflating `payload.inputs` without bound (since `validation.js:2137-2138` exempts AA units from `MAX_INPUTS_PER_PAYMENT_MESSAGE`).
5. With enough injected dust, the resulting `objUnit` exceeds size/complexity limits (or otherwise becomes impossible to reliably compose and broadcast), causing the AA's payout to fail/bounce repeatedly, freezing the AA's ability to pay out asset `X` while the dust remains unspent.
