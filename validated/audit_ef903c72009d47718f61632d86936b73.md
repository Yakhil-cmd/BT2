### Title
Bridge KAIA/ERC20 Transfer Permanently Locked When Recipient Contract Reverts or Is Blacklisted — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`, `contracts/service_chain/bridge/BridgeTransferERC20.sol`)

---

### Summary

The Kaia service-chain bridge's `handleKLAYTransfer` and `handleERC20Transfer` functions unconditionally push assets to the `_to` recipient address. If the recipient is a contract that reverts on receiving KAIA, or if the bridged ERC20 token has a blacklisting mechanism (e.g., USDC) and `_to` is blacklisted, every operator attempt to settle that nonce will revert. Because there is no skip or override mechanism, the bridged assets are permanently locked inside the bridge contract with no recovery path.

---

### Finding Description

**`handleKLAYTransfer` — `BridgeTransferKLAY.sol`**

The execution order is:

1. `_lowerHandleNonceCheck` — gate check
2. `_voteValueTransfer` — operator quorum
3. `_setHandledRequestTxHash` — marks request tx as handled
4. `handleNoncesToBlockNums[_requestedNonce] = _requestedBlockNumber` — records block
5. `_updateHandleNonce` — advances `lowerHandleNonce` / `recoveryBlockNumber`
6. `emit HandleValueTransfer`
7. **`(bool ok, ) = _to.call.value(_value)("");`**
8. **`require(ok, "handleKLAYTransfer: transfer failed");`** [1](#0-0) 

Steps 3–6 mutate state before the transfer. However, because Solidity reverts the entire transaction on `require(ok, ...)`, all state mutations are also rolled back. The nonce is therefore never consumed. Operators will retry indefinitely, but every attempt reverts if `_to` is a contract with no `receive()` / `fallback()` or one that explicitly reverts.

**`handleERC20Transfer` — `BridgeTransferERC20.sol`**

In lock-unlock mode (non-mintBurn):

```solidity
IERC20(_tokenAddress).safeTransfer(_to, _value);
``` [2](#0-1) 

`safeTransfer` reverts if the token contract reverts — which happens when `_to` is blacklisted by a token with an access-control list (USDC, USDT, etc.). The entire `handleERC20Transfer` call reverts, the nonce is never consumed, and the tokens remain locked in the bridge.

**No skip mechanism exists.** `_lowerHandleNonceCheck` only prevents re-handling nonces below `lowerHandleNonce`: [3](#0-2) 

`lowerHandleNonce` advances only when `handleNoncesToBlockNums[i] > 0` for consecutive nonces: [4](#0-3) 

Because the failing nonce's state is always reverted, `handleNoncesToBlockNums[N]` is never set, `lowerHandleNonce` never advances past N, and `recoveryBlockNumber` is frozen at the block before N.

---

### Impact Explanation

- **Permanent loss of bridged assets.** The user burns or locks assets on the source chain (via `requestKLAYTransfer` / `requestERC20Transfer`), but the destination-side settlement always reverts. The assets are irrecoverably locked in the bridge contract.
- **Recovery mechanism frozen.** `recoveryBlockNumber` is stuck at the block preceding the failing nonce. The off-chain recovery loop (`vt_recovery`) will perpetually re-attempt the same failing nonce.
- **Subsequent `lowerHandleNonce` advancement blocked.** While operators can still handle higher nonces (the check is `lowerHandleNonce <= _requestedNonce`), the lower bound never advances, which corrupts the sliding-window invariant the bridge relies on for replay protection and recovery. [5](#0-4) 

---

### Likelihood Explanation

**Trigger paths (no privileged access required):**

1. **KAIA path:** The `_to` address is a contract with no payable fallback (e.g., a multisig, a DeFi vault, or a contract deployed via CREATE2 after the request was submitted). Any user who bridges KAIA to such an address triggers the lock.
2. **ERC20 path (direct analog to the external report):** The `_to` address is blacklisted by the token issuer (USDC Centre, Tether, etc.) between the time the `RequestValueTransfer` event is emitted on the source chain and the time operators call `handleERC20Transfer` on the destination chain. The recipient can also intentionally get themselves blacklisted to grief the bridge or to prevent a specific settlement.
3. **CREATE2 griefing:** An attacker who knows the `_to` address in advance can deploy a reverting contract there before operators process the nonce.

The bridge explicitly supports USDC-class tokens (registered via `registerToken`), making path 2 realistic on mainnet. [6](#0-5) 

---

### Recommendation

1. **Pull pattern:** Instead of pushing assets to `_to` in `handleKLAYTransfer` / `handleERC20Transfer`, record `claimable[nonce][_to] += value` and let the recipient call a `claim()` function. This decouples settlement finality from recipient reachability.
2. **Fallback address:** If the push fails, send assets to a configurable `recoveryAddress` (e.g., the bridge owner) so the nonce is consumed and `lowerHandleNonce` can advance.
3. **Nonce skip governance:** Add an `onlyOwner` function to forcibly mark a nonce as handled (with assets sent to a recovery address) so the bridge is not permanently frozen on a single bad nonce.

---

### Proof of Concept

**KAIA path:**

```solidity
// Attacker deploys this at the _to address before operators process nonce N
contract RevertOnReceive {
    receive() external payable { revert("blocked"); }
}
```

Operators call `handleKLAYTransfer(..., N, ...)`. The call at line 98 of `BridgeTransferKLAY.sol` returns `ok = false`. `require(ok, ...)` reverts the entire transaction. All state (nonce, `lowerHandleNonce`, `handledRequestTx`) is rolled back. Every subsequent operator attempt for nonce N reverts identically. The user's KAIA is permanently locked.

**ERC20 / USDC path:**

1. User calls `requestERC20Transfer(USDC, _to, 1000e6, 0, "")` on the source chain. USDC is burned/locked.
2. USDC Centre blacklists `_to`.
3. Operators call `handleERC20Transfer(..., USDC, _to, 1000e6, N, ...)`.
4. `IERC20(USDC).safeTransfer(_to, 1000e6)` reverts (blacklist check in USDC).
5. Entire transaction reverts. Nonce N is never consumed. 1000 USDC is permanently locked in the bridge. [7](#0-6) [8](#0-7) [9](#0-8)

    function handleKLAYTransfer(
        bytes32 _requestTxHash,
        address _from,
        address payable _to,
        uint256 _value,
        uint64 _requestedNonce,
        uint64 _requestedBlockNumber,
        bytes memory _extraData

        public
        onlyOperators

        _lowerHandleNonceCheck(_requestedNonce);

        if (!_voteValueTransfer(_requestedNonce)) {

        _setHandledRequestTxHash(_requestTxHash);

        handleNoncesToBlockNums[_requestedNonce] = _requestedBlockNumber;
