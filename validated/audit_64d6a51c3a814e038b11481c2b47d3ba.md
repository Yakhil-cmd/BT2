### Title
Cross-organization webhook confusion allows forging a "verified" push event that targets a stack belonging to a different, uninvolved organization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The rebasing/deflationary-token analog here is a "verified vs. acted-upon" mismatch: the report's core flaw is that a value trusted at intake (the transferred amount) is not the same value later acted upon (the post-rebase balance). In `WebhooksController`, the value used to select and verify the cryptographic signature (`repository.owner.login`, or the `organization.login` fallback) is not the same value the event handlers subsequently use to locate the target `Stack` (`repository.full_name`). Nothing binds these two fields together, so an attacker who legitimately controls a GitHub organization/App installation wired into this Shipit instance can forge a payload whose `repository.full_name` names a completely different organization's repository.

### Finding Description
`WebhooksController#verify_signature` selects which organization's webhook secret to validate against using: [1](#0-0) [2](#0-1) 

`repository_owner` is read from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). This value is used only to fetch the org's `GithubApp`/secret via `Shipit.github(organization: repository_owner)` and HMAC-verify the payload with that org's own `webhook_secret` [3](#0-2) .

Once the signature check passes, the actual event handlers (e.g. `PushHandler`) resolve the target `Stack` using an entirely different field, `repository.full_name`: [4](#0-3) [5](#0-4) 

`Repository.from_github_repo_name` simply splits the string on `/` and looks up any repo/stack by that owner/name pair, with no cross-check against `repository.owner.login`: [6](#0-5) 

Because `repository.owner.login` (used for signature-org selection) and `repository.full_name` (used for stack lookup) are independent JSON fields inside the same attacker-supplied payload, nothing in the code enforces that `full_name` is consistent with `owner.login`. An attacker who controls their own organization's GitHub App/webhook configuration in this multi-tenant Shipit instance (a legitimate, unprivileged capability - configuring their own org's webhook secret does not require any Shipit session, `ApiClient` token, or access to the victim's repository) can:

1. Sign a payload with their own org's `webhook_secret` (which they legitimately know, since it's their own org's config).
2. Set `repository.owner.login` to their own org (so `Shipit.github(organization: ...)` resolves to their own app/secret and the HMAC check succeeds).
3. Set `repository.full_name` to `"victim-org/victim-repo"` - a stack that belongs to a different organization entirely.

The signature verification binds "the organization that authenticated" (their own org, whose secret validated the HMAC) to a completely different "repository that is written" (the victim stack acted upon by the handler) - exactly the trust-binding break called out in the analog rules.

### Impact Explanation
The `PushHandler` calls `stack.sync_github(expected_head_sha: params.after)` on the resolved victim stack: [7](#0-6) . This is an unauthorized, cross-organization write path into a `Stack` that the attacker's org has no legitimate access to or authorization over - directly matching the "unauthorized deploy/rollback" impact class, since it can force a resync against an attacker-chosen `expected_head_sha` on a victim's stack, which downstream can drive continuous-deployment behaviour or check-run/status handling for a repository the attacker never had write access to.

Other handlers (`pull_request` opened/labeled/reopened/closed, etc.) exhibit the identical pattern - they resolve `repository` via `Repository.from_github_repo_name(params.repository.full_name)` independent from the org used for signature verification - so the same confusion can archive/unarchive review stacks or otherwise mutate victim-org state [8](#0-7) .

### Likelihood Explanation
This requires the attacker to have a legitimate GitHub App/organization already configured in the shared Shipit instance's secrets (`secrets.github` keyed by organization, per `Shipit.github_app_config`) [9](#0-8) . This is realistic for any shared/multi-tenant Shipit deployment onboarding multiple organizations - a scenario the engine explicitly supports via `Shipit.github_organizations` and per-org webhook secrets. No Shipit session, `ApiClient` token, or victim-repo access is required; only the attacker's own org's webhook secret and the target stack's existence (which is discoverable, e.g. via stack listing pages or the public API).

### Recommendation
In `Handler#stacks` / `#repository_name`, validate that the repository referenced (`full_name`) belongs to the same organization that authenticated the webhook (`repository.owner.login` verified in `WebhooksController`), rejecting the payload if they diverge. Alternatively, thread the authenticated `repository_owner` from `WebhooksController` into each handler and require `repository.full_name.split('/').first == authenticated_owner` before performing any lookup or mutation.

### Proof of Concept
1. Configure two orgs in `secrets.github`: `attacker-org` (attacker controls this webhook secret) and `victim-org` (has a `Stack` for `victim-org/victim-repo`).
2. Attacker crafts a `push` payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org-webhook-secret, payload)` and POSTs to `/webhooks`.
4. `verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `attacker-org`'s `GithubApp`, and the HMAC check succeeds (attacker used their own known secret).
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")`, finds the victim's real stack, and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` - a write triggered against `victim-org`'s stack despite the signature having been verified against `attacker-org`'s credentials only.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end
```
