### Title
Webhook signature verification is skipped entirely when `webhook_secret` is unset, letting unauthenticated `membership` events grant `Shipit.github_teams` authorization - (File: lib/shipit/github_app.rb)

### Summary
`GitHubApp#verify_webhook_signature` unconditionally returns `true` when no `webhook_secret` is configured for the target organization, and `Shipit::WebhooksController` relies solely on this check to accept any inbound webhook body. Because `webhook_secret` is documented as *optional* per‑organization, any deployment (or any single organization in a multi‑org config) that leaves it blank accepts **completely unsigned** payloads. The `membership` webhook handler then trusts payload fields (`organization.login`, `team`, `member.login`) to create teams and add/remove `Membership` rows, which directly control `User#authorized?` via `Shipit.github_teams`. This is the same bug class as the reported issue — a value acted upon by application logic while the check meant to bound/verify it is a no‑op — except here the "check" is the HMAC webhook signature and the "acted upon value" is the entire attacker-controlled JSON payload.

### Finding Description
The webhook signature check is: [1](#0-0) 

`return true unless webhook_secret` means that whenever an organization's config in `secrets.yml` has no `webhook_secret` (explicitly called out as optional in `docs/setup.md` and demonstrated by test fixtures where it's left `nil`), **any** POST to `/webhooks` claiming that organization is treated as verified, with no HMAC check performed at all: [2](#0-1) [3](#0-2) 

The controller determines which organization's `GitHubApp` (and therefore which webhook secret) to use straight from the untrusted payload itself, before any verification occurs: [4](#0-3) [5](#0-4) 

Once `verify_signature` passes (trivially, when `webhook_secret` is blank), `WebhooksController#create` dispatches the raw, attacker-supplied JSON straight to registered handlers: [6](#0-5) 

The `membership` event handler trusts the payload's `organization`, `team`, and `member` fields with no independent validation against GitHub, creating a `Team` on the fly and adding/removing `Membership` records based solely on the request body: [7](#0-6) 

`Membership`/`Team` records are exactly what backs authorization: `User#authorized?` checks whether the current user's `teams` intersect `Shipit.github_teams`, which gates access to the entire application: [8](#0-7) [9](#0-8) 

**Binding broken (equality that should hold but doesn't):**
`organization the inbound webhook is cryptographically authenticated for == organization whose Team/Membership records the payload is allowed to mutate`.
When `webhook_secret` is blank for an organization, the left side of this equality is never established (no signature is checked), yet the right side (team/membership writes gated by `Shipit.github_teams`) still executes fully from the unauthenticated payload.

### Impact Explanation
An unprivileged network attacker who can reach the `/webhooks` endpoint (this is a public, unauthenticated endpoint by design — that's the whole point of webhooks) can, for any organization configured without a `webhook_secret`, forge a `membership` event `action: 'added'` naming any GitHub login as `member` and any (real or GitHub-team-shaped) `team` matching one of `Shipit.github_teams`. This adds that arbitrary GitHub login as a member of the team that gates access, and once that GitHub user authenticates via OAuth (`GithubAuthenticationController#callback`, itself unprivileged and public), `User#authorized?` returns true, granting them access to the entire Shipit installation — deploy triggers, merges, rollbacks, and API client management. This is "escalation into `Shipit.github_teams` authorization," one of the explicitly listed High-impact outcomes.

### Likelihood Explanation
The webhook secret is explicitly documented as optional (`docs/setup.md`: "Webhook secret (optional): ... *keep it in clear on the side, you'll need it later*" implies it can be skipped), and the shipped test/dummy configs (`secrets.yml`, `secrets_double_github_app.yml`) demonstrate real-world configurations with `webhook_secret: # nil`. Any operator who follows the documented "optional" path, or any multi-org install where one org's app was set up without a webhook secret, is directly exposed. No credentials, tokens, or prior access are required — only network reachability of `/webhooks`, which is required to be public for the feature to function at all.

### Recommendation
- Treat a missing/blank `webhook_secret` as a hard misconfiguration rather than "verification passed": fail closed (reject with 422/500) instead of `return true unless webhook_secret` in `GitHubApp#verify_webhook_signature`.
- Make `webhook_secret` mandatory in `docs/setup.md` and in config validation (`Shipit.all_settings_present?`), refusing to boot or serving 503 on `/webhooks` if any configured organization lacks one.
- In `MembershipHandler`, cross-check `organization.login` from the payload against the organization actually authenticated by `verify_signature` (currently they're the same field used for both purposes with no independent confirmation once signature checking is bypassed) so a compromised/blank secret for one org can't be used to write teams under another.

### Proof of Concept
1. Deploy Shipit with a `secrets.yml` GitHub app entry for organization `acme` where `webhook_secret` is omitted or blank (a documented-as-optional, and test-fixture-demonstrated, configuration) — see `test/dummy/config/secrets.yml` lines 6-13 and `docs/setup.md` line 30 ("Webhook secret (optional)").
2. As an unauthenticated network client, send:
```
POST /webhooks
X-Github-Event: membership
Content-Type: application/json

{
  "action": "added",
  "team": {"id": 999, "name": "Deployers", "slug": "deployers", "url": "https://example.com"},
  "organization": {"login": "acme"},
  "member": {"login": "attacker-github-handle"}
}
```
No `X-Hub-Signature` header is required — `verify_webhook_signature` returns `true` because `webhook_secret` is blank for `acme` (`lib/shipit/github_app.rb:76-77`).
3. `MembershipHandler#process` creates/looks up the `deployers` `Team` (matching one of `Shipit.github_teams`) and adds `attacker-github-handle` as a member (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-34`).
4. `attacker-github-handle` logs in via `/github/auth/github`; `GithubAuthenticationController#callback` creates/finds the `User` and sets the session (`app/controllers/shipit/github_authentication_controller.rb:7-21`).
5. `User#authorized?` now returns `true` because the user's `teams` includes the forged membership matching `Shipit.github_teams` (`app/models/shipit/user.rb:80-82`), granting full application access.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class MembershipHandler < Handler
        params do
          requires :action, String
          requires :team do
            requires :id, Integer
            requires :name, String
            requires :slug, String
            requires :url, String
          end
          requires :organization do
            requires :login, String
          end
          requires :member do
            requires :login, String
          end
        end
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
      end
