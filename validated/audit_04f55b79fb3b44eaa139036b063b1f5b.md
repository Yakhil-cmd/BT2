### Title
Cross-repository CI status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler` breaks the "authenticated organization" vs "repository written" binding - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
The webhook signature check in `WebhooksController#verify_signature` authenticates a `status` event against the GitHub App/organization derived from the payload's own `repository.owner.login` field, but the actual write performed by `Shipit::Webhooks::Handlers::StatusHandler` is keyed **only** by the attacker-supplied commit `sha`, with no scoping to the repository/organization that was cryptographically verified. This breaks the required binding `verified_organization == repository_written_to`.

### Finding Description
`WebhooksController#verify_signature` picks the `GitHubApp` (and thus the `webhook_secret` used for HMAC verification) using a field taken directly from the untrusted JSON body: [1](#0-0) [2](#0-1) 

This only proves that the request was signed with the secret belonging to *some* organization/app that the payload claims to be from (`repository.owner.login`). It says nothing about which repository/commit the event is allowed to affect.

`StatusHandler#process`, however, resolves the target purely from the attacker-controlled `sha` field, with **no join or scope on repository/stack/organization at all**: [3](#0-2) 

Compare this to every other handler (`Handler#stacks`, `PushHandler`, `CheckSuiteHandler`, PR handlers), which at least scope lookups through `Repository.from_github_repo_name(payload.dig('repository','full_name'))`: [4](#0-3) 

`StatusHandler` is the outlier: it calls `Commit.where(sha: params.sha)` globally across **all stacks in the Shipit instance**, then calls `commit.create_status_from_github!(params)` for every match: [5](#0-4) 

This creates a `Status` record that feeds directly into deployability logic: [6](#0-5) [7](#0-6) 

and can trigger continuous deployment scheduling once a commit becomes `deployable?`: [8](#0-7) [9](#0-8) 

**Equality that should hold, but doesn't:** `organization authenticated by verify_signature` (derived from `repository.owner.login` in the payload) `== organization/repository whose commit status gets written` (derived from a global, unscoped `sha` lookup). Before the fix would need to exist, these two are completely decoupled: any entity capable of producing a validly-signed `status` webhook for **any one** org/app configured in this Shipit instance (e.g., their own organization, if the instance is configured per `docs/setup.md`'s documented multi-org support) can forge a commit status for a `sha` belonging to a **different** organization's stack, since the sha is looked up with zero repository scoping.

### Impact Explanation
Commit status (`success`/`pending`/`failure`) is the primary gate for `deployable?` and for `ci.require` checks that block or allow deploys and continuous delivery in Shipit (`README.md` "ci.require"). By forging a `success` status for a target commit sha in another stack (a sha which is often publicly visible on GitHub, or guessable/known from PR activity), an attacker who is only entitled to send authenticated webhooks for one configured organization can:
- Flip a foreign commit's aggregate `status` to `success`, satisfying `deployable?` and required-status checks it never legitimately passed.
- Trigger `schedule_merges` and, if `continuous_deployment?` is enabled on the victim stack, cause `ContinuousDeliveryJob` to be scheduled, resulting in an **unauthorized deploy** of a commit that never actually passed CI on GitHub.

This satisfies the "High"/"Critical" impact bar (escalation into unauthorized deploy) defined in scope, because it lets a party authenticated for repository/org A cause a real deploy action for repository/org B's stack.

### Likelihood Explanation
Exploitability requires the attacker to be able to produce one validly-signed `status` webhook payload for a Shipit-configured organization/app it is entitled to (a realistic scenario for the documented multi-tenant/multi-org GitHub App configuration in `docs/setup.md`, or generally an attacker who has push/webhook rights on any repo mapped into the Shipit instance) and to know a target commit `sha` in a different stack — SHAs are not secrets and are frequently public. No `ApiClient` token, `webhook_secret` of the *target* org, or privileged Shipit account is required — only a valid signature for *any one* configured org, which is exactly the trust boundary the report's fee-quote/fee-execution "verified vs. executed" pattern generalizes to here (a value proven for one entity is silently reused to act on a different entity).

### Recommendation
Scope `StatusHandler#process` (and any other unscoped handler) to the repository/organization that was actually verified in `verify_signature`, e.g. by joining through `stacks`/`Repository.from_github_repo_name(payload.dig('repository','full_name'))` the same way `Handler#stacks` does, and by passing/validating that the verified `repository_owner` used for signature verification matches the `repository.owner.login` used by the handler for every event type — not just deriving it ad hoc per-handler. Consider making `verify_signature`'s resolved organization available to handlers and asserting equality before any write.

### Proof of Concept
1. Configure Shipit with two GitHub Apps/organizations, `OrgA` and `OrgB` (per the documented multi-org `github:` config in `docs/setup.md`), each with its own `webhook_secret`, and create a Stack in Shipit tracking a repository owned by `OrgB` with a known commit `sha_victim` (e.g. the head of an active PR) and `ci.require` configured.
2. As an operator with legitimate webhook signing rights only for `OrgA` (e.g. controlling `OrgA`'s GitHub App/webhook secret), construct a `status` event payload:
```json
{
  "sha": "sha_victim",
  "state": "success",
  "context": "required-ci-context",
  "repository": { "owner": { "login": "OrgA" } }
}
```
3. Sign the payload body with `OrgA`'s `webhook_secret` and POST it to `/webhooks` with header `X-Github-Event: status`.
4. `verify_signature` resolves `repository_owner = "OrgA"` and successfully verifies the signature using `OrgA`'s secret (see `app/controllers/shipit/webhooks_controller.rb:24-30,59-62`).
5. `StatusHandler#process` runs `Commit.where(sha: "sha_victim")` — matching the commit that actually belongs to `OrgB`'s stack, with no check that it belongs to `OrgA` — and creates a `success` status on it (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`; `app/models/shipit/commit.rb:165-169`).
6. If the `OrgB` stack has `continuous_deployment` enabled and this satisfies its required statuses, `Commit#deployable?` becomes true and `schedule_continuous_delivery` enqueues `ContinuousDeliveryJob`, deploying a commit that never passed real CI on `OrgB`'s repository (`app/models/shipit/commit.rb:227-229,281-287`).
