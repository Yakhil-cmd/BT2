### Title
Yield-timeout processing in `resolve_promise_yield_timeouts` performs unbounded, un-gas-charged trie work per chunk - ([File: runtime/runtime/src/lib.rs])

### Summary
`resolve_promise_yield_timeouts`, called from `process_receipts` (which is invoked by chunk application, the same layer as `process_transactions`), drains the `PromiseYieldTimeout` trie queue for all entries whose `expires_at <= block_height`. The loop only stops when the shared `total.compute` counter (accumulated from local/delayed/incoming receipt processing) reaches `compute_limit`, or when the trie's storage-proof size limit is exceeded, but the loop body itself never calls `total.add(...)` to charge gas/compute for the work it does (trie reads, key removal, receipt construction, `forward_or_buffer_receipt`) [1](#0-0) [2](#0-1) .

### Finding Description
An unprivileged account can call a deployed contract's `FunctionCall` action to create many `yield_create` promises (via `PromiseYieldCreate` receipts), each of which enqueues a `PromiseYieldTimeout` entry keyed by `expires_at = block_height + yield_timeout_length_in_blocks` [3](#0-2) . Because `yield_timeout_length_in_blocks` is fixed at protocol-config granularity (200 blocks in observed configs), the attacker can submit many yield-creating transactions across many blocks that all resolve to the identical `expires_at` height, causing the queue to accumulate an arbitrarily large number of same-height entries.

When that height is reached, `resolve_promise_yield_timeouts` walks the queue starting at `first_index`, and for every entry with `expires_at <= apply_state.block_height` it performs: a trie lookup for the timeout entry, a trie lookup for the corresponding `PromiseYieldReceipt`, construction of a new `PromiseResume` receipt, an optional `ReceiptToTx` push, a call to `receipt_sink.forward_or_buffer_receipt`, and a trie removal of the queue entry [4](#0-3) . None of this per-entry work adds anything to `total.gas` or `total.compute` — the only invocation of `TotalResourceGuard::add` visible in the surrounding `process_receipts`/action-processing code paths is tied to receipt/transaction execution, not to the timeout-draining loop. The loop's sole exit conditions are `total.compute >= compute_limit` (a value that is set by *other* receipt processing, not by this loop) and `state_update.trie.check_proof_size_limit_exceed()` (a storage-proof soft limit, not a hard gas-metered bound). This breaks the stated invariant that "timeout processing per chunk is bounded and gas-charged": the number of timeout entries drained in one chunk is effectively unbounded by gas, only incidentally bounded by however much of the previously-accumulated `total.compute`/storage-proof budget happens to already exist, and by however large the storage-proof grows as a byproduct of trie reads/removals (an indirect and non-protocol-defined limit).

### Impact Explanation
If `total.compute` is low when timeout processing begins (e.g., chunk mostly idle, or attacker times timeouts for a lightly loaded chunk) the drain loop can process a very large number of queue entries with essentially free CPU/IO/state-write work from the chunk producer's perspective, since no gas is burned and no compute quota is consumed for it. This can inflate chunk application time disproportionate to gas accounted for the chunk, and pushes an unbounded number of new `PromiseResume` outgoing receipts through `receipt_sink.forward_or_buffer_receipt` in one chunk. This matches a chunk-processing time/resource-exhaustion class issue (chunk producers taking longer than the deterministic time budget the gas-per-chunk model is meant to guarantee), which could delay chunk/block production for the shard under a sufficiently large accumulated backlog. It does not appear to allow direct balance/supply manipulation.

### Likelihood Explanation
Feasibility depends on how large the timeout queue backlog can practically grow: creating N yield-promises requires N separate `yield_create` calls (each limited per-call by `max_promises_per_function_call_action`/`max_number_input_data_dependencies`), so accumulating a very large backlog targeting one height requires paying gas for many prior transactions across many blocks, spread out before the shared timeout height. The economic cost to the attacker (transaction gas fees to create each yield) provides a natural friction, but the exploit does not require any special privilege — only an ordinary account with a deployed contract able to call `yield_create` repeatedly over time. The severity in a single chunk is bounded eventually by the storage-proof soft-limit check, which was not fully confirmed in this review to be a hard, tight per-chunk safety bound equivalent to gas metering.

### Recommendation
Charge gas/compute for each entry processed in `resolve_promise_yield_timeouts` (e.g., a fixed per-timeout-entry cost accounted via `total.add(...)`, similar to how other receipt categories are charged), and/or impose an explicit, protocol-defined maximum number of timeout entries processed per chunk independent of the "already exhausted" `total.compute` check, so the loop's own break condition is driven by work it itself performs rather than only by prior unrelated processing.

### Proof of Concept
Add a test to `runtime/runtime/src/tests/apply.rs`:
1. Deploy a test contract with a callable `yield_create`-style method.
2. Submit many transactions (e.g., hundreds) across several chunks, each creating a yielded promise, arranging (by controlling submission block heights) for all their `PromiseYieldTimeout` entries to share the same `expires_at` height.
3. Apply an otherwise near-empty chunk (no other receipts, so `total.compute` starts at 0) at the shared `expires_at` height and measure: (a) `apply_result.total_compute_usage`/`total_gas_burnt` reported for the chunk against the number of `PromiseResume` receipts actually produced, and (b) wall-clock time of `resolve_promise_yield_timeouts`.
4. Assert that the number of processed timeouts is not gas/compute-accounted proportionally (i.e., `total.gas`/`total.compute` remains near-zero while dozens/hundreds of `PromiseResume` receipts are generated), and that the balance checker/gas totals do not reflect the real resource cost of draining the queue — demonstrating the missing charge described above.
