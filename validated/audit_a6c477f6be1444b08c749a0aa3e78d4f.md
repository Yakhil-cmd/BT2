### Title
Cross-repository commit-status injection via `StatusHandler` — organization that authenticated (GitHub App installation) vs. the repository/stack whose CI-gate is written ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates a `status` webhook only against the GitHub organization/App installation that produced it [1](#0-0) , but `StatusHandler#process` then applies the status payload to **every** `Commit` record in the entire Shipit database whose `sha` matches, with no check that the commit belongs to the repository/organization identified in the payload or covered by the verified signature: [2](#0-1) . Every other webhook handler in the codebase scopes its side effects through `Handler#stacks`/`Repository.from_github_repo_name(repository_name)` (e.g. `PushHandler`, `PullRequest::OpenedHandler`) [3](#0-2) [4](#0-3) , but `StatusHandler` never joins against `repository_name`/`stacks`, breaking the equality: `organization that authenticated == repository whose commit-status/CI-gate is written`.

### Finding Description
The engine binds webhook trust to a GitHub App installation/organization: `Shipit.github(organization: repository_owner)` selects which app's `webhook_secret` verifies the HMAC, where `repository_owner` is read straight from the payload (`repository.owner.login` / `organization.login`) [1](#0-0) [5](#0-4) .

GitHub Apps' `webhook_secret` is a single secret shared by **every** installation of that App. Any GitHub user can independently install a public/installable GitHub App on a repository they legitimately own, without any relation to the organizations Shipit actually tracks, and receive genuinely, correctly-signed webhook deliveries for events on their own repository. Nothing in `verify_signature` ties the signature to a *specific, admin-approved* repository — it only proves "this payload came from *some* legitimate installation of the App", not "this payload concerns a repository Shipit is authorized to act on."

`StatusHandler` then does:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 

`Commit#sha` has no uniqueness scoping visible here to the payload's own `repository.full_name`; the base `Handler` class defines `repository_name`/`stacks` precisely for this purpose [3](#0-2) , but `StatusHandler` doesn't inherit that scoping into its query — it looks up commits globally across every stack/repository tracked by the Shipit instance. Because `sha` values are content-addressed (SHA-1 of tree+parents+author/committer metadata), an attacker can trivially reproduce an identical `sha` to a commit that already exists in a target stack simply by cloning the target's (often public) git history into a repository the attacker controls, then installing the App there and firing a `status` event (e.g., via the GitHub REST API for commit statuses) with that `sha`, `state: success`, and `context` matching whatever the target stack's `shipit.yml` requires (`ci.require` / `merge.require`).

`create_status_from_github!` writes the forged status onto the matched `Commit`, and `add_status` re-evaluates deployability and schedules merges: `stack.schedule_merges if new_status.pending? || new_status.success?` [6](#0-5) . That status is consumed by `MergeRequest::StatusChecker`/`all_status_checks_passed?` to gate automatic PR merging [7](#0-6) , and by `Commit#deployable?` to gate continuous deployment [8](#0-7) .

### Impact Explanation
An unprivileged attacker (any GitHub user able to install the Shipit GitHub App on a repository they own — no Shipit session, `ApiClient` token, `webhook_secret`, private key, or org admin rights over the *target* org is needed) can inject a fabricated "success" CI status onto a commit belonging to a stack/repository they have no access to, satisfying `ci.require`/`merge.require`. This can:
- cause the merge queue to auto-merge a pull request (`ProcessMergeRequestsJob` → `merge_request.merge!` → `stack.github_api.merge_pull_request`) [9](#0-8) [10](#0-9) , or
- cause `schedule_continuous_delivery`/`ContinuousDeliveryJob` to trigger an unauthorized production deploy of the target stack.

This matches the Critical bucket ("an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Requires: (1) the target commit's exact SHA (feasible for public/open-source or leaked repositories by re-pushing identical git objects, or simply observing a real SHA that the attacker also has in a repo/fork they control), (2) the attacker be able to install the shared GitHub App on their own repository (true for public/installable Apps, which is the documented setup model in `docs/setup.md`), and (3) knowledge of the required status `context` name(s), typically visible in `shipit.yml`/README of the target project. No secrets, tokens, or Shipit accounts are required.

### Recommendation
Scope `StatusHandler#process` (and any similarly unscoped handler) through `repository_name`/`stacks`, e.g. restrict the `Commit.where(sha: params.sha)` lookup to commits whose `stack` belongs to `Repository.from_github_repo_name(repository_name)`, mirroring the pattern already used by `Handler#stacks` and the `PushHandler`.

### Proof of Concept
1. Attacker owns `attacker/mirror`, an exact git clone of the target's tracked repository (or independently reproduces a target commit's SHA).
2. Attacker installs the (public) Shipit GitHub App on `attacker/mirror`; GitHub signs future webhooks for this installation using the App's real `webhook_secret`.
3. Attacker calls GitHub's "Create Commit Status" API on `attacker/mirror` for `sha=<target-sha>`, `state=success`, `context=<required-context>`.
4. GitHub delivers a `status` webhook, correctly signed; `verify_signature` passes because it only validates that *an* App installation produced it [1](#0-0) .
5. `StatusHandler#process` finds the victim stack's `Commit` with the same `sha` (global, unscoped lookup) and records the forged "success" status [2](#0-1) .
6. The victim stack's merge queue / continuous-deployment logic now considers the commit's CI green and merges/deploys it.
