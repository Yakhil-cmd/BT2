### Title
Path Traversal via Attacker-Controlled Release Asset Name Allows Arbitrary File Write - (File: pkg/cmd/release/download/download.go)

### Summary
`gh release download` writes each release asset to `filepath.Join(w.dir, name)` in `destinationWriter.makePath`, where `name` is `a.Name`, taken verbatim from the `name` field of a `releaseAsset` object returned by the GitHub Releases API. Because this value is never checked for path-separator or `..` sequences before being joined into the destination path and passed to `os.OpenFile`, a malicious repository owner can craft a release asset name (or a crafted API response from a "wrong-host" GHES-style endpoint) that causes the victim's `gh release download` to write outside the intended `--dir`.

### Finding Description
`downloadRun` builds the list of assets to fetch directly from `release.Assets`, which is decoded from the JSON response of `FetchRelease`/`FetchLatestRelease` into `shared.ReleaseAsset` [1](#0-0) . The only checks applied to `a.Name` before use are the glob pattern filter and a Windows reserved-filename check [2](#0-1) ; neither rejects path separators or `..` segments.

`a.Name` is then propagated as `downloadTarget.name` [3](#0-2)  and passed into `downloadAsset` → `dest.Copy(fileName, resp.Body)` [4](#0-3) .

`destinationWriter.makePath` builds the final path with `filepath.Join(w.dir, name)`, which normalizes (`Clean`s) the joined string but does not prevent it from resolving outside `w.dir` when `name` contains `..` segments [5](#0-4) . `Copy` then creates any needed parent directories with `os.MkdirAll` and opens/truncates the resulting path with `os.OpenFile(fp, os.O_WRONLY|os.O_CREATE|os.O_TRUNC, 0644)` [6](#0-5) , writing attacker-supplied bytes to that location.

No `safepath`-style containment check (e.g., verifying the resolved path stays under `w.dir`) exists anywhere in this file. The asset's `APIURL` is wrapped in `safeurl.NewImmutableSafeURL` to guard the request destination [7](#0-6) , but this only protects the outbound HTTP request URL — it does nothing to sanitize the `Name` field used for the local filesystem path.

Exploit flow: an unprivileged attacker publishes a release in their own public repository with an asset whose `name` field is set (via direct REST API calls, bypassing whatever the github.com web UI might restrict) to a traversal string such as `../../../../.ssh/authorized_keys` or `../../.bashrc`. When a victim runs `gh release download <tag> -R attacker/repo`, `gh` fetches the release, iterates `release.Assets`, and writes the HTTP response body to a path outside the chosen `--dir`, overwriting or creating an arbitrary file relative to the victim's current/destination directory.

### Impact Explanation
This is an arbitrary file write outside the intended destination directory, controlled entirely by an untrusted third party's repository content. Depending on the victim's working directory and permissions, this could overwrite configuration/startup files (e.g., shell rc files, SSH `authorized_keys`) leading to persistence or code execution the next time such a file is sourced/executed. This matches the "file write or overwrite outside the intended path" bounty impact class.

### Likelihood Explanation
Preconditions are minimal: the attacker only needs a public GitHub repository with a release containing an asset whose name they fully control at upload time via the REST API, and the victim needs to run an ordinary `gh release download` command against that repo (a very common invocation pattern, e.g. in CI or scripts pulling third-party release assets). No token leakage, MITM, or elevated privileges required. The main uncertainty is whether GitHub's release-asset upload API server-side validates/rejects `/` or `..` in the `name` parameter before persisting it — this repo's client code performs no independent validation, so the vulnerability's exploitability depends on that external constraint, which could not be verified from this codebase.

### Recommendation
In `destinationWriter.makePath` (or `Check`/`Copy`), reject or sanitize `name` before joining: use `filepath.Base(name)` to strip any directory components, and/or verify with `filepath.Rel`/prefix-check that the resolved path stays within `filepath.Clean(w.dir)` before calling `os.MkdirAll`/`os.OpenFile`. Reject asset names containing `..`, absolute paths, or path separators outright, similar to how `isWindowsReservedFilename` already special-cases dangerous names.

### Proof of Concept
```go
func TestDestinationWriter_PathTraversal(t *testing.T) {
    tmp := t.TempDir()
    dest := destinationWriter{dir: filepath.Join(tmp, "downloads")}

    maliciousName := "../../evil.txt"
    err := dest.Copy(maliciousName, strings.NewReader("pwned"))
    require.NoError(t, err)

    // Expect the file to have been written outside tmp/downloads,
    // demonstrating traversal escape.
    escapedPath := filepath.Join(tmp, "evil.txt") // two levels up from tmp/downloads resolves near tmp
    _, statErr := os.Stat(escapedPath)
    assert.NoError(t, statErr, "file was written outside the intended destination directory")
}
```
This can be extended to an httpmock-based integration test that stubs `GET /repos/OWNER/REPO/releases/latest` to return an asset object with `"name": "../../evil.txt"`, then runs `downloadRun`, and asserts the file lands outside `opts.Destination`.
