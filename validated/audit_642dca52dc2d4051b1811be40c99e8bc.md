## Analog Found

The reported bug class — a mutable, network-controlled fee that can retroactively invalidate a previously reserved amount and permanently strand queued/committed funds — has a direct analog in `ocore`'s textcoin feature.

### Title
Rising TPS fee can permanently strand funds locked in a private-asset textcoin - (File: `wallet.js`)

### Summary
When a textcoin is created, the sender reserves a fixed byte amount on a fresh one-time address to cover the recipient's future claim fee, sized against the **TPS fee at send time**. The TPS fee is a network-wide value that fluctuates with congestion and can also be permanently raised via governance (`system_vote`/`system_vote_count` on `base_tps_fee`, `tps_fee_multiplier`, `tps_interval`). Because the textcoin's balance is fixed once broadcast, if the TPS fee later rises above what was reserved, the claim transaction can no longer be composed. For private-asset textcoins the automatic fallback of paying the shortfall from the recipient's own wallet is explicitly disabled, so the coins become permanently unclaimable — the same "queue item silently frozen because a global fee grew past the reserved value" pattern described in the report.

### Finding Description
At send time, `addFeesToParams` in `wallet.js` computes the claim-fee reservation using the **current** estimated TPS fee and bakes it into the textcoin's fixed output amount: [1](#0-0) 

`estimateTpsFee` derives this from the live network TPS/tps_fee governance parameters (`base_tps_fee`, `tps_interval`, `tps_fee_multiplier`), which are dynamic and can rise over time: [2](#0-1) [3](#0-2) 

These parameters are governed by on-chain votes (`system_vote`/`system_vote_count`), which any legitimate holder can push higher over time, and the resulting variable is looked up "live" (via `getCurrentTpsFeeToPay`/`getCurrentTps`) rather than pinned to the value known at textcoin-creation time: [4](#0-3) [5](#0-4) 

The textcoin sits on a plain one-time address whose balance is fixed the moment it is broadcast — there is no way to "top up" the reserved fee automatically. When the recipient eventually claims it (which by design can happen an arbitrary time later — textcoins are explicitly meant to be redeemable long after creation), `composeJoint`'s input-selection step recomputes the **current** required amount, including the live `tps_fee`: [6](#0-5) 

If the coin's now-fixed balance is smaller than `amount + naked_size + oversize_fee + tps_fee`, composition fails with `NOT_ENOUGH_FUNDS`, exactly as in `pickDivisibleCoinsForAmount`'s target-amount computation: [7](#0-6) 

`receiveTextCoin`'s `ifNotEnoughFunds` handler tries to cover the shortfall from the recipient's own wallet — but only for non-private claims. For private-asset textcoins this fallback is explicitly disabled: [8](#0-7) 

So a private-asset textcoin whose reserved fee has been outpaced by a rising TPS fee has no automatic recovery path and is permanently unclaimable — the funds are frozen exactly like the Y2K deposit queue once `relayerFee` overtakes a queued deposit.

### Impact Explanation
Funds locked in a private-asset textcoin become permanently unclaimable through the normal claim flow once the network's TPS fee (driven either by organic congestion or by a governance vote raising `base_tps_fee`/`tps_fee_multiplier`) exceeds what was reserved at creation time. Because private textcoins intentionally disable the "pay fee from recipient's wallet" fallback (to preserve recipient privacy), there is no automatic remediation; the sender would need to be aware of the problem and manually top up the underlying one-time address, which is not part of the normal user flow and may never happen. This is a freeze of funds for an ordinary, unprivileged wallet user.

### Likelihood Explanation
Textcoins are explicitly designed to be claimed at an arbitrary future time (e.g. email/notification-based delivery), and TPS-driven fees are inherently variable and can also increase via a passed system vote. No attacker action is even required — organic network growth or a legitimate governance vote is sufficient to trigger this over time, making the scenario plausible rather than purely theoretical.

### Recommendation
- Reserve fees for textcoins against a safety-margined estimate of future TPS fee growth, or periodically re-fund unclaimed textcoins to track the live TPS fee.
- For private-asset textcoins, provide a privacy-preserving mechanism for the recipient (or sender) to top up the reserved fee (e.g. an out-of-band, non-attributable resend) instead of unconditionally failing the claim.
- Alternatively, allow `receiveTextCoin` to detect an underfunded private textcoin and prompt for/accept an additional funding transaction rather than only emitting `"Not enough funds on the textcoin"`.

### Proof of Concept
1. Sender creates a private-asset textcoin via `sendMultiPayment`; `addFeesToParams` reserves `TEXTCOIN_ASSET_CLAIM_FEE + tps_fee_at_send_time` bytes on the fresh one-time address (`wallet.js:2310-2358`).
2. Before the recipient claims it, either network congestion rises (`getCurrentTps`/`getCurrentTpsFee`) or an OP-backed `system_vote_count` raises `base_tps_fee`/`tps_fee_multiplier` (`main_chain.js:1877-1903`, `validation.js:1893-1907`).
3. Recipient calls `receiveTextCoin`; `composeAndSaveIndivisibleAssetPaymentJoint`/`composeAndSaveDivisibleAssetPaymentJoint` internally invoke `composeJoint`, which now computes a larger `target_amount` including the higher live `tps_fee` (`composer.js:498-510`).
4. The fixed balance on the textcoin address is insufficient, `pickDivisibleCoinsForAmount` returns no inputs, and `ifNotEnoughFunds` fires (`wallet.js:2698-2711`).
5. Because `opts._private` is `true`, the code explicitly refuses to retry with fees paid from the recipient's own wallet and returns `"Not enough funds on the textcoin"` — the private-asset textcoin's funds are now permanently stuck.
