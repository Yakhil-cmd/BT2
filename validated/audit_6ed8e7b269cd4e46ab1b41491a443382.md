### Title
Unsanitized control characters in arbiter/prosaic contract `title`/`text` allow deceptive contract terms during wallet approval - ([File: arbiter_contract.js])

### Summary
The `title` and `text` fields of arbiter contracts (and the analogous fields of prosaic contracts) are free-form strings supplied by a paired peer device with no restriction on control characters, escape sequences, or bidirectional-override characters, yet they are the exact bytes that get cryptographically bound into the contract hash and eventually into the counter-signed shared-address unit. This is the same bug class as CVE-2025-1691: a message that is *displayed* to a human for approval can be crafted with control characters so that what is rendered differs from what is actually signed/committed, tricking the user into approving something other than what they see.

### Finding Description
`arbiter_contract.js` builds the value that both parties sign/commit to directly from the caller-supplied `title` and `text`: [1](#0-0) 

These fields arrive from the remote peer as free text in the `arbiter_contract_offer` device message and are validated only for non-emptiness/type, never for embedded control characters: [2](#0-1) 

Contrast this with every other free-text channel in ocore that is exposed to network-reachable/AA-reachable data and is explicitly hardened against control-character abuse:
- `data_feed` names/values reject embedded `\n`: [3](#0-2) 
- ojson/oscript string literals recursively reject `\n` anywhere in a formula/AA definition: [4](#0-3) 
- `device_name` at least strips HTML-like tags before display: [5](#0-4) 

No equivalent sanitization exists for arbiter/prosaic contract `title`/`text`, even though these are the values a human reviews before approving a shared-address definition and countersigning a payment. `prosaic_contract.js` has the identical pattern (`text`/`title` stored and forwarded verbatim): [6](#0-5) 

An attacker acting as the paired counterparty (a role explicitly reachable per the rules — "private-payment counterparty or paired device") can embed control characters (e.g. `\r`, `\b`, ANSI CSI escape sequences, or Unicode bidirectional-override characters `U+202E`/`U+2066`) inside `text`/`title` so that the string a wallet UI renders shows innocuous contract terms (e.g. amount, obligations, recipient) while the actual byte sequence — the one hashed by `getHashSrc` and bound into the shared-address definition/dispute data — encodes different terms. Because the hash commits to the raw string, the victim's client will happily display "clean" text (with the control bytes suppressing/reordering/overwriting the malicious portion visually) while cryptographically agreeing to different contract content, then proceed to cosign the shared-address payment unit.

### Impact Explanation
The victim can be induced to accept and cosign an arbiter contract (and the associated payment out of a jointly-controlled shared address) whose actual, hash-committed terms differ from what was visually presented — e.g., a different payee party, a different intended dispute-resolution mapping, or misleading counterparty identity in `my_party_name`/`peer_party_name` which also enter the hash. This results in the victim authorizing spending they did not actually intend, satisfying "concrete unauthorized spending" via the shared-address cosigning flow (`wallet.js` signer flow that specifically watches for prosaic/arbiter contract deposits/claims): [7](#0-6) 

### Likelihood Explanation
Requires user interaction (the victim must review/approve the contract offer) and requires the attacker to be the paired peer initiating the contract — matching the CVE's AC:H/UI:R/PR:H profile. No special privilege beyond being a paired correspondent is needed; this is a normal, expected interaction path (accepting a business/arbiter contract offer) rather than a privileged/administrative one.

### Recommendation
Reject or strip control characters (C0/C1 control codes, ANSI escape sequences, and Unicode bidi-control characters) from `title`, `text`, `my_party_name`, and `peer_party_name` in both `arbiter_contract.js`/`prosaic_contract.js` storage/validation paths and in the `wallet.js` message handlers (`arbiter_contract_offer`, `prosaic_contract_offer`, `arbiter_contract_shared`, `prosaic_contract_shared`) before they are stored, hashed, or displayed — analogous to the `\n` rejection already applied to `data_feed` names/values and ojson strings.

### Proof of Concept
1. Attacker pairs with victim's wallet as a normal correspondent device.
2. Attacker sends `arbiter_contract_offer` with `text` containing, e.g., `"Pay 100 USD to Alice" + "\r" + "Pay 100 USD to Mallet-controlled-address" + spaces-to-overwrite-visible-line` (or RTL-override sequences) such that common terminal/GUI rendering shows only the first, benign line while the full string (including the injected line) is what gets hashed via `getHashSrc` (`arbiter_contract.js:194-203`) and stored/forwarded.
3. Victim reviews the rendered (benign-looking) text, accepts, and the wallet proceeds to cosign the resulting shared-address transaction (`wallet.js:2043-2088`), committing to the full, hidden terms instead of the displayed ones.

function getHashSrc(contract) {
	const payer_name = contract.me_is_payer ? contract.my_party_name : contract.peer_party_name;
	const payee_name = contract.me_is_payer ? contract.peer_party_name : contract.my_party_name;
	const payer_address = contract.me_is_payer ? contract.my_address : contract.peer_address;
	const payee_address = contract.me_is_payer ? contract.peer_address : contract.my_address;
	const src = contract.creation_date > exports.NEW_HASH_DATE
		 ? [contract.title, contract.text, contract.creation_date, payer_address, payer_name || '', contract.arbiter_address, payee_address, payee_name || '', contract.amount, contract.asset || 'null'].join(exports.DELIMITER)
		 : [contract.title, contract.text, contract.creation_date, payer_name || '', contract.arbiter_address, payee_name || '', contract.amount, contract.asset || 'null'].join("");
	return src;
}

function getHash(contract) {
	return crypto.createHash("sha256").update(getHashSrc(contract), "utf8").digest("base64");
}
