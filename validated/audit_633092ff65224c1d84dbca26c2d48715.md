### Title
Webhook organization used for signature verification is decoupled from the repository/stack actually mutated by handlers, enabling cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `GithubApp` (and therefore which `webhook_secret`) to use for HMAC verification based on `repository.owner.login` (or `organization.login`) read from the **unverified** JSON body, then hands the same unverified body to handlers that resolve the target `Stack`/`Commit` using a *different* field (`repository.full_name`) or, in the case of `StatusHandler`, no repository scoping at all. On a multi-organization Shipit deployment (`secrets.github` keyed by multiple orgs, see `Shipit.github_app_config`/`github_organizations`), an attacker who legitimately controls the webhook secret for *one* configured organization can forge a signed payload whose `repository.owner.login` matches their own org (so signature verification passes) while `repository.full_name`/`sha` targets a different, victim organization's stack or commit.

### Finding Description
`verify_signature` derives the signing organization purely from the request body: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  ...
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization:)` looks up a distinct `webhook_secret` per organization when the multi-tenant `secrets.github` schema is used: [3](#0-2) 

Once the signature is accepted for organization *A*, every handler re-parses the **same unverified body** but binds to a stack/commit using unrelated fields:

- `Handler#repository_name` reads `payload.dig('repository', 'full_name')`, independent of `repository.owner.login` used for signing: [4](#0-3) 

- `PushHandler#process` uses that repository lookup to trigger a real GitHub sync on the resolved stacks: [5](#0-4) 

- `StatusHandler#process` is scoped to **no repository at all** — it matches purely by commit SHA across the entire installation: [6](#0-5) 

The trust binding the system implicitly relies on — "the organization whose secret signed this webhook == the organization whose repository/commit this webhook is allowed to mutate" — is never enforced. Nothing checks that `repository.owner.login` (used to select the verifying `webhook_secret`) equals the owner encoded in `repository.full_name` (used by `PushHandler`/`CheckSuiteHandler`) or that the commit belongs to a repository owned by the signing org at all (`StatusHandler`).

### Impact Explanation
On a Shipit instance configured for multiple GitHub organizations (a supported, documented configuration via `secrets.github` per-org keys), any organization admin who can configure their own GitHub App's webhook and thus knows/controls their own org's `webhook_secret` can forge a signed webhook claiming `repository.owner.login = <their org>` while setting `repository.full_name` (push/check_suite) or `sha`/`state` (status) to target a victim organization's stack/commit that they have no legitimate access to:
- `PushHandler` will invoke `stack.sync_github` on the victim's stack, forging arbitrary sync/refresh activity against a repository the attacker does not own.
- `StatusHandler` has zero repository scoping — the attacker can inject fabricated commit statuses (`create_status_from_github!`) onto any commit in the entire Shipit instance merely by knowing its SHA. Commit statuses gate deploy eligibility and merge-queue eligibility (`ci.require`/`ci.blocking`, merge status), so a forged "success" status can make an otherwise non-deployable/non-mergeable commit appear deployable/mergeable, resulting in an unauthorized deploy or merge on a repository outside the attacker's own organization.

This crosses the "cross-repository writes"/"unauthorized deploy ... or merge" boundary using only a credential the attacker legitimately owns for their own tenant, not the victim's `webhook_secret`.

### Likelihood Explanation
Requires the Shipit instance to host more than one GitHub organization (multi-tenant `secrets.github` config) and the attacker to be an authenticated administrator of their own tenant organization (able to configure their own GitHub App/webhook secret) — a realistic scenario for a shared Shipit deployment serving several teams/orgs. No access to the victim's secret, GitHub token, or Shipit session is needed.

### Recommendation
After verifying the signature, re-derive `repository_owner`/target org strictly from the same trusted source used for verification, and reject (or scope) any handler operation whose resolved repository owner does not match the organization that produced a valid signature. For `StatusHandler` specifically, scope the `Commit` lookup to commits belonging to repositories under the verified signing organization instead of a global SHA match.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.github`, e.g. `attacker-org` and `victim-org`, each with its own `webhook_secret`.
2. As an admin of `attacker-org`, craft a `status` webhook body:
```json
{
  "sha": "<victim commit sha, e.g. from victim-org's public repo>",
  "state": "success",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. Sign it with `attacker-org`'s known `webhook_secret` and send it to `/webhooks` with `X-Github-Event: status`.
4. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and accepts the signature.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` with no ownership check, creating a fabricated `success` status on the victim commit — potentially unblocking a deploy/merge gated by `ci.require`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
