### Title
`StatusHandler#process` applies GitHub status webhooks by bare SHA with no repository/stack scoping - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with no filter tying the lookup to the repository that the webhook's signature actually authenticated, unlike every other handler in the codebase (`PushHandler`, `CheckSuiteHandler`, the `PullRequest::*` handlers), all of which scope through `Handler#stacks`, itself derived from `Repository.from_github_repo_name(payload.dig('repository','full_name'))`. If the same SHA exists as a `Commit` row under more than one `Stack` (same commit content pushed/mirrored into multiple stacks, a shared history, or a copied commit with identical tree/parents/timestamps), a status webhook whose signature was validated for one organization/repository will be applied to `Commit` rows belonging to unrelated stacks.

### Finding Description
The broken binding: the invariant the code should enforce is `commit.stack.repository == webhook.repository` (equivalently, `stacks_from_payload.include?(commit.stack)`), for every `Commit` row updated by `StatusHandler#process`. In the actual code this equality is never checked.

Path:
1. `POST /webhooks` reaches `Shipit::WebhooksController#create` [5](#0-4) .
2. `verify_signature` computes `repository_owner` purely from the attacker-supplied JSON body (`params.dig('repository','owner','login')` or `organization.login`) and verifies the HMAC signature using the webhook secret configured for *that* organization [6](#0-5) . This step authenticates that the request originated from GitHub for a specific organization/app installation — it does **not** authenticate that the `sha` in the payload belongs to that repository.
3. `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler.call(params)` [7](#0-6) .
4. `StatusHandler#process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a bare, unscoped ActiveRecord query across the entire `commits` table [1](#0-0) . The `commits` table's uniqueness constraint is on `[sha, stack_id]`, not `sha` alone, so the same SHA can legitimately exist as separate rows under multiple stacks [8](#0-7) .
5. Contrast with every other handler: `Handler#stacks` scopes to `Repository.from_github_repo_name(repository_name)&.stacks` [9](#0-8) , and both `PushHandler#process` and `CheckSuiteHandler#process` explicitly operate through `stacks.where(...)` [3](#0-2) [4](#0-3) . `StatusHandler` is the sole exception.
6. Once `create_status_from_github!` runs on a commit belonging to the victim stack, `Commit#add_status` fires `deployable_status`/`commit_status` hooks and calls `stack.schedule_merges` on state transitions to `pending`/`success` [10](#0-9) ; a `failure` status on a required context flips `Commit#deployable?` to false (blocking an in-flight deploy candidate) via `required_statuses`/`Status::Common#required?` [11](#0-10) , and on stacks with `continuous_deployment: true` a `success` transition schedules `ContinuousDeliveryJob`, which calls `stack.trigger_continuous_delivery` and runs `trigger_deploy(commit, Shipit.user, ...)` — i.e. the deploy is attributed to and executed under the identity returned by `Shipit.user`, which resolves to the bot user when `bot_login` is configured [12](#0-11) [13](#0-12) .

Why existing guards fail: `verify_signature` only proves the request came from GitHub for the claimed organization; it says nothing about which repository's commit graph the `sha` belongs to, and `StatusHandler` throws away the `repository`/`full_name` payload field entirely (it isn't even in its `params do ... end` schema) [14](#0-13) . `ExplicitParameters` only validates types/presence of declared fields, not cross-repository ownership. There is no `require_permission!`/`User#authorized?` check in this unauthenticated webhook path (by design, since webhooks aren't user-authenticated), so the only real trust boundary is the per-organization signature, which this handler doesn't reconcile against the target commit's actual stack.

### Impact Explanation
For any two stacks that end up containing `Commit` rows with the same `sha` (which can occur through shared history, monorepo forks, cherry-picked/backported commits with identical content producing identical SHAs, or repository renames/migrations tracked as separate `Repository`/`Stack` records), a `status` webhook correctly signed for organization/repository A will be applied to the matching `Commit` row(s) in stack B as well, regardless of B's repository. On a victim stack configured with `bot_login` (so `Shipit.user` resolves to the GitHub App bot identity) and `continuous_deployment: true`, a forged/cross-repo `failure` on a required context can block deployability or delay CD (`should_delay_continuous_delivery?`), while a `success`/state flip can trigger `ContinuousDeliveryJob` → `trigger_deploy` running as the bot, i.e. an attacker-influenced deploy/rollback decision executed with the bot's authority on a repository it never authenticated for. This matches the "payload for one repository mutating another's stack/commit" and "unauthorized deploy/rollback" categories — Critical severity per the stated impact taxonomy, though it is conditioned on the SHA-collision precondition described in Likelihood below.

### Likelihood Explanation
Preconditions: (1) a `status` webhook must be validly signed for *some* organization configured in Shipit (i.e., attacker needs access to trigger a real GitHub status event on a repo whose org's app installation targets this Shipit instance — this is available to "any GitHub user who can... emit webhooks from a repository they own" only if that repo/org is itself onboarded to the same Shipit instance/app installation); (2) the exact same `sha` must exist as a `Commit` row in a different, victim `Stack`. Since Git SHAs are content-addressed (tree, parents, author/committer identity and timestamps, message), achieving SHA equality across unrelated stacks generally requires either genuinely shared/forked history between the repositories tracked by different stacks, or deliberately reproducing an existing commit's exact metadata — feasible for repositories with shared git ancestry (common in multi-stack setups: staging/production stacks on the same repo, or monorepo-derived stacks) but not a generic "any repo, any commit" cross-tenant attack. Given that constraint, likelihood is moderate rather than trivial: the bug is a genuine missing-scope defect exploitable within realistically common Shipit configurations (multiple stacks tracking the same or forked repositories), but is not exploitable against an arbitrary unrelated victim repository without a shared commit history.

### Recommendation
Scope `StatusHandler#process` the same way as the other handlers: require and use `repository.full_name` from the payload, resolve `stacks` via `Repository.from_github_repo_name`, and only update commits within those stacks, e.g. `stacks.each { |stack| stack.commits.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) } }`.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb` or extending `test/controllers/webhooks_controller_test.rb`):
1. Create two stacks, `stack_a` (repository `attacker/repo`) and `stack_b` (repository `victim/repo`, with `bot_login`/`Shipit.user` configured and `continuous_deployment: true`, requiring context `github-actions` via `cached_deploy_spec` `ci.require`).
2. Create a `Commit` with the same `sha` (e.g. `"deadbeef" * 5`) under both `stack_a` and `stack_b`.
3. Assert baseline binding: `commit_b.state == 'unknown'` (or current state) and `commit_b.deployable? == expected_before`.
4. POST a `status` webhook payload with `repository.full_name = 'attacker/repo'`, `sha` = the shared sha, `context: 'github-actions'`, `state: 'failure'`, stubbing/allowing signature verification to succeed only for `attacker`'s org.
5. Assert the binding after: `commit_b.reload.state == 'failure'` and/or `commit_b.deployable?` flips to `false`, and `commit_b.statuses.where(stack_id: stack_b.id).count` increased — proving a webhook authenticated for `attacker/repo` mutated `victim/repo`'s stack's commit, violating "a `github-actions` status affects only the repository that authenticated it."
