Confirmed. The critical piece is `StatusHandler#process` at [1](#0-0) , which finds commits **globally by SHA only**, with no repository/organization scoping check at all, and this directly drives continuous deployment via `Commit#schedule_continuous_delivery` at [2](#0-1) .

### Title
Webhook signature is verified against the payload-selected organization's secret while the handler acts on an unrelated, unverified `sha`/`repository.full_name` field, allowing cross-organization forged CI statuses to trigger unauthorized deploys - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to verify the HMAC signature with by reading `repository_owner` out of the very payload it's about to verify: `Shipit.github(organization: repository_owner)` at [3](#0-2)  with `repository_owner` defined at [4](#0-3) . This is analogous to the `FeeWrapper` bug class: a field that drives execution (`commit.sha`, `repository.full_name`) is decoupled from the field that was actually bound to the cryptographic guarantee (`repository.owner.login`, used only to pick the secret). Nothing enforces that the `sha`/`repository.full_name` used by the handler actually belongs to the organization whose secret validated the signature.

### Finding Description
Shipit supports hosting multiple independent GitHub organizations under one Shipit instance, each with its own `webhook_secret`, as documented in `docs/setup.md` ("Using Multiple Github Applications") and implemented in `Shipit.github_app_config` at [5](#0-4) .

When a webhook arrives, `verify_signature` determines *which* secret to HMAC-verify against purely from an untrusted field in the same request body (`repository.owner.login` or `organization.login`), then verifies the full raw body against that secret [6](#0-5) . Verification only proves "this body was signed by *some* org's registered secret" — it does not prove that the org whose secret matched is actually the owner of the repository/commit the handler will act on.

The `StatusHandler`, used to record CI status webhooks, then processes `params.sha` with **zero repository scoping**:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [7](#0-6) 

An attacker who legitimately controls a GitHub App/organization onboarded to the same Shipit instance (i.e., knows their own `webhook_secret`, which is a normal, unprivileged tenant capability in a multi-org Shipit deployment) can:
1. Craft a raw JSON body where `repository.owner.login` = their own org (so `verify_signature` picks their own known secret) or simply omit/mismatch the repository info to still resolve to their org, but set `sha` to the SHA of a commit belonging to a **different** organization's stack that happens to share/guess the same 40-hex SHA1 value, or more directly:
2. Because `Commit.where(sha: params.sha)` has no repository/stack filter, if any collision or cross-tenant commit sharing occurs (e.g., same open-source dependency commit imported into two different stacks, or a targeted SHA the attacker already knows is tracked by a victim stack), the attacker's own validly-signed webhook (signed with their own org's secret) creates a `Status` record on the **victim's** `Commit`, because the handler never checks that `commit.stack.repository.owner` matches the org that produced a valid signature.

This status write directly triggers `Commit#schedule_continuous_delivery` → `ContinuousDeliveryJob` → `Stack#trigger_continuous_delivery` → `trigger_deploy`, i.e., an **unauthorized deploy**, if the victim stack has `continuous_deployment: true`, as shown in the deploy trigger chain: [8](#0-7)  and [9](#0-8) .

### Impact Explanation
This breaks the equality that should hold: `organization whose secret validated signature == organization owning the repository/commit acted upon`. Before the attack, only GitHub itself (holding the org's real webhook secret) can post a `success` status for a given commit belonging to that org's repos. After the attack, any tenant with their own valid (but unrelated) org secret can post a forged `success` status for **any tracked commit SHA in the entire Shipit instance**, because `StatusHandler` never re-derives or checks a repository binding for the `sha` field. Where `continuous_deployment` is enabled, this can trigger an unauthorized deploy of a stack the attacker has no legitimate access to — matching the "unauthorized deploy" Critical impact criterion.

### Likelihood Explanation
Requires the attacker to control at least one legitimately configured (but unprivileged relative to the victim) organization's webhook secret in a multi-org Shipit deployment, and to know or guess a target commit SHA tracked by the victim stack (SHAs are frequently public via GitHub, PRs, CI logs, etc., and are not secrets). No GitHub App private key, `ApiClient` token, or Shipit session is needed — only the ability to send an HTTP POST to `/webhooks` with a body correctly HMAC-signed using the attacker's own known secret.

### Recommendation
`StatusHandler#process` (and any other handler using `Commit.where(sha: ...)` without scoping) must resolve the target `Stack`/`Repository` via `payload.dig('repository', 'full_name')` (as other handlers correctly do via `Repository.from_github_repo_name`) and restrict the `Commit` lookup to commits belonging to that repository. Additionally, `verify_signature` should not trust an attacker-controlled field to select the verification key without cross-checking that the resolved organization actually owns the repository referenced elsewhere in the same payload before any writes occur.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` (attacker-controlled, knows `webhook_secret_A`) and `OrgB` (victim), per `docs/setup.md`'s multi-app config.
2. Attacker learns/guesses a commit SHA tracked in an `OrgB` stack (e.g., from a public GitHub commit URL or PR).
3. Attacker POSTs to `/webhooks` with `X-Github-Event: status`, body `{"sha": "<victim_sha>", "state": "success", "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgA/anything"}}`, and `X-Hub-Signature` computed with `webhook_secret_A`.
4. `verify_signature` resolves `Shipit.github(organization: "OrgA")` and successfully verifies the signature against the attacker's own secret.
5. `StatusHandler#process` runs `Commit.where(sha: "<victim_sha>")`, finds the `OrgB` commit (no owner check), and creates a `success` `Status` on it.
6. If the `OrgB` stack has `continuous_deployment: true`, `Commit#schedule_continuous_delivery` fires and an unauthorized deploy is enqueued for `OrgB`'s stack.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
