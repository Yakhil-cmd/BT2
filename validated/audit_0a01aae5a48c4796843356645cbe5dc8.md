### Title
Unallowlisted PR-label injection into `git` process environment enables `GIT_PROXY_COMMAND` RCE - (File: app/models/shipit/review_stack.rb, lib/shipit/stack_commands.rb, lib/shipit/command.rb)

### Summary
`ReviewStack#env` merges every pull-request label name (uppercased) as an environment-variable key with value `"true"`, with no allowlist of permitted keys, and these merged keys flow unchanged through `StackCommands#env`/`TaskCommands#env` into `Command#unbundled_env`, which is passed directly to `PTY.spawn` for every `git` invocation (`fetch`, `git_clone`, `checkout`, etc.). An attacker who opens a PR with a label literally named `git-proxy-command` (case-insensitive, becomes `GIT-PROXY-COMMAND` after upcase — note the dash) or `GIT_PROXY_COMMAND` can inject a variable that `git` may honor to invoke an attacker-chosen program during network operations.

### Finding Description
The broken binding claimed is: *the set of keys in the environment hash passed to `PTY.spawn` should be restricted to the deploy spec's `machine_env` and declared `VariableDefinition` names*, versus what the code actually does: `ReviewStack#env` (`app/models/shipit/review_stack.rb:84-93`) does `super.merge(pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" })` — merging attacker-controlled keys with no allowlist at all.

Path: `LabelCapturingHandler#capture_labels` (`app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb:98-102`) persists `params.pull_request.labels.map(&:name)` verbatim from the webhook payload, with no allowlist or filtering on the label name string, onto `pull_request.labels`. `ReviewStack#env` reads that persisted list and upcases each name into an env hash key with value `"true"`. `StackCommands#env` (`lib/shipit/stack_commands.rb:13-15`) does `super.merge(@stack.env)`, so for a `ReviewStack` this includes the label-derived keys. `StackCommands#fetch`/`#git_clone` (`lib/shipit/stack_commands.rb:27-35, 112-114`) pass `env:` into `Commands#git`, which builds a `Command.new("git", ..., env: ...)` (`lib/shipit/commands.rb:28-32`). `Command#unbundled_env` (`lib/shipit/command.rb:103-105`) does `BASE_ENV.merge(...).merge(@env.stringify_keys)` — again no key allowlist — and `Command#start` passes this merged hash straight to `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` (`lib/shipit/command.rb:92`).

The attacker's exact request: open a pull request from a fork against a repository with an active/provisioned `ReviewStack`, and add a label named e.g. `git_proxy_command` (GitHub label names are case-insensitive but the raw string is preserved; `label_name.upcase` produces `GIT_PROXY_COMMAND`) with a value chosen by naming a helper script the attacker controls to be reachable/executed. GitHub then emits a `pull_request` webhook (`labeled` action) which is processed by `LabelCapturingHandler`, which stores the label and re-derives env on next `fetch`/`git_clone`/task run.

None of the existing guards stop this: `verify_signature`/`GitHubApp#verify_webhook_signature` only authenticate that the payload came from the configured GitHub App/webhook source for *that* repository — they don't restrict label *content*. The `ExplicitParameters` schema for `LabelCapturingHandler` only requires `labels: Array { requires :name, String }` — any string is accepted, no format/allowlist validation. `EnvironmentVariables#permit`, if it exists, is not applied to `ReviewStack#env`'s label merge — this merge point bypasses whatever allowlisting exists for declared `VariableDefinition`s in the deploy spec, because it's a raw hash merge of attacker strings performed at the `ReviewStack` level, downstream of and additive to `machine_env`.

### Impact Explanation
This allows any user who can open a pull request against a repository with an active ReviewStack (i.e., any GitHub user with fork/PR privileges on a public repo, or any collaborator on a private one) to inject environment variables recognized by `git` — notably `GIT_PROXY_COMMAND`, `GIT_SSH_COMMAND`/`GIT_SSH`, `GIT_ASKPASS` (if not otherwise set), `GIT_EXTERNAL_DIFF`, etc. — into every `git fetch`/`git clone` invocation for that stack's working directory, and into any task/deploy step (`TaskCommands#env`) since `TaskCommands#env` also merges `@stack.env`. Since `git` on `fetch`/`clone` over supported transports can invoke `GIT_PROXY_COMMAND` to establish a proxy connection, and the value is entirely attacker-supplied text (though in this specific env-key-only scenario the value is hardcoded to `"true"`, which alone likely wouldn't execute a full arbitrary command — see caveat below), this is an environment-variable injection primitive on the deploy host process reachable from an unprivileged PR author. This matches "Critical — RCE on the deploy host via `Command`/`PTY.spawn`" if the value can be crafted to be a valid, executable command string; the given design (label *name* becomes the key, fixed value `"true"`) limits the *value* the attacker controls unless a separate primitive lets the attacker also control the value (e.g., via a different label format or via `@task.env`/deploy spec keys elsewhere). The blast radius is scoped to the single stack/repository owning the pull request; it does not by itself cross tenants, since `ReviewStack#env` only merges the *current stack's* pull request's labels.

### Likelihood Explanation
Precondition: the target repository must have review stacks enabled and provisioned/active for the attacker's PR (`labeled_active_stack?`/`opened_active_stack?` gating in `LabelCapturingHandler`). Attacker cost is trivial — adding a label to their own PR requires no special permission on a repo they control (their own fork triggering the webhook) or, per the threat model, on any repo where they can label PRs. It's fully repeatable per PR/per label change and requires no secrets. The main limiting factor for full RCE is that the environment *value* here is fixed to `"true"`; achieving code execution via `GIT_PROXY_COMMAND=true` specifically would not execute an attacker binary named `true`'s content — `true` is a real, harmless no-op binary on the PATH, so as posed, this specific chain injects a recognized git env var but with an attacker-uncontrolled value, undermining the "arbitrary command" claim in the question.

### Recommendation
Do not merge raw pull-request label names as environment variable keys in `ReviewStack#env`. Restrict any PR-label-derived environment key to an explicit prefix/allowlist (e.g., only permit keys declared in the deploy spec's `VariableDefinition`s, filtered through the same `EnvironmentVariables#permit`/allowlist used for other environment sources) and reject/strip any label name that collides with `git`-recognized or otherwise security-sensitive variable names (`GIT_*`, `LD_PRELOAD`, `PATH`, etc.) before merging into the process environment reaching `Command#unbundled_env`/`PTY.spawn`.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_env_test.rb (conceptual)
test "ReviewStack#env merges attacker-controlled label names as env keys with no allowlist" do
  stack = shipit_review_stacks(:shipit_review_stack) # or build one with a pull_request
  stack.pull_request.update!(labels: ['git_proxy_command'])

  env = stack.env
  assert_equal 'true', env['GIT_PROXY_COMMAND'],
    "expected label name to be upcased into an unallowlisted GIT_PROXY_COMMAND env key"
end

test "Command#unbundled_env inherits ReviewStack-derived GIT_PROXY_COMMAND key" do
  command = Shipit::Command.new('git', 'fetch', env: { 'GIT_PROXY_COMMAND' => 'true' }, chdir: Dir.mktmpdir)
  assert_includes command.unbundled_env.keys, 'GIT_PROXY_COMMAND'
end
```
This demonstrates the key-injection binding is broken (no allowlist between PR label names and the env hash reaching `PTY.spawn`), while noting the attacker does not control the *value* in this specific chain (fixed to `"true"`), which limits — but does not eliminate — the practical severity relative to the "arbitrary command" claim in the question.
