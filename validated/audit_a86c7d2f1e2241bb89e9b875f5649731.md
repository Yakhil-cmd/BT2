### Title
StatusHandler writes GitHub status data to any Commit matching a SHA regardless of reporting repository - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits solely `Commit.where(sha: params.sha)` and calls `commit.create_status_from_github!(params)` on every match, without ever checking that the commit's `stack`/`repository` corresponds to the repository that authenticated the webhook. Since `WebhooksController#verify_signature` only proves the payload was signed by the org named in `payload['repository']['owner']['login']` (the attacker's own org), an attacker who owns any GitHub repo can push a commit whose SHA collides with a commit already tracked by a completely different (victim) tenant's stack, and have their own CI emit a `status` webhook that gets applied to the victim's `Commit` row.

### Finding Description
The broken binding is: **the org whose `webhook_secret` verified the request (`repository_owner` from the payload, e.g. `attacker`) must equal the org that owns the `Stack`/`Commit` being mutated**. In the actual code, `WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-49) resolves `Shipit.github(organization: repository_owner)` from `params.dig('repository', 'owner', 'login')` and checks the signature against that org's `GithubHook#webhook_secret`. This only proves the sender controls the named repository/org's secret — it says nothing about which `Commit` rows in the database will be touched.

`Shipit::Webhooks::Handlers::Handler` (app/models/shipit/webhooks/handlers/handler.rb:32-38) even provides a `stacks` helper that scopes lookups via `Repository.from_github_repo_name(repository_name)&.stacks`, and other handlers (e.g. `CheckSuiteHandler`) use it. `StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24), however, does **not** use `stacks` or `repository_name` at all:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

Because `sha` is a global (non-unique-per-repo) column on `Commit`, any commit sharing that SHA in any stack across the entire Shipit instance will have `create_status_from_github!` invoked, writing a `Status` row into that commit's `statuses` association (`app/models/shipit/commit.rb:165-169`), which affects `Commit#status`, `deployable?`, `blocked?`, `deployed?`, and downstream continuous-deployment scheduling (`schedule_continuous_delivery`) for the victim's stack.

Exploit flow: attacker forks victim's public repo (or otherwise engineers a SHA collision, e.g. shared early history) so a SHA already recorded as a `Commit` for the victim's stack is reachable in `attacker/evil`. Attacker's own CI (fully attacker-controlled, e.g. GitHub Actions in `attacker/evil`) sends `POST /webhooks` with `X-Github-Event: status`, `repository.full_name: attacker/evil`, `sha: <shared sha>`, `state: success`, signed with `attacker`'s legitimate `webhook_secret`. `verify_signature` succeeds because it correctly validates against `attacker`'s own secret; `drop_unhandled_event`/`ExplicitParameters` schema for `StatusHandler` do not check repository identity; `StatusHandler#process` then mutates the victim's `Commit` regardless of which repo/org authenticated the request.

### Impact Explanation
An attacker who controls no privileged Shipit credential can inject an arbitrary CI status (e.g. forging `success`) onto a commit belonging to a different tenant's stack. If that commit is otherwise pending review/CI and the victim's stack has `continuous_deployment?` enabled with `ignore_ci?` false, this forged "success" status can make the commit `deployable?` and trigger `schedule_continuous_delivery`, potentially causing an unauthorized deploy of the victim's stack. This is a cross-repository write into another tenant's stack/commit data caused by a payload that authenticated for a different repository — matching the "Critical: a payload for one repository mutating another's stack, commit... or an unauthorized deploy" category. It's repeatable against any repository/stack whose commit SHAs are known or predictable/shared (forks of public repos trivially satisfy this), and the attacker only needs to control one unprivileged GitHub repository and its CI.

### Likelihood Explanation
Preconditions: the victim's repository must be public (or its early commit history otherwise known/shared) so the attacker can produce a fork sharing SHAs, and the victim must have a `Commit` row already tracked (normal for active Shipit stacks). The attacker needs only an ordinary, unprivileged GitHub account: create a public fork, add a CI job that emits a signed webhook using the fork's own legitimate GitHub App/webhook credentials for `attacker`'s org. No Shipit session, API token, or knowledge of `webhook_secret`/`secret_key_base` is required — everything used to sign the request is the attacker's own repo's legitimate secret. This is a low-cost, low-skill, fully repeatable attack against any Shipit deployment tracking public repositories with fork-able early history.

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` to the stacks/repository that actually authenticated the webhook, mirroring the `stacks` helper already used elsewhere: e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or `Commit.joins(:stack => :repository).where(sha: params.sha, shipit_repositories: { ... repository_name ... })`, so a status is only ever applied to commits belonging to the repository named (and cryptographically verified) in the payload.

### Proof of Concept
Minitest plan (extend `test/controllers/webhooks_controller_test.rb` or `test/models/shipit/webhooks/handlers_test.rb`):
1. Fixture setup: create `victim_stack` belonging to repository `victim/repo`, with `Commit` fixture `victim_commit` whose `sha == "deadbeef...".freeze` (SHA collision value), `statuses.count == 0`.
2. Create a second `GithubHook`/org config for `attacker` with its own `webhook_secret`, stub/allow `Shipit.github(organization: 'attacker').verify_webhook_signature` to return `true` (simulating a correctly signed request from the attacker's own repo).
3. POST to `/webhooks` with `X-Github-Event: status`, body: `{ "sha" => victim_commit.sha, "state" => "success", "repository" => { "full_name" => "attacker/evil", "owner" => { "login" => "attacker" } } }`.
4. Assert: `assert_difference('victim_commit.statuses.count', 1) { post :create, body: payload, as: :json }` — proving a status was written to the victim's commit even though the request authenticated only for `attacker/evil`, and that `StatusHandler#stacks`/`repository_name` was never consulted (no code path checks `payload.dig('repository','full_name')` against `victim_commit.stack.repository`).
5. Additionally assert `victim_commit.reload.status.state == 'success'` to show the forged status is now visible and affects `deployable?`.
