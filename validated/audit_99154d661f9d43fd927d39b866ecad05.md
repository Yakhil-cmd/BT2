### Title
Repay/recapitalize refund legs pay a declared-but-unreceived amount out of pool custody without debiting `cash` — (File: contracts/pool/src/ops/repay.rs)

### Summary
The CVE class is "cleanup frees a resource that was never initialized": on an early-exit path, a value that was never populated is released. The exact analog exists in the pool's repay and recapitalize legs: the refund is computed from the *declared* `action.amount` / `amount` (what the caller claims to have paid), not from any measured inbound receipt, and `Cache::transfer_out` sends real custody to the payer without touching the `cash` book.

### Finding Description
In `ops::repay::apply` (`contracts/pool/src/ops/repay.rs:25-34`), `resolve_repay` splits the declared `action.amount` into `net_repay` and `overpayment`; only `net_repay` is credited to `cash` (`cache.credit_cash(net_repay)` at line 57), while `transfer_out(payer, overpayment)` at line 32 pays the declared excess out of the pool's token balance unconditionally. The same shape exists in `ops::recapitalize::apply` (`contracts/pool/src/ops/recapitalize.rs:26-38`): `refund = amount - applied` is paid out at line 34 while only `applied` is credited. Neither leg verifies that `amount` was actually received by the pool — the code comments ("The controller transfers the repay amount into the pool before this call") make trust in the inbound transfer an assumption, not a check.

The pool's own tests demonstrate the consequence. `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` (`contracts/pool/tests/flows.rs:3590-3611`) calls `repay` with a declared amount equal to the pool's full custody against a debt-free market: `resolve_repay` takes the full-close branch, `net_repay == 0` passes the `RepayRoundsToZeroShares` disjunct, and `assert_unfunded_refund_drained_custody` (`flows.rs:3378-3401`) confirms the payer is "refunded in full for a payment that never happened", the pool balance goes to zero, and `cash` is unchanged — "the market reports itself solvent and cannot pay" (`flows.rs:3404-3406`). The recapitalize leg is shown to be unmeasured in `tests/test-harness/tests/controller/outbound_transfer_measurement.rs:36-37` ("`transfer_out` moves the declared `refund` out of the pool whatever the payer receives").

### Impact Explanation
If the declared amount can exceed the measured receipt on any reachable repay/recapitalize path, the refund leg transfers genuine pool custody (suppliers' principal) to the caller while the `cash` book still reports the funds as present. That is theft of user funds plus a silent solvency gap: `Cache::require_reserves` reads the book, so subsequent withdrawals/borrows are admitted against tokens the pool no longer holds and revert inside the SAC transfer — permanently freezing the remaining suppliers' funds. Even absent an unfunded call, the unmeasured refund means any shortfall between the declared amount and the actual delivered amount (e.g., a reduced receipt) is absorbed by the pool, not the payer.

### Likelihood Explanation
The reachable surface is the unprivileged `repay` and `recapitalize` controller entrypoints (both documented as public, pause-agnostic per `docs/reference/endpoints.md:63,90`). Exploitability hinges on whether the controller enforces measured inbound receipts equal to `action.amount` before invoking the pool legs — the docs note that "pool supply measures receipts again" (`endpoints.md:82`), implying measurement is a per-leg opt-in rather than a uniform invariant, and the pool code itself performs no receipt check. I could not fully verify within this investigation whether the controller measures the inbound transfer for repay/recapitalize or merely authorizes a transfer that may deliver less than declared; if it does not measure, the unfunded-refund drain shown in the pool tests is directly reachable.

### Recommendation
- Measure inbound receipts in the pool (or controller) for repay and recapitalize: snapshot `token.balance(pool)` before and after the authorized transfer and use the measured delta, not `action.amount`, as the basis for `net_repay`/`applied` and `overpayment`/`refund`.
- Alternatively, have `transfer_out` for refunds debit `cash` (or assert `cash` covers custody) so a refund can never exceed what the book records as received.

### Proof of Concept
Per the existing test in `contracts/pool/tests/flows.rs:3590-3611`:

```rust
// Pool holds `custody_before` tokens, `borrowed == 0` (no debt).
// Attacker calls repay declaring amount == custody_before, transferring nothing.
let credited = t
    .client()
    .repay(&payer, &t.ract(0, custody_before))
    .get_unchecked(0)
    .actual_amount;

assert_eq!(credited, 0);                          // no debt retired
assert_eq!(token.balance(payer), custody_before); // full "refund" paid
assert_eq!(token.balance(&t.pool), 0);            // pool custody drained
// cash book unchanged: market reports reserves it no longer holds;
// supplier withdraws are admitted by require_reserves and revert in SAC transfer.
```

The identical pattern applies to `recapitalize`: with `backing_shortfall == 0`, `applied = 0` and `refund = amount`, so the entire declared amount exits custody for a contribution the book never recorded. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)

```rust
pub(crate) fn accounting(
    env: &Env,
    hub_asset: HubAssetKey,
    amount: i128,
) -> RecapitalizationOutcome {
    require_nonneg_amount(env, amount);
    let mut cache = ops::renewed_market(env, &hub_asset);

    let applied = amount.min(guards::backing_shortfall(&cache));
    let refund = amount
        .checked_sub(applied)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow));

    cache.credit_cash(applied);
    cache.commit();
```

```rust
fn test_unfunded_repay_overpayment_refund_also_pays_out_of_custody() {
    let t = TestSetup::new();
    let token = token::Client::new(&t.env, &t.asset);
    let payer = Address::generate(&t.env);

    let custody_before = token.balance(&t.pool);
    let before = t.state_snapshot();
    assert_eq!(
        before.cash, custody_before,
        "fixture guard: book and custody must start in sync"
    );
    assert_eq!(before.borrowed, 0, "fixture must carry no debt");

    // Nothing transferred in, no debt to retire: the whole amount is "excess".
    let credited = t
        .client()
        .repay(&payer, &t.ract(0, custody_before))
        .get_unchecked(0)
        .actual_amount;
    assert_eq!(credited, 0, "no debt was retired, so nothing is credited");
    assert_unfunded_refund_drained_custody(&t, &payer, custody_before, &before);
}
```
