### Title
`in_data_feed()` accepts data-feed messages from non-serial (`sequence != 'good'`) units, unlike the equivalent `data_feed()` lookup - (File: `data_feeds.js`)

### Summary
The CVE describes a validator that failed to check an authority indicator (the `AA` flag) before trusting untrusted records, letting an attacker bypass a security check that a sibling code path enforced correctly. In `ocore--009`, the AA-formula function `in_data_feed()` (backed by `dataFeeds.dataFeedExists()`) scans currently-unstable data-feed messages but omits the `sequence !== 'good'` filter that the sibling function `readDataFeedValue()` (backing `data_feed()`) explicitly applies. This lets an AA treat a data-feed message from a unit that is provably non-serial (losing side of a double-spend, destined to be voided) as if it were a valid, counted record.

### Finding Description
`dataFeedExists()` is used by the oscript function `in_data_feed[...]` when it is evaluated inside an AA (`bAA` is the current-execution flag passed through from `formula/evaluation.js`). When `bAA` is true, it first scans `storage.assocUnstableMessages` for matching data-feed payloads: [1](#0-0) 

Note that the loop checks `objUnit.bAA`, the `latest_included_mc_index` range, and address intersection — but never checks `objUnit.sequence`.

Compare this with `readDataFeedValue()`, which backs the `data_feed[...]` oscript function and iterates the exact same `storage.assocUnstableMessages` structure for the unstable-AA case, but explicitly skips any unit whose `sequence` is not `'good'`: [2](#0-1) 

The call sites in `formula/evaluation.js` confirm both are triggered by the same underlying AA formula surface — `data_feed[...]` calls `readDataFeedValue` and `in_data_feed[...]` calls `dataFeedExists`, both passing the AA execution context: [3](#0-2) 

`sequence` marks whether a unit is the winner ('good') or loser ('bad'/'final-bad') of a double-spend conflict; only 'good' units' messages are meant to count as authoritative data. `readDataFeedValue()` enforces this, but `dataFeedExists()` (i.e., `in_data_feed`) does not — directly mirroring the CVE's bug class where a validation check that should gate acceptance of a record (an "authority"/validity flag) is applied inconsistently, letting spoofed/losing data flow through one path while a parallel path correctly rejects it.

### Impact Explanation
An AA author whose oscript definition uses `in_data_feed[...]` to gate a payout, unlock, or state transition can be manipulated by an oracle-posting attacker: the attacker deliberately creates a double-spend so that one of the conflicting units (the one carrying the desired data-feed payload) is destined to resolve as non-serial ('bad'/'final-bad'). Before finality, `in_data_feed()` will still report the feed as "found" because it never filters on `sequence`, while `data_feed()` (used to fetch the actual value elsewhere in the same AA) would correctly ignore that same unit. This inconsistency lets an attacker force an AA into an execution branch based on data that every honest node's parallel/authoritative check would reject, leading to AA fund loss, incorrect AA branching, or node disagreement about whether a data-feed-gated condition should be considered satisfied.

### Likelihood Explanation
Any address, including unprivileged unit posters, can post a `data_feed` message and construct a double-spend so that the feed-bearing unit is provisionally unstable and later resolved as non-serial. Because `in_data_feed[...]` is a standard, commonly used oscript primitive available to any AA definition, the vulnerable code path is reachable purely by posting units — no special privilege, hub, or peer role is required.

### Recommendation
Add the same `if (objUnit.sequence !== 'good') continue;` guard to the unstable-message scan inside `dataFeedExists()` in `data_feeds.js`, matching the check already present in `readDataFeedValue()`, so that `in_data_feed[...]` and `data_feed[...]` apply identical validity criteria to unstable AA data.

### Proof of Concept
1. Attacker controls address `X` and crafts two conflicting units `U1` and `U2` spending the same output (double-spend), where `U1` contains message `app: 'data_feed', payload: { "price": 100 }`.
2. Both units propagate; `U1` and `U2` become "unstable" and appear in `storage.assocUnstableMessages`/`assocUnstableUnits`.
3. An AA with oscript containing `in_data_feed[[oracles=X, feed_name="price", feed_value=100]] ? ... : ...` is triggered while `U1`/`U2` are still unstable but the DAG has already determined (via `determineIfIncludedOrEqual`/serial ordering) that `U2` will win and `U1` will be marked non-serial.
4. Because `dataFeedExists()` (lines 34-49 in `data_feeds.js`) never checks `objUnit.sequence`, the AA's `in_data_feed` check returns `true` based on `U1`'s payload even though `U1` is not the serial/valid unit — diverging from what `data_feed[...]` (which does filter on `sequence`) would report for the same data, and diverging from what will ultimately be true once `U1` is finalized as 'final-bad'.
