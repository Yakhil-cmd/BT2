## Analysis

I found a credible analog of the reported bug class in the webhook ingestion path, matching the "organization authenticated versus repository written" binding described in the rules.

### The binding that should hold
`repository_owner` used to select and verify the HMAC signature **must equal** the repository/stack that a webhook event is allowed to act on.

### What I verified

`WebhooksController#verify_signature` picks *which* GitHub App / webhook secret to validate against purely from a field inside the untrusted JSON body itself: [1](#0-0) [2](#0-1) 

So `repository_owner` = `params.dig('repository','owner','login')` (or `organization.login`), and `Shipit.github(organization: repository_owner)` is used only to fetch that organization's configured `webhook_secret` for HMAC verification. The signature computation covers the whole raw POST body, but the *identity check* only proves "whoever sent this request knows the webhook secret configured for the organization named in this payload's own `repository.owner.login` field" — it does **not** prove that the rest of the payload (e.g. `repository.full_name`, the actual stack being targeted) genuinely belongs to that same organization's installation.

`PushHandler#process` then acts on stacks resolved from the payload's repository/branch fields — entirely independent of which organization's secret was used to authenticate the request: [3](#0-2) 

Docs confirm Shipit explicitly supports multi-tenant configurations where distinct GitHub organizations each have their own independently-configured `webhook_secret`: [4](#0-3) 

### The exploit

In a multi-org Shipit deployment, an attacker who legitimately controls **their own** GitHub organization (with the Shipit GitHub App installed, and thus knows their own org's `webhook_secret`) can POST directly to `/webhooks` with:
- `X-Github-Event: push`
- `repository.owner.login` = **attacker's own org** (so `verify_signature` fetches the attacker's own secret and the HMAC they compute with their own known secret passes)
- `repository.full_name` / `ref` / `after` = crafted to reference a **different tenant's** repository/branch and an attacker-chosen SHA

Because `verify_signature` never checks that `repository.full_name`'s owner matches the org whose secret validated the signature, and `PushHandler` resolves the target `Stack` from that same unchecked field, the forged event is accepted and `stack.sync_github(expected_head_sha: params.after)` is invoked against a stack the attacker does not own — a cross-tenant/cross-repository write triggered with attacker-controlled `expected_head_sha`.

### What I could not fully verify
I was not able to read `app/models/shipit/webhooks/handlers/handler.rb` (the base `stacks` scope) or `status_handler.rb` within the available tool budget, so I cannot conclusively confirm the exact query used to resolve `stacks` from the payload, nor whether the same flaw combined with a forged `status` event (fake "success" CI status) could escalate this into a fully unauthorized deploy via continuous delivery. The push-handler path alone is enough to demonstrate the broken binding and an unauthorized cross-tenant `sync_github` call with an attacker-chosen `expected_head_sha`, which is the concrete, provable impact from what I directly read.

### Title
Webhook signature verification is bound to the wrong organization, allowing cross-tenant stack sync forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret used to authenticate an inbound webhook from an attacker-controlled field (`repository.owner.login`) inside the very payload being verified, rather than from any externally-trusted routing context. Webhook event handlers (e.g. `PushHandler`) then act on a *different* payload field (`repository.full_name`/`ref`) to select which `Stack` to mutate. In a multi-org Shipit configuration, these two fields are never checked for consistency.

### Finding Description
`repository_owner` (app/controllers/shipit/webhooks_controller.rb:59-62) is read from the JSON body and used to look up `Shipit.github(organization: repository_owner)`, whose `webhook_secret` is then used to verify `X-Hub-Signature` over the raw POST body (app/controllers/shipit/webhooks_controller.rb:24-30). This proves only that the sender knows *some* configured organization's secret — specifically the one named by a field the sender themselves supplied. It does not bind the verified organization to the resource that downstream handlers subsequently act on. `PushHandler#process` (app/models/shipit/webhooks/handlers/push_handler.rb:12-23) resolves target stacks and branch purely from other unauthenticated-relative-to-org payload fields and calls `stack.sync_github(expected_head_sha: params.after)`.

### Impact Explanation
An attacker who administers their own GitHub organization with the Shipit GitHub App installed (a legitimate but low-privilege tenant in a multi-org install) can forge a push webhook whose `repository.owner.login` matches their own org (so it passes signature verification with their own known secret) while other repository fields point at a different tenant's tracked repository/stack. This lets them invoke `sync_github` with an attacker-chosen `expected_head_sha` against a stack belonging to another organization/tenant — a cross-tenant, cross-repository interaction the requester has no legitimate authorization over, matching the "cross-repository writes" / "unauthorized organization boundary" impact class.

### Likelihood Explanation
Requires only that the attacker's own organization has the Shipit GitHub App installed with its own webhook secret (a normal, documented multi-tenant configuration) and network access to the shared `/webhooks` endpoint — no session, API token, or webhook_secret of the victim organization is needed. This is a plausible, low-effort attack path for any org onboarded as one tenant of a shared Shipit instance.

### Recommendation
Cross-check that the organization used to validate the signature (`repository_owner`) matches the actual owner of the repository/stack being acted upon before dispatching to handlers, e.g. resolve the target `Stack`/`Repository` first and confirm `repository.owner.login == stack.repository.owner` (case-insensitively) prior to calling `sync_github` or any other mutating handler logic, rejecting mismatches with a 422.

### Proof of Concept
1. Attacker operates GitHub org `attacker-org`, installs Shipit's GitHub App, and knows `attacker-org`'s `webhook_secret`.
2. Attacker crafts a push payload:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen sha>",
     "repository": {
       "owner": { "login": "attacker-org" },
       "full_name": "victim-org/victim-repo"
     }
   }
   ```
3. Attacker computes `X-Hub-Signature` over the raw body using `attacker-org`'s known webhook secret and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and validates successfully.
5. `PushHandler#process` finds Stack(s) for `victim-org/victim-repo`/`main` and calls `sync_github(expected_head_sha: "<attacker-chosen sha>")`, an action on a stack outside the attacker's organization.
