### Title
`StatusHandler#process` writes GitHub status updates by bare SHA with no repository/stack scoping, letting a webhook authenticated for one repository mutate `Commit`/`Status` rows belonging to a different stack that happens to share the same commit SHA - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves target records with `Commit.where(sha: params.sha)` and calls `create_status_from_github!` on every match, with no filter on `params.repository.full_name` or any organization/stack scope [1](#0-0) . Every other handler in this engine (`PullRequest::OpenedHandler`, `PullRequest::ReopenedHandler`, etc.) resolves the target strictly through `Repository.from_github_repo_name(params.repository.full_name)` before acting [2](#0-1) , and the base `Handler` class itself exposes a `stacks` helper that does the same repository-scoped lookup [3](#0-2) , so `StatusHandler` is a clear outlier that never uses this scoping and does not even declare `repository` in its `params` schema [4](#0-3) .

### Finding Description
Binding claimed by the invariant: `status.stack_id == repository_that_authenticated(webhook).stacks`. Actual code makes `status.stack_id ∈ { commit.stack_id | commit.sha == params.sha }` for **every** `Commit` row in the whole Shipit installation, independent of which repository's signature validated the request.

Trace:
1. `WebhooksController#create` parses the JSON body and dispatches to `Shipit::Webhooks.for_event('status')`, which is `[Handlers::StatusHandler]` [5](#0-4) .
2. `verify_signature` authenticates the *request* only against `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight from `params.dig('repository','owner','login')` in the payload [6](#0-5) [7](#0-6) . This proves the request came from GitHub for *some repository under that organization* - it proves nothing about which repository's `Commit`/`Status` rows may be touched.
3. `StatusHandler#process` then does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with `sha` and `context` fully attacker/CI-controlled and no repository filter at all [1](#0-0) .
4. `create_status_from_github!` → `add_status` recomputes `commit.status`, emits `deployable_status`, and unconditionally calls `stack.schedule_merges if new_status.pending? || new_status.success?` for whichever stack happens to own that `Commit` row [8](#0-7) . Whether a given context is `required?`/`blocking?` is evaluated per-stack via `commit.required_statuses`/`commit.blocking_statuses` [9](#0-8) , so if the victim stack's deploy spec requires `github-actions`, a forged/misdirected `success` state flips that requirement and can unblock merges/deploys on the victim stack even though the request was signed for a different, unrelated repository.

Why existing guards don't help: `verify_signature` is organization-scoped, not repository- or stack-scoped, and `ExplicitParameters` only validates the shape of `sha`/`state`/`context`, not their relationship to `params.repository.full_name` (which `StatusHandler` doesn't even request). There is no `Repository.from_github_repo_name` check anywhere in this handler, unlike every PR handler.

Caveat on exploitability: this is a **repository-isolation defect**, not something automatically weaponizable against an arbitrary victim from an arbitrary attacker account. To actually flip a status on a specific victim `Commit` row, the attacker's validly-signed webhook must carry the exact same 40-hex SHA as a `Commit` row that belongs to a *different* stack than the one that authenticated it. That requires either (a) two Stacks in the same Shipit instance that track overlapping git history under the same GitHub organization/App installation (e.g., two environment stacks of the same repo, or a repo and an in-org fork sharing pre-fork history), or (b) an actual SHA-1 collision, which is not feasible on demand. Given (a), the requirement in the question that "review_stacks_enabled false" and the `provision?`/`unarchive?` operator-precedence issue in `PullRequest::OpenedHandler`/`ReopenedHandler` (`review_stacks_enabled && allow_all? || (allow_with_label? && ...) || (prevent_with_label? && ...)`, where `&&` binds tighter than `||`, so `review_stacks_enabled` only gates the `allow_all` branch and not the label-based branches) [10](#0-9)  is a real, independent bug, but it is not actually load-bearing for the `StatusHandler` write: `StatusHandler#process` never reads `review_stacks_enabled` or any provisioning flag at all - it acts on whatever `Commit` rows already exist regardless of how the owning stack/review-stack was provisioned. The two bugs are adjacent, not chained as described.

### Impact Explanation
Confirmed impact is a `Status` row (and via `add_status`, `schedule_merges`/`deployable_status` side effects) written for a `Commit`/`Stack` that did not authenticate the request - matching the "payload for one repository mutating another's stack/commit" Critical category, but only between stacks in the same Shipit instance that share commit history (multi-environment stacks of one repo, or same-org forks/mirrors). It is repeatable against any such pair of stacks for as long as they share overlapping SHAs, and can unblock `required_statuses`/trigger `schedule_merges`, indirectly enabling an unauthorized merge/deploy on the victim stack. It is not, from what is verifiable here, a fully generic "any internet attacker against any arbitrary victim repo" primitive, because the organization-scoped signature check still gates who can send a validly-signed request in the first place.

### Likelihood Explanation
Requires: (1) the attacker has a repository under an organization whose GitHub App/webhook secret Shipit trusts (they can be a legitimate low-privilege member/fork owner within that org's installation), and (2) a victim stack in the same Shipit instance whose `Commit` table contains a row with a SHA that is also reachable/producible by the attacker's repo (shared history via multi-stack-per-repo setups or forks). This is a plausible but non-trivial operational configuration, not universally present in every Shipit deployment. Attacker cost per successful hit is low (one webhook), and it is repeatable once the SHA-sharing precondition exists.

### Recommendation
Scope `StatusHandler#process` to the repository that authenticated the request: require `repository.full_name` in the `params` schema, resolve it via `Repository.from_github_repo_name`, and restrict the `Commit` lookup to `commit.stack.repository_id == repository.id` (or otherwise join through `Stack`/`Repository`) before calling `create_status_from_github!`, mirroring the pattern already used in `Handler#stacks` and the `PullRequest` handlers. Separately, fix the operator-precedence bug in `provision?`/`unarchive?` by adding parentheses so `review_stacks_enabled` gates all three provisioning behaviors, not just `allow_all?`.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Create two `Stack`s/`Repository`s, `victim_repo` (`review_stacks_enabled: false`, deploy spec requiring `github-actions`) and `attacker_repo`, each with a `Commit` row sharing the identical `sha` (simulate shared history by inserting both fixtures with the same `sha` value).
2. Assert-before: `victim_commit.reload.status.state` is not `success` for context `github-actions`, and `victim_stack.commits.last.deployable?` (or equivalent required-status check) is false.
3. Call `Shipit::Webhooks::Handlers::StatusHandler.call({'sha' => shared_sha, 'state' => 'success', 'context' => 'github-actions', 'repository' => {'full_name' => attacker_repo.github_repo_name}})`.
4. Assert-after: `victim_commit.reload.status.state == 'success'`, and that `Hook`/`schedule_merges` fired for `victim_stack` even though the payload's `repository.full_name` was `attacker_repo`'s - demonstrating the write crossed repository boundaries because `StatusHandler` never checked `params.repository.full_name` against `victim_commit.stack.repository`.

        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
