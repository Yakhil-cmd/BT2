### Title
Webhook signature is verified against `repository.owner.login`, but the write target is looked up from the independent `repository.full_name` field — cross-organization/cross-repository writes - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which organization's webhook secret to validate the HMAC signature against using `repository.owner.login` (or `organization.login`) extracted from the JSON body. Every event `Handler` subclass (push, status, check_suite, pull_request, membership) instead resolves the record to mutate using `repository.full_name`, a separate JSON field that is never cross-checked against `repository.owner.login`. Because both fields live inside the same attacker-controlled JSON payload, whoever holds the webhook secret for organization A can forge a payload whose `owner.login` is `A` (so the signature check passes with A's secret) while `full_name` points at organization B's repository, causing Shipit to act on B's stack.

### Finding Description
`verify_signature` computes the signing organization purely from payload content: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization: ...)` returns a `GithubApp` configured with a per-organization `webhook_secret` (`@webhook_secret = @config[:webhook_secret]`), confirming Shipit supports multiple independently-configured organizations and the existence of `Shipit::GithubOrganizationUnknown` for unrecognized ones: [3](#0-2) [4](#0-3) 

However, `Handler`, the base class of every webhook handler, resolves the actual `Repository`/`Stack` to operate on from a *different* field: [5](#0-4) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`Repository.from_github_repo_name` splits `full_name` on `/` into an independent `owner/name` pair used purely for the DB lookup: [6](#0-5) 

Nothing in the request pipeline asserts `repository.owner.login == full_name.split('/').first`. Consequently, the binding the code implicitly relies on — "the organization whose secret validated this signature" ⇔ "the repository this event acts on" — is never enforced. `PushHandler#process` and `StatusHandler#process` act directly on whatever stack/commit `repository_name` (i.e. `full_name`) resolves to: [7](#0-6) [8](#0-7) 

### Impact Explanation
An attacker who legitimately controls (and thus knows the webhook secret of) organization A configured in the same Shipit instance can submit a `push` webhook payload with `repository.owner.login = "A"` (so `verify_signature` fetches and successfully checks A's secret) but `repository.full_name = "B/victim-repo"`. `repository_owner` (used only for auth) and `repository_name`/`stacks` (used for the actual mutation) diverge, so Shipit will:
- Enqueue `GithubSyncJob`/`stack.sync_github` for organization B's stack (`PushHandler`), forcing an unauthenticated resync of a repository the requester doesn't own, or
- Create commit statuses on organization B's commits (`StatusHandler`) via `commit.create_status_from_github!`, or
- Trigger equivalent cross-tenant effects in `check_suite`, `pull_request`, and `membership` handlers, all of which inherit the same `repository_name`/`full_name` resolution.

This is a cross-repository write reachable by anyone possessing a *valid webhook secret for any one organization hosted on the instance*, letting them act on any other organization's stacks/commits without ever knowing that organization's secret. This matches the explicitly listed Critical impact "cross-repository writes."

### Likelihood Explanation
Exploitability requires only knowledge of one organization's webhook secret (an assumption already required to reach the webhook endpoint at all, so it isn't an added privilege beyond what any legitimate single-organization operator already has). No repository write access, no `ApiClient` token, and no session are needed — only the ability to send an HTTP POST with a crafted JSON body and a correctly computed HMAC keyed with the attacker's own known secret. On any Shipit deployment configured with more than one GitHub organization, this is directly reachable.

### Recommendation
Enforce that the organization used to validate the webhook signature is the same organization the resolved repository/stack actually belongs to. Concretely, in `Handler#repository_name`/`stacks`, verify that the owner portion of `full_name` equals `payload.dig('repository', 'owner', 'login')` (the same field `WebhooksController#repository_owner` used for signing), and reject/short-circuit the event if they differ. Alternatively, restructure the lookup so a single canonical field (validated once at signature-verification time) is threaded through to every handler instead of independently re-derived from `full_name`.

### Proof of Concept
Given two organizations configured in Shipit: `attacker-org` (secret known to attacker) and `victim-org` (secret unknown to attacker, hosting stack `victim-org/victim-repo` tracking branch `main`):

```
POST /github/webhooks
X-Github-Event: push
X-Hub-Signature: sha1=<HMAC-SHA1 computed with attacker-org's known webhook_secret over the raw body below>

{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```

- `WebhooksController#verify_signature` computes `repository_owner` = `"attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and successfully verifies the signature using the attacker's own known secret.
- `PushHandler#stacks` resolves `repository_name` = `payload.dig('repository', 'full_name')` = `"victim-org/victim-repo"`, looks up that `Repository`, and calls `stack.sync_github(expected_head_sha: params.after)` on `victim-org`'s stack — an action the attacker was never authorized to trigger.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
