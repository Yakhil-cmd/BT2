### Title
Stack-scoped API tokens can read CCMenu build status of any stack, bypassing their stack authorization - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
An `ApiClient` token that is scoped to a single stack (via `ApiClient#stack_id`) is meant to only ever "touch" that one stack, as enforced by `Api::BaseController#stack`/`#stacks`, which filter by `current_api_client.stack_id`. `Api::CCMenuController` overrides `#stack` to bypass this scoping entirely, breaking the binding: `stack a token authorizes == stack a token touches`.

### Finding Description
`Api::BaseController` defines the stack-scoping mechanism that every other API controller relies on: [1](#0-0) 

`stacks` restricts the visible/actionable stacks to `current_api_client.stack_id` when the client is scoped, and `stack` resolves `params[:stack_id]` only within that restricted relation via `stacks.from_param!(...)`. Controllers such as `Api::StacksController`, `Api::TasksController`, `Api::DeploysController`, `Api::LocksController`, etc. all inherit this `stack`/`stacks` behavior (confirmed for `Api::StacksController`, which reuses `stacks.from_param!`) [2](#0-1) , so a token scoped to stack A cannot resolve stack B through `params[:stack_id]`/`params[:id]`.

`Api::CCMenuController`, however, redefines `stack` to resolve directly against the global `Stack` model, ignoring the client's `stack_id` scope entirely: [3](#0-2) 

The `require_permission :read, :stack` check only verifies the client has the generic `read:stack` permission string; it does not verify which stack is being accessed [4](#0-3) . Because `CCMenuController#stack` uses `Stack.from_param!` instead of `stacks.from_param!`, any `stack_id` in the URL is resolved against every stack in the installation, not just the one the client's token was issued for.

### Impact Explanation
This is an unauthenticated-scope escalation: a party holding a stack-scoped `ApiClient` token (e.g. the token minted per-stack by `CCMenuUrlController#client`, which explicitly creates a client scoped to a single stack with `read:stack` permission) can pass a different `stack_id` to `GET /api/stacks/:stack_id/ccmenu` and retrieve that other stack's build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `activity`, `webUrl`, lock state, etc.) — data belonging to a stack the token was never authorized to see. This is an unauthenticated read of stack state across the intended trust boundary, matching the "High" impact bucket (unauthenticated read of stack state / task output) defined by the scope rules.

### Likelihood Explanation
Exploitation requires only a valid, but narrowly-scoped, API client token (e.g. the CCMenu token created automatically by `CCMenuUrlController` for any authenticated Shipit user for a single stack) — no elevated privileges, GitHub write access, or repository access are needed. The attacker simply swaps the `stack_id` segment of the URL. This is a simple, deterministic bypass, not a race condition or timing issue.

### Recommendation
Remove the `stack` override in `Api::CCMenuController` and use the inherited `stacks.from_param!(params[:stack_id])` from `Api::BaseController` (or otherwise verify `current_api_client.stack_id` matches the resolved stack) so that stack-scoped clients cannot resolve stacks outside their authorized scope, consistent with every other API controller.

### Proof of Concept
1. As a Shipit user, visit a stack's CCMenu URL fetch endpoint (`GET /ccmenu/*stack_id`), which creates/returns a stack-scoped `ApiClient` (permissions `read:stack`, `stack_id` = Stack A) and its `authentication_token` [5](#0-4) .
2. Using that token, call `GET /api/stacks/<stack-B-owner>/<stack-B-repo>/<stack-B-branch>/ccmenu` (i.e., substitute Stack B's `stack_id` param) with `Authorization: Basic <token>--` or `?token=<token>`.
3. Because `Api::CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly instead of the scoped `stacks.from_param!`, the request succeeds and returns Stack B's build status/activity/lock state — despite the token being scoped only to Stack A.
