### Title
Webhook signature is verified against `repository.owner.login`, but events are applied to `repository.full_name` — cross-organization spoofing of GitHub events - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App/organization config (and therefore which `webhook_secret`) to use for HMAC verification based on `repository_owner`, derived from the incoming payload itself: [1](#0-0) [2](#0-1) 

```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

This value is only used to look up `Shipit.github(organization: repository_owner)` (Shipit supports one `webhook_secret`/App config per GitHub organization, see `config/secrets.development.shopify.yml` and `lib/shipit/github_app.rb`), and to compute/verify `X-Hub-Signature` against that organization's secret.

Once the signature check passes, the entire raw payload is dispatched unchanged to event handlers (`Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`). Every handler resolves the target repository/stack from a *different* field of the same attacker-controlled payload: [3](#0-2) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`repository.owner.login` (used for **authentication**) and `repository.full_name` (used for **authorization/target selection**) are never checked to be consistent. In a multi-org Shipit deployment, an operator/administrator of *Organization A* (a legitimately configured tenant with its own valid `webhook_secret`, which they naturally control because they set up their own organization's GitHub App/webhook) can craft and correctly sign a webhook where `repository.owner.login = "OrgA"` (so the signature validates against OrgA's secret) but `repository.full_name = "OrgB/some-repo"` — a repository belonging to an entirely different, unrelated organization tracked in the same Shipit instance.

The binding that should hold is:
`organization authenticated (repository.owner.login, used to pick webhook_secret) == organization whose repository is written (repository.full_name, used to resolve the Stack/Repository that gets mutated)`

This binding is never enforced, so `verify_signature` authenticates one tenant while the handler layer acts on another tenant's data.

### Impact Explanation
This directly matches one of the explicitly allowed analog classes: *"an organization that authenticated versus the repository that is written."* Concretely, using their own legitimately-known webhook secret, a member of one onboarded organization can forge GitHub events (`push`, `status`, `pull_request`, `check_suite`, `membership`) against another organization's repository/stack that Shipit tracks:
- `PushHandler` triggers `stack.sync_github(expected_head_sha:)` for a stack under a foreign repository.
- `StatusHandler` (same `Handler#stacks`/`repository_name` resolution pattern) can write commit statuses on a foreign repo's tracked commits, which feed directly into Shipit's `ci.require`/deployability checks (`Stack`/`DeploySpec` `required_statuses` logic), potentially manipulating whether a commit under another org's stack is considered deployable.
- `MembershipHandler` can create/manipulate `Team`/`User` membership records tied to organizations it doesn't own.

This crosses a tenant boundary without any GitHub-side authorization for the target repository, enabling state changes (sync triggers, forged CI status, team/membership writes) on a stack the attacker's organization does not own — a cross-organization write achieved purely through payload manipulation, satisfying the "cross-repository writes" / "unauthorized deploy" impact bar when combined with status forging that gates deploy checks.

### Likelihood Explanation
Requires only that the Shipit instance is configured for multiple GitHub organizations (a documented, supported configuration — see `config/secrets.development.shopify.yml`) and that the attacker controls (as an admin of) one of those onboarded organizations along with knowledge of their own org's `webhook_secret` (which any org admin legitimately possesses when installing their own webhook/App). No secret belonging to the victim organization is needed, and no privileged Shipit account, `ApiClient` token, or GitHub write access to the victim repo is required — only the ability to send an HTTP POST with a correctly-signed body using one's own credentials.

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler`), enforce that the organization used to validate the signature is the same organization referenced by every field the handlers subsequently trust (`repository.full_name`'s owner segment, `organization.login`, etc.), rejecting payloads where they diverge. Alternatively, resolve the target `Repository`/`Stack` first, and require that its GitHub organization matches `repository_owner` used for signature verification before dispatching to handlers.

### Proof of Concept
1. Shipit instance configured with two organizations, `OrgA` and `OrgB`, each with their own `webhook_secret` (per `config/secrets.development.shopify.yml` schema).
2. Attacker administrates `OrgA` and knows `OrgA`'s `webhook_secret` (they configured it when setting up OrgA's GitHub App/webhook).
3. Attacker crafts a `push` (or `status`) webhook payload:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen sha>",
     "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
   }
   ```
4. Attacker computes `X-Hub-Signature` using `OrgA`'s known `webhook_secret` and POSTs to `/webhooks`.
5. `verify_signature` calls `Shipit.github(organization: "OrgA")` and validates successfully since the signature was computed with OrgA's real secret.
6. `Shipit::Webhooks::Handlers::PushHandler#stacks` resolves `Repository.from_github_repo_name("OrgB/victim-repo")` — a repository belonging to `OrgB` — and triggers `sync_github`/state changes on it, even though the request was authenticated as belonging to `OrgA`.
