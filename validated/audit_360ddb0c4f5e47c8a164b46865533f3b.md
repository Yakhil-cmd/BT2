### Title
`ReviewStack#env` merges unfiltered, uppercased pull request label names into command env, letting a fork PR overwrite `PATH` on the `dependencies.override` step - ([File: app/models/shipit/review_stack.rb])

### Summary
`ReviewStack#env` merges `pull_request.labels.each_with_object({}) { |n,h| h[n.upcase] = "true" }` into the stack env with no key allowlist, and `LabelCapturingHandler#capture_labels` persists label names verbatim from the webhook payload with no filtering. Because `TaskCommands#env` merges `@stack.env` before building `Command`, and `Command#unbundled_env` merges the caller-supplied `@env` *after* computing its own safe `PATH`, a label literally named `path` (any casing) becomes the key `PATH` in the merged env, overwriting the safe `PATH` value with the fixed string `"true"` for every `dependencies.override` (and other) step run against that review stack.

### Finding Description
Binding that should hold: `Command#unbundled_env['PATH']` should always equal Shipit's own computed value `"#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}"`, never a value influenced by an unprivileged pull request. In the code this is violated:

- `LabelCapturingHandler#capture_labels` writes `pull_request.update!(labels: params.pull_request.labels.map(&:name))` straight from the webhook body with no allowlist. [1](#0-0) 
- `ReviewStack#env` upcases every label name into an env key with the fixed value `"true"`, with no key allowlist/denylist: [2](#0-1) 
- `TaskCommands#env` merges `@stack.env` early in the chain used to build `dependencies.override` commands: [3](#0-2) 
- `Command#unbundled_env` computes a safe `PATH` first, then merges the caller-supplied `@env` last, so any `PATH` key in `@env` wins: [4](#0-3) 
- That merged env reaches `PTY.spawn` directly in `Command#start`: [5](#0-4) 

Exploit flow: An attacker opens a pull request from a fork against a repository configured with `provisioning_behavior=prevent_with_label` (so a `ReviewStack` is created for the fork PR by default), applies a label whose name upcases to `PATH` (the audit's threat model explicitly grants "label their own PR" as an attacker capability), and commits a directory literally named `true/` in the fork containing a malicious executable with the same name as a bare command Shipit resolves via `dependencies.override` (e.g. `npm`, `bundle`, `yarn`, whichever `DeploySpec#dependencies_steps` discovers or the fork's own `shipit.yml` specifies). When Shipit checks out the fork's commit and runs dependency-install commands with `chdir: steps_directory` (the checked-out working directory), the injected `PATH="true"` makes the shell resolve the bare command name only inside the attacker-controlled `true/` subdirectory of the checkout, executing the attacker's binary on the Shipit deploy host instead of the real dependency-manager binary.

Why existing guards fail: `EnvironmentVariables#permit` (an allowlist-based sanitizer) exists in the codebase, but it is not invoked anywhere in the `ReviewStack#env` → `TaskCommands#env` → `Command#start` chain; that sanitizer is only used elsewhere for interpolation of `deploy_variables`/`rollback_variables`, not for the label-derived env. No key filtering (e.g. excluding `PATH`, `LD_PRELOAD`, `BUNDLE_*`) is applied when merging pull request labels into env.

### Impact Explanation
An unprivileged fork contributor can achieve arbitrary command execution on the Shipit deploy host during the dependency-install phase of their own review-stack task, matching the Critical - RCE class ("a command running that should not"). The blast radius is scoped to the review stack of the labeled PR (attacker's own fork-derived stack), but that stack still runs with the Shipit deploy host's full privileges/credentials (e.g. `GITHUB_TOKEN`, git credentials in `Commands#base_env`), so a compromised `dependencies.override` step can pivot to reading secrets available to the process or affecting the shared deploy host if it is not adequately sandboxed per-stack. Repeatable on every dependency-install run of that PR's review stack, and reproducible against any repository configured with review stacks (any provisioning behavior, since `ReviewStack#env` is unconditional).

### Likelihood Explanation
Preconditions: repository must have review stacks enabled (any `provisioning_behavior`, including `prevent_with_label`); attacker needs to be able to open a PR from a fork and apply a label to it (granted as an attacker capability by this audit's rules) and control commit contents of the fork (trivial, since it's their own fork). No Shipit credentials, secrets, or GitHub write access to the base repo beyond opening/labeling a PR are required. Cost is low: one label plus one committed file/directory.

### Recommendation
In `ReviewStack#env` (app/models/shipit/review_stack.rb), allowlist or filter which keys can be derived from pull request labels — e.g. skip/reject reserved names such as `PATH`, `LD_PRELOAD`, `BUNDLE_*`, `GIT_*`, `RUBYOPT`, etc., or prefix label-derived keys (e.g. `LABEL_<NAME>`) so they can never collide with process-critical environment variables. Additionally, harden `Command#unbundled_env` (lib/shipit/command.rb) to always compute `PATH` last (i.e., never let caller-supplied `@env` override `PATH`), or explicitly strip `PATH` from any caller-supplied `env` hash before merging.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_test.rb (or a new deploy_commands test)
test "[prevent_with_label] PATH can be injected via an uppercased pull request label" do
  stack = shipit_stacks(:review_stack)
  stack.repository.update!(provisioning_behavior: :prevent_with_label, provisioning_label_name: "no-review-stack")
  stack.pull_request.update!(labels: ["path"])  # webhook-supplied label name, unfiltered

  env = stack.env
  assert_equal "true", env["PATH"], "expected PATH to be overwritten by the pull request label"

  command = Shipit::Command.new("npm install", env: Shipit::TaskCommands.new(stack.trigger_continuous_delivery).env.merge(env), chdir: Dir.mktmpdir)
  assert_equal "true", command.unbundled_env["PATH"], "expected Command#unbundled_env to inherit the fork-controlled PATH instead of Shipit's safe PATH"
end
```
This demonstrates the two sides of the broken binding: `Command#unbundled_env['PATH']` should equal Shipit's computed safe path (`Shipit.shell_paths.join(':') + ':' + ENV['PATH']`) but instead equals the attacker-supplied literal `"true"`, confirming the fork-controllable `PATH` reaches the spawned process for the `dependencies.override` step.
