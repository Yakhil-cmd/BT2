### Title
Stack-scoped ApiClient token grants read access to any stack's deploy status via CCMenu - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` accessor to bypass the stack-scoping enforced by `Shipit::Api::BaseController`, allowing any `read:stack`-permissioned `ApiClient` token — even one explicitly restricted to a single stack via its `stack_id` — to read the CCMenu XML (build/deploy status, last build label/time, activity, `webUrl`) of every stack in the Shipit instance.

### Finding Description
`Shipit::ApiClient` supports scoping a token to one stack via `belongs_to :stack, optional: true` and the `stack_id` column [1](#0-0) . `Shipit::Api::BaseController` enforces this binding centrally: the `stacks` helper filters to `Stack.where(id: current_api_client.stack_id)` when the token is scoped, and `stack` looks up the requested stack only within that filtered relation: [2](#0-1) 

This is exactly the equality that is supposed to hold: `stack a token authorises == stack a token touches`.

`CCMenuController`, however, redefines `stack` to bypass the `stacks` scoping entirely and resolve the stack straight from the request parameter: [3](#0-2) 

Permission enforcement (`require_permission :read, :stack`) only checks that the token's `permissions` array contains `read:stack` via `ApiClient#check_permissions!`, which has no notion of which stack the token is scoped to: [4](#0-3) 

Consequently, for any `ApiClient` with `read:stack` permission, regardless of its `stack_id`, `GET /api/:stack_id/ccmenu` (or the token-in-querystring variant, since `CCMenuController` also overrides `authenticate_api_client` to accept `params[:token]`) will render CCMenu data for *any* stack identified in the URL, not just the one the token is bound to: [5](#0-4) 

This breaks the same class of binding bug described in the external report (an `else` branch referencing the wrong entity's limit value): here the controller uses the *global* `Stack.from_param!` lookup instead of the *scoped* `stacks.from_param!` lookup that the rest of the API layer relies on for authorization.

### Impact Explanation
This is a High-severity issue: it is "unauthenticated read of stack state" relative to the token's intended scope — an `ApiClient` token intentionally restricted to one stack (e.g., distributed to an external CI dashboard tool via `CCMenuUrlController`, which creates tokens scoped for CCMenu use) can be replayed against `/api/:other_stack_id/ccmenu` to read build status, last build label/time, and `webUrl` for stacks it was never authorized to see. This crosses the exact "stack a token authorises vs. stack it touches" boundary called out as in-scope.

### Likelihood Explanation
Likelihood is high for any deployment using per-stack scoped `ApiClient` tokens (a feature the engine explicitly supports and exposes in the UI): the attacker only needs a single valid `read:stack` token for one stack (already a low-privilege, intentionally narrow-scoped credential) and the numeric/string identifier of another stack, which is guessable/enumerable (stack `to_param` is `owner/name/environment`). No additional session, admin, or GitHub access is required beyond possessing one legitimately-scoped API token.

### Recommendation
Change `CCMenuController#stack` to use the scoped lookup consistent with the rest of the API surface:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
removing the private `Stack.from_param!` bypass, so a stack-scoped token can only ever resolve to the stack it was issued for.

### Proof of Concept
1. Create (or use) an `ApiClient` with `permissions: ['read:stack']` and `stack_id` set to Stack A's id (e.g., via the existing `CCMenuUrlController#client` flow, or directly via `ApiClientsController#create`/`update`).
2. Obtain the client's `authentication_token` (e.g., via `CCMenuUrlController#fetch`, which embeds the token in a `ccmenu_url`).
3. Send `GET /api/<Stack B id-or-param>/ccmenu?token=<token>` where Stack B is a different stack than the one the token is scoped to.
4. Observe that `CCMenuController#show` renders Stack B's CCMenu XML (`name`, `activity`, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`) successfully, even though the token's `stack_id` only authorizes Stack A — confirming the scoping bypass caused by `CCMenuController#stack` resolving via unscoped `Stack.from_param!` instead of the base controller's scoped `stacks.from_param!`.
