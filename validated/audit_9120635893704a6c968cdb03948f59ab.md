### Title
`handleERC721Transfer` Uses `transferFrom` Instead of `safeTransferFrom`, Permanently Locking Bridged ERC721 Tokens While Consuming Bridge Nonce — (`contracts/service_chain/bridge/BridgeTransferERC721.sol`)

---

### Summary

In `BridgeTransferERC721.sol`, the `handleERC721Transfer` function updates critical bridge state (nonce, handled-tx-hash mapping) **before** executing the token transfer, and then calls `IERC721.transferFrom` instead of `safeTransferFrom` in the non-mintBurn path. When the recipient `_to` is a contract that does not implement `IERC721Receiver`, the transfer call succeeds at the EVM level (no revert), the token is moved into an unrecoverable contract, the bridge nonce is permanently consumed, and the request is permanently marked as handled — making the loss irrecoverable.

---

### Finding Description

The vulnerable code path is in the non-mintBurn branch of `handleERC721Transfer`:

```solidity
// BridgeTransferERC721.sol lines 43–70
function handleERC721Transfer(...) public onlyOperators {
    _lowerHandleNonceCheck(_requestedNonce);
    if (!_voteValueTransfer(_requestedNonce)) { return; }

    _setHandledRequestTxHash(_requestTxHash);           // STATE CHANGE 1
    handleNoncesToBlockNums[_requestedNonce] = _requestedBlockNumber; // STATE CHANGE 2
    _updateHandleNonce(_requestedNonce);                // STATE CHANGE 3

    emit HandleValueTransfer(...);

    if (modeMintBurn) {
        require(ERC721MetadataMintable(_tokenAddress).mintWithTokenURI(...), "mint failed");
    } else {
        IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId); // ← no safeTransferFrom
    }
}
``` [1](#0-0) 

Compare this to the ERC20 sibling, which correctly uses `safeTransfer`:

```solidity
// BridgeTransferERC20.sol line 71
IERC20(_tokenAddress).safeTransfer(_to, _value);
``` [2](#0-1) 

The ERC721 path has two compounding defects:

1. **State-before-transfer ordering**: All three state mutations (`_setHandledRequestTxHash`, `handleNoncesToBlockNums`, `_updateHandleNonce`) are committed before the token is delivered. For a non-standard ERC721 that silently returns without reverting on failure, the nonce is consumed and the request is permanently marked handled while the token never leaves the bridge.

2. **Missing `safeTransferFrom`**: ERC721's `safeTransferFrom` calls `onERC721Received` on the recipient if it is a contract, reverting if the hook is absent. Plain `transferFrom` skips this check entirely. When `_to` is a contract without `IERC721Receiver`, the call succeeds, the token is transferred into an unrecoverable contract, and the bridge records the operation as complete.

---

### Impact Explanation

- **Permanent loss of bridged ERC721 assets**: The token is transferred to a contract that cannot handle it and is permanently locked there.
- **Bridge nonce permanently consumed**: `_updateHandleNonce` and `handleNoncesToBlockNums` are already committed, so operators cannot re-submit the handle transaction for the same request nonce.
- **Request permanently marked handled**: `_setHandledRequestTxHash` prevents any future attempt to process the same source-chain request.
- **No recovery path**: The user's ERC721 is gone from the bridge's custody, the bridge records the transfer as successful, and the nonce window advances — leaving the user with no recourse short of governance intervention.

This satisfies the allowed impact gate: **unauthorized burn / permanent loss of bridged assets with nonce consumption**.

---

### Likelihood Explanation

- Any bridge user who specifies a contract address as `_to` (e.g., a multisig, a DAO treasury, a DeFi protocol, or any contract deployed without `IERC721Receiver`) triggers this path.
- No special privilege is required on the user side; the user only needs to initiate a bridge request on the source chain with a contract as the destination.
- The bridge operators faithfully relay the request and call `handleERC721Transfer` — this is the normal, expected operational flow.
- Contract recipients are common in DeFi (e.g., bridging NFTs into a vault or DAO).

---

### Recommendation

Replace `transferFrom` with `safeTransferFrom` in the non-mintBurn branch of `handleERC721Transfer`, mirroring the pattern already used for ERC20:

```solidity
// Before
IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId);

// After
IERC721(_tokenAddress).safeTransferFrom(address(this), _to, _tokenId);
```

Additionally, follow the Checks-Effects-Interactions pattern by moving the state mutations **after** the transfer call, so that any revert rolls back the nonce and handled-hash state:

```solidity
function handleERC721Transfer(...) public onlyOperators {
    _lowerHandleNonceCheck(_requestedNonce);
    if (!_voteValueTransfer(_requestedNonce)) { return; }

    // Perform transfer FIRST
    if (modeMintBurn) {
        require(ERC721MetadataMintable(_tokenAddress).mintWithTokenURI(_to, _tokenId, _tokenURI), "mint failed");
    } else {
        IERC721(_tokenAddress).safeTransferFrom(address(this), _to, _tokenId);
    }

    // Then commit state
    _setHandledRequestTxHash(_requestTxHash);
    handleNoncesToBlockNums[_requestedNonce] = _requestedBlockNumber;
    _updateHandleNonce(_requestedNonce);

    emit HandleValueTransfer(...);
}
```

### Proof of Concept

1. User on the child chain owns ERC721 token ID `42` of a registered token.
2. User calls `requestERC721Transfer` with `_to = address(someVault)` where `someVault` is a contract that does not implement `IERC721Receiver`.
3. Bridge operators observe the `RequestValueTransfer` event and call `handleERC721Transfer` on the parent chain with `_requestedNonce = N`, `_to = someVault`, `_tokenId = 42`.
4. Inside `handleERC721Transfer`:
   - `_setHandledRequestTxHash(txHash)` — request hash permanently recorded as handled. [3](#0-2) 
   - `handleNoncesToBlockNums[N] = blockNumber` — nonce-to-block mapping written.
   - `_updateHandleNonce(N)` — `lowerHandleNonce` / `upperHandleNonce` advanced.
   - `IERC721(_tokenAddress).transferFrom(address(this), someVault, 42)` — succeeds (no revert), token now in `someVault`. [4](#0-3) 
5. Token ID `42` is permanently locked in `someVault` (no `onERC721Received`, no withdrawal function).
6. Nonce `N` is consumed; operators cannot re-submit. User's NFT is irrecoverably lost.
