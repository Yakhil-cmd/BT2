### Title
Rounding of `earned_headers_commission_share` splits creates spendable value not backed by the original commission - (File: `headers_commission.js`)

### Summary
When a stable unit wins the headers commission from a parent unit, the commission (`full_amount`) is split among the recipients defined by that unit's `earned_headers_commission_recipients` message (or its single author, if unset) using `Math.round(full_amount * share / 100.0)` computed independently for each recipient. Since every recipient's cut is rounded to the nearest integer in isolation rather than being derived so that the shares sum exactly to `full_amount`, a poster who controls the recipient list can choose share percentages that each round up, causing the sum of the distributed amounts to exceed the actual commission collected from the payer unit — analogous to the pUSDe/`previewWithdraw()` bug where per-party rounding-up leaks value that isn't backed by the underlying pool.

### Finding Description
`calcHeadersCommissions()` in `headers_commission.js` computes, for each winning child unit, one output row per recipient: [1](#0-0) 

and, in the SQL/DB path, the equivalent per-recipient computation: [2](#0-1) 

Both branches use `Math.round(full_amount * share / 100.0)` (round-half-up) independently for each `(payer_unit, recipient)` pair. There is no adjustment (e.g., giving the last recipient `full_amount - sum(previous rounded amounts)`) to guarantee the rounded shares sum to exactly `full_amount`. The only cross-checks performed (`_.isEqual(arrValuesRAM.sort(), arrValues.sort())`) verify that the RAM and DB computation paths agree with each other, not that the total distributed amount matches `full_amount`. The resulting per-recipient amounts are inserted directly into `headers_commission_contributions`, then summed per address into `headers_commission_outputs`, which become spendable inputs validated in `validation.js` via `paid_witnessing`/`headers_commission.getMaxSpendableMciForLastBallMci` and `mc_outputs.calcEarnings`.

Because `earned_headers_commission_recipients` (and the implicit multi-author 100%-split case) is a message any unit author can freely attach when composing/posting a unit — it is not privileged — an attacker who authors the "winning" child unit (winner selection is deterministic via `getWinnerInfo`'s SHA1-based tie-break, but any unit can be the sole/simple winner among its own single-lineage children) can define many recipient addresses under their control, each with a percentage chosen so that `full_amount * share / 100` rounds up (e.g. a `.5`-and-above fraction). Every recipient rounds up independently, so the sum of rounded outputs can exceed `full_amount` by up to `0.5 * (number_of_recipients - 1)` (bounded by the max allowed recipients), creating new, spendable base-asset (byte) value that was never actually paid in by the parent/payer unit.

### Impact Explanation
Each of these `headers_commission_outputs` becomes a legitimate spendable MC (main-chain) input once validated (`validatePaymentInputsAndOutputs`, `checkInputDoubleSpend` in `validation.js`), and all full nodes independently recompute the exact same over-counted amounts (since the computation is deterministic on-chain data), so this isn't a node-disagreement bug — it is a silent, protocol-wide over-issuance of bytes beyond what the payer's `headers_commission` field actually represents. Repeated across many units/recipients this is a genuine, if per-instance small, supply-inflation vector: value paid out to earned-commission recipients does not net back against what was actually collected from the payer, analogous to the sUSDe leak in the reported bug where a rounded-up transfer amount is paid out of a pool not sized to cover it.

### Likelihood Explanation
Any unprivileged unit poster can attach an `earned_headers_commission_recipients` list to their own units, and headers-commission winners are determined deterministically from the DAG structure, which a poster largely controls for their own lineage (single-author simple case, or by arranging to be the sole eligible child). Triggering the rounding gain requires no special access — only crafting recipient share percentages and repeating the pattern across many won headers commissions to accumulate value over time, which is straightforward to automate.

### Recommendation
Avoid independent per-recipient rounding. Compute recipient amounts using integer (floor) division and assign the remainder deterministically to one recipient (e.g., the last one, or the largest share) so that `sum(recipient_amounts) === full_amount` exactly, mirroring the ERC4626 fix of using a rounding mode that never lets the sum of distributed parts exceed the total pool.

### Proof of Concept
1. A user posts (or arranges to author) a unit whose `earned_headers_commission_recipients` message lists N addresses they control, with percentages chosen so each `full_amount * share_i / 100` has a fractional part ≥ 0.5 (e.g., for `full_amount = 3` and two recipients at 50%/50%, each computes `1.5` → rounds to `2`, giving a total of `4` instead of `3`).
2. Once this unit becomes stable and wins the headers commission from its parent (`calcHeadersCommissions` in `headers_commission.js`), `headers_commission_contributions`/`headers_commission_outputs` are populated with the over-counted per-recipient amounts [3](#0-2) .
3. Each recipient address can later spend its `headers_commission` input via a normal payment (validated in `validation.js`'s MC-input path) [4](#0-3) , realizing more total value than the payer unit's `headers_commission` actually represents.
