## Analog Found

The `atlasSolverCall()` bug class — "check the value used to authenticate, but never check that the same value is what's actually acted on" — has a direct analog in `WebhooksController`. The organization used to select the webhook signing secret is *never* bound to the repository whose data actually gets written.

### Title
Webhook signature verification selects the secret by an unverified `repository.owner.login` field, decoupling the authenticated organization from the repository actually written - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks which GitHub App/organization's `webhook_secret` to verify the HMAC signature against using `repository_owner`, a value read directly out of the still-unverified JSON body [1](#0-0) . `repository_owner` is computed from `params.dig('repository', 'owner', 'login')` [2](#0-1) . Every downstream handler, however, resolves which `Repository`/`Stack`/`Commit` to mutate using a *different* field from the same untrusted body — `repository.full_name` (handlers) or `sha` (status handler) — with no re-check that it matches the organization whose secret validated the request [3](#0-2) [4](#0-3) .

### Finding Description
The engine supports multiple independent GitHub organizations, each configured with its own `webhook_secret` in `secrets.yml` [5](#0-4) . `Shipit.github(organization: repository_owner)` looks up the `GitHubApp` (and thus the secret) for that specific org, then `verify_webhook_signature` HMACs the raw body against it [6](#0-5) .

Because the entire request body is attacker-controlled up to that point, an org owner who legitimately knows *their own* `webhook_secret` (e.g., an org they administer that is also tracked by this same Shipit instance) can craft a payload where:
- `repository.owner.login` = their own org (so `repository_owner` resolves to their own `GitHubApp`, whose secret they know, and the HMAC computed with that secret verifies successfully), while
- `repository.full_name` = a completely different, victim repository/stack tracked under a different organization in the same Shipit instance, and
- for the `status` event, `sha`/`state`/`description`/`target_url`/`context` are set to arbitrary attacker-chosen values, since `StatusHandler#process` writes them straight into `Commit#create_status_from_github!` for any commit matching `sha` across all stacks, with no repository/org scoping at all [4](#0-3) .

This is the same class of bug as `atlasSolverCall()`: the code verifies a caller/credential (the org secret) but never asserts that the *object of the verified credential* is the same object being acted upon. Here: **organization authenticated ≠ repository/commit written**.

### Impact Explanation
Shipit's Continuous Delivery gates deploys on commit status checks (`ci.require`, README §CI) [7](#0-6) . Forging a `success` status for an arbitrary commit sha on a stack belonging to a different, victim organization — using only credentials the attacker legitimately possesses for their own low-trust org — can satisfy CI gating and cause Shipit to proceed with an **unauthorized deploy** of that victim stack. This meets the "unauthorized deploy" Critical-impact bucket.

### Likelihood Explanation
Requires the attacker to be a legitimate administrator of at least one org configured in the same multi-tenant Shipit instance (and thus know that org's own `webhook_secret`, which they set themselves when installing their GitHub App) — an unprivileged-relative-to-other-orgs position, not requiring any Shipit session, API token, or GitHub access to the victim org. The payload shape needed (`repository.owner.login` distinct from `repository.full_name`, or a bare `sha`/`state` status payload) is trivial to construct and send directly to `/webhooks`.

### Recommendation
After verifying the signature, re-derive the organization/repository binding strictly from the same field the secret was selected on, and reject/require that `repository.full_name`'s owner matches `repository_owner` before dispatching to handlers. For `StatusHandler`, scope the `Commit.where(sha:)` lookup by the repository resolved from the verified organization instead of a global, org-unscoped `sha` lookup.

### Proof of Concept
1. Shipit instance configured with two orgs in `secrets.yml`: `attacker-org` (attacker knows its `webhook_secret`) and `victim-org` (tracks stack `victim-org/app`).
2. Attacker crafts a `status` webhook payload:
```json
{
  "sha": "<victim commit sha tracked by victim-org/app>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker_webhook_secret, body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `verify_signature` resolves `repository_owner` → `attacker-org`, fetches `attacker-org`'s `GitHubApp`, and the signature verifies successfully [1](#0-0) .
5. `StatusHandler#process` finds the victim commit by bare `sha` (no org/repo scoping) and creates a fabricated `success` status on it [4](#0-3) .
6. If `victim-org/app`'s `ci.require` includes `ci/required-check`, continuous delivery may now deploy that commit without genuine CI approval.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
