## Title
Webhook signature verified against attacker-controlled `repository.owner.login` while write actions key off a different, unverified `repository.full_name` field - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and thus which `webhook_secret`) to validate the inbound signature against using a value taken directly out of the untrusted JSON body, while the handlers that actually act on the payload (create commits/statuses, sync stacks, archive/unarchive review stacks) resolve the target repository from a completely different field of that same body. The field used to select the verifying secret is never bound to the field used to decide what gets written.

### Finding Description
`WebhooksController#verify_signature` computes: [1](#0-0) 

using `repository_owner`: [2](#0-1) 

`repository_owner` is derived purely from the JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`), and is used only to pick which per-organization `GithubApp`/`webhook_secret` in `Shipit.github(organization: ...)` is used to compute the HMAC comparison.

Meanwhile, every handler that performs a write resolves the *target* repository from a different field of the same JSON body — `repository.full_name` — via `Handler#repository_name`: [3](#0-2) 

For example `PushHandler` uses `stacks` (built from `repository_name`) to call `stack.sync_github`: [4](#0-3) 

`StatusHandler` writes a `Status` for any `Commit` whose sha matches `params.sha`, again without checking that `repository_owner` corresponds to the commit's actual repository: [5](#0-4) 

Nothing enforces `repository.owner.login == repository.full_name.split('/').first`. Shipit is explicitly designed to be multi-tenant, hosting several independent GitHub organizations, each with its own `GithubApp` config and its own (optionally blank) `webhook_secret`: [6](#0-5) 

`GithubApp#verify_webhook_signature` computes the HMAC using the `webhook_secret` belonging to whichever organization was named by `repository_owner`: [7](#0-6) 

The binding that should hold is:
```
organization whose secret authenticated the request == repository that gets written to
```
Instead the engine checks:
```
organization named in payload["repository"]["owner"]["login"]  (authenticates)
      ≠ (unchecked)
repository named in payload["repository"]["full_name"]          (is written)
```

An attacker who controls (or has push access to) any GitHub repository belonging to *any* one of the organizations onboarded onto the same Shipit instance can trigger a real, GitHub-signed delivery (push/status/etc.) for their own repository. Since GitHub signs the raw JSON body with that organization's own `webhook_secret`, the attacker does not need to know the secret at all — GitHub computes and attaches a valid `X-Hub-Signature` for them. The attacker only needs the ability to shape the JSON body that GitHub sends, which for a `status` event is fully controlled by the sender via the Status API/webhook payload fields (`sha`, `state`, `description`, `context`, `target_url`), and for events carrying an explicit `repository` object, the attacker can influence `repository.owner.login` vs. `repository.full_name` if any part of that JSON is derived from data the attacker controls (e.g., commit metadata, branch/ref names, or a compromised/less-trusted org onboarded to the same Shipit instance).

Because `repository_owner` and `repository_name` are read independently from the same untrusted JSON body with no cross-check, whichever organization's App happens to have a usable secret (including an org configured with `webhook_secret: nil`, which per `verify_webhook_signature`'s `return true unless webhook_secret` bypasses verification entirely) can be used to authenticate a payload whose `repository.full_name` names a stack belonging to a *different, more privileged* organization tracked by the same Shipit instance.

### Impact Explanation
This breaks the deployment-trust binding between "the organization that authenticated the webhook" and "the repository that is written," which is the exact analog class flagged in the audit rules. Concretely, using `StatusHandler`, an attacker can inject a forged `success`/`failure` `Status` for an arbitrary commit sha belonging to a stack in a different organization than the one whose credentials verified the signature, by having that other organization's webhook secret be blank/unconfigured (an explicitly supported and documented state in `docs/setup.md`: *"Webhook secret (optional)"*). Forged commit statuses feed into Shipit's deployability/merge-status calculations (`Status`, `Status::Group`, and downstream `MergeRequest` logic), which can influence whether a commit is treated as deployable/mergeable — i.e., this can contribute to an unauthorized deploy decision. Using `PushHandler`, an attacker can force `sync_github` on an unrelated stack, causing Shipit to fetch and process commit state for that stack outside of the legitimate owning organization's authenticated event stream, corrupting the state Shipit uses to decide when it's safe to deploy.

### Likelihood Explanation
Likelihood is elevated by the fact that per-organization `webhook_secret` is explicitly optional in this codebase and documented as such, so any multi-org Shipit deployment that has at least one organization without a webhook secret configured has a permanently open door for the mismatch to be exploited by anyone able to reach `/webhooks` with a crafted body claiming `repository.owner.login` for the unsecured org while `repository.full_name` names a different, secured stack. No privileged Shipit account, `ApiClient` token, or knowledge of any real secret is required — only the ability to name arbitrary values inside the JSON body sent to a public, unauthenticated `/webhooks` endpoint.

### Recommendation
Bind the two identifiers before dispatching to handlers: require that `payload.dig('repository','owner','login')` match the owner segment of `payload.dig('repository','full_name')` (and, for `organization` events, similarly validate `organization.login` against the resolved repository), rejecting the request with `422` on mismatch. Alternatively, have `verify_signature` and the handlers derive the organization/repository from a single, consistently-parsed value, and stop treating a blank `webhook_secret` as an automatic pass-through unless explicitly required by the deployment's threat model.

### Proof of Concept
1. Configure Shipit with two organizations in `config/secrets.yml`: `org-a` (attacker-controlled GitHub org, `webhook_secret` left blank/unset per the documented optional setting) and `org-b` (victim org hosting the tracked stack `org-b/critical-service`).
2. Attacker sends (or, via a real GitHub delivery from their own `org-a` repo, triggers) a `status` webhook to `/webhooks` with:
   - `X-Github-Event: status`
   - Body: `{"sha": "<victim commit sha in org-b/critical-service>", "state": "success", "context": "ci/tests", "repository": {"owner": {"login": "org-a"}, "full_name": "org-b/critical-service"}}`
3. `WebhooksController#verify_signature` calls `Shipit.github(organization: "org-a")`; since `org-a`'s `webhook_secret` is blank, `GithubApp#verify_webhook_signature` returns `true` unconditionally per [8](#0-7) , regardless of what signature (if any) is attached.
4. `StatusHandler#process` looks up `Commit.where(sha: params.sha)` — matching the victim commit in `org-b/critical-service` — and calls `commit.create_status_from_github!(params)`, writing a forged `success` status for that org-b commit, authenticated only under `org-a`'s (missing) credentials.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
