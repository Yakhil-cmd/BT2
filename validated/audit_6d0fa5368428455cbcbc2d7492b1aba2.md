### Title
Webhook signature is verified using an org key selected from an unverified payload field, while a different unverified payload field decides which repository/stack is acted on - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App/webhook secret to check the HMAC against using `repository_owner`, a value read straight out of the still-unauthenticated JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`). Once the HMAC check passes, the event is dispatched to handlers (e.g. `PushHandler`) that resolve the actual `Repository`/`Stack` to act on using a *different* field of the same body, `repository.full_name`, via `Shipit::Repository.from_github_repo_name`. In a Shipit instance configured with multiple GitHub organizations (each with its own `webhook_secret`, as documented in `docs/setup.md`), this is the same trust-binding break as the reported `PermitCollector`/`TwoCryptoZap` bug: the entity whose credential was used to authenticate the message (`repository.owner.login`) is not cryptographically or logically bound to the entity that the message is actually applied to (`repository.full_name`).

### Finding Description
- `verify_signature` in `app/controllers/shipit/webhooks_controller.rb` does:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
`Shipit.github(organization: ...)` looks up per-organization config (`app_id`, `webhook_secret`, etc.), as shown in `docs/setup.md`'s multi-org example. `repository_owner` is derived purely from the JSON body, which is attacker-controlled and not yet verified at the point it is read.
- `GitHubApp#verify_webhook_signature` (`lib/shipit/github_app.rb`) computes an HMAC over `request.raw_post` using the secret for whatever organization `repository_owner` says it is. This only proves the sender knows *that organization's* secret - it says nothing about whether the rest of the payload (in particular `repository.full_name`) is genuinely associated with that organization.
- After verification, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches to handlers such as `Shipit::Webhooks::Handlers::PushHandler`, whose `process` method resolves the target via:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```
(`app/models/shipit/webhooks/handlers/handler.rb`). `Repository.from_github_repo_name` (`app/models/shipit/repository.rb`) simply splits `owner/name` and looks up the DB row - it never checks that this owner matches the `repository_owner`/organization whose secret validated the request.

Because the whole JSON body is attacker-supplied before signing, an attacker who is an admin of one org configured in this multi-tenant Shipit instance (and therefore legitimately knows that org's `webhook_secret`, since they configured/own the GitHub App for their own org) can craft a payload where `repository.owner.login`/`organization.login` = "attacker-org" (used only to select the verification key) while `repository.full_name` = "victim-org/victim-repo" (used to pick the actual `Stack`/`Repository` acted upon). The HMAC is computed correctly by the attacker over their own crafted body, so `verify_signature` passes, yet the handler acts on a completely different, unrelated repository/stack that the attacker does not control.

This is the structural analog of the PoC's flaw: the credential/authentication check is bound to one field (`owner`/`nonce`-equivalent = the org secret), while the value actually operated on (`full_name`/collector-equivalent) is a separate, unchecked field within the same "signed" data.

### Impact Explanation
Depending on which handler is triggered, this crosses a repository trust boundary: e.g. `PushHandler` can invoke `stack.sync_github(expected_head_sha: ...)` for a victim stack that is completely unrelated to the attacker's own organization, and other handlers (`status`, `check_suite`, `pull_request` variants, `membership`) can create/update `Commit`, `Status`, `PullRequest`, `Team`/`User` records or archive/unarchive review stacks for arbitrary repositories/stacks configured in the same Shipit instance, all driven by attacker-controlled body fields. If continuous deployment is enabled on the victim stack, a forged sync can feed into automatic deploy triggering. This reaches the "cross-repository writes / unauthorized deploy" bar only when the deployment is multi-org (multiple `github.<org>.webhook_secret` configured) and the attacker legitimately administers at least one of the configured orgs - which is the documented supported configuration (see `docs/setup.md`'s multi-org example), not a hypothetical.

### Likelihood Explanation
Requires the Shipit instance to be configured for multiple GitHub organizations sharing one webhooks endpoint (a documented, supported configuration) and requires the attacker to be a legitimate admin/owner of at least one of those configured orgs (which is a much weaker requirement than compromising the webhook secret of the *target* org). Given that setup, forging the payload is trivial - it's just crafting arbitrary JSON and signing it with a secret the attacker legitimately possesses.

### Recommendation
After selecting the GitHub App/secret with `repository_owner` and verifying the HMAC, re-validate that every downstream identifier derived from the payload (`repository.full_name`, `organization.login`, etc.) is actually owned by that same `repository_owner`/organization before dispatching to handlers - i.e., assert `repository.full_name.split('/').first == repository_owner` (case-insensitively) in `WebhooksController#verify_signature`, or have `Shipit::Webhooks::Handlers::Handler` take the verified organization as an explicit, separate argument and check it against `repository.full_name` before resolving stacks/repositories.

### Proof of Concept
Given a Shipit instance configured with two organizations, `attacker-org` (secret known to the attacker) and `victim-org` (target, unrelated to the attacker):

```ruby
payload = {
  "ref" => "refs/heads/main",
  "after" => "deadbeef" * 5,
  "repository" => {
    "owner" => { "login" => "attacker-org" },   # used only to pick the verification secret
    "full_name" => "victim-org/victim-repo"      # used to pick the actual Stack/Repository acted on
  }
}.to_json

signature = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", attacker_org_webhook_secret, payload)

post "/github/events", headers: { "X-Github-Event" => "push", "X-Hub-Signature" => signature }, body: payload
# => WebhooksController#verify_signature uses Shipit.github(organization: "attacker-org"),
#    HMAC matches (attacker knows this secret) => request accepted.
# => Shipit::Webhooks::Handlers::PushHandler resolves Repository.from_github_repo_name("victim-org/victim-repo")
#    and calls stack.sync_github(expected_head_sha: "deadbeef"*5) on a stack the attacker does not own/administer.
```
