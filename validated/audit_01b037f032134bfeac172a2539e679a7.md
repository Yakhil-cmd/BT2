### Title
`handleERC20Transfer` Missing `onlyRegisteredToken` Guard Allows Operator to Drain Arbitrary ERC20 Tokens from Bridge — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

---

### Summary

`BridgeTransferERC20.handleERC20Transfer` accepts a caller-supplied `_tokenAddress` without the `onlyRegisteredToken` modifier that guards the symmetric outbound path `_requestERC20Transfer`. With the default operator threshold of 1, a single operator can invoke `handleERC20Transfer` with any token address and a fresh nonce, causing the bridge to transfer or mint tokens it should never touch.

---

### Finding Description

`_requestERC20Transfer` (the outbound/deposit path) carries both `onlyRegisteredToken(_tokenAddress)` and `onlyUnlockedToken(_tokenAddress)`: [1](#0-0) 

`handleERC20Transfer` (the inbound/withdrawal path) carries only `onlyOperators` and performs no token-address validation before executing the transfer: [2](#0-1) 

The `onlyRegisteredToken` modifier is defined in `BridgeTokens` and enforces that `registeredTokens[_token] != address(0)`: [3](#0-2) 

The voting mechanism (`_voteValueTransfer`) uses `keccak256(msg.data)` as the vote key, so each unique `(_tokenAddress, _value, _to, _requestedNonce, …)` tuple is a distinct vote. The default threshold is **1**: [4](#0-3) 

With threshold = 1, a single operator's call immediately satisfies the quorum and executes the transfer: [5](#0-4) 

---

### Impact Explanation

**Lock/unlock mode (`modeMintBurn = false`):**  
`IERC20(_tokenAddress).safeTransfer(_to, _value)` is called. The bridge holds deposited ERC20 tokens from legitimate users. An operator can drain any ERC20 balance held by the bridge — including registered tokens — by supplying a fresh nonce and an arbitrary `_to`. The nonce is then permanently consumed (`closedValueTransferVotes[nonce] = true`), preventing legitimate recovery.

**Mint/burn mode (`modeMintBurn = true`):**  
`ERC20Mintable(_tokenAddress).mint(_to, _value)` is called. If the bridge holds the minter role on any ERC20Mintable contract (which is the normal setup for bridged tokens), an operator can mint an unbounded amount of any such token to any address.

Both paths result in **unauthorized transfer or mint of bridged assets**, matching the allowed impact gate.

---

### Likelihood Explanation

- The default `operatorThresholds[ValueTransfer]` is 1, so no collusion is required.
- The Kaia service-chain bridge is commonly deployed with a single operator account controlled by the service-chain operator.
- The function is `public`, reachable from any EOA that holds the operator role.
- No on-chain guard prevents an operator from supplying an unregistered or locked token address.

---

### Recommendation

Add `onlyRegisteredToken(_tokenAddress)` and `onlyUnlockedToken(_tokenAddress)` to `handleERC20Transfer`, mirroring the guards already present on `_requestERC20Transfer`:

```solidity
function handleERC20Transfer(
    bytes32 _requestTxHash,
    address _from,
    address _to,
    address _tokenAddress,
    uint256 _value,
    uint64 _requestedNonce,
    uint64 _requestedBlockNumber,
    bytes memory _extraData
)
    public
    onlyOperators
    onlyRegisteredToken(_tokenAddress)   // ADD
    onlyUnlockedToken(_tokenAddress)     // ADD
{
    ...
}
```

Apply the same fix to `handleERC721Transfer` in `BridgeTransferERC721.sol` for consistency.

---

### Proof of Concept

Setup: bridge deployed in lock/unlock mode (`modeMintBurn = false`), threshold = 1, operator = `attacker`, bridge holds 1 000 USDT deposited by legitimate users.

```
// attacker is the sole operator (threshold = 1)
bridge.handleERC20Transfer(
    bytes32(0xdeadbeef...),   // fake requestTxHash — not checked
    victim,                   // _from (irrelevant)
    attacker,                 // _to — receives the tokens
    USDT_ADDRESS,             // _tokenAddress — registered, but no lock check
    1_000e6,                  // _value — full bridge balance
    999,                      // _requestedNonce — fresh, above lowerHandleNonce
    block.number,
    ""
);
// Result: bridge.safeTransfer(USDT, attacker, 1_000e6) executes.
// closedValueTransferVotes[999] = true — nonce permanently consumed.
// Legitimate users can no longer withdraw their USDT.
```

The vote passes in a single call because `voteCounts[keccak256(msg.data)] >= operatorThresholds[ValueTransfer]` (1 >= 1). [6](#0-5) [7](#0-6)

    function _voteValueTransfer(uint64 _requestNonce)
        internal
        returns(bool)
    {
        require(!closedValueTransferVotes[_requestNonce], "closed vote");

        bytes32 voteKey = keccak256(msg.data);
        if (_voteCommon(VoteType.ValueTransfer, _requestNonce, voteKey)) {
            closedValueTransferVotes[_requestNonce] = true;
            return true;
        }

        return false;
    }
