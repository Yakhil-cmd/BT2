### Title
AA response with multiple payment messages bounces entirely on a single unprivileged/attacker-injected bad asset, blocking legitimate co-recipients - (File: aa_composer.js)

### Summary
When an Autonomous Agent (AA) response includes several `payment` messages (e.g. a payout that distributes different assets to different parties in one trigger), `sendUnit()` processes all messages with `async.eachSeries` and bounces the **entire** response unit if a single message's asset fails validation. Because asset identifiers used inside an AA template can be sourced from attacker-controlled trigger data or from state accumulated from unprivileged depositors, an attacker can inject one bad asset (e.g. a permissionlessly-issued private asset) into that list and force the whole multi-party payout to revert, denying unrelated legitimate outputs in the same response — the same bug class as the OpenQ report where one malicious ERC20 in a loop reverted the whole claim.

### Finding Description
`sendUnit()` builds the AA response unit from the `messages` array produced by AA template evaluation and iterates over them with `async.eachSeries`: [1](#0-0) 

For every non-base `payment` message it calls `storage.loadAssetWithListOfAttestedAuthors(...)`, and if the asset is a **private asset** it returns an error unconditionally:
```
if (objAsset.is_private) // it'll fail validation anyway due to lack of spend_proofs
    return cb("sending private asset from AA");
``` [2](#0-1) 

Any `cb(err)` from this per-message check aborts `async.eachSeries` for the *entire* messages array, and the final callback bounces the whole response:
```
function (err) {
    if (err)
        return bounce(err);
    ...
}
``` [3](#0-2) 

`bounce()` rolls the AA state and any state-var changes back to the savepoint and discards all messages that were part of this response, not just the offending one: [4](#0-3) 

The same all-or-nothing pattern also exists in the dry-run/estimation path (`sendDummyUnit`), where a single asset with a failing `issued_by_definer_only` check aborts the whole `arrAssetsWithNegativeBalances` loop and bounces: [5](#0-4) 

Asset issuance itself is completely permissionless — any unprivileged unit author can define a new asset, including a private one, via a plain `asset` message (as used throughout the AA sample templates, e.g. `is_private: false/true` fields): [6](#0-5) 

Many real AA templates compose several `payment` messages for different assets/recipients inside a single response (dividends, refunds, exchange payouts), keyed off state vars or `trigger.data` that ordinary users can influence, e.g.: [7](#0-6) [8](#0-7) 

If the asset selected for one of these messages is attacker-supplied (directly from `trigger.data`, or indirectly because the AA records asset identifiers contributed by unprivileged depositors into a state var later used to build payout messages — the same pattern as OpenQ's unwhitelisted token deposit), the attacker only needs to get his private asset into that slot once. From that point, any trigger causing the AA to emit that message together with other legitimate payment messages (e.g. a base-currency payout to a different beneficiary) will bounce as a whole, refunding only the current trigger's bounce fee and reverting every other output/state change bundled in that response.

### Impact Explanation
This lets an unprivileged attacker deny legitimate outputs/state changes to unrelated parties whenever an AA batches several payments (potentially to different beneficiaries or in different assets) inside one response, mirroring the "competitor unable to claim reward" scenario: a legitimate recipient's payment is bundled with an attacker-poisoned asset payment and never gets paid because the whole unit bounces every time it is attempted. Because state changes are also rolled back (`revert`/`bounce`), this can also freeze AA logic that depends on those state updates (e.g., marking a payout as done), effectively locking funds/functionality tied to that code path as long as the attacker-controlled asset stays part of the response.

### Likelihood Explanation
Any user can permissionlessly define a private asset for near-zero cost and does not need any special role. The precondition is an AA design that (a) selects one of the assets to pay from attacker-influenceable input (`trigger.data`, or state populated by unprivileged deposits) and (b) bundles that payment together with other unrelated outputs in the same response — a common and idiomatic AA pattern shown across the codebase's own AA samples that combine multiple `payment` messages per response. Given how frequently AAs combine multi-asset messages in one response, the reachable surface is realistic for any AA author who forwards or distributes attacker/deposit-supplied asset identifiers.

### Recommendation
- In `sendUnit()`, do not let a single failing payment message (e.g. `is_private`, unattested authors, or unknown asset) abort processing of unrelated payment messages in the same response; instead, either validate/reject the individual offending message at template-authoring/evaluation time, or make the AA's `if`/`init` logic explicitly check `is_private`/asset validity before including it in `messages` so the failure is deterministic and attributable to the attacker's own trigger rather than to the whole batch.
- Provide an oscript primitive (e.g. an `is_private`/`is_valid_asset` getter usable in `if:`/`init:`) so AA authors can filter out unpayable/malicious assets before emitting the `payment` message, preventing them from ever reaching `sendUnit`'s bounce-everything path.
- Document this footgun for AA authors: never batch a payout keyed on attacker/depositor-controlled asset identifiers together with unrelated outputs to third parties in the same response.

### Proof of Concept
1. Attacker posts a normal unit defining a private asset `M` via an `asset` message with `is_private: true` (permissionless, standard ocore feature, e.g. as shown in the `option_contract.oscript`/`futures_contract.oscript` `asset` message templates).
2. Target AA is designed to forward/record any asset a user deposits and later batches a payout for that asset alongside an unrelated `base` payment to a different beneficiary in the same response (a pattern directly analogous to `fundraising_proxy.oscript`'s multi-message payout messages).
3. Attacker triggers the AA using asset `M` (or gets `M` recorded into the state var later read back into a payment message).
4. When the AA composes its response, `sendUnit()`'s `async.eachSeries` hits the `objAsset.is_private` check for asset `M` and returns `cb("sending private asset from AA")`, which propagates to `bounce(err)`, reverting the entire response — including the unrelated `base` payment meant for the other beneficiary — every time this trigger path executes.
