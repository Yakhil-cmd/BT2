### Title
Missing sufficiency check after fixed-cap asset issuance in `issueAsset()` can permanently break AA payouts of that asset - (File: aa_composer.js)

### Summary
In `aa_composer.js`, the AA response-composition routine `completePaymentPayload()` calls `issueAsset()` whenever the AA does not hold enough of a non-base asset to satisfy a payment message it is trying to send. `issueAsset()` computes the amount to issue from a fixed, pre-declared parameter (`objAsset.cap`) instead of from the actually required shortfall (`target_amount - total_amount`), and the caller never re-checks sufficiency after the issuance completes. This mirrors the reported bug class: an amount/fee is derived from a static, "gross" parameter rather than the dynamic amount actually needed, and the code proceeds without capping/validating the result against what is truly required.

### Finding Description

When `objAsset.cap` is truthy, `issue_amount` is always set to the *full, fixed cap* — never to `target_amount - total_amount` (the actual amount still missing to complete the payment), analogous to the reported bug where `feesUSD` was computed from the full position size rather than the actual `pnl`. If the cap is smaller than what is actually required to complete the AA's own payment output, `addIssueInput()` still unconditionally proceeds and calls `cb2()` with no error, even though `total_amount` may remain below `target_amount`:
```174:aa_composer.js
function addIssueInput(serial_number){
    var input = { type: "issue", amount: issue_amount, serial_number: serial_number };
    payload.inputs.unshift(input);
    total_amount += issue_amount;
    var change_amount = total_amount - target_amount;
    if (change_amount > 0)
        payload.outputs.push({ address: address, amount: change_amount });
    cb2();
}
``` [2](#0-1) 

The caller treats a successful `cb2()` from `issueAsset` as "done" and immediately proceeds to finalize and sort outputs without re-verifying that enough funds were actually accumulated:
```213:aa_composer.js
issueAsset(function (err) {
    if (err) {
        console.log("issue failed: " + err);
        return cb('not enough funds for ' + target_amount + ' of asset ' + asset);
    }
    sortOutputsAndReturn();

``` [3](#0-2) 

Because a capped asset can only ever be issued once (enforced by the `"already issued"` check, mirroring the "already exercised" one-shot nature of a derivatives position), once the AA has minted its capped supply, if that fixed cap is insufficient to cover a payment that the AA's own message logic later needs to make (e.g., because the AA definition sets a cap independent of dynamic trigger-driven amounts, or the AA needs to pay out more of the asset than the cap allows after some legitimate combination of triggers), the shortfall can never be corrected — there is no mechanism analogous to "cap fees to pnl" here to make the message succeed with the actually available/issuable amount.

### Impact Explanation
When the composed payment message under-funds its output (input total < declared output total), the resulting unit fails balance validation in `validatePaymentInputsAndOutputs()`:
```2666:validation.js
if (total_input !== total_output + objUnit.headers_commission + ...)
    return callback("inputs and outputs do not balance: ...");
``` [4](#0-3) 
which causes the AA response to bounce via `bounce(err)`. If bounce fees can be covered, the incoming trigger funds are refunded to the sender; if they cannot (or the specific payout combination can never be satisfied given the fixed cap), the AA's held asset balance for that shortfall condition becomes permanently un-payable through that code path — an instance of AA fund freezing, since the AA can never re-issue the capped asset to make up the difference.

### Likelihood Explanation
This requires the AA definition to declare a fixed `cap` for an asset it issues (a legitimate, common oscript pattern — see `test/samples/create_an_asset.oscript` and `test/aa_composer.test.js` "issue recently defined asset" test) whose value can end up smaller than what a later, unprivileged trigger-driven payment message needs the AA to hand out in that asset. Since asset issuance is one-shot for capped assets, any AA whose payout arithmetic (dependent on trigger data, similar to option/position payoff calculations) can exceed the originally declared cap will hit this path deterministically once triggered with the right (attacker-controllable) trigger data, matching the report's "medium likelihood, data-dependent" profile.

### Recommendation
After `issueAsset()` completes (specifically after a capped-asset issuance), verify that `total_amount >= target_amount` before calling `sortOutputsAndReturn()`; if not, treat it the same as an issuance failure ("not enough funds for ... of asset ...") rather than silently proceeding to build an unbalanced payment message. Additionally, consider validating at AA-definition time (or documenting clearly) that a fixed `cap` must be sufficient for all amounts the AA's own logic could ever need to pay out in that asset, or allow issuance to be capped to the actual `target_amount - total_amount` need (bounded by `objAsset.cap`) rather than always issuing the full cap in one shot.

### Proof of Concept
Not independently executed; based on static code-path tracing:
1. Define an AA that, in a `case` triggered by `trigger.data`, first creates an asset with a small fixed `cap` (e.g. `cap: 100`), consistent with `create_an_asset.oscript`.
2. In a later `case`, have the AA attempt to pay out this asset in an amount that depends on trigger data or accumulated state such that it can exceed the `cap` (e.g., `outputs: [{address: "{trigger.address}", amount: "{trigger.data.amount}"}]` with no bound relative to `cap`).
3. Trigger the payout with `trigger.data.amount > cap` while the AA's current asset balance is `0` (immediately after asset creation, before any of the capped supply has been distributed elsewhere).
4. `completePaymentPayload()` finds insufficient stable/unstable outputs, calls `issueAsset()`, which issues exactly `cap` (not `trigger.data.amount`) because `objAsset.cap` is truthy; `total_amount` (now `cap`) remains below `target_amount` (`trigger.data.amount`), yet `cb2()` fires with no error and `sortOutputsAndReturn()` runs.
5. The composed unit is unbalanced and fails `validatePaymentInputsAndOutputs`, causing `bounce()`; because the asset is capped and single-issue, any subsequent trigger requesting more than `cap` of this asset from the AA will hit the identical failure forever, and the `cap` amount already issued/held by the AA (or received via other output types) can never be spent on the amounts this response case demands, permanently blocking that response path.
