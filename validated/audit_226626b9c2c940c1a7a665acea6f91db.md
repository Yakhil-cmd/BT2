### Title
Data Race in `RemoveVotesAfter` Corrupts In-Memory Governance Vote Map During Reorg — (`kaiax/gov/headergov/impl/rewind.go`)

---

### Summary

`RemoveVotesAfter` iterates `h.groupedVotes` at the outer `range` loop **without holding `h.mu`**, while `AddVote` (called from both `PostInsertBlock` and the background `migrate()` goroutine) writes to the same map **under `h.mu.Lock()`**. This is a classic Go concurrent map read/write data race: the lock is acquired only *inside* the loop body for deletions, leaving the outer iteration completely unprotected. The result is undefined behavior — map corruption, a panic under `-race`, or a silently lost/surviving governance vote — which causes the wrong `UnitPrice` or `MintingAmount` to be applied to blocks following the reorg.

---

### Finding Description

**`RemoveVotesAfter` — lock acquired too late:**

```go
// rewind.go:18-39
func (h *headerGovModule) RemoveVotesAfter(blockNum uint64) {
    dirty := false
    for epochIdxIter, votes := range h.groupedVotes {  // ← reads map WITHOUT h.mu
        for blockNumIter := range votes {               // ← reads inner map WITHOUT h.mu
            if blockNumIter > blockNum {
                dirty = true
                h.mu.Lock()                             // ← lock acquired AFTER the read
                delete(h.groupedVotes[epochIdxIter], blockNumIter)
                ...
                h.mu.Unlock()
            }
        }
    }
    ...
}
``` [1](#0-0) 

**`AddVote` — correctly holds the lock, but that doesn't protect the concurrent reader:**

```go
// execution.go:73-83
func (h *headerGovModule) AddVote(blockNum uint64, vote headergov.VoteData) {
    h.mu.Lock()
    defer h.mu.Unlock()
    ...
    h.groupedVotes[epochIdx][blockNum] = vote  // ← writes map under h.mu
}
``` [2](#0-1) 

Go's memory model requires **both** the reader and the writer to hold the same lock for a map access to be safe. Here only the writer holds `h.mu`; the reader (`RemoveVotesAfter`) does not. This is a data race by definition.

**Two concurrent callers that make this reachable without operator privilege:**

1. **Background `migrate()` goroutine** — started unconditionally by `Start()`, calls `accumulateVotesInEpoch` → `AddVote` in a loop with only a 50 ms throttle. It runs for the entire historical migration period, which on a long-running chain can last hours. [3](#0-2) 

2. **`RewindDelete`** — called during any chain reorg, which is triggered by receiving a heavier valid chain from a P2P peer (fully permissionless). [4](#0-3) 

The `migrate()` goroutine holds no blockchain-level lock, so it is not serialized with `RewindDelete`. The race window is open for the entire migration period.

---

### Impact Explanation

A corrupted `groupedVotes` map means that after a reorg:

- A governance vote for `UnitPrice` or `MintingAmount` that should have been removed (because the block carrying it was rewound) may survive in memory, causing the wrong fee or minting parameter to be applied to all subsequent blocks.
- Conversely, a valid vote that should remain may be silently deleted, causing the governance change to be missed entirely.
- In the worst case, the Go runtime detects the concurrent map access and panics, crashing the node.

All three outcomes constitute an invalid state transition: honest nodes applying different governance parameters diverge from each other, which is a consensus split.

---

### Likelihood Explanation

- Every node running with a non-trivial chain history starts the `migrate()` goroutine automatically.
- Chain reorgs are a normal part of P2P operation and require no special privilege to trigger — any peer can broadcast a valid competing chain tip.
- The 50 ms throttle in `migrate()` keeps the goroutine alive for hours on long chains, giving a large window for the race.
- The race is reliably reproducible with Go's `-race` detector.

---

### Recommendation

Acquire `h.mu` (as a write lock) for the **entire duration** of `RemoveVotesAfter`, not just the inner delete:

```go
func (h *headerGovModule) RemoveVotesAfter(blockNum uint64) {
    h.mu.Lock()
    defer h.mu.Unlock()

    dirty := false
    for epochIdxIter, votes := range h.groupedVotes {
        for blockNumIter := range votes {
            if blockNumIter > blockNum {
                dirty = true
                delete(h.groupedVotes[epochIdxIter], blockNumIter)
                if len(h.groupedVotes[epochIdxIter]) == 0 {
                    delete(h.groupedVotes, epochIdxIter)
                }
            }
        }
    }

    if dirty {
        WriteVoteDataBlockNums(h.ChainKv, h.VoteBlockNums())
    }
}
```

Apply the same fix to `RemoveGovAfter`, which has the identical pattern. [5](#0-4)

func (h *headerGovModule) migrate() {
	defer h.wg.Done()

	// Scan all epochs in the background including 0th epoch
	pBorder := ReadLowestVoteScannedEpochIdx(h.ChainKv)
	if pBorder == nil {
		logger.Crit("Unexpected nil: lowest vote scanned epoch index")
		return
	}

	border := *pBorder

	for int64(border) > 0 {
		if h.quit.Load() == 1 {
			return
		}

		time.Sleep(migrationThrottlingDelay)

		border -= 1
		h.accumulateVotesInEpoch(border)
	}

	if border == 0 {
		logger.Info("HeaderGovModule migrate complete")
	}
}
