### Title
Uncaught `throw Error("no src_coin")` in payment-input validation can crash a full node processing a crafted unit for a private, fixed-denomination asset - ([File: validation.js])

### Summary
`net/eth.c`'s `eth_get_gso_type` in QEMU crashed the process via an `assert()` reachable with attacker-controlled packet data lacking a valid Layer-3 protocol (CVE-2020-27617). The analogous bug class in ocore is a synchronous `throw Error(...)` used as an *assertion* inside unit-validation logic that is reachable with attacker-controlled joint content, rather than being a true internal invariant. Because ocore's node process installs a global `uncaughtException` handler that deliberately re-throws to crash the process, any such reachable `throw` inside validation is a remote, unauthenticated (any unit poster) denial-of-service.

### Finding Description
`validatePaymentInputsAndOutputs()` in `validation.js` handles the `"transfer"` input case for payment messages. For assets that are private and have fixed denominations, it deliberately skips the normal DB lookup of the source output (because private-chain outputs aren't stored yet at that point in the private-payment flow) and instead expects the caller to have pre-populated `objValidationState.src_coin`: [1](#0-0) 

`objValidationState.src_coin` is populated **only** by `indivisible_asset.js`'s private-chain-specific validator, `validatePrivatePayment()`, when it processes a `"transfer"` input while walking a locally-supplied private payment chain: [2](#0-1) 

That path is invoked from `private_payment.js`'s `validateAndSavePrivatePaymentChain()`, which is only reached through the private-payment/private-chain handling flow (e.g. `network.js`'s `handleOnlinePrivatePayment` / `handleSavedPrivatePayments`), not through ordinary unit broadcast validation (`network.js`'s `handleJoint` → `validation.validate`).

However, `validatePaymentInputsAndOutputs` is also invoked for **every ordinary broadcast unit** during normal `validation.validate()` processing (via `validateMessages`/`validatePayment`), and nothing in that ordinary path (used by all full nodes receiving a joint over the wire) ever sets `objValidationState.src_coin`. If an attacker composes and broadcasts a unit whose payment message references an asset that is `is_private && fixed_denominations` with a `"transfer"`-type input (with the required message shape—hidden/blinded outputs, valid asset field, valid denomination consistent with the asset, etc., to pass the earlier structural checks), then when any full node validates this unit through the ordinary joint-handling pipeline, execution reaches:
```
if (!objValidationState.src_coin)
    throw Error("no src_coin");
```
This is a synchronous `throw` executed deep inside `async`-driven validation callbacks, not wrapped by a `try/catch` at that call site, and not treated as a soft validation error passed through the callback-based error channel (`ifUnitError`/`ifJointError`). It propagates as an uncaught exception.

`network.js` installs a global handler for exactly this situation: [3](#0-2) 
which explicitly re-throws to terminate the process ("crash the process to avoid ending up in an inconsistent state").

### Impact Explanation
Any unprivileged party able to compose and broadcast a single unit (an "unpaired" ordinary wallet, no special privileges beyond posting a valid-looking unit) can crash any full node that receives and validates that unit through the normal joint-handling pipeline. Because the crashing unit will be re-delivered/re-processed on restart or forwarded to other peers, this can be used to repeatedly crash multiple nodes in the network, potentially preventing new units from being confirmed if enough witnessing/relay nodes are taken down repeatedly — a network-wide availability impact, consistent with the "network unable to confirm new units" acceptance criterion.

### Likelihood Explanation
The precondition (existence of an `is_private && fixed_denominations` asset) requires such an asset to already be defined on the DAG, which any user can define via a normal asset-definition message; it is not privileged. Constructing a syntactically valid payment message that reaches the `"transfer"` case for that asset without ever going through the private-chain code path (so `src_coin` is never set) appears achievable by simply broadcasting the unit directly instead of routing it through the private-payment protocol. This requires care to satisfy earlier structural/hash checks in `validatePaymentInputsAndOutputs` and `validateMessages`, but no cryptographic material beyond what an ordinary asset issuer/spender already possesses.

### Recommendation
- Replace `throw Error("no src_coin")` (and the sibling `throw Error(...)` checks at validation.js lines 2419-2423) with a graceful validation failure via the `cb(...)` error channel (`return cb("no src_coin")`, etc.), consistent with how other structural violations in this function are reported.
- More fundamentally, add an explicit guard rejecting ordinary (non-private-chain) validation of payment messages referencing `is_private && fixed_denominations` assets with `"transfer"` inputs when `objValidationState.src_coin` is absent, returning a proper `ifUnitError`/`ifJointError` instead of relying on an internal invariant that is actually attacker-influenced.
- Audit other `throw Error(...)` calls within `validatePaymentInputsAndOutputs`, `validateAuthor`, and related validation functions that are reachable from ordinary joint validation (not merely from trusted internal composer code) and convert genuinely-reachable ones to soft errors.

### Proof of Concept
1. Attacker defines (or reuses) an asset `A` with `is_private: true` and `fixed_denominations: true` (a normal, unprivileged asset-definition operation).
2. Attacker crafts and broadcasts a unit whose payment message references asset `A`, with a hidden/blinded output structure matching what private assets normally look like on-chain, and an input of `type` unset (i.e., `"transfer"`), referencing an arbitrary prior output for that asset — bypassing the private-payment protocol entirely (i.e., not sending it through `handleOnlinePrivatePayment`/`private_payment.js`, just broadcasting the unit directly like any other unit).
3. When a peer full node receives this unit via normal gossip and calls `validation.validate()` (via `network.js`'s `handleJoint`), execution reaches `validatePaymentInputsAndOutputs`'s `"transfer"` case for a `is_private && fixed_denominations` asset.
4. Since this node never ran `indivisible_asset.js`'s private-chain-specific `validatePrivatePayment()` for this unit, `objValidationState.src_coin` is `undefined`, and `throw Error("no src_coin")` fires at validation.js:2416-2417.
5. The exception propagates uncaught, triggering `network.js`'s `process.on('uncaughtException')` handler at validation.js/network.js:4530-4543, which re-throws and crashes the node process.

Note: I was unable to fully verify (due to context/tool limits) that all upstream structural checks in `validateMessages`/`validatePayment` can be satisfied for such a payload without also setting `src_coin`, i.e., I could not trace every earlier guard that constructs/validates the payment message shape before reaching this branch. A Devin session with full repository access should confirm the exact minimal payload needed to reach this code path in a live broadcast (as opposed to the private-chain flow) before treating this as a fully confirmed, exploitable PoC.
