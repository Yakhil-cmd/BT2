Based on my investigation, the strongest admission-boundary analog I found is in `multisig_account.move`'s prologue validation function, which is structurally similar to the reported issue: a threshold/flag-gated comparison whose disabled state allows a mismatch between what was approved and what actually executes.

### Title
Multisig transaction payload mismatch bypasses on-chain payload verification when `abort_if_multisig_payload_mismatch` feature is disabled - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
`validate_multisig_transaction`, invoked by the VM as part of the transaction prologue during both mempool validation and execution, is supposed to guarantee that the payload actually being executed matches the payload the owners voted to approve. This guarantee is enforced by two independent checks, but the second one is gated behind a feature flag and an "is the payload non-empty" condition, similar to how the reported Vault bug gated a safety check behind a configurable `THRESHOLD`. When the flag is off (or when the stored transaction has no `payload_hash`), a non-matching payload can pass prologue admission and be committed under the multisig account's authority.

### Finding Description
`validate_multisig_transaction` performs quorum/timelock checks and then two payload-integrity checks: [1](#0-0) 

1. If `transaction.payload_hash.is_some()`, it asserts `sha3_256(payload) == *payload_hash`.
2. Only if the feature `abort_if_multisig_payload_mismatch_enabled()` is turned on, **and** `transaction.payload.is_some()`, **and** the caller-supplied `payload` is *not empty*, it asserts `payload == *stored_payload`.

If a multisig transaction was created via the path that stores the full payload on-chain but not a hash (`payload_hash` is `None`), and the `abort_if_multisig_payload_mismatch` feature is not enabled, then neither check fires for a non-empty, non-matching `payload` argument: check 1 is skipped because there's no hash to compare against, and check 2 is entirely gated by the feature flag. This is functionally the same "safety check that can be silently disabled/weakened" pattern as the reported Vault bug, where a single configuration knob (`THRESHOLD` there, a feature flag here) controls whether admission logic actually enforces the invariant it claims to enforce.

The comment in the spec file corroborates that this is a known, only-partially-verified admission gate: [2](#0-1) 

### Impact Explanation
If exploitable, this allows an owner who holds sufficient approvals for one transaction (payload A, approved by co-owners) to submit a different payload B at execution time. Because `validate_multisig_transaction` is the VM prologue gate that decides whether the transaction is admissible, this is a pre-validation mismatch that lets a transaction that should fail admission (wrong payload vs. the one approved) execute and commit under the multisig account's signer authority — i.e., unauthorized execution under the wrong approval set, matching the "Authenticator/approval validation accepting the wrong approval set" and "Pre-validation mismatch causing execution/commit" impact categories.

### Likelihood Explanation
This depends entirely on two runtime conditions I could not fully verify with the tools available:
1. The default/current on-chain state of the `abort_if_multisig_payload_mismatch` feature flag (I found its definition in `features.move`/`aptos_features.rs` but could not confirm whether it is enabled by default on mainnet or still gated behind governance).
2. Whether the `create_transaction` (non-hash) entry function that stores `payload` without a `payload_hash` is still reachable in the current codebase — I was unable to locate its definition text within the indexed portion of `multisig_account.move` in the final iteration (searches for `create_transaction`/`create_transaction_with_hash` bodies did not return within budget), so I cannot confirm the exact conditions under which `payload_hash` stays `None`.

Because of this, I cannot fully prove that this local candidate independently holds against the "unprivileged root cause, exact corrupted binding" bar required — the vulnerability's practical impact hinges on an on-chain feature-flag default I could not confirm from the code I was able to retrieve.

### Recommendation
- Make the payload-match check (`payload == *stored_payload`) unconditional whenever `transaction.payload.is_some()` and a non-empty `payload` is supplied, rather than gating it behind `abort_if_multisig_payload_mismatch_enabled()`.
- Consider always requiring a `payload_hash` to be stored (deprecating the no-hash `create_transaction` path) so payload verification is never solely dependent on the state of a governance feature flag.

### Proof of Concept
Could not be constructed with full confidence given the above unknowns. The conceptual PoC would be:
1. Confirm `abort_if_multisig_payload_mismatch` is disabled on the target network.
2. Owner A creates a multisig transaction via the path that stores `payload` but no `payload_hash` (payload A).
3. Owners vote/approve to reach quorum for payload A.
4. Owner A submits the actual `SignedTransaction` whose entry-function payload is B (different from A) referencing the same multisig `sequence_number`.
5. `validate_multisig_transaction` is called in the prologue with the caller-supplied `payload` = B; since `payload_hash` is `None` and the feature flag is off, both checks are skipped, and payload B executes with the authority intended only for payload A.

**Given the unresolved dependency on the feature-flag default and the exact `create_transaction` implementation, this should be treated as an unconfirmed candidate rather than a proven vulnerability.** I recommend starting a Devin session with repository access to read the full `create_transaction`/`create_transaction_with_hash` bodies and the on-chain default value of `abort_if_multisig_payload_mismatch_enabled` (in `aptos_features.rs`/genesis feature-flag initialization) to conclusively confirm or refute this finding before treating it as a report-worthy result.

    /// `validate_multisig_transaction` is called by the VM as part of the transaction prologue.
    /// The timelock change added `ETIMELOCK_NOT_EXPIRED` as a new abort path, separate from the
    /// existing `ENOT_ENOUGH_APPROVALS` quorum failure. This spec documents the verifiable
    /// abort vectors; the quorum, timelock, and payload-match aborts depend on transaction-
    /// level state (and, for timelock, an inline helper plus the optional
    /// `MultisigAccountTimeLock` resource) and are left to `pragma aborts_if_is_partial`.
    spec validate_multisig_transaction(owner: &signer, multisig_account: address, payload: vector<u8>) {
        use std::signer;
        pragma aborts_if_is_partial;
        let multisig_account_resource = global<MultisigAccount>(multisig_account);
        let sequence_number = multisig_account_resource.last_executed_sequence_number + 1;
        let owner_addr = signer::address_of(owner);

        // The multisig account must exist (assert_multisig_account_exists).
        aborts_if !exists<MultisigAccount>(multisig_account);
        // The signer must be an owner of the multisig account (assert_is_owner).
        aborts_if !vector::spec_contains(multisig_account_resource.owners, owner_addr);
        // Sequence-number arithmetic must not overflow.
        aborts_if multisig_account_resource.last_executed_sequence_number + 1 > MAX_U64;
        // The pending transaction must exist at the next sequence number
        // (assert_transaction_exists).
        aborts_if !table::spec_contains(multisig_account_resource.transactions, sequence_number);
    }
