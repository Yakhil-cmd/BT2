### Title
Webhook signature verification keys off `repository.owner.login` while all event handlers act on the unverified `repository.full_name` field, letting one organization's webhook secret forge events for another organization's repositories - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In a multi-organization Shipit deployment (`github: { org1: {...webhook_secret...}, org2: {...webhook_secret...} }`), the webhook signature check selects *which organization's secret to verify with* using an attacker-controlled JSON field, while every downstream handler resolves *which repository/stack to mutate* using a different attacker-controlled field from the same unverified body. The HMAC signature never binds these two fields together, so a payload signed with Org A's webhook secret can freely claim to be about Org B's repository.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/secret to validate against like this: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight from the JSON body (`params.dig('repository', 'owner', 'login')`) *before* the signature is verified, and is only used to select which org's `webhook_secret` to HMAC-check against via `Shipit.github(organization: repository_owner)` and `GitHubApp#verify_webhook_signature`: [3](#0-2) [4](#0-3) 

Once the signature is accepted, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` runs handlers over the *same raw body*, but every handler resolves its target repository/stack from a **different** field, `repository.full_name`, via `Handler#repository_name` / `Handler#stacks`: [5](#0-4) 

Nothing ties `repository.owner.login` (used to pick the verifying secret) to `repository.full_name` (used to pick the acted-upon repository/stack). Both are attacker-supplied fields inside the same JSON body covered by one HMAC signature, but the signature only proves "this body was signed by the org whose secret matched `repository.owner.login`" — it does not prove that `repository.full_name` actually belongs to that org.

Concretely, `PushHandler` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`), `CheckSuiteHandler` (`app/models/shipit/webhooks/handlers/check_suite_handler.rb:13-17`), `StatusHandler`, and the `PullRequest::*Handler` classes (e.g. `ClosedHandler`, which calls `review_stack.archive!` based solely on `params.repository.full_name`) all trust `repository.full_name` to look up `Repository`/`Stack` records, independent of which org's secret validated the request: [6](#0-5) 

This is exactly the class of bug in the report: a field acted upon (`repository.full_name`, which drives stack/state mutation) is never actually covered by the trust decision that the signature was meant to certify (that the payload legitimately originates from the organization owning that repository) — the signature only certifies the unrelated `repository.owner.login`/`organization.login` field used to pick the verification key.

### Impact Explanation
In any Shipit deployment configured with multiple GitHub organizations (the documented `github: { org1: {...}, org2: {...} }` schema), an attacker who legitimately controls one configured organization's GitHub App/webhook secret (e.g., an org admin of a small, low-trust org onboarded to the same Shipit instance) can forge a webhook payload where `repository.owner.login`/`organization.login` = their own org (so the signature check passes with their own secret) but `repository.full_name` = a victim org's repository configured in the same Shipit instance. This lets them trigger `sync_github`, force check-run refreshes, inject fabricated commit statuses, and archive/mutate review stacks (`PullRequest::ClosedHandler#process` → `review_stack.archive!`) for repositories/stacks they do not own or have access to — a cross-tenant, cross-repository state-mutation primitive that can corrupt CI status gating used to authorize deploys (`ci.require`), directly undermining the deploy-authorization chain. This satisfies the "cross-repository writes" Critical impact bucket.

### Likelihood Explanation
Requires a Shipit instance configured with the multi-organization `github:` secrets schema (documented and supported, see `Shipit.github_app_config`/`Shipit.github_organizations` in `lib/shipit.rb:190-200`) and requires the attacker to possess a valid webhook secret for *any one* of the configured organizations — which is a normal, low-privilege credential for an org admin, not a Shipit account, `ApiClient` token, or GitHub App private key. No Shipit session or repository write access is needed; only knowledge of one tenant's webhook secret, which is a data-in-transit configuration secret rather than a "privileged account" as excluded by the rules.

### Recommendation
Bind the field used to select/verify the signing secret to the field used for repository resolution: after verifying the signature, re-derive `repository_owner` from `repository.full_name`'s owner segment (or vice versa) and reject the webhook (422) if they disagree; or, in multi-org mode, verify the payload's signature against *every* configured org's secret whose name matches `repository.full_name`'s owner rather than trusting `repository.owner.login` in isolation.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `github: { orga: {webhook_secret: "SECRET_A", ...}, orgb: {webhook_secret: "SECRET_B", ...} }`, each with a stack registered (`orga/repo1`, `orgb/repo2`).
2. As an attacker who only knows `SECRET_A` (e.g., an admin of `orga`'s GitHub App), craft a `push` event body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "orga" }, "full_name": "orgb/repo2" }
}
```
3. Sign the raw body with `SECRET_A` (`sha1=<hmac>`) and POST it to `/webhooks` with `X-Github-Event: push` and `X-Hub-Signature`.
4. `WebhooksController#verify_signature` computes `repository_owner = "orga"`, fetches `Shipit.github(organization: "orga")`, and verifies successfully against `SECRET_A` — passing.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("orgb/repo2")`, matching `orgb`'s stack, and calls `stack.sync_github(expected_head_sha: <attacker-chosen-sha>)`, mutating state for a repository the attacker never had a valid secret for.

```ruby
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([

      ].join(' '))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
