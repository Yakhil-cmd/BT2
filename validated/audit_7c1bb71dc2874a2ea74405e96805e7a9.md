### Title
Cross-organization webhook forgery via signature verification keyed on unverified `repository.owner.login` - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
Shipit officially supports hosting multiple GitHub Apps, one per organization, each with its own independent `webhook_secret`, as documented in `docs/setup.md` and exercised by `test/dummy/config/secrets_double_github_app.yml` [6](#0-5) [7](#0-6) . `WebhooksController#verify_signature` selects *which* app/secret to validate the HMAC signature against by reading `repository.owner.login` straight out of the still-unverified JSON body [2](#0-1) . `Shipit.github_app_config` maps that organization key to a specific `GitHubApp` config, and `GitHubApp#verify_webhook_signature` returns `true` unconditionally when that organization's `webhook_secret` is blank/unset — which the shipped example configs explicitly show as a supported state (`webhook_secret: # nil`) [8](#0-7) [9](#0-8) . The downstream handler that actually acts on the payload (`Handler#stacks`/`repository_name`, used by `PushHandler`) resolves the target repository from a *different* field, `repository.full_name`, which is not tied to the organization used for signature verification [1](#0-0) .

### Finding Description
The equality that should hold is:
`Organization whose secret authenticated the HTTP request == Organization that owns the repository being mutated.`

Before the pull request/attack, only genuine GitHub webhooks signed with an org's real `webhook_secret` (or an org with a properly random/secret configured) can trigger sync/push processing for that org's repositories.

The attack sequence:
1. Deployment is configured (as documented) with multiple GitHub orgs, e.g. `OrgOne` (has a strong `webhook_secret`) and `OrgTwo` (no `webhook_secret` set, a supported and shipped configuration pattern in `secrets.development.example.yml`/`secrets_double_github_app.yml`) [10](#0-9) .
2. An unauthenticated attacker POSTs to `/webhooks` with `X-Github-Event: push`, a body whose `repository.owner.login` is `"OrgTwo"` (to select the org with no secret) but whose `repository.full_name` is `"OrgOne/some-repo"` (the real, targeted repository under the org that actually has a secret).
3. `verify_signature` computes `repository_owner` from this unverified body ("OrgTwo"), fetches `Shipit.github(organization: "OrgTwo")`, and calls `verify_webhook_signature`, which returns `true` immediately because `OrgTwo`'s `webhook_secret` is blank — no HMAC check is performed at all [8](#0-7) .
4. Execution proceeds to `WebhooksController#create`, which dispatches the full, attacker-controlled `params` (including the forged `repository.full_name`) to `PushHandler` [11](#0-10) .
5. `PushHandler#stacks` looks up stacks by `repository.full_name = "OrgOne/some-repo"` and calls `stack.sync_github(expected_head_sha: ...)`, enqueueing `GithubSyncJob` against the real `OrgOne` stack [4](#0-3) .
6. `GithubSyncJob` then fetches commits via `stack.github_api` (using `OrgOne`'s legitimate installation token, since `github_app` is resolved from the stack's actual `repository.owner`, not from the forged webhook), and writes/creates commits, potentially advancing state that downstream continuous-deployment logic acts on [5](#0-4) [12](#0-11) .

The root cause is that the signature check authenticates the request against an organization identity chosen from an unauthenticated field of the same payload, while the code that mutates state uses a different, also-unauthenticated field to pick the target repository. Nothing binds "the org whose secret validated this request" to "the org whose repository is being modified." This mirrors the reported bug class: a payload field acted on (`repository.full_name`) that is never actually covered/bound by the verification step (which instead trusts `repository.owner.login`).

### Impact Explanation
This allows spoofed push (and other) webhooks to be delivered for any stack belonging to any organization, as long as the deployment has at least one configured GitHub org with no `webhook_secret` set — a state the project's own example/dummy configs present as normal and supported. This triggers unauthorized `GithubSyncJob` runs, commit ingestion, and — combined with `continuous_deployment`/merge-queue features — can lead to unauthorized deploy pipeline activity being kicked off for a repository the attacker does not control, satisfying the "unauthorized deploy" / cross-repository-write-adjacent High/Critical impact bar.

### Likelihood Explanation
The webhook endpoint is unauthenticated by design (it's meant to be hit by GitHub) and reachable by anyone who can guess/know the Shipit host. The only precondition is a realistic, explicitly documented multi-org configuration where at least one org has no webhook secret configured — a scenario the codebase ships example configuration for. No credentials, session, or API token are required from the attacker.

### Recommendation
Do not select the verification secret from an unauthenticated field of the same request that is later trusted to identify the mutation target. Concretely:
- Require `webhook_secret` to be present for every configured organization (fail closed instead of `return true unless webhook_secret` in `GitHubApp#verify_webhook_signature`).
- After verifying the signature, re-derive/cross-check that the `repository.full_name`'s owner matches the `organization` whose secret validated the request, rejecting mismatches.

### Proof of Concept
1. Configure Shipit with two orgs per `docs/setup.md`'s multi-app scheme: `OrgOne` (real `webhook_secret`) and `OrgTwo` (`webhook_secret` left blank).
2. `POST /webhooks` with header `X-Github-Event: push` and no/garbage `X-Hub-Signature`, body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "OrgTwo" }, "full_name": "OrgOne/some-repo" }
}
```
3. `verify_signature` resolves `Shipit.github(organization: "OrgTwo")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` without checking any signature.
4. `PushHandler` processes the payload against `OrgOne/some-repo`'s stack, enqueueing `GithubSyncJob` and syncing commits for a repository the attacker never authenticated against.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
