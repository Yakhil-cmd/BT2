### Title
Attacker-triggerable AA response self-validation failure causes unconditional `throw Error` and full node crash - ([File: aa_composer.js])

### Summary
`handleTrigger()`'s internal `validateAndSaveUnit()` self-validates every unit an AA autonomously generates in response to a trigger. Several outcomes of that self-validation — outcomes that are reachable through ordinary AA/trigger-composition edge cases, not just internal bugs — are treated as "impossible" and immediately `throw Error(...)` instead of being handled gracefully. Because this code runs inside nested async DB callbacks with no enclosing `try/catch`, the thrown error propagates as an uncaught exception, which is caught only by the global `process.on('uncaughtException')` handler in `network.js`, and that handler *deliberately rethrows* to kill the whole process. This mirrors the free5GC pattern: a delivery/validation failure that is reachable by an unprivileged sender (an AA trigger author) is converted into a hard `os.Exit`-equivalent crash instead of a recoverable bounce.

### Finding Description
`validateAndSaveUnit()` re-validates the AA-generated response unit using the normal `validation.validate()` pipeline and treats most non-`ifUnitError` outcomes as fatal: [1](#0-0) 

In particular:
- `ifOk` throws `"nonserial AA"` whenever `objAAValidationState.sequence !== 'good'`.
- `ifJointError`, `ifTransientError`, `ifNeedHashTree`, `ifNeedParentUnits`, and `ifOkUnsigned` all throw unconditionally.

The `sequence !== 'good'` branch is the most concerning: it is reached whenever the freshly composed AA response unit is found to conflict (double-spend) with another unit already known to the node at self-validation time. This is not a purely theoretical/internal-bug case — AA response units spend the AA's own balance/outputs, and secondary/chained triggers (`handleSecondaryTriggers`) can cause multiple response units referencing overlapping spendable outputs to be composed and self-validated in the same trigger-processing session: [2](#0-1) 

If the sequence check for the composed response unit resolves to anything other than `'good'` (e.g., due to a race with another unstable unit touching the same AA outputs, which an attacker can influence by carefully timing/crafting concurrent triggers/payments to the same AA), the code path unconditionally throws instead of bouncing the trigger.

This throw is not guarded by any local `try/catch` in the caller chain (`handleTrigger` → `handlePrimaryAATrigger` → `db.takeConnectionFromPool` callback chain), so it becomes an uncaught exception. The process-wide safety net for uncaught exceptions is: [3](#0-2) 

which explicitly re-throws to terminate the Node.js process ("crash the process to avoid ending up in an inconsistent state"). This is functionally identical to free5GC's `logger.PFDManageLog.Fatal(err)` (`os.Exit(1)`-equivalent): a condition reachable from attacker-controlled/attacker-influenced input (AA trigger composition) is converted into a full-node kill switch rather than a bounce/error response.

### Impact Explanation
Any full node that executes the same AA trigger (all full nodes must, since AA execution is deterministic and consensus-critical) will independently hit the same throw and crash simultaneously when the triggering unit becomes stable. This is a network-wide, self-inflicted DoS: a single crafted trigger/payment sequence directed at a vulnerable AA can take down every full node that processes it, halting confirmation of new units network-wide until operators manually restart and patch/avoid the trigger — squarely matching the accepted impact category "a network unable to confirm new units."

### Likelihood Explanation
Any unprivileged AA trigger sender can post payments/triggers to any public AA. Constructing overlapping/concurrent triggers or trigger chains that make an AA's own composed response unit collide with another live unit spending the same AA-owned output is achievable by careful trigger timing (e.g., firing multiple triggers into the same AA in quick succession so that secondary/chained response units reference overlapping unstable outputs). This requires some engineering effort but no special privileges, no auth bypass, and no cooperation from node operators — only knowledge of AA balance/output composition and predictable trigger ordering, which is public information for any AA.

### Recommendation
- Replace the unconditional `throw Error(...)` branches in `validateAndSaveUnit()` (`aa_composer.js` lines ~1804-1824) with a graceful bounce of the AA response (treat non-`'good'` sequence and other unexpected validation outcomes as a recoverable error that causes `bounce(...)`/`revert(...)` of the AA trigger, exactly as `ifUnitError` already does), rather than crashing the process.
- Add regression tests that intentionally create colliding/racing AA response units (e.g., via chained secondary triggers touching the same AA balance) to confirm the AA bounces cleanly instead of crashing the node.
- Audit other `throw Error(...)` sites inside `aa_composer.js`'s trigger execution path that are reachable via externally influenced trigger data/timing and convert genuinely-reachable ones into bounce paths, reserving `throw` only for states that are truly unreachable regardless of attacker input (e.g., internal cache corruption unrelated to trigger content).

### Proof of Concept
Conceptual PoC (concrete unit crafting requires live-network AA state and cannot be fully scripted without direct code/test-harness access, which was not available in this review):
1. Deploy/target a public AA that sends its own balance as an output in its response messages (a common AA pattern).
2. As an unprivileged AA trigger sender, submit two (or a primary plus chained secondary) triggers to the same AA in rapid succession, timed so that the AA composes two response units that both reference/spend the same not-yet-stabilized AA output.
3. When both response units reach `validateAndSaveUnit()`'s self-validation during trigger execution, one of them resolves with `objAAValidationState.sequence !== 'good'` (a double-spend/non-serial state), hitting `throw Error("nonserial AA")` at `aa_composer.js:1824`.
4. The uncaught exception propagates to `process.on('uncaughtException')` in `network.js:4530-4543`, which rethrows and terminates the full node process.
5. Because AA execution must be deterministic across all full nodes, every full node processing the same stabilizing unit crashes identically, taking down the network's ability to confirm further units until operators intervene.

				throw Error("AA validation returned ok unsigned");
