### Title
Inconsistent verification of `is_valid_signed_package` signatures — non-network-aware signed packages are re-validated against the *current* on-chain state instead of a fixed signing-time snapshot - (File: signed_message.js, definition.js)

### Summary
Off-chain signed packages (used by AAs such as payment channels and order-book contracts to accept a counterparty's off-chain commitment) are verified through `Definition.validateAuthentifiers`, which supports far more than a plain ECDSA `sig` check — it also supports state-dependent ops (`address`, `seen address`, `seen definition change`, `in data feed`, `formula`, etc.) that read live chain state at `objValidationState.last_ball_mci`. For "non-network-aware" signed packages (no `last_ball_unit` field), this `last_ball_mci` is derived from the *current* mci of whichever AA execution happens to call `is_valid_signed_package`, not from a fixed point tied to when the message was actually signed. As a result, the exact same signed package/signature can be judged valid at one point in time and invalid (or vice versa) at another, exactly analogous to the Across `SignatureChecker`/EIP-1271 issue where a signature valid at one verification point becomes invalid at another because the underlying validation logic depends on mutable state rather than a pure, static signature check.

### Finding Description
`signed_message.validateSignedMessage()` resolves the address definition to use for verification in `validateOrReadDefinition()`: [1](#0-0) 

For the non-network-aware branch (no `last_ball_unit` in the package), the definition is taken directly from the embedded `objAuthor.definition` (hash-locked to the address), but the `last_ball_mci` handed to `Definition.validateAuthentifiers` is simply the caller's current `mci`:
```
cb(objAuthor.definition, (mci >= constants.pemCurvesFixMci) ? mci : -1, 0);
``` [2](#0-1) 

That `mci` originates from wherever `validateSignedMessage`/`is_valid_signed_package` is invoked. Inside an AA formula, it is simply the AA's own current evaluation mci, not any mci tied to the moment the counterparty actually created/signed the package: [3](#0-2) 

`objValidationState.last_ball_mci` is then used by several definition ops to look up *live, mutable* chain state:
- `address` — recursively resolves another address's **current** definition at `last_ball_mci`: [4](#0-3) 
- `seen address` / `seen definition change` — check whether an address had activity/definition changes by `last_ball_mci`: [5](#0-4) 

Because none of these lookups are pinned to the state that existed when the signature was actually produced (there is no `last_ball_unit` snapshot for the non-network-aware path), the *same* signed package, with the *same* static signature bytes, can pass verification when checked once (e.g. by the receiving counterparty locally, at an earlier mci) and fail — or newly pass — when later checked on-chain by the AA at a different mci. This mirrors the Across bug precisely: the "origin-chain" check (the counterparty's own, earlier verification) and the "destination-chain" check (the AA's on-chain verification via `is_valid_signed_package`) can diverge because the validation mechanism is not a pure static-key check but depends on external, mutable state (nested address definitions, `seen address` activity, data feeds, etc.).

`Definition.validateAuthentifiers` and `validateAuthorSignaturesWithoutReferences` document this exact class of problem in-code: [6](#0-5) 
The comment `// inconsistent for multisig addresses` on `validateSignedMessageSync` is a direct acknowledgment that the same signed-message verification can produce inconsistent results depending on context/timing for definitions more complex than a single static signature.

Real usage of `is_valid_signed_package` for fund-moving decisions can be found in the bundled payment-channel and order-book AA samples, where a counterparty's off-chain signed state update is trusted to move real balances: [7](#0-6) [8](#0-7) 

### Impact Explanation
If a depositor/peer's address is defined using anything beyond a bare `sig` (e.g. `["address", other_address]`, or a definition incorporating `seen address`/`in data feed`), a signed package that is accepted as valid by one party (at signing/exchange time, or in a light-wallet local check) can later be rejected by the AA when submitted on-chain (or, in the opposite direction, a package that should no longer be honored — e.g. after cosigner rotation — could still be accepted if the AA's mci lags behind the moment the definition changed). In payment-channel-style AAs (as in the bundled sample), this directly translates into:
- Loss of funds for the honest party, if a legitimately signed fraud-proof/close message is rejected by the AA due to a definition/state change between signing and submission, or
- Unauthorized/incorrect fund movement, if a stale or no-longer-authorized signature (backed by a since-changed nested definition) is still accepted by the AA because the referenced address's definition change hasn't yet reached the `last_ball_mci` the AA happens to use.

This is a concrete AA fund-loss / unauthorized-spending vector reachable purely by posting ordinary units (address_definition_change) and AA triggers containing an `is_valid_signed_package` check — no special privileges required.

### Likelihood Explanation
Any AA author who uses `is_valid_signed_package` to gate a payment based on a counterparty-signed package (a common and documented oscript pattern, as shown in the bundled `payment_channels.oscript` and `order_book_exchange.oscript` samples) is exposed if the signing address's definition is anything other than a single static `sig`. Multisig/nested/"address"-referencing definitions are a normal, supported feature (not exotic), and address_definition_change is a standard, unprivileged operation any address owner can post. The race between "message signed under definition D1" and "AA evaluates trigger after address owner posts a definition change to D2" is realistically triggerable by either counterparty in a payment channel, especially since channel/exchange protocols rely on messages being exchanged and settled with some delay.

### Recommendation
- Require signed packages used with `is_valid_signed_package` to always be network-aware (i.e. mandate `last_ball_unit`) so that `last_ball_mci`, and therefore all definition/state lookups (`address`, `seen address`, `seen definition change`, `in data feed`, etc.), are pinned to a stable point-in-time snapshot chosen at signing time rather than to the AA's current evaluation mci.
- Alternatively, restrict the address definitions eligible for `is_valid_signed_package` verification to those that resolve to a fixed set of static signature checks (`sig`/`hash` only, no `address`, `seen *`, `in data feed`, `formula` referencing mutable state), eliminating the possibility that verification results can change between two invocations.
- Document explicitly (as the existing `// inconsistent for multisig addresses` comment hints) that AA authors relying on `is_valid_signed_package` for fund-moving decisions must not use non-network-aware packages together with definitions containing time/state-dependent ops.

### Proof of Concept
1. Address `X` is defined as `["address", "Y"]`, where `Y` is itself a `sig` address (e.g. a single-signature "delegate" key) — this mirrors an EIP-1271-style indirection.
2. Owner of `X`/`Y` signs an off-chain package (no `last_ball_unit`, i.e. non-network-aware) committing to a channel/order state, using `Y`'s current key, and sends it to a payment-channel AA counterparty who locally verifies it is valid via `is_valid_signed_package` at their current, earlier mci — the check passes because `Y`'s definition is the one active at that time.
3. Before the counterparty submits the fraud-proof/settlement trigger to the AA, the owner of `Y` posts an ordinary `address_definition_change` unit rotating `Y`'s key (an ordinary, unprivileged operation), which becomes stable at a later `mci`.
4. When the counterparty finally submits the trigger, the AA calls `is_valid_signed_package(trigger.data.sentByPeer, X)`, which resolves through `signed_message.validateSignedMessage(..., evaluated_address, mci, ...)` using the AA's current mci, causing `Definition.validateAuthentifiers`'s `address` op to fetch `Y`'s **new** definition rather than the one active when the package was signed — the exact same signature that was valid moments earlier is now rejected by the AA, blocking the honest counterparty from claiming funds they are entitled to (or, in the reverse timing, allowing a since-invalidated key to still be treated as valid).
