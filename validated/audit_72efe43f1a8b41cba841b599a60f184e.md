### Title
Non-binding `in merkle` authentifier allows proof replay / front-running of address spends - (File: definition.js)

### Summary
Address definitions can include an `['in merkle', [arrAddresses, feed_name, element, min_mci]]` authentifier [1](#0-0)  that is satisfied merely by presenting a serialized Merkle proof whose root matches a value posted by a trusted oracle address in a data feed. Unlike a signature authentifier, this proof is never bound to the unit being signed (no unit hash, no nonce, no per-spend randomness is part of what's verified), so once it is revealed publicly it can be copied and reused by anyone to satisfy the same spending condition in a different, competing unit.

### Finding Description
The `'in merkle'` case pulls the caller-supplied `serialized_proof` from `assocAuthentifiers[path]`, deserializes it, and checks two things only:
1. `merkle.verifyMerkleProof(element, proof)` — that the (hard-coded, definition-level) `element` is consistent with `proof.siblings` and `proof.root` [2](#0-1) [3](#0-2) .
2. `dataFeeds.dataFeedExists(arrAddresses, feed_name, '=', proof.root, ...)` — that the trusted oracle previously published that exact root as a data-feed value [4](#0-3) .

Neither check ties `serialized_proof` to:
- the unit that is currently being validated (no reference to `objUnit.unit`, `objUnitHash`, or any per-unit challenge), or
- the specific output/spend being authorized.

Since `element` is fixed inside the address definition (which is public once revealed on-chain) and `proof.root` is a value the oracle already published publicly via the data feed, the only "secret" material required to satisfy this authentifier is the sibling list, which itself must be disclosed in plaintext inside the unit's `authentifiers` the very first time anyone uses this spending path. Because Obyte units are gossiped to peers before they become stable, any node that observes the pending unit can extract the `serialized_proof` string from `assocAuthentifiers[path]` and immediately reuse the identical string as their own authentifier for a competing unit built against the same address/definition/path — `verifyMerkleProof` and `dataFeedExists` will both pass again since nothing in the check is consumed, incremented, or bound to unit identity. This lets an attacker front-run the original unit (get their own conflicting/double-spending unit committed to the DAG first) or simply replay the disclosed authentifier indefinitely for any future spend from that address, as long as the `and`-combined witness/signature conditions (if any) in the rest of the definition are also satisfiable by the attacker (e.g., when `'in merkle'` is combined with `'or'`, or is the sole top-level condition, or the co-signing condition is weak/shared).

### Impact Explanation
An address whose definition relies on `'in merkle'` as (part of) its spending authorization can have its funds diverted: an attacker who observes the not-yet-stable unit containing the authentifier can extract and replay it in a competing unit that redirects the payment to an address of the attacker's choosing, winning the race to stabilization. This is unauthorized spending of funds from the address — a concrete asset-loss impact, matching the "unauthorized spending" bar.

### Likelihood Explanation
Requires an address definition that actually uses `'in merkle'` (a niche but supported base-layer feature intended for oracle-gated claims/vesting, e.g. "prove this data-feed root contains element X"). Once such an address is used, the authentifier must be disclosed in a broadcast unit to be spent at all, so every use of this feature is inherently exposed to replay by any network observer during the propagation window before stabilization — no special privileges are needed by the attacker beyond normal DAG observation, which any unprivileged node has.

### Recommendation
Bind the `'in merkle'` authentifier to the specific unit/spend it authorizes, e.g. by requiring the proof (or an accompanying signature) to cover the unit hash, or by marking data-feed roots / proofs as single-use (tracked and rejected on reuse) similar to how signatures are inherently bound to `objectHash.getUnitHashToSign`. At minimum, document and discourage using `'in merkle'` without an accompanying per-unit binding factor (e.g., combined via `and` with a signature over the specific unit), and add validation to reject definitions where `'in merkle'` alone (or via `or`) can authorize spending without any unit-binding condition.

### Proof of Concept
1. Address `A` is created with definition `['in merkle', [[oracleAddr], 'claim', 'secret-element']]` (optionally `or`'d/`and`'d with a weak co-signer condition).
2. Oracle posts merkle root `R` (over a set including `'secret-element'`) to the `claim` data feed.
3. Legitimate holder builds unit `U1` spending from `A` to their own address, including authentifier `assocAuthentifiers[path] = serializeMerkleProof(proof_for_secret_element)`, and broadcasts it.
4. Before `U1` stabilizes, an attacker observing the P2P broadcast copies the `serialized_proof` string, builds a conflicting/double-spending unit `U2` from the same address `A` (spending the same output(s)) to the attacker's address, embedding the identical authentifier at the same `path`.
5. Both `merkle.verifyMerkleProof(element, proof)` [5](#0-4)  and `dataFeeds.dataFeedExists(...)` [4](#0-3)  pass for `U2` exactly as they did for `U1`, since neither check references `U1`'s or `U2`'s unit hash.
6. If `U2` wins the race for DAG inclusion/stabilization, the attacker successfully diverts funds originally intended for the legitimate claimant.

function verifyMerkleProof(element, proof){
	// Node-as-Leaf issue might matter in some cases
	try {
		var index = proof.index;
		var the_other_sibling = hash(element);
		for (var i = 0; i < proof.siblings.length; i++) {
			// this also works for duplicated trailing nodes
			if (index % 2 === 0)
				the_other_sibling = hash(the_other_sibling + proof.siblings[i]);
			else
				the_other_sibling = hash(proof.siblings[i] + the_other_sibling);
			index = Math.floor(index / 2);
		}
		return (the_other_sibling === proof.root);
	}
	catch (e){
		return false;
	}
}
