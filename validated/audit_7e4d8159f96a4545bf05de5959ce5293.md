### Title
Missing network/domain binding in `getSignedPackageHashToSign()` allows cross-network signature replay in `is_valid_signed_package` - (File: object_hash.js, signed_message.js)

### Summary
The reported bug is a missing `DOMAIN_SEPARATOR()` in an ERC2612 token, which lets a signature valid on one chain/contract be replayed on another because the signed hash carries no chain/contract-binding data. The analogous weakness in ocore is in the "signed message" mechanism used by `is_valid_signed_package()` in AA formulas: the hash that gets signed, `getSignedPackageHashToSign()`, is built from the naked package with no field binding it to a particular network (mainnet vs. testnet) or to the specific unit/AA context in which it will be checked, unlike `getUnitHashToSign()` which preserves the unit's `alt` field.

### Finding Description
Regular unit signing preserves the network-distinguishing `alt` field: `getUnitHashToSign()` clones the whole unit (via `getNakedUnit`) and only strips commissions/timestamps/messages payloads, leaving `alt` intact in the source string that is hashed and signed [1](#0-0) , and `getNakedUnit` never deletes `alt` [2](#0-1) .

By contrast, `getSignedPackageHashToSign()`, used for the free-standing "signed message" object that an address owner signs off-chain and that AAs can verify with `is_valid_signed_package`, only removes `authentifiers` from a deep clone and hashes everything else — it never includes `alt` or any other network/context identifier at all, because the signed-message object itself never carries an `alt` field: [3](#0-2) 

The validator that accepts such packages, `validateSignedMessage()`, restricts the allowed top-level fields to `["signed_message", "authors", "last_ball_unit", "timestamp", "version"]` — there is no `alt`/network field permitted or checked: [4](#0-3) 

The oscript entry point `is_valid_signed_package` in AA formula evaluation calls straight into `signed_message.validateSignedMessage()` and returns `true`/`false` to the AA based solely on the address matching and the ECDSA authentifier check, with no network-binding check: [5](#0-4) 

Since Obyte addresses are derived purely from the definition (`chash` of `["sig", {pubkey}]` etc.) and are identical across networks (mainnet/testnet share the same address derivation), the same private key produces the same address regardless of network. Because the signed-package hash has no field that ties it to a specific network or a specific consuming AA/context, a signed_message produced for one context (e.g., a testnet dApp, or a different AA's oracle/attestation scheme) is byte-identical and equally valid when replayed against `is_valid_signed_package(..., address)` in a mainnet AA that expects a fresh, context-bound attestation from that address.

### Impact Explanation
An AA author relying on `is_valid_signed_package` as an authorization/attestation gate (e.g., "address X attests to fact Y, therefore release funds/mint asset/change state") cannot cryptographically distinguish a signature intended for their AA from one produced for a different AA, a different network, or a different application — because the signed hash carries no domain separator. An attacker who has captured (or convinced the address owner to produce, e.g. on testnet or another unrelated dApp) any validly-signed message from the target address can replay it into a victim AA to satisfy its `is_valid_signed_package` check, potentially triggering unauthorized fund release, state changes, or asset issuance/transfer conditions gated by that check. This can lead to concrete AA fund loss or unauthorized spending of AA balances.

### Likelihood Explanation
Exploitation only requires an AA trigger sender (unprivileged) to submit a previously-obtained signed package that satisfies the address check — no special network position or privileged access is needed. The likelihood depends on AA authors actually using `is_valid_signed_package` as a security-critical authorization mechanism and on an attacker being able to obtain a validly-signed message from the target address for a different purpose/network; this is a realistic scenario for oracle/attestation-style AAs that trust off-chain-signed data from a known address, especially given that mainnet and testnet share address derivation.

### Recommendation
Bind the signed-package hash to an explicit domain: include a network/`alt` field (and ideally an application/AA-specific context tag or nonce) inside the object hashed by `getSignedPackageHashToSign()`, and enforce/validate that field in `validateSignedMessage()` (reject if `alt` doesn't match the current network, similar to how full units retain `alt`). AA authors should also be documented/encouraged to embed their own context binding (e.g., AA address, purpose string) inside `signed_message` payload to avoid cross-application replay even after this fix.

### Proof of Concept
1. Address `A` (definition `["sig", {"pubkey": P}]`) signs a `signed_message` package for an unrelated purpose (e.g., a testnet demo or a different AA), producing `objSignedPackage` with `authors[0].authentifiers.r = signature` computed over `getSignedPackageHashToSign(objSignedPackage)` — note the hash contains no `alt`/network/context field [3](#0-2) .
2. An attacker submits the same `objSignedPackage` unmodified as `trigger.data.signed_package` to a victim AA on mainnet that runs `is_valid_signed_package(trigger.data.signed_package, 'A')` [6](#0-5) .
3. `validateSignedMessage()` accepts the package because all required fields are present and the ECDSA signature verifies over the same (context-free) hash [7](#0-6) , causing the AA to treat the replayed, out-of-context signature as valid authorization.

function getUnitHashToSign(objUnit) {
	var objNakedUnit = getNakedUnit(objUnit);
	for (var i=0; i<objNakedUnit.authors.length; i++)
		delete objNakedUnit.authors[i].authentifiers;
	var sourceString = (typeof objUnit.version === 'undefined' || objUnit.version === constants.versionWithoutTimestamp) ? getSourceString(objNakedUnit) : getJsonSourceString(objNakedUnit);
	return crypto.createHash("sha256").update(sourceString, "utf8").digest();
}
