### Title
Webhook team-membership escalation via cross-organization `github_id` collision - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which organization's HMAC secret to validate a `membership` webhook against using an attacker-controlled field (`organization.login` / `repository.owner.login`) from the same JSON payload being verified. `MembershipHandler#find_or_create_team!` then looks up the `Team` to mutate purely by `params.team.id` (the numeric GitHub team ID), with no check that this team belongs to the organization whose secret verified the request. An attacker who owns any organization with a Shipit-configured webhook (their own org, with their own `webhook_secret`) can therefore sign a payload claiming `organization.login: "attacker-org"` but `team.id: <victim-org's team github_id>`, and get their own login added as a member of the victim's (e.g. `shopify`) privileged `Team`.

### Finding Description
The broken binding, as an equality that must hold but doesn't: `organization_whose_secret_verified_request == organization_owning_team_id_in_payload`. In `app/controllers/shipit/webhooks_controller.rb:24-30`, `verify_signature` computes `repository_owner` from `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0)  and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [2](#0-1) . This value is entirely attacker-supplied JSON body content, so the attacker can set it to their own organization to obtain a verifiable signature using a secret they legitimately possess (`Shipit.github(organization: 'attacker-org')`'s configured `webhook_secret`, per the multi-org config documented in `docs/setup.md`).

Once signature verification passes, `MembershipHandler#process` calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id)` [3](#0-2) . If a `Team` row already exists with that `github_id` (e.g., a real `shopify` team used in `Shipit.github_teams`), the `find_or_create_by!` block (which would set `team.organization = params.organization.login`) never executes — the existing row, with `organization: 'shopify'`, is returned unmodified. The handler then calls `team.add_member(User.find_or_create_by_login!(params.member.login))` [4](#0-3) , adding the attacker's own GitHub login as a member of the pre-existing privileged team, using nothing but the signature validity of `attacker-org`.

None of the existing guards catch this: `drop_unhandled_event` only checks the event type is registered [5](#0-4) ; the `ExplicitParameters` schema in `MembershipHandler.params` only validates types/presence of `team.id`, `organization.login`, `member.login`, not their cross-consistency [6](#0-5) ; and `verify_webhook_signature` only proves the payload was signed by whichever org's secret was looked up — which is itself derived from attacker-controlled payload content [7](#0-6) .

Team membership directly feeds `User#authorized?`: `Shipit.github_teams.empty? || teams.where(id: Shipit.github_teams.map(&:id)).exists?` [8](#0-7) , and `Shipit.github_teams` resolves the configured `oauth.teams` handles to `Team` records via `Team.find_or_create_by_handle` [9](#0-8) . Adding a `Membership` row for the attacker's user against that same `Team` id makes `authorized?` return true, bypassing `force_github_authentication`'s team-membership gate [10](#0-9) .

### Impact Explanation
This is a real authentication/authorization bypass: an attacker with only their own low-privilege GitHub org and its Shipit webhook secret can grant themselves membership in a privileged `Shipit::Team` (matching `Shipit.github_teams`), which flips `User#authorized?` to `true` for their account and grants them full access to the Shipit UI/API otherwise restricted to members of e.g. `shopify/developers`. This matches "escalation into `Shipit.github_teams` authorization" (High/Critical per the rubric). It is repeatable per victim team as long as the attacker can guess/discover the target `Team`'s `github_id` (sequential integers, or discoverable via unauthenticated GitHub team listing APIs), and does not require compromising the victim org's own secret at all.

### Likelihood Explanation
Preconditions: (1) attacker must control at least one GitHub organization that is itself configured in Shipit's multi-org `github:` secrets block (i.e., attacker has a legitimate installation with its own `webhook_secret` they know), (2) a `Team` row exists in Shipit's DB for the victim org (created previously via a legitimate `membership` webhook or `Team.find_or_create_by_handle`), and (3) the attacker knows or can guess/discover that team's numeric GitHub `github_id`. GitHub team IDs are sequential/enumerable and, depending on org visibility settings, can be discoverable through public GitHub API endpoints without authentication. Given a valid webhook_secret for their own org (attacker's own, not the victim's), constructing and POSTing the forged payload is trivial and fully repeatable.

### Recommendation
In `MembershipHandler#find_or_create_team!`, require that the resolved `params.organization.login` matches the existing `Team#organization` before mutating membership — e.g., look up by `github_id` scoped to `organization: params.organization.login`, and reject/no-op (or raise) if a `Team` with that `github_id` exists under a different organization. More generally, `verify_signature` should not let attacker-controlled payload content select the signing key without then constraining every payload field to that same organization; the webhook processing pipeline should verify that all organization-scoped identifiers in the payload (team, repository owner) belong to the organization whose secret validated the signature.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (new test)
test ":membership webhook from attacker's own org cannot mutate another org's Team" do
  victim_team = shipit_teams(:shopify_developers) # organization: 'shopify'

  # Attacker's own org has its own configured webhook_secret ('1234' in fixtures/test config)
  payload = {
    action: 'added',
    team: { id: victim_team.github_id, name: 'x', slug: 'x', url: 'http://example.com' },
    organization: { login: 'attacker-org' },       # attacker's own org
    member: { login: 'attacker' }
  }.to_json

  signature = "sha1=#{OpenSSL::HMAC.hexdigest('sha1', 'attacker-org-secret', payload)}"
  @request.headers['X-Github-Event'] = 'membership'
  @request.headers['X-Hub-Signature'] = signature

  # equality that must hold: params.dig('organization','login') (used for HMAC org)
  # must equal Team.find_by(github_id: params['team']['id']).organization
  assert_equal 'attacker-org', JSON.parse(payload).dig('organization', 'login')
  assert_equal 'shopify', victim_team.organization
  refute_equal JSON.parse(payload).dig('organization', 'login'), victim_team.organization

  assert_no_difference -> { Shipit::Membership.where(team: victim_team).count } do
    post :create, body: payload, as: :json
    assert_response :unprocessable_entity # or :ok in current vulnerable behavior — assert it should be rejected
  end

  refute victim_team.members.exists?(login: 'attacker')
end
```
This test encodes the two sides of the broken binding explicitly (`organization.login` used for signature vs. `Team#organization` of the record actually mutated) and asserts they diverge while the current code still allows the mutation — demonstrating the vulnerability; the fix should make this test pass by rejecting the cross-org mutation.
