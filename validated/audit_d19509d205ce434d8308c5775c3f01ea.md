### Title
Unbounded private-payment chain array allows memory-exhaustion DoS in `handlePrivatePaymentChains` - (File: wallet.js)

### Summary
`memberlist`'s CVE-2026-14362 is a memory-exhaustion DoS caused by processing crafted push/pull state messages without adequate bounds. The closest reachable analog in ocore that fits an allowed actor (a private-payment counterparty, not a generic network peer) is `handlePrivatePaymentChains` in [1](#0-0) , which accepts an attacker-supplied `body.chains` array and performs only shape validation, never bounding the number of chains, the number of elements per chain, or their sizes before hashing, iterating, and queuing further async DB/validation work per element.

### Finding Description
`handlePrivatePaymentChains(ws, body, from_address, callbacks)` reads `arrChains = body.chains` from a message sent by any correspondent device (a private-payment counterparty) and validates only that it is a well-formed nested array of objects with the expected fields: [2](#0-1) 

There is no cap on:
- the number of chains in `arrChains`,
- the number of elements (`arrPrivateElements`) inside each chain,
- the size of `payload`, `inputs`, or `outputs` per element.

Every chain is then processed with `objectHash.getBase64Hash(arrChains)` (hashing the whole structure) and iterated with `async.eachSeries`, each element triggering `objectHash.getBase64Hash(objHeadPrivateElement.payload, true)`, DB queries, and validation logic (`validatePrivatePayment`-style processing further down in the file) that clones/holds data in memory, and — for light clients — triggers `network.requestUnfinishedPastUnitsOfPrivateChains(arrChains)`, which forwards the entire uncapped structure into further network requests: [3](#0-2) 

By contrast, comparable code paths in the codebase enforce explicit bounds before doing heavy work, e.g. `MAX_MESSAGES_PER_UNIT`, `MAX_PARENTS_PER_UNIT`, `isTooDeeplyNestedOrHasTooManyNodes`, and array/dictionary size caps inside `formula/validation.js` (`arrPairs.length > 5`, `arrItems.length > 100`, etc.) and `validation.js` unit checks such as [4](#0-3) . No equivalent size guard exists on `body.chains` before it is hashed and processed, making it structurally analogous to memberlist processing an oversized push/pull payload without pre-validating its size.

### Impact Explanation
A malicious correspondent (paired device / private-payment counterparty — an explicitly in-scope actor per the analog constraints) can send a single `private_payments` message containing an extremely large `chains` array (many chains, each with many elements, each with large `payload.inputs`/`outputs` arrays) to a wallet. Processing this message forces the receiving node to:
1. Deep-hash the entire structure via `objectHash.getBase64Hash(arrChains)`.
2. Iterate and hash every element's payload.
3. Retain the whole parsed structure in memory across the async chain, and for light clients, propagate it further via `requestUnfinishedPastUnitsOfPrivateChains`.

This can exhaust memory/CPU on the receiving wallet node, potentially crashing the process — the same "memory exhaustion via crafted push/pull-style message" bug class as CVE-2026-14362, but triggered by an unprivileged private-payment counterparty rather than a raw network peer.

### Likelihood Explanation
Likelihood is moderate: any device correspondent that has been paired (or can trigger private-payment forwarding) can send this payload with no special privileges beyond an established pairing, and the code path is reachable directly from `handleMessageFromHub` without additional authentication of the array's size. However, exploitation requires a sufficiently large JSON payload to be transmitted through the hub/websocket layer, so any pre-existing message-size limits on the transport (not confirmed to exist for this specific code path) could partially mitigate it — this could not be fully verified given the available code index.

### Recommendation
Add explicit upper bounds in `handlePrivatePaymentChains` before hashing/iterating `arrChains`, e.g.:
- Cap `arrChains.length` and the length of each `arrPrivateElements` array to small constants (similar to `MAX_MESSAGES_PER_UNIT`/`MAX_PARENTS_PER_UNIT`).
- Cap `payload.inputs.length` / `payload.outputs.length` per element.
- Reject the whole message early (before `objectHash.getBase64Hash`) if any of these bounds are exceeded.

### Proof of Concept
1. Pair with (or spoof, if pairing verification is otherwise weak) a victim wallet as a device correspondent.
2. Send a `private_payments` message whose `body.chains` contains a very large number of chains (e.g., tens of thousands), each with a moderately large `payload.inputs`/`payload.outputs` array, satisfying only the minimal shape checks in [5](#0-4) .
3. Observe that `handlePrivatePaymentChains` proceeds to hash and iterate the entire structure without rejecting it for size, consuming excessive memory/CPU on the receiving node.

*Note: I was not able to fully confirm within the available index whether an upstream websocket/message-size limit (e.g., a hard cap on total message bytes) exists that would restrict how large `body.chains` can practically be before reaching this handler; this would need to be verified in a full Devin session with access to the complete `network.js` message-size configuration.*
