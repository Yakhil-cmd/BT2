### Title
First-Definer-Wins Race in AA-Defined-AA Balance Bookkeeping - ([File: storage.js])

### Summary
The bug class in the external report is "first-to-cache wins": an unprivileged, untrusted actor can race a trusted actor to populate a shared, content-keyed cache, and whichever write lands first becomes authoritative bookkeeping state that everyone else then trusts. `insertAADefinitions()` in `storage.js` implements exactly this pattern for AA-defined-AA definitions: the `aa_addresses` table is keyed by `address` (the content hash of the AA bytecode) and populated with `INSERT ... IGNORE`, so the *first* unit to successfully insert a given address permanently fixes the `unit`/`mci` context that all later balance recalculations for that address are anchored to.

### Finding Description
AAs can define other AAs at runtime via an `app: 'definition'` message [1](#0-0) . Because the address of a new AA is `chash160(definition)`, any AA anywhere in the DAG can independently attempt to "define" the exact same address (e.g., two unrelated factory AAs, in two different branches, produce byte-identical child AA code with the same address). The persistence layer treats this as a cache lookup keyed by address: [2](#0-1) 

- The `aa_addresses` row is inserted with `INSERT IGNORE`, so only the first successful writer's `(unit, mci)` is stored [3](#0-2) .
- If a second insert for the same address arrives, the code detects `res.affectedRows === 0` and explicitly branches on which `unit` "won": if it isn't the caller's own unit, the second (possibly canonical/trusted) definer's context is silently discarded ("ignoring repeated definition of AA ... in another unit ...") [4](#0-3) .
- If it *is* the same unit (i.e., the previously-inserted "unconfirmed" pre-stabilization write from `writer.js`), the code performs a `REPLACE INTO aa_balances` recomputation gated by an `mci_cond` window that depends on `mci`, `bForAAsOnly`, and whether `is_aa_response` [5](#0-4) .

This insertion happens twice in the unit's lifecycle for the *same* content-addressed AA: once immediately when the defining AA response unit is written, while still unstable (`bForAAsOnly=true`, using `initial_trigger_mci`) [6](#0-5) , and once again at stabilization time using the last-ball mci for validation [7](#0-6) . Because the first (unconfirmed) write happens as soon as a node locally processes/writes the unit — before global stabilization order is fixed — the `unit`/`mci` context that ultimately drives the `aa_balances` SUM query's inclusion/exclusion window (`main_chain_index<=?`, `outputs.unit!=?`, `OR is_aa_response=1`, etc.) is determined by local processing order rather than final consensus order. This mirrors the CVE's core flaw: the artifact/context that "wins" the cache is decided by whoever writes first, not by trust or canonical ordering, and once written it is treated as authoritative truth for all subsequent balance computations of that AA address (`readAABalances`, `updateInitialAABalances`), which every future trigger to that address relies on for spending decisions.

### Impact Explanation
`aa_balances` is the ledger AAs use to decide what they can safely spend (`updateInitialAABalances` reads it before every trigger is processed). If the address-keyed "first insert wins" logic locks in the wrong `unit`/`mci` context, the subsequent `SUM(...) ` balance recomputation can double-count or omit outputs sent to the address in the window between definition and stabilization, producing balances that don't match the true sum of unspent, confirmed outputs to that address. Because this is silent (no validation failure, no error is raised — the discrepancy is only ever logged via `console.log`), it can lead directly to AA fund loss (AA pays out more than it legitimately holds) or freezing (AA under-counts its balance and can no longer act on funds it has actually received) — squarely inside the categories the validation rules call out as acceptable impact.

### Likelihood Explanation
Triggering this requires only the ability to compose ordinary AA triggers/messages that any unprivileged trigger sender can post — no special privileges, no witness/hub/network position, and no reliance on malicious peers. An attacker only needs to arrange for the same content-addressed child-AA definition to be posted from two different trigger contexts (e.g., by pre-computing bytecode and racing two independent triggers into two different AAs that both emit the identical `definition` payload) so that the local-processing race resolves in the attacker's favor before the "trusted" definer's context is recorded. The complexity of engineering the exact mci/ordering condition (`bForAAsOnly`, `pemCurvesFixMci`, `testnetAAsDefinedByAAsAreActiveImmediatelyUpgradeMci`) is non-trivial and I was not able to fully trace every edge of the balance-recalculation arithmetic in the remaining time, so I cannot guarantee a concrete overspend/underspend scenario end-to-end from this analysis alone — this is the main residual uncertainty.

### Recommendation
Make the AA-address definition/balance bookkeeping independent of first-write ordering: derive the `mci`/context used for the `aa_balances` recompute window deterministically from stabilized DAG order (e.g., always use the stabilization-time recompute and never trust the pre-stabilization "unconfirmed" `unit` as authoritative), and treat any second, differing definer as a conflict to be resolved deterministically by consensus rules rather than by "first insert wins." Add an invariant check that fails loudly (rather than just `console.log`) when a same-address definition arrives from a different unit than the one already recorded, so silent balance recomputation divergences cannot occur unnoticed.

### Proof of Concept
I was not able to construct or verify a full end-to-end sequence of unit templates that deterministically wins this race and produces a measurable balance discrepancy within the remaining investigation time. The proof-of-concept would require: (1) two AAs, in independent branches, each producing byte-identical child-AA definitions (so `chash160` addresses collide) via `app: 'definition'` messages, sent with payments to the not-yet-existing address at carefully chosen relative timings/mci so that local write order differs from stabilization order, then (3) inspecting the resulting `aa_balances` row for that address versus the true sum of unspent confirmed outputs to it. This would need to be validated in a live/test ocore node to confirm the exploitability and exact magnitude of the discrepancy — flagging this as unverified rather than proven.
