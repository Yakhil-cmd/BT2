### Title
Global, repository-unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` lets a status webhook attributed to one (secret-less) org mutate a Commit belonging to any other Stack/repository - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits solely by `sha`, with no repository/stack scoping, then calls `commit.create_status_from_github!(params)` on whatever `Commit` rows match. The broken binding is: `payload.repository.full_name` (the org/repo the webhook's signature was verified against) `==` `commit.stack.repository.full_name` (the repository owning the mutated `Commit` row) — the handler never enforces this equality.

### Finding Description
The claimed binding, stated explicitly:
`Shipit.github(organization: repository_owner_from_payload).verify_webhook_signature(...)` verifies authenticity **only for the org named in the payload**, and the intended invariant is that any DB row mutated as a result must belong to that same, verified repository: `payload['repository']['full_name'] == commit.stack.repository.full_name`.

Path:
1. `WebhooksController#create` parses the body and dispatches to `Shipit::Webhooks.for_event(event)` handlers [1](#0-0) .
2. `verify_signature` picks the `GitHubApp` for `repository_owner` (taken straight from the unauthenticated payload) and calls `verify_webhook_signature` [2](#0-1) .
3. `GitHubApp#verify_webhook_signature` explicitly bypasses HMAC verification when that org has no `webhook_secret` configured: `return true unless webhook_secret` [3](#0-2) . So for an org configured in Shipit but without a `webhook_secret`, any payload claiming to be from that org is accepted unconditionally, regardless of who actually sent it.
4. `StatusHandler#process` then does: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [4](#0-3) . This query is **global across all stacks/repositories** — it is not scoped by `stack_id` or `repository_name`.
5. Contrast with the base `Handler` class, which provides a `stacks` helper that *does* scope by `repository_name` from the payload (`Repository.from_github_repo_name(repository_name)&.stacks`) [5](#0-4) . `StatusHandler` deliberately/accidentally bypasses this scoping helper and queries `Commit` directly by `sha` only.
6. `create_status_from_github!` writes the attacker-supplied `state`/`description`/`target_url`/`context` onto the found commit via `Status.replicate_from_github!` [6](#0-5) [7](#0-6) .

Exploit flow: an attacker controls (or has push access to) a repository under a GitHub org **A** that is configured in Shipit but for which no `webhook_secret` is set (org A must be a known org — `Shipit.github(organization:)` raises `GithubOrganizationUnknown` and returns 422 otherwise). The attacker crafts a `status` event JSON body with `repository.owner.login = "A"`, and `sha` equal to a commit sha that exists in victim org **B**'s Stack (identical content commits — e.g. shared upstream/fork commits — produce identical shas across repositories). Because org A has no secret, `verify_signature` passes unconditionally. `StatusHandler#process` then finds and mutates **every** `Commit` row across the whole database matching that sha, including org B's, with attacker-chosen `state`/`description`/`target_url`.

Existing guards do not stop this: `verify_signature` only authenticates the org named in the payload (org A), not the repository owning the target `Commit`; there is no post-verification check that `params.dig('repository','full_name')` matches `commit.stack.repository.full_name`.

### Impact Explanation
A payload correctly authenticated (or exempted) for repository/org A can write a fabricated CI status onto a `Commit` belonging to an entirely different repository/org B's `Stack`. Downstream, `Status` creation can influence `commit.state`, `enable_ci_on_stack`, `schedule_continuous_delivery`, and merge-request processing (`ProcessMergeRequestsJob`) as shown by `create_status_from_github!` side effects [8](#0-7) , meaning an attacker can potentially force a victim commit to appear `success`/`failure`, unblocking or blocking deploys/merges tied to a repository they do not control. This is a cross-tenant write and matches "a payload for one repository mutating another's stack, commit, task or team" — Critical.

### Likelihood Explanation
Preconditions: (1) at least one Shipit-configured GitHub org/App entry with no `webhook_secret` set (a realistic misconfiguration/multi-org deployment gap — the docs even show `webhook_secret` as populated per-org but nothing enforces it must be non-blank for every configured org) [9](#0-8) ; (2) a sha collision between the attacker-named repository and the victim's tracked commit, which is realistic in shared-upstream/fork scenarios (identical git commit content yields identical shas independent of repository). Attacker cost is a single unauthenticated HTTP POST to `/webhooks`, fully repeatable and scriptable against any known sha. No Shipit session, API token, or GitHub secret is required.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to the stacks belonging to the verified `repository_name` from the payload — mirroring the `stacks` helper already defined in `Handler` — instead of a global `Commit.where(sha:)` query, e.g. `stacks.flat_map(&:commits).select { |c| c.sha == params.sha }` or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`. Additionally, require `webhook_secret` to be present for every configured GitHub org (fail closed) rather than defaulting `verify_webhook_signature` to `true` when unset.

### Proof of Concept
Minitest plan (controller or model level):
1. Create two Stacks/Repositories, org A (`repository_params` login `"org-a"`, no `webhook_secret` in test config) and org B (`"org-b"`), each with a `Commit` sharing the same `sha` value (e.g. `"deadbeef"*5`).
2. Stub/leave `Shipit.github(organization: 'org-a').verify_webhook_signature` to return `true` (simulating no secret, as in `lib/shipit/github_app.rb:76-77`).
3. POST to `/webhooks` with `X-Github-Event: status`, body `{ sha: commitA.sha, state: 'success', repository: { full_name: 'org-a/repo', owner: { login: 'org-a' } } }`.
4. Assert on both sides of the binding:
   - `assert_difference('commitA.statuses.count', 1) { post :create, ... }` — org A's commit is legitimately updated.
   - `assert_no_difference('commitB.statuses.count') { ... }` — org B's commit (`payload.repository.full_name` "org-a/repo" != `commitB.stack.repository.full_name` "org-b/repo") must NOT be mutated.
5. Under the current code, step 4's second assertion fails, proving `Commit.where(sha:)` in `app/models/shipit/webhooks/handlers/status_handler.rb:21` writes to `commitB` despite the mismatched repository binding.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
