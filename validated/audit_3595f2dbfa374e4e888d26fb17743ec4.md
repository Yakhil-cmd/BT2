### Title
Hookify PreToolUse/Stop `block` rules can be silently bypassed via regex/hook-timeout starvation (ReDoS) - ([File: plugins/hookify/core/rule_engine.py])

### Summary
The `hookify` plugin implements a user-configurable security-blocking mechanism: `.claude/hookify.*.local.md` rule files define `regex_match` conditions that are evaluated against untrusted, attacker-influenceable content (Bash `command`, file `new_text`/`content`) inside the `PreToolUse`/`Stop` hook process before Claude Code allows the tool call or session stop. Just like the Oracle in the external report, which can "fulfil" a request by spending just enough gas to update its own state while starving the external callback of the gas needed to actually run it (so the requester's logic never executes, yet payment is still released), the hookify hook process can be starved of the CPU-time "stipend" it needs to finish rule evaluation. When that happens, the enforcement check never completes, but the surrounding operation (the tool call / session stop) proceeds anyway, exactly mirroring the "state updated, callback not executed, payment still released" pattern from the report.

### Finding Description
Hookify's `RuleEngine._regex_match` compiles and executes attacker-influenced regex patterns against attacker-influenceable text with no execution-time bound: [1](#0-0) 

This is invoked from `_check_condition` for every `regex_match` condition, itself called by `_rule_matches`/`evaluate_rules` for every configured rule on every `PreToolUse`/`PostToolUse`/`Stop`/`UserPromptSubmit` event: [2](#0-1) 

The entire evaluation is wrapped by a Python-level `try/except` whose designed fail-open behavior is to *allow the operation* on any caught exception, exiting 0 unconditionally: [3](#0-2) 

Critically, this fail-open path only triggers for **exceptions inside the Python process**. If the regex evaluation instead **hangs** (catastrophic backtracking / ReDoS on a `.*`, nested-quantifier, or alternation-heavy pattern matched against long/adversarial text — patterns the docs explicitly recommend, e.g. `(eval|exec)\(`, `\.env$|credentials|secrets`, `.*`), the hook process never reaches the `try/except`/`finally` at all. Instead, Claude Code's hook harness kills the process once the configured timeout elapses: [4](#0-3) 

The regexes are cached via `lru_cache` and only guarded against `re.error` (invalid syntax), not against runaway execution time: [5](#0-4) 

Because `block` rules are the only intended defense (per the plugin's own documentation, `action: block` is meant to "Prevent operation from executing"): [6](#0-5) 

...starving the regex engine of the CPU-time budget it needs to complete (analogous to under-supplying gas to the Oracle's callback) prevents the `block` decision from ever being computed and returned to Claude Code — yet the tool call is not held back indefinitely; hook timeout is a non-blocking failure mode by design in this hook framework (only exit code `2` is documented as blocking; anything else, including a timeout kill, is "Non-blocking error"): [7](#0-6) 

### Impact Explanation
This is a direct hook-bypass of a locally-configured security control. Any content that reaches a `regex_match` field — a Bash command string, a file's `new_text`/`content` being written, or a user prompt — can be crafted (by the model acting on attacker-controlled/untrusted content via prompt injection, or by any process that can influence tool inputs) to defeat the user's configured `block` rules (e.g., "block `rm -rf`", "block writing secrets to `.env`") by pairing it with a pathological string that causes the matching regex to hang past the hook timeout. The dangerous Bash command or sensitive file write then executes without the intended block, because the enforcement mechanism never produced a "deny" decision in time — a direct, unauthorized action bypassing an approval boundary the user explicitly configured to prevent it.

### Likelihood Explanation
Requires: (1) a hookify `block` rule using `regex_match` (a documented, encouraged configuration pattern), and (2) the ability to influence the text being matched (command text, file content, or prompt text) with a value long/structured enough to trigger catastrophic backtracking. Both conditions are realistic in normal usage — the plugin's own examples use exactly the alternation/anchor-style patterns prone to backtracking blowup, and inputs like file content or long Bash strings are attacker/model-influenceable. This does not require any special privilege beyond the ability to get Claude to construct or process a crafted string, e.g. via prompt injection from fetched content.

### Recommendation
Bound regex execution the way the report recommends bounding gas: require a hard, measured resource budget for the check that runs *before* the enforcement decision is finalized, rather than letting the overall operation proceed by default when that budget is exhausted. Concretely:
- Enforce a strict, low internal timeout around each `_regex_match` call (e.g., using a separate process/thread with an alarm, or `regex`/`re2`-style bounded engines) and treat a timeout as an explicit **block/deny**, not a pass-through.
- Reject or flag rule patterns known to be susceptible to catastrophic backtracking at rule-authoring time (static analysis / lint in `hookify.md`/`writing-rules` tooling).
- Make the hookify hook harness itself fail closed (return `permissionDecision: deny` or exit 2) on any non-zero/timeout/killed exit for rules marked `action: block`, instead of relying on the external harness's default non-blocking treatment of non-2 exit codes.

### Proof of Concept
1. Create `.claude/hookify.block-secrets.local.md`:
```
---
name: block-secrets
enabled: true
event: file
action: block
pattern: (a+)+b
---
Blocked: pattern indicates unsafe content.
```
2. Have Claude (or any tool-input source) attempt a `Write`/`Edit` whose `new_text` contains a long string of `a` characters with no trailing `b` (e.g., `"a"*40 + "!"`), which is matched against `(a+)+b` via `_regex_match`.
3. `re.compile(r"(a+)+b", re.IGNORECASE).search(...)` exhibits exponential backtracking on this input, hanging well past the hook's configured timeout (`timeout: 10` in `plugins/hookify/hooks/hooks.json`).
4. Claude Code's hook harness kills the hung `pretooluse.py` process on timeout; per the documented exit-code semantics only exit code `2` is blocking, so the harness treats the killed/non-2 hook as non-blocking and the `Write`/`Edit` proceeds — bypassing the configured `block` rule despite the sensitive content it was meant to catch.

Note: I could not directly inspect the core Claude Code hook-execution harness's exact timeout-kill handling logic (it is closed-source/not present in this repository); the analysis above is based on the harness behavior as documented in this repo's own hook-development skill docs (`plugins/plugin-dev/skills/hook-development/SKILL.md`) and the hookify plugin's shipped hook scripts/config, which are within the indexed repository content.

```python
@lru_cache(maxsize=128)
def compile_regex(pattern: str) -> re.Pattern:
    """Compile regex pattern with caching.

    Args:
        pattern: Regex pattern string

    Returns:
        Compiled regex pattern
    """
    return re.compile(pattern, re.IGNORECASE)
```

```python
    def evaluate_rules(self, rules: List[Rule], input_data: Dict[str, Any]) -> Dict[str, Any]:
        """Evaluate all rules and return combined results.

        Checks all rules and accumulates matches. Blocking rules take priority
        over warning rules. All matching rule messages are combined.

        Args:
            rules: List of Rule objects to evaluate
            input_data: Hook input JSON (tool_name, tool_input, etc.)

        Returns:
            Response dict with systemMessage, hookSpecificOutput, etc.
            Empty dict {} if no rules match.
        """
        hook_event = input_data.get('hook_event_name', '')
        blocking_rules = []
        warning_rules = []

        for rule in rules:
            if self._rule_matches(rule, input_data):
                if rule.action == 'block':
                    blocking_rules.append(rule)
                else:
                    warning_rules.append(rule)

        # If any blocking rules matched, block the operation
        if blocking_rules:
            messages = [f"**[{r.name}]**\n{r.message}" for r in blocking_rules]
            combined_message = "\n\n".join(messages)

            # Use appropriate blocking format based on event type
            if hook_event == 'Stop':
                return {
                    "decision": "block",
                    "reason": combined_message,
                    "systemMessage": combined_message
                }
            elif hook_event in ['PreToolUse', 'PostToolUse']:
                return {
                    "hookSpecificOutput": {
                        "hookEventName": hook_event,
                        "permissionDecision": "deny"
                    },
                    "systemMessage": combined_message
                }
            else:
                # For other events, just show message
                return {
                    "systemMessage": combined_message
                }

        # If only warnings, show them but allow operation
        if warning_rules:
            messages = [f"**[{r.name}]**\n{r.message}" for r in warning_rules]
            return {
                "systemMessage": "\n\n".join(messages)
            }

        # No matches - allow operation
        return {}
```

```python
    def _regex_match(self, pattern: str, text: str) -> bool:
        """Check if pattern matches text using regex.

        Args:
            pattern: Regex pattern
            text: Text to match against

        Returns:
            True if pattern matches
        """
        try:
            # Use cached compiled regex (LRU cache with max 128 patterns)
            regex = compile_regex(pattern)
            return bool(regex.search(text))

        except re.error as e:
            print(f"Invalid regex pattern '{pattern}': {e}", file=sys.stderr)
            return False
```

```python
def main():
    """Main entry point for PreToolUse hook."""
    try:
        # Read input from stdin
        input_data = json.load(sys.stdin)

        # Determine event type for filtering
        # For PreToolUse, we use tool_name to determine "bash" vs "file" event
        tool_name = input_data.get('tool_name', '')

        event = None
        if tool_name == 'Bash':
            event = 'bash'
        elif tool_name in ['Edit', 'Write', 'MultiEdit']:
            event = 'file'

        # Load rules
        rules = load_rules(event=event)

        # Evaluate rules
        engine = RuleEngine()
        result = engine.evaluate_rules(rules, input_data)

        # Always output JSON (even if empty)
        print(json.dumps(result), file=sys.stdout)

    except Exception as e:
        # On any error, allow the operation and log
        error_output = {
            "systemMessage": f"Hookify error: {str(e)}"
        }
        print(json.dumps(error_output), file=sys.stdout)

    finally:
        # ALWAYS exit 0 - never block operations due to hook errors
        sys.exit(0)
```
