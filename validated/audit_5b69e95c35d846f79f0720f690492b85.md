### Title
AA composer omits `is_transferrable`, `spender_attested`, and `cosigned_by_definer` restrictions when sending custom-asset payments, causing AA balances to become permanently frozen - (File: aa_composer.js)

### Summary
The Teller report concerns collateral tokens that can be paused/made non-transferrable, causing loans to become unliquidatable and collateral to become permanently stuck. The ocore analog is the Autonomous Agent (AA) response composer, which builds outgoing `payment` messages for custom assets without checking the asset's transfer restrictions (`is_transferrable`, `spender_attested`, `cosigned_by_definer`) before composing the response unit — restrictions that are explicitly enforced everywhere else in the codebase (wallet composers and unit validation).

### Finding Description
When an AA sends a payment for a non-base asset, `handleTrigger`'s `completePaymentPayload` path in `aa_composer.js` loads the asset via `storage.loadAssetWithListOfAttestedAuthors` and only checks two conditions before composing the message: [1](#0-0) 
- `objAsset.fixed_denominations` → skip (indivisible assets not supported)
- `objAsset.is_private` → bounce ("sending private asset from AA")

It never checks:
- `objAsset.is_transferrable` — whether the asset can be sent to an arbitrary address rather than back to the definer
- `objAsset.cosigned_by_definer` — whether the definer's signature is required
- `objAsset.spender_attested` — whether the recipient address must be attested

Contrast this with the ordinary wallet composers, which explicitly enforce these same rules before building a payment: [2](#0-1) [3](#0-2) 

And with the authoritative unit-validation logic in `validatePaymentInputsAndOutputs`, which will reject such a payment at final consensus-validation time: [4](#0-3) 

Because an AA is a smart-contract address that anyone can pay into, an AA can receive/accumulate balance in a third-party-defined asset that is `is_transferrable: false` (and the AA is not the definer), or `spender_attested: true` with an attestor list the AA's target recipients will never satisfy, or `cosigned_by_definer: true`. The AA composer will happily build a `payment` message spending that balance to the trigger's `address`, believing it succeeded (no `cb(err)` is raised for these conditions), only to have the resulting unit rejected by `validatePaymentInputsAndOutputs` at the final validation stage that every node (including the responding node itself) performs. AAs cannot dynamically detect these restrictions ahead of time via oscript (there is no formula getter exposed for `is_transferrable`/`spender_attested`/`cosigned_by_definer` per the visible `asset[...]` formula surface used in tests, which only exposes `cap`, `is_issued`, etc.) so AA authors have no reliable way to guard against sending such a restricted asset out.

### Impact Explanation
If the produced response unit fails full validation because of an unmet `is_transferrable`/`cosigned_by_definer`/`spender_attested` restriction, the AA's already-credited balance in that asset (updated in `updateInitialAABalances`/`updateFinalAABalances`) cannot be paid out to the intended recipient through this code path. Depending on how the higher-level trigger-processing/bounce machinery treats this specific failure mode (this could not be conclusively traced to a graceful "bounce" versus a hard validation failure within the available search results), the outcome is either:
- The AA's response never validates, so the balance is effectively permanently stuck in the AA (loss of user funds sent to the AA, or the AA becomes unable to fulfill part of its intended payout logic for that asset), or
- The trigger is treated as bounced every time, meaning the AA can never forward this particular asset regardless of retries, since the underlying restriction never changes.

This matches "AA fund loss or freezing" from the validation criteria — funds credited to an AA in a restricted asset cannot be reliably sent onward, unlike the equivalent wallet-composer code path which proactively refuses to build such an invalid payment and returns a clear, immediate error instead of letting a bad unit reach the network/validation stage.

### Likelihood Explanation
Likelihood is Medium: this requires an attacker or ordinary user to (a) define a custom asset with `is_transferrable: false`/`spender_attested: true`/`cosigned_by_definer: true`, and (b) send that asset to an AA (or have the AA issue/hold it) such that the AA's own logic later tries to forward it to a third-party address that doesn't satisfy the restriction. No privileged access is required — any unprivileged asset issuer can define such an asset and any unprivileged unit poster can send it to a target AA, which is exactly the reachable attack surface named in the validation rules (posted unit + asset issuance + AA trigger).

### Recommendation
Add the same pre-checks used in `divisible_asset.js`/`indivisible_asset.js` to `aa_composer.js`'s `completePaymentPayload`/message-processing loop before composing a non-base asset payment:
- If `!objAsset.is_transferrable` and the destination is not the definer and the AA is not the definer, reject/bounce with a clear error.
- If `objAsset.cosigned_by_definer` and the definer is not among signers (which for AAs is always true since AAs can't cosign), reject/bounce.
- If `objAsset.spender_attested` and the destination address(es) are not attested, reject/bounce.

This surfaces the failure as an immediate, well-defined bounce (refunding the trigger sender per normal AA semantics) rather than letting an un-validatable unit be constructed, preventing silent freezing of AA-held balances in restricted assets.

### Proof of Concept
1. Definer `D` creates asset `X` with `is_transferrable: false`, `issued_by_definer_only: true` (standard non-transferrable asset, definable by any unprivileged user via a normal `asset` message) — validated by `validateAssetDefinition` in `validation.js`. [5](#0-4) 
2. `D` sends some amount of `X` to AA address `A` as part of a trigger (public, non-private asset — no special coordination needed since `is_transferrable:false` assets can still be paid to any address as a one-way transfer into the AA, and `updateInitialAABalances` credits the AA's balance for `X`). [6](#0-5) 
3. A subsequent (or the same) trigger causes the AA to attempt `messages: [{app:'payment', payload:{asset: "X", outputs:[{address: "{trigger.address}", amount: ...}]}}]` to pay the triggering user (not the definer `D`).
4. `completePaymentPayload`'s asset-loading step only checks `fixed_denominations` and `is_private`; it proceeds to build the payment with no error. [7](#0-6) 
5. When the resulting unit is fully validated, `validatePaymentInputsAndOutputs` will reject it because `X` is not transferrable and neither input nor output address is the definer: [8](#0-7) 
6. The AA's balance in `X` cannot be paid out through this response, unlike a wallet user who would have received an immediate, clean `"the asset is not transferrable and definer not found on either side of the deal"` error before ever attempting to build/broadcast the unit.
