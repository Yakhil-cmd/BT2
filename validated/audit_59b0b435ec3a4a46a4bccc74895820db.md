Double floor-division in `min-ustx-for-sats-amount` lets stakers under-collateralize sBTC bond rewards below the configured `stx-value-ratio`/`min-ustx-ratio` - ([File: stackslib/src/chainstate/stacks/boot/pox-5.clar])

### Summary
`min-ustx-for-sats-amount` computes the minimum STX a staker must lock to back a given sBTC bond position using two chained, truncating (floor) integer divisions instead of one combined computation. This mirrors the reported bug class: an equality intended to enforce "value locked/paid ≥ value credited" is broken by rounding, letting an attacker obtain reward-eligible sBTC-bond exposure while contributing less STX collateral than the ratio parameters intend.

### Finding Description
`min-ustx-for-sats-amount` is defined as:
```
(/ (* (/ (* stx-value-ratio sats-amount) u100) min-ustx-ratio) u10000)
``` [1](#0-0) 

This performs `(stx-value-ratio * sats-amount) / 100` (floor), then multiplies by `min-ustx-ratio` and divides by `10000` (floor again). Each `/` truncates, so the two-step formula can yield a strictly smaller result than the mathematically intended single-step `stx-value-ratio * sats-amount * min-ustx-ratio / 1_000_000`. This floor result is used as the *lower bound* gate in `register-for-bond`:
```
(asserts!
    (>= amount-ustx
        (min-ustx-for-sats-amount sats-total (get stx-value-ratio bond)
            (get min-ustx-ratio bond)))
    ERR_INSUFFICIENT_STX)
``` [2](#0-1) 

Because the intermediate `(/ (* stx-value-ratio sats-amount) u100)` step discards a remainder before it is ever multiplied by `min-ustx-ratio`, the staker's required `amount-ustx` can be lower than what a single non-truncated calculation would require for the same `sats-total`. `sats-total` (the sBTC amount) directly drives `target-yield` in `calculate-bond-rewards` — `(/ (/ (* total-sats (get target-rate bond)) u10000) u50)` — i.e., reward accrual is proportional to sBTC staked, not to the (rounded-down) STX actually locked. [3](#0-2) 

This is structurally the same defect class as the external report: a protocol invariant ("collateral/backing value must cover the credited value") is enforced via a rounded-down threshold check rather than a rounded-up one, so the attacker's contribution (`amount-ustx`) can be strictly less than the value backing the credit they receive (`sats-total`-driven rewards/weight), at every unit boundary where the double floor-division loses a remainder.

### Impact Explanation
If exploitable, this would let a staker register for sBTC bonds while locking STX below the intended `stx-value-ratio × min-ustx-ratio` backing ratio, i.e., signing weight/reward eligibility exceeding the STX value actually locked as collateral — matching the "High" impact bucket (signing weight or reward slots exceeding locked value). However, I could not fully verify magnitude/exploitability within the available context: the rounding loss per call is bounded by the ratio parameters' scale (division by `100` then `10000`), and I was unable to confirm (within the tool budget) whether repeated small `register-for-bond`/`unstake-sbtc` cycling can accumulate a materially exploitable gap, or whether other checks (e.g. `SIGNER_SET_MIN_USTX` minimums, allowlist `max-sats` caps) bound the practical loss to negligible dust that only favors the staker by sub-unit amounts each time. This is a genuine rounding-direction concern (the check should round the required minimum *up*, not down, to preserve the invariant `amount-ustx ≥ ratio(sats)` without loss), but I do not have concrete evidence it can be chained into a significant, protocol-level loss (unlike the original Morpho report, where `repaidShares` could round to exactly zero on a single call, giving unbounded free liquidation).

### Likelihood Explanation
Low-to-Medium. The bug is a one-line rounding-direction issue reachable by any allowlisted staker on every `register-for-bond` call (an ordinary unprivileged action), so the precondition to trigger it is trivial. But because it only ever *shaves fractions of a uSTX* off the required floor per call (bounded by the two division steps), turning it into a economically significant advantage likely requires many repeated small-amount registrations/unstakes, which I could not confirm is unblocked by other minimums (`SIGNER_SET_MIN_USTX`) or gas/step limits in the contract.

### Recommendation
Change `min-ustx-for-sats-amount` to compute the minimum required STX with a single combined, rounded-up division, e.g. `ceil(stx-value-ratio * sats-amount * min-ustx-ratio / 1_000_000)`, or explicitly round up at each intermediate step, so that `register-for-bond`'s `>= amount-ustx` check can never accept an `amount-ustx` smaller than the value truly implied by `stx-value-ratio`/`min-ustx-ratio` for the requested `sats-total`.

### Proof of Concept
Not independently reproduced within the available tooling/context. The mechanism is illustrated by picking `sats-amount`, `stx-value-ratio`, `min-ustx-ratio` such that `stx-value-ratio * sats-amount` is not an exact multiple of `100` (so the first `/` truncates a nonzero remainder) and that remainder, once carried forward, would have changed the final `/10000` result compared to the non-truncated single-step formula — i.e. `floor(floor(a*b/100)*c/10000) < floor(a*b*c/1_000_000)` for some integer `a,b,c`. This can be confirmed by direct arithmetic (e.g. small a/b/c triples chosen so the intermediate remainder pushes the final division below a multiple-of-10000 boundary), but I was not able to execute/verify a full end-to-end exploit chain (`register-for-bond` → reward accrual advantage) in this session due to tool/iteration limits.
