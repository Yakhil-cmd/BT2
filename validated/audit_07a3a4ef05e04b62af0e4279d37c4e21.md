### Title
Webhook signature is scoped to `repository.owner.login`, but event handlers act on `repository.full_name` — cross-organization webhook forgery bypasses the "authenticated organization = repository acted upon" binding (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the HMAC against using `repository_owner`, derived from the payload's `repository.owner.login` (or `organization.login`) field. But the handlers that actually act on the payload (`PushHandler`, pull-request handlers, etc.) look up the target `Stack`/`Repository` using a *different* payload field — `repository.full_name` — via `Repository.from_github_repo_name`. Nothing enforces that these two fields agree, so a party who legitimately controls the webhook secret for organization A can forge a payload whose `repository.owner.login` is `"A"` (to pass signature verification) while `repository.full_name` names a repository belonging to a different, victim organization "B" tracked by Shipit. This breaks the "organization that authenticated versus the repository that is written" binding required by the multi-org GitHub App model.

### Finding Description
Shipit supports multiple GitHub Apps/organizations, each with its own `webhook_secret` [1](#0-0) . Incoming webhooks are verified like this:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  # Fallback to the organization sub-object if repository isn't included in the payload
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

The secret used is resolved purely from `repository.owner.login` via `Shipit.github(organization:)`, which looks up the per-organization config keyed by that string: [3](#0-2) 

Once the signature check passes, the raw body is dispatched unchanged to all registered handlers for the event:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [4](#0-3) 

Every handler resolves the acted-upon repository from a *different* payload field, `repository.full_name`, through `Handler#repository_name`/`stacks`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [5](#0-4) 

`PushHandler` (and the pull-request handlers) then act on whatever stacks belong to that `full_name`-resolved repository, triggering a real GitHub sync/deploy pipeline based on attacker-supplied `after` SHA and branch ref:
```ruby
def process
  stacks
    .not_archived
    .where(branch:)
    .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [6](#0-5) 

`Repository.from_github_repo_name` splits `full_name` on `/` and does a plain `owner/name` lookup with no relation to which organization's secret validated the request: [7](#0-6) 

**The binding that should hold:** `organization authenticated by signature == owner of the repository the handler acts on`.

**Before the attack:** legitimate GitHub webhooks always have `repository.owner.login` equal to the owner segment of `repository.full_name`, so the two fields coincide and the binding holds implicitly (not by enforcement, but by GitHub's own payload construction).

**After the attacker's request:** an attacker who is a legitimate GitHub App/org admin for organization "A" registered in Shipit (and therefore knows/can trigger deliveries signed with A's `webhook_secret`, or otherwise obtains a valid signature for org A, e.g. via a public repo installed under org A) can POST a crafted JSON body directly to the public `WebhooksController#create` endpoint where:
- `repository.owner.login` = `"A"` (used only to pick the HMAC key for verification)
- `repository.full_name` = `"B/victim-repo"` (a stack tracked under a completely different organization "B", never checked against the verifying secret)

Because the HMAC is computed over the full raw body, the signature is technically "valid" for the crafted body signed with A's secret — the verification step never inspects `full_name` at all, and the handler never inspects `owner.login`. The equality `authenticated_org == acted_upon_repo.owner` is broken: the attacker authenticates as A but writes into B's `full_name`-resolved stack.

### Impact Explanation
This lets an entity that controls (or can forge a signature for) any one configured GitHub organization/App in a multi-org Shipit deployment force `GithubSyncJob`/`stack.sync_github` on stacks belonging to a totally different, unrelated organization, by supplying an arbitrary `after` commit SHA and target branch. Because push syncing drives what Shipit considers the deployable head for a stack, and Shipit's deploy pipeline builds/deploys from that head, this is a cross-repository write into another organization's deployment state driven by a signature that was never actually validated against that organization's secret — an unauthorized cross-organization deploy trigger. This matches the "cross-repository writes" / "unauthorized deploy" high/critical impact category defined in scope.

### Likelihood Explanation
Requires the attacker to already control (or otherwise possess a valid signature for) at least one of the GitHub organizations configured in a multi-organization Shipit deployment — a realistic, not-privileged-to-Shipit-itself scenario for large organizations onboarding many teams/orgs onto one shared Shipit instance. No Shipit account, API token, or session is needed; only the ability to produce one valid `X-Hub-Signature` for any configured org (e.g., by triggering a real webhook delivery from that org's repos and replaying it with a modified `repository.full_name`, since GitHub webhook payloads are otherwise attacker-influenceable JSON fields prior to signing on GitHub's side is not applicable here — the attacker directly POSTs to Shipit's public endpoint, bypassing GitHub delivery entirely, and only needs the shared secret bytes or a previously captured valid signature+body pair to splice `full_name`). This is a design-level control-flow gap rather than a narrow edge case, making exploitation straightforward for anyone in that trust position.

### Recommendation
Bind signature verification and payload processing to the *same* field. Either:
1. Verify the webhook signature using the organization derived from `repository.full_name` (or cross-check that `repository.owner.login` equals the owner segment of `repository.full_name` before verifying), and reject on mismatch; or
2. Pass the verified `organization` down to `Shipit::Webhooks::Handlers::Handler` and have `Handler#stacks`/`repository_name` only resolve repositories whose owner matches the organization that successfully authenticated the request.

### Proof of Concept
1. Configure Shipit with two GitHub orgs, `OrgA` and `OrgB`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`) [8](#0-7) .
2. Attacker controls `OrgA`'s webhook secret (e.g., is an admin of the GitHub App installed for `OrgA`).
3. Attacker crafts a `push` event JSON body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen-sha>",
     "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
   }
   ```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(OrgA_webhook_secret, body)` and POSTs it to `/github/webhooks`.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgA"`, fetches `OrgA`'s app via `Shipit.github(organization: "OrgA")`, and the HMAC checks out — request passes [9](#0-8) .
6. `PushHandler#process` resolves the target repository from `repository.full_name` = `"OrgB/victim-repo"`, finds `OrgB`'s stacks, and calls `stack.sync_github(expected_head_sha: <attacker-chosen-sha>)` [6](#0-5)  — a sync/deploy trigger on `OrgB`'s stack was executed using only `OrgA`'s credentials.
