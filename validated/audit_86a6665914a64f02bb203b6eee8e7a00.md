### Title
Payload-named pool addresses are invoked with no venue allowlist, letting a forged `routeXdr` execute arbitrary contract code inside the caller's signed auth tree and drain wallet tokens - (File: contracts/swap-aggregator/src/venues/soroswap.rs)

### Summary
`execute_strategy(sender, total_in, swap_xdr)` accepts a fully caller-supplied `StrategyPayload` whose `assets` registry names the pool contracts each hop will call. `Program::decode` type-checks indices and opcodes but never validates that a `pool` address is a genuine Soroswap/Aquarius/Phoenix/Sushi/Comet contract — there is no pool/venue allowlist anywhere in the router. The adapters then `invoke_contract(&ctx.hop.pool, ...)` on whatever address the payload names. Because `execute_strategy` runs under `sender.require_auth()`, any `require_auth`-protected call that rogue pool code makes against the `sender` (e.g. `token.transfer(sender, attacker, amount)` on an unrelated wallet token) is recorded as a sub-invocation of the sender's auth entry at simulation time and executes if the user signs the tree. This is the on-chain analog of the advisory: an untrusted catalog/quote (`routeXdr` built off-chain, potentially rewritten in transit) supplies content-unrestricted "commands" (pool addresses) that are invoked verbatim, with no default allowlist mitigation.

### Finding Description
- `StrategyPayload { amounts, assets, ops }` is fully attacker-controllable; instruction `idx_a` selects the pool contract purely by index into `assets` [1](#0-0) .
- `dispatch_hop` routes each hop to a venue adapter with no check that `hop.pool` is a legitimate pool of that venue [2](#0-1) .
- The Soroswap adapter (and likewise Phoenix/Sushi/Aquarius/Comet) calls `env.invoke_contract(&ctx.hop.pool, "swap", ...)` directly on the payload-supplied address [3](#0-2) .
- The only signature is the sender's, whose auth entry must cover the nested input `transfer`; any additional `sender`-authorized call a rogue pool makes rides inside that same auth tree [4](#0-3) .
- The threat model confirms the mechanism: the router "keeps no allowlist" of the addresses its payload names, a rogue callee's `token.transfer` from the caller "executes if the caller signs that tree," and "the loss is then the caller's wallet, not the routed amount" — bounded by nothing on-chain [5](#0-4) .
- The test fixture `RogueHopPool` demonstrates a payload-named "pool" that transfers an unlisted wallet token out of the victim under their own auth [6](#0-5) .

### Impact Explanation
Theft of user funds beyond the swapped amount: a user who signs a crafted route (e.g. served by a malicious or MITM'd quote response — the exact advisory scenario) loses arbitrary tokens from their wallet via a `transfer` sub-invocation, not just the routed `total_in`. Neither the router's `min_out` check, the measured-delta settlement, nor the controller's final risk gate bounds the loss.

### Likelihood Explanation
Likelihood hinges on the victim signing an auth tree containing the malicious sub-invocation. Simulation auto-populates that tree, so a wallet/SDK that doesn't diff the authorization (and a route fetched from a compromised quote channel — the cleartext-catalog analog) suffices. It is not a free exploit: the attacker cannot force the signature, and a careful client rejects extra children. Rated Medium likelihood; impact is High (arbitrary wallet token theft), net Medium-High.

### Recommendation
Maintain a governance-managed allowlist of legitimate pool addresses per venue (or per token pair) in the router, and reject any hop whose `pool` is not listed — the direct analog of the advisory's "allowlist the resolved command." Independently, adapters could assert pool identity by calling a cheap view (`get_reserves` shape, `share_id` for Aquarius) — though only an allowlist prevents arbitrary code execution, since a rogue pool can fake any view. Document that clients must reject auth trees with unexpected sub-invocations (already noted in the threat model).

### Proof of Concept
The repo's own fixture demonstrates it: `UnlistedPoolRouter::execute_strategy` decodes a payload, calls `invoke_contract(&route.hop_pool, "swap", ...)` on the payload-named address, and `RogueHopPool::swap` executes `token::Client::new(&env, &wallet_token).transfer(&victim, &to, &amount)` — a transfer of an unrelated token from the victim that simulation attaches to the caller's auth entry and enforcing mode accepts if signed [7](#0-6) . The production router is identically exposed: `Program::decode` performs only format/index checks and `dispatch_hop` places `ctx.hop.pool` on the call stack with no legitimacy check [8](#0-7) .

    pub fn execute_strategy(env: Env, sender: Address, total_in: i128, swap_xdr: Bytes) -> i128 {
        sender.require_auth();
        let route = RoutedSwap::from_xdr(&env, &swap_xdr).expect("route must decode");
        let router = env.current_contract_address();
        token::Client::new(&env, &route.token_in).transfer(&sender, &router, &total_in);

    }

/// Attacker-deployed "pool". `amount == 0` is the benign control.
#[contract]
pub struct RogueHopPool;

#[contractimpl]
impl RogueHopPool {
    pub fn __constructor(env: Env, victim: Address, token: Address, to: Address, amount: i128) {
        env.storage()
            .instance()
            .set(&symbol_short!("PLAN"), &(victim, token, to, amount));
    }

    pub fn swap(env: Env) {
        let (victim, wallet_token, to, amount): (Address, Address, Address, i128) = env
            .storage()
            .instance()
            .get(&symbol_short!("PLAN"))
            .expect("plan is set by the constructor");
        if amount > 0 {
            token::Client::new(&env, &wallet_token).transfer(&victim, &to, &amount);
        }
    }
}
