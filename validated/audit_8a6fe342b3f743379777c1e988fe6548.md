Malformed Private Payment Chain Element Triggers Uncaught `throw Error` and Crashes the Node - (File: `validation.js`)

### Summary
A private-payment counterparty can send a private payment chain whose intermediate element has an invalid `amount` field. This value is copied unchecked into `objValidationState.src_coin.amount` in `indivisible_asset.js`, and later, `validatePaymentInputsAndOutputs()` in `validation.js` hits an unchecked assertion (`throw Error("no src coin amount")`) instead of returning a normal validation error. Because this is a synchronous JS `throw` (not a callback error), it propagates as an uncaught exception, and `network.js`'s global `uncaughtException` handler deliberately re-throws to crash the whole node process — an analog of CVE-2023-37005's assertion-based DoS from a malformed message missing a required field.

### Finding Description
In `indivisible_asset.js`, `validatePrivatePayment()` handles the "transfer" branch of a private payment element: [1](#0-0) 

`prev_hidden_output` is taken directly from `objPrevPrivateElement.payload.outputs[input.output_index]` — fully attacker-controlled data supplied by the private-payment counterparty (`objPrevPrivateElement` is another element of the same chain, sent over the wire). Its `amount` field is never checked to be a valid positive integer before being copied into `objValidationState.src_coin.amount`: [2](#0-1) 

This `objValidationState` is then passed into `validation.validatePayment()`: [3](#0-2) 

Inside `validation.js`, `validatePaymentInputsAndOutputs()`'s `"transfer"` case for private fixed-denomination assets asserts on the same unchecked field with a hard `throw`, not a callback-based error: [4](#0-3) 

If `src_coin.amount` is not a positive integer (e.g. attacker sets it to a negative number, string, or omits it), `isPositiveInteger(src_coin.amount)` returns `false` and `throw Error("no src coin amount")` fires synchronously, inside a validation callback chain with no surrounding `try/catch`. This becomes an uncaught exception.

`network.js` explicitly treats any uncaught exception as fatal and re-throws to terminate the process: [5](#0-4) 

The private-payment chain is reachable from an unprivileged counterparty over the device-messaging channel, e.g. via `handlePrivatePaymentChains()` in `wallet.js`, which forwards to `network.handleOnlinePrivatePayment()`: [6](#0-5) [7](#0-6) 

which ultimately calls `privatePayment.validateAndSavePrivatePaymentChain()` → `indivisibleAsset.validateAndSavePrivatePaymentChain()` → `validatePrivatePayment()` → `validation.validatePayment()`, hitting the unguarded `throw`.

### Impact Explanation
This directly matches the CVE's bug class: a malformed message (missing/invalid required field, here `amount`) reaches an assertion (`throw Error`) instead of graceful validation rejection. Because the process-wide `uncaughtException` handler re-throws to crash the process, any counterparty able to send a private payment (recipient of a private-asset transfer, e.g. any wallet paired with the victim, or a hub forwarding such a message) can repeatedly crash the victim node — a network-wide denial-of-service condition preventing the node from confirming new units while it keeps restarting/crashing.

### Likelihood Explanation
The attacker only needs to be a private-payment counterparty (a normal wallet interaction reachable by anyone who can be paired with or send a private asset transfer to the victim, or route it through a hub) and craft one field (`amount`) of an intermediate chain element to be invalid. No special privilege, race condition, or complex setup is required, and the check that's missing (`isPositiveInteger` on `prev_hidden_output.amount`) is trivial to bypass since the whole private element payload is attacker-supplied JSON.

### Recommendation
In `indivisible_asset.js`'s `validatePrivatePayment()`, validate `prev_hidden_output.amount` with `ValidationUtils.isPositiveInteger()` (and `objAsset` cap constraints) before assigning it to `objValidationState.src_coin.amount`, returning `callbacks.ifError(...)` on failure instead of allowing the bad value to flow into `validation.js`. Additionally, harden `validatePaymentInputsAndOutputs()`'s `"transfer"` case in `validation.js` (lines 2416-2424) to return a normal validation error through `cb(...)`/`callback(...)` rather than `throw Error(...)`, since this code path processes attacker-supplied private-chain data, not just internally-generated invariants.

### Proof of Concept
1. As a wallet paired with the victim (or a hub relaying private payments), construct a private payment chain for a private, fixed-denomination (indivisible) asset with at least two elements.
2. In the non-head (earlier, "prev") element's `payload.outputs[output_index]`, set `amount` to an invalid value (e.g. `-1`, a string, or omit it) while keeping the `output_hash` consistent so `validateSpendProof`/output-hash checks in the head element still pass up to the point of the vulnerable check.
3. Send the chain to the victim node via `handlePrivatePaymentChains` (device message) or `handleOnlinePrivatePayment` (direct/hub relay).
4. The victim's validation reaches `indivisible_asset.js` `validatePrivatePayment()`, sets `objValidationState.src_coin.amount` to the malformed value, and calls into `validation.js`'s `validatePaymentInputsAndOutputs()`, which executes `throw Error("no src coin amount")` at line 2423-2424, crashing the node process via the global `uncaughtException` handler in `network.js`.
5. Repeat to repeatedly crash the target node.
