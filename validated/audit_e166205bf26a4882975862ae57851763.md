### Title
Missing Persistent Outpoint Tracking Allows a Single BTC Lockup to Be Credited to Multiple PoX-5 Bonds - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
`register-for-bond` accepts an L1 BTC lockup proof and, via `verify-l1-lockups`/`validate-l1-lockup`, credits the prover with `amount-sats` of collateral for a bond. Duplicate-outpoint protection is implemented only as an in-memory accumulator (`seen-outpoints`) that is created fresh on every call and discarded afterward, with no map persisted across separate `register-for-bond` invocations. As a result, the same real, single Bitcoin UTXO can be submitted as proof multiple times across different `bond-index` calls, crediting `amount-sats` more than once and inflating the staker's counted collateral/reward shares without any additional BTC ever being locked.

### Finding Description
`verify-l1-lockups` builds its de-duplication state purely as a local fold accumulator: [1](#0-0) 

`validate-l1-lockup` only checks `seen-outpoints` — a value scoped to that single call's `fold` — for duplicates: [2](#0-1) 

The proof-of-lock checks performed per output are: the reconstructed P2WSH script matches (staker, unlock-burn-height, staker-unlock-bytes, early-unlock-bytes), the claimed `unlock-burn-height` is `>=` the target bond's minimum required unlock height (not `==`), the BTC header is valid, and a Merkle proof ties the output to that header: [3](#0-2) 

Because these checks only bind an output to *a* bond whose minimum-unlock-height requirement is satisfied (an inequality, not an exact bond-index match), and because there is no contract-level map (e.g., a persistent `(map txid/output-index -> consumed)` table) recording that a given `(txid, output-index)` has already been consumed by a prior `register-for-bond` call, the caller can invoke `register-for-bond` a second time (for a different `bond-index`, or after their first membership has been superseded) using the *exact same* lockup tuple. `grep` over `pox-5.clar` confirms no persistent outpoint-tracking map exists anywhere outside the transient `seen-outpoints` field used inside a single `verify-l1-lockups` call.

`register-for-bond` uses the returned `sats-total` directly to compute `new-sbtc`/reward-share bookkeeping and stores it in `protocol-bond-memberships` (`amount-sats: uint`): [4](#0-3) [5](#0-4) 

This breaks the intended equality "sats credited to a staker as collateral == sats actually and currently locked on Bitcoin for that staker." One real BTC lockup can be counted as collateral for two (or more) separate bond periods simultaneously, each contributing to `protocol-bonds-total-staked`, signer/reward-share totals, and ultimately reward payouts — i.e., a double-counted commitment.

### Impact Explanation
This is a Critical-severity issue per the rules: it enables double-counting a BTC commitment across multiple bonds, letting a staker claim signer weight / bond reward-shares backed by BTC that is only locked once. This can result in reward payouts exceeding what the actually-locked BTC entitles the staker to, and inflates a staker's counted stake beyond their real collateral, undermining the reserve/solvency assumptions of the bond system.

### Likelihood Explanation
Exploitation only requires an unprivileged staker who is allow-listed for more than one bond period (or who is later re-added to a new bond's allowlist) — no admin, signer, or other party's key is needed. The only constraint is that the reused lockup's fixed on-chain `unlock-burn-height` must satisfy the second bond's `>=` minimum, which is realistic since bond minimum-unlock-height requirements are cycle-based and a single sufficiently-far-future lockup can satisfy several bonds' minimums.

### Recommendation
Persist consumed outpoints in a durable map (e.g., `(map {txid: (buff 32), output-index: uint} bool)`) that is checked and inserted at the point `validate-l1-lockup`/`register-for-bond` credits sats, so that a given Bitcoin output can back at most one bond membership for its entire lifetime (until legitimately released via unlock/early-exit). Additionally, consider binding the committed script (or the credited proof) to the specific `bond-index` (not just an inequality on unlock height) so a lockup cannot satisfy more than the bond it was created for.

### Proof of Concept
1. Staker `staker` locks BTC once into the canonical timelock P2WSH derived from `construct-lockup-output-script(staker, H, staker-unlock-bytes, early-unlock-bytes)`, where `H` is chosen larger than the minimum unlock height of both `bond-index=0` and `bond-index=1`.
2. `staker` calls `register-for-bond(bond-index=0, signer-manager, amount-ustx, ok({outputs: [proof], staker-unlock-bytes}), ...)`. `verify-l1-lockups`/`validate-l1-lockup` pass (script, header, merkle proof, `unlock-burn-height >= bond0.minimum-unlock-height`), crediting `amount-sats` to bond 0's membership/totals.
3. Once `staker`'s prior membership record is not blocking a new registration (e.g., after the bond-0 term’s natural progression or via any code path that clears/overwrites `protocol-bond-memberships`), `staker` calls `register-for-bond(bond-index=1, ...)` again with the identical `proof` tuple (same `tx`, `output-index`, `header`, `leaf-hashes`). Because `seen-outpoints` is scoped only to this second call's fold, and no persistent contract state records that this outpoint was already used for bond 0, the checks in `validate-l1-lockup` pass again, crediting the same `amount-sats` a second time — now counted toward bond 1's totals/rewards as well, without any new BTC being locked.
