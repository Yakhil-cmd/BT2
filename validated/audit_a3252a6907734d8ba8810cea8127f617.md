### Title
`StatusHandler#process` writes GitHub status onto every commit sharing a SHA across all repositories/stacks, regardless of which repo authenticated the webhook - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)` and applies the incoming status to **every** matching row, with no filter on the repository that the webhook's signature actually authenticated for. Every other handler in the engine scopes lookups through `Handler#stacks`, which is derived from `payload.dig('repository', 'full_name')`; `StatusHandler` is the outlier that never calls `stacks` or otherwise constrains by repository.

### Finding Description
The invariant that should hold is: `commit.stack.repository.full_name == payload['repository']['full_name']` for every `Commit` mutated by a `status` webhook. `StatusHandler` breaks this: [1](#0-0) 

`Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` matches on the bare `sha` column across the entire `commits` table, spanning every `Stack`/`Repository` in the installation. Compare this to `Handler#stacks`, which every other handler uses to scope by `repository.full_name`: [2](#0-1) 

The webhook signature check itself is scoped by *organization*, not by repository: [3](#0-2) 

so a validly-signed `status` webhook for one repository in an organization is not cryptographically bound to that repository at all inside `StatusHandler`; it is bound only by the `sha`. If two Stacks (potentially unrelated repositories, forks, or an org where the attacker legitimately controls one repo) contain a `Commit` row with the same `sha` (a routine occurrence for shared git history, cherry-picks, or fork networks), a status event authenticated for the attacker's own repository/organization will also mutate the status of the victim's commit, flipping `commit.status` via `add_status`, which can trigger `stack.schedule_merges` and continuous-deployment scheduling.

Separately, the `review_stacks_enabled` claim was investigated: `OpenedHandler#provision?` does have a real operator-precedence defect — [4](#0-3) 
`repository.review_stacks_enabled && repository.provisioning_behavior_allow_all? || (...) || (...)` binds `&&` tighter than `||`, so the `allow_with_label?`/`prevent_with_label?` branches are **not** gated by `review_stacks_enabled` at all. This is a genuine bug in `OpenedHandler`/`LabeledHandler`, but it only affects `ReviewStack` provisioning for pull requests on the repository whose `full_name` is in the payload (`repository.review_stacks`) — it does not, by itself, let an attacker act on a *different* repository's stack, and `LabeledHandler#respond_to_label_change?` does separately check `repository.review_stacks_enabled`. This precedence bug is real but is confined to same-repository review-stack provisioning, not a cross-tenant amplifier as framed in the question — it does not by itself produce a ship/block on an unrelated victim stack.

The composite scenario the question describes (an unprivileged attacker sending a forged `status` webhook that both crosses into a victim's stack via `StatusHandler` and simultaneously exploits the `provision?` precedence bug to force provisioning despite `review_stacks_enabled == false`) does not actually chain: `StatusHandler` never touches `review_stacks_enabled` or provisioning logic at all — it only writes `Status` rows via `commit.create_status_from_github!`. The `provision?` bug is confined to PR-open/label webhooks in `opened_handler.rb`/`labeled_handler.rb`, an entirely separate code path from `status_handler.rb`. So while the `StatusHandler` scoping bug (real, cross-repo write) and the `provision?` precedence bug (real, same-repo gating bug) are each independently notable, the question's specific combined exploit — a `ci/lint` status forcing ship/block on a `review_stacks_enabled: false` stack via the provisioning precedence bug — is not supported by the code: the status path and the provisioning path do not intersect.

### Impact Explanation
`StatusHandler`'s missing repository scoping is a real cross-tenant write: a status authenticated for repository A can flip CI state (`Status`) for a `Commit` belonging to Stack B in a different repository, provided the SHAs collide, which can cause deployable/blocking state changes and `stack.schedule_merges` to fire for the victim's stack. This matches "a payload for one repository mutating another's stack's commit." However, exploitability is gated by the attacker's ability to produce a `Commit` row with a colliding `sha` in the victim's stack (requires either legitimate SHA sharing via a fork/mirror relationship or a SHA1 collision), which is a nontrivial precondition, not something the attacker fully controls at will.

### Likelihood Explanation
Requires: (1) a validly-signed `status` webhook for a repository/organization the attacker controls or that shares a webhook secret, and (2) a genuine `sha` collision between a commit in the attacker's controlled repository/stack and a commit in the victim's stack (e.g., shared fork history). Condition (2) is not attacker-controllable in the general case and is not demonstrated to be trivially reachable in this codebase or test suite.

### Recommendation
Scope `StatusHandler#process` to commits belonging to the repository identified in the webhook payload, e.g. via `stacks.flat_map(&:commits).where(sha: params.sha)` or by joining through `Stack`/`Repository` using `Handler#stacks`, mirroring the pattern used by other handlers. Independently, fix the operator precedence in `OpenedHandler#provision?` (and confirm `LabeledHandler`'s already-correct gating) by parenthesizing `(repository.review_stacks_enabled && repository.provisioning_behavior_allow_all?)`.

### Proof of Concept
Not provided as a single reproducible minitest: the composite exploit chain described in the question (`status` webhook driving `provision?`'s `review_stacks_enabled` bypass to force a ship/block) has no code path connecting `status_handler.rb` to the provisioning logic in `opened_handler.rb`/`labeled_handler.rb`; they operate on disjoint webhook events and disjoint models. A valid, narrower PoC would test `StatusHandler` cross-repo writes in isolation (two stacks/repositories, two `Commit` rows sharing one `sha`, assert that processing a `status` webhook for repository A's `Commit` also mutates repository B's `Commit#statuses`), and a separate PoC for the `provision?` precedence bug (repository with `review_stacks_enabled: false` and `provisioning_behavior: allow_with_label`, PR opened with the label, assert a `ReviewStack` is still created). As posed, combining both into one "ci/lint forces ship/block via review_stacks precedence bug" scenario is not supported by the code.
