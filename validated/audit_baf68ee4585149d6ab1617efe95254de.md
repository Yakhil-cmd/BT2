### Title
Cross-repository CI status forgery via unscoped SHA lookup in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves target commits purely by `Commit.where(sha: params.sha)`, without ever comparing the verified webhook payload's `repository.full_name` to the `stack.repository.full_name` of the matched commit(s). Any GitHub organization/repo that is a legitimately configured Shipit tenant (its own `webhook_secret`) can push a real, correctly-signed `status` event for a commit SHA that happens to also exist in a different, unrelated stack, and Shipit will write that CI state onto the victim's commit.

### Finding Description
The broken binding is: `payload.dig('repository','full_name')` (attacker's own repo, e.g. `attacker/leaky-ci`) `!= commit.stack.repository.full_name` (`victim/prod`) for every `Commit` returned by `Commit.where(sha: params.sha)`, yet [1](#0-0)  proceeds to call `commit.create_status_from_github!(params)` regardless.

Path: `WebhooksController#create` parses the JSON body and dispatches to `Shipit::Webhooks.for_event(event)` handlers [2](#0-1) . Before dispatch, `verify_signature` calls `Shipit.github(organization: repository_owner)` and validates the HMAC signature against that organization's own `webhook_secret` [3](#0-2) . Because Shipit supports multiple GitHub organizations each with an independent `webhook_secret` [4](#0-3) [5](#0-4) , a webhook that is genuinely emitted by GitHub for the attacker's own installed repo passes signature verification cleanly — this check authenticates *who sent the request*, not *which commit/stack the payload is allowed to touch*.

`StatusHandler` then only requires `sha`/`state`/`branches` in its param schema [6](#0-5)  and never calls the base `Handler#stacks`/`repository_name` scoping helper that other handlers use, e.g. `PushHandler#process` explicitly scopes work to `stacks.not_archived.where(branch:)` derived from `repository_name` [7](#0-6) , whereas `StatusHandler#process` skips that entirely and iterates every `Commit` row matching the raw SHA across the whole database [1](#0-0) . `Commit#create_status_from_github!` then writes a `Status` scoped to that commit's own (victim) `stack_id` [8](#0-7) , and can trigger `deployable_status`/`commit_status` hooks and `ContinuousDeliveryJob` scheduling for the victim stack via `add_status` [9](#0-8) .

Exploit flow: attacker has `attacker/leaky-ci` configured as a Shipit tenant with its own `webhook_secret`. They craft a commit with tree/parents/author/committer/timestamps identical to a public commit already imported into `victim/prod`'s `Commit` table, producing an identical SHA-1. They push it and trigger a real GitHub `status` event (`state=success`) for that SHA from their own repo. The signature check passes using the attacker's own legitimate secret; `StatusHandler` finds the SHA match in `victim/prod`'s `Commit` row and writes a forged success status to it, with no comparison ever made between `attacker/leaky-ci` and `victim/prod`.

### Impact Explanation
This is a payload from one repository (`attacker/leaky-ci`) mutating another repository's stack/commit data (`victim/prod`'s `Status` record and derived `deployable_status`), matching the Critical impact category ("a payload for one repository mutating another's stack, commit, task or team"). If `victim/prod` has continuous deployment enabled, a forged `success` status can make a commit `deployable?` [10](#0-9)  and schedule `ContinuousDeliveryJob` [11](#0-10) , potentially triggering an unauthorized deploy. This is repeatable against any stack/commit whose SHA the attacker can reproduce, and is not limited to a single victim — any tenant with matching content can be targeted.

### Likelihood Explanation
Preconditions: (1) the attacker must control a GitHub org/repo that is already configured as its own Shipit tenant (own `webhook_secret` in the multi-tenant `secrets.github` config) — this requires the host to run Shipit in a multi-org/self-service mode where arbitrary repos can become tenants; (2) the attacker must produce a commit whose SHA-1 exactly matches one already present in the victim's `Commit` table, achievable deterministically by duplicating tree+parents+author+committer+timestamps+message of an existing public commit into their own repo (git hashing is fully content-deterministic, no cryptographic collision needed). Given both preconditions, the attack costs only a normal GitHub push and a normal GitHub-emitted `status` webhook — no secrets, sessions, or privileged roles are needed, and it is fully repeatable.

### Recommendation
In `StatusHandler#process`, scope the lookup by both `sha` and the verified `repository_name`, e.g. filter to `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { owner: ..., name: ... })` matching `payload.dig('repository','full_name')`, mirroring the `stacks`/`repository_name` scoping already used by `PushHandler` and other handlers, before calling `create_status_from_github!`.

### Proof of Concept
In `test/models/webhooks/handlers/status_handler_test.rb` (or equivalent), minitest plan:
1. Create two stacks/repositories: `victim_repo` (`victim/prod`) with `victim_commit` (fixed sha `SHA_X`), and `attacker_repo` (`attacker/leaky-ci`) with no commit at `SHA_X`.
2. Build a payload: `{ 'sha' => 'SHA_X', 'state' => 'success', 'branches' => [{'name'=>'master'}], 'repository' => {'full_name' => 'attacker/leaky-ci'} }`.
3. Assert the binding before: `payload.dig('repository','full_name')` (`'attacker/leaky-ci'`) `!= victim_commit.stack.repository.full_name` (`'victim/prod'`).
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)`.
5. Assert `victim_commit.reload.statuses.last.state == 'success'` — i.e., the write happened despite the mismatched repository binding, proving the vulnerability.
6. Assert the equality after processing still does not hold (`repository_name != victim stack.repository.full_name`), confirming no binding was ever enforced.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
