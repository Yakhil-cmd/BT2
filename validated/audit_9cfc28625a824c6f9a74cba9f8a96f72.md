### Title
Silent Fallthrough on `getBase64Hash` Failure Leads to Double Callback Invocation and Continued Processing of a Malformed Private Payment Chain - (File: network.js)

### Summary
In `handleSavedPrivatePayments()`'s inner `validateAndSave` closure, a failed hash computation is caught but execution is not stopped — the function falls through and continues to process the private payment chain with corrupted state, mirroring the "unchecked/ignored return-value-of-a-critical-operation" bug class from the reference report (there, `approve()`'s boolean success signal is discarded and the caller proceeds as if it succeeded; here, the failure signal from the `try/catch` around `objectHash.getBase64Hash()` is effectively discarded because the code doesn't `return` after handling it).

### Finding Description
`validateAndSave` computes `json_payload_hash` from the head private element's payload inside a `try` block: [1](#0-0) 

If `objectHash.getBase64Hash()` throws, the `catch` block logs the error, optionally notifies the peer, and calls `deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb)` — which removes the row from `unhandled_private_payments` and invokes `cb` to signal completion of processing this chain to the outer `async.each`. Critically, there is no `return` statement after this `catch` block, so execution falls through to the next lines, which build `key` using the now-`undefined` `json_payload_hash` and unconditionally call: [2](#0-1) 

This means `privatePayment.validateAndSavePrivatePaymentChain(...)` still runs against `arrPrivateElements` even though the code has just determined the payload is malformed and has already deleted the pending record and invoked `cb`. Depending on which callback (`ifOk`, `ifError`, or `ifWaitingForChain`) fires, `deleteHandledPrivateChain(...)` (and therefore `cb`) can be invoked a second time for the same row, or the chain can still be accepted/emitted via `eventBus.emit("new_direct_private_chains", ...)` and `assocNewUnits[row.unit] = true` despite the head element's payload having already failed hash computation.

### Impact Explanation
This can lead to processing a private payment chain whose payload could not even be hashed (implying malformed/corrupted local state), while simultaneously the "cleanup" path has already fired. Consequences include:
- Double invocation of the `async.each` iteratee callback `cb` for the same row, which can desynchronize the completion counting in `async.each`, causing `handleSavedPrivatePayments` to finish prematurely or to mis-signal `new_my_transactions` for units that were never fully validated.
- A malformed private-payment chain can still reach `ifOk`, resulting in `assocNewUnits[row.unit] = true` and the wallet believing it has received a validated private payment when the payload was actually corrupt, risking inconsistent private-payment state (fund tracking/freezing issues) for the receiving wallet.

### Likelihood Explanation
Reachable purely from data an unprivileged private-payment counterparty can control: any peer/hub can deliver a private-payment chain via `private_payment` messages that populate `unhandled_private_payments`, and a malformed `payload` object (e.g., something that throws during `objectHash.getBase64Hash`, such as circular references or invalid types) is fully attacker-controlled input, making this trivially triggerable by any device sending a private payment.

### Recommendation
Add a `return;` immediately after the `deleteHandledPrivateChain(...)` call inside the `catch` block in `validateAndSave` (network.js, around line 2476) so that execution does not fall through to build `key` and call `privatePayment.validateAndSavePrivatePaymentChain` a second time with a failed/undefined hash, and does not risk invoking `cb` more than once for the same row.

### Proof of Concept
1. Craft a `private_payment` message (or populate `unhandled_private_payments`) whose head element's `payload` throws when passed to `objectHash.getBase64Hash` (e.g., a payload containing a value that `objectHash` cannot serialize/hash, such as a circular reference or unsupported type nested inside `payload`).
2. Send it to a victim node/wallet so it lands in `unhandled_private_payments` and `handleSavedPrivatePayments` is triggered.
3. In `validateAndSave`, the `try` throws, `catch` logs and calls `deleteHandledPrivateChain(..., cb)` — deleting the row and calling `cb()`.
4. Execution falls through (no `return`), `key` is built with `json_payload_hash === undefined`, and `privatePayment.validateAndSavePrivatePaymentChain(...)` runs anyway; whichever callback fires (`ifOk`/`ifError`/`ifWaitingForChain`) calls `cb()` a second time (or emits `new_direct_private_chains`/marks the unit as new) for a chain that was already deemed unprocessable and deleted, demonstrating the double-callback / continued-processing-after-failure behavior.

					var validateAndSave = function(){
						var objHeadPrivateElement = arrPrivateElements[0];
						try {
							var json_payload_hash = objectHash.getBase64Hash(objHeadPrivateElement.payload, true);
						}
						catch (e) {
							console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
							if (ws)
								sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
							deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
						}
						var key = 'private_payment_validated-'+objHeadPrivateElement.unit+'-'+json_payload_hash+'-'+row.output_index;
						privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {
							ifOk: function(){
								if (ws)
									sendResult(ws, {private_payment_in_unit: row.unit, result: 'accepted'});
								if (row.peer) // received directly from a peer, not through the hub
									eventBus.emit("new_direct_private_chains", [arrPrivateElements]);
								assocNewUnits[row.unit] = true;
								deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
								console.log('emit '+key);
								eventBus.emit(key, true);
							},
							ifError: function(error){
								console.log("validation of priv: "+error);
							//	throw Error(error);
								if (ws)
									sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: error});
								deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
								eventBus.emit(key, false);
							},
							// light only. Means that chain joints (excluding the head) not downloaded yet or not stable yet
							ifWaitingForChain: function(){
								console.log('waiting for chain: unit '+row.unit+', message '+row.message_index+' output '+row.output_index);
								cb();
							}
						});
