### Title
Webhook signature is verified against an attacker-chosen organization while the payload's repository/commit data is trusted unscoped, allowing forged CI status and push events on a victim's stack - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's webhook secret to verify the HMAC signature against based on a field taken directly from the untrusted payload (`repository.owner.login`, falling back to `organization.login`), not from the resource that the event handler subsequently acts on. [1](#0-0) [2](#0-1) 

Once the signature passes, the actual handlers key off a different, independently attacker-controlled field of the same payload: `Handler#repository_name` reads `payload.dig('repository', 'full_name')` to resolve the target `Repository`/`Stack`, and `StatusHandler` doesn't even scope by repository at all — it matches `Commit.where(sha: params.sha)` across the entire installation. [3](#0-2) [4](#0-3) 

This breaks the equality that the design implicitly assumes: **organization authenticated by the signature == repository/commit written by the handler**. An attacker who controls (knows the configured `webhook_secret` for) one onboarded GitHub organization can forge a webhook whose `repository.owner.login`/`organization.login` names their own org (so signature verification passes using their own org's secret via `Shipit.github(organization: repository_owner)` / `GitHubApp#verify_webhook_signature`), while the `repository.full_name` or `sha` fields reference a victim organization's stack/commit. [5](#0-4) [6](#0-5) 

### Finding Description
- `WebhooksController#repository_owner` is computed purely from the JSON body of the incoming request, with no relation enforced to the repository that will later be resolved and mutated:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 
- `verify_signature` uses this attacker-supplied `repository_owner` to pick which `GitHubApp` (and therefore which `webhook_secret`) to validate the `X-Hub-Signature` against:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [7](#0-6) 
`Shipit.github` looks up per-organization config (`github_app_config`) so different organizations can have different secrets. [8](#0-7) 
- After the signature check succeeds, `Handler#stacks` resolves the target repository using a *different* field of the same untrusted body — `repository.full_name` — with no cross-check that its owner matches the organization that was actually verified:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end
def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 
- `StatusHandler` is even weaker: it never resolves a repository/stack scope at all, it simply matches any `Commit` in the entire installation by raw `sha` and writes a status onto it:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [4](#0-3) 

So the binding broken is: `organization authenticated by webhook signature` ≠ `repository/commit actually written by the handler`. Before an attack, these two are expected to coincide because a legitimate GitHub-originated webhook always signs the exact payload it sends, with the exact repository it describes belonging to the org whose secret produced the signature. After the attack, an attacker directly POSTs a self-crafted JSON body to the webhooks endpoint, setting `repository.owner.login`/`organization.login` to their own (attacker-known-secret) org while setting `repository.full_name` (for push/check_suite events) or `sha` (for status events) to reference a victim's stack/commit, and signs the raw body with their own org's known `webhook_secret`.

### Impact Explanation
For `StatusHandler`, this lets an unprivileged party (anyone who knows the `webhook_secret` of *any* organization onboarded to the Shipit instance) inject a forged `success`/`failure` `CommitStatus` onto an arbitrary commit belonging to a completely different, victim organization's stack, since matching is global (`Commit.where(sha: ...)`) and never checks that the commit's stack/repository corresponds to the authenticated org. If that stack relies on CI status for `deployable?`/continuous deployment gating, this can flip a commit from non-deployable to deployable and precipitate an unauthorized deploy — meeting the Critical bar ("an unauthorized deploy"). For `PushHandler`/`CheckSuiteHandler`, the same organization mismatch lets a forged event trigger `stack.sync_github` or check-run refresh actions scoped to a victim stack whose owner differs from the org that signed the request.

### Likelihood Explanation
Exploitation requires the attacker to know the `webhook_secret` configured for at least one organization onboarded to the same Shipit instance (e.g., their own organization's project that also uses this Shipit deployment) — this is a realistic scenario in any shared/multi-tenant Shipit deployment serving multiple GitHub organizations, and does not require any Shipit session, API token, or GitHub write access to the victim repository. It only requires crafting a raw HTTP POST with a valid HMAC computed with a secret the attacker legitimately possesses for their own org.

### Recommendation
Cross-validate that the organization used to select the webhook secret (`repository_owner`) matches the actual owner embedded in `repository.full_name` (and any repository/commit resolution performed by handlers) before verification succeeds, and reject the request otherwise. Additionally, scope `StatusHandler` (and any handler resolving commits directly by `sha`) to the repository named in the payload rather than matching commits globally, e.g. by joining through `Repository.from_github_repo_name(repository_name)` before filtering `Commit.where(sha: ...)`.

### Proof of Concept
1. Attacker is a member/admin of `attacker-org`, an organization already onboarded to this Shipit instance, and therefore knows `attacker-org`'s configured `webhook_secret` (the same secret entered on GitHub's webhook config page for that org).
2. Attacker crafts a JSON body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/decoy" },
  "sha": "<victim commit sha, known publicly on GitHub>",
  "state": "success",
  "context": "ci/build"
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(body, attacker-org's webhook_secret)>` and POSTs it to the Shipit webhooks endpoint with `X-Github-Event: status`.
4. `verify_signature` computes `repository_owner = "attacker-org"`, loads `attacker-org`'s `GitHubApp`, and the HMAC check passes because the attacker legitimately knows that secret. [9](#0-8) 
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, which matches the victim's commit (belonging to `victim-org`, unrelated to `attacker-org`), and calls `commit.create_status_from_github!(params)`, writing a forged "success" status onto a commit the attacker has no relationship to. [4](#0-3) 

Note on completeness: I could not fully trace whether the victim stack's `deployable?`/continuous-deployment logic in `app/models/shipit/commit.rb`, `app/models/shipit/undeployed_commit.rb`, and `app/models/shipit/stack.rb` would directly convert this forged status into an automatic unauthorized deploy versus merely displaying a misleading status in the UI — this would need to be confirmed by reading those files directly (their `deployable?`/`continuous_deployment` logic) to fully substantiate the Critical severity claim.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
