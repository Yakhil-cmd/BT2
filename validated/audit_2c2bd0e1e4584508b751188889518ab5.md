### Title
CCMenu API token authorizes only a generic `read:stack` permission but is never bound to the specific stack it was issued for, allowing cross-stack read access - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
The CCMenu integration is designed to hand out a per-stack, unauthenticated (session-less) URL that exposes a stack's build/deploy status. In practice the token it relies on is not scoped to any particular stack, and the endpoint that consumes the token also bypasses the one mechanism (`Api::BaseController#stack`/`#stacks`) that would otherwise restrict a scoped `ApiClient` to its own stack. The result is that a `read:stack` CCMenu token minted for stack A can be used to read the build status of any other stack B on the same Shipit instance, simply by changing the `stack_id` in the URL.

### Finding Description
`CCMenuUrlController#client` mints (or reuses) the `ApiClient` used to authenticate CCMenu requests: [1](#0-0) 

`find_or_create_by!(creator: current_user, name: 'CCMenu Client')` only matches on `creator` and `name` — it never sets or matches on `stack:`. So the very first time a user requests a CCMenu URL for any stack, a single `ApiClient` record with `stack_id: nil` and permission `read:stack` is created and is thereafter reused (and returned) for every subsequent CCMenu URL that same user requests for any other stack.

Separately, `Shipit::Api::BaseController` implements stack scoping specifically for API clients bound to one stack: [2](#0-1) 

But `Api::CCMenuController` overrides `stack` and bypasses this scoping entirely, resolving the stack directly and unconditionally from the unscoped `Stack` model: [3](#0-2) 

`require_permission :read, :stack` only checks that the string `"read:stack"` is present in `ApiClient#permissions` — it never validates that the requested `stack` matches `current_api_client.stack_id`: [4](#0-3) 

The binding that should hold is: `stack the token authorizes == stack the endpoint touches`. Because (a) the token is never bound to a stack in the first place, and (b) even the generic scoping mechanism (`stacks`) that exists elsewhere in the same base controller is skipped here, the equality never holds — any `stack_id` supplied in the URL is served.

### Impact Explanation
A CCMenu URL is explicitly designed to be embedded in third-party CI dashboard tools without further authentication (`api_stack_ccmenu_url` + `?token=...`), i.e., its whole purpose is to be shared/exposed outside of a logged-in session. Whoever holds one CCMenu token — meant to expose only one stack's status — can enumerate `stack_id` values and read the build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`, `name`) of every stack hosted on the Shipit instance, including stacks/repositories the token holder was never granted visibility into. This is an unauthenticated (token-only) cross-stack read of stack state, matching the High-impact criterion "unauthenticated read of stack state, task streams or deploy output."

### Likelihood Explanation
No special privilege is required beyond being any existing Shipit user who is allowed to request a single CCMenu URL for a stack they can see (a normal, low-privilege action any authenticated team member can perform via `CCMenuUrlController#fetch`, reachable at the standard `ShipitController` authentication level). Once minted, the resulting token/URL — by design meant to be pasted into external dashboards — silently authorizes reading every other stack simply by tampering with the `stack_id` path/query parameter. This requires no signature forgery, no credential theft, and no elevated GitHub team membership.

### Recommendation
- Bind the `ApiClient` created in `CCMenuUrlController#client` to the specific stack (`stack:` attribute) and include `stack` in the `find_or_create_by!` lookup key, so a distinct scoped client is created per stack.
- Remove the `stack` override in `Api::CCMenuController` and instead reuse `Api::BaseController#stack`/`#stacks`, so scoped clients are restricted to their own `stack_id`, consistent with the rest of the API.
- Alternatively, explicitly assert `current_api_client.stack_id == stack.id` (when the client is scoped) before rendering CCMenu data.

### Proof of Concept
1. As user U (member of a Shipit team), call `GET /stacks/:stack_A_id/ccmenu_url` (routed to `CCMenuUrlController#fetch`) → response includes `ccmenu_url` with `token=T`.
2. `T` decrypts to an `ApiClient` with `permissions: ["read:stack"]` and `stack_id: nil` (see `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')`).
3. Request `GET /api/stacks/:stack_B_id/ccmenu.xml?token=T` for an arbitrary stack B that U was never granted a CCMenu link for. `Api::CCMenuController#authenticate_api_client` authenticates via `ApiClient.authenticate(params[:token])` successfully (token is valid), `require_permission :read, :stack` passes because the client has `"read:stack"`, and `#stack` resolves stack B unconditionally via `Stack.from_param!(params[:stack_id])`.
4. The response renders stack B's `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, and `webUrl` — data the token was never intended to expose.
