## Analysis

The Ditto report describes a class of bug where **an unprivileged actor can cheaply grow a globally-shared state table with no hard cap, and every later computation must scan that entire table linearly** — eventually degrading or halting core protocol operations.

The closest reachable analog in `ocore` is the in-memory global cache `storage.assocUnstableMessages`, which accumulates `data_feed` / `definition` / `system_vote` / `system_vote_count` messages from **every currently-unstable unit** network-wide, and is fully scanned (unbounded `for...in` loop) by core validation/execution paths that any unprivileged AA-trigger sender can invoke.

### Title
Unbounded growth of `storage.assocUnstableMessages` enables linear-cost DoS on AA data-feed evaluation - (File: `data_feeds.js`)

### Summary
Every unit carrying a `data_feed`, `definition`, `system_vote`, or `system_vote_count` message is added to the global in-memory map `storage.assocUnstableMessages` and stays there until the unit stabilizes [1](#0-0) . Multiple hot paths — most notably `dataFeedExists()` and `readDataFeedValue()`, which back the `in data feed` / `data_feed` oscript primitives used by AA triggers — perform a full `for (var unit in storage.assocUnstableMessages)` scan of this table on every invocation [2](#0-1) [3](#0-2) . Any unprivileged address can post many cheap units carrying `data_feed` messages (bounded only by `MAX_DATA_FEEDS_PER_MESSAGE`/fees, not by any global cap) to inflate this table while those units remain unstable, increasing the CPU cost of *every* subsequent AA trigger evaluation across the whole node, network-wide — the same "unrestricted registration → linear-time computation on every op" pattern flagged in the Ditto report for validator registration.

### Finding Description
`storage.assocUnstableMessages[unit]` is populated unconditionally for any unit with one of these message apps, with no limit on the total number of unstable units tracked simultaneously [1](#0-0) . Entries are only removed once the corresponding unit's MCI becomes stable [4](#0-3) , i.e., after real consensus-driven stabilization latency, not proportional to any spam-prevention mechanism specific to this table.

Several core functions perform a full, unfiltered iteration over this entire map for every call, regardless of how many entries are actually relevant to the caller:
- `dataFeedExists()` (used to evaluate the `in data feed` oscript primitive during AA execution) [5](#0-4) 
- `readDataFeedValue()` (used to evaluate the `data_feed` oscript primitive) [6](#0-5) 
- `getUnconfirmedAADefinition()` / `getUnconfirmedAADefinitionsPostedByAAs()`, used when resolving AA definitions during AA-to-AA calls [7](#0-6) 
- `hasUnstableOpVoteCount()` / `getUnstableVotes()`, used in main-chain vote counting [8](#0-7) [9](#0-8) 

Because `dataFeedExists`/`readDataFeedValue` are invoked once per `in data feed`/`data_feed` primitive evaluated during **every** AA trigger execution — and AA trigger execution is a mandatory, synchronous step of `stabilizeMci()` that runs for every AA-addressed payment as soon as its MCI stabilizes [10](#0-9)  — an attacker can post a burst of low-cost units each carrying a `data_feed` message (limited only by `MAX_DATA_FEED_NAME_LENGTH`/`MAX_DATA_FEED_VALUE_LENGTH`/`MAX_DATA_FEEDS_PER_MESSAGE` per-message size limits [11](#0-10) , not by any cap on the number of concurrently-unstable such units) to keep `assocUnstableMessages` inflated for as long as those units remain unstable. Every AA trigger relying on an oracle (a very common pattern) then pays a cost proportional to the *entire* inflated table, not just to the oracle addresses it queries — mirroring the "each new validator occupies space, and many computations run linear time over validator state" root cause from the report.

### Impact Explanation
Any AA that uses `in data feed`/`data_feed` (extremely common for price oracles, DEX AAs, prediction markets, etc.) is slowed by this attack. Since AA trigger execution happens synchronously as part of `stabilizeMci()`, sufficiently degraded per-trigger performance directly slows down the node's ability to process the queue of pending AA triggers after each MCI advance, which can cascade into delayed processing of new units on affected nodes and, in a severe burst, contend with `handleAATriggers()`'s ability to keep up — matching the "network unable to confirm new units" category. It can also cause specific AAs with tight gas/time budgets to time out or behave inconsistently across nodes if the scan cost differs due to timing of message arrival vs. stabilization, risking disagreement about trigger outcomes.

### Likelihood Explanation
The only real friction is standard per-unit fees and existing message-size caps (`MAX_DATA_FEEDS_PER_MESSAGE`, `MAX_MESSAGES_PER_UNIT`), which limit throughput but impose no cap on the number of *simultaneously unstable* data-feed-bearing units network-wide. Any address (no whitelist or special role required) can compose and broadcast such units through the normal wallet/composer path [12](#0-11) , making this reachable by an ordinary unprivileged unit poster.

### Recommendation
- Impose a hard cap on the number of tracked unstable units (or unstable messages) inside `storage.assocUnstableMessages`, rejecting/deferring further additions once the cap is hit, analogous to Ditto's `max_n_validators`.
- In `dataFeedExists()`/`readDataFeedValue()`, avoid a full unfiltered table scan: index unstable data-feed messages by author address (similar to how the stable data feeds are indexed via `kvstore` key prefixes) so lookups are proportional to the number of relevant oracle addresses, not to the total size of `assocUnstableMessages`.
- Consider fee scaling (e.g., increasing the `data_feed` message fee) proportional to the current size of the unstable-message backlog to economically disincentivize inflating this table.

### Proof of Concept
1. Attacker repeatedly composes and broadcasts low-value units, each containing a valid `data_feed` message (well within `MAX_DATA_FEEDS_PER_MESSAGE`/`MAX_MESSAGES_PER_UNIT`), from many throwaway addresses, at a rate the network fee model permits.
2. Because stabilization requires witness-driven MC advancement, a substantial number of such units remain in `storage.assocUnstableMessages` simultaneously [1](#0-0) .
3. Any legitimate AA trigger that evaluates `in data feed`/`data_feed` (e.g. a price-oracle-based AA) now pays the cost of a full `for (var unit in storage.assocUnstableMessages)` scan over the inflated table on every trigger [2](#0-1) , degrading the throughput of `handleAATriggers()` invoked from `stabilizeMci()` for every MCI advance [10](#0-9) , network-wide, for the duration the attacker sustains the flood.

function getUnstableVotes(emergency_count_command_timestamp) {
	let votes = [];
	for (let unit in storage.assocUnstableMessages) {
		for (let m of storage.assocUnstableMessages[unit]) {
			if (m.app === 'system_vote' && m.payload.subject === 'op_list') {
				const { timestamp, author_addresses, sequence, level } = storage.assocUnstableUnits[unit];
				if (sequence !== 'good')
					continue;
				if (emergency_count_command_timestamp - timestamp < constants.EMERGENCY_COUNT_MIN_VOTE_AGE) {
					console.log('unstable vote from', author_addresses, 'is too young');
					continue;
				}
				const arrOPs = m.payload.value;
				votes.push({ timestamp, level, author_addresses, arrOPs });
			}
		}
	}
	return votes;
}

function getUnconfirmedAADefinition(address) {
	for (var unit in assocUnstableMessages) {
		var objUnit = assocUnstableUnits[unit] || assocStableUnits[unit]; // just stabilized
		if (!objUnit)
			throw Error("unstable unit " + unit + " not in assoc");
		if (objUnit.sequence !== 'good')
			continue;
		var messages = assocUnstableMessages[unit];
		for (var i = 0; i < messages.length; i++) {
			var message = messages[i];
			if (message.app !== 'definition')
				continue;
			var payload = message.payload;
			if (payload.address === address)
				return payload.definition;
		}
	}
	return null;
}

// arrAddresses is an array of AA addresses whose definitions are posted by other AAs
function getUnconfirmedAADefinitionsPostedByAAs(arrAddresses) {
	var payloads = [];
	for (var unit in assocUnstableMessages) {
		var objUnit = assocUnstableUnits[unit] || assocStableUnits[unit]; // just stabilized
		if (!objUnit)
			throw Error("unstable unit " + unit + " not in assoc");
		if (!objUnit.bAA)
			continue;
		assocUnstableMessages[unit].forEach(function (message) {
			if (message.app !== 'definition')
				return;
			var payload = message.payload;
			if (arrAddresses.indexOf(payload.address) >= 0)
			payloads.push(payload);
		});
	}
	return payloads;
}
