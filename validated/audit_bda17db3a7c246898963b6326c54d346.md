## Title
Stack-scoped `ApiClient` tokens can read any stack's build status via `CCMenuController` — ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Finding Description
`Shipit::ApiClient` supports scoping a token to a single stack via `stack_id`. The scoping is enforced centrally in `Api::BaseController`: [1](#0-0) 

`stacks` restricts the queryable set to the client's own `stack_id` when one is set, and every controller that calls the inherited `stack` helper (e.g. `Api::StacksController`) is protected by this scoping — an `ApiClient` created with `stack: shipit` (see the `here_come_the_walrus` fixture) can only see that one stack through `stacks`/`stack`.

`Api::CCMenuController`, however, overrides `stack` and bypasses the scoped lookup entirely: [2](#0-1) 

It only enforces the *generic* permission bit `read:stack` via `require_permission :read, :stack`, which is checked with `ApiClient#check_permissions!`: [3](#0-2) 

`check_permissions!` only checks that the string `"read:stack"` is present in the client's `permissions` array — it never consults `stack_id`. Because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly instead of the scoped `stacks.from_param!`, any token carrying `read:stack` — including one that was deliberately scoped by an administrator to a single stack — can retrieve the CCMenu XML status for **any** stack in the installation simply by changing the `stack_id` request parameter.

This is the same class of bug as the external report: a value that a privileged party authorized/verified for one specific target (the stack a scoped token is bound to) is silently decoupled from the value actually acted upon at execution time (the stack whose data is rendered), because the enforcement path (`CCMenuController#stack`) diverges from the trusted path (`BaseController#stack`/`stacks`).

### Impact Explanation
An `ApiClient` token intentionally scoped to Stack A (e.g. issued for a CI dashboard or a low-privilege integration and expected to only ever see Stack A) can be replayed against `/api/stacks/:stack_id/cc_menu.xml` for Stack B, C, … to read: stack name, build activity, last build status/label/time, and web URL for stacks the token was never authorized to see. This is an authorization-scope escape (cross-stack unauthorized read of stack state), matching the "escalation into authorization ... unauthenticated/unauthorized read of stack state" High-impact bucket in scope for this exercise.

### Likelihood Explanation
Any holder of a valid `ApiClient` authentication token with `read:stack` permission (which is the default/common permission bundled onto many clients, including scoped ones) can trigger this with a single unauthenticated-scope-bypassing GET request — no special privileges, repository write access, or session are required beyond possessing the token that was already issued to them for a narrower purpose. This is a straightforward parameter-substitution attack.

### Recommendation
Make `Api::CCMenuController#stack` use the scoped lookup consistently with the rest of the API, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
where `stacks` is inherited from `Api::BaseController` and respects `current_api_client.stack_id`. Remove the local override that calls `Stack.from_param!` directly.

### Proof of Concept
1. Admin creates a scoped `ApiClient` bound to `stack_id` = Stack A, permissions `["read:stack"]` (as done via `CCMenuUrlController#client` pattern or the admin UI), and hands its `authentication_token` to a third party.
2. The third party requests:
   `GET /api/stacks/<Stack-B-param>/cc_menu.xml?token=<TokenScopedToStackA>`
3. `CCMenuController#authenticate_api_client` authenticates the token successfully; `require_permission :read, :stack` passes because `permissions` includes `read:stack`.
4. `CCMenuController#stack` resolves Stack B via `Stack.from_param!(params[:stack_id])`, ignoring the token's `stack_id` binding, and the controller renders Stack B's build status — data the token was never authorized to access. [4](#0-3) [1](#0-0)
