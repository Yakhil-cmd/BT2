The test at `flows.rs:3408` documents a real analog: `recapitalize` can pay out an "unfunded refund" — draining actual pool tokens while the cash book still shows them. Let me verify the recapitalize implementation.### Title
Unfunded recapitalize refund drains pool custody and leaves supplier withdrawals reverting on the token transfer - (File: contracts/pool/src/ops/recapitalize.rs)

### Summary
`recapitalize` credits only `min(amount, backing_shortfall)` to the cash book but unconditionally transfers `amount - applied` back to `payer`, trusting that the full `amount` was actually delivered. When the received tokens are less than `amount`, the pool pays real custody for tokens it never got, while the `cash` book — which the withdraw liquidity guard reads — still shows them as available. A later supplier `withdraw` passes the book-based `require_reserves` check and then reverts inside the SAC token transfer for lack of balance, exactly mirroring the Ubiquity `collectRedemption` failure where bookkeeping funds owed to users were drained by another path.

### Finding Description
The original report's class: funds recorded as owed to users are spendable through a second path, so the claim fails at the token transfer despite the books showing them covered. In XOXNO Lending the pool keeps `cash` as the reserve book (INV-ACCT-02) and the withdraw path only checks that book before sending tokens.

`ops::recapitalize::accounting` computes `applied = amount.min(backing_shortfall)` and `refund = amount - applied` from the caller-supplied `amount`, then `apply` executes `cache.transfer_out(&payer, outcome.refund)` — a real token transfer — while `credit_cash(applied)` may credit far less, or nothing. [1](#0-0)  The refund is denominated in the caller's requested `amount`, not in measured receipt of what actually arrived; INV-ACCT-03's measured-receipt rule covers the *credit*, but the *refund* is computed off `amount` regardless. [2](#0-1) 

The withdraw guard reads the `cash` book, not the token balance, so after an unfunded refund the book still reports the supplier's backing while custody is gone. The in-repo test `test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody` proves exactly this: after `recapitalize` refunds the pool's entire custody, a supplier's `withdraw` passes `require_reserves` and fails inside the SAC transfer with `BalanceError = 10`, not any pool guard. [3](#0-2) 

Reachability: `LiquidityPool::recapitalize` is `#[only_owner]` (the controller), but `recapitalize` is a public controller entrypoint any unprivileged payer can invoke with an attacker-chosen `amount`; the pool relies on the controller having transferred `amount` in, and the refund is computed and paid out of pool custody against that claimed figure rather than a measured balance delta. If actual receipt (e.g., measured credit, a non-standard/fee token leg, or any gap between the requested and delivered amount) falls short of `amount`, the refund pays out suppliers' tokens.

### Impact Explanation
Theft of user funds / temporary freezing of funds: custody backing supplier shares is paid out as a refund to the recapitalize caller, while `cash` still records the reserve. Suppliers' subsequent `withdraw` calls revert inside the token transfer — the same user-facing failure as `collectRedemption` — until enough cash accrues from repayments or a real recapitalization restores custody.

### Likelihood Explanation
Requires a recapitalize call where delivered tokens are less than the claimed `amount`. `recapitalize` is a permissionless controller path and the pool trusts the parameter instead of measuring its own balance increase, so any payer who can cause a receipt shortfall (or any shortfall credited market where the refund still computes off `amount`) triggers the drain. Impact is capped by the pool's token balance, and medium severity matches the original.

### Recommendation
In `ops::recapitalize::apply`/`accounting`, measure the pool's actual token balance delta around the credit (as the flash-loan path already does per the "Security notes" in `contracts/pool/src/lib.rs:34-36`) and base `refund` on the measured receipt — `refund = received - applied` — instead of the caller-supplied `amount`. Alternatively, compute the shortfall first, pull only `min(amount, shortfall)` in, and never transfer out within recapitalize.

### Proof of Concept
Encoded by `contracts/pool/tests/flows.rs:3408-3483` (`test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody`):
1. Supplier deposits `deposit` tokens; `cash` book equals token balance.
2. Call `pool.recapitalize(hub_asset, payer, custody)` with `amount = custody` while delivering nothing: `applied = min(custody, shortfall=0) = 0`, `refund = custody`; pool token balance goes to 0 while `cash` still shows `deposit`.
3. Supplier calls `withdraw` for the full position: `require_reserves` passes against the stale book, then the SAC `transfer` reverts with `BalanceError = 10`; supplier receives nothing and the book still overstates custody after rollback. [4](#0-3)

pub(crate) fn accounting(
    env: &Env,
    hub_asset: HubAssetKey,
    amount: i128,
) -> RecapitalizationOutcome {
    require_nonneg_amount(env, amount);
    let mut cache = ops::renewed_market(env, &hub_asset);

    let applied = amount.min(guards::backing_shortfall(&cache));
    let refund = amount
        .checked_sub(applied)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow));

    cache.credit_cash(applied);
    cache.commit();

    RecapitalizationOutcome {
        cache,
        mutation: PoolAmountMutation {
            actual_amount: applied,
        },
        refund,
    }
}

Token-funded supply, repayment and recapitalization credit the pool's measured

/// reads the book, not the balance, so it admits exits that then fail inside
/// the SAC transfer. The market reports itself solvent and cannot pay.
#[test]
fn test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody() {
    let t = TestSetup::new();
    let token = token::Client::new(&t.env, &t.asset);
    let token_admin = token::StellarAssetClient::new(&t.env, &t.asset);
    let payer = Address::generate(&t.env);
    let receiver = Address::generate(&t.env);

    // A legitimate supplier, with custody moved in as the controller would.
    let deposit = 10_000_000_000i128;
    token_admin.mint(&t.pool, &deposit);
    let supplied = t
        .client()
        .supply(&t.sup(0, deposit))
        .get_unchecked(0)
        .position
        .scaled_amount;
    assert_eq!(
        t.state_snapshot().cash,
        token.balance(&t.pool),
        "fixture guard: book and custody must still agree after the deposit"
    );

    // Drain every token via an unfunded refund.
    let custody = token.balance(&t.pool);
    t.client().recapitalize(&hub(&t.asset), &payer, &custody);
    assert_eq!(token.balance(&t.pool), 0, "custody is gone");

    let book = t.state_snapshot().cash;
    assert!(
        book >= deposit,
        "the book still claims more than the supplier's deposit: {book}"
    );

    // The supplier's exit clears the pool's own liquidity guard -- the book
    // says the cash is there -- and then fails in the token transfer.
    let outcome = t
        .client()
        .try_withdraw(&receiver, &false, &t.wdr(supplied, i128::MAX, 0));
    assert!(
        outcome.is_err(),
        "the withdraw cannot be paid, so it must fail"
    );
    // The failure must come from custody, not from a pool guard. The SAC
    // reports insufficient balance as its own contract error `BalanceError = 10`.
    // The asserts check that exact code and that neither pool liquidity guard
    // fired: `require_reserves` read the book and let the exit through.
    const SAC_BALANCE_ERROR: u32 = 10;
    match outcome {
        Err(Ok(err)) => {
            assert_ne!(
                err,
                Error::from_contract_error(CollateralError::InsufficientLiquidity as u32),
                "the pool's own liquidity guard must NOT be what stopped this -- \
                 it reads the cash book, which still shows the funds"
            );
            assert_ne!(
                err,
                Error::from_contract_error(CollateralError::PoolInsolvent as u32),
                "the pool's solvency guard must NOT be what stopped this either"
            );
            assert_eq!(
                err,
                Error::from_contract_error(SAC_BALANCE_ERROR),
                "the exit must fail inside the SAC transfer for want of custody"
            );
        }
        Err(Err(host_abort)) => panic!("expected a SAC contract error, got {host_abort:?}"),
        Ok(_) => unreachable!("asserted is_err above"),
    }
    assert_eq!(token.balance(&receiver), 0, "the supplier received nothing");
    assert_eq!(
        t.state_snapshot().cash,
        book,
        "the failed exit rolled back, so the book still overstates custody"
    );
}
