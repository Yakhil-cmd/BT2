## Title
P_MAX spam-protection in the SPICE pending transaction queue is enforced by transaction *type* (access-key vs. gas-key) rather than by the underlying account resource, allowing unbounded backlog growth via gas-key transactions - (File: `chain/client/src/pending_transaction_queue.rs`)

### Summary
NEP-611's `P_MAX` mechanism restricts the number of *pending, uncertified* access-key transactions that a contract-holding account can have in flight, to protect chunk producers/SPICE certification from backlog griefing. The check, however, is gated on `!is_gas_key_tx` — i.e. it only counts ordinary access-key transactions and completely exempts "gas key" transactions (those carrying a `nonce_index`). This mirrors the Nouns pattern: a spam-protection counter keyed to one identity/path (access-key transactions from the account) while the account can trivially "move" its activity to a different, unmetered path (gas-key transactions) that is not subject to the same count-based cap, defeating the intended protection.

### Finding Description
`PendingTxSession::check_pending` computes `is_gas_key_tx` from whether the transaction's nonce has a `nonce_index` (i.e., it uses a gas key) and then applies P_MAX only when `!is_gas_key_tx`: [1](#0-0) 

The deploy-exclusivity check is guarded the same way (`if !is_gas_key_tx { ... }`), so gas-key transactions bypass both the deploy exclusivity rule and the P_MAX cap entirely.

Gas-key transactions are instead only constrained by a *balance* check (`paid_from_gas_key`, tracked in `pending_gas_key_costs`), not by a *count* limit: [2](#0-1) 

The doc comment for `P_MAX` explicitly states the intended protection covers "pending access key transactions across all uncertified blocks" for contract accounts, but says nothing about gas-key transactions being similarly bounded in *count*: [3](#0-2) 

A contract account that funds a gas key (via `TransferToGasKey`/gas-key creation, exposed through `promise_batch_action_add_gas_key_with_function_call` and the `AddKey`/gas-key mechanism) can submit an arbitrary number of pending, uncertified gas-key transactions limited only by the account's gas-key balance, not by any P_MAX-style count cap — exactly the unmetered backlog growth P_MAX was designed to prevent for access-key transactions.

This is structurally analogous to the Nouns bug: the spam-protection counter is bound to one identity/channel (ordinary access-key transactions from an account) while the same account can switch to another channel (gas-key transactions) that is free of the count restriction, at the cost only of gas-key funding — a cost the attacker controls and can size to be arbitrarily large while still queuing many small/cheap transactions.

### Impact Explanation
The `pending_transaction_queue` module and its P_MAX cap exist specifically to bound the size of the uncertified transaction backlog per contract account in SPICE's execution model (chunk producer throttling, per `ClientConfig::spice_pending_transaction_queue_enabled` and `update_pending_transaction_queue_for_block`): [4](#0-3) [5](#0-4) 

If gas-key transactions are exempt from the count cap, a contract account can flood the uncertified backlog with many small gas-key transactions, growing the per-shard `pending_accounts`/`pending_gas_key_costs`/`pending_nonces` maps in `PendingTransactionQueue` without bound (bounded only by wallet funding, which is cheap relative to the resource consumption caused on chunk producers tracking this state across all uncertified blocks until certification). This degrades or defeats the intended anti-spam/anti-DoS protection of NEP-611 for the SPICE feature, potentially causing unbounded resource growth in the pending-transaction-queue bookkeeping and reduced throughput/backlog buildup for certification, which is the harm class the mechanism exists to prevent.

### Likelihood Explanation
Medium. This requires the `protocol_feature_spice` feature and `spice_pending_transaction_queue_enabled` to be active — this is gated behind a feature flag and not the default configuration in the observed test harness (`#[cfg_attr(not(feature = "protocol_feature_spice"), ignore)]` on all relevant tests). Within that scope, exploitation only requires an ordinary unprivileged account: deploy a contract, create/fund a gas key, and submit gas-key transactions instead of access-key transactions — no validator or node-level privilege is needed.

### Recommendation
Apply the P_MAX (or an equivalent count-based) cap to gas-key transactions from contract accounts as well, not just ordinary access-key transactions, so that switching to the gas-key path cannot be used to sidestep the uncertified-backlog limit. At minimum, track and bound the total number of pending gas-key transactions per contract account alongside the existing balance-based `pending_gas_key_costs` check.

### Proof of Concept
1. Deploy a contract on account `A` and certify it (`HasContract::Yes` for `A`), as in `test_ptq_p_max_contract_account`.
2. Create and fund a gas key on `A` with a small `nonce_index` (via `AddKey`/`TransferToGasKey`), giving it a balance sufficient for `N ≫ P_MAX` cheap transfers.
3. Submit `N` gas-key transactions (each with `TransactionNonce::from_nonce_and_index`) from `A`, exceeding `P_MAX`.
4. Observe that unlike ordinary access-key transactions (capped at `P_MAX = 4` per `test_ptq_p_max_contract_account`), these are all admitted by `check_pending` because `is_gas_key_tx` short-circuits the `has_contract == HasContract::Yes && !is_gas_key_tx && total_access_key_count >= P_MAX` check, so no `Skip` occurs regardless of pending count, contrary to the count-based backlog protection intended by NEP-611 for contract accounts.     /// Called on BlockStatus::Next.
    fn update_pending_transaction_queue_for_block(&self, block: &Block) -> Result<(), Error> {
        if !block.is_spice_block() {
            return Ok(());
        }
        if !self.config.spice_pending_transaction_queue_enabled() {
            return Ok(());
        }

        // Remove newly certified blocks from the pending transaction queue.
        let prev_uncertified =
            self.chain.spice_core_reader.get_uncertified_chunks(block.header().prev_hash())?;
        let certified_block_hashes =
            find_newly_certified_block_hashes(&prev_uncertified, block.spice_core_statements());
        if !certified_block_hashes.is_empty() {
            let mut ptq = self.chunk_producer.pending_transaction_queue.lock();
            for block_hash in &certified_block_hashes {
                ptq.remove_certified_block(block_hash);
            }
        }

        // Add new block's chunk transactions.
        let epoch_id = self.epoch_manager.get_epoch_id(block.hash())?;
        let protocol_version = self.epoch_manager.get_epoch_protocol_version(&epoch_id)?;
        let config = self.runtime_adapter.get_runtime_config(protocol_version);
        let gas_price = self.chain.get_block_header(block.header().prev_hash())?.next_gas_price();
        for chunk_header in block.chunks().iter_new() {
            let shard_id = chunk_header.shard_id();

                continue;

            let mut ptq = self.chunk_producer.pending_transaction_queue.lock();

                *block.hash(),
