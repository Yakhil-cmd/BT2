### Title
Cross-organization commit-status forgery bypasses CI gating and triggers unauthorized deploys - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates a webhook only against the GitHub organization named in the payload's `repository.owner.login` (or `organization.login`), by looking up that organization's own `webhook_secret` via `Shipit.github(organization: repository_owner)`. [1](#0-0)  That verification only proves the sender knows the webhook secret configured for *that org's* GitHub App — it says nothing about which repository/commit the payload's other fields refer to. `Handlers::StatusHandler`, which processes the `status` event, never checks this binding at all: it looks up commits purely `Commit.where(sha: params.sha)`, globally, across the entire Shipit installation, with no scoping by organization or repository. [2](#0-1) 

### Finding Description
The equality that should hold is: `organization that authenticated the signature == organization that owns the commit/stack being mutated`. Instead:

- Sign-off side: `verify_signature` picks the GitHub App/secret using `params.dig('repository','owner','login')` (or `organization.login`), i.e. whatever organization string the attacker put in the JSON body. [3](#0-2) [4](#0-3) 
- Write side: `StatusHandler#process` never consults `repository.full_name` or any organization scoping at all — it matches commits solely by `sha`, a value shared across the whole database, and calls `commit.create_status_from_github!(params)` on every match. [5](#0-4) 

Shipit supports multiple GitHub organizations in one instance, each configured with its own independent `webhook_secret` (see `test/dummy/config/secrets_double_github_app.yml` showing `OrgOne`/`OrgTwo` each with a distinct app/secret). [6](#0-5)  An attacker who legitimately administers the GitHub App for their own organization (Org A) — and therefore legitimately possesses Org A's `webhook_secret` — can craft a `status` event whose top-level JSON sets `repository.owner.login = "OrgA"` (so `verify_signature` checks/succeeds against Org A's known secret and passes the whole-body HMAC), but whose `sha` field is the commit SHA of a totally unrelated stack belonging to Org B. Because `StatusHandler` never re-derives or checks organization/repository ownership of the matched `Commit` records, the forged status (`state: "success"`, arbitrary `description`/`target_url`/`context`) is written onto Org B's commit.

This status write flows directly into deploy-gating logic: `Commit#create_status_from_github!` → `add_status`, which recomputes `deployable?`/`blocked?` and, on a transition to `pending`/`success`, calls `stack.schedule_merges` and fires `Hook.emit(:deployable_status, ...)`. [7](#0-6) [8](#0-7)  `Status` also triggers `schedule_continuous_delivery` on create. [9](#0-8)  Tests confirm that a commit transitioning to `success` on a stack with `continuous_deployment: true` enqueues a real `ContinuousDeliveryJob` and creates a `Deploy`. [10](#0-9) 

### Impact Explanation
This breaks the "organization that authenticated vs. repository that is written" binding explicitly called out as in-scope. A user who controls only their own organization's GitHub App/webhook secret can forge a passing CI status on a commit belonging to a different organization's stack that they have no access to on GitHub, bypassing CI gating (`Commit#deployable?`) and, on stacks with continuous deployment enabled, causing Shipit to enqueue and execute an actual unauthorized deploy of code they don't control the CI signal for. This matches the Critical-tier impact "unauthorized deploy."

### Likelihood Explanation
The prerequisite is only that the attacker administers *any* org's GitHub App wired into the same multi-tenant Shipit instance (a supported, documented configuration — see `secrets_double_github_app.yml`), which is a much lower bar than compromising the target org. The victim commit SHA is typically public (visible in GitHub, PRs, CI logs) and doesn't need to be secret. No rate limiting or additional authentication guards this handler beyond the (org A-scoped) signature check.

### Recommendation
In `StatusHandler` (and any other handler using `Handler#stacks`/`Commit.where` lookups), scope the query to the repository named in the signed payload (`payload.dig('repository','full_name')`) and additionally verify that the resolved `Repository#owner` matches the organization used to authenticate the signature (`repository_owner` from `WebhooksController`). Reject the event if these do not match, closing the org-vs-repository binding gap. Apply the same scoping check generically in `Handler#stacks`/`Handler#repository_name` derived lookups.

### Proof of Concept
1. Attacker administers Org A's GitHub App on the shared Shipit instance and knows Org A's `webhook_secret` (legitimate, since they configured it).
2. Attacker learns a commit SHA belonging to Org B's tracked stack (public on GitHub).
3. Attacker POSTs to `/webhooks` with header `X-Github-Event: status`, body:
```json
{
  "sha": "<org-b-commit-sha>",
  "state": "success",
  "context": "ci/forged",
  "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgA/whatever"}
}
```
   signed (`X-Hub-Signature`) with Org A's real `webhook_secret`.
4. `verify_signature` resolves `Shipit.github(organization: "OrgA")` and validates successfully against Org A's secret. [3](#0-2) 
5. `StatusHandler#process` runs `Commit.where(sha: "<org-b-commit-sha>")` and calls `create_status_from_github!`, writing a forged `success` status onto Org B's commit despite the request never having been authenticated for Org B. [5](#0-4) 
6. If Org B's stack has `continuous_deployment: true`, this status transition schedules an unauthorized real deploy. [10](#0-9)

      verified = github_app.verify_webhook_signature(

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
