### Title
Headers-commission splitting rounds each recipient's share independently, allowing supply inflation via crafted `earned_headers_commission_share` values - (File: `headers_commission.js`)

### Summary
`calcHeadersCommissions()` distributes a parent unit's `headers_commission` among the addresses listed in a winning child unit's `earned_headers_commission_recipients`. Each recipient's payout is computed as `Math.round(full_amount * share / 100.0)` independently for every recipient, instead of computing all-but-one shares and giving the last recipient the exact remainder (`full_amount - sum_of_others`). Because integer rounding is applied per-share rather than reconciled against the total, the sum of all recipients' rounded amounts can exceed (or fall short of) `full_amount`. This mirrors the reported bug class: dividing a fixed pool by a fraction and truncating/rounding without validating/reconciling that the parts reconstruct the whole, silently creating or destroying value.

The only constraint enforced on `earned_headers_commission_recipients` is that the `earned_headers_commission_share` values are positive integers, sorted by address, and sum to exactly 100: [4](#0-3) 

A unit author (of a multi-authored unit) fully controls the list of recipient addresses and their percentage shares — these are arbitrary self-chosen values, not derived from any external computation. Given `full_amount` (the parent's `headers_commission`, an integer number of bytes) and `N` recipients with shares `s_1..s_N` summing to 100, the code computes `amount_i = round(full_amount * s_i / 100)` for each `i` independently. The sum `Σ amount_i` is not guaranteed to equal `full_amount`; each term carries an independent rounding error of up to ±0.5 units, so the aggregate error can be up to roughly `(N-1) * 0.5` units in either direction, bounded only by `MAX_AUTHORS_PER_UNIT` (the number of possible recipients tied to the unit's authors).

By carefully selecting shares (e.g., values whose `full_amount * share/100` fractional parts sit just above `0.5`, causing `Math.round` to round up for every recipient), an attacker who authors many multi-authored units and racks up headers-commission wins across the DAG can systematically bias the aggregate rounding in their favor across a very large number of parent units over time. This effectively mints extra bytes out of thin air (or, in the opposite direction, silently burns bytes for other users splitting commissions), which is a supply-inflation/accounting-integrity defect rather than a mere rounding cosmetic issue, because there is no reconciliation step (no "last recipient gets the remainder" pattern, no post-hoc adjustment, no check that `Σ amount_i == full_amount`).

### Impact Explanation
Headers commission outputs directly become spendable byte balances credited to addresses (`headers_commission_outputs` table, later spent via `type: "headers_commission"` inputs in `inputs.js`). If per-recipient rounding systematically inflates the sum beyond `full_amount`, the network mints extra base-currency bytes with no corresponding burn — a supply-inflation bug. This satisfies the "supply inflation" impact category explicitly accepted by the analysis criteria. The effect on a single distribution is tiny (sub-byte), but it is reachable by any address that authors multi-authored units and is repeatable indefinitely across the DAG, so an attacker who systematically wins headers commissions with a favorably-crafted `earned_headers_commission_recipients` list can accumulate the rounding bias over a large number of units.

### Likelihood Explanation
Any user can author a multi-authored unit and freely choose the `earned_headers_commission_recipients` addresses/shares subject only to the sum-to-100 and sorting constraints validated in `validateHeadersCommissionRecipients`. No privileged role, witness status, or node compromise is required — this is fully reachable from a standard unit-posting flow. The only friction is that gains per distribution are small and require winning the headers-commission race (`getWinnerInfo`, hash-based selection) repeatedly, so the exploit is slow but has no cap other than persistence and DAG activity.

### Recommendation
Do not round every recipient's share independently. Instead:
1. Round shares for all recipients except the last one (sorted by address, as already required), and
2. Assign the last recipient `full_amount - Σ(previously assigned amounts)` so the total distributed always reconciles exactly to `full_amount`, eliminating any possibility of aggregate over- or under-distribution.

This mirrors the general fix pattern recommended in the source report: never let independent integer roundings of parts of a fixed pool go unreconciled against the whole.

### Proof of Concept
1. Author a unit with, e.g., 3 authors and `earned_headers_commission_recipients` shares `[34, 33, 33]` (sum = 100, valid per `validateHeadersCommissionRecipients`).
2. Get this unit selected as the winning headers-commission recipient for several parent units whose `headers_commission` values are chosen (or naturally occur) such that `full_amount * 34/100`, `full_amount * 33/100` each round up under `Math.round`'s half-up behavior (e.g., `full_amount = 3`: `3*0.34=1.02→1`, `3*0.33=0.99→1`, `3*0.33=0.99→1`; sum = 3, matches. Try `full_amount = 5`: `5*0.34=1.7→2`, `5*0.33=1.65→2`, `5*0.33=1.65→2`; sum = 6 ≠ 5, a 1-byte excess is minted).
3. Repeat across many won parent units/mci ranges over time to accumulate the excess bytes credited via `headers_commission_outputs`, which are later spendable as real balance through `type: "headers_commission"` inputs. [5](#0-4) [6](#0-5)

function validateHeadersCommissionRecipients(objUnit, cb){
	if (objUnit.authors.length > 1 && typeof objUnit.earned_headers_commission_recipients !== "object")
		return cb("must specify earned_headers_commission_recipients when more than 1 author");
	if ("earned_headers_commission_recipients" in objUnit){
		if (!isNonemptyArray(objUnit.earned_headers_commission_recipients))
			return cb("empty earned_headers_commission_recipients array");
		var total_earned_headers_commission_share = 0;
		var prev_address = "";
		for (var i=0; i<objUnit.earned_headers_commission_recipients.length; i++){
			var recipient = objUnit.earned_headers_commission_recipients[i];
			if (!isPositiveInteger(recipient.earned_headers_commission_share))
				return cb("earned_headers_commission_share must be positive integer");
			if (hasFieldsExcept(recipient, ["address", "earned_headers_commission_share"]))
				return cb("unknown fields in recipient");
			if (!isValidAddress(recipient.address))
				return cb("invalid recipient address checksum");
			if (recipient.address <= prev_address)
				return cb("recipient list must be sorted by address");
			total_earned_headers_commission_share += recipient.earned_headers_commission_share;
			prev_address = recipient.address;
		}
		if (total_earned_headers_commission_share !== 100)
			return cb("sum of earned_headers_commission_share is not 100");
	}
	cb();
}
