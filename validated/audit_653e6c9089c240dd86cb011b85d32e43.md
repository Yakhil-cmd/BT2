### Title
Uncaught exception during AA trigger execution permanently halts stabilization and all subsequent unit writes - (File: aa_composer.js, writer.js)

### Summary
`handleAATriggers()` is invoked synchronously from `writer.saveJoint()` right after an MCI becomes stable (`writer.js:724-727`, also `main_chain.js:1263-1276` and `main_chain.js:1691-1723`), while the node is holding the global write lock (`objValidationState.bUnderWriteLock` / write mutex). Inside it, `handlePrimaryAATrigger()` calls `handleTrigger()`, whose internal `sendUnit()`/`completePaymentPayload()`/balance-accounting logic contains numerous unconditional `throw Error(...)` statements (e.g. `aa_composer.js:1053` "last ball unit not found", and dozens of others reachable from attacker-controlled trigger/message state such as asset lookups, balance bookkeeping, and `pickParents()`).

### Finding Description
Any trigger unit posted by an ordinary user to a stable AA address is inserted into the `aa_triggers` table (`main_chain.js:1711-1720`) and is then processed by `handleAATriggers()` before `unlock()` is ever called (`writer.js:715-777`). Unlike the well-formed error paths that funnel through `bounce()`/`revert()` (which gracefully roll back and still complete the trigger, e.g. `aa_composer.js:909-945`, `1759-1798`), several code paths in the same execution instead `throw Error(...)` on unexpected/edge-case conditions rather than calling `bounce`/`cb(err)`. If a crafted trigger (payload, asset reference, balance overflow edge case, secondary-AA chain, etc.) drives execution into one of these `throw` statements, the exception propagates up through the `async`/promise chain used by `handleAATriggers`/`handlePrimaryAATrigger` and crashes the Node.js process (uncaught exception), because these are unconditional guard-style throws, not passed to the `onDone`/`cb` error channel used for normal validation failures.

Because the `aa_triggers` row for the offending unit is only deleted from the DB **after** `handleTrigger()` completes (`aa_composer.js:101-104`, inside the same transaction that is aborted by the crash), the row remains in `aa_triggers` on disk. On process restart, `handleAATriggers()` (called again as part of normal startup/stabilization flow) re-reads the same pending row and re-executes the identical trigger, hitting the identical `throw`, crashing the node again — an infinite crash loop with no automatic recovery, exactly analogous to the SUI signer getting permanently stuck reprocessing the same malformed withdrawal.

### Impact Explanation
Because `handleAATriggers()` executes under the global write mutex before further units can be written/stabilized, a stuck/crashing trigger blocks the entire node from stabilizing new MCIs and processing subsequent units system-wide (not just for the targeted AA address) — a full node liveness DoS: "a network unable to confirm new units," matching the accepted impact classes. Every full node that processes this stable trigger (which is deterministic and mandatory for correctness) will crash identically, so it isn't a single-node quirk but a fork/halt condition across all full nodes, since none of them can advance past this MCI. This is worse than the SUI case (single withdrawal path stuck) because it blocks unrelated units and other AAs as well.

### Likelihood Explanation
Likelihood depends on whether an ordinary unprivileged unit poster can actually drive `handleTrigger()`'s execution into one of the unconditional `throw Error` sites (as opposed to only internal invariant violations that are truly unreachable from trigger data). This requires deeper code-flow analysis of `aa_composer.js` (particularly `sendUnit`, `completePaymentPayload`, `pickParents`, and `updateInitialAABalances`) than could be completed with the available tool budget to definitively separate "attacker-reachable" throws from "genuine internal invariant" throws, several of which are guarded by prior validation in `aa_validation.js`/`validation.js`. This should be verified in the actual source with a Devin session before treating any specific throw site as exploitable.

### Recommendation
Audit every `throw Error(...)` inside `aa_composer.js`'s trigger-execution call graph (`handleTrigger`, `sendUnit`, `completePaymentPayload`, `updateInitialAABalances`, `pickParents`) to confirm none of them can be reached purely by attacker-controlled trigger contents; convert any reachable ones into `bounce(err)`/`cb(err)` calls so malformed AA-triggering data degrades to a normal bounce response instead of a process crash. Additionally, consider deleting/marking the `aa_triggers` row (or moving it to a dead-letter state) before executing the trigger body, so a crash does not cause an infinite re-processing loop on restart.
