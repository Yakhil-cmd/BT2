## Assessment: Valid finding — but not exactly as framed by the prompt (GITHUB_TOKEN "override" isn't itself the exploit vector). The real, exploitable break is that `machine.environment` in `shipit.yml` is merged into the task/deploy environment with **no allowlist**, unlike every other user-influenceable env source in this codebase.

### Title
`DeploySpec#machine_env` bypasses `EnvironmentVariables.permit` and lets a fork's `shipit.yml` override security-relevant process environment (`PATH`, `GIT_ASKPASS`, `GITHUB_TOKEN`, etc.) reaching `PTY.spawn` - (File: `lib/shipit/task_commands.rb`)

### Summary
`TaskCommands#env` merges `deploy_spec.machine_env` (sourced from `machine.environment` in `shipit.yml`) directly into the environment hash passed to `Command.new`, with no call to `EnvironmentVariables.permit`, unlike `deploy.variables`, `rollback.variables`, and task `variables`, which are all explicitly allowlisted. Because `Command#unbundled_env` merges the caller-supplied `@env` last, any key an attacker names in their fork's `shipit.yml` (including `PATH`, `GIT_ASKPASS`, `GITHUB_TOKEN`, `RUBYOPT`, `LD_PRELOAD`, `BUNDLE_GEMFILE`, etc.) silently overrides the value shipit-engine itself computed, right before `PTY.spawn`.

### Finding Description
The invariant that should hold is: **every environment key merged into the hash passed to `Command`/`PTY.spawn` must either be an internal, non-attacker-controlled value, or have passed through `EnvironmentVariables.with(env).permit(variable_definitions)`** — i.e. `TaskCommands#env['K'] == (internal value) || K ∈ allowlist(variable_definitions)`. This invariant is enforced for:
- `deploy.variables` via `DeploySpec#filter_deploy_envs` [1](#0-0) 
- `rollback.variables` via `DeploySpec#filter_rollback_envs` [2](#0-1) 
- task `variables` via `TaskDefinition#filter_envs` [3](#0-2) 

But it is **not** enforced for `machine.environment`. `DeploySpec#machine_env` just reads the raw config with no filtering: [4](#0-3) . `DeploySpec::FileSystem` parses this straight from the checked-out `shipit.yml` on the task's `working_directory` [5](#0-4) [6](#0-5) .

`TaskCommands#env` merges this unfiltered hash after `Commands#base_env` (which sets `GITHUB_TOKEN`, `GITHUB_DOMAIN`, optionally `GIT_ASKPASS`) and stack/task metadata, but before `@task.env`: [7](#0-6) . `Commands#base_env` is where the legitimate `GITHUB_TOKEN`/`GIT_ASKPASS` are set: [8](#0-7) .

Finally, `Command#unbundled_env` merges the caller's `@env` **last**, so any key it contains wins over `BASE_ENV` and the hard-coded safe `PATH`: [9](#0-8) , and this is what's passed to `PTY.spawn`: [10](#0-9) .

Exploit flow:
1. Attacker forks the tracked repository, opens a PR whose `shipit.yml` (on their own branch) contains, e.g., `machine: {environment: {PATH: "/tmp/evil:$PATH"}}` or `machine: {environment: {GIT_ASKPASS: "./evil_askpass.sh"}}`.
2. If the repository has Review Stacks enabled with "Allow All" (or "Allow With Label" and the attacker labels their own PR), `OpenedHandler#process` auto-creates a `ReviewStack` for the fork branch with no reviewer approval [11](#0-10) .
3. When any task/deploy is later run against that stack (a manual "restart"/"deploy" click, or continuous deployment if enabled for the environment), `TaskCommands#deploy_spec` parses the attacker's `shipit.yml` from the checked-out fork branch and `TaskCommands#env` merges the unfiltered `machine.environment` values into the process environment used for every step's `Command`.
4. `Command#unbundled_env` lets those attacker-supplied keys override the safe defaults, and `PTY.spawn` runs subsequent steps (git, bundle, capistrano, etc.) with attacker-controlled `PATH`/`GIT_ASKPASS`/interpreter env vars, enabling arbitrary code execution on the deploy host and/or credential exfiltration (e.g. a malicious `GIT_ASKPASS` script that reads the real `GITHUB_TOKEN` still present in the merged env and exfiltrates it over the network when git or other steps invoke it).

Existing guards do not catch this: `EnvironmentVariables#permit` exists and is used for `deploy.variables`/`rollback.variables`/task `variables`, but `DeploySpec#machine_env`/`FileSystem#cacheable_config` never routes through it — this is an inconsistency in the codebase's own trust model, not a defense that was bypassed via a flaw elsewhere.

### Impact Explanation
An attacker who can only open a PR from their own fork can smuggle attacker-chosen environment variables (`PATH`, `GIT_ASKPASS`, `RUBYOPT`, `LD_PRELOAD`, `BUNDLE_GEMFILE`, or literally `GITHUB_TOKEN`) into the exact environment hash handed to `PTY.spawn` for any subsequent task/deploy step run against that ReviewStack. This is Critical: RCE on the deploy host via `Command`/`PTY.spawn`, and a viable path to exfiltrate the real `GITHUB_TOKEN` (still present in the merged env unless directly overwritten) via a malicious `GIT_ASKPASS`/interpreter hook. Blast radius is scoped to the deploy host process running that stack's tasks, but the deploy host is shared infrastructure, so this can affect credentials/processes beyond just the attacker's own review environment. Repeatable per PR/branch.

### Likelihood Explanation
Preconditions: the host repository must have Review Stacks enabled with a provisioning behavior that doesn't require maintainer action (`allow_all`, or `allow_with_label`/`prevent_with_label` where the attacker fully controls their own PR's labels). This is documented as the common/recommended configuration ("most likely 'Allow All'"). No secrets or privileged roles are required by the attacker — only the ability to open a PR from a fork and author `shipit.yml`. Actual code execution additionally requires a task/deploy to run against the ReviewStack (manual click by a maintainer who reasonably assumes review-stack environment vars are sandboxed, or continuous deployment enabled for that stack/environment).

### Recommendation
Route `machine.environment` through an explicit allowlist mechanism before merging, analogous to `EnvironmentVariables.permit` for `deploy.variables`/`rollback.variables`. Concretely: reject/strip any `machine.environment` key that collides with reserved/security-sensitive names (`PATH`, `GIT_ASKPASS`, `GITHUB_TOKEN`, `GITHUB_DOMAIN`, `LD_PRELOAD`, `RUBYOPT`, `BUNDLE_GEMFILE`, etc.), or require repository maintainers to explicitly declare which `machine.environment` keys are permitted (mirroring `deploy.variables` schema), and merge `deploy_spec.machine_env` *before* the internally computed safe values in `TaskCommands#env`/`Commands#base_env` (not after) so it can never win a key collision with engine-controlled variables.

### Proof of Concept
```ruby
# test/lib/shipit/task_commands_machine_env_test.rb
require "test_helper"

module Shipit
  class TaskCommandsMachineEnvTest < ActiveSupport::TestCase
    test "fork-controlled machine.environment overrides the engine's GITHUB_TOKEN and PATH with no allowlist check" do
      stack = shipit_stacks(:review_stack)
      task = shipit_tasks(:shipit_restart)
      task.stack = stack

      commands = Shipit::TaskCommands.new(task)

      # Simulate a DeploySpec parsed from the attacker's own fork's shipit.yml
      malicious_spec = stub(
        machine_env: { "GITHUB_TOKEN" => "attacker-controlled-token", "PATH" => "/tmp/evil:/usr/bin" },
        clear_working_directory?: true
      )
      commands.stubs(:deploy_spec).returns(malicious_spec)

      real_token_before_override = commands.env["GITHUB_TOKEN"] # value Commands#base_env computed from Shipit.github

      env = commands.env

      # BROKEN BINDING: env['GITHUB_TOKEN'] should equal the value Command#unbundled_env
      # would compute from Shipit.github, reconciled against an allowlist. Instead it is
      # silently replaced by the unfiltered shipit.yml value.
      assert_equal "attacker-controlled-token", env["GITHUB_TOKEN"]
      refute_equal real_token_before_override, env["GITHUB_TOKEN"]

      # PATH is likewise overridable, letting attacker binaries shadow real ones in PTY.spawn
      assert_equal "/tmp/evil:/usr/bin", env["PATH"]

      command = Shipit::Command.new("echo hi", env:, chdir: ".")
      assert_equal "/tmp/evil:/usr/bin", command.unbundled_env["PATH"]
    end
  end
end
```
This demonstrates that `deploy_spec.machine_env` (attacker-authored `shipit.yml`) is merged into `TaskCommands#env` and ultimately `Command#unbundled_env`/`PTY.spawn` with no `EnvironmentVariables.permit` check, unlike `deploy.variables`/`rollback.variables`/task `variables`.
