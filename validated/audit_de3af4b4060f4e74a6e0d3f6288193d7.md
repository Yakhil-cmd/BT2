### Title
Stop-hook advances the git review `baseline_sha` past files dropped by `_prioritize_diff_files()`, permanently exempting them from future security review — ([File: plugins/security-guidance/hooks/security_reminder_hook.py])

### Summary
The Beanstalk report shows `addMigratedDepositsToAccount()` advancing the reward checkpoint (`lastStem`) to cover *all* of an account's deposits for a token, even though the function only processed the migrated subset — silently forfeiting rewards on the deposits it never touched. The `security-guidance` Stop hook in this repo has the same structural flaw: it advances its own "processed" checkpoint (`baseline_sha`) over the *entire* current working-tree state, even when it only actually reviewed a subset of the changed files.

### Finding Description
`handle_stop_hook()` parses the full diff into `diff_files` and, when the count exceeds `MAX_DIFF_FILES`, calls `_prioritize_diff_files()` to keep only the top-N highest-risk files, discarding the rest (`_stop_dropped`) without ever sending them to the LLM reviewer: [1](#0-0) 

Only the *kept* subset (`diff_files`) is passed to `analyze_code_security()`: [2](#0-1) 

If the LLM flags anything in that reviewed subset (`concrete_guidance` is non-empty), the hook then calls `capture_git_baseline(cwd)` to snapshot the *entire* current working tree and unconditionally advances `state["baseline_sha"]` to it: [3](#0-2) 

`capture_git_baseline` (via `git stash create`, referenced at line 468 of the same file) captures the whole working tree, not just `review_paths`. Because every subsequent Stop-hook fire diffs content against `baseline_sha` (`content_base = baseline_sha or diff_base`, line 1807), any file that was dropped by `_prioritize_diff_files()` in this turn — and thus never analyzed — is now "baked into" the new baseline and will never appear as a diff again, even though it was never security-reviewed. This exactly mirrors the Beanstalk bug: `lastStem`/`stemTip` is advanced across the whole token even though the loop only processed the deposits named in `depositData.depositIds`, forfeiting rewards on the untouched deposits.

The dropped file set is not small or theoretical: `_prioritize_diff_files()` explicitly deprioritizes (and, once over the cap, drops) files matching `_LOW_PRIORITY_SUFFIXES`/`_LOW_PRIORITY_PATH_TOKENS` (`.config.js`, `/migrations/`, test files, etc.), and any file lacking `_SECURITY_RISK_PATH_TOKENS` substrings in its path: [4](#0-3) 

Malicious or vulnerable code placed in a large, multi-file turn (e.g., a helper module without an "auth/route/exec" path token, or code in a `.config.js`/migration-styled file) can be silently and permanently exempted from the plugin's own security net the moment *any other* file in the same turn triggers a finding.

### Impact Explanation
This is a hook-bypass class issue: it defeats the purpose of the `security-guidance` Stop hook, whose entire job is to force Claude to fix flagged issues (`sys.exit(2)` at line 1946) and re-review subsequent changes. Once `baseline_sha` silently advances past unreviewed files, those files' content is treated as "pre-existing" in every later diff and is never surfaced to the LLM reviewer again for the rest of the session (or until an unrelated commit/push review happens to catch it independently). This does not compromise Claude Code's core process-isolation/approval mechanisms directly, but it does silently and permanently disable a security control an operator has installed for large, multi-file agentic turns — the exact class of over-cap turn the comment at line 1829-1834 says the hook is deliberately trying to *not* skip.

### Likelihood Explanation
Requires a turn that changes more files than `MAX_DIFF_FILES` (explicitly anticipated and handled by the code, not an edge case) and where at least one high-risk-path file triggers a finding while a low-priority/no-token file in the same turn carries the actual vulnerable/malicious code. Large multi-file scaffolding/refactor turns performed by agents are common, making this reachable without any special user privilege.

### Recommendation
Only advance `baseline_sha` to cover the files that were actually reviewed, not the entire working tree. Options: (1) exclude the `_stop_dropped` files' content from the new baseline snapshot (e.g., by re-stashing only `review_paths`, or by tracking a per-file "last reviewed" marker independent of the global stash SHA), or (2) if `_stop_dropped > 0`, keep `baseline_sha` at its previous value for the un-reviewed files so they resurface as a diff on the next Stop fire, analogous to mowing/settling all pending state before checkpointing in the Beanstalk fix.

### Proof of Concept
1. In a single agentic turn, modify > `MAX_DIFF_FILES` source files, such that one file's path contains a `_SECURITY_RISK_PATH_TOKENS` match (e.g., `api/handler.py`) with an obviously flaggable issue, and another unrelated file (e.g., `utils/config.js`, no risk tokens, or under `/migrations/`) contains actual malicious/vulnerable code.
2. Stop hook fires: `diff_files` count exceeds `MAX_DIFF_FILES` → `_prioritize_diff_files` keeps `api/handler.py`-style files, drops `utils/config.js` (`_stop_dropped` at line 1841 counts it).
3. LLM flags the issue in `api/handler.py`; `concrete_guidance` is non-empty → block 1883-1916 runs, `capture_git_baseline(cwd)` snapshots the *whole* tree (including `utils/config.js`) and `state["baseline_sha"]` is set to `new_sha`.
4. In subsequent turns, `utils/config.js`'s malicious content is already inside the new baseline stash, so `get_git_diff(... , content_base=baseline_sha ...)` never shows it as changed again — the Stop hook will never review it, regardless of how many more turns occur, unless it's touched again by an unrelated future edit.

def _prioritize_diff_files(diff_files, cap):
    """When `diff_files` exceeds `cap`, return the top-`cap` by security
    relevance plus the count dropped. Otherwise return (diff_files, 0).

    Score = (risk_tokens_in_path, not_low_priority, added_lines). The
    added-lines proxy is `content.count('\\n+')` which counts diff additions
    cheaply without re-parsing hunks. This is a heuristic, not a guarantee —
    the goal is to review the likely-dangerous subset of an over-cap diff
    instead of reviewing nothing. Diffs that exceed the cap are typically
    large multi-file scaffolds, and the cross-file source→sink vulnerabilities
    in them concentrate in a handful of api/client/route files.
    """
    if len(diff_files) <= cap:
        return diff_files, 0

    def _score(item):
        fp, content = item
        low = fp.lower()
        # Prepend "/" so leading-slash patterns in _LOW_PRIORITY_PATH_TOKENS
        # match top-level dirs (git diff paths are repo-root-relative, e.g.
        # `migrations/001.py` not `/migrations/001.py`). Same trick as
        # _is_reviewable_source.
        low_slashed = "/" + low
        risk = sum(1 for t in _SECURITY_RISK_PATH_TOKENS if t in low)
        low_prio = (
            fp.endswith(_LOW_PRIORITY_SUFFIXES)
            or any(t in low_slashed for t in _LOW_PRIORITY_PATH_TOKENS)
        )
        # added_lines: count('\n+') over-counts by including '+++' header and
        # any literal '+' at line start in context, but it's a consistent
        # ordinal across files in the same diff which is all we need.
        added = content.count("\n+")
        return (risk, not low_prio, added)

    ranked = sorted(diff_files, key=_score, reverse=True)
    return ranked[:cap], len(diff_files) - cap
