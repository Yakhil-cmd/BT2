### Title
Deploy/task attribution can be spoofed via unauthenticated `X-Shipit-User` header, decoupling the authenticated `ApiClient` from the recorded `User` - (File: app/controllers/shipit/api/base_controller.rb)

### Summary
`Shipit::Api::BaseController#current_user` resolves the acting `User` purely from the client-supplied `X-Shipit-User` HTTP header, with no cryptographic or ownership binding to the authenticated `ApiClient` (which is verified only via Basic Auth against `Shipit.api_clients_secret`). This mirrors the report's bug class: a value used to drive privileged state changes (`checkpointToken`'s stale balance) is decoupled from the value that should govern it (the post-transfer balance). Here, the identity used to author deploys/rollbacks/tasks/locks (`current_user`) is decoupled from the identity that was actually authenticated (the `ApiClient`/its `creator`), breaking the "GitHub identity vs. `User` bound to the session" trust binding called out in scope.

### Finding Description
Authentication in the API only validates the bearer token against `ApiClient.authenticate`, which resolves to an `ApiClient` record, not a `User`: [1](#0-0) 

The acting `User` for the request is determined completely separately, from an arbitrary client-supplied header, with no verification that this header corresponds to the client's `creator` or to any credential the caller actually possesses: [2](#0-1) 

This `current_user` is then used as the authoritative author/actor for privileged, audit-significant state transitions:
- Deploy creation: `stack.trigger_deploy(commit, current_user, ...)` [3](#0-2) 
- Task trigger/abort: `stack.trigger_task(params[:task_name], current_user, ...)` and `task.abort!(aborted_by: current_user)` [4](#0-3) 

The recorded `User` then propagates into the actually-executed deploy environment/audit trail, e.g. `SHIPIT_USER`, `EMAIL`, `GIT_COMMITTER_NAME`, `GIT_COMMITTER_EMAIL` used by the shell commands that perform the deploy: [5](#0-4) 

Equality that should hold but is broken: `identity authenticated by ApiClient credential == identity recorded as task/deploy author`. Before the request: the caller only holds a valid `ApiClient` Basic Auth token (possibly scoped to `deploy:stack`) belonging to `creator: X`. After the request: `current_user` can be set to any arbitrary `login` present in the `User` table (e.g. `Y`, a team lead, an admin, or a user with elevated `Shipit.github_teams` membership) simply by sending `X-Shipit-User: Y`, with no verification that the caller is actually `Y` or acting on `Y`'s behalf.

### Impact Explanation
Any holder of a valid `ApiClient` token with `deploy:stack` permission can attribute deploys, rollbacks, task triggers, and task aborts to an arbitrary other `User` in the system by forging the `X-Shipit-User` header. This corrupts the audit trail that Shipit relies on for attribution (who deployed/rolled back/aborted what), and since the author identity flows into deploy scripts (`GIT_COMMITTER_NAME`/`EMAIL`/`SHIPIT_USER`), an attacker can make an unauthorized deploy/rollback/task execution appear to have been performed by a specific trusted user, including users with elevated review/merge authority. This falls under "an unauthorized deploy, rollback" impact category since the deploy/rollback/task action's authorized actor is misrepresented, defeating any downstream logic or human review that trusts the recorded author field.

### Likelihood Explanation
This requires only possession of a legitimate `ApiClient` token with the relevant permission (`deploy:stack`, `write:stack`, etc.) — no privileged GitHub or Shipit admin access is needed beyond having any provisioned API client. Any integration or CI pipeline with an API token that also wants to identify itself as a user (the intended, documented use of the header) can trivially set an arbitrary value instead of its own identity, since the controller performs no ownership check between the token's `creator` and the supplied header. This is a low-effort, directly reachable, unprivileged-attacker-relative (relative to whatever operation the client's permissions already allow) issue.

### Recommendation
Bind `current_user` to the authenticated `ApiClient`: either use `current_api_client.creator` directly as the acting user, or, if delegated identification via `X-Shipit-User` must be supported, only accept it when the `ApiClient` is explicitly authorized to impersonate/act-as arbitrary users (e.g., a dedicated permission scope), and record both the authenticated client and the claimed user separately in the audit log rather than conflating them into a single unverified `current_user`.

### Proof of Concept
1. Obtain any valid `ApiClient` token with `deploy:stack` permission (e.g. a CI-integration token).
2. Send: `POST /shopify/repo/production/deploys.json` with `Authorization: Basic <token>` and header `X-Shipit-User: victim_admin_login`, along with a valid `sha`.
3. `current_user` resolves to the `User` record for `victim_admin_login` (per `identify_user`), and the created `Deploy` is recorded with `user: victim_admin_login`, and deploy scripts run with `SHIPIT_USER`/`GIT_COMMITTER_NAME` set to the victim's identity — despite the victim never authenticating or authorizing this deploy.
