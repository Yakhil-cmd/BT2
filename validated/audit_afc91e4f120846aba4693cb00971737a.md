### Title
Cross-repository `shipit/checks` status forgery via unscoped `Commit.where(sha:)` lookup - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits purely by SHA across the entire database, without restricting the query to the repository that authenticated the webhook. A properly-signed `status` webhook from an attacker-controlled repository can therefore flip the `shipit/checks` status of a commit belonging to a completely different (victim) stack whenever the two repositories happen to share a commit SHA, directly affecting `blocked?`/`deployable?` on the victim stack.

### Finding Description
The broken binding: the invariant the code is supposed to preserve is
`commit.stack.github_repo_name == payload['repository']['full_name']`
i.e. a status webhook should only mutate commits belonging to the repository that signed it. This invariant is never checked.

Trace:
- `Shipit::WebhooksController#create` (`app/controllers/shipit/webhooks_controller.rb:10-15`) parses the raw payload and dispatches it to handlers after `verify_signature`, which validates the HMAC signature using `Shipit.github(organization: repository_owner)` (`app/controllers/shipit/webhooks_controller.rb:24-30`). This only proves the payload was signed by *some* GitHub App installation known to Shipit for the org named in the payload — it says nothing about which Shipit *stack*/repository the SHA belongs to.
- `Shipit::Webhooks::Handlers::Handler` provides a `stacks` helper that correctly scopes lookups to `Repository.from_github_repo_name(repository_name)` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`), and other handlers (e.g. `push_handler.rb`) use this scoping.
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) ignores this helper entirely and instead does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
This matches **every** `Commit` record in the database with that SHA, regardless of which repository/stack it belongs to.
- `Commit#create_status_from_github!` → `add_status` writes the status, recomputes `status`, and calls `stack.schedule_merges` (`app/models/shipit/commit.rb:165-169, 366-386`).
- `Commit#blocked?` (`app/models/shipit/commit.rb:231-237`) and `#deployable?` (`app/models/shipit/commit.rb:227-229`) directly depend on the newly written status when `stack.blocking_statuses` is configured for `shipit/checks`.

Exploit flow: an attacker who controls (or forks) a public repository that shares commit history with a victim's tracked repository (git SHAs are content-addressed, so identical commits — e.g. an initial commit, a vendored commit, or a cherry-picked commit — produce identical SHAs across unrelated repositories) sends a `status` webhook `{repository: {full_name: attacker/repo, owner: {login: attacker_org}}, sha: <shared_sha>, context: "shipit/checks", state: "failure"}`. `verify_signature` succeeds because it is signed for the attacker's own org/app. `StatusHandler#process` then updates the status for **every** `Commit` row with that SHA — including the one belonging to the victim's stack. If the victim stack's `deploy.yml` configures `blocking_statuses` including `shipit/checks`, this failure marks `commit.blocked?` true for any commit newer than the last deploy up to and including the shared commit, blocking merges/deploys (or, sent as `state: "success"`, clearing a legitimate failure and forcing `deployable?` true), an unauthorized deploy/block on a repository that never authenticated the request.

None of the existing guards prevent this: `verify_signature` authenticates the org, not the target stack; `drop_unhandled_event` only filters unknown event types; the `ExplicitParameters` schema only validates types/presence, not repository ownership; there is no `require_permission!`/`stacks` scoping applied in `StatusHandler#process`, unlike the base `Handler#stacks` helper that other handlers correctly use.

### Impact Explanation
A payload correctly authenticated for repository A mutates commit/status state that gates deploy/merge decisions for repository B's stack — this is the "payload for one repository mutating another's stack/commit" case, classified Critical. The attacker can flip `shipit/checks` to `failure` (to block a competitor's deploy pipeline / merges) or to `success` (to force `blocked?` false and let an otherwise-blocked deploy proceed), repeatably for any SHA collision they can arrange, against any stack in the same Shipit installation that has ingested a commit with that SHA.

### Likelihood Explanation
Preconditions: the attacker needs (1) their own GitHub org/repo registered with a Shipit-known GitHub App installation (something an "unprivileged" internet user can often arrange by installing a public GitHub App on their own repo), and (2) a commit SHA that also exists as a `Commit` row for the victim stack (achievable via shared history — forks, vendored/cherry-picked commits, or simply commits from a shared upstream that both stacks track) — and (3) the victim stack configured with `blocking_statuses` including `shipit/checks`. Cost is a single signed HTTP POST; the exploit is deterministic and repeatable per matching SHA.

### Recommendation
Scope `StatusHandler#process` to only commits belonging to the authenticating repository, mirroring the pattern in `Handler#stacks`:
```ruby
def process
  stacks.flat_map(&:commits).select { |c| c.sha == params.sha }.each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
or equivalently `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, ensuring the repository named in the signed payload matches the stack that owns the commit before any status is written.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, illustrative — no live GitHub required):
1. Create `stack_a` for repo `attacker/repo` and `stack_b` (victim) for repo `victim/repo`, with `stack_b`'s `deploy.yml`/stubbed `blocking_statuses` returning `['shipit/checks']`.
2. Create `commit_a = stack_a.commits.create!(sha: 'deadbeef' * 5, ...)` and `commit_b = stack_b.commits.create!(sha: 'deadbeef' * 5, ...)` with identical SHA (simulating shared history), where `commit_b` is newer than `stack_b.last_deployed_commit`.
3. Before: assert `commit_b.blocked? == false` (equality: `commit_b.stack.github_repo_name == 'victim/repo'` and no failing `shipit/checks` recorded for it).
4. Build a webhook payload `{repository: {full_name: 'attacker/repo', owner: {login: 'attacker_org'}}, sha: commit_a.sha, context: 'shipit/checks', state: 'failure'}` and call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)`.
5. After: assert `commit_b.reload.blocked? == true` (or that `commit_b.statuses.last.state == 'failure'`) even though the payload's `repository.full_name` was `'attacker/repo'`, proving `commit_b.stack.github_repo_name != payload['repository']['full_name']` yet the write still occurred — violating the invariant.
