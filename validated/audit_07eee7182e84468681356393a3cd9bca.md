## Title
Stack-scoped `ApiClient` tokens bypass their stack scope in `CCMenuController#show` - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` resolution method inherited from `Shipit::Api::BaseController` and resolves the target `Stack` directly from the client-supplied `params[:stack_id]` against `Stack.all`, instead of the caller's authorized stack scope. This breaks the binding "a stack a token authorizes versus a stack it touches": a `read:stack`-permissioned `ApiClient` token scoped to a single stack can be replayed against any other stack's `stack_id` to read its build/deploy status.

### Finding Description
`Shipit::Api::BaseController` enforces per-client stack scoping centrally: [1](#0-0) 

`current_api_client.stack_id?` restricts the queryable `Stack` set to the one the client was scoped to when it isn't a "global" (`stack_id` nil) client. Every other API controller that resolves `stack` (e.g. `DeploysController`, `StacksController` via `stack`) relies on this scoped `stacks` relation, so a stack-scoped token can never touch a stack outside its own.

`CCMenuController`, however, defines its own private `stack` method that ignores this scoping entirely: [2](#0-1) 

It calls `Stack.from_param!(params[:stack_id])` directly against the full `Stack` model, not the `stacks` scope from `BaseController`. The `require_permission :read, :stack` before_action only checks that the token *has* the `read:stack` permission string; it never checks which stack the permission applies to. `ApiClient#check_permissions!` only inspects the permission name, not scope: [3](#0-2) 

`ApiClient` records support per-stack scoping via `belongs_to :stack, optional: true`: [4](#0-3) 

and this scoping is exactly what `BaseController#stacks` is meant to enforce: [5](#0-4) 

Because `CCMenuController#stack` bypasses this, the equality that should hold — `token.authorized_stack == stack_being_read` — is broken: any valid `read:stack` token (even one legitimately scoped to a single, less-sensitive stack) can be presented with an arbitrary `stack_id` and will be granted read access to that stack's CI/deploy status.

### Impact Explanation
This matches the "High" impact class of "unauthenticated read of stack state, task streams or deploy output": possession of any single stack-scoped `read:stack` token (which may be distributed to low-trust integrations such as CI dashboards, per the `CCMenuUrlController` flow that mints per-user CCMenu tokens) is sufficient to read the deploy/build status (`lastBuildStatus`, `lastBuildLabel`, `webUrl`, lock state, etc., rendered in `shipit/ccmenu/project`) of every other stack in the Shipit instance, including stacks the token holder has no authorization for.

### Likelihood Explanation
Likelihood is high: exploitation requires only a valid `ApiClient` token with the common `read:stack` permission (no special privilege) and an HTTP GET with a different `stack_id`. `CCMenuUrlController` itself demonstrates that such stack-scoped tokens are routinely minted and handed to users/integrations (e.g. CI dashboard tooling), and the attack requires no repository write access, no webhook secret, and no session.

### Recommendation
Remove the custom `stack` override in `CCMenuController`, or reimplement it using the inherited scoped `stacks` relation from `BaseController` so it respects `current_api_client.stack_id`:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
This ensures a stack-scoped token can only resolve stacks within `current_api_client`'s authorized scope, consistent with every other API controller.

### Proof of Concept
1. As an authenticated user, create/obtain an `ApiClient` scoped to `stack_id = A` with `permissions: ['read:stack']` (e.g. via `CCMenuUrlController#fetch` or the `ApiClientsController` UI attaching `stack: A`).
2. Note the client's `authentication_token`.
3. Send `GET /api/stacks/:B/cc.xml?token=<token for A>` where `B` is a different, unrelated stack the client was never granted access to.
4. `CCMenuController#authenticate_api_client` authenticates the token successfully; `stack` resolves `Stack.from_param!(params[:stack_id])` for stack `B` directly, bypassing the `stacks` scope check that `BaseController` would otherwise apply.
5. The response renders stack `B`'s deploy/build status, proving unauthorized cross-stack read access via a token scoped to a different stack.
