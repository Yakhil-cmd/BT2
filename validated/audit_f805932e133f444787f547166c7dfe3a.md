```rust
fn copy(&mut self, range: std::ops::Range<usize>) -> Result<(), PrepareError> {
    Ok(self.output_code.extend(self.code.get(range).ok_or(PrepareError::Deserialization)?))
}
``` [1](#0-0) 

This performs a single `Vec::extend` from a byte slice, which is a `O(range.len())` memcpy operation. It is invoked either directly (for the `Version` payload) or via `copy_section`, which writes a section id/length header and then calls `copy` for the section's byte range: [2](#0-1) 

Across the whole `run()` loop, each `wp::Payload` corresponds to a non-overlapping byte range of the original module (`Version`, `TypeSection`, `ImportSection`, `FunctionSection`, `TableSection`, `MemorySection`, `GlobalSection`, `ExportSection`, `StartSection`, `ElementSection`, `DataCountSection`, `DataSection`, `CodeSectionStart`, `CustomSection`), and each such range is copied via `copy`/`copy_section` at most once. Since `wasmparser::Parser::parse_all` produces payloads whose ranges partition the input in order without overlap, the sum of all `range.len()` values across all `copy`/`copy_section` calls is bounded by `code.len()` (the size of the original module, which is exactly the fee-charged code size, per `action_creation_config.deploy_contract_cost_per_byte`). Thus the total work performed inside `copy` over the whole preparation pass is linear in the charged code size, regardless of how many sections, types, functions, or table entries the attacker crafts — those counts are additionally bounded independently by `function_limit`, `type_limit`, `table_limit`, `table_element_limit`, `local_limit`, and `function_body_size_limit` checks in `run()`, which reject modules exceeding configured limits before/while parsing (`PrepareError::TooManyFunctions`, `TooManyTypes`, `TooManyTables`, `TooManyTableElements`, `TooManyLocals`, `FunctionBodyTooLarge`). [3](#0-2) [4](#0-3) 

`output_code` is also pre-allocated with `Vec::with_capacity(code.len())`, and even where it grows beyond that (e.g., export name prefixing, added memory import/export sections for Wasmtime), `Vec` growth is amortized `O(1)` per element, so no per-call quadratic blowup is introduced by repeated `extend` calls. [5](#0-4) 

I found no code path by which pathological section counts, type shapes, or function-table shapes could make the work done inside `copy` itself super-linear in the charged code size — the byte-range coverage is disjoint and bounded by the input size, and the surrounding per-section/per-element limits are enforced independently before any unbounded iteration could occur.
