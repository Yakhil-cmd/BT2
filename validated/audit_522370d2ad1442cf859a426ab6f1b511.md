### Title
`StatusHandler#process` inserts a `Shipit::Status` on any commit matching a global SHA, without scoping to the webhook's authenticated repository - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` queries `Commit.where(sha: params.sha)` across the entire `commits` table and calls `commit.create_status_from_github!(params)` on every match, never consulting `Repository.from_github_repo_name` (via the `stacks` helper) to restrict results to the repository whose signature `WebhooksController#verify_signature` validated. Other handlers (`CheckSuiteHandler`, `PushHandler`) explicitly scope through `stacks` (which is built from `Repository.from_github_repo_name(repository_name)`), but `StatusHandler` does not, so a correctly-signed webhook for attacker-owned repo A can write a `Status` row (with attacker-chosen `context`/`description`/`target_url`) onto a `Commit` belonging to a completely different stack/repo B, as long as any commit sha collides between A and B's histories.

### Finding Description
The binding the question implies should hold is: `commit.stack.repository.full_name == payload['repository']['full_name']` for every `commit` on which `create_status_from_github!` is invoked, since `WebhooksController#verify_signature` only proves the signature matches `Shipit.github(organization: repository_owner)` for the repository named in the payload [1](#0-0) . Tracing `StatusHandler#process`:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 

This never calls `stacks` (the helper defined on `Handler` that does `Repository.from_github_repo_name(repository_name)&.stacks || Stack.none`) [3](#0-2) . Compare with `CheckSuiteHandler#process`, which correctly scopes via `stacks.where(branch: ...)` before touching commits [4](#0-3) , and `PushHandler#process`, which scopes via `stacks.not_archived.where(branch:)` [5](#0-4) . `StatusHandler` is the outlier that queries the global `Commit` table directly by `sha` with no repository filter at all.

`Commit#create_status_from_github!` then unconditionally persists the status against that commit's own stack: `statuses.replicate_from_github!(stack_id, github_status)` [6](#0-5) , and `Status.replicate_from_github!` writes `state`, `description`, `target_url`, `context`, `created_at` verbatim from the payload [7](#0-6) .

Exploit flow: the attacker owns/controls repo A (e.g. a fork). They craft a commit whose SHA collides with (or is identical to) a commit that already exists in target stack B's `commits` table — trivial if B's history includes a commit that was also pushed/cherry-picked/merged into A, since Git SHAs are content-addressed and identical commit content yields an identical SHA regardless of which repository holds it. The attacker then sends a `status` event webhook to `POST /webhooks` for repo A, correctly signed with A's own webhook secret (which the attacker/repo-owner legitimately possesses for their own repo), with `context`/`description`/`target_url` set to arbitrary strings. `verify_signature` validates the signature against A's org/secret and passes [8](#0-7) . `StatusHandler#process` then finds the `Commit` row belonging to stack B (because it queries all commits by sha, unscoped) and inserts a `Shipit::Status` under B's `stack_id` with the attacker's chosen strings.

Existing guards that were checked and do not prevent this:
- `verify_signature` only proves the payload's own repo/org signature is valid; it says nothing about which `Commit`/`Stack` rows the handler is permitted to touch [1](#0-0) .
- `drop_unhandled_event` only checks the event type is registered, not the repository [9](#0-8) .
- `ExplicitParameters` schema for `StatusHandler` only validates types/presence of `sha`, `state`, `description`, `target_url`, `context`, `created_at`, `branches`; it enforces no repository binding [10](#0-9) .
- `Repository.from_github_repo_name` exists and is used by sibling handlers via `stacks`, but `StatusHandler` simply never calls it [11](#0-10) , [3](#0-2) .

The `params.branches` field mentioned in the question is indeed accepted but entirely unused in `process` [12](#0-11)  — but that unused field is not itself the vulnerability; the root cause is the complete absence of any repository/stack scoping in the SHA lookup, which is a broader and more direct cross-repository write path than "smuggling a branch name."

### Impact Explanation
Any commit-sha collision between an attacker-controlled repository and a target repository lets the attacker write a `Shipit::Status` row into the target stack's commit with arbitrary `context`, `description`, and `target_url` strings, without ever authenticating against the target repository's webhook secret. Because `Status#enable_ci_on_stack` runs `after_create` and status transitions can trigger `deployable_status` hooks and `ProcessMergeRequestsJob` (per `Commit#add_status`/`create_status_from_github!` behavior shown in `test/models/commits_test.rb`), a forged success/failure status can influence CI gating and merge-request automation on a stack the attacker does not own or control. This is a cross-repository mutation of another repository's `Commit`/`Status` records, matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team").

### Likelihood Explanation
The attacker needs: (1) ability to run/own a GitHub repository (any unprivileged GitHub user can fork or create one) with a valid webhook configured to Shipit for that repo — this is normal, unprivileged setup within scope; (2) a commit whose SHA is present in the target stack's `commits` table. Since SHAs are content-derived, this is trivially satisfiable when the attacker's repo shares any history/commit with the victim repo (common for forks, or when an attacker crafts a commit tree/blob identical to a known public commit of the target). No secrets, sessions, or privileged roles are required — only the attacker's own legitimate webhook secret for their own repo. This is repeatable against any target stack whose commit SHAs the attacker can reproduce or guess (public repos make source commits public, so exact SHA reproduction is generally feasible for any public commit).

### Recommendation
Scope `StatusHandler#process` through the same `stacks` mechanism used by other handlers, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This ensures only commits belonging to stacks whose `Repository` matches `payload['repository']['full_name']` (and therefore the signature verified by `verify_signature`) can receive a status write.

### Proof of Concept
Minitest plan (place under `test/models/shipit/webhooks/handlers/status_handler_test.rb`, not shown/created here per scope, but structured as follows):

1. Create `stack_a` bound to `Repository` `attacker/repo-a`, and `stack_b` bound to `Repository` `victim/repo-b`.
2. Create `commit_b` under `stack_b` with `sha: 'deadbeef...'`.
3. Build `payload` for a `status` event with `repository.full_name = 'attacker/repo-a'`, `sha: 'deadbeef...'`, `context: 'evil-context'`, `description: 'evil-description'`, `target_url: 'http://evil.example.com'`.
4. Assert the binding before tracing: `commit_b.stack.repository.full_name` ('victim/repo-b') `!= payload['repository']['full_name']` ('attacker/repo-a').
5. Call `Shipit::Webhooks::Handlers::StatusHandler.new(payload).process` (bypassing controller-level signature check, since the point is that the handler itself has no repo scoping — signature validation is orthogonal to this bug).
6. Assert `commit_b.statuses.count` increased by 1, and the new `Shipit::Status` row has `context == 'evil-context'`, `description == 'evil-description'`, `target_url == 'http://evil.example.com'`, while it belongs to `stack_id == stack_b.id` — proving repo A's payload mutated repo B's stack data.
7. As a control, assert that fixing `process` to use `stacks.each { |stack| stack.commits.where(sha: ...) }` (scoped to `Repository.from_github_repo_name('attacker/repo-a')`) results in zero statuses created on `commit_b`, since `stack_a.commits` does not include `commit_b`.
