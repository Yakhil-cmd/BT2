## Title
Webhook signature verification authenticates the payload's `repository.owner.login` while every event handler acts on the independently-controlled `repository.full_name` field, allowing cross-organization webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to validate an inbound webhook against using `repository_owner`, a value read straight out of the untrusted JSON body via `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). Every `Shipit::Webhooks::Handlers::Handler` subclass, however, resolves the `Repository`/`Stack` it will act on using a *different* field of the same untrusted body: `payload.dig('repository', 'full_name')`. Nothing in the request path checks that these two values are consistent, so an attacker who legitimately controls one GitHub App installation (and therefore genuinely knows that installation's `webhook_secret`) can produce a validly-signed payload whose `repository.owner.login` matches their own org (satisfying signature verification) while `repository.full_name` names a completely different, victim-owned repository tracked by the same Shipit instance.

### Finding Description [1](#0-0) 

`verify_signature` does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
This binds "which organization's secret signed this request" strictly to the `repository.owner.login` sub-field.

Once verification passes, `create` dispatches the full raw payload to handlers: [2](#0-1) 

Every handler's target repository/stack lookup goes through the shared base class: [3](#0-2) 
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```
Concrete handlers such as `PushHandler` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) and the various `PullRequest::*Handler` classes (e.g. `opened_handler.rb:50-54`, `closed_handler.rb:49-53`, `labeled_handler.rb:65-68`) all resolve their target `Repository`/`Stack` via `full_name`, never cross-checking it against `owner.login`.

This is exactly the "authenticated field vs. acted-upon field" divergence described in the analog bug class: the signature verification binds trust to `repository.owner.login`, but the code that decides *which repository is written to* (i.e., which `Stack` receives a sync/PR/label/status event) binds to `repository.full_name`. These two JSON leaves are attacker-controlled and independent, so the equality `owner_login_used_for_auth == owner_implied_by_full_name_used_for_action` is never enforced.

### Impact Explanation
An attacker who owns/administers any GitHub organization that has a Shipit GitHub App installed for it (a normal, unprivileged setup step available to any of the "multiple GitHub organizations" configurations described in `docs/setup.md`) legitimately possesses that org's `webhook_secret`. They can:
1. Sign an arbitrary JSON body with their own known `webhook_secret`.
2. Set `repository.owner.login` = their own org (so `Shipit.github(organization: ...)` resolves to their own app config and signature verification succeeds).
3. Set `repository.full_name` = `victim-org/victim-repo`, a repository tracked by Shipit under a completely different, unrelated GitHub App/organization.

The forged event is then processed as if it legitimately originated from GitHub for the victim's repository: e.g. a forged `push` event triggers `stack.sync_github(expected_head_sha: ...)` for the victim's stacks, forged `pull_request` events can archive/unarchive review stacks or mutate `PullRequest` records tied to the victim repository, and forged `status`/`check_suite` events can inject fabricated CI states for the victim's commits. Because Shipit's continuous-deployment/merge-queue gating and stack state machine consume this synced/forged data, this can escalate into unauthorized synchronization, spurious stack state changes, or interference with the merge/deploy gating logic of a repository the attacker does not control and was never granted access to — crossing the "cross-repository writes" / "unauthorized deploy" boundary called out as Critical impact.

### Likelihood Explanation
Exploitation requires only that the attacker control (or have installed) one legitimate, unprivileged GitHub App/organization entry in Shipit's multi-org configuration — a scenario explicitly supported and documented (`docs/setup.md:182-209`). No Shipit session, `ApiClient` token, or GitHub write access to the victim repository is required; only knowledge of one's own app's `webhook_secret`, which the attacker legitimately possesses by design. This makes the attack straightforward for any onboarded, unprivileged organization in a multi-org Shipit deployment.

### Recommendation
After successful signature verification, enforce that the organization implied by `repository.full_name` (or `organization.login` for org-level events) equals the `repository_owner` value that was used to select the verifying GitHub App/secret, rejecting the webhook (422) on mismatch. Alternatively, derive the verifying app strictly from a value that the handlers also use to resolve the target repository (i.e., use `full_name`'s owner segment consistently in both places) so the two lookups can never diverge.

### Proof of Concept
1. Configure two GitHub App orgs in `config/secrets.yml` (`attacker-org`, `victim-org`), as supported by `docs/setup.md:182-209`.
2. Attacker knows `attacker-org`'s `webhook_secret` (they administer that org/app).
3. Attacker crafts a `push` event payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<arbitrary sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org_webhook_secret, raw_body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `WebhooksController#verify_signature` calls `Shipit.github(organization: 'attacker-org')` and successfully verifies the signature against the attacker's own known secret.
6. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name('victim-org/victim-repo')` (per `handler.rb:36-38`) and calls `stack.sync_github(expected_head_sha:)` for the victim's stack — an action the attacker was never authorized to trigger.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
