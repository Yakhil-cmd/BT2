### Title
Independent per-recipient rounding of `earned_headers_commission_share` can mint extra spendable bytes not backed by the payer's `headers_commission` - (File: headers_commission.js)

### Summary
Any unpermissioned unit author can multi-author a unit and freely choose how many co-authors receive `earned_headers_commission_recipients` shares, as long as the declared shares sum to exactly 100. When that unit wins a parent's headers commission, `calcHeadersCommissions()` splits the fixed `headers_commission` amount among the declared recipients by independently rounding `full_amount * share / 100` for each recipient with `Math.round`. Because each recipient's payout is rounded independently rather than derived from a single running remainder, the sum of the rounded payouts can exceed the actual `full_amount` collected from the payer unit. This is the same root-cause class as the reported `Scaler.scale()` bug (naive fixed-point division/rounding applied per-unit-of-value without reconciling the total), except here the direction is inflationary rather than lossy: instead of "many small stakes round down to 0," "many small shares round up past their true fraction," and the aggregate exceeds 100% of the divisible amount.

### Finding Description
`validateHeadersCommissionRecipients()` in `validation.js` only enforces that the sum of declared `earned_headers_commission_share` values equals exactly 100: [1](#0-0) 

It does not constrain the *number* of recipients (bounded only by `MAX_AUTHORS_PER_UNIT`), nor does it prevent shares like `1, 1, 1, ..., 1` (many 1% shares) that individually round awkwardly against a small `headers_commission` amount.

At commission-distribution time, `calcHeadersCommissions()` computes, for every winning child unit that declared external/multiple recipients, an independent rounded amount per recipient: [2](#0-1) [3](#0-2) 

Each `amount = Math.round(full_amount * share / 100.0)` is computed and inserted separately into `headers_commission_contributions`, then summed per address into `headers_commission_outputs`: [4](#0-3) 

Because rounding is applied per-recipient instead of using a cumulative/remainder-tracking split (e.g., largest-remainder method), the sum `Σ round(full_amount * share_i / 100)` is not guaranteed to equal `full_amount`. With many small shares (e.g., dozens of 1% shares) chosen adversarially relative to `full_amount`, the sum of independently-rounded shares can exceed `full_amount`, silently minting extra spendable value that was never actually paid by any payer unit.

These `headers_commission_outputs` are later spendable as `type: "headers_commission"` inputs in ordinary payment messages and are validated purely by summing recorded output rows (via `mc_outputs.calcEarnings`), with no cross-check against the original `headers_commission` amount actually collected from any specific payer: [5](#0-4) 

### Impact Explanation
If the rounding-up bias can be made to exceed the true `headers_commission` paid by parent units, extra base-currency (bytes) become spendable that were never actually paid into the system by anyone — this is a supply-inflation bug, one of the explicitly in-scope high-impact categories (concrete unauthorized spending / supply inflation). Any unprivileged multi-author unit poster can attempt to trigger this by carefully choosing the number and size of `earned_headers_commission_share` entries, without needing any special network position (no malicious-peer/hub assumption, no operator privilege).

### Likelihood Explanation
Likelihood is constrained by several factors that are not fully verified here due to tool-call limits: (1) whether the maximum bias per commission event is large enough to be economically significant given typical `headers_commission` magnitudes and `MAX_AUTHORS_PER_UNIT`, (2) whether repeated wins (an attacker's unit winning headers commission many times) can accumulate the bias to a meaningful sum, and (3) whether any other reconciliation exists elsewhere in the codebase that caps total emitted `headers_commission_outputs` against total collected `headers_commission` across the ledger (not found in the reviewed code, but not exhaustively ruled out). The rounding bias per single distribution event is small (bounded by roughly half a unit per recipient), so achieving significant inflation likely requires many repeated wins and/or intentionally crafted share distributions, making this feasible but requiring sustained effort rather than a one-shot exploit.

### Recommendation
Replace independent per-recipient rounding with a total-preserving allocation method (e.g., largest-remainder/Hamilton apportionment): compute each recipient's floor amount, sum the floors, then distribute the leftover remainder (`full_amount - Σ floor`) one unit at a time to the recipients with the largest fractional remainders, guaranteeing `Σ amount_i === full_amount` exactly. Apply the same fix to the MySQL `ROUND(...)` SQL path in `calcHeadersCommissions` (`headers_commission.js`, lines ~50-51) for consistency between storage backends.

### Proof of Concept
Conceptual PoC (requires further validation against actual `MAX_AUTHORS_PER_UNIT` and typical `headers_commission` sizes, which could not be fully checked within the available tool budget):
1. Craft a multi-author unit with N co-authors and an `earned_headers_commission_recipients` array where shares are e.g. `[1,1,...,1]` (N shares of 1, summing to 100, N=100 would require ≤ `MAX_AUTHORS_PER_UNIT`; adjust N/shares to whatever the actual author-count cap allows while still summing to 100).
2. Get this unit selected as the winning child for a parent unit's `headers_commission` via the existing `getWinnerInfo` selection logic in `headers_commission.js` (deterministic hash-based selection over candidate children — reachable by simply constructing qualifying sibling units).
3. Let `calcHeadersCommissions()` run; compare `Σ headers_commission_contributions.amount` for that unit/payer pair against the payer's actual `headers_commission` column value.
4. If `Σ amount > full_amount`, the excess is confirmed as unbacked value inserted into `headers_commission_outputs`, later spendable as `type: "headers_commission"` payment inputs per `validation.js:2582-2599`.

function validateHeadersCommissionRecipients(objUnit, cb){
	if (objUnit.authors.length > 1 && typeof objUnit.earned_headers_commission_recipients !== "object")
		return cb("must specify earned_headers_commission_recipients when more than 1 author");
	if ("earned_headers_commission_recipients" in objUnit){
		if (!isNonemptyArray(objUnit.earned_headers_commission_recipients))
			return cb("empty earned_headers_commission_recipients array");
		var total_earned_headers_commission_share = 0;
		var prev_address = "";
		for (var i=0; i<objUnit.earned_headers_commission_recipients.length; i++){
			var recipient = objUnit.earned_headers_commission_recipients[i];
			if (!isPositiveInteger(recipient.earned_headers_commission_share))
				return cb("earned_headers_commission_share must be positive integer");
			if (hasFieldsExcept(recipient, ["address", "earned_headers_commission_share"]))
				return cb("unknown fields in recipient");
			if (!isValidAddress(recipient.address))
				return cb("invalid recipient address checksum");
			if (recipient.address <= prev_address)
				return cb("recipient list must be sorted by address");
			total_earned_headers_commission_share += recipient.earned_headers_commission_share;
			prev_address = recipient.address;
		}
		if (total_earned_headers_commission_share !== 100)
			return cb("sum of earned_headers_commission_share is not 100");
	}
