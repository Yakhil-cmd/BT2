### Title
Webhook signature verified against `repository.owner.login`/`organization.login`, but event handlers act on unrelated fields (`repository.full_name` or bare commit `sha`) — cross-repository forged CI status triggers unauthorized deploys - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate an inbound webhook's HMAC signature against based on `repository.owner.login` (or `organization.login`) pulled from the *unverified* JSON body. [1](#0-0) [2](#0-1) 

Shipit is explicitly designed to be multi-tenant: `config/secrets.*.yml` allows configuring several independent GitHub organizations, each with its own `webhook_secret`. [3](#0-2) 

Once the signature check passes for *some* configured organization, the raw payload is dispatched to event handlers that determine **which stack/repository/commit to mutate using a completely different, unauthenticated-by-binding field**:
- `Webhooks::Handlers::Handler#stacks` resolves the target `Repository` via `payload.dig('repository', 'full_name')`, not `repository.owner.login`. [4](#0-3) 
- `StatusHandler#process` is even more permissive: it does not scope by repository/organization at all — it looks up `Commit.where(sha: params.sha)` across the **entire** Shipit instance and calls `create_status_from_github!` on every match. [5](#0-4) 

There is no code path that checks "the organization whose secret verified this request" equals "the organization/repository the handler is about to mutate."

### Finding Description
The binding that should hold is:
`organization authenticated by verify_signature == organization/repository whose state is mutated by the handler`

In `verify_signature`, `Shipit.github(organization: repository_owner)` is used purely to pick the HMAC key; `repository_owner` is read straight from the attacker-controlled JSON body before signature verification occurs. [6](#0-5) 

Because Shipit supports multiple organizations, each with an independently configured `webhook_secret` (owned/known by whoever set up that org's GitHub App — a legitimate, non-privileged actor with respect to *other* organizations' stacks hosted on the same Shipit instance), an attacker who legitimately controls Organization A's webhook secret can:

1. Compute a valid `X-Hub-Signature` using Organization A's `webhook_secret` over a JSON body where `repository.owner.login` (or `organization.login`) is set to `"OrgA"` — this passes `verify_signature`.
2. In that same signed body, set the `event` to `status` and supply a `sha` belonging to a commit that lives in Organization B's (the victim's) repository/stack — a value entirely uncorrelated with `OrgA`.
3. `StatusHandler#process` finds the matching `Commit` purely `Commit.where(sha: params.sha)` — with no repository/organization filter — and calls `commit.create_status_from_github!(params)`, letting the attacker fabricate an arbitrary CI status (e.g. `state: 'success'`) for the victim's commit. [7](#0-6) 

A forged `success` status flips `Commit#deployable?` and feeds `Commit#schedule_continuous_delivery`, which enqueues `ContinuousDeliveryJob` when `stack.continuous_deployment?` is true. [8](#0-7) [9](#0-8) [10](#0-9) 

`ContinuousDeliveryJob#perform` then calls `stack.trigger_continuous_delivery`, which builds and runs a real `Deploy` for Organization B's stack. [11](#0-10) [12](#0-11) 

For the `push` event, the same root cause exists one level less severely: `Handler#stacks` resolves stacks via `repository.full_name` from the body, not the organization that was cryptographically authenticated, so the same style of cross-tenant forged "sync" (and ultimately CI-status/deploy) triggering applies to any handler built on `Handler#stacks`. [4](#0-3) [13](#0-12) 

### Impact Explanation
This meets the Critical bar: "an unauthorized deploy." An entity that legitimately controls one organization's webhook credentials on a shared/multi-org Shipit instance can forge GitHub `status` webhooks for **any commit in any other organization's repository tracked by the same Shipit instance**, and — if that victim stack has `continuous_deployment` enabled — cause a real deploy to run on the victim's infrastructure with attacker-chosen "success" CI state, without ever touching the victim organization's actual GitHub repository, webhook secret, or Shipit account.

### Likelihood Explanation
Exploitability requires only that the Shipit deployment be configured for more than one GitHub organization (an explicitly documented and supported configuration, see `config/secrets.development.shopify.yml`) and that the attacker legitimately controls one of those organizations' GitHub App webhook secret — which is not "privileged access to Shipit" in the sense excluded by scope rules (it does not require `api_clients_secret`, a Shipit session, or a GitHub App private key belonging to the victim). No collusion with Shipit administrators or victim organization is needed; the attacker only needs to know a commit SHA belonging to the victim (obtainable from a public repo or PR).

### Recommendation
- In `WebhooksController#verify_signature`/`create`, after signature verification, re-derive the organization from the verified request context and pass it explicitly into `Shipit::Webhooks.for_event(event)` handlers, requiring each handler to confirm that the resolved `Repository`'s owner/organization equals the authenticated organization before mutating any state.
- In `Webhooks::Handlers::Handler#stacks`, scope repository resolution by both `full_name` and the authenticated organization, rejecting mismatches.
- In `StatusHandler#process`, scope `Commit.where(sha: params.sha)` to commits belonging to stacks/repositories owned by the authenticated organization, not a global lookup.

### Proof of Concept
1. Attacker legitimately administers GitHub App/organization `"attacker-org"` configured in this Shipit instance, and thus knows its `webhook_secret`.
2. Attacker finds a commit SHA (`victim_sha`) belonging to a stack under organization `"victim-org"` with `continuous_deployment: true`.
3. Attacker crafts:
```json
{
  "sha": "victim_sha",
  "state": "success",
  "context": "ci/travis",
  "repository": { "owner": { "login": "attacker-org" } }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC_SHA1(attacker-org_webhook_secret, body)` and POSTs to `/webhooks` with header `X-Github-Event: status`.
5. `verify_signature` resolves `repository_owner == "attacker-org"`, fetches `attacker-org`'s app, and the signature validates successfully.
6. `StatusHandler#process` executes `Commit.where(sha: "victim_sha")`, finds the victim's commit (no organization check), and calls `create_status_from_github!`, marking it deployable.
7. If `victim-org`'s stack has continuous deployment enabled, `ContinuousDeliveryJob` triggers a real deploy shortly after.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

```ruby
    def trigger_continuous_delivery
      return if cached_deploy_spec.blank?

      commit = next_commit_to_deploy

      if should_resume_continuous_delivery?(commit)
        continuous_delivery_resumed!
        return
      end

      if should_delay_continuous_delivery?(commit)
        continuous_delivery_delayed!
        return
      end

      begin
        trigger_deploy(commit, Shipit.user, env: cached_deploy_spec.default_deploy_env)
      rescue Task::ConcurrentTaskRunning
      end
    end
```
