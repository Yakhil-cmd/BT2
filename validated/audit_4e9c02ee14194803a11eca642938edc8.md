### Title
Cross-repository commit status forgery via unscoped SHA lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` authenticates a webhook delivery against the GitHub App/organization derived from the payload's own `repository.owner.login`/`organization.login` field [1](#0-0) . That authentication only proves the payload came from a legitimate, signed delivery for *that* organization/repository. However, `StatusHandler#process` never re-checks that the commit it mutates actually belongs to the repository/stack that was authenticated — it looks the commit up globally by SHA across the entire `commits` table [2](#0-1) . This breaks the binding "organization authenticated == repository written": any organization/repository that can deliver a signed `status` webhook can write a `CommitStatus` onto a `Commit` row owned by a completely different stack/repository, as long as the SHA values coincide.

### Finding Description
The `Handler` base class defines a `stacks` helper that scopes lookups to `Repository.from_github_repo_name(repository_name)` where `repository_name` is `payload.dig('repository', 'full_name')` [3](#0-2) . Every other handler that mutates state uses this scoped `stacks` relation (e.g. `PushHandler#process` calls `stacks.not_archived.where(branch:)` [4](#0-3) ).

`StatusHandler` is the outlier: it does not use `stacks`/`repository_name` at all:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 

`Commit` is a global table shared by all stacks (`belongs_to :stack`, no default scoping by repository) [5](#0-4) . `create_status_from_github!` records the status against the commit's own `stack_id`, and it can trigger `Hook.emit(:deployable_status, ...)` and `stack.schedule_merges` when the status changes deployability [6](#0-5) [7](#0-6) . `Commit#deployable?` is directly driven by the status state: `!locked? && (stack.ignore_ci? || (success? && !blocked?))` [8](#0-7) .

**Binding broken (equality that should hold but doesn't):**
`organization/repository authenticated by verify_signature` == `repository/stack whose Commit row is mutated by StatusHandler`

Before the attack: a victim stack B has a commit with SHA `S` (reachable e.g. via a shared history, fork, cherry-pick, or vendored dependency commit that is byte-identical and thus SHA-identical to a commit in the attacker's own repository A). Any legitimate GitHub `status` event on repository A, signed with A's own webhook secret, is verified by `verify_signature` using `Shipit.github(organization: repository_owner)` where `repository_owner` is A's org login — so the signature check passes and is entirely correct for repository A. After the attack: `StatusHandler#process` still writes a `success`/`failure` `CommitStatus` onto stack B's `Commit` row because the SQL lookup `Commit.where(sha: params.sha)` has no repository/stack filter, flipping `success?`/`deployable?` for commit `S` in stack B and potentially triggering `stack.schedule_merges` / continuous-deployment scheduling for a stack the attacker never authenticated against.

### Impact Explanation
This lets an attacker who only controls (or has webhook-emitting rights on, e.g. via their own CI marking commit statuses) an unrelated, unprivileged repository forge the CI/deploy-readiness status of a commit belonging to a victim's stack, without ever authenticating against that stack's organization. Since `deployable?` and the continuous-deployment scheduling path both key off the forged status, this can be used to mark an otherwise-blocked/failing commit as `success`, unblocking or triggering an unauthorized deploy path in a target stack (`Commit#schedule_continuous_delivery` / `stack.schedule_merges`) — this maps to the "unauthorized deploy" impact category.

### Likelihood Explanation
Exploitability depends on being able to get two commits with the *identical* SHA into two different stacks (git SHAs are content-addressed, so this is realistic for forks, mirrored/vendored dependency commits, or monorepo-derived stacks sharing history) and on the attacker having any means to trigger a signed `status` webhook for their own controlled repository (routine CI usage). No privileged Shipit credentials, webhook secrets, or GitHub App keys are needed on the attacker's side — only ownership of some repository the app is installed on. This is a moderate-likelihood, code-level scoping bug rather than a purely theoretical issue, since the root cause (`Commit.where(sha:)` with no stack/repo filter) is directly visible in the handler.

### Recommendation
Scope the lookup in `StatusHandler#process` the same way every other handler does: resolve the target stacks via `stacks` (i.e., `Repository.from_github_repo_name(payload.dig('repository','full_name'))`) and restrict `Commit.where(sha: params.sha, stack_id: stacks.ids)` (or iterate `stacks.flat_map(&:commits)` filtered by sha) before calling `create_status_from_github!`, so a status event can only ever affect commits that belong to the repository that was actually authenticated by `verify_signature`.

### Proof of Concept
1. Attacker creates public repository `attacker/repo` that is either the fork origin of, or otherwise shares an identical commit `S` with, victim stack `victim/repo` tracked by Shipit (identical SHA achievable via fork/cherry-pick/shared vendor commit).
2. Attacker's own CI (or manual `POST /repos/attacker/repo/statuses/S`) causes GitHub to send a legitimately signed `status` webhook for `attacker/repo` with `sha: S, state: "success"`.
3. `WebhooksController#verify_signature` correctly verifies this payload using `attacker`'s configured GitHub App/org webhook secret and proceeds [1](#0-0) .
4. `StatusHandler#process` runs `Commit.where(sha: 'S')`, which also matches the `Commit` row belonging to `victim/repo`'s stack, and calls `create_status_from_github!` on it, recording a `success` status for the victim's stack without any authentication against `victim/repo`'s organization [2](#0-1) .
5. The victim commit's `deployable?`/`status` flips based on the forged status, potentially unblocking deploy/merge scheduling for the victim stack.
