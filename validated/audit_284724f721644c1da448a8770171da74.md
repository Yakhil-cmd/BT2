### Title
Webhook signature is verified against `repository.owner.login` while stack-targeting handlers key off `repository.full_name`, allowing a webhook sender authenticated for one organization to trigger syncs on another org's stack - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to check against using `repository_owner`, computed as `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). But `Shipit::Webhooks::Handlers::Handler#repository_name` (and every handler that inherits from it, e.g. `PushHandler`) resolves the target `Repository`/`Stack` using a *different* field of the same payload: `payload.dig('repository', 'full_name')`. These two fields are never cross-checked against each other. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
The equality that should hold is: `organization that authenticated the signature == owner of the repository whose stacks are acted upon`. It does not hold, because these are read from independent JSON keys inside the attacker-controlled request body:

- Signature check organization: `params.dig('repository', 'owner', 'login')` [2](#0-1) 
- Repository/stack lookup key: `payload.dig('repository', 'full_name')` [4](#0-3) 

`Repository.from_github_repo_name` splits `full_name` on `/` and looks up any `Repository` row by `owner`/`name`, with no relation back to `repository.owner.login`: [5](#0-4) 

Because a Shipit deployment can be configured for multiple GitHub organizations, each with its own `webhook_secret` (`config/secrets*.yml` show a `github: { OrgOne: {...}, OrgTwo: {...} }` structure), an entity that is a legitimate webhook sender for `OrgOne` (i.e., knows `OrgOne`'s `webhook_secret`, e.g. because they administer that org's GitHub App or can trigger its webhook delivery) can send a request where:
- `repository.owner.login = "OrgOne"` (so `verify_signature` selects and validates against `OrgOne`'s secret, which passes),
- `repository.full_name = "OrgTwo/victim-repo"` (an unrelated, victim organization's repository also tracked by the same Shipit instance). [6](#0-5) 

`PushHandler#process` then resolves stacks purely from `full_name` and enqueues a sync for the victim's stack using an attacker-supplied `after` SHA: [7](#0-6) 

`GithubSyncJob#perform` uses that `expected_head_sha` to drive `fetch_missing_commits`/`append_commit`, and always ends by scheduling `CacheDeploySpecJob`, feeding the (attacker-chosen) synced head into the deploy-spec cache pipeline for the victim's stack: [8](#0-7) 

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" binding explicitly called out in scope. An attacker who is a legitimate webhook sender for their own configured organization (not privileged for the victim org at all) can inject forged push/status/check_suite/pull_request-family events that address a stack belonging to an entirely different organization tracked by the same Shipit instance, forcing `GithubSyncJob`/`CacheDeploySpecJob` to run against attacker-influenced state (`expected_head_sha`) for that victim stack. Depending on downstream deploy-spec caching and continuous-delivery triggers keyed off newly synced commits, this can escalate into cross-repository state manipulation and potentially an unauthorized sync/deploy trigger for a repository the attacker does not control — satisfying the "cross-repository writes" / "unauthorized deploy" impact bar.

I was not able to fully trace whether `CacheDeploySpecJob` or subsequent continuous-deployment logic in `app/models/shipit/stack.rb` / `app/jobs/shipit/continuous_delivery_job.rb` can be driven to an actual automatic deploy purely from a synced commit with no independent CI status check, so the exact severity ceiling (state corruption vs. an actual triggered deploy) is not fully confirmed within this pass.

### Likelihood Explanation
Requires: (1) a Shipit instance configured with more than one organization (multi-org configs are a documented, supported feature — see `secrets_double_github_app.yml`), and (2) the attacker being a legitimate webhook sender for at least one of the configured organizations (i.e., knowing that org's `webhook_secret`, which they would if they administer their own org's installed GitHub App). No access to the victim org, no Shipit account, and no `ApiClient` token is required. The payload shape is simple JSON and easily crafted.

### Recommendation
In `WebhooksController#verify_signature`, after signature verification succeeds, also assert that `repository_owner` matches the owner portion parsed from `repository.full_name` (and `organization.login` when used as fallback) before dispatching to handlers, rejecting the request otherwise. Alternatively, make `Handler#repository_name` (and all subclasses) derive the target repository strictly from the same field validated during signature verification, rather than an independent field of the payload.

### Proof of Concept
Given a Shipit instance configured with two orgs, `OrgOne` (attacker-controlled webhook secret `S1`) and `OrgTwo` (victim, has a tracked repo `OrgTwo/victim-repo` with a `master`-branch stack):

```
POST /webhooks HTTP/1.1
X-Github-Event: push
X-Hub-Signature: sha1=<HMAC-SHA1(S1, body)>

body = {
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "OrgOne" },
    "full_name": "OrgTwo/victim-repo"
  }
}
```

`verify_signature` reads `repository_owner = "OrgOne"`, fetches `Shipit.github(organization: "OrgOne")`, and validates the signature against `S1` — succeeds. `PushHandler#process` then resolves stacks via `Repository.from_github_repo_name("OrgTwo/victim-repo")`, enqueuing `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` for the victim's stack.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
```
