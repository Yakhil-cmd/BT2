### Title
`Shipit::CCMenuUrlController#client` mints a global `read:stack` `ApiClient` with `stack_id == nil` instead of scoping it to the requested stack - ([File: app/controllers/shipit/ccmenu_url_controller.rb])

### Summary
`CCMenuUrlController#client` calls `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')` without including `stack:` in either the `create_with` hash or the `find_or_create_by!` lookup criteria. The resulting `ApiClient` therefore has `stack_id == nil`, and per `Api::BaseController#stacks` (`current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`), a nil `stack_id` is treated as "unlimited" — granting `read:stack` on every stack in the system, not just the stack the user was viewing when they clicked "Fetch URL".

### Finding Description
The intended binding is: `client.stack_id == stack.id` (the `ApiClient` minted for stack A's CCMenu URL should only authorize reads of stack A). The actual code produces `client.stack_id == nil`: [1](#0-0) 

Because `find_or_create_by!(creator: current_user, name: 'CCMenu Client')` does not include `stack:` in its search/creation attributes, the very first time any user clicks "Fetch URL" for *any* stack, a single global `ApiClient` record is created with `stack_id = nil` and `permissions = ['read:stack']`. Every subsequent click by that same user, for any other stack, finds that same record (memoized per-request via `find_or_create_by!`, persisted via ActiveRecord's uniqueness-by-attributes lookup) and returns the *same* token, regardless of which stack was requested.

`Api::BaseController#stacks` explicitly treats a nil `stack_id` as unrestricted access: [2](#0-1) 

This token is checked only via `ApiClient#check_permissions!`, which just checks the `permissions` array (`read:stack`) and never checks `stack_id` against the requested stack — the stack scoping is entirely delegated to `stacks`/`stack` in `BaseController`, and (separately, worth noting) `Api::CCMenuController` overrides `stack` to call `Stack.from_param!` directly rather than `stacks.from_param!`, bypassing scoping outright for the ccmenu endpoint specifically: [3](#0-2) 

So there are two compounding problems reachable from this controller: (1) the minted client's `stack_id` is never set at all (global by construction), and (2) even a correctly-scoped client would not be enforced by `CCMenuController#show`, since its `stack` method skips the `stacks` scope. Either one alone is sufficient to let a token minted for stack A's CCMenu URL read stack B's CCMenu status.

Attack flow:
1. Authenticated Shipit user (any user, no special role) opens the settings page for stack A and clicks "Fetch URL", hitting `GET /ccmenu/*stack_id` with `stack_id=A`.
2. `CCMenuUrlController#client` creates (or reuses) an `ApiClient` with `permissions: ['read:stack']`, `stack_id: nil`, and returns a signed `authentication_token`.
3. The attacker then issues `GET /api/stacks/B/ccmenu?token=<token>` for an unrelated stack B (or any stack in the system).
4. `Api::CCMenuController#show` calls `require_permission!(:read, :stack)` which only checks `permissions.include?('read:stack')` — true — and resolves `stack` via `Stack.from_param!(params[:stack_id])` with no scoping to `current_api_client.stack_id` at all.
5. Stack B's CCMenu XML (build status, last build label/time, web URL) is returned to the attacker.

No existing guard (`require_permission`, `ExplicitParameters`, model validations, `verify_signature`, etc.) prevents this divergence — the missing piece is simply that `stack:` is never part of the `ApiClient` creation criteria, and separately, `CCMenuController#stack` never consults `stacks`.

### Impact Explanation
An authenticated but otherwise unprivileged Shipit user obtains a durable, reusable API token that discloses build/deploy status metadata (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`, lock state) for **every stack in the Shipit instance**, including private/unrelated repositories they have no access to. This is a cross-tenant/cross-repository read of stack state using a credential the platform believed was scoped to a single stack — matching the "High: unauthorized read of stack state" category. It does not by itself allow mutation, deploy, or RCE, but it is a full authorization-scope break (`stack_id` scoping is meant to be the sole boundary for third-party/limited API clients, and here it is nil for a client that should have been bound to one stack).

### Likelihood Explanation
Trivial to trigger: any logged-in user (regardless of role, team membership, or repository permission) can click "Fetch URL" once for any stack they can see, extract the `token` query parameter from the JSON response, and immediately reuse it against `/api/stacks/:other_stack/ccmenu`. No GitHub secrets, webhook secrets, or `api_clients_secret` are needed — the token is legitimately issued by the app itself. It is fully repeatable and requires zero special configuration beyond default Shipit setup.

### Recommendation
- Include `stack:` in both `create_with` and `find_or_create_by!` so the `ApiClient` is scoped per (creator, stack) pair, e.g. `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, stack: stack, name: 'CCMenu Client')`.
- Additionally fix `Api::CCMenuController#stack` to use the scoped `stacks.from_param!(params[:stack_id])` (inherited helper) instead of the unscoped `Stack.from_param!`, so that stack-scoped `ApiClient`s are actually enforced for this endpoint.

### Proof of Concept
```ruby
# test/controllers/ccmenu_url_controller_test.rb (conceptual, no live GitHub required)
test "ccmenu url token for stack A must not authorize reading stack B" do
  stack_a = shipit_stacks(:shipit)
  stack_b = Stack.create!(repository: Repository.new(owner: "foo", name: "bar"), branch: "main")

  session_login_as(shipit_users(:walrus)) # authenticated, unprivileged user
  get :fetch, params: { stack_id: stack_a.to_param }
  assert_response :ok
  token = URI(JSON.parse(response.body)["ccmenu_url"]).query[/token=([^&]+)/, 1]

  client = ApiClient.find_by!(name: 'CCMenu Client', creator: shipit_users(:walrus))
  # Binding under test:
  assert_equal stack_a.id, client.stack_id, "client minted for stack A must be scoped to stack A"

  get :show, controller: 'shipit/api/ccmenu', params: { stack_id: stack_b.to_param, token: token }
  assert_response :forbidden # or :not_found — must NOT be :ok for an unrelated stack
end
```
Both assertions currently fail against the shown code: `client.stack_id` is `nil` (not `stack_a.id`), and the second request returns `200 OK` with stack B's CCMenu XML instead of being rejected.
