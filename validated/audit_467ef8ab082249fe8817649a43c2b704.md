### Title
AA composer silently drops payment messages for fixed-denomination (indivisible) assets after AA state changes are already computed, permanently freezing those assets in the AA - (File: aa_composer.js)

### Summary
The Sherlock report describes a class of bug where an irreversible action (burning tokens on the source chain) is committed before it is verified that the corresponding action on the destination side (crediting the recipient) can actually succeed, leading to permanent, unrecoverable loss of funds. The analogous root cause in `ocore` exists in the Autonomous Agent (AA) response composer: an AA's formula-computed messages and state changes are evaluated as if a `payment` message for a fixed-denomination asset will be sent, but the composer then silently discards that very message, with no bounce and no correction of the AA's internal bookkeeping, permanently trapping the asset in the AA.

### Finding Description
When an AA trigger is processed, `aa_composer.js`'s `handleTrigger()` first runs `evaluateAA()` to compute `template.messages` (including the special `state` message that updates `stateVars`/`var[...]`), based purely on the AA's oscript logic (e.g., a `payment` message intended to forward a previously received fixed-denomination/indivisible asset out of the AA) [1](#0-0) .

Later, inside `sendUnit()`, while iterating the resulting messages to build the actual response unit, any payment message referencing an asset with `fixed_denominations` is explicitly skipped from being completed (no inputs/outputs picked, no proof built): [2](#0-1) 

And after all messages are processed, any remaining payment messages that reference a fixed-denomination asset are filtered out entirely from the composed unit before it is built and validated: [3](#0-2) 

This mirrors the design restriction that AAs cannot issue fixed-denomination/private assets themselves [4](#0-3)  and that AA-defined assets are barred from being both private and fixed-denomination [5](#0-4) , but there is no equivalent restriction preventing an AA from *receiving* a fixed-denomination asset (e.g., an NFT-like indivisible coin sent to it by a user or another AA) and later attempting to forward or refund it via a `payment` message in its own logic.

The critical flaw is the ordering: the `state` message (and any other state var updates) is computed by `evaluateAA()` *before* the composer decides to drop the fixed-denomination payment message, and `executeStateUpdateFormula()` is invoked later in the same `sendUnit()` flow, independent of whether the payment message survived the filtering step [6](#0-5) . If the AA's oscript logic assumes the payment succeeded (e.g., decrementing an internal ledger var, marking a claim as fulfilled, or emitting a `response` field indicating the asset was sent), that assumption becomes permanently wrong: the asset never leaves the AA, yet the AA's own state believes it did. Because this filtering behavior is deterministic and occurs on every trigger, there is no future trigger or retry path within AA logic that can ever successfully transfer that asset back out — the asset is permanently stuck at the AA's address with no protocol-level mechanism to move it, analogous to `avail.burn()` executing irrevocably while the corresponding cross-chain credit can never be completed.

### Impact Explanation
This falls under "AA fund loss or freezing" from the validation criteria. Any AA that is designed to accept and later relay/refund an indivisible (fixed-denomination) asset — e.g., a marketplace, custody, or escrow AA handling NFT-like tokens — will have those assets permanently locked at its address once such a payment message is generated, while its own internal accounting (state vars, `response` fields) will report the transfer as completed. This can mislead users/integrators into believing the asset was moved (or refunded) when it was not, and there is no way within the AA's own logic to recover it, since the composer will silently drop the same kind of message every time.

### Likelihood Explanation
This is triggered by ordinary AA authors writing normal-looking oscript logic that includes a `payment` message with an asset whose `fixed_denominations` flag is `true`, something not explicitly disallowed for arbitrary (non-AA-issued) assets by `aa_validation.js`'s AA-definition-time validation of `payment` outputs — the restriction on fixed-denomination assets is only enforced for assets *issued by* the AA, not for pre-existing fixed-denomination assets an AA merely receives and later tries to pay out. Any user or attacker can trigger this simply by sending a fixed-denomination asset to an AA that attempts to forward/refund it, or by designing/depositing into an AA whose oscript author was unaware of this silent-drop behavior.

### Recommendation
The composer should not silently discard `payment` messages for fixed-denomination assets after the AA's state-changing logic has already run. Instead, `aa_validation.js` should reject AA definitions at validation time if any `payment` message can reference a fixed-denomination asset (making the current runtime silent-drop unreachable), or `aa_composer.js` should treat encountering such a message as a hard bounce (reverting all state changes for that trigger, consistent with how other message-processing errors are handled via `bounce(err)`), rather than only filtering it out post hoc while other state changes are already committed.

### Proof of Concept
1. Define an existing public, transferable, fixed-denomination asset `X` (not issued by any AA) with a valid `asset_denominations` schedule.
2. Deploy an AA whose oscript logic accepts asset `X` as a trigger input and, in response, attempts to forward/refund the same asset `X` via a `payment` message while also updating a state var (e.g., `var['refunded_' || trigger.unit] = true;`) or emitting `response['refunded'] = true;`.
3. Send an amount of asset `X` to the AA as a trigger.
4. Observe that `aa_composer.js` skips the fixed-denomination payment message at lines 1327-1330, then filters it out entirely at line 1356 (no bounce occurs, and `handleSuccessfulEmptyResponseUnit`/normal flow continues if other messages remain) [7](#0-6) , while the `state` message and its `var['refunded_...']=true`/`response['refunded']=true` are still applied via `executeStateUpdateFormula` [8](#0-7) .
5. Confirm asset `X` remains held at the AA's address indefinitely (`balance[X]` at the AA never decreases), while the AA's `var`/`response` state falsely reports the refund/forward as completed — matching the "burn without ability to credit" loss pattern from the original report.
