### Title
Missing cosigner authorization check on `sign` requests allows any paired device to solicit signatures for shared-address units - ([File: wallet.js])

### Summary
`wallet.js`'s `handleMessageFromHub` implements the `sign` command that lets a remote device ask the local wallet to co-sign an arbitrary unsigned unit for a given `address`/`signing_path`. In the `ifLocal` branch, the check that would verify the requesting device (`from_address`) is actually a registered cosigner/extended-pubkey holder of that address's wallet is commented out, leaving the endpoint reachable by **any** correspondent device without proof that it is entitled to request a signature for that address. [1](#0-0) 

### Finding Description
The `sign` subject handler validates the shape of the request (`address`, `signing_path`, `unsigned_unit`, `private_payloads`, etc.) but does not verify authorization of the sender against the actual membership of the multisig/shared address. In `findAddress(...).ifLocal`, the intended authorization check is explicitly disabled: [2](#0-1) 

Once accepted, the handler either fires the `signing_request` event (used by wallet UIs to prompt a confirmation dialog) or, for JSON-based units, calls `network.handleOnlineJoint` after validation succeeds and then emits `signing_request` as well: [3](#0-2) 

The comment states the check "would make multilateral signing impossible," implying it was deliberately dropped to support the "multilateral signing" use case (different addresses cosigning the same message/contract), rather than being an oversight limited to a narrow feature. However, as written, the check removal applies to **all** `sign` requests for **any** local address, not just the multilateral-signing use case — meaning any paired ("correspondent") device, even one with no legitimate relationship to a specific shared/multisig address held by the victim, can submit a `sign` request naming that address and an arbitrary `unsigned_unit`/`signing_path`, and the local node will process it as if the sender were a valid cosigner (subject only to structural validation of the unit, not to sender legitimacy for that address).

This is analogous to the rdiffweb CVE-2022-4314 issue: a state-changing/sensitive operation (soliciting a wallet signature over an attacker-supplied transaction) is reachable by a principal (any paired correspondent) who is not authorized to perform it for the target resource (a specific multisig address), because the authorization/ownership check was removed rather than properly scoped.

### Impact Explanation
Reachability is limited to devices that are already paired correspondents of the victim wallet (an unprivileged but not fully-anonymous "paired device" per the analog scope). From that vantage point, an attacker-controlled correspondent can:
- Flood the victim's wallet with spoofed signing requests for addresses it does not co-own, potentially causing UI clutter/DoS of the confirmation flow, or
- More critically, craft `unsigned_unit` payloads that redirect outputs, alter amounts, or reference attacker-chosen `private_payloads` for a shared/multisig address the victim actually is a cosigner of, and have the local wallet treat the request as legitimate up to the point of surfacing a `signing_request` event — increasing the chance a user is tricked into approving a malicious transaction that appears to originate from a legitimate cosigning flow rather than an unverified third party (since the missing check would normally have rejected it outright before ever reaching the user).

Because final approval typically still requires a human to confirm in the wallet UI, this does not by itself achieve fully automated fund theft, but it removes a server-side authorization guardrail that was explicitly designed to prevent non-cosigners from participating in a given address's signing workflow at all, which is a legitimate improper-privilege-management weakness under the reported bug class.

### Likelihood Explanation
Any two devices that have completed device pairing (a normal, low-friction operation in ocore) can trigger this path — no special hub, node-operator, or address-holder privilege is required. Because the check is fully removed at the code level, the exploit does not rely on race conditions or version-specific bugs, only on the attacker knowing (or guessing) a target `address` and constructing a structurally valid `unsigned_unit`.

### Recommendation
Restore and generalize the cosigner-membership check before invoking `callbacks.ifOk()`/emitting `signing_request` in the `sign` handler: verify that `from_address` is a member of `wallet_signing_paths`/`extended_pubkeys` for `body.address` (directly or transitively, to preserve legitimate multilateral-signing use cases), and reject the request otherwise. If multilateral signing genuinely requires accepting requests from non-cosigner devices for a *different* address in the same message, scope that exception narrowly (e.g., only for `signed_message` flows) rather than disabling the check for standard payment-unit signing requests.

### Proof of Concept
1. Device B pairs with Device A (normal, unprivileged pairing flow).
2. Device A is a cosigner of shared/multisig address `SHARED_ADDR` together with Device C (not paired with B).
3. Device B sends a `sign` message to Device A:
```json
{
  "subject": "sign",
  "body": {
    "address": "SHARED_ADDR",
    "signing_path": "r.0",
    "unsigned_unit": { "version": "...", "authors": [{"address": "SHARED_ADDR", "authentifiers": {"r.0": "----...----"}}], "messages": [ /* attacker-crafted payment outputs */ ] }
  }
}
```
4. Device A's `handleMessageFromHub` -> `sign` case -> `findAddress(...).ifLocal` accepts the request without checking that Device B is a listed signer of `SHARED_ADDR`, and emits `signing_request`, presenting the attacker-controlled transaction to Device A's user for signing under the guise of a normal cosigning workflow. [4](#0-3)
